### Title
Shell metacharacter injection via `Build.FullProjectDir()`/`TmpProjectDir()` in `executeChownOnDir` chown command when `FF_DISABLE_UMASK_FOR_DOCKER_EXECUTOR` is enabled - (File: executors/docker/docker_command.go)

### Summary
`executeChownOnDir` builds a shell command string with Go's `%q` verb and feeds it as stdin to a helper container whose entrypoint is `/bin/bash` (no `-c`, no argv separation), meaning the string is parsed by bash as shell syntax, not passed as a literal argv element. Go's `%q` only performs Go-string-literal escaping (backslash/quote/control chars) — it does **not** escape `$`, backticks, or other bash metacharacters — so a project directory value containing `$(...)` or backticks will trigger command substitution inside the helper container.

### Finding Description
`executeChownOnDir` (`executors/docker/docker_command.go:389-418`) constructs:
```go
Stdin: strings.NewReader(fmt.Sprintf("chown -RP -- %d:%d %q", uid, gid, dir))
``` [1](#0-0) 

`dir` is `s.Build.FullProjectDir()` or `s.Build.TmpProjectDir()`, called from `executeChown`: [2](#0-1) 

This stdin content is delivered via `exec.Docker.Exec` (`executors/docker/internal/exec/exec.go`), which uses `ContainerAttach`+`ContainerStart` and pipes `streams.Stdin` directly into the container's process: [3](#0-2) 

The helper container's `Cmd` in this code path (only reachable when `isUmaskDisabled()` is true, which is exactly the precondition for `changeFilesOwnership`/`executeChown` to run) is `/bin/bash` with no arguments: [4](#0-3) 

Since the container's entrypoint is bare `bash`, everything written to its stdin is parsed and executed as shell script — this is not an "exec with argv" call where quoting is irrelevant; it is a genuine shell interpretation of the composed string. Go's `%q` formatting quotes `dir` using Go/C-style escaping of `"`, `\`, and control characters, but leaves `$` and `` ` `` untouched. Bash's double-quote parsing treats `$(...)` and backticks as command substitution even inside double quotes. Therefore, if `dir` contains a sequence like `$(id > /tmp/pwn)` or a backtick command, the resulting bash invocation will execute that embedded command in the helper container (typically running as root) as a side effect of `chown`.

`FullProjectDir`/`TmpProjectDir` are derived from the build directory path, which is influenced by job-controllable inputs such as `GIT_CLONE_PATH` (validated only for staying within the builds root / no `..` traversal, not for shell metacharacters) and `CI_PROJECT_DIR`-related path composition. I was not able to fully re-verify the exact `GIT_CLONE_PATH`/project-dir sanitization routine in this session (the relevant validator file wasn't retrieved), so I cannot state with certainty that no metacharacter filtering exists there — this is the main residual uncertainty in this finding.

### Impact Explanation
If the project directory path is attacker-influenced and passes through unfiltered, an unprivileged pipeline author could achieve arbitrary command execution inside the helper container (running as root in the umask-disabled path), beyond the intended `chown` operation. This is a runner-side command execution issue distinct from the job's authored script/payload, matching the scoped impact ("script generation/quoting causes runner-side command execution outside the authored job payload").

### Likelihood Explanation
Preconditions: (1) `FF_DISABLE_UMASK_FOR_DOCKER_EXECUTOR` must be enabled on the runner, which gates both `isUmaskDisabled()` (making `executeChown` reachable) and the helper container's `/bin/bash` entrypoint. (2) The attacker must be able to make `FullProjectDir()`/`TmpProjectDir()` contain a `$(...)` or backtick payload, e.g., via `GIT_CLONE_PATH`, which is job-variable controlled. Because (1) depends on an explicit, non-default runner configuration choice, exploitability is conditional rather than universal, but once that flag is set, any pipeline author on that runner could attempt the injection — this is not an "admin compromise" scenario, it's a normal job author abusing a supported job variable.

### Recommendation
Do not build shell command strings with `fmt.Sprintf` + `%q` for execution via a bare shell entrypoint. Either:
- Pass the chown command as an argv list (`Cmd: []string{"chown", "-RP", "--", fmt.Sprintf("%d:%d", uid, gid), dir}`) executed without invoking a shell, or
- If a shell must interpret stdin, properly shell-quote `dir` (e.g., single-quote it and escape embedded single quotes, `strings.ReplaceAll(dir, "'", `'\''`)`), instead of relying on Go's `%q`, which is not shell-safe.
Additionally, validate/reject directory path values containing shell metacharacters (`$`, `` ` ``, `;`, `|`, newline) wherever `GIT_CLONE_PATH`/project dir values are accepted from job configuration.

### Proof of Concept
Go unit test idea for `executeChownOnDir` (or an integration test mocking `exec.Docker`):
```go
func TestExecuteChownOnDir_ShellInjection(t *testing.T) {
    mockExec := new(exec.MockDocker)
    var capturedStdin string
    mockExec.On("Exec", mock.Anything, mock.Anything, mock.MatchedBy(func(s exec.IOStreams) bool {
        b, _ := io.ReadAll(s.Stdin)
        capturedStdin = string(b)
        return true
    }), mock.Anything).Return(nil)

    s := &commandExecutor{ /* minimal setup */ }
    maliciousDir := `/builds/group/project$(touch /tmp/pwned)`
    err := s.executeChownOnDir(&container.InspectResponse{ID: "c1"}, mockExec, 1000, 1000, maliciousDir)
    require.NoError(t, err)

    // Assert the generated stdin, when parsed by bash, contains an unescaped $() substitution
    assert.Contains(t, capturedStdin, `$(touch /tmp/pwned)`)
    // This proves %q did not neutralize the metacharacter; a bash-driven helper container
    // executing this stdin would run `touch /tmp/pwned`.
}
```
