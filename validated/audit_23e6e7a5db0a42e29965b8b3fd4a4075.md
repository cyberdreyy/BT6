### Title
Front-runnable multisig account names in `MultisigFactory::create` allow an attacker to deploy an attacker-controlled multisig under a victim's intended account name - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` derives the multisig sub-account solely from a caller-supplied `name` and immediately issues `create_account`/`deploy_contract`/`new` without ever checking whether `name.<factory>` is already taken or reserved for a specific intended set of `members`. [1](#0-0)  Any unprivileged actor can observe a pending `create` call for a given `name` (via mempool/cross visibility, the same "front-run any operation seen" mechanism described in the source report for `loanId`) and submit their own `create` call with that same `name` but with themselves as the sole member and `num_confirmations = 1`. Because NEAR subaccount creation is first-come-first-served, whichever `create` lands first permanently claims `name.<factory>` with its own `members`/`num_confirmations`, and the legitimate caller's later `create_account` action fails.

### Finding Description
The equality that should hold is: *the multisig account deployed at `name.<factory>` is governed by the `members`/`num_confirmations` that the party who reserved `name` intended*. In `create`, `name` is fully attacker-controllable and there is no on-chain reservation, allow-list, or existence check comparable to the de-duplication used in `staking-pool-factory::create_staking_pool` (`self.staking_pool_account_ids.insert(...)`) [2](#0-1) . `multisig-factory::create` has no equivalent guard:

```
let account_id = format!("{}.{}", name, env::current_account_id());
Promise::new(account_id)
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(b"new".to_vec(), json!({ "members": members, "num_confirmations": num_confirmations }) ... )
``` [3](#0-2) 

Because the `create_account` action targets a deterministic name chosen entirely by the caller, and the predecessor for the action is the factory itself (not the caller), any address can race to claim any `name`. Once created, control of the multisig is entirely determined by the `members`/`num_confirmations` supplied in that winning call — governed by `confirm`'s signer-key check in `multisig/src/lib.rs` (`assert_valid_request`/`confirm`) [4](#0-3) . An attacker who wins the race sets `members = [{ "public_key": <attacker key> }]`, `num_confirmations = 1`, giving themselves unilateral control (`Transfer`, `AddKey`, `FunctionCall`, etc.) over anything later sent to `name.<factory>`.

### Impact Explanation
Before the attacker's call: `name.<factory>` does not exist; the intended party has not yet deployed their multisig. After the attacker's front-running call: `name.<factory>` exists, is controlled solely by the attacker's key, with `num_confirmations = 1`. Any NEAR later transferred to that address — by the original deployer retrying, by counterparties who trusted the name as belonging to the intended owners, or by the victim's own subsequent deposits before noticing the account already exists — can be moved out unilaterally by the attacker via a single `confirm` call. This is a wrongly-parameterised deployment that lets NEAR be moved by a party not entitled to it, matching the Critical impact class (wrongly parameterised deployment / unauthorized fund movement).

### Likelihood Explanation
No privileged role, victim key, or social engineering is required. The attacker only needs to observe a pending `create` call (or simply race common/predictable names) and submit their own `create` transaction with higher priority/gas — a purely permissionless, unprivileged action, directly analogous to the `loanId` front-running described in the source report, except here the winning party gains custody of the resulting account rather than merely denying service.

### Recommendation
Before issuing `create_account`, check that `name.<current_account_id>` does not already exist (e.g., mirror the `staking_pool_account_ids` de-duplication set used by `staking-pool-factory`), and/or require the deployment to bind `name` to a claim made in an earlier, separate step (e.g., a commit-reveal or a reservation tied to `predecessor_account_id`) so that only the party who legitimately reserved the name can supply its `members`.

### Proof of Concept
1. Victim intends to deploy a multisig at `alice.multisig-factory` with `members = [victim's keys]`, `num_confirmations = 2`, and submits a `create` transaction.
2. Attacker observes this pending transaction (or simply predicts the desired `name`) and submits their own `create("alice", [{"public_key": attacker_key}], 1)` with higher gas price so it is included first.
3. `alice.multisig-factory` is created and deployed with the attacker's `members`/`num_confirmations`, per `multisig-factory/src/lib.rs` lines 29-49.
4. Victim's original transaction now fails at the `create_account` action since `alice.multisig-factory` already exists.
5. Anyone who subsequently transfers NEAR to `alice.multisig-factory` believing it is governed by the victim's intended members can have those funds moved out unilaterally by the attacker calling `confirm` with their sole key (`num_confirmations = 1`), per `multisig/src/lib.rs` lines 246-266.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
