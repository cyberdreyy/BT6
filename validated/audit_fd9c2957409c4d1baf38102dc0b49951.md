### Title
Division-before-multiplication in `_calcInterestWithApr` truncates epoch interest to zero/dust, underpaying withdraw receipts and mid-epoch deposits - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant._calcInterestWithApr` divides the scaled APR by `100` **before** multiplying by `_amount` and `epochDuration`. This is the same bug class as the Ajna report: an intermediate `wdiv`-style operation collapses the numerator before the large multiplications can amplify it. The result feeds `depositDuringEpoch` and the withdraw-request interest path, so withdraw receipts and mid-epoch discounted mints are systematically underpaid, with the missing interest left in NAV for remaining holders. [1](#0-0) 

### Finding Description
The interest formula is:

```solidity
// contracts/IdleCDOEpochVariant.sol:807-809
function _calcInterestWithApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
    return _amount * (_apr / 100) * epochDuration / (365 days * ONE_TRANCHE_TOKEN);
}
```

`_apr / 100` executes first in integer arithmetic. Two consequences:

1. **Zero-interest epochs**: whenever the stored APR is below `100` in its stored units (i.e. the APR is a fractional-percent value with respect to the `100` divisor — e.g. a 0.5% APR encoded as `50`), `_apr / 100 == 0`, so the whole expression is `0` regardless of `_amount` or `epochDuration`. All interest computed through this path is silently zero.
2. **Fractional-percent truncation**: for any APR not an exact multiple of `100` (e.g. `350` for 3.5%), up to `99` APR units are dropped before multiplication — a relative loss of up to ~`99/_apr` that is then amplified by `_amount * epochDuration`.

This helper is called by `_calcInterest` (`IdleCDOEpochVariant.sol:800-802`), which feeds:

- `depositDuringEpoch` (`IdleCDOEpochVariant.sol:693-728`): `interest` is added to `expectedEpochInterest` and, via `trancheInterest`, to the mint numerator `(_amount + trancheInterest) * _trancheTotSupply / expectedFinal`. A truncated interest mints fewer shares to the depositor than fair value — the depositor is underpaid and the shortfall accrues to existing tranche holders' NAV.
- The withdraw-request interest path (`requestWithdraw` → `_calcInterestWithdrawRequest` → `_calcInterest`, around `IdleCDOEpochVariant.sol:773-776`): the receipt `principal + interest - totalFees` is fixed at request time via `creditVault.requestWithdraw(_underlyings, msg.sender, principal)`. Understated `interest` permanently shrinks the payout the requester can claim at `claimWithdrawRequest`, while `interestForOverUnderPerformance` (`diff`) and `pendingWithdrawFees` are skewed correspondingly.

No guard stops this: `_skimDonatedAssets`, `isWalletAllowed`, epoch-phase checks and `Default` reverts do not constrain the arithmetic, and the truncation happens on every call in a low/fractional-APR configuration. The manager setting a fractional-percent APR is an honest privileged action; the loss then applies deterministically to every unprivileged user transacting.

### Impact Explanation
Direct theft/loss of unclaimed yield with quantified magnitude:

- With APR stored such that `_apr < 100` (sub-1% fixed-APR epoch), a requester withdrawing principal `P` receives `P` instead of `P + interest`; the full epoch interest for that position (~`P * apr * epochDuration / 365d`) stays in pool NAV and is captured by remaining AA/BB holders. Broken invariant: fair mint/burn / one-receipt-one-payout — the receipt is permanently fixed too low at `requestWithdraw` and cannot be corrected later because `pendingWithdraws` is already set.
- With `_apr = 350` (3.5%), the computed APR is `3`, so ~14% of every withdrawer's epoch interest is forfeited to the residual holders each epoch — repeatable and unbounded per epoch.

### Likelihood Explanation
Medium. It requires only that the configured vault APR contain a fractional-percent component (any `_apr % 100 != 0`) — a normal, honest parameter choice — and that a user calls `requestWithdraw` or `depositDuringEpoch` during a running epoch/buffer window. No attacker privilege, no oracle manipulation, no edge-case timing is needed; every eligible user is affected automatically. The main caveat is that the exact magnitude depends on the APR unit convention chosen at `IdleCreditVault.initialize` (`lastApr`/`unscaledApr`); if APR is 1e18-scaled the truncation is dust, but if APR is stored in percent-hundredths (the encoding implied by the `/100` divisor, consistent with `_apr / 100` appearing in the fork tests' mirror function `_calcInterestAtApr`) the loss is material. [2](#0-1) 

### Recommendation
Reorder to multiply-first, divide-last, preserving full precision:

```solidity
function _calcInterestWithApr(uint256 _amount, uint256 _apr) internal view returns (uint256) {
    return _amount * _apr * epochDuration / (100 * 365 days * ONE_TRANCHE_TOKEN);
}
```

Apply the same ordering in the withdraw-request interest computation (`totInterest * _trancheAprRatio / FULL_ALLOC` and `_amount * totTrancheinterest / _instantBalance` chain) and audit `depositDuringEpoch`'s proration `(remaining + buffer) / (epochDuration + buffer)` — it already multiplies before dividing and is correct, but should be kept consistent after the fix.

### Proof of Concept
Foundry fork sketch (adapt to the repo's `IdleCreditVault.t.sol` harness, which already wires `idleCDO`, `AAtranche`, `underlying`, `strategy`):

```solidity
function test_interestTruncatedToZero_lowApr() public {
    // owner/manager sets a sub-1% APR, e.g. 0.5% encoded as 50 units
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setApr(50);   // _apr = 50

    uint256 amount = 1_000_000 * ONE_SCALE;          // 1M underlying
    // expected: ~ amount * 0.005 * epochDuration / 365 days  (> 0)
    uint256 interest = cdoEpoch.exposed_calcInterest(amount); // wrap _calcInterest
    assertEq(interest, 0);                            // BUG: 50/100 == 0 -> interest lost

    // withdraw-request path: user requests withdraw during allowed window
    vm.prank(owner); cdoEpoch.startEpoch(...);        // epoch running, apr stored
    // warp into buffer where allowAAWithdrawRequest is true
    uint256 receipt = cdoEpoch.requestWithdraw(userAATokens, address(AAtranche));
    // receipt == principal only; pendingWithdraws fixed too low;
    // claimWithdrawRequest later pays no interest while residual holders keep it.
}

function test_fractionalApr_truncation() public {
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setApr(350);  // 3.5%
    uint256 amount = 1_000_000 * ONE_SCALE;
    uint256 got = cdoEpoch.exposed_calcInterest(amount);
    uint256 expected = amount * 350 * cdoEpoch.epochDuration() / (100 * 365 days * ONE_TRANCHE_TOKEN);
    assertLt(got, expected);                         // ~14% of interest forfeited
}
```

Both cases demonstrate the broken fair-payout invariant on idle-tranches' own accounting path: division (`_apr / 100`) before multiplication zeroes or shrinks `interest`, and since `requestWithdraw` crystallizes the receipt and `depositDuringEpoch` crystallizes the mint at call time, the shortfall is permanent for the transacting user and accrues to remaining tranche NAV.
