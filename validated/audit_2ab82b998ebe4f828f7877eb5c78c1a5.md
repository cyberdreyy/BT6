### Title
Loss-adjusted withdraw receipt is silently upgraded to par when the user makes a second withdraw request — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks loss-adjusted receipts per epoch (`lossRecoveryPriceByEpoch`, `withdrawsRequestsByEpoch`), but the claim path looks up the loss price using only `lastWithdrawRequest[_user]` — a single slot overwritten on every new `requestWithdraw`. If a user has a haircut receipt from epoch X and then requests another withdrawal in epoch Y, the haircut ledger for epoch X becomes unreachable ("freed" from lookup while its basis survives in the aggregate `withdrawsRequests`), and `_claimFundedWithdrawRequest` pays the full aggregate at par. This is a use-after-free analog: stale per-epoch loss data is orphaned while the aggregate still spends against it.

### Finding Description
- On `requestWithdraw`, the vault mints a receipt and records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` [1](#0-0) .
- On a `stopEpochWithDuration` loss, `collectWithdrawFunds` funds only `_amount < pendingBasis` and stores `lossRecoveryPriceByEpoch[epochNumber]` [2](#0-1) .
- At claim time, `_claimLossAdjustedWithdrawRequest` only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) . If `lastWithdrawRequest` now points to a later, fully-funded epoch, the price is 0 and the function returns without clearing epoch X's `withdrawsRequestsByEpoch` entry.
- Control then falls to `_claimFundedWithdrawRequest`, which after the newer epoch ends pays `withdrawsRequests[_user]` — the aggregate including the haircutted epoch-X amount — at full par [4](#0-3) .

The broken invariant is the loss waterfall / "one receipt one payout": the strategy only received `W1 * lossRecoveryPrice + W2` from the borrower, but pays out `W1 + W2`. The shortfall `W1 * (1 - lossRecoveryPrice)` is taken from underlying held for other claimants' receipts and default reserve.

### Impact Explanation
An attacker (any KYC'd tranche holder) extracts `W1 * (1 - lossRecoveryPrice)` of underlying beyond their entitlement, directly stealing funds reserved for other users' pending withdraw receipts. With e.g. a 50% recovery price, each haircut receipt re-requested before claiming nets a 50%-of-principal theft. No privileged role misbehavior is required; the sequence uses only unprivileged calls around honest `stopEpochWithDuration`/`stopEpoch` executions.

### Likelihood Explanation
Likelihood is moderate: it requires a `stopEpochWithDuration` partial loss (an intended, manager-invoked mode), and the code comments explicitly document that users who "request another withdraw" before claiming "will have to wait for another epoch to claim both requests" [5](#0-4)  — i.e., the exact precondition is a supported, advertised user flow, not an edge case. Once the loss epoch exists, any user can trigger it deterministically.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, don't key the loss lookup solely on `lastWithdrawRequest`. Either iterate/check `withdrawsRequestsByEpoch` against all epochs with non-zero `lossRecoveryPriceByEpoch` (e.g., also check epochs older than `lastWithdrawRequest`), or record a per-user loss-epoch marker that isn't overwritten by new requests. Alternatively, revert in `requestWithdraw` if the user has an unclaimed loss-adjusted receipt, forcing them to claim the haircut first.

### Proof of Concept

```solidity
// 1. Deposit and request withdraw W1 while epoch running.
idleCDO.depositAA(amount);
_toggleEpoch(true, 0, 0);
cdoEpoch.requestWithdraw(W1, address(AAtranche)); // epoch X

// 2. Epoch X ends with partial loss: manager calls stopEpochWithDuration
//    so collectWithdrawFunds(_funded < pendingBasis) stores
//    lossRecoveryPriceByEpoch[X] = price < RECOVERY_FULL.
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpochWithDuration(apr, interest, duration, loss);

// 3. Do NOT claim. Request a second withdraw W2 in the new epoch.
//    lastWithdrawRequest[user] is overwritten to Y; epoch-X per-receipt
//    entry survives but is no longer reachable via the loss lookup.
_toggleEpoch(true, 0, 0);
cdoEpoch.requestWithdraw(W2, address(AAtranche)); // lastWithdrawRequest = Y

// 4. Epoch Y ends fully funded.
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpoch(0, 0);

// 5. Claim: _claimLossAdjustedWithdrawRequest sees
//    lossRecoveryPriceByEpoch[Y] == 0, returns 0 without clearing X.
//    _claimFundedWithdrawRequest pays withdrawsRequests[user] = W1 + W2 at par.
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;

// Strategy only received W1 * price + W2; assert overpayment:
assertEq(paid, W1 + W2);                    // paid at par
assertLt(strategyUnderlyingBalance, expectedReserveForOthers); // drained
assertGt(strategy.withdrawsRequestsByEpoch(user, X), 0); // X entry was never cleared... 
// (in the buggy path it IS still non-zero until _claimFundedWithdrawRequest
//  zeroes the aggregate, leaving the haircut basis unpaid at source)
```

Expected: `paid == W1 + W2` while the strategy's funded balance is only `W1 * lossRecoveryPrice / 1e18 + W2`, leaving other users' receipts underfunded by `W1 * (1 - lossRecoveryPrice / 1e18)`.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
