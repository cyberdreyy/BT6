### Title
Client-controlled `requestID` reuse allows a late/stale DON node response to be aggregated into an unrelated attacker execution after `reapExpiredCallbacks` deletes the original entry - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler.callbacks` is keyed solely by the client-supplied JSON-RPC `id` (`requestID`) with no binding to workflow owner, workflow ID, or a server-generated nonce/generation counter. `reapExpiredCallbacks` deletes an expired entry from this map, and `setupCallback` immediately allows a brand-new (possibly unrelated) request to reuse the exact same `requestID` string, after which `HandleNodeTriggerResponse` matches any late-arriving node response for that ID against whichever callback currently occupies the map.

### Finding Description
`setupCallback` only rejects a `requestID` if it is *currently* present in `h.callbacks` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:402-405`); it performs no check against recently-expired IDs. `reapExpiredCallbacks` (`http_trigger_handler.go:527-544`) removes entries once `now.Sub(callback.createdAt) > CleanUpPeriodMs` and calls `cleanupCallback`, which just closes `doneCh` and `delete`s the map entry (`http_trigger_handler.go:439-446`) — it does not notify the original caller, and it does not "reserve" the ID to prevent reuse.

`HandleNodeTriggerResponse` (`http_trigger_handler.go:448-496`) looks up `h.callbacks[resp.ID]` purely by the string ID, resolves the responding node to a shard via the static `nodeAddrToShard` map, and feeds the response into `saved.responseAggregators[shard.donID]` — an `IdenticalNodeResponseAggregator` (`core/services/gateway/common/aggregation/response_aggregator.go:38-75`) that aggregates strictly by matching a response digest across a threshold of distinct node addresses, with no per-execution nonce embedded in the response and no check that the response actually corresponds to the currently-stored `savedCallback`'s originating workflow/owner.

Because a client fully controls its own `req.ID`, an authorized (non-privileged) caller can deliberately choose a `requestID` equal to one it knows/predicts will soon be reaped for another user's request, and call `setupCallback` immediately after the reap. A stale response from a slow DON node for the original (now-deleted) request, arriving after this window, will be routed into the new caller's `saved.responseAggregators` because the lookup is purely by string key. If the attacker also targets the same public `workflowID`/deterministic input (so the digest of the stale node response matches digests the attacker's own request is collecting), that stale vote can contribute toward the attacker's quorum threshold, letting an unrelated, one-node vote from a foreign execution context count toward completing the attacker's request — a violation of "request binding across time" for the callback map.

### Impact Explanation
This falls into the "cross-user response confusion" impact class: a response bound to one execution context (workflow/owner/callback) can be attributed to a different, unrelated execution merely because both requests reused the same client-chosen `requestID` across the reap boundary. In the best case for an attacker this reduces the effective number of live/independent nodes needed to satisfy their own quorum (undermining the DON's fault-tolerance/quorum guarantee for that request), and in the worst case a caller could receive an aggregated response containing a stale vote it should not have received. The impact is bounded by the coincidence needed for the stale response's content digest to match, and does not by itself leak secret data, since `IdenticalNodeResponseAggregator` requires exact digest matches to count towards quorum.

### Likelihood Explanation
Exploitability requires: (1) the attacker to be an authorized workflow caller able to submit `workflows.execute` (no elevated role needed, satisfying the "unprivileged" constraint), (2) knowledge or successful prediction of a `requestID` that is about to be reaped for another party's request (acknowledged as a precondition — it depends on the *victim's own client* using low-entropy/sequential IDs, which the node does not enforce nor prevent), and (3) tight timing between the reap tick and setupCallback vs. the arrival of a late node response, plus (for a meaningful "vote steal") a matching response digest. This makes the exploit's overall reliability low/moderate and situational rather than deterministic, but the underlying binding weakness in `httpTriggerHandler.callbacks` and `HandleNodeTriggerResponse` is concretely present and independently verifiable via unit test, regardless of how often the full attack chain succeeds in practice.

### Recommendation
Do not key `h.callbacks` purely by the client-supplied `requestID`. Bind callback identity to a server-generated, monotonically-unique composite key (e.g., `workflowID + requestID + generation-nonce`) that is embedded in the request forwarded to nodes and validated on the response path, so a reaped/expired entry's identifier can never be legitimately reused to match a different execution's node responses. Additionally, `cleanupCallback`/`reapExpiredCallbacks` should explicitly notify the original caller with a timeout error rather than silently dropping the entry, and `HandleNodeTriggerResponse` should verify that the responding shard/workflow context matches what was recorded at `setupCallback` time for that specific execution, not merely that some aggregator exists under the current map entry for that donID.

### Proof of Concept
Go unit test plan in `http_trigger_handler_test.go`:
1. Configure `httpTriggerHandler` with a short `CleanUpPeriodMs`/`MaxTriggerRequestDurationMs` and one shard with a set of member nodes.
2. Call `setupCallback(ctx, "X", callbackA, ...)` for "victim" workflow A; capture `doneCh`.
3. Advance time (or fake clock) past `CleanUpPeriodMs` and invoke `reapExpiredCallbacks(ctx)`; assert `h.callbacks["X"]` no longer exists and `doneCh` is closed.
4. Immediately call `setupCallback(ctx, "X", callbackB, ...)` for an unrelated "attacker" workflow B; assert it succeeds (no conflict error) and installs a new `savedCallback` under `h.callbacks["X"]`.
5. Call `HandleNodeTriggerResponse(ctx, resp, nodeAddr)` with `resp.ID = "X"` and a payload from a node belonging to workflow A's original shard/DON (simulating a stale, delayed response for the reaped request).
6. Assert that the response is aggregated into workflow B's (`callbackB`'s) `responseAggregators` and, given a matching digest with previously-collected responses for B, that `callbackB.SendResponse` is invoked — demonstrating that a stale response for a completed/foreign request context (A) was bound to and can affect the outcome of an unrelated new request (B), violating request binding across time.
