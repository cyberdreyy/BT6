### Title
Signer skips its own chainstate/conflict re-check before pushing a block accepted by peer signatures - (File: stacks-signer/src/v0/signer.rs)

### Summary
Every path that puts this signer's own signature over a block, or that acts on reaching a signature/pre-commit threshold, re-runs `check_block_against_signer_db_state` (and, in the pre-commit path, the same-height conflict guard) immediately before acting — except `store_and_process_block_signature`, which is reached when *peer* acceptances push the aggregate signature weight over threshold. That function marks the block locally accepted and immediately broadcasts/pushes it to the node without re-verifying the chainstate/conflict state the way `handle_block_pre_commit` and `handle_block_validate_ok` do.

### Finding Description
The signer's block-lifecycle design (documented in `docs/signer-flows.md` sections 4/5/7) enforces a strict invariant: any time a signature is about to be produced or a block is about to be pushed as accepted, the signer must re-check `check_block_against_signer_db_state` because the world may have moved since the block was first validated (a rival block may have been signed at the same height, in the same or another tenure).

This is implemented consistently in:
- `handle_block_validate_ok` (validate-ok → pre-commit path), which calls `check_block_against_signer_db_state` before `mark_pre_committed` [1](#0-0) .
- `handle_block_pre_commit` (pre-commit threshold → own signature path), which calls `check_block_against_signer_db_state` and then the same-height/any-tenure conflict guard (`get_signed_conflicts`, `conflict_still_blocks`, `reorg_permit_stands`) before `mark_locally_accepted` [2](#0-1) .

But `store_and_process_block_signature`, invoked from `handle_block_signature` when a peer's `BlockAccepted` message is received, does **not** perform either check. It only guards against re-processing the exact same block (`block_info.signed_group.is_some()`) and then, once the aggregate signature weight crosses threshold, unconditionally calls `mark_locally_accepted(true)` and `broadcast_signed_block`, pushing the block to the node: [3](#0-2) 

There is no call to `check_block_against_signer_db_state`, no re-check of `get_signed_conflicts`/`conflict_still_blocks`, and no check of `block_info.valid` before this signer marks the block accepted and hands it to its own node via `broadcast_signed_block`. This breaks the equality the rest of the codebase enforces everywhere else: "a signature is never acted upon without a last-look at this signer's own chainstate view." A signer that has itself already signed a conflicting sibling block (at the same or higher height, in this or another tenure) — a case `handle_block_pre_commit`'s conflict guard exists specifically to prevent — can still be driven, by peer `BlockAccepted` gossip alone, to `mark_locally_accepted` and push a rival, already-signed-against block to its own node.

### Impact Explanation
This affects the safety equality between "validated/consistent-with-local-chainstate" and "acted upon as accepted." If the aggregate 70% weight is reached via peer `BlockAccepted` messages while this signer's own view has moved on (e.g., it has already signed a different block at the same height, per section 5's conflict guard), the missing recheck lets this signer's node receive and attempt to process a block its own state machine would otherwise refuse to sign. This is the same bug class as the phpMyFAQ report — a subset of otherwise-parallel code paths silently omitting the guard that sibling paths correctly apply — mapped onto the safety-relevant "sign/act only after a last look" invariant rather than an authorization check. It does not, on its own, forge a signature from a majority of signers (that still requires genuine acceptances from the honest signer set), so it does not clear the bar of "a signer signing an invalid/non-canonical/conflicting block" outright without further confirmation of what `broadcast_signed_block`/`handle_post_block` and the node's own acceptance path do with a locally-inconsistent-but-already-70%-signed block; I was not able to fully inspect `broadcast_signed_block`/`mark_locally_accepted`'s downstream effects or the node's post-block handling in the remaining budget to confirm whether the node-side ultimately re-validates and would reject such a push. That downstream confirmation is necessary to elevate this from "asymmetric missing guard" to a confirmed Critical/High-impact break.

### Likelihood Explanation
Reaching the aggregate-signature threshold via peer gossip is a normal, one-slot-miner-plus-gossip-reachable event (no majority-signer collusion needed to trigger the code path — only ordinary honest peer traffic under a race where this same signer has independently signed a conflicting block). The precondition (this signer itself has signed a rival block before its own aggregate-threshold count fires) is the same race that `handle_block_pre_commit`'s conflict guard was built to close, indicating the scenario is realistic in practice, not purely theoretical.

### Recommendation
Have `store_and_process_block_signature` re-run the same last-look sequence used in `handle_block_pre_commit`: call `check_block_against_signer_db_state` and the `get_signed_conflicts`/`conflict_still_blocks`/`reorg_permit_stands` guard on `block_info.block` before calling `mark_locally_accepted`/`broadcast_signed_block`, mirroring the ordering already established at [4](#0-3) .

### Proof of Concept
Not independently confirmed end-to-end within the available tool budget. The reachable trigger is: (1) this signer independently signs block A at height h (via the pre-commit path, which correctly applies the conflict guard); (2) a rival block B at height h (or a tenure-change block confirming a stale parent) separately accumulates ≥70% acceptance weight from peer `BlockAccepted` gossip before this signer's own state is consulted; (3) `handle_block_signature` → `store_and_process_block_signature` for B crosses the threshold and calls `mark_locally_accepted`/`broadcast_signed_block` for B without checking that this signer already signed conflicting A. Confirming actual node-side impact requires further inspection of `broadcast_signed_block`/`handle_post_block` and the node's block-acceptance validation, which was not completed here.

    /// Store the block acceptance signature and check if we have reached a consensus decision on the block because of it. If we have, update the block state accordingly and broadcast the block if accepted.
    fn store_and_process_block_signature(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        signer_address: &StacksAddress,
        signature: &MessageSignature,
    ) {
        let block_hash = &block_info.signer_signature_hash();
        // signature is valid! store it.
        // if this returns false, it means the signature already exists in the DB, so just return.
        if !self
            .signer_db
            .add_block_signature(block_hash, signer_address, signature)
            .unwrap_or_else(|_| panic!("{self}: Failed to save block signature"))
        {
            return;
        }

        // If this isn't our own signature and we haven't seen a pre-commit from this signer yet, try treating it as a pre-commit in case the caller is running an outdated version
        if signer_address != &self.stacks_address && !self.signer_db.has_committed(block_hash, signer_address).inspect_err(|e| warn!("Failed to check if pre-commit message already considered for {signer_address:?} for {block_hash}: {e}")).unwrap_or(false) {
            self.handle_block_pre_commit(stacks_client, sortition_state, signer_address, block_hash);
            return;
        }

        if block_info.signed_group.is_some() {
            // We have already processed this block to the accepted state. Adding more signatures will not change anything so nothing to check.
            return;
        }
        // do we have enough signatures to broadcast?
        // i.e. is the threshold reached?
        let signatures = self
            .signer_db
            .get_block_signatures(block_hash)
            .unwrap_or_else(|_| panic!("{self}: Failed to load block signatures"));

        // put signatures in order by signer address (i.e. reward cycle order)
        let addrs_to_sigs: HashMap<_, _> = signatures
            .into_iter()
            .filter_map(|sig| {
                let Ok(public_key) = Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(
                    block_hash.bits(),
                    &sig,
                ) else {
                    return None;
                };
                let addr = StacksAddress::p2pkh(self.mainnet, &public_key);
                Some((addr, sig))
            })
            .collect();

        let signature_weight = self.signer_weights.get(signer_address).unwrap_or(&0);
        let total_signature_weight = self.compute_signature_signing_weight(addrs_to_sigs.keys());
        let total_weight = self.compute_signature_total_weight();

        let min_weight = NakamotoBlockHeader::compute_voting_weight_threshold(total_weight)
            .unwrap_or_else(|_| {
                panic!("{self}: Failed to compute threshold weight for {total_weight}")
            });

        if min_weight > total_signature_weight {
            info!("{self}: Received block acceptance, but have not yet reached the acceptance threshold.";
                "signer_signature_hash" => %block_hash,
                "signature_weight" => signature_weight,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "block_height" => block_info.block.header.chain_length,
                "total_weight_approved" => total_signature_weight,
                "total_weight" => total_weight,
                "percent_approved" => (total_signature_weight as f64 / total_weight as f64 * 100.0),
            );
            return;
        }
        info!("{self}: have reached the block acceptance threshold";
            "signer_signature_hash" => %block_hash,
            "signature_weight" => signature_weight,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "total_weight_approved" => total_signature_weight,
            "total_weight" => total_weight,
            "percent_approved" => (total_signature_weight as f64 / total_weight as f64 * 100.0),
        );

        // have enough signatures to broadcast!
        // move block to LOCALLY accepted state.
        // It is only considered globally accepted IFF we receive a new block event confirming it OR see the chain tip of the node advance to it.
        if let Err(e) = block_info.mark_locally_accepted(true) {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally accepted: {e:?}");
            }
        }
        let _ = self.signer_db.insert_block(block_info).map_err(|e| {
            warn!("Failed to set group threshold signature timestamp for {block_hash}: {e:?}");
            panic!("{self} Failed to write block to signerdb: {e}");
        });
        self.broadcast_signed_block(stacks_client, block_info.block.clone(), &addrs_to_sigs);
    }
