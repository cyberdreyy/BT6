### Title
`setFeeCalculator` migration does not carry over vault price state, causing deposits/redeems to revert until admin re-registers - ([File: v3/src/core/FeeVault.sol])

### Summary
`FeeVault.setFeeCalculator` (v3/src/core/FeeVault.sol:81-91) lets an authorized admin swap the vault's fee calculator and calls `newFeeCalculator.registerVault()` on the new contract. When the new fee calculator is a `PriceAndFeeCalculatorV2` instance, `registerVault()` (v3/src/core/PriceAndFeeCalculatorV2.sol:81-94) only sets `anchorTimestamp` and `pauseOnBadAnchorUpdate`; it does not copy over `maxPriceAge`/thresholds or `anchorPrice` from the vault's prior calculator. This mirrors the ZetaChain `UpdateSystemContract` bug: a legitimate, authorized contract-swap operation fails to migrate critical per-vault state (thresholds/price), leaving downstream user-facing functions broken until the admin manually re-runs `setThresholds`/`setInitialPrice`.

### Finding Description
Path: admin calls `setFeeCalculator(newFeeCalculator)` on `FeeVault` → `newFeeCalculator.registerVault()` is invoked → `PriceAndFeeCalculatorV2.registerVault()` initializes only `anchorTimestamp` (to `block.timestamp`) and `pauseOnBadAnchorUpdate = true` for `msg.sender` (the vault) in the new calculator's storage — `maxPriceAge`, `minUpdateIntervalMinutes`, tolerance ratios, and `anchorPrice` all remain zero-valued in the new contract's mapping (`VaultPriceStateV2`), since it is a fresh mapping entry unrelated to the old calculator.

Immediately after the swap, any ordinary user calling `ProvisionerV2.deposit`/`redeem` (which route through `PRICE_FEE_CALCULATOR.convertTokenToUnits`/`convertUnitsToToken`/etc.) hits `_getCurrentPrice` returning `anchorPrice == 0`, and any attempt to fix pricing via `setInitialPrice` reverts with `Aera__ThresholdNotSet()` (v3/src/core/PriceAndFeeCalculatorV2.sol:104) because thresholds were never copied. Deposit/redeem math using a zero price either reverts on downstream oracle/rounding checks or produces degenerate (zero) conversions, effectively halting the deposit/redeem pipeline for all users of that vault until the admin manually calls `setThresholds` then `setInitialPrice` on the new calculator — an operational sequence not enforced or automated anywhere in `setFeeCalculator`.

This is a genuine root-cause analog to the C4 report: an authorized, ordinary "upgrade" administrative call (not malicious, not requiring privileged abuse beyond the documented admin action) leaves a broken/incomplete state transition that halts core user flows (deposit/redeem) for an unbounded window until manually remediated — precisely the "temporary freeze of user funds/interactions caused by an incomplete state migration" pattern.

### Impact Explanation
All depositors/redeemers of the vault attached to the swapped fee calculator are blocked from depositing or redeeming (their transactions revert or compute using price 0) from the moment `setFeeCalculator` executes until the admin performs the follow-up `setThresholds` + `setInitialPrice` calls. This is a temporary freeze of protocol-facing deposit/redeem functionality for all users of the affected vault, consistent with a Medium-severity temporary DoS/freeze under Immunefi-style scoring (no permanent fund loss, but funds/withdrawals unavailable for an indeterminate period).

### Likelihood Explanation
Requires the vault's authorized admin (owner/authority) to call `setFeeCalculator` to point at a new `PriceAndFeeCalculatorV2` instance — a standard, expected operational action (e.g., upgrading the fee/price calculator implementation), not an attack. Given that `setFeeCalculator` is a normal maintenance operation, hitting this bug is a near-certainty on any calculator migration unless operators manually pre-empt it by calling `setThresholds`/`setInitialPrice` in the same transaction/batch, which the code does not enforce or automate.

### Recommendation
Modify `setFeeCalculator` (or `PriceAndFeeCalculatorV2.registerVault`) to snapshot/copy the vault's existing `VaultPriceStateV2` (thresholds, `anchorPrice`, `highestPrice`, `lastTotalSupply`) from the old fee calculator into the new one atomically as part of the migration, or require/perform an atomic `registerVault` + `setThresholds` + `setInitialPrice` sequence within `setFeeCalculator` itself, so the vault is never left in a state where deposits/redeems can be attempted against an uninitialized price state.

### Proof of Concept
1. Deploy `MultiDepositorVault`/`FeeVault` with `PriceAndFeeCalculatorV2` A configured via `registerVault`, `setThresholds`, `setInitialPrice(vault, price)`.
2. Perform normal deposits via `ProvisionerV2.deposit` to confirm functioning state.
3. Deploy a second `PriceAndFeeCalculatorV2` B (same numeraire/oracle registry).
4. As vault owner, call `setFeeCalculator(B)` on the `FeeVault`.
5. Assert `B.getVaultState(vault)` returns `maxPriceAge == 0` and `anchorPrice == 0`.
6. Attempt `ProvisionerV2.deposit(...)` (which now routes to calculator B) and assert it reverts or computes a degenerate 0-unit conversion.
7. Attempt to call `setInitialPrice` directly on B and assert it reverts with `Aera__ThresholdNotSet()`, proving the admin cannot even quickly fix state without first calling `setThresholds`, confirming an enforced downtime window.
