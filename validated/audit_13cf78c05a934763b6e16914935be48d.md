## Title
Deleting a multisig member does not purge that member's confirmations from other pending requests, allowing a request to execute below the configured confirmation threshold - (File: `multisig2/src/lib.rs`)

## Summary
The `MultiSigContract` in `multisig2/src/lib.rs` counts a stored `HashSet<String>` of confirmations against `num_confirmations` to decide whether a request is authorized. When a member is removed via `DeleteMember`, `delete_member` only discards the *requests that member originally created* — it never scans the `confirmations` set of other still-pending requests to drop confirmations the departing member had cast on them. This lets a request execute using a confirmation from an account/key that is no longer a member, i.e. `confirmations counted` diverges from `live members`, letting a request pass with fewer real (live) approvals than `num_confirmations` requires.

## Finding Description
`delete_member` is invoked from `execute_request` when a `DeleteMember` action reaches quorum: [1](#0-0) 

It removes the member from `self.members`, and only cleans up requests where the member was the **signer** (`r.member == member`) — it does not iterate `self.confirmations` to strip that member's entries from *other* requests they had confirmed but did not create: [2](#0-1) 

Meanwhile, `confirm` simply compares the size of the stored confirmation set (plus the new confirmer) to `num_confirmations`, without re-validating that every stored confirmer is still a current member: [3](#0-2) 

So the invariant that should hold — `confirmations counted == live members who approved` — is broken. A stale confirmation from a deleted member remains valid weight toward quorum on any request that member confirmed but did not originate.

The same class of bug exists in the earlier `multisig` contract's `DeleteKey` handling, which likewise only purges requests originated by the deleted key, not confirmations that key placed on other requests: [4](#0-3) 

## Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An attacker (any single current member, or a member about to be removed) can pre-plant a confirmation on a sensitive pending request (e.g., a `Transfer`, `AddKey`, or `FunctionCall` request), then let/cause that member to be removed through the normal `DeleteMember` flow. The stale confirmation persists and still counts toward `num_confirmations`, so the request can later be pushed to execution with fewer *live* members actually approving it than the configured threshold, effectively lowering the multisig's security guarantee (e.g., a 3-of-4 wallet can be drained with only 2 live confirmations plus 1 confirmation from an already-removed member).

## Likelihood Explanation
Likelihood is high in any multisig deployment where membership changes over time (a very common operational event — rotating signers, revoking a compromised key, offboarding an employee). No special privilege beyond being one ordinary member is required to place the "poisoned" confirmation beforehand; the removal itself follows the normal governance flow and does not need to be malicious — it simply fails to clean up unrelated stale confirmations.

## Recommendation
In `delete_member` (and equivalently `DeleteKey`/`delete_key` handling in `multisig/src/lib.rs`), iterate all entries in `self.confirmations` (not just requests originated by the removed member) and remove the departing member's/key's entry from every confirmation set. Alternatively, validate on every `confirm()` call (or at execution time) that all recorded confirmers in a request's confirmation set are still current members before counting them toward `num_confirmations`.

## Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `B` calls `add_request` to create request `R` (e.g., `Transfer` to an attacker-controlled account) — confirmations start empty.
3. `D` calls `confirm(R)` — confirmations for `R` become `{D}` (1 of 3).
4. Separately, `A`, `B`, `C` reach quorum on a `DeleteMember { member: D }` request and it executes via `execute_request` → `delete_member`. This only removes requests where `D` is the *signer*; request `R` (signed by `B`) is untouched, and `D`'s confirmation entry on `R` is not purged, per [2](#0-1) .
5. `D` is now not a member (`self.members` no longer contains `D`), yet `R`'s confirmation set still contains `D`.
6. `A` calls `confirm(R)` → confirmations `{D, A}` (2 of 3, but only `A` is a live member).
7. `C` calls `confirm(R)` → `confirmations.len() + 1 = 3 >= num_confirmations(3)` per [5](#0-4) , so `execute_request` runs the `Transfer`, moving funds with only 2 genuine live-member approvals (`A`, `C`) instead of the required 3.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
