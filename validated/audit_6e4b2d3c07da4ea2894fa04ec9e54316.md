### Title
Unfunded instant-withdraw receipts drain funded withdraw reserves in `claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns a user's entire `instantWithdrawsRequests[_user]` receipt and pays out underlying from the strategy's token balance without checking whether that receipt was ever funded. Instant receipts are only backed when the borrower sends funds at `startEpoch` and the CDO moves them via `collectInstantWithdrawFunds` (which decrements `pendingInstantWithdraws`). A receipt created mid-epoch (APR-drop instant path in `requestWithdraw`) is unfunded yet still claimable in the same transaction, so the attacker is paid from underlyings that belong to already-funded normal withdraw claimants whose payouts sit in the vault awaiting `claimWithdrawRequest`. Analogous to the CVE bug class: a crafted request sequence reaches a code path that "reads" (pays out) funds that were never allocated to it — an accounting/authorization failure rather than a raw DoS.

### Finding Description
In `requestWithdraw`, when `lastEpochApr > unscaledApr + instantWithdrawAprDelta` the CDO calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` (`IdleCDOEpochVariant.sol:761-768`). The vault mints the user a 1:1 strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). These funds are only collected later at `startEpoch` via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`).

`claimInstantWithdrawRequest` then burns `instantWithdrawsRequests[_user]` in full and calls `_transferFundedClaim(_user, amount)` (`IdleCreditVault.sol:380-393`). `_transferFundedClaim` only excludes `defaultRecoveryReserve` (`IdleCreditVault.sol:897-907`); it does not verify the receipt was funded by `collectInstantWithdrawFunds`. Meanwhile, `collectWithdrawFunds` transfers borrower repayments into the strategy to back pending normal receipts (`IdleCreditVault.sol:411-430`), and those underlyings sit unclaimed until users call `claimWithdrawRequest`. The attacker withdraws against that balance.

Broken invariant: one receipt, one funded payout — an unfunded instant receipt is paid 1:1 from other claimants' segregated funds. No guard stops it: `claimInstantWithdrawRequest` only checks `allowInstantWithdraw` in the CDO wrapper (`IdleCDOEpochVariant.sol:975-979`), and `_transferFundedClaim`'s reserve guard only applies once `defaultRecoveryReserve != 0`.

### Impact Explanation
Direct theft. The attacker converts unfunded instant receipts into real underlyings held for funded withdraw claimants, up to `underlyingToken.balanceOf(strategy) - defaultRecoveryReserve`. Victims' later `claimWithdrawRequest` calls revert on insufficient balance — their funded claims are permanently impaired. Loss is bounded by funded-but-unclaimed withdraw reserves plus any prefunded instant float belonging to other users.

### Likelihood Explanation
Requires (a) `allowInstantWithdraw` enabled and an APR drop exceeding `instantWithdrawAprDelta` so the instant path triggers, and (b) a positive unfunded portion coexisting with vault-held funded reserves — a normal state after `stopEpoch` funds pending receipts while a new epoch runs. The attacker is any KYC-passing tranche holder; no privileged cooperation needed.

### Recommendation
In `claimInstantWithdrawRequest`, pay only the funded portion: cap the transfer at `instantWithdrawsRequests[_user] - unfundedAmount` where unfunded is tracked per-user (e.g., subtract the user's share of `pendingInstantWithdraws`), or revert while the user's receipt contributes to `pendingInstantWithdraws` (require `instantWithdrawsRequestsByEpoch[_user][epochNumber] == 0` or funding confirmation). Alternatively, fund instant receipts atomically at request time.

### Proof of Concept
```solidity
// Foundry fork test sketch against a live idle-tranches deployment
function testUnfundedInstantClaimDrainsFundedReserves() external {
    // 1. Setup: deposit AA, start epoch, stop epoch with borrower repayment
    //    so the vault holds funded underlyings for pending normal receipts.
    idleCDO.depositAA(10_000e6);
    _startEpoch();
    _stopEpochWithBorrowerFunding(); // collectWithdrawFunds pulls underlying into strategy

    // victim requests normal withdraw -> funded at next stopEpoch, unclaimed
    uint256 req = cdoEpoch.requestWithdraw(0, AA);
    _startEpoch();
    _stopEpochWithBorrowerFunding(); // strategy now holds victim's funded underlyings

    // 2. Force APR drop > instantWithdrawAprDelta (e.g., via new epoch params)
    //    so requestWithdraw takes the instant path.
    uint256 bal = IERC20(tranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(bal, AA); // creates UNFUNDED instant receipt mid-epoch
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // 3. Attacker claims immediately; vault pays from victim's funded reserve.
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - pre, 0);

    // 4. Victim's funded claim now reverts/underflows on insufficient balance.
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat I could not fully verify within the available context: whether an external or off-chain flow tops up the strategy balance before instant claims become callable in the intended design (i.e., whether `pendingInstantWithdraws > 0` is ever expected to coincide with claimable balances). If the intended invariant is that instant claims are only processed after funding, the missing enforcement in `claimInstantWithdrawRequest` is still the defect.
