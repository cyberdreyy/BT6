### Title
Unselected blocking send on `outCh` in `readLogs` prevents goroutine exit on context cancellation - (File: executors/kubernetes/log_processor.go)

### Summary
`kubernetesLogProcessor.readLogs` reads a line from `linesCh` inside a `select` that includes a `ctx.Done()` case, but then performs the send `outCh <- logLine` at line 268 outside of any `select`/`ctx.Done()` guard. If the consumer of `outCh` (trace forwarding in the executor) stops draining while a line is in flight, this send blocks indefinitely and is never interrupted by context cancellation.

### Finding Description
In `readLogs` [1](#0-0) , the loop's `select` statement (lines 243-250) races `ctx.Done()` against receiving from `linesCh`. Once a line is received (the `case line, more := <-linesCh` branch), execution falls through to process the line and unconditionally executes `outCh <- logLine` at line 268. This send is a plain channel operation, not wrapped in a second `select` with `ctx.Done()`. If the goroutine draining `outCh` (the caller of `Process()`, which forwards log lines into the job trace) has stopped consuming — e.g., because the job's trace/output pipeline was torn down or backpressured while the job author caused a burst of high-volume/timed stdout — this send blocks forever. Because the block occurs mid-iteration, the loop can never reach the next `select` to observe `ctx.Done()`, so cancellation of `ctx` (as done by `attach`/`processStream` on job cancellation or teardown) does not unblock this goroutine.

This is a genuine gap: the sibling goroutine in `scan()` (lines 294-298) does correctly guard its `linesCh <-` send with a `select` containing `ctx.Done()`, but `readLogs`'s `outCh <-` send at line 268 lacks the equivalent guard.

Attacker control: an unprivileged job author fully controls job stdout volume and timing (arbitrary shell commands/output), and can trigger cancellation via pipeline cancellation, job timeout, or any teardown path that cancels the executor's context while log streaming is active. This is enough to create the race between output line delivery and trace consumer shutdown that leaves the send unblocked-on-cancel.

### Impact Explanation
When the send blocks, the `readLogs` goroutine (and via `errgroup` in `processStream`, also the `Stream` goroutine tied to the same context/pipe) never returns. This leaks the goroutine, keeps the `io.Pipe` and the underlying exec/attach stream to the Kubernetes pod open, and prevents `kubernetesLogProcessor.Finalize()`'s `wg.Wait()`-guarded resources from being cleaned up promptly (note: `wg` only tracks the `scan` goroutine, not `readLogs` itself, so `Finalize` may return while `readLogs` is still stuck, but the leaked goroutine/pipe/stream persist regardless). This matches the scoped impact: a persistent per-job resource leak (goroutine + open stream) that survives cancellation and accumulates across jobs run by the same runner process, degrading it over time (file descriptors, goroutines, memory).

### Likelihood Explanation
This requires a specific race: the job must produce output while the trace-forwarding consumer of `outCh` stops draining before `Process()`'s producer side observes cancellation, and cancellation must happen concurrently. This is plausible under job cancellation/timeout/teardown scenarios where the executor tears down trace forwarding before fully draining in-flight log channels — an unprivileged job author cannot directly force the consumer to stop, but can reliably create favorable timing (large/bursty output near job end) to increase likelihood of hitting the window, and can trigger cancellation via job cancel/timeout. Repeated attempts across pipelines make the leak cumulative even if any single race is probabilistic rather than deterministic.

### Recommendation
Guard the send at line 268 with a `select` that also includes `case <-ctx.Done(): return nil`, e.g.:
```go
select {
case <-ctx.Done():
    return nil
case outCh <- logLine:
}
```
This ensures the goroutine can exit promptly on cancellation even if the consumer is not draining `outCh`.

### Proof of Concept
Go unit test in `executors/kubernetes/log_processor_test.go`:
1. Construct a `kubernetesLogProcessor` with a fake `logStreamer` (or directly call `readLogs`) supplying an `io.Reader` that yields at least one log line (e.g., `"5 hello\n"`).
2. Create `outCh := make(chan string)` with no reader ever draining it (simulate consumer stopping).
3. Create `ctx, cancel := context.WithCancel(context.Background())`.
4. Run `go func() { done <- l.readLogs(ctx, reader, outCh) }()`.
5. Immediately `cancel()` after the goroutine has read at least one line (synchronize via a small sleep or instrumentation).
6. Assert that `done` receives a value within a short timeout (e.g., `select { case <-done: case <-time.After(time.Second): t.Fatal("readLogs did not exit after ctx cancellation") }`).
Expected current behavior: the test times out / fails because `readLogs` blocks forever on `outCh <- logLine`, proving the goroutine does not honor `ctx.Done()` once it has committed to the unselected send.
