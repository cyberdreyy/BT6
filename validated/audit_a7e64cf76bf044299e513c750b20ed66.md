### Title
Unauthenticated APR configuration during the setup window allows any EOA to hijack vault rate parameters - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Keycloak CVE is a privilege-boundary failure: a permission check that should gate a privileged operation is skipped under a specific configuration state, letting a low-privilege caller reach an admin-only code path. `IdleCreditVault.setApr()` contains the same shape: when `idleCDO` is still `address(0)` (the deployment window between `initialize()` and the owner's `setWhitelistedCDO()` call), the caller check is skipped entirely, so **any EOA** can write `lastApr` and `unscaledApr`. Worse, `setAprs()` and `setAprsWithBuffer()` write `unscaledApr` *before* delegating to `setApr()`, so the unscaled rate is never bounded by `maxApr` and is only protected by the same skippable check.

### Finding Description
In `IdleCreditVault.sol`:

```solidity
function setAprs(uint256 _unscaledApr, uint256 _apr) external {
    unscaledApr = _unscaledApr;          // written unconditionally, before auth
    setApr(_apr);                        // auth inside here
}

function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    ...
    lastApr = _apr;
}
```

Lines 206–235 of `contracts/strategies/idle/IdleCreditVault.sol`. The `if (_cdo != address(0))` guard is exactly the "missing privilege boundary check" of the report: during a legitimate protocol state (strategy initialized, CDO not yet whitelisted — which persists until the owner calls `setWhitelistedCDO`), the authorization boundary collapses to "everyone". An attacker monitoring mempool/deployment can front-run `setWhitelistedCDO` and:

- Set `lastApr` to `maxApr` (20e18), inflating `getApr()`-driven interest expectations.
- Set `unscaledApr` to an arbitrary nonzero value, permanently misconfiguring the APR0 accounting mode for a vault intended to run at APR 0.

`unscaledApr` directly gates `requestWithdraw`'s APR0 path (`if (unscaledApr == 0 && !isClosed)` at line 285) and `prepareStopEpochWithApr0` reverts when `unscaledApr != 0` while `apr0TotalPrincipal > 0` (line 506). A nonzero `unscaledApr` injected on an APR0 vault therefore sends normal withdraw requests down the wrong accounting branch and can make `stopEpoch` revert once APR0 principal exists — a temporary freezing of all queued withdrawals until the manager manually corrects the rate.

### Impact Explanation
Direct impact is misconfiguration of a core accounting parameter by an unauthorized party: corrupted APR0 routing for withdraw receipts and a revert path in `prepareStopEpochWithApr0` that blocks `stopEpoch` settlement while APR0 principal is pending — i.e., temporary freezing of depositor funds and interest settlement. The window is real but narrow (deploy → `setWhitelistedCDO`), and the honest manager can repair values afterwards, capping severity at Medium, consistent with the source advisory.

### Likelihood Explanation
Requires the deployment to go through the `idleCDO == address(0)` phase — which it always does, since `setWhitelistedCDO` is a separate owner transaction — and an attacker to act inside that window. If deployment and whitelisting are bundled in one transaction/multisig batch, the window closes; if they are separate mempool transactions, front-running is trivial. Likelihood: Low–Medium.

### Recommendation
Remove the `_cdo == address(0)` exemption and enforce `msg.sender == owner() || msg.sender == manager` (or a dedicated initializer step) unconditionally; additionally validate `unscaledApr` against a bound and move the `unscaledApr` write after the authorization check in `setAprs`/`setAprsWithBuffer`.

### Proof of Concept
Foundry fork PoC outline:
1. Deploy `IdleCreditVault` via proxy and call `initialize(underlying, owner, manager, borrower, "X", apr)` — leaving `idleCDO == address(0)`.
2. `vm.prank(attacker)` (arbitrary EOA): `vault.setAprs(type(uint256).max / 1e18, 20e18)` — succeeds because the `_cdo != address(0)` check is skipped.
3. Assert `vault.unscaledApr()` equals attacker value and `vault.lastApr() == 20e18` before the owner's `setWhitelistedCDO` executes.
4. Show consequence: after `setWhitelistedCDO`, a user `requestWithdraw` on an intended-APR0 vault takes the non-APR0 branch, or `prepareStopEpochWithApr0` reverts on `NotAllowed` once `apr0TotalPrincipal > 0` while `unscaledApr != 0`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

  function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);
  }
