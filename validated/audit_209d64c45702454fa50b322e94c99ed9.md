### Title
Stale signer rejection weight is never retracted on vote-flip, letting a minority of signers permanently inflate `total_weight_rejected` and wedge the miner/coordinator into declaring `SignersRejected` for a block that reaches real acceptance - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
This is the same bug class as the DODO H-5 report: a state-accounting update that should be symmetric (add on one event, retract on the reversing event) is only ever additive in one direction. In DODO, `_poolRepayAll` decremented `info.balance` instead of crediting it, permanently corrupting the vault's recorded balance so an attacker could siphon the phantom difference. In `StackerDBListener::run`, the analogous "ledger" is `BlockStatus.total_weight_approved` / `total_weight_rejected`: a signer's weight is added to `total_weight_rejected` when it rejects a block, but that weight is never removed when the same signer subsequently (and legitimately, per the documented reconsideration flow) accepts the very same block. The two counters are gated by two different, non-consistent keys (`gathered_signatures` for accept, `responded_signers` for reject), so a reject-then-accept sequence double-books the signer's weight into both tallies, corrupting the invariant that `total_weight_approved` and `total_weight_rejected` are disjoint, weight-conserving sums bounded by `total_weight`.

### Finding Description
`BlockStatus` tracks two weight tallies used to decide a block's fate: [1](#0-0) 

On `BlockResponse::Accepted`, dedup/weight-add is gated on `gathered_signatures` (keyed by `slot_id`): [2](#0-1) 

On `BlockResponse::Rejected`, dedup/weight-add is gated on a *different* set, `responded_signers`: [3](#0-2) 

Because the accept path's gate (`gathered_signatures`) is untouched by a prior reject, and the reject path's gate (`responded_signers`) is untouched by a prior accept, the two events are not mutually exclusive for the same slot:

- Reject arrives first for `slot_id`: `responded_signers.insert(slot_id)` → true → `total_weight_rejected += weight`.
- Accept arrives later for the *same block* and *same signer*: `gathered_signatures.contains_key(slot_id)` is still false (this signer never accepted before) → `total_weight_approved += weight` as well.

The signer's weight is now counted in **both** `total_weight_rejected` and `total_weight_approved` simultaneously, and `total_weight_rejected` is never decremented — there is no code path anywhere in this loop that subtracts from `total_weight_rejected`. This breaks the "aggregated-weight vs verified-accepts" equality: the rejection tally no longer reflects the set of signers who currently object to the block; it reflects the set of signers who have *ever* objected, even those who have since recanted.

This reject-then-accept sequence is not a hypothetical protocol violation — the signer-side documentation explicitly describes a flow where a signer that previously rejected a block can later sign it upon reconsideration, and the `BlockInfo` state machine explicitly permits the `LocallyRejected → LocallyAccepted` transition: [4](#0-3) [5](#0-4) 

So any signer (a single "one-slot" actor, malicious or merely reconsidering under normal churn) can trigger the stuck-rejection accounting simply by voting reject then accept on the same `signer_signature_hash`.

### Impact Explanation
The consumer of this ledger is the mining coordinator's wait loop, which checks the *rejection* condition before the *approval* condition: [6](#0-5) 

Because `block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` is evaluated first, stale/never-retracted rejection weight from signers who have since flipped to acceptance can push the rejection tally over the "blocking minority" threshold (`total_weight - weight_threshold`, i.e. >30% weight) even though those same signers currently endorse the block and the live acceptance tally may independently also reach the 70% approval threshold. When this happens the coordinator returns `NakamotoNodeError::SignersRejected`, discards the proposal, and the miner treats affected transactions as (temporarily or permanently) excluded — a liveness wedge that stalls block production despite a real, current supermajority of endorsing weight. This requires only a minority of signers' weight (the normal ~30% blocking share, not a majority) to exhibit an accept-after-reject sequence, which the documented reconsideration semantics make a routine occurrence rather than an edge case.

This does not require compromising any signer's key or the auth token; a single signer legitimately reconsidering (or an adversarial signer intentionally rejecting once, then accepting) is sufficient to permanently corrupt its own weight's classification for that block, and enough such signers (still under 70%/30% thresholds) can wedge the round.

### Likelihood Explanation
The signer-side design explicitly allows and documents reject→accept transitions on reconsideration (`docs/signer-flows.md` sections around the pre-commit/reconsideration re-check), so this is not a contrived edge case but a codified part of normal operation whenever chain state changes favorably between an initial rejection and a later re-evaluation (e.g., after a conflicting block goes stale). Any deployment where a meaningful fraction of signer weight is momentarily conflicted (a common occurrence during forks/timeouts, per the "async sibling validation" tests referenced in `stacks-signer/src/v0/tests.rs`) is exposed. No majority coordination is needed — only cumulative weight near the pre-existing 30% blocking threshold.

### Recommendation
Track accept/reject membership with a single, unified per-slot vote-state map (e.g., `HashMap<u32, BlockVote>` where `BlockVote` is `Accepted(weight)` or `Rejected(weight)`), and when a signer's vote flips from Rejected to Accepted (or vice versa), retract the weight from the previous bucket before crediting the new one, e.g.:
```rust
match previous_vote {
    Some(BlockVote::Rejected) => block.total_weight_rejected = block.total_weight_rejected.saturating_sub(weight),
    Some(BlockVote::Accepted) => block.total_weight_approved = block.total_weight_approved.saturating_sub(weight),
    None => {}
}
```
before adding the new weight to the appropriate tally, ensuring `total_weight_approved` and `total_weight_rejected` remain disjoint, monotone-per-slot, and bounded by `total_weight` at all times.

### Proof of Concept
1. Coordinator starts tracking a block `B` with signer weights summing to `total_weight`, `weight_threshold = 70%`, blocking minority = 30%.
2. A set of signers whose combined weight is just over 30% each send `BlockResponse::Rejected(B)` (e.g., because of a transient chainstate mismatch resolved later). Each triggers `responded_signers.insert(slot_id) == true` → `total_weight_rejected` climbs above the blocking minority threshold. At this exact moment `get_block_status`'s rejection check (`signer_coordinator.rs:509-513`) can already fire and return `SignersRejected`, or if timing allows the flip to land first:
3. The same signers, upon reconsideration (as the signer-flows doc describes), each send `BlockResponse::Accepted(B)` for the identical `signer_signature_hash`. Since `gathered_signatures` never contained their `slot_id`, each addition credits `total_weight_approved` as well — but `total_weight_rejected` is never decremented.
4. Now `total_weight_rejected` still exceeds the blocking-minority threshold (stale) while `total_weight_approved` may simultaneously reach 70% (live). Depending on poll timing in `get_block_status`'s loop, the coordinator can observe the stale-but-still-present `total_weight_rejected > blocking_minority` condition and abort with `SignersRejected`, discarding a block that in reality now has enough current acceptances — a liveness wedge triggered by ordinary vote reconsideration from well under a majority of signers.
