### Title
`claimInstantWithdrawRequest` doesn't remove the claim from `instantWithdrawClaimsByEpoch`, corrupting default-recovery accounting - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a stale-membership desync: `_revokeRole` clears the role flag but never removes the account from `_roleMembers[role]`, so the aggregate member set no longer matches reality. In `IdleCreditVault`, the analogous aggregate is `instantWithdrawClaimsByEpoch[epochNumber]`, the per-epoch instant-withdraw claim basis used by `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` during `finalizeDefaultRecovery`. When a user claims an already-funded instant withdrawal via `claimInstantWithdrawRequest`, the code zeroes `instantWithdrawsRequests[_user]` and burns the receipt, but never decrements `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` — even though the default-claim path `_claimDefaultedInstantWithdrawRequest` does decrement both. The per-epoch claim set therefore retains already-paid receipts, inflating recovery basis and prefunded reserve with phantom funds. [1](#0-0) [2](#0-1) 

### Finding Description
`requestInstantWithdraw` records the claim in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` [3](#0-2) . The ordinary claim path clears only the first:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are left untouched. By contrast, the defaulted-epoch claim path `_claimDefaultedInstantWithdrawRequest` correctly clears all three aggregates, confirming these counters are meant to track *outstanding* claims. [4](#0-3) 

The stale entries matter at default finalization. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve()` credits `instantBasis - pendingInstant` to `reserveAmount` as "already-held underlying". A claimed-and-paid receipt inflates both: the numerator (`reserveAmount`) is credited for underlying that was already transferred out, and the denominator (`totalBasis`) counts a claim that no longer exists. [5](#0-4) [6](#0-5) 

Since `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, adding equal phantom amounts to numerator and denominator pushes the price toward 1 when the true recovery ratio is below par. The reserve is then consumed via `_transferDefaultRecovery` at the inflated price — early claimants are overpaid, and the reserve drains before later claimants (including remaining instant receipt holders) can claim, leaving them permanently underpaid or reverting on `safeTransfer`. [7](#0-6) [8](#0-7) 

### Impact Explanation
Direct theft / permanent underpayment of recovery claims. A lender who claims a funded instant withdrawal in epoch N leaves a phantom claim in `instantWithdrawClaimsByEpoch[N]`. If the borrower defaults in the same epoch while other instant requests remain partially funded (`pendingInstantWithdraws != 0`), the phantom claim inflates `recoveryPrice` above the true `realReserve / realBasis`. The attacker — any KYC'd lender — can hold a second defaulted-epoch receipt (or simply have extracted par value pre-default) while honest claimants' payouts are calculated against an overstated reserve. Concretely: with true reserve R and true basis B (R < B), and phantom amount P, claimants are priced at `(R+P)/(B+P) > R/B`, so aggregate payouts exceed R; the last claimants' `safeTransfer` reverts or pays less, and their shortfall equals the phantom-inflated excess paid earlier. The `defaultRecoveryReserve` isolation guard in `_transferFundedClaim` does not help because the corruption happens inside the reserve accounting itself. [9](#0-8) 

### Likelihood Explanation
The preconditions are ordinary vault operations, not attacker-privileged actions: (1) an instant withdraw request is funded via `collectInstantWithdrawFunds` while the epoch is still running, (2) the requester claims before epoch end (no epoch gating exists on `claimInstantWithdrawRequest`), and (3) the borrower defaults in that same epoch with `pendingInstantWithdraws != 0`. Instant withdrawals during a stressed epoch — exactly when a default is likely — are the expected usage pattern, so the trigger conditions coincide naturally. No privileged role acts maliciously; the manager, borrower, and CDO behave normally.

### Recommendation
Mirror the default-claim cleanup in the funded-claim path. In `claimInstantWithdrawRequest`, also decrement the per-epoch aggregates:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
uint256 epoch = epochNumber; // or track request epoch per user
instantWithdrawsRequestsByEpoch[_user][epoch] -= amount; // or map to stored request epoch
instantWithdrawClaimsByEpoch[epoch] -= amount;
instantWithdrawsRequests[_user] = 0;
```

Because claims can occur in a later epoch than the request, the clean fix is to iterate/zero the user's `instantWithdrawsRequestsByEpoch` entries for the epochs that contributed to `instantWithdrawsRequests[_user]` (or store the user's instant request epoch analogously to `lastWithdrawRequest`) and reduce `instantWithdrawClaimsByEpoch` for those epochs accordingly. Ensure `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see outstanding claims.

### Proof of Concept
Foundry fork test sketch against `IdleCreditVault` + `IdleCDOEpochVariant` (pattern follows `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// Epoch N running, instant withdraws enabled.
// 1. Attacker A and victim B each requestInstantWithdraw(50e6) via cdo.requestInstantWithdraw.
//    instantWithdrawClaimsByEpoch[N] = 100e6, pendingInstantWithdraws = 100e6.
// 2. Manager partially funds: cdo collects only A's 50e6 via collectInstantWithdrawFunds.
//    pendingInstantWithdraws = 50e6; strategy holds 50e6.
// 3. A calls claimInstantWithdrawRequest -> receives 50e6 at par.
//    BUG: instantWithdrawClaimsByEpoch[N] still 100e6 (should be 50e6).
// 4. Borrower defaults; owner calls finalizeDefault -> finalizeDefaultRecovery(recovered, source).
//    basis includes 100e6 instant claims; prefundedReserve = 100e6 - 50e6 = 50e6 (phantom,
//    already paid to A). recoveryPrice inflated toward 1e18.
// 5. B calls claimInstantWithdrawRequest -> paid claimBasis * inflatedPrice from reserve.
// Assert: sum(instant recovery payouts) > actual underlying held by strategy, or B's
// safeTransfer reverts / B receives less than the fair pro-rata share computed from the
// real reserve. Assert instantWithdrawClaimsByEpoch[N] did not decrease after step 3.
```

Key assertions: `instantWithdrawClaimsByEpoch[epochNumber]` unchanged by `claimInstantWithdrawRequest`, and `strategy.underlyingToken.balanceOf(strategy) < defaultRecoveryReserve` inconsistency after finalization, demonstrating the reserve is credited for funds already paid out.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
