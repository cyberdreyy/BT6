### Title
Withdraw receipt claimant cannot specify a recipient, so a USDC/USDT-blacklisted lender cannot claim funded withdrawals — `claimWithdrawRequest` / `claimInstantWithdrawRequest` pay only to `msg.sender` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In the epoch credit-vault flow, a lender's withdrawal proceeds are paid via `IdleCDOEpochVariant.claimWithdrawRequest()` / `claimInstantWithdrawRequest()`, which hardcode `msg.sender` as the beneficiary. `IdleCreditVault` then burns the user's strategy-token receipts and `safeTransfer`s the underlying (typically a blocklistable stablecoin such as USDC or USDT) to that same address. There is no `to`/`recipient` parameter anywhere in the chain. If the user is added to the token's blocklist between `requestWithdraw` and claim, every claim reverts and the lender's funds are frozen until they are removed from the blocklist — they cannot redirect the payout to a clean address.

### Finding Description
The relevant call chain:

- `IdleCDOEpochVariant.claimWithdrawRequest()` passes `msg.sender` as `_user` and offers no recipient argument (`contracts/IdleCDOEpochVariant.sol:967-971`, `975-979`).
- `IdleCreditVault.claimWithdrawRequest(_user)` → `_claimFundedWithdrawRequest(_user)` burns the receipt tokens then calls `_transferFundedClaim(_user, amount)`, which does `underlyingToken.safeTransfer(_user, _amount)` (`contracts/strategies/idle/IdleCreditVault.sol:301-350`, `897-907`).
- The same pattern applies to `claimInstantWithdrawRequest` (`:380-393`), defaulted-epoch and post-default claims via `_transferDefaultRecovery(_user, _amount)` (`:912-917`).
- Receipt tokens are address-bound: `_transfer` reverts unless `msg.sender == idleCDO` (`:939-942`), so a blacklisted user cannot transfer the receipt NFT-of-claim to a clean EOA to redeem on their behalf either.
- `IdleCDOEpochQueue.claimWithdrawRequest` has the identical `safeTransfer(msg.sender, ...)` pattern (`contracts/IdleCDOEpochQueue.sol:393-411`).

Because the underlying token for credit vaults is a fiat-backed stablecoin with a blocklist (USDC/USDT), a transfer to a blocked address reverts at the token level. The revert undoes the receipt burn, so the claim is not lost, but there is no code path to send the payout to any address other than the blocked one.

### Impact Explanation
A lender holding a non-zero funded withdraw receipt (`withdrawsRequests`, APR0 settled principal/interest, `instantWithdrawsRequests`, `postDefaultRequests`, or defaulted-epoch claims) whose address is blacklisted by the underlying token issuer cannot execute any claim. The funds sit in `IdleCreditVault` backing the receipt; the user is frozen out of their collateral/yield for as long as the blocklist entry persists — potentially permanently if the issuer never unblocks. This is a temporary (potentially indefinite) freezing of user funds equal to the full claim amount, matching the accepted impact class.

### Likelihood Explanation
Requires an external condition — the user being added to the stablecoin's blocklist after creating a receipt. Blocklist additions occur in practice (sanctions, exploited-fund tracing), and users can be blocked even without wrongdoing (e.g., receiving tainted funds). The same user could still deposit/trade elsewhere with a fresh address, but this protocol gives them no way to move the payout destination, so a single blocklisting converts a fully-funded claim into an inaccessible balance.

### Recommendation
Add a recipient parameter to the claim path, e.g. `IdleCDOEpochVariant.claimWithdrawRequest(address _to)` / `claimInstantWithdrawRequest(address _to)` forwarded to `IdleCreditVault.claimWithdrawRequest(msg.sender, _to)`, and have `_transferFundedClaim`/`_transferDefaultRecovery` transfer to `_to` while burning receipts from `msg.sender`. Alternatively, allow receipt holders to transfer their strategy-token receipts so a clean address can claim. Apply the same `to` parameter to `IdleCDOEpochQueue.claimWithdrawRequest`/`claimDepositRequest` and, if desired, keep `DefaultDistributor.claim(_to)` semantics (it already supports a recipient).

### Proof of Concept
Foundry fork test (mainnet fork with USDC as underlying; use USDC's real `blacklister` to block the claimant):

```solidity
// test/foundry/BlacklistClaim.t.sol
function test_BlacklistedUserCannotClaim() public {
    // 1. Pool running normal epoch; user deposits AA, buffer starts
    vm.prank(user);
    cdo.depositAA(amount);

    vm.prank(manager);
    cdo.stopEpoch(newApr, 0);            // buffer opens

    // 2. User requests withdraw -> mints receipt tokens to `user`
    vm.prank(user);
    cdo.requestWithdraw(0, AA);

    // 3. Next epoch starts/stops; collectWithdrawFunds funds the receipt
    vm.prank(manager);
    cdo.startEpoch();
    vm.warp(epochEnd + 1);
    _borrowerApproveAndFund();           // borrower repays interest + pendingWithdraws
    vm.prank(manager);
    cdo.stopEpoch(newApr2, 0);           // IdleCreditVault now holds user's underlying

    // 4. USDC blacklister blocks `user`
    vm.prank(usdcBlacklister);
    FiatTokenV2(usdc).blacklist(user);

    // 5. Claim reverts: underlyingToken.safeTransfer(user, amount) fails
    vm.prank(user);
    vm.expectRevert();                   // "SafeERC20: low-level call failed" / blacklist revert
    cdo.claimWithdrawRequest();

    // 6. No alternative path: receipt transfer is blocked too
    vm.prank(user);
    vm.expectRevert(NotAllowed.selector);
    IdleCreditVault(strategy).transfer(helper, receiptBal);

    // Funds remain in the vault; user has no way to redirect payout -> frozen
    assertEq(usdc.balanceOf(strategy), userClaimAmount);
}
```

Same repro applies to `claimInstantWithdrawRequest` (user blacklisted between `requestInstantWithdraw` and `getInstantWithdrawFunds`/claim) and to `IdleCDOEpochQueue.claimWithdrawRequest(epoch)` after `processWithdrawalClaims`.
