### Title
Signer drops `BlockProposal` events with no retry/persistence when `initialize_runloop()` fails at a reward-cycle boundary - ([File: stacks-signer/src/runloop.rs])

### Summary
`RunLoop::run_one_pass` only attempts to process an incoming `SignerEvent` after successfully leaving `State::Uninitialized`; if `initialize_runloop()` errors (e.g. reward-set data transiently unavailable at a reward-cycle boundary), the event — including a `SignerEvent::MinerMessages(BlockProposal)` — is discarded with only a `warn!` log and the function returns `None`. No signer or database write occurs for the proposal before it is dropped.

### Finding Description
In `run_one_pass`, when `self.state == State::Uninitialized`, the code calls `self.initialize_runloop()`; on error it logs, warns "Ignoring event", and returns immediately — before the event is ever handed to `signer.process_event(...)` for any configured signer: [1](#0-0) 

Because `SignerEvent::MinerMessages` chunks are delivered as one-shot, push-based notifications from the node's `StackerDBChannel`/event dispatcher (a `Sender<StackerDBChunksEvent>` fired once per new chunk write, not a persistently re-queryable log), a proposal that arrives during a failing-`initialize_runloop` window is not observable to the signer again unless the miner (or some other StackerDB writer) re-publishes it: [2](#0-1) 

No `signerdb` row is created for a dropped-before-processing proposal (writes only happen inside `signer.process_event`, which is never reached on this path), so there is no local record for the signer to reconcile once it later transitions out of `State::Uninitialized`.

Because reward-cycle boundary heights are public, a miner who wins a slot can deliberately time a single `BlockProposal` gossip to land in this narrow, naturally-occurring window (transient emptiness of the reward-set data source at cycle boundaries is a known, attacker-independent condition), without needing majority signer control, node-operator access, or any auth token.

### Impact Explanation
This is a bounded liveness loss, not a chain-safety break: the specific canonical `BlockProposal` broadcast during the failure window is never delivered to the signer's state machine and never gets a `BlockResponse`, unless the miner re-gossips it. This matches the "signer wedged into never signing valid blocks (liveness)" category, scoped to that one block rather than a permanent wedge of the whole signer. It is repeatable each time a signer restarts/re-initializes near a reward-cycle boundary while a proposal is in flight.

### Likelihood Explanation
Preconditions are narrow but realistic and publicly observable: the signer must be in `State::Uninitialized` and `initialize_runloop()` must fail (documented as happening transiently at reward-cycle boundaries), and a proposal must be gossiped during exactly that window. The attacker needs only their own single miner slot plus normal StackerDB gossip — no privileged role, no majority stake, and no local access — satisfying the allowed threat model. Exploitability, however, depends on timing precision against transient/incidental node-side failures the attacker does not fully control, which lowers practical likelihood.

### Recommendation
Buffer events received while `self.state == State::Uninitialized` (or more generally, while `initialize_runloop`/`refresh_runloop` are failing) instead of discarding them — e.g., retain the last N `MinerMessages` events (or persist a minimal pending-proposal record) and re-dispatch them to `signer.process_event` immediately after a successful (re)initialization, rather than silently returning `None` on failure.

### Proof of Concept
Rust test plan against `stacks-signer/src/runloop.rs` unit-test harness:
1. Construct a `RunLoop` with a mocked `StacksClient`/reward-set source configured to return `Err` for `initialize_runloop()` for the first `K` calls, then `Ok`.
2. Set `self.state = State::Uninitialized`.
3. Call `run_one_pass(Some(SignerEvent::MinerMessages(BlockProposal(..))), &sender)` once during the failing window; assert it returns `None` and that `warn!("Ignoring event...")` fires (or assert no call reaches `process_event`).
4. Assert no row is written to the test `signerdb` for that proposal's `signer_signature_hash`.
5. Advance past `K` failing calls so `initialize_runloop()` succeeds; call `run_one_pass(None, &sender)` (simulating the next tick with no new event).
6. Assert the earlier `BlockProposal` is never processed and no `BlockResponse` is ever produced for it, confirming the event is permanently lost (LIVENESS_DOMAIN wedge for that single proposal).
