### Title
Vault↔cash transfers during the buffer desync `bufferStartVaultAssets`, causing the same assets to be re-counted as a phantom loss in the next epoch's `totalInterestDueNow` - (contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The H-6 bug class is a *gain/loss baseline that is updated on one side but not synced on the other*, so the same price/interest delta is computed twice (or the inverse delta is invented). The direct analog in idle-tranches is `ProgrammableBorrower`'s epoch baseline: `onStopEpoch` snapshots `bufferStartVaultAssets = _currentVaultAssets()` (vault assets only), but `emergencyExitVault` can move assets out of the vault into on-hand cash during the buffer without updating that baseline. At the next `onStartEpoch`, `bufferedVaultDelta = currentVaultAssets - bufferStartVaultAssets` treats the withdrawn amount as a loss, while the same cash is simultaneously added to `epochStartVaultAssets` as principal — so `_vaultNetInterest` reports a phantom loss equal to the redeemed amount and `totalInterestDueNow()` under-reports (or zeroes) real epoch interest.

### Finding Description
`onStopEpoch` records the buffer baseline as vault assets only:

```solidity
// ProgrammableBorrower.sol:259-261
bufferedVaultDelta = 0;
bufferInterest = 0;
bufferStartVaultAssets = _currentVaultAssets();
```

During the buffer (`epochAccountingActive == false`), `emergencyExitVault` is callable and does not touch any baseline — the `epochWithdrawnFromVault` update is skipped because accounting is inactive:

```solidity
// ProgrammableBorrower.sol:361-371
assets = vault.redeem(_shares, address(this), address(this));
if (epochAccountingActive) {
  epochWithdrawnFromVault += assets;
}
```

At the next `onStartEpoch`, the delta is computed against the stale vault-only baseline while the redeemed cash is folded into the new principal baseline:

```solidity
// ProgrammableBorrower.sol:210-219
bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets); // = -R
uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets; // includes R cash
_depositToVault(underlyingToken.balanceOf(address(this)), 0);   // R re-deposited
epochStartVaultAssets = startAssets;                             // principal includes R
```

`_vaultNetInterest` then computes `netDelta = bufferedVaultDelta + earned - principal = -R + V - V = -R`:

```solidity
// ProgrammableBorrower.sol:337-347
uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
```

`IdleCDOEpochVariant._stopEpoch` prices the whole epoch off `totalInterestDueNow()` via `_resolveStopEpochInterest` (contracts/IdleCDOEpochVariant.sol:357, 997-1000), so the phantom loss R directly reduces `lastEpochInterest` and the `mintStrategyTokens`/`_updateAccounting` gain, i.e. tranche NAV.

### Impact Explanation
A phantom loss of R (the redeemed amount) is applied to `totalInterestDueNow`: real epoch interest is reduced by up to R, or entirely masked, and the shortfall is converted into `vaultLoss`. Tranche prices are crystallized too low at `stopEpoch`, so lenders' `requestWithdraw`/claim receipts and NAV are permanently understated — the R cash sits in the borrower contract classified as principal, effectively freezing unclaimed yield. This mirrors the report's impact: the cumulative value is computed against a desynchronized baseline and withdrawal amounts are wrong.

### Likelihood Explanation
The trigger is `emergencyExitVault` during the buffer — an honest owner/manager action explicitly intended for "redeem vault shares back" situations (e.g., reacting to external vault risk between epochs), which is precisely when it would be called. No precondition blocks it during the buffer, and there is no re-sync of `bufferStartVaultAssets` or tracking of buffer-period withdrawals. The resulting mispricing is deterministic on the very next `stopEpoch`. Likelihood is bounded by the need for an (honest) privileged call in a short buffer window, but the window is exactly when such an unwind is rational.

### Recommendation
Track buffer-period vault movements symmetrically: in `emergencyExitVault` (and any path that changes vault assets while accounting is inactive), adjust `bufferStartVaultAssets` by the redeemed assets (e.g., `bufferStartVaultAssets = bufferStartVaultAssets > assets ? bufferStartVaultAssets - assets : 0`), or track a `bufferWithdrawnFromVault` counter added to `earnedAssets` in `_vaultNetInterest`'s buffer delta at `onStartEpoch`. Equivalently, compute `bufferedVaultDelta` against total exposure (`_currentVaultAssets() + onHandCashBaseline`) rather than vault-only assets.

### Proof of Concept
Reproducible Foundry setup (extend `test/foundry/ProgrammableBorrowerCreditVault.t.sol` harness):

```solidity
function testBufferEmergencyExitCreatesPhantomLoss() external {
    uint256 amount = 10_000 * oneScale;
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);          // epoch 1 running, funds in vault

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);              // bufferStartVaultAssets = V, accounting off

    // During buffer, manager redeems R from the vault to on-hand cash
    uint256 shares = programmableBorrower.vaultSharesBalance() / 2;
    vm.prank(manager);
    uint256 R = programmableBorrower.emergencyExitVault(shares);

    // Next epoch starts: baseline desync
    vm.prank(manager);
    cdoEpoch.startEpoch();
    // bufferedVaultDelta == -int(R); epochStartVaultAssets includes R as principal

    vm.warp(cdoEpoch.epochEndDate() + 1);
    // Phantom loss R reduces totalInterestDueNow below the real vault+borrower interest
    uint256 due = programmableBorrower.totalInterestDueNow();
    uint256 trueInterest = /* vault PnL + borrower interest measured off-chain */;
    assertApproxEqAbs(due + R, trueInterest, 2);  // due is understated by R

    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);              // NAV crystallized with phantom loss
    // assert virtualPrice / lastEpochInterest lower than expected by ~R
}
```

Note on confidence: the buffer-desync mechanics follow directly from the code paths cited (`onStopEpoch` baseline write, `emergencyExitVault` skipping baseline updates when `epochAccountingActive == false`, `onStartEpoch` delta computation). I verified there is no compensating baseline update for buffer-period redeems in `ProgrammableBorrower.sol`. The one uncertainty is that the trigger is a privileged-but-honest call rather than a purely unprivileged attacker action — within the stated model this qualifies as "sequencing around honest owner/manager calls," since the accounting flaw itself is unconditioned and deterministically misprices the following epoch.
