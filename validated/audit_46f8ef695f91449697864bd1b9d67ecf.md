### Title
Missing zero-address validation on `new_authority` in `transfer_to_new_account`/`transfer_to_new_account_pda` permits permanent loss of account control - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
The account-authority-callable instructions `transfer_to_new_account` and `transfer_to_new_account_pda` accept a `new_authority: UncheckedAccount` and write it directly into the new `MarginfiAccount.authority` field with no check that it is not `Pubkey::default()`. This is directly analogous to the reported Celo `Proxy._setOwner` issue, where failing to reject the zero address as a new owner can lead to permanent loss of control.

### Finding Description
Both instructions derive/initialize a new `MarginfiAccount` and set its `authority` to whatever `new_authority` account key was supplied by the caller, with the account annotated only as: [1](#0-0) 
No constraint requires `new_authority.key() != Pubkey::default()`. The migration logic then disables the old account and moves all lending positions to the new account, whose new `authority` field can legitimately be the zero pubkey: [2](#0-1) [3](#0-2) 
The same unchecked pattern is repeated in `TransferToNewAccountPda`: [4](#0-3) [5](#0-4) 

Because there is no private key for the all-zero pubkey, any position moved to an account whose `authority == Pubkey::default()` becomes permanently uncontrollable by any real signer: withdrawals, borrows, order placement, emissions-destination changes, and any further `transfer_to_new_account` calls (all of which require `authority` to sign, see `is_signer_authorized` checks) can never be executed again by a legitimate party. This matches the reported bug class precisely — the report explicitly calls out that "some Ethereum clients may default to sending null parameters if none are specified," and the same class of client/integration bug (a dApp, bot, or third-party CPI integration passing an unset/default pubkey) is directly reachable here since `new_authority` is a fully permissionless, user-supplied `UncheckedAccount`.

Notably, marginfi's own off-chain tooling already treats this as a real risk and defends against it client-side: [6](#0-5) 
This confirms the team is aware zero-address transfer is dangerous, but the guard exists only in one CLI code path — not in the on-chain program, which any direct instruction call (including from third-party integrators using raw CPI, SDKs, or scripts that don't replicate the CLI's check) can bypass.

### Impact Explanation
If `new_authority` is ever `Pubkey::default()` (via bug, misconfigured integration, or default/unset parameter), the resulting `MarginfiAccount` — along with all of the user's transferred deposits, borrows, and open orders — becomes permanently unrecoverable by its owner. The old account is disabled (`ACCOUNT_DISABLED`) and its balances zeroed, so there is no rollback path. This is a durable, protocol-level freeze of user funds with direct financial effect, consistent with "durable freeze/inconsistency with financial effect" in scope.

### Likelihood Explanation
`transfer_to_new_account`/`transfer_to_new_account_pda` are permissionless, user-authority-triggered instructions with `new_authority` fully unchecked on-chain. Likelihood of accidental triggering is non-trivial given how common zero/uninitialized pubkey defaults are in SDKs and integrator code (the project's own CLI needed to add a manual guard), and there is no way to recover once triggered.

### Recommendation
Add an explicit on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` (and any other authority-transfer path) rejecting `new_authority.key() == Pubkey::default()`, e.g. via a `check!`/Anchor `constraint` on the `new_authority` account, mirroring the guard already present in `p0-cli/src/processor/account.rs`. Do not rely solely on off-chain/CLI validation for a state-mutating, fund-affecting instruction.

### Proof of Concept
1. Create a `MarginfiAccount` with active deposit/borrow positions using authority `A`.
2. Call `transfer_to_new_account` (or `transfer_to_new_account_pda`) with `authority = A` (signer) and `new_authority = Pubkey::default()`.
3. The instruction succeeds: the old account is disabled and its balances zeroed [7](#0-6) ; the new account is initialized with `authority = Pubkey::default()` [8](#0-7) .
4. No subsequent instruction can be signed as `authority` for the new account (no private key exists for the zero pubkey), so all migrated collateral/liabilities are permanently stuck, recoverable only through protocol-level bankruptcy/liquidation mechanisms rather than by the rightful owner.
