### Title
Post-default instant withdraw receipts bypass the default-recovery haircut and drain `defaultRecoveryReserve` at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` explicitly routes post-finalization requests into `postDefaultRequests` (reserve-backed, haircut already applied), but `requestInstantWithdraw` has no `defaultRecoveryFinalized` branch at all. A receipt created after default finalization is indistinguishable from a funded pre-default receipt and is paid 1:1 by `claimInstantWithdrawRequest` through `_transferFundedClaim`, bypassing the recovery-ratio check — the analog of skipping the second authentication factor with a credential that was never re-validated.

### Finding Description
In `IdleCreditVault.requestWithdraw`, once `defaultRecoveryFinalized` is true the function burns/mints the receipt and records `postDefaultRequests[_user]`, which is later paid via `_transferDefaultRecovery` at the haircut already baked into `virtualPrice` (lines 247–257, 760–767). By contrast, `requestInstantWithdraw` (lines 356–375) only calls `_ensureDefaultRecoveryInitialized()`, then mints receipt tokens and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws` unconditionally — with no `defaultRecoveryFinalized` handling.

On the claim side, `claimInstantWithdrawRequest` (lines 380–393) only applies the defaulted haircut when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. `defaultInstantWithdrawsFinalized` is set to `pendingInstantWithdraws != 0` at finalization (line 696). Therefore:

- If the instant bucket was fully funded at finalization (`pendingInstantWithdraws == 0`, flag false), a **new** post-default instant receipt falls straight to the par path: `_burn(_user, amount)` then `_transferFundedClaim(_user, amount)` — paying full face value with zero haircut.
- The strategy's underlying balance after finalization is effectively `defaultRecoveryReserve` (plus recovery dust). `_transferFundedClaim` transfers from that same balance while `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` assume payouts come only via `_transferDefaultRecovery`, which prices claims at `defaultRecoveryPrice`. A par payout to the attacker leaves the reserve short for legitimate defaulted-epoch claimants, whose later claims revert on insufficient balance.

Broken invariant: one receipt, one recovery-priced payout — a post-default receipt obtains par payout against reserve earmarked for haircutted claims.

### Impact Explanation
Direct theft / insolvency: an attacker holding tranche tokens (or a KYC-passing lender) requests an instant withdraw after default finalization and claims it at 100% of face value, while every honest defaulted claimant is entitled only to `defaultRecoveryPrice` (< 1e18 after a loss). The excess `(1 − defaultRecoveryPrice) × amount` is extracted from `defaultRecoveryReserve`, permanently reducing funds available to defaulted withdraw and instant-withdraw claimants. Loss is bounded only by the reserve size and the attacker's receipt amount.

### Likelihood Explanation
Requires: (a) borrower default with `finalizeDefaultRecovery` executed (honest privileged sequence, allowed by scope), (b) the CDO still permitting `requestInstantWithdraw` post-default — there is no `defaulted()`/finalized check in the strategy function itself, so feasibility depends solely on `IdleCDOEpochVariant` gating, which does not distinguish pre- vs post-default instant requests at the strategy layer, and (c) `pendingInstantWithdraws == 0` at finalization so the haircut branch is skipped (common when instant claims were prefunded). No malicious privileged role is needed; the attacker is any tranche holder.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, either revert or route the receipt through `postDefaultRequests`-style reserve accounting, and in `claimInstantWithdrawRequest` apply the defaulted-epoch haircut based on `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` regardless of the `defaultInstantWithdrawsFinalized` flag. Additionally, make `_transferFundedClaim` unable to spend `defaultRecoveryReserve` (e.g., cap it at `balance − defaultRecoveryReserve`).

### Proof of Concept
Foundry fork sketch (against the epoch-variant vault + `IdleCreditVault` strategy):

```solidity
// 1. Deposit, run epoch, borrower defaults; manager finalizes:
//    finalizeDefaultRecovery(recovered, source) with pendingInstantWithdraws == 0
//    => defaultRecoveryFinalized = true, defaultRecoveryPrice < 1e18,
//       defaultInstantWithdrawsFinalized = false
// 2. Attacker (tranche holder) calls CDO instant-withdraw entry point:
cdo.requestInstantWithdraw(attackerAmount); // -> strategy.requestInstantWithdraw
//    succeeds: no defaultRecoveryFinalized check in the strategy
// 3. Attacker claims:
cdo.claimInstantWithdrawRequest(); // -> strategy.claimInstantWithdrawRequest
//    skipped haircut branch (flag false) -> _transferFundedClaim pays par
assertEq(underlying.balanceOf(attacker), attackerAmount); // full payout
// 4. Honest defaulted claimant now fails or is short:
vm.expectRevert(); // reserve drained: _transferDefaultRecovery underflows balance
cdo.claimWithdrawRequest(victim);
```

Caveat: this hinges on `IdleCDOEpochVariant` still routing instant-withdraw requests after default finalization. The strategy code itself contains no guard, but I did not fully verify the CDO-side entry gating within the available context; if the CDO hard-blocks instant requests post-default, the same asymmetry still leaves defaulted-epoch instant receipts exposed to par payout whenever `defaultInstantWithdrawsFinalized` is false while `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` is nonzero.
