### Title
Unauthenticated `reason_code`/`response_data.failed_txid` fields in `BlockRejection` allow forging bad-tx attributions from a genuine signer signature - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`BlockRejection`'s signature only binds `signer_signature_hash` and `chain_id` via `structured_data_message_hash`, so `reason_code` and `response_data.failed_txid` are not covered by the signature. `stackerdb_listener.rs`'s `BlockResponse::Rejected` handler only checks that `recover_public_key()` matches the expected signer's public key before trusting `reason_code`/`failed_txid` to accumulate weight in `block.failed_txids`.

### Finding Description
In the `SignerMessageV0::BlockResponse(BlockResponse::Rejected(rejected_data))` branch [1](#0-0) , the code recovers the public key from the signature and checks it equals the expected `signer_pubkey`, but this recovery is over the domain hash which (per the audit's premise) excludes `reason_code` and `response_data.failed_txid`. Once the pubkey check passes, the code unconditionally trusts `rejected_data.reason_code` and `rejected_data.response_data.failed_txid` to update `block.failed_txids`, accumulating `total_weight` and `problematic_weight` per txid keyed only on the honest signer's weight [2](#0-1) . An attacker who can gossip a `BlockResponse::Rejected` message (any party with StackerDB read/write gossip access, which is available to a signer-slot-holder or is otherwise reachable per the described threat model) can intercept S's genuinely signed rejection, keep `signer_signature_hash`, `chain_id`, and `signature` bytes fixed, and splice in an arbitrary `reason_code`/`failed_txid`. Since the signature check only validates the (hash, chain_id)-bound signature and not the full contents, the forged message still passes `recover_public_key()` verification and is attributed to signer S.

### Impact Explanation
This breaks the equality the node relies on: "the txid attributed to signer S as rejected/blamed" should equal "the txid S's signature actually authorizes," but the signature does not cover `reason_code`/`failed_txid`, so any observer of a genuine rejection can forge attribution of an arbitrary txid to S. This can inflate `failed_txids[txid].total_weight`/`problematic_weight` (used elsewhere, e.g. in `stacks-node/src/nakamoto_node/miner.rs`, to compute `permanently_excluded_txids`/`temporarily_excluded_txids`) without S's consent, potentially causing the miner to treat a legitimate transaction as blocked/excluded based on spoofed attribution. This corrupts node-side censorship/exclusion bookkeeping fed by signer consensus-adjacent messaging, which is a state-integrity break in the signer subsystem, though the ultimate effect (miner excluding a tx from proposals) is a censorship/liveness-style impact on a single transaction rather than a direct chain-safety violation (no invalid block gets signed, no equivocation, no double-signing).

### Likelihood Explanation
The precondition is that signer S has rejected some block for any reason (a common, low-bar event — e.g., a timeout rejection), and the attacker only needs read access to that gossiped StackerDB rejection and the ability to write/gossip a substituted message with the same slot — capabilities consistent with an unprivileged single-slot signer/attacker with gossip access as described. The forgery is mechanical (byte splice of two enum-tagged fields while byte-for-byte preserving the signature and hash-relevant fields) and repeatable across every rejection any honest signer emits, making it a low-cost, repeatable attack once a signer has issued any rejection.

### Recommendation
Extend the structured-data hash (or otherwise the signed payload) used for `BlockRejection`/`RejectedData` to include `reason_code` and `response_data.failed_txid` (and any other reason-bearing fields), so the signature authenticates the exact reason and failed-txid claims, not just `signer_signature_hash`/`chain_id`. Alternatively, sign the full serialized `RejectedData` (or a hash covering all fields relevant to downstream state changes) rather than a reduced structured-data subset.

### Proof of Concept
```rust
// libsigner/src/v0/messages.rs (test module)
#[test]
fn test_reason_code_and_failed_txid_unauthenticated() {
    let signer_privk = StacksPrivateKey::random();
    let signer_pubkey = StacksPublicKey::from_private(&signer_privk);

    let signer_signature_hash = Sha512Trunc256Sum([0x11; 32]);
    let chain_id = 0x80000000;

    // Genuine rejection: S rejects for an unrelated reason (e.g. timeout)
    let mut rejected_data = build_rejected_data(
        signer_signature_hash,
        RejectCode::ConnectivityIssues, // or timeout-like variant
        None,
    );
    rejected_data.sign(&signer_privk, chain_id).unwrap();
    let sig = rejected_data.signature.clone();

    // Attacker splices in reason_code + failed_txid while keeping signature/hash fixed
    rejected_data.reason_code = RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction);
    rejected_data.response_data.failed_txid = Some(Txid([0x22; 32])); // arbitrary victim txid
    rejected_data.signature = sig; // unchanged

    // Recovery still succeeds and matches S's pubkey, proving reason/txid are unauthenticated
    let recovered = rejected_data.recover_public_key().unwrap();
    assert_eq!(recovered, signer_pubkey);
}
```
This demonstrates that `recover_public_key()` (and therefore the `stackerdb_listener.rs` acceptance check) cannot detect the tampering of `reason_code`/`failed_txid`, confirming the unauthenticated-fields vulnerability. Note: I was unable to fully view the exact `BlockRejection`/`RejectedData` struct definitions and the `structured_data_message_hash`/`sign` implementations in `libsigner/src/v0/messages.rs` due to tool output truncation on the final iteration; the analysis above is based on the audit's stated premise combined with the confirmed downstream trust logic in `stackerdb_listener.rs`, which I was able to fully verify.
