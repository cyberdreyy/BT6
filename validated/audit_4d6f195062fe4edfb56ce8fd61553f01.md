### Title
Incorrect boundary comparison in `_defaultPrefundedInstantReserve` undercounts prefunded instant reserve, permanently locking recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._defaultPrefundedInstantReserve` computes the already-funded portion of current-epoch instant-withdraw receipts by comparing the *current-epoch* claim basis (`instantWithdrawClaimsByEpoch[epochNumber]`) against the *aggregate* unfunded counter (`pendingInstantWithdraws`), which can also contain unfunded instant receipts from older epochs. This is an incorrect boundary comparison between a per-epoch value and a cross-epoch total: whenever stale unfunded instant receipts exist, the prefunded reserve is undercounted (or truncated to zero), so `finalizeDefaultRecovery` computes a lower `recoveryPrice` and a smaller `defaultRecoveryReserve` than the underlying actually held. The excess tokens can never be distributed to recovery claimants (`_transferDefaultRecovery` only spends `defaultRecoveryReserve`, and `_transferFundedClaim` explicitly protects the reserve), so they are permanently stranded in the contract.

### Finding Description
At finalization, the recovery basis includes current-epoch instant claims only when `pendingInstantWithdraws != 0`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:644-649
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

The prefunded portion of those claims is then derived at lines 716-723:

```solidity
uint256 pendingInstant = pendingInstantWithdraws;
if (pendingInstant == 0) return prefundedReserve;
uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;
}
```

`pendingInstantWithdraws` is decremented in `collectInstantWithdrawFunds` (line 401) for *any* epoch's funding, and in `_claimDefaultedInstantWithdrawRequest` (line 852). It is never namespaced per epoch, while `instantWithdrawClaimsByEpoch[epochNumber]` is strictly current-epoch. The correct boundary is `instantBasis` vs. the *current-epoch unfunded remainder*, not vs. the global counter. If an older epoch left `X` unfunded instant receipts and the current epoch's instant bucket of size `B` was partially funded down to `P`, the code computes `instantBasis(=B) > pendingInstant(=P + X)`, yielding `B - (P + X)` instead of `B - P` — undercounting the reserve by `X` (or zeroing it entirely when `B <= P + X`). `defaultRecoveryReserve` and `defaultRecoveryPrice` are then set too low (lines 686-692), the aggregate `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` paid to each claimant is too small, and the uncounted already-held underlyings remain locked: no path can spend reserve-tracked funds except recovery claims, and the reserve never reflects them.

### Impact Explanation
All default-recovery claimants (unprivileged withdraw requesters and instant-withdraw receipt holders) are permanently underpaid by up to the prefunded amount `min(B - P, X)`, and the corresponding underlying tokens are permanently frozen in `IdleCreditVault` — there is no sweep path for reserve-accounted funds (`_transferFundedClaim` reverts when it would touch the reserve, lines 897-906). This satisfies "permanent freezing" of user funds with a quantifiable loss equal to the miscounted prefunded remainder.

### Likelihood Explanation
The trigger requires: (a) an epoch ending with unfunded instant receipts (borrower under-funded `getInstantWithdrawFunds`), leaving `pendingInstantWithdraws > 0`; (b) a later epoch in which new instant receipts are partially funded via `collectInstantWithdrawFunds` so `instantWithdrawClaimsByEpoch[epochNumber] > pendingInstantWithdraws` fails or under-fires; (c) borrower default followed by `finalizeDefaultRecovery`. All steps use only honest privileged sequencing plus an ordinary default; no malicious privileged role is needed. The window is narrow but entirely reachable in production operation.

### Recommendation
Track the unfunded remainder per epoch (e.g., `pendingInstantWithdrawsByEpoch[epochNumber]`, incremented in `requestInstantWithdraw` and decremented in `collectInstantWithdrawFunds`), and compute `prefundedReserve = instantBasis - pendingInstantByEpoch` rather than comparing against the global `pendingInstantWithdraws`. Alternatively, cap `prefundedReserve` to `min(instantBasis, currentEpochUnfunded)` using an epoch-scoped pending counter.
