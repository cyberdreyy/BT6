The report's bug class — a trust binding (whitelisting) that is granted for one purpose but not enforced everywhere it needs to be, causing recorded state to diverge from live reality — maps to a real bug in `multisig2/src/lib.rs`: confirmations are counted by string identity in a `HashSet` and never re-validated against the current `members` set, so a removed member's stale confirmation on an *unrelated* pending request keeps counting toward the execution threshold.

### Title
Deleting a multisig member does not purge their confirmations on requests they didn't create, allowing execution below live-member threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in `multisig2/src/lib.rs` only removes pending requests and confirmations that were *created* by the member being deleted [1](#0-0) . It never scans the `confirmations` map for other, still-pending requests that the removed member had already confirmed. `confirm()` counts confirmations purely by set size compared to `num_confirmations`, with no check that every entry in the set still corresponds to a current member [2](#0-1) . As a result, a former member's confirmation persists and is counted, so a request can execute with fewer confirmations from *currently valid* members than the configured `num_confirmations`.

### Finding Description
`MultiSigContract` stores `confirmations: LookupMap<RequestId, HashSet<String>>`, keyed by `request_id`, containing the string form of each confirming `MultisigMember` [3](#0-2) .

When a member is removed via `DeleteMember`, `delete_member` computes `request_ids` as only the requests whose `MultiSigRequestWithSigner.member` (the request's *creator*) equals the member being deleted, and purges confirmations only for those requests: [4](#0-3) 

If the removed member had instead confirmed (but not created) some other pending request R created by a different member, that confirmation entry remains inside `self.confirmations.get(&R)` untouched — `delete_member` never inspects the `confirmations` map itself, only `self.requests`.

Later, when `confirm()` is called for R by a remaining live member, the threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` [5](#0-4)  still includes the stale entry from the now-deleted member. The check never re-validates that each string in the `HashSet` corresponds to a `MultisigMember` still present in `self.members`.

This breaks the intended equality: `confirmations counted == confirmations from live members`. In reality, `confirmations counted == confirmations from live members + stale confirmations from removed members on requests they didn't create`.

### Impact Explanation
This is Critical per the rubric: "a multisig request executed below threshold." A request (e.g., a `Transfer`, `AddKey`, `FunctionCall`, or even another `DeleteMember`/`AddMember` action) can reach execution with confirmations from fewer than `num_confirmations` *currently authorized* members, because one of the counted confirmations belongs to an account/key that has since been removed from the multisig. Funds can move, keys can be added, or membership can be altered by a quorum that no longer represents the required threshold of trusted parties — undermining the entire K-of-N security guarantee the contract exists to provide.

### Likelihood Explanation
This requires no external attacker privilege beyond the ordinary multisig workflow: any organization that rotates or removes members (a common, expected operation, e.g. offboarding an employee or revoking a compromised key) is exposed if that member had confirmed but not yet triggered execution of any request before being removed. The removed member does not need to act maliciously after removal — their earlier confirmation is silently repurposed. This is a normal operational sequence, not a contrived edge case, making the likelihood of triggering it high in real deployments with active pending requests during a member change.

### Recommendation
When deleting a member, iterate over **all** entries in `self.confirmations` (or maintain a reverse index from member → confirmed request ids) and remove `member.to_string()` from every confirmation set, not just requests the member created. Alternatively, when counting confirmations in `confirm()`, filter the stored set to only those entries whose corresponding member is still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 3 members `{A, B, C}` and `num_confirmations = 2`.
2. Member `A` creates request `R` (`add_request`) targeting some sensitive action (e.g., `Transfer` or `AddKey`).
3. Member `B` calls `confirm(R)` — since `1 < 2`, this just records `B`'s confirmation into `confirmations[R]` (no execution yet).
4. The organization legitimately removes `B` from the multisig via a separate `DeleteMember { member: B }` request that reaches its own threshold and executes `delete_member` — this only purges requests where `r.member == B` (i.e., requests *created* by B), so `confirmations[R]` still contains `B`'s stale entry [1](#0-0) .
5. Member `C` (a live member) calls `confirm(R)`. `confirmations[R].len() == 1` (stale `B`) `+ 1 (C) == 2 >= num_confirmations (2)`, so `execute_request(R)` runs [5](#0-4) .
6. `R` executes with confirmations from only one live member (`C`) plus one removed member (`B`), instead of two live members as the `num_confirmations = 2` threshold requires.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
