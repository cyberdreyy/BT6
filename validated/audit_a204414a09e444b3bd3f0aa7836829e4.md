### Title
Loss-adjusted withdraw receipt is paid at par when a later epoch has no `lossRecoveryPriceByEpoch` entry — epoch-key confusion in `_claimLossAdjustedWithdrawRequest` (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug (CVE-2024-36884) is a type/index confusion: `nvidia_smmu_context_fault` treated a `struct arm_smmu_domain` pointer as a plain `void *`/irq cookie and dereferenced the wrong offset. The idle-tranches analog is epoch-index confusion: `_claimLossAdjustedWithdrawRequest` looks up the loss-recovery price using `lastWithdrawRequest[_user]` — the *latest* request epoch — while the user's claimable basis is a flat aggregate `withdrawsRequests[_user]` that can span *multiple* request epochs. A receipt that was haircut in epoch `E1` is silently re-priced at par once the user's `lastWithdrawRequest` moves to a later epoch `E2` that has no loss price, because the claim falls through to `_claimFundedWithdrawRequest` which pays the whole aggregate at 1:1.

### Finding Description
In `collectWithdrawFunds`, a `stopEpochWithDuration` loss haircut is recorded per-epoch: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, and `pendingWithdraws` is zeroed because only the funded (post-haircut) amount is pulled from the CDO [1](#0-0) .

`claimWithdrawRequest` then tries three paths in order [2](#0-1) :

```solidity
function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;
    ...
}
``` [3](#0-2) 

The lookup keys the *per-epoch* price by a *single* scalar `lastWithdrawRequest`. But the funded claim pays the full aggregate `withdrawsRequests[_user]` (+ APR0 buckets) at par, with no per-epoch filtering [4](#0-3) .

Attack sequence (running → stopped → running phases, normal mode):

1. Epoch `E1`: attacker requests a withdraw (KYC'd lender / tranche holder — unprivileged). `lastWithdrawRequest[attacker] = E1`, `withdrawsRequestsByEpoch[attacker][E1] = X`, `withdrawsRequests[attacker] = X`.
2. Borrower repays with a loss; manager calls `stopEpochWithDuration(_lossAmount)` (honest privileged action). `collectWithdrawFunds` funds `X * price < X`, sets `lossRecoveryPriceByEpoch[E1]`, zeroes `pendingWithdraws`. The strategy now holds only the haircutted `X·p` for that receipt.
3. Epoch `E2` starts. Attacker requests another withdraw `Y` → `lastWithdrawRequest = E2`, aggregate `withdrawsRequests = X + Y`.
4. Epoch `E2` stops fully funded (`collectWithdrawFunds` with `_amount >= pendingBasis`, no price written for `E2`). `epochNumber` is now `E2+1`.
5. Attacker claims: `defaultRecoveryFinalized` is false, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[E2] == 0` → returns 0. `_claimFundedWithdrawRequest` gate `epochNumber (E2+1) <= lastWithdrawRequest (E2)` fails → proceeds, burns `X + Y` receipts and calls `_transferFundedClaim(_user, X + Y)` at par.

The `E1` receipt's haircut `X·(1−p)` is paid out of the strategy's underlying balance — funds that belong to active LPs (the CDO's strategy-token backing) and to other pending claimants.

### Impact Explanation
Direct theft / insolvency. The invariant "a pending receipt can only be paid the amount actually funded for it" is broken: the funded-path pays aggregate basis at par even though part of that basis was only funded at `lossRecoveryPrice < 1`. The overpay `X·(1−p)` is drawn from the strategy's underlying balance, which is active LP collateral — i.e., remaining AA/BB tranche holders absorb a loss that was already crystallized against the epoch-`E1` withdrawer. Quantified: up to the full haircut of the user's prior loss-adjusted request, repeatable across epochs; at the limit (loss price → near zero is prevented by the `lossRecoveryPrice == 0` revert, but e.g. a 50% haircut lets the attacker recover 2× the funded amount for that receipt).

### Likelihood Explanation
High, conditional on `stopEpochWithDuration` losses occurring. No privileged or malicious actor is needed beyond honest manager calls; the attacker is an ordinary withdraw requester performing two `requestWithdraw`s across two epochs and one `claimWithdrawRequest`. The necessary conditions are (a) a loss-adjusted epoch in which the user had a pending receipt, and (b) any later funded epoch where the user re-requests — both routine. Existing guards do not stop it: `lossRecoveryPriceByEpoch` is keyed correctly at write time, `_clearWithdrawClaimForEpoch` only clears the epoch passed in, and the funded-path gate only checks *recency* (`epochNumber <= lastWithdrawRequest`), not whether every constituent receipt was fully funded. Note the symmetric failure also exists in reverse (a loss epoch's price applied to an older par receipt, though clearing is then scoped to that epoch, limiting harm to the attacker themself).

### Recommendation
Key the loss-adjusted claim by the user's actual receipt epochs rather than a single `lastWithdrawRequest` scalar — e.g., iterate `lossRecoveryPriceByEpoch` over all epochs with non-zero `withdrawsRequestsByEpoch[_user][e]` (bounded by tracking a per-user epoch list), or store the haircut price inside the per-user per-epoch record at `collectWithdrawFunds` time. In `_claimFundedWithdrawRequest`, subtract any claim basis belonging to epochs that have a non-zero `lossRecoveryPriceByEpoch` entry (or were defaulted) from the par-paid aggregate, so only genuinely fully-funded basis is paid at 1:1.

### Proof of Concept
Foundry fork sketch (mainnet fork with an `IdleCDOEpochVariant` + `IdleCreditVault` pair):

```solidity
// setup: attacker holds tranche tokens / strategy tokens via CDO
uint256 E1 = vault.epochNumber();

// 1. epoch E1: request withdraw of X underlying-equivalent
cdo.requestWithdraw(X, tranche);           // lastWithdrawRequest[atk] = E1

// 2. manager stops epoch with a loss; borrower funds only X*p
vm.prank(manager);
cdo.stopEpochWithDuration(interest, loss); // -> collectWithdrawFunds(X*p), price p<1 stored at [E1]

// 3. new epoch starts; attacker requests again
uint256 E2 = vault.epochNumber();          // E2 = E1+1
cdo.requestWithdraw(Y, tranche);           // lastWithdrawRequest[atk] = E2

// 4. epoch E2 fully funded
vm.prank(manager);
cdo.stopEpoch(interest);                   // collectWithdrawFunds full, no price at E2

// 5. claim pays X+Y at par instead of X*p + Y
uint256 balBefore = underlying.balanceOf(atk);
cdo.claimWithdrawRequest();                // -> vault.claimWithdrawRequest(atk)
uint256 got = underlying.balanceOf(atk) - balBefore;
assertEq(got, X + Y);                      // expected funded amount: X*p + Y
assertGt(got, X * price_E1 / 1e18 + Y);    // stolen = X*(1-p), drained from LP backing
```

Caveat: I was unable to read `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` in this session to confirm the exact ordering of `epochNumber` bump (in `deposit`, `IdleCreditVault.sol:610`) versus `collectWithdrawFunds`, and the `_transferFundedClaim` balance source. If `epochNumber` at `collectWithdrawFunds` time equals the request epoch (`E1`), the write/read keys are consistent for the single-epoch case but the multi-epoch confusion described above still holds, because the read key (`lastWithdrawRequest`) only ever names the latest epoch.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
