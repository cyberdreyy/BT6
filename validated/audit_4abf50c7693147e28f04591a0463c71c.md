### Title
`juplend_init_position` activates a bank to `Operational` without verifying any fTokens were actually minted for the seed deposit - ([File: programs/marginfi/src/instructions/juplend/init_position.rs])

### Summary
`juplend_init_position` transfers `amount` underlying tokens into the liquidity vault, CPIs into JupLend's `deposit`, and unconditionally flips the bank from `Uninitialized` to `Operational` without ever checking how many fTokens landed in `integration_acc_2`. Because JupLend's deposit-to-shares conversion floors on every step, a sufficiently skewed `token_exchange_price`/`liquidity_exchange_price` ratio on the shared JupLend `Lending` state can cause the minimum allowed seed amount (10) to mint zero or negligible fTokens, yet the bank is still marked `Operational`.

### Finding Description
`juplend_init_position` only enforces a floor on the raw underlying `amount`: [1](#0-0) 

It never reads `integration_acc_2`'s balance before/after the CPI, and never compares against `expected_shares_for_deposit_from_rates` the way `juplend_deposit` does. Compare this to `juplend_deposit`, which explicitly computes `expected_shares`, snapshots `pre_f_token_balance`/`post_f_token_balance`, and `require_eq!`s the minted amount against the expectation: [2](#0-1) 

The underlying conversion function floors at every step: [3](#0-2) 

and the project's own unit tests already document that tiny deposits can floor entirely to zero shares once the exchange price diverges from 1e12: [4](#0-3) 

The `Lending` account (`integration_acc_1`) is a shared JupLend pool state that can be reused by multiple mrgn-wrapped banks (added via admin `lending_pool_add_bank_juplend`) at different points in time, so by the time a new wrapped bank calls `juplend_init_position`, that pool's `token_exchange_price` may already have drifted substantially from the initial 1e12 due to interest/rewards accrual from unrelated activity. If the price ratio has drifted enough that `floor(10 * 1e12 / liquidity_price) -> normalized -> floor(norm * 1e12 / token_price)` rounds to 0 (or a negligible value), the JupLend CPI still succeeds (depositing the underlying token into the pool) but mints ~0 fTokens into `integration_acc_2`. Since `juplend_init_position` performs no post-deposit check, the bank is transitioned to `Operational` regardless.

### Impact Explanation
This produces a durable "dust-activated" bank: `bank.config.operational_state == Operational` while `integration_acc_2` (the fToken vault backing the bank) holds little to no real value, even though `liquidity_vault` and the JupLend-side `lending_supply_position_on_liquidity` reflect that the underlying tokens were spent. Since `Uninitialized -> Operational` is a one-time, unreversible transition (per the module's own doc comment, admin pause paths cannot re-arm this instruction), this misconfiguration cannot be corrected without a privileged intervention outside the reachable instruction set, matching the described `NO_PHANTOM_COLLATERAL` concern: an Operational bank whose recorded fToken backing under-represents/misrepresents the deposit that activated it.

### Likelihood Explanation
Exploitability is conditioned on the shared `Lending` pool's `token_exchange_price`/`liquidity_exchange_price` having drifted enough (empirically, on the order of >10x from 1e12, given the enforced minimum `amount == 10`) that the triple-floor conversion rounds the seed deposit down to (near-)zero fTokens. This is not achievable on a brand-new JupLend pool immediately after `add_pool`, but is plausible for banks added later that reuse a JupLend `Lending` state that has already accrued substantial interest from prior activity (deposits/borrows by other banks/users of the same pool over time), which the instruction imposes no check against. The call itself is permissionless and requires no elevated privileges — any account meeting the `has_one`/PDA constraints can invoke it once per bank.

### Recommendation
Mirror `juplend_deposit`'s verification in `juplend_init_position`: snapshot `integration_acc_2`'s balance before and after the CPI, compute the expected minted shares via `expected_shares_for_deposit_from_rates` using the current `integration_acc_1` exchange prices, and `require_gte!`/`require_eq!` that the actual minted fTokens meet a minimum-viable-backing threshold (nonzero, ideally matching the exact expected value) before allowing the `Uninitialized -> Operational` transition. Consider also enforcing this check strictly for `assets`/`shares` consistency rather than just the raw `amount` floor.

### Proof of Concept
1. Unit/integration test extending `local_tests.rs`/`jlr11_rounding_loop.spec.ts` patterns:
   - Set up a JupLend `Lending` state with `liquidity_exchange_price = 1_000_000_000_000` and `token_exchange_price` inflated to e.g. `11_000_000_000_000` (11x), simulating a mature, shared pool.
   - Add a new mrgn-wrapped bank via `lending_pool_add_bank_juplend` pointed at this pool.
   - Call `juplend_init_position(amount = 10)` (the minimum allowed by `require_gte!`).
   - Assert (expected to fail under current code, illustrating the bug): `integration_acc_2` (fToken vault) balance delta == 0 (or negligible), while `bank.config.operational_state == Operational` and `liquidity_vault`/JupLend `supply_position_on_liquidity` reflect the full 10-unit deposit.
   - After applying the fix, assert the instruction returns `MarginfiError::JuplendInitPositionDepositInsufficient` (or a new dedicated error) instead of transitioning to `Operational`.
2. Fuzz extension: sweep `amount` from 10 upward against varying `token_exchange_price`/`liquidity_exchange_price` ratios and assert `mintedShares > 0` (and ideally `>= MIN_LOOP_SHARES`) is enforced before the state transition, consistent with the existing `jlr11_rounding_loop.spec.ts` rounding-loss probing methodology.

pub fn juplend_init_position(ctx: Context<JuplendInitPosition>, amount: u64) -> MarginfiResult {
    // Require minimum seed deposit amount (same as other integrations)
    require_gte!(
        amount,
        10,
        MarginfiError::JuplendInitPositionDepositInsufficient
    );

    // Transfer underlying tokens from fee payer -> liquidity vault
    ctx.accounts.cpi_transfer_user_to_liquidity_vault(amount)?;

    // Deposit into JupLend via CPI: liquidity_vault -> f_token_vault
    let authority_bump = ctx.accounts.bank.load()?.liquidity_vault_authority_bump;
    ctx.accounts.cpi_juplend_deposit(amount, authority_bump)?;

    // Activate (one-time): Uninitialized -> Operational.
    {
        let mut bank = ctx.accounts.bank.load_mut()?;
        bank.config.operational_state = BankOperationalState::Operational;
    }

    Ok(())
}

#[inline]
pub fn expected_shares_for_deposit_from_rates(
    assets: u64,
    liquidity_exchange_price: u64,
    token_exchange_price: u64,
) -> Option<u64> {
    let liquidity_ex_price = liquidity_exchange_price as u128;
    let token_ex_price = token_exchange_price as u128;
    if liquidity_ex_price == 0 || token_ex_price == 0 {
        return None;
    }

    let registered_amount_raw = (assets as u128)
        .checked_mul(EXCHANGE_PRICES_PRECISION)?
        .checked_div(liquidity_ex_price)?;

    let registered_amount = registered_amount_raw
        .checked_mul(liquidity_ex_price)?
        .checked_div(EXCHANGE_PRICES_PRECISION)?;

    let shares_u128 = registered_amount
        .checked_mul(EXCHANGE_PRICES_PRECISION)?
        .checked_div(token_ex_price)?;

    shares_u128.try_into().ok()
}
