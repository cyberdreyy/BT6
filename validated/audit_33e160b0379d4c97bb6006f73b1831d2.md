### Title
Unfunded instant-withdraw receipts can steal funded withdrawal proceeds from the strategy - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The CVE-2017-9992 bug class — a decoder consuming a crafted input without validating it against the actual buffer bounds — maps here to `claimInstantWithdrawRequest` paying out a receipt without validating that the receipt was actually funded. Instant-withdraw receipts are minted in `requestInstantWithdraw` (IdleCreditVault.sol:356-375) and funded later when the CDO calls `collectInstantWithdrawFunds`, which pulls underlying from the CDO into the strategy and decrements `pendingInstantWithdraws` (IdleCreditVault.sol:398-403). The claim path, however, never checks whether the claimed amount was ever funded: it burns the user's receipt and calls `_transferFundedClaim`, which transfers strategy-held underlying unconditionally as long as the balance is not part of `defaultRecoveryReserve` (IdleCreditVault.sol:380-393, 897-907). Any underlying sitting in the strategy that belongs to funded normal withdraw receipts (`collectWithdrawFunds`, IdleCreditVault.sol:411-430) is therefore reachable by an unfunded instant claimant.

### Finding Description
`requestInstantWithdraw` burns CDO strategy tokens and mints the user a 1:1 receipt, recording it in `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (the *unfunded remainder*, per the comment at IdleCreditVault.sol:849-851). Funding is asynchronous: `collectInstantWithdrawFunds` is called by the CDO at epoch transitions to pull cash for the instant queue. `claimInstantWithdrawRequest` only checks the default-finalization branch, then burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)`. There is no epoch wait (unlike `_claimFundedWithdrawRequest`, which enforces `epochNumber > lastWithdrawRequest` at IdleCreditVault.sol:326-328), and no check that `pendingInstantWithdraws` no longer covers the claimed amount — i.e., no check that the specific receipt was funded.

The crafted-input analog: the "decoder" (`claimInstantWithdrawRequest`) trusts the receipt's face value and reads/writes past the funded "buffer" (cash actually collected for instant claims), paying out from a shared balance that includes other users' funded claims.

### Impact Explanation
An attacker who holds an unfunded instant receipt can claim it immediately against underlying that `collectWithdrawFunds` pulled into the strategy for *normal* withdraw receipts. Those funds are accounted to `withdrawsRequests`/`withdrawsRequestsByEpoch` of honest users; the attacker burns his receipt and takes the cash, leaving honest claimants' `_transferFundedClaim` calls to revert on insufficient balance — direct theft plus permanent freezing of their claims. The `_transferFundedClaim` guard only isolates `defaultRecoveryReserve`; it does not reserve the funded-withdraw bucket. Loss equals the funded pending-withdraw balance drained, up to the attacker's receipt amount.

### Likelihood Explanation
Requires (a) an instant withdraw receipt that is pending funding — obtainable when `lastEpochApr > unscaledApr + instantWithdrawAprDelta` so `requestWithdraw` routes through the instant path (IdleCDOEpochVariant.sol:761-770); APR changes are made by honest roles between epochs, which the attacker can sequence around — and (b) a non-zero strategy underlying balance from previously collected withdraw funds. Both are normal operating states, not edge conditions: pending withdraws are funded at every stopEpoch via `collectWithdrawFunds`. The attacker only needs to claim before his own receipt is funded.

### Recommendation
Track funded vs unfunded instant receipts separately and gate `claimInstantWithdrawRequest` on the receipt's epoch being funded, e.g. revert unless `instantWithdrawsRequestsByEpoch[_user][e]` is covered by a funded epoch, or only allow claiming amounts `<= instantWithdrawClaimsByEpoch`-funded totals. Alternatively, move funded instant cash into a dedicated accounting bucket (like `defaultRecoveryReserve`) that `_transferFundedClaim`-style payouts for other claim types cannot spend, and/or require `epochNumber > requestEpoch` for instant claims so a full funding window elapses first.

### Proof of Concept
Foundry fork sketch (against the epoch-variant CDO + `IdleCreditVault` strategy):

```solidity
// Setup: pool running with APR drop between epochs so instant path is enabled.
// 1. Honest user H requests normal withdraw in epoch N; manager stops epoch,
//    borrower funds -> collectWithdrawFunds moves H's cash into the strategy.
// 2. Attacker A (KYC'd tranche holder) deposits, then calls requestWithdraw
//    while lastEpochApr > unscaledApr + instantWithdrawAprDelta, minting an
//    instant receipt and increasing pendingInstantWithdraws (unfunded).
// 3. Before the next epoch transition collects instant funds, A calls
//    claimInstantWithdrawRequest via the CDO:
//      - instantWithdrawsRequests[A] burned, set to 0
//      - _transferFundedClaim sends H's funded underlying to A
// 4. Assert: A's underlying balance increased by receipt amount while
//    pendingInstantWithdraws still counts A's receipt as unfunded;
//    H's claimWithdrawRequest now reverts (strategy balance shortfall).
```

Key assertion: `pendingInstantWithdraws` was never decremented for A's claim (only `collectInstantWithdrawFunds` decrements it), proving the payout was unfunded and sourced from H's collected withdraw funds.
