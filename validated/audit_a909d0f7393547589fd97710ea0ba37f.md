### Title
External initiator credentials bypass "EIs not allowed" restriction and can trigger arbitrary job runs via `POST /v2/jobs/:ID/runs` due to identity confusion in `AuthenticateExternalInitiator` - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` unconditionally injects a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` into the gin context under `SessionUserKey`, making an EI-authenticated request indistinguishable from a real run-role user session to any downstream code that calls `auth.GetAuthenticatedUser`. `PipelineRunsController.Create` relies on exactly this check (`isUser`) to decide whether integer job-ID runs are permitted, with an explicit code comment stating "only users are allowed to run jobs using int IDs - EIs not allowed" — but the check cannot actually distinguish the two, so EI credential holders can hit the code path meant to be user-only.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates solely via the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers against `bridges.ExternalInitiator` records, then does: [1](#0-0) 

This sets both `SessionExternalInitiatorKey` and `SessionUserKey` — with the *same* `SessionUserKey` used by `AuthenticateBySession`/`AuthenticateByToken` for real user sessions.

`GetAuthenticatedUser` (`core/web/auth/auth.go:178-187`) has no way to tell whether the `*clsessions.User` object it retrieves originated from a real authenticated user or from the synthetic EI stand-in — it just checks presence and type.

`PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go:89-128`) uses this ambiguous signal to gate a feature that its own comment says should be user-only: [2](#0-1) 

Because `isUser` is derived from `auth.GetAuthenticatedUser(c)`, it evaluates to `true` for both real users and EI-authenticated requests, so the "EIs not allowed" comment is not enforced by the code — an EI credential holder that clears `RequiresRunRole` (trivially true since the synthetic user has `Role: UserRoleRun`) can reach the `prc.App.RunJobV2(ctx, jobID, nil)` call using an arbitrary integer job ID from the URL path, with **no check that the target job is associated with the authenticating external initiator**. Unlike the webhook-specific EI trigger path (keyed to a specific EI/job pairing), this endpoint accepts any job ID supplied by the caller.

### Impact Explanation
This is an authorization bypass / cross-identity confusion: an external-initiator credential (which should only be able to trigger runs for the job(s) it's bound to) can instead trigger a pipeline run for **any job** on the node by supplying its integer ID, because the request-binding invariant (EI identity ≠ run-role user identity) is violated in `AuthenticateExternalInitiator`. This maps to Chainlink's "unauthorized job run" bounty impact class — an unprivileged/scoped credential can cause unintended execution of arbitrary job pipelines (potentially including fund-moving or external-effecting jobs) outside its intended scope.

### Likelihood Explanation
Preconditions are minimal: possession of any valid external-initiator access key/secret pair (a low-privilege credential explicitly scoped to trigger only its own bound job) is sufficient. No admin/operator access is required. The exploit is a single HTTP POST with EI headers to `/v2/jobs/:ID/runs` using any target job's integer ID, fully repeatable, and requires no race condition or timing.

### Recommendation
Do not reuse `SessionUserKey`/`GetAuthenticatedUser` to represent external-initiator identity. Introduce a distinct check (e.g. `auth.GetAuthenticatedExternalInitiator(c)`) and explicitly reject EI-authenticated requests in `PipelineRunsController.Create` by checking for `SessionExternalInitiatorKey` presence rather than inferring "isUser" from `GetAuthenticatedUser`. Additionally, if EI-triggered runs by ID are ever intended, add explicit binding verification that the target job belongs to the authenticated external initiator before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Create a job (integer ID `jobID`) not associated with any external initiator.
2. Create an unrelated `ExternalInitiator` record with its own access key/secret (bound conceptually to a different/no job).
3. `POST /v2/jobs/{jobID}/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials, and no session cookie / API token.
4. Assert response is `200 OK` with a created pipeline run resource for `jobID` (demonstrating the "EIs not allowed" comment is not enforced), and that `GetAuthenticatedUser` inside the handler returns `ok=true` with `Role: UserRoleRun` despite no real user session existing — proving cross-identity confusion between EI and user auth methods.
