### Title
JWT replay-protection check-then-act race allows HTTP trigger token reuse - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` verifies a JWT and enforces single-use semantics via a `jwtReplayCache`, but the "check" (`isReplay`) and the "act" (`recordUsage`) are two separate, independently-locked operations rather than one atomic check-and-set. This mirrors the Sudoswap pattern where a cached balance is read, external work happens, and the cache is only updated afterward, leaving a window where the same input can be accepted twice.

### Finding Description
`Authorize` is reachable from an unprivileged client via the internet-facing gateway's HTTP trigger path: `httpTriggerHandler.HandleUserTriggerRequest` → `authorizeRequest` → `WorkflowMetadataHandler.Authorize` [1](#0-0) .

Inside `Authorize`, the JTI replay check and the recording of usage are non-atomic: [2](#0-1) 

The cache primitives themselves take separate locks per call: [3](#0-2) 

Because `isReplay` (RLock, read, RUnlock) and `recordUsage` (Lock, write, Unlock) are not combined into a single atomic "check-and-set" critical section, and because signature verification (`utils.VerifyRequestJWT`) plus the authorized-key map lookup happen in between them, two (or more) concurrent requests carrying the exact same JWT (same `jti`) can both pass `isReplay` before either calls `recordUsage`. This is structurally identical to the Sudoswap bug: a cached "already spent/used" state is read once, real work is performed using stale state, and the cache is updated only after that work — allowing the same credential to be consumed more than once.

### Impact Explanation
An external, unauthenticated network attacker who obtains or intercepts a single valid HTTP-trigger JWT (which is otherwise designed to be single-use per `jti`) can replay it concurrently to bypass the replay-protection guarantee. Because `Authorize` gates `HandleUserTriggerRequest`, a successful bypass results in duplicate workflow executions being dispatched to the DON for the same token/request, i.e., unauthorized duplicate job/workflow runs beyond what the token issuer intended — a direct analog of the "double payment" mechanic in the reference report (spend/credit happens twice off one authorization event).

### Likelihood Explanation
Exploitation requires only the ability to send two requests with the same bearer JWT to the gateway at (or near) the same time — no special network position, no cryptographic break, and no privileged access. The race window spans JWT signature verification and map lookups (non-trivial CPU work), which is realistically wide enough to hit in practice, especially under load or when an attacker deliberately fires parallel requests. This makes the likelihood moderate-to-high for any attacker who has captured a single valid JWT (e.g., via logs, a compromised proxy, or a leaked token) and wants to abuse its "one-time" trust before it naturally expires.

### Recommendation
Make the check-and-record operation atomic under a single critical section (or use an atomic map primitive such as `sync.Map` `LoadOrStore`/a mutex-guarded "reserve" step) so that only one concurrent caller can ever observe `isReplay == false` for a given `jti`. Concretely, replace the separate `isReplay` + later `recordUsage` calls in `Authorize` with a single `jwtCache.reserve(jti) bool` method that takes the write lock once, checks for existence, and inserts atomically if absent, returning false if it was already present. Also consider whether `recordUsage` should happen immediately upon successful signature verification rather than after unrelated authorization-key checks, to minimize any residual reordering risk.

### Proof of Concept
1. Obtain one valid HTTP-trigger JWT for an authorized workflow (`jti = X`).
2. Fire two (or more) `workflows.execute` requests to the gateway concurrently, each carrying the identical JWT.
3. Both requests call `utils.VerifyRequestJWT` successfully and both call `h.jwtCache.isReplay(claims.ID)` before either has called `h.jwtCache.recordUsage(claims.ID)` [4](#0-3) .
4. Both requests pass authorization and are dispatched to the DON via `sendWithRetries`, resulting in two workflow executions from a single "one-time" JWT [5](#0-4) .

Note: I was not able to run a live concurrency test to empirically confirm the race window size in this environment; the finding is based on static analysis of the lock structure, which unambiguously shows the check and the record are not atomic.

		return err
	}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
