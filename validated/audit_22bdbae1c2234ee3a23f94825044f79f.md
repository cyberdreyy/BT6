### Title
Loss-adjusted withdraw receipts are keyed by `epochNumber` at funding time but recovered via `lastWithdrawRequest`, letting pending receipts bypass the haircut and claim at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Pillow advisory is an incomplete-fix bug: a decoding mode combination the earlier patch missed still reaches the vulnerable buffer path. The credit-vault analog is a *residual-state / mismatched-key* bug in the loss-adjusted withdrawal flow. `collectWithdrawFunds` stores the recovery price under the strategy's current `epochNumber`, while `_claimLossAdjustedWithdrawRequest` looks it up under the user's `lastWithdrawRequest` epoch. When these two epoch counters diverge, the loss-adjusted claim path returns zero and the receipt silently falls through to `_claimFundedWithdrawRequest`, which pays the full unhaircutted amount — the same class of "fix applied on one path, bypassed on the other" as CVE-2021-25289.

### Finding Description
When a `stopEpochWithDuration` realizes a loss, the borrower funds only `pendingToFund < pendingWithdraws`. `collectWithdrawFunds` then writes:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:417-421
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
if (lossRecoveryPrice == 0) revert NotAllowed();
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

The claim side, however, indexes by the *user's request epoch*:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:789-794
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
(uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
```

`requestWithdraw` stores `lastWithdrawRequest[_user] = currentEpoch` (line 282), i.e. the epoch in which the request was made. `epochNumber` is incremented inside `deposit()` during `stopEpoch` (lines 607-610). If `collectWithdrawFunds` executes after that increment (the epoch in which funding occurs), the price is stored under `requestEpoch + 1` while the user lookup reads `requestEpoch` → `lossRecoveryPrice == 0` → early return with nothing cleared.

`claimWithdrawRequest` then unconditionally continues:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:312-313
amount += _claimLossAdjustedWithdrawRequest(_user);
return amount + _claimFundedWithdrawRequest(_user);
```

`_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` (which still contains the full, unhaircutted basis since `pendingWithdraws` was zeroed but the user-level ledger was untouched) at par via `_transferFundedClaim`, and burns the receipt tokens — one receipt, full payout, haircut never applied. Because `collectWithdrawFunds` only pulled `pendingToFund` underlying from the CDO, the strategy does not hold enough funded underlying to cover all par claims: earlier claimants drain the balance, and the `_transferFundedClaim` reserve/balance guard (lines 897-906) reverts for later claimants.

Broken invariant: loss socialization / one-receipt-one-payout. Existing guards do not stop it — the `NotAllowed` guard only protects the `defaultRecoveryReserve`, and only *after* insolvency is already realized.

### Impact Explanation
Every pending withdraw receipt in a loss-adjusted epoch is paid at 100% instead of `lossRecoveryPrice`. For a realized loss `L` allocated to the pending bucket (`pendingLoss = _lossAmount * pendingBasis / totalBasis` per `previewLossAdjustedWithdrawFunds`, lines 454-459), first-come claimants collectively overdraw up to `pendingLoss` of underlying that was never funded — direct theft from other claimants and from the strategy's funded balance, and permanent freezing (revert) of the remaining receipts' payouts. Loss equals the full pending-bucket haircut, which scales with `pendingWithdraws` and `_lossAmount`.

### Likelihood Explanation
Requires a `stopEpochWithDuration` with `_lossAmount > 0` while `pendingWithdraws > 0` — a normal (honest) manager action on borrower under-repayment, and any unprivileged user holding a pending receipt benefits. The only precondition is the key divergence between `epochNumber` at `collectWithdrawFunds` time and `lastWithdrawRequest` at request time; per `deposit()` (lines 607-610) `epochNumber` is bumped during `stopEpoch` before receipts are funded, which makes the divergence the default ordering rather than an edge case. Note: I could not fully verify the exact call ordering of `epochNumber += 1` vs `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` within this scan; if funding occurs *before* the increment the keys coincide and the bug does not trigger — this should be confirmed first in a PoC.

### Recommendation
Key `lossRecoveryPriceByEpoch` consistently. Either store the price under the epoch in which the receipts were requested (e.g. pass the request epoch or use `epochNumber - 1` when `collectWithdrawFunds` runs post-increment), or make `_claimLossAdjustedWithdrawRequest` look up the funding epoch and clear all per-epoch receipt entries in `withdrawsRequestsByEpoch[_user][*]` rather than relying on `lastWithdrawRequest`. Additionally, `_claimFundedWithdrawRequest` should clear `withdrawsRequestsByEpoch` entries to avoid stale per-epoch state surviving a funded claim.

### Proof of Concept
Foundry fork PoC sketch (run against `IdleCDOEpochVariant` + `IdleCreditVault`, APR0 disabled):

```solidity
function testLossAdjustedReceiptPaysAtPar() external {
    // 1. Deposit AA and BB during buffer, manager calls startEpoch()
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _startEpoch();

    // 2. Epoch ends; borrower repays principal+interest; manager calls stopEpoch -> epochNumber = 1
    _stopEpochHealthy();

    // 3. Attacker (any tranche holder) requests withdraw in epoch 1
    uint256 trancheAmt = idleCDO.AATranche().balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheAmt, address(AAtranche));
    // strategy.lastWithdrawRequest(attacker) == 1

    // 4. Epoch 1 runs; borrower under-repays by loss L.
    //    manager calls stopEpochWithDuration(L) -> strategy.collectWithdrawFunds(pendingToFund)
    //    is invoked AFTER deposit()/epochNumber += 1 inside stopEpoch,
    //    so lossRecoveryPriceByEpoch[2] = price but lossRecoveryPriceByEpoch[1] == 0
    _stopEpochWithLoss(lossAmount);
    assertGt(strategy.lossRecoveryPriceByEpoch(2), 0);
    assertEq(strategy.lossRecoveryPriceByEpoch(1), 0); // key mismatch

    // 5. Attacker claims: _claimLossAdjustedWithdrawRequest returns 0 (lookup on epoch 1),
    //    _claimFundedWithdrawRequest pays withdrawsRequests at par via _transferFundedClaim
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    uint256 expectedHaircut = requestedBasis * strategy.lossRecoveryPriceByEpoch(2) / RECOVERY_FULL;
    // BUG: attacker receives full requestedBasis, not expectedHaircut
    assertGt(underlying.balanceOf(attacker) - balPre, expectedHaircut);

    // 6. A second receipt holder's claim now reverts in _transferFundedClaim
    //    because balance - reserve < amount -> NotAllowed (funds drained at par)
    vm.expectRevert(NotAllowed.selector);
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();
}
```

Step 4's assertion `lossRecoveryPriceByEpoch(1) == 0` is the crux: it validates the epoch-key divergence before asserting the par payout and the victim's frozen claim.
