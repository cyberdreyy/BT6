### Title
Missing allowlist validation on `profile` path segment allows arbitrary sub-path forwarding to internal plugin debug server - (File: core/web/loop_registry.go)

### Summary
`pluginPPROFHandler` builds the outbound URL to the plugin's internal debug server by concatenating the caller-supplied `profile` route parameter directly into the URL's path (and even into the `fmt.Sprintf` format string itself) with no validation against a fixed set of pprof endpoints. This lets any caller who can reach this route pick which internal `/debug/pprof/*` (or, depending on gin's URL-decoding/route-matching behavior, potentially other) sub-path on the plugin's internal HTTP listener is proxied back to them.

### Finding Description
`pluginPPROFHandler` reads the plugin name and the `profile` route parameter directly from the gin context and appends `profile` unsanitized into the target URL: [1](#0-0) 

Specifically:
```go
pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
```
Note that `gc.Param("profile")` is concatenated into the **format string** before `fmt.Sprintf` runs, not passed as a formatted argument — there is no check that `profile` is one of the legitimate pprof profile names (`heap`, `goroutine`, `cmdline`, `profile`, `trace`, `block`, `mutex`, `allocs`). The registry-side lookup (`l.registry.Get(pluginName)`) only validates that the plugin name is registered — it does nothing to validate or constrain the sub-path being proxied.

`pluginPPROFPOSTSymbolHandler` similarly forwards attacker-controlled request bodies to `/debug/pprof/symbol` on the internal plugin listener: [2](#0-1) 

The `doRequest` helper then blindly forwards the constructed request to the internal plugin host/port and returns the raw response body to the caller: [3](#0-2) 

Because there is no explicit allowlist enforced in `discoveryHandler`'s route family (`pluginMetricHandler`, `pluginPPROFHandler`, `pluginPPROFPOSTSymbolHandler`), the invariant stated in the question ("plugin routes must expose only an explicit allowlist of endpoints, admin-gated") is not enforced at the handler level — the code trusts the caller-supplied `profile` value to be a legitimate pprof endpoint name rather than validating it against a fixed set.

I was not able to retrieve `core/web/router.go`'s exact registration/middleware lines for these routes in this session (tool budget exhausted), so I cannot confirm from the code what auth/role middleware (if any) is applied to `/plugins/:name/pprof/:profile` and `/plugins/:name/pprof/symbol` versus the unauthenticated `/discovery` endpoint. This is a material gap: whether a 'view'-role session can actually reach `pluginPPROFHandler`/`pluginPPROFPOSTSymbolHandler` depends entirely on that router-level gating, which I could not verify.

### Impact Explanation
If the route is reachable by a low-privileged (or under-gated) session, an attacker can pull `/debug/pprof/cmdline`, `/debug/pprof/heap`, or other Go runtime debug data from the plugin's internal debug listener via this proxy, which can leak process command-line arguments, environment-derived configuration, or in-memory data. This matches the "server credential/key theft" bounty impact class only if such data (command line/heap) actually contains node secrets/keys in the specific plugin's process — this depends on the specific LOOP plugin's memory contents and was not independently verified here.

### Likelihood Explanation
Preconditions: a session that can reach the `/plugins/:name/pprof/:profile` and `/plugins/:name/pprof/symbol` routes, and a registered LOOP plugin exposing a Prometheus/pprof port (`EnvCfg.PrometheusPort`). The minimal required privilege level for reaching these routes could not be confirmed in this session because the router.go registration/middleware could not be re-fetched; this is the key unresolved factor determining whether this is exploitable by a 'view'-role user as the question posits, or only by users who already have admin/operator access (in which case it would not qualify under the stated threat model).

### Recommendation
- In `pluginPPROFHandler`, validate `gc.Param("profile")` against an explicit allowlist of legitimate pprof profile names before constructing `pluginURL`, and reject anything else with 400/404.
- Build the URL using `net/url` (e.g., `url.URL{Path: ...}`) rather than string concatenation into a `fmt.Sprintf` format string, to avoid format-string and path-injection classes of bugs entirely.
- Confirm and, if needed, tighten the router.go middleware chain for `/plugins/:name/pprof/*` and `/plugins/:name/pprof/symbol` to require an explicit admin-only role check, not just generic session authentication.

### Proof of Concept
1. Handler-level Go test: instantiate `LoopRegistryServer` with a fake registry containing one registered plugin backed by a local `httptest.Server` acting as the "internal plugin listener," exposing only `/debug/pprof/heap` and `/debug/pprof/cmdline`.
2. Call `pluginPPROFHandler` via a gin test context with `profile` set to a value that is not a real pprof endpoint (e.g., `cmdline?../otherpath` or a value containing `%`) and assert whether the constructed `pluginURL` reaches an endpoint other than the intended `/debug/pprof/<name>`.
3. Router-level integration test (needed to close the confirmed gap): using the actual router setup in `core/web/router.go`, create a session with only the 'view' role and issue `GET /plugins/<name>/pprof/cmdline` and `POST /plugins/<name>/pprof/symbol`; assert whether the response is `403 Forbidden` (expected/secure) or `200 OK` with proxied plugin debug data (vulnerable). This step is required to determine whether the finding is actually reachable by the attacker profile in the question.

func (l *LoopRegistryServer) pluginPPROFHandler(gc *gin.Context) {
	pluginName := gc.Param("name")
	p, ok := l.registry.Get(pluginName)
	if !ok {
		gc.Data(http.StatusNotFound, "text/plain", fmt.Appendf(nil, "plugin %q does not exist", html.EscapeString(pluginName)))
		return
	}

	// unlike discovery, this endpoint is internal btw the node and plugin
	pluginURL := fmt.Sprintf("http://%s:%d/debug/pprof/"+gc.Param("profile"), l.loopHostName, p.EnvCfg.PrometheusPort)
	urlVals, timeout := pprofURLVals(gc)
	if s := urlVals.Encode(); s != "" {
		pluginURL += "?" + s
	}
	l.logger.Infow("Forwarding plugin pprof request", "plugin", pluginName, "url", pluginURL)
	l.doRequest(gc, "GET", pluginURL, nil, timeout, pluginName)
}

func (l *LoopRegistryServer) doRequest(gc *gin.Context, method, url string, body io.Reader, timeout time.Duration, pluginName string) {
	ctx, cancel := context.WithTimeout(gc.Request.Context(), timeout)
	defer cancel()
	req, err := http.NewRequestWithContext(ctx, method, url, body)
	if err != nil {
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "error creating plugin pprof request: %s", err))
		return
	}
	res, err := http.DefaultClient.Do(req)
	if err != nil {
		msg := "plugin pprof handler failed to post plugin url " + html.EscapeString(url)
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}
	defer res.Body.Close()
	b, err := io.ReadAll(res.Body)
	if err != nil {
		msg := fmt.Sprintf("error reading plugin %q pprof", html.EscapeString(pluginName))
		l.logger.Errorw(msg, "err", err)
		gc.Data(http.StatusInternalServerError, "text/plain", fmt.Appendf(nil, "%s: %s", msg, err))
		return
	}

	gc.Data(http.StatusOK, "text/plain", b)
}
