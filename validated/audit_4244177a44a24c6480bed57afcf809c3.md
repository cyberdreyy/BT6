## Analysis

The strongest analog to the Bribe.sol bug class (an incremental total that is bumped on one side of a transition but never adjusted on the reverse transition) is in the node-side signer-response tallying in `stackerdb_listener.rs`, which mirrors `Bribe.deposit()`/`Bribe.withdraw()`/`Bribe.resetVoting()` exactly: weight is added on one action but never removed on the reverse action for the same voter.

### Title
Stale rejection weight is never removed when a signer flips from Rejected to Accepted, allowing a single signer's weight to be double-counted across `total_weight_approved` and `total_weight_rejected` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node's `StackerDBListener` tracks per-block consensus with a `BlockStatus` struct holding independently-incremented counters `total_weight_approved` and `total_weight_rejected` [1](#0-0) . When a `Rejected` message arrives, the signer's weight is added to `total_weight_rejected` and its slot id recorded in `responded_signers` [2](#0-1) . When that same signer later sends `Accepted` for the same block (a legitimate, protocol-supported transition — the signer state machine explicitly allows `LocallyRejected --> LocallyAccepted` on re-evaluation, and `stacks-signer/src/signerdb.rs` even has a dedicated `reject_then_accept` test proving this is sanctioned behavior at the signer-DB level) [3](#0-2) , the handler only adds weight to `total_weight_approved`; it never subtracts the same signer's previously-added weight from `total_weight_rejected` [4](#0-3) .

### Finding Description
This is the exact analog of the `Bribe.sol` flaw: `deposit()` increments `totalVoting`, but `withdraw()`/`resetVoting()` never decrement/clear it, so the aggregate becomes inconsistent with the real, current state. Here:

- `Accepted` handler: `if !block.gathered_signatures.contains_key(&slot_id) { block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight); }` then unconditionally `block.gathered_signatures.insert(...)`, `block.responded_signers.insert(...)` [4](#0-3)  — no code path removes this signer's weight from `total_weight_rejected` even if that slot id already contributed to it.
- `Rejected` handler symmetrically only adds to `total_weight_rejected` on `responded_signers.insert(slot_id)` success [2](#0-1) , again never subtracting from `total_weight_approved` (this direction is actually correct by design, per the comment in `reset_rejections`: "Block approvals cannot be cleared because an old approval could always be used to make a block reach the approval threshold" [5](#0-4) ). But the reverse direction — a *rejection* becoming stale once the signer accepts — has no equivalent safeguard or cleanup.
- The only cleanup mechanism, `reset_rejections`, is called solely on a proposal timeout by the miner's `SignCoordinator::get_block_status` loop [6](#0-5) , not upon receiving a later Accepted from a previously-rejecting signer. Between proposal rounds (i.e. while the same round is still pending), a signer's stale rejection weight persists in `total_weight_rejected` even after that same signer accepts.

This breaks the invariant that each signer's weight should be attributed to at most one current, non-stale bucket. The coordinator's decision logic directly consumes this inflated `total_weight_rejected`:

```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
}
``` [7](#0-6) 

### Impact Explanation
A single signer that legitimately rejects a block and then (per the sanctioned `LocallyRejected -> LocallyAccepted` re-evaluation path) flips to accepting the same block still has its earlier weight permanently counted toward `total_weight_rejected` in this round. If enough signers do this (or if this stale weight, combined with genuinely-rejecting signers, crosses the >30% blocking-minority threshold), the coordinator concludes the block is globally rejected (`SignersRejected`) and abandons it — even though the real, current opinions of the signer set may have already reached the 70% acceptance threshold. This is a miscounted response causing the node/miner to incorrectly treat an approvable block as rejected, a liveness degradation on that block/tenure (the miner is forced to discard a valid, on-its-way-to-being-signed block and re-propose).

### Likelihood Explanation
No majority of signers, no other signer's key, and no StackerDB/transport exploit is required — only one signer whose earlier rejection reason becomes stale/re-evaluable (a normal occurrence, e.g. `should_reevaluate_reject_reason`, chain state catching up, or reproposal) flipping its vote to Accepted within the same round, which the miner can influence by simply re-broadcasting/re-proposing the block (a one-slot-miner-triggerable action) before the timeout-driven `reset_rejections` fires.

### Recommendation
When processing an `Accepted` response for a slot id that is already present in `responded_signers` from a prior `Rejected`, subtract that signer's weight from `total_weight_rejected` (and remove any associated `failed_txids` contribution) before adding it to `total_weight_approved`, mirroring the equivalent cleanup that `stacks-signer/src/signerdb.rs::add_block_signature` already performs by deleting the stale `block_rejection_signer_addrs` row for that signer [8](#0-7) .

### Proof of Concept
1. Node proposes block B to N signers with weight threshold 70%, blocking minority >30%.
2. Signer S (weight w) initially rejects B for a transient reason (e.g. `NotFoundError`/stale burn view) — `handle Rejected`: `total_weight_rejected += w`, `responded_signers.insert(S)` [2](#0-1) .
3. The transient condition clears (matches `should_reevaluate_reject_reason`), S re-evaluates and legitimately signs/accepts B — `handle Accepted`: `total_weight_approved += w`; no corresponding decrement of `total_weight_rejected`.
4. `BlockStatus.total_weight_rejected` still includes S's weight `w`, so combined with other genuinely-rejecting signers whose combined weight is `blocking_minority - w`, the coordinator's check `total_weight_rejected + weight_threshold > total_weight` at [9](#0-8)  triggers, returning `SignersRejected` even though the real current rejecting weight is below the 30% blocking minority once S's flip is accounted for.
