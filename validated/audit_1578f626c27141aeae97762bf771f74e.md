### Title
Underflow in `EscrowDst._withdraw` fee subtraction permanently blocks maker withdrawal and enables secret-leak theft of source funds - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` computes the maker's payout as `immutables.amount - integratorFeeAmount - protocolFeeAmount` using Solidity 0.8 checked arithmetic. Because `immutables.parameters` (which encodes both fee amounts) is supplied verbatim by whoever calls `createDstEscrow`, and there is no on-chain check that `integratorFeeAmount + protocolFeeAmount <= immutables.amount` at destination-escrow creation time, a taker/resolver can create a destination escrow whose fee fields exceed the amount. Any subsequent `withdraw`/`publicWithdraw` call reverts on arithmetic underflow, permanently denying the maker their funds — the exact same root cause described in the external report (unchecked subtraction producing a negative value that panics/reverts and blocks the "liquidation"/withdrawal path).

### Finding Description
`BaseEscrowFactory.createDstEscrow` deploys the destination escrow strictly from caller-supplied `dstImmutables`, funding it with `dstImmutables.amount` in tokens/native currency and validating only the timelock ordering and the `msg.value`/token transfer amount: [1](#0-0) 

Nothing in this function validates the contents of `dstImmutables.parameters`, which is later decoded by `ImmutablesLib` into `protocolFeeAmountCd` / `integratorFeeAmountCd`: [2](#0-1) 

`EscrowDst._withdraw` unconditionally subtracts both fee amounts from `immutables.amount` without any bounds check: [3](#0-2) 

Since Solidity 0.8 arithmetic reverts on underflow, if `integratorFeeAmount + protocolFeeAmount > immutables.amount`, the whole `withdraw`/`publicWithdraw` transaction reverts every time it is attempted (the value is fixed at escrow creation and cannot be corrected later, since `immutables` are hashed/locked via `_validateImmutables`, see `Escrow._validateImmutables` at [4](#0-3) ). This is the destination-chain analog of the reported liquidation bug: an unchecked/unvalidated subtraction that produces a negative value and makes a critical state-transition function permanently unreachable.

Unlike the audited `_postInteraction` path, which does enforce `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();` for the source-side fee computation ( [5](#0-4) ), this guard only protects `EscrowSrc`. It is never re-applied to the resolver-supplied `dstImmutables.parameters` consumed inside `createDstEscrow`/`EscrowDst`, so nothing forces the destination-side fee fields to be consistent with (or even related to) the source-side computation.

Crucially, `EscrowDst.cancel()` refunds the *taker* (the resolver) the full `immutables.amount` with no fee subtraction: [6](#0-5) 

So the party who can set the malformed fee parameters (the taker, via `createDstEscrow`) is also the party who is unaffected by the underflow and who fully reclaims the deposited funds once the cancellation timelock elapses.

### Impact Explanation
This crosses into Critical territory (direct theft of user funds), not just temporary freezing:
1. A malicious/unprivileged taker calls `createDstEscrow` with `parameters` encoding `protocolFeeAmount + integratorFeeAmount > amount`, funding the escrow normally.
2. The maker, believing the destination escrow is correctly funded (client-side checks typically only verify balance/timelocks, not the internal fee split encoded in an opaque `bytes parameters`), reveals the secret by calling `EscrowDst.withdraw`. This transaction reverts due to the underflow, but the `secret` argument is still visible on-chain in the calldata of the (reverted, but included/broadcast) transaction.
3. The taker extracts the leaked secret and uses it to withdraw the maker's funds from the corresponding `EscrowSrc` on the source chain (`EscrowSrc.withdraw`/`withdrawTo`, [7](#0-6) ).
4. The maker can never successfully withdraw on the destination side (every attempt underflows and reverts), and once `DstCancellation` time is reached, the taker calls `EscrowDst.cancel()` to reclaim the full destination amount back to themselves.
Net result: the taker obtains both the maker's source-chain funds and their own destination-chain deposit back, while the maker permanently loses their source funds. This is a direct theft of user funds in motion during the live swap lifecycle, triggered entirely by an unprivileged resolver acting through the public `createDstEscrow`/`withdraw`/`cancel` flow.

### Likelihood Explanation
The trigger requires only crafting `dstImmutables.parameters` (fully attacker-controlled bytes passed to a public, unauthenticated function `createDstEscrow`) such that the two fee values sum to more than `amount`. No privileged role, governance action, or external validator/bridge assumption is needed — any resolver participating in the normal swap flow can perform this. The only precondition is that the maker (or their automated client) does not independently recompute/verify the encoded fee fields before revealing the secret, which is plausible since `parameters` is opaque calldata not decoded by the `createDstEscrow` call itself.

### Recommendation
Enforce a fee-sanity invariant at destination escrow creation, mirroring the guard already present in `_postInteraction`:
```solidity
function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
    ...
    uint256 integratorFeeAmount = dstImmutables.integratorFeeAmountCd();
    uint256 protocolFeeAmount = dstImmutables.protocolFeeAmountCd();
    if (integratorFeeAmount + protocolFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
    ...
}
```
Additionally, `EscrowDst._withdraw` should defensively guard the subtraction (e.g., using unchecked math with a `require`/custom revert that still allows fee-less payout, or capping fees to `amount`) so a malformed `parameters` field can never make `withdraw` permanently unreachable.

### Proof of Concept
1. Taker (resolver) calls `BaseEscrowFactory.createDstEscrow(dstImmutables, srcCancellationTimestamp)` with:
   - `dstImmutables.amount = 1000`
   - `dstImmutables.parameters` encoding `protocolFeeAmount = 600`, `integratorFeeAmount = 600` (sum 1200 > 1000), plus valid recipients.
   - Funds the escrow with `msg.value`/`safeTransferFrom` per `amount` as required by the existing checks — these checks only compare `msg.value`/transferred amount to `dstImmutables.amount`, not to the fee breakdown (`contracts/BaseEscrowFactory.sol:165-185`).
2. Maker calls `EscrowDst.withdraw(secret, immutables)` once `DstWithdrawal` stage begins.
3. Inside `_withdraw`, `integratorFeeAmount (600) + protocolFeeAmount (600) = 1200 > immutables.amount (1000)`, so `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` underflows and the whole call reverts (`contracts/EscrowDst.sol:84-93`).
4. The `secret` is now exposed on-chain (calldata of the maker's transaction). Taker immediately calls `EscrowSrc.withdrawTo(secret, taker, srcImmutables)` to claim the maker's source funds (`contracts/EscrowSrc.sol:53-60,111-119`).
5. After `DstCancellation`, taker calls `EscrowDst.cancel(immutables)`, which sends the entire `immutables.amount` (1000) back to the taker with no fee deduction (`contracts/EscrowDst.sol:64-73`), fully recovering their own deposit while having also stolen the maker's source-chain funds.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
