### Title
ProgrammableBorrower accepts zero ERC4626 shares after depositing pool principal - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower._depositToVault()` deposits underlying assets into the configured ERC4626 vault but never verifies that the vault returned nonzero or economically sufficient shares. [1](#0-0)  An unprivileged vault depositor can use the standard first-depositor/donation pattern to make the facility’s epoch-start deposit mint zero shares, then redeem their own share for both their donation and the pool’s deposit. [2](#0-1) 

### Finding Description
During programmable-borrower epoch startup, `IdleCDOEpochVariant` transfers the pool’s available underlyings to the borrower adapter and invokes `onStartEpoch`. [3](#0-2)  `onStartEpoch` deposits the adapter’s full token balance into the configured ERC4626 vault through `_depositToVault`. [4](#0-3) 

`_depositToVault` records the returned `shares` only in an event and does not check `shares != 0`, compare the result to `previewDeposit`, or validate that `convertToAssets(shares)` covers the deposited assets. [1](#0-0)  ERC4626 `deposit` returns a share count but the interface does not require a nonzero return for a nonzero deposit. [5](#0-4) 

If the vault’s share supply is inflated before `startEpoch`, integer rounding can mint zero shares while the vault keeps the deposit. [1](#0-0)  `ProgrammableBorrower` then reports zero vault assets because `_currentVaultAssets` derives the position solely from its zero vault-share balance. [6](#0-5) 

### Impact Explanation
Suppose the pool starts an epoch with `A` underlyings and the attacker controls one vault share backed by more than `A` assets after a direct donation. [7](#0-6)  The formula `A * totalSupply / totalAssets` rounds to zero, so the vault keeps `A` and `ProgrammableBorrower` receives no shares. [5](#0-4) 

The attacker can redeem their single share for the donated balance plus the stolen `A`, producing a direct profit of approximately `A` minus the one-unit seed deposit. [6](#0-5)  The facility subsequently has neither cash nor vault shares, so the CDO’s borrower pull fails and the epoch enters the default path. [8](#0-7)  The broken invariant is fair custody of deposited principal: pool assets are transferred to an external vault without receiving a redeemable claim. [1](#0-0) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to calculate shares with round-down semantics and include direct donations in `totalAssets`, a common vulnerable vault shape. [9](#0-8)  The attacker only needs to be an ordinary user of that external vault and must temporarily provide enough donated assets to exceed the upcoming facility deposit. [7](#0-6) 

No privileged role is malicious: the honest manager merely calls `startEpoch`, while the attacker controls the vault’s pre-deposit exchange rate through a public deposit and direct token transfer. [10](#0-9)  Existing checks validate the vault address and asset during initialization but do not impose a minimum share or asset-value outcome on each deposit. [11](#0-10) 

### Recommendation
Reject economically empty deposits in `_depositToVault` before updating any accounting. [1](#0-0)  At minimum, require `shares != 0`; preferably compute a same-transaction floor with `previewDeposit(_assetAmount)` or verify `vault.convertToAssets(shares)` is within an explicit bounded tolerance of `_assetAmount`. [12](#0-11) 

The same protection should cover deposits made from `onStartEpoch` and `_repay`, because both paths route pool assets through `_depositToVault`. [7](#0-6) [13](#0-12) 

### Proof of Concept
The Foundry fork test can use a minimal ERC4626-compatible vault whose `totalAssets()` is its token balance and whose deposit mints `assets * totalSupply / totalAssets` rounded down. [9](#0-8) [5](#0-4) 

```solidity
function testZeroShareEpochDepositStealsPoolAssets() public {
    uint256 poolAssets = 1_000_000e6;
    uint256 donation = poolAssets + 1;

    // LP deposits into the credit vault before the epoch starts.
    underlying.mint(lp, poolAssets);
    vm.startPrank(lp);
    underlying.approve(address(cdoEpoch), poolAssets);
    cdoEpoch.depositAA(poolAssets);
    vm.stopPrank();

    // Ordinary external-vault user seeds one share and inflates assets/share.
    underlying.mint(attacker, donation + 1);
    vm.startPrank(attacker);
    underlying.approve(address(externalVault), 1);
    externalVault.deposit(1, attacker);           // attacker receives 1 share
    underlying.transfer(address(externalVault), donation);
    vm.stopPrank();

    // Honest manager starts the epoch. The adapter deposits poolAssets
    // but floor(poolAssets * 1 / (donation + 1)) == 0.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    assertEq(externalVault.balanceOf(address(programmableBorrower)), 0);
    assertEq(programmableBorrower.vaultSharesBalance(), 0);

    // The attacker redeems the only share for donation + seed + poolAssets.
    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    externalVault.redeem(1, attacker, attacker);

    assertEq(
        underlying.balanceOf(attacker) - attackerBefore,
        donation + 1 + poolAssets
    );

    // Closing the epoch cannot recover the principal and enters default.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);

    assertTrue(cdoEpoch.defaulted());
}
```

The decisive assertion is that `vault.deposit` succeeds while `vaultSharesBalance()` remains zero, leaving the pool assets claimable by the attacker’s pre-existing share. [1](#0-0) [14](#0-13)
