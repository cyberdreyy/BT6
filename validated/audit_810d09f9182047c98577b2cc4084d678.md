Checking the ordering of `epochNumber` increment vs `collectWithdrawFunds` during `stopEpoch` in the CDO.### Title
Loss-adjusted withdraw receipts bypass `lossRecoveryPriceByEpoch` haircut because `collectWithdrawFunds` keys the haircut to the post-increment `epochNumber` — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.deposit()` increments `epochNumber` while the epoch is still flagged as running (i.e., during the `stopEpoch` callback), but `collectWithdrawFunds()` stores the realized stop-epoch loss haircut under `lossRecoveryPriceByEpoch[epochNumber]` using the already-incremented value. Receipts requested during the ending epoch carry `lastWithdrawRequest == N`, while the haircut is stored at `N + 1`. The claim path then falls through `_claimLossAdjustedWithdrawRequest` (lookup at epoch `N` returns 0) into `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests` basis at par — the intended loss haircut on pending receipts is never applied. ### Finding Description
- `deposit()` (lines 607–611): when `IIdleCDOEpochVariant(idleCDO).isEpochRunning()` is still true — the in-`stopEpoch` deposit of repaid borrower funds — it executes `epochNumber += 1`.
- `collectWithdrawFunds()` (lines 411–430): on a partial funding (`_amount < pendingWithdraws`, the `stopEpochWithDuration` loss path), it writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws`.
- `requestWithdraw()` (lines 259–293) pins each receipt to `lastWithdrawRequest[_user] = currentEpoch` — the epoch in which the request was made.
- `claimWithdrawRequest()` → `_claimLossAdjustedWithdrawRequest()` (lines 789–801) reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If that is 0 it returns 0, and `_claimFundedWithdrawRequest()` (lines 319–350) pays `withdrawsRequests[_user]` at par once `epochNumber > lastWithdrawRequest[_user]`.

This is the credit-vault analog of the CVE-2023-0590 race/use-after-free class: two operations (`deposit` inside `stopEpoch` and `collectWithdrawFunds`) act on a shared epoch pointer in an order that leaves a stale reference — the haircut keyed to `N+1` while receipts point at `N` — so the cleared/loss-adjusted receipt is still honored at full value through the funded-claim path.

### Impact Explanation
Pending withdraw receipts that should bear a pro-rata share of the realized stop-epoch loss are instead paid 1:1 from strategy-held underlying. The overpayment equals `pendingLoss = pendingBasis * _lossAmount / totalBasis` per `previewLossAdjustedWithdrawFunds` (lines 440–460). Because `pendingWithdraws` was zeroed and only `_amount` underlyings were collected, the strategy is left short: later claimants (including loss-adjusted receipts keyed at `N+1`, funded receipts, and post-default flows drawing on the same funded balance via `_transferFundedClaim`) face insolvency — a direct transfer of the crystallized loss from other LPs/claimants to the early claimant.

### Likelihood Explanation
Requires an unprivileged lender with a pending `requestWithdraw` receipt in the epoch where `stopEpoch` realizes a partial loss (borrower under-repays). No privileged misbehavior needed; the sequencing of honest `stopEpoch` → `deposit` (epochNumber increment) → `collectWithdrawFunds` calls is what mis-keys the haircut. The attacker then simply calls `claimWithdrawRequest()` in any later epoch.

### Recommendation
Key `lossRecoveryPriceByEpoch` to the epoch the receipts were requested in — i.e., store the haircut before the `epochNumber` increment takes effect (e.g., `epochNumber - 1` when called inside `stopEpoch`, or capture the request epoch from `pendingWithdraws` accounting), so it aligns with `lastWithdrawRequest[_user]` lookups in `_claimLossAdjustedWithdrawRequest`.

### Proof of Concept
A Foundry test would: (1) deposit AA/BB, run an epoch, and call `cdoEpoch.requestWithdraw` so `lastWithdrawRequest == N`; (2) call `stopEpochWithDuration`/`stopEpoch` with `_lossAmount > 0` so the borrower under-funds and `collectWithdrawFunds` executes after the internal `deposit` bumped `epochNumber` to `N+1`; (3) warp past the buffer and call `claimWithdrawRequest()`, asserting the payout equals the full request amount instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, and that a second claimant's withdrawal reverts on insufficient funded balance.

Caveat: I could not read `IdleCDOEpochVariant.stopEpoch`'s call order in this session, so the finding hinges on `collectWithdrawFunds` being invoked after the `deposit()` that increments `epochNumber`. If the CDO collects withdraw funds before the deposit hook, the index aligns and this does not trigger; the misalignment should be verified directly against that ordering.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
