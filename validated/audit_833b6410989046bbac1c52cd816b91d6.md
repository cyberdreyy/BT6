### Title
ProgrammableBorrower deposits into ERC4626 vault without minimum-share validation, enabling first-depositor share inflation theft - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
`ProgrammableBorrower` deposits all idle pool assets into an external ERC4626 vault during `onStartEpoch`, but `_depositToVault` accepts whatever share amount the vault returns. An unprivileged vault depositor can create the vault’s first share, donate assets to inflate the share price, and cause the borrower contract’s deposit to mint zero or dust shares. The attacker then redeems their shares and receives both the donation and the pool’s deposited assets.

### Finding Description
`onStartEpoch` snapshots the pre-deposit asset total as `epochStartVaultAssets`, then calls `_depositToVault` with the full contract balance. [1](#0-0)  `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` and records the returned `shares` only in an event; it does not compare the result with `previewDeposit`, `convertToShares`, or a caller-supplied minimum. [2](#0-1) 

In an ERC4626 vault whose conversion uses `assets * totalShares / totalAssets`, an attacker can:

1. Deposit `1` unit into a fresh vault and receive the first share.
2. Donate `D` underlying units directly to the vault.
3. Let `ProgrammableBorrower` deposit `A` underlying units during `onStartEpoch`.
4. If `D + 1 > A`, the deposit mints `floor(A / (D + 1)) = 0` shares.
5. Redeem the attacker’s single share for approximately `1 + D + A`.

The contract’s later solvency views use `vault.balanceOf(address(this))` and `convertToAssets`, so the stolen deposit becomes a vault loss rather than an immediately revertible condition. [3](#0-2) 

### Impact Explanation
The attacker can take the full pool deposit `A`, less the first-deposit unit and any rounding remainder. For example, if the attacker deposits `1`, donates `1_000e6` USDC, and the borrower contract later deposits `999e6` USDC, the borrower receives zero shares while the attacker redeems approximately `1_999e6` USDC.

The loss is eventually surfaced through `vaultLoss`, `totalInterestDueNow`, failed close-pool settlement, or default recovery, but the assets have already left the facility through the attacker’s ERC4626 redemption. [4](#0-3)  A pool close can therefore end in `defaulted` accounting and zero recovery even though the configured borrower did not draw the funds. [5](#0-4) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to permit the inflation pattern and for the attacker to control its first share or otherwise make `previewDeposit(A)` fall below the economically required amount. The attacker can be an ordinary vault user and does not need to control the borrower, manager, owner, guardian, or `ProgrammableBorrower`.

`setVault` is owner/manager controlled, but the vulnerability does not require a malicious vault implementation; it relies on an honest ERC4626 vault with vulnerable share-accounting behavior being configured. [6](#0-5)  Vaults with virtual shares, an initialized minimum supply, or deposit fees may reduce practical exploitability.

### Recommendation
Use ERC4626 `mint` with an exact share amount, or validate the returned shares against a bound derived before execution. Preferably:

```solidity
uint256 expectedShares = vault.previewDeposit(_assetAmount);
uint256 minShares = expectedShares * (BPS - maxDepositSlippageBps) / BPS;
uint256 shares = vault.deposit(_assetAmount, address(this));
if (shares < minShares || shares == 0) revert VaultDepositSlippage();
```

For the first integration deposit, require a non-dust share amount based on `convertToShares(_assetAmount)` and/or `previewDeposit(_assetAmount)`. The deployment process should also reject empty ERC4626 vaults without virtual-share or minimum-liquidity protection.

### Proof of Concept
A Foundry PoC should configure `ProgrammableBorrower` with an ERC4626 vault that has no virtual-share inflation defense, seed the vault through an ordinary depositor account, then call `onStartEpoch` from the configured IdleCDO address.

```solidity
// test/foundry/ProgrammableBorrowerDepositInflation.t.sol
function test_onStartEpoch_shareInflationStealsDeposit() public {
    uint256 donation = 1_000e6;
    uint256 poolAssets = 999e6;
    address attacker = makeAddr("attacker");

    // Configure an ERC4626 vault whose conversion is
    // shares = assets * totalSupply / totalAssets, with no virtual shares.
    deal(address(asset), attacker, 1 + donation);
    deal(address(asset), address(programmableBorrower), poolAssets);

    vm.startPrank(attacker);
    asset.approve(address(vault), 1);
    vault.deposit(1, attacker);                 // first share
    asset.transfer(address(vault), donation);   // inflate share price
    vm.stopPrank();

    vm.prank(idleCDO);
    programmableBorrower.onStartEpoch(0);

    assertEq(vault.balanceOf(address(programmableBorrower)), 0);
    assertEq(vault.totalSupply(), 1);

    uint256 before = asset.balanceOf(attacker);
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);

    // Attacker receives donation + first deposit + pool deposit.
    assertGt(asset.balanceOf(attacker) - before, donation + poolAssets - 1);

    assertEq(programmableBorrower.vaultSharesBalance(), 0);
    assertEq(programmableBorrower.vaultLoss(), poolAssets);
}
```

The PoC can be run against a fork-configured external vault by replacing the local vault setup with the deployed vault address and using the real underlying token. The decisive assertions are that `vault.deposit` returns or leaves `0` shares, `vaultLoss()` equals the deposited principal, and the attacker’s redemption includes the pool deposit. [7](#0-6)
