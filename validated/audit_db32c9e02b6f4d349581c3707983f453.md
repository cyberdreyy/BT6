## Title
Unbounded recursive RLP decoding of `TrieNode` in the fault-proof MPT crate allows stack-overflow DoS via a single malicious preimage - (File: `crates/proof/mpt/src/node.rs`)

### Summary
`TrieNode::decode` recursively decodes Merkle-Patricia-Trie nodes (`Branch`/`Extension`/`Leaf`) directly from RLP with no recursion-depth limit, exactly the bug class described in the docx4j `w:basedOn` advisory (CWE-674/CWE-770 unbounded recursion). Unlike the CBOR parser in this same repo (`crates/proof/tee/registrar/src/cbor.rs`), which enforces `MAX_CBOR_NESTING_DEPTH`, the trie-node decoder has no equivalent guard.

### Finding Description
`Decodable for TrieNode::decode` peeks the RLP header and, for a 2-element list, calls `try_decode_leaf_or_extension_payload`, which for an extension node recursively invokes `Self::decode(buf)` again on the same buffer to decode the pointed-to child node inline: [1](#0-0) 

For a 17-element list it decodes a `Vec::<Self>` (branch node), which itself recursively calls `Self::decode` for each of the (up to 16) children: [2](#0-1) 

The real MPT encoding normally forces any child node ≥32 bytes to be "blinded" (replaced by its keccak256 hash) during `encode`: [3](#0-2) 

but `decode` never verifies that this blinding invariant was honored by the bytes it is given — it simply trusts the RLP grammar (`list_length == 2` ⇒ extension/leaf, `list_length == 17` ⇒ branch) and recurses. An attacker who controls the raw preimage bytes fed to `TrieNode::decode` can therefore construct a single blob containing thousands of nested inline `Extension`/`Branch` structures (each only a few bytes), all decoded within one call stack, with no cap on recursion depth — directly analogous to the cyclic `w:basedOn` style chain in the docx4j advisory causing unbounded recursion in `PropertyResolver`.

This decoder is the trie-node ingestion point for both L1 and L2 chain providers used by the fault-proof program: [4](#0-3) [5](#0-4) 

Both decode preimage-oracle-supplied bytes keyed only by a keccak256 commitment, and the preimage oracle in a dispute game is populated by the party responding to hints (i.e., an untrusted/adversarial participant in the fault-proof/dispute-game flow), so the raw bytes handed to `TrieNode::decode` are attacker-influenced.

### Impact Explanation
A `StackOverflowError`/process abort inside the fault-proof program (or any node deriving/verifying L1 or L2 state via `base-proof-mpt`) terminates the process abnormally rather than failing gracefully. In the context of dispute resolution and derivation, this can crash/halt the honest verifier or fault-proof execution, preventing the correct output root from ever being computed or a dispute from being resolved — matching the "node halt" / "wrong provable output root" impact classes. This is a Denial-of-Service reachable by a dispute-game participant supplying a crafted preimage, consistent with the CVSS `AV:N/AC:L/PR:N/UI:N/.../A:H` profile of the referenced advisory.

### Likelihood Explanation
No cycle or nesting-depth protection exists anywhere in `TrieNode::decode`, `try_decode_leaf_or_extension_payload`, or the recursive `Vec::<Self>::decode` path for branch children — the crate's own README even describes this as "a recursive, in-memory implementation" without mentioning any depth bound: [6](#0-5) 

Constructing a deeply-nested-but-tiny-per-level RLP blob (each extension level a few bytes) requires no special preconditions beyond the ability to supply a preimage blob that satisfies the RLP list-length grammar, making exploitation straightforward once an attacker can supply oracle preimages.

### Recommendation
Add an explicit recursion/nesting-depth limit to `TrieNode::decode` (and its `try_decode_leaf_or_extension_payload` helper), similar to the `MAX_CBOR_NESTING_DEPTH` guard already present in `crates/proof/tee/registrar/src/cbor.rs`, rejecting RLP payloads whose extension/branch nesting exceeds the maximum possible real MPT depth (bounded by nibble-path length, i.e. 64).

### Proof of Concept
Construct an RLP blob representing a chain of inline `Extension` nodes (2-element lists, each child inlined because its encoded length is kept under 32 bytes) nested thousands of levels deep, e.g.:
```
node_0 = leaf
node_i = rlp([path_i, node_{i-1}])   // inline, no blinding, each < 32 bytes
```
Feed the outermost `node_N` bytes as the preimage returned for a queried hash from `OracleL1ChainProvider::trie_node_by_hash` / `OracleL2ChainProvider::trie_node_by_hash`. Calling `TrieNode::decode(&mut node_N.as_ref())` recurses `N` times with no depth check, crashing the process with a stack overflow once `N` is large enough (a few thousand levels).

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }

# `base-proof-mpt`

A recursive, in-memory implementation of Ethereum's hexary Merkle Patricia Trie (MPT).

## Overview

Implements Ethereum's Merkle Patricia Trie with support for retrieval, insertion, deletion, and
root computation via RLP-encoded trie node encoding. Starting from a trie root hash, `TrieNode`
lazily fetches and caches node preimages via `TrieProvider`, enabling stateless block execution
without storing the full state. Designed as the trie backend for [`base-proof-executor`](../executor).
