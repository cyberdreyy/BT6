### Title
User enumeration via distinguishable authentication error messages returned to unauthenticated clients - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` returns different, attacker-visible error strings depending on whether the submitted email exists in the `users` table, and `SessionsController.Create` forwards these raw error messages verbatim to the HTTP client with a 401 status. This lets an unauthenticated caller distinguish registered from unregistered emails, though not via the specific `constantTimeEmailCompare` vs `CheckPasswordHash` comparison the question hypothesizes — that particular branch is effectively dead code.

### Finding Description
`CreateSession` first calls `o.FindUser(ctx, sr.Email)`, which runs `SELECT * FROM users WHERE lower(email) = lower($1)`. If no row matches, the raw database error (e.g. a "no rows in result set"-style error from `sqlx`) is returned immediately: [1](#0-0) .

If a user *is* found, `user.Email` returned from the query is guaranteed (by the `lower(email) = lower($1)` predicate) to case-insensitively equal `sr.Email`, so the subsequent `constantTimeEmailCompare` check at [2](#0-1)  can essentially never fail in this flow — it is dead code, not a reachable attacker-triggerable divergence. The real divergence exercised by an attacker is between (a) the early `FindUser` error path (non-existent email) and (b) the `CheckPasswordHash` failure path returning `"Invalid password"` for an existing email with a wrong password: [3](#0-2) .

`SessionsController.Create` propagates whichever error is returned directly into the JSON API error response with `jsonAPIError(c, http.StatusUnauthorized, err)`: [4](#0-3) . Because the two error values have different text/type, an unauthenticated attacker submitting `POST /sessions` with a guessed email and any password can distinguish "no such user" from "wrong password for existing user," enabling account/email enumeration prior to holding any valid credential.

Additionally, before reaching `CreateSession`, the controller itself calls `GetUserWebAuthn` for any submitted email and returns a 500 on DB error, but this does not itself leak existence information beyond what `CreateSession` already reveals.

Note: the specific mechanism named in the question — a timing/behavioral difference between the `constantTimeEmailCompare` failure ("Invalid email") and `CheckPasswordHash` failure ("Invalid password") paths — is not practically exploitable because the email-mismatch branch cannot be reached through normal `FindUser`-based lookups (the SQL predicate already guarantees a case-insensitive match). The genuine enumeration surface is the distinct error text between the "email not found" (raw DB error) and "Invalid password" paths.

### Impact Explanation
This is a low/informational-severity user enumeration issue: an attacker can determine whether a specific email is a registered node API user without any credentials, which can facilitate targeted credential-stuffing or phishing but does not itself bypass authentication, disclose secrets, or achieve privilege escalation.

### Likelihood Explanation
Trivially reproducible by any unauthenticated network client capable of reaching the `POST /sessions` endpoint; requires no credentials and no special role.

### Recommendation
Return a single generic error (e.g., "invalid email or password") for both the "user not found" and "invalid password" cases in `CreateSession`, and ensure `SessionsController.Create` does not leak internal error text to the client (wrap with a generic message before calling `jsonAPIError`). Remove or clearly document the now-unreachable `constantTimeEmailCompare` check, or restructure so it provides genuine defense rather than dead code.

### Proof of Concept
Go handler-level integration test plan:
1. Seed one user (`existing@example.com`) with a known password hash in the test DB used by `localauth.orm`.
2. Call `orm.CreateSession` with `{Email: "nonexistent@example.com", Password: "wrong"}` and assert the returned error text/type (currently the raw `FindUser` DB error, e.g. contains `sql:`).
3. Call `orm.CreateSession` with `{Email: "existing@example.com", Password: "wrong"}` and assert the returned error is `"Invalid password"`.
4. Assert the two error strings differ, demonstrating enumeration.
5. At the HTTP layer, POST both payloads to `/sessions` via `SessionsController.Create` and assert the JSON API error `detail`/`errors[0].detail` fields differ between the two cases, confirming the leak is externally observable.
