### Title
Rate-limit bypass via hex-case aliasing of `body.Sender` in `processTrigger` - ([File: core/capabilities/webapi/trigger/trigger.go])

### Summary
`triggerConnectorHandler.processTrigger` normalizes the sender address for the allowlist check but uses the raw, unnormalized string for the per-sender rate limiter, allowing an already-allowed sender to bypass per-sender quotas by varying the hex-case of the same Ethereum address across requests.

### Finding Description
In `processTrigger`, the sender's checksummed/normalized form is computed once via `ethCommon.HexToAddress(body.Sender)` in `HandleGatewayMessage` [1](#0-0) , and the allowlist check uses this normalized value: `trigger.allowedSenders[sender.String()]` [2](#0-1) . `ethCommon.Address.String()` always returns the canonical EIP-55 mixed-case representation regardless of the case the caller sent, so `0xABCDEF...` and `0xabcdef...` both normalize to the identical allowlist key and both pass the allowlist check equally.

However, the very next check — the per-sender rate limiter — uses the **raw, un-normalized** input string instead: `trigger.rateLimiter.Allow(body.Sender)` [3](#0-2) . Because `body.Sender` is the attacker-supplied string taken directly off the wire (via `hc.ValidatedMessageFromReq` and the message body) [4](#0-3) , an attacker who is already an allowed sender can submit requests where `body.Sender` alternates hex case for the same underlying address (e.g. `0xAbCd...` vs `0xaBcD...`). The allowlist check treats every variant identically (pass), but if the rate limiter's per-sender bucket keying is based on the exact string value passed to `Allow` (a `map[string]...`-style bucket keyed on the string, which is the typical implementation for such a limiter), each distinct-case variant is treated as a separate bucket. This lets the attacker multiply their effective per-sender quota by the number of distinct case permutations they send, defeating `PerSenderRPS`/`PerSenderBurst`.

The root cause is the inconsistency between the two checks: one normalizes the identity (`sender.String()`), the other does not (`body.Sender` raw string) — violating the invariant that identity-based checks (allowlist and rate limiting) should operate on the same canonical identity.

### Impact Explanation
This is a quota/allowlist bypass: a legitimate but rate-limited sender can flood the shared trigger channel (`ch`, buffered at `defaultSendChannelBufferSize = 1000`) [5](#0-4) [6](#0-5)  by exceeding their configured `PerSenderRPS`/`PerSenderBurst`, causing resource exhaustion for the workflow trigger and potentially starving other legitimate triggers/executions sharing the same channel and downstream workflow engine. This matches Chainlink's "rate-limit/allowlist quota bypass" bounty impact class rather than full node compromise.

### Likelihood Explanation
The attacker only needs to already be a member of `AllowedSenders` for the target trigger (a precondition explicitly granted in this scenario), and control of the `body.Sender` field of a signed gateway request they legitimately send. No additional privilege is required, and case variation of a hex string is trivial and fully attacker-controlled and repeatable — an attacker can generate up to 2^(number of hex digits) distinct-case string variants of the same 40-hex-character address, each usable as a separate bucket.

### Recommendation
Use the normalized `sender.String()` (or equivalently `sender.Hex()`/lower-cased canonical form) consistently as the key passed into `trigger.rateLimiter.Allow(...)`, instead of the raw `body.Sender`, e.g. change line 106 to `trigger.rateLimiter.Allow(sender.String())`. Ensure `TriggerEventID` construction (`body.Sender + payload.TriggerEventId`) at line 111 is reviewed as well, since it also uses the raw un-normalized sender string and could allow distinguishable/duplicate execution IDs for the same sender.

### Proof of Concept
Go test plan for `core/capabilities/webapi/trigger/trigger_test.go`:
1. Register a trigger via `RegisterTrigger` with `AllowedSenders = []string{"0xAbC1230000000000000000000000000000000A"}` (or its checksummed equivalent), and a `RateLimiter` config with `PerSenderRPS` small and `PerSenderBurst = 1`.
2. Call `HandleGatewayMessage` (or directly `processTrigger`) N+1 times with `body.Sender` set to distinct hex-case variants of the same address (e.g. all-lowercase, all-uppercase-hex-digits, mixed case) with valid topics.
3. Assert: with the current code, all N+1 requests succeed (`ACCEPTED`, `fullyMatchedWorkflows` increments each time) despite `PerSenderBurst = 1`, demonstrating the bypass.
4. After applying the fix (normalizing the key passed to `Allow`), assert that only the first request succeeds and subsequent same-address requests (regardless of case) return the `"request rate-limited for sender"` error, confirming the per-sender bucket is now keyed on canonical identity.
