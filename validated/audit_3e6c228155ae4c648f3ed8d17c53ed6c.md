## Finding

### Title
Signer flip‑flopping from Reject to Accept permanently inflates `total_weight_rejected`, letting the miner declare a block globally rejected despite it having actually reached the signing threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::poll_events` tallies per‑block signer responses into a `BlockStatus { total_weight_approved, total_weight_rejected, responded_signers, gathered_signatures, .. }` structure that the `SigningCoordinator` (`signer_coordinator.rs`) polls to decide whether a block has reached the 70% signing threshold or the >30% blocking‑minority rejection threshold. The two response arms use different, asymmetric de‑duplication keys, so a single signer who first rejects and later reconsiders and accepts the very same block (a normal, expected code path per the documented `LocallyRejected --> LocallyAccepted : re-evaluated` transition) gets its weight counted into *both* tallies permanently, since neither tally is ever decremented.

### Finding Description
`BlockResponse::Rejected` handling gates its weight addition on `responded_signers`: [1](#0-0) 

`BlockResponse::Accepted` handling gates its weight addition on the unrelated `gathered_signatures` map, and unconditionally also inserts into `responded_signers` regardless of whether it was already present: [2](#0-1) 

Sequence:
1. Signer S sends `Rejected`. `responded_signers.insert(S)` returns `true` (first time) → `total_weight_rejected += weight(S)`.
2. S later re‑evaluates and sends `Accepted` for the *same* block (this is the documented, expected re‑evaluation path in the signer state machine, not an attack). `gathered_signatures.contains_key(S)` is `false` (its first Accept) → `total_weight_approved += weight(S)` is also applied.

Because `total_weight_rejected` is never decremented when a signer's vote later switches to Accepted (the Accepted branch only touches `gathered_signatures`/`responded_signers`, never `total_weight_rejected`), S's weight is now double‑booked: it counts toward both the approval tally and the (stale) rejection tally simultaneously. This breaks the invariant that `total_weight_approved` and `total_weight_rejected` should reflect the *current*, mutually exclusive set of signer votes ("aggregated-weight vs verified-accepts" equality).

The reverse ordering (Accept first, then Reject) is correctly guarded, because the Accept path already inserts into the shared `responded_signers` set, so a subsequent Reject's `responded_signers.insert()` returns `false` and is a no‑op. Only the Reject‑then‑Accept ordering is vulnerable.

The consuming coordinator loop checks rejection first: [3](#0-2) 
and only falls through to the acceptance branch otherwise: [4](#0-3) 

Because `total_weight_rejected` can retain a stale contribution from a signer who has since switched to Accepted, the sum of the two tallies can exceed `total_weight`, and the rejection‑threshold check (`total_weight_rejected + weight_threshold > total_weight`) can fire using inflated/stale data even while the true, current set of accepting signers has actually reached the real 70% threshold.

### Impact Explanation
This does not corrupt the final on‑chain signature verification (`NakamotoBlockHeader::verify_signer_signatures`, `stackslib/src/chainstate/nakamoto/mod.rs`), since that code recomputes weight strictly from the deduplicated `signer_signature` vector against the reward set. The damage is confined to the miner-side coordinator's *live* bookkeeping (`BlockStatus`), used to decide when to stop waiting for signers and whether to declare `NakamotoNodeError::SignersRejected` (with `temporarily_excluded_txids` / `permanently_excluded_txids`). A block that has, in truth, already reached the 70% signing weight can instead be spuriously treated as rejected by a blocking minority because a single signer's earlier (now‑retracted) rejection is never cleared from `total_weight_rejected`. This is a liveness wedge: the miner drops a legitimately-signable block, and may permanently ban transactions that are not actually problematic (`permanently_excluded_txids`), stalling block production/inclusion for no protocol reason — triggerable by nothing more than one signer's ordinary vote reconsideration plus normal StackerDB gossip propagation/reordering.

### Likelihood Explanation
No majority or malicious collusion is required: a single signer that legitimately changes its mind from reject to accept (an explicitly supported flow, per `should_reevaluate_reject_reason` / `LocallyRejected --> LocallyAccepted` re‑evaluation) combined with ordinary out‑of‑order message delivery over StackerDB triggers the double‑count. This makes the bug reachable in normal operation, not just adversarially.

### Recommendation
Make the two tallies mutually exclusive per slot: track a single per‑slot "current vote" (e.g., an enum keyed by `slot_id`) and recompute `total_weight_approved`/`total_weight_rejected` by summing weights of slots currently in each state, or explicitly subtract the previous vote's weight from the opposite tally before adding it to the new one, e.g. when a slot transitions from Rejected to Accepted, subtract `weight(S)` from `total_weight_rejected` before adding it to `total_weight_approved` (and vice versa).

### Proof of Concept
1. Miner is coordinating a block with `weight_threshold` such that one signer S carries enough weight to matter to the >30% blocking minority.
2. S's signer initially rejects the proposal (e.g., due to a transient chainstate check) and broadcasts `BlockResponse::Rejected`. `stackerdb_listener` records: `responded_signers.insert(S) == true` → `total_weight_rejected += weight(S)`.
3. S's local state machine re‑evaluates and now signs the same block, broadcasting `BlockResponse::Accepted`. `stackerdb_listener` checks `gathered_signatures.contains_key(S) == false` → `total_weight_approved += weight(S)`; `total_weight_rejected` is left untouched.
4. `total_weight_rejected` now permanently includes `weight(S)` even though S is no longer rejecting. If other signers push `total_weight_rejected` further, the coordinator's check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (`signer_coordinator.rs` L509‑519) can fire and return `NakamotoNodeError::SignersRejected`, even though the true, current accept weight (including S) has reached `weight_threshold`.
