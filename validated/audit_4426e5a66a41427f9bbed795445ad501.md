### Title
Stale confirmations from removed multisig members count toward the confirmation threshold, letting a request execute below the required live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`confirm()` counts entries in a request's confirmation set against `num_confirmations` without verifying that every counted confirmer is still a current multisig member. When a member is removed, only the *requests that member created* are purged; confirmations that member previously *added* to requests created by other members are never cleaned up. A stale confirmation therefore keeps counting toward the K-of-N threshold even after the confirming member has been removed, letting a request execute with fewer currently-valid approvers than `num_confirmations` requires.

### Finding Description
The multisig invariant is: `confirmations counted == live members who approved`. This binding is broken because member removal only cleans confirmations for self-created requests, not confirmations placed by that member on other requests.

In `multisig2/src/lib.rs`, `delete_member` removes stale requests only for ones the deleted member created: [1](#0-0) 

But the confirmation set for other requests is a separate structure (`self.confirmations: LookupMap<RequestId, HashSet<String>>`) that is never scanned or scrubbed of the removed member's entries: [2](#0-1) 

`confirm()` blindly trusts the stored confirmation set size to decide when to execute: [3](#0-2) 

`current_member()` is only checked for the *new* confirmer submitting the current call — it never re-validates the membership of confirmers already recorded in the set: [4](#0-3) 

The identical pattern (keyed by public key instead of `MultisigMember`) exists in the v1 contract, where `DeleteKey` execution only purges requests created by that key: [5](#0-4) [6](#0-5) 

**Equality broken:** `confirmations.len() >= num_confirmations` is meant to imply `live_members_who_approved >= num_confirmations`. After a member removal that doesn't touch requests it didn't create, `confirmations.len()` can reach `num_confirmations` while `live_members_who_approved < num_confirmations`.

### Impact Explanation
This is a threshold bypass: a request (e.g., a `Transfer` or `AddKey`/`FunctionCall` action) can be executed by the multisig with genuinely fewer currently-authorized approvers than the configured K-of-N policy guarantees. Per the report's scope, "a multisig request executed below threshold" is a Critical impact — funds or privileged actions (adding a full access key, deploying new code) can move or execute without the intended quorum of live signers.

### Likelihood Explanation
The trigger condition — removing a member/key while other unrelated requests are pending confirmation from that member — is a normal, expected operational event (key rotation, offboarding, replacing a compromised key), not an exotic attacker setup. Any multisig that has ever had a pending request confirmed by a member who was later removed is exposed; the remaining signers (possibly including a colluding minority) can then reach the nominal threshold count using the phantom confirmation and push the request through with fewer real approvers than intended.

### Recommendation
When removing a member (`delete_member`/`DeleteKey`), iterate over **all** active requests' confirmation sets (not just requests created by that member) and remove any entry belonging to the removed member/key. Alternatively, at `confirm()`/execution time, re-validate that every principal in the stored confirmation set is still a current member (filter the set through `self.members.contains(..)`) before comparing its size against `num_confirmations`, and only count still-valid confirmers.

### Proof of Concept
1. Initialize a 3-of-5 multisig with members `M1..M5`.
2. `M1` calls `add_request` to create Request `A` (e.g., `Transfer` of pool funds to an address `M1`/`M2` control).
3. `M2` calls `confirm(A)` → confirmations = `{M2}` (1/3).
4. `M3` calls `confirm(A)` → confirmations = `{M2, M3}` (2/3).
5. Separately, a legitimate `DeleteMember{M2}` request is created and confirmed by other members (e.g., `M1, M3, M4`) and executes, removing `M2` from `self.members` — `delete_member` only purges requests *created by* `M2`, so Request `A` (created by `M1`) is untouched; `M2`'s stale confirmation on `A` remains in `self.confirmations`.
6. `M4` calls `confirm(A)` → confirmations = `{M2, M3, M4}`, `len()+1... == 3 >= num_confirmations(3)` → `execute_request` runs and the transfer/action executes, even though only `M3` and `M4` are currently valid members who approved it (2 live approvers, not 3).

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
