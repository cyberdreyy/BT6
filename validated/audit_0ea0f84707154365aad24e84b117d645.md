## Analysis Result

I found a legitimate analog in `multisig/src/lib.rs`. The bug class matches "confirmations counted versus live members" — a stale confirmation from a key that has since been revoked from the multisig account can still count toward the `num_confirmations` threshold, letting a request execute with fewer genuinely live approvals than the configured threshold.

### Title
Stale Confirmations From Deleted Keys Are Not Purged, Allowing Requests to Execute Below the Effective Threshold - (File: multisig/src/lib.rs)

### Summary
The `confirm()` function counts entries in a per-request `confirmations: HashSet<PublicKey>` against `num_confirmations` to decide whether to execute a request [1](#0-0) . When a `DeleteKey` action is executed, the contract only removes outstanding *requests that were created* by the deleted key (`r.signer_pk == pk`) and the key's `num_requests_pk` entry; it never scans other requests' `confirmations` sets to strip out a confirmation previously cast by that now-deleted key [2](#0-1) . As a result, a confirmation recorded by a public key that is no longer a valid access key on the account remains counted forever against any request it had confirmed but not created.

### Finding Description
The intended custody binding of a K-of-N multisig is: `confirmations counted == number of currently-authorized (live) signers who approved`. This binding is broken because:
- `confirm()` only checks `HashSet<PublicKey>` membership and its length, never cross-checking whether each stored public key is still a valid access key on the contract account [3](#0-2) .
- `DeleteKey`'s cleanup logic filters `self.requests` by `r.signer_pk == pk` only — i.e., it purges requests *authored* by the removed key, not confirmations *cast* by that key on requests authored by someone else [2](#0-1) .
- There is no global registry of "current members" in this contract; the contract's own docs even acknowledge it cannot query the blockchain for the current set of access keys [4](#0-3) .

This is the same "recorded claim vs. current reality" custody-binding break as the external report's Vault bug: there, a recorded deposit balance was decoupled from the actual remaining position via partial withdrawal; here, a recorded confirmation is decoupled from the confirmer's actual current authorization via key deletion, but is still trusted at face value.

### Impact Explanation
This maps to the "Critical" impact bucket explicitly called out in scope: *"a multisig request executed below threshold."* A K-of-N multisig can execute a `Transfer`, `AddKey`/`DeleteKey`, `FunctionCall`, or `DeployContract` request with only `K-1` (or fewer) genuinely live confirming keys, because one of the "confirmations" belongs to a key that was already revoked. This can lead to unauthorized fund transfers, unauthorized key additions (full takeover), or unauthorized code deployment on the multisig account — with an effective threshold lower than the account's configured security policy.

### Likelihood Explanation
This is reachable with only unprivileged, in-scope multisig member actions (no foundation, no owner, no redeploy required):
1. A key gets confirmed on a request it doesn't create.
2. That key is legitimately removed later (e.g., employee offboarding, key rotation) via a separate `DeleteKey` request executed by the remaining members.
3. The stale confirmation persists on the still-pending request.
4. Confirmations from the remaining live keys reach the (now effectively pre-satisfied) count and the request executes with one fewer live approver than intended.

This requires no special race condition beyond ordinary contract usage (confirm, then later delete a different, previously-confirming key) and is fully realizable by legitimate key holders acting within their granted permissions.

### Recommendation
When executing `DeleteKey`, iterate over all entries in `self.confirmations` (not just `self.requests` filtered by `signer_pk`) and remove the deleted public key from every confirmation set. Alternatively, revalidate at `confirm()` time that every public key in a request's confirmation set is still present as a valid access key on `env::current_account_id()` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 3` and keys `K1, K2, K3, K4` as function-call access keys.
2. `K4` calls `add_request` to create request `A` (e.g., `Transfer` to attacker-controlled account). `confirmations[A] = {}`.
3. `K1` calls `confirm(A)` → `confirmations[A] = {K1}` (1 < 3, not yet executed).
4. `K2` calls `confirm(A)` → `confirmations[A] = {K1, K2}` (2 < 3, not yet executed).
5. Separately, members create and fully confirm a `DeleteKey { public_key: K1 }` request (`request.signer_pk` for that request is *not* `K1`, so request `A`'s confirmation set is untouched by the cleanup in lines 198-216 of `multisig/src/lib.rs`). `K1` is now removed from the account's access keys.
6. `K3` calls `confirm(A)` → `confirmations[A].len() + 1 = 2 + 1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`, even though only `K2` and `K3` are actually live, authorized signers at execution time (`K1`'s stale confirmation counted as the third). [5](#0-4) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
