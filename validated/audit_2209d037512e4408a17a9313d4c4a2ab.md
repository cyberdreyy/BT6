## Title
Stale confirmations from deleted multisig members still count toward `num_confirmations`, allowing a request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` counts entries in the raw `confirmations` set for a request against `num_confirmations` without verifying that each confirming identity is still a current multisig member. `delete_member()` only purges requests *originated by* the removed member; it never scans other pending requests to strip a confirmation the removed member previously cast on someone else's request. A request can therefore be pushed to execution using a mix of live and already-revoked confirmations, breaking the invariant that execution requires `num_confirmations` *live* members to have approved it. The same pattern exists in the legacy `multisig/src/lib.rs` (`DeleteKey`).

### Finding Description
`confirm()` decides whether to execute a request purely from the size of the stored confirmation set: [1](#0-0) 

The set is validated only by `assert_valid_request()`, which checks that the *caller* is a member and that the request/confirmations entries exist — it never re-validates the *existing* entries in the confirmations set against the current member list: [2](#0-1) 

`delete_member()` cleans up only requests where the removed member was the *creator* (`r.member == member`); confirmations the removed member cast on requests created by *other* members are left untouched in the `confirmations` map: [3](#0-2) 

Concrete sequence for a 3-member / `num_confirmations = 2` multisig (members A, B, C):
1. C calls `add_request` with a malicious `Transfer`/`FunctionCall` (request `X`, created by C). `confirmations[X] = {}`.
2. A calls `confirm(X)` → `confirmations[X] = {A}` (1 < 2, not yet executed).
3. Separately, a `DeleteMember{A}` request reaches 2 confirmations from B and C and executes, removing A as a member. This only removes requests *created* by A — request `X` (created by C) and its confirmation set `{A}` are untouched.
4. C calls `confirm(X)` again. `confirmations[X].len() + 1 = 2 >= num_confirmations (2)` → the request executes, even though only C is actually a live member among the confirmers; A's confirmation is stale.

The equality that should hold is:
`count(confirmations ∩ live_members) >= num_confirmations`
but the code enforces only:
`count(stored confirmations) >= num_confirmations`
which can include confirmations from accounts/keys that are no longer members.

### Impact Explanation
This directly matches the listed Critical impact "a multisig request executed below threshold." A request (fund transfer, `AddKey`, `DeployContract`, further `DeleteMember`/`AddMember`, arbitrary `FunctionCall` on behalf of the multisig account) can execute with fewer live-member approvals than `num_confirmations` mandates, because a revoked member's stale approval is silently counted. This undermines the entire security assumption of the multisig (k-of-n *current* signer approval) and can be used to move funds or grant access with insufficient real consensus.

### Likelihood Explanation
No compromise of member keys, redeploy, or external/social-engineering step is required — only the ordinary sequence of legitimate multisig operations (create request, partially confirm, later remove that confirming member via a separate legitimate `DeleteMember` action, then have the remaining confirmer finish confirming). This is a plausible operational sequence for any multisig that rotates membership while requests are outstanding, and the remaining confirmer needs no special privilege beyond being a normal member of the multisig — the bug is in a code path anyone can trigger through routine confirm/delete-member usage.

### Recommendation
When counting confirmations in `confirm()` (and when computing `get_num_confirmations`), filter the stored confirmation set to only those entries still present in `self.members` before comparing against `num_confirmations`. Additionally, `delete_member()` should scan all pending requests' confirmation sets (not just requests created by the removed member) and strip the removed member's entry from each, so stale approvals cannot silently count toward future execution.

### Proof of Concept
Using the existing test harness in `multisig2/src/lib.rs` (`MultiSigContract::new(members(), 2)` with 3 members):
1. `add_request` as member C for a `Transfer` action → `request_id`.
2. `confirm(request_id)` as member A (adds A's confirmation, count = 1).
3. Execute a separate `DeleteMember{A}` request confirmed by B and C to remove A as a member (this only clears requests A had *created*, not A's confirmation recorded on step 2's request).
4. `confirm(request_id)` as member C → confirmation count becomes 2 (`stale A` + `C`) which is `>= num_confirmations(2)`, so `execute_request` runs and the `Transfer` is sent, even though A is no longer a member and only one truly live member (C) approved it. [1](#0-0) [3](#0-2)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
