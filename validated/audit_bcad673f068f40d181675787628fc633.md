### Title
Cross-job pipeline run disclosure via missing job/runID ownership check in `PipelineRunsController.Show` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` handles `GET /v2/jobs/:ID/runs/:runID` but never uses the `:ID` path parameter to verify that the requested run belongs to that job. It parses only `:runID`, fetches the run by ID via `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)`, and returns the full pipeline run resource including task inputs/outputs.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Show` (lines 67-84) does: [1](#0-0) 
It calls `pipelineRun.SetID(c.Param("runID"))` and then `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)`, which is a plain global lookup by primary key with no job-scoping predicate — the ORM interface's `FindRun(ctx context.Context, id int64) (Run, error)` signature confirms no job ID parameter is accepted or filtered on: [2](#0-1) 
The `:ID` path parameter (job ID) is read and used in the sibling `Index` handler to scope `PipelineRuns` queries by job (`prc.App.JobORM().PipelineRuns(ctx, &jobSpec.ID, offset, size)`), but `Show` never reads `c.Param("ID")` at all — it is completely unused in that function. As a result, any authenticated user who can invoke this route (with at least view-role authorization on the jobs/runs route group) can supply an arbitrary or unrelated job ID in the path along with a runID belonging to a different job, and the handler will still return that run's full data via `presenters.NewPipelineRunResource`, which serializes pipeline task inputs/outputs (potentially containing bridge responses, secrets embedded in task results, or other sensitive job-specific data).

### Impact Explanation
This is a cross-tenant/cross-job information disclosure: an authenticated user without access rights tied to a specific job can read that job's pipeline run inputs/outputs by guessing or enumerating sequential integer `runID`s (pipeline run IDs are auto-incrementing int64 primary keys), bypassing any job-level access segmentation implied by the `:ID` path parameter. This matches the "unauthorized disclosure of sensitive data" / "cross-user response confusion" bounty impact class, since run outputs can contain bridge/task secrets or proprietary computation results.

### Likelihood Explanation
The only precondition is having any credential capable of invoking node API routes protected at "view" role (no special per-job entitlement is enforced), plus knowledge or brute-force enumeration of a numeric `runID` (small integer space, sequential). No race conditions or timing dependencies are needed — a single GET request with any job ID in the path and the target `runID` in the query path reproduces the issue every time.

### Recommendation
Modify `PipelineRunsController.Show` to parse `c.Param("ID")` into a job ID and pass it into a job-scoped ORM lookup (e.g. add a `FindRun(ctx, jobID, runID)` variant or add a `WHERE pipeline_run.pipeline_spec_id IN (SELECT id FROM pipeline_specs WHERE job_id = ?)` join), returning 404/403 if the run does not belong to the specified job — mirroring the scoping already done in `Index`.

### Proof of Concept
Go handler-level integration test plan:
1. Create Job A and Job B, each with a pipeline spec, and trigger one run per job so Run A belongs to Job A and Run B belongs to Job B (record `RunB.ID`).
2. As an authenticated view-role user, send `GET /v2/jobs/{JobA.ID}/runs/{RunB.ID}`.
3. Assert response status 200 and that the returned pipeline run resource's data (inputs/outputs) matches Run B's data, despite the path specifying Job A — demonstrating the isolation invariant is violated.
4. Additionally assert `FindRun` is invoked with only the runID and no job filter, confirming the root cause in code.

func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
