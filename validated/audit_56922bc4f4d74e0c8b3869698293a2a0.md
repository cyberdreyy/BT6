### Title
Single-step, unchecked authority transfer for `MarginfiAccount` permanently and irrecoverably disables the old account - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
`transfer_to_new_account` / `transfer_to_new_account_pda` let a `MarginfiAccount`'s authority migrate all positions to a brand-new account under a `new_authority` in a single, one-step, non-reversible instruction. The `new_authority` account is explicitly documented as unchecked and there is no on-chain validation (e.g., zero-address check, two-step accept/claim) before the old account is permanently disabled.

### Finding Description
The instruction accounts struct marks the destination authority as completely unvalidated: [1](#0-0) 

and the handler unconditionally finalizes the migration in the same transaction: it sets `migrated_to`, zeroes out the old account's `lending_account`, and disables it via `ACCOUNT_DISABLED`, with no separate claim/acceptance step from `new_authority`: [2](#0-1) [3](#0-2) 

This is precisely the bug class in the report: a critical, security-relevant address change (transfer of account ownership/authority) is performed as a single irreversible step rather than a propose-then-claim two-step process. The report's stated risk — "if an incorrect address is used accidentally... it will force [recovery] and require appropriate changes" — maps directly here: once `transfer_to_new_account`/`transfer_to_new_account_pda` executes with a wrong `new_authority`, the old account is disabled (`ACCOUNT_DISABLED`), its lending positions are zeroed, and `migrated_to` is permanently set, blocking any retry (`AccountAlreadyMigrated` is enforced on the old account going forward): [3](#0-2) 

Unlike the `MarginfiGroupConfigure` admin-authority changes (which are a privileged-admin path and out of scope per the analog rules), this transfer is initiated by the unprivileged account authority (a regular user), making it a valid unprivileged-user analog to the reported issue.

Only the off-chain CLI wrapper checks for the zero pubkey before submitting the transaction; this is a client-side convenience, not an on-chain guarantee: [4](#0-3) 

The core protocol instruction itself performs no such validation, and the TypeScript test even flags this explicitly: [5](#0-4) 

### Impact Explanation
If a user (or an integrator building on top of `transfer_to_new_account`/`transfer_to_new_account_pda`) supplies an incorrect `new_authority` (e.g., a typo'd pubkey, an address for which they don't control the private key, or the system default `Pubkey::default()`), all funds/positions migrated to the new account become permanently inaccessible to the original authority. There is no owner-side recourse: the old account is disabled and cannot be reused (`AccountAlreadyMigrated`), and there is no pending/claim step that would allow catching the mistake before it becomes irreversible. This is a durable, financially-impactful loss-of-funds condition for the affected user, consistent with "durable freeze/inconsistency with financial effect."

### Likelihood Explanation
The instruction is fully permissionless for the account's own authority and requires only a single signature and a plain `Pubkey` argument for `new_authority` with no validation, no timelock, and no two-step confirmation. Any legitimate user calling this instruction directly (via CLI, SDK, or a third-party integration) with a malformed or incorrect target key triggers the loss immediately upon confirmation — this requires no adversarial action, only ordinary human/input error, which the original report also identifies as the realistic threat model.

### Recommendation
Introduce a two-step transfer for `transfer_to_new_account`/`transfer_to_new_account_pda`:
1. First step: the current authority proposes `new_authority` (stored as a "pending" migration target on the old account) without disabling the old account or moving positions.
2. Second step: a transaction signed by `new_authority` claims the migration, at which point the old account is finalized/disabled and balances are moved.

At minimum, add an on-chain check rejecting `new_authority == Pubkey::default()`, and document/require integrators to add a "sanity-check" confirmation (e.g., requiring `new_authority` to sign a marker instruction) before the transfer is finalized irreversibly.

### Proof of Concept
1. User A creates a `MarginfiAccount` with active bank positions (deposits/borrows).
2. User A calls `transfer_to_new_account` with `new_authority` set to a pubkey they don't control the private key for (e.g., a typo or a burn address), per [6](#0-5) .
3. The instruction executes in one step: `new_account` is initialized with `new_authority` as owner, and `old_account` is irreversibly disabled and zeroed, per [7](#0-6) .
4. Any subsequent attempt by User A to retry or reverse the transfer on the old account fails with `AccountAlreadyMigrated`, per [3](#0-2) , permanently locking the migrated funds/positions.

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,

    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
