### Title
Unclaimed APR0 withdraw receipt bricks `stopEpoch` after any APR increase, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` unconditionally reverts `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. Any lender can create a non-zero `apr0TotalPrincipal` by calling `requestWithdraw` while the pool APR is 0. If the APR is subsequently raised (an ordinary, honest manager operation between epochs or via `_newApr` semantics), every `stopEpoch`/`stopEpochWithDuration` call reverts inside the epoch state machine. The epoch can never close, `claimWithdrawRequest` can never mature (epochNumber is only incremented by `deposit` during `stopEpoch`), and all tranche-holder funds are frozen in the vault. This is the direct analog of the Xen "incorrect assertion" host crash: a cheap unprivileged action creates a state in which a hard assertion on a privileged routine permanently fails.

### Finding Description
The flow:

1. Pool operates at `unscaledApr == 0` (APR0 mode is a first-class supported mode; `requestWithdraw` routes to `_requestWithdrawApr0` when `unscaledApr == 0`).
2. Attacker (any KYC-passing lender) calls `IdleCDOEpochVariant.requestWithdraw`. The strategy mints them a receipt and `_requestWithdrawApr0` sets `apr0Users[attacker].principal = amount`, `principalEpoch = epochNumber`, and increments `apr0TotalPrincipal` (`contracts/strategies/idle/IdleCreditVault.sol:567-577`).
3. Attacker simply never calls `claimWithdrawRequest`, so `apr0Users[attacker].principal` is never settled/cleared (`_settleApr0` only runs on claim or on a subsequent request by the same user, `IdleCreditVault.sol:545-565`).
4. The honest manager later raises the APR via `setAprsWithBuffer`/`setApr` (`IdleCreditVault.sol:217-235`) — a routine configuration change, or it is carried over from `_setScaledApr(_newApr)` inside a stop that occurred while `apr0TotalPrincipal` was still nonzero for an earlier epoch.
5. On the next `stopEpoch`, `IdleCDOEpochVariant._stopEpoch` calls `_strategy.prepareStopEpochWithApr0(_interest)` at `IdleCDOEpochVariant.sol:362`, which hits:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:505-508
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`apr0TotalPrincipal` is only ever reset at `IdleCreditVault.sol:540` *after* this check, or by the attacker's own claim through `_clearWithdrawClaimForEpoch` (`IdleCreditVault.sol:822-830`), which itself requires an epoch boundary that can no longer be reached. The assertion therefore fails on every subsequent `stopEpoch` call.

### Impact Explanation
While `stopEpoch` reverts:

- `epochNumber` is never incremented (it only advances inside `deposit` during stopEpoch, `IdleCreditVault.sol:607-610`), so every pending withdraw request stays immature (`epochNumber <= lastWithdrawRequest` check at `IdleCreditVault.sol:326` keeps reverting).
- `isEpochRunning` stays true, deposits stay paused, withdraw requests stay disabled (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` remain false from `startEpoch`).
- The pool is hard-frozen for the entire epoch horizon: no user can exit, and no new epoch lifecycle can proceed.

Recovery requires the owner/manager to notice, set `unscaledApr` back to 0, and run one full stopEpoch to flush the bucket — i.e., the freeze duration is bounded only by operator response and governance latency, and it forces the pool to keep operating at APR 0 for an extra epoch cycle (interest denial on the whole TVL). On a 10M TVL vault at a 10% APR, each additional locked epoch of ~30 days forfeits ~82k of yield and blocks all exits for that period.

### Likelihood Explanation
- Attacker cost is one `requestWithdraw` (principal is returned later — the receipt is not sacrificed, only held). Any KYC'd tranche holder qualifies; no collusion, no privileged role, no oracle manipulation.
- The trigger condition (an APR change while an APR0 receipt is open) is a normal operational action, not an attacker-controlled edge: APRs are expected to float between epochs, and there is no guard preventing `setApr` while `apr0TotalPrincipal != 0`.
- The revert is unconditional and located on the only code path that closes an epoch; nothing else clears `apr0TotalPrincipal` for a non-claiming user, so once reached, 100% of `stopEpoch` calls fail.

### Recommendation
Do not gate `stopEpoch` on `unscaledApr`. Either:
- Settle the open APR0 bucket lazily inside `prepareStopEpochWithApr0` at the stored `apr0RateByEpoch` / zero rate regardless of the current APR (the bucket is already snapshotted per epoch), or
- Reject `setApr`/`setAprsWithBuffer` transitions away from 0 while `apr0TotalPrincipal != 0`, pushing the invariant to the configuration edge instead of the epoch-closing critical path, or
- Allow `stopEpoch` to force-close the APR0 bucket (`apr0TotalPrincipal = 0`) and treat open APR0 receipts as settled principal-only when APR is nonzero.

### Proof of Concept
Foundry fork-style PoC (against the repo's own test harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testApr0ReceiptBricksStopEpochAfterAprRaise() external {
    // Setup: zero fees for clarity, APR0 mode
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // unscaledApr = 0

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Epoch 0 runs at APR 0
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // epochNumber -> 1, unscaledApr still 0

    // Attacker: normal KYC'd lender opens an APR0 withdraw request in the buffer
    address attacker = makeAddr("apr0-griefer");
    _depositWithUser(attacker, amount, true);
    uint256 bal = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(bal / 2, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // Honest manager raises APR for the next epoch (ordinary config change)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e18, 5e18); // unscaledApr = 5e18

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint256).max);
    underlying.approve(address(cdoEpoch), 0);

    // Every stopEpoch now reverts: assertion failure -> frozen vault
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker still refuses to claim; epochNumber cannot advance,
    // all pending claims revert, all LP funds remain locked.
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
    assertTrue(cdoEpoch.isEpochRunning());
}
```

The revert originates at `IdleCreditVault.sol:506-508` (`unscaledApr != 0 && apr0TotalPrincipal != 0`) reached from `IdleCDOEpochVariant.sol:362`, with the unclaimed receipt created through `requestWithdraw` → `_requestWithdrawApr0` (`IdleCreditVault.sol:567-577`).
