Confirmed: `multisig2/src/lib.rs`'s `delete_member` has the exact same flaw as `multisig/src/lib.rs`'s `DeleteKey` handler — it purges only requests *originated by* the removed member (`filter_map(|(k, r)| if r.member == member ...)`), but never scans `self.confirmations` for entries where the removed member is a *confirmer* on requests originated by other, still-live members. That stale confirmation remains counted in `confirm()`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check.

### Title
Stale confirmations from removed multisig members still count toward execution threshold - (multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
The multisig contracts let a request execute once `confirmations.len() + 1 >= num_confirmations`. When a member/key is removed, the code deletes only the *requests that member originated*, but never removes that member's *confirmations on other pending requests*. A confirmation recorded by a member who is later removed keeps counting toward the k-of-n threshold, letting a request execute with fewer currently-authorized approvers than the configured threshold requires.

### Finding Description
In `multisig/src/lib.rs`, `confirm()` checks the threshold purely against the size of the `confirmations` `HashSet<PublicKey>` stored for a request: [1](#0-0) 

When a key is removed via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes requests whose *original signer* (`r.signer_pk`) equals the deleted key, then removes the `num_requests_pk` entry for that key and deletes the on-chain access key: [2](#0-1) 

It never iterates `self.confirmations` to strip the removed key's public key from confirmation sets of requests it merely *confirmed* (but did not originate). Those stale confirmations remain in place and are still counted the next time `confirm()` computes `confirmations.len() as u32 + 1 >= self.num_confirmations`.

The identical pattern exists in `multisig2/src/lib.rs`'s member-based rewrite: `delete_member()` filters requests by `r.member == member` (i.e., only requests *originated* by the removed member) and only then clears confirmations for those requests: [3](#0-2) 

while `confirm()` again just checks set size against `num_confirmations` with no re-validation that every entry in the confirmation set is still a current member: [4](#0-3) 

The binding that should hold is: `confirmations counted for a request == confirmations from currently authorized (live) members`. Both contracts break this — a confirmation recorded before a member's removal remains counted after removal, so `confirmations counted > confirmations from live members`.

### Impact Explanation
This crosses an authorisation-threshold boundary explicitly called out as Critical impact ("a multisig request executed below threshold"). A `Transfer`, `AddKey`/`AddMember` with a new full-access key, `DeployContract`, or arbitrary `FunctionCall` request can be executed with fewer live-member approvals than `num_confirmations` mandates, because a revoked member's earlier "vote" is silently retained. This can move NEAR or hand out contract control (e.g., adding a new full access key) with an authorization count that no longer reflects the current member set.

### Likelihood Explanation
This requires only routine, expected multisig operation — no compromise of protocol invariants, no external actor, no redeploy. Any organization that rotates keys/members (a normal, documented operation) while there are unconfirmed pending requests will trigger this: a member confirms request A, is later removed for a legitimate reason (offboarding, compromised key, rebalancing), and A's stale confirmation from that removed member remains. The remaining live members only need to reach `num_confirmations - 1` additional confirmations to trigger execution, effectively executing with one fewer live approver than configured. This is a natural sequence of operations, not a contrived edge case, making likelihood high wherever multiple pending requests coexist with member turnover.

### Recommendation
When removing a key (`DeleteKey`) or member (`DeleteMember`), iterate over all entries in `self.confirmations` (not just requests originated by that key/member) and remove the deleted key/member's public key or member entry from every confirmation set. Alternatively, when validating in `confirm()`/`execute_request()`, re-check that every public key/member present in the stored confirmation set is still contained in the live key/member set before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 3` and keys `K1, K2, K3, K4` all having function-call access to the contract (as documented, each key is an implicit member).
2. `K1` calls `add_request_and_confirm(R1)` where `R1 = Transfer{amount}` to an attacker/insider-controlled `receiver_id` → `confirmations(R1) = {K1}` (len 1, below threshold).
3. `K2` calls `confirm(R1)` → `confirmations(R1) = {K1, K2}` (len 2, still below threshold 3).
4. Organization legitimately offboards `K2`: `K1`, `K3`, `K4` create and confirm a separate request `R_delete = DeleteKey{K2}` which reaches threshold and executes via `execute_request` → `promise.delete_key(K2)`. Per [2](#0-1) , this only purges requests where `signer_pk == K2` (i.e., requests *K2 created*), not `R1`'s confirmation entry, since `R1` was created by `K1`.
5. `confirmations(R1)` is still `{K1, K2}` even though `K2`'s access key no longer exists on-chain.
6. `K3` (a live member) calls `confirm(R1)`. In `confirm()` [1](#0-0) , `confirmations.len() as u32 + 1 == 3 >= num_confirmations (3)`, so `R1` executes the `Transfer` — approved by only 2 currently-live members (`K1`, `K3`) plus one phantom, revoked confirmation (`K2`), instead of the intended 3 live approvals.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);

        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
