### Title
Builder withdrawal amount is not capped to available balance when committed to the execution payload, allowing Gwei to be paid to `fee_recipient` without being debited from the builder - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` builds each `Withdrawal` object using the raw, uncapped `builder_pending_withdrawals[i].amount` (the *requested* amount), while `apply_withdrawals` only debits `min(withdrawal.amount, builder_balance)` from the builder's registry balance. Since `payload_expected_withdrawals` is the binding commitment that the execution layer must honor by crediting exactly `withdrawal.amount` to `withdrawal.address`, any case where a pending builder withdrawal's `amount` exceeds the builder's actual balance results in the execution layer paying out more Gwei than was ever removed from consensus-layer state — this is the same class of bug as the reported `received > 0` vs `received == _amount` check: the code checks/caps one side of a transfer ("received"/"deducted") more loosely than the side that is actually paid out ("amount committed to the payload").

### Finding Description
In `get_builder_withdrawals` (specs/gloas/beacon-chain.md, `##### New get_builder_withdrawals`), each pending builder withdrawal is turned into a `Withdrawal` entry with the **full requested `amount`**, with no capping to the builder's balance: [1](#0-0) 

This `Withdrawal` list becomes `state.payload_expected_withdrawals`, which per the spec note is a binding commitment: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer" — i.e. the EL must credit exactly `withdrawal.amount` to `withdrawal.address`.

However, the corresponding balance deduction in `apply_withdrawals` caps the debit to the builder's *actual* balance: [2](#0-1) 

So if a `BuilderPendingWithdrawal.amount` (or a `BuilderPendingPayment.withdrawal.amount`) is larger than the builder's balance at the time `process_withdrawals` runs, the committed `Withdrawal.amount` (paid on the execution layer) is the full, un-capped requested amount, while only `min(amount, balance)` is actually removed from `state.builders[i].balance`. The difference is Gwei paid to the `fee_recipient` on the execution layer that was never debited anywhere on the consensus layer — breaking the invariant that Gwei paid out must equal Gwei removed from an owner's balance.

This is not a hypothetical edge case invented for this analysis: the repository's own tests for `process_withdrawals` explicitly exercise and assert this exact behavior as "expected": [3](#0-2) 
and again with tighter, "realistic" bounds: [4](#0-3) 

Both tests confirm: `withdrawal.amount` in the committed payload equals the **requested** (uncapped) amount, while the builder balance is only reduced to `0` (capped), i.e. the shortfall is unaccounted for anywhere in consensus-layer state yet is contractually owed by the execution layer.

The design intends that `can_builder_cover_bid` (checked when a bid is accepted, and when quorum-processed via `settle_builder_payment`/`process_builder_pending_payments`) always keeps the sum of a builder's pending withdrawals+payments ≤ balance: [5](#0-4) 
But nothing re-verifies or re-caps this invariant at the point the withdrawal is actually materialized into `payload_expected_withdrawals` days/epochs later. Any drift between the balance-at-commitment-time and the balance-at-withdrawal-time (e.g. an `apply_parent_execution_payload` code path such as the direct-append-when-payment-is-evicted branch, ordering/timing of multiple pending withdrawals for the same builder, or any future change that adds a way to reduce builder balance without correspondingly updating `builder_pending_withdrawals`/`builder_pending_payments`) turns into unconditionally over-paid, unbacked Gwei, because `get_builder_withdrawals` never re-checks against current balance.

### Impact Explanation
This falls in the "Critical" bucket: **Gwei created and paid to a non-owner** (the builder's `fee_recipient`) that the consensus layer never actually removed from any account. Because `payload_expected_withdrawals` is a binding commitment that execution-layer clients must honor verbatim (the withdrawal `amount` field is used to credit balance on the EL side), the mismatch directly manifests as new, unbacked ETH appearing at an execution-layer address — a supply-invariant violation, which is categorically more severe than a normal accounting bug since it cannot be "fixed" after the fact (the EL balance increase is final).

### Likelihood Explanation
Likelihood is currently uncertain/moderate rather than trivially demonstrated from an honest bid flow alone: `can_builder_cover_bid` is designed to prevent a builder's cumulative pending obligations from exceeding its balance at commitment time. Whether there exists a fully protocol-reachable honest sequence (bid → pending payment → quorum settle → eviction/direct-append branches → withdrawal processing) that lets a builder's balance drop below its already-committed pending withdrawal total before `get_builder_withdrawals` runs was not fully confirmed within the scope of this review — the repository's own test suite treats the shortfall scenario as a "known"/tested behavior (see the two cited tests) but constructs the pending-withdrawal state directly via test helpers rather than through the full bid→settlement pipeline, so it is not certain from the available spec text whether this exact under-collateralized state is reachable by an honest sequence of blocks or only via test-harness state injection. This should be validated further (e.g., by tracing every code path that appends to `builder_pending_withdrawals`/`builder_pending_payments` or that can reduce `state.builders[i].balance`, to check whether `can_builder_cover_bid`'s accounting can ever be invalidated between commitment and settlement).

### Recommendation
Either:
1. Cap the `amount` field written into the `Withdrawal` object in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)`, matching what `apply_withdrawals` actually deducts, so the payload commitment and the balance deduction are provably equal; or
2. If the un-capped commitment is intentional (i.e., the invariant "sum of pending obligations ≤ balance" is meant to always hold by construction via `can_builder_cover_bid`), add an explicit `assert withdrawal.amount <= builder.balance` (or equivalent) at the point of materializing builder withdrawals, and document in the spec text why this invariant can never be violated — mirroring the original report's guidance to either enforce the exact-amount equality or explicitly justify the relaxed check.

### Proof of Concept
Conceptual/state-based PoC (not an exploit against honest bid flow, since a definitive protocol-reachable trigger for balance dropping below committed obligations was not confirmed in this review):
1. Populate `state.builder_pending_withdrawals` with an entry for `builder_index` whose `amount = 5 ETH`.
2. Set `state.builders[builder_index].balance = 1 ETH` (less than the pending withdrawal amount).
3. Call `process_withdrawals(state)` (via `get_expected_withdrawals` → `apply_withdrawals`).
4. Observe: `state.payload_expected_withdrawals` contains a `Withdrawal` with `amount = 5 ETH` (committed to be paid to `fee_recipient` on the EL), while `state.builders[builder_index].balance` is reduced only to `0` (a 1 ETH deduction). The execution layer will credit the `fee_recipient` address the full 5 ETH per the committed withdrawal list, creating 4 ETH that was never removed from any consensus-layer balance.
This exact behavior is reproduced by the repository's own test: [6](#0-5)

```python
def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount
