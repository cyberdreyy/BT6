## Missing Return After Failed Claim Extraction Leads to Session Creation Without Validated Identity - (File: `core/sessions/oidcauth/oidc.go`)

### Summary
`handleTokenExchange` in the OIDC authentication flow fails to `return` after an unsuccessful type-assertion on the `email` claim, mirroring the reported bug class of "missing validation on a critical operation, with execution silently continuing as if it had succeeded." Instead of aborting the login flow, the handler proceeds to create and persist a session row using the empty-string `email` value.

### Finding Description
In `handleTokenExchange`, after the OIDC ID token is verified and claims are parsed, the code extracts `email`: [1](#0-0) 

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims. error: %v", err)
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
}
oi.lggr.Tracef("Received and validated ID claims: %v\n", idClaims)
```

Unlike every other error branch in this same function (e.g. state mismatch, token exchange failure, ID token verification failure, claim extraction failure, role-mapping failure — each of which calls `return` immediately after writing the HTTP error response), this branch omits `return`. Execution falls through and continues to: [2](#0-1) 

which inserts a new row into `oidc_sessions` using `strings.ToLower(email)` (i.e., `""` when the assertion failed) together with the previously computed `role`, and then sets the session cookie (`SessionIDKey`) to point at that new session ID and returns HTTP 200 success to the client — even though the response body already wrote a 500 status via `c.String` earlier (Gin does not stop handler execution on `c.String`, only `c.Abort()`/`return` would).

This exactly parallels the external report's root cause: a critical outcome (whether the "transfer"/operation actually succeeded) is not checked before treating it as a success and continuing the privileged action (crediting tokens / here, creating an authenticated session and issuing a valid session cookie).

### Impact Explanation
If an IdP response is missing/malforms the `email` claim (attacker-influenced IdP response, misconfigured provider, or a compromised/rogue-but-technically-valid IdP token that satisfies signature/issuer/audience checks yet omits `email`), the server will still:
- Insert a valid, non-expired session row keyed to `user_email = ""` with the computed role.
- Set the session cookie for the caller.

Any subsequent request using that cookie will be treated as an authenticated session via `AuthorizedUserWithSession`, mapped to `email = ""`. Depending on how downstream code keys off `Email` (e.g., in audit logs, per-user resource scoping, or later `FindUser` lookups), this can create cross-user identity confusion or an authenticated session that is not cleanly tied to any real account, an unprivileged-actor-reachable authentication/session integrity issue.

### Likelihood Explanation
Reaching this code path requires only that `claims["email"]` be absent or non-string in the ID token returned by the configured OIDC provider during `handleTokenExchange`, which is invoked by any client completing the OIDC redirect flow — no special privileges required. Because the login flow otherwise appears to succeed (HTTP 200 `ExchangeTokenResponse{Success: true}` and a set session cookie), this is a straightforward, deterministic bug to trigger against any environment where `email` can be omitted from the ID token claims (either due to provider misconfiguration, scope mismatch, or the OIDC provider not guaranteeing this claim).

### Recommendation
Add a `return` statement (and `c.Abort()` semantics equivalent) immediately after writing the error response when the `email` claim assertion fails, so the request is not processed further:

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```

Additionally, consider validating that `email` is non-empty before using it to create/query session and user records, consistent with the `return`-after-error pattern used throughout the rest of `handleTokenExchange`.

### Proof of Concept
1. Configure an OIDC provider (or a malicious/compromised one accepted due to misconfiguration) whose ID token passes signature/issuer/audience verification in `oi.provider.Verifier(oi.oidcConfig).Verify(...)` but omits the `email` claim (or returns a non-string value for it).
2. Complete the standard OIDC redirect flow to `handleSignIn` → provider → `handleTokenExchange` with `code`/`state`.
3. Observe that despite the `c.String(http.StatusInternalServerError, ...)` write, execution continues: `role` is computed from group claims, a row is inserted into `oidc_sessions` with `user_email = ""`, `ginSession.Set(webauth.SessionIDKey, clSession.ID)` is called, and the handler ultimately responds `c.JSON(http.StatusOK, ExchangeTokenResponse{Success: true})` with a valid session cookie set.
4. Use the returned session cookie against protected API routes; `AuthorizedUserWithSession` will resolve a valid, non-expired session tied to `email=""` and the mapped role.
