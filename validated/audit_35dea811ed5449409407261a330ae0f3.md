### Title
Loss haircut applied only to the latest request epoch lets multi-epoch withdraw receipts claim unfunded amounts at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The xfrm bug is a "reference released too early, then the consumer still uses the stale pointer" flaw: `dev_put()` runs before `transport_finish`/`NF_HOOK` reads `skb->dev`. The analog in `IdleCreditVault` is the epoch pointer `lastWithdrawRequest[_user]`. When `stopEpochWithDuration` realizes a loss, the haircut is funded pro-rata over **all** `pendingWithdraws` but stored under a single key, `lossRecoveryPriceByEpoch[epochNumber]` (`collectWithdrawFunds`, line 421). At claim time, `_claimLossAdjustedWithdrawRequest` resolves the loss epoch solely via `lastWithdrawRequest[_user]` (line 790), which only points to the user's *latest* request epoch. Receipts recorded in earlier epochs (`withdrawsRequestsByEpoch[_user][N]`) are never haircutted: they survive in the aggregate `withdrawsRequests[_user]` and are then paid at par by `_claimFundedWithdrawRequest` (line 338-349), even though the borrower only funded them at the loss-adjusted ratio.

### Finding Description
Sequence:
1. During epoch N, attacker calls `requestWithdraw` → `withdrawsRequestsByEpoch[user][N] += amt`, `pendingWithdraws += amt`, `lastWithdrawRequest[user] = N` (lines 282-294).
2. Epoch N ends without loss (or the attacker simply doesn't claim — claims are only gated by `epochNumber <= lastWithdrawRequest`, and a new request resets that gate).
3. During epoch N+1, attacker requests again → `lastWithdrawRequest[user] = N+1`, second receipt added. Nothing prevents this: `requestWithdraw` only blocks re-requesting when `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is already set (lines 263-270), which is not yet true during epoch N+1.
4. Epoch N+1 ends with a loss via `stopEpochWithDuration(_lossAmount)`: `collectWithdrawFunds` collects `pendingBasis - pendingLoss` but stores `lossRecoveryPriceByEpoch[N+1]` covering the *aggregate* basis including the epoch-N receipt (lines 413-429, `previewLossAdjustedWithdrawFunds` lines 454-459).
5. Attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[user] = N+1`, clears only `withdrawsRequestsByEpoch[user][N+1]`, pays it at `lossRecoveryPrice`, and `_clearWithdrawClaimForEpoch` resets `lastWithdrawRequest[user] = 0` (lines 789-836).
   - `_claimFundedWithdrawRequest` then computes `normalAmount = withdrawsRequests[user]`, which still contains the epoch-N receipt, and pays it **at par** via `_transferFundedClaim` (lines 338-349).

The epoch-N receipt was funded at `lossRecoveryPrice` but redeemed at `RECOVERY_FULL`. The difference is taken from the strategy's funded reserve that belongs to other claimants.

### Impact Explanation
Direct theft / insolvency: with a 50% loss haircut, an attacker splitting 100k across epochs N and N+1 recovers `50k * 0.5 + 50k * 1.0 = 75k` while the vault only received `100k * 0.5 = 50k` for those receipts. The extra 25k is drained from underlyings reserved for other users' funded claims, so later claimants' transfers revert or are underpaid — permanent loss socialized onto honest users. Broken invariant: one receipt, one payout at its funded recovery ratio.

### Likelihood Explanation
Requires only a KYC-passing tranche holder making two `requestWithdraw` calls in consecutive epochs before a loss epoch. The gap exists because the loss haircut is keyed by a single mutable pointer (`lastWithdrawRequest`) while the liability is an aggregate across epochs — exactly the premature-release/stale-pointer class of the reference bug. No privileged action needed by the attacker; loss epochs occur via the honest manager/borrower path.

### Recommendation
Apply `lossRecoveryPriceByEpoch` per receipt epoch, not per `lastWithdrawRequest`: in `_claimLossAdjustedWithdrawRequest`/`_withdrawClaimAmountsForEpoch`, iterate or track all epochs with pending receipts carrying a nonzero `lossRecoveryPriceByEpoch`, or store per-user per-epoch recovery prices. Alternatively, fold the haircut into the aggregate (e.g., scale `withdrawsRequests[user]` at `collectWithdrawFunds` time proportionally) so `_claimFundedWithdrawRequest` cannot pay an unhaircutted basis.

function testLossEpochOnlyHaircutsLatestRequestEpoch() external {
    address attacker = makeAddr('attacker');
    uint256 tranches1 = _depositWithUser(attacker, 50_000e6); // epoch N request
    _depositWithUser(makeAddr('lp'), 50_000e6);

    // epoch N: attacker requests withdraw of tranches1
    _requestWithdrawWithUser(attacker, tranches1);
    _stopCurrentEpochWithApr(10e18); // epoch N ends healthy; receipt pending

    vm.prank(attacker);
