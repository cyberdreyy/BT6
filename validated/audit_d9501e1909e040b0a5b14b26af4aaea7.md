### Title
Re-requesting a withdraw overwrites `lastWithdrawRequest`, masking a prior loss-adjusted epoch's haircut and paying the haircutted receipt at par — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` indexes loss-adjusted (haircutted) withdraw receipts through a single per-user slot, `lastWithdrawRequest[_user]`, rather than iterating the epochs in which the user actually requested. Like the ath12k bug where a shared ring mask causes one ring's interrupt to process a different ring, a second `requestWithdraw` overwrites the shared index, so the loss-adjusted claim path in `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` under the wrong epoch and never applies the haircut. The full aggregate `withdrawsRequests[_user]` is then paid at par via `_claimFundedWithdrawRequest`, while the vault only holds the haircutted funded amount for the earlier epoch — a direct solvency break paid out of other claimants' reserves.

### Finding Description
- At request time, `requestWithdraw` stores per-epoch basis in `withdrawsRequestsByEpoch[_user][currentEpoch]` and overwrites the single shared marker `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282-293`).
- When a `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` is called with `_amount < pendingWithdraws`; it stores the haircut `lossRecoveryPriceByEpoch[epochNumber]` and pulls only `_amount` underlying into the vault (`IdleCreditVault.sol:411-421`). The unfunded remainder is never paid — claimants are supposed to receive `claimBasis * lossRecoveryPrice / 1e18`.
- `claimWithdrawRequest` dispatches to `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:789-800`). There is exactly one `lastWithdrawRequest` slot shared across all of a user's request epochs.
- If the user requests again in a later epoch `N+1`, `lastWithdrawRequest` is overwritten to `N+1`. If epoch `N+1`'s stop was fully funded, `lossRecoveryPriceByEpoch[N+1] == 0`, the loss-adjusted branch returns 0, and `_clearWithdrawClaimForEpoch` is never called for epoch `N` — `withdrawsRequestsByEpoch[user][N]` and its share of `withdrawsRequests[user]` remain intact.
- `_claimFundedWithdrawRequest` then gates only on `epochNumber > lastWithdrawRequest[_user]` and pays the entire aggregate `withdrawsRequests[_user]` (which still includes the epoch-`N` haircutted basis) at par (`IdleCreditVault.sol:319-349`).

Attack sequence (all steps are callable by any tranche holder):
1. Epoch `N` (running): attacker calls `IdleCDOEpochVariant.requestWithdraw(amount, tranche)` → `IdleCreditVault.requestWithdraw` records basis in epoch `N`.
2. Manager calls `stopEpochWithDuration` with a nonzero `_lossAmount`; borrower funds only `pendingToFund`. `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[N']` and transfers the reduced amount.
3. Epoch `N+1` buffer: attacker deposits/re-uses remaining tranche tokens (or a second account consolidates via the same user path) and calls `requestWithdraw` again → `lastWithdrawRequest[attacker] = N+1`.
4. Next `stopEpoch` funds the new request at par; `epochNumber` advances past `N+1`.
5. Attacker calls `claimWithdrawRequest` via the CDO: loss-adjusted lookup for epoch `N+1` returns 0, `_settleApr0`/funded path pays `withdrawsRequests[attacker]` (old haircutted basis + new basis) at par and clears `lastWithdrawRequest`.

The vault paid out `A_old` that was never funded — only `A_old * lossRecoveryPrice` was collected. The deficit is absorbed by the underlying reserve backing other pending receipts and instant-withdraw claims.

### Impact Explanation
Direct insolvency/theft: each haircutted receipt that re-requests and re-claims is paid the un-haircutted difference (`claimBasis * (1 - lossRecoveryPrice)`) from funds belonging to other pending claimants, instant withdrawers, or the funded reserve. With a 50% recovery price the attacker steals roughly half of any prior pending receipt; scaled across a large `pendingWithdraws` epoch the shortfall can permanently freeze later `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls once the vault's underlying balance is drained. The broken invariant is the loss waterfall: a receipt that was economically haircutted at `stopEpochWithDuration` escapes its loss.

### Likelihood Explanation
Requires: (a) a `stopEpochWithDuration` with a realized loss (an accepted, non-default epoch mode used for borrower shortfalls), and (b) the attacker holding or re-acquiring tranche tokens to file a second request — both unprivileged actions. No privileged attacker needed; manager/borrower actions are honest sequencing only. One caveat I could not fully verify before finalizing: `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]` at collect time, while receipts are indexed by the request-time epoch — the exact epochNumber increment ordering in `stopEpochWithDuration`/`onStopEpoch` determines whether the lookup key mismatches even for a single request, which would make the bug strictly worse (haircut never found). Either way, the shared `lastWithdrawRequest` index masks the haircut for re-requesters.

### Recommendation
Do not key `lossRecoveryPriceByEpoch` lookups off the mutable single-slot `lastWithdrawRequest`. Track per-user request epochs (or clear all epochs with a nonzero `lossRecoveryPriceByEpoch` when claiming), e.g., iterate `withdrawsRequestsByEpoch[_user]` epochs or store an explicit per-user loss-epoch list. At minimum, in `requestWithdraw`, revert or force-claim any existing receipt whose epoch has a nonzero `lossRecoveryPriceByEpoch` before overwriting `lastWithdrawRequest`, so a re-request cannot hide a haircutted receipt in the funded aggregate.

### Proof of Concept
```solidity
// Foundry fork test against IdleCreditVault / IdleCDOEpochVariant deployment.
// Assumes standard epoch variant, fixed-APR mode, honest manager/borrower.
function testLossHaircutBypassedByReRequest() external {
    // --- Epoch N: attacker (any tranche holder) requests withdraw ---
    uint256 amountA = 100e6; // 100 USDC worth of tranches
    _depositWithUser(attacker, amountA);            // via idleCDO depositAA/BB
    vm.prank(manager); cdoEpoch.startEpoch();
    uint256 tranches = IERC20(tranche).balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.requestWithdraw(tranches, tranche);

    // --- stopEpochWithDuration with loss: only pendingToFund is collected ---
    vm.warp(cdoEpoch.epochEndDate() + 1);
    (uint256 pendingToFund, uint256 activeLoss) =
        strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(underlying, borrower, repay);
    vm.prank(borrower); IERC20(underlying).approve(cdoEpoch, repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount);
    // vault now holds only pendingToFund for attacker's receipt (< full basis)

    // --- Epoch N+1 buffer: attacker re-requests (overwrites lastWithdrawRequest) ---
    _depositWithUser(attacker, amountB);
    vm.prank(manager); cdoEpoch.startEpoch();
    // second request in the next buffer/running phase sets lastWithdrawRequest = N+1
    vm.prank(attacker); cdoEpoch.requestWithdraw(tranches2, tranche);

    // --- Epoch N+1 stop fully funded (no loss) ---
    _stopCurrentEpochFullyFunded(); // lossRecoveryPriceByEpoch[N+1] == 0

    // --- Attacker claims: haircut for epoch N is skipped, aggregate paid at par ---
    uint256 balPre = IERC20(underlying).balanceOf(attacker);
    vm.prank(attacker); /* via CDO */ cdoEpoch.claimWithdrawRequest();
    uint256 received = IERC20(underlying).balanceOf(attacker) - balPre;

    // received == full (oldBasis + newBasis) at par, while vault was only funded
    // pendingToFund for the old receipt => shortfall drained from other claimants.
    assertGt(received, fundedReserveForAttacker);
    // Subsequent claimants' claimWithdrawRequest now reverts / underpays
    // (vault underlying balance < withdrawsRequests aggregate).
}
```
The PoC passes if `claimWithdrawRequest` pays more than `pendingToFund + newBasis` to the attacker, demonstrating that `lossRecoveryPriceByEpoch` for the first request epoch was never applied because `lastWithdrawRequest` was overwritten.
