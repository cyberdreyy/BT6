### Title
Stale `interestForOverUnderPerformance` deltas after `epochDuration`/split-ratio changes desynchronize `expectedEpochInterest` from the recomputed base, enabling forced default - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` tracks the interest adjustments caused by withdraw requests as a cumulative bucket (`interestForOverUnderPerformance`), where each request's delta is computed under the APR/duration/split configuration *at request time*. At `startEpoch`, however, the base interest is *fully recomputed* on post-burn `getContractValue()` under the *current* `epochDuration`/`bufferPeriod`/APR, then summed with the stale cumulative deltas. This is the same broken invariant as the HMX bug: an aggregate is built from deltas priced under an old config while the base is priced under a new config, so the sum no longer equals the true obligation. If the combined value overstates what the borrower owes, `getFundsFromBorrower` reverts and `_handleBorrowerDefault` freezes the pool; if it understates, tranche holders permanently lose yield the borrower keeps.

### Finding Description
In `requestWithdraw`, each request computes `(interest, diff)` via `_calcInterestWithdrawRequest`, which scales interest by the *current* `epochDuration` and `bufferPeriod` (`contracts/IdleCDOEpochVariant.sol:856-878`), and the correction `diff` is accumulated:

- `interestForOverUnderPerformance += diff` (`IdleCDOEpochVariant.sol:784`)
- The receipt amount is fixed in `creditVault.requestWithdraw(...)` and NAV is reduced by `principal` (`IdleCDOEpochVariant.sol:788-790`).

At `startEpoch`, the expected interest is recomputed fresh but added to the stale bucket:

```solidity
int256 adjustedActiveInterest = int256(_calcInterest(getContractValue())) + interestForOverUnderPerformance;
expectedEpochInterest = pendingWithdrawFees + uint256(adjustedActiveInterest);
```
(`IdleCDOEpochVariant.sol:260-263`)

`_calcInterest` uses the *current* `epochDuration` (`IdleCDOEpochVariant.sol:807-809`). Between a request and `startEpoch`, the honest owner/manager can call `setEpochParams` (only blocked while `isEpochRunning`, `IdleCDOEpochVariant.sol:117-125`) or change APR/split parameters. Requests made during the buffer carry `diff` (and the pending-fee/`pendingWithdraws` interest component) priced under the *old* `epochDuration`, while the base `_calcInterest(getContractValue())` is priced under the *new* one. The two terms are therefore denominated in different assumptions, exactly as in the HMX report where the cumulative reserve was decremented under the old `initialMarginFractionBPS`/`maxProfitRateBPS` while the per-position reserve was recomputed under the new values.

Concretely, an AA request stores `diff = interestWithoutSplit(amount) − AAinterest(amount) > 0`, representing the yield the withdrawn principal would have redirected to BB. If `epochDuration` is then shortened before `startEpoch`, `diff` still reflects the long-epoch interest, inflating `expectedEpochInterest` above what the borrower actually owes; `stopEpoch`'s `getFundsFromBorrower(_expectedInterest + _pendingWithdraws)` pull can exceed the borrower's real liability/approval, revert, and trigger `_handleBorrowerDefault` (`IdleCDOEpochVariant.sol:408, 501-505`), which sets `defaulted`, pauses the pool and disables all withdraw requests (`IdleCDOEpochVariant.sol:577-599`). If `epochDuration` is lengthened, the opposite drift under-credits BB/other tranche holders relative to the borrower's true obligation — a permanent, unrecovered yield loss. The same staleness applies to `trancheAPRSplitRatio`/`fee` changes, since `diff`, `pendingWithdrawFees` and each receipt's interest were all fixed under the old parameters while the surviving NAV accrues under the new ones.

### Impact Explanation
- **Overstatement path**: borrower repayment pull fails at `stopEpoch` → `_handleBorrowerDefault` → `defaulted = true`, pool paused, AA/BB requests disabled. All unclaimed pending receipts and active NAV are frozen until the owner runs the default/finalizeDefaultRecovery flow, i.e., temporary-to-permanent freezing of the entire TVL caused by an accounting drift, not a real credit loss.
- **Understatement path**: expected interest is lower than the contractual obligation; remaining tranche holders crystallize less yield while the borrower retains the difference (mispriced `lastEpochInterest`/`lastNAV`), a direct transfer of value away from LPs.

### Likelihood Explanation
Medium-low. It requires (a) an open withdraw request sitting in `interestForOverUnderPerformance`/`pendingWithdrawFees`, and (b) an honest owner/manager `setEpochParams` (or equivalent parameter) update landing in the same buffer window before `startEpoch`. No malicious privileged action is needed — the attacker only needs to keep a request open across the honest config change, which any KYC-passed tranche holder can do. The code's own comment (`bufferPeriod` "should not be changed once set otherwise interest calculations will be wrong", `IdleCDOEpochVariant.sol:114`) acknowledges the fragility for `bufferPeriod` but `epochDuration` and split/fee parameters carry the same class of drift and remain changeable. I could not fully verify the magnitude of the overstatement needed to exhaust a real borrower's approval, so the default-trigger leg assumes the borrower funds exactly the expected amount.

### Recommendation
Apply the report's fix pattern — subtract the whole old value and add the whole new value instead of mixing vintages:
- Recompute `interestForOverUnderPerformance` (and the interest component embedded in pending receipts) under the *current* parameters inside `startEpoch`, e.g., store per-request `principal`, tranche and request-epoch parameters and re-derive `diff` at `startEpoch`; or
- Restrict `setEpochParams`, APR, split-ratio and fee changes to only apply when `interestForOverUnderPerformance == 0 && pendingWithdrawFees == 0`, or epoch-version the parameters so requests settle under the configuration active at request time; or
- Document/enforce that `epochDuration`, like `bufferPeriod`, is immutable after the first request cycle.

### Proof of Concept
Sketch of a Foundry PoC against `IdleCDOEpochVariant` + `IdleCreditVault` on a fork:

```solidity
// 1. Buffer phase: KYC'd attacker deposits AA, then calls
//    cdo.requestWithdraw(amount, AATranche). This stores diff>0 in
//    interestForOverUnderPerformance priced with epochDuration = D1.
// 2. Honest owner calls cdo.setEpochParams(D2, bufferPeriod) with D2 << D1.
// 3. Owner calls cdo.startEpoch(). expectedEpochInterest =
//      _calcInterest(TVL_new /*D2*/) + staleDiff /*D1*/ + pendingWithdrawFees,
//    which exceeds the borrower's true liability by diff*(1 - D2/D1).
// 4. At epoch end, owner calls cdo.stopEpoch(newApr, 0):
//    borrower.approve covers only the real obligation, so
//    getFundsFromBorrower reverts -> _handleBorrowerDefault ->
//    defaulted == true, paused, claimWithdrawRequest/requests frozen.
// 5. Assert: cdo.defaulted() && strategy.pendingWithdraws() > 0 while
//    claimers cannot withdraw — freezing caused purely by drift, no credit loss.
// Mirror case with D2 >> D1: assert BB virtualPrice accrues less than
// owed interest (permanent yield theft from remaining LPs).
```

The PoC needs a mainnet fork of a live `IdleCDOEpochVariant` deployment (or a full local harness replicating `requestWithdraw`/`startEpoch`/`stopEpoch` with a funded mock borrower approving exactly `expectedEpochInterest` computed under the *new* duration).
