### Title
Group rate-limiter accounting uses low-biased oracle price, systematically undervaluing withdrawal outflows - ([File: programs/marginfi/src/utils/general.rs])

### Summary
`record_withdrawal_outflow` computes the USD `value` used for the group-level hourly/daily rate-limiter cap via `calc_value(balance_amount, price, decimals, None)`, but every caller supplies `price` from `fetch_asset_price_for_bank_low_bias`, which explicitly requests `PriceBias::Low`. This means the value used to check/report outflow against the group cap is *always* conservatively low relative to real market value, not merely under rare timing-manipulation windows — it is a structural under-reporting built into every withdrawal path.

### Finding Description
`record_withdrawal_outflow` in `programs/marginfi/src/utils/general.rs` (lines 464–525) only checks `price > I80F48::ZERO` [1](#0-0) , then uses that `price` to compute `value = calc_value(...)`, which is compared against `group.rate_limiter.hourly/daily.effective_remaining_capacity(...)` and emitted in `RateLimitFlowEvent` [2](#0-1) .

Every instruction that calls `record_withdrawal_outflow` (marginfi_account, drift, juplend, kamino, solend withdraw paths) sources `price` from `fetch_asset_price_for_bank_low_bias`, which explicitly requests `OraclePriceType::RealTime` with `PriceBias::Low` [3](#0-2) . In `lending_account_withdraw`, this same low-biased price is fetched once and reused both for the receivership zero-check and for rate-limit accounting [4](#0-3) .

`PriceBias::Low` is designed to *undervalue* an asset (standard collateral-conservatism direction used elsewhere in risk engine calculations, e.g. for collateral weighting), which is the opposite of what's needed for outflow/rate-limit accounting, where a conservative bias should *overstate* outflow value to avoid letting withdrawals slip under the cap. As a result, `value` computed here is always ≤ the true market value of the withdrawn amount (bounded further down by `bank.config.oracle_max_confidence`), so the hourly/daily cap comparisons (`value.to_num::<i64>() > remaining`) and the derived off-chain `RateLimitFlowEvent` aggregation both systematically under-count real notional outflow. This holds on every call, not just under attacker-chosen timing — attacker-controlled timing to further land within a favorable confidence-interval price only compounds an already-present structural bias.

### Impact Explanation
Since the group-level rate limiter here is a "read-only validation + event emission" control aggregated off-chain by an admin (per the doc comment on `record_withdrawal_outflow`), any systematic undervaluation directly degrades this durable safety control: on-chain checks (`GroupHourlyRateLimitExceeded`/`GroupDailyRateLimitExceeded`) under-trigger, and the off-chain reconciliation via `update_group_rate_limiter` will be fed under-counted `native_amount * price` data, allowing real net outflow to exceed intended notional caps without on-chain or off-chain detection. This matches the PRICE_CONSERVATISM invariant cited in the question: value used for rate-limit accounting must not systematically understate real withdrawal value.

### Likelihood Explanation
This requires no special preconditions beyond the group rate limiter being enabled (`group.rate_limiter.is_enabled()`/`group_rate_limit_enabled`) — a normal, permissionless withdrawal instruction call by any unprivileged user triggers the low-biased pricing path every time. It is fully repeatable and deterministic (bias direction is hardcoded), rather than depending on rare oracle-staleness timing windows, making it more likely and consistently exploitable across repeated withdrawals to accumulate under-counted outflow relative to the true cap.

### Recommendation
For rate-limiter/outflow accounting, fetch price with a conservative *high* bias (or unbiased/high-confidence-adjusted price) instead of `PriceBias::Low`, e.g. introduce a `fetch_asset_price_for_bank_high_bias` (analogous to the existing low-bias helper) and use it specifically when computing `value` in `record_withdrawal_outflow` and in the deleverage-withdraw-limit check in `lending_account_withdraw`, while keeping low-bias pricing only for genuine collateral/health-engine valuation.

### Proof of Concept
Rust unit test plan (`programs/marginfi/src/utils/general.rs` test module or a new integration test):
1. Construct a `Bank`/oracle price feed mock with a known true mid price `P` and confidence interval `[P - c, P + c]`.
2. Call `fetch_asset_price_for_bank_low_bias` and confirm it returns `P - c` (or lower), then call `calc_value(balance_amount, P-c, decimals, None)` and compare against `calc_value(balance_amount, P, decimals, None)` — assert the rate-limit-reported `value` is strictly less than the true mid-price value by the confidence margin.
3. Integration test: enable `group.rate_limiter.hourly` with a cap `C`; perform repeated withdrawals of true notional value slightly above `C` (using true mid-price) but whose `record_withdrawal_outflow`-computed low-biased `value` stays under `C`; assert `GroupHourlyRateLimitExceeded` is never raised even though cumulative real value (`native_amount * true_price`) exceeds `C`, demonstrating cap bypass caused by the pricing bias rather than by legitimate limiter capacity.

pub fn fetch_asset_price_for_bank_low_bias<'info>(
    bank_key: &Pubkey,
    bank: &Bank,
    clock: &Clock,
    remaining_accounts: &'info [AccountInfo<'info>],
) -> Result<I80F48> {
    let oracle_ais = oracle_accounts_for_bank(bank_key, bank, remaining_accounts)?;
    let pf = OraclePriceFeedAdapter::try_from_bank(bank, oracle_ais, clock)?;
    let price = pf.get_price_of_type(
        OraclePriceType::RealTime,
        Some(PriceBias::Low),
        bank.config.oracle_max_confidence,
    )?;

    Ok(price)
}
