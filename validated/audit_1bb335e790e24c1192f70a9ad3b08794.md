### Title
APR0 withdraw-request dust permanently locks the epoch state machine at APR=0 / bricks `stopEpoch` — (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
An unprivileged KYC-passing lender can poison the `apr0TotalPrincipal` bucket with a tiny `requestWithdraw` while `unscaledApr == 0`. `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`, and `apr0TotalPrincipal` is only cleared inside that same function — which itself requires `unscaledApr == 0` to succeed. The attacker re-requests during every buffer period, so the pool can never again run a non-zero-APR epoch: every `stopEpoch`/`stopEpochWithDuration` with `_newApr != 0` reverts, and borrower principal plus all pending receipts stay locked inside the epoch state machine.

### Finding Description
- `requestWithdraw` routes to `_requestWithdrawApr0` whenever `unscaledApr == 0`, incrementing `apr0TotalPrincipal` (`IdleCreditVault.sol:285-286`, `567-577`).
- `stopEpoch` → `prepareStopEpochWithApr0` reverts with `NotAllowed` if `apr0TotalPrincipal != 0` and `unscaledApr != 0` (`IdleCreditVault.sol:506-508`), and is the only non-default path that resets `apr0TotalPrincipal = 0` (`IdleCreditVault.sol:540`). `_settleApr0` moves principal to `settledPrincipal` but never decrements `apr0TotalPrincipal`; the user's own claim does not unwind the bucket.
- `stopEpochWithDuration` sets the new APR *after* `_stopEpoch` via `_setScaledApr` → `setAprsWithBuffer`, which writes `unscaledApr = _newApr` unconditionally (`IdleCDOEpochVariant.sol:520-528`, `IdleCreditVault.sol:217-219`). There is no check that a pending APR0 bucket exists before raising APR.
- Sequence: (1) manager runs an epoch/buffer at APR 0 (supported mode, exercised in `testApr0Withdraw*` tests); (2) attacker (KYC'd, wallet-allowed) calls `requestWithdraw(1 wei of tranche)` → `apr0TotalPrincipal > 0`, `lastWithdrawRequest[attacker] = epoch`; (3) honest manager calls `stopEpochWithDuration(newApr > 0, ...)` — this succeeds and sets `unscaledApr > 0`; (4) the next epoch runs, ends, and every subsequent `stopEpoch` reverts in `prepareStopEpochWithApr0`. Borrower funds cannot be pulled, `isEpochRunning` stays true, deposits/`depositDuringEpoch` expire at `epochEndDate`, and withdraw requests remain closed. The only escape is manager setting `unscaledApr` back to 0 — at which point the attacker re-poisons the bucket in the next buffer period, since `requestWithdraw` is open then (`allowAAWithdrawRequest` is true outside epochs). Even the close-pool sentinel path (`_interest == 1`) still calls `prepareStopEpochWithApr0` and reverts.

### Impact Explanation
Permanent freezing of funds / permanent liveness failure of the epoch state machine. As long as one dust APR0 receipt bucket exists, the vault is trapped: either APR is held at 0 forever (all yield denied — theft of yield / griefing of the entire TVL), or `stopEpoch` reverts indefinitely with borrower principal unrecoverable through the normal path (only a hard-default + `finalizeDefault` cycle clears the bucket). Attacker cost is negligible: the requested principal is a claimable receipt, not burned value.

### Likelihood Explanation
Requires only: an epoch run at `unscaledApr == 0` (a supported configuration with dedicated tests), a wallet-allowed lender, and a later honest APR increase — all routine operations. No privileged misbehavior needed; the attacker spends dust and risks nothing since the receipt remains claimable. The repeat-poisoning makes the DoS sustainable indefinitely.

### Recommendation
- In `prepareStopEpochWithApr0`, do not revert when `unscaledApr != 0`; settle the stale bucket at rate 0 (or last stored rate) and clear `apr0TotalPrincipal`, or
- block APR increases while `apr0TotalPrincipal != 0` inside `setAprsWithBuffer`/`_stopEpoch` with a clear error, and/or decrement `apr0TotalPrincipal` in `_settleApr0`/`_claimFundedWithdrawRequest` once the user's epoch is finalized, so a claimed receipt cannot hold the bucket hostage.

### Proof of Concept
```solidity
// Foundry fork test (pattern follows testApr0WithdrawMultiUserProRataSameEpoch)
function testApr0DustLocksNonZeroApr() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0 mode

    // attacker: KYC'd lender
    address attacker = makeAddr("apr0-griefer");
    _depositWithUser(attacker, 1e18, true);          // dust deposit
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                        // ends epoch, APR still 0

    // poison bucket during buffer while requests are open and unscaledApr == 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // apr0TotalPrincipal = dust

    // honest manager raises APR for next epoch — call succeeds
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    // manager sets new apr via stopEpochWithDuration path / setAprsWithBuffer
    // unscaledApr is now > 0 while apr0TotalPrincipal != 0

    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, type(uint256).max); // even full repayment fails
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 1);                        // close-pool sentinel also reverts
    // every future stopEpoch reverts until APR is forced back to 0;
    // attacker re-requests each buffer to keep the bucket non-zero.
}
```

Note: I verified the revert path (`IdleCreditVault.sol:506-508`), the single reset site (`:540`), and that `_settleApr0`/`_claimFundedWithdrawRequest` never decrement `apr0TotalPrincipal` outside the default-clearing path (`:822-828`). Residual uncertainty: whether the intended recovery (manager calling `setAprsWithBuffer(0,…)` then stopping) is considered a sufficient mitigation — even so, the attacker can re-poison each buffer at dust cost, so the freeze is repeatable rather than one-shot.
