### Title
Instant-withdraw receipts requested mid-epoch are paid from the funded reserve before they are funded (TOCTOU between request and claim) - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` creates a receipt and inflates `pendingInstantWithdraws`, but the matching underlying is only pulled from the CDO/borrower at the next `startEpoch` via `collectInstantWithdrawFunds`. `claimInstantWithdrawRequest` pays out the full `instantWithdrawsRequests[_user]` immediately, with no epoch gating and no check that the receipt was actually funded. An attacker can therefore create an instant receipt while an epoch is already running and claim it in the same transaction, draining underlying that the vault is holding for other users' already-funded claims.

### Finding Description
The Devise advisory's bug class is a check performed at one point in time and acted on later against changed state. The analog here is the funding-vs-claim split of instant withdrawals:

- `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`. No underlying moves at this point.
- Funding happens only in `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`), callable only at `startEpoch`, which decrements `pendingInstantWithdraws` and pulls underlying from the CDO.
- `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) burns the entire `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` with no check that the request's epoch was funded, no `epochNumber`/epoch-state gate, and it never decrements `pendingInstantWithdraws`.

On the CDO side, `IdleCDOEpochVariant.requestWithdraw` (`IdleCDOEpochVariant.sol:739-770`) can route into `requestInstantWithdraw` whenever `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, and `claimInstantWithdrawRequest` (`IdleCDOEpochVariant.sol:975-979`) is gated only by the `allowInstantWithdraw` flag — neither requires that the request predates the current epoch's funding step. The test at `test/foundry/IdleCreditVault.t.sol:4784` confirms mid-epoch instant claims are intended to be served from whatever underlying the vault/CDO currently holds ("new deposits are enough to cover all instant withdraws"), so the "check" (receipt exists) and the "use" (pay from vault balance) are separated by a funding step that may never have covered the new receipt.

### Impact Explanation
The vault's underlying balance is a shared reserve backing all funded claims: normal withdraw receipts funded via `collectWithdrawFunds`, instant receipts funded via `collectInstantWithdrawFunds`, and post-default recovery reserves. A receipt created after the last funding step is unfunded, yet `claimInstantWithdrawRequest` still transfers the full amount. The attacker effectively draws on underlying earmarked for other users' receipts, breaking the "one receipt, one funded payout" invariant. Loss equals the attacker's instant receipt amount (bounded only by their tranche balance), and manifests as theft of other claimants' funded reserves or a permanent/temporary freeze when later legitimate claims revert on insufficient vault balance.

### Likelihood Explanation
Requirements: a deployment where instant withdrawals are enabled (`allowInstantWithdraw` and `_isInstantWithdrawEnabled()` true, i.e., non-programmable borrower) and the current `unscaledApr` is at least `instantWithdrawAprDelta` below `lastEpochApr`. The attacker needs only tranche tokens (a KYC'd lender or any holder), calls `requestWithdraw` mid-epoch while the vault holds funded reserves, then `claimInstantWithdrawRequest`. Honest privileged sequencing (manager's `setAprs`, epoch transitions) supplies the APR drop; no privileged role is the attacker.

### Recommendation
Track per-epoch funding for instant receipts the same way normal receipts do: in `claimInstantWithdrawRequest`, only pay amounts whose epoch was funded (e.g., compare `instantWithdrawsRequestsByEpoch[_user][epoch]` against funded epochs, or record a per-user `lastInstantFundedEpoch`), and decrement `pendingInstantWithdraws` on claim or revert when the claim exceeds funded reserves. Alternatively, gate instant requests so they can only be created while `!isEpochRunning`, matching the funding schedule.

### Proof of Concept
```solidity
// Foundry fork-style PoC on the existing IdleCreditVault harness
function testUnfundedInstantClaimDrainsFundedReserve() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());

    // Honest user deposits and creates a normal withdraw receipt
    address honest = makeAddr("honest");
    _depositWithUser(honest, 10_000 * ONE_SCALE, true);
    vm.prank(honest);
    uint256 honestReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Epoch runs; stopEpoch funds honest's receipt into the strategy reserve
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    assertEq(IdleCreditVault(address(strategy)).pendingWithdraws(), 0);

    // Attacker deposits (buffer) and an APR drop enables instant mode
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // lastEpochApr > currentApr + delta

    // New epoch starts; only pendingInstantWithdraws existing at startEpoch get funded
    _startEpochAndCheckPrices(1);

    // Attacker requests instant withdraw MID-EPOCH: receipt is unfunded
    vm.prank(attacker);
    uint256 attackerReceipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Same-epoch claim succeeds anyway, paid from the reserve backing honest's receipt
    uint256 vaultBalPre = underlying.balanceOf(address(strategy));
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(address(strategy)), vaultBalPre - attackerReceipt);

    // Honest user's funded claim now reverts or is shorted
    vm.prank(honest);
    vm.expectRevert(); // insufficient reserve
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I could not fully trace `_transferFundedClaim` and the `startEpoch`/`getInstantWithdrawFunds` funding path within the available iterations; the PoC assumes the vault pays claims from a common underlying balance, which the test at `test/foundry/IdleCreditVault.t.sol:4784` ("new deposits are enough to cover all instant withdraws") supports. The core gap — no epoch/funding check in `claimInstantWithdrawRequest` — is directly visible at `contracts/strategies/idle/IdleCreditVault.sol:380-393`.
