### Title
Stale confirmation from a removed member counted toward `num_confirmations`, allowing sub-threshold execution - (`multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges the `confirmations` entries for requests that the removed member originally *created* (`add_request`); it never scans other active requests for confirmations that member had *cast*. `confirm()` later counts `confirmations.len()` without re-validating that each entry belongs to a current member, so a stale confirmation from an already-removed member can be combined with fewer live members to reach `num_confirmations` and execute the request.

### Finding Description
The invariant the code is supposed to maintain is:
`executed_request.confirmations.filter(is_current_member).count() == num_confirmations`

but the actual code only guarantees:
`executed_request.confirmations.len() == num_confirmations`

Trace:
- `confirm()` [1](#0-0)  fetches `confirmations` for the `request_id`, asserts the calling member hasn't already confirmed, and then checks `confirmations.len() as u32 + 1 >= self.num_confirmations` before inserting and possibly executing. It never re-checks that the *existing* entries in the set are still members.
- `delete_member()` [2](#0-1)  filters `self.requests` for entries whose `MultiSigRequestWithSigner.member == member` (i.e., requests the removed member *created*) and clears their confirmations. It does **not** iterate other requests' `confirmations` HashSets to strip entries where the removed member had merely *confirmed* (not created) the request.
- `current_member()` [3](#0-2)  is only used to validate the *caller* of `confirm`/`add_request`/`delete_request`; it is never applied retroactively to the already-stored `confirmations` set.

Exploit flow (members A, B, C, D, `num_confirmations = 3`):
1. A calls `add_request` creating request R1 (e.g., `Transfer` to an attacker-controlled account).
2. B calls `confirm(R1)` — `confirmations(R1) = {B}` (len 1 < 3, stored, not executed).
3. Separately, A, C, D confirm a `DeleteMember { member: B }` request; it executes `delete_member`, which checks `members.len() - 1 >= num_confirmations` (3 members remain, `3 >= 3` OK) and only clears confirmations for requests *created* by B — R1 was created by A, so `confirmations(R1)` is untouched and still contains `B`.
4. Members are now `{A, C, D}`. C calls `confirm(R1)` → `confirmations(R1) = {B, C}` (len 2 < 3, no execution).
5. D calls `confirm(R1)` → `confirmations.len() + 1 == 3 >= num_confirmations` → **R1 executes**, transferring funds, even though the request was only ever validly confirmed by two live members (C and D) plus one stale entry from a removed non-member (B).

Existing guards fail to prevent this: `assert_valid_request` only checks the *caller*, `current_member()` is not applied to stored confirmations, and `delete_member`'s cleanup only targets self-created requests, not requests confirmed-but-not-created by the removed member.

### Impact Explanation
An attacker (or a rogue/compromised member) can arrange for a member to confirm a large transfer request and then engineer their own removal (or wait for a routine membership change) without that stale confirmation being purged, letting the remaining members inadvertently execute the request with effectively fewer than `num_confirmations` live confirmers. This lets NEAR/wNEAR move out of the multisig account below the intended `num_confirmations` live-member threshold — matching the Critical impact category ("a multisig request executed below `num_confirmations` live members"). The bug is repeatable across any multisig deployed from this contract and across any number of membership changes, since the underlying purge logic is unconditionally incomplete.

### Likelihood Explanation
The precondition is simply that a member confirms a request without it reaching threshold, and that member is later removed via `DeleteMember` while the confirmed-but-unexecuted request remains active — a completely ordinary sequence of multisig operations with no attacker-only privilege needed beyond being (or having been) a member of the multisig, or manipulating timing of legitimate member operations. No special balances or exotic setup are required, only normal multisig membership churn, making this highly feasible and repeatable.

### Recommendation
When removing a member in `delete_member`, iterate over **all** active requests (not just those the member created) and remove the departing member's entry from each request's `confirmations` set. Alternatively/additionally, in `confirm()`, before counting confirmations toward `num_confirmations`, filter the stored set to only entries whose `MultisigMember` still exists in `self.members`.

```rust
fn test_stale_confirmation_after_member_removal() {
    // Setup contract with 4 members (A, B, C, D) and num_confirmations = 3.
    // (Use existing test helpers: alice/bob as accounts, two AccessKey members.)

    // 1. As member A: add_request(R1 = Transfer{...} to some receiver).
    // 2. As member B: confirm(R1) -> assert confirmations(R1).len() == 1.
    // 3. As members A, C, D: add_request_and_confirm a DeleteMember{member: B} request,
    //    confirmed by C then D to execute delete_member(B).
    //    assert members no longer contains B.
    // 4. As member C: confirm(R1) -> assert confirmations(R1).len() == 2 (still contains stale "B").
    // 5. As member D: confirm(R1) -> triggers execution since
    //    confirmations.len() (2, incl. stale B) + 1 >= num_confirmations (3).
    //    assert c.requests.len() == 0 (executed) even though only C and D
    //    are live-member confirmers (2 < num_confirmations 3).
}
```
This test demonstrates the binding `confirmations.len() == num_confirmations` holding while the correct binding `live_member_confirmations == num_confirmations` (2 ≠ 3) is violated at execution time, proving unauthorized sub-threshold execution.

```rust
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
```
