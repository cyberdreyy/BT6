### Title
Post-default instant withdraw receipts drain the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is an alternate completion path that skips the integrity verification performed on the normal path. The analog here is `requestInstantWithdraw` + `claimInstantWithdrawRequest`: after `finalizeDefaultRecovery` crystallizes `defaultRecoveryPrice` and sizes `defaultRecoveryReserve` to cover exactly `totalBasis` (active basis + defaulted-epoch claim basis), a *new* instant withdraw request creates a receipt in `instantWithdrawsRequestsByEpoch[user][epochNumber]`, where `epochNumber` still equals `defaultRecoveryEpoch` (no new epoch can ever start on a defaulted vault). `claimInstantWithdrawRequest` then routes that brand-new receipt through `_claimDefaultedInstantWithdrawRequest`, which pays it out of `defaultRecoveryReserve` at `defaultRecoveryPrice` — the "verification" that only pre-default receipts belong to the recovery basis is never performed for instant requests, unlike `requestWithdraw`, which explicitly guards the post-default case.

### Finding Description [1](#0-0)  shows `requestWithdraw` has a dedicated post-default branch: when `defaultRecoveryFinalized` is true it requires the user to have no outstanding receipts and routes the request into `postDefaultRequests`, never touching `withdrawsRequestsByEpoch`/`lastWithdrawRequest`.

`requestInstantWithdraw` has no such branch. It only calls `_ensureDefaultRecoveryInitialized()` (a lazy-migration helper that is already a no-op once `defaultRecoveryInitialized` is true) and then unconditionally records the receipt under the *current* epoch: [2](#0-1) 

After `finalizeDefaultRecovery`, `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` [3](#0-2) . Since `epochNumber` only increments in `deposit()` while an epoch is running — impossible after default — any post-default instant receipt lands in `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`.

`claimInstantWithdrawRequest` then calls `_claimDefaultedInstantWithdrawRequest`, which clears that entry and pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve` [4](#0-3) [5](#0-4) . The reserve was sized in `finalizeDefaultRecovery` as `reserveAmount = recovered + prefunded + prior reserve` against a fixed `totalBasis`; it contains no headroom for receipts created after finalization.

### Impact Explanation
Any unprivileged user able to trigger a CDO instant withdraw after default finalization (a KYC-passing lender holding tranche tokens, calling the CDO's instant-withdraw path) gets their new receipt paid out of `defaultRecoveryReserve`. Each such claim decrements `defaultRecoveryReserve` in `_transferDefaultRecovery` [6](#0-5)  while the legitimate defaulted-epoch claims remain outstanding. Once the reserve is drained below the sum of honest claims, subsequent `_claimDefaultedWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`/`_claimPostDefaultWithdrawRequest` calls revert on underflow or the ERC20 transfer — permanently freezing the remaining recovery funds. Loss is bounded by the attacker's post-default instant-withdraw amount (up to the full reserve, i.e., all recovered funds, if they hold enough tranche tokens).

### Likelihood Explanation
The vault must default and be finalized with a non-empty instant-pending bucket (`defaultInstantWithdrawsFinalized == true`) and the CDO must still permit instant withdraw requests post-default. `requestInstantWithdraw` itself imposes no epoch/default gating — the only control is whether `IdleCDOEpochVariant` still routes user instant-withdraw calls into it after `defaulted()` is set. If the CDO does not block instant withdrawals in defaulted state, the exploit is a single request followed by a claim. Note the per-user dedup in `instantWithdrawsRequestsByEpoch` does not help: a fresh attacker's entry at `defaultRecoveryEpoch` is indistinguishable from a defaulted receipt.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert (`NotAllowed`) or route the amount into `postDefaultRequests`-style accounting that pays from funded underlying via `_transferFundedClaim`, never from `defaultRecoveryReserve`. Additionally, in `_claimDefaultedInstantWithdrawRequest`, only treat receipts recorded *before* finalization as defaulted claims (e.g., record `epochNumber` into a separate post-default mapping or store a `defaultRecoveryEpoch` cutoff), so receipts created after `defaultRecoveryEpoch` cannot consume the isolated reserve.

```solidity
//       amt * p / 1e18 from defaultRecoveryReserve.
// 5. Honest user H calls claimInstantWithdrawRequest(H):
//    -> _transferDefaultRecovery underflows / transfer fails:
//       reserve was drained by A's post-default claim.
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
