### Title
Instance executor never validates `services` images against `allowed_services`, unlike Docker/Kubernetes - (File: executors/instance/instance.go)

### Summary
The Instance executor's `Prepare` function only calls `common.VerifyAllowedImage` for the job's primary `Image.Name`, and only when `VMIsolation.Enabled` and an image is set at the job level. It has no equivalent check for `options.Build.Services`, and does not reference `InternalImages` at all. Docker and Kubernetes executors, by contrast, validate both the primary image and every service image (with more call sites for the same helper), so a job specifying a disallowed service image would be rejected under Docker/Kubernetes but is never even inspected under the Instance executor.

### Finding Description
`executors/instance/instance.go` `Prepare` (lines 47-66) contains the only enforcement point for image restrictions in this executor: [1](#0-0) 

This block:
- Only fires when `options.Config.Autoscaler.VMIsolation.Enabled` is true and `options.Build.Image.Name != ""`.
- Reads allowed images solely from `options.Config.Instance.AllowedImages`.
- Never sets `InternalImages` in the `VerifyAllowedImageOptions` struct, unlike the multi-match usage seen in `executors/docker/docker.go` and `executors/kubernetes/kubernetes.go` (which reference `InternalImages`/`AllowedServices` several times each, per grep results, implying separate validation paths for helper/service images).
- Never references `options.Build.Services` anywhere in the file — there is no loop over service definitions and no call to `VerifyAllowedImage` (or any equivalent) for them.

Because a job author fully controls the `services:` field in `.gitlab-ci.yml`, and the Instance executor maps job images directly to VM images (`MapJobImageToVMImage: true` in `NewProvider`, line 144), an attacker-controlled service image is passed straight through to VM/container provisioning with zero allow-list enforcement, whereas the same job running under Docker or Kubernetes would have that service image checked against `allowed_services`.

### Impact Explanation
A job author who is otherwise constrained by an administrator's `allowed_images`/`allowed_services` configuration on Docker/Kubernetes runners can bypass that restriction entirely by targeting a runner configured with the Instance (autoscaler/VM-isolation) executor, since the enforcement code path for services simply does not exist there. This lets the job run scripts against, or alongside, a service container/image that was never authorized by the runner administrator's allow-list, undermining the intended uniform image-restriction invariant across executor types.

### Likelihood Explanation
This requires no special privileges beyond what any pipeline author already has (ability to define `image`/`services` in `.gitlab-ci.yml`). It is fully reachable whenever a fleet mixes Instance executor runners with Docker/Kubernetes runners under a shared assumption that `allowed_images`/`allowed_services` are enforced consistently — a realistic and common deployment scenario. The bug is deterministic and trivially repeatable (any job with a `services:` entry on an Instance/autoscaler runner skips validation).

### Recommendation
Add service-image validation to `executors/instance/instance.go` `Prepare`, mirroring the Docker/Kubernetes logic: iterate `options.Build.Services`, and for each service call `common.VerifyAllowedImage` using the runner's configured `AllowedServices` (a new/existing config field analogous to `Instance.AllowedImages`), and pass `InternalImages` consistently so helper/internal service images used across executors are treated identically.

### Proof of Concept
Go test (`executors/instance/instance_test.go`), differential style:
1. Build a `common.RunnerConfig` with `Instance.AllowedImages = []string{"allowed/*"}` and (proposed) `Instance.AllowedServices = []string{"allowed/*"}`.
2. Construct a `common.Build` with `Image.Name = "allowed/image"` (passes) and `Services = []common.Image{{Name: "evil/malicious-service"}}`.
3. Call `executor.Prepare` with `VMIsolation.Enabled = true`.
4. Assert `Prepare` returns `common.ErrDisallowedImage` (or equivalent) for the disallowed service — currently it returns `nil` because no check exists.
5. Run the same `VerifyAllowedImageOptions` for the service image through `docker.go`'s/`kubernetes.go`'s equivalent `Prepare`/create-container path with the same allow-list, and assert it rejects — proving current divergent accept/reject behavior between executors for the identical service image and config.

	// Validate if the image defined in a job is allowed
	//
	// If nesting is not enabled, the image is irrelevant.
	// If image is not defined on a job level there is no need for validation - runner config
	// variable will be enforced later.
	if options.Config.Autoscaler.VMIsolation.Enabled && options.Build.Image.Name != "" {
		var allowed []string
		if options.Config.Instance != nil {
			allowed = options.Config.Instance.AllowedImages
		}

		// verify image is allowed
		if err := common.VerifyAllowedImage(common.VerifyAllowedImageOptions{
			Image:         options.Build.Image.Name,
			OptionName:    "images",
			AllowedImages: allowed,
		}, e.BuildLogger); err != nil {
			return err
		}
	}
