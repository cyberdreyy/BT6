### Title
Operator can permanently freeze all staker withdrawals in `staking_contract` by setting a beneficiary that rejects direct coin transfers - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::set_beneficiary_for_operator` lets an **operator** (a lower-trust role that never owns the staked funds) redirect their commission payout to any address, without validating that the address can actually receive a direct `AptosCoin` transfer. Because `distribute_internal` — the function that must run before a staker's `unlock_stake`, `switch_operator`, `update_commision`, or `request_commission` can proceed — pays the operator's commission through `aptos_account::deposit_coins`, a beneficiary that has opted out of direct coin transfers (or whose `CoinStore` cannot accept the deposit) will make `distribute_internal` abort every single time it is invoked. Since `distribute_internal` is called unconditionally at the top of the staker-facing entry points, this permanently blocks the staker (the actual owner of the funds) from ever withdrawing principal or rewards from that staking contract, exactly mirroring the "missing approval → always-revert → funds locked" bug class in the reference report.

### Finding Description
`set_beneficiary_for_operator` is operator-controlled and performs no validation on `new_beneficiary`: [1](#0-0) 

Compare this to `vesting::set_beneficiary`, which explicitly guards against this exact failure mode with a comment describing the intended invariant: [2](#0-1) 

`staking_contract.move` has no equivalent `assert_account_is_registered_for_apt`-style check for `set_beneficiary_for_operator`.

Every staker-facing mutating entry point (`unlock_stake`, `switch_operator_with_same_commission`, `switch_operator`, `update_commision`, and the permissionless `distribute`) unconditionally calls `distribute_internal` first: [3](#0-2) 

`distribute_internal` withdraws the total unlocked/pending-inactive balance, then iterates over every shareholder in the internal `distribution_pool` and pays them via `aptos_account::deposit_coins`, including the operator's beneficiary when the operator itself holds shares (i.e., has unpaid commission): [4](#0-3) 

The commission share for the operator is (re)created any time rewards accrue, via `request_commission_internal`, which is itself invoked from `unlock_stake`, `switch_operator`, `update_commision`, and the operator-callable `request_commission` entry function: [5](#0-4) 

If the operator sets its beneficiary to an address that has called `aptos_account::set_allow_direct_coin_transfers(false)` (or otherwise cannot accept an un-registered/frozen `CoinStore` deposit), then once the operator has any pending commission share in `distribution_pool`, `aptos_account::deposit_coins` will abort inside the `while` loop of `distribute_internal`. Because the loop processes **all** shareholders (including the staker's own pending withdrawal) atomically in a single Move transaction, one bad recipient aborts the entire transaction, and there is no way to skip or bypass the failing recipient. Since `distribute_internal` runs at the very start of `unlock_stake`/`switch_operator`/`update_commision`/`distribute`, the staker's ability to ever withdraw principal or rewards from this staking contract is now permanently blocked — the operator holds no ownership over the staker's principal, yet can trap it indefinitely through an action fully within the operator's own permission scope.

### Impact Explanation
This is a permanent, non-recoverable loss of claim rights for the staker: once the operator's beneficiary is unable to receive a direct transfer, every function that could unlock/withdraw/redistribute the staker's stake (`unlock_stake`, `switch_operator`, `update_commision`, `distribute`, `request_commission`) reverts forever, because `distribute_internal` is a mandatory precondition in all of them. The staker cannot self-remedy this because `set_beneficiary_for_operator` is restricted to the operator signer — the staker has no way to reset the operator's beneficiary or bypass the failing payout. This satisfies the required impact "Permanent lock or non-recoverable loss of claim rights in stake, delegation, commission, beneficiary flows," since a lower-privileged operator role can strand a higher-privileged staker's principal and rewards.

### Likelihood Explanation
Reaching this state does not require any privileged capability beyond the operator role that the staker itself already delegated when creating the `staking_contract` (`create_staking_contract`). The operator merely needs to:
1. Call `set_beneficiary_for_operator` with any address of its choosing, and
2. Have that address call the standard, permissionless `aptos_account::set_allow_direct_coin_transfers(false)` beforehand (or use any account with a frozen/incompatible `CoinStore`).
No governance, admin rights, or leaked keys are needed, and the vesting module's own code comment demonstrates the Aptos team is aware this exact scenario is a real risk pattern that was patched for `vesting::set_beneficiary` but left unaddressed for `staking_contract::set_beneficiary_for_operator`.

### Recommendation
Add the same safeguard used in `vesting::set_beneficiary` to `staking_contract::set_beneficiary_for_operator`: require that `new_beneficiary` is registered/able to receive direct `AptosCoin` transfers before accepting the update, e.g. call an equivalent of `assert_account_is_registered_for_apt(new_beneficiary)`. Additionally, consider hardening `distribute_internal` itself so that a single failing recipient (operator beneficiary or otherwise) cannot block distribution to all other shareholders — e.g., isolate failures per-recipient or fall back to leaving payment as a claimable balance instead of aborting the whole loop.

### Proof of Concept
1. Staker `S` creates a staking contract with operator `O` via `create_staking_contract`, with `commission_percentage > 0`.
2. `O` calls `staking_contract::set_beneficiary_for_operator(O, B)` where `B` is an address that has called `aptos_account::set_allow_direct_coin_transfers(false)`.
3. The validator earns rewards; `O` (or anyone) triggers `request_commission`/`unlock_stake`, causing `request_commission_internal` to add `O`'s commission as pending shares in `distribution_pool`.
4. `S` calls `unlock_stake` (or anyone calls `distribute`) once the stake becomes inactive: `distribute_internal` iterates the `distribution_pool`, reaches `O`'s share, resolves the recipient to `B` via `beneficiary_for_operator`, and calls `aptos_account::deposit_coins(B, ...)`, which aborts because `B` rejects direct transfers.
5. The entire transaction reverts. Every subsequent call to `unlock_stake`, `switch_operator`, `update_commision`, `request_commission`, or `distribute` for this `(S, O)` pair reverts identically, since `distribute_internal` always runs first — permanently freezing `S`'s stake and rewards in the pool.

        operator: address,

        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount

        // This won't become fully unlocked until the stake pool's lockup expires.

        let pool_address = staking_contract.pool_address;
        emit(
            RequestCommission {
                operator,
                pool_address,
                accumulated_rewards,
                commission_amount
            }
        );

        commission_amount
    }
