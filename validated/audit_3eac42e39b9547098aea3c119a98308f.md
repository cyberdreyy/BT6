Confirmed: `createDstEscrow` is a fully public function with no whitelist/permission check, and it takes `dstImmutables` entirely as caller-supplied calldata, including the `parameters` field (protocol fee amount, integrator fee amount, protocol fee recipient, integrator fee recipient). Nothing on-chain in `createDstEscrow` cross-checks this data against the fee terms committed during `_postInteraction` on the source chain (only emitted off-chain in `DstImmutablesComplement`). The maker's actual payout is computed as `immutables.amount - integratorFeeAmount - protocolFeeAmount` at withdraw time, entirely from the caller-controlled `parameters`.

### Title
Unvalidated destination-escrow fee parameters allow an unprivileged caller to redirect integrator/protocol fees away from the intended recipient - (File: contracts/BaseEscrowFactory.sol)

### Summary
`createDstEscrow` in [1](#0-0)  accepts the full `IBaseEscrow.Immutables` struct, including the `parameters` bytes blob (protocol/integrator fee amounts and recipients), directly from `msg.sender` with no cross-check against the fee terms established on the source chain during `_postInteraction`.

### Finding Description
On the source chain, `_postInteraction` computes `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient` from the order's committed fee data and packs them into `DstImmutablesComplement.parameters`, which is only emitted as an event for off-chain reconstruction [2](#0-1) . This value is never stored on-chain or bound to the destination escrow deployment. When any address later calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)`, the contract takes `dstImmutables.parameters` verbatim from calldata, uses it to compute the CREATE2 salt/hash, and deploys the escrow [3](#0-2) . At withdrawal time, `EscrowDst._withdraw` decodes `integratorFeeRecipientCd()`/`protocolFeeRecipientCd()` from this same attacker-supplied `parameters` and pays them before paying the maker the remainder [4](#0-3) . This mirrors the Turnstile analog: fee routing is derived from data the calling/depositing party fully controls rather than from a value bound to the authorized application/integrator, so a caller can substitute their own address as `integratorFeeRecipient`/`protocolFeeRecipient` and/or inflate the fee amounts, since `_withdraw` only validates the immutables' hash matches what was used at deployment — not that the fee terms match what the maker's order actually authorized.

### Impact Explanation
If exploited, the "fee" portion (`integratorFeeAmount`/`protocolFeeAmount`) deducted from `immutables.amount` before the maker receives funds can be inflated and routed to an attacker-chosen recipient instead of the legitimate integrator/protocol, directly reducing the maker's payout on the destination chain. This is a theft of value from the amount otherwise due to the maker/integrator via a fee-recipient substitution — conceptually the same "redirect fee routing via caller-controlled proxy/parameter" root cause as the Turnstile finding.

### Likelihood Explanation
Low-to-uncertain in practice: `createDstEscrow` is normally called by the resolver who is also the one funding the escrow with `immutables.amount` of tokens out of their own pocket, so the resolver has no direct financial incentive to shortchange the maker by this specific fee-substitution — they would still transfer the same total `immutables.amount`, and diverting the fee split does not net them extra profit unless they also set themselves as `integratorFeeRecipient`/`protocolFeeRecipient`, in which case they do gain the diverted amount at the maker's expense. Whether this is actually reachable end-to-end depends on off-chain infrastructure (maker/relayer) verifying `dstImmutables` against the `SrcEscrowCreated` event's `DstImmutablesComplement.parameters` before the maker calls `withdraw` — a check this repository's own documented threat model does not describe as enforced on-chain [1](#0-0) . I could not verify within this repo whether any off-chain component performs this reconciliation, so likelihood of an unsuspecting maker actually withdrawing from a maliciously parameterized escrow is uncertain.

### Recommendation
Bind the destination escrow's fee `parameters` to the source-chain-committed values on-chain (e.g., include a hash/commitment of `DstImmutablesComplement.parameters` in the order/extension data validated during `createDstEscrow`), rather than trusting `dstImmutables.parameters` supplied unchecked by the caller of `createDstEscrow`.

### Proof of Concept
1. Maker signs an order via the Limit Order Protocol; resolver fills it, triggering `_postInteraction`, which computes and emits `DstImmutablesComplement.parameters = (protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` for chain X reconciliation [2](#0-1) .
2. Resolver (or any address) calls `createDstEscrow` on the destination chain with a `dstImmutables.parameters` blob it crafts itself, substituting its own address as `integratorFeeRecipient` and/or `protocolFeeRecipient`, and/or increasing the fee amounts, funding the escrow with `immutables.amount` as required [5](#0-4) .
3. When the maker (or public withdrawer) calls `withdraw(secret, immutables)` using the immutables that match this deployed escrow, `_withdraw` pays the attacker-chosen fee recipient(s) first, then pays the maker only `amount - integratorFeeAmount - protocolFeeAmount` [6](#0-5) , resulting in the maker receiving less than the originally agreed amount and the attacker capturing the difference.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
