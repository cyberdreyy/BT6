### Title
Fee-on-transfer underlying causes `IdleCreditVault` to mint more strategy tokens than underlying received, inflating NAV and leaving late withdrawers' funds stuck - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.deposit()` pulls `_amount` of underlying from the CDO but mints exactly `_amount` of 1:1-priced strategy tokens without measuring the actual received balance. With a fee-on-transfer token the vault receives less than it accounts for, so `IdleCDOEpochVariant`'s NAV (strategy tokens × `price() == oneToken`) overstates real assets and the shortfall is socialized onto the last claimants, whose withdraw receipts can never be paid in full.

### Finding Description
The external report describes recording the requested amount rather than the actually received amount when transferring ERC20s. The same pattern exists here, in the credit-vault strategy rather than a claims mapping.

In `IdleCreditVault.deposit` (contracts/strategies/idle/IdleCreditVault.sol:596-617):

```solidity
function deposit(uint256 _amount) external virtual override returns (uint256) {
  _onlyIdleCDO();
  if (_amount > 0) {
    underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
    _mint(msg.sender, _amount);
  }
  ...
  totEpochDeposits += _amount;
  return _amount;
}
```

Two uncorrected mismatches:

1. `_mint(msg.sender, _amount)` mints `_amount` strategy tokens even though only `_amount - fee` arrived. `price()` is hardcoded to `oneToken` (line 174-176), so `IdleCDOEpochVariant.getContractValue()` counts `_amount` of NAV while the vault only holds `_amount - fee`.
2. `totEpochDeposits += _amount` records the full requested amount, which is the figure used by the epoch funding flow (`stopEpoch`/`startEpoch` and `sendInterestAndDeposits`) to size how much cash is routed to the borrower or kept as buffer.

The caller-side `IdleCDO._deposit`/`IdleCDOCreditVault._deposit` already does the correct thing for the tranche depositor (it measures `_contractTokenBalance(_token) - _preBal` before minting tranche shares at IdleCDO.sol:250-253 and IdleCDOCreditVault.sol:203-206), but then calls `strategy.deposit(_amount)` with the *nominal* amount. Two consequences:

- If the CDO has no spare underlying balance, `safeTransferFrom` in the strategy reverts (CDO only holds `amount - fee`), permanently DoSing deposits for that vault. If the CDO holds prior donations/fees, the pull succeeds and the fee is silently paid out of other depositors' money while the new strategy tokens are minted at full value.
- Even where the pull succeeds, the vault now owes `_amount` in strategy tokens against `_amount - fee` held. Since the vault pays withdraw and instant-withdraw receipts 1:1 (`withdrawsRequestsByEpoch`, `instantWithdrawsRequestsByEpoch`, `sendInterestAndDeposits`), cumulative claims exceed reserves and the final redeemers cannot withdraw — funds are stuck, exactly the reported impact.

### Impact Explanation
Insolvency / permanent freezing of funds. Every fee-on-transfer deposit mints unbacked strategy tokens into the CDO's NAV at fixed `price() == 1`. The deficit is not attributed to the depositor (who already received correctly-priced tranche shares); it is embedded in the vault's claim base, so epoch withdraw receipts and instant-withdraw claims sum to more than the underlying balance. The last claimants' withdrawals revert or are underpaid permanently — a quantified loss equal to the cumulative transfer fees.

### Likelihood Explanation
Requires the vault's configured `token` to charge a transfer fee (e.g., USDT with fee enabled, or any rebasing/fee token). `initialize()` accepts an arbitrary `_underlyingToken` with no compatibility check (line 124-140), so no privileged misbehavior is needed — any lender depositing during the buffer phase triggers the divergence through the normal `depositAA`/`depositBB` → `_deposit` → `strategy.deposit` path.

### Recommendation
Measure actual received balance in `IdleCreditVault.deposit` (and symmetrically in `IdleCDO._deposit`'s strategy call) instead of trusting `_amount`:

```solidity
uint256 balBefore = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - balBefore;
_mint(msg.sender, received);
totEpochDeposits += received;
return received;
```

Alternatively, explicitly reject fee-on-transfer/rebasing tokens at vault deployment and document the supported-token assumption.

### Proof of Concept
Foundry sketch using a mock deflationary ERC20 (1% transfer fee):

```solidity
function test_feeOnTransfer_depositMismatch() public {
    FeeToken feeToken = new FeeToken(); // burns 1% on transfer
    // deploy IdleCreditVault + IdleCDOEpochVariant with feeToken as underlying
    feeToken.mint(lender, 1000e6);
    vm.startPrank(lender);
    feeToken.approve(address(cdo), 1000e6);
    cdo.depositAA(1000e6);           // AA tranche minted for 990e6 (actual received)
    vm.stopPrank();

    // strategy minted 1000e6 strategyTokens to CDO but only holds 990e6
    assertEq(vault.balanceOf(address(cdo)), 1000e6);
    assertEq(feeToken.balanceOf(address(vault)), 990e6);

    // NAV is overstated: getContractValue() counts 1000e6 while only 990e6 exist
    // at claim time, withdraw receipts totaling 1000e6 exceed the 990e6 reserve;
    // the last claimer's claimWithdrawRequest reverts on insufficient balance
}
```

The same PoC works against `IdleCDO._deposit` + any `onlyIdleCDO` strategy `deposit` that mints/pulls nominal `_amount` (e.g., `IdleClearpoolStrategy.deposit` at contracts/strategies/clearpool/IdleClearpoolStrategy.sol:231-246 and `IdleHarvestStrategy.deposit` at contracts/strategies/harvest/IdleHarvestStrategy.sol:193-198), where the second pull either reverts or drains pre-existing strategy balance.
