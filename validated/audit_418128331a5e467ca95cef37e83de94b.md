## Title
Builder-payment withdrawal amount is not capped to the builder's actual balance before being committed to the execution layer, allowing supply-inflating over-payment - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` copies the raw `amount` field of a queued `BuilderPendingWithdrawal` straight into the `Withdrawal` that is placed in `state.payload_expected_withdrawals`, without capping it against `state.builders[builder_index].balance`. That `Withdrawal` list is what the execution layer is contractually required to mint into the recipient account. Meanwhile `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from the consensus-layer balance. When a builder's committed pending withdrawals sum to more than its remaining balance (e.g. two payments settle before the sweep drains the queue), the EL pays the full requested amount to `fee_recipient` while the CL only debits the builder's actual balance, permanently inflating the tracked ETH supply.

### Finding Description [1](#0-0) 
`get_builder_withdrawals` builds a `Withdrawal(amount=withdrawal.amount, ...)` directly from each entry in `state.builder_pending_withdrawals`, with no comparison to `state.builders[builder_index].balance`. [2](#0-1) 
`apply_withdrawals`, by contrast, explicitly caps the on-chain deduction: `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)`.

The withdrawal that gets asserted as `payload_expected_withdrawals` is the value the block commits the execution layer to honor (per the note directly above `process_withdrawals`, the EL "mints the full committed amount regardless" of what happens on the CL side). Since the amount placed in the committed `Withdrawal` is the *uncapped* requested amount but only the *capped* amount is removed from the builder's tracked balance, any shortfall becomes unbacked ETH paid to `withdrawal.fee_recipient` — a Gwei-creation event with no corresponding CL-side debit.

This is validated directly by the existing spec test: [3](#0-2) 
`test_builder_withdrawal_insufficient_balance` sets a builder's balance to 1 ETH but a queued pending withdrawal amount of 5 ETH, and asserts that the resulting committed withdrawal still carries `amount == 5 ETH` while `builders[0].balance` only drops to `0`. The test comment even states "deduction capped to available balance" as the *expected* behavior, confirming the mismatch is not accidental but the spec's actual behavior — i.e., the committed payment (5 ETH minted on the EL side) is 4 ETH larger than what was actually debited from the builder.

This is structurally the same bug class as the RocketPool report: value that the accounting layer commits to disburse is disconnected from the ledger that is supposed to back it, so `Gwei` promised/paid does not equal `Gwei` actually removed from an owner's balance — except here the direction is inflation (excess payout) rather than lock-up, which is a more severe variant of the same root cause (loss of the "amount committed == amount debited" equality).

### Impact Explanation
This breaks the equality "a Gwei paid by the execution layer must correspond 1:1 to a Gwei removed from the payer's consensus-layer balance." Because `payload_expected_withdrawals` is the CL's binding commitment enforced on the EL, any block including such a withdrawal forces the EL to mint ETH that is not backed by an actual balance decrease anywhere in the beacon state. This is a supply-inflation / Gwei-created bug and is Critical per the stated criteria ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
The scenario requires only that a builder's `builder_pending_withdrawals` entries (created from settled bid payments once weight reaches quorum) sum, at sweep time, to more than the builder's remaining balance — e.g. multiple payments settling in quick succession, or a payment settling after the builder's balance has already been reduced by an earlier withdrawal or an unrelated builder-exit/withdrawal path. No malicious peer, coalition, or client bug is required — this can occur purely from the ordering of legitimate protocol events (multiple blocks by the same builder being finalized/settled close together). I was not able to fully trace every path by which `builder_pending_withdrawals` amounts get queued (e.g., whether `can_builder_cover_bid` checks account for all in-flight pending withdrawals at bid-acceptance time) within the remaining investigation budget, so I cannot rule out that an existing check elsewhere fully prevents queuing more pending withdrawal value than the builder's current balance. This is the main residual uncertainty for this finding.

### Recommendation
Cap the `amount` written into the committed `Withdrawal` in `get_builder_withdrawals` (and in `get_builders_sweep_withdrawals`, which does read `builder.balance` correctly) to `min(withdrawal.amount, state.builders[builder_index].balance)`, tracking the running balance across the loop (similar to how `get_balance_after_withdrawals` tracks validator balances across `prior_withdrawals` in the validator-sweep path), so the value committed to the execution layer can never exceed what `apply_withdrawals` will actually deduct.

### Proof of Concept
Using the existing spec test as the concrete state trace:
1. Pre-state: `state.builders[0].balance = 1_000_000_000` (1 ETH); `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=F)]`.
2. `get_expected_withdrawals` → `get_builder_withdrawals` emits `Withdrawal(validator_index=builder_idx(0), address=F, amount=5_000_000_000)` unconditionally (specs/gloas/beacon-chain.md:1822-1829).
3. `process_withdrawals` sets `state.payload_expected_withdrawals` to include this 5 ETH withdrawal — the value the EL must mint to `F`.
4. `apply_withdrawals` executes `state.builders[0].balance -= min(5_000_000_000, 1_000_000_000)` → balance becomes `0` (specs/gloas/beacon-chain.md:1926-1929), i.e., only 1 ETH was actually removed from any tracked balance.
5. Net effect: the execution layer pays out 5 ETH to `F`, but only 1 ETH was debited anywhere in the beacon state — 4 ETH of unbacked Gwei is created, matching `test_builder_withdrawal_insufficient_balance` (tests/core/pyspec/eth_consensus_specs/test/gloas/block_processing/test_process_withdrawals.py:114-156), which encodes exactly this amount/balance mismatch as expected output.

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
