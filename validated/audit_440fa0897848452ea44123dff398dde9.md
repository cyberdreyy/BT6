### Title
`JsonRpcRequestProcessor::bank()` silently falls back to the root bank when a requested commitment slot is missing, returning wrong-slot state to unprivileged RPC callers - (File: rpc/src/rpc.rs)

### Summary
This is a bug-class analog to the reported issue: both bugs share the pattern of a query path that, upon failing to obtain the *intended* up-to-date data (Asset.lotPrice() failing to get a fresh oracle price; the RPC `bank()` helper failing to find the bank at the requested commitment slot), silently substitutes a different, non-requested value (a stale cached price vs. an unrelated root bank) instead of surfacing an error or fetching the correct value, so downstream consumers receive data attributed to the wrong context.

### Finding Description
`JsonRpcRequestProcessor::bank()` resolves the `Arc<Bank>` to use for a given `CommitmentConfig`. For `Processed`/`Finalized` commitments it computes the target `slot` via `self.block_commitment_cache.read().unwrap().slot_with_commitment(commitment.commitment)` and then looks it up in `bank_forks`: [1](#0-0) 

If that slot is not present in `bank_forks` (a scenario the code itself documents as a "known bug in snapshot creation" or a race between an old bank being purged and `BlockCommitmentCache` not yet updated), the code does not return an error to the caller. Instead it logs a warning and falls back to an unrelated bank — `r_bank_forks.root_bank()`: [2](#0-1) 

Every unprivileged JSON-RPC handler that resolves its working bank via this helper (directly or through `get_bank_with_config`) is affected: the caller asked for state "as of slot X with commitment Y" but may silently receive state from the root bank, which can be a different slot with a different account/program/blockhash state, without any indication in the response that a fallback occurred (aside from a server-side log line the caller cannot see).

### Impact Explanation
This matches the "wrong-slot/fork/account data returned" impact category permitted by the validation rules. An unprivileged caller issuing any commitment-scoped JSON-RPC read (e.g., `getAccountInfo`, `getBalance`, `getProgramAccounts`, `getLatestBlockhash`, `simulateTransaction`, etc.) during the described race/bug window would receive a response whose `context.slot` and returned state correspond to `root_bank()`'s slot rather than the slot actually implied by their commitment, which can silently break client assumptions (e.g., "read-your-write" consistency, fee/blockhash validity, staleness bounds) analogous to how the Reserve Protocol's fallback pricing silently substitutes an older price for a fresher one, causing misestimation of value.

### Likelihood Explanation
The code's own comments state the missing-slot condition is expected to occur from "a known bug in snapshot creation" or from a race between bank purging in `BankForks` and delayed `BlockCommitmentCache` updates — i.e., it is an acknowledged, reachable (if rare) production condition, not purely theoretical. It requires no special privilege — any client making a standard commitment-scoped RPC call can trigger the fallback path when the race/bug window is hit; the request path itself is a single, unprivileged JSON-RPC call.

### Recommendation
Replace the silent `unwrap_or_else(|| r_bank_forks.root_bank())` fallback with a way to surface the mismatch to the caller — e.g., return an explicit RPC error (analogous to how `BlockhashQuery`/`is_blockhash_valid` propagate expiry as errors rather than silently substituting a different value) instead of transparently substituting `root_bank()`. At minimum, the returned response should reflect the actual slot/bank used so callers can detect the substitution rather than unknowingly consuming state from an unintended slot.

### Proof of Concept
Not independently reproduced in this repo; the finding is derived directly from the documented fallback logic and its accompanying comments in `bank()`: [2](#0-1) 

which explicitly acknowledges the missing-slot condition as a known, reachable bug scenario rather than an unreachable/theoretical case. Full end-to-end reproduction (triggering the snapshot/race condition against a running validator) was not performed as part of this analysis and would require live validator process access.

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
