### Title
Stale per-epoch instant-withdraw ledger is never cleared on the funded claim path, allowing a defaulted-epoch re-claim of already-paid receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant-withdraw receipt but only clears the aggregate counter `instantWithdrawsRequests[_user]`; it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the borrower later defaults in that same epoch, `_claimDefaultedInstantWithdrawRequest` re-reads the stale per-epoch entry as if the receipt were still outstanding, letting the same receipt be visited twice — the direct analog of `InlineVec::clear`/`SerVec::clear` revisiting already-freed elements because `len` was only updated after the loop.

### Finding Description
In the rkyv bug, element bookkeeping (`self.len`) is updated only after iterating, so a mid-loop panic leaves stale length and a second `clear()` re-processes freed elements. Here, per-epoch bookkeeping is the analog of `len`:

- `requestInstantWithdraw` writes three ledgers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366-374).
- `claimInstantWithdrawRequest` pays out via `_transferFundedClaim` but clears only the aggregate: `instantWithdrawsRequests[_user] = 0` (lines 387-392). The per-epoch entries that the default-recovery path uses are left untouched.
- After `finalizeDefaultRecovery` sets `defaultRecoveryFinalized`, `defaultInstantWithdrawsFinalized` and `defaultRecoveryEpoch` equal to the epoch in which the request was made, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — which still includes the already-claimed amount (lines 842-855).

Because instant withdrawals are claimed *during* a running epoch and a default is declared against that same `epochNumber`, the funded claim and the defaulted claim can target the same epoch key. The stale marker is the "len left at its original value" of the rkyv bug: the defaulted claim path cannot distinguish paid receipts from unpaid ones.

### Impact Explanation
A user who claimed a funded instant withdrawal in epoch E can, after the borrower defaults on epoch E and recovery is finalized, be re-evaluated with a `claimBasis` that includes the already-paid amount. Two outcomes, both harmful:

- If the user holds enough receipt strategy tokens (e.g., from a second instant request made in the same epoch before stop), `_burn(_user, claimBasis)` succeeds and `_transferDefaultRecovery` pays the stale component again, draining `defaultRecoveryReserve` and diluting other defaulted-epoch claimants' recovery price.
- If `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` underflows (the aggregate was already reduced by the funded claim path's users), the subtraction reverts, permanently blocking that user's legitimate defaulted-epoch claim and potentially griefing reserve distribution accounting.

### Likelihood Explanation
Requires: an epoch with instant withdrawals enabled, a user who claims a funded instant receipt during the running epoch, and a subsequent borrower default on that same epoch with `finalizeDefaultRecovery` completing. All attacker actions (request, claim, optional second request) are unprivileged and honest-privileged sequencing (stopEpoch, default handling) is required anyway for any default-path bug. The stale-state precondition is created by ordinary, legitimate usage — no special timing beyond acting within one epoch.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers alongside the aggregate, mirroring `_claimDefaultedInstantWithdrawRequest`: zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or track per-epoch funded flags) and decrement `instantWithdrawClaimsByEpoch[epochNumber]` for the paid amount, so the default-recovery path never revisits a settled receipt.

```solidity
//    user -> cdoEpoch.requestInstantWithdraw via IdleCDO -> instant ledgers written for epoch E

//    -> paid at par; instantWithdrawsRequests[user] == 0
```

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
