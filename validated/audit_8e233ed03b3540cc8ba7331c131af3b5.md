### Title
Stale rejection weight is never retracted when a signer later accepts, letting phantom reject-weight force a valid block into `SignersRejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tallies `total_weight_approved` and `total_weight_rejected` per block independently, using `gathered_signatures` and `responded_signers` only to prevent the *same* vote type from being double-counted. It never removes a signer's weight from `total_weight_rejected` when that same signer subsequently sends an `Accepted` message for the block, so a signer who rejects and then changes their mind to accept still counts permanently toward the reject tally while also counting toward the accept tally. This is the same bug class as the report's "stale worst-price never reconciled with the real state" - a stale, unretracted value (here, rejection weight) is left baked into an aggregate (`total_weight_rejected`) that a downstream equality check (`blocking minority` vs `weight_threshold`) relies on being an accurate, current tally of votes.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the accept path only guards against re-adding weight for a repeated accept: [1](#0-0) 

and the reject path only guards against re-adding weight for a repeated reject, via `responded_signers.insert(slot_id)`: [2](#0-1) 

Walking through the two possible vote-flip orders:
- **Accept → Reject**: `responded_signers` already contains the slot from the accept, so the later reject's `responded_signers.insert(slot_id)` returns `false` and the reject weight is silently dropped (not double counted — matches the intended "don't count both" semantics).
- **Reject → Accept**: the reject path adds the slot to `responded_signers` and bumps `total_weight_rejected`. When the *same* signer later sends `Accepted`, the accept path's only guard checks `gathered_signatures.contains_key(&slot_id)` (still empty, since rejects never touch `gathered_signatures`), so it happily adds the signer's weight to `total_weight_approved` too — **without ever decrementing `total_weight_rejected`**.

The result: after a reject-then-accept flip, that signer's weight is counted in *both* buckets simultaneously. `total_weight_rejected` is a stale snapshot that no longer reflects the signer's current (accepted) vote, exactly analogous to `last.sharePrice` in the external report being frozen at a stale value instead of being reconciled after the real state-changing event.

Notably, the signer-side database (`stacks-signer/src/signerdb.rs`) explicitly implements the *correct* behavior for this exact scenario — `add_block_signature` clears any prior rejection when a signature is recorded, verified by the `reject_then_accept` test: [3](#0-2) 

and the project's own CHANGELOG documents this as an intentional fix: "Do not count both a block acceptance and a block rejection for the same signer/block." That fix, however, was applied only to the individual signer's local bookkeeping in `signerdb.rs`, not to the node-side `StackerDBListener` that the mining coordinator actually uses to decide whether to abandon a block proposal.

### Impact Explanation
The miner's block-acceptance loop in `signer_coordinator.rs` checks the rejection threshold before the approval threshold: [4](#0-3) 

If `total_weight_rejected` carries phantom weight from a signer who has actually since accepted, that phantom weight can combine with genuine rejections from other signers to cross the "> blocking minority" threshold (`total_weight_rejected + weight_threshold > total_weight`), causing the coordinator to return `Err(NakamotoNodeError::SignersRejected {...})` and abandon a block even though the *true, current* vote state (each signer's latest message) might already have enough real approvals to clear the 70% threshold. This is a liveness wedge on block production/finalization driven by an aggregated-weight-vs-verified-current-votes mismatch, triggerable by a single signer flipping their own vote (no majority required), matching the allowed impact category "a signer wedged into never signing valid blocks" / miscounted response equivalent at the coordinator level.

### Likelihood Explanation
Medium. It requires only one signer (buggy or malicious) to send a `Rejected` message and later send an `Accepted` message for the same block signature hash — an entirely normal client-driven sequence (e.g. re-evaluation after a state update causes a signer to change its verdict, which the docs describe as a supported flow: "For some rejection reasons, a signer will reconsider a block proposal it previously rejected"). No control of other signers' keys, no majority, and no StackerDB-mechanics exploitation is needed — only crafting/ordering of the two legitimate message types from one signer's own key.

### Recommendation
In `StackerDBListener::run`'s accept-handling branch, when a signer's slot is found in `responded_signers` but not yet in `gathered_signatures` (i.e., they previously rejected), subtract that signer's weight from `total_weight_rejected` (and remove any per-txid `failed_txids` weight attributed to them) before adding their weight to `total_weight_approved`, mirroring the reconciliation already implemented in `stacks-signer/src/signerdb.rs`'s `add_block_signature`/rejection-clearing logic.

### Proof of Concept
1. Coordinator inserts a fresh `BlockStatus` for a proposal via `StackerDBListenerComms::insert_block` (`total_weight_approved = 0`, `total_weight_rejected = 0`). [5](#0-4) 
2. Signer S (weight `w_S`) sends `BlockResponse::Rejected` for the block. `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w_S`.
3. Other signers whose combined weight plus `w_S` is close to, but under, the blocking minority (`total_weight - weight_threshold`) also send genuine rejections.
4. Signer S re-evaluates and sends `BlockResponse::Accepted` for the same block. Since `gathered_signatures` doesn't contain `slot_S`, `total_weight_approved += w_S` — but `total_weight_rejected` still contains `w_S` from step 2 (never decremented).
5. If the other genuine rejections' weight plus the still-present phantom `w_S` now exceeds the blocking minority, `signer_coordinator.rs`'s loop hits the rejected branch first and returns `SignersRejected`, discarding the proposal — even though S's *current* vote is Accept and the true tally of latest votes might not actually cross the reject threshold.
