### Title
Already-claimed instant-withdraw receipts remain in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` and are double-counted as default-recovery basis when the borrower defaults in the same epoch, freezing recovery claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the Carapace `_assessState` bug (a resolved "late" state persisting and being re-counted on the next assessment), `IdleCreditVault` never clears per-epoch instant-withdraw receipt accounting when a receipt is normally claimed. If the borrower later defaults while `epochNumber` is unchanged (the `epochNumber += 1` increment only happens inside the successful `stopEpoch` path via `deposit`), `finalizeDefaultRecovery` treats the already-paid receipts as still outstanding default-epoch claims. This inflates the recovery basis, fabricates a "prefunded" reserve that no longer exists, and makes affected users' recovery claims revert permanently.

### Finding Description
`requestInstantWithdraw` records per-epoch bookkeeping: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) . The normal claim path `claimInstantWithdrawRequest` only zeroes the aggregate `instantWithdrawsRequests[_user]` — it never clears either per-epoch entry [2](#0-1) . Those per-epoch entries are only decremented inside `_claimDefaultedInstantWithdrawRequest`, i.e. after a default [3](#0-2) .

`epochNumber` is bumped only in `deposit` while `isEpochRunning` (the successful `stopEpoch` path) [4](#0-3) . When `stopEpoch`'s borrower pull fails, the catch block calls `_handleBorrowerDefault` and the epoch counter is not advanced [5](#0-4) . `finalizeDefaultRecovery` then sets `defaultRecoveryEpoch = epochNumber`, the same epoch in which instant receipts were created and already paid [6](#0-5) .

Two stale reads result:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still includes already-claimed receipts — whenever `pendingInstantWithdraws != 0` [7](#0-6) . `_defaultPrefundedInstantReserve` then computes `instantBasis - pendingInstant` and counts that phantom cash as held reserve, inflating `reserveAmount` and `recoveryPrice` beyond actual underlying held [8](#0-7) .

2. On claim, `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` (including the already-paid amount) and executes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows since the aggregate was already zeroed — permanently reverting that user's recovery claim and corrupting `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` for everyone else [9](#0-8) .

The stale-state pattern mirrors the source bug exactly: a "resolved" condition (funded + claimed instant receipt) is not marked resolved in the per-epoch state, so the next default assessment in the same cycle re-counts it.

### Impact Explanation
Any unprivileged user who makes and claims an instant withdrawal during an epoch that later defaults leaves phantom claim basis in the recovery calculation. Consequences:

- `defaultRecoveryReserve` is overstated by the claimed amounts while the cash is gone, so recovery payments exhaust the strategy balance early; the last claimants' transfers revert → permanent freezing of remaining recovery funds.
- Every user whose epoch-N instant receipt was already claimed has `instantWithdrawsRequests[user] -= claimBasis` underflow, so their defaulted-epoch instant recovery claim can never execute.
- `totalBasis` is inflated, so `recoveryPrice` is mispriced for all normal/APR0 pending withdraw claimants.

No privileged misbehavior is required: the attacker is an ordinary instant-withdraw requester, the borrower default path is reachable via honest `stopEpoch`/`startEpoch` manager calls, and existing guards (`_onlyIdleCDO`, `defaultRecoveryFinalized` one-shot check, `NotAllowed` on double finalize) do not catch it.

### Likelihood Explanation
Requires three conditions, all reachable in normal operation: (a) at least one instant withdrawal is funded via `getInstantWithdrawFunds` and claimed mid-epoch, (b) another instant receipt remains pending so `pendingInstantWithdraws != 0` at default, and (c) the borrower fails to fund `stopEpoch` (or `sendFundsToBorrower` fails at `startEpoch`), which is precisely the stressed scenario the default machinery exists for. The user triggering the stale state needs no special access and may even be unaware; a deliberate attacker can additionally time an instant request/claim to maximize the phantom basis.

### Recommendation
Clear per-epoch instant bookkeeping on the funded claim path: in `claimInstantWithdrawRequest`, delete `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrease `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (mirroring `_claimDefaultedInstantWithdrawRequest`). Alternatively, key instant claims by an epoch identifier that is guaranteed to differ from any later `defaultRecoveryEpoch`, or recompute `instantWithdrawClaimsByEpoch`/prefunded reserve from `pendingInstantWithdraws` and live `instantWithdrawsRequests` instead of trusting stale per-epoch aggregates.

### Proof of Concept
Foundry fork sketch (contracts under test in `test/foundry/IdleCreditVault.t.sol` use the same helpers):

```solidity
// Setup: depositAA(user1, X), depositAA(user2, Y); manager starts epoch 0.
// 1) During epoch 0 (epochNumber == 0):
//    user1.requestInstantWithdraw via cdoEpoch (instant request);
//    user2 also requests instant withdraw (kept pending / only partially funded).
// 2) manager calls getInstantWithdrawFunds() with borrower funded for user1's
//    request only -> user1.claimInstantWithdrawRequest() succeeds.
//    instantWithdrawsRequests[user1] == 0 but
//    instantWithdrawsRequestsByEpoch[user1][0] and
//    instantWithdrawClaimsByEpoch[0] still hold user1's amount.
// 3) Borrower unfunded -> manager stopEpoch(0,0) -> catch -> _handleBorrowerDefault.
//    epochNumber is still 0 (no successful deposit() ran).
// 4) manager finalizeDefault(recovered, manager):
//    - defaultRecoveryEpoch == 0
//    - defaultPendingClaimBasis() includes instantWithdrawClaimsByEpoch[0]
//      which still counts user1's already-paid receipt
//    - _defaultPrefundedInstantReserve() overcounts reserve by that amount
// 5) assert: user1.claimInstantWithdrawRequest() (or the CDO claim path)
//    reverts on underflow of instantWithdrawsRequests[user1] -= claimBasis;
//    assert: sum of recovery payouts > strategy underlying balance,
//    so the last claimant's _transferDefaultRecovery reverts.
```

Key assertions: `strategy.instantWithdrawsRequestsByEpoch(user1, 0) != 0` after the funded claim, and `finalizeDefault` producing a `recoveryPrice` that exceeds `actualReserve * RECOVERY_FULL / totalBasis`.
