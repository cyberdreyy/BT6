### Title
Withdrawal requests revert via underflow when projected fees exceed principal + interest, permanently freezing lender funds - (contracts/IdleCDOEpochVariant.sol)

### Summary
In `IdleCDOEpochVariant.requestWithdraw`, the withdrawal receipt is computed as `principal + interest - totalFees` where `totalFees` is the upfront management fee charged on the **principal** (not just the gain) plus the performance fee on interest. `_totalWithdrawFees` returns the full management fee whenever `_mgmtFee >= _interest`, with no cap against `principal + interest`. When accrued/projected fees exceed the user's claim value, the subtraction underflows and the request reverts — mirroring the reference bug where fees subtracted from a user's balance exceed that balance. Unlike the reference, there is no "decline fees" escape hatch, so the user's funds are frozen rather than merely losing yield.

### Finding Description
`requestWithdraw` in `contracts/IdleCDOEpochVariant.sol` (lines 772–776):

```solidity
uint256 principal = _underlyings;
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
```

`_totalWithdrawFees` (lines 900–906) returns `_mgmtFee` unconditionally when `_mgmtFee >= _interest`:

```solidity
uint256 _mgmtFee = _calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration());
return _mgmtFee >= _interest ?
  _mgmtFee :
  _interest - _netGainAfterFees(_interest, _mgmtFee);
```

The management fee is computed on the full principal over `_withdrawRequestManagementFeeDuration()` = `epochDuration` plus any remaining buffer (lines 925–931). Since fees are charged on principal while interest is only the pro-rata tranche share of epoch yield, `totalFees` can exceed `principal + interest` whenever `managementFee * (epochDuration + remainingBuffer) / 365 days` approaches or exceeds ~100% (e.g., a high management fee rate combined with a long epoch duration, or repeated fee accrual on a low-yield pool — management fee accrues regardless of whether the epoch earns interest, as shown by `testStopEpochCarriesManagementFeesAboveGrossInterest` where accrued fees exceed gross interest).

When `totalFees > principal + interest`, `principal + interest - totalFees` reverts on underflow. Every withdrawal path for that user — partial or full (`_amount == 0`) — reverts, because the fee is proportional to principal. The same underflow exists in the `maxWithdrawable` view (line 913), which subtracts elapsed-time management fee since `latestHarvestBlock` from the user's principal; after enough elapsed time without a checkpoint, even the view reverts.

Note the asymmetry with `stopEpoch`: there, unfundable fees are explicitly capped (`_availableForFees`, lines 451–455) and the remainder stays in `unclaimedFees` — the codebase already recognizes fees can exceed available value, but `requestWithdraw` lacks the equivalent clamp.

### Impact Explanation
Permanent freezing of user funds: a lender holding tranche tokens cannot create a withdrawal receipt at all while the condition holds. The tranche tokens cannot be exited through `requestWithdraw` (the only exit in epoch-based vaults), so principal is locked with no alternative path. Loss magnitude is the user's full deposit value for the duration of the freeze.

### Likelihood Explanation
Requires a management fee configuration where `mgmtFee rate × fee duration ≥ ~principal` relative to interest, i.e., high `managementFee` and/or long `epochDuration + bufferPeriod`, or extended time since the last fee checkpoint. These are honest owner/manager parameters, but nothing in `requestWithdraw` defends against the resulting arithmetic. The condition is deterministic once configured — no attacker action needed; any ordinary lender requesting a withdrawal triggers it. I could not fully verify the upper bound enforced on `managementFee` in `setFeeParams` within the available search context; if the rate is capped well below 100%/yr the window narrows to long-duration epochs.

### Recommendation
Clamp the fee deduction: cap `totalFees` at `principal + interest` (or at `interest` plus a bounded principal carve-out), and carry the unfunded remainder into `pendingWithdrawFees`/`unclaimedFees` the same way `stopEpoch` carries unfundable fees into `unclaimedFees` (lines 451–459). Apply the same saturating subtraction in `maxWithdrawable` for elapsed management fees so the preview matches the executable path.

### Proof of Concept
Foundry fork test sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testRequestWithdrawUnderflowsWhenFeesExceedPrincipalPlusInterest() external {
    uint256 amount = 10_000 * ONE_SCALE;

    // Configure a high management fee (e.g. 50-100% annualized)
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(50_000); // 50% if FULL_ALLOC = 100_000

    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Long epoch so _withdrawRequestManagementFeeDuration() * mgmtFee > principal + interest
    vm.prank(manager);
    cdoEpoch.setEpochParams(365 days * 3, 30 days);

    uint256 trancheAmount = IERC20Detailed(address(AAtranche)).balanceOf(address(this));

    // principal + interest - totalFees underflows -> full and partial requests both revert
    vm.expectRevert();
    cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));

    vm.expectRevert();
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // full-balance path also bricked
}
```

Key assertions: `requestWithdraw` reverts for any amount of the user's balance; `maxWithdrawable` also reverts once `block.timestamp - latestHarvestBlock` is large enough that the elapsed management fee exceeds `currentUnderlyings`. The user retains tranche tokens but has no exit path while the fee configuration stands.
