### Title
Divide-before-multiply precision loss in `jovian_da_footprint()` truncates the Jovian DA-footprint gas estimate - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
`L1FeeParams::jovian_da_footprint()` computes the Jovian DA-footprint gas by dividing the FastLZ-estimated, `1e6`-scaled transaction size by `1_000_000` *before* multiplying by the DA-footprint gas scalar, instead of multiplying first and dividing afterward. This is the exact "divide before multiplication" pattern from the reported Sherlock finding, and it truncates sub-`1e6` (i.e. sub-byte) precision before scaling, systematically underestimating the resulting DA-footprint gas.

### Finding Description
`tx_estimated_size_fjord()` returns the FastLZ-estimated compressed transaction size scaled by `1e6` (a fixed-point representation, not necessarily a multiple of `1e6`): [1](#0-0) 

`jovian_da_footprint()` immediately divides this scaled size by `1_000_000` (`wrapping_div`) and only then multiplies by `da_footprint_gas_scalar`: [2](#0-1) 

Compare this to the sibling function `data_gas()` in the same file, which correctly multiplies before dividing: [3](#0-2) 

and to `calculate_tx_l1_cost_fjord()` / `calculate_l1_fee_scaled_ecotone()`, which also multiply before dividing: [4](#0-3) 

Because `jovian_da_footprint()` divides by `1e6` first, any fractional remainder below one whole "compressed byte" (i.e. `estimated_size % 1_000_000`) is discarded before the scalar multiplication is applied, rather than after. The correct order — `estimated_size * scalar / 1_000_000` — would only lose sub-unit precision in the final gas value; the current order compounds the loss by discarding it before scaling by potentially large scalar values.

### Impact Explanation
The Jovian DA-footprint value feeds directly into transaction-pool admission control. `crates/execution/txpool/src/validator.rs` defines `BaseTxPoolError::DaFootprintExceedsBlockGasLimit`, whose doc comment explicitly describes the DA footprint as `estimated_da_size * da_footprint_gas_scalar`: [5](#0-4) 

The same `jovian_da_footprint` computation is also used in block execution/building paths (`crates/common/evm/src/executor/block_executor.rs`, `crates/execution/payload/src/builder.rs`, `crates/execution/flashblocks/src/state_builder.rs`, `crates/common/evm2/src/executor.rs`) for Jovian-era resource metering. Since the divide-before-multiply order systematically underestimates the DA footprint charged per transaction, the protocol's DA/resource metering under-accounts for the true L1 data-availability cost of transactions, allowing more DA-footprint gas to be packed into a block than the intended Jovian schedule permits.

### Likelihood Explanation
This is deterministic, unconditional code executed for every non-empty, non-scalar-unset transaction once the Jovian upgrade's DA-footprint scalar is configured, and it is reachable purely by submitting ordinary transactions (txpool admission and block building both call it). No privileged role or special conditions are required — any unprivileged transaction sender's transaction is subject to this miscalculation.

### Recommendation
Reorder the computation in `jovian_da_footprint()` to multiply before dividing, matching the pattern already used in `data_gas()` and `calculate_tx_l1_cost_fjord()`:
```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .saturating_mul(scalar)
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_to::<u64>()
}
```
This preserves full precision of `estimated_size * scalar` before scaling down, eliminating the systematic underestimation.

### Proof of Concept
Given `tx_estimated_size_fjord(input) = 100_999_999` (just under 101 "compressed bytes" scaled by `1e6`) and `scalar = 7`:
- Current (buggy) order: `100_999_999 / 1_000_000 = 100`; `100 * 7 = 700`.
- Correct order: `100_999_999 * 7 = 706_999_993`; `706_999_993 / 1_000_000 = 706`.

The buggy computation underestimates the DA-footprint gas by `706 - 700 = 6` units for this single transaction, and the discrepancy scales with `scalar`, understating true DA-footprint gas consistently across every transaction once Jovian's `da_footprint_gas_scalar` is active — mirroring the same class of `_normalizeDecimals`-style precision loss described in the source report.
