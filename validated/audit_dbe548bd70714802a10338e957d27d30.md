## Analysis Result

I found a genuine local analog to the reported bug class: an unprivileged actor can permanently block reward/commission distribution to every other shareholder in a `staking_contract` (and equivalently `vesting`) pool by opting out of direct coin transfers.

### Title
Unprivileged shareholder can permanently block `distribute_internal` for all co-shareholders via `DirectTransferConfig` opt-out - (`aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` iterates over every shareholder in `distribution_pool` in a `while` loop and calls `aptos_account::deposit_coins` for each recipient without any error isolation. [1](#0-0) 
`aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not registered for the coin and has disabled `can_receive_direct_coin_transfers` (via `DirectTransferConfig`, which any account can toggle with `set_allow_direct_coin_transfers`). [2](#0-1) [3](#0-2) 

This is structurally the same bug class as the ERC721 report: an unsafe/uncontrolled external "receive" callback path is invoked in a loop over multiple beneficiaries, and if one recipient rejects the transfer, the whole operation reverts, denying funds to everyone else — the exact DoS risk the report explicitly calls out as a mitigation concern for `safeTransferFrom`.

### Finding Description
`distribute()` (callable by anyone) invokes `distribute_internal`, which loops `while (distribution_pool.shareholders_count() > 0)` and unconditionally calls `aptos_account::deposit_coins(recipient, ...)` for each shareholder, including the operator/beneficiary. [4](#0-3) 
Any shareholder (staker, delegator distribution beneficiary, or operator beneficiary) is free to call `set_allow_direct_coin_transfers(false)` on their own account, an ordinary unprivileged, permissionless action. Once done, if that address is not already registered for `AptosCoin`, any subsequent `deposit_coins` call to it aborts. [5](#0-4) 
Because the `while` loop has no try/catch equivalent (Move has no such construct) and no way to skip/remove a poisoned recipient, the abort propagates and reverts the entire `distribute_internal` transaction — meaning no shareholder, including honest ones, gets paid, and `distribution_pool` state (which was about to be updated via `redeem_shares`) is rolled back entirely.

The exact same pattern exists in `vesting::distribute`, which loops over `shareholders()` and calls `aptos_account::deposit_coins(recipient_address, share_of_coins)` for each one without isolation. [6](#0-5) 

### Impact Explanation
This does not steal funds, but it permanently traps/locks distribution rights: once any single shareholder in a `staking_contract` or `vesting` pool disables direct transfers (and is unregistered for `AptosCoin`), `distribute()` can never succeed again for the entire pool, blocking commission payouts to the operator and rewards to every other staker/delegator/beneficiary indefinitely. Because `unlock_stake`, `switch_operator`, and `terminate_vesting_contract` all call `distribute_internal`/`distribute` internally as a precondition, this also blocks unlocking, operator switching, and vesting contract termination for the whole pool. [7](#0-6) [8](#0-7) 
This matches the "permanent lock or non-recoverable loss of claim rights" impact category, though it is a griefing/DoS vector rather than a value-theft one — closer to the "Low"/"Medium" classification the original report's judges settled on, not obviously Critical/High since (a) it requires a shareholder to intentionally opt out (self-inflicted or coordinated griefing by one malicious co-shareholder), and (b) an already-registered account is immune.

### Likelihood Explanation
Low-to-moderate likelihood: it requires an existing shareholder in a shared `staking_contract`/`vesting` pool to deliberately (or negligently) disable direct transfers and remain unregistered for `AptosCoin`. This is plausible as a griefing attack by any delegator/shareholder against the rest of the pool (self-DoS with no cost beyond one transaction), but the affected structures (`staking_contract`, `vesting`) typically involve few, curated participants (staker + operator, or admin-selected vesting shareholders), reducing the attack surface compared to `delegation_pool`, which supports many permissionless delegators but pays out per-delegator rather than via an all-or-nothing loop (delegation_pool credits via internal `pool_u64` shares, not a `deposit_coins` push in a loop, so it is not vulnerable to this specific pattern).

### Recommendation
Isolate failures per-recipient in `distribute_internal` (`staking_contract.move`) and `distribute` (`vesting.move`): e.g., check `coin::is_account_registered` / `can_receive_direct_coin_transfers` before pushing funds, and if a recipient cannot receive, hold their share in an escrow/pending-withdrawal state (pull-based) instead of aborting the whole batch, so honest shareholders are not held hostage by one non-compliant recipient.

### Proof of Concept
1. Staker creates a `staking_contract` with operator O; both staker and O accrue rewards in the shared `distribution_pool`.
2. Operator O calls `aptos_account::set_allow_direct_coin_transfers(false)` on the address used as `beneficiary_for_operator` (an ordinary unprivileged action), while that beneficiary address remains unregistered for `AptosCoin`.
3. Rewards accrue; anyone calls `staking_contract::distribute(staker, operator)` (or it's triggered internally via `unlock_stake`/`switch_operator`).
4. Inside `distribute_internal`'s loop, when it reaches the operator's beneficiary as `recipient`, `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. [9](#0-8) 
5. The entire transaction reverts — the staker also does not receive their share, and this recurs on every future call to `distribute`, `unlock_stake`, or `switch_operator` for this pool until the operator (attacker) re-enables direct transfers or registers the coin, giving the attacker unilateral control over whether the pool's distribution/unlock functionality works.

**Uncertainty note:** I was unable to fully verify the middle portion of `aptos_account.move`'s `deposit_coins`/`can_receive_direct_coin_transfers` implementation (lines ~61–120) due to index truncation of blank/formatting lines; the behavior is inferred from the surrounding code (lines 20-42, 121-130) and is consistent with documented Aptos framework semantics, but a full read of the file via a Devin session would be needed to confirm there is no additional guard (e.g., special-casing for the staking/vesting resource-account signer) that mitigates this path.
