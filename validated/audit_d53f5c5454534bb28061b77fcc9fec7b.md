### Title
Unauthenticated `/v2/resume/:runID` endpoint allows any unprivileged client to write task results into production pipeline runs - (File: core/web/pipeline_runs_controller.go)

### Summary
The EL-2021-09 report describes a class of bug where a "publicly accessible token" was sufficient to modify sensitive production resources without proper authorization. In chainlink, the `Resume` endpoint on pipeline runs is deliberately mounted on the unauthenticated router group and is guarded only by a UUID `runID` (task ID) rather than any session, API-key, or role check, allowing any unprivileged network client that can guess or obtain a run's task UUID to write results into that pipeline run.

### Finding Description
The v2 router explicitly separates an unauthenticated group from the authenticated one, and mounts `Resume` outside of the `auth.Authenticate(...)` middleware chain used for the rest of `/v2`: [1](#0-0) 

The handler itself performs no authentication or authorization check — it only parses the `runID` path parameter as a UUID and decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, then calls `App.ResumeJobV2` to inject that result into the running pipeline: [2](#0-1) 

The only "credential" gating write access is the run's UUID (`taskID`), which functions like a bearer token: anyone in possession of it — whether via logs, external systems, network capture, or brute-force guessing given a 128-bit UUID — can resume/modify the run outcome (the exact analog to the Sourcify issue, where possession of a token was sufficient to modify production resources without further authorization). The audit log entry itself is even tagged `audit.UnauthedRunResumed`, confirming this is a known-unauthenticated code path: [3](#0-2) 

By contrast, every other route that can mutate node state (bridges, external initiators, config, transfers) is wrapped in `auth.Authenticate` plus a role check (`RequiresEditRole`, `RequiresAdminRole`, `RequiresRunRole`): [4](#0-3) [5](#0-4) 

`Resume` is the sole state-mutating write path deliberately left open, relying entirely on UUID secrecy as its authorization boundary.

### Impact Explanation
If a run's UUID is disclosed by any means (log aggregation systems, monitoring dashboards, external adapter callbacks, browser history, proxy logs, or a predictable/guessable generation scheme), an unprivileged network client can supply arbitrary task results to resume/complete that pipeline run — effectively forging the outcome of an in-flight job task without any authentication. Because `ResumeJobV2` feeds directly into job pipeline execution, this can influence downstream actions the job takes (e.g., writing wrong values, forcing job completion/failure, or causing follow-on transactions based on attacker-controlled result data), directly matching the "unauthorized job run" impact category.

### Likelihood Explanation
Exploitation requires that an attacker learn a specific run's UUID. This is more constrained than a fully open endpoint, but UUIDs of this kind are frequently exposed through client callbacks (this is the entire purpose of the endpoint — external bridges/adapters call it back with results), logging, and network intermediaries, and the endpoint design intentionally trusts the UUID alone as the authorization mechanism, mirroring exactly the "publicly accessible token" bug class from the external report.

### Recommendation
- Treat the `runID` used by `/v2/resume/:runID` as a genuine bearer credential: generate it with sufficient entropy, avoid logging/echoing it in server logs or client-visible audit fields, and consider binding it to a single-use, time-limited token rather than the run's primary UUID.
- Where feasible, require an additional shared secret (e.g., a per-run resume token issued alongside the run) instead of relying solely on the UUID.
- Ensure the endpoint's audit logging and any external-facing metrics/logs do not leak the `runID`/task UUID to parties other than the intended callback recipient.

### Proof of Concept
1. Identify or intercept a task UUID for a pending pipeline run using `resumeAfterTask` (commonly exposed to external adapters/bridges as part of the async callback flow).
2. As an unauthenticated client, send:
```
PATCH /v2/resume/<taskID> HTTP/1.1
Content-Type: application/json

{"error": null, "value": "<attacker-controlled-value>"}
```
3. `PipelineRunsController.Resume` (core/web/pipeline_runs_controller.go:133-159) accepts the request without any session/API-key/role check, decodes the body, and calls `App.ResumeJobV2`, injecting the attacker-supplied result into the job pipeline.

```go
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
```

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
