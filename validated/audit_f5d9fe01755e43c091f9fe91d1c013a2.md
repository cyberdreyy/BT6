### Title
Global block-rejection table keyed only by `signer_addr` lets a later rejection silently erase an earlier block's rejection record - ([File: stacks-signer/src/signerdb.rs])

### Summary
`block_rejection_signer_addrs`, the table `add_block_rejection_signer_addr` writes to, is created with `PRIMARY KEY (signer_addr)` only, i.e. one row per signer address for the *entire database*, not per `(signer_signature_hash, signer_addr)`. The comment above the table even says the sighash alone should be sufficient to identify state, implying the schema's intent was a composite scope, but the declared primary key does not include `signer_signature_hash`. This is the same class of bug as the reported `periodsPaid`/`exists` offset collision: a storage key that omits a distinguishing field causes state for one logical record (rejection of block A by signer X) to be overwritten by an unrelated record (rejection of block B by the same signer X). [1](#0-0) 

### Finding Description
The table is declared as:
```
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    PRIMARY KEY (signer_addr)
) STRICT;
``` [1](#0-0) 

Meanwhile, the write/query logic (`add_block_rejection_signer_addr`) is written as if the row is scoped per `(signer_signature_hash, signer_addr)`: it selects `reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2`, and on a miss it does a plain `INSERT`, not an `INSERT OR REPLACE`: [2](#0-1) 

Because the actual primary key is `signer_addr` alone, once a signer address has any row in the table (from rejecting block A), a subsequent `INSERT` for that same signer rejecting a *different* block B will violate the primary key and fail (or, if the caller silently swallows/logs the error, the second block's rejection is effectively dropped) — this is the same root-cause shape as the "wrong offset" issue: because the key does not include the block-identifying field, records for different blocks collide on the same storage slot.

This directly touches the vote-tally equality the prompt cares about: `store_and_process_block_rejection` reads `get_block_rejection_signer_addrs(block_hash)` to compute `total_reject_weight` and decide whether the 70%/30% blocking-minority threshold has been crossed: [3](#0-2) 

If a signer's rejection for the currently-evaluated block never gets durably recorded (because the same signer previously rejected a different block and now collides on the single-address-keyed row), that signer's weight is dropped from the rejection tally for the new block. In a chain where a signer flips its vote across sequential proposals at the same height (e.g., during a proposal-refresh/reorg-permit cycle that this codebase explicitly handles via `should_reevaluate_reject_reason`), the same signer address rejecting two different candidate blocks in sequence hits this collision, and the second rejection can fail to persist/tally — the rejection count is silently undercounted relative to what was actually voted, i.e., a rejection is effectively dropped from the tally rather than a rejection being recounted as an acceptance in the strict sense, but it produces the same "aggregated-weight vs verified-accepts/rejects" mismatch the analysis targets.

### Impact Explanation
This is a "rejection miscounted" class issue: it can prevent a block from being correctly marked `GloballyRejected` even though a threshold-crossing set of rejections was actually sent, because a legitimate signer's rejection silently fails to be recorded due to a primary-key collision with an earlier, unrelated block's rejection row from the same signer. That undermines the >30% blocking-minority guarantee described in the flow docs (section 6, `handle_block_rejection`/`store_and_process_block_rejection`), which is exactly the equality ("aggregated-weight vs verified-accepts/rejects") the prompt is scoped to protect. Depending on how the resulting DB error is handled by the caller (`warn!` and continue, per the code at signerdb.rs:1934-1939 for the signature-exists case, and unknown handling for a raw INSERT failure at 1973-1976), this could also become a liveness wedge (repeated panics if `.unwrap()` is used on insert failure elsewhere) or, more likely, a silent undercount of rejections, delaying/blocking the blocking-minority threshold from being reached.

### Likelihood Explanation
Reaching this requires only a single already-participating signer (any one signer, not a majority) to reject two different block proposals at the same or later point in time — a completely normal occurrence given the "early votes"/re-proposal flow already documented in this repo (`should_reevaluate_reject_reason`, `check_block_against_signer_db_state` re-checks, and reorg-permit flows that can flip a rejection between competing block candidates). No malicious majority collusion or privileged access is needed; a single miner offering two competing proposals at a height is enough to make one honest signer reject both in sequence.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)` (matching the intent already encoded in the query logic and in `block_signatures`' equivalent scoping), and add a migration to correct any existing single-column-keyed table. Add explicit error handling/insert-or-replace logic scoped by the composite key so that a rejection for one block never silently displaces or fails against a rejection recorded for a different block by the same signer.

### Proof of Concept
1. Deploy the signer against two competing block proposals A and B at the same Stacks height (e.g., via a byzantine/duplicate miner scenario already exercised in `stacks-node/src/tests/signer/v0/reorg.rs`).
2. Have signer X call `add_block_rejection_signer_addr(block_A_hash, X, reason1)` — this inserts row `(signer_addr = X)` successfully.
3. Have signer X later call `add_block_rejection_signer_addr(block_B_hash, X, reason2)` for the competing/re-proposed block B. Because the table's primary key is `signer_addr` alone, this second `INSERT` collides with the first row and fails the `PRIMARY KEY` constraint (STRICT table), or if wrapped with ON CONFLICT semantics elsewhere, silently overwrites/loses block A's rejection row.
4. Observe via `get_block_rejection_signer_addrs(block_B_hash)` that signer X's rejection of block B is missing/errored, undercounting the rejection weight used in `store_and_process_block_rejection`'s threshold check.

Note: I was unable to fully confirm whether a later schema migration (not found via search in `signerdb.rs`) subsequently redefines this table with a composite primary key before it reaches production use; the code I found for both the `CREATE TABLE` statement and the read/write logic are consistent with the vulnerable single-column-PK schema as described above.
