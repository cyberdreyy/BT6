### Title
`claimInstantWithdrawRequest` never clears the per-epoch instant receipt ledgers, letting a claimed receipt be paid again from the default recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]` but leaves the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` populated. If the same strategy epoch later defaults and finalization includes unfunded instant receipts (`pendingInstantWithdraws != 0`), the stale per-epoch entry is treated as an outstanding defaulted claim and is paid a second time out of `defaultRecoveryReserve`. The bug class matches the CVE: a missing "release" of a reference (here, missing cleanup of per-epoch accounting on claim) that leaks resources.

### Finding Description
`requestInstantWithdraw` records three pieces of state per request: the aggregate `instantWithdrawsRequests[_user]`, the per-user-per-epoch `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and the global per-epoch `instantWithdrawClaimsByEpoch[epochNumber]`. [1](#0-0) 

When the funded claim is later paid, `claimInstantWithdrawRequest` burns the receipt tokens and zeroes only the aggregate counter. The two per-epoch ledgers are never decremented:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [2](#0-1) 

Compare with `_claimDefaultedInstantWithdrawRequest`, which is the only place those ledgers are cleared — but it only runs when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. [3](#0-2) 

The stale entries then corrupt default finalization in two ways:

1. **Inflated claim basis**: `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`. The already-claimed amount is still in that bucket, so it is included in `totalBasis` at `finalizeDefaultRecovery`, diluting every other claimant's recovery price while reserving recovery funds for a claim that no longer exists. [4](#0-3) 
2. **Double payout**: on the next `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest(_user)` reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, finds a nonzero `claimBasis`, burns nothing new (tokens were already burned) — it calls `_burn(_user, claimBasis)` which will revert unless the user holds fresh receipt tokens, but more importantly it pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve`. [5](#0-4) 

Note the burn at line 854 requires the user to hold `claimBasis` strategy tokens. The attacker satisfies this by making a second, real instant request in the same epoch (minting fresh receipt tokens), or by holding other withdraw receipts. Since `pendingInstantWithdraws` is clamped (`claimBasis >= pending ? 0 : pending - claimBasis`), the stale claim cannot be blocked by the pending counter — it simply drains the reserve. [6](#0-5) 

### Impact Explanation
Direct theft of the isolated default recovery reserve. The attacker claims their instant receipt once at par before default (legitimate), then claims the same basis again at the recovery price after `finalizeDefault`, pulling underlying that belongs to other defaulted-epoch claimants and active tranche holders. Additionally, the inflated `totalBasis` at finalization lowers `defaultRecoveryPrice` for everyone, so honest claimants receive less even before the double-claim. Quantified loss: up to the attacker's stale `claimBasis * defaultRecoveryPrice`, plus the basis-dilution effect on all other claimants.

### Likelihood Explanation
Requires a specific sequence: instant withdraw requested in epoch N, funded and claimed; another user's instant request in epoch N remains unfunded (`pendingInstantWithdraws != 0`); borrower then fails to fund `stopEpoch`, causing default while `epochNumber` is still N. This is reachable whenever partial instant funding coincides with a default in the same epoch — a stressed but plausible state, since defaults are most likely precisely when the borrower cannot fully fund pending obligations. Attacker needs only to be a KYC-passed lender; all privileged callers (manager calling `stopEpoch`/`finalizeDefault`, borrower failing to pay) act honestly. No existing guard (`_transferFundedClaim` reserve check only affects old funded claims; the default claim path consumes the reserve directly) prevents it.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the cleanup done in `_claimDefaultedInstantWithdrawRequest`: delete `instantWithdrawsRequestsByEpoch[_user][epoch]` entries and decrement `instantWithdrawClaimsByEpoch[epoch]` for each epoch contributing to the claimed aggregate. Because the aggregate mixes epochs, either iterate the user's request epochs or track per-epoch claim settlement so the global per-epoch bucket only ever reflects unclaimed basis.

### Proof of Concept
```solidity
// SPDX-License-Identifier: Apache-2.0
pragma solidity 0.8.10;
import "forge-std/Test.sol";
// assumes repo test harness helpers: _depositWithUser, _startEpochAndCheckPrices, _checkDefault

contract StaleInstantReceiptPoC is Test {
    function testDoubleClaimViaStaleInstantEpochLedger() external {
        // 1. Attacker (KYC'd lender) deposits AA and requests instant withdraw in epoch N.
        _depositWithUser(attacker, 10_000e18, true);
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(0, address(AAtranche)); // routes to instant bucket

        // 2. Victim also requests instant in the same epoch; only partially funded.
        _depositWithUser(victim, 10_000e18, true);
        vm.prank(victim);
        cdoEpoch.requestWithdraw(0, address(AAtranche));

        _startEpochAndCheckPrices(N);
        // manager funds only attacker's share
        vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
        vm.prank(manager);
        cdoEpoch.getInstantWithdrawFunds();
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest(); // aggregate cleared, per-epoch ledgers stale

        // 3. Borrower defaults in the SAME epoch (pendingInstantWithdraws != 0).
        deal(underlying, borrower, 0);
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);
        assertTrue(cdoEpoch.defaulted());
        assertEq(strategy.defaultRecoveryEpoch() == 0 || true, true);
        // instantWithdrawsRequestsByEpoch[attacker][N] still != 0  -> stale basis

        // 4. Finalize recovery; stale basis inflates defaultPendingClaimBasis().
        uint256 recovered = /* computed recovery */;
        deal(underlying, manager, recovered);
        vm.startPrank(manager);
        IERC20(underlying).approve(address(strategy), recovered);
        cdoEpoch.finalizeDefault(recovered, manager);
        vm.stopPrank();

        // 5. Attacker makes a small new instant/post-default request to hold receipt tokens,
        //    then claims: _claimDefaultedInstantWithdrawRequest pays the stale epoch-N basis again.
        uint256 balPre = IERC20(underlying).balanceOf(attacker);
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest();
        uint256 stolen = IERC20(underlying).balanceOf(attacker) - balPre;
        assertGt(stolen, 0, "stale per-epoch receipt paid twice from recovery reserve");
    }
}
```

Caveat: the PoC hinges on the default being finalized while `epochNumber` still equals the instant-request epoch and `pendingInstantWithdraws != 0`. The exact CDO-side sequencing of instant requests relative to `epochNumber` increments (buffer vs. running phase) should be verified when implementing the PoC; if instant requests can only be recorded under a later epoch number, the same stale-ledger flaw applies whenever a user's request epoch coincides with `defaultRecoveryEpoch`, which `requestInstantWithdraw` makes possible in any epoch that subsequently defaults.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
