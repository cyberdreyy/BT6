### Title
Multi-epoch pending withdraw receipts bypass the loss haircut via single-epoch `lastWithdrawRequest` pointer - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes an attacker bypassing Starlette's path normalization (`%2E%2E`/`%2F`) so a single normalized path escapes the intended directory scope. `IdleCreditVault` has the same shape: pending withdraw receipts are an aggregate, multi-epoch bucket (`pendingWithdraws`), but both the loss-recovery guard in `requestWithdraw` and the loss-adjusted claim path normalize a user's entire position to **one** epoch via `lastWithdrawRequest[_user]`. When the borrower underfunds `collectWithdrawFunds` twice across two epochs, receipts recorded in the earlier epoch escape the stored `lossRecoveryPriceByEpoch` haircut and are paid at par from an underfunded reserve, breaking solvency for remaining claimants.

### Finding Description
`collectWithdrawFunds` applies a partial funding as a loss: it sets `pendingWithdraws = 0` and stores the recovery price under a **single** key, `lossRecoveryPriceByEpoch[epochNumber]` [1](#0-0) . If instead the funding is partial-but-above... no — the escape comes from the `else` branch: when `_amount >= pendingBasis` is false the loss path runs, but when the borrower simply underfunds without invoking the loss branch, `pendingWithdraws = pendingBasis - _amount` leaves an **untracked unfunded remainder** that rolls into the next epoch's `pendingBasis` with no per-epoch haircut attached [2](#0-1) .

The protection against stacking a new request on top of a loss-adjusted receipt checks only `lossEpoch = lastWithdrawRequest[_user]` [3](#0-2) . A user whose unfunded receipt from epoch A rolls forward can freely open a new request in epoch B (guard passes because `lossRecoveryPriceByEpoch[A] == 0`), which overwrites `lastWithdrawRequest[_user] = B` [4](#0-3) .

When the next `stopEpochWithDuration`-style underfunding hits, the aggregate `pendingBasis` (epoch-A remainder + epoch-B receipts) is haircut and `lossRecoveryPriceByEpoch[B]` is set. On claim, `_claimLossAdjustedWithdrawRequest` haircuts only the receipts keyed to `lastWithdrawRequest == B` [5](#0-4) , then `_claimFundedWithdrawRequest` pays the remaining `withdrawsRequests[_user]` — including the epoch-A remainder that was inside the haircut basis — **at par** [6](#0-5) .

### Impact Explanation
Broken invariant: "one receipt, one (loss-adjusted) payout" and solvency of the funded reserve. The strategy only received `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` from the borrower for the whole pending bucket, but users whose receipts span two epochs withdraw `basis_A * 1.0 + basis_B * price`. First-come claimants drain the strategy's underlying reserve; later pending redeemers' `_transferFundedClaim` calls revert on insufficient balance — direct theft of other users' funded withdraw proceeds and temporary/permanent freezing of their claims until the borrower tops up. The attacker is any ordinary KYC'd tranche holder; no privileged action is required — the sequencing only needs two consecutive underfunded epochs, which the honest borrower/manager produce during a partial-repayment or loss event.

### Likelihood Explanation
Requires: (1) a withdraw request left unfunded across a stopEpoch (borrower underfunding via the non-loss `else` branch), (2) a second request in the following epoch, (3) a subsequent loss-adjusted stopEpoch. All steps use honest privileged calls in their normal order; the window is real whenever the borrower repays partially. The bug is deterministic once state is reached — every multi-epoch claimant over-withdraws.

### Recommendation
Track pending basis per epoch (e.g., `pendingWithdrawsByEpoch`) or store the loss recovery price against every epoch that contributes to the underfunded `pendingBasis`. In `_claimFundedWithdrawRequest`, do not pay `withdrawsRequests[_user]` at par while any contributing epoch has a non-zero `lossRecoveryPriceByEpoch`; alternatively block new `requestWithdraw`s whenever the user has any receipt in an epoch that was underfunded, not only when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`.

### Proof of Concept
Foundry fork PoC sketch (mainnet fork as in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. Epoch N (running): attacker deposits AA, calls cdoEpoch.requestWithdraw(amt, AATranche)
//    -> withdrawsRequestsByEpoch[attacker][N] = amt; pendingWithdraws += amt
// 2. Honest manager stopEpoch; borrower underfunds via the else-branch path
//    (collectWithdrawFunds funded < pendingBasis but pendingWithdraws left > 0 remainder)
//    -> attacker's epoch-N receipt remains pending, lossRecoveryPriceByEpoch[N] == 0
// 3. Epoch N+1 buffer: attacker calls requestWithdraw again
//    -> guard at IdleCreditVault.sol:261-271 passes (lossRecoveryPriceByEpoch[N]==0)
//    -> lastWithdrawRequest[attacker] = N+1; pendingWithdraws includes epoch-N remainder
// 4. Epoch N+1 running -> honest stopEpochWithDuration(_lossAmount>0):
//    previewLossAdjustedWithdrawFunds computes pendingToFund < pendingBasis;
//    collectWithdrawFunds(pendingToFund) sets pendingWithdraws=0 and
//    lossRecoveryPriceByEpoch[N+1] = price < RECOVERY_FULL.
// 5. Attacker calls cdoEpoch.claimWithdrawRequest():
//    - _claimLossAdjustedWithdrawRequest haircuts only withdrawsRequestsByEpoch[N+1]
//    - _claimFundedWithdrawRequest pays withdrawsRequests[attacker] remainder
//      (epoch-N basis) at par.
//    Assert: attackerReceived > (amt_N + amt_{N+1}) * price / FULL;
//    Assert: strategy underlying balance < sum of remaining users' claimBasis * price,
//    i.e., a subsequent honest user's claimWithdrawRequest() reverts (insolvency).
```

Uncertainty: exact `epochNumber` increment timing relative to `collectWithdrawFunds` inside `stopEpoch` should be confirmed when writing the PoC (it is bumped in `deposit()` during stop), but the core defect — aggregate `pendingBasis` haircut keyed to a single epoch while per-user payout spans multiple epochs at par — is independent of that detail.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".

      // successful stop can fully fund the aggregate before lazy initialization occurs.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
