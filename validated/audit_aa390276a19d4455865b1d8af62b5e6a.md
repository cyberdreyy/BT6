### Title
Multisig executes requests using stale confirmations from access keys already revoked via `DeleteKey`, allowing execution below the effective live-member threshold - (File: multisig/src/lib.rs)

### Summary
The `MultiSigContract::confirm` flow counts confirmations stored in `self.confirmations` to decide when `num_confirmations` has been reached and a request should execute [1](#0-0) . When a key is revoked through the `DeleteKey` request action, the contract only purges requests and confirmations for requests *created* (signed) by that key, but never removes that key's public key from the `confirmations` sets of *other* pending requests it had merely confirmed [2](#0-1) . As a result, a stale confirmation from a now-revoked key remains counted toward the threshold for unrelated pending requests, allowing those requests (including `Transfer` actions moving NEAR) to execute with fewer *live* confirming members than the configured `num_confirmations`.

### Finding Description
The multisig's core custody guarantee is the equality: *number of confirmations from currently valid/live keys ≥ `num_confirmations`* before any request (e.g., a `Transfer`) is executed. `confirm()` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` [3](#0-2) , where `confirmations` is a persisted `HashSet<PublicKey>` per request, populated at line 262.

When `DeleteKey` is executed to revoke a compromised or departing key, the contract's cleanup logic is:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter(|(_k, r)| r.signer_pk == pk)
    .map(|(k, _r)| k).collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
self.num_requests_pk.remove(&pk);
``` [4](#0-3) 

This filter only matches requests whose *creator* (`signer_pk`) equals the deleted key. It never iterates `self.confirmations` to strip the revoked `pk` from the confirmation sets of requests created by *other* keys that the revoked key had previously confirmed. Those confirmation entries persist in storage untouched.

Consequently: if key `K` confirmed request `R` (created by a different key), and `K` is later revoked via a separate `DeleteKey { public_key: K }` request executed against the same multisig account, `R`'s stored confirmation set still contains `K`. When the remaining live keys confirm `R` up to `num_confirmations - 1` (with `K`'s stale confirmation making up the difference), `execute_request` fires the `Transfer`/`FunctionCall`/`AddKey` actions in `R` using a confirmation count that includes a party no longer entitled to authorize anything on the account.

### Impact Explanation
This breaks the binding "confirmations counted versus live members": the multisig contract will authorize and execute a `Transfer` of NEAR (or other privileged actions such as `AddKey`, `DeployContract`) with fewer than `num_confirmations` currently-valid confirmers, i.e. a multisig request executed below its intended threshold. Per the stated impact criteria this is Critical — NEAR moved (or account control granted) by a party (the stale, revoked key) not entitled to it, and a multisig request executed below its live threshold.

### Likelihood Explanation
This does not require any privileged access beyond normal multisig operation: any key holder that confirms a pending request and is subsequently removed from the multisig (a routine key-rotation/off-boarding operation any deployment will perform) leaves an exploitable stale confirmation. No malicious validator, redeploy, or foundation action is needed — the flaw is triggered purely by the documented `DeleteKey` request action combined with ordinary pending-request confirmation, both of which are core, intended multisig operations.

### Recommendation
When executing `DeleteKey`, iterate over all outstanding requests (not just those created/signed by the deleted key) and remove the deleted public key from every request's `confirmations` set. Alternatively, validate at `confirm`-threshold-check time (or lazily, at execution time) that every public key present in a request's `confirmations` set is still a currently authorized access key/multisig member before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(3)` with keys `A`, `B`, `C` (3-of-3, or generalize to k-of-n).
2. Key `A` calls `add_request_and_confirm(request_transfer)` creating request `R1` (a `Transfer`), confirmations = `{A}`.
3. Key `B` calls `confirm(R1)`, confirmations = `{A, B}` (below threshold 3, so `R1` stays pending) [1](#0-0) .
4. Separately, key `A` (or any signer) creates and gets confirmed a `DeleteKey { public_key: B }` request `R2` which executes, revoking `B`'s access key. During execution, the cleanup only removes requests where `r.signer_pk == B`; since `B` did not create `R1`, `R1`'s confirmation set `{A, B}` is left untouched [2](#0-1) .
5. Key `A` alone now calls `confirm(R1)` again is not needed — the account only needs one more *live* confirmation. If threshold were e.g. `num_confirmations = 2` and `B` was the second confirmer already counted at step 3, `R1` would have already executed at step 3 even though `B`'s key is later revoked retroactively-irrelevant; but for a 3-of-3 case, only key `C` (a still-valid key) needs to call `confirm(R1)`. `confirmations.len() (2, including stale B) + 1 (C) = 3 >= num_confirmations(3)`, so `execute_request` fires the `Transfer`, moving funds with only `A` and `C` being genuinely live/authorized confirmers while `B`'s revoked-but-stale confirmation made up the count.

This demonstrates a `Transfer` (NEAR movement) authorized and executed using a confirmation from a key that no longer holds any authority on the account — a concrete violation of the multisig's live-threshold custody guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
