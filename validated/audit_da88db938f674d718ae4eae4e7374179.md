Based on my investigation, I found a genuine analog in the `CostPacer::scheduling_budget` mechanism in the banking stage scheduler, which exhibits the same class of flaw as the reported bug: a rate/allocation calculation derived from elapsed wall-clock time since a reference point, with no bound-check or staleness detection if that time delta becomes abnormally large (e.g., due to a stall, GC pause, thread scheduling delay, or clock anomaly).

### Title
Unbounded elapsed-time-based cost pacing allows compute budget over-allocation on scheduler stalls - (File: core/src/banking_stage/transaction_scheduler/scheduler_controller.rs)

### Summary
The `CostPacer::scheduling_budget` function [1](#0-0)  computes an allowed compute-unit allocation for the current leader slot by linearly interpolating `block_limit` over a configured `fill_time` window based on `current_time.saturating_duration_since(self.detection_time)`. Like the reported oracle bug — which trusted elapsed observation data without validating that the elapsed interval was reasonable — this function has no check on whether `time_since` is anomalously large due to thread scheduling delays, GC pauses, lock contention, or other transient host-level stalls in the `SchedulerController::run` loop [2](#0-1) .

### Finding Description
`cost_pacer` is (re)initialized once per detected new leader slot with `detection_time: now` [3](#0-2) . On every loop iteration thereafter, `process_transactions` calls `cost_pacer.scheduling_budget(now)` to determine how many compute units may currently be scheduled [4](#0-3) . If `time_since >= fill_time`, the function immediately returns the *entire* `block_limit` regardless of how much cost has already been scheduled elsewhere in the slot's actual wall-clock budget, and regardless of whether the large `time_since` value resulted from real elapsed slot time or from an anomalous stall in the scheduler thread (e.g. resource contention, OS scheduling jitter, or a burst of expensive housekeeping work such as `incremental_recheck` or `clean_time_us`). This mirrors the oracle bug's root cause: a value (block_limit / TWAP) that is fine under normal operating assumptions becomes wrong when the assumption of "time passed corresponds to real progress" breaks down, and the code has no explicit staleness/anomaly check comparable to the "refuse to return a sample" precedent noted in the original report.

### Impact Explanation
If the pacer's `detection_time` significantly lags behind actual elapsed processing due to a stall, `scheduling_budget` will unlock the full remaining `block_limit` all at once rather than the intended gradual/paced allocation, allowing the scheduler to admit a burst of transactions that consume the entire block's compute budget in a compressed window. This does not by itself break the hard `block_cost` limit enforced by `CostTracker::try_add` [5](#0-4) , so the impact is confined to defeating the intended smoothing/pacing behavior (potential burstiness/fairness degradation for transaction admission) rather than a hard consensus or fund-safety violation.

### Likelihood Explanation
Requires the leader's banking-stage scheduler thread to experience a stall or delay comparable to or exceeding `fill_time` (a config value, `DEFAULT_SCHEDULER_PACING_NON_FILL_TIME_MILLIS`-scaled) within a single leader slot window, which is a plausible but narrow operational condition rather than an easily attacker-triggerable one from ordinary transaction/RPC/QUIC input alone.

### Recommendation
Add a sanity bound/staleness check on `time_since` in `CostPacer::scheduling_budget` — e.g., cap the assumed elapsed time to the slot duration, or detect and log/report when `time_since` exceeds an expected maximum, rather than unconditionally granting the full `block_limit` once `fill_time` is exceeded.

### Proof of Concept
1. Leader slot begins; `cost_pacer` set with `detection_time = now`, `block_limit`, `fill_time = Some(t)` [6](#0-5) .
2. The `run()` loop stalls (e.g., due to `incremental_recheck`, GC, contention) for a duration `>= t` before the next `process_transactions` call.
3. `scheduling_budget(now)` computes `time_since >= fill_time` and returns `block_limit - shared_block_cost.load()`, i.e., the entire remaining budget, in a single call, instead of the intended linear ramp [7](#0-6) .

        let mut most_recent_leader_slot = None;
        let mut cost_pacer = None;

        while !self.exit.load(Ordering::Relaxed) {
            let now = Instant::now();
            // BufferedPacketsDecision is shared with legacy BankingStage, which will forward
            // packets. Initially, not renaming these decision variants but the actions taken
            // are different, since new BankingStage will not forward packets.
            // For `Forward` and `ForwardAndHold`, we want to receive packets but will not
            // forward them to the next leader. In this case, `ForwardAndHold` is
            // indistinguishable from `Hold`.
            //
            // `Forward` will drop packets from the buffer instead of forwarding.
            // During receiving, since packets would be dropped from buffer anyway, we can
            // bypass sanitization and buffering and immediately drop the packets.
            let (decision, decision_time_us) =
                measure_us!(self.decision_maker.make_consume_or_forward_decision());
            self.timing_metrics.update(|timing_metrics| {
                timing_metrics.decision_time_us += decision_time_us;
            });
            let new_leader_slot = decision.bank().map(|b| b.slot());
            self.count_metrics
                .maybe_report_and_reset_slot(new_leader_slot);
            self.timing_metrics
                .maybe_report_and_reset_slot(new_leader_slot);

            if most_recent_leader_slot != new_leader_slot {
                self.container.flush_held_transactions();
                most_recent_leader_slot = new_leader_slot;
                cost_pacer = decision.bank().map(|b| {
                    let cost_tracker = b.read_cost_tracker().unwrap();
                    let block_limit = cost_tracker.get_block_limit();
                    let shared_block_cost = cost_tracker.shared_block_cost();
                    drop(cost_tracker);

                    // If pacing_fill_time is greater than the bank's slot time,
                    // adjust the pacing_fill_time to be the slot time, and warn.
                    let fill_time = self.config.scheduler_pacing.fill_time();
                    if let Some(pacing_fill_time) = fill_time.as_ref()
                        && pacing_fill_time.as_nanos() > b.ns_per_slot
                    {
                        warn!(
                            "scheduler pacing config pacing_fill_time {:?} is greater than the \
                             bank's slot time {}, setting to slot time",
                            pacing_fill_time, b.ns_per_slot,
                        );
                        self.config.scheduler_pacing = SchedulerPacing::FillTimeMillis(
                            NonZeroU64::new(
                                (b.ns_per_slot as u64 / 1_000_000)
                                    .saturating_sub(DEFAULT_SCHEDULER_PACING_NON_FILL_TIME_MILLIS),
                            )
                            .unwrap_or(NonZeroU64::new(1).unwrap()),
                        );
                    }

                    CostPacer {
                        block_limit,
                        shared_block_cost,
                        detection_time: now,
                        fill_time,
                    }
                });

impl CostPacer {
    fn scheduling_budget(&self, current_time: &Instant) -> u64 {
        let target = if let Some(fill_time) = &self.fill_time {
            let time_since = current_time.saturating_duration_since(self.detection_time);
            if time_since >= *fill_time {
                self.block_limit
            } else {
                // on millisecond granularity, pace the cost linearly.
                let allocation_per_milli = self.block_limit / fill_time.as_millis() as u64;
                let millis_since_detection = time_since.as_millis() as u64;
                allocation_per_milli * millis_since_detection
            }
        } else {
            self.block_limit
        };

        target.saturating_sub(self.shared_block_cost.load())
    }
}
