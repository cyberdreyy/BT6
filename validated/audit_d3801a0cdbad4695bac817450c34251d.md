### Title
Non-atomic `declare_work()` + `channel.send()` in `TransactionStatusSender::send_transaction_status_batch` lets concurrent banking-stage workers violate the `DependencyTracker` ordering invariant, causing premature `mark_this_and_all_previous_work_processed` and stale Blockstore reads via RPC - (File: runtime/src/transaction_execution.rs)

### Summary
`TransactionStatusSender::send_transaction_status_batch` calls `DependencyTracker::declare_work()` and then `crossbeam_channel::Sender::send()` as two separate, non-atomic steps. Because multiple `ConsumeWorker`/vote-worker threads share the same `TransactionStatusSender` clone (and thus the same `Arc<DependencyTracker>` and channel), a thread that reserves a lower `work_id` can be preempted between `declare_work()` and `send()`, allowing a thread with a higher `work_id` to send first. `TransactionStatusService` processes messages strictly in channel-arrival order and calls `mark_this_and_all_previous_work_processed(work_id)` after writing each batch, so it can mark a higher work id "done" before the lower-numbered batch has even been enqueued, breaking the documented invariant that "notifying id `s` implies all ids < `s` are processed."

### Finding Description
`DependencyTracker::declare_work` hands out monotonically increasing ids via an atomic `fetch_add` [1](#0-0) , and `mark_this_and_all_previous_work_processed`/`wait_for_dependency` rely on the contract that "notify a work of id number 's' will implicitly imply that all work with id number less than 's' have been processed" [2](#0-1) .

That contract is only true if the order in which ids are *declared* matches the order in which the corresponding messages are *sent* into the channel. `TransactionStatusSender::send_transaction_status_batch` does these as two unsynchronized steps:
```
let work_sequence = self.dependency_tracker.as_ref().map(|dt| dt.declare_work());
if let Err(e) = self.sender.send(TransactionStatusMessage::Batch((... , work_sequence))) { ... }
``` [3](#0-2) 

This `TransactionStatusSender` is cloned into a shared `Committer` and handed to every parallel `ConsumeWorker` (`solCoWorker0N`) and the vote worker (`solBanknStgVote`), all spawned from `BankingStage::spawn_internal_central`/`spawn_vote_worker` [4](#0-3) [5](#0-4) , each independently calling `Committer::collect_balances_and_send_status_batch` → `send_transaction_status_batch` on transaction commit [6](#0-5) .

If thread A calls `declare_work()` (getting `N`) and is preempted before `sender.send()`, and thread B then calls `declare_work()` (getting `N+1`) and completes `sender.send()` first, `TransactionStatusService::write_transaction_status_batch` (single consumer, strict channel order) will process B's batch, write it to Blockstore, and call `dependency_tracker.mark_this_and_all_previous_work_processed(N+1)` [7](#0-6)  — all before A's batch (work id `N`, containing an earlier instruction such as `InitializeMint`/`SetAuthority`/`MintTo`) has even entered the channel, let alone been written to Blockstore.

Any waiter blocked in `DependencyTracker::wait_for_dependency` on an id ≤ N+1 (e.g. `OptimisticallyConfirmedBankTracker::process_notification`, which calls `tracker.wait_for_dependency(dependency_work)` before handling `BankNotification` [8](#0-7) ) returns immediately, even though the earlier batch's Blockstore write has not happened yet. Subsequent `getTransaction`/`getTokenAccountBalance` RPC reads of Blockstore for that slot can then observe missing/stale data (e.g., wrong mint decimals/authority decoded by `parse_token.rs`) despite the confirmation/notification logic believing all prior work is durably persisted.

### Impact Explanation
This is a wrong-data-returned bug: an RPC client's `getTransaction`/`getTokenAccountBalance` call can read Blockstore for a slot the node has already told subscribers/other-waiters is "confirmed" (via `OptimisticallyConfirmedBankTracker`), but whose transaction-status data (and derived token/account decode) has not actually been persisted yet, so it returns stale/incorrect on-chain token metadata (decimals, mint authority, etc.). This matches the "wrong-slot/fork/account data returned" bounty category since it is a genuine break of a documented ordering invariant reachable purely by normal, high-throughput transaction submission that engages multiple banking-stage worker threads (no leader/validator control required beyond being a normal client generating load).

### Likelihood Explanation
Preconditions: `dependency_tracker` must be `Some` (enabled config), and multiple `ConsumeWorker`/vote-worker threads must hold clones of the same `TransactionStatusSender`, which is the default multi-worker `BankingStage` architecture. The race window is the gap between `fetch_add` and `sender.send()` in `send_transaction_status_batch`, which is extremely narrow under normal scheduling, so triggering it "in the wild" purely by submitting transactions is unlikely without OS-level scheduling assistance; however, it is deterministically reproducible in a controlled unit/integration test using a synchronization barrier, confirming the invariant is not actually enforced by the code (only by scheduling luck).

### Recommendation
Make id-reservation and channel-send atomic with respect to ordering: e.g., hold a mutex/spinlock around `declare_work()` + `send()` in `send_transaction_status_batch` so no other thread can declare and send a higher id while the current thread's id is unsent, or replace the "declare-then-send" scheme with a single serialized submission point (e.g., a dedicated ordering queue) that assigns the id and enqueues the message atomically under the same lock.

### Proof of Concept
Add a test in `runtime/src/dependency_tracker.rs` (or a new integration test alongside `rpc/src/transaction_status_service.rs`) that:
1. Creates a `DependencyTracker` and two threads sharing a `TransactionStatusSender`-like wrapper that calls `declare_work()` then, gated by a `std::sync::Barrier`, calls `sender.send()`.
2. Thread A calls `declare_work()` first (gets `N`), then blocks on the barrier before sending.
3. Thread B calls `declare_work()` second (gets `N+1`), then sends immediately (does not wait on the barrier), pushing its message into the channel first.
4. A consumer thread (mimicking `TransactionStatusService`) reads messages strictly in arrival order and calls `mark_this_and_all_previous_work_processed(work_id)` after "writing" each batch to a fake Blockstore (e.g., appending to a shared `Mutex<Vec<Slot>>`).
5. Assert that when `mark_this_and_all_previous_work_processed(N+1)` fires (observable via a waiter calling `wait_for_dependency(N+1)` returning), the fake Blockstore does **not** yet contain the entry for work `N` — demonstrating the invariant "notify id s implies all ids < s are processed" is violated.

    /// Notify all waiting threads that a work has been processed with the given work id.
    /// This function will update the processed work id and notify all waiting threads only if the work
    /// id is greater than the procsessed work id. Notify a work of id number 's' will
    /// implicitly imply that all work with id number less than 's' have been processed.
    pub fn mark_this_and_all_previous_work_processed(&self, work_id: u64) {
        let mut processed_work_id = self.processed_work_id.lock().unwrap();
        if less_than(&processed_work_id, work_id) {
            *processed_work_id = Some(work_id);
            self.condvar.notify_all();
        }
    }

    /// To wait for the dependency work with 'work_id' to be processed.
    pub fn wait_for_dependency(&self, work_id: u64) {
        if work_id == 0 {
            return; // No need to wait for work id 0 as real work starts from 1.
        }
        let mut processed_work_id = self.processed_work_id.lock().unwrap();
        while less_than(&processed_work_id, work_id) {
            processed_work_id = self.condvar.wait(processed_work_id).unwrap();
        }
    }
