### Title
Node-side signer response coordinator double-counts a signer's weight in both `total_weight_approved` and `total_weight_rejected` for the same block, wedging block finalization - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener`'s message loop tracks two independent tallies per proposed block — `total_weight_approved` (from `BlockResponse::Accepted`) and `total_weight_rejected` (from `BlockResponse::Rejected`) — gated by two *different* sets (`gathered_signatures` vs. `responded_signers`). A single signer that first rejects and later legitimately reconsiders and accepts the same block (a path the signer-side code explicitly supports) ends up with its weight counted in both tallies simultaneously, because nothing removes its weight from `total_weight_rejected` when it later accepts. Since the rejection check in `signer_coordinator.rs` is evaluated before the acceptance check, this stale, double-counted rejection weight can make a block that has truly reached the 70% acceptance threshold still be treated as `SignersRejected`, wedging block finalization.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` holds: [1](#0-0) 

On `BlockResponse::Accepted`, the approve-tally is only incremented if the slot is *not yet* in `gathered_signatures`: [2](#0-1) 

On `BlockResponse::Rejected`, the reject-tally is incremented if the slot is *not yet* in `responded_signers`: [3](#0-2) 

These two gates are not mutually exclusive: `responded_signers` is populated by *both* the accept and reject branches, but the accept branch's gate is `gathered_signatures`, which is disjoint state. Concretely:
1. Signer X sends `Rejected` for block B. `responded_signers.insert(X)` → true, so `total_weight_rejected += weight(X)`.
2. Signer X later sends `Accepted` for the *same* block B (this is an explicitly supported reconsideration path on the signer side — see the comment in `stacks-signer/src/v0/signer.rs`: "we do not change our votes on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider").
3. In the accept branch, `gathered_signatures.contains_key(X)` is false (X was never in this map), so `total_weight_approved += weight(X)` fires again — X's weight is added to `total_weight_approved` while its weight is still permanently present in `total_weight_rejected` (nothing subtracts it there).

The `reset_rejections` helper acknowledges that approvals are treated as durable/one-way ("an old approval could always be used to make a block reach the approval threshold") but only clears `total_weight_rejected` on an explicit timeout-driven retry, not on this accept-after-reject transition: [4](#0-3) 

The consuming decision logic in the coordinator checks the rejection condition *before* the acceptance condition: [5](#0-4) 

Because X's weight persists in `total_weight_rejected` even after it switches to accept, `total_weight_rejected + weight_threshold > total_weight` can remain permanently true (blocking-minority condition satisfied by stale weight) even once genuine `total_weight_approved` has also crossed `weight_threshold` from the other signers plus X's legitimate later accept. Since the reject branch is checked first, the miner treats the block as rejected (`NakamotoNodeError::SignersRejected`) despite verified accepted weight actually reaching the threshold — breaking the equality between "aggregated weight" and "verified accepts" for this coordinator.

### Impact Explanation
This breaks the aggregated-weight-vs-verified-accepts equality that the miner's coordinator relies on to decide whether a block has been globally accepted or rejected. A single signer flipping its vote (an explicitly supported, non-malicious reconsideration flow) can leave stale weight permanently counted on the rejection side, causing a block that has legitimately reached the 70% signature threshold to still be reported as rejected by the coordinator. This is a liveness wedge: the miner can be stuck unable to finalize an otherwise-valid, sufficiently-signed block, and must repeatedly re-propose, without any majority of malicious signers being required.

### Likelihood Explanation
Only one signer needs to reject and later accept the same block proposal — a flow the signer codebase documents as legitimate reconsideration, and also reachable via ordinary message reordering/redelivery over StackerDB (no majority collusion, no key compromise, no auth_token access required). The affected code is exactly the miner-side coordinator (`stackerdb_listener.rs` / `signer_coordinator.rs`) that gathers and aggregates signer responses.

### Recommendation
Make the approve/reject tallies mutually exclusive per slot, mirroring the mutual-exclusion already implemented on the signer side (`add_block_signature`/`add_block_rejection_signer_addr` in `stacks-signer/src/signerdb.rs`, where accepting deletes any prior rejection row and vice versa). Concretely, when a slot's `Accepted` message is processed, remove its weight from `total_weight_rejected` (and drop it from `responded_signers`'s rejection semantics) if it was previously counted there, and vice versa for `Rejected` after a prior `Accepted`. Alternatively, track a single per-slot vote value (`Accepted`/`Rejected`) and recompute both weight totals from that canonical map on every update, rather than maintaining two independently-gated running counters.

### Proof of Concept
1. Miner proposes block B; `StackerDBListener` inserts fresh `BlockStatus` (`total_weight_approved = 0`, `total_weight_rejected = 0`).
2. Signer X (weight wX) sends `BlockResponse::Rejected(B)`. `responded_signers = {X}`, `total_weight_rejected = wX`.
3. Enough other signers send `BlockResponse::Accepted(B)` such that `total_weight_approved` from them alone is `weight_threshold - wX` (just short of threshold without X).
4. Signer X reconsiders (a supported flow per `stacks-signer/src/v0/signer.rs` comments) and sends `BlockResponse::Accepted(B)`.
5. In the accept handler, `gathered_signatures.contains_key(X)` is false, so `total_weight_approved += wX`, reaching `weight_threshold`. Meanwhile `total_weight_rejected` is still `wX` and was never decremented.
6. If `wX + weight_threshold > total_weight` (i.e., X's stale rejection weight alone exceeds the 30% blocking minority margin), `signer_coordinator.rs`'s reject-check (evaluated first) fires `NakamotoNodeError::SignersRejected` even though `total_weight_approved >= weight_threshold` is also true — the block is wrongly treated as rejected despite reaching legitimate acceptance weight.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
