## Analysis: Front-Runnable Nonce Account Initialization

The PoolTogether report describes a generic bug class: public/unauthenticated initializer functions that create state for a proxy-style contract can be called by anyone before the intended owner, letting an attacker set malicious values. Agave has a directly analogous unprivileged initialization path in the System Program's durable-nonce account handling.

### Title
Unauthenticated `InitializeNonceAccount` instruction allows front-running of nonce account creation, enabling authority hijack and fund theft - (File: `programs/system/src/system_processor.rs`, `programs/system/src/system_instruction.rs`)

### Summary
`SystemInstruction::InitializeNonceAccount` transitions an account from `State::Uninitialized` to `State::Initialized` and sets an arbitrary `nonce_authority` supplied in the instruction data, but the handler never requires the target nonce account itself to be a transaction signer, nor does it verify the caller has any relationship to the account's original creator.

### Finding Description
`process_instruction` for `SystemInstruction::InitializeNonceAccount(authorized)` only checks account count, fetches the recent-blockhashes and rent sysvars, and calls `initialize_nonce_account`, with no signer requirement on the target account: [1](#0-0) 

`initialize_nonce_account` itself only checks writability and that the account is `Uninitialized`, then blindly stores whatever `nonce_authority` pubkey was passed in the instruction: [2](#0-1) 

By contrast, comparable initializers elsewhere in the codebase (BPF Loader `InitializeBuffer`/`DeployWithMaxDataLen`, Vote Program `InitializeAccount`) all guard `AccountAlreadyInitialized` but critically also require the intended owner/authority to sign — e.g. vote account initialization enforces `verify_authorized_signer(&vote_init.node_pubkey, signers)` in addition to the uninitialized check: [3](#0-2) 

The nonce initializer has no equivalent "does the caller/creator agree" check — it is `Uninitialized -> Initialized` gated only by account state, not by any signature tied to the account's creator. The standard client helper `create_nonce_account` bundles `CreateAccount` + `InitializeNonceAccount` into a single atomic message, masking the gap: [4](#0-3) 

But nothing in the runtime enforces that these two instructions must be atomic. Any system-owned, rent-exempt, correctly-sized, `Uninitialized` account is a valid target for `InitializeNonceAccount` from any transaction, regardless of who paid to create it.

### Impact Explanation
Once an attacker front-runs initialization by submitting `InitializeNonceAccount(target, attacker_pubkey)` before the legitimate creator's own initialize instruction lands, the attacker becomes the `nonce_authority`. `withdraw_nonce_account` then allows the authority to withdraw the account's full balance to any destination, requiring only the authority's signature: [5](#0-4) 

This lets the attacker drain the lamports the victim funded into the account (deposited via `CreateAccount` for rent-exemption), a concrete unauthorized fund loss. It also lets the attacker "poison" the nonce account so the victim's own later `InitializeNonceAccount` call fails with `InstructionError::AccountAlreadyInitialized`, causing denial of the victim's intended durable-nonce setup.

### Likelihood Explanation
Exploitability depends on the account-creation and initialization steps not being submitted as a single atomic transaction. This can happen whenever a wallet, exchange, or program splits account funding/creation from nonce initialization into separate transactions or defers initialization (e.g., pre-funding an address before deciding to initialize it as a nonce account), a pattern that is not prevented by the protocol. Any observer of the mempool/QUIC-ingested `CreateAccount` transaction targeting a to-be-nonce address can race an `InitializeNonceAccount` transaction against the victim's own initialize transaction.

### Recommendation
Require the target nonce account (or its designated creator/base key) to be a signer of `InitializeNonceAccount`, mirroring the `verify_authorized_signer` pattern used in `programs/vote/src/vote_state/mod.rs`'s `initialize_account`/`initialize_account_v2`, so that only the party controlling the account's keypair (or a designated authority established at creation) can transition it out of `Uninitialized`.

### Proof of Concept
1. Victim submits `CreateAccount(payer, nonce_pubkey, lamports=min_rent, space=NonceState::size(), owner=system_program)` as a standalone transaction (not bundled with `InitializeNonceAccount`).
2. Attacker observes this transaction in the mempool/QUIC stream and, before the victim's follow-up `InitializeNonceAccount(nonce_pubkey, victim_authority)` lands, submits `InitializeNonceAccount(nonce_pubkey, attacker_pubkey)` — no signature from `nonce_pubkey` is required per `system_processor.rs:448-466`.
3. The account transitions to `State::Initialized { authority: attacker_pubkey, .. }` per `initialize_nonce_account` (`system_instruction.rs:163-211`).
4. Victim's original `InitializeNonceAccount` now fails with `InstructionError::InvalidAccountData` (account already `Initialized`), per the `State::Initialized(_)` branch.
5. Attacker submits `WithdrawNonceAccount(nonce_pubkey, full_balance, attacker_dest)`, signing as `attacker_pubkey`; `withdraw_nonce_account` (`system_instruction.rs:125-151`) validates only `check_signer(&data.authority)` — which is the attacker — and transfers all lamports out.

```rust
pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
```
