### Title
Vote-flip from Rejected to Accepted double-counts a signer's weight in both `total_weight_approved` and `total_weight_rejected` - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener`'s message loop maintains a shared `BlockStatus` struct that the mining coordinator (`signer_coordinator.rs`) polls to decide whether a proposed block has reached the 70% signing threshold or the >30% blocking-minority rejection threshold. The two branches that update this tally use inconsistent de-duplication keys: the `Rejected` branch gates on `responded_signers`, while the `Accepted` branch gates on a different set, `gathered_signatures`. When the same signer later reverses an earlier rejection into an acceptance for the same block (a transition the signer state machine explicitly supports), the signer's weight gets added to `total_weight_approved` without ever being subtracted from `total_weight_rejected`, so the same weight is now counted on both sides of the tally simultaneously.

### Finding Description
`BlockStatus` tracks `total_weight_approved`, `total_weight_rejected`, and a single `responded_signers: HashSet<u32>` (by slot id) meant to prevent double-counting a signer's response. [1](#0-0) 

In the `Rejected` arm, the weight is only added the first time `responded_signers.insert(slot_id)` returns `true`: [2](#0-1) 

In the `Accepted` arm, however, the guard used is `!block.gathered_signatures.contains_key(&slot_id)` — a completely different map — and `responded_signers.insert(slot_id)` is called only afterward, unconditionally, with its return value ignored: [3](#0-2) 

Consequence: if a signer's slot previously sent `Rejected` (weight added to `total_weight_rejected`, slot id placed in `responded_signers`) and subsequently sends `Accepted` for the *same* block hash, the `Accepted` branch sees the slot id absent from `gathered_signatures` and adds the weight to `total_weight_approved` as well — `total_weight_rejected` is never decremented. The signer's weight is now counted in both buckets at once, breaking the invariant that `total_weight_approved + total_weight_rejected ≤ total_weight` that the coordinator's threshold arithmetic depends on.

This reversal is not a theoretical/majority-only scenario: the signer-side state machine explicitly allows `LocallyRejected → LocallyAccepted` on re-evaluation (e.g. `should_reevaluate_reject_reason`), and a single honest signer reconsidering a block it previously rejected (for a re-evaluable reason) will naturally emit `Rejected` then `Accepted` for the same `signer_signature_hash`. No majority collusion, no key compromise, and no protocol violation is required — this is triggerable by ordinary gossip/re-proposal handling from one signer.

### Impact Explanation
The coordinator (`get_block_status` in `signer_coordinator.rs`) checks the rejection condition first, then the approval condition: [4](#0-3) 

Because a flipped signer's weight persists in `total_weight_rejected` even after that signer accepts, `total_weight_rejected` can remain inflated by stale weight while `total_weight_approved` simultaneously and legitimately reaches the 70% threshold. Since the rejection branch is evaluated first, the miner can be told the block was rejected by a blocking minority (`SignersRejected`, including txid exclusion/ban logic driven by the same stale weight) even though the *current* set of votes has already reached genuine 70% consensus. This wedges block production: signatures that already satisfy consensus are discarded, the miner unnecessarily re-proposes or excludes transactions based on phantom rejection weight, stalling tenure progress until a fresh block/proposal cycle clears the stale `BlockStatus` entry. This matches the High-impact category of a wedge that degrades liveness/causes the coordinator to act on a stale, inconsistent tally rather than the true accepted/rejected state.

### Likelihood Explanation
This requires only one signer flipping its own vote on one block hash — an event the signer's own re-evaluation logic is designed to produce — plus no fix on the node side to reconcile the two tallies. No majority of signers, no compromised keys, and no auth token access are needed; it is purely a bookkeeping inconsistency between the `Accepted` and `Rejected` message-handling branches inside `StackerDBListener`, which is populated directly from ordinary StackerDB gossip.

### Recommendation
Use a single, consistent per-signer tracking structure (e.g., a `HashMap<u32, Vote>` recording each slot's *current* verdict) instead of two independently-guarded counters keyed by different sets. When a signer's verdict changes from Rejected to Accepted (or vice versa), atomically move the weight: subtract it from the old bucket's total before adding it to the new bucket's total, mirroring the fix applied to the analogous `remainingReward`/`accountedReward` accounting bug in the referenced report.

### Proof of Concept
1. Miner proposes block `B` (hash `H`) to signer set with weights `w1..wn`.
2. Signer `S` (slot `k`, weight `w_k`) initially rejects `B` for a re-evaluable reason (e.g. it hadn't yet observed the parent block was processed). `StackerDBListener` processes `BlockResponse::Rejected`, `responded_signers.insert(k)` succeeds, `total_weight_rejected += w_k`.
3. `S`'s local chainstate check re-evaluates and now finds `B` valid (`should_reevaluate_reject_reason` path in `stacks-signer/src/v0/signer.rs`), so `S` signs `B` and broadcasts `BlockResponse::Accepted`.
4. `StackerDBListener` processes `Accepted`: `gathered_signatures` does not contain `k`, so `total_weight_approved += w_k` is applied; `total_weight_rejected` is left unchanged at its previous value that already included `w_k`.
5. Now `total_weight_approved + total_weight_rejected > total_weight` by `w_k`. If enough other signers accept, `total_weight_approved` reaches the 70% threshold while `total_weight_rejected` (inflated by the stale `w_k`) also crosses the >30% blocking-minority line, causing `get_block_status` to return `SignersRejected` for a block that in fact has legitimate 70% current support — stalling that tenure's block production.
