### Title
Cross-user response hijacking via MessageId collision in gateway capabilities handler `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's `capabilities` handler stores each in-flight user callback in `h.savedCallbacks` keyed only by the client-supplied `msg.Body.MessageId`, with no binding to the resolved signer/sender and no uniqueness check. An unauthenticated/unprivileged attacker who can guess or observe another user's `MessageId` can submit a second, independently-signed request with the same ID to the same `DonId`, overwrite the victim's saved callback, and receive the victim's DON response instead of the victim.

### Finding Description
`gateway.ProcessRequest` (core/services/gateway/gateway.go:218-292) decodes the incoming request, resolves the handler for the target DON/service, creates a fresh per-request `callback := handlerscommon.NewCallback()`, and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` [1](#0-0) . For legacy DON-routed messages, only `msg.Validate()` is enforced, which checks signature format/length and message field constraints, and derives `Body.Sender` from the signature — but does not enforce ID uniqueness or bind the message ID to a specific sender [2](#0-1) .

Inside `handler.HandleLegacyUserMessage`, the callback is registered in a shared map keyed solely by `msg.Body.MessageId`, with no existence check before the write:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
``` [3](#0-2) 

When a DON node later responds with the same `MessageId`, `handleWebAPITriggerMessage` looks the callback up purely by ID and deletes/sends to whatever is currently stored, again with no sender check:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [4](#0-3) 

Exploit flow:
1. Victim submits a legacy request with `MessageId = X` to `DonId = D`; `HandleLegacyUserMessage` stores `savedCallbacks[X] = victimCallback` and forwards to DON members.
2. Attacker, knowing/guessing `X` and `D`, signs and submits their own request with the identical `MessageId = X` to the same DON before the DON responds. Since `MessageId` is fully attacker-chosen and signature validation only checks that the request is self-consistently signed (not that the ID is unclaimed or belongs to the same sender as a prior request), this succeeds and overwrites `savedCallbacks[X] = attackerCallback`.
3. When the DON node responds to the victim's original forwarded request with `MessageId = X`, `handleWebAPITriggerMessage` looks up `savedCallbacks[X]`, finds the attacker's callback (which overwrote the victim's), and delivers the victim's response payload to the attacker's HTTP connection via `attackerCallback.SendResponse`.
4. The victim's original `callback.Wait(ctx)` in `gateway.ProcessRequest` never receives a response and times out, while the attacker receives data intended for the victim.

No component in this path (`Message.Validate`, `HandleLegacyUserMessage`, `handleWebAPITriggerMessage`) checks that the sender resolved from the second request's signature matches the sender bound to the first occupant of that `MessageId`, nor rejects a colliding ID outright.

### Impact Explanation
This breaks the isolation invariant between concurrent gateway users: an attacker can redirect another user's `web_api_trigger` response (which can carry sensitive workflow trigger payloads) to themselves, and simultaneously deny/starve the legitimate requester (their request silently times out). This matches the "cross-user response confusion" / unauthorized access-to-another-user's-data impact class.

### Likelihood Explanation
The only precondition is knowledge of a target `MessageId` and `DonId`/service name, both of which travel in the JSON-RPC request and are frequently predictable or observable (e.g., sequential/deterministic IDs generated by client SDKs, or IDs leaked through logs/telemetry/shared infra). No credentials beyond the attacker's own signing key are required, and any address can sign a legacy Message. The race window is the round-trip time to the DON, which is easily large enough (network + OCR-style consensus latency) for an attacker to win the overwrite race reliably, and the attack is trivially repeatable.

### Recommendation
Bind `savedCallbacks` entries to both `MessageId` and the resolved sender (e.g., key by `hash(DonId, Sender, MessageId)` or store the expected sender and verify it on both save and node-response lookup), and reject (rather than silently overwrite) a `HandleLegacyUserMessage` call whose `MessageId` collides with a still-pending, different-sender entry.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two signed `api.Message`s with identical `Body.MessageId = "X"`, `Body.DonId` equal, but different private keys (victim vs attacker), each with distinct `Payload`.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`, then immediately `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`, asserting `h.savedCallbacks["X"]` now points to `attackerCallback`.
3. Simulate the DON's response to the victim's forwarded request by invoking `handler.HandleNodeMessage` with a node response carrying `MessageId = "X"` and the victim-associated payload.
4. Assert `attackerCallback.Wait(ctx)` returns the victim's payload (`require.Contains` on the response body matching the victim's expected content), and assert `victimCallback.Wait(ctx)` times out / never receives a response — proving cross-user response delivery.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
