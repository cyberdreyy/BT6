### Title
Cross-vote double counting lets a single flipped signer inflate both approval and rejection weight in the miner's block-status tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies signer weight toward the 70% signing threshold and the 30% rejection threshold by tracking two separate dedup sets for the two message kinds: `gathered_signatures` (keyed by slot, populated only by `Accepted`) and `responded_signers` (a shared "has this slot already counted" set, but checked inconsistently). The `Accepted` handler dedups against `gathered_signatures`, while the `Rejected` handler dedups against `responded_signers`. Because these are two different sets, a signer that first sends `Rejected` (which inserts into `responded_signers` and bumps `total_weight_rejected`) and later sends `Accepted` for the *same* block hash is not blocked by the `Accepted` branch's guard (`gathered_signatures.contains_key(&slot_id)` is still false), so that signer's weight is added a second time, this time to `total_weight_approved`.

block.gathered_signatures.insert(slot_id, signature);

- `BlockResponse::Rejected` branch:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [2](#0-1) 

The intent of `responded_signers` is clearly to be the single "already counted" record per signer (its name and the reject-side idempotency check make that plain), yet the accept-side idempotency check uses a *different* structure (`gathered_signatures`). This creates an asymmetry:

- Accept → later Reject from the same signer: correctly suppressed, because `responded_signers` already contains the slot from the Accept branch (which also inserts into `responded_signers` at line 465), so the reject-side `insert()` returns `false` and no reject weight is added.
- Reject → later Accept from the same signer: **not** suppressed, because the accept-side guard checks `gathered_signatures`, which was never touched by the reject branch. The signer's weight is added to `total_weight_approved` even though it was already added to `total_weight_rejected` moments earlier.

This is exploitable by exactly one signer flipping its own vote for the same `signer_signature_hash`. The signer-side state machine explicitly permits this transition: `BlockInfo::check_state` allows `LocallyRejected -> LocallyAccepted` as long as the block hasn't reached global consensus (`GloballyRejected`/`GloballyAccepted` are the only states that block it): [3](#0-2) . The signer proposal-reevaluation path (`should_reevaluate_reject_reason`, described in `docs/signer-flows.md` section 3) is designed to let a signer revisit and reverse a prior rejection when the reject reason is deemed "re-evaluable," and broadcast a new response accordingly. A malicious or simply reconfigured signer can trivially send `Rejected` then `Accepted` (or replay an old cached `Accepted` after a `Rejected`) for the same block hash without any node-side check preventing the double count.

The consequence breaks the intended equality "aggregated approved-weight == weight of distinct signers who genuinely accepted." `total_weight_approved` can include weight units contributed by signers who are simultaneously (and correctly) still tallied in `total_weight_rejected`, i.e., the same weight is double-counted across both pools. `signer_coordinator.rs::get_block_status` uses exactly this counter to decide whether the block is signed (`block_status.total_weight_approved >= self.weight_threshold`) and to assemble/push the pushed signature set: [4](#0-3) .

### Impact Explanation
This maps to the listed critical impact "a rejection recounted as an accept." Because a single flipped signer's weight is double counted, the *real* distinct approving weight needed to reach the 70% threshold can be less than 70% of total signer weight — the coordinator can believe the vote has crossed the threshold earlier than a legitimate, non-duplicated tally would allow, while a portion of that counted weight is simultaneously present in the rejection pool. This weakens the safety margin of the signing threshold with attacker-controlled input from a single non-majority signer, undermining the "aggregated-weight vs verified-accepts" invariant that the entire pre-commit/threshold design in `docs/signer-flows.md` (sections 5–6) is built to guarantee.

### Likelihood Explanation
Only one misbehaving (or buggy/out-of-sync) signer is required, and no elevated privileges, majority coordination, or another signer's key are needed — only crafting/replaying two ordinary `BlockResponse` StackerDB messages (`Rejected` then `Accepted`) for the same `signer_signature_hash`. The signer-side state machine explicitly supports the reject→accept transition (reevaluation), so this can even happen without malice under specific rejection-reason re-evaluation flows, and can be deliberately forced by an adversarial signer sending both messages back-to-back.

### Recommendation
Use a single, consistent dedup structure across both `Accepted` and `Rejected` handling. Specifically, the `Accepted` branch should check `responded_signers` (not `gathered_signatures`) before adding weight to `total_weight_approved`, mirroring the `Rejected` branch, so that once a signer's weight has been counted toward either pool, it can never be counted toward the other for the same block.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected(H, ...)`. Listener: `responded_signers.insert(slot_S)` succeeds → `total_weight_rejected += w`. [2](#0-1) 
3. Same signer `S`, after reconsidering (or replaying a stale message, or acting maliciously), sends `BlockResponse::Accepted(H, sig)` for the same `H`. `gathered_signatures.contains_key(slot_S)` is `false` (never touched by step 2) → `total_weight_approved += w`. [1](#0-0) 
4. `S`'s weight `w` is now counted in both `total_weight_rejected` and `total_weight_approved`. Repeating with a small set of flipping signers lets `total_weight_approved` cross `weight_threshold` using less real distinct approving weight than the protocol assumes, while those same signers' weight simultaneously counts toward pushing the rejection tally.
