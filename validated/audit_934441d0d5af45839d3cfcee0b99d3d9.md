Based on my research, I've identified a strong structural analog to the FairSide `pendingWithdrawals` bug in Agave's vote program's `pending_delegator_rewards` accounting (SIMD-0123 delegator block-reward mechanism).

### Title
`pending_delegator_rewards` is never decremented after block-reward distribution, permanently over-reserving vote-account lamports and blocking legitimate withdrawals - (File: programs/vote/src/vote_state/handler.rs, programs/vote/src/vote_state/mod.rs, runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`VoteStateHandler` exposes `add_pending_delegator_rewards` to increase the `pending_delegator_rewards` counter whenever lamports are deposited via `deposit_delegator_rewards` [1](#0-0) , and this counter is read (but never decremented) as a reserved-balance floor inside `withdraw` [2](#0-1) . The bank-side reward calculation reads this same field to compute each delegator's share of the block reward pool [3](#0-2) , but no corresponding "subtract" function for `pending_delegator_rewards` exists anywhere in the vote program or bank reward-distribution code that I could locate.

### Finding Description
`pending_delegator_rewards` is meant to track lamports sitting in the vote account that are earmarked for distribution to delegators (deposited via `deposit_delegator_rewards`, which increments the field with `add_pending_delegator_rewards`) [4](#0-3) . The withdraw path enforces that the authorized withdrawer cannot pull the vote account balance below `rent_exempt_minimum + pending_delegator_rewards`, and blocks closing the account entirely while `pending_delegator_rewards > 0` [2](#0-1) .

The bank's epoch-reward calculation (`calculate_block_reward`) reads `pending_delegator_rewards` from the vote state to compute each delegator's proportional share of the block-reward pool, and clamps the computed amount to be no larger than `pending_delegator_rewards` [5](#0-4) . This is the "payout" side of the mechanism—analogous to `Withdrawable.withdraw` in the FairSide report—yet across every location where `pending_delegator_rewards` is referenced (`handler.rs`, `vote_state/mod.rs`, `vote_processor.rs`, `calculation.rs`, `vote_state_view/frame_v4.rs`), only an `add_pending_delegator_rewards` increment function is present; no decrement/consume method exists in the vote program's public or private API.

This mirrors the FairSide root cause exactly: a storage field that tracks an amount "yet to be paid out" is incremented on deposit but never decremented on the corresponding payout/distribution event, leaving the bookkeeping permanently overstated relative to the account's true remaining obligation.

### Impact Explanation
If block rewards computed from `pending_delegator_rewards` are actually paid out (lamports moved from the vote account to delegator stake accounts) without the vote account's `pending_delegator_rewards` field being reduced to reflect the payout, the effect is:
- The authorized withdrawer is permanently blocked from withdrawing lamports that have already been distributed to delegators, since `withdraw` keeps reserving the full historical (undecremented) `pending_delegator_rewards` amount as an untouchable minimum balance.
- The vote account can never be closed (`remaining_balance == 0` path requires `pending_delegator_rewards == 0`), a permanent denial of a legitimate account-closure operation, even long after all deposited rewards have been fully distributed.
- If the reward-distribution logic instead relies on the stale (never-decreasing) `pending_delegator_rewards` figure as an input to subsequent epochs' reward calculations, delegators could be paid out repeatedly against the same already-consumed pool across multiple epochs (double-distribution) up to the vote account's actual remaining lamports, which is a fund-accounting integrity issue.

### Likelihood Explanation
This path is reachable purely through the normal validator/vote-account lifecycle: any vote account owner who receives block-revenue-sharing deposits (SIMD-0123 `DepositDelegatorRewards`) and later has rewards distributed across an epoch boundary is affected — no privileged or malicious actor is required. However, I was not able to locate, within the available search budget, the exact bank-level code path that performs the lamport debit for block-reward distribution to confirm whether it does or does not also update the serialized `VoteStateV4.pending_delegator_rewards` field via a re-serialize. It is possible such an update exists in code I did not surface (e.g., a distribution routine elsewhere in `runtime/src/bank/partitioned_epoch_rewards/` that I did not fully enumerate). Given the absence of any decrement API across the vote program itself, likelihood is assessed as plausible but not fully confirmed.

### Recommendation
Audit the block-reward distribution routine in `runtime/src/bank/partitioned_epoch_rewards/` (wherever `calculate_block_reward`'s output is applied to move lamports) to confirm whether it deserializes the vote account, subtracts the distributed amount from `pending_delegator_rewards`, and re-serializes the account state. If no such decrement occurs, add a `sub_pending_delegator_rewards` method to `VoteStateHandler` (`programs/vote/src/vote_state/handler.rs`) symmetric to `add_pending_delegator_rewards`, and invoke it at the exact point lamports are debited from the vote account for delegator payout, ensuring the account's serialized state and its lamport balance stay consistent.

### Proof of Concept
Not independently verified end-to-end due to inability to trace the exact bank-side debit routine within the available search iterations; verification would require: (1) locating the exact function in `runtime/src/bank/partitioned_epoch_rewards/` that applies `calculate_block_reward`'s result to actually move lamports out of the vote account, and (2) confirming whether that function updates `pending_delegator_rewards` in the account's serialized `VoteStateV4` data. If it does not, a minimal repro is: deposit delegator rewards via `DepositDelegatorRewards`, let one epoch's rewards be distributed to delegators (draining lamports from the vote account), then call `withdraw` for the drained account and observe it still fails/blocks based on the stale `pending_delegator_rewards` value from before distribution (test harness exists at `programs/vote/src/vote_processor.rs:5219` `test_withdraw_pending_delegator_rewards` [6](#0-5)  which could be extended to simulate a distribution event and check for the missing decrement).

/// Deposit delegator rewards into a vote account (SIMD-0123).
pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
