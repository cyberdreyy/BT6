### Title
Unsynchronized read of `Session.proxyPool` in `proxyHandler` races with `SetProxyPool` write - ([File: session/session.go])

### Summary
`Session.proxyHandler` reads `s.proxyPool` (session.go:130) without holding `s.lock`, while `Session.SetProxyPool` (session.go:245-249) reassigns `s.proxyPool` under `s.lock`. Because the executor calls `SetProxyPool` asynchronously after `NewSession` already registered `proxyHandler` on the mux (session.go:68, 111-118), a client request to `/proxy/...` can race with the executor's pool population, producing a genuine unsynchronized concurrent read/write on a Go map variable.

### Finding Description
`NewSession` creates the session, immediately calls `setMux()`, which registers both `/proxy/` and `/exec` routes (session.go:68, 111-118) before the executor has had a chance to call `SetInteractiveTerminal` or `SetProxyPool`. For `/exec`, `execHandler` explicitly waits on `s.terminalSetCh` (or a 1-minute timeout) before proceeding (session.go:159-173) - that path is deliberately race-free by design.

For `/proxy/`, however, `proxyHandler` has no equivalent wait mechanism and, critically, reads `s.proxyPool[serviceName]` directly without acquiring `s.lock` (session.go:130). Meanwhile `SetProxyPool` writes `s.proxyPool = pooler.Pool()` while holding `s.lock` (session.go:245-249). If a client sends a request to the `/proxy/` endpoint at (or immediately after) session creation, while the executor goroutine is concurrently calling `SetProxyPool` to install the real pool, the two accesses to `s.proxyPool` are unsynchronized - one under lock, one without. This is a real data race under the Go memory model, and because it involves a map field being reassigned/read concurrently, it is flagged by the race detector and can, depending on internal map machinery and read/write interleaving, surface at runtime.

None of the existing checks stop this: the `withAuthorization` wrapper (session.go:96-109) only checks the session token; it does not check whether the session executor has finished wiring up state. `proxyHandler`'s nil checks (session.go:131, 137) only guard against a *fully assigned but empty* map/entry - they do nothing to protect the underlying map access itself from a concurrent write.

### Impact Explanation
The immediate, concrete impact is a data race on `Session.proxyPool`, detectable by `go test -race`, which is a legitimate defect on its own (undefined behavior, non-deterministic results, potential for `fatal error: concurrent map read and map write` which is unrecoverable and crashes the entire runner process — not just the offending goroutine). This is a process-wide fatal event in Go, so if triggered it would disrupt the whole `gitlab-runner` process and any other jobs/sessions it is concurrently serving, matching the claimed "runner-wide disruption" impact. However, this requires very tight timing (a proxy request arriving in the narrow window between `NewSession`/`setMux` and the executor's `SetProxyPool` call), and the exploitable "stale/foreign handler" claim is not substantiated: `SetProxyPool` fully replaces the map in one atomic Go-level assignment (session.go:248), so there is no mechanism for a request to be routed to another job's/session's proxy pool — each `Session` object owns its own `proxyPool` field, so there is no cross-session data leakage, only a race with the same session's own pool population.

### Likelihood Explanation
Preconditions: the attacker (a normal job/pipeline author with a running interactive web terminal / service proxy session) must send a `/proxy/...` request within the narrow race window between session creation and the executor's asynchronous `SetProxyPool` call. This window is typically very short in practice, making exploitation timing-sensitive and non-deterministic. It is reproducible under `go test -race` by directly invoking `proxyHandler` concurrently with `SetProxyPool`, but exploiting it over the network reliably (to force a real runtime fatal error rather than a benign nil/not-found response) is not guaranteed and depends on internal Go map implementation timing.

### Recommendation
Acquire `s.lock` around the read of `s.proxyPool` in `proxyHandler`, mirroring the pattern already used in `terminalAvailable`, `newTerminalConn`, `closeTerminalConn`, and `SetProxyPool`:

```go
func (s *Session) proxyHandler(w http.ResponseWriter, r *http.Request) {
    ...
    s.lock.Lock()
    serviceProxy := s.proxyPool[serviceName]
    s.lock.Unlock()
    ...
}
```

Optionally, add a similar "wait for pool to be set" mechanism (a channel analogous to `terminalSetCh`) so proxy requests arriving before the executor finishes wiring up services get a graceful wait/timeout rather than an immediate "not found" or racy read.

### Proof of Concept
```go
func TestProxyHandlerRaceWithSetProxyPool(t *testing.T) {
    s, err := NewSession(nil)
    require.NoError(t, err)

    var wg sync.WaitGroup
    wg.Add(2)

    // goroutine 1: executor asynchronously populates the pool
    go func() {
        defer wg.Done()
        pool := proxy.NewPool()
        pool["svc"] = &proxy.Proxy{Settings: proxy.NewProxySettings("svc", []proxy.Port{{Number: 80}})}
        s.SetProxyPool(fakePooler{pool: pool})
    }()

    // goroutine 2: attacker hits /proxy/ endpoint immediately
    go func() {
        defer wg.Done()
        req := httptest.NewRequest("GET", s.Endpoint+"/proxy/svc/80/", nil)
        req.Header.Set("Authorization", s.Token)
        rec := httptest.NewRecorder()
        s.Handler().ServeHTTP(rec, req)
    }()

    wg.Wait()
}
```
Run with `go test -race ./session/...`; the assertion is that the race detector reports no data race on `Session.proxyPool`. func NewSession(logger *logrus.Entry) (*Session, error) {
	endpoint, token, err := generateEndpoint()
	if err != nil {
		return nil, err
	}

	if logger == nil {
		logger = logrus.NewEntry(logrus.StandardLogger())
	}

	logger = logger.WithField("uri", endpoint)

	sess := &Session{
		Endpoint:      endpoint,
		Token:         token,
		DisconnectCh:  make(chan error),
		TimeoutCh:     make(chan error),
		terminalSetCh: make(chan struct{}),

		log: logger,
	}

	sess.setMux()

	return sess, nil
}

func (s *Session) withAuthorization(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		logger := s.log.WithField("uri", r.RequestURI)
		logger.Debug("Endpoint session request")

		if s.Token != r.Header.Get("Authorization") {
			logger.Error("Authorization header is not valid")
			http.Error(w, http.StatusText(http.StatusUnauthorized), http.StatusUnauthorized)
			return
		}

		next.ServeHTTP(w, r)
	})
}

func (s *Session) setMux() {
	s.lock.Lock()
	defer s.lock.Unlock()

	s.mux = http.NewServeMux()
	s.mux.Handle(s.Endpoint+"/proxy/", s.withAuthorization(http.HandlerFunc(s.proxyHandler)))
	s.mux.Handle(s.Endpoint+"/exec", s.withAuthorization(http.HandlerFunc(s.execHandler)))
}

func (s *Session) proxyHandler(w http.ResponseWriter, r *http.Request) {
	serviceName, port, requestedURI, ok := parseProxyParams(strings.TrimPrefix(r.URL.Path, s.Endpoint+"/proxy/"))
	if !ok {
		http.Error(w, http.StatusText(http.StatusNotFound), http.StatusNotFound)
		return
	}

	logger := s.log.WithField("uri", r.RequestURI)
	logger.Debug("Proxy session request")

	serviceProxy := s.proxyPool[serviceName]
	if serviceProxy == nil {
		logger.Warn("Proxy not found")
		http.Error(w, http.StatusText(http.StatusNotFound), http.StatusNotFound)
		return
	}

	if serviceProxy.ConnectionHandler == nil {
		logger.Warn("Proxy connection handler is not defined")
		http.Error(w, http.StatusText(http.StatusNotFound), http.StatusNotFound)
		return
	}

	serviceProxy.ConnectionHandler.ProxyRequest(w, r, requestedURI, port, serviceProxy.Settings)
}
