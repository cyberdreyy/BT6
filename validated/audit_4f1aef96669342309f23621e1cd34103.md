## Title
Permissionless, signer-less `InitializeNonceAccount` allows front-running/hijack of nonce accounts to drain deposited lamports - (File: `programs/system/src/system_instruction.rs`)

## Summary
The reported bug class is a permissionless, idempotent "prepare" function (`prepareCondition`) that lets an unauthenticated caller set critical initial state (a price oracle / initial pricing data) that later controls fund flows, with no check that the caller is the intended initializer. This is directly analogous to `initialize_nonce_account` in Agave's system program: it sets the security-critical `authority` field of a nonce account based solely on the account's current `State` (Uninitialized → Initialized), without ever checking that any party has signed the transaction.

## Finding Description
`initialize_nonce_account` in `programs/system/src/system_instruction.rs` only checks that the target account is writable and currently `State::Uninitialized`; it never checks a `signers: &HashSet<Pubkey>` set (it doesn't even take one as a parameter), unlike its sibling instructions `advance_nonce_account` and `authorize_nonce_account`, which both explicitly verify `signers.contains(&data.authority)` before mutating state: [1](#0-0) 

Compare this with `authorize_nonce_account`, which requires the account's *own* authority to be a signer before it will change the authority field: [2](#0-1) 

The dispatcher in `system_processor.rs` confirms `InitializeNonceAccount` is routed straight to `initialize_nonce_account` without any additional signer gating beyond what that function itself performs (none): [3](#0-2) 

Because Solana's runtime only requires that a writable account be *owned* by the invoked program to allow data mutation (not that its key be a transaction signer), and because `initialize_nonce_account`'s only gate is the account's on-chain `State` byte layout (`Uninitialized`), **anyone** can submit an `InitializeNonceAccount` instruction naming themselves as `nonce_authority` against any system-owned, rent-exempt, uninitialized account of the correct size — with zero signature requirement tying them to that account.

This exactly mirrors the reported Solidity issue: `prepareCondition` is idempotent/permissionless and lets the first caller lock in the `priceOracle` (a critical, fund-controlling field) purely based on "has this been prepared yet," not "is this the authorized initializer." Here, `initialize_nonce_account` lets the first caller lock in `nonce_authority` purely based on "is this account Uninitialized yet," not "does the caller control this account."

The intended safe usage pattern bundles `CreateAccount` + `InitializeNonceAccount` atomically in one transaction/message (as seen in the CLI helper `create_nonce_account`), where `CreateAccount` requires the new account's private key to sign, indirectly protecting the subsequent `InitializeNonceAccount`: [4](#0-3) 

But nothing in the on-chain processor enforces that these two instructions must be atomic or come from the same transaction/signer. If a wallet, exchange, bridge, or program funds a nonce-account-shaped account in one transaction and initializes it in a later, separate transaction (or the initialize instruction is otherwise delayed/re-ordered — via priority-fee front-running, network congestion, or leader reordering across slots), an attacker can race to submit their own `InitializeNonceAccount` naming themselves as authority.

Once the attacker becomes `authority`, `withdraw_nonce_account` will honor their signature and let them drain all lamports funded into the account: [5](#0-4) 

## Impact Explanation
An attacker who wins this race becomes the sole `nonce_authority` of an account funded by the victim, and can subsequently call `WithdrawNonceAccount` to steal all lamports deposited into it (minus/including rent-exempt reserve, whichever the attacker chooses to withdraw), or `AdvanceNonceAccount`/`AuthorizeNonceAccount` to further manipulate the account. This is a direct unauthorized fund theft primitive reachable by any ordinary user crafting a standard system-program instruction — no privileged access, leaked keys, or node-level compromise required.

## Likelihood Explanation
Exploitability depends on the victim splitting `CreateAccount` and `InitializeNonceAccount` into separate transactions (or otherwise allowing a window where the account is funded-but-uninitialized before their own initialize instruction lands) — the "happy path" CLI/SDK helper bundles them atomically. However, many custom integrations, bridges, or scripts that build nonce accounts manually, or PDA/pre-funded-account patterns for durable-nonce provisioning, may not guarantee atomicity, and an attacker only needs to watch pending transactions/mempool and submit a higher-priority-fee `InitializeNonceAccount` naming themselves. This matches the "frontrunning/reorg" threat model of the original report closely.

## Recommendation
Add an explicit signer check to `initialize_nonce_account` requiring the target account's own key (or a designated funder) to be present in `signers` before transitioning from `Uninitialized` to `Initialized`, mirroring the checks already present in `advance_nonce_account` and `authorize_nonce_account`. At minimum, document and enforce (at the SDK/CLI level and ideally on-chain) that `InitializeNonceAccount` must only be processed atomically with the `CreateAccount` that funds it, so no window exists where an uninitialized-but-funded account is exposed to permissionless initialization.

## Proof of Concept
1. Alice sends transaction A: `system_instruction::create_account` funding new account `N` (owned by System Program, sized to `nonce::state::State::size()`), requiring `N`'s keypair to sign only this instruction. `N` is now `Uninitialized` and rent-exempt.
2. Alice intends to send transaction B later: `SystemInstruction::InitializeNonceAccount(alice_pubkey)` on `N`.
3. Mallory observes `N` on-chain (or in-flight) as funded-but-`Uninitialized`, and submits her own transaction with `SystemInstruction::InitializeNonceAccount(mallory_pubkey)` targeting `N`, with a higher priority fee so it lands first. No signature from `N` or Alice is required — `initialize_nonce_account` (`programs/system/src/system_instruction.rs:163-211`) never checks `signers`.
4. Mallory's instruction succeeds: `N`'s `nonce::state::Data::authority = mallory_pubkey`.
5. Alice's later transaction B fails with `InstructionError::InvalidAccountData` (state already `Initialized`, per lines 202-209).
6. Mallory submits `SystemInstruction::WithdrawNonceAccount(all_lamports)` signed by herself; `withdraw_nonce_account`'s `check_signer(&data.authority)` (`programs/system/src/system_instruction.rs:80-161`) passes because she is now the authority, and she drains all lamports Alice deposited into `N`.

pub(crate) fn withdraw_nonce_account(
    from_account_index: IndexOfAccount,
    lamports: u64,
    to_account_index: IndexOfAccount,
    rent: &Rent,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.is_writable() {
        ic_msg!(
            invoke_context,
            "Withdraw nonce account: Account {} must be writeable",
            from.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    let check_signer = |signer: &Pubkey| {
        if !signers.contains(signer) {
            ic_msg!(
                invoke_context,
                "Withdraw nonce account: Account {} must sign",
                signer
            );
            return Err(InstructionError::MissingRequiredSignature);
        }
        Ok(())
    };

    let state: Versions = from.get_state()?;
    match state.state() {
        State::Uninitialized => {
            if lamports > from.get_lamports() {
                ic_msg!(
                    invoke_context,
                    "Withdraw nonce account: insufficient lamports {}, need {}",
                    from.get_lamports(),
                    lamports,
                );
                return Err(InstructionError::InsufficientFunds);
            }
            check_signer(from.get_key())?;
        }
        State::Initialized(data) => {
            if lamports == from.get_lamports() {
                let durable_nonce =
                    DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
                if data.durable_nonce == durable_nonce {
                    ic_msg!(
                        invoke_context,
                        "Withdraw nonce account: nonce can only advance once per slot"
                    );
                    return Err(SystemError::NonceBlockhashNotExpired.into());
                }
                check_signer(&data.authority)?;
                from.set_state(&Versions::new(State::Uninitialized))?;
            } else {
                let min_balance = rent.minimum_balance(from.get_data().len());
                let amount = checked_add(lamports, min_balance)?;
                if amount > from.get_lamports() {
                    ic_msg!(
                        invoke_context,
                        "Withdraw nonce account: insufficient lamports {}, need {}",
                        from.get_lamports(),
                        amount,
                    );
                    return Err(InstructionError::InsufficientFunds);
                }
                check_signer(&data.authority)?;
            }
        }
    };

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;

    Ok(())
}

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}

pub(crate) fn authorize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Authorize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }
    match account
        .get_state::<Versions>()?
        .authorize(signers, *nonce_authority)
    {
        Ok(versions) => account.set_state(&versions),
        Err(AuthorizeNonceError::Uninitialized) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
        Err(AuthorizeNonceError::MissingRequiredSignature(account_authority)) => {
            ic_msg!(
                invoke_context,
                "Authorize nonce account: Account {} must sign",
                account_authority
            );
            Err(InstructionError::MissingRequiredSignature)
        }
    }
}
