### Title
Stale confirmations from deleted members count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`confirm` executes a request once `confirmations.len() + 1 >= num_confirmations`, but confirmation entries are only purged for requests **authored** by a deleted member, not for requests that member merely **confirmed**. A member who confirms request R1 and is later removed via `DeleteMember` on a different request R2 leaves a stale entry in `confirmations[R1]`, letting fewer live members than `num_confirmations` execute R1.

### Finding Description
The broken binding: distinct *live* members who confirmed R1 should equal `num_confirmations` before execution, i.e. `|{m in confirmations[R1] : m ∈ self.members}| == num_confirmations`. In practice the code checks only `confirmations.len() + 1 >= num_confirmations` [1](#0-0) , which is a raw count of stored strings, not a count of currently-live members.

Root cause is in `delete_member`: when a member is removed, only requests **authored** by that member are purged via the filter `r.member == member` [2](#0-1) . Confirmations that member made on requests authored by *other* members are never touched, because `delete_member` never scans `self.confirmations` for entries containing the removed member's string identifier. `self.members.remove(&member)` on line 374 removes them from live members, but their stale string stays inside the `HashSet<String>` for any other request they confirmed [3](#0-2) .

Exploit flow:
1. Member A calls `add_request` creating R1 (e.g. `Transfer` or `AddKey`).
2. Mallory (current `MultisigMember::Account`) calls `confirm(R1)`, inserting her identifier into `confirmations[R1]` (not yet reaching threshold).
3. A majority of the *remaining* live members create/confirm a separate request R2 containing `DeleteMember { member: mallory }`, which executes and removes mallory from `self.members`, but `confirmations[R1]` is untouched since R1's author is A, not mallory.
4. Any other live member C calls `confirm(R1)`. `confirmations.len()` is now 2 (mallory + C), satisfying `+1 >= num_confirmations` for a 2-of-n or higher multisig where the real live-confirmer count is only 1.
5. `execute_request` runs the `Transfer`/`AddKey`/etc. action with only one genuinely live confirming member, violating the multisig's `num_confirmations` guarantee.

None of the existing guards (`assert_valid_request`, `assert_self_request`, `assert_one_action_only`) check membership of the *confirmers* already recorded in `confirmations[request_id]`; they only validate the request exists and the *current* caller is a member.

### Impact Explanation
An attacker (or a departing/compromised former member) can get contract funds transferred, a full access key added, or other privileged self-actions executed with effectively fewer live confirmations than `num_confirmations` requires. This directly matches the Critical category: "a multisig request executed below `num_confirmations` live members." This is repeatable for every request that a soon-to-be-removed member confirms before its execution, across any multisig contract instance using this code.

### Likelihood Explanation
Preconditions are simple and require no special privilege beyond being (or briefly being) a legitimate multisig member: a member confirms a request, is later removed by other members, and the original request still has enough stale+live confirmations to cross the threshold. This can occur naturally during routine member rotation (e.g., a key holder leaving the company) without any malicious intent from the remaining members, making it highly feasible and low-cost to trigger, whether intentionally by a rogue confirmer or accidentally through normal governance.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests authored by that member) and strip the removed member's identifier from every confirmation set; alternatively, change `confirm`'s threshold check to count only confirmers still present in `self.members` at execution time (i.e., filter `confirmations` against current `self.members` before comparing to `num_confirmations`).

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_after_member_removal_executes_below_threshold() {
    // Setup: contract with members [A, B, mallory, C], num_confirmations = 2
    // A creates R1: Transfer to some receiver (not requiring assert_self_request)
    testing_env!(context_with_account(a(), amount));
    let mut c = MultiSigContract::new(vec![
        MultisigMember::Account { account_id: a() },
        MultisigMember::Account { account_id: b() },
        MultisigMember::Account { account_id: mallory() },
        MultisigMember::Account { account_id: cee() },
    ], 2);

    let r1 = c.add_request(MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    });

    // mallory confirms R1 (not enough yet, count=1 < 2)
    testing_env!(context_with_account(mallory(), amount));
    c.confirm(r1);
    assert!(c.confirmations.get(&r1).unwrap().contains(&mallory_member().to_string()));

    // Majority deletes mallory via a separate request R2 (self-request, DeleteMember)
    testing_env!(context_with_account(a(), amount));
    let r2 = c.add_request(MultiSigRequest {
        receiver_id: alice_current_account(), // == current_account_id
        actions: vec![MultiSigRequestAction::DeleteMember { member: mallory_member() }],
    });
    testing_env!(context_with_account(b(), amount));
    c.confirm(r2); // executes since 2 live confirmations (A+B) reach threshold

    // BINDING CHECK 1: mallory removed from live members
    assert!(!c.get_members().contains(&mallory_member()));
    // BINDING CHECK 2: stale confirmation for R1 still present
    assert!(c.confirmations.get(&r1).unwrap().contains(&mallory_member().to_string()));

    // C confirms R1: only C is a genuinely live new confirmer, but count reaches 2 (mallory+C)
    testing_env!(context_with_account(cee(), amount));
    c.confirm(r1); // this executes execute_request (Transfer) despite only 1 live confirmer

    // R1 was removed/executed
    assert!(c.list_request_ids().iter().find(|&&id| id == r1).is_none());
    // Demonstrates execution occurred with only 1 live confirming member vs num_confirmations=2
}
```
This test demonstrates that `execute_request` for R1 fires using one stale (`mallory`, no longer a member) plus one genuinely live confirmation (`cee`), violating the `num_confirmations` live-member guarantee.
