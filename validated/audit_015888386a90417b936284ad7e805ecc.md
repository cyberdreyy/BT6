### Title
ERC4626 deposit-cap exhaustion blocks borrower repayment and can force a false default - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary

`ProgrammableBorrower` treats depositing into its configured ERC4626 vault as an infallible part of repayment and epoch-start accounting. `_depositToVault` calls `vault.deposit` without checking `maxDeposit` or catching a deposit-capacity failure. [1](#0-0)  An unprivileged depositor in that external vault can consume the remaining capacity during a running epoch, causing an honest borrower’s `repay(0)` transaction to revert and leaving `borrowerPrincipal` recorded as unpaid. [2](#0-1)  A subsequent close-pool `stopEpoch(..., 1)` interprets the remaining borrower ledger entry as a real default, pausing the CDO and disabling withdrawal requests. [3](#0-2) [4](#0-3) 

### Finding Description

`repay` and `executeRepay` both enter `_repay`, which pulls repayment assets from the borrower and updates `borrowerPrincipal`, `borrowerInterestDebt`, and `borrowerInterestAccrued`. [5](#0-4) [2](#0-1)  The function documents that funds received while an epoch is active are redeployed into the ERC4626 vault before returning. [6](#0-5)  The partial-repayment path demonstrates this behavior by calling `_depositToVault` after updating the ledger. [7](#0-6) 

ERC4626 explicitly permits a vault to impose a per-receiver deposit limit through `maxDeposit`. [8](#0-7)  The same interface specifies that `deposit` must revert when all assets cannot be deposited, including because a deposit limit was reached. [9](#0-8)  `_depositToVault` performs no `maxDeposit` check, no partial deposit, and no `try/catch`, so a compliant external vault can revert the entire repayment transaction after capacity has been consumed by a third party. [1](#0-0) 

The same unchecked deposit also exists in `onStartEpoch`, where all idle underlying held by the borrower adapter is deposited before epoch accounting is enabled. [10](#0-9)  `IdleCDOEpochVariant.startEpoch` calls this hook after transferring funds to the borrower adapter, so a vault deposit revert also prevents the epoch from starting. [11](#0-10) 

The more serious path is repayment during a running programmable epoch. Once `epochAccountingActive` is true, the vault cannot be replaced through `setVault`. [12](#0-11)  If an external vault user fills the remaining deposit capacity, the honest borrower cannot clear `borrowerPrincipal` through `repay`; when management later requests all funds, `onStopEpoch` returns `false` solely because that borrower-debt ledger is still nonzero. [3](#0-2)  `IdleCDOEpochVariant` treats this `false` result as borrower default. [4](#0-3) 

### Impact Explanation

A third-party ERC4626 depositor can prevent a willing borrower from recording repayment and thereby cause a solvent facility to be marked `defaulted`. `_handleBorrowerDefault` pauses the CDO, marks the epoch stopped, and disables AA and BB withdrawal requests. [13](#0-12)  For example, with 10,000 USDC in the pool and 1,000 USDC drawn by the borrower, a saturated vault makes `repay(0)` revert, preserves the 1,000 USDC `borrowerPrincipal`, and causes `stopEpoch(0, 1)` to default and freeze the full pool pending recovery or operator intervention. [14](#0-13) [15](#0-14) 

The existing stop-epoch liquidity handling only wraps `vault.withdraw` failures and does not protect the separate `vault.deposit` dependency used by repayment. [16](#0-15) 

### Likelihood Explanation

The issue requires programmable-borrower mode and an ERC4626 vault with a finite or dynamic deposit limit. Any ordinary depositor in that vault can consume its remaining capacity; the attacker does not need a protocol role, borrower permission, KYC status, or control over the manager. [17](#0-16)  The required capital is the vault’s remaining `maxDeposit`, which may be small near a cap, and the attacker may later withdraw from the external vault. [8](#0-7) 

The impact is not guaranteed permanent because operators may be able to run a normal epoch stop, unwind the vault position, or configure a different vault after accounting becomes inactive. Nevertheless, while the cap remains saturated, borrower repayment and epoch restart are blocked, and a close-pool call can unnecessarily enter the default path. [18](#0-17) [19](#0-18) 

### Recommendation

Do not make repayment accounting depend on a successful ERC4626 deposit. In `_depositToVault`, read `vault.maxDeposit(address(this))`, deposit at most the available amount, and leave any excess underlying idle in `ProgrammableBorrower`. [20](#0-19)  The deposit should also be wrapped in `try/catch` because `maxDeposit` can become stale inside a composed transaction. [9](#0-8) 

For `repay`, the token transfer and borrower-debt ledger updates should remain committed even when vault redeployment is unavailable; failed redeployment should leave cash on hand instead of reverting the repayment. [2](#0-1)  For `onStartEpoch`, deposit only the currently accepted amount and retain the remainder as idle underlying so epoch startup is not bricked by a deposit cap. [21](#0-20)

contract CappedDepositVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public immutable depositCap;

  constructor(address _asset, uint256 _depositCap)
    ERC20("Capped Vault", "CAP")
  {
    assetToken = IERC20Detailed(_asset);
    depositCap = _depositCap;
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function totalAssets() public view returns (uint256) {
    return assetToken.balanceOf(address(this));
  }

  function convertToAssets(uint256 shares) external pure returns (uint256) {
    return shares;
  }

  function maxDeposit(address) public view returns (uint256) {
    uint256 held = totalAssets();
    return held >= depositCap ? 0 : depositCap - held;
  }

  function deposit(uint256 assets, address receiver)
    external
    returns (uint256 shares)
  {
    require(assets <= maxDeposit(receiver), "deposit-cap");
    assetToken.transferFrom(msg.sender, address(this), assets);
    shares = assets;
    _mint(receiver, shares);
  }

  function withdraw(uint256 assets, address receiver, address owner)
    external
    returns (uint256 shares)
  {
    shares = assets;
    if (msg.sender != owner) {
      _spendAllowance(owner, msg.sender, shares);
    }
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }

  function redeem(uint256 shares, address receiver, address owner)
    external
    returns (uint256 assets)
  {
    assets = shares;
    if (msg.sender != owner) {
      _spendAllowance(owner, msg.sender, shares);
    }
    _burn(owner, shares);
    assetToken.transfer(receiver, assets);
  }
}

function testProgrammableBorrowerRepayBlockedByExternalVaultDepositCap()
  external
{
  uint256 amount = 10_000 * oneScale;
  uint256 drawAmount = 1_000 * oneScale;
  address griefer = makeAddr("externalVaultDepositor");

  // Keep enough headroom for epoch startup, but make the remaining cap fillable.
  CappedDepositVault cappedVault =
    new CappedDepositVault(USDC, amount + 2_000 * oneScale);

  vm.prank(manager);
  programmableBorrower.setVault(address(cappedVault));

  vm.prank(owner);
  cdoEpoch.setIsInterestMinted(true);

  idleCDO.depositAA(amount);
  _startEpochAndCheckPrices(0);

  // The honest borrower draws part of the facility.
  vm.prank(revolvingBorrower);
  programmableBorrower.borrow(drawAmount);

  // An unprivileged user of the ERC4626 vault consumes all remaining capacity.
  uint256 remainingCap =
    cappedVault.maxDeposit(address(programmableBorrower));
  deal(USDC, griefer, remainingCap, true);

  vm.startPrank(griefer);
  underlying.approve(address(cappedVault), remainingCap);
  cappedVault.deposit(remainingCap, griefer);
  vm.stopPrank();

  assertEq(
    cappedVault.maxDeposit(address(programmableBorrower)),
    0,
    "deposit cap should be exhausted"
  );

  // The borrower has enough assets and allowance to repay everything.
  uint256 owed =
    drawAmount + programmableBorrower.borrowerInterestOwedNow();
  deal(USDC, revolvingBorrower, owed, true);

  // Repayment reverts because the forced vault redeposit exceeds maxDeposit.
  vm.prank(revolvingBorrower);
  vm.expectRevert(bytes("deposit-cap"));
  programmableBorrower.repay(0);

  assertEq(
    programmableBorrower.borrowerPrincipal(),
    drawAmount,
    "repayment should not be credited"
  );

  // Close-pool settlement interprets the still-recorded debt as a default.
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 1);

  assertTrue(cdoEpoch.defaulted(), "false borrower default");
  assertTrue(cdoEpoch.paused(), "pool should be paused");
}
