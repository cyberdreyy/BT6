Confirmed same pattern exists in both `multisig` (v1, DeleteKey) and `multisig2` (DeleteMember). Both purge only requests *authored* by the removed key/member, but never scan `self.confirmations` to strip that key/member's stale confirmation entries from other requests they had confirmed. Since `confirm()` only compares `confirmations.len()` against `num_confirmations`, a stale confirmation left behind by a deleted signer still counts toward the threshold, letting a request execute (Transfer, AddKey/AddMember, DeployContract, FunctionCall) with strictly fewer live, authorized approvers than the configured threshold.

### Title
Stale confirmations from deleted multisig keys/members are not purged, allowing execution below the configured confirmation threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`DeleteKey` (multisig v1) and `DeleteMember` (multisig2) remove the departing signer/member from the member set and delete *requests they authored*, but do not remove their prior confirmations recorded on requests authored by other members. `confirm()` only checks the size of the confirmations set, so a stale confirmation from an already-removed key/member still counts toward `num_confirmations`, letting a request execute with fewer currently-authorized approvers than required.

### Finding Description
In `multisig/src/lib.rs`, the `DeleteKey` branch of `execute_request` (lines 198-216) removes `requests` and `confirmations` only for requests where `r.signer_pk == pk` (i.e. requests the removed key itself created): [1](#0-0) 

It never inspects the `confirmations` map for entries where the removed public key appears as a *confirmer* on requests authored by someone else. The equivalent logic in multisig2's `delete_member` has the same gap: [2](#0-1) 

`confirm()` in both contracts determines execution purely from the cardinality of the confirmations set: [3](#0-2) [4](#0-3) 

The binding that should hold is: `count(confirmations authored by currently-live members) >= num_confirmations` before a request executes. Because stale confirmations are never purged when a key/member is removed, the actual invariant enforced is `count(confirmations, including entries from removed members) >= num_confirmations`, which is weaker and can be satisfied by fewer live approvers than intended.

### Impact Explanation
This is a Critical-class impact per the rubric: "a multisig request executed below threshold." An attacker (or a departing/compromised member who confirms pending requests before being removed) can cause `Transfer`, `AddKey`/`AddMember`, `DeployContract`, or `FunctionCall` actions to execute with less than `num_confirmations` live approvals, breaking the multisig custody guarantee that funds/keys can only move with `K`-of-`N` live authorization.

### Likelihood Explanation
This requires a normal governance sequence already supported by the contract's own API (member confirms a pending request, then that same member/key is later removed via a separate `DeleteKey`/`DeleteMember` request) — no owner or foundation privilege beyond what any member already has is required, and no malicious redeploy or external actor is needed. Any member who confirms a request and is later removed (e.g., due to key rotation or an employee departure) leaves an exploitable stale confirmation, making this readily reachable through the existing state machine.

### Recommendation
When deleting a key/member, iterate all entries in `self.confirmations` and remove the departing signer's public key (or member identity) from every confirmation set, not just from requests they authored themselves.

### Proof of Concept
1. Multisig configured with `num_confirmations = 2`, members `{A, B, C}`.
2. Member `A` creates request `R` (`add_request`), does not confirm it.
3. Member `B` calls `confirm(R)` → `confirmations[R] = {B}` (1 confirmation, below threshold).
4. Members submit and confirm a separate `DeleteKey`/`DeleteMember` request removing `B` (reaching threshold with live members, e.g. `A` and `C`); it executes: `B` is removed from `members`/keys, but `confirmations[R]` is untouched because `R` was authored by `A`, not `B`.
5. Member `C` calls `confirm(R)` → `confirmations[R].len() == 1` (stale `B`) `+ 1 (C) == 2 >= num_confirmations` → `R` executes.
6. Result: request `R` executed with only one currently-live approver (`C`), even though the contract is configured to require two live approvers — the multisig executed a request below its authorized threshold. [1](#0-0) [5](#0-4) [2](#0-1) [4](#0-3)
