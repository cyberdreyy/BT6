### Title
Redeem "solve" path in `ProvisionerV2` reverts if `request.receiver` is a blacklisted address on the payment token, unlike the equivalent refund path which has a fallback - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2._solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` transfer the redeemed payment token directly to `request.receiver` via a plain `token.safeTransfer(request.receiver, ...)` when a redeem request is solved before its deadline [1](#0-0) . This mirrors the disclosed Dinari `SellOrderProcessor._cancelOrderAccounting` bug: if the payment token (e.g. a blacklist-capable stablecoin such as USDC/USDT) restricts transfers to `request.receiver`, the transfer reverts and the whole `solveRequestsVault` batch transaction reverts with it. Notably, every *refund* path (`refundRequest`, `cancelRequest`, and the "deadline passed" branches of the solve functions) already uses `_transferWithFallback`, which falls back to sending funds to the original requester if the transfer to `receiver` fails [2](#0-1) . The "solved" branch for redeems is the one code path that was not given this same protection.

### Finding Description
A user calls `requestRedeem(token, unitsIn, minTokensOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver)` specifying an arbitrary `receiver` address [3](#0-2) . Later, when a guardian/solver calls `solveRequestsVault`, and the request's deadline has not yet passed, `_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice` first `exit`s the vault (burning units, pulling tokens into the provisioner) and then attempts `token.safeTransfer(request.receiver, tokenOutAfterTip)` [4](#0-3)  or `token.safeTransfer(request.receiver, request.tokens)` [5](#0-4) . If `receiver` is blacklisted by the underlying token (e.g. USDC/USDT compliance blacklist), this transfer reverts and unwinds the entire transaction — including the `exit` call and any other, unrelated requests batched in the same `solveRequestsVault` call.

By contrast, the deadline-passed ("refund") branches for the exact same functions call `_transferWithFallback`, which sends to `receiver` if possible but silently falls back to the original requester on failure [6](#0-5) , and the same protective pattern is used by `refundRequest`/`cancelRequest` via `_clearHashAndTransferRefund` [7](#0-6) . `solveRequestsDirect`'s peer-to-peer redeem path has the analogous gap too: it does `token.safeTransferFrom(msg.sender, request.receiver, request.tokens)` with no fallback [8](#0-7) .

### Impact Explanation
For the specific redeem request with a blacklisted receiver, the "solve while not expired" path can never succeed via either `solveRequestsVault` or `solveRequestsDirect` — every attempt reverts. If bundled with other unrelated requests in the same `solveRequestsVault` batch call, this also blocks those other users' requests from being solved in that batch until the guardian identifies and excludes the offending request, a temporary freeze of solving/yield realization for affected requests. However, unlike the original Dinari finding, funds are not permanently stuck: the user (or an authorized caller) can still recover the escrowed vault units through `cancelRequest` (if `redeemCancellationsEnabled`) or `refundRequest` after the deadline, both of which use `_transferWithFallback` and correctly route funds back to the requester if the receiver transfer fails.

### Likelihood Explanation
This requires: (1) a redeem request whose `receiver` differs from `request.user` and is (or later becomes) blacklisted on the settlement token, and (2) that request being included in a `solveRequestsVault` batch before its deadline. Since `receiver` is a caller-supplied, unchecked parameter at request-creation time, and stablecoins like USDC/USDT are realistic deployed settlement assets with compliance blacklists, this is plausible but depends on the guardian's batching behavior and on a third party blacklisting the address — it is not solely user-triggerable to cause fund loss, only request-specific DoS of the "solve-before-deadline" path and potential temporary batch-level DoS.

### Recommendation
Use `_transferWithFallback` (or an equivalent try/fallback-to-requester pattern) for the payment-token transfer in the "solved" (deadline not yet passed) branches of `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice`, and similarly guard the redeem-side transfer in `_solveRequestDirect`, so a single blacklisted/restricted receiver cannot revert an entire solve batch or block the peer-to-peer solve path.

### Proof of Concept
Not independently constructed as a full Foundry PoC in this pass — the mechanism (plain `safeTransfer`/`safeTransferFrom` to `request.receiver` without a fallback in the redeem-solve branches, versus the `_transferWithFallback` protection used everywhere else) is confirmed by direct code inspection: [1](#0-0)  and [5](#0-4)  versus [2](#0-1) . A PoC would deploy a mock ERC20 with a blacklist hook (reverting `transfer`/`transferFrom` to a flagged address), set it as the redeem token in `ProvisionerV2`, call `requestRedeem(..., receiver = blacklistedAddress)`, blacklist that address, then call `solveRequestsVault`/`solveRequestsDirect` and assert the call reverts, while confirming `cancelRequest`/`refundRequest` for the same request still succeed and correctly fall back to the original requester.

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
