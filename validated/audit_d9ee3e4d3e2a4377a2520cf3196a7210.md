### Title
Multisig executes requests using stale confirmations from removed members, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
The `confirm()` function counts confirmation entries stored per-request without verifying that each confirming party is still a current member of the multisig. `delete_member()` only purges confirmations/requests that were *originated* by the removed member, not confirmations that member *cast* on other, still-pending requests. This lets a request execute with fewer than `num_confirmations` live/authorized approvals.

### Finding Description
`confirm()` accumulates confirmations into a `HashSet<String>` keyed by request id and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

Membership removal is implemented in `delete_member()`, which only cleans up requests where `r.member == member` (i.e., requests *added* by the removed member) and the associated `num_requests_pk` counter: [2](#0-1) 

It does **not** scan `self.confirmations` for entries where the removed member's identity string appears as a confirmer on *other* pending requests (requests added by a different member). Those stale confirmations remain in the `HashSet<String>` and continue to count toward the `num_confirmations` threshold check in `confirm()`.

The binding that should hold is:
```
confirmations_counted_toward_threshold(request) ⊆ live_members
```
After a `DeleteMember` action executes (itself requiring `num_confirmations` approvals, so it is reachable through the normal multisig flow — not solely an owner/privileged action but any coalition of members that can reach quorum), any request that already collected a confirmation from the now-removed member keeps that confirmation counted. If enough of the *remaining* live members confirm afterward, the sum (stale confirmation + live confirmations) can reach `num_confirmations` even though the number of currently-live approvers is one less than `num_confirmations`.

`assert_valid_request()` (referenced in `confirm()`/`delete_request()`) and `current_member()` only check that the *new* confirming caller is a current member; they never re-validate the previously stored confirmation set against current membership.

### Impact Explanation
This breaks the core custody guarantee of a K-of-N multisig: "a multisig request executed below threshold," which is explicitly a Critical-severity outcome (funds moved, keys added, or contract code deployed via `Transfer`, `AddKey`, `FunctionCall`, `DeployContract`, etc., in `MultiSigRequestAction`) without the intended number of *live* member approvals. Because `Transfer`, `AddKey` (full access key), `FunctionCall`, and `DeployContract` are all `MultiSigRequestAction` variants executable through `confirm()`, an attacker scenario is: a member confirms a high-value `Transfer` request, is later removed for being compromised/malicious, but their confirmation is never invalidated — the transfer can still execute using their stale approval combined with fewer newly-live confirmations than the configured threshold.

### Likelihood Explanation
The bug is triggered by the ordinary member-removal workflow (`DeleteMember` executed via normal multisig consensus) combined with any pre-existing pending request that the removed member had already confirmed. No special privilege beyond normal multisig membership is required to create/confirm requests, and member removal is a documented, expected operation (e.g., removing a compromised key). The condition is easy to hit unintentionally (rotating keys/members while requests are in flight) and can also be deliberately engineered by a soon-to-be-removed or malicious member who confirms multiple pending requests before being removed, "banking" votes that outlive their membership.

### Recommendation
When executing `delete_member()`, iterate all entries in `self.confirmations` (not just requests keyed by `r.member == member`) and remove the departing member's identity string from every confirmation set; alternatively, re-validate the confirmation set against `self.members` inside `confirm()`'s threshold check before comparing against `num_confirmations`, filtering out confirmations from accounts/keys that are no longer members.

### Proof of Concept
1. Initialize `MultiSigContract::new(members=[A,B,C], num_confirmations=2)`.
2. Member `B` calls `add_request` for a `Transfer` (created by `B`).
3. Member `A` (not the request author) calls `confirm(request_id)` — confirmations set = `{A}`, size 1 < 2, no execution yet.
4. Members reach quorum on a separate `DeleteMember{member: A}` request and it executes via `confirm()` → `execute_request()` → `delete_member()`. Since the pending Transfer request was authored by `B`, not `A`, `delete_member()`'s filter `r.member == member` does not match it, so the Transfer request and its confirmations (`{A}`) survive untouched, and `A` is removed from `self.members`.
5. Member `B` (now the only truly live confirmer besides the stale one) calls `confirm(request_id)` on the Transfer request. `confirmations.len() as u32 + 1` = `1 + 1 = 2 >= num_confirmations(2)` → the Transfer executes, funded by one live confirmation (`B`) plus one stale confirmation from the now-removed `A`, i.e., executed with only 1 of 2 required *live* approvals.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
