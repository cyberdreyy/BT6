### Title
Stale parent-tenure-choice permit allows a signer to sign a now-invalid reorg tenure-change block - (File: `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/chainstate/v1.rs`, `stacks-signer/src/chainstate/v2.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` decides, once, whether a tenure-change block is allowed to reorg an intervening tenure (permitted only if the reorged tenure has ≤1 globally-accepted block, or was proposed too close to the burn-block transition). This check runs only at proposal time (`check_proposal` in v1, `validate_tenure_change_payload` in v1/v2). The re-check that runs immediately before a signature is actually produced, `check_block_against_signer_db_state`, never calls `check_parent_tenure_choice` again — it only re-verifies `check_tenure_change_confirms_parent` / `check_latest_block_in_tenure`. If the reorged tenure gains a second globally-accepted block during the (potentially long) window between proposal/validation and the pre-commit threshold being crossed, the reorg permit is stale, yet the signer still signs.

### Finding Description
`check_parent_tenure_choice` is the sole gate on whether a tenure-change block's chosen parent tenure is a legitimate reorg: [1](#0-0) 

It is invoked from proposal-time validation only: [2](#0-1) [3](#0-2) 

The signature-producing path re-checks chainstate before signing, but this re-check function only calls the parent-confirmation and latest-block-in-tenure checks, never `check_parent_tenure_choice`: [4](#0-3) 

and that re-check is exactly what gates producing the actual signature at the pre-commit threshold: [5](#0-4) 

As documented, the window between validation and threshold-crossing is explicitly non-trivial and other state can move in the meantime: [6](#0-5) 

The eligibility rule itself is time-of-check: a reorg is permitted only if the tenure being reorged has at most one globally accepted block at the moment `check_parent_tenure_choice` runs: [1](#0-0) 

If, between proposal time and the moment pre-commit weight crosses 70%, that intervening tenure receives a second globally-accepted block (e.g., because a slow/partitioned segment of the network kept extending it, or gossip of the newer proposal was delayed to some signers), the permit granted at proposal time is stale: re-running `check_parent_tenure_choice` at that later moment would now return `false`. But because the pre-sign re-check (`check_block_against_signer_db_state`) never re-invokes `check_parent_tenure_choice`, the signer proceeds to sign anyway once other pre-commits push the weight over threshold.

### Impact Explanation
This lets a one-slot miner (with ordinary gossip-timing variance, no majority of signers needed) obtain a valid signer signature over a tenure-change block whose reorg is, by the signer's own rule, no longer legitimate at signing time — i.e., a signer signs a non-canonical/invalid reorg. This breaks the "approved-parent vs canonical" equality that `check_parent_tenure_choice` exists to enforce, matching the Critical impact class: a signer signing an invalid or non-canonical block.

### Likelihood Explanation
The pre-commit threshold is reached asynchronously via StackerDB gossip and can take a non-trivial amount of time (docs explicitly call out that state, including signed blocks, "may have changed materially" in this window). No majority collusion or key compromise is required — only ordinary timing where the reorged tenure gains a second globally-accepted block after this proposal was validated/pre-committed but before threshold weight is reached. This is a naturally occurring race under normal network conditions, not a contrived edge case.

### Recommendation
Re-run `check_parent_tenure_choice` (or an equivalent freshness check of the reorg permit) inside `check_block_against_signer_db_state`/`check_block_against_signer_db_state`'s tenure-change branch, immediately before a signature is produced (both at validate-ok time and at the pre-commit-threshold signing point), analogous to how `check_tenure_change_confirms_parent` is already re-verified there.

### Proof of Concept
1. Sortition history: tenure T1 (canonical) → T_mid (intervening sortition, currently 0 or 1 globally-accepted blocks) → T2 (new miner's sortition).
2. Miner of T2 proposes a tenure-change block whose `prev_tenure_consensus_hash` points at T1, reorging T_mid. At this moment `check_parent_tenure_choice` (called from `validate_tenure_change_payload`) sees `globally_accepted_blocks(T_mid) <= 1` and returns `true`; the proposal passes `check_proposal` and is submitted for validation, then pre-committed to by signers as pre-commits trickle in.
3. Before pre-commit weight crosses the 70% threshold, a second block in T_mid becomes globally accepted network-wide (e.g., a slower segment of signers/miners kept building T_mid, unaware of/slower to adopt T2's competing proposal). Now `globally_accepted_blocks(T_mid) == 2`, so re-running `check_parent_tenure_choice` at this instant would return `false` (see `stacks-signer/src/chainstate/mod.rs` lines 210-223).
4. A signer whose local pre-commit tally now crosses threshold calls `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs` lines 1803-1841) before signing; this function only re-verifies `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure`, not `check_parent_tenure_choice`, so it returns `None` (no rejection).
5. The signer proceeds to sign the tenure-change block (`stacks-signer/src/v0/signer.rs` lines 1345-1366 falls through to signing), producing a valid signature over a tenure-change block that reorgs a tenure which, by the signer's own stated rule, should no longer be reorgable.
