### Title
Buffer-period deposits ignore stale programmable-borrower vault losses and overmint tranche shares - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
In programmable-borrower mode, a KYC-passing lender can deposit during the buffer period after the external ERC4626 position has lost value but before `startEpoch` snapshots that loss into `bufferedVaultDelta`. The deposit is priced from the CDO’s one-to-one `IdleCreditVault` receipt balance, so the attacker receives tranche shares at the pre-loss price and shifts part of the already-incurred vault loss to existing tranche holders.

### Finding Description
`depositAA`/`depositBB` route through `_deposit`, which calls `_updateAccounting` and then mints shares at the current tranche price [1](#0-0) . For the credit-vault implementation, `getContractValue` values the CDO’s `strategyToken` balance directly rather than the programmable borrower’s live ERC4626 asset value [2](#0-1) .

That accounting is stale during the buffer period. `ProgrammableBorrower.onStopEpoch` stores the post-stop vault position in `bufferStartVaultAssets`, but the resulting buffer gain or loss is only measured when `onStartEpoch` later computes `bufferedVaultDelta = currentVaultAssets - bufferStartVaultAssets` [3](#0-2) [4](#0-3) . Deposits remain available while the pool is unpaused between epochs, and no deposit path calls `totalInterestDueNow`, `vaultLoss`, or otherwise refreshes the pending buffer delta [5](#0-4) .

Consequently, if the vault loses 10% during the buffer, an attacker can deposit at tranche prices that still assume the old strategy-token backing. At the next `startEpoch`, the loss is carried into `bufferedVaultDelta`; at the following `stopEpoch`, `totalInterestDueNow` subtracts it from pool-facing yield [6](#0-5) . The attacker’s newly minted shares participate in the post-loss share base even though the deposit occurred after the economic loss.

### Impact Explanation
This violates fair minting and causes direct value transfer from existing tranche holders to the late depositor. If pre-deposit TVL is `T` and the unrecognized vault loss is `L`, an attacker deposit of `D` is minted using approximately `T` instead of `T - L` as backing. When `L` is later recognized, the attacker bears only their pro-rata share of the old loss instead of entering at the already-reduced price.

For example, with `T = 1,000,000`, an unrecognized `L = 100,000`, and a price near `1.0`, an attacker depositing `D = 100,000` receives shares for about 10% of the enlarged pool rather than about 11.11% of the true `900,000` pre-deposit NAV. The excess share allocation dilutes existing holders’ recovery of the `100,000` loss; roughly `9,000` underlying-equivalent value is transferred to the attacker in this simple case.

### Likelihood Explanation
A KYC-passing lender can perform the deposit, and vault losses do not require a privileged action. The sequence only requires the vault to suffer a material loss during the buffer window and the attacker to deposit before the owner or manager starts the next epoch. Existing guards do not prevent it: deposits are intentionally enabled during the buffer, `skipDefaultCheck` is not set, `defaulted` remains false, and `_updateAccounting` only sees unchanged `IdleCreditVault` receipt balances [7](#0-6) [8](#0-7) .

The issue is limited to programmable-borrower deployments where undrawn funds remain in the ERC4626 vault across the buffer period. It also requires enough buffer time for a material vault loss and for the attacker to observe it.

### Recommendation
Refresh programmable-borrower buffer PnL before pricing buffer-period deposits and withdrawal requests. For example, expose a non-mutating valuation that includes `bufferedVaultDelta`/current buffer delta in the CDO’s managed NAV, or add a borrower hook that checkpoints `currentVaultAssets - bufferStartVaultAssets` before every deposit. After refreshing, mint tranche shares using the loss-adjusted NAV. The same refreshed value should be used for `requestWithdraw` so exiting users cannot crystallize stale pre-loss prices either.

### Proof of Concept
A reproducible Foundry fork test should:

```solidity
// Arrange an existing programmable-borrower credit vault with at least one AA LP.
uint256 initialDeposit = 1_000_000e6;
idleCDO.depositAA(initialDeposit);

// Manager starts and later stops epoch 0.
cdoEpoch.startEpoch();
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpoch(0, 0);

// Enter the buffer period. At this point PB.bufferStartVaultAssets() > 0.
uint256 shares = morphoVault.balanceOf(address(programmableBorrower));
uint256 baselineAssets = morphoVault.convertToAssets(shares);

// Cause or use an actual MetaMorpho loss. In a forked-fork test this can be
// produced through the underlying market; in a mock harness it is applyLoss().
uint256 loss = baselineAssets / 10;
vault.applyLoss(loss);

uint256 currentAssets = morphoVault.convertToAssets(shares);
assertEq(baselineAssets - currentAssets, loss);

// The CDO still prices shares from its unchanged strategy-token balance.
uint256 stalePrice = cdoEpoch.virtualPrice(address(aaTranche));

// KYC-passing attacker deposits after the vault loss but before startEpoch.
uint256 attackerDeposit = 100_000e6;
underlying.mint(attacker, attackerDeposit);
vm.startPrank(attacker);
underlying.approve(address(cdoEpoch), attackerDeposit);
uint256 minted = cdoEpoch.depositAA(attackerDeposit);
vm.stopPrank();

// Manager starts the next epoch, which snapshots the already-incurred loss.
cdoEpoch.startEpoch();
assertEq(
    programmableBorrower.bufferedVaultDelta(),
    -int256(loss)
);

// After another epoch and stop, the loss is charged against pool-facing yield.
vm.warp(cdoEpoch.epochEndDate() + 1);
uint256 due = programmableBorrower.totalInterestDueNow();
cdoEpoch.stopEpoch(0, 0);

// Compare the attacker's minted amount with a run that first checkpoints the
// buffer loss. The attacker should receive fewer shares under the fixed path.
uint256 fairSupplyBefore = aaTranche.totalSupply() - minted;
uint256 fairNavBefore = initialDeposit - loss;
uint256 fairMinted = attackerDeposit * fairSupplyBefore / fairNavBefore;
assertLt(fairMinted, minted);
```

The concrete fork implementation should use the repository’s `ProgrammableBorrowerCreditVault` fixture and a real MetaMorpho vault loss source rather than manipulating balances directly. The key assertion is that `depositAA` succeeds at `stalePrice` while `ProgrammableBorrower.onStartEpoch` subsequently encodes the negative `bufferedVaultDelta` that existed before the attacker’s deposit.

  function onStartEpoch(uint256 _pendingWithdraws) external nonReentrant {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // Reserve the amount IdleCDO expects to pull back at stopEpoch before the real borrower can draw again.
    epochPendingWithdraws = _pendingWithdraws;
    uint256 currentVaultAssets = _currentVaultAssets();
    uint256 bufferStartAssets = bufferStartVaultAssets;
    // Carry vault PnL generated while the pool was in the buffer into the new active epoch so it
    // is eventually realized in tranche prices at the next stopEpoch.
    bufferedVaultDelta = int256(currentVaultAssets) - int256(bufferStartAssets);
    bufferStartVaultAssets = 0;
    // Snapshot total assets before re-depositing idle cash so the epoch principal baseline uses the
    // exact pre-deposit amount instead of a post-deposit share-conversion round-down.
    uint256 startAssets = underlyingToken.balanceOf(address(this)) + currentVaultAssets;
    // Any idle balance left on the contract between epochs is parked immediately into the vault.
    _depositToVault(underlyingToken.balanceOf(address(this)), 0);
    // Reset the epoch accounting baseline from the exact pre-start total assets so the new epoch
    // does not treat the just-deposited idle balance as fresh vault profit or loss.
    epochStartVaultAssets = startAssets;
    epochDepositedToVault = 0;
    epochWithdrawnFromVault = 0;
    epochAccountingActive = true;
    emit EpochAccountingStarted(startAssets);

  function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
    return totalGain > loss ? totalGain - loss : 0;
  }

  /// @notice Compute the net vault delta split into interest and loss (mutually exclusive).
  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
