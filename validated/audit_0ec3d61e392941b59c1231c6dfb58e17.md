### Title
`claimInstantWithdrawRequest` pays instant receipts from other users' funded underlyings without validating the receipt was actually funded - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault.claimInstantWithdrawRequest` burns the caller's instant-withdrawal receipt tokens and pays `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`, without checking that the borrower ever funded that instant request through `collectInstantWithdrawFunds`, and without any epoch gate. This is the vault analog of the Linux HMM bug: the kernel code dereferenced `struct page` pointers that were only guaranteed valid while the notifier lock was held and the seqno was still valid. Here, the instant receipt is only a valid claim on strategy underlyings once the funding step has occurred; the claim path dereferences it unconditionally. `_transferFundedClaim` only protects the default-recovery reserve, so underlyings already collected via `collectWithdrawFunds` to back *normal* pending withdraw receipts are spendable by an instant claimant.

### Finding Description

The normal withdraw path has a validity gate: `_claimFundedWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest[_user]`, i.e., a receipt cannot be paid until the epoch that was supposed to fund it has ended (`IdleCreditVault.sol:326-328`). Instant receipts have no equivalent gate:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
        _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    _burn(_user, amount);
    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
}
```

`_transferFundedClaim` only enforces `balance - defaultRecoveryReserve >= amount` (`IdleCreditVault.sol:897-907`). `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls funds from the CDO (`IdleCreditVault.sol:398-403`), but the claim path never checks `pendingInstantWithdraws`, `instantWithdrawClaimsByEpoch`, or any per-epoch funded marker — the receipt is "dereferenced" without the funding guarantee that makes it valid.

### Impact Explanation

An unprivileged tranche holder can steal other users' already-funded withdraw claims. When a `stopEpoch` collects `pendingWithdraws` via `collectWithdrawFunds`, the strategy holds underlyings earmarked for normal receipt holders. An attacker calls `requestInstantWithdraw` and `claimInstantWithdrawRequest` (through `IdleCDOEpochVariant`) in the same transaction — no epoch wait, no funding requirement — and is paid at par out of those funded underlyings. Legitimate claimants' subsequent `claimWithdrawRequest` then reverts or underpays on the depleted balance. This breaks "one receipt one payout": the instant receipt is redeemed against funding that belongs to a different claim class. Loss is bounded by funded-but-unclaimed normal withdrawals (and prefunded amounts in the prefunded variant), which can be the entire pending withdrawal cohort.

### Likelihood Explanation

Only requires a whitelisted/KYC'd tranche holder (listed attacker class) to hold tranche tokens and observe a funded-but-unclaimed pending withdrawal window — a routine state after every `stopEpoch` until claimants act. No privileged role misbehavior is needed; owner/manager/borrower remain honest. The guard structure itself confirms the gap: the code went to the trouble of gating normal claims by epoch and of isolating the recovery reserve, but left instant claims payable against any non-reserve balance. One caveat I could not fully verify within available iterations: whether `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`getInstantWithdrawFunds` performs an equivalent funded check at the CDO layer before calling the strategy; if it does, the strategy-level gap is defense-in-depth rather than exploitable. A PoC should confirm by calling through the CDO entrypoint.

### Recommendation

Gate instant claims on actual funding, mirroring the normal-path epoch check:

- Record the request epoch for instant requests (already tracked in `instantWithdrawsRequestsByEpoch[_user][epochNumber]`) and only pay the portion whose epoch has been funded via `collectInstantWithdrawFunds`, or track a funded-vs-pending instant counter and cap claims at `min(instantWithdrawsRequests[_user], fundedInstantClaims[_user])`.
- Alternatively, have `collectInstantWithdrawFunds` move collected underlyings into an isolated accounting bucket (like `defaultRecoveryReserve`) that `_transferFundedClaim` cannot serve instant claims from.
