### Title
Paused ERC4626 vault blocks `stopEpoch`, forcing the borrower to keep accruing interest during the freeze - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` parks all facility liquidity in an external ERC4626 vault. When `IdleCDOEpochVariant.stopEpoch` runs, it calls `onStopEpoch`, which must pull any shortfall via `vault.withdraw`. If the external vault pauses withdrawals (e.g., a pausable ERC4626 like MetaMorpho during curator intervention, or any vault with `whenNotPaused` transfer guards), `vault.withdraw` reverts, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, and `stopEpoch` cannot complete. The epoch stays "running", `epochAccountingActive` remains true, and `borrowerInterestAccruedNow()` keeps accruing at `borrowerApr` on the drawn principal. The honest borrower is forced to pay interest for a period during which it was impossible to settle the epoch — the exact analog of the paused-NFT report where borrowers keep paying interest while a third-party pause blocks repayment.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol` (lines 395-408), `stopEpoch` calls `IProgrammableBorrower.onStopEpoch` and only proceeds to pull funds if it returns `true`; a revert bubbles up and aborts the whole stop.

In `contracts/strategies/idle/ProgrammableBorrower.sol` (lines 240-253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true; // insolvency → default path
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable(); // covered-but-paused → retryable
  }
}
```

The retryable design handles transient liquidity failures, but nothing stops the interest clock. `_accrueBorrowerInterest` computes `borrowerInterestAccruedNow()` as `principal * borrowerApr * elapsed`, so every second the vault remains paused extends the epoch and mints additional borrower debt. Only when the vault unpauses can `stopEpoch` succeed — or, if the pause is permanent, `emergencyExitVault` (owner/manager) is the only escape and it also reverts on a paused `redeem`.

Contrast with `onDefault` (lines 289-300), which deliberately avoids `convertToAssets` "even if the external vault's valuation view is unavailable during stress" — the codebase already recognizes that vault unavailability is a hazard, but the pause case still leaves the borrower accruing contractual APR with no way to close the epoch.

### Impact Explanation
Quantified loss = `borrowerPrincipal * borrowerApr * pauseDuration`. With a 365% APR configuration and a multi-day external-vault pause, the borrower owes days of extra interest it could not avoid, since `stopEpoch` is the only path that snapshots `epochEndDate` accounting and the borrower cannot unilaterally stop the epoch. The extra interest is eventually either paid by the borrower (unfair charge, matching the reported bug's "borrowers are still forced to pay the interest") or, if it pushes the position past recoverable value, contributes to a default that socializes the loss onto tranche holders BB-first. Funds are also temporarily frozen for all tranche holders with pending withdraw requests for the pause duration.

### Likelihood Explanation
The analog requires only that the whitelisted external ERC4626 vault pauses `withdraw`/`redeem` — an unprivileged, realistic third-party condition (the report itself demonstrates mainstream NFTs with `whenNotPaused` transfer guards; many ERC4626 vaults including MetaMorpho can enter states where `maxWithdraw` is capped or redemptions revert). No privileged attacker is needed; any user of the programmable borrower's vault sleeve is affected. The catch block explicitly anticipates this failure mode (`StopEpochVaultLiquidityUnavailable`), confirming it is reachable; the gap is that the borrower's APR keeps running through the freeze with no compensation or cap mechanism.

### Recommendation
- Cap `borrowerInterestAccruedNow` accrual at `epochEndDate`, or track and subtract the duration during which `stopEpoch` attempts failed due to `StopEpochVaultLiquidityUnavailable` (e.g., record `firstFailedStopTimestamp` and freeze interest accrual from that point until a successful stop or `startEpoch`).
- Alternatively, allow a permissionless "stop-with-pause" path that closes accounting using `_currentVaultAssets()` valuation without requiring the actual withdraw, deferring the cash pull.
- At minimum, document that borrower APR continues accruing during external vault pauses and set `borrowerApr` accordingly.

### Proof of Concept
Foundry fork/invariant-style PoC outline (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// setup as in testProgrammableBorrowerStopEpochAutoRealizesInterestWithRealVault
idleCDO.depositAA(10_000e6);
cdoEpoch.startEpoch();
programmableBorrower.borrow(5_000e6);           // borrower draws at borrowerApr

vm.warp(cdoEpoch.epochEndDate() + 1);

// External vault pauses withdrawals (covered position: shortfall <= _currentVaultAssets)
vault.setPaused(true);                           // or setWithdrawLimit(0) / revert-on-withdraw

uint256 accruedBefore = programmableBorrower.borrowerInterestAccruedNow();

vm.prank(manager);
vm.expectRevert();                               // StopEpochVaultLiquidityUnavailable
cdoEpoch.stopEpoch(0, 0);

// Pause persists: epoch still running, accounting still active
vm.warp(block.timestamp + 7 days);

uint256 accruedDuringPause = programmableBorrower.borrowerInterestAccruedNow();
assertGt(accruedDuringPause, accruedBefore);     // borrower charged for the frozen period

vault.setPaused(false);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);
// borrowerInterestDebt now includes the 7 extra days of APR the borrower could not avoid
```
