### Title
`ExtractZipArchive` performs no path-containment check, letting archive entries write outside the extraction root - (File: helpers/archives/zip_extract.go)

### Summary
`ExtractZipArchive` and its helpers (`extractZipFile`, `extractZipFileEntry`, `extractZipDirectoryEntry`, `extractZipSymlinkEntry`) use `file.Name` directly from the zip entry to build filesystem paths, with zero validation against `..` segments, absolute paths, or symlink targets. The only entry-name filter present, `errorIfGitDirectory`, is a cosmetic warning (not a block) and can itself be bypassed for entries whose cleaned path starts with a path separator.

### Finding Description
`extractZipFile` calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and then, depending on entry type, `extractZipFileEntry` (`os.OpenFile(file.Name, ...)`), `extractZipDirectoryEntry` (`os.Mkdir(file.Name, ...)`), or `extractZipSymlinkEntry` (`os.Symlink(string(data), file.Name)`), all operating directly on the attacker-supplied `file.Name`/link target: [1](#0-0) [2](#0-1) [3](#0-2) 

There is no `filepath.Abs`/`filepath.Clean` + prefix check against an extraction root, unlike the tar+zstd extractor in the same codebase, which explicitly enforces containment: [4](#0-3) 

The only filter applied per-entry in `ExtractZipArchive` is `errorIfGitDirectory`, and its result only gates a log warning, not extraction — `extractZipFile` is called unconditionally afterward regardless of the git-directory check outcome: [5](#0-4) 

`isPathAGitDirectory` additionally only inspects `parts[0]` after `filepath.Clean`, so an entry name beginning with a path separator (e.g. `/.git/...`) cleans to a path whose first split segment is empty, silently missing that case too: [6](#0-5) 

`ExtractZipArchive` is reachable from job cache/artifact restoration through the legacy zip extractor path: [7](#0-6) 
which is invoked by `CacheExtractorCommand.Execute` via `archive.NewExtractor(format, f, size, wd)` for cache download/extraction: [8](#0-7) 

An attacker who controls the contents of a cache/artifact zip archive (e.g. a pipeline author poisoning a shared cache key, or a job whose artifact/cache archive is later restored by another job in the same project) can craft entry names with `../../` segments, absolute paths, or symlink entries pointing outside the intended working directory (`wd`). Because none of `extractZipFile`'s helpers validate against `wd`, the write lands wherever the crafted path resolves to on disk, limited only by OS filesystem permissions of the runner process. I could not fully confirm within this session whether the default (non-legacy) zip extractor used by `archive.NewExtractor` also lacks containment or has been hardened separately — that would need to be checked in a live session — but the `ziplegacy`/`archives.ExtractZipArchive` code path itself is unambiguously reachable and unambiguously missing containment.

### Impact Explanation
A malicious cache/artifact zip can write or overwrite arbitrary files reachable by the runner's job user outside the intended cache/build root (zip-slip), which can lead to overwriting trusted configuration files or planting files later read as secrets/config by subsequent build steps, matching the "secret exposure or trusted-config overwrite" impact class. Severity is bounded by the OS-level permissions of the job process (this does not itself escape the executor sandbox), but within that sandbox it breaks the invariant that "file operations must stay within intended build/cache/artifact roots."

### Likelihood Explanation
Exploitation only requires the attacker to control the bytes of a zip archive that the runner later extracts via `ExtractZipArchive` (e.g., by pushing to a shared cache key, or supplying job artifacts consumed downstream). No special runner privileges are required, and the bug is fully deterministic/repeatable — any crafted `..`/absolute/symlink entry name reproduces the traversal.

### Recommendation
In `extractZipFile` (and the symlink/dir/file entry helpers), resolve each entry against the intended extraction root with `filepath.Join(root, file.Name)`, then `filepath.Clean`/`filepath.Abs` the result and reject (rather than warn-and-continue) any entry whose resolved path is not a descendant of `root`, mirroring the containment check already implemented in `tarzstd_extractor.go`. Also validate symlink targets so they cannot resolve outside `root`. Change `errorIfGitDirectory`'s result to actually skip extraction of the offending entry, and fix `isPathAGitDirectory` to also match leading-separator or drive-rooted variants.

### Proof of Concept
Go unit test in `helpers/archives/zip_extract_test.go`:
```go
func TestExtractZipArchive_PathTraversal(t *testing.T) {
    dir := t.TempDir()
    outside := filepath.Join(filepath.Dir(dir), "pwned.txt")
    defer os.Remove(outside)

    buf := &bytes.Buffer{}
    zw := zip.NewWriter(buf)
    w, _ := zw.Create("../" + filepath.Base(outside))
    w.Write([]byte("attacker-controlled"))
    zw.Close()

    wd, _ := os.Getwd()
    _ = os.Chdir(dir)
    defer os.Chdir(wd)

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    err := ExtractZipArchive(zr)
    assert.NoError(t, err)

    // Assert the file did NOT escape the extraction directory.
    _, statErr := os.Stat(outside)
    assert.True(t, os.IsNotExist(statErr), "zip-slip: file escaped extraction root")
}
```
Expected current behavior: the file is created outside `dir` (test fails), confirming the missing containment check.

func extractZipFileEntry(file *zip.File) (err error) {

	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))

	}
