### Title
Unstaked withdrawal debits internal `last_total_balance` accounting without verifying the outgoing NEAR transfer succeeded - ([File: staking-pool/src/internal.rs])

### Summary
`internal_withdraw` in the staking-pool contract fires a NEAR transfer and unconditionally decrements the contract's internal `last_total_balance` ledger in the same synchronous call, without ever checking whether the transfer promise actually succeeded. This is the same bug class as the Evmos advisory: a local accounting state change is made together with an external transfer whose outcome is never awaited/verified, so the internal ledger can diverge from the real custodied balance.

### Finding Description
`internal_withdraw` decrements the caller's `account.unstaked` and immediately schedules a bare `Promise::new(account_id).transfer(amount)`, then synchronously subtracts `amount` from `self.last_total_balance` — with no `.then(...)` callback checking `is_promise_success()`: [1](#0-0) 

Contrast this with every other cross-contract interaction in this codebase (e.g. the lockup contract's staking-pool withdraw flow), which always verifies promise success in a callback before updating accounting state: [2](#0-1) 

If the outgoing transfer receipt fails (for example, because the destination account no longer exists — a scenario the project's own README explicitly acknowledges can happen when "the owner withdraws tokens and while the call is being processed deletes their account"), the NEAR is refunded back into the staking-pool contract's real balance. But `self.last_total_balance` has already been permanently decremented as if the funds left: [3](#0-2) 

The custody binding broken is: `last_total_balance` (claimed value debited) versus the NEAR actually delivered to the withdrawer. On the very next `internal_ping()` call, the contract compares its real `account_balance()` against the artificially-lowered `last_total_balance` and treats the entire refunded amount as a legitimate staking "reward," which is then split between the owner's fee and `total_staked_balance` and distributed pro-rata to all current stake-share holders: [4](#0-3) 

So the funds that were supposed to be paid to the withdrawing account (whose `unstaked` balance was already zeroed and can never reclaim that amount) are instead silently re-attributed as reward income to unrelated delegators and the pool owner. The accounting invariant `last_total_balance == real contract balance representing all outstanding claims` is violated, and it is settled on by every other delegator's next `ping()`/`stake`/`unstake`/`withdraw` call, which use the corrupted `total_staked_balance` / share price to compute their own entitlements.

### Impact Explanation
This is a High-severity accounting divergence: rewards/fees get mis-attributed away from the rightful (but now balance-wiped) withdrawer to the owner and remaining stakers, based on an internal ledger (`last_total_balance`) that no longer reflects the real custodied NEAR. This is exactly the class of bug called out in scope: "an accounting value diverging from reality where another party settles on it" / "rewards or fees mis-attributed."

### Likelihood Explanation
The failure path (transfer to a deleted/non-existent account refunding to the sending contract) is explicitly documented by the project itself as a known, reachable scenario, and no code exists anywhere in `internal_withdraw` to defend against it or reconcile the ledger afterward — unlike the analogous, correctly-guarded flow in the lockup contract's staking callbacks.

### Recommendation
Chain the withdrawal transfer with a callback (mirroring the pattern already used in `lockup/src/owner_callbacks.rs` and `lockup/src/foundation_callbacks.rs`) that checks `is_promise_success()` before mutating `self.last_total_balance` and the account's `unstaked` field, or roll back both fields if the transfer promise fails.

### Proof of Concept
1. Delegator deposits and stakes, then unstakes, waiting the required epochs.
2. Delegator calls `withdraw`/`withdraw_all`, which reduces `account.unstaked` and `self.last_total_balance` by `amount` and schedules `Promise::new(account_id).transfer(amount)`.
3. Before the transfer receipt executes, the destination account (`account_id`) is deleted (e.g., via a `delete_account` action in the same or an adjacent block).
4. The transfer receipt fails and the NEAR is refunded to the staking-pool contract's real balance, but `self.last_total_balance` was already decremented in step 2 and is never corrected.
5. On the next call that triggers `internal_ping()`, `total_balance - self.last_total_balance` includes the refunded `amount`, which is distributed as `owners_fee` and `remaining_reward` added to `total_staked_balance`, benefiting the owner and all other stake-share holders instead of the original withdrawer, whose `unstaked` balance was already zeroed with no compensating claim.

    /// Distributes rewards after the new epoch. It's automatically called before every action.
    /// Returns true if the current epoch height is different from the last epoch height.
    pub(crate) fn internal_ping(&mut self) -> bool {
        let epoch_height = env::epoch_height();
        if self.last_epoch_height == epoch_height {
            return false;
        }
        self.last_epoch_height = epoch_height;

        // New total amount (both locked and unlocked balances).
        // NOTE: We need to subtract `attached_deposit` in case `ping` called from `deposit` call
        // since the attached deposit gets included in the `account_balance`, and we have not
        // accounted it yet.
        let total_balance =
            env::account_locked_balance() + env::account_balance() - env::attached_deposit();

        assert!(
            total_balance >= self.last_total_balance,
            "The new total balance should not be less than the old total balance"
        );
        let total_reward = total_balance - self.last_total_balance;
        if total_reward > 0 {
            // The validation fee that the contract owner takes.
            let owners_fee = self.reward_fee_fraction.multiply(total_reward);

            // Distributing the remaining reward to the delegators first.
            let remaining_reward = total_reward - owners_fee;
            self.total_staked_balance += remaining_reward;

            // Now buying "stake" shares for the contract owner at the new share price.
            let num_shares = self.num_shares_from_staked_amount_rounded_down(owners_fee);
            if num_shares > 0 {
                // Updating owner's inner account
                let owner_id = self.owner_id.clone();
                let mut account = self.internal_get_account(&owner_id);
                account.stake_shares += num_shares;
                self.internal_save_account(&owner_id, &account);
                // Increasing the total amount of "stake" shares.
                self.total_stake_shares += num_shares;
            }
            // Increasing the total staked balance by the owners fee, no matter whether the owner
            // received any shares or not.
            self.total_staked_balance += owners_fee;

            env::log(
                format!(
                    "Epoch {}: Contract received total rewards of {} tokens. New total staked balance is {}. Total number of shares {}",
                    epoch_height, total_reward, self.total_staked_balance, self.total_stake_shares,
                )
                    .as_bytes(),
            );
            if num_shares > 0 {
                env::log(format!("Total rewards fee is {} stake shares.", num_shares).as_bytes());
            }
        }

        self.last_total_balance = total_balance;
        true
    }
