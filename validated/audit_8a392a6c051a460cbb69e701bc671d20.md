### Title
Unbounded per-tick scan over all post-anchor dispute games can stall the challenger's fault-proof monitoring - ([File: crates/proof/challenge/src/scanner.rs])

### Summary
`GameScanner::scan` in the Base fault-proof challenger deliberately avoids any lookback cap and instead re-evaluates the *entire* range of factory indices between the current anchor game and the newest game on every tick, performing several RPC calls per game (`status()`, `tee_prover()`, `zk_prover()`, `countered_index()`, `intermediate_output_roots()`, etc.). This mirrors the reported Knox `_processOrders` pattern: a loop that iterates every element of a collection whose size is controlled by external, permissionless actions and grows without any cap, so the loop's cost grows unboundedly with attacker-controlled input.

### Finding Description
`GameScanner::scan` computes `scan_start` from the anchor game's factory index and then iterates `scan_start..game_count`, concurrently querying every post-anchor game: [1](#0-0) [2](#0-1) 

The design comment explicitly states the scanner "avoids an arbitrary lookback cap while still skipping historical games at or before the accepted anchor" — i.e., there is no upper bound on the number of games scanned per tick, only a floor (the anchor). `game_count` comes from `DisputeGameFactory.game_count()`, and new dispute games are created via the permissionless `DisputeGameFactory.create(...)` entry point, which any dispute-game participant can call (subject to posting `initBonds[gameType]`): [3](#0-2) 

If the anchor game does not advance quickly (e.g., because games remain unresolved/in-progress, or because resolution requires waiting periods and challenge windows before `AnchorStateRegistry` advances), and an adversary keeps creating additional dispute games faster than the anchor advances, the range `scan_start..game_count` grows without bound. Every subsequent `scan()` call must issue several RPC calls per game in that ever-growing range (bounded in concurrency only by `SCAN_CONCURRENCY = 32`), so per-tick scan latency and RPC load grow linearly (or worse, given L1 RPC latency/rate limits) with the number of games created. This is structurally the same defect class as the reported `_processOrders` issue: an attacker-influenced collection is iterated in full on every invocation with no cap, so an attacker can inflate the collection to make the operation arbitrarily expensive/slow.

### Impact Explanation
If scan latency exceeds the tick interval or the dispute/challenge window, the challenger falls behind and may fail to detect and dispute a fraudulent proposal (invalid intermediate/output root) within the contestation period. Since the challenger is the mechanism that disputes wrong TEE/ZK output-root proposals in the fault-proof system, a stalled or overwhelmed challenger directly threatens the correctness guarantee of the dispute-game system: a wrong provable output root could go unchallenged and finalize. This satisfies the "wrong provable output root" / fault-proof-program impact category.

### Likelihood Explanation
Creating dispute games is permissionless to any bonded participant, and Base's own tests demonstrate scans can already run against hundreds/thousands of factory indices (`ANCHOR_SEARCH_BATCH_SIZE = 1024` for anchor lookup). An adversary with modest capital (paying `initBonds` per game) can repeatedly create new games faster than the anchor advances, continuously growing the scanned range. Because the scanner intentionally has "no arbitrary lookback cap," there is no existing safety valve bounding per-tick cost — likelihood is moderate, gated mainly by the L1 gas/bond cost of creating many dispute games and by how quickly the anchor otherwise advances in practice, which I was unable to fully verify from the available index (anchor-advancement cadence and bond amounts were not located in the indexed code).

### Recommendation
Bound the number of games evaluated per scan tick (e.g., process the post-anchor range in fixed-size batches like `ANCHOR_SEARCH_BATCH_SIZE`, carrying over remaining work to subsequent ticks), and/or track a persistent "last fully scanned index" watermark so a growing backlog degrades gracefully (falling behind on stale games first) rather than making every tick's cost proportional to the total number of ever-created, unresolved games. Consider also rate-limiting or requiring escalating bonds for rapid repeated game creation to reduce the attacker's ability to inflate `game_count` cheaply.

### Proof of Concept
Not independently reproduced against a live system (challenger and L1 fork infra were not exercised in this review); the analysis is based on static code reading of `GameScanner::scan`/`scan_start_index` and the permissionless `DisputeGameFactory.create` interface. Conceptually:
1. Adversary calls `DisputeGameFactory.create(gameType, rootClaim, extraData)` repeatedly (paying `initBonds[gameType]` each time), creating N new in-progress games faster than the `AnchorStateRegistry` anchor advances.
2. Each `GameScanner::scan()` tick must now evaluate `scan_start..game_count`, i.e., all N (plus previously accumulated) games, each requiring multiple RPC round-trips.
3. As N grows, tick duration grows correspondingly, eventually exceeding the polling interval and/or the dispute window, delaying detection of a concurrently-created fraudulent proposal among the flood of games.

/// On every tick the scanner locates the current anchor game in the factory

    pub async fn scan(&mut self) -> Result<Vec<CandidateGame>> {
        let game_count = self.factory_client.game_count().await?;

        if game_count == 0 {
            debug!("factory has no games");
            return Ok(vec![]);
        }

        let end = game_count - 1;
        let scan_start = self.scan_start_index(game_count).await;

        let games_to_scan = game_count.saturating_sub(scan_start);

        let scanner = &*self;
        let results: Vec<(u64, Result<Option<CandidateGame>>)> =
            stream::iter(scan_start..game_count)
                .map(|i| async move { (i, scanner.evaluate_game(i).await) })
                .buffer_unordered(Self::SCAN_CONCURRENCY)
                .collect()
                .await;

        let mut candidates = Vec::new();

        for (i, result) in results {
            match result {
                Ok(Some(candidate)) => candidates.push(candidate),
                Ok(None) => {}
                Err(e) => warn!(error = %e, index = i, "game query failed"),
            }
        }
