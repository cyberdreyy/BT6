Based on my analysis of `stackerdb_listener.rs`, the claimed defect is real in the miner-node's local bookkeeping code, but it does not clear the bar this audit requires (an unprivileged single-slot attacker breaking a safety/liveness guarantee through a reproducible, attacker-controlled path). I could not verify the missing piece: whether the *signer's own state machine* (`stacks-signer/src/v0/signer.rs`) can ever legitimately emit `BlockResponse::Rejected` and then later `BlockResponse::Accepted` for the **same** `signer_signature_hash`, or whether a stale `Accepted`/`Rejected` StackerDB chunk can be replayed by a third party for a hash a signer has already responded to once. Without that guarantee, the exploit path is not established as attacker-reachable.

### What I confirmed in the code
- `BlockStatus.total_weight_rejected` is only ever incremented, never decremented, when a signer's `Rejected` message is the first response recorded for that `slot_id`: `if block.responded_signers.insert(slot_id) { block.total_weight_rejected = ...saturating_add(...) }`. [1](#0-0) 
- The `Accepted` branch checks only `gathered_signatures.contains_key(&slot_id)` (not `responded_signers`) to decide whether to add weight to `total_weight_approved`, so a signer who previously rejected and is later accepted still gets counted in `total_weight_approved` too. [2](#0-1) 
- In `SignerCoordinator::get_block_status`, the rejection-threshold check is evaluated strictly before the approval-threshold check on the same `block_status` snapshot, so if both predicates are true, `SignersRejected` wins. [3](#0-2) 
- The only mechanism that clears `total_weight_rejected` is `reset_rejections`, which is invoked solely on a rejection-timeout retry (miner resends the *same* proposal), not on receipt of a later `Accepted`. [4](#0-3) 

### Why I cannot confirm this is exploitable by the defined attacker
The audit requires an **unprivileged attacker with one miner slot plus gossip** to trigger this — not a signer's own internal non-determinism. The scenario needs a genuine signer to emit `Rejected(H)` and then later `Accepted(H)` for the identical `signer_signature_hash`. Both messages must be validly signed by that signer's own key (`stackerdb_listener.rs` verifies `signer_pubkey.verify(...)` on Accept and `recover_public_key()` on Reject), so the attacker cannot forge either message — they can at best gossip/replay chunks the signer or others already broadcast. Whether the stacks-signer state machine (`stacks-signer/src/v0/signer.rs`) can itself produce this Reject→Accept sequence for one unchanged `H` (e.g., due to a legitimate re-evaluation after initially rejecting for a missing parent), or whether a stale `Accepted` chunk for an already-responded hash can be "replayed" through StackerDB by a non-owning party, is exactly what I was unable to verify before running out of iterations. If the signer state machine only ever sends a single, final response per `signer_signature_hash` (which is the typical design intent to prevent equivocation), then this bug is unreachable by the described attacker and is merely a benign accounting quirk under network reordering of the *same signer's own* messages, not something the attacker can induce.

Given this, I cannot assert with confidence that the code path is attacker-triggerable under the strict preconditions (single miner slot, no majority signers, no auth_token, no local access). A complete audit would require reading `stacks-signer/src/v0/signer.rs`'s `handle_block_validate_response`/`handle_block_proposal` logic and `signerdb.rs`'s equivocation/replay guards to determine whether a Reject-then-Accept sequence for one hash is ever produced or replayable.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
