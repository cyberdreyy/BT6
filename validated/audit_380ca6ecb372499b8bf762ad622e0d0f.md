### Title
Loss-adjusted withdrawal claims are keyed only to `lastWithdrawRequest`, so a receipt from an earlier epoch in the same loss event is paid at par instead of the haircut price - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Wireshark bug is an out-of-bounds/over-read: code reads past the intended boundary and consumes bytes belonging to a different logical record. The analog in `IdleCreditVault` is a mis-scoped read of per-epoch accounting: when a borrower funds pending withdrawals with a realized loss, `collectWithdrawFunds` writes a single `lossRecoveryPriceByEpoch[epochNumber]` that haircuts **all** pending receipts in the aggregate `pendingWithdraws` bucket, but `_claimLossAdjustedWithdrawRequest` only looks up `lastWithdrawRequest[_user]` and clears only that epoch's per-user receipt. Any receipt the same user holds from an earlier epoch — which was part of the haircut basis — then falls through to `_claimFundedWithdrawRequest` and is paid **at par**, over-drawing the funded pool.

### Finding Description
`requestWithdraw` records receipts both in the aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]`, and explicitly supports stacking requests across epochs ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests") [1](#0-0) . The only cross-epoch guard prevents a new request when the *previous request epoch* already has a loss price [2](#0-1) .

When `stopEpoch` realizes a loss, `previewLossAdjustedWithdrawFunds` splits the loss pro-rata over `activeBasis + pendingBasis`, so `pendingToFund = pendingBasis * (1 - lossShare)` covers every pending receipt of every epoch [3](#0-2) . `collectWithdrawFunds` stores that ratio under only the current `epochNumber` and zeroes `pendingWithdraws` [4](#0-3) .

At claim time, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — a single-epoch read — and `_clearWithdrawClaimForEpoch` subtracts only that epoch's slice from `withdrawsRequests[_user]` and resets `lastWithdrawRequest` to 0 [5](#0-4) [6](#0-5) . `claimWithdrawRequest` then calls `_claimFundedWithdrawRequest`, which pays the remaining `withdrawsRequests[_user]` (the earlier-epoch receipt) at 1:1 — the `epochNumber <= lastWithdrawRequest` gate passes because the marker was just cleared [7](#0-6) .

### Impact Explanation
Broken invariant: loss waterfall / fair claim. A user holding receipts in two epochs when one loss-adjusted funding occurs is paid `epochN_amount * lossPrice + epochEarlier_amount * 1.0`, while the strategy only received `(epochN + epochEarlier) * lossPrice` for the entire pending bucket. The excess is paid out of strategy underlying that belongs to other claimants and LPs — direct theft of `earlierAmount * (1 - lossRecoveryPrice)` per offending user, and insolvency for the last claimants (the reserve guard in `_transferFundedClaim` only protects `defaultRecoveryReserve`, not other users' funded claims) [8](#0-7) . Quantified example: user requests 100 (epoch 1), then 100 (epoch 2); a 50% loss funding sets `lossRecoveryPrice = 0.5e18` on a 200 basis (funded 100). The user claims `100*0.5 + 100*1.0 = 150`, draining 50 underlying owed to other pending claimants.

### Likelihood Explanation
Requires only unprivileged actions: two `requestWithdraw` calls in different epochs before a loss-adjusted `stopEpochWithDuration`/`collectWithdrawFunds`. Loss epochs are an admitted protocol mode (`previewLossAdjustedWithdrawFunds`, `stopEpochWithDuration(_lossAmount)`). No privileged misbehavior needed; the honest borrower/manager triggers it by partially funding pending withdrawals. The stacked-request path is a documented, supported flow, so any user naturally holding receipts across the loss epoch hits this.

### Recommendation
Track per-epoch loss claims correctly: either (a) iterate all epochs with `withdrawsRequestsByEpoch[_user][e] != 0` where `lossRecoveryPriceByEpoch[e]` was set during the same funding event, or (b) since the haircut applies to the aggregate pending bucket regardless of request epoch, store a single global `lossRecoveryPrice` plus a flag and apply it to the user's entire `withdrawsRequests[_user]` + APR0 basis in `_claimLossAdjustedWithdrawRequest`, clearing all epochs. Alternatively, force users to claim/roll earlier receipts into the current epoch at request time so one user can never hold receipts spanning a loss boundary.

### Proof of Concept
Foundry fork sketch (mode: fixed-APR, cash interest, epoch with loss funding via `stopEpochWithDuration`/`previewLossAdjustedWithdrawFunds` path):

```solidity
// setup: deposit via idleCDO.depositAA for attacker, startEpoch, warp past buffer
// epoch 1
cdoEpoch.requestWithdraw(0, AAtranche);          // attacker receipt W1 = 100e18, lastWithdrawRequest = 1
// honest manager/borrower run epoch 1 to completion (stopEpoch fully funds pending)
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpoch(apr, 0);                       // epochNumber -> 2, W1 funded but unclaimed

// epoch 2
cdoEpoch.requestWithdraw(0, AAtranche);          // attacker receipt W2 = 100e18, lastWithdrawRequest = 2
vm.warp(cdoEpoch.epochEndDate() + 1);
// borrower repays with a realized loss; manager calls stopEpochWithDuration loss path
// => strategy.collectWithdrawFunds(100e18) on pendingBasis 200e18
// => lossRecoveryPriceByEpoch[2] = 0.5e18, pendingWithdraws = 0, strategy holds 100e18 for bucket

// claim
cdoEpoch.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest: clears epoch-2 slice -> pays 100 * 0.5 = 50
// _claimFundedWithdrawRequest: epochNumber(3) > lastWithdrawRequest(0) -> pays W1 = 100 at par
assertEq(underlying.balanceOf(attacker) - balPre, 150e18); // funded bucket was only 100e18
// the extra 50e18 is taken from underlying belonging to other pending/funded claimants
```

Expected: strategy transfers 150e18 for receipts whose aggregate funded amount was 100e18, proving over-read/mis-keyed claim basis and direct theft from the shared funded pool.

```text
  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
