### Title
Shared EIP-8130 payer capacity can be griefed to block sponsored transactions from other senders - (File: `crates/execution/txpool/src/guard.rs`, `crates/execution/txpool/src/limits.rs`)

### Summary
`MempoolGuard::try_admit` gates every EIP-8130 transaction on shared, per-`payer` admission capacity (`signature_limit`, `payment_limit`, or a `PayerBook` balance reservation). All of these dimensions are keyed by the *payer* address, not the sender, so every sender sponsored by the same payer competes for the same small pool of slots/balance. Because admission is strictly first-come/no-preemption, an attacker who is any authorized sender under a shared payer can cheaply occupy the payer's entire admission capacity with throwaway transactions, permanently rejecting every other sponsored sender's transaction from entering the mempool — the same "fill-the-cap-then-vacate/never-confirm" griefing pattern described in the external Leap `maxRaiseAmount` report, but here targeting a shared, cheaply-refillable resource instead of an on-chain raise cap.

### Finding Description
`MempoolGuard::try_admit` charges admission against dimensions keyed by `admission.payer`:
- `signature_counts.try_increment(admission.payer, limits.signature_limit)` when the payer is not locked [1](#0-0) 
- `payment_counts.try_increment(admission.payer, limits.payment_limit)` for count-limited (non-trusted) payers, or `PayerBook::try_reserve` for balance-bounded (trusted) payers [2](#0-1) 

Both `DEFAULT_SIGNATURE_LIMIT` and `DEFAULT_PAYMENT_LIMIT` default to 4 [3](#0-2) , and these counters/reservations are shared across *every distinct sender* sponsored by the same payer — the design comment even documents that this is a payer-scoped, not sender-scoped, dimension [4](#0-3) .

Critically, `PayerBook::try_reserve` performs no priority-based preemption: a new reservation is admitted only if `reserved + max_cost ≤ balance`; if the book is already full, the call simply returns `false` regardless of the incoming transaction's fee/priority [5](#0-4) . Eviction of lower-priority entries only happens reactively, when the payer's *on-chain balance decreases* via `set_balance` [6](#0-5)  — never in response to admission-time contention from a higher-priority arrival. The same non-preemptive behavior holds for the plain count-based `InflightCounters::try_increment`, which just rejects once the cap is hit [7](#0-6) .

This mirrors the external report's root cause exactly: a shared, capped resource (`maxRaiseAmount` there; payer signature/payment/balance capacity here) can be filled by an attacker at low cost, with no lock-up or preemption mechanism to protect transactions submitted by other, legitimate participants competing for the same capacity.

### Impact Explanation
Any account authorized as a sender under a shared sponsoring payer (e.g., an app's gas-sponsorship account used by many end users) can submit a handful of low-cost EIP-8130 transactions that:
- consume the payer's `signature_limit` (default 4) via `payer_signature_charged` [8](#0-7) , and/or
- consume the payer's `payment_limit` slots or its entire `PayerBook` balance reservation [2](#0-1) 

Once full, `pre_admit_protocol_transaction` rejects all subsequently submitted transactions from *other* senders sharing that payer with `LimitRejection::PayerLimit`/`PaymentLimit`/`PayerBalance`, regardless of their fee or legitimacy [9](#0-8) . The attacker only needs to keep their own occupying transactions from being mined/expiring (e.g., low fee, or refreshed just before eviction) to sustain the block. This denies service to every other user of a shared sponsorship channel — a concrete denial of a specific class of transactions from reaching the chain, analogous to the reported prevention of deposits from reaching the cap.

### Likelihood Explanation
The attack requires only that the attacker be one of (possibly many) senders authorized by a shared payer's EIP-8130 policy — a common pattern for gas-sponsorship/paymaster-style services — and the default caps are very small (4), making the griefing cheap and easy to sustain by resubmitting equivalent transactions as old ones are evicted or expire. No special privileges beyond being an ordinary txpool submitter are needed, matching the "unprivileged transaction sender" reachability constraint.

### Recommendation
Introduce priority-based preemption at admission time (fee-bump-style replacement) for the payer-scoped dimensions — i.e., allow a higher-priority incoming transaction to evict lower-priority reservations/counts from the same payer's capacity, similar to how `PayerBook::set_balance` already evicts lowest-priority entries first. Alternatively, scope a portion of the payer's capacity per-sender (e.g., a minimum guaranteed slot per distinct sender) so that no single sender can monopolize a shared payer's entire admission budget.

### Proof of Concept
1. Payer `P` sponsors senders `A` (attacker) and `B` (victim) under an EIP-8130 policy, with `P` non-trusted and default `payment_limit = 4`.
2. `A` submits 4 distinct low-fee EIP-8130 transactions with `payer = P`, each admitted via `MempoolGuard::try_admit`, filling `payment_counts[P]` to the cap [10](#0-9) .
3. `B` submits a legitimate, higher-fee sponsored transaction with `payer = P`; `try_admit` rejects it with `LimitRejection::PaymentLimit` because `payment_counts.try_increment(P, 4)` fails [7](#0-6) .
4. `A`'s transactions are never mined (or are replaced with fresh copies just before expiry), so `B`'s sponsored transaction is indefinitely denied admission to the mempool while `A`'s cost remains minimal.

//!
//! Two independent dimensions gate admission:
//!
//! * the **sender limit**, bounded by signature/auth-surface stability, and
//! * the **payer limit**, bounded by balance-drain risk.

//! the max cost of all sponsored transactions must not exceed the payer's
//! balance. For a trusted account ETH can only leave through gas it sponsors, so
//! `Σ max_cost ≤ balance` is a true upper bound on the only drain.

    /// Attempts to reserve one slot for `account` against `cap`. Returns `true`
    /// and increments the count if the account is below `cap`; returns `false`
    /// and leaves the count unchanged otherwise.
    pub fn try_increment(&mut self, account: Address, cap: u32) -> bool {
        let entry = self.counts.entry(account).or_insert(0);
        if *entry >= cap {
            return false;
        }
        *entry += 1;
        true
    }

    /// Attempts to reserve `max_cost` for `hash` at `priority`. Succeeds (and is
    /// a no-op returning `true`) if `hash` is already reserved. Otherwise
    /// succeeds only if the new reservation still fits within the balance:
    /// `reserved + max_cost ≤ balance`.
    pub fn try_reserve(&mut self, hash: TxHash, max_cost: U256, priority: u128) -> bool {
        if let Some(existing) = self.entries.get(&hash) {
            debug_assert_eq!(
                *existing,
                (priority, max_cost),
                "reservation parameters changed for an existing transaction hash"
            );
            return true;
        }
        let Some(new_reserved) = self.reserved.checked_add(max_cost) else {
            return false;
        };
        if new_reserved > self.balance {
            return false;
        }
        self.by_priority.insert((priority, hash), max_cost);
        self.entries.insert(hash, (priority, max_cost));
        self.reserved = new_reserved;
        true
    }

    /// Updates the cached balance and, if it can no longer cover the
    /// reservation, evicts transactions from the low-priority end until
    /// `reserved ≤ balance`. Returns the evicted hashes in eviction order
    /// (lowest priority first).
    pub fn set_balance(&mut self, balance: U256) -> Vec<TxHash> {
        self.balance = balance;
        let mut evicted = Vec::new();
        while self.reserved > self.balance {
            let Some(&(_, hash)) = self.by_priority.keys().next() else {
                break;
            };
            assert!(self.remove(&hash), "priority index must reference an existing reservation");
            evicted.push(hash);
        }
        evicted
    }

    fn pre_admit_protocol_transaction(
        &self,
        hash: TxHash,
        replaced: Option<TxHash>,
        validated: &TransactionValidationOutcome<T>,
    ) -> PoolResult<bool> {
        let mut guard = self.guard.write();
        if guard.contains(&hash) || replaced.is_some_and(|hash| guard.contains(&hash)) {
            return Ok(false);
        }
        let Some(admission) = validated
            .as_valid_transaction()
            .and_then(|transaction| Self::admission_for(transaction.transaction()))
        else {
            return Ok(false);
        };
        if let Err(rejection) = guard.try_admit(admission) {
            return Err(Self::limit_rejection_error(hash, rejection));
        }
        Ok(true)
    }
