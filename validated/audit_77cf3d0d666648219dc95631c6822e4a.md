### Title
Fail-open error handling in the own-tenure stale-conflict guard lets a signer sign two conflicting sibling blocks at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` in the v0 signer guards against a signer putting a second signature over a sibling block at a height it has already signed. When the first signature is still "fresh" the guard blocks unconditionally, but once it goes stale the guard falls back to asking the signer's own node whether that tenure's canonical tip has already reached the proposed height. If that RPC call to the node fails (timeout, transient error, node lag), the code treats the tenure as **unconfirmed** and proceeds to sign — rather than refusing until the ambiguity is resolved. A single miner can produce two conflicting tenure-start blocks (siblings) for the same slot, wait out the freshness window, and cause a signer whose node experiences even a routine transient hiccup to sign both.

### Finding Description
In `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs`), once a fresh conflict is ruled out, the code re-checks stale same-tenure conflicts: [1](#0-0) 

```rust
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash
        && !self.reorg_permit_stands(stacks_client, conflict)
}) {
    match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
        Ok(tip) => {
            let tip_height = tip.anchored_header.height();
            if tip_height >= block_info.block.header.chain_length {
                // refuse to sign
                return;
            }
        }
        Err(e) => {
            warn!(
                "{self}: Failed to fetch the canonical tip of the proposed block's tenure: {e:?}. Treating the tenure as unconfirmed.";
                ...
            );
            // falls through -> signs anyway
        }
    }
}
```

`conflicts` here is populated from `get_signed_conflicts`, i.e. blocks this very signer has already signed (`mark_locally_accepted`) at the same or higher height [2](#0-1) . The comment in the flow doc makes explicit that this branch exists specifically because the chainstate re-check (`check_block_against_signer_db_state`) only looks at one tenure and the proposal-time `DuplicateBlockFound` check never re-runs, so this is the *only* remaining guard against a signer double-signing two siblings in its own tenure once the first signature goes stale [3](#0-2) .

The failure mode: when `get_tenure_tip` errors, the code cannot prove the tenure has *not* reached the conflicting height, yet it chooses to sign rather than to hold. This is a fail-open default in exactly the place meant to prevent the signer from countersigning a second, conflicting block for a slot it already committed a signature to — the equivalent of the referenced Craft CMS bug class, where a relocation/ownership check that should gate an action was effectively skipped/unchecked on the failure path, permitting an action (asset move / here, a second signature) that should have required a positive confirmation.

### Impact Explanation
A signer producing a signature over two conflicting (non-canonical relative to each other) blocks at the same chain height breaks the "one signature per signer per slot" equivocation guard that the pre-commit/threshold design is built to enforce (see the explicit design goal in the flow docs: "a rival is still alive" must stay silent) [4](#0-3) . This falls squarely in the Critical impact class: a signer signing a conflicting block. If enough signers hit the same transient node-RPC failure while re-evaluating a stale conflict (plausible under load or during a burnchain event, which is exactly when these tips are being requested per section 8 of the docs), it becomes possible for a genuine safety violation — two block signatures for the same slot — to accumulate.

### Likelihood Explanation
Triggering the precondition (two conflicting tenure-start siblings racing within the `tenure_last_block_proposal_timeout` window) requires only a single miner and normal StackerDB gossip, matching the in-scope threat model (`docs/signer-flows.md`'s own `async_sibling_validation` test module documents and exercises exactly this race) [5](#0-4) . The only additional requirement is that the signer's `get_tenure_tip` RPC to its own node fails or times out at the moment the stale-conflict re-check runs — an ordinary operational condition, not one requiring compromising the node, another signer's key, or a signer majority.

### Recommendation
Change the error branch at `stacks-signer/src/v0/signer.rs` lines 1449–1455 to fail closed: on an error from `get_tenure_tip`, refuse to sign (same as `return;` in the `tip_height >= ...` branch) rather than falling through to sign. Optionally retry the query before defaulting, but the default on unresolved ambiguity should be "hold," consistent with every other branch in this function that treats connectivity failures as a reason not to proceed (e.g. `get_signed_conflicts` query failure already returns without signing at lines 1387–1391) [6](#0-5) .

### Proof of Concept
1. A single miner proposes tenure-start block A at height h; enough signer weight pre-commits and one signer S crosses its own pre-commit threshold and signs A (`mark_locally_accepted`), recording it via `get_signed_conflicts`-visible state.
2. A fails to reach 70% signature weight overall (e.g., the miner or network drops it) and is never pushed/confirmed by the node, so `get_tenure_tip` for that tenure continues to report the parent tip (height < h).
3. The miner waits past `tenure_last_block_proposal_timeout` (so A's entry in S's `get_signed_conflicts` becomes stale) and re-proposes a conflicting sibling B at height h in the same tenure.
4. B passes `check_proposal`/`check_block_against_signer_db_state` and reaches the pre-commit threshold at S.
5. In `handle_block_pre_commit`, S finds the stale, same-tenure conflict (A) and calls `stacks_client.get_tenure_tip(...)`. If that call to S's own node errors (network hiccup, node overloaded, request timeout) — a routine occurrence — the `Err(e)` branch logs a warning and falls through, and S signs B.
6. S has now produced signatures over two conflicting blocks (A and B) at the same height in the same tenure, exactly the invariant the guard exists to prevent.

```markdown
Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
```
