### Title
Unchecked ERC4626 `deposit` return lets a vault shareholder steal idle lender funds via share-price inflation - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower._depositToVault()` calls `vault.deposit(_assetAmount, address(this))` and never checks the returned `shares`. This is the same bug class as the FFmpeg report — a return value of an allocation function is not validated before the result is trusted. If the external ERC4626's share price is inflated so that the deposited amount mints zero (or economically negligible) shares, the pool's underlying is transferred into the vault but the contract owns no claim on it. The value is captured by existing vault shareholders. An attacker who is a shareholder of the configured vault (an allowed role per the threat model) can inflate the vault price, wait for the next `onStartEpoch` / `repay` / `borrow`-driven redeposit, and redeem their shares for the donated pool principal.

### Finding Description
`ProgrammableBorrower` parks all idle capital in an ERC4626 vault. `_depositToVault` is invoked from three places:

- `onStartEpoch()` deposits the entire idle underlying balance when a new epoch starts (`contracts/strategies/idle/ProgrammableBorrower.sol:216`).
- `_repay()` redeposits repayments while epoch accounting is active (`:499`, `:527`).
- Any operator-triggered redeposit path through the same helper.

The helper at `:378-385`:

```solidity
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
  if (_assetAmount == 0) return;
  uint256 shares = vault.deposit(_assetAmount, address(this));
  if (epochAccountingActive && _principalAssets != 0) {
    epochDepositedToVault += _principalAssets;
  }
  emit DepositedIntoVault(_assetAmount, shares);
}
```

`shares` is only logged; there is no `require(shares > 0)` and no `convertToAssets(shares)` sanity check. ERC4626 vaults legitimately round deposits down, and a vault whose `totalAssets` has been inflated (donation attack on the vault itself, or a vault whose share price grew large relative to the deposit size) will mint `shares = floor(assets * totalSupply / totalAssets)` which can be `0` while still pulling the full `_assetAmount` via `transferFrom` inside `deposit`.

After the deposit, `_currentVaultAssets()` (`:546-549`) values the position as `convertToAssets(balanceOf(this))`. With zero or dust shares, the position reads ~0:

- If the deposit happened in `onStartEpoch`, `epochStartVaultAssets` was snapshotted from the pre-deposit balance (`:214-219`), so the epoch's `principalAssets` baseline includes the lost assets while `earnedAssets` excludes them → `_vaultNetInterest()` reports a `loss` equal to the stolen amount → `totalInterestDueNow()` drops and the vault sleeve loss is socialized to LPs at `stopEpoch`, or `onStopEpoch` returns true while the shortfall check (`:245`) lets `transferFrom` fail into a default.
- Meanwhile the attacker's vault shares are now backed by the extra `_assetAmount`, which they recover via `redeem`.

The attacker needs to be able to influence the configured vault's share price. The threat model explicitly allows "a user of the programmable borrower's ERC4626 vault" as an attacker. If the vault is one where the attacker can become the dominant/sole shareholder before a pool deposit (e.g., a fresh or thin vault), a donation to the vault raises the share price above the pool's deposit size, the pool mints 0 shares, and the attacker redeems for principal + stolen amount.

### Impact Explanation
Direct theft of lender funds: the pool's idle underlying balance is donated to vault shareholders. For a zero-share mint, the loss equals the entire redeposited amount (potentially the full pool NAV at `onStartEpoch`, or full repayment amounts during an epoch). The loss then materializes either as a vault-sleeve loss socialized across AA/BB via `totalInterestDueNow`, or as a forced borrower default in `onStopEpoch` when the missing liquidity prevents the `transferFrom` to IdleCDO — permanent loss of LP principal, not a mere DoS.

### Likelihood Explanation
Requires the configured vault to have share price manipulable by the attacker to the point where a pool deposit rounds to ~0 shares — i.e., attacker must dominate the vault's share supply and donate enough to push `pricePerShare` above the deposit size. For vaults with a large existing third-party share base this is uneconomical; for the typical deployment pattern (dedicated or low-TVL ERC4626 used as the facility's parking vault) the attacker can be the first/dominant LP and the attack only costs them a temporarily-parked donation that they fully recover plus the stolen deposit. No privileged role is needed; the trigger is the honest manager's routine `startEpoch`/`stopEpoch`/`repay` calls. The missing check is unconditional in code.

### Recommendation
In `_depositToVault`, validate the minted shares:

```solidity
uint256 shares = vault.deposit(_assetAmount, address(this));
if (shares == 0) revert InvalidAmount();
// optionally: if (vault.convertToAssets(shares) < _assetAmount * MIN_FACTOR) revert ...
```

Prefer measuring the vault share balance delta (`balanceOf` before/after) rather than trusting the return value, and enforce a minimum acceptable share/asset ratio. Consider also snapshotting `epochStartVaultAssets` after the redeposit or capping it at the post-deposit `_currentVaultAssets()` so a partial-loss deposit cannot silently book principal it no longer owns.
