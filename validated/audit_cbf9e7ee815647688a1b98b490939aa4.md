I need to verify whether claimed instant-withdraw receipts leave stale per-epoch data that can be reused after a default.### Title
Stale per-epoch instant-withdraw receipts are never cleared on claim, inflating default recovery basis with phantom funds and double-counting already-paid claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` pays out and burns a user's instant-withdraw receipt but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and the epoch-level aggregate `instantWithdrawClaimsByEpoch[epoch]` uncleared. This is the credit-vault analog of CVE-2023-2481 ("buffer not cleared → sensitive material duplicated"): an already-consumed receipt persists in storage and is later re-read by the default-recovery path as if the funds were still held. When `finalizeDefaultRecovery` runs in the same epoch, the stale amount is counted both in `defaultPendingClaimBasis` and in `_defaultPrefundedInstantReserve`, booking phantom reserve that was already transferred to the claimant — inflating `defaultRecoveryReserve` beyond actual holdings and permanently undercollateralizing later recovery claims.

### Finding Description
In `requestInstantWithdraw`, each request records three pieces of state: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:366-372`). On the funded claim path, `claimInstantWithdrawRequest` only zeroes the aggregate `instantWithdrawsRequests[_user]` before paying (`IdleCreditVault.sol:387-392`):

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The per-epoch entries are never cleared — the "buffer" retaining already-spent claim data. Those entries are only consumed by `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (`IdleCreditVault.sol:844`) and subtracts from `instantWithdrawClaimsByEpoch[defaultEpoch]` (`IdleCreditVault.sol:853`). But that path only executes when `defaultInstantWithdrawsFinalized` is true, i.e. `pendingInstantWithdraws != 0` at finalization (`IdleCreditVault.sol:696`).

The stale data is re-read during `finalizeDefaultRecovery`:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the claim basis whenever `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-648`) — including amounts already claimed at par.
- `_defaultPrefundedInstantReserve` returns `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (`IdleCreditVault.sol:716-723`) — treating the already-paid-out amount as underlying still held by the strategy.
- `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (`IdleCreditVault.sol:686`), so `defaultRecoveryReserve` is credited with funds that no longer exist.

### Impact Explanation
Broken invariant: solvency of the isolated recovery reserve ("one receipt, one payout").

Concrete sequence (instant-withdraw mode enabled, epoch `E` running):
1. Attacker requests instant withdraw `X`; CDO calls `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`, `pendingInstantWithdraws -= X`, funds sit in the strategy. Attacker calls `claimInstantWithdrawRequest` and receives `X` at par. `instantWithdrawsRequestsByEpoch[attacker][E]` and `instantWithdrawClaimsByEpoch[E]` still contain `X`.
2. Another user requests instant withdraw `I` in the same epoch `E`, so `pendingInstantWithdraws == I > 0` and `instantWithdrawClaimsByEpoch[E] == X + I`.
3. Borrower fails to repay; epoch `E` defaults and `finalizeDefaultRecovery` runs. `defaultPendingClaimBasis` includes the phantom `X`, and `_defaultPrefundedInstantReserve` counts `X` as held reserve. `defaultRecoveryReserve` is set to `recovered + X_phantom + ...` while the strategy's actual balance is `X` lower.
4. Every recovery claim decrements `defaultRecoveryReserve` against a balance short by `X`. Once real funds are exhausted, remaining claimants' `_transferDefaultRecovery` calls underflow/revert — their recovery is permanently unclaimable. The early claimer (attacker) effectively obtained par value while his receipt continued to inflate the recovery entitlement of the pool.

Quantified loss: up to the total instant-withdraw amount claimed at par within the defaulted epoch — those funds are permanently missing from recovery payouts. `transferToken` cannot be used to top up without owner action, and `defaultRecoveryReserve` accounting is immutable post-finalization.

### Likelihood Explanation
Medium-low. It requires the honest manager to enable instant withdraws, at least one funded-and-claimed instant request and at least one still-pending instant request in the same epoch, and a borrower default finalized in that epoch. All attacker steps (request instant withdraw, claim it) are unprivileged user actions; the privileged actors only perform their normal honest calls. No existing guard stops it: `_transferFundedClaim` only protects `defaultRecoveryReserve` when it is non-zero (it is still zero pre-default), and nothing clears the per-epoch claim records on the funded path.

### Recommendation
Clear the per-epoch receipt on the funded claim path in `claimInstantWithdrawRequest`: zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrease `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (mirroring what `_claimDefaultedInstantWithdrawRequest` does), so already-paid claims can never re-enter default-recovery accounting. Alternatively, track funded vs. unfunded instant claims separately so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` only count receipts whose funds are actually still held.

### Proof of Concept
Foundry fork PoC (sketch, using the repo's existing `IdleCreditVault.t.sol` harness):

```solidity
function testStaleInstantReceiptInflatesRecovery() external {
    // Setup: deposit, enable instant withdraws (allowInstantWithdraw), start epoch E.
    idleCDO.depositAA(100_000 * ONE_SCALE);
    // manager: enable instant withdraws, startEpoch
    // ...

    // 1. Attacker instant request X, funded via getInstantWithdrawFunds, claimed at par.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(X, address(AAtranche));
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();          // borrower supplies funds
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();      // paid X at par
    // stale: instantWithdrawsRequestsByEpoch[attacker][E] == X
    //        instantWithdrawClaimsByEpoch[E] == X

    // 2. Victim requests instant I in same epoch, left unfunded.
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(I, address(AAtranche));
    assertEq(strategy.pendingInstantWithdraws(), I);
    assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), X + I); // stale X included

    // 3. Epoch defaults; finalizeDefaultRecovery counts phantom X.
    // ... borrower fails to repay; manager triggers default + finalizeDefaultRecovery
    uint256 balStrategy = underlying.balanceOf(address(strategy));
    assertGt(strategy.defaultRecoveryReserve(), balStrategy); // reserve booked > real holdings

    // 4. Drain order: early claimants succeed, last claimant's _transferDefaultRecovery reverts
    //    -> victim's recovery permanently unclaimable by amount ~X.
}
```

Key assertions: `instantWithdrawClaimsByEpoch[E]` retains the claimed `X`; after `finalizeDefaultRecovery`, `defaultRecoveryReserve` exceeds `underlying.balanceOf(strategy)` by `X`; the final recovery claim reverts in `_transferDefaultRecovery`.
