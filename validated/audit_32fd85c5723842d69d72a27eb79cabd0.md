### Title
No effective replay protection at gateway.ProcessRequest allows repeated forwarding of a captured legacy signed request to DON nodes, causing duplicate node-side processing - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` decodes and validates a legacy signed message via `msg.Validate()`, but that validation only checks structural fields and signature correctness — it never checks `MessageId` uniqueness, a timestamp, or nonce/expiry at the gateway layer itself. Downstream, whether a specific handler is protected against MessageId replay is inconsistent: `vault`, `confidentialrelay`, and `v2/http_trigger_handler` reject a repeated `req.ID`, but the legacy web API trigger handler (`core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage`) does not check for an existing entry before overwriting `h.savedCallbacks[msg.Body.MessageId]` and re-forwarding the message to all DON members via `don.SendToNode`.

### Finding Description
`gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) performs: decode → `msg.Validate()` (`core/services/gateway/api/message.go:54-88`, checks signature length/validity, field lengths, non-null suffixes) → dispatch to `h.HandleLegacyUserMessage`. Nowhere in this path is `MessageId` checked against previously-seen values, nor is a timestamp/expiry enforced at the gateway level.

For the legacy `web_api_trigger` capability path, `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-420`) does enforce a payload-level `Timestamp` staleness check (`payload.Timestamp` must not be older than `MaxAllowedMessageAgeSec`), but this only rejects *old* messages — it does not prevent replay of a message that is still within the freshness window. The handler then unconditionally does:
```
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
```
There is no lookup/rejection of an already-in-flight `MessageId` before this store-and-forward, unlike the vault handler's `newActiveRequest` (`core/services/gateway/handlers/vault/handler.go:466-481`, `"request ID already exists"`), the confidential relay handler (`core/services/gateway/handlers/confidentialrelay/handler.go:368-383`), or the v2 HTTP trigger handler's `setupCallback` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:398-405`, `"in-flight request ID"`). So an attacker who captures one valid signed legacy `web_api_trigger` request (same `MessageId`/`Signature`/`DonId`) can resend the identical raw bytes multiple times within the staleness window, and each call causes a fresh fan-out `SendToNode` to every DON member.

However, whether this actually causes *duplicate capability execution* depends on node-side deduplication that is outside `gateway.go`. On the node side, `core/capabilities/webapi/trigger/trigger.go` `processTrigger` does not appear to deduplicate on `TriggerEventId`/`MessageId` before pushing `capabilities.TriggerResponse` onto `trigger.ch` — it only applies a per-sender rate limiter (`trigger.rateLimiter.Allow`). Whether that rate limiter is sufficient to block a burst of identical replays, or whether some other layer (workflow engine execution-ID dedup) blocks it, could not be conclusively verified from the available index.

### Impact Explanation
If the replay reaches the node-side trigger unblocked, repeated identical `web_api_trigger` payloads would cause repeated workflow trigger firings (`trigger.ch <- tr`) attributed to the same `MessageId`/sender, i.e., duplicate capability invocation and DON-side resource consumption (fan-out to all DON members on every replay from the gateway alone is itself amplification: 1 attacker request → N `SendToNode` calls per replay). This matches a "duplicate capability execution / resource exhaustion" impact class, but is bounded by the per-sender `rateLimiter.Allow` gate at `processTrigger`, and is limited to the legacy `web_api_trigger` method path specifically (other legacy/JSON-RPC handlers already implement MessageId/request-ID dedup).

### Likelihood Explanation
Feasible: an attacker only needs to capture one valid signed request (network capture, log leak, or their own legitimate request) and can resend the raw bytes any number of times within `MaxAllowedMessageAgeSec`. No additional privilege beyond ordinary gateway client access is required, matching the stated unprivileged-attacker precondition. Repeatability is high (concurrent resends), but the actual duplicate-execution impact is throttled by the node-side per-sender `rateLimiter`, whose exact effectiveness against this specific replay pattern was not confirmed from the code available in the index.

### Recommendation
Add MessageId-based replay rejection in `HandleLegacyUserMessage` before overwriting `h.savedCallbacks`, mirroring the "already exists" guard used by the vault, confidentialrelay, and v2 HTTP trigger handlers. Additionally consider enforcing a nonce/one-time-use check at `gateway.ProcessRequest` or `msg.Validate()` (e.g., a short-lived MessageId cache) so all legacy handlers benefit consistently.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, construct a valid signed `triggerRequest` (as in `TestHandlerReceiveHTTPMessageFromClient`).
2. Call `handler.HandleLegacyUserMessage(ctx, msg, cb1)` — assert `don.SendToNode` invoked once per DON member.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, cb2)` again with the identical `msg` (same `MessageId`/`Signature`) before the staleness window expires — assert (current behavior) that `don.SendToNode` is invoked again for all members and `cb1`'s original saved callback is silently overwritten/orphaned (no error returned), demonstrating no MessageId-replay protection at this layer.
4. Expected secure behavior after fix: second call should return an error such as `"message ID already in flight"` and `don.SendToNode` should not be invoked a second time.
