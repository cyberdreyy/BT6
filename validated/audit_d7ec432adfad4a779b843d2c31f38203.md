## Title
Node-side signer weight double-counted when a signer flips from `Rejected` to `Accepted` for the same block, poisoning `total_weight_rejected`/`total_weight_approved` accounting - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node's `StackerDBListener` tracks per-block signer votes with two independent idempotency guards for the two message types: the `Accepted` path guards against double-counting using `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` path guards using `responded_signers.insert(slot_id)`. Because these are two different sets, a signer that first rejects and then later (validly) accepts the same block gets counted in *both* `total_weight_rejected` and `total_weight_approved`, and its rejection weight is never retracted. This can cause the node to spuriously treat a properly-signed block as rejected (or corrupt the failed-txid exclusion logic), even though the signer's live vote is acceptance.

### Finding Description
In `handle_signer_messages` (`stackerdb_listener.rs`), the `Accepted` branch only skips re-adding weight if the slot already appears in `gathered_signatures`: [1](#0-0) 

The `Rejected` branch instead guards on `responded_signers.insert(slot_id)`: [2](#0-1) 

Note that the `Accepted` branch *also* inserts into `responded_signers` (line 465), but that insertion result is discarded — it is not used to prevent a later `Accepted` weight-add, and the `Rejected` branch never removes anything from `gathered_signatures` or subtracts from `total_weight_rejected`.

Sequence that triggers the bug for a single signer S with weight w:
1. S sends `BlockResponse::Rejected` for block B (e.g. due to a transient `ConnectivityIssues`/`NoSortitionView`/`NotFoundError` rejection — reasons the signer itself is designed to reconsider, see `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`): [3](#0-2) 
   - Node: `responded_signers.insert(slot_id)` succeeds (first time) → `total_weight_rejected += w`.
2. The miner re-proposes the identical block (or the signer's local re-evaluation completes) and S now validates and signs it, sending `BlockResponse::Accepted` for the *same* `signer_signature_hash`.
   - Node: `gathered_signatures.contains_key(&slot_id)` is `false` (S never sent an Accepted before) → `total_weight_approved += w` is executed unconditionally.
   - Result: S's weight `w` is now present in *both* `total_weight_rejected` and `total_weight_approved` for block B, and `total_weight_rejected` is never decremented.

This breaks the equality that `total_weight_approved` and `total_weight_rejected` are disjoint, verified partitions of `total_weight` (the same equality that the signer-side code explicitly protects against, as evidenced by the `reject_then_accept` test and the changelog entry "Do not count both a block acceptance and a block rejection for the same signer/block" on the signer side): [4](#0-3) [5](#0-4) 

The node's `stackerdb_listener.rs`/`signer_coordinator.rs` pair, which is what the miner uses to decide `SignersRejected` vs. gathered-signature broadcast, has no equivalent protection.

### Impact Explanation
`signer_coordinator.rs::gather_signatures` consumes `block_status.total_weight_rejected` and `block_status.total_weight_approved` directly to decide the block's fate: [6](#0-5) 

Because a signer's weight can remain "stuck" in `total_weight_rejected` forever after that signer has actually accepted the block, repeated transient/reconsidered rejections from a handful of signers can accumulate stale rejection weight that never gets cleared. Once accumulated stale rejection weight crosses `total_weight - weight_threshold` (>30% by weight), the miner will:
- Enter the rejection branch (`NakamotoNodeError::SignersRejected`) even though the corresponding signers currently show acceptance and true consensus for the block may exist, wedging mining/block-broadcast for that tenure (a liveness impact: the node abandons a block that a genuine majority of current weight has actually signed).
- Simultaneously corrupt the `failed_txids`/`blocking_minority` bookkeeping used to permanently or temporarily exclude transactions, since that logic also relies on `total_weight_rejected` weight sums that no longer reflect current signer intent.

This is a liveness wedge triggerable by ordinary protocol operation (a signer transiently rejecting for a reconsiderable reason and then accepting after re-proposal) — no signer majority, key compromise, or auth token is required, only the natural reject→accept sequence that the signer client itself is designed to perform via `should_reevaluate_reject_reason`.

### Likelihood Explanation
The reject→accept sequence for the same `signer_signature_hash` is a normal, designed code path on the signer side (`should_reevaluate_block` / `should_reevaluate_reject_reason` explicitly allow reconsideration and re-signing for several reject reasons, e.g. `ConnectivityIssues`, `NoSortitionView`, `NotFoundError`, `NoSignerConsensus`, `Unknown`), and there is an existing integration test (`signer_reevaluates_proposal_with_missing_burn_view`) that exercises exactly this pattern of "reject, then reconsider and process again." Any transient network hiccup between a signer and a stacks-node/burn view, or a deliberately timed re-proposal by the block-producing miner, can reproduce the double-count on the node side without cooperation from other signers.

### Recommendation
Make the `Accepted` and `Rejected` branches in `stackerdb_listener.rs` share a single idempotency/attribution model per signer slot, mirroring the fix already applied on the signer side:
- Track, per slot, the signer's single current "vote weight contribution" (e.g., an enum `Accepted(weight)`/`Rejected(weight)` keyed by slot id) instead of two independently-guarded weight accumulators and two independently-guarded sets (`gathered_signatures` vs `responded_signers`).
- When a `Rejected` message arrives for a slot that is already in `gathered_signatures` (i.e., previously accepted), ignore it (already effectively done via the `!self.signer_db...has_committed` style checks used on the signer side) — but, symmetrically, when an `Accepted` message arrives for a slot that previously contributed to `total_weight_rejected`, first subtract that signer's weight from `total_weight_rejected` before adding it to `total_weight_approved`.
- Add a unit test analogous to `stacks-signer/src/signerdb.rs::reject_then_accept` but for `stackerdb_listener.rs`'s `BlockStatus`, asserting `total_weight_approved + total_weight_rejected <= total_weight` is preserved through arbitrary reject/accept orderings for the same signer and block.

### Proof of Concept
Not runnable from the index alone (requires a live signer/node harness), but the reachable sequence is:
1. Configure/observe a signer to reject a proposed block B with a reconsiderable reason, e.g. via the existing test scaffolding pattern in `signer_reevaluates_proposal_with_missing_burn_view` (`stacks-node/src/tests/signer/v0/missing_burn_block_proposal.rs:64-157`), which demonstrates a signer rejecting then being made to reprocess the identical proposal.
2. Let that same signer subsequently validate and sign B (send `BlockResponse::Accepted` for the identical `signer_signature_hash`).
3. Observe, on the node side, `stackerdb_listener.rs`'s `BlockStatus.total_weight_rejected` for B retains that signer's weight while `total_weight_approved` also gains it — i.e. `total_weight_approved + total_weight_rejected` for B exceeds what a single consistent vote per signer should produce, which `signer_coordinator.rs::gather_signatures` (lines 487-545) will use directly to decide rejection vs. broadcast.
