### Title
Unconditional overwrite of `savedCallbacks[MessageId]` in `HandleLegacyUserMessage` enables cross-request/cross-user response confusion - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the caller's `Callback` in `h.savedCallbacks[msg.Body.MessageId]` without checking whether an entry for that `MessageId` already exists, then fans the request out to all DON members with `errors.Join`. Because `MessageId` is a client-supplied field covered only by the client's own signature (not tied to session/connection identity by the gateway), any request (including a retried or colliding one) with the same `MessageId` silently replaces the previously stored callback, so the eventual DON response is delivered to the second/attacker-controlled `Callback` instead of the original caller.

### Finding Description
`HandleLegacyUserMessage` validates the message, then does: [1](#0-0) 
This write is unconditional — there is no `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists` guard. `MessageId` originates entirely from `MessageBody.MessageId`, a field chosen by the message's own signer and only constrained by length/null-byte checks in `Message.Validate()`: [2](#0-1) 
There is no uniqueness/replay check against previously-seen IDs. On the response path, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` and forwards the *first* DON response it receives to whatever `Callback` is currently registered under that key: [3](#0-2) 
So if two `HandleLegacyUserMessage` calls occur with the same `MessageId` (e.g., a caller retries after `errors.Join` aggregated a partial `SendToNode` failure, or two independent gateway clients pick/reuse the same ID), the second call's registration silently replaces the first. Whichever DON member responds first will have its payload routed to the *second* caller's `Callback`, not the original one. The `errors.Join(err, don.SendToNode(...))` fan-out loop itself doesn't roll back or de-register the already-saved callback on partial failure, so the map entry remains "live" and available to be overwritten by a subsequent identically-keyed request even though messages were already dispatched to some DON members for the first request.

This is reachable by an unprivileged/unauthenticated gateway client: `HandleLegacyUserMessage` is invoked directly per incoming user message with attacker-controlled `msg.Body.MessageId` and payload, and no authentication/authorization layer restricts which `MessageId` values a given caller may use, nor enforces that each ID may only be registered once.

### Impact Explanation
Scoped impact is cross-request/cross-user response confusion: a caller's HTTP/gateway response can be delivered to the wrong invoker's callback, potentially exposing the original requester's data (e.g., HTTP proxy response contents fetched via `MethodWebAPITarget`/`MethodComputeAction`) to a different caller who supplied a colliding `MessageId`. This maps to Chainlink's "unauthorized disclosure of information belonging to another user" bounty class rather than fund loss or node compromise, since no keys/secrets/job execution are directly affected — but it is a real confidentiality/isolation violation of per-request callback routing.

### Likelihood Explanation
No special privilege is required beyond being any client able to submit a signed gateway message (unauthenticated/unprivileged per the threat model). The attacker only needs to choose a `MessageId` that will also be used by a legitimate concurrent request (via prediction, brute force within the 128-byte ID space, or simply retry logic reusing the same ID after a reported partial send failure). Feasibility depends on how `MessageId`s are generated by legitimate clients (e.g., predictable counters/timestamps would make collision easy; high-entropy random IDs make it harder but not impossible, especially combined with legitimate retry behavior after a partial-failure error is returned). The bug itself is deterministically reproducible: two sequential `HandleLegacyUserMessage` calls with the same `MessageId` and two different `Callback` mocks will show the map entry overwritten.

### Recommendation
Add an idempotency/collision check before registering a callback: if `h.savedCallbacks[msg.Body.MessageId]` already exists, either reject the new request (return an error response to the caller) instead of overwriting, or key callbacks by a tuple that also includes sender/connection identity so collisions across different callers cannot occur. Additionally, on partial `SendToNode` failures in the fan-out loop, consider explicitly deleting the just-registered callback (or marking the request as failed) so a legitimate retry with the same `MessageId` is safely handled rather than silently colliding with a still-pending entry.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a mocked `handlers.DON` whose `SendToNode` succeeds for member A and fails for member B (returns non-nil error), and two mock `handlers.Callback` implementations, `cbA` and `cbB`, each recording whether `SendResponse` was invoked and with what payload.
2. Build a valid signed `api.Message` with `Body.MessageId = "same-id"` and call `h.HandleLegacyUserMessage(ctx, msg, cbA)`. Assert it returns a non-nil error (from `errors.Join`) while `h.savedCallbacks["same-id"].Callback == cbA`.
3. Call `h.HandleLegacyUserMessage(ctx, msg /* same MessageId */, cbB)` again. Assert `h.savedCallbacks["same-id"].Callback == cbB`, confirming `cbA` was silently overwritten with no error/notification.
4. Simulate a DON node response for `MessageId = "same-id"` via `HandleNodeMessage` and assert that `cbB.SendResponse` is invoked (not `cbA`), demonstrating the response-confusion outcome even though `cbA`'s underlying request was the one actually delivered to member A.
