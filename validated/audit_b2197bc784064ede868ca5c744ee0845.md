## Title
Unvalidated `integratorFeeAmount + protocolFeeAmount` in `createDstEscrow` causes withdrawal underflow revert, permanently blocking `EscrowDst.withdraw` during the live swap window — (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw` subtracts `integratorFeeAmount` and `protocolFeeAmount` (taken verbatim from `immutables.parameters`) from `immutables.amount` with no bounds check: [1](#0-0) 

This is the same root cause as the external report: a fee value is subtracted from a principal amount with no guarantee the subtraction cannot underflow. On the source-chain path, `BaseEscrowFactory._postInteraction` explicitly guards against this by rejecting the fill if `integratorFeeAmount + protocolFeeAmount >= takingAmount`: [2](#0-1) 

However `createDstEscrow`, which is invoked directly by the taker/resolver (an unprivileged actor per the "destination escrow creation" entry point) with an arbitrary `dstImmutables.parameters` blob (containing `protocolFeeAmount` and `integratorFeeAmount`), performs **no equivalent check**: [3](#0-2) 

### Finding Description
The `dstImmutables` struct passed into `createDstEscrow` (including `parameters` holding `protocolFeeAmount`/`integratorFeeAmount`) is fully caller-controlled calldata. `createDstEscrow` only checks that `msg.value` matches the expected safety-deposit/native amount and that the timelocks are consistent with `srcCancellationTimestamp`; it never verifies `protocolFeeAmount + integratorFeeAmount < immutables.amount`. Because the fee amounts are embedded in `immutables.parameters`, which is part of the CREATE2 salt via `immutables.hashMem()`, a taker can deploy a syntactically valid `EscrowDst` clone whose committed fees exceed the deposited `amount`.

When the maker (or anyone) later calls `withdraw`/`publicWithdraw`, `_withdraw` first pays out the (inflated) fee amounts, then computes:
```solidity
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
``` [4](#0-3) 
which underflows and reverts the entire transaction (including the fee transfers, since Solidity ≥0.8 reverts on underflow and rolls back state). Every subsequent withdrawal attempt with the correct secret will revert identically, so the maker can never receive destination funds during the withdrawal window; funds can only ever return to the taker via `cancel()` once the cancellation timelock elapses.

This also creates a secondary, more severe consequence: because `withdraw`/`publicWithdraw` require the plaintext `secret` as a calldata argument, a maker attempting to withdraw against such a maliciously configured escrow will have their reverted transaction (and therefore the secret) visible in the mempool/tx trace. A malicious taker who deliberately engineers the fee-underflow condition can watch for the maker's (failing) withdrawal attempt, extract the secret from the reverted calldata, and immediately use it to claim the maker's principal on the source-chain `EscrowSrc` via `withdrawTo`, while the destination escrow eventually cancels back to the same taker.

### Impact Explanation
- At minimum this matches "Medium: smart contract unable to operate because required token/native balances can be broken by an unprivileged actor" — the taker (unprivileged, entering via the in-scope "destination escrow creation" flow) can break `EscrowDst.withdraw`/`publicWithdraw` for the entire lifetime of the escrow's withdrawal window purely by choosing bad fee parameters at creation time, with no way for the contract or the maker to recover except waiting for cancellation.
- Combined with the secret-exposure-on-revert mechanic, this escalates to theft of the maker's source-chain principal ("direct theft of user funds in motion" — Critical/High), because the malicious taker can complete their own source-side withdrawal using the leaked secret while the destination leg is guaranteed to fail and cancel back to the same taker.

### Likelihood Explanation
The trigger requires nothing beyond an already-supported, permissionless call: a taker calling `createDstEscrow` with attacker-chosen `parameters`. No governance, oracle manipulation, or privileged role is needed — it only requires the resolver/taker to be dishonest, which is within the "unprivileged user" attacker model and not excluded (this is not a "malicious relayer/node/bridge" assumption, since `createDstEscrow` is a normal user-facing entry point). The main mitigating factor is that a well-behaved off-chain relayer/maker client is expected to independently recompute `addressOfEscrowDst`/verify `parameters` against the source-chain `SrcEscrowCreated` event before revealing the secret; if that off-chain check is diligently enforced, exploitation is prevented. The on-chain contracts themselves, however, provide no such enforcement, unlike the symmetric check present in `_postInteraction` for the source path.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`:
```solidity
uint256 protocolFeeAmount = immutables.protocolFeeAmount();
uint256 integratorFeeAmount = immutables.integratorFeeAmount();
if (protocolFeeAmount + integratorFeeAmount >= immutables.amount) revert InvalidFeeAmounts();
```
Alternatively/additionally, have `EscrowDst._withdraw` fail safe (skip fee payout and pay the maker the full amount, or cap fees) instead of unconditionally reverting the whole call, closing the secret-exposure vector.

### Proof of Concept
1. Taker fills the source order normally, causing `EscrowSrc` to lock the maker's tokens with `hashlock = H(secret)`.
2. Taker calls `createDstEscrow` with `dstImmutables.parameters = abi.encode(protocolFeeAmount, integratorFeeAmount, protocolFeeRecipient, integratorFeeRecipient)` where `protocolFeeAmount + integratorFeeAmount > dstImmutables.amount`, and funds the escrow with exactly `dstImmutables.amount` tokens (or native value) as required by [5](#0-4) . This call succeeds — no check rejects it.
3. When the maker calls `EscrowDst.withdraw(secret, immutables)` after `DstWithdrawal` timelock, `_withdraw` reverts at the underflow line every time: [6](#0-5) .
4. The taker observes `secret` in the maker's reverted transaction, immediately calls `EscrowSrc.withdrawTo(secret, taker, srcImmutables)` to claim the maker's principal on the source chain [7](#0-6) , then after `DstCancellation` calls `EscrowDst.cancel` to reclaim the destination deposit back to themselves [8](#0-7) , netting both legs of the swap while the maker receives nothing on the destination chain.

        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);

            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);

        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
