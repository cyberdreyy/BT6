I found a concrete analog of the reported bug class in the **Gloas** builder-withdrawal machinery. Instead of a hardcoded Go constant, the spec carries a stale/uncapped `amount` field through the withdrawal pipeline, so the value credited on the execution layer can diverge from the value actually debited on the consensus layer.

### Title
Builder withdrawal `Withdrawal.amount` is not capped to the builder's actual balance, creating a payload/payment mismatch - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` builds each `Withdrawal` record using the raw, previously-queued `builder_pending_withdrawals[i].amount` value, while the actual balance debit performed later in `apply_withdrawals` is capped with `min(withdrawal.amount, builder_balance)`. Because the execution layer credits the `amount` field of the committed `Withdrawal` object verbatim, this can commit to paying out more Gwei than is actually removed from the builder's consensus-layer balance.

### Finding Description
`get_builder_withdrawals` copies the requested amount straight from `state.builder_pending_withdrawals` into the `Withdrawal.amount` field without checking it against `builder.balance`: [1](#0-0) 

That `Withdrawal` list becomes `state.payload_expected_withdrawals`, which is the value the execution payload is required to match (the withdrawals root committed by the block). Later, when the withdrawal is actually applied to consensus-layer state, the debit is silently capped: [2](#0-1) 

So if a builder's balance is smaller than the queued `builder_pending_withdrawals[i].amount` at the time the withdrawal sweep runs, the state only loses `min(amount, balance)` Gwei, but the `Withdrawal` record — and therefore the amount the execution layer will credit to `fee_recipient`/`execution_address` — still states the full, uncapped `amount`. This breaks the required equality between what a block commits to pay out and what consensus state actually removes from an account: Gwei is effectively paid without a corresponding debit, i.e. created.

This is precisely mirrored by the existing spec test suite, which documents the discrepancy as expected rather than treating it as a bug: the withdrawal record retains the full requested amount even though the builder balance is only reduced to zero: [3](#0-2) [4](#0-3) 

The same asymmetry is documented in the AI-generated report for `process_withdrawals`, which explicitly notes "Actual = `min(amount, builder.balance)`" for the state-side debit while the withdrawal amount itself is the unclamped requested value: [5](#0-4) 

### Impact Explanation
If this uncapped amount is faithfully credited by the execution layer (which is the standard withdrawal semantics — the EL adds `withdrawal.amount` to the target address's balance), then Gwei is created out of nothing: the execution-layer payment exceeds the consensus-layer debit. This falls squarely in the Critical impact bucket described by the rules ("Gwei created ... or paid to a non-owner", "a payload executed or paid that the block did not commit to" in the sense that the commit and the actual balance change diverge).

### Likelihood Explanation
Reaching the mismatch does not require a malicious peer or coalition: it only requires a builder's balance to fall below a previously queued `builder_pending_withdrawal.amount` before the withdrawal is swept out — for example when multiple builder payments/withdrawals accumulate against the same builder faster than `can_builder_cover_bid` accounting anticipates, or through ordinary sequencing of `process_builder_pending_payments` and `process_withdrawals` across epochs. The condition is exercised directly by existing unit tests, showing it is a reachable and even spec-anticipated state, not a purely theoretical corner case.

### Recommendation
Cap the amount written into the `Withdrawal` record itself (in `get_builder_withdrawals`) to `min(withdrawal.amount, builder.balance)`, mirroring the cap already applied in `apply_withdrawals`, so the value committed to the execution payload always matches the value actually debited from consensus-layer state.

### Proof of Concept
1. Queue a `BuilderPendingWithdrawal` for `builder_index` with `amount = 5_000_000_000` Gwei while `state.builders[builder_index].balance = 1_000_000_000` Gwei (as in `test_builder_withdrawal_insufficient_balance`).
2. Run `get_expected_withdrawals` / `process_withdrawals`: the resulting `Withdrawal` entry has `amount == 5_000_000_000`, but `state.builders[builder_index].balance` becomes `0` (only 1 ETH debited).
3. The execution payload commits to and (per standard EL withdrawal processing) pays out `5_000_000_000` Gwei to the builder's `fee_recipient`, while only `1_000_000_000` Gwei was ever removed from any account — a 4 ETH mismatch between commitment and actual state change. [6](#0-5)
