### Title
v1 signer's tenure-change duplicate-block check only consults global acceptance, allowing it to sign a second, conflicting tenure-start block before its own locally-accepted block globalizes - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::validate_tenure_change_payload` in the v1 chainstate module guards against signing two tenure-start blocks for the same tenure by calling `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0)  instead of `get_last_signed_block`, which is what the v2 equivalent uses [2](#0-1) . Because global acceptance requires a threshold of signer signatures while local acceptance only requires this one signer's own signature, there is a window between "I (this signer) signed B1" and "B1 globally accepted" during which the v1 check returns `None` and lets the same signer sign a conflicting tenure-start block B2 for the same consensus hash.

### Finding Description
The v2 code comment explicitly documents the intended safety property: "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place if it failed to reach consensus." [3](#0-2)  This is implemented by querying `get_last_signed_block`, which (per this v2 comment and its usage) covers both `LocallyAccepted` and `GloballyAccepted` states. The v1 implementation of the exact same guard, however, queries `get_last_globally_accepted_block` [4](#0-3) , which only returns a result once the block has crossed the group signature threshold — not merely been signed locally by this signer.

Exploit flow for a pure v1 signer set (mixed v1/v2 in one reward cycle is not possible, so this only affects cycles running the older signer protocol):
1. Miner proposes tenure-start block B1 for consensus hash CH. A v1 signer S evaluates it, all other checks pass, `get_last_globally_accepted_block(CH)` is `None` (nothing signed yet), so S signs B1. S's local state now records B1 as `LocallyAccepted` (`signed_self`), but the group-wide threshold has not yet been reached (e.g., other signers are slow, network is partitioned, or the miner deliberately withholds B1 from enough signers to delay quorum).
2. Before global acceptance is recorded, the same miner (or an equivocating actor with the miner's key/slot) crafts a second tenure-start block B2 for the same CH with a different parent-block choice or transaction set, and gossips it to signer S (or another v1 signer who also only saw B1 locally-signed).
3. S evaluates B2 via `check_proposal` → `validate_tenure_change_payload`. All prior checks (parent tenure match, `check_tenure_change_confirms_parent`, `check_parent_tenure_choice`) can pass because they don't inspect the conflicting sibling block. The duplicate check calls `get_last_globally_accepted_block(CH)`, which still returns `None` because B1 has not globalized. S therefore signs B2, producing two mutually exclusive tenure-start blocks signed by the same signer for the same tenure.
4. If enough other v1 signers are in the same state (each individually signed B1 locally but haven't seen global confirmation), the miner can potentially assemble threshold signatures for both B1 and B2, creating a genuine chain-safety violation (equivocation/fork at the tenure-start point) — the exact uniqueness property v2's `get_last_signed_block` was designed to close.

Existing guards that fail to stop this: the sortition/miner-pubkey checks in `check_proposal` only verify the proposer is a legitimate current/last-sortition miner and don't detect sibling tenure-start blocks; `check_tenure_change_confirms_parent` and `check_parent_tenure_choice` validate parent linkage, not intra-tenure uniqueness; only the final `get_last_globally_accepted_block`-based check (line 505) is meant to catch this, and it is the one with the gap.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property for tenure-start blocks in v1 signer sets: an unprivileged single-slot miner can induce affected v1 signers to sign two conflicting blocks for one tenure before the first globalizes. If a sufficient number of v1 signers are simultaneously in the "locally-signed-but-not-yet-global" window (a realistic condition during normal quorum-gathering latency, network partition, or timing manipulation by the miner), both blocks could accumulate enough signatures to be seen as valid by different observers, producing a chain-safety violation (a genuine equivocation/fork at a tenure boundary). This matches the "Critical" category: a signer signing a conflicting block, and losing the equivocation guard.

### Likelihood Explanation
Preconditions: a pure v1 signer set (v1/v2 mixing within one cycle is not possible, so this is scoped to cycles still running the v1 protocol) and a tenure where B1 has reached `LocallyAccepted` for at least one signer S but not yet `GloballyAccepted` cycle-wide. The attacker capability is exactly the allowed unprivileged one: win a single miner slot, then gossip a second `BlockProposal` (B2) for the same consensus hash before quorum finalizes B1. No majority of signers, no compromised keys, no auth_token, and no node/local access are required. The attack is repeatable every time a v1-protocol tenure exhibits a signing/quorum-latency window, which is a normal and expected occurrence (not an edge case), making this readily exploitable during any v1-only reward cycle.

### Recommendation
Change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to call `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the v2 logic at `stacks-signer/src/chainstate/v2.rs` lines 344-345, so that a signer refuses to sign a second tenure-start block once it has locally signed a first one for the same tenure, closing the local-signature race window.

### Proof of Concept
Add a test in `stacks-signer/src/chainstate/tests/v1.rs`:
1. Construct a `SortitionsView` (v1) and a `SignerDb` backed by a temp sqlite file, with a valid current sortition and tenure-change block B1 for consensus hash `CH`.
2. Call `signer_db.mark_locally_accepted` (or the equivalent internal call path that `check_proposal`/block-signing invokes) on B1's signer_signature_hash, transitioning it to `LocallyAccepted`/`signed_self`, without ever calling the global-acceptance path.
3. Assert `signer_db.get_last_globally_accepted_block(&CH)` returns `None` (confirms the precondition), and `signer_db.get_last_signed_block(&CH)` returns `Some(B1)` (confirms B1 is locally signed).
4. Construct B2: same `consensus_hash = CH`, same `prev_tenure_consensus_hash`/parent tenure as B1, but a different block body/signer_signature_hash (a conflicting sibling tenure-start block).
5. Call `sortitions_view.validate_tenure_change_payload(&proposed_by, &tenure_change_payload_for_B2, &B2, &mut signer_db, &client)`.
6. Assert the current (buggy) behavior returns `Ok(())` — demonstrating the signer would sign B2 despite having already locally signed B1 for tenure `CH`.
7. After applying the fix (swapping to `get_last_signed_block`), re-run the same test and assert it now returns `Err(RejectReason::DuplicateBlockFound)`.
