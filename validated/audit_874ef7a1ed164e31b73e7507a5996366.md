### Title
Older-epoch withdraw receipts escape `stopEpochWithDuration` loss haircut because `lossRecoveryPriceByEpoch`/`lastWithdrawRequest` are keyed to a single epoch — underfunded claim reserve, last claimants frozen - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a "context field programmed under the wrong identifier" defect: the event-ring index was written to a register field that hardware v5.0+ never reads, so a required index was effectively never programmed and completions hung forever. The vault analog is in `IdleCreditVault`'s loss-adjusted withdrawal accounting. When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` stores a single haircut under `lossRecoveryPriceByEpoch[epochNumber]` (the stop epoch). At claim time, `_claimLossAdjustedWithdrawRequest` only applies that haircut to receipts tagged at `lastWithdrawRequest[_user]` — i.e. receipts requested in the most recent request epoch. Receipts requested in *earlier* epochs and still unclaimed are haircutted in the aggregate funding math (`pendingBasis`) but are paid out at par through `_claimFundedWithdrawRequest`. The haircut is "not programmed" for those older receipts.

### Finding Description
`requestWithdraw` records receipts per epoch (`withdrawsRequestsByEpoch[_user][currentEpoch]`) and a single marker `lastWithdrawRequest[_user] = currentEpoch` (lines 282–293). The only ordering guard (lines 263–270) blocks a new request when the *previous* request epoch already has a `lossRecoveryPrice`. It does not prevent a user from holding receipts across epochs when no loss has occurred yet.

When a loss arrives via `collectWithdrawFunds` (lines 411–430), `previewLossAdjustedWithdrawFunds` computes `pendingToFund = pendingBasis - pendingLoss` where `pendingLoss` is shared pro-rata across **all** `pendingWithdraws` (lines 440–460). So the funded reserve reflects a haircut applied to every pending receipt, regardless of request epoch.

At claim time the asymmetry appears:

- `_claimLossAdjustedWithdrawRequest` (lines 789–801) reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and `_clearWithdrawClaimForEpoch` clears only that one epoch's receipts.
- `_claimFundedWithdrawRequest` (lines 319–350) then pays `withdrawsRequests[_user]` — which still contains the older-epoch receipts — **at par**, provided `epochNumber > lastWithdrawRequest[_user]`, which is true for any epoch-older receipt.

Concretely: user A requests in epoch N and does not claim; user B requests in epoch N+1 (or A requests again in N+1 — the guard passes because `lossRecoveryPriceByEpoch[N] == 0`). Stop of epoch N+1 takes a loss, storing `lossRecoveryPriceByEpoch[N+1] = price < 1` and funding only `(B_N + B_{N+1}) * price` into the strategy. A's epoch-N receipt has `lossRecoveryPriceByEpoch[N] == 0`, so it pays full `B_N`; B pays `B_{N+1} * price`. Total payouts = `B_N + B_{N+1}*price` > reserve `= (B_N + B_{N+1})*price`. Shortfall = `B_N * (1 - price)`.

### Impact Explanation
Broken invariant: pro-rata loss socialization and solvency of the funded claim reserve. Older-epoch receipts escape the haircut that was already charged against them in `pendingToFund`, so first claimants are overpaid and the strategy's underlying reserve is drained below what later (correctly haircutted) claimants are owed. The last claimants' `claimWithdrawRequest` reverts on the underflowing `safeTransfer` in `_transferFundedClaim` — permanent freezing of their unclaimed funds, with quantified shortfall equal to `Σ olderReceipts × (1 − lossRecoveryPrice)`. With a 50% haircut and one epoch-old receipt equal to half the pending basis, the haircutted claimant can lose ~25% of basis beyond the intended haircut.

### Likelihood Explanation
Requires a `stopEpochWithDuration` loss while at least one receipt from an earlier epoch remains unclaimed — normal operation whenever users do not claim promptly (the code explicitly supports claiming "at any time even if a new epoch started", line 323). Attacker path is unprivileged: a lender can deliberately leave an epoch-N receipt unclaimed, request or wait for a second epoch, and withdraw at par immediately after a loss-stop, front-running haircutted claimants. No existing guard stops it: the `lossRecoveryPrice` guard only fires when the *prior* epoch already carried a loss, `_claimFundedWithdrawRequest` performs no epoch-range check against `lossRecoveryPriceByEpoch`, and the funded path cannot distinguish pre-loss receipts.

### Recommendation
Track which epochs' receipts each pending claim belongs to, or enforce the invariant that all `pendingWithdraws` at a loss-stop belong to the epoch receiving the haircut. Options: (a) in `requestWithdraw`, also revert when the user has any outstanding unfunded receipt (`withdrawsRequests[_user] != 0` or open `apr0Users.principal`) once a prior epoch has been stopped without full funding — i.e. force claim/settlement of earlier receipts before a new request; (b) store a `lossRecoveryPriceByEpoch` entry keyed to every epoch with outstanding receipts at loss time, not only `epochNumber`; (c) at `_claimFundedWithdrawRequest`, check `lossRecoveryPriceByEpoch` across the user's unsettled epochs rather than only `lastWithdrawRequest`. The simplest fix consistent with existing design: maintain a per-user "earliest unfunded epoch" pointer and require receipts to be claimed (or haircutted) in epoch order, or disallow inter-epoch mixing by reverting new requests while any older receipt remains unclaimed past its funding stop.

### Proof of Concept
```solidity
// Foundry fork PoC, mode: fixed-APR, standard IdleCDOEpochVariant.
// Phase: buffer after stop of epoch N (receipt unfunded but valid).
IdleCreditVault strat = IdleCreditVault(address(strategy));

// Epoch N buffer: alice requests, never claims.
vm.prank(alice);
cdoEpoch.requestWithdraw(aaAlice, address(AAtranche));
uint256 aliceBasis = strat.withdrawsRequests(alice);

// Stop epoch N fully funded; start + run epoch N+1 buffer.
_stopEpochAndStartNext();               // epochNumber -> N+1, alice receipt funded at par value

// Epoch N+1 buffer: bob requests (guard passes: lossRecoveryPriceByEpoch[N] == 0).
vm.prank(bob);
cdoEpoch.requestWithdraw(aaBob, address(BBtranche));
uint256 bobBasis = strat.withdrawsRequests(bob);

// Borrower repays with a realized loss at stop of epoch N+1.
// previewLossAdjustedWithdrawFunds haircuts pendingBasis = aliceBasis + bobBasis.
uint256 loss = (aliceBasis + bobBasis + activeBasis) / 4; // e.g. 25% of total basis
_dealBorrowerAndWarp();
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, loss, DURATION);
// collectWithdrawFunds pulled only (aliceBasis + bobBasis) * price into the strategy.

// Alice claims: lossRecoveryPriceByEpoch[N] == 0 -> funded path pays FULL basis.
vm.prank(alice);
cdoEpoch.claimWithdrawRequest();        // receives aliceBasis (escapes haircut)

// Bob claims: haircut applied, but reserve is now short by aliceBasis * (1 - price).
uint256 reserve = underlying.balanceOf(address(strat));
uint256 bobOwed = bobBasis * strat.lossRecoveryPriceByEpoch(N + 1) / 1e18;
assertLt(reserve, bobOwed);             // insolvency: bob's claim reverts / is frozen
vm.prank(bob);
vm.expectRevert();                      // safeTransfer underflow on _transferFundedClaim
cdoEpoch.claimWithdrawRequest();
```
Same-user variant also works: alice requests again in epoch N+1 (`lastWithdrawRequest` moves to N+1), the loss-stop clears only her N+1 receipt at `price`, and the funded path then pays her epoch-N remainder at par — identical reserve shortfall for other claimants.
