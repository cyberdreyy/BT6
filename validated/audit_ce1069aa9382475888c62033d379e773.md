### Title
Group-level rate limiter uses a stale read-only capacity check that multiple concurrent/batched withdrawals or borrows can all pass simultaneously, allowing outflow far beyond the configured cap - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
`record_withdrawal_outflow` checks a withdraw/borrow's USD value against `group.rate_limiter`'s `effective_remaining_capacity` but never decrements or persists that capacity — the check is read-only, and the real accounting update happens asynchronously through `update_group_rate_limiter`, called later by an off-chain aggregator. This mirrors the MagicSpend M-01 pattern exactly: a limit-check performed against a snapshot of remaining capacity that is not synchronously updated, so any number of qualifying operations issued before the off-chain settlement lands can each independently pass the same check.

### Finding Description
In `record_withdrawal_outflow`, when `group_rate_limit_enabled` is true, the function computes `value` (USD value of the outflow) and compares it against `group.rate_limiter.hourly/daily.effective_remaining_capacity(clock.unix_timestamp)`, returning an error only if `value > remaining` [6](#0-5) . Crucially, this comparison uses `group: &MarginfiGroup` passed by immutable reference, and the group's `rate_limiter.cur_window_outflow` counter is never incremented as part of this call — `try_record_outflow` (which does mutate state) is only invoked on the *bank-level* limiter, not the group-level one [7](#0-6) .

The `group` account passed into `LendingAccountWithdraw` is loaded as a non-`mut` `AccountLoader<'info, MarginfiGroup>` [1](#0-0) , confirming the group's rate-limiter counters are architecturally incapable of being updated inside this instruction. The actual mutation of `group.rate_limiter` happens exclusively in `update_group_rate_limiter`, gated to the `delegate_flow_admin`, which processes off-chain aggregated `RateLimitFlowEvent`s at intervals (documented as ~every 10 minutes, enforced by `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` of 1,500 slots) [8](#0-7) .

This is the identical root cause to the MagicSpend M-01 bug class: a capacity/balance check performed against state that is not updated at the same time the check passes, enabling multiple qualifying operations to each independently "reserve" against the same remaining capacity before it is truly consumed. The project's own documentation states this explicitly: "The group rate limiter is checked read-only during user actions, then settled later from aggregated events... This avoids serializing all activity in a group through one writable group account" [9](#0-8) .

### Impact Explanation
Any number of withdraw/borrow instructions (across `lending_account_withdraw`, `lending_account_borrow`, and the Kamino/Drift/Solend/JupLend integration withdraws) submitted before the off-chain admin's next `update_group_rate_limiter` call — whether packed into one transaction, or simply issued in quick succession within the same aggregation window — will each independently see the pre-settlement `remaining capacity` and pass the check. The group-level hourly/daily USD outflow cap, intended to bound a group's aggregate outflow (e.g., during an oracle/market stress event or a liquidity-drain scenario the limiter is meant to guard against), can therefore be exceeded by an arbitrarily large multiple, limited only by how many withdraw/borrow instructions a user (or colluding users) can issue before the aggregator's next settlement — this is directly analogous to how batched `MagicSpend` userOps could all pass a stale balance check and jointly overdraw the paymaster. Since bank-level rate limiting still enforces its own real cap per bank, the blast radius is bounded by the sum of all banks' bank-level caps, but the group-level protection meant to bound aggregate cross-bank outflow is effectively bypassable within the admin update interval.

### Likelihood Explanation
Likelihood is moderate-to-high in practice whenever group-level rate limiting is enabled: this requires no special privilege — any account holder who can withdraw/borrow can trigger this, and the window of exposure (up to `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` ≈ 10 minutes, or longer if the aggregator is delayed) is entirely predictable and repeatable each cycle. The test suite itself demonstrates the group's counter staying at 0 across 4 separate user actions until a single batched admin update is applied [5](#0-4) , confirming the staleness window is real and reproducible, not merely theoretical.

### Recommendation
Given the explicit architectural tradeoff (avoiding a writable group account on every instruction), a full "state-tracks-remaining-balance" fix akin to the mitigation initially attempted for MagicSpend (PR coinbase/magic-spend#16) is not straightforward here either, for the same underlying reason: serializing per-instruction updates would defeat the purpose of the read-only design. Consider adopting a probabilistic/defense-in-depth mitigation analogous to Coinbase's final fix (`maxWithdrawDenominator`): cap any single outflow to a fraction of the currently perceived remaining capacity (e.g., disallow single withdraws/borrows larger than `remaining_capacity / N`), shortening the effective abuse window (`MAX_RATE_LIMIT_UPDATE_LAG_SLOTS`) as much as operationally tolerable, and/or requiring the delegate flow admin to settle more frequently under detected high-outflow conditions. Additionally, document this residual risk clearly for auditors/admins so the group-level limit is understood as a soft/eventual cap rather than a hard real-time one.

### Proof of Concept
1. Admin configures a group hourly outflow limit of 10 USD via `configure_group_rate_limits`, with bank-level limits set high (e.g., 1,000 USDC) so only the group limit is binding.
2. Within the same aggregation window (before any `update_group_rate_limiter` call), a user (or several colluding users under the same group) issues four separate borrow instructions of 3, 2, 1, and 1 USD notionally, plus a repay of 1 USD — each instruction reads `group.rate_limiter.hourly.effective_remaining_capacity()` against the *same unmodified* group state (still `cur_window_outflow == 0`), and each independently passes the "value <= remaining" check, exactly as demonstrated in `tests/specs/basic/17_rateLimiter.spec.ts` lines 787-827 [5](#0-4) .
3. Only after all of these succeed does the admin later call `update_group_rate_limiter` and discover the true net outflow (6 USD gross, 5 USD net) — at which point the damage (successful withdrawals exceeding what a real-time cap would have allowed at any single check point) is already done, since each of the 4 actions was validated independently against a stale zero baseline rather than against each other's cumulative effect.
4. By repeating this pattern with more simultaneous/rapid actions (or a single transaction containing many withdraw instructions against different banks in the same group, all checking the same unmutated `group` account), the attacker can drive aggregate group outflow to a multiple of the configured cap before the next admin settlement closes the window, directly analogous to userOp1/userOp2 both passing MagicSpend's stale `address(this).balance` check in the same batch.

```rust
const MAX_RATE_LIMIT_UPDATE_LAG_SLOTS: u64 = 1_500; // ~10 minutes at ~400ms/slot

/// (delegate_flow_admin only) Update the group rate limiter inflow/outflow state.
///
/// The delegate flow admin aggregates `RateLimitFlowEvent` events off-chain,
/// computes the USD-denominated inflows and outflows, and calls this instruction
/// at intervals to update the group rate limiter state.
///
/// This avoids requiring the group account to be writable (mut) in every user-facing
/// instruction, which would serialize all transactions for a group into a single slot.
pub fn update_group_rate_limiter(
    ctx: Context<UpdateGroupRateLimiter>,
    outflow_usd: Option<u64>,
    inflow_usd: Option<u64>,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,
) -> MarginfiResult {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let clock = Clock::get()?;

    check!(
        outflow_usd.is_some() || inflow_usd.is_some(),
        MarginfiError::GroupRateLimiterUpdateEmpty
    );
    validate_event_slots(
        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::GroupRateLimiterUpdateFutureSlot
    );
    check!(
        clock.slot.saturating_sub(event_end_slot) <= MAX_RATE_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::GroupRateLimiterUpdateStale
    );
    check!(
        update_seq == group.rate_limiter_last_admin_update_seq.saturating_add(1),
        MarginfiError::GroupRateLimiterUpdateOutOfOrderSeq
    );

    if let Some(inflow) = inflow_usd {
        check!(
            is_valid_rate_limit_amount(inflow),
            MarginfiError::InvalidConfig
        );
        group
            .rate_limiter
            .record_inflow(inflow, clock.unix_timestamp);
        msg!("Group rate limiter inflow recorded: {} USD", inflow);
    }

    if let Some(outflow) = outflow_usd {
        group
            .rate_limiter
            .try_record_outflow(outflow, clock.unix_timestamp)?;
        msg!("Group rate limiter outflow recorded: {} USD", outflow);
    }
```

```markdown
## Why These Flows Exist

Both systems avoid making the group account writable in every user transaction.

- Bank-level rate limiting is updated inline because the bank account is already writable.
- Group-level rate limiting is checked read-only during user actions, then settled later from
  aggregated events.
- Deleverage withdraw limits are also checked read-only during the withdraw, then settled later from
  aggregated events.

This avoids serializing all activity in a group through one writable group account.

## Group Rate Limit Flow

### 1. Configuration

Two levels exist:

- Bank rate limits: `configure_bank_rate_limits`
  - Tracks native token net outflow on the bank account.
- Group rate limits: `configure_group_rate_limits`
  - Tracks USD net outflow across the whole group.

Each has hourly and daily windows.

- `0` disables that window.
- Deposits/repays release capacity.
- Withdraws/borrows consume capacity.

### 2. User transaction path

During a withdraw or borrow:

- The bank rate limiter is updated immediately on the writable bank account.
- The group rate limiter is only checked read-only.
- The protocol converts the flow to USD using the instruction price/oracle path.
- If the projected group hourly or daily capacity is exceeded, the user instruction fails.
- A `RateLimitFlowEvent` is emitted for off-chain aggregation.
```
