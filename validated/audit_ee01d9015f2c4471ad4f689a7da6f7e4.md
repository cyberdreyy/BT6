### Title
`DuplicateBlockFound` guard in `validate_tenure_change_payload` only detects `GloballyAccepted` blocks, missing `LocallyAccepted` blocks in the same tenure - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`validate_tenure_change_payload` rejects a second tenure-change block for tenure T only if `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` returns `Some`, i.e., only if a block in T has already reached the `GloballyAccepted` state. A block that this signer has already locally accepted (signed) in T but that has not yet crossed the global-acceptance threshold is invisible to this check, unlike v2's use of `get_last_signed_block`.

### Finding Description
The relevant code is: [1](#0-0) 

This queries `get_last_globally_accepted_block`, whose name and usage pattern (contrasted with v2's `get_last_signed_block`, confirmed to exist as a distinct call in `stacks-signer/src/chainstate/v2.rs`) implies it only matches blocks recorded as `GloballyAccepted` in the local `SignerDb`, not `LocallyAccepted` ones. If a signer has already locally accepted block A (a tenure-change block for T) but A has not yet gathered enough signatures to be globally accepted, and an attacker (the current miner slot holder) then proposes a second tenure-change block B1 also for T, this specific check in `validate_tenure_change_payload` returns `Ok` for B1 because `get_last_globally_accepted_block` returns `None`.

I was not able to verify within the available tool budget whether `check_block_against_signer_db_state` in `stacks-signer/src/v0/signer.rs` (invoked after validate-ok, before the signer actually emits a signature) independently re-checks for an existing `LocallyAccepted` block in tenure T before allowing a signature on B1. The question asserts this second gate only re-runs `check_tenure_change_confirms_parent` against the parent tenure and does not re-check duplication within T itself, but I could not confirm this claim by reading the function body directly.

### Impact Explanation
If confirmed, this would allow two distinct tenure-change blocks (A and B1) for the same tenure T to each accumulate signer weight independently — since a single signer's local acceptance of A does not, per this code path, block them from later also accepting/signing B1 — potentially producing two non-canonical, conflicting globally-accepted blocks for the same tenure. That would break the uniqueness/canonicity safety property (Critical), matching the category "a signer signing an invalid, non-canonical, or conflicting block."

This requires: (1) v1 protocol active, (2) block A already `LocallyAccepted` (not yet `GloballyAccepted`) in tenure T by the signer under evaluation, and (3) no independent guard elsewhere in the signing pipeline (e.g., in `check_block_against_signer_db_state` or the BlockResponse/state-machine logic) blocking a second signature within the same tenure.
