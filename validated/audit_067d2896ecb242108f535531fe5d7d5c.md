### Title
Stale per-epoch instant-withdraw basis is never cleared on funded claims, inflating default recovery basis and permanently stranding recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug class — edge-case input skipping a setup/cleanup path so a downstream consumer reads uninitialized or stale state — maps directly onto `IdleCreditVault`'s instant-withdraw ledger. `requestInstantWithdraw` records receipts in three places (`instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`), but the normal funded claim path `claimInstantWithdrawRequest` only clears the aggregate `instantWithdrawsRequests`. The per-epoch entries `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` are never decremented on a successful funded claim — the cleanup is "skipped" exactly like `af_alg_get_rsgl()` skipping `first_rsgl` initialization on empty input. That stale basis is later consumed by `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` if the same epoch ends in a borrower default.

### Finding Description
In `requestInstantWithdraw` (lines 356-375) the strategy records `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`. In `claimInstantWithdrawRequest` (lines 380-393), when the claim is funded (pre-default or fully-funded path), only `instantWithdrawsRequests[_user]` is zeroed; the per-epoch bookkeeping is left intact. `collectInstantWithdrawFunds` (lines 398-403) decrements `pendingInstantWithdraws` only by the amount the CDO collected.

If the borrower repays only part of the instant queue, or funds a subset of instant withdrawals, `pendingInstantWithdraws` remains non-zero while `instantWithdrawClaimsByEpoch[epochNumber]` still includes basis belonging to users who already claimed and were paid. If that epoch then defaults and `finalizeDefaultRecovery` runs, `defaultPendingClaimBasis()` (lines 644-649) adds the full stale `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis:

- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is diluted by claim basis that no longer corresponds to any outstanding obligation (line 688).
- Every legitimate claimant (active AA/BB holders and pending withdraw requesters) receives less than their fair recovery share.
- The over-reserved amount computed against the inflated basis can never be claimed — the already-paid users cannot re-claim because `_claimDefaultedInstantWithdrawRequest` tries to `_burn(_user, claimBasis)` receipt tokens they no longer hold (burned in the original funded claim), so the excess reserve is stranded in the strategy forever.

The broken invariant is solvency/fair distribution of the recovery waterfall: basis counted in `totalBasis` does not correspond to outstanding claims, and the resulting `defaultRecoveryReserve` excess is unrecoverable by any user path (recovery tokens can only leave via `_transferDefaultRecovery` which requires a matching claim).

Existing guards do not stop it: `defaultInstantWithdrawsFinalized` is set whenever `pendingInstantWithdraws != 0` (line 696), which is precisely the partially-funded case where stale basis exists; `_defaultPrefundedInstantReserve` (lines 716-723) only corrects the reserve side, not the basis side.

### Impact Explanation
Direct economic harm without privileged misbehavior: after a partial instant-withdraw funding followed by a borrower default in the same epoch, the recovery price paid to all defaulted-epoch claimants and active tranche holders is lower than it should be, and a portion of the recovery reserve equal to the stale (already-paid) instant basis is permanently locked in `IdleCreditVault`. Loss is quantified as `alreadyClaimedInstantBasis * reserveAmount / (realBasis + staleBasis)` diverted from legitimate claimants, plus permanent freezing of the corresponding reserve.

### Likelihood Explanation
Requires a specific but plausible sequence: an epoch with instant withdrawals enabled where the CDO collects only part of `pendingInstantWithdraws` (borrower shortfall or partial funding at `getInstantWithdrawFunds`), some users claim their funded instant withdrawals during the running epoch, and the borrower then defaults at `stopEpoch`/`stopEpochWithDuration`. No privileged role needs to misbehave; the sequence is driven by ordinary user claims and an honest default.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledger alongside the aggregate: delete `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` (and `pendingInstantWithdraws` consistently) by the claimed amount whenever a funded claim is paid, mirroring the cleanup done in `_claimDefaultedInstantWithdrawRequest`. Alternatively, base `defaultPendingClaimBasis` on `pendingInstantWithdraws`-consistent data rather than the cumulative per-epoch ledger.

// 6. B and active tranche holders each receive claim * recoveryPrice < fair share.
//    Reserve equal to A * recoveryPrice remains locked: A's defaulted-claim path reverts
//    on _burn(A) since A's receipt tokens were already burned in step 3.
