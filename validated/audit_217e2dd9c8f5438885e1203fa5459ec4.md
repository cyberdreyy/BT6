### Title
Unclaimed APR0 withdraw principal permanently blocks `stopEpoch` at any nonzero APR, freezing the epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged KYC-passed lender can create APR0 principal by calling `requestWithdraw` during a zero-APR epoch and then simply never claim. Once the manager raises the APR, every subsequent `stopEpoch` call reverts, so the epoch can never be closed and borrower funds plus all pending withdrawals stay locked.

### Finding Description
- In `requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0`, which records per-user principal in `apr0Users[_user].principal` and increments the global `apr0TotalPrincipal` (IdleCreditVault.sol:285-294).
- In `prepareStopEpochWithApr0` (called from `IdleCDOEpochVariant._stopEpoch` at IdleCDOEpochVariant.sol:362), the fast path is skipped when `_principal = apr0TotalPrincipal` is nonzero, and the function then reverts if `unscaledApr != 0` (IdleCreditVault.sol:499-508).
- `apr0TotalPrincipal` is only reduced when the user claims (`_settleApr0` inside `_claimFundedWithdrawRequest`, IdleCreditVault.sol:330-347) or when an APR0 settlement runs inside `prepareStopEpochWithApr0` — which is exactly the path that now reverts. There is no privileged path to force-settle or delete another user's `apr0Users` entry; `claimWithdrawRequest` is `_onlyIdleCDO` and is driven by the user's own claim.
- So the attacker sequence is: deposit during a buffer period while `unscaledApr == 0`, call `requestWithdraw` (receipt minted to the attacker at line 275), then never claim. After the manager sets a nonzero `unscaledApr` via `setAprs`/`setAprsWithBuffer`, every `stopEpoch`/`_stopEpoch` reverts `NotAllowed` at line 506-508.

### Impact Explanation
Broken invariant: epoch state machine liveness — the running epoch cannot be stopped. All funds currently lent to the borrower remain locked in the borrower contract, no new epoch can start, normal withdraw requests cannot be funded, and no interest accrues. This is temporary-to-permanent freezing of the entire vault TVL. The only escape is for the honest manager to keep `unscaledApr == 0` and run a full extra zero-interest epoch so `prepareStopEpochWithApr0` settles the attacker's principal, or for the attacker to voluntarily claim — i.e., the protocol is held hostage to either a forfeited interest epoch or attacker cooperation.

### Likelihood Explanation
Requires only a KYC-passing lender (an explicitly allowed unprivileged actor) and one `requestWithdraw` transaction while APR is zero. Cost is the opportunity cost of parked principal; no privileged cooperation needed. The honest manager's mitigation (one forced zero-APR epoch) bounds the freeze but concretely quantifies the loss as one epoch of interest on the full TVL plus delayed withdrawals for all users.

### Recommendation
Do not gate `prepareStopEpochWithApr0` on `unscaledApr == 0` for already-recorded APR0 principal. Either (a) settle outstanding `apr0Users` principal at the moment APR is raised (in `setAprs`/`setAprsWithBuffer`), or (b) treat leftover `apr0TotalPrincipal` as normal pending principal when the epoch is stopped at nonzero APR, so a single unclaimed receipt cannot wedge the state machine.
