### Title
Stale confirmations from removed multisig members still count toward `num_confirmations`, allowing execution below the required live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Deleting a multisig member/key only purges requests *created* by that member, not that member's confirmations left on requests created by *other* members. A subsequent `confirm()` call then counts the removed member's stale confirmation toward the threshold, letting a request execute with fewer genuinely-authorized live confirmations than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides to execute a request purely by counting entries in the `confirmations` `HashSet<String>` for that request: `if confirmations.len() as u32 + 1 >= self.num_confirmations { ... execute ... }` [1](#0-0) . Nothing in this path checks whether the accounts/keys already present in that set are still members of `self.members`.

`delete_member()` only cleans up requests whose *creator* (`r.member`) equals the removed member, and removes that member's `num_requests_pk` entry; it does **not** scan `self.confirmations` for entries where the removed member had merely confirmed (not created) a still-pending request created by someone else: [2](#0-1) . The check performed at removal time (`self.members.len() - 1 >= self.num_confirmations`) only guards against the *total* member count dropping below the threshold, not against ghost confirmations remaining in unrelated pending requests: [3](#0-2) .

The same pattern exists in the original `multisig/src/lib.rs`: `DeleteKey` only removes requests signed by that key (`r.signer_pk == pk`) and `num_requests_pk`, leaving that key's confirmations on other pending requests untouched, while `confirm()` there likewise just counts `confirmations.len()`: [4](#0-3) .

The invariant that should hold is: `confirmations_counted_toward_threshold == confirmations_from_currently_live_members`. This is violated because the confirmation record is never invalidated when its author's membership is revoked, so `confirmations_counted > confirmations_from_live_members` is possible.

### Impact Explanation
This lets a request (including a `Transfer`, `DeployContract`, `AddKey`/`AddMember`, or `FunctionCall`) execute while the number of *currently authorized* signers who actually approved that specific request is below `num_confirmations`. Concretely, with `num_confirmations = K` and members `{A, B, C, ...}`:
1. Member `A` creates request `R` (e.g., a `Transfer`).
2. Member `B` confirms `R` (not enough yet, so it stays pending): confirmations = `{B}`.
3. Members remove `B` from the multisig via a separate, properly-confirmed `DeleteMember` request. `R`'s confirmation set still contains `B`, because `delete_member` only removes requests *created by* `B`, not confirmations `B` left on `R`.
4. Any remaining member (e.g., `A`, confirming its own request) calls `confirm(R)`. The check `confirmations.len() + 1 >= num_confirmations` counts `B`'s stale confirmation plus `A`'s live one, reaching the threshold and executing `R` — even though `B` is no longer a member and no second *live* member ever approved `R`.

This directly matches the Critical impact category "a multisig request executed below threshold," since funds can be transferred, keys/members added, or arbitrary `FunctionCall`s executed with fewer genuine live approvals than the contract's own `K`-of-`N` policy requires.

### Likelihood Explanation
No privileged role, victim key, or external actor is needed beyond the normal ability of any current multisig member to call `confirm`/`add_request`/`delete_member` through the contract's own public methods — actions every member is already entitled to perform. The scenario only requires ordinary contract usage: a request left partially confirmed while membership changes, which is a realistic operational pattern (pending requests plus member rotation/offboarding are expected multisig activities, not attacker-crafted edge cases).

### Recommendation
When removing a member/key in `delete_member` (`multisig2/src/lib.rs`) and the `DeleteKey` action (`multisig/src/lib.rs`), iterate over all entries in `self.confirmations` and strip the removed member's/key's entry from every pending request's confirmation set, not just requests it created. Alternatively, `confirm()` should validate, at counting time, that every entry in `confirmations` still corresponds to a current member (filtering `self.members`) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request({Transfer amount to X})` → `request_id = R` (confirmations = `{}`).
3. `B` calls `confirm(R)` → confirmations = `{B}` (1 < 2, stays pending) per `confirm` logic [1](#0-0) .
4. `A` and `C` create/confirm a `DeleteMember{member: B}` request; it executes and removes `B` from `self.members` via `delete_member`, which does not touch `R`'s confirmation set since `R.member == A`, not `B` [2](#0-1) .
5. `A` calls `confirm(R)`. `confirmations` still equals `{B}`; `confirmations.len() + 1 == 2 >= num_confirmations (2)`, so `execute_request` fires the `Transfer` — despite only one currently-live member (`A`) ever approving `R`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
