### Title
Loss-adjusted (stopEpochWithDuration) haircut only applied to the last request epoch — earlier unclaimed withdraw receipts escape the loss and drain funded pool — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` distributes the haircut pro-rata over **all** `pendingWithdraws` (the aggregate basis of every unclaimed receipt), but stores the recovery price under only the current `epochNumber` in `lossRecoveryPriceByEpoch`. At claim time, `_claimLossAdjustedWithdrawRequest` looks up the haircut solely via `lastWithdrawRequest[_user]` — a single-epoch marker. Receipts recorded in `withdrawsRequestsByEpoch[user][olderEpoch]` are never matched to the loss epoch: they "fall through" exactly like h3's mixed-case `ChuNkEd` header — present in the aggregate basis, but invisible to the check — and are later paid **at par** through `_claimFundedWithdrawRequest`. The funded pool was sized for all receipts at the haircut price, so par-paying stale receipts makes the strategy insolvent for the remaining loss-epoch claimants, whose claims then revert in `_transferFundedClaim`'s reserve/balance guard.

### Finding Description
The flow:

1. `requestWithdraw` accumulates receipts in `withdrawsRequests[user]`, `withdrawsRequestsByEpoch[user][currentEpoch]` and `pendingWithdraws`, and updates `lastWithdrawRequest[user] = currentEpoch` (`IdleCreditVault.sol:273-293`). A user may stack requests across multiple epochs without claiming; the only guard (`:263-271`) checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`, so prior-epoch receipts do not block a new request.
2. On a losing `stopEpochWithDuration`, `previewLossAdjustedWithdrawFunds` computes `pendingLoss = _lossAmount * pendingBasis / totalBasis` over the **aggregate** basis and the borrower funds only `pendingToFund = pendingBasis - pendingLoss` (`:457-459`). The docstring states "all pending receipts share their aggregate portion of the loss pro rata."
3. `collectWithdrawFunds` then records `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` — one price keyed to one epoch, applied to money owed for receipts spanning many epochs (`:417-421`).
4. In `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest`, only `lossEpoch = lastWithdrawRequest[user]` is checked (`:790`). `_clearWithdrawClaimForEpoch` clears **only** `withdrawsRequestsByEpoch[user][lossEpoch]` (`:815-820`), leaving `withdrawsRequestsByEpoch[user][olderEpoch]` and its share of `withdrawsRequests[user]` intact.
5. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[user]` (the leftover older-epoch amounts) at par via `_transferFundedClaim` (`:338-349`).

The invariant break: loss socialization is computed on the aggregate pending basis but enforced only on the last-requested-epoch subset — a lookup keyed on one epoch that silently misses matching receipts in other epochs, the same "case-sensitive match skips a real value" pattern as the h3 TE bug.

### Impact Explanation
Quantified example: user A requests 100 in epoch 1 (never claims), then 100 in epoch 2; user B requests 100 in epoch 2. `pendingWithdraws = 300`. Borrower repays with a loss such that `lossRecoveryPriceByEpoch[2] = 0.5e18` and only `pendingToFund = 150` underlyings are funded (`collectWithdrawFunds`). Claims: A gets `100*0.5 + 100*1.0 = 150`, then B's `100*0.5 = 50` claim reverts in `_transferFundedClaim` (balance 0 < amount) — B's funded payout is permanently frozen/stolen by A's earlier claim. Direct theft of up to the full haircut-skipping portion and insolvency for remaining loss-epoch claimants.

### Likelihood Explanation
Requires: a `stopEpochWithDuration` loss (attacker cannot force it — manager/borrower driven, but losses are a designed mode), and a user holding unclaimed receipts across ≥2 epochs including the loss epoch. Any ordinary lender who simply doesn't claim between epochs qualifies; no privileged action needed by the victim. An attacker can also deliberately stack requests across epochs to maximize the par-paid share. The path is reachable in normal (non-default) operation and no existing guard stops it: the `requestWithdraw` loss-receipt guard only inspects `lastWithdrawRequest`, which by construction points at the newest epoch, not the older unclaimed one.

### Recommendation
Either apply the loss price to **all** outstanding receipt epochs (e.g., store a global "funded price" or clear every non-zero `withdrawsRequestsByEpoch[user][*]` under the same `lossRecoveryPrice`), or forbid stacking: revert in `requestWithdraw` whenever `withdrawsRequests[user] != 0` / any prior receipt is unclaimed, not only when `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0`. A cheap variant: iterate/mark — set a flag `hasPendingReceipt[user]` and revert until claimed.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_requestWithdrawWithUser`, `_stopCurrentEpochWithApr`, and the loss path in `IdleCDOEpochQueue.t.sol:811-858`):

```solidity
function testLossHaircutEscapesEarlierEpochReceipt() external {
    address A = makeAddr("A");
    address B = makeAddr("B");
    _depositWithUser(A, 100 * ONE_SCALE, true);
    _depositWithUser(B, 100 * ONE_SCALE, true);

    // epoch N: A requests 100 tranche-equivalent, does NOT claim
    _requestWithdrawWithUser(A, 100e18);
    // stop epoch N normally (full funding, no loss) -> epoch N+1
    _stopCurrentEpochWithApr(10e18);

    // epoch N+1: A requests again (allowed: no loss price on epoch N), B requests
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(A, 100e18);
    _requestWithdrawWithUser(B, 100e18);

    // borrower repays with a loss -> lossRecoveryPriceByEpoch[N+1] = 0.5e18
    uint256 lossAmount = /* per previewLossAdjustedWithdrawFunds */;
    deal(address(underlying), strategy.borrower(), fundsToRepay, true);
    vm.prank(strategy.borrower()); underlying.approve(address(cdoEpoch), fundsToRepay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), lossAmount);

    // A claims: gets epochN+1 share at 0.5 AND epochN share at PAR -> 150
    vm.prank(A); cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(A), 150 * ONE_SCALE);

    // B is owed 100*0.5 = 50, but pool is drained -> revert / unpaid
    vm.prank(B);
    vm.expectRevert(NotAllowed.selector); // _transferFundedClaim guard
    cdoEpoch.claimWithdrawRequest();
}
```

Expected: A receives 150 though the strategy only funded 150 total for a 300 aggregate basis; B's legitimate 50 payout is unpayable — theft of B's haircut-adjusted claim plus permanent freezing of the remaining receipt.
