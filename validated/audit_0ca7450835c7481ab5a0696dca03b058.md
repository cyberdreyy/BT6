### Title
Off-by-one freshness check in `get_tenure_last_block_info` lets a signer sign a conflicting sibling block at the same height in the same tenure exactly at the timeout boundary - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::get_tenure_last_block_info` decides whether a previously signed block in a tenure is still "fresh" (and therefore must veto a competing proposal at the same height) using a strict `>` comparison against `get_epoch_time_secs()`. At the exact instant `now == signed_over_time + tenure_last_block_proposal_timeout`, the function already treats the earlier signed block as *timed out* and returns `None`, even though it was signed only moments ago. This is the same class of boundary bug as the AirdropBroker report: an equality point where a guard that is supposed to still be "active" is treated as already having transitioned to the next state, letting an action that should be blocked by the old state go through instead.

### Finding Description
`get_tenure_last_block_info` (`stacks-signer/src/chainstate/mod.rs`) is the single source of truth used by `check_latest_block_in_tenure` to decide whether a fresh signed tip exists in a tenure that must veto a same/lower-height competing proposal:

```rust
if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
    > get_epoch_time_secs()
{
    // The last accepted block is not timed out, return it
    Ok(Some(block_info))
} else {
    // The last accepted block is timed out
    ...
    Ok(None)
}
```

The comparison is strict `>`. When `get_epoch_time_secs() == signed_over_time + tenure_last_block_proposal_timeout.as_secs()` exactly, the branch evaluates to `false`, and the function returns `Ok(None)` — i.e. "there is no fresh signed tip in this tenure" — even though the block was signed precisely `tenure_last_block_proposal_timeout` seconds ago, not longer. That single second boundary is the exact analog of the AirdropBroker `<` vs `<=` bug: at the instant the timeout "just" elapses, the code silently treats the old guarantee as void.

`check_latest_block_in_tenure` (same file, lines ~376-478) relies on this `None` result to skip the veto:

```rust
if let Some(info) = last_block_info {
    if block.header.chain_length <= info.block.header.chain_length {
        ... return Ok(false);   // veto: reject the competing proposal
    }
}
...
let tip = match client.get_tenure_tip(tenure_id) { ... };
...
Ok(tip.height() < block.header.chain_length)
```

If `last_block_info` is `None` at that boundary second, the height-based veto is skipped, and the decision falls through to asking the stacks-node for its own view of the tenure tip via `client.get_tenure_tip`. As `docs/signer-flows.md` states, this call is a *fallback*, not a guaranteed-consistent recheck: the node only knows about a block once it has been globally accepted/pushed; a block this signer just signed (`signed_self`) but which has not yet crossed the network's 70% threshold or been pushed to the node is invisible to `get_tenure_tip`. In that gap, `tip.height() < block.header.chain_length` for a new competing sibling proposal at the same height can trivially be true (the node's tenure tip is still lower), so the check passes and the competing block moves on to pre-commit and, eventually, signature.

This directly breaks the "one signed block per height per tenure" equality invariant that `check_latest_block_in_tenure`/`get_tenure_last_block_info` exists to enforce, exactly at the second the freshness window elapses — a miner (or colluding pair of proposals) only needs to time a second, conflicting block proposal to land in that single-second window to get a signer to sign two different blocks at the same chain height in the same tenure.

Note: `handle_block_pre_commit`'s later `get_signed_conflicts`/`conflict_still_blocks` path (section 5 of `docs/signer-flows.md`) is a secondary backstop, but per the docs it is explicitly scoped to catch what the tenure-based recheck in `check_latest_block_in_tenure` cannot see (siblings in other tenures); it does not change the boundary semantics of `get_tenure_last_block_info` itself, and its own freshness cutoff (`last_endorsed > cutoff` in `signerdb.rs`) is a separately-computed comparison that is not verified here to close this exact one-second gap.

### Impact Explanation
This falls under "a signer signing an invalid/non-canonical/conflicting block" — a signer produces a valid signature over two different blocks at the same height within the same tenure, which is exactly the invariant `check_latest_block_in_tenure` is designed to prevent. If enough signers hit this same one-second race independently (which is plausible since all of them measure wall-clock freshness against the same `signed_over_time` recorded when the original block was signed), a competing/conflicting block could accumulate enough weight to also be signed, producing two Nakamoto blocks at the same height with valid signer-set signatures — a consensus-visible equivocation. This is a Critical-class outcome per the stated impact categories.

### Likelihood Explanation
The trigger requires only a single miner (no majority of signers, no other signer's key, no auth token) that:
1. Gets an original block signed in its tenure (normal operation).
2. Proposes a second, conflicting block at the same height, timed to arrive/complete validation exactly `tenure_last_block_proposal_timeout` seconds after the first block's `signed_self`/`signed_group` timestamp, before the node has processed/pushed the first block.

Hitting an exact one-second window is a narrow timing target, and default `tenure_last_block_proposal_timeout_secs` is 30s, so the race is tight but not implausible over repeated attempts, especially if a miner deliberately delays broadcasting the winning block to keep the node's view of the tenure tip stale while proposing the sibling. This is comparable in spirit to the original finding, which the project itself later judged Medium severity because it required no privileged access, only careful timing.

### Recommendation
Change the freshness comparison in `get_tenure_last_block_info` from strict `>` to `>=` (or equivalently treat exact equality as "still fresh"):

```rust
if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
    >= get_epoch_time_secs()
{
    Ok(Some(block_info))
} else {
    Ok(None)
}
```

This removes the one-second gap in which a previously-signed block stops vetoing a same-height competitor before its timeout window has actually fully elapsed, aligning the boundary semantics with the intended guarantee.

### Proof of Concept
Exact reproduction requires timing control over wall-clock seconds and is best driven by a background agent with terminal/test access (not available in this ask-only session):
1. Configure a signer with a short `tenure_last_block_proposal_timeout_secs` (e.g. 3s, as used in existing tests such as `stacks-signer/src/chainstate/tests/v2.rs::pre_committed_block_does_not_veto_replacement`).
2. Have a miner get block A signed in tenure T at height h, recording `signed_self`/`signed_group = t0`.
3. Delay handing block A to the node (so `client.get_tenure_tip(T)` still reports a tip below h) while proposing a sibling block B at the same height h in the same tenure, timed so that block B's `check_latest_block_in_tenure` evaluation lands at `now == t0 + tenure_last_block_proposal_timeout` exactly.
4. Observe that `get_tenure_last_block_info` returns `None` for tenure T at this instant, `check_latest_block_in_tenure` returns `true` for B, and B proceeds toward being signed — producing two independently signed blocks at height h in tenure T.
