### Title
Instant withdrawal claims pay out before the instant bucket is funded, draining other users' reserved claim funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays a user's full `instantWithdrawsRequests` balance directly from the vault's underlying-token reserve without verifying that the borrower funds for that instant epoch were actually collected via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`. Like CVE-2017-12154 — where a code path omitted enforcing that required controls existed when a flag was unset — the claim path assumes (but never ensures) that the instant-withdraw funding control ran. An unprivileged KYC-passing lender can request an instant withdrawal during an APR drop and claim immediately, paid out of the reserve that was collected to back *other* users' matured normal withdraw receipts.

### Finding Description
When a withdraw request is made while `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, `IdleCDOEpochVariant.requestWithdraw` routes to `IdleCreditVault.requestInstantWithdraw` (contracts/IdleCDOEpochVariant.sol:761-770). That mints a strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:356-375). The borrower funds are only pulled later when the manager calls `getInstantWithdrawFunds` → `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and transfers underlying into the vault (lines 398-403).

However `claimInstantWithdrawRequest` (lines 380-393) burns the user's receipt and calls `_transferFundedClaim(_user, amount)` unconditionally — there is no check that `pendingInstantWithdraws` was reduced to cover this epoch's instant claims, no per-epoch funding flag, and no `instantWithdrawDelay`/epoch-maturity gate (unlike normal claims which enforce `epochNumber <= lastWithdrawRequest[_user]` at line 326). The CDO-side wrapper only checks `allowInstantWithdraw` (contracts/IdleCDOEpochVariant.sol:975-979). The vault's underlying balance is the shared reserve for *funded* normal claims collected via `collectWithdrawFunds` (lines 411-430), so an unfunded instant claim is paid out of money earmarked for other users.

### Impact Explanation
Direct theft: whenever the vault holds a non-zero funded-claim reserve (the steady state, since matured normal receipts can be claimed at any time), an attacker who deposits, then requests a withdrawal during an epoch where APR dropped by more than `instantWithdrawAprDelta`, receives an instant receipt and can claim it in the same transaction — before the borrower has repaid anything. The payout comes entirely from the reserve backing other users' pending claims, leaving them undercollateralized and their later claims failing on insufficient balance. Loss equals the attacker's claimed amount, up to the full reserve balance.

### Likelihood Explanation
Requires a KYC-passing lender (in-scope attacker), `allowInstantWithdraw` enabled, and an APR decrease between epochs exceeding `instantWithdrawAprDelta` — a configuration the codebase explicitly supports (`setInstantWithdrawParams`). The reserve must be non-zero, which is common because funded claims remain in the vault until each user claims. No privileged collusion is needed; the manager's honest `getInstantWithdrawFunds` call happens strictly after the window the attacker exploits.

### Recommendation
Track instant-claim funding per epoch: only allow `claimInstantWithdrawRequest` to pay amounts that were actually collected (e.g., record `instantWithdrawsRequestsByEpoch` settlement and require the epoch's `instantWithdrawClaimsByEpoch` to be funded via `collectInstantWithdrawFunds` before claims, or maintain a separate funded-instant balance checked at claim time). Alternatively, gate claims until `pendingInstantWithdraws` coverage for the user's epoch exists, mirroring the `epochNumber <= lastWithdrawRequest` maturity check used for normal claims.

### Proof of Concept
Foundry fork sketch (adapting the harness in test/foundry/IdleCreditVault.t.sol):

```solidity
function testInstantClaimDrainsFundedReserve() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    uint256 amountWei = 10_000 * ONE_SCALE;

    // victim deposits and requests a normal withdraw
    address victim = makeAddr('victim');
    _depositWithUser(victim, amountWei, true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // next epoch: borrower repays at stopEpoch, funding victim's receipt
    // into the vault reserve via collectWithdrawFunds
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr / 2, _expectedFundsEndEpoch());
    uint256 reserve = underlying.balanceOf(address(strategy));
    assertGt(reserve, 0);

    // attacker (KYC'd) deposits in buffer, then requests withdraw:
    // APR dropped > instantWithdrawAprDelta => instant receipt minted
    address attacker = makeAddr('attacker');
    uint256 attackerTranches = _depositWithUser(attacker, amountWei, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerTranches, address(AAtranche));

    // BUG: claim succeeds before getInstantWithdrawFunds is ever called;
    // payout comes from victim's funded reserve
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balPre, 0);

    // victim's funded claim now undercollateralized
    vm.prank(victim);
    vm.expectRevert(); // insufficient vault balance
    cdoEpoch.claimWithdrawRequest();
}
```

Note: I could not fully inspect `_transferFundedClaim` and `getInstantWithdrawFunds` internals within this session; if `_transferFundedClaim` enforces a per-bucket funded-balance invariant I did not observe, this finding would be invalid and should be re-verified against that function before reporting.
