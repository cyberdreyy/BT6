### Title
Loss-adjusted withdraw receipts from earlier epochs are later paid at par via `_claimFundedWithdrawRequest`, letting an attacker withdraw more than the strategy collected - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When the borrower partially repays a stop, `collectWithdrawFunds` records a `lossRecoveryPrice` for that epoch and zeroes `pendingWithdraws`, but it does not clear the per-user receipt basis (`withdrawsRequestsByEpoch[user][epoch]` / `withdrawsRequests[user]`). At claim time `_claimLossAdjustedWithdrawRequest` only looks up the loss price for `lastWithdrawRequest[_user]` — a single epoch. If a user has receipts in two different loss-adjusted epochs, only the newest one is haircut; the older epoch's basis falls through to `_claimFundedWithdrawRequest`, which pays it at par from strategy underlyings. The strategy only ever collected the loss-adjusted amount for that old epoch, so the par payout is directly underfunded.

### Finding Description
The flow (attacker = ordinary KYC'd lender):

1. Epoch N running. Attacker calls `requestWithdraw` → `withdrawsRequestsByEpoch[attacker][N] = A`, `pendingWithdraws += A`.
2. Owner calls `stopEpochWithDuration`/`stopEpoch` such that the borrower repays less than `pendingWithdraws`; `collectWithdrawFunds(_amount < pendingBasis)` stores `lossRecoveryPriceByEpoch[N] = _amount * RECOVERY_FULL / pendingBasis` and sets `pendingWithdraws = 0`. Only `lossRecoveryPrice * basis` worth of underlyings reaches the strategy — the shortfall is the socialized loss.
3. Epoch N+1 running. Attacker requests again → basis `B` recorded under `withdrawsRequestsByEpoch[attacker][N+1]`, `lastWithdrawRequest[attacker] = N+1`.
4. Epoch N+1 also ends loss-adjusted (honest borrower repays partially again): `lossRecoveryPriceByEpoch[N+1]` set, `pendingWithdraws = 0` again.
5. Attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest[attacker] = N+1`, clears only `withdrawsRequestsByEpoch[attacker][N+1]` and pays `B * lossRecoveryPriceByEpoch[N+1]` — correct.
   - `_clearWithdrawClaimForEpoch` then resets `lastWithdrawRequest[attacker] = 0`, so the `epochNumber <= lastWithdrawRequest` guard in `_claimFundedWithdrawRequest` passes.
   - `_claimFundedWithdrawRequest` computes `normalAmount = withdrawsRequests[attacker]`, which still includes the epoch-N basis `A` (only the N+1 piece was subtracted), and calls `_transferFundedClaim(attacker, A + ...)` at par.

Result: the epoch-N receipt is paid 100% even though the strategy received only `A * lossRecoveryPriceByEpoch[N]` for it. The excess is paid from underlyings that belong to other claimants or the recovery reserve boundary in `_transferFundedClaim` does not cover this case (the reserve check only protects `defaultRecoveryReserve`, not other users' funded claims).

### Impact Explanation
Direct theft / insolvency: the attacker redeems a haircut receipt at full price, extracting the difference `A * (1 - lossRecoveryPriceByEpoch[N])` from other lenders' funded claims. If the strategy doesn't hold enough, later claimants' transactions revert — permanent freezing of unclaimed funded withdrawals. Loss magnitude is bounded by the haircut size; with a severe partial repayment (e.g., 50% recovery) the attacker doubles the stolen share of what remains.

### Likelihood Explanation
Requires two loss-adjusted (`stopEpochWithDuration`-style) epochs where the attacker held a pending request in each — plausible whenever the borrower underpays repeatedly, and the attacker controls only their own deposit/request timing (unprivileged). No privileged cooperation needed; manager/owner calls are honest `stopEpoch` variants that legitimately record a loss.

### Recommendation
Track per-user claimable loss-adjusted basis across *all* epochs, not just `lastWithdrawRequest`. Either iterate `lossRecoveryPriceByEpoch` entries for the user, store a per-user list of request epochs, or clear `withdrawsRequests`/`withdrawsRequestsByEpoch` for every epoch that carries a non-zero `lossRecoveryPriceByEpoch` during the claim. Alternatively, store a per-user `lossClaimEpochs` array so `_claimLossAdjustedWithdrawRequest` drains each loss epoch before the funded path runs.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testClaimParForOlderLossEpoch() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(attacker, amount, true);

    // Epoch 0: request, then stop with 50% loss funding
    vm.prank(attacker);
    uint256 reqA = cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(0);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 funded0 = pending / 2; // borrower repays half
    deal(defaultUnderlying, borrower, funded0);
    vm.prank(borrower); underlying.approve(address(cdoEpoch), funded0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(owner); cdoEpoch.stopEpochWithDuration(...); // triggers collectWithdrawFunds(funded0)
    // lossRecoveryPriceByEpoch[0] == 0.5e18

    // Epoch 1: request again, stop loss-adjusted again
    vm.prank(attacker);
    uint256 reqB = cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);
    // ... borrower partially funds again, lossRecoveryPriceByEpoch[1] set

    // Claim: reqB paid at lossRecoveryPrice, reqA paid AT PAR
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;
    // BUG: got == reqA + reqB * price1  (> funded0 + funded1)
    assertGt(got, funded0 + funded1);
}
```

Key assertions: `withdrawsRequestsByEpoch[attacker][0]` remains non-zero after the first underfunded `collectWithdrawFunds`, and `_claimFundedWithdrawRequest` includes it in `normalAmount` paid at par.
