### Title
Unbounded pre-allocation in `parse_address_lookup_table` via `bincode::deserialize` on attacker-controlled `ExtendLookupTable` instruction data - ([File: transaction-status/src/parse_address_lookup_table.rs])

### Summary
`parse_address_lookup_table` calls `bincode::deserialize(&instruction.data)` on raw, attacker-supplied `CompiledInstruction` bytes with no length or size-limit validation before decoding the `ExtendLookupTable { new_addresses: Vec<Pubkey> }` variant. Because bincode's default `Vec<T>` deserialization pre-allocates capacity based on the untrusted length prefix read from the byte stream (via `SeqAccess::size_hint`), a crafted instruction with a small physical payload but an inflated length prefix can trigger an attempted allocation far larger than the input data, before EOF is ever reached.

### Finding Description
`parse_address_lookup_table(instruction, account_keys)` is reached from `transaction-status/src/parse_instruction.rs::parse` [1](#0-0) , which is invoked whenever a client requests `encoding=jsonParsed` for `getTransaction`/`getConfirmedTransaction` (via `rpc/src/rpc.rs::get_transaction`) and the instruction's `program_id` matches the Address Lookup Table program in `PARSABLE_PROGRAM_IDS`.

The vulnerable call is:
```rust
let address_lookup_table_instruction: ProgramInstruction = deserialize(&instruction.data)
    .map_err(|_| ParseInstructionError::InstructionNotParsable(ParsableProgram::AddressLookupTable))?;
``` [2](#0-1) 

`instruction.data` here is the raw, unvalidated bytes taken directly from a `CompiledInstruction` embedded in a transaction that was previously accepted into the ledger/entry data — the attacker fully controls these bytes (the instruction need not execute successfully on-chain; it only needs to be included/observable in transaction-status history, consistent with the stated precondition). `ProgramInstruction::ExtendLookupTable { new_addresses: Vec<Pubkey> }` is a length-prefixed vector. With standard bincode/serde deserialization, `Vec<T>`'s generic `visit_seq` implementation pre-allocates `Vec::with_capacity(size_hint)`, and bincode's `SeqAccess::size_hint()` returns the raw attacker-supplied length value read from the stream without cross-checking it against the number of bytes actually remaining in the buffer. Thus an attacker can encode a `ProgramInstruction` discriminant for `ExtendLookupTable` followed by a length prefix of `u32::MAX` (or larger, since bincode uses a u64 length by default) while supplying far fewer actual `Pubkey` bytes — the whole instruction still fits comfortably within the 1232-byte packet limit. `bincode::deserialize` will attempt to allocate a `Vec<Pubkey>` sized for the claimed length (up to `u64::MAX * 32` bytes) before it ever reads enough bytes to hit EOF and fail.

No existing guard prevents this: `check_num_address_lookup_table_accounts` only validates the number of *account* indices, not the length of `new_addresses` [3](#0-2) , and `parse_address_lookup_table` performs no cap on `instruction.data` size or on the deserialized vector length before allocation occurs.

### Impact Explanation
Every RPC client that calls `getTransaction`/`getConfirmedTransaction` with `encoding=jsonParsed` on the slot containing the crafted transaction will trigger the oversized allocation attempt in the validator's JSON-RPC serving thread, causing an allocation failure/abort or severe memory pressure on the validator process from a single, cheap RPC call. This matches the "unbounded cost for a single low-rate call" / decoder-triggered crash category, and is persistent (every future read of that transaction re-triggers it) rather than a one-off spike.

### Likelihood Explanation
Feasible and repeatable with a single unprivileged transaction: an attacker only needs the transaction to be included in a slot (or even fail on-chain, since transaction-status is recorded regardless per precondition), and then any single `getTransaction(..., encoding: jsonParsed)` call from a client (attacker or otherwise) reaches the vulnerable decode path. No special validator/leader access or elevated privileges are needed; only bincode's default (unbounded) deserialization behavior needs to hold, which is exercised identically on every read.

### Recommendation
Bound the size of vectors decoded from attacker-controlled instruction data before or during deserialization: use `bincode::config().with_limit(instruction.data.len() as u64)` (or a `bincode::deserialize_with_limit`/`Options::deserialize` with a limit set to the actual buffer length) instead of the unbounded top-level `bincode::deserialize`, so the length-prefix cannot request an allocation larger than the bytes actually available. Alternatively, validate `new_addresses` length against `instruction.data.len() / size_of::<Pubkey>()` before allocating, or switch to a manual/streaming decode that reads pubkeys incrementally without a bulk pre-allocation.

### Proof of Concept
```rust
// transaction-status/src/parse_address_lookup_table.rs (test module)
#[test]
fn test_extend_lookup_table_oversized_length_prefix_does_not_over_allocate() {
    use solana_message::{AccountKeys, compiled_instruction::CompiledInstruction};

    // ProgramInstruction discriminant for ExtendLookupTable (index 2, per
    // solana_address_lookup_table_interface::instruction::ProgramInstruction enum order).
    let mut data = vec![2u8, 0, 0, 0]; // u32 enum discriminant for ExtendLookupTable
    // bincode-encoded Vec length prefix (u64, little-endian) inflated to a huge value,
    // while supplying essentially no actual Pubkey bytes afterward.
    data.extend_from_slice(&u64::MAX.to_le_bytes());
    // (no trailing pubkey bytes -- total data stays well under 1232 bytes)

    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![0, 1],
        data,
    };
    let account_keys = AccountKeys::new(
        &[solana_pubkey::Pubkey::new_unique(), solana_pubkey::Pubkey::new_unique()],
        None,
    );

    // Expected (fixed) behavior: parse fails quickly with an error, without attempting
    // to allocate memory proportional to u64::MAX * 32 bytes.
    let result = parse_address_lookup_table(&instruction, &account_keys);
    assert!(result.is_err(), "decoder should reject oversized length prefix without huge allocation");
}
```
Running this test against the current implementation is expected to abort the process (allocation failure/OOM) or hang attempting a multi-exabyte allocation, rather than returning a fast `Err`; after applying a size-limited bincode configuration, the test should return an `Err` immediately.
