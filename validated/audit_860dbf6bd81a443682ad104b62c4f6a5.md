### Title
Undefined Behavior from Unvalidated Enum Discriminant via Unsafe Transmute of Attacker-Controlled Account Data - (File: svm/src/program_loader.rs)

### Summary
`svm/src/program_loader.rs`'s `loader_v4_get_state` function reinterprets raw, attacker-controllable account bytes as a `&LoaderV4State` struct via `std::mem::transmute`, without validating that the embedded `status: LoaderV4Status` enum field actually contains one of the declared discriminant values. This mirrors the CVE-2026-21505 bug class (invalid enum value causing undefined behavior) but in a code path reachable from a single submitted Solana transaction.

### Finding Description
`loader_v4_get_state` casts a raw byte slice directly into a `&LoaderV4State` reference: [1](#0-0) 

This function is invoked from `load_program_accounts` whenever an account owned by `loader_v4::id()` is loaded as a program: [2](#0-1) 

and again from `get_program_deployment_slot`: [3](#0-2) 

The resulting `state.status` field (a `LoaderV4Status` enum) is then pattern-matched with `matches!(state.status, LoaderV4Status::Retracted)`, i.e., the compiler is trusted to have a valid, in-range discriminant at that memory location.

Critically, the account bytes being transmuted are **not required to have ever been written by the (now-removed) Loader V4 program**. An account's `owner` field can be set to an arbitrary pubkey — including `loader_v4::id()` — by the `SystemInstruction::CreateAccount` system-program instruction, as long as the transaction supplies the new account's keypair as signer, per `parse_system.rs`'s handling of `CreateAccount { lamports, space, owner }`: [4](#0-3) 

This lets an unprivileged transaction sender: (1) create an account owned by `loader_v4::id()` with data bytes fully under their control (including an arbitrary byte at the `status` field offset that does not correspond to any valid `LoaderV4Status` discriminant), and (2) reference that account as a program-id in a subsequent instruction, forcing `load_program_accounts`/`loader_v4_get_state` to transmute and match against the bogus discriminant.

### Impact Explanation
Reading and pattern-matching an out-of-range enum discriminant is Undefined Behavior in Rust. Compilers may generate jump-table-based matches that assume the discriminant is always one of the declared variants; an invalid discriminant can therefore cause out-of-bounds jump-table reads, panics, or unpredictable control flow. Because this code executes as part of ordinary program/account loading during transaction processing (not sandboxed BPF execution), UB here can manifest as a validator process crash/panic, satisfying the "transaction-triggered cluster halt" impact category. It is a stronger version of the upstream iccDEV finding because agave's version reaches the UB through `unsafe { transmute }` directly against attacker-supplied bytes, whereas properly-designed decoders elsewhere in the codebase (e.g., `ShredVariant::try_from`, `wincode`'s `SchemaRead` for enums) explicitly validate discriminants and return `Err` on unknown values: [5](#0-4) 

### Likelihood Explanation
Reaching this path requires only two ordinary, permissionless instructions: a `SystemInstruction::CreateAccount` setting `owner = loader_v4::id()` with crafted data, followed by any instruction naming that account as the instruction's `program_id`. No privileged accounts, special feature-set gates, or leader cooperation are needed, making this reachable directly from a single unprivileged transaction sender.

### Recommendation
Replace the unsafe `transmute` in `loader_v4_get_state` with a checked decode that validates the `status` field against the known `LoaderV4Status` discriminants (e.g., using `TryFrom`/`num_enum::TryFromPrimitive` as is already done for `ShredVariant`/`ShredType` in `ledger/src/shred.rs`) and returns `InstructionError::InvalidAccountData` on an unrecognized value instead of assuming any 8 bytes at that offset form a valid enum tag.

### Proof of Concept
1. Attacker submits a transaction with `SystemInstruction::CreateAccount { lamports, space: LoaderV4State::program_data_offset(), owner: loader_v4::id() }` for a fresh keypair `P`, then writes arbitrary bytes into `P`'s data at the `status` field offset such that the byte pattern does not equal any of `LoaderV4Status`'s valid discriminants (this can be done in the same transaction if the account can be pre-populated, or via any instruction/account model that allows writing raw bytes to an account it owns — since `loader_v4` program no longer exists, no program guards writes to accounts it "owns").
2. Attacker submits a follow-on transaction that references pubkey `P` as an instruction's `program_id`.
3. Transaction processing calls `load_program_accounts` → `loader_v4_get_state(program_account.data())`, which `transmute`s the crafted bytes into `&LoaderV4State` and evaluates `matches!(state.status, LoaderV4Status::Retracted)` against the invalid discriminant, exercising undefined behavior in the validator process.

Note: I could not directly inspect the `solana_loader_v4_interface` crate (external dependency, not in this repo's index) to confirm the exact byte layout/offset of the `status` field within `LoaderV4State`; the index size limits may exclude that dependency's source. Confirming the precise discriminant encoding and byte-for-byte PoC bytes would require a Devin session with access to that crate's full source and the ability to compile/run a local validator to demonstrate the crash.

// Plucked from the now-removed Loader V4 program library.
fn loader_v4_get_state(data: &[u8]) -> Result<&LoaderV4State, InstructionError> {
    unsafe {
        let data = data
            .get(0..LoaderV4State::program_data_offset())
            .ok_or(InstructionError::AccountDataTooSmall)?
            .try_into()
            .unwrap();
        Ok(std::mem::transmute::<
            &[u8; LoaderV4State::program_data_offset()],
            &LoaderV4State,
        >(data))
    }
}
