### Title
Cross-user response hijacking via attacker-controlled `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`HandleLegacyUserMessage` stores the per-request `Callback` in a shared map keyed solely by the attacker/client-supplied `msg.Body.MessageId`, with an unconditional overwrite and no check for an existing entry or sender/ownership binding: [1](#0-0) 

The `MessageId` is never server-generated — it originates entirely from the client-supplied `api.Message.Body.MessageId` field, whose only validation is a length/null-suffix check, not uniqueness or binding to the signer: [2](#0-1) 

Any unprivileged client can sign their own message (their own valid ECDSA signature satisfies `Validate()`) while choosing an arbitrary `MessageId` value, including one that matches a victim's currently in-flight request. `gateway.ProcessRequest` routes each incoming legacy request independently to `HandleLegacyUserMessage`, with no cross-request coordination or ID reservation: [3](#0-2) 

When the DON eventually replies, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId` and delivers the response to whichever `Callback` is currently stored — with no verification that the response corresponds to the original sender: [4](#0-3) 

Exploit flow: victim A submits `HandleLegacyUserMessage` with `MessageId=X`, which stores A's callback at `savedCallbacks[X]` and forwards the request to DON nodes. Before the DON responds, the attacker submits their own signed message using the same `MessageId=X`. This overwrites `savedCallbacks[X]` with the attacker's callback. When the DON returns a response tagged with `MessageId=X` (matching A's original forwarded request), `handleWebAPITriggerMessage` deletes the entry and invokes `SendResponse` on the callback found in the map — the attacker's — while A's HTTP request blocks until `callback.Wait` times out.

### Impact Explanation
This is a cross-user response confusion / hijack: the attacker intercepts a reply intended for another user's in-flight request while the legitimate user's request silently fails (times out with `RequestTimeoutError`). Depending on what the trigger response contains, this could leak data intended for another caller and constitutes a denial of service against the victim's specific request. This maps to Chainlink's "unauthorized access to another user's data/response" and "request impersonation" bounty impact classes.

### Likelihood Explanation
Exploitability requires the attacker to know or guess a currently in-flight legitimate `MessageId` and race their own signed request in before the DON responds. This is fully achievable by any unprivileged, unauthenticated gateway client that can sign requests with its own key — no special privilege or node/DON compromise is needed. The main constraint is the race window (time between initial forward to DON nodes and DON's reply) and knowledge/predictability of the victim's `MessageId`; if IDs are sequential, timestamp-based, or otherwise observable/guessable by the calling application, this is straightforwardly repeatable.

### Recommendation
Bind `savedCallbacks` entries to request ownership, not just the client-chosen `MessageId`. Options:
- Reject the write (return an error) if `h.savedCallbacks[msg.Body.MessageId]` already exists instead of unconditionally overwriting it at line 412.
- Generate the map key server-side (e.g., combine `MessageId` with sender address extracted from `msg.Validate()`, or use a server-generated UUID) so that a different sender cannot collide with another sender's in-flight ID.
- When delivering the DON response in `handleWebAPITriggerMessage`, additionally verify the response's sender/payload correlates to the original requester before invoking `SendResponse`.

### Proof of Concept
Go unit test in `handler_test.go`:
1. Build two valid signed `api.Message`s with two different private keys (`keyA`, `keyAttacker`) but identical `Body.MessageId`.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)`; assert `handler.savedCallbacks[msgA.Body.MessageId]` stores `cbA`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)` with the same `MessageId` before any node response; assert this either (a) returns an error / is rejected (desired fixed behavior), or (b) currently silently overwrites `savedCallbacks[MessageId]` to `cbAttacker` (demonstrating the bug).
4. Simulate a DON response via `handler.HandleNodeMessage` for that `MessageId`; assert `cbAttacker.Wait()` receives the response while `cbA.Wait()` times out — proving cross-user hijack in the current implementation.
