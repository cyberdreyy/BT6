Confirmed: `tracker.actionable` only deduplicates log noise—it never changes control flow to stop extraction.

### Title
`.git` directory-check in zip extraction is warn-only, never blocks writes to disk - ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` calls `errorIfGitDirectory` on each archive entry, but the returned `*os.PathError` is only used to decide whether to print a de-duplicated warning via `printGitArchiveWarning`; the function's return value is discarded entirely and extraction proceeds unconditionally via `extractZipFile`. This means any `.git` entry inside an attacker-supplied artifact/cache zip is written to disk exactly like any other entry, defeating the intended protection completely.

### Finding Description
In `ExtractZipArchive` [1](#0-0) , for every zip entry the loop does:
```
if err := errorIfGitDirectory(file.Name); tracker.actionable(err) {
    printGitArchiveWarning("extract")
}
if err := extractZipFile(file); tracker.actionable(err) {
    logrus.Warningf(...)
}
```
`errorIfGitDirectory` returns a non-nil `*os.PathError` when the entry path begins with `.git` [2](#0-1) , but that error is never propagated, never returned from `ExtractZipArchive`, and never used to `continue`/`break` the loop. `extractZipFile` is invoked unconditionally on the very next line regardless of the outcome of the check, and for a directory-mode entry it calls `extractZipDirectoryEntry`, which performs `os.Mkdir(file.Name, ...)` [3](#0-2) . `ExtractZipArchive` itself unconditionally returns `nil` [4](#0-3) , so callers see success even though a `.git` path was written. `tracker.actionable` only controls log-spam de-duplication by `Op` string and has zero effect on control flow [5](#0-4) . Thus the "check" is purely cosmetic — a warning log line — with no enforcement whatsoever.

### Impact Explanation
An attacker who controls an artifact or cache zip (e.g. crafts one in an earlier job stage, or supplies a malicious cache/artifact that a later job downloads and extracts) can have Runner materialize a `.git` directory/files inside the job's working directory during artifact/cache restore. This can poison the git repository state used by subsequent `git` operations performed by the Runner's own git-based checkout/clean logic (e.g. hooks, config, refs), leading to corrupted checkout state or execution of attacker-controlled git hooks on the next `git` invocation in that workspace.

### Likelihood Explanation
Fully reliable and deterministic: any pipeline author can produce a zip artifact/cache containing a `.git/...` entry, upload it as an artifact, and have a subsequent job (or even the same job's cache/artifact download step) extract it via `ExtractZipArchive`/`ExtractZipFile`. No race condition or timing dependency exists — the warning path and the `Mkdir`/write path are sequential statements in the same loop iteration with no shared control-flow variable connecting them, so `.git` creation happens 100% of the time regardless of the warning's result.

### Recommendation
Make `errorIfGitDirectory`'s result actually gate extraction: if it returns non-nil, `continue` (skip) that entry instead of calling `extractZipFile`, and consider propagating an aggregate error/skip-count from `ExtractZipArchive` so callers can detect that git paths were stripped.

### Proof of Concept
Go unit test in `helpers/archives`:
```go
func TestExtractZipArchive_DoesNotBlockGitDirectory(t *testing.T) {
    dir := t.TempDir()
    zipPath := filepath.Join(dir, "a.zip")
    // build zip with entry ".git/" (directory mode) using archive/zip
    ... write zip with a directory entry named ".git/" ...

    wd, _ := os.Getwd()
    _ = os.Chdir(dir)
    defer os.Chdir(wd)

    r, _ := zip.OpenReader(zipPath)
    defer r.Close()
    err := ExtractZipArchive(&r.Reader)

    assert.NoError(t, err) // ExtractZipArchive reports success
    info, statErr := os.Stat(filepath.Join(dir, ".git"))
    assert.NoError(t, statErr)
    assert.True(t, info.IsDir()) // .git directory was actually created despite the "check"
}
```
Expected result: test passes today, proving `errorIfGitDirectory`'s error has no effect on either the return value of `ExtractZipArchive` or on whether `.git` is created on disk.

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}

func (p *pathErrorTracker) actionable(e error) bool {
	pathErr, isPathErr := e.(*os.PathError)
	if e == nil || isPathErr && pathErr == nil {
		return false
	}

	if !isPathErr {
		return true
	}

	p.lock.Lock()
	defer p.lock.Unlock()

	seen := p.seenOps[pathErr.Op]
	p.seenOps[pathErr.Op] = true

	// actionable if *not* seen before
	return !seen
}
