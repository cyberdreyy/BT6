## Confirmed analog in the txpool `MempoolGuard` payer admission path

### Title
Non-trusted EIP-8130 sponsored-payer admission is count-limited, not balance-reserved, allowing multiple in-flight sponsored transactions to be individually validated against the same stale balance and wasting inclusion/execution effort - (File: `crates/execution/txpool/src/guard.rs`)

### Summary
The reported bug class is: a component computes an operation's resource requirement (swap amount) from a single read of "current balance" without accounting for other in-flight operations that will consume the same balance before this one executes, so multiple operations can be individually valid at admission time but not all executable, wasting fees. `MempoolGuard::try_admit` in `crates/execution/txpool/src/guard.rs` reproduces this exact pattern for EIP-8130 sponsored ("payer") transactions whose payer is not classified as `payer_trusted`.

### Finding Description
`MempoolGuard` implements two different accounting paths for a sponsoring payer's ability to fund sponsored transactions:

- **Trusted (balance-bounded) payers** get an aggregate reservation via `PayerBook::try_reserve`, which deducts `max_cost` from a tracked, shared balance ledger across all of that payer's in-flight transactions [1](#0-0) . This is precisely the "deduct the in-flight amounts from the current balance" mitigation recommended for the original DCA bug.
- **Non-trusted payers** are instead admitted purely by a **count** limit (`payment_counts.try_increment(admission.payer, self.limits.payment_limit)`, default `DEFAULT_PAYMENT_LIMIT = 4`) [2](#0-1) [3](#0-2) .

Each individual EIP-8130 transaction's fee affordability is validated in `FeeCheck::validate_balance` / `FeeCheck::validate_gas_and_tip`, which reads the payer's **live balance at validation time** and checks it against that single transaction's `max_fee_charge` [4](#0-3) [5](#0-4) . This check, and the guard's count-based admission, do not subtract the `max_cost` already committed by other sponsored transactions from the same payer that are simultaneously sitting in the pool. As a result, up to `payment_limit` (4) sponsored transactions from distinct senders naming the same non-trusted payer can each independently pass the "payer can afford this transaction" check against the *same* unconsumed balance snapshot, even though the payer's balance can only cover one (or a few) of them once they are actually included and their combined fees are charged sequentially in `validate_against_state_and_deduct_caller` (`crates/common/evm/src/handler.rs:104-185`, `crates/common/evm2/src/handler.rs:68-92`).

The situation mirrors the reported CoW-DCA case even more directly than a race between two builder-side re-executions: the pool admits several sponsored transactions concurrently, each carrying an individually-valid affordability check, but the aggregate commitment exceeds the payer's real balance. The intended fix pattern (deduct in-flight amounts from the balance, as done for `payer_trusted`) exists in the same file but is deliberately not applied to the count-limited path, based on the classification of "trusted" (locked + trusted bytecode) vs. not.

### Impact Explanation
When several sponsored EIP-8130 transactions from the same under-reserved payer are pooled, the builder/block-assembly step will execute them in some order. The first will succeed and debit the payer's balance in `validate_against_state_and_deduct_caller`; subsequent ones, which were validated against the pre-debit balance, will fail the `LackOfFundForMaxFee`-equivalent check at inclusion time and be dropped from the block (or, if a builder does not re-validate before inclusion, execution work and block space is wasted on transactions that cannot complete). This wastes builder/node resources (CPU for repeated re-validation/eviction, mempool slots) and can be weaponized by an attacker who signs several senders all naming the same lightly-balanced payer to force repeated churn/wasted admission-and-eviction cycles in the pool, though it does not directly cause fund loss or block-halt on its own — it is a resource/availability degradation analog of the original wasted-fee bug, not a theft.

### Likelihood Explanation
Likely to trigger under adversarial conditions: an attacker only needs to submit up to `DEFAULT_PAYMENT_LIMIT` (4) sponsored transactions from distinct senders naming a payer whose classification as `payer_locked`/`payer_trusted` is false (i.e., an EOA payer, or a payer whose bytecode is not on the trusted-proxy allowlist) and whose balance covers roughly one, but not all four, `max_cost` charges. Both `validate_balance` and the guard's admission run independently per transaction with no shared/reserved ledger for this class, so all four can pass admission simultaneously.

### Recommendation
Extend the aggregate-reservation accounting (`PayerBook`) used for `payer_trusted` payers to the non-trusted, count-limited payer path as well, or otherwise deduct in-flight `max_cost` from the payer's balance snapshot before validating/admitting subsequent sponsored transactions from the same payer. At minimum, `on_balance_changed`-style invalidation should also re-check outstanding non-trusted-payer sponsored transactions against the payer's real balance so overcommitted transactions are evicted proactively rather than discovered wasteful only at inclusion.

### Proof of Concept
1. Deploy/select a payer account `P` that is an EOA (or has code not in `trusted_proxy_code_hashes`), so `payer_locked`/`payer_trusted` resolve to `false` in `validate_eip8130_full` (`crates/execution/txpool/src/validator.rs:988-1084`).
2. Fund `P` with balance `B` sufficient for one sponsored transaction's `max_fee_charge` (e.g., `B ≈ max_fee_charge_1`), but not for the sum of several.
3. Submit `DEFAULT_PAYMENT_LIMIT` (4) EIP-8130 sponsored transactions from 4 distinct sender accounts, each naming `P` as payer, each with `max_cost` close to `B`.
4. Each transaction independently passes `FeeCheck::validate_balance(payer_balance=B, ...)` (`crates/execution/eip8130/src/fee.rs:100-111`) because the check re-reads `B` without subtracting the other pooled transactions' committed costs, and each passes `MempoolGuard::try_admit`'s count-based `payment_counts.try_increment` (`crates/execution/txpool/src/guard.rs:260-262`) since it never inspects balance for this payer class.
5. During block building, the first included sponsored transaction debits `P`'s balance in `validate_against_state_and_deduct_caller`; the remaining three fail the balance check at execution/inclusion time, having consumed pool admission, validation, and (if a builder includes them optimistically) execution slots for nothing.

*Note: I could not execute this end-to-end in a live devnet within this session; the above is derived from static analysis of the cited admission and fee-check code paths and the explicit trusted/non-trusted branch divergence in `guard.rs`. Confirming the exact block-builder behavior on an over-committed non-trusted payer (whether it drops silently or reverts and burns intrinsic gas) would require running the load-test/devnet harness.*

    #[must_use = "discarding the result silently skips the gas-and-tip check"]
    pub fn validate_gas_and_tip(
        payer_balance: U256,
        sender_balance: U256,
        payer_is_sender: bool,
        gas_limit: u64,
        payer_auth_cost: u64,
        max_fee: u128,
        tip: U256,
    ) -> Result<(), FeeError> {
        let gas = Self::max_fee_charge(gas_limit, payer_auth_cost, max_fee);
        if payer_is_sender {
            let required = gas.saturating_add(tip);
            if payer_balance < required {
                return Err(FeeError::InsufficientBalance { balance: payer_balance, required });
            }
            return Ok(());
        }
        if payer_balance < gas {
            return Err(FeeError::InsufficientBalance { balance: payer_balance, required: gas });
        }
        if sender_balance < tip {
            return Err(FeeError::InsufficientBalance { balance: sender_balance, required: tip });
        }
        Ok(())
    }
