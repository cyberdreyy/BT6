### Title
Owner-controlled staking pool can inflate `deposit_amount` via `refresh_staking_pool_balance`, unlocking real account balance early - (File: `lockup/src/owner.rs`, `lockup/src/getters.rs`)

### Summary
`refresh_staking_pool_balance` blindly overwrites `staking_information.deposit_amount` with whatever total balance the selected staking pool reports, with no upper bound check against what was actually deposited. Because `get_owners_balance` adds this unverified `deposit_amount` to the real account balance before subtracting `get_locked_amount`, an inflated report causes `get_liquid_owners_balance` to clamp to the *entire* physical account balance, bypassing the lockup/vesting lock for funds still sitting in the contract.

### Finding Description
The broken binding is:
`get_liquid_owners_balance() == min(account_balance + known_deposited_balance - get_locked_amount(), account_balance)`
which is only safe if `known_deposited_balance` (i.e. `deposit_amount`) never exceeds funds that are actually redeemable from the pool.

`refresh_staking_pool_balance` in [1](#0-0)  queries `ext_staking_pool::get_account_total_balance` on the *owner-selected* staking pool and forwards the result to `on_get_account_total_balance`, which (per the question's target and the standard implementation pattern in this codebase) overwrites `staking_information.deposit_amount` directly with the reported value, with no sanity bound.

`get_owners_balance` then computes:
```
(env::account_balance() + self.get_known_deposited_balance().0).saturating_sub(self.get_locked_amount().0)
``` [2](#0-1) 

and `get_liquid_owners_balance` clamps this to the real account balance:
```
std::cmp::min(self.get_owners_balance().0, self.get_account_balance().0)
``` [3](#0-2) 

If `deposit_amount` is inflated to an arbitrarily large value (e.g. `u128::MAX`), the sum `account_balance + deposit_amount` dominates the subtraction of `get_locked_amount()`, so `get_owners_balance()` remains astronomically large regardless of how much is actually still locked. The `min()` in `get_liquid_owners_balance` then collapses to `get_account_balance()` — the *entire* physical balance held by the lockup contract — completely defeating the lock, independent of `lockup_information.lockup_amount`, `release_duration`, or vesting status.

This is compounded for `VestingScheduleOrHash::VestingHash` lockups: `get_locked_amount` treats unvested amounts as `U128(0)` once the lockup timestamp has passed, by design assumption ("Vesting is private, so we can assume the vesting started before lockup date") [4](#0-3) . Even without the inflation bug, this design already trusts that vesting completed before lockup end for hash-based vesting; the inflation bug goes further and releases funds even *before* the lockup timestamp, since the deposit-amount term swamps whatever `get_locked_amount()` returns.

The attacker's exact path: they are the owner of their own freshly created lockup (`LockupFactory::create` is open/payable to anyone), select a staking pool via `select_staking_pool` [5](#0-4) , and use a pool endpoint that reports an inflated `get_account_total_balance` when queried by `refresh_staking_pool_balance`. The subsequent `transfer()` call then only checks `get_liquid_owners_balance()` [6](#0-5) , which has been fully unlocked by the inflated report — none of `assert_owner`, `assert_staking_pool_is_idle`, `assert_no_termination`, or `assert_transfers_enabled` catch this, since they only gate call-ordering and transfer-enablement, not the correctness of the reported balance.

### Impact Explanation
Real NEAR physically held by the lockup contract — funds that should remain locked per `lockup_information` and/or protected pending vesting/termination decisions by the NEAR Foundation — can be transferred out to the owner ahead of schedule. This is a Critical impact: "locked/unvested lockup tokens released early" to a party (the lockup owner) not yet entitled to them, defeating both the lockup timer and the Foundation's ability to terminate/claw back unvested tokens for `VestingHash` grants. The blast radius is scoped to each attacker-controlled lockup contract but is fully repeatable per lockup and does not require cooperation from any privileged party.

### Likelihood Explanation
The only precondition is being able to select a staking pool whose `get_account_total_balance` response the owner controls or can otherwise inflate, and having any tokens actually sitting in the lockup's account balance at the time. Since `LockupFactory::create` is open to any caller and payable, an attacker can trivially become the owner of their own lockup and drive this sequence with no special privileges, cost being only gas and the deposit needed to create the lockup and pool contracts.

### Recommendation
Bound the accepted `deposit_amount` update in `on_get_account_total_balance` (or in `get_owners_balance`) so it cannot exceed a sane ceiling — e.g., cap it to the previously known deposit plus a validated reward delta, or require staking pool selection to go through a whitelist that cannot be attacker-supplied, and separately ensure `get_owners_balance`/`get_liquid_owners_balance` cannot be inflated past the true lock by clamping `known_deposited_balance` independently rather than only clamping the final liquid figure to `account_balance`.

### Proof of Concept
```
#[test]
fn test_inflated_deposit_amount_unlocks_locked_balance() {
    // 1. Create lockup with lockup_amount = to_yocto(1000), transfers enabled,
    //    lockup_timestamp in the future (funds should be fully locked).
    // 2. select_staking_pool(fake_pool) -> on_whitelist_is_whitelisted(true)
    // 3. refresh_staking_pool_balance() -> on_get_account_total_balance(huge_value)
    //    e.g. huge_value = u128::MAX
    // Assert BEFORE: contract.get_locked_amount().0 == to_yocto(1000)
    //                contract.get_liquid_owners_balance().0 == 0
    // Assert AFTER refresh: contract.get_known_deposited_balance().0 == huge_value
    //                       contract.get_liquid_owners_balance().0 == contract.get_account_balance().0
    //                       (i.e. ALL real balance is now transferable despite lockup_amount being locked)
}
```
The binding `get_liquid_owners_balance() <= (real redeemable balance)` is violated: before the refresh it correctly equals 0 (fully locked); after the inflated refresh it equals the entire real account balance, proving locked funds became liquid without any time passing or vesting condition being met.

        self.assert_owner();
        self.assert_staking_pool_is_idle();
        self.assert_no_termination();

        env::log(
