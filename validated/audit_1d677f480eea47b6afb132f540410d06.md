### Title
APR0 withdraw receipts escape their loss haircut when `principalEpoch` lags behind `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the CVE's out-of-bounds read (reading the wrong state for the current context), `IdleCreditVault.requestWithdraw` looks up the loss-adjusted receipt guard at the wrong epoch key for APR0 users. `Apr0UserData.principalEpoch` is only set when the principal bucket transitions from zero (line 571-574), while `lastWithdrawRequest` is updated on every request (line 282). If an APR0 user's pending receipt is haircut by `stopEpochWithDuration`/`collectWithdrawFunds` in a later epoch than `principalEpoch`, the guard in `requestWithdraw` (lines 263-271) fails to detect it because it requires `apr0Users[_user].principalEpoch == lossEpoch`. The user opens a new request, `lastWithdrawRequest` is overwritten past the loss epoch, and the entire APR0 principal bucket — including the haircutted portion — is later claimed at par through `_claimFundedWithdrawRequest` (lines 338-349), skipping `_claimLossAdjustedWithdrawRequest` entirely.

### Finding Description
The loss-adjusted claim path keys off `lastWithdrawRequest[_user]`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:789-800
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
```

The re-request guard keys the APR0 receipt off `principalEpoch`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:263-270
if (
  lossRecoveryPrice != 0 &&
  (withdrawsRequestsByEpoch[_user][lossEpoch] != 0 ||
  (apr0Users[_user].principal != 0 && apr0Users[_user].principalEpoch == lossEpoch))
) revert NotAllowed();
```

But `_requestWithdrawApr0` never updates `principalEpoch` for subsequent requests:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:570-574
if (_apr0User.principal == 0) {
  _apr0User.principalEpoch = epochNumber;
}
_apr0User.principal += _amount;
```

Attack sequence (APR0 mode, `unscaledApr == 0`):

1. Buffer phase, epoch E1: attacker calls `requestWithdraw(amount, attacker, principal)` → `principalEpoch = E1`, `lastWithdrawRequest = E1`, `pendingWithdraws += amount`.
2. Epoch E1 → E2 boundary: `stopEpoch` runs normally (no loss yet; `collectWithdrawFunds` funds at par → `pendingWithdraws` would be cleared... to keep the receipt pending into E2 the loss must land on the epoch in which the receipt is pending). Concretely: the attacker re-requests in epoch E2 (guard passes, `principalEpoch` stays E1, `lastWithdrawRequest = E2`), then epoch E2 ends via `stopEpochWithDuration(_lossAmount)` and `collectWithdrawFunds` funds less than `pendingBasis`, writing `lossRecoveryPriceByEpoch[E2] < 1e18` and zeroing `pendingWithdraws`.
3. Buffer phase, epoch E3: attacker calls `requestWithdraw` again. Now `lossEpoch = lastWithdrawRequest = E2`, `lossRecoveryPriceByEpoch[E2] != 0`, but `withdrawsRequestsByEpoch[attacker][E2] == 0` (APR0 path never writes it) and `principalEpoch == E1 != E2` → the `NotAllowed` revert is bypassed. `lastWithdrawRequest` is set to E3.
4. After epoch E3 ends (`epochNumber > E3`), attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[E3] == 0` and returns 0 — the E2 haircut is never applied. `_claimFundedWithdrawRequest` then pays `settledPrincipal + principal + settledInterest` at par via `_transferFundedClaim`.

The haircut `principal_E2 * (1 - lossRecoveryPriceByEpoch[E2])` is paid out of funded strategy underlyings that belong to other claimants/LPs. Additionally, the APR0 rate applied at settlement is read from `apr0RateByEpoch[E1]`, so the mixed-epoch bucket settles interest at the wrong epoch's rate as well — the same class of stale-index read.

### Impact Explanation
Direct theft / insolvency: the attacker recovers the full principal that the protocol already crystallized as a loss, funded from underlyings reserved for other withdraw claimants in `_transferFundedClaim`. Loss equals `principal * (1 - lossRecoveryPriceByEpoch[lossEpoch])` plus any miscalculated APR0 interest. With a 50% loss-adjusted price on a 1M USDC pool, an attacker holding the dominant pending receipt extracts ~500k USDC above their entitlement, leaving later claimants unbacked.

### Likelihood Explanation
Requires only a KYC-passing lender (an allowed unprivileged attacker) in a fixed-APR0 pool where an epoch ends with a realized loss (`stopEpochWithDuration` with `_lossAmount > 0`, the bad-debt-loss path explicitly supported). The attacker needs one request before the loss epoch, one request in the loss epoch, and one request after — all normal user calls. No privileged cooperation and no timing race is needed; honest borrower/manager epoch calls sequence around the attacker's requests.

### Recommendation
Track APR0 pending receipts per epoch like normal receipts (e.g., write the pending APR0 principal into `withdrawsRequestsByEpoch` or a dedicated per-epoch mapping at request time, or update `principalEpoch` on every `_requestWithdrawApr0` call / store per-epoch principal), so the guard at lines 263-271 and `_clearWithdrawClaimForEpoch` key on the correct epoch. Alternatively, iterate/check whether `lossRecoveryPriceByEpoch` is nonzero for any epoch with an unclaimed receipt rather than relying on a single `lastWithdrawRequest` cursor that newer requests can move past.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers; APR0 pool configured via `setAprsWithBuffer(0, ...)`):

```solidity
function testApr0LossHaircutEscape() external {
    // APR0 mode: unscaledApr == 0
    _setApr0Mode();
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 1_000_000 * ONE_SCALE, true); // KYC'd lender

    // E1 buffer: first APR0 request -> principalEpoch = E1, lastWithdrawRequest = E1
    _requestWithdrawWithUser(attacker, SMALL_TRANCHES);
    _stopCurrentEpoch(); // E1 fully funded, pendingWithdraws == 0... 

    // E2 buffer: second APR0 request -> principalEpoch stays E1, lastWithdrawRequest = E2
    _requestWithdrawWithUser(attacker, BIG_TRANCHES);

    // E2 ends with realized loss: borrower funds less than pendingBasis
    deal(defaultUnderlying, borrower, partialFunds);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(lossApr, lossAmount); // -> collectWithdrawFunds(partial)
    // lossRecoveryPriceByEpoch[E2] = partial * 1e18 / pendingBasis < 1e18

    // E3 buffer: guard bypassed because principalEpoch(E1) != lossEpoch(E2)
    _requestWithdrawWithUser(attacker, DUST_TRANCHES); // does NOT revert (bug)
    // lastWithdrawRequest = E3

    _stopCurrentEpoch(); // epochNumber > E3

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    // attacker receives settledPrincipal+principal at PAR; the E2 haircut
    // (BIG_TRANCHES * (1 - lossRecoveryPriceByEpoch[E2])) was never applied.
    assertGt(underlying.balanceOf(attacker) - balPre,
             BIG_TRANCHES * strategy.lossRecoveryPriceByEpoch(E2) / 1e18);
}
```

The assertion shows the payout exceeds the haircut-adjusted entitlement, draining funded underlyings owed to other claimants.
