### Title
Stale confirmations from removed multisig members still count toward execution threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges pending requests and confirmations that were *created* by the removed member, but it never scrubs that member's confirmations from *other* pending requests they had merely confirmed. Because `confirm` counts entries in the `confirmations` set without checking that each confirming identity is still in `self.members`, a request can later be pushed over `num_confirmations` using one or more confirmations from accounts/keys that have since been removed from the multisig, letting it execute with fewer live-member confirmations than the configured threshold.

### Finding Description
`confirm` decides whether to execute a request purely by set size: [1](#0-0) 

It never re-validates that the accounts/keys already present in `confirmations` are still current members — it only checks that the *current* caller is a member via `assert_valid_request`/`current_member`: [2](#0-1) 

`delete_member` cleans up state, but the cleanup is scoped to requests *originated by* the removed member only: [3](#0-2) 

```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```

If the removed member had instead *confirmed* (not created) some other pending request `R`, that confirmation entry inside `self.confirmations.get(&R)` is left untouched. The invariant the contract is supposed to maintain is:

```
confirmations_counted_towards_threshold(R) == confirmations_from_current_live_members(R)
```

After a member removal, this equality breaks: `confirmations_counted_towards_threshold(R)` can include an entry belonging to an account/key that is no longer in `self.members`, while `confirmations_from_current_live_members(R)` is strictly smaller.

### Impact Explanation
This is a threshold-bypass on the multisig's own custody boundary: a `MultiSigRequest` (e.g. `Transfer`, `AddKey`/full-access-key, `DeployContract`, `FunctionCall`) can be pushed to execution with a live-member confirmation count strictly below `num_confirmations`, because a stale confirmation from a removed member is counted as if it were live. This matches the "Critical" impact category explicitly listed in scope: *"a multisig request executed below threshold."* Any funds transfer, key addition, or contract upgrade bundled in that request would then be executed with less authorization than the multisig's configured security policy requires.

### Likelihood Explanation
This requires only ordinary multisig operation, not a privileged bug or malicious validator:
1. A request is created and gets confirmations from fewer than `num_confirmations` members (a routine partial-confirmation state that can persist indefinitely — there is no expiry tied to membership changes).
2. Independently, one of those confirming members is later removed via a normal `DeleteMember` request (e.g., because a key is rotated/compromised or an employee leaves) — a routine administrative action.
3. Remaining members then push the still-pending request to the confirmation threshold; the stale confirmation is counted, and the request executes.

No attacker-supplied code, no compromise of a live key, and no exploitation of gas/DoS is required — only ordinary sequencing of two legitimate multisig actions (partial confirmation followed by member removal followed by continued confirmation of the old request). This is a plausible operational sequence for any multisig account that rotates or revokes members while requests are outstanding.

### Recommendation
When executing `delete_member`, iterate over *all* pending requests' confirmation sets (not just those the deleted member created) and remove the deleted member's identity from each. Alternatively, validate at `confirm`-time (when counting toward `num_confirmations`) that every entry in `confirmations` still corresponds to a current member of `self.members`, discarding stale entries before comparing against the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A.add_request(R)` where `R` is a `Transfer` (or `AddKey` full-access-key) request to an attacker-controlled receiver. (`A` is the request's `member`, no confirmation yet.)
3. `B.confirm(R)` → `confirmations(R) = {B}` (1 confirmation, count 1 < 3, not executed): [1](#0-0) 
4. `C.confirm(R)` → `confirmations(R) = {B, C}` (count 2 < 3, not executed).
5. Separately, members execute a `DeleteMember { member: C }` request (reaching its own 3-of-4 threshold from `A, B, D`), removing `C` from `self.members`. Because `R.member == A` (not `C`), the filter in `delete_member` does not touch `R`'s confirmations: [4](#0-3) . `confirmations(R)` still equals `{B, C}` even though `C` is no longer a member.
6. `D.confirm(R)` → `confirmations(R).len() + 1 == 3 >= num_confirmations (3)` → `execute_request(R)` fires, transferring funds to the attacker/adding the key, even though only `B` and `D` are live members who actually authorized it (`A` never confirmed, `C` is removed) — only 2 genuine live confirmations backed a 3-of-4 threshold. [5](#0-4)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
