### Title
Front-running of `InitializeNonceAccount` allows attacker to hijack nonce authority before the legitimate owner's initialization lands - (File: `programs/system/src/system_instruction.rs`)

### Summary
The Frax report describes a class of bug where a privileged/authority field (withdrawal credentials) can be set by an attacker who front-runs the legitimate party's transaction, before the victim's large-value deposit lands, permanently redirecting control of the funded resource. Agave's System Program `InitializeNonceAccount` instruction exhibits the same structural weakness: it sets the durable-nonce `authority` field without requiring any signature from the account being initialized, so whoever's `InitializeNonceAccount` instruction executes first against a funded, uninitialized, system-owned account wins control of it — permanently, since re-initialization is rejected.

### Finding Description
`initialize_nonce_account` only checks that the target account is writable and uninitialized; it never checks that the account (or any specific authority) is a transaction signer: [1](#0-0) 

The dispatcher in `system_processor.rs` likewise performs no signer check before calling it — it only validates account count and pulls sysvars: [2](#0-1) 

This is different from `AuthorizeNonceAccount`, which explicitly requires the current authority to sign via the `signers` set (see `authorize_inx_bad_authority_fail` test expecting `MissingRequiredSignature`) — but `InitializeNonceAccount` has no equivalent check at all. The `authorized` pubkey supplied in the instruction data becomes the account's permanent authority the moment the instruction executes, exactly like the ETH `withdrawal_credentials` field being fixed by whichever deposit reaches the beacon chain contract first.

The CLI mitigates this by always bundling `CreateAccount` and `InitializeNonceAccount` into a single atomic transaction/message: [3](#0-2) 

But nothing in the System Program itself enforces this atomicity. Any account that is (a) owned by the System Program, (b) uninitialized (all-zero/default state), and (c) funded to at least the rent-exempt minimum for `nonce::state::State::size()` is a valid target for `InitializeNonceAccount` by *anyone*, regardless of who funded/created it. If a wallet, exchange, program, or CLI script performs account creation and nonce initialization as two separate transactions (e.g., funding an address ahead of time, or a multi-step onboarding flow), an attacker monitoring the mempool/leader schedule can submit their own `InitializeNonceAccount(attacker_pubkey)` targeting that address between the two transactions.

### Impact Explanation
Once `InitializeNonceAccount` succeeds, the state transitions to `Initialized` and any subsequent initialize call fails with `InvalidAccountData`: [4](#0-3) 

so the legitimate owner's own initialize transaction (if it still runs) will simply error out, while the attacker now holds the nonce `authority`. That authority controls `AdvanceNonceAccount`, `AuthorizeNonceAccount`, and — critically — `WithdrawNonceAccount`, meaning the attacker can withdraw all lamports funded into the account (which is precisely the "misdirected funds" impact class the original report describes for withdrawal credentials). This is reachable purely from an ordinary user's transaction against the System Program; no privileged access is required.

### Likelihood Explanation
Likelihood is bounded by how often callers split account creation and nonce initialization into separate transactions instead of bundling them atomically (as `solana-cli`/`create_nonce_account` do). It is not exploitable against the standard CLI flow (which is atomic), but any custom integration, wallet, exchange withdrawal system, or on-chain program that funds an address first and initializes it as a nonce account in a later transaction is exposed. Given nonce accounts are a widely used primitive for durable transactions (exchanges, bots, programs), this pattern is plausible outside the reference CLI.

### Recommendation
Require that the account being initialized (or a designated authority) sign the `InitializeNonceAccount` instruction, mirroring the signer requirement already present in `AuthorizeNonceAccount`, so an unrelated party cannot claim authority over a pre-funded but uninitialized account. Alternatively/additionally, document and consider enforcing (e.g., via a runtime check or a new instruction variant) that `InitializeNonceAccount` may only be processed in the same transaction/instruction sequence as the account's `CreateAccount`, closing the front-running window entirely.

### Proof of Concept
1. Victim submits transaction A: `SystemInstruction::CreateAccount` funding address `N` (owned by System Program, uninitialized, balance ≥ rent-exempt minimum for nonce state), intending to send transaction B: `SystemInstruction::InitializeNonceAccount(victim_authority)` shortly after.
2. Attacker observes transaction A land (or observes address `N` is funded/uninitialized) and immediately submits `SystemInstruction::InitializeNonceAccount(attacker_authority)` targeting `N`, with no requirement to sign as `N` — see `initialize_nonce_account`, which checks only writability and state, never a signer set.
3. If the attacker's transaction lands first, `N`'s state becomes `State::Initialized(Data{ authority: attacker_authority, .. })`.
4. Victim's transaction B now fails with `InstructionError::InvalidAccountData` because the account is already `Initialized`.
5. Attacker calls `WithdrawNonceAccount` (or `AuthorizeNonceAccount`) as the recognized authority and drains/repurposes the lamports the victim funded into `N`.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
