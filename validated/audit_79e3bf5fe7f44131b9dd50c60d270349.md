### Title
Unchecked failure to extract `email` claim allows OIDC session creation with attacker-influenced empty user identity - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` fails to `return` after detecting that the OIDC ID token's `email` claim is missing or of the wrong type. Execution continues with `email == ""`, and a new authenticated session row is written to `oidc_sessions` using that empty value, mirroring the reported bug class: a failure/error condition is detected and logged, but not propagated, so the calling code silently continues as if nothing went wrong.

### Finding Description
In `handleTokenExchange`: [1](#0-0) 
the type assertion `claims["email"].(string)` failing is logged and a 500 response is written via `c.String(...)`, but unlike every other error branch in this function (which call `return` immediately, e.g. lines 195, 203, 211, 218, 224, 244, 270), this branch has no `return`. Execution falls through to: [2](#0-1) 
where role mapping (`IDClaimsToUserRole`, based on independently-validated group claims) proceeds, a new session record is inserted into `oidc_sessions` with `user_email = ""`, an audit log entry is written, and finally the session cookie is saved and a `200 OK` JSON response is written at the end of the handler: [3](#0-2) 
Because Gin only fixes the response status on the first `WriteHeader` call, the earlier `c.String(http.StatusInternalServerError, ...)` call does not abort the handler; the function keeps running to completion and creates a working, valid authenticated session cookie for the client despite the intended error path.

The resulting session is persisted and later read back by `AuthorizedUserWithSession`: [4](#0-3) 
which returns a `clsessions.User{Email: "", Role: <role from group claims>}` for any request presenting that session cookie — a fully authenticated, unprivileged-client-obtained session tied to an empty/ambiguous identity rather than being rejected.

### Impact Explanation
An OIDC identity provider response lacking (or misformatted for) the standard `email` claim — which is a realistic condition depending on `email` scope grants, custom claim configurations, or a provider/response quirk — results in the node minting a valid, role-bearing session cookie associated with `user_email = ""` instead of aborting the login. This is a request-impersonation / broken-authentication analog to the report's "operation continues despite unchecked failure": the intended fail-closed behavior (reject login on missing email) is instead fail-open, silently issuing a session under an empty identity while still assigning a real RBAC role (Admin/Edit/Run/Read) derived from group claims. Audit logs (`AuthLoginSuccessNo2FA`) will also record an empty email, undermining traceability, and any downstream code that keys behavior off `user_email` for uniqueness or user-scoping could treat all such empty-email sessions as one indistinguishable identity, creating cross-session/cross-user confusion.

### Likelihood Explanation
Likelihood is moderate: it requires an OIDC provider response (from the configured, presumably-trusted IdP) that omits or malforms the `email` claim while still supplying a role/group claim that maps successfully — plausible with certain scope configurations or custom claim setups, and reachable by any unprivileged client that can complete the standard `/oidc-login` → provider → `/exchange` flow without any privileged access needed.

### Recommendation
Add a `return` after the 500 response in the `email` claim check so the handler aborts immediately on failure, consistent with every other error path in this function:

```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```

### Proof of Concept
1. Configure OIDC login with a valid IdP where the ID token issued for a user omits the `email` claim (or configure a claim-mapping/proxy that strips it) while the token still carries valid group claims mapping to a role (e.g., Admin).
2. Client completes `/oidc-login` and posts the resulting `code`/`state` to the token-exchange endpoint handled by `handleTokenExchange`.
3. `claims["email"].(string)` assertion fails (`ok == false`); code logs the error, writes a 500 response, but does not return.
4. Execution continues: role mapping succeeds, a row is inserted into `oidc_sessions` with `user_email = ''` and the mapped role, and `ginSession.Save()` persists a valid session cookie for the client.
5. The client's browser now holds a valid session cookie; subsequent authenticated requests via `AuthenticateBySession`/`AuthenticateGQL` succeed and return a `User{Email: "", Role: <mapped role>}`, despite the server having detected and reported a failure during login.
