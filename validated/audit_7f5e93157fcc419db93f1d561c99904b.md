### Title
Attacker can front-run the deterministic lockup address for any victim owner and permanently install a self-chosen `VestingSchedule` - ([File: lockup-factory/src/lib.rs])

### Summary
`create()` derives the lockup account id deterministically from `sha256(owner_account_id)` and performs `create_account()` unconditionally, with no check that the caller is the owner, the foundation, or any authorized grantor, and no check that the address is still free. [1](#0-0)  Any unprivileged account can call `create` for a `victim` `owner_account_id` who has no lockup yet, attaching only `MIN_ATTACHED_BALANCE` (3.5 NEAR) and supplying `vesting_schedule=Some(VestingScheduleOrHash::VestingSchedule(<attacker_schedule>))`, deploying `LockupContract` at that fixed address with a vesting schedule the victim's real grantor never chose. [2](#0-1) [3](#0-2) 

### Finding Description
The claimed binding is: `vesting_schedule_in_deployed_contract(owner=victim) == vesting_schedule_the_victim's_rightful_grantor_intended`. Tracing the code shows this binding is not enforced at all.

- `create()` is `#[payable]` and public, with no `assert_owner`, no `assert_called_by_foundation`, and no restriction on `predecessor_account_id`; the only guard is `attached_deposit() >= MIN_ATTACHED_BALANCE`. [4](#0-3) 
- The target account id is fully deterministic from `owner_account_id` alone: `sha256(owner_account_id)[..20] + "." + factory_account_id`. [5](#0-4) 
- `vesting_schedule` is taken verbatim from caller input and forwarded into `LockupArgs`, which is passed to the deployed contract's `new`. [6](#0-5) [7](#0-6) 
- In `LockupContract::new`, when `Some(VestingScheduleOrHash::VestingSchedule(vs))` is supplied, it is stored directly as `VestingInformation::VestingSchedule(vs)`; the only extra requirement is that a valid `foundation_account_id` (taken from the factory's own state, not attacker input) accompanies it. [8](#0-7)  There is no signature, no hash-commitment requirement, and no check that the `owner_account_id`'s real grantor authorized this specific schedule.

Exploit flow: attacker (unprivileged) calls `create(owner_account_id = victim, vesting_schedule = Some(VestingScheduleOrHash::VestingSchedule(attacker_schedule)), ...)` with `attached_deposit == MIN_ATTACHED_BALANCE`. The factory computes the same deterministic address the victim's legitimate grantor (e.g. the Foundation) would later use, and deploys `LockupContract` there with the attacker's chosen schedule. Because NEAR account creation is a one-time action, once this address exists, any later legitimate `create()` call for the same `owner_account_id` will fail at `create_account()` — the whole batched promise fails, and `on_lockup_create` merely refunds the deposit to the legitimate caller rather than raising any error that would reveal the takeover. [9](#0-8)  The victim's real lockup, with the schedule their real grantor intended, can never be deployed at that name again through this factory. The address is permanently squatted with a `LockupContract` whose `vesting_information` and `lockup_amount` (only the attacker's 3.5 NEAR) were entirely attacker-chosen, satisfying "a lockup deployed with parameters its rightful creator never chose."

None of the listed guards (`assert_self`, `is_promise_success`, `assert_one_yocto`, etc.) address this because they operate on the callback/rollback path, not on authorization of who may call `create` or claim a given `owner_account_id`/deterministic address first.

### Impact Explanation
No NEAR is stolen from a third party in this specific call (the attacker only spends their own 3.5 NEAR), but the deterministic lockup address for `owner_account_id = victim` becomes irreversibly occupied by a contract whose `vesting_schedule`/`lockup_amount` were chosen unilaterally by an attacker, blocking the legitimate grantor (e.g. NEAR Foundation) from ever deploying the victim's real, intended lockup terms through this factory for that owner. This matches the Critical category "a lockup deployed with parameters its rightful creator never chose." It is repeatable against any owner account that hasn't yet had a lockup created, i.e. it can be front-run against the entire population of not-yet-onboarded lockup recipients.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only to know (or guess) a target `owner_account_id` before the legitimate grantor calls `create` for it, and to have 3.5 NEAR available. There is no whitelist, allowlist, or owner check gating `create()`, so this is trivially callable by anyone, at any time, against any not-yet-created owner lockup. This is a front-running race rather than a guaranteed-first attack (the legitimate grantor could win the race if they create first), but nothing in the contract prevents or detects the attacker's attempt, and cost is low and fully repeatable across many victim accounts.

### Recommendation
Restrict `create()` so only an authorized party (e.g., `assert_called_by_foundation`/an allow-listed grantor, or requiring the `predecessor_account_id == owner_account_id` for self-created lockups without vesting, and foundation-only for vesting lockups) can deploy a lockup for a given `owner_account_id`. Alternatively, require that any `vesting_schedule` supplied as a plain `VestingSchedule` (not a hash) be signed/authorized by the foundation, and reject `create()` calls where `vesting_schedule.is_some()` unless `predecessor_account_id == foundation_account_id`.

### Proof of Concept
```rust
// cargo test in lockup-factory
#[test]
fn test_front_run_victim_lockup_with_attacker_schedule() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker-chosen schedule: immediately fully vested (start == end == now)
    let attacker_schedule = VestingSchedule {
        start_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        cliff_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
        end_timestamp: to_ts(GENESIS_TIME_IN_DAYS).into(),
    };

    context.is_view = false;
    context.predecessor_account_id = String::from(attacker_account()); // unprivileged attacker
    context.attached_deposit = MIN_ATTACHED_BALANCE; // exactly minimum
    testing_env!(context.clone());

    // Attacker calls create() for victim owner, choosing the vesting schedule directly
    contract.create(
        account_tokens_owner(), // victim owner, has no lockup yet
        0.into(),
        None,
        Some(VestingScheduleOrHash::VestingSchedule(attacker_schedule)),
        None,
        None,
    );

    // Deterministic address is now taken with attacker's schedule for victim owner.
    // A subsequent legitimate create() call by the real grantor for the same owner
    // will fail at create_account() (simulate PromiseResult::Failed) and only
    // trigger the refund path in on_lockup_create, never reaching a state where
    // the legitimate schedule is installed:
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        MIN_ATTACHED_BALANCE.into(),
        String::from(legit_grantor_account()),
    );
    assert_eq!(res, false); // legitimate deployment permanently blocked for this owner
}
```
This demonstrates the binding `vesting_schedule_deployed(victim) == vesting_schedule_intended_by_rightful_grantor` is broken: the deployed schedule is the attacker's, and the rightful grantor's subsequent attempt is rejected by the NEAR runtime's account-creation uniqueness rule, with only a deposit refund and no error surfaced to prevent or reverse the takeover.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
