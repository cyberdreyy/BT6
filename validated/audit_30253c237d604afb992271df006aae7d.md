### Title
Post-default instant withdraw receipts collide with the default-epoch claim key and drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` has no `defaultRecoveryFinalized` handling, unlike `requestWithdraw` which routes post-default requests into the separate `postDefaultRequests` bucket. After `finalizeDefaultRecovery`, `epochNumber == defaultRecoveryEpoch` and never advances again (the pool is defaulted; no further `stopEpoch`/`deposit` increments it). A new instant-withdraw request made after default is therefore recorded under `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — the exact key `_claimDefaultedInstantWithdrawRequest` reads to identify *pre-default* defaulted receipts. The fresh receipt is paid out of `defaultRecoveryReserve` at `defaultRecoveryPrice`, a reserve that was sized only for claims existing at finalization. This is the direct analog of CVE-2022-40304: a corrupted/reused key (epoch index) makes an entry be claimed twice — once as its real value and once as a default-recovery claim that was never provisioned.

### Finding Description
- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) burns the CDO's strategy tokens, mints receipt tokens to the user, and unconditionally does:
  ```
  instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
  instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
  pendingInstantWithdraws += _amount;
  ```
  There is no `if (defaultRecoveryFinalized)` branch and no requirement to claim old receipts first — contrast with `requestWithdraw` (lines 247-258), which explicitly reverts unless the user has no open requests and routes the request to `postDefaultRequests`.
- `finalizeDefaultRecovery` (lines 690-696) sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`, then `defaultRecoveryReserve = reserveAmount` sized from `defaultPendingClaimBasis()` computed *before* any post-default requests.
- `claimInstantWithdrawRequest` (lines 380-393): when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`, it calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` where `defaultEpoch = defaultRecoveryEpoch` — i.e., the same bucket the post-default request just wrote to. It then pays `(claimBasis * defaultRecoveryPrice) / 1e18` via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve` (lines 912-917).
- The receipt's cost basis is the post-default tranche price (BB-side claim basis is haircut/zero via `_defaultBBBasis` at lines 744-755 and the active-NAV burn at 701-705), while the payout comes out of the fixed `defaultRecoveryReserve` at `defaultRecoveryPrice`. Nothing adds backing for the new receipt — `pendingInstantWithdraws` grows but no `collectInstantWithdrawFunds` ever runs again, and `defaultPendingClaimBasis` is only consulted at finalization, which already happened.

### Impact Explanation
Every defaulted-epoch recovery claimant (normal withdrawers, unfunded instant withdrawers, active AA/BB holders whose NAV was crystallized at `defaultRecoveryPrice`) shares `defaultRecoveryReserve`. An attacker holding defaulted tranches can mint an instant receipt post-default and immediately claim `receiptBasis * defaultRecoveryPrice` from that reserve. Because the reserve was provisioned only for pre-default claims, each such claim is unbacked: it directly steals underlying owed to legitimate claimants and can fully deplete the reserve, leaving later honest claimants with reverts/dust (permanent loss of unclaimed recovery). Loss is bounded only by the attacker's defaulted-tranche holdings times the recovery price; with `defaultRecoveryPrice < 1` the attacker profits whenever their acquisition cost of the receipt basis is below the recovery ratio.

### Likelihood Explanation
- Attacker is a normal KYC'd tranche holder requesting an instant withdrawal — unprivileged path, no privileged collusion.
- Requires `defaultInstantWithdrawsFinalized == true`, i.e., some unfunded instant requests at default (`pendingInstantWithdraws != 0` at finalization), and the CDO still accepting instant-withdraw requests post-default (`allowInstantWithdraw`/`disableInstantWithdraw` flags are manager-set but were already enabled for the instant bucket to exist).
- I could not fully verify the CDO-side gating of `requestInstantWithdraw` after `defaulted = true` (the `IdleCDOEpochVariant` function bodies were not fully retrieved before the iteration limit). If the CDO hard-reverts instant requests when `defaulted`, this path is unreachable and the finding degrades to a defense-in-depth gap; the strategy-level asymmetry (guarded `requestWithdraw` vs unguarded `requestInstantWithdraw`) strongly suggests the intended invariant is "no new receipts may enter the defaulted-epoch key", which `requestInstantWithdraw` violates.

### Recommendation
Mirror the `requestWithdraw` post-default logic in `requestInstantWithdraw`: after `_ensureDefaultRecoveryInitialized()`, if `defaultRecoveryFinalized`, either revert outright or route the request into a post-default bucket that can never be read by `_claimDefaultedInstantWithdrawRequest` (e.g., reject instant requests since no future epoch will fund them). Additionally, in `_claimDefaultedInstantWithdrawRequest`, snapshot/limit the claim basis to `instantWithdrawClaimsByEpoch[defaultEpoch]` as recorded at finalization rather than reading the mutable per-user epoch entry.

### Proof of Concept
Foundry fork sketch (`.t.sol`, against `IdleCDOEpochVariant` + `IdleCreditVault` proxy):

```solidity
// Setup: deposit AA/BB, start epoch, user A requests instant withdraw,
// next epoch starts with partial funding so pendingInstantWithdraws != 0.
cdoEpoch.stopEpoch(apr, funded);           // epoch N ends
// borrower defaults
cdoEpoch.requestWithdraw / borrower fails; manager calls _handleBorrowerDefault();
// finalize recovery at price p < 1e18
strategy.finalizeDefaultRecovery(recovered, recoverySource); // via CDO finalizeDefaultRecovery
assertEq(strategy.defaultRecoveryEpoch(), strategy.epochNumber()); // key collides

// Attack: attacker holds defaulted tranches (bought post-default at defaulted price)
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(trancheAmount, tranche);   // writes instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch]
// pendingInstantWithdraws was reset? note: it was not cleared at finalization -> still !=0,
// so claimInstantWithdrawRequest takes the defaulted-instant path:
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// Attacker receives claimBasis * defaultRecoveryPrice from defaultRecoveryReserve
// without that basis having been provisioned; honest defaulted claimants are left short:
assertLt(strategy.defaultRecoveryReserve(), expectedReserveForHonestClaimants);
```

Key assertions: `strategy.instantWithdrawsRequestsByEpoch(attacker, defaultRecoveryEpoch)` equals the post-default request amount, and the payout decremented `defaultRecoveryReserve` that `finalizeDefaultRecovery` sized only for pre-default claims.
