### Title
Unbounded zip entry processing in `ExtractZipArchive`/`fastzip` extraction allows inode/CPU exhaustion via crafted artifact archives - ([File: commands/helpers/artifacts_downloader.go])

### Summary
`ArtifactsDownloaderCommand.Execute` calls `extractor.Extract(context.Background())` with no deadline, entry-count limit, or path-depth limit enforced beforehand. The underlying zip extraction path (`ExtractZipArchive` in `helpers/archives/zip_extract.go`, used by the `ziplegacy` extractor, and the `fastzip`-based extractor) iterates every zip entry and calls `os.MkdirAll`/`os.Mkdir` per entry with no cap, so a crafted archive with millions of tiny/zero-byte entries or deeply nested paths can drive excessive directory-creation syscalls and inode consumption on the runner host.

### Finding Description
`ArtifactsDownloaderCommand.Execute` [1](#0-0)  builds an extractor via `archive.NewExtractor` and calls `extractor.Extract(context.Background())` — no timeout/deadline is attached, and no pre-check of entry count or nesting depth is performed on the downloaded archive before extraction begins.

For the legacy zip path, `ExtractZipArchive` loops over every `zip.File` entry unconditionally and calls `extractZipFile`, which in turn calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` for every single entry, followed by `os.Mkdir`/`os.OpenFile` depending on entry type [2](#0-1) [3](#0-2) . There is no limit on the number of `archive.File` entries processed, nor any restriction on path depth, so a zip with N distinct deeply-nested empty directory paths (or N unique parent directories for zero-byte files) results in on the order of N `MkdirAll` calls, each potentially walking/creating many directory levels. The `fastzip`-backed extractor [4](#0-3)  delegates entirely to the third-party `fastzip.Extractor.Extract(ctx)`, which likewise has no built-in entry-count or depth cap exposed through this integration — only extractor *concurrency* is configurable via `FASTZIP_EXTRACTOR_CONCURRENCY` [5](#0-4) , which controls parallelism, not resource ceilings.

Existing protections (`errorIfGitDirectory`, `path_error_tracker.go`, `path_check_helper.go`) address `.git`-directory warnings and path-error suppression/logging, not entry-count or depth limits — they do not stop the extraction loop from running to completion regardless of scale.

### Impact Explanation
Because there is no cap on entry count, path depth, or wall-clock time (context.Background()), a maliciously crafted artifact — small in byte size (zero-byte files compress trivially) but with millions of entries and/or deeply nested directory paths — can cause the runner process to issue a very large number of `MkdirAll`/`Mkdir`/file-create syscalls. On a shared runner host this can exhaust inodes on the filesystem backing the build directory and consume significant CPU/I/O for an extended period, degrading or blocking other jobs scheduled on the same host (concurrency-per-host DoS). This matches the shared-host resource-exhaustion impact scoped in the question.

### Likelihood Explanation
The attacker only needs to be a normal pipeline author capable of producing a job artifact (fully within an unprivileged GitLab user's control) — CI jobs routinely produce and upload arbitrary file trees as artifacts, and a `zip` containing many trivially-small/empty entries is easy to construct without hitting server-side byte-size limits (which cap total artifact bytes, not entry count or path depth). Extraction is triggered automatically whenever a downstream job with `dependencies:`/`needs:` consumes the artifact, meaning it can execute on a runner host before that job's own script runs, on hosts the attacker's own build stage never directly touched. The main mitigating factor is that the job (and therefore the extraction call) is still bounded by the overall CI job timeout, which limits worst-case duration but not per-entry resource cost incurred during that window; this is a real, though moderate/timeout-bounded, resource-exhaustion path with no code-level cap on entry count or path depth.

### Recommendation
Enforce, prior to calling `extractor.Extract`, hard limits on: (1) total number of zip entries, (2) maximum path depth/length per entry, and (3) overall extraction wall-clock time via a derived `context.WithTimeout` instead of `context.Background()` passed from `ArtifactsDownloaderCommand.Execute`. Reject or truncate archives that exceed these limits before the extraction loop runs, and propagate `ctx.Err()` checks inside `ExtractZipArchive`'s per-file loop so a timeout can abort mid-extraction.

### Proof of Concept
Go test plan (`helpers/archives/zip_extract_test.go` style):
1. Programmatically build an in-memory zip (`archive/zip.Writer`) with N=2,000,000 unique zero-byte file entries, each under a distinct deeply nested path (e.g., `a/b/c/.../<i>/file`) of depth ~50.
2. Call `archives.ExtractZipArchive(zr)` (or the full `ArtifactsDownloaderCommand.Execute` path via `archive.NewExtractor(archive.Zip, ...)` + `extractor.Extract(context.Background())`) and measure wall-clock time and inode/file count created via `os.Stat`/`du -i` on the target temp dir.
3. Assert that extraction either (a) completes within a bounded time budget (e.g., fails the test if it exceeds N seconds) or (b) is rejected outright once an entry-count/depth cap is implemented — currently no such assertion can pass because no cap exists, demonstrating the gap.

```go
func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
```

```go
func ExtractZipArchive(archive *zip.Reader) error {
	tracker := newPathErrorTracker()

	for _, file := range archive.File {
		if err := errorIfGitDirectory(file.Name); tracker.actionable(err) {
			printGitArchiveWarning("extract")
		}

		if err := extractZipFile(file); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}
	}

	for _, file := range archive.File {
		if err := lchmod(file.Name, file.Mode()); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}

		// Process zip metadata
		if err := processZipExtra(&file.FileHeader); tracker.actionable(err) {
			logrus.Warningf("%s: %s (suppressing repeats)", file.Name, err)
		}
	}

	return nil
}
```

```go
func (e *extractor) Extract(ctx context.Context) error {
	opts, err := getExtractorOptionsFromEnvironment()
	if err != nil {
		return err
	}

	extractor, err := fastzip.NewExtractorFromReader(e.r, e.size, e.dir, opts...)
	if err != nil {
		return err
	}
	defer extractor.Close()

	return extractor.Extract(ctx)
}
```

```go
func getExtractorOptionsFromEnvironment() ([]fastzip.ExtractorOption, error) {
	var opts []fastzip.ExtractorOption

	if val := os.Getenv(extractorConcurrency); val != "" {
		concurrency, err := strconv.ParseInt(val, 10, 64)
		if err != nil {
			return nil, fmt.Errorf("fastzip extractor concurrency: %w", err)
		}

		opts = append(opts, fastzip.WithExtractorConcurrency(int(concurrency)))
	}

	return opts, nil
```
