### Title
Builder-index reuse lets a pending bid payment settle against the wrong builder's balance - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_builder_exit_request` allows a builder to exit while it still owes an unsettled `BuilderPendingPayment` recorded by an earlier `SignedExecutionPayloadBid`, because it only checks pending *withdrawals owed to* the builder, not payments *owed by* the builder. Once the builder is exited, swept (`balance == 0`) and its withdrawable epoch has passed, `get_index_for_new_builder` freely reassigns that same `builder_index` to a brand-new builder via `process_builder_deposit_request`. When the deferred payment is later settled by `settle_builder_payment` (invoked from `apply_parent_execution_payload`), the debt is charged against `state.builders[builder_index]`, which by then is the *new* builder — an unrelated party pays for a bid it never made.

### Finding Description
When a bid is accepted, `process_execution_payload_bid` records a `BuilderPendingPayment` keyed only by `builder_index` and a slot-derived `payment_index`: [1](#0-0) 

This payment is deferred and only later resolved during `apply_parent_execution_payload`, which calls `settle_builder_payment(state, payment_index)` up to roughly two epochs after the bid was accepted: [2](#0-1) 

In the meantime, the builder that placed the bid can exit. `process_builder_exit_request` only blocks the exit if the builder has an outstanding *withdrawal* balance, not an outstanding *payment obligation*: [3](#0-2) 

Once exited and swept to `balance == 0`, the same numeric slot is freely reused for a new builder: [4](#0-3) 

The spec text itself acknowledges that `builder_index` values are recycled and that state keyed by an index can become stale relative to the identity of the entity now occupying that slot: [5](#0-4) 

However, that mitigation note only covers *deposits* landing on a stale index (redirected to the exited builder's `execution_address`); it says nothing about the *pending payment settlement path*, which still resolves purely by `builder_index` against `state.builders[builder_index]` at settlement time — i.e. whatever builder currently occupies that slot, not the builder that actually signed the bid.

This is the direct analog of the Venus `placeBid()` bug: the identifier (`comptroller` in Venus / `builder_index` here) is treated as a durable handle to a specific economic actor, but the underlying entity behind that handle can be swapped out (auction restarted / builder registry slot reassigned) between commitment and settlement, with no equality check (`auctionStartBlock` in Venus) binding the settlement to the original actor (e.g. the original builder's `pubkey` or `deposit_epoch`).

### Impact Explanation
If exploited, `settle_builder_payment` decreases the balance of whichever builder currently sits at the recycled `builder_index`, not the original bidder. This is Gwei deducted from a builder that never authorized or committed to the bid — a validator/builder mutated (balance decreased) without its authority, matching the Critical/High impact class ("Gwei created, destroyed or paid to a non-owner" / "a builder ... re-credentialed without its authority").

### Likelihood Explanation
This requires: (1) a builder to place a bid that is accepted and queued as a pending payment, (2) that same builder to exit before the payment settles (allowed by the spec since only *outgoing* withdrawal balance is checked, not owed payments), (3) the builder's balance to be fully swept to zero and its withdrawable epoch to pass, and (4) a new builder deposit to land and be assigned the recycled index before settlement occurs (settlement can be delayed up to ~2 epochs, matching the window `apply_parent_execution_payload`/`process_builder_pending_payments` operate over). This is a purely permissionless sequencing issue reachable by any builder acting alone (no coalition, no client bug), similar to the low-but-real likelihood the C4 judges assigned Medium to the original Venus finding.

### Recommendation
Bind the pending payment/settlement to the specific builder identity rather than just its index — e.g., store and check the builder's `pubkey` (or a monotonically increasing generation counter incremented on every index reuse) alongside `builder_index` in `BuilderPendingPayment`/`BuilderPendingWithdrawal`, and have `settle_builder_payment` verify the stored identity still matches `state.builders[builder_index]` before debiting the balance; alternatively, disallow reuse of a `builder_index` for a new builder registration until all pending payments referencing that index have fully settled.

### Proof of Concept
1. Builder B at index `i` submits a bid with `value = V` for slot `S`; `process_execution_payload_bid` records `builder_pending_payments[...] = {withdrawal: {amount: V, builder_index: i, fee_recipient: F}, weight: 0, proposer_index: P}` (`specs/gloas/beacon-chain.md:2124-2137`).
2. Before the bid's parent payload is settled (up to ~2 epochs later, per `apply_parent_execution_payload`), builder B submits a `BuilderExitRequest`. Since B has no pending *withdrawal* balance (`get_pending_balance_to_withdraw_for_builder(state, i) == 0`), `process_builder_exit_request` allows the exit (`specs/gloas/beacon-chain.md:2291-2307`).
3. B's balance is swept to 0 by the normal builder sweep/withdrawal mechanism, and its `withdrawable_epoch` elapses.
4. A new builder C submits a `BuilderDepositRequest`; `get_index_for_new_builder` returns the recycled index `i` because `builder.withdrawable_epoch <= current_epoch and balance == 0` (`specs/gloas/beacon-chain.md:2212-2219`), and C is registered at index `i` with its own deposited balance.
5. `apply_parent_execution_payload` finally runs `settle_builder_payment(state, payment_index)` for B's original bid; it resolves the payment against `state.builders[i]`, which is now builder C, causing C's freshly deposited balance to be debited for a bid it never placed.

###### New `get_index_for_new_builder`

```python
def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))
```

*Note*: Builder indices are reusable. When a builder exits, its index may later
be reassigned to a different builder with a new public key. Any deposit sent to
an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on

```python
def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
