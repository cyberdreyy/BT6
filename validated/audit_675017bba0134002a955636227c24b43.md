### Title
Post-default withdraw requests can drain the default-recovery reserve before being funded, stealing recovery from defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2022-37434's attacker-controlled length field driving an out-of-bounds read, `IdleCreditVault` lets an attacker-controlled request amount drive a payout out of a shared underlying pool that exceeds the reserve segment actually allocated to it. After `finalizeDefaultRecovery`, any new withdraw request is registered as `postDefaultRequests[_user]` and paid 1:1 via `_transferDefaultRecovery`, which unconditionally decrements `defaultRecoveryReserve` and transfers strategy-held underlying — regardless of whether the borrower has funded that new receipt. The "buffer" being over-read is the default recovery reserve.

### Finding Description
- `requestWithdraw` post-finalization mints a receipt and records `postDefaultRequests[_user] = _amount` without requiring any funding for it [1](#0-0) .
- `claimWithdrawRequest` routes to `_claimPostDefaultWithdrawRequest` first [2](#0-1) .
- `_claimPostDefaultWithdrawRequest` has no epoch-wait, no funding check, and pays the full basis 1:1 by calling `_transferDefaultRecovery` [3](#0-2) .
- `_transferDefaultRecovery` decrements `defaultRecoveryReserve` and calls `underlyingToken.safeTransfer` — it never verifies the reserve accounting covers this claim class [4](#0-3) .
- `collectWithdrawFunds` post-default decreases `pendingWithdraws` and pulls underlying into the strategy, but never segregates funding for post-default claims from the recovery reserve [5](#0-4) .
- Meanwhile defaulted-epoch claimants (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) and the `defaultRecoveryPrice`-based payouts depend on `defaultRecoveryReserve` staying intact [6](#0-5) .

### Impact Explanation
Broken invariant: one receipt, one payout; donation/reserve isolation. An unprivileged KYC'd lender can, right after `finalizeDefault`, deposit into the CDO, call `requestWithdraw`, and immediately `claimWithdrawRequest`. The claim is paid at par out of underlying reserved for defaulted-epoch receipts. Recovery claimants whose basis was priced at `defaultRecoveryPrice` then find `defaultRecoveryReserve` (accounting) or the token balance insufficient: `_transferDefaultRecovery`/`safeTransfer` reverts, permanently freezing their recovery, or the attacker simply walks away with reserve funds up to the reserve size. Quantified loss: up to `min(attacker deposit size, defaultRecoveryReserve)` stolen/frozen.

### Likelihood Explanation
Requirements are all satisfiable by an unprivileged user in the "finalized default" phase: post-default deposits/requests are explicitly kept working by design (the code preserves "request/claim UX after default"), and no guard ties a post-default claim to borrower funding. The attacker only needs the CDO's deposit/withdraw paths to be open post-default (`postDefaultRequests` flow exists precisely for that).

### Recommendation
- Do not pay post-default claims from `defaultRecoveryReserve` accounting; introduce a separate funded counter (e.g., `postDefaultFunded`) that `collectWithdrawFunds` increments when it sources post-default receipts, and gate `_claimPostDefaultWithdrawRequest` on it.
- Alternatively, keep the same epoch-wait gating used for normal receipts (`epochNumber <= lastWithdrawRequest` style) so post-default claims are only payable after a funding round.
- In `_transferDefaultRecovery`, cap each claim at its proportional share of the remaining reserve rather than paying par.

### Proof of Concept
Foundry fork scenario (sketch):

```solidity
// setup: epoch running, borrower defaults, owner calls
// cdoEpoch.finalizeDefault(recovered, recoverySource)
// => defaultRecoveryReserve = R, defaultRecoveryPrice < 1e18, pending claims exist

address attacker = makeAddr("attacker");
deal(underlying, attacker, ATTACK);

vm.startPrank(attacker);
IERC20Detailed(underlying).approve(address(idleCDO), ATTACK);
idleCDO.depositAA(ATTACK);          // or whichever tranche/entry is open post-default
cdoEpoch.requestWithdraw(0, address(AAtranche)); // becomes postDefaultRequests[attacker]
cdoEpoch.claimWithdrawRequest();   // pays ATTACK 1:1 via _transferDefaultRecovery
vm.stopPrank();

// attacker received ATTACK from the recovery reserve before borrower funded anything
assertEq(IERC20Detailed(underlying).balanceOf(attacker), ATTACK);
// honest defaulted claimant now reverts or is underpaid:
// cdoEpoch.claimWithdrawRequest() by victim -> defaultRecoveryReserve underflow / safeTransfer revert
```

No privileged misbehavior required: owner/manager act honestly; the flaw is that unfunded post-default receipts are settled against the isolated recovery reserve.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];

    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }
