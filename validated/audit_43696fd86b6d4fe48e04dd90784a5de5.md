### Title
Instant-withdraw receipts are priced pre-loss and must be fully funded before `stopEpoch`, letting users exit at par ahead of a realized loss - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The external report describes a user front-running a loss-locking transaction to redeem at the pre-loss exchange rate while peers absorb the impairment. The direct analog exists in `IdleCDOEpochVariant`: instant-withdraw requests are fixed at the current (pre-loss) tranche price in `requestWithdraw`, and `stopEpoch`/`stopEpochWithDuration` cannot execute while instant withdrawals are pending (`_pendingInstant() != 0` reverts). A loss applied via `stopEpochWithDuration(_lossAmount)` is split only between active LPs and pending *normal* receipts (`previewLossAdjustedWithdrawFunds`, `lossRecoveryPriceByEpoch`, BB-first waterfall), so instant withdrawers escape the haircut entirely and the loss is concentrated on everyone else.

### Finding Description
- In `requestWithdraw` (`IdleCDOEpochVariant.sol:739-791`), when the APR dropped by more than `instantWithdrawAprDelta`, the request is routed to `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` where `_underlyings` is computed at the current tranche price (`_trancheToUnderlyings`, L756/L815-817), and the user's tranche tokens are burned at that pre-loss value via `_withdrawOps`.
- `_stopEpoch` reverts while `_pendingInstant() != 0` (L343-345). Therefore the honest manager must call `getInstantWithdrawFunds` (L558-573), which pulls the full receipt amount from the borrower and marks `allowInstantWithdraw = true`, before any `stopEpoch`/`stopEpochWithDuration` can run.
- When a partial loss is later realized through `stopEpochWithDuration` (L520-530), `previewLossAdjustedWithdrawFunds` (`IdleCreditVault.sol:440-460`) splits the loss only across `activeBasis + pendingBasis` (normal receipts), and `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch` (L411-430) to haircut queued receipts. Already-funded instant receipts are absent from both bases and pay out 1:1 through `_transferFundedClaim`.
- A lender who anticipates the loss (borrower distress is observable; the loss-bearing `stopEpochWithDuration` and the preceding `getInstantWithdrawFunds` are public mempool transactions, and the instant request can be submitted any time during the preceding buffer/running phase while withdraw requests are allowed) requests an instant withdraw at the pre-loss price, gets funded at par, and exits. Remaining LPs and normal receipt holders absorb the entire `_lossAmount`.

Concrete numbers mirroring the report: NAV = 1,000,000, two users with 100,000 each. Alice instant-withdraws 100,000 funded at par by `getInstantWithdrawFunds`. Manager then calls `stopEpochWithDuration` with `_lossAmount = 500,000`; Alice's claim is already outside the basis, so the 900,000 remaining basis absorbs the full loss (~4/9 effective price for Bob's pending receipt), exactly the report's asymmetry.

### Impact Explanation
Direct loss transfer: users who exit via instant withdrawal before the loss crystallizes receive par value, while identical-position peers receive the haircut. The broken invariant is fair loss socialization — the loss waterfall (`previewLossAdjustedWithdrawFunds` + BB-first `_updateAccounting`) is bypassed for a privileged-by-timing class of claimants that the epoch machine is forced to pay out first. Quantified loss equals the escaping amount times the post-loss discount (55,556 tokens in the 1,000,000/500,000-loss example).

### Likelihood Explanation
Medium-low, gated by design conditions: instant mode only activates when the manager lowered APR by more than `instantWithdrawAprDelta` at a prior stop, the borrower must remain liquid enough to fund instant receipts (a full default reverts `getInstantWithdrawFunds` and haircuts instant receipts via `defaultRecoveryPrice` / `_claimDefaultedInstantWithdrawRequest`), and the attacker must foresee the partial loss. The realistic scenario is a partial write-off/underpayment (`stopEpochWithDuration` with `_lossAmount`, or write-off via `IdleCreditVaultWriteOffEscrow`) where the borrower still repays enough to cover instant claims — precisely the case where normal receipts get `lossRecoveryPriceByEpoch` haircuts but instant claims do not.

### Recommendation
- Include funded-but-unclaimed instant receipts in the loss basis of `previewLossAdjustedWithdrawFunds`, or apply `lossRecoveryPriceByEpoch`/`defaultRecoveryPrice` to instant claims in the loss epoch.
- Alternatively, allow `stopEpoch` to proceed with `pendingInstantWithdraws != 0` by haircutting them pro rata instead of forcing full pre-loss funding.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `testStopEpochWithDurationLossUsesBBFirstWaterfall` and `testClaimWithdrawRequestWithInstantDefault` in `test/foundry/IdleCreditVault.t.sol:3777` and `:5974`):

```solidity
// Setup: depositAA for attacker and victim, depositBB for buffer
idleCDO.depositAA(100_000e18); // attacker
_depositWithUser(victim, 100_000e18, true);

// Epoch 0: stop with lower APR so instant mode activates
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

// Buffer: attacker requests instant withdraw at pre-loss price
uint256 attackerBal = IERC20(AAtranche).balanceOf(address(this));
uint256 instantAmt = cdoEpoch.requestWithdraw(attackerBal, address(AAtranche));
// victim requests a normal withdraw in same window
vm.prank(victim);
uint256 victimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

// Epoch 1 runs; after instantWithdrawDeadline manager funds instant claims
_startEpochAndCheckPrices(1);
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
deal(defaultUnderlying, borrower, instantAmt);
vm.prank(borrower);
underlying.approve(address(cdoEpoch), instantAmt);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();
cdoEpoch.claimInstantWithdrawRequest(); // attacker paid 1:1 at pre-loss price

// Manager realizes a loss at stopEpochWithDuration
vm.warp(cdoEpoch.epochEndDate() + 1);
uint256 loss = cdoEpoch.getContractValue() / 2;
// borrower repays only interest + loss-adjusted pending basis
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);
vm.prank(borrower);
underlying.approve(address(cdoEpoch), type(uint256).max);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, 0, duration, loss);

// Assert: attacker received ~instantAmt (par); victim's claim is haircut
// by lossRecoveryPriceByEpoch[epoch] < RECOVERY_FULL
assertLt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), RECOVERY_FULL);
```

Uncertainty: whether `requestWithdraw` is callable while `isEpochRunning` (no explicit flag check at L741-744, and the withdraw-request allow flags may be cleared at `startEpoch`); if requests are only possible during the buffer, the attack window narrows to the buffer before the loss epoch, which still suffices since the instant request only needs to precede `getInstantWithdrawFunds`, not the loss tx itself.
