### Title
Mid-epoch depositor can lock a full-epoch interest receipt via immediate `requestWithdraw`, stealing unearned yield from other LPs - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The Lucky-13 report is a "computed time difference" bug: a value is derived from a duration measurement that does not reflect the real elapsed exposure. The exact analog exists in `IdleCDOEpochVariant`: `depositDuringEpoch` prices a mid-epoch depositor's shares using *remaining* epoch time, but `requestWithdraw` then prices that same depositor's withdraw receipt using the *full* epoch duration. An unprivileged KYC'd lender can deposit late in a running epoch, immediately request a withdrawal, and receive a receipt that pays a pro-rata share of the entire epoch's tranche interest, even though the discounted mint only charged them for the residual time.

### Finding Description
`depositDuringEpoch` mints tranche tokens at a discount so the depositor ends the epoch with `amount + trancheInterest`, where `trancheInterest` is explicitly prorated by `(remaining + buffer) / (epochDuration + buffer)` — i.e., the deposit only earns for the time actually remaining [1](#0-0) . The minted share count is `(amount + trancheInterest) * trancheSupply / expectedFinal`, so at current `price ≈ lastNAV/supply` the position's underlying value is roughly `amount * (1 + r_remaining)`.

`requestWithdraw` then calls `_calcInterestWithdrawRequest`, which computes `totInterest = _calcInterest(_managedContractValue()) * epochDuration / (epochDuration + buffer)` — the interest for the **whole** epoch duration — and credits the requester `_amount * totTrancheInterest / trancheNAV` on top of their principal [2](#0-1) . There is no remaining-time scaling and no check that the position was held for the epoch. The receipt `principal + interest - fees` is then registered as `pendingWithdraws` in `IdleCreditVault.requestWithdraw`, which the borrower must fully fund at `stopEpoch` [3](#0-2) .

So an attacker holding the position for e.g. the last 1% of a 30-day epoch receives approximately `amount * (1 + r_full)` instead of `amount * (1 + r_full/100)`. The overstated interest is paid out of the epoch's `expectedEpochInterest` pool funded by the borrower, directly diluting the interest of honest AA/BB holders and other pending receipts; if enough value is cycled this way, `stopEpoch` is underfunded relative to claims, shifting loss onto the remaining LPs via the normal waterfall.

Broken invariant: fair mint/burn — the withdraw receipt is denominated in full-epoch interest while the mint only paid for residual-time interest. Existing guards don't stop it: `depositDuringEpoch` only blocks AYS/programmable/zero-supply cases [4](#0-3) , and `requestWithdraw` has no minimum-holding-period or elapsed-time check, only the `allowXXWithdrawRequest` and `isWalletAllowed` flags [5](#0-4) .

### Impact Explanation
Direct theft of yield / LP insolvency. Quantified: depositing `D` at fraction `f` of epoch elapsed yields excess interest of roughly `D * trancheRate * (1 - f) * (1 + small)` per cycle. On a 10% APR, 30-day epoch with deposits enabled at 99% elapsed, a 1M-USDC attacker locks ~`1M * 0.10 * (30/365) ≈ 8,200` USDC of interest for ~7 hours of exposure; the fair amount is ~82 USDC. Repeatable every epoch and per-account.

### Likelihood Explanation
Requires a supported configuration: `isDepositDuringEpochDisabled == false` plus `allowAAWithdrawRequest`/`allowBBWithdrawRequest` enabled and a non-programmable, non-AYS vault — all owner-set flags for features the codebase explicitly supports and tests (e.g. `testDepositDuringEpochNumericalAA` enables mid-epoch deposits mid-epoch [6](#0-5) ). The attacker is an ordinary KYC'd lender with no privileged role. Note uncertainty: whether protocol operators in practice enable both flags simultaneously is a deployment question I could not verify from the repo alone.

### Recommendation
Scale `_calcInterestWithdrawRequest`'s interest by the fraction of the epoch the underlying position actually earned, consistent with `depositDuringEpoch` — e.g., track per-position effective entry time or compute withdraw interest as `totTrancheInterest * (epochEndDate - requestTime + buffer) / (epochDuration + buffer)` for positions minted mid-epoch. Simpler and safer: disallow `requestWithdraw` for tranche tokens minted via `depositDuringEpoch` in the same epoch (store per-user `lastDepositEpoch`/block and gate on it), or disallow mid-epoch deposits entirely while withdraw requests are enabled.

### Proof of Concept
Foundry fork PoC outline (based on `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// Setup: seed AA and BB deposits (e.g. 1000e6 each), setEpochParams(30 days, 0),
// setAprs(10e18, 10e18), disable AYS, enable isDepositDuringEpochDisabled=false
// and allowAAWithdrawRequest=true. Start epoch via manager.startEpoch.

// 1. Warp to epochEndDate - 1 day (97% elapsed).
vm.warp(cdoEpoch.epochEndDate() - 1 days);

// 2. Attacker (KYC'd EOA) deposits D = 1_000_000e6 via depositDuringEpoch(AA).
//    minted is sized for ~1 day of interest (~274 USDC), not full epoch.
uint256 minted = cdoEpoch.depositDuringEpoch(1_000_000e6, address(AAtranche));

// 3. Immediately requestWithdraw(minted, AA) in the same/next block.
uint256 receipt = cdoEpoch.requestWithdraw(minted, address(AAtranche));
//    receipt ≈ D + D * trancheRate(epochDuration) — full-epoch interest share.

// 4. Manager stopEpoch(apr, fundsForPendingWithdraws); epochNumber++.
// 5. claimWithdrawRequest pays the inflated receipt.
// Assert: attacker profit ≈ D * 10% * 30/365 (~8.2k) vs fair ~274
// and honest holders' claimable NAV drops correspondingly.
```

  function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
  }

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
