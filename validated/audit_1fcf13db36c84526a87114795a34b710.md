### Title
`validate_tenure_change_payload` accepts a second, conflicting tenure-start block because it checks `get_last_globally_accepted_block` instead of `get_last_signed_block` - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
The `DuplicateBlockFound` guard in `SortitionsView::validate_tenure_change_payload` is supposed to stop a signer from approving a second tenure-change ("first block of tenure") proposal once it has already committed to one for the same `consensus_hash`. Instead of checking whether the signer has *signed* a block in that tenure, it checks whether one has been *globally accepted*, which is a strictly later and independently-timed condition.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` performs its uniqueness check as: [1](#0-0) 

The code comment and log message say "we've already signed a block in this tenure," but the actual query is `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which only returns `Some` once the block has reached the globally-accepted state (i.e., after the signer set/coordinator has observed threshold agreement and recorded it in `signerdb`). It does not reflect the local signer's own `signed_self`/`signed_group` state on a block it has already produced a signature for. `signerdb.rs` maintains a distinct accessor, `get_last_signed_block`, precisely because "signed" and "globally accepted" are different, non-synchronous states.

Call path: `SortitionsView::check_proposal` (stacks-signer/src/chainstate/v1.rs, around line 319) dispatches to `validate_tenure_change_payload` whenever `block.get_tenure_change_tx_payload()` is `Some`. If a miner (attacker with one winning slot) presents a second tenure-change block B2 for the same `consensus_hash` immediately after the signer has locally/group-signed B1 for that tenure — but before B1's global-acceptance record is written to `signerdb` — the `get_last_globally_accepted_block` lookup returns `None`, the guard is skipped, and `Ok(())` is returned. The signer then proceeds to sign B2, producing two signatures for two distinct tenure-start blocks at the same `(tenure consensus_hash, height)`.

I was not able to fully verify from the available index whether some other, independent guard (e.g., a general per-height/per-hash conflicting-signature check invoked elsewhere in the signing pipeline, such as in `stacks-signer/src/v0/signer.rs`) would separately catch and reject B2 before a signature is emitted; this would need to be confirmed by reading the full sign path in a live checkout, since the indexed context only exposed the presence of `get_last_signed_block` in `signerdb.rs` without letting me inspect its callers/definition body or the full `Signer::sign`-adjacent logic in `v0/signer.rs`.

### Impact Explanation
If no other check intercepts it, this breaks block **uniqueness**: the same signer produces valid signatures for two conflicting tenure-start blocks at the same tenure/height, which is a chain-safety violation (Critical) — it can contribute to two divergent block sets both carrying this signer's weight, undermining the assumption that each signer commits to at most one block per height.

### Likelihood Explanation
Preconditions: (1) the signer has already signed B1 for a tenure but B1 has not yet reached the `GloballyAccepted` state in `signerdb` (a normal, non-adversarial timing window that occurs on every tenure start while signatures are still being aggregated), and (2) the attacker (a single winning miner slot) crafts and gossips a second tenure-change block B2 referencing the same `consensus_hash`/parent tenure before B1's global acceptance is recorded. This requires only miner-slot access and standard proposal gossip — no privileged role, no majority of signers, no auth token — and is repeatable every tenure. The window is race-dependent (bounded by however long it takes the signer network to reach and record global acceptance), so it is a timing-sensitive but realistically exploitable condition, not merely theoretical, given it directly matches the difference between two accessor functions that already coexist in the same `SignerDb` module.

### Recommendation
Change the guard in `validate_tenure_change_payload` (stacks-signer/src/chainstate/v1.rs, ~line 505) to query `signer_db.get_last_signed_block(&block.header.consensus_hash)` (or equivalent "have I produced any signature in this tenure" check covering `signed_self`/`signed_group` states) rather than `get_last_globally_accepted_block`, so the uniqueness check triggers as soon as this signer has committed a signature to any block in the tenure, not only after global consensus is externally observed.

### Proof of Concept
Rust test plan (in `stacks-signer/src/chainstate/tests/v1.rs` or an equivalent unit test harness for `SortitionsView`):
1. Construct a `SignerDb` and insert block B1 for `consensus_hash = CH`, marking it `signed_self` (and/or `signed_group`) but explicitly NOT `GloballyAccepted`.
2. Assert `signer_db.get_last_signed_block(&CH)` returns `Some(B1)` while `signer_db.get_last_globally_accepted_block(&CH)` returns `None` — establishing the broken equality.
3. Build a `SortitionsView` with `cur_sortition.consensus_hash = CH`, and construct B2, a distinct `NakamotoBlock` with a `TenureChangePayload` for the same `CH`/parent tenure, differing in miner signature/hash from B1.
4. Call `check_proposal(..., &B2, ...)` and assert it returns `Ok(())` (reproducing the bug) instead of `Err(RejectReason::DuplicateBlockFound)`.
5. After applying the fix (swap to `get_last_signed_block`), rerun the same test and assert `check_proposal` now returns `Err(RejectReason::DuplicateBlockFound)` for B2.
