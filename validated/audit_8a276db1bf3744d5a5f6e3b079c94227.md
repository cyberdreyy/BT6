### Title
Fail-open APR setter before `idleCDO` is linked lets anyone inflate vault interest - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr` skips its caller check entirely while `idleCDO == address(0)` — the same fail-open-on-unset-config bug class as CVE-2026-67349's `adminAuthMiddleware` bypass when `ADMIN_TOKEN` is unset. Between `initialize()` and the owner's `setWhitelistedCDO()` call, any EOA can call `setApr`/`setAprs`/`setAprsWithBuffer` and push the fixed APR up to `maxApr` (default `DEFAULT_MAX_APR = 20e18`), minting attacker-favorable interest terms before the pool ever goes live.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol:225-235`:

```solidity
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
```

The only guard on `lastApr` in this window is `maxApr`. `setAprs` and `setAprsWithBuffer` (lines 206-220) are also callable by anyone in this window and additionally let the attacker set `unscaledApr` arbitrarily, which flips the vault out of the APR0 accounting path (`unscaledApr == 0` is required for `apr0` flows in `requestWithdraw`/`prepareStopEpochWithApr0`, lines 285 and 506).

Deployment flow (`IdleCreditVaultFactory`) creates the strategy via `initialize()` and links the CDO via `setWhitelistedCDO` — these are separate transactions, so a nonzero window exists on every deployment, and it persists if the owner ever rotates `idleCDO` (no way to unset, but upgrade/relink flows re-open it).

### Impact Explanation
Once the pool starts (`startEpoch`), `IdleCDOEpochVariant` books `expectedEpochInterest` from the vault's `lastApr` scaled over epoch + buffer duration. An attacker who pre-seeded `lastApr = 20e18` (scaled ≈ 2000%/yr) and deposited into AA/BB tranches receives tranche tokens whose price embeds that inflated interest:

- Honest borrower overpays: at `stopEpoch`, the borrower owes principal + `expectedEpochInterest`; the inflated interest flows to tranche holders — i.e., the attacker — at NAV-dilutive rates. Direct value transfer from borrower to attacker LP.
- If the borrower cannot cover the inflated obligation, `stopEpoch` underfunds → `_handleBorrowerDefault`/`finalizeDefaultRecovery` socializes the shortfall across all LPs (insolvency path). Either way, real funds move based on an APR no authorized party ever set.
- Setting `unscaledApr != 0` in an APR0-mode vault also breaks `_requestWithdrawApr0`/`prepareStopEpochWithApr0` accounting assumptions, which can wedge withdraw claims (revert on `NotAllowed` at line 507) — temporary freezing of pending withdraws.

### Likelihood Explanation
- Requires no privileges: the attacker is any EOA; the window is between `initialize` and `setWhitelistedCDO` (or any relink). Factory deployments that don't bundle the link in one tx are exposed.
- Cost is only the deposit capital; `maxApr` is the only bound, and `setMaxApr` is owner-only but defaults to `20e18`.
- The payout depends on the borrower actually repaying at the inflated rate, which caps realized theft at borrower solvency — hence medium rather than critical, mirroring the source CVE's 6.0.

### Recommendation
In `setApr`, remove the fail-open branch: revert when `idleCDO == address(0)` unless `msg.sender == owner()` or `manager`, or gate all three APR setters behind an explicit setup flag cleared when `setWhitelistedCDO` is called. Alternatively set `idleCDO` inside `initialize`/factory atomically so the unauthenticated window never exists.

### Proof of Concept
Foundry-style sketch (fork or local deploy of `IdleCreditVault` + `IdleCDOEpochVariant`):

```solidity
// 1. Owner deploys + initializes strategy (idleCDO still address(0))
IdleCreditVault vault = new IdleCreditVault();
vault.initialize(USDC, owner, manager, borrower, "B", 5e18); // intended APR 5e18 scaled

// 2. Attacker EOA, before owner calls setWhitelistedCDO:
vm.prank(attacker);
vault.setAprs(20e18, 20e18); // succeeds: check skipped, capped only by maxApr

// 3. Owner finishes wiring
vm.prank(owner);
vault.setWhitelistedCDO(address(cdoEpoch));

// 4. Attacker deposits into AA tranche during buffer phase
vm.prank(attacker);
cdoEpoch.depositAA(1_000_000e6);

// 5. Owner/manager starts epoch; expectedEpochInterest now reflects APR 20e18
// 6. Borrower repays principal + inflated interest at stopEpoch;
//    attacker claims withdraw request with inflated tranche price
//    => attacker extracts interest far above agreed terms (borrower overpayment),
//       or triggers default loss socialization if borrower can't pay.

assertGt(vault.lastApr(), 5e18); // APR was never authorized above 5e18
```

The assertion that `setAprs` succeeds while `idleCDO == address(0)` is the core of the PoC; the epoch flow demonstrates the fund impact.
