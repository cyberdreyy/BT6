### Title
Unbounded scan over dead/unrooted forks in `get_confirmed_signatures_for_address2` allows a single `getSignaturesForAddress` RPC call to consume excessive CPU/time - (File: `ledger/src/blockstore.rs`)

### Summary
`Blockstore::get_confirmed_signatures_for_address2`, which backs the `getSignaturesForAddress` JSON-RPC method, contains a `while` loop that walks the persistent `address_signatures_cf` index backwards to accumulate `limit` results. The loop's termination is coupled to *finding `limit` valid entries*, not to the number of index entries scanned. Any entry whose slot is neither rooted nor an ancestor of the caller-supplied `highest_slot` is silently skipped (not counted toward `limit`) but the iterator still advances, so the scan can walk through the entire address history back to `first_available_block` without ever satisfying the loop's exit condition, all within a single unprivileged RPC call.

### Finding Description
`get_confirmed_signatures_for_address2` first computes `confirmed_unrooted_slots`, the set of slots between `max_root` and the caller's `highest_slot` on the *current* fork: [1](#0-0) 

It then iterates the `address_signatures_cf` column family (keyed by `(address, slot, transaction_index, signature)`) in reverse from the starting slot: [2](#0-1) 

The loop condition is `while address_signatures.len() < limit`. Inside, for every entry belonging to the queried `address`, the code only pushes the entry into `address_signatures` — and thus only makes progress toward satisfying the loop condition — if `self.is_root(slot) || confirmed_unrooted_slots.contains(&slot)`. If the slot is neither rooted nor a confirmed ancestor of `highest_slot` (e.g., because the transaction landed on an abandoned/duplicate fork, or on a stale bank snapshot no longer connected to the current heaviest fork), the entry is skipped via `continue`, but the iterator still advances one step. Because `address_signatures_cf` entries for such transactions are written whenever `write_transaction_status` runs during block replay (not just for the canonical fork) and are not necessarily purged the moment a fork becomes non-canonical, this index can retain a large number of "dead" entries for an address that transacted heavily across many forks over the ledger's retained history.

The only bounds on the scan are:
- `slot < lowest_slot` (i.e., `first_available_block`, which for a validator retaining full transaction history can be the genesis of the retained ledger), and
- `key_address != address` (i.e., the iterator has exhausted all entries for that address).

Neither of these bounds is related to `limit`. Consequently, a single call with a popular/heavily-used address and a `highest_slot` that is far ahead of (or on a different fork from) most of that address's historical activity can force the scan to walk through the address's entire retained history of dead-fork entries before it can gather `limit` valid results (or exhaust the index), all inside one synchronous RPC invocation. This is the direct analog of the `_removeNft` unbounded-loop griefing pattern in the report: an inexpensive, unprivileged action (ordinary transaction activity that lands on forks that are later abandoned — a normal, frequent occurrence in consensus, not even requiring malice) inflates a persisted collection, and a completely unprivileged read/removal-style operation must linearly scan that collection without an early, cost-bounded exit.

### Impact Explanation
`getSignaturesForAddress` is a permissionless, commonly exposed JSON-RPC method. A single call against it can trigger a scan whose cost is proportional to the total number of `address_signatures_cf` entries for the given address across all forks retained in the ledger, not to `limit` or to any request-scoped bound. On an RPC node with a long transaction-history retention window and a heavily used address (e.g., a popular program or hot wallet), this can consume disproportionate CPU and I/O for a single, low-rate request, degrading the node's ability to serve other RPC/JSON-RPC clients — a legitimate availability impact matching "unbounded cost for a single low-rate call."

### Likelihood Explanation
Likelihood is moderate to high on any node that: (a) serves `getSignaturesForAddress` (the "full" RPC API, not the minimal/accounts-only subset), (b) retains long transaction history (`--limit-ledger-size` set high, or the default long retention), and (c) has processed addresses with substantial activity that included dead/duplicate forks. Because fork switches are a routine part of Solana consensus (and can be induced by any validator's own natural block production/leader rotation, not just an attacker), the "dead entries" precondition can arise organically over time without any adversarial action — this mirrors the C4 judge's comment that the underlying report class "doesn't need a malicious actor to happen... can happen by simply being very successful."

### Recommendation
Bound the scan independent of `limit`:
- Track the number of index entries examined (not just matched) and cap it (e.g., a `MAX_SCANNED_ENTRIES` constant), returning a partial/error result or falling back to `bigtable_ledger_storage` when the cap is hit.
- Alternatively, avoid writing (or promptly prune) `address_signatures_cf` entries for slots that are marked dead/pruned once a fork is abandoned, so the reverse iterator never has to walk through large runs of permanently-unrootable entries.
- Add per-request time-budget checks (similar to the existing `Measure` timers already present in this function) that abort the scan and return a clear error rather than blocking the RPC thread indefinitely.

### Proof of Concept
Conceptual reproduction (cannot be executed without a live cluster/ledger, but the code path is deterministic):
1. Configure a validator/RPC node with `--enable-rpc-transaction-history` and a large ledger retention window (`--limit-ledger-size` set high or default).
2. Drive sustained transaction activity from/to a single address across many slots, ensuring that some fraction of those slots end up on forks that are later abandoned (this occurs naturally under normal leader rotation and occasional short forks; no special exploit is required, though an adversary could accelerate it by intentionally causing forks near their own leader slots).
3. Let the ledger accumulate a large number of `address_signatures_cf` entries for that address that fall outside `confirmed_unrooted_slots` for a subsequent `highest_slot`.
4. Issue a single `getSignaturesForAddress` RPC call for that address with a small `limit` (e.g., `limit: 1`) and a `before`/`until` window, or simply query without them so `highest_slot` is far from the dead-fork slots.
5. Observe that `get_confirmed_signatures_for_address2`'s `while` loop iterates through the dead entries (bounded only by `first_available_block`), producing latency and CPU cost far exceeding what the requested `limit` would suggest, all triggered by one RPC call as shown by the existing internal `address_signatures_iter_timer` instrumentation: [3](#0-2) .
