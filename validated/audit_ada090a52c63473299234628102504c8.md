## Finding

### Title
`BlockRejection` signatures do not commit to `reason_code`/`response_data`, allowing rejection-reason forgery under a genuine signer signature - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection::hash()` computes the value that gets signed and later re-verified for a signer's block rejection. That hash commits only to `signer_signature_hash` and `chain_id` — not to `reason`, `reason_code`, or any field of `response_data` (`reject_reason`, `tenure_extend_timestamp`, `tenure_extend_read_count_timestamp`, `failed_txid`). Yet those excluded fields are exactly what downstream logic parses and acts on. This is the same bug class as the xmldom advisory: the byte range that is authenticated/verified diverges from the byte range that is subsequently interpreted, so a party who never possesses the signer's key can still produce a `BlockRejection` object that verifies successfully but carries attacker-chosen semantic content.

### Finding Description
`BlockRejection::hash()`: [1](#0-0) 

only feeds `signer_signature_hash` (plus the `chain_id` via the structured-data domain) into the signed digest. The struct itself carries much more state that is deserialized and consumed: [2](#0-1) 

and `verify()`/`recover_public_key()` re-derive the same narrow hash to check the signature: [3](#0-2) 

Because `reason_code: RejectCode` and `response_data: BlockResponseData` (containing `RejectReason`, including the attacker-shaped variant `RejectReason::ConsensusHashMismatch { expected, actual }` with two fully-attacker-controlled `ConsensusHash` fields) are outside the signed digest, anyone holding one authentic `BlockRejection` bytestring for a given `signer_signature_hash`/`chain_id` pair can splice in a different `reason`, `reason_code`, or `response_data` (different `RejectReason` variant, different `failed_txid`, different `tenure_extend_timestamp`) and the object will still `verify()` and `recover_public_key()` to the original honest signer. The consensus_serialize/consensus_deserialize round-trip for `BlockRejection` treats all these fields as ordinary struct members with no cryptographic binding to the signature: [4](#0-3) 

This directly parallels the report's bug class: the "serializer" (the signer) intends one semantic meaning (i.e., "I reject this block because of X"), but a downstream verifier only checks a narrower invariant (the block hash + chain id), so a forged/relayed rendering with a different `X` is misinterpreted as authentic. Consumers such as `signerdb::add_block_rejection_signer_addr`, which records rejections keyed by `RejectReasonPrefix`, and `should_reevaluate_reject_reason` / `check_block_against_signer_db_state` in `stacks-signer/src/v0/signer.rs` (referenced by `docs/signer-flows.md`), treat `reason_code`/`response_data.reject_reason` as trustworthy signer-attributed data once `verify()`/`recover_public_key()` succeeds: [5](#0-4) 

### Impact Explanation
An attacker who intercepts/relays a signer's genuine `BlockRejection` for block `H` can rewrite `reason_code`/`response_data.reject_reason` (or fabricate `ConsensusHashMismatch{expected, actual}` values) while the signature and `verify()`/`recover_public_key()` still attribute the forged message to the honest signer. This can:
- Miscategorize a rejection under `RejectReasonPrefix` used by `add_block_rejection_signer_addr`, corrupting the tallies used to decide whether to re-evaluate/re-submit a block.
- Feed a fabricated `expected`/`actual` `ConsensusHash` pair, attributed to an honest signer, into any logic that consumes `RejectReason::ConsensusHashMismatch` for re-evaluation decisions, potentially steering the local signer's `should_reevaluate_reject_reason`/`should_reevaluate_block` state machine.

This maps to the High-impact bucket: a signer can be pushed into an incorrect view of another signer's rejection reason (a form of "acting on a stale/incorrect state"), which can wedge or misdirect the local decision of whether to re-validate/resubmit a proposal.

### Likelihood Explanation
Reachable by any network-level relay/gossip participant that observes a legitimate `BlockRejection` broadcast (no majority of signers, no private key, and no auth token required) — it only requires re-serializing an already-seen valid rejection with a different `reason_code`/`response_data`. Because the message travels over StackerDB chunks, the *chunk* itself is separately signed by the writer's slot key, which limits pure on-wire tampering to entities that also control that slot or can otherwise reintroduce the doctored `BlockRejection` bytes into a code path that only checks `BlockRejection::verify()`/`recover_public_key()` (rather than the chunk signature) for attribution. I could not fully confirm within the available context whether any consumer verifies `BlockRejection.signature` independently of the StackerDB chunk signature (e.g., replay through pending-response queues, cross-signer forwarding, or event-observer paths) — this would need to be checked in a full Devin session to establish the exact reachable trigger surface and thus the precise likelihood/severity.

### Recommendation
Include `reason_code` and all `response_data` fields (or a canonical hash over them) inside `BlockRejection::hash()`'s signed digest, so that any semantic content interpreted downstream is cryptographically bound to the signer's actual attestation, closing the gap between "what is verified" and "what is interpreted."

### Proof of Concept
1. Capture (or construct from a real, previously-broadcast) `BlockRejection` object `msg` for block hash `H`, signed by signer `S`, with `reason_code = RejectCode::ValidationFailed(...)` and `response_data.reject_reason = RejectReason::InvalidParentBlock`.
2. Replace `msg.reason_code`, `msg.reason`, and `msg.response_data` with `response_data.reject_reason = RejectReason::ConsensusHashMismatch { expected: <attacker_hash>, actual: <attacker_hash_2> }` (or any other reason), leaving `msg.signer_signature_hash`, `msg.chain_id`, and `msg.signature` untouched.
3. Call `msg.verify(&S_pubkey)` — it returns `Ok(true)` because `hash()` only covers `signer_signature_hash`/`chain_id`.
4. Feed `msg` into `SignerDb::add_block_rejection_signer_addr(&H, &S_addr, RejectReasonPrefix::from(&msg.reason_code))` (via `stacks-signer/src/signerdb.rs`) — the forged reason is recorded as if `S` genuinely reported it. [6](#0-5)

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

        write_next(fd, &self.reason.as_bytes().to_vec())?;
        write_next(fd, &self.reason_code)?;
        write_next(fd, &self.signer_signature_hash)?;
        write_next(fd, &self.chain_id)?;
        write_next(fd, &self.signature)?;
        write_next(fd, &self.metadata)?;
        write_next(fd, &self.response_data)?;
        Ok(())
    }

    fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<Self, CodecError> {
        let reason_bytes = read_next::<Vec<u8>, _>(fd)?;
        let reason = String::from_utf8(reason_bytes).map_err(|e| {
            CodecError::DeserializeError(format!("Failed to decode reason string: {:?}", e))
        })?;
        let reason_code = read_next::<RejectCode, _>(fd)?;
        let signer_signature_hash = read_next::<Sha512Trunc256Sum, _>(fd)?;
        let chain_id = read_next::<u32, _>(fd)?;
        let signature = read_next::<MessageSignature, _>(fd)?;
        let metadata = read_next::<SignerMessageMetadata, _>(fd)?;
        let response_data = read_next::<BlockResponseData, _>(fd)?;
        Ok(Self {
            reason,
            reason_code,
            signer_signature_hash,
            chain_id,
            signature,
            metadata,
            response_data,
        })
    }
