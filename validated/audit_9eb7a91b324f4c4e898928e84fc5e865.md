### Title
Fee-on-transfer tokens break vault solvency: `depositDuringEpoch` and `_deposit` account for nominal amount, not received amount - (File: contracts/IdleCDOEpochVariant.sol, contracts/IdleCDOCreditVault.sol)

### Summary
The credit vault measures the actually-received token amount only in the buffer-phase `_deposit` (to price minted shares), but every other leg of the deposit flow — the amount forwarded to `IdleCreditVault.deposit`, the strategy tokens minted via `mintStrategyTokens`, the shares minted and the borrower transfer in `depositDuringEpoch` — uses the nominal `_amount`. If the configured pool currency ever enables a transfer fee (e.g., USDT), each deposit leaves the vault short by the fee while liabilities are recorded at full nominal value, progressively draining NAV and eventually rendering tranche positions insolvent.

### Finding Description
Two complementary mismatches exist:

1. **`IdleCDOCreditVault._deposit`** (`contracts/IdleCDOCreditVault.sol:191-212`): shares are minted on the *received* amount (`_contractTokenBalance(_token) - _preBal`, line 206), but `IIdleCDOStrategy(strategy).deposit(_amount)` on line 211 forwards the *nominal* amount. Inside `IdleCreditVault.deposit` (`contracts/strategies/idle/IdleCreditVault.sol`), the strategy executes `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` pulling the full `_amount` out of the CDO, while the CDO only received `_amount - fee` from the depositor. The difference is drawn from the vault's residual balance (other users' funds / buffer liquidity), and strategy tokens minted correspond to the nominal `_amount`, inflating the CDO's claim on the strategy relative to real assets.

2. **`IdleCDOEpochVariant.depositDuringEpoch`** (`contracts/IdleCDOEpochVariant.sol:656-733`): after `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` (line 685), no balance delta is measured. Minted shares are computed from the nominal `_amount + trancheInterest` (line 724), `expectedEpochInterest` is bumped by interest on the nominal amount, `IdleCreditVault(strategy).mintStrategyTokens(_amount)` mints nominal strategy tokens (line 730), and `_transferUnderlyings(_borrower(), _amount)` forwards the full nominal amount to the borrower (line 732) even though only `_amount - fee` arrived. Each mid-epoch deposit therefore books and disburses `fee` more than was collected.

`_skimDonatedAssets()` does not help: it only redirects unsolicited surplus to `feeReceiver`; the shortfall here is a deficit against recorded liabilities, not a donatable surplus.

### Impact Explanation
Insolvency / unfair mint. With a fee-on-transfer underlying of rate `f`, every deposit of `A` mints tranche claims (or inflates the CDO's strategy-token balance) priced on `A` while only `A·(1-f)` is ever received, and in `depositDuringEpoch` a further `A` is pushed to the borrower from vault funds. An unprivileged KYC-passed lender can repeat deposits so the cumulative `A·f` shortfall socializes onto other tranche holders — exhausting BB NAV first and then AA NAV — exactly the loss-waterfall inversion `_updateAccounting` is meant to enforce (BB absorbs losses first, `contracts/IdleCDOCreditVault.sol:330-333`). In the worst case, withdrawals revert because recorded NAV exceeds real token balance — permanent freezing of the deficit portion.

### Likelihood Explanation
The vulnerability requires the configured `token` to charge a transfer fee. The pools are denominated in stablecoins such as USDC/USDT; USDT retains a dormant fee mechanism that can be activated by its issuer, matching the report's USDT 0.5% scenario. No privileged action is needed by the attacker beyond ordinary KYC-gated `depositAA`/`depositBB`/`depositDuringEpoch` calls during buffer or running phases. Likelihood is conditional on the token enabling fees (or a rebasing token being configured), but impact is direct and unprivileged.

### Recommendation
- In `depositDuringEpoch`, measure `received = balanceOf(this) - preBal` after `_transferUnderlyingsFrom` and use `received` for share minting, `_calcInterest`, `mintStrategyTokens` and the borrower transfer.
- In `IdleCDOCreditVault._deposit`, pass the measured received amount (not `_amount`) to `strategy.deposit`.
- Mirror the balance-delta pattern in `IdleCreditVault.deposit`/`mintStrategyTokens` and in `IdleCDOEpochQueue.requestDeposit`, or explicitly document and enforce (e.g., via a token allowlist) that fee-on-transfer/rebasing tokens are unsupported.

### Proof of Concept
Foundry test sketch (deploy vault with a fee-on-transfer ERC20 mock standing in for the pool currency; fee = 1%):

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract FeeToken is ERC20 {
    uint256 public constant FEE_BPS = 100; // 1%
    constructor() ERC20("FeeUSDT","fUSDT") {}
    function mint(address to, uint256 a) external { _mint(to, a); }
    function _transfer(address f, address t, uint256 a) internal override {
        uint256 fee = a * FEE_BPS / 10_000;
        super._transfer(f, t, a - fee);
        _burn(f, fee);
    }
}

contract FeeOnTransferInsolvencyTest is Test {
    // assume: vault = IdleCDOEpochVariant with FeeToken as `token`,
    // strategy = IdleCreditVault, KYC'd attacker, epoch running

    function testDepositDuringEpochDrainsNav() public {
        uint256 navBefore = vault.getContractValue();
        feeToken.mint(attacker, 1000e6);
        vm.startPrank(attacker);
        feeToken.approve(address(vault), 1000e6);
        vault.depositDuringEpoch(1000e6, AA);   // mints shares for ~1000e6 + interest
        vm.stopPrank();
        // vault received 990e6 but minted ~1000e6+int of AA claims
        // and forwarded 1000e6 to borrower from vault balance
        assertLt(vault.getContractValue(), navBefore + 990e6);
        // repeat deposits until lastNAVBB is exhausted -> next _updateAccounting
        // detects nav < lastNAV and reverts Default() / emergency shutdown
    }
}
```

Expected: each iteration mints ~1% more tranche value than assets received; repeated deposits force `_updateAccounting` to observe `nav < lastNAV`, taking a BB-first loss that, once BB is wiped, triggers `revert Default()` / `_emergencyShutdown` — i.e., unprivileged deposits push the pool into loss socialization/insolvency without any borrower default.

Uncertain/not fully verified: `IdleCreditVault.deposit`/`mintStrategyTokens` internals were only inspected via grep counts (line numbers not confirmed), but the pull pattern `safeTransferFrom(msg.sender → strategy, _amount)` with nominal `_amount` is confirmed by the CDO-side call site and is consistent with sibling strategies (e.g., `IdleClearpoolStrategy.deposit`, `contracts/strategies/clearpool/IdleClearpoolStrategy.sol:231-246`).
