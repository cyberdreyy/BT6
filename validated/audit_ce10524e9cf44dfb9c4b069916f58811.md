### Title
Local, per-signer signature "staleness" timeout allows equivocation on two conflicting blocks at the same height/tenure - (File: stacks-signer/src/v0/signer.rs)

### Summary
The pre-commit-to-signature path in `handle_block_pre_commit` guards against a signer double-signing two conflicting blocks at the same Stacks height by consulting `get_signed_conflicts` and refusing to sign while a conflicting signature is "fresh." Freshness is a purely local, per-signer wall-clock measurement (`tenure_last_block_proposal_timeout`) with no verification that the conflicting block has actually become unreachable at the network level. A single miner — who alone decides when (or whether) to submit an assembled 70% signature set to the node — can front-run this timeout: collect (or let signers collect) enough signatures over block `A`, withhold it from the node so it never becomes `GloballyAccepted`, wait for the conflict to go stale in each signer's local view, then get a second, disjoint/overlapping quorum to sign a conflicting block `B` at the same height. Because the staleness clock is local and not network-verified, the same signers who signed `A` are freed to also sign `B` once their personal timer expires, letting both `A` and `B` independently reach the 70% weighted threshold required by `NakamotoBlockHeader::verify_signer_signatures`, which checks only aggregate weight, not liveness/freshness.

### Finding Description
The relevant guard lives in `Signer::handle_block_pre_commit`: [1](#0-0) 

`conflicts` here are computed from `SignerDb::get_signed_conflicts`, which returns every block ever signed (by this signer or "observed group") at or above the proposed height, across all tenures: [2](#0-1) 

The only thing preventing this signer from signing a second, conflicting block at the same height is whether a conflicting signature is both "fresh" (`last_endorsed > freshness_cutoff`) and `conflict_still_blocks` returns true. `conflict_still_blocks`'s own comment states the intent explicitly: [3](#0-2) 

and it returns `true` (still blocking) specifically for an *unconfirmed* sibling at the same height: [4](#0-3) 

However, staleness (`freshness_cutoff`) is evaluated first and is a pure local-clock check: [5](#0-4) 

Once a conflicting signature is older than `tenure_last_block_proposal_timeout`, the freshness gate is bypassed entirely and the signer falls through to a second, weaker check that only asks the node for the *same tenure's* confirmed tip height — it does not ask whether the earlier block `A` has already collected (or could still collect) a full quorum of signatures elsewhere on the network: [6](#0-5) 

Global acceptance of a block is defined purely by the node observing/announcing it (`NewBlock` event) or by `check_latest_block_in_tenure` seeing it as the tenure's processed tip — never by counting signatures independently on the signer side: [7](#0-6) 

This means a miner who withholds pushing an assembled signed block to the node can keep block `A` permanently "not yet globally accepted" from every signer's point of view, even though `A`'s signature set may already satisfy the weighted 70% threshold required by consensus: [8](#0-7) 

Because `verify_signer_signatures` only checks accumulated weight against `compute_voting_weight_threshold`, with no notion of "freshness" or "who changed their mind," any signature ever produced remains a valid, reusable "bearer instrument" (as the code's own commentary acknowledges): [9](#0-8) 

Putting this together: the miner (i) gets/observes a quorum of signatures over `A` but does not submit it, (ii) waits out `tenure_last_block_proposal_timeout` so that each signer's local conflict-freshness view of `A` expires, (iii) proposes a conflicting block `B` at the same height/tenure, letting the same (or an overlapping) set of signers — now believing `A` is stale/dead — sign `B` as well. If the overlap between signers of `A` and `B` is at least 40% of total weight (70% + 70% − 100%), both blocks independently satisfy the 70% signature threshold. The miner, having secretly retained `A`'s complete signature set the whole time, can then choose to submit either `A` or `B` to the network — a single, non-colluding actor unilaterally deciding which of two fully quorum-signed, conflicting blocks becomes canonical. This breaks the "aggregated-weight vs verified-accepts" equality the signer set is meant to guarantee, and is a direct analog of the reported "admin front-running/timing" bug class, with the miner playing the role of the timing-privileged actor.

### Impact Explanation
This is a Critical-class break: it results in a signer set producing two independently, fully quorum-signed *conflicting* blocks at the same height in the same tenure. This is the exact "signer signing a conflicting block" condition called out as Critical impact — it defeats the core safety guarantee of the Nakamoto signer protocol (that only one block per height/tenure can ever gather threshold signatures), and gives a single miner the power to choose after the fact which of two valid histories becomes canonical, entirely through message-timing control rather than through corrupting cryptography or requiring a majority of malicious signers.

### Likelihood Explanation
The attack requires only: (1) control of a single mining slot for one tenure (a normal, permissionless role); (2) the ability to delay submitting the assembled/observed signature set for `A` to the stacks-node past `tenure_last_block_proposal_timeout`; and (3) proposing a second, conflicting block `B` afterward. No signer private keys, no majority of signers, and no protocol-level access are required — only ordinary control over when/whether a miner publishes an assembled block, which is inherent to the miner's role. The `tenure_last_block_proposal_timeout` value is a known, fixed configuration parameter, making the required wait deterministic rather than probabilistic.

### Recommendation
Do not let a signature's "freshness" alone clear a same-height/tenure conflict. Before allowing a signer to sign a new block `B` that conflicts with a previously-signed (but not yet globally accepted) block `A`, require positive proof from the node that `A` is provably dead (e.g., that the burnchain/tenure state has moved past it, as `conflict_still_blocks` already does for the *cross-tenure* case) rather than relying on the passage of a local timer alone for the *same-tenure* recovery path. Alternatively, before permitting the local timeout-based fallback to sign a conflicting block, the signer should verify with peers/StackerDB whether `A` already has (or is close to having) sufficient weight to be considered committed, so that time-based recovery cannot be exploited by a miner who is silently sitting on a completed signature set.

### Proof of Concept
1. Miner proposes block `A` at height `h` in tenure `T`. Enough signers (≥70% weight) pre-commit and sign `A` per `handle_block_pre_commit`'s SIGN branch (`stacks-signer/src/v0/signer.rs:1466-1478`), broadcasting their `BlockAccepted` responses over StackerDB.
2. Miner does not push `A` to its stacks-node (skips/holds `handle_post_block`), so no `NewBlock` event ever fires and `A` never becomes `GloballyAccepted` in any signer's `SignerDb`.
3. Miner waits `tenure_last_block_proposal_timeout` (a known config value) so that, per-signer, `A`'s `last_endorsed` timestamp falls below `freshness_cutoff` in every signer's evaluation (`stacks-signer/src/v0/signer.rs:1393-1421`).
4. Miner proposes block `B` at the same height `h` in tenure `T` (e.g., different transaction set). Each signer runs `handle_block_pre_commit`; the fresh-conflict guard no longer fires because `A` is stale, and the second same-tenure check only verifies the node's tenure tip has not advanced past `h` (still true, since `A` was withheld) — so signers proceed to sign `B` (`stacks-signer/src/v0/signer.rs:1432-1465`).
5. If ≥70% weight signs `B` as well (with sufficient overlap with `A`'s signer set), the miner now holds two independently valid, fully-quorum-signed, conflicting blocks `A` and `B` at height `h`/tenure `T`, and can submit either to the network at will.

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
