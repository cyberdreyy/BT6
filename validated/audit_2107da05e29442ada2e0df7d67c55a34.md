## Title
Malformed/unrecognized signer message in `StackerDBListener::run` kills the whole miner-side signature-aggregation thread instead of skipping the message - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::run` iterates over every `(slot_id, _pk, message)` decoded from a StackerDB event in a single `for` loop [1](#0-0) . If, for a single message in that batch, `self.signer_entries.get(&slot_id)` misses or `StacksPublicKey::from_slice(&signer_entry.signing_key)` fails to parse, the function does a hard `return Err(...)` from inside `run()`'s event loop, exactly the same "one bad item aborts the whole batch" pattern flagged in the external `BulkCreateUnstakes` report.

### Finding Description
`run()` is a `loop { ... }` that never terminates except on explicit shutdown flags or an `Err` return [2](#0-1) . Inside each iteration it processes a whole batch of `messages` decoded from a `StackerDBChunksEvent` [3](#0-2) . The per-message loop looks up `signer_entries` and parses the signer's public key, but instead of `continue`-ing past a bad entry (as every other malformed-input branch in this same function does — see the `continue` used for unrecoverable/mismatched signatures a few lines later at lines 411-426), it returns `Err(NakamotoNodeError::SignerSignatureError(...))`, propagating out of `run()` and terminating the whole listener thread [4](#0-3) .

Once `StackerDBListener::run()` returns an `Err`, the thread that hosts it exits; the `blocks`/`signer_idle_timestamps`/`global_state_evaluator` state it maintains stops being updated for every subsequent tenure and block proposal that the miner is trying to get signed, because `SignerCoordinator::propose_block`/`get_block_status` depends entirely on `StackerDBListenerComms` reading these shared structures [5](#0-4) [6](#0-5) . This mirrors the bug class in the external report precisely: one bad record in a batch triggers a hard stop that prevents processing of everything else (all future signer responses across all future block proposals), rather than being logged and skipped.

### Impact Explanation
This is a liveness wedge: once the listener thread dies, the miner can no longer learn about any future signer pre-commits/signatures/rejections via this channel, effectively stalling block signing for the whole tenure (and likely subsequent tenures, since nothing restarts the listener automatically in the code shown). That matches the "High" impact bucket in the rubric (a component wedged into never processing valid signer responses again).

### Likelihood Explanation
I could **not** conclusively prove that a single, unprivileged signer (a "one-slot" actor) can make `slot_id` miss from `self.signer_entries` or make `signing_key` fail to parse:
- `self.signer_entries` is built once at `StackerDBListener::new()` from the reward set's own `signers()` list, keyed by their natural index [7](#0-6) , and StackerDB slot IDs for the signer contract are assigned 1:1 with reward-set members, so under normal operation every `slot_id` seen in `messages` should already exist in `signer_entries`.
- The `signing_key` bytes come from the reward set itself (chain-derived data), not from the incoming message, so a malicious signer cannot forge this field via a crafted StackerDB write.

I was not able to find a concrete gossip/miner-triggerable path (e.g. reward-cycle rollover race, stale `signer_entries` snapshot vs. a live StackerDB write) that lets an attacker actually hit these two `Err` branches, and I did not find any historical fix/PR reference for this exact code path in the indexed portion of the repo. Given the ask-only/analog-validation rubric's requirement to "map the bug class to the *strongest reachable path*" and "prove root cause with exact file/function support," I can show the code pattern (hard-stop-on-error identical to the reported bug class) but cannot establish attacker reachability with confidence using the tools and index available to me.

### Recommendation
If reachable, change the two `return Err(...)` branches at [1](#0-0)  to `warn!(...); continue;`, consistent with the handling used for other malformed-signer-message cases later in the same loop (invalid/mismatched signatures at lines 411-426), so that one bad or stale slot entry cannot terminate signature aggregation for all future blocks.

### Proof of Concept
Not established — I was unable to confirm within the indexed code a concrete way for an unprivileged signer or miner to cause `self.signer_entries.get(&slot_id)` to miss or `StacksPublicKey::from_slice` to fail against otherwise-valid reward-set data. Given this uncertainty around reachability, and per the "reject on sight" instruction for findings that can't be proven root-caused/reachable, I present this as a code-pattern match to the reported bug class rather than a confirmed exploitable vulnerability.
