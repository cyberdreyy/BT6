### Title
Broken EI/real-user distinction lets an External-Initiator credential trigger arbitrary job runs by integer job ID via `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go], [File: core/web/auth/auth.go])

### Summary
The `/v2/jobs/:ID/runs` route is reachable with only External Initiator (EI) credentials because it is registered under the `userOrEI` group with `auth.AuthenticateExternalInitiator` as an accepted method. `AuthenticateExternalInitiator` unconditionally injects a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` into the gin context under `SessionUserKey`, the same key used by real session/token authentication. `PipelineRunsController.Create` then uses `auth.GetAuthenticatedUser(c)` to decide whether the caller is allowed to trigger a run by integer job ID ("only users are allowed to run jobs using int IDs - EIs not allowed"), but that check can never distinguish a genuine authenticated user from an EI-derived synthetic user, since both populate the exact same context key.

### Finding Description
Routing: the endpoint is mounted as [1](#0-0) 
under `userOrEI`, which accepts `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, or `auth.AuthenticateBySession` — any one succeeding is sufficient [2](#0-1) .

Root cause: `AuthenticateExternalInitiator` authenticates the EI key/secret pair, then sets both the EI object and a synthetic run-role `User` under `SessionUserKey`: [3](#0-2) 
This synthetic user has no `Email`/`ID` tied to any real account — it exists purely to satisfy `RequiresRunRole`'s minimum-role check.

Downstream, `PipelineRunsController.Create` attempts an EI-vs-user distinction using the wrong primitive: [4](#0-3) 
`auth.GetAuthenticatedUser(c)` simply checks for the presence of `SessionUserKey` — it does not (and cannot) tell whether that user came from a real session/token or was synthesized by `AuthenticateExternalInitiator`. Because the EI path also populates `SessionUserKey`, `isUser` evaluates to `true` for an EI-only request, defeating the explicit intent encoded in the code comment ("EIs not allowed") for integer job-ID runs. The attacker-controlled `idStr` path parameter is parsed directly into `jobID` and passed to `prc.App.RunJobV2(ctx, jobID, nil)` with no ownership/association check tying that job ID to the specific EI credential used.

Why existing checks don't stop it: `RequiresRunRole` only checks `user.Role != clsessions.UserRoleView` [5](#0-4) , which the synthetic `UserRoleRun` user passes trivially. There is no code path that rejects a request solely because it came from `SessionExternalInitiatorKey` rather than a real session/token.

### Impact Explanation
An attacker holding nothing but a valid EI access key/secret (a low-privilege, narrow-purpose credential intended only to relay external webhook events into the specific job it's registered for) can trigger execution of **any** job on the node by supplying an arbitrary integer job ID, bypassing the code's own explicit restriction that integer-ID job runs are reserved for real users. This is an authorization-bypass/privilege-escalation issue: identity is silently substituted (an EI is treated as an authenticated "user") rather than verified, and the resulting job-run trigger is not bound to the EI's associated job. Depending on what jobs exist on the node (e.g., jobs with side effects such as transactions, external bridge calls, or on-chain writes), this can cause unauthorized job execution, resource exhaustion, or unintended fund-moving pipeline runs.

### Likelihood Explanation
Minimal precondition: possession of any valid EI access key/secret registered on the node (these are lower-trust credentials distributed to external initiator systems, not admin/edit users). No other capability, role, or session is required. The request is a single unauthenticated (from the node's perspective of "real user") HTTP POST with two headers, fully repeatable, and does not require guessing the job ID if the attacker can enumerate or knows job IDs (job IDs are small monotonic integers, easily brute-forced given `/v2/jobs` may be restricted, but IDs are sequential/small-space).

### Recommendation
Distinguish EI-derived identity from real user identity structurally instead of relying on a shared `SessionUserKey`/role heuristic:
- Use a distinct context key (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` for presence) in `PipelineRunsController.Create` to explicitly reject EI-authenticated requests from the integer-ID path, rather than inferring "is a user" from `GetAuthenticatedUser`.
- Alternatively, avoid setting `SessionUserKey` at all in `AuthenticateExternalInitiator`, and have `RequiresRunRole` accept either a real user with run-role-or-above OR a valid external initiator context, without conflating the two under one key.
- If EI-triggered runs by integer ID must remain supported, add an explicit association check binding the EI's registered job(s) to the requested job ID before invoking `RunJobV2`.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a `gin.Context`/router mirroring `userOrEI` group registration for `POST /v2/jobs/:ID/runs` with `auth.Authenticate(mockAuthr, auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` and `auth.RequiresRunRole(prc.Create)`.
2. Configure a mock `Authenticator` whose `FindExternalInitiator` returns a valid `bridges.ExternalInitiator` for a given access key/secret, and whose `AuthorizedUserWithSession`/`FindUserByAPIToken` return `sql.ErrNoRows` (simulating an attacker with only EI creds, no session/token).
3. Send `POST /v2/jobs/5/runs` with headers `X-Chainlink-EA-AccessKey` and `X-Chainlink-EA-Secret` set to the valid EI credentials only (no session cookie, no API key/secret headers).
4. Assert:
   - The `Authenticate` middleware succeeds (200-level continuation, not 401).
   - `RequiresRunRole` does not reject (synthetic user has `Role: UserRoleRun`).
   - Inside `Create`, `auth.GetAuthenticatedUser(c)` returns `ok == true`, causing the `isUser` branch to execute and call `prc.App.RunJobV2(ctx, 5, nil)` on a mock `Application`.
   - Assert the mock `RunJobV2` was invoked with job ID `5` even though job `5` has no relation to the EI's registered webhook job, demonstrating that any job ID is triggerable by EI-only credentials, and that no ownership/association check exists between the EI and the target job.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
