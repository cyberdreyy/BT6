### Title
APR0 per-epoch interest rate truncation permanently strands borrower-funded yield in IdleCreditVault - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`prepareStopEpochWithApr0` books the full `_apr0NetInterest` into `pendingWithdraws` (cash that is actually pulled from the borrower at `stopEpoch`), but distributes it to requesters via a `1e18`-scaled per-unit rate `apr0RateByEpoch[epochNumber] = _apr0NetInterest * 1e18 / _principal`. Division truncates, so `Σ principal_i * rate / 1e18 < _apr0NetInterest`. The residual is funded but can never be claimed, mirroring the `deltaPerShare` truncation in `RewardableERC20._claimAndSyncRewards` where rewards are booked but unreachable.

### Finding Description
In `IdleCreditVault.prepareStopEpochWithApr0` the APR0 bucket accounting is:

- `pendingWithdraws += _apr0NetInterest` (untruncated, full amount).
- `apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal` (truncated).
- `apr0TotalPrincipal = 0`, closing the bucket forever. [1](#0-0) 

Each user's settlement then recomputes interest with a second truncation:

`_apr0User.settledInterest += (_principal * _rate) / 1e18` [2](#0-1) 

`stopEpoch` pulls `_expectedInterest + _pendingWithdraws` from the borrower and pushes `_pendingWithdraws` into the strategy via `collectWithdrawFunds` — i.e. the full `_apr0NetInterest` is funded in underlyings. [3](#0-2) [4](#0-3) 

Two truncation modes strand funds:

1. **Total truncation (the external bug's `deltaPerShare == 0` case).** If `_apr0NetInterest * 1e18 < _principal`, `apr0RateByEpoch[epoch] == 0` while `pendingWithdraws` was still increased by `_apr0NetInterest`. Every APR0 user settles with `settledInterest += 0` — the entire bucket's interest is paid by the borrower and locked in the vault with no claim path. Feasible for 18-decimal underlyings when the epoch interest allocated to the APR0 bucket is small relative to its principal (low realized interest, short epochs, large bucket).
2. **Partial truncation.** When `rate > 0`, each user loses `< principal_i / 1e18` wei at `_settleApr0`/`_withdrawClaimAmountsForEpoch`, and the aggregate shortfall equals the remainder discarded by the `* 1e18 / _principal` division. Because claims are receipt-based (`claimBasis * price / RECOVERY_FULL` and `settledInterest`), no later claimant can ever absorb the remainder — unlike Synthetix-style `rewardPerTokenStored` accumulators, nothing rolls over.

There is no recovery path for underlying: `IdleCreditVault` has no skim/rescue for the accounting token, and `collectWithdrawFunds`/`claimWithdrawRequest` only release exactly the booked claim amounts. The stranded amount sits in the vault's `underlyingToken` balance permanently (until, at best, an unrelated default-recovery reserve happens to draw on it).

### Impact Explanation
Permanent freezing of unclaimed yield. Borrower-funded APR0 interest up to `_apr0NetInterest - Σ principal_i·rate/1e18` is locked in the strategy forever. The bound is `apr0TotalPrincipal / 1e18` wei per epoch (plus `<1` wei per claimant), which is dust for 6-decimal underlyings but reaches token-scale for 18-decimal underlyings with large APR0 buckets and small realized interest — the same regime the external report flags (small per-period reward vs large supply). No guard catches it: `_settleApr0`/`_withdrawClaimAmountsForEpoch`/`_claimDefaultedWithdrawRequest` all consume the truncated rate consistently, and `pendingWithdraws` is decremented only by actual claimed basis, not by the stranded remainder.

### Likelihood Explanation
Requires an APR0 withdraw bucket to exist at `stopEpoch` with a nonzero `_apr0NetInterest` — a normal, expected configuration (APR=0 epochs exist precisely to service these requests). No attacker action is needed; the truncation is deterministic every epoch the bucket is nonzero. Full-to-zero truncation additionally needs `_apr0NetInterest * 1e18 < _principal`, achievable when realized epoch interest is small vs the bucket principal, e.g. large bucket, low realized override interest, or an 18-decimal underlying.

### Recommendation
Avoid the shared truncated-rate pattern for one-shot distributions. Options:

- Store and settle the exact per-user net interest at `stopEpoch` time (accumulate `_apr0NetInterest` proportionally per user when requests are created, or keep a remainder variable that is credited to the last/largest claimant), so `Σ claims == pendingWithdraws` delta exactly.
- Or, keep `apr0RateByEpoch` but increase `pendingWithdraws` by `Σ principal_i * rate / 1e18` (recompute the distributable total from the truncated rate) instead of the untruncated `_apr0NetInterest`, and leave the remainder out of the borrower pull so it is never stranded.
- Whichever is chosen, add an invariant check: after settlement of an epoch, `pendingWithdraws` decrease must equal the sum of claimable basis + settled interest.

### Proof of Concept
Foundry fork scenario on `IdleCreditVault.t.sol` harness:

```solidity
// 18-decimal underlying vault, APR forced to 0 (same setup as testApr0WithdrawMixedAABBProRata)
// 1. Deposit, startEpoch, stopEpoch(0,0), force lastEpochApr = 0.
// 2. Users request APR0 withdraws: apr0TotalPrincipal = P (e.g. 1e24).
// 3. Next epoch, manager calls stopEpoch(0, I) where I makes
//    _apr0InterestGross = (I - pendingFees) * P / (TVL + P)  small (e.g. < P / 1e18).
// 4. Assert: strategy.apr0RateByEpoch(reqEpoch) == 0 while
//    strategy.pendingWithdraws() increased by apr0Net (> 0), and borrower actually
//    transferred pendingWithdraws to the strategy via collectWithdrawFunds.
// 5. claimWithdrawRequest() for every APR0 user: each receives principal + 0 interest.
//    After all claims, underlying.balanceOf(strategy) retains the stranded apr0Net,
//    and no subsequent claim/default/recovery path releases it.
```

Key assertions: `apr0RateByEpoch[reqEpoch] == 0`, `pendingWithdraws` credited `apr0Net`, final vault underlying balance `== apr0Net` residue after all claims — matching the external PoC's `deltaPerShare == 0` outcome where booked rewards are permanently undistributable.
