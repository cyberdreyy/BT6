### Title
Write-off requests can be created with a zero asking price, letting anyone seize escrowed tranche tokens for free — (`contracts/IdleCreditVaultWriteOffEscrow.sol`)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` validates that the tranche-token amount is non-zero, but it does not validate `underlyingsRequested`. A request with `underlyings == 0` is stored like any other, and `fullfillWriteOffRequest` only enforces `_underlyings >= currentRequest.underlyings` — satisfied by `0`. Any unprivileged caller (the contract explicitly allows any wallet to fulfill) can therefore pull all escrowed tranche tokens out of a zero-priced request without paying a single wei of underlying.

### Finding Description
The escrow is meant to let lenders exchange defaulted-risk tranche tokens for underlying at a self-declared price. The bug-class analog to "an account created without a password" is a request created without a required payout field:

- `createWriteOffRequest` rejects `amount == 0` but never checks `underlyingsRequested` (lines 86–101).
- `fullfillWriteOffRequest` enforces only `currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings` → revert. With `underlyings == 0`, passing `_underlyings = 0` satisfies the check (line 129).
- Execution then transfers `0` underlying to the user (fee on 0 is 0), and `IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches)` sends the full escrowed tranche balance to the caller (line 151).

The fulfiller needs no KYC credential — the test suite explicitly demonstrates non-Keyring wallets fulfilling requests — so any EOA can front-run a genuine buyer or simply notice a zero-priced request and take the tranches.

### Impact Explanation
The attacker receives the victim lender's tranche tokens at zero cost. Those tranche tokens are redeemable claims on the credit vault (withdrawal requests / write-off via `writeOffDeposit` if the borrower buys them back, or secondary transfer). Loss equals the full market/redeemable value of the escrowed tranches; the lender receives nothing. This breaks the "one receipt one payout / fair exchange" invariant: the escrow guarantees atomic swap of tranches for the declared underlyings, and a zero-price declaration removes the swap leg entirely.

### Likelihood Explanation
Creating a zero-priced request requires only a lender error or a lender who deposits first and prices later across multiple `createWriteOffRequest` calls (the function accumulates into `userRequests` — an early call with 0 contributes tokens locked at an effectively zero floor before the user adds a price; actually accumulation mixes, but a single zero-price request stands alone too). Once such a request exists, fulfillment is permissionless and atomic — a single opportunistic transaction. Monitoring bots scanning the escrow can capture it immediately. No privileged role, no timing window, no capital required (flash-loanable tranche-free; attacker only needs gas).

### Recommendation
In `createWriteOffRequest`, revert when `underlyingsRequested == 0` (e.g., `if (underlyingsRequested == 0) revert Is0();`), or require that the aggregate `userRequests[msg.sender].underlyings` stays non-zero whenever `tranches != 0`. Optionally cap `underlyings` to the tranche redeemable value to prevent pricing mistakes, and emit an event with the declared price so victims/indexers can catch mispriced requests before fulfillment.

### Proof of Concept
Foundry-style PoC (fork of mainnet, using the same fixtures as `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "./IdleCreditVaultWriteOffEscrow.t.sol";

contract ZeroPriceWriteOffTheftTest is IdleCreditVaultWriteOffEscrowTest {
  function testZeroPriceRequestLetsAnyoneTakeTranchesForFree() external {
    // Epoch is running; LP holds AA tranche tokens and approved the escrow (setup does this).
    // LP creates a request but forgets / neglects to set an asking price.
    uint256 lpTranches = 10_000e18;
    vm.prank(LP);
    escrow.createWriteOffRequest(lpTranches, 0); // underlyingsRequested = 0

    (uint256 tranches, uint256 underlyings) = escrow.userRequests(LP);
    assertEq(tranches, lpTranches);
    assertEq(underlyings, 0);

    // Attacker: any EOA, no KYC, no underlying balance, no approval needed.
    address attacker = makeAddr("attacker");
    uint256 attackerUnderlyingPre = underlying.balanceOf(attacker);

    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(LP, lpTranches, 0); // pays 0 underlying

    // Attacker received the entire escrowed tranche balance for free.
    assertEq(tranche.balanceOf(attacker), lpTranches, "attacker stole escrowed tranches for 0 underlying");
    assertEq(underlying.balanceOf(attacker), attackerUnderlyingPre, "attacker paid nothing");
    // LP received nothing.
    assertEq(underlying.balanceOf(LP), 0, "LP got 0 underlying for escrowed tranches");

    (tranches, underlyings) = escrow.userRequests(LP);
    assertEq(tranches, 0);
    assertEq(underlyings, 0);
  }
}
```

Broken invariant confirmed live: `fullfillWriteOffRequest` executes end-to-end with `_underlyings == 0` (no revert — the fee branch computes `0`, `safeTransfer` of 0 succeeds), delivering `_tranches` to the caller. No existing guard (`EpochNotRunning`, `WrongRequest`, `Is0`, `nonReentrant`, Keyring) prevents it; the only missing check is the zero-price validation at creation.
