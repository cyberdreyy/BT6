### Title
Miner-side `StackerDBListener` never nets a signer's stale rejection weight when the signer later flips to acceptance for the same block - `[File: stacks-node/src/nakamoto_node/stackerdb_listener.rs]`

### Summary
The mined-block signature/rejection tally kept by `StackerDBListener` (consumed by `SignerCoordinator::get_block_status`) accumulates a signer's rejection weight into `total_weight_rejected` and never removes it if that same signer subsequently re-evaluates and sends an `Accepted` response for the same block. This is the same class of bug as the reported limiter: an "outflow" (rejection weight) is recorded against one bucket (`total_weight_rejected`) and the corresponding "inflow" (the signer's later acceptance) is applied to a different bucket (`total_weight_approved`) instead of netting against the original bucket. The stale rejection weight is never unwound, so a single signer's weight can end up counted in both totals simultaneously.

### Finding Description
`BlockStatus` tracks per-block tallies with two independent counters and one combined dedup set: [1](#0-0) 

On `Accepted`, weight is added to `total_weight_approved` gated only on `gathered_signatures` not containing the slot, and then the slot is unconditionally inserted into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

On `Rejected`, weight is added to `total_weight_rejected` gated only on `responded_signers.insert(slot_id)` returning `true` (i.e., first response ever from that slot): [3](#0-2) 

Sequence that breaks the invariant "each signer's weight is counted at most once, in at most one bucket, matching their current live opinion":

1. Signer S (weight w) sends `Rejected` for block B first. `responded_signers.insert(slot_S)` → `true`, so `total_weight_rejected += w`.
2. Per the documented signer lifecycle, `LocallyRejected --> LocallyAccepted` is an expected, legitimate re-evaluation transition (`docs/signer-flows.md`, `BlockInfo::check_state`), and the local state machine allows a signer to re-sign a block it previously rejected once its view changes. S subsequently sends `Accepted` for the same B.
3. In the `Accepted` handler, the check is only `!gathered_signatures.contains_key(&slot_S)` — it does **not** check or clear `responded_signers`/`total_weight_rejected`. Since S was never in `gathered_signatures`, the branch fires: `total_weight_approved += w`.
4. `total_weight_rejected` still contains `w` from step 1 — it is never decremented. S's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected`.

This exactly mirrors the reported bug: `add_outflow`/`reduce_outflow` (here, add-to-rejected / never-reduce-on-flip-to-accept) operate on different "segments" (buckets) with no cross-bucket netting, so the aggregate no longer reflects the true net state.

### Impact Explanation
`SignerCoordinator::get_block_status` uses these two counters directly to decide the fate of a block proposal: [4](#0-3) 

Because a flipped signer's weight is double-counted, `total_weight_rejected` can carry stale weight indefinitely (it decays only via the whole-proposal `reset_rejections` call on a fresh timeout cycle for a *new* proposal, not via correction of the same signer's later message). This lets a stale rejection count push `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` to trip even though the actual, current live opinion of the signer set supports acceptance — causing the coordinator to return `NakamotoNodeError::SignersRejected` for a block that in fact has enough live approving weight, or to keep waiting/aborting the wrong way. This is an availability/liveness wedge on block production (a valid, signable block can be spuriously treated as rejected because of a vote the signer already retracted), matching the "High: a signer wedged into never signing valid blocks... " class of impact, transposed to the miner/coordinator's tally which gatekeeps whether a legitimately-approved block is ever pushed to the node.

It also breaks the aggregated-weight vs. verified-accepts equality that the tally is supposed to enforce: at any instant, `total_weight_approved + total_weight_rejected` should never exceed `total_weight` for a well-behaved signer set with one vote per signer, but this code allows it to exceed that bound whenever any single signer legitimately reconsiders their vote.

### Likelihood Explanation
This does not require a malicious majority or another signer's key — it only requires a *single* signer, acting entirely within its own documented state machine (`LocallyRejected --> LocallyAccepted` re-evaluation, explicitly supported by `BlockInfo::check_state` per `docs/signer-flows.md`), to reject then later accept the same block proposal. Re-evaluation is a normal occurrence (e.g., a signer initially rejects due to a transient local-view mismatch, then re-checks and signs once the chain catches up), so this can happen without any adversarial intent, making the miscount readily reachable in ordinary operation, not just a contrived attack.

### Recommendation
When processing an `Accepted` message for a slot that is present in `responded_signers` but not in `gathered_signatures`, first check whether that slot previously contributed to `total_weight_rejected` (and to any `failed_txids` entries) and subtract/undo that contribution before adding to `total_weight_approved` (and symmetrically for a rejection arriving after a prior acceptance, if that transition is ever allowed). Concretely, track each slot's current disposition (`Approved(weight)` / `Rejected(weight)`) in a single map instead of two independently-incremented counters plus a shared "responded" set, and derive `total_weight_approved`/`total_weight_rejected` by summing that map, or explicitly net out the old bucket when a slot's disposition changes.

### Proof of Concept
Deterministic reproduction against `StackerDBListener`'s tally logic (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:386-591`):

1. Configure a block `B` with `weight_threshold = 70` out of `total_weight = 100`, with signer `S` (`slot_id = 5`) carrying weight `w = 40`.
2. Signer `S` sends `BlockResponse::Rejected` for `B`.
   - `responded_signers.insert(5)` → `true` ⇒ `total_weight_rejected = 40`.
3. Signer `S` re-evaluates and sends `BlockResponse::Accepted` for `B` (a legitimate `LocallyRejected → LocallyAccepted` transition).
   - `gathered_signatures.contains_key(5)` is `false` ⇒ `total_weight_approved += 40` ⇒ `total_weight_approved = 40`.
   - `gathered_signatures.insert(5, sig)`, `responded_signers.insert(5)` (already present, no-op).
   - `total_weight_rejected` remains `40` — never decremented.
4. Query state: `total_weight_approved = 40`, `total_weight_rejected = 40`. Sum = `80 > w = 40`, i.e., signer `S`'s weight is counted twice across the two buckets, in violation of "one signer, one live vote."
5. If two more independent signers (weight 30 each, total additional weight 60, still under a "majority" bound if defined loosely, but here just enough to combine with the stale 40) also reject, `total_weight_rejected` reaches `100`, tripping `total_weight_rejected.saturating_add(70) > 100` and returning `SignersRejected`, even though signer `S` (40 weight) has *actually* signed acceptance and the live rejecting weight is only 60 — below the blocking-minority threshold of 30 needed to reject when threshold is 70. The stale, un-netted 40 from `S`'s retracted rejection is what tips the false rejection decision.

**Uncertainty / what I could not fully verify**: I could not locate a test exercising the exact reject→accept sequence for the same slot in `stackerdb_listener.rs`, nor confirm whether any downstream consumer clears `BlockStatus` between distinct proposals in a way that would prevent this from manifesting for the *same* block hash (rather than a new proposal). The `reset_rejections` call I found resets the coordinator's local `rejections` counter for timeout-step purposes, not the underlying `BlockStatus.total_weight_rejected`/`responded_signers`; I was not able to fully inspect its body due to iteration limits, so I cannot be certain it doesn't also clear `BlockStatus` state before the block hash changes. If it does clear per-block state on every retry, the practical window for exploitation would be narrower (limited to retries of the *same* block hash without a full state reset), but the core accounting flaw — no netting between the reject and later accept for the same signer/slot on the same block — stands as shown above.
