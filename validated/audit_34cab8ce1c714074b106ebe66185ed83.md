### Title
Re-requesting a withdrawal after a loss-adjusted epoch lets the old receipt escape its haircut and claim at par - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records a per-epoch loss haircut in `lossRecoveryPriceByEpoch`, but the loss-adjusted claim path is keyed only on `lastWithdrawRequest[user]` — a single scalar that is overwritten on every new `requestWithdraw`. A user whose epoch-N receipt was haircutted can submit a second withdraw request in a later epoch, which moves `lastWithdrawRequest` past the loss epoch. Their claim then skips `_claimLossAdjustedWithdrawRequest` entirely and the still-recorded epoch-N receipt is paid at full par through `_claimFundedWithdrawRequest`, breaking the loss-socialization invariant.

### Finding Description
In `requestWithdraw` the strategy does three things: it mints a receipt to the user, adds `_amount` to the aggregate `withdrawsRequests[user]` and to `withdrawsRequestsByEpoch[user][currentEpoch]`, and sets `lastWithdrawRequest[user] = currentEpoch` [1](#0-0) .

When `stopEpochWithDuration` underfunds pending receipts, `collectWithdrawFunds` stores the haircut as `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws` [2](#0-1) .

On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` and clears only that single epoch's receipt via `_clearWithdrawClaimForEpoch` [3](#0-2) . If `lastWithdrawRequest` has been overwritten by a newer request, the lookup returns 0, the function returns early, and execution falls into `_claimFundedWithdrawRequest`, which pays the aggregate `withdrawsRequests[user]` — still containing the epoch-N receipt — at par and burns the receipt tokens [4](#0-3) . `_clearWithdrawClaimForEpoch` only ever touches `withdrawsRequestsByEpoch[user][claimEpoch]` for the epoch passed in, so the epoch-N ledger entry remains but its accounting is consumed by the par payout [5](#0-4) . The comment in `_claimFundedWithdrawRequest` explicitly permits re-requesting before claiming ("if a user does not claim… he will have to wait for another epoch"), so nothing prevents the sequence.

### Impact Explanation
Only `pendingToFund` underlyings were transferred into the vault to cover haircutted epoch-N receipts. The attacker recovers `receiptAmount * (1 - lossRecoveryPrice)` more than funded, i.e. direct theft of reserve denominated in the epoch-N haircut. Every other claimant of that epoch is correctly haircutted; the attacker's escape comes out of the shared funded reserve, so later funded/instant claims revert on insufficient balance — partial insolvency and freezing of other users' claims. Quantified: for a 50% recovery price the attacker doubles their epoch-N payout; loss equals the unpaid loss share they should have absorbed.

### Likelihood Explanation
The attacker is an ordinary KYC-passed lender/tranche holder who already has a pending withdraw request when `stopEpochWithDuration` realizes a loss — a normal, non-privileged position. They then need one more tranche balance (kept or re-deposited via the queue/CDO in a buffer phase) to call `requestWithdraw` again, overwriting `lastWithdrawRequest`. After one additional epoch wait they call `claimWithdrawRequest` through `IdleCDOEpochVariant`. No privileged cooperation is required beyond the honest manager's normal `stopEpoch` sequence. The precondition is a loss-adjusted epoch plus a re-request, which is a plausible market scenario, though it requires the attacker to hold or re-acquire tranche tokens.

### Recommendation
Track loss exposure per epoch rather than through a single `lastWithdrawRequest` pointer. Concretely: in `claimWithdrawRequest`, iterate or accumulate over all epochs for which `withdrawsRequestsByEpoch[user][e] != 0` and apply `lossRecoveryPriceByEpoch[e]` when set, instead of only checking `lastWithdrawRequest`; alternatively, on `requestWithdraw`, eagerly settle/clear any earlier `withdrawsRequestsByEpoch` entries whose `lossRecoveryPriceByEpoch` is non-zero (paying them at the haircut before recording the new request), or revert `requestWithdraw` while the user has an unsettled loss-epoch receipt.

### Proof of Concept
A Foundry fork test mirroring `test/foundry/IdleCreditVault.t.sol` setup (same `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices` helpers):

```solidity
function testLossEpochReceiptEscapesHaircutAfterReRequest() external {
    uint256 amount = 10000 * ONE_SCALE;
    address alice = makeAddr('alice');
    _depositWithUser(alice, amount * 2, true);   // AA tranches
    _startEpochAndCheckPrices(0);

    // epoch N request
    uint256 tr = IdleCDOTranche(address(AAtranche)).balanceOf(alice);
    vm.prank(alice);
    cdoEpoch.requestWithdraw(tr / 2, address(AAtranche));

    // borrower underfunds at stopEpochWithDuration -> lossRecoveryPriceByEpoch[N] < RECOVERY_FULL
    // (manager calls stopEpochWithDuration with _lossAmount > 0; collectWithdrawFunds stores haircut)
    _stopEpochWithLoss(/* partial funding */);

    // buffer/epoch N+1: alice requests again, overwriting lastWithdrawRequest
    vm.prank(alice);
    cdoEpoch.requestWithdraw(tr / 4, address(AAtranche));

    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, apr, _expectedFundsEndEpoch()); // epoch N+2, claims unlocked

    uint256 balPre = underlying.balanceOf(alice);
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(alice) - balPre;

    // epoch-N receipt paid at par instead of par * lossRecoveryPrice / RECOVERY_FULL
    assertGt(got, expectedHaircuttedPayout, "loss haircut escaped");
}
```

Uncertainty noted: the exact ordering of `epochNumber` increment versus `collectWithdrawFunds` inside `stopEpochWithDuration` in `IdleCDOEpochVariant.sol` was not fully verified within the search budget; if the haircut is stored under an epoch different from `lastWithdrawRequest`, the same haircut-escape occurs even without a re-request (which would make the bug strictly worse and simpler to trigger). Either way the single-pointer lookup cannot correctly attribute loss-adjusted receipts across multiple request epochs.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
