### Title
Post-finalization instant withdraw receipts claim against `defaultRecoveryEpoch` and drain `defaultRecoveryReserve` without being counted in `totalBasis` — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` records receipts under the current `epochNumber`, which after a borrower default remains equal to `defaultRecoveryEpoch` until a new running-epoch `deposit()` bumps it. Once `defaultRecoveryFinalized` is set, `finalizeDefaultRecovery` sized `defaultRecoveryReserve` strictly against `defaultPendingClaimBasis()` (basis existing at finalization). A new instant request created after finalization lands in `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, so `claimInstantWithdrawRequest` routes it through `_claimDefaultedInstantWithdrawRequest`, which pays `claimBasis * defaultRecoveryPrice` out of the recovery reserve even though that basis was never part of `totalBasis`. This is the direct analog of the CVE-2019-9771 NULL-dereference class: a lookup on a missing/zero-value basis (absent from accounting) is treated as valid and dereferenced for payout.

### Finding Description
- `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` where `totalBasis = activeBasis + defaultPendingClaimBasis()`, and `defaultPendingClaimBasis()` only includes `instantWithdrawClaimsByEpoch[epochNumber]` as it stands at finalization (IdleCreditVault.sol:644-649, 679-696).
- `requestInstantWithdraw` has no post-default handling (unlike `requestWithdraw`, which has the `defaultRecoveryFinalized` branch at lines 247-257). It blindly does `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` and mints a 1:1 receipt (lines 366-374).
- `epochNumber` is only incremented inside `deposit()` when the epoch is running (lines 607-610). In the defaulted/finalized phase it stays equal to `defaultRecoveryEpoch`, so the attacker's new receipt is indexed under the defaulted epoch.
- On claim, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest` (lines 382-385), which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, cannot distinguish pre- vs post-finalization receipts, and pays `claimBasis * defaultRecoveryPrice` via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve` (lines 842-856, 912-917).

### Impact Explanation
Every post-finalization instant receipt of size `X` consumes `X * defaultRecoveryPrice` from a reserve that was only funded for the basis existing at finalization. Because these claims are unbacked, the reserve is exhausted early: subsequent legitimate defaulted-epoch claimants (normal receipts in `_claimDefaultedWithdrawRequest`, instant receipts, post-default requests) hit `defaultRecoveryReserve -= _amount` underflow in `_transferDefaultRecovery` and their recovery payouts revert permanently — theft/permanent freezing of unclaimed recovery yield. The attacker acquires tranche tokens at the post-haircut `virtualPrice`, requests an instant withdraw, and extracts a full recovery-priced claim basis that was never socialized into the reserve, converting a cheap post-default position into a first-in-line reserve drain.

### Likelihood Explanation
Requires: (1) a borrower default with partial funding such that `pendingInstantWithdraws != 0` at finalization (`defaultInstantWithdrawsFinalized == true`, line 696); (2) instant withdrawals enabled on the CDO side so `requestInstantWithdraw` is reachable in the defaulted phase; and (3) the claim executed before any new running epoch increments `epochNumber`. The attacker is an unprivileged tranche-token holder; no privileged cooperation is needed. Likelihood is moderate — it hinges on the CDO permitting instant-withdraw requests while defaulted, which could not be fully confirmed from the strategy file alone, but the strategy-side code contains no guard preventing it and `requestWithdraw` shows the intended pattern was considered and simply omitted here.

### Recommendation
In `requestInstantWithdraw`, when `defaultRecoveryFinalized` is true, either revert or record the receipt under a fresh marker (e.g., a `postDefaultInstantRequests` map or `defaultRecoveryEpoch + 1` bucket) so `_claimDefaultedInstantWithdrawRequest` never matches it. Alternatively, key the defaulted-claim lookup on a snapshot taken at finalization rather than the mutable `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`. Mirror the `requestWithdraw` post-default branching so both receipt types behave consistently.

### Proof of Concept
Foundry fork PoC sketch (in `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
// Setup: depositAA/depositBB, borrower defaults at stopEpoch, manager calls
// finalizeDefault with partial recovery so defaultRecoveryPrice < 1e18 and
// pendingInstantWithdraws != 0 (defaultInstantWithdrawsFinalized == true).
uint256 reserveBefore = strategy.defaultRecoveryReserve();
uint256 price = strategy.defaultRecoveryPrice();
uint256 epoch = strategy.epochNumber();
assertEq(epoch, strategy.defaultRecoveryEpoch());

// Attacker: unprivileged tranche holder requests instant withdraw post-finalization.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(ATTACK_AMOUNT, address(AAtranche));
// Receipt lands in the defaulted epoch bucket that was never part of totalBasis.
assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), ATTACK_AMOUNT);

// Claim pays out of the isolated recovery reserve at defaultRecoveryPrice.
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // or claimInstantWithdrawRequest path
// Reserve drained by ATTACK_AMOUNT * price / 1e18 with zero backing in totalBasis.

// Legitimate defaulted-epoch claimant now reverts on
// `defaultRecoveryReserve -= _amount` underflow -> unclaimed recovery frozen.
vm.prank(victim);
vm.expectRevert(); // panic underflow in _transferDefaultRecovery
cdoEpoch.claimWithdrawRequest();
```
