### Title
Builder payment can be paid out twice (once via quorum eviction, once via the "older‑than‑previous‑epoch" fallback) - (File: specs/gloas/beacon-chain.md)

### Summary
`state.builder_pending_payments` is a two‑epoch rotating queue that is settled either (a) synchronously by `settle_builder_payment` when the revealing (child) block for a slot arrives within the current or previous epoch, or (b) opportunistically by `process_builder_pending_payments` at every epoch boundary, which appends `payment.withdrawal` to `state.builder_pending_withdrawals` whenever `payment.weight >= quorum`, and then unconditionally overwrites/rotates the array slot. If the child block that reveals a slot's execution requests is delayed by two or more epochs, `apply_parent_execution_payload` falls back to reconstructing the withdrawal directly from `state.latest_execution_payload_bid` — with no check for whether that payment was already paid out via the quorum path. This can pay the same builder bid to the same `fee_recipient` twice.

### Finding Description
In `specs/gloas/beacon-chain.md`:

`process_execution_payload_bid` records a pending payment for slot `S` at
`state.builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH]` [1](#0-0) , while also caching the bid itself in `state.latest_execution_payload_bid` [2](#0-1) .

`process_attestation` accumulates `payment.weight` for "same‑slot" attestations, independent of when the payload for that slot is ultimately revealed [3](#0-2) .

Every epoch boundary, `process_builder_pending_payments` checks the first half of the queue against a quorum and appends qualifying payments to `builder_pending_withdrawals`, then rotates the array (overwriting the first half with the old second half) regardless of the outcome: [4](#0-3) 

Normally the revealing block for slot `S` arrives at `S+1` and `apply_parent_execution_payload` calls `settle_builder_payment`, consuming the array entry before any epoch‑boundary quorum check can see it: [5](#0-4) 

But if the revealing block is delayed by 2+ epochs (parent's slot is older than `get_previous_epoch(state)`), the array entry has already rotated out (evicted) by `process_builder_pending_payments`. The code assumes this eviction always happened *without* producing a withdrawal, and unconditionally re‑adds one from the cached bid: [6](#0-5) 

The assumption is false whenever the payment's weight reached quorum *before* it rotated out of the two‑epoch window: `process_builder_pending_payments` will have already pushed `payment.withdrawal` onto `builder_pending_withdrawals` at some earlier epoch boundary (see line 1670-1671), and the array‑slot rotation does not clear or mark the entry as "already paid" — it is simply overwritten by whatever payment moves into that slot next. `state.latest_execution_payload_bid`, which is used for the fallback, is a single global cache of the *most recent* bid and is completely decoupled from whether that bid's withdrawal has already been queued. When the long‑delayed child block finally arrives, `apply_parent_execution_payload` reaches the `elif parent_bid.value > 0` branch and appends a second, independent `BuilderPendingWithdrawal` with the identical `amount`/`fee_recipient`/`builder_index`.

Both withdrawal entries are later executed by `apply_withdrawals`, which decreases `state.builders[builder_index].balance` by `min(withdrawal.amount, builder_balance)` for each entry independently [7](#0-6) , and the execution layer is required to mint/pay the corresponding withdrawal amount to `fee_recipient` for each entry in `payload_expected_withdrawals`. This mirrors the audited Solidity bug: two independently‑correct‑looking code paths (`process_builder_pending_payments`'s quorum path and `apply_parent_execution_payload`'s "evicted" fallback) both account for the *same* quantity, because the second path's "already evicted implies never paid" assumption is not actually enforced anywhere in the state.

### Impact Explanation
This breaks the invariant that a single committed builder bid produces exactly one payment to its `fee_recipient`. When triggered, the builder is charged (has balance debited) twice for one bid, and the execution layer mints/pays the bid amount to the fee recipient twice — i.e., Gwei is paid out to a recipient beyond what the block/bid committed to. Per the stated impact classes this is a Critical-class issue ("Gwei created, destroyed, or paid to a non-owner" / "a payload or payment applied that the block did not commit to").

### Likelihood Explanation
The trigger requires two specific but not extraordinary conditions to coincide:
1. The child block that reveals the parent's execution requests is delayed by two or more full epochs (achievable via missed slots / a slow/adversarial proposer sequence, not requiring any BLS/library bug or peer collusion).
2. The pending payment for that stalled slot accumulates enough "same‑slot" attesting weight to cross the quorum threshold before the two‑epoch window elapses (attestations can be included in the slot immediately following `S`, independent of when `S`'s own reveal block eventually shows up).

Both conditions are within the control of a single builder/proposer sequence (or can occur from natural periods of missed proposals), so no coalition or foreign key is required. I was not able to fully trace `is_attestation_same_slot` and `get_builder_payment_quorum_threshold`'s exact bodies within the available tool budget (grep did not return line-level matches before the session ended), so the precise numeric quorum and exact same-slot-attestation eligibility window are not fully confirmed from source; this is noted as an open verification item for a full audit pass, though the array-rotation and fallback code paths that create the double-count are directly confirmed from the cited spec text.

### Recommendation
Track settlement state explicitly instead of inferring it from the two‑epoch queue position. For example, mark a payment (or the cached `latest_execution_payload_bid`) as "withdrawal already queued" once `process_builder_pending_payments` pushes it to `builder_pending_withdrawals`, and have the `elif parent_bid.value > 0` fallback in `apply_parent_execution_payload` check that flag before appending a second withdrawal, rather than assuming any payment that fell out of the two‑epoch window was never paid.

### Proof of Concept
Conceptual sequence (spec-level, no client bug required):
1. Block for slot `S` is proposed with a builder bid of value `V`; `process_execution_payload_bid` records the pending payment at `builder_pending_payments[SLOTS_PER_EPOCH + S%SLOTS_PER_EPOCH]` and caches the bid in `state.latest_execution_payload_bid`.
2. The next slot's block includes attestations flagged as "same-slot" for `S`, pushing `payment.weight` above `quorum` (per `process_attestation`'s weight-accumulation logic at lines 2382-2389).
3. The chain then experiences 2+ epochs without a block whose parent is `S` (missed slots / delayed proposer), so `apply_parent_execution_payload` for slot `S` is never invoked in that window.
4. At each epoch boundary, `process_builder_pending_payments` runs; once `S`'s payment rotates into `builder_pending_payments[:SLOTS_PER_EPOCH]`, its `weight >= quorum` causes it to be appended to `builder_pending_withdrawals` (withdrawal #1), and the array slot is subsequently overwritten by rotation.
5. Eventually a block arrives whose `parent_slot == S`. Since `compute_epoch_at_slot(S)` is now older than `get_previous_epoch(state)`, `apply_parent_execution_payload` takes the `elif parent_bid.value > 0` branch and appends a second `BuilderPendingWithdrawal` with the same `amount`, `fee_recipient`, and `builder_index` (withdrawal #2).
6. Both withdrawals are later processed by `apply_withdrawals`, debiting the builder's balance twice and causing the execution layer to pay `fee_recipient` the bid amount `V` twice for a single committed bid.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
