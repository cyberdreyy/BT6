### Title
Stale confirmations from a removed member allow multisig requests to execute below live-member quorum - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only purges requests and confirmations for requests that the removed member *created*; it never scans the `confirmations` map to strip entries the removed member added as a *confirmer* on requests created by other members. Those stale confirmation strings continue to count toward `num_confirmations` in `confirm()`, letting a request execute with fewer genuinely live-member approvals than the configured threshold.

### Finding Description
The broken binding: the number of confirmations counted in `confirm()` (`confirmations.len() + 1`) is claimed to equal the number of *current, live* members who approved the request, i.e. `confirmations.len() + 1 == |{live members who confirmed}|`. In reality this equality does not hold once a confirming (but non-creating) member is removed.

In `confirm()`: [1](#0-0) 
the quorum check `confirmations.len() as u32 + 1 >= self.num_confirmations` treats every string previously inserted into the `confirmations` `HashSet<String>` as an equally valid vote, with no re-validation against the current `members` set.

`delete_member` is supposed to purge stale state for a removed member, but it only does so for requests the member originally *created* (`r.member == member`, where `member` is `MultiSigRequestWithSigner.member`, the request's creator/signer), not for requests the member merely *confirmed*: [2](#0-1) 

Exploit flow:
1. Multisig has members A, B, C, D with `num_confirmations = 3`.
2. Member A calls `add_request` to create request `R` (a `Transfer` moving funds out). `R.member == A`.
3. Member B calls `confirm(R)`. Since `1 + 1 < 3`, it just inserts `"B"` into `confirmations[R]` — `confirmations[R] = {B}`.
4. Someone gets a separate `DeleteMember { member: B }` request confirmed by quorum and executed. `delete_member` iterates `self.requests` filtering by `r.member == B`; since `R.member == A`, `R` is untouched and `confirmations[R]` still contains `"B"`, even though B is no longer in `self.members`.
5. Now only A, C, D remain (3 members, `num_confirmations = 3`, so full quorum should require all three). But C calls `confirm(R)`: `confirmations[R].len() (1) + 1 = 2 < 3`, not yet executed, so it inserts `"C"` → `{B, C}`. D calls `confirm(R)`: `len() (2) + 1 = 3 >= 3` → `execute_request` fires the `Transfer`.
6. The request executed with confirmations from B (stale/removed), C, and D — i.e., only 2 of the 3 currently-live members (C, D) actually approved, while A never confirmed. `assert_valid_request` (which only checks the caller is a current member, that the request exists, and that confirmations exist) does not detect or reject this: [3](#0-2) 

None of the existing guards (`assert_valid_request`, `current_member`, `assert_self_request`) validate that every entry already present in the `confirmations` set still corresponds to a current member; they only validate the new caller.

### Impact Explanation
This directly matches the listed Critical impact: "a multisig request executed below `num_confirmations` live members." NEAR funds held by the multisig account can be transferred (`Transfer` action) or contract/account state changed (`AddKey`, `DeployContract`, `AddMember`) with fewer genuine live-member approvals than the multisig's stated policy requires, undermining the entire security guarantee of the multisig. This is repeatable for every request that received a partial confirmation from a member before that member is later removed — the stale vote silently persists forever until the request is deleted or executed.

### Likelihood Explanation
No special privileges beyond being a normal multisig member/confirmer are needed to *create* the stale state (any member simply confirming a request before being removed via ordinary contract lifecycle events triggers it) — an attacking member could deliberately confirm several pending requests, then arrange or wait for their own removal (e.g., voluntary "DeleteMember" cleanup, a compromised key being revoked, key rotation), leaving behind a phantom vote that others unknowingly complete a quorum with. This requires normal governance activity (adding/removing members is routine) and no unusual gas or storage cost; the flaw is triggered by ordinary contract usage, making it highly feasible and low-cost to encounter or engineer.

### Recommendation
When removing a member in `delete_member`, also strip that member's `to_string()` entry from `confirmations` for every request they confirmed (not just requests they created), or alternatively re-validate every string in a request's `confirmations` set against the current `members` set at the time of the quorum check in `confirm()`, discarding stale entries before comparing against `num_confirmations`.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
