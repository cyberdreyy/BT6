### Title
Queued BB deposits in prefunded mode are accepted but can never be processed — funds silently sit in the queue without ever entering the vault - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external bug class is "an interface accepts a user action but never forwards it to the processing layer, so the action silently never takes effect" (LES `SendTx` drops the sequencer forwarding). The idle-tranches analog lives in `IdleCDOEpochQueue`: when the CDO is the prefunded variant with the queue enabled, `requestDeposit` still accepts underlying tokens for the **BB tranche queue**, but every processing path for that queue is unreachable — `processDeposits` is disabled whenever prefunding is enabled, and `processDepositsToBorrower` is AA-only. The deposit succeeds from the user's point of view (tokens pulled, request recorded) but is never converted into tranche tokens — exactly the "accepted but never forwarded" shape of the LES issue.

### Finding Description
`requestDeposit` pulls `underlying` from the user and records `userDepositsEpochs[msg.sender][nextEpoch]` / `epochPendingDeposits[nextEpoch]` for `epochNumber() + 1` [1](#0-0) . The prefunded-mode gate (deposit cutoff + `checkPrefunding`) is applied **only** for the AA tranche queue (`tranche == _cdo.AATranche()`), so BB queue deposits are accepted unconditionally while the epoch is running [2](#0-1) .

However, the only two ways queued deposits become real deposits are both dead ends for a BB queue in prefunded mode:

1. `processDeposits()` — the legacy buffer-period path that calls `_cdo.depositBB(_pending)` — hard-reverts whenever the prefunded flow is enabled on the CDO: `_checkNotAllowed(_isPrefundedQueueEnabled())` [3](#0-2) .
2. `processDepositsToBorrower()` — the prefunded path — hard-reverts for any queue whose `tranche != _cdo.AATranche()` [4](#0-3) .

The final settlement hook `processPrefundedDeposits` is also AA-only and callable only by the CDO itself [5](#0-4) .

The same asymmetry exists for AA queue deposits made *before* the prefunding window: they are accepted, but if `checkPrefunding` can never pass (emergency state, TVL cap hit, zero AA price — see `testZeroAAPriceCannotBecomeNonCancellablePrefund`), they too can never be processed, and `stopEpoch` on the prefunded variant reverts while `epochPendingDeposits != 0` [6](#0-5) .

### Impact Explanation
A BB-tranche lender (KYC-passing, unprivileged) who calls `requestDeposit` on the BB queue of a prefunded deployment has their underlying pulled and a deposit request recorded, but no code path — privileged or otherwise — can ever convert that request into tranche tokens. The deposit "succeeds" from a UX standpoint while never entering the vault, mirroring the LES issue where the transaction appears submitted but never reaches the sequencer. Additionally, for the AA queue, stranded `epochPendingDeposits` block `stopEpoch` entirely (revert in `processPrefundedDeposits`), which can delay epoch finalization until requests are individually deleted. The only user recourse is `deleteRequest`, which remains available because `epochPrice[_requestEpoch]` is never set [7](#0-6) , so the impact is temporary freezing and silently-failed deposit rather than permanent loss — the same severity class as the original medium finding.

### Likelihood Explanation
Any prefunded-variant deployment that keeps the BB queue's `requestDeposit` reachable exposes the path: the user needs only a standard queued deposit while the epoch is running. No privileged misbehavior is required; the honest owner/manager simply has no function they can call to settle the BB queue. The stuck-epoch variant requires only that AA pending deposits exist when prefunding is no longer permitted (e.g., emergency flag raised while deposits were queued), which is a realistic sequencing.

### Recommendation
Mirror the LES fix ("match the RPC change in the other backend"): align `requestDeposit` gating with the actual processing capabilities. Concretely: revert in `requestDeposit` for BB queues when `_isPrefundedQueueEnabled()` is true (or route BB queued deposits through a supported settlement path), and make `stopEpoch` tolerate un-prefundable pending AA deposits — e.g., auto-refund them or allow skipping them — instead of reverting via `processPrefundedDeposits` when `epochPendingDeposits != 0`.

### Proof of Concept
Foundry-style scenario (extend `test/foundry/IdleCDOEpochQueue.t.sol` patterns such as `testProcessDepositsToBorrowerRevertsForBBQueue` [8](#0-7) ):

```solidity
function testBBQueueDepositAcceptedButNeverProcessed() external {
    // prefunded CDO variant with AA queue enabled (existing setup)
    vm.prank(manager);
    IdleCDOEpochVariantPrefunded(address(cdoEpoch)).setEpochQueue(address(queue));

    // deploy + init a BB tranche queue on the same prefunded CDO
    IdleCDOEpochQueue bbQueue = new IdleCDOEpochQueue();
    bbQueue.initialize(address(cdoEpoch), address(bbTranche), false); // BB tranche

    uint256 amount = 1e6;
    address user1 = makeAddr('user1');
    deal(address(underlying), user1, amount);

    // user deposit is ACCEPTED: underlying pulled, request recorded
    vm.startPrank(user1);
    underlying.approve(address(bbQueue), amount);
    bbQueue.requestDeposit(amount);              // succeeds — no prefunded gate for BB
    vm.stopPrank();
    assertEq(bbQueue.epochPendingDeposits(strategy.epochNumber() + 1), amount);

    // Path 1: legacy processing is disabled in prefunded mode
    _stopCurrentEpoch();
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    bbQueue.processDeposits();                    // _isPrefundedQueueEnabled() -> revert

    // Path 2: prefunded path is AA-only
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    bbQueue.processDepositsToBorrower();          // tranche != AATranche -> revert

    // Deposit is stranded: epochPrice is never set, no tranche tokens are ever minted.
    // User's only option is deleteRequest — the deposit silently never entered the vault.
    uint256 balPre = underlying.balanceOf(user1);
    vm.prank(user1);
    bbQueue.deleteRequest(strategy.epochNumber() + 1);
    assertEq(underlying.balanceOf(user1) - balPre, amount);
}
```

**Caveat on severity:** because `epochPrice` is never set, `deleteRequest` remains open, so the loss is bounded to silent failure plus temporary freezing (recoverable by an attentive user), not permanent loss. If the audit bar requires unrecoverable theft/insolvency, this analog is weaker than the original medium; it is nonetheless the closest match to the "accepted but never forwarded" bug class in the codebase, and the AA-queue variant additionally blocks `stopEpoch` while stranded pending deposits exist.

  function deleteRequest(uint256 _requestEpoch) external {
    // if the epoch price is already set, deposits were already processed so
    // the deposit request can't be deleted.
    _checkNotAllowed(epochPrice[_requestEpoch] != 0 || epochPrefundedDeposits[_requestEpoch] != 0);

    uint256 amount = userDepositsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user deposit for the epoch
    userDepositsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending deposits
    epochPendingDeposits[_requestEpoch] -= amount;
    // transfer underlyings back to the user
