Based on the code I was able to retrieve, both `multisig/src/lib.rs` and `multisig2/src/lib.rs` exhibit the same structural gap that the report's "join after game started" bug class maps onto: **confirmations recorded against a request are never invalidated when the confirming member/key is later removed**, so a stale confirmation can still count toward the threshold even though it no longer represents a "live" signer.

### Title
Stale confirmations from removed members/keys still count toward `num_confirmations` threshold - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
`confirm()` in both `multisig/src/lib.rs` [1](#0-0)  and `multisig2/src/lib.rs` [2](#0-1)  only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, comparing the *count of stored confirmations* against the threshold, without re-validating that every previously-stored confirmer is still a current key/member. When `MultiSigRequestAction::DeleteKey` (v1) or `MultiSigRequestAction::DeleteMember` (v2) is executed, the code only purges **requests originated by** the removed key [3](#0-2) , but it does **not** scan and strip that key's confirmations from other, still-open requests that it had already confirmed.

### Finding Description
The intended invariant is: `confirmations counted == confirmations by currently-live members`. The actual state can diverge: a request can retain a confirmation from a key/member that has since been deleted via a separate, already-executed `DeleteKey`/`DeleteMember` request. When a subsequent live signer confirms, `confirmations.len() + 1 >= num_confirmations` can become true and the request executes, even though the number of *currently valid* confirmers is one less than `num_confirmations`.

### Impact Explanation
This lets a request execute below the intended `num_confirmations` threshold, i.e. "a multisig request executed below threshold" — explicitly one of the listed Critical impacts. This can be used to move funds, add/delete keys, or deploy contracts with fewer independently-authorized approvals than the account owner configured, directly breaking the multisig custody guarantee.

### Likelihood Explanation
Requires: (1) an open request with at least one confirmation, (2) that confirmer's key/membership later removed via a separate `DeleteKey`/`DeleteMember` request, (3) the first request never deleted/cleared. Since key rotation/removal is a normal multisig operation and requests can remain open for a period (`REQUEST_COOLDOWN`), this is a realistic sequence achievable by the multisig's own members without any external attacker, foundation, or victim key needed for the removal step itself — only the earlier confirmer's key needs to have been removed by ordinary multisig operation.

### Recommendation
When executing `DeleteKey` (v1) / `DeleteMember` (v2), also scan `self.confirmations` for all open requests and remove the deleted key/member's entry, or alternatively re-validate at `confirm()` time that every entry in the stored confirmation set still corresponds to a live key/member before counting it toward the threshold.

### Proof of Concept
Not independently verified in this pass — I was unable to re-fetch the full `execute_request`/`DeleteKey`/`DeleteMember` handlers on the final iteration due to a tool error, so I could not 100% confirm the absence of a cleanup pass over `self.confirmations` for non-originating requests. Based on the code previously retrieved [3](#0-2)  and [4](#0-3) , the `DeleteKey`/`DeleteMember` handlers only remove requests whose `signer_pk`/`member` equals the deleted key/member — they do not iterate `self.confirmations` to strip that key from confirmation sets of other open requests. This should be verified directly in the repository (e.g., by starting a full Devin session with file access) to confirm no such cleanup exists elsewhere before treating this as conclusively proven.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
