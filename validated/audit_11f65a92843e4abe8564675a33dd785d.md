### Title
`StatusCache` truncates 32/64-byte transaction keys to a 20-byte slice, allowing signature/status collisions to be returned by `getSignatureStatuses` — (File: `runtime/src/status_cache.rs`)

### Summary
`StatusCache` — the structure backing `Bank::get_signature_status_slot()` and thus the `getSignatureStatuses` / `getSignatureStatus` JSON-RPC methods — stores and looks up transaction status entries using only the first `CACHED_KEY_SIZE = 20` bytes of the 64-byte `Signature` (or 32-byte message hash), not the full key.

### Finding Description
`StatusCache::insert()` and `StatusCache::get_status()` both truncate the caller-supplied key to a fixed 20-byte slice before using it as a `HashMap` key: [1](#0-0) [2](#0-1) [3](#0-2) 

For any newly-created blockhash bucket, `key_index` is always initialized to `0`: [4](#0-3) 

meaning the lookup key is effectively bytes `[0..20)` of the 64-byte transaction `Signature` for that blockhash. `Bank::get_signature_status_slot()` calls `get_status_any_blockhash`, which iterates every known blockhash bucket and returns the first status whose 20-byte prefix matches: [5](#0-4) 

This value flows directly into the RPC-visible `getSignatureStatuses` handler: [6](#0-5) [7](#0-6) 

Because only the leading 20 bytes are compared, any two 64-byte values sharing the same first 20 bytes are indistinguishable to the cache — this is the exact truncated-hash "pigeonhole" pattern the external report describes for the 256-bit→160-bit address truncation. Here the truncation is even more direct: real transaction signatures are public (visible in blocks, on explorers, via `getConfirmedSignaturesForAddress2`, etc.), so an attacker does not need to search for a collision at all — they can take any legitimate, already-processed signature `S`, keep its first 20 bytes, and replace the remaining 44 bytes with anything they want to form a forged 64-byte value `S'`. The `getSignatureStatuses` RPC input path only base58-decodes the string into a fixed-length signature without validating it cryptographically against any message, so `S'` is accepted as a normal query argument.

### Impact Explanation
Querying `getSignatureStatuses`/`getSignatureStatus` with the forged signature `S'` causes `get_status_any_blockhash` to match the 20-byte prefix and return the slot/confirmation/error status that actually belongs to the original transaction identified by `S`, not to `S'`. This is a "wrong data returned for a query" condition: an unprivileged RPC client receives a `TransactionStatus` (slot, confirmations, error) for a signature it never actually knew/derived correctly, degrading the integrity of one of the most commonly relied-upon RPC endpoints for confirming transaction landing/finality. Any downstream tooling (wallets, bridges, exchanges) that polls `getSignatureStatuses` to confirm a specific transaction could be misled into believing an unrelated transaction's status applies to the signature they submitted, e.g. reporting a transfer as "confirmed"/"finalized" via a colliding value.

### Likelihood Explanation
No brute-force birthday search is even required in the common case, since legitimate signatures are public; an attacker only has to copy 20 bytes and can freely vary the other 44. This is reachable with a single, ordinary `getSignatureStatuses` RPC call by any unprivileged client, requiring no special permissions, mocked components, or multi-request DoS budget.

### Recommendation
Use the full key (entire signature or full message hash) as the `HashMap` key in `StatusCache`, or at minimum increase `CACHED_KEY_SIZE` to the full 32/64 bytes so no truncation-induced collision is possible, removing reliance on a partial-byte comparison for consensus/RPC-critical status lookups.

### Proof of Concept
1. Observe any confirmed transaction's signature `S` (public, e.g., from `getConfirmedSignaturesForAddress2` or a block explorer).
2. Construct `S' = S[0..20] || random_44_bytes`, base58-encode it.
3. Call JSON-RPC `getSignatureStatuses(["S'"])` against the validator.
4. `Bank::get_signature_status_slot` → `StatusCache::get_status_any_blockhash` finds the bucket entry keyed by `S[0..20]` (inserted for the real transaction) and returns its slot/status, which the RPC layer serializes as the status for `S'` even though `S'` was never processed.
