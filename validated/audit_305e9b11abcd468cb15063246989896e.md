### Title
A single queued prefunded deposit above the guarded-launch cap permanently bricks `stopEpochWithDuration`, locking all pool funds at the borrower - ([File: contracts/IdleCDOEpochQueue.sol])

### Summary
In the prefunded variant, `stopEpoch` is disabled and `stopEpochWithDuration` unconditionally calls `prefundedDepositsToProcess()`, which reverts while `epochPendingDeposits[nextEpoch] != 0`. The only way to clear that pending amount is `processDepositsToBorrower()`, which forwards the *entire* pending balance to the borrower and first enforces `checkPrefunding(_pending)` — including the guarded-launch TVL cap. A KYC-passing lender can queue a deposit that pushes the pending total over the cap (or simply ensure pending stays nonzero and unprefundable), making every subsequent `stopEpochWithDuration` revert. The epoch can never be stopped or closed, so principal already lent to the borrower can never be recalled — a permanent freeze of the whole pool.

### Finding Description
`IdleCDOEpochVariantPrefunded._beforeStopEpoch` reverts whenever `msg.sig == this.stopEpoch.selector` and a queue is configured, so `stopEpochWithDuration` is the only stop path [1](#0-0) . At the end of that path, `_afterStopEpochWithDuration` calls `queue.prefundedDepositsToProcess()` [2](#0-1) , which reverts if `epochPendingDeposits[epoch] != 0` [3](#0-2) . Clearing pending requires `processDepositsToBorrower()`, which calls `checkPrefunding(_pending)` — reverting on `defaulted`, `priceAA == 0`, or the guarded-launch limit via `_guarded(_amount)` [4](#0-3) [5](#0-4) . Any user passing `isWalletAllowed` (Keyring KYC) can call `requestDeposit` while the epoch is running [6](#0-5) .

### Impact Explanation
If an attacker leaves a pending deposit that cannot be prefunded (e.g., pushes aggregate pending above the guarded-launch cap, or keeps pending nonzero when `priceAA == 0`/after partial-loss pause), `stopEpochWithDuration` always reverts and `stopEpoch` is blocked. The borrower-side principal is never recallable because `getFundsFromBorrower` is only reachable through the stop flow. All LP funds in the epoch are permanently locked; the attacker's only cost is their own queued deposit, which they can later retrieve via `deleteRequest` only if the pool is ever unbricked — but their lock alone keeps `epochPendingDeposits != 0` forever. This mirrors the source bug: the protocol can advance into a state where a required settlement step was never performable, and no recovery path exists.

### Likelihood Explanation
Requires only a KYC-passing lender (explicitly in-scope) and one `requestDeposit` during a running epoch on a prefunded-variant pool with a configured queue. No privileged cooperation and no borrower default needed. The guardrail gap is structural: there is no partial-prefunding path, no manager-side eviction of a queued deposit, and no way to unset `epochQueue` safely (changing it strands prefunded bookkeeping, per the contract's own invariant comment at `setEpochQueue`).

### Recommendation
Allow `stopEpochWithDuration` to settle epochs even with queue-held pending deposits — e.g., refund `epochPendingDeposits` back to users (pro-rata `deleteRequest`-style) inside the stop flow, or let `processDepositsToBorrower` prefund a capped subset / let the manager force-refund individual queued deposits. Additionally, `requestDeposit` should enforce `checkPrefunding` against a cap headroom so a single deposit cannot push pending over the guarded limit, and `setEpochQueue` should be blocked while any `epochPendingDeposits`/`epochPrefundedDeposits` are nonzero.

function testPendingQueueDepositOverCapPermanentlyBlocksStopEpoch() external {
    // attacker is a KYC'd lender
    address attacker = makeAddr('attacker');
    _whitelist(attacker);

    vm.prank(manager);
    cdoEpoch.setEpochQueue(address(queue));
    vm.prank(manager);
    queue.setPrefundedDepositWindow(PREFUNDED_DEPOSIT_WINDOW);

    // epoch running; attacker queues a deposit that makes
    // pending > guarded-launch cap (or any unprefundable state)
    uint256 amount = <amount exceeding _guarded headroom>;
    deal(address(underlying), attacker, amount);
    vm.startPrank(attacker);
    underlying.approve(address(queue), amount);
    queue.requestDeposit(amount);
    vm.stopPrank();

    // manager cannot prefund: checkPrefunding reverts (guarded cap)
    vm.prank(manager);
    vm.expectRevert(); // NotAllowed / guarded
    queue.processDepositsToBorrower();

    // borrower funds sit ready to repay, but the epoch can never stop
    uint256 toRepay = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
    deal(address(underlying), strategy.borrower(), toRepay);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), toRepay);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector)); // prefundedDepositsToProcess: pending != 0
    cdoEpoch.stopEpochWithDuration(0, 0, cdoEpoch.epochDuration(), 0);

    // direct stopEpoch selector is also blocked while queue is set
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // attacker never calls deleteRequest -> epochPendingDeposits stays nonzero forever;
    // borrower principal can never be recalled -> all LP funds permanently locked.
}
