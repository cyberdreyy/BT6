Based on my investigation, I found a concrete quota-bypass analog in the HTTP Trigger gateway path.

### Title
HTTP Trigger rate limit is scoped per-workflow-ID, not per-owner, allowing an attacker-controlled owner to bypass the intended request quota by registering multiple workflows - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The `checkRateLimit` function in the internet-facing gateway's HTTP trigger handler enforces a request-rate cap using `settings.ScopeWorkflow`, keyed by `workflowID`, even though the rate limiter is meant to bound how fast an owner/client can trigger workflow executions. Because the enforcement key is the individual workflow ID rather than the owner, a single unprivileged actor who controls (or registers) multiple `workflowID`s under the same `workflowOwner` gets an independent token bucket for each workflow, allowing them to multiply their effective throughput arbitrarily — mirroring the reported `MaviaToken` pattern where a per-single-unit cap is trivially bypassed by splitting activity across many "units" instead of tracking cumulative usage per actor.

### Finding Description
`checkRateLimit` builds the settings context using both `Owner` and `Workflow`: [1](#0-0) 

but the actual limiter (`userRateLimiter`, created via `lf.MakeRateLimiter(cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit)`) is explicitly documented and named as **PerWorkflow**: [2](#0-1) 

and the resulting limit-exceeded error reports `settings.ScopeWorkflow`, not `settings.ScopeOwner`: [3](#0-2) 

This is the same bug class as the `tfMaxAmount` issue: a limit is meant to constrain a single actor's total activity, but is actually enforced on a narrower unit (a single transfer / a single workflow) with no aggregation across units belonging to the same actor (owner). The documentation for the settings system explicitly confirms scopes resolve independently per workflow before falling back to owner/org/global (i.e., a workflow-scoped bucket is entirely separate from any owner-level bucket), reinforcing that no owner-level accumulation occurs for this particular limiter: [4](#0-3) 

By contrast, other quota mechanisms in the same codebase correctly aggregate per-owner (e.g., `syncerlimiter.NewWorkflowLimits`, which explicitly tracks both a `Global` and `PerOwner` resource pool and aggregates usage across all of an owner's workflows): [5](#0-4) 
This shows the codebase is aware of the owner-aggregation pattern elsewhere but does not apply it to the HTTP trigger request-rate limiter.

### Impact Explanation
An unprivileged, external HTTP-trigger client (an "unprivileged actor" invoking the internet-facing CRE HTTP trigger gateway) can bypass the intended per-owner rate limit entirely by registering N workflows under the same owner and round-robining requests across them, achieving N× the intended throughput. This can be used to overwhelm the DON/gateway/back-end nodes handling `MethodWorkflowExecute` requests, defeating the purpose of `PerWorkflow.HTTPTrigger.RateLimit` as an anti-abuse/DoS control at the gateway boundary, and puts additional unbounded load on the per-node and global rate limiters that are meant to be the secondary defense.

### Likelihood Explanation
Likelihood is moderate-to-high in environments where workflow registration is self-service for a given owner/org, since exploiting this requires no credential compromise — only registering additional workflows (a normal, permitted action) and directing HTTP trigger traffic at each one.

### Recommendation
Change the HTTP trigger request-rate limiter to key/aggregate by `workflowOwner` (or an owner+workflow combined scope, with the owner scope as the binding constraint) rather than by `workflowID` alone, consistent with how `syncerlimiter.NewWorkflowLimits` already aggregates `PerOwner` and `Global` limits. At minimum, add an owner-level `ResourcePoolLimiter`/rate limiter alongside the existing per-workflow one, similar to the two-tier design already used for workflow execution counts.

### Proof of Concept
1. As an unprivileged actor owning `workflowOwner = 0xA`, register workflow `W1` and workflow `W2` on the gateway (both legitimately permitted actions).
2. Send HTTP trigger requests (`MethodWorkflowExecute`) against `W1` until `checkRateLimit` returns `ErrLimitExceeded` for scope `ScopeWorkflow` (confirming `W1`'s bucket is exhausted), as demonstrated by the existing test `TestHttpTriggerHandler_HandleUserTriggerRequest_RateLimiting`: [6](#0-5) 
3. Immediately send the same volume of requests against `W2` (same owner `0xA`) and observe they succeed without being throttled, because `checkRateLimit` resolves a fresh, independent token bucket keyed to `W2`'s `workflowID` — demonstrating the owner-level cap is not actually cumulative and is trivially bypassed by adding workflows, analogous to bypassing `tfMaxAmount` via multiple sub-cap transfers.

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	// TODO orgID https://smartcontract-it.atlassian.net/browse/CRE-1707
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}
