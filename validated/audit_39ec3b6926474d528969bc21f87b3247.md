### Title
Mis-indexed `lossRecoveryPriceByEpoch` read lets loss-adjusted withdraw receipts claim at par, draining funded withdrawal reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the haircut ratio under `lossRecoveryPriceByEpoch[epochNumber]` *after* `deposit()` has already bumped `epochNumber`, while user receipts were recorded under the *request* epoch in `withdrawsRequestsByEpoch[_user][requestEpoch]` and `lastWithdrawRequest[_user]`. The claim path `_claimLossAdjustedWithdrawRequest` reads the mapping at `lastWithdrawRequest[_user]` (the old epoch), finds `0`, and silently skips the haircut — an off-by-one/mis-indexed storage read analogous to CVE-2022-2953's out-of-bounds read. The receipt is then paid in full by `_claimFundedWithdrawRequest`, paying out more than was funded.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 282, 293).
- `deposit()` increments `epochNumber` while `isEpochRunning()` is true, i.e. during `stopEpoch` (lines 607-610).
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (line 421) — keyed to the *new* epoch N+1, not the request epoch N.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` → `0` → returns early (lines 790-792).
- The requestWithdraw guard (lines 262-271) reads the same wrong index, so it also fails to enforce the "claim loss-adjusted receipt before requesting again" invariant.
- `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` at par (lines 338-349), even though only `_amount = pendingBasis - pendingLoss` was collected at line 428.

### Impact Explanation
Every user whose withdraw request is haircut by a `stopEpochWithDuration(_lossAmount)` loss receives their full pre-loss basis. The strategy only holds the funded (post-loss) amount, so early claimants drain underlying that should be shared pro-rata; later claimants' transfers revert (insolvency), or the deficit is absorbed by active LP-backed balances. This is direct theft of the haircut amount plus permanent freezing of remaining claims. Quantified loss = `pendingBasis - pendingToFund` per loss epoch (e.g., with 1000 USDC pending and a 20% loss allocation to receipts, claimants collectively extract the full 1000 USDC against only 800 funded).

### Likelihood Explanation
Any epoch stopped via `stopEpochWithDuration` with a non-zero loss and pending withdraw receipts triggers it — a normal (borrower shortfall) flow, no privileged misbehavior needed. The mis-indexed read is deterministic: `epochNumber` is always incremented before `collectWithdrawFunds` writes the haircut. No existing guard stops it: `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, the `lossRecoveryPrice` guard at lines 262-270 reads the same wrong index, and `pendingWithdraws` is already zeroed. Caveat: this assumes `collectWithdrawFunds` is invoked after the `deposit()` call that bumps `epochNumber` inside `stopEpoch`/`stopEpochWithDuration` in `IdleCDOEpochVariant.sol` (the standard ordering where interest/funds are deposited before pending withdrawals are collected); if the CDO calls it before the increment, the keys match and the bug does not manifest.

### Recommendation
Key the haircut by the epoch in which the receipts were requested, consistent with `lastWithdrawRequest[_user]` — e.g., store `lossRecoveryPriceByEpoch[epochNumber - 1]`, or write the entry before incrementing `epochNumber`. Alternatively, record the haircut against `lastWithdrawRequest` at request time. Add a fork test asserting a loss-adjusted receipt pays `claimBasis * lossRecoveryPrice / 1e18`, not par.

### Proof of Concept
```solidity
// Foundry fork PoC (concept, against existing harness helpers)
function testLossAdjustedReceiptPaysPar() external {
    uint256 amountWei = 10_000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);

    _startEpochAndCheckPrices(0);   // epoch N running
    _stopEpochAndCheckPrices(0, apr, expectedFunds); // epochNumber -> N+1

    // user requests withdraw during epoch N+1 buffer; lastWithdrawRequest = N+1... 
    // (request made while epochNumber == N+1? No: requests made at epoch N are the victims)
    // Simpler: request during running epoch N window where allowed, or buffer after stop of N-1.
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));

    _startEpochAndCheckPrices(1);
    // borrower returns only partial funds for pending receipts
    _stopEpochWithLoss(lossAmount); // internally: deposit() bumps epochNumber, collectWithdrawFunds(shortfall)

    // Stored at index epochNumber (N+2), but lastWithdrawRequest == request epoch.
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), 0);
    assertEq(strategy.lossRecoveryPriceByEpoch(strategy.lastWithdrawRequest(address(this))), 0); // mis-indexed read

    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    // BUG: paid full requested amount at par instead of haircut amount
    assertEq(underlying.balanceOf(address(this)) - balPre, requested);
}
```
The PoC asserts the stored haircut is unreachable from the user's request epoch and that the claim pays `requested` in full, exceeding the funded amount.
