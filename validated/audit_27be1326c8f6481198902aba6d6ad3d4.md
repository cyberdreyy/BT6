### Title
Stale-epoch instant-withdraw receipts are excluded from default recovery basis yet still claimed at par — recovery ratio inflated and old receipt permanently frozen - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`defaultPendingClaimBasis` decides whether unfunded instant-withdraw receipts exist by checking the aggregate counter `pendingInstantWithdraws` (the "header"), but then only adds `instantWithdrawClaimsByEpoch[epochNumber]` (the "tail") — instant receipt basis recorded for the *current* epoch. An unfunded instant receipt created in an earlier epoch contributes to `pendingInstantWithdraws` yet is never included in the recovery basis or reserve. After `finalizeDefaultRecovery`, that user's `claimInstantWithdrawRequest` pays the full `instantWithdrawsRequests` at par through `_transferFundedClaim`, whose reserve guard then reverts — permanently freezing the claim — while the recovery price seen by all other claimants was computed on a basis that omitted the stale receipt, overpaying them from `defaultRecoveryReserve`.

### Finding Description
The kernel bug checks `rsp` length only against the fixed header but reads a candidate struct at `buf + 20` whenever `candidate_cnt >= 1`. The analog here is the same shape: `defaultPendingClaimBasis` (contracts/strategies/idle/IdleCreditVault.sol:644-649) uses `pendingInstantWithdraws != 0` as the "count" signal that instant claims exist, but unconditionally reads `instantWithdrawClaimsByEpoch[epochNumber]` — the tail — without checking that the pending receipts were actually recorded in `epochNumber`:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

`requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (lines 367-374). `epochNumber` is bumped in `deposit`/`stopEpoch` (line 610). `collectInstantWithdrawFunds` can partially fund the queue, leaving `pendingInstantWithdraws > 0` while the claims remain keyed to the old epoch.

At default finalization (lines 685-696):
- `_defaultPrefundedInstantReserve` (lines 716-723) likewise only looks at `instantWithdrawClaimsByEpoch[epochNumber]`, so already-collected funding for a stale-epoch receipt is not counted as reserve.
- `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` is true, but `defaultRecoveryEpoch` is the new `epochNumber`, so `_claimDefaultedInstantWithdrawRequest` (line 844) reads `instantWithdrawsRequestsByEpoch[user][newEpoch] == 0` and clears nothing.
- `claimInstantWithdrawRequest` (lines 380-393) then burns and pays the entire `instantWithdrawsRequests[_user]` — including the unfunded defaulted-epoch portion — via `_transferFundedClaim`. Since the unfunded part has no backing outside `defaultRecoveryReserve`, the guard at line 904 (`balance - reserve < _amount`) reverts, freezing the claim forever. There is no other path to clear `instantWithdrawsRequests`.

Meanwhile `totalBasis` excluded the stale instant basis, so `recoveryPrice` (line 688) is inflated: every other defaulted-epoch claimant (an attacker EOA can hold such a receipt) drains more than its pro-rata share of `defaultRecoveryReserve` before the frozen victim can ever claim.

### Impact Explanation
Two impacts from one missing per-epoch check:

1. Theft of recovery funds: recovery price is computed on a basis that omits stale-epoch instant claims, so the reserve is distributed over a smaller denominator. An attacker holding a normal defaulted-epoch withdraw receipt claims an inflated amount; on a 100k reserve with 90k normal basis + 10k stale instant basis, claimants receive ~10% more than fair share.
2. Permanent freezing: the stale-epoch instant receipt can never be claimed — `_claimDefaultedInstantWithdrawRequest` clears nothing (wrong epoch key) and `_transferFundedClaim` reverts once the non-reserve balance is insufficient. The user's receipt and any prefunded backing are stuck in the strategy permanently.

### Likelihood Explanation
Requires: (a) an instant withdraw request that is only partially funded by `collectInstantWithdrawFunds`, leaving `pendingInstantWithdraws > 0`; (b) `epochNumber` incremented (any `stopEpoch` + `deposit` path) before (c) borrower default and `finalizeDefaultRecovery`. Partial instant funding and epoch rollover are normal protocol operations (buffer/stop phases), and the trigger sequence uses only honest manager/borrower calls plus the attacker's own withdraw request. The attacker role is an unprivileged KYC'd tranche holder / withdraw requester, which is in scope.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, aggregate instant claim basis across all epochs with outstanding receipts rather than only `epochNumber` — e.g., track a global `instantWithdrawClaims` total alongside the per-epoch map, or store the epoch of each pending instant receipt. Alternatively, in `_claimDefaultedInstantWithdrawRequest`, fall back to clearing `instantWithdrawsRequests[_user]` at `defaultRecoveryPrice` whenever `defaultInstantWithdrawsFinalized` is set and the per-epoch entry is empty, so stale-epoch receipts are haircutted rather than paid at par or frozen.

### Proof of Concept
Foundry fork PoC sketch against `IdleCDOEpochVariant` + `IdleCreditVault`:

```solidity
function testStaleEpochInstantReceiptFrozenAndRecoveryInflated() external {
    // 1. Attacker (KYC'd AA holder) deposits; victim also deposits.
    idleCDO.depositAA(100_000 * ONE_SCALE);

    // 2. Epoch 0 runs; victim requests instant withdraw of 10_000.
    _startEpochAndCheckPrices(0);
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(10_000 * ONE_SCALE, address(aaTranche));
    // instantWithdrawClaimsByEpoch[0] = 10k, pendingInstantWithdraws = 10k

    // 3. stopEpoch funds only part of the instant queue:
    //    CDO calls collectInstantWithdrawFunds(6_000) -> pendingInstantWithdraws = 4_000
    //    epochNumber bumps to 1 on the stopEpoch deposit path.
    _stopEpochPartialInstantFunding(6_000 * ONE_SCALE);

    // 4. Epoch 1: borrower defaults. finalizeDefaultRecovery runs:
    //    pendingInstantWithdraws=4k (header non-zero) but
    //    instantWithdrawClaimsByEpoch[1] == 0 (missing tail for epoch 1)
    //    -> basis excludes victim's 4k unfunded + 6k prefunded receipt;
    //    recoveryPrice computed on smaller totalBasis.
    _defaultAndFinalize(recoveredAmount);

    // 5. Attacker's defaulted-epoch withdraw receipt claims inflated amount:
    uint256 attackerClaim = strategy.previewClaim(attacker);
    assertGt(attackerClaim, fairShare); // overpaid from defaultRecoveryReserve

    // 6. Victim claim reverts: _claimDefaultedInstantWithdrawRequest clears
    //    byEpoch[1] == 0, then _transferFundedClaim reverts at line 904
    //    because non-reserve balance < instantWithdrawsRequests[victim].
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimInstantWithdrawRequest();
    // victim's 10k receipt (6k prefunded in strategy + 4k unfunded) frozen forever.
}
```

The PoC requires confirming the exact partial-funding path in `IdleCDOEpochVariant.collectInstantWithdrawFunds` wiring and that `epochNumber` increments between the instant request and default finalization; both follow from `deposit()` at line 607-610 and the per-epoch keying at lines 371-372.
