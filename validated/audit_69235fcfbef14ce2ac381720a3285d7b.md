### Title
`jsonAPIError` leaks raw internal error text (including wrapped "finding external initiator" DB errors) in unauthenticated 401 responses - ([File: core/web/auth/auth.go])

### Summary
`Authenticate` returns non-`ErrorAuthFailed` errors from `AuthenticateByToken` and `AuthenticateExternalInitiator` directly to `jsonAPIError`, which serializes `err.Error()` verbatim into the JSON response body sent to the unauthenticated caller. Any non-`sql.ErrNoRows` failure from `FindUserByAPIToken` or `FindExternalInitiator` (e.g., a DB connectivity error, malformed row, driver error) is thus echoed back to the client, including the `errors.Wrap(err, "finding external initiator")` message which embeds the underlying driver/SQL error text.

### Finding Description
In `core/web/auth/auth.go`, `AuthenticateByToken` (lines 93-99) only converts `sql.ErrNoRows`/`ErrUserSessionExpired` to the generic `auth.ErrorAuthFailed`; any other error from `FindUserByAPIToken` is returned as-is [1](#0-0) . Similarly, `AuthenticateExternalInitiator` (lines 126-133) wraps any non-`sql.ErrNoRows` error from `FindExternalInitiator` with `errors.Wrap(err, "finding external initiator")` and returns it [2](#0-1) .

`Authenticate` (lines 157-175) propagates this error unchanged to `jsonAPIError(c, http.StatusUnauthorized, err)` when it is not `auth.ErrorAuthFailed` [3](#0-2) . `jsonAPIError`, defined in `core/web/auth/helpers.go`, calls `err.Error()` and writes it directly into the JSON body via `models.NewJSONAPIErrorsWith(err.Error())` with no redaction [4](#0-3) .

This means any underlying store/driver error (context deadline exceeded, connection refused, malformed data, a future ORM implementation that surfaces raw SQL text) reaches the unauthenticated caller verbatim, and for the external-initiator path the static prefix "finding external initiator" is always disclosed too, confirming implementation details of the code path being probed.

However, note the actual `AccessKey`/`Secret`/email values submitted by the attacker are never included in these error paths — `FindUserByAPIToken`/`FindExternalInitiator` errors are DB-layer errors, not comparisons against the submitted token, so this does not leak whether a specific `AccessKey` exists (the `sql.ErrNoRows` case, which is the "does this exist" case, is already normalized to the generic `auth.ErrorAuthFailed`).

### Impact Explanation
This is a low-severity information disclosure: an unauthenticated attacker can potentially learn transient backend/DB error strings (e.g., internal error text, wording that reveals the ORM layer or the "finding external initiator" code path) during outages or edge-case failures. It does not, by itself, reveal whether a specific access key/API token exists (that case is already normalized to `ErrorAuthFailed`), nor does it expose secrets, tokens, or another user's data. It falls short of the bounty's core impact classes (auth bypass, credential disclosure, privilege escalation) since the only leaked errors are non-existence-independent DB/driver failures, not existence-revealing branch differences.

### Likelihood Explanation
Triggering this requires the backend `FindUserByAPIToken`/`FindExternalInitiator` calls to fail with something other than `sql.ErrNoRows` (e.g., a real DB outage, timeout, or driver-level failure) — this is not attacker-controllable through normal token/header manipulation, since `sql.ErrNoRows` is the deterministic result of supplying a non-existent `AccessKey`. No credential or role is needed to send the request, but the vulnerable branch is only reachable during genuine backend errors, not through crafted attacker input, making exploitation for enumeration purposes infeasible.

### Recommendation
In `AuthenticateByToken` and `AuthenticateExternalInitiator`, log the underlying error server-side and return a generic error (or `auth.ErrorAuthFailed`) to the caller instead of propagating the raw/wrapped error into `jsonAPIError`. Alternatively, have `Authenticate` map any error that isn't `auth.ErrorAuthFailed` to a fixed generic message before calling `jsonAPIError`, while still logging full details via `c.Error(err)` for operators.

### Proof of Concept
Go handler-level integration test:
1. Construct a fake `Authenticator` whose `FindExternalInitiator` returns a non-`sql.ErrNoRows` error, e.g. `errors.New("dial tcp: connection refused")`.
2. Build a `gin.Engine` with `Authenticate(fakeAuthr, AuthenticateExternalInitiator)` as middleware wrapping a no-op handler.
3. Send an HTTP request with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers set to arbitrary values.
4. Assert HTTP status is 401 and assert the JSON body's `errors[0].detail` contains `"finding external initiator: dial tcp: connection refused"`.
5. Repeat with `FindUserByAPIToken` returning a non-`ErrNoRows` error (e.g., a wrapped DB error) for `AuthenticateByToken`, and assert the raw error text appears in the response body.
6. Expected (current, vulnerable) result: raw internal error text is present in the response; expected (fixed) result: response body contains only a generic message such as `"Unauthorized"`.

```go
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
