### Title
Unregistered/opted-out shareholder can block `vesting::distribute()` for all other shareholders - ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`vesting::distribute()` pays out pending rewards/vested tokens to every shareholder (or their beneficiary) of a vesting contract in a single transaction via `aptos_account::deposit_coins`. `deposit_coins` aborts if the recipient has not registered for `AptosCoin` and has explicitly opted out of unregistered direct transfers via `aptos_account::set_allow_direct_coin_transfers(false)` [1](#0-0) . The framework authors were aware of this exact failure mode: the `set_beneficiary` function comment states the registration check "is a requirement so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered" [2](#0-1) , and accordingly calls `assert_account_is_registered_for_apt(new_beneficiary)` before accepting a new beneficiary [2](#0-1) .

However, this check only fires along the `set_beneficiary` admin path. The default beneficiary for any shareholder is the shareholder itself, set at `create_vesting_contract` time from the caller-supplied `shareholders`/`buy_in` lists [3](#0-2) , without any equivalent `assert_account_is_registered_for_apt` gate on those addresses. Any shareholder fully controls their own `DirectTransferConfig` via the permissionless `aptos_account::set_allow_direct_coin_transfers` entry function [4](#0-3) , which can be toggled at any time after the vesting contract is created.

### Finding Description
`distribute()` in `vesting.move` is intentionally permissionless ("Allow anyone to distribute already unlocked funds...does not need to be restricted") and pays out to all shareholders of a `VestingContract` in one call, using `staking_contract`'s underlying distribution pool and `aptos_account::deposit_coins` for the transfer step. `deposit_coins` will `abort` with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if:
1. The recipient account is not yet registered for `AptosCoin`, and
2. The recipient has called `set_allow_direct_coin_transfers(false)` on their own account [1](#0-0) .

Because a vesting-contract shareholder is by default their own beneficiary (no `set_beneficiary` call is required, and thus no `assert_account_is_registered_for_apt` gate is ever applied to them), any shareholder can leave their account unregistered for `AptosCoin` and flip `allow_arbitrary_coin_transfers` to `false`. When `distribute()` is subsequently invoked (by anyone, since it's permissionless) for the shared vesting contract, the attempt to pay that one shareholder aborts the entire transaction, reverting distribution to *every other* shareholder sharing that vesting contract's `grant_pool`.

### Impact Explanation
This blocks the reward/vested-token claim rights of all honest co-shareholders in a multi-shareholder vesting contract, indefinitely, at the sole discretion of one uncooperative shareholder — with no way for the admin or other shareholders to route around it, since `distribute()` has no per-shareholder try/catch or skip-on-failure logic (based on the documented rationale in `set_beneficiary`, this appears to be a known systemic risk of the payout design). This matches the "Permanent lock or non-recoverable loss of claim rights in ... vesting flows" impact category: an unprivileged party can strand value belonging to other, non-consenting participants.

### Likelihood Explanation
Likelihood is High for any vesting contract with multiple shareholders sharing a single grant pool: `set_allow_direct_coin_transfers` is a permissionless entry function callable by any account on itself at any time, requires no special privilege, and the attacker need not register for `AptosCoin` beforehand (the default state). Any shareholder who is unhappy, adversarial, or bribed by a competing party has a trivial, cheap, repeatable griefing vector against all other shareholders of the same contract.

### Recommendation
- Apply the same `assert_account_is_registered_for_apt` (or an equivalent check that tolerates opted-out accounts) to every shareholder address at `create_vesting_contract` time, not just when `set_beneficiary` is called.
- More robustly, change `distribute()`/`distribute_internal()` to isolate failures per-recipient (e.g., catch/skip a failing deposit and leave that shareholder's share pending) so that one recipient's account configuration cannot block payouts to others — mirroring the fix pattern used in the original Bull-vs-Bear report (isolate the failure-prone external transfer instead of letting it abort the whole flow).

### Proof of Concept
1. Admin creates a vesting contract with shareholders `[Alice, Bob]` via `vesting::create_vesting_contract`, where neither has set a custom beneficiary. Bob's account has never registered for `AptosCoin`.
2. Bob calls `aptos_account::set_allow_direct_coin_transfers(bob_signer, false)`.
3. Vesting period elapses; the pool accrues rewards/vested tokens for both Alice and Bob.
4. Anyone calls `vesting::distribute(contract_address)`.
5. When the payout loop reaches Bob, `aptos_account::deposit_coins<AptosCoin>(bob_address, coins)` hits `!coin::is_account_registered<AptosCoin>(bob_address)` and `!can_receive_direct_coin_transfers(bob_address)`, causing `abort EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The entire `distribute()` transaction reverts, and Alice (and any other shareholders) cannot receive their already-vested/reward funds as long as Bob keeps his config set this way — despite `distribute()` being documented as callable by "anyone."

*(Note: I could not directly inspect the exact loop body of `distribute_internal` due to tool/index truncation, so the exact statement ordering is inferred from the documented rationale in `set_beneficiary` and the mechanics of `aptos_account::deposit_coins`. Recommend verifying the precise iteration logic in a full-repo session before remediation.)*

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
