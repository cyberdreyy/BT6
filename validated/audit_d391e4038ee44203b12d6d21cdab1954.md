### Title
Deterministic-address account creation (`CreateAccount`/`CreateAccountWithSeed`) can be griefed via front-run pre-funding, causing `AccountAlreadyInUse` DoS - (File: `programs/system/src/system_processor.rs`)

### Summary
The Sherlock finding describes a front-running class where an attacker races a deterministic-address creation call (`cloneDeterministic`) so that when the legitimate `createStream()` transaction lands, initialization is blocked because the target address is already "occupied." The analogous primitive in Agave is the System Program's account-creation instructions, which derive the destination address deterministically (`Pubkey::create_with_seed`) or otherwise rely on the caller supplying a specific `to` pubkey, and which unconditionally reject creation if the destination account is observed to already hold lamports.

### Finding Description
`Address::create` re-derives `to_address` from `(base, seed, owner)` for `CreateAccountWithSeed`/`AllocateWithSeed`/`AssignWithSeed`, so any observer who knows `base`, `seed`, and `owner` (all of which must typically be public/predictable for CLI/dApp flows such as nonce accounts, stake accounts, or seeded PDAs) can compute the exact target address in advance. [1](#0-0) 

The `create_account` handler, used by both `SystemInstruction::CreateAccount` and `SystemInstruction::CreateAccountWithSeed`, checks whether the destination account already has `lamports > 0` and, if so, unconditionally fails the instruction with `SystemError::AccountAlreadyInUse`, before any ownership/authorization semantics are considered: [2](#0-1) 

Because this is a pure lamports-balance check (not an ownership or data check), any unprivileged party can grief the target address by simply sending it a `system_instruction::transfer` for 1 lamport before the legitimate creator's transaction lands. Once the account has any lamports, the legitimate `CreateAccount`/`CreateAccountWithSeed` transaction unconditionally fails with `AccountAlreadyInUse`, exactly mirroring the reported bug class where a front-runner deploys to a deterministic address ahead of the intended actor, blocking correct initialization.

This is directly reachable from ordinary user transactions/CLI flows that rely on deterministically-derived destination addresses, e.g. nonce-account creation and stake-account creation with a seed: [3](#0-2) [4](#0-3) 

Notably, the codebase already contains a mitigation for a related scenario — `create_account_allow_prefund`, added specifically to permit account creation even when the account has been pre-funded — but this alternate path is only reachable through specific instruction variants (e.g. loader/program-account creation paths), not through the general-purpose `CreateAccount`/`CreateAccountWithSeed` instructions used by ordinary transfers, nonce accounts, or stake accounts: [5](#0-4) 

### Impact Explanation
An attacker who observes an in-flight (or simply predicts, since `create_with_seed` is deterministic and inputs are often public) `CreateAccount`/`CreateAccountWithSeed` transaction can pre-fund the destination address with a negligible lamport transfer. This causes the legitimate account-creation transaction to fail on-chain with `AccountAlreadyInUse`, denying the user's intended state initialization (e.g., a nonce account, stake account, or any protocol-level PDA/seeded account created through the System Program). Unlike the original report where the griefed protocol became permanently "useless" because the deterministic address can never be reused, here the impact is bounded to denial-of-service/griefing of specific creation transactions — the victim can choose a new seed/nonce and retry — but any protocol or off-chain integration that depends on a *fixed*, publicly-derivable seed (no per-attempt randomness) for its account address is permanently blocked at that address, matching the "protocol becomes useless" severity from the original report.

### Likelihood Explanation
Likelihood is high for any flow using a fixed/predictable seed and low-value victim transactions relayed through the public transaction ingest path (QUIC/RPC), since front-running requires only observing the pending transaction (or predicting its seed) and submitting a cheap 1-lamport transfer to the derived address before the legitimate transaction is committed. No special privileges, precompiles, or validator-internal access are needed — an ordinary user transaction suffices.

### Recommendation
For flows that must guarantee successful creation, use the `CreateAccountAllowPrefund`/`create_account_allow_prefund` instruction path (or ownership/state validation rather than a strict `lamports == 0` check) wherever the destination address is derived deterministically and publicly, so that adversarial pre-funding cannot block the intended initialization. At minimum, downstream consumers (CLI/stake/nonce flows) should be documented/guarded to always incorporate a fresh, unpredictable seed component (e.g., a random nonce as already partially done via the `nonce` parameter pattern seen in `StreamFactory`-style designs) to reduce predictability of the derived address.

### Proof of Concept
1. Victim intends to create a nonce account with a fixed seed: `nonce_address = Pubkey::create_with_seed(&creator_pubkey, "myseed", &system_program::id())`, as done in `cli/src/nonce.rs`'s `resolve_derived_address` flow. [6](#0-5) 
2. Before the victim's `CreateNonceAccount` transaction lands, an attacker (who knows `creator_pubkey` and the seed convention, e.g. from a public dApp integration) submits `system_instruction::transfer(attacker, nonce_address, 1)`.
3. When the victim's transaction executes, `create_account` in `system_processor.rs` observes `to.get_lamports() > 0` and returns `SystemError::AccountAlreadyInUse`, aborting the nonce-account creation. [7](#0-6) 
4. The victim cannot re-target the same deterministic address; if the seed is not re-randomized, the deterministic account address is permanently blocked.

        address: &Pubkey,
        with_seed: Option<(&Pubkey, &str, &Pubkey)>,
        invoke_context: &InvokeContext,
    ) -> Result<Self, InstructionError> {
        let base = if let Some((base, seed, owner)) = with_seed {
            // The conversion from `PubkeyError` to `InstructionError` through
            // num-traits is incorrect, but it's the existing behavior.
            let address_with_seed =
                Pubkey::create_with_seed(base, seed, owner).map_err(|e| e as u64)?;
            // re-derive the address, must match the supplied address
            if *address != address_with_seed {
                ic_msg!(
                    invoke_context,
                    "Create: address {} does not match derived address {}",
                    address,
                    address_with_seed
                );
                return Err(SystemError::AddressWithSeedMismatch.into());
            }
            Some(*base)
        } else {
            None
        };

        Ok(Self {
            address: *address,
            base,
        })
    }

fn create_account(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    to_address: &Address,
    lamports: u64,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(
                invoke_context,
                "Create Account: account {:?} already in use",
                to_address
            );
            return Err(SystemError::AccountAlreadyInUse.into());
        }

        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    transfer(
        from_account_index,
        to_account_index,
        lamports,
        invoke_context,
        instruction_context,
    )
}

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
}
