## Analysis

This is a genuine analog to the Nouns Builder finding. The Nouns Builder bug is a **threshold/participation-count divergence**: the code counts a tally (`forVotes`) against a computed threshold, but the tally can be satisfied by stale/insufficient real participation. The equivalent bug class explicitly called out in the rules — "confirmations counted versus live members" — exists in both `multisig/src/lib.rs` and `multisig2/src/lib.rs`.

### Root cause
When a signer (v1: `DeleteKey`, v2: `DeleteMember`) is removed from the multisig, the contract only purges **requests that signer created**, not **confirmations that signer previously cast on other still-pending requests**: [1](#0-0) [2](#0-1) 

The threshold check in `confirm()` simply counts the size of the stored confirmation set, without verifying every entry is still a live member/key: [3](#0-2) [4](#0-3) 

`assert_valid_request` only validates that the **current caller** is a live member; it never re-validates the pre-existing entries in `confirmations`: [5](#0-4) [6](#0-5) 

### Title
Stale confirmations from removed multisig members/keys count toward the approval threshold, letting a request execute below the configured `num_confirmations` - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`confirm()` accepts a request once `confirmations.len() + 1 >= num_confirmations`. `DeleteKey` (v1) and `DeleteMember` (v2) remove requests *created by* the departing signer but never scrub that signer's *confirmations* on other pending requests. Once removed, that signer's stale approval remains in the set and is still counted toward the threshold, so the request can later be pushed to execution with fewer currently-authorized signers than `num_confirmations` requires.

### Finding Description
The invariant the multisig is supposed to enforce is: `confirmations counted == confirmations from current live members`. In practice, `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` (v1) / `HashSet<String>` (v2) is never re-validated against membership after a member/key is removed. `delete_member`/`DeleteKey` clean up only the departing signer's *own* requests and `num_requests_pk` entry: [7](#0-6) 

Any request created by a *different* member that the departing signer had already confirmed keeps that stale entry in its confirmation set forever. Since `confirm()` never re-checks that stored confirmers are still members, that ghost confirmation is silently counted: [8](#0-7) 

This breaks the custody binding "a multisig request executed below threshold" — the number of *live* authorizing parties can be one less than `num_confirmations` while the code still treats the request as fully approved.

### Impact Explanation
This is Critical per the rules' impact list: "a multisig request executed below threshold." A `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` request (i.e., direct movement of NEAR funds or account takeover) can be executed with fewer live signers than the multisig's own configured security threshold, because a removed member's/key's earlier confirmation is still counted.

### Likelihood Explanation
Requires no attacker-controlled bypass of validation — it is triggered by completely ordinary multisig operations: (1) a member confirms a pending request, (2) that member is later removed (rotation, revoked key, offboarding a departing team member, or key compromise remediation), (3) any remaining member confirms afterward. Membership changes are a routine multisig lifecycle event, so this can occur unintentionally, and could also be deliberately engineered by a departing/compromised signer who confirms several outstanding requests just before being removed, guaranteeing those requests only need one further live signature regardless of the nominal threshold.

### Recommendation
When removing a member/key (`DeleteMember`/`DeleteKey`), iterate over **all** pending requests' confirmation sets (not just requests the departing signer created) and remove that signer's entry. Alternatively, re-validate at `confirm()` time that every entry in the stored confirmation set still corresponds to a current member/key before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(request)` → confirmations = `{A}`.
3. `B` calls `confirm(request_id)` → confirmations = `{A, B}` (2 < 3, not yet executed).
4. Members pass a separate `DeleteMember { member: B }` request (using 3 legitimate confirmations from A, C, D) — `B` is removed from `self.members`, but `delete_member` only purges requests *created by* `B`; `request_id`'s confirmation set still contains `B`.
5. `C` calls `confirm(request_id)` → `confirmations.len() = 3` (`A`, stale `B`, `C`) `>= num_confirmations (3)` → request executes, even though only `A` and `C` are still live members. Effective live approvals: 2, configured threshold: 3.

The same pattern applies to v1 `multisig/src/lib.rs` using `DeleteKey` instead of `DeleteMember`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
