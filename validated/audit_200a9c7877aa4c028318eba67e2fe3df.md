### Title
Bridge Token Permanent Lock When Recipient Is on Regulated Coin Deny List — (File: `crates/sui-framework/packages/bridge/sources/bridge.move`)

---

### Summary

The Sui native bridge's `claim_and_transfer_token` function unconditionally calls `transfer::public_transfer(token, owner)` after minting bridged tokens. If the bridged token type `T` is a regulated coin (e.g., USDC, USDT) and the recipient `owner` is on the Sui deny list for that coin type, the Sui execution layer rejects the transfer with `AddressDeniedForCoin`. Because the abort reverts all state changes — including the `record.claimed = true` write — the `BridgeRecord` is left permanently in the unclaimed state. No future call to `claim_and_transfer_token` or `claim_token` can succeed, because every attempt will hit the same deny-list rejection. The EVM-side funds remain locked in the vault forever.

---

### Finding Description

**Root cause — no deny-list guard before `transfer::public_transfer`**

`claim_token_internal` mints the coin and sets `record.claimed = true`, then returns the coin to `claim_and_transfer_token`, which immediately transfers it to the address embedded in the bridge message: [1](#0-0) 

```move
// claim from treasury
let token = inner.treasury.mint<T>(amount, ctx);
// Record changes
record.claimed = true;
event::emit(TokenTransferClaimed { message_key: key });
(option::some(token), owner)
``` [2](#0-1) 

```move
public fun claim_and_transfer_token<T>(...) {
    let (token, owner) = bridge.claim_token_internal<T>(...);
    if (token.is_some()) {
        transfer::public_transfer(token.destroy_some(), owner)  // ← no deny-list check
    } else {
        token.destroy_none();
    };
}
```

The Sui execution layer enforces the deny list for regulated coins at the point where a coin object is transferred to an address. This is confirmed by the transactional tests: [3](#0-2) 

```
task 6, lines 50-52:
//# run sui::pay::split_and_transfer ... --sender A
Error: Transaction Effects Status: Address B is denied for coin test::regulated_coin::REGULATED_COIN
```

The deny-list check for receiving is performed during execution via `check_coin_deny_list_v2_during_execution`: [4](#0-3) 

When `transfer::public_transfer(coin, owner)` is called and `owner` is on the deny list for coin type `T`, the entire transaction aborts. Because Move's execution model reverts all state changes on abort, `record.claimed` is rolled back to `false`. The bridge message is now permanently stuck: every subsequent call to `claim_and_transfer_token` or `claim_token` will mint the coin, attempt the same transfer, hit the same deny-list rejection, and revert again.

The bridge treasury's `mint` function has no deny-list awareness: [5](#0-4) 

```move
public(package) fun mint<T>(self: &mut BridgeTreasury, amount: u64, ctx: &mut TxContext): Coin<T> {
    let treasury = &mut self.treasuries[type_name::with_defining_ids<T>()];
    coin::mint(treasury, amount, ctx)
}
```

The bridge package itself imports no deny-list module: [6](#0-5) 

---

### Impact Explanation

**Permanent fund lock (High/Medium).**

- The EVM-side funds are locked in the `SuiBridge` vault after the user calls `bridgeERC20`/`bridgeETH`.
- On the Sui side, the `BridgeRecord` is approved (`verified_signatures` is set) but can never reach `claimed = true`.
- The minted coin is destroyed on every failed attempt (the mint is reverted), so no tokens accumulate anywhere.
- The user's funds are irrecoverably locked: they cannot be refunded on the EVM side (no refund path exists in the bridge protocol) and cannot be delivered on the Sui side.

---

### Likelihood Explanation

- USDC and USDT — the primary stablecoins bridged via the Sui native bridge — are regulated coins whose issuers (Circle, Tether) maintain deny lists for compliance (OFAC sanctions, court orders).
- A user can initiate a bridge transfer from Ethereum before being added to the Sui-side deny list. The deny-list addition takes effect for receiving at the next epoch boundary (~24 hours), which is well within the window between deposit and claim.
- `claim_and_transfer_token` is a public function callable by any address, so the lock is not gated on the recipient's cooperation.
- No special privilege is required to trigger the lock: the coin issuer exercises their normal compliance authority; the bridge user initiates a normal bridge transfer.

---

### Recommendation

Before calling `transfer::public_transfer`, check whether the recipient is on the deny list for coin type `T`. If denied, either:

1. Hold the minted coin in a per-user escrow object inside the bridge (allowing the user to claim once removed from the deny list), or
2. Emit a `TokenTransferDenied` event and return `(option::none(), owner)` without setting `record.claimed = true`, so relayers can retry later (mirroring the limiter pattern already used at lines 595–597).

The limiter already demonstrates the correct pattern for non-fatal failures: [7](#0-6) 

```move
if (!bypass_limiter && !inner.limiter.check_and_record_sending_transfer<T>(...)) {
    event::emit(TokenTransferLimitExceed { message_key: key });
    return (option::none(), owner)   // ← does NOT set claimed = true
};
```

A deny-list failure should be handled the same way.

---

### Proof of Concept

1. User calls `SuiBridge.bridgeERC20(USDC, amount, suiRecipient, SUI_CHAIN_ID)` on Ethereum. Funds are locked in the vault.
2. Bridge authorities approve the transfer; `BridgeRecord { claimed: false, verified_signatures: Some(...) }` is stored on Sui.
3. USDC issuer calls `coin::deny_list_v2_add(deny_list, deny_cap, suiRecipient, ctx)` on Sui.
4. Epoch advances. `suiRecipient` is now denied for receiving USDC.
5. Any caller invokes `bridge::claim_and_transfer_token<USDC>(bridge, clock, ETH_CHAIN, seq_num, ctx)`.
6. `claim_token_internal` mints USDC and sets `record.claimed = true` in memory.
7. `transfer::public_transfer(usdc_coin, suiRecipient)` is attempted.
8. Sui execution layer detects `suiRecipient` is denied for `USDC`; aborts with `AddressDeniedForCoin`.
9. All state changes revert: `record.claimed` returns to `false`; minted coin is destroyed.
10. Steps 5–9 repeat indefinitely. EVM funds remain locked. Bridge message is permanently unclaimable.

```rust
pub fn check_coin_deny_list_v2_during_execution(
    receiving_funds_type_and_owners: BTreeMap<TypeTag, BTreeSet<SuiAddress>>,
    cur_epoch: EpochId,
    object_store: &dyn ObjectStore,
) -> DenyListResult {
    let non_gas_coin_owners = receiving_funds_type_and_owners
        .into_iter()
        .filter_map(|(ty, owners)| {
            if GAS::is_gas_type(&ty) {
                None
            } else {
                Some((ty.to_canonical_string(false), owners))
            }
        })
        .collect::<BTreeMap<_, _>>();
    let num_non_gas_coin_owners = non_gas_coin_owners.values().map(|v| v.len() as u64).sum();
    let regulated_coin_owners = non_gas_coin_owners
        .into_iter()
        .filter_map(|(coin_type, owners)| {
            let deny_list_config = get_per_type_coin_deny_list_v2(&coin_type, object_store)?;
            Some((coin_type, (deny_list_config, owners)))
        })
        .collect::<BTreeMap<_, _>>();
    let result = check_new_regulated_coin_owners(regulated_coin_owners, cur_epoch, object_store);
    // `num_non_gas_coin_owners` is used to charge for gas. As such we must be extremely careful
    // to not use a number that is not consistent across all validators. For example, relying on
    // the number of coins with a deny list is _not_ consistent since the deny list is created
    // on the first addition to the deny list. But the total number of coins/owners denied would
    // be consistent since we rely on the results from the last epoch (i.e. relying on the Config's
    // internal invariants)
    DenyListResult {
        result,
        num_non_gas_coin_owners,
    }
}
