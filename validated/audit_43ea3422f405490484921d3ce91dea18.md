### Title
Missing fee-vs-amount validation in `createDstEscrow` allows taker to permanently break `EscrowDst.withdraw`/`publicWithdraw` via arithmetic underflow, freezing the maker's destination funds - (File: contracts/BaseEscrowFactory.sol, contracts/EscrowDst.sol)

### Summary
`BaseEscrowFactory._postInteraction` (source side) enforces `integratorFeeAmount + protocolFeeAmount < takingAmount` before creating the source escrow, but the symmetric destination-side entrypoint `createDstEscrow` accepts a fully caller-supplied `Immutables` struct — including `amount` and the fee values packed into `parameters` — with no equivalent check. `EscrowDst._withdraw` unconditionally computes `immutables.amount - integratorFeeAmount - protocolFeeAmount`, which underflows and reverts if the fees exceed the amount, permanently disabling `withdraw`/`publicWithdraw` for that escrow.

### Finding Description
On the source path, `_postInteraction` explicitly guards against oversized fees: [1](#0-0) 

On the destination path, `createDstEscrow` takes `dstImmutables` directly from `msg.sender` (the taker/resolver) with no fee-vs-amount check: [2](#0-1) 

The `amount`, and — via the opaque `bytes parameters` field — `protocolFeeAmount`/`integratorFeeAmount`/recipients, are read back out by `ImmutablesLib` accessors with no cross-validation against `amount`: [3](#0-2) 

`EscrowDst._withdraw` then performs an unchecked (Solidity 0.8 checked-by-default, but here relied upon to revert) subtraction that underflows if `integratorFeeAmount + protocolFeeAmount > immutables.amount`: [4](#0-3) 

Because `immutables` (and therefore the fee amounts) are hashed and pinned via `onlyValidImmutables` / `Create2.computeAddress` in `Escrow._validateImmutables`, they cannot be corrected after deployment — every future `withdraw` and `publicWithdraw` call on that escrow will revert identically: [5](#0-4) 

The only remaining exit is `cancel()`, which is caller-gated to the taker and only refunds the maker's asset to the taker, not the maker, and only after the `DstCancellation` timelock: [6](#0-5) 

This exactly mirrors the GoGoPool root cause: an unprivileged/actor-controlled input (there: `duration`/price; here: attacker-chosen fee values in `createDstEscrow`) causes an arithmetic underflow in a fee/slash-style subtraction, making the "intended-to-succeed" state transition (`recordStakingEnd`/slash there, `withdraw` here) permanently revert, while a fallback path (there: withdraw stake; here: `cancel()`) lets the party who caused the break recover funds that the counterparty was supposed to receive.

### Impact Explanation
The maker's destination funds become permanently unwithdrawable through the intended `withdraw`/`publicWithdraw` flow for the lifetime of the escrow (the underflow is deterministic and immutable-bound). If the maker ever submits a `withdraw(secret, immutables)` transaction (even one that will revert), the plaintext `secret` is exposed in the publicly broadcast/mined calldata before the revert, letting the taker use the now-public secret to withdraw the maker's source-chain funds via `EscrowSrc.withdraw`/`withdrawTo` while the maker's corresponding destination-chain funds remain stuck in `EscrowDst` and are eventually reclaimable only by the taker via `cancel()`. This is theft of user funds in motion / temporary-to-permanent freezing of the maker's destination-chain funds during the live swap lifecycle, fitting the "High" (temporary freezing during swap lifecycle) up to "Critical" (theft of funds in motion) bounty categories depending on whether the secret-leak-then-src-withdraw sequence is executed.

### Likelihood Explanation
`createDstEscrow` is a public, unprivileged entrypoint on the documented destination path (`createDstEscrow -> timelock binding -> native/ERC20 funding -> destination withdraw/cancel flow`), and the taker fully controls the `Immutables.parameters` payload with no on-chain cross-check against `amount`. Triggering the underflow requires only choosing `protocolFeeAmount`/`integratorFeeAmount` such that their sum exceeds `amount` — a single, trivially craftable transaction, no privileged role or timing race required.

### Recommendation
Add a fee-sanity check in `createDstEscrow` mirroring the one in `_postInteraction`, e.g.:
```solidity
(uint256 protocolFeeAmount, uint256 integratorFeeAmount) = (dstImmutables.protocolFeeAmount(), dstImmutables.integratorFeeAmount());
if (protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
Alternatively, make `EscrowDst._withdraw` clamp the fee deductions instead of relying on an unchecked subtraction, or clamp to zero when fees exceed `amount`, consistent with how GoGoPool's mitigation clamped `slashGGPAmt` to the available `GGP` balance rather than reverting.

### Proof of Concept
1. Taker calls `createDstEscrow` with `dstImmutables.amount = 100`, `dstImmutables.parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (sum `120 > 100`), and funds the escrow with `nativeAmount`/`safeTransferFrom` matching `dstImmutables.amount` and `safetyDeposit` per `createDstEscrow`'s balance checks: [7](#0-6) 
2. Maker (or anyone) calls `EscrowDst.withdraw(secret, immutables)` after `DstWithdrawal` timelock; `onlyValidSecret` passes, then `uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` underflows and reverts: [8](#0-7) 
3. Every subsequent `withdraw`/`publicWithdraw` call with the same immutables reverts identically (immutables are pinned via CREATE2/hash validation), so the maker can never withdraw; the taker instead reclaims their deposited funds via `cancel()` after `DstCancellation`, while the maker's leaked secret (from the reverted `withdraw` calldata) is available to withdraw the maker's source-chain escrow.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
