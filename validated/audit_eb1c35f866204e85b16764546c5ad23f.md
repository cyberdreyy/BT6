### Title
Unbounded per-notification serialization cost for `accountSubscribe` with `Base64`/`Base64Zstd` encoding and no `dataSlice` - ([File: rpc/src/rpc_pubsub.rs], [File: account-decoder/src/lib.rs])

### Summary
A single websocket client can call `accountSubscribe` with `encoding: base64` (or `base64+zstd`) and no `dataSlice` on a pubkey it later writes with maximal account data. Every subsequent commitment/slot notification triggers `encode_ui_account` to base64-encode (and optionally zstd-compress) the entire account payload with no size cap, unlike the `Binary`/`Base58` paths, which are explicitly bounded by `MAX_BASE58_BYTES`.

### Finding Description
`RpcSolPubSubImpl::account_subscribe` in [1](#0-0)  builds an `AccountSubscriptionParams` directly from the client-supplied `encoding` and `data_slice` with no validation against payload size — unlike `rpc.rs::encode_account`, which explicitly rejects (`Err(InvalidRequest)`) `Binary`/`Base58` encodings whose sliced length exceeds `MAX_BASE58_BYTES` (128 bytes) before ever calling the encoder, as seen at [2](#0-1)  and [3](#0-2) .

The shared encoder `encode_ui_account` in [4](#0-3)  only performs this cheap length pre-check for the `Binary`/`Base58` branches via `encode_bs58` (which checks `slice.len() <= MAX_BASE58_BYTES` before encoding, returning an error string instead of encoding otherwise, per [5](#0-4) ). The `Base64` branch unconditionally calls `BASE64_STANDARD.encode(slice_data(...))` on the full (unsliced, if no `data_slice` is given) account data, and `Base64Zstd` additionally runs a zstd compressor over the full buffer — with no analogous length check or rejection path.

Because the pubsub notification pipeline calls into this same encoder every time `notify_subscribers` fires for a slot in which the subscribed account changed (test harnesses such as [6](#0-5)  demonstrate this call sequence: `account_subscribe` with `Base64` encoding, then `process_transaction_and_notify`/`notify_subscribers`), an attacker who repeatedly rewrites their own account to the maximum allowed size (10 MiB) forces the validator to base64-encode (and possibly zstd-compress) up to 10 MiB of data on every notifying slot for as long as the subscription is open, using only the standard single-write-per-slot cadence permitted to an unprivileged client.

### Impact Explanation
This is a single-subscription resource-amplification issue: CPU (base64 encoding / zstd compression) and memory (allocating the encoded string, and the JSON-RPC notification payload built from it) scale linearly with attacker-controlled on-chain account size, with no explicit ceiling enforced for `Base64`/`Base64Zstd` subscriptions, unlike the deliberate 128-byte cap enforced for `Base58`/`Binary`. This matches the "unbounded cost for a single low-rate call" category — the cost of one subscription is not bounded by an explicit limit but tracks on-chain data size (up to the maximum account size), for every notifying slot rather than a one-time cost.

### Likelihood Explanation
The precondition is trivial for any unprivileged actor: create/own an account (e.g. bump it to near-maximum size via `system_instruction::allocate`/`create_account` limited by rent-exempt balance, or use an existing large owned account), open one `accountSubscribe` websocket subscription with `encoding: base64` and no `dataSlice`, and periodically rewrite the account's data (well within one write per `CLUSTER_SLOT_TIME_TARGET / 2`). Every notified slot thereafter repeats the full-size encode. This is fully repeatable and requires no validator/operator/staked-node control.

### Recommendation
Apply a size guard to the `Base64`/`Base64Zstd` branches of `encode_ui_account` (or specifically in the pubsub subscription-notification path) analogous to the existing `MAX_BASE58_BYTES` check for `Base58`/`Binary`: either enforce a maximum encodable data size (returning an error/omitting data, or requiring `dataSlice`) for pubsub notifications, or require a `dataSlice` for `Base64`/`Base64Zstd` account subscriptions on large accounts, and consider rate/size-based backpressure on the pubsub notification worker itself so a single large-account subscription cannot dominate the notifier queue.

### Proof of Concept
Rust integration test plan (extending the existing pattern in `rpc/src/rpc_pubsub.rs::tests::test_account_subscribe_with_encoding` / `client-test/tests/client.rs::test_account_subscription`):
1. Set up `BankForks`/`RpcSubscriptions`/pubsub test connection as in `test_account_subscribe_with_encoding` ( [7](#0-6) ).
2. Store an account owned by the test client with data size at or near the maximum account size (10 MiB), using `bank.store_account`.
3. Call `rpc.account_subscribe(pubkey, Some(RpcAccountInfoConfig{ encoding: Some(UiAccountEncoding::Base64), data_slice: None, .. }))`.
4. In a loop simulating repeated low-rate rewrites, mutate the account's data (keep it at max size) and call `subscriptions.notify_subscribers(commitment_slots)` for each slot.
5. Measure wall-clock/CPU time and peak allocation size of each `notify_subscribers` call (e.g. via `std::time::Instant` around the call, or a custom allocator counter).
6. Assert failure of the invariant: show that per-notification cost/allocation size grows linearly with the stored account size and exceeds any fixed ceiling (there is none), in contrast to a parallel run with `encoding: Base58` on data > 128 bytes, which is rejected/errors out immediately without full encoding cost (per `test_encode_account_throws_when_data_too_large_to_base58_encode`, [8](#0-7) ).

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}

fn encode_bs58<T: ReadableAccount>(
    account: &T,
    data_slice_config: Option<UiDataSliceConfig>,
) -> String {
    let slice = slice_data(account.data(), data_slice_config);
    if slice.len() <= MAX_BASE58_BYTES {
        bs58::encode(slice).into_string()
    } else {
        "error: data too large for bs58 encoding".to_string()
    }
}

pub fn encode_ui_account<T: ReadableAccount>(
    pubkey: &Pubkey,
    account: &T,
    encoding: UiAccountEncoding,
    additional_data: Option<AccountAdditionalDataV3>,
    data_slice_config: Option<UiDataSliceConfig>,
) -> UiAccount {
    let space = account.data().len();
    let data = match encoding {
        UiAccountEncoding::Binary => {
            let data = encode_bs58(account, data_slice_config);
            UiAccountData::LegacyBinary(data)
        }
        UiAccountEncoding::Base58 => {
            let data = encode_bs58(account, data_slice_config);
            UiAccountData::Binary(data, encoding)
        }
        UiAccountEncoding::Base64 => UiAccountData::Binary(
            BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
            encoding,
        ),
        UiAccountEncoding::Base64Zstd => {
            let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
            match encoder
                .write_all(slice_data(account.data(), data_slice_config))
                .and_then(|()| encoder.finish())
            {
                Ok(zstd_data) => UiAccountData::Binary(BASE64_STANDARD.encode(zstd_data), encoding),
                Err(_) => UiAccountData::Binary(
                    BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
                    UiAccountEncoding::Base64,
                ),
            }
        }
        UiAccountEncoding::JsonParsed => {
            if let Ok(parsed_data) =
                parse_account_data_v3(pubkey, account.owner(), account.data(), additional_data)
            {
                UiAccountData::Json(parsed_data)
            } else {
                UiAccountData::Binary(
                    BASE64_STANDARD.encode(slice_data(account.data(), data_slice_config)),
                    UiAccountEncoding::Base64,
                )
            }
        }
    };
    UiAccount {
        lamports: account.lamports(),
        data,
        owner: account.owner().to_string(),
        executable: account.executable(),
        rent_epoch: account.rent_epoch(),
        space: Some(space as u64),
    }
}
