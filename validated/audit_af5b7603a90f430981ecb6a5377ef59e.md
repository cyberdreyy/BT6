### Title
Unbounded nested loop over `registeredWorkflows` × attacker-controlled `Topics` array causes CPU-exhaustion DoS in WebAPI trigger handler - (File: core/capabilities/webapi/trigger/trigger.go)

### Summary
`triggerConnectorHandler.processTrigger()` iterates over every registered workflow trigger and, for each one, iterates over the full `payload.Topics` slice supplied in the incoming gateway message. `Topics` is decoded directly from the external, unprivileged HTTP client request forwarded by the Gateway with no size limit, mirroring the "unbounded for-loop" root cause described in the Visor Finance report (looping over an attacker-growable array with no bound).

### Finding Description
The Gateway forwards inbound JSON-RPC messages from external, unauthenticated-at-this-layer callers to node capability handlers keyed by method name. For `MethodWebAPITrigger`, the message is routed to `triggerConnectorHandler.HandleGatewayMessage`: [1](#0-0) 

The payload is unmarshalled straight from the request body with no bound on the `Topics` field: [2](#0-1) 

`processTrigger` then runs a nested loop: outer loop over `h.registeredWorkflows` (a map populated by every workflow that registers a web-api trigger via `RegisterTrigger`) and an inner loop over `topics := payload.Topics`, which comes directly from the untrusted request with no length validation: [3](#0-2) 

There is no cap on `len(payload.Topics)` anywhere in the decode/validate path (`webapicap.TriggerRequestPayload` — inspected generated types show no length constraint), and `h.registeredWorkflows` size grows with the number of active workflows using this trigger type, which is not attacker-controlled but can be large in a busy DON. The combination of an unbounded, attacker-supplied `Topics` array times the number of registered workflows produces `O(N × M)` work per single incoming message, with `N` (topics) fully controlled by the caller.

This directly parallels the referenced Visor Finance bug class: an externally reachable function iterates an array whose size an unprivileged caller can inflate, with no bound check, leading to resource exhaustion of the processing loop (the on-chain analog being gas exhaustion; here it is CPU time and event-loop blocking).

### Impact Explanation
A single malicious or malformed `web_api_trigger` message with a very large `Topics` array (e.g., hundreds of thousands of strings) forces the node to perform a large cross-product of comparisons under `h.mu`-free iteration (note: `processTrigger` does not even take `h.mu` while reading `h.registeredWorkflows`, a separate data-race concern) for every registered webapi-trigger workflow. This can:
- Consume significant CPU for extended periods, degrading throughput of the DON's gateway-connector processing pipeline for all workflows, not just the targeted one.
- Because `HandleGatewayMessage` returns errors via response rather than rejecting oversized payloads upfront, the cost is paid before any authorization/rate-limiting check on the sender-topic pairing (rate limiting is only applied per-matched topic and only for senders/topics that already pass the `allowedTopics` and `allowedSenders` checks — the initial iteration itself is unbounded and unthrottled).
- This is a Denial-of-Service against normal external clients/workflow triggers reachable without any privileged credentials — the payload only needs to reach the Gateway's `web_api_trigger` method.

### Likelihood Explanation
Likelihood is high for triggering the resource-consumption behavior itself, since:
- The message path (`Gateway → gatewayConnector.readLoop → triggerConnectorHandler.HandleGatewayMessage`) is reachable by any external caller able to reach the gateway with a `web_api_trigger` method call and valid JSON-RPC envelope; no special role or workflow-owner authorization is required before the payload is parsed and the loop executes.
- There is no size validation of `payload.Topics` before entering the loop, so building a request with a huge topic array is trivial for an unprivileged attacker.
The severity of actual harm depends on gateway-level message size limits (not confirmed in the explored code) and the number of workflows registered with this trigger type at the time of the attack; both factors affect exploitability but do not eliminate the missing-bound root cause.

### Recommendation
- Enforce an explicit maximum length on `payload.Topics` (and reject/truncate oversized requests) before entering `processTrigger`'s loop, similar to the `maxBatchedWorkflowIDs` truncation pattern already used elsewhere in the codebase (e.g., `core/capabilities/remote/trigger_subscriber.go`).
- Restructure the lookup to avoid the full cross-product scan, e.g., index registered triggers by topic (`map[topic][]webapiTrigger`) so a single incoming message only touches the workflows actually subscribed to the supplied topics, rather than scanning every registered workflow for every topic.
- Take `h.mu` (or an RLock) while reading `h.registeredWorkflows` in `processTrigger` to avoid concurrent map access issues introduced by the same code path.

### Proof of Concept
Not independently executable from the static analysis performed; conceptual PoC:
1. Register a webapi-trigger workflow (`RegisterTrigger`) so `h.registeredWorkflows` is non-empty.
2. As an external, unauthenticated Gateway client, send a `web_api_trigger` JSON-RPC message whose `payload.Topics` array contains a very large number of entries (e.g., 100,000+ strings) via `HandleGatewayMessage`.
3. Observe that `processTrigger` performs `len(registeredWorkflows) × len(topics)` iterations before any rate limiting or sender authorization can reject the excess work, consuming disproportionate CPU relative to the small request size.

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
