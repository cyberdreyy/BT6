### Title
Pending withdraw receipts escape the `stopEpochWithDuration` haircut epoch and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The DJL advisory is a path-traversal: an archive entry escapes its intended destination directory and writes outside it. The credit-vault analog is a withdraw receipt that escapes its intended *epoch* scope. `collectWithdrawFunds` stores the loss haircut under a single key `lossRecoveryPriceByEpoch[epochNumber]`, while `pendingWithdraws` — the basis on which the haircut is computed — aggregates receipts from multiple request epochs. `_claimLossAdjustedWithdrawRequest` resolves a user's loss epoch solely via `lastWithdrawRequest[_user]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]`, so receipts recorded under other epochs are never haircutted and are later paid at par through `_claimFundedWithdrawRequest` from the same underfunded bucket.

### Finding Description
- `requestWithdraw` records `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, `withdrawsRequests[_user] += _amount`, and sets `lastWithdrawRequest[_user] = currentEpoch` (IdleCreditVault.sol:282-293).
- Its only loss guard checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e. it can only catch a receipt that was *already* haircutted. It cannot protect requests made before a loss exists (lines 261-271).
- `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingWithdraws` over the *aggregate* pending basis, zeroes `pendingWithdraws`, and stores the price under `lossRecoveryPriceByEpoch[epochNumber]` (lines 411-421).
- `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and `_clearWithdrawClaimForEpoch` clears only the per-epoch entry for that one epoch, decrementing `withdrawsRequests[_user]` by just `withdrawsRequestsByEpoch[_user][lossEpoch]` (lines 789-837).
- Any remainder in `withdrawsRequests[_user]` (receipts from older, unclaimed epochs) then flows into `_claimFundedWithdrawRequest` and is paid 1:1 via `_transferFundedClaim` (lines 312-349, 397-403). `lastWithdrawRequest` was reset to 0 by the epoch-matching clear, so the maturity gate `epochNumber <= lastWithdrawRequest[_user]` passes.

Attack sequence (KYC'd lender, normal mode):
1. Buffer after epoch N: `requestWithdraw(r1)` → tagged epoch N.
2. Do not claim. Next buffer after epoch N+1: `requestWithdraw(r2)` → tagged N+1; `lastWithdrawRequest` = N+1; `pendingWithdraws` = r1 + r2.
3. Manager calls `stopEpochWithDuration(..., _lossAmount)` → borrower funds `pendingToFund < pendingWithdraws`; `lossRecoveryPriceByEpoch` records `price < 1` computed over r1 + r2.
4. Attacker calls `claimWithdrawRequest`: the loss-adjusted path pays only `r2 * price`; the funded path then pays `r1` in full, even though the strategy only received `(r1 + r2) * price`.

Invariant broken: fair burn/one-receipt-one-haircut — the loss waterfall applied to the funding side is not applied to all claims it was sized on.

### Impact Explanation
Direct theft/insolvency: the attacker receives `r1 * (1 - lossRecoveryPrice)` more than intended, drawn from the strategy's funded claim pool that backs other users' receipts (and the default-recovery reserve accounting). The shortfall materializes as later claimants reverting on insufficient balance or as dilution of remaining LPs. The overpayment scales linearly with the attacker's older-epoch basis `r1`, which they fully control.

### Likelihood Explanation
Requires only that a user hold two unfunded requests in different epochs and that a `stopEpochWithDuration` loss occurs — the honest manager/owner performs the loss call, the attacker merely sequences their own `requestWithdraw`/`claimWithdrawRequest` calls around it. The multi-epoch pending-receipt state arises naturally whenever a user re-requests without claiming (the code comments at lines 322-324 explicitly acknowledge this is permitted). No privileged collusion needed.

### Recommendation
Apply the haircut by aggregate basis, not by a single epoch key: either iterate/`pendingBasis`-proportion all of the user's per-epoch entries when clearing a loss-adjusted claim, or store `lossRecoveryPriceByEpoch` under every epoch contributing to `pendingWithdraws` (track a funded/pending basis list), or revert `requestWithdraw` whenever the user has any unclaimed older-epoch receipt so `lastWithdrawRequest` cannot orphan receipts under a prior epoch key.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Setup: standard epoch variant, fixed APR, wallet allowed.
idleCDO.depositAA(100_000 * ONE_SCALE);          // attacker LP position

// Epoch N: request r1
uint256 r1 = 10_000 * ONE_SCALE;
cdoEpoch.requestWithdraw(r1, address(AAtranche));
// do NOT claim; start + run + stop epoch N+1 normally so epochNumber advances
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, 0); // funds returned, requests unfunded-by-design remain pending
// Buffer of epoch N+1: request r2
uint256 r2 = 10_000 * ONE_SCALE;
cdoEpoch.requestWithdraw(r2, address(AAtranche));

// Next running epoch ends with a realized loss via honest manager:
deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - loss);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(newApr, 0, duration, loss); // sets lossRecoveryPriceByEpoch

// Attacker claims once:
uint256 pre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 got = underlying.balanceOf(attacker) - pre;

// Expected: (r1 + r2) * lossRecoveryPrice / 1e18
// Actual:   r2 * lossRecoveryPrice / 1e18 + r1   (r1 escapes haircut at par)
assertGt(got, (r1 + r2) * price / 1e18 + 1);
```

Uncertainty note: I could not confirm within the iteration budget the exact line where `epochNumber` increments relative to `collectWithdrawFunds`. If the increment lands before the loss is recorded, `lossRecoveryPriceByEpoch[lastWithdrawRequest]` reads 0 and the *entire* claim (r1 + r2) pays at par via the funded path while the strategy received only the haircutted amount — an even larger overpayment. Either ordering produces the same broken invariant; only the magnitude differs.
