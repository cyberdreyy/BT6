### Title
Lockup contract's `new()` never validates a publicly-supplied `VestingSchedule`, allowing an attacker to self-deploy a lockup with a degenerate/invalid schedule that unlocks (vests) tokens instantly - ([File: lockup/src/lib.rs])

### Summary
The external report flags a missing range check on an initialization parameter (`initialPrice`) that, if skipped, breaks the invariants the rest of the contract relies on. The analogous defect in this repository is in `LockupContract::new`, which accepts a `vesting_schedule: Option<VestingScheduleOrHash>` argument but only calls `VestingSchedule::assert_valid()` when the schedule is later *revealed* during termination — never at contract initialization when a `VestingScheduleOrHash::VestingSchedule(vs)` variant is supplied directly. [1](#0-0) 

### Finding Description
`LockupContract::new` builds `vesting_information` from the caller-supplied `vesting_schedule` argument: [1](#0-0) 

For the `VestingScheduleOrHash::VestingSchedule(vs)` branch, the schedule is stored as-is with no call to `vs.assert_valid()`, unlike the validation logic defined in `VestingSchedule::assert_valid()`: [2](#0-1) 

That validation function is the only place that would enforce `start_timestamp <= cliff_timestamp <= end_timestamp` and `start_timestamp < end_timestamp`. Because it is skipped at `new()`, a schedule with, e.g., `end_timestamp == start_timestamp` (or `end_timestamp` already in the past relative to the current lockup timestamp) can be stored.

This schedule directly drives `get_unvested_amount`/`get_locked_amount`, the functions the lockup contract and its owner rely on to determine how much of the `lockup_amount` is transferable/withdrawable: [3](#0-2) 

`lockup-factory::create()`, the entry point that deploys and initializes a lockup contract on behalf of an `owner_account_id`, forwards the `vesting_schedule` parameter verbatim to the lockup contract's `new()` without any validation of its own, and it is not gated to only the foundation account — any caller supplying the required attached deposit can invoke it and choose their own `owner_account_id` and `vesting_schedule`: [4](#0-3) 

Since the vesting schedule is meant to encode an employment/vesting agreement set by the NEAR Foundation (the entity with authority to terminate vesting), letting the schedule bypass validation breaks the binding between "tokens vested per the intended schedule" and "tokens the contract's `get_unvested_amount`/`get_locked_amount` report as vested," letting the party choosing the schedule collapse the entire vesting duration to zero.

### Impact Explanation
If an attacker can craft the `vesting_schedule` used during deployment (e.g., by controlling the `create()` call to the lockup factory, or any deployment path that forwards an unchecked `VestingScheduleOrHash::VestingSchedule`), they can set `end_timestamp` at or before the effective lockup start, causing `get_unvested_amount` to immediately report `0` unvested and `get_locked_amount`/`get_owners_balance` to treat the entire locked balance as liquid. This is a Critical-severity issue per the rubric: "locked or unvested tokens released early."

### Likelihood Explanation
Reaching this path requires only calling `lockup-factory::create()` (or any future integration that forwards a raw `VestingSchedule` to `LockupContract::new`) with a crafted schedule and the minimum attached deposit — no privileged role, foundation approval, or redeploy is required. The missing check is a straightforward oversight (validation exists in code as `VestingSchedule::assert_valid()`, but is simply never invoked for the direct/public schedule variant at initialization), making exploitation deterministic and reliable.

### Recommendation
Call `vs.assert_valid()` inside `LockupContract::new` for the `VestingScheduleOrHash::VestingSchedule(vs)` branch (mirroring how `assert_valid()` is applied when a hashed schedule is revealed during termination), and additionally require that `end_timestamp` is strictly in the future relative to the lockup's effective start to prevent an already-vested schedule from being supplied at creation time.

### Proof of Concept
1. Call `lockup_factory.create(owner_account_id, lockup_duration, lockup_timestamp, Some(VestingScheduleOrHash::VestingSchedule(VestingSchedule { start_timestamp: T, cliff_timestamp: T, end_timestamp: T })), release_duration, whitelist_account_id)` with the minimum attached deposit, where `T` is a timestamp already in the past (or equal to the lockup unlock timestamp). [5](#0-4) 
2. This forwards the schedule unchecked to the deployed lockup contract's `new()`, which stores it as `VestingInformation::VestingSchedule(vs)` without calling `assert_valid()`. [1](#0-0) 
3. Immediately after deployment, `get_unvested_amount(vesting_schedule)` returns `0` (fully vested) since `block_timestamp >= end_timestamp`, and `get_locked_amount()`/`get_owners_balance()` report the full `lockup_amount` as available, even though the intended multi-year vesting schedule was supposed to gate the release. [3](#0-2)

    pub fn assert_valid(&self) {
        assert!(
            self.start_timestamp.0 <= self.cliff_timestamp.0,
            "Cliff timestamp can't be earlier than vesting start timestamp"
        );
        assert!(
            self.cliff_timestamp.0 <= self.end_timestamp.0,

        assert!(
            self.start_timestamp.0 < self.end_timestamp.0,

    /// Returns the amount of tokens that are locked in the account due to lockup or vesting.
    pub fn get_locked_amount(&self) -> WrappedBalance {
        let lockup_amount = self.lockup_information.lockup_amount;
        if let TransfersInformation::TransfersEnabled {
            transfers_timestamp,
        } = &self.lockup_information.transfers_information
        {
            let lockup_timestamp = std::cmp::max(
                transfers_timestamp
                    .0
                    .saturating_add(self.lockup_information.lockup_duration),
                self.lockup_information.lockup_timestamp.unwrap_or(0),
            );
            let block_timestamp = env::block_timestamp();
            if lockup_timestamp <= block_timestamp {
                let unreleased_amount =
                    if let &Some(release_duration) = &self.lockup_information.release_duration {
                        let end_timestamp = lockup_timestamp.saturating_add(release_duration);
                        if block_timestamp >= end_timestamp {
                            // Everything is released
                            0
                        } else {
                            let time_left = U256::from(end_timestamp - block_timestamp);
                            let unreleased_amount = U256::from(lockup_amount) * time_left
                                / U256::from(release_duration);
                            // The unreleased amount can't be larger than lockup_amount because the
                            // time_left is smaller than total_time.
                            unreleased_amount.as_u128()
                        }
                    } else {
                        0
                    };

                let unvested_amount = match &self.vesting_information {
                    VestingInformation::VestingSchedule(vs) => self.get_unvested_amount(vs.clone()),
                    VestingInformation::Terminating(terminating) => terminating.unvested_amount,
                    // Vesting is private, so we can assume the vesting started before lockup date.
                    _ => U128(0),
                };
                return std::cmp::max(
                    unreleased_amount
                        .saturating_sub(self.lockup_information.termination_withdrawn_tokens),
                    unvested_amount.0,
                )
                .into();
            }
        }
        // The entire balance is still locked before the lockup timestamp.
        (lockup_amount - self.lockup_information.termination_withdrawn_tokens).into()
    }

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,

        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,

                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }
