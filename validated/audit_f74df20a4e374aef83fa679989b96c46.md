## Title
Stale confirmations from a removed multisig member are still counted toward `num_confirmations`, allowing request execution below the live-member threshold - (multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
In both `multisig` (v1) and `multisig2` (v2), removing a signer (`DeleteKey` / `DeleteMember`) only purges the requests *originated* by that signer. It never scrubs that signer's public key/member id from the `confirmations` set of *other*, still-pending requests. `confirm()` counts `confirmations.len()` regardless of whether every entry still corresponds to a live member, so a stale confirmation left behind by a removed signer can still push a pending request over the `num_confirmations` threshold and trigger execution, even though the number of currently-authorized approvers is lower than the number recorded.

### Finding Description
`confirm()` in both versions determines whether to execute a request purely by counting set membership: [1](#0-0) 

```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    ...
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    ...
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        ...
    }
}
```

When a member is removed via `DeleteMember` (v2) or `DeleteKey` (v1), the cleanup logic only removes **requests originated by that member/key**, not confirmations that member placed on **other** pending requests: [2](#0-1) 

```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
```

The equivalent v1 code has the exact same gap: [3](#0-2) 

```
MultiSigRequestAction::DeleteKey { public_key } => {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
```

Both filters only match `request.member == removed_member` (the *originator* of a request), i.e. requests where the removed member was the one who called `add_request`. Any request added by a **different** member, on which the soon-to-be-removed member had separately called `confirm()`, is left untouched: its `confirmations` set still contains that member's key/id.

`assert_valid_request()` / `current_member()` only checks who is calling `confirm()` right now; nothing in `confirm()` re-validates that every already-stored entry in `confirmations` still belongs to `self.members`. This directly breaks the intended equality: `confirmations counted == live members who approved`. After a removal, `confirmations counted > live approving members`.

### Impact Explanation
This maps to the report's "Critical: a multisig request executed below threshold" category. Concretely:
1. Member A adds a sensitive request (e.g., `Transfer`, `AddKey`, `FunctionCall` to drain funds or add an attacker-controlled key) that requires `num_confirmations = 3`.
2. Member B (a compromised, malicious, or soon-to-depart signer — the "attacker" in this scenario) confirms it, bringing confirmations to 1.
3. The group discovers B is compromised and executes a `DeleteMember`/`DeleteKey` request to remove B. `delete_member`/`DeleteKey` only clears requests B *authored*; B's stale confirmation on A's pending request remains in `self.confirmations`.
4. Only one more legitimate member (C) needs to confirm to reach threshold (1 stale from B + 1 live from C + 1 original from confirm-and-add convenience, depending on flow), and the request executes — even though the intent of removing B was to invalidate its authorization. The number of *currently authorized* approvers backing execution is smaller than `num_confirmations` requires.
This lets a since-revoked signer's approval survive removal and count toward executing arbitrary `MultiSigRequestAction`s (fund transfers, key/member additions, function calls) — a genuine authorization-threshold bypass, not merely a griefing/DoS issue.

### Likelihood Explanation
Requires: (a) a member/key is compromised or turns malicious and confirms a pending request before being caught, and (b) the response is to remove that member rather than to also `delete_request` every pending request they touched. This is a realistic incident-response sequence (revoke first, "clean up" second) and the contract provides no automatic protection or warning that other confirmations by the removed member persist — nothing in `get_confirmations`/`confirm` flags stale entries. The `Gotchas` note in `multisig/README.md` only documents the DoS-lockout scenario, not this authorization-integrity gap, so operators are unlikely to know they must manually audit and `delete_request` every request the removed member touched.

### Recommendation
When removing a member/key (`DeleteMember` in v2, `DeleteKey` in v1), iterate over **all** `confirmations` entries (not just requests authored by that member) and remove the member's public key/id from each `HashSet`. Additionally, `confirm()` should defensively re-validate, at execution time, that every public key/member id in the `confirmations` set still belongs to a current member before counting it toward `num_confirmations` (or re-derive the count by intersecting stored confirmations with the current member set at confirmation time).

### Proof of Concept
1. Deploy `multisig2` with 3 members `{A, B, C}` and `num_confirmations = 3`.
2. `A` calls `add_request` with a `Transfer` action to an attacker-controlled account → `request_id = R`.
3. `B` calls `confirm(R)` → `confirmations[R] = {B}` (len 1).
4. The group detects `B` is compromised and submits/executes a `DeleteMember{member: B}` request (via the normal multisig flow) — see `delete_member` at [4](#0-3) . This removes B from `members` and deletes B's own *authored* requests, but `confirmations[R]` is untouched and still contains `B`.
5. `C` calls `confirm(R)`. In `confirm()`, `confirmations.len() (1, stale B) + 1 (C, live) = 2 < 3` — in a 3-of-3 setup this specific numeric example still falls short, but with `num_confirmations = 2` (2-of-3), step 3's stale confirmation from removed `B` combined with any second live confirmer immediately satisfies `>= num_confirmations`, executing `R` with only one live-member approval instead of two. Generalizing, in any k-of-n multisig, a request needs only `k-1` **live** confirmations once one confirming member has been removed, silently lowering the effective threshold by one for every removed member who had confirmed a still-pending request.

Note: I was unable to browse commit history/tests further to see whether a later patch in this repo addresses this (the search only surfaced the current implementation); this should be verified in the live source before finalizing, but the described code paths as read are unambiguous.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
