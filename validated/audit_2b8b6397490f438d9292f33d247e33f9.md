### Title
Dust-sized APR0 withdraw request permanently reverts `stopEpoch` after any APR re-enable, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` hard-reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged KYC-passing lender can open an APR0-mode withdraw request for a dust amount (`requestWithdraw` → `_requestWithdrawApr0` increments `apr0TotalPrincipal`), and the bucket is only cleared inside `prepareStopEpochWithApr0` itself — after the revert. Once the manager restores a nonzero APR, every `stopEpoch`/`stopEpochWithDuration` call reverts, freezing the entire pool.

### Finding Description
`requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:243-295) mints a receipt and, when `unscaledApr == 0`, records the request via `_requestWithdrawApr0`, which does `apr0TotalPrincipal += _amount` (line 576). There is no minimum amount, so `_amount` can be 1 wei of strategy-token principal.

At epoch end, the CDO calls `prepareStopEpochWithApr0` (line 490). If `apr0TotalPrincipal != 0` the function checks `if (unscaledApr != 0) revert NotAllowed()` (lines 505-508) *before* clearing `apr0TotalPrincipal` (line 540). Because the revert happens before the bucket reset, the state can never be cleared by a later `stopEpoch` under nonzero APR.

The attack sequence:

1. Pool runs in APR0 mode (`unscaledApr == 0`), epoch running.
2. Attacker (whitelisted lender) deposits dust and calls `IdleCDOEpochVariant.requestWithdraw(dust, tranche)` → `apr0TotalPrincipal = dust`.
3. Honest manager legitimately re-enables yield via `setAprs` (`unscaledApr != 0`) — a routine configuration call the attacker simply sequences around, e.g. by keeping a dust APR0 receipt permanently open and re-opening one each buffer phase.
4. Every subsequent `stopEpoch`/`stopEpochWithDuration` reverts in `prepareStopEpochWithApr0`. The epoch can never stop.

Since `claimWithdrawRequest`/`claimInstantWithdrawRequest` require `stopEpoch` to fund `pendingWithdraws`/`pendingInstantWithdraws` and to advance `epochNumber` (lines 326-328), and active deposits cannot redeem outside the epoch flow, all user funds are frozen for as long as `unscaledApr != 0` persists. Recovery requires the manager to notice and set APR back to 0, stop the epoch, and re-apply APR — but the attacker can reopen a dust APR0 receipt every cycle for near-zero cost, keeping the freeze effectively permanent against any fixed-APR operation.

Broken invariant: solvency/liveness of the epoch state machine — a single unprivileged dust receipt vetoes `stopEpoch`.

### Impact Explanation
Permanent (or indefinitely renewable) freezing of 100% of vault TVL: all tranche holders' deposits and all pending/instant withdraw receipts cannot be paid because `stopEpoch` always reverts. Attacker cost is a dust deposit plus gas. Acceptable impact class: temporary/permanent freezing of user funds with quantified loss (entire TVL locked while frozen).

### Likelihood Explanation
Requires the pool to have operated at `unscaledApr == 0` (a supported mode — `requestWithdraw` explicitly branches on it) and the manager to later set a nonzero APR, which is a normal operational action. No malicious privileged role is needed; the attacker's only transaction is an ordinary `requestWithdraw`. Guards that do not stop it: `_onlyIdleCDO` (attacker goes through the CDO normally), KYC/`isWalletAllowed` (attacker is a legitimate lender), and the `lossRecoveryPrice`/`defaultRecovery` paths are not involved. The one uncertainty is whether `setAprs` itself reverts when `apr0TotalPrincipal != 0`; based on the indexed code no such guard is visible, but if one exists the finding reduces to the manager being unable to ever raise APR while any dust APR0 receipt exists — still a freeze of the APR-configuration path reachable by any lender.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0` when `apr0TotalPrincipal != 0`. Either settle the open APR0 bucket with zero interest (set `apr0RateByEpoch[epochNumber] = 0` and clear `apr0TotalPrincipal`), or block APR changes in `setAprs` while `apr0TotalPrincipal != 0` so the revert precondition is unreachable. Additionally consider a minimum request size to make griefing non-dust.

### Proof of Concept
Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testApr0DustRequestBricksStopEpoch() external {
    // APR0 mode
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1e6, true); // dust deposit, whitelisted lender

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch());

    // Attacker opens dust APR0 withdraw receipt
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    assertEq(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 1);

    _startEpochAndCheckPrices(1);

    // Honest manager re-enables yield mid-epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(address(underlying), strategy.borrower(), type(uint256).max, true);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), type(uint256).max);

    // stopEpoch permanently reverts: apr0TotalPrincipal != 0 && unscaledApr != 0
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(10e18, 0);
}
```
