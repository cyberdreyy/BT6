### Title
Signer vote flip (reject → accept) causes weight double-counting in `StackerDBListener`, letting a rejected block appear approved - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tracks per-block vote weight in a shared `BlockStatus` struct, but gates the two counters (`total_weight_approved`, `total_weight_rejected`) on two different sets. A signer that first rejects and later accepts the same block (a legitimate flip permitted by the v0 signer's own state machine) gets its weight counted on *both* sides, breaking the invariant that a signer's weight should count toward exactly one side of the tally — the direct analog of the Ajna finding, where a state-transition happens without properly clearing/reconciling the prior partial state.

### Finding Description
`BlockStatus` holds one shared `responded_signers: HashSet<u32>` plus a separate `gathered_signatures: BTreeMap<u32, MessageSignature>` map: [1](#0-0) 

On a `BlockResponse::Rejected` message, the weight is added and the signer marked "responded" using `responded_signers.insert(slot_id)` as the sole gate: [2](#0-1) 

On a `BlockResponse::Accepted` message for the *same block/slot*, the gate used is `!block.gathered_signatures.contains_key(&slot_id)`, not `responded_signers`: [3](#0-2) 

Sequence:
1. Signer S rejects block B. `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += S.weight`.
2. Later, S's local state changes (e.g. a conflicting sibling goes stale, per the "reject_reason re-evaluable" / `should_reevaluate_reject_reason` re-proposal flow documented for the v0 signer) and S signs B, broadcasting an `Accepted` message.
3. The node's accept handler checks `gathered_signatures.contains_key(&slot_id)`, which is still `false` (S never signed before) — the gate does not consult `responded_signers` — so it proceeds to add weight again: `total_weight_approved += S.weight`, and inserts S into `gathered_signatures` and `responded_signers` (already present, no-op, and it is never removed from the rejected tally).

Result: S's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` for the same block. There is no code path anywhere in `stackerdb_listener.rs` that decrements `total_weight_rejected` when a signer flips to accept, or vice versa.

### Impact Explanation
`total_weight_approved` and `total_weight_rejected` are the aggregated tallies the block-push/miner coordinator uses to decide when a block has reached consensus (≥ threshold approved) or is dead (rejected weight makes threshold unreachable). Double counting one signer's weight on both sides:
- Can push `total_weight_approved` over the threshold using weight that is simultaneously recorded as a rejection, i.e. a rejection is effectively recounted as part of an acceptance tally — this matches the report's core equality break ("aggregated-weight vs verified-accepts").
- Inflates `total_weight_rejected` past what real distinct rejecting signers contributed, which can incorrectly declare a block dead (blocking legitimate progress) even though the same weight is also present in the approved side.

Either direction corrupts the aggregated-weight vs. real per-signer-vote equality the coordinator relies on to decide whether to broadcast a block, which is a Critical-class consensus safety concern per the scope's own criteria (aggregated-weight vs verified-accepts equality break).

### Likelihood Explanation
This requires only a single signer to change its own vote from reject to accept for the same `signer_signature_hash` — no majority, no other signer's key, and no StackerDB/transport exploit is needed. The v0 signer's own documented flow (re-evaluation of a stale rejection reason on re-proposal, `should_reevaluate_reject_reason`) shows that a signer legitimately reconsiders and can later sign a block it previously rejected, so this sequence is reachable through normal, permitted signer behavior, not solely through malicious action — making it readily triggerable.

### Recommendation
Use a single source of truth for "has this signer already contributed weight, and to which side" per block (e.g., track an enum `Option<Vote>` per `slot_id` instead of two independently-gated collections). On a vote flip, subtract the old contribution from whichever total it was previously added to before adding the new contribution to the other total, so a signer's weight is reflected in exactly one of `total_weight_approved` / `total_weight_rejected` at any time.

### Proof of Concept
1. Node has `weight_threshold` computed from `total_weight`.
2. Signer S (weight w) sends `BlockResponse::Rejected` for block B → `stackerdb_listener.rs:515-518` increments `total_weight_rejected` by `w` (verify via `responded_signers.insert` returning `true`).
3. Signer S later sends `BlockResponse::Accepted` for the same block B (e.g. after reconsidering per its own reject-reason re-evaluation logic) → handler at `stackerdb_listener.rs:443-465` checks only `gathered_signatures.contains_key(&slot_id)` (false, since S never signed), so it increments `total_weight_approved` by `w` as well.
4. Inspect `BlockStatus` for B: `total_weight_approved + total_weight_rejected` now exceeds the sum that would result from summing each distinct signer's weight exactly once, since `w` appears in both totals — demonstrating the double-count and the resulting corrupted approve/reject equality used by the coordinator to decide block push/finality.
