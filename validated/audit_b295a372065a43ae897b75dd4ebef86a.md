### Title
Missing `return` after failed OIDC email-claim extraction allows session issuance to proceed with an unvalidated identity - (File: core/sessions/oidcauth/oidc.go)

### Summary
In `handleTokenExchange`, after the ID-token claims are unmarshalled, the code extracts the user's email with a type assertion. If the assertion fails, the handler logs an error and writes an HTTP 500 response but — unlike every other error branch in the same function — it does **not** `return`. Execution falls through and continues to build the role mapping, insert a new row into `oidc_sessions`, and finally set/save the authenticated session cookie, returning a `200 Success: true` response to the client.

### Finding Description
`handleTokenExchange` validates several steps of the OIDC exchange and, on error, consistently calls `return` after writing a JSON/string error response: [1](#0-0) 

However, the email extraction step breaks this pattern: [2](#0-1) 

Because there is no `return` here, execution proceeds to map roles, insert the session row, and set the session cookie regardless of whether `email` was actually recovered from the claims: [3](#0-2) 

The same fall-through pattern recurs a few lines later: if the `INSERT INTO oidc_sessions` call fails, the error is logged and a 500 status is written via `c.String`, but the function again does not `return` — it proceeds to audit-log a "success" event and set the authenticated session cookie for a session ID that was never persisted to the database: [4](#0-3) 

This is the same bug class as the reported `execute()` finding: a failure signal (an `!ok` check or a DB error) is observed and logged, but the calling code does not halt processing on that failure the way it does everywhere else in the same function, so a privileged side effect (creating/persisting a session and issuing an authenticated cookie) proceeds using state that was never validated.

### Impact Explanation
When the email claim is missing/malformed, the handler still completes the login flow: it computes an RBAC role from the ID claims, inserts an `oidc_sessions` row with `user_email = ""`, sets the `SessionIDKey` cookie, and returns a success response. The client ends up with a valid, cookie-authenticated session bound to an empty/unvalidated `user_email`, mapped to whatever role was derived from the group claims. Because `FindUser`/`AuthorizedUserWithSession` key off `user_email`, this creates orphaned or ambiguous session records not properly bound to a specific user identity, undermining the identity-to-role binding that RBAC and audit logging rely on. In the second fall-through, a session cookie is handed to the client for a session row that failed to be written to `oidc_sessions`, producing an inconsistent auth state (client believes it is authenticated, server-side authorization lookups for that session ID will fail).

### Likelihood Explanation
This code path is reached on every completed OIDC login (`/exchange` callback), which is invoked by any client completing the OAuth2 authorization-code flow — an unprivileged, unauthenticated actor prior to token exchange. Triggering the email-missing branch requires either an IdP/tenant misconfiguration or a token/claims response that omits the `email` field, and triggering the DB-insert-failure branch requires only a transient DB error. Neither is attacker-controlled with certainty, which lowers likelihood, but both are realistic operational conditions (IdP claim misconfiguration, DB hiccups) that are not otherwise guarded against by the code.

### Recommendation
Add `return` immediately after both error-handling branches, mirroring the pattern used elsewhere in `handleTokenExchange`:
- After the `email, ok := claims["email"].(string)` check fails.
- After the `oi.ds.ExecContext(... INSERT INTO oidc_sessions ...)` call fails.

This ensures no session row is created and no authenticated cookie is issued unless every prerequisite step succeeded, consistent with the rest of the function's error handling.

### Proof of Concept
1. Configure (or simulate) an OIDC provider/tenant whose ID token claims omit the `email` field for a given user (or intercept the flow such that `claims["email"]` is absent).
2. Complete the OAuth2 authorization code flow and hit `POST /exchange` with a valid `code`/`state`.
3. Observe that despite `ok == false` at [5](#0-4) 
execution continues to [4](#0-3) 
inserting a session row with `user_email = ""`, setting `ginSession.Set(webauth.SessionIDKey, clSession.ID)`, and returning `ExchangeTokenResponse{Success: true}` — granting the client a live, cookie-authenticated session despite the earlier failure.
