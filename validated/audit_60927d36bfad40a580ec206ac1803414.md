### Title
`eth_getBalance` returns stale/incorrect balance during the canonical-commit vs. flashblocks-reconciliation race window - ([File: crates/execution/flashblocks/src/rpc/eth.rs])

### Summary
The Xen bug (XSA-218) is a race between two independent state-mutating actors where one side observes a "mapping" that has already been logically invalidated by the other side but not yet reflected in the structure it reads, yielding false state information. Base's flashblocks RPC layer has the same class of hazard: consumers of pending state read from two independently-updated sources — the node's canonical DB (advanced synchronously by block import) and the `FlashblocksState`/`PendingBlocks` snapshot (advanced asynchronously by `StateProcessor`, see `crates/execution/flashblocks/src/processor.rs`). Because these two update paths are not atomic with respect to each other, a reader that queries them without anchoring both reads to the same block can observe an inconsistent (false) combined state.

### Finding Description
`FlashblocksState`/`StateProcessor` maintains a `PendingBlocks` overlay that is asynchronously reconciled against canonical blocks: [1](#0-0) 
`on_canonical_block_received` records the new canonical height and updates `last_canonical_block`/drops stale snapshots, but the actual reconciliation of pending state runs asynchronously on the `StateProcessor` task via an unbounded queue: [2](#0-1) 

This means there is a window after a block becomes canonical in the underlying provider (`self.eth_api`'s DB, i.e. "latest") but before `StateProcessor` has cleared/reconciled the corresponding pending overlay. This exact race is acknowledged and tested in the repo: [3](#0-2) 
The test comment states plainly: *"race condition when a canon block comes in but user requests their nonce prior to the StateProcessor processing the canon block causing it to return an n+1 nonce instead of n because underlying reth node `latest` block is already updated, but relevant pending state has not been cleared yet."*

The `get_transaction_count` RPC handler was hardened against this by anchoring the canonical-count lookup to `pending_blocks.get_canonical_block_number()` (the block number recorded inside the *same* pending snapshot) rather than to the node's `latest` tag, so canon count and flashblock delta are drawn from a consistent point: [4](#0-3) 

`eth_call` similarly anchors to `pending_blocks.get_canonical_block_number()`: [5](#0-4) 

However, `get_balance` does **not** follow the same pattern. It only consults the pending overlay's own balance map, and if the queried address has no entry there (i.e., it was not touched by any flashblock transaction), it silently falls through to `EthState::balance(&self.eth_api, address, block_number)` using the original, un-anchored `block_number` (the caller-supplied `pending` tag), which resolves against the underlying provider's own definition of "pending"/"latest" — not against `pending_blocks.get_canonical_block_number()`: [6](#0-5) 

Because the fallback path is not anchored to the same canonical block the flashblocks overlay is built on, a client can receive a balance value reflecting a *different* canonical/pending combination than what the rest of the flashblocks pending-state API (nonce, call, block) is reporting concurrently — i.e., a false/inconsistent view of "mapped" account state during the exact race window the project's own tests were written to catch for the nonce path.

### Impact Explanation
An RPC/dApp/exchange client reading `eth_getBalance(address, "pending")` during the canonical-commit/reconciliation race window can be given a balance figure inconsistent with the account's true pending state (e.g., stale pre-block balance served as "pending" while `eth_getTransactionCount("pending")` for the same address already reflects the newer canonical block). This can mislead automated systems (e.g., a bridge, CEX hot-wallet, or automated trading bot) that gate financial decisions (deposits, withdrawal confirmations, double-spend checks) on `eth_getBalance` pending results, causing a wrong/stale-value RPC response that the node "can no longer correctly serve" for the duration of the race window. This is a data-integrity failure in a public RPC surface reachable by any anonymous client with no special access needed, matching the "RPC the node can no longer serve" / wrong-output class called out in the validation criteria.

### Likelihood Explanation
The window exists on every canonical block import while `StateProcessor`'s unbounded queue has not yet drained the corresponding `StateUpdate::Canonical` message — this is an ordinary, frequently-occurring timing condition (not an attacker-controlled edge case), and the project's own regression test for the analogous nonce case confirms the race is real and reproducible in normal operation (`test_nonce_uses_pending_canon_block_instead_of_latest`). No adversarial input is required; any client polling `eth_getBalance("pending")` around block boundaries can observe it. However, this requires a low, best-effort effort to invoke, and I was unable to run the code myself, so it's uncertain how frequently `get_balance` actually falls back all the way to `EthState::balance` with the unanchored `block_number` in production traffic patterns versus how often accounts queried have a pending-state override present.

### Recommendation
Mirror the pattern already used in `get_transaction_count` and `call`: when `block_id.is_pending()` and `pending_blocks.get_balance(address)` returns `None`, resolve the fallback canonical balance against `pending_blocks.get_canonical_block_number()` (optionally with `pending_blocks.get_state_overrides()` applied) instead of delegating to `EthState::balance` with the original, un-anchored `block_number`. This ensures every branch of `eth_getBalance` is anchored to the same canonical block as the rest of the pending-state RPC surface.

### Proof of Concept
Conceptual reproduction, following the same harness pattern as the existing nonce race test:
1. Using `FlashblocksBuilderTestHarness` (as in `crates/execution/flashblocks-node/tests/state.rs`), send a base flashblock and a flashblock transferring funds to `Account::Bob`, then read `pending_blocks.get_balance(Bob)` to confirm an override exists (this is the "safe" path).
2. Call `test.new_canonical_block_without_processing(...)` to advance the underlying provider's canonical/"latest" state without letting `StateProcessor` reconcile pending state yet (as the existing nonce test does).
3. Immediately issue `eth_getBalance(some_address_not_touched_by_any_flashblock, "pending")` for an address that has no entry in `pending_blocks`'s balance override map (e.g., an untouched account whose canonical balance just changed in the newly-committed block due to gas refunds/fee burns or an unrelated transaction in that same block).
4. Because `pending_blocks.get_balance(address)` returns `None`, the code falls through to `EthState::balance(&self.eth_api, address, block_number)` with the raw `pending` tag — observe that this resolves against the node's already-advanced canonical tip rather than `pending_blocks.get_canonical_block_number()`, producing a balance inconsistent with the value implied by the pending nonce/call APIs for the same block window, analogous to the nonce double-count demonstrated in `test_nonce_uses_pending_canon_block_instead_of_latest`.

    /// Processes updates from the queue until the channel closes.
    pub async fn start(&self) {
        while let Some(update) = self.rx.lock().await.recv().await {
            let prev_pending_blocks = self.load_pending_or_drop_stale();
            match update {
                StateUpdate::Canonical(block) => {
                    debug!(message = "processing canonical block", block_number = block.number);
                    match self.process_canonical_block(prev_pending_blocks, &block) {
                        Ok(new_pending_blocks) => {
                            self.pending_blocks.swap(new_pending_blocks);

                            let mut cache = self.cache.lock().await;
                            cache.update_canonical(block.number);
                            let cached = cache.drain(block.number + 1);
                            drop(cache);

                            if !cached.is_empty() {
                                debug!(
                                    message = "replaying cached flashblocks after canonical block",
                                    canonical_block = block.number,
                                    cached_count = cached.len(),
                                );
                                for flashblock in cached {
                                    let fb_prev = self.load_pending_or_drop_stale();
                                    self.apply_flashblock(fb_prev, flashblock).await;
                                }
                            }
                        }
                        Err(e) => {
                            error!(message = "could not process canonical block", error = %e);
                        }
                    }
                }
                StateUpdate::Flashblock(flashblock) => {
                    debug!(
                        message = "processing flashblock",
                        block_number = flashblock.metadata.block_number,
                        flashblock_index = flashblock.index
                    );
                    self.apply_flashblock(prev_pending_blocks, flashblock).await;
                }
            }
        }
    }

#[tokio::test]
async fn test_nonce_uses_pending_canon_block_instead_of_latest() {
    // Test for race condition when a canon block comes in but user
    // requests their nonce prior to the StateProcessor processing the canon block
    // causing it to return an n+1 nonce instead of n
    // because underlying reth node `latest` block is already updated, but
    // relevant pending state has not been cleared yet
    let mut test = FlashblocksBuilderTestHarness::new().await;

    test.send_flashblock(FlashblockBuilder::new_base(&test).build()).await;
    test.send_flashblock(
        FlashblockBuilder::new(&test, 1)
            .with_transactions(vec![test.build_transaction_to_send_eth(
                Account::Alice,
                Account::Bob,
                100,
            )])
            .build(),
    )
    .await;

    let pending_nonce = test
        .provider
        .latest()
        .unwrap()
        .basic_account(&Account::Alice.address())
        .unwrap()
        .unwrap()
        .nonce
        + test
            .flashblocks
            .get_pending_blocks()
            .get_transaction_count(Account::Alice.address())
            .to::<u64>();
    assert_eq!(pending_nonce, 1);

    test.new_canonical_block_without_processing(vec![
        test.build_transaction_to_send_eth_with_nonce(Account::Alice, Account::Bob, 100, 0),
    ])
    .await;

    let pending_nonce = test
        .provider
        .latest()
        .unwrap()
        .basic_account(&Account::Alice.address())
        .unwrap()
        .unwrap()
        .nonce
        + test
            .flashblocks
            .get_pending_blocks()
            .get_transaction_count(Account::Alice.address())
            .to::<u64>();

    // This is 2, because canon block has reached the underlying chain
    // but the StateProcessor hasn't processed it
    // so pending nonce is effectively double-counting the same transaction, leading to a nonce of 2
    assert_eq!(pending_nonce, 2);

    // On the RPC level, we correctly return 1 because we
    // use the pending canon block instead of the latest block when fetching
    // onchain nonce count to compute
    // pending_nonce = onchain_nonce + pending_txn_count
    let canon_block = test.flashblocks.get_pending_blocks().get_canonical_block_number();
    let canon_state_provider = test.provider.state_by_block_number_or_tag(canon_block).unwrap();
    let canon_nonce =
        canon_state_provider.account_nonce(&Account::Alice.address()).unwrap().unwrap();
    let pending_nonce = canon_nonce
        + test
            .flashblocks
            .get_pending_blocks()
            .get_transaction_count(Account::Alice.address())
            .to::<u64>();
    assert_eq!(pending_nonce, 1);

        }

    }
