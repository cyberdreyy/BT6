Confirmed: `check_num_accounts` in `transaction-status/src/parse_instruction.rs` only validates that `accounts.len() >= num` (i.e., that enough account-index bytes are present in the compiled instruction), but never checks that any of those index *values* are within bounds of `account_keys`. Since `account_keys` comes from `solana_message::AccountKeys`, which indexes with a plain slice `Index<usize>` (panicking on out-of-range access), a crafted `CompiledInstruction` whose `accounts` bytes contain an index value ≥ `account_keys.len()` will cause a panic when the RPC's `jsonParsed` transaction encoding path (`getTransaction`, `getBlock`, etc.) indexes `account_keys[account_indexes[N] as usize]` in the SPL-Token, system, address-lookup-table, or other parser modules.

### Title
Unvalidated instruction account indices cause RPC decoder panic on JSON-parsed transaction encoding - (File: transaction-status/src/parse_instruction.rs, transaction-status/src/parse_token.rs, transaction-status/src/parse_system.rs)

### Summary
The Optimism report's root cause is that an externally-supplied field (`l1QueueOrigin`) embedded in a transaction is trusted without validating it against the actual transaction data, letting an attacker mis-declare that field and drive the fraud-proof logic down an incorrect path. The analogous condition in agave's transaction-status parsers is that instruction *account index bytes*, which are attacker-controlled data inside an arbitrary (even unconfirmed/self-submitted) transaction, are validated only for count, never for value range, before being used to index into `account_keys`. This lets a crafted transaction cause the RPC/CLI decoding layer to read out of bounds.

### Finding Description
`check_num_accounts` (and its per-program wrappers `check_num_token_accounts`, `check_num_system_accounts`, `check_num_address_lookup_table_accounts`, etc.) in `transaction-status/src/parse_instruction.rs` only enforces `accounts.len() >= num`: [1](#0-0) 

Every parser (e.g. `parse_token`, `parse_system`, `parse_confidential_transfer_instruction`, `parse_transfer_fee_instruction`, etc.) then unconditionally indexes `account_keys[account_indexes[N] as usize]` using these unchecked byte values, e.g.: [2](#0-1) [3](#0-2) [4](#0-3) 

`account_indexes`/`instruction.accounts` are `u8` values taken directly from the `CompiledInstruction` inside the transaction message — fully attacker-controlled when constructing an arbitrary transaction (it does not even need to succeed on-chain; the instruction's `accounts` field is not validated against the actual account_keys length by the runtime's parsing/serialization layer used for RPC display, only by execution-time account resolution). `AccountKeys` is backed by a plain slice, so indexing beyond its length panics.

### Impact Explanation
This maps to the "decoder panic and misreporting" impact category explicitly accepted by the Validate rules. Any unprivileged user can submit (or even just construct and have indexed via CLI/local paths) a transaction with an out-of-range account index in an SPL-Token/System/etc. instruction. When any RPC consumer requests it with `encoding: jsonParsed` (via `getTransaction`, `getBlock`, `getConfirmedSignaturesForAddress2` with `showTransactions`, etc.), the parser call chain (`transaction-status/src/parse_instruction.rs::parse` → e.g. `parse_token`/`parse_system`) will panic, crashing the thread handling the RPC request. Depending on how the RPC service handles panics (tokio task/thread pool), this can take down or degrade the validator's JSON-RPC subsystem for other clients — a concrete validator-process-availability impact, not merely theoretical.

### Likelihood Explanation
Likelihood is high for any RPC node with `enable_rpc_transaction_history` and `jsonParsed` encoding support (the default `getTransaction`/`getBlock` behavior many wallets/explorers use). An attacker needs only to get such a transaction into a slot that's queried (attacker can submit their own transaction and immediately query it themselves), requiring no elevated privileges, no validator/peer role, and only a single RPC call to trigger.

### Recommendation
Validate every account index in `check_num_accounts` (and any direct indexing sites in `parse_token`, `parse_system`, `parse_stake`, `parse_vote`, `parse_bpf_loader`, `parse_associated_token`, `parse_address_lookup_table`, and all `spl_token_2022` extension parsers) against `account_keys.len()` before use, returning `ParseInstructionError::InstructionKeyMismatch` instead of allowing an out-of-bounds panic. Alternatively, change all `account_keys[idx]` call sites to use a fallible accessor (e.g., `account_keys.get(idx)` mapped to an error) rather than direct `Index` panics.

### Proof of Concept
1. Construct (client-side, no special privileges) a `Message`/`CompiledInstruction` targeting an SPL-Token program instruction (e.g. `TransferFeeInstruction::WithdrawWithheldTokensFromAccounts { num_token_accounts: 200 }`) whose `accounts` byte array satisfies `check_num_token_accounts` (length check only) but contains index bytes (e.g. `250`) far beyond the transaction's actual `account_keys.len()` (e.g. 3).
2. Submit or otherwise get this transaction recorded (it can fail on-chain execution — the account-index validation gap exists purely in the transaction-status/RPC decoding path shown above, which runs independent of execution success).
3. Call `getTransaction`/`getBlock` with `"encoding":"jsonParsed"` for that signature/slot.
4. The RPC worker thread panics inside `parse_token`/`account_keys[account_indexes[i] as usize]` (as shown in `transaction-status/src/parse_token/extension/transfer_fee.rs:103-105` and similar sites), disrupting the RPC service for that request path.

pub(crate) fn check_num_accounts(
    accounts: &[u8],
    num: usize,
    parsable_program: ParsableProgram,
) -> Result<(), ParseInstructionError> {
    if accounts.len() < num {
        Err(ParseInstructionError::InstructionKeyMismatch(
            parsable_program,
        ))
    } else {
        Ok(())
    }
}
