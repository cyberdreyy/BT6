### Title
Unbounded fan-out to DON nodes on unsupported JSON-RPC methods before method validation - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`(*handler).HandleJSONRPCUserMessage` reserves a slot in `h.activeRequests` and calls `fanOutToNodes`, forwarding the raw request to every member of `h.donConfig.Members`, without first checking `req.Method` against the handler's supported method set (`MethodSecretsGet`, `MethodCapabilityExec`). The only place that validates the method is `(*bundler).Bundle`'s `default` case, which runs later, after responses have already been collected from (or sent to) all DON nodes.

### Finding Description
`HandleJSONRPCUserMessage` at [1](#0-0)  only validates `req.ID` non-empty and length, then immediately calls `h.newActiveRequest` (consuming a slot keyed by `req.ID` in `h.activeRequests`) and `h.fanOutToNodes`, which unconditionally sends `&ar.req` to every node in `h.donConfig.Members` via `h.don.SendToNode` — see [2](#0-1) . There is no check of `req.Method` against `h.Methods()` (`MethodSecretsGet`, `MethodCapabilityExec` at [3](#0-2) ) anywhere in this path.

The method is only validated in `(*bundler).Bundle`'s `default` branch, which returns `errUnknownMethod` — see [4](#0-3) . This is invoked from `HandleNodeMessage` (after a node response is already collected, per-node compute already spent) at [5](#0-4) , from `removeExpiredRequests` on timeout at [6](#0-5) , or from `forwardAfterGrace` at [7](#0-6)  — all strictly after fan-out has occurred.

Whether an attacker can actually deliver an unsupported method to this handler at all depends on upstream routing, which I could confirm partially:
- When multiple handlers are registered for a service (`len(m.typeToHandler) > 1`), `multiHandler.getHandler` rejects unknown methods before dispatch, via the `methodToHandler` map lookup at [8](#0-7) .
- However, when only a single handler type is registered for a service, `getHandler` returns that handler directly and **bypasses the method-map check entirely**, per the comment "If there's only one handler, return it directly... for cases where only one handler is registered more generally" at [9](#0-8) . In that configuration, any `req.Method` — including ones not in `{MethodSecretsGet, MethodCapabilityExec}` — reaches `HandleJSONRPCUserMessage` unfiltered.

I was not able to fully confirm from the indexed code whether production DON configurations for the confidential-relay service always register more than one handler type (which would close this gap via the `multiHandler` method-map check) or whether single-handler-per-service configurations are supported/used in practice for this handler. This is a material precondition for exploitability that I could not resolve with the available index.

### Impact Explanation
If reachable (single-handler service configuration), an attacker can force `fanOutToNodes` to broadcast an unsupported-method request to every DON node in `h.donConfig.Members` for a paid-for relay DON subscription, consuming node compute/websocket write bandwidth per request, before the gateway itself ever rejects the method. This matches a resource-exhaustion / DoS class of impact against the DON's compute budget rather than a direct confidentiality/authorization break — the bundler still fails closed for the actual response bundle, and no secrets or capability results leak (the `default` case returns `errUnknownMethod` and no data is bundled).

### Likelihood Explanation
No privileged access is required — only the ability to send a gateway JSON-RPC user request. Exploitability is gated entirely on the gateway's routing configuration: if `NewMultiHandler` is instantiated with a single handler for the service (`len(m.typeToHandler) == 1`), the bypass at [10](#0-9)  applies and the attack is trivially repeatable per request ID. If multiple handlers are always configured for confidential-relay services in practice, the method-map check blocks this before it reaches `HandleJSONRPCUserMessage`, and the vulnerability is not remotely reachable. I could not verify which configuration is used in production from the available context.

### Recommendation
Add an explicit method allowlist check at the top of `(*handler).HandleJSONRPCUserMessage` (before `newActiveRequest`/`fanOutToNodes`), rejecting any `req.Method` not in `h.Methods()` (mirroring the check the vault handler already performs via `vaulttypes.IsGatewaySecretsMethod` before allocating an active request, see [11](#0-10) ). Additionally, do not rely on `multiHandler`'s single-handler bypass to gate method validity; the per-handler `HandleJSONRPCUserMessage` should always self-validate regardless of routing configuration.

### Proof of Concept
Go handler-level test plan (`core/services/gateway/handlers/confidentialrelay/handler_test.go`):
1. Construct a `handler` with a mock `gwhandlers.DON` whose `SendToNode` records calls, and a `donConfig` with N members.
2. Call `h.HandleJSONRPCUserMessage(ctx, jsonrpc.Request[json.RawMessage]{ID: "req-1", Method: "confidential.unknown"}, callback)`.
3. Assert: (a) `h.activeRequests["req-1"]` was created (slot consumed), and (b) the mock DON's `SendToNode` was invoked once per node in `donConfig.Members` (fan-out executed) — proving fan-out happens despite an unsupported method.
4. Separately confirm `(*bundler).Bundle` rejects the same method via `TestBundler_unknownMethod` (already present at [12](#0-11) ), demonstrating the check exists only post-fan-out.
5. To assess reachability from the gateway entrypoint, add a `multiHandler` test with a single registered handler type and an unsupported method, asserting `ProcessRequest`/`HandleJSONRPCUserMessage` is invoked without a pre-dispatch method rejection (contrast with the multi-handler case in the existing `TestGateway_NewGatewayFromConfig_NewStyleConfig_UserRouting` test at [13](#0-12) , which does reject unknown methods when multiple handlers are configured).

```go
func (h *handler) fanOutToNodes(ctx context.Context, l logger.Logger, ar *activeRequest) error {
	var (
		group      errgroup.Group
		nodeErrors atomic.Uint32
	)

	// Each send is bounded independently. A node whose websocket accepts no writes blocks
	// until its context is cancelled, and because the caller only reads the response callback
	// after this function returns, an unbounded send would hold the request open until the
	// client gives up, discarding a bundle that already reached quorum.
	sendCtx, cancel := context.WithTimeout(ctx, h.nodeSendTimeout)
	defer cancel()

	for _, node := range h.donConfig.Members {
		group.Go(func() error {
			err := h.don.SendToNode(sendCtx, node.Address, &ar.req)
			if err != nil {
				nodeErrors.Add(1)
				l.Errorw("error sending request to node", "node", node.Address, "error", err)
			}
			return nil
		})
	}

	_ = group.Wait()

	numNodeErrors := nodeErrors.Load()
	remainingPossibleResponses := len(h.donConfig.Members) - int(numNodeErrors)
	if remainingPossibleResponses < h.donConfig.F+1 && numNodeErrors > 0 {
		return h.sendResponseAndClearRequest(ctx, ar, h.constructErrorResponse(ar.req, api.FatalError, errors.New("failed to forward user request to nodes")))
	}

	l.Debugw("successfully forwarded request to relay nodes")
	return nil
}
```

```go
func (m *multiHandler) getHandler(method string) (handlers.Handler, error) {
	// If there's only one handler, return it directly.
	// This preserves backwards compatibility for cases where the method
	// isn't specified on responses (and for cases where only one handler is registered more generally).
	if len(m.typeToHandler) == 1 {
		for _, handler := range m.typeToHandler {
			return handler, nil
		}
	}

	handler, ok := m.methodToHandler[method]
	if !ok {
		return nil, errors.New("no handler found for method " + method)
	}

	return handler, nil
}
```
