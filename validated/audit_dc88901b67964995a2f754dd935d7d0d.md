### Title
v1 `validate_tenure_change_payload` checks global (not local/signed) acceptance for its duplicate-block guard, allowing a signer to sign two conflicting tenure-start blocks - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionStateV1::validate_tenure_change_payload` gates its "already have a block in this tenure" rejection on `signer_db.get_last_globally_accepted_block(...)` [1](#0-0)  while the v2 equivalent gates the identical check on `signer_db.get_last_signed_block(...)`, which is explicitly documented to include locally-accepted (i.e., already signed) blocks [2](#0-1) . Because global acceptance requires observing a threshold of signatures across the whole signer set, an attacker can get a signer running v1 chainstate to sign a second, competing tenure-start block for the same tenure before the first one it already signed becomes globally accepted.

### Finding Description
The safety property that must hold is: for a given tenure, any single signer must sign at most one distinct block (uniqueness/no-equivocation). Both v1 and v2 attempt to enforce this in `validate_tenure_change_payload` by rejecting a new tenure-start proposal if the signer already "has" a block in that tenure.

- v2 correctly keys this off `get_last_signed_block`, whose own doc comment states: "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place if it failed to reach consensus." [3](#0-2) 
- v1 instead keys the same guard off `get_last_globally_accepted_block`, which only returns a hit once the signer has observed that a threshold of the *whole* signer set has accepted the block — not merely that this local signer has already signed it [4](#0-3) .

Exploit flow: an attacker who wins one miner slot proposes block A (a tenure-change block) with a correct `prev_tenure_consensus_hash`. The signer under attack validates and signs A via `check_proposal` → `validate_tenure_change_payload`, storing it as `LocallyAccepted` in signerdb. Before enough other signers have signed A for it to reach `get_last_globally_accepted_block`'s threshold, the attacker gossips a second, competing tenure-start proposal B for the same tenure (also satisfying the `prev_tenure_consensus_hash == parent_tenure_id` check and the parent-tenure-choice check, since it targets the same parent tenure). When `validate_tenure_change_payload` runs for B on the same signer, `get_last_globally_accepted_block` returns `None` (A isn't global yet), so the `DuplicateBlockFound` rejection never fires, and B is signed too — even though this signer already signed A. This breaks the “sign at most one distinct block per tenure” invariant that the `DuplicateBlockFound` guard is meant to enforce, unlike v2 where `get_last_signed_block` would immediately return A and correctly reject B.

### Impact Explanation
This is a Critical uniqueness/safety violation: a single signer can be induced to sign two conflicting blocks (A and B) for the same tenure. If enough signers running v1 are tricked the same way (each independently, using only their own single-slot proposal-crafting ability plus gossip — no collusion with other signers' keys needed), the aggregate signatures for A and B could each partially accumulate, splitting the signer set's signature weight across two competing chain tips and undermining the finality/uniqueness guarantee signer aggregate signatures are supposed to provide.

### Likelihood Explanation
Preconditions are the ones described in the question: a reward cycle running v1 chainstate, and a window where the honest signer has locally accepted/signed block A but no signer has yet observed global acceptance (an ordinary, expected race window during normal tenure-start block gossip/aggregation, not a rare edge condition). The attacker needs nothing beyond winning one miner slot and gossiping two competing tenure-change proposals for the same parent tenure — no majority of signers, no victim key, no auth token. This is fully repeatable each time a v1 tenure start proposal has not yet reached global acceptance.

### Recommendation
In `SortitionStateV1::validate_tenure_change_payload`, replace the `get_last_globally_accepted_block` lookup with `get_last_signed_block` (as done in v2), so the guard fires as soon as this signer has locally signed any block in the tenure, not only once global acceptance is observed.

### Proof of Concept
Rust test plan (in `stacks-signer/src/chainstate/tests/v1.rs`, mirroring the existing v2 duplicate-block test in `stacks-signer/src/chainstate/tests/v2.rs`):
1. Set up a `SortitionsView`/`SortitionStateV1` with signerdb, a current sortition for tenure T with parent tenure P.
2. Construct tenure-change block A for T with `prev_tenure_consensus_hash = P`. Call `check_proposal`, assert `Ok(())`, then explicitly write A into signerdb as `LocallyAccepted` (simulating that this signer signed it) via the same signerdb API v0/signer.rs uses after a successful check, without marking it globally accepted.
3. Construct a second, distinct tenure-change block B for the same tenure T (different miner/parent choice or different transactions) with the same `prev_tenure_consensus_hash = P`.
4. Call `check_proposal`/`validate_tenure_change_payload` for B again on the same view/db.
5. Assert that v1 wrongly returns `Ok(())` (bug reproduced), and add a parallel assertion using v2's `GlobalStateView::validate_tenure_change_payload` (or a direct call to `get_last_signed_block`) confirming it would instead return `Err(RejectReason::DuplicateBlockFound)`. [5](#0-4) [6](#0-5)

    /// in tenure changes, we need to check:
    /// (1) if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    /// (2) if the parent tenure was a valid choice
    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }
