## Title
Deterministic lockup address at `hex::encode(sha256(owner_account_id))` can be squatted by any unprivileged caller before the real grantor acts, fixing attacker-chosen terms - (File: `lockup-factory/src/lib.rs`)

## Summary
`LockupFactory::create` derives the new lockup's account id purely from `owner_account_id` — `hex::encode(&env::sha256(owner_account_id.as_bytes())[..20])` — with no binding to the caller, no reservation mechanism, and no check that a grant for that owner has not already been promised. Any account holding `MIN_ATTACHED_BALANCE` can call `create` first for a not-yet-granted `owner_account_id`, permanently occupying that deterministic address with attacker-chosen `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration` and `whitelist_account_id`, before the legitimate grantor's `create` call for the same owner can succeed.

## Finding Description
The invariant the protocol relies on is:
`lockup_account_at(hex::encode(sha256(owner_account_id)))` params == `params chosen by owner's intended grantor`.

In `create` [1](#0-0) , the target account is computed solely from `owner_account_id` — nothing about `env::predecessor_account_id()` factors into the address, and nothing checks whether this owner already has (or is expected to have) a lockup. `create` is `#[payable]` and reachable by anyone who attaches `MIN_ATTACHED_BALANCE` [2](#0-1) .

The batched promise `create_account().deploy_contract(CODE).transfer(deposit).function_call("new", LockupArgs)` [3](#0-2)  succeeds for whichever caller's transaction reaches the chain first for a given `owner_account_id`; `create_account` fails for any subsequent caller targeting the same derived address because the account already exists. The callback `on_lockup_create` only distinguishes success/failure via `is_promise_success()` and refunds the deposit to the losing caller's `predecessor_account_id` — it performs no comparison of terms and has no way to detect or reverse a squat [4](#0-3) .

Exploit flow: an attacker who knows (or predicts, e.g. from a public grant announcement) the intended `owner_account_id` of an upcoming grant calls `create` with that same `owner_account_id` but attacker-chosen `vesting_schedule`/`lockup_duration`/`release_duration`/`whitelist_account_id` (e.g. no vesting, zero lockup duration, or a self-controlled whitelist), attaching only `MIN_ATTACHED_BALANCE`. This reaches the chain first (or is simply the only successful attempt in a same-block race), so the deterministic address is created with the attacker's terms — a contract instance of the trusted, protocol-embedded `lockup_contract.wasm` binary [5](#0-4) , but parameterized by the attacker instead of the grantor. When the legitimate grantor later calls `create` for the same owner with the correct terms, `create_account` fails (account exists), the whole batch atomically fails, and `on_lockup_create` merely refunds the grantor's deposit [6](#0-5) ; it never overwrites or removes the squatted contract. No existing guard (`assert_self`, `is_promise_success`, `MIN_ATTACHED_BALANCE` check) validates who is entitled to create at that address or that the terms match a grantor's intent — none of these checks concern authorship of terms, only promise-success bookkeeping.

## Impact Explanation
The account at `hex::encode(sha256(owner_account_id)).<factory>` — the address any tooling, exchange, or the grantor itself would treat as "the lockup for `owner_account_id`" — ends up permanently running with parameters "an account... deployed with parameters its rightful creator never chose," matching the Critical impact category explicitly listed in the rules. Any NEAR later routed to that address (directly, or via a subsequent legitimate-looking `create` attempt whose deposit isn't refunded due to gas exhaustion in the callback, or via off-chain assumption that the address is already the correct lockup) is held under attacker-dictated terms rather than the grantor's intended vesting/lockup schedule. This is repeatable for every not-yet-created `owner_account_id` the attacker can predict, and costs only `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squat attempt, refundable losses aside.

## Likelihood Explanation
The attacker needs no privileges: only enough NEAR to cover `MIN_ATTACHED_BALANCE` and knowledge (or a guess) of the `owner_account_id` string that a future legitimate grant will target — which is often public (grant recipients are frequently announced before the lockup transaction is submitted). Winning the race requires only submitting the transaction before (or in the same block, first, as) the legitimate grantor's transaction; there is no commit-reveal, no reservation, and no ownership check preventing this. This is directly reproducible and repeatable across any number of distinct owners.

## Recommendation
Bind the derived lockup address to something the attacker cannot control or reuse — e.g. require the grantor to be a privileged/whitelisted caller (foundation or vetted account) for factory-created lockups, or incorporate a factory-tracked, one-time reservation/nonce per `owner_account_id` that only an authorized party can set, and have `on_lockup_create`/`create` reject creation attempts for an `owner_account_id` whose derived account already exists rather than silently refunding and leaving the squat in place undetected.

## Proof of Concept
Because the unit-test harness in `lockup-factory/src/lib.rs`'s `#[cfg(test)] mod tests` (`testing_env!`/`MockedBlockchain`) mocks promise results and does not model real NEAR account-existence semantics for `create_account`, a faithful reproduction requires a `near-workspaces` (or `near-sdk-sim`) integration test against real runtime semantics:

1. Deploy `lockup-factory` and initialize with `whitelist_account_id`/`foundation_account_id`.
2. As `attacker.near`, call `create(owner_account_id="victim.near", lockup_duration=0, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=Some(attacker_whitelist))` with `MIN_ATTACHED_BALANCE` attached; await success — assert the resulting account `hex::encode(sha256("victim.near"))[..20].<factory>` exists and its deployed `lockup_contract` state shows `lockup_duration == 0` and no vesting.
3. As `foundation.near`, call `create(owner_account_id="victim.near", lockup_duration=<24 months>, vesting_schedule=Some(real_schedule), ...)` with sufficient deposit; assert the transaction's `create_account` action fails, `on_lockup_create` returns `false`, and the deposit is refunded to `foundation.near`.
4. Assert the equality binding: query the lockup contract state at the derived address and show it equals the attacker's `LockupArgs`, not the foundation's — proving `lockup_account_at(hash(owner)).terms == attacker_chosen_terms != grantor_chosen_terms`.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
