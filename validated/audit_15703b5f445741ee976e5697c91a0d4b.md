### Title
`requestWithdraw` computes interest share against stale `_lastSavedNAV` instead of current tranche NAV, letting withdrawers overclaim epoch interest - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The Perennial bug class is a fee/interest calculation that reads a snapshot ("latest") position instead of the effective "current" position that includes pending changes. The direct analog in this codebase is `_calcInterestWithdrawRequest` in `IdleCDOEpochVariant.sol`, which prices a withdrawal receipt's interest using `_lastSavedNAV(_tranche)` — a NAV snapshot taken at the last accounting update — while the amount actually leaving the pool and the fees charged are based on the live contract value. When current tranche NAV has diverged from the saved snapshot (mid-epoch deposits, intra-epoch accounting drift), the interest minted into the withdraw receipt is computed on a denominator that does not reflect the real claim base.

### Finding Description
`requestWithdraw` first calls `_updateAccounting()` and `_skimDonatedAssets()`, converts tranche tokens via the live `_tranchePrice`, then computes interest with `_calcInterestWithdrawRequest`:

```solidity
uint256 _trancheBal = _lastSavedNAV(_tranche);
_interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
``` [1](#0-0) 

`totInterest` itself is computed over `_managedContractValue()` — the *current* NAV — but the per-user scaling denominator is `_lastSavedNAV(_tranche)`, the stale per-tranche snapshot. Deposits during buffer/epoch and any NAV movement after the last saved point are not reflected in `_trancheBal`, yet the withdrawer's receipt (`creditVault.requestWithdraw(_underlyings, msg.sender, principal)` at line 788) is fixed at request time and paid out at par at the next `stopEpoch` via `pendingWithdraws`. The discrepancy is therefore locked in: interest owed is minted against a NAV base that differs from the NAV base actually generating that interest, exactly like the report's `latestPositionLocal` vs `currentPositionLocal` mismatch where the close notional is priced off the wrong position size.

### Impact Explanation
If `_lastSavedNAV(_tranche)` < current tranche NAV (deposits entered the tranche after the last accounting save), the withdrawing user's pro-rata interest share is inflated — `_amount * totTrancheInterest / _trancheBal` divides by a smaller base — and the excess is locked into `pendingWithdraws` at line 788-790, directly diluting remaining tranche holders of the same class (unjust enrichment funded by other lenders' yield, a broken fair burn / one-receipt-one-fair-payout invariant). If `_lastSavedNAV` > current NAV (recent loss or fee accrual not yet snapshotted), the user is underpaid — mirroring the "user overpays" direction of the original report. Loss magnitude is proportional to the NAV drift between saves times the tranche's APR share for a full epoch.

### Likelihood Explanation
Requires an unprivileged, KYC-passed lender to call `requestWithdraw` while `lastNAV{AA,BB}` is stale relative to actual tranche NAV — e.g., after another depositor entered mid-epoch or after `_updateAccounting` changed NAV without refreshing the saved per-tranche figure. No privileged cooperation is needed; `requestWithdraw` is only gated by the `allow{AA,BB}WithdrawRequest` flags and `isWalletAllowed` (lines 740-744). I was unable to fully confirm in the remaining context whether `_deposit`/`_updateAccounting` always refresh `lastNAVAA`/`lastNAVBB` synchronously; if they do in every path (including deposits during the running epoch and the instant-withdraw early-return branch at lines 761-769), the staleness window collapses and this reduces to a non-issue, so the validity hinges on verifying where `lastNAVAA`/`lastNAVBB` are written relative to `_deposit` and `_minted` interest paths.

### Recommendation
In `_calcInterestWithdrawRequest`, compute the interest-share denominator from the *current* tranche NAV (current tranche supply × live `_tranchePrice`, or `getContractValue` split by tranche) rather than `_lastSavedNAV(_tranche)`, so the claim base matches the NAV base used for `totInterest`. Equivalently, ensure `lastNAVAA`/`lastNAVBB` are updated atomically on every state transition that changes tranche NAV (deposits, `_updateAccounting`, loss events) before `requestWithdraw` can read them, and have `arjun-io`-style review confirm edge cases where pending but un-settled flows (APR0 bucket, pending instant withdraws) should be excluded from the denominator.

### Proof of Concept
Sketch (Foundry fork, credit-vault deployment on `IdleCDOEpochVariant`):

```solidity
// epoch running, APR > 0, AYS active
uint256 navBefore = cdoEpoch.lastNAVAA();

// Attacker (KYC'd) deposits a large AA amount mid-epoch so current
// AA NAV grows but lastNAVAA is not refreshed.
idleCDO.depositAA(largeAmount);

// Attacker requests full withdraw of a second tranche position.
uint256 requested = cdoEpoch.requestWithdraw(attackerBal, address(AAtranche));

// Compute fair interest with current NAV denominator vs the stale
// _lastSavedNAV denominator; assert requested > fair by drift *
// totTrancheInterest / lastNAVAA. After startEpoch + funded stopEpoch,
// claimWithdrawRequest pays the inflated receipt at par, diluting

```

Note: this PoC assumes deposits do not synchronously update `lastNAVAA`; that write path could not be fully verified within available context and should be confirmed before treating the finding as exploitable.

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
```
