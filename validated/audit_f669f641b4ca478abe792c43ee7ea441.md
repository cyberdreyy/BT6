### Title
Dust queued withdrawal makes `processWithdrawRequests` revert permanently, freezing all queued withdraw requests for the epoch - ([File: contracts/IdleCDOEpochQueue.sol](contracts/IdleCDOEpochQueue.sol))

### Summary
The external report describes a NULL-dereference DoS: a return value obtained on an unchecked path is dereferenced without validation, and a single crafted request crashes the whole server. The analog in idle-tranches is `IdleCDOEpochQueue.processWithdrawRequests`: it trusts the `_underlyingsRequested` return of `IdleCDOEpochVariant.requestWithdraw` and computes `_epochPrice = _underlyingsRequested * ONE_TRANCHE / _pending`, reverting with `Is0()` whenever the implied epoch price rounds to zero. A KYC-passing lender can queue a 1-wei tranche withdraw request while the epoch is running; when the tranche price is below `1e18` (any realized loss, or a discounted BB tranche), `requestWithdraw` returns `_underlyings == 0`, the `Is0()` check fires, and `processWithdrawRequests` reverts on every call for that epoch, trapping every other user's queued tranche tokens in the queue with no processed claim.

### Finding Description
- `IdleCDOEpochQueue.requestWithdraw` accepts any nonzero `amount` of tranche tokens while the epoch is running and accumulates it into `epochPendingWithdrawals[nextEpoch]`; there is no minimum-amount or minimum-value check. [1](#0-0) 
- During the buffer period, the owner/manager calls `processWithdrawRequests`, which forwards the aggregate `_pending` to `IdleCDOEpochVariant.requestWithdraw` and divides the returned underlying amount by `_pending` to set `epochWithdrawPrice`; if that division yields 0 it reverts with `Is0()` and leaves `epochPendingWithdrawals` and all `userWithdrawalsEpochs` untouched. [2](#0-1) 
- In `IdleCDOEpochVariant.requestWithdraw`, `_underlyings = _amount * _tranchePrice(_tranche) / ONE_TRANCHE_TOKEN`, then interest is added and fees subtracted. For `_amount = 1` and `_tranchePrice < 1e18` (e.g., a loss-adjusted or junior BB price, which the loss-waterfall code paths such as `stopEpochWithDuration(_lossAmount)` and `finalizeDefault` can produce, or any BB tranche priced below par), `_underlyings` rounds down to 0 and the function returns 0 rather than reverting — the exact "unchecked degenerate return" pattern of the NULL-deref report. [3](#0-2) [4](#0-3) 
- Because the revert happens atomically, no state is cleaned up: the next call to `processWithdrawRequests` re-executes the same aggregate request and reverts again. The dust request cannot be skipped or filtered — there is no per-user processing and no way to exclude one request from `epochPendingWithdrawals`. The poisoned epoch's processing is deterministically dead, mirroring the "single request crashes the whole process" property of CVE-2026-72582.

### Impact Explanation
Every user who queued a withdrawal for that epoch has already transferred tranche tokens into the queue and cannot receive a processed claim while the dust request is pending. Their only recovery is `deleteWithdrawRequest`, which remains callable because `epochWithdrawPrice` stays 0 and `isEpochWithdrawZero` is never set — but that path returns tranche tokens, not underlyings, forcing users to re-request directly on `IdleCDOEpochVariant` during the buffer window (if it is still open) and to re-wait a full epoch otherwise. [5](#0-4)  The attacker can repeat the attack each running epoch at a cost of 1 wei of tranche token, so the DoS is renewable indefinitely. This is a temporary freezing of user funds (all queued withdrawals for the epoch) achieved by an unprivileged user at near-zero cost, not merely a gas/availability issue — the queue's entire withdrawal-settlement function is bricked while honest users' tokens sit inside it.

### Likelihood Explanation
- Attacker requirements are minimal: any KYC-passing wallet holding ≥1 wei of the queue's tranche token — a "KYC-passing lender" or "tranche-token holder," both in-scope roles.
- The preconditions are realistic: (a) epoch is running so `requestWithdraw` is open, and (b) `virtualPrice(tranche) < 1e18`, which occurs naturally after any loss event via `stopEpochWithDuration(_lossAmount)`, after default finalization, or for a junior BB tranche trading below par. Even at exactly `1e18`, the attack can be tuned by requesting `amount` such that `amount * price / 1e18` rounds to 0 while `amount` stays the sole/dominant pending request.
- No existing guard stops it: `_checkAllowed` passes (KYC'd, epoch running), `requestWithdraw` has no minimum, the `Is0()` check is precisely the unchecked-return failure, and `pendingClaims` never becomes true so the queue is not even marked as in-progress — the failure is silent except for the revert.

### Recommendation
Handle the degenerate return the same way the prefunded-deposit path already handles zero-minted shares (`epochPrice[_epoch] = _prefundedMinted == 0 ? _cdo.virtualPrice(tranche) : ...`): in `processWithdrawRequests`, when `_underlyingsRequested == 0`, either skip processing that epoch's dust-level requests, fall back to `virtualPrice`, or mark the epoch via the existing `isEpochWithdrawZero` mechanism so users can clear their receipts and later epochs are not blocked. Alternatively, enforce a minimum queued-withdrawal value (e.g., require `_trancheToUnderlyings(amount) > 0`) in `requestWithdraw`. [6](#0-5) [7](#0-6) 

### Proof of Concept
Foundry-fork PoC sketch (modeled on `test/foundry/IdleCDOEpochQueue.t.sol` helpers `_depositWithUser`, `_requestWithdrawWithUser`, `_stopCurrentEpoch`):

```solidity
function testDustWithdrawRequestBlocksEpochProcessing() external {
    // buffer: epoch #0 -> #1, set a discounted tranche price (< 1e18)
    // e.g. via a stopEpochWithDuration with a small _lossAmount so that
    // virtualPrice(tranche) < ONE_TRANCHE.
    _stopCurrentEpochWithLoss(); // helper: realize a small loss

    // honest users queue normal withdraw requests during the running epoch
    vm.prank(manager);
    cdoEpoch.startEpoch();
    _requestWithdrawWithUser(user1, tranches1);
    _requestWithdrawWithUser(user2, tranches2);

    // attacker (KYC'd, holds 1 wei of tranche) queues a dust request
    deal(address(tranche), attacker, 1);
    vm.startPrank(attacker);
    tranche.approve(address(queue), 1);
    queue.requestWithdraw(1);           // 1 wei tranche -> underlying value rounds to 0
    vm.stopPrank();

    // buffer period: epoch stops, manager tries to process
    _stopCurrentEpoch();
    uint256 epoch = strategy.epochNumber();

    // single 1-wei request makes the whole epoch's processing revert forever
    vm.prank(manager);
    vm.expectRevert(Is0.selector);
    queue.processWithdrawRequests();

    // retrying never helps: pending withdrawals remain, price stays 0
    vm.prank(manager);
    vm.expectRevert(Is0.selector);
    queue.processWithdrawRequests();
    assertGt(queue.epochPendingWithdrawals(epoch), 0);
    assertEq(queue.epochWithdrawPrice(epoch), 0);

    // honest users cannot claim; they can only take tranche tokens back
    vm.expectRevert(NotAllowed.selector);
    vm.prank(user1);
    queue.claimWithdrawRequest(epoch);
}
```

Uncertainty: whether `IdleCreditVault.requestWithdraw(0, ...)` inside `IdleCDOEpochVariant.requestWithdraw` itself reverts on a zero amount was not fully verified from the indexed snippet; if it reverts, the same attack applies at a slightly larger dust amount where `_underlyings` is nonzero but `underlyings * 1e18 < pending` still holds (possible when the dust request shares the epoch with larger requests and the tranche price is low enough that the aggregate rounds the implied price to 0 — though the sole-dust-request case at `price < 1e18` is the clean variant). The twin analog in `processDeposits` (`_pending * ONE_TRANCHE / _trancheMinted` division by zero when `depositAA`/`depositBB` mints 0 shares for a dust deposit) is also unguarded, in contrast to the explicitly handled prefunded path.

  function deleteWithdrawRequest(uint256 _requestEpoch) external {
    // if the epoch withdraw price is already set, withdrawal requests were already processed so
    // the withdraw request can't be deleted. Withdraw requests can be deleted even if the epoch is running
    _checkNotAllowed(epochWithdrawPrice[_requestEpoch] != 0 || isEpochWithdrawZero[_requestEpoch]);

    uint256 amount = userWithdrawalsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user withdraw request for the epoch
    userWithdrawalsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending withdraw requests
    epochPendingWithdrawals[_requestEpoch] -= amount;
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, amount);
  }
