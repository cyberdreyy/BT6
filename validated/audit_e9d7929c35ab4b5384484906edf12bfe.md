### Title
Stale loss-adjusted withdraw receipts are later paid at par via `lastWithdrawRequest` overwrite - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` tracks only the *latest* request epoch per user in `lastWithdrawRequest`. When a receipt from an earlier epoch was funded at a loss-adjusted price (`lossRecoveryPriceByEpoch[N] < 1e18` set by `collectWithdrawFunds` / `stopEpochWithDuration(_lossAmount)`), a second `requestWithdraw` in a later epoch overwrites `lastWithdrawRequest` to the new epoch `M`. On claim, `_claimLossAdjustedWithdrawRequest` only checks `lossRecoveryPriceByEpoch[M]` (zero for a fully funded epoch), so the old haircutted basis stays inside `withdrawsRequests[_user]` and is paid **at par** by `_claimFundedWithdrawRequest`. This is the on-chain analog of the CVE-2017-7866 out-of-bounds write: the claim path "writes" a payout beyond the bounds of what was actually funded for that receipt.

### Finding Description
- `requestWithdraw` records per-epoch basis in `withdrawsRequestsByEpoch[_user][currentEpoch]` and sets `lastWithdrawRequest[_user] = currentEpoch` (contracts/strategies/idle/IdleCreditVault.sol:282-293).
- If the borrower underfunds a stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = funded * 1e18 / pendingBasis` and clears `pendingWithdraws` (lines 411-421). The strategy then only holds `basis * price` for that epoch's receipts.
- `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` (line 790). After a second request in epoch M, `lastWithdrawRequest == M`, `lossRecoveryPriceByEpoch[M] == 0`, so the epoch-N claim is skipped (lines 789-795).
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — still containing the un-claimed epoch-N basis — at 1:1 (lines 338-349), gated only by `epochNumber > lastWithdrawRequest[_user]` (line 326), which is satisfied after epoch M stops.
- `_transferFundedClaim` only excludes `defaultRecoveryReserve` from spendable balance (lines 897-906); other claimants' funded underlyings in the strategy are unprotected.

### Impact Explanation
The attacker extracts `basis_N * (1 - lossRecoveryPrice)` more underlying than funded for their epoch-N receipt, draining underlying reserved for other users' funded withdraw/instant claims held in the strategy. Quantified loss: with e.g. a 50% loss-adjusted price on a 100k receipt, a repeat request plus claim steals ~50k underlying units from other pending claimants. Broken invariant: "one receipt, funded payout" — receipts are paid beyond their funded bounds.

### Likelihood Explanation
Requires: (a) `stopEpochWithDuration(_lossAmount > 0)` — i.e., borrower underpays at epoch stop while pending withdraws exist (honest-manager flow, plausible on partial default/loss); (b) the attacker holds a receipt in that epoch and submits another `requestWithdraw` in a later epoch (repeat requests are explicitly supported — the funded-claim comments note unclaimed requests merge into the next epoch, lines 323-324); (c) the later epoch funds at par; (d) the strategy holds sufficient other funded underlying to cover the overpayment — true whenever other claimants' funded claims remain. Uncertainty: I could not fully verify within available iterations that `IdleCDOEpochVariant.requestWithdraw` never blocks a second request while one is outstanding, but the code and tests indicate repeat requests are permitted.

### Recommendation
In `_claimLossAdjustedWithdrawRequest` / `_claimFundedWithdrawRequest`, iterate or track *all* epochs with nonzero `lossRecoveryPriceByEpoch` for the user instead of only `lastWithdrawRequest[_user]`. Alternatively, in `requestWithdraw`, first settle any prior loss-adjusted epoch's claim (or reprice the old basis by its `lossRecoveryPrice`) before merging new basis into `withdrawsRequests[_user]`, so the aggregate funded bucket can never exceed actually funded amounts.
