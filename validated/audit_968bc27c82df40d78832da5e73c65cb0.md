### Title
`ProgrammableBorrower.onStopEpoch` treats ERC4626 share valuation as withdrawable liquidity — a vault user can freeze `stopEpoch` and all pool withdrawals by draining vault liquidity - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`onStopEpoch` decides whether the pool's stop‑epoch cash requirement is covered by comparing the shortfall to `convertToAssets(shares)` (`_currentVaultAssets()`), i.e. share *valuation*, rather than to actually withdrawable liquidity (`vault.maxWithdraw`). When the valuation check passes, it attempts `vault.withdraw(shortfall)` and reverts with `StopEpochVaultLiquidityUnavailable` if the external vault cannot pay. Any unprivileged user of the borrower's ERC4626 vault can keep the vault illiquid (borrow out available cash, or deposit into vaults with withdrawal caps/queues), so every `stopEpoch`/`stopEpochWithDuration` call on `IdleCDOEpochVariant` reverts. While the revert persists, `isEpochRunning` stays `true`, deposits are paused, AA/BB withdraw requests are disabled, and pending withdraw receipts cannot be funded — the entire pool TVL is frozen at the attacker's discretion. The owner's only fallback is a hard default, which converts a temporary liquidity squeeze into a permanent loss event for LPs.

### Finding Description
In `ProgrammableBorrower.onStopEpoch` (lines 239–253):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  // covered check uses share valuation, not withdrawable liquidity
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The design assumes `convertToAssets(balanceOf)` ≈ withdrawable assets. For general ERC4626 vaults (lending markets, vaults with `maxWithdraw` caps, queued withdrawals, or simply fully-utilized liquidity), valuation can greatly exceed `maxWithdraw(address(this))`. Because the "covered" path reverts instead of returning `false`, the failure propagates out of `IdleCDOEpochVariant._stopEpoch` (line ~398: the hook call is *outside* the `try`/`catch` that triggers `_handleBorrowerDefault`), so `stopEpoch` reverts entirely rather than entering the default path. This makes the freeze **unbounded**: even an owner who would prefer to take a controlled default cannot do so through `stopEpoch` while the vault stays illiquid — the revert happens before any state is committed.

Attacker: any unprivileged user of the ERC4626 vault (explicitly in scope). Cost: only the vault's borrow/funding cost of keeping liquidity withdrawn; no capital is risked inside the credit pool.

### Impact Explanation
- **Broken invariant:** epoch state machine liveness — a stoppable epoch must either settle or default; here a third party can wedge it in `isEpochRunning` indefinitely.
- **Effect:** temporary freezing of the entire pool TVL (all active AA/BB NAV plus pending withdraw receipts), since deposits are paused, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are `false`, and `claimWithdrawRequest` funding depends on the stopped epoch settling.
- **Escalation:** the only escape is `finalizeDefault`/`_handleBorrowerDefault`-style unwinding (emergency path), which socializes a "loss" that was actually just a liquidity squeeze — turning a freeze into potential permanent NAV damage, or forcing honest owner intervention under duress.
- Quantified loss: freeze of 100% of pool TVL for the duration of vault illiquidity, repeatable each epoch at the cost of vault borrow interest.

### Likelihood Explanation
Medium. It requires a programmable-borrower deployment whose vault can be made illiquid (any lending-style ERC4626 with utilization, or any vault where `maxWithdraw < convertToAssets` due to caps/queues). No privileged role is needed; the timing (just before `epochEndDate`) is trivially watchable on-chain. The check at line 245 explicitly documents the intent to distinguish "economically uncovered" from "liquidity unavailable", but uses the wrong oracle (valuation vs. `maxWithdraw`) for that distinction.

### Recommendation
- Replace the coverage check with a liquidity-aware probe: `if (shortfall > vault.maxWithdraw(address(this)))` treat as covered-failure and either return `false` (default path) or `true` per policy, rather than attempting a withdraw that will revert.
- Alternatively, wrap the `vault.withdraw` in a bounded retry and expose a separate manager-gated path to convert persistent vault illiquidity into an explicit default, so a third-party vault user cannot hold the epoch state machine hostage.
- Document that the ERC4626 vault must guarantee withdrawable liquidity up to `convertToAssets`, or restrict integrations to vaults where `maxWithdraw == convertToAssets` always holds.
