### Title
Front-runnable, permission-less `name` parameter in `MultisigFactory::create` lets any attacker squat `<name>.<factory>` with attacker-chosen members before the intended owner - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` derives the deployed contract's account id purely from the attacker-supplied `name` argument, with no binding to `env::predecessor_account_id()`, no reservation mechanism, and no existence check before issuing the `CreateAccount` receipt. Any unprivileged caller can therefore claim `<name>.<factory>` first, deploying `multisig2` with a `members` list and `num_confirmations` entirely of their own choosing, permanently pre-empting the account the intended owner expected to control.

### Finding Description
The broken binding: for a name `n` that a legitimate user intends to claim, the invariant the ecosystem relies on is `members_of("n.<factory>") == members_chosen_by_intended_owner("n")`. `create` breaks this because it never checks that `name == env::predecessor_account_id()` (or any relationship at all) and never checks that `n.<factory>` is unclaimed before scheduling account creation: [1](#0-0) 

```rust
#[payable]
pub fn create(
    &mut self,
    name: AccountId,
    members: Vec<MultisigMember>,
    num_confirmations: u64,
) -> Promise {
    let account_id = format!("{}.{}", name, env::current_account_id());
    Promise::new(account_id)
        .create_account()
        .deploy_contract(CODE.to_vec())
        .transfer(env::attached_deposit())
        .function_call(
            b"new".to_vec(),
            json!({ "members": members, "num_confirmations": num_confirmations })
                .to_string()
                .as_bytes()
                .to_vec(),
            0,
            env::prepaid_gas() - CREATE_CALL_GAS,
        )
}
```

Because `CreateAccount` for a sub-account `name.<factory>` can only be executed by the factory contract itself (NEAR enforces that the immediate parent account is the actor performing sub-account creation), the *only* gate on who gets to own that name is this open `create` entrypoint — and it has none: `name`, `members` and `num_confirmations` are all fully attacker-controlled, there is no `assert_eq!(name, env::predecessor_account_id())`, no whitelist, and no pre-existing-account check performed by the factory itself (unlike `staking-pool-factory::create_staking_pool`, which at least tracks `staking_pool_account_ids` and validates account-id format, and `lockup-factory::create`, which derives the account id deterministically from `sha256(owner_account_id)` rather than from an attacker-chosen string) — compare: [2](#0-1) [3](#0-2) 

Exploit flow: the attacker observes (off-chain, e.g. from a company's public communication about "we will deploy our multisig at `acme.multisig-factory.near`") that a victim intends to use a specific `name`. Before the victim's transaction lands, the attacker calls `create("acme", [attacker_key], 1)` with the minimum deposit. The NEAR runtime executes `CreateAccount` for `acme.multisig-factory.near` and initializes `multisig2` with the attacker as sole member (`num_confirmations=1`). When the real owner later calls `create("acme", [...])`, the `CreateAccount` action fails because the account already exists, but the intended owner does not learn this until after their transaction is on-chain and, more importantly, third parties who trusted the name based on off-chain convention before that failure (or who never see the owner's failed attempt) may send funds directly to `acme.multisig-factory.near`, believing it is controlled by the legitimate party's members — those funds are transferable at will by the attacker via `add_request`/`confirm` in `multisig2`, since `num_confirmations` and the member set were entirely attacker-chosen.

No existing guard prevents this: there is no `assert_owner`, no `assert_self()`, no `is_valid_account_id` cross-check against predecessor, and no dedup/whitelist bookkeeping in `MultisigFactory` at all — the struct itself is empty (`pub struct MultisigFactory {}`), it stores no state to track claimed names. [4](#0-3) 

### Impact Explanation
Funds transferred to `<name>.<factory>` by any party who trusts the name-to-owner mapping are moved out under the sole control of the attacker's chosen members and confirmation threshold — i.e. "a multisig deployed with parameters its rightful creator never chose" and, if funds are ever sent, "NEAR moved out of a multisig by a party not entitled to it." This is repeatable against every name the attacker can guess or observe being planned, for as many names as the attacker is willing to pay the minimum deposit + gas for, at essentially the deposit cost of the multisig creation itself. Blast radius extends to any user or protocol integration that resolves a multisig's identity by its sub-account name under `multisig-factory` rather than by independently verifying its `members`/`num_confirmations` state on-chain before trusting it.

### Likelihood Explanation
Preconditions are minimal: the attacker needs only an unprivileged NEAR account, the minimum attached deposit for `create`, and knowledge (or a guess) of a `name` someone else plans to claim on this specific factory. There is no rate limiting, whitelist, or owner check to bypass — `create` is `#[payable]` and callable by anyone. The attack is directly repeatable across arbitrary names and is a pure race condition (whoever's transaction lands first at the factory wins the name), so it is trivially reproducible in a local test without any privileged setup.

### Recommendation
Bind the created sub-account's identity to the caller, e.g. require `name == env::predecessor_account_id()` (mirroring how ownership is asserted elsewhere), or derive the multisig account id deterministically from a hash of the caller/owner identity as `lockup-factory` does, and/or maintain an on-chain reservation/whitelist so a name can only be claimed by its designated owner. At minimum, track already-created names in `MultisigFactory` state and reject duplicate/squatted attempts explicitly rather than relying on an implicit `CreateAccount` failure that offers no protection against front-running.

### Proof of Concept
Using `near-sdk-sim`/`near-workspaces` (mirroring the pattern in `staking-pool-factory/tests/spec.rs`):
1. Deploy `multisig-factory` contract to `factory` account.
2. As `attacker` (an account with no special privileges), call `factory.create(name="acme", members=[{"public_key": attacker_pk}], num_confirmations=1)` with the minimum deposit; assert the call succeeds and `acme.factory` now exists with `attacker_pk` as its sole member (query via a view call analogous to `multisig2`'s member listing, e.g. simulate `list_request`/state read confirming `members == [attacker_pk]`).
3. As `victim` (the "intended owner"), subsequently call `factory.create(name="acme", members=[{"public_key": victim_pk}], num_confirmations=2)`; observe the transaction fails because `acme.factory` already exists (`CreateAccount` action failure), proving the victim can never obtain the name they intended.
4. Assert the equality that should have held — `members_of("acme.factory") == [victim_pk]` — is false; instead `members_of("acme.factory") == [attacker_pk]`, demonstrating the broken binding and that any funds later sent to `acme.factory` are controlled solely by the attacker.
