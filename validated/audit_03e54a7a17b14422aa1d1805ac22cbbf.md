### Title
First-depositor share-price inflation via direct token donation lets an attacker steal subsequent depositors' funds - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault` mints tranche tokens at `_amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` where the price is NAV-per-tranche-token. Because `getContractValue()` includes the contract's idle `token` balance, a first depositor can mint dust tranche tokens and then donate underlying tokens directly to the CDO, inflating the tranche price to an arbitrary value. Subsequent depositors receive near-zero (or zero, with no revert) tranche tokens for large deposits, and the attacker redeems their dust shares for the victims' funds.

### Finding Description
- `_deposit` calls `_updateAccounting()` and then mints via `_mintSharesAtCurrPrice`, which computes `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` with no minimum-mint check and no revert on `_minted == 0` (`IdleCDOCreditVault.sol` `_mintSharesAtCurrPrice`, `_mintShares`). `_mintShares` still credits `lastNAVAA`/`lastNAVBB` with the full deposited `_underlyings` even when zero shares are minted.
- `_virtualPriceAux` computes `_virtualPrice = (lastTrancheNAV + totalTrancheGain) * ONE_TRANCHE_TOKEN / trancheSupply`. When a tranche has supply > 0, any increase in `nav` is recognized as `totalGain` (minus `fee`) and pushed into the price. With a single active class (`_lastNAV == _lastTrancheNAV`), the entire gain accrues to that class.
- `nav = getContractValue()` counts `strategyTokens * price + _contractTokenBalance(token) - unclaimedFees`, so a plain `ERC20.transfer` of `token` to the CDO raises `nav` and therefore the tranche price on the next accounting update. There is no donation-skim/isolation mechanism for the idle balance (no `_skimDonatedAssets` guard on this path).
- Attack sequence (buffer/running phase, honest privileged roles):
  1. Attacker is first AA depositor: `depositAA(1)` → minted `1 * 1e18 / 1e18 = 1` wei of AA tranche; `lastNAVAA = 1`.
  2. Attacker `transfer`s `D` underlying directly to the CDO (e.g. `D = 100_000e6` USDC).
  3. Victim calls `depositAA(A)`. `_updateAccounting` sees `nav ≈ D + 1`, `totalGain ≈ D`, all of it assigned to AA → `priceAA ≈ (D + 1) * 1e18 / 1`. Minted to victim: `A * 1e18 / priceAA ≈ A / D` shares. For any `A < D` the victim gets 0 or near-0 shares while `lastNAVAA += A`.
  4. Attacker calls `withdrawAA(1)`: burns 1 share at the inflated price and receives ≈ `D + A` — recovering the donation plus the victim's deposit.
- Guards do not stop this: `_guarded` only caps deposit size/TVL, `_checkDefault`/`skipDefaultCheck` only react to strategy price decreases, `whenNotPaused` is unrelated, and there is no minimum first-deposit or dead-share reserve.

### Impact Explanation
Direct theft of user funds. Any depositor whose deposit is smaller than the attacker's donation loses their entire deposit (minted shares round to 0 and NAV is still credited), and larger depositors lose a proportional fraction. Loss is quantified as up to 100% of each post-donation deposit until the tranche supply recovers; the attacker profits `victim deposits − rounding dust`.

### Likelihood Explanation
Requires being the first depositor of a tranche class (or acting while tranche supply is near-zero, e.g. after full withdrawals that leave `trancheSupply` minimal relative to NAV). Deployment scripts that seed initial liquidity mitigate it in practice, but nothing in the contract enforces a minimum first mint, and the condition can recur whenever a tranche class is fully exited and re-entered. Attack cost is the donated amount, which is fully recoverable via the redeem, so the attack only needs a victim deposit to be profitable.

### Recommendation
Enforce a minimum initial mint: on the first deposit of a tranche class (`trancheSupply == 0`), require a minimum deposit amount and mint/burn a reserve of shares to a dead address or `feeReceiver` so `pricePerShare` cannot be inflated by donations. Alternatively, track an internal `totalAssets`-style NAV excluding unsolicited idle `token` balance, or revert in `_mintSharesAtCurrPrice` when `_minted == 0`.

### Proof of Concept
Foundry fork PoC (conceptual, on `IdleCDOCreditVault` during the buffer phase):

```solidity
// test/foundry/ShareInflation.t.sol
function testShareInflation() public {
    // attacker: first AA deposit of 1 wei
    deal(address(token), attacker, 1);
    vm.startPrank(attacker);
    token.approve(address(cdo), 1);
    cdo.depositAA(1);            // mints 1 wei of AA tranche
    vm.stopPrank();
    assertEq(AAtranche.totalSupply(), 1);

    // attacker donates D underlying directly to the CDO
    uint256 D = 100_000 * 10**token.decimals();
    deal(address(token), attacker, D);
    vm.prank(attacker);
    token.transfer(address(cdo), D);

    // victim deposits A < D
    uint256 A = 50_000 * 10**token.decimals();
    deal(address(token), victim, A);
    vm.startPrank(victim);
    token.approve(address(cdo), A);
    cdo.depositAA(A);            // _updateAccounting inflates priceAA first
    vm.stopPrank();
    // victim received ~0 tranche tokens but NAV was credited with A
    assertLt(AAtranche.balanceOf(victim), 1e10);

    // attacker redeems dust share for ~D + A
    uint256 balBefore = token.balanceOf(attacker);
    vm.prank(attacker);
    cdo.withdrawAA(1);
    assertGt(token.balanceOf(attacker) - balBefore, D); // donation + victim funds
}
```

If `getContractValue` excluded idle `token` balance, the analog would instead apply to donations of `strategyToken`, which are counted identically.
