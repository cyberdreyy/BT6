## Title
Global tx-replay set applied to block validation without checking it belongs to the block's own fork/tenure context (`check_block_against_local_state`, `SortitionsView::check_proposal`) — cross-context replay-set reuse - (File: stacks-signer/src/v0/signer.rs, stacks-signer/src/chainstate/v1.rs, stacks-signer/src/v0/signer_state.rs)

### Summary
The v0 (v1 sortition-state) proposal-validation path passes a `ReplayTransactionSet` into `check_proposal` and checks a block's transactions against it (via `is_in_replay` / read-count-extend gating and node-side prefix matching), but the value fed in is the **global** replay set (`self.global_state_evaluator.get_global_tx_replay_set().unwrap_or_default()`), not one that is verified to be scoped to *this* block's tenure/fork. The fork-context binding for a replay set (`ReplayScope { fork_origin, past_tip }`) is tracked only as an **in-memory, unpersisted field on the `Signer` struct** (`tx_replay_scope: ReplayScopeOpt`) — a fact the code itself documents as fragile ("Possibly caused by the scope being a local state in the Signer struct, which is not persisted" — `ReplayState::infer_state`, `stacks-signer/src/v0/signer_state.rs:105-136`). This is structurally the same defect class as the reported CVE: authentication/authorization *state* computed for one context (proxyA / one Bitcoin fork) is carried forward and applied unconditionally to a *different* context (proxyB / a different, later fork or tenure) because only the explicit path (an actual local fork-detection transition) clears/rebinds it, while other code paths that consume the state (validation calls, global-state fallbacks) don't re-verify which context it belongs to. [1](#0-0) [2](#0-1) 

### Finding Description
`SortitionsView::check_proposal` (v1 chainstate) takes a `replay_set: ReplayTransactionSet` argument and uses it, among other things, to decide whether a read-count tenure-extend is currently permitted (`is_in_replay = replay_set.is_some()`), bypassing the normal idle-timeout gate when the signer believes it is "in replay": [3](#0-2) 

The caller that supplies this set in production, `check_block_against_local_state`, does not derive it from the block being checked or its tenure — it pulls the **global consensus** replay set: [2](#0-1) 

`GlobalStateEvaluator::get_global_tx_replay_set()` and the `StateMachineUpdateContent`/`SignerStateMachine` wire format only carry `tx_replay_set` (the transaction list) — they never carry the `ReplayScope` (`fork_origin`, `past_tip`) that ties that set to a specific Bitcoin fork: [4](#0-3) 

The scope only exists locally, per-process, in the `Signer::tx_replay_scope` field, and the code that infers whether the local machine is validly "in replay" explicitly acknowledges the scope can be silently absent because it "is a local state in the Signer struct, which is not persisted" (`ReplayState::infer_state`). Meanwhile the transaction list itself (`tx_replay_set`) *is* propagated through `SignerStateMachine`/`StateMachineUpdate` and is durable enough to survive a `capitulate_viewpoint` transition (carried forward unchanged into a brand-new `SignerStateMachine` when the miner view flips) and to be echoed by `GlobalStateEvaluator` from every signer's broadcast state: [5](#0-4) 

Consequence: the equality this is supposed to preserve is "the transactions this block is being validated/gated against actually belong to the fork this block's tenure is replaying." Because the replay *set* travels through global consensus independent of its *scope*, a signer can end up gating a proposal from a *new, unrelated* tenure/fork (i.e., a different "proxy" in the CVE's terms) using a leftover global replay set that was legitimately computed for a *prior* fork. The `is_in_replay` gate in `validate_tenure_change_payload`'s read-count-extend branch is exactly the kind of check that this leftover state can silently satisfy, letting a tenure-extend bypass the idle-timeout requirement in a tenure it has no real relationship to the stale replay context.

### Impact Explanation
This does not meet the bar of "sign an invalid/non-canonical/conflicting block" outright, and I was not able to fully trace, within the available search budget, a path that turns this into a signature over a block the node itself would reject (the `/v3/block_proposal` endpoint independently re-validates the actual replay-tx ordering against its own node-local replay computation — see `stackslib/src/net/api/postblock_proposal.rs`). The signer-side gate only affects whether the **read-count tenure-extend** is *locally* considered eligible before the node validates the block; the node is the final backstop for the transaction-replay contents themselves.

Given that the node revalidates transaction contents independently, I could not confirm a concrete safety break (a signature that the rest of the network would treat as valid over content the node would reject) or a liveness wedge within the scope investigated. The mismatch between a persisted/broadcast `tx_replay_set` and an unpersisted, unscoped `tx_replay_scope` is a genuine structural weakness (explicitly flagged as fragile in the code's own comments) that closely mirrors the reported CVE's pattern of state crossing between two contexts via an implicit propagation path, but I cannot substantiate, with the evidence gathered, that it currently reaches one of the required Critical/High impacts (invalid/non-canonical/conflicting signature, miscounted vote, cross-context signature, or a liveness wedge) without further tracing that exceeds what was retrievable via search (in particular, the full body of `handle_fork_for_new_replay`/`handle_fork_on_in_progress_replay` and how `tx_replay_scope` is reconciled against `tx_replay_set` on every `bitcoin_block_arrival` and capitulation transition would need direct file review to rule in or out an exploitable divergence).

### Likelihood Explanation
Unconfirmed — requires a signer restart or a specific bitcoin-fork/tenure sequencing that decouples the locally tracked `tx_replay_scope` from the broadcast `tx_replay_set` while a read-count tenure-extend proposal is in flight; I could not verify from the retrieved code whether existing guards (`handle_possible_bitcoin_fork`, `handle_possible_replay_failsafe`) fully close this window in all cases.

### Recommendation
Persist the `ReplayScope` alongside `tx_replay_set` (or bind the two atomically in one persisted/broadcast structure) so that any consumer of a replay set — local or derived from global consensus — can verify it applies to the tenure/fork of the block currently being evaluated before using it to gate any check (in particular the `is_in_replay` bypass in `validate_tenure_change_payload`). Treat a `tx_replay_set` with no verifiably-matching scope for the current block's tenure as "not in replay" rather than defaulting to a permissive `unwrap_or_default()`/`is_some()` check.

### Proof of Concept
Not constructed — this analysis is based on static tracing of the code's own documented fragility (`ReplayState::infer_state`'s comment) and the observed gap between what is persisted/broadcast (`tx_replay_set`) versus what is only held in local process memory (`tx_replay_scope`). I was unable to build a concrete end-to-end sequence (restart timing, fork sequencing, and the node's independent revalidation) within the tool budget to demonstrate an actual signature-safety violation; this should be validated further with direct access to `handle_fork_for_new_replay`, `handle_fork_on_in_progress_replay`, and the full `bitcoin_block_arrival` state-transition logic before treating it as a confirmed vulnerability.

impl ReplayState {
    /// Infers the appropriate `ReplayState` based on the contents of the replay transaction set
    /// and the optional scope.
    ///
    /// # Arguments
    ///
    /// * `replay_set` - A reference to a set of transactions intended for replay.
    /// * `scope_opt` - An optional scope defining the boundaries or context for the replay.
    ///
    /// # Returns
    ///
    /// * `Some(ReplayState::Unset)` if the `replay_set` is empty.
    /// * `Some(ReplayState::InProgress)` if the `replay_set` is non-empty and a `scope` is provided.
    /// * `None` if the `replay_set` is non-empty but no `scope` is provided.
    ///   - Possibly caused by the scope being a local state in the `Signer` struct, which is not persisted.
    fn infer_state(replay_set: &ReplayTransactionSet, scope_opt: &ReplayScopeOpt) -> Option<Self> {
        if replay_set.is_empty() {
            return Some(Self::Unset);
        }

        scope_opt
            .as_ref()
            .map(|scope| Self::InProgress(replay_set.clone(), scope.clone()))
    }
