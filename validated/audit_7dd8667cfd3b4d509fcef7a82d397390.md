### Title
Underfunded instant-withdraw queue at `startEpoch` permanently blocks `stopEpoch` and freezes all LP funds - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
CVE-2017-13140 is a boundary-condition hang: a PNG with width exactly equal to `MAGICK_WIDTH_LIMIT` wedges `ReadOnePNGImage` in `LockSemaphoreInfo`. The analog in idle-tranches is the liquidity boundary check in `startEpoch`: when the aggregate pending instant-withdraw amount exceeds the underlyings liquid on the CDO, the function takes an early-return branch that leaves `pendingInstantWithdraws` non-zero. Because `_stopEpoch` hard-reverts whenever `_pendingInstant() != 0`, the epoch can never be closed and every deposited underlying is frozen.

### Finding Description
In `IdleCDOEpochVariant.startEpoch`, after skimming donations the CDO computes `pendingInstant = _pendingInstant()` and `totUnderlyings = _contractTokenBalance(token)` and calls `collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings))` on `IdleCreditVault`. `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` by the amount actually collected, so when `pendingInstant > totUnderlyings` the residual stays positive [1](#0-0) . In that case `startEpoch` returns early without setting `allowInstantWithdraw = true` [2](#0-1) .

`stopEpoch`/`_stopEpoch` then reverts on `_pendingInstant() != 0` with `NotAllowed` [3](#0-2) . There is no path for the residual to clear:

- `claimInstantWithdrawRequest` is gated by `allowInstantWithdraw`, which was never set [4](#0-3) .
- `collectInstantWithdrawFunds` is `_onlyIdleCDO()` and is only invoked inside `startEpoch` [5](#0-4) ; no other CDO function re-collects instant funds, and a new `startEpoch` requires the epoch to be stopped first.
- `isEpochRunning` stays true, blocking `unpause`/`restoreOperations` (`_beforeUnpause` reverts while `isEpochRunning`) and `depositDuringEpoch` once `epochEndDate` passes [6](#0-5) .

An unprivileged KYC-passed lender creates the condition by holding tranche tokens and calling `requestWithdraw` during the buffer when the instant-withdraw APR condition (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`) holds, requesting an amount larger than the CDO's liquid underlying balance. Because nearly all liquidity is lent to the borrower during a running epoch, the liquid balance at the next `startEpoch` is typically only buffered deposits plus repaid interest, so the attacker's required position is small relative to TVL. This mirrors the CVE: an input sized past a limit (`pendingInstant > totUnderlyings`) drives the state machine into a hang it cannot exit.

### Impact Explanation
All LP funds (AA and BB principal plus accrued interest already sent to the borrower) are frozen for as long as the borrower does not voluntarily return funds outside the epoch flow. `stopEpoch` is the only function that recalls principal and funds pending receipts, and it reverts deterministically. Withdrawal requests, claims, and deposits are all halted — `requestWithdraw`/`claimInstantWithdrawRequest` are disabled and deposits are paused for the whole epoch. This is temporary freezing of the entire vault TVL; it becomes effectively permanent if the honest borrower has no out-of-band repayment path.

### Likelihood Explanation
Likelihood is moderate. Prerequisites: instant withdrawals enabled (`instantWithdrawAprDelta` configured and an APR decrease across epochs), plus an attacker wallet passing `isWalletAllowed`. The attacker bears no direct cost — their own request is also frozen — but the attack scales trivially because the contract's liquid balance is minimal mid-cycle. The honest owner/manager cannot unwind it: `restoreOperations` returns early while `isEpochRunning` and `emergencyShutdown` does not clear `pendingInstantWithdraws`.

### Recommendation
In `startEpoch`, when `pendingInstant > totUnderlyings`, either (a) still set `allowInstantWithdraw = true` and let `collectInstantWithdrawFunds` be re-invoked later (e.g., expose a manager/keeper function to pull additional instant funds once the borrower repays or once more underlying accrues), or (b) haircut/partially fulfill instant receipts proportionally and zero `pendingInstantWithdraws` so `_stopEpoch` can proceed. At minimum, add an escape hatch that clears the unfunded residual (converting it into a normal pending withdrawal recorded via `withdrawsRequestsByEpoch`/`lossRecoveryPriceByEpoch`) instead of blocking the epoch state machine.

### Proof of Concept
```solidity
// test/foundry/PocInstantWithdrawFreeze.t.sol — fork of IdleCreditVault.t.sol harness
function testPocInstantWithdrawStarvesStopEpoch() external {
    // enable instant withdrawals: 100s delay, 1% min APR delta
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    // honest LP deposits
    idleCDO.depositAA(10_000 * ONE_SCALE);

    // attacker deposits a position larger than expected liquid balance
    address attacker = makeAddr("attacker");
    uint256 atkAmt = 2_000 * ONE_SCALE;
    uint256 atkTranches = _depositWithUser(attacker, atkAmt);

    // epoch 0 runs at high APR
    _startEpochAndCheckPrices(0);
    // stop epoch setting a much lower APR for next epoch -> instant path opens
    _stopCurrentEpochWithApr(1e18);

    // buffer: attacker requests instant withdraw exceeding liquid CDO balance
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(atkTranches, address(AAtranche));
    // instant requests burn tranches and mint receipts via requestInstantWithdraw

    // next startEpoch: pendingInstant > totUnderlyings -> early return, residual stays
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod());
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertGt(strategy.pendingInstantWithdraws(), 0, "residual instant pending");
    assertFalse(cdoEpoch.allowInstantWithdraw(), "claims disabled");

    // epoch ends; borrower is fully funded to repay
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // stopEpoch can never succeed -> LP funds frozen
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // no rescue: unpause/restoreOperations also blocked while epoch is running
    vm.prank(owner);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.unpause();
}
```

Uncertainty note: I could not fully inspect `_pendingInstant()`'s definition (e.g., whether it discounts requests past `instantWithdrawDeadline`). If it zeroes stale requests, the freeze window is bounded by that deadline rather than indefinite, but the underfunded residual still blocks `stopEpoch` until it clears, and the core issue — no mechanism to fund or convert the residual — stands.
