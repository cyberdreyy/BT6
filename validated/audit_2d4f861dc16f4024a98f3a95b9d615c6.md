### Title
Leftover IDLE rewards permanently locked in `DelegateStakingRewardsIDLE` when a new period starts or no stakers exist - (File: contracts/DelegateStakingRewardsIDLE.sol)

### Summary
`DelegateStakingRewardsIDLE` follows the same Synthetix `notifyRewardAmount` pattern as the external report, renamed to `depositReward`. Rewards that are not allocated to stakers — because `depositReward` is called after `periodFinish`, or because rewards stream while `_totalSupply == 0` — accumulate in the contract. The only recovery path, `recoverERC20`, rejects `stakingToken`, and in this deployment `rewardsToken == stakingToken == IDLE`, so the residue is permanently unrecoverable.

### Finding Description
In `depositReward` (contracts/DelegateStakingRewardsIDLE.sol:151-173), when `block.timestamp >= periodFinish` the new `rewardRate` is set to `reward / rewardsDuration` and any un-distributed remainder of the previous period is silently dropped from accounting — it stays as a token balance but is owed to no one. Similarly, `rewardPerToken()` (lines 69-74) returns `rewardPerTokenStored` unchanged when `_totalSupply == 0`, so all rewards emitted between `lastUpdateTime` and `periodFinish` while nobody is staked accrue to zero stakers and are never claimable via `earned`/`getReward`.

The recovery escape hatch does not cover this case:

```solidity
// contracts/DelegateStakingRewardsIDLE.sol:176-180
function recoverERC20(address tokenAddress, uint256 tokenAmount) external onlyOwner {
    require(tokenAddress != address(stakingToken), "Cannot withdraw the staking token");
    IERC20(tokenAddress).safeTransfer(owner(), tokenAmount);
}
```

`stakingToken` is `IDLE` (constructor line 52 even calls `IIdle(stakingToken).delegate(...)`), and `rewardsToken` is set independently but is also `IDLE` for this contract (it exists to delegate IDLE voting power while distributing IDLE rewards to whitelisted stakers). When `rewardsToken == stakingToken`, the `require` blocks any withdrawal of the reward token, so residue can never be swept. No `totalRewardAmount`/solvency tracking exists to distinguish "owed to stakers" from "stuck residue", unlike e.g. `ERC4626Strategy.transferToken` which explicitly documents a leftovers sweep (contracts/strategies/ERC4626Strategy.sol:128-139).

### Impact Explanation
Permanent freezing of unclaimed yield. Every time `rewardsDistribution` tops up after `periodFinish` instead of before, the leftover `remaining * rewardRate` worth of IDLE becomes unclaimable. Likewise, any rewards streamed during windows with zero staked supply are burned-equivalent. The loss is bounded by the reward stream but repeats every such period; for a gauge-style contract funded periodically this is a recurring leak of governance-token rewards intended for stakers.

### Likelihood Explanation
- `depositReward` is called by `rewardsDistribution` (the IdleCDO) on harvest cadence; any call landing after `periodFinish` orphans the remainder rather than rolling it over.
- Whitelist-gated staking plus `exit()` makes zero-`totalSupply` windows realistic (all whitelisted stakers exit, rewards keep streaming until `periodFinish`).
- No privileged actor is required; the loss materializes from ordinary sequencing of honest `depositReward` calls and user exits.

### Recommendation
Track owed rewards explicitly and permit sweeping only the excess after `periodFinish` and once obligations are settled:

```solidity
uint256 public totalRewardOwed; // sum of rewards[account] accrued

// in updateReward(account): totalRewardOwed += earned(account) - rewards[account] delta
// in getReward(): totalRewardOwed -= reward paid

function sweepStuckRewards() external onlyOwner {
    require(block.timestamp >= periodFinish, "period active");
    uint256 stuck = rewardsToken.balanceOf(address(this)) - totalRewardOwed - _totalSupply;
    rewardsToken.safeTransfer(owner(), stuck);
}
```

If `rewardsToken != stakingToken` is guaranteed by deployment, at minimum relax `recoverERC20` to allow sweeping `rewardsToken` balances exceeding `totalRewardOwed` after `periodFinish`. Alternatively, roll over leftover on the `block.timestamp >= periodFinish` branch too (treat undistributed residue as part of the new `reward`).

### Proof of Concept
Foundry fork test sketch (contracts-style, `forge test --fork-url $MAINNET`):

```solidity
function test_StuckRewards_AfterPeriodAndZeroStakers() public {
    // IDLE = stakingToken = rewardsToken
    deal(IDLE, rewardsDistribution, 1000e18);

    // Period 1: no one stakes, rewards still stream
    vm.prank(rewardsDistribution);
    IERC20(IDLE).approve(address(staking), 1000e18);
    vm.prank(rewardsDistribution);
    staking.depositReward(address(0), 1000e18);

    // entire duration elapses with _totalSupply == 0
    vm.warp(block.timestamp + 7 days + 1);

    // Period 2: new deposit does NOT roll over the 1000e18 residue
    deal(IDLE, rewardsDistribution, 700e18);
    vm.startPrank(rewardsDistribution);
    IERC20(IDLE).approve(address(staking), 700e18);
    staking.depositReward(address(0), 700e18); // block.timestamp >= periodFinish branch
    vm.stopPrank();

    // 1000e18 from period 1 is owed to nobody; rewardRate only accounts for 700e18
    // A whitelisted user stakes, earns, and fully exits
    deal(IDLE, alice, 100e18);
    vm.startPrank(alice);
    IERC20(IDLE).approve(address(staking), 100e18);
    staking.stake(100e18);
    vm.warp(block.timestamp + 7 days);
    staking.exit();
    vm.stopPrank();

    uint256 residue = IERC20(IDLE).balanceOf(address(staking));
    assertGt(residue, 0); // ~1000e18 of orphaned rewards remain

    // Owner cannot recover: rewardsToken == stakingToken => revert
    vm.expectRevert("Cannot withdraw the staking token");
    vm.prank(owner);
    staking.recoverERC20(IDLE, residue);
}
```

The residue has no claim path: `earned` only distributes `rewardRate`-accounted amounts, `getReward` pays only recorded `rewards[account]`, and `recoverERC20` reverts on the reward/staking token, so the ~1000 IDLE is locked forever.
