### Title
Stale Confirmations From Deleted Multisig Members Are Still Counted Toward Execution Threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` executes a pending request once the number of entries in its `confirmations: HashSet<String>` reaches `num_confirmations`. `delete_member` (invoked via a `DeleteMember` request) only purges pending requests that the removed member itself originated; it never scans other members' pending requests to strip out confirmations previously cast by the member being removed. Consequently, a confirmation cast by a member who is later removed remains permanently counted toward the threshold of any request they didn't originate, letting a request execute with fewer live, currently-authorized confirmations than `num_confirmations` requires.

### Finding Description
`confirm` decides execution purely by comparing the size of the stored confirmation set to `num_confirmations`: [1](#0-0) 

`delete_member`, which is the only code path that removes a member and cleans up multisig state, filters `self.requests` for requests where `r.member == member` (i.e., requests *added* by that member) and clears confirmations only for those requests. It never inspects `self.confirmations` for other requests where the departing member is merely a *confirmer*: [2](#0-1) 

The same gap exists in the legacy `multisig` contract: `DeleteKey` only clears confirmations for requests whose `signer_pk` (the originator) matches the removed key, not requests the key merely confirmed: [3](#0-2) [4](#0-3) 

The invariant the contract is supposed to enforce is:
`confirmations_recorded_by_live_members(request) >= num_confirmations` before execution.

What is actually enforced is:
`|confirmations set (possibly containing removed members)| >= num_confirmations`.

These two are not equal once a confirming member is removed while their confirmation is still attached to an outstanding request added by someone else.

### Impact Explanation
This is a multisig request executed below the effective threshold: a departed/compromised member's stale vote continues to count as legitimate authorization after that member is stripped of membership, permanently lowering the number of currently-authorized signers needed to push a `Transfer`, `AddKey`, `FunctionCall`, `AddMember`/`DeleteMember`, or `DeployContract` action through. In the worst case this allows funds to move, keys to be added, or contract code to be deployed with fewer live approvals than the configured `K` of `K-of-N` scheme — a direct violation of the multisig's core custody guarantee (`Critical`: "a multisig request executed below threshold").

### Likelihood Explanation
This does not require any misuse of privilege beyond the ordinary, documented multisig lifecycle: (1) a member confirms a pending request that they did not originate, (2) that member is later removed via a normal `DeleteMember`/`DeleteKey` action (e.g., because the key is thought compromised, or the employee left), and (3) the previously-cast confirmation remains attached and is later combined with fresh confirmations from remaining members to reach the threshold. Any organization that rotates or revokes multisig membership while requests are outstanding is exposed, and revoking a member is precisely the scenario administrators expect to fully and immediately remove that member's influence.

### Recommendation
When removing a member, iterate over all pending `confirmations` entries (not just the requests the member originated) and remove that member's identifier from every confirmation set. Alternatively, validate at `confirm`/execution time that every account or public key present in the stored confirmation set is still a current member of `self.members`, discarding stale entries before comparing the count to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 2`.
2. `A.add_request(transfer_to_attacker)` creates request `R` (0 confirmations).
3. `B.confirm(R)` — 1 confirmation recorded (`{B}`), not yet enough to execute.
4. Legitimately remove `B` from the multisig via a fully-confirmed `DeleteMember { member: B }` request. `delete_member` only clears confirmations/requests where `B` was the *originator*; `R` (originated by `A`) still has `B` in its confirmation set.
5. `C.confirm(R)` — `confirmations.len() + 1 == 2 >= num_confirmations`, so `R` executes with `B`'s now-stale, unauthorized confirmation counted, even though only `A` and `C` are actually live members participating, and `B` no longer has any standing in the contract.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
