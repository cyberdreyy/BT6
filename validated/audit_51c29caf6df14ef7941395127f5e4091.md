### Title
Drained ERC4626 vault liquidity makes `stopEpoch` permanently revert via `StopEpochVaultLiquidityUnavailable`, freezing all epoch funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In the programmable-borrower mode, `IdleCDOEpochVariant.stopEpoch` calls `ProgrammableBorrower.onStopEpoch`, which must pull `_amountRequired` from the configured ERC4626 vault. When the vault's share price still economically covers the shortfall (`shortfall <= _currentVaultAssets()`) but the vault has no immediately withdrawable underlying liquidity, `vault.withdraw` reverts and the `catch` block reverts the whole call with `StopEpochVaultLiquidityUnavailable`. Because this revert propagates up through `stopEpoch`, the honest manager/owner can never stop the epoch while the vault is illiquid, so no borrower default can be declared and no lender withdrawal path opens — an analog of the ZServer "uncaught exception crashes the worker" DoS, mapped onto the epoch state machine. [1](#0-0) 

### Finding Description
`onStopEpoch` handles three cases:

1. `_isRequestingAllFunds` with outstanding borrower debt → return `false` (handled as default).
2. `shortfall > _currentVaultAssets()` → return `true` and let the CDO's `transferFrom` fail, which takes the existing default path.
3. Otherwise → `try vault.withdraw(...)`, and on any revert `revert StopEpochVaultLiquidityUnavailable()`.

Case 3 conflates "shares are worth enough" (`convertToAssets`-based solvency) with "shares are redeemable now". Many ERC4626 vaults (lending/credit-style vaults in particular) hold illiquid positions: `convertToAssets` still reports full value while `withdraw`/`redeem` reverts or returns less because idle cash is lent out. An unprivileged user of that same ERC4626 vault can create this state on demand by simply withdrawing (or borrowing, depending on vault type) all of the vault's liquid underlying before `stopEpoch` is called.

Since `epochAccountingActive` is only cleared *after* the withdraw succeeds (lines 259-265), every subsequent `stopEpoch` retry takes the same path and reverts identically while the vault stays illiquid. There is no fallback path that treats "covered but unredeemable" as a default, and `onDefault` can only be reached *through* the CDO's stop/default flow, which is exactly what is being reverted.

Sequence (epoch running, prefunded/programmable mode):

1. Lenders deposited; manager calls `startEpoch`. `onStartEpoch` parks all idle underlying into the vault (`_depositToVault` at line 216).
2. Epoch ends; manager must call `stopEpoch` to pull `_amountRequired` = pending withdraws + expected interest from `ProgrammableBorrower`.
3. Attacker, as an ordinary ERC4626 vault user, withdraws/borrows the vault's free underlying so the vault is illiquid but still solvent (share price unchanged).
4. Manager calls `stopEpoch` → `onStopEpoch` → `vault.withdraw(shortfall)` reverts → `StopEpochVaultLiquidityUnavailable` → `stopEpoch` reverts.
5. Repeat ad infinitum: epoch can never be stopped, `defaulted` is never set, `claimWithdrawRequest`/`claimInstantWithdrawRequest` stay gated, and lender funds are frozen for as long as the attacker keeps the vault drained (cheap to sustain in credit-style vaults, or free if the vault is naturally illiquid).

### Impact Explanation
Temporary freezing of all funds in the credit vault: pending normal withdraw requests, instant withdraw requests, and all tranche principal remain locked because `stopEpoch` cannot complete and the default/finalization path (`finalizeDefault` → `finalizeDefaultRecovery`) is only reachable after a stopped/defaulted epoch. The freeze duration is attacker-controlled: for a lending-style ERC4626 vault the attacker can keep liquidity extracted for the entire borrow duration, and re-drain whenever liquidity returns, at the cost of normal vault usage (no privileged role required). This matches the accepted "temporary freezing" impact class with quantifiable exposure equal to the entire pool NAV for the duration of the freeze.

### Likelihood Explanation
- Attacker capability: any unprivileged EOA that can use the shared ERC4626 vault — explicitly within the allowed attacker set.
- Trigger cost: one `withdraw`/`borrow` transaction on the external vault, timed just before `stopEpoch` (manager calls are public and predictable at `epochEndDate`).
- No existing guard prevents it: the `shortfall > _currentVaultAssets()` check (line 245) only catches *insolvency*, not *illiquidity*; the `try/catch` deliberately reverts instead of degrading to the default path; `nonReentrant` and `_checkOnlyIdleCDO` do not help.
- Dependency: requires the configured vault to be of a type where shares can be worth full value while spot withdrawals fail — a standard property of lending/credit ERC4626 vaults, which is precisely the stated purpose of this contract ("keep undrawn capital parked inside an ERC4626 vault").

### Recommendation
Treat a failed `vault.withdraw` inside `onStopEpoch` the same way as an insolvent vault: return `true` (or a dedicated status) and let `IdleCDOEpochVariant`'s `transferFrom` shortfall logic route into the existing borrower-default path, which correctly sets `defaulted` and enables `finalizeDefault`/`onDefault` (note `onDefault` already avoids touching the vault's valuation views for exactly this robustness reason, lines 289-301). Alternatively, first attempt a bounded `vault.redeem`/`maxWithdraw` of whatever is available and pass the residual shortfall through to the CDO so it can declare default, rather than reverting the state transition itself. The epoch state transition must never depend on a third-party vault's instantaneous liquidity.

### Proof of Concept
Foundry fork sketch (deploy `IdleCreditVault` + `IdleCDOEpochVariant` wired to `ProgrammableBorrower` pointing at a lending-style ERC4626, or a mock vault whose `withdraw` reverts when its idle balance is drained while `convertToAssets` stays constant):

```solidity
// setup: lender deposits AA, manager calls startEpoch()
//      -> ProgrammableBorrower.onStartEpoch deposits all idle underlying into `vault`
idleCDO.depositAA(100_000e6);
vm.prank(manager);
cdoEpoch.startEpoch();

// attacker: ordinary user of the same ERC4626 vault drains its liquid underlying
// (vault shares still cover, convertToAssets unchanged, but withdraw() now reverts)
vm.prank(attacker);
externalVault.withdraw(externalVault.maxWithdraw(attacker), attacker, attacker);
// or: lendingVault.borrow(...) such that cash == 0

// warp past epoch end, manager tries to stop the epoch
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);

// retries keep reverting; no default can be declared, no claims open
vm.prank(manager);
vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0);
assertFalse(cdoEpoch.defaulted());          // never set
vm.prank(lender);
vm.expectRevert(NotAllowed.selector);       // claimWithdrawRequest still gated
cdoEpoch.claimWithdrawRequest();
// lender funds remain frozen while attacker keeps vault illiquid
```

```text
  function onStopEpoch(uint256 _amountRequired, bool _isRequestingAllFunds) external nonReentrant returns (bool success) {
    _checkOnlyIdleCDO();
    _accrueBorrowerInterest();
    // if we want to close the pool and the borrower still owes any amount, consider it a failure and let IdleCDO handle it as a default instead of a close. 
    if (_isRequestingAllFunds && (borrowerPrincipal != 0 || borrowerInterestDebt != 0 || borrowerInterestAccrued != 0)) {
      return false;
    }

    uint256 onHand = underlyingToken.balanceOf(address(this));
    if (_amountRequired > onHand) {
      uint256 shortfall = _amountRequired - onHand;
      // If the vault shares do not economically cover the shortfall, let IdleCDO's later
      // transferFrom fail and use the existing default path. Only an otherwise-covered ERC4626
      // withdrawal failure should make stopEpoch retryable.
      if (shortfall > _currentVaultAssets()) return true;
      try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        if (epochAccountingActive) {
          epochWithdrawnFromVault += shortfall;
        }
        emit WithdrawnFromVault(shortfall, shares, address(this));
      } catch {
        revert StopEpochVaultLiquidityUnavailable();
      }
```
