### Title
Late-epoch APR0 withdraw requests steal epoch interest from earlier requesters and active LPs - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
In the Curves bug, fee distribution tracking (`onBalanceChange`) is skipped once `holdersFeePercent` is set to zero, so a new shareholder can claim fees accrued before they joined. The analog in this codebase is the APR=0 withdraw flow in `IdleCreditVault`: when `unscaledApr == 0`, withdraw-requested principal is bucketed and, at `stopEpoch`, receives a pro-rata share of the whole epoch's realized interest via `prepareStopEpochWithApr0`. The per-epoch rate `apr0RateByEpoch` is a snapshot computed only from `apr0TotalPrincipal` at `stopEpoch` — there is no time-weighting or "balance change" checkpoint. An attacker who requests a withdraw in the last transaction before `stopEpoch` earns the same full-epoch rate as requesters who locked for the entire epoch, diluting them, and also inflates the APR0 bucket's share of interest at the expense of active tranche holders.

### Finding Description
`requestWithdraw` routes requests to `_requestWithdrawApr0` when `unscaledApr == 0`, adding `_amount` to the user's open APR0 bucket (`apr0Users[_user].principal`) and the global `apr0TotalPrincipal`, tagged with the current `epochNumber`. At epoch end, `prepareStopEpochWithApr0` computes:

```solidity
uint256 _apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit;
...
apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;
```

where `_principal = apr0TotalPrincipal` measured at `stopEpoch` time. The stored rate is uniform for every requester in that epoch regardless of when during the epoch the request was made, and the bucket's gross share grows linearly with total bucket principal. There is no equivalent of a per-block/per-second accrual or an `onBalanceChange`-style checkpoint that would tie a requester's claim to how long their principal was actually in the bucket.

Attack sequence (running epoch, APR0 mode — i.e., `unscaledApr == 0`):

1. Victim deposits early, calls `requestWithdraw` at epoch start; their principal sits in the APR0 bucket for the whole epoch duration.
2. Attacker (a KYC-passed lender) deposits and calls `requestWithdraw` via the CDO in the block immediately before `stopEpoch`.
3. `stopEpoch` → `prepareStopEpochWithApr0` splits the full epoch interest pro-rata over `apr0TotalPrincipal`, now including the attacker's just-added principal.
4. After `epochNumber` increments, both victim and attacker settle via `_settleApr0` / `claimWithdrawRequest` at the identical `apr0RateByEpoch` rate.

The attacker receives `attackerPrincipal * apr0RateByEpoch / 1e18` despite having been in the bucket for ~0% of the epoch, and the increased `_principal / _totalPrincipalForSplit` ratio simultaneously shrinks `_expInterest` left for active AA/BB LPs.

### Impact Explanation
Direct theft of yield: earlier APR0 requesters' `settledInterest` is reduced proportionally to the attacker's share of the bucket, and active tranche holders lose interest because the APR0 bucket's gross allocation `_interestNetOfFees * _principal / (_tvl + _principal)` grows with the attacker's principal. The stolen amount is bounded by the epoch's net interest but scales with attacker principal; with a large deposit the attacker can capture the majority of the APR0 bucket's epoch interest having borne no time exposure. No privileged misbehavior is required — only a running epoch with `unscaledApr == 0` and the honest manager/borrower calling `stopEpoch`.

### Likelihood Explanation
Requires the vault to operate in APR0 mode (`unscaledApr == 0`, a supported configuration with dedicated accounting) and the attacker to hold enough capital to meaningfully dilute `apr0TotalPrincipal`. Any unprivileged whitelisted lender can execute it in a single transaction pair (deposit + request) just before `stopEpoch`; there is no timing-window guard, minimum-epoch-tenure check, or deposit/request same-block restriction applied to the APR0 bucket. The pattern is repeatable every epoch.

### Recommendation
Time-weight the APR0 interest instead of using a flat per-epoch snapshot, or treat the request epoch boundary atomically: e.g., record each request's entry time and accrue `rate * timeInBucket / epochDuration`, or only grant `apr0RateByEpoch` to principal that was in the bucket for the full epoch (requests made during epoch N settle at epoch N+1's rate). At minimum, exclude requests made in the same block/late window as the `stopEpoch` call from that epoch's rate, analogous to always calling `onBalanceChange` before the fee pool state changes.

### Proof of Concept
Fork a mainnet credit vault configured with `unscaledApr == 0` (APR0 mode) and an active epoch:

```solidity
function testApr0LateJoinerDilution() public {
    // Epoch N running, unscaledApr == 0
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    // Victim deposits and requests withdraw at epoch start
    _depositWithUser(victim, 100_000e6);
    vm.prank(victim);
    cdo.requestWithdraw(AAbal(victim), address(AAtranche));

    // Warp to just before stopEpoch; attacker deposits + requests withdraw
    vm.warp(epochEnd - 1);
    _depositWithUser(attacker, 900_000e6);
    vm.prank(attacker);
    cdo.requestWithdraw(AAbal(attacker), address(AAtranche));

    // Borrower repays principal + interest; manager stops epoch
    _stopEpochWithBorrowerRepay();

    // Both claims settle at the SAME apr0RateByEpoch[epochN]
    uint256 rate = vault.apr0RateByEpoch(epochN);
    // Attacker captures ~90% of the APR0 bucket's full-epoch interest
    // despite ~1 block of tenure; victim's settledInterest is cut ~90%.
    vm.prank(attacker);
    uint256 stolen = cdo.claimWithdrawRequest();
    assertGt(stolen - attackerPrincipal, victimInterestExpected * 9 / 10);
}
```
