### Title
Miner-side vote tally lets a signer's stale rejection weight persist after it flips to acceptance, breaking `total_weight_approved`/`total_weight_rejected` vs. real signer intent — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The bug class in the ZetaChain report is a running-total accumulator that is incremented on one branch of a vote but never correspondingly decremented on the other, so the aggregate no longer reflects the true current tally. The `StackerDBListener` in this repo maintains exactly this kind of accumulator — `BlockStatus.total_weight_approved` / `total_weight_rejected` — and it has the same asymmetry: a signer's weight can be added to *both* pools for the same block, with no decrement ever applied to the stale side.

### Finding Description
`BlockStatus` tracks two independent running counters plus two different "already counted" guards: [1](#0-0) 

On `BlockResponse::Accepted`, weight is added to `total_weight_approved` guarded by `gathered_signatures.contains_key(&slot_id)`: [2](#0-1) 

On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` guarded by a *different* set, `responded_signers.insert(slot_id)`: [3](#0-2) 

Because the accept path's guard (`gathered_signatures`) is disjoint from the reject path's guard (`responded_signers`), a signer that first rejects a block (adding its weight to `total_weight_rejected` and inserting itself into `responded_signers`) and later — per the documented "reconsider on new reject reason" flow — sends `Accepted` for the *same* block hash, will have its weight added a second time, now to `total_weight_approved`, since `gathered_signatures` did not yet contain its slot id. Nothing in this code path ever decrements `total_weight_rejected` when that happens. This is the exact analog of the ZetaChain bug: a state flip on one side of a binary vote is not mirrored by an equal-and-opposite adjustment of the other accumulator, so `total_weight_approved + total_weight_rejected` can exceed the real, current signer intent and can exceed `total_weight` itself.

This corrupted `total_weight_rejected` is consumed directly by the coordinator's decision loop, which checks the rejection condition *before* the acceptance condition: [4](#0-3) 

Because the check at line 509-513 is evaluated first and returns immediately with `NakamotoNodeError::SignersRejected`, a block that has genuinely accumulated enough *current* approving weight to clear `weight_threshold` can still be discarded as rejected purely because of leftover, stale rejection weight from signers who have since reconsidered and accepted — weight that was never backed out of `total_weight_rejected`.

### Impact Explanation
This breaks the "aggregated-weight vs. verified-accepts" equality explicitly called out in scope: the miner's rejected-weight tally no longer represents the set of signers who currently reject the block. Concretely: a valid, sufficiently-signed block can be treated as `SignersRejected` (miner discards it, and the txid-exclusion logic downstream of the rejection branch acts on stale per-signer rejection data), producing a liveness wedge on block production — the miner stalls or bans transactions based on votes that have already been superseded by real acceptances. It does not require a majority of signers or key material; it only requires that a subset of signers change their vote from reject to accept for the same proposal, which is an explicitly supported reconsideration flow.

### Likelihood Explanation
This is triggerable by a single miner slot: propose (or re-propose via gossip/timeout retry) the same block such that some signers initially reject (e.g., due to a transient view mismatch) and later accept once conditions change — a flow the docs describe as legitimate ("we do not change our votes on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider," `docs/signer-flows.md`). No majority collusion or private key access is needed; it can also occur from ordinary out-of-order message delivery over StackerDB gossip.

### Recommendation
Use a single per-signer "current vote" map (slot_id → Accepted/Rejected) rather than two independently-guarded accumulators. When a signer's vote changes, subtract its weight from the previous bucket's running total before adding it to the new bucket's total, so `total_weight_approved` and `total_weight_rejected` always reflect only the signers' most recent responses.

### Proof of Concept
1. Miner proposes block B; signers S1..Sn receive it.
2. S1 sends `BlockResponse::Rejected` for B (some recoverable reason) → `total_weight_rejected += w(S1)`, `responded_signers.insert(S1)`.
3. Later, S1 reconsiders (new proposal/timeout path) and sends `BlockResponse::Accepted` for B → since `gathered_signatures` doesn't contain S1, `total_weight_approved += w(S1)` — `total_weight_rejected` is left untouched.
4. Repeat with enough signers so `total_weight_rejected.saturating_add(weight_threshold) > total_weight` becomes true purely from stale rejection weight, even though the *current* votes (post-flip) would clear `total_weight_approved >= weight_threshold`.
5. `get_block_status` in `signer_coordinator.rs` evaluates the rejection branch first and returns `Err(SignersRejected { .. })`, discarding a block that current signer intent actually approves.
