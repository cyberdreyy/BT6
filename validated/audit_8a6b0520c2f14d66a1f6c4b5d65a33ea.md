### Title
Masking-store key/data written into job-writable TmpProjectDir enables exfiltration via artifacts:paths - (File: `commands/helpers/internal/store/store.go`, `commands/helpers/proxy_exec.go`)

### Summary
`store.Open` (`commands/helpers/internal/store/store.go:29-78`) derives the AddMask encryption key by XOR-ing a key embedded in `masking.db` with a second key file (`runner<sha256(pathname)>`), and writes both files under `dir`, which `NewProxy`/`ProxyExecCommand.Execute` sets to the job's `TmpProjectDir` (`commands/helpers/proxy_exec.go:80-90`, `shells/proxy_exec.go:32-38`). Because both halves of the key material and the ciphertext live in the same job-writable directory that is also the root for `artifacts:paths`, a pipeline author can configure `artifacts:paths: [.]` (or any path covering the project dir) to have the runner archive `masking.db` and the key file together, fully reconstructing the AEAD key and decrypting the masked phrases.

### Finding Description
`Open(dir)` computes `pathname := filepath.Join(dir, "masking.db")` and `keyPath := filepath.Join(dir, "runner"+hex(sha256(pathname)))`, both inside `dir` [1](#0-0) . It writes a random 32-byte key to `keyPath` and another random 32-byte key inline into `masking.db` [2](#0-1) , then derives the actual chacha20poly1305 key by XOR-ing the two [3](#0-2) . `NewProxy` calls `store.Open(dir)` with `dir` being the value of `dst`, which comes from `RUNNER_TEMP_PROJECT_DIR` or `--temp-dir`, both ultimately set to `info.Build.TmpProjectDir()` by `shells/proxy_exec.go` [4](#0-3) [5](#0-4) [6](#0-5) . `TmpProjectDir()` is the job's working directory, which is also the base for `artifacts:paths`/cache configured by the pipeline author. Since the key filename is deterministic (`"runner"+hex(sha256(pathname))`) and `pathname` is deterministic given a known `dir`, an attacker who controls the job's `.gitlab-ci.yml` can trivially predict/glob for both files and add them to `artifacts:paths`. Once both `masking.db` (holds key half 1 + ciphertext of masked phrases) and the `runner<hash>` file (key half 2) are captured in the archive, an attacker with access to the resulting artifact (self, on the same project, in a later job/stage, or by downloading the artifact) can XOR the two key halves to recover the chacha20poly1305 key and decrypt every masked phrase stored via `AddMask()` for that job. There is no check anywhere in `Open`, `NewProxy`, or the artifact-archiving path that excludes these files from being archived, and no separation of the key material from the job workspace.

### Impact Explanation
Any masked value (`AddMask()` phrase) produced during proxy-exec'd job steps can be recovered by the job itself simply by publishing its own workspace as an artifact — defeating the confidentiality goal of the masking store, and allowing the value to be exfiltrated in cleartext within the same job/stage (not just "cross-project"; even a single job's own artifact bundling defeats the mechanism, matching the scoped impact of exposing this job's secrets via artifact bundling).

### Likelihood Explanation
High feasibility: the only precondition is a pipeline author (a normal, unprivileged CI user for their own project) configuring `artifacts:paths` to include the project's working directory (a common and unremarkable configuration, e.g. `artifacts: paths: [.]` or a broad glob), which is entirely within their control. No cross-project or elevated access is needed; the attack is fully reproducible and deterministic, since `Open` uses no per-invocation randomness that would prevent the two persisted files from being combined offline.

### Recommendation
Do not persist masking key material (or any part of it) inside the job's/project's working directory that is included in artifact/cache scope. Store `masking.db` and the derived key file in a runner-controlled, non-job-writable location (outside `TmpProjectDir`, e.g. a directory scoped to the runner's private build metadata that is never eligible for `artifacts:paths`/cache glob matching), or explicitly exclude these filenames from archiving/upload code paths regardless of user-specified `artifacts:paths` patterns.

func TestMaskingKeyMaterialInsideProjectDir(t *testing.T) {

    db, err := store.Open(dir)

    require.NoError(t, db.Add("supersecret"))
    db.Close()

    // Simulate artifacts:paths archiving the whole project dir.
    entries, _ := os.ReadDir(dir)
    var hasDB, hasKey bool
    for _, e := range entries {
        if e.Name() == "masking.db" {
            hasDB = true
        }
        if strings.HasPrefix(e.Name(), "runner") {
            hasKey = true
        }
    }
    // Current (vulnerable) behavior: both files present -> archive would contain
    // full key material alongside encrypted secrets.
    require.True(t, hasDB && hasKey, "key material co-located with job workspace")

    // Attacker-side: reconstruct key from archived files and decrypt masking.db,
    // proving the phrase "supersecret" is recoverable purely from artifact contents.
}
