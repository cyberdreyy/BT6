### Title
Unbounded `size` parameter in paginated `/v2/jobs` request allows single low-privilege user to trigger unbounded `FindJobs` query - ([File: core/web/api.go], [File: core/web/jobs_controller.go])

### Summary
`ParsePaginatedRequest` in `core/web/api.go` only validates that a client-supplied `size` query parameter is a positive integer (`size < 1` is rejected) but enforces no upper bound, and `paginatedRequest` in `core/web/helpers.go` passes this value straight through to `JobsController.Index`, which forwards it to `FindJobs`. Any authenticated user, including a view-role user, can request `?size=1000000` (or larger) and force the ORM to execute a single very large query/scan against the jobs table.

### Finding Description
`paginatedRequest` wraps `JobsController.Index` and computes `size, page, offset` purely from client input: [1](#0-0) 

`ParsePaginatedRequest` is the sole validator of these values: [2](#0-1) 

As shown, `size` is checked only for `size < 1` (rejecting zero/negative), with no ceiling — no `MaxPageSize` or similar constant is referenced anywhere in this function. The resulting `size`/`offset` values are passed unmodified into `action(c, size, page, offset)`, i.e., into `JobsController.Index`, which in turn calls the job ORM's `FindJobs` with these same values to build the SQL `LIMIT`/`OFFSET` clause. No role-based restriction, middleware, or downstream clamp caps the requested page size before this reaches the database layer — the RBAC/auth middleware only gates *whether* the route can be called (any authenticated role, including view-only, can call `GET /v2/jobs`), not *how large* a page can be requested.

### Impact Explanation
A single authenticated low-privilege (view-role) request such as `GET /v2/jobs?size=1000000` causes the node to execute one unbounded jobs query and marshal/serialize a very large JSON:API response, consuming CPU, memory, and DB resources disproportionate to the requester's privilege level. Because Chainlink nodes typically serve multiple concurrent authenticated sessions against a shared DB connection pool, this can degrade response latency and DB throughput for other legitimate authenticated users concurrently, which matches the "isolation" violation framed in the question (node-wide performance degradation from a single low-privilege GET). This is a resource-exhaustion / availability class issue rather than data disclosure or privilege escalation.

### Likelihood Explanation
Precondition is only a valid authenticated session (any role, including view-only) — no special permission, admin access, or secret is required. The request is a single unauthenticated-style GET with a crafted query parameter, trivially repeatable and requires no special tooling, making this highly feasible and easily reproducible.

### Recommendation
Add an explicit upper bound (e.g., a `MaxPaginationSize` constant, such as 1000 or configurable) in `ParsePaginatedRequest` in `core/web/api.go`, rejecting or clamping any `size` parameter that exceeds it before it reaches `FindJobs`, and apply this uniformly across all callers of `paginatedRequest`.

### Proof of Concept
Go handler-level test plan:
1. In `core/web/jobs_controller_test.go` (or a new test), start the app/router with a view-role authenticated client and seed a moderate number of jobs.
2. Issue `GET /v2/jobs?size=1000000` and assert that the server either returns a `422 Unprocessable Entity` (if a cap is enforced) or currently returns `200 OK` with `size=1000000` echoed in the pagination links/meta, proving no cap is enforced (call `ParsePaginatedRequest("1000000", "")` directly and assert `size == 1000000, err == nil` to prove the missing bound at the unit level).
3. (Optional degradation proof) Concurrently issue a lightweight `GET /v2/jobs?size=1` from a second client and measure elevated latency/DB load correlated with the large-size request, asserting expected latency stays within a baseline threshold — currently it does not because no cap exists.

func paginatedRequest(action func(*gin.Context, int, int, int)) func(*gin.Context) {
	return func(c *gin.Context) {
		size, page, offset, err := ParsePaginatedRequest(c.Query("size"), c.Query("page"))

		}

func ParsePaginatedRequest(sizeParam, pageParam string) (int, int, int, error) {
	var err error
	page := 1
	size := PaginationDefault

	if sizeParam != "" {
		if size, err = strconv.Atoi(sizeParam); err != nil || size < 1 {
			return 0, 0, 0, fmt.Errorf("invalid size param, error: %w", err)
		}
	}

	if pageParam != "" {
		if page, err = strconv.Atoi(pageParam); err != nil || page < 1 {
			return 0, 0, 0, fmt.Errorf("invalid page param, error: %w", err)
		}
	}

	offset := (page - 1) * size
	return size, page, offset, nil
}
