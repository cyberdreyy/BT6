### Title
Post-default withdraw receipts pay out at par from the fixed `defaultRecoveryReserve`, starving and then permanently freezing defaulted-epoch claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After a borrower default is finalized, `IdleCreditVault.requestWithdraw` mints a receipt to the requester and records it in `postDefaultRequests`, and `_claimPostDefaultWithdrawRequest` pays it 1:1 via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` by the full amount. But `defaultRecoveryReserve` was sized at finalization to cover only the pre-default claim basis times `defaultRecoveryPrice` (< 1e18). Every post-default claim therefore consumes reserve units that were meant to be shared, at a haircut, among defaulted claimants — so early post-default claimers are overpaid and later claims hit a `defaultRecoveryReserve -= _amount` underflow and revert permanently.

### Finding Description
In `finalizeDefaultRecovery` the strategy sets `defaultRecoveryReserve = reserveAmount` where `reserveAmount / totalBasis = defaultRecoveryPrice` (typically < 1e18). The reserve is therefore exactly `price * Σ(claimBasis)` — the total payable to defaulted normal receipts (`_claimDefaultedWithdrawRequest`), defaulted instant receipts (`_claimDefaultedInstantWithdrawRequest`), and nothing more. [1](#0-0) 

Post-default, `requestWithdraw` mints a receipt and records `postDefaultRequests[_user] = _amount` without pulling or reserving any new underlying — the CDO only burns/mints strategy tokens. [2](#0-1) 

`_claimPostDefaultWithdrawRequest` then burns the receipt and calls `_transferDefaultRecovery(_user, amount)` at par, and `_transferDefaultRecovery` unconditionally does `defaultRecoveryReserve -= _amount`. [3](#0-2) [4](#0-3) 

Since the reserve only contains `price * totalBasis`, the sum `Σ(defaulted claimBasis * price) + Σ(postDefaultRequests)` exceeds `defaultRecoveryReserve`. Claims are processed FCFS, so once cumulative claims reach the reserve size, the next `_transferDefaultRecovery` underflows on `defaultRecoveryReserve -= _amount` (Solidity checked arithmetic) and every subsequent defaulted/post-default claim reverts forever. The "already-haircut amount" rationale in the comment only justifies the *price* paid to the requester — it does not create any new reserve backing, because no underlying enters the strategy when a post-default request is created. [5](#0-4) 

The broken invariant is one-receipt-one-payout / donation-reserve isolation: the isolated recovery reserve is spent on claims it was never provisioned for.

### Impact Explanation
Any tranche-token holder can, after default finalization, call `IdleCDOEpochVariant.requestWithdraw` (allow flags and `isWalletAllowed` still apply to a KYC-passed user) and then `claimWithdrawRequest` to extract reserve funds at par — effectively stealing the haircut belonging to defaulted-epoch claimants. Once enough post-default par claims have been paid, every remaining defaulted or post-default claim reverts, permanently freezing recovery funds in the strategy (which `transferToken` can only rescue via owner). Quantified loss: up to the full unclaimed remainder of `defaultRecoveryReserve`, equal to `reserveAmount - Σ(claims already paid)`.

### Likelihood Explanation
Requires a borrower default plus `finalizeDefaultRecovery` — an epoch phase the codebase explicitly supports. The attacker needs only to hold tranche tokens (or buy them cheaply post-default) and be wallet-allowed; no privileged role. The revert is deterministic arithmetic underflow, not a gas or ordering edge case. Guard `requestWithdraw` post-default checks (`_hasWithdrawRequest`, `instantWithdrawsRequests`, `postDefaultRequests` non-zero) only limit one pending request per user, not aggregate reserve consumption across users. [6](#0-5) 

### Recommendation
Either fund post-default receipts separately (e.g., require the CDO to transfer `_amount` underlying into the strategy and add it to `defaultRecoveryReserve`, or pay post-default claims via `_transferFundedClaim` against non-reserve balance), or include post-default claims in `totalBasis`/`defaultRecoveryPrice` accounting so all claimants share the same haircut. At minimum, `claimWithdrawRequest` for post-default receipts should not decrement `defaultRecoveryReserve` unless matching underlying was added to it.

### Proof of Concept
Foundry fork PoC (sketch, runnable in `test/foundry/IdleCreditVault.t.sol` harness style):

```solidity
function testPostDefaultClaimDrainsRecoveryReserve() external {
    // 1. Victim deposits, epoch 0 runs, victim requests normal withdraw.
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(victim, amount, true);
    _startEpochAndCheckPrices(0);
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 2. Borrower defaults; manager/guardian trigger default + finalize recovery
    //    at price < 1e18 (e.g. 50% recovery).
    _stopEpochAndCheckPrices(0, initialProvidedApr, 0); // no borrower repayment
    vm.prank(manager);
    cdoEpoch._handleBorrowerDefault();
    uint256 recovered = /* partial recovery */;
    deal(defaultUnderlying, recoverySource, recovered);
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);

    IdleCreditVault strat = IdleCreditVault(address(strategy));
    uint256 reserve = strat.defaultRecoveryReserve();

    // 3. Attacker (tranche holder, KYC'd) deposits post-default or already holds
    //    tranches; requests withdraw -> postDefaultRequests receipt.
    vm.prank(attacker);
    uint256 req = cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche));
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(); // pays req at par, reserve -= req

    // 4. Victim's defaulted claim now hits
    //    defaultRecoveryReserve -= claimBasis * price  -> underflow -> revert.
    vm.prank(victim);
    vm.expectRevert(); // arithmetic underflow in _transferDefaultRecovery
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertion: `postDefaultRequests` total is paid from `defaultRecoveryReserve` although the reserve was computed as `recoveredAmount * ... / totalBasis` covering only pre-default basis, so `Σ claims > defaultRecoveryReserve` and late claims revert permanently.

    amount = postDefaultRequests[_user];

    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
