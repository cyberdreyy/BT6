### Title
Unfunded instant-withdraw receipts are paid at par because `claimInstantWithdrawRequest` burns the aggregate `instantWithdrawsRequests` balance instead of the funded per-epoch receipt - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestInstantWithdraw` mints receipt tokens and adds the amount to both `instantWithdrawsRequests[_user]` and the global `pendingInstantWithdraws` queue. Funds only arrive later, when the IdleCDO calls `collectInstantWithdrawFunds(_amount)`, which decrements `pendingInstantWithdraws`. `claimInstantWithdrawRequest`, however, burns the *entire* aggregate `instantWithdrawsRequests[_user]` and pays it out at par through `_transferFundedClaim`, with no check that the claimed amount was actually funded. A user can therefore stack a new unfunded receipt on top of an already-funded one and drain underlying belonging to other funded claimants.

### Finding Description
The external bug class is "an identifier derived from a mutable counter (`totalSupply()`/length) collides after a burn/pop". The analog lives in the instant-withdraw receipt accounting: per-epoch ownership is tracked (`instantWithdrawsRequestsByEpoch[_user][epoch]`), but the payout path ignores it and uses the aggregate counter `instantWithdrawsRequests[_user]`, which mixes funded and unfunded receipts into one indistinguishable balance — the same "wrong slot" failure as minting with a reused token id.

Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` (lines 356–375): burns the CDO's strategy tokens, mints receipts to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws`. There is **no** guard requiring the user to claim a previous funded receipt first (contrast with `requestWithdraw`, lines 263–271, which explicitly reverts if a loss-adjusted receipt is unclaimed).
- `collectInstantWithdrawFunds` (lines 398–403): decreases `pendingInstantWithdraws` and pulls underlying from the CDO into the vault. Funding is partial-capable — nothing enforces that a user's receipt is fully funded before claiming.
- `claimInstantWithdrawRequest` (lines 380–393): reads `amount = instantWithdrawsRequests[_user]` (the aggregate, including unfunded pending receipts), burns it all, and calls `_transferFundedClaim(_user, amount)`.
- `_transferFundedClaim` (lines 897–907): only guards the `defaultRecoveryReserve`; it does not compare `_amount` against the user's funded portion or against `pendingInstantWithdraws`. It transfers whatever the vault holds.

Attack sequence (running epoch, instant mode enabled):

1. Attacker (KYC'd lender) requests instant withdraw of 100. Borrower/CDO funds it via `collectInstantWithdrawFunds(100)`; vault now holds 100 earmarked for the attacker, `pendingInstantWithdraws` back to its prior level, `instantWithdrawsRequests[attacker] = 100`.
2. Before claiming, attacker calls `requestInstantWithdraw(50)`. `instantWithdrawsRequests[attacker] = 150`, `pendingInstantWithdraws += 50`, but no funds are collected.
3. Another user's funded claim (or liquidity pulled into the vault for other claims) leaves the vault balance ≥ 150.
4. Attacker calls `claimInstantWithdrawRequest` (via the CDO): the vault burns all 150 receipts and transfers 150 underlying, although only 100 was ever funded. The extra 50 is stolen from other claimants' funded receipts, making their later claims revert (insolvency).

The per-epoch mappings exist precisely to disambiguate receipt funding status, but the claim path never consults them — the aggregate "slot" is reused for a second request whose funding state differs.

### Impact Explanation
Direct theft of underlying held by the vault for other users' funded instant-withdraw claims, quantified as the unfunded portion of the attacker's receipt (up to the vault's underlying balance). Secondary effect: honest claimants' `claimInstantWithdrawRequest` calls revert on insufficient balance, i.e., temporary/permanent freezing of their funded payouts until the shortfall is restored.

### Likelihood Explanation
Requires instant withdrawals to be enabled on the vault and the attacker to hold tranche tokens (any KYC-passing lender qualifies). The sequence uses only unprivileged calls plus the normal, honest manager/CDO funding flow (`collectInstantWithdrawFunds`), which is triggered by ordinary epoch operations. The only timing requirement is that the second `requestInstantWithdraw` lands after the first receipt is funded and before it is claimed — the user fully controls when to claim, so this is trivially achievable whenever the vault holds funded claim liquidity from any user. Caveat: the CDO-side entry points (`requestWithdraw`/`claimInstantWithdrawRequest` wrappers in `IdleCDOEpochVariant`) were not fully verified for an additional per-user gate; if such a gate exists it would mitigate the issue, but none is visible in the vault code itself.

### Recommendation
Track the funded portion per user (or per epoch) and pay only funded receipts in `claimInstantWithdrawRequest`. Concretely: in `collectInstantWithdrawFunds`, attribute collected amounts to specific epochs/receipts (e.g., a `fundedInstantByEpoch` mapping), and in `claimInstantWithdrawRequest` burn and pay only the funded basis, leaving unfunded receipts in `instantWithdrawsRequests[_user]`. Alternatively, revert `requestInstantWithdraw` when `instantWithdrawsRequests[_user] != 0` so aggregate and per-epoch state can never diverge — mirroring the guard already applied to normal loss-adjusted receipts in `requestWithdraw` (lines 263–271).

### Proof of Concept
Foundry fork PoC (uses the existing `IdleCreditVault.t.sol` harness helpers such as `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopCurrentEpoch`):

```solidity
function testInstantWithdrawUnfundedReceiptPaysAtPar() external {
    // epoch running, instant withdraws enabled (instantDelay elapsed)
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");

    uint256 tranchesA = _depositWithUser(attacker, 100e6);
    uint256 tranchesV = _depositWithUser(victim,   50e6);

    // attacker requests instant withdraw of 100, victim of 50
    _requestInstantWithdrawWithUser(attacker, tranchesA); // requestInstantWithdraw path
    _requestInstantWithdrawWithUser(victim,   tranchesV);

    IdleCreditVault vault = IdleCreditVault(address(strategy));

    // CDO funds both claims -> vault holds 150 underlying
    vm.prank(address(cdoEpoch));
    vault.collectInstantWithdrawFunds(150e6);

    // attacker stacks a NEW unfunded receipt before claiming
    uint256 tranchesA2 = _depositWithUser(attacker, 50e6);
    _requestInstantWithdrawWithUser(attacker, tranchesA2);
    // pendingInstantWithdraws == 50 (unfunded), instantWithdrawsRequests[attacker] == 150

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    // attacker received 150 although only 100 was funded:
    // victim's funded 50 was spent; victim's claim now reverts on insufficient balance
    assertEq(underlying.balanceOf(attacker) - balPre, 150e6);
    vm.prank(victim);
    vm.expectRevert(); // ERC20: transfer amount exceeds balance (or NotAllowed)
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Key assertions: `instantWithdrawsRequests[attacker]` aggregates funded + unfunded receipts, `_transferFundedClaim` pays the aggregate, and the victim's funded claim becomes unpayable.
