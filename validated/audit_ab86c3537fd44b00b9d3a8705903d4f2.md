The `confirm()` function at multisig2/src/lib.rs:294-315 counts entries in the `confirmations: HashSet<String>` for a request without verifying that each recorded confirmer is still a current member. `delete_member()` at lines 355-379 only purges confirmations for requests *originated* by the removed member (`r.member == member`), never scrubbing that member's confirmation entries from *other* pending requests. ### Title
Stale confirmations from removed multisig members count toward the approval threshold, allowing execution below the effective K-of-N quorum - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` decides whether to execute a pending request purely by comparing the size of the `confirmations: HashSet<String>` for that request against `self.num_confirmations` [1](#0-0) . Membership in `confirmations` is never re-validated against the live `members: UnorderedSet<MultisigMember>` set at confirm/execute time, and `delete_member` does not remove a departing member's confirmations from requests they didn't originate [2](#0-1) .

### Finding Description
The binding the contract is supposed to enforce is:
`count(live members who confirmed request R) >= num_confirmations`

What is actually enforced is:
`len(confirmations[R]) >= num_confirmations`, where `confirmations[R]` is a set of stringified `MultisigMember` values recorded at the time each member called `confirm`, regardless of whether that member is still in `self.members` by the time the threshold is reached.

`delete_member` (invoked only via `execute_request`'s `DeleteMember` branch [3](#0-2) ) removes the member from `self.members` and cleans up:
- outstanding *requests the deleted member originated* (`r.member == member`) and their confirmation sets,
- the deleted member's `num_requests_pk` entry,

but it does **not** scan other pending requests' `confirmations` maps to strip out a confirmation the deleted member gave on a request *someone else* originated [4](#0-3) . That confirmation entry silently remains in `LookupMap<RequestId, HashSet<String>>` and continues to count toward `confirm`'s threshold check.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." A request can be executed with fewer *live* confirming members than `num_confirmations` mandates, letting a minority of current members (aided by a stale confirmation from a since-removed member) push through transfers, key additions, contract upgrades, or further member/threshold changes — i.e., an unauthorised move of NEAR or unauthorised control action that the K-of-N scheme was designed to prevent.

### Likelihood Explanation
This requires no attacker privilege beyond being (or having been) one of several legitimate multisig members — exactly the kind of "confirmations counted versus live members" scenario called out as in-scope. It naturally arises in ordinary multisig operations whenever a member is removed (e.g., due to key rotation or compromise) while any other request is still pending with that member's earlier confirmation attached; no malicious deployment or foundation/owner privilege is needed beyond normal request/confirm/delete-member flows.

### Recommendation
In `confirm`, before comparing against `self.num_confirmations`, filter `confirmations` to only those entries where `self.members.contains(&member)` is still true, or alternatively have `delete_member` iterate all pending requests' confirmation sets (not just those it originated) and remove the departing member's entry from each. Additionally, consider re-validating `num_confirmations` against `self.members.len()` whenever a member is deleted, and validating confirmer-liveness at both `confirm`-time and `execute_request`-time to close the same class of bug reported for `RoleManager.getRoleMemberCount()`.

### Proof of Concept
1. Initialize `MultiSigContract::new` with members `A, B, C, D` and `num_confirmations = 3` [5](#0-4) .
2. `A` calls `add_request_and_confirm(R)` for some `Transfer` action → `confirmations[R] = {A}` [6](#0-5) .
3. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (2 < 3, not yet executed) [7](#0-6) .
4. Separately, a `DeleteMember { member: B }` request is created and confirmed to threshold by `A, C, D`, and executes via `delete_member`. This removes `B` from `self.members` and cleans up only requests `B` originated — `R` (originated by `A`) is untouched, so `confirmations[R]` still contains `B` [8](#0-7) .
5. `C` calls `confirm(R)` → `confirmations[R].len() + 1 == 3 >= num_confirmations(3)` → `R` executes [9](#0-8) , even though only `A` and `C` are currently live confirming members — one short of the intended 3-of-N quorum.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
