### Title
Rejection weight is never released when a signer later accepts, letting stale reject-weight permanently poison the miner's approval tally - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` that tallies signer `BlockResponse` messages for the miner's `NakamotoBlockBuilder`/`SignCoordinator` loop uses two different, unsynchronized de-duplication keys for the "accepted" and "rejected" code paths: the `Accepted` branch gates its weight increment on `block.gathered_signatures.contains_key(&slot_id)`, while the `Rejected` branch gates its increment on `block.responded_signers.insert(slot_id)`. Both branches also unconditionally insert into the shared `responded_signers` set. Because a signer legitimately may reject a block first (e.g. before its own validation completes) and later re-evaluate and sign it — a transition explicitly modeled as valid in the signer state machine (`LocallyRejected --> LocallyAccepted : re-evaluated`, `stacks-signer/src/signerdb.rs` `BlockInfo::check_state`) — that signer's weight gets added to `total_weight_rejected` on the first message and *also* added to `total_weight_approved` on the second, with no mechanism to ever remove or reconcile the earlier contribution. This breaks the coordinator's implicit invariant that `total_weight_approved + total_weight_rejected` reflects each signer's *current*, single stance, i.e. the aggregated-weight vs. verified-response equality is violated. ### Finding Description
`handle_signer_message`'s `BlockResponse::Accepted` arm increments `block.total_weight_approved` only if the responding slot is not yet present in `gathered_signatures` (a `HashMap<slot_id, signature>`), then unconditionally does `block.gathered_signatures.insert(slot_id, signature)` and `block.responded_signers.insert(slot_id)`. [1](#0-0) 

The `BlockResponse::Rejected` arm increments `block.total_weight_rejected` only `if block.responded_signers.insert(slot_id)` — i.e. only the *first* message from that slot ever adds weight to the reject tally, and it marks the slot as "responded" for good. [4](#0-3) 

Consider the sequence: signer S (weight w) sends `Rejected` for block B first (a normal outcome if S's own validation was slower than others', or S rejected transiently and later re-evaluated per the documented `LocallyRejected --> LocallyAccepted` transition). This adds `w` to `total_weight_rejected` and marks S's slot as `responded`. S later legitimately signs B and broadcasts `Accepted`. The `Accepted` arm checks `gathered_signatures.contains_key(slot_id)`, which is still empty for S (S never sent an `Accepted` before), so the check passes and `w` is *also* added to `total_weight_approved`. S's rejection weight is never subtracted from `total_weight_rejected`.

The consumer of these tallies, the miner's wait loop in `SignCoordinator`, evaluates a strict if/else-if chain each iteration:
```
if total_weight_rejected + weight_threshold > total_weight { return Err(SignersRejected) }
else if total_weight_approved >= weight_threshold { return Ok(signatures) }
else if timed_out { return Err(SignatureTimeout) }
else { continue }
``` [5](#0-4) 

Because rejected weight is permanently "sticky" (never reconciled with a later accept from the same signer), a small number of signers that transiently reject before ultimately signing can accumulate enough phantom weight in `total_weight_rejected` to trip the `> total_weight - weight_threshold` blocking-minority condition on some polling iteration — even though, at that same moment, the *true* current opposition (signers who have not since accepted) is well under the 30% blocking threshold, and the block may in fact already carry ≥70% real, current, verified acceptances. Since the reject-check is evaluated first in the if/else chain and returns immediately (`SignersRejected`), the miner discards a validly, sufficiently-signed block, and there is no path for the tally to self-correct (no decrement exists anywhere for `total_weight_rejected`).

This is a violation of the "aggregated-weight vs verified-accepts" equality specifically named in scope: the coordinator's accounting no longer reflects each signer's live position, and the discrepancy is one-directional and irreversible for the lifetime of that `block_sighash` entry in the `blocks` map.

### Impact Explanation
This wedges the miner's block-broadcast coordinator into treating a block that has, at the moment of decision, met the real 70% signature threshold as globally rejected, purely because of stale rejection weight from signers who have since legitimately re-evaluated and signed. This matches the "High" impact category of a party (here, the block-push coordinator, which gatekeeps whether a validly-signed block is ever pushed to the network) being wedged from acting on the correct, current, verified aggregate state — a liveness break in the miner/coordinator's block-acceptance logic, entirely reachable via the normal one-signer reject-then-accept sequence that the signer's own state machine explicitly permits and that requires no majority or privileged access to trigger (a single signer's ordinary re-evaluation is sufficient to poison the tally).

### Likelihood Explanation
The triggering sequence — a signer rejecting a proposal before its own stacks-node validation completes (or before pre-commit threshold reasoning resolves) and later re-evaluating and signing the *same* block — is not an attacker-crafted corner case; it is a documented, expected transition (`LocallyRejected --> LocallyAccepted : re-evaluated`) that can occur under ordinary network/timing jitter with zero adversarial input, gossip only. No majority, no other signer's key, and no auth token are required; the bug is purely in how the coordinator's own bookkeeping (`gathered_signatures` vs `responded_signers`) fails to reconcile a single signer's evolving stance.

### Recommendation
Track each signer slot's *current* stance in a single map (e.g. `slot_id -> Vote::{Accepted, Rejected}`) rather than two independently-gated collections. On receiving a new response from a slot, if a prior opposite-direction vote exists, subtract that slot's weight from the old tally before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect the *current* state of each signer's message rather than accumulating stale, irreversible contributions.

### Proof of Concept
1. Start a tenure with N signers where each has equal weight `w`, and `weight_threshold` requires ≥70% of `N*w`.
2. Let signer S1 (and possibly a few others near the 30%-blocking margin) send `BlockResponse::Rejected` for block B — e.g. due to a slower validation race, a common and expected occurrence (see `stacks-signer/src/v0/signer.rs` `handle_block_validate_reject` firing before a re-evaluation completes). `stackerdb_listener.rs` records their weight into `total_weight_rejected` and marks them `responded`.
3. S1 (and the others) subsequently complete validation/pre-commit and broadcast `BlockResponse::Accepted` for the *same* block B once ≥70% weight has genuinely signed.
4. Because the `Accepted` arm's dedup check is against `gathered_signatures` (empty for S1) rather than `responded_signers`, S1's weight is added to `total_weight_approved` too, but is never removed from `total_weight_rejected`.
5. If the miner's `SignCoordinator::wait_for_signer_signatures` loop polls at a point where `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (true, since S1's — and any other flip-flopping signers' — weight is still counted there from step 2, on top of any genuinely-still-opposed signers), the coordinator returns `Err(SignersRejected)` and discards block B, even though `total_weight_approved` at that same instant already reflects a real, current 70%+ acceptance.
