### Title
Re-proposal of an identical block resets a `GloballyRejected` verdict back to `Unprocessed`, letting a signer reconsider (and potentially sign) a block the network already rejected - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_proposal` decides whether to re-evaluate an already-tracked block via `should_reevaluate_block`. That gate only refuses to reopen a block when `BlockInfo::globally_approved_and_responded()` is true — but that helper checks only `BlockState::GloballyAccepted`, never `BlockState::GloballyRejected`. Combined with `should_reevaluate_reject_reason`, a block whose *local* reject reason falls into a "re-evaluable" bucket (e.g. `ConnectivityIssues`, `NoSortitionView`, `NoSignerConsensus`, `ConsensusHashMismatch`, `Unknown`) is reopened even if its persisted `state` is `GloballyRejected`. Reopening does not call `move_to`/`check_state` (which forbids `GloballyRejected -> GloballyAccepted`); instead it discards the whole `BlockInfo` via `BlockInfo::from(block_proposal.clone())`, which resets `state` to `Unprocessed`, `valid` to `None`, and `reject_reason` to `None`, and this fresh record then overwrites the DB row for that `signer_signature_hash`. This is directly analogous to the tough-cookie flaw: an object is "reinitialized" from external input rather than merged/validated, silently dropping a previously-established security invariant (the block's terminal, network-settled rejection status).

### Finding Description
The block lifecycle invariant is explicitly documented and enforced by `BlockInfo::check_state`: [1](#0-0) 

`GloballyRejected` and `GloballyAccepted` are each declared mutually unreachable, and this is the *only* place that invariant is checked — it is enforced on `move_to`, not on construction.

The re-evaluation gate that is supposed to prevent reopening a settled block only checks the accepted side of the terminal pair: [2](#0-1) 

`should_reevaluate_reject_reason` treats several reject reasons as transient/re-evaluable, all of which describe *this signer's own local/environmental* validation failure rather than the block's actual content: [3](#0-2) 

`should_reevaluate_block` combines these: if the block is not `GloballyAccepted`-and-responded (true for any `GloballyRejected` block, since that check never inspects `GloballyRejected`), and the stored `reject_reason` is in the re-evaluable set, execution falls through to `true` at the bottom of the function — i.e. "re-evaluate this block from scratch": [4](#0-3) 

Back in `handle_block_proposal`, "re-evaluate" means constructing an entirely new `BlockInfo` from the incoming (identical-hash) proposal, explicitly noted in the comment as overwriting all prior proposal info, and then persisting it via `insert_block`: [5](#0-4) [6](#0-5) 

`BlockInfo::from` unconditionally sets `state: BlockState::Unprocessed`, `valid: None`, `reject_reason: None`, discarding whatever `state` the row previously held: [7](#0-6) 

Because the blocks table's primary key is `(reward_cycle, signer_signature_hash)`, this insert overwrites the previously `GloballyRejected` row rather than being blocked by `check_state`: [8](#0-7) 

From this reset `Unprocessed` state, the normal flow proceeds: `check_block_against_state` → `submit_block_for_validation` → (on OK) `mark_pre_committed` → pre-commit threshold → `mark_locally_accepted`, i.e. the signer can end up signing/pre-committing a block whose signer-signature-hash was already recorded by this same signer as `GloballyRejected`.

### Impact Explanation
This breaks the documented equality "each global state is unreachable from the other" / "signed vs. globally-rejected" invariant that the whole `BlockState` state machine exists to protect (see `docs/signer-flows.md` section 2, and `check_state` itself). A block that the network already drove to `GloballyRejected` can be reopened by nothing more than the miner re-broadcasting the exact same proposal, and this individual signer can end up producing a fresh acceptance signature/pre-commit for it — a signer signing a block that has already reached a conflicting terminal consensus decision. This matches the "Critical" impact bucket in scope: a rejection recounted/reopened into a path that can yield a signature, undermining the safety guarantee that `GloballyRejected` is final for that signer.

### Likelihood Explanation
No majority collusion or key compromise is required. The only actor needed is the single block-proposing miner (in scope, "gossip" re-delivery), replaying the byte-identical proposal (same `signer_signature_hash`, since any change to the header/timestamp changes the hash and is treated as a distinct block). The trigger condition — this signer's *own* recorded `reject_reason` being one of the re-evaluable, "transient/environmental" categories (`ConnectivityIssues`, `NoSortitionView`, `NoSignerConsensus`, `ConsensusHashMismatch`, `Unknown`, `TestingDirective`) while the network overall reached `GloballyRejected` for a substantive reason — is a realistic and even expected occurrence: it is exactly the class of reason the code introduced `should_reevaluate_reject_reason` to allow retrying, but the retry path was not also gated on "already globally rejected."

### Recommendation
Extend `globally_approved_and_responded` (or add a parallel check used by `should_reevaluate_block`) to also short-circuit on `BlockState::GloballyRejected`, so a block that has reached either terminal global state is never reopened via `BlockInfo::from`. Alternatively, when re-evaluating a known block, preserve/merge the persisted `state` (and route any transition through `move_to`/`check_state`) instead of discarding the whole `BlockInfo` and reconstructing it from the raw proposal.

### Proof of Concept
1. Miner proposes block `B`. This signer attempts validation but hits a transient condition and locally rejects with `reject_reason = RejectReason::ConnectivityIssues(..)` (or `NoSortitionView`/`NoSignerConsensus`/`ConsensusHashMismatch`/`Unknown`), broadcasting a rejection.
2. Other signers reject `B` for a substantive/content reason; group rejection weight is reached and this signer's `BlockInfo` for `B` transitions to `BlockState::GloballyRejected` (persisted via `signer_db.insert_block`).
3. Miner re-broadcasts the identical `B` (same header/timestamp ⇒ same `signer_signature_hash`).
4. `handle_block_proposal` looks up the prior `BlockInfo` (state=`GloballyRejected`, reject_reason=`ConnectivityIssues`), calls `should_reevaluate_block`: `globally_approved_and_responded()` is `false` (wrong state checked), `should_reevaluate_reject_reason` is `true` → function returns `true`.
5. `handle_block_proposal` builds `block_info = BlockInfo::from(block_proposal.clone())` (state reset to `Unprocessed`, `reject_reason=None`), stores it via `signer_db.insert_block`, overwriting the `GloballyRejected` row, and resumes normal validation/pre-commit/signing flow for `B`.

Note: I did not have tool budget remaining to trace every call site of `mark_globally_rejected` (it is referenced in `stacks-signer/src/chainstate/mod.rs` and covered by tests in `stacks-signer/src/tests/signer_state.rs`, but I could not fully inspect that call site in this session) to enumerate every way a signer's local `BlockInfo` reaches `GloballyRejected` with one of the listed reject reasons. The core defect — `should_reevaluate_block`'s asymmetric terminal-state check and the full-reset semantics of `BlockInfo::from` — is directly confirmed in `signerdb.rs` and `v0/signer.rs` as cited above.

    fn should_reevaluate_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &BlockInfo,
        block_proposal: &BlockProposal,
    ) -> bool {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        if block_info.globally_approved_and_responded() {
            info!("{self}: received a block proposal for a globally accepted block to which we have already responded. Ignoring.";
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "block_height" => block_info.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_info.block.header.consensus_hash,
                "timestamp" => block_info.block.header.timestamp,
                "signed_group" => block_info.signed_group,
                "signed_self" => block_info.signed_self,
                "valid" => ?block_info.valid
            );
            return false;
        }
        if !should_reevaluate_reject_reason(block_info) {
            if block_info.state == BlockState::PreCommitted {
                // We validated this block but haven't signed it. Signing requires the
                // pre-commit threshold and the conflict checks in `handle_block_pre_commit`.
                // Re-broadcast our pre-commit and re-run that evaluation instead of
                // responding with a signature directly, so a re-proposed block can't
                // bypass those checks.
                info!(
                    "{self}: received a block proposal for a block we have pre-committed to but not signed. Re-evaluating the pre-commit.";
                    "signer_signature_hash" => %signer_signature_hash,
                    "block_id" => %block_info.block.block_id(),
                    "block_height" => block_info.block.header.chain_length,
                    "burn_height" => block_proposal.burn_height,
                    "consensus_hash" => %block_info.block.header.consensus_hash
                );
                self.send_block_pre_commit(signer_signature_hash.clone());
                let address = self.stacks_address.clone();
                self.handle_block_pre_commit(
                    stacks_client,
                    sortition_state,
                    &address,
                    &signer_signature_hash,
                );
                return false;
            }
            if let Some(block_response) = self.determine_response(block_info) {
                self.send_block_response(&block_info.block, block_response);
                return false;
            } else {
                let is_pending = self
                    .signer_db
                    .has_pending_block_validation(&signer_signature_hash)
                    .unwrap_or_else(|e| {
                        warn!("{self}: Failed to load pending block validations: {e:?}");
                        false
                    });
                if is_pending {
                    debug!(
                        "{self}: received a block proposal for a block for which we is already pending validation. Do nothing.";
                        "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                        "block_id" => %block_info.block.block_id()
                    );
                    return false;
                } else {
                    info!(
                        "{self}: received a block proposal for this block before, but we do not have a pending validation for it.";
                        "reject_reason" => ?block_info.reject_reason,
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %block_info.block.block_id(),
                        "block_height" => block_info.block.header.chain_length,
                        "burn_height" => block_proposal.burn_height,
                        "consensus_hash" => %block_info.block.header.consensus_hash
                    );
                }
            }
        } else {
            info!(
                "{self}: received a block proposal for this block before, but our rejection reason allows us to reconsider";
                "reject_reason" => ?block_info.reject_reason,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_proposal.block.block_id(),
                "block_height" => block_proposal.block.header.chain_length,
                "burn_height" => block_proposal.burn_height,
                "consensus_hash" => %block_proposal.block.header.consensus_hash
            );
        }
        true
    }

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
