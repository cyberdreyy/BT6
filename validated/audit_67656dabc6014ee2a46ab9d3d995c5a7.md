### Title
Incorrect price representation: `TranchesChainlinkOracle` returns a 1e18-scaled price while declaring `decimals()` equal to the loan token's decimals - ([File: contracts/strategies/morpho/TranchesChainlinkOracle.sol](contracts/strategies/morpho/TranchesChainlinkOracle.sol))

### Summary
`TranchesChainlinkOracle.latestRoundData()` returns `cdo.virtualPrice(collateralToken)`, which is scaled by `ONE_TRANCHE_TOKEN = 1e18` (NAV × 1e18 / supply). However, `decimals()` reports `loanTokenDecimals` (e.g., 6 for USDC). Any Chainlink-compatible consumer that normalizes `answer` by `10**decimals()` — such as `MorphoChainlinkOracleV2`, the intended consumer per `IMorphoChainlinkOracleV2` — reads the collateral price inflated (or deflated) by `10**(18 - loanTokenDecimals)`. For a USDC-denominated vault the reported price is 1e12× too large.

### Finding Description
`IdleCDO` / `IdleCDOCreditVault` compute tranche prices as `nav * ONE_TRANCHE_TOKEN / trancheSupply`, i.e., always in 1e18 fixed-point regardless of the underlying's decimals (`_virtualPriceAux` in `IdleCDOCreditVault.sol:336`, `ONE_TRANCHE_TOKEN = 1e18`). The adapter contract correctly returns this value as the oracle `answer` but incorrectly declares its scale:

```solidity
function decimals() external view returns (uint8) {
    // decimals of the virtualPrice are equal to decimals of the loanToken
    return uint8(loanTokenDecimals);   // WRONG: virtualPrice is 1e18-scaled
}
```

The comment at `TranchesChainlinkOracle.sol:25` encodes the flawed assumption. `virtualPrice` decimals are fixed at 18 by construction; they are independent of `loanToken.decimals()`. Only when the loan token happens to have 18 decimals does the declared precision coincide with the actual scale — the same class of bug as the external report, where a price in one fixed-point representation is exposed as if it were another.

### Impact Explanation
`MorphoChainlinkOracleV2` computes its `SCALE_FACTOR` at deployment from the feed's `decimals()` (`IAggregatorV3Minimal.decimals()` is explicitly part of the price formula per `IMetaMorphoOracleFactory`). With `decimals()` returning 6 instead of 18 for a USDC-loan vault, the composed oracle overvalues tranche collateral by ~1e12. An unprivileged attacker can post a small amount of tranche tokens as collateral in the Morpho market and borrow far more loan token than the collateral is worth — direct theft from the lending market, quantified as roughly `(10^(18-loanTokenDecimals) - 1) × collateral value` of over-borrowing. For tokens with more than 18 decimals the inverse (undervaluation) causes wrongful liquidations.

### Likelihood Explanation
The mispricing exists unconditionally whenever a vault's loan token has decimals ≠ 18 and the adapter is wired into an oracle consumer — no privileged misbehavior, timing, or oracle manipulation is required. The flaw is deterministic: `latestRoundData()` and `decimals()` disagree on every call. Its exploitation is bounded only by whether an external market integrates this feed, which is the adapter's sole purpose.

### Recommendation
Report the true scale of the returned value. Either make `decimals()` return 18 (matching `ONE_TRANCHE_TOKEN`), or rescale `latestRoundData()` to `virtualPrice * oneToken / 1e18` so the answer is genuinely denominated in `loanTokenDecimals`. When composing through `MorphoChainlinkOracleV2`, ensure the `SCALE_FACTOR` math (base/quote vault samples and token decimals) is recomputed against the corrected feed precision.

### Proof of Concept
```solidity
// Fork test against a USDC (6-decimals) credit vault using TranchesChainlinkOracle
function testOracleDecimalsMismatch() public {
    // tranche token of a USDC-denominated IdleCDOCreditVault
    TranchesChainlinkOracle oracle = new TranchesChainlinkOracle(address(AAtranche));

    assertEq(oracle.decimals(), 6); // declared precision = USDC decimals

    (, int256 answer,,,) = oracle.latestRoundData();
    // answer == cdo.virtualPrice(AAtranche) == ~1e18 for a par tranche
    assertApproxEqAbs(uint256(answer), 1e18, 1e16);

    // A Chainlink consumer normalizes: price = answer / 10**decimals()
    uint256 consumerPrice = uint256(answer) / 10**oracle.decimals();
    // consumerPrice == ~1e12 USDC per tranche token instead of ~1 USDC
    assertEq(consumerPrice, 1e12);
}
```

Uncertainty: the loss materializes in external consumers (e.g., Morpho markets) rather than inside the credit vault itself; if the audit scope treats external oracle consumers as out of scope, the finding's impact is limited to integrator-facing mispricing rather than a direct drain of vault funds.
