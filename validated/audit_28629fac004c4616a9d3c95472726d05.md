### Title
Claimed instant-withdraw receipts leave stale per-epoch ledger entries that corrupt default-recovery accounting and freeze legitimate claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external report is a stale-read race: `service.head` was read without locks, so consumers acted on a cached value that no longer matched reality. The analog in `IdleCreditVault` is a stale-ledger read: `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . If that same epoch later defaults, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch basis as if the receipt were still outstanding [2](#0-1) .

### Finding Description
`requestInstantWithdraw` records receipts in three places: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch total `instantWithdrawClaimsByEpoch[currentEpoch]` [3](#0-2) . On claim, only the aggregate is zeroed — the per-epoch entries remain [1](#0-0) .

Withdraw requests are keyed by `epochNumber` at stop time, and on borrower default `epochNumber` is not bumped (see `_prefundedEpochToProcess` comment [4](#0-3) ), so a receipt recorded under epoch N and claimed during running epoch N sits under the same key that becomes `defaultRecoveryEpoch` when epoch N ends in default.

After `finalizeDefault`, `claimInstantWithdrawRequest` routes into `_claimDefaultedInstantWithdrawRequest`, which computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — including the already-paid amount — then executes `instantWithdrawsRequests[_user] -= claimBasis` [5](#0-4) . Because the stale amount was already removed from the aggregate, the subtraction underflows and the whole call reverts, permanently blocking the user's claim of any legitimate same-epoch defaulted receipts. It also attempts to decrement `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` by the inflated basis [6](#0-5) , corrupting the funded/unfunded split those ledgers drive during recovery finalization.

### Impact Explanation
- **Permanent freezing**: a user holding a genuine defaulted-epoch instant receipt plus one already-claimed receipt in the same epoch can never call `claimInstantWithdrawRequest` — the arithmetic underflow reverts on every attempt, freezing their recovery entitlement denominated in `defaultRecoveryReserve`.
- **Recovery dilution**: `instantWithdrawClaimsByEpoch[defaultEpoch]` retains the claimed amount, so the epoch's outstanding instant-claim total used by finalization is overstated; reserve accounting treats already-paid receipts as outstanding, shrinking the effective recovery available to honest claimants.

### Likelihood Explanation
Requires the confluence of: instant withdrawals enabled (`allowInstantWithdraw`), a user claiming an instant receipt during a running epoch, and that same epoch ending in borrower default with finalized recovery. Defaults are an infrequent but explicitly supported mode (`_claimDefaultedInstantWithdrawRequest` exists for exactly this path), and no existing guard prevents the sequence — `requestInstantWithdraw` has no staleness check analogous to the `lossRecoveryPriceByEpoch` guard in `requestWithdraw` [7](#0-6) .

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch entries symmetrically with `requestInstantWithdraw`: for each request epoch with a nonzero `instantWithdrawsRequestsByEpoch[_user]` (at minimum the current `epochNumber`), zero it and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, mirroring how `_clearWithdrawClaimForEpoch` keeps normal receipts consistent [8](#0-7) .

// test/foundry/IdleCreditVault.t.sol — add to existing suite
function testStaleInstantReceiptBlocksDefaultClaim() external {
    // enable instant withdrawals, deposit, run epoch 0
    // ... standard setup with instantDelay, minAprDelta ...

    // stopEpoch(0) with low APR -> CDO calls strategy.requestInstantWithdraw(amt1, user)
    // instantWithdrawsRequestsByEpoch[user][1] += amt1; instantWithdrawClaimsByEpoch[1] += amt1
    _stopCurrentEpochWithApr(1e18); // triggers instant path, epochNumber = 1

    // epoch 1 running; wait instantDelay; user claims (funded via collectInstantWithdrawFunds)
    skip(instantDelay + 1);
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest();
    // instantWithdrawsRequests[user] == 0
    // BUT instantWithdrawsRequestsByEpoch[user][1] == amt1 (stale)  <-- bug
    assertEq(IdleCreditVault(address(strategy)).instantWithdrawsRequestsByEpoch(user, 1), amt1);

    // epoch 1 ends with borrower default; manager finalizes recovery
    _startDefaultAndFinalize();

    // user also had a second pending instant receipt amt2 recorded under epoch 1
    // claimBasis = amt1 (stale) + amt2 > instantWithdrawsRequests[user] = amt2 -> underflow
    vm.prank(user);
    vm.expectRevert(); // permanent freeze of amt2 recovery
    cdoEpoch.claimInstantWithdrawRequest();
}
```

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {

        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
