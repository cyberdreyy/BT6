### Title
Frontrunning `requestWithdraw` shifts `trancheAPRSplitRatio` and silently shrinks the victim's locked withdrawal receipt - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` in `IdleCDOEpochVariant` permanently fixes the amount of underlyings a user will receive at request time, but the computation depends on `trancheAPRSplitRatio`, a mutable value that any unprivileged lender can move with a deposit or withdrawal request in the opposite tranche. Just like the Canto `Tray.buy()` case — where the minted tray depends on a `lastHash` that a frontrunner changes — the victim precomputes a receipt amount off-chain, a frontrunner's transaction changes the inputs, and the victim ends up locked into a materially smaller payout than the one they priced, with no expected-amount check to revert.

### Finding Description
`requestWithdraw(_amount, _tranche)` computes the receipt in three steps:

1. `_underlyings = _trancheToUnderlyings(_amount, _tranche)` — principal at the current tranche price [1](#0-0) .
2. `(interest, diff) = _calcInterestWithdrawRequest(_underlyings, _tranche)`, which scales the projected epoch interest by `trancheAPRSplitRatio` via `_calcTrancheInterestShare` [2](#0-1) .
3. `creditVault.requestWithdraw(_underlyings, msg.sender, principal)` mints the user a receipt for exactly this amount; from then on the payout is fixed (`withdrawsRequestsByEpoch`) and leaves live NAV [3](#0-2) .

`trancheAPRSplitRatio` is recomputed on every deposit and withdrawal by `_updateSplitRatio(_getAARatio(true))` [4](#0-3) . With AYS active, the ratio is clamped between `minAprSplitAYS`-derived bounds and moves with the AA/BB TVL ratio. A BB-tranche withdrawal request (or an AA deposit) executed in the same block before the victim's `requestWithdraw` lowers the AA APR split, reducing `_interest` for an AA requester — and conversely a frontrun AA withdrawal request raises the BB share and reduces a BB requester's interest. Because the receipt is locked at request time (`requestWithdraw` burns the principal and mints the fixed receipt), the victim cannot re-price or abort: the transaction they already sent commits them to the new, worse terms.

Concretely, in a running-epoch buffer phase (fixed-APR mode, AYS active): a victim AA holder simulates `requestWithdraw(0, AATranche)` — which defaults to their full balance [5](#0-4)  — and expects `principal + interest - fees`. A frontrunner (any KYC-passed BB holder) submits `requestWithdraw` on `BBTranche`; `_withdrawOps` runs `_updateSplitRatio(_getAARatio(true))`, pushing `trancheAPRSplitRatio` down. The victim's transaction then computes `_interest` against the lower ratio and locks in a smaller receipt. The loss equals `totTrancheInterest * Δratio * _amount / _trancheBal`, which on a large pool with a wide AYS band is a meaningful slice of one full epoch of yield — a permanent, quantified loss of expected yield, not merely a price tick.

The analogous mitigation in the report (check `lastHash` against the value the user precomputed) maps directly to a `minUnderlyings`/expected-terms parameter, which `requestWithdraw` lacks entirely.

### Impact Explanation
The victim's receipt is minted for fewer underlyings than they precomputed and is irreversible — after `claimWithdrawRequest` they receive permanently less than the fair value of their tranche tokens at the ratio they saw. Unlike a deposit at a worse price (which still tracks NAV), the haircut here is locked: `interestForOverUnderPerformance` transfers the would-be yield to the remaining tranche, so the foregone interest is effectively captured by the frontrunner's side of the book if they remain in the pool [6](#0-5) . Loss is quantified as the drop in `_interest` caused by the split-ratio move, capped by the AYS min/max band but potentially a full epoch's worth of split differential on the withdrawn principal.

### Likelihood Explanation
Any unprivileged KYC-passed lender holding either tranche can execute the frontrun during the buffer window, when `requestWithdraw` is open (`allowAAWithdrawRequest`/`allowBBWithdrawRequest`) [7](#0-6) . Withdrawal requests are most frequent exactly in this window, so sandwiching opportunities are routine, not exceptional. No existing guard stops it: `_skimDonatedAssets`, `_updateAccounting`, `isWalletAllowed`, and the default checks all pass; the receipt is simply priced on post-frontrun state.

### Recommendation
Add an expected-terms check to `requestWithdraw`, mirroring the report's `lastHash` fix:

```solidity
function requestWithdraw(uint256 _amount, address _tranche, uint256 _minUnderlyings) external returns (uint256) {
    ...
    if (_underlyings < _minUnderlyings) revert Slippage();
}
```

Alternatively pin the receipt to a caller-supplied `expectedAprSplitRatio` (revert if `trancheAPRSplitRatio != expected`), so a frontrun deposit/withdraw reverts the victim's transaction instead of locking a worse receipt.

### Proof of Concept
Foundry fork PoC (setup matches `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testFrontrunRequestWithdrawShrinksReceipt() external {
    // AYS active, fixed APR epoch running
    uint256 amountWei = 10000 * ONE_SCALE;
    uint256 mintedAA_victim = _depositWithUser(victim, amountWei, true);   // AA
    uint256 mintedBB_frtr   = _depositWithUser(frontrunner, amountWei, false); // BB

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch()); // buffer opens

    // Victim previews receipt at current trancheAPRSplitRatio
    uint256 expected = _previewRequestWithdraw(victim, mintedAA_victim); // principal + interest - fees

    // Frontrunner: BB withdraw request -> _updateSplitRatio lowers AA split
    vm.prank(frontrunner);
    cdoEpoch.requestWithdraw(mintedBB_frtr, address(BBtranche));

    // Victim's already-sent tx executes on worse state
    vm.prank(victim);
    uint256 got = cdoEpoch.requestWithdraw(0, address(AAtranche));

    assertLt(got, expected); // receipt locked at lower amount; no revert, funds committed
}
```

The assertion shows the victim's minted receipt is strictly smaller than the amount they precomputed, with the difference accruing to remaining BB holders via `interestForOverUnderPerformance`.
