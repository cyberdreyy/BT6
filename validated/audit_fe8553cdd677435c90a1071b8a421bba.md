Based on the investigation, the strongest analog to "return status ignored" in this repo is in `stacks-signer/src/v0/signer.rs`, where the `Result` returned by the `BlockInfo` state-transition guards (`mark_locally_accepted`, `mark_pre_committed`, `mark_locally_rejected`) is used only to decide whether to *log a warning*, not to gate the subsequent action. In several call sites the code proceeds to broadcast a signature/response regardless of whether the guarded transition actually succeeded.

I was not able to fully read the body of `BlockInfo::check_state` (only located its existence via `signerdb.rs`), so the exact set of transitions it forbids is not fully confirmed from the index; the finding is based on the call-site control-flow pattern, which is unambiguous.

### Title
Signer broadcasts a block-acceptance signature even when the state-machine guard rejects the transition - (File: stacks-signer/src/v0/signer.rs)

### Summary
`Signer::handle_block_pre_commit`'s signing branch calls `block_info.mark_locally_accepted(false)`, whose `Err` return is the canonical state-machine's verdict on whether locally accepting (signing) this block is a legal transition from the block's current state (per `BlockInfo::check_state`, documented in `docs/signer-flows.md` as governing reachability between `Unprocessed` → `PreCommitted`/`LocallyAccepted` → `LocallyRejected`/`GloballyAccepted`/`GloballyRejected`). The `Err` value is consumed only for logging (and even then, suppressed when `has_reached_consensus()` is true) — it is never used to prevent the following unconditional actions: inserting the block, creating a `BlockAccepted` message, calling `handle_block_signature` (which tallies the signature toward the group threshold and can trigger `broadcast_signed_block`), and sending the acceptance response.

### Finding Description [1](#0-0) 

```rust
// It is only considered globally accepted IFF we receive a new block event confirming it OR see the chain tip of the node advance to it.
if let Err(e) = block_info.mark_locally_accepted(false) {
    if !block_info.has_reached_consensus() {
        warn!("{self}: Failed to mark block as locally accepted: {e:?}",);
    }
}
self.signer_db
    .insert_block(&block_info)
    .unwrap_or_else(|e| self.handle_insert_block_error(e));
let accepted = self.create_block_acceptance(&block_info.block);
// have to save the signature _after_ the block info
self.handle_block_signature(stacks_client, sortition_state, &accepted);
self.send_block_response(&block_info.block, accepted.into());
```

Regardless of whether `mark_locally_accepted` succeeded in actually moving `block_info` into the `LocallyAccepted` state, the function falls through and (a) persists `block_info` as-is, (b) constructs a real `BlockAccepted` signature (`create_block_acceptance`), (c) feeds it into `handle_block_signature`, which tallies it toward the group signing threshold via `store_and_process_block_signature` and can immediately call `broadcast_signed_block`, and (d) broadcasts the acceptance to the rest of the signer set over StackerDB. The identical discard-and-continue pattern recurs for `mark_pre_committed` (`stacks-signer/src/v0/signer.rs:1961-1970`) and `mark_locally_rejected` (`stacks-signer/src/v0/signer.rs:1355-1359`, `1950-1954`, `2020-2024`), all of which log conditionally on `has_reached_consensus()` but never `return` on failure before performing DB writes/broadcasts. [2](#0-1) 

This is the direct structural analog of the reported bug: `ICohort(_cohort).requestClaim(...)`'s success/failure status is discarded and the caller proceeds as if it succeeded. Here, the `Result` of a safety-critical state-machine gate is discarded for control-flow purposes and the caller proceeds to sign/broadcast as if the gate had passed.

### Impact Explanation
If `check_state` is ever asked to authorize a transition that is not legal from the block's current recorded state (for example, the in-memory `block_info` was concurrently advanced past `LocallyAccepted` toward a terminal `GloballyRejected`/`GloballyRejected` state by an interleaved event before this branch runs, since `block_info` is taken out of the tracking map and reinserted across multiple mutation points in this file), the guard's `Err` is meant to stop the "sign it" branch from completing. Because the `Err` only suppresses a log line rather than aborting, the signer still emits and tallies a real signature over a block its own state machine just refused to endorse. Depending on what `check_state` actually forbids, this can produce the signer signing a block it should not — the kind of safety break explicitly called out as Critical impact.

### Likelihood Explanation
This requires no majority collusion and no external key material — it is triggered purely by the interleaving of events a single miner/gossip participant can induce (e.g., timing a competing pre-commit/proposal/response so that `block_info`'s state advances between when it's looked up and when `mark_locally_accepted` is invoked in this code path). Given the file's own doc comments emphasize careful "re-check the world before the signature leaves the box" ordering elsewhere (e.g. `check_block_against_signer_db_state`, conflict guards), the state-machine guard here is evidently intended to be load-bearing, yet its failure is not enforced.

### Recommendation
On `Err` from `mark_locally_accepted`/`mark_pre_committed`/`mark_locally_rejected`, do not fall through to broadcasting/tallying actions unless the specific `Err` variant is verified to correspond to a benign already-ahead-of-target-state case (which the `has_reached_consensus()`/`state != LocallyAccepted` checks attempt but do not fully gate for the signing branch). At minimum, `return` before `create_block_acceptance`/`handle_block_signature`/`send_block_response` when the mark fails and consensus has not already been reached.

### Proof of Concept
Not independently reproducible from the index alone: exercising this requires driving a race between the pre-commit threshold path in `handle_block_pre_commit` and a concurrent state transition on the same `block_info` (e.g., a rejection or a differing group-signed outcome arriving via `handle_block_response`/`handle_block_validate_reject`) so that `check_state` rejects the `LocallyAccepted` transition at the exact moment the pre-commit-threshold branch calls `mark_locally_accepted`. I could not confirm the precise set of forbidden transitions in `BlockInfo::check_state` from the available index content, so the exact reachable trigger condition is unverified.
