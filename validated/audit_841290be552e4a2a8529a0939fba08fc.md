### Title
Multisig requests can execute below the configured confirmation threshold because stale confirmations from removed members are never purged - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution of a pending request purely by counting the size of the `confirmations` set stored for that `request_id` against `num_confirmations`. When a member is removed via `DeleteMember` (`multisig2`) or `DeleteKey` (`multisig`), the code only purges *requests originated by* that member, not the confirmations that member previously cast on *other* pending requests. Those stale confirmations remain in the set and continue to count toward the K-of-N threshold, so a request can be executed with fewer currently-valid signers than `num_confirmations` requires - breaking the multisig's core custody guarantee.

### Finding Description
`confirm()` counts the confirmations already recorded for a request and, once that count plus the new confirmation reaches `num_confirmations`, immediately executes the request: [1](#0-0) 

The only validation performed before counting is `assert_valid_request`, which checks that the *new* confirmer is a current member - it does not re-validate that the *previously stored* confirmations still belong to current members: [2](#0-1) 

When a member is removed, `delete_member` only cleans up requests that member itself created (`r.member == member`); it never scans other pending requests' `confirmations` sets to strip out that member's stale confirmation: [3](#0-2) 

The `confirmations` field is a simple `LookupMap<RequestId, HashSet<String>>` keyed by member identity string, with no liveness binding to the current `members` set: [4](#0-3) 

The same pattern exists in the legacy `multisig` contract: `DeleteKey` only purges requests whose *signer_pk* (originator) matches the deleted key, leaving that key's confirmations on other pending requests intact: [5](#0-4) [6](#0-5) 

**Exploit path:**
1. Multisig has members `{A, B, C, D}` with `num_confirmations = 3`.
2. Member `D` confirms a pending malicious request `R` (e.g. a `Transfer` or `AddKey` action created by another colluding member `C`), bringing `R`'s confirmations to `{C, D}` (2 of 3).
3. `D` is subsequently removed from the multisig via a legitimately-executed `DeleteMember(D)` request (confirmed by `A, B, C`). `delete_member`'s guard `members.len() - 1 >= num_confirmations` (`4-1 >= 3`) passes, so `D` is removed. Since `R` was created by `C`, not `D`, `delete_member` does not touch `R`'s confirmations - `{C, D}` remains stored.
4. Live members are now `{A, B, C}`. `D`'s stale confirmation is still counted. A single additional live confirmation (from `A` or `B`) satisfies `confirmations.len() + 1 >= 3`, and `R` executes.
5. `R` executes having only 2 genuinely live confirming members (`A`/`B` and `C`) instead of the required 3, because one of the "confirmations" belongs to a member who no longer has any authority over the account.

This breaks the equality the contract is supposed to enforce: `confirmations recorded == confirmations from currently-authorized members`. The threshold guarantee (`K` live signers required before funds move / keys are added / contract is upgraded) can be silently weakened to `K - 1` (or fewer, if multiple confirmers are later removed) any time a confirming member is removed after confirming but before the request is executed or explicitly deleted.

### Impact Explanation
This is a Critical-impact finding per the custody-binding rules: a multisig request (fund transfer, `AddKey`/`AddMember`, contract upgrade, etc.) can be executed with a live-confirmation count below the configured `num_confirmations` threshold, because previously-cast confirmations from now-removed members are never invalidated. Funds or privileged operations can be authorized with fewer authentic signers than the K-of-N scheme promises.

### Likelihood Explanation
This does not require breaking cryptography or any privileged foundation role - it only requires the ordinary, expected multisig lifecycle: a member confirms a request, and later a member-removal request (a routine operational action, e.g. rotating out a compromised or departing signer) is executed while the earlier request is still pending. No special timing tricks beyond ordinary operational sequencing are needed, and a malicious or compromised member who anticipates being removed can deliberately pre-confirm requests to bank a "free" stale confirmation that outlives their membership.

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate over all pending requests' `confirmations` sets (not just those the removed member originated) and strip that member's identity from every entry, re-checking whether removal drops a request below what's needed. Alternatively, revalidate at `confirm()`-time that every already-stored confirming identity in the set is still present in `self.members` before counting toward the threshold, discarding stale entries lazily.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. As `C`, call `add_request_and_confirm` with a `Transfer` action to an attacker-controlled `receiver_id` -> `R` has confirmations `{C}`.
3. As `D`, call `confirm(R)` -> `R` has confirmations `{C, D}` (2/3).
4. Execute a legitimate `DeleteMember(D)` request via 3 confirmations from `A, B, C` -> `D` is removed; `members = {A, B, C}`.
5. Inspect storage: `get_confirmations(R)` still returns `{C, D}`.
6. As `A`, call `confirm(R)` -> `confirmations.len() + 1 == 3 >= num_confirmations`, so `R` executes the `Transfer`, despite only `A` and `C` being genuinely live confirming members (2 real confirmations, not 3).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
