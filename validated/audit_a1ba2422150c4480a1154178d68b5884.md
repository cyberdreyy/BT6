### Title
Claimed instant-withdraw receipts leave stale per-epoch basis, enabling double payout from default recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays out and zeroes only the aggregate `instantWithdrawsRequests[_user]` ledger, but never clears the per-epoch accounting entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. These stale entries are a classic use-after-free analog: state that was logically consumed by a funded claim remains live and is later re-read by `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` when the borrower defaults in the same epoch. The attacker can re-request in the same epoch after claiming, then claim the stale basis a second time from the recovery reserve.

### Finding Description
The instant-withdraw flow keeps two ledgers:

- Aggregate: `instantWithdrawsRequests[_user]`, decremented in `claimInstantWithdrawRequest` (IdleCreditVault.sol:387-392).
- Per-epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, incremented in `requestInstantWithdraw` (IdleCreditVault.sol:366-374).

`claimInstantWithdrawRequest` only clears the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The per-epoch entries are only cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 842-856), which runs solely after `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. So a funded, already-paid instant claim leaves `instantWithdrawsRequestsByEpoch[user][N]` and `instantWithdrawClaimsByEpoch[N]` permanently non-zero.

Attack sequence (single epoch N, instant withdrawals enabled):

1. Attacker deposits via the CDO, then calls `requestInstantWithdraw`. Basis `X` is recorded in both ledgers.
2. The CDO funds the request via `collectInstantWithdrawFunds` (decrementing `pendingInstantWithdraws`), and the attacker calls `claimInstantWithdrawRequest`, receiving `X` underlying. `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` still equal `X` — freed state left dangling.
3. Attacker calls `requestInstantWithdraw` again for `Y`. Now `instantWithdrawsRequestsByEpoch[attacker][N] = X + Y` while only `Y` is legitimately pending.
4. Borrower defaults in epoch N; `stopEpoch`/`_handleBorrowerDefault` and `finalizeDefaultRecovery` run. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[N]` — inflated by the already-paid `X` — which raises `totalBasis` and adds a phantom `X` to `prefundedReserve` via `_defaultPrefundedInstantReserve` (instantBasis > pendingInstant because `pendingInstantWithdraws` was already decremented by the funded claim).
5. After finalization, `_claimDefaultedInstantWithdrawRequest` reads `claimBasis = instantWithdrawsRequestsByEpoch[user][N] = X + Y`, burns only `X + Y` receipt tokens, and pays `(X + Y) * defaultRecoveryPrice` from `defaultRecoveryReserve` — the attacker is paid again for the already-claimed `X`.

Note the prefunded-reserve path makes this worse: `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held by the strategy, crediting `X` to `reserveAmount` even though those funds were already transferred out to the attacker — so `defaultRecoveryPrice` is computed on a reserve that is partially phantom, while the claim itself is fully real.

### Impact Explanation
Direct theft of the default recovery reserve. The attacker extracts an extra `X * defaultRecoveryPrice` underlying beyond their legitimate claim, draining `defaultRecoveryReserve` that belongs to other defaulted-epoch claimants and active tranche holders. If recovery is high (e.g., borrower repaid partially before default), the stolen amount approaches `X`. Other claimants' `_transferDefaultRecovery` payouts then fail or are reduced once the reserve is exhausted — insolvency/unpaid claims for honest users.

### Likelihood Explanation
Requires instant withdrawals enabled, the ability to claim and re-request within the same epoch, and a subsequent borrower default in that epoch — all unprivileged actions plus an ordinary credit event the vault is explicitly designed to handle. No privileged misbehavior needed. The stale-state gap exists unconditionally; only the default trigger is probabilistic. Caveat: I verified the strategy-side ledgers; whether `IdleCDOEpochVariant` permits a second `requestInstantWithdraw` in the same epoch after a claim (and whether the CDO blocks re-requests) should be confirmed in the PoC — the strategy itself imposes no such guard on instant requests.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers alongside the aggregate: subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epoch]`/`instantWithdrawClaimsByEpoch[epoch]` (or track a per-user per-epoch claimed offset). Alternatively, keep per-epoch entries but record `instantWithdrawsClaimedByEpoch[user][epoch]` and have `_claimDefaultedInstantWithdrawRequest` and `defaultPendingClaimBasis` use `byEpoch - claimed` as the basis. Also make `_defaultPrefundedInstantReserve` compute prefunded amounts from actually-held underlying rather than from the stale claim basis.

### Proof of Concept
Foundry fork PoC sketch (instant-withdraw variant):

```solidity
function testInstantClaimStaleBasisDoublePay() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18); // enter epoch 1
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    uint256 amount = 100e6;
    uint256 tranches = _depositWithUser(attacker, amount);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(block.timestamp + 101); // past instantDelay

    // 1) instant request X, funded and claimed
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches / 2, address(tranche)); // pseudo-name
    // manager/borrower funds instant queue -> collectInstantWithdrawFunds
    // attacker claims: receives X underlying
    // ASSERT BUG: strategy.instantWithdrawsRequestsByEpoch(attacker, epoch) still == X
    //             strategy.instantWithdrawClaimsByEpoch(epoch) still == X

    // 2) second instant request Y in same epoch
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(tranches / 2, address(tranche));

    // 3) borrower defaults; finalizeDefaultRecovery pulls partial recovery
    // assert defaultPendingClaimBasis() includes stale X
    // 4) attacker claimInstantWithdrawRequest -> paid (X + Y) * recoveryPrice
    // assert underlying.balanceOf(attacker) increased by more than Y * recoveryPrice
}
```

Key assertion: after step 1's claim, `instantWithdrawsRequestsByEpoch(attacker, epoch) != 0` proves the freed basis was never released; after finalization, the attacker receives payment on `X` twice.
