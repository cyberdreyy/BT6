### Title
Withdraw parser mislabels/omits confidential-transfer proof-context accounts when `account_indexes.len()` equals the `check_num_token_accounts` floor of 4 - ([File: transaction-status/src/parse_token/extension/confidential_transfer.rs])

### Finding Description
`parse_confidential_transfer_instruction`'s `ConfidentialTransferInstruction::Withdraw` arm only enforces a floor of 4 accounts via `check_num_token_accounts(account_indexes, 4)` [1](#0-0) , but the number of accounts actually required depends on `equality_proof_instruction_offset` and `range_proof_instruction_offset`: up to two extra accounts (`instructionsSysvar` and/or `equalityProofContextStateAccount`/`rangeProofContextStateAccount`) may be needed beyond the fixed `account`, `mint`, and `owner` slots.

The manual offset-walking logic reserves the *last* account_indexes slot for `parse_signers` via the `offset < account_indexes.len().saturating_sub(1)` guard, then sequentially tries to assign `instructionsSysvar`, `equalityProofContextStateAccount`, and `rangeProofContextStateAccount` [2](#0-1) . When `account_indexes.len() == 4` (the allowed minimum), `saturating_sub(1) == 3`, so only a single optional slot (`account_indexes[2]`) can ever be filled before the loop guard blocks further assignment, regardless of how many proof-context/sysvar accounts should actually exist.

Concretely, if an attacker sets `equality_proof_instruction_offset == 0` (context-account-based) and `range_proof_instruction_offset != 0` (instruction-offset/sysvar-based) with only 4 `account_indexes`:
- `has_sysvar` is `true` (since `range_offset != 0`), so `account_indexes[2]` is unconditionally labeled `"instructionsSysvar"` — even though `equality_proof_instruction_offset == 0` means that slot should logically be the equality proof's context-state account.
- The subsequent `equality_proof_instruction_offset == 0` check then fails the `offset < 3` guard (offset is now 3) and is skipped, so `"equalityProofContextStateAccount"` is never emitted at all.
- `parse_signers` is then called with `offset == 3`, binding `account_indexes[3]` to `"owner"`.

Similarly, when both offsets are `0` (both context-account-based, needing 2 context accounts) but only 4 accounts are supplied, only `"equalityProofContextStateAccount"` gets filled (from `account_indexes[2]`); `"rangeProofContextStateAccount"` is silently omitted, and `account_indexes[3]` — which should be the range-proof context account — is instead mislabeled as `"owner"` by `parse_signers`.

This is reachable by any unprivileged client: `parse_token`/`parse_confidential_transfer_instruction` is purely a decoding path invoked from RPC's `jsonParsed` encoding (e.g., `getTransaction`) and does not depend on whether the instruction actually succeeds on-chain. An attacker can submit a transaction invoking `spl_token_2022` with a `ConfidentialTransferInstruction::Withdraw` instruction, arbitrary `WithdrawInstructionData` offsets, and exactly 4 accounts (satisfying `check_num_token_accounts` even though the real `spl-token-2022` instruction builder — see `inner_withdraw` used in the file's own `test_withdraw` test — would supply 5 accounts for any offset combination involving one context account and one instruction-offset proof, or 5–6 for the "all context" case). The transaction may fail on-chain execution due to insufficient/invalid accounts from the program's perspective, but it still lands in a block (as a failed transaction) and remains queryable via `getTransaction`/`getConfirmedTransaction`, triggering this parser and producing mislabeled JSON.

Existing guards do not catch this: `check_num_token_accounts` only checks a fixed floor (4) independent of the dynamic proof-offset combination, and the sequential `if`/`offset` bookkeeping has no cross-check that the number of accounts consumed by optional fields matches what the offsets imply.

### Impact Explanation
Downstream integrators/indexers relying on `jsonParsed` output for `withdrawConfidentialTransfer` instructions can receive wrong account attribution: an `equalityProofContextStateAccount` or `rangeProofContextStateAccount` can be misreported as `instructionsSysvar`, entirely omitted, or misreported as `owner`. This falls under "wrong ... account data returned" from a single unprivileged RPC-visible transaction/query, a decoder misreporting bug in the transaction-status crate.

### Likelihood Explanation
Fully attacker-controlled and reproducible with a single crafted transaction: the attacker chooses `instruction_data` (the offsets) and `account_indexes` length/order directly. No special privileges, staking, or leader control needed — only submitting one transaction (which can even fail execution) and later calling `getTransaction` on it. It is deterministic and requires no race conditions.

### Recommendation
Compute the exact expected account count for `Withdraw` (and the analogous `Transfer`/`TransferWithFee` arms which share the same pattern) from the actual offsets before assigning any optional fields, e.g., derive `needs_sysvar`, `needs_equality_ctx`, `needs_range_ctx` booleans and use `check_num_token_accounts(account_indexes, 2 + needs_sysvar as usize + needs_equality_ctx as usize + needs_range_ctx as usize + 1 /* owner */)` (plus multisig-signer count) instead of a static floor of 4, then remove the `offset < account_indexes.len().saturating_sub(1)` short-circuits that silently skip fields when the account list is shorter than expected.

### Proof of Concept
```rust
// transaction-status/src/parse_token/extension/confidential_transfer.rs (test module)
#[test]
fn test_withdraw_floor_account_count_misreports_context_accounts() {
    use solana_message::compiled_instruction::CompiledInstruction;

    // Craft WithdrawInstructionData bytes with:
    //   equality_proof_instruction_offset == 0  (context-account based)
    //   range_proof_instruction_offset   != 0  (instruction-offset/sysvar based)
    // then supply exactly 4 account_indexes: [account, mint, X, Y]
    // Real spl-token-2022 encoder would need 5 accounts here:
    // [account, mint, equalityProofContextStateAccount, instructionsSysvar, owner]
    let account = Pubkey::new_unique();
    let mint = Pubkey::new_unique();
    let equality_ctx = Pubkey::new_unique(); // should map to X
    let owner = Pubkey::new_unique();        // should map to Y (but real builder puts sysvar+owner after ctx)

    let account_keys_vec = vec![account, mint, equality_ctx, owner];
    let account_keys = AccountKeys::new(&account_keys_vec, None);
    let account_indexes: [u8; 4] = [0, 1, 2, 3];

    let withdrawal_data = WithdrawInstructionData {
        amount: 42.into(),
        decimals: 9,
        new_decryptable_available_balance: Default::default(),
        equality_proof_instruction_offset: 0,
        range_proof_instruction_offset: 1, // nonzero
    };
    let instruction_data = encode_instruction_data(&withdrawal_data); // helper to serialize via spl-token-2022 encoding

    let parsed = parse_confidential_transfer_instruction(
        &instruction_data,
        &account_indexes,
        &account_keys,
    )
    .unwrap();

    // BUG: account_indexes[2] (equality_ctx) gets mislabeled as instructionsSysvar
    assert_eq!(parsed.info["instructionsSysvar"], json!(equality_ctx.to_string()));
    // BUG: equalityProofContextStateAccount is missing entirely despite offset == 0
    assert!(parsed.info.get("equalityProofContextStateAccount").is_none());
    // BUG: account_indexes[3] (intended as owner in a valid 5-account layout would be
    // instructionsSysvar, and index 4 would be owner) is misreported as "owner"
    assert_eq!(parsed.info["owner"], json!(owner.to_string()));
}
```
Expected assertions on a fixed implementation: the account count required should scale with the offset combination (rejecting the 4-account instruction with a parse error, or correctly assigning `equalityProofContextStateAccount` to index 2 and `instructionsSysvar`/`owner` to subsequent indexes only if enough accounts are present), matching what `inner_withdraw`'s real encoder (exercised in the existing `test_withdraw` table) would produce for each offset combination.
