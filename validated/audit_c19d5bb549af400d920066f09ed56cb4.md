### Title
Stale-APR share minting in `depositDuringEpoch` lets an unprivileged user front-run an honest `setAprs`/`stopEpoch` rate change and mint inflated tranche shares - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
`depositDuringEpoch` prices newly minted tranche tokens using the *current* strategy APR (`_getStrategyApr()` → `unscaledApr`), `trancheAPRSplitRatio`, `fee`, and `managementFee` at the moment of the call. These parameters are controlled by honest privileged setters (`IdleCreditVault.setAprs`, `stopEpoch(_newApr)`, split-ratio/fee setters) but there is no slippage/expected-parameter check on the user side. An unprivileged, KYC-passed lender can watch the mempool for an honest APR *decrease* (or split-ratio/fee change) and front-run it with `depositDuringEpoch`, receiving shares priced on the stale high APR. The phantom interest baked into the mint is diluted across honest holders at withdrawal, an analog of the Fintroller front-run: a state-changing privileged call sandwiched against a user transaction whose price depends on the changed parameter.

### Finding Description
In `depositDuringEpoch` (`contracts/IdleCDOEpochVariant.sol:656`), minted shares are computed as:

```
uint256 interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer);
uint256 trancheInterest = _calcTrancheInterestShare(
    _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)), _tranche);
uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
```
(`contracts/IdleCDOEpochVariant.sol:691-724`)

`_calcInterest` reads the live strategy APR (`_getStrategyApr()` → `IdleCreditVault.unscaledApr`). When the honest manager later lowers `unscaledApr` via `setAprs` (or sets a lower APR at `stopEpoch`), the attacker already holds `trancheInterest * supply / expectedFinal` excess shares whose embedded interest will never accrue. `expectedEpochInterest += interest` (line 728) also inflates the expected-interest bucket, but the real loss lands on holders: at `requestWithdraw`, `_calcInterestWithdrawRequest` splits the *actual* (lower) interest pro-rata over the now-larger tranche supply (`_amount * totTrancheInterest / _trancheBal`, line 870), so the attacker's inflated share count extracts a disproportionate fraction of real interest and, because shares also redeem principal at `tranchePrice`, pulls underlying value that honest NAV must absorb.

The same surface applies to `requestWithdraw` itself: `_totalWithdrawFees(principal, interest)` (line 774) and `_calcTrancheInterestShare` (line 884) use the *current* `fee`, `managementFee`, and `trancheAPRSplitRatio` with no `minOut`/`expectedFee` parameter — a user whose request lands after an honest fee/split increase receives strictly less than quoted, exactly the Fintroller pattern. There is no timelock, no epoch-boundary gating, and no user-supplied expected-parameter check on either path; `_skimDonatedAssets`, `_updateAccounting`, KYC, and epoch-running checks do not prevent it.

### Impact Explanation
Direct theft via dilution: the attacker converts principal into shares worth more than the value they will actually generate, then redeems them through the normal `requestWithdraw`/`claimWithdrawRequest` path, extracting real interest and NAV from honest tranche holders. The magnitude is bounded by `trancheInterest * trancheSupply / expectedFinal` evaluated at the stale-vs-new APR delta — proportional to deposit size and the APR step, so with a large deposit and a large rate cut the extraction scales linearly. On the withdraw side, a victim's receipt is silently haircut by an intra-block fee/split change with no recourse, violating the "receipt amount quoted equals receipt amount minted" invariant.

### Likelihood Explanation
Requires only an unprivileged KYC-passed wallet (the standard lender barrier) observing an honest manager/owner parameter tx in the mempool — public RPCs and bundlers make this routine. Preconditions: `isEpochRunning` with `block.timestamp < epochEndDate`, non-AYS fixed-APR mode, non-programmable borrower, and the target tranche having nonzero supply (lines 658-677) — i.e., any normal running epoch where rate updates occur mid-epoch or at `stopEpoch`. No malicious privileged role is needed; the privileged caller is honest, the attacker merely sequences around it.

### Recommendation
Mirroring the external report's fix: add user-supplied expectation parameters so the transaction reverts on a changed pricing input rather than silently repricing.

- `depositDuringEpoch(uint256 _amount, address _tranche, uint256 _minMinted)` (or `expectedApr`/`expectedSplitRatio`): revert if `_minted < _minMinted` or if `unscaledApr`/`trancheAPRSplitRatio`/`fee` differ from the caller's expectation.
- `requestWithdraw(uint256 _amount, address _tranche, uint256 _minUnderlyings)`: revert if the computed `_underlyings` is below the caller's floor after `_totalWithdrawFees`.
- Optionally restrict `setAprs`/split-ratio/fee setters to epoch boundaries (`stopEpoch`/`startEpoch` window), removing mid-epoch repricing surface entirely.

### Proof of Concept
Foundry fork PoC (mainnet fork, `TestIdleCDOBase`-style setup, fixed-APR non-AYS epoch):

```solidity
// Setup: epoch running, APR = 10%, honest holders in AA tranche.
// Attacker = KYC'd EOA holding `underlyings`.

// 1. Manager broadcasts setAprs(5%, ...) — an APR decrease.
// 2. Attacker front-runs in the same block:
uint256 minted = cdoEpoch.depositDuringEpoch(attackerAmount, address(AAtranche));
//    minted embeds trancheInterest computed at stale 10% APR.

// 3. Manager's tx lands: unscaledApr = 5%.
// 4. Epoch ends; stopEpoch delivers only 5%-based interest.
//    expectedEpochInterest was inflated by the stale-APR deposit,
//    so the shortfall is socialized across all holders.

// 5. Next epoch: attacker calls requestWithdraw(minted, AAtranche)
//    then claimWithdrawRequest(). Because shares grew while real
//    interest did not, attacker's payout exceeds deposit + fair
//    share of actual interest; assert:
assertGt(attackerProfit, honestHolderFairShareDelta);
// and assert honest holders' aggregate claim < their entitlement
// absent the front-run.
```

Key assertion pair: `minted > sharesThatWouldBeMintedAtNewApr` (stale-price capture) and post-claim `underlying balance delta > deposit + proportional real interest` (theft/dilution quantified). I was unable to confirm the exact access-control modifier on `IdleCreditVault.setAprs` within the iteration budget, but the vector only requires the APR to be manager-updatable mid-epoch, which the codebase's `unscaledApr`/`instantWithdrawAprDelta` mid-epoch APR-drop handling confirms is a supported state change.
