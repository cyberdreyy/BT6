### Title
Withdrawal receipts are re-counted as active NAV, creating unbounded borrower debt - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary

`IdleCreditVault.requestWithdraw` burns the requested principal from the CDO and mints an unrestricted ERC20 strategy-token receipt to the user. Because `getContractValue()` treats every strategy token held by the CDO as active NAV, transferring that receipt back to the CDO causes the already-requested principal to be counted again while its pending withdrawal liability remains outstanding. Repeating the deposit/request/donate cycle can inflate `pendingWithdraws` far beyond the capital supplied to the borrower.

### Finding Description

A normal withdrawal request burns `_principal` strategy tokens from the CDO, mints `_amount` strategy tokens to the requester, and records `_amount` in `pendingWithdraws`. [1](#0-0) 

The strategy receipt is an ordinary `ERC20Upgradeable` token and has no transfer restriction preventing the requester from sending it back to the CDO. [2](#0-1) 

`getContractValue()` counts the CDO’s entire `strategyToken` balance, without excluding withdrawal receipts held by the CDO. [3](#0-2) 

A subsequent deposit or withdrawal calls `_updateAccounting()`, which reads that inflated NAV and crystallizes the donated receipt as tranche NAV. [4](#0-3) 

The same receipt remains payable through `claimWithdrawRequest`, so its value exists simultaneously as active tranche backing and as a pending withdrawal claim. [5](#0-4) 

The double count can then be withdrawn again through `requestWithdraw`, which burns the inflated strategy-token balance and mints a new receipt while increasing `pendingWithdraws`. [6](#0-5) 

### Impact Explanation

An unprivileged KYC-passing lender can turn one unit of withdrawal receipt into both active NAV and a pending claim, then repeat the cycle to create borrower liabilities unrelated to actual deposits.

For example, with zero fees and temporarily zero interest:

1. Attacker deposits `100`.
2. Attacker requests `50`; CDO balance becomes `50`, the attacker receives a `50` receipt, and `pendingWithdraws = 50`.
3. Attacker transfers the `50` receipt to the CDO; CDO strategy-token balance becomes `100`.
4. Attacker requests the remaining `50` tranche tokens. Accounting values them at `100`, burns `100` strategy tokens from the CDO, mints another `100` receipt, and raises `pendingWithdraws` to `150`.
5. Attacker deposits `1`, donates the `100` receipt, and requests the newly minted tranche position. Accounting values it at `101`, so `pendingWithdraws` becomes `251` while the CDO’s active balance returns to zero.

At epoch stop, `pendingWithdraws` is included in the amount pulled from the borrower and transferred to the strategy for claims. [7](#0-6) 

The attacker therefore forces the honest borrower to fund claims exceeding the capital and interest actually advanced. If the borrower cannot fund the inflated liability, the vault enters default and legitimate active lenders absorb the shortfall through default recovery. [8](#0-7) 

### Likelihood Explanation

The attacker needs only a wallet allowed by `isWalletAllowed`, sufficient underlying for a deposit, and the ability to transfer receipt tokens. [9](#0-8) 

The exploit does not require control of the owner, manager, guardian, borrower, queue, fee receiver, or Keyring administrator. It operates between epochs while withdrawal requests are enabled, and every step is a permitted user action.

`_skimDonatedAssets()` does not prevent the issue because it removes only raw underlying tokens, while the double-counted asset is the strategy token itself. [10](#0-9) 

### Recommendation

Do not count all strategy tokens held by the CDO as active NAV.

The CDO should track active strategy-token backing separately from receipt tokens returned to the CDO, or strategy withdrawal receipts should be non-transferable or represented by a separate receipt token that is excluded from `getContractValue()`.

At minimum, `requestWithdraw` should subtract pending withdrawal receipt liabilities when deriving active NAV. Accounting should enforce:

```solidity
activeStrategyBalance = cdoStrategyTokenBalance - outstandingReceiptBasisHeldByCDO;
```

A safer structural fix is to avoid minting transferable strategy tokens to users as withdrawal receipts and store receipt claims solely in accounting mappings.

### Proof of Concept

The following Foundry-style test demonstrates the inflation cycle. It assumes the standard `IdleCreditVault.t.sol` fixture, an allowed caller, zero fees, and fixed-APR mode.

```solidity
function testWithdrawReceiptDonationInflatesPendingWithdraws() external {
    uint256 depositAmount = 100 * ONE_SCALE;
    uint256 firstRequest = 50 * ONE_SCALE;

    // Attacker opens an active position.
    idleCDO.depositAA(depositAmount);

    // First request: CDO loses 50 active strategy tokens and attacker receives
    // a transferable 50-token withdrawal receipt.
    uint256 firstReceipt = cdoEpoch.requestWithdraw(
        firstRequest,
        address(AAtranche)
    );

    assertEq(strategy.balanceOf(address(cdoEpoch)), depositAmount - firstReceipt);
    assertEq(strategy.pendingWithdraws(), firstReceipt);

    // Return the receipt to the CDO. It is counted again as active strategy-token NAV.
    strategy.transfer(address(cdoEpoch), firstReceipt);

    assertEq(strategy.balanceOf(address(cdoEpoch)), depositAmount);
    assertEq(strategy.pendingWithdraws(), firstReceipt);

    // The remaining tranche position is now valued using the double-counted NAV.
    uint256 attackerTranches = AAtranche.balanceOf(address(this));
    uint256 secondReceipt = cdoEpoch.requestWithdraw(
        attackerTranches,
        address(AAtranche)
    );

    // The second receipt is approximately the full original deposit even though
    // only 50 of active principal remained before the donation.
    assertApproxEqAbs(secondReceipt, depositAmount, 2);

    // Borrower must now fund both receipts: 50 + 100 for only 100 of deposits.
    assertApproxEqAbs(
        strategy.pendingWithdraws(),
        firstReceipt + depositAmount,
        2
    );
    assertEq(strategy.balanceOf(address(cdoEpoch)), 0);

    // Repeat once after depositing 1 unit: donate the second receipt and mint a
    // new receipt from the inflated active balance.
    idleCDO.depositAA(ONE_SCALE);
    strategy.transfer(address(cdoEpoch), secondReceipt);

    uint256 thirdReceipt = cdoEpoch.requestWithdraw(
        AAtranche.balanceOf(address(this)),
        address(AAtranche)
    );

    assertGt(thirdReceipt, depositAmount);
    assertGt(strategy.pendingWithdraws(), depositAmount + firstReceipt);
}
```

The critical assertion is `pendingWithdraws > depositAmount`: receipts that were already separated into pending claims were returned to the CDO, counted as active NAV, burned through another withdrawal request, and minted as a new claim.
