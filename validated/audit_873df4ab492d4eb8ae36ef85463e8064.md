## Analysis

I identified a valid analog of the reported bug class in this repository. The external report's core pattern is: **two related operations rely on different sources of truth for the same underlying quantity, and stale/inconsistent state from one path lets a threshold check pass incorrectly.** In `multisig2`, this maps to confirmations recorded for a request versus the set of currently *live* members entitled to grant them — i.e., "confirmations counted versus live members," one of the explicitly valid custody bindings.

### Root cause

`delete_member()` only purges confirmations/requests where the removed member was the **original requester** (`r.member == member`), never where the removed member appears inside another request's **confirmations set**: [1](#0-0) 

Meanwhile `confirm()` treats `confirmations.len()` as the count of members entitled to authorize the request, without checking that every entry in that set still corresponds to a current member of `self.members`: [2](#0-1) 

`self.members` and `self.confirmations` are independent pieces of state [3](#0-2) , and nothing keeps them synchronized when a member is removed while holding an outstanding confirmation on a request they did not create.

## Title
Stale confirmations from removed members are counted toward the K-of-N threshold, allowing sub-threshold execution - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` executes a request once `confirmations.len() + 1 >= num_confirmations`, but `delete_member` never removes a departing member's confirmation from requests they did not originally create. A member can confirm a request, get removed from the multisig, and their stale confirmation still counts toward the threshold, letting the request execute with fewer *live* confirming members than `num_confirmations` requires.

### Finding Description
The binding that must hold is: **number of confirmations from currently valid members ≥ `num_confirmations`**. The contract instead enforces: **size of the `confirmations` HashSet (regardless of member validity) ≥ `num_confirmations`**.

- `confirm()` inserts `member.to_string()` into `self.confirmations[request_id]` [2](#0-1) .
- `delete_member()` is invoked via `DeleteMember` action inside `execute_request` [4](#0-3) , and only cleans up requests *authored* by the removed member: `filter_map(|(k, r)| if r.member == member { ... })` [5](#0-4) . It does not scan `self.confirmations` for entries containing the removed member's identifier on requests authored by *other* members.
- `current_member()` (used only by `add_request`/`confirm`/`delete_request` callers, i.e., the acting caller) validates the caller against `self.members` [6](#0-5) , but nothing re-validates *previously stored* confirmations against the current `self.members` set at threshold-check time.

Because `MultisigMember::to_string()` serializes to a stable JSON string keyed by public key or account id [7](#0-6) , the stale string remains a permanent, uncredited "ghost vote" in the `HashSet<String>` for any request it was added to before removal.

### Impact Explanation
This is a **Critical** custody-threshold violation per the given impact classes ("a multisig request executed below threshold"). A `Transfer`, `AddKey` (full access key), or `DeployContract` request — anything the multisig guards — can be executed by real signatures from fewer members than `num_confirmations` mandates, because a ghost confirmation from an already-removed member fills the gap. This directly breaks the equality `live_confirmations == num_confirmations_required` that the K-of-N scheme is supposed to guarantee, and can lead to unauthorized transfers of NEAR held by the multisig account or unauthorized key/contract changes.

### Likelihood Explanation
Medium-to-High. It requires only ordinary multisig operation, no privileged bug abuse beyond normal member management:
1. Member B confirms request X (authored by member A, not yet at threshold).
2. Members (via a separate, properly-threshold-confirmed `DeleteMember` request) remove B from the multisig for a legitimate reason (e.g., B's key was compromised, B left the organization) — this is a normal, expected admin action, not an attack in itself.
3. B's stale confirmation on request X survives.
4. One additional live member confirms X; the stale entry lets it cross the threshold and execute with one fewer live signer than intended.

This does not require a malicious deployment, redeploy, or victim key theft — merely the ordinary sequence of "confirm, then later remove that confirmer," which is a foreseeable operational pattern (e.g., removing a compromised key precisely *because* its holder is no longer trusted, while that holder's stale confirmation still lingers on unrelated pending requests).

### Recommendation
When removing a member in `delete_member`, iterate over `self.requests` (not filtered by `r.member == member`) and for each request's `confirmations` set, remove the departing member's string key; alternatively, at threshold-check time in `confirm`, filter `confirmations` to only those members still contained in `self.members` before comparing against `num_confirmations`. The latter is the more robust fix, since it removes the "confirmations counted vs. live members" mismatch at the point of enforcement rather than relying on complete cleanup during every mutation of the member set.

### Proof of Concept
Using `multisig2/src/lib.rs` test harness conventions:
1. `MultiSigContract::new([A, B, C, D], 3)`.
2. A calls `add_request` for request X (e.g., `Transfer`) — not self-confirmed.
3. B calls `confirm(X)` → `confirmations[X] = {B}` (1/3).
4. Separately, run a fully-confirmed `DeleteMember{member: B}` request (requires 3 confirmations from A, C, D — none of whom is B) which succeeds and removes B from `self.members`. Per `delete_member`, since request X's `r.member == A` (not B), request X and its `confirmations[X] = {B}` are left untouched.
5. C calls `confirm(X)` → `confirmations[X].len() = 1`, `+1 = 2`, still `< 3`, so no execution yet (illustrates the count doesn't yet include the live add) — inserts C: `confirmations[X] = {B, C}`.
6. D calls `confirm(X)`: `confirmations.len() = 2`, `+1 = 3 >= 3` → **executes**, even though the only *live* confirming members are C and D (2 live members), not 3. B's confirmation, from a since-removed member, was decisive in reaching the threshold.

Note: I was not able to execute this scenario against the actual compiled test harness (no terminal/build access in this mode); the trace above is derived directly from reading `confirm`, `delete_member`, and `execute_request` in `multisig2/src/lib.rs` and should be validated with an actual `#[test]` (e.g., extending `add_key_delete_key_storage_cleared`) in a Devin session with build tooling.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
