### Title
APR0 withdraw request permanently bricks `stopEpoch` once APR is raised, freezing all pool funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed()` whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. `apr0TotalPrincipal` is increased by any unprivileged lender who calls `requestWithdraw` while the vault's APR is 0, and it is only cleared inside the same function that reverts (or per-user through the default-recovery claim path). An attacker can therefore open an APR0 receipt during a zero-APR epoch; if the honest manager later sets a nonzero APR via `setAprs` before the epoch settles, every subsequent `stopEpoch` reverts forever. The analog to CVE-2020-24823 is a crafted input state that crashes a core processing function — here the "crafted ELF" is an attacker's APR0 receipt, and the "segfault" is a permanent revert inside the epoch state machine.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` routes to `_requestWithdrawApr0` whenever `unscaledApr == 0` (lines 285-286). `_requestWithdrawApr0` increments the global `apr0TotalPrincipal` (line 576).
- `prepareStopEpochWithApr0`, called by `IdleCDOEpochVariant.stopEpoch`, reverts at lines 506-508:
  ```solidity
  if (unscaledApr != 0) {
    revert NotAllowed();
  }
  ```
  whenever `apr0TotalPrincipal != 0` (checked at line 499-504).
- `apr0TotalPrincipal` is only zeroed at line 540 — unreachable because the revert happens earlier — or decremented per-user in `_clearWithdrawClaimForEpoch` (line 827) which only runs on the default-finalization claim path.

So once a nonzero `apr0TotalPrincipal` exists and `unscaledApr` is nonzero, no clean `stopEpoch` can ever execute. The revert is sticky: changing APR back to 0 is the only escape, and there is no guarantee the manager intends to keep APR at 0 permanently — any honest APR configuration change after the request permanently blocks the epoch lifecycle.

### Impact Explanation
Permanent freezing of all pool funds: with `stopEpoch` bricked, `epochNumber` can never advance, so all pending withdraw requests (`claimWithdrawRequest` requires `epochNumber > lastWithdrawRequest`), new epochs, and borrower repayment accounting are frozen. The only exit is borrower default finalization, which forces a loss/haircut on LPs that would not otherwise occur. An attacker paying only gas to deposit and request a withdraw during a zero-APR window can hold the entire vault's lifecycle hostage to a single future manager APR change.

### Likelihood Explanation
The trigger requires (a) the vault operating at `unscaledApr == 0` — a supported mode exercised in the test suite — and (b) the manager later raising the APR, an ordinary honest administrative action. Any lender can create the poisoned state cheaply; there is no guard preventing `requestWithdraw` from seeding `apr0TotalPrincipal`, and no guard preventing `setAprs` from being called while an APR0 bucket is open. Likelihood is moderate: it needs both the APR0 regime and a subsequent APR change.

### Recommendation
Resolve the inconsistency instead of reverting in `prepareStopEpochWithApr0`: when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, settle the outstanding APR0 bucket at zero interest (rate 0 for that epoch) and clear `apr0TotalPrincipal`, or alternatively make `setAprs` revert while `apr0TotalPrincipal != 0` so the manager cannot enter the bricked state. The revert-in-stopEpoch pattern is unsafe because the clearing code path is unreachable once the state exists.

### Proof of Concept
```solidity
function testApr0RequestThenAprRaiseBricksStopEpoch() external {
    // Vault already in APR0 mode: manager sets APRs to 0 (see testApr0WithdrawGetsInterestAtStopEpoch)
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // Attacker: deposit via a fresh address and queue an APR0 withdraw request
    address attacker = makeAddr('apr0-attacker');
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    _startEpochAndCheckPrices(0);

    // Honest manager raises APR before the APR0 epoch settles
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(5e17, 0); // unscaledApr != 0

    // Every subsequent stopEpoch reverts NotAllowed: epoch can never close
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialProvidedApr, 0);
    // repeated attempts also revert; apr0TotalPrincipal cannot be cleared
}
```

Caveat: I verified the revert condition and the `apr0TotalPrincipal` lifecycle in `IdleCreditVault.sol` (lines 285-294, 490-541, 567-577, 811-837), but the grep results did not return the exact `stopEpoch` call site in `IdleCDOEpochVariant.sol`, so the claim that `prepareStopEpochWithApr0` is unconditionally invoked inside `stopEpoch` should be confirmed there before finalizing the PoC.
