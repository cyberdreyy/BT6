### Title
Loss-adjusted stopEpoch only haircuts the latest request epoch — older unclaimed receipts are paid at par, draining funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` applies a single `lossRecoveryPriceByEpoch[epochNumber]` haircut to the **aggregate** `pendingWithdraws`, which can contain receipts a user accumulated over several epochs. But `_claimLossAdjustedWithdrawRequest` only looks up `lastWithdrawRequest[_user]` and clears `withdrawsRequestsByEpoch[_user][lossEpoch]`. Any receipt basis recorded under an earlier epoch escapes the haircut and is then paid at par through `_claimFundedWithdrawRequest`, even though the borrower only funded the haircutted amount — an over-read of receipt basis outside the loss epoch's coverage.

### Finding Description
In `requestWithdraw` (IdleCreditVault.sol:243-295) each request adds to `pendingWithdraws`, sets `lastWithdrawRequest[_user] = currentEpoch`, and records per-epoch basis in `withdrawsRequestsByEpoch[_user][currentEpoch]`. A user may request again in a later epoch before claiming (the code comments at 322-324 explicitly support merging requests); the only guard (263-271) blocks a new request when the *previous* `lastWithdrawRequest` epoch already has a loss price.

When an epoch ends with a loss, `collectWithdrawFunds` (411-430) computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` over the whole `pendingWithdraws` — which includes the user's old epoch-N basis — and stores it under the **current** `epochNumber` (421).

At claim time:
- `_claimLossAdjustedWithdrawRequest` (789-801) reads `lossEpoch = lastWithdrawRequest[_user]` (the latest epoch, N+1), and `_clearWithdrawClaimForEpoch` (811-837) only zeroes `withdrawsRequestsByEpoch[_user][N+1]` and subtracts only that epoch's `normalAmount` from `withdrawsRequests[_user]`. The user is paid `basis(N+1) * price`.
- `_claimFundedWithdrawRequest` (319-350) then pays the remaining `withdrawsRequests[_user]` — which still contains the epoch-N basis — at par, burning the minted receipt tokens and transferring full underlying via `_transferFundedClaim`.

The epoch-N basis was haircut in the funding computation but is paid in full. The strategy collected only `pendingBasis * price` underlying yet pays out `basis(N+1)*price + basis(N)`, i.e. `(1 - price) * basis(N)` more than was funded.

### Impact Explanation
Broken invariant: pro-rata loss socialization of pending receipts. The overpayment is real underlying held by the strategy that was reserved for *all* haircutted claimants (and for subsequent requests). The attacker — an ordinary KYC'd tranche holder — directly extracts `(1 - lossRecoveryPrice) * oldReceiptBasis` of excess underlying. With a 50% loss price and a 100k old receipt, the theft is 50k underlying, leaving later claimants (including other users' loss-adjusted receipts and the default recovery reserve) undercollateralized — insolvency / freezing of unclaimed funds for honest users.

### Likelihood Explanation
Fully reproducible by an unprivileged lender with two withdraw requests in consecutive buffer phases, followed by any `stopEpochWithDuration`-style loss epoch (which the honest manager/borrower trigger via normal underfunding — no malicious privileged role needed). The guards do not stop it: the re-request guard at 263-271 only checks the epoch stored in `lastWithdrawRequest` *before* it is overwritten, and `lossRecoveryPriceByEpoch` for the earlier epoch is 0 at that point, so merging is permitted by design.

### Recommendation
Apply the loss haircut per-epoch to **all** unclaimed epochs contributing to `pendingWithdraws`, not only `lastWithdrawRequest`. Options:
- Track a per-user list/set of open request epochs (or a global `epochsWithLosses` check) so `_claimLossAdjustedWithdrawRequest` iterates every epoch with `lossRecoveryPriceByEpoch != 0` and haircuts each corresponding `withdrawsRequestsByEpoch` entry.
- Alternatively, revert `requestWithdraw` whenever the user has any outstanding `withdrawsRequests`/`apr0Users` principal from a different epoch (extend the existing `_hasWithdrawRequest`-style guard used in the post-default branch at 247-257 to the pre-default path), forcing claim-or-lose-haircut semantics before merging requests across epochs.

//    _claimLossAdjustedWithdrawRequest pays 100k * 0.5 = 50k (epoch-2 part).

The asserting invariant: total underlying paid to receipt holders must equal `pendingBasis * lossRecoveryPrice` (what the borrower actually funded); here the user alone extracts `150k` against `100k` funded.
