### Title
Instant-withdraw receipts from a previous epoch escape default-recovery accounting, freezing/stealing recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` keys instant-withdraw claim basis to `epochNumber` via `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`, but epoch rollover (`deposit()` during `stopEpoch` increments `epochNumber`) orphans prior-epoch instant receipts: they remain in `instantWithdrawsRequests` and `pendingInstantWithdraws`, yet `defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` (current epoch). After `finalizeDefaultRecovery`, those old-epoch receipts are excluded from `defaultRecoveryReserve` backing and cannot be paid through either the defaulted-claim path (per-epoch entry is keyed to `defaultRecoveryEpoch`) or the funded path (which reverts if it would dip into the reserve). This is the on-chain analog of a pathname escaping its restricted directory: an epoch-keyed "path" resolves outside the scope the recovery accounting intended.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 366–374).
- `deposit()` increments `epochNumber` when called during `stopEpoch` (lines 607–611), but no code clears or migrates old-epoch `instantWithdrawClaimsByEpoch` entries, and `collectInstantWithdrawFunds` only decreases the aggregate `pendingInstantWithdraws` (lines 398–403), not the per-epoch buckets.
- `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch (lines 644–649). Old-epoch instant basis is silently dropped.
- `_defaultPrefundedInstantReserve()` computes the "already funded" reserve as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (lines 716–723). When old-epoch pending instant receipts exist, `pendingInstantWithdraws` includes them while `instantBasis` does not, so prefunded reserve is under-counted.
- After `finalizeDefaultRecovery`, a user whose instant receipt was created in epoch `N < defaultRecoveryEpoch` calls `claimInstantWithdrawRequest`: `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` → zero (lines 842–845), so nothing is cleared; then the funded path burns `instantWithdrawsRequests[_user]` receipts and calls `_transferFundedClaim`, which must satisfy `balance - defaultRecoveryReserve >= amount` (lines 897–907). Since the reserve was computed without these claims, the transfer either reverts (permanent freezing of that user's claim while receipts are already burned — actually `_burn` executes before `_transferFundedClaim`, so a revert restores state, but the claim is unclaimable) or, if other unfunded underlyings sit in the strategy, drains funds belonging to other claimants.

### Impact Explanation
Direct theft or permanent freezing of recovery funds. Any prior-epoch instant-withdraw requester either (a) cannot claim at all — their underlying is trapped inside `defaultRecoveryReserve` which was computed without their basis, so their claim reverts indefinitely — or (b) pays at par out of underlyings not earmarked for them, leaving later defaulted-epoch claimants (tranche holders) underfunded by exactly the old-epoch instant amount. Quantified loss equals the aggregate old-epoch `pendingInstantWithdraws` remainder at default time — e.g., a user with 100k USDC of instant receipts from epoch N-1 permanently loses the claim or causes an equivalent shortfall to other claimants.

### Likelihood Explanation
Requires a specific but realistic sequence: an instant withdraw requested in epoch N that is not fully funded before `stopEpoch` rolls `epochNumber` to N+1, followed by a borrower default and `finalizeDefaultRecovery`. Instant withdrawals are a supported feature; partial funding is explicitly contemplated (`pendingInstantWithdraws` is the "unfunded remainder", `_defaultPrefundedInstantReserve` exists precisely because funding can be partial). No privileged misbehavior is needed — only the honest manager/borrower sequence of `startEpoch`/`stopEpoch` calls plus a default. Attacker role: any lender using `requestInstantWithdraw` whose request straddles an epoch boundary — an ordinary unprivileged user.

### Recommendation
In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, aggregate instant basis across all epochs with outstanding claims instead of `instantWithdrawClaimsByEpoch[epochNumber]` only — e.g., maintain a running `totalInstantWithdrawClaims` counter incremented in `requestInstantWithdraw` and decremented in `collectInstantWithdrawFunds`/claims, and use it for both the basis and the prefunded-reserve computation. Alternatively, block epoch rollover (`deposit` during `stopEpoch`) while `pendingInstantWithdraws != 0` and old-epoch instant claims remain unfunded.

### Proof of Concept
Foundry fork PoC (modeled on `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` setup which etches `IdleCDOEpochVariant`/`IdleCreditVault` bytecode over mainnet instances):

```solidity
function testOldEpochInstantReceiptFrozenAfterDefault() public {
    // Setup: etch contracts, LP holds tranches, pool running at epoch N
    // 1. LP (attacker/victim is an ordinary lender) requests instant withdraw
    vm.prank(address(cdoEpoch));
    strategy.requestInstantWithdraw(100_000e6, LP);

    // 2. Partial funding only: CDO collects part of it
    vm.startPrank(address(cdoEpoch));
    deal(address(underlying), address(cdoEpoch), 40_000e6);
    underlying.approve(address(strategy), 40_000e6);
    strategy.collectInstantWithdrawFunds(40_000e6); // pendingInstantWithdraws = 60k, epoch bucket = 100k
    // 3. Epoch rolls: stopEpoch path calls deposit() -> epochNumber = N+1
    strategy.deposit(1); // triggers epochNumber += 1
    vm.stopPrank();

    // 4. Borrower defaults; owner finalizes with partial recovery
    //    finalizeDefaultRecovery computes basis = pendingWithdraws + instantWithdrawClaimsByEpoch[N+1]
    //    -> LP's 100k basis (recorded under epoch N) is EXCLUDED
    //    -> prefundedReserve = max(0, instantBasis[N+1]=0 - pending=60k) = 0 (under-counted by 40k)

    // 5. LP calls claimInstantWithdrawRequest via CDO
    vm.prank(address(cdoEpoch));
    // _claimDefaultedInstantWithdrawRequest sees instantWithdrawsRequestsByEpoch[LP][N+1] == 0
    // funded path: balance - defaultRecoveryReserve < 100k -> revert NotAllowed()
    vm.expectRevert(NotAllowed.selector);
    strategy.claimInstantWithdrawRequest(LP);
}
```

Uncertainty note: I could not fully verify the exact `IdleCDOEpochVariant` call ordering around `stopEpoch`/`deposit()`/`collectInstantWithdrawFunds` and `finalizeDefaultRecovery` wiring (the CDO-side file was only partially inspected). The strategy-side epoch-keying gap is confirmed from the code above, but the PoC's epoch-rollover path should be validated against `IdleCDOEpochVariant.stopEpoch`/`_beforeStopEpoch` to confirm `deposit()` is invoked while `pendingInstantWithdraws` can remain nonzero.
