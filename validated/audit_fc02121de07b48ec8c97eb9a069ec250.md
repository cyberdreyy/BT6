### Title
EI credentials bypass "no int-ID job runs for EIs" restriction via impersonated UserRoleRun context - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` sets `SessionUserKey` to a synthetic `*clsessions.User{Role: UserRoleRun}` after successfully authenticating an external initiator. `PipelineRunsController.Create`'s `isUser` check (`auth.GetAuthenticatedUser`) only checks whether a `*clsessions.User` object exists in context, not whether the request was actually authenticated as a real user, so EI credentials satisfy the `isUser` gate and can trigger `POST /v2/jobs/:intID/runs` despite the code comment stating "EIs not allowed."

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered in the `userOrEI` group with authenticator chain `AuthenticateExternalInitiator, AuthenticateByToken, AuthenticateBySession` and wrapped in `auth.RequiresRunRole(prc.Create)` [1](#0-0) .

`AuthenticateExternalInitiator` validates the EI's access key/secret via `FindExternalInitiator`/`bridges.AuthenticateExternalInitiator`, and on success sets `c.Set(SessionExternalInitiatorKey, ei)` and also `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` — a synthetic user object, not a real authenticated user [2](#0-1) .

`GetAuthenticatedUser` simply checks whether *any* `*clsessions.User` value exists under `SessionUserKey` and returns `ok=true` if so, with no way to distinguish "real user session/token" from "EI-derived synthetic user" [3](#0-2) .

In `PipelineRunsController.Create`, `isUser` is derived from `auth.GetAuthenticatedUser(c)`, and the comment explicitly states "only users are allowed to run jobs using int IDs - EIs not allowed." However, because EI authentication populates the exact same `SessionUserKey` context value with `Role: UserRoleRun`, `isUser` evaluates to `true` for EI-only requests, and the int32 ID branch executes, calling `prc.App.RunJobV2(ctx, jobID, nil)` and returning a full pipeline run resource [4](#0-3) .

`RequiresRunRole` middleware also does not distinguish EI from real users — it only checks `user.Role != UserRoleView`, which the synthetic EI user satisfies since its `Role` is `UserRoleRun` [5](#0-4) .

Thus, the intended restriction ("EIs not allowed" to use int job IDs, distinct from the intended webhook/UUID-based EI job triggering) is not enforced at the code level — it is contradicted by the impersonation performed in `AuthenticateExternalInitiator`.

### Impact Explanation
An attacker holding only EI credentials for job A can enumerate/guess any job's numeric ID and trigger `RunJobV2` for arbitrary jobs (not just their own), since `PipelineRunsController.Create` does not check job ownership or EI-to-job binding for the int32 path — it only checks `isUser`. This is an authorization bypass allowing an EI-scoped credential to gain the "run any job" capability intended to be restricted to real run-role+ human users, corresponding to the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Precondition is minimal: possession of any valid EI access-key/secret pair (the credential's intended purpose is to trigger webhook job runs). No other role or admin access is required. The exploit is a single unauthenticated-as-user HTTP POST with EI headers and an integer job ID; it's fully repeatable and deterministic.

### Recommendation
Distinguish EI-originated authentication from real user authentication in context (e.g., use a separate context key/type or a boolean flag alongside `SessionUserKey`), and have `PipelineRunsController.Create`'s `isUser` check explicitly verify the absence of `SessionExternalInitiatorKey` / a "real user" flag before allowing the int32-ID path. Do not synthesize a `*clsessions.User` object for EI requests when downstream code relies on `GetAuthenticatedUser` to gate user-only functionality.

### Proof of Concept
Handler/integration test (in `core/web/pipeline_runs_controller_test.go`-style suite):
1. Create an external initiator via `ExternalInitiatorsController.Create` (or ORM) and a job.
2. Send `POST /v2/jobs/<jobID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) set to the EI's credentials, and no session cookie or user API token.
3. Assert current (buggy) behavior: response is `200 OK` with a `pipelineRun` resource, i.e., `RunJobV2` was invoked — proving EIs bypass the "EIs not allowed" comment.
4. Expected/fixed behavior: assert `401 Unauthorized` or `403 Forbidden`, confirming that EI-derived context is rejected on the int-ID `/runs` path and only genuine session/API-token users can trigger `RunJobV2` via that pathway.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
