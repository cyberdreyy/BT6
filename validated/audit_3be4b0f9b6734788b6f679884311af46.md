### Title
Loss-adjusted withdraw receipts are claimed at par because `lossRecoveryPriceByEpoch` is keyed by the funding epoch while claims look it up by the request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Traefik bug is a representation desync: a length computed in the decoded-path domain is used to slice the encoded-path domain, so the authorization layer sees one path while the backend serves another. The same class exists in `IdleCreditVault`: a loss haircut is stored under the strategy epoch at funding time (`epochNumber` after `stopEpoch` bumped it), but users claim via `lastWithdrawRequest[_user]`, which was recorded one epoch earlier at request time. The lookup misses, the haircut path is skipped, and the funded-claim path pays the full un-haircut basis.

### Finding Description
`requestWithdraw` records the user's receipt against the *request* epoch: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` [1](#0-0) . `epochNumber` is incremented inside `deposit` when the epoch is still running, i.e. during `stopEpoch` [2](#0-1) . When the borrower underfunds pending receipts, `collectWithdrawFunds` stores the recovery ratio under the *post-stop* epoch: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` [3](#0-2) . On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the request epoch — finds `0`, and returns `0` [4](#0-3) . Execution then falls into `_claimFundedWithdrawRequest`, whose only gate is `epochNumber <= lastWithdrawRequest[_user]`, which is false after the bump, so it burns the receipt and calls `_transferFundedClaim` for the full `withdrawsRequests[_user]` at par [5](#0-4) . The same request-epoch vs funding-epoch desync exists in `defaultPendingClaimBasis`/`_claimDefaultedInstantWithdrawRequest` (`instantWithdrawClaimsByEpoch[epochNumber]` vs per-user request epochs) [6](#0-5) .

### Impact Explanation
Only `pendingToFund = pendingBasis - pendingLoss` was pulled into the strategy by `collectWithdrawFunds`, yet every pending receipt in that epoch can claim its full pre-loss basis at par. Early claimants drain the funded amount plus any other strategy balance not protected by the `defaultRecoveryReserve` guard, while later claimants' transfers revert — realized loss socialization is bypassed, producing direct overpayment/theft and permanent freezing for remaining receipts [7](#0-6) . Quantified loss: up to `pendingLoss` (the haircut portion, proportional to `_lossAmount * pendingBasis / totalBasis` in `previewLossAdjustedWithdrawFunds`) is stolen by first-come claimants [8](#0-7) .

### Likelihood Explanation
Trigger requires only a `stopEpochWithDuration(_lossAmount > 0)` (honest borrower partially defaulting on owed interest/principal — a normal credit event), plus any pending withdraw receipt from the stopped epoch held by an unprivileged user. No privileged misbehavior is needed; the epoch bump happens automatically in `deposit` during `stopEpoch`. The `requestWithdraw` guard that forces claiming a loss-adjusted receipt before re-requesting does not prevent this because the lookup misses by epoch, not by user state [9](#0-8) . One caveat I could not fully verify within this pass: the exact ordering of `collectWithdrawFunds` relative to the `epochNumber` bump inside `IdleCDOEpochVariant.stopEpochWithDuration` — the fork PoC below must confirm `epochNumber` is already incremented when `collectWithdrawFunds` runs (the `_prefundedEpochToProcess` comment indicates the just-finished epoch equals `epochNumber` post-stop, which supports this ordering) [10](#0-9) .

### Recommendation
Key the loss-recovery price consistently: store `lossRecoveryPriceByEpoch[epochNumber - 1]` (the request epoch) in `collectWithdrawFunds`, or have `_claimLossAdjustedWithdrawRequest` resolve the funding epoch (`lastWithdrawRequest[_user] + 1`). Alternatively, record the claim epoch explicitly per receipt at request time so request and funding epochs cannot diverge. Add a regression test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] != 0` after an underfunded stop.

### Proof of Concept
Foundry fork PoC outline (against a deployed `IdleCDOEpochVariant` + `IdleCreditVault` on mainnet):

```solidity
// 1. During running epoch N: user requests withdraw via CDO
vm.prank(user); // via IdleCDOEpochVariant.requestWithdraw(trancheAmount, tranche)
cdo.requestWithdraw(amount, AAtranche); // sets lastWithdrawRequest[user] = N

// 2. Owner calls stopEpochWithDuration with a loss (borrower underfunds)
vm.prank(owner);
cdo.stopEpochWithDuration(duration, lossAmount); // deposit() bumps epochNumber to N+1
//    -> strategy.collectWithdrawFunds(pendingToFund < pendingBasis)
//    -> lossRecoveryPriceByEpoch[N+1] = price < 1e18; lossRecoveryPriceByEpoch[N] == 0

// 3. User claims through the CDO during buffer/epoch N+1
uint balBefore = underlying.balanceOf(user);
vm.prank(user);
cdo.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[N] == 0 -> skipped
// _claimFundedWithdrawRequest: epochNumber(N+1) <= lastWithdrawRequest(N) is false
//   -> pays full pendingBasis at par instead of basis * price
assertEq(underlying.balanceOf(user) - balBefore, pendingBasis); // not pendingToFund share
```

The assertion shows the user received the un-haircut basis while the strategy only funded the haircut amount — subsequent claimants revert on insufficient balance.

    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;

    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
