### Title
Docker executor's `resumeDependencies()` reattaches to containers by ID alone, without verifying job/runner ownership - ([File: executors/docker/docker.go])

### Summary
The docker executor's `resumeDependencies()` trusts `build-container-id`, `helper-id`, and `service-ids` parsed from `envKeyFields` and calls `ContainerInspect`/`ContainerStart` on them with no check that these containers were created for the resuming job, runner, or project. This is inconsistent with the autoscaler executor, which explicitly checks `RunnerID`/`SystemID` on the `EnvironmentKey` before trusting it.

### Finding Description
`common.ParseEnvironmentKey` (`common/environment_key.go:26-58`) parses `<runner-id>/<system-id>/<fields>` into an `EnvironmentKey{RunnerID, SystemID, Fields}`. The docker executor's `resumeDependencies()` calls this and then `parseEnvKeyFields(envKey.Fields)` [1](#0-0) , but never inspects `envKey.RunnerID` or `envKey.SystemID` — it goes straight to `e.dockerConn.ContainerInspect(e.Context, fields.buildContainerID)` and later `ContainerInspect`/`ContainerStart` for the helper and each service ID [2](#0-1) . `parseEnvKeyFields` itself (`executors/docker/environment_key_fields.go:32-51`) only checks that `build-container-id` and `helper-id` are non-empty and that `service-ids` doesn't contain empty entries — it performs zero ownership validation of the IDs themselves.

Contrast this with `executors/internal/autoscaler/executor.go:190-208` (`validateEnvKey`), which explicitly rejects the key if `key.RunnerID != runnerID` or `key.SystemID != systemID` before extracting any executor fields. The docker executor has no equivalent check inside `resumeDependencies()`, and it also never cross-checks the inspected containers' own labels — even though `executors/docker/internal/labels/labels.go:31-58` already stamps every managed container/volume with `com.gitlab.gitlab-runner.job.id`, `.project.id`, `.runner.id`, etc. Those labels are set at creation time but are never read back during resume to confirm the found container actually belongs to the current job/project/runner.

The `EnvironmentKey` itself is also logged verbatim into the job trace when produced (`b.logger.Infoln("Job environment suspended:", s)` in `common/build.go:306`, confirmed also via `SetEnvironmentKey` trace call in `common/build_test.go:5872`), meaning the full container-ID set for a job is disclosed to anyone able to view that job's log.

### Impact Explanation
If any mechanism (backend key routing, replay, misconfiguration of a shared runner across environments/projects) causes a job's `Job.SuspendOptions.EnvironmentKey` to carry `build-container-id`/`helper-id`/`service-ids` belonging to a different job, the docker executor will unconditionally adopt those containers — inspecting them, adopting their mounts/network mode, and starting their services — without any ownership check. This would expose that job's build/helper/service containers and mounted volumes to a different job's shell/script execution, i.e. cross-job container takeover, violating the stated invariant that resumed containers must belong to the same job.

### Likelihood Explanation
Exploitation requires the `SuspendableEnvironments` feature flag enabled and a mechanism by which a foreign `EnvironmentKey` (or its container-ID fields) ends up attached to a different job's `SuspendOptions.EnvironmentKey`. The Runner code itself provides no barrier against this scenario for the docker executor (no RunnerID/SystemID check, no label-based ownership check), unlike the autoscaler executor which does check RunnerID/SystemID. Whether a normal unprivileged pipeline author can actually cause GitLab's backend to hand back a foreign key to their own job is a backend/API question outside this repository, so full end-to-end exploitability by an unprivileged user cannot be confirmed from Runner code alone — but the missing defense-in-depth check inside the docker executor is a concrete, verifiable gap in this codebase.

### Recommendation
In `executors/docker/docker.go`'s `resumeDependencies()`, add the same `RunnerID`/`SystemID` validation used by `executors/internal/autoscaler/executor.go`'s `validateEnvKey` before trusting `envKey.Fields`. Additionally, after `ContainerInspect` for the build/helper/service containers, verify the container's own labels (`com.gitlab.gitlab-runner.job.id`, `.project.id`, `.runner.id`, `.runner.system_id`) match the current `e.Build` before adopting them, rejecting resume with an explicit ownership-mismatch error otherwise.

### Proof of Concept
Add a unit test in `executors/docker/docker_test.go` alongside `TestResumeDependencies`:
```go
func TestResumeDependencies_RejectsForeignContainer(t *testing.T) {
    c := docker.NewMockClient(t)
    e := executorWithMockClient(c)
    require.NoError(t, e.dockerConnector.Connect(t.Context(), common.ExecutorPrepareOptions{}, e))
    e.Config.Docker = &common.DockerConfig{}
    e.Build = &common.Build{Runner: &common.RunnerConfig{RunnerCredentials: common.RunnerCredentials{ID: 7}, SystemID: "sys-1"}}
    e.Build.JobInfo.ProjectID = 42 // "this" job's project
    e.Build.Variables = append(e.Build.Variables, spec.Variable{Key: featureflags.SuspendableEnvironments, Value: "true"})
    // envKey/container IDs belong to a foreign job/project (label project.id=99)
    e.Build.Job.SuspendOptions.EnvironmentKey =
        "7/sys-1/build-container-id=foreign-build-cid&helper-id=foreign-helper-cid"

    foreignBuild := container.InspectResponse{
        ID: "foreign-build-cid",
        HostConfig: &container.HostConfig{},
        Config: &container.Config{Labels: map[string]string{"com.gitlab.gitlab-runner.project.id": "99"}},
    }
    c.On("ContainerInspect", mock.Anything, "foreign-build-cid").Return(foreignBuild, nil).Once()

    err := e.resumeDependencies()
    require.Error(t, err) // expected: ownership-mismatch error once the fix is applied
}
```
Currently this test would need the container-inspect mock chain to complete successfully (no ownership check exists), demonstrating the gap; after the recommended fix, `resumeDependencies()` should return an explicit "container does not belong to this job/project" error instead of adopting the container.
