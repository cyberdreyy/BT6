### Title
Uncaught panic during single-transaction SBF VM execution crashes the unified-scheduler and halts block production - (File: program-runtime/src/vm.rs)

### Summary
The production SVM execution path that runs a transaction's BPF/SBF program (`program-runtime/src/vm.rs::execute`) invokes `vm.execute_program(...)` with no `std::panic::catch_unwind` boundary. Any panic that occurs while executing a single, attacker-submitted transaction inside the VM/interpreter/JIT or a syscall implementation is not isolated to that transaction. It unwinds through the handler thread of the unified scheduler, which — per its own documented design — treats any handler-thread panic as a fatal, whole-scheduler abort condition and then explicitly *re-panics* the caller thread when joining. This is directly analogous to the wasmvm advisory (CWA-2024-008): a bug that causes a native-VM panic during otherwise normal execution of a single message degrades/halts the chain instead of failing gracefully as an instruction error.

### Finding Description
`program-runtime/src/vm.rs::execute` (the function that actually loads accounts, builds the memory mapping, and runs the sBPF program for a transaction instruction) contains no panic guard around VM execution: [1](#0-0) 

The only other place in the codebase that wraps program execution in `catch_unwind` is the **test-only** mock builtin invoker in `program-test`: [2](#0-1) 

There is no equivalent protection in the production path (`program-runtime/src/vm.rs`, `svm/src/transaction_processor.rs::load_and_execute_sanitized_transactions`, or the SVM syscalls in `syscalls/src/lib.rs`). The syscall implementations do contain `.expect()`/`panic!()`/`unreachable!()` call sites (confirmed present in `syscalls/src/lib.rs`), and the underlying `solana_sbpf` interpreter/JIT is an external dependency whose internal invariants (array bounds, arithmetic, `unwrap()`s) are not shielded from the caller. Any panic triggered here — whether from a latent bug in a syscall's bounds/overflow handling, from the JIT/interpreter itself, or from a debug-assertion firing on attacker-crafted account/memory layouts — propagates straight out of `execute()`.

Under the unified scheduler, transaction execution happens on dedicated handler threads. The scheduler explicitly acknowledges that handler-thread panics are not contained per task; they are detected via a `defer!` guard and converted into a fatal `HandlerPanicked` signal that aborts the *entire* scheduler: [3](#0-2) 

When the caller (replay/bank-freezing code) subsequently joins the handler/scheduler threads, the original panic payload is extracted and **re-panicked** in the joining thread: [4](#0-3) 

This is a validated, intentional behavior of the scheduler (there is even a dedicated test asserting the panic is expected to propagate): [5](#0-4) 

So the chain is: single transaction → `execute()` in `vm.rs` panics inside VM/syscall code with no catch_unwind → handler thread panics → scheduler aborts (`SchedulerThreadAborted`) → panic is re-raised in the thread that calls `ensure_join_threads`/`wait_for_completed_scheduler` (replay stage / bank freeze path on both leader and follower validators).

### Impact Explanation
Unlike a normal `InstructionError` (e.g. `ProgramFailedToComplete`, which is how `sol_panic_`/`abort()` guest-program panics are gracefully mapped via `SyscallPanic`/`SyscallAbort`, see `syscalls/src/lib.rs:716-757`), a *native* Rust panic inside the VM/host execution code bypasses all of that graceful error mapping. It is caught nowhere below the scheduler's thread-join boundary, so it tears down the whole scheduler pool for the affected bank and re-panics on the thread driving replay/leader block production. On the leader this can abort in-flight block production for the slot; on followers it forces scheduler pool churn/thread respawn and, per the explicit `panic!(...)` in `ensure_join_threads`, can crash the calling thread itself. A single crafted transaction reaching this code path can therefore degrade or halt block production across the cluster, matching the “panic in VM can slow down block production” bug class from the report. This is not an unsigned fund-movement/CPI-escalation bug, but it satisfies the accepted “transaction-triggered cluster halt” category.

### Likelihood Explanation
The likelihood hinges on whether an attacker can actually trigger a native panic (not a graceful `EbpfError`) inside `vm.execute_program` or a syscall via a single submitted transaction. This is plausible but not proven in the reviewed code: the syscalls do contain `.expect()`/`panic!()`/`unreachable!()` sites, and the interpreter/JIT is a large surface with historically-known integer/index edge cases, but I could not confirm within this scan a specific unguarded panic condition reachable purely from transaction/account/instruction data (as opposed to internal invariants that are already defended against with checked arithmetic and `translate_slice`/`translate_mut` bounds checks visible in `syscalls/src/sysvar.rs`). The structural weakness — the complete absence of a `catch_unwind` boundary around per-transaction VM execution, combined with the scheduler's designed “any handler panic = abort everything + re-panic” behavior — is confirmed and is the root architectural gap that makes any future/latent panic bug in the VM or a syscall immediately cluster-impacting rather than contained to a single failed transaction.

### Recommendation
Wrap the per-transaction VM execution call (`vm.execute_program(...)` in `program-runtime/src/vm.rs::execute`) in `std::panic::catch_unwind(AssertUnwindSafe(...))`, converting any caught panic into a normal `InstructionError` (e.g., `ProgramFailedToComplete`) exactly as `program-test/src/lib.rs` already does for the mock/test invocation path. This ensures a single malformed/malicious transaction can fail with an ordinary transaction error instead of unwinding through the scheduler and being deliberately re-panicked by `unified-scheduler-pool::ensure_join_threads`. Additionally, audit the `.expect()`/`panic!()`/`unreachable!()` sites in `syscalls/src/lib.rs` to confirm none are reachable with attacker-controlled inputs, replacing any that are with proper `Result`-based error returns.

### Proof of Concept
A concrete PoC could not be constructed from static review alone because it requires identifying a specific attacker-reachable panic trigger inside `solana_sbpf`'s interpreter/JIT or a syscall's `.expect()`/`unreachable!()` path (e.g., a crafted account layout, CPI depth, or instruction data that trips an internal invariant). Conceptually, the PoC shape is:
1. Deploy an SBF program engineered to hit whatever native panic condition exists in the VM/syscall layer (not the graceful `sol_panic_`/`abort()` syscalls, which are already handled).
2. Submit one transaction invoking that program.
3. Observe that `execute()` in `program-runtime/src/vm.rs` panics with no `catch_unwind`, the unified-scheduler handler thread panics, `HandlerPanicked` propagates, the scheduler aborts, and `ensure_join_threads`/`join_with_panic_message` re-panics on the replay/leader thread — disrupting block production for that bank instead of returning a normal per-instruction error.
