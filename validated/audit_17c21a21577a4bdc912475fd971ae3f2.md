### Title
Miner-side StackerDB listener double-counts a flipped signer vote across `total_weight_approved` and `total_weight_rejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`docs/signer-flows.md` documents that a signer's local verdict on a block is explicitly designed to flip (`LocallyRejected --> LocallyAccepted : re-evaluated`) when `should_reevaluate_reject_reason` allows it [1](#0-0) . This means the same signer can legitimately broadcast a `Rejected` `BlockResponse` for a given `signer_signature_hash` and later broadcast an `Accepted` response for that exact same hash. The miner-side coordinator that tallies these votes, `StackerDBListener`, tracks acceptance and rejection weight in two independent structures that are never reconciled against each other, so a single signer's weight can be added to *both* `total_weight_approved` and `total_weight_rejected` for the same block.

### Finding Description
`BlockStatus` tracks, per block, a `responded_signers: HashSet<u32>` (keyed by slot id) plus a separate `gathered_signatures: BTreeMap<u32, MessageSignature>` (also keyed by slot id), along with `total_weight_approved`/`total_weight_rejected` counters [2](#0-1) .

On the `Accepted` path, weight is only added if `!block.gathered_signatures.contains_key(&slot_id)`; there is no check of `responded_signers` (the set the rejection path uses) before crediting weight: [3](#0-2) 

On the `Rejected` path, weight is added the first time `block.responded_signers.insert(slot_id)` returns `true`; it never consults `gathered_signatures`: [4](#0-3) 

Because these two code paths use disjoint membership tests (`gathered_signatures` vs. `responded_signers`) instead of a single per-signer "already voted" record shared between both branches, a signer that rejects a block and later (legitimately, per the documented re-evaluation flow) accepts the same block hash gets its weight counted into `total_weight_rejected` once and then again into `total_weight_approved` — the same slot's weight is now represented in both tallies simultaneously. `reset_rejections`, the only place that clears rejection weight, is invoked solely on a proposal timeout, not when an individual signer's vote flips, so the stale rejection weight from before the flip is never removed on its own: [5](#0-4) 

This breaks the coordinator's implicit accounting invariant that `total_weight_approved + total_weight_rejected <= total_weight` (one vote per signer). The consumer of these counters, `SignCoordinator`, uses both fields to decide between three outcomes — reject (`total_weight_rejected + weight_threshold > total_weight`), accept (`total_weight_approved >= weight_threshold`), or keep waiting — and can also derive per-txid exclusion sets from the rejection weight: [6](#0-5) 

Because the tallies are no longer mutually exclusive, a stale/duplicated rejection weight can push `total_weight_rejected` toward the blocking-minority threshold (or a stale acceptance can push `total_weight_approved` toward the signing threshold) using weight from a signer whose current, live vote is actually the opposite — an accounting oversupply directly analogous to JUSD balances that keep growing because repaid tokens are never burned.

### Impact Explanation
This is a miner-side (node) coordinator bug, not a stacks-signer client bug, but it sits squarely in the "aggregated-weight vs verified-accepts" equality class called out in scope: the miner's aggregated `total_weight_approved`/`total_weight_rejected` no longer reflects the verified, current, single vote per signer. A single signer that is permitted by design to flip its vote (`should_reevaluate_reject_reason`) can, without colluding with anyone else, contribute stale weight to the wrong side of the tally, potentially causing the miner to declare `SignersRejected` (excluding transactions or aborting the block) or reach acceptance based on inflated counts that do not correspond to the live, current opinions of `weight_threshold`-worth of distinct signers. This is a liveness/decision-integrity issue triggerable by one slot's message stream (no majority required), matching the report's oversupply-of-uncorrected-state pattern.

### Likelihood Explanation
Likelihood is moderate-to-high in real operation: the signer's own state machine is explicitly designed to move `LocallyRejected -> LocallyAccepted` when a reevaluable reject reason resolves (e.g., after a fresh proposal for the same block content), so this flip is not a fabricated edge case but a normal path exercised by the shipped signer logic. Any signer that rejects a block on first pass (e.g., transient validation issue) and then legitimately accepts it on reevaluation will trigger the double count on the miner's coordinator.

### Recommendation
Track one canonical "signer's current vote" (with weight) per slot id shared by both the `Accepted` and `Rejected` branches, so that when a signer's vote changes, the previous contribution is subtracted from the old tally before the new one is added to the other tally — i.e., make `total_weight_approved`/`total_weight_rejected` mutually exclusive per slot id rather than independently additive via two separate membership sets (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Miner submits a block proposal with hash `H`; `StackerDBListenerComms::insert_block` initializes `BlockStatus` with zeroed weights [7](#0-6) .
2. Signer `S` (slot `k`, weight `w`) first sends `BlockResponse::Rejected` for `H` (e.g., a transient validation failure). The listener adds `w` to `total_weight_rejected` and marks slot `k` in `responded_signers` [8](#0-7) .
3. `S`'s local signer state later reevaluates the same block (`should_reevaluate_reject_reason` returns true per the documented flip path) and `S` now sends `BlockResponse::Accepted` for the *same* `H`.
4. The listener's `Accepted` branch checks only `gathered_signatures.contains_key(&k)` (false, since `S` never sent an acceptance before) and adds `w` again, this time to `total_weight_approved` [9](#0-8) .
5. Now `total_weight_approved` and `total_weight_rejected` both include `S`'s weight `w` for block `H`, even though `S` currently holds only one live opinion (accept). If other signers' weight pushes `total_weight_rejected + weight_threshold > total_weight` before this flip is accounted for anywhere, `SignCoordinator::run` will return `SignersRejected` using a tally that double-counts `S`, even though `S`'s current, live vote is acceptance [10](#0-9) .

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
