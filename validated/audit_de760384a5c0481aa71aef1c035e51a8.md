### Title
Overwritten `lastWithdrawRequest` epoch pointer orphans loss-adjusted receipts, letting them be re-claimed at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The kernel bug is a use-after-free: `ops_init()` frees `data` on failure but leaves a stale pointer in `net->gen`, which the later teardown path (`nfqnl_nf_hook_drop`) dereferences. The analog in `IdleCreditVault` is the single-slot epoch "pointer" `lastWithdrawRequest[_user]`. When an epoch ends with a realized loss, `collectWithdrawFunds` zeroes `pendingWithdraws` (releases the borrower's obligation) and stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]`. The only way back to that released/haircut bucket is `lastWithdrawRequest` — and `requestWithdraw` overwrites it on every new request. A user who re-requests before claiming permanently orphans the loss-adjusted bookkeeping entry, and `_claimFundedWithdrawRequest` then pays the orphaned basis again at full par.

### Finding Description

- On a loss-adjusted `stopEpochWithDuration`, `collectWithdrawFunds` sets `pendingWithdraws = 0` and records `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice`, i.e., the borrower funds only `pendingToFund < pendingBasis` [1](#0-0) .
- The user's receipt, however, remains fully valued: `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][lossEpoch]` still hold the pre-haircut amounts, and the strategy-token receipt is unburned [2](#0-1) .
- On `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` dereferences exactly one epoch: `lossEpoch = lastWithdrawRequest[_user]`. If the user made a newer request in epoch N+1, `lastWithdrawRequest` points at N+1, `lossRecoveryPriceByEpoch[N+1] == 0`, and the function returns 0 without clearing epoch N [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still includes the loss-adjusted epoch-N amount — at 1:1 par, and clears `lastWithdrawRequest` [4](#0-3) . The orphaned `withdrawsRequestsByEpoch[_user][N]` entry is never consulted again; the epoch-N haircut is silently dropped.

This is the same structural defect as the CVE: a single mutable reference (`net->gen` ptr / `lastWithdrawRequest`) is the only handle to state that the protocol already considered released (`kfree(data)` / `pendingWithdraws = 0` + funded haircut amount), and the cleanup/claim path dereferences the wrong target.

### Impact Explanation

Direct theft of funded withdraw proceeds. The strategy only received `pendingToFund` (post-haircut) underlying for epoch N receipts, but pays the attacker the full pre-haircut basis. The stolen amount is the attacker's share of `pendingLoss = _lossAmount * pendingBasis / totalBasis` from `previewLossAdjustedWithdrawFunds` [5](#0-4) . Because the strategy pays out of its own underlying balance, the loss falls on other funded claimants, who then find the strategy undercollateralized — a broken solvency/fair-payout invariant, quantifiable up to the full `pendingLoss` share of the user's epoch-N receipt.

### Likelihood Explanation

Requirements: an epoch that ends via `stopEpochWithDuration` with `_lossAmount > 0` while the attacker holds a pending receipt (an unprivileged KYC-passing lender can simply request withdraw twice across consecutive epochs — the code comments even acknowledge "requests another withdraw" as a normal flow [6](#0-5) ). No existing guard stops it: `_transferFundedClaim` only protects `defaultRecoveryReserve`, not peer claims [7](#0-6) . Uncertain: whether this is already a known/acknowledged issue; the per-epoch bookkeeping looks recently added and may have been audited.

### Recommendation

Track all epochs with a nonzero `lossRecoveryPriceByEpoch` receipt per user (e.g., iterate pending per-epoch entries or keep an epoch list) instead of the single `lastWithdrawRequest` slot, or subtract loss-adjusted amounts from `withdrawsRequests[_user]` in `collectWithdrawFunds` so the funded path cannot re-pay them at par.

### Proof of Concept

```solidity
// Foundry fork PoC (sketch)
// 1. LP deposits; manager startEpoch; user requestWithdraw in epoch N.
// 2. Borrower repays short by L; manager calls stopEpochWithDuration(L)
//    -> collectWithdrawFunds(pendingToFund < basis), lossRecoveryPriceByEpoch[N] set.
// 3. user calls requestWithdraw again in epoch N+1 -> lastWithdrawRequest = N+1.
// 4. Epoch N+1 stops normally, fully funded.
// 5. user claimWithdrawRequest:
//      _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N+1] == 0 -> skips N.
//      _claimFundedWithdrawRequest pays withdrawsRequests[user] (N + N+1, unhaircut) at par.
// assert: user received epoch-N basis in full; strategy balance now < sum of
//         remaining funded claims; other claimant's claimWithdrawRequest reverts
//         on insufficient balance.
```

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
