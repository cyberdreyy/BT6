### Title
APR0 withdraw receipt permanently reverts `stopEpoch` once APR is raised, freezing all vault funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0` (IdleCreditVault.sol:505-508). Any unprivileged lender can leave a dust APR0 withdraw receipt in the bucket; when the manager later sets a non-zero APR for the next epoch, every subsequent `stopEpoch` call reverts, so the epoch can never close and no funds can be recalled or withdrawn. The bucket can only be cleared by a `stopEpoch` that runs at `unscaledApr == 0` or by the default-claim path, so the freeze persists until the manager is forced to drop APR to zero (or a default occurs).

### Finding Description
In `IdleCreditVault`, a user-facing `requestWithdraw` while `unscaledApr == 0` routes to `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` (IdleCreditVault.sol:567-577). At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`; when `_principal = apr0TotalPrincipal` is non-zero the function enforces `if (unscaledApr != 0) revert NotAllowed()` (lines 505-508). The only places that reduce `apr0TotalPrincipal` are:

- line 540: `apr0TotalPrincipal = 0` — reached only *after* the revert check, inside the same call, so it requires a `stopEpoch` executed while APR is still zero.
- `_clearWithdrawClaimForEpoch` (lines 822-828) — reachable only through the defaulted/post-default claim path.

`_settleApr0` (lines 545-565) moves user principal to `settledPrincipal` but never decrements `apr0TotalPrincipal`, so neither the victim user claiming nor time passing removes the poisoned bucket.

Attack sequence (APR0 mode, epoch N):
1. Attacker (KYC-passing lender) deposits a dust amount and calls `requestWithdraw` while `unscaledApr == 0`. `apr0TotalPrincipal` becomes `dust > 0`.
2. Epoch N's `stopEpoch` runs at APR 0 — but only if the request survives into epoch N+1's bucket. The attacker requests *after* `startEpoch` of epoch N+1 during the buffer while `unscaledApr` is still 0, or the manager legitimately sets a non-zero APR for epoch N+1 via `setAprsWithBuffer`/`setAprs` at epoch start.
3. Once `unscaledApr != 0` and `apr0TotalPrincipal != 0`, every `stopEpoch`/`stopEpochWithDuration` call reverts with `NotAllowed`. `epochNumber` never increments, `epochEndDate` stays in the past, `requestWithdraw`/`claimWithdrawRequest` funded claims remain gated by `epochNumber <= lastWithdrawRequest[_user]` (line 326), and borrower repayments cannot be booked.

The guard at lines 506-508 was presumably meant to assert that an APR0 bucket only exists in a zero-APR epoch, but it converts a legitimate manager APR change into a user-triggerable liveness failure.

### Impact Explanation
Broken invariant: epoch state machine liveness / solvency of the withdraw pipeline. With `stopEpoch` permanently reverting, all lender principal and accrued interest in the vault is frozen — deposits are already paused while the epoch runs, withdraws cannot be fulfilled because `epochNumber` never advances, and the borrower cannot be moved into the normal default/recovery flow through `stopEpochWithDuration`. Recovery requires the honest manager to set `unscaledApr` back to 0 for an entire epoch (forcing the pool to run interest-free) just to clear a dust-sized attacker's receipt, i.e. temporary freezing of the entire TVL plus forced forfeiture of one epoch's yield. Cost to the attacker is one dust deposit plus gas.

### Likelihood Explanation
The attacker only needs to pass the same KYC/whitelist check as any lender (`isWalletAllowed`) and hold a minimal tranche position. No privileged collusion is needed: honest managers routinely change APR between epochs, so the trigger condition (`apr0TotalPrincipal != 0` when APR becomes non-zero) is reached by ordinary sequencing. The freeze is deterministic once triggered — no race, no external dependency.

### Recommendation
- Do not revert on the `unscaledApr != 0` + non-zero APR0 bucket combination. Either settle the stale APR0 bucket at the stored `apr0RateByEpoch`/`apr0TotalPrincipal` basis (zero interest is the correct outcome when APR is no longer 0), or clear `apr0TotalPrincipal` when the bucket's epoch is superseded.
- Alternatively, tie APR0 receipts to their request epoch: in `prepareStopEpochWithApr0`, only apply the APR0 split when the open principal's `principalEpoch` matches the epoch that ran at APR 0, and zero the bucket unconditionally at each `stopEpoch`.
- Add a regression test: APR0 request → manager sets non-zero APR → `stopEpoch` must succeed and the APR0 claim must remain payable.

### Proof of Concept
Foundry fork test sketch (concrete environment follows `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testApr0DustBlocksStopEpochAfterAprIncrease() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0); // APR = 0 epoch

    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 1 * ONE_SCALE, true);   // dust deposit, passes KYC

    _startEpochAndCheckPrices(0);
    // stop epoch 0 at APR 0
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // attacker files a dust APR0 withdraw while unscaledApr == 0
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(attacker), address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // honest manager sets a normal APR for epoch 1 and starts it
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialApr, initialApr);
    _startEpochAndCheckPrices(1);

    // epoch 1 ends: borrower repays, but stopEpoch always reverts
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + amount);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // no user action clears it: settledPrincipal moves but apr0TotalPrincipal stays
    // -> funds frozen until manager is forced back to APR 0 for a whole epoch
}
```

The revert condition and the absence of any non-default clearing path for `apr0TotalPrincipal` are verified directly in `IdleCreditVault.sol`.
