## Title
Missing MessageId uniqueness check in gateway trigger handler allows cross-user response hijacking - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
The Caviar bug class is a "shared mutable slot overwritten by an unprivileged/attacker-controlled call before the rightful owner's response completes." The chainlink gateway's legacy `web_api_trigger` handling contains an analogous pattern: the `MessageId` used as the key into the shared `savedCallbacks` map is fully controlled by the unprivileged HTTP client hitting the gateway, and the handler never checks for a collision before overwriting the slot, unlike the sibling `OutgoingConnectorHandler` which explicitly guards against this.

## Finding Description
Any external, unauthenticated (pre-signature-check) or authenticated-but-unprivileged client can `POST` a JSON-RPC request to the internet-facing gateway HTTP endpoint. The request `ID` becomes the gateway `MessageId` with no server-side randomness or per-sender namespacing: [1](#0-0) 

The gateway's `ProcessRequest` only bounds the length of the ID (`<=200` chars) before dispatching to the handler: [2](#0-1) 

In `HandleLegacyUserMessage`, the handler stores the caller's callback directly into the shared `savedCallbacks` map keyed by this attacker-controlled `MessageId`, with **no existence/duplicate check**: [3](#0-2) 

When a DON node later responds with that same `MessageId`, `handleWebAPITriggerMessage` looks up and deletes whatever callback currently occupies that slot and delivers the node's response to it — "first" node response wins, and it is delivered to whichever caller most recently claimed the slot: [4](#0-3) 

This is the exact structural analog of the Caviar bug: a shared resource (the ETH refund slot / here, the response callback slot) keyed by data that an unprivileged actor controls, mutated without a compare-and-swap/uniqueness guard, so a second (attacker) request can clobber the first (victim) request's claim on the slot before it resolves — resulting in cross-user response confusion. This is confirmed by contrast with the sibling `OutgoingConnectorHandler`, which handles the analogous scenario (gateway responses matched by `MessageId`) correctly by rejecting duplicates: [5](#0-4) 

`api.Message.Validate()` only constrains ID length/format, not uniqueness across in-flight requests: [6](#0-5) 

## Impact Explanation
If an attacker can predict or observe a victim's in-flight `MessageId` (e.g., sequential/predictable IDs generated by a legitimate integrator, or by racing a flood of guesses during the request's outstanding window — bounded by `MaxAllowedMessageAgeSec`/DON round-trip time), the attacker can submit a second trigger request with the identical `MessageId`. This overwrites the victim's entry in `savedCallbacks`, so the DON's legitimate response to the victim is instead delivered to the attacker's HTTP connection (cross-user response confusion / information disclosure of another tenant's workflow trigger response), while the victim's original HTTP request instead hangs until timeout or receives the attacker's manufactured response is not directly deliverable back but the victim's callback is silently discarded (denial of service for the victim). Given `web_api_trigger` payloads can contain business-sensitive trigger/workflow data, this is a concrete unprivileged-actor confidentiality/integrity issue on the internet-facing gateway.

## Likelihood Explanation
Exploitability depends on the attacker's ability to predict or observe another party's `MessageId` within the outstanding request window, and on the gateway operator's client population not being uniquely trusted (the gateway is explicitly designed to be internet/DON-facing for external triggers). Since there is zero server-side entropy or uniqueness enforcement on `MessageId`, and the parallel `OutgoingConnectorHandler` code path demonstrates the project is aware this needs a check (`"duplicate message received for ID"`), the missing guard in the trigger-handler path is a genuine, non-speculative gap rather than a defense-in-depth nicety.

## Recommendation
Add the same duplicate-key check used in `OutgoingConnectorHandler.responses.new()` to `HandleLegacyUserMessage` (and any other handlers keying `savedCallbacks` off caller-supplied `MessageId`), rejecting the request (or generating a server-side unique correlation ID) if the `MessageId` is already in-flight, rather than silently overwriting the existing callback.

## Proof of Concept
1. Victim sends a signed `web_api_trigger` request to the gateway with `id = "X"`; `HandleLegacyUserMessage` stores victim's callback at `savedCallbacks["X"]` and forwards the request to DON members (`core/services/gateway/handlers/capabilities/handler.go:411-419`).
2. Before the DON responds, an attacker sends their own signed `web_api_trigger` request also using `id = "X"`. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with the attacker's callback (no duplicate check present, contrast with `outgoing_connector_handler.go:452-455`).
3. When a DON node responds with `MessageId = "X"` (intended for the victim's request), `handleWebAPITriggerMessage` pulls the current occupant of `savedCallbacks["X"]` — the attacker's callback — and delivers the victim's node response to the attacker's HTTP connection.

	// decode
	jsonRequest, err := jsonrpc2.DecodeRequest[json.RawMessage](rawRequest, auth)
	if err != nil {
		return newError("", api.UserMessageParseError, err.Error())
	}
	msg, err := g.codec.DecodeJSONRequest(jsonRequest)
	if err != nil {
		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
	}
	if len(jsonRequest.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return newError(jsonRequest.ID, api.UserMessageParseError, "request ID is too long: "+strconv.Itoa(len(jsonRequest.ID))+". max is 200 characters")
	}
	var isLegacyRequest = false
	var h handlers.Handler
	var handlerKey string
	if msg == nil || msg.Body.DonId == "" {
		serviceName := jsonRequest.ServiceName()
		if handler, ok := g.serviceToMultiHandler[serviceName]; ok {
			h = handler
			handlerKey = serviceName
		} else if donID, ok := g.serviceNameToDonID[serviceName]; ok {
			// Fallback to legacy service name -> DON ID mapping
			if handler, ok := g.handlers[donID]; ok {
				h = handler
				handlerKey = donID
			}
		}
		if h == nil {
			return newError(jsonRequest.ID, api.HandlerError, "Service name not found: "+serviceName)
		}
	} else {
		// Legacy request with DON ID - validate and fetch handler
		isLegacyRequest = true
		if err = msg.Validate(); err != nil {
			return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
		}
		handlerKey = msg.Body.DonId
		var ok bool
		h, ok = g.handlers[handlerKey]
		if !ok {
			return newError(jsonRequest.ID, api.UnsupportedDONIdError, "Unsupported DON ID: "+handlerKey)

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (r *responses) new(id string) (chan *api.Message, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	_, ok := r.chs[id]
	if ok {
		return nil, fmt.Errorf("already have response for id: %s", id)
	}

	// Buffered so we don't wait if sending
	ch := make(chan *api.Message, 1)
	r.chs[id] = ch
	return ch, nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
