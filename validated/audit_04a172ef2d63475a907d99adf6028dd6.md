### Title
Griefing freeze of `stopEpoch` by draining the programmable borrower's ERC4626 vault liquidity - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` is on the critical path of `IdleCDOEpochVariant.stopEpoch`. When on-hand tokens cannot cover `_amountRequired`, it calls `vault.withdraw(shortfall, ...)` inside a `try/catch` that still reverts with `StopEpochVaultLiquidityUnavailable` on any failure [1](#0-0) . An unprivileged user of the external ERC4626 vault (the deployed MetaMorpho-style vault, where any EOA can deposit/withdraw/borrow) can drain the vault's liquid assets at the moment an epoch stop is attempted, making `vault.withdraw` revert and therefore making `stopEpoch` revert. This is the analog of CVE-2015-8270: a crash (forced revert) on a dereference of attacker-influenceable external state, here turned into a freezing-of-funds primitive rather than a mere process crash.

### Finding Description
The guard only protects the *insolvency* case: `if (shortfall > _currentVaultAssets()) return true;` lets IdleCDO take the default path when the vault position cannot economically cover the shortfall [2](#0-1) . But `_currentVaultAssets()` values the position via `vault.convertToAssets(shares)` — the *mark-to-market* value — while `vault.withdraw` requires *idle liquidity* in the vault [3](#0-2) . A vault that is fully lent out (or whose liquidity was just withdrawn/borrowed by the attacker) has convertToAssets coverage but zero withdrawable liquidity. `vault.withdraw` reverts, the `catch` reverts `StopEpochVaultLiquidityUnavailable`, and the whole `stopEpoch` transaction fails. Since `stopEpoch` is the only transition out of a running epoch, `requestWithdraw` claims and `claimWithdrawRequest`/`collectWithdrawFunds` payouts for the epoch cannot settle while it is blocked.

### Impact Explanation
Temporary freezing of all lender funds in the running epoch: no stop → no loss/pricing settlement → queued withdraw requests cannot be claimed. The attacker is unprivileged (any vault depositor/borrower, not the honest borrower/manager/owner roles). Loss is the time-value of frozen principal plus forced missed exits; the freeze persists as long as the attacker can keep vault liquidity drained (repeatable each time a stop is retried, e.g., via flash-borrowed vault debt repaid only when liquidity returns). Broken invariant: epoch liveness — the epoch state machine can be stalled by external third-party state that neither manager nor guardian controls quickly (the owner-trusted `rescueTokens`/`emergencyExitVault` escape exists but `emergencyExitVault`'s `vault.redeem` fails on the same missing liquidity [4](#0-3) ).

### Likelihood Explanation
Requires an ERC4626 vault whose idle liquidity can be fully consumed by an unprivileged user (typical for lending vaults like MetaMorpho: high utilization states occur naturally; an attacker can also flash-drive utilization). No privilege, no KYC, no vault cooperation needed — only the ability to hold vault borrowing/withdrawal demand across the stop attempt. The revert path is explicitly coded (`catch { revert StopEpochVaultLiquidityUnavailable(); }`), so it triggers deterministically whenever liquidity < shortfall ≤ convertToAssets(shares).

### Recommendation
Distinguish liquidity failure from solvency failure: when `vault.withdraw` reverts, fall back to a redeem/max-withdraw of whatever liquidity exists (`vault.maxWithdraw`/`maxRedeem` clamp) instead of reverting, and let the residual shortfall flow into the existing default/shortfall handling in IdleCDO. Alternatively, wrap the hook call in IdleCDO so a hook revert does not permanently gate the epoch transition, or allow `stopEpochWithDuration(_lossAmount)` to proceed on the defaulted path without requiring vault liquidity.

```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test — mainnet fork with the deployed MetaMorpho vault used by ProgrammableBorrower.
// Attacker = ordinary vault user (no role in idle-tranches).
function testGriefStopEpochByDrainingVaultLiquidity() public {
    uint256 amount = 10_000 * oneScale;

    // Honest setup: lender deposits, manager starts epoch, borrower draws some funds.
    idleCDO.depositAA(amount);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(5_000 * oneScale);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // --- ATTACK: unprivileged ERC4626 vault user drains vault idle liquidity ---
    // e.g., Morpho vault: borrow all idle assets (or withdraw everything as a large LP),
    // leaving vault.maxWithdraw(address(programmableBorrower)) == 0 while
    // vault.convertToAssets(shares) still > 0.
    address attacker = makeAddr("attacker");
    _drainMorphoVaultLiquidity(attacker); // legitimate vault borrow, no idle-tranches role

    // onHand < amountRequired  =>  shortfall <= convertToAssets(shares)  =>  guard passes
    // but vault.withdraw(shortfall,...) reverts -> StopEpochVaultLiquidityUnavailable
    vm.prank(manager);
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);   // epoch cannot stop -> withdraw requests stay unpayable

    // Freeze persists across retries while vault liquidity is held drained:
    vm.warp(block.timestamp + 1 days);
    vm.prank(manager);
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Lender requestWithdraw claims for this epoch cannot settle (epoch still running).
    assertTrue(cdoEpoch.epochEndDate() != 0);
}
```
