### Title
Reject-then-Accept from the same signer double-counts weight in both `total_weight_rejected` and `total_weight_approved`, letting a stale rejection wedge a quorum-reached block as globally rejected - (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
In `StackerDBListener::run`, the `BlockResponse::Rejected` handler only touches `block.responded_signers`, never `block.gathered_signatures`; the `BlockResponse::Accepted` handler only checks `gathered_signatures` before crediting `total_weight_approved`. A signer that first rejects and later accepts the same `signer_signature_hash` therefore has its weight added to `total_weight_approved` without ever being subtracted from `total_weight_rejected`, breaking the accounting invariant that a signer's weight should count toward at most one side of the tally.

### Finding Description
The invariant that should hold is: `total_weight_rejected == Σ weight of signers whose *latest* response for H is Rejected`, and symmetrically for `total_weight_approved`. This is enforced correctly in one direction but not the other:

- Accept-then-Reject: on Accept, `block.responded_signers.insert(slot_id)` is set and `gathered_signatures.insert(slot_id, signature)` is set [1](#0-0) . A later Reject for the same slot hits `if block.responded_signers.insert(slot_id)` which returns `false` (already present), so the whole reject-accounting body — including `total_weight_rejected += weight` — is skipped [2](#0-1) . This direction is safe.
- Reject-then-Accept: on Reject, only `block.responded_signers.insert(slot_id)` is touched; `gathered_signatures` is never written [2](#0-1) . When the Accept later arrives for the same slot, the guard is `if !block.gathered_signatures.contains_key(&slot_id)` [3](#0-2) , which is still true (rejection never populated it), so `total_weight_approved` is incremented too — with `total_weight_rejected` never decremented. The same weight `w` is now counted in both totals simultaneously.

This isn't a hypothetical race: the codebase explicitly documents and tests that a signer legitimately transitions from Rejected to Accepted for the *same* `signer_signature_hash` when a block is re-proposed (e.g., parent not yet processed) — see `should_reevaluate_block`/`handle_block_proposal` in the signer [4](#0-3)  and the dedicated `reject_then_accept` test in `signerdb.rs`, which correctly clears the stale rejection when a signature is later recorded [5](#0-4) . The signer's own local DB retracts stale rejections on accept; the miner-side `stackerdb_listener.rs` aggregation does not — an inconsistency between the two.

Downstream, `SignerCoordinator::get_block_status` checks the reject condition before the accept condition:
```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    return Err(NakamotoNodeError::SignersRejected { .. });
} else if block_status.total_weight_approved >= self.weight_threshold {
    return Ok(...);
}
``` [6](#0-5) 
Because the reject branch is evaluated first, a permanently-inflated `total_weight_rejected` (from weight that has actually flipped to Accept) can push the reject predicate over the line even while `total_weight_approved` simultaneously reaches quorum, causing the miner to discard a validly-quorum'd block as `SignersRejected`.

The attacker model explicitly allows running one's own signer with its own weight and gossiping StackerDB messages it consumes. An attacker who wins a miner slot and also operates their own signer (their own weight, no privilege needed) can deterministically send `Rejected` for H followed by `Accepted` for H from their own signer key — this requires no network-timing luck, replay of anyone else's key, or majority collusion. Each time they do this, their own weight is durably double-booked into `total_weight_rejected`, permanently biasing the aggregate toward `SignersRejected` for that block hash for the remainder of that proposal's lifetime (rejections are only cleared wholesale on `reset_rejections`, which zeroes the counter rather than fixing the double-count root cause) [7](#0-6) .

### Impact Explanation
This is a liveness break on the miner/node side: a block that legitimately reaches signature quorum (`total_weight_approved >= weight_threshold`) can still be treated by `SignerCoordinator::get_block_status` as globally rejected (`NakamotoNodeError::SignersRejected`) because stale, superseded rejection weight from a signer who has since accepted is never retracted from `total_weight_rejected`. This wedges valid, quorum-reached blocks and is repeatable — the attacker's own signer weight is durably counted twice for every block proposal round in which they choose to reject-then-accept.

### Likelihood Explanation
Preconditions are minimal and fully within the described attacker capability: winning one miner slot (to control the proposal) and running one signer under their own key/weight (explicitly permitted). No majority-signer collusion, no other signer's key, no auth token, and no local host access are required. The reject-then-accept transition for the same `signer_signature_hash` is a normal, supported code path (re-proposal of the same block reuses the same header/hash across the coordinator's resend loop in `propose_block`) [8](#0-7) , so the attacker doesn't even need to fabricate anything unusual — they trigger it purely through the ordinary message sequence their own signer emits.

### Recommendation
In the `BlockResponse::Rejected` handler, when a slot transitions from a prior state, retract any weight it previously contributed to the opposite bucket, and in the `BlockResponse::Accepted` handler, symmetrically retract stale rejected weight when a slot is newly recorded into `gathered_signatures`. Concretely: track each slot's current disposition (Accepted/Rejected) in a single map rather than a separate `HashSet` + `BTreeMap`, and when overwriting a slot's disposition, subtract the old weight from its old bucket before adding to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect each signer's *latest* response only.

### Proof of Concept
```rust
// stacks-node/src/nakamoto_node/stackerdb_listener.rs (test module)
#[test]
fn reject_then_accept_double_counts_weight() {
    use std::collections::{BTreeMap, HashMap, HashSet};

    let slot_id = 0u32;
    let weight = 100u32;

    let mut block = BlockStatus {
        responded_signers: HashSet::new(),
        gathered_signatures: BTreeMap::new(),
        total_weight_approved: 0,
        total_weight_rejected: 0,
        failed_txids: HashMap::new(),
    };

    // --- Reject branch logic (mirrors production code) ---
    if block.responded_signers.insert(slot_id) {
        block.total_weight_rejected = block.total_weight_rejected.saturating_add(weight);
    }
    assert_eq!(block.total_weight_rejected, weight);
    assert_eq!(block.total_weight_approved, 0);

    // --- Accept branch logic (mirrors production code) for the SAME slot/H ---
    if !block.gathered_signatures.contains_key(&slot_id) {
        block.total_weight_approved = block.total_weight_approved.saturating_add(weight);
    }
    block.gathered_signatures.insert(slot_id, Default::default());
    block.responded_signers.insert(slot_id);

    // BUG: weight is counted on both sides simultaneously.
    assert_eq!(block.total_weight_rejected, weight, "stale reject weight never retracted");
    assert_eq!(block.total_weight_approved, weight, "accept weight added despite prior reject");

    // Demonstrates the wedge condition used by SignerCoordinator::get_block_status:
    let total_weight = weight; // only this one signer in this toy example
    let weight_threshold = weight; // 100% threshold for simplicity
    let reject_wedge = block.total_weight_rejected.saturating_add(weight_threshold) > total_weight;
    let accept_ok = block.total_weight_approved >= weight_threshold;
    assert!(reject_wedge && accept_ok, "both predicates true simultaneously; reject checked first wins");
}
```
