### Title
Unchecked mid-epoch deposit lets fee-on-transfer shortfalls mint full tranche shares and overfund the borrower - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` does not measure the number of underlying tokens actually received. It mints tranche shares and strategy tokens for the requested `_amount`, then transfers the full `_amount` to the borrower even when `transferFrom` delivers less. The regular `_deposit` path correctly mints from the post-transfer balance delta, so the epoch deposit path has an inconsistent and exploitable missing received-token check. [1](#0-0) [2](#0-1) 

### Finding Description
During a running fixed-APR epoch, `depositDuringEpoch` is callable by a wallet-allowed lender when mid-epoch deposits are enabled, AYS is inactive, and the vault is not programmable. After `_transferUnderlyingsFrom(msg.sender, address(this), _amount)`, the code never compares the pre-transfer and post-transfer CDO balances. [3](#0-2) 

All subsequent accounting uses the requested `_amount`: minted tranche shares are calculated from `_amount + trancheInterest`, `_mintShares` records `_amount`, `expectedEpochInterest` increases by interest on `_amount`, the credit vault mints `_amount` strategy tokens, and `_amount` is transferred to the borrower. If the underlying transfers only `received = _amount - shortfall`, the CDO immediately sends `shortfall` tokens belonging to existing depositors to the borrower while creating claims for the full requested deposit. [4](#0-3) 

The normal credit-vault `_deposit` path demonstrates the intended invariant: it snapshots `_preBal`, transfers the underlying, and mints only against `_contractTokenBalance(_token) - _preBal`. That protection is absent from `depositDuringEpoch`. [5](#0-4) 

### Impact Explanation
A fee-on-transfer, rebasing, or otherwise non-exact-transfer underlying causes each affected mid-epoch deposit to create `shortfall = _amount - received` unbacked principal. The attacker receives tranche shares priced as though they supplied `_amount`, while the borrower receives `_amount`; the missing balance is taken from the vault’s existing assets. The attacker can later request or claim withdrawal against the inflated tranche position, directly transferring the shortfall and associated over-credited interest from honest tranche holders to the attacker. The loss is at least the aggregate transfer shortfall and is proportional to the deposited amount. [6](#0-5) 

The existing donation skimming does not prevent this because it only sweeps the balance before the attacker’s transfer and does not verify the amount subsequently received. Epoch gating, KYC, tranche checks, and strategy-token minting also do not enforce a one-unit-received/one-unit-credited invariant. [7](#0-6) 

### Likelihood Explanation
Exploitation requires the configured underlying to return less than the requested amount from `transferFrom`, so ordinary exact-transfer assets are not affected. Where a vault is configured with a fee-on-transfer or non-exact-transfer asset, any KYC-passing lender can trigger the issue during an eligible running epoch without privileged access. The required state is ordinary operation: a nonzero tranche supply, running epoch, deposits during epoch enabled, AYS inactive, and non-programmable borrower mode. [8](#0-7) 

### Recommendation
Measure the actual received amount and use it for every subsequent operation:

```solidity
uint256 preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 received = _contractTokenBalance(token) - preBal;
require(received == _amount, "unexpected token amount");
```

If non-exact-transfer assets must be supported rather than rejected, replace `_amount` with `received` in the interest calculation, mint calculation, `_mintShares` principal parameter, `mintStrategyTokens`, and borrower transfer. The latter approach changes depositor economics and should be explicitly specified; strict equality is simpler and matches the existing fair-mint invariant. [4](#0-3) 

### Proof of Concept
A Foundry fork test can deploy or configure the epoch vault with a fork-compatible fee-on-transfer ERC20 and execute the following sequence:

```solidity
// Vault state: fixed-APR, non-programmable, AYS inactive,
// epoch running, depositDuringEpoch enabled, existing AA supply.
uint256 amount = 1_000_000e6;
uint256 feeBps = 100; // 1%
uint256 expectedReceived = amount - amount * feeBps / 10_000;

feeToken.approve(address(cdoEpoch), amount);
uint256 cdoBalBefore = feeToken.balanceOf(address(cdoEpoch));
uint256 borrowerBefore = feeToken.balanceOf(borrower);

uint256 minted = cdoEpoch.depositDuringEpoch(amount, AAtranche);

uint256 actualReceived = feeToken.balanceOf(address(cdoEpoch)) - cdoBalBefore;
uint256 borrowerReceived = feeToken.balanceOf(borrower) - borrowerBefore;

assertEq(actualReceived, expectedReceived);
assertEq(borrowerReceived, amount);
assertGt(minted, 0);
assertEq(strategy.balanceOf(address(cdoEpoch)), strategyBefore + amount);
```

The invariant violation is visible in one transaction: the CDO receives `expectedReceived`, but mints shares and strategy-token backing for `amount` and sends `amount` to the borrower. Requesting withdrawal for the attacker’s minted tranche balance then demonstrates conversion of the unbacked credit into a payout funded by pre-existing depositors. [9](#0-8)

```text
  function depositDuringEpoch(uint256 _amount, address _tranche) external virtual returns (uint256 _minted) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == BBTranche && !isBBDepositEnabled) ||
      isDepositDuringEpochDisabled ||
      skipDefaultCheck ||
      // programmable borrowers use APR=0 so mid-epoch deposits would dilute existing depositors
      isProgrammableBorrower ||
      // check if AYS is active as we don't support deposits during epoch in that case
      isAYSActive ||
      // check if epoch is still running even if not manually stopped yet
      !isEpochRunning || block.timestamp >= epochEndDate ||
      !isWalletAllowed(msg.sender)
    );

    if (_amount == 0) {
      return _minted;
    }

    uint256 _trancheTotSupply = _trancheSupply(_tranche);
    // Avoid pricing discontinuities for the first mid-epoch deposit in a tranche
    _checkNotAllowed(_trancheTotSupply == 0);

    _skimDonatedAssets();
    // Check that limit is not exceeded after removing skimmable raw donations.
    _guarded(_amount);
    _updateAccounting();

    // Get underlyings from user
    _transferUnderlyingsFrom(msg.sender, address(this), _amount);

    // interest for the remaining epoch plus the full buffer period
    // NOTE: _calcInterest already gives full‑epoch + full‑buffer interest for the whole epoch
    //   So when a user joins mid‑epoch, we take the fraction of that full‑period interest 
    //   that matches the time they actually remain plus the entire buffer
    uint256 buffer = bufferPeriod;
    uint256 remaining = epochEndDate - block.timestamp;
    uint256 interest = _calcInterest(_amount) *
      // the time the depositor actually participates (remaining epoch + full buffer)
      (remaining + buffer) /
      // the total time baked into the scaled APR (epoch + buffer).
      (epochDuration + buffer);

    uint256 expectedInt = expectedEpochInterest;
    uint256 pendingFees = pendingWithdrawFees;
    uint256 trancheExpected;
    // existing holders' share of net expected interest for the epoch (pre-deposit)
    // (exclude pendingWithdrawFees since they go to fee receivers, not tranche holders)
    if (expectedInt > pendingFees) {
      trancheExpected = _calcTrancheInterestShare(
        _netGainAfterFees(expectedInt - pendingFees, _calculateManagementFee(lastNAVAA + lastNAVBB, remaining)),
        _tranche
      );
    }
    // interest this deposit will earn for the tranche over the remaining time (net of fees)
    uint256 trancheInterest = _calcTrancheInterestShare(
      _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)),
      _tranche
    );
    // pre-deposit expected final NAV for existing holders.
    // This won't ever be zero as we checked _trancheTotSupply and we seed initial NAV at tranche creation
    uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;

    // mint at a discounted price so depositor gets principal + its prorated interest at epoch end
    // A mid‑epoch depositor should get _amount + trancheInterest at epoch end.
    // So they need minted = (amount + trancheInterest) / priceEnd.
    // priceEnd = expectedFinal / _trancheTotSupply
    // so minted = (amount + trancheInterest) * _trancheTotSupply / expectedFinal
    _minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
    _mintShares(_tranche, msg.sender, _minted, _amount);

    // update expected epoch interest
    expectedEpochInterest += interest;
    // mint strategy tokens to this contract
    IdleCreditVault(strategy).mintStrategyTokens(_amount);
    // transfer underlyings to the borrower
    _transferUnderlyings(_borrower(), _amount);
```
