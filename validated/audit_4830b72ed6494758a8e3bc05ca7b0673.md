### Title
Unsanitized `VaultSecret.Path` allows Vault path traversal outside declared engine path via `path.Join` - ([File: helpers/vault/secret_engines/kv_v2/engine.go], [File: helpers/vault/secret_engines/generic/engine.go], [File: helpers/vault/secret_engines/registry.go])

### Summary
`VaultSecret.Path` and `VaultSecret.Engine.Path` are fully attacker-controlled strings from the `.gitlab-ci.yml` `secrets:` keyword, expanded via `vars.ExpandValue()` with no sanitization, then passed unmodified into `kv_v2.engine.Get`/`generic.engine.Get`, which build the final Vault API path via `path.Join(e.path, "data"/"metadata", secretPath)`. Because `path.Join` performs `Clean()`-style normalization of `..` segments without ever validating the result stays under `e.path`, a pipeline author can supply a `Path` containing `../` sequences to make the resolved Vault path escape the intended engine path prefix.

### Finding Description
The full call chain is: `spec.VaultSecret.expandVariables` (`common/spec/spec.go:805-811`) expands `Path`/`Engine.Path` from job CI variables with no path validation, then `helpers/secrets/resolvers/vault/resolver.go:38-53` calls `s.GetField(secret, secret)` → `helpers/vault/service/vault.go:97-118` `GetField` → `getSecretEngine` uses `secret_engines.GetFactory(engineDetails.EngineName())` (`helpers/vault/secret_engines/registry.go:21-33`) to build an engine bound to `engineDetails.EnginePath()`, then calls `engine.Get(secretDetails.SecretPath())`.

Both concrete engines compute the request path purely with `path.Join`: [1](#0-0) [2](#0-1) 

No component in this chain performs `filepath.Clean`-and-prefix-check, rejects `..` segments, or otherwise confirms the resolved path stays under `e.path`. `path.Join("team-a", "../team-b/db")` normalizes to `"team-b/db"`, i.e., a job declaring `engine.path: team-a` and `path: ../team-b/db` produces the Vault request path `team-b/db`, entirely outside the declared engine prefix. Because the resulting string is passed to `defaultClient.Read`/`Write` (`helpers/vault/client.go:96-104`), which forwards it verbatim to `Logical().Read(path)`/`Write(path, ...)`, the escape happens before any HTTP-level normalization and is fully under attacker control. [3](#0-2) [4](#0-3) [5](#0-4) 

The same unsanitized-join pattern also affects `helpers/gitlab_secrets_manager/service/gitlab_secrets_manager.go:22-33` (`GetSecret` → `engine.Get(secret.Path)`), though the code comment there notes GitLab Secrets Manager paths are server (Rails) generated and not directly user-controlled, unlike the generic Vault secrets path.

None of the existing checks (image/service allow-lists, masking, cleanup logic) apply here — there is simply no path-containment check anywhere between the CI-config-controlled `Path` field and the Vault API call.

### Impact Explanation
If the Vault/OpenBao token used by the runner (via JWT auth role, etc.) is authorized (by policy) to read paths beyond the specific engine-path prefix the job was meant to be scoped to — a common real-world setup where one auth role/token backs multiple engine mounts or subpaths for operational convenience — a pipeline author can declare a `secrets:` entry with a traversal-laden `path` (e.g. `path: ../other-project/db-password`) and read secrets outside the path they were authorized to declare in their own job definition, i.e., cross-project/cross-team secret exfiltration confined to whatever the shared token's policy allows.

### Likelihood Explanation
Fully reachable from a normal user-writable `.gitlab-ci.yml` `secrets:` block — no special privileges are needed to set `path`/`engine.path`, which flow straight through `ExpandValue` (CI variable expansion) into the Vault path construction. The only precondition is that the Vault token bound to the runner/job's auth role has policy access beyond the intended per-job path scope, which is a realistic and common Vault ACL layout (broad role, per-job scoping enforced only by which subpath a job declares). The bug is deterministic and trivially repeatable — no timing or race conditions are involved.

### Recommendation
After computing `path.Join(e.path, ...)` in `kv_v2.engine.dataPath`/`metadataPath` and `generic.engine.fullPath`, validate that the resulting path is still prefixed by (a cleaned) `e.path` before issuing the Vault request; reject with an error otherwise. Additionally, reject/sanitize `..` path segments in `VaultSecret.Path` and `VaultSecret.Engine.Path` at job validation/expansion time (`common/spec/spec.go`), consistent with the invariant that a job may only access the Vault path prefix it explicitly declared.

### Proof of Concept
Go unit test (add to `helpers/vault/secret_engines/kv_v2/engine_test.go`):
```go
func TestEngine_Get_PathTraversalEscapesEnginePrefix(t *testing.T) {
    enginePath := "team-a/"
    maliciousPath := "../team-b/db-secret"

    clientMock := vault.NewMockClient(t)
    clientMock.On("Read", mock.Anything).
        Run(func(args mock.Arguments) {
            resolvedPath := args.String(0)
            // Assert the resolved path never escapes the declared engine prefix.
            assert.True(t, strings.HasPrefix(resolvedPath, path.Clean(enginePath)),
                "resolved path %q escaped engine prefix %q", resolvedPath, enginePath)
        }).
        Return(vault.NewMockResult(t), nil)

    e := NewEngine(clientMock, enginePath)
    _, _ = e.Get(maliciousPath)
}
```
Expected (current) result: the assertion fails because `dataPath` resolves to `team-b/data/db-secret`, proving the request path escapes the `team-a/` engine prefix.

```go
func (v *defaultVault) GetField(engineDetails Engine, secretDetails Secret) (interface{}, error) {
	engine, err := v.getSecretEngine(engineDetails)
	if err != nil {
		return nil, err
	}

	secret, err := engine.Get(secretDetails.SecretPath())
	if err != nil {
		return nil, fmt.Errorf("reading secret: %w", err)
	}

	field := secretDetails.SecretField()
	for key, data := range secret {
		if key != field {
			continue
		}

		return data, nil
	}

	return nil, nil
}

func (v *defaultVault) getSecretEngine(engineDetails Engine) (vault.SecretEngine, error) {
	engineFactory, err := secret_engines.GetFactory(engineDetails.EngineName())
	if err != nil {
		return nil, fmt.Errorf("requesting SecretEngine factory: %w", err)
	}

	engine := engineFactory(v.client, engineDetails.EnginePath())

	return engine, nil
```
