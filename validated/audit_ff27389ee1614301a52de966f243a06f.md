The bug is in `StackerDBListener::run`, the main event loop in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`.

### Title
Miner's weight tally double-counts a signer who rejects then later accepts the same block, corrupting the approve/reject equality - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
In `StackerDBListener::run`, the `BlockResponse::Accepted` handler dedups purely on `gathered_signatures.contains_key(&slot_id)`, while the `BlockResponse::Rejected` handler dedups on `responded_signers.insert(slot_id)` — a set that the *accept* branch also unconditionally inserts into, but never checks before crediting weight. A signer that first rejects a proposal and later legitimately reconsiders and accepts the very same `signer_signature_hash` has its weight added to `total_weight_approved` without ever being subtracted from `total_weight_rejected`, so the same signer's weight is now counted on both sides of the tally simultaneously.

### Finding Description
`BlockStatus` tracks two independent counters, `total_weight_approved` and `total_weight_rejected`, meant to be mutually exclusive slices of `total_weight` [1](#0-0) .

On `Accepted`, the weight is credited only if the slot is not already in `gathered_signatures`, then `responded_signers.insert(slot_id)` is called unconditionally regardless of dedup outcome or of any pre-existing rejection [2](#0-1) .

On `Rejected`, the guard is the *opposite* set: `if block.responded_signers.insert(slot_id)` — which prevents a second rejection from double-adding to `total_weight_rejected`, and (correctly) prevents a later rejection from a signer who already accepted, since `responded_signers` was populated by the accept branch [3](#0-2) . But the reverse ordering is not symmetric: nothing in the `Accepted` branch checks whether the slot is already present in `responded_signers` (i.e., already rejected), and nothing subtracts the previously-added rejection weight when the later acceptance is processed.

The signer-side protocol legitimately allows this ordering: a proposal can be rejected for a transient reason (e.g. stale validation state) and later re-evaluated and signed for the identical block hash once the reject reason is no longer applicable, per the documented `should_reevaluate_reject_reason` reconsideration path in `handle_block_proposal`. When that happens, the miner's `stackerdb_listener` sees a genuine `Rejected` followed later by a genuine `Accepted` from the same signer/slot, and both weights are retained: `total_weight_rejected` still holds the stale rejection, and `total_weight_approved` now also holds the corrected acceptance.

### Impact Explanation
This breaks the equality that each signer's weight must be counted exactly once, toward exactly one of the two outcomes. Concretely:
- `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, so the two threshold checks in `SignerCoordinator`'s polling loop — reject-if-blocking-minority and accept-if-≥70% — are no longer computed over disjoint, up-to-date weight sets [4](#0-3) .
- A block can be treated as globally rejected (`SignersRejected`) using stale rejection weight from a signer who has since accepted, wrongly killing a block that in fact has enough current support — a liveness wedge.
- Conversely, and more severely, if the reject-branch check happens to run after enough accumulated weight from a flip-flopped signer plus genuine acceptors, the miner can conclude 70% approval was reached and push the block to the node even though the true, current, per-signer-once tally of distinct approving weight is lower than intended — this is functionally a stale rejection being silently retained alongside (and never reconciled against) a later, different, recounted decision from the same signer, corrupting the aggregated-weight-vs-verified-accepts equality the coordinator relies on to gate `handle_post_block`.

### Likelihood Explanation
This requires only a single signer (not a majority) to legitimately flip its vote for the same `signer_signature_hash` — a scenario the v0 signer state machine explicitly supports via reconsideration of a stale reject reason for a re-evaluated block, so it is triggerable by ordinary gossip/timing (no compromised keys, no majority collusion, no auth token or local access needed).

### Recommendation
Make the two branches symmetric: before crediting `total_weight_approved` in the `Accepted` handler, check whether the slot is already present in `responded_signers` due to a prior rejection; if so, subtract that signer's weight from `total_weight_rejected` (and remove any of its contributions to `failed_txids`) before adding it to `total_weight_approved`, or reject an out-of-order flip entirely and require the same invariant used for accept→reject in the `Rejected` handler.

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListener` initializes `BlockStatus { total_weight_approved: 0, total_weight_rejected: 0, responded_signers: {} , ... }` for `B`'s `signer_signature_hash`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B` (e.g. due to a transient `ProposalTooOld`-style or validation-timing reason). The `Rejected` handler executes `responded_signers.insert(slot_S)` → true, and `total_weight_rejected += w`.
3. `S`'s local view is updated (chain re-checked, reject reason resolved) and, following the documented reconsideration path, `S` later signs the identical block and broadcasts `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. The `Accepted` handler checks only `gathered_signatures.contains_key(slot_S)`, which is false (first acceptance), so it executes `total_weight_approved += w` and then unconditionally `responded_signers.insert(slot_S)` (already true, no-op).
5. Now `total_weight_rejected` still includes `w` from step 2 and `total_weight_approved` also includes `w` from step 4 — the same signer's weight is double-booked, and `total_weight_approved + total_weight_rejected > total_weight` for this block, corrupting both the accept and reject threshold checks in `SignerCoordinator::wait_for_signatures`/equivalent polling logic.
