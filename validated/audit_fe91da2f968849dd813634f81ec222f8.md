### Title
Builder index reuse allows a leftover payment/withdrawal entitlement to debit a new builder's balance - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_index_for_new_builder()` recycles a `BuilderIndex` slot based solely on `builder.balance == 0` and `builder.withdrawable_epoch <= current_epoch`, without checking whether the slot still has an outstanding entitlement recorded in `state.builder_pending_payments` or `state.builder_pending_withdrawals` (both of which reference builders only by `builder_index`, not by `pubkey`). This is the same class of bug as the OpenDollar `transferSAFEOwnership()` finding: an authorization/entitlement record tied to a slot (safe id / builder index) is not cleared when the slot's ownership changes hands, so it is later honored against the new occupant.

### Finding Description
A `Builder`'s identity in the state (`state.builders[builder_index]`) is looked up only by index in the withdrawal/payment settlement path:

- `get_index_for_new_builder` frees a slot for a brand-new builder once `withdrawable_epoch <= get_current_epoch(state)` and `balance == 0`: [1](#0-0) 

- `process_builder_deposit_request` uses that free slot to register a completely different `pubkey`/`execution_address` at the same `builder_index` via `add_builder_to_registry`: [2](#0-1) 

- Meanwhile, `state.builder_pending_payments` and `state.builder_pending_withdrawals` entries created for the *old* builder only carry `builder_index` (plus an independent `fee_recipient` and `amount`), and are looked up purely by that numeric index: [3](#0-2) 

- Contrast this with `process_builder_exit_request`, which *does* require `get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0` to return before allowing an exit to be initiated: [4](#0-3) 

However, `get_index_for_new_builder`/`process_builder_deposit_request` (the slot-reuse path) apply no equivalent check against `get_pending_balance_to_withdraw_for_builder`. They only gate on `builder.balance == 0`. Because `process_execution_payload_bid` never decrements `builder.balance` when a bid is accepted (it only asserts `can_builder_cover_bid`, and the actual balance reduction happens later in `process_withdrawals` when the queued `BuilderPendingWithdrawal`/settled `BuilderPendingPayment` is swept), and because the builder-withdrawal sweep is rate-limited (processes at most `MAX_WITHDRAWALS_PER_PAYLOAD - 1` builder withdrawals per block per the `process_withdrawals` field-effects description), a builder can reach `balance == 0` and a past `withdrawable_epoch` while one or more of its `builder_pending_payments`/`builder_pending_withdrawals` entries referencing its `builder_index` are still queued and not yet settled/applied: [5](#0-4) [6](#0-5) 

Once a new builder registers at that reused `builder_index`, the stale queued entry is later processed against `state.builders[builder_index]` — which is now the *new* builder — deducting `withdrawal.amount` (bound for `fee_recipient`) from the new builder's balance, exactly as `state.builders[*].balance` is described as being decreased "by withdrawal amounts for each builder withdrawal" using the withdrawal's `builder_index` field: [7](#0-6) 

This is structurally identical to the ODSafeManager issue: `safeCan[owner][safe][user]` is keyed by the mutable "owner" slot and is not cleared on `transferSAFEOwnership`, so a stale grant is later honored against the wrong current owner. Here, `builder_pending_payments`/`builder_pending_withdrawals` are keyed by the mutable `builder_index` slot and are not cross-checked before that slot is reassigned to a new `pubkey`/`execution_address`, so a stale entitlement is later applied against the wrong current builder.

### Impact Explanation
This breaks the equality that a builder's balance may only be debited for withdrawals/payments that builder itself committed to. Instead, Gwei belonging to a newly-registered, unrelated builder is silently transferred out to a `fee_recipient` chosen by the *previous* occupant of that index — Gwei is destroyed from the new builder without its authority and paid to an address it never authorized. This matches the "Gwei created, destroyed or paid to a non-owner" / "a validator or builder mutated without its authority" criteria for a valid analog (Critical/High class impact), since honest spec-following nodes would all apply the same erroneous debit deterministically (so it isn't a consensus split, but it is a real, protocol-level balance-loss bug reachable without any privileged actor — any two builders churning through deposit/exit naturally trigger it).

### Likelihood Explanation
The trigger conditions are: (1) a builder submits bid(s) generating `builder_pending_payments`/`builder_pending_withdrawals` entries, (2) the builder's exit is initiated and its balance is swept to zero while a queued payment/withdrawal entry for it is still pending (rate-limited sweep makes backlog plausible, especially with `MAX_WITHDRAWALS_PER_PAYLOAD` limits and the `builder_pending_payments` rotation window of `2*SLOTS_PER_EPOCH`), and (3) a new builder deposits and is assigned the recycled index before the stale entry drains. Because `get_index_for_new_builder` performs no check against `get_pending_balance_to_withdraw_for_builder`, none of this requires a malicious peer, client bug, or coalition — it can occur under normal operation given adversarial but valid transaction/request timing from any builder pair, making it a plausible, unprivileged, protocol-level defect.

### Recommendation
`get_index_for_new_builder` (and/or `process_builder_deposit_request`) should refuse to reuse a `builder_index` whose `get_pending_balance_to_withdraw_for_builder(state, index) != 0`, mirroring the check already present in `process_builder_exit_request`. Alternatively, pending payment/withdrawal records should be resolved (settled or purged) before the slot is considered free, or records should carry enough builder-identity binding (e.g., pubkey) to be validated against the current occupant at settlement time.

### Proof of Concept
1. Builder A occupies `builder_index = 5`. It submits a winning bid; `process_execution_payload_bid` records a `BuilderPendingPayment` for index 5 with `fee_recipient = X`, `amount = V` [6](#0-5) .
2. Builder A submits a `BuilderExitRequest`; since no pending balance existed yet at that moment (the bid above is submitted concurrently in the same/adjacent slot such that `get_pending_balance_to_withdraw_for_builder` was 0 at initiation time), `initiate_builder_exit` succeeds, setting `withdrawable_epoch` [8](#0-7) .
3. Epochs pass; `settle_builder_payment` moves the payment into `state.builder_pending_withdrawals` for index 5, and the sweep in `process_withdrawals` — rate-limited per block — has not yet processed it, while builder A's `balance` independently reaches 0 (e.g., all other funds were already swept out in earlier withdrawals) and `withdrawable_epoch <= current_epoch`.
4. A new builder B submits a `BuilderDepositRequest` with a fresh `pubkey`. `get_index_for_new_builder` sees index 5 has `balance == 0` and `withdrawable_epoch` in the past, and reassigns index 5 to builder B via `add_builder_to_registry` [9](#0-8) .
5. On a later slot, `process_withdrawals` drains the still-queued `BuilderPendingWithdrawal{builder_index=5, fee_recipient=X, amount=V}`, decrementing `state.builders[5].balance` — now builder B's balance — by `V`, and paying `V` to `X`, an address builder B never authorized [7](#0-6) .

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance

###### New `get_index_for_new_builder`

```python
def get_index_for_new_builder(state: BeaconState) -> BuilderIndex:
    for index, builder in enumerate(state.builders):
        if builder.withdrawable_epoch <= get_current_epoch(state) and builder.balance == 0:
            return BuilderIndex(index)
    return BuilderIndex(len(state.builders))
```

###### New `process_builder_deposit_request`

*Note*: Builder indices are reusable. When a builder exits, its index may later
be reassigned to a different builder with a new public key. Any deposit sent to
an exited builder will be withdrawn to the builder’s execution address. Exited
builders cannot be reactivated, although a newly registered builder’s public key
may have previously appeared in the builder set. Implementations that rely on
caching should account for this behavior.

```python
def process_builder_deposit_request(state: BeaconState, request: BuilderDepositRequest) -> None:
    # Ignore deposits with unexpected withdrawal credential prefixes
    if not is_builder_withdrawal_credential(request.withdrawal_credentials):
        return

    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        if is_valid_builder_deposit_signature(request):
            add_builder_to_registry(
                state,
                request.pubkey,
                PAYLOAD_BUILDER_VERSION,
                ExecutionAddress(request.withdrawal_credentials[12:]),
                request.amount,
                state.slot,
            )
    else:
        builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
        builder = state.builders[builder_index]

        # If exited and swept, reset the withdrawable epoch
        if builder.withdrawable_epoch != FAR_FUTURE_EPOCH and builder.balance == 0:
            epoch = get_current_epoch(state)
            builder.withdrawable_epoch = epoch + MIN_BUILDER_WITHDRAWABILITY_DELAY

        # Increase balance by deposit amount
        builder.balance += request.amount

```python
def process_builder_exit_request(state: BeaconState, request: BuilderExitRequest) -> None:
    builder_pubkeys = [b.pubkey for b in state.builders]
    if request.pubkey not in builder_pubkeys:
        return

    builder_index = BuilderIndex(builder_pubkeys.index(request.pubkey))
    builder = state.builders[builder_index]

    if not is_active_builder(state, builder_index):
        return
    if builder.execution_address != request.source_address:
        return
    if get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0:
        return

    initiate_builder_exit(state, builder_index)
```
