### Title
Two sibling tenure-change blocks in the same tenure can each cross the pre-commit signing threshold before the duplicate-tenure-change check or the own-tenure signed-conflict guard has anything to compare against — ([File: stacks-signer/src/v0/signer.rs])

### Summary
The invariant "at most one tenure-change block per tenure gets signed" is enforced only once, at proposal-arrival time, via `validate_tenure_change_payload`'s `DuplicateBlockFound` check, which looks at *signed* blocks only (`get_last_signed_block` in v2, `get_last_globally_accepted_block` in v1). Every later re-check — at validate-ok and at pre-commit-threshold time — either checks the *parent* tenure only (`check_tenure_change_confirms_parent`) or relies on `get_signed_conflicts`, which likewise only returns blocks that already carry a signature. A pre-commit "carries no signature" (confirmed by `has_signed_block_in_tenure`'s own regression-test comment). This is structurally the same class of bug as the reported `EthPrivErc20Vault` issue: a control (whitelist / one-tenure-change-per-tenure) is enforced at one entry point (`deposit` / initial proposal) but not re-enforced at the other paths that produce the same effect (`transfer` / pre-commit-driven signing).

### Finding Description
- The one-time duplicate check lives in `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs`, `v2.rs`), invoked only during `handle_block_proposal`'s fresh evaluation, per `docs/signer-flows.md` section 7: "Two things belong to the proposal path only and are **not** re-run at validate-ok or at signing: `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we have already accepted a block in the tenure a tenure-change block is starting."
- At pre-commit-threshold time, `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1803-1840`) for a tenure-change block calls `check_tenure_change_confirms_parent`, which checks the **parent** tenure's tip, never the block's own tenure for a duplicate tenure-start.
- The only remaining guard against two siblings in the *same* tenure both getting signed is the own-tenure fallback in `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1423-1450`), which is explicitly commented as compensating for exactly this gap ("The chainstate checks don't cover this for tenure-change blocks"). But this fallback:
  1. only sees a "conflict" via `get_signed_conflicts`, which by design excludes merely pre-committed blocks (`signerdb.rs` `get_signed_conflicts`/`has_signed_block_in_tenure` doc comments: "Blocks that were only pre-committed carry no signature and are never returned"), and
  2. when it does find a same-tenure conflict, only blocks signing if the **node's own tenure tip** (`stacks_client.get_tenure_tip`) already reports height ≥ the proposed block — an asynchronous, racy check.
- Nothing prevents a single signer from independently pre-committing to two different tenure-change block proposals (B1, B2) for the same tenure, since pre-commit is tracked per `signer_signature_hash`, not exclusively per tenure, and `check_block_against_signer_db_state` for both blocks only inspects the parent tenure (identical for both siblings), so both pass.

### Impact Explanation
If a miner (or a colluding signer with knowledge of timing) broadcasts two competing tenure-change block proposals B1 and B2 for the *same* tenure before either accumulates enough weight to be recorded as *signed* anywhere in the signer set, every signer can pre-commit to both, since neither the proposal-time duplicate check nor the pre-commit-time re-check treats a merely-pre-committed sibling as a conflict. Once B1 crosses the ≥70% weight threshold and is signed by (some) signers, B2 can still be independently signed by others, or even the same signer, as long as B2's own re-check happens before the node has processed/advanced its canonical tip past B1 (`get_tenure_tip` returning a stale/lower height, or being unreachable, which per `docs/signer-flows.md` section 7's flow explicitly falls through to "passes"). This yields two independently ≥70%-signed, conflicting Nakamoto blocks for the same tenure/height — a signer signing a *conflicting* block, matching the report's "Critical" impact bucket in the rules (a rejection-vs-acceptance / conflicting-block equality break), not merely a liveness issue.

### Likelihood Explanation
This requires only a single miner (one-slot) plus ordinary StackerDB gossip — no majority of signers, no other signer's key, and no node/local access beyond what a miner normally has. The race window is real: block validation by the node and by each signer runs asynchronously (`spawn_validation_thread`, `stackslib/src/net/api/postblock_proposal.rs:348-381`), and pre-commit accumulation across signers is not synchronized against the node's tip advancement. The codebase's own test (`signer_waits_for_validation_before_signing` in `stacks-node/src/tests/signer/v0/signers_wait_for_validation.rs`) and the explicit code comments in `handle_block_pre_commit` show the authors are aware similar TOCTOU races exist around pre-commit/signing timing, making this a plausible, not merely theoretical, race — though its exact reliability depends on network timing between the two proposals, node validation latency, and tip-advancement speed, which I was not able to fully verify by tracing an end-to-end integration test.

### Recommendation
Re-run an own-tenure "duplicate tenure-start" check at pre-commit/signing time that also treats a fresh, higher-weight *pre-commit* (not just a signature) on a sibling tenure-change block in the same tenure as a conflict, rather than relying solely on `get_signed_conflicts` (which ignores pre-commits) and the asynchronous `get_tenure_tip` node query. Alternatively, make `check_block_against_signer_db_state` for tenure-change blocks also verify, via `signerdb`, whether *any* other tenure-change block for the same tenure has already reached (or is close to reaching) pre-commit/signing weight before allowing a second one to be signed.

### Proof of Concept
1. Miner proposes B1: a tenure-change block starting tenure T, and immediately proposes B2: a second, competing tenure-change block also claiming to start tenure T (different transaction set/timestamp, same parent block, same consensus hash context), before any signer has signed either.
2. Every signer runs `handle_block_proposal` for both; `check_block_against_state` → `check_proposal` → `validate_tenure_change_payload` finds no already-*signed* block in tenure T for either (per v2, `get_last_signed_block`), so both proposals pass and get submitted to the node for validation.
3. Node validates both independently (`postblock_proposal.rs::validate`) since it hasn't processed either yet; each signer receives `BlockValidateOk` for both B1 and B2 and calls `handle_block_validate_ok`, which runs `check_block_against_signer_db_state` → for tenure-change blocks, `check_tenure_change_confirms_parent` (parent tenure only) → passes for both → both get `mark_pre_committed` and broadcast pre-commits.
4. Enough weight accumulates on B1's pre-commits to cross 70%; the re-check in `handle_block_pre_commit` (`signer.rs:1345-1421`) finds no signed conflict yet (nothing signed) → signs B1.
5. Before the node's tenure tip for T advances past B1's height, B2 also crosses 70% pre-commit weight on possibly overlapping signers; `get_signed_conflicts` now finds B1 (same consensus_hash) but the own-tenure fallback (`signer.rs:1436-1447`) queries `get_tenure_tip(T)`, which — if the node hasn't yet processed B1 — reports a height below B2's, so the check passes and B2 is also signed.
6. Result: two ≥70%-weight signed, mutually conflicting tenure-change blocks exist for tenure T.
