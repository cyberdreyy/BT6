### Title
Interest-rate model changes are not accrued before applying, letting any user retroactively misprice a stale interest window via the permissionless accrue instruction - (File: programs/marginfi/src/instructions/marginfi_group/configure_bank_lite.rs)

### Summary
`lending_pool_configure_bank_interest_only` (and the general `lending_pool_configure_bank` path) mutate `bank.config.interest_rate_config` directly without first calling `accrue_interest` to settle interest under the old curve. Because `last_update` is untouched by the configuration change, the next accrual — which any unprivileged user can trigger via the permissionless `lending_pool_accrue_bank_interest` instruction — applies the brand-new rate curve retroactively across the *entire* elapsed `time_delta` since `last_update`, including the period that was actually governed by the old rate model.

### Finding Description
`lending_pool_configure_bank_interest_only` updates the interest curve in place with no accrual step: [2](#0-1) 

The general configure path does the same inside `Bank::configure`: [3](#0-2) 

`accrue_interest` computes `time_delta` from `self.last_update` to `current_timestamp` and applies a *single* interest-rate calculator (built from whatever `interest_rate_config` is in place *at accrual time*) across that whole `time_delta`: [4](#0-3) 

Since a config update neither calls `accrue_interest` nor advances `last_update`, if the bank has gone any length of time without activity, then an admin changes the curve, the *next* accrual (whenever it happens) will price the whole stale window—both the pre-change and post-change portion—entirely under the *new* curve. Critically, that next accrual does not require any privileged party: `lending_pool_accrue_bank_interest` is permissionless, gated only by `!group.load()?.is_protocol_paused()`, with no admin/signer check on the caller: [5](#0-4) 

This turns a plain configuration-timing bug into an unprivileged, deterministically triggerable misvaluation: any user (e.g., an existing borrower or depositor) can call the permissionless accrue instruction immediately after an admin's rate-model change and force retroactive application of the new curve over a window that legitimately should have accrued at the old rate.

### Impact Explanation
This is a genuine accounting/misvaluation bug with direct financial effect on lenders and borrowers, independent of any presumed benign or malicious intent by the admin: whichever direction the rate changes, some class of user (borrowers if the new rate is lower, depositors if the new rate is higher, or vice versa) is retroactively over/under-charged for a period that should have used the previous curve. Because the trigger (`lending_pool_accrue_bank_interest`) is permissionless, an unprivileged actor can deliberately time the call to lock in the mispriced accrual to their advantage (e.g., quickly repaying/depositing to capture a favorable retroactive rate before other activity naturally triggers accrual under mixed conditions). The magnitude scales with how stale the bank was (`time_delta`) and the delta between old and new rate curves.

### Likelihood Explanation
Likelihood is moderate: it requires (1) a rate-model change via `lending_pool_configure_bank_interest_only`/`lending_pool_configure_bank`, and (2) the bank having accumulated some elapsed time since `last_update` (i.e., no intervening deposit/borrow/withdraw/repay/accrue in the interim). Banks with lower activity or curve updates that occur after periods of inactivity are the most exposed. Any unprivileged user can then call the permissionless accrual instruction to crystallize the misapplied rate, so no special access is required to realize the effect once the precondition is met.

### Recommendation
Force an interest accrual (`accrue_interest`) using the *old* `interest_rate_config` and current timestamp before mutating `bank.config.interest_rate_config` in both `Bank::configure` (for the `lending_pool_configure_bank` path) and `lending_pool_configure_bank_interest_only`. This ensures `last_update` and share values are settled under the prior curve before the new curve takes effect, matching the mitigation pattern recommended in the analogous BendDAO finding (call `updateInterestRates`/`accrue_interest` immediately after any rate model reassignment, before it can affect subsequent accrual windows).

### Proof of Concept
1. Admin creates a bank and lets it run normally so `last_update` reflects some timestamp `T0`, with active deposits/borrows.
2. No further deposit/borrow/withdraw/repay/accrue transactions occur for a substantial period (`Δt`), so `last_update` remains `T0` while wall-clock time advances to `T1 = T0 + Δt`.
3. Admin calls `lending_pool_configure_bank_interest_only` (or `lending_pool_configure_bank`) to change the interest curve (e.g., lowering `hundred_util_rate`/`zero_util_rate`), intending the new curve to apply going forward. `bank.config.interest_rate_config` is updated; `last_update` is still `T0`.
4. Any unprivileged user immediately submits `lending_pool_accrue_bank_interest` (permissionless, no admin signer required).
5. Inside `accrue_interest`, `time_delta = T1 - T0` is computed and the *entire* `Δt` window is priced using the *new* curve (`self.config.interest_rate_config.create_interest_rate_calculator(...)` reads the post-update config), even though `Δt` spans time when the old curve was actually in effect.
6. Resulting `asset_share_value`/`liability_share_value` changes misprice interest for the whole `Δt` window under the wrong curve, producing a financial gain/loss for depositors/borrowers depending on the direction of the rate change — realized by whichever user first calls the permissionless accrual after the config change.

pub fn lending_pool_accrue_bank_interest(
    ctx: Context<LendingPoolAccrueBankInterest>,
) -> MarginfiResult {
    let clock = Clock::get()?;
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = &ctx.accounts.group.load()?;

    bank.accrue_interest(
        clock.unix_timestamp,
        group,
        #[cfg(not(feature = "client"))]
        ctx.accounts.bank.key(),
    )?;

    // TODO see if we can recycle some things like the InterestRateCalc from accrue to save some CU
    bank.update_bank_cache(group)?;

    Ok(())
}

#[derive(Accounts)]
pub struct LendingPoolAccrueBankInterest<'info> {

        has_one = group @ MarginfiError::InvalidGroup

pub fn lending_pool_configure_bank_interest_only(
    ctx: Context<LendingPoolConfigureBankInterestOnly>,
    interest_rate_config: InterestRateConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    msg!(
        "Configuring bank: {:?} mint: {:?}",
        ctx.accounts.bank.key(),
        bank.mint
    );

    // If settings are frozen, interest rates can't update.
    if bank.get_flag(FREEZE_SETTINGS) {
        msg!("WARN: Bank settings frozen, did nothing.");
    } else {
        bank.config
            .interest_rate_config
            .update(&interest_rate_config);
        bank.config.interest_rate_config.validate()?;
        msg!("Bank configured!");
    }

    Ok(())
}
