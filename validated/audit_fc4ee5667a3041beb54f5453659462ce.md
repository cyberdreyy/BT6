### Title
Loss-adjusted haircut applied to only one receipt epoch — earlier pending receipts pay out at par and drain funded underlyings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` haircut spreads a `stopEpochWithDuration` loss pro-rata over the aggregate `pendingWithdraws` basis, but records a single recovery price under `lossRecoveryPriceByEpoch[epochNumber]`. User receipt basis is tracked per epoch in `withdrawsRequestsByEpoch[user][epoch]`, while `_claimLossAdjustedWithdrawRequest` only haircuts the epoch pointed to by `lastWithdrawRequest[user]`. Any receipt basis stored under other epochs that was part of the same haircutted `pendingWithdraws` is subsequently paid at par by `_claimFundedWithdrawRequest`. The attacker-controlled "offset" — which epoch index their receipt lands in — lets them write/claim past the intended bounds, the direct analog of the unsanitized-offset buffer overflow in CVE-2019-15695.

### Finding Description
When `stopEpoch` runs with a loss, `IdleCDOEpochVariant._stopEpoch` calls `previewLossAdjustedWithdrawFunds(_lossAmount)`, which splits the loss pro-rata across the entire aggregate `pendingWithdraws` bucket, then `collectWithdrawFunds(pendingToFund)` stores one haircut `lossRecoveryPriceByEpoch[epochNumber]` for the whole bucket (`IdleCreditVault.sol:411-430`).

On the user side, `requestWithdraw` records basis per request epoch: `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and overwrites `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:259-294`).

At claim time, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which reads only `lossEpoch = lastWithdrawRequest[_user]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch`, paying `claimBasis * lossRecoveryPrice / 1e18` (`IdleCreditVault.sol:789-801`). It then falls through to `_claimFundedWithdrawRequest`, which pays the entire remaining `withdrawsRequests[_user]` aggregate at par with no haircut lookup at all (`IdleCreditVault.sol:319-350`).

The guard in `requestWithdraw` (`IdleCreditVault.sol:261-271`) only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, so it never protects receipts keyed under *earlier* epochs either.

Sequence:
1. Epoch N running. Attacker (KYC'd AA holder) calls `requestWithdraw` → basis `r1` keyed at epoch N. Epoch N stops fully funded; attacker does not claim.
2. Epoch N+1 running. Attacker calls `requestWithdraw` → basis `r2` keyed at epoch N+1; `lastWithdrawRequest = N+1`.
3. Epoch N+1 ends with `_lossAmount > 0` (loss path). `collectWithdrawFunds` funds only `pendingToFund = (r1 + r2) * recoveryPrice` and stores `lossRecoveryPriceByEpoch[...]`. The funded underlyings cover only the haircutted total.
4. Attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` haircuts only one epoch's piece (the one `lastWithdrawRequest`/`lossRecoveryPriceByEpoch` resolves to — either the N+1 piece, or, if `epochNumber` was already incremented by the `deposit()` call inside `getFundsFromBorrower` before `collectWithdrawFunds` runs at `IdleCDOEpochVariant.sol:408-410`, *neither* piece, since the price lands on a key no user receipt references). `_claimFundedWithdrawRequest` then pays the remaining aggregate at par.

In the best case for the attacker, payout = `r2 * price + r1` (or `r1 + r2` fully at par if the epoch key is off-by-one) while only `(r1 + r2) * price` was funded. The invariant broken is "one receipt → one haircutted payout": receipts sharing one loss haircut are not all charged it.

### Impact Explanation
Direct theft/insolvency. The attacker withdraws `r_early * (1 - lossRecoveryPrice)` more underlyings than were funded for their receipts — with a 50% haircut and an earlier-epoch receipt of size `r1`, the excess is `r1 / 2`. This is paid out of the strategy's funded withdrawal balance, so other claimants' funded receipts (or, once drained, `defaultRecoveryReserve` guarded by `_transferFundedClaim`) become unpayable: permanent loss for later claimants equal to the over-payment. The attacker needs only a normal withdraw request in two consecutive epochs and a loss stop — no privileged role.

### Likelihood Explanation
Requires a `stopEpochWithDuration(_lossAmount > 0)` (borrower shortfall — a normal, expected protocol event) while the attacker holds unclaimed receipts from ≥2 request epochs. Keeping a receipt unclaimed across one epoch boundary is a single omitted transaction and is explicitly contemplated by the code comments ("if a user does not claim a withdraw request and instead requests another withdraw"). The attacker can pre-position the small epoch-N receipt cheaply. Cost is only gas; benefit scales with `r1`.

### Recommendation
Apply the loss haircut per epoch, not via a single `lastWithdrawRequest` cursor:
- Store `lossRecoveryPriceByEpoch` for every epoch that contributed to the haircutted `pendingWithdraws` basis (e.g., record a loss marker range, or store `lossRecoveryPrice` plus the set of affected epochs), and have `_claimFundedWithdrawRequest` iterate/lookup each epoch key in `withdrawsRequestsByEpoch[user]` and apply that epoch's recovery price instead of paying at par blindly.
- Alternatively, block multi-epoch pending receipts: revert in `requestWithdraw` whenever `withdrawsRequestsByEpoch[_user][epoch]` for any prior epoch is nonzero (not only the `lastWithdrawRequest` epoch), forcing claim-before-re-request for all pending basis.
- Add a regression test: receipts in two different epochs + a partial-loss `stopEpochWithDuration` → user must receive `(r1 + r2) * lossRecoveryPrice` total.

### Proof of Concept
Foundry fork test sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testLossHaircutMissesEarlierEpochReceipt() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amount, true);   // KYC'd AA deposit

    // --- epoch N running ---
    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));       // r1 keyed at epoch N
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch()); // fully funded stop

    // --- epoch N+1 running: do NOT claim r1; open r2 ---
    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));       // r2 keyed at epoch N+1
    uint256 r1r2 = IERC20Detailed(strategyToken).balanceOf(attacker);

    // --- epoch N+1 stops with a realized loss (e.g. 50% on pending bucket) ---
    uint256 loss = ...;                                    // chosen so pendingLoss > 0
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, loss, ...);

    uint256 price = IdleCreditVault(address(strategy))
        .lossRecoveryPriceByEpoch(IdleCreditVault(address(strategy)).epochNumber());
    assertGt(price, 0);
    assertLt(price, 1e18);

    // --- claim ---
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // funded amount was (r1+r2) * price / 1e18 — attacker must not exceed it
    assertGt(paid, r1r2 * price / 1e18, 'over-paid: earlier-epoch receipt escaped haircut');
}
```

Uncertainty I could not fully resolve within available iterations: whether `epochNumber` is incremented (via `deposit()` inside `getFundsFromBorrower` at `IdleCDOEpochVariant.sol:408`) *before* `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` at line 410. If it is, the bug is strictly worse — the haircut key is off-by-one and *no* pending receipt is ever haircutted, making every pending request claimable at par. If not, the exploit stands as described (all but the latest-epoch receipt escape the haircut). Either way the aggregate-vs-per-epoch accounting mismatch is the defect.
