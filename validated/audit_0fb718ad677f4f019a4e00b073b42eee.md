### Title
Unbounded growth of `responseCache.cache` via caller-controlled `Store=true` requests with distinct cache keys - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Finding Description
`responseCache` stores every cacheable response in an in-memory map keyed by `req.Hash()` (method, URL, headers, body, workflowOwner) with no cap on map size or entry count. In `Fetch`, when `storeOnFetch` (i.e., `req.CacheSettings.Store`) is true and the response has a cacheable status code, the entry is unconditionally written into `rc.cache` under a lock, with removal only happening later via `DeleteExpired`, which runs on a fixed ticker (`CleanUpPeriodMs`, default 10 minutes) and only deletes entries whose `storedAt + rc.ttl` (a single global TTL, `OutboundRequestCacheTTLMs`, default 10 minutes) has passed. [1](#0-0) [2](#0-1) 

`CacheSettings.Store` and `CacheSettings.MaxAgeMs` originate from `gateway_common.OutboundHTTPRequest`, which is populated by the workflow/node's HTTP action request and passed straight to `Fetch`/`Set` with no per-key or aggregate cache size limit anywhere in `http_handler.go`. [3](#0-2) 

The only throttling in this path is a per-node rate limiter, a global node rate limiter, and a per-workflow trigger rate limiter (`cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit`); none of these bound the number of *distinct* cache keys that can accumulate in `rc.cache` before the next TTL sweep. As long as a workflow/caller can vary the request (URL, body, headers) to produce unique hashes, and set `Store=true`, each unique request adds a permanent (until TTL expiry) entry to the shared map, which is not partitioned or quota-limited per workflow/owner.

### Impact Explanation
Because `rc.cache` is shared across all subscribers of the gateway's HTTP-action/HTTP-trigger capability, a single caller able to originate many uniquely-keyed HTTP-action requests with `Store=true` can inflate this map's memory footprint for as long as the TTL window (default 10 minutes) lasts before cleanup. Since entry count is bounded only by (request rate × TTL) rather than by any explicit maximum size, a high enough request rate (bounded only by generic rate limiters not designed for this purpose) can cause significant memory growth in the gateway process, degrading availability of the http-action/http-trigger capability for other tenants sharing the same gateway instance. This corresponds to a resource-exhaustion / availability-degradation class finding rather than a data-confidentiality or authorization bypass.

### Likelihood Explanation
Exploitability depends on the caller's ability to (a) originate `OutboundHTTPRequest`s with `CacheSettings.Store=true` and varying content to generate distinct `Hash()` values, and (b) do so at a rate/volume not effectively curbed by the existing per-node/per-workflow rate limiters over the TTL window. This requires a legitimate but potentially low-privilege workflow-owner capability to submit HTTP-action requests (an authenticated DON/workflow-triggering credential), not admin or host access. I was unable to confirm the exact numeric values of `cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit`, `GatewayHTTPGlobalRate`, or `GatewayHTTPPerNodeRate` in this codebase (search returned no matches in an accessible `cresettings` path), so the real-world feasibility (how large the cache could actually grow given those limits) could not be fully quantified from the available index and would need confirmation via a live Devin session or by reading the `chainlink-common` `cresettings` package directly.

### Recommendation
Add an explicit maximum size (or memory budget) to `responseCache`, evicting oldest/least-recently-used entries (or rejecting new stores) once the limit is reached, independent of the TTL sweep. Consider also enforcing a per-workflow/per-owner quota on the number of distinct cache entries a single caller can hold, so that no single tenant can exhaust the shared cache used by all subscribers.

### Proof of Concept

2. In a loop, call `Fetch` N times (e.g., N = 100,000) with `storeOnFetch=true` and a distinct `gateway.OutboundHTTPRequest` each iteration (vary `URL` or `Body` so `req.Hash()` differs) and a `fetchFn` returning a `200` status response.
3. After the loop, assert `len(rc.cache) == N` (or read `rc.cache` size via a test-only accessor) and show there is no configured maximum — i.e., the test should fail against a fix that caps cache size (e.g., asserting `len(rc.cache) <= someMaxSize)` fails on current code, but passes once a max-size/eviction policy is added).

```go
func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
```
