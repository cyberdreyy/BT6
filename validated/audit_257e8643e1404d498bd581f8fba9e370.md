### Title
Pending withdraw receipts bypass the stop-epoch loss haircut because `lossRecoveryPriceByEpoch` is keyed by the post-increment `epochNumber`, while claims look it up via the stale request epoch stored in `lastWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Ghost symlink bug is a *trusted-pointer resolves to the wrong resource* class: an attacker plants an indirection (symlink) inside a trusted path, and the server follows it to an arbitrary file. In `IdleCreditVault`, the analog indirection is `lastWithdrawRequest[_user]`, the per-user pointer to "the epoch my pending receipt lives in." `requestWithdraw` stamps it with the current `epochNumber` (the epoch in which the request was opened), but `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epochNumber]` *after* `deposit()` has already incremented `epochNumber` during `stopEpoch`. The receipt's epoch key and the loss's epoch key are permanently off by one, so a loss-adjusted receipt resolves like a "symlink to nowhere": `_claimLossAdjustedWithdrawRequest` finds `lossRecoveryPriceByEpoch[lossEpoch] == 0` and returns 0, after which `claimWithdrawRequest` falls through to `_claimFundedWithdrawRequest` and pays the full, unhaircutted basis. Receipt holders escape the loss waterfall entirely, and the strategy's underlyings (funded only at the haircutted amount) are drained first-come-first-served, leaving later claimants and active LPs with an unbacked deficit.

### Finding Description
`requestWithdraw` records the request epoch as the pointer for later loss lookup:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:281-293
lastWithdrawRequest[_user] = currentEpoch;              // stamped at request time = N
...
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

At `stopEpoch`, the CDO deposits realized interest via `deposit()`, which increments `epochNumber` while `isEpochRunning()` is still true:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:607-610
if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
    totEpochDeposits = 0;
    epochNumber += 1;                                    // now N+1
}
```

`collectWithdrawFunds` then books the loss under the *new* epoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:417-421
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
if (lossRecoveryPrice == 0) revert NotAllowed();
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;   // key = N+1
```

But both the claim path and the new-request guard dereference the *request* epoch:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:789-800 (claim)
uint256 lossEpoch = lastWithdrawRequest[_user];              // = N
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]; // lossRecoveryPriceByEpoch[N] == 0
if (lossRecoveryPrice == 0) return amount;                   // haircut path silently skipped
```

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:261-270 (request guard, same broken lookup)
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice != 0 && (...)) revert NotAllowed();    // never triggers
```

Then `claimWithdrawRequest` (`:312-313`) adds `_claimLossAdjustedWithdrawRequest` (returns 0) to `_claimFundedWithdrawRequest`, whose only epoch gate is `epochNumber > lastWithdrawRequest` (N+1 > N — satisfied), and which pays `withdrawsRequests[_user]` at par via `_transferFundedClaim` (`:338-349`). The only balance sanity check is `balance - reserve < amount`, and since `defaultRecoveryReserve` is 0 pre-default, the full unhaircutted payout succeeds as long as any balance exists.

The broken invariant is the **loss waterfall**: `collectWithdrawFunds` intentionally funds only `pendingBasis - pendingLoss`, but every pending receipt is still paid `pendingBasis`. The strategy burns the receipt and transfers the full amount — i.e., the loss that `previewLossAdjustedWithdrawFunds` assigned to pending receipts is instead silently socialized back onto whoever holds the bag (later claimants get `transfer` reverts; if the deficit is absorbed by residual strategy funds, active tranche holders).

Note on certainty: this depends on `collectWithdrawFunds` being invoked *after* the interest `deposit()` inside `stopEpoch`/`stopEpochWithDuration` in `IdleCDOEpochVariant` (the natural order — accrue/repay interest into the strategy, then fund pending receipts). If the CDO instead calls `collectWithdrawFunds` before the epoch-bumping `deposit`, the keys match and this is not exploitable; I could not re-verify the CDO-side call order in this pass. The reported mechanism is consistent with the comment at `:281` ("buffer + epochDuration is 1 epoch"), which shows the request epoch and the stop-time epoch are deliberately distinct values.

### Impact Explanation
Direct theft / insolvency, proportional to `pendingWithdraws × (1 − lossRecoveryPrice)`. For a $10M pending bucket with a 20% realized loss, `collectWithdrawFunds` pulls in only $8M, yet all receipts redeem $10M total: the first claimants to call `claimWithdrawRequest` through the CDO walk away whole, and the last ~$2M of claims revert on insufficient balance (permanent freezing of the remainder) or the shortfall is pulled from strategy funds backing active tranches (theft from LPs). Either way the intended `lossRecoveryPrice` haircut is never applied to anyone. Secondary impact: the re-request guard at `:263-271` is dead for the same reason, so a user can also stack new requests on top of a loss-affected receipt without claiming first.

### Likelihood Explanation
High conditional on the call ordering: any `stopEpochWithDuration(_lossAmount > 0)` while `pendingWithdraws > 0` triggers it, and that path exists precisely so managers can realize borrower shortfalls — a normal, expected operating mode, not an edge case. The attacker needs only an ordinary pending withdraw request opened during the epoch (KYC-passing lender — in scope); no privileged role, no reentrancy, no oracle manipulation. The window is every epoch stop that applies a loss. The mitigating factor is the unverified sequencing inside `IdleCDOEpochVariant.stopEpoch` noted above.

### Recommendation
Key the loss record to the epoch the pending receipts were actually stamped with. In `collectWithdrawFunds` the pending receipts were all created while `epochNumber` was still the pre-increment value, so store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or, cleaner, have the CDO call `collectWithdrawFunds` before the epoch-bumping `deposit`, or pass the request epoch explicitly from the CDO). Symmetrically, `requestWithdraw`'s guard at `:263-271` and `_claimLossAdjustedWithdrawRequest` should resolve the epoch through a single helper (`_lossEpochFor(_user)`) so the write key and the read key can never diverge. Add a regression test: request withdraw in epoch N → `stopEpochWithDuration(loss)` → assert `claimWithdrawRequest` pays `basis × lossRecoveryPrice / 1e18`, not `basis`.

### Proof of Concept
Foundry fork sketch (setup with a real `IdleCreditVault` + `IdleCDOEpochVariant` on mainnet pool currency, e.g. USDC):

```solidity
function test_LossHaircutBypassedByEpochMismatch() public {
    // === Epoch N is running; Alice is a KYC'd lender holding tranche tokens ===
    uint256 aliceDeposit = 1_000_000e6;
    depositAA(alice, aliceDeposit);                  // via IdleCDO depositAA

    // Alice opens a pending withdraw during epoch N
    // -> strategy.lastWithdrawRequest[alice] == N
    // -> strategy.withdrawsRequestsByEpoch[alice][N] == receiptAmt
    vm.prank(address(cdo));
    strategy.requestWithdraw(receiptAmt, alice, principalAmt);

    // Borrower repays short: manager calls stopEpochWithDuration(loss)
    // Internally: deposit(interest) bumps epochNumber to N+1 (isEpochRunning still true),
    // then collectWithdrawFunds(shortfall) sets lossRecoveryPriceByEpoch[N+1] < 1e18
    // and pendingWithdraws = 0, having pulled only the haircutted amount.
    vm.prank(manager);
    cdo.stopEpochWithDuration(duration, lossAmount, /*...*/);

    // Sanity: loss was booked under N+1, pointer still says N
    assertEq(strategy.lastWithdrawRequest(alice), N);
    assertEq(strategy.lossRecoveryPriceByEpoch(N), 0);        // <-- lookup will miss
    assertGt(strategy.lossRecoveryPriceByEpoch(N + 1), 0);

    // Alice claims through the CDO
    uint256 balBefore = usdc.balanceOf(alice);
    vm.prank(alice);
    cdo.claimWithdrawRequest();

    uint256 paid = usdc.balanceOf(alice) - balBefore;
    uint256 expectedHaircut = receiptAmt * strategy.lossRecoveryPriceByEpoch(N + 1) / 1e18;

    // BUG: paid == receiptAmt (full par), not the haircutted amount
    assertEq(paid, receiptAmt);
    assertGt(paid, expectedHaircut);

    // Second claimant Bob (or active LP value) is left short:
    // strategy balance is exhausted before the aggregate basis is honored.
}
```

The assertion that `lossRecoveryPriceByEpoch[N] == 0` while `lossRecoveryPriceByEpoch[N+1] > 0`, together with `paid == receiptAmt` at par, demonstrates both the pointer-miss and the waterfall violation. If instead the test shows the loss recorded under `N`, the CDO ordering is the opposite of assumed and this finding is invalid.
