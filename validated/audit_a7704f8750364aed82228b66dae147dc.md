## Analog Found: Single blocked recipient in `staking_contract`'s shared `distribution_pool` can permanently DoS all other stakers'/operators' withdrawals

### Title
A single recipient who disables direct coin transfers can permanently block `distribute()`/`distribute_internal()`, freezing commission and stake withdrawals for every other shareholder in the shared distribution pool - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::distribute_internal` withdraws all currently-inactive stake from the underlying stake pool in one shot and then pays out every shareholder in the contract's `distribution_pool` (staker's unlocked principal + any pending operator commissions from current/former operators) in a single atomic loop. If depositing to **any one** of those shareholders aborts, the entire transaction — including the withdrawal that already happened — reverts, and no shareholder in that pool can ever get paid until the offending recipient is fixed. Because any account can unilaterally call `aptos_account::set_allow_direct_coin_transfers(false)` on itself, a former or current operator (or any address that ends up as a distribution recipient) can trivially and permanently poison the shared pool for everyone else, exactly mirroring the "one bad strategy blocks the whole batched withdrawal" bug class from the report.

### Finding Description
`distribute_internal` withdraws the total withdrawable balance in one call and then loops over every shareholder of the `distribution_pool`, redeeming their shares and calling `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has not registered a `CoinStore<AptosCoin>` and has explicitly disabled `can_receive_direct_coin_transfers`: [2](#0-1) 

Any account can flip this flag on itself with no privilege at all: [3](#0-2) 

A `distribution_pool` accumulates multiple unrelated shareholders over time: the staker (for unlocked principal), the current operator (for commission), and any *former* operators after a `switch_operator` call, since unpaid commission for the old operator is recorded as a pending distribution in the same pool that continues to be used by the new operator: [4](#0-3) 

Because `distribute` is a permissionless entry function callable by anyone (`distribute(staker, operator)`), and it always tries to pay out the *entire* pending distribution set atomically, any former operator (who no longer has an active role in the contract, and is thus already "unprivileged" with respect to it) can call `aptos_account::set_allow_direct_coin_transfers(&self_signer, false)` on their own account before their pending commission is deposited, or simply never register a `CoinStore<AptosCoin>` and disable direct transfers. From that point on, every call to `distribute()` for that staker/operator pair will abort on that one shareholder's payout, in the middle of the shared loop, undoing the `stake::withdraw_with_cap` that already occurred in the same transaction. This blocks the staker's own principal withdrawal and the current operator's commission withdrawal indefinitely, since they are bundled into the same distribution call.

### Impact Explanation
This breaks the "withdrawal/commission accounting across active/inactive/commission state must preserve value and withdrawal rights" invariant: a single account with a stale, already-redeemed claim in the shared `distribution_pool` can indefinitely deny the staker and the current operator access to already-unlocked stake and commission, without needing any current role (owner/operator/voter/beneficiary) in the contract. The `MAXIMUM_PENDING_DISTRIBUTIONS` cap (20) referenced in `create_staking_contract_with_coins` shows the team was aware of griefing via too many pending recipients, but did not address griefing via a single recipient that refuses to accept the deposit.

### Likelihood Explanation
Likelihood is moderate-to-high: it only requires (1) a `switch_operator` call (a normal staker action) to leave a stale distribution entry for the old operator, and (2) the old operator calling `set_allow_direct_coin_transfers(false)` on their own account — a completely permissionless, self-serve action with no cost beyond gas. No attacker needs to hold any current role in the staking contract.

### Recommendation
- Skip/segregate a recipient's payout instead of aborting the whole loop in `distribute_internal` (e.g., catch failure to deposit and re-credit shares, or transfer via a coin type that always supports auto-registration), similar to the `indicesToSkip` mitigation suggested in the referenced report.
- Alternatively, force-register recipients for `AptosCoin` at the time they become eligible for a distribution (when `add_distribution`/`update_distribution_pool` first adds them as shareholders), rather than depending on `deposit_coins`' best-effort auto-registration during the payout loop.

### Proof of Concept
1. Staker creates a staking contract with `operator_1`, stake accrues rewards.
2. `operator_1` requests commission; some commission becomes pending in `distribution_pool`.
3. Staker calls `switch_operator(operator_1_address, operator_2_address, ...)`, leaving `operator_1` as a stale shareholder of the pool with unpaid commission: [4](#0-3) 
4. `operator_1` calls `aptos_account::set_allow_direct_coin_transfers(&operator_1_signer, false)` on their own account (no privilege required).
5. Any subsequent call to `staking_contract::distribute(staker, operator_2)` reaches the payout loop, attempts `aptos_account::deposit_coins(operator_1_address, ...)`, and aborts because `operator_1` has no registered `CoinStore<AptosCoin>` and disallows direct transfers.
6. The staker's principal withdrawal and `operator_2`'s commission — bundled in the same `distribution_pool` — can never be distributed while `operator_1`'s stale entry remains, permanently freezing funds that are already unlocked/inactive on the stake pool.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }

    #[view]
    /// Return true if `account` can receive direct transfers of coins that they have not explicitly registered to
    /// receive.
    ///
    /// By default, this returns true if an account has not explicitly set whether the can receive direct transfers.
    public fun can_receive_direct_coin_transfers(
        account: address
    ): bool acquires DirectTransferConfig {
        !exists<DirectTransferConfig>(account)
            || borrow_global<DirectTransferConfig>(account).allow_arbitrary_coin_transfers
    }
