### Title
Legacy Gateway `Message` signatures carry no expiry/deadline, enabling indefinite replay of captured requests - (File: core/services/gateway/api/message.go)

### Summary
The Chainlink Gateway's legacy `Message` signing scheme, defined in `core/services/gateway/api/message.go`, signs only `MessageId`, `Method`, `DonId`, `Receiver`, and `Payload` [1](#0-0) . There is no timestamp, nonce, or expiry field bound to the signature, and `Message.Validate()` performs only length/format checks and signer extraction — it never checks freshness [2](#0-1) . This mirrors the reported `_validateSignature` deadline issue: a validly signed request has no built-in "valid until"/"valid after" window, so once an unprivileged actor captures a signed message off the wire, it remains cryptographically valid forever.

### Finding Description
`gateway.ProcessRequest` is the externally-reachable entry point for legacy requests. It only calls `msg.Validate()` before dispatching to the handler — no timestamp/deadline check happens at this shared layer [3](#0-2) . Freshness enforcement is left entirely to individual handlers, and it is inconsistent:

- The WebAPI capabilities handler (`core/services/gateway/handlers/capabilities/handler.go`) does implement an ad-hoc, payload-specific staleness check using `payload.Timestamp` and `MaxAllowedMessageAgeSec`, comparing it against `time.Now()` [4](#0-3) . This is not part of the shared signature/message validation — it is a field the handler chooses to interpret from the JSON payload, and it is not authenticated as part of the cryptographic signature scope in the same enforced way the EIP-4337 deadline check would be. If a payload lacks or misrepresents this field it degrades silently (only checked when `payload.Timestamp` is present and decodable).
- Replay protection against re-submission of the same message within that freshness window is bounded only by an in-memory `savedCallbacks` map keyed by `MessageId`, which is deleted as soon as a response is delivered or pruned after `CallbackMaxAgeSec` [5](#0-4) . Once the entry is removed, a captured, still-signature-valid message (within `MaxAllowedMessageAgeSec`, default 2 minutes window is per-handler config) can be resubmitted and reprocessed as a fresh legacy trigger request, because nothing in `Message`/`Validate()` prevents re-verification of an already-used signature.
- Other legacy handlers, such as the dummy/test handler and `OutgoingConnectorHandler.HandleGatewayMessage`, call `Message.Validate()`/`ValidatedMessageFromReq` but perform no staleness or replay check at all [6](#0-5) [7](#0-6) .

Because the deadline/expiry enforcement is not a property of the signature itself (unlike, e.g., the `WorkflowMetadataHandler`'s JWT-based auth path, which does bind `exp`/`iat` claims to the signed token and rejects lifetimes exceeding a max duration [8](#0-7) ), any handler that omits the ad-hoc payload timestamp check inherits an unbounded-validity signature scheme.

### Impact Explanation
An unprivileged actor who observes or otherwise obtains a previously-signed legacy `Message` (e.g., via a compromised transport hop, logging, or a misbehaving intermediary) can resubmit it to the gateway indefinitely for handlers that don't independently enforce freshness, or after the per-handler callback/dedup window has expired for those that do. This can result in duplicate/unauthorized triggering of node-side capability executions (e.g., `web_api_trigger` workflow triggers), which is a job-run integrity violation — actions being executed again without the legitimate signer's renewed consent.

### Likelihood Explanation
Exploitation requires the attacker to first obtain a validly signed message (not to forge one), which limits likelihood to scenarios involving network observation, logging exposure, or handler bugs that leak raw signed payloads. However, because the freshness check is optional, payload-specific, and inconsistently applied across handlers (dummy handler and `OutgoingConnectorHandler` have none at all), the actual attack surface is broader than a single well-defended handler; likelihood is Medium, consistent with the reported severity of the analog bug.

### Recommendation
Bind an expiry (and optionally not-valid-before) timestamp directly into the signed `MessageBody` fields covered by `GetRawMessageBody` in `core/services/gateway/api/message.go`, and enforce the check centrally inside `Message.Validate()` (or in `gateway.ProcessRequest`/`ValidatedMessageFromReq`) rather than leaving it to each handler to optionally reimplement. Additionally, maintain a persistent (not just in-flight) short-lived nonce/message-ID cache to reject exact replays within the validity window across all legacy handlers, not only the WebAPI capabilities handler.

### Proof of Concept
1. A legitimate client signs and submits a `web_api_trigger` legacy `Message` with `payload.Timestamp = now` to the Gateway; `capabilities.handler.HandleLegacyUserMessage` accepts it and stores the callback in `savedCallbacks` keyed by `MessageId` [9](#0-8) .
2. The node responds, and the entry is deleted (or pruned once older than `CallbackMaxAgeSec`), but `payload.Timestamp` may still be within `MaxAllowedMessageAgeSec` since the two window configs are independent.
3. An observer who captured the original signed JSON payload (e.g., via proxy log, browser devtools, or shared infra) resubmits the identical `Message` (same signature, same `MessageId`) to `gateway.ProcessRequest`. `msg.Validate()` succeeds (the signature format/signer are still valid — signatures never expire), the staleness check in the handler still passes because it only checks `payload.Timestamp` age, and the request is processed again as a new trigger, invoking the node capability a second time without the original signer's fresh authorization.
