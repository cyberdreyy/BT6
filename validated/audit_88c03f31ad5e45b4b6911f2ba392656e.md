### Title
Malicious/misbehaving staking pool causes `#[callback]` deserialization panic, permanently freezing the lockup contract's `TransactionStatus::Busy` state — ([File: lockup/src/owner.rs, lockup/src/foundation.rs])

### Summary
Multiple flows in the lockup contract query the delegated staking pool with `#[callback]`-annotated cross-contract callbacks (`on_get_account_total_balance`, `on_get_account_unstaked_balance_to_withdraw_by_owner`, `on_get_account_staked_balance_to_unstake`, `on_get_account_unstaked_balance_to_withdraw`). These callbacks are only reachable if the promise to the staking pool succeeds and returns a well-formed `WrappedBalance`; the near-sdk `#[callback]` macro panics before the function body runs whenever the promise fails or returns malformed data. Because the code that resets `staking_information.status` back to `Idle` lives inside the function body (after the `#[callback]` extraction), a staking pool that fails or returns bad data on these specific view calls causes the lockup contract's staking status to remain `Busy` forever, exactly analogous to the referenced report: an external, "trusted" counterparty (there, the loan-repayment listener; here, the whitelisted staking pool) can break an assumption that a callback path always resolves cleanly, and there is no code path to recover.

### Finding Description
The owner deposits/stakes/unstakes/withdraws only when `assert_staking_pool_is_idle()` passes: [1](#0-0) 

Several flows set the state to `Busy` and only reset it to `Idle` from *inside* a `#[callback]`-consuming function body, e.g. `refresh_staking_pool_balance` → `on_get_account_total_balance`: [2](#0-1) [3](#0-2) 

and `withdraw_all_from_staking_pool` → `on_get_account_unstaked_balance_to_withdraw_by_owner`: [4](#0-3) [5](#0-4) 

The same pattern exists in the foundation termination path, where `termination_prepare_to_withdraw` queries the staking pool and hands the result to a `#[callback]`-consuming function: [6](#0-5) [7](#0-6) [8](#0-7) 

In near-sdk's `#[callback]` handling, when the underlying promise (`get_account_total_balance`, `get_account_unstaked_balance`, `get_account_staked_balance`) fails or returns bytes that can't be deserialized into `WrappedBalance`, the generated callback wrapper panics ("Callback computation failed") *before* the annotated function body executes. Every one of the above `Busy`→`Idle` reset statements is unreachable in that failure case, because it is located after the `#[callback]` parameter in the function body, not in a wrapper that always runs regardless of promise success (unlike the sibling callbacks such as `on_staking_pool_withdraw`, which use `is_promise_success()` and unconditionally reset status first).

The staking pool an owner selects only has to pass `is_whitelisted` at selection time: [9](#0-8) 
Nothing prevents the pool operator — who fully controls their own contract's code post-selection — from later making `get_account_total_balance`/`get_account_unstaked_balance`/`get_account_staked_balance` panic or return malformed output. This is the direct analog of the report's "malicious lender" that breaks an assumed-safe external callback: here it is a "malicious/misbehaving staking pool" that the lockup contract trusts to always answer these queries correctly, exactly matching the allowed analog category of "an account trusted as a pool ... versus the code and arguments that trust was granted for."

### Impact Explanation
Once `staking_information.status` is stuck at `Busy`, `assert_staking_pool_is_idle()` unconditionally panics for every subsequent `deposit_to_staking_pool`, `deposit_and_stake`, `stake`, `unstake`, `unstake_all`, `withdraw_from_staking_pool`, `withdraw_all_from_staking_pool`, `refresh_staking_pool_balance`, and `unselect_staking_pool` call: [1](#0-0) 
There is no owner-callable recovery path to force the status back to `Idle`. All NEAR delegated to that staking pool (and, in the foundation-termination case, the unvested deficit the foundation is entitled to recover) becomes permanently inaccessible — this is a "funds frozen" condition satisfying the High/Critical impact bar.

### Likelihood Explanation
The trigger only requires the already-selected staking pool operator to change/break the behavior of three specific view methods after being trusted — no owner or foundation privilege is needed by the attacker, and no redeploy of the lockup contract is required. This mirrors real-world risk since staking pool contracts are long-lived, upgradable, operator-controlled external contracts.

### Recommendation
Move the `self.set_staking_pool_status(TransactionStatus::Idle)` reset out of the `#[callback]`-gated function bodies and into a wrapper that always executes regardless of promise success/failure (mirroring the `is_promise_success()` pattern already used in `on_staking_pool_withdraw`, `on_staking_pool_unstake`, etc.), or replace the `#[callback]` parameter extraction with a manual `PromiseResult` check (`env::promise_result(0)`) so the status can be reset to `Idle` (and marked as a failed refresh) even when the pool's response is missing or malformed, for all of `on_get_account_total_balance`, `on_get_account_unstaked_balance_to_withdraw_by_owner`, `on_get_account_staked_balance_to_unstake`, and `on_get_account_unstaked_balance_to_withdraw`.

### Proof of Concept
1. Owner selects a staking pool `P` that passes the whitelist check via `select_staking_pool`.
2. Owner calls `refresh_staking_pool_balance()`; this sets `staking_information.status = Busy` and calls `ext_staking_pool::get_account_total_balance` on `P`, chained to `on_get_account_total_balance`.
3. The operator of `P` (who controls `P`'s code) has changed `get_account_total_balance` to panic or return a value that cannot deserialize into `WrappedBalance` (`U128`).
4. The near-sdk-generated `#[callback]` extraction for `on_get_account_total_balance` panics with "Callback computation failed" before the function body (and therefore `self.set_staking_pool_status(TransactionStatus::Idle)`) ever runs.
5. `staking_information.status` remains `Busy` forever; every subsequent staking-related call on the lockup contract (`stake`, `unstake`, `withdraw_from_staking_pool`, `unselect_staking_pool`, etc.) now panics in `assert_staking_pool_is_idle()`, permanently freezing all NEAR delegated to `P`.

use crate::*;
use near_sdk::{near_bindgen, PromiseOrValue, assert_self, is_promise_success};
use std::convert::Into;

#[near_bindgen]
impl LockupContract {
    /// Called after the request to get the current staked balance to unstake everything for vesting
    /// schedule termination.
    pub fn on_get_account_staked_balance_to_unstake(
        &mut self,
        #[callback] staked_balance: WrappedBalance,
    ) -> PromiseOrValue<bool> {
        assert_self();
        if staked_balance.0 > 0 {
            // Need to unstake
            env::log(
                format!(
                    "Termination Step: Unstaking {} from the staking pool @{}",
                    staked_balance.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );

            ext_staking_pool::unstake(
                staked_balance,
                &self
                    .staking_information
                    .as_ref()
                    .unwrap()
                    .staking_pool_account_id,
                NO_DEPOSIT,
                gas::staking_pool::UNSTAKE,
            )
            .then(
                ext_self_foundation::on_staking_pool_unstake_for_termination(
                    staked_balance,
                    &env::current_account_id(),
                    NO_DEPOSIT,
                    gas::foundation_callbacks::ON_STAKING_POOL_UNSTAKE_FOR_TERMINATION,
                ),
            )
            .into()
        } else {
            env::log(b"Termination Step: Nothing to unstake. Moving to the next status.");
            self.set_staking_pool_status(TransactionStatus::Idle);
            self.set_termination_status(TerminationStatus::EverythingUnstaked);
            PromiseOrValue::Value(true)
        }
    }
