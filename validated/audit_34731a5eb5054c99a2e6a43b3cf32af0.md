## Title
Stale confirmations from removed multisig members still count toward the confirmation threshold, allowing requests to execute below the live-member quorum - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
The multisig contracts (`multisig` and `multisig2`) let a member confirm a pending request, then later be removed from the member set without that confirmation being purged from the request's confirmation set. Because `confirm()` only compares the *size* of the stored confirmation set to `num_confirmations` — it never re-validates that every entry in that set is still a current member — a request can execute with a confirmation count that includes votes from accounts/keys that are no longer authorized members. This breaks the intended binding: "confirmations counted" should equal "confirmations from live members," but the code lets them diverge.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` reads the existing confirmation `HashSet` for a request and, once its length plus the new confirmation reaches `num_confirmations`, executes the request: [1](#0-0) 

`delete_member()` removes a member from `self.members`, and cleans up only the *requests that member itself authored* (`r.member == member`) plus their `num_requests_pk` entry — it never scans `self.confirmations` to strip that member's confirmation from *other* outstanding requests that member had merely confirmed (not authored): [2](#0-1) 

The same pattern exists in the legacy `multisig` contract: `DeleteKey` only removes requests where `r.signer_pk == pk` (requests authored by that key), leaving that key's confirmations on other pending requests intact: [3](#0-2) 

and `confirm()` there likewise just compares set length to `num_confirmations`: [4](#0-3) 

The binding that should hold is:
`count(confirmations for request R) == count(confirmations in R made by accounts/keys ∈ current self.members)`

Because member/key removal never re-validates or purges confirmations on requests it did not author, this equality is violated whenever a member who already confirmed some other pending request is later removed.

### Impact Explanation
This crosses an authorization/threshold boundary: a `MultiSigRequest` (e.g. a `Transfer` of contract funds, an `AddKey`/`AddMember` granting new access, or a `DeployContract` upgrading the account) can be executed with fewer *live* members having actually approved it than `num_confirmations` requires. For example, with `num_confirmations = 3` and members `{A, B, C, D}`:
1. `B` creates a `Transfer` request `R`.
2. `A` confirms `R` (`confirmations = {A}`, count 1).
3. The group later removes `A` (e.g. because `A`'s key was compromised) via `DeleteMember{A}`. `delete_member` only removes requests *authored* by `A`; `R` (authored by `B`) keeps `confirmations = {A}` untouched.
4. `C` confirms `R` → `{A, C}`, count 2.
5. `D` confirms `R` → count 3 ≥ `num_confirmations` → `R` executes.

Only `B` (implicitly, as the request author is not itself a confirmation) plus `C` and `D` are current members, yet the executed confirmation count includes the removed member `A`. The multisig request is executed with the *effective* live-member approval below the configured threshold, matching the rubric's Critical impact: "a multisig request executed below threshold."

### Likelihood Explanation
This does not require a redeploy, foundation, or social engineering — it is triggered by the routine, expected operational flow of removing/rotating a multisig member (which is explicitly one of the supported `MultiSigRequestAction` operations: `DeleteMember`/`DeleteKey`). Any multisig that ever revokes a compromised or departing member's access while other requests are pending is exposed; a malicious or compromised member simply needs to confirm one or more high-value pending requests before being removed for their stale approval to remain counted.

### Recommendation
When removing a member (`delete_member` in `multisig2`) or a key (`DeleteKey` in `multisig`), iterate over all entries in `self.confirmations` (not just requests authored by that member/key) and remove the departing member's/key's confirmation from every set. Alternatively, when computing whether a request has reached `num_confirmations` in `confirm()`, filter the stored confirmation set to only those entries that are still present in `self.members` (or, for legacy `multisig`, still valid access keys) before comparing against the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. As `B`, call `add_request` with a `Transfer` action to an attacker/receiver account (`R`).
3. As `A`, call `confirm(R)` → `confirmations(R) = {A}`.
4. Execute a separate, fully-confirmed request `DeleteMember{A}` to remove `A` from `self.members` (e.g. because `A` is later deemed compromised). Observe `confirmations(R)` is untouched (`delete_member` only cleans up requests where `r.member == A`).
5. As `C`, call `confirm(R)` → `confirmations(R) = {A, C}`, len 2.
6. As `D`, call `confirm(R)` → len 2 + 1 = 3 ≥ `num_confirmations` → `execute_request` fires the `Transfer`, even though only `B` (author), `C`, and `D` are current members — `A`'s stale confirmation was needed to hit the threshold. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
