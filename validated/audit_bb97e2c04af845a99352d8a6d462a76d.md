### Title
Vault-liquidity exhaustion makes `stopEpoch` permanently revertible, freezing all pending withdraw receipts - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` trusts the external ERC4626 vault to honor withdrawals whenever the share balance nominally covers the shortfall. If `vault.withdraw()` reverts for any reason other than insufficient share value — most notably an unprivileged attacker draining the vault's available liquidity (e.g., borrowing all idle assets out of a Morpho-style vault) — the hook reverts `StopEpochVaultLiquidityUnavailable`, which propagates through `IdleCDOEpochVariant.stopEpoch` and blocks epoch settlement entirely. All maturing `pendingWithdraws` receipts and tranche NAV stay frozen until the attacker restores vault liquidity.

### Finding Description
The CVE-2020-25647 bug class — consuming an external device's values with almost no bounds checking — maps directly onto `onStopEpoch`'s consumption of the external ERC4626 vault's guarantees. The code checks only the *economic* cover of the shares: [1](#0-0) 

If `shortfall <= _currentVaultAssets()`, the code assumes `vault.withdraw(shortfall, ...)` must succeed. That assumption is unsound for ERC4626 vaults backed by lending markets (the codebase's own fork tests use Morpho steakhouse USDC): share value can fully cover the withdrawal while vault cash liquidity is zero because all assets are lent out. The catch path deliberately reverts rather than defaulting, so the CDO's `stopEpoch` call fails atomically.

There is no fallback: `pendingWithdraws` can only be funded inside `stopEpoch`, `claimWithdrawRequest` gates on `epochNumber > lastWithdrawRequest` [2](#0-1) , and `epochNumber` only increments on a successful stop. Interest accrual for all tranche holders is likewise stalled because `totalInterestDueNow` is only realized at `stopEpoch` [3](#0-2) .

### Impact Explanation
An attacker who is merely "a user of the programmable borrower's ERC4626 vault" (an explicitly in-scope unprivileged role) can freeze 100% of `pendingWithdraws` plus the entire tranche NAV for as long as the underlying vault stays illiquid. By borrowing the vault's free liquidity on the external market and rolling the position, the attacker sustains the freeze indefinitely at the cost of ordinary market borrow interest — no pool funds are needed. This is temporary freezing of user funds at a scale equal to total pool TVL, satisfying the acceptance bar.

### Likelihood Explanation
Only a normal, honest `manager.stopEpoch()` call is needed to trigger the revert; the attacker pre-positions by draining vault liquidity beforehand (cheaply detectable on-chain and repeatable each time liquidity returns). No privileged role is required, no defaults occur, and no existing guard (`_onlyIdleCDO`, skim, default path, `isWalletAllowed`) mitigates it — the design explicitly chooses the retryable-revert path precisely in the covered-but-unwithdrawable case. Main residual uncertainty (not verified due to tool limits): whether `IdleCDOEpochVariant.stopEpoch` wraps `onStopEpoch` in a `try/catch` that swallows the revert and proceeds to a default path; the borrower's own comments ("should make stopEpoch retryable") indicate the revert propagates.

### Recommendation
Do not let an external vault's transferability failure hard-revert epoch settlement. Options: pre-flight a bounded `vault.maxWithdraw(address(this))` check and route the shortfall into the existing default/loss path (`stopEpochWithDuration`) so receipts are haircut rather than frozen; or cap the retry window and escalate to default after N failed stops; or have `onStopEpoch` return a status instead of reverting so the CDO can choose `finalizeDefault` deterministically.

### Proof of Concept
Foundry fork (pattern follows `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

1. Deploy per the test fixture with `STEAKHOUSE_USDC` (or any Morpho vault), `setIsInterestMinted(true)`, `depositAA(10_000e6)`, `startEpoch()`.
2. `deal(USDC, lp, ...)`; LP calls `cdoEpoch.requestWithdraw(...)` so `pendingWithdraws > 0`.
3. Attacker (unprivileged vault user) borrows all freely withdrawable liquidity out of the Morpho vault via its market, so `vault.maxWithdraw(address(programmableBorrower)) < shortfall` even though `convertToAssets(shares)` still covers it.
4. `vm.warp(epochEndDate + 1)`; `vm.prank(manager); cdoEpoch.stopEpoch(0, 0)` → reverts with `StopEpochVaultLiquidityUnavailable` [4](#0-3) .
5. Assert `epochNumber` unchanged, `pendingWithdraws` still > 0, `lp.claimWithdrawRequest()` reverts `NotAllowed`.
6. Repeat step 4 across later timestamps while attacker maintains the borrow → freeze persists; attacker repays the market loan to demonstrate attacker-controlled duration.
