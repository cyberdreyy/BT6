### Title
Unfunded instant-withdraw receipts can be claimed immediately, draining reserves set aside for other claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol](https://github.com/ThankGod76/idle-tranches--008/blob/main/contracts/strategies/idle/IdleCreditVault.sol))

### Summary

`IdleCreditVault.claimInstantWithdrawRequest` pays out `instantWithdrawsRequests[_user]` at par with no check that the receipt's backing funds have actually been collected from the borrower. The receipt is created during the buffer period (`requestInstantWithdraw`), but its funding only arrives when the next epoch starts (`collectInstantWithdrawFunds` → `startEpoch`). In between, the strategy contract already holds underlying tokens reserved for matured normal-withdraw claims (`collectWithdrawFunds` transfers at `stopEpoch`) and, after a default, the `defaultRecoveryReserve`. Because `_transferFundedClaim` pays out of the strategy's aggregate underlying balance rather than a bucket reserved for that specific receipt, an attacker can claim an *unfunded* instant receipt and get paid out of funds earmarked for other users — the credit-vault analog of a use-after-free: the "object" (receipt backing) is dereferenced before it is allocated/funded, or after it was freed for someone else.

### Finding Description

The request side is in `IdleCDOEpochVariant.requestWithdraw` (contracts/IdleCDOEpochVariant.sol:761-769): when `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, the CDO calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` during the buffer window after `stopEpoch`.

In `IdleCreditVault`:

```solidity
// requestInstantWithdraw (lines 356-375): mints receipt tokens and bumps
// instantWithdrawsRequests[_user] / pendingInstantWithdraws, but no funds move.
```

Funding arrives only later via `collectInstantWithdrawFunds` (lines 398-403), invoked by the CDO at `startEpoch`, which pulls `_amount` from the CDO and decrements `pendingInstantWithdraws`.

The claim path (lines 380-393):

```solidity
function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    _burn(_user, amount);
    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
}
```

There is no analog of the `epochNumber <= lastWithdrawRequest` maturity check used in `_claimFundedWithdrawRequest` (lines 326-328), and no verification that `pendingInstantWithdraws` was actually funded. The CDO-side guard (contracts/IdleCDOEpochVariant.sol:975-978) only checks `allowInstantWithdraw`, which is enabled precisely during the buffer — the same window in which the request is created and in which the receipt is still unfunded. The comment "Can be done when epoch is running as funds will get transferred from borrower when epoch starts" documents the intended invariant, but nothing enforces it.

Meanwhile the strategy's underlying balance at that moment legitimately contains:
- underlyings transferred by `collectWithdrawFunds` at `stopEpoch` backing the whole `withdrawsRequests`/`withdrawsRequestsByEpoch` set of matured claims (lines 411-429), and
- `defaultRecoveryReserve` backing post-default and defaulted-epoch claims (`_transferDefaultRecovery`, lines 760-784).

### Impact Explanation

An unprivileged, KYC-passing lender requests an instant withdraw during the buffer (a normal user action, triggered by an APR drop produced by honest manager `stopEpoch`), then calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` in the same window — before `startEpoch` and before `collectInstantWithdrawFunds`. The strategy transfers `amount` underlyings drawn from the balance reserved for other users' matured claims. Direct theft: the attacker receives funds that were never transferred in for their receipt, and honest claimants' later `claimWithdrawRequest` calls either underpay or revert on insufficient balance — permanent loss equal to the attacker's receipt size, bounded only by the reserves the strategy holds. Broken invariant: one receipt one payout, backed by its own funding (solvency of the claims reserve).

### Likelihood Explanation

Requires an APR decrease that enables instant withdrawals and an attacker holding tranche tokens — both ordinary conditions. The window is the entire buffer period between `stopEpoch` and `startEpoch` each such epoch. No privileged cooperation is needed; the sequence uses only attacker transactions interleaved with honest manager calls. The only mitigating uncertainty: whether the strategy holds nonzero reserves at that exact moment (it does whenever prior-epoch funded claims are unclaimed or a default reserve exists, which is common in steady state, since claims are pull-based and can sit unclaimed indefinitely per the "old requests can still be claimed" design).

### Recommendation

Track funded vs unfunded instant receipts and gate claims on funding, e.g.:
- Record instant receipts per epoch (already done via `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`); only allow `claimInstantWithdrawRequest` for receipts whose epoch has been funded through `collectInstantWithdrawFunds`, clearing `instantWithdrawClaimsByEpoch[epoch]` against a per-epoch funded flag.
- Alternatively, restrict `claimInstantWithdrawRequest` in `IdleCDOEpochVariant` to `isEpochRunning` (matching the documented intent), so a claim can never precede the `startEpoch` collection that funds it.
- Account a dedicated funded reserve for instant claims so `_transferFundedClaim` cannot pay them out of normal-withdraw or default-recovery reserves.

### Proof of Concept

Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `deal(defaultUnderlying, borrower, ...)`):

```solidity
function testInstantClaimBeforeFundingDrainsReserve() external {
    _useStandardEpochVariant();
    // victim deposits, requests normal withdraw in epoch N buffer
    uint256 victimTranche = _depositWithUser(victim, 100_000 * ONE_SCALE);
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(victim, victimTranche);
    // stopEpoch funds victim's receipt into the strategy
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    _stopCurrentEpochWithApr(initialProvidedApr - cdoEpoch.instantWithdrawAprDelta() - 1);
    // strategy now holds underlying reserved for victim's claim; APR dropped -> instant enabled

    // attacker deposits during buffer of epoch N+1 and requests instant withdraw
    uint256 atkTranche = _depositWithUser(attacker, 50_000 * ONE_SCALE);
    vm.prank(attacker);
    uint256 atkReceipt = cdoEpoch.requestWithdraw(atkTranche, address(AAtranche)); // routed to requestInstantWithdraw

    // BUG: claim succeeds BEFORE startEpoch / collectInstantWithdrawFunds fund the receipt
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, atkReceipt, "unfunded receipt paid");

    // victim's matured claim now reverts/underpays: reserve was stolen
    vm.prank(victim);
    vm.expectRevert(); // insufficient strategy balance
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertion: `pendingInstantWithdraws == atkReceipt` (still unfunded) at the moment the attacker's claim transfers underlying out, proving the payout came from reserves backing `withdrawsRequests`/`defaultRecoveryReserve` rather than the attacker's own funding.
