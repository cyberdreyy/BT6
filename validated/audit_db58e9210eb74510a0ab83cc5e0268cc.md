### Title
Session server's bare `&http.Server{}` has no timeouts/limits, allowing one job's connection to a shared session server to degrade service for other jobs' sessions - ([File: session/server.go])

### Summary
`NewServer` in `session/server.go` constructs `httpServer: &http.Server{}` with only `Handler` set, leaving `ReadTimeout`, `ReadHeaderTimeout`, `WriteTimeout`, `IdleTimeout`, and `MaxHeaderBytes` at Go's defaults (no timeout, 1MB header cap). Because one `session.Server`/`tlsListener` is shared by the runner process across all concurrently-running jobs (routed per-request via `sessionFinder`/`RequestURI` in `handleSessionRequest`), a slow-header or slow-body connection opened against one job's session endpoint can occupy a server goroutine indefinitely.

### Finding Description
`session/server.go:40-90` builds the shared HTTP server and starts it once via `Server.Start` → `s.httpServer.Serve(s.tlsListener)` [1](#0-0) , with the listener and handler shared by all jobs on that runner process; `handleSessionRequest` dispatches by looking up the session via `s.sessionFinder(r.RequestURI)` and delegating to `session.Handler().ServeHTTP` [2](#0-1) . Since `&http.Server{}` sets no `ReadHeaderTimeout`/`ReadTimeout`, Go's `net/http` will block indefinitely reading headers or body from a slow client, holding the accepted connection (and the goroutine `net/http` spawns per connection) open. Because `http.Server.Serve` spawns one goroutine per accepted connection and there is no bound (no `MaxHeaderBytes` override, no timeouts, no connection-count limiting middleware), enough slow/hanging connections directed at one job's endpoint can consume goroutines/file descriptors that are shared with all other jobs' session traffic on that runner instance.

However, for this to be a *bug worth flagging* as opposed to a generic "hardening" comment, the exploit needs a concrete privileged trigger and impact bound to the documented scope (single job's inputs causing shared cross-job denial). The attacker here is the job's own CI-triggered client connecting to its own session endpoint (e.g., via `session.Endpoint + "/exec"` websocket path used by the interactive terminal, or the trace/service proxy handlers in `session/session.go`) [3](#0-2) . A job author can open raw TCP/TLS connections to the advertised session server address (this is a network-reachable endpoint by design, gated only by the per-session bearer token check inside the handler, not by header size/time) and stall sending headers — the `Authorization` check occurs only after the request is fully parsed, so `net/http`'s header-reading state (with no deadline) is reached before any per-job authorization or session lookup runs.

On the persistence question, `waitForTerminal`'s cancellation path only calls `b.Session.Kill()` which is scoped to the terminal/interactive session object, not the underlying `net.Conn`/`http.Server` connection; there is no code found (in `session/server.go`, `session/session.go`, or `Server.Close`) that iterates and force-closes in-flight connections tied to a specific job when only that job is cancelled — `Server.Close()` closes the *entire* shared `httpServer`, not a per-job subset [4](#0-3) . So a stalled connection opened before cancellation is not proactively terminated by job cancellation; it will persist until the client disconnects, TCP times out at the OS level, or the whole session server is shut down (runner process exit) — genuinely outliving the individual job's lifecycle from the server's perspective.

### Impact Explanation
Impact is a shared-resource (goroutine/FD) exhaustion risk on the process-wide session HTTP server, potentially delaying or blocking session dispatch (interactive web terminal, proxy, trace endpoints) for other concurrently-running jobs on the same runner manager. This is a bounded availability degradation of a non-critical auxiliary feature (session server), not a sandbox escape, secret leak, or cross-project data access — it does not violate isolation of build/cache/artifact roots, does not leak masked values, and does not let one job impersonate another's session (auth token check still applies once the request is parsed).

### Likelihood Explanation
Preconditions are realistic: `session_server` must be enabled (default in most managed configurations to support interactive terminals/`kubectl exec`-like features), and the attacker only needs to be a normal pipeline author who can open a raw connection to the advertised session address and trickle bytes slowly — no special privileges beyond running a job are required. The number of connections needed to meaningfully starve the goroutine pool depends on OS-level FD/goroutine limits, which are typically high (thousands), so a single job alone is unlikely to cause practical exhaustion without opening many parallel slow connections; Go's default per-connection goroutine model tolerates a substantial number before real degradation. This makes the finding real but of limited severity/feasibility for a *single* job with default OS resource limits, though it is a genuine missing-hardening gap.

### Recommendation
Set explicit resource bounds on `s.httpServer` in `NewServer` (`session/server.go`): configure `ReadHeaderTimeout`, `ReadTimeout`, `WriteTimeout`, `IdleTimeout`, and a bounded `MaxHeaderBytes`. Additionally, consider tracking connections per session (via `http.Server.ConnState` or a wrapped listener) so that `Session.Kill()`/build cancellation can forcibly close the underlying `net.Conn` for that specific job's session, preventing stalled connections from outliving job cancellation.

### Proof of Concept
Go integration test in `session` package:
1. Start a `session.Server` with default `NewServer` config against a `sessionFinder` returning two distinct fake sessions (`sessionA`, `sessionB`), each with a trivial handler that responds `200 OK` immediately.
2. Open `N` (e.g., 200) raw TLS connections to the server's listen address, send `GET /session/<tokenA>/exec HTTP/1.1\r\n` for `sessionA` but withhold the terminating `\r\n\r\n` (stall headers) on all of them, without closing.
3. Concurrently, in a loop with a bounded deadline (e.g., 5s), perform a normal HTTP request to `sessionB`'s endpoint and assert it completes successfully within the deadline.
4. Assert: without `ReadHeaderTimeout` set, under sufficient concurrent stalled connections, `sessionB` requests either time out or measurably increase in latency, demonstrating that `sessionA`'s misbehaving client degrades `sessionB`'s dispatch — and that closing/cancelling `sessionA`'s owning build does not unblock the stalled connections (assert connections remain open post-cancellation via a probe on the server side, e.g., checking `net.Conn` is still readable/open).

```go
func (s *Server) handleSessionRequest(w http.ResponseWriter, r *http.Request) {
	logger := s.log.WithField("uri", r.RequestURI)
	logger.Debug("Processing session request")

	session := s.sessionFinder(r.RequestURI)
	if session == nil || session.Handler() == nil { //nolint:staticcheck
		logger.Error("Mux handler not found")
		http.NotFound(w, r)
		return
	}

	session.Handler().ServeHTTP(w, r)
}
```

```go
func (s *Server) Start() error {
	if s.httpServer == nil {
		return errors.New("http server not set")
	}

	err := s.httpServer.Serve(s.tlsListener)

	// ErrServerClosed is a legitimate error that should not cause failure
	if err == http.ErrServerClosed {
		return nil
	}
	return err
}
```
