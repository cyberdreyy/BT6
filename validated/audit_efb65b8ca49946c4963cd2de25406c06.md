### Title
Default recovery claim allows a third party to redirect a claimant's entire payout - ([File: contracts/DefaultDistributor.sol](contracts/DefaultDistributor.sol))

### Summary
`DefaultDistributor.claim` lets an unprivileged caller redirect the recovery payout for any tranche holder who has already approved the distributor. The function transfers the caller’s entire tranche balance into the distributor but sends the corresponding recovery proceeds to an attacker-controlled `_to` address. [1](#0-0) 

### Finding Description
The intended claim flow requires a holder to approve `trancheToken` for `DefaultDistributor` and then call `claim`. However, `claim(address _to)` uses `msg.sender` only as the source of tranche tokens and does not bind the payout recipient to `msg.sender`. [1](#0-0) 

Once a victim approves the distributor, an attacker can front-run or otherwise precede the victim’s claim and call `claim(attacker)`. The distributor consumes the victim’s entire tranche balance through `transferFrom`, calculates `trancheBal * rate / ONE_TRANCHE`, and transfers that underlying amount to the attacker. [2](#0-1) 

No privileged role is needed. `isActive` must be true, but activation is the normal owner-controlled claim phase rather than attacker-controlled behavior. [3](#0-2) 

### Impact Explanation
The attacker can steal 100% of an approved claimant’s recovery distribution. The victim permanently loses both the tranche balance used as the claim receipt and the underlying payout.

For example, if a victim holds `100e18` tranche tokens and the distributor rate is `2e6` underlying units per tranche token, the attacker receives `200e6` underlying units while the victim receives zero. This violates the “one receipt, one payout” and recovery-ownership invariants.

### Likelihood Explanation
Exploitation requires the victim to have granted the distributor an allowance for at least their tranche balance. That allowance is already the expected prerequisite for claiming because `claim` pulls the full balance with `transferFrom`. [4](#0-3) 

An EOA cannot atomically approve and claim in one transaction, so an attacker monitoring the mempool or permissionless claim flow can exploit the window between approval and claim. Contract wallets that combine the operations atomically are not exposed through this particular sequencing path.

### Recommendation
Remove the `_to` parameter and transfer proceeds to `msg.sender`, or require `_to == msg.sender`. Alternatively, require an owner-signed authorization that binds the recipient to the claim.

Also consider accepting an explicit tranche amount rather than claiming the caller’s entire balance, and clearing any consumed allowance consistently.

### Proof of Concept
Add this test to `test/foundry/DefaultDistributor.t.sol`. It uses the existing mainnet-fork setup and demonstrates the payout redirection.

```solidity
function testClaimPayoutCanBeRedirectedAfterVictimApproval() external {
    address victim = address(1);
    address attacker = address(0xbabe);

    IdleCDOTranche(address(tranche)).mint(victim, 100 * 1e18);

    distributor = new DefaultDistributor(
        address(underlying),
        address(tranche),
        address(this)
    );

    deal(address(underlying), address(distributor), 200 * 1e6);
    distributor.setIsActive(true);

    uint256 attackerUnderlyingBefore = underlying.balanceOf(attacker);

    vm.prank(victim);
    tranche.approve(address(distributor), tranche.balanceOf(victim));

    vm.prank(attacker);
    distributor.claim(attacker);

    assertEq(tranche.balanceOf(victim), 0);
    assertEq(tranche.balanceOf(address(distributor)), 100 * 1e18);
    assertEq(
        underlying.balanceOf(attacker) - attackerUnderlyingBefore,
        200 * 1e6
    );
    assertEq(underlying.balanceOf(victim), 0);
}
```
