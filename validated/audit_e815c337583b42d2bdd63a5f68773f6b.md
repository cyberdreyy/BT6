### Title
`getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` abort the entire multi-account response when a single matched account fails base58 encoding - ([File: rpc/src/rpc.rs])

### Summary
### Finding Description
`encode_account` in `rpc/src/rpc.rs` returns an `Err` when the requested account (or its sliced data) exceeds `MAX_BASE58_BYTES` (128 bytes) while `UiAccountEncoding::Binary` or `UiAccountEncoding::Base58` is requested: [1](#0-0) 

This function is used inside the non-`JsonParsed` branches of `get_program_accounts`, `get_token_accounts_by_owner`, and `get_token_accounts_by_delegate`, where the results of a program/owner/delegate scan (which can match an arbitrary, attacker-influenced number of accounts) are mapped through `encode_account` and collected via `.collect::<Result<Vec<_>>>()?`: [2](#0-1) [3](#0-2) [4](#0-3) 

Because `Result::collect` short-circuits on the first `Err`, if *any single account* among the (potentially large) set of matched accounts has data larger than 128 bytes (a very common size for real token/program accounts) and the caller used `binary`/`base58` encoding, the whole RPC call fails with an "Encoded binary (base 58) data should be less than 128 bytes" error — even though every other matched account could have been successfully encoded and returned. This is the same bug class as the reported `LiqFacet::removeLiq` issue: a batch/loop operation over multiple independent resources is entirely blocked by one resource being in a "bad" state (there, a paused vault; here, an over-sized account), instead of skipping/handling that one item and returning the rest.

By contrast, `get_multiple_accounts` and `get_account_info` do NOT have this problem for the same reason: they invoke `get_encoded_account`/`encode_account` per-pubkey but each result is already wrapped so failures don't abort sibling entries the way `get_program_accounts`/`get_token_accounts_by_owner`/`get_token_accounts_by_delegate` do via the eager `collect::<Result<Vec<_>>>()?` over the whole matched set.

### Impact Explanation
An unprivileged RPC client can supply a `programId`/`owner`/`delegate` filter (via `getProgramAccounts`, `getTokenAccountsByOwner`, or `getTokenAccountsByDelegate`) together with `binary`/`base58` encoding, and get zero results (an error) for a query that should return many valid accounts, as long as at least one matched account's data (or the encoded data-slice) exceeds 128 bytes. Since token/program account data commonly exceeds 128 bytes, this can make a legitimate scan return an error instead of the (correct) list of accounts, denying the client the wrong-yet-otherwise-successfully-encodable data for all other accounts in the same call. This is a functional-correctness/availability defect for a single unprivileged JSON-RPC call rather than a validator crash, so impact is Medium.

### Likelihood Explanation
Likelihood is high: this triggers deterministically whenever `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByDelegate` is called with `encoding: "base58"` or `"binary"` against a filter matching at least one account whose data (post data-slice) is >128 bytes — a very common real-world size for e.g. token-2022 accounts with extensions, or any custom program account. No special privileges or timing are required; a single, ordinary unprivileged RPC call is sufficient to observe the failure.

### Recommendation
In the non-`JsonParsed` encoding branch of `get_program_accounts`, `get_token_accounts_by_owner`, and `get_token_accounts_by_delegate`, avoid failing the entire response when one account cannot be base58-encoded. Either (a) fall back per-account to the same "error: data too large for bs58 encoding" sentinel string that `encode_bs58` already uses elsewhere instead of returning `Err` from `encode_account` in this bulk context, or (b) filter out/`Some`-wrap only the failing entries instead of using `collect::<Result<Vec<_>>>()?`, so one oversized account does not prevent the rest of the (correctly-encodable) results from being returned.

### Proof of Concept
1. Store several accounts owned by program `P`, where at least one account has data > 128 bytes.
2. Call `getProgramAccounts` (or `getTokenAccountsByOwner`/`getTokenAccountsByDelegate`) with `{"programId": "P", "config": {"encoding": "base58"}}` (or `"binary"`).
3. Observe: the RPC call returns a JSON-RPC error ("Encoded binary (base 58) data should be less than 128 bytes...") instead of an array containing the successfully-encodable accounts, because `.collect::<Result<Vec<_>>>()?` in `rpc/src/rpc.rs` (lines 656-666, 2170-2182, 2236-2248) aborts on the first `Err` from `encode_account` (lines 2575-2601).

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
