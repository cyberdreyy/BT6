### Title
Global contract deploy fee (`tokens_burnt`) is not rolled back when a later action in the same receipt fails, causing a balance-conservation mismatch - ([File: runtime/runtime/src/global_contracts.rs], [File: runtime/runtime/src/lib.rs])

### Summary
`action_deploy_global_contract` deducts `storage_cost` from the in-memory `account` and unconditionally adds it to `result.tokens_burnt` as soon as this single action succeeds [1](#0-0) . If a subsequent action in the same action receipt fails, the overall receipt result becomes `Err`, `set_account()` is skipped (so the balance deduction is never persisted) and `state_update.rollback()` discards trie writes [2](#0-1) , but the accumulated `result.tokens_burnt` value is still added into `tx_burnt_amount` unconditionally right after, independent of the `Ok`/`Err` branch [3](#0-2) .

### Finding Description
`action_deploy_global_contract` computes `storage_cost`, subtracts it from `account.amount()`, and adds it to `result.tokens_burnt` before the whole action-receipt processing loop has determined the final outcome of the receipt [4](#0-3) . It also pushes a `GlobalContractDistributionReceipt` into `result.new_receipts` via `initiate_distribution` [5](#0-4) .

Later in `lib.rs`, whether the mutated in-memory `account` is actually persisted to the trie is gated strictly on `result.result.is_ok()` [6](#0-5) , and the whole `state_update` is committed or rolled back based on the same condition [7](#0-6) . However, right after that branch, `tx_burnt_amount` is computed by unconditionally folding in `result.tokens_burnt` regardless of whether the receipt ultimately succeeded or failed [3](#0-2) .

An attacker can submit a batch action receipt containing `DeployGlobalContractAction` followed by a deterministically-failing action (e.g. a `Transfer` whose deposit exceeds the remaining balance, or any action producing `ActionErrorKind::LackBalanceForState`/`NotEnoughBalance`). The deploy action succeeds locally and increments `result.tokens_burnt`, but the following action fails and sets `result.result = Err(...)`. Because `set_account`/`state_update.commit` are skipped, the account's persisted balance is never actually reduced by `storage_cost`, and the code is never actually written to the global-contract trie key (since the distribution receipt is a downstream cross-shard receipt, not the code write itself — but even the nonce-increment `state_update.set()` calls made inside `initiate_distribution`/`increment_nonce` get discarded by `state_update.rollback()`). Yet the scalar `result.tokens_burnt` value survives in the `ActionResult` struct (a plain Rust value, unaffected by `state_update.rollback()`) and is folded into `tx_burnt_amount`/`stats.balance.tx_burnt_amount` regardless of the `Ok`/`Err` outcome.

This produces a balance-accounting mismatch: the chunk's aggregate "burnt tokens" statistic includes `storage_cost` tokens that were never actually removed from any account's persisted balance. This directly conflicts with NEAR's balance-conservation invariant (`incoming == outgoing + burnt`) checked elsewhere in the runtime, since the "burnt" side is inflated without a matching decrease in outgoing account balances.

### Impact Explanation
This is a value-conservation defect: tokens can be recorded as "burnt" in the runtime's balance bookkeeping without any actual balance deduction occurring in persisted state, for a global contract deploy whose payload is never durably stored. Depending on how strictly the runtime's balance checker enforces `incoming == outgoing + burnt`, this either (a) triggers a chunk-apply balance-mismatch failure/panic (shard-halting condition), or (b) silently corrupts the chunk's burnt-token accounting used for gas-fee/reward bookkeeping — both fall under "token inflation or loss" / "shard-halting panic" bounty categories.

### Likelihood Explanation
The precondition is fully reachable by an unprivileged account: any user can construct a transaction/receipt with a `DeployGlobalContractAction` followed by an action guaranteed to fail (e.g., insufficient balance for a subsequent transfer) inside the same action list. No special permissions, validator access, or non-standard gas/deposit values are required beyond standard fees to submit the deploy action, which is well within reach of a normal funded account. It is fully repeatable and deterministic.

### Recommendation
Do not accumulate `result.tokens_burnt` (or push `result.new_receipts`) for an action before the overall receipt's success is finalized, or explicitly reset/roll back `result.tokens_burnt` and drop any pending distribution receipts whenever the receipt ultimately fails (mirroring how `set_account`/`state_update.commit` are already gated on `result.result.is_ok()`). Concretely, either compute `tx_burnt_amount` conditionally (excluding `result.tokens_burnt` on the `Err` branch for actions whose state effects were rolled back), or have `action_deploy_global_contract`'s balance/fee mutation only take effect transactionally with the rest of the receipt's actions (e.g., accumulate a pending storage fee that is only committed to `result.tokens_burnt` once the whole receipt succeeds).

### Proof of Concept
Runtime apply-path integration test (in `runtime/runtime/src/tests/apply.rs` style):
1. Create an account with a funded balance sufficient to cover `DeployGlobalContractAction`'s `storage_cost` but insufficient to also cover a subsequent large `Transfer` action.
2. Build one `Receipt`/`ActionReceipt` whose `actions` list is `[DeployGlobalContractAction{code}, Transfer{deposit: huge_amount}]`.
3. Apply the receipt through `Runtime::apply`/`process_receipt`.
4. Assert:
   - The execution outcome status is `Failure` (due to the second action failing).
   - `tokens_burnt` in the execution outcome/`stats.balance.tx_burnt_amount` is `0` (currently it will be non-zero, equal to `storage_cost`).
   - No `GlobalContractDistribution` receipt appears among the produced outgoing receipts for that chunk.
   - The account's final persisted balance equals its balance before the receipt was applied (no deduction from the failed deploy fee).
