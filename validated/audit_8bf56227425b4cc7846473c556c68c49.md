### Title
Freshness-cutoff short-circuit in the pre-commit conflict guard lets a signer sign two conflicting blocks at the same height - ([File: stacks-signer/src/v0/signer.rs])

### Summary
When a signer reaches the pre-commit signing threshold for a block, it re-checks whether it has already signed a conflicting block at the same (or higher) Stacks height before producing its signature. That guard first filters conflicts by a local wall-clock "freshness cutoff" and only consults the node (`conflict_still_blocks`, `reorg_permit_stands`) for conflicts that pass this filter. If a previously-signed conflicting block's `last_endorsed` timestamp falls outside the freshness window — which happens whenever global consensus/acceptance is delayed past `tenure_last_block_proposal_timeout` — the conflict is dropped entirely from consideration without ever asking the node whether that earlier block is still live/canonical. This lets the signer sign a second, conflicting block at the same height even though the first one may still be perfectly capable of reaching the chain.

### Finding Description
The relevant logic is the `find` predicate in `handle_block_pre_commit`: [1](#0-0) 

```
let freshness_cutoff = get_epoch_time_secs().saturating_sub(
    self.proposal_config.tenure_last_block_proposal_timeout.as_secs(),
);
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(...)
}) { ... refuse to sign ... }
```

Because Rust's `&&` short-circuits, a conflict whose `last_endorsed` is not strictly newer than `freshness_cutoff` is discarded immediately — `reorg_permit_stands` and `conflict_still_blocks`, the only checks that actually ask the node whether the earlier signed block is still reachable/canonical, are never invoked for it. `get_signed_conflicts` deliberately returns every signed block at or above the target height regardless of tenure or state (Locally- or Globally-accepted), and computes `last_endorsed` as `MAX(signed_self, signed_group)`: [2](#0-1) 

The design intent, per the accompanying documentation, is that "a dead signature must not stall the chain restarting beneath it," i.e. staleness is supposed to represent a signature whose underlying block died in a reorg. But the actual staleness signal used is purely a time-since-last-endorsement measurement, not a liveness fact from the node. If the *first* block a signer signed is still live (its tenure's sortition is canonical and the node can still reach it) but simply hasn't yet accumulated 70% weight and been pushed — e.g., the proposing miner deliberately withholds broadcasting the aggregated signature set to the node, or gossip to a subset of signers is slow — the conflict record for it goes stale purely due to elapsed wall-clock time. At that point this signer will treat any *new* conflicting block proposed by the same miner at the same height as conflict-free and will sign it once its own pre-commit threshold is reached, per the `handle_block_pre_commit` sign path documented in `docs/signer-flows.md` sections 5.

This breaks the "one signed block per height" equality that the signer's local safety machinery is supposed to enforce (`BlockInfo::check_state`, `signerdb.rs:313-329`, guarantees state monotonicity per block record but says nothing about cross-block-at-same-height exclusivity — that exclusivity is *only* enforced by this freshness/conflict check): [3](#0-2) 

If enough signers independently experience the same staleness (because they all last-endorsed block A around the same time, and the miner waits out `tenure_last_block_proposal_timeout` before proposing conflicting block B), a supermajority-weight of signatures could end up split across two different blocks at the same height — an equivocation.

### Impact Explanation
This is a Critical-class issue per the rules ("a signer signing an invalid, non-canonical, or conflicting block"): a single signer can be induced, by a single miner controlling proposal timing plus normal gossip delay, to sign a second conflicting block at a height it already signed a block for, without any node-side liveness check on the first block. If replicated across enough signers by the same timing, this produces two independently-signable blocks at the same chain height — a chain split / equivocation, which is exactly the safety property the pre-commit conflict guard exists to prevent.

### Likelihood Explanation
Requires only:
- A single miner that controls when to submit block A's aggregated signature set to the stacks-node (can be delayed indefinitely on the miner's own initiative), and
- Ordinary network/gossip delay, or the miner choosing to wait past `self.proposal_config.tenure_last_block_proposal_timeout`,
before proposing a conflicting block B at the same height.

No majority of signers, no other signer's key, and no auth_token/local access are needed — the vulnerable signer acts unilaterally based on its own local timestamp bookkeeping. The main uncertain condition is exact reproducibility across "enough" signers simultaneously reaching the same staleness threshold; I was not able to fully verify from the index whether `mark_globally_accepted`/`mark_locally_accepted` refresh `signed_group`/`signed_self` in a way that could extend `last_endorsed` (I could not load `stacks-signer/src/v0/signer_state.rs`/relevant `signerdb.rs` mark_* functions in this pass to double check), so the timing window's exact width and refresh conditions should be independently confirmed.

### Recommendation
Do not let the local freshness-cutoff filter fully suppress the liveness check. At minimum, always invoke `conflict_still_blocks` (a node-derived, ground-truth liveness check) for any conflict whose underlying block has not been observed as dead (e.g., via `GloballyRejected` state or a confirmed orphaned sortition), regardless of how long ago it was last endorsed — reserve the timestamp-based short-circuit only for cost optimization once the node-side liveness question has been definitively answered "not blocking" at least once, or track explicit death events (reorg orphaning) instead of elapsed time as the staleness signal.

### Proof of Concept
1. Miner proposes block A at height H. Enough signers (including the victim signer S) pre-commit and S reaches the local pre-commit threshold, calls `mark_locally_accepted`, and signs A (`handle_block_pre_commit`, sign branch).
2. Miner intentionally withholds pushing the aggregated block A to the stacks-node (never broadcasts `BlockPushed`/doesn't submit the signed block), so S's node never reports `NewBlock`, and A never reaches `GloballyAccepted` for S.
3. Miner waits longer than `proposal_config.tenure_last_block_proposal_timeout` since S's `signed_self` timestamp on A.
4. Miner proposes a new, conflicting block B at the same height H (e.g., a re-proposed tenure-start block). S validates B, pre-commits, and reaches the pre-commit threshold for B.
5. In `handle_block_pre_commit` for B, `get_signed_conflicts` returns A as a conflict, but `conflict.last_endorsed <= freshness_cutoff` (per step 3), so the predicate in `stacks-signer/src/v0/signer.rs:1403-1411` short-circuits to `false` without ever calling `conflict_still_blocks` to ask the node whether A is still reachable.
6. S proceeds to sign B (`handle_block_pre_commit` sign branch), producing two distinct signer signatures from S over two conflicting blocks A and B at the same height H.

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
