### Title
Fee-on-transfer underlying can force a repaying borrower into default - (File: `contracts/IdleCDOEpochVariant.sol`)

### Summary
`IdleCDOEpochVariant.stopEpoch` assumes that `transferFrom` delivers the full requested repayment. With a fee-on-transfer underlying, the CDO receives less than the amount it subsequently distributes as pending withdrawals, fees, principal, and interest. The later transfer can therefore fail even though the borrower approved and paid the full nominal amount, causing the catch block to treat the repayment as a borrower default.

### Finding Description
During epoch settlement, the CDO calls the external self-call `getFundsFromBorrower` for the nominal amount owed. [1](#0-0) 

`getFundsFromBorrower` performs only a `transferFrom` and does not verify the actual balance delta received by the CDO. [2](#0-1) 

The CDO then treats the nominal amount as fully received. For a closed pool it transfers the full borrowed principal to the strategy, while pending withdrawals are separately collected by `IdleCreditVault.collectWithdrawFunds`. [3](#0-2) [4](#0-3) 

The strategy also assumes that pulling `_amount` delivers `_amount`: it transfers the underlying and mints the same nominal number of strategy tokens. [5](#0-4) 

If the underlying charges a transfer fee, the CDO's actual balance is lower than its accounting basis. Once the settlement flow attempts to distribute the full nominal principal, withdrawals, fees, and interest, an outgoing transfer can revert for insufficient balance. The enclosing `catch` then invokes `_handleBorrowerDefault`, even though the borrower supplied the entire amount requested. [6](#0-5) 

### Impact Explanation
A repaying borrower can be marked defaulted because the token's transfer fee creates a shortfall between the amount pulled and the amount accounted for.

For a requested repayment of `P + I`, a transfer fee `f` leaves only `P + I - f` in the CDO. The settlement path still attempts to distribute obligations totaling `P + I`, so the final `f` cannot be sourced from the repayment. In the close-pool path, the CDO first attempts to move the full `P` principal to the strategy. [3](#0-2) 

The resulting default can socialize the artificially created shortfall across tranche holders and pending withdrawal receipts through the default-recovery flow.

### Likelihood Explanation
The issue is conditional on a credit vault being deployed with an underlying token that charges a transfer fee or burns tokens during transfer. The escrow and settlement code does not restrict the underlying to feeless ERC-20s; `IdleCreditVaultWriteOffEscrow.initialize` simply binds the token returned by the CDO. [7](#0-6) 

No malicious privileged role is required. An honest borrower can approve and pay the exact amount requested while the protocol records a default solely because less than that nominal amount arrived.

### Recommendation
Settlement should account for the amount actually received rather than the nominal `transferFrom` argument.

At minimum:

- Measure `balanceOf(address(this))` before and after `getFundsFromBorrower`.
- Use the received delta for withdrawal funding, fees, principal return, and interest accounting.
- Revert before state changes if the received amount is below the required amount, rather than entering the borrower-default path.
- Preferably reject fee-on-transfer or deflationary underlying tokens during credit-vault deployment.

The same actual-received pattern is already used in `_deposit`, which calculates minted tranche shares from the observed balance delta. [8](#0-7) 

### Proof of Concept
The following Foundry PoC pattern demonstrates the broken invariant: the borrower pays the requested nominal amount, the token takes a fee, and settlement still enters the default path.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "openzeppelin-contracts/token/ERC20/ERC20.sol";

contract FeeOnTransferToken is ERC20 {
    uint256 public constant FEE_BPS = 100; // 1%

    constructor() ERC20("FeeToken", "FEE") {
        _mint(msg.sender, 100_000_000e18);
    }

    function _transfer(
        address from,
        address to,
        uint256 amount
    ) internal override {
        uint256 fee = amount * FEE_BPS / 10_000;
        super._transfer(from, to, amount - fee);
        super._transfer(from, address(0xdead), fee);
    }
}

contract FeeOnTransferDefaultPoC is Test {
    FeeOnTransferToken internal token;

    // Existing repo fixture/helper that deploys IdleCDOEpochVariant,
    // IdleCreditVault, tranches, borrower, owner and manager using
    // the supplied token as the vault underlying.
    IdleCDOEpochVariant internal cdo;
    IdleCreditVault internal strategy;
    IdleCDOTranche internal aaTranche;

    address internal owner = address(0x100);
    address internal lender = address(0x200);
    address internal borrower = address(0x300);

    function setUp() public {
        token = new FeeOnTransferToken();

        // Deploy the credit-vault fixture with token as `token`.
        // The fixture should configure:
        // - borrower
        // - AA/BB tranches
        // - epoch duration and buffer
        // - lender KYC/allowance
        (cdo, strategy, aaTranche) = _deployCreditVaultFixture(
            address(token),
            borrower,
            owner
        );

        uint256 principal = 1_000_000e18;

        token.transfer(lender, principal);
        token.transfer(borrower, principal * 2);

        vm.startPrank(lender);
        token.approve(address(cdo), principal);
        cdo.depositAA(principal);
        vm.stopPrank();
    }

    function testRepaymentWithTransferFeeStillDefaults() public {
        // Start an epoch and route principal to the honest borrower
        // through the repo's existing fixture.
        _startEpochWithPrincipal();

        uint256 requestedRepayment = _repaymentRequestedByPool();

        // Honest borrower approves exactly what the protocol requests.
        vm.prank(borrower);
        token.approve(address(cdo), requestedRepayment);

        // _interest == 1 is the protocol's close-pool / request-all-funds path.
        vm.prank(owner);
        cdo.stopEpoch(0, 1);

        // The transfer fee means the CDO receives less than the nominal amount.
        // Settlement still attempts to distribute the full nominal amount and
        // falls into _handleBorrowerDefault.
        assertTrue(cdo.defaulted());
    }
}
```

The deterministic shortfall is:

```text
actualReceived = requestedRepayment - transferFee
requiredForSettlement = requestedRepayment
shortfall = transferFee
```

Therefore any positive transfer fee makes the repayment insolvent relative to the settlement accounting when the full repayment must be distributed.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;

      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
