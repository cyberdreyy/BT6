### Title
Attached NEAR deposit becomes permanently stuck in `MultisigFactory` when the deployed multisig account creation fails - ([File: multisig-factory/src/lib.rs])

### Summary
`MultisigFactory::create` is a `#[payable]` function that forwards the caller's attached deposit to a brand-new sub-account in the same promise batch that creates the account, deploys the multisig contract, and calls its `new` initializer. Unlike the sibling `staking-pool-factory` contract, which implements an explicit `on_staking_pool_create` callback to detect batch failure and refund the depositor, `MultisigFactory::create` has no `.then(...)` callback at all. If the batched actions fail (e.g. the sub-account name already exists, or the deployed contract's `new` call panics), the attached NEAR is not delivered to the intended multisig account, is refunded by the protocol back to the `MultisigFactory` contract's own balance, and then has no code path to ever leave the factory. This mirrors the reported BathBuddy issue where a contract that can receive value has no logic to release it back out.

### Finding Description
`create` immediately spends the attached deposit inside a single promise batch with no failure handling: [1](#0-0) 

Compare this to `StakingPoolFactory::create_staking_pool`, which attaches an explicit callback, `on_staking_pool_create`, that checks `is_promise_success()` and, on failure, actively transfers the deposit back to `predecessor_account_id`: [2](#0-1) 

Because `create`'s batch (`create_account` → `deploy_contract` → `transfer` → `function_call("new", ...)`) is a single atomic receipt, a failure in any one action (e.g. the target account name is already taken, causing `create_account` to fail, or the deployed multisig2 contract's `new` init panicking on invalid `members`/`num_confirmations`) causes the whole receipt including the `transfer` to fail.     /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
