## Title
Asymmetric weight accounting between `BlockResponse::Accepted` and `BlockResponse::Rejected` lets a single signer's weight be double-counted into both `total_weight_approved` and `total_weight_rejected` for the same block, corrupting the coordinator's accept/reject decision — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` (the block-signing coordinator's StackerDB message handler) tallies per-block signer weight in two independent counters, `total_weight_approved` and `total_weight_rejected`, gated by two *different* dedup sets (`gathered_signatures` for acceptance, `responded_signers` for both). Because the acceptance path checks `gathered_signatures` instead of `responded_signers`, a signer who first rejects a block and later accepts the *same* block (a sequence the signer's own state machine explicitly permits via re-evaluation of "re-evaluable" reject reasons) has its weight added to `total_weight_rejected` once, and then added to `total_weight_approved` again later, with no decrement of the former. This breaks the implicit invariant `total_weight_approved + total_weight_rejected <= total_weight` that `signer_coordinator.rs`'s decision logic depends on, allowing a single non-majority signer to corrupt the block acceptance/rejection accounting and the per-txid "problematic" weight tally used to permanently ban transactions.

### Finding Description
In `handle_block_pre_commit`/`store_and_process_block_signature`-equivalent node-side logic (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`), when a `BlockAccepted` message arrives: [1](#0-0) 

the code gates the `total_weight_approved` increment on `!block.gathered_signatures.contains_key(&slot_id)`, then unconditionally inserts `slot_id` into **both** `gathered_signatures` and `responded_signers`.

When a `BlockResponse::Rejected` message arrives: [2](#0-1) 

the code gates the `total_weight_rejected` increment on `block.responded_signers.insert(slot_id)` returning `true` (i.e., first time seen in `responded_signers`).

This produces an asymmetry:
- **Accept-after-reject**: signer rejects first → `responded_signers` now contains their `slot_id`, `total_weight_rejected += weight`. They later send an acceptance for the *same* `signer_signature_hash` → since `gathered_signatures` does **not** yet contain their `slot_id` (only `responded_signers` does), the acceptance branch's guard passes and `total_weight_approved += weight` as well. The weight is now counted in **both** totals, permanently, with no removal from `total_weight_rejected`.
- **Reject-after-accept** (the opposite order) is correctly protected: the rejection branch's guard is `responded_signers.insert(slot_id)`, which was already set true during the earlier acceptance, so the second, contradicting rejection message is silently dropped and does not inflate `total_weight_rejected`.

The reject-then-accept sequence for the *same block* is not a theoretical corner case: the signer's own proposal-arrival logic (`should_reevaluate_reject_reason`, documented in `docs/signer-flows.md` section 3) explicitly allows a previously-rejected block to be re-evaluated and subsequently accepted when the reject reason is judged re-evaluable, without requiring a new block hash. A single one-slot signer can also trigger this deliberately (or simply by having its validator flip verdicts on retried validation) by broadcasting a `Rejected` response and later a valid `Accepted` signature for the identical `signer_signature_hash`.

This corrupted `total_weight_rejected`/`total_weight_approved` state is then consumed directly by the coordinator's decision loop: [3](#0-2) 

which checks rejection-crosses-blocking-minority *before* checking acceptance-crosses-threshold. Because `total_weight_rejected` for the flip-flopping signer is never decremented, it remains available to (together with genuinely rejecting signers) push `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`, causing the coordinator to declare `SignersRejected` even though the same signer's weight has also (correctly) been recorded as an acceptance and even if a true 70%-weight quorum of distinct signers has actually accepted the block.

The same stale weight additionally pollutes the per-txid "problematic transaction" weight tally, which is used to *permanently* ban transactions from all future blocks once `info.problematic_weight > blocking_minority`: [4](#0-3) 

A signer's earlier "problematic transaction" rejection vote is never retracted even after that signer subsequently signs a block containing the same transaction, so its weight keeps counting toward permanently excluding that transaction.

### Impact Explanation
This is a liveness wedge triggerable by a single, non-majority signer (or gossip-observed message pair) without requiring collusion of a majority of signers. It corrupts the coordinator's accounting invariant (`approved + rejected <= total_weight`), can cause the node to prematurely and incorrectly conclude `SignersRejected` for a block that a genuine supermajority actually accepted, and can permanently ban legitimate transactions (`permanently_excluded_txids`) based on stale, unretracted "problematic" weight from a signer who has since reconsidered. This matches the "High" impact bar: a wedge that stalls legitimate block/transaction processing based on a stale, unretracted vote, achievable by one signer.

### Likelihood Explanation
Reaching the reject→accept-for-the-same-block sequence does not require a majority or any privileged access — it only requires one signer (or an observer replaying that signer's two legitimate StackerDB messages) to have first rejected and then, per the existing "re-evaluable reject reason" logic, accepted the identical block. The severity of the resulting miscount scales with that signer's weight and how close the pool of honest rejections is to the 30% blocking minority, so the practical trigger window depends on network conditions, but the underlying accounting defect is deterministic and always present.

### Recommendation
Make the acceptance-weight bookkeeping symmetric with the rejection-weight bookkeeping: gate the `total_weight_approved` increment on the same `responded_signers` set used by the rejection path (or maintain a single per-slot "resolved" set with an explicit terminal vote per signer), and/or explicitly decrement/clear a signer's prior `total_weight_rejected`/`failed_txids` contribution when a later, valid acceptance for the same `signer_signature_hash` arrives from that signer. At minimum, ensure a signer's weight can only ever be counted in exactly one of `total_weight_approved`/`total_weight_rejected` for a given block at any time, and that per-txid "problematic" weight is revocable when the same signer subsequently signs a block containing that transaction.

### Proof of Concept
1. A miner proposes block `B` (`signer_signature_hash = h`).
2. Signer `S` (any single signer in the reward set) sends `BlockResponse::Rejected(h, ...)` (e.g., a re-evaluable rejection reason). The node's `StackerDBListener` inserts `S`'s `slot_id` into `responded_signers` and adds `S.weight` to `block.total_weight_rejected`.
3. `S` later re-evaluates and sends `BlockResponse::Accepted(h, signature)` for the same `h` (permitted per `should_reevaluate_reject_reason`). The acceptance handler checks `gathered_signatures`, which does not contain `S`'s `slot_id`, so it adds `S.weight` to `block.total_weight_approved` as well — `S.weight` is now counted in both totals.
4. If enough additional honest signers reject `B` such that `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (aided by `S`'s stale contribution), `signer_coordinator.rs`'s `wait_for_signatures`-style loop returns `Err(SignersRejected)` for `B`, even though `total_weight_approved` may independently have also reached `weight_threshold` from a genuine distinct-signer quorum — an inconsistent, wedged outcome directly attributable to one signer's un-retracted rejection.
