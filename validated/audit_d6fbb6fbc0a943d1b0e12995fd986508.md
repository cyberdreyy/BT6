### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, letting a request execute below the real live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges requests that were *originally submitted* by the removed member; it never scans other pending requests' confirmation sets to strip out confirmations that the removed member previously cast on requests submitted by someone else. `confirm()` simply counts `confirmations.len()` against `self.num_confirmations` without re-validating that every confirming identity in the set is still a current member. This is the same class of bug as the Blend flash-loan report: a security-relevant check (membership/eligibility) is correctly enforced on one code path (`current_member()` for new confirmations) but silently skipped on another path (the confirmation count used to trigger execution), letting a stale credential that should no longer be trusted still be spent.

### Finding Description
`confirm()` counts confirmations purely by set size: [1](#0-0) 

The only place membership is validated is when a *new* confirmation is being added, via `current_member()`, which checks `self.members.contains(&member)`: [2](#0-1) 

But `delete_member` only removes requests where the *deleted member is the original submitter* (`r.member == member`). It does not iterate `self.confirmations` to drop the deleted member's confirmation from *other* members' still-pending requests: [3](#0-2) 

The equality this breaks is: `confirmations recorded in state == confirmations from members currently entitled to confirm`. Once a member is removed, any confirmation they previously placed on someone else's pending request remains in `self.confirmations`, silently retained as "live" weight even though that identity no longer has multisig authority. If `confirmations.len() + 1 >= num_confirmations` is later reached using new confirmations from other live members plus this stale one, `execute_request` runs a transaction (transfer, add key, deploy contract, etc.) authorized by fewer *currently trusted* signers than `num_confirmations` mandates.

### Impact Explanation
This falls under the Critical bucket: "a multisig request executed below threshold." An attacker scenario: a member who is later removed (e.g., a compromised/departing member) confirms a `Transfer` request to an attacker-controlled account before removal, but the request doesn't yet reach threshold. The member is then removed via `DeleteMember` (a legitimate governance action). The stale confirmation is never cleaned up. Any remaining live member(s) confirming afterward can push the confirmation count to `num_confirmations` and trigger execution, even though only `num_confirmations - 1` currently-live members actually authorized it. Funds can move (or keys/contract deployments can be authorized) with an authorization threshold that was never actually met by trusted members.

### Likelihood Explanation
Removing a member from an active multisig (e.g., because that member's key was compromised or they left) while they have outstanding confirmations on other pending requests is a normal and expected sequence — no special conditions are required beyond that ordering. `add_request` allows requests to remain pending, unconfirmed, for extended periods (limited only by `REQUEST_COOLDOWN`/`active_requests_limit`), so there's ample opportunity for a member's confirmation to be "in flight" when they are removed. This does not require any privileged action beyond ordinary multisig governance (deleting a member is already a normal multisig-approved action), and no attacker key theft, redeploy, or social engineering is needed to trigger the state divergence — only ordinary operational timing.

### Recommendation
In `delete_member`, iterate all pending requests' confirmation sets and remove the deleted member's identity from every one of them (not just requests they submitted), or alternatively, when counting confirmations in `confirm()`, filter `confirmations` to only those entries still contained in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `D` calls `add_request_and_confirm(request_to_transfer_to_attacker)` submitted with `receiver_id` = attacker's account → confirmations = `{D}`.
3. `A` calls `confirm(request_id)` → confirmations = `{D, A}` (2 of 3, not yet executed).
4. Members execute a separate, properly-authorized `DeleteMember { member: D }` request (3 confirmations, normal governance) — `delete_member` runs but since `r.member == D` is false for the transfer request (it was authored by D though — note: if D is the request's *author*, this specific example would actually get cleaned up by the existing filter; to bypass that, have `B` submit the transfer request instead and have `D` merely confirm it, not author it).
   - Corrected: `B` calls `add_request(transfer_request)` → confirmations = `{}`.
   - `D` calls `confirm(request_id)` → confirmations = `{D}`.
   - `A` calls `confirm(request_id)` → confirmations = `{D, A}`.
   - Members remove `D` via `DeleteMember` (since request's `r.member == B`, not `D`, the transfer request and its confirmation set including `D` are untouched).
5. `C` (still a live member) calls `confirm(request_id)` → confirmations count becomes 3 (`D` (stale/removed), `A`, `C`) ≥ `num_confirmations` (3) → `execute_request` fires, transferring funds to the attacker's account, even though `D`'s authorization should no longer count. [1](#0-0) [3](#0-2)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
