### Title
Instant-withdraw claim clears the aggregate receipt but not the per-epoch claim basis, double-counting already-paid claims in default recovery - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the user's receipt and zeroes `instantWithdrawsRequests[_user]`, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` nor decrements `instantWithdrawClaimsByEpoch[epoch]`. This is the same bug class as the BloomPool partial match: one of two coupled accounting legs is decremented while the other is left intact. When a later default finalization runs while `pendingInstantWithdraws != 0`, the already-claimed amounts are counted again both as outstanding claim basis (`defaultPendingClaimBasis`) and as prefunded reserve (`_defaultPrefundedInstantReserve`), inflating `defaultRecoveryPrice` beyond what the strategy actually holds. Later claimants (tranche holders or honest withdrawers) are then left unpaid — an over-allocation/insolvency identical in effect to the double-filled borrower funds in the report. [1](#0-0) 

### Finding Description
On request, three counters are incremented together: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and `instantWithdrawClaimsByEpoch[epoch]` (plus `pendingInstantWithdraws`). [2](#0-1) 

On claim, only the per-user aggregate is cleared; the two per-epoch entries persist permanently:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [3](#0-2) 

Funding is decoupled from claiming: `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` by whatever amount was actually collected, so a partial collection leaves `pendingInstantWithdraws > 0` while some users have already been paid. [4](#0-3) 

At `finalizeDefaultRecovery`, the stale entries corrupt both sides of the recovery ratio:

- `defaultPendingClaimBasis` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` — including already-claimed amounts — to the basis that gets haircut. [5](#0-4) 
- `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epoch] - pendingInstantWithdraws` as "already-held underlying reserved for those claims," but the paid-out portion is no longer held by the strategy — it was transferred to claimants. This phantom reserve is added to `defaultRecoveryReserve`/`reserveAmount`. [6](#0-5) 

The result: `recoveryPrice = reserveAmount / totalBasis` is computed over a reserve that partially doesn't exist and a basis that double-counts paid claims, so `defaultRecoveryPrice` and `defaultRecoveryReserve` are over-stated. `_transferDefaultRecovery` will happily pay claimants at the inflated price until the real balance runs out; the last claimants' transfers then revert or drain value belonging to active tranche holders. [7](#0-6) 

Additionally, a user who claimed then re-requested in the same epoch would hit `instantWithdrawsRequests[_user] -= claimBasis` underflow/double-subtraction in `_claimDefaultedInstantWithdrawRequest`, because the per-epoch entry was never cleared while the aggregate was. [8](#0-7) 

### Impact Explanation
Direct insolvency/permanent freezing of recovery funds: defaulted-epoch claimants and active AA/BB holders are promised `defaultRecoveryReserve` at `defaultRecoveryPrice`, but part of that reserve was already paid out. Early claimants (an attacker can be one — an ordinary tranche-token holder requesting an instant withdraw, then claiming after partial collection) extract the real funds; later honest claimants find the reserve exhausted and their claims revert. The loss equals the sum of instant receipts claimed while `pendingInstantWithdraws` was still non-zero for the default epoch — quantifiable as `claimed` × `defaultRecoveryPrice` of phantom payouts.

### Likelihood Explanation
Requires an unprivileged sequence only: a lender requests an instant withdrawal during buffer, `startEpoch`/queue collection funds the instant queue only partially (prefunded/partial-liquidity mode explicitly contemplated by `_defaultPrefundedInstantReserve`'s own docs), the user claims, then the epoch defaults. All attacker actions (deposit, `requestWithdraw`, `claimInstantWithdrawRequest`) are available to any KYC-passed lender; privileged actors remain honest. The trigger — partial instant funding followed by a default — is plausible in stressed conditions, which is exactly when defaults occur.

### Recommendation
In `claimInstantWithdrawRequest`, also clear the per-epoch legs: set `instantWithdrawsRequestsByEpoch[_user][<requestEpoch>] = 0` and decrement `instantWithdrawClaimsByEpoch[<requestEpoch>]` by the claimed amount (requires storing/tracking the request epoch per user, analogous to `lastWithdrawRequest` for normal withdrawals), so the default-epoch claim basis and prefunded-reserve computation only ever see unfunded, unclaimed receipts.

### Proof of Concept
Foundry fork scenario (sketch, mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Epoch N buffer: users A (attacker) and B each requestInstantWithdraw(100e6)
// via cdoEpoch.requestWithdraw with instant mode enabled (allowInstantWithdraw).
// startEpoch: strategy collects only 100 of 200 -> collectInstantWithdrawFunds(100)
//   pendingInstantWithdraws = 100; instantWithdrawClaimsByEpoch[N] = 200.
// A calls cdoEpoch.claimInstantWithdrawRequest():
//   burns A's 100 receipt, transfers the 100 funded underlyings to A.
//   BUG: instantWithdrawsRequestsByEpoch[A][N] and claimsByEpoch[N] untouched.
// Borrower defaults in epoch N -> manager calls finalizeDefault(recovered, src).
// In finalizeDefaultRecovery:
//   defaultPendingClaimBasis() = pendingWithdraws + 200  // A's paid 100 counted again
//   _defaultPrefundedInstantReserve() = 200 - 100 = 100  // phantom: already paid to A
//   defaultRecoveryReserve += phantom 100; recoveryPrice inflated.
// B and other claimants claim at inflated price until real balance is exhausted;
// final claimants' _transferDefaultRecovery reverts -> unpaid claims / insolvency.
assertEq(creditVault.instantWithdrawsRequestsByEpoch(A, N), 100); // stale after claim
assertEq(creditVault.instantWithdrawClaimsByEpoch(N), 200);       // should be 100
```

Uncertainty: I could not read the `IdleCDOEpochVariant.startEpoch`/`getInstantWithdrawFunds` internals (grep returned match counts only), so the exact partial-collection call path is inferred from `collectInstantWithdrawFunds` semantics and `_defaultPrefundedInstantReserve`'s documented intent; the stale-accounting defect itself is verified in `IdleCreditVault.sol`.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
