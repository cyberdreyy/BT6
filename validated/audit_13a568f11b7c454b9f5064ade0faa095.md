### Title
v1 `validate_tenure_change_payload` misses locally-signed duplicate tenure-start blocks, breaking uniqueness during v1/v2 version skew - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`v1::validate_tenure_change_payload` checks for an existing block in the current tenure using `SignerDb::get_last_globally_accepted_block`, which only detects blocks that reached the 70%-signature `GloballyAccepted` state. `v2::validate_tenure_change_payload` was hardened to use `get_last_signed_block`, which also catches blocks this signer already `LocallyAccepted` (i.e., already signed but not yet globally confirmed). A v1-active signer can therefore be induced to sign a second, competing tenure-start block for a tenure it already signed, while a v2-active signer correctly rejects it as `DuplicateBlockFound`.

### Finding Description
The equality that must hold is: for any given tenure (`consensus_hash`), an honest signer must never sign a second tenure-change block once it has already signed one, regardless of whether that first signature reached global 70% consensus.

- v1: `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` [1](#0-0)  only returns a block if it is in the `GloballyAccepted` state, so a block this same signer already `LocallyAccepted` (signed, but which never reached 70% weight, e.g., because some peers rejected it) is invisible to this check.
- v2: `signer_db.get_last_signed_block(&block.header.consensus_hash)` explicitly also matches `LocallyAccepted` blocks, with the code comment stating the rationale: "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place" [2](#0-1) .

The active chainstate implementation (`v1` vs `v2`) a given signer uses is selected per-signer from `SortitionStateVersion::from_protocol_version`, driven by the signer's locally negotiated `active_signer_protocol_version` [3](#0-2) . This negotiation is weight-based consensus across the observed `StateMachineUpdate` gossip and is not synchronized instantaneously — the codebase itself contains tests (`downgrade_signer_protocol_version`, `mixed_signer_set_80_percent_new_20_percent_old` in `stacks-node/src/tests/signer/multiversion.rs`) that exercise exactly this "mixed v1/v2 signer set" scenario as a real, anticipated network state [4](#0-3) .

Exploit flow: a miner proposes tenure-start block A for tenure T; some signers sign it (LocallyAccepted) but it fails to reach the 70% global threshold (e.g., a portion of signers reject/timeout on unrelated grounds). The miner then proposes a second, different tenure-start block B for the same tenure T. Signers still running v1 logic call `get_last_globally_accepted_block`, find nothing (A was never globally accepted), and sign B. Signers running v2 logic call `get_last_signed_block`, find A, and reject B with `DuplicateBlockFound`. The v1 subset and any prior signers of A now represent two different signed sets for two different blocks in the same tenure.

### Impact Explanation
This breaks the uniqueness/equivocation-guard property that governs which chain-safety guarantee "a signer never signs two conflicting blocks for the same tenure" is supposed to enforce for the v1-protocol subset of signers. If a subset of honest v1 signers can be brought to sign a duplicate tenure-start block after already signing an earlier one, this is exactly the equivocation the `DuplicateBlockFound` guard exists to prevent, matching the Critical category ("a signer signing an invalid, non-canonical, or conflicting block"). Whether this fully finalizes into two independently-confirmed chains additionally depends on whether the v1-weighted subset alone can reach the 70% threshold for block B, which is a function of signer-set composition during the transition rather than of this bug alone.

### Likelihood Explanation
The precondition is a genuine, codebase-acknowledged rolling-upgrade window where some signers negotiate/operate at protocol version < `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (2) while others are already on v2 [5](#0-4) . The attacker (a single winning miner slot) needs only to gossip two different `BlockProposal`s for the same tenure — no privileged access, no signer key, no auth token. However, actually causing a *finalized* chain split additionally requires the v1-weighted subset to independently reach the 70% signing threshold, which is outside the attacker's direct control and depends on the specific signer-weight distribution during the transition window, making full finalization less than guaranteed on any single attempt, though the per-signer equivocation (v1 signers double-signing) is reliably reproducible.

### Recommendation
Update `v1::validate_tenure_change_payload` to use `SignerDb::get_last_signed_block` (or an equivalent that also matches `LocallyAccepted` blocks) instead of `get_last_globally_accepted_block`, matching the v2 semantics, so that v1-protocol signers cannot be induced to sign a second tenure-start block for a tenure they have already locally signed.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests` (mirroring `check_tenure_change_rejects_when_locally_accepted_block_exists` in `v2.rs` tests):
1. Set up a `SignerDb` with a block `A` for tenure `T` stored as `BlockState::LocallyAccepted` (signed by this signer, not globally accepted).
2. Construct a competing tenure-change `NakamotoBlock` `B` for the same tenure `T` with a valid parent-tenure match and `confirms_expected_parent = true`.
3. Call `SortitionsView::validate_tenure_change_payload` (v1 path) with this state.
   - Assert result is `Ok(())` (accepts the duplicate) — this is the vulnerable behavior.
4. Call the v2 `validate_tenure_change_payload` with the identical `SignerDb`/block setup.
   - Assert result is `Err(RejectReason::DuplicateBlockFound)`.
5. The divergent assertions (`Ok` vs `Err(DuplicateBlockFound)`) on identical DB/block state directly demonstrate the version-skew equivocation surface described above.
