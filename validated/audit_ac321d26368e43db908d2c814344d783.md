### Title
Default finalization reads instant-withdraw claims under the post-rollover `epochNumber`, so unfunded instant receipts are excluded from recovery basis yet paid at par (or freeze all claims) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a stale-context metadata bug: `IP6CB(skb)->nhoff` is meaningful only on the receive path, but `decode_session6` reused it on the transmit path, producing a slab-use-after-free. The analog in `IdleCreditVault` is identical in shape: instant-withdraw receipts are recorded under `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` **at request time**, but default recovery reads them under `epochNumber` / `defaultRecoveryEpoch` **at finalization time**, after `epochNumber` has already been bumped. A receipt requested in epoch N is looked up under epoch N+1, so it is both excluded from the haircut basis and routed to the wrong claim path.

### Finding Description
`requestInstantWithdraw` keys the receipt to the current `epochNumber`: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount; instantWithdrawClaimsByEpoch[currentEpoch] += _amount;` [1](#0-0) 

`epochNumber` is incremented in `deposit()` whenever an epoch is running (i.e., during `stopEpoch`) [2](#0-1) . The code itself acknowledges `pendingInstantWithdraws` can remain non-zero into the next epoch: "This can happen when startEpoch moved the CDO's available cash to the strategy but that cash covered only part of the instant queue" [3](#0-2) .

On default, `defaultPendingClaimBasis` reads `instantWithdrawClaimsByEpoch[epochNumber]` — the *new* epoch key — so a prior-epoch unfunded instant receipt contributes **zero** basis [4](#0-3) . `defaultRecoveryEpoch` is then set to that same new `epochNumber` [5](#0-4) . When the user claims, `_claimDefaultedInstantWithdrawRequest` looks up `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — again the wrong key — finds 0, and clears nothing [6](#0-5) . Execution then falls through in `claimInstantWithdrawRequest`, which pays `instantWithdrawsRequests[_user]` **in full at par** via `_transferFundedClaim` [7](#0-6)  — an unfunded receipt paid as if it were funded, while the recovery reserve it was supposed to share is untouched.

### Impact Explanation
An unprivileged user (any tranche holder allowed to request an instant withdraw) requests an instant withdrawal during epoch N's buffer. The epoch stops (`epochNumber` → N+1), `startEpoch` collects only part (or none) of the instant queue, leaving `pendingInstantWithdraws > 0` keyed under epoch N. The borrower defaults and the CDO calls `finalizeDefaultRecovery`. Two outcomes, both with fund impact:

- **Theft at par:** the attacker's unfunded receipt is paid 1:1 through `_transferFundedClaim` instead of at `defaultRecoveryPrice`. If the strategy holds any non-reserve underlying (old funded receipts, in-flight collections), the attacker drains it ahead of honest claimants whose receipts were correctly haircut.
- **Permanent freezing:** if `balance - reserve < amount`, `_transferFundedClaim` reverts [8](#0-7) . Because `_claimDefaultedInstantWithdrawRequest` never decremented `instantWithdrawsRequests` or `pendingInstantWithdraws` (wrong epoch key), the revert is permanent — the claim can never succeed and the receipt can never be repriced.

Quantified loss: every unfunded prior-epoch instant receipt is paid `amount × (1 − defaultRecoveryPrice)` too much, or the full `amount` is frozen.

### Likelihood Explanation
No privileged misbehavior is required: the attacker only calls the unprivileged `requestInstantWithdraw`/`claimInstantWithdrawRequest` path through the CDO. The trigger is an ordinary sequence — instant request in buffer, `stopEpoch` (bumps `epochNumber`), `startEpoch` with insufficient instant liquidity (explicitly contemplated by the code comments), then a borrower default + finalization, which honest owner/manager/borrower actions already perform. Timing is opportunistic, not attacker-controlled in a disallowed way: any unfunded instant receipt spanning an `epochNumber` boundary before default qualifies.

### Recommendation
Track instant-withdraw claims by their **request** epoch, not the finalization epoch. Concretely: in `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, aggregate `instantWithdrawClaimsByEpoch` over all epochs that still contribute to `pendingInstantWithdraws` (or store a single `pendingInstantEpoch`/aggregate basis instead of a per-current-epoch mapping), and in `_claimDefaultedInstantWithdrawRequest` clear `instantWithdrawsRequestsByEpoch[_user]` across the epochs present rather than only `defaultRecoveryEpoch`. Alternatively, snapshot the epoch key at request time on a per-user basis (like `lastWithdrawRequest`) and look claims up by that stored key.

### Proof of Concept
Foundry fork sketch (using `test/foundry/IdleCreditVault.t.sol` harness conventions):

```solidity
// 1. Epoch N running: attacker deposits, then requests instant withdraw in buffer.
//    instantWithdrawsRequestsByEpoch[attacker][N] = A; pendingInstantWithdraws = A.
// 2. manager.stopEpoch(...) -> strategy.deposit() bumps epochNumber to N+1.
// 3. manager.startEpoch() -> collectInstantWithdrawFunds(A') with A' < A
//    (or 0): pendingInstantWithdraws = A - A' > 0, all still keyed under epoch N.
// 4. borrower defaults; cdoEpoch calls finalizeDefaultRecovery:
//      basis += instantWithdrawClaimsByEpoch[N+1] == 0   // attacker's A excluded
//      defaultRecoveryEpoch = N+1
//      defaultInstantWithdrawsFinalized = true
// 5. attacker calls claimInstantWithdrawRequest():
//      _claimDefaultedInstantWithdrawRequest reads
//          instantWithdrawsRequestsByEpoch[attacker][N+1] == 0 -> clears nothing
//      amount = instantWithdrawsRequests[attacker] == A
//      _burn(attacker, A); _transferFundedClaim(attacker, A)
//    -> attacker paid A at par instead of A * defaultRecoveryPrice,
//       or reverts permanently if balance - reserve < A.
assertApproxEqAbs(claimed, A, 1); // instead of A * defaultRecoveryPrice / 1e18
```

Uncertainty I could not fully resolve within the tool budget: the exact `IdleCDOEpochVariant` orchestration of `collectInstantWithdrawFunds`/`startEpoch` and whether an epoch rollover is possible while `pendingInstantWithdraws > 0` under all configurations — but the strategy's own comments in `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` explicitly describe pending instant withdrawals surviving `startEpoch`, which is the precondition for the stale-epoch-key read.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
