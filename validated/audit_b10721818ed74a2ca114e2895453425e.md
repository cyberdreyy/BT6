### Title
Stale Confirmations From Removed Multisig Members Are Never Purged, Allowing Requests To Execute Below The Live Member Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2`'s `confirm` counts votes as raw string entries in a `HashSet<String>` and executes a request once that count reaches `num_confirmations` [1](#0-0) . When a member is removed via `DeleteMember`, `delete_member` only purges confirmations for requests that member *originally created* (`r.member == member`); it does not scan and remove that member's confirmation entry from other requests they merely confirmed [2](#0-1) . As a result, a confirmation cast by an account that is later removed from the multisig remains permanently counted toward the threshold of any request it confirmed but did not create.

### Finding Description
The binding that must hold is: `confirmations counted == live members who approved`. The code breaks this equality.

- `confirm()` inserts `member.to_string()` into `self.confirmations[request_id]` and executes the request once `confirmations.len() + 1 >= self.num_confirmations` [3](#0-2) . It never re-validates, at count time, that every entry already in the set still belongs to `self.members`.
- `delete_member()` cleans confirmations only for requests where the removed member is the *creator* (`r.member == member`) [4](#0-3) . It does not iterate `self.confirmations` values to strip the removed member's string from requests created by *other* members that this member had merely confirmed.
- `current_member()` / `assert_valid_request()` only validate the *caller* of the current transaction, not the historical confirmers already stored in a request's confirmation set [5](#0-4) [6](#0-5) .

Consequently a confirmation from an account that is no longer a member is treated identically to a confirmation from a current member, silently inflating the count of "valid" approvals — analogous to the reported bug class of trusting an unverified claim (a JWT `jti`) without checking it against current authoritative state.

### Impact Explanation
This lets a request execute with fewer than `num_confirmations` *live* members having approved it, i.e. "a multisig request executed below threshold," which is explicitly listed as a Critical impact. Any request type is affected, including `Transfer`, `FunctionCall`, `AddKey`, and `DeployContract`, so the multisig's fund-custody guarantee (K-of-N live members must authorize any transfer) is broken — funds can be moved, or the contract's code/keys can be altered, with effectively fewer than K currently-trusted approvers.

### Likelihood Explanation
This does not require the foundation, a redeploy, or any outside party — it only requires normal, expected multisig governance operations that are explicitly supported by the contract: (1) a member confirms a pending request, and (2) at any later point (even for unrelated reasons, e.g., key rotation, offboarding) that member is removed via `DeleteMember`. Membership changes are a documented, ordinary use case of this contract, and once such an unrelated removal happens, any request the removed member had confirmed but not created retains a phantom vote indefinitely (until deleted or executed), which can be combined with genuinely new confirmations from current members to reach the threshold.

### Recommendation
When executing `DeleteMember`, iterate all outstanding `confirmations` entries (not just the ones where the removed member was the original requester) and strip the removed member's string from each set, updating `num_requests_pk` bookkeeping if it was also a creator elsewhere. Alternatively, validate at `confirm()` execution time that every string in `confirmations.get(&request_id)` still corresponds to `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B` calls `add_request_and_confirm(R)` where `R` is e.g. a `Transfer` — confirmations for `R` = `{B}`.
3. `A` calls `confirm(R)` — confirmations for `R` = `{B, A}` (2 of 3, request not yet executed).
4. Separately, members `B, C, D` create and confirm a `DeleteMember { member: A }` request (3 confirmations, satisfies `members.len() - 1 = 3 >= num_confirmations = 3`), which executes and removes `A` from `self.members`. Because `R`'s creator field is `B` (not `A`), the cleanup loop in `delete_member` does not touch `R`'s confirmation set, so `{B, A}` remains stored for `R`.
5. Current members are now `{B, C, D}`. `C` calls `confirm(R)` — confirmations for `R` becomes `{B, A, C}`, length 3 `>= num_confirmations (3)`, so `execute_request` runs and `R`'s `Transfer` is sent — even though only `B` and `C`, i.e. 2 of the 3 current live members, actually approved it. `A`'s stale confirmation, cast before removal, counted toward and completed the threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

        }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
