### Title
Unbounded per-notification encoding cost for `Base64`/`Base64Zstd`/`JsonParsed` `accountSubscribe` when subscribed account is resized to max size - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
`accountSubscribe` with `encoding=base64`, `base64+zstd`, or `jsonParsed` causes `notify_watchers`/`check_commitment_and_notify`/`filter_account_result` to call `encode_ui_account`, which serializes/compresses/parses the **entire** account data on every qualifying slot notification with no explicit byte cap. Since a program the attacker controls can grow the subscribed account up to `MAX_PERMITTED_DATA_LENGTH` (10 MiB) via repeated reallocs, each subsequent notification's CPU/memory cost scales with attacker-controlled on-chain data size rather than any fixed limit.

### Finding Description
`RpcSolPubSubImpl::account_subscribe` (`rpc/src/rpc_pubsub.rs:424-443`) accepts an `AccountSubscriptionParams` with an `encoding` chosen by the caller (`UiAccountEncoding::Binary` default, but the caller can request `Base64`, `Base64Zstd`, or `JsonParsed`) and performs no validation of account size vs. encoding at subscribe time (the account may not even exist yet).

On every bank/gossip notification, `RpcSubscriptions::process_notifications` calls `notify_watchers` (`rpc/src/rpc_subscriptions.rs:908-1185`), which for `SubscriptionParams::Account` calls `check_commitment_and_notify` (`rpc_subscriptions.rs:136-175`) with `filter_account_result` (`rpc_subscriptions.rs:370-392`) as the filter function. `filter_account_result` calls:

```
encode_ui_account(&params.pubkey, &account, params.encoding, None, None)
``` [1](#0-0) 

This bypasses the size-limiting logic present in the HTTP `getAccountInfo` path (`rpc/src/rpc.rs::encode_account`, `rpc.rs:2575-2601`), which explicitly rejects `Binary`/`Base58` encodings whose payload exceeds `MAX_BASE58_BYTES` (128 bytes) before calling `encode_ui_account`: [2](#0-1) 

`encode_ui_account` itself (`account-decoder/src/lib.rs:46-101`) only self-limits the `Binary`/`Base58` branches via `encode_bs58`, which returns an error string (`"error: data too large for bs58 encoding"`) when data exceeds `MAX_BASE58_BYTES` (128 bytes) — capping cost for those two encodings: [3](#0-2) 

However, the `Base64`, `Base64Zstd`, and `JsonParsed` branches have **no size cap at all**:
- `Base64` performs `BASE64_STANDARD.encode(slice_data(...))` over the full account data.
- `Base64Zstd` runs a zstd compression pass over the full account data.
- `JsonParsed` calls `parse_account_data_v3` over the full data (and falls back to full `Base64` encoding of the whole buffer on parse failure). [4](#0-3) 

Because `filter_account_result` never invokes the HTTP path's `encode_account` size guard, subscribing with `encoding: "base64"` (or `base64+zstd`, or `jsonParsed`) is a direct, unguarded route to encode arbitrarily large account payloads on every slot notification. The resulting serialized notification is written into a per-thread buffer and stored as an `Arc<String>` in `RpcNotifier::notify` (`rpc_subscriptions.rs:289-322`), then broadcast over the subscriber's websocket connection: [5](#0-4) 

An attacker deploys/owns a program, subscribes to one of its accounts with `encoding=base64`, then submits ordinary transactions (each capable of growing account data by `MAX_PERMITTED_DATA_INCREASE`, 10 KiB, per CPI realloc call) to progressively grow the account up to the network maximum account size (10 MiB, `MAX_PERMITTED_DATA_LENGTH`). From that point forward, every slot in which the account is modified (which the attacker also fully controls, e.g., touching a single byte each slot) triggers a ~10 MiB base64 encode (or zstd compression, or JSON parse attempt) inside the single-threaded/rayon-parallelized notification path, for as long as the one subscription remains open — with no config-enforced ceiling on notification payload bytes.

### Impact Explanation
This is a single, legitimate, unprivileged websocket subscription (one `accountSubscribe` call) whose ongoing notification cost is proportional to attacker-controlled on-chain account size rather than bounded by an explicit limit — matching the "unbounded cost for a single low-rate call" RPC DoS category. Repeated ~10 MiB encodes/compressions per relevant slot from one subscription impose sustained CPU (JSON/base64/zstd encoding), memory allocation (buffer growth, `Arc<String>` payloads), and network bandwidth (websocket send of tens of megabytes per notification) load on the validator's RPC/pubsub notification thread(s), which are shared (`notification_threads` rayon pool in `rpc_subscriptions.rs:624-651`) across all subscribers, potentially degrading service for other RPC/pubsub clients.

### Likelihood Explanation
Fully within attacker capability: no privileged access needed. The attacker only needs (1) a program capable of `realloc`-ing one of its own accounts (any BPF program using standard SPL/system-program realloc CPI patterns can do this incrementally over multiple transactions, well within the "≤1 call per CLUSTER_SLOT_TIME_TARGET/2" constraint since growth doesn't need to happen every slot), and (2) to issue a single `accountSubscribe` with `encoding: "base64"` (or `base64+zstd`/`jsonParsed`) on that pubkey. This is fully reproducible deterministically.

### Recommendation
Apply the same (or a tighter, pubsub-specific) payload-size guard used in `rpc::encode_account` to the pubsub notification path in `filter_account_result`/`notify_watchers`: reject or truncate (via forced `data_slice`) account encodings whose resulting payload would exceed a fixed maximum notification size for all encodings (`Base64`, `Base64Zstd`, `JsonParsed`), not just `Binary`/`Base58`. Alternatively, enforce a `max_notification_bytes` config with an explicit check on `account.data().len()` before invoking `encode_ui_account`, dropping or downgrading the notification (e.g., sending only account metadata plus an error data flag) for oversized accounts.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}

fn encode_bs58<T: ReadableAccount>(
    account: &T,
    data_slice_config: Option<UiDataSliceConfig>,
) -> String {
    let slice = slice_data(account.data(), data_slice_config);
    if slice.len() <= MAX_BASE58_BYTES {
        bs58::encode(slice).into_string()
    } else {
        "error: data too large for bs58 encoding".to_string()
    }
