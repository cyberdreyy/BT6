### Title
External-initiator credentials can trigger runs on arbitrary integer job IDs, bypassing per-job EI scoping - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` determines whether a caller is allowed to run a job by integer ID solely via `auth.GetAuthenticatedUser(c)` returning `ok == true`. However, `AuthenticateExternalInitiator` (in `core/web/auth/auth.go`) also populates the same `SessionUserKey` context value with a synthetic `clsessions.User{Role: clsessions.UserRoleRun}` for any successfully authenticated external-initiator (EI) credential. As a result, the comment/intent "only users are allowed to run jobs using int IDs - EIs not allowed" is not actually enforced, and any valid EI credential can call `RunJobV2` for any job ID, not just the job it was registered against.

### Finding Description
- In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` authenticates the EI access-key/secret headers, then unconditionally does:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [1](#0-0) 

- `GetAuthenticatedUser` simply reads `SessionUserKey` from context and returns `(user, ok)` — it cannot distinguish between a real, session/token-authenticated `clsessions.User` and the synthetic `UserRoleRun` user object created for EI credentials:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
}
``` [2](#0-1) 

- `PipelineRunsController.Create` uses exactly this ambiguous signal to gate integer-ID job runs:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
    ...
}
``` [3](#0-2) 

Because `isUser` is `true` for both genuine users and EI-forced sessions, the stated invariant ("EIs not allowed" to run by int ID, only via their bound webhook UUID) is not enforced in code — it exists only as a comment. `RunJobV2` itself takes only a job ID and performs no EI-to-job binding check at this call site. There is no code path here that verifies the calling EI's registered/authorized job matches the requested `:ID` route parameter. Any request authenticated purely as an EI (via `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) that passes `AuthenticateExternalInitiator` will satisfy `isUser` and can invoke `RunJobV2` for an arbitrary integer job ID, including jobs the EI was never granted access to.

### Impact Explanation
This is an authorization bypass allowing an external-initiator credential (typically scoped/expected to be tied to one specific webhook job) to trigger pipeline runs of any other job on the node by integer ID. Depending on job type (e.g., jobs with on-chain transmission tasks, VRF, or Keeper-style pipelines), this could cause unauthorized on-chain transactions, unintended consumption of node resources/gas, or state changes tied to a job the credential holder was never authorized to invoke — matching the "unauthorized job run/action triggered by improperly scoped credential" impact class.

### Likelihood Explanation
Preconditions are minimal: possession of any valid, currently-active external-initiator access key/secret pair (issued for any one job) is sufficient. No admin/user session, no job-specific binding check, and no additional privilege is required. The attack is a single unauthenticated-role HTTP POST (`POST /v2/jobs/<jobB_ID>/runs`) with just the EI headers, fully repeatable, and does not depend on race conditions or misconfiguration.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser` presence to gate int-ID runs. Distinguish EI-authenticated sessions explicitly, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` and rejecting (or separately authorizing) when an EI is present, and/or add an explicit marker (e.g., a distinct context key or a `IsExternalInitiator` field) set by `AuthenticateExternalInitiator` instead of overloading `SessionUserKey` with a synthetic user. If EIs must be permitted to trigger runs by ID, validate that the EI's associated job(s) match the requested `:ID` before calling `RunJobV2`.

### Proof of Concept
1. Create two webhook jobs, Job A and Job B, on a test node.
2. Register an external initiator credential `EI1` associated only with Job A (via the external initiator creation flow used for webhook triggers).
3. Using `EI1`'s access key/secret in `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, send `POST /v2/jobs/<JobB_intID>/runs`.
4. Assert current behavior: request passes `AuthenticateExternalInitiator` → `SessionUserKey` set to `UserRoleRun` → `isUser == true` in `Create` → `RunJobV2` is invoked for Job B → HTTP 200 with a `pipelineRun` resource returned, despite `EI1` never being granted access to Job B.
5. Expected/fixed behavior: request should be rejected (HTTP 401/403) because `EI1` is not authorized for Job B, verifying via `auth.GetAuthenticatedExternalInitiator(c)` (non-nil) that the request originated from an EI credential and blocking/scoping the run accordingly.
