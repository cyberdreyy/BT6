### Title
Lockup contract's `new()` initializer is missing a re-initialization guard, allowing full contract takeover - ([File: lockup/src/lib.rs])

### Summary
`LockupContract::new()` is a public `#[init]` method that anyone can call as a normal function call against the deployed lockup account. Unlike every other contract in this codebase (`staking-pool`, `whitelist`, `multisig`, `lockup-factory`, `staking-pool-factory`, `voting`), the lockup contract's `new()` does not assert `!env::state_exists()` before writing state. [1](#0-0) 

### Finding Description
Every sibling initializer in this repository explicitly guards against double-initialization:
- `lockup-factory/src/lib.rs`: `assert!(!env::state_exists(), "The contract is already initialized");` [2](#0-1) 
- `multisig/src/lib.rs`: `assert!(!env::state_exists(), "Already initialized");` [3](#0-2) 
- `staking-pool-factory/src/lib.rs` and `staking-pool/src/lib.rs`: same `assert!(!env::state_exists(), ...)` pattern. [4](#0-3) [5](#0-4) 
- `whitelist/src/lib.rs`: same pattern. [6](#0-5) 
- `voting/src/lib.rs`: same pattern. [7](#0-6) 

By contrast, `LockupContract::new()` performs argument validation but never checks whether state already exists before unconditionally overwriting `owner_account_id`, `lockup_information`, `vesting_information`, `staking_information`, and `foundation_account_id`: [8](#0-7) 

Because the lockup account is intentionally keyless (per the design docs, it must have no access keys to prevent the owner from bypassing the contract logic), the only way to interact with it is through its public contract methods. `new` is a normal `pub fn`, not `#[private]`, so any account on the network can call it directly against the already-deployed lockup contract (e.g. `near call <lockup_account> new '{...}' --accountId attacker.near`), re-running the initializer with attacker-chosen arguments.

Binding broken: the equality "owner_account_id recorded in contract state == the account the NEAR Foundation/funding entity actually designated as owner" no longer holds after an attacker-driven re-init. Likewise "vesting/lockup schedule enforced by the contract == the schedule that was contractually agreed" is broken, since the attacker can pass `vesting_schedule: None`, `lockup_timestamp: 0`, `lockup_duration: 0`, and `transfers_information: TransfersEnabled { transfers_timestamp: 0 }`.

### Impact Explanation
After the attacker's re-init call:
- `owner_account_id` becomes the attacker's account, granting them all owner-only privileges defined in `lockup/src/owner.rs` (transfer, staking pool selection/deposit/withdraw, etc.).
- `vesting_information` is reset to `VestingInformation::None` and `lockup_information` reflects instantly-unlocked, zero-duration schedules, so previously locked/unvested NEAR becomes immediately transferable.
- `staking_information` is reset to `None`, discarding the contract's record of any staking pool relationship (funds actually delegated to a staking pool are orphaned from the contract's bookkeeping).
- The attacker, now the recorded owner, can call the owner's `transfer` method to move the account's NEAR balance to themselves.

This matches the Critical category: "NEAR moved by a party not entitled to it" and "locked or unvested tokens released early," since a party who was never granted ownership gains full custodial control and can release/move funds that were meant to remain locked/vested.

### Likelihood Explanation
Likelihood is high for any deployed lockup contract, because:
- No privileged role, key, or social engineering is required — this is a plain, unauthenticated function call to a public method.
- The lockup account is guaranteed to have no access keys (by design), so there is no competing "legitimate" caller path that would need to be bypassed; the vulnerable method itself is the only entry point an attacker needs.
- The bug is a straightforward code omission relative to every other contract in the repo, which all include the guard — this asymmetry strongly suggests the lockup contract's `new()` simply lacks the check that should be there.

### Recommendation
Add the same guard used elsewhere in the codebase at the top of `LockupContract::new()`:
```rust
assert!(!env::state_exists(), "The contract is already initialized");
``` [9](#0-8) 

### Proof of Concept
1. Deploy/observe an existing lockup contract at account `lockup1` (funded and initialized normally by the factory).
2. From any unprivileged account, call:
```
near call lockup1 new '{
  "owner_account_id": "attacker.testnet",
  "lockup_duration": "0",
  "lockup_timestamp": "0",
  "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "0"}},
  "vesting_schedule": null,
  "release_duration": null,
  "staking_pool_whitelist_account_id": "staking-pool-whitelist",
  "foundation_account_id": null
}' --accountId attacker.testnet
```
Because `new()` never checks `env::state_exists()`, this call succeeds and fully overwrites the contract state, per `lockup/src/lib.rs` lines 190-243. [8](#0-7) 
3. `attacker.testnet` is now `owner_account_id`. They then call the owner-only `transfer` method (defined in `lockup/src/owner.rs`) to move the contract's NEAR balance out, since the previously locked/vesting schedule has been reset to fully unlocked/no-vesting.

Note: I could not fully verify the exact body of `lockup/src/owner.rs`'s `transfer`/`assert_owner` implementation within the available tool budget (the file exists and contains an `assert_owner`-style check, confirmed by grep, but I did not read its full contents), though its existence and predecessor-based owner check are consistent with the documented owner-methods API referenced in `lockup/README.md` lines 129-133. If further certainty is needed on the exact transfer mechanics, a full read of `lockup/src/owner.rs` is recommended. [10](#0-9)

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
```
