### Title
Name squatting a multisig sub-account lets an attacker permanently seize `<name>.<factory>` with attacker-chosen members - (`multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` lets any unprivileged caller pick an arbitrary `name`, `members`, and `num_confirmations` and immediately create `<name>.<factory>` with those parameters. Because NEAR sub-account names are globally unique under their parent, an attacker who calls `create` first for a given `name` permanently occupies that address with their own members, and the intended/legitimate owner's later `create` call for the same `name` will fail, since the account already exists.

### Finding Description
The binding this contract is supposed to preserve is: for any sub-account `<name>.<factory>` that users trust as "the multisig belonging to `name`", `members(<name>.<factory>) == members_chosen_by(name's rightful owner)`. Nothing in the code enforces this.

```rust
pub fn create(
    &mut self,
    name: AccountId,
    members: Vec<MultisigMember>,
    num_confirmations: u64,
) -> Promise {
    let account_id = format!("{}.{}", name, env::current_account_id());
    Promise::new(account_id)
        .create_account()
        .deploy_contract(CODE.to_vec())
        .transfer(env::attached_deposit())
        .function_call(
            b"new".to_vec(),
            json!({ "members": members, "num_confirmations": num_confirmations })
                .to_string().as_bytes().to_vec(),
            0,
            env::prepaid_gas() - CREATE_CALL_GAS,
        )
}

There is no check that `env::predecessor_account_id()` matches or is authorized to claim `name`, no reservation mechanism, and no guard preventing a second party from racing to create the same `name` first. `name`, `members`, and `num_confirmations` are all fully attacker-controlled parameters passed straight into the `multisig2` contract's `new` call. Unlike `lockup-factory/src/lib.rs::create`, which derives the sub-account from `sha256(owner_account_id)` and includes an `on_lockup_create` callback (`assert_self`, `is_promise_success`) that refunds the caller if account creation fails, `multisig-factory::create` has no callback at all - it fires the batched promise and never checks whether the underlying `create_account` action succeeded.

Exploit flow: an attacker observes (or anticipates) that a party/org is about to deploy its multisig at `alice.multisig-factory.near`. The attacker calls `create("alice", [attacker_key_or_account], 1)` first. Since the sub-account doesn't yet exist, `create_account` succeeds, `multisig2` is deployed and initialized with the attacker as sole member. When the legitimate party later calls `create("alice", [legit_members...], k)`, the `create_account` action in their batched promise fails because the account already exists; the whole batch fails and, because there is no refund callback, the attacker's target address remains live with attacker-chosen members while the rightful owner's attempt is wasted. Any protocol component, user, or integrator that trusts `alice.multisig-factory.near` as "Alice's multisig" is now interacting with an attacker-controlled contract.

None of the existing guards mitigate this: `assert_self()`/`is_promise_success()` do not exist for this call path, there is no `assert_owner`, no `is_valid_account_id`-style ownership check tying `name` to `env::predecessor_account_id()`, and the `multisig2::new` initializer only guards against re-initialization of an already-existing state, which is precisely why the legitimate owner can never recover the name afterward.

### Impact Explanation
Any user or protocol that treats `<name>.<multisig-factory>` as trusted (e.g., routes NEAR/tokens, grants roles, or treats it as an org's governance contract) can have funds or authority routed to a contract whose members were chosen entirely by an attacker rather than by the intended owner. This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" (here: a multisig deployed with attacker-chosen members instead of the intended owner's). The attack is repeatable across every unclaimed name at zero-ish marginal cost (only account-creation storage cost + the attacker's own tiny deposit, since `members`/`num_confirmations` are attacker-supplied), and the effect is permanent - the legitimate name can never be reclaimed once squatted because NEAR account names are unique per parent.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to know or guess the `name` a victim will want (often predictable - e.g. matching the victim's own account prefix, a known org name, or a name announced publicly before deployment) and to submit their `create` call before the victim's. There's no special privilege required - this is exactly the "unprivileged attacker" scenario in scope. Cost is low (one transaction with a small deposit/gas), and the race is directly winnable by whoever transacts first, making this fully feasible and repeatable across many target names.

### Recommendation
Bind the sub-account creation to an authorization check, e.g. require `name == env::predecessor_account_id()` (self-service naming) or require the caller to prove ownership of the target base account, and/or add a callback (`assert_self()` + `is_promise_success()`) that refunds the attached deposit to the caller when `create_account` fails, mirroring `lockup-factory::on_lockup_create`. At minimum, document and enforce a first-come reservation scheme with owner-verification rather than allowing arbitrary third parties to instantiate multisigs at arbitrary sub-account names.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
