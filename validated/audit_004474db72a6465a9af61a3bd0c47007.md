### Title
External Initiator credentials satisfy the user-role check and can trigger arbitrary Job IDs via `PipelineRunsController.Create` - (File: `core/web/pipeline_runs_controller.go`)

### Summary
`PipelineRunsController.Create` intends to block External Initiator (EI) credentials from triggering int-ID job runs ("EIs not allowed"), relying on `auth.GetAuthenticatedUser(c)` returning `ok == false` for EI-authenticated requests. However, `AuthenticateExternalInitiator` in `core/web/auth/auth.go` also sets `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}`, so `GetAuthenticatedUser` returns `ok == true` for EI-authenticated requests as well. This defeats the intended check and lets any valid EI credential trigger `RunJobV2` for any integer job ID, with no verification that the job is associated with that EI.

### Finding Description
`AuthenticateExternalInitiator` (core/web/auth/auth.go, lines 119-151) authenticates the EI token/secret pair and then does: [1](#0-0) 
It sets both `SessionExternalInitiatorKey` and `SessionUserKey` (to a fabricated `User{Role: UserRoleRun}`) into the gin context so that role-based middleware (`RequiresRunRole`, etc.) treats EI requests as "run"-privileged users.

`PipelineRunsController.Create` (core/web/pipeline_runs_controller.go, lines 109-125) attempts to reject EI-triggered int-ID runs using: [2](#0-1) 
The comment states "only users are allowed to run jobs using int IDs - EIs not allowed," but the guard `_, isUser := auth.GetAuthenticatedUser(c)` checks only whether `SessionUserKey` is set — which it is, for both real user sessions/tokens AND EI-authenticated requests (since `AuthenticateExternalInitiator` populates the same key). Consequently `isUser` is `true` for EI credential holders too, and the code proceeds to parse `idStr` as an int32 job ID and calls `prc.App.RunJobV2(ctx, jobID, nil)` with no check that the job ID is bound to, or associated with, the specific external initiator that authenticated the request (`GetAuthenticatedExternalInitiator` is never consulted in this function).

This means any EI with valid credentials can invoke `POST /v2/jobs/:ID/runs` for an arbitrary integer job ID belonging to any job/initiator, not just the job wired to that EI.

### Impact Explanation
This is an authorization-bypass / request-binding violation: a low-privilege credential (an External Initiator's access key/secret, scoped conceptually to trigger only its own bound job) can be used to trigger pipeline runs for arbitrary jobs across the node. Depending on job task graphs, this can cause unauthorized on-chain transactions, unwanted external HTTP/bridge calls, resource exhaustion, or interference with other users' jobs — mapping to Chainlink's "unauthorized job run / fund movement" bounty impact class.

### Likelihood Explanation
Requires only a valid EI credential pair (access key + secret) for any existing external initiator — a credential level explicitly treated as an unprivileged/limited-scope actor in this threat model. No user session, API token, or admin access is needed. The exploit is a single crafted HTTP request (`POST /v2/jobs/<targetJobID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) and is fully repeatable against any integer job ID on the node.

### Recommendation
In `PipelineRunsController.Create`, distinguish real authenticated users from EI-authenticated pseudo-users, e.g. by checking `auth.GetAuthenticatedExternalInitiator(c)` first and rejecting (or by using a dedicated context key/flag instead of overloading `SessionUserKey`) so that EI credentials cannot pass the `isUser` check. If EI-triggered runs by int ID must be supported, verify that the requested job is actually bound to the authenticated external initiator before calling `RunJobV2`.

### Proof of Concept
Go handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Create job A associated with External Initiator EI-1, and unrelated job B (any type with integer ID) not associated with EI-1.
2. Authenticate an HTTP client using EI-1's access key/secret via `AuthenticateExternalInitiator` headers.
3. `POST /v2/jobs/<jobB.ID>/runs` using EI-1's credentials.
4. Assert the response is `401/403` (expected/desired behavior) — but current code returns `200` with a created pipeline run resource, and `App.RunJobV2` is invoked with `jobB.ID`, proving the EI could trigger a job it has no binding to.
