### Title
Pending withdrawals can lock in pre-loss prices after a programmable-borrower vault drawdown - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw` prices receipts from CDO NAV, but NAV consists of strategy-token balances and does not include the programmable borrower’s ERC4626 position. [1](#0-0) [2](#0-1)   
Vault losses incurred during the buffer are only stored by `ProgrammableBorrower.onStartEpoch` as `bufferedVaultDelta`, and are later netted only against interest rather than immediately reducing the CDO’s strategy-token NAV. [3](#0-2) [4](#0-3)   
A lender can therefore request a withdrawal after observing an external-vault loss but before that loss is crystallized, receive funding at the stale par value, and leave the loss concentrated on the remaining lenders. [5](#0-4) 

### Finding Description
In programmable-borrower mode, CDO NAV is represented by minted `IdleCreditVault` strategy tokens, while the actual assets sit inside the external ERC4626 vault. [1](#0-0) [6](#0-5)   
After a successful `stopEpoch`, withdrawal requests are reopened while assets remain in the external vault. [7](#0-6)   
If the vault loses value during the buffer, `requestWithdraw` still calls `_updateAccounting` and `_trancheToUnderlyings` against the unchanged strategy-token balance, so it creates a receipt for the pre-loss amount. [8](#0-7) [9](#0-8)   
On the next `startEpoch`, `ProgrammableBorrower` records the negative vault delta in `bufferedVaultDelta`, but the CDO strategy-token balance and tranche prices remain unchanged. [10](#0-9)   
At the following `stopEpoch`, `totalInterestDueNow` floors the negative vault delta at zero, so in minted-interest mode the CDO only pulls the pending withdrawal amount from the programmable borrower. [11](#0-10) [12](#0-11)   
If the remaining vault balance can still cover that receipt, `onStopEpoch` withdraws the requested amount and `collectWithdrawFunds` funds it at par. [13](#0-12) [14](#0-13) 

### Impact Explanation
The stale-price withdrawal transfers the vault loss to remaining tranche holders. [15](#0-14)   
For example, with two equal lenders contributing 1,000 units total, a 10% vault loss reduces real backing to 900. [11](#0-10)   
If one lender submits a 500-unit request before the loss is reflected, the next stop can fund the full 500-unit receipt while only 400 units remain for the other lender’s still-recorded 500-unit position. [16](#0-15) [13](#0-12)   
The attacker receives 100% of the stale claim instead of the post-loss proportional value of 450, producing a 50-unit transfer from the remaining lender and a 100-unit insolvency relative to recorded strategy-token NAV. [1](#0-0) 

### Likelihood Explanation
The attack requires an observable external-vault drawdown during the buffer period and a withdrawal request before the manager starts the next epoch and the loss is realized. [17](#0-16)   
This is feasible because withdrawal requests are explicitly reopened after a successful stop, while `requestWithdraw` uses local NAV rather than the programmable borrower’s current vault valuation. [7](#0-6) [2](#0-1)   
The attacker only needs to be a KYC-passing tranche holder and does not need control over the manager, borrower, or external vault. [18](#0-17) 

### Recommendation
Before accepting a programmable-borrower withdrawal request, include the live borrower position—cash plus `vault.convertToAssets(shares)`—in NAV or force a realization of the pending `bufferedVaultDelta`. [19](#0-18)   
Alternatively, disable new withdrawal requests while a programmable borrower has an unrealized negative `bufferedVaultDelta`, and require a loss-aware `stopEpochWithDuration` or equivalent accounting transition before reopening requests. [20](#0-19) [21](#0-20)   
The accounting fix should also ensure that vault principal losses, not only reduced positive interest, lower `expectedEpochInterest` or burn strategy tokens before pending receipts are funded. [22](#0-21) 

### Proof of Concept
A Foundry fork PoC can reuse the programmable-borrower test setup and select a fork state where the configured ERC4626 vault realizes a loss between `stopEpoch` and `startEpoch`, such as through a public vault accrual/liquidation path. [11](#0-10)

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim, amount, true);

    // Epoch 0: assets are parked in the programmable borrower's ERC4626 vault.
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Buffer period: realize a 10% loss in the external ERC4626 position.
    uint256 assetsBeforeLoss = programmableBorrower.totalUnderlying();
    _realizeExternalVaultLoss(assetsBeforeLoss / 10);
    assertEq(
        programmableBorrower.totalUnderlying(),
        assetsBeforeLoss * 9 / 10
    );

    // NAV still contains 1,000 strategy tokens, so the request is priced pre-loss.
    assertEq(cdoEpoch.getContractValue(), 2 * amount);
    vm.prank(attacker);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(aaTranche));
    assertEq(receipt, amount);

    // Start and stop the next epoch. Vault loss only reduces totalInterestDueNow
    // to zero; it does not reduce the 500-unit pending receipt.
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    assertEq(underlying.balanceOf(attacker) - attackerBefore, amount);
    assertEq(programmableBorrower.totalUnderlying(), 400 * oneScale);
    assertEq(cdoEpoch.getContractValue(), 500 * oneScale);
}

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
