### Title

Fee-on-transfer underlying underfunds withdrawal receipts while clearing them at face value - ([File: `contracts/strategies/idle/IdleCreditVault.sol`])

### Summary

`IdleCreditVault.collectWithdrawFunds` accounts for borrower-funded withdrawal receipts using the requested gross amount, but only performs a `safeTransferFrom` without measuring the actual received amount. With a fee-on-transfer underlying, the strategy receives less than the cleared `pendingWithdraws` basis, leaving later claimants unpaid.

### Finding Description

When a lender calls `requestWithdraw`, the CDO calls `IdleCreditVault.requestWithdraw`, which mints receipt tokens for `_amount` and adds the same gross `_amount` to `pendingWithdraws`. [1](#0-0) 

At `stopEpoch`, `IdleCDOEpochVariant` pulls `expectedInterest + pendingWithdraws` from the borrower and then calls `collectWithdrawFunds(_pendingWithdraws)`. [2](#0-1) 

`collectWithdrawFunds` clears or reduces `pendingWithdraws` by the nominal `_amount`, then transfers `_amount` from the CDO to the strategy. [3](#0-2) 

For a fee-on-transfer token, the strategy’s actual balance increase is lower than `_amount`. The code does not compare balances before and after either the borrower-to-CDO transfer or the CDO-to-strategy transfer. As a result, funded receipt accounting is settled at face value while the strategy holds less underlying.

The same issue exists in `collectInstantWithdrawFunds`, which subtracts the gross amount from `pendingInstantWithdraws` and then performs a gross `safeTransferFrom`. [4](#0-3) 

### Impact Explanation

This creates a withdraw-claim solvency deficit equal to the transfer fee taken on the CDO-to-strategy leg, potentially compounded by the borrower-to-CDO leg.

For example, assume:

- Underlying charges a 5% transfer fee.
- Two lenders each request withdrawals for `100e6` tokens.
- `pendingWithdraws == 200e6`.
- Sufficient borrower interest is pulled so `collectWithdrawFunds(200e6)` does not revert.
- The strategy receives only `190e6`, while `pendingWithdraws` is cleared as though `200e6` arrived.

The first claimant can receive `100e6`; the second claimant is owed another `100e6`, but only `90e6` remains, so their funded claim reverts on transfer. The receipt remains burned or cleared depending on where execution reaches the transfer, but the claim cannot be paid in full.

The issue also affects default recovery funding: `finalizeDefaultRecovery` calculates `reserveAmount` and `recoveryPrice` using the nominal `_recoveredAmount` before pulling tokens, while the actual amount received can be lower under a fee-on-transfer token. [5](#0-4) 

### Likelihood Explanation

Likelihood is conditional on deploying a credit vault whose configured `underlyingToken` charges a fee on transfer. The affected paths are ordinary epoch funding and withdrawal-claim funding, not an exceptional privileged path.

Existing balance-delta handling in `_deposit` only protects tranche minting for the user-to-CDO leg. It does not protect subsequent funding transfers because `collectWithdrawFunds`, `collectInstantWithdrawFunds`, and `finalizeDefaultRecovery` continue to use nominal amounts rather than actual received amounts. [6](#0-5) 

### Recommendation

Measure the actual amount received for every funding transfer that clears or reserves a nominal claim.

In `IdleCreditVault`:

```solidity
uint256 before = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - before;
```

Then either:

1. Revert unless `received == _amount`, explicitly rejecting fee-on-transfer underlyings; or
2. Update `pendingWithdraws`, `pendingInstantWithdraws`, `defaultRecoveryReserve`, and `defaultRecoveryPrice` using `received`.

The safer remediation is to reject fee-on-transfer tokens or require exact received amounts, because recovery ratios, pending-request haircuts, APR calculations, and borrower obligations are all denominated in gross underlying units.

### Proof of Concept

A Foundry test can deploy a fee-on-transfer ERC20 mock, an `IdleCreditVault`, and a minimal CDO harness exposing `requestWithdraw`, `collectWithdrawFunds`, and `claimWithdrawRequest`.

```solidity
// test/foundry/FeeOnTransferWithdrawFunding.t.sol
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../../contracts/strategies/idle/IdleCreditVault.sol";

contract FeeOnTransferERC20 is ERC20Upgradeable {
    uint256 public constant FEE_BPS = 500; // 5%

    function initializeToken() external initializer {
        __ERC20_init("Fee USDT", "fUSDT");
    }

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }

    function _transfer(
        address from,
        address to,
        uint256 amount
    ) internal override {
        uint256 fee = amount * FEE_BPS / 10_000;
        uint256 received = amount - fee;

        super._transfer(from, to, received);
        if (fee != 0) {
            super._transfer(from, address(0xdead), fee);
        }
    }
}

contract CDOHarness {
    IdleCreditVault public strategy;

    constructor(IdleCreditVault _strategy) {
        strategy = _strategy;
    }

    function requestWithdraw(uint256 amount, address user, uint256 principal) external {
        strategy.requestWithdraw(amount, user, principal);
    }

    function collectWithdrawFunds(uint256 amount) external {
        strategy.collectWithdrawFunds(amount);
    }

    function claimWithdrawRequest(address user) external returns (uint256) {
        return strategy.claimWithdrawRequest(user);
    }

    function mintFunding(uint256 amount) external {
        // Test-only equivalent of borrower-funded CDO cash.
        FeeOnTransferERC20(address(strategy.underlyingToken())).mint(
            address(this),
            amount
        );
        strategy.underlyingToken().approve(address(strategy), amount);
    }
}

contract FeeOnTransferWithdrawFundingTest is Test {
    FeeOnTransferERC20 token;
    IdleCreditVault strategy;
    CDOHarness cdo;

    address alice = address(0xA11CE);
    address bob = address(0xB0B);

    function setUp() public {
        token = new FeeOnTransferERC20();
        token.initializeToken();

        strategy = new IdleCreditVault();
        strategy.initialize(
            address(token),
            address(this),
            address(this),
            address(0xB04410),
            "borrower",
            0
        );

        cdo = new CDOHarness(strategy);
        strategy.setWhitelistedCDO(address(cdo));
    }

    function testWithdrawFundingIsShortByTransferFee() public {
        uint256 aliceClaim = 100e6;
        uint256 bobClaim = 100e6;
        uint256 pending = 200e6;

        cdo.requestWithdraw(aliceClaim, alice, aliceClaim);
        cdo.requestWithdraw(bobClaim, bob, bobClaim);

        // Make gross funding available at the CDO, as would happen after a
        // successful borrower repayment plus enough interest/cash buffer.
        cdo.mintFunding(pending);
        cdo.collectWithdrawFunds(pending);

        // Accounting cleared 200e6, but the strategy received only 190e6.
        assertEq(token.balanceOf(address(strategy)), 190e6);
        assertEq(strategy.pendingWithdraws(), 0);

        // Alice can be paid at face value.
        cdo.claimWithdrawRequest(alice);
        assertEq(token.balanceOf(alice), 100e6);

        // Bob remains owed 100e6 but only 90e6 exists, so the funded claim fails.
        vm.expectRevert();
        cdo.claimWithdrawRequest(bob);
    }
}
```

The invariant violated is “one funded receipt, one payout”: `pendingWithdraws` and user receipt balances are cleared against the nominal funding amount, while the underlying reserve increases by less than that amount.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
