### Title
A single dust-sized APR0 withdraw request permanently reverts `stopEpoch` once APR is raised - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` reverts with `NotAllowed` whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0` [1](#0-0) . Because `stopEpoch` unconditionally routes through this function, any single tranche holder who leaves even a dust-sized withdraw request open in the APR0 bucket can make every `stopEpoch` call revert once the manager sets a non-zero APR — freezing the whole vault's epoch lifecycle, analogous to a single under-funded protocol reverting `payOffDebtAll` in the Sherlock report.

### Finding Description
When the vault runs with `unscaledApr == 0`, `requestWithdraw` records the requested principal in the global `apr0TotalPrincipal` bucket via `_requestWithdrawApr0`, which increments the aggregate with each user's amount [2](#0-1) . At `stopEpoch`, `prepareStopEpochWithApr0` fast-returns only when `_principal == 0`; otherwise it enforces `if (unscaledApr != 0) revert NotAllowed()` [3](#0-2) .

The bucket is only closed inside this same function (`apr0TotalPrincipal = 0`) [4](#0-3) , so there is no path that drains the bucket while APR is non-zero — the revert is self-perpetuating. The only escape is for the manager to set APR back to 0 (which prevents the pool from repricing its yield) or to stop the epoch under APR0 accounting and lose the intended APR transition.

Attack sequence (running epoch, APR0 mode):
1. Vault operates with `unscaledApr == 0`; attacker (any KYC-passing lender) deposits a minimal AA amount.
2. Attacker calls `requestWithdraw`, leaving a dust `apr0Users[attacker].principal` and `apr0TotalPrincipal > 0`.
3. Manager (honest) calls `setAprs(apr > 0)` to begin paying yield again — `unscaledApr != 0` while the bucket is non-zero.
4. `manager.stopEpoch(...)` → `prepareStopEpochWithApr0` reverts `NotAllowed`, repeatedly and permanently while both conditions hold.

### Impact Explanation
Temporary freezing of all vault funds: `stopEpoch` is the gate for epoch rollover, withdraw funding, and interest distribution. While it reverts, no withdraw request can be funded or claimed, no new epoch can start, and interest accounting is stalled — for the cost of a dust deposit plus a withdraw request. If the manager cannot or does not restore APR to 0 promptly, the freeze persists; during a borrower distress scenario this delay directly impairs loss processing via `stopEpochWithDuration(_lossAmount)` as well.

### Likelihood Explanation
The trigger requires the honest manager to raise APR while any APR0 request is pending — a normal operational action the attacker cannot prevent and can cheaply front-run, since the dust request can be placed at any time during the APR0 window and persists across epochs (unsettled APR0 principal survives in `apr0Users`). Attacker cost is negligible; griefing succeeds every time the APR transition is attempted.

### Recommendation
Decouple bucket settlement from the APR check: either allow `prepareStopEpochWithApr0` to settle/close the APR0 bucket with zero interest when `unscaledApr != 0` instead of reverting, or let pending APR0 requests be forcibly settled at `apr0RateByEpoch == 0` during `stopEpoch`, so a single outstanding request cannot veto the epoch state machine.
