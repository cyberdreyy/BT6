### Title
Missing slippage protection in `depositAA`/`depositBB` allows strategy-token donation inflation of the mint price - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`depositAA`/`depositBB` mint tranche tokens at the current `_tranchePrice` with no `minSharesOut` parameter. Because `getContractValue()` counts the raw `strategyToken` balance held by the CDO, an unprivileged attacker who holds IdleCreditVault strategy-token receipts (minted 1:1 to users on `requestWithdraw`) can donate them to the CDO to inflate NAV, force `_updateAccounting` to book the donation as yield, and raise the mint price before a victim's deposit executes. The victim receives fewer tranche tokens than the fair amount, and the shortfall accrues to existing tranche holders — including the attacker.

### Finding Description
The deposit path has no user-controllable bound on shares received:

- `depositAA`/`depositBB` take only `_amount` and forward to `_deposit` [1](#0-0) 
- `_deposit` calls `_updateAccounting()` then mints via `_mintSharesAtCurrPrice(_amount, msg.sender, _tranche)` — `_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` — with no minimum-output check [2](#0-1) 
- `getContractValue()` returns `_contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees`, so an unsolicited `strategyToken` transfer directly raises NAV [3](#0-2) 
- The donation guard `_skimDonatedAssets()` only transfers `token` (underlying) to `feeReceiver`; it does nothing for `strategyToken` donations [4](#0-3) 
- `_updateAccounting` treats any `nav > _lastNAV` delta as gain, accrues a fee, and pushes the remainder into `priceAA`/`priceBB` via `_virtualPriceAux` [5](#0-4) 

Attack sequence (buffer phase, deposits enabled):

1. Attacker is a large AA tranche holder (KYC-passed lender) and also holds `strategyToken` receipts obtained legitimately via `requestWithdraw` on another position or on the secondary market — the tests confirm receipts are minted to `msg.sender` and sit in user balances (`strategyToken bal user`). [6](#0-5) 
2. Attacker transfers `D` strategyTokens directly to the CDO. NAV inflates by `D`; on the next `_updateAccounting` the tranche price rises by roughly `D * (1 - fee) * share` per token.
3. Victim's pending `depositAA(X)` executes. `_updateAccounting` books the donation, the new AA price is `p' > p`, and the victim mints `X * ONE / p'` shares instead of `X * ONE / p` — worth `X * (1 - p/p')` less than fair.
4. The missing shares' value is captured by all existing holders. If the attacker is the dominant holder of that tranche, they recapture the victim's shortfall plus their own donation (minus the performance fee), a net profit at the victim's expense.

The analog to the Napier report is exact in structure: a user-facing function consumes a fixed input (`_amount`) while the output (minted shares) floats with a manipulable spot price, and the protective parameter (`underlyingInMax` / `minSharesOut`) is declared neither as input nor enforced.

### Impact Explanation
Direct theft of deposit value: the victim mints fewer tranche tokens than the economically fair amount, with the difference redistributed to existing tranche holders. Loss is quantified by `X * (p' - p) / p'`. Only unprivileged actors are required — a tranche-token holder combined with a direct strategy-token sender — and no epoch-timing restrictions block it since deposits are open precisely in the buffer phase.

### Likelihood Explanation
Requires the attacker to (a) hold or acquire strategyTokens (possible — they are ordinary ERC20 receipts minted to withdrawers), (b) hold a large fraction of the target tranche for the recapture to exceed the donation cost and fee haircut, and (c) sequence around a victim deposit in the same buffer phase. Profitability is conditional, but no existing guard (skim, `_guarded`, `_checkSameBlock` — which only guards `_withdraw`, KYC, epoch gating) prevents it.

### Recommendation
Add a `minSharesOut` (or `minAmountOut` equivalent) parameter to `depositAA`/`depositBB` (and `depositDuringEpoch`) and revert when `minted < minSharesOut`. Independently, either skim unsolicited `strategyToken` donations in `_skimDonatedAssets` or track strategy-token backing in a state counter rather than reading the raw balance in `getContractValue`.

### Proof of Concept
A Foundry fork test would: deposit a large AA position for the attacker, execute a small `requestWithdraw` to obtain strategyTokens on the attacker, transfer `D` strategyTokens to `cdoEpoch`, then call `depositAA` from a victim address and assert `minted * p' / ONE < X` while `attackerAA_value_after - attackerAA_value_before - D > 0`. Caveat: I did not fully verify the transferability of the IdleCreditVault receipt token (the grep on it did not return before the iteration limit); if `strategyToken` transfers are restricted to the CDO/vault, the donation leg fails and the finding collapses to the weaker "no `minSharesOut` bound" note, which on its own — with price moves driven only by honest manager calls — likely does not meet the bar.

  function _deposit(uint256 _amount, address _tranche) internal virtual whenNotPaused returns (uint256 _minted) {
    if (_amount == 0) {
      return _minted;
    }
    // check that we are not depositing more than the contract available limit
    _guarded(_amount);
    // interest accrued since last depositXX/withdrawXX is splitted between AA and BB
    // according to trancheAPRSplitRatio. NAVs of AA and BB are updated and tranche
    // prices adjusted accordingly
    _updateAccounting();
    // get underlyings from sender
    address _token = token;
    uint256 _preBal = _contractTokenBalance(_token);
    _transferUnderlyingsFrom(msg.sender, address(this), _amount);
    // mint tranche tokens according to the current tranche price
    _minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
    // update trancheAPRSplitRatio
    _updateSplitRatio(_getAARatio(true));

    // direct deposit in the strategy
    IIdleCDOStrategy(strategy).deposit(_amount);
  }
```

  function _updateAccounting() internal virtual returns (bool shutdown) {
    _accrueManagementFee();
    uint256 _lastNAVAA = lastNAVAA;
    uint256 _lastNAVBB = lastNAVBB;
    uint256 _lastNAV = _lastNAVAA + _lastNAVBB;
    uint256 nav = getContractValue();
    uint256 _aprSplitRatio = trancheAPRSplitRatio;
    // If gain is > 0, then collect some fees in `unclaimedFees`
    if (nav > _lastNAV) {
      unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
    }
    (uint256 _priceAA, int256 _totalAAGain) = _virtualPriceAux(AATranche, nav, _lastNAV, _lastNAVAA, _aprSplitRatio);
    (uint256 _priceBB, int256 _totalBBGain) = _virtualPriceAux(BBTranche, nav, _lastNAV, _lastNAVBB, _aprSplitRatio);
    lastNAVAA = uint256(int256(_lastNAVAA) + _totalAAGain);
    lastNAVBB = uint256(int256(_lastNAVBB) + _totalBBGain);

    // Ordinary losses exhaust BB before reducing AA. Stop normal interactions once BB is wiped,
    // or when an AA-only vault is fully wiped, so the loss must be crystallized explicitly.
    if ((_totalBBGain < 0 && -_totalBBGain >= int256(_lastNAVBB)) || (_lastNAV != 0 && nav == 0)) {
      shutdown = true;
      if (!skipDefaultCheck) revert Default();
      // Keep a total wipe distinguishable from an uninitialized vault when no BB NAV existed.
      if (nav == 0) _priceAA = 0;
      _emergencyShutdown(true);
    }
    priceAA = _priceAA;
    priceBB = _priceBB;
  }
```
