### Title
Deposit refunded and NEAR kept in orphaned lockup account after `new` fails - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` batches `create_account`, `deploy_contract`, `transfer(attached_deposit)` and `function_call("new", ...)` into a single receipt, then attaches a `.then(on_lockup_create)` callback. Because NEAR does not roll back earlier actions in a receipt when a later action in the same receipt fails, if the `function_call` to `new` fails after `create_account`/`deploy_contract`/`transfer` already succeeded, `on_lockup_create` sees `is_promise_success() == false` and refunds the *entire* `attached_deposit` to the caller, while the newly created account still physically holds that same NEAR and has deployed (but uninitialized) lockup code.

### Finding Description
The invariant the question asks to check is:
`refunded_amount + NEAR_left_in_created_account == attached_deposit`

Tracing `LockupFactory::create` [1](#0-0) :
- A single `Promise::new(lockup_account_id)` chains `create_account()`, `deploy_contract(CODE)`, `transfer(env::attached_deposit())`, and `function_call(b"new", ...)` — these are actions on **one receipt**, not independent promises.
- `env::attached_deposit()` is used both for the `.transfer()` action and as the `attached_deposit` argument passed to the callback.
- `.then(ext_self::on_lockup_create(...))` schedules the callback with `is_promise_success()` reflecting only whether the *whole* batched receipt succeeded.

In `on_lockup_create` [2](#0-1) , if `is_promise_success()` is `false` (i.e., the receipt failed — which happens if the trailing `function_call` to `new` fails, even though the preceding `create_account`/`deploy_contract`/`transfer` actions already executed and are **not reverted**), the callback unconditionally transfers the *full* `attached_deposit.0` back to `predecessor_account_id`.

The lockup contract's `new` is marked `#[init]` and asserts `!env::state_exists()` implicitly, plus explicit `is_valid_account_id` and foundation/vesting-consistency asserts [3](#0-2) . If this `function_call` fails for any reason (insufficient fixed gas budget `gas::LOCKUP_NEW = 25 TGas`, or any panic path), the target account already:
1. Exists (created),
2. Has the lockup WASM deployed,
3. Holds the full attached NEAR (from `.transfer()`),
4. Has **no initialized state** (since `new` never completed) and **no access keys** (since `create_account()` was called without adding keys).

Because the account has no access keys but is a deployed contract with uninitialized state, **any account** (including the attacker) can subsequently call `new` directly on that lockup account (no access key is required to invoke a public function call on an existing contract account) with arbitrary attacker-chosen parameters, since `#[init]`'s `state_exists()` guard still passes. This lets the attacker take over a funded lockup account and initialize it with parameters of their choosing (their own `owner_account_id`, fabricated `vesting_schedule`, arbitrary `staking_pool_whitelist_account_id`, etc.), while also having already received a full refund of the `attached_deposit` from `on_lockup_create`. Net effect: the invariant is broken — `refunded_amount (= attached_deposit)` PLUS `NEAR left in account (≈ attached_deposit)` exceeds `attached_deposit` by roughly 2x, and the leftover funds sit in an attacker-controllable, protocol-"trusted" lockup contract instance.

None of the existing guards (`assert_self()`, `is_promise_success()`) catch this because they only test receipt-level success/failure, not the fact that earlier actions within the same failed receipt already had durable side effects (account creation, deployment, and fund transfer).

### Impact Explanation
NEAR leaves the factory-created lockup account's legitimate control path: the depositor gets their full deposit refunded AND a duplicate amount of NEAR remains parked in a deployed-but-uninitialized "lockup" contract that anyone can subsequently initialize with attacker-chosen parameters and pass off as a factory-created, trusted lockup. This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" — the code and address are those of a `lockup_contract.wasm` instance under the factory's namespace, but its `owner_account_id`, `vesting_schedule`, and `staking_pool_whitelist_account_id` end up chosen by the attacker instead of the intended creator/factory logic. This is repeatable per attempt/deposit and is not contingent on the foundation, an owner, or a redeploy.

### Likelihood Explanation
The exploit requires only that the trailing `function_call("new", ...)` action inside the single create-account receipt fails after the preceding `create_account`/`deploy_contract`/`transfer` actions have already succeeded. I was able to confirm the code-level root cause (non-atomicity of the batched receipt combined with unconditional full-deposit refund on any failure, and the missing access key on the newly created account leaving `new` callable by anyone) directly in `lockup-factory/src/lib.rs` and `lockup/src/lib.rs`. However, I could **not fully verify from static code review alone a concrete, deterministic, attacker-supplied input** that reliably makes the `function_call` fail while the preceding actions succeed — the most plausible mechanism is exhausting the fixed `gas::LOCKUP_NEW` (25 TGas) budget for the `new()` execution (a scenario that has historically occurred on NEAR due to gas repricing), rather than an input-driven assertion failure, since all attacker-supplied account-ID fields are already typed as `ValidAccountId` and validated before this point, and the factory itself keeps the `vesting_schedule`/`foundation_account_id` combination internally consistent. This introduces uncertainty about repeatability purely at the attacker's discretion versus dependence on gas-budget/environment conditions, which borders the audit's "gas or storage consumption" exclusion for the *triggering mechanism*, even though the *consequence* (double NEAR + hijackable lockup) is a genuine fund-safety defect distinct from a DoS/griefing claim.

### Recommendation
- Do not batch `create_account` + `deploy_contract` + `transfer` + `function_call("new", ...)` into a single receipt whose partial failure leaves funds in an uninitialized, keyless, publicly-callable account. Instead, add a full access key controlled by the factory (or omit the transfer until `new` succeeds), or perform the NEAR transfer only after confirming `new` succeeded (e.g., transfer as part of, or after, the `function_call`, gated by its result) rather than before it.
- Alternatively, on failure in `on_lockup_create`, delete the orphaned account (recovering its balance to the factory or predecessor) via `Promise::new(lockup_account_id).delete_account(beneficiary)` instead of independently re-transferring `attached_deposit` to the predecessor.
- Increase/parameterize `gas::LOCKUP_NEW` with sufficient margin and add monitoring/alerts for `new` call failures post-funding.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
