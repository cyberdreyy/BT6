### Title
Multisig request can execute below the intended confirmation threshold because stale confirmations from removed members are never purged - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
`confirm` in the multisig contracts counts confirmations by string/key identity stored in a `HashSet`, and only removes a member's confirmations from requests that member *originated* when that member is deleted. Confirmations that member placed on *other* still-pending requests are never invalidated. This breaks the equality the contract is supposed to guarantee: `confirmations counted == confirmations by currently-live members`. A request can therefore be executed once it accumulates `num_confirmations` entries in its `HashSet`, even though one or more of those entries belong to a member who has since been removed from the multisig.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only cleans requests where the removed member was the *creator* (`r.member == member`): [1](#0-0) 

It does not scan the `confirmations: LookupMap<RequestId, HashSet<String>>` map for entries confirmed by that member on requests created by *other* members. `confirm` then evaluates the threshold purely by counting HashSet size, with no re-validation that every entry in the set still corresponds to a current member: [2](#0-1) 

`assert_valid_request` similarly never checks that existing confirmations are still held by live members - it only checks that the *caller* is a current member: [3](#0-2) 

The same pattern exists in the older `multisig/src/lib.rs` contract, where `DeleteKey` only purges requests signed by that key, not confirmations made by that key on other requests: [4](#0-3) [5](#0-4) 

**Binding broken:** `confirmations counted for request R == number of currently-live members who confirmed R`. Once a confirming member is removed, this equality is violated for any request they confirmed but did not create, yet the contract still trusts the stale count when deciding to execute.

### Impact Explanation
This lets a multisig request execute with fewer effectively-live confirmations than `num_confirmations` requires. Example with 5 members, `num_confirmations = 3`:
1. Member A creates request X (e.g., `Transfer` to an attacker-controlled account).
2. Member B (compromised/malicious) confirms X → confirmations = {B}.
3. The remaining members detect B is malicious/compromised and remove B via a `DeleteMember` request. Because X was created by A (not B), X and its confirmation set are untouched - B's confirmation for X survives.
4. Members C and D each confirm X, believing it needs 2 more of *their* signatures. Confirmations = {B, C, D} → size 3 ≥ `num_confirmations` → X executes.
5. In reality only 2 currently-live members (C, D) approved X; B's stale confirmation from before removal was still counted, so the transfer executed one signature below the account's real live-member threshold.

This falls squarely under the Critical impact category: "a multisig request executed below threshold," since it lets funds move (or any privileged action execute, including adding a full-access key or deleting further members) without the intended number of *currently authorized* signers.

### Likelihood Explanation
This requires only ordinary multisig operation, no attacker deployment or foundation privilege: a member being removed (for being compromised, offboarded, or malicious) while having outstanding confirmations on other pending requests is a normal and even expected operational sequence for a multisig wallet (key rotation/compromise response). No special timing or race condition is needed beyond the routine order "confirm, then later remove member, then later reach threshold on the older request" - which is a very ordinary usage pattern for these contracts.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over all entries in `confirmations` (not just requests created by that member) and remove the confirming member's entry from every request's `HashSet`. Additionally, `confirm`/`assert_valid_request` should re-validate that every existing confirmation belongs to a currently-live member before counting it toward the threshold, so stale confirmations from removed members can never contribute to reaching `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D, E], num_confirmations = 3)`.
2. As A: `add_request` for `Transfer{amount}` to an arbitrary receiver → request_id X.
3. As B: `confirm(X)` → `confirmations[X] = {B}`.
4. As A/C/D (enough confirmations): submit and confirm a `DeleteMember{member: B}` request, which executes and removes B from `members`, but leaves `confirmations[X]` unchanged (delete_member only purges requests where `r.member == B`, and X's creator is A).
5. As C: `confirm(X)` → `confirmations[X] = {B, C}` (size 2 < 3, not yet executed).
6. As D: `confirm(X)` → `confirmations[X] = {B, C, D}` (size 3 ≥ 3) → `execute_request` fires the transfer, even though B is no longer a member and only C and D are live confirming members. [2](#0-1) [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
