### Title
Guardian retains `submit()` access after removal from `Whitelist` — stale authorization not enforced at point of use ([File: v3/src/core/BaseVault.sol])

### Summary
`BaseVault.submit()` authorizes callers purely by checking `guardianRoots.tryGet(msg.sender)` and never re-validates that the caller is still present in the `Whitelist` contract. Removing an address from the `Whitelist` (e.g., because the guardian key was compromised, or the guardian is being formally revoked) does not automatically clear that guardian's `guardianRoots` entry. A separate function, `checkGuardianWhitelist`, exists to perform this cleanup, but nothing forces it to run atomically with the whitelist removal. This is the same "insufficient session expiration" pattern as CVE-2024-25628: a revoked credential (whitelist membership) does not immediately invalidate the associated privileged session (guardian root), so the invalidated actor continues to pass the authorization check used at the actual access point.

### Finding Description
`_setGuardianRoot` requires `WHITELIST.isWhitelisted(guardian)` only at grant time: [1](#0-0) 

But the enforcement point for actually using guardian privileges, `submit()`, checks only the locally cached `guardianRoots` map, with no reference to `WHITELIST` at all: [2](#0-1) 

Revocation of guardian status is expected to happen via `Whitelist.setWhitelisted(guardian, false)`: [3](#0-2) 

However, that call is on a completely separate contract and has zero effect on `BaseVault.guardianRoots`. The only way to actually clear the stale guardian root is to explicitly call `checkGuardianWhitelist(guardian)` (or `removeGuardian`), which is a distinct, unlinked transaction: [4](#0-3) 

Because `submit()`'s guardian check (`guardianRoots.tryGet(msg.sender)`) never consults `WHITELIST.isWhitelisted`, a guardian whose whitelist status has been revoked continues to pass the guard and can keep calling `submit()` with the merkle proof previously issued to them, executing every operation still authorized by their (stale) root — until someone happens to invoke `checkGuardianWhitelist`/`removeGuardian` in a follow-up transaction. This mirrors alf.io's flaw where a deleted/invalidated user's stale session still passed the admin-area check because invalidation state was checked in a different code path than the one actually gating access.

### Impact Explanation
Vault owners revoke a guardian's whitelist status specifically when that guardian must no longer be trusted (e.g., suspected key compromise or malicious behavior detected). Because `submit()` doesn't re-check the whitelist, the just-revoked (and presumably compromised/malicious) guardian retains full ability to execute every operation still permitted by their merkle root — which typically includes swaps, rebalances, and fund movements through the vault's approved operation set — directly against vault assets. This is a real vector for fund loss/misappropriation, since the entire point of the whitelist revocation is denied in practice: privileged, fund-moving access persists past the moment it was supposed to be terminated.

### Likelihood Explanation
This does not require any admin/guardian collusion to exploit — the precondition is simply the normal, expected admin action of calling `Whitelist.setWhitelisted(guardian, false)` to revoke a guardian. No follow-up call to `removeGuardian`/`checkGuardianWhitelist` is enforced by the protocol, so any deployment/ops sequence that revokes whitelist status without immediately also clearing the guardian root (a very plausible real-world scenario, since these are two separate, unlinked contract calls) leaves an exploitable window where the just-revoked guardian keeps privileged access.

### Recommendation
Enforce the whitelist check directly inside `submit()` (not only at grant time), e.g., `require(WHITELIST.isWhitelisted(msg.sender), Aera__GuardianNotWhitelisted())` before executing operations, or automatically clear `guardianRoots[guardian]` as part of the same transaction that removes an address from `Whitelist` (e.g., have `Whitelist.setWhitelisted` call back into all vaults, or require callers to invoke `checkGuardianWhitelist` atomically). This ensures revocation of guardian status takes effect immediately at the actual point of privileged access, rather than depending on a separate manual cleanup call.

### Proof of Concept
1. Deploy `Whitelist`, `BaseVault` (or `MultiDepositorVault`), set `guardian` as whitelisted, and call `setGuardianRoot(guardian, root)` with a merkle root authorizing at least one fund-moving operation (e.g., a swap/transfer to an arbitrary address in the approved operation set).
2. As `guardian`, call `submit(data)` once to confirm normal operation works.
3. As owner, call `whitelist.setWhitelisted(guardian, false)` to revoke the guardian — do **not** call `baseVault.removeGuardian(guardian)` or `baseVault.checkGuardianWhitelist(guardian)`.
4. Assert `whitelist.isWhitelisted(guardian) == false`.
5. As `guardian` (now unauthorized per the whitelist), call `submit(data)` again with the same/previously-derived merkle proof for an operation that moves vault funds.
6. Assert the call **succeeds** and vault funds move — demonstrating that `Aera__CallerIsNotGuardian()` is never triggered and no whitelist re-check occurs, i.e., the revoked guardian's "session" (guardian root) was never expired at the actual access-control checkpoint.
7. Only after separately calling `checkGuardianWhitelist(guardian)` does a subsequent `submit()` call from `guardian` revert, confirming the gap existed between steps 3–6.

    /// @inheritdoc IBaseVault
    function checkGuardianWhitelist(address guardian) external returns (bool isRemoved) {
        // Requirements: check that the guardian is not in the whitelist
        if (!WHITELIST.isWhitelisted(guardian)) {
            // Effects: set the guardian root to zero
            guardianRoots.remove(guardian);

            isRemoved = true;

            // Log guardian root set
            emit GuardianRootSet(guardian, bytes32(0));
        }
    }

    /// @notice Set the guardian root
    /// @param guardian Address of the guardian
    /// @param root Merkle root
    function _setGuardianRoot(address guardian, bytes32 root) internal virtual {
        // Requirements: check that the guardian address is not zero
        require(guardian != address(0), Aera__ZeroAddressGuardian());

        // Requirements: check that the guardian is whitelisted
        require(WHITELIST.isWhitelisted(guardian), Aera__GuardianNotWhitelisted());

        // Requirements: check that root is not zero
        require(root != bytes32(0), Aera__ZeroAddressMerkleRoot());

        // Effects: set guardian root
        guardianRoots.set(guardian, root);

        // Log guardian root set
        emit GuardianRootSet(guardian, root);
    }
