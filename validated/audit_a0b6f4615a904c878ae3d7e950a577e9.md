### Title
Gasless Stablecoin Transfer DoS via Dust Deposit Manipulating the Remaining-Balance Guard - (File: `crates/sui-core/src/accumulators/funds_read.rs`)

### Summary

The `check_remaining_amounts_after_withdrawal` function on the signing/voting path reads the **current live balance** of the sender's address accumulator via `get_latest_account_amount`, then rejects the transaction if the post-withdrawal remainder falls in the forbidden zone `(0, min_transfer_amount)`. Because any unprivileged holder of an allowlisted gasless token can call `balance::send_funds` to deposit an arbitrary amount into any address balance, an attacker can front-run a victim's gasless withdrawal by depositing a small "dust" amount, pushing the computed remainder into the forbidden zone and causing the signing check to reject the victim's transaction.

### Finding Description

The gasless stablecoin transfer system enforces a minimum-transfer invariant at two points:

1. **Signing/voting path** — `check_remaining_amounts_after_withdrawal` in `crates/sui-core/src/accumulators/funds_read.rs`: [1](#0-0) 

The function reads the **latest unsequenced balance** (`get_latest_account_amount`) and computes:

```
remaining = actual_amount - requested_amount
if remaining == 0 → OK (full withdrawal)
if 0 < remaining < min_amount → REJECT
``` [2](#0-1) 

The trait documentation explicitly states this is an "unsequenced read" that "does not guarantee consistency with the root accumulator version" and "can only be used on the signing/voting path where deterministic results are not required."

2. **Post-execution path** — `check_gasless_execution_requirements` in `sui-execution/latest/sui-adapter/src/temporary_store.rs`: [3](#0-2) 

This second check uses the **declared reservation amount** (not the live balance), so it is not susceptible to the same manipulation.

The attack exploits the signing-path check. `balance::send_funds` is a public function callable by any token holder: [4](#0-3) 

**Attack scenario:**

1. Victim holds `X` units of USDC in their address balance and constructs a gasless transaction to withdraw `X` (their entire balance), declaring `FundsWithdrawal(MaxAmountU64(X))`.
2. Attacker observes the pending transaction and calls `balance::send_funds<USDC>(dust, victim_address)` where `0 < dust < min_transfer_amount` (e.g., `dust = 1`, `min_transfer_amount = 10_000` for USDC at 0.01 minimum).
3. The signing check now reads `actual_amount = X + dust`. With `requested_amount = X`, `remaining = dust`. Since `0 < dust < min_transfer_amount`, the check returns `InvalidWithdrawReservation`.
4. The victim's transaction is rejected at the input-object checking stage before certification.

The snap file confirms this rejection path: [5](#0-4) 

The attacker can repeat this for every retry the victim makes, as long as the victim's declared withdrawal amount does not equal their full current balance.

### Impact Explanation

An unprivileged attacker holding any nonzero amount of an allowlisted gasless token (USDC, USDSUI, USDY, FDUSD, AUSD, USDB, SUI_USDE) can persistently prevent a targeted address from executing gasless stablecoin transfers with a specific declared amount. The victim's gasless transaction is rejected at the signing/voting stage. The victim's funds are **not locked** — they can still use regular (gas-paying) transactions or can attempt to withdraw their entire current balance (leaving `remaining = 0`). However, the victim may not hold SUI for gas, which is precisely the use-case for gasless transfers, making the fallback non-trivial for some users.

This matches the "harmful smart-contract behavior" class under the Medium/High gate, though the practical severity is bounded by the victim's ability to use regular transactions.

### Likelihood Explanation

The attack requires only a tiny amount of the gasless token (1 unit of USDC = $0.000001) and a single `send_funds` call. The attacker does not need any special privilege. The attack is repeatable and cheap. The victim cannot prevent deposits to their address balance, as `send_funds` is unconditionally public.

### Recommendation

Replace the live-balance read in `check_remaining_amounts_after_withdrawal` with the **declared reservation amount** rather than the current on-chain balance. The signing-path check should verify that the declared withdrawal amount itself is either the full declared balance or at least `min_transfer_amount` — without reading the live balance at all. The live balance is already checked for sufficiency by `check_amounts_available`; the remaining-balance guard should be computed from the declared amounts only, consistent with how `check_gasless_execution_requirements` handles it at execution time using `withdrawal_reservations`.

Alternatively, the signing-path remaining-balance check can be removed entirely and enforcement delegated solely to the post-execution check in `check_gasless_execution_requirements`, which already correctly uses the declared reservation and actual accumulator events rather than the live balance.

### Proof of Concept

```
Setup:
  - Victim address A has 10_000 USDC in address balance
  - min_transfer_amount for USDC = 1_000
  - Attacker address B holds 1 USDC

Step 1: Victim constructs gasless PTB:
  withdraw<Balance<USDC>>(10_000) → redeem_funds → send_funds(@C)
  (FundsWithdrawal MaxAmountU64 = 10_000)

Step 2: Attacker front-runs:
  balance::send_funds<USDC>(Balance{value:1}, @A)
  → A's balance is now 10_001

Step 3: Signing check runs:
  actual_amount = 10_001
  requested_amount = 10_000
  remaining = 1
  1 > 0 && 1 < 1_000 → REJECT

Result: "Invalid gasless withdrawal of coin type USDC from address A.
         Gasless transactions must either use the entire address balance,
         or leave at least 1000. Remaining amount would be 1"

Victim's transaction is rejected. Attacker repeats for every retry.
```

```rust
    fn check_remaining_amounts_after_withdrawal(
        &self,
        requested_amounts: &BTreeMap<AccumulatorObjId, (u64, TypeTag, SuiAddress)>,
        min_amounts: &BTreeMap<TypeTag, u64>,
    ) -> SuiResult {
        for (object_id, (requested_amount, type_tag, owner)) in requested_amounts {
            let actual_amount = self.get_latest_account_amount(object_id);
            let remaining = actual_amount.saturating_sub(*requested_amount as u128);
            if remaining == 0 {
                continue;
            }
            let coin_type =
                Balance::maybe_get_balance_type_param(type_tag).unwrap_or_else(|| type_tag.clone());
            if let Some(&min_amount) = min_amounts.get(&coin_type)
                && min_amount > 0
                && remaining < min_amount as u128
            {
                return Err(SuiErrorKind::UserInputError {
                    error: UserInputError::InvalidWithdrawReservation {
                        error: format!(
                            "Invalid gasless withdrawal of coin type {coin_type} \
                             from address {owner}. \
                             Gasless transactions must either use the entire address \
                             balance, or leave at least {min_amount}. \
                             Remaining amount would be {remaining}",
                        ),
                    },
                }
                .into());
            }
        }

        Ok(())
    }
