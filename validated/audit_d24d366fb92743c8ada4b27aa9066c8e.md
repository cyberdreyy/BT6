I need to check the ordering of `epochNumber` increment vs `collectWithdrawFunds` during `stopEpoch` — there's a potential epoch-index mismatch for `lossRecoveryPriceByEpoch`.### Title
Loss-adjusted withdrawal haircut is keyed to the wrong epoch, letting pending receipts claim at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The FFmpeg bug is an out-of-bounds write caused by incorrect packing/indexing. The vault analog is an epoch-index off-by-one: `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` using the epoch counter **after** it has been incremented inside `deposit()` during `stopEpoch`, while user receipts are recorded and later looked up under the pre-increment request epoch (`lastWithdrawRequest[_user]`). The lookup in `_claimLossAdjustedWithdrawRequest` therefore misses, and the haircutted receipt falls through to the par-paying `_claimFundedWithdrawRequest` path.

### Finding Description
- In `IdleCreditVault.requestWithdraw`, receipts are indexed by the **current** `epochNumber` at request time: `withdrawsRequestsByEpoch[_user][currentEpoch]` and `lastWithdrawRequest[_user] = currentEpoch` (lines ~260-294).
- In `deposit()`, called by the CDO during `stopEpoch` while `isEpochRunning()` is still true, `epochNumber += 1` is executed first (lines ~607-610).
- In `collectWithdrawFunds`, when the funded `_amount < pendingWithdraws`, the haircut is stored as `lossRecoveryPriceByEpoch[epochNumber]` (line ~421) — i.e. under the already-incremented epoch `N+1`, not the request epoch `N`.
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 and returns 0 (lines ~789-795).
- Execution then reaches `_claimFundedWithdrawRequest`, whose gate `epochNumber <= lastWithdrawRequest[_user]` now passes (`N+1 > N`), and pays `withdrawsRequests[_user]` at **par**, burning the full receipt and calling `_transferFundedClaim` (lines ~319-349).

The guard added in `requestWithdraw` (lines ~263-271) does not help: it only prevents *new* requests while a non-zero haircut exists at `lastWithdrawRequest` — the haircut is never stored under that key, so it reads zero.

### Impact Explanation
Broken invariant: loss waterfall / fair burn. A pending-withdraw claimant whose receipt should be haircutted by `stopEpochWithDuration(_lossAmount)` instead redeems 1:1 from the strategy's underlying balance. The excess comes directly out of the funded amount meant for *other* claimants of the same loss epoch (or out of recovered/reserved liquidity), so later claimants revert on insufficient balance — i.e., direct theft plus temporary/permanent freezing of remaining claims. The loss equals `claimBasis * (1 - lossRecoveryPrice)` per exploiting claimant, capped by the funded shortfall `pendingBasis - _amount`.

### Likelihood Explanation
Triggerable by any KYC-passing tranche holder: request a withdrawal during the buffer, then wait for an epoch stop where the borrower under-funds `pendingWithdraws` (a `stopEpochWithDuration` loss — an honest-manager action in scope). No privileged misbehavior required; the miscalculation happens entirely in strategy accounting. Caveat: I could not fully confirm the intra-`stopEpoch` call ordering in `IdleCDOEpochVariant.sol` (whether `deposit()`/`epochNumber++` precedes `collectWithdrawFunds`); if the ordering is reversed this exact manifestation collapses, though the same risk applies to `defaultRecoveryEpoch = epochNumber` in `finalizeDefaultRecovery` and `instantWithdrawClaimsByEpoch[epochNumber]` in `defaultPendingClaimBasis`, which share the same post-increment indexing assumption.

### Recommendation
Store loss/recovery data under the **request** epoch, not the post-increment counter: capture `uint256 requestEpoch = epochNumber - 1` (or snapshot `epochNumber` before `deposit()` increments it) in `collectWithdrawFunds` and `finalizeDefaultRecovery`, or key claims by the epoch in which `stopEpoch` began. Add a regression test asserting `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` is non-zero after a lossy stop.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (based on test/foundry/IdleCreditVault.t.sol helpers)
function testLossHaircutKeyedToWrongEpoch() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    idleCDO.depositAA(amountWei);              // user AA deposit
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // buffer of epoch N: request withdraw -> lastWithdrawRequest[user] = N
    uint256 requested = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
    uint256 reqEpoch = strategy.lastWithdrawRequest(address(this));

    _startEpochAndCheckPrices(1);
    // manager stops with a loss: borrower funds only part of pendingWithdraws
    cdoEpoch.stopEpochWithDuration(loss, duration);   // collectWithdrawFunds stores
                                                      // lossRecoveryPriceByEpoch[N+1]

    // haircut was recorded under reqEpoch+1, not reqEpoch
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);
    assertGt(strategy.lossRecoveryPriceByEpoch(reqEpoch + 1), 0);

    // user claims at PAR instead of haircut -> drains other claimants' funded share
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balPre, requested); // should be requested * recoveryPrice
}
```
