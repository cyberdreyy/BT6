### Title
Unchecked Zero Recipient Address in Bridge Token Transfer Allows Permanent Fund Lock — (`crates/sui-framework/packages/bridge/sources/bridge.move` / `bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

Both the Move-side bridge (`send_token`, `send_token_v2`) and the EVM-side bridge (`bridgeERC20`, `bridgeETH`, `bridgeERC20V2`, `bridgeETHV2`) validate the recipient address only for **byte-length** but never check whether the address is all-zeros. A bridge user who supplies a zero recipient address causes tokens to be permanently burned or locked with no recovery path.

---

### Finding Description

**Sui → EVM direction (`bridge.move` `send_token` / `send_token_v2`)**

`send_token` enforces only a length check on `target_address`:

```move
assert!(target_address.length() == EVM_ADDRESS_LENGTH, EInvalidEvmAddress);
assert!(token_amount > 0, ETokenValueIsZero);
``` [1](#0-0) 

A caller may pass `target_address = x"0000000000000000000000000000000000000000"` (20 zero bytes). The tokens are immediately burned on Sui via `send_token_internal` → `inner.treasury.burn(token)`: [2](#0-1) 

The bridge message is stored and the committee signs it. On the EVM side, `_transferTokensFromVault` checks `tokenAddress != address(0)` (the ERC-20 contract address) but **never** checks `recipientAddress != address(0)`:

```solidity
require(tokenAddress != address(0), "SuiBridge: Unsupported token");
// recipientAddress is used directly — no zero check
vault.transferERC20(tokenAddress, recipientAddress, amount);
``` [3](#0-2) 

Tokens are transferred to `address(0)` on EVM — permanently inaccessible.

---

**EVM → Sui direction (`SuiBridge.sol` `bridgeERC20` / `bridgeETH`)**

`bridgeERC20` validates only the byte-length of the Sui recipient address:

```solidity
require(
    recipientAddress.length == SUI_ADDRESS_LENGTH,
    "SuiBridge: Invalid recipient address length"
);
``` [4](#0-3) 

A caller may pass `recipientAddress = bytes(32 zero bytes)`. ERC-20 tokens are transferred into the vault and locked. The committee signs the bridge message. On the Sui side, `claim_token_internal` derives the owner as:

```move
let owner = address::from_bytes(token_payload.token_target_address());
``` [5](#0-4) 

`owner` resolves to `@0x0` (the Sui system address). `claim_and_transfer_token` — callable by **anyone** — then executes:

```move
transfer::public_transfer(token.destroy_some(), owner)
``` [6](#0-5) 

Minted tokens are transferred to `@0x0` and become permanently inaccessible. The EVM vault tokens are also permanently locked because `record.claimed` is set to `true`, closing the only recovery path. [7](#0-6) 

The same pattern exists in `SuiBridgeV2.sol` `bridgeERC20V2` / `bridgeETHV2`: [8](#0-7) 

---

### Impact Explanation

| Direction | EVM-side loss | Sui-side loss |
|---|---|---|
| Sui → EVM | Tokens transferred to `address(0)` (burned) | Tokens burned on Sui |
| EVM → Sui | Tokens permanently locked in vault | Tokens minted to `@0x0` (inaccessible) |

In the EVM→Sui direction the loss is **double**: EVM tokens are locked in the vault forever (no refund mechanism exists once `claimed = true`) and the minted Sui tokens go to the system address. This constitutes **permanent fund lock** and **unintended permanent burning**, matching the High/Medium bounty impact class.

---

### Likelihood Explanation

Any bridge user who accidentally (or through a UI bug) submits a zero recipient address triggers the loss. The `claim_and_transfer_token` function is permissionless, so a third party can finalize the irreversible transfer to `@0x0` without the victim's consent once the committee has signed. No privileged role is required.

---

### Recommendation

**`bridge.move` (`send_token`, `send_token_v2`):** Add a non-zero check on `target_address` before burning the token:

```move
assert!(target_address != vector::tabulate!(EVM_ADDRESS_LENGTH, |_| 0u8), EInvalidEvmAddress);
```

**`SuiBridge.sol` / `SuiBridgeV2.sol` (`bridgeERC20`, `bridgeETH`, `bridgeERC20V2`, `bridgeETHV2`):** Reject all-zero Sui recipient addresses:

```solidity
bool isZero = true;
for (uint i = 0; i < recipientAddress.length; i++) {
    if (recipientAddress[i] != 0) { isZero = false; break; }
}
require(!isZero, "SuiBridge: Zero recipient address");
```

**`_transferTokensFromVault` (both `SuiBridge.sol` and `SuiBridgeV2.sol`):** Add `require(recipientAddress != address(0), "SuiBridge: Zero recipient address");` mirroring the existing `tokenAddress` check. [9](#0-8) 

---

### Proof of Concept

**EVM → Sui (permanent double lock):**

1. Attacker/user calls `SuiBridge.bridgeERC20(tokenID, amount, bytes(new bytes(32)), destinationChainID)` — 32 zero bytes as Sui recipient.
2. ERC-20 tokens are transferred into the vault; `TokensDeposited` event emitted with zero recipient.
3. Bridge committee observes the event and signs the bridge message (no zero-address filter exists in the committee signing path).
4. Anyone calls `bridge::claim_and_transfer_token<T>(bridge, clock, source_chain, seq_num, ctx)` on Sui.
5. `claim_token_internal` derives `owner = @0x0`, mints tokens, sets `record.claimed = true`.
6. `transfer::public_transfer(token, @0x0)` executes — tokens owned by the system address, inaccessible.
7. EVM vault tokens are permanently locked; no refund path exists.

**Sui → EVM (permanent burn):**

1. User calls `bridge::send_token<T>(bridge, target_chain, x"0000000000000000000000000000000000000000", coin, ctx)`.
2. Length check passes (20 bytes); tokens burned on Sui.
3. Committee signs; EVM `transferBridgedTokensWithSignatures` executes.
4. `_transferTokensFromVault` calls `vault.transferERC20(tokenAddress, address(0), amount)` — tokens sent to `address(0)`, permanently burned.
