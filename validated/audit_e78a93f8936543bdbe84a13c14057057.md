### Title
Loss recovery price stored under post-increment epoch, letting haircutted withdraw receipts claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` records a stop-epoch haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` has already been incremented by `deposit()` earlier in the same `stopEpoch` transaction. Withdraw receipts were booked under the pre-increment epoch via `lastWithdrawRequest` / `withdrawsRequestsByEpoch`. Every subsequent lookup keys off the request epoch, so the stored haircut is never found: receipts that were only partially funded can be claimed at par, draining the strategy and leaving later claimants unpaid.

### Finding Description
- During a running epoch `N`, `requestWithdraw` stores receipts under `withdrawsRequestsByEpoch[_user][N]` and sets `lastWithdrawRequest[_user] = N` (`IdleCreditVault.sol:260-293`).
- In `deposit()`, when the CDO calls it while `isEpochRunning()` is still true (i.e. inside `stopEpoch`), the vault executes `epochNumber += 1` (`IdleCreditVault.sol:607-610`). So when `stopEpoch` later calls `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws`, the haircut is written to `lossRecoveryPriceByEpoch[N+1]` — one epoch past the epoch the receipts were recorded under (`IdleCreditVault.sol:411-421`). This is the off-by-one: the recovery index is allocated one slot beyond the slot the receipts occupy.
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. index `N`, finds `0`, and returns early (`IdleCreditVault.sol:789-792`).
- Execution falls into `_claimFundedWithdrawRequest`, whose maturity guard `epochNumber <= lastWithdrawRequest[_user]` (`N+1 <= N`) passes, and it pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` (`IdleCreditVault.sol:326-349`), even though the strategy only received the haircutted amount.
- The same off-by-one defeats the re-request guard in `requestWithdraw` (`IdleCreditVault.sol:261-271`): it checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]` (= index `N`, still `0`), so a user can file a new request in epoch `N+1`, moving `lastWithdrawRequest` forward and permanently orphaning the stored price at `N+1`. This also corrupts the pending-principal accounting for subsequent epochs.

### Impact Explanation
The borrower funds only `pendingBasis * lossRecoveryPrice`, but claimants draw `pendingBasis` at par. The first claimants to call `claimWithdrawRequest` after the loss epoch over-withdraw; once the funded reserve is exhausted, later claimants' transfers revert — direct insolvency / permanent freezing of the tail of the withdraw queue. Quantified loss = `pendingBasis - fundedAmount` (the haircut), which can be arbitrarily large up to the full pending-withdraw bucket. Broken invariant: one-receipt-one-payout and loss socialization.

### Likelihood Explanation
Requires a `stopEpochWithDuration(_lossAmount)` with `_lossAmount > 0` while `pendingWithdraws > 0` — a routine partial-loss epoch, not an edge case. Any affected receipt holder (unprivileged KYC'd lender) can trigger the over-claim; the bug is deterministic given the index mismatch. No privileged misbehavior needed — the honest manager simply stops the epoch with a loss.

### Recommendation
Store the haircut under the epoch the receipts were booked in. Either capture `uint256 requestEpoch = epochNumber - 1` (or a stored `pendingWithdrawsEpoch`) in `collectWithdrawFunds` and write `lossRecoveryPriceByEpoch[requestEpoch]`, or move the `epochNumber` increment in `deposit()` to after the collect call. Additionally index `lossRecoveryPriceByEpoch` lookups consistently (store the request epoch alongside `pendingWithdraws` rather than relying on `lastWithdrawRequest`).

### Proof of Concept
Foundry fork test (sketch — mirrors the harness in `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testLossReceiptOffByOne() external {
    _stopCurrentEpoch();            // epoch 0 -> 1 (buffer)
    uint256 tr = _depositWithUser(user1, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch();          // running epoch 1
    _requestWithdrawWithUser(user1, tr);               // receipt booked at epoch 1
    // stop with partial loss: borrower funds only half the pending basis
    _stopCurrentEpochWithLoss(pendingBasis / 2);       // deposit() bumps epochNumber to 2,
                                                       // lossRecoveryPriceByEpoch[2] = 0.5e18
    assertEq(strategy.lossRecoveryPriceByEpoch(2), 0.5e18);
    assertEq(strategy.lossRecoveryPriceByEpoch(1), 0); // receipt epoch has no price
    // claim pays at par instead of 50%
    uint256 pre = underlying.balanceOf(user1);
    vm.prank(user1); cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(user1) - pre, pendingBasis); // over-claim of pendingBasis/2
    // second user's claim now reverts on insufficient funded balance
    vm.expectRevert();
    vm.prank(user2); cdoEpoch.claimWithdrawRequest();
}
```

Caveat: this conclusion assumes `collectWithdrawFunds` is invoked after the epoch-bumping `deposit()` inside `stopEpoch` (the comment at `IdleCreditVault.sol:607-609` confirms deposits during `stopEpoch` perform the increment); verifying the exact call order in `IdleCDOEpochVariant._stopEpoch` is recommended, since the grep results did not surface its body.
