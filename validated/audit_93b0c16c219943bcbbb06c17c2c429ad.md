### Title
Attacker-chosen `MessageId` collision in `savedCallbacks` map causes cross-user trigger response delivery - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each user's response callback keyed solely by the attacker-controlled `msg.Body.MessageId` [1](#0-0) , unconditionally overwriting any existing entry for that key. `handleWebAPITriggerMessage` then delivers the first node response to whichever `savedCallback` currently occupies that map slot, identified only by `msg.Body.MessageId`, with no sender/session binding check [2](#0-1) . Two concurrent requests to the same DON using the same `MessageId` therefore let one caller's callback silently replace another's, causing a legitimate user's trigger response to be delivered to a different (attacker-controlled) caller.

### Finding Description
The gateway HTTP entrypoint (`gateway.ProcessRequest`) validates message structure/signature via `msg.Validate()` [3](#0-2)  but places no constraint that `MessageId` is unique, unpredictable, or tied to the requester beyond signature validity. `msg.Body.MessageId` is a free-form string chosen entirely by the caller, limited only by `MessageIdMaxLen` and a non-null-terminator rule [4](#0-3) ; the code explicitly notes allowlisting/rate-limiting is not yet applied for legacy messages (`// TODO: apply allowlist and rate-limiting here`) [5](#0-4) , so any party able to produce a validly-signed message (using any ECDSA keypair, not necessarily a DON-authorized one at this layer) can reach `HandleLegacyUserMessage`.

In `HandleLegacyUserMessage`, the callback for a request is stored with:
```go
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
```
with no check for an existing entry under that key [1](#0-0) . If a second signed request with the identical `MessageId` string arrives for the same `DonId` while the first is still outstanding, it silently overwrites the map entry, replacing the first caller's `Callback` reference.

When a node later responds with `MethodWebAPITrigger` and that `MessageId`, `handleWebAPITriggerMessage` looks the entry up and delivers the payload to whatever `savedCallback` is currently stored, deleting it from the map:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ...})
``` [2](#0-1) 
There is no verification that the response actually corresponds to the request that originally registered under that key (no requester/session token, no nonce binding). The only sender check performed, `msg.Body.Sender != nodeAddr` in `HandleNodeMessage` [6](#0-5) , validates the node's identity, not which user's callback should receive the payload — it does nothing to prevent map-slot hijacking between two competing HTTP callers.

Exploit flow: an unauthenticated/unprivileged client (any holder of an ECDSA key, since no allowlist is enforced at this layer) sends a legacy `web_api_trigger` message to a known `DonId` with `MessageId="X"`. While that request is still pending (`callback.Wait(ctx)` in `gateway.ProcessRequest`) [7](#0-6) , the attacker races a second signed message to the same `DonId` reusing `MessageId="X"`, overwriting `h.savedCallbacks["X"]` with their own callback. Whichever node response for `MessageId="X"` arrives first (which may be the response to the legitimate victim's trigger, since both requests are dispatched to the same DON members) is delivered to the attacker's HTTP connection instead of the victim's, and vice versa — a straightforward cross-user response confusion.

### Impact Explanation
This is a cross-user response confusion vulnerability: an attacker can receive another user's workflow-trigger response data by simply colliding `MessageId` values, without any privileged access. Depending on payload content this exposes response data intended for a different caller and denies the legitimate caller its own response (their `callback.Wait` will time out since the entry was deleted/redirected). This matches the "cross-user response confusion" / unauthorized-disclosure impact class called out in scope.

### Likelihood Explanation
No privileged access is required — only the ability to send a validly-signed legacy gateway message (any keypair works since allowlisting is explicitly not yet enforced per the code's own TODO) and knowledge of a target `DonId`, which is not secret. `MessageId` collision requires either (a) predictable/enumerable IDs used by the victim client, or (b) the attacker itself choosing to race a `MessageId`, which is entirely under attacker control and unbounded (they can attempt many concurrent collisions). This makes the attack straightforward to script and repeat.

### Recommendation
Bind each `savedCallback` to a server-generated, unpredictable correlation identifier (or hash it with the requester's verified signer address / connection identity) rather than trusting the client-supplied `MessageId` alone. Reject `HandleLegacyUserMessage` calls that attempt to reuse a `MessageId` currently present in `h.savedCallbacks` for the same `DonId`, and validate on response delivery that the responding node was actually one dispatched-to for that specific stored callback (e.g., store and check the expected node set / original sender binding), not merely match by `MessageId`.

### Proof of Concept
Handler-level Go test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler+mock DON as in existing tests (`setupHandler`).
2. Craft `msgA := triggerRequest(t, keyA, ..., messageID="X")` and `msgB := triggerRequest(t, keyB, ..., messageID="X")` targeting the same `donID`.
3. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` then immediately `handler.HandleLegacyUserMessage(ctx, msgB, cbB)`, asserting via internal state (`h.savedCallbacks["X"]`) that the stored callback is now `cbB`.
4. Simulate a node response for `msgA` (`hc.ValidatedResponseFromMessage(msgA)`) via `handler.HandleNodeMessage`.
5. Assert that `cbB.Wait(ctx)` (not `cbA`) receives the response payload for `msgA`, and that `cbA.Wait(ctx)` times out — demonstrating the victim's response was delivered to the attacker's callback.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()
