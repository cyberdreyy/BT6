### Title
Cross-user response confusion via `MessageId` collision in WebAPI trigger `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's WebAPI capabilities handler stores in-flight user callbacks in `h.savedCallbacks` keyed only by the attacker-controlled `msg.Body.MessageId`, with no uniqueness check or binding to the requester's identity. A second (attacker) request using the same `MessageId` as a pending victim request silently overwrites the victim's callback entry, so the next node response bearing that `MessageId` is delivered to whichever caller's callback is currently in the map. Note: the question cites `core/web/router.go` as the location of `handleWebAPITriggerMessage`/`savedCallbacks`, but that file contains only the node's HTTP/GraphQL router setup and has no relation to this logic — the actual code lives in `core/services/gateway/handlers/capabilities/handler.go` (and an identical pattern in `core/services/gateway/handlers/handler.dummy.go`).

### Finding Description
`HandleLegacyUserMessage` registers a pending callback keyed purely by `msg.Body.MessageId` with an unconditional map write, not an insert-if-absent: [1](#0-0) 

There is no check for `_, exists := h.savedCallbacks[msg.Body.MessageId]` before writing, so a second request with a colliding `MessageId` overwrites the first entry's `*savedCallback` (which holds the original caller's `Callback`) without warning or error.

When a node responds with method `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks the response up strictly by `MessageId` and delivers it to whatever callback is currently registered under that key, then deletes the entry: [2](#0-1) 

`MessageId` is fully attacker-controlled: `Message.Validate()` only checks length/format constraints (non-empty, ≤128 bytes, no trailing null byte) and derives `Sender` from the ECDSA signature, but it never ties `MessageId` uniqueness to `Sender`, nor rejects a `MessageId` reused by a different signer: [3](#0-2) 

Exploit flow:
1. Victim signs and submits a legacy WebAPI trigger message with `MessageId = "X"`. `HandleLegacyUserMessage` runs, stores `savedCallbacks["X"] = victimCallback`, and forwards the request to all DON members.
2. Attacker (any holder of a valid signing key able to submit gateway legacy messages — no special privilege required) submits their own signed message with the same `MessageId = "X"` before the victim's response arrives. This overwrites `savedCallbacks["X"]` with the attacker's own callback; the victim's `*savedCallback` reference is dropped from the map with no notification.
3. When any DON node responds to the victim's original request, `handleWebAPITriggerMessage` matches on `MessageId = "X"`, finds the attacker's callback now registered, and delivers the victim's node response payload (which may include the victim's requested capability output) to the attacker.
4. Alternatively, if the attacker's forged request's response arrives first, it consumes the slot and the victim's own request is later found `!found` and silently dropped, causing the victim to never receive a response (denial of response / hang until the caller's own timeout).

No component in this path validates that the responder-to-callback binding is unique per submitter; the signature only authenticates the sender of the *original request*, and is not used to guard the `savedCallbacks` map key.

### Impact Explanation
This allows cross-user response leakage: an attacker can redirect a victim's WebAPI-trigger capability execution result to themselves by winning a `MessageId` collision race, or cause denial-of-response for the victim. This falls under Chainlink's "unauthorized disclosure of another user's request/response data" / "cross-user request-response confusion" impact class for the Gateway service, since gateway responses can contain workflow-execution output data intended only for the original requester.

### Likelihood Explanation
- No special privilege is required beyond the ability to submit a signed legacy gateway message (any address able to construct a valid ECDSA signature over the message body, as accepted by `Message.Validate()`/`ExtractSigner`).
- The attacker only needs to guess or observe a pending victim `MessageId` (e.g., if MessageIds are predictable, sequential, or observable via other channels) and win a timing race against the node response.
- This is fully reproducible in a unit test that calls `HandleLegacyUserMessage` twice with the same `MessageId` from two different signers, then invokes `HandleNodeMessage`/`handleWebAPITriggerMessage`, and observes which callback receives the response.
- Feasibility of winning the race depends on external timing (network/node latency), which introduces some non-determinism in production but is deterministic and trivially demonstrable in a unit test/PoC.

### Recommendation
- Reject `HandleLegacyUserMessage` requests whose `MessageId` already has a live entry in `savedCallbacks` (return a `MessageIdCollisionError` to the caller rather than silently overwriting).
- Key `savedCallbacks` by a composite of `(Sender, MessageId)` or by a gateway-generated unique correlation ID, rather than trusting client-supplied `MessageId` alone.
- Apply the same fix to `core/services/gateway/handlers/handler.dummy.go`'s `HandleLegacyUserMessage`, which has the identical unconditional-overwrite pattern.

### Proof of Concept
Go unit test plan (added to `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` via `NewHandler` with a mock `handlers.DON`.
2. Sign message A (`MessageId = "collide"`) with victim's private key; call `handler.HandleLegacyUserMessage(ctx, msgA, victimCallback)`. Assert `savedCallbacks["collide"]` is set to the victim's callback.
3. Sign message B (`MessageId = "collide"`, different payload) with attacker's private key; call `handler.HandleLegacyUserMessage(ctx, msgB, attackerCallback)`.
4. Assert (expected-to-fail-today) that `savedCallbacks["collide"]` still references `victimCallback` (currently it will reference `attackerCallback`, demonstrating the overwrite bug).
5. Simulate a node response for message A's `MessageId` via `handler.HandleNodeMessage(ctx, respForA, nodeAddr)`.
6. Assert that `victimCallback.SendResponse` (via `hc.NewCallback().Wait`) receives the response containing message A's payload — currently it will instead be delivered to `attackerCallback`, proving cross-user response confusion.
7. Add a variant test asserting `HandleLegacyUserMessage` returns an explicit error/rejection when a `MessageId` collision with a pending different-sender request is detected (post-fix expected behavior).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {

	}

	return nil
