### Title
Unauthenticated flooding of `HandleLegacyUserMessage` allows attacker to evict a victim's pending `savedCallback` via `pruneCallbacks`, silently dropping the victim's node response - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`pruneCallbacks` evicts the oldest half of `savedCallbacks` purely by creation time whenever the map exceeds `MaxSavedCallbacks`, with no per-sender fairness or allowlist check on the code path that populates the map (`HandleLegacyUserMessage` explicitly has a `// TODO: apply allowlist and rate-limiting here` at line 384). An attacker who can submit many `HandleLegacyUserMessage` requests can inflate `savedCallbacks` past `MaxSavedCallbacks`, causing the next `pruneCallbacks` tick to evict a victim's older-but-still-pending entry before the victim's legitimate node response arrives via `handleWebAPITriggerMessage`.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) stores every accepted request in the shared map keyed by `msg.Body.MessageId`: [1](#0-0) 
There is no allowlist or per-sender rate limit at this call site — this gap is explicitly acknowledged in a `TODO` comment: [2](#0-1) 
The only rate limiter present, `nodeRateLimiter`, is applied to `handleWebAPIOutgoingMessage` (node → client direction), not to inbound user submissions: [3](#0-2) 

`pruneCallbacks` runs on a timer and, once the map exceeds `MaxSavedCallbacks`, sorts *all* entries by `createdAt` and deletes the oldest `len(entries)-maxSize/2`: [4](#0-3) 
This eviction is purely time-ordered and has no concept of sender identity, so a flood of new entries from any source pushes out old entries irrespective of who created them.

When the victim's legitimate node response later arrives, `handleWebAPITriggerMessage` looks up the callback by `MessageId` and silently returns `nil` if not found — no error is surfaced to the victim: [5](#0-4) 

**Why I could not fully validate exploitability**: `HandleLegacyUserMessage` requires a valid, verifiable signed message (`common.ValidatedRequestFromMessage`, line 397) and stores callbacks keyed by `MessageId`, not by sender/user identity — so the "isolation" invariant as framed (one user's request evicting another's) already assumes any caller who can produce a validly-signed message counts as "unauthenticated" because there's no allowlist gating *which* signers are accepted, not because there's no authentication at all. I was unable to trace, within the available tool budget, whether an upstream layer (e.g. `gateway.go` HTTP routing, DON allowlist config, or a per-DON dedicated `WebAPICapabilitiesAllowedSenders` check) restricts which addresses can invoke this handler before reaching `HandleLegacyUserMessage`. If such an allowlist exists upstream, the attacker would need a valid allowlisted signing key, materially changing likelihood. The `TODO` comment at line 384 within this exact function suggests no allowlist is enforced at this specific layer, supporting the attacker's ability to submit many distinct messages, but I could not conclusively rule out an outer authorization gate on the gateway HTTP endpoint that serves this handler.

### Impact Explanation
If exploitable as described, impact is a targeted denial-of-service: a specific victim's legitimate node-computed HTTP trigger response is discarded without any error surfaced to the victim, effectively silently failing their request (response-loss / DoS class, not fund loss or credential disclosure).

### Likelihood Explanation
Feasibility requires the attacker to be able to submit `MaxSavedCallbacks/2 + 1` (default `10001`) validly-formed and signed `HandleLegacyUserMessage` requests with fresh `MessageId`s before the next prune tick (default every 30s) and before the victim's node response returns. This is a substantial but plausible volume for a scripted attacker if no upstream allowlist/rate-limit exists on inbound legacy user messages, consistent with the code-level `TODO` acknowledging the missing allowlist/rate-limiting at this exact function. The requirement to target a *specific known* victim `MessageId` and win a timing race against the real node response adds some practical difficulty, but the underlying design flaw (creation-time-only eviction, no isolation by sender) is real and directly present in `pruneCallbacks`.

### Recommendation
- Bound per-sender pending-callback counts (e.g., a `map[senderAddr]int` count alongside `savedCallbacks`) and reject/rate-limit new submissions from senders who already hold many pending entries, rather than allowing unbounded growth from a single source to trigger global eviction.
- Enforce the `TODO`'d allowlist/rate-limiting in `HandleLegacyUserMessage` before inserting into `savedCallbacks`.
- Consider evicting per-sender fairly (e.g., round-robin or proportional eviction) instead of pure global creation-time ordering, so no single sender can starve others out of the shared cache.
- Surface an explicit error/metric when a callback is evicted before use, rather than silently dropping it, so at minimum monitoring can detect exploitation attempts.

### Proof of Concept
Extend `TestPruneCallbacks` in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Set `MaxSavedCallbacks` to a small test value (e.g., 10).
2. Create one "victim" callback via `HandleLegacyUserMessage` with a known `MessageId` and a callback mock that records whether `SendResponse` is invoked.
3. Flood the handler with `MaxSavedCallbacks/2 + 1` additional `HandleLegacyUserMessage` calls with fresh `MessageId`s (simulating an unprivileged flooding sender), advancing creation timestamps so they are newer than the victim's entry.
4. Invoke `pruneCallbacks()` directly (or wait for the prune ticker) and assert the victim's `MessageId` is no longer present in `h.savedCallbacks`.
5. Simulate the victim's legitimate node response via `HandleNodeMessage` with `MethodWebAPITrigger` and the victim's `MessageId`; assert `handleWebAPITriggerMessage` returns `nil` with no error, and assert the victim's callback mock's `SendResponse` was **never called** — demonstrating silent response loss with no client-facing error.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

	maxSize := h.config.MaxSavedCallbacks

		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
