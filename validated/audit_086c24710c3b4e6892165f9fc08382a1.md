### Title
Global unauthenticated request-ID map in confidentialrelay handler enables cross-user existence side-channel - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`HandleJSONRPCUserMessage` performs no sender authentication or per-owner namespacing before calling `newActiveRequest`, unlike the sibling vault handler which prefixes `req.ID` with the authorized owner. Because `h.activeRequests` is a single global map keyed only on the raw, caller-supplied `req.ID`, an attacker who can reach the gateway HTTP endpoint for this DON can submit a guessed/known `req.ID` and learn — via the differential "request ID already exists" error vs. a success response — whether another user currently has a matching in-flight relay request.

### Finding Description
`HandleJSONRPCUserMessage` only validates that `req.ID` is non-empty and ≤200 chars before calling `h.newActiveRequest(req, callback)`: [1](#0-0) 

`newActiveRequest` keys the single global `h.activeRequests` map purely by `req.ID`, with no binding to a sender/owner identity: [2](#0-1) 

This is confirmed to be intentional collision behavior by the handler's own test, which asserts that a second, unrelated caller sending the same `req.ID` gets the collision error rather than being treated as a distinct request: [3](#0-2) 

By contrast, the vault handler in the same package family binds the request ID to the caller's authorized owner *before* storing it, via `authorizedOwner + RequestIDSeparator + originalRequestID`, so that requests from different owners can never collide on the raw ID even if they reuse the same client-chosen ID: [4](#0-3) 

The confidentialrelay handler has no equivalent authorization/ownership binding step at the gateway layer — the gateway's `ProcessRequest` routes the raw JSON-RPC request straight to `HandleJSONRPCUserMessage` (only a generic JWT auth token is optionally attached at decode time, which is not used here to namespace request IDs), and the actual attestation/ownership check happens later, inside the DON enclave logic (`core/capabilities/confidentialrelay/handler.go`), not at the gateway request-admission stage: [5](#0-4) 

Because request IDs for `MethodCapabilityExec`/`MethodSecretsGet` are workflow/execution-derived (e.g. `workflow_id`/`execution_id`-based identifiers used across the confidential relay protocol), they are plausibly guessable or discoverable through other channels (e.g., observing on-chain workflow triggers), and any unauthenticated caller reaching this gateway service can send a `HandleJSONRPCUserMessage` request with a candidate ID and directly observe the collision error to confirm that a specific victim workflow execution currently has an in-flight relay request.

### Impact Explanation
This is a low-severity information side channel: it discloses only the existence/timing of another party's in-flight confidential-relay request (a boolean presence signal plus rough timing window bounded by `RequestTimeoutSec`), not any secret data, response content, or actionable authorization bypass. It does not allow reading, forging, or disrupting the victim's request (the victim's original `activeRequest` and callback are untouched; the attacker's colliding call is simply rejected). It maps to Chainlink's "informational disclosure" / minor side-channel bounty class rather than authentication bypass or fund/data exposure, since no cross-user data or control is obtained — only existence/timing metadata.

### Likelihood Explanation
Exploitability requires only unprivileged access to the gateway HTTP endpoint serving this DON/service and knowledge or a guess of a target `req.ID`. No credentials, roles, or special access are needed beyond what's needed to submit any confidentialrelay request. The main constraint is guessability of the victim's `req.ID`; if IDs are derived from public/discoverable values (workflow ID + execution ID patterns used elsewhere in this system), the side channel is straightforward and repeatable, though this repo does not show the exact ID-generation scheme for the confidentialrelay caller, so guessability strength is not fully confirmed from these files alone.

### Recommendation
Namespace `h.activeRequests` keys by authenticated sender/owner (mirroring the vault handler's `owner + RequestIDSeparator + req.ID` pattern) so that a colliding raw ID from a different, unauthenticated/unrelated caller cannot be distinguished from a fresh ID. At minimum, add an authorization step before `newActiveRequest` that establishes caller identity for the confidentialrelay method, and salt/scope the map key with that identity so only the original submitter or the authorized party can trigger or observe the "already exists" collision for a given logical execution.

### Proof of Concept
Go handler-level integration test:
1. Instantiate the handler as in `handler_test.go`'s `setupHandler`.
2. As "victim," call `h.HandleJSONRPCUserMessage(ctx, req1, cb1)` with `req1.ID = "wf1-exec1"` and a real `MethodCapabilityExec` payload — expect `nil` error (request now active).
3. As "attacker" with a distinct `Callback` and no authentication/ownership relation to the victim, call `h.HandleJSONRPCUserMessage(ctx, req2, cb2)` using the **same** `ID = "wf1-exec1"` but attacker-controlled/irrelevant params.
4. Assert the attacker's call returns `"request ID already exists: wf1-exec1"` (as already demonstrated generically in `TestConfidentialRelayHandler_DuplicateRequestID`), proving that an arbitrary, non-owning caller can detect the existence of another party's in-flight request via the differential error, without any authorization check preventing it.
5. Contrast with expected fix behavior: after adding per-owner namespacing, assert the attacker's identically-ID'd request is treated as a distinct entry (owner-prefixed key) rather than colliding, i.e., no leakage of the victim's request existence.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}

func (p *GatewayVaultRequestProcessor) authorizeAndStamp(
	ctx context.Context,
	req *jsonrpc.Request[json.RawMessage],
	stamp func(prefixedRequestID string) error,
) (*AuthorizedGatewayVaultRequest, error) {
	incomingOwner := ""
	if idx := strings.Index(req.ID, vaulttypes.RequestIDSeparator); idx != -1 {
		incomingOwner = req.ID[:idx]
	}

	p.lggr.Debugw("authorizing gateway vault request", "method", req.Method, "requestID", req.ID)
	authResult, err := p.authorizer.AuthorizeRequest(ctx, *req)
	if err != nil {
		authErr := fmt.Errorf("request not authorized: %w", err)
		p.lggr.Errorw("gateway vault request authorization failed", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "incomingOwner", incomingOwner, "error", authErr)
		return nil, authErr
	}

	originalRequestID := req.ID
	authorizedOwner := authResult.AuthorizedOwner()
	prefixedRequestID := authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID
	req.ID = prefixedRequestID
