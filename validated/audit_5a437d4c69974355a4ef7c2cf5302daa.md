### Title
Claimed instant-withdraw receipts are never removed from the per-epoch claim ledger, letting a user claim the same receipt twice after default finalization — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The external bug is a "count the new entry before clearing the old one" flaw: the same actor's repeated action is added to an aggregate without removing the prior contribution, producing an inflated count. The analog lives in `IdleCreditVault`'s instant-withdraw receipt accounting. `claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. Those per-epoch fields are exactly what `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` later read when a default is finalized in that same epoch. A user can therefore claim an instant receipt at par while funded, and—after requesting a fresh instant withdraw post-finalization to re-acquire receipt tokens—claim the same stale basis again from `defaultRecoveryReserve`.

### Finding Description
In `requestInstantWithdraw`, three counters are incremented together: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . The normal claim path only clears the aggregate: it burns `instantWithdrawsRequests[_user]`, sets it to 0, and pays out, leaving both per-epoch entries intact [2](#0-1) .

The per-epoch entries are only consumed by the default path: `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, and `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [3](#0-2) [4](#0-3) .

Attack sequence:

1. Epoch E is running with instant withdrawals enabled. Attacker requests an instant withdraw of `A`. Receipt tokens `A` are minted to the attacker; `instantWithdrawsRequestsByEpoch[attacker][E] = A`, `instantWithdrawClaimsByEpoch[E] = A`, `pendingInstantWithdraws = A`.
2. The CDO funds the queue (`collectInstantWithdrawFunds`), `pendingInstantWithdraws` returns to 0. Attacker calls `claimInstantWithdrawRequest`, burns `A`, receives `A` underlying at par. Stale `byEpoch` entries remain `A`.
3. Another user requests `B` instantly; it stays unfunded, so `pendingInstantWithdraws = B` but `instantWithdrawClaimsByEpoch[E] = A + B` still includes the already-paid `A`.
4. Borrower defaults; `finalizeDefaultRecovery` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[E]`—overstated by `A`—and sets `defaultInstantWithdrawsFinalized = true` since `pendingInstantWithdraws != 0` [5](#0-4) . `_defaultPrefundedInstantReserve` also counts `A` as already-reserved underlying that was actually paid out [6](#0-5) .
5. `requestInstantWithdraw` has no default/finalization guard: the attacker calls it again via the CDO's instant-withdraw entry point, minting fresh receipt tokens [7](#0-6) .
6. Attacker calls `claimInstantWithdrawRequest`; `_claimDefaultedInstantWithdrawRequest` sees the stale `A` basis for `defaultEpoch = E`, burns `A` from the fresh receipts, and pays `A * defaultRecoveryPrice` out of `defaultRecoveryReserve`—a second payout for a receipt already redeemed at step 2 [8](#0-7) .

### Impact Explanation
Direct theft of the isolated default-recovery reserve. The stale per-epoch basis (i) inflates `totalBasis` in `finalizeDefaultRecovery`, diluting `defaultRecoveryPrice` for all defaulted claimants, and (ii) lets the attacker withdraw `A * recoveryPrice` a second time from `defaultRecoveryReserve`, which is decremented per claim [9](#0-8) . Loss is bounded by the attacker's instant-withdraw size but repeatable per epoch's worth of stale entries; other claimants' recovery is correspondingly reduced—an insolvency of the reserve. The "one receipt, one payout" invariant is broken.

### Likelihood Explanation
Requires: an instant-withdraw-enabled epoch where at least one receipt is claimed before finalization, a default finalized while `pendingInstantWithdraws != 0` (partially unfunded queue—common when instant liquidity runs short), and CDO-side reachability of `requestInstantWithdraw` after finalization (the strategy itself does not gate it). The attacker needs no privilege—only a KYC'd position with tranche tokens. No existing guard (the reserve isolation check in `_transferFundedClaim`, KYC, `_onlyIdleCDO`) stops the stale-entry claim.

### Recommendation
Keep the three ledgers consistent on every claim path. In `claimInstantWithdrawRequest`, before zeroing the aggregate, subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epoch]` (and `instantWithdrawClaimsByEpoch[epoch]`) for the relevant epoch(s)—e.g.:

```diff
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
+ uint256 curEpoch = epochNumber;
+ if (instantWithdrawsRequestsByEpoch[_user][curEpoch] >= amount) {
+   instantWithdrawsRequestsByEpoch[_user][curEpoch] -= amount;
+   instantWithdrawClaimsByEpoch[curEpoch] -= amount;
+ }
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Additionally, gate `requestInstantWithdraw` on `!defaultRecoveryFinalized`, mirroring the protection added to `requestWithdraw` [10](#0-9) .

### Proof of Concept
Foundry fork PoC (scaffold consistent with `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testInstantReceiptDoubleClaimAfterDefault() external {
    // Epoch E running, instant withdraws enabled via setInstantWithdrawParams
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _depositWithUser(victim,   100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 1) attacker requests instant withdraw, gets funded, claims at par
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(attackerTranches, address(AAtranche));
    _fundInstantWithdraws(); // borrower funds; pendingInstantWithdraws == 0
    uint256 paid1 = _claimInstant(attacker); // burns A receipts, pays A at par
    assertGt(paid1, 0);

    // 2) victim requests instant withdraw, stays unfunded
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(victimTranches, address(AAtranche));
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // 3) borrower defaults; manager finalizes recovery in same epoch
    _defaultAndFinalize(recoveredAmount, manager);
    assertTrue(strategy.defaultInstantWithdrawsFinalized());

    // 4) attacker re-requests instant withdraw post-default to get fresh receipts
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(dust, address(AAtranche)); // mints new receipts

    // 5) stale byEpoch basis pays attacker a second time from recovery reserve
    uint256 reservePre = strategy.defaultRecoveryReserve();
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 reservePost = strategy.defaultRecoveryReserve();
    assertLt(reservePost, reservePre); // attacker claimed already-paid basis
}
```

Note: I could not fully verify the CDO-side gating of `requestInstantWithdraw` after `defaultRecoveryFinalized` in `IdleCDOEpochVariant` within this session; if a `defaulted()`/closed check exists there, step 4 would instead require claiming in the same transaction ordering or finding an unguarded entry, but the stale-ledger issue itself (never decremented on the funded claim path) is confirmed in the strategy code.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
