### Title
Failed `new()` after account creation leaves both a refund and a funded, uninitialized attacker-controllable staking pool account - (File: `staking-pool-factory/src/lib.rs`)

### Summary
`create_staking_pool` chains `create_account().transfer(deposit).deploy_contract(...).function_call(b"new", ...)` as one promise batch, then refunds the deposit in `on_staking_pool_create` if `is_promise_success()` is false [1](#0-0) [2](#0-1) . Because NEAR only rolls back the state changes of the specific action that fails (the `FunctionCall` to `new`), and not the preceding `create_account`/`transfer`/`deploy_contract` actions in the same receipt, a deliberately-failed `new()` leaves the new account created, funded with the full deposit, and running the staking-pool wasm - while the factory independently refunds the same deposit amount to the caller.

### Finding Description
The claimed binding is: `refund_amount + balance_left_at(staking_pool_account_id) == attached_deposit`. The code assumes this holds because `on_staking_pool_create` treats promise failure as "nothing happened" and unconditionally refunds: [3](#0-2) 

but `create_account()`, `transfer(attached_deposit)` and `deploy_contract(...)` are separate actions in the same action receipt as the `function_call(b"new", ...)` — if only the last action (`new`) fails/panics/runs out of gas, the account creation, the NEAR transfer, and the code deployment already committed to state and are not reverted; only `is_promise_success()` for the whole receipt reports failure. The factory's `assert_self()`/`is_promise_success()` guard in `on_staking_pool_create` only distinguishes "success vs. failure of the composite receipt" — it has no way to know that partial state (funded, code-deployed account) survived the failure, so it refunds the deposit anyway [4](#0-3) .

Attacker flow:
1. Call `create_staking_pool(id, owner_id=attacker, stake_public_key, reward_fee_fraction)` with `attached_deposit = MIN_ATTACHED_BALANCE` and craft conditions so the trailing `function_call(b"new", ...)` fails deterministically (e.g., insufficient gas for `new`'s internal work, or a panic inside `StakingContract::new`) while `create_account`/`transfer`/`deploy_contract` still succeed.
2. `on_staking_pool_create` sees `is_promise_success() == false`, removes the id from `staking_pool_account_ids`, and sends the full `attached_deposit` back to `predecessor_account_id` (the attacker) [5](#0-4) .
3. The `id.factory` account still exists on-chain, holds the transferred deposit balance, and runs the deployed staking-pool wasm, but has no initialized state (`new` never committed) — meaning `state_exists()` is false, so **anyone**, including the attacker, can call `new()` directly on that account (no access key required to invoke a public method on a contract) and become `owner_id` of a pool that already holds the deposit balance in its raw NEAR account balance.
4. The attacker has now received the refund AND separately controls a contract holding the original deposit, without ever losing net NEAR - and this account was never routed through the whitelist, but its balance is real NEAR that a subsequent owner-controlled interaction (e.g., `internal_ping`'s `total_balance = account_locked_balance + account_balance - attached_deposit` accounting, `staking-pool/src/internal.rs` lines 205-212) could recognize as "reward" once the attacker stakes/deposits, letting them extract or credit themselves with the leftover balance as if it were legitimate stake.

No existing guard prevents this: `assert_self()` only checks the caller is the contract itself, `is_promise_success()` only reports the outer receipt result, and there is no check that the target account balance is zero / matches expectations before refunding.

### Impact Explanation
NEAR that should be either (a) fully refunded to the caller with nothing left behind, or (b) fully consumed by a successfully created and whitelisted pool, instead ends up split: the caller gets the refund, and the same amount of NEAR sits in an un-whitelisted, attacker-initializable account. This breaks the "refund + funds-left = deposit" invariant and creates funds that can be scooped into an attacker-parameterized pool the factory never approved/whitelisted — matching the Critical impact category of "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" adjacent behavior (here, a pool created/initialized with attacker-chosen owner outside the factory's intended flow). This is repeatable per unique `staking_pool_id` (each attempt requires a fresh id since the failed `create_account` cannot reuse an existing account).

### Likelihood Explanation
The attacker needs only the `MIN_ATTACHED_BALANCE` deposit (30 NEAR) and control over gas/parameters to force `new()` to fail while the preceding actions succeed - a low-cost, permissionless action requiring no special privilege, callable by any account. The main uncertainty is precisely engineering a deterministic failure of `new()` alone (e.g., gas tuning) versus failure of the whole receipt (e.g., if `create_account` fails first, nothing is funded and the bug doesn't manifest) — this requires accurate calibration of `gas::STAKING_POOL_NEW` versus what `StakingContract::new` actually needs, which is plausible but would need to be demonstrated empirically (e.g., via `near-workspaces`/sandbox, not a plain unit test, since `testing_env!`-based unit tests fake `is_promise_success()` and cannot reproduce genuine partial-receipt persistence).

### Recommendation
Do not rely solely on `is_promise_success()` for the composite receipt. Either (a) split account creation/funding from `new()` initialization and check `env::state_exists()`/target account balance in the callback before deciding whether to refund, or (b) if `new()` fails, actively drain/reclaim the created account's balance back into the factory before refunding (e.g., issue a `Promise::new(staking_pool_account_id).transfer(remaining_balance)` back to the factory or block reuse of that account/refund unless the account is verified empty), and/or make `new()` itself the very first action so failure can't leave a funded, deployed remnant.

### Proof of Concept
Because the vulnerable behavior depends on genuine NEAR receipt/action semantics (partial persistence within a single action receipt when only the trailing `FunctionCall` fails), this cannot be demonstrated with the repo's existing `testing_env!` unit-test harness, which merely injects a `PromiseResult::Failed`/`Successful` value and does not model partial state persistence of `create_account`/`transfer`/`deploy_contract` actions. A conclusive PoC requires a `near-workspaces` (or `near-sdk-sim`) integration test:
1. Deploy `staking-pool-factory` and the real `staking-pool.wasm`.
2. Call `create_staking_pool` with a `stake_public_key`/gas configuration crafted so `StakingContract::new` panics or runs out of gas (e.g., pass an intentionally-triggering config, or cap gas below what `new` needs while `deploy_contract` still succeeds).
3. After the callback resolves, assert: (a) predecessor's balance increased by ~`attached_deposit` (refund happened), AND (b) `view_account("<id>.factory")` shows a non-zero balance and deployed code, with `state_exists()` false.
4. As a third, unrelated account, call `new(...)` directly on `"<id>.factory"` with attacker-chosen `owner_id`/`stake_public_key`, and confirm it succeeds and the account's pre-existing NEAR balance remains under the new owner's contract.
5. Sum: `refund_received + balance_at_created_account` should exceed `attached_deposit` originally spent, violating the claimed invariant.

    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
