### Title
Loss-adjusted withdraw receipts are upgraded to par when the user makes a later request — haircut bypass steals from other claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]`. Since `lastWithdrawRequest` stores only the *most recent* request epoch, a user who holds a haircut receipt from an earlier loss epoch and then files any later request permanently escapes the haircut: the earlier basis stays inside `withdrawsRequests` and is paid at par through `_claimFundedWithdrawRequest`. The overpayment is drawn from underlyings collected for *all* pending receipts, so later claimants are left unbacked.

### Finding Description
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` is called with `_amount < pendingWithdraws`; it stores `lossRecoveryPriceByEpoch[epochNumber] = funded * 1e18 / pendingBasis` and zeroes `pendingWithdraws` (lines 411-430). Users whose receipts were created in that epoch are supposed to claim `basis * lossRecoveryPrice / 1e18` via `_claimLossAdjustedWithdrawRequest` (lines 789-801).

The bug is in how the loss epoch is located:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

`lastWithdrawRequest[_user]` is overwritten on every `requestWithdraw` (line 282) and only ever holds the latest epoch. Per-epoch basis is correctly recorded in `withdrawsRequestsByEpoch[user][epoch]` (line 293), but the claim path only ever inspects the single latest epoch.

Attack sequence (attacker = ordinary KYC'd lender / tranche holder):

1. Epoch N ends. Attacker calls `IdleCDOEpochVariant.requestWithdraw`, creating a receipt in epoch N (`withdrawsRequestsByEpoch[attacker][N] = R`, `withdrawsRequests[attacker] = R`, `lastWithdrawRequest[attacker] = N`).
2. Epoch N+1 runs; at `stopEpoch` the manager passes a `_lossAmount`, so `collectWithdrawFunds` funds only `R * p` (recovery price `p < 1`) and stores `lossRecoveryPriceByEpoch[N+1]`... — more precisely the haircut is keyed to the `epochNumber` at funding time, which is the epoch during which the request matured. Let E be the epoch for which `lossRecoveryPriceByEpoch[E] != 0` and the attacker's `withdrawsRequestsByEpoch[attacker][E] != 0`.
3. Before claiming, the attacker deposits/reuses remaining tranche balance and calls `requestWithdraw` again in a later epoch F. Now `lastWithdrawRequest[attacker] = F` while `withdrawsRequestsByEpoch[attacker][E]` still equals R and `withdrawsRequests[attacker] = R + R'`.
4. After one more epoch passes, attacker calls `IdleCDOEpochVariant.claimWithdrawRequest` → strategy `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest`: `lossEpoch = F`, `lossRecoveryPriceByEpoch[F] == 0` → returns 0, never clears the E receipt.
   - `_claimFundedWithdrawRequest`: gate `epochNumber <= lastWithdrawRequest` passes once epoch F+1 started; it pays the entire `withdrawsRequests[attacker] = R + R'` **at par** (lines 338-349).

The haircutted amount `R * (1 - p)` is paid out in full. Since `collectWithdrawFunds` only transferred `basis * p` into the strategy, the excess comes from underlyings held for other users' funded receipts / post-default reserve boundary — i.e., other claimants' `claimWithdrawRequest` calls will underflow or revert (`_transferFundedClaim` guard at line 904 reverts when the balance can't cover both reserve and the claim, permanently freezing honest claims).

### Impact Explanation
Direct theft plus permanent freezing of unclaimed withdrawals. The attacker receives `R * (1 - lossRecoveryPrice)` more than entitled per receipt; the strategy was only funded `R * p` for that receipt, so the shortfall is socialized onto every other pending/funded claimant, whose claims then revert on the `balance - reserve < _amount` guard or on transfer underflow. Quantified loss: up to `attackerReceipt * (1 - recoveryPrice)` per attack; repeatable across epochs.

### Likelihood Explanation
Requires only an unprivileged whitelisted lender and an epoch stopped with `_lossAmount > 0` (a legitimate, honest-manager action — `stopEpochWithDuration` exists precisely for realized losses) plus the ability to request withdraws in two different epochs, which normal users do routinely. No privileged collusion, no oracle manipulation. The second request can even be made on dust tranche balance, making the escape cheap.

### Recommendation
Track loss-adjusted basis per epoch instead of keying off `lastWithdrawRequest`. In `claimWithdrawRequest`, iterate or explicitly look up `withdrawsRequestsByEpoch[_user]` against every epoch with a nonzero `lossRecoveryPriceByEpoch` (e.g., store a per-user list of request epochs, or have `_claimLossAdjustedWithdrawRequest` scan the user's known request epochs rather than only the latest). At minimum, block `requestWithdraw` when the user still has an unclaimed receipt in a loss-adjusted epoch, or have `requestWithdraw` force-claim/settle prior loss-adjusted receipts before overwriting `lastWithdrawRequest`.
