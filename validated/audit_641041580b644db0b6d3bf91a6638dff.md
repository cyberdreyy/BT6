### Title
Claimed instant-withdraw receipts remain in `instantWithdrawsRequestsByEpoch`, inflating default recovery basis and permanently freezing recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never clears the per-epoch accounting `instantWithdrawsRequestsByEpoch[_user][epoch]` or the global `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in the same epoch after a user already claimed funded instant withdrawals, `defaultPendingClaimBasis()` still counts those claimed receipts, inflating `totalBasis` in `finalizeDefaultRecovery`, while `_defaultPrefundedInstantReserve()` counts already-paid-out funds as "prefunded reserve". This mirrors the stacksafe() bug class: one ledger (`instantWithdrawClaimsByEpoch`, sized by all requests) is indexed/iterated as bound while the counterpart ledger (`instantWithdrawsRequests` / actual strategy balance) is shorter — the missing "index exceeds current bounds" check.

### Finding Description
In `requestInstantWithdraw`, three ledgers are incremented: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . On a normal funded claim, `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and transfers underlying — but the two per-epoch mappings are left untouched [2](#0-1) .

On default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [3](#0-2) , and `_defaultPrefundedInstantReserve()` treats `instantBasis - pendingInstant` as underlying already held for claimants [4](#0-3) . Both include receipts that were already fully claimed and paid — the "old state bound exceeds current state bound" condition. Then `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount / totalBasis` on this phantom basis [5](#0-4) . Worse, `_claimDefaultedInstantWithdrawRequest` later reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, computes `instantWithdrawsRequests[_user] -= claimBasis` on an already-zeroed aggregate (underflow revert), and decrements `instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` inconsistently [6](#0-5) .

### Impact Explanation
- The reserve is credited with `prefundedReserve` funds that were already transferred out to claimants, so `defaultRecoveryReserve` exceeds the strategy's actual underlying balance. Recovery claims that should succeed either revert on transfer (insufficient balance) or drain funds owed to later claimants — permanent freezing of recovery for honest users.
- If the stale-epoch user (or any user whose per-epoch entry persists) calls `claimInstantWithdrawRequest` after `defaultInstantWithdrawsFinalized`, `_claimDefaultedInstantWithdrawRequest` underflows on `instantWithdrawsRequests[_user] -= claimBasis`, reverting and permanently blocking that user's claim path — the same entry point also serves older funded receipts.
- The inflated `totalBasis` lowers `defaultRecoveryPrice`, diluting all defaulted-epoch claimants, including active tranche holders whose NAV was burned/minted to `activeFinalNAV`.

### Likelihood Explanation
Requires: instant withdrawals enabled, a user requests and fully claims a funded instant withdrawal during epoch N (pendingInstantWithdraws stays non-zero due to other claimants or partial collection via `collectInstantWithdrawFunds`), then the borrower defaults in the same epoch and the honest owner calls `finalizeDefaultRecovery`. Unprivileged users only need to perform legitimate request/claim transactions; sequencing around honest owner/manager/borrower calls. Partially funded instant queues are an intended mode per the `_defaultPrefundedInstantReserve` comments.

### Recommendation
In `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (or track a claim epoch per user as with `lastWithdrawRequest`). Additionally, in `_claimDefaultedInstantWithdrawRequest`, bound `claimBasis` by `min(instantWithdrawsRequestsByEpoch[user][defaultEpoch], instantWithdrawsRequests[user])` — the analog of the kernel fix's `i >= cur->allocated_stack` check — so a stale per-epoch entry can never exceed the live aggregate.

### Proof of Concept
Foundry fork test sketch against `IdleCDOEpochVariant` + `IdleCreditVault`:
1. Enable instant withdrawals (`setInstantWithdrawParams`), deposit for user A and user B, `startEpoch`.
2. A and B call `cdoEpoch.requestInstantWithdraw(amount)`. Fund only A: borrower returns `amount` → `collectInstantWithdrawFunds(amount)`; `pendingInstantWithdraws == amount(B)` remains.
3. `claimInstantWithdrawRequest(A)` — A paid; assert `instantWithdrawsRequestsByEpoch[A][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` still hold A's basis.
4. Borrower defaults in same epoch; owner calls `finalizeDefault`/`finalizeDefaultRecovery(recovered, source)`.
5. Assert `defaultRecoveryReserve > underlying.balanceOf(strategy)` (phantom prefunded reserve counted) and `defaultPendingClaimBasis()` includes A's already-paid amount.
6. A calls `claimInstantWithdrawRequest` → reverts on underflow; B's recovery claim leaves the reserve short by exactly A's double-counted basis.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];

      prefundedReserve = instantBasis - pendingInstant;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
