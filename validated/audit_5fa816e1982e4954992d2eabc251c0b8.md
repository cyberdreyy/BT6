### Title
Stale confirmations from removed multisig members/keys still count toward the approval threshold, allowing execution below the intended live-member quorum - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
`DeleteKey` (multisig) and `DeleteMember` (multisig2) only purge pending *requests created by* the removed key/member, but never scrub that key/member's *confirmations already recorded on other pending requests*. Since `confirm()` compares `confirmations.len()` against `self.num_confirmations` without validating that every entry in the confirmation set still corresponds to a live signer, a removed member's stale confirmation continues to count. This lets a request execute once enough live signers confirm to make up the remaining count, even though the number of currently-authorized approvers backing it is below `num_confirmations`.

### Finding Description
`confirm()` in both contracts checks:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations { ... execute_request(...) }
``` [1](#0-0) [2](#0-1) 

The count is derived from `self.confirmations.get(&request_id)`, a set of member identifiers that confirmed *that specific request*. Removal logic (`DeleteKey` in multisig, `DeleteMember` in multisig2) only cleans requests whose *creator* (`r.signer_pk` / `r.member`) matches the removed identity:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter(|(_k, r)| r.signer_pk == pk)   // only requests CREATED by pk
    .map(|(k, _r)| k).collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [3](#0-2) 

The multisig2 equivalent has the identical gap (`r.member == member` filters by request *creator*, not by confirmer): [4](#0-3) 

Neither routine iterates `self.confirmations` to strip the departing identity's vote from requests it merely *confirmed but did not create*. `delete_member` additionally only asserts that the *total member count* stays `>= num_confirmations` [5](#0-4) , it does nothing about confirmations already cast by the member being removed.

**Equality that should hold:** `confirmations.len()` for a pending request should equal the number of *currently live* members/keys who approved it. After a `DeleteKey`/`DeleteMember` action executes, this breaks: `confirmations.len()` still includes the departed identity, so `live_confirmations < recorded_confirmations`.

### Impact Explanation
This is a "multisig request executed below threshold" scenario (Critical, per the given impact categories): a pending, unrelated request created by member A and confirmed by member B can later execute with `num_confirmations` recorded confirmations even though B has since been removed via a separate `DeleteMember`/`DeleteKey` request, meaning the request is authorized by fewer *live* approvers than the configured threshold intends. Because the removed member's key/account no longer has any obligation to have re-validated the still-pending request (e.g., a `Transfer` or `FunctionCall` to move funds or add an access key), the multisig's core security guarantee — that `num_confirmations` *current* signers must agree — is violated.

### Likelihood Explanation
This requires only ordinary, sequential use of already-existing multisig operations (no privileged bypass, no assumption violating documented init): a request gets partial confirmations, a subsequent `DeleteMember`/`DeleteKey` request executes (a routine key-rotation event, which is explicitly anticipated by the contract's own gotcha note about member count), and the stale confirmation is never invalidated. Any organization rotating signers on an outstanding request is exposed, making this a realistic operational hazard rather than a purely theoretical one.

### Recommendation
When removing a member/key (`DeleteMember`/`DeleteKey`), iterate over **all** pending requests' confirmation sets (not just ones the removed identity created) and remove the departing identity's entry from each, decrementing effective progress toward `num_confirmations` accordingly. Alternatively, when counting confirmations in `confirm()`, filter the confirmation set to only currently valid members before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig configured with `num_confirmations = 2`, members `{A, B, C}`.
2. A calls `add_request` creating request `R` (`Transfer` to some address), `confirmations(R) = {}`.
3. B calls `confirm(R)` → `confirmations(R) = {B}` (1 < 2, not yet executed) [6](#0-5) .
4. Separately, A and C (or A and B) create and confirm a `DeleteMember{member: B}` request, which executes and removes B from `members`, but only purges requests *created* by B — `R` is untouched, and `confirmations(R)` still contains B [7](#0-6) .
5. C now calls `confirm(R)` → `confirmations(R).len() + 1 = 2 >= num_confirmations (2)` → `execute_request(R)` fires [8](#0-7) .
6. `R` executes with approvals from only 1 live member (C) plus 1 stale/departed confirmation (B), violating the intended 2-of-live-members threshold.
