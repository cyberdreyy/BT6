### Title
Vote-account block-revenue commission can be front-run to 100% with no timelock, letting a validator instantly steal delegators' share of block rewards - (File: programs/vote/src/vote_state/mod.rs)

### Summary
`VoteInstruction::UpdateCommissionBps` for `CommissionKind::BlockRevenue` (SIMD-0291/SIMD-0123) applies instantly and unconditionally, with the code explicitly stating "No commission update rule, per SIMD-0249 and SIMD-0291." [1](#0-0)  This is unlike the legacy per-epoch commission, which is rate-limited to the first half of an epoch for increases via `is_commission_update_allowed` [2](#0-1) , and unlike inflation-rewards commission, whose effect on reward payout is deliberately delayed a full epoch specifically "to prevent last minute commission rugs" [3](#0-2) . Block-revenue commission has neither a timelock at the instruction level nor a delay at the point rewards are actually computed/paid, exactly mirroring the NFTX report's root cause: an untrusted pool "manager" (here, the vote-account withdraw authority) can front-run a fee/commission to the maximum right before value flows in, at the expense of users (delegators) who cannot react in time.

### Finding Description
The vote program's authorized withdrawer can freely call `UpdateCommissionBps { commission_bps, kind: CommissionKind::BlockRevenue }` at any time, and the update takes effect on the very same slot/transaction ordering as any deposit: `vote_state::update_commission_bps` sets `block_revenue_commission_bps` with only a signer check — no timing gate [4](#0-3) . The instruction also imposes no upper bound (a test confirms values like 15,000 or 50,000 bps — i.e. 150%/500% — are "allowed at program level") [5](#0-4) .

Block revenue is credited to the vote account via `DepositDelegatorRewards`, which stores `pending_delegator_rewards` in the vote account state after commission is taken [6](#0-5) . When the epoch-reward calculation later distributes this pool among delegators, it reads `vote_state.pending_delegator_rewards()` and splits it proportionally by stake in `calculate_block_reward` [7](#0-6) . Because commission was already deducted at deposit time and the commission-bps update instruction has no epoch-position restriction or delay, a vote-account authority observing (or anticipating) an imminent large block-revenue deposit transaction can:

1. Submit `UpdateCommissionBps { commission_bps: 10000 (or higher), kind: BlockRevenue }` immediately before the deposit transaction lands (same slot, front-run via priority fee/ordering).
2. Let the large `DepositDelegatorRewards` transaction execute, which computes the delegator share using the now-100%-commission rate, leaving `pending_delegator_rewards` at (or near) zero.
3. Immediately submit another `UpdateCommissionBps` transaction reverting the rate back to its normal, attractive value, so future/observed delegators are not deterred.

Unlike the inflation-rewards path — where `redeem_delegation_rewards` explicitly reads a *cached, one-epoch-delayed* commission snapshot (`snapshot_epoch_vote_accounts`) specifically to stop this exact attack [8](#0-7)  — the block-revenue commission has no analogous protection anywhere in the deposit or distribution path.

### Impact Explanation
Delegators to a vote account lose the entirety (or an arbitrarily large fraction) of their block-revenue share for that deposit event, with funds instead flowing to the validator identity or a custom commission collector [9](#0-8) . This is a direct unauthorized transfer of value from unprivileged stakers to a vote-account authority who is not a trusted party from the delegators' perspective, matching the "concrete unauthorized fund mutation" bar. Because block-revenue commission (SIMD-0123/0291) can be set above 100% (up to 65,535 bps, i.e. 655%), the attacker can extract more of `pending_delegator_rewards` than their own stake would ever "earn," entirely at delegators' expense.

### Likelihood Explanation
The attack requires the vote-account's authorized withdrawer to actively front-run their own protocol's commission field around a revenue-deposit transaction — a capability inherent to any validator, with no external permission needed. It does require the attacker to control (or coordinate with) the party calling `DepositDelegatorRewards` for the deposit's timing to be predictable, and requires `block_revenue_sharing`/SIMD-0123 features to be active in the target cluster. Given this is a fully permissionless capability of the vote-account owner and needs no other actor's cooperation to trigger the exploit (they can always be the one calling deposit as well, or simply toggle commission right before any incoming deposit they anticipate), likelihood is moderate-to-high once the feature is live.

### Recommendation
Apply the same delay/rate-limit protections used for inflation-rewards commission to block-revenue commission:
- Enforce an `is_commission_update_allowed`-style epoch-position gate (or an explicit timelock) on `UpdateCommissionBps` for `CommissionKind::BlockRevenue`, at minimum for increases.
- At distribution time, use a commission value snapshotted from a prior epoch (mirroring `snapshot_epoch_vote_accounts` used for inflation rewards) rather than reading the live, same-block `block_revenue_commission_bps` when computing/withholding the delegator's share in `calculate_block_reward` / at `DepositDelegatorRewards` time.
- Reconsider allowing commission_bps values beyond 10,000 (100%) at the program level, since this permits the collector to be paid more than the entire deposited amount, worsening this issue.

### Proof of Concept
1. Vote account `V` has `block_revenue_commission_bps = 1000` (10%), attracting delegators.
2. Withdraw authority observes an upcoming large `DepositDelegatorRewards` deposit transaction (or intends to submit it themselves) that will credit `V.pending_delegator_rewards`.
3. Withdraw authority submits `UpdateCommissionBps { commission_bps: 10000, kind: BlockRevenue }` in the same slot, ordered before the deposit transaction — permitted unconditionally per `update_commission_bps`, which contains no timing check [10](#0-9) .
4. `DepositDelegatorRewards` is processed; commission is deducted at 100%, so essentially none of the deposited revenue accrues to `pending_delegator_rewards` for delegators, while the block-revenue collector receives the full amount.
5. Withdraw authority submits another `UpdateCommissionBps` restoring the rate to 1000 bps immediately after, so subsequent observers of on-chain state see the "normal" advertised commission again.
6. During epoch reward distribution, `calculate_block_reward` splits the now-near-zero `pending_delegator_rewards` among stakers proportionally — delegators receive nothing from this deposit despite `V` having falsely appeared to charge only 10% commission [11](#0-10) .

```rust
/// Update the vote account's commission in basis points (SIMD-0291, SIMD-0123).
pub fn update_commission_bps<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    commission_bps: u16,
    kind: CommissionKind,
    signers: &HashSet<Pubkey, S>,
    block_revenue_sharing_enabled: bool,
) -> Result<(), InstructionError> {
    // Per SIMD-0291: BlockRevenue returns InvalidInstructionData unless
    // SIMD-0123 (block_revenue_sharing) is enabled.
    if matches!(kind, CommissionKind::BlockRevenue) && !block_revenue_sharing_enabled {
        return Err(InstructionError::InvalidInstructionData);
    }

    let mut vote_state = get_vote_state_handler_checked(vote_account, target_version)?;

    // No commission update rule, per SIMD-0249 and SIMD-0291.

    // Require authorized withdrawer to sign.
    verify_authorized_signer(vote_state.authorized_withdrawer(), signers)?;

    match kind {
        CommissionKind::InflationRewards => {
            vote_state.set_inflation_rewards_commission_bps(commission_bps);
        }
        CommissionKind::BlockRevenue => {
            vote_state.set_block_revenue_commission_bps(commission_bps);
        }
    }

    vote_state.set_vote_account_state(vote_account)
}
```

```rust
/// Given the current slot and epoch schedule, determine if a commission change
/// is allowed
pub fn is_commission_update_allowed(slot: Slot, epoch_schedule: &EpochSchedule) -> bool {
    // always allowed during warmup epochs
    if let Some(relative_slot) = slot
        .saturating_sub(epoch_schedule.first_normal_slot)
        .checked_rem(epoch_schedule.slots_per_epoch)
    {
        // allowed up to the midpoint of the epoch
        relative_slot.saturating_mul(2) <= epoch_schedule.slots_per_epoch
    } else {
        // no slots per epoch, just allow it, even though this should never happen
        true
    }
}
```

```rust
/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
```
