### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing a request to execute below the live-signer threshold - ([File: multisig2/src/lib.rs])

### Summary
`confirm()` decides whether to execute a pending request purely by the *size* of the `confirmations` `HashSet<String>` (`confirmations.len() as u32 + 1 >= self.num_confirmations`), never re‑validating that every entry in that set still belongs to a currently live member. `delete_member()` only purges *requests originated by* the removed member, but never scrubs that member's *confirmations left on other, still-pending requests*. This lets a request execute with fewer distinct live-member approvals than `num_confirmations` requires — the confirmation-count binding ("confirmations counted" == "live members who approved") is broken.

### Finding Description
`MultiSigContract::confirm` in `multisig2/src/lib.rs` treats the request as ready to execute solely based on set cardinality: [1](#0-0) 

`delete_member` only removes requests that the deleted member originally *submitted* (`r.member == member`); it does not iterate `self.confirmations` to strip that member's entries from other pending requests they merely *confirmed*: [2](#0-1) 

Sequence:
1. Multisig has members A, B, C with `num_confirmations = 2`.
2. Someone adds request X (e.g. a `Transfer` or `FunctionCall`). Member A confirms it (1/2). `confirmations[X] = {A}`.
3. Members later approve a `DeleteMember { member: A }` action (a separate, legitimately-threshold-approved request). `delete_member` removes A from `self.members` and from `num_requests_pk`, and deletes only requests *authored* by A — request X (authored by whoever submitted it, not A) is untouched, and `confirmations[X]` still contains A's stale confirmation.
4. Member B — a single remaining live signer — calls `confirm(X)`. `confirmations.len()` is 1 (A's stale entry), so `1 + 1 >= 2` is true, and the request executes.

Effectively the request executed with only **one** live, current-member approval even though `num_confirmations = 2`, because the code counted a confirmation from an account that is no longer a member. This is a direct analog of the H‑01 pattern: a stored reference to an identity (owner index / confirmation entry) becomes stale/decoupled from the live set (owner mapping / member set), and the code trusts the stale reference instead of re-validating it against current state, producing an incorrect security decision (request executed below the intended trust threshold).

The identical construction exists in the legacy `multisig/src/lib.rs`: `MultiSigRequestAction::DeleteKey` removes only requests whose `signer_pk == pk`, but never scrubs `pk`'s confirmations from other pending requests' `HashSet<PublicKey>`: [3](#0-2) [4](#0-3) 

### Impact Explanation
This breaks the core multisig custody guarantee: "a multisig request executed below threshold," which is explicitly Critical impact — it means fewer than `num_confirmations` currently-authorized signers actually approved the on-chain action (which may itself be a `Transfer` of NEAR, an `AddKey`/`AddMember` granting new control, or a `FunctionCall`). Any pending request that has already accumulated one or more confirmations from a member who is subsequently removed becomes easier to push through than the configured policy intends, and in the smallest cases (e.g., `num_confirmations = 2` and one stale confirmation) a single live signer can unilaterally finalize actions meant to require multi-party agreement.

### Likelihood Explanation
This requires no unusual attacker capability beyond normal, expected multisig usage: any member submitting/confirming a request before another member is later removed (a routine occurrence in a rotating-membership multisig) creates the exposure, and any remaining live member (not necessarily malicious — this can happen accidentally) can trigger execution once the stale count crosses the threshold. No index manipulation, replay, or off-chain signature relay is needed (unlike the original H‑01 CoinbaseSmartWallet bug, which relies on cross-chain replay of `executeWithoutChainIdValidation`); here the divergence is purely a server-side accounting bug in `confirm`/`delete_member`, making it easy to hit unintentionally in any multisig that experiences membership churn while requests are outstanding.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate all pending `confirmations` entries (not only `requests` authored by the removed identity) and remove the departing member's/key's confirmation from every request; if the resulting confirmation count now equals `num_confirmations - 1` or more, do not auto-execute retroactively. Additionally, `confirm()` should validate that every identity in the stored confirmation set is still present in `self.members` at confirmation/execution time (e.g., recompute `confirmations.iter().filter(|m| self.members.contains(m)).count()`), rather than trusting the raw `HashSet` length.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]`, `num_confirmations = 2`.
2. As A, call `add_request` for a `Transfer` action; call `confirm` — confirmations = `{A}` (1/2, not yet executed).
3. Separately, get 2/3 members to approve and execute `DeleteMember { member: A }` (this is code path `execute_request → delete_member`, `multisig2/src/lib.rs:239-241` and `355-379`). A is removed from `self.members`; request from step 2 is untouched because `r.member == member` filter only matches requests A itself submitted.
4. As B (a single live signer), call `confirm` on the request from step 2. `self.confirmations.get(&request_id)` still returns `{A}` (len 1); `1 + 1 >= 2` passes and `execute_request` runs the `Transfer`, even though only one currently-live member (B) actually approved it.

        self.assert_valid_request(request_id);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
