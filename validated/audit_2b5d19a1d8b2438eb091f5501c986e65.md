### Title
Loss-adjusted withdraw receipts are paid at par after a new `requestWithdraw` overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a `stopEpochWithDuration` loss is realized, `IdleCreditVault.collectWithdrawFunds` records a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws`, meaning pending receipts were only partially funded. The later claim path `_claimLossAdjustedWithdrawRequest` looks up the haircut using `lastWithdrawRequest[_user]` as the epoch key. If the same user makes any new `requestWithdraw` before claiming, `lastWithdrawRequest[_user]` is overwritten to the new epoch, the loss-epoch haircut entry is never matched, the old per-epoch receipt is never cleared, and the still-populated `withdrawsRequests[_user]` aggregate is then paid in full at par by `_claimFundedWithdrawRequest`. The user recovers 100% of a receipt that was only funded at, e.g., 50%, draining underlyings that belong to other claimants or LPs.

### Finding Description
Relevant flow, all in `contracts/strategies/idle/IdleCreditVault.sol`:

1. On a lossy stop, `collectWithdrawFunds(_amount)` with `_amount < pendingBasis` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and sets `pendingWithdraws = 0` [1](#0-0) . The strategy now holds only `_amount` for the whole pending bucket.
2. `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]`: `uint256 lossEpoch = lastWithdrawRequest[_user]; uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]; if (lossRecoveryPrice == 0) return 0;` [2](#0-1) .
3. `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds the new amount to `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]`, while the old loss-epoch entry in `withdrawsRequestsByEpoch[_user][lossEpoch]` remains non-zero [3](#0-2) .
4. On the next `claimWithdrawRequest` (callable once `epochNumber > lastWithdrawRequest[_user]`), the loss path returns 0 because `lossRecoveryPriceByEpoch[newEpoch] == 0`, and `_claimFundedWithdrawRequest` pays `amount = withdrawsRequests[_user] + apr0 buckets` in full via `_transferFundedClaim` [4](#0-3) . `_clearWithdrawClaimForEpoch` is never invoked for the old loss epoch, so `withdrawsRequestsByEpoch[_user][lossEpoch]` and the corresponding share of `withdrawsRequests[_user]` are treated as a funded at-par receipt [5](#0-4) .

The broken invariant is "one receipt, one haircut-adjusted payout": the haircut was applied at funding time (`pendingToFund` in `previewLossAdjustedWithdrawFunds`) [6](#0-5) , but the payout side keys the haircut on a mutable per-user pointer that any subsequent self-request destroys. No guard stops it: `defaultRecoveryInitialized` is already set, `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, and the epoch gating in `_claimFundedWithdrawRequest` only enforces the one-epoch wait.

### Impact Explanation
Direct theft / insolvency. The attacker receives `basis` instead of `basis * lossRecoveryPrice / RECOVERY_FULL`. With a 50% haircut, a 100k USDC receipt is funded with 50k but pays out 100k, extracting 50k of underfunded underlyings. Since the strategy only holds the partial funding, the excess comes from the same underlying balance that backs other users' funded claims and instant-withdraw payouts, so later claimants revert on `NotAllowed` / insufficient balance — i.e., permanent freezing of other users' funds proportional to the extraction.

### Likelihood Explanation
Requires only unprivileged actions by a KYC-passing lender: (a) a normal `requestWithdraw`, (b) an honest manager-triggered `stopEpochWithDuration` loss where the borrower funds less than `pendingBasis` (a partial-recovery scenario the code explicitly supports), (c) a second `requestWithdraw` of any size in a later epoch, (d) `claimWithdrawRequest` after one more epoch. No privileged misbehavior, no oracle manipulation, no timing race — the state corruption happens entirely inside the strategy's own bookkeeping. The main precondition is the loss-adjusted epoch mode existing in the deployment, which is a first-class code path.

### Recommendation
Do not key the loss-epoch lookup to the mutable `lastWithdrawRequest`. Options: iterate/derive the claimable loss epoch from `withdrawsRequestsByEpoch[_user]` (e.g., track a separate `lastLossClaimEpoch` or check all epochs with recorded receipts), or store the haircut alongside each user's per-epoch receipt at funding time. Additionally, `requestWithdraw` should either refuse while an unclaimed loss-adjusted receipt exists or sweep the old loss claim before overwriting `lastWithdrawRequest`, matching how `_clearWithdrawClaimForEpoch` already isolates per-epoch basis.

### Proof of Concept
Foundry fork PoC sketch (existing harness in `test/foundry/IdleCreditVault.t.sol` provides `_stopCurrentEpochWithApr`, `deal`, and the `cdoEpoch`/`strategy` handles):

```solidity
// setup: attacker deposits via idleCDO.depositAA, epochs run normally
// epoch N: attacker requests withdraw of X tranches -> basis B
uint256 basis = cdoEpoch.requestWithdraw(tranches, AAtranche);

// epoch N ends with a realized loss: borrower funds only 50% of pendingWithdraws
uint256 pendingBasis = strategy.pendingWithdraws();
uint256 funded = pendingBasis / 2;
deal(underlying, borrower, expectedInterest + funded);
// borrower approves; manager stops with duration + loss
cdoEpoch.stopEpochWithDuration(apr, interest, duration, lossAmount);
// strategy.lossRecoveryPriceByEpoch(N) == RECOVERY_FULL/2, pendingWithdraws == 0

// epoch N+1 buffer: attacker requests a tiny new withdraw, overwriting lastWithdrawRequest
cdoEpoch.requestWithdraw(dust, AAtranche);

// epoch N+1 runs and stops normally (borrower repays)
// attacker claims: loss path misses (price[epoch N+1] == 0), funded path pays full B + dust at par
uint256 pre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
assertApproxEqAbs(underlying.balanceOf(attacker) - pre, basis + dustPayout, 1);
// expected honest payout was only funded (~basis/2) for the epoch-N receipt
// strategy balance is now short ~basis/2 vs remaining funded claims -> later claimants revert
```

The assertion that the attacker receives `~2x` the funded amount, plus a subsequent honest claimant reverting in `_transferFundedClaim`/transfer, demonstrates the insolvency directly.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
