# No vulnerability found for this question.

Analysis: The guard in `conflict_still_blocks` returns `true` (still blocks) whenever `node_reaches_conflict || (!conflict.globally_accepted && conflict.stacks_height <= proposed_height)` [1](#0-0) . The question's exploit premise requires this inequality to *flip to false* by having the attacker "re-propose at h+1" after a conflict recorded at height h. But increasing `proposed_height` from `h` to `h+1` while `conflict.stacks_height` stays at `h` makes `conflict.stacks_height <= proposed_height` (i.e. `h <= h+1`) *more* true, not false — the described re-proposal does not flip the guard at all. Flipping the condition to `false` actually requires the opposite: `conflict.stacks_height > proposed_height`, i.e. the attacker would need to propose a *lower* height than an existing recorded conflict.

Even under the corrected direction, the "above the proposed height" branch only applies to a `SignedConflictInfo` that reached the signer's own `get_signed_conflicts` record, and — per the documented semantics — "locally accepted" conflicts of this kind are only created once the signer set collectively reaches the ~70% signing weight threshold, not by a single signer/proposer acting alone [2](#0-1) . Producing a phantom higher-height conflict to exploit this branch would require controlling or colluding with a majority of signer weight, which is explicitly out of scope for the assumed unprivileged, single-slot attacker. The same-tenure node-tip check in `check_block_against_signer_db_state`/pre-commit re-check also independently guards against signing over state the node has already confirmed [3](#0-2) .

Given the inequality direction in the exploit idea is mathematically backward, and the corrected version still requires majority-signer collusion (out of scope), there is no viable path for a single unprivileged attacker to force an invalid or non-canonical signature via this guard.
