### Title
Stale confirmations from removed keys are not purged, allowing execution below the effective confirmation threshold - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig/src/lib.rs` executes a request once `confirmations.len() + 1 >= num_confirmations`, treating the recorded confirmation set as proof that `num_confirmations` *currently authorized* keys approved the action. However, when a key is removed via the `DeleteKey` action, the contract only purges requests that key itself *originated*; it never scrubs that key's public key out of the `confirmations` sets of other pending requests it had co-signed. This breaks the intended equality `confirmations.len() == number of live signing keys that approved this request`.

### Finding Description
`confirm` (`multisig/src/lib.rs:246-266`) reads the `confirmations` set for a request and adds the caller's `signer_account_pk`, executing once the size threshold is met: [1](#0-0) 

The `DeleteKey` action, executed as part of `execute_request` (`multisig/src/lib.rs:198-216`), only removes requests whose `signer_pk` equals the deleted key (`r.signer_pk == pk`), plus the `num_requests_pk` counter for that key: [2](#0-1) 

It does **not** iterate `self.confirmations` to strip the deleted key from confirmation sets of requests it did not originate but had already confirmed. Since `PublicKey` bytes are not otherwise checked for liveness in `confirm`/`assert_valid_request` (`multisig/src/lib.rs:246-266`, `293-310`) beyond `predecessor_account_id == current_account_id` (i.e., "some access key of this account signed"), a confirmation recorded by a key that is later deleted keeps counting toward `num_confirmations` for any request it had confirmed before removal.

Concretely: with `num_confirmations = 3` and keys A, B, C, D:
1. A creates request R (targeting some other receiver, unrelated to key management).
2. C confirms R → `confirmations(R) = {C}`.
3. A and B then jointly confirm+execute a separate `DeleteKey{C}` request, removing C's access key from the account.
4. Because step 3's `DeleteKey` handling only clears requests where `signer_pk == C` (i.e., requests C created), R survives with `confirmations(R) = {C}` untouched.
5. A confirms R → `confirmations.len()+1 = 2`, still below 3, so no problem alone; but if D also confirms, `confirmations.len()+1 = 3 >= num_confirmations`, and R executes. The effective set of *live* approvers is `{A, D}` plus a stale approval from the now-revoked key `C` — i.e., R executes with only 2 currently-valid keys' consent instead of the required 3.

This is the direct structural analog of the reported class ("confirmations counted versus live members" / an aggregate accounting value that is updated asymmetrically on removal vs. addition, so a downstream threshold check reads a stale/incorrect total) — here `confirmations.len()` is the aggregate, and removal (`DeleteKey`) fails to symmetrically decrement it for confirmations the removed key gave to other requests, mirroring how `Bribe.withdraw` failed to symmetrically decrement `totalVoting` that `Bribe.deposit` had incremented.

### Impact Explanation
This breaks the multisig authorization threshold: `MultiSigRequestAction::Transfer`, `AddKey`, `FunctionCall`, etc. can be executed via `execute_request` with fewer currently-authorized keys than the account's configured `num_confirmations`, because a stale confirmation from a revoked key is counted as live. This matches the Critical impact category — "a multisig request executed below threshold" — since NEAR (or access to the account, e.g. adding a new full-access key) can move/execute under a weakened effective threshold.

### Likelihood Explanation
Requires: (a) a key being removed from the multisig at some point after it has confirmed at least one still-pending, not-yet-fully-confirmed request; and (b) other members later completing confirmation of that pending request. Key rotation/removal is a normal, expected multisig operation (e.g., replacing a lost/compromised device key), and pending requests with partial confirmations commonly persist across such rotations (requests only auto-expire via `delete_request` after a cooldown, not automatically). No privileged action beyond normal member behavior is required by the exploiting party — the surviving members do not need to know they are relying on a stale confirmation. This is a realistic, unprivileged-relative-to-intent scenario.

### Recommendation
When executing `DeleteKey`, iterate all pending `confirmations` entries (not just requests where `signer_pk == pk`) and remove the deleted public key from every confirmation set, e.g.:
```rust
let stale_ids: Vec<u32> = self.confirmations
    .iter()
    .filter(|(_, confs)| confs.contains(&pk))
    .map(|(id, _)| id)
    .collect();
for request_id in stale_ids {
    let mut confs = self.confirmations.get(&request_id).unwrap();
    confs.remove(&pk);
    self.confirmations.insert(&request_id, &confs);
}
```
Alternatively, validate at `confirm`/execution time that every public key in a request's `confirmations` set is still a currently active access key of the account before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 3` and keys `A, B, C, D` as full-access keys on the account.
2. `A` calls `add_request` for `Transfer{amount}` to some receiver → request `R1`.
3. `C` calls `confirm(R1)` → `confirmations(R1).len() == 1`.
4. `A` calls `add_request_and_confirm` for `DeleteKey{C}`, then `B` calls `confirm` on that request to reach 3 confirmations (or use `num_confirmations=2` for a smaller repro) and execute it — `C`'s key is removed from the account.
5. Inspect `get_confirmations(R1)` — it still contains `C`'s public key (`multisig/src/lib.rs:198-216` never touched `R1`'s confirmations because `R1.signer_pk == A`, not `C`).
6. `A` calls `confirm(R1)` (2nd confirmation), then `D` calls `confirm(R1)` (3rd) — `confirmations.len()+1 >= 3` triggers `execute_request`, transferring funds even though only `A` and `D` are currently valid keys that explicitly approved `R1`; `C`'s stale confirmation supplied the third vote after being revoked.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
