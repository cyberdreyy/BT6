### Title
`vesting::distribute` permanently DoS's an entire vesting contract (and blocks admin emergency termination) if any single shareholder opts out of direct coin transfers - ([File: aptos-move/framework/aptos-framework/sources/vesting.move])

### Summary
`vesting::distribute` iterates over *all* shareholders of a vesting contract in a single atomic loop, sending each shareholder's share via `aptos_account::deposit_coins`. That call aborts if the recipient is unregistered for `AptosCoin` and has opted out of arbitrary/direct coin transfers via the permissionless `aptos_account::set_allow_direct_coin_transfers`. Because the loop has no per-recipient fallback/skip, a single griefing (or even innocuous) shareholder can make the whole `distribute` transaction abort — blocking payouts to *every other* shareholder. Worse, `terminate_vesting_contract` itself calls `distribute` first, so the admin's only "emergency exit" path is blocked by the same failure, exactly mirroring the external report's "broken hook blocks user funds" pattern, but rooted in local, unprivileged, permissionless code rather than an external protocol hook.

`aptos_account::deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient is not yet registered for the coin type and has disabled direct transfers:
```

    ...

        coin::register<CoinType>(&create_signer(to));

``` [2](#0-1) 

`can_receive_direct_coin_transfers` is controlled entirely by the target account itself via the fully permissionless `set_allow_direct_coin_transfers`:
```
aptos-move/framework/aptos-framework/sources/aptos_account.move:187-219
public entry fun set_allow_direct_coin_transfers(account: &signer, allow: bool) acquires DirectTransferConfig { ... }
``` [3](#0-2) 

The `vesting` module authors were clearly aware of this specific abort/DoS risk — they added a registration check *only* for the `set_beneficiary` path:
```
aptos-move/framework/aptos-framework/sources/vesting.move:915-923
public entry fun set_beneficiary(...) acquires VestingContract {
    // Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
    // fail and block all other accounts from receiving APT if one beneficiary is not registered.
    assert_account_is_registered_for_apt(new_beneficiary);
    ...
``` [4](#0-3) 

However, this check is only performed when the admin explicitly calls `set_beneficiary` for a shareholder. The *default* recipient for any shareholder that never has a beneficiary set is the shareholder's own address (`get_beneficiary` falls back to `shareholder` if no beneficiary entry exists), and that address is never validated at `create_vesting_contract` time or anywhere else. Any shareholder can, at any point after (or even before) the vesting contract distributes funds to them, call `aptos_account::set_allow_direct_coin_transfers(false)` on their own account while remaining unregistered for `AptosCoin`, or otherwise ensure they are unregistered when `distribute` runs. This causes every subsequent call to `distribute()` (and `distribute_many()`) for that contract to abort deterministically.

Critically, `terminate_vesting_contract` — the intended "wind down" / emergency path — itself calls `distribute` first:
```
aptos-move/framework/aptos-framework/sources/vesting.move:770-793
public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
    assert_active_vesting_contract(contract_address);
    // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
    distribute(contract_address);
    ...
``` [5](#0-4) 

So once `distribute` is permanently reverting due to one bad shareholder, `terminate_vesting_contract` also permanently reverts, and `admin_withdraw` requires the contract to already be in `VESTING_POOL_TERMINATED` state, which can never be reached. There is no per-shareholder skip/queue mechanism and no other function that lets the admin bypass a single failing recipient.

### Impact Explanation
This traps the vested/staked funds of *all* shareholders in a vesting contract — not just the misbehaving one — with no recovery path once the pool has any withdrawable stake and one shareholder is unregistered/opted-out. This satisfies the "permanent lock or non-recoverable loss of claim rights in vesting flows" and "share-accounting corruption that... traps value" impact classes, and is triggerable entirely by an unprivileged actor (a shareholder acting on their own account) — no admin/governance role is required to trigger the DoS, only to notice its permanence.

### Likelihood Explanation
The precondition (a shareholder account unregistered for `AptosCoin` and having opted out of direct transfers, or simply never having registered) is easily achievable by any of the shareholders using an ordinary, permissionless entry function (`set_allow_direct_coin_transfers`). No special privileges, timing races, or governance actions are needed; the only requirement is that `distribute` (or the `distribute` inside `terminate_vesting_contract`) is invoked while that condition holds, which happens on every rewards/vest cycle.

### Recommendation
- In `distribute()`, don't let one recipient's failed/aborting deposit revert the entire distribution: use a non-aborting deposit primitive (e.g., check `coin::is_account_registered` / `can_receive_direct_coin_transfers` before attempting deposit, and if the recipient cannot currently receive funds, hold their share in an escrow/claimable balance instead of aborting the whole loop).
- Alternatively, validate at `create_vesting_contract` time (and continuously) that every shareholder address is capable of receiving direct APT transfers, mirroring the check already added in `set_beneficiary`.
- Decouple `terminate_vesting_contract` from a mandatory successful `distribute()` call, or wrap the internal `distribute` call in a try/skip pattern so termination (the emergency exit) can never be blocked by a single recipient's deposit failure.

### Proof of Concept
1. Admin creates a vesting contract with shareholders `A` and `B` via `create_vesting_contract`.
2. Shareholder `B` (unprivileged) calls `aptos_account::set_allow_direct_coin_transfers(signer_of_B, false)` and ensures `B` has no `CoinStore<AptosCoin>` registered (e.g., a fresh account that has never registered for APT, funded only via a mechanism that doesn't auto-register, or an account that never transacted before being added as a shareholder).
3. Time passes; rewards/vesting accrue and become withdrawable.
4. Anyone calls `vesting::distribute(contract_address)`. The loop reaches shareholder `B`, calls `aptos_account::deposit_coins(B, ...)`, which hits `!coin::is_account_registered<AptosCoin>(B)` and `!can_receive_direct_coin_transfers(B)`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. The whole transaction reverts — `A` also receives nothing.
5. Admin attempts `terminate_vesting_contract(admin, contract_address)` to unwind and recover funds; this internally calls `distribute(contract_address)` at line 775, which aborts identically. `admin_withdraw` can never be reached since `state` never transitions to `VESTING_POOL_TERMINATED`.
6. All shareholders' vested/staked APT is now permanently unrecoverable through the vesting module.

(Note: this analysis is based on static review of `vesting.move` and `aptos_account.move`; I was not able to fully trace whether `AptosCoin`'s underlying `coin.move`/fungible-asset migration path could make `is_account_registered<AptosCoin>` unconditionally `true` in the current mainnet-deployed framework, which would affect exploitability. This should be verified directly against `coin.move`'s `is_account_registered` and `deposit` implementations, plus current on-chain migration state, before treating this as fully confirmed.)

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
