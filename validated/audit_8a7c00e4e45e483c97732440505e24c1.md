### Title
Unauthenticated/unallowlisted trigger requests forwarded to all DON nodes by the legacy Web API gateway handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The external report concerns systems trusting external data feeds without on-chain/timing verification, letting the retrieval-to-execution delay bias trade outcomes. The closest reachable unprivileged-actor analog in this repository is the legacy Web API gateway trigger path, where `HandleLegacyUserMessage` forwards any structurally-valid, non-stale trigger message straight to every DON member without applying an allowlist or per-sender rate limit — a gap the code itself flags as unfinished.

### Finding Description
`(*handler).HandleLegacyUserMessage` validates only payload structure and message staleness before broadcasting the request to the DON: [1](#0-0) 

The staleness check compares `payload.Timestamp` against `time.Now()` using `h.config.MaxAllowedMessageAgeSec`, but there is no verification of *who* is allowed to invoke `MethodWebAPITrigger` for a given DON/capability before the request is dispatched — the code contains an explicit marker for this: [2](#0-1) 

After the (weak) checks, the message is forwarded to every member of the DON unconditionally: [3](#0-2) 

By contrast, the newer/parallel paths in this codebase explicitly implement authorization before forwarding to nodes: the Vault gateway handler enforces an `Authorizer`/allowlist plus a replay guard before any request reaches node logic [4](#0-3) [5](#0-4) , and the gateway connector enforces timestamp-bounded, gateway-ID-scoped challenge/response authentication [6](#0-5) . The legacy capabilities handler lacks the equivalent sender/allowlist gate at the point it decides to broadcast to the DON, meaning trust is placed in the payload timestamp alone (an externally supplied, unverified value) rather than in an authenticated/authorized sender — directly mirroring the report's theme of "too much trust outside the contract" and time-based bias in externally supplied data.

### Impact Explanation
If this legacy handler is reachable by unprivileged/unauthenticated HTTP clients (its `TODO` comment states allowlist and rate-limiting are not yet applied at this call site), any client able to reach the gateway's user-facing endpoint can cause `MethodWebAPITrigger` messages to be broadcast to every node in a DON, consuming DON node resources and potentially triggering workflow executions that should have been restricted to authorized senders/capabilities. This is a concrete unauthorized-job/trigger-dispatch risk, not merely an informational note, because forwarding occurs unconditionally to `donConfig.Members` once the minimal structural/staleness checks pass.

### Likelihood Explanation
Likelihood depends on whether this legacy `handler` package (as opposed to the v2 handler in `core/services/gateway/handlers/capabilities/v2/http_handler.go`) is still wired into a production gateway configuration and reachable from the public/user-facing listener. I could not confirm from the indexed code whether this legacy handler is currently registered in a live deployment path or has been fully superseded by the v2 handler — this is an open question that would need verification against the gateway's handler registration/config (e.g., `core/services/gateway/gateway.go`, `multihandler.go`) to establish current exposure.

### Recommendation
Enforce sender/allowlist authorization (mirroring the Vault handler's `Authorizer` pattern) and per-sender rate limiting in `HandleLegacyUserMessage` before forwarding any `MethodWebAPITrigger` message to DON members, and resolve/remove the outstanding `TODO` at `core/services/gateway/handlers/capabilities/handler.go:384`. If this legacy handler is retained only for backward compatibility, confirm and document whether it is still routed to from production configurations, and if not, disable/remove it to eliminate the exposure.

Not independently reproducible from static review alone; the concrete PoC would require confirming the legacy handler is registered against a reachable gateway endpoint, then submitting a `web_api_trigger` message with a fresh timestamp and arbitrary payload without prior allowlist registration, observing it is broadcast to `don.SendToNode` for all DON members as shown in [7](#0-6) .

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (c *gatewayConnector) ChallengeResponse(ctx context.Context, url *url.URL, challenge []byte) ([]byte, error) {
	challengeElems, err := network.UnpackChallenge(challenge)
	if err != nil {
		return nil, err
	}
	if len(challengeElems.ChallengeBytes) < c.config.AuthMinChallengeLen {
		return nil, network.ErrChallengeTooShort
	}
	gatewayId, found := c.urlToId[url.String()]
	if !found || challengeElems.GatewayId != gatewayId {
		return nil, network.ErrAuthInvalidGateway
	}
	nowTs := uint32(c.clock.Now().Unix())
	ts := challengeElems.Timestamp
	if ts < nowTs-c.config.AuthTimestampToleranceSec || nowTs+c.config.AuthTimestampToleranceSec < ts {
		return nil, network.ErrAuthInvalidTimestamp
	}
	return c.signer.Sign(ctx, challenge)
}
