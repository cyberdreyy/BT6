One more check needed on `epochNumber` increment ordering relative to `collectWithdrawFunds` in `stopEpochWithDuration`.### Title
Loss-adjusted withdraw receipts escape the haircut once a newer request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The blind SQL injection in Cloudlog is an attacker-controlled search parameter that makes the backend return rows outside the scope the application intended. The closest analog in idle-tranches is the epoch keying of withdraw receipts in `IdleCreditVault.claimWithdrawRequest`: the loss-adjusted claim path looks up `lossRecoveryPriceByEpoch` using only the *latest* request epoch (`lastWithdrawRequest[_user]`), while the funded claim path pays the *aggregate* `withdrawsRequests[_user]` at par. A user who holds a haircutted receipt from a loss epoch and then files a new withdraw request causes the loss-epoch receipt to be silently folded into the par-value claim, escaping the loss socialization.

### Finding Description
`claimWithdrawRequest` runs two payout legs in sequence [1](#0-0) :

1. `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]` and only pays the haircut (`claimBasis * lossRecoveryPrice / RECOVERY_FULL`) if `lossRecoveryPriceByEpoch[lossEpoch]` is non-zero [2](#0-1) .
2. `_claimFundedWithdrawRequest` then pays the *whole remaining* `withdrawsRequests[_user]` aggregate at par, gated only by `epochNumber > lastWithdrawRequest[_user]` [3](#0-2) .

`requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds to both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [4](#0-3) . There is no check for an existing loss-adjusted receipt.

Attack sequence (unprivileged KYC'd lender, running → stopped-with-loss → running epochs):

1. Epoch N running: attacker calls `requestWithdraw`. `lastWithdrawRequest = N`, receipt recorded under `withdrawsRequestsByEpoch[N]` and added to `withdrawsRequests`.
2. `stopEpochWithDuration(..., _lossAmount)` is executed by manager with a loss; `collectWithdrawFunds` is funded below `pendingBasis`, so `lossRecoveryPriceByEpoch[...]` is set < R ECOVERY_FULL and `pendingWithdraws` is zeroed [5](#0-4) . All epoch-N receipts are now haircutted.
3. Epoch N+1 running: attacker calls `requestWithdraw` again for any small amount. `lastWithdrawRequest` is overwritten to N+1.
4. After epoch N+1 ends (`epochNumber = N+2`), attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest = N+1`; `lossRecoveryPriceByEpoch[N+1] == 0`, so it returns 0 and never clears `withdrawsRequestsByEpoch[N]`.
   - `_claimFundedWithdrawRequest` passes (`N+2 > N+1`) and pays the full `withdrawsRequests[_user]` — including the epoch-N receipt that was funded only at `lossRecoveryPrice` — at par.

Invariant broken: loss waterfall / loss socialization. The loss-adjusted reserve collected from the borrower covers epoch-N receipts only at `lossRecoveryPrice`; paying them at par overdraws the strategy's funded-claim reserve.

### Impact Explanation
Direct theft / insolvency of unclaimed yield: the attacker receives `receipt_N * (1 - lossRecoveryPrice/RECOVERY_FULL)` more than entitled, paid from the same funded reserve meant for all other epoch-N claimers. Every other epoch-N withdrawer is diluted; if the attacker dominates the pending bucket, the reserve is drained and later legitimate claimers cannot be paid (permanent under-funding of claims). Loss scales linearly with the attacker's epoch-N receipt size and the haircut depth.

### Likelihood Explanation
Requires only: (a) holding a withdraw receipt in an epoch that ends with `stopEpochWithDuration` loss or partial funding, and (b) filing a second `requestWithdraw` in the next running epoch — both are normal user operations, no privileged cooperation needed. The trigger (a borrower shortfall at stop) is a designed-in code path, not an edge case. Note: depending on whether `epochNumber` is incremented before `collectWithdrawFunds` runs inside `stopEpoch`, the stored key may be `N+1` rather than `N`; in that case the loss claim path is *never* reachable for epoch-N receipts at all (lookup of `lossRecoveryPriceByEpoch[lastWithdrawRequest]` mismatches), and they are paid at par immediately — an even simpler variant of the same bug. This ordering was not fully verifiable from the indexed snippets and should be confirmed in a PoC.

### Recommendation
Track loss-adjusted receipts independently of `lastWithdrawRequest`. Options:
- In `_claimLossAdjustedWithdrawRequest`, iterate/lookup the user's *actual* receipt epochs (e.g., check `withdrawsRequestsByEpoch[_user][e]` against all epochs with non-zero `lossRecoveryPriceByEpoch`), not just `lastWithdrawRequest`.
- Or in `requestWithdraw`, if the user has an outstanding receipt in an epoch with a pending `lossRecoveryPriceByEpoch`, settle it immediately or revert.
- At minimum, keep a per-user flag/list of epochs with loss-adjusted receipts so `_claimFundedWithdrawRequest` can exclude their basis from the par claim.

### Proof of Concept

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
