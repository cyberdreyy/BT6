### Title
Permissionless front-running of `init_global_fee_state` allows an attacker to become the program's global fee admin - ([File: programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs])

### Summary
The external report describes a Solidity "uninitialized template contract" pattern: a factory constructs base/implementation contracts that anyone can then call `initialize()` on to claim ownership, because no access control gates the initializer. marginfi-v2 is an Anchor/Solana program and has no equivalent clone-factory/implementation-contract pattern, so the literal bug class (uninitialized `pairTokenBase`/`poolBase` templates) does not apply. However, the closest structurally analogous issue is `init_global_fee_state`, a "runs once per program" instruction that creates the singleton `FeeState` PDA and assigns whoever calls it as `global_fee_admin` — with no restriction on who the caller (`payer`) may be.

### Finding Description
`InitFeeState` only requires an arbitrary `Signer` as `payer`; there is no check that the caller is the deploying authority, the program upgrade authority, or any pre-agreed key [1](#0-0) . The instruction sets `fee_state.global_fee_admin = admin_key` and `fee_state.global_fee_wallet = fee_wallet` directly from caller-supplied arguments [2](#0-1) . Because the `fee_state` account is a PDA derived solely from the fixed seed `FEE_STATE_SEED` (no group-specific or admin-specific seed component) [3](#0-2) , its address is fully deterministic and identical across the whole program deployment — comparable to the single `poolCommitterBase`/`poolBase` template addresses in the Solidity report that anyone can race to initialize.

This is functionally the same root cause as the reported bug class: an unprotected/racy initializer on a "template"/singleton state object that grants privileged ownership to whichever party calls it first. In the Solidity report, an attacker races the constructor's un-initialized templates to become `owner`; here, an attacker can race the program deployer's first call to `init_global_fee_state` (submitting their own transaction with a higher priority fee or simply monitoring mempool/slot activity right after program deployment) to become `global_fee_admin` before the legitimate team does so, since the instruction has no `#[account(constraint = ...)]`/hardcoded-admin/upgrade-authority check.

The `MarginfiGroupInitialize` instruction, by contrast, is not vulnerable to this class: the `marginfi_group` account is a fresh keypair (not a deterministic PDA) provided and signed for by the caller [4](#0-3) , so there is no shared "template" address for an attacker to race — each group creator controls their own unique account. This confirms `init_global_fee_state` (and analogously `init_global_fee_state_v2`, which has the identical no-admin-check pattern [5](#0-4) ) is the only reachable analog of the reported bug class.

### Impact Explanation
If an attacker's transaction to `init_global_fee_state` lands before the intended admin's transaction, the attacker becomes `global_fee_admin` and can set `global_fee_wallet` to an address they control, along with `program_fee_fixed`/`program_fee_rate`/flat SOL fees. Since `FeeState` is per-program and singleton, this would let the attacker redirect all future protocol/program fee revenue (bank-init fees, liquidation fees, order fees, and program fee shares taken from every group's interest) to their own wallet, and would require redeploying/migrating the whole state to fix, since the PDA seed is fixed and `init` cannot be repeated once occupied. This meets the "value redirection" / "unauthorized state change with financial effect" bar.

### Likelihood Explanation
Likelihood is a function of deployment operational security, not user interaction: it requires the attacker to win a slot-ordering race against the legitimate deployer's `init_global_fee_state` call immediately after/alongside program deployment. This is a narrow, single-shot window (the instruction can only ever succeed once per program because it uses Anchor's `init` on a deterministic seed), and most teams protect this by bundling the initialization call in the very same transaction/deployment script as the program upgrade, or restricting it via multisig atomic execution. Given the code as written contains no explicit protection (no hardcoded pubkey check, no `access_control`), the risk is real but requires either public mempool visibility around deployment time or a delay between deploy and init call — making it a credible but situational/timing-dependent bypass rather than a fully unprotected privileged-admin analog excluded by the rules.

### Recommendation
Add an explicit authorization check to `InitFeeState`/`InitFeeStateV2` restricting who may call it — e.g., require the payer/signer to match the program's upgrade authority (verified via the `BpfLoaderUpgradeable` program-data account) or a hardcoded governance pubkey compiled into the program, so that the `init` call cannot be front-run by an arbitrary signer. Alternatively, ensure the initialization instruction is always submitted atomically with program deployment/upgrade in the same transaction so no window for a third party exists.

### Proof of Concept
1. Program is deployed but `init_global_fee_state` has not yet been called (the `FeeState` PDA at `[FEE_STATE_SEED]` does not exist).
2. An attacker who monitors the deployment (or simply beats the legitimate operator to submitting the call) constructs and sends their own `init_global_fee_state` instruction with `admin_key = attacker_key`, `fee_wallet = attacker_wallet`, per the account/instruction layout [6](#0-5) .
3. Because there is no access-control constraint on `payer`, the transaction succeeds, permanently setting `fee_state.global_fee_admin` and `fee_state.global_fee_wallet` to attacker-controlled keys [7](#0-6) .
4. All subsequent protocol/program fees routed to `global_fee_wallet` (bank-init flat fee, liquidation flat fee, program fee rate/fixed on every group) now flow to the attacker, and only the attacker (as `global_fee_admin`) can subsequently modify fee parameters via `edit_global_fee`.

#[allow(unused_variables)]
pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}

#[derive(Accounts)]
pub struct InitFeeState<'info> {
    /// Pays the init fee
    #[account(mut)]
    pub payer: Signer<'info>,

    #[account(
        init,
        seeds = [
            FEE_STATE_SEED.as_bytes()

        bump,
        payer = payer,
        space = 8 + FeeState::LEN,
    )]
    pub fee_state: AccountLoader<'info, FeeState>,

}
