### Title
Signer-side block-proposal validation accepts an orphaned tenure-extend burn view as canonical due to self-referential sortition handle - ([File: stackslib/src/net/api/postblock_proposal.rs])

### Summary
`NakamotoBlockProposal::validate` resolves the block's burn view via `NakamotoChainState::get_block_burn_view`, which for a `TenureChange` with an `Extend` cause simply trusts the block's own `burn_view_consensus_hash` field. It then builds `db_handle`/`burn_dbconn` by calling `sortdb.index_handle(&sort_tip.sortition_id)` rooted at that attacker-chosen snapshot, and all subsequent canonicity checks (`check_block_has_valid_tenure` -> `db_handle.has_consensus_hash`, and `validate_normal_nakamoto_block_burnchain` -> `validate_nakamoto_tenure_snapshot` -> `SortitionDB::get_canonical_burn_chain_tip(db_handle)`) are evaluated relative to that self-chosen root rather than against the sortition DB's actual, independently-derived canonical tip.

### Finding Description
In `NakamotoBlockProposal::validate`, the burn view is computed as: [1](#0-0) 

`get_block_burn_view` only validates, for an `Extend` cause, that the claimed `tenure_change.burn_view_consensus_hash` *descends from the parent's burn view* — it never checks that this consensus hash is on the sortition DB's currently canonical fork: [2](#0-1) 

`SortitionDB::get_block_snapshot_consensus` is a plain lookup by consensus hash and returns a snapshot regardless of whether it is on the canonical fork (orphaned snapshots remain in the DB). The resulting `sort_tip` is then used to construct `db_handle = sortdb.index_handle(&sort_tip.sortition_id)`, i.e., a handle whose root/chain-tip context *is* the attacker-supplied, potentially orphaned snapshot: [3](#0-2) 

`check_block_has_valid_tenure` then calls `db_handle.has_consensus_hash(tenure_id)`, which only verifies ancestry against `db_handle`'s own root — not against the sortition DB's true canonical tip: [4](#0-3) 

Likewise, `validate_normal_nakamoto_block_burnchain` calls `validate_nakamoto_tenure_snapshot(db_handle, block)`, which computes `sort_tip = SortitionDB::get_canonical_burn_chain_tip(db_handle)` — again using the same self-referential `db_handle`, so "canonical" here means canonical *within the fork rooted at the attacker-chosen sort_tip*, not canonical within the whole sortition history: [5](#0-4) 

By contrast, the analogous node-side ingestion path (`process_next_nakamoto_block`) contains an explicit comment acknowledging that canonicity of the burn view must be checked *before* this point ("This should be checked already during block acceptance and parent block processing"), implying the signer-facing `validate()` path is expected to perform an independent canonicity check that it does not actually perform: [6](#0-5) 

Exploit flow: after a Bitcoin reorg orphans a sortition `S` that was canonical moments earlier, an attacker who wins the current miner slot crafts a `TenureChange` with `Extend` cause whose `burn_view_consensus_hash` is `S`'s consensus hash. Since `S` still exists in the sortition DB (just non-canonical) and the parent's burn view can be made to legitimately descend from `S` within that stale fork, `get_block_burn_view` returns `S`'s hash without complaint. `validate()` then builds all subsequent checks against a `db_handle` rooted at `S`, so `has_consensus_hash` and `get_canonical_burn_chain_tip` both operate in `S`'s own (non-canonical) fork context and report success, even though `S` is not on the current canonical Bitcoin fork.

### Impact Explanation
If confirmed, this would let a signer sign a `BlockResponse::Accepted` for a tenure-extend block anchored to a burn view that is not on the canonical Bitcoin fork, i.e., a non-canonical tenure/block getting a valid signer signature — a Critical chain-safety violation (a signer signing a non-canonical/invalid block) as described in the question's impact categories.

### Likelihood Explanation
Preconditions require a recent Bitcoin reorg orphaning a previously-canonical sortition, and the attacker must hold the current miner slot to submit the crafted `Extend`-cause tenure-change block; both are attacker-cost-bounded to "win a single miner slot" plus gossip of the resulting `BlockProposal`, matching the assumed attacker capability. Reorgs of this depth are not routine, so the precondition window is narrow but not implausible, and the flaw would be repeatable each time such a window occurs.

### Recommendation
In `NakamotoBlockProposal::validate` (and in `get_block_burn_view`'s `Extend` branch), independently resolve the sortition DB's actual canonical tip via `SortitionDB::get_canonical_burn_chain_tip` on the *unscoped* connection (not on a handle rooted at the attacker-supplied burn view), and verify that the claimed `burn_view_consensus_hash`/`sort_tip.sortition_id` is an ancestor of that independently-derived canonical tip before using it to build `db_handle`/`burn_dbconn` for subsequent checks.

### Proof of Concept
Rust test plan (stackslib, extending existing block-proposal validation tests):
1. Build a sortdb fork history: create canonical sortition chain `A -> B -> C`, capture `C`'s consensus hash, then fork the chain at `B` to create a new canonical chain `A -> B -> C'` such that `C` becomes orphaned but remains queryable via `SortitionDB::get_block_snapshot_consensus`.
2. Construct a `NakamotoBlock` whose parent's burn view is `B`, and whose `TenureChange` has cause `Extend` with `burn_view_consensus_hash = C` (the orphaned snapshot), signed by the attacker's miner key for the current (post-fork) tenure.
3. Call `NakamotoBlockProposal::validate(...)` with this proposal against the sortdb where `C'` is canonical, and assert that:
   - Before fix: `validate()` returns `Ok(BlockValidateOk)` (or passes `check_block_has_valid_tenure`/`validate_nakamoto_tenure_snapshot`) despite `C` being non-canonical — demonstrating `sort_tip.sortition_id` (`C`) ≠ the true canonical tip's ancestor at that height.
   - After fix: `validate()` returns `Err(BlockValidateRejectReason { reason_code: ValidateRejectCode::NonCanonicalTenure/NoSuchTenure, .. })` because the independently-derived canonical tip does not have `C` as an ancestor.

    pub(crate) fn check_block_has_valid_tenure(
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }

        db_handle: &SortitionHandleConn,
        block: &NakamotoBlock,
    ) -> Result<BlockSnapshot, ChainstateError> {

        // containing the parent block-commit.  This is the snapshot that corresponds to when the
        // miner begain its tenure; it may not be the burnchain tip.
        let consensus_hash = &block.header.consensus_hash;

        let sort_tip = SortitionDB::get_canonical_burn_chain_tip(db_handle)?;

        // burn chain tip that selected this commit's block (the tenure sortition)
        let Some(tenure_burn_chain_tip) =
            SortitionDB::get_block_snapshot_consensus(db_handle, consensus_hash)?
        else {
            warn!("No sortition for {}", consensus_hash);
            return Err(ChainstateError::InvalidStacksBlock(
                "No sortition for block's consensus hash".into(),
            ));
        };

            db_handle,
