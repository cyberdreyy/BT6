### Title
`UseGlobalContract` action is missing the actor-permission ("self-only") check, allowing an unrelated predecessor to rebind a victim account's `AccountContract` - (File: runtime/runtime/src/global_contracts.rs, runtime/runtime/src/actions.rs)

### Summary
`action_use_global_contract` in `runtime/runtime/src/global_contracts.rs` mutates whatever account is named by `receipt.receiver_id()`, using only that receiver as the target — it never checks that the receipt's `predecessor_id`/`actor_id` equals the receiver. Per `docs/RuntimeSpec/Actions.md` (lines 26-32) the runtime enforces `predecessor_id == receiver_id` only for `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount` — `UseGlobalContract` and `DeployGlobalContract` are explicitly not in that self-only list, and the `ActorNoPermission` check in `runtime/runtime/src/actions.rs` is likewise scoped to that enumerated set. This means a `DelegateAction`/`DelegateActionV2` (or a promise batch created by an attacker-controlled contract) whose `receiver_id` differs from `sender_id`/predecessor can carry a `UseGlobalContract` action that gets applied to the differing receiver account.

### Finding Description
`action_use_global_contract`/`use_global_contract` take `account_id` and `account` that come from the receipt's target (`receipt.receiver_id()`), and simply overwrite `account.set_contract(...)` with the attacker-chosen `GlobalContractIdentifier` (by `CodeHash` or `AccountId`) with no comparison to `predecessor_id`/`actor_id`: [1](#0-0) 

In `runtime/runtime/src/lib.rs`, the dispatch for `Action::UseGlobalContract` passes `account_id` (derived from the receipt) straight into `action_use_global_contract` with no actor/permission gate comparable to the ones applied to `DeployContract`/`Stake`/`AddKey`/`DeleteKey`: [2](#0-1) 

The spec explicitly documents which actions require `predecessor_id == receiver_id` — a list that excludes `UseGlobalContract` and `DeployGlobalContract`: [3](#0-2) 

Meanwhile, the same `ActorNoPermission` machinery elsewhere is only exercised/tested for the enumerated actions (`meta_tx_deploy`, `meta_tx_stake`, `meta_tx_add_key`, `meta_tx_delete_key`), each of which forces `receiver = sender` and comments "Can only deploy/stake/add key/delete key on own account": [4](#0-3) 

By contrast, the existing test helper for `UseGlobalContract` via `DelegateAction` sets `sender_id` and `receiver_id` to the *same* account and never exercises (or asserts rejection of) the mismatched case: [5](#0-4) 

Exploit flow: an attacker (`attacker.near`) signs a `DelegateAction` with `sender_id = attacker.near`, `receiver_id = victim.near`, `actions = [UseGlobalContract { contract_identifier: <attacker's own global contract> }]`, signed with the attacker's own key (fully within their rights). They wrap it in a transaction and relay it themselves (or via any relayer, even themselves acting as relayer). Because `predecessor_id`/`actor_id` for the resulting inner receipt is `attacker.near` while `receiver_id`/`account_id` is `victim.near`, and `UseGlobalContract` is not subject to the actor-equality check, `action_use_global_contract` rebinds `victim.near`'s `AccountContract` to the attacker's chosen global contract with no participation from the victim's access key. The same effect is reachable without Delegate at all: an attacker's own already-deployed contract can call `promise_batch_action_use_global_contract_by_account_id`/`by_hash` targeting an arbitrary `receiver_id` (this is normal, unrestricted cross-account promise dispatch, exactly like `FunctionCall`), producing a receipt with `predecessor_id = attacker_contract`, `receiver_id = victim`.

### Impact Explanation
Rebinding a victim's `AccountContract` is a full authorization escalation across accounts: any subsequent `FunctionCall` receipt sent to `victim.near` will execute the attacker's wasm code under the victim's identity and balance. That attacker-controlled code can then issue `Transfer`, `FunctionCall`, or other promises whose `predecessor_id` is `victim.near`, enabling theft of the victim's NEAR balance and abuse of any privileges the victim account holds (e.g. draining funds, corrupting protocol/FT contracts if the victim account is a well-known contract). This falls under "authorization escalation across accounts or promises" and "theft of user funds" per the NEAR bounty program's Contracts execution category.

### Likelihood Explanation
The attacker needs only an ordinary funded account and no interaction with the victim: they self-sign a `DelegateAction`/`DelegateActionV2` with mismatched `sender_id`/`receiver_id`, or deploy their own trivial contract that issues a cross-account promise with a `UseGlobalContract` batch action. Both paths use only standard, permissionless RPC transaction submission. Cost is limited to gas plus the target's `use_global_contract_byte` fee (charged to the sending account, not the victim). The attack is fully repeatable against any account and requires no validator/node privileges, matching an unprivileged-client threat model.

### Recommendation
Add `UseGlobalContract` (and `DeployGlobalContract`, if it has the same gap) to the actor-permission check that currently guards `DeployContract`/`Stake`/`AddKey`/`DeleteKey`, requiring `actor_id == account_id` (i.e., `predecessor_id == receiver_id`, honoring the `CreateAccount`-then-`account_id`-becomes-actor exception) before `action_use_global_contract` is allowed to mutate the account's `AccountContract`.

### Proof of Concept
Add an integration test in `test-loop-tests/src/tests/global_contracts.rs` mirroring `use_global_contract_via_delegate_action` but with `sender_id != receiver_id`:
1. Create `attacker.near` and `victim.near` accounts, fund both.
2. Have `attacker.near` deploy a global contract (`DeployGlobalContract`) containing distinguishable wasm.
3. Construct `DelegateAction { sender_id: attacker.near, receiver_id: victim.near, actions: [UseGlobalContract { contract_identifier: GlobalContractIdentifier::AccountId(attacker.near) }] }`, sign with attacker's key, wrap in a `Delegate` transaction from `attacker.near` to `victim.near`.
4. Submit the transaction and assert the outcome (expect `ActionErrorKind::ActorNoPermission` after the fix; currently the tx succeeds).
5. Query `victim.near`'s account via `view_account`/state and confirm `AccountContract` now equals `GlobalByAccount(attacker.near)`, proving the rebind occurred without any action signed by `victim.near`'s key.

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())

Each transaction consists a list of actions to be performed on the `receiver_id` side. Since transactions are first
converted to receipts when they are processed, we will mostly concern ourselves with actions in the context of receipt
processing.
 
For the following actions, `predecessor_id` and `receiver_id` are required to be equal:

- `DeployContract`
- `Stake`
- `AddKey`
- `DeleteKey`
- `DeleteAccount`

NOTE: if the first action in the action list is `CreateAccount`, `predecessor_id` becomes `receiver_id`
for the rest of the actions until `DeleteAccount`. This gives permission by another account to act on the newly created account.
