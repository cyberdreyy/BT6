### Title
Cross-user response delivery via MessageId reuse in `savedCallbacks` (stale-callback hijack) - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores a caller's callback in `h.savedCallbacks[msg.Body.MessageId]` without checking whether that key already/still exists, and `handleWebAPITriggerMessage` blindly delivers whatever DON-node response with a matching `MessageId` arrives to whatever callback currently occupies that map slot. Since `MessageId` is attacker-chosen (only length/format is validated) and the pruning of stale entries is time/size based rather than tied to individual request completion, a late (but otherwise validly signed by the DON node) response for an earlier, already-pruned or overwritten request can be delivered to a different, unrelated caller who later reused the same `MessageId`.

### Finding Description
- `HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:411-414) unconditionally overwrites `h.savedCallbacks[msg.Body.MessageId]` with the new callback: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}`. No check exists for whether the ID is already in use by another (possibly still in-flight) request. [1](#0-0) 
- `handleWebAPITriggerMessage` (handler.go:148-162) looks up `savedCallbacks` purely by `msg.Body.MessageId` from the DON node's response, deletes the entry, and forwards the response to whichever callback was found — there is no cross-check that the response corresponds to the same request/user that originally registered that callback (e.g., no requester/sender binding stored and compared). [2](#0-1) 
- `MessageId` itself is fully caller-supplied; `Message.Validate()` only enforces length bounds and disallows a trailing null byte — it does not enforce uniqueness or bind the ID cryptographically to a specific requester session. [3](#0-2) 
- `pruneCallbacks` removes entries purely based on age (`CallbackMaxAgeSec`, default 120s) or map size, independent of whether a DON response for that entry is still outstanding. [4](#0-3) 

Exploit flow:
1. Attacker (or victim A, whichever the attacker times) sends request A with `MessageId = "X"`. `savedCallbacks["X"]` = A's callback.
2. Request A's DON round-trip is slow/delayed beyond `CallbackMaxAgeSec`, or the map is size-pruned, so `savedCallbacks["X"]` is deleted by `pruneCallbacks` while the DON node's response for A is still in flight.
3. Attacker submits request B, deliberately reusing `MessageId = "X"`. `HandleLegacyUserMessage` writes `savedCallbacks["X"]` = B's callback (or, without even needing pruning, an attacker could just resend an ID with a request while a first request with that ID is still outstanding, immediately overwriting it before it's pruned).
4. The delayed DON-node response tagged with `MessageId = "X"` (from the request originally sent to nodes for A) arrives at `handleWebAPITriggerMessage`, finds `savedCallbacks["X"]` = B's callback, deletes it and delivers A's response payload to B.

Since `msg.Body.Sender != nodeAddr` in `HandleNodeMessage` only checks that the response came from the expected node address, not that it correlates to the originating request's actual issuer, this check does not stop the hijack. [5](#0-4) 

### Impact Explanation
This causes cross-user response confusion: an attacker (as a normal, unprivileged gateway user) can cause another user's (or their own second, isolated) web-API-trigger response — including HTTP response bodies/headers fetched on behalf of the DON — to be delivered into an attacker-controlled callback slot, or conversely cause a legitimate user to receive a stale/foreign response not belonging to their request. Depending on payload sensitivity (headers/response bodies from external endpoints fetched by DON nodes on a user's behalf), this is a request/response isolation violation that could leak data intended for a different tenant/callback, matching a "cross-user response confusion" / broken request-response binding impact class.

### Likelihood Explanation
No elevated privileges are required — any client able to submit gateway messages with attacker-chosen `MessageId` values can attempt this. The main precondition is timing: the attacker needs their new request (reusing `MessageId=X`) to be registered in `savedCallbacks` before or shortly after the stale in-flight DON response for the original request tagged `X` arrives, and this timing window is bounded by `CallbackMaxAgeSec` (default 120s) or the periodic size-based eviction (`CallbackPruneIntervalSec`, default 30s). Because pruning is a global periodic sweep, not per-request tracking of "did the response arrive," and eviction can occur "briefly exceed under heavy load" per the code's own comment, this is a realistic and repeatable race rather than a purely theoretical one.

### Recommendation
Bind each `savedCallback` entry to additional context beyond the bare `MessageId` — e.g., store and verify the original requester's identity/session token (or a random, gateway-generated correlation nonce not attacker-controlled) alongside the callback, and reject/ignore late node responses whose associated request no longer matches the expected requester. Alternatively, disallow reuse of an in-flight `MessageId` in `HandleLegacyUserMessage` (reject if a non-expired entry already exists for that key), and track per-request completion so a pruned/timed-out request's late response is dropped instead of being deliverable to a newly registered callback under the same key.

### Proof of Concept
Go unit test plan (in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` with a short `CallbackMaxAgeSec`/`CallbackPruneIntervalSec` (or directly manipulate `h.savedCallbacks` and call `h.pruneCallbacks()`).
2. Register callback A via `handler.HandleLegacyUserMessage` with `MessageId = "X"`, using a mock `handlers.Callback` (`callbackA`) that records any response delivered to it.
3. Simulate expiry: forcibly age the entry past `CallbackMaxAgeSec` (or call `pruneCallbacks()` to remove it), verifying `h.savedCallbacks["X"]` is now absent.
4. Register callback B via a second `HandleLegacyUserMessage` call, also using `MessageId = "X"`, with mock `callbackB`.
5. Call `handler.HandleNodeMessage` (or directly `handleWebAPITriggerMessage`) with a DON-node response `msg` whose `Body.MessageId = "X"`, simulating the late response to request A.
6. Assert: `callbackB.SendResponse` was invoked with A's response payload (demonstrating the hijack) — and assert this is the vulnerable current behavior. The fix should instead assert the late response is dropped/rejected and `callbackB` never receives it, and/or that `callbackA`/`callbackB` isolation is enforced (e.g., via an error logged and no delivery, or a distinct internal request token check).

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
