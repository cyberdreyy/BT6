### Title
Stale confirmations from removed multisig members still count toward `num_confirmations`, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`confirm()` counts the size of the stored `confirmations` set against `num_confirmations` without verifying that every public key/account in that set still belongs to a current member. `delete_member` (and the equivalent `DeleteKey` action in the older `multisig/src/lib.rs`) only purges *requests originated by* the removed member — it never scrubs that member's *confirmations left on requests created by others*. A confirmation given by a member who is later removed therefore remains valid currency toward the K-of-N threshold, letting a request execute with fewer genuinely live approvals than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` simply checks that the calling member hasn't already confirmed, then compares the confirmation-set size to `num_confirmations`: [1](#0-0) 

Membership removal happens in `delete_member`, which is only invoked from the `DeleteMember` request action: [2](#0-1) 

Note the filter `if r.member == member` (line 365) — it only removes *requests whose original requester* was the deleted member. It does not scan `self.confirmations` for entries where the deleted member's identity appears as a *confirmer* of some other pending request. The identical pattern exists in the older `multisig` contract's `DeleteKey` handling: [3](#0-2) 

which filters by `r.signer_pk == pk` (the requester), again leaving that key's confirmations on requests created by *other* members untouched.

As a result, the binding the K-of-N scheme is supposed to enforce —
`confirmations recorded == approvals from currently live members`
— can diverge: `confirmations recorded ≥ num_confirmations` while `live-member approvals < num_confirmations`.

### Impact Explanation
This crosses the threshold-authorization boundary called out in scope: "a multisig request executed below threshold." A `Transfer`, `AddKey`, `FunctionCall`, or any other `MultiSigRequestAction` (including moving NEAR out of the account) can be pushed through `execute_request` with genuine approval from fewer members than the configured `num_confirmations`, because a stale confirmation from a since-removed member is still tallied. This is a Critical-impact issue per the scope's definition of "a multisig request executed below threshold."

### Likelihood Explanation
No attacker privilege beyond ordinary multisig operation is required to trigger the divergence — it is a natural consequence of legitimate member rotation (a very common operation for any multisig, e.g. onboarding/offboarding signers) combined with any request that was only partially confirmed at the time of the rotation. Any member (or an outside party who convinces members to rotate signers while a request is pending) can end up in this state; it requires no compromise of a key, no owner privilege beyond normal membership, and no social engineering beyond what multisig usage already implies.

### Recommendation
When executing `DeleteMember` (or `DeleteKey` in the legacy contract), scan all pending requests' confirmation sets and remove the deleted member's identity/key from every one of them (not just requests where that member was the original requester). Alternatively, when tallying confirmations in `confirm()`, filter the stored confirmation set against `self.members` (or the live access-key list) before comparing its length to `num_confirmations`, so stale confirmations from removed members never count toward execution.

### Proof of Concept
Using `multisig2::MultiSigContract` with `num_confirmations = 2` and members `{A, B, C}`:

1. Member `A` calls `add_request(R)` for `Transfer { amount }` to some receiver — `R` is stored with `member = A`; `confirmations[R] = {}`.
2. Member `C` calls `confirm(R)` — `confirmations[R] = {C}` (1 of 2, not yet executed).
3. Members `A` and `B` create and confirm a separate request `DeleteMember { member: C }`, which reaches 2 confirmations and executes `delete_member`, removing `C` from `self.members`. Because `delete_member`'s cleanup only removes requests where `r.member == C` (requests C *created*), and `R` was created by `A`, `R`'s stale confirmation set `{C}` is left untouched.
4. Member `B` calls `confirm(R)`. `confirm()` checks `!confirmations[R].contains(B)` (true), then `confirmations.len() + 1 (=2) >= num_confirmations (2)` → `execute_request(R)` fires the `Transfer`.
5. The transfer executes with confirmations nominally `{C, B}` even though `C` is no longer a member — only one currently-live member (`B`) actually approved, violating the intended 2-of-N guarantee. [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
