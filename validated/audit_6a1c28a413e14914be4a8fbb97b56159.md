### Title
Permanent Loss of `add_stake` Fee Rewards via Sustained `NULL_SHAREHOLDER` Trap - ([File: aptos-move/framework/aptos-framework/sources/delegation_pool.move])

### Summary
`delegation_pool::add_stake` routes the `add_stake` fee to a special, unownable `NULL_SHAREHOLDER` address (`@0x0`), intending to redistribute that fee back to the pool as rewards once `pending_active` on the stake pool returns to zero [1](#0-0) . Any unprivileged delegator can prevent this release from ever happening by re-invoking `add_stake` at least once per epoch, keeping `pending_active` perpetually non-zero, which permanently strands the accumulated fee value under an address that no one can ever unlock, withdraw, or redeem.

### Finding Description
`add_stake` synchronizes the pool, computes an `add_stake_fee` for the newly added amount, and buys shares for that fee into the `NULL_SHAREHOLDER` (`@0x0`) active-shares balance: [2](#0-1) 

The only mechanism that ever releases these fee shares back to the rest of the pool as rewards is in `synchronize_delegation_pool`, and it is conditioned on `pending_active == 0`: [3](#0-2) 

`NULL_SHAREHOLDER` shares are explicitly documented as unspendable: `unlock_internal` rejects any attempt to unlock stake on behalf of `NULL_SHAREHOLDER`, and a dedicated test confirms it also cannot be evicted by the pool owner: [4](#0-3) [5](#0-4) 

Because address `0x0` has no controllable signer in the Aptos framework, any coin value permanently attributed to it as active shares can never be claimed, unlocked, or withdrawn by anyone. The design assumes `pending_active` naturally clears to `0` once an epoch passes without new `add_stake` calls, but nothing prevents an unprivileged delegator from calling `add_stake` (even with a trivially small amount) once per epoch, indefinitely, which keeps `pending_active` non-zero and blocks the `redeem_active_shares(pool, NULL_SHAREHOLDER, MAX_U64)` cleanup path from ever executing. Each such call adds further fee-shares to `NULL_SHAREHOLDER`, compounding the permanently-stranded balance over time. `get_stake`'s view logic also confirms these shares are excluded from redistribution only when `pending_active == 0`, so as long as this condition never holds, `NULL_SHAREHOLDER`'s share of the pool value is real and counted against `total_active_shares`, but is unclaimable by anyone: [6](#0-5) 

### Impact Explanation
This causes a permanent, non-recoverable loss of stake value belonging to the delegation pool — specifically, the `add_stake` fee that is supposed to be refunded as rewards to delegators and factored into operator commission never gets released, and instead accumulates forever under an unspendable `0x0` share balance. Any unprivileged delegator (not the operator or pool owner) can trigger and sustain this condition merely by calling the permissionless `add_stake` entry function repeatedly. This matches the "Permanent lock or non-recoverable loss of claim rights in stake/delegation flows" impact category.

### Likelihood Explanation
Likelihood is high in terms of technical feasibility: `add_stake` is a fully permissionless entry function requiring no special role, and the attacker only needs to submit one low-value `add_stake` transaction per epoch to sustain the trap indefinitely. The cost to the attacker is limited to the fee fraction on their own trivial deposit each epoch (a small, self-funded cost), while the effect denies redistribution of accumulated fee value to the entire pool's delegators and operator. However, exploiting this to meaningfully "grief" other participants' commission/reward accounting at scale requires sustained, repeated on-chain action across many epochs, which is operationally simple but not a one-shot attack.

### Recommendation
Decouple the release of `NULL_SHAREHOLDER` fee shares from the `pending_active == 0` condition being observed at synchronization time. For example, track the actual epoch/OLC boundary at which each fee batch was accrued (rather than relying on the live `pending_active` value, which any user can keep non-zero), and release shares belonging to fees accrued in strictly earlier epochs regardless of whether new `add_stake` calls have occurred in the current epoch.

### Proof of Concept
Not independently executed in this review (no sandbox access). Based on the code, the sequence would be:
1. Delegator calls `add_stake(delegator, pool_address, amount)` once right after an epoch boundary while the validator is producing rewards, generating a non-zero `add_stake_fee` credited to `NULL_SHAREHOLDER` (`delegation_pool.move:1495,1511`).
2. Before the next epoch reconfiguration completes and the stake pool's own `pending_active` naturally clears, the delegator (or anyone) repeats step 1 with a minimal `amount`, keeping `pending_active > 0` on the underlying `stake` pool.
3. Every call to `synchronize_delegation_pool` observes `pending_active != 0` and therefore skips the `redeem_active_shares(pool, NULL_SHAREHOLDER, MAX_U64)` cleanup (`delegation_pool.move:1930-1937`), so previously accrued `NULL_SHAREHOLDER` fee shares are never released to the pool as rewards.
4. Repeating steps 1–2 every epoch indefinitely causes `NULL_SHAREHOLDER`'s accumulated active-share balance to grow without bound, permanently representing real stake-pool value that can never be unlocked (blocked by the assertion at `delegation_pool.move:1545`) or evicted (`delegation_pool.move:4778-4802`).

Note: I was unable to fully confirm, from the indexed portion of `stake.move`, the exact mechanics of how/when `pending_active` transitions to `active` at epoch boundaries (the relevant function was not found in this search pass), so the precise timing window an attacker must hit each epoch to sustain the trap is based on standard Aptos stake-pool semantics rather than a directly cited line. A Devin session with full repository access would be needed to pin down that exact epoch-transition code path and validate the PoC end-to-end with a Move unit test.
