### Title
Unstaking any dust amount resets `unstaked_available_epoch_height` for the entire unstaked balance, re-locking already-matured funds - ([File: staking-pool/src/internal.rs])

### Summary
`StakingContract::inner_unstake` unconditionally overwrites `account.unstaked_available_epoch_height` with `env::epoch_height() + NUM_EPOCHS_TO_UNLOCK` every time any amount is unstaked, even a single yocto. Because `account.unstaked` is a single pooled balance (not tracked per-unstake-event), a fresh dust unstake resets the withdrawal timer for the entire accumulated unstaked balance, including a portion that had already matured and was withdrawable.

### Finding Description
The invariant being tested is: `withdrawable(unstaked_old) == withdrawable(unstaked_old)` before and after a later `unstake(dust)` call, i.e. an already-matured unstaked balance should stay withdrawable regardless of subsequent unstakes.

In `inner_unstake`: [1](#0-0) 
the code does `account.unstaked += receive_amount;` followed by `account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;` — this timestamp field applies to the whole `account.unstaked` balance, not just the newly added `receive_amount`. The `Account` struct only has a single scalar `unstaked_available_epoch_height`, so there is no way to distinguish "old, matured" unstaked tokens from "new, just-unstaked" tokens: [2](#0-1) 

`internal_withdraw` and the `can_withdraw` view both gate on this single field against the entire `account.unstaked` balance: [3](#0-2) [4](#0-3) 

Exploit flow (works identically whether or not `reward_fee_fraction` is zero — zero fee just removes noise from reward-share accounting during the trace):
1. Delegator stakes, then calls `unstake(large_amount)`. `unstaked_available_epoch_height` is set to `epoch + 4`.
2. Delegator waits ≥4 epochs; the balance matures (`can_withdraw == true`), but the delegator does not withdraw yet.
3. Delegator (or anyone able to trigger unstake on that account — here, the account owner themselves, since `unstake` is only callable by `predecessor_account_id`) calls `unstake(1)` (a 1-yocto dust unstake), reachable via `unstake` → `inner_unstake`: [5](#0-4) 
4. `inner_unstake` adds the 1 yocto to `account.unstaked` (now containing the old matured balance + 1 yocto) and resets `unstaked_available_epoch_height` to `epoch + 4` again, re-locking the entire balance for 4 more epochs.

No existing guard prevents this: `internal_ping`'s balance assertion, `assert_owner`, `assert_one_yocto`, and the U256 rounding pair are unrelated to this field; there is no check in `inner_unstake` for "is there already a matured unstaked balance that should be preserved."

### Impact Explanation
The delegator's already-matured, withdrawable NEP-defined `unstaked` balance becomes non-withdrawable for a further `NUM_EPOCHS_TO_UNLOCK` (4) epochs purely as a side effect of an unrelated, minimal unstake action. No funds leave the contract and no accounting value diverges from reality (the balance and share counts remain correct), but the funds are frozen and recoverable — this matches the High severity category "funds frozen for at least one epoch but recoverable." The freeze is repeatable indefinitely by any delegator, against themselves or (more importantly) it is a general contract defect affecting every delegator on every staking pool deployed from this code, since it triggers on ordinary usage patterns and not solely deliberate self-harm.

### Likelihood Explanation
The only precondition is having a matured unstaked balance and calling `unstake`/`unstake_all` again with any (even 1 yocto) amount before withdrawing — a very low-cost, single-transaction action requiring no special privilege, deposit, or setup beyond normal delegation. It is trivially and repeatably reproducible by any account against its own balance, and also occurs unintentionally to ordinary users who unstake incrementally across multiple epochs.

### Recommendation
Track the unstaked balance and its unlock epoch such that newly unstaked amounts do not retroactively re-lock already-matured funds — e.g., only extend `unstaked_available_epoch_height` for the portion of `unstaked` that is not yet available for withdrawal, or maintain per-unstake-event unlock records instead of a single scalar overwritten on every call.

### Proof of Concept
```rust
#[test]
fn test_unstake_dust_relocks_matured_balance() {
    let mut emulator = Emulator::new(
        owner(),
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".to_string(),
        zero_fee(),
    );
    let deposit_amount = ntoy(1_000_000);
    emulator.update_context(bob(), deposit_amount);
    emulator.contract.deposit();
    emulator.amount += deposit_amount;
    emulator.update_context(bob(), 0);
    emulator.contract.stake(deposit_amount.into());
    emulator.simulate_stake_call();

    // Unstake most of the balance, then let it mature (4+ epochs).
    emulator.contract.unstake((deposit_amount - 1).into());
    emulator.simulate_stake_call();
    emulator.skip_epochs(4);
    emulator.update_context(bob(), 0);
    emulator.contract.ping();

    assert!(emulator.contract.get_account(bob()).can_withdraw,
        "matured balance should be withdrawable");

    // Attacker (bob) unstakes a dust 1-yocto amount.
    emulator.contract.unstake(1.into());
    emulator.simulate_stake_call();

    // BROKEN INVARIANT: the previously matured balance is now locked again.
    assert!(!emulator.contract.get_account(bob()).can_withdraw,
        "already-matured balance got re-locked by a dust unstake");
}
```

    /// Unstakes the given amount from the inner account of the predecessor.
    /// The inner account should have enough staked balance.
    /// The new total unstaked balance will be available for withdrawal in four epochs.
    pub fn unstake(&mut self, amount: U128) {
        // Unstake action always restakes
        self.internal_ping();

        let amount: Balance = amount.into();
        self.inner_unstake(amount);

        self.internal_restake();
    }
