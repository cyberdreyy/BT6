### Title
Loss haircut escapes via multi-epoch receipts: underfunded `collectWithdrawFunds` only haircuts the latest request epoch, earlier-epoch receipts pay out at par - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The GHSL-2023-082 tar-slip bug class — an attacker-supplied "entry" landing outside its intended containment directory — maps onto `IdleCreditVault`'s per-epoch receipt accounting: a withdraw receipt's basis is recorded per request epoch (`withdrawsRequestsByEpoch[user][epoch]`), but when `stopEpochWithDuration`/`collectWithdrawFunds` underfunds the aggregate `pendingWithdraws`, the resulting `lossRecoveryPriceByEpoch` haircut is keyed to a single epoch and `_claimLossAdjustedWithdrawRequest` clears only that epoch's slice. Receipt basis recorded in any earlier epoch slot escapes the haircut entirely and is paid at par through `_claimFundedWithdrawRequest`, even though the collected funds were only sized to cover the haircut total.

### Finding Description
1. `requestWithdraw` records basis per user per *current* `epochNumber` (`withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`) and updates `lastWithdrawRequest[_user] = currentEpoch`, while `pendingWithdraws` aggregates all epochs' basis into one bucket (lines 282–293). The only guard prevents a *new* request when `lastWithdrawRequest` already points to an epoch with a stored haircut (lines 263–271) — it does nothing for receipts spread across epochs before any loss exists.

2. In `collectWithdrawFunds`, when the borrower-funded `_amount < pendingBasis`, a single `lossRecoveryPrice = _amount * 1e18 / pendingBasis` is computed over the **aggregate** basis and stored only at `lossRecoveryPriceByEpoch[epochNumber]` (lines 411–421). `pendingWithdraws` is then zeroed. The collected `_amount` therefore equals `haircut × (sum of all epochs' basis)`.

3. On claim, `_claimLossAdjustedWithdrawRequest` uses `lossEpoch = lastWithdrawRequest[_user]` (the *latest* request epoch) and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)`, which zeroes only `withdrawsRequestsByEpoch[_user][lossEpoch]` and subtracts only that slice from `withdrawsRequests[_user]` (lines 789–801, 811–820). The user receives `claimBasis(lossEpoch) * lossRecoveryPrice / 1e18`.

4. The same call then continues into `_claimFundedWithdrawRequest`, which pays the remaining `withdrawsRequests[_user]` — i.e., every earlier-epoch receipt — **at par** (lines 319–349). The epoch-gating check at line 326 passes because `epochNumber` has advanced, and `_transferFundedClaim` only guards the default-recovery reserve, not the haircut accounting (lines 897–907).

Net payout for such a user: `basis_latest × p + Σ basis_older` — strictly greater than the pro-rata share `p × totalBasis` the collected `_amount` was sized for. Users whose entire basis sits in `lastWithdrawRequest` (single-epoch requesters) receive only `p × basis`, and the strategy is drained before all claims are paid: the last claimants' `safeTransfer` reverts on insufficient balance, or (worse) the under-reserve check at line 904 makes *every* subsequent funded claim revert, permanently freezing the default-recovery reserve for all defaulted-epoch claimants.

### Impact Explanation
Direct theft + insolvency: each earlier-epoch receipt escapes its proportional share of the realized loss and is paid at par from funds that were only collected to cover `haircut × totalPending`. The overpayment equals `(1 − p) × basis_older` per affected receipt and is borne by other pending claimants whose transfers revert for lack of balance, or by recovery claimants if the funded bucket cannibalizes the boundary before the reserve guard triggers. Loss is quantifiable: `attacker_gain = basisOlderEpochs × (RECOVERY_FULL − lossRecoveryPrice) / RECOVERY_FULL`.

### Likelihood Explanation
The attacker is an ordinary KYC-passing lender (in-scope): they merely need withdraw requests spanning ≥2 epochs, which is a normal usage pattern — request, wait one epoch without claiming (the code explicitly notes unclaimed requests roll into later ones, lines 320–325), then request again. No privileged role, no timing race. It triggers whenever `stopEpochWithDuration` realizes a loss with mixed-age pending receipts — a plausible stressed-epoch scenario, not an edge case requiring collusion. Existing guards do not stop it: the `lastWithdrawRequest`/haircut guard at lines 263–271 only checks whether `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is already set, which is impossible at request time because the price is written later during `collectWithdrawFunds`.

### Recommendation
Apply the haircut to the user's *entire* pending basis, not just the `lossEpoch` slice. Concretely: in `_claimLossAdjustedWithdrawRequest`, compute `claimBasis = withdrawsRequests[_user] + apr0 principal + apr0 interest` across all epochs (or iterate/clear every epoch key), zero `withdrawsRequests[_user]` fully, and burn the full receipt balance. Alternatively, at `collectWithdrawFunds` time, migrate/merge all per-epoch receipt bases into `epochNumber`, or record a per-user total-haircut flag so `_claimFundedWithdrawRequest` cannot pay earlier-epoch basis at par after a loss-adjusted `stopEpoch`.

### Proof of Concept
Foundry fork PoC sketch against `IdleCreditVault` + `IdleCDOEpochVariant`:

```solidity
// Setup: running epoch E. Attacker (KYC'd LP) holds AA tranche tokens.
uint256 basisA = 500_000e6;
// Epoch E: attacker requests withdraw #1 -> withdrawsRequestsByEpoch[attacker][E] = basisA
cdoEpoch.requestWithdraw(basisA, AA);
// honest stopEpoch (full funding) -> epochNumber becomes E+1; attacker does NOT claim
vm.warp(epochEnd + 1); cdoEpoch.stopEpoch(apr, 0);
// Epoch E+1: attacker requests withdraw #2 -> basis at [E+1], lastWithdrawRequest = E+1
cdoEpoch.requestWithdraw(basisB, AA); // basisB = 500_000e6, pendingWithdraws now = basisA + basisB

// Honest LP also has pendingWithdraws contribution basisC recorded at epoch E+1.

// Epoch E+1 ends with realized loss L so that lossRecoveryPrice p < 1:
// owner calls stopEpochWithDuration(apr, duration, _lossAmount)
// -> collectWithdrawFunds(p * totalPending) stores lossRecoveryPriceByEpoch[E+1] = p
// Collected = p * (basisA + basisB + basisC)

// Attacker claims:
cdoEpoch.claimWithdrawRequest(AA);
// _claimLossAdjustedWithdrawRequest pays basisB * p  (only epoch E+1 slice haircut)
// _claimFundedWithdrawRequest pays basisA * 1      (epoch E slice at par!)
// attacker receives basisA + p*basisB > p*(basisA+basisB)

// Honest LP claims afterwards: haircut on their basisC only, but strategy balance
// is now short by basisA*(1-p) -> transfer reverts or reserve guard reverts.
assertLt(underlying.balanceOf(address(strategy)), remainingClaims);
```

Expected result: attacker's payout exceeds their pro-rata share by `basisA * (1 - p)`; the final claimant's `claimWithdrawRequest` reverts (insolvency), confirming both theft and freezing of remaining claims. Reproducible on a mainnet fork fixture mirroring `test/foundry/IdleCreditVault.t.sol` with two sequential epoch requests and one `stopEpochWithDuration` loss epoch.
