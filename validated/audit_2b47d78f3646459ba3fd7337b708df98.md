### Title
Claimed instant-withdraw receipts are never freed from `instantWithdrawClaimsByEpoch`, inflating default recovery price and permanently freezing other claimants' recovery - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug class is "drop path forgets to free an allocated resource": a resource is consumed but its accounting entry is never released, corrupting later accounting. The exact analog lives in `claimInstantWithdrawRequest`. When a user claims a funded instant-withdraw receipt, the function burns the receipt tokens and zeroes `instantWithdrawsRequests[_user]` (IdleCreditVault.sol:387-392), but it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` and never decrements `instantWithdrawClaimsByEpoch[epoch]` — the only places those are decremented are inside `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:847-853), which runs only after a default. Already-claimed receipts therefore remain permanently "live" in the epoch's aggregate claim basis.

### Finding Description
`requestInstantWithdraw` records each receipt twice: per-user aggregate `instantWithdrawsRequests[_user]` and per-epoch aggregates `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]` (IdleCreditVault.sol:367-374). On the normal claim path, only the per-user aggregate is cleared; the per-epoch entries leak:

```
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);   // per-epoch entries untouched
```

These leaked entries feed default recovery accounting in two ways:

1. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (IdleCreditVault.sol:646-648). This basis includes receipts that were already paid out in full.
2. `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` as "already-held underlying reserved for those claims" (IdleCreditVault.sol:716-723). Already-claimed receipts inflate `instantBasis` without any corresponding held tokens, so `reserveAmount` — and therefore `defaultRecoveryPrice = reserveAmount * 1e18 / totalBasis` in `finalizeDefaultRecovery` (IdleCreditVault.sol:685-692) — is set higher than the strategy actually holds.

Every subsequent recovery claim does `defaultRecoveryReserve -= _amount` then `safeTransfer` (IdleCreditVault.sol:912-917). Because `defaultRecoveryReserve` overstates the real token balance, early claimants are paid at an inflated price (stealing share from honest claimants), and once the real underlying balance is exhausted the remaining claims revert permanently, since `finalizeDefaultRecovery` can only run once (`defaultRecoveryFinalized` guard, IdleCreditVault.sol:666).

### Impact Explanation
Two fund-impacting outcomes, both permanent:

- **Theft of unclaimed yield/recovery**: claimants processed before the reserve is exhausted receive more than their pro-rata recovery share; the excess comes directly out of what later claimants were owed.
- **Permanent freezing of recovery**: later claims always revert on `safeTransfer` because the strategy holds less underlying than `defaultRecoveryPrice` implies. There is no recovery path — finalization is one-shot and `defaultRecoveryReserve` cannot be corrected.

Quantified example: current-epoch instant basis 100 (Alice 60 already claimed and paid, Bob 40 unfunded), normal pending 0, active basis 100, external recovery 80. `prefundedReserve = 100 - 40 = 60` is counted even though Alice's 60 was already spent. `reserveAmount = 80 + 60 = 140`, `totalBasis = 200`, `recoveryPrice = 0.7` instead of the correct `80/140 ≈ 0.571`. Bob claims `40*0.7 = 28` fine, but active-LP recovery is priced at `100*0.7 = 70` while only `80 - 28 - (reserve double-counted as held)` real tokens exist; the last claimants' transfers revert.

### Likelihood Explanation
Requires: (a) instant withdraws enabled on the vault, (b) at least one instant receipt claimed in the current epoch while another instant request remains unfunded (`pendingInstantWithdraws != 0`), and (c) borrower default + `finalizeDefaultRecovery` in the same epoch. The attacker is an ordinary instant-withdraw user whose early claim is a legitimate action; the inflation then harms every other recovery claimant. No privileged misbehavior needed — the leak is automatic on the normal claim path.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the cleanup done in `_claimDefaultedInstantWithdrawRequest`: clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (only for the still-current epoch; older epochs' entries should be cleared when their receipts are claimed or tracked separately). Alternatively, make `_defaultPrefundedInstantReserve` compute prefunded reserve from actual held balance rather than `instantBasis - pendingInstant`, so already-paid claims cannot be counted as reserve.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testClaimedInstantReceiptInflatesRecovery() external {
    // 1. Deposit via AA tranche, start epoch (instant withdraw variant enabled).
    _depositWithUser(alice, 60e6);
    _depositWithUser(bob,   40e6);
    _startEpoch();
    _stopEpoch();

    // 2. Alice and Bob request instant withdraws in the same strategy epoch.
    cdoEpoch.requestInstantWithdraw(60e6, alice);   // via CDO path
    cdoEpoch.requestInstantWithdraw(40e6, bob);

    // 3. Borrower funds only Alice's claim partially:
    //    collectInstantWithdrawFunds(60e6) leaves pendingInstantWithdraws = 40e6.
    // 4. Alice claims -> paid 60e6; instantWithdrawClaimsByEpoch[epoch] still 100e6.
    cdoEpoch.claimInstantWithdrawRequest(); // alice
    assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 100e6); // leaked

    // 5. Borrower defaults; recovery source supplies 80e6.
    _handleBorrowerDefault();
    strategy.finalizeDefaultRecovery(80e6, recoverySource);

    // 6. recoveryPrice is inflated by 60e6 phantom prefunded reserve.
    //    Bob's / active-LP claims either overpay early claimants or revert
    //    once the real balance is exhausted:
    vm.expectRevert(); // ERC20: transfer amount exceeds balance
    cdoEpoch.claimInstantWithdrawRequest(); // bob -> permanently frozen
}
```

Key assertion: after step 4, `instantWithdrawClaimsByEpoch` still includes Alice's fully-paid 60e6, which `_defaultPrefundedInstantReserve` then books as held reserve that does not exist.

Note: I verified the leak directly in the code paths above, but the exact CDO-side call sequence for `collectInstantWithdrawFunds` timing (whether it can interleave as described before default) was not fully traced end-to-end; the PoC assumes the standard epoch flow where instant funding is collected by the CDO between epochs.
