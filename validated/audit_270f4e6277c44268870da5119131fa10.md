### Title
Reorg-timing protection window computed from a locally-delayed `approved_time` instead of `proposed_time`, letting a signer improperly sanction a reorg of an established tenure - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` is the guard that decides whether a new miner is allowed to reorg a tenure that already produced a block. The rule is: a reorg is only allowed if the reorged tenure's first block was "poorly timed" — i.e. proposed too close to the next sortition for a competing miner to have RBF'd it. The elapsed time that decides this is computed from `local_block_info.approved_time` (the time *this signer* finished validating/pre-committing the block), not from the block's actual proposal time, even though the surrounding comment and log fields explicitly describe the intended quantity as time-since-proposal-was-received.

### Finding Description
In `check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs`, ~lines 246-278): [1](#0-0)

The comment says the quantity being measured is "time between when the proposal was received and the next sortition," but the code substitutes `local_block_info.approved_time` — a per-signer timestamp stamped at `mark_pre_committed` or `mark_locally_accepted` (whichever happens first) — for the proposal-received time. Elsewhere in the codebase (`docs/signer-flows.md` section 2, and the same function's own logging a few lines later: `"violating_tenure_proposed_time" => local_block_info.proposed_time`) confirms `BlockInfo` carries a distinct `proposed_time` field that is separate from, and can lag well behind, `approved_time` due to validation queueing, node load, network delay, or an intentionally slow-validating node.

Because `approved_time` reflects when *this particular signer* got around to validating/pre-committing the block rather than when the block was actually proposed, any delay in this signer's own validation pipeline compresses `proposal_to_sortition`, even if the tenure was, in objective/proposal-time terms, established long before the next sortition. This lets `Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing` fire when it should not, wrongly classifying a legitimately-established tenure as "poorly timed" and pushing it into `superseded_tenures`.

Once superseded, `record_superseded_tenure` / `SignerDb::mark_tenure_superseded` [2](#0-1)  permanently records that this signer's own prior signature over that tenure's block must "stop counting as a conflict" via `get_signed_conflicts`/`reorg_permit_stands` [3](#0-2) , so the signer will go on to sign the replacement (reorging) tenure-change block despite having already signed the original tenure's block — this is the same "protection window bypassed by a stale/incorrect elapsed-time calculation" bug class as the external report, just manifesting in the signer's reorg-permission timelock instead of a fee schedule.

Because `approved_time` is a purely local, per-signer value (not something the network agrees on), different signers can independently reach different verdicts for the exact same reorg based only on how fast their own node happened to validate the earlier block — breaking the intended global consistency of "is this reorg permitted," and letting at least one, possibly several, signers sign a non-canonical/conflicting replacement of an already-established tenure.

### Impact Explanation
This breaks the approved-parent-vs-canonical equality that `check_parent_tenure_choice` exists to protect: a signer can be tricked (via ordinary validation delay, no majority collusion needed) into treating an established tenure as "poorly timed" and thus (a) permitting its own earlier, valid signature to be disregarded as a conflict, and (b) signing a subsequent block that reorgs that tenure. This matches the Critical bucket: "a signer signing an invalid, non-canonical, or conflicting block." It is a single-signer, per-evaluation decision (no majority is required to trigger the misclassification on that signer), and it is directly reachable by a one-slot miner that wins the next sortition and proposes a tenure-change block reorging the prior tenure, combined with ordinary or induced validation latency on the victim signer(s).

### Likelihood Explanation
Likelihood is Medium: it requires the affected signer's `approved_time` for the earlier tenure's block to have lagged close to the next sortition's arrival, which can happen under normal network/node load, a slow validation queue, or could be deliberately induced by an attacker who delays broadcasting/validating that block on purpose (the codebase already exposes fault-injection stalls, e.g. `TEST_VALIDATE_STALL`, showing validation delay is a realistic, controllable condition). It does not require a majority of signers, another signer's key, or any node-side compromise — only ordinary conditions affecting one signer's local validation timing.

### Recommendation
Use the block's actual proposal-received timestamp (`local_block_info.proposed_time`, which the function already logs) rather than `approved_time` when computing `proposal_to_sortition` in `check_parent_tenure_choice`. This ties the reorg-timing decision to an objective, proposal-time reference instead of a per-signer validation-completion time that can be delayed independently of how "well-timed" the tenure actually was.

### Proof of Concept
1. Miner A wins a sortition and proposes tenure A's first block `B_A` at time `T0`.
2. Signer `S`'s validation/pre-commit of `B_A` is delayed (ordinary node load, or deliberately induced, e.g. via the existing `TEST_VALIDATE_STALL`-style stall mechanism) so that `S`'s `approved_time` for `B_A` lands close to `T1`, the time `S` receives the next sortition's burn block — even though `B_A` was proposed at `T0`, well outside the `first_proposal_burn_block_timing` window measured from true proposal time.
3. Miner M2 wins the next sortition and proposes a tenure-change block whose parent skips tenure A, attempting to reorg it.
4. Signer `S` evaluates M2's proposal via `check_proposal → check_parent_tenure_choice`. It computes `proposal_to_sortition = sortition_state_received_time.saturating_sub(local_block_info.approved_time)`, which is small because `approved_time` (not `proposed_time`) was used, so `Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing` is satisfied. `S` classifies tenure A as "poorly timed," permits the reorg, and records tenure A as superseded.
5. `S` then signs M2's tenure-change block, effectively signing a block that reorgs an already-established tenure it previously signed, while other signers whose `approved_time` for `B_A` was not delayed correctly refuse the same reorg — producing signer disagreement over which block is canonical and a signature over a conflicting/non-canonical block from `S`.

Note: I was not able to fully re-confirm the exact `BlockInfo` field definitions for `proposed_time` vs `approved_time` in the final tool iteration (ran out of budget before reading `signerdb.rs`'s `BlockInfo` struct in full); this is inferred from the log statement in the same function (`"violating_tenure_proposed_time" => local_block_info.proposed_time`) and the `docs/signer-flows.md` description of `approved_time` semantics, both of which are cited above.
