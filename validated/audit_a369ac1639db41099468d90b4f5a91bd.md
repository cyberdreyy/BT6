### Title
Permanent DoS of `staking_contract` commission/withdrawal flow via unregistered + opted-out recipient in `distribute_internal` - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`staking_contract::distribute_internal` pays out every shareholder in the pending `distribution_pool` in a single loop via `aptos_account::deposit_coins`, with no isolation between individual transfers. `aptos_account::deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient's account exists, is not yet registered for `AptosCoin`, and has opted out of unregistered direct transfers via the fully permissionless `set_allow_direct_coin_transfers(false)`. Because `distribute_internal` is invoked unconditionally at the start of `request_commission`, `update_commision`, and `switch_operator`, a single uncooperative/self-opted-out shareholder in the distribution pool (staker, operator, or a former operator still owed a distribution) can permanently block commission requests, operator switching, and withdrawal for every other participant of that staking contract.

### Finding Description
`distribute_internal` iterates over all shareholders currently in `staking_contract.distribution_pool` and pays them in one transaction: [1](#0-0) 

The payout call is `aptos_account::deposit_coins(recipient, coin::extract(&mut coins, amount_to_distribute))` with no try/catch equivalent (Move has no exception-catching mechanism for aborts triggered deep inside a call).

`deposit_coins` can abort under an unprivileged, self-inflicted precondition: [2](#0-1) 

Specifically, if `to` already has an `account::Account` resource (so `create_account` at line 114-115 is skipped) but is **not yet registered for `AptosCoin`**, and `can_receive_direct_coin_transfers(to)` returns `false` (i.e., the account owner previously called the permissionless `set_allow_direct_coin_transfers(false)`), then `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`. This mirrors the Solidity report's root cause: an external transfer call that can unconditionally revert, and the caller performs no defensive check (equivalent to the missing `code.length` check) before making the call.

Because `distribute_internal` is called as the very first step of these staking-contract entry functions:
- `request_commission` — [3](#0-2) 
- `update_commision` — [4](#0-3) 
- `switch_operator` (via `distribute_internal` at line 785, confirmed in the earlier retrieved context)

any abort inside `distribute_internal` aborts the entire enclosing transaction, blocking all of these operations for **every** party tied to that `staking_contract` (staker, current operator, and any prior operator still holding shares in the distribution pool from a prior `switch_operator` call), not just the opted-out account.

The distribution pool can contain more than one shareholder at a time — e.g., after a `switch_operator` call, the old operator retains an entry in `distribution_pool` until it becomes withdrawable and is paid, alongside the staker and/or new operator's queued distributions. Any one of these parties can independently disable receipt of unregistered coins on their own account.

### Impact Explanation
This satisfies the "Stake And Lockup Gate" criteria for permanent lock / non-recoverable loss of claim rights: once one shareholder's payout in the shared `distribution_pool` becomes un-payable, `distribute_internal` aborts before extracting/paying *any* recipient (all payouts happen in the same atomic loop, and the whole transaction reverts), so no participant — including the staker and legitimate operator — can call `distribute`, `request_commission`, `update_commision`, or `switch_operator` on that staking contract again. Because the underlying stake pool continues to accumulate rewards that flow only through this accounting path, this can strand principal, commission and reward withdrawal rights indefinitely for the staker and every operator associated with that contract, which is a High/Critical-tier DoS/loss-of-claim-rights impact on core stake accounting.

### Likelihood Explanation
Likelihood is high relative to the analogous Solidity finding: the precondition (`set_allow_direct_coin_transfers(false)` on an account that has an `Account` resource but no `AptosCoin` `CoinStore`) is entirely permissionless and requires no privileged capability, unlike Move's `coin::freeze_coin_store` (which requires a `FreezeCapability` and is therefore out of scope for unprivileged analysis). Any operator, prior operator, or staker who wants to grief the shared staking contract (or who accidentally toggles this setting before ever registering for APT) can trigger this. It requires only ordinary entry-function calls already exposed to unprivileged users (`aptos_account::set_allow_direct_coin_transfers`) plus the normal lifecycle of `switch_operator`/`unlock_stake` populating `distribution_pool` with a second shareholder.

### Recommendation
Do not process all distribution-pool recipients within a single atomic loop that fails all-or-nothing. Consider:
- Wrapping each individual payout attempt with a resilient pattern (e.g., check `coin::is_account_registered<AptosCoin>(recipient) || can_receive_direct_coin_transfers(recipient)` before calling `deposit_coins`, and if the check fails, skip/queue that recipient's funds in an escrow-style pending balance the recipient can claim later via a self-registering entry function) instead of calling `aptos_account::deposit_coins` unconditionally inside the shared loop.
- Alternatively, allow other unaffected shareholders' distributions to complete even if one recipient's deposit would fail, by isolating per-recipient state mutations and only reverting the state for the specific failing recipient.

### Proof of Concept
1. Staker creates a staking contract with `create_staking_contract`, operator A joins the validator set, rewards accrue.
2. Operator A calls `staking_contract::switch_operator(staker, operator_a, operator_b, ...)`. This calls `distribute_internal` (paying out any already-inactive stake) and `request_commission_internal`, which via `add_distribution` inserts operator A into `distribution_pool` for its unpaid commission (not yet withdrawable).
3. Before the pool's lockup expires and while operator A's shares are still in `distribution_pool`, operator A's designated payout address (itself or its `beneficiary_for_operator`) — an address that already has an `Account` resource but has never registered an `AptosCoin` `CoinStore` — calls `aptos_account::set_allow_direct_coin_transfers(false)`.
4. Once the stake pool's lockup expires and the pending distribution becomes withdrawable, the staker (or operator B) calls `distribute`, `request_commission`, or `update_commision`. `distribute_internal` iterates the pool, reaches operator A's entry, calls `aptos_account::deposit_coins(operator_a_or_beneficiary, ...)`, which aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. The abort propagates through the entire transaction: no shareholder is paid, and every subsequent call to `distribute`, `request_commission`, `update_commision`, or `switch_operator` on this staking contract fails identically, permanently freezing the staker's and operator B's funds tied to this contract.
