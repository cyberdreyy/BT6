### Title
Loss-adjusted `stopEpochWithDuration` haircut is only applied to the user's latest request epoch, letting earlier pending receipts claim at par and drain the vault - ([File: contracts/strategies/idle/IdleCreditVault.sol](https://github.com/EzraCole/idle-tranches--013/blob/main/contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` aggregates all pending withdraw receipts into `pendingWithdraws`, but the haircut recorded by `collectWithdrawFunds` in `lossRecoveryPriceByEpoch` is only ever applied to receipts recorded under `lastWithdrawRequest[_user]` — the user's *latest* request epoch. A user holding receipts from an earlier epoch claims that earlier portion at full par via `_claimFundedWithdrawRequest`, even though the borrower only funded the haircutted aggregate. The vault pays out more than it collected, directly stealing from other pending/funded claimants and causing insolvency.

### Finding Description
- `requestWithdraw` adds `_amount` to the global `pendingWithdraws` and records per-epoch basis in `withdrawsRequestsByEpoch[_user][currentEpoch]`, while `lastWithdrawRequest[_user]` is overwritten with the current epoch (lines 279-293). A user may hold receipts in multiple epochs simultaneously; the only blocking condition is when the *previous* request epoch already has a nonzero `lossRecoveryPriceByEpoch` (lines 261-271). There is no guard against stacking a new request on top of an older, still-unclaimed funded receipt — the code comments at lines 323-324 explicitly allow it.
- On `stopEpochWithDuration` with `_lossAmount > 0`, `IdleCDOEpochVariant._stopEpoch` calls `previewLossAdjustedWithdrawFunds` then `collectWithdrawFunds(_pendingWithdraws)` (IdleCDOEpochVariant.sol lines 393, 408-410). When `_amount < pendingBasis`, `collectWithdrawFunds` zeroes `pendingWithdraws` and stores a single pro-rata `lossRecoveryPriceByEpoch[epochNumber]` (lines 414-421) — i.e., the haircut is applied to the **entire aggregate** pending basis, including the user's older-epoch receipt.
- At claim time, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, ...)`, which clears **only** `withdrawsRequestsByEpoch[_user][lossEpoch]` and decrements `withdrawsRequests[_user]` by that epoch's amount (lines 794-799, 815-820).
- Execution then falls through to `_claimFundedWithdrawRequest`, which pays the remaining `withdrawsRequests[_user]` (the older-epoch receipt) **at par** from the strategy's funded balance (lines 338-349).
- Net result: the pool funded `aggregate * lossRecoveryPrice`, but the user receives `newEpochBasis * price + oldEpochBasis * 1.0`. The excess is paid out of underlyings belonging to other pending claimants and the default-recovery/funded reserve, breaking solvency of the receipt pool.

Broken invariant: loss waterfall / fair redemption — the haircut intended to socialize a realized loss across *all* pending receipts is only enforced on the last-epoch slice.

### Impact Explanation
Direct theft / insolvency. An attacker deliberately keeps an old withdraw receipt unclaimed, opens a new request, and after a loss-adjusted `stopEpochWithDuration` claims the old receipt at par. The overpayment equals `oldEpochBasis * (1 - lossRecoveryPrice)`. With e.g. a 50% loss price and a large old receipt, the attacker drains roughly half the old basis from funds reserved for other claimants, leaving the last claimants unable to withdraw (permanent freezing of their funded yield) once the strategy balance is depleted.

### Likelihood Explanation
- Attacker requirements: unprivileged KYC'd lender making two `requestWithdraw` calls in different buffer phases and then `claimWithdrawRequest` — all normal user flows.
- Triggering condition: `stopEpochWithDuration` with `_lossAmount > 0` while `pendingWithdraws` contains receipts spanning multiple request epochs. `_lossAmount` is set by the honest manager (e.g., partial borrower repayment / realized loss), not the attacker, but the attacker can cheaply keep a stale receipt open at all times so the condition is exploitable whenever a lossy stop occurs.
- Existing guards do not stop it: the `requestWithdraw` re-request guard only fires when the *previous* epoch already has a loss price; `claimWithdrawRequest` happily processes both paths in one call (lines 303-313).
- Requires `defaultRecoveryInitialized == true` for the loss path, which is lazily set on first `requestWithdraw`/`requestInstantWithdraw` (`_ensureDefaultRecoveryInitialized`), so it is active in practice.

### Recommendation
Apply the epoch loss price to **all** receipt slices included in the haircutted `pendingBasis`, not just the latest. Options:
- In `_claimLossAdjustedWithdrawRequest`, iterate over all epochs with nonzero `withdrawsRequestsByEpoch[_user]` (or track a per-user list of pending request epochs) and apply `lossRecoveryPriceByEpoch[lossEpoch]` to each, since `collectWithdrawFunds` haircutted the aggregate.
- Simpler and safer: in `requestWithdraw`, revert whenever `withdrawsRequests[_user] != 0` or an open APR0 bucket exists (extend `_hasWithdrawRequest` usage to the non-default path), forcing users to claim/settle one receipt before opening another — this matches the already-enforced post-default rule at lines 247-251.

### Proof of Concept
Foundry fork test (mainnet fork, existing `IdleCreditVault.t.sol` harness):

```solidity
function testLossHaircutBypassedAcrossEpochs() external {
    IdleCreditVault cv = IdleCreditVault(address(strategy));

    // --- Epoch 0: attacker deposits and requests withdraw, does NOT claim ---
    _depositWithUser(attacker, 100_000 * ONE_SCALE);
    idleCDO.depositAA(100_000 * ONE_SCALE); // victim liquidity
    _startEpochAndCheckPrices(0);
    // attacker requests in epoch N (buffer phase)
    vm.prank(attacker);
    uint256 receipt1 = cdoEpoch.requestWithdraw(attackerBal / 2, address(AAtranche));
    // epoch ends, request funded at par (no loss), attacker still does not claim
    _stopEpochAndCheckPrices(0, apr, _expectedFundsEndEpoch());

    // --- Epoch 1 buffer: attacker opens a second withdraw request ---
    _startEpochAndCheckPrices(1);
    vm.prank(attacker);
    uint256 receipt2 = cdoEpoch.requestWithdraw(attackerBal / 4, address(AAtranche));
    // pendingWithdraws now = receipt1 + receipt2 across two epochs

    // --- Epoch 1 ends with a realized loss on pending receipts ---
    // manager calls stopEpochWithDuration with _lossAmount s.t.
    // collectWithdrawFunds stores lossRecoveryPriceByEpoch[1] = e.g. 5e17
    // borrower only funds (receipt1 + receipt2) * 5e17

    // --- Attack: single claim pays receipt2 at 50% but receipt1 at 100% ---
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // Vulnerable: got == receipt2 * 5e17/1e18 + receipt1
    // Correct:    got == (receipt1 + receipt2) * 5e17/1e18
    assertEq(got, receipt2 * 5e17 / 1e18 + receipt1); // overpaid by receipt1/2
    // strategy underlying balance is now short for remaining claimants
}
```

Note: exact epoch-index bookkeeping (whether the price key lands on the request epoch vs. the just-stopped epoch) should be confirmed against where `epochNumber` is incremented relative to `collectWithdrawFunds` inside `_stopEpoch`; the theft path holds as long as `lastWithdrawRequest` resolves to the epoch carrying `lossRecoveryPriceByEpoch`, which is the case for the attacker's latest request epoch.
