## Analysis

The reachable analog to the `NativeVault` bug is in the **node-side signing coordinator's weight tally**, not in the on-chain `verify_signer_signatures` check (which independently re-derives weight from the actual signatures in the block header and is therefore safe [1](#0-0) ). The vulnerable equality is the aggregated-weight cache (`total_weight_approved` / `total_weight_rejected`) that `stacks-node`'s `SignerCoordinator` (get_block_status) relies on to decide whether a block proposal has been accepted or rejected before it ever reaches chain-level verification.

`StackerDBListener::poll` maintains `BlockStatus.total_weight_approved` and `total_weight_rejected` as independent, monotonically-increasing accumulators, one per slot id: [2](#0-1) 

The `Accepted` arm only guards against double-adding by checking `gathered_signatures.contains_key(&slot_id)`, while the `Rejected` arm gates on the separate `responded_signers` set: [3](#0-2) 

Because `responded_signers.insert(slot_id)` is also executed unconditionally in the `Accepted` branch (line 465), a signer who first sends a `Rejected` message (adding its weight to `total_weight_rejected`) and later sends an `Accepted` message for the same block (e.g. after re-evaluating, which the signer-side design explicitly permits — see `LocallyRejected --> LocallyAccepted : re-evaluated` in the flow docs) will have its weight added to `total_weight_approved` too, because the `Accepted` branch never checks `responded_signers`/`total_weight_rejected` before crediting weight. The stale rejection weight is never retracted. This is the same class of defect as the `NativeVault` report: a derived aggregate (`total_weight_rejected`) is not kept consistent with the mutable underlying state (the signer's current vote), exactly like `node.totalRestakedETH` not tracking `balanceOf` after a transfer.

This inconsistent cache is then consumed by `SignerCoordinator::get_block_status`, which checks the rejection condition **before** the acceptance condition: [4](#0-3) 

If enough signers rejected the proposal and only later flipped to accept (their stale rejection weight persisting alongside the fresh acceptance weight), the coordinator can conclude `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and abort with `NakamotoNodeError::SignersRejected`, discarding transactions via `temporarily_excluded_txids`/`permanently_excluded_txids`, even though the block may have legitimately accumulated ≥ `weight_threshold` of *current* valid signatures. This does not let an invalid block get signed (the chain-level `verify_signer_signatures` check is unaffected), but it can cause the coordinator to treat a validly-signable block as rejected based on stale weight, i.e. "acting on a stale … threshold," a liveness/miner-stall issue.

I was not able to fully verify, within the remaining budget, whether the signer-side `stacks-signer/src/v0/signer.rs`/`signerdb.rs` bookkeeping (`add_block_signature`, `add_block_rejection_signer_addr`, `compute_signature_signing_weight`, `compute_reject_code_signing_weight`) has an equivalent flip-without-retraction defect, since those tallies are recomputed fresh from the DB on each call rather than cached incrementally (unlike the node-side listener) — this looks like it avoids the bug, but I could not inspect the full bodies of `add_block_signature`/`add_block_rejection_signer_addr` in `signerdb.rs` to confirm whether a later opposite vote is stored alongside (not replacing) the earlier one.

### Title
Stale rejection weight is never retracted when a signer later accepts, letting the mining coordinator misjudge block consensus - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block as two independently-incrementing, never-decrementing counters keyed by slot id. A signer who rejects and later (upon re-evaluation) accepts the same proposal has its weight counted in both buckets simultaneously, because the `Accepted` handler's dedup check (`gathered_signatures.contains_key`) is blind to a prior entry in `responded_signers`/`total_weight_rejected`.

### Finding Description
`handle_block_response`-equivalent logic in `StackerDBListener::poll` at [2](#0-1)  adds a signer's weight to `total_weight_approved` solely based on whether that slot id already appears in `gathered_signatures`. The `Rejected` handler at [3](#0-2)  adds weight to `total_weight_rejected` based on a separate `responded_signers` set. Neither branch clears or checks the other bucket when a signer's vote changes, so `total_weight_approved + total_weight_rejected` can exceed the honest total once any signer switches its vote — breaking the intended equality between "aggregated tallied weight" and "current, verified per-signer vote," the same class of desync as `NativeVault`'s `node.totalRestakedETH` vs `balanceOf` mismatch after a transfer.

### Impact Explanation
`SignerCoordinator::get_block_status` in [4](#0-3)  evaluates the rejection condition before the acceptance condition, using this same stale/duplicated tally. A block that has genuinely reached the ≥70% acceptance weight threshold can instead be treated as rejected (or vice versa be reasoned about incorrectly) because of leftover weight from a signer's earlier, superseded vote, stalling block/tenure production — a liveness impact consistent with "acting on a stale … threshold."

### Likelihood Explanation
Any signer that re-evaluates a proposal it previously rejected (a flow explicitly supported by the signer state machine, e.g. `should_reevaluate_block`/`LocallyRejected --> LocallyAccepted`) can trigger this by nature of normal operation; no majority collusion, secret keys, or privileged access are required — a single signer flipping its vote once suffices to desync the tally the coordinator relies on.

### Recommendation
Track a single, exclusive per-slot vote state (e.g. an enum `Accepted(weight)`/`Rejected(weight)`) rather than two independently-accumulating counters, and update `total_weight_approved`/`total_weight_rejected` by first removing any prior contribution for that slot id before adding the new one, mirroring the fresh-recompute-from-DB approach already used on the signer side in `store_and_process_block_signature`/`store_and_process_block_rejection`.

### Proof of Concept
1. Signer S (weight w) sends `BlockResponse::Rejected` for block B → `total_weight_rejected += w`, `responded_signers += {S}`.
2. S later re-evaluates and sends `BlockResponse::Accepted` for B (permitted by the signer's own state machine).
3. In `StackerDBListener::poll`, the `Accepted` arm checks only `gathered_signatures.contains_key(&S)`, which is `false`, so it adds `w` to `total_weight_approved` as well; `total_weight_rejected` is never decremented.
4. `total_weight_approved + total_weight_rejected` now exceeds the actual total signer weight expressible by unique current votes, and `SignerCoordinator::get_block_status`'s rejection/acceptance branching (which checks stale `total_weight_rejected` first) can produce a decision inconsistent with the signers' current, live votes.
