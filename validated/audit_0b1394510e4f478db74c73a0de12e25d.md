### Title
`getTokenLargestAccounts` silently reports balance `0` for malformed Token-2022 accounts instead of surfacing a decode error - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_token_largest_accounts` decodes each candidate account with `StateWithExtensions::<TokenAccount>::unpack(...).map(...).unwrap_or(0)`, silently substituting `0` whenever the full (extensions-aware) unpack fails. An attacker who creates a Token-2022 account with a valid base region (correct mint/state so it passes the `TokenAccountState` filter) but a corrupted extension TLV region can make `unpack()` return `Err` while the base `amount` field is nonzero, causing that account's true balance to be reported as `0` in the "largest accounts" heap instead of erroring or being excluded diagnosably.

### Finding Description
`get_token_largest_accounts` (`rpc/src/rpc.rs:2076-2130`) calls `get_filtered_spl_token_accounts_by_mint` (`rpc/src/rpc.rs:2359-2405`), which filters candidate accounts using `RpcFilterType::TokenAccountState` and a mint `Memcmp`. The `TokenAccountState` filter is implemented in `rpc/src/filter.rs:7-13` as:
```rust
RpcFilterType::TokenAccountState => Account::valid_account_data(account.data()),
```
`GenericTokenAccount::valid_account_data` only checks basic shape/state validity of the fixed-size base region; it does not perform full TLV extension parsing the way `StateWithExtensions::<TokenAccount>::unpack` does.

Once an account passes that shallow filter, `get_token_largest_accounts` does the real decode:
```rust
let amount = StateWithExtensions::<TokenAccount>::unpack(account.data())
    .map(|account| account.base.amount)
    .unwrap_or(0);
``` [1](#0-0) 

For Token-2022 mints, `StateWithExtensions::unpack` unpacks the base struct and then walks/validates the TLV-encoded extension bytes appended after the fixed base region. An attacker can write (via normal token-program instructions or any means resulting in owner-matching account data returned by the RPC's `getProgramAccounts`/index path) a token account whose base 165-byte region is well formed (correct mint, `AccountState::Initialized`, and an attacker-chosen large `amount`) but whose trailing extension bytes are malformed (e.g., a bogus/overflowing extension length or unknown extension discriminator) such that the extensions-aware `unpack()` returns `Err`. Because `valid_account_data` (used by the `TokenAccountState` filter in `filter.rs:7-13`) only validates the base region/account-type marker and not full extension integrity, the malformed account still passes the by-mint filter in `get_filtered_spl_token_accounts_by_mint` (`rpc/src/rpc.rs:2359-2405`) and reaches the loop in `get_token_largest_accounts`.

The `unwrap_or(0)` fallback then silently records `amount = 0` for that account/address rather than propagating an error or excluding/flagging the account, so the response's top-N heap can misreport a zero balance for an account that in reality holds a large, attacker-controlled balance encoded in its base bytes. ### Impact Explanation
This is a data-integrity/misreporting issue in a public read RPC (`getTokenLargestAccounts`): the value returned to RPC clients does not reflect the actual raw account bytes for an account that otherwise passes the mint/state filters, violating the parse-fidelity expectation that "parsed amount reflects raw account bytes, not a silent default." It falls under the accepted "wrong ... account data returned" / decoder-misreporting category from the rules, since a single unprivileged RPC call (`getTokenLargestAccounts`) returns an incorrect ranking/balance for an account the attacker controls. It does not cause a validator crash, does not affect consensus state, and only affects the accuracy of this one read-only reporting endpoint for accounts the attacker itself created.

### Likelihood Explanation
Feasible with a single client: an attacker only needs to get an owner-correct Token-2022 account with valid base fields but a corrupted extension TLV region into ledger state for a given mint (e.g., by directly submitting a transaction that writes such bytes, or via any path that results in such data being stored/returned by the index-backed `by-mint` scan), then issue one `getTokenLargestAccounts` call. No elevated privileges, validator control, or repeated/high-rate calls are required — this matches the single-call constraint in the rules.

### Recommendation
In `get_token_largest_accounts` (`rpc/src/rpc.rs:2101-2103`), do not collapse unpack failures to `0`. Either:
- Skip/exclude accounts that fail `StateWithExtensions::<TokenAccount>::unpack` from the "largest accounts" computation (consistent with how `get_token_account_balance` and `get_token_supply` already propagate an explicit error via `map_err` at `rpc/src/rpc.rs:2028-2029` and `2051-2053`), or
- Log/surface a diagnosable error state for malformed-but-owner-matching accounts instead of silently defaulting the amount to `0`.
Additionally, consider tightening `Account::valid_account_data` (or adding a stricter check in the `TokenAccountState` filter path) so it validates full extension TLV integrity before an account is treated as a legitimate token account by the by-mint index scan.
