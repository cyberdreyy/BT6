### Title
Miner can indefinitely refresh `last_activity_time` with cheap conflicting proposals to prevent the inactivity fallback from ever firing - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` treats *any* conflicting proposal — one that is only locally pre-committed, or a globally-accepted block still inside `reorg_attempts_activity_timeout` — as valid "miner activity" and refreshes `last_activity_time` via `signer_db.update_last_activity_time`. This value is the sole input (besides "have I signed a block in this tenure") to `SortitionState::is_timed_out`, which gates the miner-inactivity fallback that lets signers abandon a stalled tenure and adopt the next miner. A single miner can therefore keep the current tenure "alive" forever, at negligible cost, by repeatedly submitting new, trivially-varied, node-executable block proposals that conflict with its own prior (never-finalized) proposal, without ever collecting the 70% signatures needed to actually finish the tenure.

### Finding Description
`check_latest_block_in_tenure` (stacks-signer/src/chainstate/mod.rs:383-479) is invoked on every proposal, at validate-ok, and at signing time (`check_block_against_signer_db_state`, `check_proposal`). When a proposal conflicts with the tenure's current tip, two branches call `update_last_activity_time`:

1. If the existing tip is only locally accepted (`signed_group.is_none()`), or globally accepted but still inside `reorg_attempts_activity_timeout`, any conflicting proposal at ≤ height is explicitly counted as "valid miner activity" (lines 403-417): [1](#0-0) 
2. If the existing tip is only *pre-committed* (no signature at all — `BlockState::PreCommitted`) and the pre-commit is still "fresh" (`approved_time + tenure_last_block_proposal_timeout > now`), a conflicting proposal at the same height is likewise counted as activity, without ever rejecting or vetoing the new proposal: [2](#0-1) 

A pre-commit is a per-signer, unilateral decision made as soon as a signer's own node executes the block successfully — it requires no majority and no signature (see `handle_block_pre_commit`, which stores an individual pre-commit and only checks group threshold *before* actually signing): [3](#0-2) 

`SortitionState::is_timed_out` (the only gate that lets a signer conclude the current miner has gone inactive and fall back to a prior/next miner) is driven entirely by `last_activity_time` (falling back to burn-block-received time if unset), and returns `false` as long as that timestamp is "fresh": [4](#0-3) 

Because generating a new, distinct, node-executable block proposal (e.g. bump the timestamp) is essentially free for the sole miner of a tenure (an L2/appchain-cost analog of the PSM3 report's "cheap swap in/out"), the one-slot miner can perpetually manufacture "conflicts" against its own prior pre-commit or locally-accepted block, refreshing `last_activity_time` on every signer that has an unfinished pre-commit/local-accept, and thereby permanently suppress `is_timed_out`. This is exactly the bug class in the report: a single low-cost actor repeatedly toggling shared, timing-sensitive state (here, an activity/freshness timestamp instead of an asset balance) to defeat a protective mechanism intended to help a different party (here, the tenure-fallback/liveness path instead of a withdrawing depositor).

Notably, the project has already patched one variant of this exact issue — a pre-commit incorrectly counted as a *signed* block, permanently suppressing the timeout (`stacks-signer/changelog.d/precommit-suppresses-miner-timeout.fixed`) — confirming this is a recognized, real bug class in this exact mechanism, but the activity-refresh path analyzed here is a separate vector not covered by that fix: [5](#0-4) 

### Impact Explanation
This is a liveness wedge: a signer (or the whole signer set, since every signer runs the same check against its own local DB) can be kept from ever concluding the current miner is inactive, so the state machine never falls back to a valid alternative miner/tenure. A malicious or buggy single-slot miner that never intends to finish a tenure can indefinitely stall Stacks chain progress for that tenure using only proposal messages it is already entitled to send, matching the "signer wedged into never signing valid blocks" High-impact category.

### Likelihood Explanation
Requires only the current tenure's sole miner (a role already held by one entity per slot, no majority of signers needed) to keep sending cheap, distinct, executable-but-never-finalized block proposals before `tenure_last_block_proposal_timeout` / `reorg_attempts_activity_timeout` elapses. No signer collusion, no elevated keys, and no auth token are needed — it exploits normal proposal-handling logic that is explicitly designed to treat such conflicts as "activity."

### Recommendation
Bound how many times a single un-finalized (never globally/locally signed) tenure tip may refresh `last_activity_time` via this path, or require the "freshness" window used in `check_latest_block_in_tenure` for a pre-commit to be anchored to the *first* pre-commit's timestamp for the tenure rather than being renewable by each new competing proposal. Consider decoupling "still fits in principle" (should not vote to abandon) from "this specific competing proposal proves this miner is alive" so that manufacturing an unbounded stream of distinct, never-finished proposals cannot indefinitely refresh the activity clock.

### Proof of Concept
Conceptual sequence (cannot be executed without live signers/node, but follows directly from the cited code):
1. Miner M wins tenure T and proposes block B0 at height H. All signers validate B0 locally and `mark_pre_committed` (per-signer, no majority needed).
2. M never gathers 70% weight for B0 (e.g. intentionally slow-walks signature collection or signers are split).
3. Before `tenure_last_block_proposal_timeout` on B0's pre-commit expires, M proposes B1 (same height H, different timestamp) that conflicts with B0.
4. Each signer's `check_latest_block_in_tenure` sees B0 as a still-fresh pre-commit (`is_fresh_pre_commit == true`), does not veto B1, but calls `signer_db.update_last_activity_time(T, now)` per lines 442-446.
5. Signers `mark_pre_committed` on B1 (fresh `approved_time`). Repeat with B2, B3, … before each prior pre-commit goes stale.
6. `SortitionState::is_timed_out` never observes `elapsed > timeout` because `last_activity_time` is perpetually refreshed, so the fallback to a competing miner/tenure never triggers, stalling the chain for tenure T indefinitely.

impl SortitionState {
    /// Check if the sortition identified by the ConsensusHash is timed out based on
    /// the blocks within the signer db and the block proposal timeout
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        signer_db: &SignerDb,
        eval: &GlobalStateEvaluator,
        local_address: &StacksAddress,
        timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = signer_db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) =
            signer_db.get_burn_block_received_time_from_signers(eval, sortition, local_address)?
        else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = signer_db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };
        if elapsed > timeout {
            info!("Sortition has timed out";
                "sorition" => %sortition,
                "timeout" => %timeout.as_secs(),
                "elapsed" => %elapsed.as_secs()
            )
        }
        Ok(elapsed > timeout)
    }
