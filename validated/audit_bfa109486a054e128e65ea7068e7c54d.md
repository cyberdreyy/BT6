### Title
Cost-model's per-block accounts-data-growth estimate omits program-side account resizes, letting a transaction under-report allocation and evade `WouldExceedAccountDataBlockLimit` DOS protection - (File: `cost-model/src/cost_model.rs`)

### Summary
The CLOB report describes a DOS bypass where a capacity-limiting counter (`incrementLimitsPlaced`) is only incremented on the "create" code path (`postLimitOrder`) but not on an equivalent "amend" path that has the same resource-consuming effect, letting an attacker create unlimited effective new positions in one transaction while the counter stays low. The analogous pattern exists in Agave's cost model: `CostModel::calculate_allocated_accounts_data_size` (`cost-model/src/cost_model.rs` lines 242-301) only accounts for account-growing System Program instructions (`CreateAccount`, `CreateAccountWithSeed`, `Allocate`, `AllocateWithSeed`, `CreateAccountAllowPrefund`) when estimating how much account data a transaction will allocate. Any account growth performed by an arbitrary (non-system) program — e.g. a BPF program calling `AccountInfo::realloc`/`set_data_length`/`extend_from_slice`, or growth triggered implicitly by writing past the current account boundary (handled in `transaction-context/src/transaction.rs` `access_violation_handler`, lines 517-625) — contributes **zero** to the `allocated_accounts_data_size` field that feeds `CostTracker::would_fit` (`cost-model/src/cost_tracker.rs` lines 272-310) and its `WouldExceedAccountDataBlockLimit` check.

### Finding Description
`CostModel::calculate_transaction_cost` (`cost-model/src/cost_model.rs` lines 103-127) computes `allocated_accounts_data_size` purely from statically decoding top-level System Program instructions via `calculate_account_data_size_on_instruction`/`calculate_account_data_size_on_deserialized_system_instruction` (lines 203-261). Every other instruction — including instructions belonging to *any other program*, whether native/builtin or BPF, that can legitimately resize an account's data (via `BorrowedInstructionAccount::set_data_length`, `set_data_from_slice`, `extend_from_slice` in `transaction-context/src/instruction_accounts.rs` lines 177-226, or via a CPI-driven realloc as exercised in `program-runtime/src/cpi.rs` `update_caller_account`) — is classified `SystemProgramAccountAllocation::None` and adds nothing to the estimate.

This estimated `allocated_accounts_data_size` is the exact value that `CostTracker::would_fit` compares against `self.limits.allocated_data_size` (backed by `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` in `cost-model/src/block_cost_limits.rs`) to decide whether a transaction may be admitted into a block, i.e., it is the *only* gate protecting the leader from being made to process/store more account-data growth per block than the block's data-size budget allows. Just as the CLOB `amend()` path bypassed `incrementLimitsPlaced()` while still creating a new priced position (the actual resource-consuming action), a transaction that grows account data exclusively through non-system-program instructions bypasses the estimator that is supposed to gate `WouldExceedAccountDataBlockLimit`, while the growth itself is real and later recorded on-chain via `TransactionAccounts::update_accounts_resize_delta`/`resize_delta` (`transaction-context/src/transaction_accounts.rs` lines 297-326) and rolled into `Bank::update_accounts_data_size_delta_on_chain` (`runtime/src/bank.rs` lines 4419-4430).

Each *individual* transaction's total growth is still bounded per-transaction by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (enforced in `TransactionAccounts::can_data_be_resized`, `transaction-context/src/transaction_accounts.rs` lines 309-326), so this is not an unbounded-growth or consensus-safety bug — the on-chain, execution-time accounting is correct and consistent across validators. The defect is specifically that the **leader-side cost-tracker's block-admission decision** (`CostTracker::would_fit`, `WouldExceedAccountDataBlockLimit`) systematically undercounts account-data growth whenever it originates from non-system-program instructions, exactly mirroring the CLOB bug's core defect: a DOS/resource-limiting gate that is enforced on one code path (system-program account creation) but silently skipped on another code path that produces the same resource consumption (arbitrary-program account resize).

### Impact Explanation
An attacker can submit transactions that grow account data heavily through custom/BPF program instructions (each individually staying under `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`) rather than through `system_program::CreateAccount`/`Allocate`. Because `CostModel::calculate_allocated_accounts_data_size` reports these as `0` allocated bytes, the leader's `CostTracker::would_fit` will admit far more real account-data growth per block than `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` was designed to permit, degrading the leader-side resource-DOS protection this limit exists for (bounding per-block accounts-db growth/leader cost accounting). This is a leader-side cost/resource-accounting weakening reachable purely from a single unprivileged transaction sender, but it does not cause unsigned fund movement, consensus divergence, or a cluster halt by itself — it only defeats a scheduling/admission heuristic, not the consensus-critical, correctly-enforced per-transaction cap.

### Likelihood Explanation
High likelihood of being reachable: any unprivileged sender can construct ordinary transactions invoking a custom program (or even certain builtin programs) that call `set_data_length`/`extend_from_slice`/realloc-via-CPI to grow account data, with zero special privileges, and repeat this across many transactions in the mempool to consistently under-report allocation to the leader's cost tracker.

### Recommendation
Extend `CostModel::calculate_allocated_accounts_data_size` (and the underlying `calculate_account_data_size_on_instruction` dispatch in `cost-model/src/cost_model.rs`) so that account-data growth is estimated conservatively for *all* programs, not only the System Program's allocation instructions — e.g., by using each instruction's declared/worst-case realloc budget (bounded by `MAX_PERMITTED_DATA_INCREASE`/`MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`) for any writable account touched by non-system-program instructions, analogous to how the CLOB fix moved the `incrementLimitsPlaced()` call to cover every code path (`_processAmend`) that creates the same resource-consuming effect as `postLimitOrder`.

### Proof of Concept
Not independently reproducible from the indexed code alone; the reasoning is derived directly from reading `CostModel::calculate_account_data_size_on_instruction`/`calculate_account_data_size_on_deserialized_system_instruction` (`cost-model/src/cost_model.rs` lines 203-261), which returns `SystemProgramAccountAllocation::None` for every instruction whose `program_id != system_program::id()`, combined with `CostTracker::would_fit` (`cost-model/src/cost_tracker.rs` lines 272-293) which trusts this estimate for `WouldExceedAccountDataBlockLimit`, and the fact that real account growth via non-system-program instructions is still permitted and correctly tracked at execution time in `TransactionAccounts::can_data_be_resized`/`update_accounts_resize_delta` (`transaction-context/src/transaction_accounts.rs` lines 297-326). A full runtime PoC (building and running a BPF program invoking realloc without going through System Program instructions, then observing the leader admit it despite the cost estimate showing zero allocated data) would require executing code in the repo, which is outside the scope of this static analysis.
