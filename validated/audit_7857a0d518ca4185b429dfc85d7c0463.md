## Analog Found

### Title
Floor-rounded global-state agreement threshold falls below the canonical ceil-rounded 70% supermajority - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
The reported bug is about integer-division truncation silently lowering a computed value below its true mathematical result. The codebase contains a directly analogous flaw: two different implementations of the *same* 70% "supermajority" concept (`NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD = 7`) use different rounding conventions. `NakamotoBlockHeader::compute_voting_weight_threshold` rounds the threshold *up* (ceiling), but `GlobalStateEvaluator::reached_agreement`, which gates the signer's global state-machine consensus (active protocol version, agreed burn view, agreed current miner, agreed tx-replay-set), rounds the threshold *down* (floor). This means "global agreement" can be declared with strictly less supporting weight than the canonical supermajority the rest of the system enforces.

### Finding Description
The canonical, ceiling-rounded threshold used for actual block-signature approval is: [1](#0-0) 

```rust
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```

This is used everywhere a signer or the node decides whether enough weight has actually signed/pre-committed a block: `stacks-signer/src/v0/signer.rs::handle_block_pre_commit`, `store_and_process_block_signature`, `process_block_rejection`, and `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, all of which call `compute_voting_weight_threshold` and compare weight `>=`/`>` it.

In contrast, the global signer state-machine consensus (gossiped via StackerDB `StateMachineUpdate` messages, aggregated in `GlobalStateEvaluator`) uses a *floor*-rounded threshold: [2](#0-1) 

```rust
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```

`reached_agreement` is the sole gate for `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and `determine_global_state` (which fixes the agreed `current_miner`, `burn_block`/`burn_block_height`, and `tx_replay_set`): [3](#0-2) [4](#0-3) 

**Concrete example:** with `total_weight = 13` (a plausible reward-slot total), `compute_voting_weight_threshold(13)` = `ceil(9.1)` = `10`. But `reached_agreement` accepts `vote_weight >= floor(9.1) = 9`. So a coalition holding weight `9` (≈69.2%, i.e. *not* the true 70% supermajority) is judged by `GlobalStateEvaluator` to have reached "global agreement" on the current miner / burn view / protocol version / tx-replay-set, even though the same nominal 70% threshold, computed the way the rest of the system computes it, would require `10`.

Unlike `reached_agreement`, the companion function `reached_disagreement` happens to remain consistent with the node-side blocking-minority computation in `stacks-node/src/nakamoto_node/signer_coordinator.rs` (`total_weight.saturating_sub(weight_threshold)`), because `total - ceil(x) == floor(total - x)` for this particular pair — so only the agreement side, not the disagreement side, carries the precision-loss asymmetry.

### Impact Explanation
Because `determine_global_state` fixes the signer set's agreed view of `current_miner` (`MinerState::ActiveMiner{...}` vs `NoValidMiner`) and the agreed `tx_replay_set`, a set of signers whose combined weight is below the canonical 70% supermajority (but above the floor-rounded threshold) can force the rest of the signer set's local `GlobalStateEvaluator` to lock in a "globally agreed" miner/tenure or transaction-replay set that a true supermajority did not actually endorse. Any signer logic that trusts `determine_global_state()`'s output as equivalent to "70% of signers approved this" (the same guarantee `compute_voting_weight_threshold` is meant to provide for block signatures) is acting on a state derived from a weaker, silently-lowered bar — an instance of the "aggregated-weight vs verified-accepts" equality being broken by rounding-direction inconsistency. This maps to the High-impact category: a signer can be made to act on a stale/incorrectly-computed threshold for reward-set-weighted consensus.

### Likelihood Explanation
This is not merely a theoretical edge case: `NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD * total_weight % 10 == 0` is the exception rather than the rule for arbitrary `total_weight` values (reward-slot totals derived from PoX stacking, which are essentially arbitrary integers), so the floor/ceil discrepancy is present for the large majority of possible `total_weight` values, not just contrived ones. It requires only ordinary StackerDB gossip of `StateMachineUpdate` messages by signers already participating in the protocol — no majority-key compromise, no auth-token access, and no consensus-mechanics exploit beyond the pre-existing weighted-vote gossip path.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` use the same ceiling-rounded threshold formula as `NakamotoBlockHeader::compute_voting_weight_threshold` (or, better, factor out a single shared helper used by both `stackslib` and `libsigner`) so that "global agreement" and "block-signature approval" always require the identical, ceiling-rounded 70% supermajority weight.

### Proof of Concept
Using the existing test harness in `libsigner/src/tests/signer_state.rs`:
```rust
#[test]
fn reached_agreement_floor_vs_ceiling_threshold_mismatch() {
    // total_weight = 13: ceil(13*7/10) = 10, floor(13*7/10) = 9
    let evaluator = evaluator_with_total_weight(13);

    // The canonical block-approval threshold (compute_voting_weight_threshold) requires 10.
    assert_eq!(
        NakamotoBlockHeader::compute_voting_weight_threshold(13).unwrap(),
        10
    );

    // But GlobalStateEvaluator::reached_agreement accepts 9 — one weight unit
    // (≈7.7% of total_weight) below the canonical supermajority requirement.
    assert!(
        evaluator.reached_agreement(9),
        "reached_agreement wrongly reports consensus with only 9/13 (69.2%) weight"
    );
}

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
