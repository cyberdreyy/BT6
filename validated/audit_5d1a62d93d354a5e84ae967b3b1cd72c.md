### Title
v1 signer's own local tenure-start signature is invisible to its own duplicate-tenure-start check, letting a v1-pinned signer sign a second conflicting tenure-start block - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`v1::SortitionsView::validate_tenure_change_payload` guards against re-signing a tenure-start block by querying `signer_db.get_last_globally_accepted_block`, while `v2::GlobalStateView::validate_tenure_change_payload` uses `signer_db.get_last_signed_block` (locally-or-globally accepted). A v1-pinned signer that has already locally signed one tenure-start block in a tenure, but that block never reached global acceptance, will not see its own signature when a second, conflicting tenure-start block for the same tenure is proposed, and will happily sign it too. A v2 signer facing the identical local signer_db state correctly rejects the duplicate via `DuplicateBlockFound`.

### Finding Description
`SortitionData::check_tenure_change_confirms_parent`/duplicate checks are the last guard before a signer signs a tenure-start block for a given `consensus_hash` (tenure id). In v1: [1](#0-0) 

`get_last_globally_accepted_block` only returns a block once the *reward-set-wide* threshold has been reached; a block this very signer signed but the rest of the set rejected or never finished voting on is not visible here.

In v2, the equivalent check explicitly broadens the definition, and the code comment states the rationale ("locally or globally accepted... a block we have merely pre-committed to carries no signature from us"): [2](#0-1) 

Both checks operate on the same `signer_db` state and the same `block.header.consensus_hash` key, so they should produce identical verdicts for identical signer_db content - the equality the question posits. They do not: `get_last_globally_accepted_block` vs. `get_last_signed_block` are not equivalent, and the difference is entirely about whether the *signer's own* prior local signature is counted.

Exploit flow (single miner slot, gossip only):
1. Attacker wins a sortition slot (own BTC, unprivileged) and proposes tenure-start block A for tenure `T`.
2. Enough v1 and v2 signers locally accept/sign A (weight below the global-acceptance threshold, e.g. because some other signers reject A for an unrelated reason, or the vote round is abandoned) - so A is locally-signed by some signers but never becomes globally accepted.
3. Attacker crafts a second, distinct tenure-start block B for the same tenure `T` (different tx set/timestamp, same miner pubkey) and gossips it as a new `BlockProposal`.
4. A signer pinned to protocol v1 (`TEST_PIN_SUPPORTED_SIGNER_PROTOCOL_VERSION` or natural negotiation) that already signed A re-evaluates B: `get_last_globally_accepted_block(T)` returns `None` (A never got global acceptance), so the `DuplicateBlockFound` branch is skipped, and the signer proceeds to sign B.
5. A v2 signer with the identical local signer_db state calls `get_last_signed_block(T)`, finds A (locally accepted by itself), and correctly returns `DuplicateBlockFound`, rejecting B.

The v1 vs v2 signers in the same reward set now disagree on whether B is a duplicate for the same tenure id - breaking the "one canonical verdict per tenure" invariant the question describes.

### Impact Explanation
This breaks uniqueness/canonicity: multiple, mutually exclusive tenure-start blocks (A and B) for the same tenure can each accumulate signer signatures - A from the earlier round, B from v1 signers (plus any v2 signers/other participants who for other legitimate reasons also treat B as valid, e.g., those who never saw/signed A). If the combined weight that signed A and the weight that signs B each can reach the threshold in different rounds, the network node/consensus layer that consumes signer approvals could end up with two independently-signed blocks at the same (tenure, height) - a Critical chain-safety violation (conflicting canonical blocks). Even short of that extreme, it demonstrates a real fail-open path in v1's own re-signing guard: a v1 signer is not prevented from re-signing over a tenure-start after having already signed one for the same tenure, which the v1 code's own comment ("we've already signed a block in this tenure") documents as its explicit intent to prevent, but the implementation fails to do so when the earlier block missed global acceptance.

### Likelihood Explanation
Preconditions: (1) a mixed v1/v2 reward set, achievable naturally during a protocol-version rollout or forced via `TEST_PIN_SUPPORTED_SIGNER_PROTOCOL_VERSION` (test-only knob) or by an attacker simply timing the attack against real v1-pinned signers during migration windows; (2) a tenure where the first tenure-start block signed by the target v1 signer does not reach global acceptance (a routine occurrence any time the signer set is contentious, slow, or split) - the attacker doesn't need to control this, only observe it and then submit a second proposal. The attacker needs a single winning miner slot and the ability to gossip a `BlockProposal`, matching the unprivileged-miner threat model, and the attack is repeatable every time a first tenure-start block fails to globally finalize.

### Recommendation
Make `v1::validate_tenure_change_payload`'s duplicate check consistent with v2: use `signer_db.get_last_signed_block` (or equivalent locally-or-globally-accepted lookup) instead of `get_last_globally_accepted_block`, so a v1 signer's own prior local signature over a tenure-start block is always visible to its own duplicate check, matching v2 semantics.

### Proof of Concept
```rust
// stacks-signer/src/chainstate/tests/mod.rs (new test)
// Setup: identical SignerDb state for both harnesses:
//  - insert a NakamotoBlock `block_a` (tenure-start for consensus_hash T) into signer_db
//    with BlockState::LocallyAccepted (signed by this signer, NOT globally accepted).
//  - craft `block_b`: a distinct tenure-start NakamotoBlock for the same consensus_hash T
//    (same miner pubkey/sortition winner, different tx set), not yet in signer_db.

#[test]
fn v1_v2_duplicate_tenure_start_verdict_diverges() {
    let mut signer_db = /* build SignerDb with block_a inserted as LocallyAccepted only */;

    // v1 path
    let v1_result = v1::SortitionsView::validate_tenure_change_payload(
        /* proposed_by, tenure_change, &block_b, &mut signer_db, &client */
    );

    // v2 path, same signer_db state
    let v2_result = v2::GlobalStateView::validate_tenure_change_payload(
        /* tenure_change, &block_b, parent_tenure_id, &mut signer_db, &client, &config */
    );

    // Equality expected by design intent: both should reject as DuplicateBlockFound.
    assert!(matches!(v2_result, Err(RejectReason::DuplicateBlockFound)));
    // Bug: v1 does NOT detect the duplicate because it only checks global acceptance.
    assert!(v1_result.is_ok(), "v1 fails to flag duplicate tenure-start against its own locally-signed block");
}
```
This test demonstrates the asymmetry: identical `signer_db` state (one locally-accepted, non-globally-accepted tenure-start block) produces `Ok` (accept) under v1 and `Err(DuplicateBlockFound)` under v2 for a second tenure-start block in the same tenure, violating the UNIQUENESS-across-protocol-versions property the question requires.
