### Title
Mid-epoch APR update is not checkpointed: `depositDuringEpoch` charges upfront interest at the newly set APR instead of the APR that was locked in at `startEpoch` - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` fixes the borrower's epoch interest at `startEpoch` via `expectedEpochInterest` (computed from `lastApr` at that instant), but a mid-epoch `setApr`/`setAprs` call by the manager mutates `lastApr` immediately. Any subsequent `depositDuringEpoch` call computes the dilution-compensating upfront interest with the *current* `lastApr`, not the APR that governs the running epoch. An attacker can deposit mid-epoch right after an APR cut and pay less upfront interest than the rate at which the pool is actually accruing, diluting existing tranche holders.

### Finding Description
At epoch start, `startEpoch` snapshots the interest the borrower owes for the whole epoch into `expectedEpochInterest` using `_calcInterest(getContractValue())`, which reads `lastApr` (`IdleCDOEpochVariant.sol:260-262`). After that, the epoch's economics are frozen — but `lastApr` is not. `IdleCreditVault.setApr`/`setAprs`/`setAprsWithBuffer` (`IdleCreditVault.sol:206-235`) only check `msg.sender == idleCDO || msg.sender == manager`; there is no `isEpochRunning` guard (contrast `setEpochParams`, which reverts while an epoch runs at `IdleCDOEpochVariant.sol:122`).

When a lender deposits mid-epoch through `depositDuringEpoch`, the upfront interest meant to compensate existing LPs for the remaining time is computed from the live rate: `interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer)` (`IdleCDOEpochVariant.sol:691-697`). If the manager lowered the APR mid-epoch, the attacker is charged at the new lower rate even though the epoch keeps paying out `expectedEpochInterest` computed at the old higher rate. The symmetric case (APR raised) overcharges honest depositors, transferring value to existing LPs.

This is the same bug class as the Aloe report: a rate-parameter change is applied to a period whose accrual was fixed under the previous rate, with no checkpoint honoring the old rate for the elapsed time.

### Impact Explanation
Unfair interest accrual / dilution of existing AA and BB tranche holders. The attacker's tranche tokens are minted at a price that assumes they prepaid interest at the live (lower) APR, while the fixed `expectedEpochInterest` they share in was computed at the prior (higher) APR. The stolen amount is roughly `(aprOld - aprNew) * deposit * (remaining + buffer) / (epochDuration + buffer)`, scaled to the pool's active basis — on a large mid-epoch deposit with a material APR cut this is a direct transfer from incumbent LPs. In the APR-increase direction it is a permanent loss for the depositing user.

### Likelihood Explanation
Medium-low. Requires (a) `isDepositDuringEpochDisabled` to be false, `isAYSActive` false, and non-programmable mode — an opt-in configuration; (b) an honest manager to call `setApr`/`setAprs` mid-epoch (there is no epoch-running guard preventing it); (c) a KYC-passing wallet to call `depositDuringEpoch` in the same epoch. All actors except the depositor remain honest; the attacker merely sequences their deposit after the legitimate rate change, which an unprivileged KYC'd lender can always do.

### Recommendation
Either forbid APR changes while an epoch is running (add `!isEpochRunning` to `setApr`/`setAprs`, mirroring `setEpochParams`), or persist the epoch-start APR in the CDO (e.g. store `epochApr` alongside `expectedEpochInterest`) and have `depositDuringEpoch` compute the upfront charge from that locked rate rather than the mutable `lastApr`. The `ProgrammableBorrower.setBorrowerApr` pattern — `_accrueBorrowerInterest()` before updating `borrowerApr` — is the correct precedent already present in the codebase.

### Proof of Concept
Foundry fork PoC sketch (against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testMidEpochAprCutLetsDepositorUnderpay() external {
    // Setup: fixed-APR mode, deposits-during-epoch enabled, AYS off
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);          // existing LP
    _startEpochAndCheckPrices(0);       // expectedEpochInterest fixed at old APR

    uint256 oldApr = IdleCreditVault(address(strategy)).lastApr();

    // Honest manager cuts the APR mid-epoch (no guard prevents this)
    vm.warp(block.timestamp + epochDuration / 2);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(oldApr / 2, oldApr / 2);

    // Attacker (KYC'd wallet) deposits mid-epoch
    uint256 depositAmt = 50_000 * ONE_SCALE;
    deal(defaultUnderlying, attacker, depositAmt);
    vm.prank(attacker);
    uint256 minted = cdoEpoch.depositDuringEpoch(depositAmt, AAtranche);

    // Interest charged used aprNew for the remaining half epoch + buffer,
    // but the attacker shares expectedEpochInterest computed at aprOld.
    // Assert underpayment vs charging at aprOld:
    uint256 chargedOld = _calcInterestLike(depositAmt, oldApr);
    uint256 chargedNew = _calcInterestLike(depositAmt, oldApr / 2);
    assertLt(chargedNew, chargedOld);   // attacker paid less than epoch-implied rate
}
```

Uncertainty note: the exact assertion should compare `minted` against a reference mint computed with the epoch-start APR; the delta `chargedOld - chargedNew` quantifies LP dilution at `stopEpoch` when the fixed `expectedEpochInterest` is distributed across the enlarged supply.
