### Title
`claimInstantWithdrawRequest` pays out unfunded instant-withdraw receipts without verifying funds were collected — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns the user's entire `instantWithdrawsRequests` receipt balance and transfers the same amount of underlying from the strategy, but unlike the normal `claimWithdrawRequest` path it never checks that the corresponding epoch has been funded via `collectInstantWithdrawFunds`. The function assumes the receipt implies funded underlying, the same "unconstrained operand" bug class as the external report: a witness/state value is consumed as if a precondition (funding) held, with no constraint enforcing it.

### Finding Description
In `requestInstantWithdraw` (IdleCreditVault.sol:356-375) the strategy mints the user a receipt and records `instantWithdrawsRequests[_user] += _amount` and `pendingInstantWithdraws += _amount`. Funding is a separate step: `collectInstantWithdrawFunds` (lines 398-403) is called by the IdleCDO at a later point and pulls underlying in via `safeTransferFrom(idleCDO, ...)`.

The claim path (lines 380-393) reads:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Compare with `_claimFundedWithdrawRequest` (lines 319-350), which enforces `epochNumber <= lastWithdrawRequest[_user]` → `revert NotAllowed()`, i.e. a normal receipt cannot be claimed until after the epoch ended and `stopEpoch` has collected funds. No analogous gate exists for instant receipts: there is no check that `pendingInstantWithdraws` was actually collected, no per-epoch funding flag, and no reserve accounting guarding the payout. `_transferFundedClaim` (lines 897-907) only protects `defaultRecoveryReserve` — every other underlying balance held by the strategy (prefunded reserve for other users' instant claims, loss-adjusted funded withdrawals sitting in `pendingWithdraws`-backed balance, residual liquidity) is spendable by an unfunded instant claim.

The per-epoch tracking (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) exists solely to distinguish funded vs. defaulted receipts at finalization (lines 842-856); it is ignored on the normal claim path, confirming the "funded" precondition is assumed rather than constrained — exactly like `operand_to_check` being assumed a valid word by `FieldWordRangeChecker`.

### Impact Explanation
A KYC-passed lender with AA/BB tranche tokens calls `requestInstantWithdraw` (via the CDO) during the buffer/running epoch, then calls `claimInstantWithdrawRequest` through the CDO before the borrower repays and before `collectInstantWithdrawFunds` pulls underlying. The strategy pays the receipt 1:1 out of whatever underlying it holds — funds earmarked for other users' already-funded claims or prefunded reserves. The attacker receives real underlying for an unfunded receipt; later legitimate claimants' `_transferFundedClaim` calls revert on insufficient balance or pay out short. Loss is bounded by the strategy's liquid underlying balance and equals the attacker's instant-withdraw amount — direct theft / insolvency of funded claims.

### Likelihood Explanation
Attacker needs only a tranche position (any KYC'd lender) and two calls that can be made in the same epoch. The exploit succeeds whenever the strategy holds underlying not belonging to the attacker's request — which is the normal state whenever other users' claims have been collected or a prefunded reserve exists. The only mitigating factor is whether `IdleCDOEpochVariant` gates the user-facing claim on funding collection; the strategy-level entry point itself performs no such check and relies entirely on the caller, so any sequencing where the CDO exposes the claim before collection (or any future/other whitelisted CDO via `setWhitelistedCDO`) is exploitable.

### Recommendation
Constrain the claim to funded receipts, mirroring the normal path: track a funded instant basis per epoch (or a cumulative `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds`) and in `claimInstantWithdrawRequest` pay at most `min(instantWithdrawsRequests[_user], fundedShare)`, reverting or deferring the unfunded remainder. Alternatively require `epochNumber` to have advanced past the request epoch before paying, as `_claimFundedWithdrawRequest` does via `lastWithdrawRequest`.

### Proof of Concept
Foundry fork sketch (deposit during buffer, request instant withdraw, claim before borrower repayment):

```solidity
// Setup: fork mainnet, idleCDO = deployed IdleCDOEpochVariant, vault = its strategy.
// attacker = KYC'd lender holding tranche tokens.

// 1) Epoch running; strategy already holds underlying W collected for other users' claims
//    (or prefunded reserve). pendingInstantWithdraws == 0 for attacker epoch.

// 2) Attacker requests instant withdraw through the CDO
vm.prank(attacker);
cdo.withdrawInstant(amountTranche); // -> vault.requestInstantWithdraw(amount, attacker)
// vault minted receipt; pendingInstantWithdraws == amount; no underlying collected yet

// 3) Attacker claims in the same epoch, before collectInstantWithdrawFunds
vm.prank(attacker);
cdo.claimInstantWithdrawRequest(attacker); // -> vault.claimInstantWithdrawRequest(attacker)
// _burn(attacker, amount); underlying.safeTransfer(attacker, amount);
// underlying paid out of W (other users' funded claims) -> theft
assertEq(underlying.balanceOf(attacker), amount);
// later: legit user's claimInstantWithdrawRequest reverts / strategy insolvent
```

The test should assert that `pendingInstantWithdraws` was still nonzero and `collectInstantWithdrawFunds` had never been called when the attacker was paid, demonstrating that payout was not constrained to funded receipts.
