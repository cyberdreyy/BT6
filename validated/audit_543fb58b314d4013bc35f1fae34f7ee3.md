### Title
Unsafe integer conversion in gateway staleness check allows bypass of message freshness validation - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The `web_api_trigger` message-freshness check in the gateway's capabilities handler performs an unsigned-integer subtraction/comparison over an untrusted, client-supplied timestamp field, mirroring the class of bug in the ENS report: comparing values via raw arithmetic that is not safe against sign/wraparound, instead of validating the values with a range-safe comparison.

### Finding Description
`HandleLegacyUserMessage` in [1](#0-0)  decodes an untrusted `webapicap.TriggerRequestPayload` from the raw message body sent by an external, unprivileged HTTP/WS client to the internet-facing gateway, and then checks message freshness with: [2](#0-1) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    ...
    return callback.SendResponse(... "stale message" ...)
}
```

`payload.Timestamp` originates entirely from the client-controlled JSON body (`json.Unmarshal(body.Payload, &payload)`, [3](#0-2) ) and is only checked against zero beforehand ( [4](#0-3) ). The freshness check converts this attacker-supplied value to `uint` and compares it against a fixed constant (`uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`). This is analogous to `RRUtils.serialNumberGte`'s flaw: the code assumes normal integer range/ordering semantics for a value that can be crafted by an untrusted party to exploit signed/unsigned conversion or wraparound behavior at the type boundary, rather than validating the value is within a sane bound before using it in security-relevant arithmetic.

If the underlying `Timestamp` field is a signed type (as is typical for Unix-timestamp fields carried over JSON, e.g., `int64`), an attacker can supply a negative value. Converting a negative signed integer to `uint` in Go wraps around to a very large unsigned value near `2^64-1`, which is always greater than the fixed left-hand side of the comparison — causing the staleness check to always pass (i.e., never flag the message as stale) regardless of the message's actual age. This defeats the intended replay/staleness protection for the gateway's `web_api_trigger` message path, which subsequently gets forwarded to all DON members via `don.SendToNode` ( [5](#0-4) ).

Note: I was not able to verify the exact declared Go type of `webapicap.TriggerRequestPayload.Timestamp` (int64 vs uint64) within the indexed portion of the codebase before running out of search budget; the exploitability depends on that field being a signed integer type. If it is unsigned, JSON unmarshaling would reject negative literals and this specific vector would not apply, though the general anti-pattern of doing security-relevant arithmetic via raw type conversion without bounds validation remains present.

### Impact Explanation
If exploitable, this allows any unauthenticated external client hitting the gateway's public trigger endpoint to bypass the staleness/freshness safeguard on `web_api_trigger` messages, enabling old or fabricated requests to be treated as fresh and relayed to DON nodes — a "quota/validation bypass" reachable directly from an unprivileged client request into the gateway message envelope pipeline.

### Likelihood Explanation
Likelihood depends entirely on the concrete Go type of the `Timestamp` field, which could not be confirmed with available tooling. If signed, the bypass requires no special access — a single crafted JSON payload with a negative timestamp is sufficient, making likelihood high. If unsigned, the vector as described does not apply.

### Recommendation
Replace the raw-conversion arithmetic with an explicit, type-safe validation, mirroring the fix recommended in the referenced report (avoid ad hoc arithmetic that can wrap; validate ranges directly):
- Reject payloads where `payload.Timestamp < 0` (if signed) before any conversion.
- Compute the staleness check using same-signedness arithmetic, e.g. `time.Now().Unix() - int64(payload.Timestamp) > int64(h.config.MaxAllowedMessageAgeSec)`, guarding against negative differences (future timestamps) as well.
- Add an explicit upper bound check (reject timestamps far in the future) to fully close the freshness validation gap.

### Proof of Concept
Conceptual PoC (pending confirmation of the `Timestamp` field's Go type):
1. Send a `web_api_trigger` JSON-RPC message to the gateway's public endpoint with `payload.Timestamp = -1` (or any negative value).
2. `uint(payload.Timestamp)` wraps to `18446744073709551615` (max uint64), which is always `>= uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`.
3. The staleness check at [2](#0-1)  never trips, and the message is forwarded to DON nodes as if fresh, regardless of its true age or replay status.
