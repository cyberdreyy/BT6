### Title
Unanchored regex match in `overwriteRegexCheck` allows partial-match bypass of `KUBERNETES_NAMESPACE_OVERWRITE` restriction - (File: executors/kubernetes/overwrites.go)

### Summary
`overwriteRegexCheck` (executors/kubernetes/overwrites.go:620-630) validates the user-supplied `KUBERNETES_NAMESPACE_OVERWRITE` value using `regexp.MatchString`, which reports whether the pattern matches *anywhere* in the string rather than requiring a full-string match. If the admin-configured `NamespaceOverwriteAllowed` regex is not explicitly anchored with `^...$`, an unprivileged pipeline author can supply a namespace string that merely contains the allowed substring (e.g. `evil/ci-victim` against pattern `ci-.*`) and have it accepted by `createOverwrites`, causing the build pod to be scheduled into an arbitrary namespace.

### Finding Description
`createOverwrites` (overwrites.go:147-167) reads `KUBERNETES_NAMESPACE_OVERWRITE` from job variables (fully attacker-controlled, since it's a `.gitlab-ci.yml`/variable value) and passes it to `evaluateOverwrite`, which calls `overwriteRegexCheck(regex, overwriteValue)` at line 606. That function does:

```go
r, err := regexp.Compile(regex)
match := r.MatchString(value)
``` [1](#0-0) 

Go's `regexp.MatchString`/`Regexp.MatchString` performs an *unanchored* search — it returns true if the pattern matches any substring of the input, not the whole input, unless the pattern itself contains `^` and `$` (or `\A`/`\z`). Consequently, if a cluster admin configures `NamespaceOverwriteAllowed` as `ci-.*` (a common, intuitively "permissive but intended" pattern meant to allow only namespaces starting with `ci-`), the check does not enforce a prefix constraint — a value such as `evil/ci-victim` still satisfies the regex because `ci-victim` appears within it, and `regexp` engines run on the whole string looking for any matching substring.

`evaluateOverwrite` then returns `overwriteValue` unmodified as `o.namespace`, which is later used directly to schedule the build pod (via `kubernetes.go`), placing it into a namespace the admin did not intend to expose — potentially one belonging to another project/team, with its own ServiceAccount, imagePullSecrets, and mounted credentials.

The only enforced check is the regex itself; there's no additional canonicalization, path/namespace format validation, or anchor-injection logic. This is a "root cause" issue in the sense that the API silently accepts partial-match semantics that most admins writing simple prefix/suffix patterns will not expect, and no code path anchors user-supplied regex automatically.

### Impact Explanation
If exploited, a pipeline author in one project can direct their build pod into a Kubernetes namespace belonging to a different project (as long as that namespace name contains a substring matching the admin's configured pattern), gaining access to that namespace's default/named ServiceAccount token, mounted `imagePullSecrets`, and any other Kubernetes secrets accessible from within a pod in that namespace. This matches the scoped impact: cross-project registry credential / ServiceAccount token exfiltration.

### Likelihood Explanation
- Preconditions: the Kubernetes executor is used with `NamespaceOverwriteAllowed` configured as a non-anchored regex (e.g., `ci-.*`, `.*-runner`, or any pattern without `^`/`$`) — a plausible, commonly-seen misconfiguration since GitLab's own documentation examples for this setting have historically not stressed the anchoring requirement, and the regex is otherwise deliberately permissive by admin intent.
- Attacker needs no special privileges beyond being able to set CI/CD variables in their own project's `.gitlab-ci.yml` (a normal, unprivileged capability).
- The attack is deterministic and repeatable: the exploit is just supplying a crafted `KUBERNETES_NAMESPACE_OVERWRITE` value and observing the pod get scheduled in a foreign namespace.
- Feasibility depends entirely on the admin's regex choice, so this is a real logic gap in the validation function itself (unanchored matching), not merely a "bad admin configuration" issue — the same regex string behaves unexpectedly permissively because of Go's `regexp` semantics, which most administrators are unlikely to know without deep Go knowledge.

### Recommendation
Anchor the regex match to require the value to fully match the pattern, e.g., wrap in `^(?:%s)$` before compiling, or use `regexp.MustCompile` with the pattern surrounded by `\A(?:...)\z` before calling `MatchString`, so partial substring matches are rejected regardless of how the admin writes the pattern:

```go
func overwriteRegexCheck(regex, value string) error {
    r, err := regexp.Compile(`\A(?:` + regex + `)\z`)
    ...
}
```
Additionally, update documentation/config validation to warn administrators if their `*OverwriteAllowed` pattern lacks anchors, and add explicit unit tests asserting that partial matches (e.g., `evil/ci-victim` against `ci-.*`) are rejected.

func (o *overwrites) evaluateOverwrite(
	fieldName, value, regex, overwriteValue string,
	logger buildlogger.Logger,
) (string, error) {
	if regex == "" {
		logger.Debugln("Regex allowing overrides for", fieldName, "is empty, disabling override.")
		return value, nil
	}

	if overwriteValue == "" {
		return value, nil
	}

	if err := overwriteRegexCheck(regex, overwriteValue); err != nil {
		return value, err
	}

	logValue := overwriteValue
	if fieldName == "BearerToken" {
		logValue = "XXXXXXXX..."
	}

	logger.Println(fmt.Sprintf("%q overwritten with %q", fieldName, logValue))

	return overwriteValue, nil
}

func overwriteRegexCheck(regex, value string) error {
	var err error
	var r *regexp.Regexp
	if r, err = regexp.Compile(regex); err != nil {
		return err
	}
	if match := r.MatchString(value); !match {
		return &malformedOverwriteError{value: value, pattern: regex}
	}
	return nil
}
