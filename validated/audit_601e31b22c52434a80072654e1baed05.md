Based on my investigation, I found a concrete analog in the signer's block-record persistence layer where a miner-controlled field is trusted without being cross-checked against the block's actual sortition-derived reward cycle, and the on-disk record for that block is keyed in a way that lets a different (and possibly non-authoritative) reward-cycle context silently clobber another cycle's committed decision.

### Title
Miner-controlled `reward_cycle` field lets a concurrently active reward-cycle Signer instance overwrite another cycle's committed block decision, losing the equivocation guard - (File: stacks-signer/src/v0/signer.rs, stacks-signer/src/signerdb.rs)

### Summary
`stacks-signer` runs two `Signer` instances concurrently during the prepare-phase overlap window (current and next reward cycle), both sharing the *same* on-disk `SignerDb` file. Each `BlockProposal` carries a `reward_cycle` field that is entirely self-reported by the miner and is only used to route/gate the message to the matching `Signer` instance (`if block_proposal.reward_cycle != self.reward_cycle { return; }`). Because the current `blocks` table schema keys rows solely by `signer_signature_hash` (not `(reward_cycle, signer_signature_hash)` as in older schema versions), and `insert_block` performs an unconditional `INSERT OR REPLACE`, a proposal delivered to the "wrong" but concurrently live reward-cycle `Signer` instance can overwrite the authoritative block record (including `signed_self`/`state`) that the correct cycle's `Signer` previously committed.

### Finding Description
`handle_block_proposal` gates processing purely on the wrapper-level, miner-supplied `reward_cycle` field: [1](#0-0) 

It then looks up any prior decision via `block_lookup_by_reward_cycle`, which filters the DB record by `self.reward_cycle` (the instance's own, real cycle): [2](#0-1) 

`SignerDb::block_lookup` itself queries only by `signer_signature_hash`, with no reward-cycle constraint: [3](#0-2) 

`insert_block` writes the block keyed by `signer_signature_hash` alone (current schema drops `reward_cycle` from the primary key, see the migration that redefines the table with `signer_signature_hash TEXT NOT NULL PRIMARY KEY`), and unconditionally replaces any existing row, including its `reward_cycle` column, on every insert: [4](#0-3) [5](#0-4) 

Meanwhile, `runloop.rs` keeps two `Signer` instances alive simultaneously across the reward-cycle boundary (current + next), both configured with the *same* `db_path`, i.e. the same physical SQLite file: [6](#0-5) 

Because `signer_signature_hash` is computed purely from the immutable `NakamotoBlockHeader` fields and does not include the wrapper-level `reward_cycle`, a single real, valid block can be wrapped in two different `BlockProposal` messages that differ only in the self-declared `reward_cycle` (e.g., `N` and `N+1`). During the overlap window both the cycle-`N` and cycle-`N+1` `Signer` instances are live and will each pass their own `reward_cycle` equality check, each independently evaluate the *same* block (using node-side `SortitionsView`/consensus_hash checks that are agnostic to the wrapper's `reward_cycle` field), and each call `insert_block`. Whichever call lands last wins the row via `INSERT OR REPLACE`, silently discarding the other cycle's `signed_self`/`state`/`vote` fields and replacing `reward_cycle` with its own value.

### Impact Explanation
This breaks the persisted "already decided" guard that `handle_block_proposal` relies on (`prior_block_info` via `block_lookup_by_reward_cycle`) to avoid re-evaluating/re-signing a block. If cycle `N`'s committed `LocallyAccepted`/`signed_self` record is overwritten with a fresh, unsigned record stamped `reward_cycle = N+1`, a later resend or retry of the legitimate cycle-`N` proposal (or of pending responses) is treated by cycle `N`'s signer as brand new: the equivocation/duplicate-decision guard is lost, and the same underlying block can be independently re-evaluated and re-signed. It also corrupts every downstream query that assumes `reward_cycle` correctly partitions the `blocks` table (e.g., `has_unprocessed_blocks(reward_cycle)`, and per-tenure conflict/threshold bookkeeping), since a genuinely cycle-`N` block can now be misfiled under `N+1` or vice versa. This matches the High-impact category of "losing the equivocation guard," reachable by a one-slot miner without needing a majority of signers.

### Likelihood Explanation
This requires no special access beyond what a normal miner already has: crafting two `BlockProposal` wrapper messages around the same block with different self-declared `reward_cycle` values, and sending them while two `Signer` instances are concurrently active (a routine occurrence at every reward-cycle prepare-phase boundary per `runloop.rs`). No signer key, no majority, and no node-side bug is required — only the `reward_cycle` field of the miner-authenticated `BlockProposal` needs to be inconsistent with the block's real sortition-derived cycle.

### Recommendation
Restore `reward_cycle` as part of the effective identity used for block-record isolation (either back to a composite key including a verified/derived `reward_cycle`, or a separate DB/table per Signer instance), and independently derive/validate a block's reward cycle server-side from its `consensus_hash`/burn height rather than trusting the wrapper's self-reported `reward_cycle` field before using it for storage keys or overwrite decisions.

### Proof of Concept
1. Run two `stacks-signer` instances configured for adjacent reward cycles `N` and `N+1` sharing the same `db_path`, as `refresh_signer_config`/`initialize_runloop` do during the prepare-phase overlap (`stacks-signer/src/runloop.rs:313-386`).
2. As the current-tenure miner, build one valid `NakamotoBlock` for tenure/consensus_hash belonging to cycle `N`.
3. Send `BlockProposal { block, reward_cycle: N, .. }` to the signer set — the cycle-`N` `Signer` locally accepts and signs it, persisting `BlockInfo{reward_cycle: N, signed_self: Some(t), state: LocallyAccepted}` under `signer_signature_hash = H`.
4. Immediately send a second message `BlockProposal { block, reward_cycle: N+1, .. }` (same block, only the wrapper field differs) — the cycle-`N+1` `Signer` instance passes its own `reward_cycle` check, evaluates the same block, and calls `insert_block`, which `INSERT OR REPLACE`s row `H` with a fresh `BlockInfo{reward_cycle: N+1, signed_self: None, state: Unprocessed/whatever fresh state}` (`stacks-signer/src/signerdb.rs:1807-1852`).
5. Observe that `block_lookup_by_reward_cycle(H)` from the cycle-`N` `Signer` now returns `None` (since the stored `reward_cycle` is `N+1`), demonstrating the loss of its previously committed decision.

    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }
