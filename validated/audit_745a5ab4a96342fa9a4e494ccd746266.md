This codebase contains a real analog to the reported pattern. In `ProvisionerV2.sol`, deposit refunds for async deposit requests rely on `_transferWithFallback`, which has a fallback shortcut that silently degrades into a non-recoverable revert when the requester and receiver are the same address — the common case for ordinary self-deposits.

### Title
Blacklisted self-depositor can permanently lose escrowed deposit tokens in ProvisionerV2 - (File: v3/src/core/ProvisionerV2.sol)

### Summary
`ProvisionerV2.requestDeposit` escrows the deposit token in the contract and defaults `receiver = msg.sender` for ordinary users. Every recovery path for this escrow (`cancelRequest`, `refundRequest`, and the deadline-expired branch of `solveRequestsVault`) routes through `_clearHashAndTransferRefund` → `_transferWithFallback`, which, when `receiver == requester`, skips the safe "try" transfer and calls the reverting `safeTransfer` directly. If the depositor's address becomes blacklisted on the deposit token (e.g. USDC) after creating the request, every refund attempt reverts, permanently locking the escrowed tokens with no override path reachable by an ordinary user.

### Finding Description
`_transferWithFallback` at [1](#0-0)  is:
```solidity
function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
    if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
        token.safeTransfer(requester, amount);
    }
}
```
When `receiver == requester` (the default for a self-deposit via `requestDeposit(token, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge, isFixedPrice)`, which sets `receiver = msg.sender`), the function bypasses the non-reverting `trySafeTransfer` path entirely and calls the reverting `token.safeTransfer(requester, amount)`. If `requester` (== `receiver` == the original depositor) is blacklisted for the escrowed token, this call always reverts.

Every user-reachable path for reclaiming escrowed deposit tokens funnels through this same logic:
- `cancelRequest` (self-cancel before deadline): `_clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token)` [2](#0-1) 
- `refundRequest` (after deadline, callable by anyone): `_clearHashAndTransferRefund(token, request, request.user, request.tokens, token)` [3](#0-2) 
- `_solveDepositVaultAutoPrice` / `_solveDepositVaultFixedPrice` expired branch: `_transferWithFallback(token, request.user, request.receiver, request.tokens)` [4](#0-3) 

In all three, `requester == receiver == request.user` for a standard self-deposit, so the reverting-`safeTransfer` shortcut is always taken and always reverts, leaving `asyncRequestHashes[depositHash]` set and the tokens permanently trapped. The only alternative admin path, `refundDeposit`, is gated by `requiresAuth` [5](#0-4)  and is only for the sync-deposit flow, not reachable by an ordinary user to redirect the async-request refund elsewhere.

### Impact Explanation
An ordinary depositor's escrowed deposit tokens become permanently frozen with no ordinary-user-reachable recovery path once their address is blacklisted on the deposit token after submitting an async deposit request. This is a direct freezing-of-user-funds scenario.

### Likelihood Explanation
Requires the deposit token to support blacklisting (e.g. USDC) and the user's own address to become blacklisted after calling `requestDeposit` but before the request is solved or cancelled — a realistic real-world event (e.g. regulatory/compliance action against the address) independent of any protocol privileged action.

### Recommendation
Add an explicit "rescue" mechanism allowing a user (or authorized party acting on the user's behalf, similar to the reported fix pattern) to redirect a stuck refund to an alternate address, and/or use `trySafeTransfer` even when `receiver == requester`, falling back to leaving the request refundable/claimable to a caller-supplied alternate address instead of reverting unconditionally.

### Proof of Concept
1. Deploy `ProvisionerV2` wired to a mock blacklistable ERC20 (mimic USDC's `isBlacklisted` check reverting transfers to/from blacklisted addresses).
2. As `alice`, call `requestDeposit(token, tokensIn, minUnitsOut, 0, deadline, maxPriceAge, true)` — this escrows `tokensIn` in the Provisioner with `receiver = alice`.
3. Blacklist `alice` on the mock token.
4. Assert `alice.cancelRequest(token, request)` reverts (transfer to `alice` reverts).
5. Warp past `deadline`; assert `refundRequest(token, request)` called by any third party also reverts.
6. Assert a solver's `solveRequestsVault` call for this request's expired branch also reverts.
7. Confirm `tokensIn` remains stuck in the Provisioner with no successful path to return it to `alice`.
