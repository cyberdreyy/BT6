## Title
Reject→Accept weight double-counting in the miner's signer coordinator lets one signer's flipped vote wedge out an already-signed block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side `SignCoordinator`/`StackerDBListener` that tallies signer responses for a proposed block keeps two weight buckets, `total_weight_approved` and `total_weight_rejected`, that are supposed to be mutually exclusive per signer slot. The guard that prevents double-counting is asymmetric: it fully protects the accept→reject ordering but not the reject→accept ordering, so a single signer who sends a `Rejected` response followed later by an `Accepted` response for the same block gets counted in *both* buckets permanently.

### Finding Description
`BlockStatus` in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` tracks `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected`. [1](#0-0) 

For an `Accepted` message, the code guards against double counting using `gathered_signatures.contains_key(&slot_id)`, then unconditionally inserts the slot into `responded_signers`: [2](#0-1) 

For a `Rejected` message, the guard is `responded_signers.insert(slot_id)` (i.e., "have we ever heard from this signer before, regardless of kind"): [3](#0-2) 

Because the `Accepted` branch never checks `responded_signers`, and the `Rejected` branch's insert into `responded_signers` does not stop a later `Accepted` from being counted, the sequence Reject → Accept from the same signer slot results in:
- `total_weight_rejected` incremented once (on the reject), and
- `total_weight_approved` incremented once (on the later accept, since `gathered_signatures` was empty for that slot at that time).

The same signer's weight now sits in both tallies simultaneously and is never removed from `total_weight_rejected`, even though the signer's live opinion is "accept." (The reverse order, Accept → Reject, is correctly protected because `responded_signers` is already populated by the accept branch.)

This breaks the invariant the rest of the coordinator relies on — that a signer's weight should count toward at most one side of the vote. In `stacks-node/src/nakamoto_node/signer_coordinator.rs`, the rejection check is evaluated *before* the acceptance check: [4](#0-3) 

If enough of this double-counted weight (or a mix of double-counted plus genuine rejection weight) pushes `total_weight_rejected + weight_threshold > total_weight`, the coordinator returns `NakamotoNodeError::SignersRejected` and discards the block — even when `total_weight_approved >= weight_threshold` is *also* true at that same moment, because the `else if` for acceptance is never reached.

### Impact Explanation
This is a liveness wedge reachable by a single signer's message ordering (a legitimate revocable-rejection flip, or simple StackerDB gossip retransmission/out-of-order delivery of an old rejection chunk after a newer acceptance was already recorded from a different node's perspective). No majority collusion, key compromise, or auth token access is required — one signer flipping its vote is enough to corrupt the tally maintained purely on the miner side. The result is that a block which has genuinely reached the 70% approval weight can still be thrown away by the coordinator as "rejected," forcing the miner to abandon signatures it already legitimately gathered and re-propose. Repeated occurrences of this pattern (e.g., a chronically flaky or reconnecting signer) can repeatedly wedge block production on the miner side.

### Likelihood Explanation
Moderate-to-high: it requires only one signer (out of the whole set) to send a rejection followed later by an acceptance for the same block hash — a scenario explicitly acknowledged as legitimate by the surrounding signer-side design (a rejection is described elsewhere in the codebase as "a revocable opinion" that can be superseded by a signature). Message reordering/redelivery over StackerDB gossip makes this reachable without any special conditions.

### Recommendation
Make the double-counting guard symmetric: both the `Accepted` and `Rejected` branches should check/update `responded_signers` (or an equivalent single per-slot "current vote" map) consistently, and a later opposite-kind message from the same slot should adjust (subtract-then-add) the weight rather than being allowed to additively double-book it. Alternatively, track a single `HashMap<slot_id, Vote>` recording each signer's *latest* response and recompute `total_weight_approved`/`total_weight_rejected` from that map on every update, so a signer's weight can never appear in both totals at once.

### Proof of Concept
1. Node proposes block `B`; `SignCoordinator` initializes `BlockStatus` with empty tallies.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B`. `stackerdb_listener.rs` line 515-518: `responded_signers.insert(slot_S)` succeeds, `total_weight_rejected += w`.
3. Signer `S` later sends `BlockResponse::Accepted` for the same `B` (a legitimate flip, or a delayed/duplicated StackerDB chunk). Line 443: `gathered_signatures.contains_key(&slot_S)` is `false` (this branch never checked `responded_signers`), so `total_weight_approved += w` as well. `S`'s weight is now counted on both sides.
4. If other signers accept up to `weight_threshold - w` and other/duplicated rejections bring `total_weight_rejected` to `total_weight - weight_threshold + 1`, then in `signer_coordinator.rs` line 509-513 the rejection branch fires first and returns `Err(SignersRejected{..})`, discarding the block despite `total_weight_approved >= weight_threshold` also holding at that same tally snapshot.
