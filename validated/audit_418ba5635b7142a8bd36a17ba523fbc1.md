Based on the code I could inspect, this is a legitimate accounting issue in `delegation_pool.move`.

### Title
Permissionless `synchronize_delegation_pool` pays operator commission to the current operator's beneficiary regardless of when it accrued, allowing commission earned by the old operator to be redirected to the new operator after `set_operator` - (File: aptos-move/framework/aptos-framework/sources/delegation_pool.move)

### Summary
`synchronize_delegation_pool` computes the commission owed since the last synchronization via `calculate_stake_pool_drift`, and pays it out using whichever address `stake::get_operator(pool_address)` currently returns, not the operator who was active while the rewards accrued.

### Finding Description
`calculate_stake_pool_drift` derives `commission_active`/`commission_pending_inactive` purely from the stake-pool's coin deltas since the last sync (`pool.total_coins_inactive` baseline and active/pending_active/pending_inactive totals), with no record of which operator earned which portion of the drift. [1](#0-0) 

When the commission is actually paid, it is routed to `beneficiary_for_operator(stake::get_operator(pool_address))` — i.e. whatever the *current* operator/beneficiary mapping is at the moment `synchronize_delegation_pool` executes: [2](#0-1) 

The pool owner changes the delegation pool's operator by calling `stake::set_operator` directly on the underlying stake pool; there is no wrapper inside `delegation_pool.move` (no `fun set_operator` was found in that file) that first forces a `synchronize_delegation_pool` call to settle the outgoing operator's commission before flipping `stake::get_operator`. Because `synchronize_delegation_pool` is a public, permissionless entrypoint, anyone — most plausibly the incoming new operator itself — can call it immediately after the owner's `set_operator` transaction lands and before the old operator (or owner) manages to trigger a settlement. At that point all commission accrued since the previous sync, including the portion earned while operator A was in charge, is computed and paid to `beneficiary_for_operator(operator_B)`.

### Impact Explanation
This breaks the invariant that commission accrued under operator A must be paid to operator A (or A's beneficiary). The scoped impact is the uncommitted commission for a single pool for the interval between the last sync and the operator switch — this can represent a full lockup cycle's worth of unclaimed commission being misdirected to the new operator instead of the rightful old operator.

### Likelihood Explanation
Exploitation requires only: (1) an owner calling `stake::set_operator` on a delegation pool without first synchronizing, and (2) any address calling the permissionless `synchronize_delegation_pool` before the old operator/owner does so. The realistic beneficiary of this race is the incoming operator (who has direct incentive to front-run the settlement), and mempool visibility of `set_operator` transactions makes timing straightforward. No special privileges are needed to trigger `synchronize_delegation_pool`.

### Recommendation
`delegation_pool.move` should force a synchronization (settling commission to the current, pre-change operator) as part of any operator-change flow that this module is aware of, or the framework should provide a dedicated `delegation_pool::update_operator` entrypoint that internally calls `synchronize_delegation_pool` before invoking `stake::set_operator`, so commission is always settled to the outgoing operator prior to the switch taking effect.

### Proof of Concept
1. Owner O owns a delegation pool with operator A; rewards accrue over time, growing `commission_active`/`commission_pending_inactive` since the last `synchronize_delegation_pool`.
2. O submits `stake::set_operator(pool_signer, B)` to switch the pool's operator from A to B.
3. Before O or A can call `synchronize_delegation_pool` (or before the old operator's beneficiary is settled), B (or a colluding/opportunistic third party) calls the permissionless `delegation_pool::synchronize_delegation_pool(pool_address)`.
4. `calculate_stake_pool_drift` computes the full unsettled commission since the last sync (which include's A's tenure), and `beneficiary_for_operator(stake::get_operator(pool_address))` resolves to B's beneficiary because `stake::get_operator` already returns B.
5. Commission that should have gone to A's beneficiary is paid to B's beneficiary instead — verifiable by extending `test_change_operator` (delegation_pool.move:3653) to interleave a `synchronize_delegation_pool` call between reward accrual/`set_operator` and asserting A's beneficiary balance is short-changed while B's is inflated.

Note: I was unable to fully confirm from the retrieved source whether any other framework-level entrypoint (e.g. in `staking_contract.move`, which does define its own `set_operator`) enforces a pre-switch settlement specifically for delegation pools that are wrapped by a staking contract; that path should be verified with a full read of `staking_contract.move`'s operator-change logic before treating this as fully unmitigated across all pool configurations.

    /// Calculate stake deviations between the delegation and stake pools in order to
    /// capture the rewards earned in the meantime, resulted operator commission and
    /// whether the lockup expired on the stake pool.
    fun calculate_stake_pool_drift(pool: &DelegationPool): (bool, u64, u64, u64, u64) {
        let (active, inactive, pending_active, pending_inactive) = stake::get_stake(get_pool_address(pool));
        assert!(
            inactive >= pool.total_coins_inactive,
            error::invalid_state(ESLASHED_INACTIVE_STAKE_ON_PAST_OLC)
        );
        // determine whether a new lockup cycle has been ended on the stake pool and
        // inactivated SOME `pending_inactive` stake which should stop earning rewards now,
        // thus requiring separation of the `pending_inactive` stake on current observed lockup
        // and the future one on the newly started lockup
        let lockup_cycle_ended = inactive > pool.total_coins_inactive;

        // actual coins on stake pool belonging to the active shares pool
        active += pending_active;
        // actual coins on stake pool belonging to the shares pool hosting `pending_inactive` stake
        // at current observed lockup cycle, either pending: `pending_inactive` or already inactivated:
        if (lockup_cycle_ended) {
            // `inactive` on stake pool = any previous `inactive` stake +
            // any previous `pending_inactive` stake and its rewards (both inactivated)
            pending_inactive = inactive - pool.total_coins_inactive
        };
