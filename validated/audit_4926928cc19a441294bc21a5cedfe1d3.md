### Title
`GaslessRateLimiter` per-validator local counter is bounded by the full `gasless_max_tps` value, allowing N validators to collectively admit N × max\_tps gasless transactions per second — (`File: crates/sui-core/src/gasless_rate_limiter.rs`)

---

### Summary

`GaslessRateLimiter::try_acquire` enforces a two-layer check: a consensus-fed global counter (`ConsensusGaslessCounter`) and a per-validator local fixed-window counter (`FixedWindowCounter`). Both layers are compared against the same `gasless_max_tps` value. Because the consensus counter is only updated **after** consensus commits are processed, each of the N validators on the network can independently admit up to `max_tps` gasless transactions during the lag window before the global counter catches up. The effective network-wide gasless admission rate is therefore N × `max_tps`, not `max_tps`.

---

### Finding Description

`GaslessRateLimiter::try_acquire` in `crates/sui-core/src/gasless_rate_limiter.rs`:

```rust
pub fn try_acquire(&self, config: &ProtocolConfig) -> bool {
    let Some(max_tps) = config.gasless_max_tps_as_option() else {
        return true;
    };
    if self.consensus_counter.current_count() >= max_tps {   // (1) global check
        return false;
    }
    // no single validator can admit more than max_tps burst
    self.local.lock().try_acquire(max_tps)                   // (2) per-validator check
}
``` [1](#0-0) 

Both checks (1) and (2) use the same `max_tps` ceiling. The `ConsensusGaslessCounter` is populated by `process_gasless_transactions`, which calls `record_commit` only **after** a consensus commit is fully processed:

```rust
fn process_gasless_transactions(&self, commit_info: &ConsensusCommitInfo,
    user_transactions: &[VerifiedExecutableTransactionWithAliases]) {
    let gasless_count = user_transactions.iter()
        .filter(|txn| txn.tx().transaction_data().is_gasless_transaction())
        .count() as u64;
    self.consensus_gasless_counter.record_commit(commit_info.timestamp, gasless_count);
}
``` [2](#0-1) 

This means the consensus counter always lags behind the actual admitted count. During the lag window (the time between a validator admitting a transaction and the next consensus commit being processed), the consensus counter reads stale data. Each validator's local `FixedWindowCounter` is the only real-time gate, and it is capped at the full `max_tps` value — the same ceiling as the intended global limit.

The `FixedWindowCounter` is per-validator and resets every second:

```rust
fn try_acquire(&mut self, max_tps: u64) -> bool {
    if self.window_start.elapsed().as_secs() >= 1 {
        self.count = 0;
        self.window_start = Instant::now();
    }
    if self.count < max_tps { self.count += 1; true } else { false }
}
``` [3](#0-2) 

With `gasless_max_tps = 300` (as set in protocol version 129) and a mainnet validator set of ~100+ validators, an attacker can submit distinct gasless transactions to each validator simultaneously. Each validator independently passes check (2) (local count 1 < 300) and check (1) (consensus counter still 0 from the previous commit). All transactions are forwarded to consensus. The actual network-wide gasless admission rate becomes N × 300 ≈ 30,000 TPS instead of the intended 300 TPS. [4](#0-3)

### Impact Explanation

Gasless transactions carry no gas fee, so the attacker bears zero cost. By routing distinct gasless transactions to each validator's public RPC endpoint simultaneously, the attacker can sustain a gasless transaction flood at N × `max_tps` — roughly two orders of magnitude above the intended cap. This can cause sustained network congestion, degraded throughput for legitimate transactions, and potential fullnode instability under load. The impact class is **Low** (public-input fullnode crash / validator invariant-violation error on unmodified software) and could reach **Medium** (network and node shutdown reachable from public input) depending on how the node handles the excess load.

---

### Likelihood Explanation

Validator RPC endpoints are publicly discoverable. An ordinary SUI holder can craft valid gasless transactions (which are constrained in size and computation but not in count) and submit them concurrently to multiple validators using standard HTTP clients. No privileged access, leaked keys, or malicious peer assumptions are required. Likelihood is **Medium**.

---

### Recommendation

The per-validator local counter should be bounded by a fraction of `max_tps`, not the full value. One approach:

```rust
// Divide the global budget across validators proportionally.
// The validator count can be read from the epoch store's committee.
let per_validator_limit = max_tps / validator_count;
self.local.lock().try_acquire(per_validator_limit.max(1))
```

Alternatively, the local counter can be removed entirely and replaced with a pre-consensus admission counter that is shared across all in-flight (not yet committed) transactions on the node, so the consensus counter's lag does not create an exploitable window.

---

### Proof of Concept

1. Read `gasless_max_tps` from the current protocol config (e.g., 300).
2. Discover the public RPC endpoints of N validators (publicly available).
3. Construct N distinct valid gasless transactions (each within `gasless_max_tx_size_bytes`, `gasless_max_computation_units`, etc.).
4. Submit each transaction to a different validator's endpoint simultaneously (e.g., via parallel HTTP POST to `/submit_transaction`).
5. Before any consensus commit fires, each validator's `ConsensusGaslessCounter` still reads 0 (no commit has been processed yet), and each validator's local counter reads 0. Both checks pass on every validator.
6. All N transactions are forwarded to consensus. The consensus counter is updated only after the commit, by which point all N transactions are already admitted.
7. Repeat every second. Sustained gasless admission rate = N × 300 ≈ 30,000 TPS, versus the intended 300 TPS cap. [1](#0-0) [2](#0-1)
