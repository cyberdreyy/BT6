### Title
External Initiator can trigger arbitrary numeric-ID job runs via `PipelineRunsController.Create`, bypassing the job/EI webhook binding - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `POST /v2/jobs/:ID/runs` route accepts External Initiator (EI), token, and session authentication, and wraps `PipelineRunsController.Create` with `auth.RequiresRunRole`. Because `AuthenticateExternalInitiator` also sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}`, the `isUser` check in `Create` (which only checks `GetAuthenticatedUser` presence, not credential type) treats an EI exactly like a real user with run role, letting it call `RunJobV2` for any numeric job ID regardless of which webhook job the EI is actually bound to.

### Finding Description
The route is registered in `core/web/router.go`:
```go
userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateExternalInitiator,
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
``` [1](#0-0) 

`AuthenticateExternalInitiator` in `core/web/auth/auth.go` authenticates the EI credential, then unconditionally sets a fabricated user object with `Role: UserRoleRun` into the same session key used for real users:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [2](#0-1) 

`RequiresRunRole` only checks that `user.Role != UserRoleView`, so the EI's synthetic run-role user passes: [3](#0-2) 

Inside `PipelineRunsController.Create`, the gating logic is:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    var jobID int32
    jobID64, err := strconv.ParseInt(idStr, 10, 32)
    if err == nil {
        jobID = int32(jobID64)
        jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
        ...
    }
}
jsonAPIError(c, http.StatusUnprocessableEntity, errors.New("bad job ID"))
``` [4](#0-3) 

The comment states "EIs not allowed," but the check `_, isUser := auth.GetAuthenticatedUser(c)` only tests whether *any* user object was set in context — it does not distinguish a real session/token user from the synthetic user object created for EI auth. Since `AuthenticateExternalInitiator` places a `*clsessions.User` under `SessionUserKey`, `GetAuthenticatedUser` returns `ok=true` for EI-authenticated requests, making `isUser` `true`. Consequently, any authenticated EI can supply an arbitrary numeric job ID in the URL and reach `prc.App.RunJobV2(ctx, jobID, nil)` — there is no check anywhere in this path that the EI is the one bound to that specific job's webhook spec (no lookup against `ExternalInitiatorWebhookSpec`/job binding is performed before calling `RunJobV2`).

### Impact Explanation
This is an authorization bypass allowing an EI credential holder to trigger runs of jobs it is not bound to. Depending on job configuration, triggering an unrelated job run can cause unauthorized on-chain transaction submission, unintended external HTTP/bridge calls, or unauthorized consumption/side effects of another tenant's job pipeline — cross-initiator job triggering as scoped in the question. This matches a "unauthorized job run" / authorization-bypass impact class.

### Likelihood Explanation
Requires only a valid EI credential (access key/secret) issued for *some* job — no special privilege beyond that is needed. The attacker (an EI holder for job "foo") simply issues `POST /v2/jobs/<other-job-numeric-id>/runs` with valid EI headers. This is trivially repeatable and requires no race conditions or timing; the numeric job ID is guessable/enumerable (sequential integer job IDs). This is fully reachable given the router wiring for `/v2/jobs/:ID/runs` shown above.

### Recommendation
Fix `PipelineRunsController.Create` to distinguish EI auth from real user auth, e.g. check `auth.GetAuthenticatedExternalInitiator(c)` first and reject/handle separately, or have `AuthenticateExternalInitiator` set a distinct context key (not reuse `SessionUserKey`) so `isUser` genuinely reflects session/token user auth. Additionally, before calling `RunJobV2` for an EI-authenticated request, verify the target job's webhook spec is actually bound to the authenticated `ExternalInitiator` (join against `external_initiator_webhook_specs`).

### Proof of Concept
Handler-level integration test plan (Go, using `httptest` + gin router as built in `router_test.go`/`pipeline_runs_controller_test.go` patterns):
1. Create two webhook jobs, JobA bound to `ExternalInitiator` EI1, JobB bound to a different `ExternalInitiator` EI2 (or to no EI at all).
2. Authenticate as EI1 (set `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers matching EI1's stored token).
3. Send `POST /v2/jobs/{JobB.ID}/runs` (JobB's numeric ID, not bound to EI1).
4. Assert that `prc.App.RunJobV2` is invoked (e.g., via a mock `chainlink.Application` recording calls) with `JobB.ID`, and that the response is `200 Created`/pipeline run resource rather than `422 bad job ID`.
5. Additionally unit-test `auth.GetAuthenticatedUser(c)` after running `AuthenticateExternalInitiator` in isolation, asserting `ok == true`, confirming the root cause that EI auth is indistinguishable from user auth for the `isUser` check.
6. Expected (fixed) behavior: the request should be rejected (403/422) because JobB is not bound to EI1, or `isUser` should evaluate `false` for EI-authenticated contexts.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
