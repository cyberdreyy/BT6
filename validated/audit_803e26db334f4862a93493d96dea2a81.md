### Title
Sensitive-field redaction in the debug request logger relies on a hardcoded, incomplete "password" name assumption - ([File: core/web/router.go])

### Summary
`loggerFunc` in `core/web/router.go` logs every incoming HTTP request's query parameters and JSON body at debug level, running them through a redaction filter (`redact`/`readSanitizedJSON`) before logging. That filter's `isBlacklisted` function assumes any sensitive field can be identified purely by the substring `"password"` (or a short hardcoded list of password-like key names), mirroring the reported bug class where `getPriceOfAssetQuotedInUSD()` made an unproven naming assumption (`startsWith('W')` ⇒ wrapped token) to decide behavior.

### Finding Description
The request logging middleware reads the full request body and query string for every route and logs them (at Debug level) after applying redaction: [1](#0-0) 

Redaction is implemented purely by key-name matching against a tiny hardcoded blacklist and a `strings.Contains(lk, "password")` check: [2](#0-1) 

This is applied to both the URL query values and the JSON body: [3](#0-2) 

Just as the external report's `getPriceOfAssetQuotedInUSD()` incorrectly assumed a token name pattern (`'W'` prefix ⇒ wrapped) to make a security/behavior-relevant decision, `isBlacklisted` incorrectly assumes any sensitive credential-carrying field will contain the literal substring `password`. Any other secret-carrying field name (e.g. `secret`, `token`, `apiKey`, `accessKey`, `clientSecret`, `privateKey`, `oldToken`, etc.) is NOT redacted and will be written verbatim into node logs whenever it appears in a request body or query string handled through this middleware.

### Impact Explanation
If any current or future JSON-accepting endpoint accepts a field whose name doesn't contain "password" (e.g. a hypothetical secret/token field, or a field with different casing/language not literally spelled "password"), that value will be persisted in plaintext into the node's debug logs. Log files are frequently shipped to less-trusted aggregation systems, shared with support teams, or accessible to a broader set of operators than the credential owner, so this constitutes an unintended secret-disclosure surface driven purely by an unverified/incomplete naming assumption in `isBlacklisted`, directly analogous to the reported bug class of "assumption about names leads to flawed/incorrect output."

### Likelihood Explanation
This is a logging-time behavior, not an authentication bypass — it depends entirely on which fields the various JSON-accepting web controllers named. I could not find, in the reachable code and index, an in-scope currently-existing request body field carrying a raw secret that is *not* already named with "password" and sent to an endpoint wrapped by `loggerFunc` (external initiator secrets, API tokens, and OIDC/WebAuthn secrets are generated server-side and returned in responses, which this middleware does not log). Because I could not concretely prove an unprivileged-actor-reachable path where a currently-named non-"password" secret field is submitted and logged, this is a latent/fragile design weakness rather than a confirmed exploitable disclosure today.

### Recommendation
Broaden `isBlacklisted` beyond a fixed name list/`"password"` substring — e.g., also match `secret`, `token`, `key`, `credential`, `authorization`, etc., or better, switch to an explicit whitelist of safe-to-log fields per endpoint rather than a denylist keyed on assumed substrings. This mirrors the report's own recommendation: avoid naming-based assumptions and instead use a reliable, explicit source of truth (e.g., per-field struct tags marking `sensitive:"true"`).

### Proof of Concept
Not applicable as a working exploit against current code — I could not identify a currently reachable endpoint whose request body/query carries a secret value under a key name lacking "password" that flows through `loggerFunc`. The finding is a structural weakness in `isBlacklisted` (core/web/router.go:643-658) that could silently leak any future or overlooked secret-carrying field name into debug logs, exactly matching the reported bug class of naming-based assumptions producing incorrect/unsafe results rather than validated data.

func readSanitizedJSON(buf *bytes.Buffer) (string, error) {
	var dst map[string]any
	err := json.Unmarshal(buf.Bytes(), &dst)
	if err != nil {
		return "", err
	}

	cleaned := map[string]any{}
	for k, v := range dst {
		if isBlacklisted(k) {
			cleaned[k] = "*REDACTED*"
			continue
		}
		cleaned[k] = v
	}

	b, err := json.Marshal(cleaned)
	if err != nil {
		return "", err
	}
	return string(b), err
}

func redact(values url.Values) string {
	cleaned := url.Values{}
	for k, v := range values {
		if isBlacklisted(k) {
			cleaned[k] = []string{"REDACTED"}
			continue
		}
		cleaned[k] = v
	}
	return cleaned.Encode()
}

// NOTE: keys must be in lowercase for case insensitive match
var blacklist = map[string]struct{}{
	"password":             {},
	"newpassword":          {},
	"oldpassword":          {},
	"current_password":     {},
	"new_account_password": {},
}

func isBlacklisted(k string) bool {
	lk := strings.ToLower(k)
	if _, ok := blacklist[lk]; ok || strings.Contains(lk, "password") {
		return true
	}
	return false
}
