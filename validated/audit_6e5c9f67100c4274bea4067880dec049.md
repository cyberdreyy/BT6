## Title
Stale Confirmations From Removed Multisig Members Allow Request Execution Below the True Confirmation Threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
The multisig contracts (`multisig` and `multisig2`) purge outstanding *requests* originated by a removed key/member when that key/member is deleted, but they never purge that key/member's *confirmations* recorded on requests originated by other members. A stale confirmation from a now-deleted member continues to count toward `num_confirmations`, so a pending request can later be executed with fewer live-member approvals than the configured threshold requires.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` only removes requests whose *originator* (`r.member`) equals the member being deleted: [1](#0-0) 

It does not scan `self.confirmations` for entries where the removed member appears as a *confirmer* on some other, still-pending request. The same gap exists in `multisig/src/lib.rs`'s `DeleteKey` handling, which filters by `r.signer_pk == pk` only: [2](#0-1) 

Meanwhile, `confirm` decides whether to execute a request purely by counting entries already stored in `self.confirmations`, without re-validating that those entries still correspond to current members: [3](#0-2) 

The intended invariant is: `confirmations counted for a request == confirmations from currently live members`. Because deletion only cleans up requests keyed by the deleted member as *originator*, a confirmation the deleted member cast on someone else's request survives in the `confirmations` map, breaking that equality. A subsequent confirmation from one genuinely current member can then push `confirmations.len() + 1 >= num_confirmations` and trigger `execute_request`, even though the number of *live* approvers is one less than `num_confirmations`.

This mirrors the reported analog's root cause class: state recorded under one identity/binding (a confirmation tied to a member who has since been removed) is still treated as valid entitlement (a vote counted toward threshold) after the entitlement should have been revoked — the same "recorded claim vs. current reality" mismatch as the BoostController delegation-mapping bug.

### Impact Explanation
This directly maps to the explicitly listed Critical impact: "a multisig request executed below threshold." A `Transfer`, `AddKey`, `FunctionCall`, or `DeployContract` action can be executed by the contract with fewer than `num_confirmations` live, authorized approvals, allowing NEAR (or other privileged actions) to move without the intended authorization threshold being met by currently valid signers.

### Likelihood Explanation
The bug is triggered by ordinary, expected multisig lifecycle operations — a member confirms a pending request, is later removed via a normal `DeleteMember`/`DeleteKey` execution, and another live member later confirms the still-pending request. No malicious insider collusion, redeploy, or external actor is required beyond the multisig's own normal member-rotation workflow, which the contract is documented to support (`SetNumConfirmations`, key/member rotation). Any multisig that rotates members while requests are outstanding is exposed.

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` handling in `multisig/src/lib.rs`), iterate over `self.confirmations` for **all** active requests and strip the removed member's/key's entry from each confirmation set (not just requests it originated). Alternatively, validate at `confirm`/`execute_request` time that every entry in a request's confirmation set still belongs to a current member before counting it toward `num_confirmations`.

### Proof of Concept
Using `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`:
1. `C` calls `add_request(X)` where `X` is a `Transfer` action — `confirmations[X] = {}`.
2. `A` calls `confirm(X)` — `confirmations[X] = {A}` (1 < 2, not executed).
3. Members `B` and `C` create and confirm a separate request `Y = DeleteMember{A}`; it reaches 2 confirmations and executes `delete_member(A)` per [4](#0-3) . This removes `A` from `members` and purges only requests where `r.member == A` — request `X` (originated by `C`) is untouched, so `confirmations[X]` still equals `{A}`.
4. `B` calls `confirm(X)`. `assert(!confirmations.contains(&B))` passes; `confirmations.len() (1) + 1 = 2 >= num_confirmations (2)` per [5](#0-4) , so `execute_request(X)` fires and the `Transfer` executes.
5. Result: the transfer executed with confirmations `{A, B}`, but `A` was no longer a member at execution time. Only `B` — a single live member — actually authorized this specific transfer, while the contract believed the 2-of-2 (now effectively 2-of-2 remaining members `B`,`C`) threshold was met. `C`, a live member, never approved the transfer that moved funds.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
