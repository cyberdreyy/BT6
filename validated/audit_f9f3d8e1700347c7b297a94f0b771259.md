### Title
Stale `lastWithdrawRequest` makes earlier loss-adjusted receipts claimable at par, overpaying one user from other claimants' funded underlyings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Prototype pollution is a bug where attacker-controlled keys corrupt shared object state. The analog in `IdleCreditVault` is keyed-state pollution across epochs: `lastWithdrawRequest[_user]` is a single slot that is overwritten on every `requestWithdraw`, while `lossRecoveryPriceByEpoch` is keyed per epoch. When a user has receipts in two different loss-adjusted epochs, a single `claimWithdrawRequest` clears only the latest loss epoch's haircut basis and then pays the older loss-adjusted basis through the at-par funded path, breaking the loss-socialization invariant and overpaying the claimant.

### Finding Description
`requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and records the basis per epoch in `withdrawsRequestsByEpoch[_user][currentEpoch]` while also accumulating the aggregate `withdrawsRequests[_user]` [1](#0-0) . When the manager stops an epoch with a loss, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws`, i.e., all pending receipts of that epoch are only funded at `lossRecoveryPrice` [2](#0-1) .

On claim, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which looks up the haircut price only via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — a single epoch key [3](#0-2) . `_clearWithdrawClaimForEpoch` clears only that epoch's `withdrawsRequestsByEpoch` entry and resets `lastWithdrawRequest[_user] = 0` [4](#0-3) . Execution then falls through to `_claimFundedWithdrawRequest`, whose epoch gate (`epochNumber <= lastWithdrawRequest[_user]` → revert) is bypassed because the marker is now `0`, and which pays the remaining `withdrawsRequests[_user]` — still containing the older loss-epoch basis — at par [5](#0-4) .

Broken invariant: loss waterfall / fair claim pricing. A receipt funded at `lossRecoveryPrice < 1` is paid at `1.0`. `_transferFundedClaim` only protects `defaultRecoveryReserve`, not other users' funded underlyings [6](#0-5) .

### Impact Explanation
The claimant receives `basis_epochA * (1 - lossRecoveryPrice_A)` more underlying than funded for that receipt. The vault's underlying balance is the shared pool backing all pending claims, so the overpayment is stolen directly from other users' funded withdraw receipts — later claimants find the pool insolvent and their claims revert on `safeTransfer`. Quantified loss: if the attacker held the only receipt of epoch A with basis 100,000 USDC at a 50% recovery price, they extract an extra 50,000 USDC belonging to other claimants. Costs are only two withdraw requests and two claims, executable by any KYC-passing lender.

### Likelihood Explanation
Requires two `stopEpochWithDuration`/`collectWithdrawFunds` calls with `_lossAmount > 0` (partial funding) in different epochs, with the same user holding a pending receipt in each. Loss-adjusted stops are a designed protocol path (borrower repays partially), and repeated partial repayment across consecutive epochs is realistic in distressed credit pools. The attacker needs no privileges — just patience to keep an unclaimed receipt across one epoch boundary, which the code explicitly permits ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch"). No existing guard (skim, default revert, epoch gating, reserve check) detects that the residual `withdrawsRequests[_user]` belongs to a haircut epoch.

### Recommendation
Track per-epoch claim state instead of a single `lastWithdrawRequest` marker. Options:
- Iterate/clear all epochs with non-zero `lossRecoveryPriceByEpoch` for the user (or store a per-user set of request epochs), applying each epoch's recovery price.
- Alternatively, store `claimEpoch -> recovery price` per user (`lossRecoveryPriceByUserEpoch[_user][epoch]`) at claim time and never route a basis that has a non-zero loss price through `_claimFundedWithdrawRequest`.
- At minimum, in `_claimFundedWithdrawRequest`, exclude any `withdrawsRequestsByEpoch` entries whose epoch has a non-zero `lossRecoveryPriceByEpoch` from the at-par `normalAmount`.

### Proof of Concept
Foundry fork-style test against `IdleCreditVault`/`IdleCDOEpochVariant` harness (as in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossEpochPollutionPaysPar() external {
    // epoch A: user deposits and requests withdraw
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // receipt basis A

    _startEpochAndCheckPrices(0);
    // stop epoch with partial loss -> collectWithdrawFunds stores
    // lossRecoveryPriceByEpoch[0] = 0.5e18 (50% haircut)
    _stopEpochWithLoss(0, lossA);                    // pendingWithdraws = 0

    // do NOT claim; open next epoch, request again
    _startEpochAndCheckPrices(1);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // receipt basis B
    _stopEpochWithLoss(1, lossB);                    // lossRecoveryPriceByEpoch[1]

    // single claim:
    // 1) _claimLossAdjustedWithdrawRequest clears epoch-1 basis at haircut price
    //    and resets lastWithdrawRequest[attacker] = 0
    // 2) _claimFundedWithdrawRequest then pays remaining
    //    withdrawsRequests[attacker] (epoch-0 basis) AT PAR
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    uint256 paid = underlying.balanceOf(attacker) - balPre;
    uint256 expected = basisB * lossPriceB / 1e18 + basisA * lossPriceA / 1e18;
    assertGt(paid, expected); // overpaid by basisA * (1 - lossPriceA)
    // subsequent honest claimant's claimWithdrawRequest reverts /
    // vault underlying balance < sum of remaining funded claims
}
```

Key assertions: `creditVault.withdrawsRequests(attacker)` retained the epoch-A basis after the first loss stop, `lastWithdrawRequest` was overwritten to epoch 1 by the second request, and the funded path paid it at par because `lossRecoveryPriceByEpoch` is only consulted for `lastWithdrawRequest[_user]`.
