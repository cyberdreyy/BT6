### Title
Unbounded per-request ancestor-walk in `Blockstore::get_complete_transaction`/`get_confirmed_signatures_for_address2` causes O(unrooted-slot-depth) cost on every unprivileged `getTransaction`/`getSignaturesForAddress` call - (File: ledger/src/blockstore.rs)

### Summary
Every `getTransaction` and `getSignaturesForAddress` JSON-RPC call at `confirmed` commitment (the default) causes the validator to reconstruct the full "confirmed but unrooted" slot set by walking blockstore ancestor metadata from the current confirmed slot back to the last root. Unlike the Autonomint bug, this loop resets after each new root, but its length is entirely determined by cluster/runtime state (the depth of the not-yet-rooted fork) rather than by any protocol-level bound, so it re-executes this walk from scratch on every single low-rate RPC call.

### Finding Description
`JsonRpcRequestProcessor::get_transaction` (unprivileged RPC handler for `getTransaction`) calls `blockstore.get_complete_transaction(signature, highest_confirmed_slot)` when commitment is `confirmed` (the default commitment level): [1](#0-0) 

`get_complete_transaction` builds `confirmed_unrooted_slots` by walking blockstore metadata one slot at a time from `highest_confirmed_slot` down to `max_root`, using `AncestorIterator::new_inclusive`: [2](#0-1) 

`AncestorIterator` performs one `blockstore.meta(slot)` RocksDB lookup per slot traversed: [3](#0-2) 

The identical pattern exists in `get_confirmed_signatures_for_address2`, the backing function for `getSignaturesForAddress` (also invoked at default `confirmed` commitment via `RpcClient::get_signatures_for_address`): [4](#0-3) [5](#0-4) 

In both cases, the number of iterations is `highest_confirmed_slot - max_root`, i.e., the number of slots that have been optimistically/gossip-confirmed but not yet rooted. Under normal healthy-cluster conditions this gap is small (a handful of slots), but it is not enforced by any hard cap in this code path — it grows with root-confirmation lag, which can increase during network instability, partial partitions, heavy fork switching, or slow vote landing. Each single `getTransaction`/`getSignaturesForAddress` call fully re-walks this chain from scratch (there is no caching of `confirmed_unrooted_slots` across requests), so the cost of one request scales linearly with a runtime-dependent variable that a client does not control and that is not validated against any RPC-configurable limit — structurally the same class of defect as the reported bug: forcing a fixed-cost-looking single operation to iterate an unbounded/attacker-uncontrolled amount of historical state accumulated since a reference checkpoint (there, "since deposit"; here, "since last root").

### Impact Explanation
If root-confirmation lag grows (which can happen during degraded cluster conditions, e.g., partition/fork churn, and is outside the caller's control), every single `getTransaction` or `getSignaturesForAddress` call at `confirmed` commitment pays a cost proportional to that lag, performing one RocksDB metadata read per unrooted slot before even attempting to locate the requested transaction/signature. This increases per-request CPU/I/O cost server-side for an ordinary, single, unprivileged JSON-RPC call, and could compound RPC-thread resource pressure exactly when the cluster is already stressed by root-confirmation delays — worsening degraded conditions rather than gracefully bounding them.

### Likelihood Explanation
This code path executes unconditionally on the default confirmed-commitment `getTransaction`/`getSignaturesForAddress` RPC calls that any unprivileged client can make (no special permissions required), and the ancestor walk is unbounded by any explicit limit — its cost is a direct function of cluster state (unrooted depth) at call time, not of any parameter the RPC operator can cap. Under normal, healthy conditions the impact is negligible (small unrooted depth), but the code offers no defense-in-depth cap should that gap grow, which is the same structural gap identified in the referenced report (missing bound on iteration count tied to accumulated history).

### Recommendation
Bound the ancestor walk (e.g., cap the number of slots traversed by `AncestorIterator` when building `confirmed_unrooted_slots`, or cache/incrementally maintain the unrooted-slot set instead of recomputing it from scratch per RPC call) so that a single `getTransaction`/`getSignaturesForAddress` request cannot incur cost proportional to an unbounded, caller-uncontrolled cluster-state variable.

### Proof of Concept
Not applicable — no exploit was constructed under this analog scan (analysis is based on static code-path tracing per the task rules, not a runtime PoC). Confirming the practical severity would require measuring achievable root-confirmation lag under adversarial-adjacent but realistic conditions, which is outside the scope of this review.

    /// Returns a complete transaction
    pub fn get_complete_transaction(
        &self,
        signature: Signature,
        highest_confirmed_slot: Slot,
    ) -> Result<Option<ConfirmedTransactionWithStatusMeta>> {
        let max_root = self.max_root();
        let confirmed_unrooted_slots: HashSet<_> =
            AncestorIterator::new_inclusive(highest_confirmed_slot, self)
                .take_while(|&slot| slot > max_root)
                .collect();
        self.get_transaction_with_status(signature, &confirmed_unrooted_slots)
    }
