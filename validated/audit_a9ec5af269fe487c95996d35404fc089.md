### Title
Multisig confirmations from removed access keys remain counted toward the confirmation threshold, allowing a request to execute below the intended number of live signers - ([File: multisig/src/lib.rs])

### Summary
The `MultiSigContract::confirm` function counts the size of the `confirmations: HashSet<PublicKey>` for a request against `num_confirmations` without verifying that each recorded public key is still a valid, live access key on the multisig account. When a key that has already confirmed a still-pending request is later removed via a `DeleteKey` action on a *different* request, its earlier confirmation is never purged from the pending request's confirmation set, so it continues to count toward the threshold even though it no longer represents a live, authorized signer.

### Finding Description
`confirm()` reads the confirmations already recorded for a request and executes it once the size reaches `num_confirmations`: [1](#0-0) 

The only cleanup of stale confirmations happens inside `execute_request`'s `DeleteKey` handling, and it is scoped to requests whose `signer_pk` (the request *creator*) equals the deleted key — it never scans other pending requests' `confirmations` sets for occurrences of the deleted key as a *confirmer*: [2](#0-1) 

Concretely, the binding that should hold is:
```
confirmations_counted(request) == live_access_keys_that_confirmed(request)
```
but the contract only guarantees `confirmations_counted(request) == keys_that_ever_confirmed(request)`, which can exceed the live set once a confirming key is removed while its confirmation on an unrelated, still-open request remains recorded.

`assert_valid_request` only checks that the call is a self-call (`predecessor_account_id == current_account_id`) and that the request/confirmations entries exist — it performs no liveness check against the confirming key: [3](#0-2) 

### Impact Explanation
This breaks the multisig's core authorization invariant: a request can be executed (transferring NEAR, deploying code, adding/deleting keys, etc.) with fewer *currently authorized* signers than `num_confirmations` requires, because a stale confirmation from a removed key is counted as if it were live. This is a direct instance of "a multisig request executed below threshold," which is explicitly listed as a Critical impact.

### Likelihood Explanation
No privileged role, redeploy, or out-of-scope actor is needed — only ordinary multisig lifecycle events that are expected to occur in the normal operation of any near/core-contracts multisig account:
1. Key `B` confirms pending request `R1` (created by key `A`), leaving `R1` with 1/`N` confirmations.
2. Independently, key `B` is removed from the account through a separate, unrelated `DeleteKey` request (e.g., as part of routine key rotation or an employee offboarding) — a normal, legitimate multisig action.
3. `R1`'s confirmation set still contains `B`'s public key because `execute_request`'s `DeleteKey` branch only removes requests *signed by* `B`, not confirmations *by* `B` on other requests.
4. Remaining live keys confirm `R1`; once `confirmations.len() + 1 >= num_confirmations`, `R1` executes — even though one of the counted confirmations (`B`) is no longer a valid signer, meaning only `num_confirmations - 1` live keys actually authorized it.

This requires only routine key removal timed relative to a pending request, which is a realistic and easily reproducible sequence rather than a contrived edge case.

### Recommendation
When a `DeleteKey` action executes, purge the deleted public key from the `confirmations` set of *every* pending request (not just requests it created), or alternatively validate at `confirm()`/execution time that all public keys already present in a request's confirmation set still correspond to keys currently authorized on the account before counting them toward `num_confirmations`.

### Proof of Concept
```
Setup: multisig account with keys A, B, C, D; num_confirmations = 3.

1. A: add_request(Transfer{...}) -> request R1 created (signer_pk=A), 0 confirmations.
2. B: confirm(R1) -> confirmations(R1) = {B}  (1/3)
3. Separately, some quorum executes DeleteKey{public_key: B} via a different request R2
   (R2.signer_pk != B, so R1 is untouched; confirmations(R1) still = {B}).
4. C: confirm(R1) -> confirmations(R1) = {B, C} (2/3)
5. D: confirm(R1) -> confirmations.len()+1 == 3 >= num_confirmations -> execute_request(R1) runs.

Result: R1 executes with only C and D as live signers (B was removed in step 3),
i.e., the request was authorized by 2 live keys even though num_confirmations=3.
```

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
