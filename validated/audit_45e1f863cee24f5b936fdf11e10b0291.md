### Title
Symlink target (Linkname) in tar.zst archives is never validated against extraction root, allowing creation of dangling symlinks pointing outside the job workspace - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
The `(*extractor).Extract` function validates that the *symlink entry's own path* (`hdr.Name`) resolves inside `e.dir` (lines 57-64), but it never validates `hdr.Linkname` — the symlink's *target* — before calling `os.Symlink(hdr.Linkname, path)` in the deferred-processing loop (lines 113-117). A crafted cache/artifact archive can therefore create a symlink inside the job workspace whose target is an absolute path or a relative path with `../` traversal pointing to any file readable by the job process, e.g. `/etc/gitlab-runner/config.toml` or a mounted CI token file.

### Finding Description
In the first pass of `Extract` (lines 43-105), each tar header's own path is Abs-joined against `e.dir` and checked with `strings.HasPrefix(path, e.dir+separator)` (lines 57-64) — this guards where the entry is *written*, not what a symlink *points to*. When the entry is a symlink (`fi.Mode()&os.ModeSymlink != 0`), it is only queued into the `deferred` map (lines 75-77) and processed later at lines 107-117:

```go
if fi.Mode()&os.ModeSymlink != 0 {
    if err := os.Symlink(hdr.Linkname, path); err != nil {
        return err
    }
}
```

`hdr.Linkname` comes directly from the attacker-controlled tar stream and is passed to `os.Symlink` unchecked — there is no equivalent `filepath.Abs`/`HasPrefix` validation applied to it as is done for `hdr.Name`. Because `path` (the symlink's own location) is already confirmed to be inside `e.dir`, the symlink file itself is created inside the workspace, but it can point anywhere on the filesystem, including outside the workspace and outside any chroot/sandbox the extraction root represents.

An attacker who controls a cache key/artifact (any pipeline author, since cache/artifact archives are runner-side, cross-job/cross-pipeline content the user fully controls) can craft a tar entry with `Typeflag=Symlink` and `Linkname="../../../etc/gitlab-runner/config.toml"` (or an absolute path). When this cache is restored in a later job, the extractor creates that dangling/escaping symlink inside the job's working directory without error. A subsequent job script step that does `cat path/to/symlink` will read and print the contents of the target file into the job trace — a value the masker has no knowledge of (since it was never a known CI/CD variable), so it is exfiltrated unmasked into build logs.

This is a real gap since the review of the archiver counterpart (`tarzstd_archiver.go`) shows only the *own* path is checked when writing entries (mirroring the same pattern), and no other check in `Extract` restricts `Linkname`.

### Impact Explanation
An unprivileged pipeline author can exfiltrate arbitrary files readable by the job process's user/filesystem namespace (e.g. runner config, mounted secrets, sibling project files if paths are shared) by embedding a malicious symlink in a cache or artifact archive and then reading through it in a later step. This is a workspace-escape / secret-exfiltration primitive scoped exactly to "extracted archive entries resolving outside `e.dir` via symlink targets."

### Likelihood Explanation
Feasible and repeatable: any GitLab user who can push a `.gitlab-ci.yml` and control `cache:`/`artifacts:` restore in a job can craft the malicious tar.zst payload (trivial with Go's `archive/tar` package to write a `tar.Header{Typeflag: tar.TypeSymlink, Linkname: "../../secret"}`), upload it as a cache/artifact, then in a subsequent job (or step) that restores this cache, run a shell command to read the symlink target. No special privileges, executor misconfiguration, or admin cooperation are required.

### Recommendation
Validate `hdr.Linkname` the same way `hdr.Name` is validated before calling `os.Symlink`: resolve the target relative to the symlink's directory (or reject absolute targets outright), and reject if the resolved target escapes `e.dir`, mirroring the existing check at lines 62-64. At minimum, refuse absolute `Linkname` values and any relative target whose cleaned resolution (`filepath.Clean(filepath.Join(filepath.Dir(path), hdr.Linkname))`) does not have `e.dir` as a prefix.

```go
func TestExtractor_SymlinkEscape(t *testing.T) {
    dir := t.TempDir()
    var buf bytes.Buffer
    zw, _ := zstd.NewWriter(&buf)
    tw := tar.NewWriter(zw)
    _ = tw.WriteHeader(&tar.Header{
        Name:     "escape-link",
        Linkname: "../../../etc/passwd",
        Typeflag: tar.TypeSymlink,
        Mode:     0777,
    })
    tw.Close()
    zw.Close()

    r := bytes.NewReader(buf.Bytes())
    ext, _ := NewExtractor(r, int64(r.Len()), dir)
    err := ext.Extract(context.Background())
    require.NoError(t, err) // currently succeeds - should instead be rejected

    target, _ := os.Readlink(filepath.Join(dir, "escape-link"))
    require.True(t, strings.HasPrefix(target, dir), "symlink target %q escapes extraction dir %q", target, dir)
    // with the current code this assertion FAILS, proving the escape
}
```
