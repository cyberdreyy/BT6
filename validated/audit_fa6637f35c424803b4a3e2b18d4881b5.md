### Title
`getTokenLargestAccounts` silently treats unparseable token accounts as zero balance, misreporting largest-holder query results - (File: rpc/src/rpc.rs)

### Summary
`JsonRpcRequestProcessor::get_token_largest_accounts` unpacks each SPL token account returned by the mint filter and, if the unpack fails, silently substitutes a balance of `0` instead of surfacing an error or skipping the account, mirroring the reported bug class where an oracle/data-source failure is silently coerced to zero and propagated into a downstream calculation that clients trust as authoritative.

### Finding Description
In `get_token_largest_accounts`, each candidate account's balance is computed as: [1](#0-0) 

`StateWithExtensions::<TokenAccount>::unpack(account.data()).map(|account| account.base.amount).unwrap_or(0)` — if the account fails to unpack as a `TokenAccount` (e.g. it's a different-length/garbage-owned account or a token-2022 extension layout the decoder doesn't handle), the code does not return an RPC error and does not exclude/flag the entry; it silently records the balance as `0`, exactly the same "silent-zero-on-failure" pattern as `ChainlinkPriceFeed.getPriceAt()` returning `0` on failure. This value is then inserted into the `token_balances` max-heap used to compute the top `NUM_LARGEST_ACCOUNTS` holders and is returned to the unprivileged JSON-RPC caller: [2](#0-1) 

Because the (address, 0) entry competes in the same heap as genuine balances, it will generally just be dropped for being smaller than real large balances — but if a legitimately large-balance account fails the unpack (for example, `get_filtered_spl_token_accounts_by_mint` matches accounts by locating the mint bytes at a fixed offset, which can spuriously match non-`TokenAccount` data of the same or greater length whose layout differs, e.g. token-2022 multisig/extension records), the caller is given a wrong ("0") balance for that address, and the true top-N largest-holder result is silently corrupted for the query, all without any error indication to the client — the same "wrong answer with no error" outcome flagged in the report.

### Impact Explanation
This affects an unprivileged read-only RPC method (`getTokenLargestAccounts`) that any client can call. The RPC method can return a wrong-account-data result (misrepresenting a token holder's balance as zero and thus corrupting the "largest accounts" ranking) with no error signaled to the caller, which is the "wrong-slot/fork/account data returned" class explicitly called out as an acceptable impact target for this scan.

### Likelihood Explanation
Likelihood of triggering with a genuinely mis-decoded but real, larger-than-heap-threshold balance is low in normal conditions, since the mint-filter in `get_filtered_spl_token_accounts_by_mint` is designed to match legitimate SPL/Token-2022 layout accounts; failures would primarily occur on adversarially/incidentally-crafted account data owned by the token program that happens to match the mint-offset filter but not unpack cleanly (e.g. crafted extension data or corrupted accounts), which is a plausible but not everyday occurrence.

### Recommendation
Do not coerce unpack failures to `0`; instead skip the account from the ranking (do not insert it into the heap at all) or return an internal error for the request so RPC clients are not silently given an inaccurate "largest accounts" answer that discards a real balance.

### Proof of Concept
Not independently reproduced here; the root-cause defect is demonstrated purely from the source at [1](#0-0) , where any `Err` result from `StateWithExtensions::<TokenAccount>::unpack` is mapped to `unwrap_or(0)` rather than propagated or filtered, analogous to the reported `getPriceAt` pattern `success ? roundData.answer : 0`. A concrete end-to-end PoC would require constructing a program-owned account matching the mint filter that fails `TokenAccount::unpack`, which was not further validated within the scope of this scan.
