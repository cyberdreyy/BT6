### Title
Uncapped `Withdrawal.amount` committed to `payload_expected_withdrawals` for builder pending withdrawals mints Gwei not backed by any deducted balance - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas fork, `get_builder_withdrawals` copies the *requested* `amount` field from `state.builder_pending_withdrawals` verbatim into the `Withdrawal` objects that become `state.payload_expected_withdrawals` — the field the execution layer is contractually required to honor. However, `apply_withdrawals` caps the corresponding CL-side deduction from the builder's registry balance at `min(withdrawal.amount, builder_balance)`. When a builder's registered balance is smaller than the pending withdrawal's requested amount, the beacon state removes only the capped amount from `state.builders[...].balance`, while the EL-facing `Withdrawal.amount` — and thus the ETH the execution layer must credit to `fee_recipient` — remains the full, uncapped, un-backed requested amount.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md) builds each `Withdrawal` directly from `state.builder_pending_withdrawals` with no balance check: [1](#0-0) 

That list is later applied via the modified `apply_withdrawals`, which — unlike ordinary validator withdrawals handled by `decrease_balance` — explicitly clamps the balance deduction to what's actually available: [2](#0-1) 

`process_withdrawals` documents that the resulting `payload_expected_withdrawals` list is binding on the execution layer: [3](#0-2) 

The spec's own test suite makes the mismatch explicit: with a builder balance of 1 ETH and a pending withdrawal requesting 5 ETH, the resulting `Withdrawal.amount` committed to `payload_expected_withdrawals` is asserted to be the full 5 ETH (`withdrawal_amounts_builders={builder_index: withdrawal_amount}`), while the builder's CL balance is only reduced to 0 (1 ETH deducted): [4](#0-3) 

This breaks the equality that every Gwei paid out via `payload_expected_withdrawals` must be backed by an equal reduction in some tracked balance (validator `balances[]` or `builders[*].balance`). Here, 4 ETH is committed for EL payout with no corresponding CL-side balance decrease — Gwei effectively created and paid to the withdrawal's `fee_recipient`, who need not be the entity that ever held that value.

Contrast this with the validator-side partial withdrawal path (`get_pending_partial_withdrawals`, inherited from Electra), which explicitly clamps the *committed* withdrawal amount before it is ever placed into the withdrawals list: [5](#0-4) 
`get_builder_withdrawals` has no analogous clamp — the cap only happens after the fact, inside `apply_withdrawals`, which affects the CL balance but not the EL-bound `Withdrawal.amount` that was already fixed by `get_builder_withdrawals`/`update_payload_expected_withdrawals`.

A concrete state where a builder's balance is smaller than a pending withdrawal's requested amount is reachable without any malicious peer: multiple `BuilderPendingWithdrawal` entries can accumulate for the same builder (as shown by `test_duplicate_builder_index_in_pending_withdrawals`), and `apply_withdrawals` processes them sequentially against a balance that is mutated in place — so once an earlier entry in the same block drains the balance, every subsequent entry for that builder in `state.builder_pending_withdrawals` still contributes its full, uncapped `amount` to `payload_expected_withdrawals` even though nothing further is deducted from `builders[*].balance`. [6](#0-5) 

### Impact Explanation
This is a Critical-severity issue under "Gwei created, destroyed or paid to a non-owner" and "a payload executed or paid that the block did not commit to" — actually here it's the opposite: a payload paid that the CL balances do not back. Because `payload_expected_withdrawals` is spec-mandated to be honored by the execution layer, any execution client that follows the spec would credit the full uncapped amount to `fee_recipient`, inflating total ETH supply beyond what beacon-chain balances/builder registry account for, while all spec-following consensus clients agree on the (smaller) CL-side deduction. This is a direct, protocol-level supply invariant violation, not merely a documentation nit.

### Likelihood Explanation
No malicious peer, coalition, or client bug is required — only that a builder's tracked balance fall below the sum of its currently queued `builder_pending_withdrawals` entries at processing time, which can occur through ordinary sequential processing of multiple pending withdrawals for the same builder within `apply_withdrawals`, since the cap is enforced per-entry against a balance that is already being drawn down by earlier entries in the same call.

### Recommendation
Cap the `amount` written into the `Withdrawal` object in `get_builder_withdrawals` to the builder's actual available balance at the time it is enqueued (mirroring the electra approach in `get_pending_partial_withdrawals`, e.g. `amount = min(withdrawal.amount, remaining_balance)`, tracking `remaining_balance` decremented across iterations for the same builder), so the value committed to `payload_expected_withdrawals` can never exceed what `apply_withdrawals` actually removes from `state.builders[*].balance`.

### Proof of Concept
1. Builder `B` has `balance = 1 ETH`.
2. Two `BuilderPendingWithdrawal` entries for `B` are queued (e.g., from two settled bids), each requesting `amount = 3 ETH` (only individually checked against balance at queuing time, per `process_execution_payload_bid`'s per-bid check).
3. In a single call to `process_withdrawals`:
   - `get_builder_withdrawals` emits two `Withdrawal` objects, each with `amount = 3 ETH`, into `payload_expected_withdrawals` (see `specs/gloas/beacon-chain.md:1815-1834`).
   - `apply_withdrawals` processes them sequentially: first iteration deducts `min(3 ETH, 1 ETH) = 1 ETH`, leaving `balance = 0`; second iteration deducts `min(3 ETH, 0) = 0` (`specs/gloas/beacon-chain.md:1923-1931`).
4. Result: `state.builders[B].balance` decreased by only 1 ETH total, but `payload_expected_withdrawals` commits the execution layer to pay out `3 ETH + 3 ETH = 6 ETH` to the withdrawal's `fee_recipient` — 5 ETH of which is unbacked, matching the pattern already demonstrated in isolation by `test_builder_withdrawal_insufficient_balance` (`tests/.../test_process_withdrawals.py:114-156`).

##### New `get_builders_sweep_withdrawals`

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
