### Title
A single un-claimed queue deposit permanently bricks `stopEpoch` on the prefunded variant, freezing all pool funds - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external report is a low-privileged network DoS that makes the server hang/crash. The closest analog in this codebase is a liveness failure with fund impact: on `IdleCDOEpochVariantPrefunded`, the atomic stop-epoch path calls `IdleCDOEpochQueue.processPrefundedDeposits`, which reverts whenever `epochPendingDeposits[_epoch] != 0` (`_checkNotAllowed(epochPendingDeposits[_epoch] != 0 || _prefunded == 0)` at `contracts/IdleCDOEpochQueue.sol:265`). Any unprivileged KYC'd user can leave a dust deposit sitting in `epochPendingDeposits` (a deposit made inside the deposit window that the manager never prefunds, since `processDepositsToBorrower` is optional and window-gated at `contracts/IdleCDOEpochQueue.sol:159-168`). Once the prefunded window closes (`block.timestamp + prefundedDepositWindow >= epochEndDate`), `processDepositsToBorrower` can never move it to `epochPrefundedDeposits` again, and `processPrefundedDeposits` reverts forever — so `stopEpoch` reverts forever, `isEpochRunning` stays true, and all tranche holders' principal and the pending withdraw receipts are permanently frozen.

### Finding Description
- `IdleCDOEpochVariantPrefunded` settles queued deposits inside `stopEpoch` by calling `queue.processPrefundedDeposits(minted)`; the queue reverts unless `epochPendingDeposits[_epoch] == 0 && epochPrefundedDeposits[_epoch] != 0` (`contracts/IdleCDOEpochQueue.sol:261-265`).
- Moving pending → prefunded requires `processDepositsToBorrower()`, callable only while the epoch is running and only before the cutoff `block.timestamp + prefundedDepositWindow < epochEndDate` (`contracts/IdleCDOEpochQueue.sol:158-164`). After that point the pending bucket is unreachable for prefunding.
- `deleteRequest(_requestEpoch)` is the only other way to clear `epochPendingDeposits`, and it only clears `msg.sender`'s entry (`contracts/IdleCDOEpochQueue.sol:184-198`) — the attacker simply never calls it.
- Result: `stopEpoch`/`stopEpochWithDuration` (`contracts/IdleCDOEpochVariant.sol:322-506`) reverts in every subsequent attempt, `isEpochRunning` remains true, deposits stay paused, `allowAA/BBWithdrawRequest` remain false, and claims of previously funded withdraw receipts that depend on epoch progression are stuck. Borrower repayment becomes irrelevant because the revert happens inside the epoch state machine, not the token transfer.

### Impact Explanation
Permanent freezing of the entire pool: LP principal, accrued interest, and pending withdraw receipts. With a dust deposit (e.g. 1 wei of underlying) an unprivileged lender converts an honest operational gap (manager did not prefund before the cutoff) into an irreversible halt of the epoch machine. This is a fund-impacting DoS, matching the CVE's availability-only profile.

### Likelihood Explanation
High feasibility for the attacker (one `requestDeposit`, then inaction), but it depends on the honest manager not calling `processDepositsToBorrower` before the cutoff — prefunding is optional, not automatic. If the deployment sets `prefundedDepositWindow` close to `epochDuration`, or the manager is simply inactive, a single queued dust deposit bricks the vault. Note uncertainty: this hinges on `requestDeposit` permitting a deposit that can survive un-prefunded past the cutoff — the code shows the cutoff is enforced for prefunding (`contracts/IdleCDOEpochQueue.sol:164`) and comments state the same cutoff gates new deposits; if deposits are truly blocked once inside the window, the attack reduces to "deposit just before the cutoff in the same block the window closes," which is still feasible via back-to-back transactions.

### Recommendation
Make the stop path tolerant of stale queue-held deposits: in `processPrefundedDeposits`, refund-or-roll `epochPendingDeposits[_epoch]` into the next epoch (or auto-refund to users) instead of reverting when it is non-zero but `epochPrefundedDeposits[_epoch] > 0` or when the window has passed. Alternatively let `stopEpoch` permissionlessly sweep/refund leftover pending deposits, or hard-block `requestDeposit` once `block.timestamp + prefundedDepositWindow >= epochEndDate` *and* allow anyone to clear stranded pending deposits after the window.

### Proof of Concept
Foundry fork sketch:

```solidity
// Setup: prefunded CDO variant + AA queue enabled, epoch running.
// 1. Attacker (KYC'd) queues a dust deposit while epoch is running.
queue.requestDeposit(1);                       // epochPendingDeposits[next] = 1
uint256 requestEpoch = strategy.epochNumber() + 1;

// 2. Manager never calls processDepositsToBorrower (optional path);
//    time passes until prefund window is closed.
vm.warp(cdoEpoch.epochEndDate() - PREFUNDED_DEPOSIT_WINDOW);

// 3. Prefunding is now impossible.
vm.expectRevert(NotAllowed.selector);
vm.prank(manager);
queue.processDepositsToBorrower();

// 4. Epoch ends; every stopEpoch reverts inside processPrefundedDeposits
//    because epochPendingDeposits[requestEpoch] != 0.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(newApr, 0);                  // permanent

// 5. isEpochRunning stays true forever -> deposits paused,
//    withdraw requests disabled, LP funds frozen.
assertTrue(cdoEpoch.isEpochRunning());
```
