### Title
Unbounded zstd compression cost in `encode_ui_account` for `base64+zstd` account encoding - ([File: account-decoder/src/lib.rs])

### Summary
`encode_ui_account`'s `UiAccountEncoding::Base64Zstd` branch runs `zstd::stream::write::Encoder` over the full (optionally sliced) account data with no size cap, unlike the `Base58`/`Binary` paths which reject data over `MAX_BASE58_BYTES`. Since accounts can hold up to `MAX_ACCOUNT_DATA_LEN`/`MAX_PERMITTED_DATA_LENGTH` (10 MiB) of attacker-controlled bytes, a single `getAccountInfo`/`getMultipleAccounts` call with `encoding=base64+zstd` forces the validator's JSON-RPC worker to zstd-compress up to 10 MiB (times the number of pubkeys in `getMultipleAccounts`) synchronously on the request-handling thread.

### Finding Description
`encode_ui_account` in [1](#0-0)  handles `UiAccountEncoding::Base64Zstd` by calling `zstd::stream::write::Encoder::new(Vec::new(), 0)` and writing the entire `slice_data(account.data(), data_slice_config)` output into it, with no length check before compressing. Contrast this with the `Base58`/`Binary` path, `encode_bs58`, which explicitly checks `slice.len() <= MAX_BASE58_BYTES` and returns an error string instead of encoding oversized data [2](#0-1) .

The RPC entrypoint `encode_account` in `rpc/src/rpc.rs` only enforces the `MAX_BASE58_BYTES` guard for `Binary`/`Base58` encodings; for any other encoding (including `Base64Zstd`) it calls `encode_ui_account` unconditionally [3](#0-2) . `get_encoded_account`, used by `getAccountInfo`/`getMultipleAccounts`, calls `encode_account` directly for non-JsonParsed-SPL-token cases [4](#0-3) .

An account's data length can legitimately reach `MAX_PERMITTED_DATA_LENGTH` / `MAX_ACCOUNT_DATA_LEN` (10 MiB), which is a normal, unprivileged, on-chain-writable value enforced elsewhere in the runtime (e.g., `system_processor::allocate`, BPF loader extend/create checks) [5](#0-4) [6](#0-5) . Any unprivileged actor can fund and grow an account (via `Allocate`/`CreateAccount`/BPF loader `ExtendProgram`, all within normal transaction limits) to this size, then repeatedly (subject to the one-call-per-slot constraint) call `getAccountInfo` or `getMultipleAccounts` with `encoding=base64+zstd` against that pubkey, forcing the validator to run a zstd compression pass over up to 10 MiB (or more for `getMultipleAccounts` with multiple large pubkeys) on the RPC worker thread every single call. There is no explicit cost bound, timeout, or size threshold gating this — the cost scales linearly (or worse, depending on zstd's algorithmic behavior on the data pattern) with attacker-controlled on-chain data size, unlike the base58 path which has an explicit ceiling.

### Impact Explanation
This falls under "RPC/validator resource exhaustion from a single low-rate request" — unbounded CPU/memory cost per request scaling with attacker-controlled state rather than a fixed cost bound. A single call can tie up an RPC worker thread compressing up to 10 MiB of data (and `getMultipleAccounts` can multiply this across several large accounts in one call), degrading RPC responsiveness for other users on that node. This does not crash or corrupt consensus state, but it is a genuine violation of "cost of one request must be bounded by explicit limits," matching the "unbounded per-request cost from on-chain data" bounty category referenced in the prompt.

### Likelihood Explanation
Feasibility is high and repeatable: growing an account to `MAX_PERMITTED_DATA_LENGTH` requires only ordinary system/BPF-loader instructions available to any funded account owner, no special privilege. Once such an account exists on-chain (which can be publicly discovered or self-created), any client can issue `getAccountInfo`/`getMultipleAccounts` with `encoding=base64+zstd` at the permitted rate (≤ one call per `CLUSTER_SLOT_TIME_TARGET / 2`) and reliably trigger the same maximal compression cost every time, since nothing memoizes or caches the encoded result.

### Recommendation
Apply an explicit size guard to the `Base64Zstd` branch in `encode_ui_account` (or in `encode_account` in `rpc/src/rpc.rs`) similar to the `MAX_BASE58_BYTES` check for `Base58`/`Binary`: reject or fall back to plain `Base64` when `slice_data(...).len()` exceeds a bounded threshold (e.g., a configurable max, or the existing RPC response size limits), so the zstd compression cost is capped independent of on-chain account size.

### Proof of Concept
Add a benchmark/unit test in `account-decoder/src/lib.rs` (extending the existing `test_base64_zstd` test) that measures wall-clock time and peak memory of `encode_ui_account` with `UiAccountEncoding::Base64Zstd` for data sizes of 1 KiB, 1 MiB, and 10 MiB (`MAX_PERMITTED_DATA_LENGTH`):

```rust
#[test]
fn test_base64_zstd_cost_scales_unbounded() {
    for size in [1024, 1024 * 1024, 10 * 1024 * 1024] {
        let data = vec![0u8; size];
        let account = AccountSharedData::from(Account { data, ..Account::default() });
        let start = std::time::Instant::now();
        let _ = encode_ui_account(
            &Pubkey::default(), &account, UiAccountEncoding::Base64Zstd, None, None,
        );
        let elapsed = start.elapsed();
        println!("size={size} elapsed={elapsed:?}");
        // Expected failing assertion: no cap exists, so elapsed grows roughly linearly
        // with size instead of being bounded by a fixed ceiling or rejected outright.
    }
}
```
Expected result confirming the bug: no error/rejection occurs at 10 MiB, and elapsed time/memory grows with size, demonstrating the RPC-facing `encode_account`/`get_encoded_account` path in `rpc/src/rpc.rs` has no equivalent guard to the `MAX_BASE58_BYTES` check for this encoding.

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
```
