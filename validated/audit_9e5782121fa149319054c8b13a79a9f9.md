### Title
Stale rejection weight is never cleared when a signer later accepts a block, permanently corrupting the node's approval/rejection tally — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` maintains two independent per-block weight counters, `total_weight_approved` and `total_weight_rejected`, gated by two *different* mechanisms. The `Rejected` branch gates its weight increment on `block.responded_signers.insert(slot_id)` (only counts the first response ever seen from that slot), while the `Accepted` branch gates its weight increment on `block.gathered_signatures.contains_key(&slot_id)` — a completely separate set. A signer that first rejects and later legitimately re-evaluates and accepts the same block (a documented, expected flow in the v0 signer) gets its weight added to `total_weight_rejected` *and*, independently, to `total_weight_approved`, with no mechanism to roll back the earlier rejection weight. This breaks the equality the node relies on ("rejected weight vs. still-live signers") and can wedge the tally for an otherwise-valid, fully-signed block.

### Finding Description
Two code paths in the same event loop: [1](#0-0) 
Acceptance path: weight is added to `total_weight_approved` gated only by `!block.gathered_signatures.contains_key(&slot_id)`, and `responded_signers.insert(slot_id)` is called unconditionally as a side effect, regardless of whether this slot already appears in `responded_signers` from an earlier rejection. [2](#0-1) 
Rejection path: weight is added to `total_weight_rejected` only `if block.responded_signers.insert(slot_id)` succeeds (i.e., only the *first* response from that slot ever counts toward `total_weight_rejected`).

Sequence that breaks the equality:
1. Signer S rejects block B for a transient/re-evaluable reason (e.g. `ConnectivityIssues`, `NoSignerConsensus`, or any `RejectReason` covered by `should_reevaluate_reject_reason`, as documented in `docs/signer-flows.md` section 3). The node's listener records this: `responded_signers` now contains S's slot, and `total_weight_rejected += S.weight`.
2. S re-evaluates (per the documented `should_reevaluate_block`/`should_reevaluate_reject_reason` path in `stacks-signer/src/v0/signer.rs`) and legitimately signs/accepts B once conditions resolve, broadcasting a `BlockAccepted`.
3. The listener's `Accepted` branch checks only `gathered_signatures` (empty for S so far) → adds S.weight to `total_weight_approved`. It does **not** check or clear S's earlier contribution to `total_weight_rejected`.
4. Result: S's weight is now counted in *both* `total_weight_approved` and `total_weight_rejected` for the same block, permanently. There is no code path that ever decrements `total_weight_rejected` when a signer's vote is superseded.

This is directly reachable by a single miner/proposal + normal signer gossip: no majority of signers or possession of another signer's key is needed — it only requires one signer that transiently rejects (for a re-evaluable reason) and later accepts the same block, which is an explicitly supported and expected transition in this codebase (see `docs/signer-flows.md`, "prior reject reason re-evaluable? `should_reevaluate_reject_reason`").

### Impact Explanation
The coordinator's "block is dead" signal is: `block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` ( [3](#0-2) ). Because rejected weight can never be retracted even after the same signer flips to accept, `total_weight_rejected` accumulates stale contributions from signers who have since approved the block. This can cause the coordinator to conclude a block has crossed the "impossible to reach 70%" threshold and abandon it (`cvar.notify_all()` on the rejection branch) even while `total_weight_approved` is independently climbing toward (or has already reached) the real 70% threshold from the *same* signers' later, superseding acceptances. This is a liveness wedge: a fully valid, correctly-signed block can be treated by the miner/coordinator as globally dead due to permanently "double-booked" signer weight, stalling tenure progress — without requiring a majority of colluding signers, just one signer whose vote legitimately flips from reject to accept.

### Likelihood Explanation
The reject→accept transition is not a hypothetical edge case; it is an explicitly designed and tested signer behavior (`should_reevaluate_reject_reason`, `should_reevaluate_block` in `stacks-signer/src/v0/signer.rs`, documented in `docs/signer-flows.md` section 3). Any transient rejection reason (connectivity hiccup, momentary lack of signer-protocol-version consensus, a stale sortition view that later refreshes) that a single signer experiences before ultimately accepting a valid block triggers this in the node's tally logic. No attacker action or malicious behavior is required — a single honest signer's normal retry path is sufficient.

### Recommendation
Make the rejection and acceptance weight bookkeeping symmetric and mutually exclusive per slot: track a signer's *current* vote (accept/reject) per slot in a single map, and when a slot's vote changes, subtract its weight from the previous tally before adding it to the new one (or simply always recompute both totals from the current map of per-slot votes instead of monotonically-accumulating counters gated by different membership sets).

### Proof of Concept
1. Node proposes block B to a signer set including signer S (weight w).
2. S sends `BlockResponse::Rejected` for B for a re-evaluable reason (e.g., a transient `ConnectivityIssues`/`NoSignerConsensus` rejection). Listener: `total_weight_rejected += w`, `responded_signers = {S}`.
3. Conditions resolve; S's local state machine re-evaluates B (per `should_reevaluate_reject_reason`) and now signs it, broadcasting `BlockResponse::Accepted`.
4. Listener's Accepted handler: `gathered_signatures` does not yet contain S's slot → `total_weight_approved += w`; `responded_signers.insert(S)` is a no-op since S is already present.
5. Final state: `total_weight_rejected` still includes `w` from step 2 (never cleared) while `total_weight_approved` also includes `w` from step 4 — S's weight is counted in both tallies simultaneously, and if enough such flips accumulate, `total_weight_rejected` can spuriously cross the "globally dead" threshold even as `total_weight_approved` crosses the acceptance threshold for the same valid block.
