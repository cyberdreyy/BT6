### Title
Cross-Chain Nonce Collision in `isTransferProcessed` Enables Permanent Fund Lock — (`bridge/evm/contracts/SuiBridge.sol`)

### Summary

The `SuiBridge` contract tracks processed token-transfer messages using a mapping keyed solely by `message.nonce` (a `uint64`). Because the `MessageVerifier` modifier explicitly skips the sequential nonce check for `TOKEN_TRANSFER` messages, and because the processed-flag map does not include the source `chainID` in its key, two legitimate transfers originating from different source chains that happen to share the same nonce value will collide: the first one processed marks `isTransferProcessed[nonce] = true`, permanently blocking the second one even though it carries valid committee signatures and represents a distinct, legitimate cross-chain transfer.

### Finding Description

`MessageVerifier.verifyMessageAndSignatures` deliberately omits the sequential nonce enforcement for `TOKEN_TRANSFER` messages:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(message.chainID == committee.config().chainID(), ...);
    require(message.nonce == nonces[message.messageType], ...);
    nonces[message.messageType]++;
}
``` [1](#0-0) 

Instead, `SuiBridge.transferBridgedTokensWithSignatures` (and its V2 counterpart) relies on a per-nonce boolean flag:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [2](#0-1) 

The replay guard and the mark-as-processed step both use only `message.nonce` as the key:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
...
isTransferProcessed[message.nonce] = true;
``` [3](#0-2) 

The same pattern is present in `SuiBridgeV2`: [4](#0-3) 

The `message.chainID` field identifies the **source** chain of the transfer. The bridge is designed to accept transfers from multiple supported source chains (the `onlySupportedChain` modifier validates that the source chain is in the supported set): [5](#0-4) 

Because nonces are assigned independently per source chain, two different source chains will inevitably produce transfers with the same nonce value (e.g., both chain A and chain B will eventually emit a transfer with `nonce = 1`). The first one to be claimed on the EVM side sets `isTransferProcessed[1] = true`; the second one — carrying a completely different, valid committee signature over a different message hash — is then permanently rejected.

The message encoding does include `chainID` in the signed bytes, so the committee signatures themselves are not interchangeable: [6](#0-5) 

The bug is not signature replay in the classical sense; it is a **nonce-namespace collision**: the processed-flag map conflates nonces from different source chains into a single flat namespace, so a nonce consumed by chain A silently invalidates the same nonce from chain B.

### Impact Explanation

Any token transfer originating from a source chain whose nonce collides with an already-processed nonce from another source chain is permanently unclaimable on the EVM side. The tokens were already locked or burned on the source chain; they can never be recovered. This constitutes **permanent fund lock** for legitimate bridge users.

### Likelihood Explanation

The bridge contract is designed to support multiple source chains simultaneously (`isChainSupported` accepts a list). Nonce sequences on independent chains are monotonically increasing from 0 and will overlap at every integer. The collision is therefore **certain** once the bridge is configured with more than one active source chain, and requires no malicious actor — only two ordinary bridge users on different source chains.

### Recommendation

Key the processed-flag map by `(chainID, nonce)` rather than `nonce` alone:

```solidity
mapping(uint8 chainID => mapping(uint64 nonce => bool)) public isTransferProcessed;
```

Update all reads and writes accordingly:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
...
isTransferProcessed[message.chainID][message.nonce] = true;
```

This mirrors the correct pattern used by the Move-side bridge, which keys transfer records by `BridgeMessageKey { source_chain, message_type, bridge_seq_num }`: [7](#0-6) 

### Proof of Concept

1. Deploy `SuiBridge` configured to support two source chains: chain A (`chainID = 0`) and chain B (`chainID = 1`).
2. A user on chain A locks tokens; the committee signs a `TOKEN_TRANSFER` message with `chainID = 0, nonce = 1`. The claim succeeds; `isTransferProcessed[1] = true`.
3. A different user on chain B locks tokens; the committee signs a `TOKEN_TRANSFER` message with `chainID = 1, nonce = 1` (a completely different message hash and different committee signatures).
4. The chain B user calls `transferBridgedTokensWithSignatures` with the valid chain-B signatures. The call reverts with `"SuiBridge: Message already processed"` because `isTransferProcessed[1]` is already `true`.
5. The chain B user's tokens are permanently locked on chain B with no recourse.
