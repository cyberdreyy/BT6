### Title
Junior (BB) capital escapes the BB-first waterfall by converting to pending withdraw receipts, forcing pro-rata loss onto honest receipts and remaining active LPs - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external report describes an attacker with more funds forcing an honest defender to absorb loss by opening parallel loss-bearing games. The closest idle-tranches analog lives in the epoch-loss socialization path: `IdleCreditVault.requestWithdraw` strips tranche identity when a user requests a withdrawal, and `previewLossAdjustedWithdrawFunds` then splits any realized `stopEpochWithDuration` loss **pro rata** between the aggregate pending-receipt bucket and active LPs, with only the *active* remainder applied through the ordinary BB-first waterfall. A large BB holder can therefore move junior capital into the pending bucket during the epoch, escaping the junior-first ordering and diluting honest pending receipts (including former AA receipts) plus the remaining active LPs.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`, `requestWithdraw` (lines 243-295) burns the CDO's strategy tokens and mints a fungible receipt to the user while adding `_amount` to `pendingWithdraws`. The comment at line 391-392 of `IdleCDOEpochVariant.sol` states the design explicitly: "Pending receipts have no tranche identity, so their aggregate loss is pro rata across all receipts. The remaining active loss is applied BB-first."

When the owner/manager later calls `stopEpochWithDuration(_newApr, _interest, _duration, _lossAmount)`, `_stopEpoch` calls `previewLossAdjustedWithdrawFunds(_lossAmount)` (IdleCreditVault.sol lines 440-460), which computes:

- `pendingLoss = _lossAmount * pendingBasis / totalBasis` (line 457) — applied to *all* receipts equally via `lossRecoveryPriceByEpoch[epochNumber]` set in `collectWithdrawFunds` (lines 414-421).
- `activeLoss = _lossAmount - pendingLoss` (line 459) — burned via `_strategy.burnStrategyTokens` and `_forceUpdateAccounting()` at IdleCDOEpochVariant.sol lines 496-499, which realizes it through the BB-first waterfall.

So the protection ordering "BB absorbs losses before AA" is **only** enforced on the `activeLoss` portion. The `pendingLoss` portion is spread pro rata across all receipts regardless of whether they originated from AA or BB deposits.

Concretely: pool has 50 AA (honest) and 50 BB (attacker). The honest AA user requests a 10 withdrawal; the attacker requests withdrawal of all 50 BB. `pendingBasis = 60`, active basis = 40 AA. If a realized loss of 40 is then applied:

- `pendingLoss = 40 * 60/100 = 24` → honest AA receipt loses `10 * 24/60 = 4`, attacker loses `20`.
- `activeLoss = 16` → there is no active BB left; the 16 is burned from honest AA NAV via `_forceUpdateAccounting`.

Honest AA LPs lose 20 total. Without the attacker's maneuver, the waterfall would have burned all 40 from the attacker's BB and AA would have lost zero. The attacker effectively converted 20 units of junior liability into senior-borne loss — the same "richer attacker offloads losses onto honest participants" structure as the dispute-game report.

### Impact Explanation
Direct loss transfer: honest AA pending receipts and remaining active AA LPs absorb a loss that the documented waterfall assigns to BB first. In the example above the honest side loses 20/50 = 40% of honest NAV that should have been fully protected. The magnitude scales with the attacker's share of the pending bucket — the larger the attacker's requested BB position relative to honest pending receipts and active BB, the more loss is socialized into the pro-rata bucket.

### Likelihood Explanation
Requirements: the CDO must operate with the loss-bearing `stopEpochWithDuration` path, and the attacker must time a BB withdrawal request into the epoch before a stop that realizes a loss. Loss events are exactly when this is most dangerous (distressed borrower → manager stops epoch with `_lossAmount`). Withdrawal requests are permissionless to any tranche-token holder (`_onlyIdleCDO` only gates the vault function; the CDO exposes user-facing request functions), no KYC beyond the normal deposit whitelist is involved, and the attacker needs no privileged role — only more capital, matching the report's premise. The guard in `requestWithdraw` (line 263-271) only blocks *repeat* requests after a loss-adjusted epoch; it does not prevent the initial conversion.

Uncertainty I could not fully resolve in scope: whether the CDO's user-facing withdraw-request entrypoints restrict requests to the buffer window, and whether a manager would realistically pass a large `_lossAmount` while a huge pending bucket exists (the manager is honest but the code gives no protection). Neither changes the broken invariant — the pending bucket simply has no tranche identity to enforce BB-first ordering on.

### Recommendation
Retain tranche identity for pending receipts: record per-epoch pending basis split by origin tranche (e.g., `pendingAABasis`/`pendingBBBasis`, tracked at `requestWithdraw` time using the redeemed tranche), and in `previewLossAdjustedWithdrawFunds` apply the pending bucket's share of loss to BB-origin receipts first, cascading to AA-origin receipts only after BB-origin receipts are exhausted. Alternatively, disallow withdrawal requests once a loss-signaling event is pending, or cap `_lossAmount` application so pending receipts cannot receive a better recovery price than the most junior tranche class they originated from.
