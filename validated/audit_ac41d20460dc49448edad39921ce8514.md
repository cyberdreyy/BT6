## Finding

### Title
Single-purpose liveness timeout `tenure_last_block_proposal_timeout` is repurposed as the equivocation-guard freshness window for cross-tenure signed conflicts - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`tenure_last_block_proposal_timeout` is documented and tuned as a liveness/handoff knob: "Time to wait for the last block of a tenure to be globally accepted or rejected before considering a new miner's block at the same height as potentially valid" [1](#0-0) . The same value is silently reused inside `handle_block_pre_commit` as the freshness cutoff that decides whether a *previously signed, potentially cross-tenure conflicting* block still vetoes a new signature — the signer's anti-equivocation guard [2](#0-1) . These two uses have fundamentally different correctness requirements (miner-handoff convenience vs. equivocation safety), exactly the same class of defect as the referenced oracle-slippage bug where one slippage setting was repurposed for an unrelated ratio check.

### Finding Description
The setting is defined once, with a single semantic meaning tied to tenure-tip staleness for the `check_latest_block_in_tenure`/`get_tenure_last_block_info` code path: it decides how long a *signed tenure tip* remains authoritative before the signer falls back to asking the node [3](#0-2) . The config docs and the WARNING about tuning it only discuss this handoff/liveness tradeoff [4](#0-3) .

The very same duration, `self.proposal_config.tenure_last_block_proposal_timeout`, is reused inside `handle_block_pre_commit` to compute `freshness_cutoff`, which gates whether a *conflicting signed block in ANY tenure* (from `get_signed_conflicts`, spanning all tenures at or above the candidate height) still blocks the signer from placing a fresh signature on a competing block: [5](#0-4) 

Crucially, once a cross-tenure conflict is judged *stale* by this same cutoff, the code no longer verifies whether the conflicting block is actually dead/orphaned via `conflict_still_blocks`: the follow-up check at lines 1432-1457 only re-examines conflicts in the *same* tenure as the new block, and explicitly treats a stale conflict from another tenure as no longer speaking for the signer: [6](#0-5) 

So the entire equivocation defense for cross-tenure siblings collapses to a single time comparison keyed off a setting whose intended purpose and safe range were chosen for a different concern (tenure-tip handoff timing, default 30s, `DEFAULT_TENURE_LAST_BLOCK_PROPOSAL_TIMEOUT_SECS`) [7](#0-6) .

### Impact Explanation
An operator who lowers `tenure_last_block_proposal_timeout` to speed up legitimate miner handoffs (the documented, sanctioned tuning knob) simultaneously narrows the equivocation-guard window. Once a signed conflict crosses that (now shorter) age threshold, `handle_block_pre_commit` will sign a second, conflicting block at the same height in a different tenure without confirming the first block is actually dead/orphaned on-chain. This directly matches the Critical impact category of a signer signing a conflicting block, since a fresh signature over block A stops being defended purely because an unrelated liveness timer elapsed, not because block A's tenure was actually shown to be non-canonical.

### Likelihood Explanation
This does not require a majority of signers or any key compromise — a single miner (or a byzantine actor observing normal block timing) can simply delay a competing sibling proposal in a different tenure until just past `tenure_last_block_proposal_timeout` after the first block's signature timestamp (`last_endorsed`), which is entirely achievable with default settings (30s) and trivially achievable if the operator lowered the value for handoff-speed reasons as the docs suggest. No special access is needed beyond normal block-proposal gossip.

### Recommendation
Introduce a distinct configuration value (and cutoff computation) for the pre-commit equivocation-freshness window used in `handle_block_pre_commit`'s cross-tenure conflict check, separate from `tenure_last_block_proposal_timeout`, which should remain scoped to `get_tenure_last_block_info`/`check_latest_block_in_tenure`. Additionally, consider not exempting stale cross-tenure conflicts from the `conflict_still_blocks` liveness check — staleness of the local timestamp should not, by itself, prove the other tenure is orphaned.

### Proof of Concept
1. Signer signs block `A` in tenure `T1` at height `h` (endorsement time `t0` recorded as `last_endorsed`) via `handle_block_pre_commit`, reaching the pre-commit weight threshold [8](#0-7) .
2. An adversarial/competing miner delays a conflicting sibling block `B` at the same height `h` in a different tenure `T2` until `t0 + tenure_last_block_proposal_timeout` has elapsed (a value the operator may have tuned down for faster handoffs, or simply the 30s default).
3. When `B` reaches its own pre-commit threshold, `get_signed_conflicts` returns `A` as a conflict, but `conflict.last_endorsed > freshness_cutoff` is now false, so the `conflicts.iter().find(...)` at [9](#0-8)  does not trigger, and `conflict_still_blocks` is never consulted.
4. The subsequent check at [10](#0-9)  only inspects same-tenure conflicts, so the stale cross-tenure conflict with `A` is ignored entirely.
5. The signer proceeds to sign `B`, producing valid signatures over two conflicting blocks at the same height in different tenures — purely because a liveness-tuning timer elapsed, not because `A`'s tenure was proven non-canonical.

    /// Get the last signed block from the given tenure if it has not timed out.
    /// Even globally accepted blocks are allowed to be timed out, as that
    /// triggers the signer to consult the Stacks node for the latest globally
    /// accepted block. This is needed to handle Bitcoin reorgs correctly.
    ///
    /// The timeout window is measured from the last time a signature actually covered the
    /// block: our own (`signed_self`) or the observed group/global acceptance
    /// (`signed_group`), whichever is later, matching how `get_signed_conflicts` measures
    /// endorsement freshness. `approved_time` is deliberately not used: it is stamped at
    /// pre-commit, which carries no signature, so it would close the window early. This also
    /// means a globally accepted block we never signed ourselves gets a full window from the
    /// time its acceptance was observed, rather than timing out instantly for lack of a
    /// timestamp.
    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }
