### Title
Loss-adjusted withdraw receipts keyed to the pre-increment epoch are paid at par after `stopEpochWithDuration` losses - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records each user's withdraw-request epoch in `lastWithdrawRequest[_user]` at request time (`requestWithdraw`, line 282) and records the realized haircut in `lossRecoveryPriceByEpoch[epochNumber]` inside `collectWithdrawFunds` (line 421). `epochNumber` is incremented inside `deposit()` whenever the CDO deposits while `isEpochRunning()` is still true (lines 607-610) — i.e., during `stopEpoch`. If `collectWithdrawFunds` executes after the epoch-closing deposit (the normal funding order: borrower repays → CDO deposits → CDO collects for pending receipts), the haircut is stored under the *new* epoch number N+1, while every affected receipt is still keyed to epoch N. `_claimLossAdjustedWithdrawRequest` then reads `lossRecoveryPriceByEpoch[N] == 0` (lines 790-792) and the receipt falls through to `_claimFundedWithdrawRequest`, which pays the full basis at par.

### Finding Description
- At `requestWithdraw` time: `lastWithdrawRequest[_user] = epochNumber` (= N) and `withdrawsRequestsByEpoch[_user][N] += _amount` (lines 282-293).
- At stop: `deposit()` is called while `isEpochRunning()` is still true, so `epochNumber` becomes N+1 (lines 607-610). `collectWithdrawFunds(_amount < pendingBasis)` then stores `lossRecoveryPriceByEpoch[epochNumber]` = `lossRecoveryPriceByEpoch[N+1]` (line 421), not N.
- At claim: `claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = 0 → returns 0 → `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` in full (lines 338-349), burning receipts 1:1 despite the haircut.
- The same key mismatch disables the guard in `requestWithdraw` (lines 261-271): `lossRecoveryPriceByEpoch[N]` reads 0, so a user with a haircut receipt can open new requests and `lastWithdrawRequest` is overwritten, permanently losing the loss-epoch linkage.
- Symmetrically, any *later* epoch's receipts keyed to N+1 would read a nonzero `lossRecoveryPriceByEpoch[N+1]` and could be wrongly haircut or have claims misattributed across epochs (`_clearWithdrawClaimForEpoch`).

This mirrors the CVE-2019-0609 bug class: stale/mismatched object state (epoch-keyed receipt basis) causes use of an object after its accounting context changed, corrupting payout accounting.

### Impact Explanation
Direct theft / insolvency: after a `stopEpochWithDuration(_lossAmount)` that funds only part of `pendingWithdraws`, every pending receipt claims at par instead of at `lossRecoveryPrice`. The overpayment equals `pendingBasis * (1 - lossRecoveryPrice)` — e.g., a 50% haircut on 1M USDC of pending receipts overpays ~500k USDC, drained from strategy underlyings that back other claimants and the `defaultRecoveryReserve` (which `_transferFundedClaim` only protects partially, lines 899-905). If the strategy lacks funds, later claimants' transactions revert — permanent freezing of their receipts. Broken invariant: one receipt one (haircutted) payout; loss waterfall for pending receipts.

### Likelihood Explanation
Triggers on any `stopEpochWithDuration` with `_lossAmount > 0` and nonzero `pendingWithdraws`, in the standard epoch flow — no privileged misbehavior required. The attacker is any tranche-token holder with a pending withdraw request. The only precondition is that `collectWithdrawFunds` is invoked after the `deposit()` that increments `epochNumber` within `stopEpoch`/`stopEpochWithDuration`, which is the natural ordering since the CDO must deposit borrower repayments before pulling them into the strategy for receipts. Caveat: I could not fully trace the exact call order inside `IdleCDOEpochVariant.stopEpochWithDuration` in this pass; if `collectWithdrawFunds` provably runs before any `deposit()` in the same transaction, this finding does not hold.

### Recommendation
Key the loss recovery price to the epoch the receipts belong to, not the post-increment counter: store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or capture `epochNumber` before `deposit()` bumps it and pass it to `collectWithdrawFunds`), or increment `epochNumber` only after all stop-epoch receipt accounting completes. Add a regression test asserting that a partially funded epoch-N receipt claims exactly `basis * lossRecoveryPrice / 1e18`.

### Proof of Concept
```solidity
// Foundry fork test against the live vault deployment
function testLossReceiptPaidAtPar() public {
    // setup: Alice deposits AA, then requests withdraw in epoch N
    idleCDO.depositAA(1_000_000e6);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // lastWithdrawRequest[alice] = N
    vm.prank(manager);
    cdoEpoch.startEpoch();                            // borrower takes funds

    // stop with loss: borrower repays only 50% of pendingWithdraws
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = creditVault.pendingWithdraws();
    deal(underlying, borrower, expectedRepay);        // partial funding
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, duration);   // deposit() bumps epochNumber->N+1,
                                                      // collectWithdrawFunds stores price under N+1
    assertEq(creditVault.lossRecoveryPriceByEpoch(N), 0);        // receipt's epoch: no haircut
    assertGt(creditVault.lossRecoveryPriceByEpoch(N + 1), 0);    // stored under next epoch

    // Alice claims and receives FULL basis instead of 50%
    uint256 balBefore = underlying.balanceOf(alice);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(alice) - balBefore;
    assertEq(paid, pending);              // BUG: should be pending * recoveryPrice / 1e18
}
```
