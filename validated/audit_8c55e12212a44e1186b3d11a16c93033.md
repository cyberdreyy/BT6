### Title
Fee-on-transfer underlying mints unbacked tranche shares in `depositDuringEpoch` - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant.depositDuringEpoch` pulls `_amount` of underlying from the caller but computes the minted shares, the recorded principal, the minted strategy tokens, and the borrower forwarding all from the nominal `_amount`, never measuring the actual received balance. Every other deposit path in the codebase (`IdleCDO._deposit` at contracts/IdleCDO.sol:250-253, `IdleCDOCreditVault._deposit` at contracts/IdleCDOCreditVault.sol:203-206) uses a balance-before/after delta; this function does not. If the vault's underlying is a fee-on-transfer token (e.g. USDT with its fee mode enabled), the vault receives `_amount - fee` but the attacker is credited as if `_amount` arrived.

### Finding Description
In `depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:656-733):

1. `_transferUnderlyingsFrom(msg.sender, address(this), _amount)` at line 685 transfers the nominal amount — for a FOT token the contract balance increases by only `_amount - fotFee`.
2. `interest` and `trancheInterest` are computed on the full `_amount` (lines 693-713).
3. `_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal` mints shares for the full nominal principal plus prorated interest (line 724).
4. `IdleCreditVault(strategy).mintStrategyTokens(_amount)` mints strategy tokens for `_amount` (line 730).
5. `_transferUnderlyings(_borrower(), _amount)` forwards the full nominal `_amount` to the borrower (line 732), so the missing `fotFee` is taken from the CDO's own token balance (residual liquidity held for instant withdrawals / unswept funds), or the call reverts only if the CDO holds less than `fotFee`.

The broken invariant is fair mint/burn / solvency: shares backed by `_amount + trancheInterest` are issued while only `_amount - fotFee` of new value enters the system. The shortfall is silently covered by the vault's existing balance, i.e. by other tranche holders' NAV. `_skimDonatedAssets()` at line 679 runs before the transfer, so it does not protect this path — the deficit is created after the skim, inside the same call.

### Impact Explanation
Direct theft of vault funds equal to the FOT fee per deposit, repeatable every call while the epoch is running and while the CDO holds enough residual underlying to cover the fee. With a 0.1-1% FOT fee, an attacker depositing `N` extracts ~`N * feeRate` of other holders' principal per call, and also inflates `expectedEpochInterest` (line 728) by interest on principal that was never net-contributed. If the CDO balance is smaller than the fee, the function reverts, bounding single-call theft to the vault's residual balance.

### Likelihood Explanation
Requires (a) a running epoch in fixed-APR mode (`isProgrammableBorrower`, `isAYSActive`, `skipDefaultCheck`, `isDepositDuringEpochDisabled` all false, `block.timestamp < epochEndDate`), (b) a KYC-passing attacker wallet (`isWalletAllowed` — permitted per the attacker model), (c) an existing tranche supply (`_trancheTotSupply != 0`), and (d) a fee-on-transfer underlying. The gate on tranche supply and flags is administrative, not economic, so once such a token is the vault underlying the exploit is permissionless for any allowed lender and repeatable.

### Recommendation
Measure the received amount and use it everywhere `_amount` is currently used:

```solidity
uint256 _preBal = _contractTokenBalance(token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(token) - _preBal;
```

Then compute `interest`, `trancheInterest`, `_minted`, `mintStrategyTokens`, and the borrower transfer from `_received` (or revert if `_received < _amount` if parity with nominal deposits is required).

### Proof of Concept
Foundry fork test outline (USDT-style FOT underlying, e.g. enable fee via USDT owner on a mainnet fork or use a mock FOT token as `token`):

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract FotDepositDuringEpochTest is Test {
    IdleCDOEpochVariant cdo;      // deployed epoch-variant CDO with FOT `token`
    MockFotToken token;           // underlying with e.g. 1% transfer fee
    address attacker = makeAddr("kycLender");
    address borrower;

    function testFotDepositDuringEpoch() public {
        // Epoch is running, fixed-APR, supply exists, attacker is wallet-allowed.
        // Seed attacker with 1_000_000e6 FOT tokens and approve the CDO.
        uint256 amount = 1_000_000e6;
        uint256 vaultBalBefore = token.balanceOf(address(cdo));
        uint256 navBefore = cdo.lastNAVAA() + cdo.lastNAVBB();

        vm.prank(attacker);
        cdo.depositDuringEpoch(amount, cdo.AATranche());

        // Vault net-received amount - fee, but borrower got the full `amount`,
        // so the CDO balance dropped by `fee` relative to a fair deposit.
        uint256 received = amount - amount * token.feeBps() / 10_000;
        assertEq(token.balanceOf(borrower), /* prev */ + amount);
        assertEq(token.balanceOf(address(cdo)), vaultBalBefore + received - amount); // < before
        // Attacker holds shares priced on `amount` (plus prorated interest)
        // while only `received` new value entered -> NAV deficit = amount - received.
        assertGt(attackerShareValue(attacker), received);
    }
}
```

Uncertainties: I confirmed `_deposit` variants use balance deltas while `depositDuringEpoch` does not; I did not fully trace `_mintShares`'s fourth argument (`_amount`, recorded principal) or `mintStrategyTokens` internals in `IdleCreditVault`, but the mint math and the borrower forwarding at lines 724-732 are sufficient to establish the deficit. If the CDO holds no residual underlying balance, the forwarding transfer reverts, turning the issue into a revert rather than theft — exploitation therefore also requires the vault to carry at least `fotFee` residual balance during the running epoch.
