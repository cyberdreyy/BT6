## Title
Operator-controlled beneficiary with no APT-registration check can permanently freeze all pending stake/commission distributions in `staking_contract` - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator (an unprivileged, non-staker role) point their commission payout to any arbitrary address, with **no check that the address can actually receive `AptosCoin`**: [1](#0-0) 

Compare this with the sibling `vesting::set_beneficiary`, which explicitly guards against this exact class of bug: [2](#0-1) 

The comment on `vesting::set_beneficiary` states the rationale directly: *"Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't fail and block all other accounts from receiving APT if one beneficiary is not registered."* The Aptos team clearly recognized this failure mode in `vesting.move`, but the equivalent guard is absent from `staking_contract::set_beneficiary_for_operator`.

### Finding Description
`distribute_internal` pays out **all** pending shareholders of a `StakingContract`'s `distribution_pool` — both the staker's unlocked principal (added via `unlock_stake`/`add_distribution(staker, ...)`) and the operator's commission (added via `request_commission_internal`/`add_distribution(operator, ...)`) — in a single atomic loop: [3](#0-2) 

If the recipient resolved for the operator's share (`beneficiary_for_operator(operator)`) cannot accept a direct `AptosCoin` deposit — i.e. the account doesn't exist yet in a way that can't auto-register, or more concretely, the account exists but has disabled arbitrary transfers via `set_allow_direct_coin_transfers(account, false)` and is not registered for `AptosCoin` — then `aptos_account::deposit_coins` aborts: [4](#0-3) 

Because Move has no try/catch, this abort reverts the **entire** `distribute`/`distribute_internal` transaction — including the withdrawal-with-capability that already pulled coins out of the stake pool (`stake::withdraw_with_cap`) and the payouts intended for the staker and any other beneficiaries in the same pool. Since `distribute` is a permissionless entry function (`"Allow anyone to distribute already unlocked funds"`) that always executes the same shareholder loop, every future call to `distribute()` for that `(staker, operator)` pair will deterministically hit the same abort as long as the poisoned beneficiary remains unable to receive coins.

Critically, `set_beneficiary_for_operator` is callable by the operator alone, independent of any staking-contract pool (`"the operator does not need to be validated with respect to a staking pool"`): [5](#0-4) 

so an operator can set a beneficiary that cannot receive `AptosCoin` (for example, an address the operator controls where `set_allow_direct_coin_transfers(false)` was called before ever registering `AptosCoin`) and thereby permanently trap the staker's principal, accumulated rewards, and future commission in the `distribution_pool` for every `staker` who has delegated to that operator — with no recovery path, since `distribute_internal` cannot skip a bad recipient. `unlock_stake`, `switch_operator`, and `update_commission_percentage` all call `distribute_internal` first, so those paths are affected too.

### Impact Explanation
This is a high-impact stake-and-lockup invariant break: once triggered, a staker's unlocked/inactive stake and rewards, plus the operator's own commission, become **permanently non-withdrawable** from the `distribution_pool` for that `(staker, operator)` pair, since every code path that would flush the pool (`distribute`, `unlock_stake`, `switch_operator`, `update_commission_percentage`) is gated by the same atomic loop that always tries to pay the poisoned beneficiary first/along with everyone else. This matches the "Permanent lock or non-recoverable loss of claim rights" and "Operator commission... corruption that... traps value" impact categories.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the operator to deliberately (or accidentally) configure a beneficiary address that is not registered for `AptosCoin` and has direct-transfer acceptance disabled. This is entirely achievable by an operator with no special privileges — they merely need to control (or convince the staker's environment to accept) an address they've configured with `set_allow_direct_coin_transfers(signer, false)` prior to registering for `AptosCoin`, then call `set_beneficiary_for_operator`. It is a self-service, unprivileged action.

### Recommendation
Add the same guard to `staking_contract::set_beneficiary_for_operator` (and ideally `switch_operator`'s beneficiary-adjacent paths) that already exists in `vesting::set_beneficiary`: assert `new_beneficiary` is an existing account registered to receive `AptosCoin` (`aptos_account::assert_account_is_registered_for_apt`) before allowing the beneficiary change. Additionally, consider hardening `distribute_internal` itself to skip/quarantine a shareholder whose payout cannot be deposited (e.g., route unpayable amounts to a claimable/pull-based holding resource) rather than reverting the whole distribution for all shareholders.

### Proof of Concept
1. Operator account `O` is created and calls `aptos_account::set_allow_direct_coin_transfers(O, false)` before ever calling `coin::register<AptosCoin>` for itself (or targets any other such unregistered address it controls).
2. Staker `S` calls `staking_contract::create_staking_contract(S, O, voter, amount, commission_pct, seed)`.
3. Operator calls `staking_contract::set_beneficiary_for_operator(O, O)` (no registration check blocks this) — this succeeds because there is no `assert_account_is_registered_for_apt` guard.
4. Time passes; stake earns rewards. `S` calls `unlock_stake` (or anyone calls `distribute`), which internally calls `distribute_internal`.
5. `distribute_internal` iterates shareholders including the operator's commission share, resolves the beneficiary via `beneficiary_for_operator(O)` = `O`, and calls `aptos_account::deposit_coins(O, ...)`. Because `O` is unregistered for `AptosCoin` and has disabled arbitrary transfers, `deposit_coins` aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
6. The abort reverts the entire transaction, including the withdrawal from the stake pool and the staker's own payout in the same loop. Every subsequent call to `distribute`/`unlock_stake`/`switch_operator` for this `(S, O)` pair reproduces the same abort, permanently freezing all pending distributions.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }

    public entry fun set_beneficiary(
        admin: &signer,
        contract_address: address,
        shareholder: address,
        new_beneficiary: address,
    ) acquires VestingContract {
        // Verify that the beneficiary account is set up to receive APT. This is a requirement so distribute() wouldn't
        // fail and block all other accounts from receiving APT if one beneficiary is not registered.
        assert_account_is_registered_for_apt(new_beneficiary);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);

        let old_beneficiary = get_beneficiary(vesting_contract, shareholder);
        let beneficiaries = &mut vesting_contract.beneficiaries;
        if (beneficiaries.contains_key(&shareholder)) {
            let beneficiary = beneficiaries.borrow_mut(&shareholder);
            *beneficiary = new_beneficiary;
        } else {
            beneficiaries.add(shareholder, new_beneficiary);
        };

        emit(
            SetBeneficiary {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
                shareholder,
                old_beneficiary,
                new_beneficiary,
            },
        );
