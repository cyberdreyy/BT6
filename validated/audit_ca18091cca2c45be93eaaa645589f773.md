### Title
Loss-adjusted withdraw receipts are paid at par after a re-request overwrites `lastWithdrawRequest` — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The closest analog of "funds distributed without verifying the claim was actually approved" is in `IdleCreditVault`: a withdraw receipt that was haircut by a `stopEpochWithDuration` loss (`lossRecoveryPriceByEpoch[epoch]`) loses its epoch linkage when the user submits a new `requestWithdraw`, because `lastWithdrawRequest[_user]` is overwritten while `withdrawsRequests[_user]` still aggregates the old basis. On the next claim, `_claimLossAdjustedWithdrawRequest` looks up the *new* epoch (price = 0, no-op), and `_claimFundedWithdrawRequest` then pays the entire aggregate — including the haircutted amount — at par. The required status check (was this receipt loss-adjusted?) is effectively skipped before funds are transferred, exactly like the RFPSimple `_distribute` paying out regardless of milestone status.

### Finding Description
In `requestWithdraw`, the strategy records the request per-epoch and updates the user's marker to the current epoch: [1](#0-0) 

When the borrower underfunds `stopEpoch`, `collectWithdrawFunds` stores a haircut in `lossRecoveryPriceByEpoch[epochNumber]` but leaves each user's `withdrawsRequestsByEpoch` entry intact: [2](#0-1) 

On claim, `_claimLossAdjustedWithdrawRequest` only consults `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If the user re-requested in a later epoch, that lookup returns 0 and the function exits without clearing the old epoch's claim: [3](#0-2) 

`_claimFundedWithdrawRequest` then burns and pays `withdrawsRequests[_user]` — which still includes the loss-adjusted epoch's claimBasis — at par via `_transferFundedClaim`. When `defaultRecoveryReserve` is 0, `_transferFundedClaim` has no reserve check and simply transfers: [4](#0-3) [5](#0-4) 

The documented "wait another epoch" note (line 323-324) acknowledges the timer reset but not that re-requesting silently voids the loss haircut.

### Impact Explanation
A lender whose withdraw request was haircut by a realized loss can recover 100% of the receipt by simply submitting a second `requestWithdraw` before claiming. This breaks the loss-socialization invariant: the haircut intended for that claimant is paid out of the strategy's funded balance, directly stealing underlyings that belong to other funded claimants or the default recovery reserve. Quantified loss = `claimBasis * (1 - lossRecoveryPrice/RECOVERY_FULL)` per re-requesting user, up to the full pending-withdraw bucket.

### Likelihood Explanation
Requires an epoch stopped with a realized loss (`stopEpochWithDuration` / underfunded `collectWithdrawFunds`) while the attacker holds a pending receipt — a routine state after borrower underpayment. The attacker only needs to submit one additional `requestWithdraw` (any positive amount, as a KYC-passing lender) and wait one epoch. No privileged cooperation is needed; the attacker is an ordinary lender.

### Recommendation
Track each user's claimable epochs independently of `lastWithdrawRequest`, or in `requestWithdraw` first settle/clear any existing loss-adjusted claim for the previous epoch (apply `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` to `withdrawsRequestsByEpoch[_user][prevEpoch]` and convert it to a fixed funded amount) before overwriting `lastWithdrawRequest[_user]`. Alternatively, iterate `withdrawsRequestsByEpoch` over all epochs with nonzero `lossRecoveryPriceByEpoch` in `claimWithdrawRequest` rather than keying off the single latest marker.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Setup: user deposits into a tranche, epoch runs, user calls requestWithdraw(X) in epoch N.
// 1. Borrower underfunds stopEpoch: owner calls stopEpoch with _lossAmount > 0 such that
//    collectWithdrawFunds(funded < pendingWithdraws) → lossRecoveryPriceByEpoch[N] = 0.5e18.
// 2. Epoch N+1 starts; user calls requestWithdraw(1) (dust) → lastWithdrawRequest[user] = N+1.
// 3. Epoch N+1 ends fully funded; epochNumber > N+1.
// 4. CDO calls claimWithdrawRequest(user):
//    - _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[N+1] == 0 → returns 0,
//      withdrawsRequestsByEpoch[user][N] never cleared.
//    - _claimFundedWithdrawRequest: pays withdrawsRequests[user] = X + 1 at par.
// 5. assert user received X + 1 underlying instead of X*0.5 + 1.
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
