### Title
Cross-user response hijacking via unauthenticated `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each incoming legacy trigger request's callback in `h.savedCallbacks` keyed only by the client-supplied `msg.Body.MessageId`, with no check for whether that ID is already in use or whether it "belongs" to the same sender. Any unauthenticated caller of `/gateway` (needing only a self-generated ECDSA signature, not any privileged credential) can submit a `MethodWebAPITrigger` message with a `MessageId` equal to a victim's in-flight request, silently overwriting the victim's saved callback, so the eventual node response for that `MessageId` is delivered to the attacker instead of the original caller.

### Finding Description
In `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`), after validating the message's own JSON structure and signature (which only proves *some* valid keypair signed it — `Message.Validate` in `core/services/gateway/api/message.go:54-88` does not check the ID against any per-sender namespace or allowlist), the handler does:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 

This unconditionally overwrites any existing entry for the same `MessageId` — there is no `found` check, no comparison of `msg.Body.Sender`, and the explicit `// TODO: apply allowlist and rate-limiting here` comment at line 384 confirms no sender-based authorization exists at this stage. [2](#0-1) 

Later, when a DON node replies, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageId` and routes the response to whichever `Callback` is currently stored:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [3](#0-2) 

The `MessageId` is fully attacker-controlled (it is copied directly from the incoming JSON-RPC request into `msg.Body.MessageId` via `common.ValidatedMessageFromReq`, `core/services/gateway/handlers/common/message_util.go:36-58`, or the legacy path's `msg.Body.MessageId` field), and only needs to satisfy length/format checks in `Validate()` — not uniqueness or ownership tied to the sender. [4](#0-3) 

Exploit flow:
1. Victim POSTs a legit `web_api_trigger` request with `MessageId = "X"`, which stores `savedCallbacks["X"] = victimCallback`.
2. Before nodes respond, attacker (any address, self-signed, no credential) POSTs a second `web_api_trigger` request also using `MessageId = "X"`, overwriting `savedCallbacks["X"] = attackerCallback`.
3. When any DON node responds to `MessageId "X"` (which could correspond to the victim's original forwarded request, since the gateway forwards both requests to nodes under the same `MessageId`), `handleWebAPITriggerMessage` delivers that response into `attackerCallback`, and the victim's HTTP connection either hangs until timeout or (if attacker's request is a duplicate ID that the node also executes) attacker's own request executes twice while stealing the victim's response.

There is no code path in `HandleLegacyUserMessage` that rejects a duplicate `MessageId` or restricts callback overwrite to the same `msg.Body.Sender`, so isolation between users' cache entries is not enforced.

### Impact Explanation
This is a cross-user response confusion vulnerability: an unauthenticated attacker can capture another user's capability-execution response (which may include response bodies containing external HTTP call results triggered by the victim's workflow), or silently drop/replace the victim's callback, causing their legitimate request to time out. This maps to a scoped "unauthorized cross-user information disclosure / request impersonation" impact rather than fund loss, but represents a real request/response isolation break in the Gateway's legacy trigger handling.

### Likelihood Explanation
Exploitation requires only the ability to POST to `/gateway` with `method=web_api_trigger`, a self-generated ECDSA keypair (no allowlisted or privileged credential — the TODO at line 384 confirms allowlisting is not yet implemented), and predicting or guessing the victim's `MessageId` (client-chosen, e.g. sequential, timestamp-based, or otherwise low-entropy IDs would make this trivial; even random IDs are feasible to race against if the attacker can observe or brute force in-flight IDs during high load, given `defaultMaxSavedCallbacks = 20000` and a 120-second callback window at `defaultCallbackMaxAgeSec`). This is fully repeatable and requires no operator or DON-side compromise.

### Recommendation
Scope `savedCallbacks` entries by both `MessageId` and `msg.Body.Sender` (e.g., composite key `sender+":"+messageId`), and/or reject `HandleLegacyUserMessage` calls when an entry for the same `MessageId` already exists and is not yet expired/consumed, returning a clear "duplicate message ID" error instead of silently overwriting.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` style:
1. Construct two signed `api.Message` triggers with different signing keys (`nodes[0].PrivateKey` vs a second independent key) but identical `MessageId` ("dup-id"), each with distinct `handlers.Callback` instances (`cbVictim`, `cbAttacker`).
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, cbVictim)`, then assert `handler.savedCallbacks["dup-id"].Callback == cbVictim` (via reflection or a wrapping test-only identity field).
3. Call `handler.HandleLegacyUserMessage(ctx, attackerMsg, cbAttacker)` before any node response is processed.
4. Assert `handler.savedCallbacks["dup-id"].Callback == cbAttacker` — proving silent overwrite with no sender-uniqueness check.
5. Simulate a node response for `MessageId "dup-id"` via `handler.HandleNodeMessage`, and assert that `cbAttacker.Wait(ctx)` receives the response payload while `cbVictim.Wait(ctx)` times out/never resolves — demonstrating the cross-user response hijack end-to-end.
