### Title
Shared `requestCache` has no per-sender quota, allowing a single attacker with many distinct sender identities to exhaust `maxCacheSize` and deny legitimate users - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces only a single global capacity check (`len(c.cache) >= maxCacheSize`) with no per-sender limit, so any handler that uses this shared generic cache to track in-flight gateway requests is vulnerable to a single actor filling the entire cache with distinct `(sender, messageId)` keys and starving other users' requests with "request cache is full" errors.

### Finding Description
`requestCache[T].NewRequest` keys entries by `globalId{sender, id}` [1](#0-0)  and rejects new requests only when the total map size reaches `maxCacheSize`, with no accounting per sender: [2](#0-1) . Because the key includes `sender`, an attacker who can produce many distinct signer identities (trivial — an EOA keypair is free to generate and `Sign()` requires no privileged access) can submit `maxCacheSize` distinct well-formed requests, each occupying one cache slot until its `timeout` fires [3](#0-2) . While these entries are pending, any other user's `NewRequest` call — including legitimate victims — will fail with `"request cache is full"`.

However, I was not able to locate a production call site in this codebase snapshot that actually instantiates `NewRequestCache`/`RequestCache[T]` and wires an unauthenticated or minimally-authenticated attacker path into `NewRequest`; the only references to this type outside its own test file are indirect (e.g., package imports in `capabilities/handler.go` and `vault/handler.go` for other helpers such as `common.ValidatedRequestFromMessage`, not `NewRequestCache`). The gateway's other in-flight-request tracking paths that I could confirm (e.g., `capabilities/handler.go`'s `savedCallbacks` map) do not use this cache and separately carry a `// TODO: apply allowlist and rate-limiting here` comment [4](#0-3) , indicating that at least this legacy path is unrelated to `requestcache.go`. I could not confirm within the available index whether any currently-wired handler routes an attacker-reachable, minimally-authenticated request into `requestCache.NewRequest` without an upstream per-sender allowlist/rate limiter (several handlers such as the v2 HTTP trigger handler do enforce `userRateLimiter`/per-workflow-owner rate limits before any caching stage, e.g. [5](#0-4) ).

### Impact Explanation
If a handler uses this shared cache without an upstream per-sender quota, the impact is a denial-of-service on gateway request processing (legitimate victim requests rejected with cache-full errors) — this maps to Chainlink's "Denial of Service" bounty impact class, not to fund loss, key disclosure, or auth bypass. It does not itself expose cross-user data or allow request impersonation.

### Likelihood Explanation
Preconditions for exploitation require: (1) a real handler wiring an unauthenticated/self-generated-signer path directly into `requestCache.NewRequest`, and (2) that handler lacking any upstream per-sender allowlist/rate-limit gate. I could confirm the first condition (missing per-sender quota) is true in `requestcache.go` itself, but I could not confirm the second condition (an actual unguarded, attacker-reachable caller) from the available code in this repository snapshot — the callers I inspected either don't use this cache or already enforce per-sender/per-workflow rate limiting upstream of any queue insertion. Given the indexing limits noted, I could not fully rule out an unguarded caller existing elsewhere in the repo.

### Recommendation
Regardless of current wiring, harden `requestCache` defensively: add a per-sender counter/quota (e.g., `map[sender]int` alongside `cache`) and reject `NewRequest` when a sender's own pending-request count exceeds a configurable per-sender limit, in addition to the existing global `maxCacheSize` check, so that no single sender identity can monopolize the shared cache.

### Proof of Concept
Go unit test plan for `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `NewRequestCache[T](timeout, maxCacheSize=N)`.
2. In a loop, call `NewRequest` with `N-1` distinct attacker `sender` values (unique EOA-style strings) and unique `MessageId`s; assert all succeed.
3. Call `NewRequest` once more with a legitimate victim `sender`/`MessageId`; assert it fails with `"request cache is full"`.
4. Assert failure — no per-sender quota exists to reject the attacker before the cache fills — demonstrating the described DoS at the `requestCache` component level (caveat: this PoC demonstrates the component-level gap; confirming end-to-end exploitability requires identifying and testing the specific unauthenticated handler that wires into this cache, which was not conclusively located in this review).
