### Title
Sum of per-delegation block-reward fractions to a single vote account is not bounded by `pending_delegator_rewards`, only individually clamped — ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
`calculate_block_reward` computes each stake delegation's share of a vote account's `pending_delegator_rewards` as `pending_delegator_rewards * stake / total_active_stake`, individually capping each result at `pending_delegator_rewards`. This is the same class of bug as the PoolTogether report: individual "fractions" of a shared reward pool are clamped to at most 1.0 each, but nothing guarantees that the sum of fractions across all delegations to the same vote account stays ≤ 1.0.

### Finding Description
`calculate_block_reward` computes, per stake delegation, a proportional share of the vote account's `pending_delegator_rewards`: [1](#0-0) 

The denominator `total_active_stake` is looked up from a snapshotted `reward_epoch_delegated_stakes` map (the stake distribution as of the end of the reward epoch), while the numerator `stake` is `delegation_effective_stake(...)` computed live, potentially during a *recalculation* pass. The code comment itself acknowledges the resulting hazard:

> "During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`... We can also have individual rewards look greater than the pending rewards. This is harmless in practice, but we clamp it just to be safe" [2](#0-1) 

Each individual result is clamped with `.min(pending_delegator_rewards)`, exactly mirroring PoolTogether's per-participant fraction clamp to `[0, 1.0]`. But — as in the PoolTogether bug — this per-item clamp does not enforce that the **sum** across all delegations to a given vote account is bounded by `pending_delegator_rewards`. If the recalculation-time skew described in the comment (`stake > total_active_stake`) affects multiple delegations to the same vote account simultaneously (e.g., because several delegators already received partial rewards before a mid-epoch recalculation, or the numerator computed via `delegation_effective_stake` diverges from the frozen `total_active_stake` denominator for many stake accounts at once), each of those delegations can independently compute (and be clamped to) up to the *full* `pending_delegator_rewards`, and the accumulated `block_reward_lamports_distributed`/`block_reward_lamports_minted` in `distribute_epoch_rewards_in_partition` would exceed the vote account's actual `pending_delegator_rewards` balance. [3](#0-2) 

Unlike the stake/vote-account "inflation" reward path — which is proven correct by construction because `points` is a global sum and each stake's share is `points_i / total_points * rewards` (guaranteed ≤ 1.0 in aggregate) — and unlike `commission_split`/`commission_split_preserve_lamports`, which are proven via proptest invariants to always sum exactly to the input (`voter + staker == rewards`), `calculate_block_reward` has no equivalent aggregate accounting or clamp against the vote account's actual balance/`pending_delegator_rewards` total at the point of distribution.

### Impact Explanation
If the sum of block rewards distributed to stake accounts of one vote account exceeds `pending_delegator_rewards`, either:
- lamports are minted/credited to stake accounts beyond what the vote account can fund from its reward budget (an inflation/overpayment of capitalization tracked via `stake_reward_lamports_minted`/`block_reward_lamports_distributed` in `distribute_epoch_rewards_in_partition`), or
- the vote account's actual lamport balance becomes insufficient to cover the aggregate promised delegator rewards, which could manifest at withdrawal time given the `withdraw` function's invariant that withdrawable balance = `lamports - pending_delegator_rewards - rent_exempt_minimum`. [4](#0-3) 

This directly parallels the "overpaying rewards" impact class from the PoolTogether report, applied to Alpenglow block-revenue-sharing rewards (SIMD-0123) rather than an on-chain auction.

### Likelihood Explanation
This can only occur during the specific "recalculation" scenario explicitly called out in the code comment — mid-epoch recalculation of rewards after some stake accounts have already received partial distributions, with `use_fixed_point_stake_math`/`block_revenue_sharing` features active. The comment states this condition is believed to be "harmless in practice," suggesting the authors already reasoned about — and may have bounded — the actual magnitude of the discrepancy elsewhere (e.g., limits on how much effective stake can drift within a recalculation window). I could not fully verify from the available code/tests whether an aggregate cross-check against `pending_delegator_rewards` (or the vote account's real balance) exists at distribution time; the tests found (`test_calculate_block_reward_prop`) only assert the single-delegation invariant `reward <= pending_delegator_rewards`, not a cross-delegation sum invariant. Given this, likelihood is assessed as low/uncertain without further code review of the recalculation path bounds, but the finding is not proven unreachable either.

### Recommendation
Add an aggregate check/clamp when computing or distributing block rewards: track the running total distributed against each vote account's `pending_delegator_rewards` (or decrement `pending_delegator_rewards` as rewards are computed) so the sum of block rewards to any one vote account's delegators cannot exceed the vote account's actual reward budget, analogous to how `total_stake_rewards_lamports` is checked against `point_value.rewards` in `distribute_reward_commissions`'s `assert!`. [5](#0-4) 

### Proof of Concept
No concrete on-chain PoC was constructed; the existing test suite only demonstrates the single-delegation clamp (`test_calculate_block_reward_specific`, `test_calculate_block_reward_prop`) and does not include a multi-delegation, cross-account-sum test analogous to the PoolTogether `test_finishDraw_multipleStarts_with_exceeding_reserve` reproduction. [6](#0-5)
