## Analysis

The strongest analog to the reported bug class (unvalidated parameter accepted from a privileged-but-external source, later causing a DoS that is itself hard to walk back) is the `GasLimitUpdate` decoder for L1 `SystemConfig` `ConfigUpdate` logs, which is a fully in-scope "derivation of attacker-written L1 deposit and system-config data" path.

### Title
Missing lower-bound validation on L1-sourced `gas_limit` `SystemConfig` update can zero out the L2 block gas limit and halt user-transaction inclusion - (File: `crates/common/genesis/src/updates/gas_limit.rs`)

### Summary
`GasLimitUpdate::try_from` decodes the `gas_limit` field of a `ConfigUpdate` log emitted by the L1 `SystemConfig` contract during derivation. The only bound enforced is an upper check against `u64::MAX`; there is no check that the value is non-zero or above any sane minimum before it is applied to the derived `SystemConfig` and propagated into L2 block-building.

### Finding Description
`GasLimitUpdate::try_from` decodes the ABI-encoded `gas_limit` value straight from log data and only rejects it if it exceeds `u64::MAX`: [1](#0-0) 

`GasLimitUpdate::apply` then writes this value into `SystemConfig.gas_limit` unconditionally, with no floor: [2](#0-1) 

This derived `SystemConfig.gas_limit` is propagated directly into block-building payload attributes (`gas_limit: Some(self.system_config.gas_limit)`), which is the block gas limit target the payload builder uses to decide how much execution it will pack into a block: [3](#0-2) 

The codebase itself documents the consequence of an unvalidated zero: a test helper comment explicitly calls out that a zero `gas_limit` "causes the production payload builder to reject all transactions," and works around it only in test fixtures: [4](#0-3) 

This is structurally identical to the reported `TradingVaultV2._rewardsDuration` issue: a numeric parameter that arrives from an external/privileged update path is applied to protocol state without a sanity floor, and once applied, its effect (an unusably small or zero block-building budget) is difficult to correct because the same unauthenticated derivation path is the only way to overwrite it, and every block derived in the meantime still has to be built/validated against the bad value.

### Impact Explanation
A `SystemConfig.gas_limit` of `0` (or another degenerate low value) reaching the sequencer's/builder's payload-attributes flow causes the block-building pipeline to reject essentially all user transactions (per the documented behavior above), effectively halting normal chain operation for L2 users until a corrective `ConfigUpdate` is committed on L1 and derived through — and derivation itself may struggle to build blocks in the interim. This is a node/chain halt impact class.

### Likelihood Explanation
This path is reached purely through derivation of L1-emitted `ConfigUpdate` logs from the `SystemConfig` contract — no additional privilege beyond whatever already controls that contract's gas-limit setter is required, and the decoder itself performs no defense-in-depth validation before applying the value protocol-wide. Given the report explicitly flags "no maximum/minimum bound on a duration/limit-like parameter" as the vulnerability class, and this Base code path has the identical shape (attacker/privileged-writer supplied numeric parameter, upper-bound-only check, no defense against degenerate low values), this is a directly reachable analog.

### Recommendation
Add a lower bound (and ideally a sane minimum) check in `GasLimitUpdate::try_from` (or in `SystemConfig::update_with_receipts`) alongside the existing upper bound, rejecting/ignoring `gas_limit == 0` (or below some protocol-defined minimum) the same way `GasConfigUpdate` already ignores an invalid scalar and retains the prior value: [5](#0-4) 

### Proof of Concept
1. The L1 `SystemConfig` contract emits a `ConfigUpdate` log of `UpdateType.GAS_LIMIT` (topic `GAS_LIMIT_UPDATE_TYPE`) with payload `gas_limit = 0`.
2. During L1 receipt processing, `SystemConfig::process_config_update_log` → `GasLimitUpdate::try_from` decodes `0`, which passes the only check (`gas_limit <= u64::MAX`). [6](#0-5) 
3. `GasLimitUpdate::apply` sets `SystemConfig.gas_limit = 0`.
4. Once the L2 epoch advances to the L1 block containing this log, `StatefulAttributesBuilder`/`StandaloneAttributesBuilder` uses this `SystemConfig.gas_limit` as the block's `gas_limit` payload attribute, and the payload builder rejects all non-exempt transactions because the available gas budget is zero — matching the documented workaround comment in the test harness.

    fn process_config_update_log(
        &mut self,
        log: &Log,
        ecotone_active: bool,

        let log = SystemConfigLog::new(log.clone(), ecotone_active);
