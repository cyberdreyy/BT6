### Title
Unprivileged front-running of `LockupFactory::create` lets an attacker permanently squat a victim's deterministic lockup address with attacker-chosen parameters - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` computes the lockup account name deterministically as `sha256(owner_account_id)[..20].<factory>` and performs no check on who the caller is or whether that account was already reserved for a specific grantor/vesting schedule. Any unprivileged account can call `create` for an arbitrary `owner_account_id` (a victim who never asked for it) with `vesting_schedule = None`, permanently occupying that address and blocking the legitimate grantor's later `create` call for the same `owner_account_id`.

### Finding Description
The broken binding: `lockup_account_id_for(owner_account_id) == the account that is created exactly once, by the party entitled to set its vesting_schedule/release_duration`. In the code, this binding is violated because `lockup_account_id` depends solely on `owner_account_id`: [1](#0-0) [2](#0-1) 

`create` is `#[payable]` with no `assert_owner`, no `assert_called_by_foundation`, and no restriction that `predecessor_account_id` must equal `owner_account_id` or the foundation account. The only gate is `env::attached_deposit() >= MIN_ATTACHED_BALANCE` (3.5 NEAR), which any unprivileged attacker can pay from their own funds: [3](#0-2) 

The attacker calls `create(owner_account_id = victim, lockup_duration, lockup_timestamp, vesting_schedule = None, release_duration = None, whitelist_account_id = None)` attaching `MIN_ATTACHED_BALANCE`. This schedules `Promise::new(lockup_account_id).create_account().deploy_contract(CODE).transfer(...).function_call("new", LockupArgs{ owner_account_id: victim, vesting_schedule: None, foundation_account_id: None, ... })`: [4](#0-3) 

Because NEAR account creation is idempotent-fails-if-exists, once this promise succeeds the account `lockup_account_id` exists on-chain permanently with the attacker's chosen (non-vesting) parameters. When the legitimate grantor later calls `create` for the same `owner_account_id` (victim) with the intended `vesting_schedule`, the resulting promise is scheduled for the identical `lockup_account_id`; `create_account()` will fail on a real network since the account already exists, and the callback `on_lockup_create` will observe `is_promise_success() == false` and simply refund the deposit: [5](#0-4) 

None of the existing guards (`assert_self`, `is_promise_success`) prevent this — `assert_self` only protects the callback from being called by anyone other than the factory itself, and `is_promise_success` only detects failure after the fact, it does not prevent the pre-emption. There is no check anywhere in `lib.rs`/`utils.rs` restricting who may call `create` or verifying that `owner_account_id` consents to or requested the call.

### Impact Explanation
The attacker permanently plants a lockup contract at the victim's deterministic address with attacker-chosen parameters (`vesting_schedule = None`, arbitrary `lockup_duration`/`lockup_timestamp`, no foundation oversight), which is exactly the "a lockup deployed with parameters its rightful creator never chose" Critical category. The legitimate grantor (e.g., NEAR Foundation or whoever was meant to create the victim's real vesting lockup) can never create the intended lockup at that name again — the account creation step will fail forever once occupied. This is repeatable against any victim account name for the cost of one `MIN_ATTACHED_BALANCE` (3.5 NEAR) attachment per victim, blocking arbitrarily many intended grants.

### Likelihood Explanation
No special privileges are required — any account able to send a transaction and attach ~3.5 NEAR can perform this. The attacker only needs to know or guess a victim `owner_account_id` intended for a future lockup (e.g., a known upcoming grantee) before the legitimate `create` call lands. This is fully feasible and repeatable across any number of victim accounts, each requiring a fresh `MIN_ATTACHED_BALANCE` deposit.

### Recommendation
Restrict `create` so that it can only be called by a trusted party (e.g., `assert_called_by_foundation` / the `foundation_account_id`) for attaching a vesting schedule, and/or require the `predecessor_account_id` to equal `owner_account_id` for self-serve, non-vesting lockups, so an attacker cannot supply an arbitrary victim `owner_account_id`. Alternatively, incorporate the caller/predecessor or a nonce into the derived `lockup_account_id` so identity of the deterministic name cannot be squatted by an unrelated third party.

### Proof of Concept
```rust
// unit test in lockup-factory/src/lib.rs tests module, using existing test_utils helpers
#[test]
fn test_attacker_preempts_victim_lockup() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    let lockup_duration: WrappedTimestamp = 63036000000000000u64.into();

    // Step 1: ATTACKER calls create() for victim's owner_account_id with weak params (no vesting)
    context.predecessor_account_id = String::from("attacker"); // unprivileged, not foundation
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner() /* == victim */, lockup_duration, None, None, None, None);

    // Simulate account creation success at the deterministic lockup_account_id
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    let created = contract.on_lockup_create(lockup_account(), ntoy(30).into(), String::from("attacker"));
    assert!(created); // attacker's non-vesting lockup now exists at lockup_account()

    // Step 2: LEGITIMATE grantor tries create() for same victim with a real vesting schedule
    let vesting_schedule = Some(new_vesting_schedule(10)).map(|vs| {
        VestingScheduleOrHash::VestingHash(
            VestingScheduleWithSalt { vesting_schedule: vs, salt: SALT.to_vec().into() }.hash().into(),
        )
    });
    context.predecessor_account_id = String::from(account_tokens_owner());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, vesting_schedule, None, None);

    // On a real network, create_account() for the same lockup_account_id fails because it already exists.
    // Simulate that failure and assert the intended vesting lockup was never established:
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let legit_created = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner()),
    );
    assert_eq!(legit_created, false); // legitimate vesting lockup permanently blocked at this address
}
```
This demonstrates `lockup_account_id_for(owner_account_id)` binds to whichever caller reaches it first, not to the party entitled to set the vesting terms, satisfying the Critical impact category "a lockup deployed with parameters its rightful creator never chose."

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
