### Title
Post-default withdraw requests drain the default recovery reserve at par, stealing haircutted claimants' recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` supports a "post-default" withdraw-request flow so users keep a request/claim UX after `finalizeDefaultRecovery`. New requests made after default finalization are recorded in `postDefaultRequests`, but their claims are paid out of `defaultRecoveryReserve` at 1:1 via `_transferDefaultRecovery`, even though that reserve is sized to cover only `basis * defaultRecoveryPrice` for pre-existing (defaulted-epoch) claimants. Post-default requesters therefore consume recovery funds earmarked for defaulted receipts.

### Finding Description
After `finalizeDefaultRecovery` sets `defaultRecoveryReserve = reserveAmount` and `defaultRecoveryPrice = reserveAmount * 1e18 / totalBasis` (IdleCreditVault.sol:686-692), the reserve exactly covers all defaulted-epoch claims at the recovery ratio. Every `_transferDefaultRecovery` call decrements `defaultRecoveryReserve` (lines 912-917), which is the isolation invariant: only defaulted/post-default claims may spend it, and `_transferFundedClaim` explicitly guards `balance - reserve >= amount` (lines 899-905).

When `defaultRecoveryFinalized` is true, `requestWithdraw` takes a special path (lines 247-257): it burns the CDO's strategy tokens, mints a receipt to the user, and sets `postDefaultRequests[_user] = _amount` — where `_amount` is the underlying-denominated claim the CDO passes in. The corresponding claim, `_claimPostDefaultWithdrawRequest` (lines 760-767), pays the full `_amount` via `_transferDefaultRecovery`, spending the recovery reserve at par.

The problem: post-default claims are funded by *new* borrower repayments sent to the strategy (strategy token balance above `defaultRecoveryReserve`), which is exactly the bucket `_transferFundedClaim` is designed to spend (`balance - reserve`). By routing the payment through `_transferDefaultRecovery` instead, a post-default claim consumes the isolated reserve at 100% while defaulted-epoch claimants are only entitled to `defaultRecoveryPrice` (typically < 100%) of their basis. The reserve is finite: each post-default claim of `X` removes `X` from a pool that was budgeted to pay defaulted claims at `X * price`.

### Impact Explanation
An unprivileged user (any KYC-passing lender / tranche holder who can still call `requestWithdraw` post-default via `IdleCDOEpochVariant.requestWithdraw`) can front-run honest defaulted-epoch claimants: request a withdraw after finalization, have the borrower (or a direct token sender) fund the strategy, and claim `_amount` paid entirely from `defaultRecoveryReserve`. When honest claimants later call `claimWithdrawRequest` → `_claimDefaultedWithdrawRequest`, `_transferDefaultRecovery` underflows (`defaultRecoveryReserve -= _amount`) and reverts — their defaulted recovery is permanently frozen, and the attacker received funds priced at par that partially belonged to other claimants (the haircut share). Loss is bounded by the reserve but directly proportional to post-default claim volume: with `defaultRecoveryPrice = p`, every post-default claim of `X` steals `X * (1 - p)` of other users' recovery plus freezes up to `X` of their claims.

### Likelihood Explanation
- Requires only an unprivileged user after `defaultRecoveryFinalized`; `requestWithdraw` explicitly permits new requests post-default once prior receipts are claimed (lines 247-251).
- Funding the claim requires underlying to reach the strategy (borrower repayment or direct transfer — both plausible; a direct token sender is an allowed attacker class). Note `collectWithdrawFunds`/`_transferFundedClaim` paths also let funded balances coexist with the reserve.
- No existing guard stops it: `_hasWithdrawRequest` only blocks users with open requests, `_transferDefaultRecovery` has no accounting that distinguishes reserve from post-default-funded balances, and `defaultRecoveryReserve` is never incremented by post-default funding.

### Recommendation
In `_claimPostDefaultWithdrawRequest`, pay via `_transferFundedClaim` (post-default requests are funded at par by new money, not by the recovery reserve), or track a separate post-default funded bucket. If post-default claims must use the reserve for UX reasons, add the funded amount to `defaultRecoveryReserve` at funding time so reserve accounting stays consistent, and consider pricing post-default claims at `defaultRecoveryPrice` like other defaulted receipts.

```solidity
// Foundry fork PoC (sketch) — contracts: IdleCreditVault, IdleCDOEpochVariant
// Phase: defaulted + finalized (defaultRecoveryFinalized == true)

function test_PostDefaultRequestDrainsRecoveryReserve() external {
    // --- setup: depositors AA/BB, epoch running, borrower defaults ---
    idleCDO.depositAA(100_000e6);
    idleCDO.depositBB(50_000e6);
    _startEpoch();
    _defaultBorrower();                 // borrower fails to repay
    cdoEpoch.finalizeDefaultRecovery(30_000e6, recoverySource); 
    // => defaultRecoveryReserve = 30_000e6, defaultRecoveryPrice < 1e18

    // honest user has a defaulted-epoch receipt basis B, entitled to B * price
    uint256 honestBasis = creditVault.withdrawsRequestsByEpoch(honest, epoch);
    uint256 honestEntitlement = honestBasis * creditVault.defaultRecoveryPrice() / 1e18;

    // --- attacker: KYC'd lender with remaining tranche balance post-default ---
    // (or any user able to requestWithdraw post-finalization)
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(attackerTrancheBal, address(BBtranche));
    // => IdleCreditVault.requestWithdraw sets postDefaultRequests[attacker] = amount
    vm.stopPrank();

    // borrower repays attacker's post-default request to the strategy
    // (equivalently any funded balance above the reserve)
    underlying.mint(borrower, attackerAmount);
    vm.prank(borrower);
    underlying.transfer(address(creditVault), attackerAmount);

    // attacker claims: paid at PAR from defaultRecoveryReserve
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest(attacker);
    assertEq(underlying.balanceOf(attacker), attackerAmount);
    // reserve decreased by full attackerAmount instead of 0
    assertEq(creditVault.defaultRecoveryReserve(), 30_000e6 - attackerAmount);

    // honest defaulted claimant now reverts or is underpaid:
    vm.prank(honest);
    vm.expectRevert(); // defaultRecoveryReserve -= _amount underflows / NotAllowed
    cdoEpoch.claimWithdrawRequest(honest);
}
```

```text
  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
```
