### Title
External Initiator credentials satisfy the "isUser" check in `PipelineRunsController.Create`, bypassing the "EIs not allowed" restriction - ([File: core/web/external_initiators_controller.go])

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered on the `userOrEI` group, which accepts three authentication methods in order: `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` [1](#0-0) . When an attacker authenticates with only a valid EI access-key/secret pair via the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, `AuthenticateExternalInitiator` verifies the EI credentials and then sets **both** `SessionExternalInitiatorKey` and `SessionUserKey` on the gin context, with the latter populated as `&clsessions.User{Role: clsessions.UserRoleRun}` [2](#0-1) .

In `PipelineRunsController.Create`, the code determines whether the caller is a "user" purely by calling `auth.GetAuthenticatedUser(c)`, which reads back `SessionUserKey`: `_, isUser := auth.GetAuthenticatedUser(c)` [3](#0-2) . Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for an EI-only caller — even though the accompanying code comment explicitly states "only users are allowed to run jobs using int IDs - EIs not allowed" [4](#0-3) . As a result, the `int32` job-ID branch executes and calls `prc.App.RunJobV2(ctx, jobID, nil)` for the attacker's chosen job ID, triggering a real pipeline run [5](#0-4) .

The `auth.RequiresRunRole` wrapper on this route does not block this either, since the synthetic user's `Role` is `UserRoleRun`, which satisfies a run-role gate by design (EIs are intended to reach `Create`, just supposedly restricted to webhook/UUID job identification, not arbitrary int32 IDs).

### Impact Explanation
An attacker holding only pre-provisioned EI credentials (no user session, no API token) can trigger pipeline runs on **any** job identified by its integer database ID via `POST /v2/jobs/<int32-jobID>/runs`, not just the webhook job the EI was scoped to invoke. This is unauthorized triggering of pipeline runs by a lower-privileged credential holder, matching the "unauthorized job run" bounty impact class. Depending on the pipeline tasks configured on the targeted job (e.g., ETH transfers, external HTTP calls with attacker-influenced `meta`), this could cause side effects beyond the EI's intended scope.

### Likelihood Explanation
The only precondition is possession of a single EI's access key/secret — a credential class explicitly designed to be more restricted than a full user session/API token. No additional privilege, session cookie, or admin action is required, and the request is a single unauthenticated (from a user standpoint) HTTP POST with two headers. This is fully reproducible and repeatable given any valid EI credential.

### Recommendation
Do not overload `SessionUserKey` to represent EI callers. Introduce a distinct check (e.g., inspect `SessionExternalInitiatorKey` first, or return a real/typed indicator from `GetAuthenticatedUser` that cannot be spoofed by EI auth) so that `PipelineRunsController.Create` can reliably differentiate a real user session/token from an EI-authenticated context, and reject int32-ID job runs from EI callers as the code comment intends.

### Proof of Concept
Go handler-level test outline:
1. Provision an EI via `POST /v2/external_initiators` (or directly insert via ORM) to obtain `AccessKey`/`Secret`.
2. Insert a non-webhook job (e.g. a cron/direct-request job) with a known int32 `jb.ID`.
3. Send `POST /v2/jobs/<jb.ID>/runs` using only `static.ExternalInitiatorAccessKeyHeader` / `static.ExternalInitiatorSecretHeader` headers (no session cookie, no API token), similar to `cltest.UnauthenticatedPost` usage pattern seen in `core/services/job/runner_integration_test.go` [6](#0-5) , but targeting an int32 job ID instead of a UUID webhook job.
4. Assert response is `200 OK`/`201` with a `pipelineRun` resource (instead of the expected `422`/`403` rejection), and assert `app.PipelineORM()` shows a new row in `pipeline_runs` for that job — proving `RunJobV2` executed for an EI-only caller.
5. Unit-test alternative: directly call `auth.GetAuthenticatedUser(ginCtxWithEIAuthApplied)` and assert `isUser == true`, demonstrating the root-cause identity confusion independent of the full HTTP stack.
