### Title
Epoch tag recorded at request time vs. `epochNumber` overwritten mid-`stopEpoch` lets a loss-adjusted withdraw receipt claim at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` mirrors the PackageKit TOCTOU pattern: `requestWithdraw` caches the receipt's epoch (`lastWithdrawRequest[_user]`, `withdrawsRequestsByEpoch[_user][currentEpoch]`) at "authorization" time, but the loss haircut is keyed to whatever `epochNumber` happens to be at `collectWithdrawFunds` execution time. Because `epochNumber` is bumped inside `deposit()` during the same `stopEpoch` — before pending receipts are funded/loss-adjusted — a receipt requested in epoch N is tagged N while its haircut is stored under `lossRecoveryPriceByEpoch[N+1]`. The claim path then looks up the stale tag, misses the haircut, and pays the full basis from underfunded reserves.

### Finding Description
Three code points combine exactly like the advisory's three bugs:

1. **Unconditional epoch-tag write (request time).** `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` where `currentEpoch = epochNumber` read at call time (lines 260–293). `contracts/strategies/idle/IdleCreditVault.sol:260-293`
2. **State overwrite before the flag is read.** `deposit()` increments `epochNumber` when called while `isEpochRunning()` is still true — i.e., during `stopEpoch`'s deposit phase, before `collectWithdrawFunds` runs (lines 607–614). `collectWithdrawFunds` then stores the realized loss under `lossRecoveryPriceByEpoch[epochNumber]` — the already-incremented N+1 — while zeroing `pendingWithdraws` and pulling only `_amount < pendingBasis` from the CDO (lines 411–430). `contracts/strategies/idle/IdleCreditVault.sol:607-614` and `contracts/strategies/idle/IdleCreditVault.sol:411-430`
3. **Late read of the stale tag.** `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — N — finds 0, and returns early (lines 789–801). The receipt then falls through to `_claimFundedWithdrawRequest`, which passes its gate because `epochNumber (N+1) > lastWithdrawRequest (N)` and pays the full unhaircutted `withdrawsRequests[_user]` (lines 319–349). `contracts/strategies/idle/IdleCreditVault.sol:789-801` and `contracts/strategies/idle/IdleCreditVault.sol:319-349`

The guard at `requestWithdraw` lines 263–271 only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest]`, so it never sees a haircut stored under N+1 and does not stop a follow-up request either — the corrupted state persists silently, just like the dismissed `RUNNING → WAITING_FOR_AUTH` transition.

### Impact Explanation
The vault transferred only `pendingBasis * lossRecoveryPrice` to the strategy, but the receipt holder withdraws `pendingBasis` in full. `_transferFundedClaim` only ring-fences `defaultRecoveryReserve`, so the excess is paid from underlyings belonging to other funded claims and the CDO itself: a direct theft of `basis * (1 - lossRecoveryPrice)` by the first claimant, and permanent freezing/insolvency for later claimants whose transfers revert or underpay. On a 1,000,000-unit pending bucket with a 30% realized loss, the first user to claim extracts ~300,000 units that were never funded.

### Likelihood Explanation
Requires only an unprivileged tranche holder: deposit, call `requestWithdraw` during the buffer of epoch N, wait for a `stopEpoch` that realizes any partial loss on pending receipts (an honest manager/borrower path — `stopEpochWithDuration(_lossAmount)` is a normal operation), then call `claimWithdrawRequest`. No privileged role is attacker-controlled; the sequence is entirely user-initiated around honest manager calls.

### Recommendation
Store the loss under the epoch the pending receipts actually belong to (e.g., `epochNumber - 1` semantics captured before `deposit()` bumps the counter), or snapshot `epochNumber` into a local at the top of `stopEpoch` and pass it to `collectWithdrawFunds`. Alternatively, track per-user pending-receipt epochs in a set rather than a single `lastWithdrawRequest` slot, and make `_claimLossAdjustedWithdrawRequest` scan all request epochs, not just the latest tag.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "../IdleCreditVault.t.sol"; // reuse existing harness helpers

contract LossEpochTagToctouPoC is TestIdleCreditVault {
    function testLossEpochTagMismatchPaysPar() external {
        uint256 amount = 1_000_000 * ONE_SCALE;
        address alice = makeAddr("alice");
        _depositWithUser(alice, amount, true);          // KYC'd lender, AA
        idleCDO.depositAA(amount);                      // second LP to keep pool solvent

        // epoch 0 runs
        _startEpochAndCheckPrices(0);
        _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
        // buffer of epoch 1: alice requests withdraw -> tagged epochNumber == 1
        uint256 aliceTranches = IERC20Detailed(address(AAtranche)).balanceOf(alice);
        vm.prank(alice);
        uint256 basis = cdoEpoch.requestWithdraw(aliceTranches, address(AAtranche));
        assertEq(strategy.lastWithdrawRequest(alice), 1);

        // manager stops epoch 1 WITH a loss covering only part of pending receipts.
        // Inside stopEpoch: strategy.deposit() bumps epochNumber to 2 BEFORE
        // collectWithdrawFunds stores lossRecoveryPriceByEpoch[2].
        uint256 loss = _expectedFundsEndEpoch() / 4;    // 25% loss
        _stopEpochWithLoss(1, loss);                    // helper: stopEpochWithDuration
        assertEq(strategy.epochNumber(), 2);
        assertGt(strategy.lossRecoveryPriceByEpoch(2), 0);
        assertEq(strategy.lossRecoveryPriceByEpoch(1), 0);   // alice's tag -> no haircut
        assertEq(strategy.pendingWithdraws(), 0);            // basis cleared at funding

        uint256 balPre = underlying.balanceOf(alice);
        vm.prank(alice);
        cdoEpoch.claimWithdrawRequest();
        uint256 claimed = underlying.balanceOf(alice) - balPre;

        uint256 funded = basis * strategy.lossRecoveryPriceByEpoch(2) / 1e18;
        // BUG: alice is paid the full basis although only `funded` was transferred in.
        assertEq(claimed, basis);
        assertGt(claimed, funded);                      // stolen = basis - funded
    }
}
```
Note: this PoC assumes `IdleCDOEpochVariant.stopEpoch` invokes `strategy.deposit()` (which bumps `epochNumber` inside `deposit()` at `IdleCreditVault.sol:610`) before calling `collectWithdrawFunds`. That ordering should be verified against the actual `stopEpoch` implementation; if funding happens before the counter bump, the tags align and the bug collapses — this was the one ordering I could not fully trace within the iteration limit.
