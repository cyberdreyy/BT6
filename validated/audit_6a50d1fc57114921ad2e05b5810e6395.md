### Title
Unfunded instant-withdraw receipts are paid from commingled strategy funds, letting early claimants drain other users' funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays out the full aggregate `instantWithdrawsRequests[_user]` without verifying that the underlying for that receipt was actually collected into the strategy via `collectInstantWithdrawFunds`. This is the credit-vault analog of the tcpdump buffer over-read: the function "reads" (pays out) receipt data past the boundary of what was funded, treating unfunded receipts as backed. Because funded normal-withdraw proceeds (`collectWithdrawFunds`) and funded instant proceeds sit in the same strategy balance, an unprivileged user holding an unfunded instant receipt can withdraw underlyings that belong to other claimants.

### Finding Description
Instant withdraw requests are created by `requestInstantWithdraw`, which mints the user a 1:1 strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). Separately, the CDO pulls underlying into the strategy with `collectInstantWithdrawFunds(_amount)`, which decrements `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`).

The claim path, `claimInstantWithdrawRequest`, burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` (`IdleCreditVault.sol:380-393`). Critically:

- `pendingInstantWithdraws` is decremented only at collect time, never at claim time, and the claim path never checks it. A receipt that was recorded but whose underlying was never collected (borrower under-funded the instant bucket, or the CDO collected only partially) is still fully claimable.
- `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) only guards `defaultRecoveryReserve`; it does not reserve the outstanding `pendingInstantWithdraws` basis of *other* users or the funded normal-withdraw bucket. So a claim on an unfunded receipt is paid out of whatever underlying balance the strategy holds — including funds collected for other users' instant and normal withdraw claims.

The per-epoch ledgers (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) exist only for default accounting; the happy-path claim reads the aggregate with no funded-boundary check — the direct analog of reading a buffer past its valid length.

### Impact Explanation
A user whose instant-withdraw receipt was never funded can still burn it and receive underlying tokens, stealing from the strategy balance that backs honest claimants (funded instant receipts, funded normal withdraw receipts). The loss is bounded by the strategy's spendable balance minus `defaultRecoveryReserve`; in practice the attacker can extract up to the full unfunded receipt amount, directly causing insolvency for the last claimants (their claims revert on insufficient balance — permanent freezing/theft of their funded claims).

### Likelihood Explanation
Requires an epoch where instant withdraws are enabled and the borrower's repayment (or CDO's collection via `collectInstantWithdrawFunds`) covers only part of `pendingInstantWithdraws`, while the strategy still holds underlying collected for other claims. The attacker is an ordinary KYC-passing lender/tranche holder requesting an instant withdraw — no privileged role needed. The sequence is entirely within normal epoch transitions.

### Recommendation
In `claimInstantWithdrawRequest`, track the funded portion of instant receipts (e.g., decrement `pendingInstantWithdraws` per claim or maintain a funded-claims counter set by `collectInstantWithdrawFunds`) and only pay receipts that have been collected; alternatively have `_transferFundedClaim` also reserve the outstanding `pendingInstantWithdraws` basis of non-claiming users so unfunded receipts cannot spend other users' funded proceeds.

### Proof of Concept
Foundry fork scenario (against `IdleCDOEpochVariant` + `IdleCreditVault` + real underlying, using the existing `test/foundry/IdleCDOEpochQueue.t.sol` harness pattern):

```solidity
// Setup: enable instant withdrawals via cdoEpoch.setInstantWithdrawParams(delay, aprDelta, true)
// Users A (attacker) and B both depositAA, then request instant withdraws of amountA and amountB
// during the running epoch (via cdoEpoch path -> strategy.requestInstantWithdraw).

// Epoch stops; borrower repays only enough for ONE instant request.
// Honest manager calls the CDO collect path, which pulls only amountB's underlying:
//   strategy.collectInstantWithdrawFunds(amountB)   // pendingInstantWithdraws = amountA remains

// Attacker A calls the user-facing claim path on the CDO:
//   cdoEpoch.claimInstantWithdrawRequest()          // -> strategy.claimInstantWithdrawRequest(A)
// Inside IdleCreditVault:
//   amount = instantWithdrawsRequests[A] == amountA  // unfunded receipt, still fully counted
//   _burn(A, amountA); _transferFundedClaim(A, amountA) // pays out of B's collected funds

// Assert: underlying.balanceOf(A) increased by amountA even though pendingInstantWithdraws
// still equals amountA (nothing was collected for A).

// Victim B then calls claimInstantWithdrawRequest():
//   reverts / underpays because strategy balance is now short by amountA,
//   even though B's receipt WAS funded. Theft of B's funded claim by A.
```

Key assertions:
- `strategy.pendingInstantWithdraws() == amountA` after A's claim (A's receipt was never funded).
- `underlying.balanceOf(A)` increased by `amountA`.
- B's subsequent claim reverts on insufficient strategy balance or pays less than `amountB`.

Note: this finding assumes the CDO-side `claimInstantWithdrawRequest` entry point is reachable by the receipt holder independently of whether `collectInstantWithdrawFunds` covered that receipt (consistent with how `claimWithdrawRequest` is user-callable in `IdleCDOEpochVariant.sol`); if the CDO strictly couples collection to each claim, the unfunded-claim path is not reachable and this reduces to a defense-in-depth gap in `_transferFundedClaim`.
