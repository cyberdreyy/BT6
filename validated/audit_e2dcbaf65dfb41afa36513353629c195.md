### Title
`createDstEscrow` deploys destination escrows with unvalidated fee amounts, enabling always-reverting `withdraw`/`publicWithdraw` and theft of maker funds via `cancel` - (File: contracts/BaseEscrowFactory.sol)

### Summary
`BaseEscrowFactory.createDstEscrow` accepts caller-supplied `Immutables` (including the packed `parameters` field holding `protocolFeeAmount`/`integratorFeeAmount`) with no check that `integratorFeeAmount + protocolFeeAmount < amount`. The equivalent check exists on the source path (`_postInteraction`) but is missing on the destination path, so `EscrowDst._withdraw`'s unchecked subtraction `immutables.amount - integratorFeeAmount - protocolFeeAmount` will underflow and revert forever for a maliciously configured escrow, letting the taker later reclaim the maker's funds via `cancel()`.

### Finding Description
On the source chain, `BaseEscrowFactory._postInteraction` explicitly guards against fee amounts consuming the whole taking amount: [1](#0-0) 

This check protects the values later embedded into `DstImmutablesComplement.parameters` (`protocolFeeAmount`, `integratorFeeAmount`) emitted in `SrcEscrowCreated`.

However, `createDstEscrow` is a permissionless external function that takes the full `Immutables` struct — including `parameters` — directly from `msg.sender`, with **no re-validation of the fee invariant**: [2](#0-1) 

There is no on-chain linkage forcing the `dstImmutables.parameters` passed into `createDstEscrow` to match the values computed/emitted by `_postInteraction` on the source chain — the caller is free to encode any `protocolFeeAmount`/`integratorFeeAmount` values.

When the destination escrow is later settled, `EscrowDst._withdraw` performs an unchecked subtraction using these caller-chosen values: [3](#0-2) 

Since Solidity 0.8.23 has built-in overflow/underflow checks, if `integratorFeeAmount + protocolFeeAmount > immutables.amount`, the subtraction on line 92 reverts unconditionally. Both `withdraw` and `publicWithdraw` route through `_withdraw`: [4](#0-3) 

so **no path can ever deliver funds to the maker** for such an escrow. Once the `DstCancellation` timelock passes, the `taker` (the same account that deployed the malformed escrow via `createDstEscrow`, funding it with the maker's expected settlement amount) can call `cancel()` and reclaim the **entire** `immutables.amount` back to themselves: [5](#0-4) 

This is the same root-cause class as the reported OETH bug: a subtraction/balance invariant that is enforced on one code path (`_postInteraction`) but omitted on a structurally parallel path (`createDstEscrow`) that feeds the same downstream computation, producing either a wrong value (OETH) or, here, a permanently broken (always-reverting) computation that can be leveraged to divert funds.

### Impact Explanation
This matches the **Critical** bounty category: permanent freezing of the maker's destination funds, escalating to direct theft when the taker exercises `cancel()` after the cancellation timelock to reclaim the funds that were supposed to go to the maker. It is triggered purely by the permissionless `createDstEscrow` entry point explicitly listed as in-scope in the "Destination path" pivot, requiring no privileged role — any account acting as `taker` in a self-crafted `Immutables` struct can execute this.

### Likelihood Explanation
Likelihood is high for an economically motivated participant: `createDstEscrow` performs no validation on the `parameters` bytes beyond length checks performed lazily via `ImmutablesLib` accessors at withdrawal time. Constructing a malicious `Immutables.parameters` (`protocolFeeAmount`, `integratorFeeAmount`, and recipients) that sum to >= `amount` requires only ABI-encoding four extra words; there is no economic cost beyond funding the safety deposit and the destination amount itself (which is later reclaimed via `cancel`), making this cheap and repeatable.

### Recommendation
Add the same invariant check used in `_postInteraction` to `createDstEscrow`:
```solidity
if (dstImmutables.integratorFeeAmount() + dstImmutables.protocolFeeAmount() >= dstImmutables.amount) revert InvalidFeeAmounts();
```
placed before deployment/funding in `createDstEscrow`, mirroring line 92 of `contracts/BaseEscrowFactory.sol`.

### Proof of Concept
1. Attacker (as `taker`) calls `createDstEscrow` with a self-chosen `maker`, valid `hashlock`, `amount = A`, and `parameters` encoding `protocolFeeAmount = A`, `integratorFeeAmount = 1`, plus arbitrary fee recipients (their own addresses), funding it with `msg.value = safetyDeposit (+ amount if native)`.
2. `createDstEscrow` deploys the clone with no fee-sum validation (see `contracts/BaseEscrowFactory.sol:165-185`).
3. Once the withdrawal window opens, any attempt to call `withdraw`/`publicWithdraw` on the clone reaches `EscrowDst._withdraw` line 92 (`contracts/EscrowDst.sol:92`), where `A - A - 1` underflows and reverts — permanently, since `immutables` are fixed at deployment.
4. After `DstCancellation` time, the attacker (as `taker`) calls `cancel()` (`contracts/EscrowDst.sol:64-73`), receiving back the full `immutables.amount` and the safety deposit, while the intended maker never received anything.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```
