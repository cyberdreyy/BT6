### Title
Cross-job pipeline run disclosure via `PipelineRunsController.Show` ignoring the `:ID` job path parameter - ([File: core/web/pipeline_runs_controller.go])

### Summary
`GET /v2/jobs/:ID/runs/:runID` is expected to return a run scoped to the job identified by `:ID`, but `Show` only looks up the run by `:runID` and never checks that it belongs to `:ID`. Any authenticated user (including view-role) can supply job A's ID with job B's run ID and receive job B's run data.

### Finding Description
The route is registered as `authv2.GET("/jobs/:ID/runs/:runID", prc.Show)` (mounted under `authv2`, which only requires authentication, not any specific role) [1](#0-0) . In the handler, `c.Param("ID")` is never read; only `c.Param("runID")` is parsed and passed to `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)`, which looks up the run purely by its own primary key with no job-ownership filter: [2](#0-1) . Since `FindRun` performs no cross-check against the `:ID` path segment, an authenticated view-role user who knows or guesses/enumerates any `runID` (a small sequential integer, easily enumerable) can fetch that run's full data regardless of which job it belongs to or whether the requester has any relationship to that job.

### Impact Explanation
This is a cross-user/cross-job authorization (IDOR) issue: an authenticated but otherwise low-privileged (view-role) user can read pipeline run outputs, task run inputs/outputs, and error data belonging to jobs they should not have visibility into or association with in the URL they used. This matches the "unauthorized access to another user's job data / cross-user response confusion" impact class — sensitive data disclosure through broken object-level authorization, not full node compromise but a legitimate confidentiality/authorization violation.

### Likelihood Explanation
Exploitation only requires a valid session or API token with the lowest privilege (view role, which is granted access to `authv2` routes with no role restriction on this endpoint) and knowledge of any run ID, which are sequential integers and thus easily enumerable across all jobs on the node. No special timing, race condition, or admin access is required — the request is trivially repeatable.

### Recommendation
In `Show`, parse `c.Param("ID")` into a job ID (as `Index` already does), and either call an ORM method that scopes the run lookup by both job ID and run ID (e.g., `FindRun(ctx, jobID, runID)`), or after fetching the run, verify `pipelineRun.PipelineSpec.JobID`/equivalent matches the requested job ID, returning `404 Not Found` on mismatch.

### Proof of Concept
Go handler-level integration test (in `core/web/pipeline_runs_controller_test.go` style):
1. Create Job A and Job B via `JobsController.Create` (or directly via ORM) as an admin.
2. Trigger a pipeline run for Job B, capturing its `runID` from the response.
3. As a view-role authenticated client, issue `GET /v2/jobs/<JobA.ID>/runs/<JobB_runID>`.
4. Assert: currently returns HTTP 200 with a JSON body whose `id`/`pipelineSpecID`/outputs correspond to Job B's run — i.e., the response is job B's data despite the URL specifying job A.
5. Expected (fixed) behavior: assert HTTP 404 (or 403) instead, since the `runID` does not belong to job A.

```go
func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
```
