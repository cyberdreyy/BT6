### Title
Unauthenticated APR manipulation during the pre-`setWhitelistedCDO` window - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.setApr` enforces caller restrictions only when `idleCDO != address(0)`. Because `idleCDO` is configured in a separate, owner-initiated `setWhitelistedCDO` transaction rather than atomically inside `initialize`, there is a window after deployment where the vault is live (`token`, `borrower`, `lastApr`, `maxApr` all set) but `idleCDO == address(0)`. During that window any unprivileged EOA can call `setApr`/`setAprs`/`setAprsWithBuffer` and overwrite `lastApr`/`unscaledApr` to any value up to `maxApr` (default `20e18`). This is the direct analog of improper ACL on a privileged resource: an authorization check silently disabled because the privileged identity is not yet bound. [1](#0-0) [2](#0-1) 

### Finding Description
- `initialize` sets `token`, `borrower`, `manager`, `lastApr = _apr`, `unscaledApr = _apr`, `maxApr = DEFAULT_MAX_APR`, but never sets `idleCDO`. [3](#0-2) 
- `setWhitelistedCDO` is `onlyOwner` and normally called in a later transaction, so `idleCDO == 0` persists between the two transactions. [4](#0-3) 
- `setApr` skips its `NotAllowed` check entirely when `_cdo == address(0)` — the comment claims this "can happen only during the setup", but nothing prevents a third party from calling it during that setup window. [1](#0-0) 
- `setAprs` and `setAprsWithBuffer` inherit the same weakness and additionally write `unscaledApr` before delegating the permission check to `setApr`. [5](#0-4) 
- `lastApr` is returned by `getApr()` [6](#0-5)  and is what `IdleCDOEpochVariant` uses to compute `expectedEpochInterest` — the fixed interest the borrower owes per epoch. `unscaledApr == 0` also gates the separate `apr0Users` accounting flow in `requestWithdraw`/`prepareStopEpochWithApr0`. [7](#0-6) 

Attack sequence (buffer phase, before first `startEpoch`, while `idleCDO == 0`):
1. Attacker (a KYC-passing lender holding tranche tokens, or any EOA) calls `setApr(20e18)` — or `setAprs(0, 0)` to force the APR0 path.
2. Owner completes setup via `setWhitelistedCDO`; `idleCDO` is now bound, the attacker-set `lastApr`/`unscaledApr` remain.
3. `startEpoch` runs: with inflated `lastApr`, `expectedEpochInterest` is computed at up to 2000% scaled APR, so the honest borrower must repay principal plus massively inflated interest, which flows to tranche holders (the attacker included). Alternatively, `unscaledApr = 0` routes withdraw requesters into the `apr0Users` bucket, and `prepareStopEpochWithApr0` reverts `NotAllowed` only if `unscaledApr != 0` — the corrupted flag silently changes who receives realized interest. [8](#0-7) 

### Impact Explanation
Direct theft of yield: the attacker raises `lastApr` up to `maxApr` (20e18) and every tranche holder — including the attacker's own position — is owed interest computed on that inflated APR for the first epoch, paid from borrower funds. Loss is bounded by `maxApr * TVL * (epochDuration + buffer)/YEAR` (≈5.5% of epoch TVL per week at the default cap). The alternative `unscaledApr = 0` write misroutes withdraw-request interest into/out of the `apr0Users` bucket, diverting net interest between requesters and active LPs — theft/redistribution of unclaimed yield. No existing guard stops it: the `maxApr` cap only bounds magnitude, and the `NotAllowed` check is explicitly skipped when `idleCDO == 0`.

### Likelihood Explanation
Conditional on deployment sequencing: `initialize` and `setWhitelistedCDO` are two distinct transactions and are not executed atomically by the factory in-contract (the vault's own initializer cannot set `idleCDO` because the CDO is deployed after the strategy). Any block gap between them is exploitable by a public-mempool observer at near-zero cost (one `setApr` call). No privileged role is required, no timing manipulation beyond calling first, and the corrupted values persist until manager/CDO later overwrites them — which for `unscaledApr` may never happen if epochs run with the CDO-driven `setAprsWithBuffer` only updating `lastApr`. Caveat: if a deployment script batches both calls in one transaction, the window closes; the vulnerability is that the contract itself does not enforce this.

### Recommendation
Bind the privileged identity atomically: either require `idleCDO` as an `initialize` parameter (deploying the CDO behind a known/predicted address or a factory that passes a precomputed proxy address), or revert in `setApr`/`setAprs`/`setAprsWithBuffer` when `idleCDO == address(0)` and add a separate one-time `onlyOwner` APR setter for the genuine setup path. Alternatively, guard `setApr` with `msg.sender == owner()` while `idleCDO` is unset.

### Proof of Concept
Foundry fork test (scaffold mirrors existing `test/foundry` credit-vault setups):

```solidity
// test/foundry/SetAprAccessControl.t.sol
function test_AnyoneCanSetAprBeforeWhitelistedCDO() public {
    // Deploy vault + initialize via factory; DO NOT call setWhitelistedCDO yet.
    IdleCreditVault vault = IdleCreditVault(factory.createVault(...));
    // factory internally called initialize(...) -> idleCDO == address(0)
    assertEq(vault.idleCDO(), address(0));
    assertEq(vault.lastApr(), INITIAL_APR);

    address attacker = makeAddr("attacker"); // no role, not KYC'd, not manager
    vm.prank(attacker);
    vault.setApr(20e18);              // succeeds: check skipped, capped only by maxApr
    assertEq(vault.lastApr(), 20e18);

    vm.prank(attacker);
    vault.setAprs(0, 0);              // also corrupts unscaledApr -> APR0 flow hijack
    assertEq(vault.unscaledApr(), 0);

    // Owner finishes setup; attacker-set values persist.
    vm.prank(owner);
    vault.setWhitelistedCDO(address(cdo));
    assertEq(vault.lastApr(), 0);
    assertEq(vault.unscaledApr(), 0);
    // Subsequent epochs compute expectedEpochInterest / apr0 accounting off
    // attacker-controlled APR until manager explicitly corrects both fields.
}
```

    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();

    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
