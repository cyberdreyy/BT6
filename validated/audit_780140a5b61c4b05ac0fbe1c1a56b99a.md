## Title
Operator-controlled beneficiary can permanently freeze a staker's principal in `staking_contract` by weaponizing `aptos_account::deposit_coins`'s opt-out revert - (`File: aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
The reported ERC20 bug class is: a call site assumes a token transfer will always succeed, but an external, attacker-influenced transfer target can make it revert, permanently blocking withdrawal. The Aptos-native analog is `staking_contract::distribute_internal`, which is unconditionally invoked as a prerequisite step by every staker-facing withdrawal entrypoint (`unlock_stake`, `distribute`, `unlock_rewards`) and pays the operator's commission to `beneficiary_for_operator(operator)` via `aptos_account::deposit_coins`. That deposit function reverts if the recipient has opted out of unsolicited coin transfers and is not yet registered for the coin type. Because the operator — not the staker — controls the beneficiary address, an operator can pick a beneficiary address it also controls and configure it to reject the transfer, causing `distribute_internal` to abort on every future call and permanently freezing the staker's entire stake.

### Finding Description
`distribute_internal` withdraws all currently-withdrawable (inactive + pending_inactive) stake from the pool and pays out every shareholder in the internal `pool_u64` distribution pool, including the operator's commission: [1](#0-0) 

Note the redirection: if `recipient == operator`, the payout target is swapped to `beneficiary_for_operator(operator)`, an address fully controlled by the operator via `set_beneficiary_for_operator`: [2](#0-1) 

The payment call, `aptos_account::deposit_coins`, aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` whenever the recipient is unregistered for the coin type and has disabled arbitrary transfers via `set_allow_direct_coin_transfers(false)`: [3](#0-2) [4](#0-3) 

Because `distribute_internal` is called unconditionally at the top of `unlock_stake`, and again by the standalone `distribute` entrypoint (used, e.g., by vesting's `withdraw_stake` and the CLI's `withdraw-stake` flow for `StakingContract`-backed pools), any abort inside it fails the entire transaction and rolls back the staker's requested unlock/withdrawal too: [5](#0-4) [6](#0-5) 

An operator can:
1. Create/control a second account, disable direct coin transfers on it via `set_allow_direct_coin_transfers(false)` while never registering it for `AptosCoin` under the legacy `coin` module path.
2. Call `set_beneficiary_for_operator(operator, that_address)` on the staking contract they operate.
3. As soon as the operator accrues any nonzero commission (`distribution_amount != 0` with the operator holding shares), every subsequent `distribute_internal` invocation — triggered by the staker's own `unlock_stake`/`distribute`/`unlock_rewards` calls — will attempt `aptos_account::deposit_coins` to the poisoned beneficiary and abort.

This traps the staker's entire principal (and rewards) inside the stake pool with no code path to bypass `distribute_internal`, since it is not staker-gated and runs before the staker's own operation executes.

### Impact Explanation
This breaks the "Owner, operator, voter, and beneficiary boundaries must hold" and "Unlock/withdraw ... paths must not ... permanently strand value" invariants explicitly called out in the task's pivots. A role (operator) that is only supposed to earn commission gains the unilateral ability to permanently lock the staker's principal and rewards, without ever touching the staker's keys or the owner capability. This is a high-severity, non-recoverable loss of claim rights for the staker — value becomes permanently unwithdrawable through the intended `staking_contract` API.

### Likelihood Explanation
The only precondition is that the attacker already occupies the `operator` role for a `staking_contract` (a role assigned by the staker at contract creation, not a privileged system role) and controls one throwaway address to use as its beneficiary. No collusion from the staker or owner capability is required, and the griefing address only needs to be set up once before commission next accrues. This is realistically triggerable by any operator who wants to hold a staker's funds hostage (e.g., to extort a higher commission split or retaliate against a switch-operator attempt).

### Recommendation
- Make the operator's commission payout resilient to recipient-side reverts: wrap `aptos_account::deposit_coins` to the beneficiary in a fallback path (e.g., deposit into an escrow/claimable resource if the direct deposit would abort) instead of letting one payout failure abort the entire distribution and the staker's requested operation.
- Alternatively, decouple the staker's `unlock_stake`/`distribute` success from the operator's commission payout success — allow the staker-owned share of `distribution_pool` to be redeemed independent of whether the operator's/beneficiary's share succeeds.
- Consider disallowing `set_beneficiary_for_operator` targets that have not affirmatively pre-registered/opted-in for `AptosCoin`, or validate the beneficiary can currently accept `AptosCoin` before allowing it to be set.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`.
2. `operator` sets up account `X`, calls `aptos_account::set_allow_direct_coin_transfers(X_signer, false)`, and does not register `X` for `AptosCoin` under the legacy `coin` module path.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, X)`.
4. Validator earns rewards; commission accrues so the operator's pool_u64 share of the distribution pool becomes nonzero.
5. Staker calls `unlock_stake(staker, operator, amount)` (or `distribute`/`unlock_rewards`). Execution reaches `distribute_internal` → `aptos_account::deposit_coins(X, ...)` → aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`, reverting the entire transaction.
6. Every future call to `unlock_stake`, `distribute`, or `unlock_rewards` for this staker/operator pair reverts identically, since a nonzero operator commission is unavoidable once rewards accrue — permanently freezing the staker's stake.

**Caveat / unverified detail:** I could not fully confirm within this session whether `coin::is_account_registered<AptosCoin>` and `coin::deposit<AptosCoin>` retain the "opt-out" abort behavior post-migration to the fungible-asset primary store, versus the newer `aptos_account::fungible_transfer_only` path (which the code explicitly documents as bypassing frozen/opt-out checks because "APT cannot be frozen"). `staking_contract.move` uses the generic `Coin<AptosCoin>`/`aptos_account::deposit_coins<CoinType>` path (not `fungible_transfer_only`), which is what is analyzed above, but the exact current semantics of `coin::is_account_registered`/`coin::deposit` for the migrated `AptosCoin` type should be double-checked in `aptos-move/framework/aptos-framework/sources/coin.move` before treating this as conclusively exploitable on current mainnet state.

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
