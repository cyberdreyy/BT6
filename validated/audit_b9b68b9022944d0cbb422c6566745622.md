I found a genuine analog to the reported bug in the Gloas builder-withdrawal logic. The `Vault`-style flaw ("optimistically transfer, don't verify/cap the amount actually backed") maps directly onto how builder pending withdrawals are computed vs. applied.

## Analysis

`get_builder_withdrawals` builds the `Withdrawal` objects that become part of `state.payload_expected_withdrawals` — the object the execution layer is contractually committed to honor (crediting `withdrawal.amount` Gwei to `withdrawal.address`) — using the **raw requested** `withdrawal.amount` from `state.builder_pending_withdrawals`, with no cap against the builder's actual balance: [1](#0-0) 

But `apply_withdrawals`, which mutates the consensus-layer-tracked `builder.balance`, caps the deduction to `min(withdrawal.amount, builder_balance)`: [2](#0-1) 

So if a `BuilderPendingWithdrawal.amount` exceeds the builder's current `balance`, the CL-committed `Withdrawal.amount` (which the EL must pay out in full to `fee_recipient`) still equals the full requested amount, while the CL-side balance is only reduced by the smaller, capped amount. This is exactly the "optimistic transfer without checking the real backing" bug pattern from the report — except here it's not funds getting stuck, it's Gwei effectively minted: the execution layer pays out more than the beacon state actually deducts.

This is confirmed by the test suite itself, which explicitly asserts this behavior as expected: [3](#0-2) 

### Title
Builder withdrawal amount is not capped to available balance before being committed to the execution payload, allowing Gwei to be created beyond the builder's tracked balance - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` copies the requested `amount` from `state.builder_pending_withdrawals` uncapped into the `Withdrawal` object that is committed to `payload_expected_withdrawals`. `apply_withdrawals` only reduces `builder.balance` by `min(withdrawal.amount, builder_balance)`. The execution layer is required to pay the full, uncapped `withdrawal.amount` to the withdrawal address, so when a pending withdrawal request exceeds the builder's actual balance, more Gwei is paid out on the execution layer than is deducted from consensus-layer state.

### Finding Description
`BuilderPendingWithdrawal.amount` entries are appended (e.g., via bid-payment settlement) without an enforced invariant that they never exceed `builder.balance` at the time of processing (a builder's balance can be reduced between when the pending withdrawal is queued and when it is processed, e.g. by other withdrawals draining it first). `get_builder_withdrawals` propagates this `amount` verbatim into the payload-level `Withdrawal.amount`, which becomes part of the deterministic `payload_expected_withdrawals` that the execution layer is required to honor exactly. `apply_withdrawals`, however, only decreases `state.builders[builder_index].balance` by `min(withdrawal.amount, builder_balance)` — capping the CL-side accounting but not the EL-side payment commitment. The two sides of the withdrawal (CL deduction vs. EL credit) can therefore diverge, breaking the invariant that a withdrawal transfers exactly the Gwei that was deducted from the source.

### Impact Explanation
This breaks the "Gwei created, destroyed, or paid to a non-owner" equality: the execution layer credits `withdrawal.amount` Gwei to `fee_recipient`/`address` while the beacon state only debits `min(withdrawal.amount, builder_balance)` from the builder. Any shortfall is Gwei paid out that was never backed by a corresponding balance decrease anywhere in the system — net new value created on the execution layer.

### Likelihood Explanation
Requires a builder's `balance` to be less than a queued `BuilderPendingWithdrawal.amount` at processing time (e.g., balance drained by an intervening builder-sweep withdrawal or exit before the pending payment settles). The test suite itself demonstrates this exact scenario is reachable and treated as expected/spec-conformant, not filtered out.

### Recommendation
Cap `withdrawal.amount` to `min(requested_amount, builder.balance)` inside `get_builder_withdrawals` (or wherever the `Withdrawal` object destined for the execution payload is constructed), so the amount committed to the execution layer always matches the amount actually deducted from the builder's consensus-layer balance.

### Proof of Concept
1. Queue a `BuilderPendingWithdrawal` for `builder_index` requesting `amount = 5 ETH`.
2. Ensure `state.builders[builder_index].balance = 1 ETH` at processing time (e.g., balance was reduced by another withdrawal processed earlier in the same sweep, or simply set lower than the pending request as in `test_builder_withdrawal_insufficient_balance`).
3. Call `get_expected_withdrawals(state)` / run block processing: the resulting `Withdrawal.amount` in `payload_expected_withdrawals` is `5 ETH` (per [4](#0-3) ), which the execution layer must pay out in full to the builder's `fee_recipient`.
4. `apply_withdrawals` reduces `state.builders[builder_index].balance` from `1 ETH` to `0` — only 1 ETH deducted from CL state, but 5 ETH was paid on the EL side, a 4 ETH discrepancy created from nothing.
