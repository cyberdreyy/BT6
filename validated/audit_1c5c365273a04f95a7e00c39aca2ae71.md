### Title
Fee-on-transfer recovery funding overstates the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`finalizeDefaultRecovery` calculates and stores the recovery reserve and recovery price using the declared `_recoveredAmount` before pulling the tokens. If the underlying takes a transfer fee, the strategy records more recoverable assets than it receives, causing inflated claims and a permanent shortfall for later claimants. [1](#0-0) 

### Finding Description
`reserveAmount` is calculated as `_recoveredAmount + prefundedReserve + defaultRecoveryReserve`, and `defaultRecoveryReserve` and `defaultRecoveryPrice` are persisted before the external transfer is executed. [2](#0-1) 

The strategy can also mint additional strategy tokens to the CDO when the overstated recovery price increases `activeFinalNAV`, giving active tranches accounting value that is not backed by received underlying. [3](#0-2) 

Only after this accounting is finalized does the strategy pull `_recoveredAmount`; the code never verifies that the strategy balance increased by the same amount. [4](#0-3) 

A valid sequence is:

1. The vault is funded while the configured ERC-20 has no fee, or while its fee is disabled.
2. Borrower default occurs and the CDO enters the defaulted state.
3. The token activates a nonzero transfer fee.
4. A recovery source approves `R` tokens.
5. The manager calls `IdleCDOEpochVariant.finalizeDefault(R, recoverySource)`. [5](#0-4) 
6. `finalizeDefaultRecovery` books `R`, but the strategy receives only `R - fee`.
7. Defaulted receipt claims are paid according to the inflated `defaultRecoveryPrice`, so earlier claimants can consume the entire real reserve and later claims revert or remain unpaid. [6](#0-5) 

Normal deposits already use the received-balance delta for tranche minting, which makes the recovery path inconsistent with the vault’s own fee-on-transfer handling. [7](#0-6) 

### Impact Explanation
For a claimed recovery of `R` and transfer fee `f`, the strategy books `R` but receives `R - f`, creating an immediate reserve deficit of `f`. [8](#0-7) 

Claims continue to be valued against the inflated `defaultRecoveryPrice`, so payouts can exhaust the actual token balance before all valid claims are paid. [6](#0-5) 

Because finalization is one-time, the shortfall cannot be corrected by another recovery top-up through this path, leaving affected users with permanently frozen or unpaid claims. [9](#0-8) 

### Likelihood Explanation
Likelihood is conditional: the underlying must support or later activate transfer fees, and a default must reach recovery finalization. [10](#0-9) 

No privileged attacker is required for the token discrepancy itself; an unprivileged recovery source merely approves the declared amount, while the honest manager performs the finalization call. [11](#0-10) 

If the fee is enabled before the vault is initially funded, deposits may revert earlier because the deposit path forwards the declared `_amount` to the strategy rather than the received amount; therefore, the most realistic deployment scenario is a token whose fee is activated after funding. [12](#0-11) 

### Recommendation
Measure the actual received recovery amount and use it for `reserveAmount`, `defaultRecoveryReserve`, and `defaultRecoveryPrice`:

```solidity
uint256 balanceBefore = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(_recoverySource, address(this), _recoveredAmount);
uint256 received = underlyingToken.balanceOf(address(this)) - balanceBefore;
require(received == _recoveredAmount, "fee-on-transfer unsupported");
```

Alternatively, pull the recovery before calculating the reserve and recovery price and account for `received` rather than `_recoveredAmount`. [1](#0-0) 

The same received-amount convention used by `_deposit` should also be applied to `depositDuringEpoch`, which currently mints shares and forwards `_amount` without measuring the token delta. [13](#0-12)

```solidity
contract ToggleFeeToken is ERC20 {
    uint256 public feeBps;

    constructor() ERC20("FeeToken", "FEE") {}

    function setFeeBps(uint256 bps) external {
        feeBps = bps;
    }

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }

    function _update(address from, address to, uint256 amount) internal override {
        if (from == address(0) || to == address(0) || feeBps == 0) {
            super._update(from, to, amount);
            return;
        }

        uint256 fee = amount * feeBps / 10_000;
        super._update(from, address(0), amount);
        super._update(address(0), to, amount - fee);
    }
}

function testFeeOnTransferRecoveryUnderfundsReserve() public {
    uint256 attackerClaimBasis = 990e6;
    uint256 victimClaimBasis = 10e6;
    uint256 declaredRecovery = 1000e6;
    uint256 actualRecovery = 990e6;

    // Fund the vault while the fee is disabled.
    feeToken.setFeeBps(0);
    _depositAA(attacker, attackerClaimBasis);
    _depositAA(victim, victimClaimBasis);

    // Both users create pending withdrawal receipts.
    _requestWithdraw(attacker, attackerClaimBasis);
    _requestWithdraw(victim, victimClaimBasis);

    // Advance through an epoch and enter the existing defaulted state.
    _startEpoch();
    _forceBorrowerDefault();

    // The underlying activates a 1% transfer fee before recovery finalization.
    feeToken.setFeeBps(100);

    feeToken.mint(attackerRecoverySource, declaredRecovery);
    vm.prank(attackerRecoverySource);
    feeToken.approve(address(strategy), declaredRecovery);

    vm.prank(manager);
    cdoEpoch.finalizeDefault(declaredRecovery, attackerRecoverySource);

    // Declared reserve is 1000, but actual strategy balance increased by only 990.
    assertEq(strategy.defaultRecoveryReserve(), declaredRecovery);
    assertEq(feeToken.balanceOf(address(strategy)), actualRecovery);

    // Attacker's 990 claim consumes the entire real reserve.
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertEq(feeToken.balanceOf(attacker), actualRecovery);

    // Victim has a valid 10-token recovery claim but no real assets remain.
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

The key assertion is that storage records `1000e6` while the strategy receives only `990e6`, producing a deterministic `10e6` recovery deficit. [1](#0-0)
