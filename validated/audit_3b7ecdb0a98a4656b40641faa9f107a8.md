### Title
Confidential Transfer instruction parser mislabels arbitrary accounts based on unvalidated offset-derived heuristics - (File: `transaction-status/src/parse_token/extension/confidential_transfer.rs`)

### Summary
`parse_confidential_transfer_instruction()` decodes SPL Token-2022 confidential-transfer instructions for RPC/`transaction-status` output (`getTransaction`, `getConfirmedSignaturesForAddress2`, `logsSubscribe`, `blockSubscribe` with `jsonParsed`/decoded transaction detail). For `Withdraw`/`Transfer`/`Mint`/`ConfidentialBurn` variants, it infers whether an optional "proof context state account" vs "instructions sysvar" trailing account is present purely from a numeric offset field embedded in the *instruction data* (`equality_proof_instruction_offset`, `range_proof_instruction_offset`, etc.), without cross-checking that the actual account list matches that inferred layout. This mirrors the pattern in the referenced report: the parser assumes a specific semantic ("claiming happened" / "sysvar is present") based on an easily attacker-controlled field, then unconditionally labels whatever account happens to occupy that slot with that semantic tag.

### Finding Description
In `transaction-status/src/parse_token/extension/confidential_transfer.rs`, e.g. for `Withdraw`: [1](#0-0) 

the code computes `has_sysvar` from `withdrawal_data.equality_proof_instruction_offset`/`range_proof_instruction_offset` — both values that come straight out of attacker-controlled instruction data — and then, without verifying the account actually is a sysvar or a proof-context account, inserts a label (`instructionsSysvar`, `equalityProofContextStateAccount`, `rangeProofContextStateAccount`) pointing at whatever key sits at the computed `offset` in `account_indexes`. The only guard is a bounds check (`offset < account_indexes.len().saturating_sub(1)`), not a semantic validation of what that account actually is. The same pattern recurs in `Transfer`, `TransferWithFee`, `confidential_mint_burn.rs::Mint/Burn`, and `permissioned_burn.rs::ConfidentialBurn`: [2](#0-1) [3](#0-2) 

Because `parse_token()` is reached for any `CompiledInstruction` whose `program_id` matches the (upgradeable, attacker-deployable-lookalike is not needed — any tx addressed at the real spl-token-2022 id) token program and whose data decodes via `decode_instruction_type`/`decode_instruction_data` (a raw Borsh/pod unpack, not a runtime-verified state check): [4](#0-3) 

a transaction does not need to succeed on-chain to be included in a block and later fetched/parsed by RPC — a failed transaction (e.g., one whose accounts don't actually contain valid sysvar/proof context accounts, or where the offsets are inconsistent with the account list length) is still recorded and its message is still handed to this parser during `getTransaction`, `getSignaturesForAddress`-derived detail fetches, or subscription notifications. The parser will happily attach the `instructionsSysvar`/`...ContextStateAccount` labels to arbitrary accounts based solely on the attacker-chosen offset fields, regardless of whether that account is genuinely a sysvar or proof context account.

### Impact Explanation
This is a decoder-misreporting bug reachable by any unprivileged user via standard JSON-RPC/transaction-status calls that request `jsonParsed` transaction detail. It results in RPC clients/monitoring tools/exchanges being served JSON that mislabels arbitrary pubkeys as "instructionsSysvar" or "proofContextStateAccount", which can mislead downstream consumers about which accounts play a security-relevant role in a confidential-transfer operation — directly analogous to the referenced report's core issue of the controller adding false semantic meaning (`tokensIn`) to accounts based on an unverified assumption tied to how the call was shaped, rather than what actually happened.

### Likelihood Explanation
High reachability: any user can submit a transaction invoking the SPL Token-2022 confidential-transfer program with a crafted account list/offset combination (it does not need to succeed on-chain to be recorded and later queried), and any RPC consumer requesting `jsonParsed` encoding for that transaction/signature/subscription will receive the mislabeled output. No special privileges are required on either the submitting or querying side.

### Recommendation
Do not infer account roles purely from a decoded numeric/boolean field embedded in the instruction data. Where possible, validate the exact expected account count for the code path being taken (as opposed to only the minimum via `check_num_token_accounts`) before assigning semantic labels, and treat mismatches as `InstructionNotParsable` rather than emitting a best-effort but unverified label.

### Proof of Concept
1. Craft (do not need to broadcast successfully; a transaction that fails at instruction execution is still persisted with its original message) a transaction whose single instruction targets the SPL Token-2022 program id with data matching `ConfidentialTransferInstruction::Withdraw` and `WithdrawInstructionData { equality_proof_instruction_offset: 0, range_proof_instruction_offset: 0, .. }`.
2. Populate the account list with 5 arbitrary pubkeys instead of the real proof-context-state accounts the live program would require (only `check_num_token_accounts(account_indexes, 4)` is enforced, i.e. a minimum, not exact match/semantic check) — see: [5](#0-4) 
3. Submit the transaction (it will fail on-chain execution because the "proof context state" accounts are not real, but the transaction and its message are still recorded).
4. Call `getTransaction` with `"encoding": "jsonParsed"` for that signature; observe the parser labels the attacker-chosen accounts as `"equalityProofContextStateAccount"`/`"rangeProofContextStateAccount"` purely because the offset fields were `0`, without any verification that those accounts are legitimate proof-context accounts.
