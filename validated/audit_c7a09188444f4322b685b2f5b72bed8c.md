### Title
Global, unscoped `requestID` keyspace in HTTP Trigger Handler allows any unprivileged workflow caller to block another user's trigger request - (File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go)

### Summary
`HandleUserTriggerRequest` validates and authorizes a caller's workflow HTTP trigger request, then registers it in a shared, gateway-wide `callbacks map[string]savedCallback` keyed *only* by the caller-supplied `req.ID` (`setupCallback`, lines 398-434). The uniqueness check (`in-flight request ID`) applies across **all workflows and all users** sharing this gateway node, not per-workflow or per-authorized-key.

### Finding Description
This is the same bug class as the Stakehouse "Freezing of funds" report: a piece of state that gates a legitimate action (there, `lastInteractedTimestamp`; here, request-ID uniqueness) can be mutated/occupied by an unrelated, unprivileged actor before the check is performed, causing the legitimate actor's operation to fail.

In `HandleUserTriggerRequest`, `req.ID` is fully attacker-controlled input from any workflow-invoking client, validated only for being non-empty and not containing `/` (`validateRequestID`, lines 183-195). Authentication/authorization (`authorizeRequest`) and rate limiting (`checkRateLimit`) are scoped to the *workflow*, but the callback bookkeeping keyed by `req.ID` in `setupCallback` has no such scoping — it is a single flat map shared by the entire gateway handler instance across all workflows/users. If two different, unrelated callers (potentially targeting different workflows entirely) submit a `workflows.execute` request with the same `id` value, the second one to arrive is rejected with `jsonrpc.ErrConflict` ("requestID ... has already been used"), even though the two requests are unrelated and the first caller isn't the intended victim's request at all (`setupCallback`, lines 402-405; confirmed by the existing "duplicate request ID" test).

Because request IDs are typically short, sequential, timestamp-based, or otherwise predictable strings chosen by client SDKs/workflows, an attacker who can invoke *any* workflow trigger request (their own, unrelated workflow) can pre-register a colliding `req.ID` to deny service to a specific victim request they anticipate or observe (e.g., via monitoring retried/predictable IDs, or racing to squat common IDs like `"1"`, `"request-1"`, incrementing counters, etc.), analogous to the giant-pool attacker sending a 0-value transfer to reset another user's `lastInteractedTimestamp` and block their legitimate withdrawal.

### Impact Explanation
This is a griefing/denial-of-service vector against the HTTP trigger execution path: a low-cost, unprivileged action by one caller (submitting a request with a chosen ID) can prevent an unrelated, legitimate workflow owner's trigger request from being processed, causing their `workflows.execute` call to fail with a conflict error instead of executing. Unlike the original financial "freezing of funds" impact, this does not directly move funds, but it blocks the execution of workflow logic that CRE users depend on being triggered reliably — a service-availability impact scoped to unprivileged, cross-user interference within the gateway's request-handling surface.

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to guess or predict a specific victim's chosen `req.ID` ahead of time, or to systematically squat commonly-used/likely IDs to maximize collisions across many potential future requests. Since `req.ID` format constraints are minimal (any non-empty string without `/`), and no scoping/namespacing by workflow or sender is applied, the barrier to attempting this is low for a client that can already call the gateway's HTTP trigger endpoint for its own (unrelated) workflow.

### Recommendation
Scope the in-flight-request uniqueness check (the `callbacks` map key) to the combination of authenticated workflow ID (or authorized key) and `req.ID`, rather than to the raw `req.ID` alone — mirroring how `authorizeRequest` and `checkRateLimit` are already workflow-scoped. This prevents one workflow/caller's chosen request ID from colliding with another unrelated workflow/caller's request.

### Proof of Concept
Not independently exploitable-verified beyond code inspection; the existing `TestHttpTriggerHandler_HandleUserTriggerRequest` "duplicate request ID" subtest demonstrates the underlying mechanism (second request with a colliding ID is rejected with `jsonrpc.ErrConflict`/"in-flight request"), but that test uses the same workflow/caller for both requests. Extending it to use two different, unrelated `workflowID`s (and different authorized keys) with the same `req.ID` would demonstrate the cross-user collision directly; this was not run against a live instance as part of this analysis. func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
}

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// Build one response aggregator per shard the workflow is assigned to.
	assigned := h.workflowMetadataHandler.WorkflowShards(workflowID)
	if len(assigned) == 0 {
		// this shouldn't happen because we checked it in authorizeRequest()
		h.handleUserError(ctx, requestID, jsonrpc.ErrInternal, fmt.Sprintf("Workflow %s is not assigned to any DONs", workflowID), callback)
		return nil, errors.New("workflow is not assigned to any shards")
	}

	aggregators := make(map[string]*aggregation.IdenticalNodeResponseAggregator, len(assigned))
	for _, shard := range assigned {
		// (N+F)//2 + 1 threshold where N = number of nodes, F = number of faulty nodes
		threshold := (len(shard.members)+shard.f)/2 + 1
		agg, err := aggregation.NewIdenticalNodeResponseAggregator(threshold)
		if err != nil {
			return nil, errors.New("failed to create response aggregator: " + err.Error())
		}
		aggregators[shard.donID] = agg
	}

	doneCh := make(chan struct{})
	h.callbacks[requestID] = savedCallback{
		Callback:            callback,
		requestStartTime:    requestStartTime,
		createdAt:           time.Now(),
		responseAggregators: aggregators,
		doneCh:              doneCh,
	}
	return doneCh, nil
}
