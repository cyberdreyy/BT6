### Title
Group USD rate-limiter check for JupLend partial withdraw values fToken shares as if they were native underlying tokens, allowing withdrawal of more real USD value than the configured cap - (File: programs/marginfi/src/instructions/juplend/withdraw.rs)

### Summary
In `juplend_withdraw`'s non-`withdraw_all` path, `record_withdrawal_outflow` is invoked with `native_amount = amount` (the true underlying units, correctly used for the bank-level rate limiter) but `balance_amount = shares_to_burn` (fToken share units) for the group-level USD check. Since `shares_to_burn = ceil(amount * 1e12 / token_exchange_price)`, whenever `token_exchange_price != 1e12` the group check computes `calc_value(shares_to_burn, price, decimals)` — a quantity that mixes fToken share counts with the underlying-token oracle price and underlying decimals — which diverges from the real USD value of the underlying withdrawn (`calc_value(amount, price, decimals)`).

### Finding Description [1](#0-0) 

For the partial-withdraw branch, `shares_to_burn` is derived from `amount` and `lending.token_exchange_price` via `expected_shares_for_withdraw_from_rate`, then `native_outflow = amount` is passed as `native_amount` (correctly used by the per-bank limiter, `bank.rate_limiter.try_record_outflow(native_amount, ...)`), while `shares_to_burn` is passed as `balance_amount`, which feeds the group-level check: [2](#0-1) 

`calc_value(I80F48::from_num(balance_amount), price, bank.get_balance_decimals(), None)` treats `balance_amount` as if it were denominated in underlying-token native units with `bank.get_balance_decimals()` decimals and multiplies by `price` (the underlying-token oracle price). But `shares_to_burn` is a JupLend fToken share count, not an underlying-token amount — it is scaled by the exchange rate: `shares_to_burn = ceil(amount * 1e12 / token_exchange_price)`. When `token_exchange_price > 1e12` (the normal, expected state as JupLend's exchange rate only grows from accrued yield), `shares_to_burn < amount`, so `calc_value(shares_to_burn, ...) < calc_value(amount, ...)` — i.e., the group check systematically undervalues the real USD outflow relative to `amount`'s true value. Contrast this with the other integrations: `solend/withdraw.rs` and `marginfi_account/withdraw.rs` pass the *same* native-unit value for both `native_amount` and `balance_amount`, and `drift/withdraw.rs` passes `token_amount` (actual native units) as `native_amount` and `expected_scaled_balance_change` (also scaled in a way tied to actual assets, per that integration's own accounting) — but JupLend uniquely mixes fToken share units with an underlying-price/decimals calculation for the group check. [3](#0-2) [4](#0-3) 

Because `shares_to_burn` shrinks relative to `amount` as `token_exchange_price` grows above `1e12`, an attacker can pick larger `amount` values while `calc_value(shares_to_burn, price, decimals)` stays under the group's remaining hourly/daily capacity, so the on-chain `check!` in `record_withdrawal_outflow` (`GroupHourlyRateLimitExceeded`/`GroupDailyRateLimitExceeded`) never trips even though the real underlying/USD value withdrawn (`calc_value(amount, price, decimals)`) is larger and, summed over multiple calls, can exceed the group admin's configured cap. The per-bank limiter (`bank.rate_limiter`) uses the correct `native_amount`, so this bug is specific to the group-level USD cap check. [5](#0-4) 

The group check compares against `effective_remaining_capacity`, which folds in both `prev_window_outflow`/`cur_window_outflow` state; the mismatch persists across repeated calls because each call under-records the true consumed capacity (using the shrunk `shares_to_burn`-based value) rather than the real `amount`-based value, letting the attacker accumulate outflow beyond what the cap was intended to permit.

### Impact Explanation
This is a durable rate-limit bypass with direct financial impact: the group admin configures the hourly/daily USD outflow cap specifically to bound aggregate outflow risk (e.g. to react to compromised risk parameters or bank misconfiguration) via `configure_group_rate_limits`, but an unprivileged JupLend withdrawer can drain more real USD-equivalent value per window than that configured cap by repeatedly calling `juplend_withdraw(amount, false)`. This falls within scope as a rate-limit bypass exploitable purely by an unprivileged withdrawer over multiple calls, not a pure oracle/liquidity/DoS issue excluded by SECURITY.md.

### Likelihood Explanation
Preconditions are realistic and require no privileged access: the group rate limiter must be enabled by the admin (a normal, expected configuration, not a misconfiguration), and JupLend's `token_exchange_price` must differ from `1e12`, which is the expected long-term steady state since the exchange rate accrues upward from lending yield over time. Any unprivileged holder of a JupLend position can trigger this repeatedly with ordinary `amount` selections; no special account permissions, oracle manipulation, or race conditions are needed.

### Recommendation
For the JupLend partial-withdraw path, pass a value denominated in real underlying-token units to the group-level check instead of `shares_to_burn`. E.g., call `record_withdrawal_outflow` with `balance_amount = amount` (matching `native_amount`) so the group's USD check is computed on the same real underlying quantity as the bank-level limiter, consistent with how `solend/withdraw.rs` and `marginfi_account/withdraw.rs` do it. If `balance_amount` is intended to carry share-unit semantics for some other purpose, the group-level `calc_value` call inside `record_withdrawal_outflow` should be parameterized so it always operates on native underlying-token amounts, not raw share counts, whenever the caller's balance representation is not 1:1 with the underlying asset.

### Proof of Concept
Rust unit/fuzz test plan:
1. Set up a `MarginfiGroup` with `rate_limiter` configured via `configure_group_rate_limits` with an hourly cap `C` (USD, in native-underlying-equivalent terms) and a `Bank` tagged `ASSET_TAG_JUPLEND` with `bank.rate_limiter` disabled (or set high) so only the group check is exercised.
2. Set `lending.token_exchange_price = 2_000_000_000_000` (2x `1e12`), and set the oracle `price` for the bank's mint to a known fixed value.
3. Compute `amount_A` such that `shares_to_burn_A = expected_shares_for_withdraw_from_rate(amount_A, token_exchange_price)` yields `calc_value(shares_to_burn_A, price, decimals) == C - 1` (just under cap), while `calc_value(amount_A, price, decimals)` (real USD value) is roughly `2x` that (since `shares_to_burn_A ≈ amount_A / 2`).
4. Call `juplend_withdraw(amount_A, false)` once — assert it succeeds even though the real underlying USD value withdrawn exceeds `C`.
5. Repeat multiple such calls in a loop, each keeping `calc_value(shares_to_burn, price, decimals)` under the remaining group capacity per `effective_remaining_capacity`, while summing `calc_value(amount, price, decimals)` across calls.
6. Assert: sum of real underlying USD outflow (`Σ calc_value(amount_i, price, decimals)`) exceeds the group's configured hourly cap `C`, even though every individual call passed the on-chain `GroupHourlyRateLimitExceeded` check — demonstrating the invariant "aggregate USD outflow permitted by the group rate limiter must not exceed the configured cap" is violated.

            fn try_record_outflow(
                &mut self,
                amount: u64,
                current_timestamp: i64,
            ) -> MarginfiResult<()> {
                // Advance windows before computing remaining capacity to avoid boundary gaps.
                self.hourly.maybe_advance_window(current_timestamp);
                self.daily.maybe_advance_window(current_timestamp);

                // An amount that does not fit in i64 cannot be represented and
                // is treated as exceeding every window.
                let amount_i64 = amount_as_i64(amount);
                let exceeds = |remaining: i64| match amount_i64 {
                    Some(a) => a > remaining,
                    None => true,
                };

                if self.hourly.is_enabled() {
                    let remaining = self.hourly.remaining_capacity(current_timestamp);
                    if exceeds(remaining) {
                        msg!(
                            concat!(
                                $prefix,
                                " hourly rate limit exceeded: amount={}, remaining={}"
                            ),
                            amount,
                            remaining
                        );
                        return err!(MarginfiError::$hourly_err);
                    }
                }

                if self.daily.is_enabled() {
                    let remaining = self.daily.remaining_capacity(current_timestamp);
                    if exceeds(remaining) {
                        msg!(
                            concat!(
                                $prefix,
                                " daily rate limit exceeded: amount={}, remaining={}"
                            ),
                            amount,
                            remaining
                        );
                        return err!(MarginfiError::$daily_err);
                    }
                }

                // Both checks passed, record the outflow.
                if self.hourly.is_enabled() {
                    self.hourly.try_record_outflow(amount, current_timestamp)?;
                }
                if self.daily.is_enabled() {
                    self.daily.try_record_outflow(amount, current_timestamp)?;
                }

                Ok(())
            }
