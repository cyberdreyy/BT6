### Title
Claimed instant-withdraw receipts are never released from per-epoch accounting, inflating default recovery basis and trapping recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The kernel bug class is an unreleased fragment: `sock_sendmsg()` frees the response pages but never releases the record-marker fragment, which leaks outside the tracked set. The analog in `IdleCreditVault` is `claimInstantWithdrawRequest`: it clears the aggregate receipt counters (`instantWithdrawsRequests[_user]`, `pendingInstantWithdraws` via `collectInstantWithdrawFunds`) but never releases the per-epoch "record marker" entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. These stale fragments are later read by `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` as if the receipts were still outstanding, corrupting default recovery accounting. [1](#0-0) 

### Finding Description

`requestInstantWithdraw` records three ledgers: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the epoch total `instantWithdrawClaimsByEpoch[currentEpoch]` [2](#0-1) . The normal claim path `_claimFunded`/`claimInstantWithdrawRequest` burns the receipt tokens, zeroes `instantWithdrawsRequests[_user]`, and pays the user — but it never decrements the two per-epoch entries [3](#0-2) . Only `_claimDefaultedInstantWithdrawRequest` touches them, assuming they still represent outstanding basis [4](#0-3) .

Consequences when the same epoch later defaults:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still includes already-paid receipts — whenever `pendingInstantWithdraws != 0` (partial prefunding leaves it nonzero) [5](#0-4) .
2. `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` using that inflated basis, crediting `defaultRecoveryReserve` with underlying that was already paid out and is not held by the strategy [6](#0-5) .
3. `finalizeDefaultRecovery` prices recovery against the inflated `totalBasis` and stores an inflated `reserveAmount`, so `defaultRecoveryPrice` is diluted and `defaultRecoveryReserve` exceeds the actual token balance [7](#0-6) .
4. When the affected user later calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `claimBasis` including the already-claimed amount and executes `instantWithdrawsRequests[_user] -= claimBasis` plus `_burn(_user, claimBasis)`, both of which underflow because the aggregate was already zeroed — the call reverts permanently [8](#0-7) .

### Impact Explanation

Any unprivileged lender who requests an instant withdrawal (a tranche-token holder acting when APR drops) and claims it during an epoch that is subsequently defaulted poisons the recovery accounting for that epoch. The phantom basis (a) dilutes `defaultRecoveryPrice` for all defaulted-epoch claimants, and (b) inflates `defaultRecoveryReserve` beyond real holdings so that `safeTransfer` in `_transferDefaultRecovery` reverts for late claimants — permanently freezing part of the recovered underlying inside the strategy. Direct theft is bounded by the phantom amount, but permanent freezing of unclaimed recovery equal to the leaked per-epoch basis is achievable, and the attacker can also cause their own legitimate remaining receipts to be frozen via the underflow.

### Likelihood Explanation

Requires: an epoch where instant withdrawals are enabled and the APR drop triggers instant mode, a user who requests and claims during that epoch, `pendingInstantWithdraws` remaining nonzero at finalization (partial prefunding — a normal condition when CDO cash is short), and the borrower defaulting in that same epoch. None of these require privileged misbehavior; borrower default is an organic protocol event the code explicitly supports. The sequence is fully reproducible in a Foundry test: request instant withdraw in buffer, `startEpoch`, `claimInstantWithdrawRequest`, default + `finalizeDefault` while `pendingInstantWithdraws != 0`.

### Recommendation

In `claimInstantWithdrawRequest` (and the funded path it wraps), clear the per-epoch fragments alongside the aggregate: subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][<requestEpoch>]` and `instantWithdrawClaimsByEpoch[<requestEpoch>]`, tracking the request epoch the way `lastWithdrawRequest` does for normal requests (e.g., store `lastInstantWithdrawRequest[_user]`), or iterate/zero all nonzero per-epoch entries being paid.

### Proof of Concept

Foundry fork/test outline (mirroring `testProcessWithdrawalClaimsInstantEpoch` and the default-finalization tests in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: standard epoch variant, instant withdrawals enabled
cdoEpoch.setInstantWithdrawParams(instantDelay, 1e18, false); // prank manager
idleCDO.depositAA(amount); // KYC'd user
// buffer: APR drops -> requestWithdraw routes to requestInstantWithdraw
cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche));
// startEpoch: CDO cash covers only part of instant queue -> pendingInstantWithdraws > 0
cdoEpoch.startEpoch(); // prank manager
skip(instantDelay + 1);
cdoEpoch.claimInstantWithdrawRequest(); // user paid; per-epoch entries NOT cleared
assertGt(strategy.instantWithdrawsRequestsByEpoch(user, epoch), 0); // leaked fragment
assertGt(strategy.instantWithdrawClaimsByEpoch(epoch), 0);
// borrower defaults on this epoch; owner/manager finalize with partial recovery
cdoEpoch.stopEpochWithDuration(...); cdoEpoch.finalizeDefault(recovered, source);
// basis inflated by paid receipt -> defaultRecoveryPrice diluted, reserve > balance
// subsequent claims revert on `instantWithdrawsRequests[user] -= claimBasis` underflow
// or on safeTransfer when reserve exceeds actual balance -> recovery permanently frozen
```
