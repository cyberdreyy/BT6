## Analysis

The claim is confirmed as a real, exploitable vulnerability.

`BaseEscrowFactory.createDstEscrow()` accepts an arbitrary caller-supplied `dstImmutables` struct, including `dstImmutables.parameters`, with **no length or content validation whatsoever** before deploying and funding the clone [1](#0-0) . Any unprivileged taker/resolver can pass `parameters: ""` (empty bytes) and fund the clone normally, since funding checks only verify `msg.value` and perform the ERC20 transfer, never inspecting `parameters` [2](#0-1) .

`EscrowDst._withdraw()` unconditionally calls `immutables.integratorFeeAmountCd()` and `immutables.protocolFeeAmountCd()` [3](#0-2) , and `ImmutablesLib` reverts with `IndexOutOfRange` whenever `parameters.length < 0x40` [4](#0-3) . Because `withdraw`/`publicWithdraw` require `onlyValidImmutables(immutables.hash())`, which recomputes the CREATE2 address from a hash that includes the exact `parameters` bytes [5](#0-4) [6](#0-5) , any caller must resubmit the exact same empty `parameters` to pass validation — but doing so guarantees the fee-decoding revert. This makes `withdraw()` and `publicWithdraw()` permanently unusable for that specific clone once deployed with a too-short `parameters` blob.

`cancel()` does **not** touch `ImmutablesLib` fee fields [7](#0-6) , so after `DstCancellation` the taker who created the broken escrow can reclaim their own deposited destination tokens/native funds back to themselves — the maker never receives the destination-side payout. Since in the Fusion+ cross-chain flow the resolver/taker typically already knows the secret off-chain (it is disclosed to resolvers before they fund the destination escrow), the resolver does not need the on-chain reveal from `EscrowDst.withdraw()` to later claim the maker's source-chain funds via `EscrowSrc.withdraw()` [8](#0-7) . This turns the bug from a pure "temporary freeze" into a potential rug-pull vector: the resolver fills the order (locking maker funds on the source chain), deploys a destination clone doomed to fail withdrawal, later cancels it back to themselves, and separately withdraws the maker's original funds on the source chain using the secret — the maker's expected destination payout is permanently lost while the resolver recovers their own destination deposit.

At minimum, independent of the rug-pull escalation, this is a direct freeze: **any unprivileged actor who funds a destination escrow with a `parameters` blob shorter than 0x40 bytes permanently bricks `withdraw()`/`publicWithdraw()` for that escrow**, since the immutables-hash binding makes it impossible to submit corrected parameters later.

### Title
Unvalidated `parameters` length in `createDstEscrow()` permanently bricks `EscrowDst.withdraw()`/`publicWithdraw()` - (File: contracts/BaseEscrowFactory.sol, contracts/libraries/ImmutablesLib.sol)

### Summary
`BaseEscrowFactory.createDstEscrow()` deploys and funds a destination escrow clone using a caller-supplied `Immutables.parameters` blob without validating its length or fee-field content. `EscrowDst.withdraw()`/`publicWithdraw()` unconditionally decode integrator/protocol fee fields from that blob via `ImmutablesLib`, which reverts with `IndexOutOfRange` if `parameters.length < 0x40`. Because immutables (including `parameters`) are bound into the CREATE2 salt/hash used for `onlyValidImmutables`, no alternate/corrected parameters can ever be supplied later, making the revert permanent for that clone.

### Finding Description
`createDstEscrow` performs only balance checks (`msg.value` vs `safetyDeposit`/`amount`) and never validates `dstImmutables.parameters` [1](#0-0) . `EscrowDst._withdraw` reads `integratorFeeAmountCd()`/`protocolFeeAmountCd()` from `immutables.parameters`, both of which enforce minimum length via `IndexOutOfRange` in `ImmutablesLib` [4](#0-3) [9](#0-8) . The `onlyValidImmutables` modifier recomputes the deterministic clone address from the full immutables hash (which incorporates the exact bytes of `parameters`) and reverts `InvalidImmutables` if it doesn't match `address(this)` [10](#0-9) . Consequently, the only `parameters` value that will ever pass `onlyValidImmutables` for a given clone is the one originally supplied at creation — if that value is too short, decoding will always revert.

### Impact Explanation
This qualifies for High: temporary freezing of funds during the live swap lifecycle, since `cancel()` (which doesn't touch fee decoding) still allows the taker to reclaim the destination deposit after `DstCancellation`, but the maker's payout via `withdraw`/`publicWithdraw` is permanently blocked for that clone. Depending on off-chain secret-sharing assumptions in the Fusion+ resolver flow, this could enable a resolver to extract the maker's source-chain funds via `EscrowSrc.withdraw()` while never delivering the destination payout, escalating the impact toward theft — though that escalation depends on off-chain secret-disclosure timing that is outside the scope of the on-chain contracts alone.

### Likelihood Explanation
High likelihood: `createDstEscrow` is a fully public, unprivileged entrypoint, and constructing an empty or short `parameters` blob requires no special access, only a single ABI-encoding choice by the caller.

### Recommendation
Validate `dstImmutables.parameters.length` (e.g., require `>= 0x80`, matching the four ABI-encoded fee fields) inside `createDstEscrow` before deploying/funding the clone, rejecting malformed blobs at creation time rather than allowing them to brick withdrawal later.

### Proof of Concept
1. Attacker (any address) calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.parameters = ""` and correct `msg.value`/token approvals [1](#0-0) .
2. The clone deploys successfully and is funded; `SrcEscrowCreated`/`DstEscrowCreated` flow completes normally.
3. Once the withdrawal window opens, `taker` calls `EscrowDst.withdraw(secret, immutables)` with the same `immutables` (required for `onlyValidImmutables` to pass).
4. `_withdraw` calls `immutables.integratorFeeAmountCd()`, which checks `parameters.length < 0x40` and reverts `IndexOutOfRange` [11](#0-10) .
5. Every subsequent call to `withdraw`/`publicWithdraw` with the only valid immutables value reverts identically — the escrow can never pay the maker, only be cancelled back to the taker after the cancellation timelock.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function hash(IBaseEscrow.Immutables calldata immutables) internal pure returns(bytes32 ret) {
        // Compute the EIP-712 hash for the immutables struct
        bytes calldata parameters = immutables.parameters;
        assembly ("memory-safe") {
            let ptr := mload(0x40)

            // Copy immutables.parameters to memory and compute its hash
            calldatacopy(ptr, parameters.offset, parameters.length)
            let parametersHash := keccak256(ptr, parameters.length)

            mstore(add(ptr, IMMUTABLES_LAST_WORD), parametersHash)
            ret := keccak256(ptr, IMMUTABLES_SIZE)
        }
