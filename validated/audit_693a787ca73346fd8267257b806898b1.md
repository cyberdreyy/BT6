### Title
Post-default withdraw requests pay out at par from `defaultRecoveryReserve`, draining the shared recovery fund and permanently freezing earlier defaulted claimants' payouts - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Kibana report maps to the "specially crafted request that crashes a later, legitimate request" bug class: in `IdleCreditVault`, a crafted post-default `requestWithdraw` is paid 1:1 out of `defaultRecoveryReserve`, a pool that was sized to pay all defaulted claims only at `recoveryPrice ≤ 1`. Each post-default request therefore over-draws the reserve, and once it is depleted, every earlier defaulted/instant receipt's claim reverts on the `defaultRecoveryReserve -= _amount` underflow — a direct theft plus permanent freeze of unclaimed recovery funds.

### Finding Description
When `defaultRecoveryFinalized` is true, `requestWithdraw` takes a dedicated branch: it burns `_amount` of the CDO's strategy tokens, mints an equal receipt to the user, and records `postDefaultRequests[_user] = _amount` without touching `pendingWithdraws` [1](#0-0) . `claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest`, which burns the receipt and calls `_transferDefaultRecovery(_user, amount)` — paying the full amount from the reserve [2](#0-1) [3](#0-2) .

The reserve was sized at finalization as `reserveAmount = _recoveredAmount + prefundedReserve + prior reserve` with `recoveryPrice = reserveAmount / totalBasis`, where `totalBasis = activeBasis + pendingBasis` [4](#0-3) . Legitimate draws against it are `pendingBasis * recoveryPrice` (defaulted receipts via `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` [5](#0-4) [6](#0-5) ) plus the active-side remainder `activeBasis * recoveryPrice` (the CDO's `activeBalance` was burned/minted down to `activeFinalNAV = activeBasis * recoveryPrice` [7](#0-6) ). The reserve therefore has exactly zero slack.

A post-default request of size `x` burns `x` active strategy tokens (an entitlement worth `x * recoveryPrice` of reserve) but creates a claim paid at par `x`. Each request thus over-draws `x * (1 - recoveryPrice)` from funds earmarked for other claimants. Any unprivileged tranche holder can repeat this: deposit/withdraw is still permitted post-default precisely because this branch exists to "preserve request/claim UX after default". Once the reserve is exhausted, `_transferDefaultRecovery` underflows on `defaultRecoveryReserve -= _amount`, permanently reverting all remaining defaulted-epoch and post-default claims [3](#0-2) .

### Impact Explanation
Direct theft and permanent freezing of unclaimed recovery funds. With `recoveryPrice = p < 1`, an attacker requesting `x` post-default extracts `x` from a pool containing only `p`-weighted coverage, stealing `x(1-p)` belonging to defaulted-epoch withdraw requesters, unfunded instant requesters, and active LPs. Claimants who call later lose their entire `claimBasis * recoveryPrice` payout — unrecoverable, since no mechanism replenishes `defaultRecoveryReserve`. Quantified: for a vault defaulted at 50% recovery, an attacker cycling `A` of post-default requests drains up to `A/2` of other claimants' recovery per unit of reserve consumed, and can iterate until reserve is zero.

### Likelihood Explanation
High once a default is finalized. Preconditions: `defaultRecoveryFinalized == true`, `recoveryPrice < 1` (any loss), and the attacker holding or acquiring tranche tokens post-default (buying wiped-price tranches makes the attack cheaper). No privileged role, no timing race, and no guard stops it: `_hasWithdrawRequest` only blocks users with pending receipts, `NotAllowed` checks don't bound cumulative post-default draws, and `_transferFundedClaim`'s reserve guard protects the reserve only from funded claims — not from `_transferDefaultRecovery` itself [8](#0-7) .

### Recommendation
Pay post-default requests at `defaultRecoveryPrice`, not at par: `amount = postDefaultRequests[_user] * defaultRecoveryPrice / RECOVERY_FULL`, or track a separate post-default reserve bucket funded by an equivalent burn of the active-side entitlement so the shared recovery pool is untouched. Alternatively, account for each post-default request's reserve consumption at request time (`defaultRecoveryReserve -= _amount * price / RECOVERY_FULL`-equivalent accounting) so claims can never exceed the sized coverage.

### Proof of Concept
Foundry fork PoC (schematic — harness mirrors `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Setup: USDC vault, borrower, manager, CDO epoch variant; alice = defaulted requester, attacker = LP.
// 1. alice deposits AA 1000e6; attacker deposits BB 1000e6; manager startEpoch; borrower borrows.
// 2. alice.requestWithdraw(500e6) -> pending receipt in epoch N.
// 3. Borrower defaults: cdo._handleBorrowerDefault(); then finalizeDefaultRecovery
//    pulling recovered = 50% of total basis -> recoveryPrice = 0.5e18, reserve sized exactly.
// 4. Attacker (holds tranche tokens with remaining NAV):
//    for (uint i; i < N; ++i) {
//        cdo.requestWithdraw(x, BBtranche);        // postDefaultRequests[attacker] = x
//        cdo.claimWithdrawRequest(attacker);       // pays x 1:1 from defaultRecoveryReserve
//    }
// 5. alice.claimWithdrawRequest() -> reverts: defaultRecoveryReserve underflow in
//    _transferDefaultRecovery (arithmetic underflow, Solidity 0.8).
// Assert: attacker profit == x*(1 - recoveryPrice) per iteration; alice's
// 500e6 * recoveryPrice payout permanently unclaimable.
```

Uncertainty note: the PoC assumes the epoch CDO still forwards `requestWithdraw`/`claimWithdrawRequest` to the strategy after default finalization; the strategy's dedicated `defaultRecoveryFinalized` branch strongly indicates this, but I could not read `IdleCDOEpochVariant.sol`'s gating in this session to fully confirm the entry-point path.

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
