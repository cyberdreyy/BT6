### Title
Infinite Tight-Loop With No Backoff When `query_range=1` and RPC Returns -32005 — (`crates/sui-bridge/src/eth_syncer.rs`)

### Summary

`run_event_listening_task` contains a dead-end branch: when `query_range` has already been halved to `1` and the RPC still returns a -32005 / "query returned more than" error, the code logs the message *"Retrying with standard backoff"* but implements **no backoff whatsoever**. It sets `more_blocks = true` and `continue`s, causing the loop to spin indefinitely on the same `start_block` with no sleep, no exponential delay, and no `start_block` advance.

### Finding Description

The relevant path in `run_event_listening_task`: [1](#0-0) 

`query_range` starts at `ETH_LOG_QUERY_MAX_BLOCK_RANGE` (1000). [2](#0-1) 

When a -32005 error arrives:

1. `new_range = (query_range / 2).max(1)` — once `query_range` is already `1`, this evaluates to `(0).max(1) = 1`, so `new_range == query_range`.
2. The `if new_range == query_range` branch fires, logs an error, but **does not update `query_range`** (the `query_range = new_range` assignment is in the `else` branch only).
3. Execution falls through unconditionally to `more_blocks = true; continue;`.
4. Because `more_blocks` is `true`, the top-of-loop guard `if !more_blocks { last_finalized_block_receiver.changed().await … }` is skipped — **no async yield that would allow other tasks to make progress or introduce any delay**.
5. The loop immediately re-issues `get_events_in_range(contract_address, start_block, start_block)` — the identical single-block query — which returns -32005 again.
6. Repeat forever. `start_block` never advances.

The inline comment *"Retrying with standard backoff"* is factually wrong; there is no backoff of any kind in this branch. [3](#0-2) 

### Impact Explanation

Once the syncer is stuck on block N:

- Every bridge deposit emitted in blocks N, N+1, N+2, … is never forwarded to the downstream channel.
- The `events_sender` channel never receives those events, so the bridge action executor never sees them.
- All user funds deposited from Ethereum after block N are permanently unprocessable until an operator manually restarts the syncer against a different RPC endpoint — a privileged, out-of-band intervention that is not guaranteed or timely.

This satisfies the **permanent fund lock** impact class in the active bounty scope.

### Likelihood Explanation

The trigger condition is: a single Ethereum block contains more bridge-contract log entries than the RPC node's per-query result cap. Many public and private RPC providers cap `eth_getLogs` results at 2,000–10,000 entries. A determined attacker can submit a burst of bridge deposit transactions (each emitting at least one log) timed to land in the same block. The cost is proportional to the RPC cap and the per-transaction gas cost; it is non-trivial but well within reach of a motivated attacker, and the damage is asymmetric (one-time cost, indefinite bridge halt).

No malicious validator, bridge authority, or admin cooperation is required. The attacker is an ordinary Ethereum account interacting with the public bridge contract.

### Recommendation

Replace the no-op error branch with a real bounded-exponential backoff. For example:

```rust
if new_range == query_range {
    // Already at minimum window; sleep before retrying to avoid spinning.
    let backoff = Duration::from_secs(backoff_secs);
    backoff_secs = (backoff_secs * 2).min(MAX_BACKOFF_SECS);
    tokio::time::sleep(backoff).await;
} else {
    query_range = new_range;
    backoff_secs = INITIAL_BACKOFF_SECS; // reset on progress
}
```

Alternatively, after a configurable number of consecutive -32005 failures at `query_range=1`, fall through to the `retry_with_max_elapsed_time!` path (lines 199–205) which already implements proper bounded retry with backoff.
