### Title
Tranche oracle reports 1e18-scaled prices while advertising loan-token decimals - ([File: contracts/strategies/morpho/TranchesChainlinkOracle.sol])

### Summary

`TranchesChainlinkOracle.latestRoundData()` returns `cdo.virtualPrice(collateralToken)` unchanged, while `decimals()` reports the loan token's decimals. `IdleCDO.virtualPrice()` is scaled by `ONE_TRANCHE_TOKEN = 1e18`, so a USDC-denominated market interprets a `1e18` price as `1e12` USDC instead of `1e6` USDC. [1](#0-0) [2](#0-1) [3](#0-2) 

An unprivileged tranche holder can use the overvalued collateral to borrow and drain loan assets from any lending market that consumes this oracle, leaving the position undercollateralized. The overvaluation factor is `10 ** (18 - loanTokenDecimals)` when the loan token has fewer than 18 decimals. [4](#0-3) 

### Finding Description

The oracle constructor derives `loanTokenDecimals` from `cdo.token()`, and `decimals()` exposes that value to consumers. [5](#0-4)  However, the answer returned by `latestRoundData()` is the raw tranche virtual price, which is denominated per `1e18` tranche tokens rather than per `10 ** loanTokenDecimals`. [6](#0-5) [7](#0-6) 

For example, with a six-decimal loan token and a tranche whose true value is one loan token, `latestRoundData()` returns approximately `1e18`. A consumer that scales by the advertised `decimals() == 6` values the tranche at approximately `1e12` loan tokens, an overvaluation of `1e12x`. [1](#0-0) 

There is no normalization or guard requiring the loan token to have 18 decimals, so common deployments using USDC or USDT expose an incorrectly scaled collateral price. [8](#0-7) 

### Impact Explanation

The broken invariant is fair collateral valuation: one tranche token should be valued at its actual underlying redemption value, not at `10 ** (18 - loanTokenDecimals)` times that value. [3](#0-2) [1](#0-0) 

An attacker can acquire a small amount of the tranche token, supply it as collateral to a market using this oracle, and borrow all available loan liquidity because the market calculates collateral value using `answer / 10 ** decimals()`. [1](#0-0) 

For a USDC market, depositing one tranche token worth about one USDC can quote roughly `1e12` USDC of collateral value; the resulting loss can be the full loan liquidity supplied to the market, minus the actual collateral value. [1](#0-0) 

### Likelihood Explanation

No privileged attacker is required: the attacker only needs to hold or acquire the tranche token and borrow against it in a market configured to use this oracle. [8](#0-7) 

The issue is conditional on a non-18-decimal loan token and on an external lending market trusting the oracle, so it does not affect every deployment. When those conditions hold, exploitation is a single deposit-and-borrow sequence and does not require price manipulation, privileged calls, or changes to Idle vault state. [8](#0-7) 

### Recommendation

Either return `18` from `decimals()` so consumers preserve the existing `1e18` scaling, or normalize `latestRoundData()` to the loan token's decimals.

If the oracle interface must report loan-token decimals, rescale the answer explicitly:

```solidity
uint256 answer = cdo.virtualPrice(collateralToken);
if (loanTokenDecimals <= 18) {
  answer /= 10 ** (18 - loanTokenDecimals);
} else {
  answer *= 10 ** (loanTokenDecimals - 18);
}
```

Add tests for both six-decimal and 18-decimal loan tokens asserting that `answer / 10 ** decimals()` equals the tranche's actual underlying value. [8](#0-7) [3](#0-2) 

### Proof of Concept

A reproducible Foundry fork test can compare the value computed through the oracle's advertised decimals with the actual `1e18`-scaled tranche value:

```solidity
// test/foundry/TranchesChainlinkOracle.t.sol
function testOracleAnswerScaleMismatch() public {
    vm.createSelectFork(vm.envString("ETH_RPC_URL"));

    address tranche = vm.envAddress("TRANCHE_TOKEN");
    TranchesChainlinkOracle oracle = new TranchesChainlinkOracle(tranche);
    IdleCDO cdo = oracle.cdo();

    uint8 oracleDecimals = uint8(oracle.decimals());
    uint8 loanDecimals = IERC20Detailed(cdo.token()).decimals();
    (, int256 answer,,,) = oracle.latestRoundData();

    assertEq(oracleDecimals, loanDecimals);
    assertEq(uint256(answer), cdo.virtualPrice(tranche));
    assertLt(oracleDecimals, 18); // e.g. USDC = 6

    uint256 trancheAmount = 1e18;
    uint256 actualAssets = trancheAmount * uint256(answer) / 1e18;
    uint256 quotedAssets = trancheAmount * uint256(answer) / (10 ** oracleDecimals);

    assertEq(
        quotedAssets,
        actualAssets * 10 ** (18 - oracleDecimals),
        "oracle overvalues tranche collateral"
    );
}
```

With `TRANCHE_TOKEN` set to a deployed tranche whose CDO loan token is USDC, the test demonstrates that the oracle reports the raw `1e18` virtual price while telling consumers to scale it as a six-decimal answer. [1](#0-0) [2](#0-1)

    // decimals of the virtualPrice are equal to decimals of the loanToken
    return uint8(loanTokenDecimals);
  }
