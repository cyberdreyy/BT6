### Title
External Initiator credentials can trigger runs on arbitrary jobs (no EI-to-job binding check) - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) validates only that the caller holds a valid access key/secret for *some* `ExternalInitiator` row, then sets a synthetic `SessionUserKey` with `Role: UserRoleRun` in addition to `SessionExternalInitiatorKey`. `PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go:89-128`) checks only `auth.GetAuthenticatedUser(c)` (`isUser`) to decide whether to call `prc.App.RunJobV2(ctx, jobID, nil)`, and never inspects `auth.GetAuthenticatedExternalInitiator(c)` or validates that the authenticated EI is associated with `jobID`. Consequently a caller authenticated as external initiator A can trigger a run on any integer job ID, including jobs tied to a different external initiator B, a non-webhook job, or a job with no EI binding at all.

### Finding Description
- `AuthenticateExternalInitiator` in `core/web/auth/auth.go:119` looks up the EI row by access key (`store.FindExternalInitiator`), authenticates the secret via `bridges.AuthenticateExternalInitiator` (`core/bridges/external_initiator.go:61`), and on success does:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
```
This stores a synthetic `User` object with `Role: UserRoleRun` into the same context key used for normal user-session authentication (`SessionUserKey`).
- `PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go:109-125`) does:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    jobID64, err := strconv.ParseInt(idStr, 10, 32)
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
```
Because `GetAuthenticatedUser` returns `true` for *any* context that has `SessionUserKey` set — including the synthetic user created for EI auth — `isUser` is `true` for an EI-authenticated request as well, despite the comment stating "EIs not allowed." The handler never calls `auth.GetAuthenticatedExternalInitiator(c)` nor validates that the retrieved `ei` is linked to the job identified by `idStr`. `RunJobV2` is invoked with the raw path-supplied `jobID`, with no EI-to-job binding check anywhere in this code path.
- The only restriction present filters out UUID-formatted IDs (webhook job external UUIDs), which is unrelated to authorization; it does not restrict which numeric job ID an EI-authenticated caller can target.

This confirms the root cause described in the question: `AuthenticateExternalInitiator` only proves possession of a valid EI credential, and `PipelineRunsController.Create` performs no check that the specific `ei` is the one associated with `jobID`.

### Impact Explanation
An attacker who holds valid AccessKey/Secret for one external initiator (a low-privilege, narrowly-scoped credential intended only to trigger its own bound job(s)) can call `POST /v2/jobs/:jobID/runs` with any numeric job ID and force `RunJobV2` to execute that job's pipeline — including jobs belonging to a different external initiator or jobs with no external-initiator association. This is an authorization/binding bypass leading to unauthorized job execution, which can cause unintended on-chain transactions, unauthorized bridge/API calls, or consumption of node resources/funds depending on job task graph. This matches the "unauthorized job run" impact class.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs valid credentials for any single, unprivileged external initiator (e.g., obtained legitimately for one integration) and knowledge/guessing of a target job's integer ID (job IDs are sequential integers, and may be discoverable via other means). No admin/operator access is required. The exploit is a single unauthenticated (from the target job's perspective) HTTP POST with valid EI headers, fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, do not rely solely on `auth.GetAuthenticatedUser`; explicitly branch on `auth.GetAuthenticatedExternalInitiator(c)` when present and verify that the resolved job's webhook/EI spec actually references that specific `ExternalInitiator` (e.g., look up the job's `WebhookSpec.ExternalInitiatorWebhookSpecs` and confirm `ei.ID` is present) before calling `RunJobV2`. Alternatively, avoid setting a real `SessionUserKey` for EI auth (use a distinct context key/type so `GetAuthenticatedUser` cannot conflate EI sessions with real user sessions), and require an explicit EI-to-job binding check in the runs-creation path.

### Proof of Concept
1. Create two `ExternalInitiator` rows, EI-A and EI-B, each with distinct AccessKey/Secret.
2. Create Job-A bound to EI-A (webhook spec referencing EI-A) and Job-B bound to EI-B (or Job-B with no EI binding at all).
3. Authenticate as EI-A by setting `static.ExternalInitiatorAccessKeyHeader`/`static.ExternalInitiatorSecretHeader` to EI-A's credentials.
4. Send `POST /v2/jobs/:Job-B-ID/runs` using EI-A's headers.
5. Assert (current/expected-vulnerable behavior): request returns `200`/pipeline-run resource and `prc.App.RunJobV2` is invoked with Job-B's ID — i.e., the run is *not* rejected, despite EI-A having no association with Job-B.
6. Contrast with expected-secure behavior: response should be `401`/`403` because EI-A is not bound to Job-B.
This can be implemented as a `core/web/pipeline_runs_controller_test.go` handler-level integration test using the existing test harness (`cltest.NewApplication`, EI/job fixtures already used in `external_initiator_test.go` and `pipeline_runs_controller_test.go`).
