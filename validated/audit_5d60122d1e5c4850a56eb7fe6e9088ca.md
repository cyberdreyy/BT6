### Title
Signer re-check of tenure-change blocks omits the own-tenure "second BlockFound" duplicate guard — ([File: stacks-signer/src/v0/signer.rs])

### Summary
The proposal-time check `validate_tenure_change_payload` rejects a tenure-change (`BlockFound`) block with `RejectReason::DuplicateBlockFound` whenever the signer has already signed *any* block in that same tenure, regardless of height. This check is **only invoked once, at proposal arrival** (inside `check_proposal`). The equivalent re-check function used later in the lifecycle — `check_block_against_signer_db_state`, called both when the node's validation result comes back (`handle_block_validate_ok`) and again right before a signature is actually produced (`handle_block_pre_commit`) — for a tenure-change block **only re-verifies the parent tenure** via `check_tenure_change_confirms_parent`, and never re-runs the own-tenure duplicate check. This function is even annotated by the developers themselves with `"WARNING: This is an incomplete check."` [1](#0-0) 

The docs acknowledge the gap and claim it is covered by a different backstop (`get_signed_conflicts`, used in the pre-commit signing path), but that backstop only returns previously-signed blocks at or **above** the new proposal's own height, so it does not cover a duplicate `BlockFound` proposed at a **higher** chain length than the already-signed tenure-start block.

### Finding Description
Analogous to the appchain-registry bug (a privilege/ownership check present in one function but missing in the sibling function that needed the same check), the Stacks signer has two logically-parallel gatekeeping functions for tenure-change blocks:

1. **Proposal-time (`check_proposal` → `validate_tenure_change_payload`)** — full check:
   - Confirms `prev_tenure_consensus_hash` matches the expected parent tenure.
   - **AND** checks `signer_db.get_last_signed_block(&block.header.consensus_hash)` (OWN tenure): if any block has already been signed in this tenure, rejects with `RejectReason::DuplicateBlockFound`, since a tenure must have only one `BlockFound` tenure-change. [2](#0-1) 

2. **Re-check at validate-ok / pre-commit-threshold time (`check_block_against_signer_db_state`)** — partial check:
   - For a tenure-change block it calls only `SortitionData::check_tenure_change_confirms_parent(...)` (the PARENT tenure check).
   - It never re-invokes the own-tenure `DuplicateBlockFound` logic. [1](#0-0) 

The project's own documentation states this explicitly: *"Two things belong to the proposal path only and are not re-run at validate-ok or at signing: `validate_tenure_change_payload` rejects with `DuplicateBlockFound`... Because the duplicate check never runs again, a block that crosses the pre-commit threshold long after it was proposed relies on section 5's own-tenure conflict guard to cover the same ground."* [3](#0-2) 

That claimed backstop is `get_signed_conflicts`, invoked from `handle_block_pre_commit` right before signing:
```
let conflicts = self.signer_db.get_signed_conflicts(block_info.block.header.chain_length, &block_hash)
```
which is documented as returning "every signed block **at or above** the given Stacks height." [4](#0-3) [5](#0-4) 

Because the query is height-bounded from below (only height ≥ the *new* proposal's own height is returned), an already-signed tenure-start block at a **lower** height than the new (second) `BlockFound` proposal in the same tenure is never surfaced as a "conflict" by this query, and the parent-tenure-only re-check in `check_block_against_signer_db_state` cannot see it either — leaving no guard against a second `BlockFound` tenure-change at a higher chain length in an already-signed tenure between validate-ok and the pre-commit/signing step.

### Impact Explanation
If a single miner (one-slot miner within scope of this analysis) can get a first `BlockFound` block for tenure T signed at height H, and then propose a second, distinct `BlockFound` tenure-change block also carrying consensus_hash = T but built to a higher chain length H' > H (with a parent chain that a node considers valid), a signer could pre-commit and ultimately sign it: the tenure-parent check passes (it checks the parent *tenure*, not the current one), and the height-bounded `get_signed_conflicts` guard at signing time does not catch the earlier, lower-height signed block. This is a **Critical**-class outcome per the rules given (a signer signing a conflicting/non-canonical block that duplicates tenure-change state that was supposed to be unique per tenure), because the guard that is supposed to enforce the "one BlockFound per tenure" invariant only runs once, at proposal time, and its designated backstop has a height-direction blind spot.

### Likelihood Explanation
This requires no majority collusion — only the proposing miner (one-slot) and the normal gossip/re-proposal flow that already exists in the codebase (block proposals are re-evaluated across the validate-ok → pre-commit → sign pipeline, and this exact re-evaluation gap is what the docs call out as a known, accepted blind spot rather than something actively tested for the higher-height case). The scenario does depend on the attacker being able to construct a chain-length-H' block whose ancestry a node's block-validation endpoint will accept as internally consistent even though it duplicates a BlockFound in tenure T — this part could not be fully verified against `postblock_proposal.rs` node-side validation logic within the remaining investigation budget, so likelihood carries some uncertainty tied to whether the node itself would independently reject such a malformed chain before the signer's re-check point is ever reached.

### Recommendation
Re-run the own-tenure `DuplicateBlockFound` check (`get_last_signed_block` on the block's own `consensus_hash`) inside `check_block_against_signer_db_state` for tenure-change blocks, symmetric to what `validate_tenure_change_payload` already does at proposal time — rather than relying solely on the height-bounded `get_signed_conflicts` backstop, which only defends against duplicates at or above the new proposal's own height.

### Proof of Concept
Conceptual (not executed, due to no access to a live node to test node-side acceptance of the crafted chain):
1. Miner proposes `BlockFound` tenure-change block B1 for tenure T at chain_length H. Signers validate, pre-commit, and sign B1 (`check_proposal`'s `validate_tenure_change_payload` passes since no prior signed block existed in T).
2. B1 becomes `GloballyAccepted`/`LocallyAccepted` — `get_last_signed_block(T)` now returns B1.
3. Miner constructs a second, distinct `BlockFound` tenure-change block B2, still carrying `consensus_hash = T`, but with a parent chain built to chain_length H' > H.
4. B2 is submitted as a new proposal. At proposal time, `validate_tenure_change_payload` would reject it (`DuplicateBlockFound`) — but B2 is instead injected/re-evaluated directly at the validate-ok or pre-commit re-check stage (e.g., via `should_reevaluate_block`'s re-send/re-run path, or a validation response arriving out of order), which only calls `check_block_against_signer_db_state`.
5. `check_block_against_signer_db_state` for B2 (a tenure-change block) checks only `check_tenure_change_confirms_parent` (parent tenure of T) — passes.
6. At the pre-commit threshold step, `get_signed_conflicts(H', hash_B2)` looks for signed blocks at height ≥ H'; B1 at height H < H' is not returned, so no conflict is flagged.
7. Signer signs B2, producing a second signed `BlockFound` for tenure T — violating the "one tenure-change per tenure" invariant that `validate_tenure_change_payload`'s `DuplicateBlockFound` check exists specifically to enforce. [1](#0-0) [4](#0-3) [6](#0-5)

        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,

        let signer_signature_hash = proposed_block.header.signer_signature_hash();

                proposed_block,

    fn validate_tenure_change_payload(
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        parent_tenure_id: &ConsensusHash,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        config: &ProposalEvalConfig,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the signer's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            config.tenure_last_block_proposal_timeout,
            config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // We already confirmed in check miner activity that the current tenure is valid. So check we are not
        // reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count
        // here: a block we have merely pre-committed to carries no signature from us, so it is safe to
        // accept a competing tenure-start block in its place if it failed to reach consensus.
        let last_in_current_tenure = signer_db
            .get_last_signed_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }
