### Title
Attacker-controlled `MessageId` collision overwrites another user's pending gateway callback - ([File: core/services/gateway/handlers/handler.dummy.go])

### Summary
`dummyHandler.HandleLegacyUserMessage` stores each incoming user callback in `d.savedCallbacks` keyed solely by the attacker-supplied `msg.Body.MessageId`, with no check for an existing entry before overwriting it. This is the exact same unguarded map-write pattern present in the capabilities handler (`h.savedCallbacks[msg.Body.MessageId] = ...` in `core/services/gateway/handlers/capabilities/handler.go`), confirming the bug class recurs across handler implementations that share `HandleLegacyUserMessage`.

### Finding Description
`dummyHandler.HandleLegacyUserMessage` (`core/services/gateway/handlers/handler.dummy.go:62-66`) does:
```go
d.mu.Lock()
d.savedCallbacks[msg.Body.MessageId] = &savedCallback{msg.Body.MessageId, callback}
don := d.don
d.mu.Unlock()
```
`msg.Body.MessageId` originates directly from the JSON-RPC request `ID` field supplied by the caller in `HandleJSONRPCUserMessage` (`core/services/gateway/handlers/handler.dummy.go:52`: `msg.Body.MessageId = jsonRequest.ID`), or is set directly on the `api.Message` when `HandleLegacyUserMessage` is invoked with a pre-built message. There is no uniqueness check against existing keys in `d.savedCallbacks` before the map write, so a second request using the same `MessageId` as a still-pending request silently replaces the first request's stored `Callback`. When a node response later arrives for that `MessageId` (`HandleNodeMessage`, lines 84-108), the response is delivered to whichever `Callback` is currently stored — the attacker's — while the original caller's callback reference is discarded and orphaned (their `cb.Wait()` will never resolve, or in the capabilities handler case, the attacker instead could receive the victim's response depending on race timing).

This is structurally identical to the capabilities handler's `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:411-414`), which the question references as the confirmed baseline bug.

### Impact Explanation
This maps to a cross-user response confusion / request impersonation impact: an attacker who can submit gateway messages with a colliding `MessageId` can hijack or deny another user's pending gateway callback, either capturing the victim's DON response (which could include plaintext execution results, e.g. computed values, non-secret payloads depending on handler) or silently dropping/denying the victim's request outcome. However, `dummyHandler` is registered under `DummyHandlerType` (`core/services/gateway/handler_factory.go:79-80`) and its own documentation/name ("DummyHandler forwards each request/response without doing any checks") indicates it is a no-op/testing pass-through handler with no authentication, allowlist, or validation logic (unlike `capabilities.handler`, which enforces payload/timestamp/method checks before the same map write). There is no evidence in the codebase that `DummyHandlerType` is used in production DON/gateway configurations for real user-facing capabilities — it is likely retained for internal test/dev routing.

### Likelihood Explanation
No credentials beyond the ability to reach the gateway's user-message endpoint for a DON configured with the `dummy` handler type are required, and `MessageId` is fully attacker-chosen with no server-side uniqueness enforcement, so if this handler is reachable, the collision is trivially and repeatably reproducible (two concurrent/sequential requests with the same ID). The realistic likelihood is limited by the fact that the affected handler's role in production deployments could not be confirmed from the available code/config in this repo — no gateway configuration file wiring `DummyHandlerType` to a live, externally-reachable DON was found in the indexed files.

### Recommendation
Before inserting into `d.savedCallbacks`, check for an existing (non-expired) entry under the same `MessageId` and reject the new request (e.g., return an error / distinct response) instead of silently overwriting it — mirroring a fix that should also be applied to the capabilities handler's identical pattern. Alternatively, derive the map key from a value that combines the caller's identity/session with the message ID rather than trusting a bare client-supplied ID.

### Proof of Concept
Extend `handler.dummy_test.go` with a table/unit test:
1. Create `dummyHandler` via `handlers.NewDummyHandler`.
2. Build `msgA` and `msgB`, both with `Body.MessageId = "dup-id"` but different senders/signing keys, and register two separate `hc.NewCallback()` instances `cbA`, `cbB`.
3. Call `handler.HandleLegacyUserMessage(ctx, &msgA, cbA)` then, before any node response arrives, call `handler.HandleLegacyUserMessage(ctx, &msgB, cbB)`.
4. Assert that `d.savedCallbacks["dup-id"]` now references `cbB`'s callback (inspect via a node response keyed to `"dup-id"` and confirm it resolves `cbB.Wait()` and not `cbA.Wait()`).
5. Assert `cbA.Wait()` never resolves (times out), demonstrating the original caller's callback was silently dropped/overwritten — confirming the map-overwrite bug recurs at `core/services/gateway/handlers/handler.dummy.go:63-64`.
