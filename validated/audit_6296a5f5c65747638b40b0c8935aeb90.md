### Title
Repeated sync deposits reset a single shared per-receiver refund lock, indefinitely delaying redemption of the receiver's units - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.deposit`/`mint` route through `_syncDeposit`, which unconditionally overwrites the single per-receiver lock timestamp `userUnitsRefundableUntil[receiver]` with `block.timestamp + depositRefundTimeout` on every call [1](#0-0) . Since `redeem`/`withdraw` are gated by this single, non-cumulative timestamp for the entire receiver address (not per-deposit) [2](#0-1) [3](#0-2) , an ordinary user who makes a second sync deposit before their first deposit's lock expires resets the lock forward for *all* of their previously deposited units, mirroring the "Cooling Period Reset on Multiple Requests" pattern from the report.

### Finding Description
`deposit()` and `mint()` are both public, callable by any receiver-authorized caller (`_requireValidReceiver` only requires `receiver == msg.sender` or explicit approval, no privileged role) [4](#0-3) [5](#0-4) . Both funnel into `_syncDeposit`:

```
function _syncDeposit(...) internal {
    uint256 refundableUntil = block.timestamp + depositRefundTimeout;
    ...
    userUnitsRefundableUntil[receiver] = refundableUntil;   // unconditional overwrite
    IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(...);
}
``` [6](#0-5) 

`redeem()` and `withdraw()` both require `userUnitsRefundableUntil[msg.sender] < block.timestamp` to proceed [2](#0-1) [3](#0-2) . Because the lock is stored as a single scalar per address rather than tracked per-deposit (e.g., a max-of or per-batch schedule), any new sync deposit by the same receiver — even a tiny, unrelated one — pushes the lock further into the future and blocks redemption of the *entire* unit balance, including units from an earlier deposit whose own timeout had almost elapsed. This is the exact "cooling period reset on multiple requests" root cause: a shared, overwritten timestamp instead of independently-tracked eligibility windows.

Ordinary-user sequence:
1. User calls `deposit(token, tokensIn1, minUnitsOut1, self)` at `T0`. Lock set to `T0 + depositRefundTimeout`.
2. Before that lock expires (e.g., at `T0 + depositRefundTimeout - 1`), the same user calls `deposit` again with a minimal amount for the same receiver. Lock is overwritten to `(T0 + depositRefundTimeout - 1) + depositRefundTimeout`.
3. `redeem`/`withdraw` for the user's *entire* unit balance (including the first deposit) now reverts with `Aera__UnitsLocked` until the new, much later timestamp — repeatable indefinitely to hold funds hostage.

`depositRefundTimeout` can be configured up to `MAX_DEPOSIT_REFUND_TIMEOUT = 30 days` [7](#0-6) , so each repeated small deposit can add up to another 30-day freeze on top of whatever time remained.

### Impact Explanation
This causes a temporary freezing of a user's own sync-deposited units/funds: redemption via `redeem`/`withdraw` reverts (`Aera__UnitsLocked`) for the receiver's whole balance, extendable indefinitely by repeated minimal deposits, matching Immunefi Medium-severity "temporary freezing of user funds" impact. No admin, guardian, solver, or oracle collusion is required — it is triggerable purely with the standard `deposit`/`mint` entry points using the receiver's own funds.

### Likelihood Explanation
Likelihood is high for any user who deposits more than once within the `depositRefundTimeout` window (a normal usage pattern, e.g., dollar-cost-averaging deposits, or a UI that batches/executes deposits close together). No special permissions, price manipulation, or third-party dependency is needed; only two ordinary `deposit` calls from the same account within the window are required. The freeze is self-inflicted or could be triggered by any depositor address approved via `setDepositReceiverApproval` for a victim receiver.

### Recommendation
Do not use a single overwritten scalar for the redeem lock. Options:
- Extend the lock only forward via `max(existing, new)` is still insufficient since it still cascades earlier deposits' locks; better: track per-deposit refundability (already recorded via `syncDepositHashes`) and gate `redeem`/`withdraw` only against units actually still within their own individual refund window, or
- Restrict the redeem-lock check to only the newly-deposited amount, allowing the user to redeem previously-deposited (already-unlocked) units even if a new deposit is pending refund.

### Proof of Concept
Foundry steps (local fork):
1. Deploy/point to a live `ProvisionerV2` instance with `depositRefundTimeout` set (e.g., 7 days), sync deposits enabled for a token.
2. As `user`, call `deposit(token, amount1, minUnitsOut1, user)` at `t0`. Assert `userUnitsRefundableUntil[user] == t0 + depositRefundTimeout`.
3. Warp to `t0 + depositRefundTimeout - 1`.
4. Call `deposit(token, amount2 (minimal), minUnitsOut2, user)` again. Assert `userUnitsRefundableUntil[user]` is now `(t0 + depositRefundTimeout - 1) + depositRefundTimeout`, i.e., ~2x the original window from `t0`.
5. Warp to the originally expected unlock time `t0 + depositRefundTimeout + 1` and call `redeem`/`withdraw` for `amount1`'s units. Assert it reverts with `Aera__UnitsLocked`, proving the first deposit's funds remain frozen well past its intended eligibility window solely due to the second, unrelated deposit.

    /// @notice Handles a synchronous deposit, records the deposit hash, and enters the vault
    /// @dev Reverts if the deposit hash already exists. Sets the refundable period for the user
    /// @param token The ERC20 token to deposit
    /// @param tokenAmount The amount of tokens to deposit
    /// @param unitAmount The amount of vault units to mint for the user
    /// @param receiver The address receiving the minted units
    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }
