This is a genuine spec-level analog of the "override defeated by front-running" bug class, found in the ePBS (Gloas) builder-payment / proposer-slashing interaction.

### Title
Builder payment clawback in `process_proposer_slashing` is always settled first by `process_parent_execution_payload`, so the intended payment-voiding protection never fires - (File: specs/gloas/beacon-chain.md)

### Summary
`process_proposer_slashing` in Gloas is supposed to void ("clear") the `BuilderPendingPayment` tied to a proposal slot when that slot's proposer is later proven to have equivocated. However, `process_block` always runs `process_parent_execution_payload` (which calls `settle_builder_payment`, irrevocably moving the payment into `builder_pending_withdrawals`) *before* `process_operations` (which runs `process_proposer_slashing`) — in every single block, including the very next block after the slot in question. Because a `ProposerSlashing` can only be constructed and included after two conflicting signed headers exist (i.e., essentially never in the same block as the payment's own registration), the clawback logic operates on an already-emptied entry in effectively all real-world cases, and the builder payment always escapes the clawback.

### Finding Description
The block-processing order for Gloas is: [1](#0-0) 

`process_parent_execution_payload` (step 1) is executed for the *parent* slot's bid before `process_operations` (step 7, containing `process_proposer_slashing`) executes for the *current* block. Inside `process_parent_execution_payload` → `apply_parent_execution_payload`, the payment for the parent slot is unconditionally settled: [2](#0-1) 

`settle_builder_payment` always clears the entry (moving it to `builder_pending_withdrawals` first if non-zero) regardless of anything else: [3](#0-2) 

The payment entry that is later supposedly voidable is registered when the bid is processed for its own slot, at the same array index that `settle_builder_payment` will later clear: [4](#0-3) 

The clawback itself lives in `process_proposer_slashing`, explicitly intended to void the payment for a slashed proposer's slot within a 2-epoch window: [5](#0-4) 

Walking through a concrete timeline: proposer P proposes slot N with a non-zero builder bid; `process_execution_payload_bid` registers `builder_pending_payments[SLOTS_PER_EPOCH + N % SLOTS_PER_EPOCH]`. The very next block, at slot N+1, runs `process_parent_execution_payload` as the *first* step of `process_block`, which calls `settle_builder_payment` on that exact same index — appending the withdrawal to `builder_pending_withdrawals` and clearing the entry to empty — before that same block's `process_operations` (and hence any `ProposerSlashing` op) has run. A `ProposerSlashing` proving P equivocated at slot N requires two conflicting *signed* headers, something that by construction cannot be assembled and included earlier than block N+1's operations, and in practice is discovered and included even later. By the time such a slashing is ever processed (block N+1 or later), `builder_pending_payments[...]` for slot N is already `BuilderPendingPayment.empty()` (proposer_index defaults to 0), so the equality check `payment.proposer_index == header_1.proposer_index` fails to match the real payment (which no longer exists) and the clear is a no-op on an already-empty slot — the withdrawal has already been irrevocably queued.

The only scenario in which the clawback can possibly fire is if the *same block* N that registers the payment also carries a `ProposerSlashing` against its own proposer for slot N — a case that would require the proposer to self-report their own earlier equivocation in the very block they are proposing, which is not the general adversarial case the code's comment ("Remove the BuilderPendingPayment ... if it is still in the 2-epoch window") is describing.

### Impact Explanation
This breaks the equality the spec text itself sets up: the payment queued for a slot's builder should be revocable when the slot's proposer is proven to be an equivocator, but the processing order guarantees the payment is always already settled into `builder_pending_withdrawals` before any `ProposerSlashing` can reach `process_operations`. The result is a builder payment that the spec's own code intends to prevent, but which is paid out in essentially all real cases — a builder payment that "escapes" its intended clawback, matching the High-severity impact category of a builder payment/withdrawal escaping its intended control.

### Likelihood Explanation
This triggers deterministically on every chain that ever slashes a block proposer whose slot carried a non-zero builder payment, since `ProposerSlashing` evidence can never realistically arrive before the very next block's `process_parent_execution_payload` already settles the payment. No adversarial coordination, stake, or race condition timing is needed — the bug is inherent in the fixed function ordering inside `process_block`, so it fires on the ordinary, expected use of the slashing mechanism.

### Recommendation
Reorder `process_block` so that `process_operations` (and specifically `process_proposer_slashing`) runs, or at least is checked, before `process_parent_execution_payload` settles the parent's payment; alternatively, have `apply_parent_execution_payload`/`settle_builder_payment` consult slashing state (or defer settlement) so a slot's builder payment cannot be irrevocably queued until any pending equivocation evidence for that slot's proposer has had a chance to clear it.

### Proof of Concept
1. Builder B bids a non-zero `value` for slot N; proposer P proposes block N referencing B's bid. `process_execution_payload_bid` (during block N's own transition) sets `state.builder_pending_payments[SLOTS_PER_EPOCH + N % SLOTS_PER_EPOCH]` with `proposer_index = P`.
2. Proposer P (having earlier signed two conflicting headers for slot N, e.g. due to a missed/duplicate proposal or a bug) is later provably an equivocator; independent parties construct the `ProposerSlashing` evidence.
3. Any proposer, including a fully honest one, proposes block N+1. `process_block` runs `process_parent_execution_payload` → `apply_parent_execution_payload` → `settle_builder_payment` for slot N's index first, appending the withdrawal to `state.builder_pending_withdrawals` and clearing the pending-payment entry to `BuilderPendingPayment.empty()`.
4. Only afterwards does block N+1's `process_operations` run. Even if the `ProposerSlashing` for P's slot-N equivocation is included in this very block N+1, `process_proposer_slashing` finds `state.builder_pending_payments[payment_index]` already empty (`proposer_index == 0`), so the intended clear is a no-op.
5. The builder's payment for the equivocating proposer's slot is paid out via the standard withdrawal sweep regardless — the protection never had a chance to activate.

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)

    if payment.withdrawal.amount > 0:
