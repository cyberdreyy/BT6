### Title
Race condition in `HandleLegacyUserMessage` allows cross-request/cross-user response misdelivery via `MessageId` collision - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the response callback in `h.savedCallbacks` keyed **only** by the attacker-supplied `msg.Body.MessageId`, then releases the mutex before broadcasting the request to all DON members. Because `MessageId` is a client-chosen field with no per-sender scoping or uniqueness enforcement, two concurrent requests (from the same or different signers) that pick the same `MessageId` can race on the map entry, causing the response payload from one request to be delivered to the other request's callback.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`:

```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()

for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [1](#0-0) 

`msg.Body.MessageId` is not server-generated: it is an arbitrary, attacker-controlled string bounded only by length checks in `Message.Validate()` (`MessageIdMaxLen`, non-empty, no trailing null byte) — there is no uniqueness or sender-binding requirement. [2](#0-1) 
This is confirmed by the reference client tooling, where `MessageId` is a plain CLI flag defaulting to a fixed literal (`"12345"`), fully chosen by the caller: [3](#0-2) 

On the response path, `handleWebAPITriggerMessage` looks the callback up **solely by `MessageId`**, deletes it, and forwards whatever raw response arrived to whichever callback is currently occupying that slot:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [4](#0-3) 

Exploit flow: two requests (from any sender(s)) share the same `MessageId` and are processed concurrently by two goroutines G1 (payload A, callback A) and G2 (payload B, callback B):
1. G1 locks, writes `savedCallbacks[id] = cbA`, unlocks.
2. G2 locks, overwrites `savedCallbacks[id] = cbB`, unlocks (cbA reference is lost from the map).
3. G1's loop and G2's loop both broadcast their respective requests (reqA, reqB) to all DON members — since the loop runs outside the lock and is unsynchronized with the map state, both broadcasts proceed regardless of which callback is currently stored.
4. When a node returns its response for reqA (built from A's request/signature), `handleWebAPITriggerMessage` looks up `savedCallbacks[id]`, finds `cbB` (because it was the last writer), deletes the entry, and delivers A's response data to `cbB` — i.e., user B's callback now receives content correlated with user A's request, and vice versa for B's own response, which will find no entry (already deleted) and be silently dropped.

This violates the intended request-callback binding: "each user request is processed by a separate goroutine ... waits on callbackCh" per the `Handler` interface contract, which implicitly assumes a callback receives the response to *its own* request. [5](#0-4) 

No authentication/signature check prevents this: `Message.Validate()` only verifies the signature belongs to *some* valid sender for that message, it does not enforce that `MessageId` is unique or bound to that sender across concurrent in-flight requests. [6](#0-5) 

### Impact Explanation
This is a cross-user response confusion vulnerability: an unauthenticated/low-privilege gateway client can cause another concurrent legitimate user's trigger response (potentially containing sensitive workflow trigger output) to be delivered to the attacker's own callback, or cause a legitimate user to receive a response correlated with a different request/sender. This matches the "attacker-controlled data returned to another user" / cross-user response confusion bounty impact class. It does not grant fund movement or credential disclosure directly, but breaks the request-isolation invariant of the gateway.

### Likelihood Explanation
Exploitability depends on the attacker being able to cause `MessageId` collision with a *concurrently in-flight* legitimate request. Since `MessageId` is entirely client-chosen with no uniqueness enforcement, an attacker can trivially collide with their own requests, and can also collide with other users' requests if those IDs are predictable/short (as suggested by example tooling using literal/short IDs) or if the attacker can observe/guess pending IDs (e.g., via monitoring, replay, or predictable client-side ID schemes). The race window requires precise timing between the map write and the node's response return, making it a genuine but timing-dependent bug — feasible with repeated attempts given attacker control over both request timing and `MessageId` value.

### Recommendation
- Scope `savedCallbacks` keys by a composite of `(sender, MessageId)` or generate/enforce a server-side unique correlation ID per accepted request instead of trusting client-supplied `MessageId` alone.
- Reject `HandleLegacyUserMessage` calls that reuse a `MessageId` already present in `savedCallbacks` (return an error instead of silently overwriting).
- Hold the callback registration and the SendToNode broadcast under a single atomic unit relative to that specific `MessageId`/sender pair, or use a per-request unique key so concurrent requests can never collide.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two valid, signed `triggerRequest` messages with **identical** `MessageId` ("dup-id") but different `Payload` content and different signers (or same signer, different payload).
2. Create two distinct `hc.Callback` instances `cbA`, `cbB`.
3. Launch two goroutines calling `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` and `handler.HandleLegacyUserMessage(ctx, msgB, cbB)` concurrently, synchronized via a barrier so both hit `h.mu.Lock()` write region as close together as possible; mock `don.SendToNode` to record which request was sent for each call.
4. After both goroutines return, invoke `handler.HandleNodeMessage`/`handleWebAPITriggerMessage` with a node response corresponding to `msgA`'s content.
5. Assert deterministically that the response is delivered to `cbA` (the callback associated with `msgA`) and not `cbB`. Run the test with `-race` and repeat in a loop (e.g., 1000 iterations) to demonstrate that the assertion fails intermittently — i.e., `cbB.Wait()` sometimes receives `msgA`'s response content — proving the invariant is race-dependent rather than deterministic.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response

		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
