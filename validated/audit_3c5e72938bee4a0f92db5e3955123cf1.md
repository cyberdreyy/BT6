### Title
Cross-epoch instant-withdraw over-read excludes old unfunded receipts from default recovery basis, letting them drain the reserve at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE-2020-24977 bug class is an out-of-bounds / over-read: data is read past the boundary that was actually provisioned. The analog in `IdleCreditVault` is an epoch-bounds over-read: default finalization reads only `instantWithdrawClaimsByEpoch[epochNumber]` (the *current* epoch) as the instant-receipt claim basis, while `pendingInstantWithdraws` and `instantWithdrawsRequests[user]` are *global aggregates* spanning all epochs. An instant receipt left unfunded in an earlier epoch is never added to `totalBasis` in `finalizeDefaultRecovery`, yet after finalization it is still paid at par through `_transferFundedClaim`, out of the same strategy balance backing `defaultRecoveryReserve`.

### Finding Description
- `defaultPendingClaimBasis()` adds current-epoch instant claims only when `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`). It reads `instantWithdrawClaimsByEpoch[epochNumber]` — a single-epoch bucket — but the gate (`pendingInstantWithdraws`) is a lifetime aggregate of unfunded instant requests (`IdleCreditVault.sol:374`, `collectInstantWithdrawFunds` at `:398-403` only decrements by what the borrower actually funded).
- `requestInstantWithdraw` records receipts per epoch (`instantWithdrawsRequestsByEpoch[user][epochNumber]`, `:371-372`) but never prevents a new request while older unfunded receipts exist, and epoch rollover (`epochNumber += 1` in `deposit`, `:610`) moves the index forward without clearing old buckets.
- At finalization, `_defaultPrefundedInstantReserve()` compares the *aggregate* `pendingInstantWithdraws` against only the *current-epoch* `instantWithdrawClaimsByEpoch[epochNumber]` (`:716-723`). If a stale unfunded receipt from epoch N-1 inflated `pendingInstantWithdraws` above the epoch-N basis, `prefundedReserve` clamps to 0 and `totalBasis` omits the stale receipt entirely, inflating `defaultRecoveryPrice` (`:679-688`).
- After finalization, `claimInstantWithdrawRequest` (`:380-392`) first clears the defaulted-epoch slice via `_claimDefaultedInstantWithdrawRequest` (`instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, `:843-844`), then pays the *entire remaining* `instantWithdrawsRequests[user]` — including the stale unfunded epoch-N-1 basis — at par via `_transferFundedClaim`. Those underlyings come out of the strategy balance that constitutes `defaultRecoveryReserve`.

Broken invariant: fair recovery distribution / one receipt one payout. The reserve was sized for `totalBasis` at `defaultRecoveryPrice`, but an excluded-basis receipt consumes it at `RECOVERY_FULL`.

### Impact Explanation
Direct theft / insolvency of the default recovery reserve. An unprivileged lender holding an unfunded instant-withdraw receipt from an epoch prior to the default epoch claims it at 100% instead of `defaultRecoveryPrice`, over-reading value never provisioned for it. Quantified loss: `staleReceipt * (1 - defaultRecoveryPrice)` is extracted from the reserve, so defaulted-epoch withdraw and instant claimants (and post-default `postDefaultRequests` claimants paid 1:1 from the same reserve, `:760-767`) are left underpaid or reverted on `safeTransfer` — i.e., last claimers' recovery is stolen or frozen. The `_burn`/`safeTransfer` would revert with insufficient balance only after earlier claimants already extracted the shortfall, so the loss is borne by honest recovery claimants.

### Likelihood Explanation
Requires a specific but plausible sequence: an epoch ends with instant requests only partially funded by the borrower (`pendingInstantWithdraws > 0` persists into the next epoch — supported by the prefunded-instant design at `:716-723`), a subsequent epoch runs, a new instant request lands in the new `epochNumber`, and the borrower defaults before full funding. All steps use only unprivileged `requestInstantWithdraw` calls plus honest manager/borrower epoch sequencing; no privileged misbehavior is needed. The recovery-price miscalculation is deterministic once the state exists. Likelihood is moderate: it needs partial instant funding to survive an epoch boundary and then a default, both of which are normal protocol states (partial funding and borrower default are explicitly handled paths).

### Recommendation
Account for stale-epoch instant receipts at finalization: either include the full aggregate instant basis (sum over all epochs with unfunded receipts, or track an `instantWithdrawClaimsTotal`) in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` instead of `instantWithdrawClaimsByEpoch[epochNumber]`, and make `_claimDefaultedInstantWithdrawRequest` clear all per-epoch slices at `defaultRecoveryPrice`; or haircut every unfunded instant receipt (not just `defaultRecoveryEpoch` ones) by clearing `instantWithdrawsRequests[user]` fully through `_transferDefaultRecovery`. Alternatively, prevent new instant requests while `pendingInstantWithdraws > 0` spans an epoch boundary. Also bound the saturating subtraction `pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis` (`:852`) so it cannot mask cross-epoch double counting.

    // (reserve - s) / basis < defaultRecoveryPrice  -> reserve shortfall / last-claim revert
