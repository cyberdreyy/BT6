### Title
Unsigned `reason_code` / `response_data.failed_txid` fields in `BlockRejection` let an attacker relabel a captured honest rejection as an arbitrary "problematic transaction" ban vote - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`stackerdb_listener.rs` accumulates per-txid rejection weight (`FailedTxInfo::total_weight` / `problematic_weight`) keyed off `rejected_data.reason_code` and `rejected_data.response_data.failed_txid`, but the only cryptographic check performed on an incoming `BlockRejection` is `recover_public_key()` matching the expected signer for the slot. If `BlockRejection`'s signed digest does not cover `reason_code` and `response_data`, an attacker with only gossip access can take one genuinely signed rejection from an honest signer, mutate those two fields to point at a victim `Txid`, and have it accepted as if that honest signer voted the victim transaction "problematic" — without holding any private key.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `BlockResponse::Rejected` handling path (around lines 486-546) does the following:
1. Looks up the in-flight block by `rejected_data.signer_signature_hash`.
2. Calls `rejected_data.recover_public_key()` and checks the recovered key equals the expected signer's key for the claimed `slot_id`: [1](#0-0) 
3. If that check passes, it unconditionally trusts `rejected_data.reason_code` and `rejected_data.response_data.failed_txid` to update `FailedTxInfo`: [2](#0-1) 

The security of step 3 depends entirely on `reason_code` and `response_data` being part of the digest that `recover_public_key()`/`verify()` actually checks. If `BlockRejection::hash()` (in `libsigner/src/v0/messages.rs`) only covers `signer_signature_hash` (and not `reason_code`/`response_data`), then an attacker who observes one genuine `BlockRejection` gossiped by an honest signer can:
- keep the original `signature` and `signer_signature_hash` untouched (so `recover_public_key()` still resolves to the honest signer's real pubkey), and
- freely rewrite `reason_code` to `RejectCode::ValidationFailed(ValidateRejectCode::ProblematicTransaction)` and `response_data.failed_txid` to an arbitrary victim `Txid`,

then regossip the mutated message. `stackerdb_listener.rs` has no independent check binding `reason_code`/`failed_txid` to what was actually signed, so it will credit the honest signer's real weight toward `problematic_weight` for the victim txid the honest signer never flagged.

I was unable to directly inspect the body of `BlockRejection::hash()` / the signing routine in `libsigner/src/v0/messages.rs` within the available tool budget to confirm definitively which fields are included in the signed digest. This finding is therefore contingent on that premise (as stated in the question) being accurate; it should be verified against the actual `hash()`/`sign()` implementation before treating this as confirmed.

### Impact Explanation
If confirmed, this breaks the fail-closed invariant that "fields the aggregator trusts == fields actually covered by the signature." The consequence reaches into `signer_coordinator.rs`'s `permanently_excluded_txids` mechanism, which relies on aggregated `problematic_weight`/`total_weight` per txid to decide whether to permanently ban a transaction from future blocks. A poisoned tally could cause a legitimate transaction to be permanently excluded — a liveness violation against that transaction/user, not a chain-validity break. This best matches the **High** category (a bounded-liveness guarantee lost), since it does not cause a signer to sign an invalid/conflicting block, nor does it flip a rejection into a counted acceptance for block-level consensus.

Note that reaching the actual ban threshold requires accumulating enough total weight across multiple distinct honest signers' captured rejections (since a single captured message only carries that one signer's own weight, and `responded_signers` dedup prevents replaying the same slot twice for the same block). The severity is bounded by how much weight the attacker can harvest via repeated gossip observation over time, not by the attacker's own stake.

### Likelihood Explanation
Preconditions: attacker needs gossip/read access to the signer StackerDB set (to capture at least one genuine, currently-in-flight `BlockRejection` from an honest signer) plus write/gossip access to redistribute the mutated message — both consistent with the stated unprivileged threat model (one miner slot + gossip, no keys, no local host access). No majority of signers or private keys are required. This is repeatable per captured rejection and could be repeated across multiple tenures/blocks to accumulate weight toward a target txid, contingent on the unresolved premise about `BlockRejection::hash()`'s field coverage.

### Recommendation
Verify `BlockRejection::hash()`/`sign()` in `libsigner/src/v0/messages.rs`. Ensure the signed digest includes `reason_code` and all `response_data` fields (at minimum `failed_txid`), not just `signer_signature_hash`. If it does not, extend the hash computation to bind these fields cryptographically, and reject any message where the recomputed hash-over-full-content does not match what was signed.
