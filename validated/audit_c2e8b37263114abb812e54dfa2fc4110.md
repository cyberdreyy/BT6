## Finding: Confirmations from removed multisig members remain counted toward the approval threshold

### Title
Stale confirmations from deleted members allow a request to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges the confirmations/requests that were *originally created* by the member being removed. It never scans the confirmation sets of *other* active requests to strip out a vote the removed member had already cast on them. Because `confirm` (`multisig2/src/lib.rs` lines 292-315) counts `confirmations.len()` without re-validating that every entry in that set still corresponds to a current member, a request can execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
The custody binding here is: *a request is only allowed to execute once it has been approved by `num_confirmations` **currently valid** members* — i.e. `confirmations_from_live_members == num_confirmations` should hold at execution time.

`delete_member` breaks this invariant: [1](#0-0) 
It filters `self.requests` for entries whose `r.member == member` (the request's *creator*) and wipes those specific requests/confirmations. It does **not** iterate over `self.confirmations` of requests created by *other* members to remove the deleted member's vote from those sets.

`confirm` then blindly trusts the stored confirmation count: [2](#0-1) 
It only checks that the *new* confirmer is a current member (`current_member()`), but the pre-existing entries in `confirmations` (stored as serialized `MultisigMember` strings, not live-checked) are never re-validated against `self.members`.

Concretely: with members `{A, B, C, D}` and `num_confirmations = 3`,
1. `A` creates request `R1` (e.g. `Transfer`) and confirms it. `B` also confirms `R1`. `confirmations(R1) = {A, B}` (2/3).
2. A separate request to `DeleteMember { B }` is created and confirmed by `A, C, D` (3/3) and executes, removing `B` from `self.members` and its access key. Since `R1` was created by `A` (not `B`), `delete_member`'s cleanup loop skips it — `confirmations(R1)` still contains `B`.
3. `C` now confirms `R1`. `confirmations.len() + 1 = 3 >= num_confirmations (3)` → `R1` executes the `Transfer`.

`R1` executed with only two currently-valid confirmations (`A`, `C`) plus one stale vote from a removed member (`B`), i.e. `confirmations_counted (3) != live_member_confirmations (2)`, one less than the configured threshold of 3.

### Impact Explanation
This is a Critical-class issue per the given rubric: *"a multisig request executed below threshold."* Any pending request that already has confirmations from a member who is later removed retains those confirmations indefinitely. This lets the remaining members execute a `Transfer`, `AddKey`, `FunctionCall`, or any other multisig action with strictly fewer live approvals than the multisig's own `num_confirmations` policy demands, undermining the security guarantee that K-of-N members must currently agree before funds move or keys change.

### Likelihood Explanation
This does not require any privileged bypass beyond normal multisig operation: creating requests, confirming them, and later removing a member via the standard `DeleteMember` action are all ordinary flows exposed to any of the N members. No owner/foundation-only escape hatch or malicious deployment is needed — only that a member who had confirmed an outstanding request is subsequently removed (a realistic operational event, e.g. rotating out a compromised or departing signer) before that older request is confirmed to completion or deleted.

### Recommendation
When removing a member in `delete_member`, iterate over **all** active `self.requests`/`self.confirmations` entries (not just those created by the removed member) and strip the removed member's entry from every confirmation set. Alternatively, validate at `confirm`-time (and before executing) that every account/key in the stored confirmation set is still present in `self.members`, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `A, B, C, D` and `num_confirmations = 3`.
2. `A.add_request_and_confirm(R1)` where `R1 = Transfer { amount, receiver_id }`. `B.confirm(R1)`. Now `confirmations(R1).len() == 2`.
3. Separately create and fully confirm (`A, C, D`) a `DeleteMember { member: B }` request; it executes, removing `B` from `self.members`.
4. `C.confirm(R1)`. Because `confirmations(R1)` still contains `B`, `confirmations.len() + 1 == 3 >= num_confirmations`, so `R1`'s `Transfer` executes — approved by only `A` and `C` (2 live members) instead of the required 3. [3](#0-2) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
