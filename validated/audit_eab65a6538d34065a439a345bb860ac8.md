## Finding: Node-side signer response tally double-counts a signer's weight in both the accept and reject buckets

The bug-class in the report (inconsistent/contradictory votes not being reconciled, letting stale data leak into the wrong tally) has a direct analog in the stacks-node coordinator's tracking of signer `BlockResponse` messages, in `StackerDBListener::run` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`).

### Root cause

`BlockStatus` keeps two independent weight counters, `total_weight_approved` and `total_weight_rejected`, plus one `responded_signers` set that is used as the sole guard against double-counting [1](#0-0) .

- On `BlockResponse::Rejected`, weight is only added the first time a slot is seen, gated by `block.responded_signers.insert(slot_id)` [2](#0-1) .
- On `BlockResponse::Accepted`, weight is added whenever `!block.gathered_signatures.contains_key(&slot_id)` — this check is against the `gathered_signatures` map only, and never consults `responded_signers` or whether the slot already contributed to `total_weight_rejected` [3](#0-2) .

So the guard is asymmetric:
- Accept → Reject: `responded_signers.insert` returns `false` the second time, so the reject weight is correctly suppressed.
- Reject → Accept: nothing suppresses the accept weight; the signer's weight lands in `total_weight_approved` even though it is still sitting in `total_weight_rejected` from the earlier rejection. There is no code path in this file that ever decrements `total_weight_rejected`.

This is the same class of defect as the audited `CurrencyGovernance.reveal` bug: the code assumes a single, consistent verdict per voter/signer but never enforces or reconciles it, so a value that should have been superseded/discarded stays live in a stale bucket and gets used in later math.

By contrast, the *signer*-side ledger in `stacks-signer/src/signerdb.rs` handles this correctly: `add_block_rejection_signer_addr` refuses to record a rejection if a signature already exists [4](#0-3) , and `add_block_signature` clears any prior rejection for that signer/block, as confirmed by the `reject_then_accept` unit test [5](#0-4) . The node-side `StackerDBListener` never received the equivalent reconciliation.

### Impact

`SignerCoordinator::wait_for_signer_signatures_processed` (or equivalent) reads `block_status.total_weight_rejected` and `total_weight_approved` and checks rejection *before* acceptance [6](#0-5) . Because a single signer that first rejects then reverses to accept keeps contributing to `total_weight_rejected` forever, its stale weight can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` even though the true, current blocking-minority weight (signers who still stand by a rejection) never reached that bar. This causes the miner to treat the block as `SignersRejected` — excluding transactions and abandoning a block that a real supermajority may have actually accepted. This is a liveness wedge on block production (a "one-slot" signer, by flip-flopping a single response, can force the coordinator into the rejection branch prematurely), not a majority-only issue, since it only requires one signer's message pair plus gossip delivery through StackerDB.

### Recommendation

In the `Accepted` branch of `StackerDBListener::run`, check `responded_signers` (or a per-slot last-verdict map) before crediting `total_weight_approved`, and if the slot was previously counted as rejected, subtract its weight from `total_weight_rejected` (or otherwise store one canonical verdict per slot and recompute both totals from that single source of truth), mirroring the reconciliation already implemented in `stacks-signer/src/signerdb.rs::add_block_signature`.

### Caveat / what I could not fully verify
I was not able to view the full body of `SignerDb::add_block_signature` (only inferred its clearing behavior from the `reject_then_accept` test), and I did not have time to trace every call site that reads `BlockStatus` in `signer_coordinator.rs` to confirm there is no other reconciliation step downstream that neutralizes the stale rejected weight. If such reconciliation exists elsewhere, the severity would be reduced from a wedge to a purely informational/logging inconsistency.
