### Title
Node-unreachable fallback in `check_latest_block_in_tenure` defaults to "proposal is higher" instead of erroring - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` is the shared height-veto check run at proposal time, at validate-ok, and at signing (`check_block_against_signer_db_state`, `check_proposal`). When it needs to fall back to the node's view of a tenure's tip (because the signer's local DB has no fresh signed/pre-committed block to compare against) and the RPC call `client.get_tenure_tip(tenure_id)` fails for any reason, the function does not propagate an error or reject — it silently treats the failure as "the proposal is higher than the tenure tip" and returns `Ok(true)`, i.e., "passes." [1](#0-0) 

### Finding Description
This is the same bug class as the deprecated `latestAnswer` finding: a data source that can fail to answer is treated as if it returned a normal, valid answer instead of surfacing an error to the caller. Here, a connectivity failure to the stacks-node (`get_tenure_tip`) is silently converted into an affirmative pass (`Ok(true)`) rather than an error/rejection, even though the surrounding code elsewhere in the very same function (and in the analogous `conflict_still_blocks`/`reorg_permit_stands` helpers) is careful to route node-query failures toward the safe/blocking branch.

The comment at the call site rationalizes this as "safe because this proposal ultimately must be passed to the stacks-node for proposal processing," i.e., the node's own `/v3/block_proposal` endpoint is assumed to be the backstop: [2](#0-1) 

But this backstop assumption does not hold uniformly for every call site of `check_latest_block_in_tenure`:
- It is called from `check_block_against_signer_db_state`, which explicitly documents itself as running *after* node validation already succeeded (`handle_block_validate_ok`) and again at the pre-commit/signing threshold (`store_and_process_block_signature` → `handle_block_pre_commit`) — i.e., after the stacks-node backstop has already been consulted once. If `get_tenure_tip` fails only on this *second* re-check (e.g. transient node hiccup, restart, or an attacker/observer inducing brief unavailability of the tip endpoint at just the right moment between validate-ok and the pre-commit threshold), the "backstop" premise (a fresh call to the node's proposal-validation endpoint) is not actually re-invoked — the signer proceeds straight to counting the pre-commit/signature.
- The same code path is `confirms_latest_block_in_same_tenure`, used both at proposal arrival (where the node backstop assumption is more defensible) and reused via `check_block_against_signer_db_state` at signing time (where it is not, since the node is not re-consulted for full proposal validation before the pre-commit/signature is emitted).

Compare this to the two node-derived checks that guard the actual double-sign equivocation logic in the same file — `conflict_still_blocks` and `reorg_permit_stands` — both of which are careful to treat node errors as "leave the conflict in place" / "void the permit," i.e., always fail toward *not* signing: [3](#0-2) [4](#0-3) 

`check_latest_block_in_tenure`'s `get_tenure_tip` fallback breaks that same defensive pattern: a `ClientError` here becomes `Ok(true)` (proposal treated as higher / height-check passes), when it should instead be propagated as `Err` so the caller can reject with `ConnectivityIssues` — mirroring what `check_block_against_signer_db_state` already does for the `DBError`/other `ClientError` branches of the very same call: [5](#0-4) 

### Impact Explanation
This breaks the height-veto equality this check exists to enforce: "a proposal must confirm at least as many blocks as we already know about in this tenure." If the node's tip-fetch transiently fails at the pre-commit/signing re-check (after validate-ok already passed), the signer defaults to treating the proposal as height-valid without ever re-asking the node, and continues toward signing. Combined with the surrounding pre-commit/conflict-resolution logic, this widens the window in which a signer could sign a block that does not actually confirm the chain state it should — a liveness/safety property in the "one-per-height, approved-parent vs canonical" family the analog rules call out. It does not require a majority of signers or another signer's key: any transient failure of the local `get_tenure_tip` RPC (network blip, node restart, node under load) at the wrong moment against a race-condition-crafted competing/replayed proposal is sufficient to flip this single check from "pending" to "passed."

### Likelihood Explanation
Moderate: it requires a specific timing coincidence (a `get_tenure_tip` failure occurring exactly during the second, post-validation re-check rather than the original proposal-time check, which is the one place the "the node's proposal endpoint is the backstop" comment is actually justified). It is achievable by a party who can induce transient node RPC failures (load, minor network partition) around the pre-commit threshold window, without needing signer keys or a signer majority — but it is not a trivial, always-reachable path, and depends on the node being briefly unreachable at a very particular point in the flow.

### Recommendation
Change `check_latest_block_in_tenure` to propagate the `get_tenure_tip` error (`Err(e) => return Err(e)`) instead of defaulting to `Ok(true)`, and let each caller decide how to handle it — consistent with how `check_block_against_signer_db_state` already turns `Err` results from this same function into a `ConnectivityIssues` rejection. If the "node's proposal endpoint is the backstop" assumption is still desired for the initial proposal-arrival check, gate the fallback explicitly to that call site only, rather than sharing it with the post-validation/pre-signing re-checks where the backstop has not actually been re-invoked.

### Proof of Concept
1. A block reaches the pre-commit threshold; `store_and_process_block_signature`/`handle_block_pre_commit` invoke `check_block_against_signer_db_state`, which (for a non-tenure-change block) calls `SortitionData::check_latest_block_in_tenure`.
2. Inside `check_latest_block_in_tenure`, the local DB has no fresh signed/pre-committed block for the tenure (e.g., signer restarted or DB pruned that entry), so the code falls through to `client.get_tenure_tip(tenure_id)`.
3. Induce a transient failure of that specific RPC call at this moment (e.g., brief node restart/network blip) — see the `Err(e)` branch at [1](#0-0) .
4. The function returns `Ok(true)` unconditionally rather than propagating the error, so `check_block_against_signer_db_state` sees `is_latest == true` and returns `None` (no rejection), and the signer proceeds to sign/pre-commit without ever having re-confirmed the tenure's actual tip height.
