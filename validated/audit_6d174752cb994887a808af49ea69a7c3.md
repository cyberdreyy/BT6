### Title
Confirmations from a deleted multisig member remain counted toward `num_confirmations`, allowing a `DeleteMember`-processed request to execute below the live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` tallies confirmations by simply reading the size of the `confirmations` `HashSet<String>` stored for a `request_id`, without verifying that each recorded confirmer is still a current member of `self.members`. `delete_member()` only purges requests/confirmations for requests **originated by** the removed member (`r.member == member`), but never scans other pending requests' `confirmations` sets to strip out that removed member's prior confirmation entries. As a result, a K-of-N threshold can be met and a request executed using stale confirmations from members who have since been removed, breaking the binding "confirmations counted == live members who confirmed."

### Finding Description
`confirm()` at [1](#0-0)  increments/tallies confirmations purely from the stored `HashSet<String>` size:

```rust
let mut confirmations = self.confirmations.get(&request_id).unwrap();
...
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
} else {
    confirmations.insert(member.to_string());
    ...
}
```

There is no check that every string already in `confirmations` still corresponds to an entry in `self.members`.

`delete_member()` at [2](#0-1)  removes the member from `self.members` and deletes only the requests that member itself *added* (`if r.member == member`). It does not iterate over `self.confirmations` to purge that member's confirmations on requests **added by someone else**:

```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
...
self.members.remove(&member);
```

So if member `A` confirms a request `X` that was added by member `B`, and `A` is later removed via a separate `DeleteMember` request (permitted as long as `self.members.len() - 1 >= self.num_confirmations`, checked at [3](#0-2) ), `A`'s confirmation entry on request `X` is never cleaned up. It remains in `self.confirmations[X]` and continues to count toward the threshold in future `confirm()` calls on `X`.

Binding broken: `confirmations.len() (tallied) == number of confirmations from members currently in self.members`. After a member removal, the left side can exceed the right side, so a request can be finalized with fewer *live* member confirmations than `num_confirmations` requires.

### Impact Explanation
This falls under Critical impact — "a multisig request executed below threshold." Concretely, with `num_confirmations = 3` and members `[A, B, C, D]`:
1. `B` calls `add_request` for a `Transfer` (or any other action) request `X`.
2. `A` calls `confirm(X)` → `confirmations[X] = {A}` (len 1 < 3).
3. Members execute a separate, legitimate `DeleteMember{A}` request (requires 3 confirmations from `B, C, D`) — allowed since remaining members `{B, C, D}` still satisfy `len - 1 (3) >= num_confirmations (3)`. `A` is now removed from `self.members`, but `confirmations[X]` still contains `A`.
4. `C` calls `confirm(X)` → `confirmations[X] = {A, C}` (len 2 < 3).
5. `D` calls `confirm(X)` → `confirmations.len() + 1 = 3 >= 3` → request `X` executes, funding the transfer, key addition, etc.

Request `X` executed with confirmations from only 2 *current* live members (`C`, `D`) plus one stale confirmation from a removed member (`A`), even though the multisig is supposed to require 3-of-4 live members. This can move funds (`Transfer`), add access keys (`AddKey`), or perform any other multisig action below the intended threshold.

### Likelihood Explanation
This requires no attacker to be malicious or colluding out-of-scope; it only requires normal multisig operations that are entirely expected in production: a member confirms a request, and later membership changes (a routine key-rotation/offboarding event). No special privilege beyond being an ordinary current member of the multisig is needed to trigger or benefit from the flaw, and the sequence (confirm → unrelated member removal → later confirms reach threshold) is a realistic, low-effort operational pattern for any active multisig contract deployed with this code.

### Recommendation
When tallying confirmations in `confirm()`, filter `confirmations` to only members still present in `self.members` (or equivalently, when removing a member in `delete_member()`, iterate all pending `requests`/`confirmations` entries and strip that member's string from every confirmation set, not just requests they authored). Re-validate `confirmations.len()` against the live-member-filtered count before comparing to `num_confirmations`.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
