### Title
Missing role-based authorization on `POST /vault/dkg_results/export` allows any authenticated session/token user to exfiltrate raw DKG secret material - ([File: core/web/vault_controller.go])

### Finding Description
`VaultController.ExportDKGResult` (`core/web/vault_controller.go:91-119`) accepts an `instanceId` from the request body, loads the corresponding `ReportWithResultPackage` via `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(...)`, and returns it hex-encoded in the JSON API response with no authorization/role check inside the handler itself [1](#0-0) . The only gating present in the function body is a check that `instanceId` is non-empty and that a record exists — there is no ownership check, no capability/role check, and no scoping of which instances a given caller may export [2](#0-1) . `VerifyDKGResult`, defined immediately above it, exhibits the same pattern: it derives its authorization purely from possessing a matching DKG recipient key locally, not from the caller's identity [3](#0-2) .

Whether this is actually exploitable depends entirely on how `core/web/router.go` registers `/vault/dkg_results/export` — specifically whether it is wrapped with a role-restricting middleware (e.g. `RequiresEditRole`/`RequiresAdminRole`) or only with generic session/token authentication. I attempted to inspect the exact registration block in `router.go` (grep confirmed 3 occurrences of "vault" in that file) but was unable to retrieve the surrounding route-group code before running out of tool iterations, so I cannot confirm from this session whether a role wrapper is present or absent.

### Impact Explanation
If the route is registered without a role-restricting wrapper, any authenticated node user — including a low-privilege "view" role account or a restricted API token holder — could call this endpoint with an arbitrary `instanceId` and receive the raw DKG `ReportWithResultPackage` in hex form, which is sensitive vault/DKG secret material. This would match Chainlink's "sensitive data disclosure" / "unauthorized access to secrets" bounty impact class.

### Likelihood Explanation
Cannot be assessed with confidence without confirming the router registration. If no role wrapper exists, exploitation only requires a valid low-privilege session or API token and knowledge/guessing of an `instanceId` — a low bar. If a `RequiresEditRole`/`RequiresAdminRole` wrapper is applied at the router level (common pattern for sensitive Chainlink admin endpoints), the vulnerability does not exist as described.

### Recommendation
Regardless of the router-level finding, defense-in-depth is advisable: explicitly wrap the `/vault/dkg_results/export` (and `/vault/dkg_results/verify`) routes in `core/web/router.go` with an admin/edit-role-requiring middleware, and/or add an explicit role check inside `VaultController.ExportDKGResult` before returning secret material.

### Proof of Concept
Handler/integration test plan (to be executed against `router.go`'s actual route group):
1. Start test app with a session/API-token user assigned the lowest privilege role (e.g. "view").
2. `POST /vault/dkg_results/export` with `{"instanceId": "<existing-instance>"}` using that low-privilege credential.
3. Assert response status: expect `401`/`403` if properly protected.
4. If the response instead returns `200` with `hexPackage`/`sha` fields (per `presenters.NewExportDKGResultResource`), this confirms the authorization gap.

**Note:** I was unable to fully verify the exact middleware/role wrapper applied to this route in `core/web/router.go` within the available tool iterations — the file's vault-route registration lines were not retrievable in my last searches. Confirming this requires inspecting `core/web/router.go` directly (via a Devin session with full file access) to see whether `RequiresEditRole`/`RequiresAdminRole` (or equivalent) is applied to the `/vault/dkg_results/export` group.

func (vc *VaultController) VerifyDKGResult(c *gin.Context) {
	var req VerifyDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" || req.MasterPublicKey == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId and masterPublicKey are required"))
		return
	}

	keys, err := vc.App.GetKeyStore().DKGRecipient().GetAll()
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
	if len(keys) == 0 {
		jsonAPIError(c, http.StatusBadRequest, errors.New("no DKG recipient key found"))
		return
	}
	if len(keys) > 1 {
		jsonAPIError(c, http.StatusBadRequest, errors.New("multiple DKG recipient keys found"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	err = vaultcap.VerifyDKGResult(v.ReportWithResultPackage, req.MasterPublicKey, keys[0])
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("DKG result verification failed: %w", err))
		return
	}

	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewVerifyDKGResultResource(shaStr), "verifyDKGResult")
}
