### Title
Loss-adjusted withdraw funding is underpaid for receipts from earlier epochs: `lossRecoveryPriceByEpoch` only tags the current epoch, so users whose `lastWithdrawRequest` points to an older epoch claim at par and drain the haircutted pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` haircuts the *aggregate* `pendingWithdraws` and stores the recovery price under a single epoch key: `lossRecoveryPriceByEpoch[epochNumber]`. Claims, however, look up the recovery price per user via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Any pending receipt created in an epoch earlier than the loss epoch therefore has no haircut recorded and is paid in full by `_claimFundedWithdrawRequest`, even though the strategy only collected the haircutted amount. Early claimants withdraw more than was funded; later claimants find the vault insolvent. This is the same bug class as the ZeroLend `distributeEx` report: an accounting path that pays out the shared reward/funding pot without decrementing the corresponding claimable basis.

### Finding Description
In `collectWithdrawFunds` (lines 411-430), when the funded `_amount` is less than `pendingBasis`, the contract zeroes `pendingWithdraws` and records `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`. That haircut applies to *all* pending receipts — across every request epoch — but is indexed by a single epoch.

On the claim side (lines 789-801 and 319-350):

```solidity
// _claimLossAdjustedWithdrawRequest
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

Only the epoch stored in `lastWithdrawRequest[_user]` is checked for a haircut. Two exploitable shapes exist:

1. **Old receipt, no re-request.** User requests a withdraw in epoch N−1 (`lastWithdrawRequest[user] = N−1`). A loss is applied at the stop of epoch N, so `lossRecoveryPriceByEpoch[N]` is set while `lossRecoveryPriceByEpoch[N−1] == 0`. `_claimLossAdjustedWithdrawRequest` returns 0 and `_claimFundedWithdrawRequest` pays the full `withdrawsRequests[user]` at par (the epoch-wait check passes since `epochNumber > N−1`).

2. **Re-request bridging.** A user with a pending receipt in epoch N−1 can `requestWithdraw` again in epoch N (the guard at lines 263-271 only blocks when `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is already non-zero, which is not yet the case). `lastWithdrawRequest` is then overwritten to N and both epochs' claims are aggregated into `withdrawsRequests[user]`; on the loss-adjusted claim the user receives `claimBasis * price` for the N-epoch slice only via `withdrawsRequestsByEpoch[user][N]`, while the leftover N−1 slice in `withdrawsRequests[user]` is later paid again at par through `_claimFundedWithdrawRequest` once `lastWithdrawRequest` is cleared (line 835).

In both cases the vault only holds `pendingBasis * price` funded by the borrower, but pays some claimants the un-haircutted basis. The broken invariant is solvency of the funded-withdraw pot: total claims paid exceed funds collected for pending receipts.

### Impact Explanation
Direct theft of other users' funded withdraw proceeds. Claimants with a receipt whose `lastWithdrawRequest` differs from the loss epoch are paid at par from an underfunded pot; honest claimants who claim after them (including holders of haircutted N-epoch receipts) revert or receive nothing. The attacker's gain equals `basis * (1 − lossRecoveryPrice)`, i.e. the haircut share they dodged; the loss is socialized onto remaining claimants. The existing reserve guard in `_transferFundedClaim` (lines 897-907) only protects `defaultRecoveryReserve`, not the loss-adjusted funded pot.

### Likelihood Explanation
Requires an unprivileged lender to hold a pending withdraw receipt from an epoch earlier than the `stopEpochWithDuration` loss epoch — a normal condition whenever a user does not claim within the first eligible epoch (which the code explicitly allows: "if a user does not claim... he will have to wait for another epoch to claim both requests") or stacks requests across epochs. Then the manager/owner stops an epoch with a loss, which is a documented flow. No privileged misbehavior is needed; the attacker merely calls `claimWithdrawRequest` through the CDO.

### Recommendation
Apply the loss haircut to every pending receipt, not just the current epoch's. Options:
- Store the haircut per request epoch at request time is impossible (loss is unknown then); instead, at claim time, apply `lossRecoveryPriceByEpoch` to *each* epoch slice in `withdrawsRequestsByEpoch[_user]` for all epochs ≤ the loss epoch, or
- Keep a global "pending receipt haircut index" that multiplies any receipt created before the loss epoch, so `_claimFundedWithdrawRequest` can never pay a pre-loss receipt at par, or
- Simplest conservative fix: revert in `collectWithdrawFunds` when `_amount < pendingBasis` unless all outstanding basis belongs to `epochNumber` (e.g. require `pendingWithdraws == Σ withdrawsRequestsByEpoch[*][epochNumber]`), forcing full funding of mixed-epoch queues.

### Proof of Concept
Foundry fork PoC outline (test harness exists in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testOldEpochReceiptDrainsHaircuttedPot() public {
    // Epoch 0: epoch running, both users deposit via CDO
    _deposit(AA_USER, 1000e6);
    _deposit(BB_USER, 1000e6);
    _startEpoch();

    // User A requests withdraw during epoch 0, does NOT claim in epoch 1
    vm.prank(address(idleCDO));
    strategy.requestWithdraw(500e6, A, 500e6);

    // stop epoch 0 normally (no loss), epochNumber -> 1
    _stopEpoch();

    // User B requests withdraw during epoch 1
    vm.prank(address(idleCDO));
    strategy.requestWithdraw(500e6, B, 500e6);

    // Manager stops epoch 1 WITH a loss: borrower funds only 50%
    // pendingWithdraws = 1000e6 -> collectWithdrawFunds(500e6)
    // stores lossRecoveryPriceByEpoch[1] = 0.5e18, pendingWithdraws = 0
    _stopEpochWithLoss(500e6);

    // A's lastWithdrawRequest = 0, lossRecoveryPriceByEpoch[0] == 0
    // -> _claimLossAdjustedWithdrawRequest returns 0
    // -> _claimFundedWithdrawRequest pays A the FULL 500e6 at par
    vm.prank(address(idleCDO));
    uint256 claimedA = strategy.claimWithdrawRequest(A);
    assertEq(claimedA, 500e6);            // should have been 250e6

    // B claims the haircutted 500e6 * 0.5 = 250e6 basis...
    vm.prank(address(idleCDO));
    uint256 claimedB = strategy.claimWithdrawRequest(B);
    // vault only had 500e6 funded; A already took it all
    // -> claimedB == 0 or the transfer reverts: B's claim is insolvent
    assertEq(claimedB, 0);
}
```

Expected outcome: A steals B's share of the haircutted funding pot; the invariant `Σ paid ≤ Σ collected` is broken. The analogous `claimInstantWithdrawRequest` path should also be checked since `instantWithdrawsRequestsByEpoch` slices are epoch-indexed the same way while `_claimFundedClaim` pays the aggregate `instantWithdrawsRequests[user]` at par.
