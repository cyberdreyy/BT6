### Title
Kubernetes `terminalConn.Close()` is a no-op, so `Session.Kill()` fails to terminate a live interactive terminal after job cancellation - (File: executors/kubernetes/terminal.go)

### Summary
`TerminalConnect` in the Kubernetes executor returns a `terminalConn` whose `Close()` method unconditionally returns `nil` without cancelling anything, unlike the Docker executor's equivalent which wires a `context.CancelFunc` into `Close()`. Because `session.Session.Kill()` relies entirely on `terminalConn.Close()` to tear down an in-flight interactive terminal, calling it on job cancellation/system-interrupt does not actually stop the already-running WebSocket proxy loop for Kubernetes jobs.

### Finding Description
`TerminalConnect` builds a `terminalConn{settings: settings}` value with no cancellation hooks: [1](#0-0) . Its `Close()` implementation is a bare no-op: [2](#0-1) .

The live proxying happens inside `Start()`, which blocks in `terminalsession.ProxyTerminal` selecting on `timeoutCh`, `disconnectCh`, and the internal `wsProxy.StopCh` while streaming the pod's `pods/exec` WebSocket to the HTTP client: [3](#0-2) . `Start()` runs on the goroutine handling the incoming session HTTP request (`execHandler`), independent from the build goroutine: [4](#0-3) .

`Session.Kill()` is the only mechanism `Build.waitForTerminal` uses to stop a connected terminal when the job's context is cancelled or a system interrupt occurs (as opposed to the timeout path, which explicitly signals `TimeoutCh`): [5](#0-4) . `Session.Kill()` itself just calls `conn.Close()` and clears the pointer: [6](#0-5) .

For Kubernetes, `Close()` does nothing, so this call neither cancels a context nor pushes anything into `wsProxy.StopCh`/`disconnectCh`. The already-running `ProxyTerminal` select loop inside the concurrent `execHandler` goroutine has no way to learn that the job/build considers the terminal "killed." It keeps proxying the live `pods/exec` WebSocket stream (an interactive shell in the `build` container) until either the remote client disconnects on its own, or the pod's exec stream errors out (which only happens once `cleanupResources`/pod deletion in `executor.Cleanup()` actually removes the pod: [7](#0-6) ).

This is a real asymmetry versus the Docker executor, whose `terminalConn` carries a `ctx`/`cancelFn` pair tied to the exec creation specifically so that `Close()` (not shown in the truncated context but structurally implied by the stored `cancelFn`) can actually interrupt the live exec session: [8](#0-7) .

### Impact Explanation
When a job holding a live interactive terminal is cancelled, times out via `ctx.Done()`, or receives a `SystemInterrupt`, the Runner's own bookkeeping (`Session.terminalConn = nil`) says the terminal is closed, but the actual `pods/exec` WebSocket bridging the caller to the running pod's shell keeps running. Anyone still holding the session's terminal WebSocket connection retains an interactive shell inside the build container of a job the Runner/GitLab believes has ended, until the pod is physically deleted during `Cleanup()`. This violates the stated invariant that "session and proxy state must terminate with the live job," and can extend command execution / data access in the container beyond the job's nominal lifetime (bounded by the configured pod-deletion `CleanupGracePeriodSeconds`).

### Likelihood Explanation
The precondition is that the actor already has legitimate, authorized access to open an interactive terminal on the job (a GitLab feature gated by project permissions), so this is not a cross-job/cross-tenant hijack. Given that precondition, the bug is deterministically triggered any time the job is cancelled or interrupted while a terminal is connected — no race or timing luck required, since `Close()` for the Kubernetes path is unconditionally a no-op.

### Recommendation
Give the Kubernetes `terminalConn` its own cancellation state (context/`cancelFn` or a dedicated stop channel) created in `TerminalConnect`, and have `Close()` actually signal the running `ProxyTerminal`/`wsProxy` (e.g., write to `wsProxy.StopCh` or cancel a context threaded into `terminal.ProxyWebSocket`) so that `Session.Kill()` reliably tears down the live pod-exec stream, mirroring the Docker executor's cancellation pattern.

### Proof of Concept
Go integration test plan:
1. Set up a fake/mock `kubeClient` and `executor` similar to existing kubernetes terminal tests, invoke `TerminalConnect()` to get a `terminalConn`, and start `Start()` in a goroutine against an `httptest` WebSocket server simulating a connected client.
2. Call `terminalConn.Close()` directly (as `Session.Kill()` would) without sending anything on `timeoutCh`/`disconnectCh`.
3. Assert that the `Start()` goroutine does *not* return / the underlying `ProxyWebSocket` call is not interrupted (e.g., via a channel/flag proving the proxy loop is still active), demonstrating that `Close()` had no effect on the running proxy.
4. Compare against the Docker executor's equivalent test where calling `Close()` does cancel the context and unblocks `Start()`, to show the discrepancy.

func (s *Session) execHandler(w http.ResponseWriter, r *http.Request) {
	logger := s.log.WithField("uri", r.RequestURI)
	logger.Debug("Exec terminal session request")

	if !websocket.IsWebSocketUpgrade(r) {
		logger.Error("Request is not a web socket connection")
		http.Error(w, http.StatusText(http.StatusMethodNotAllowed), http.StatusMethodNotAllowed)
		return
	}

	ctx, cancel := context.WithTimeout(r.Context(), time.Minute)
	defer cancel()

	// There's a chance we'll get a interactive terminal connection before
	// we've hooked up the terminal to the underlying executor.
	//
	// When this occurs, we effectively wait for the terminal to be hooked up,
	// the request to be cancelled, or 1 minute (whichever comes first).
	select {
	case <-s.terminalSetCh:
	case <-ctx.Done():
	}

	if !s.terminalAvailable() {
		logger.Error("Interactive terminal not set")
		http.Error(w, http.StatusText(http.StatusServiceUnavailable), http.StatusServiceUnavailable)
		return
	}

	terminalConn, err := s.newTerminalConn()
	if _, ok := err.(connectionInUseError); ok {
		logger.Warn("Terminal already connected, revoking connection")
		http.Error(w, http.StatusText(http.StatusLocked), http.StatusLocked)
		return
	}

	if err != nil {
		logger.WithError(err).Error("Failed to connect to terminal")
		http.Error(w, http.StatusText(http.StatusInternalServerError), http.StatusInternalServerError)
		return
	}

	defer s.closeTerminalConn(terminalConn)
	logger.Debugln("Starting terminal session")
	terminalConn.Start(w, r, s.TimeoutCh, s.DisconnectCh)
}

func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()

	if s.terminalConn == nil {
		return nil
	}

	err := s.terminalConn.Close()
	s.terminalConn = nil

	return err
}

func (s *executor) Cleanup() {
	if s.eventsStream != nil {
		s.eventsStream.Stop()
	}

	s.cleanupResources()
	closeKubeClient(s.kubeClient)
	s.AbstractExecutor.Cleanup()
}

// cleanupResources deletes the resources used during the runner job
// Having a pod does not mean that the owner-dependent relationship exists as an error may occur during setting
// We therefore explicitly delete the resources if no ownerReference is found on it
// This does not apply for services as they are created with the owner from the start
// thus deletion of the pod automatically means deletion of the services if any
func (s *executor) cleanupResources() {
	// Here we don't use the build context as its timeout will prevent a successful cleanup of the resources.
	// The solution used here is inspired from the one used for the docker executor.
	// We give a configurable timeout to complete the resources cleanup.
	ctx, cancel := context.WithTimeout(context.Background(), s.Config.Kubernetes.GetCleanupResourcesTimeout())
	defer cancel()

	if s.pod != nil {
		kubeRequest := retry.WithFn(s, func() error {
			// kubeAPI: pods, delete
			return s.kubeClient.CoreV1().
				Pods(s.pod.Namespace).
				Delete(ctx, s.pod.Name, metav1.DeleteOptions{
					GracePeriodSeconds: s.Config.Kubernetes.CleanupGracePeriodSeconds,
					PropagationPolicy:  &PropagationPolicy,
				})
		})

		if err := kubeRequest.Run(); err != nil {
			s.BuildLogger.Errorln(fmt.Sprintf("Error cleaning up pod: %s", err.Error()))
		}
	}
