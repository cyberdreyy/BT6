### Title
Attacker-forged `BlockProposal.reward_cycle` label defeats `block_lookup_by_reward_cycle`, wedging block tracking across the reward-cycle boundary - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_proposal` routes and re-evaluates a proposal using a `reward_cycle` field that is entirely miner-controlled and unauthenticated against the block's real consensus-hash-derived cycle. Because `block_lookup_by_reward_cycle` performs an exact-equality filter on this field against `self.reward_cycle` of the *specific* `RegisteredSigner` instance handling the event, the exact same physical block (identical `signer_signature_hash`) can be made invisible to its own prior record simply by re-tagging the label with the adjacent cycle, forcing endless full re-evaluation instead of terminal convergence.

### Finding Description
The wedge equality the design depends on is:

```
stored BlockInfo.reward_cycle == self.reward_cycle (the instance processing the lookup)
``` [1](#0-0) 

`block_lookup_by_reward_cycle` looks a block up purely by `signer_signature_hash` (the block header hash) and then discards the result unless the stored `reward_cycle` exactly matches the *calling instance's* `self.reward_cycle`: [1](#0-0) 

`handle_block_proposal` uses this same equality twice — first as an early filter, then as the "have we seen this block" check that gates `should_reevaluate_block` (reuse of the prior verdict) vs. treating the proposal as brand new: [2](#0-1) 

The `reward_cycle` field on `BlockProposal` is set by the honest miner coordinator from `burnchain.block_height_to_reward_cycle(election_sortition.block_height)`, but it is never independently re-derived or cross-checked by the signer against the block's actual `consensus_hash`/sortition data: [3](#0-2) 

Because the whole `BlockProposal` (including this field) is inside the miner's own signed StackerDB chunk, an attacker who wins a single miner slot fully controls its value — it is not part of `signer_signature_hash` and is not validated against chain state anywhere in `check_proposal` (`stacks-signer/src/chainstate/v1.rs`/`v2.rs`), which only checks `consensus_hash`, miner pubkey hash, tenure/parent linkage and timing, never `reward_cycle`: [4](#0-3) 

Meanwhile, `RunLoop` runs up to two adjacent `RegisteredSigner` instances concurrently (keyed by `reward_cycle % 2` in `stacks_signers`), during the prepare-phase transition window, both backed by the *same* `db_path`: [5](#0-4) [6](#0-5) 

Every incoming event is dispatched to *all* configured `RegisteredSigner` instances unconditionally: [7](#0-6) 

Exploit flow:
1. Attacker wins one miner slot during the window where both cycle-N and cycle-(N+1) `RegisteredSigner` instances are alive.
2. Attacker crafts a valid `NakamotoBlock` whose `consensus_hash` is consistent with the real current sortition (cycle N), wraps it in `BlockProposal{reward_cycle: N}` and broadcasts it. The cycle-N instance accepts, evaluates, and (if not provably invalid) calls `self.signer_db.insert_block(&block_info)` with `reward_cycle = N` for that `signer_signature_hash`.
3. Attacker re-broadcasts the *identical* block (same header, same `signer_signature_hash`) inside a new `BlockProposal{reward_cycle: N+1}`. The cycle-(N+1) instance's early filter now passes (`block_proposal.reward_cycle == self.reward_cycle`). `check_proposal` still passes because it only checks real chain state (`consensus_hash`, tenure linkage), not the label. `block_lookup_by_reward_cycle` looks up the same hash, finds the row with `reward_cycle = N`, and because `N != N+1` returns `None` — the cycle-(N+1) instance treats the block as brand-new, re-runs full validation, and (per the `insert_block` upsert-by-hash semantics) writes the row's `reward_cycle` to `N+1`.
4. Any subsequent legitimate traffic for this hash addressed to the cycle-N instance (validation responses, pre-commits, `BlockResponse`s) now finds `block_info.reward_cycle == N+1 != self.reward_cycle == N` and is silently dropped ("we are not tracking it"), per the identical guard used in `handle_block_validate_ok`/`handle_block_validate_reject`: [8](#0-7) [9](#0-8) 
5. Attacker repeats the toggle indefinitely; each toggle causes a full, fresh `check_block_against_state` → `submit_block_for_validation` → `insert_block` cycle, and the record for the real block never durably accumulates a consistent, terminal `GloballyAccepted`/`GloballyRejected` verdict from the perspective of the correct signer instance.

Existing guards do not close this: `should_reevaluate_block`'s "already decided" reuse path (`docs/signer-flows.md` §3) is only reachable when `block_lookup_by_reward_cycle` returns `Some`, which it never does across the label toggle; the node-side `/v3/block_proposal` validation and `check_proposal`'s chainstate checks validate the block's *content*, not the signer-local `reward_cycle` metadata field, so they do not detect or reject the mislabeling.

### Impact Explanation
This breaks the bounded-liveness guarantee that a tracked block eventually reaches a terminal `BlockState` (`GloballyAccepted`/`GloballyRejected`) and stays there. By alternating the `reward_cycle` label on resubmissions of the same block, a single-slot miner can force perpetual re-validation and can silently strip a correctly-progressing signer instance's tracking of a block it had already validated/pre-committed/signed, because the shared-by-hash DB row's `reward_cycle` attribute gets flipped by the other concurrently-running instance. This matches the High-severity "signer wedged into never signing valid blocks (liveness)" category. It is fully repeatable for the duration of the two-instance overlap window (the prepare phase of the reward-cycle transition) and costs the attacker nothing beyond crafting and gossiping their own already-signed messages.

### Likelihood Explanation
Preconditions: the attacker must win exactly one miner slot during the window in which `stacks_signers` holds two `RegisteredSigner` instances (current cycle + next cycle in its prepare phase) sharing one `db_path`. The attacker needs no signer key, no majority weight, and no local access — only their own miner private key to sign two `BlockProposal` StackerDB chunks that differ solely in the `reward_cycle` field. This is a narrow but real and recurring window (every reward-cycle boundary), and the attack is trivially repeatable each time that window occurs.

### Recommendation
Make `reward_cycle` part of the identity of a tracked block rather than an unauthenticated, mutable attribute: store/lookup `BlockInfo` keyed by `(signer_signature_hash, reward_cycle)` rather than by hash alone with a post-hoc filter, and/or independently re-derive the block's reward cycle from its `consensus_hash`/sortition data inside `check_proposal` and reject any `BlockProposal` whose declared `reward_cycle` does not match the cycle actually implied by the block's tenure, instead of trusting the miner-supplied field for routing and lookup.

### Proof of Concept
Rust test in `stacks-signer/src/v0/tests.rs` (or an integration test alongside `stacks-node/src/tests/signer/v0/mod.rs`):
1. Spin up a `RunLoop`/two `RegisteredSigner` test doubles for adjacent cycles `N` and `N+1` sharing one `SignerDb` (as production does).
2. Build one `NakamotoBlock` with a valid header/signature; construct `BlockProposal { reward_cycle: N, .. }` and drive it through `handle_block_proposal` on the cycle-N signer; assert `signer_db.block_lookup(hash)` now shows `reward_cycle == N` and some non-terminal state (e.g. `PreCommitted`).
3. Construct a second `BlockProposal` with the identical `block` but `reward_cycle: N+1`; drive it through the cycle-(N+1) signer's `handle_block_proposal`.
4. Assert `block_lookup_by_reward_cycle` on the cycle-N signer instance now returns `None` for the same hash (i.e., `self.reward_cycle == N` finds nothing), and that `signer_db.block_lookup(hash).reward_cycle == N+1` (overwritten).
5. Assert that after any number of further alternating resubmissions, no single `reward_cycle` context's tracked `BlockInfo` for this hash ever reaches `BlockState::GloballyAccepted` or `GloballyRejected` — each toggle resets it to `Unprocessed`/re-validation.

    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }
