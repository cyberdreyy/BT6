## Title
Multisig executes a request using a stale confirmation from a removed member, bypassing the live-member confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges requests that were *created* by the member being removed; it never scrubs that member's confirmation from the `confirmations` set of *other* still-pending requests. Because `confirm()` simply counts `confirmations.len()` against `num_confirmations` without checking that every confirming entry is still a current member, a request can later be pushed over the confirmation threshold and executed using a mix of live confirmations plus one or more "ghost" confirmations from accounts that have since been removed from the multisig. The same pattern exists in the older `multisig/src/lib.rs` (`DeleteKey` action).

### Finding Description
The binding that should hold is: `confirmations counted toward num_confirmations == confirmations from currently live members`. This binding is broken.

`confirm()` only checks that the calling member hasn't already confirmed, then compares the *raw size* of the stored `confirmations` set against `num_confirmations`: [1](#0-0) 

`delete_member` removes access/membership and deletes only requests that were *added* (`r.member == member`) by the departing member; it does not scan or clean the `confirmations` `HashSet<String>` of any other outstanding request that the departing member may have already confirmed: [2](#0-1) 

So the sequence is:
1. Member `B` confirms request `R` (created by a different member `A`), adding `"B"` to `confirmations[R]`.
2. `B` is later removed via a separate, fully-confirmed `DeleteMember { member: B }` request. `delete_member` only inspects requests where `B` is the *creator*; `R` was created by `A`, so `R`'s confirmation set is left untouched and still contains `"B"`.
3. `members.len()` and `num_confirmations` are unchanged (or minimally reduced, still satisfying `members.len()-1 >= num_confirmations`), so the threshold check in `confirm()` doesn't know `B`'s prior confirmation is now stale.
4. A third live member `C` confirms `R`. `confirmations[R].len()` becomes 3 (`A`, `B`, `C`) which meets `num_confirmations = 3`, and `execute_request(R)` fires — even though only `A` and `C` are currently live members.

The equivalent structural flaw exists in the legacy contract's `DeleteKey` handling, which likewise filters by `r.signer_pk == pk` (creator) rather than scrubbing confirmation sets of unrelated requests: [3](#0-2) 

### Impact Explanation
This directly matches the Critical bucket: "a multisig request executed below threshold." A `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, or `DeployContract` action can be executed with fewer live-member confirmations than the contract's configured `num_confirmations`, because a stale confirmation from a removed member is still counted. This can move NEAR (or grant access/keys) with an effective threshold weaker than what the current member set intends, undermining the entire security guarantee of the multisig.

### Likelihood Explanation
This requires only normal contract usage: any member creates a request, other legitimate members confirm it (below threshold), a later (unrelated, self-request) `DeleteMember`/`DeleteKey` action removes one of those confirming members, and then a remaining live member supplies the "missing" confirmation. No foundation, redeploy, or external actor is needed — only ordinary sequencing of `add_request`, `confirm`, and `DeleteMember` actions that the multisig already supports, plus a pending request outliving a membership change (very plausible given `REQUEST_COOLDOWN` and no forced expiry tied to membership changes).

### Recommendation
When removing a member (`delete_member` / `DeleteKey`), iterate all outstanding requests' `confirmations` sets (not only requests it created) and remove that member's entry from every set, or alternatively validate at `confirm()`/execution time that every entry recorded in `confirmations[request_id]` is still present in `self.members` before counting it toward `num_confirmations`.

### Proof of Concept
Using `multisig2::MultiSigContract` with `members = [A, B, C, D]`, `num_confirmations = 3`:
1. `A.add_request(R)` → `request_id = 0`.
2. `A.confirm(0)` → `confirmations[0] = {A}`.
3. `B.confirm(0)` → `confirmations[0] = {A, B}` (2/3, not yet executed).
4. Separately submit and fully confirm (using `A`, `C`, `D`) a request containing `MultiSigRequestAction::DeleteMember { member: B }`. `delete_member` runs; since `R` (`request_id=0`) was created by `A`, not `B`, it is left in `requests`/`confirmations` untouched — `confirmations[0]` still contains `"B"`.
5. `members` is now `{A, C, D}`, `num_confirmations` still `3`.
6. `C.confirm(0)` → `confirmations[0].len() == 3 >= num_confirmations`, so `execute_request(R)` runs and the `Transfer` (or other action) in `R` executes, despite only `A` and `C` being live confirmers. [4](#0-3)  shows the missing cross-request confirmation cleanup, and [5](#0-4)  shows the threshold check that trusts the stale count.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
