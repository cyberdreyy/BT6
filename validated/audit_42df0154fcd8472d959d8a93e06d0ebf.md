### Title
Builder pending withdrawal and builder sweep withdrawal can double-commit Gwei from the same builder balance in `get_expected_withdrawals` - (File: specs/gloas/beacon-chain.md)

### Summary
`get_expected_withdrawals` in Gloas computes withdrawal amounts for a builder from two independent, uncoordinated sources within the same call: `get_builder_withdrawals` (processing `state.builder_pending_withdrawals`) and `get_builders_sweep_withdrawals` (processing eligible builders by `withdrawable_epoch`). Unlike the validator-sweep and pending-partial-withdrawal paths, which explicitly call `get_balance_after_withdrawals` to net out withdrawals already queued earlier in the same batch, the builder paths use the raw, un-netted `builder.balance` for both computations. This mirrors the reported LendingPool bug class: an amount is computed from a stale balance/snapshot before an intervening reduction is accounted for, and only gets "fixed up" later (via `min()`) at a point that is too late to prevent an inconsistency being committed.

### Finding Description
`get_builder_withdrawals` [1](#0-0)  emits a `Withdrawal` with `amount=withdrawal.amount` taken directly from `state.builder_pending_withdrawals`, with no clamp to the builder's current balance and no accounting for other withdrawals being built in the same call.

`get_builders_sweep_withdrawals` [2](#0-1)  independently emits a full-balance withdrawal with `amount=builder.balance` — again reading the balance directly from state, not netted against the pending withdrawal that `get_builder_withdrawals` already scheduled earlier in the very same `get_expected_withdrawals` call.

Contrast this with the validator/partial-withdrawal analogs in the same function, which correctly track cumulative effect within the batch: [3](#0-2) [4](#0-3) 

Both functions are invoked and their outputs concatenated into a single committed list in `get_expected_withdrawals`: [5](#0-4) 

That combined, uncorrected list is what becomes `state.payload_expected_withdrawals` — the commitment the execution layer is required to honor verbatim: [6](#0-5) 

Only afterward, in `apply_withdrawals`, is a `min(withdrawal.amount, builder_balance)` clamp applied — but that clamp only protects the *consensus-layer bookkeeping* (`state.builders[i].balance`) from underflowing; it does nothing to the `amount` field already baked into `payload_expected_withdrawals`, which is what the execution layer actually mints/credits to `Withdrawal.address`: [7](#0-6) 

The spec's own note on this exact class of hazard, written for the validator-decrease-balance saturation case, states the invariant plainly: *"the execution layer mints the full committed amount regardless, any CL-side saturation creates a net supply inflation."* [8](#0-7)  The same invariant is violated for builders: if a builder simultaneously has a queued `BuilderPendingWithdrawal` for amount `A` (destination `fee_recipient`) and is swept because `withdrawable_epoch <= epoch` (destination `execution_address`), the committed `payload_expected_withdrawals` will contain `A` to one address and the *pre-deduction* `balance` to another address — totaling `A + balance`, i.e. more Gwei than the builder ever had, paid to two distinct, non-equivalent addresses.

### Impact Explanation
This is a Critical-class issue under the stated rubric ("Gwei created ... or paid to a non-owner"): the execution layer would mint/credit `A + balance` Gwei to two different addresses from a builder that only ever held `balance` Gwei, producing a net supply inflation and diverting funds away from the builder's true entitlement into an extra payment to the `fee_recipient`/`execution_address` pair. Because `payload_expected_withdrawals` is a binding commitment the EL must honor exactly, this is not merely a wasted-gas inefficiency (as in the original LendingPool report) but an actual balance-conservation break if the scenario is reachable.

### Likelihood Explanation
Reachability depends on whether the protocol allows a builder to simultaneously (a) have a non-empty entry in `state.builder_pending_withdrawals` and (b) have `withdrawable_epoch <= current_epoch` with `balance > 0`, within the same block's `get_expected_withdrawals` call. I was not able to fully trace `initiate_builder_exit`, `settle_builder_payment`, and `get_pending_balance_to_withdraw_for_builder` (referenced but not fully retrieved in this session) to confirm whether an explicit guard exists preventing a builder from being both mid-exit-sweep-eligible and having a pending payment queued at the same time — this is analogous to how Electra's validator withdrawal-request path explicitly checks `pending_balance_to_withdraw == 0` before allowing a full exit [9](#0-8) . If an equivalent guard exists for builders, this finding is not reachable and should be discounted; if it does not, the double-count is directly reachable by ordinary protocol operation (a builder's payment settling from `apply_parent_execution_payload` combined with the builder's own natural exit sweep), requiring no coalition or client bug.

### Recommendation
Before computing `get_builders_sweep_withdrawals`, net the builder's balance against any withdrawal already produced for that builder earlier in the same `get_expected_withdrawals` call (i.e., the amounts from `get_builder_withdrawals`), analogous to how `get_balance_after_withdrawals` is used for validators. Concretely, `get_builders_sweep_withdrawals` should compute `amount = builder.balance - sum(pending amounts already withdrawn for this builder in `prior_withdrawals`)` rather than reading `builder.balance` directly, ensuring the total committed `payload_expected_withdrawals` for any single builder never exceeds that builder's actual balance.

### Proof of Concept
1. Builder `B` has `balance = 100` Gwei.
2. In the current block, `apply_parent_execution_payload` settles a builder payment, appending `BuilderPendingWithdrawal(builder_index=B, amount=90, fee_recipient=X)` to `state.builder_pending_withdrawals` [10](#0-9) .
3. Independently, `B.withdrawable_epoch <= current_epoch` (builder has exited/is sweep-eligible) and `B.balance == 100 > 0`.
4. `get_expected_withdrawals` runs: `get_builder_withdrawals` emits `Withdrawal(address=X, amount=90)`; later in the same call `get_builders_sweep_withdrawals` reads `state.builders[B].balance` — still `100` (unmodified by step 4's not-yet-applied withdrawal) — and emits `Withdrawal(address=B.execution_address, amount=100)`.
5. `payload_expected_withdrawals = [Withdrawal(X, 90), Withdrawal(exec_addr, 100)]`, total `190` Gwei committed for a builder that only had `100`.
6. `apply_withdrawals` only decrements CL's `state.builders[B].balance` by `min(90,100)=90` then `min(100,10)=10`, totaling `100` — consistent with CL bookkeeping — but the EL is committed to paying out `190` Gwei to `X` and `exec_addr` combined, per the binding `payload_expected_withdrawals` list, producing `90` Gwei of unbacked value paid to `X` beyond the builder's true balance. [11](#0-10)

##### New `get_builder_withdrawals`

```python
def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```

##### New `get_builders_sweep_withdrawals`

```python
def get_builders_sweep_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    epoch = get_current_epoch(state)
    builders_limit = min(len(state.builders), MAX_BUILDERS_PER_WITHDRAWALS_SWEEP)
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    builder_index = state.next_withdrawal_builder_index
    for _ in range(builders_limit):
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder = state.builders[builder_index]
        if builder.withdrawable_epoch <= epoch and builder.balance > 0:
            withdrawals.append(
                Withdrawal(
                    index=withdrawal_index,
                    validator_index=convert_builder_index_to_validator_index(builder_index),
                    address=builder.execution_address,
                    amount=builder.balance,
                )
            )
            withdrawal_index += 1

        builder_index = (builder_index + 1) % len(state.builders)
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
```

```markdown
*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
