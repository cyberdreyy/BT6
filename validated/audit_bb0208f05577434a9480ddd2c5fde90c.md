### Title
Anyone can set the vault APR (and unscaled APR) while `idleCDO` is unset — `setApr` skips its only authorization check when `idleCDO == address(0)` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.setApr` guards callers with `msg.sender != idleCDO && msg.sender != manager`, but deliberately skips the check entirely when `idleCDO` is still `address(0)` ("this can happen only during the setup"). Between `initialize` and `setWhitelistedCDO`, any unprivileged EOA can call `setApr`/`setAprs`/`setAprsWithBuffer` and set `lastApr`/`unscaledApr` to the `DEFAULT_MAX_APR` cap (20e18). This is the same bug class as the reference report: an authorization check that silently does not revert for arbitrary callers.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol` lines 225–235:

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`setAprs` (L206) and `setAprsWithBuffer` (L217) write `unscaledApr` and then delegate to `setApr`, so during the same window an attacker controls both `unscaledApr` and `lastApr`. `idleCDO` is only set later via `setWhitelistedCDO` (L954, `onlyOwner`), which is a separate transaction from `initialize` (L124–158), so there is a real (front-runnable) window where `idleCDO == 0`.

`lastApr`/`unscaledApr` feed every interest path:

- `startEpoch` computes `expectedEpochInterest = pendingWithdrawFees + _calcInterest(getContractValue())` where `_calcInterest` uses `_getStrategyApr()` = `lastApr` (`IdleCDOEpochVariant.sol` L260–262, L800–808). An inflated APR makes the expected interest far exceed what the honest borrower actually owes.
- At `stopEpoch`, the CDO tries `getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)` (L408). The honest borrower never approved/holds the inflated amount, the `transferFrom` reverts, and `_handleBorrowerDefault` fires (L504, L577–599): `defaulted = true`, deposits paused, withdraw requests disabled — a hard default of a non-defaulting borrower.
- `requestWithdraw` uses `_calcInterestWithdrawRequest` (L856–878), which also derives per-request interest from `_getStrategyApr()`. Withdraw-request receipts (`requestWithdraw` in the strategy, L243–295) mint receipt tokens for `principal + interest`, so an attacker holding tranche tokens can also inflate the interest embedded in their own pending receipt, which the borrower is then expected to fund.

### Impact Explanation
Two concrete impacts, both triggered by an honest owner/manager later calling `startEpoch`/`stopEpoch` in the normal sequence:

1. **Permanent freezing via forced default**: with `lastApr = 20e18` (the max cap), `expectedEpochInterest` is inflated by the difference between the attacker's APR and the real negotiated APR. The honest borrower's repayment `transferFrom` reverts, `_handleBorrowerDefault` sets `defaulted = true`, pauses the contract, and blocks all withdraw requests. All lender funds are frozen until a `finalizeDefault` flow, and claimants receive only `defaultRecoveryPrice` — a direct loss quantified as `(inflatedAPR − realAPR) × NAV × epochDuration/365 days` of unfunded liabilities plus recovery haircuts on all receipts.
2. **Theft of yield/principal via inflated withdraw receipts**: an attacker who deposits before the epoch, sets `unscaledApr`/`lastApr` high during the setup window, and calls `requestWithdraw` obtains a receipt minted for `principal + inflatedInterest`. If the borrower does fund the (partially) inflated amount, the attacker claims more underlyings than deposited — stealing from other LPs' share of the recovery/interest pool.

The only mitigating bound is `maxApr = DEFAULT_MAX_APR = 20e18`, which still permits a 20%-per-epoch inflation — far above real credit APRs.

### Likelihood Explanation
The exploit window is the gap between `initialize` and `setWhitelistedCDO` on a newly deployed (or re-initialized) `IdleCreditVault` proxy. Deployment scripts set these in separate transactions, so a front-runner or anyone monitoring the mempool can call `setAprsWithBuffer(20e18, 1, 0)` (any nonzero `_duration`/`_buffer` keeps the scaled value at cap). No privileged role, KYC status, or capital is required for the APR write itself; the attacker only needs tranche tokens (obtainable by a normal KYC'd deposit) for the theft variant, and needs nothing for the forced-default variant. Existing guards do not stop it: `maxApr` is a bound, not an authorization; `owner()`/`manager` checks are bypassed by design while `idleCDO == 0`.

### Recommendation
Do not skip the caller check based on `idleCDO == 0`. Instead require `msg.sender == owner() || msg.sender == manager` (or `idleCDO` once set) in `setApr`, e.g.:

```solidity
address _cdo = idleCDO;
if (msg.sender != owner() && msg.sender != manager && (_cdo == address(0) || msg.sender != _cdo)) {
    revert NotAllowed();
}
```

Alternatively, set `idleCDO` inside `initialize` (or atomically in the same deployment transaction) so the unguarded window never exists.

### Proof of Concept
Foundry-style fork PoC (run against a mainnet fork with a real underlying, e.g. USDC):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract SetAprUnauthorizedTest is Test {
    IdleCreditVault strategy;
    IdleCDOEpochVariant cdo; // deployed per repo deploy scripts
    IERC20Detailed underlyings;
    address attacker = makeAddr("attacker");
    address owner = makeAddr("owner");
    address manager = makeAddr("manager");
    address borrower = makeAddr("borrower");

    function test_AnyoneCanSetAprBeforeCdoIsSet() public {
        // 1. Deploy implementation + proxy; initialize as in production scripts
        strategy = /* deploy proxy, call initialize(token, owner, manager, borrower, "B", realApr) */;

        // idleCDO is still address(0) — setWhitelistedCDO not yet called
        assertEq(strategy.idleCDO(), address(0));

        // 2. Attacker front-runs setWhitelistedCDO and maxes the APR
        vm.prank(attacker);
        strategy.setAprsWithBuffer(20e18, 1, 0); // unscaledApr = 20e18, lastApr = 20e18
        assertEq(strategy.unscaledApr(), 20e18);
        assertEq(strategy.lastApr(), 20e18);

        // 3. Owner wires the CDO and starts the epoch as normal
        vm.prank(owner);
        strategy.setWhitelistedCDO(address(cdo));
        // ... LPs deposit, borrower draws ...
        vm.prank(manager);
        cdo.startEpoch();
        // expectedEpochInterest now assumes ~20%/epoch instead of realApr

        // 4. At epoch end, honest borrower cannot repay inflated amount ->
        //    getFundsFromBorrower reverts -> _handleBorrowerDefault()
        vm.warp(cdo.epochEndDate() + 1);
        vm.prank(manager);
        cdo.stopEpoch(0, 0);
        assertTrue(cdo.defaulted());       // forced default of solvent borrower
        assertTrue(cdo.paused());
        assertFalse(cdo.allowAAWithdrawRequest()); // withdraw requests frozen
    }
}
```

Note: the exact deploy wiring in the PoC depends on the repo's deployment scripts (`forge-scripts/`), which were not fully read within the available iterations; the core assertion — `setAprsWithBuffer` succeeding from an arbitrary address while `idleCDO == 0` — follows directly from the code at `IdleCreditVault.sol:225-235` and the fact that `idleCDO` is only assigned in `setWhitelistedCDO` (`IdleCreditVault.sol:954-957`), never in `initialize`.
