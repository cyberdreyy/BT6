### Title
Unprivileged view-role users can read the `OutgoingToken` webhook secret via `GET /v2/external_initiators` - ([File: core/web/presenters/external_initiators.go])

### Summary
The `ExternalInitiatorsController.Index` endpoint returns `presenters.ExternalInitiatorResource`, which embeds the live `OutgoingToken` secret generated for each external initiator. This route is only gated by generic authentication (any valid API token/session), not by an edit/admin role check, so any user with a minimal view-role API token can enumerate and read another external initiator's outbound webhook secret.

### Finding Description
`ExternalInitiator.OutgoingToken` and `OutgoingSecret` are randomly generated secrets created in `bridges.NewExternalInitiator` [1](#0-0)  and stored in the `external_initiators` table alongside `HashedSecret`/`Salt`. They are meant to be handed to the caller only once, at creation time, via `presenters.NewExternalInitiatorAuthentication` in the `Create` response [2](#0-1) .

However, `ExternalInitiatorsController.Index` builds its list response using `presenters.NewExternalInitiatorResource`, and that resource type unconditionally re-serializes `OutgoingToken` on every subsequent read of the collection: [3](#0-2) 

The route wiring only requires generic authentication, not an elevated role, unlike the sibling `Create`/`Destroy` routes which are wrapped with `auth.RequiresEditRole`: [4](#0-3) 

So any holder of a valid API token/session (including the minimal `view` role, which is only excluded from run/edit/admin-gated routes) can call `GET /v2/external_initiators` and receive every external initiator's `OutgoingToken` in the JSON:API response body. This is confirmed by the existing integration test, which explicitly asserts the leaked field is present in the Index response: [5](#0-4) 

No presenter redaction, role check, or ownership filter exists to stop this — the secret-confinement invariant (outbound secrets should never be re-exposed after creation, and only to the creator) is violated for any authenticated caller.

### Impact Explanation
`OutgoingToken`/`OutgoingSecret` are secrets intended to authenticate the node's outbound calls back to third-party External Adapter (EA)/webhook endpoints when jobs are created/deleted or triggered (per the documented external-initiator notification flow in the changelog and the `NewExternalInitiatorAuthentication` create-time response). A view-role token holder who reads this endpoint obtains the live secret and can impersonate the node's outbound calls to that EA service, or replay/forge callbacks that the EA is expecting to originate from the node. This is a credential-exposure / request-impersonation issue, matching Chainlink's "secret/credential disclosure" bounty impact class, scoped to the external-initiator webhook integration rather than key material or funds.

### Likelihood Explanation
Exploitation requires only a valid, low-privilege API token or session capable of passing the generic `auth.Authenticate` middleware — no edit/admin/run role is required since `GET /v2/external_initiators` has no `auth.Requires*Role` wrapper, unlike `Create`/`Destroy`. This makes the issue trivially and repeatably exploitable by any authenticated low-privilege caller with a single GET request, as demonstrated by the existing test asserting `OutgoingToken` is returned.

### Recommendation
Strip `OutgoingToken`/`OutgoingSecret`/`HashedSecret`/`Salt` from `presenters.ExternalInitiatorResource` (used by `Index`), keeping it limited to `Name`, `URL`, `AccessKey`, timestamps — mirroring how bridge/API-token list endpoints redact secrets after creation. Additionally, consider gating `GET /v2/external_initiators` with `auth.RequiresEditRole` (or higher) since it currently allows any authenticated principal, not just privileged operators, to enumerate external initiators.

### Proof of Concept
Go handler-level integration test plan (extends existing `TestExternalInitiatorsController_Index` in `core/web/external_initiators_controller_test.go`):
1. Create an application and insert an external initiator via `cltest.MustInsertExternalInitiatorWithOpts` with a known `OutgoingToken`/`OutgoingSecret`.
2. Using an HTTP client authenticated with a minimal `view`-role API token (not edit/admin), call `GET /v2/external_initiators`.
3. Parse the JSON:API response into `[]presenters.ExternalInitiatorResource`.
4. Assert the response contains `AccessKey`, `Name`, `URL` fields, but assert that `OutgoingToken` (and any `OutgoingSecret`/`HashedSecret`/`Salt` if added to the struct) is empty/absent — this assertion currently **fails** against the existing code, proving the leak (see current test lines asserting `externalInitiators[0].OutgoingToken == eiFoo.OutgoingToken`).
5. Expected fix outcome: the resource struct no longer carries `OutgoingToken`, so the field is always zero-value/omitted regardless of role.

type ExternalInitiatorResource struct {

	URL           *models.WebURL `json:"url"`
	AccessKey     string         `json:"accessKey"`
	OutgoingToken string         `json:"outgoingToken"`
	CreatedAt     time.Time      `json:"createdAt"`

func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,
		UpdatedAt:     ei.UpdatedAt,
	}
}
