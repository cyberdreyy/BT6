### Title
Post-default instant withdrawals reuse the cleared default-epoch receipt slot and drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` can still be called after `defaultRecoveryFinalized`. It writes the new request into `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, where `epochNumber` still equals `defaultRecoveryEpoch` (no `stopEpoch` ever runs post-default to bump it). On the next `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads that same per-epoch slot — which was zeroed ("freed") during finalization and is treated as exclusively owned by defaulted-epoch receipts — and pays the brand-new receipt out of `defaultRecoveryReserve` at `defaultRecoveryPrice`, decrementing `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch` for an epoch that is no longer supposed to accept new claims. This mirrors the CVE-2017-9789 pattern: a slot that was freed/reset is still referenced by the claim path.

### Finding Description
- `requestInstantWithdraw` (lines 356–375) has no `defaultRecoveryFinalized` guard, unlike `requestWithdraw` which routes post-default requests into `postDefaultRequests` (lines 247–257). It burns the CDO's strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`.
- After `finalizeDefaultRecovery`, `epochNumber` never advances (epoch increments only in `deposit` during `stopEpoch`, line 610), so `epochNumber == defaultRecoveryEpoch` permanently.
- `claimInstantWithdrawRequest` (lines 380–393) first calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — the slot just populated by the *new* request — clears it, subtracts it from `instantWithdrawsRequests` and `pendingInstantWithdraws`, and pays `claimBasis * defaultRecoveryPrice / 1e18` out of `defaultRecoveryReserve` via `_transferDefaultRecovery` (lines 842–856, 912–917).
- The recovery reserve was sized exactly for finalized claims (`reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, lines 685–693). Every post-default instant request creates an unaccounted claim that consumes this fixed reserve.
- Additionally, because `epochNumber` is frozen at `defaultRecoveryEpoch`, repeated post-default instant requests keep landing in the same "cleared" slot: each new request re-pollutes `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` after it was decremented, corrupting the accounting the same way a freed-memory region is re-used.

### Impact Explanation
The `defaultRecoveryReserve` is exhausted by post-default claims that were never part of `totalBasis`. Legitimate defaulted-epoch and post-default normal withdraw claimants (`_claimDefaultedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`) then revert in `_transferDefaultRecovery` on `defaultRecoveryReserve -= _amount` underflow — permanent freezing of their unclaimed recovery proceeds, i.e., direct insolvency of the recovery reserve. The attacker converts a post-default instant receipt (priced at par in `pendingInstantWithdraws`/`instantWithdrawsRequests` but paid from the haircut pool) into an immediate reserve draw, and each such draw reduces what honest claimants can collect. Loss is bounded by attacker-controlled tranche value but is quantifiable: every unit requested post-default removes `defaultRecoveryPrice` units of reserve from honest claimants.

### Likelihood Explanation
Requires only that the vault enters a finalized-default state and that instant withdraws remain callable through the CDO — no privileged misbehavior needed; any tranche holder can call `requestInstantWithdraw` via the IdleCDO. Whether the CDO-level entry point remains reachable post-default depends on `IdleCDOEpochVariant`/`IdleCDOCreditVault` request routing, which was not fully verified here; if the CDO blocks instant requests after default, the issue degrades to an accounting inconsistency rather than exploitable drain. The reserve accounting corruption (`instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` divergence) holds regardless.

### Recommendation
Mirror the `requestWithdraw` post-default handling: in `requestInstantWithdraw`, when `defaultRecoveryFinalized` is true, either revert or record the request under a dedicated post-default bucket (e.g., `postDefaultInstantRequests`) funded at par, never under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` while `epochNumber == defaultRecoveryEpoch`. Also gate `claimInstantWithdrawRequest`'s funded path so post-default instant receipts cannot be paid from `defaultRecoveryReserve`.

### Proof of Concept
Foundry fork sketch against an existing epoch vault deployment:

```solidity
// Assume: vault defaulted, manager called finalizeDefault via CDO,
// defaultRecoveryFinalized == true, defaultRecoveryEpoch == epochNumber().
address vault = address(strategy);
address alice = defaultedReceiptHolder;   // has defaulted-epoch claim
address attacker = trancheHolder;         // holds tranches post-default

// 1. Attacker requests an instant withdraw post-finalization via the CDO.
vm.prank(attacker);
cdo.requestInstantWithdraw(ATTACK_AMOUNT); // -> vault.requestInstantWithdraw
// instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] = ATTACK_AMOUNT
// pendingInstantWithdraws += ATTACK_AMOUNT

// 2. Attacker claims: routed through _claimDefaultedInstantWithdrawRequest.
vm.prank(attacker);
cdo.claimInstantWithdrawRequest();
// payout = ATTACK_AMOUNT * defaultRecoveryPrice / 1e18, paid from defaultRecoveryReserve

// 3. Reserve insolvency for honest claimants.
uint256 reserveBefore = IdleCreditVault(vault).defaultRecoveryReserve();
vm.prank(alice);
vm.expectRevert(); // underflow in _transferDefaultRecovery or NotAllowed
cdo.claimWithdrawRequest();
assertLt(IdleCreditVault(vault).defaultRecoveryReserve(), reserveBefore);
```

Key assertion: after step 1, `instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] != 0` even though that epoch's receipts were already cleared at finalization — the "freed" slot is re-populated and consumed by the default-claim path.

Uncertainty: I could not fully trace `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` routing post-default; if the CDO reverts these calls once `defaulted()`, the practical exploitability is limited to windows where the strategy-level calls remain reachable, but the slot-reuse accounting flaw is still present in `IdleCreditVault`.
