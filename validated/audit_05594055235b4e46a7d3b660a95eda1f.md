### Title
Unvalidated ERC4626 deposit permits first-depositor theft of programmable-borrower principal - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` deposits all idle pool principal into a configured ERC4626 vault but ignores the returned share amount. If the selected vault is empty or lacks inflation protection, an unprivileged vault user can execute a first-depositor share-inflation attack, cause the borrower contract to receive zero shares for its deposit, and redeem the donated shares for the pool’s principal.

### Finding Description
`initialize` only validates that `vault.asset()` matches the IdleCDO underlying and grants the vault unlimited allowance; it does not require an existing supply, minimum liquidity, or inflation-resistant share accounting. [1](#0-0)  `setVault` repeats the same asset check and also permits switching to a previously unused vault. [2](#0-1) 

During `onStartEpoch`, the contract snapshots `startAssets`, deposits its entire underlying balance, and records that pre-deposit amount as the epoch principal baseline. [3](#0-2)  `_depositToVault` calls `vault.deposit(_assetAmount, address(this))` but neither checks that shares were minted nor compares the returned shares with `previewDeposit`. [4](#0-3) 

An attacker can therefore front-run the first borrower deposit into an empty inflation-vulnerable vault:

1. Deposit `1` wei and receive the only vault share.
2. Donate at least the borrower deposit amount `P` directly to the vault, making one share worth more than `P`.
3. Let `onStartEpoch` deposit `P`; the vault mints `P * 1 / (P + donation + 1) == 0` shares to `ProgrammableBorrower`.
4. Redeem the sole share for the donation plus `P`.

The accounting then records a vault loss because `earnedAssets` is zero while `principalAssets` still contains the pre-deposit `P`. [5](#0-4)  However, `totalInterestDueNow` floors this result at zero, so a normal `stopEpoch` can succeed while crystallizing no interest and no principal loss. [6](#0-5)  On a later close, the hook can return success when the required principal exceeds the contract’s zero-valued vault position, leaving the subsequent CDO `transferFrom` to fail and force a hard default. [7](#0-6) 

### Impact Explanation
The attacker steals the borrower contract’s entire first vault deposit, up to the full epoch principal sent by `IdleCDOEpochVariant`. For example, with `P = 10_000e6` USDC, the attacker spends `1` wei plus a `10_000e6` donation and redeems approximately `20_000e6`, for a net gain of approximately `10_000e6`. The credit pool retains strategy-token NAV despite losing the underlying principal, creating hidden insolvency that is only forced into default when principal or pending withdrawals are pulled.

### Likelihood Explanation
Exploitation requires the configured ERC4626 vault to have an empty or manipulable initial share price and to permit a zero-share deposit. This is not exploitable against a mature, inflation-resistant vault with virtual shares or substantial existing supply. Nevertheless, the contract accepts any asset-compatible ERC4626, imposes no minimum liquidity or returned-share invariant, and the required attacker is only an unprivileged user of that vault. [8](#0-7) 

### Recommendation
- Reject vaults with zero or below-minimum `totalSupply`/`totalAssets` in `initialize` and `setVault`.
- In `_depositToVault`, require `shares != 0` and `shares >= vault.previewDeposit(_assetAmount)`; additionally verify `vault.convertToAssets(shares)` is within an explicit rounding tolerance of `_assetAmount`.
- Prefer vaults with virtual-share inflation protection or an established minimum-liquidity reserve.
- Treat an anomalous share shortfall as an epoch-start failure rather than recording the full deposit as epoch principal.

### Proof of Concept
The following regression can be added beside `ProgrammableBorrowerIdleCashRegressionTest` in `test/foundry/ProgrammableBorrowerAccountingInvariant.t.sol` and run on a mainnet fork. Its `MockInvariantVault` models an ERC4626 without inflation protection; the vulnerability is the production adapter’s failure to validate the deposit result.

```solidity
function testFirstDepositorStealsProgrammableBorrowerPrincipal() external {
    uint256 principal = 10_000e18;
    address attacker = makeAddr("erc4626FirstDepositor");

    // Simulate CDO principal already transferred to the programmable borrower.
    underlying.mint(address(borrowerContract), principal);

    // Attacker owns the only share and inflates its price above `principal`.
    underlying.mint(attacker, principal + 1);
    vm.startPrank(attacker);
    underlying.approve(address(vault), 1);
    vault.deposit(1, attacker);
    underlying.transfer(address(vault), principal);
    vm.stopPrank();

    // Honest manager/IdleCDO starts the epoch; borrower receives zero shares.
    vm.prank(idleCDO);
    borrowerContract.onStartEpoch(0);

    assertEq(vault.balanceOf(address(borrowerContract)), 0);
    assertEq(borrowerContract.totalInterestDueNow(), 0);

    // Attacker redeems the sole share for donation + stolen principal.
    vm.prank(attacker);
    vault.redeem(1, attacker, attacker);

    assertEq(underlying.balanceOf(attacker), principal + principal + 1);
}
```
