### Title
HTTP Action response cache is keyed only by `(method, URL, headers, body, workflowOwner)`, not `WorkflowID`, causing cross-workflow response confusion for the same owner - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's HTTP Action response cache is documented as being isolated per workflow ("Cache Key: Generated from workflow ID and request hash" / "Workflow Isolation: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage"), but the actual `Hash()` key used to store/retrieve entries deliberately ignores `WorkflowID` and is scoped only by `workflowOwner` plus the raw HTTP request shape. Any workflow belonging to the same owner that issues a structurally identical outbound HTTP action (same method/URL/headers/body) will be served the cached response that was originally fetched and stored by a *different* workflow, mirroring the report's root-cause pattern: shared mutable state keyed too coarsely lets one execution context clobber/consume the state of another without any authorization check tying the state to the specific requester.

### Finding Description
`responseCache` stores entries in a single map keyed by `req.Hash()`: [1](#0-0) 

The `Fetch` and `Set` methods both use this hash as the sole cache key and never take `WorkflowID` into account when reading or writing: [2](#0-1) [3](#0-2) 

The handler-level `README.md` explicitly claims stronger isolation than what is implemented: [4](#0-3) 

The test suite confirms the actual (weaker) behavior and documents it as intentional: [5](#0-4) [6](#0-5) 

This is invoked from the outbound HTTP action path in `gatewayHandler.makeOutgoingRequest`, which passes the full `OutboundHTTPRequest` (containing `WorkflowID`) into `Fetch`/`Set`, but since `Hash()` strips `WorkflowID`, the cache treats requests from different workflows (same owner) as identical: [7](#0-6) 

### Impact Explanation
This is analogous to the `lockOnBehalf` root cause: a piece of caller-supplied state (`WorkflowID`) that the system *should* use to scope an operation to the correct principal/resource is silently ignored, allowing one execution context to affect or read state belonging to another. Here, an unprivileged workflow (any workflow deployed under the same owner account, which itself could be a multi-tenant/shared owner setup, or two different applications sharing a wallet address as `workflowOwner`) can:
- Receive stale or attacker-influenced HTTP responses cached by a different, unrelated workflow (cross-workflow response confusion), potentially leaking data intended only for the other workflow's consumers if response bodies differ based on context not captured by `Hash()` (e.g., time-sensitive or session-based upstream responses).
- Poison the cache for another workflow by triggering a request with `Store: true` before the legitimate workflow runs, so the legitimate workflow silently consumes attacker-influenced cached data instead of making its own live HTTP call.

Because the cache key omits `CacheSettings` too, differing TTL/store intents from different workflows are also conflated. Severity is bounded by the fact that `workflowOwner` is still part of the key, so isolation across different owners holds — the confusion is limited to workflows sharing the same owner value.

### Likelihood Explanation
Likelihood is moderate: it requires two workflows under the same `workflowOwner` to issue outbound HTTP actions with identical method/URL/headers/body (a realistic and even common scenario for workflows hitting the same third-party API from the same account), and for at least one to set `CacheSettings.Store=true` with a `MaxAgeMs` window during which another workflow reads with a compatible `MaxAgeMs`. No special privilege is needed beyond being any workflow owned by that same address — this is reachable purely from the CRE workflow layer talking to the internet-facing gateway, with no gateway-side authentication bypass required.

### Recommendation
Include `WorkflowID` (and ideally the `CacheSettings` fields that determine cache semantics) directly in the cache key computed by `Hash()`, rather than relying only on `workflowOwner` plus request shape, so that the documented "Workflow Isolation... scoped by workflow ID" guarantee in the README actually matches the implementation. Add a regression test asserting different `WorkflowID` values under the same owner produce different cache keys (the inverse of the existing `TestRequestHash` subtest at lines 139-149).

### Proof of Concept
Given the existing test `TestRequestHash` (`response_cache_test.go:139-149`), the following demonstrates the bug directly against implemented code:
```go
req1 := createTestRequest("GET", "https://example.com")
req1.WorkflowOwner = "0xowner"
req1.WorkflowID = "workflow-A" // Workflow A, owned by 0xowner

req2 := createTestRequest("GET", "https://example.com")
req2.WorkflowOwner = "0xowner"
req2.WorkflowID = "workflow-B" // unrelated Workflow B, same owner

require.Equal(t, req1.Hash(), req2.Hash()) // passes today — cross-workflow collision
```
Consequently, if Workflow A executes with `CacheSettings.Store=true` and gets a cached 200 response, Workflow B (a completely different workflow, potentially untrusted relative to A) issuing the same request shape within the TTL window will receive Workflow A's cached response via `responseCache.Fetch`, as shown by the caching flow in `http_handler.go:403-441` and `response_cache.go:66-108`.

func (rc *responseCache) Fetch(ctx context.Context, req gateway.OutboundHTTPRequest, fetchFn func() gateway.OutboundHTTPResponse, storeOnFetch bool) gateway.OutboundHTTPResponse {
	cacheKey := req.Hash()
	cacheMaxAge := time.Duration(req.CacheSettings.MaxAgeMs) * time.Millisecond

	// Fast path: check cache without singleflight overhead.
	rc.cacheMu.RLock()
	cachedResp, exists := rc.cache[cacheKey]
	rc.cacheMu.RUnlock()
	if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
		rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
		return cachedResp.response
	}

	// Slow path: singleflight deduplicates concurrent fetches per key.
	// Cache check + store happen inside the flight so the key isn't released
	// until the result is cached, closing the race window between singleflight
	// completion and cache write.
	result, _, _ := rc.flight.Do(cacheKey, func() (any, error) {
		// Re-check cache: a previous flight may have just stored the result.
		rc.cacheMu.RLock()
		cachedResp, exists := rc.cache[cacheKey]
		rc.cacheMu.RUnlock()
		if exists && cachedResp.storedAt.Add(cacheMaxAge).After(time.Now()) {
			rc.metrics.IncrementCacheHitCount(ctx, rc.lggr)
			return cachedResp.response, nil
		}

		response := fetchFn()

		if storeOnFetch && isCacheableStatusCode(response.StatusCode) {
			rc.cacheMu.Lock()
			rc.cache[cacheKey] = &cachedResponse{
				response: response,
				storedAt: time.Now(),
			}
			rc.cacheMu.Unlock()
		}

		return response, nil
	})

	return result.(gateway.OutboundHTTPResponse)
}

// Set caches a response if it is cacheable (2xx or 4xx and cache is empty or expired for the given request)
func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (h *gatewayHandler) makeOutgoingRequest(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	requestID := resp.ID
	h.lggr.Debugw("handling outgoing message", "requestID", requestID, "nodeAddr", nodeAddr)
	var req gateway_common.OutboundHTTPRequest
	err := json.Unmarshal(*resp.Result, &req)
	if err != nil {
		return fmt.Errorf("failed to unmarshal HTTP request from node %s: %w", nodeAddr, err)
	}
	timeout := time.Duration(req.TimeoutMs) * time.Millisecond
	httpReq := network.HTTPRequest{
		Method:           req.Method,
		URL:              req.URL,
		Headers:          req.Headers, //nolint:staticcheck // forward deprecated Headers for backward compatibility; request uses MultiHeaders when set
		MultiHeaders:     req.MultiHeaders,
		Body:             req.Body,
		MaxResponseBytes: req.MaxResponseBytes,
		Timeout:          timeout,
	}

	sendResponseTimeout := time.Duration(defaultSendResponseTimeoutMs) * time.Millisecond

	// send response to node async
	h.wg.Go(func() {
		// not cancelled when parent is cancelled to ensure the goroutine can finish
		baseCtx := context.WithoutCancel(ctx)
		httpCtx, httpCancel := context.WithTimeout(baseCtx, timeout)
		defer httpCancel()
		l := logger.With(h.lggr, "requestID", requestID, "method", req.Method, "timeout", req.TimeoutMs)
		var outboundResp gateway_common.OutboundHTTPResponse
		callback := h.createHTTPRequestCallback(httpCtx, requestID, httpReq, req)
		if req.CacheSettings.MaxAgeMs > 0 {
			h.metrics.IncrementCacheReadCount(ctx, h.lggr)
			outboundResp = h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)
		} else {
			outboundResp = callback()
			if req.CacheSettings.Store {
				h.responseCache.Set(req, outboundResp)
			}
		}
