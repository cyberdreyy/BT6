### Title
`/debug/vars` accessible to any authenticated view-role user with no role gate, exposing process runtime internals via `expvar.Handler` - (File: core/web/router.go)

### Summary
The `debugRoutes` function registers `GET /debug/vars` behind only `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`, with no `auth.RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` wrapper, unlike nearly every other sensitive endpoint in `v2Routes`. Any successfully authenticated session, including the lowest-privilege `view` role, can therefore call `GET /debug/vars` and receive whatever variables are registered in Go's standard `expvar` package (built-in `cmdline` and `memstats`, plus any others self-registered by imported dependencies process-wide via `expvar.Publish`), potentially leaking runtime/memory information and command-line arguments of the chainlink node process.

### Finding Description
`debugRoutes` in `core/web/router.go` is defined as:
```go
func debugRoutes(app chainlink.Application, r *gin.RouterGroup) {
	group := r.Group("/debug", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	group.GET("/vars", expvar.Handler())
}
``` [1](#0-0) 

Compared to `v2Routes`, where nearly every mutating/sensitive read handler is wrapped in `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole` (e.g. `authv2.GET("/users", auth.RequiresAdminRole(uc.Index))`), `debug/vars` has no such role check [2](#0-1) . `auth.Authenticate` with `AuthenticateBySession` only verifies that a valid session cookie maps to *any* authenticated user regardless of role, and sets `SessionUserKey` in the gin context without checking `user.Role` [3](#0-2) [4](#0-3) . The role gate functions `RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole` explicitly check `user.Role` and reject `view`-role users for anything beyond `RunRole` [5](#0-4) , but none of these wrappers are applied to the `/debug/vars` route, so a `view`-role authenticated user passes straight through to `expvar.Handler()`.

`expvar.Handler()` is the standard library handler (via `github.com/gin-contrib/expvar`) that dumps the full JSON of all registered `expvar.Var`s in the process, which always includes `cmdline` (process command-line arguments) and `memstats` (Go runtime memory statistics), and additionally any vars registered by other imported packages process-wide through `expvar.Publish`. A search of the repo found no explicit `expvar.Publish`/`NewMap`/`NewString`/`NewInt` calls in application code, meaning the exposure is currently limited to the Go-standard `cmdline` and `memstats` vars plus whatever third-party dependencies self-register (not verifiable from this index alone).

### Impact Explanation
This is an authorization-exactness bug: an endpoint intended to require at least a privileged role level (as is the pattern for nearly all other operational/debug data in this router) instead allows the lowest-privilege `view` role — and indeed any authenticated user via cookie-session — to retrieve internal runtime/process data (`cmdline`, `memstats`, and potentially other registered vars). This matches an information disclosure / broken access-control impact class: a low-privileged credential holder can read internal operational data (process command line arguments, memory internals) that should be restricted to a higher trust tier, consistent with the "authorization bypass" and "sensitive data exposure" bounty categories. It does not directly lead to fund movement or key disclosure, so the severity is best characterized as a low/medium information-disclosure/access-control issue rather than a critical one, since (in this codebase) no secrets or private keys are shown to be registered via `expvar`.

### Likelihood Explanation
Exploitation only requires a valid session cookie for a user with the `view` role (the lowest privilege tier in the system) or any other authenticated role — there is no role check at all on this route. This is trivially and repeatably reachable: any node operator who creates a `view`-role account for a third party (e.g., a monitoring dashboard user) unintentionally grants that user access to `/debug/vars`. No special conditions, race conditions, or elevated permissions are needed beyond basic session authentication.

### Recommendation
Wrap the `/debug/vars` route with an explicit role gate consistent with other debug/operational endpoints, e.g. `auth.RequiresAdminRole(...)` (or at minimum `auth.RequiresEditRole`), so that only sufficiently privileged users can access process/runtime internals:
```go
func debugRoutes(app chainlink.Application, r *gin.RouterGroup) {
	group := r.Group("/debug", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	group.GET("/vars", auth.RequiresAdminRole(func(c *gin.Context) { expvar.Handler().ServeHTTP(c.Writer, c.Request) }))
}
```

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, following existing patterns such as `TestUsersController` for setting up sessions with roles):
1. Set up a test app via `cltest.NewApplicationEVMDisabled`/`setupUserWebAuthenticationTestClient` and create a session/user with `clsessions.UserRoleView` (or use existing helper for constructing a "view" role authenticated `httptest` client).
2. Issue `GET /debug/vars` using the view-role authenticated client (session cookie set, no admin/edit/run role).
3. Assert response status is `200 OK` (not `401`/`403`), proving no role gate is enforced.
4. Assert the JSON response body contains keys `"cmdline"` and `"memstats"` (or other registered vars), proving internal process/runtime data is exposed to the low-privilege session.
5. As a control, verify that other endpoints intended for `view` users only (e.g. `/v2/users` — admin-only) correctly return `401`/`403` for the same view-role session, to contrast expected behavior with the unguarded `/debug/vars` route.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
```

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
