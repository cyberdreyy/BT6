### Title
Fee-on-transfer underlying breaks share minting: `IdleCreditVault.deposit` mints strategy tokens for the full requested amount while receiving less - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a protocol that accounts for the full requested token amount while a fee-on-transfer token (e.g. STA, PAXG) delivers less, so users are credited more (or paid less) than the real balance moved. The same defect exists in the credit vault strategy: `IdleCreditVault.deposit` pulls `_amount` underlying from the CDO and mints `_amount` strategy tokens 1:1 without measuring the actual received balance. The IdleCDO side then double-counts the fee: `IdleCDO._deposit` correctly mints tranche shares on the received delta, but immediately forwards the nominal `_amount` to the strategy, paying the second transfer fee out of pre-existing NAV.

### Finding Description
In `IdleCreditVault.deposit` (contracts/strategies/idle/IdleCreditVault.sol:596-617):

```solidity
if (_amount > 0) {
  underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
  _mint(msg.sender, _amount);
}
```

Strategy tokens are the vault's unit of account (1:1 with underlying, see `burnStrategyTokens`/`sendInterestAndDeposits` at lines 581-592). If `token` charges a fee on transfer, the vault receives `_amount - fee` but mints `_amount` shares to the CDO. `getContractValue`/`_updateAccounting` in `IdleCDOCreditVault` (contracts/IdleCDOCreditVault.sol:222-236) then treat the CDO as owning `_amount` underlying of strategy position, inflating NAV and tranche prices above real assets. The shortfall is only discovered at redemption, when `_liquidate`/`redeemUnderlying` cannot return the accounted amount and the last withdrawers are left unpaid — a solvency/fair-mint break.

The same nominal-amount assumption appears in `IdleCDO._deposit` (contracts/IdleCDO.sol:249-258): shares are minted on `_contractTokenBalance(_token) - _preBal` (correct), but `IIdleCDOStrategy(strategy).deposit(_amount)` pulls the full `_amount` from the CDO, so the second transfer fee is silently taken from existing depositors' unlent balance. Similarly `_withdraw` (lines 493-506) decrements NAV by `toRedeem` but the user receives `toRedeem - fee`, mirroring the reported "user gets less than supposed" impact.

### Impact Explanation
Every deposit through the epoch vault with a fee-on-transfer underlying mints more strategy tokens than assets received, permanently inflating `lastNAVAA`/`lastNAVBB`. Loss is socialized onto all tranche holders: early redeemers are paid in full while the deficit concentrates on the last withdrawers, whose claims become unbacked (permanent loss / frozen funds equal to the cumulative unpaid fees). In `IdleCDO._deposit` the depositor is minted shares only for the net amount while the strategy pulls the gross amount, so each deposit silently taxes the vault NAV.

### Likelihood Explanation
Requires the vault's `token` to be a fee-on-transfer or rebasing-on-transfer ERC20. `token` is fixed at initialization, so this is conditional on deploying a tranche/credit vault over such an asset (the same precondition as the original Blueberry finding, rated Medium). No privileged action is needed; any KYC-passing lender depositing through the normal `depositAA`/`depositBB` → strategy `deposit` path triggers the over-mint, and the rules only require an unprivileged actor.

### Recommendation
Measure actual received amounts everywhere underlying crosses a boundary:
- In `IdleCreditVault.deposit`, record `balBefore`/`balAfter` and `_mint(msg.sender, received)`; propagate `received` to `totEpochDeposits`.
- In `IdleCDO._deposit`, call `strategy.deposit(received)` (the same delta used for minting) instead of `_amount`.
- In `_withdraw`, either deduct the fee from `toRedeem` before `_withdrawOps` or document/enforce that only non-fee tokens are supported.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// test/FeeOnTransferDeposit.t.sol
contract FeeToken is ERC20 {
    uint256 public feeBps = 100; // 1%
    function _transfer(address f, address t, uint256 a) internal override {
        super._transfer(f, t, a * (10000 - feeBps) / 10000);
        super._transfer(f, address(0xdead), a * feeBps / 10000);
    }
}

function testDepositOverMints() public {
    // deploy IdleCDOEpochVariant + IdleCreditVault with token = FeeToken
    uint256 amount = 1_000e6;
    feeToken.mint(lender, amount);
    vm.prank(lender); feeToken.approve(address(cdo), amount);
    vm.prank(lender); cdo.depositAA(amount);

    // CDO minted tranche shares for 990e6 (delta) but
    // vault minted strategy tokens for the full 1_000e6 it pulled
    assertEq(vault.balanceOf(address(cdo)), 1_000e6);      // shares
    assertEq(feeToken.balanceOf(address(vault)), 990e6);   // backing
    // NAV overstates assets by 10e6; a second depositor redeeming
    // the full share balance cannot be paid -> insolvency
}
```

The invariant violated is one-receipt-one-payout/fair-mint: strategy token supply exceeds underlying held, so `getContractValue()` > recoverable assets and final withdrawers are unpayable.
