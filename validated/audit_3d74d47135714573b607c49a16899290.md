### Title
Signer weight double-counted in both `total_weight_approved` and `total_weight_rejected` when a signer switches its vote from Rejected to Accepted - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::run` tallies per-signer vote weight into two independent counters, `total_weight_approved` and `total_weight_rejected`, using two different "already counted" guards (`gathered_signatures` for accepts, `responded_signers` for rejects, but `responded_signers` is shared and populated by *both* paths). If a signer first sends a `Rejected` response and later sends an `Accepted` response for the same block (a legitimate, protocol-permitted re-evaluation — the v0 signer's own `BlockState` diagram explicitly allows `LocallyRejected --> LocallyAccepted: re-evaluated`), the node adds that signer's weight to `total_weight_approved` without ever subtracting it from the earlier-recorded `total_weight_rejected`. The signer's weight is now counted in both buckets simultaneously, exactly mirroring the H-21 pattern where a value (`tokenTaken`) is adjusted post-hoc without updating the baseline/checkpoint the aggregate calculation depends on.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- The `Accepted` branch guards the weight increment with `gathered_signatures`: [1](#0-0) 

- The `Rejected` branch guards the weight increment with `responded_signers`, a set that the `Accepted` branch also inserts into (line 465) but never checks against before adding weight: [2](#0-1) 

Because these are two separate sets guarding two separate counters:
1. Signer S sends `Rejected` first → `responded_signers.insert(S) == true` → `total_weight_rejected += S.weight`. `gathered_signatures` is untouched.
2. Signer S later sends `Accepted` for the *same* block hash (permitted — the signer-side state machine allows a rejected block to be re-evaluated and locally accepted) → the guard checked is `!block.gathered_signatures.contains_key(&slot_id)`, which is `true` (S was never in `gathered_signatures`) → `total_weight_approved += S.weight` is added on top of the still-present `total_weight_rejected` contribution from step 1. Nothing decrements `total_weight_rejected`.

The result: `total_weight_approved + total_weight_rejected` can exceed the signer's true single weight contribution and even exceed `self.total_weight`, breaking the invariant that each signer's weight should count toward exactly one side of the aggregated tally at any time — the "aggregated-weight vs verified-accepts" equality the rules call out.

(Note: the reverse direction, Accepted-then-Rejected, is correctly guarded — `responded_signers.insert(slot_id)` returns `false` on the second call so `total_weight_rejected` is not incremented — but the guard asymmetry means only one direction is safe.)

### Impact Explanation
This is consumed by `SignerCoordinator::get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs`, which checks rejection-crosses-blocking-minority *before* checking acceptance-reaches-threshold: [3](#0-2) 

Because the check order is reject-first, a stale/duplicated rejection weight retained from a signer that has since switched to accepting can push `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` to true even though the signer's *current* vote is acceptance and the true weighted rejection is lower than recorded. This causes the miner's coordinator to declare `NakamotoNodeError::SignersRejected` for a block that in reality has (or could reach) sufficient acceptance weight — a liveness fault where a validly-progressing block is wrongly discarded/retried because of miscounted aggregate weight, not because of any genuine rejecting majority. This is a "miscounted response" breaking the aggregated-weight vs verified-accepts equality, triggerable unilaterally by a single signer flipping its own vote (no majority collusion required), which is within the rules' scope of analog-triggerable issues.

### Likelihood Explanation
The trigger requires only one signer (byzantine, buggy, or legitimately re-evaluating per the documented `LocallyRejected --> LocallyAccepted` transition) to broadcast a `Rejected` `BlockResponse` followed later by an `Accepted` `BlockResponse` for the same `signer_signature_hash` — both are normal StackerDB messages any registered signer can emit, and the signer-side code base itself documents scenarios where a block moves from rejected back to accepted (see `docs/signer-flows.md` §2 state diagram, and `stacks-signer/src/v0/signer.rs::should_reevaluate_reject_reason`/`should_reevaluate_block`). No majority or privileged access is needed to produce the double-count on the node's coordinator side.

### Recommendation
Use a single per-signer "current vote" map (accept/reject) instead of two independently-guarded counters, and when a signer's vote changes, subtract its weight from the previous bucket before adding it to the new one (i.e., recompute both totals from the current vote map rather than incrementally accumulating without reversal) — analogous to the source report's fix of re-checkpointing state on every adjustment rather than assuming the prior baseline still holds.

### Proof of Concept
1. Node's `StackerDBListener` tracks a block `B` in `self.blocks`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B` → `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
3. Signer `S` later sends `BlockResponse::Accepted` for the same `B` (e.g., after a conflict it was blocked on goes stale, per the v0 signer's own re-evaluation logic) → `gathered_signatures.contains_key(S)` is false → `total_weight_approved += w` is added, while `total_weight_rejected` still includes `w` from step 2.
4. Now `total_weight_approved + total_weight_rejected` double-counts `w`, and `SignerCoordinator::get_block_status`'s rejection check (evaluated before the acceptance check) can trip on the stale `total_weight_rejected`, causing `NakamotoNodeError::SignersRejected` to be returned for a block that should otherwise be accepted.
