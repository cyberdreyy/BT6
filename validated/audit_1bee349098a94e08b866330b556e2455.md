### Title
Junior (BB) holders front-run `stopEpochWithDuration` loss by converting to pending withdraw receipts, escaping the BB-first waterfall - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the gauge-weight front-run, `stopEpochWithDuration(_newApr, _interest, _duration, _lossAmount)` in `IdleCDOEpochVariant` applies a manager-supplied loss that is split *pro-rata* between active LPs and the pending withdraw-receipt bucket. Any tranche holder can monitor the mempool, call `requestWithdraw` (via the CDO) right before the loss-applying stop, and be reclassified from "active" (exposed to the BB-first waterfall) into the pro-rata "pending receipts" bucket, diluting honest pending claimants and dodging the junior-first loss ordering.

### Finding Description
`IdleCDOEpochVariant._stopEpoch` accepts a `_lossAmount` and, when non-zero, burns strategy tokens and runs `_forceUpdateAccounting()` so the active-side remainder follows the ordinary BB-first waterfall (`contracts/IdleCDOEpochVariant.sol`, `_stopEpoch` / `stopEpochWithDuration`). The split between pending receipts and active positions is computed by `IdleCreditVault.previewLossAdjustedWithdrawFunds`:

```solidity
uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
pendingToFund = pendingBasis - pendingLoss;
activeLoss = _lossAmount - pendingLoss;
``` [1](#0-0) 

`requestWithdraw` burns the user's principal and mints a receipt counted in `pendingWithdraws` / `withdrawsRequestsByEpoch`, with no check that a loss is imminent and no tranche identity retained:

```solidity
_burn(msg.sender, _principal);
_mint(_user, _amount);
pendingWithdraws += _amount;
``` [2](#0-1) 

Loss-adjusted receipts are later paid via `lossRecoveryPriceByEpoch[epoch]` set in `collectWithdrawFunds` when the borrower funds less than `pendingWithdraws`. Because a BB holder's receipt enters the aggregate pending bucket, their loss becomes the flat pro-rata `lossRecoveryPrice` instead of the BB-first waterfall (where BB NAV is wiped before AA loses anything).

### Impact Explanation
The loss-waterfall invariant is broken: BB capital is contractually supposed to absorb losses before AA, and pending withdraw receipts are only supposed to bear their pro-rata share. A BB holder who front-runs a `stopEpochWithDuration(..., _lossAmount)` call:

- converts an active junior position (which would absorb up to 100% of `activeLoss` before AA is touched) into a pending receipt that only loses `lossRecoveryPrice` pro-rata;
- inflates `pendingBasis`, which *increases* `pendingLoss`, shifting loss onto pre-existing honest withdraw requesters and off the remaining BB bucket;
- directly steals value from other LPs equal to the difference between their waterfall share (~100% of their pro-rata-scaled active loss) and the flat pending receipt haircut.

This is direct fund impact with a quantified loss borne by other participants, not a DoS.

### Likelihood Explanation
`stopEpochWithDuration` is a public owner/manager call whose `_lossAmount` argument is visible in the mempool. Withdraw requests are permissionless for KYC'd lenders and are accepted while the epoch is running (requests wait one epoch to claim; `lastWithdrawRequest`/`epochNumber` gating only affects claiming, not requesting). The only relevant guard — forcing a user to claim a previously loss-adjusted receipt before re-requesting — does not prevent the initial repositioning. No deposit/withdraw freeze exists during a running epoch, so a single front-run transaction suffices whenever management signals a loss realization.

### Recommendation
Apply tranche-aware accounting to the pending bucket, or prevent loss-dodging repositioning:

- Record receipt provenance (AA vs BB) in `withdrawsRequestsByEpoch`, or apply the BB-first waterfall to pending receipts too (e.g., attribute pending loss pro-rata but order pending AA receipts behind BB).
- Alternatively, disallow `requestWithdraw` in the same block/epoch as a loss-applying `stopEpochWithDuration`, or compute `pendingBasis`/`activeBasis` from a snapshot taken before the stop transaction rather than live balances.
- Prefer increase/decrease-of-exposure semantics: settle losses against the composition recorded at epoch start, not the mutable end-of-epoch one.

### Proof of Concept
Foundry-style test against a live `IdleCDOEpochVariant` + `IdleCreditVault` deployment (fork mainnet, use an existing credit vault):

```solidity
function testBBHolderFrontrunsLossStop() public {
    // Setup: running epoch. alice holds BB tranche, bob has a pending withdraw request.
    uint256 bbBefore = cdotoken_BB.balanceOf(alice);
    uint256 loss = 1_000_000e6; // manager's _lossAmount

    // --- Honest path (no front-run) ---
    uint256 snapshot = vm.snapshot();
    vm.prank(manager);
    cdo.stopEpochWithDuration(newApr, 0, duration, loss);
    // AA unaffected, BB eats the whole activeLoss via _forceUpdateAccounting
    uint256 aaNavHonest = cdo.virtualPrice(AAtranche);
    vm.revertTo(snapshot);

    // --- Attack path ---
    // Alice sees stopEpochWithDuration(loss) in mempool and front-runs it.
    vm.prank(alice);
    cdo.requestWithdrawBB(bbBefore); // -> IdleCreditVault.requestWithdraw: pendingWithdraws += amount

    vm.prank(manager);
    cdo.stopEpochWithDuration(newApr, 0, duration, loss);
    // previewLossAdjustedWithdrawFunds now gives the pending bucket (incl. alice)
    // a pro-rata share; activeLoss shrinks, alice's receipt claims at lossRecoveryPrice.
    vm.warp(block.timestamp + bufferPeriod);
    vm.prank(alice);
    cdo.claimWithdrawRequest();
    // alice's payout > what BB position would be worth under BB-first waterfall;
    // bob's pending receipt is haircut more than it would have been without alice's entry.
    assertGt(aliceReceived, aliceBBValueIfStayed);
}
```

Expected result mirrors the external report's pattern: the aggregate loss is the same, but its *distribution* is manipulated — Alice's reclassification forces Bob and remaining LPs to absorb loss that the waterfall assigned to her.

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }
