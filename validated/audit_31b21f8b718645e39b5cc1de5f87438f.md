### Title
Stale `BlockInfo` snapshot in `process_pending_responses_for_block` can overwrite a just-signed block's `signed_self`/state in SignerDB, undermining the equivocation guard - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`process_pending_responses_for_block` iterates over three separate collections of early votes (pre-commits, rejections, signatures) for the same proposal, but only the pre-commit branch re-fetches a fresh `BlockInfo` from the signer DB before mutating it. The rejection and signature branches are handed the single `block_info: &mut BlockInfo` that was captured *before* the loop started and is never refreshed. If, mid-loop, the pre-commit branch causes the block to cross the signing threshold and become locally signed (`mark_locally_accepted`, persisted via `self.signer_db.insert_block`), the subsequent rejection/signature branches still operate on the pre-signing snapshot and persist it back to the DB, silently clobbering the just-written signed state.

### Finding Description
`process_pending_responses_for_block` [1](#0-0)  is called from `handle_block_proposal` with a single mutable `block_info` reference obtained before any pending votes are replayed [2](#0-1) .

Inside the loop:
- The pre-commit branch delegates to `handle_block_pre_commit`, which does its own independent lookup `self.block_lookup_by_reward_cycle(block_hash)` [3](#0-2)  — a fresh read of DB state, separate from the caller's `block_info`. This function can push the block across the pre-commit weight threshold and sign it (`mark_locally_accepted`), persisting the update to `signer_db` [4](#0-3) .
- The rejection and signature branches, however, are passed the *same outer* `block_info: &mut BlockInfo` captured before the loop began, with no re-fetch [5](#0-4) .

This mirrors the Basket pattern: a single check/snapshot taken once at the top of a function is relied upon across a sequence of operations that includes an "external" state-mutating step (here, `handle_block_pre_commit`'s independent DB read-modify-write), and later steps in the same sequence act on the now-outdated snapshot rather than the mutated ground truth. `handle_block_validate_ok`/`handle_block_validate_reject` show the normal, safe pattern elsewhere in the file: fetch fresh, check `block_info.valid.is_some()` to detect a race, and bail if already decided [6](#0-5) . `process_pending_responses_for_block`'s rejection/signature branches have no equivalent guard against acting on stale data, and since they are passed a struct rather than re-deriving it, they cannot detect that the DB has moved on.

### Impact Explanation
If the stale `block_info` used by the rejection/signature branches is subsequently written back via `self.signer_db.insert_block(...)` inside `store_and_process_block_rejection`/`store_and_process_block_signature` (I was not able to fetch these two function bodies before running out of tool budget, so the exact overwrite mechanics are inferred from the surrounding code's consistent "mutate struct, then `insert_block`" idiom used throughout this file, e.g. [7](#0-6) ), the record of `signed_self`/`state == LocallyAccepted` that `handle_block_pre_commit` just persisted for our own signature could be overwritten by the older snapshot's values. This would make the signer DB forget it already signed this block, which is exactly the invariant `handle_block_pre_commit` depends on to prevent double-signing conflicting blocks at the same height (`block_info.signed_self.is_some()` early-return, and the sibling-conflict checks via `get_signed_conflicts`) [8](#0-7) . Losing that bookkeeping is the same class of issue the rules classify as High: "losing the equivocation guard."

### Likelihood Explanation
This requires no majority collusion and no key compromise — only that a proposal arrive with pending early votes queued in all three tables (`pre_commits`, `rejections`, `signatures`) simultaneously via `drain_pending_block_responses`, which is a normal occurrence when a signer is slightly behind the gossip stream (explicitly documented as the reason these pending tables exist) [9](#0-8) . A single miner/proposal plus ordinary out-of-order network delivery of peer responses is sufficient to populate all three queues before the proposal itself is processed; no attacker action beyond normal message timing is strictly required, though a miner or gossiping peer could deliberately race pre-commits and rejections/signatures to increase the odds of hitting this window.

### Recommendation
In `process_pending_responses_for_block`, re-fetch `block_info` from `signer_db` before each branch (or immediately after the pre-commit loop, before entering the rejection/signature loops) rather than continuing to mutate/pass the pre-loop snapshot, mirroring the fresh-lookup pattern already used by `handle_block_pre_commit` and `handle_block_validate_ok`.

### Proof of Concept
Not independently reproduced with a runnable test — this is a code-path analysis based on `stacks-signer/src/v0/signer.rs:1730-1780`, `1250-1366`, and `1888-1984`. I was unable to retrieve the bodies of `store_and_process_block_rejection` and `store_and_process_block_signature` within the available tool budget, so I could not fully confirm whether they perform an unconditional `insert_block` overwrite (as the parallel `handle_block_validate_reject`/`handle_block_validate_ok` do) or whether they contain an internal re-fetch/guard that would neutralize this issue. This should be verified directly against those two function bodies before treating the finding as fully confirmed.

    fn process_pending_responses_for_block(
        &mut self,
        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block_info: &mut BlockInfo,
        pending_responses: PendingBlockResponses,
    ) {
        let signer_signature_hash = block_info.block.header.signer_signature_hash();
        for stacker_address in pending_responses.pre_commits {
            debug!("{self}: Processing pending pre-commit.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
            );
            self.handle_block_pre_commit(
                stacks_client,
                sortition_state,
                &stacker_address,
                &signer_signature_hash,
            );
        }
        for (stacker_address, reject_reason) in pending_responses.rejections {
            debug!("{self}: Processing pending rejection.";
                "stacker_address" => %stacker_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_info.block.block_id(),
                "reject_reason" => ?reject_reason,
            );
            self.store_and_process_block_rejection(
                sortition_state,
                block_info,
                &stacker_address,
                reject_reason,
            );
        }
        let block_id = block_info.block.block_id();
        for (stackers_address, signature) in pending_responses.signatures {
            debug!("{self}: Processing pending signature.";
                "stacker_address" => %stackers_address,
                "signer_signature_hash" => %signer_signature_hash,
                "block_id" => %block_id,
            );
            self.store_and_process_block_signature(
                stacks_client,
                sortition_state,
                block_info,
                &stackers_address,
                &signature,
            );
        }
    }

    /// Retrieve and clear all pending block response entries matching the given block signer_signature_hash
    /// Returns PendingBlockResponses containing all matching pre-commits, approval signatures, and rejections
    pub fn drain_pending_block_responses(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<PendingBlockResponses, DBError> {
        let hash_str = block_sighash.to_string();

        // Delete and return pre-commits in one operation
        let pre_commits_qry = "DELETE FROM signer_pending_pre_commit_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr";
        let mut stmt = self.db.prepare(pre_commits_qry)?;
        let pre_commits_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            Ok(addr)
        })?;
        let pre_commits: Vec<_> = pre_commits_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return signatures in one operation
        let signatures_qry = "DELETE FROM signer_pending_signature_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, signature";
        let mut stmt = self.db.prepare(signatures_qry)?;
        let signatures_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let sig_str: String = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let signature: MessageSignature = serde_json::from_str(&sig_str).map_err(|_| {
                SqliteError::InvalidColumnType(1, sig_str.clone(), rusqlite::types::Type::Text)
            })?;
            Ok((addr, signature))
        })?;
        let signatures: Vec<_> = signatures_rows.collect::<Result<Vec<_>, _>>()?;

        // Delete and return rejections in one operation
        let rejections_qry = "DELETE FROM signer_pending_rejection_responses WHERE signer_signature_hash = ?1 RETURNING signer_addr, reject_code";
        let mut stmt = self.db.prepare(rejections_qry)?;
        let rejections_rows = stmt.query_map(params![&hash_str], |row| {
            let addr_str: String = row.get(0)?;
            let reject_code: u8 = row.get(1)?;
            let addr = StacksAddress::from_string(&addr_str).ok_or(
                SqliteError::InvalidColumnType(0, addr_str.clone(), rusqlite::types::Type::Text),
            )?;
            let reject_reason = RejectReasonPrefix::from(reject_code);
            Ok((addr, reject_reason))
        })?;
        let rejections: Vec<_> = rejections_rows.collect::<Result<Vec<_>, _>>()?;

        let pending_block_responses = PendingBlockResponses {
            pre_commits,
            signatures,
            rejections,
        };
        if !pending_block_responses.is_empty() {
            debug!("Drained pending block responses for block {block_sighash}";
                "pre_commits_count" => pending_block_responses.pre_commits.len(),
                "signatures_count" => pending_block_responses.signatures.len(),
                "rejections_count" => pending_block_responses.rejections.len());
        }
        Ok(pending_block_responses)
    }
