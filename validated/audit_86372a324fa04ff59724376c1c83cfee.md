### Title
Loss-adjusted withdrawal haircut bypass: a second `requestWithdraw` moves `lastWithdrawRequest` to a new epoch, so older pending receipts inside the haircut basis are later paid at par via `_claimFundedWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.requestWithdraw` tracks only the *latest* request epoch in `lastWithdrawRequest[_user]` (line 282), while receipt balances are stored per-epoch in `withdrawsRequestsByEpoch[_user][epoch]` and aggregated in `withdrawsRequests[_user]`/`apr0Users`. When `collectWithdrawFunds` records a partial funding, the haircut `lossRecoveryPriceByEpoch[epochNumber]` is applied to the *entire* `pendingWithdraws` aggregate — including receipts from earlier epochs — but `_claimLossAdjustedWithdrawRequest` only clears the receipt whose epoch equals `lastWithdrawRequest[_user]` and the residual older receipts are then paid 1:1 by `_claimFundedWithdrawRequest`. A receipt inside the haircutted basis therefore escapes the loss by being represented under a different epoch key, analogous to the MCPVault deny-list bypass where the same resource slips through under an alternate canonical representation.

### Finding Description
Relevant code in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestWithdraw` (lines 243–295) only blocks a *new* request when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` **and** the receipt for that epoch is still pending (lines 261–271). If no loss was recorded at the previous request epoch, the guard passes and `lastWithdrawRequest[_user] = currentEpoch` overwrites the marker (line 282), while the old receipt stays in `withdrawsRequestsByEpoch[_user][oldEpoch]` and in the `withdrawsRequests[_user]` aggregate.
- `collectWithdrawFunds` (lines 411–430) computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` where `pendingBasis = pendingWithdraws` is the **global** aggregate — it includes the caller's older-epoch receipts.
- `claimWithdrawRequest` (lines 301–314) calls `_claimLossAdjustedWithdrawRequest` (lines 789–801), which calls `_clearWithdrawClaimForEpoch(_user, lastWithdrawRequest[_user])` — clearing **only** the newest epoch's `withdrawsRequestsByEpoch` entry and the matching `apr0Users.principalEpoch` (lines 815–836). `withdrawsRequests[_user]` is decremented by only that epoch's amount.
- `_claimFundedWithdrawRequest` (lines 319–350) then sees `lastWithdrawRequest[_user] == 0` (cleared), passes the `epochNumber <= lastWithdrawRequest` check, settles any older APR0 principal via `_settleApr0`, burns `withdrawsRequests[_user] + settledPrincipal`, and transfers the **full un-haircutted** amount.

Attack sequence (APR0 variant shown; normal-only works identically):
1. Epoch N running/buffer: attacker calls `CDO.requestWithdraw` → receipt recorded in epoch N (`lastWithdrawRequest = N`). No loss at stop of epoch N, so `lossRecoveryPriceByEpoch[N] == 0`.
2. Epoch N+1 buffer: attacker requests again → guard passes (no loss price at N), `lastWithdrawRequest = N+1`. Both receipts now sit in `pendingWithdraws`.
3. `stopEpochWithDuration`/`stopEpoch` for epoch N+1 is called with a realized loss: `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[N+1] < RECOVERY_FULL` over a `pendingBasis` that includes the epoch-N receipt.
4. Attacker calls `claimWithdrawRequest`: epoch N+1 receipt paid at the haircut; the epoch-N receipt is then paid **at par** from the same loss-adjusted funded pool.

### Impact Explanation
Direct theft / insolvency. The attacker extracts `oldReceipt * (1 - lossRecoveryPrice/RECOVERY_FULL)` more underlyings than entitled. Since the strategy was only funded `pendingBasis * lossRecoveryPrice` total, the over-payment comes out of other claimants' funded claims — the last claimants to call `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert on insufficient balance (permanent freezing of their funded yield), or the deficit is silently socialized. Broken invariant: "one receipt one payout at its epoch's recovery price" and the loss waterfall that pending receipts share losses pro rata.

### Likelihood Explanation
Requires only an unprivileged KYC-passed lender with two withdraw requests in consecutive epochs and a subsequent `stopEpochWithDuration(_lossAmount)` partial funding (honest manager call). The guard in `requestWithdraw` (lines 263–271) is explicitly designed to force claiming a loss-adjusted receipt before re-requesting, but it only inspects the *latest* epoch marker — exactly the representation mismatch the external report describes (case/trailing-dot aliases bypassing a deny-list). No privileged misbehavior needed; any realized stop-epoch loss while a user holds receipts spanning multiple epochs triggers it.

### Recommendation
Make claim clearing iterate over all epochs contributing to `pendingWithdraws`, or enforce the invariant symmetrically: in `requestWithdraw`, revert if `withdrawsRequests[_user] != 0 || apr0Users[_user].principal != 0 || apr0Users[_user].settledPrincipal != 0` whenever *any* unclaimed receipt predates a not-yet-funded epoch — i.e., key the guard on outstanding receipt existence rather than only `lastWithdrawRequest`. Alternatively, in `_claimLossAdjustedWithdrawRequest`, apply `lossRecoveryPrice` to the user's *entire* outstanding claim basis that was inside `pendingBasis`, not just the `lastWithdrawRequest` epoch.
