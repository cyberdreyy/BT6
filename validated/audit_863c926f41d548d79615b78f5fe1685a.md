### Title
`EscapeForPosix` fails to neutralize control/ANSI-escape bytes, allowing terminal-escape injection into CI job trace logs - (File: functions/script_legacy/internal/escape.go)

### Summary
`EscapeForPosix` only escapes `` ` ``, `"`, `\`, `$` and marks a short list of punctuation as quote-triggers, but unlike `EscapeForAnsiC` it never hex-escapes control bytes (0x00–0x1F, 0x7F) or non-ASCII bytes. When `CommandFormatter.FormatLogLine` and `TraceSectionWriter.writeSectionStart` run in POSIX mode (`posixMode`/`PosixEscape` = true), any raw control character (including ESC `0x1b`) present in a user-authored `.gitlab-ci.yml` script line passes through unescaped into the generated `echo`/`printf` statement that logs the command to the job trace.

### Finding Description
`EscapeForAnsiC` explicitly hex-escapes control characters and non-ASCII bytes to defeat terminal manipulation via ANSI escape sequences, per its own doc comment: "Control characters and non-ASCII bytes are hex-escaped to prevent terminal manipulation... prevents jobs from clearing the screen or rewriting logs using ANSI escape sequences" [1](#0-0) . Its default branch performs this hex-escaping for any byte `< 0x20 || == 0x7F || > 0x7F` [2](#0-1) .

`EscapeForPosix`, used for the same purpose when POSIX mode is enabled, has no such default branch — any rune not in the explicit switch cases (backtick, `"`, `\`, `$`, or the quoting-trigger punctuation set) is written through completely unmodified via `buf.WriteRune(r)` [3](#0-2) . This includes ESC (`0x1b`), CR (`\r`), BS (`\b`), and other control bytes that are exactly the class of characters `EscapeForAnsiC` was built to neutralize.

`FormatLogLine` calls `EscapeForPosix(command)` when `f.posixMode` is true and wraps the result in `echo %s` [4](#0-3) . `TraceSectionWriter.escape` does the analogous thing for section headers via `printf` [5](#0-4) . The `command` value ultimately originates from the pipeline author's `script:` lines in `.gitlab-ci.yml`, which is fully attacker(pipeline-author)-controlled and can contain raw control bytes (e.g., via YAML double-quoted scalars with `\x1B`, `\r`, `\b` escapes, which YAML decodes to literal bytes before the runner ever sees the string). Because `EscapeForPosix` does not neutralize these bytes, the generated log-echo statement embeds them verbatim, and they will render as live terminal control codes when the trace is displayed in any raw-terminal context (`gitlab-runner exec`, downloading and `cat`-ing the job trace, some terminal-based log viewers).

Existing protections do not stop this: the double-quote wrapping only guards against POSIX double-quote metacharacters (`` ` ``, `"`, `\`, `$`), which is correct for preventing shell injection, but it does nothing against raw control bytes, and no other sanitation step exists between YAML parsing and log emission for the POSIX code path.

### Impact Explanation
An attacker with only pipeline-author privileges can inject terminal control/escape sequences (screen clear, cursor movement, carriage-return line overwrite, terminal title/OSC sequences, and in vulnerable terminal emulators, more exotic sequences) into the command-echo lines of the job trace whenever the shell/script generator runs in POSIX escape mode. This does not escape the sandbox or leak secrets by itself, but it breaks the log-integrity invariant that trace output faithfully and safely represents what happened: a reviewer viewing the raw trace in a terminal could have prior log lines obscured, overwritten, or spoofed, hiding malicious commands from manual audit of job output.

### Likelihood Explanation
Fully attacker-controlled and reproducible: any pipeline author can put a script line whose text contains literal control bytes (via YAML `\x1B`, `\r` escapes in double-quoted scalars) and set/rely on the POSIX-escape shell path (`shells/bash.go` `PosixEscape` config) to trigger `EscapeForPosix` instead of `EscapeForAnsiC`. No special privileges, race conditions, or admin cooperation are required.

### Recommendation
Add the same control-character/non-ASCII hex-escaping default branch used in `EscapeForAnsiC` to `EscapeForPosix` (e.g., hex-escape via `printf`-safe `\xHH` sequences valid inside POSIX double quotes, or fall back to `$'...'` ANSI-C quoting whenever control bytes are present), so control bytes are neutralized regardless of which escaping mode is active.

### Proof of Concept
Go unit test in `functions/script_legacy/internal/escape_test.go` style:
```go
func TestEscapeForPosix_ControlBytesNotNeutralized(t *testing.T) {
    input := "echo hi\x1b[2Jclear-attack" // literal ESC byte
    out := EscapeForPosix(input)
    // BUG: raw ESC byte passes through unescaped
    if strings.ContainsRune(out, 0x1b) {
        t.Fatalf("EscapeForPosix leaked raw ESC byte into output: %q", out)
    }
}
```
Expected (buggy) result: the assertion fails because `out` still contains the raw `0x1b` byte, proving `EscapeForPosix` (unlike `EscapeForAnsiC`) does not neutralize control characters. A corresponding CI job PoC would set a script step containing a YAML double-quoted string with `\x1B[2J` while running under the POSIX-escape shell config, then inspect the raw job trace bytes downloaded via the API/CLI to confirm the literal ESC byte is present unescaped in the `echo`/`printf` log line.

```go
func EscapeForPosix(s string) string {
	if s == "" {
		return "''"
	}

	var buf strings.Builder
	needsQuoting := false

	for _, r := range s {
		switch r {
		case '`', '"', '\\', '$':
			buf.WriteRune('\\')
			buf.WriteRune(r)
			needsQuoting = true
		case ' ', '!', '#', '%', '&', '(', ')', '*', '<', '=', '>', '?', '[', '|':
			buf.WriteRune(r)
			needsQuoting = true
		default:
			buf.WriteRune(r)
		}
	}
```
