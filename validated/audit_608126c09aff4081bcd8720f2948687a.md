### Title
Rejection weight is silently re-counted as acceptance weight, letting a single signer's stale vote inflate both tallies past the true 70% threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side vote tally in `StackerDBListener::run` gates duplicate-counting of `BlockResponse::Accepted` and `BlockResponse::Rejected` messages using two *different* per-slot sets (`gathered_signatures` for accepts, `responded_signers` for both), instead of a single authoritative "current vote" per slot. A signer that legitimately rejects a block and later re-evaluates and accepts it (a flow the signer state machine explicitly supports per `docs/signer-flows.md` section 2/3: `LocallyRejected --> LocallyAccepted : re-evaluated`) has its weight counted on *both* sides simultaneously at the node, because the accept path only checks `gathered_signatures.contains_key(&slot_id)` and never checks/clears `responded_signers`'/rejection state.

### Finding Description
`BlockStatus` ( [1](#0-0) ) tracks two independent membership structures per block: `responded_signers: HashSet<u32>` and `gathered_signatures: BTreeMap<u32, MessageSignature>`.

For an `Accepted` message, the weight-add guard is: [2](#0-1) 
This only checks `gathered_signatures.contains_key(&slot_id)`. If the slot previously only sent a rejection (which populates `responded_signers` but not `gathered_signatures`), this check passes and `total_weight_approved` is incremented in addition to the prior `total_weight_rejected` increment from the earlier rejection.

For a `Rejected` message, the guard is: [3](#0-2) 
Here `responded_signers.insert(slot_id)` correctly blocks a second reject-weight increment if the slot already accepted (since Accept also inserts into `responded_signers` at line 465), but the reverse direction — accept-after-reject — is not symmetric, because Accept is gated by the wrong set.

On the signer side, this reject→accept transition is a legitimate, protocol-sanctioned state change (`BlockInfo::check_state`, `LocallyRejected --> LocallyAccepted : re-evaluated`), so a single, honest signer re-broadcasting its updated opinion after a prior rejection is enough to trigger this — no majority collusion required, matching the "one-slot miner (plus gossip)" trigger constraint.

### Impact Explanation
`self.total_weight_rejected` and `self.total_weight_approved` are used independently by `parse_and_verify_block_responses` in the coordinator to decide the fate of a proposed block: [4](#0-3) 
Because a single signer's weight can now be simultaneously present in both `total_weight_rejected` and `total_weight_approved`, the sum of the two can exceed `self.total_weight` (the honest total). This breaks the invariant that "aggregated weight" reflects distinct signers' *current* votes:
- The stale rejection weight is never retracted when the signer later accepts, so `total_weight_rejected` can remain inflated with weight that no longer represents that signer's live opinion. If this pushes `total_weight_rejected` past the 30% blocking-minority threshold (line 511-513) before/independently of `total_weight_approved` reaching 70%, the coordinator aborts a block via `NakamotoNodeError::SignersRejected` that in truth has (or would have) legitimate majority support — a liveness wedge on block production for that miner.
- Conversely, the double-counted accept weight can also help `total_weight_approved` cross the acceptance threshold using inflated weight from a signer whose "current" vote share should count only once, undermining the guarantee that ≥70% of the true reward-set weight actively and currently accepted the exact block being pushed.

This falls under "aggregated-weight vs verified-accepts" equality breaking, and in the rejection-then-abort scenario constitutes a liveness wedge (block production stalls / miner needlessly aborts a signable block), classified High per the rules' impact bucket.

### Likelihood Explanation
Medium: the trigger doesn't require malice or majority collusion — it can occur from ordinary honest signer behavior any time a signer legitimately reverses a prior rejection into an acceptance for the same block (a supported and expected code path per the state machine docs), or trivially by a single malicious signer intentionally emitting a Rejected message immediately before its normal Accepted response for the same `signer_signature_hash`.

### Recommendation
Track a single authoritative "current vote + weight" per slot (e.g., an enum `Accepted(sig)`/`Rejected` stored in one map keyed by `slot_id`), and when a new response for a slot supersedes a prior one, subtract the previous weight contribution from the corresponding tally before adding the new one — mirroring how `SignerDb::add_block_signature`/`add_block_rejection_signer_addr` correctly delete the opposing entry on the signer side ( [5](#0-4)  and [6](#0-5) , which already implement mutual exclusivity signer-side but the analogous node-side tally in `stackerdb_listener.rs` does not).

### Proof of Concept
1. Miner proposes block B; signer S (weight W) validates and initially rejects it (e.g., transiently sees a stale conflict) → node records `responded_signers.insert(S)`, `total_weight_rejected += W`.
2. Per `docs/signer-flows.md` section 5 (`should_reevaluate_block`/re-evaluation flow), S's local conflict view later resolves and S legitimately transitions `LocallyRejected --> LocallyAccepted` and broadcasts an `Accepted` for the *same* `signer_signature_hash`.
3. Node handling of the `Accepted` message checks only `!gathered_signatures.contains_key(&S)` (true, since S was never added there) → node adds `total_weight_approved += W` in addition to the already-recorded `total_weight_rejected += W` from step 1.
4. `total_weight_approved + total_weight_rejected` now exceeds `self.total_weight`, and depending on timing either: (a) the coordinator declares `SignersRejected` due to inflated stale rejection weight even though S's live vote is Accept (liveness stall), or (b) S's weight is used to help cross the 70% acceptance bar while it also still counts toward the rejection tally, corrupting the aggregated-weight accounting that downstream consumers rely on as ground truth for signer consensus.
