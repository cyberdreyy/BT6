### Title
Unchecked u64 subtraction in `L1BlockInfo::operator_fee_refund` can underflow when gas refund exceeds remaining gas headroom - ([File: crates/common/evm/src/l1block.rs])

### Summary
`L1BlockInfo::operator_fee_refund` computes the gas actually used as `gas.limit() - (gas.remaining() + gas.refunded() as u64)` using plain (non-checked, non-saturating) `u64` subtraction, unlike every other fee-arithmetic path in the codebase, which consistently uses `checked_*`/`saturating_*` operations.

### Finding Description
`operator_fee_refund` is the Isthmus/Jovian operator-fee analog of the WatchPug `handleFees()` bug: the reported Solidity bug is an unguarded subtraction (`BASE - feePct`) whose operands are derived from attacker/time-influenced inputs, causing an underflow revert that disrupts core protocol operations. Here the same subtraction-without-bound-check pattern exists at: [1](#0-0) 

```rust
pub fn operator_fee_refund(&self, gas: &Gas, spec_id: BaseSpecId) -> U256 {
    ...
    let operator_cost_gas_used = self.operator_fee_charge_inner(
        U256::from(gas.limit() - (gas.remaining() + gas.refunded() as u64)),
        spec_id,
    );
    operator_cost_gas_limit.saturating_sub(operator_cost_gas_used)
}
```

Every other subtraction in this crate's fee/gas paths is explicitly guarded: `settle_fees` in `eip8130.rs` uses `checked_sub` with an explicit error on underflow [2](#0-1) , and the `charge_upfront`/`validate_against_state_and_deduct_caller` paths use `checked_sub`/`saturating_sub` [3](#0-2) . `operator_fee_refund` is the one outlier that performs a raw `-` on two `u64` values whose relationship (`gas.remaining() + gas.refunded() <= gas.limit()`) is only true by convention of revm's internal gas accounting, not enforced at this call site.

Whether this is actually exploitable depends on whether `gas.remaining() + gas.refunded()` can exceed `gas.limit()` at the point this function is called — e.g., if it is invoked with the raw (uncapped) EIP-3529 refund counter before the `gas_used / 5` cap is applied, a transaction that touches enough zeroed storage slots to accumulate a large refund could push `gas.refunded()` above the gas actually consumed. I could not fully confirm from the indexed code the exact call-site ordering relative to refund capping (the caller in `crates/common/evm/src/handler.rs` truncates before showing the exact call), so this should be treated as a **plausible but unconfirmed** underflow condition rather than a proven one.

### Impact Explanation
If the underflow is reachable: in a debug/overflow-checked build this panics, crashing the node process on execution of a single, otherwise valid, attacker-crafted (or naturally-occurring) transaction — a node-halt / chain-split risk if only some nodes run with overflow checks enabled. In a release build without `overflow-checks`, the subtraction wraps to a huge `u64`, which is then fed into `operator_fee_charge_inner`'s scalar multiplication (which does use `saturating_mul`), producing a saturated, incorrect operator fee charged against the transaction's actual gas usage — a fee-accounting correctness bug, though `saturating_sub` on the final `operator_cost_gas_limit.saturating_sub(operator_cost_gas_used)` would clamp the visible result to zero rather than mint or lose funds outright.

### Likelihood Explanation
Low-to-moderate. This requires either: (a) building with `overflow-checks=true` (uncommon for release nodes, but used in CI/debug), combined with a transaction whose refund counter genuinely exceeds the gas headroom before capping is applied, or (b) confirming that this function is called with the raw refund count rather than the already-capped value. I was not able to fully trace the call order from the caller site within the indexing limits, so likelihood cannot be confirmed with certainty from static inspection alone.

### Recommendation
Replace the raw subtraction with `checked_sub`/`saturating_sub` and either return zero or an explicit error on underflow, consistent with the rest of this crate's fee-arithmetic style (e.g., matching the `checked_sub` pattern used in `eip8130.rs`'s `settle_fees`). Additionally, verify and document at the call site whether `gas.refunded()` passed to `operator_fee_refund` is the capped or uncapped EIP-3529 refund value.

### Proof of Concept
Not independently reproduced (this is a Rust node crate, not a deployable Solidity contract, and no execution environment was available). Conceptually: construct a transaction that maximizes SSTORE-clear refunds relative to gas actually used so that `gas.remaining() + gas.refunded() > gas.limit()` at the point `operator_fee_refund` is invoked; on an overflow-checked build this panics the executing node, and on a release build it silently wraps, corrupting the computed operator-fee-used value.
