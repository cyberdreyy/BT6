### Title

Blacklisted credit-vault users cannot redirect or transfer matured withdrawal claims - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

`IdleCDOEpochVariant.claimWithdrawRequest()` hardcodes `msg.sender` as the receipt owner, while `IdleCreditVault` always pays that same address and prevents users from transferring the receipt to another account. If the underlying asset is a blacklistable token such as USDC, a claimant blacklisted after creating a withdrawal request can never redirect the payout, permanently freezing the claim while the blacklist remains active.

### Finding Description

A withdrawal request burns the user's tranche position and creates a claim denominated in underlying tokens through `IdleCreditVault.requestWithdraw(_underlyings, msg.sender, principal)`. [1](#0-0) 

Once the epoch is funded, `IdleCDOEpochVariant.claimWithdrawRequest()` accepts no receiver argument and passes only `msg.sender` to the strategy. [2](#0-1) 

`IdleCreditVault.claimWithdrawRequest(_user)` clears the claim and sends the funded underlying tokens to `_user`; there is no separate beneficiary parameter. [3](#0-2) [4](#0-3) 

The same recipient restriction applies to instant withdrawals, post-default requests, defaulted withdrawals, loss-adjusted withdrawals, and recovery payouts because every path ends at `_transferFundedClaim(_user, amount)` or `_transferDefaultRecovery(_user, amount)`. [5](#0-4) [6](#0-5) 

The user cannot work around the restriction by transferring the strategy-token receipt because `_transfer` reverts unless the caller is the CDO contract. [7](#0-6) 

The queued-withdrawal path has the same limitation: the queue processes the claim and `claimWithdrawRequest` subsequently transfers the matured underlying payout to `msg.sender`. [8](#0-7) [9](#0-8) 

### Impact Explanation

A funded claim's entire principal and accrued interest can remain locked if the claim owner's address is blacklisted by the underlying token. The failed ERC20 transfer reverts the whole claim transaction, so accounting remains unchanged and the user can retry, but every retry necessarily pays the same blacklisted address.

The owner-only `transferToken` rescue function does not provide a proper claim settlement path because it moves contract funds without clearing the user's claim state. [10](#0-9) 

The maximum affected amount is the user's complete matured withdrawal claim, including principal and accrued yield.

### Likelihood Explanation

The issue requires the claim owner to become blacklisted by the underlying asset after creating the receipt. This is externally conditional and therefore low-to-medium likelihood, but USDC is an actual supported test underlying on the mainnet fork used by the credit-vault suite. [11](#0-10) [12](#0-11) 

No privileged vault role needs to act maliciously, and none of the epoch guards, KYC checks, reserve checks, or claimability checks provide a recipient-override path once the claim is funded.

### Recommendation

Allow the receipt owner to choose the payout destination while keeping ownership bound to `msg.sender`:

- Change `IdleCDOEpochVariant.claimWithdrawRequest()` to `claimWithdrawRequest(address receiver)`.
- Change `claimInstantWithdrawRequest()` and queue claim functions similarly.
- In `IdleCreditVault`, retain `msg.sender`/`_user` as the accounting and burn owner, but pass a separate `receiver` to `_transferFundedClaim` and `_transferDefaultRecovery`.
- Reject `receiver == address(0)`.
- Preserve the existing CDO-only strategy access control and receipt-transfer restrictions.
- Apply the same treatment to normal, instant, loss-adjusted, defaulted, post-default, and queue-mediated claims.

### Proof of Concept

Add this test to `test/foundry/IdleCreditVault.t.sol`; it uses the existing mainnet USDC fork and simulated blacklisting:

```solidity
interface IUSDCBlacklist {
  function blacklister() external view returns (address);
  function blacklist(address account) external;
}

function testBlacklistedUserCannotRedirectFundedClaim() external {
  address user = makeAddr('blacklisted-user');
  address recovery = makeAddr('recovery-address');
  uint256 amountWei = 10_000 * ONE_SCALE;

  // Fund the user and create a normal withdrawal receipt.
  _depositWithUser(user, amountWei, true);

  vm.prank(user);
  uint256 claimAmount = cdoEpoch.requestWithdraw(0, address(AAtranche));
  assertGt(claimAmount, 0);

  // Epoch 0 runs and borrower funding is collected by the credit vault.
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

  assertEq(
    IERC20Detailed(address(strategy)).balanceOf(user),
    claimAmount,
    'withdrawal receipt was not minted'
  );

  // Simulate the external asset issuer blacklisting the claimant.
  address blacklister = IUSDCBlacklist(USDC).blacklister();
  vm.prank(blacklister);
  IUSDCBlacklist(USDC).blacklist(user);

  // The matured claim always pays user, so USDC rejects it.
  vm.prank(user);
  vm.expectRevert();
  cdoEpoch.claimWithdrawRequest();

  // The failed transfer rolled back the claim.
  assertEq(
    IdleCreditVault(address(strategy)).withdrawsRequests(user),
    claimAmount,
    'claim was unexpectedly consumed'
  );

  // The user cannot transfer the receipt to a clean recovery address either.
  vm.prank(user);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  IERC20Detailed(address(strategy)).transfer(recovery, claimAmount);
}
```
