Confirmed: `get_builder_withdrawals` at [1](#0-0)  builds the `Withdrawal.amount` from the raw `withdrawal.amount` field of `BuilderPendingWithdrawal` **without capping to `builder.balance`**, while `apply_withdrawals` caps the actual balance deduction to `min(withdrawal.amount, builder_balance)` at [2](#0-1) . This is exactly the reported bug-class: an amount is capped on one side of the ledger (CL balance decrease) but left uncapped on the other side (the payout amount committed for the EL to execute), so the two amounts silently diverge.

### Title
Builder withdrawal payout amount is not capped to available builder balance while the CL-side deduction is, minting uncollateralized Gwei on the execution layer - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` copies `BuilderPendingWithdrawal.amount` verbatim into the `Withdrawal.amount` field that is committed to the execution layer via `payload_expected_withdrawals`/`ExecutionPayload.withdrawals`, with no check against `state.builders[builder_index].balance`. Meanwhile `apply_withdrawals`, which mutates the CL-side `state.builders[builder_index].balance`, explicitly caps the deduction to `min(withdrawal.amount, builder_balance)`. When a `builder_pending_withdrawals` entry requests more than the builder's current balance, the CL only deducts the builder's remaining balance, but the EL is instructed (via the committed, uncapped `Withdrawal.amount`) to credit the *full* requested amount to `fee_recipient`. This mints Gwei on the EL side that was never backed by any CL balance.

### Finding Description
The two-sided nature of a `Withdrawal` is the root cause: it is simultaneously (a) an instruction that the EL must credit `amount` to `address`, and (b) implicitly the amount by which `apply_withdrawals` deducts CL state. These two amounts must always be equal for the CL/EL supply invariant to hold.

- `get_builder_withdrawals` (spec builds the committed withdrawal list): [3](#0-2) 
This loop appends `Withdrawal(..., amount=withdrawal.amount)` directly from `state.builder_pending_withdrawals`, never reading `state.builders[builder_index].balance`.

- `apply_withdrawals` (spec applies the CL-side deduction for the same list): [2](#0-1) 
Here the deduction is explicitly `min(withdrawal.amount, builder_balance)`, i.e. capped, while the value already placed in `payload_expected_withdrawals` (and thus committed to `payload.withdrawals` for the EL) remains the uncapped `withdrawal.amount`.

- `process_withdrawals` asserts the payload matches this uncapped list and then applies the capped deduction: [4](#0-3) 

The mismatch is exactly the pattern from the external report: one code path caps an amount to the actual available balance (`ShortCollateral.liquidate`'s `totalCollateralReturned = userCollateral.amount`), while a second, coupled code path (the `powerPerp.burn(msg.sender, debtRepaying)` in `Exchange._liquidate`) still uses the original, uncapped amount. Here, the "burn" analog is the EL-side mint driven by the uncapped `Withdrawal.amount`, and the "capped payout" analog is the CL-side `apply_withdrawals` deduction.

The test suite itself documents this exact divergence as intended behavior (not merely as an edge case caught by an assertion): [5](#0-4) 
Note the asserted output: `withdrawal.amount: 5 ETH (requested amount)` while `builders[0].balance: 0 (deduction capped to available balance)` — i.e. the committed EL payout (5 ETH) exceeds the CL balance that was ever backing it (1 ETH).

### Impact Explanation
This breaks the "Gwei created" equality: the execution layer will credit `fee_recipient` with the full requested `withdrawal.amount` (e.g. 5 ETH) even though the builder's CL balance backing it was only 1 ETH. The remaining 4 ETH is minted on the EL side with no corresponding CL-side balance ever having existed — new, uncollateralized Gwei enters total EL supply. Any entity that can get an over-large `amount` queued into `state.builder_pending_withdrawals` (e.g. via `process_parent_execution_payload`/builder payment settlement, which is the normal path that appends to `builder_pending_withdrawals`) profits directly, or can direct excess value to an arbitrary `fee_recipient`. This is a Critical-class issue per the given impact taxonomy ("Gwei created, destroyed or paid to a non-owner").

### Likelihood Explanation
`builder_pending_withdrawals` entries are populated by the builder-payment settlement path (`apply_parent_execution_payload`/payment-processing logic), and the `amount` in a `BuilderPendingPayment`/`BuilderPendingWithdrawal` is influenced by `state.builder_pending_payments[...].weight`/withdrawal amount, which is itself driven by the value the builder claims to pay in its bid. If a builder's balance is later reduced by other builder-balance-affecting operations (e.g. concurrent withdrawal processing, another pending withdrawal draining the same builder in the same sweep, or the payment simply exceeding the builder's remaining escrowed balance) before the withdrawal is applied, the requested amount can legitimately exceed the current balance at apply-time, since nothing checks balance sufficiency at the time the pending withdrawal is created. The overflow test in the repo's own test suite (`test_builder_withdrawal_insufficient_balance`) confirms this state is reachable through normal spec-defined transitions, not merely a theoretical corner case.

### Recommendation
Cap the amount placed into the `Withdrawal` object itself (the one committed to the EL) to the available builder balance at the time `get_builder_withdrawals` runs, i.e. `amount=min(withdrawal.amount, state.builders[builder_index].balance)`, so the same capped value is used both for the EL-committed payload and the CL-side `apply_withdrawals` deduction. Alternatively, cap the pending-withdrawal `amount` at insertion time (in the payment-settlement path) so it can never exceed the builder's committed balance.

### Proof of Concept
Using the values from the repo's own test (`test_builder_withdrawal_insufficient_balance`):
1. `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=F)]` (5 ETH requested).
3. `get_expected_withdrawals` → `get_builder_withdrawals` produces `Withdrawal(validator_index=..., address=F, amount=5_000_000_000)` — uncapped — placed into `payload_expected_withdrawals`.
4. `process_withdrawals` asserts `payload.withdrawals == expected.withdrawals`, so the execution payload committed by the proposer must contain this 5 ETH withdrawal, which the EL will credit in full to `F`.
5. `apply_withdrawals` then executes `state.builders[0].balance -= min(5_000_000_000, 1_000_000_000)` → `state.builders[0].balance = 0`.
6. Net effect: EL credits `F` with 5 ETH; CL only ever backed 1 ETH of that. 4 ETH of new Gwei exists on the EL side with no corresponding CL-side deduction — a supply-invariant violation.
