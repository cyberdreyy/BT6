### Title
Post-default instant-withdraw receipts are booked into `defaultRecoveryEpoch` and paid from `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Linux bug is an uncleared control buffer: `skb2->cb` still holds an IPv4 `inet_skb_parm`, but `icmp6_send()` reinterprets it as an `inet6_skb_parm`, so attacker-controlled bytes written under one context drive logic in another. The direct analog in `IdleCreditVault` is `requestInstantWithdraw`, which unconditionally records new receipts under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` even after `finalizeDefaultRecovery` has frozen `defaultRecoveryEpoch = epochNumber`. A receipt written in the post-default context is then reinterpreted by `_claimDefaultedInstantWithdrawRequest` as a defaulted-epoch claim and paid out of the isolated `defaultRecoveryReserve` at `defaultRecoveryPrice`, diluting the fixed recovery pool meant for real default-epoch claimants. Unlike `requestWithdraw` (which has an explicit `defaultRecoveryFinalized` branch that burns/mints into `postDefaultRequests`), the instant path was never cleared/re-routed — the exact "forgot to clear cb[]" shape.

### Finding Description
- `requestInstantWithdraw` (`contracts/strategies/idle/IdleCreditVault.sol:356-375`) performs `_ensureDefaultRecoveryInitialized()` but contains **no** `defaultRecoveryFinalized` check. It mints receipt tokens and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`.
- `finalizeDefaultRecovery` (lines 690-696) sets `defaultRecoveryEpoch = epochNumber` and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0`, and sizes `defaultRecoveryReserve = recoveredAmount + prefundedReserve + priorReserve` against `totalBasis = activeBasis + defaultPendingClaimBasis()`.
- `claimInstantWithdrawRequest` (lines 380-389) calls `_claimDefaultedInstantWithdrawRequest(_user)` whenever `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. That function (lines 842-856) reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, burns the receipt, and calls `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (line 915).
- Because `defaultRecoveryEpoch == epochNumber` until a new epoch starts (and post-default `startEpoch`/epoch advance is blocked or irrelevant while defaulted), any instant receipt created **after** finalization lands in the same `defaultRecoveryEpoch` bucket. `_withdrawClaimAmountsForEpoch`/instant-claim logic cannot distinguish a pre-default unfunded receipt from a post-default one — the storage slot is reinterpreted exactly like `IP6CB` reinterpreting `inet_skb_parm`.
- The post-default request also inflates `pendingInstantWithdraws`, but the clamped subtraction at line 852 (`claimBasis >= pending ? 0 : pending - claimBasis`) means the attacker still gets `claimBasis * defaultRecoveryPrice / 1e18` paid from the reserve.

### Impact Explanation
`defaultRecoveryReserve` is a fixed, isolated pool sized at finalization to exactly cover `activeBasis + pendingBasis` at `defaultRecoveryPrice` (lines 679-691). A post-default instant request creates claim basis that was never included in that sizing. When the attacker claims, `_transferDefaultRecovery` decrements the reserve by `claimBasis * defaultRecoveryPrice / 1e18`. If the reserve holds enough underlying, the attacker receives recovery funds that were proportionally owed to legitimate default-epoch receipt holders and to active tranche holders whose NAV was crystallized against the same `totalBasis`; those claimants' later claims then underflow or revert at line 915 (`defaultRecoveryReserve -= _amount`) / on token balance, permanently freezing part of the recovery. Loss is bounded by the available reserve and is a direct theft/dilution of unclaimed recovery proceeds — an accepted impact class.

### Likelihood Explanation
Requirements: the vault must be in APR0-or-normal instant mode with `defaultInstantWithdrawsFinalized == true` (i.e., `pendingInstantWithdraws != 0` at finalization — the partially-unfunded instant queue case the code explicitly handles, lines 636-648), and `defaultRecoveryPrice` such that the haircut payout is profitable relative to the tranche price paid to mint the receipt. The attacker only needs to be a KYC-passing lender holding tranche tokens: call `IdleCDOEpochVariant.requestInstantWithdraw` after `finalizeDefaultRecovery`, then `claimInstantWithdrawRequest`. Whether the CDO layer additionally reverts instant requests while `defaulted()` could not be confirmed — the strategy-level function itself has no such guard, and `requestInstantWithdraw`'s lack of a `defaultRecoveryFinalized` branch (asymmetric with `requestWithdraw` at line 247) indicates the case was not handled. If the CDO does not block it, exploitation requires two ordinary user calls in the defaulted phase.

### Recommendation
Mirror the `requestWithdraw` fix: in `requestInstantWithdraw`, either revert when `defaultRecoveryFinalized` is set, or route post-default instant requests to a separate `postDefaultRequests`-style bucket that is never read by `_claimDefaultedInstantWithdrawRequest`. Additionally, key instant receipts strictly by request epoch and have `_claimDefaultedInstantWithdrawRequest` only clear receipts created before `defaultRecoveryFinalized` was set — i.e., "clear the cb": prevent storage written in the post-default context from being interpreted as default-epoch basis. A secondary hardening is to record the request timestamp/flag alongside `instantWithdrawsRequestsByEpoch` entries.

    //       instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] += amount
    //       (epochNumber unchanged post-default).
    // 5. Attacker calls cdoEpoch.claimInstantWithdrawRequest().
    //    -> _claimDefaultedInstantWithdrawRequest reads the new receipt as a

    //       defaultRecoveryReserve.

Caveat: I could not verify within this iteration whether `IdleCDOEpochVariant.requestInstantWithdraw` independently reverts when `defaulted()` is true (grep confirmed the symbols exist in `contracts/IdleCDOEpochVariant.sol` but not the guard bodies). If the CDO blocks instant requests post-default, this path is unreachable and the analog does not hold — the strategy-level asymmetry with `requestWithdraw` would still be a latent defense-in-depth gap rather than an exploitable bug.
