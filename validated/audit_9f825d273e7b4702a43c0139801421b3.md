### Title
Unfunded instant-withdraw receipts can drain underlying reserved for funded withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The analog of the Goa path-traversal class ("read resources outside the intended scope") is a claim escaping its intended funding bucket: `claimInstantWithdrawRequest` pays out the strategy contract's raw underlying balance without verifying that the caller's instant receipt was ever funded via `collectInstantWithdrawFunds`, letting an unprivileged tranche holder withdraw funds that belong to other users' already-funded withdraw receipts or the default-recovery reserve.

### Finding Description
`requestWithdraw` on the CDO routes to `requestInstantWithdraw` on the vault when `lastEpochApr > currentApr + instantWithdrawAprDelta` [1](#0-0) . The vault burns the CDO's strategy tokens, mints an equal receipt to the user, and bumps `instantWithdrawsRequests`/`pendingInstantWithdraws` [2](#0-1) . Funding arrives separately through `collectInstantWithdrawFunds`, which pulls underlying from the CDO [3](#0-2) .

`claimInstantWithdrawRequest` has no epoch gating (unlike `_claimFundedWithdrawRequest`, which requires `epochNumber > lastWithdrawRequest` [4](#0-3) ) and no per-user "funded" marker. It simply burns the receipt and pays out via `_transferFundedClaim` [5](#0-4) .

The vault's underlying balance routinely holds money owed to *other* parties:

- underlying collected by `collectWithdrawFunds` at `stopEpoch` for pending normal withdraw claims [6](#0-5) 
- `defaultRecoveryReserve` backing post-default claims [7](#0-6) 
- prefunded instant cash tracked implicitly via `_defaultPrefundedInstantReserve` [8](#0-7) 

Nothing in the claim path distinguishes "this receipt's funded slice" from the aggregate balance, so any unfunded instant receipt is paid out of funds earmarked for someone else — the exact "escape the intended directory" analog.

### Impact Explanation
Direct theft/insolvency: an attacker holding tranche tokens requests a withdraw during a buffer phase when the APR has dropped by more than `instantWithdrawAprDelta`, receives an instant receipt, and immediately calls `claimInstantWithdrawRequest` before the borrower/CDO funds the instant queue. The payout is drawn from underlying reserved for other users' funded withdraw receipts or default-recovery reserve, causing a shortfall of equal size for the rightful claimants (the last claimants' transactions revert or the reserve is depleted).

### Likelihood Explanation
Requirements are modest: the attacker only needs tranche tokens (a KYC-passing lender) and an APR drop exceeding `instantWithdrawAprDelta` — a normal market event, not privileged action. The window is between the attacker's `requestInstantWithdraw` and the honest funding call `collectInstantWithdrawFunds`, plus any moment the vault holds reserve funds. Note residual uncertainty: I could not read the body of `_transferFundedClaim` to confirm it performs no funded-reserve bookkeeping; if it reverts when `pendingInstantWithdraws` is unfunded or tracks a separate funded counter, the exploit fails. The visible code shows only aggregate `pendingInstantWithdraws` accounting, with no per-claim funded flag.

### Recommendation
Track funded instant liquidity explicitly (e.g., a `fundedInstantWithdraws` counter increased in `collectInstantWithdrawFunds`), and in `claimInstantWithdrawRequest` cap the payout to `min(receipt, fundedInstantWithdraws - alreadyClaimed)` or record per-user funded amounts. Alternatively gate instant claims on `epochNumber` progression like `_claimFundedWithdrawRequest` does, and exclude `defaultRecoveryReserve` from the payable balance.

### Proof of Concept
Foundry fork outline (based on `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// setup: user1 deposits AA, epoch 0 runs and stops normally.
// 1) Attacker deposits AA during buffer, owner lowers unscaledApr below
//    lastEpochApr - instantWithdrawAprDelta.
// 2) Epoch 1 stops: collectWithdrawFunds pulls underlying into the vault
//    funding user1's pending withdraw receipt (vault now holds underlying).
// 3) Attacker calls cdoEpoch.requestWithdraw(0, AAtranche); the APR-delta
//    branch mints an instant receipt via requestInstantWithdraw.
// 4) BEFORE any collectInstantWithdrawFunds call, attacker calls
//    cdoEpoch.claimInstantWithdrawRequest(); _transferFundedClaim pays out
//    of the vault balance that belongs to user1's funded receipt.
// 5) user1's claimWithdrawRequest() now reverts/underpays by the stolen amount.
```

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
```

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
```

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
```
