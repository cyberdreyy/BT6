### Title
Coordinator never removes a signer's stale rejection weight when the signer later switches to Accept, causing a spurious `SignersRejected` liveness wedge - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The mining coordinator's StackerDB listener tallies `total_weight_approved` and `total_weight_rejected` per block independently, gated by two different sets (`gathered_signatures` vs `responded_signers`). When a signer first rejects and later reconsiders and accepts the same block — a flow the protocol explicitly supports — the signer's weight is added to `total_weight_approved` but never removed from `total_weight_rejected`. The two tallies then double-count that signer's weight, and the miner can spuriously conclude the block is globally rejected even though the up-to-date, real vote count would have reached the 70% approval threshold.

### Finding Description
In `handle_signer_message` (the `SignerMessageV0::BlockResponse` handling in `stacks-node/src/nakamoto_node/stackerdb_listener.rs`):

- On `BlockResponse::Rejected` (lines 486-518): `total_weight_rejected` is incremented, gated by `block.responded_signers.insert(slot_id)` (only true the first time this slot responds at all).
- On `BlockResponse::Accepted` (lines 386-465): `total_weight_approved` is incremented, gated by a *different* guard: `!block.gathered_signatures.contains_key(&slot_id)`. It then unconditionally inserts into both `gathered_signatures` and `responded_signers`.

Because the two increments are guarded by two different, non-exclusive sets, a signer that rejects then later accepts the same block satisfies both guards on its respective message: the `responded_signers.insert` returns `true` on the reject (weight added to `total_weight_rejected`), and later `gathered_signatures.contains_key` is still `false` on the accept (weight added to `total_weight_approved`). Nothing in the code ever subtracts the stale rejection weight. This is exactly the fee-report bug class: two conditions that should be mutually exclusive (or reconciled) each independently trigger their own accumulation, so a single actor's contribution is double-booked across both totals instead of the code enforcing "the current, single, correct" state per signer.

The reverse direction (accept, then reject) is correctly guarded — `responded_signers.insert` on the reject branch returns `false` once the signer already responded via accept, so no double-count occurs there. Only the reject→accept direction is broken.

Signers are documented to legitimately reconsider and flip a rejection into an acceptance for "reconsiderable" reject reasons (see `stacks-signer/CHANGELOG.md:180`, "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected"), so this is a reachable, non-adversarial flow, made worse if an adversarial signer deliberately flip-flops.

### Impact Explanation
This breaks the equality the coordinator relies on ("aggregated rejection weight reflects the current vote of each signer") in `signer_coordinator.rs`:

```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    // ... return Err(NakamotoNodeError::SignersRejected { .. })
} else if block_status.total_weight_approved >= self.weight_threshold {
    // ... proceed to push
}
```
(`stacks-node/src/nakamoto_node/signer_coordinator.rs:509-541`)

Because a stale rejection weight from a signer who has actually switched to Accept is never purged, `total_weight_rejected` can be permanently inflated above the blocking-minority threshold even after that signer (and potentially all signers) truly accept the block, causing the coordinator to give up on a validly, fully-signed block (`SignersRejected`), forcing the miner to abandon and rebuild the tenure. This is a liveness wedge for block production reachable by a single signer's ordinary rejection→reconsideration flow (no majority collusion required — only enough weight from flip-flopping signer(s) to cross the ~30% blocking-minority mark, which can be a single large-weight signer). It does not corrupt on-chain consensus itself (the chain's actual acceptance is still governed by cryptographic signature verification in `verify_signer_signatures`, `stackslib/src/chainstate/nakamoto/mod.rs:1097-1190`), but it degrades the coordinator's decision quality and can repeatedly stall mining/block production.

### Likelihood Explanation
Reachable without any privileged access: this only requires a normal signer, following the documented "reconsider a rejected block" flow, to send `Rejected` then later `Accepted` for the same block hash while gossiping over StackerDB — a message pattern within the intended protocol. No majority collusion, secret keys, or auth tokens are needed; a single signer with sufficient weight (or several together) is enough to trip the blocking-minority threshold check.

### Recommendation
Track a single per-slot vote state (e.g., a `HashMap<u32, Vote>` recording the signer's current decision) instead of two independently-guarded sets/counters. When a signer's response changes from Rejected to Accepted (or vice versa), subtract the stale weight from the old tally before adding it to the new one, mirroring the approach already implemented on the signer side (`stacks-signer/src/signerdb.rs`, see `reject_then_accept`/`accept_then_reject` tests at lines 3234-3298) where a later signature explicitly clears any prior rejection record for that signer/block.

### Proof of Concept
1. Miner proposes block B; coordinator's `blocks` map creates `BlockStatus` for B with `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight W ≥ blocking minority, e.g. > 30% of total) sends `BlockResponse::Rejected` for B with a reconsiderable reason. `responded_signers.insert(S) == true` → `total_weight_rejected += W`.
3. S reconsiders (per documented reconsideration flow) and sends `BlockResponse::Accepted` for B. `gathered_signatures.contains_key(S) == false` → `total_weight_approved += W`. `gathered_signatures` and `responded_signers` are updated, but `total_weight_rejected` is left unchanged at `W`.
4. Coordinator's status loop (`signer_coordinator.rs:509-513`) sees `total_weight_rejected (W) + weight_threshold > total_weight` (true, since W alone was chosen ≥ blocking minority) and returns `NakamotoNodeError::SignersRejected`, abandoning block B — even though S (and possibly every other signer) has now actually accepted it.
