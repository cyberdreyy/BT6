Based on my research, this specific frontrunning bug class (deploy-then-initialize as two separate, non-atomic transactions where anyone can win the race to call `initialize()`) maps to a concrete analog in Agave's native `system` and `vote` programs, where the "initialize" instruction handler enforces no signature/ownership tie-back to the account's creator.

### Title
Uninitialized System-Nonce / Vote accounts can have their authority hijacked via a frontrun `InitializeNonceAccount` / `InitializeAccount` call - (File: `programs/system/src/system_instruction.rs`, `programs/vote/src/vote_state/mod.rs`)

### Summary
The Agave `system_program`'s `InitializeNonceAccount` instruction and the `vote_program`'s `InitializeAccount`/`InitializeAccountV2` instructions finalize an account's authority (`nonce_authority`, `authorized_voter`/`authorized_withdrawer`) purely based on data supplied in the instruction, without requiring a signature tied to the account's creator, the fee payer that funded it, or the target account itself. As with the OpenQ `initialize()`-frontrunning report, the "deploy" step (`SystemInstruction::CreateAccount`, which allocates space + assigns ownership to the target program) and the "initialize" step are two logically distinct steps that are only atomic by convention (every caller in the codebase happens to bundle them into one `Message`/transaction), not by protocol enforcement. Anyone monitoring the chain for a freshly created, but not-yet-initialized, nonce or vote account can submit their own `InitializeNonceAccount`/`InitializeAccount` transaction first and become the account's authority.

### Finding Description
`initialize_nonce_account` only checks that the account is writable, in `State::Uninitialized`, and rent-exempt — it performs no signer check at all before setting the caller-supplied `nonce_authority`: [1](#0-0) 

The dispatcher for `SystemInstruction::InitializeNonceAccount` likewise requires only 1 instruction account (the nonce account itself, writable) plus the `recent_blockhashes` and `rent` sysvars — no signature requirement on the nonce account, the original creator, or any related identity: [2](#0-1) 

The analogous vote-program path is `vote_state::initialize_account`, which only verifies that the account is uninitialized and that the attacker-supplied `vote_init.node_pubkey` (fully attacker-controlled) is a signer — it does not require the vote account itself, the payer, or any pre-committed identity to sign: [3](#0-2) 

This is dispatched from `vote_processor.rs`'s `InitializeAccount` handler, where instruction account 0 (the vote account) is marked `is_signer: false` in every code path/test that constructs this instruction: [4](#0-3) [5](#0-4) 

All current in-tree callers only avoid this hijack because they bundle `CreateAccount` and `InitializeAccount`/`InitializeNonceAccount` into a single atomic `Message`/transaction (e.g. `vote_instruction::create_account_with_config`, `system_instruction::create_nonce_account`): [6](#0-5) [7](#0-6) 

However, this atomicity is a convention enforced purely at the client/CLI layer, not by the runtime or the instruction handlers themselves. Nothing in `system_processor.rs` or `vote_processor.rs` rejects an `InitializeNonceAccount`/`InitializeAccount` instruction submitted in its own standalone transaction against a target account that was created (funded, owned by the correct program, correctly sized) by an earlier, separate transaction.

### Impact Explanation
If any account-creation flow (custodial wallet infrastructure, staged/offline signing, retried transactions, hardware-wallet multi-step flows, or any future tooling) ever separates `CreateAccount` from `InitializeNonceAccount`/`InitializeAccount` into two transactions, an unprivileged attacker who observes the first transaction land can race a second transaction naming themselves as `nonce_authority` (nonce case) or `authorized_voter`/`authorized_withdrawer` (vote case). Once initialized, `AccountAlreadyInitialized`/`InvalidAccountData` blocks the legitimate owner from ever initializing it, and the attacker now holds the authority needed to drain the account's rent-exempt lamports via `WithdrawNonceAccount` or vote-account `Withdraw`, i.e., unsigned fund movement by an entity with no relationship to the account's creator or funder.

### Likelihood Explanation
Likelihood is limited because every current codebase caller of these instructions constructs `CreateAccount` + `Initialize*` inside one atomic `Message` signed together, which prevents this race in the officially shipped flows. The vulnerability is a latent protocol-level gap (missing defense-in-depth at the instruction-handler level) rather than an actively exploitable path in the shipped CLI/validator today; it becomes concretely exploitable only if any current or future flow (in-tree or third-party) ever splits account creation and initialization across separate transactions.

### Recommendation
Add a defense-in-depth check in `initialize_nonce_account` (`programs/system/src/system_instruction.rs`) and `vote_state::initialize_account`/`initialize_account_v2` (`programs/vote/src/vote_state/mod.rs`) requiring that either the target account itself, or a signer whose pubkey matches an identity bound at account-creation time, must sign the initialize instruction — removing reliance on client-side atomicity as the sole protection.

### Proof of Concept
1. Victim submits `system_instruction::create_account(payer, nonce_pubkey, lamports, Nonce::State::size(), &system_program::id())` as transaction T1 (requires `nonce_pubkey` keypair to sign, since it is a fresh account).
2. T1 lands on-chain; the account is now owned by `system_program`, rent-exempt, `State::Uninitialized`.
3. Before the victim's follow-up `SystemInstruction::InitializeNonceAccount(victim_authority)` transaction (T2) lands, attacker observes `nonce_pubkey` on-chain and submits their own transaction T2' containing `SystemInstruction::InitializeNonceAccount(attacker_authority)` targeting the same `nonce_pubkey`, paid for by the attacker's own fee payer, with **no signature from `nonce_pubkey` or the victim required** — see `initialize_nonce_account` at `programs/system/src/system_instruction.rs:163-211` and `system_processor.rs:448-467`.
4. If T2' lands first, `nonce_pubkey`'s state becomes `State::Initialized(Data { authority: attacker_authority, .. })`; the victim's later T2 fails with `InstructionError::InvalidAccountData` (already initialized).
5. Attacker, as `attacker_authority`, later calls `SystemInstruction::WithdrawNonceAccount` to drain the account's lamports.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }

/// Initialize the vote_state for a vote account
/// Assumes that the account is being init as part of a account creation or balance transfer and
/// that the transaction must be signed by the staker's keys
pub fn initialize_account<S: std::hash::BuildHasher>(
    vote_account: &mut BorrowedInstructionAccount,
    target_version: VoteStateTargetVersion,
    vote_init: &VoteInit,
    signers: &HashSet<Pubkey, S>,
    clock: &Clock,
) -> Result<(), InstructionError> {
    VoteStateHandler::check_vote_account_length(vote_account, target_version)?;
    let versioned = vote_account.get_state::<VoteStateVersions>()?;

    if !versioned.is_uninitialized() {
        return Err(InstructionError::AccountAlreadyInitialized);
    }

    // node must agree to accept this vote account
    verify_authorized_signer(&vote_init.node_pubkey, signers)?;

    VoteStateHandler::init_vote_account_state(vote_account, vote_init, clock, target_version)
}
