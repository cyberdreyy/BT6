### Title
RPC token-account decimal/extension data is sourced from an unverified mint account, allowing wrong-token misreporting of `jsonParsed` token balances - ([File: rpc/src/parsed_token_accounts.rs])

### Summary
The bug report's core pattern — a verification routine that omits the token/mint identity from the data it trusts, letting an attacker substitute a different token's parameters — has a direct analog in the Agave RPC JSON-parsed token-account decoding path. `get_mint_owner_and_additional_data` fetches whatever account currently lives at the `mint` pubkey embedded in a token account's raw bytes and blindly uses its decimals/extension config to render the account's UI amount, without verifying that mint account is actually owned by the same token program as the token account being displayed.

### Finding Description
`get_parsed_token_account` / `get_parsed_token_accounts` in `rpc/src/parsed_token_accounts.rs` extract the mint pubkey directly out of the token account's raw data via `get_token_account_mint`, then resolve additional formatting data for that mint via `get_mint_owner_and_additional_data`: [1](#0-0) 

This function fetches the mint account from the bank and unconditionally returns `(*mint_account.owner(), mint_data)` — the owner (token-program id) of whatever account currently occupies that address — with **no check that this owner matches the token program that actually owns the token account** being parsed. The decimals/`InterestBearingConfig`/`ScaledUiAmountConfig` extracted from that mint are then fed into `encode_ui_account` → `parse_token_v3`/`token_amount_to_ui_amount_v3` to compute the `uiAmount`/`uiAmountString` returned to RPC clients: [2](#0-1) [3](#0-2) 

This is called from multiple unprivileged JSON-RPC and pubsub surfaces:
- `getProgramAccounts` (jsonParsed) and `getTokenAccountsByOwner`: [4](#0-3) [5](#0-4) 
- Program-account subscriptions: [6](#0-5) 

Critically, the codebase demonstrates that the project is aware this exact check is required: the SVM's own token-balance collector (used for `preTokenBalances`/`postTokenBalances` in transaction status) explicitly guards against this class of confusion by rejecting any mint whose owner does not match the token account's own program: [7](#0-6) 

Note line 188: `if *mint_account.owner() != program_id { return None; }`. The RPC token-account decoding path in `parsed_token_accounts.rs` has no equivalent check, creating an inconsistency between the two "same-conceptual-data" code paths, exactly analogous to how `MerkleDistributor.verifyClaim()` omitted the token identity from its trust boundary while other parts of that system assumed it was bound.

### Impact Explanation
Because the mint account is re-resolved fresh from the bank at query time by address only (not validated against the token account's real owning program), if the address that a token account's `mint` field points to is later reoccupied by an unrelated account (e.g., an SPL Token-2022 mint with a completely different `decimals` value and/or `InterestBearingConfig`/`ScaledUiAmountConfig` extension, achievable through legitimate account-closing and re-creation flows since mint accounts are ordinary keypair addresses, not PDAs enforced to be permanently owned by one program), any RPC/pubsub client requesting `jsonParsed` encoding for that stale token account will receive a UI-amount computed with the wrong decimals/scaling — i.e., wrong account data returned by a read-only query, matching the "wrong-slot/fork/account data returned" and "decoder ... misreporting" impact buckets. Wallets, exchanges, and bots that trust the RPC's computed `uiAmount`/`uiAmountString` (rather than doing raw-amount math themselves) could display or act on an incorrect balance for a token account.

### Likelihood Explanation
No validator/operator privilege is required — any user can drive this purely by making standard `getProgramAccounts`, `getTokenAccountsByOwner`, or `programSubscribe` (jsonParsed) calls against a token account whose mint address has been vacated and reoccupied by a differently-configured mint (a legitimate, permissionless operation using close-authority/mint-close extensions and normal account creation). It requires a specific address-reuse precondition rather than being exploitable against arbitrary accounts, so likelihood is moderate rather than trivial, but the underlying missing check is unconditional and reachable through pure RPC/pubsub read paths.

### Recommendation
In `get_mint_owner_and_additional_data` (and any other call site deriving `SplTokenAdditionalDataV2` for display), verify that the resolved mint account's owner matches the actual owning program of the token account being decoded before using its decimals/extension data, mirroring the check already implemented in `SvmTokenInfo::unpack_token_account` (`svm/src/transaction_balances.rs:188`). If the owners do not match, the RPC should fail to attach additional data (falling back to raw/base64 encoding or an error) rather than silently using mismatched decimals/extensions.

### Proof of Concept
1. Create a Token-2022 mint `M` with the `MintCloseAuthority` extension and some decimals `d1`.
2. Create a Token-2022 token account `A` with `mint = M` and a nonzero balance.
3. Using the close authority, close mint `M` (its address becomes empty/system-owned).
4. Recreate a new mint at the same address `M`, this time as an SPL Token (v3) mint (or Token-2022 with `ScaledUiAmountConfig`/different decimals `d2 != d1`).
5. Call `getTokenAccountsByOwner` or `getProgramAccounts` with `encoding: "jsonParsed"` for account `A`.
6. Observe that `get_mint_owner_and_additional_data` resolves `M`'s *new* decimals/extension config and `parse_token_v3` computes `uiAmount`/`uiAmountString` for `A` using the wrong (unrelated) mint's parameters — a decoder misreport of `A`'s actual token balance, with no ownership cross-check ever performed.

pub fn get_parsed_token_accounts<I>(
    bank: Arc<Bank>,
    keyed_accounts: I,
) -> impl Iterator<Item = RpcKeyedAccount>
where
    I: Iterator<Item = (Pubkey, AccountSharedData)>,
{
    let mut mint_data: HashMap<Pubkey, AccountAdditionalDataV3> = HashMap::new();
    keyed_accounts.filter_map(move |(pubkey, account)| {
        let additional_data = get_token_account_mint(account.data()).and_then(|mint_pubkey| {
            mint_data.get(&mint_pubkey).cloned().or_else(|| {
                let (_, data) = get_mint_owner_and_additional_data(&bank, &mint_pubkey).ok()?;
                let data = AccountAdditionalDataV3 {
                    spl_token_additional_data: Some(data),
                };
                mint_data.insert(mint_pubkey, data);
                Some(data)
            })
        });

        let maybe_encoded_account = encode_ui_account(
            &pubkey,
            &account,
            UiAccountEncoding::JsonParsed,
            additional_data,
            None,
        );
        if let UiAccountData::Json(_) = &maybe_encoded_account.data {
            Some(RpcKeyedAccount {
                pubkey: pubkey.to_string(),
                account: maybe_encoded_account,
            })
        } else {
            None
        }
    })
}

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

impl SvmTokenInfo {
    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,

        let program_id = *account.owner();
        let generic_token::Account {
            mint,

            return None;

        Some(Self {
            account_index: index.try_into().ok()?,
            mint,
            amount,
            owner,
            program_id,
            decimals,
        })
