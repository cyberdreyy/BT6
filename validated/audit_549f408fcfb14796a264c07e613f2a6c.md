### Title
Signer-side tenure-duplicate-block guard (`DuplicateBlockFound`) relies solely on local, non-durable `SignerDb` state and is lost on restart/fresh join, allowing a replayed competing tenure-change block to be signed twice for the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` is the only signer-side check that prevents a signer from signing a second "first block" for a tenure that has already been globally accepted by the network, and it depends entirely on a `SELECT` against the signer's local `SignerDb::get_last_globally_accepted_block` record. This record is populated only when the local signer itself observes/records a globally-accepted block for that tenure; it is never re-derived from the stacks node or from `StackerDB` `StateMachineUpdate` chunks on signer restart or fresh join, so a signer that restarts with a fresh/emptied DB and receives a gossiped, previously-rejected competing tenure-change proposal for that tenure will treat it as the tenure's first block and sign it.

### Finding Description
The equality being enforced is: *the number of first-blocks a given signer will sign for a given (tenure, height) is at most one*, and this must hold even across a signer restart. The enforcement point is: [1](#0-0) 

This check queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — a purely local SQLite lookup — and only rejects with `RejectReason::DuplicateBlockFound` if that local row exists. No other check in `validate_tenure_change_payload` guards against a second, different tenure-change block for the same tenure: `check_tenure_change_confirms_parent` validates the *parent* tenure's last block, not the current tenure, and `check_parent_tenure_choice` validates parent-tenure selection, not same-tenure duplication. [2](#0-1) 

On signer startup/restart, only lightweight `StateMachineUpdate` chunks are re-hydrated from `StackerDB` into `SignerDb`; the actual accepted-block records (`blocks` table, which backs `get_last_globally_accepted_block`) are not refetched from the node or reconstructed from peer state: [3](#0-2) 

The `stacks-node` integration test `signer_loads_stackerdb_updates_on_startup` explicitly documents and exercises this asymmetry — clearing the signer's DB state and confirming the signer can still sign later blocks by reloading state-machine updates from `StackerDB`, but with no equivalent reload of the tenure-block equivocation guard: [4](#0-3) 

Exploit flow: (1) a miner (attacker or the legitimate tenure winner) produces two competing tenure-change block proposals for the same tenure — block A (later gets majority signatures) and block B (a validly miner-signed but displaced/`DuplicateBlockFound`-rejected proposal, both satisfying the `miner_pkh` check in `check_proposal` since they share the sortition winner's key). (2) The attacker (an unprivileged party who can gossip already-observed, validly-signed `StackerDB` chunks) captures and later replays block B's `BlockProposal`/`StackerDB` chunk to a target signer whose local `SignerDb` has no record of tenure X (because it restarted with a fresh/reset DB, or is a freshly-joined signer). (3) `check_proposal` → `validate_tenure_change_payload` → `get_last_globally_accepted_block` returns `None` locally → the `DuplicateBlockFound` branch is skipped → the signer signs block B, even though the majority of the signer set already finalized block A for that same tenure/height.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property explicitly called out as Critical/High in scope: a restart-induced loss of local history causes the signer to sign a second, conflicting block for a tenure/height that is already finalized elsewhere in the network. Any signer whose weight is added to block B's signature set, combined with weight already on block A, produces two independently, validly-signed blocks for the same tenure — a chain-safety violation (conflicting finalized state), not merely a liveness issue. The attack is repeatable against any signer instance that restarts with a wiped/absent local block history (including brand-new signers joining a reward cycle) as long as a rejected competing proposal for that tenure exists and can be gossiped.

### Likelihood Explanation
Preconditions are modest and attacker cost is low: the attacker needs (a) access to a previously-broadcast, validly signed competing tenure-change `BlockProposal`/`StackerDB` chunk for a tenure that was ultimately decided in favor of a different block, and (b) the ability to gossip that chunk to a target signer after that signer's local `SignerDb` history for the tenure has been lost (restart with reset/rebuilt DB, disk issue recovery, or a fresh signer joining the network). No majority-signer collusion, no auth token, and no privileged/local access to the signer host is required — only "craft BlockProposals and gossip StackerDB messages a signer consumes," which is within the defined attacker capability. The bug is deterministic given the precondition (missing local row ⇒ guard always skipped), making it reliably repeatable whenever the precondition is met.

### Recommendation
Do not rely solely on local, potentially-lost `SignerDb` state for the tenure-duplicate-block guard. On signer startup (and periodically), the signer should reconstruct or verify the globally-accepted-block record for the active/last tenures by querying the stacks node (e.g., via the node's canonical tenure/block info endpoints) rather than trusting an empty local table as "no prior signature exists." Alternatively, persist the `blocks`/equivocation table in a way that survives restarts independent of other reset operations, and require the signer to complete a mandatory reconciliation step against the node's chain view before accepting any tenure-change proposal after a restart or fresh join.

### Proof of Concept
Rust test plan (in `stacks-signer`, chainstate v1 test module):
1. Build a `SignerDb` at a temp path; insert a globally-accepted block A with `consensus_hash = CH_X` via the normal block-insert path so `get_last_globally_accepted_block(&CH_X)` returns `Some(A)`.
2. Call `SortitionsView::check_proposal` with a second block B (`consensus_hash = CH_X`, different `signer_signature_hash`, valid `miner_pkh`/tenure-change payload) and assert it returns `Err(RejectReason::DuplicateBlockFound)` — confirming the guard works pre-restart.
3. Simulate a restart: drop the `SignerDb` handle, delete/rebuild the DB file (or clear only the `blocks` table) to model a wiped/fresh-join signer, and re-open a fresh `SignerDb` at the same path — do not reload block A's record (mirroring that only `StateMachineUpdate` chunks are reloaded on real signer startup, not block records).
4. Re-run `check_proposal`/`validate_tenure_change_payload` with the same block B against the fresh `SignerDb`; assert `get_last_globally_accepted_block(&CH_X)` now returns `None` and the call returns `Ok(())` (acceptance) instead of `DuplicateBlockFound` — demonstrating the equivocation guard is lost.
5. Assert the equality violation directly: count of "blocks this signer will sign at (CH_X, height)" was 1 before the simulated restart and became 2 after, proving the uniqueness invariant does not hold across restart/fresh-join.
