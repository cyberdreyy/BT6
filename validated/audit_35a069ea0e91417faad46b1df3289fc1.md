### Title
APR0 withdrawal interest is not reserved before `stopEpoch`, causing an avoidable borrower default - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
In programmable-borrower APR0 mode, `epochPendingWithdraws` reserves only the principal amount of pending withdrawals recorded at epoch start, while APR0 receipt interest is added to `pendingWithdraws` immediately before the borrower is asked for liquidity. [1](#0-0) [2](#0-1)  A KYC-passing lender can create an APR0 withdrawal receipt, after which the honest borrower may draw all nominally free liquidity and leave no cash backing for the receipt's epoch-end interest. [3](#0-2) [4](#0-3)  The resulting `transferFrom` failure is handled as a hard borrower default even though the borrower remains solvent and has only exercised the protocol's permitted borrowing capacity. [5](#0-4) [6](#0-5) 

### Finding Description
`IdleCDOEpochVariant.startEpoch` passes the current `IdleCreditVault.pendingWithdraws` value to `ProgrammableBorrower.onStartEpoch`, and `ProgrammableBorrower` stores that exact value as `epochPendingWithdraws`. [7](#0-6) [1](#0-0)  For an APR0 request, `IdleCreditVault.requestWithdraw` initially adds only the post-fee principal to `pendingWithdraws` and records the user's principal in `apr0TotalPrincipal`. [8](#0-7) [9](#0-8) 

During the epoch, `availableToBorrow` computes free liquidity as current cash plus vault assets minus only the static principal reserve. [3](#0-2)  Consequently, the borrower can call `borrow(0)` and remove every asset above that principal amount, including assets that will be needed to pay APR0 receipt interest at epoch end. [10](#0-9) 

At `stopEpoch`, `prepareStopEpochWithApr0` calculates the APR0 users' pro-rata share of realized epoch interest and mutates `pendingWithdraws` upward before the CDO calculates the amount to pull. [11](#0-10) [12](#0-11)  In minted-interest mode the CDO does not pull ordinary epoch interest as cash, so the only amount requested from the programmable borrower is the newly increased pending-withdrawal amount. [13](#0-12) [5](#0-4) 

`settleBorrowerInterest` only moves accrued borrower interest from the accrued bucket to debt and does not transfer any underlying from the borrower. [14](#0-13)  Therefore, newly accrued contractual interest cannot supply the missing cash for an APR0 withdrawal receipt unless the borrower independently repays before `stopEpoch`. [15](#0-14) [16](#0-15) 

### Impact Explanation
The invariant that matured withdrawal receipts are fully cash-backed at epoch settlement is broken. [3](#0-2) [2](#0-1)  If the borrower draws all free liquidity, the deficit equals the APR0 claimants' allocated net interest minus any retained vault gain that remains in the programmable borrower. [17](#0-16) [18](#0-17) 

The failed pull triggers `_handleBorrowerDefault`, pauses the CDO, ends the epoch, and prevents new withdrawal requests until the default-recovery process is completed. [6](#0-5) [19](#0-18)  All active LPs and pending receipt holders then depend on `finalizeDefaultRecovery`, so even solvent borrowers and unaffected LPs have funds frozen until recovery is supplied and finalized. [20](#0-19) 

The loss is quantifiable per epoch as `shortfall = apr0NetInterest - retainedVaultGain` whenever that value is positive, where `apr0NetInterest` is the amount added to `pendingWithdraws` at line 535 and `retainedVaultGain` is the increase in the borrower's remaining vault assets. [21](#0-20) [22](#0-21) 

### Likelihood Explanation
The attack requires an APR0 programmable-borrower pool, a positive epoch yield, and a KYC-passing lender who requests withdrawal before the epoch starts. [23](#0-22) [24](#0-23)  The borrower does not need to act maliciously because `borrow(0)` is an intended operation that draws all currently available liquidity after subtracting only the stale principal reserve. [25](#0-24) [10](#0-9) 

Existing guards do not prevent the sequence: normal withdrawal requests are already closed once the epoch is running, `defaultRecoveryFinalized` is not active, and `epochPendingWithdraws` is never updated when APR0 interest accrues. [26](#0-25) [27](#0-26)  The liquidity check in `onStopEpoch` compares the new required amount only against current vault assets and then lets the CDO's subsequent transfer fail into the default path. [28](#0-27) [5](#0-4) 

### Recommendation
Reserve the future APR0 receipt interest as it accrues, rather than reserving only its request-time principal. [1](#0-0) [2](#0-1)  For example, maintain a dynamic `apr0PendingInterestReserve` in `availableToBorrow`, update it from realized borrower/vault yield, or conservatively cap borrower draws using a maximum possible APR0 interest amount. [3](#0-2) 

Alternatively, `onStopEpoch` should explicitly treat any shortfall in the mutated pending-withdrawal amount as a required borrower repayment before returning success, instead of allowing the later CDO transfer to become a default. [29](#0-28) [30](#0-29)  A regression test should assert that `availableToBorrow` never lets the borrower draw liquidity needed for both APR0 principal and its allocated epoch interest. [31](#0-30)

```solidity
function testApr0WithdrawInterestIsNotReservedAndCausesDefault() external {
    uint256 amount = 10_000 * oneScale;
    address lp = makeAddr("apr0-attacker");

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // KYC-passing APR0 LP deposits and requests a normal withdrawal in the buffer.
    _depositWithUser(lp, amount, true);
    vm.prank(lp);
    uint256 receiptPrincipal = cdoEpoch.requestWithdraw(0, address(aaTranche));

    // The programmable borrower reserves only the request-time principal.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    uint256 reservedPrincipal = programmableBorrower.epochPendingWithdraws();
    assertEq(reservedPrincipal, strategy.pendingWithdraws());
    assertEq(reservedPrincipal, receiptPrincipal);

    // Honest configured borrower draws every asset the stale reserve says is free.
    vm.prank(revolvingBorrower);
    programmableBorrower.borrow(0);
    assertGt(programmableBorrower.borrowerPrincipal(), 0);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 poolInterest = programmableBorrower.totalInterestDueNow();
    uint256 vaultGain = programmableBorrower.vaultInterestAccrued();
    assertGt(poolInterest, 0);

    uint256 pendingFees = cdoEpoch.pendingWithdrawFees();
    uint256 apr0Principal = strategy.apr0TotalPrincipal();
    uint256 totalPrincipalForSplit = cdoEpoch.getContractValue() + apr0Principal;
    uint256 apr0GrossInterest =
        (poolInterest - pendingFees) * apr0Principal / totalPrincipalForSplit;
    uint256 apr0NetInterest =
        apr0GrossInterest - apr0GrossInterest * cdoEpoch.fee() / 100_000;

    // The retained vault gain does not cover receipt interest because borrower
    // interest was removed from the programmable borrower as a draw.
    assertGt(apr0NetInterest, vaultGain);

    uint256 pendingBefore = strategy.pendingWithdraws();
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertGt(strategy.pendingWithdraws(), pendingBefore);
    assertTrue(cdoEpoch.defaulted());
    assertFalse(cdoEpoch.isEpochRunning());
    assertFalse(programmableBorrower.epochAccountingActive());
}
```
