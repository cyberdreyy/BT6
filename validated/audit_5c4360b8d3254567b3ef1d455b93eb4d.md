### Title
Authentication middleware leaks raw internal/database errors to unauthenticated callers via `AuthenticateExternalInitiator` - (File: core/web/auth/auth.go)

### Summary
The multi-method `Authenticate` gin middleware only continues trying subsequent authentication methods when a method returns exactly `auth.ErrorAuthFailed`; any other error short-circuits the chain and is returned verbatim to the caller in the HTTP response body. `AuthenticateExternalInitiator` only normalizes `sql.ErrNoRows` to `auth.ErrorAuthFailed`, but wraps and returns any other datastore error unmodified, which an unauthenticated client can trigger.

### Finding Description
`Authenticate` iterates over the configured `authMethod`s and stops as soon as a non-`ErrorAuthFailed` error is returned: [1](#0-0) 

`AuthenticateExternalInitiator` looks up the external initiator record using attacker-controlled request headers (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`) and only maps `sql.ErrNoRows` to the generic `auth.ErrorAuthFailed`; every other error from the datastore (e.g. a Postgres `value too long for type character varying(n)` error triggered by an oversized `AccessKey` header, or a transient DB error) is wrapped with `"finding external initiator"` context and returned as-is: [2](#0-1) 

`FindExternalInitiator` passes the header value directly into a parameterized query, so a header value that is oversized or otherwise triggers a driver/database-level error (rather than "no rows") will propagate: [3](#0-2) 

Because `Authenticate` treats any error other than `auth.ErrorAuthFailed` as terminal, this raw wrapped error is what gets abort-returned to the client with HTTP 401, exposing internal datastore error text (e.g. driver/DB error strings, potentially column/schema details) to a completely unauthenticated caller, and preventing the other authentication methods (session/token) in the chain from being attempted for that request.

This mirrors the ERC-4626 report's bug class: a function that is expected to fail gracefully/return a normalized negative result instead propagates a low-level dependency failure, breaking the invariant of the higher-level interface (`totalAssets()` must not revert ↔ auth methods must not surface arbitrary internal errors to unprivileged callers).

### Impact Explanation
An unauthenticated attacker can craft a request (e.g., an oversized `X-Chainlink-EA-AccessKey` header) that causes the datastore lookup to fail with a non-`ErrNoRows` error, resulting in:
- Disclosure of internal error strings/details in the 401 response body to an unauthenticated actor.
- Short-circuiting of the authentication method chain, meaning valid session/token credentials supplied alongside malformed external-initiator headers would not even be evaluated for that request (denial of otherwise-valid auth, not a bypass).

This is an information-disclosure and behavioral issue rather than a full authentication bypass, so severity is limited, but it violates the expectation that authentication middleware normalizes all failure modes and never exposes internal error detail to unauthenticated clients.

### Likelihood Explanation
Any endpoint protected by `Authenticate` with `AuthenticateExternalInitiator` in its method list is reachable by unauthenticated clients by definition (that's the point of the middleware), and crafting a header value likely to exceed a DB column's length or otherwise cause a query-level failure requires no special access — likelihood is moderate, dependent on the exact DB schema constraints and driver error behavior.

### Recommendation
In `AuthenticateExternalInitiator` (and generally in all `authMethod` implementations), treat all datastore/lookup errors uniformly as `auth.ErrorAuthFailed` (logging the underlying error server-side instead of returning it to the client), so the `Authenticate` loop's short-circuit-and-leak behavior cannot be triggered by malformed but unauthenticated input.

### Proof of Concept
1. Send an HTTP request to any route guarded by `Authenticate(..., AuthenticateExternalInitiator)` (e.g. via `web.Router`) with `X-Chainlink-EA-AccessKey` set to a value exceeding the `external_initiators.access_key` column's length constraint.
2. `store.FindExternalInitiator` executes `SELECT * FROM external_initiators WHERE access_key = $1` and the datastore driver returns a non-`sql.ErrNoRows` error (e.g. a "value too long" error). [3](#0-2) 
3. `AuthenticateExternalInitiator` wraps this as `"finding external initiator: <driver error>"` and returns it. [4](#0-3) 
4. `Authenticate`'s loop sees this is not `auth.ErrorAuthFailed`, breaks immediately (skipping any remaining methods), and returns the raw wrapped error text with HTTP 401 to the unauthenticated caller. [5](#0-4)

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
