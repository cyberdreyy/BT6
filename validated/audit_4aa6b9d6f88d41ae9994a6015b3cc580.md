### Title
Signer broadcasts a block signature even when the local state-machine transition to `LocallyAccepted` fails (signing despite failed/terminal state check) - ([File: stacks-signer/src/v0/signer.rs])

### Summary
In the pre-commit → signature path of `Signer::handle_block_pre_commit`, once the pre-commit weight threshold is reached and the conflict checks pass, the signer calls `block_info.mark_locally_accepted(false)`. This call can fail (return `Err`) when `BlockInfo::move_to` rejects the state transition — e.g. the block has already reached a terminal global state. The failure is only logged, guarded by `if !block_info.has_reached_consensus()`, and the code then unconditionally proceeds to construct the signature (`create_block_acceptance`), process it (`handle_block_signature`), and broadcast the acceptance response (`send_block_response`) regardless of whether the state transition actually succeeded. [1](#0-0) 

### Finding Description
This mirrors the Dompdf `registerFont` bug class: a validity/guard check (`mark_locally_accepted`, backed by `BlockInfo::check_state`/`move_to`) fails, the failure path only decides whether to *log* a warning, and the subsequent privileged action (here, signing and broadcasting a block acceptance) executes unconditionally rather than being gated on the outcome of the check.

The documented block lifecycle states that global states are terminal and mutually unreachable ("each global state is unreachable from the other" — `BlockInfo::check_state`), so `mark_locally_accepted` is expected to fail if `block_info.state` is already `GloballyRejected` (or `GloballyAccepted`). [2](#0-1) 

Despite that failure, `create_block_acceptance` (which produces a real ECDSA signature over the block hash) and `send_block_response`/`handle_block_signature` run outside the `if let Err(e) = ...` block, i.e. on both the success and failure branches: [3](#0-2) 

Compare this to the sibling handler in `handle_block_validate_ok`, where a failed `mark_pre_committed` explicitly `return`s (halting further action) unless the block is already `LocallyAccepted` or has reached consensus, and even then it merely re-persists timestamps rather than emitting a fresh signature: [4](#0-3) 

The pre-commit signing path has no equivalent `return` on failure — the "we should not sign" outcome of the state machine is swallowed and the signer signs anyway.

### Impact Explanation
If a block has already been recorded as `GloballyRejected` (via `store_and_process_block_rejection`/peer rejections reaching the 30% blocking threshold) at the moment this signer's own local pre-commit tally crosses 70% (a plausible race since pre-commits and rejections are processed from independent, asynchronously-arriving gossip messages), `mark_locally_accepted` fails the state check, yet the signer still creates and broadcasts a signature `Accepted` response for a block the network has already agreed to reject. This is exactly the "rejection recounted as acceptance" class of impact the scope calls out as Critical: it produces a signer signature on a block whose consensus outcome is (or is becoming) a rejection, undermining the equality between "signed" and "globally validated as accepted."

### Likelihood Explanation
Triggering requires only ordinary gossip timing: a majority of signers is not needed by the attacker; the race is between an honest local pre-commit tally reaching 70% and a `BlockResponse::Rejected` from other signers reaching the 30%-blocking threshold and calling `mark_globally_rejected` on the same `BlockInfo` before this code path runs `mark_locally_accepted`. A single malicious/faulty miner (or network delay) that causes conflicting acceptance/rejection message ordering across signers is sufficient to create the race; no majority collusion or key compromise is required, matching the "one-slot miner plus gossip" threat model in scope.

### Recommendation
Make the acceptance/signature path conditional on the state-machine transition actually succeeding (or on the block already being in `LocallyAccepted`/`GloballyAccepted`), and `return` early — without generating or broadcasting a new acceptance — whenever `mark_locally_accepted` fails due to the block having reached a terminal state such as `GloballyRejected`. This mirrors the existing guard already used for `mark_pre_committed` failures in `handle_block_validate_ok`.

### Proof of Concept
Conceptual sequence (based on code review; not independently executed against a live testnet):
1. Miner proposes block `B` at height `h`. Signer set is split by network delay: some signers deliver `BlockPreCommit`s reaching the local signer's 70% pre-commit tally, while at the same time enough other signers deliver `BlockResponse::Rejected` for `B`, crossing the >30% blocking threshold and causing `store_and_process_block_rejection` to call `block_info.mark_globally_rejected()`, setting `block_info.state = GloballyRejected`.
2. Before this signer observes/records the rejection tally overriding its own view, `handle_block_pre_commit` (stacks-signer/src/v0/signer.rs) proceeds past the conflict checks and calls `block_info.mark_locally_accepted(false)` on the same `BlockInfo` (now `GloballyRejected`). `move_to`/`check_state` rejects the transition and returns `Err`.
3. Because `block_info.has_reached_consensus()` is true (state already `GloballyRejected`), the warning is suppressed at line 1469, and execution falls through unconditionally to lines 1472-1478: the block is re-persisted, `create_block_acceptance` signs it, and `send_block_response` broadcasts a fresh `Accepted` for a block that has already been globally rejected.

Note: I was unable to fetch the exact implementations of `BlockInfo::has_reached_consensus` and `BlockInfo::move_to`/`check_state` (grep found matches only in `signerdb.rs` but the tool budget was exhausted before reading them), so the precise set of states for which `has_reached_consensus()` returns true, and the exact `move_to` transition table, could not be directly confirmed in this session — this should be verified by reading `stacks-signer/src/signerdb.rs` before treating the PoC as fully validated.
