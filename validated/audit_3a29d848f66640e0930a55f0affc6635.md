## Title
Own-tenure conflict guard signs on a stale, only "for now"-fresh conflict when `get_tenure_tip` errors, contradicting the "node unreachable ⇒ keep blocking" safety rule the same function follows everywhere else - (File: stacks-signer/src/v0/signer.rs)

## Summary
`handle_block_pre_commit`'s own-tenure conflict check treats a failed `get_tenure_tip` RPC call as "unconfirmed" and falls through to sign, unlike every other node-query branch in the same conflict-resolution logic (`conflict_still_blocks`, `reorg_permit_stands`, `check_tenure_change_confirms_parent`), which all explicitly keep a conflict blocking when the node cannot be asked. This is the "hardcoded resource-limited primitive fails silently and the caller proceeds as if it succeeded" pattern from the external report, translated to the signer's RPC dependency: an external call the safety property depends on can fail for reasons outside a malicious actor's control (timeouts, transient node unavailability), and the fallback here chooses the unsafe branch (sign) instead of the safe one (refuse).

## Finding Description
`handle_block_pre_commit` in `stacks-signer/src/v0/signer.rs` guards against double-signing by checking whether any previously signed conflicting block still "blocks" a newly-reaching-threshold proposal. For cross-tenure and general conflict staleness, `conflict_still_blocks` (lines 1137–1206) is meticulous: every RPC failure path (`get_sortition_by_burn_hash` error, `get_peer_info` error, `get_tenure_tip` error) returns `true` (conflict still blocks), with an explicit design comment: "Whenever the node cannot be asked, the conflict keeps blocking: that only delays the replacement until the signature goes stale, whereas wrongly signing cannot be taken back" (`docs/signer-flows.md:329-331`).

However, for a **stale** same-tenure conflict (lines 1432–1457), the code calls `stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash)` and on `Err(e)` only logs a warning — "Treating the tenure as unconfirmed" — and falls through the `match` without returning, letting the loop below sign the block: [1](#0-0) 

Compare this to the `Ok(tip)` branch, which explicitly refuses to sign ("Refusing to sign") only when the tip height is at or above the proposed height: [2](#0-1) 

But on an `Err`, the code has no way to know whether the tenure's canonical tip is actually at or above the proposed height — it simply assumes not, and proceeds to `mark_locally_accepted` / sign: [3](#0-2) 

This directly contradicts the invariant documented for the sibling function `conflict_still_blocks`, where every equivalent RPC failure returns `true` and keeps the conflict blocking rather than falling through: [4](#0-3) 

The docs summarize the general design principle that this specific branch violates: [5](#0-4) .

## Impact Explanation
If a signer's stacks-node RPC to `/v3/tenures/tip` is unavailable or errors out (network blip, node restart, overloaded node, or a miner/gossip-timed proposal arriving exactly when the node is between states) at the moment a stale-but-still-real same-tenure conflict exists, the signer will sign a **second, conflicting block in the same tenure** that it should have refused because the node's canonical tip is already at or above the new proposal's height. This breaks the "approved-parent vs canonical" / "one-per-height" equality that the whole conflict-guard subsystem exists to protect: a signer can end up putting two valid signatures over two different blocks that conflict at the same height in the same tenure, which is exactly the double-sign the guard was built to prevent (see the design rationale at `docs/signer-flows.md:274-286`, explaining that this exact own-tenure branch is "the only guard" for that scenario since `DuplicateBlockFound` checks run only at proposal time). This is a signer-safety violation (Critical bucket: "a signer signing an invalid/conflicting block") and is reachable without needing a majority of signers or another signer's key — it only requires a transient RPC failure on this signer's own node coinciding with a stale conflict, a condition entirely outside attacker or majority control (analogous to the report's "smart-contract recipient with insufficient gas" case being outside the sender's control).

## Likelihood Explanation
The trigger condition (an RPC failure to the signer's own node during pre-commit tallying) is plausible in production: node restarts, resource contention, or brief network partitions between signer and node are ordinary operational events, not adversarial actions. Because `handle_block_pre_commit` is invoked repeatedly (on every pre-commit received, including replays), a single transient failure at the moment threshold is crossed is enough; there's no retry-and-recheck before signing occurs in this branch, unlike the safe pattern used elsewhere in the same function.

## Recommendation
Make the `Err` branch of the `get_tenure_tip` call at lines 1449–1455 behave like every other RPC-failure branch in this file: treat "cannot ask the node" as "conflict still blocks" (i.e., `return` from `handle_block_pre_commit` without signing), consistent with `conflict_still_blocks`'s documented invariant. This only delays a legitimate replacement until the stale signature goes stale/is re-evaluated, whereas signing wrongly cannot be undone.

## Proof of Concept
1. Signer A locally accepts (signs) block X at height H in tenure T (`mark_locally_accepted`), recording X as a same-tenure conflict for any future proposal at height ≥ H in T.
2. X's signature ages past `tenure_last_block_proposal_timeout` so the conflict is no longer "fresh" (bypasses the fresh-conflict `return` at line 1420).
3. A new proposal Y at height H (or higher) in tenure T reaches the pre-commit threshold on signer A. `conflicts.iter().any(...)` at line 1432 finds X as a stale same-tenure conflict whose reorg permit does not stand.
4. Signer A calls `stacks_client.get_tenure_tip(T)` to check whether the node's canonical tip in T is already ≥ H (which it is, since X was already signed and, in the realistic case, already pushed/accepted by the node). If this RPC call errors (timeout, node briefly down, connection reset) instead of returning `Ok(tip)`, the code logs "Treating the tenure as unconfirmed" and falls through.
5. Execution reaches `mark_locally_accepted(false)` and signer A signs Y, producing two signed, conflicting blocks (X and Y) at height H within the same tenure T from the same signer. [6](#0-5)
