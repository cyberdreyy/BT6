## Analysis Result

### Title
Attacker-triggered `SortitionsView::reset_view()` silently discards the in-memory `miner_status` invalidation flag, letting a previously-invalidated miner's proposal pass the `InvalidMiner`/`ReorgNotAllowed` gate — ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::check_proposal` maintains an in-memory-only security flag, `SortitionState::miner_status`, that records whether the signer has already deemed the current or last sortition's miner invalid (timed out, or attempted a disallowed tenure reorg). This flag is the *only* gate that blocks further proposals from that miner (`ProposedBy::CurrentSortition` branch checks `sortition.miner_status != Valid`). When a proposal arrives whose `consensus_hash` matches neither the tracked current nor last sortition, `check_proposal` unconditionally calls `self.reset_view(client)`, which re-fetches `cur_sortition`/`last_sortition` from the node and **reconstructs them from scratch via `SortitionState::try_from`, which always sets `miner_status: SortitionMinerStatus::Valid`** — regardless of what verdict had previously been recorded. This is structurally identical to the DOMPurify defect: a fast/alternate code path (`setConfig` skipping `_parseConfig`'s clone-guard ≈ `reset_view` skipping re-derivation of `miner_status`) silently restores a security-relevant piece of state to its permissive default, erasing a protective flag that other code assumed would persist.

### Finding Description
- `SortitionState::try_from` always initializes `miner_status: SortitionMinerStatus::Valid` [1](#0-0) .
- `check_proposal` can mark `self.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock` for two independent reasons: (a) the miner timed out (`is_timed_out`), or (b) the miner attempted a disallowed tenure reorg (`check_parent_tenure_choice` returned `false`) [2](#0-1) .
- This flag is the sole gate for subsequent proposals from that same sortition: `ProposedBy::CurrentSortition(sortition) => if sortition.miner_status != SortitionMinerStatus::Valid { return Err(RejectReason::InvalidMiner) }` [3](#0-2) .
- If a proposal's `consensus_hash` matches neither `cur_sortition` nor `last_sortition`, and `reset_view_if_wrong_consensus_hash` is true, `check_proposal` calls `self.reset_view(client)` and then **recurses on the same block** [4](#0-3) .
- `reset_view` completely overwrites `self.cur_sortition` and `self.last_sortition` with freshly constructed `SortitionState`s (always `Valid`) [5](#0-4) .
- `sortition_state: &mut Option<SortitionsView>` is a single, long-lived structure reused across the signer's entire processing loop for all subsequent block proposals — it is only (re-)created when `None`, e.g., in `check_block_against_local_state` and `handle_block_proposal` [6](#0-5) [7](#0-6) .

Net effect: a single attacker-controlled proposal carrying an unrecognized `consensus_hash` (trivial to craft — any hash that isn't the tracked current/last sortition) forces `reset_view`, which throws away the `InvalidatedBeforeFirstBlock` verdict on the real current/last sortition and replaces it with `Valid`. A follow-up proposal from the miner that was previously invalidated (e.g., for an unauthorized reorg, `ReorgNotAllowed`, or timeout-based `InvalidMiner`) can now pass the `miner_status` gate that was supposed to block it permanently for that sortition's lifetime, because the flag is derived purely in-memory and is not persisted to `SignerDb` (unlike the analogous, deliberately-DB-backed `mark_tenure_superseded`/`is_tenure_superseded` mechanism used elsewhere for a similar "don't forget a sanctioned reorg" problem) [8](#0-7) [9](#0-8) .

Whether the flag is correctly re-derived on the very next `check_proposal` call is not guaranteed: the timeout branch and the parent-tenure/reorg branch are mutually exclusive (`if ... else if let Some(tip) = ...`) and the reorg branch only re-runs the expensive `check_parent_tenure_choice` when the signer's *current* canonical-tip alignment (`consensus_hash_match`/`parent_tenure_id_match`) still looks mismatched [10](#0-9) . If the local canonical tip has moved in the interim (e.g. due to concurrent processing of other proposals/pre-commits), that re-check can be skipped on the pass immediately following the reset, so the original `InvalidatedBeforeFirstBlock` verdict is not necessarily reconstructed before the next proposal from the "should-be-invalid" miner is evaluated.

### Impact Explanation
If the re-derivation does not happen before the next proposal from the previously-invalidated miner arrives, the signer treats that miner as `Valid` and continues normal evaluation (tenure-change / parent-block checks), potentially pre-committing to and ultimately signing a block from a miner whose earlier tenure-choice was already judged improper by this signer — a signer signing a block it had determined was based on a disallowed reorg / an inactive-miner tenure. This falls under the "signer signing an invalid/non-canonical/conflicting block" impact category (Critical), because the equality broken is "a miner this signer has locally judged invalid for the current sortition must not later be treated as valid without the underlying condition changing."

### Likelihood Explanation
The trigger requires only a single, easily-crafted message (a `BlockProposal` with an unrecognized `consensus_hash`) delivered via the normal StackerDB/gossip proposal channel — no majority of signers, no other signer's key, and no node cooperation is needed to *construct* the trigger. It does require the reset to land at a moment where the subsequent re-check does not reproduce the same invalidation (a timing/ordering condition), so likelihood depends on interleaving with other events (concurrent proposals, canonical-tip movement) rather than being deterministic on every attempt. I was not able to fully trace, within the available context, every downstream code path that could re-derive `miner_status` before the next proposal is processed (e.g., all callers of `check_proposal` and all ways `sortition_state` is refreshed elsewhere), so I cannot conclusively prove this is deterministically exploitable end-to-end — this should be validated with an integration test that: (1) drives a miner into `InvalidatedBeforeFirstBlock` via a rejected reorg, (2) sends one proposal with a bogus consensus hash to force `reset_view`, and (3) immediately resubmits the original invalidated miner's block to see whether it is now accepted/pre-committed instead of rejected.

### Recommendation
- Do not reset `miner_status` to `Valid` unconditionally in `reset_view`/`SortitionState::try_from`; either persist the invalidation to `SignerDb` (as is already done for superseded tenures via `mark_tenure_superseded`), or have `reset_view` re-run the full `is_timed_out` / `check_parent_tenure_choice` derivation immediately for the sortition(s) being reconstructed before returning, rather than deferring to the next `check_proposal` call under conditions that may not re-trigger the check.
- Add a regression test mirroring the DOMPurify PoC pattern: invalidate a sortition's miner via `check_parent_tenure_choice` returning `false`, force a `reset_view` via an unrelated bogus-consensus-hash proposal, and assert that a resubmission of the originally invalidated miner's proposal is still rejected.

### Proof of Concept
Conceptual reproduction using the existing test harness patterns already present in `stacks-signer/src/chainstate/tests/v1.rs`/`v2.rs`:
1. Build a `SortitionsView` where `cur_sortition.miner_status` becomes `InvalidatedBeforeFirstBlock` (e.g., drive `check_proposal` on a block whose parent-tenure choice is rejected, per the existing `check_parent_tenure_choice`-driven tests) [11](#0-10) .
2. Call `check_proposal(..., reset_view_if_wrong_consensus_hash = true, ...)` with a block whose `consensus_hash` is neither `cur_sortition.data.consensus_hash` nor `last_sortition`'s — this hits the mismatch branch and triggers `self.reset_view(client)` [4](#0-3) .
3. Resubmit the original (previously-invalidated) miner's proposal to the same `SortitionsView` and observe whether `miner_status` gate (`InvalidMiner`) is bypassed because `reset_view` reset it to `Valid` [3](#0-2) .

This mirrors the existing `check_proposal_refresh` test that already exercises the `reset_view` recursive path (for a benign refresh scenario) and would need to be extended to check for the security-flag loss [12](#0-11) .

    /// Reset the view to the current sortition and last sortition
    pub fn reset_view(&mut self, client: &StacksClient) -> Result<(), ClientError> {
        let CurrentAndLastSortition {
            current_sortition,
            last_sortition,
        } = client.get_current_and_last_sortition()?;

        let cur_sortition = SortitionState::try_from(current_sortition)?;
        let last_sortition = last_sortition
            .map(SortitionState::try_from)
            .transpose()
            .ok()
            .flatten();

        self.cur_sortition = cur_sortition;
        self.last_sortition = last_sortition;
        Ok(())
    }
