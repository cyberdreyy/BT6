## Title
Stale confirmations from removed multisig members are still counted toward the execution threshold, allowing a request to execute with fewer live signers than `num_confirmations` — (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The reported bug describes `remove_validator` deleting a validator from storage without cleaning up the pending redelegation state tied to it, leaving stale state that is later misused. The same class of defect exists in this repository's multisig contracts: when a member is removed via `DeleteMember`/`DeleteKey`, the contract only deletes **requests originated by that member**, but never removes the member's existing **confirmations on requests originated by other members**. Those stale confirmations remain in the `confirmations` map and are still counted by `confirm()` toward `num_confirmations`, so a request can later execute having received fewer confirmations from *current* members than the configured threshold.

### Finding Description
`delete_member` (multisig2) / the `DeleteKey` action handler (multisig) removes:
- requests whose `signer_pk`/`member` equals the removed member (`r.member == member` filter), and
- the `num_requests_pk`/`num_requests_per_member` counter for that member, [1](#0-0) 

but it never inspects the `confirmations: LookupMap<RequestId, HashSet<String>>` map to strip the removed member's entry from *other* requests they had already confirmed. `confirm()` then counts set size directly against `self.num_confirmations` without validating that each confirming identity is still a current member: [2](#0-1) 

The same pattern exists in the older `multisig` contract, where `DeleteKey` only purges requests filtered by `r.signer_pk == pk`, leaving that key's confirmations on other requests intact: [3](#0-2) [4](#0-3) 

This breaks the intended custody binding: `confirmations recorded for a request == approvals from currently authorized members`. After a member is removed, the equality becomes `confirmations recorded > approvals from currently authorized members`, because one or more entries in the confirmation set belong to an identity that is no longer a member.

### Impact Explanation
This matches the Critical impact category: "a multisig request executed below threshold." A transfer, `FunctionCall`, or `AddKey`/`AddMember` request can be executed on behalf of the multisig account with fewer live, currently-authorized confirmations than `num_confirmations` requires, because a stale confirmation from a removed member is still tallied. This directly weakens the authorization boundary the multisig is designed to enforce and can result in unauthorized movement of NEAR funds held by the multisig account.

### Likelihood Explanation
This requires no special privilege beyond being (or having been) a legitimate multisig member at some point — a realistic operational scenario (member rotation, key compromise response, offboarding). Any time a member is removed after having confirmed one or more still-pending, not-yet-executed requests created by other members, the vulnerable state exists. No cooperation from the foundation or a redeploy is needed; it's triggered purely through the documented `add_request`/`confirm`/`DeleteMember` flow.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over `self.confirmations` for all active `request_id`s and remove the departing member's/key's entry from every confirmation set (not just requests they originated), re-checking whether removal now causes any request to have `confirmations.len()` still satisfy the threshold only via then-current members. Alternatively, validate at execution time in `confirm()` that every identity present in the confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Multisig configured with `num_confirmations = 2`, members `{A, B, C}`.
2. Member `B` creates a malicious `Transfer` request (`add_request`), does not confirm it yet — 0 confirmations.
3. Member `A` confirms the request (`confirm`) — confirmations = `{A}` (1 of 2, not yet executed).
4. Members `B`+`C` (or `A` itself if it still has authority) submit and confirm a `DeleteMember { member: A }` request, removing `A` from the multisig. `delete_member` only removes requests where `r.member == A` (i.e., requests A originated) — it does not touch the confirmation entry `{A}` sitting on B's transfer request.
5. Member `C` (now one of only 2 live members besides B) calls `confirm` on the pending transfer request. `confirmations.len() as u32 + 1 = 2 >= num_confirmations (2)` is satisfied using stale confirmation `A` (no longer a member) plus `C`, executing the transfer despite only one currently authorized member (`C`) having approved it in real time.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
