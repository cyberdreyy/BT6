### Title
First-depositor donation inflates AA tranche price and rounds victim deposits to zero shares - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault` prices tranche shares as NAV-per-share with no virtual-share/virtual-asset offset and no decimal gap between tranche tokens and the underlying. `_updateAccounting` measures NAV via `getContractValue`, which includes the raw `token` balance held by the contract, so an unsolicited underlying transfer is booked as a gain and pushed into `priceAA`/`priceBB`. An attacker who is the first depositor can seed a tranche with dust, donate to inflate the tranche price, and cause a subsequent victim's deposit to mint zero shares while the victim's underlyings accrue entirely to the attacker's shares.

### Finding Description
Shares are minted in `_mintSharesAtCurrPrice` as:

```solidity
_minted = _amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche);
```

`contracts/IdleCDOCreditVault.sol:344-348`

The price used is `priceAA`/`priceBB`, recomputed in `_updateAccounting` (called first inside `_deposit`, `IdleCDOCreditVault.sol:200`) from `getContractValue()`, which is `strategyToken + token − unclaimedFees` (`IdleCDOCreditVault.sol:125-128`). Because the raw `token` balance is included, a direct `token.transfer(cdo, X)` before the victim's deposit raises `nav`, is treated as `totalGain` in `_virtualPriceAux` (`IdleCDOCreditVault.sol:306`), and is assigned entirely to the seeded tranche when it is the only class with saved NAV (`_lastNAV == _lastTrancheNAV`, line 321-322). The new price becomes roughly `(1 + donation) / attackerShares`. There is no virtual-shares offset: `_tranchePrice` just returns `oneToken` for empty supply and the stored NAV-per-share otherwise (`IdleCDOCreditVault.sol:422-427`).

Attack sequence in the buffer/running phase of a fresh AA-only vault:

1. Attacker (KYC-passing lender) calls `depositAA(1)`. `priceAA = oneToken`, so they mint `1e18/oneToken` shares and `lastNAVAA = 1` (`IdleCDOCreditVault.sol:355-363`).
2. Attacker transfers `D + 1` underlyings directly to the vault (a "direct token sender" is an allowed unprivileged actor).
3. Victim calls `depositAA(D)`. `_updateAccounting` sees `nav = 1 + (D+1) + (no fees path aside)`, books the donation as AA gain, and sets `priceAA ≈ (D+2)/attackerShares` per share. `_mintSharesAtCurrPrice` computes `D * ONE_TRANCHE_TOKEN / priceAA`, which rounds down to 0 shares.
4. The victim's `D` underlyings are pulled in and counted in `lastNAVAA`; the attacker holds 100% of the tranche supply backed by `1 + (D+1) + D`.
5. Attacker redeems via the normal withdrawal path (`requestWithdraw`/claim in the epoch variant or `withdrawAA`), recovering their donation plus the victim's deposit minus dust.

The attacker's donation is not lost — it is returned on redemption — so net profit is approximately `D` for a cost bounded by gas and the 1-wei seed.

### Impact Explanation
Direct theft of a victim lender's full deposit: the victim receives 0 tranche tokens while their underlyings are socialized into the attacker's share position. Any first-depositor window on a new tranche (newly deployed vault, or a tranche class with zero supply) is exposed; the theft amount is bounded only by the size of the first victim deposit, which the attacker can front-run/select via mempool ordering.

### Likelihood Explanation
Requires being first depositor on an uninitialized tranche and front-running the victim's deposit — both standard conditions for ERC4626-style inflation attacks and both available to any unprivileged KYC-passed lender. `depositAA` has no minimum-mint check and `IdleCDOTranche` uses 18 decimals while `oneToken` tracks underlying decimals, so a donation only slightly larger than the victim deposit suffices. The one mitigation I could not fully rule out is a donation-skim guard: `_managedContractValue` deliberately excludes raw `token` balance (`IdleCDOCreditVault.sol:133-137`) and comments reference skimming unsolicited transfers, but no skim executes inside `_deposit`/`_updateAccounting`/`getContractValue` in this contract, so the raw-token balance does reach `nav` in the accounting path. If the concrete epoch vault (e.g., `contracts/strategies/idle/IdleCreditVault.sol`) sweeps the `token` balance before accounting, this analog is neutralized; that call-order could not be verified within this iteration.

### Recommendation
- Exclude the raw `token` balance from `getContractValue` in the accounting path (use the strategy-token-backed value, consistent with `_managedContractValue`), or skim unsolicited underlying transfers before `_updateAccounting` runs.
- Alternatively/additionally, mint shares against `virtualPrice` computed on managed NAV only, and revert when `_minted == 0` for nonzero `_amount` in `_mintSharesAtCurrPrice`.
- If aligning with the OZ virtual-shares defense, introduce an offset between share and asset precision (e.g., share decimals ≫ underlying) plus asymmetric virtual shares/assets so a donation cannot zero out a deposit.

### Proof of Concept
Foundry fork-style PoC (schematic; assumes no pre-accounting skim in the deployed vault):

```solidity
function test_firstDepositorDonationInflation() public {
    // vault: fresh IdleCDOCreditVault-derived vault, AA deposits enabled,
    // underlying = USDC-like `token` (6 decimals), attacker is KYC'd.
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    deal(token, attacker, 2_000_000e6);
    deal(token, victim,   1_000_000e6);

    // 1. seed tranche with dust
    vm.startPrank(attacker);
    IERC20(token).approve(address(cdo), type(uint256).max);
    cdo.depositAA(1);
    uint256 attackerShares = IERC20(cdo.AATranche()).balanceOf(attacker);
    assertGt(attackerShares, 0);

    // 2. donate just over the victim deposit
    IERC20(token).transfer(address(cdo), 1_000_001e6);
    vm.stopPrank();

    // 3. victim deposit mints zero shares
    vm.startPrank(victim);
    IERC20(token).approve(address(cdo), type(uint256).max);
    uint256 minted = cdo.depositAA(1_000_000e6);
    assertEq(minted, 0);
    assertEq(IERC20(cdo.AATranche()).balanceOf(victim), 0);
    vm.stopPrank();

    // 4. attacker redeems ~entire NAV (donation + victim funds)
    //    via the vault's withdraw path; attacker balance > 2_000_000e6 seed+donation−dust
}
```

Key assertions: `minted == 0` for the victim and the attacker's redeemable value ≈ `1 + donation + victimDeposit`. If step 3 reverts on a skim of the donated balance inside the vault's deposit entry point, the guard holds and the finding does not apply — that branch should be checked against the concrete epoch-vault implementation before reporting.
