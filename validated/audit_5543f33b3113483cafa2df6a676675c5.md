### Title
Liveness griefing: invalid/conflicting block proposals refresh miner-activity timer, delaying fallback to a valid miner - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_latest_block_in_tenure` treats a proposal that *fails* the height/veto check (i.e. an invalid or conflicting/reorg-attempt block) as valid "miner activity" and refreshes `last_activity_time` for that tenure whenever the currently pinned block hasn't been globally signed long enough ago. That activity timestamp is the sole input `check_miner_inactivity`/`is_timed_out` use to decide whether the signer set should fall back from a stalled/malicious current miner to the prior valid one. A one-slot miner (the tenure's active, sortition-winning miner) can therefore keep resetting its own inactivity clock indefinitely by repeatedly gossiping cheap, invalid/non-canonical proposals, without ever producing a block the signer set will actually sign, wedging the signer set into waiting on it.

### Finding Description
`check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-478`) is the shared chainstate check run at proposal time, at validate-ok, and at signing time. When a newly proposed block does not exceed the chain length of the last *signed* block in the tenure (a reorg attempt / stale/conflicting proposal), the function still calls `signer_db.update_last_activity_time` as long as the pinned block's `signed_group` timestamp is either absent or still "fresh" relative to `reorg_attempts_activity_timeout`: [1](#0-0) 

The same activity-refresh path also fires for conflicts with a merely pre-committed (never signed) block: [2](#0-1) 

This `last_activity_time` value is exactly the signal `check_miner_inactivity` / the chainstate `is_timed_out` implementations use to decide whether to time out the current miner and fall back to the prior tenure's miner: [3](#0-2) 

The design intent (per `docs/signer-flows.md`) is to give a legitimately slow miner a grace buffer so temporary network jitter doesn't cause an unnecessary miner switch — this is analogous to the "marketcap read at call start" pattern in the reported bug: a value computed/refreshed by an action is used later as the gating condition for a state transition (here, "should we abandon this miner"), and the action that refreshes it is cheap and repeatable by exactly the party whose behavior the check is trying to police (the current miner). Because *any* conflicting proposal — even one that is stale, non-canonical, or deliberately never going to be signed — refreshes the timer, the current miner (the one party who benefits from staying "active") can grief the fallback mechanism by gossiping a steady trickle of low/no-cost invalid proposals, exactly as the DynamicLiquidTokenConverter owner in the external report could game their own threshold check by manipulating the metric the check depends on.

### Impact Explanation
This is a liveness wedge on the signer set: as long as the current miner keeps emitting conflicting/invalid proposals (which cost it nothing beyond gossip), `is_timed_out` never returns `true`, so `check_miner_inactivity` never falls back to the prior tenure's valid miner via `make_miner_state`. Signers therefore keep waiting on a miner that never produces a signable canonical block, which matches the "High" impact bucket: a signer (here, the whole signer set) wedged into never signing valid blocks because it is perpetually deferring to a miner that is being kept "active" by cheap invalid traffic rather than genuine progress.

### Likelihood Explanation
The trigger requires only the tenure's own miner (the party controlling the one block-production slot for that tenure) plus ordinary StackerDB gossip of `BlockProposal` messages — no majority of signers, no other signer's key, and no auth token are needed. The cost to the attacker is a stream of block proposals that will simply be rejected by `check_latest_block_in_tenure`'s height check; this is explicitly the same low-cost side effect the code comments acknowledge ("count this invalid block proposal towards valid miner activity"), so the mechanism is reachable and repeatable at will by the miner during its own tenure.

### Recommendation
Do not treat rejected/height-losing proposals as unconditional evidence of "activity" for the purposes of the inactivity/fallback timer. Consider bounding how many times, or for how long, a *rejected* proposal from the same miner can refresh `last_activity_time` within a tenure (e.g., only the first N rejections, or only if the miner has ever produced a signed block in this tenure), so a miner cannot indefinitely extend its own window purely by emitting invalid conflicting proposals while never advancing the signed tip.

### Proof of Concept
Not applicable as a runnable exploit in ask-only mode; the code path is walked out above: a tenure's miner that has no globally-signed block yet (`info.signed_group` is `None`) can send an unbounded stream of proposals that fail the `block.header.chain_length <= info.block.header.chain_length` check at `stacks-signer/src/chainstate/mod.rs:395`, each of which unconditionally re-enters the `update_last_activity_time` branch at lines 411-416, resetting the clock that `is_timed_out`/`check_miner_inactivity` (`stacks-signer/src/v0/signer_state.rs:284-316`) consult before ever falling back to the prior miner.
