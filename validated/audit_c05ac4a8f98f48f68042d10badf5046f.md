### Title
Unbounded `underlyingsRequested` in `createWriteOffRequest` lets any tranche holder permanently corrupt protocol-wide `pendingUnderlyings` accounting - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The LDAP-injection analog: an unprivileged user-controlled value (`underlyingsRequested`) is injected, completely unvalidated, into a shared accounting aggregate (`pendingUnderlyings`) that the protocol treats as authoritative pending-recovery input — escaping the intended scope of a single user's escrow entry. The request is permanently unfulfillable, so the injected value is never flushed.

### Finding Description
`createWriteOffRequest` accepts an arbitrary `underlyingsRequested` and adds it verbatim to both the per-user `WriteOffRequest` and the global `pendingUnderlyings` counter (contracts/IdleCreditVaultWriteOffEscrow.sol:97-101). The only cost is depositing a nonzero amount of tranche tokens, which remain refundable via `deleteWriteOffRequest`.

`fullfillWriteOffRequest` requires the fulfiller to pay `_underlyings >= currentRequest.underlyings` (line 129). By setting `underlyingsRequested` to an astronomical value (up to `type(uint256).max`, which itself overflows `pendingUnderlyings += underlyingsRequested` unless the attacker splits it across multiple `createWriteOffRequest` calls from multiple addresses to keep each add non-reverting), the attacker creates a request that no fulfiller — including the honest borrower — can ever satisfy.

Only the request owner can delete their request (line 105-113), so as long as the attacker leaves it open, `pendingUnderlyings` permanently carries the injected amount. This is the injection primitive: user input is concatenated into a privileged aggregate ("the LDAP query") with no encoding/bounds check, and the scope of the corruption is global, not per-user.

### Impact Explanation
`pendingUnderlyings` is the escrow's protocol-facing view of expected write-off recoveries. Credit vaults that consume it (e.g., for pending-recovery/loss accounting around `writeOffDeposit` and epoch pricing) will permanently overstate expected inflows, skewing NAV/virtual price and any recovery-adjusted loss math for all lenders — analogous to the CVE's "access content outside the intended hierarchy." Even in the minimal reading, an unfulfillable request permanently jams the write-off market for that escrow and inflates the aggregate by an unbounded amount at near-zero cost.

Caveat: I could not fully verify within scope how `IdleCreditVault`/`IdleCDOEpochVariant` consume `pendingUnderlyings` (the strategy-side reader of this value was not confirmed). If it is only an informational counter with no accounting consumer, impact degrades to a permanently unfulfillable request, which is weaker.

### Likelihood Explanation
Any KYC-passing tranche holder can trigger it during a running epoch (the only gate is `isEpochRunning()`), with no economic loss — tranche tokens are refundable. Likelihood is high conditional on `pendingUnderlyings` feeding accounting.

### Recommendation
Bound `underlyingsRequested` (e.g., cap at the tranche tokens' current redemption/virtual-price value), or derive the requested amount from deposited tranches rather than trusting user input — the on-chain equivalent of escaping user fragments before building the query.

### Proof of Concept
```solidity
// Fork test skeleton (Foundry), epoch in "running" phase:
// attacker = KYC'd AA/BB tranche holder
uint256 trancheAmt = 1e18;                    // minimal refundable deposit
uint256 injected   = type(uint128).max;       // unfulfillable ask

vm.startPrank(attacker);
tranche.approve(address(escrow), trancheAmt);
escrow.createWriteOffRequest(trancheAmt, injected);
vm.stopPrank();

assertEq(escrow.pendingUnderlyings(), injected);   // global aggregate corrupted
// borrower cannot fulfill: would need to pay >= injected underlying
vm.prank(borrower);
vm.expectRevert(WrongRequest.selector); // any sane _underlyings < injected reverts
escrow.fullfillWriteOffRequest(attacker, trancheAmt, reasonableAmount);
// only attacker can delete; pendingUnderlyings stays inflated indefinitely
```
