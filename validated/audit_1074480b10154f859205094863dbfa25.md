### Title
Builder sweep withdrawal double-counts balance already committed to `builder_pending_withdrawals`, minting extra Gwei on the execution layer - (File: specs/gloas/beacon-chain.md)

### Summary
In `specs/gloas/beacon-chain.md`, `get_expected_withdrawals` builds a single payload withdrawal list by calling, in order, `get_builder_withdrawals` (drains `state.builder_pending_withdrawals`), `get_pending_partial_withdrawals`, then `get_builders_sweep_withdrawals` (drains fully-exited builders whose `withdrawable_epoch <= epoch`). Unlike the analogous validator-sweep function, the builder-sweep function does not net out withdrawals for the *same* builder that were already queued earlier in the same call by `get_builder_withdrawals`. This is structurally the same class of bug as the Illuminate `withdrawFee`/`withdraw` issue: two code paths independently draw on the same underlying balance (`fees[eToken]` vs the eToken balance actually in the contract; here, `builder_pending_withdrawals[...].amount` vs `builders[i].balance`), and the second path is computed from stale, unadjusted state instead of the balance net of what the first path already claimed.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md L1802-1834) emits a `Withdrawal` for each entry in `state.builder_pending_withdrawals` using the entry's recorded `amount` verbatim: [1](#0-0) 

`get_builders_sweep_withdrawals` (L1836-1874) is then called with `prior_withdrawals` including the above list, but for each eligible builder it reads the *live, unadjusted* `state.builders[builder_index].balance` and emits a withdrawal for the full amount: [2](#0-1) 

Contrast this with the validator sweep, `get_validators_sweep_withdrawals`, which explicitly nets out withdrawals already queued in the same payload for the same validator before deciding eligibility/amount: [3](#0-2) 

If a builder simultaneously (a) has an outstanding entry in `state.builder_pending_withdrawals` with amount `X` (fee_recipient `F`) and (b) satisfies `withdrawable_epoch <= epoch` with `balance > 0` (call it `B`), `get_expected_withdrawals` places **two** `Withdrawal` records for that same builder into `payload_expected_withdrawals`: `(F, X)` from the pending queue and `(execution_address, B)` from the sweep — where `B` is the pre-deduction balance, not `B - X`.

`apply_withdrawals` then applies these sequentially against the live CL balance, clamping each deduction with `min(withdrawal.amount, builder_balance)`: [4](#0-3) 

Concretely, with `builder.balance = B` and pending withdrawal `X <= B`:
- Apply `(F, X)`: live balance is `B`, deduct `min(X, B) = X` → balance becomes `B - X`.
- Apply `(execution_address, B)`: live balance is `B - X`, deduct `min(B, B - X) = B - X` → balance becomes `0`.

Total CL-side balance removed = `X + (B - X) = B` (correctly bounded, thanks to the `min()` clamp — this is why the bug doesn't show up as a CL-state assertion failure or negative balance).

However, the beacon block's `payload_expected_withdrawals` — which the execution layer is required to honor unconditionally as balance credits (withdrawals cannot fail or be reverted on the EL side; `process_withdrawals` asserts `list(payload.withdrawals) == expected.withdrawals`, per `process_withdrawals` at L1991-2018) — commits to crediting `X` to `F` **and** `B` to `execution_address`, i.e. `X + B` Gwei total: [5](#0-4) 

So the execution layer mints `X + B` Gwei while the consensus layer's internal accounting only ever removed `B` from the builder. The extra `X` Gwei is created without being backed by any corresponding decrease anywhere in `state` — this is a direct violation of the "no Gwei created" invariant, exactly the equality broken in the Illuminate report (a fee/committed amount is paid out again after the underlying balance backing it was already spent/zeroed by another code path, because the second consumer didn't recheck against the first consumer's effect).

### Impact Explanation
This breaks the "Gwei created or destroyed" invariant — classified Critical per the impact rubric (Gwei minted on the execution layer with no corresponding reduction in consensus-layer state). Because EL withdrawals are unconditional balance increases, there is no way for this to "fail safe" the way the eToken `Safe.transfer` did; it manifests as inflation rather than a stuck function.

### Likelihood Explanation
This requires a builder to simultaneously have (1) an unresolved `builder_pending_withdrawals` entry and (2) `withdrawable_epoch <= current_epoch`. The exit path (`process_builder_exit_request`) explicitly blocks initiating an exit while `get_pending_balance_to_withdraw_for_builder(state, builder_index) != 0` (which itself sums both `builder_pending_withdrawals` and `builder_pending_payments` for the builder), which is a design guard against exactly this scenario for the "exit → become withdrawable" path: [6](#0-5) [7](#0-6) 

I was not able to verify, within the retrieved index, (a) the exact definition of `is_active_builder` (whether it gates bidding on `withdrawable_epoch` rather than only `exit_epoch`) or (b) how `process_builder_deposit_request` initializes `Builder.withdrawable_epoch`. If a builder can remain "active" (able to place new bids that generate new `builder_pending_payments`/`builder_pending_withdrawals`) for any period after its `withdrawable_epoch` has already been fixed and reached — e.g. during the gap between `exit_epoch` and `withdrawable_epoch` (`MIN_BUILDER_WITHDRAWABILITY_DELAY` = 64 epochs), or if `withdrawable_epoch` can be reached independent of an explicit exit request — the double-withdrawal race becomes reachable through entirely honest, non-adversarial operation (no malicious peer/coalition required), consistent with the in-scope rules. Given this uncertainty, I'd treat likelihood as **Medium**: the code-level flaw (missing "balance after prior withdrawals in this payload" accounting for builders, unlike validators) is concretely demonstrated, but full confirmation of an end-to-end reachable trigger needs verification of `is_active_builder` and builder exit/withdrawable-epoch lifecycle code not covered by the retrieved snippets.

### Recommendation
Make `get_builders_sweep_withdrawals` consistent with `get_validators_sweep_withdrawals`: compute the builder's balance net of any withdrawals already included in the same payload for that builder (e.g. a `get_builder_balance_after_withdrawals(state, builder_index, all_withdrawals)` helper mirroring `get_balance_after_withdrawals`), and use that adjusted balance both for the `withdrawable_epoch <= epoch and balance > 0` eligibility check and for the emitted `amount`, instead of reading `state.builders[builder_index].balance` directly.

### Proof of Concept
1. Builder `B` has `balance = 32 ETH`, `withdrawable_epoch <= current_epoch` (already past its withdrawability point), and `execution_address = A2`.
2. `state.builder_pending_withdrawals` contains one entry for `B`: `amount = 5 ETH`, `fee_recipient = A1` (created earlier via `settle_builder_payment`/`apply_parent_execution_payload`, per specs/gloas/beacon-chain.md L1725-1774).
3. Call `get_expected_withdrawals(state)`:
   - `get_builder_withdrawals` emits `Withdrawal(address=A1, amount=5 ETH)`.
   - `get_builders_sweep_withdrawals` sees `builder.balance = 32 ETH > 0` and `withdrawable_epoch <= epoch`, emits `Withdrawal(address=A2, amount=32 ETH)` (not `27 ETH`).
4. `process_withdrawals` commits `payload.withdrawals = [(A1, 5 ETH), (A2, 32 ETH)]` — total EL mint = 37 ETH.
5. `apply_withdrawals` reduces `state.builders[B].balance`: `32 - min(5,32) = 27`, then `27 - min(32,27) = 0`. Total CL-side deduction = 32 ETH.
6. Result: EL minted 37 ETH to `A1`/`A2` combined; CL only ever backed 32 ETH of builder balance — 5 ETH created with no offsetting decrease anywhere in `state`.

def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
