### Title
Stale confirmations from removed multisig members/keys are never purged from other pending requests, allowing execution below the effective live-signer threshold - ([File: multisig2/src/lib.rs], also present in [File: multisig/src/lib.rs])

### Summary
The `PushOracleReceiver` report describes a class of bug where a state-changing action consumes data that was recorded before a later, superseding event, so the contract ends up acting on stale information instead of the current state. The same bug class exists in both multisig contracts here: when a member/key is removed via `DeleteMember`/`DeleteKey`, the contract only cleans up requests *authored by* that member, but never removes that member's already-recorded confirmations from *other* pending requests that they had previously confirmed. Those stale confirmations remain counted toward `num_confirmations` when a later `confirm()` call finalizes the vote tally, letting a request execute with fewer genuinely live confirming members than `num_confirmations` requires.

### Finding Description
`MultiSigContract::confirm` in [1](#0-0)  tallies votes purely from the `confirmations: LookupMap<RequestId, HashSet<String>>` set:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
```
`delete_member` (executed via `MultiSigRequestAction::DeleteMember`) only removes requests where the request's *author* (`r.member`) equals the removed member, and clears `num_requests_pk` for that member — see [2](#0-1) . It never inspects or purges the `confirmations` HashSet of *other* still-pending requests that the removed member had previously confirmed. Consequently:
- Equality that should hold: `confirmations counted toward num_confirmations` == `confirmations from members currently in self.members`.
- After a member is removed mid-flight, a stale confirmation string from that (now former) member still sits inside another request's `confirmations` set and is counted by the `>=` check on the next `confirm()` call.

The same root cause exists in the older `multisig` contract: `DeleteKey` in [3](#0-2)  only removes requests where `r.signer_pk == pk` (i.e., requests created by that key), leaving that key's confirmations on other pending requests intact, later counted in `confirm()` at [4](#0-3) .

### Impact Explanation
This breaks the binding "confirmations counted versus live members" and results in "a multisig request executed below threshold" — explicitly a Critical-impact category. A request (e.g., a `Transfer` of NEAR funds, an `AddKey`/`AddMember` granting new access, or a `DeployContract` upgrade) can be executed by the multisig account with only `num_confirmations - 1` (or fewer) confirmations coming from members who are still part of the live member set, because one "vote" is a ghost confirmation from a member that has since been removed. This can move NEAR or grant privileged access without the intended number of currently-authorized approvers agreeing.

### Likelihood Explanation
This does not require any member to act maliciously or exploit their signing key beyond its granted scope — it can occur during entirely ordinary multisig operations: (1) a request R1 gathers partial confirmations, (2) unrelated to R1, the members decide to rotate/remove a member (e.g., an employee off-boarding or key rotation) via a `DeleteMember`/`DeleteKey` request, and (3) R1's stale confirmation from the removed member is later combined with new confirmations to cross the threshold and execute R1. Any multisig deployment that rotates members while requests are pending is exposed, which is a realistic operational pattern.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over **all** pending requests' `confirmations` sets (not just requests authored by the removed member) and remove the departing member's/key's entry from each. Alternatively, validate at `confirm()`-time (when tallying) that each entry in the stored `confirmations` set still corresponds to a current member of `self.members`, discarding stale ones before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request` creating `R1 = Transfer{amount, receiver}` (no auto-confirm).
3. `B` calls `confirm(R1)` → `confirmations(R1) = {B}` (1 < 3, not executed).
4. `C` calls `confirm(R1)` → `confirmations(R1) = {B, C}` (2 < 3, not executed).
5. Separately, `A`, `B`, `D` create and confirm/execute `R2 = DeleteMember{C}` (3 confirmations, meets threshold) → `C` is removed from `members`. `delete_member` only deletes requests authored by `C`; `R1` (authored by `A`) and its `confirmations = {B, C}` are untouched.
6. Now only `A, B, D` are live members (3 total, still `num_confirmations = 3`).
7. `D` calls `confirm(R1)`: `confirmations(R1).len() (2, i.e. {B, C}) + 1 = 3 >= 3` → `R1` executes the `Transfer`, even though the only currently-live members who ever confirmed it are `B` and `D` (2 live confirmations), one short of the required 3 live-member approvals — `C`'s stale confirmation was silently counted.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
