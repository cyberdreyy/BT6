### Title
Withdrawal requests are force-enabled and instant withdrawals cannot be disabled atomically at `stopEpoch`, so tranche holders can back-run the manager's epoch transition to grab fee-free instant receipts — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In Cooler, `clear` creates a loan with `rollable = true` and the lender must send a second transaction to disable it, which the borrower can back-run. The analog here is the epoch transition in `IdleCDOEpochVariant`: `_stopEpoch` unconditionally sets `allowAAWithdrawRequest = true` and `allowBBWithdrawRequest = true` (lines 481-482) and there is no parameter on `stopEpoch`/`stopEpochWithDuration` to keep requests closed or to disable instant withdrawals. The only way to change those flags is a separate `setAllowAAWithdraw`/`setAllowBBWithdraw`/`setInstantWithdrawParams` transaction. Because withdrawal requests reopen in the same block that `stopEpoch` executes, any KYC-passing tranche holder can back-run the manager's `stopEpoch` (or front-run the manager's follow-up disable transaction) and file a `requestWithdraw` under terms the manager did not intend — most acutely, an *instant* withdrawal receipt that skips all fees.

### Finding Description
After a normal stop, `_stopEpoch` re-enables both request flags and sets `allowInstantWithdraw = _isRequestingAllFunds` (lines 478-490). Neither flag is a parameter of `stopEpoch`. `setInstantWithdrawParams` additionally reverts while `paused()` (line 133), and the vault is paused for the entire running epoch, so the manager cannot stage the disable during the epoch — it must happen in the buffer window where requests are open.

When the manager stops the epoch with a lower `_newApr`, `requestWithdraw` routes through the instant path: if `lastEpochApr > currentApr + instantWithdrawAprDelta`, the user's tranche tokens are burned at current `tranchePrice` and a receipt for the full `_underlyings` is minted via `creditVault.requestInstantWithdraw` (lines 761-769). Critically, this path never calls `_calcInterestWithdrawRequest` or `_totalWithdrawFees`, so:

- no upfront management fee for the receipt's idle time is charged (`_withdrawRequestManagementFeeDuration` = epoch + remaining buffer),
- no performance fee on projected interest is charged,
- the receipt is funded from vault cash at `startEpoch` (`collectInstantWithdrawFunds`, line 282) ahead of and independently of normal receipts that settle at the next stop.

A normal `requestWithdraw` in the same block would pay `_totalWithdrawFees` on principal + interest (lines 772-778). An attacker holding tranche tokens who back-runs `stopEpoch` (or front-runs the manager's `setInstantWithdrawParams(..., true)` in the buffer) captures receipt value gross of fees that every normal withdrawer pays.

### Impact Explanation
Direct loss of protocol fees and unfair mint/burn terms: the attacker receives a receipt for full tranche price while normal requesters receive `principal + interest − fees`. The skipped management fee is on the order of `principal * fee * (epochDuration + bufferPeriod) / 365 days` plus the performance fee share of projected interest; `unclaimedFees`/`pendingWithdrawFees` are correspondingly lower, and instant receipts are paid out of the first cash available at `startEpoch`, senior to normal receipts. If the manager intended to keep requests closed after the stop (e.g., to apply an emergency shutdown or an explicit-loss stop with requests disabled), that is simply impossible atomically — the flags are force-opened inside `_stopEpoch` itself.

### Likelihood Explanation
Requires only that the manager lowers the APR at `stopEpoch` (the designed trigger for instant mode) while instant mode is enabled, or intends to keep a request flag disabled across a stop. Any KYC-passed tranche holder monitoring the mempool can back-run `stopEpoch` or front-run `setInstantWithdrawParams`; no privileged role is needed and no existing guard (`_checkNotAllowed` flags, `isWalletAllowed`, skim, default reverts) blocks a request in that window.

### Recommendation
- Add parameters to `stopEpoch`/`stopEpochWithDuration` (e.g., `_allowAARequests`, `_allowBBRequests`, `_disableInstant`) instead of hardcoding `allowAAWithdrawRequest = true` / `allowBBWithdrawRequest = true`, mirroring the report's Option 1 (`clear(reqID, bool rollable)`).
- Alternatively charge `_totalWithdrawFees` on the instant path as well, so instant requests only change timing, not price.
- At minimum, allow `setInstantWithdrawParams` while paused so the manager can disable instant mode during the epoch before the buffer window opens.

### Proof of Concept
Fork test against an `IdleCreditVault` deployment (mirroring `test/foundry/IdleCreditVault.t.sol` helpers `_toggleEpoch` / `_startEpochAndCheckPrices`):

```solidity
function testBackRunStopEpochInstantWithdraw() public {
    // setup: attacker holds AA tranche tokens, instant mode enabled
    idleCDO.depositAA(100_000 * ONE_SCALE);
    vm.prank(owner);
    cdoEpoch.setInstantWithdrawParams(3 days, 0, false); // delay, aprDelta=0, enabled

    // epoch 1 runs at initialApr
    _toggleEpoch(true, 0, 0);
    _toggleEpoch(false, initialApr / 2, _expectedFundsEndEpoch()); // stop with LOWER apr

    // stopEpoch has just reopened requests in the same tx;
    // attacker back-runs it before owner's setInstantWithdrawParams(disable)
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // instant receipt minted for full tranche price: pendingInstantWithdraws credited,
    // zero management/performance fees charged
    assertGt(IdleCreditVault(strategy).pendingInstantWithdraws(), 0);
    assertEq(cdoEpoch.pendingWithdrawFees(), 0); // no fees accrued vs normal path

    // next epoch: attacker claims funded receipt immediately
    _startEpochAndCheckPrices(0);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertGt(underlying.balanceOf(attacker), balBefore);
}
```
