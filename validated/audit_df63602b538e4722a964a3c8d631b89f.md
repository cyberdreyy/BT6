### Title
Denial of Service via cross-workflow requestID squatting in shared callback map - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`httpTriggerHandler.setupCallback` keys pending requests in a single, gateway-instance-wide `h.callbacks` map by the raw, user-supplied `requestID` string only, with no per-workflow or per-owner namespacing. Any caller who can get a JWT authorized for *any* workflow served by this gateway/DON instance can pre-register a `requestID` and cause a subsequent legitimate request for a *different, unrelated* workflow that happens to reuse the same `requestID` to be rejected with `jsonrpc.ErrConflict`, denying that request.

### Finding Description
`requestID` (`req.ID`) is supplied entirely by the caller in the JSON-RPC request. `validateRequestID` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:183-195`) only rejects empty IDs or IDs containing `/`; it does not enforce uniqueness scope or unpredictability, and it does not tie the ID to a particular workflow.

`setupCallback` (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:398-405`) checks for a duplicate purely against the global map key `requestID`:
```go
if _, found := h.callbacks[requestID]; found {
    h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, ...)
    return nil, fmt.Errorf("in-flight request ID: %s", requestID)
}
```
`h.callbacks map[string]savedCallback` (line 60) is a single map shared across every workflow the handler serves — there is no `(workflowID, requestID)` composite key. Because `authorizeRequest` only requires a JWT signed by a key authorized for *some* workflow that is registered with this DON (`WorkflowMetadataHandler.Authorize`, `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108`), an attacker who is merely an authorized signer for their *own* workflow A can submit a valid request with `requestID = "X"`, occupying the global slot for `"X"` until it completes or the reaper (`reapExpiredCallbacks`) times it out. If a victim later (before expiry/cleanup) submits a legitimate request for an unrelated workflow B using the same `requestID = "X"` (e.g., an idempotency key, correlation ID, or sequential ID generated by their client), that second call is rejected outright with `ErrConflict`, denying the victim's request.

Regarding the second part of the question — whether `HandleNodeTriggerResponse` (lines 448-496) could route workflow A's node response into workflow B's waiting callback — this does **not** occur. `HandleNodeTriggerResponse` looks up `h.callbacks[resp.ID]`, and because `setupCallback`'s conflict check prevents two entries from ever coexisting under the same `requestID`, workflow B's registration attempt fails immediately (no callback for B is ever created). The only credentialed workflow whose callback lives under `"X"` is workflow A's (the attacker's own), so there is no cross-owner response delivery — the underlying conflict guard, while causing the DoS, also happens to prevent the response-confusion scenario.

### Impact Explanation
This is a targeted, request-scoped Denial of Service: an attacker holding valid credentials for any single workflow on a shared gateway/DON instance can block a specific, guessed/predictable `requestID` from being used by any other unrelated workflow's caller until the squatted callback naturally completes or is reaped by `reapExpiredCallbacks` (bounded by `CleanUpPeriodMs`). This corresponds to a limited-severity availability impact (temporary denial of a single workflow execution request), not privilege escalation, data disclosure, or fund movement. There is no cross-workflow response/data leakage, since the duplicate-ID guard prevents two simultaneous callbacks from sharing the key.

### Likelihood Explanation
Exploitability requires: (1) the attacker holds a valid ECDSA key authorized for at least one workflow on the target DON/gateway instance (a fairly low bar in permissive/multi-tenant DON setups), and (2) the attacker can predict or influence the victim's future `requestID` value. Since `requestID` validation only forbids emptiness and `/`, and there is no requirement that it be a cryptographically random UUID, this is feasible in deployments where request IDs are predictable, sequential, or derived from public/shared information (e.g., timestamps, incrementing counters, or client-side correlation IDs). The attack is repeatable for any number of guessed IDs, subject to the attacker's own workflow's rate limit.

### Recommendation
Namespace the callback map key by `(workflowID, requestID)` (or by authorized signer/workflow owner plus `requestID`) instead of `requestID` alone, so that ID collisions across different workflows/owners cannot interfere with each other. This closes the DoS vector while preserving the existing conflict-based dedup within the same workflow.

### Proof of Concept
Extend `TestHttpTriggerHandler_HandleUserTriggerRequest`'s "duplicate request ID" subtest (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go:317-355`):
1. Register two distinct workflows, `workflowA` and `workflowB`, each with its own authorized signing key, on the same `httpTriggerHandler`.
2. Submit a valid `HandleUserTriggerRequest` for `workflowA` with `requestID = "X"` signed by workflowA's key; assert `err == nil` and `handler.callbacks["X"].Callback == callbackA`.
3. Before completing/aggregating callbackA, submit a second `HandleUserTriggerRequest` for `workflowB` with the same `requestID = "X"`, signed by workflowB's authorized key; assert it returns an error containing `"in-flight request"` and that `callbackB.Wait(ctx)` receives a `jsonrpc.ErrConflict` response — demonstrating the victim workflow B's legitimate request is denied purely due to an ID collision with an unrelated workflow A.
4. Additionally assert `handler.callbacks["X"].Callback == callbackA` still (not overwritten/confused with callbackB), and that no response for workflow A's nodes is ever delivered to `callbackB`, confirming no cross-workflow response routing occurs — only denial of workflow B's request.
