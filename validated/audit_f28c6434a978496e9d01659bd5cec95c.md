### Title
Claimed instant-withdraw receipts are never cleared from the per-epoch claim counters, inflating default recovery basis and reserve beyond actual holdings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the per-user aggregate `instantWithdrawsRequests[_user]`, but leaves `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` untouched — the exact analog of the CVE-2024-38616 `memset` applied to the wrong union member. If the vault is later defaulted and finalized while `pendingInstantWithdraws != 0`, the already-paid receipts are counted again as both claim basis (`defaultPendingClaimBasis`) and as "prefunded" reserve (`_defaultPrefundedInstantReserve`), so `defaultRecoveryReserve` is set above the strategy's real balance and the last recovery claimants can never be paid.

### Finding Description
The funded-claim path clears the wrong field:

- `claimInstantWithdrawRequest` zeroes `instantWithdrawsRequests[_user]` and pays out `amount`, but never decrements `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` or `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:387-392`). [1](#0-0) 
- On default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, re-counting already-claimed receipts (`IdleCreditVault.sol:644-649`). [2](#0-1) 
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant` and treats the claimed (already-transferred-out) portion as underlying still held by the strategy (`IdleCreditVault.sol:716-723`). [3](#0-2) 
- `finalizeDefaultRecovery` then stores this phantom amount into `defaultRecoveryReserve` and computes `defaultRecoveryPrice` from it (`IdleCreditVault.sol:685-692`). [4](#0-3) 

Because the ghost amount `G` enters both numerator and denominator, `recoveryPrice` is wrong and `defaultRecoveryReserve` overstates actual holdings by `G`. Claims are paid via `_transferDefaultRecovery`, which decrements the reserve counter and transfers real tokens (`IdleCreditVault.sol:912-917`); after the genuine balance is exhausted, remaining claims revert on the ERC20 transfer — permanent freezing of unclaimed recovery. Additionally, the stale `instantWithdrawsRequestsByEpoch` entry makes `_claimDefaultedInstantWithdrawRequest` attempt `instantWithdrawsRequests[_user] -= claimBasis` on an already-zeroed aggregate, which underflow-reverts and permanently bricks `claimInstantWithdrawRequest` for any user who claimed before finalization (`IdleCreditVault.sol:842-855`). [5](#0-4) 

### Impact Explanation
Direct insolvency / permanent freezing: recovery claimants collectively cannot withdraw up to the full amount `G` of instant withdrawals claimed in the defaulted epoch. Every unit previously claimed is double-counted as reserve that does not exist; the deficit is socialized onto the last claimants whose `safeTransfer` reverts. The underflow in `_claimDefaultedInstantWithdrawRequest` also permanently freezes all remaining claims (including funded normal receipts, via the shared `claimInstantWithdrawRequest` entry path) for any user who claimed an instant withdrawal in that epoch. Loss magnitude equals the instant-withdraw volume claimed in the default epoch, which an unprivileged user can make arbitrarily large.

### Likelihood Explanation
Any tranche holder can call `requestInstantWithdraw` and `claimInstantWithdrawRequest` through the CDO during a normal epoch — no privileged role needed. The only external precondition is a subsequent borrower default in the same epoch with `pendingInstantWithdraws != 0` (i.e., other instant requests only partially funded), which is the normal operating case this accounting was built for. An attacker can even maximize `G` by cycling large instant requests that get funded. Note `_ensureDefaultRecoveryInitialized` explicitly documents "Pending instant withdrawals are never cleared automatically", confirming no guard normalizes these counters. [6](#0-5) 

### Recommendation
Mirror the fix for CVE-2024-38616 (clear the correct member explicitly): in `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epoch]` for the request epoch and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount, so that `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only count still-unpaid receipts. If multi-epoch instant receipts must be supported, iterate the user's request epochs; otherwise track the single open epoch per user. Also make `_claimDefaultedInstantWithdrawRequest` tolerate stale per-epoch entries (skip when `instantWithdrawsRequests[_user] < claimBasis`) so a stale record cannot DoS the claim path.

### Proof of Concept
Foundry fork PoC (setup mirrors `test/foundry/IdleCreditVault`/`IdleCDOEpochVariant` tests; `cdo`, `strategy`, `underlying`, `manager`, `user1` funded, `user2` funded):

```solidity
function test_InstantClaimGhostReserve() external {
    _stopCurrentEpoch(); // end epoch 0
    uint256 amt = 100e6;
    _depositWithUser(user1, amt);          // user1 active
    uint256 t2 = _depositWithUser(user2, amt);

    vm.prank(manager);
    cdoEpoch.startEpoch();                  // epoch 1 running

    // user2 requests instant withdraw; funds collected, user2 claims fully
    _requestInstantWithdrawWithUser(user2, t2);
    // borrower/manager fund instant queue partially: only user2's part is collected
    vm.prank(manager);
    cdoEpoch.collectInstantWithdrawFunds(t2); // pendingInstantWithdraws -> 0 for a moment
    vm.prank(user2);
    cdoEpoch.claimInstantWithdrawRequest();   // paid; but instantWithdrawClaimsByEpoch[1] still = t2

    // a third user requests instant withdraw in the SAME epoch, left unfunded
    uint256 t3 = _depositWithUser(user3, amt);
    _requestInstantWithdrawWithUser(user3, t3); // pendingInstantWithdraws = t3 basis
    // (partial funding leaves pendingInstantWithdraws != 0 at finalization)

    // borrower defaults; finalize recovery
    _handleBorrowerDefault();
    uint256 balBefore = underlying.balanceOf(address(strategy));
    strategy.finalizeDefaultRecovery(0, address(0));

    // reserve overstates real balance by user2's claimed t2
    assertGt(strategy.defaultRecoveryReserve(), balBefore);
    // user3's recovery claim reverts: reserve counter exists but tokens were paid to user2
    vm.expectRevert();
    vm.prank(user3);
    cdoEpoch.claimInstantWithdrawRequest();
    // user2's own claim path is bricked by underflow on the stale epoch entry
    vm.expectRevert();
    vm.prank(user2);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

The assertion `defaultRecoveryReserve > actualBalance` demonstrates the phantom-reserve inflation; the reverts demonstrate permanent freezing of remaining recovery claims.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];

  /// @notice Lazily initialize recovery accounting for an upgraded strategy.
  /// @dev Legacy pending receipts must first be fully funded because their per-epoch ownership
  /// cannot be reconstructed after an implementation upgrade. A successfully closed vault has
  /// already recalled all funds, so stale normal/APR0 aggregate counters can be normalized there.
  /// Pending instant withdrawals are never cleared automatically.
  function _ensureDefaultRecoveryInitialized() internal {
    if (defaultRecoveryInitialized) return;
    if (pendingInstantWithdraws != 0) revert NotAllowed();
    if (pendingWithdraws != 0) {
      IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
      if (cdo.epochEndDate() != 0 || cdo.defaulted()) revert NotAllowed();
      pendingWithdraws = 0;
      apr0TotalPrincipal = 0;
    }
    defaultRecoveryInitialized = true;
    canTransfer = false;
  }
