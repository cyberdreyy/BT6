### Title
`BlockRejection` signature does not cover `reason`, `reason_code`, or `response_data`, letting a single signer equivocate on rejection semantics under one valid signature - (File: `libsigner/src/v0/messages.rs`)

### Summary
`BlockRejection::hash()` computes the signed digest over only the `signer_signature_hash` (and `chain_id`, via the structured-data domain). The `reason` string, `reason_code`, and `response_data` (which carries `reject_reason`, `failed_txid`, and extend timestamps) are serialized and transmitted as part of the message but are **not** part of the signed payload. Any bytes can be substituted for these fields without invalidating the signature, exactly the same class of defect as the Dynatrace report: a field that downstream logic treats as authenticated/trustworthy (there, the workflow template context; here, the rejection's reason/response_data) is actually attacker-controllable because it sits outside the boundary that was actually protected (there, the `Run Javascript` carve-out; here, the signed digest).

### Finding Description
`BlockRejection::hash()`:
```rust

    let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
``` [1](#0-0) 

This is the exact digest that `sign()`/`verify()`/`recover_public_key()` operate on: [2](#0-1) 

But the full struct that is transmitted and stored is:
```rust
pub struct BlockRejection {
    pub reason: String,
    pub reason_code: RejectCode,
    pub signer_signature_hash: Sha512Trunc256Sum,
    pub signature: MessageSignature,
    pub chain_id: u32,
    pub metadata: SignerMessageMetadata,
    pub response_data: BlockResponseData,
}
``` [3](#0-2) 

`reason`, `reason_code`, and `response_data.reject_reason` are the only fields consuming code actually uses to decide network-wide state: `handle_block_rejection` recovers and authenticates the signer purely via `rejection.recover_public_key()` / `is_valid_signer` (both of which only check the digest above), then forwards `(&rejection.response_data.reject_reason).into()` — an unauthenticated field — into `store_and_process_block_rejection`: [4](#0-3) 

That `reject_reason` classification then feeds `compute_reject_code_signing_weight(rejection_addrs.iter(), RejectReasonPrefix::ReorgNotAllowed)`, which decides whether to flip `sortition_state.cur_sortition.miner_status` to `SortitionMinerStatus::InvalidatedBeforeFirstBlock` — a consensus-visible, safety-relevant decision: [5](#0-4) 

Because the signature never binds `reason`/`reason_code`/`response_data`, a single already-participating signer (using only their own key, no majority and no other signer's key needed) can:
1. Sign one `BlockRejection` for a given `signer_signature_hash` (obtaining a valid `signature` over that hash and `chain_id` only).
2. Construct multiple differently-worded copies of the message with that same `signature` field but different `reason`, `reason_code`, and, most importantly, different `response_data.reject_reason` values (e.g. one copy tagged `ReorgNotAllowed`, another tagged something benign) — every copy still passes `verify()`/`recover_public_key()` because those checks only re-derive the digest from `signer_signature_hash`+`chain_id`, which are unchanged.
3. Selectively deliver different variants to different peers/receivers.

Every receiving signer independently calls `handle_block_rejection` → `store_and_process_block_rejection`, which records the *received* variant's `reject_reason` in its own `signerdb`. Because the message-level signature can't distinguish "the true reason the signer gave" from any forged variant, different honest signers can be made to record contradictory classifications of the *same* cryptographically-valid vote from the *same* signer for the *same* block — directly breaking the aggregated-weight-vs-verified-accepts equality the reject-tally and miner-invalidation logic depend on (`RejectReasonPrefix::ReorgNotAllowed` weight is meant to reflect what signers actually attested to, but the attestation covers none of that content).

### Impact Explanation
This falls under the Critical bucket: it corrupts a "rejection recounted"/miscounted-response invariant. The `ReorgNotAllowed` reject-weight computation is the mechanism that marks a miner's sortition as `InvalidatedBeforeFirstBlock` — a decision with consensus-visible, safety-relevant effect on which miner/tenure the signer set treats as legitimate going forward. Since the signature over `BlockRejection` never binds the very field (`response_data.reject_reason`) that this decision is keyed on, a single misbehaving signer (using only its own key) can present inconsistent, cryptographically-indistinguishable claims about why it rejected a block to different peers, undermining the network's ability to agree on whether the ReorgNotAllowed threshold was actually reached from genuine attestations.

### Likelihood Explanation
Requires only a single dishonest signer already possessing valid signing key material (explicitly in-scope per the rules — "using your own key" analogous to the "signer signing an invalid/conflicting" impact category) and standard message-delivery control over what each StackerDB/gossip peer receives; no majority or other signer's key is needed. The one caveat I could not fully verify in the time available is the exact primary key used by `add_block_rejection_signer_addr`/`get_block_rejection_signer_addrs` in `stacks-signer/src/signerdb.rs` (whether rows are keyed by `(block_hash, signer_address)` or `(block_hash, signer_address, reason)`); I was unable to retrieve that definition before running out of tool budget. This affects whether a single signer can additionally get *multiple* rows counted (double-counting) as opposed to only being able to make different peers disagree about which single reason was recorded — but either way, the root cause (the signature not covering `reason_code`/`response_data`) is proven directly from `libsigner/src/v0/messages.rs`.

### Recommendation
Include `reason_code` and the full `response_data` (or at minimum `response_data.reject_reason` and `failed_txid`) inside the structured-data digest signed/verified in `BlockRejection::hash()`, so any receiver can cryptographically detect if these fields were altered relative to what the signer actually attested, and so the same signature cannot validly accompany two different reject-reason claims.

### Proof of Concept
Conceptual, using only the `BlockRejection` API already shown above (no other signer's key or majority required):
1. Signer S calls `BlockRejection::new(hash, RejectReason::ReorgNotAllowed, S_privkey, mainnet, ts1, ts2)`, obtaining `sig = S.sign(hash(signer_signature_hash, chain_id))`.
2. S constructs a second struct with identical `signer_signature_hash`, `chain_id`, and `signature = sig`, but `reason_code`/`response_data.reject_reason` set to any other value (e.g. `RejectCode::SortitionViewMismatch`).
3. Both structs pass `BlockRejection::verify(&S_pubkey)` (per `libsigner/src/v0/messages.rs:1816-1825`), because verification only recomputes the digest from `signer_signature_hash`/`chain_id`.
4. S delivers variant (1) to a subset of signers and variant (2) to another subset; each receiver calls `handle_block_rejection`/`store_and_process_block_rejection` (`stacks-signer/src/v0/signer.rs:2208-2369`) and records a different `reject_reason` classification for the identical signed vote, corrupting the `ReorgNotAllowed` weight tally used to invalidate a miner's sortition.

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
    }
