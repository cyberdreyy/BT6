### Title
Settled APR0 receipt bypasses the loss-epoch guard in `requestWithdraw`, letting `lastWithdrawRequest` be overwritten past a loss epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Jetty bug is a stale boundary flag: `case ';'` consumes input up to `/` and appends it, but `slash` is recomputed from the stale char `c=';'`, so the following `..` is never flagged and normalization (the security check) is skipped. The analog in `IdleCreditVault.requestWithdraw` (lines 259-294) is the same shape: the loss-receipt guard reads a boundary pointer `lossEpoch = lastWithdrawRequest[_user]` and then checks two per-epoch records — `withdrawsRequestsByEpoch[_user][lossEpoch]` and `apr0Users[_user].principal/principalEpoch`. An APR0 request writes neither `withdrawsRequestsByEpoch` nor, after settlement, `apr0Users.principal`/`principalEpoch`: `_settleApr0` (lines 563-564) clears `principal` and `principalEpoch` to 0 while `settledPrincipal`/`settledInterest` remain claimable at par in `_claimFundedWithdrawRequest` (lines 339-343). The guard therefore sees a "clean" boundary — like the stale `slash=false` — lets the new request through, and `lastWithdrawRequest[_user] = currentEpoch` (line 282) overwrites the only pointer to the loss epoch. The settled APR0 principal escapes the `lossRecoveryPriceByEpoch[lossEpoch]` haircut it should have taken.

### Finding Description
In `requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:261-271):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (
  lossRecoveryPrice != 0 &&
  (withdrawsRequestsByEpoch[_user][lossEpoch] != 0 ||
  (apr0Users[_user].principal != 0 && apr0Users[_user].principalEpoch == lossEpoch))
) {
  revert NotAllowed();
}
```

The comment states the intent: a loss-adjusted receipt must be claimed before a later request, otherwise `lastWithdrawRequest` stops pointing at the epoch that stores the haircut. But the disjuncts only cover receipts that are still visible in the loss epoch's records:

- Normal path writes `withdrawsRequestsByEpoch[_user][currentEpoch]` (line 293).
- APR0 path (`unscaledApr == 0`, line 285) writes only `apr0Users` via `_requestWithdrawApr0` (lines 567-577).
- After the epoch ends, `_settleApr0` moves `principal` into `settledPrincipal` and zeroes `principal` and `principalEpoch` (lines 557-564).

So a user whose loss-epoch receipt was APR0-denominated and has since settled satisfies `lossRecoveryPrice != 0` but fails both disjuncts (`withdrawsRequestsByEpoch == 0`, `apr0Users.principal == 0`). The guard — the analog of `if (slash) normal = false;` — is skipped, the new request executes, and `lastWithdrawRequest` is advanced past the loss epoch. The settled APR0 principal plus any new receipt are then paid at par via `_claimFundedWithdrawRequest`, consuming the same funded balance that was priced assuming the epoch-N haircut (`collectWithdrawFunds` lines 411-430 set `pendingWithdraws = 0` and `lossRecoveryPriceByEpoch[epochNumber]`, i.e., the shortfall was intentionally socialized over epoch-N receipts).

### Impact Explanation
Direct theft / insolvency of the funded-receipt reserve. A stop-epoch loss that sets `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` means only `_amount < pendingBasis` was collected for epoch-N receipts. Every epoch-N receipt paid at par instead of at the recovery price overdraws the strategy's funded balance; `_transferFundedClaim` (lines ~895-906) only caps at `balance - reserve`, so the last claimants of that epoch (or later funded receipts) absorb the shortfall. Quantified: attacker claims `settledPrincipal` at 100% instead of `settledPrincipal * lossRecoveryPrice / RECOVERY_FULL`, stealing `settledPrincipal * (1 - recoveryPrice)` from other receipt holders.

### Likelihood Explanation
Requires (a) `unscaledApr == 0` at request time — a legitimate manager-set configuration, exercised in tests (`setAprs(0,0)`); (b) a partial loss at the epoch's `stopEpoch`/`collectWithdrawFunds` — the exact `stopEpochWithDuration(_lossAmount)` path. The attacker is an ordinary KYC'd lender: deposit AA, request withdraw while APR=0, wait one epoch (which applies the loss and settles the APR0 bucket), request a second withdraw — the stale-boundary guard passes — then claim at par. No privileged role needed.

Caveat: I was unable to read `_claimLossAdjustedWithdrawRequest`/`_claimDefaultedWithdrawRequest` bodies before the iteration budget ended. The finding assumes the claim-time haircut lookup keys off `lastWithdrawRequest` (consistent with the guard's comment); if it instead iterates `withdrawsRequestsByEpoch`/`apr0RateByEpoch` independently, the guard bypass alone would still desynchronize `lastWithdrawRequest` but the payout path needs verification.

### Recommendation
Extend the guard to also check settled APR0 state tied to the loss epoch, e.g. track `apr0Users[_user].settledEpoch` (or never zero `principalEpoch` after settlement) and include `apr0Users[_user].settledPrincipal != 0 && settledEpoch == lossEpoch` in the disjunct — mirroring the Jetty fix of updating `slash` to reflect the last effective character rather than the stale `c`. Alternatively, snapshot a per-user `lastLossEpoch` on the first unsettled haircut so overwriting `lastWithdrawRequest` cannot hide it.
