### Title
Missing role-based access control on GET /v2/external_initiators exposes EI credentials to unprivileged view/run-role users - ([File: core/web/router.go])

### Summary
The route `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` at [1](#0-0)  is protected only by the base `authv2` group's authentication (`AuthenticateByToken`/`AuthenticateBySession`), unlike the sibling `POST` and `DELETE` routes on the same resource which additionally require `auth.RequiresEditRole` at [2](#0-1) . Any authenticated user regardless of role — including `view` and `run` roles, which the audit rules explicitly classify as unprivileged attackers — can call this endpoint and enumerate every configured external initiator's `AccessKey` and `OutgoingToken`.

### Finding Description
`ExternalInitiatorsController.Index` returns a paginated list of `presenters.ExternalInitiatorResource` records built via `NewExternalInitiatorResource`, which includes `Name`, `URL`, `AccessKey`, and `OutgoingToken` for every external initiator registered on the node [3](#0-2) [4](#0-3) .

The route wiring shows the Index handler is reachable through the general `authv2` group (any valid session/API token, any role) while `Create` and `Destroy` explicitly require `auth.RequiresEditRole`: [5](#0-4) . `RequiresEditRole` rejects `view` and `run` roles [6](#0-5) , confirming the intended minimum privilege for touching this resource is `edit`, but `Index` bypasses that check entirely — it is invoked directly with only `paginatedRequest` wrapping it, with no role guard.

As a result, a node user provisioned with only the `view` or `run` role (e.g., a restricted API token holder) can call `GET /v2/external_initiators` and receive the `AccessKey` and `OutgoingToken` values for all external initiators configured on the node, data that the sibling endpoints treat as requiring `edit` privilege to interact with.

### Impact Explanation
This is an authorization/least-privilege bypass: identifiers used in the external-initiator authentication scheme (`AccessKey`, used together with a secret in `AuthenticateExternalInitiator` [7](#0-6) , and `OutgoingToken`, used by the node to authenticate itself to the external initiator's endpoint) are disclosed to lower-privileged roles than the resource's write operations require. This matches the "cross-user/role response confusion" and "credential exposure" impact classes: a restricted/`view`-role credential holder gains visibility into administrative resource metadata and outbound-callback tokens that should be `edit`-role-gated. Full authentication bypass is not achieved from `AccessKey` alone since the paired `Secret`/`OutgoingSecret` are not returned in this response (only in the one-time `Create` response), which limits — but does not eliminate — the impact to information disclosure of otherwise edit-role-restricted identifiers.

### Likelihood Explanation
Trivial and fully repeatable: any user with a valid session or API token of role `view` or `run` (the minimum roles the system supports) can issue `GET /v2/external_initiators` with no additional preconditions, since the route requires no elevated role check. No signature forgery, race condition, or special timing is needed.

### Recommendation
Wrap `eia.Index` with `auth.RequiresEditRole` (or at minimum `auth.RequiresRunRole` if `view` access is deemed acceptable but should still be a deliberate decision) to match the authorization level enforced on `Create`/`Destroy` for the same resource:
```go
authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```

### Proof of Concept
1. Handler-level integration test using `cltest` test app:
   - Create a user with `sessions.UserRoleView` (or `UserRoleRun`).
   - Seed one `bridges.ExternalInitiator` via `BridgeORM().CreateExternalInitiator`.
   - Authenticate as the view-role user (session or API token) and call `GET /v2/external_initiators`.
   - Assert response status is `200 OK` and the response body contains the seeded initiator's `accessKey`/`outgoingToken` fields — demonstrating the role check is absent.
2. Comparative assertion: call `POST /v2/external_initiators` and `DELETE /v2/external_initiators/:Name` with the same view-role user and assert `401 Unauthorized`, confirming inconsistent enforcement between `Index` and `Create`/`Destroy` on the same resource.
3. After applying the fix (`auth.RequiresEditRole` wrapping `Index`), rerun step 1 and assert `401 Unauthorized` for the view-role user, and `200 OK` for an edit/admin-role user.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
