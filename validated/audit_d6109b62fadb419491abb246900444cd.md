### Title
Accrued-but-unminted programmable borrower interest is excluded from NAV, letting mid-epoch depositors mint tranche shares at an understated price - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In the external Derby report, `setTotalUnderlying()` priced the vault using only balances already pulled into the vault, omitting funds still claimable via `claim()`. The idle-tranches analog lives in the epoch-based credit vault: `IdleCDOCreditVault.getContractValue()` counts only `strategyToken` balance + raw underlying − `unclaimedFees`, but during a running epoch the real yield accrues inside the `ProgrammableBorrower`'s ERC-4626 sleeve (`_currentVaultAssets()`) and inside `borrowerInterestAccruedNow()`. That interest is only crystallized into strategy tokens at `stopEpoch` via `mintStrategyTokens` / `deposit`. While the epoch runs, `virtualPrice`, `tranchePrice`, and every price-dependent mint path see a NAV that excludes the accrued yield — exactly the "totalUnderlying misses claimable funds" bug class.

### Finding Description
- `IdleCDOCreditVault.getContractValue()` returns `_contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees` (`contracts/IdleCDOCreditVault.sol:125-128`). Strategy tokens are minted 1:1 with underlyings, so any interest that exists only as `ProgrammableBorrower` vault appreciation or borrower accrual is invisible until `stopEpoch` calls `mintStrategyTokens(_grossInterest)` (`contracts/IdleCDOEpochVariant.sol:428-430`).
- In programmable mode `expectedEpochInterest` is forced to 0 at `startEpoch` (strategy APR is 0; `totalInterestDueNow()` is only read inside `stopEpoch` via `_resolveStopEpochInterest`, `contracts/IdleCDOEpochVariant.sol:1001-1005`). So the mid-epoch pricing inputs contain no compensation for the already-accrued yield.
- `_deposit` is paused during the epoch, but `depositDuringEpoch` (gated only by the owner-set `isDepositDuringEpochDisabled` flag, `contracts/IdleCDOEpochVariant.sol:150-153`) lets users mint tranche shares / epoch receipts priced off `virtualPrice`/`tranchePrice`, both of which derive from the understated NAV.
- Broken invariant: fair mint. A user depositing late in a programmable epoch buys tranche tokens at a price that excludes yield accrued since `epochStartVaultAssets`, then `stopEpoch` mints that yield into NAV and the new holder captures a pro-rata share of interest earned before they deposited — diluting existing AA/BB holders.

### Impact Explanation
Direct theft of unclaimed yield: the mid-epoch depositor extracts a fraction of `totalInterestDueNow()` proportional to their minted share, paid for entirely by pre-existing tranche holders whose price appreciation is diluted. The loss scales with accrued vault/borrower interest and deposit size; with a large deposit relative to TVL an attacker can siphon most of an epoch's interest.

### Likelihood Explanation
Requires deposits-during-epoch to be enabled (owner flag) on a programmable-borrower vault — a supported configuration, since nothing in `_checkProgrammableBorrowerMode` disables mid-epoch deposits. The attacker only needs to pass KYC (`isWalletAllowed`), deposit near `epochEndDate`, and wait for the honest manager's `stopEpoch`. No privileged collusion needed. Note: I was unable to fully read the `depositDuringEpoch` body in this pass; the finding assumes it prices shares off `virtualPrice`/`tranchePrice`/`expectedEpochInterest` without consulting `totalInterestDueNow()` — if it instead queries the programmable borrower for accrued interest, the issue is mitigated and should be downgraded.

### Recommendation
In programmable-borrower mode, price `depositDuringEpoch` (and any mid-epoch claim/withdraw preview) against `managed NAV + IProgrammableBorrower(borrower).totalInterestDueNow()` — i.e., invoke the "claim-equivalent" read of accrued interest before computing shares, mirroring the external report's "invoke claim() first" fix. Alternatively, disallow `isDepositDuringEpochDisabled == false` when `isProgrammableBorrower` is set.

### Proof of Concept
Foundry fork sketch (programmable mode, minted interest):

```solidity
// setup: programmable borrower vault, isInterestMinted = true,
// isDepositDuringEpochDisabled = false, honest manager.
idleCDO.depositAA(10_000e6);            // victim LP, buffer phase
cdoEpoch.startEpoch();                  // funds sent to ProgrammableBorrower -> ERC4626 vault

vm.warp(epochEnd - 1 days);
_accrueVaultYield();                    // vault appreciates; borrowerInterestAccrued grows
uint256 due = programmableBorrower.totalInterestDueNow(); // > 0
uint256 nav = cdoEpoch.getContractValue();                // excludes `due`

// attacker (KYC-passed) deposits late in the epoch
uint256 pxPre = cdoEpoch.virtualPrice(address(AAtranche));
idleCDO.depositDuringEpoch(largeAmount, attacker); // minted at price excluding `due`

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);               // mintStrategyTokens(due) -> NAV jumps

uint256 pxPost = cdoEpoch.virtualPrice(address(AAtranche));
// attacker redeems/requests next epoch at pxPost > pxPre,
// capturing share(largeAmount / nav) * due of pre-deposit yield.
assertGt(attackerValuePost - largeAmount, 0);
```

Key assertion: `getContractValue()` at mid-epoch excludes `totalInterestDueNow()`, yet `stopEpoch` later credits it — the gap is the extractable amount.
