## Analog Found

Marginfi's `Order` (take‑profit / stop‑loss) system reproduces the exact bug class from the report: an economic parameter (a "fee"/premium bound) is captured live from a globally mutable admin setting at *fulfillment* time rather than cached at *request* time.

### Title
Order execution max-fee is read live from `FeeState` at settlement instead of being cached at order placement, letting keepers extract a larger cut than the user consented to - (File: `programs/marginfi/src/instructions/marginfi_account/order.rs`)

### Summary
`marginfi_account_place_order` creates an `Order` account but never snapshots the current `order_execution_max_fee` from the global `FeeState`. When a keeper later executes the order via `end_execute_order`, the program re-reads the *current* `fee_state.order_execution_max_fee` to compute the minimum amount the user must retain. Because `global_fee_admin` can raise this value at any time via `edit_global_fee_state`, an order placed under one fee assumption can be executed under a materially larger allowed keeper premium, letting the permissionless keeper take a bigger cut of the user's collateral than existed when the order was placed — mirroring the reported "fulfilments based on variable service fee" bug class.

### Finding Description
`place_order` (permissionless, user-initiated) stores trigger thresholds/slippage on the `Order` account but does not cache any execution-fee bound: [1](#0-0) 

`end_execute_order`, called later by any permissionless keeper, fetches the *current* global fee state and uses `order_execution_max_fee` live to compute the `max_fee_frac` floor that bounds how much of the user's equity a take-profit execution may consume: [2](#0-1) 

That live value is then applied to gate the take-profit and "both" cases, determining the minimum amount `net` the user must be left with (`allowed_diff`): [3](#0-2) 

`order_execution_max_fee` lives on the global, admin-mutable `FeeState` and can be changed at any time between order placement and execution via `edit_global_fee_state`: [4](#0-3) [5](#0-4) 

This is functionally identical to the reported bug: a user-initiated request (`Order`) references a fee parameter that is not fixed at request time, so a "fulfillment" (order execution) performed by an unprivileged, permissionless actor (the Keeper) is settled against whatever fee value is live at that moment rather than the one the user implicitly accepted at placement. The project's own tests demonstrate the raw mechanics of this fee being adjustable and directly gating settlement outcomes: [6](#0-5) 

### Impact Explanation
If `order_execution_max_fee` is raised while take-profit/stop-loss orders are outstanding (a normal admin action, not a compromise), every subsequently-executed order becomes subject to a larger allowed keeper premium than was in force when the user created the order. A permissionless keeper executing `start_execute_order`/`end_execute_order` can then withdraw a larger cut of the user's collateral on take-profit settlement than the constraint the user relied on at order placement — a value-redirection with real financial effect on the user's account, without any additional user consent or re-signing. This is a lesser variant of the reported issue (bounded by `ORDER_EXECUTION_MAX_FEE`/admin policy rather than unbounded), but it is a concrete accounting/value-extraction bug reachable through the permissionless keeper-execution path.

### Likelihood Explanation
Orders can remain open indefinitely (until their price trigger fires), so any admin fee-state edit that happens while orders are outstanding will silently apply to all pending orders' eventual settlement, with no explicit warning to affected users and no need for any special timing on the attacker/keeper side — the very next permissionless `EndExecuteOrder` for a triggered order picks up the new value automatically.

### Recommendation
Cache `order_execution_max_fee` (and `max_slippage`, which is already cached) on the `Order` account at `place_order` time, and use that cached value in `end_execute_order`'s fee/slippage bound checks instead of re-reading the live `FeeState`. This guarantees users are always executed against the fee terms in effect when they created the order, consistent with the recommendation in the source report (cache the fee at request time).

### Proof of Concept
1. User calls `marginfi_account_place_order` to set a `TakeProfit` order; at this time `fee_state.order_execution_max_fee = 5%`.
2. Before the price trigger is hit, `global_fee_admin` calls `edit_global_fee_state` to raise `order_execution_max_fee` to, e.g., 20% (a legitimate-looking policy change, no compromise required).
3. Price trigger condition is met; a permissionless keeper calls `marginfi_account_start_execute_order` / `marginfi_account_end_execute_order`.
4. In `end_execute_order`, `max_fee_frac` is computed from the now-current 20% value (`programs/marginfi/src/instructions/marginfi_account/order.rs:418-421`), producing a much smaller `allowed_diff` floor (`start_health * (1 - 0.20)` instead of `start_health * (1 - 0.05)`).
5. The keeper can legally withdraw down to this lower floor, leaving the user with materially less equity than the 5% bound they saw/accepted at order placement, and the transaction succeeds where it would have reverted (`OrderExecutionOverWithdrawal`) under the original 5% cap — demonstrating the same fee-state race the report describes, applied to Marginfi's order settlement path.
