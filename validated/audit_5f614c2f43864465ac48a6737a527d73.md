Based on my analysis, I found a genuine analog: `staking_contract::switch_operator` leaves a stale commission distribution entry keyed to the *old* operator's address, but the beneficiary-redirect check in `distribute_internal` compares that stale recipient against the *new* (current) operator parameter — causing outstanding commission to bypass the old operator's configured beneficiary.

### Title
Stale Commission Distribution Recipient Bypasses Operator Beneficiary Redirect After `switch_operator` - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`distribute_internal` redirects payouts owed to "the operator" to that operator's registered beneficiary only when the stored distribution `recipient` equals the `operator` address passed into the call. `switch_operator` adds a pending commission distribution keyed to the *old* operator, then re-keys the `StakingContract` under the *new* operator in the `Store.staking_contracts` map. Any later public call to `distribute` for that pool passes the *new* operator as the `operator` argument, so the equality check `recipient == operator` fails for the old operator's leftover commission, and the funds are paid directly to the old operator's raw account instead of to the beneficiary the old operator had configured via `set_beneficiary_for_operator`.

### Finding Description
`request_commission_internal` records a pending payout via `add_distribution(operator, staking_contract, operator, commission_amount)` — the distribution's shareholder key is the operator address active *at that moment*. [1](#0-0) 

`switch_operator` calls `request_commission_internal(old_operator, &mut staking_contract)` (recording the pending commission under `old_operator`), then changes the pool operator and re-inserts the `StakingContract` into `staking_contracts` under `new_operator`: [2](#0-1) 

`distribute_internal` later iterates the `distribution_pool` and only redirects a payout to `beneficiary_for_operator(operator)` when `recipient == operator`, where `operator` is the argument passed to `distribute`/`distribute_internal` for the *current* key in the map (i.e. `new_operator`), not the address that actually earned the commission (`old_operator`): [3](#0-2) 

Because `switch_operator` asserts `new_operator != old_operator` (via the `!contains_key(new_operator)` check while `old_operator` is still present), the stale `recipient == old_operator` can never equal the `operator == new_operator` parameter used at distribution time, so the beneficiary lookup is permanently skipped for that pending amount.

### Impact Explanation
This matches the "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account" impact class: the accrued commission is credited directly to the old operator's raw signing address instead of the beneficiary address the operator explicitly configured for receiving commission via `set_beneficiary_for_operator`. Operators commonly separate a hot operator/signing key from a custody/beneficiary address for security reasons; this bug silently defeats that separation for any commission that was requested but not yet distributed at the time of an operator switch, sending value to a potentially less-secure or unintended account without the beneficiary's knowledge.

### Likelihood Explanation
No special privilege is required: `switch_operator`/`switch_operator_with_same_commission` are ordinary staker-callable entry functions, `set_beneficiary_for_operator` is an ordinary operator-callable entry function, and `distribute` is explicitly `public entry` and callable by anyone. Any staker who switches operators while a commission request is outstanding (a routine flow, since `switch_operator` itself force-triggers a fresh `request_commission_internal` for any newly accrued rewards) will trigger this misdirection once the lockup expires and someone calls `distribute`.

### Recommendation
Store the intended recipient's *operator identity* (or resolve the beneficiary at `add_distribution` time and store the beneficiary directly) rather than re-deriving "is this the operator" by comparing to the *current* operator parameter passed into `distribute`. Alternatively, force full settlement/distribution of any outstanding operator commission using the *old* operator's beneficiary mapping before re-keying the `StakingContract` under `new_operator`, ensuring no distribution entry keyed to `old_operator` ever survives the switch.

### Proof of Concept
1. Staker `S` creates a staking contract with operator `O1`, commission 10%, via `create_staking_contract`.
2. `O1` calls `set_beneficiary_for_operator(O1, B)` to register beneficiary `B`.
3. Time passes and epoch(s) end so the pool earns rewards (accrued commission for `O1`).
4. `S` calls `switch_operator(S, O1, O2, new_commission)`:
   - `request_commission_internal(O1, ...)` adds a distribution entry `recipient = O1` for the newly accrued commission and unlocks it (`stake::unlock_with_cap`).
   - The pool operator is changed to `O2`, and the `StakingContract` is re-inserted into `Store.staking_contracts` under key `O2`.
5. Wait for the stake pool lockup to expire so the unlocked commission becomes `inactive`.
6. Anyone calls `distribute(S, O2)` (the only valid key now, per `assert_staking_contract_exists`): `distribute_internal(S, O2, staking_contract)` withdraws the inactive coins and iterates the distribution pool; it finds `recipient = O1`, compares `O1 == O2` (false), skips the `beneficiary_for_operator(O1)` lookup, and pays the commission directly to `O1`'s address instead of `B`.
