Based on the investigation, I found a solid structural analog to the "Sales Cannot Be Frozen" bug class: a feature-disable/freeze control that is enforced only at resource-creation time but not at the point where the sensitive action (authentication/execution) actually occurs.

### Title
External Initiator Authentication Bypasses the `ExternalInitiatorsEnabled` Disable Control - (File: `core/web/auth/auth.go`)

### Summary
The `JobPipeline.ExternalInitiatorsEnabled` config flag is intended to act as the on/off switch (analogous to "freeze/unfreeze") for the External Initiator (EI) feature. It is checked only when a new `ExternalInitiator` is created, but the actual authentication method that authorizes EI-triggered job runs never re-checks this flag, so once credentials exist, disabling the feature does not revoke their ability to authenticate and trigger runs.

### Finding Description
`ExternalInitiatorsController.Create` gates creation of new EI credentials on the config flag: it returns a 405 if `App.GetConfig().JobPipeline().ExternalInitiatorsEnabled()` is false [1](#0-0) . However, the runtime authentication path used to actually authorize EI requests, `AuthenticateExternalInitiator` in `core/web/auth/auth.go`, only validates the access key/secret against stored `ExternalInitiator` records via `store.FindExternalInitiator` and `bridges.AuthenticateExternalInitiator` — it never consults the `ExternalInitiatorsEnabled` config value [2](#0-1) . This mirrors the `sale.rs` pattern: a state/flag exists conceptually as a control gate (`SaleState::Frozen` / `ExternalInitiatorsEnabled`), a check for it exists somewhere (only at `PurchaseTokens` / only at `Create`), but there is no enforcement of that gate at the actual privileged action's authorization boundary (freeze toggle / live authentication), leaving previously-issued credentials or state functioning as if the control never existed.

Once an `ExternalInitiator` record exists in the DB (created while the feature was enabled), disabling `ExternalInitiatorsEnabled` afterward — the operator's intended way to shut off this remote-trigger surface — has no effect on existing credentials, because `AuthenticateExternalInitiator` and the underlying `bridges.AuthenticateExternalInitiator` / `FindExternalInitiator` calls perform no config check [3](#0-2) .

### Impact Explanation
An operator who disables `ExternalInitiatorsEnabled` (e.g., in response to a security incident, to stop external-initiator job triggering, or as a hardening step) does not actually revoke the ability of holders of previously-issued EI `AccessKey`/`Secret` pairs to authenticate as the `run` role and trigger job runs. The `AuthenticateExternalInitiator` handler still sets `SessionUserKey` to a user with `UserRoleRun` [4](#0-3) , permitting continued unauthorized job execution against operator intent — an unauthorized-job-run class impact despite the control being "disabled."

### Likelihood Explanation
Exploitation requires only possession of a previously-valid EI `AccessKey`/`Secret` pair (which may have been leaked, retained by a former integration partner, or belong to a bridge/adapter that should have been cut off). No privilege escalation or additional bypass is needed beyond simply continuing to send the same credentials after the operator believes the feature has been turned off.

### Recommendation
Enforce the `ExternalInitiatorsEnabled` config check inside `AuthenticateExternalInitiator` in `core/web/auth/auth.go` (or in `bridges.AuthenticateExternalInitiator`) so that when the feature flag is disabled, all EI authentication attempts fail immediately regardless of whether valid credentials are presented, matching operator expectations that disabling the feature revokes the entire attack surface, not just future credential creation.

### Proof of Concept
1. Enable `ExternalInitiatorsEnabled=true`; create an `ExternalInitiator` via `POST /v2/external_initiators`, capturing its `AccessKey`/`Secret` [5](#0-4) .
2. Set `ExternalInitiatorsEnabled=false` and restart/reload config.
3. Send a request to any route protected by `auth.AuthenticateExternalInitiator` (e.g. `/v2/ping/` or a webhook-triggering route) with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the previously captured values, as done in `TestTokenAuthRequired_TokenCredentials` [6](#0-5) .
4. Observe the request still authenticates successfully (HTTP 200) with `run` role privileges, despite the feature being disabled.

	ctx := c.Request.Context()

// Implements authMethod
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}

	t.Parallel()

	app := cltest.NewApplicationEVMDisabled(t)
