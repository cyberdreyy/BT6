### Title
Missing sender allowlist/rate-limit enforcement in legacy webapi trigger path allows any signer to force DON-wide execution billed to the workflow owner - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` decodes and timestamp-validates a `TriggerRequestPayload`, then fans it out to every DON member without checking whether the message sender is authorized (allowlisted) for the target workflow/owner, exactly as flagged by the `// TODO: apply allowlist and rate-limiting here` comment. `Message.Validate()` only checks signature format/length and recovers the signer address — it performs no authorization against `donConfig` or any workflow-owner allowlist.

### Finding Description
The request flow is: `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-291`) decodes the JSON-RPC envelope, calls `msg.Validate()` (`core/services/gateway/api/message.go:54-88`) — which only validates field lengths and recovers/sets `msg.Body.Sender` from the ECDSA signature, with **no lookup against an allowlist or owner registry** — then routes to `h.HandleLegacyUserMessage(ctx, msg, callback)`.

Inside `HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`), the checks performed are: payload JSON-decodable, `Timestamp != 0`, and message not stale (`payload.Timestamp` within `MaxAllowedMessageAgeSec`). Immediately after these checks sits the literal comment `// TODO: apply allowlist and rate-limiting here` (line 384), followed only by a method-name check (`MethodWebAPITrigger`). There is no check that `msg.Body.Sender` is permitted to trigger the specific workflow/topic, nor any quota/rate-limit enforcement. The handler then unconditionally loops `for _, member := range h.donConfig.Members { don.SendToNode(ctx, member.Address, req) }` (lines 416-419), fanning the request out to the entire DON.

Any party capable of producing a validly-signed `api.Message` (i.e., any ECDSA keypair — this requires no privileged credential, membership in `donConfig`, or workflow-owner relationship) satisfies every enforced check and triggers full DON-wide execution. This is corroborated by the accompanying test file's own acknowledgment: `core/services/gateway/handlers/capabilities/handler_test.go:365` — `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated`, and by the "happy case" test (`handler_test.go:236-265`) which fans out successfully with only a locally-generated key not tied to any owner/allowlist relationship.

By contrast, the newer v2 HTTP trigger path (`core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go`) demonstrates that rate-limiting and workflow-owner/reference resolution are expected security controls for triggering workflow execution — confirming these controls are architecturally required but absent from the legacy v1 path being fanned out to DON nodes.

### Impact Explanation
This matches the Chainlink bounty impact class of unauthorized/free resource consumption at the workflow owner's expense: an unprivileged, unauthenticated (with respect to any allowlist) sender can force DON member nodes to execute workflow logic (`MethodWebAPITrigger`) that is normally gated to be paid/authorized by the workflow owner, causing free DON compute paid for by the owner, plus potential denial-of-service/resource exhaustion of the DON via repeated fan-out (no rate limiting either). It does not directly leak secrets or forge admin privileges, but it is a real authorization-bypass on a billable/execution-triggering action.

### Likelihood Explanation
Fully unauthenticated relative to the workflow: the only precondition is possessing any ECDSA keypair to sign a well-formed `TriggerRequestPayload` with a fresh `Timestamp` and `Method: MethodWebAPITrigger` — trivial and fully repeatable via a simple HTTP POST to the gateway's user-facing endpoint. No operator/admin access, no leaked credentials, no allowlist entry needed, since the code path performing that check does not exist (only a TODO comment marks its absence).

### Recommendation
Implement the allowlist/rate-limiting check exactly where the TODO indicates, before the fan-out loop in `HandleLegacyUserMessage`: resolve `msg.Body.Sender` (or an equivalent request digest/owner claim in the payload) against the workflow's registered allowlist (similar to `allowListBasedAuth.AuthorizeRequest` in `core/capabilities/vault/allow_list_based_auth.go`) and reject with `api.UserMessageParseError`/an authorization error code if the sender is not permitted; additionally apply a per-sender rate limiter (mirroring `h.nodeRateLimiter` used for outgoing node messages) before calling `don.SendToNode` in the loop.

### Proof of Concept
Go unit test plan added to `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build `handler` via `setupHandler(t)` with a `donConfig` containing members but no allowlist entry for an arbitrary test key.
2. Generate a fresh, unregistered ECDSA key (`unprivilegedKey`) not present in any allowlist/registry.
3. Construct via `triggerRequest(t, unprivilegedKey, []string{"daily_price_update"}, "", "", "")` — valid `Timestamp`, `Method: MethodWebAPITrigger`, correctly signed.
4. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)`.
5. Assert (current buggy behavior): `don.SendToNode` is invoked for every `donConfig.Members` entry (`mock.AssertExpectations`/`.Once()` per member) and `cb.Wait` returns a successful `NoError` callback — i.e., fan-out occurs despite the sender having no allowlist relationship to any workflow owner.
6. Intended/fixed behavior assertion: `don.SendToNode` should never be called, and the callback should receive an error response (e.g., a new `api.UnauthorizedSenderError` code) when the sender is not allowlisted for the requested `TriggerId`/topic — this second assertion should currently FAIL, confirming the gap.
