### Title
Post-cutoff queued deposit permanently bricks the prefunded epoch stop flow — (File: contracts/IdleCDOEpochQueue.sol)

### Summary
In the prefunded-queue deployment, a KYC-passing attacker can queue a minimal `requestDeposit` during the running epoch, timed so that the honest manager can no longer move it to the borrower via `processDepositsToBorrower`. The stranded `epochPendingDeposits[nextEpoch]` makes `prefundedDepositsToProcess()` revert forever, which blocks the prefunded variant's epoch-settlement path and permanently freezes all pool funds at the borrower. This mirrors the CVE-2018-2591 bug class: a low-privilege trigger that hangs a critical service function.

### Finding Description
`IdleCDOEpochQueue.requestDeposit` records deposits for `epochNumber + 1` and, on the AA prefunded queue, only rejects them once funds were already prefunded or once the subscription cutoff is reached — deposits are still accepted while `block.timestamp + prefundedDepositWindow < epochEndDate`. [1](#0-0) 

`processDepositsToBorrower`, the only function that clears `epochPendingDeposits` into `epochPrefundedDeposits`, is gated by the exact same cutoff (`block.timestamp + _prefundedWindow < _cdo.epochEndDate()`), can run only once per epoch, and is callable only by owner/manager. [2](#0-1) 

`prefundedDepositsToProcess`, invoked by the prefunded CDO variant during epoch settlement, hard-reverts whenever the target epoch still has raw pending deposits: `_checkNotAllowed(epochPendingDeposits[_epoch] != 0)`. [3](#0-2) 

Attack sequence (running epoch, prefunded AA queue, nonzero `prefundedDepositWindow`):
1. Wait until `block.timestamp + prefundedDepositWindow` is just below `epochEndDate` — or simply deposit after the manager's last prefund for that epoch.
2. Call `requestDeposit(1)` (or any dust amount satisfying `checkPrefunding`). This sets `epochPendingDeposits[nextEpoch] = 1`.
3. After the cutoff, `processDepositsToBorrower` reverts at its window check, so the pending deposit can never be prefunded. The attacker simply never calls `deleteRequest`, and no one else can clear `userDepositsEpochs[attacker][nextEpoch]`.
4. At `stopEpochWithDuration`, the prefunded settlement path calls `prefundedDepositsToProcess`, which reverts on `epochPendingDeposits[nextEpoch] != 0` — permanently, since the deposit is neither prefundable nor forcibly deletable.

### Impact Explanation
Permanent freezing of funds: the epoch can never be stopped through the prefunded settlement path, so all borrower-held principal and all LP/tranche funds in the vault remain locked indefinitely. Cost to the attacker is one dust deposit plus gas, and they retain the ability to recover their own dust via `deleteRequest` at any time — the griefing is economically free. Existing guards do not help: `deleteRequest` only removes the caller's own deposit, `checkPrefunding` only caps totals, and the cutoff is what creates the dead zone in the first place.

### Likelihood Explanation
Requires only a KYC-passing wallet (in-scope attacker) and a queue-configured `prefundedDepositWindow`. The deposit can be placed via a private transaction at the tail of the window so the manager has no practical opportunity to prefund it. Uncertainty: I could not fully read `IdleCDOEpochVariantPrefunded` to confirm whether a plain `stopEpoch` (which skips the post-stop hook but may still hit `_beforeStopEpoch`, described as guarding direct stops) offers an escape hatch; if `stopEpoch` also routes through `prefundedDepositsToProcess` or the pending-deposit check, the freeze is total. If a fallback path exists that ignores pending queue deposits, impact degrades to stranded queue deposits only.

### Recommendation
Decouple the two cutoffs: keep the deposit cutoff for `requestDeposit`, but allow `processDepositsToBorrower` to run until the epoch actually ends (drop or relax its `prefundedDepositWindow` gate), so any last-minute pending deposit can still be swept to the borrower. Alternatively, let `prefundedDepositsToProcess`/the stop flow tolerate residual `epochPendingDeposits` by treating them as next-epoch deposits, or add a manager function that force-refunds leftover pending deposits to their owners before settlement.

### Proof of Concept
```solidity
// Foundry fork test sketch (prefunded AA queue enabled, prefundedDepositWindow = W)
function testPendingDepositBlocksPrefundedStop() public {
    // epoch running; queue has been prefunded or not yet — irrelevant
    uint256 end = cdoEpoch.epochEndDate();
    vm.warp(end - W - 1); // still inside the deposit window, ~1s to spare

    // attacker: KYC-passing lender, dust deposit for next epoch
    deal(address(underlying), attacker, 1);
    vm.startPrank(attacker);
    underlying.approve(address(aaQueue), 1);
    aaQueue.requestDeposit(1);
    vm.stopPrank();
    assertEq(aaQueue.epochPendingDeposits(strategy.epochNumber() + 1), 1);

    // cutoff passes; manager can no longer prefund the dust deposit
    vm.warp(end - W);
    vm.prank(manager);
    vm.expectRevert(); // window check
    aaQueue.processDepositsToBorrower();

    // epoch ends; borrower repaid and approved; prefunded stop still reverts
    vm.warp(end + 1);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector); // epochPendingDeposits != 0
    cdoEpoch.stopEpochWithDuration(newApr, 0, duration, 0);

    // repeat: still blocked — funds frozen at borrower indefinitely
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpochWithDuration(newApr, 0, duration, 0);
}
```
