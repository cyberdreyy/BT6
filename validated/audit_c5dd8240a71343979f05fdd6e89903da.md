### Title
ETH sent with `withdrawAA`/`withdrawBB` in `IdleCDOEthenaVariant` is locked in the one-off cooldown clone with no refund path - (File: contracts/IdleCDOEthenaVariant.sol)

### Summary
`IdleCDOEthenaVariant._withdraw` forwards `msg.value` into the `ClonesWithImmutableArgs.clone` call that deploys a per-request `EthenaCooldownRequest` contract. The clone has no ETH withdrawal path for the user — its only sweep function is `rescue`, gated to `TL_MULTISIG`. Any ETH attached to a withdraw call is stranded in a freshly deployed clone whose address is only emitted in an event, and the tranche holder's excess payment is never credited or refunded — the same "overpayment absorbed by the contract" bug class as the Footium `mintPlayers` finding.

### Finding Description
In `contracts/IdleCDOEthenaVariant.sol` lines 82-85, `_withdraw` (invoked via the external `withdrawAA`/`withdrawBB` payable entry points of `IdleCDO`) does:

```solidity
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender),
  msg.value
));
```

`ClonesWithImmutableArgs.clone(impl, data, value)` performs a `create` endowed with `value`, so all `msg.value` lands on the new clone's balance. The clone (`contracts/strategies/ethena/EthenaCooldownRequest.sol`) exposes only:

- `startCooldown()` — callable only by the CDO (line 16),
- `unstake()` — sends sUSDe proceeds to the user, does not touch ETH (line 23),
- `rescue(_token)` — restricted to `TL_MULTISIG` and transfers only ERC20 via `IERC20Detailed(_token).transfer` (lines 27-30).

There is no `receive`-aware accounting, no refund of `msg.value`, and `rescue` cannot even move native ETH (`IERC20Detailed(0x0).transfer` would fail). The protocol presumably intends `msg.value == 0` — ETH is not needed for the cooldown flow at all — but there is no `require(msg.value == 0)` guard and the payable entry path silently accepts it.

### Impact Explanation
A tranche holder calling `withdrawAA`/`withdrawBB` (or a contract integrating the CDO) that attaches any nonzero `msg.value` — e.g. a multicall or wallet that bundles value, or a user replicating a payable-deposit pattern — permanently loses that ETH. It sits on an ephemeral clone address owned by no one; `rescue` cannot retrieve native ETH because it only does ERC20 `transfer`, and only `TL_MULTISIG` may call it anyway. Broken invariant: user funds not part of the protocol flow must be returned or credited; here the contract keeps the overpayment with no pull mechanism — exactly the Footium scenario (send 1 ETH, owe 0, lose the difference forever).

### Likelihood Explanation
Likelihood is moderate: it requires a user to send ETH on a withdraw call, which correct usage wouldn't do. However the function signature accepts it silently, the ETH-denominated variants of this codebase (Lido gateway, WETH paths) make payable interactions plausible, and loss is permanent and unquantifiable only by the amount attached. No guard (`skim`, default check, epoch gating) stops it — `_checkSameBlock` and `_checkDefault` run before the clone creation and do not inspect `msg.value`.

### Recommendation
Either make the withdraw entry non-payable, or explicitly reject value and forward nothing:

```solidity
require(msg.value == 0, 'no-eth');
```

and call `cooldownImpl.clone(abi.encodePacked(address(this), msg.sender))` with no value. Alternatively refund `msg.value` to `msg.sender` at the end of `_withdraw`. Optionally add a native-ETH sweep branch in `EthenaCooldownRequest.rescue`.

### Proof of Concept
Foundry fork test (mainnet, sUSDe cooldown active):

```solidity
function test_WithdrawETHStuckInClone() public {
    // setup: user holds AA tranche tokens, sUSDe cooldownDuration() != 0
    uint256 trancheAmt = trancheAA.balanceOf(user);
    uint256 ethSent = 0.5 ether;
    vm.deal(user, ethSent);

    vm.recordLogs();
    vm.prank(user);
    cdoEthena.withdrawAA{value: ethSent}(trancheAmt); // payable entry -> _withdraw

    // parse NewCooldownRequestContract event for clone address
    address clone = getCloneFromLogs();
    assertEq(clone.balance, ethSent);        // ETH sits on clone
    assertEq(user.balance, 0);               // user got nothing back
    // no user-callable function exists on clone to recover ETH;
    // rescue() is TL_MULTISIG-only and only moves ERC20 -> ETH unrecoverable
}
```

Note: I was unable to confirm the exact `payable` modifiers on `withdrawAA`/`withdrawBB` in `IdleCDO.sol` (the grep returned match counts, not line contents). If those entry points are non-payable, `msg.value` is always zero and this reduces to dead code rather than a live loss path — that check is the gating step for the PoC.
