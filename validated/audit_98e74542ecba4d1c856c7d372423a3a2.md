### Title
Fungible `unstaked` balance shares a single unlock-epoch gate with new deposits, causing newly-deposited funds to be frozen after a prior unstake - (File: staking-pool/src/internal.rs)

### Summary
`Account.unstaked` is a single fungible balance and `Account.unstaked_available_epoch_height` is a single scalar gate covering that whole balance. `internal_deposit` (staking-pool/src/internal.rs:24-40) adds to `account.unstaked` without touching `unstaked_available_epoch_height`, while `inner_unstake` (staking-pool/src/internal.rs:124-181) sets that same scalar to `env::epoch_height() + NUM_EPOCHS_TO_UNLOCK`. `internal_withdraw` (staking-pool/src/internal.rs:42-68) then gates ANY withdrawal amount ≤ `account.unstaked` by that single scalar.

### Finding Description
Binding claimed: `withdrawable_amount(deposit_portion) == freely_available_deposit`, i.e. NEAR that was deposited fresh via `deposit()`/`deposit_and_stake()` (with no unstake history) should be withdrawable in the same block/epoch it was deposited, independent of any older unstake lock on the same account.

Trace:
1. Delegator calls `unstake(amount)` → `inner_unstake` at staking-pool/src/internal.rs:124-181 increases `account.unstaked` by `receive_amount` and sets `account.unstaked_available_epoch_height = env::epoch_height() + 4` (staking-pool/src/internal.rs:156, constant at staking-pool/src/lib.rs:85).
2. Same delegator calls `deposit()` (staking-pool/src/lib.rs:217-225) attaching new NEAR. `internal_deposit` (staking-pool/src/internal.rs:24-40) does `account.unstaked += amount` but never reads or writes `unstaked_available_epoch_height`.
3. Delegator calls `withdraw(amount: U128)` (staking-pool/src/lib.rs:254-263) for exactly the freshly deposited amount. `internal_withdraw` (staking-pool/src/internal.rs:42-68) checks `account.unstaked >= amount` (true) and then `assert!(account.unstaked_available_epoch_height <= env::epoch_height())`, which is still the OLD future epoch from step 1 and fails, panicking with "The unstaked balance is not yet available due to unstaking delay".

Root cause: the contract conflates two logically distinct balances (funds released from unstaking, subject to a lock, vs. freshly deposited liquid funds, never locked) into one `unstaked` field guarded by one scalar epoch height, and `internal_deposit` never resets/relaxes that gate for the portion it adds. Existing guards (`internal_ping`, `assert_owner`, etc.) do not address this because the check is purely `account.unstaked_available_epoch_height <= env::epoch_height()`, which has no per-source granularity.

### Impact Explanation
No NEAR is stolen or permanently lost; the delegator's own freshly-deposited NEAR (which has no unstaking history and should be immediately withdrawable) is frozen inside the pool contract for up to `NUM_EPOCHS_TO_UNLOCK` (4) epochs, until the older unstake's lock naturally expires. This matches the "High" impact category: funds frozen for at least one epoch but recoverable. It affects only the delegator's own funds (self-inflicted via ordinary usage, not an attacker extracting value from a victim), is deterministic and repeatable by any delegator who has a pending unstake and then deposits before the 4-epoch window elapses.

### Likelihood Explanation
This requires no special privilege — any delegator can trigger it simply by calling `unstake` and then `deposit` + `withdraw` within the same 4-epoch window, which is a very plausible ordinary usage pattern (e.g., a user unstakes some funds, later deposits more to stake/manage their position, then wants to withdraw the new deposit for another purpose). No attacker capital beyond normal deposit amounts is needed, and it is trivially reproducible in a unit test with `testing_env!` epoch manipulation.

### Recommendation
Track the withdrawal-lock scope more granularly, e.g., either: (a) reset `unstaked_available_epoch_height` only relative to the unstaked-derived portion by tracking unstaked-vs-deposited sub-balances separately, or (b) upon `internal_deposit`, if `account.unstaked_available_epoch_height <= env::epoch_height()` already (no pending lock), leave as is; but if there is a pending lock, split the balance so freshly deposited funds are not subject to the old unstake's lock (e.g., maintain a separate `available_unstaked`/`pending_unstaked` pair, or record deposits with their own epoch height and pick the max of what's actually locked when withdrawing only up to the locked portion). At minimum, document this behavior explicitly if intentionally accepted, since it silently freezes non-unstake-derived deposits.

fn test_deposit_after_unstake_locks_new_deposit() {

        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".to_string(),

    emulator.contract.deposit_and_stake();
    emulator.amount += deposit_amount;
    emulator.simulate_stake_call();

    // Unstake half -> sets unstaked_available_epoch_height = epoch + 4
    emulator.update_context(bob(), 0);
    emulator.contract.unstake((deposit_amount / 2).into());
    emulator.simulate_stake_call();

    // Now deposit a fresh amount with NO unstake history
    let fresh_deposit = ntoy(10);
    emulator.update_context(bob(), fresh_deposit);
    emulator.contract.deposit();
    emulator.amount += fresh_deposit;

    // Attempt to withdraw exactly the fresh deposit, same epoch, before the 4-epoch unlock
    emulator.update_context(bob(), 0);
    let result = std::panic::catch_unwind(std::panic::AssertUnwindSafe(|| {
        emulator.contract.withdraw(fresh_deposit.into());
    }));
    // Binding claimed: fresh_deposit should be withdrawable == true, but it panics
    assert!(result.is_err(), "expected withdraw of freshly deposited funds to panic due to shared unlock gate");
}

    pub(crate) fn inner_unstake(&mut self, amount: u128) {
        assert!(amount > 0, "Unstaking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        assert!(
            self.total_staked_balance > 0,
            "The contract doesn't have staked balance"
        );
        // Calculate the number of shares required to unstake the given amount.
        // NOTE: The number of shares the account will pay is rounded up.
        let num_shares = self.num_shares_from_staked_amount_rounded_up(amount);
        assert!(
            num_shares > 0,
            "Invariant violation. The calculated number of \"stake\" shares for unstaking should be positive"
        );
        assert!(
            account.stake_shares >= num_shares,
            "Not enough staked balance to unstake"
        );

        // Calculating the amount of tokens the account will receive by unstaking the corresponding
        // number of "stake" shares, rounding up.
        let receive_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);
        assert!(
            receive_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        account.stake_shares -= num_shares;
        account.unstaked += receive_amount;
        account.unstaked_available_epoch_height = env::epoch_height() + NUM_EPOCHS_TO_UNLOCK;
        self.internal_save_account(&account_id, &account);

pub struct Account {
    /// The unstaked balance. It represents the amount the account has on this contract that
    /// can either be staked or withdrawn.
    pub unstaked: Balance,
    /// The amount of "stake" shares. Every stake share corresponds to the amount of staked balance.
    /// NOTE: The number of shares should always be less or equal than the amount of staked balance.
    /// This means the price of stake share should always be at least `1`.
    /// The price of stake share can be computed as `total_staked_balance` / `total_stake_shares`.
    pub stake_shares: NumStakeShares,
    /// The minimum epoch height when the withdrawn is allowed.
    /// This changes after unstaking action, because the amount is still locked for 3 epochs.
    pub unstaked_available_epoch_height: EpochHeight,
}
