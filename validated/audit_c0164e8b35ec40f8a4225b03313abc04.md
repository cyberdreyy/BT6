### Title
Integer underflow on stale `instantWithdrawsRequestsByEpoch` entry permanently freezes a user's default-recovery claim - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` zeroes the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch bucket `instantWithdrawsRequestsByEpoch[_user][epoch]`. If the borrower defaults in the same epoch after a user already claimed a funded instant receipt and then re-requested, `_claimDefaultedInstantWithdrawRequest` reads a `claimBasis` larger than the aggregate and the subtraction `instantWithdrawsRequests[_user] -= claimBasis` underflows, reverting every subsequent claim — a direct analog of CVE-2017-14997's integer-underflow DoS, mapped onto the vault's instant-withdraw receipt accounting.

### Finding Description
When a user requests an instant withdraw, `requestInstantWithdraw` records the amount twice: the per-user aggregate `instantWithdrawsRequests[_user]` and the per-epoch bucket `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (lines 366-374). When the request is funded, `claimInstantWithdrawRequest` burns the receipt and resets only the aggregate to 0 (lines 387-392); the per-epoch bucket is left stale.

`_claimDefaultedInstantWithdrawRequest` is only invoked once `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` (line 382). It computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (line 844) and then performs an unguarded subtraction `instantWithdrawsRequests[_user] -= claimBasis` (line 848) plus `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` (line 853). Because the epoch bucket is never cleaned on a funded claim, `claimBasis` can exceed the live aggregate whenever:

1. Epoch N is running; APR drops so the user calls `IdleCDOEpochVariant.requestWithdraw` which routes to `requestInstantWithdraw` (IdleCDOEpochVariant.sol:761-768). Receipt R1 is recorded in `instantWithdrawsRequests` and `instantWithdrawsRequestsByEpoch[N]`.
2. The borrower funds instant withdrawals; the user calls `claimInstantWithdrawRequest`. Aggregate → 0, but `instantWithdrawsRequestsByEpoch[N]` still holds R1.
3. Still within epoch N (epochNumber only increments at `stopEpoch`), the user requests again → aggregate = R2, bucket[N] = R1 + R2.
4. The borrower defaults; `finalizeDefault` sets `defaultRecoveryEpoch = N` and `defaultRecoveryPrice`.
5. Any later `claimInstantWithdrawRequest` executes `instantWithdrawsRequests[_user] -= claimBasis`, i.e., `R2 -= (R1 + R2)` → arithmetic underflow → revert.

The same stale-bucket pattern also corrupts `instantWithdrawClaimsByEpoch[defaultEpoch]` accounting even where the aggregate happens to be large enough.

### Impact Explanation
Permanent freezing of unclaimed yield/recovery: every subsequent `claimInstantWithdrawRequest` for that user reverts, so the defaulted-epoch instant receipt can never be paid out from `defaultRecoveryReserve`. The frozen amount equals the user's full defaulted instant receipt (`R2` plus any stale re-counted `R1` priced at `defaultRecoveryPrice`). Other users are unaffected, so the locked recovery reserve is effectively stranded. Loss magnitude: up to 100% of the affected user's instant-withdraw claim.

### Likelihood Explanation
Requires a borrower default in the same epoch in which a user claimed and re-requested an instant withdrawal — an uncommon but legitimate sequence driven entirely by unprivileged actions (the default is triggered by honest manager calls, which is allowed per the rules). The bug needs no privileged misbehavior: it is a pure accounting underflow on state the user controls. Given the atomic revert on Solidity ≥0.8, there is no recovery path, which raises severity despite the conditional trigger.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch bucket alongside the aggregate, e.g., `instantWithdrawsRequestsByEpoch[_user][epochNumber] = 0` (or track per-epoch funded status), before zeroing `instantWithdrawsRequests[_user]`. Alternatively, in `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` at `instantWithdrawsRequests[_user]` and at `instantWithdrawClaimsByEpoch[defaultEpoch]` before subtracting.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testPocStaleInstantEpochUnderflow() external {
    // setup: deposit AA, run an epoch, then stopEpoch with a lower APR so
    // requestWithdraw routes to requestInstantWithdraw (epoch N = epochNumber)
    idleCDO.depositAA(10_000e6);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // 1) instant withdraw request R1 in epoch N
    uint256 r1 = IERC20(AAtranche).balanceOf(address(this)) / 4;
    cdoEpoch.requestWithdraw(r1, address(AAtranche));

    // 2) borrower funds instant withdrawals; user claims -> aggregate=0, bucket[N]=R1 stale
    _startEpochAndCheckPrices(0); // epochNumber still N for receipt purposes
    deal(defaultUnderlying, borrower, 1_000_000e6);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    cdoEpoch.claimInstantWithdrawRequest(); // succeeds; bucket[N] NOT cleared

    // 3) re-request R2 in the same epoch N
    uint256 r2 = IERC20(AAtranche).balanceOf(address(this)) / 2;
    cdoEpoch.requestWithdraw(r2, address(AAtranche));

    // 4) borrower defaults in epoch N; finalizeDefault sets defaultRecoveryEpoch = N
    // ... drive default flow per _checkDefault() helpers ...

    // 5) claim reverts: instantWithdrawsRequests[user]=R2 < claimBasis=R1+R2 -> underflow
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: steps 4-5 depend on the exact default-finalization helpers in the test harness (`_checkDefault`, `finalizeDefaultRecovery`); I verified the accounting logic at `IdleCreditVault.sol:842-856` but did not trace the full default-finalization entry points within the available tool budget, so the PoC's middle section should be wired to the existing test helpers that produce `defaultInstantWithdrawsFinalized == true` for the same `epochNumber`.
