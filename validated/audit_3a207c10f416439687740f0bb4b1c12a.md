## Analysis

The reported TON bug is a "stale cached governance parameter" class: a proposal's execution relies on state that was snapshotted before critical parameters changed, and the executor never re-validates whether the actors/values behind the earlier approvals are still legitimate. The NEAR analog exists in the `multisig`/`multisig2` contracts: confirmations collected from a member are **not purged when that member is later removed**, so a removed member's confirmation still counts toward the live `num_confirmations` threshold at execution time.

### Title
Stale Confirmations From Removed Members Allow Multisig Requests to Execute Below the Live Threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
When a member is removed from the multisig via `DeleteMember`/`DeleteKey`, the contract only purges **requests originally submitted by** that member — it does not purge that member's **confirmations on other, still-pending requests**. Because `confirm()` compares the raw size of the stored confirmations set against the live `num_confirmations` value, a confirmation cast by a member who has since been removed remains counted as valid, letting a pending request be executed with fewer genuinely live confirmations than the current threshold requires.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member()` only cleans up requests where the removed member was the original signer: [1](#0-0) 

It never scans `self.confirmations` for entries containing the removed member's identity on *other* requests. Meanwhile, `confirm()` executes purely based on set cardinality vs. the live `num_confirmations`: [2](#0-1) 

Confirmations are stored as a plain `HashSet<String>` keyed by request id, created empty in `add_request()`: [3](#0-2) 

Nothing in `assert_valid_request()` re-validates that every entry already in a request's confirmation set still corresponds to a current member: [4](#0-3) 

The identical pattern exists in the legacy `multisig` contract, where `DeleteKey` only removes requests signed by the deleted key, not that key's confirmations elsewhere: [5](#0-4) 
and `confirm()` there likewise checks live `self.num_confirmations` against the (potentially stale) confirmations set: [6](#0-5) 

This is the exact custody binding the report describes for `master.fc`: "confirmations counted" (the persisted `HashSet` size) diverges from "live members" (the current `self.members` set / who is actually authorized today). A confirmation obtained under an old membership roster is not invalidated when the roster changes, exactly like a vote counted under an old `success_amount` in the TON report.

### Impact Explanation
This directly matches the specified Critical impact category: "a multisig request executed below threshold." A pending request (e.g., `Transfer`, `DeployContract`, `AddKey`/`AddMember` granting full access) can be pushed to execution with fewer than `num_confirmations` currently-authorized approvals, because a stale confirmation from a now-removed member is still tallied. This can result in unauthorized fund transfers, unauthorized code upgrades, or unauthorized key/member additions performed with a weaker-than-configured approval set — undermining the entire K-of-N security guarantee the multisig is supposed to provide.

### Likelihood Explanation
No special privilege beyond being (or having been) a multisig member is required, and member turnover (key rotation, offboarding, compromised-key replacement) is an expected, routine operation for any long-lived multisig. Any time a member is removed while they have outstanding confirmations on other pending requests, this condition triggers automatically — it does not require attacker-controlled timing beyond normal governance operations, and the remaining requesters/confirmers need not be aware a stale confirmation is silently counted.

### Recommendation
When removing a member (`DeleteMember` in `multisig2`, `DeleteKey` in `multisig`), iterate over **all** pending requests' confirmation sets — not just requests the member authored — and strip that member's confirmation from each. Equivalently, adopt a "live-member re-validation" approach analogous to the report's recommended versioning fix: on `confirm()`, filter the stored confirmation set to only entries still present in `self.members` before comparing its length to `num_confirmations`, so a stale confirmation can never count toward execution.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Attacker (member `A`) creates a malicious request `R` (e.g., `Transfer` to an attacker-controlled account) via `add_request_and_confirm` — confirmations = `{A}`.
3. Member `B` confirms `R` in good faith — confirmations = `{A, B}` (2/3, not yet executable).
4. Separately, the DAO legitimately removes `B` via a `DeleteMember` request (key rotation/offboarding) — `delete_member()` only checks `r.member == B` for requests *authored by* `B`; `R` was authored by `A`, so `R`'s stored confirmation set `{A, B}` is left untouched even though `B` is no longer a member.
5. Members are now `{A, C, D}`. Attacker (`A`) or a colluding remaining member gets one more live confirmation (from `C`, or reuses `D`), calling `confirm(R)` — the set becomes size 3, satisfying `confirmations.len() + 1 >= num_confirmations` (3 >= 3), so `execute_request(R)` fires.
6. Result: `R` executes with only 2 confirmations from currently valid members (`A` and `C`) plus 1 stale confirmation from removed member `B`, even though the DAO's live threshold requires 3 of the current 3 members — i.e., unanimous approval was silently bypassed by an approval that no longer represents an authorized party.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
