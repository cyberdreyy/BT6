### Title
Loss-adjusted withdrawal haircut is keyed only to `lastWithdrawRequest`, letting older-epoch receipts of the same user claim at par — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug is a lifetime mismatch: a waitqueue is freed while a poller still holds a reference. The analog in `IdleCreditVault` is a *pointer-lifetime* mismatch on the loss-adjusted claim state: `collectWithdrawFunds` records a per-epoch haircut in `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` resolves which epoch's receipts get haircut solely through `lastWithdrawRequest[_user]`, which only stores the user's *most recent* request epoch. Receipts the same user opened in earlier epochs remain in `withdrawsRequestsByEpoch` and are later paid at par via `_claimFundedWithdrawRequest`, even though the borrower only funded `pendingBasis * recoveryPrice`.

### Finding Description
A user can hold normal withdraw receipts in multiple epochs: `requestWithdraw` only forbids a new request when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` [1](#0-0) , so before any loss the user may stack `withdrawsRequestsByEpoch[user][e1]` and `withdrawsRequestsByEpoch[user][e2]` while `lastWithdrawRequest[user]` advances to `e2` [2](#0-1) .

When a `stopEpochWithDuration` loss occurs, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the *aggregate* `pendingWithdraws`, which includes the user's e1 receipts, and stores it only under `lossRecoveryPriceByEpoch[epochNumber]` [3](#0-2) . On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and clears only that single epoch's receipts [4](#0-3) . `_clearWithdrawClaimForEpoch` zeroes `withdrawsRequestsByEpoch[user][claimEpoch]` and subtracts only that epoch's piece from `withdrawsRequests[user]` [5](#0-4) , so the e1 remainder survives into `_claimFundedWithdrawRequest`, which pays `normalAmount` at par [6](#0-5) .

The haircut's "lifetime" (one epoch key) is not tied to the real lifetime of the receipts it was computed over (all epochs contributing to `pendingBasis`) — the exact same shape as the waitqueue freed while the poller's reference persists.

### Impact Explanation
The strategy only receives `pendingBasis * recoveryPrice` underlying, yet the multi-epoch user extracts `e1_amount * 1.0 + e2_amount * recoveryPrice`. The difference `e1_amount * (1 - recoveryPrice)` is paid out of funds reserved for other claimants, breaking the loss-socialization invariant and the "one receipt one haircut" invariant. The last claimers' funded receipts become unbacked — direct theft / insolvency bounded by the attacker's pre-loss receipt share and the haircut depth (up to near-total loss socialization escape if the attacker dominates `pendingWithdraws`).

### Likelihood Explanation
Requires only an unprivileged user (any address holding strategy-token receipts, i.e., any tranche holder via the CDO, or the queue contract itself) who requests withdrawals across two epochs before a `stopEpochWithDuration` loss. Losses are realized by honest owner/manager calls, so sequencing is entirely attacker-controlled: request in epoch N, skip claiming, request again in epoch N+1, wait for any loss-adjusted stop. No privileged misbehavior needed.

### Recommendation
Apply the loss-adjusted haircut to the user's *entire* `pendingBasis` contribution, not just the `lastWithdrawRequest` epoch. Either track loss-epochs per user (iterate all `withdrawsRequestsByEpoch` entries contributing to `pendingWithdraws`, or store a per-user claim basis at loss time), or block new `requestWithdraw` while *any* prior receipt exists (`_hasWithdrawRequest`), matching the post-default guard already used in `requestWithdraw` [7](#0-6) .

```solidity
// 1. user: cdoEpoch.requestWithdraw(x, AAtranche)  -> withdrawsRequestsByEpoch[user][N]

//                                                   lastWithdrawRequest = N+1
// 4. warp past epochEndDate; manager: stopEpochWithDuration(0, 0, duration, loss)
//    -> collectWithdrawFunds pulls pendingBasis * price; lossRecoveryPriceByEpoch[N+1] = price
// 5. user: cdoEpoch.claimWithdrawRequest()
//    -> _claimLossAdjustedWithdrawRequest pays y*price (epoch N+1 only)
//    -> _claimFundedWithdrawRequest pays x at par
// Assert: strategy underlying balance is now insufficient to cover remaining
// pending claims of other users (or the user extracted more than pendingBasis*price
// proportional share).
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
