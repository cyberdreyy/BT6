### Title
Cross-execution response contamination via requestID reuse in `httpTriggerHandler` callback map - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`setupCallback` and `cleanupCallback` key `h.callbacks` solely by the client-controlled `requestID` (`req.ID`), with no generation/epoch token binding a node response to the specific execution instance that produced it. Because a completed request is fully removed from the map on quorum (`cleanupCallback`, which is called under the same lock as `setupCallback`), a new request reusing the same `requestID` shortly after can be admitted, and a late/slow node response that was actually destined for the *old* execution will be routed into the new execution's aggregator by `HandleNodeTriggerResponse`.

### Finding Description
`setupCallback` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:398-435) only rejects a `requestID` if it is *currently* present in `h.callbacks`: [1](#0-0) 

`cleanupCallback` (lines 439-446) deletes the map entry and closes `doneCh` as soon as the first shard reaches quorum for that ID: [2](#0-1) 

`HandleNodeTriggerResponse` (lines 448-496) looks up the callback purely by `resp.ID` and routes the response into `saved.responseAggregators[shard.donID]` with no check that the response belongs to the same execution "generation" that created the aggregator: [3](#0-2) 

Sequence:
1. Attacker (or coincidence) submits request A with `req.ID = X`; `setupCallback` creates aggregators for all shards assigned to A's workflow.
2. Shard1 reaches quorum first; `HandleNodeTriggerResponse` sends the response to A's callback and calls `cleanupCallback(X)`, deleting the map entry — while shard2's send loop (`sendToShard`) may still have in-flight/slow nodes that haven't yet answered A's original request (this exact race is demonstrated/expected behavior in `TestHttpTriggerHandler_MultiShardQuorumRace`, which shows a late shard2 response is normally rejected with "callback not found" once cleaned up).
3. Immediately after cleanup, a new request B is submitted reusing the same `req.ID = X` (nothing in `setupCallback` prevents ID reuse once the prior entry is gone). A fresh `savedCallback` with brand-new `IdenticalNodeResponseAggregator` instances is created for B under the same key `X`.
4. The stale/delayed node response for A (from a node in a shard also assigned to B) finally arrives and is routed to `HandleNodeTriggerResponse`. The lookup `h.callbacks[resp.ID]` now resolves to B's entry (since A's was deleted), and the stale response is fed into B's aggregator via `agg.CollectAndAggregate`.

Because `IdenticalNodeResponseAggregator.CollectAndAggregate` (core/services/gateway/common/aggregation/response_aggregator.go:38-75) only tracks by response-content digest and node address, with no check that the node actually responded to the *current* request, this stale vote counts toward B's quorum threshold, potentially allowing B's execution to reach quorum with fewer genuinely-contributing nodes than the configured `(N+F)//2+1` threshold, or, if the stale digest matches an incoming legitimate vote by coincidence, silently inflating vote counts for an unrelated execution.

### Impact Explanation
This breaks isolation between distinct trigger executions that happen to share a reused public `req.ID`: a node's response intended for execution A can be silently credited to unrelated execution B's quorum count, corrupting the "N+F)//2+1 identical honest responses" consensus guarantee `HandleNodeTriggerResponse` relies on to accept a workflow trigger result. This matches the "cross-user response confusion" impact class and can allow an execution to be finalized based on manipulated/insufficient quorum, which is a data-integrity / unauthorized-action impact on gateway trigger handling.

### Likelihood Explanation
Exploitability requires precise timing: the attacker (or an unwitting client) must resubmit the exact same `req.ID` in the narrow window between a prior execution's quorum-triggered `cleanupCallback` and the arrival of that prior execution's still-in-flight node response from a different shard. `req.ID` is fully client-controlled (checked only in `HandleUserTriggerRequest` → `setupCallback` for concurrent uniqueness, not historical uniqueness), and the multi-shard "first shard wins" design documented in `sendWithRetries`/`TestHttpTriggerHandler_MultiShardQuorumRace` guarantees that slower shards' node responses routinely arrive after cleanup — so the race window is a normal, expected occurrence of the system, not a rare edge case. No elevated privileges are needed beyond the ability to submit HTTP trigger requests with a chosen `req.ID`.

### Recommendation
Bind each `savedCallback`/aggregator set to a unique internal generation identifier that is independent of the client-supplied `req.ID` (e.g., an incrementing counter or UUID stored alongside the callback), and have `sendToShard`/`HandleNodeTriggerResponse` validate that an incoming node response's generation token matches the currently active generation for that `requestID` before routing it into an aggregator. Alternatively, never allow `req.ID` reuse at all (track historically-used IDs, not just currently in-flight ones) for at least the `MaxTriggerRequestDurationMs` window, so a stale response can never be attributed to a different execution instance.

### Proof of Concept
Go integration test plan (extends `TestHttpTriggerHandler_MultiShardQuorumRace` pattern in http_trigger_handler_test.go):
1. Build a 2-shard handler via `createMultiShardTriggerHandler` (shard0: n1-n3, shard1: n4-n6, F=1, threshold=3), register workflow W on both shards.
2. Submit request A with `req.ID = "reused-id"`, targeting both shards; have shard0 nodes (n1,n2,n3) respond immediately with identical content so shard0 reaches quorum and `cleanupCallback("reused-id")` fires (assert callback map no longer contains the ID, mirroring the existing race test).
3. Immediately submit request B with the *same* `req.ID = "reused-id"` (new `handlers.Callback`), targeting the same two shards; confirm `setupCallback` succeeds (new entry created).
4. Deliver a stale response for A from shard1 node `n4` (content distinct from real B responses) via `handler.HandleNodeTriggerResponse(ctx, staleResp, "n4")`.
5. Assert that this call either (a) returns an error rejecting the stale response as belonging to a different generation, or (b) does NOT get counted toward B's aggregator for shard1's `donID` — verify by checking `handler.callbacks["reused-id"].responseAggregators[shard1.donID]` internal vote count/`nodeToResponse` does not include `n4`'s stale vote, and that submitting only 2 more genuine B responses from n5/n6 is insufficient to reach the threshold-of-3 quorum for B (i.e., `callback.Wait` times out) — proving the current code fails this assertion because the stale vote is silently accepted, contaminating B's quorum count.

```go
func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
```

```go
// cleanupCallback removes a callback and signals sendWithRetries to stop.
// Must be called while holding callbacksMu lock.
func (h *httpTriggerHandler) cleanupCallback(requestID string) {
	saved, exists := h.callbacks[requestID]
	if !exists {
		return
	}
	close(saved.doneCh)
	delete(h.callbacks, requestID)
}
```

```go
func (h *httpTriggerHandler) HandleNodeTriggerResponse(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	h.lggr.Debugw("handling trigger response", "requestID", resp.ID, "nodeAddr", nodeAddr, "error", resp.Error, "result", resp.Result)
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()
	saved, exists := h.callbacks[resp.ID]
	if !exists {
		return errors.New("callback not found for request ID: " + resp.ID)
	}

	// Route the response into the aggregator for the shard that owns this node.
	shard, ok := h.nodeAddrToShard[nodeAddr]
	if !ok {
		return fmt.Errorf("received trigger response from unknown node %s (no owning shard)", nodeAddr)
	}
	agg, ok := saved.responseAggregators[shard.donID]
	if !ok {
		// The node belongs to a shard this workflow isn't assigned to (or the
		// callback was captured before the workflow was assigned there).
		return fmt.Errorf("node %s (shard %s) is not assigned to workflow for request ID %s", nodeAddr, shard.donID, resp.ID)
	}
	aggResp, err := agg.CollectAndAggregate(resp, nodeAddr)
```
