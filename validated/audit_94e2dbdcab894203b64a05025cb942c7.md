### Title

Unavailable ERC-4626 vault liquidity permanently stalls epoch settlement and withdrawal claims - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary

`ProgrammableBorrower.onStopEpoch` distinguishes economic insolvency from withdrawal failure using `convertToAssets`, but it does not check whether the configured ERC-4626 vault is currently able to satisfy the withdrawal. If the vault is paused, closed to withdrawals, or economically solvent but temporarily illiquid, `vault.withdraw()` reverts and `onStopEpoch` deliberately propagates `StopEpochVaultLiquidityUnavailable`. Because this hook is invoked outside the later borrower-transfer `try/catch`, the entire `IdleCDOEpochVariant.stopEpoch` call reverts before withdraw receipts are funded or the epoch is marked stopped. An unprivileged user of the programmable borrower’s ERC-4626 vault can create this condition by consuming the vault’s available liquidity while the borrower’s shares remain valuable according to `convertToAssets`.

### Finding Description

During buffer phase, a lender can create a normal withdrawal receipt. `IdleCreditVault.requestWithdraw` adds the fixed payout to the global `pendingWithdraws` amount that must be funded at epoch stop. [1](#0-0) 

When the epoch ends, `IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower.onStopEpoch` before attempting `getFundsFromBorrower`. This call is intentionally not wrapped by the `try/catch` that converts a failed borrower transfer into a default. [2](#0-1) 

Inside `onStopEpoch`, the contract checks only whether the requested shortfall exceeds the share position valued with `_currentVaultAssets`, which uses `vault.convertToAssets`. [3](#0-2)  This value represents the claim’s economic value, not the amount currently withdrawable under ERC-4626 liquidity, status, or queue restrictions.

If the shortfall is economically covered but not withdrawable, `vault.withdraw` is attempted and any failure is caught only to be replaced by `StopEpochVaultLiquidityUnavailable`. [4](#0-3)  The revert bubbles through `stopEpoch`, so `collectWithdrawFunds`, accounting, `isEpochRunning = false`, and the epoch-number transition are all reverted. [5](#0-4) 

The funded-claim path requires the epoch to advance before a receipt can be claimed; otherwise `_claimFundedWithdrawRequest` reverts. [6](#0-5)  Consequently, every retried stop can be forced to fail while the external vault remains in the non-withdrawable state.

The recovery paths do not reliably remove the condition. `emergencyExitVault` calls the same external vault through `redeem`, which may also revert under the same vault state. [7](#0-6)  `setVault` cannot migrate the position while accounting is active or any old-vault shares remain. [8](#0-7) 

### Impact Explanation

All matured withdrawal receipts backed by the unavailable vault liquidity remain frozen. The affected amount is at least `pendingWithdraws`; if the vault cannot satisfy the pool recall, the stalled settlement also prevents normal withdrawal requests and further epoch progression for the remaining NAV.

The freeze is temporary if the vault later restores liquidity or withdrawals. It becomes permanent if the vault’s withdrawal state never recovers, because the ordinary stop flow cannot default or bypass a covered-but-unwithdrawable position and the emergency exit uses the same disabled external redemption path.

### Likelihood Explanation

The trigger does not require control of the Idle owner, manager, borrower, guardian, or vault configuration. An ordinary ERC-4626 vault user or a borrower in the underlying liquidity market can consume the currently withdrawable liquidity while the programmable borrower’s shares remain fully valued.

This state is realistic for ERC-4626 vaults whose `convertToAssets` measures total allocated assets while `maxWithdraw` is constrained by idle liquidity, withdrawal queues, caps, or operational status. The existing code explicitly recognizes covered withdrawal failures, but its handling is limited to retrying the same reverting call indefinitely. [9](#0-8) 

### Recommendation

Handle “economically covered but presently unwithdrawable” as a separate vault state instead of unconditionally reverting:

- Check `vault.maxWithdraw(address(this))` or `vault.maxRedeem(address(this))` before calling `withdraw`.
- If the shortfall exceeds the currently withdrawable amount, enter an explicit recovery/default path rather than leaving the epoch perpetually running.
- Consider withdrawing the available amount and recording the remaining covered shortfall for settlement or loss accounting.
- Add a bounded retry/deadline mechanism. After the deadline, treat persistently unavailable vault liquidity as a borrower/vault recovery event so pending receipts receive their configured recovery treatment.
- Provide an emergency path that accounts for and claims the stranded ERC-4626 shares instead of requiring both `emergencyExitVault` and `setVault` to succeed.
- If `convertToAssets` or `maxWithdraw` itself becomes unavailable, use a state transition equivalent to `onDefault` rather than allowing all lifecycle views and settlement calls to revert.

### Proof of Concept

The following reduced Foundry PoC models the external ERC-4626 state on the existing mainnet-fork programmable-borrower setup. The relevant condition is that `convertToAssets` still reports enough value while the vault’s withdrawal function reverts; on a production MetaMorpho vault this can be reached by an unprivileged vault/market user exhausting currently withdrawable liquidity.

```solidity
function testStopEpochStuckWhenCoveredVaultWithdrawalReverts() external {
    uint256 amount = 10_000 * oneScale;

    // Pool setup uses the real USDC and configured ERC4626 vault on mainnet fork.
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);

    // Create a matured withdrawal obligation that onStopEpoch must fund.
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));

    _startEpochAndCheckPrices(0);

    uint256 pending = strategy.pendingWithdraws();
    assertGt(pending, 0);

    uint256 shares = morphoVault.balanceOf(address(programmableBorrower));
    uint256 covered = morphoVault.convertToAssets(shares);
    assertGe(covered, pending, "shares remain economically solvent");

    /*
      Attacker/environment step:
      an ordinary user of the configured ERC4626 vault exhausts its
      withdrawable liquidity, or the vault enters a non-withdrawable status.
      The mock call models the resulting state transition deterministically;
      the contract's own vulnerability is that it trusts convertToAssets
      rather than checking withdrawability.
    */
    vm.mockCall(
        address(morphoVault),
        abi.encodeWithSelector(
            IERC4626.withdraw.selector,
            pending,
            address(programmableBorrower),
            address(programmableBorrower)
        ),
        abi.encodeWithSignature("Error(string)", "vault withdrawals disabled")
    );

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Every state transition required for the receipt payout was reverted.
    assertTrue(cdoEpoch.isEpochRunning(), "epoch remains running");
    assertFalse(cdoEpoch.defaulted(), "covered-but-unwithdrawable vault is not defaulted");
    assertEq(strategy.pendingWithdraws(), pending, "receipt remains unfunded");

    // The same revert can be repeated on every settlement attempt while the
    // external vault remains in that state.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);
}
```
