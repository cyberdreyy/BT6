### Title
Expired staking rewards are permanently stranded when a new reward period ignores the undistributed balance - (File: contracts/StakingRewards.sol)

### Summary
`depositReward` computes the new `rewardRate` only from the newly supplied `reward` when `block.timestamp >= periodFinish`. Rewards that remained undistributed after the previous period—such as rewards accruing while `_totalSupply == 0`—are included in the contract balance check but are not included in the new emission rate. Once the next period starts, those rewards are no longer represented by `rewardRate`, `rewardPerTokenStored`, or any user `rewards` balance, and cannot be claimed through staking logic.

### Finding Description
`rewardPerToken` returns `rewardPerTokenStored` without accruing anything while `_totalSupply == 0`. Consequently, if all stakers exit before `periodFinish`, the remainder of the previously deposited reward stays in the contract but is never assigned to a user. When the reward distributor later calls `depositReward` after `periodFinish`, line 135 replaces `rewardRate` with `reward / rewardsDuration`; unlike the active-period branch, it does not add the undistributed remainder. The balance check at line 147 then uses the entire token balance, so the stranded amount helps satisfy the reserve check while still being excluded from emissions. [1](#0-0) [2](#0-1) 

An unprivileged tranche-token holder can create the condition by withdrawing the last stake before the current reward period ends. The next honest reward notification then finalizes the loss. The same flaw exists in `DelegateStakingRewardsIDLE.depositReward`, although whitelist membership limits who can become the last staker there. [3](#0-2) 

### Impact Explanation
Undistributed rewards are permanently locked in `StakingRewards` unless the owner manually rescues them with `recoverERC20`. They are not claimable because:

- No balance existed during the zero-supply interval, so `rewardPerTokenStored` did not increase.
- The next period resets `rewardRate` without adding the old remainder.
- `getReward` only transfers amounts stored in `rewards[msg.sender]`.
- Repeated notifications repeat the same reset, so the old remainder never re-enters the rate.

For example, if a `100e18` reward period has `50e18` earned before the last staker exits and the remaining `50e18` is meant to roll over, a subsequent `100e18` deposit emits only `100e18` over the next duration. The prior `50e18` remains stranded even though it is counted in `balance` at line 146. [4](#0-3) [5](#0-4) 

### Likelihood Explanation
The trigger is ordinary protocol operation plus one unprivileged withdrawal:

1. A reward distributor starts a reward period.
2. A sole or last staker calls `withdraw`, reducing `_totalSupply` to zero.
3. The rest of the period elapses, leaving part of the deposited reward unallocated.
4. The honest distributor calls `depositReward` for a later period.
5. The stale balance is excluded from the new `rewardRate` and becomes unreachable.

No malicious privileged role is required. `stake`, `withdraw`, and `getReward` are public, while the reward distributor call is an expected protocol action. The `rewardRate <= balance / rewardsDuration` check does not prevent the issue because it checks the aggregate token balance rather than the scheduled amount. [6](#0-5) [7](#0-6) 

### Recommendation
Track the undistributed amount when starting a period after `periodFinish`, and include it in the new rate. A minimal approach is to calculate the unallocated remainder before replacing the rate:

```solidity
uint256 undistributed;
if (block.timestamp >= periodFinish && _totalSupply != 0) {
    undistributed = (periodFinish - lastUpdateTime) * rewardRate;
} else if (block.timestamp >= periodFinish && _totalSupply == 0) {
    undistributed = (periodFinish - lastUpdateTime) * rewardRate;
}

if (block.timestamp >= periodFinish) {
    rewardRate = (reward + undistributed) / rewardsDuration;
} else {
    uint256 remaining = periodFinish - block.timestamp;
    uint256 leftover = remaining * rewardRate;
    rewardRate = (reward + leftover) / rewardsDuration;
}
```

A more robust Synthetix-style accounting design should explicitly account for rewards that cannot accrue during zero-supply intervals, rather than deriving rollover solely from `periodFinish - lastUpdateTime`. Apply the same correction to `DelegateStakingRewardsIDLE.depositReward` if that contract remains supported.

### Proof of Concept
The following Foundry test demonstrates the invariant break on a forked deployment. Concrete deployment values should be supplied by the test environment:

```solidity
function testExpiredRewardBalanceStranded() public {
    // Deploy or fork StakingRewards with:
    // - stakingToken = tranche token
    // - rewardsToken = ERC20 reward token
    // - rewardsDistribution = distributor
    // - rewardsDuration = 1 days

    address alice = address(0xA11CE);
    uint256 stakeAmount = 100e18;
    uint256 firstReward = 100e18;
    uint256 secondReward = 100e18;

    deal(address(stakingToken), alice, stakeAmount);
    deal(address(rewardsToken), distributor, firstReward + secondReward);

    vm.prank(alice);
    stakingToken.approve(address(stakingRewards), stakeAmount);
    vm.prank(alice);
    stakingRewards.stake(stakeAmount);

    vm.startPrank(distributor);
    rewardsToken.approve(address(stakingRewards), firstReward + secondReward);
    stakingRewards.depositReward(address(0), firstReward);
    vm.stopPrank();

    // Half of the reward accrues to Alice.
    vm.warp(block.timestamp + 12 hours);

    // Alice exits. The remaining half cannot accrue while supply is zero.
    vm.prank(alice);
    stakingRewards.exit();
    assertEq(stakingRewards.totalSupply(), 0);

    // Finish the period. The unaccrued remainder remains in the contract.
    vm.warp(block.timestamp + 12 hours);

    // Honest distributor starts the next period.
    vm.prank(distributor);
    stakingRewards.depositReward(address(0), secondReward);

    // The rate schedules only secondReward.
    assertEq(
        stakingRewards.getRewardForDuration(),
        secondReward
    );

    // The contract still holds the old remainder plus the new reward.
    uint256 stranded =
        rewardsToken.balanceOf(address(stakingRewards)) - secondReward;
    assertGt(stranded, 0);

    // Alice restakes and waits for the whole next period.
    vm.prank(alice);
    stakingToken.approve(address(stakingRewards), stakeAmount);
    vm.prank(alice);
    stakingRewards.stake(stakeAmount);
    vm.warp(stakingRewards.periodFinish());
    vm.prank(alice);
    stakingRewards.getReward();

    // Alice receives only the newly scheduled amount; the old remainder
    // remains contract balance with no corresponding user entitlement.
    assertLe(rewardsToken.balanceOf(alice), secondReward);
    assertEq(
        rewardsToken.balanceOf(address(stakingRewards)),
        stranded
    );
}
```
