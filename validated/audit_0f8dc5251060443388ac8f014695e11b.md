## Title
Removed multisig members' stale confirmations still count toward the confirmation threshold, allowing execution below the live-member threshold - (File: `multisig2/src/lib.rs`)

## Summary
The bug in the external report is a masterchef-style reward accrual that is never invalidated when the underlying position is closed (liquidated), so a stale balance keeps contributing to a live accounting total. The same class of bug exists in `MultiSigContract` (multisig2): when a member is removed via `DeleteMember`, the contract only cleans up **requests the removed member itself created**, not the **confirmations that member cast on other members' still-active requests**. Those stale confirmations remain in the `confirmations` `HashSet` and continue to count toward `num_confirmations`, exactly like a liquidated position continuing to accrue rewards.

## Finding Description
`MultiSigContract::confirm` decides whether a request can execute purely by comparing the size of the `confirmations` set for that request against `self.num_confirmations`: [1](#0-0) 

Membership changes are handled by `delete_member`, which is only invoked from `execute_request`'s `DeleteMember` branch: [2](#0-1) 

`delete_member` removes the member from `self.members`, and it purges **requests originated (`r.member == member`)** by the removed member along with their confirmations. However, it never scans `self.confirmations` for entries where the removed member's identity (`member.to_string()`) appears as a *confirmer* on some other request that was created by a different, still-active member. Those confirmation sets are untouched.

The binding this breaks is: `confirmations counted` (the `HashSet<String>` length compared against `num_confirmations`) should always equal `confirmations from live members`. After a `DeleteMember` action executes, a stale confirmation entry from the now-removed member remains embedded in any other pending request's `confirmations` set, so the equality:

```
len(confirmations[request_id]) == count of *live* members who confirmed request_id
```

no longer holds — the left side can be strictly greater than the right side.

## Impact Explanation
Because `confirm()` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, a stale confirmation from a removed member effectively acts as a permanent "banked" vote. This lets the remaining members execute a request (transfers, key additions, contract deployments, etc.) with **fewer live-member approvals than `num_confirmations`** requires — i.e., a multisig request executed below threshold, which is explicitly called out as a Critical impact (funds moved or configuration changed by a party not entitled to approve it, using authorization that was never validly given by the current member set).

## Likelihood Explanation
This requires no owner/foundation/redeploy assistance and no malicious validator — it is reachable by any legitimate multisig workflow:
1. A pending request `A` (created by member X) is confirmed by member Y but not yet at threshold.
2. The multisig members separately approve and execute a `DeleteMember` request removing Y (e.g., Y is compromised/offboarded).
3. Request `A`'s confirmations set still contains Y's stale confirmation.
4. One fewer live confirmation than `num_confirmations` is now needed to push `A` over the threshold and execute it, effectively lowering the live-member security threshold without anyone explicitly voting to lower it.

This is a normal sequence of unprivileged member actions (any member can confirm/create requests; deletion is itself a legitimate multisig action), not a contrived edge case, so likelihood is meaningful.

## Recommendation
When executing `DeleteMember`, iterate over all `self.requests` (not just those authored by the removed member) and strip the removed member's entry out of the corresponding `self.confirmations` set, decrementing effective confirmation counts accordingly. Alternatively, validate at `confirm()`/execution time that every entry in the `confirmations` set still corresponds to a current `self.members` entry before comparing against `num_confirmations`.

## Proof of Concept
1. Initialize `MultiSigContract::new([X, Y, Z], 2)` (2-of-3).
2. Member X calls `add_request` to create request `A` targeting some sensitive action; `A`'s `confirmations` set is empty.
3. Member Y calls `confirm(A)` — `confirmations[A] = {Y}` (1 confirmation, threshold not met).
4. Members X and Z create and confirm a `DeleteMember { member: Y }` request (2-of-3 reached with X+Z), which executes and calls `delete_member(Y)`: [3](#0-2) 
   This removes Y from `self.members`, but does not touch `confirmations[A]`, which still contains `"Y"`.
5. Member Z calls `confirm(A)`. In `confirm()`: [4](#0-3) 
   `confirmations[A].len()` is `1` (stale Y) `+ 1` (Z) `= 2 >= num_confirmations (2)`, so request `A` executes — even though only one *currently live* member (Z) actually approved it after Y's removal.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
