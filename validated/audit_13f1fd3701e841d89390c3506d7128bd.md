### Title
Fee-on-transfer underlying inflates strategy tokens and over-mints mid-epoch deposits - (File: contracts/IdleCDOEpochVariant.sol, contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `token` is a fee-on-transfer (FoT) ERC20, the credit vault pulls the nominal `_amount` from the depositor but receives less. `_deposit` (buffer phase) mints tranche shares on the received delta — correct — but then calls `strategy.deposit(_amount)` with the *nominal* amount, so `IdleCreditVault.deposit` mints `_amount` strategy tokens while only `_amount - fee` was actually received. In `depositDuringEpoch` the mismatch is worse: tranche shares, expected interest, strategy tokens, and the borrower transfer are all computed on the nominal `_amount` while only `_amount - fee` arrived.

### Finding Description
In `IdleCDOCreditVault._deposit` (inherited by `IdleCDOEpochVariant`), shares are minted from `_contractTokenBalance(_token) - _preBal`, i.e. the *received* amount, but `IIdleCDOStrategy(strategy).deposit(_amount)` is then invoked with the nominal `_amount` (contracts/IdleCDOCreditVault.sol:203-211). `IdleCreditVault.deposit` performs `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` and mints the CDO `_amount` strategy tokens 1:1 without measuring the received balance (contracts/strategies/idle/IdleCreditVault.sol:596-617). With a FoT token the strategy receives `_amount - fee` but credits `_amount` strategy tokens, so `getContractValue()` (driven by the CDO's strategy-token balance) overstates NAV by `fee` per deposit, diluting existing tranche holders. If the CDO's residual balance is below `_amount` (normal case after `_skimDonatedAssets`), the second pull simply reverts.

In `depositDuringEpoch` (contracts/IdleCDOEpochVariant.sol:684-732) the flow is: pull `_amount` from the user → mint `_minted = (_amount + trancheInterest) * supply / expectedFinal` tranche shares on the nominal amount → `IdleCreditVault(strategy).mintStrategyTokens(_amount)` → `_transferUnderlyings(_borrower(), _amount)`. Every accounting step uses the nominal `_amount` even though only `_amount - fee` was received, and the outbound transfer to the borrower sends the full nominal `_amount`. Unless the CDO holds at least `fee` of residual underlying (e.g., pre-funded instant-withdraw liquidity or interest already returned by the borrower), the borrower transfer reverts; if residual funds exist, they are silently forwarded to the borrower while the depositor is minted shares for the full `_amount` plus prorated interest — a direct transfer of other users' funds to the depositor/borrower.

Any unprivileged KYC-passing lender (`isWalletAllowed(msg.sender)` is the only gate) triggers this by depositing a FoT underlying during the buffer period (`depositAA`/`depositBB`) or mid-epoch (`depositDuringEpoch`) in fixed-APR or APR0 modes. The same over-mint applies to `mintStrategyTokens`, which blindly mints `_amount` without verifying received funds.

### Impact Explanation
NAV inflation / insolvency: each deposit mints `_amount` strategy tokens backed by only `_amount - fee`, so `getContractValue()` and tranche `virtualPrice` are overstated; the last withdrawers absorb the shortfall (BB first per the waterfall). In the mid-epoch path, if the CDO holds prefunded liquidity, the depositor is over-minted tranche shares *and* the borrower is sent funds belonging to pending withdrawers — theft of pool assets equal to the accumulated transfer fees. Otherwise all deposits revert, freezing the vault's deposit function for that token.

### Likelihood Explanation
Requires a FoT token configured as the vault's `token` (e.g., USDT with fees enabled, PAXG, SAFEMOON-style tokens) and a lender depositing during the buffer period or a running epoch. No privileged cooperation needed; `_skimDonatedAssets`, `_guarded`, epoch gating, and KYC checks do not measure received balances, so nothing blocks it. The second `safeTransferFrom` hop also means any deposit *succeeds* exactly when residual CDO liquidity exists to subsidize the fee, making the theft path reachable in prefunded/instant-withdraw deployments.

### Recommendation
Measure the actual received amount once and propagate it: in `_deposit`/`depositDuringEpoch` use `received = _contractTokenBalance(token) - _preBal` and pass `received` (not `_amount`) to `strategy.deposit(...)`, `_mintShares`, `mintStrategyTokens`, `_transferUnderlyings(_borrower(), received)`, and the interest/`expectedEpochInterest` math. Alternatively, explicitly whitelist non-FoT `token` at initialization and document the restriction.

### Proof of Concept
Foundry fork test sketch (USDT-style FoT mock or mainnet token with fee enabled):

```solidity
// assume `vault` is IdleCDOEpochVariant, `token` takes 1% fee on transfer
uint256 amount = 1_000_000e6;
deal(token, lender, amount);
vm.startPrank(lender);
token.approve(address(vault), amount);

// Buffer phase: depositAA mints on received delta but strategy.deposit(amount)
// mints `amount` strategyTokens for `amount*99/100` received.
uint256 balBefore = token.balanceOf(address(vault));
uint256 stratBefore = IERC20(strategy).balanceOf(address(vault));
vault.depositAA(amount);
// strategy tokens credited for nominal amount...
uint256 minted = IERC20(strategy).balanceOf(address(vault)) - stratBefore;
assertEq(minted, amount);
// ...while actual underlying held is amount - fee (plus residual drain)
// => getContractValue() overstated by fee; subsequent withdrawers are short.

// Mid-epoch path (epoch running, lender KYC'd):
vault.depositDuringEpoch(amount, vault.AATranche());
// tranche shares minted for `amount` (+ prorated interest),
// but only `amount - fee` received; borrower sent full `amount`,
// draining prefunded liquidity or reverting.
```
