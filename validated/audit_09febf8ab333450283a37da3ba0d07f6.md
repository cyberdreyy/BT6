### Title
Stale `epochPendingWithdraws` reserve lets new withdraw requests be undercollateralized at `stopEpoch` - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` snapshots the pending-withdraw reserve once in `onStartEpoch` (`epochPendingWithdraws = _pendingWithdraws`) and never refreshes it while the epoch runs. `availableToBorrow()` and `_borrow()` then treat that stale snapshot as the full obligation to keep covered. Like the Numa bug — where a check used a stored borrow snapshot (`accountBorrows[..].principal`) instead of the live accrued value (`borrowBalanceStored`) — here the borrow-side invariant uses a stored liability snapshot instead of the live `pendingWithdraws` on `IdleCreditVault`. A withdraw request created mid-epoch silently increases the real obligation without increasing the reserve.

### Finding Description
- `onStartEpoch` stores `epochPendingWithdraws = _pendingWithdraws` once, from the CDO-supplied value at epoch start [1](#0-0) .
- `availableToBorrow()` computes `totalAssets - epochPendingWithdraws`, and `_borrow()` enforces `assets <= borrowable` against that stale reserve [2](#0-1) [3](#0-2) .
- Meanwhile `IdleCDOEpochVariant.requestWithdraw` (callable by any KYC-passed tranche holder during a running epoch — there is no `isEpochRunning` gate) calls `IdleCreditVault.requestWithdraw`, which increments the strategy's `pendingWithdraws` by the full receipt amount [4](#0-3) [5](#0-4) . No code path pushes the new `pendingWithdraws` back into `epochPendingWithdraws` mid-epoch.
- `onStopEpoch` withdraws from the ERC4626 vault only what is needed for `_amountRequired`; the CDO pulls `pendingWithdraws` including the new receipts [6](#0-5) .

Attack sequence (running epoch, programmable mode):
1. Epoch starts with `epochPendingWithdraws = X`.
2. A lender calls `requestWithdraw`, raising live `pendingWithdraws` to `X + W`.
3. The borrower draws `availableToBorrow()`, which still reserves only `X`, taking up to `W` of funds owed to the receipt.
4. At `stopEpoch`, the CDO pulls `X + W` but the facility is short by `W`. The shortfall either reverts `onStopEpoch`/`stopEpoch` (retryable freeze while the borrower's debt is outstanding) or is realized through the `stopEpochWithDuration`/`collectWithdrawFunds` loss path, where `pendingToFund < pendingBasis` stores `lossRecoveryPriceByEpoch < 1` and the receipt claim is permanently haircut [7](#0-6) .

### Impact Explanation
Direct loss or freezing of lender funds up to the full mid-epoch withdraw amount `W` not covered by the stale reserve. If the borrower is otherwise solvent the loss manifests as a `lossRecoveryPriceByEpoch` haircut permanently reducing `claimWithdrawRequest` payouts, even though no real borrower loss occurred — the missing liquidity sits in the borrower's wallet as `borrowerPrincipal`. If the borrower never repays, this converts into a default where other active LPs share a loss that was purely a reserve-accounting failure.

### Likelihood Explanation
Triggering requires only two unprivileged/honest-actor transactions in sequence: a `requestWithdraw` by a lender mid-epoch, then a `borrow`/`executeBorrow` by the (honest) borrower drawing available liquidity — a routine operation in this revolving facility. The comment at `_borrow` ("Borrows are capped by the live 'reserved vs free' view so epoch-end obligations always stay covered") is false for obligations created after `onStartEpoch`. I could not fully verify within my search budget whether the CDO calls an alternative setter to bump `epochPendingWithdraws` on new requests; no such call appears in `requestWithdraw`, and `epochPendingWithdraws` is only written in `onStartEpoch`.

### Recommendation
Use the live value instead of the stored snapshot — the direct analog of the Numa `borrowBalanceStored` fix:
- In `availableToBorrow()`, read `IdleCreditVault(...).pendingWithdraws()` (plus a safety margin for same-block requests) rather than `epochPendingWithdraws`, or
- Have `IdleCDOEpochVariant.requestWithdraw`/`IdleCreditVault.requestWithdraw` push updated pending amounts into `ProgrammableBorrower` (e.g., `setEpochPendingWithdraws`), so the reserve always reflects the current obligation.

### Proof of Concept
Foundry fork outline:
```solidity
// Running epoch on a ProgrammableBorrower deployment
cdoEpoch.startEpoch();                       // epochPendingWithdraws = pendingWithdraws (e.g., 0)

// 1. Lender requests withdraw mid-epoch -> pendingWithdraws += W on IdleCreditVault
vm.prank(lender);
cdoEpoch.requestWithdraw(amount, AAtranche); // W underlyings now owed at stopEpoch

// 2. Borrower draws what appears "free" — reserve still excludes W
vm.prank(borrower);
programmableBorrower.borrow(W);              // succeeds because availableToBorrow ignores W

// 3. stopEpoch pulls pendingWithdraws (= W) -> shortfall -> loss path or revert
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);                    // underfunded: lossRecoveryPriceByEpoch < 1

// 4. Lender claim is haircut despite a solvent borrower
vm.prank(lender);
cdoEpoch.claimWithdrawRequest();             // pays W * lossRecoveryPrice / 1e18 < W
```

**Caveat:** this finding is the strongest in-scope analog (stale stored snapshot vs live accrued/pending obligation breaking a fund-safety check), but I could not exhaustively confirm that no privileged setter refreshes `epochPendingWithdraws` mid-epoch; if one exists and is reliably called on every `requestWithdraw`, the issue reduces to a sequencing gap rather than a guaranteed shortfall.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
