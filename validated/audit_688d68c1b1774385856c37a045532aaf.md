## Title
Missing success‑verification callback in `MultisigFactory::create` causes attached NEAR deposit to be irrecoverably lost when the deterministic sub‑account name is front‑run or account creation otherwise fails - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` derives the new multisig's account ID solely from a caller‑supplied `name` (`format!("{}.{}", name, env::current_account_id())`) and immediately fires a batched `Promise` (`create_account` → `deploy_contract` → `transfer` → `function_call`) without any callback that verifies the batch succeeded, unlike its sibling factories. If that receipt fails for any reason — most notably because the account name was already claimed (the exact "predictable address, race/front‑run" pattern flagged in the external report) — the attached deposit is not returned to the caller, it is refunded to the factory contract's own account instead, permanently separating the user's NEAR from the user. [1](#0-0) 

### Finding Description
`create` builds the target account id deterministically from user input and the factory's own account id: [2](#0-1) 

It then issues a single batched promise with `create_account`, `deploy_contract`, `transfer`, and `function_call`, and returns the promise directly to the runtime — there is no `.then(ext_self::...)` callback: [3](#0-2) 

Compare this with `StakingPoolFactory::create_staking_pool` and `LockupFactory::create`, which both (a) track already‑used account IDs / rely on `create_account` failing, and (b) attach an explicit callback (`on_staking_pool_create` / `on_lockup_create`) that checks `is_promise_success()` and, on failure, transfers `attached_deposit` back to `predecessor_account_id`: [4](#0-3) [5](#0-4) 

Because `MultisigFactory::create` has neither the pre‑existence check nor the refund callback, if the batched receipt fails — e.g., because the `name.multisig-factory` account already exists (an attacker or another legitimate user claims the same human‑readable `name` first, which is exactly the "predictable, name/address‑derived deployment can be pre‑empted" bug class described in the report), or because the embedded `new` call panics (e.g. `num_confirmations` exceeds `members.len()`) — NEAR protocol refunds the balance/gas of a failed receipt to the **predecessor of that receipt**, which is the `multisig-factory` contract account itself, not the original caller who attached the deposit. The user's NEAR is silently absorbed by the factory account with no path to recovery.

The equality that should hold is: `deposit_attached_by_user == deposit_in_new_multisig OR deposit_refunded_to_user`. Here, on the failure branch, neither holds — the deposit instead lands in `multisig-factory`'s balance, breaking the custody binding.

### Impact Explanation
This is a Critical impact per the rubric ("funds permanently frozen" and "unauthorized move" — NEAR moved to a party, the factory account, not entitled to it). An attacker can observe a pending `create` call in the mempool (or a reorg re-ordering) targeting a desirable/expected `name`, submit their own `create` call with the same `name` and higher priority/gas, and get their transaction included first. The account `name.multisig-factory` then exists, so the victim's later `create_account` action fails, the whole batched receipt fails, and the victim's attached NEAR deposit is refunded to the `multisig-factory` account rather than back to the victim — a permanent, unrecoverable loss of NEAR for the victim, with no admin/owner recourse since `MultisigFactory` has no funds‑recovery method at all.

### Likelihood Explanation
Likelihood is straightforward: `name` is an arbitrary, attacker‑visible, non‑namespaced string; no reservation, no whitelist check, and no per‑name uniqueness tracking exists in the factory's persistent state. Any unprivileged actor who front‑runs the same `name` (or simply happens to reuse a popular name) triggers the loss condition; no special privileges, victim keys, or contract owner involvement are required.

### Recommendation
Add a callback (`ext_self::on_multisig_create`, mirroring `on_staking_pool_create` / `on_lockup_create`) that checks `is_promise_success()` after the batch, and refunds `env::attached_deposit()` to `env::predecessor_account_id()` if the account creation/deploy/init failed. Optionally, also track already‑used names in persistent state to fail fast before initiating the promise, and consider deploying using a caller‑bound, collision‑resistant sub‑account naming scheme.

### Proof of Concept
1. Victim `V` sends `create({"name": "acme", members: [...], num_confirmations: N})` with an attached deposit `D`.
2. Attacker `A` observes this transaction (mempool/reorg window) and sends `create({"name": "acme", ...})` with higher gas price/priority, which lands first, successfully creating `acme.multisig-factory`.
3. `V`'s transaction executes: `Promise::new("acme.multisig-factory").create_account()` fails because the account already exists, causing the whole batched receipt (including the `transfer(D)` action) to fail.
4. Per NEAR runtime semantics, the failed receipt's balance is refunded to its predecessor — the `multisig-factory` contract account — not to `V`.
5. `V` has permanently lost `D` NEAR with no multisig created and no callback path in `multisig-factory/src/lib.rs` to recover or refund it, unlike the equivalent failure paths in `staking-pool-factory` and `lockup-factory`.

    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())

                    .as_bytes()
                    .to_vec(),

                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
