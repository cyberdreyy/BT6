### Title
Global state-machine agreement/disagreement thresholds use floor rounding instead of the ceil rounding used for block approval, letting sub-70%-weight consensus be treated as reached - ([File: libsigner/src/v0/signer_state.rs])

### Summary
`GlobalStateEvaluator::reached_agreement` and `reached_disagreement` in `libsigner/src/v0/signer_state.rs` compute the 70%/30% weight thresholds with plain integer division (floor), whereas the actual on-chain block-approval threshold, `NakamotoBlockHeader::compute_voting_weight_threshold` in `stackslib/src/chainstate/nakamoto/mod.rs`, explicitly rounds *up* (ceil) to the nearest whole weight unit. This mismatch is structurally the same class of bug as the report: a boundary/threshold check that is supposed to gate on "at least X%" but is computed with the wrong rounding direction, so it fires earlier (with less real weight) than the value it is meant to approximate.

### Finding Description
The chain-level signature-weight threshold is computed with an explicit ceiling: [1](#0-0) 
```
pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
    let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
    let total_weight = u64::from(total_weight);
    let ceil = if (total_weight * threshold) % 10 == 0 { 0 } else { 1 };
    u32::try_from((total_weight * threshold) / 10 + ceil)...
}
```
This is the threshold used everywhere a block signature/pre-commit/rejection tally is checked against real 70%/30% supermajority weight (`stacks-signer/src/v0/signer.rs` lines around 1298, 2309, 2498, and `stacks-node/src/nakamoto_node/signer_coordinator.rs`).

By contrast, the `GlobalStateEvaluator` used to determine the **global state machine** (active miner, burn view, protocol version, tx-replay-set agreement) computes the same nominal 70%/30% split with floor division and no ceiling: [2](#0-1) 
```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
pub fn reached_disagreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        > u64::from(self.total_weight).strict_mul(10 - NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```
For any `total_weight` not evenly divisible by 10, `floor(total_weight*7/10) < ceil(total_weight*7/10)`. E.g. `total_weight = 13`: chain-level threshold requires `ceil(9.1) = 10`, but `reached_agreement` fires at `9` (69.2%, below the true 70% supermajority). This function gates `determine_latest_supported_signer_protocol_version`, `determine_global_burn_view`, and `determine_global_state` — the routines that decide the network-wide "current miner"/tenure view, the active signer protocol version, and the transaction replay set: [3](#0-2) [4](#0-3) 

Each individual signer independently computes this same `GlobalStateEvaluator` locally from the same set of `StateMachineUpdate` gossip messages, so this is fully triggerable by ordinary gossip/state broadcasts from any signer set without requiring a majority to misbehave — the flaw is in the arithmetic every honest node runs, not in a malicious majority.

### Impact Explanation
Because the global-state agreement threshold under-counts the weight required (rounds down instead of up), a signer's local view of the "current miner"/tenure and the active protocol version can flip to "agreed" using strictly less than a genuine 70% supermajority of weight. This directly threatens the "acting on a stale reward set/threshold" category: a signer can conclude the network has reached global consensus on a miner/tenure view (`determine_global_state`) when the real block-signing consensus mechanism (which uses the ceil-rounded threshold) would not yet consider that supermajority reached. This view feeds decisions such as whether to capitulate to another miner's tenure view and reorg permission logic (`stacks-signer/src/v0/signer.rs`), so an inconsistent, prematurely-declared "global state" can steer a signer's own block-approval behavior (e.g., permitting or vetoing a reorg, or which tenure it trusts) based on an under-thresholded reading of the network — a liveness/safety-adjacent wedge rather than a benign log discrepancy.

### Likelihood Explanation
This requires no attacker action, majority compromise, or special network conditions — it triggers whenever the number of registered signers/weight units yields a `total_weight` not exactly divisible by 10 under the 70/30 split, which is the common case for most real reward-cycle signer sets. It is a systemic rounding inconsistency between two independently-implemented "same nominal percentage" thresholds, exactly analogous to the external report's core defect: a boundary check computed with the wrong direction so it under-protects at the edge.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement` / `reached_disagreement` use the same ceiling-rounding semantics as `NakamotoBlockHeader::compute_voting_weight_threshold` (or better, have both call the single shared helper) so that "70% agreement" in the global state machine and "70% approval" in block-signature verification always require an identical, consistently-rounded minimum weight.

### Proof of Concept
Not independently confirmed by test execution — this is an analog derived from static comparison of the two threshold implementations. Suggested concrete verification: construct a signer set whose total weight is not a multiple of 10 (e.g. weights summing to 13, split roughly proportional to `[5, 4, 4]` or similar), have signers with combined weight 9 broadcast identical `StateMachineUpdate`s, and call `GlobalStateEvaluator::reached_agreement(9)`/`determine_global_state`. Compare against `NakamotoBlockHeader::compute_voting_weight_threshold(13)`, which requires `10`. The evaluator will report agreement reached at weight 9 while the chain-level threshold used for actual block-signature consensus would require 10 — confirming the discrepancy described above.

Note: I was not able to fully trace every downstream consumer of `determine_global_state`/`reached_agreement` within the remaining iteration budget (e.g., `stacks-signer/src/v0/signer_state.rs` and `stacks-signer/src/chainstate/v2.rs` usages were only partially inspected), so the precise blast radius on reorg-permit and capitulation logic in `stacks-signer/src/v0/signer.rs` should be validated further by a Devin session with full file access.

    /// Determine what the maximum signer protocol version that a majority of signers can support
    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
            *entry += weight;
        }
        // find the highest version number supported by a threshold number of signers
        let mut protocol_versions: Vec<_> = protocol_versions.into_iter().collect();
        protocol_versions.sort_by_key(|(version, _)| *version);
        let mut total_weight_support: u32 = 0;
        for (version, weight_support) in protocol_versions.into_iter().rev() {
            total_weight_support += weight_support;
            if self.reached_agreement(total_weight_support) {
                return Some(version);
            }
        }
        None
    }
