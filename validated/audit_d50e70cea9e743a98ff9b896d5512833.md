### Title
Missing zero-value validation in `createWriteOffRequest` lets any fulfiller seize escrowed tranche tokens for free - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`createWriteOffRequest` validates that `amount > 0` but accepts `underlyingsRequested == 0`. This creates a request whose stored `underlyings` total is 0, which `fullfillWriteOffRequest` then accepts with `_underlyings == 0`, allowing any EOA to claim all escrowed tranche tokens without paying anything. This is the credit-vault analog of improper input validation (CWE-20, the null-byte injection class): a parameter that should be rejected is accepted, and downstream logic treats it as legitimate.

### Finding Description
`createWriteOffRequest` escrows the caller's tranche tokens and records the requested underlying amount:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-101
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
...
underlyings: currentRequest.underlyings + underlyingsRequested
```

There is no `underlyingsRequested == 0` check. `fullfillWriteOffRequest` only enforces `_underlyings >= currentRequest.underlyings`, so a request with cumulative `underlyings == 0` is fulfilled by `_underlyings == 0`: the fulfiller transfers nothing, no fee is charged (`_underlyings * exitFee == 0`), and the full `currentRequest.tranches` is sent to `msg.sender` at line 151. The check `currentRequest.tranches != _tranches` passes trivially because the fulfiller echoes the stored value, which is publicly readable via `userRequests`. The strict equality on `_tranches` combined with the additive accumulation of `underlyings` also means a lender can accidentally create a composite request whose aggregate `underlyings` is 0 after a zero-value top-up, and the whole escrowed balance (not just the latest deposit) becomes claimable for free.

### Impact Explanation
Direct theft of escrowed tranche tokens. Once a lender's request has cumulative `underlyings == 0`, any unprivileged EOA calls `fullfillWriteOffRequest(victim, victimRequest.tranches, 0)` and receives every tranche token the victim deposited, paying zero underlying. The victim's tranche position — which has real claim value on the credit vault (loss-adjusted withdrawal rights in IdleCreditVault) — is permanently lost. Loss equals the victim's full escrowed tranche balance.

### Likelihood Explanation
Likelihood is conditional on a lender creating or topping up a request with `underlyingsRequested == 0`, which the contract currently permits without warning — no UI-level validation can be assumed. Once such a request exists, exploitation is permissionless, atomic, and gas-only cost; `fullfillWriteOffRequest` is explicitly callable by any wallet (line 122 comment). No epoch-phase restriction applies to fulfillment, so the window of exposure lasts until the victim calls `deleteWriteOffRequest`.

### Recommendation
Add `if (underlyingsRequested == 0) revert NotAllowed();` in `createWriteOffRequest`, mirroring the existing `amount == 0` check. Optionally also require `currentRequest.underlyings > 0` in `fullfillWriteOffRequest` to protect any legacy zero-underlying requests already stored on upgraded escrows (the contract already handles legacy requests at lines 111-112 and 133-134).

### Proof of Concept
Foundry-style PoC sketch (requires a running epoch so `isEpochRunning()` is true):

```solidity
// victim deposits tranche tokens into escrow requesting 0 underlying
vm.startPrank(victim);
tranche.approve(address(escrow), amount);
escrow.createWriteOffRequest(amount, 0); // accepted: no zero check
vm.stopPrank();

// attacker reads userRequests(victim) and fulfills with 0 underlying
(uint256 t, uint256 u) = escrow.userRequests(victim); // t == amount, u == 0
uint256 balPre = tranche.balanceOf(attacker);
vm.prank(attacker);
escrow.fullfillWriteOffRequest(victim, t, 0); // attacker pays nothing
assertEq(tranche.balanceOf(attacker) - balPre, t); // all escrowed tranches stolen
```
