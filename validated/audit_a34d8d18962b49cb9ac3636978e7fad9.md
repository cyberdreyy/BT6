### Title
Cross-user response confusion via unscoped `savedCallbacks` map keyed only by attacker-controllable `MessageId` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each user's response callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no binding to the sender/signer. An attacker who sends a signed request with the same `MessageId` as a victim's in-flight request overwrites the victim's callback entry, so the next matching node response (triggered by either request) is delivered to the attacker instead of the victim.

### Finding Description
`HandleLegacyUserMessage` inserts the callback with `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...Callback: callback}` [4](#0-3) . The key is only `msg.Body.MessageId`, a caller-controlled string bounded only by length/format checks in `Message.Validate` [5](#0-4)  — there is no `sender` component, unlike `common.RequestCache`, which explicitly keys by `globalId{sender, id}` for exactly this reason [1](#0-0)  and even rejects duplicate `(sender,id)` pairs [6](#0-5) .

When a node later replies, `handleWebAPITriggerMessage` looks up and deletes by `msg.Body.MessageId` alone and forwards the first matching response to whatever callback is currently stored under that key: `savedCb, found := h.savedCallbacks[msg.Body.MessageId]` then `savedCb.SendResponse(...)` [7](#0-6) . Since `HandleNodeMessage` only validates `msg.Body.Sender != nodeAddr` (i.e., that the response truly came from the claimed DON node), not that it corresponds to the correct original requester [8](#0-7) , nothing prevents the map entry from being silently replaced between when the victim submits their request and when the DON responds.

Exploit flow: victim submits a signed `web_api_trigger` request with `MessageId = X`; the gateway registers `savedCallbacks[X] = victimCallback` and forwards the request to all DON members. Before any node responds, the attacker (who knows/guesses `X`, e.g., sequential/predictable IDs) submits their own signed request also using `MessageId = X`; `HandleLegacyUserMessage` overwrites `savedCallbacks[X] = attackerCallback` and also forwards the attacker's copy to the DON. The next node response for `MessageId X` — which may be the response to the victim's original request, since IDs are echoed back unchanged from the message that was relayed to the DON — is matched only by `MessageId` and delivered to the attacker's callback, exposing the victim's webAPI trigger result to the attacker. The victim's original callback is discarded/lost with no response ever delivered.

### Impact Explanation
This breaks the "gateway request attributable to exactly one authenticated sender" invariant: the response payload for a `web_api_trigger` call intended for the victim is delivered to the attacker instead. This is a cross-user response confusion / information disclosure of another user's webAPI trigger result, and simultaneously a denial-of-service to the victim's own request (its callback is dropped and, unless purged first, the victim only sees a timeout).

### Likelihood Explanation
Preconditions are minimal: no privileged role is required, only the ability to sign and submit a gateway request via the standard user-facing `web_api_trigger` HTTP path (`gateway.ProcessRequest` → `HandleLegacyUserMessage`) [9](#0-8) . The attacker must know or guess the victim's `MessageId` and win a race before the DON responds (a window of up to `CallbackMaxAgeSec`, default 120s) [10](#0-9) . Feasibility depends heavily on how `MessageId` values are generated/exposed by the actual client generating them (sequential/predictable IDs make this trivial; random UUIDs make it impractical) — the finding is scoped to the server-side lack of sender-binding, which is the exploitable root cause regardless of client ID entropy.

### Recommendation
Key `savedCallbacks` by a composite of `(Sender, MessageId)` (mirroring `common.RequestCache`'s `globalId{sender, id}` pattern) instead of `MessageId` alone, and reject/ignore attempts to register a new callback for an already-pending `(sender, MessageId)` pair, and validate that the node response's carried sender/receiver context matches the original requester before dispatching.

### Proof of Concept
Go table/unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler via `setupHandler(t)`.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` with `MessageId = "shared-id"` and a distinct victim signer.
3. Before invoking `handleWebAPITriggerMessage`, call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` with the same `MessageId = "shared-id"` but a different (attacker) signer.
4. Assert `handler.savedCallbacks["shared-id"].Callback == attackerCallback`, proving the victim's callback was silently overwritten/lost.
5. Simulate a node response for `MessageId = "shared-id"` via `handler.handleWebAPITriggerMessage`; assert the response is delivered to `attackerCallback` (via a mock `handlers.Callback.SendResponse` expectation) and that `victimCallback.SendResponse` is never invoked.
