### Title
Missing sanity/bounds checks when decoding L1 `SystemConfig` update logs into critical L2 consensus parameters (`gasLimit`, `eip1559Denominator/Elasticity`, `minBaseFee`) - ([File: crates/common/genesis/src/updates/gas_limit.rs])

### Summary
The `SystemConfigUpdate` decoders that turn L1 `ConfigUpdate` event logs into the L2 `SystemConfig` fields (`GasLimitUpdate`, `Eip1559Update`, `MinBaseFeeUpdate`, `OperatorFeeUpdate`) only validate ABI encoding shape (pointer/length/decode success). None of them apply any semantic/threshold checks (e.g. `gas_limit > 0`, `eip1559_denominator != 0`, minimum/maximum bounds) before the value is unconditionally written into `SystemConfig` and subsequently consumed by block building and consensus. This mirrors the reported bug class: a critical parameter is accepted at "initialization"/update time with no sanity checks and no way to reject an out-of-range value, so a bad value silently propagates into chain state.

### Finding Description
`GasLimitUpdate::try_from` decodes the ABI payload and only checks the data length, pointer, and length fields, plus that the value fits in `u64`: [1](#0-0) 

`GasLimitUpdate::apply` then writes the value into `SystemConfig.gas_limit` unconditionally: [2](#0-1) 

The same pattern exists for the EIP-1559 denominator/elasticity update, which similarly performs no check that `eip1559_denominator != 0`: [3](#0-2) 

and for `MinBaseFeeUpdate`: [4](#0-3) 

These `SystemConfig` values are derived directly from L1 log data during derivation (`process_config_update_log` / `update_with_receipts`), i.e. attacker-influenced/attacker-written system-config data on L1, and flow straight into the payload attributes and consensus checks without any additional bounds validation: [5](#0-4) 

The resulting `SystemConfig.gas_limit` becomes the L2 block's `gas_limit` for future blocks (via `BaseNextBlockEnvAttributes`/`build_next_env`), and is enforced verbatim in block execution: [6](#0-5) [7](#0-6) 

If `gas_limit` is derived as `0` (or an extremely small value below the minimum intrinsic gas of any transaction), every non-deposit transaction (and, post-Regolith, every deposit transaction) will fail the `TransactionGasLimitMoreThanAvailableBlockGas` check, because `block_available_gas` becomes `0`. Because this parameter is part of the derived, canonical `SystemConfig` state (not a local RPC-settable knob like `miner_setGasLimit`/`GasLimitConfig` in `crates/execution/rpc/src/miner.rs`, which is a separate, node-local override), there is no way to override or ignore this without a hard-fork/derivation change once it has been applied — it is the equivalent of PoolTogether's un-guarded `maxExitFee`/`maxTimelockDuration`, but here the "owner" that can trigger an incorrect value is whoever writes the L1 `SystemConfig` update log data (via the L1 system config contract), and neither `TryFrom` decoding nor `apply()` reject clearly-invalid values such as zero.

Similarly, `eip1559_denominator == 0` would be accepted and stored into `SystemConfig.eip1559_denominator`; any downstream EIP-1559 base-fee formula that divides by the denominator (Holocene/Jovian base-fee param encoding/decoding and the reference `calc_next_block_base_fee`-style formula) is exposed to a division-by-zero if this value is ever used directly without re-validation at the point of use.

### Impact Explanation
This is a chain-halting/consensus-availability issue, not a fund-theft bug, but it satisfies "node halt / chain split" impact criteria: a `gas_limit` of `0` (or too small to fit any valid transaction, including the mandatory L1 attributes deposit transaction) derived from an L1 log would make every subsequent L2 block a stall point — the sequencer/builder cannot include any transactions, and validating nodes that re-derive the same `SystemConfig` would independently reach the same broken state, unable to safely produce further blocks. Because `SystemConfig` values are derived deterministically from L1 and become canonical chain state, this cannot be fixed with a node-local RPC/config change; it requires a protocol-level correction (hard fork / patch to the update decoder), which is a materially more severe outcome than PoolTogether's "redeploy the pool" fallback.

### Likelihood Explanation
Reaching this path requires only that an L1 log matching the `SystemConfigUpdate` topic and `GasConfig`/`GasLimit`/`Eip1559` update-type discriminator be emitted from the configured `l1_system_config_address`. In production this address is guarded by an owner/proxy admin on L1, so the practical likelihood depends on that L1-side privilege model, which is out of scope for the L2 derivation code itself; from the L2 derivation code's perspective the deserializer performs no independent defense against invalid values, so likelihood is "whenever the L1 authority makes a mistake or is compromised," consistent with the original finding's framing of "owner accidentally sets an incorrect value." I could not fully verify within the available tool calls whether the EIP-1559 base-fee calculation code paths (`crates/execution/chainspec/src/basefee.rs`, `crates/common/genesis/src/params.rs`) use `checked_div`/`saturating_div` versus raw division on `eip1559_denominator`, so the exact blast radius of a zero denominator (panic vs. saturating no-op) is unconfirmed and should be verified by a follow-up code review.

### Recommendation
Add explicit sanity/threshold validation in the `TryFrom<&SystemConfigLog>` implementations (and/or in `apply()`) for `GasLimitUpdate`, `Eip1559Update`, and `MinBaseFeeUpdate`:
- Reject `gas_limit == 0` or below a protocol-defined minimum (e.g., large enough to admit the mandatory L1 attributes deposit transaction plus at least one user transaction).
- Reject `eip1559_denominator == 0` (matching the `EIP1559ParamError`/holocene validation already used elsewhere for zero denominators, e.g. in `crates/common/consensus/src/extra/holocene.rs`/`ExecutorError::InvalidExtraData(Eip1559ValidationError)`), and apply the same defensive check wherever `SystemConfig.eip1559_denominator` is consumed in base-fee math.
- Consider surfacing decode/validation failures for these updates as explicit derivation-pipeline errors (rather than silently applying the value), so a bad log cannot silently corrupt canonical `SystemConfig` state.

### Proof of Concept
1. Configure a test L1 chain with `l1_system_config_address` set (as in `actions/harness/tests/derivation/main.rs`'s `gas_limit_change_does_not_disrupt_derivation`/`gas_limit_change_applies_on_adopting_origin_block` tests).
2. Call `L1Miner::enqueue_gas_limit_update(l1_sys_cfg_addr, 0)` (mirroring `enqueue_gas_limit_update` at [8](#0-7)  ) and mine the L1 block.
3. Run the L2 derivation pipeline / sequencer to adopt this L1 origin, as in `gas_limit_change_applies_on_adopting_origin_block` at [9](#0-8) .
4. Observe that `SystemConfig.gas_limit` becomes `0` with no error, and that the subsequent block-building/execution attempts fail with `TransactionGasLimitMoreThanAvailableBlockGas` for every transaction (per the gas check at [7](#0-6) ), demonstrating a chain-halt condition with no available on-chain remediation.

    fn try_from(log: &SystemConfigLog) -> Result<Self, Self::Error> {
        let LogData { data, .. } = &log.log.data;
        if data.len() != 96 {
            return Err(GasLimitUpdateError::InvalidDataLen(data.len()));
        }

        let Ok(pointer) = <sol!(uint64)>::abi_decode_validate(&data[0..32]) else {
            return Err(GasLimitUpdateError::PointerDecodingError);
        };
        if pointer != 32 {
            return Err(GasLimitUpdateError::InvalidDataPointer(pointer));
        }

        let Ok(length) = <sol!(uint64)>::abi_decode_validate(&data[32..64]) else {
            return Err(GasLimitUpdateError::LengthDecodingError);
        };
        if length != 32 {
            return Err(GasLimitUpdateError::InvalidDataLength(length));
        }

        let Ok(gas_limit) = <sol!(uint256)>::abi_decode_validate(&data[64..]) else {
            return Err(GasLimitUpdateError::GasLimitDecodingError);
        };

        // Prevent overflows here.
        let max = U256::from(u64::MAX as u128);
        if gas_limit > max {
            return Err(GasLimitUpdateError::GasLimitDecodingError);
        }

        Ok(Self { gas_limit: U64::from(gas_limit).saturating_to::<u64>() })
    }

/// A `GasLimit` system-config update takes effect on the first L2 block that
/// adopts the L1 origin carrying the change, not a block later.
///
/// With `block_time=2` and L1 `block_time=12`:
/// - L2 blocks 1-5 stay on genesis (epoch 0) and keep the genesis gas limit
/// - L2 block 6 adopts L1 block 1 and must already use the updated gas limit
#[tokio::test]
async fn gas_limit_change_applies_on_adopting_origin_block() {
    const NEW_GAS_LIMIT: u64 = 60_000_000;

    let l1_sys_cfg_addr = Address::repeat_byte(0xCC);
    let batcher_cfg = BatcherConfig::default();
    let rollup_cfg = TestRollupConfigBuilder::base_mainnet(&batcher_cfg)
        .with_l1_system_config_address(l1_sys_cfg_addr)
        .build();
    let genesis_gas_limit = rollup_cfg
        .genesis
        .system_config
        .expect("base mainnet config defines a system config")
        .gas_limit;
    assert_ne!(genesis_gas_limit, NEW_GAS_LIMIT, "test setup must change the gas limit");

    let mut h = ActionTestHarness::new(L1MinerConfig::default(), rollup_cfg);
    h.l1.enqueue_gas_limit_update(l1_sys_cfg_addr, NEW_GAS_LIMIT);
    h.l1.mine_block();

    let l1_chain = SharedL1Chain::from_blocks(h.l1.chain().to_vec());
    let mut sequencer = h.create_l2_sequencer(l1_chain);

    for _ in 1..=5u64 {
        let block = sequencer.build_next_block_with_single_transaction().await;
        assert_eq!(sequencer.head().l1_origin.number, 0, "L2 blocks 1-5 stay on genesis origin");
        assert_eq!(
            block.header.gas_limit, genesis_gas_limit,
            "epoch 0 blocks must keep the genesis gas limit"
        );
    }

    let adopting = sequencer.build_next_block_with_single_transaction().await;
    assert_eq!(sequencer.head().l1_origin.number, 1, "L2 block 6 should adopt L1 origin 1");
    assert_eq!(
        adopting.header.gas_limit, NEW_GAS_LIMIT,
        "the first L2 block that adopts the updated L1 origin must use the new gas limit immediately"
    );
}
