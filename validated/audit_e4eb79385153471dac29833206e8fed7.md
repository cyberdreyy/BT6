## Finding: RPC failure during pre-signature re-check defaults to "valid" instead of refusing to sign

### Title
Signer optimistically treats an unreachable stacks-node tenure-tip lookup as proposal validity during the pre-signature re-check, risking signature over a stale/non-canonical block - (File: stacks-signer/src/chainstate/mod.rs)

### Summary
`SortitionData::check_latest_block_in_tenure`, which is re-run immediately before a signer places a signature (via `check_block_against_signer_db_state`, called from both the validate-ok path and the pre-commit-threshold path), swallows a failure of `client.get_tenure_tip(tenure_id)` and returns `Ok(true)` — i.e. "the proposal is still the latest" — instead of surfacing the error and withholding the signature. This mirrors the reported pattern where a failed external dependency call (Chainlink price feed returning a default) is silently treated as a valid/pass result rather than causing the caller to abstain, letting an operation (signing) proceed on stale information.

### Finding Description
`check_latest_block_in_tenure` is the function that decides whether a proposed block is still ahead of everything the signer/node currently knows about in that tenure: [1](#0-0) 

When the local signer DB has no fresher record, it falls through to asking the stacks-node for the tenure's canonical tip: [2](#0-1) 

If `client.get_tenure_tip` errors (node briefly unreachable, RPC timeout, etc.), the function does not propagate the error or make the caller wait/refuse — it directly returns `Ok(true)`, i.e. "assume proposal is higher than the parent tenure for now." The in-code comment justifies this only for the *initial admission* path, where the stacks-node's own `/v3/block_proposal` endpoint will independently validate the same chainstate data before anything is signed.

However, this same function is reused, via `check_block_against_signer_db_state`, as the **re-check performed immediately before a signature is produced** — both right after a node validate-OK response (before broadcasting a pre-commit) and again once the pre-commit threshold is crossed (before actually signing): [3](#0-2) 

The purpose of this re-check, per the documented flow, is explicitly to catch state that changed *since* the original node validation — precisely the scenario in which relying on "the node will catch it elsewhere" no longer holds, because the node isn't consulted again for this purpose: [4](#0-3) 

So if the node's tenure-tip RPC is transiently unavailable exactly at this re-check moment (e.g., during a brief outage, a load spike, or an adversary-induced disruption of a signer's connection to its own node), the safety re-check silently degrades to "assume OK," and the signer proceeds to sign a block that could in fact be behind the network's true canonical tip in that tenure — i.e., a stale/non-canonical block — instead of aborting or holding the signature as `ConnectivityIssues` (the pattern used elsewhere in the same function, e.g. for DB errors just above it).

### Impact Explanation
This falls under "a signer signing an invalid, non-canonical, or conflicting block": a transient RPC failure at the exact re-check point converts a should-be-safety gate into an unconditional pass, letting the signer commit its (single, unrevocable) signature to a block that the re-check was specifically designed to catch as outdated.

### Likelihood Explanation
Requires the stacks-node's tenure-tip RPC to fail specifically during the narrow re-check windows (post validate-OK, or at pre-commit threshold) — a realistic but non-trivial timing condition (node restarts, network blips, resource exhaustion) rather than something a remote attacker can trivially force without also controlling node availability.

### Recommendation
In `check_latest_block_in_tenure`, when `client.get_tenure_tip` fails, do not blanket-return `Ok(true)`. Instead, propagate the error (as is already done for the `signer_db` failures above it) so callers in the pre-signature re-check path treat it as `ConnectivityIssues` and withhold/delay the signature, while callers on the initial-admission-only path (where the node's own validation endpoint is the real gate) can continue to optimistically proceed if that distinction is preserved by threading a parameter/flag indicating which caller context is invoking the check.

### Proof of Concept
Not executable from static review alone: reproducing requires orchestrating a stacks-node RPC outage for `get_tenure_tip` at the exact moment a signer instance runs `check_block_against_signer_db_state` (either in `handle_block_validate_response`'s validate-ok recheck, or in `handle_block_pre_commit`'s pre-commit-threshold recheck) while another, higher block already exists in that tenure that the local signer db does not yet know about. This would need to be validated in a running multi-signer testnet/integration harness, which is outside the scope of static code analysis.

Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
