### Title
Single-step, unvalidated `set_beneficiary_for_operator` can permanently strand a staker's stake distributions - ([File: aptos-move/framework/aptos-framework/sources/staking_contract.move])

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator redirect their commission payouts to any address in a single, unchecked step, exactly like the one-step `Ownable` transfer flagged in the external report. Unlike the vesting module's `set_beneficiary`, there is no validation that the new beneficiary can actually receive `AptosCoin`, and the value is later paid out through a single atomic loop (`distribute_internal`) that pays *every* shareholder of the staking contract — including the staker — in one transaction. If the chosen beneficiary address cannot accept the deposit, the whole distribution aborts, permanently blocking the staker's own withdrawal path until the operator (and only the operator) fixes the beneficiary.

### Finding Description
`set_beneficiary_for_operator` writes the new beneficiary directly with no validation and no two-step confirmation: [1](#0-0) 

That beneficiary address is later used as the payout recipient inside `distribute_internal`, which iterates over **all** shareholders of the `distribution_pool` (staker included) in a single `while` loop and calls `aptos_account::deposit_coins` for each one in the same transaction: [2](#0-1) 

`aptos_account::deposit_coins` only auto-registers a new/unregistered account if `can_receive_direct_coin_transfers` is true for that account; if the target account has disabled direct coin transfers (via `set_allow_direct_coin_transfers(false)`, a normal, permissionless self-service call), the deposit call aborts: [3](#0-2) 

Because `distribute_internal` processes the operator/beneficiary entry in the *same* atomic loop as the staker's entry, an abort on the beneficiary's deposit reverts the entire transaction — so the staker cannot withdraw their own unlocked stake either. `distribute_internal` is invoked from `distribute`, `unlock_stake`, `request_commission`, `update_commision`, and `switch_operator`, so essentially every withdrawal/administration path for that staking contract becomes permanently blocked: [4](#0-3) 

Only the operator can reset the beneficiary (`set_beneficiary_for_operator` is keyed by `operator_addr`, not by staker), so the staker has no independent recovery path — this mirrors the exact risk called out in the Ownable report: a single, unchecked address write with no ability for the affected party to unwind it.

### Impact Explanation
This corrupts the staking-contract payout/claim invariant: a role the staker does not control (the operator) can, in a single step and with no validation, cause the *staker's own* stake distribution rights to become permanently non-functional. This falls under the required "permanent lock or non-recoverable loss of claim rights in ... beneficiary ... flows" impact category, since it locks the staker's inactive/pending_inactive stake withdrawal indefinitely, with recovery gated behind the operator (a different role) taking action.

### Likelihood Explanation
Likelihood is moderate-to-high: setting `allow_arbitrary_coin_transfers` to false for a beneficiary address is a normal, permissionless account setting (not privileged), so a malicious or compromised operator can trivially select/produce such a beneficiary and call `set_beneficiary_for_operator` to grief the staker, or an operator can accidentally point the beneficiary at such an address, exactly reproducing the "human error, unrecoverable" scenario from the external report.

### Recommendation
- Validate that `new_beneficiary` in `set_beneficiary_for_operator` is capable of receiving `AptosCoin` (e.g., check `coin::is_account_registered` or `can_receive_direct_coin_transfers`) before committing the change, or register it proactively.
- Decouple the staker's payout from the operator/beneficiary payout in `distribute_internal` so that a failure to pay one recipient cannot block payouts to the others (e.g., catch/skip failed transfers and re-queue them, or process the beneficiary payout in an isolated, best-effort step rather than in the same atomic loop as the staker's).
- Consider a two-step confirmation (pending beneficiary + explicit claim by the new beneficiary) analogous to the OZ `Ownable2Step` pattern recommended in the report.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`.
2. `operator` (or an address it controls) calls `aptos_account::set_allow_direct_coin_transfers(false)` on some address `B` that has never registered `AptosCoin`.
3. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, B)`.
4. Time passes, rewards accrue, and the stake pool has inactive/pending_inactive funds.
5. Staker calls `unlock_stake`/`distribute`, or operator calls `request_commission`; `distribute_internal` attempts to pay `B` via `aptos_account::deposit_coins`, which aborts because `B` cannot receive direct transfers and is unregistered.
6. The entire transaction aborts — the staker cannot withdraw any unlocked stake through this staking contract until `operator` changes the beneficiary again, which the staker cannot force.

Note: I was not able to execute this in a live Move test environment within this session to confirm the exact abort code path end-to-end; the analysis is based on static tracing of `deposit_coins`, `can_receive_direct_coin_transfers`, and the `distribute_internal` loop structure in the indexed source.

    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
