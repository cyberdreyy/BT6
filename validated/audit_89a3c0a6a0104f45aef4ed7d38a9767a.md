### Title
APR0 withdraw request permanently bricks `stopEpoch` once APR is raised again — a stale `apr0TotalPrincipal` bucket makes `prepareStopEpochWithApr0` revert on every subsequent epoch stop (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2017-14919 is a DoS where a previously valid parameter (`windowBits = 8`) became invalid after a zlib change and crashed Node via an uncaught exception. The analog in idle-tranches: a withdraw request that was perfectly valid while `unscaledApr == 0` becomes a permanent poison state the moment the APR is set back to a non-zero value. `prepareStopEpochWithApr0` reverts `NotAllowed()` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0`, and because the revert happens before `apr0TotalPrincipal` is cleared, every subsequent `stopEpoch` reverts — the epoch pipeline is stuck exactly like the zlib crash.

### Finding Description
During an epoch where the strategy APR is 0, `IdleCDOEpochVariant.requestWithdraw` routes into `IdleCreditVault._requestWithdrawApr0`, which records the user's receipt in `apr0Users[user]` and adds the net principal to the global `apr0TotalPrincipal` bucket instead of `withdrawsRequests` (`IdleCreditVault.sol:285-286`, `:567-577`).

`prepareStopEpochWithApr0` is the strategy hook the CDO calls during `stopEpoch` to compute the epoch interest and adjusted pending fees. Its guard:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:505-508
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

fires *after* the `apr0TotalPrincipal == 0` fast path (`:502`) but *before* `apr0TotalPrincipal = 0` (`:540`). So if `apr0TotalPrincipal > 0` and `unscaledApr` was set non-zero (via `setAprs`/`setAprsWithBuffer` by the CDO at `stopEpoch`, or by the honest manager directly — both are permitted callers per `setApr` at `:225-235`), the call reverts and the bucket is never cleared. Because the same check runs on every later `stopEpoch` while the bucket stays non-zero, the revert is self-perpetuating: no epoch can ever be stopped again with a positive APR.

There is no other code path that decrements `apr0TotalPrincipal` — `_settleApr0` only mutates per-user `apr0Users` data, not the global bucket (`:545-565`). The only recovery is for the manager to set `unscaledApr` back to 0 to let one `stopEpoch` succeed and flush the bucket, i.e., funds are frozen until privileged intervention.

### Impact Explanation
An unprivileged KYC-passing lender deposits during an APR0 epoch and calls `requestWithdraw`. When the manager later raises the APR — a normal, expected operational action — the next `stopEpoch` reverts, and so does every retry. All vault funds (active NAV plus all pending receipts, including other users') cannot be released through the normal epoch cycle; queued withdraw claims can never be funded because funding only happens inside `stopEpoch`/`collectWithdrawFunds`. This is temporary freezing of all vault funds requiring emergency APR manipulation, matching the "formerly valid value now crashes the pipeline" shape of the CVE.

### Likelihood Explanation
- Attacker cost is one deposit + one `requestWithdraw` during any APR0 epoch (allowed actor: KYC-passing lender).
- Trigger is the honest manager raising APR while the bucket is non-empty — routine behavior.
- No existing guard prevents it: `_checkNotAllowed`/`isWalletAllowed` only gate the caller, `_skimDonatedAssets`/`_updateAccounting` don't touch the apr0 bucket, and the `NotAllowed` revert itself is what creates the freeze.
- The revert at `:506` would be dead code if `prepareStopEpochWithApr0` were only invoked when `unscaledApr == 0`, which indicates the hook is reached with non-zero APR — i.e., this revert is on the live `stopEpoch` path. (I could not fully verify the exact call site in `IdleCDOEpochVariant.stopEpoch`; if the CDO skips the hook when APR ≠ 0, the finding degrades to unreachable.)

### Recommendation
Do not revert on the stale-bucket condition. In `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, migrate the orphaned APR0 principal into the normal receipt path (e.g., `pendingWithdraws += apr0TotalPrincipal` and credit the affected users' `withdrawsRequests`), or clear `apr0TotalPrincipal` and settle users via `_settleApr0` at a zero rate. Alternatively, block non-zero `setAprs` while `apr0TotalPrincipal != 0` at the strategy level so the invalid transition can never be committed, rather than crashing the epoch pipeline after the fact.

### Proof of Concept
Foundry fork PoC (modeled on `test/foundry/IdleCreditVault.t.sol`, e.g. `testApr0WithdrawGetsInterestAtStopEpoch` which exercises this exact flow):

```solidity
function testApr0BucketBricksStopEpochAfterAprRaise() external {
    // APR0 setup (mirrors testApr0WithdrawGetsInterestAtStopEpoch)
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _forceLastEpochAprToZero();

    // Attacker (any KYC lender) opens an APR0 withdraw request
    uint256 trancheReq = IERC20(AAtranche).balanceOf(address(this)) / 2;
    cdoEpoch.requestWithdraw(trancheReq, address(AAtranche));
    assertGt(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 0);

    // Honest manager raises APR for the next epoch — legitimate action
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, initialProvidedApr);

    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest()
        + IdleCreditVault(address(strategy)).pendingWithdraws());

    // Every stopEpoch reverts NotAllowed because apr0TotalPrincipal != 0 && unscaledApr != 0,
    // and the revert prevents the bucket from ever being cleared.
    vm.prank(manager);
    vm.expectRevert(); // NotAllowed()
    cdoEpoch.stopEpoch(0, 0);

    vm.prank(manager);
    vm.expectRevert(); // still bricked on retry
    cdoEpoch.stopEpoch(0, 0);

    // All pending withdraw claims are unclaimable: funding only happens inside stopEpoch.
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```
