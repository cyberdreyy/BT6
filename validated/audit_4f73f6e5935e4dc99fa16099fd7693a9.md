One more look at epoch-number ordering in `stopEpoch`/`collectWithdrawFunds` to confirm the mismatch surface.### Title
Stale instant-withdraw epoch ledger inflates default recovery basis and permanently freezes recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the kernel's out-of-scope access on a dummy `iommu_domain` that lacks a real `dmar_domain`, `IdleCreditVault.claimInstantWithdrawRequest` pays a funded instant receipt but never clears the per-epoch ledger entries `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. When default recovery is later finalized, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read those stale entries as if they were still-live claims, inflating `totalBasis` and fabricating "prefunded" reserve that was already paid out. The resulting `defaultRecoveryReserve` overstates the contract's actual underlying balance, so later `_transferDefaultRecovery` calls revert, permanently freezing defaulted/post-default claimants' recovery funds.

### Finding Description
`requestInstantWithdraw` records both an aggregate (`instantWithdrawsRequests`, `pendingInstantWithdraws`) and a per-epoch ledger (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`). The funded claim path, `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393), clears only the aggregate entries:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. The only code that decrements `instantWithdrawClaimsByEpoch` is `_claimDefaultedInstantWithdrawRequest` (line 853), which runs only after default finalization.

At finalization, `defaultPendingClaimBasis()` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` to the claim basis whenever `pendingInstantWithdraws != 0`, and `_defaultPrefundedInstantReserve()` (lines 716-723) computes `instantBasis - pendingInstant` and treats the difference as underlying already held in the strategy. A receipt that was funded by `collectInstantWithdrawFunds` and already claimed via `claimInstantWithdrawRequest` remains counted in `instantBasis`, so the "prefunded" portion includes tokens that have already left the contract. `finalizeDefaultRecovery` (lines 685-692) then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` where `prefundedReserve` is phantom value.

This is the out-of-scope/dummy-object analog: the per-epoch instant ledger is accessed as though it still described a live claim structure long after the claim was settled, exactly like `domain_remove_dev_pasid` dereferencing a `dmar_domain` that the blocked domain never had.

### Impact Explanation
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on a basis diluted by already-paid claims, and `defaultRecoveryReserve` exceeds `underlyingToken.balanceOf(address(this))`.
- Defaulted-epoch claimants (`_claimDefaultedInstantWithdrawRequest`, `_claimDefaultedWithdrawRequest`) and post-default claimants (`_claimPostDefaultWithdrawRequest`) all spend from `defaultRecoveryReserve` via `_transferDefaultRecovery`. Once the real balance is exhausted, the remaining claims revert on `safeTransfer` (or on `defaultRecoveryReserve -= _amount` is fine but the token transfer fails), permanently freezing the unclaimed recovery.
- The freeze is permanent: there is no path to correct `instantWithdrawClaimsByEpoch` or top up the reserve after finalization.
- Loss magnitude: up to the full unfunded instant claim basis of the defaulted epoch — every receipt holder after the phantom reserve is consumed receives nothing.

### Likelihood Explanation
An unprivileged attacker (any KYC-passing lender / tranche holder) can create the stale state without any privileged action:

1. During a running epoch, request an instant withdraw; the honest manager's flow funds it via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds`.
2. Claim it via `claimInstantWithdrawRequest` — aggregate cleared, per-epoch ledger stale.
3. Leave (or have any other user leave) one small unfunded instant receipt in the same `epochNumber`, so `pendingInstantWithdraws != 0`.
4. On borrower default and `finalizeDefaultRecovery`, `instantWithdrawClaimsByEpoch[epochNumber]` still includes the attacker's already-paid amount, fabricating prefunded reserve.

No privileged role misbehavior is required; manager/owner calls are used only in their honest sequence. The existing guards do not stop it: `_ensureDefaultRecoveryInitialized` only checks `pendingInstantWithdraws`/`pendingWithdraws` aggregates, and `_transferFundedClaim`'s reserve guard only applies after a reserve exists — the stale-ledger read happens before any guard can see it.

### Recommendation
Mirror the kernel fix ("return early / don't treat the dummy domain as a real domain"): keep the per-epoch ledger consistent with the aggregate. In `claimInstantWithdrawRequest`, after determining the amount, locate and clear the user's `instantWithdrawsRequestsByEpoch` entry for the relevant epoch(s) and decrement `instantWithdrawClaimsByEpoch` accordingly, so that `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see live, unpaid claims. Alternatively, track a separate `instantWithdrawFundedByEpoch` counter so finalization can distinguish "claimed and paid" from "funded but unclaimed" and "unfunded" portions.

### Proof of Concept
Reproducible Foundry fork PoC sketch:

```solidity
// Epoch running: attacker deposits, then requests instant withdraw
cdoEpoch.startEpoch(); // manager
vm.prank(attacker); cdo.depositAA(100e6);
// ... instant delay passes, funds available
vm.prank(attacker); cdo.requestInstantWithdraw(50e6); // via CDO -> strategy
// honest manager funds instant queue
vm.prank(manager); cdoEpoch.getInstantWithdrawFunds();
vm.prank(attacker); cdo.claimInstantWithdrawRequest();
// attacker (or victim) leaves a small unfunded instant receipt same epoch
vm.prank(victim); cdo.requestInstantWithdraw(1e6);
// borrower default (honest failure), owner finalizes recovery
vm.prank(owner); cdo.finalizeDefault(...);
vm.prank(owner); cdo.finalizeDefaultRecovery(...);
// invariant: defaultRecoveryReserve > underlying.balanceOf(strategy)
// victim's defaulted/post-default claim now reverts -> frozen recovery
vm.expectRevert();
vm.prank(victim); cdo.claimInstantWithdrawRequest();
```

**Caveat:** within the iteration budget I could not fully verify the exact `epochNumber` at which `collectInstantWithdrawFunds`/`claimInstantWithdrawRequest` run relative to the default epoch keying (`instantWithdrawClaimsByEpoch[epochNumber]` uses the *current* epoch at finalization), nor the IdleCDOEpochVariant call order of `deposit()`/`epochNumber += 1` vs `collectWithdrawFunds`. If finalization keys on a bumped epoch while the stale entry sits on the prior epoch, the inflated-basis path narrows to same-epoch instant claims only. The stale-ledger inconsistency itself (per-epoch entries never cleared on funded claims) is confirmed in the code at IdleCreditVault.sol:380-393 and 644-649.
