### Title
Multisig created with zero attached deposit cannot pay for its own storage - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` builds a single batched promise (`create_account` → `deploy_contract` → `transfer(attached_deposit)` → `function_call("new", …)`) but never enforces a minimum attached deposit, unlike its sibling factories. An attacker can call `create` with zero (or negligible) `attached_deposit`, producing a multisig sub-account that is deployed and holds member keys/state but lacks the NEAR balance required to cover its own storage staking cost.

### Finding Description
The invariant the question asks about is: `account_balance(new_multisig) >= storage_stake_required(new_multisig)` must hold immediately after `create` succeeds, so the multisig can subsequently accept and execute requests. In `multisig-factory/src/lib.rs`:

```
pub fn create(&mut self, name: AccountId, members: Vec<MultisigMember>, num_confirmations: u64) -> Promise {
    let account_id = format!("{}.{}", name, env::current_account_id());
    Promise::new(account_id)
        .create_account()
        .deploy_contract(CODE.to_vec())
        .transfer(env::attached_deposit())
        .function_call(b"new".to_vec(), ..., 0, env::prepaid_gas() - CREATE_CALL_GAS)
}
``` [1](#0-0) 

There is no `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` guard here, whereas the comparable `staking-pool-factory` and `lockup-factory` factories both enforce a `MIN_ATTACHED_BALANCE` check before creating their sub-accounts. Searching the whole repo for `MIN_ATTACHED_BALANCE` / deposit assertions shows matches in `lockup-factory/src/lib.rs` and `staking-pool-factory/src/lib.rs`, but none in `multisig-factory/src/lib.rs` aside from the unrelated `#[payable]` attribute.

Because `env::attached_deposit()` is fully attacker-controlled, an unprivileged caller can invoke `create(name, members, num_confirmations)` with 0 yoctoNEAR attached. The resulting `<name>.<factory>` account is created, the `multisig2` contract code is deployed to it (consuming its own newly-created, zero balance for code storage), and `new` is invoked to register the `members` (including full-access `AccessKey` members). Because the account has no NEAR to cover its storage staking requirement, it is left in a state where it cannot pay for its own storage: any subsequent state-changing call (adding a request, confirming, executing) will fail with an insufficient-balance error, and yet the account remains addressable and holds the member access keys chosen by the attacker.

### Impact Explanation
If a victim later transfers funds to what they believe is a functioning multisig at this address (e.g., relying on the account name/key list), those funds become stuck: the multisig contract cannot process `add_request`/`confirm` calls because the account's balance is pinned to (or below) the minimum required for storage, so no further mutating call can succeed. This matches the Critical "funds permanently frozen" category, since NEAR sent to the account after creation cannot be moved out via the multisig logic. The attacker does not need any special permission - only the ability to call the public `create` entrypoint with `attached_deposit = 0`.

### Likelihood Explanation
The precondition is trivial: any account can call `multisig-factory`'s `create` with zero deposit and arbitrary `members`/`num_confirmations`, which is exactly the entrypoint's contract (public, `#[payable]`, no minimum-deposit assertion). This costs the attacker only gas. The "repeat in same block" nuance in the question is not required to realize the core defect - the missing minimum-deposit check by itself is sufficient to leave an underfunded multisig; I was not able to fully trace the exact NEAR runtime receipt-rollback semantics for the batched `create_account`/`deploy_contract`/`transfer`/`function_call` actions when a sub-action fails, since that depends on `nearcore` behavior outside this repo, but the structural absence of the deposit-minimum guard (present in the sibling factories) is directly verifiable in this file.

### Recommendation
Add a `MIN_ATTACHED_BALANCE` (or dynamically computed minimum, e.g. based on `CODE.len()` storage cost plus per-key storage cost times `members.len()`) assertion in `create`, mirroring `lockup-factory::create` and `staking-pool-factory::create`, e.g.:
```rust
assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit to create a multisig account");
```

### Proof of Concept
Using `near-sdk-sim` / `near-workspaces`:
1. Deploy `multisig-factory` contract.
2. Call `create("alice", members, 1)` from an unprivileged account with `deposit = 0`.
3. Assert the call succeeds and `alice.<factory>` account exists (`view_account` balance == 0 or below storage minimum).
4. Attempt `add_request`/`confirm` on the resulting multisig contract and assert it fails with an insufficient-balance / storage error, proving the created contract permanently cannot process requests, i.e. `account_balance(new_multisig) < storage_stake_required(new_multisig)` both before and after the call, breaking the claimed invariant.
