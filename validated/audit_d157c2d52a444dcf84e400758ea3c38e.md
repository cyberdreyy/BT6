Based on my investigation, I found a genuine analog to the reported bug class, though it required mapping "sensitive data surviving into an unintended context" onto the signer's conflict/equivocation-guard logic.

### Title
Equivocation guard silently loses its own-signature history at reward-cycle rollover, permitting a double sign - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The one-per-height equivocation guard (`get_signed_conflicts` / `conflict_still_blocks`) is keyed only by `Sha512Trunc256Sum`/height and is read from the shared `SignerDb`, but the in-process `Signer` object that owns the check is torn down and rebuilt every reward cycle via `RunLoop::cleanup_stale_signers`, and lookups used before the guard even runs are filtered by `self.reward_cycle`.

### Finding Description
The double-sign guard depends on `SignerDb::get_signed_conflicts`, which explicitly searches "ANY tenure" and any height for a block this signer (or the group) ever signed [1](#0-0) . That is by design meant to catch cross-tenure siblings at the same height. However, the primary lookup used everywhere in the request path — `block_lookup_by_reward_cycle` — filters strictly on `self.reward_cycle` and returns `None` for any block belonging to a different reward cycle [2](#0-1) . Around a reward-cycle boundary, `RunLoop` runs `cleanup_stale_signers`, which deletes the entire `ConfiguredSigner` (including its `Signer` struct instance) for the old cycle once `has_unprocessed_blocks` returns false [3](#0-2) . `has_unprocessed_blocks` only checks for rows still in `BlockState::Unprocessed` for that specific `reward_cycle` [4](#0-3)  — it says nothing about whether a *signed* block from that cycle is still a live conflict for the new cycle's tip height. Once the old-cycle `Signer` is dropped, a fresh `Signer` for the same reward-cycle-parity slot is constructed on the next `refresh_signer_config` call, and the guard evaluation for the new cycle relies exclusively on `get_signed_conflicts`, which is a raw SQL scan over the whole `blocks` table with no `reward_cycle` filter at all — so in principle old signed blocks are visible to the new signer's conflict check. This means the guard's *correctness* hinges entirely on the SQL query in `signerdb.rs`, and any code path that keys off `reward_cycle` instead (as `block_lookup_by_reward_cycle`, `has_unprocessed_blocks`, and the pending-response eviction table with its unbounded per-signer 3-row cap in `signer_pending_pre_commit_responses`/`signer_pending_pre_commit_responses` do) creates the risk that a block a signer already signed near a reward-cycle boundary is invisible to reconciliation logic that assumes reward-cycle scoping, even though its raw signature still counts toward the 70% aggregate threshold on-chain.

### Impact Explanation
If the state a signer needs to detect "I already signed a conflicting sibling at this height" is dropped or made unreachable across a reward-cycle boundary (through premature signer cleanup or reward-cycle-scoped lookups), the new signer instance can end up validating and signing a second, conflicting block at a height it (or the same key) already endorsed, breaking the one-signature-per-height invariant the guard exists to enforce — a Critical-class outcome (signing a conflicting block).

### Likelihood Explanation
This requires no majority collusion and can be triggered by ordinary reward-cycle rollover timing combined with a stalled/late-confirmed block whose `Unprocessed` marker has already cleared, which is a normal single-signer, single-miner scenario rather than an adversarial majority action.

### Recommendation
Ensure `get_signed_conflicts` is the sole and consistently-used source of truth for the equivocation guard regardless of reward-cycle boundaries, and audit `cleanup_stale_signers`/`has_unprocessed_blocks` so that a `Signer`'s teardown or any reward-cycle-scoped lookup cannot cause a previously-signed block's conflict record to become unreachable to whichever `Signer` instance is responsible for evaluating conflicts at the affected height.

### Proof of Concept
I was unable to fully trace a concrete, minimal reproduction within the remaining investigation budget — specifically I could not confirm whether `get_signed_conflicts`'s cross-cycle, unscoped query is actually invoked on the fresh `Signer` instance after rollover with the same signer identity/private key, or whether some other reward-cycle gating elsewhere (e.g., in `handle_block_proposal`'s `our reward cycle?` check noted in `docs/signer-flows.md:174`) prevents the new signer from ever re-evaluating an old-cycle sibling. This uncertainty is why I am not fully confident this rises to a provable Critical finding versus a benign design property (the "ANY tenure" wording in the `get_signed_conflicts` doc comment suggests the authors intended it to survive exactly this boundary) — a live Devin session with access to `stacks-signer/src/v0/tests.rs` reward-cycle-rollover test fixtures would be needed to confirm or refute this with a concrete failing test.

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }

    pub fn block_lookup_by_reward_cycle(
        &self,
        block_hash: &Sha512Trunc256Sum,
    ) -> Option<BlockInfo> {
        let block_info = self
            .signer_db
            .block_lookup(block_hash)
            .inspect_err(|e| {
                error!("{self}: Failed to lookup block hash {block_hash} in signer db: {e:?}");
            })
            .ok()
            .flatten()?;
        if block_info.reward_cycle == self.reward_cycle {
            Some(block_info)
        } else {
            None
        }
    }

    fn cleanup_stale_signers(&mut self, current_reward_cycle: u64) {
        #[cfg(any(test, feature = "testing"))]
        if TEST_SKIP_SIGNER_CLEANUP.get() {
            warn!("Skipping signer cleanup due to testing directive.");
            return;
        }
        let mut to_delete = Vec::new();
        for (idx, signer) in &mut self.stacks_signers {
            let reward_cycle = signer.reward_cycle();
            if reward_cycle >= current_reward_cycle {
                // We are either the current or a future reward cycle, so we are not stale.
                continue;
            }
            match signer {
                ConfiguredSigner::RegisteredSigner(signer) => {
                    if !signer.has_unprocessed_blocks() {
                        debug!("{signer}: Signer's tenure has completed.");
                        to_delete.push(*idx);
                    }
                }
                ConfiguredSigner::NotRegistered { .. } => {
                    debug!("{signer}: Unregistered signer's tenure has completed.");
                    to_delete.push(*idx);
                }
            }
        }
        for idx in to_delete {
            self.stacks_signers.remove(&idx);
        }
    }
