### Title
Missing allowlist and per-sender rate-limiting on legacy `web_api_trigger` gateway messages allows unauthenticated fan-out to all DON members - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` in the capabilities gateway handler validates only payload shape, timestamp freshness, and method name before forwarding the message to every member of the configured DON via `don.SendToNode`. The code contains an explicit `// TODO: apply allowlist and rate-limiting here` marker at exactly the point where sender authorization/quota checks should occur, and no such check exists anywhere else in the call path.

### Finding Description
The gateway's public entry point `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218`) receives a signed legacy JSON-RPC message from an HTTP client, calls `msg.Validate()` (structural/signature-format validation), resolves the handler by `msg.Body.DonId`, and then calls `h.HandleLegacyUserMessage(ctx, msg, callback)`. [1](#0-0) 

Inside `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341`), the checks performed are: (1) payload JSON decodes, (2) `payload.Timestamp != 0`, (3) message is not stale relative to `MaxAllowedMessageAgeSec`. Immediately after these checks, at line 384, the code has `// TODO: apply allowlist and rate-limiting here`, and then only verifies `msg.Body.Method == MethodWebAPITrigger` before building a request and forwarding it to **every** configured DON member: [2](#0-1) 

Notably, the analogous node-originated path `handleWebAPIOutgoingMessage` explicitly enforces `h.nodeRateLimiter.Allow(nodeAddr)` before proceeding [3](#0-2) , confirming that rate-limiting infrastructure (`ratelimit.RateLimiter`) exists in this handler but is deliberately not applied to the user-facing legacy trigger path, matching the TODO. There is no per-sender allowlist check anywhere in `HandleLegacyUserMessage`, `common.ValidatedRequestFromMessage`, or `gateway.ProcessRequest`.

### Impact Explanation
Any caller who can reach the gateway's user HTTP port and craft a structurally valid, non-stale legacy message addressed to a known/guessable `DonId` can have it forwarded to all DON members with no allowlist gate and no per-sender rate limit at this layer. This enables cost-free spam/flooding of `MethodWebAPITrigger` messages toward a DON, causing unbounded fan-out load on every DON member and resource exhaustion, and — if the DON-side capability does not independently re-verify sender authorization for the specific workflow — unauthorized triggering of workflow execution. This aligns with a "request impersonation / allowlist bypass leading to unauthorized job run" bounty impact class.

### Likelihood Explanation
The precondition is only network access to the gateway's user-facing port and the ability to produce a signature that passes `msg.Validate()`'s structural checks — no special role, credential, or admin access is required, consistent with the "unprivileged caller" threat model. The gap is directly evidenced by the TODO comment and by the absence of an allowlist/rate-limit call between the timestamp check and the `don.SendToNode` fan-out loop, making this a straightforward, repeatable path (no timing races or exotic conditions).

### Recommendation
Implement the missing checks at the marked TODO location in `HandleLegacyUserMessage`: (1) verify `msg.Body.Sender` (or equivalent signer identity) against a per-DON/per-workflow allowlist before accepting `MethodWebAPITrigger` messages, mirroring the allowlist enforcement used elsewhere in the gateway/DON trust model; (2) apply a per-sender `ratelimit.RateLimiter` (the same mechanism already used in `handleWebAPIOutgoingMessage`) keyed by sender address before the `don.SendToNode` fan-out loop, rejecting or throttling requests that exceed quota.

### Proof of Concept
Go handler-level integration test plan:
1. Instantiate `capabilities.NewHandler` with a `HandlerConfig` and a mock `handlers.DON` (from `core/services/gateway/handlers/mocks/don.go`) tracking calls to `SendToNode`.
2. Construct N distinct legacy `api.Message` payloads with `Method = MethodWebAPITrigger`, valid/self-generated signatures (no allowlist membership), unique `MessageId`s, fresh `Timestamp`, targeting the same `DonId`.
3. Call `h.HandleLegacyUserMessage(ctx, msg, callback)` for each message from a simulated "unauthenticated" sender identity not present in any allowlist config.
4. Assert that `don.SendToNode` is invoked once per DON member for every one of the N messages (i.e., N × len(donConfig.Members) total calls), demonstrating unrestricted fan-out.
5. Assert there is no rejection, throttling, or error returned regardless of message volume or sender identity, confirming absence of allowlist/rate-limit enforcement at this layer.
