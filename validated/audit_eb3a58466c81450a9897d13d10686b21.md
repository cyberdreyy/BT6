### Title
Fail-open handling of an unreachable node lets a signer sign two conflicting blocks in the same tenure (equivocation) - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
In `handle_block_pre_commit`, when a proposal that has just reached the pre-commit threshold conflicts with a block the signer already signed/accepted *in the same tenure*, the signer is supposed to ask its own node whether that earlier block already reached the tenure's canonical tip before signing the new, conflicting one. If that RPC call to the node fails for any reason (timeout, node restart, transient network blip), the code does not refuse to sign — it logs "Treating the tenure as unconfirmed" and falls through to signing the new block anyway. This mirrors the external report's root cause exactly: an irreversible, safety-critical action (here, putting a signature on a block) is committed *before* confirming the state on the other side (whether the prior conflicting block already became canonical), and the failure path is treated as "proceed" instead of "abstain."

### Finding Description
`handle_block_pre_commit` determines whether a fresh, same-height/same-tenure conflicting signature still blocks the current proposal: [1](#0-0)

When `get_tenure_tip` errors, execution falls through the `match` and continues to the final `mark_locally_accepted`/sign step, exactly as if there had been no conflict at all. This is the "own tenure, node unreachable" branch documented in `docs/signer-flows.md`: [3](#0-2) 
```
LIVE -- "no, only locally accepted<br/>and a sibling at this height" --> HOLD1
...
OWN -- yes --> TIP{"own tenure confirmed<br/>at ≥ this height?<br/>get_tenure_tip(own tenure)"}
TIP -- yes --> HOLD2["refuse to sign"]:::hold
TIP -- "no — never confirmed" --> SIGN
TIP -- "node unreachable" --> SIGN
```
and explicitly called out as an intentional asymmetry versus the cross-tenure case, where an unreachable node instead defaults to *not* signing: [4](#0-3) 

The problem is that "node unreachable" and "the prior conflicting block genuinely never became canonical" are treated as the same outcome, when they are not. `stacks_client.get_tenure_tip` failing only proves the signer could not talk to its own node at that instant — it proves nothing about whether the earlier, already-signed conflicting block was broadcast and accepted by that very node (or another honest node) moments before. A signer can have: (1) signed block B at height h in tenure T, (2) `handle_post_block`/broadcast succeeded and the node adopted B, (3) a transient RPC hiccup on the *next* `get_tenure_tip` call for an unrelated re-proposal at height h in the same tenure T, and (4) the signer then signs block B′, a genuine sibling of B at the same height in the same tenure. That is a direct equivocation: the signer has now put a valid signature on two conflicting blocks at the same height, which is exactly the "signer signing a conflicting block" class of critical impact called out in the rules — breaking the one-per-height / approved-vs-canonical equality that `get_last_signed_block`/`get_signed_conflicts` machinery exists to enforce.

Note this is distinct from (and worse than) the intentionally accepted risk for *other tenures'* conflicts, where the same failure mode explicitly holds back the signature (`SORT -- "could not ask..." --> HOLD1`) — the asymmetry for the *own*-tenure branch is a deliberate liveness/safety trade-off that, per the documentation's own reasoning, favors availability over the one invariant (never sign two blocks at the same height) the whole conflict-tracking system is built to protect.

### Impact Explanation
This is a Critical-class analog per the task's rubric: a signer signing a conflicting block. A single transient failure of the signer's connection to its own stacks-node (no majority collusion, no other signer's key, no auth token) is sufficient to flip the "confirm before sign" check into "assume safe, sign." The resulting double signature over two blocks at the same height in the same tenure is exactly the equivocation the pre-commit/conflict-tracking design (sections 2, 5, 7 of `docs/signer-flows.md`) exists to prevent.

### Likelihood Explanation
The trigger condition — an RPC call to the signer's own node failing/timing out at the specific moment `handle_block_pre_commit` is re-evaluating a same-tenure sibling proposal — is a plausible, one-slot-miner-and-gossip-triggerable condition: a miner can legitimately (or adversarially, by racing re-proposals) submit two competing blocks at the same height in one tenure; the signer only needs to experience an ordinary node hiccup at exactly the wrong instant. No majority of signers, no compromised keys, and no auth-token access are required.

### Recommendation
Treat an unreachable/erroring `get_tenure_tip` in the own-tenure conflict check the same conservative way the cross-tenure branch does: refuse to sign (`HOLD`) rather than falling through to `SIGN`, or retry the query with a bounded backoff before deciding. At minimum, do not silently unify "node unreachable" with "conflict resolved" for a check whose entire purpose is to prevent equivocation.

### Proof of Concept
1. Signer signs block `B` at height `h` in tenure `T` (`mark_locally_accepted`, `signed_self` set) and successfully broadcasts it; the node adopts `B` as its tip.
2. `B`'s `last_endorsed` timestamp later falls outside `tenure_last_block_proposal_timeout` (i.e. it becomes "stale" per the freshness check), which is required to reach the second conflict branch in `handle_block_pre_commit` rather than the first (fresh-conflict) branch.
3. A re-proposed sibling block `B′` at the same height `h` in tenure `T` reaches the pre-commit threshold.
4. `handle_block_pre_commit` enters the branch at `stacks-signer/src/v0/signer.rs:1432-1457`; the call to `stacks_client.get_tenure_tip(&T)` fails (e.g., node briefly unresponsive/restarting).
5. Code logs "Treating the tenure as unconfirmed" and falls through; no fresh fully-blocking conflict remains, so it proceeds to `mark_locally_accepted` and signs `B′`.
6. The signer now holds valid signatures over both `B` and `B′`, two conflicting blocks at height `h` in tenure `T`.
