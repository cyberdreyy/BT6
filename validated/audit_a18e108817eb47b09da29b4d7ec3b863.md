### Title
Stale confirmations from removed multisig keys are still counted toward the confirmation threshold, allowing a request to execute below the required number of live signers - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
The `confirm()` function in both the basic multisig (`multisig/src/lib.rs`) and the extended multisig (`multisig2/src/lib.rs`) counts confirmations purely from the stored `confirmations` `HashSet` without verifying that each confirming key/member is still a currently authorized signer. When a key/member is removed via `DeleteKey`/`DeleteMember`, the code only purges pending *requests that key originally created*; it never scrubs that key's already-recorded confirmations from *other* requests it had previously confirmed. This lets a stale confirmation from a removed signer be counted toward `num_confirmations`, letting a request execute with fewer live, currently-authorized confirmers than the configured K-of-N threshold requires — the exact "confirmations counted vs. live members" divergence analogous to the KintoWallet report's improper signer-count validation.

### Finding Description
`confirm()` treats `self.confirmations.get(&request_id).unwrap().len()` as the number of valid signers who have approved a request: [1](#0-0) 

Confirmations are only cleaned up when a request is deleted/executed, or as a side effect of `DeleteKey`, which removes pending requests **originated by** the deleted key: [2](#0-1) 

This loop filters `requests` by `r.signer_pk == pk` — i.e., only requests *added* by the removed key. It does not iterate over `self.confirmations` to strip the removed key's public key from the confirmation sets of requests it merely *confirmed* (but did not add). Consequently, a request `R` added by key `K2` and confirmed by key `K1` retains `K1` in `confirmations[R]` forever, even after `K1`'s access key is deleted from the account via a separate `DeleteKey` request.

Because `confirm()` (line 255) does no live-membership check — it neither re-derives "current members" from account state nor cross-checks each stored confirming key against a live members list — the stale entry from the now-unauthorized `K1` is indistinguishable from a live confirmation and is still counted toward `num_confirmations`.

The same defect exists in the account/member-based `multisig2` contract: `delete_member()` also only purges requests where `r.member == member` (the member's own authored requests), never scrubbing that member from other requests' confirmation sets, and `confirm()` there has the identical `confirmations.len() as u32 + 1 >= self.num_confirmations` check with no live-member cross-check at count time: [3](#0-2) [4](#0-3) 

The equality that should hold is:
`confirmations_counted(R) == confirmations_from_currently_live_members(R)`

but the code allows `confirmations_counted(R) > confirmations_from_currently_live_members(R)` whenever a confirmer is later removed, breaking the threshold invariant `live_confirmations(R) >= num_confirmations` that is supposed to gate `execute_request`.

### Impact Explanation
This is a Critical-impact analog per the rules: "a multisig request executed below threshold." A transfer, `DeployContract`, `FunctionCall`, or key-management request can be pushed through `execute_request` (including NEAR `Transfer` actions, line 173) with fewer genuinely live, currently-authorized signers than `num_confirmations` requires, because a removed key's stale confirmation still counts. This directly undermines the security guarantee of the K-of-N multisig custody model — funds or contract upgrades that should require K live signers can be authorized with fewer.

### Likelihood Explanation
The bug is reachable purely through the contract's own public API (`add_request`, `confirm`, `DeleteKey`/`DeleteMember`) without needing the foundation, an external redeploy, or a compromised key — it only needs the ordinary sequence of operations available to any of the multisig's own signers (add a request, have another signer confirm it, then have the confirming signer removed through a routine key-rotation flow, which is an expected multisig operation). No malicious validator, RPC interception, or social engineering is required; it is a straightforward consequence of the missing confirmation-scrubbing logic in `DeleteKey`/`DeleteMember`.

### Recommendation
When removing a key/member (`DeleteKey`/`DeleteMember`), iterate over all pending requests' `confirmations` sets (not just requests authored by that key) and remove the deleted key/member from each. Alternatively, at `confirm()` time, validate that every entry in `confirmations` still corresponds to a live, currently authorized key/member before comparing the count against `num_confirmations`, discarding stale entries so the effective count always reflects live signers.

### Proof of Concept
Using `multisig/src/lib.rs` with `num_confirmations = 2` and keys `K1, K2, K3`:
1. `K2` calls `add_request(R)` where `R` is `Transfer{amount}` to an attacker-controlled `receiver_id` → `R.signer_pk = K2`, `confirmations[R] = {}`.
2. `K1` calls `confirm(R)` → `confirmations[R] = {K1}` (1 of 2 needed; not yet executed).
3. `K2` and `K3` create and confirm a separate request `R2 = DeleteKey{K1}` and execute it (2-of-3 reached on `R2`). In `execute_request`'s `DeleteKey` branch (lines 198-216), only requests with `signer_pk == K1` are purged — `R` (signer_pk = `K2`) is untouched, and `confirmations[R]` still contains `K1`. `K1`'s access key is now deleted from the account.
4. `K3` (the only other live signer) calls `confirm(R)`. `confirmations[R].len()` (1, from stale `K1`) `+ 1` (`K3`) `= 2 >= num_confirmations (2)` → `execute_request(R)` runs the `Transfer`, even though only one currently-live signer (`K3`) ever approved it and `K2` never confirmed `R` at all.

This demonstrates a 2-of-3 multisig transfer executing with only 1 live confirmation, bypassing the configured threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
