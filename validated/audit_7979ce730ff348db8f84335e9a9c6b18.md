### Title
`DriftHarvestReward::cpi_transfer_to_destination` transfers reward token without a zero-amount guard, permanently DoS'ing reward harvesting for that spot market - (File: `programs/marginfi/src/instructions/drift/harvest_reward.rs`)

### Summary
`drift_harvest_reward` withdraws admin-deposited rewards from an arbitrary Drift spot market and then unconditionally transfers whatever balance lands in the intermediary token account to the destination, with no check that the amount is non-zero, mirroring the `ExtraRewardStashV2.stashRewards()` bug class where an unchecked zero-value transfer to an arbitrary/externally-controlled token can permanently block reward collection.

### Finding Description
`cpi_transfer_to_destination` computes `amount = accessor::amount(&self.intermediary_token_account...)` and calls `transfer_checked(cpi_ctx, amount, decimals)` regardless of whether `amount` is zero: [1](#0-0) 

The `reward_mint` for this instruction is not restricted to a small, curated allow-list; it is simply "the harvest spot market's mint" which the constraints only require to differ from the bank's own mint and from the bank's Drift spot market: [2](#0-1) 

Because `reward_mint` is a `Token-2022`-compatible `InterfaceAccount<Mint>` (via `TokenInterface`), it can carry arbitrary Token-2022 extensions (e.g., a transfer-hook program) that reject zero-amount transfers — the SPL analog of a "revert on zero-value transfer" ERC-20, exactly the token class the original report warns about.

The withdraw step uses `withdraw(cpi_ctx, market_index, u64::MAX, true)` (reduce-only), which drains whatever balance exists in the target Drift admin-deposit position: [3](#0-2) 

After the first successful harvest, the admin-deposit position balance is (near) zero. Any subsequent call to `drift_harvest_reward` for that same spot market/reward mint pair will withdraw ~0 tokens and then attempt `transfer_checked` with `amount == 0`. If the reward mint enforces non-zero transfer amounts via a Token-2022 transfer-hook extension, this call will always revert going forward — permanently bricking harvesting for that reward token, exactly as described in the referenced finding ("stashRewards() can be blocked for even an extended period of time").

Notably, `programs/marginfi/src/instructions/drift/claim_bad_debt.rs` already implements the correct defensive pattern for an analogous transfer: [4](#0-3) 
This shows the codebase is aware of and mitigates the zero-transfer risk elsewhere, but the same guard is missing in `harvest_reward.rs`.

Additionally, `DriftHarvestReward`'s account list has no signer/admin field at all — the instruction appears callable permissionlessly by anyone holding the correct PDAs, meaning any party (not just a trusted admin) could accidentally or intentionally trigger the zero-amount call that bricks the ATA/spot-market pairing before the intended harvester acts.

### Impact Explanation
If the configured reward mint reverts on zero-amount transfers (e.g. via a Token-2022 transfer hook), `drift_harvest_reward` becomes permanently unusable for that spot market once the admin-deposit balance is fully drained (or if called when balance is already zero). This durably freezes the protocol's ability to harvest that reward stream to the global fee wallet, a base/permanent-freeze impact on a legitimate (if auxiliary) revenue-collection code path. Severity is Medium, consistent with the original finding's rating, since it affects availability of reward collection rather than fund safety directly.

### Likelihood Explanation
Likelihood depends on the admin choosing/being forced to interact with a Drift spot market whose mint has zero-transfer-reverting behavior, or simply calling the harvest instruction a second time after the position is already drained (a very plausible operational sequence, since nothing prevents repeated calls). Given the instruction appears to lack a signer restriction and can be invoked by anyone, the "harvest again with dust/zero balance" trigger is easily reachable even without an adversarial token.

### Recommendation
Guard the transfer with a zero-amount check, matching the pattern already used in `claim_bad_debt.rs`:
```rust
let amount = accessor::amount(&self.intermediary_token_account.to_account_info())?;
if amount == 0 {
    return Ok(());
}
transfer_checked(cpi_ctx, amount, decimals)?;
```
Also consider explicitly requiring a signer with admin authority for `drift_harvest_reward`, and validating `reward_mint` does not carry unsupported/blocking Token-2022 extensions before allowing it to be configured for harvesting.

### Proof of Concept
1. Admin configures a Drift spot market with `reward_mint` = a Token-2022 mint with a transfer-hook extension that reverts on `amount == 0` transfers.
2. Admin (or any caller, since no signer is enforced) calls `drift_harvest_reward` once — this succeeds, draining the admin-deposit position and transferring the harvested balance to `destination_token_account`.
3. Any caller invokes `drift_harvest_reward` again for the same spot market before new rewards accrue: `cpi_withdraw_from_position` withdraws ~0 tokens, then `cpi_transfer_to_destination` computes `amount = 0` and calls `transfer_checked(cpi_ctx, 0, decimals)`, which reverts due to the mint's transfer-hook logic.
4. Because nothing resets or bypasses this state, every subsequent call to `drift_harvest_reward` for this spot market fails identically, permanently blocking reward harvesting for that token — mirroring the `stashRewards()` DoS in the referenced report.
