Based on my investigation, the strongest analog I found is in the LDAP authentication provider, where deactivation checks are enforced in some auth paths (session creation, user sync) but not in the per-request session-authorization path.

### Title
Deactivated LDAP users retain full session/API-token access because `AuthorizedUserWithSession` never re-checks the upstream `ActiveAttribute` - ([File: core/sessions/ldapauth/ldap.go])

### Summary
The LDAP authenticator enforces the upstream "active" flag (`ActiveAttribute`) only at session-creation time (`FindUser`/`CreateSession`) and during the periodic background sync (`LDAPServerStateSyncer.Work` / `validateUsersActive`), but the hot path used on every authenticated request, `AuthorizedUserWithSession`, does not check user-active status at all — it just reads the cached `ldap_sessions` row and returns the cached role if it hasn't expired.

### Finding Description
`FindUser` calls `validateUsersActive` to filter out deactivated LDAP users before granting a role [1](#0-0) , and the same active-attribute filtering is applied by the background reaper/syncer job in `sync.go` [2](#0-1) , which is expected to purge stale sessions/tokens for users who have since been deactivated upstream.

However, `AuthorizedUserWithSession` — the function invoked by `AuthenticateBySession` on essentially every authenticated node-API request — only reads the cached `ldap_sessions` table by session ID and checks expiry; it performs no upstream LDAP query and no active-attribute check: [3](#0-2) . It is wired directly into the web authentication middleware: [4](#0-3) .

This mirrors the referenced bug class exactly: the "deactivation" check (isOracleActive / user-active) is enforced on the primary creation/mint path but is skipped on a parallel, economically/functionally equivalent path (spread minting / authenticated per-request session use). Here, once a user is deactivated in the upstream LDAP directory, their already-issued session ID continues to authenticate every request with full role privileges until either the session naturally expires (`SessionTimeout`) or the separate background `LDAPServerStateSyncer` job runs and happens to purge the row.

### Impact Explanation
A node operator who revokes/deactivates a user in the upstream LDAP directory (e.g., because of termination or compromise) does not immediately lose access on this Chainlink node: any session ID issued before deactivation keeps working with the user's original role (potentially Admin) for the full session lifetime, or until the next background sync cycle. This is a genuine authorization-bypass window controlled entirely by config-defined sync interval and session timeout, not by actual deactivation.

### Likelihood Explanation
This is reachable by any legitimate former/deactivated user who retained a valid session cookie before their upstream deactivation — no special privilege is required beyond having authenticated previously. It requires only that LDAP auth is enabled with `ActiveAttribute` configured and that the operator does not otherwise revoke sessions manually. The syncer's periodicity (config-controlled) determines exposure duration, so likelihood is moderate-to-high in any operational deployment relying on the active-attribute mechanism to enforce timely deactivation.

### Recommendation
Make `AuthorizedUserWithSession` consistent with `FindUser`: either (a) re-validate the cached user's active status against the upstream LDAP `ActiveAttribute` on every session lookup (with reasonable caching/rate limiting), or (b) have the syncer's session/token purge run synchronously/inline for the specific `sessionID` being authorized rather than solely on a fixed background interval, so deactivation takes effect immediately rather than being bounded only by session TTL and the reaper's polling cadence.

### Proof of Concept
1. Configure LDAP auth with `ActiveAttribute` set (e.g., `organizationalStatus`).
2. Authenticate as an LDAP user via `CreateSession`, which succeeds because `FindUser`/`validateUsersActive` confirms the user is active, producing a valid `ldap_sessions` row: [5](#0-4) .
3. Deactivate the user in the upstream LDAP directory (flip the active attribute value).
4. Before the next `LDAPServerStateSyncer.Work` cycle runs (interval is operator-configured), continue issuing authenticated API requests using the existing session cookie.
5. `AuthenticateBySession` → `AuthorizedUserWithSession` succeeds because it only checks `created_at + SessionTimeout >= now()` against the cached `ldap_sessions` row, with no LDAP re-query, granting the (stale) cached role for every request during that window: [6](#0-5) .

Note: I was not able to fully verify whether `reaper.go`'s sync is ever triggered synchronously on a per-request basis (the doc comment at the top of `ldap.go` claims "This sync happens for every auth endpoint hit", but the code of `AuthorizedUserWithSession` I reviewed does not call any sync/validate-active function). If such per-request triggering exists elsewhere and calls into the syncer, it would mitigate this finding; I could not locate that wiring within the given tool-call budget and recommend confirming this in `core/sessions/ldapauth/reaper.go` before treating this as conclusively unmitigated.

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field. The state of the upstream LDAP server
// is polled and synced at the defined interval via a SleeperTask
func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

func (l *ldapAuthenticator) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	conn, err := l.ldapClient.CreateEphemeralConnection()
	if err != nil {
		return "", errors.New("unable to establish connection to LDAP server with provided URL and credentials")
	}
	defer conn.Close()

	var returnErr error

	// Attempt to LDAP Bind with user provided credentials
	escapedEmail := ldap.EscapeFilter(strings.ToLower(sr.Email))
	searchBaseDN := fmt.Sprintf("%s=%s,%s,%s", l.config.BaseUserAttr(), escapedEmail, l.config.UsersDN(), l.config.BaseDN())
	if err = conn.Bind(searchBaseDN, sr.Password); err != nil {
		l.lggr.Infof("Error binding user authentication request in LDAP Bind: %v", err)
		returnErr = errors.New("unable to log in with LDAP server. Check credentials")
	}

	// Bind was successful meaning user and credentials are present in LDAP directory
	// Reuse FindUser functionality to fetch user roles used to create ldap_session entry
	// with cached user email and role
	foundUser, err := l.FindUser(ctx, escapedEmail)
	if err != nil {
		l.lggr.Infof("Successful user login, but error querying for user groups: user: %s, error %v", escapedEmail, err)
		returnErr = errors.New("log in successful, but no assigned groups to assume role")
	}

	isLocalUser := false
	if returnErr != nil {
		// Unable to log in against LDAP server, attempt fallback local auth with credentials, case of local CLI Admin account
		// Successful local user sessions can not be managed by the upstream server and have expiration handled by the reaper sync module
		foundUser, returnErr = l.localLoginFallback(ctx, sr)
		isLocalUser = true
	}

	// If err is still populated, return
	if returnErr != nil {
		return "", returnErr
	}

	l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)

	// Save session, user, and role to database. Given a session ID for future queries, the LDAP server will not be queried
	// Sessions are set to expire after the duration + creation date elapsed, and are synced on an interval against the upstream
	// LDAP server
	session := sessions.NewSession()
	_, err = l.ds.ExecContext(
		ctx,
		"INSERT INTO ldap_sessions (id, user_email, user_role, localauth_user, created_at) VALUES ($1, $2, $3, $4, now())",
		session.ID,
		strings.ToLower(sr.Email),
		foundUser.Role,
		isLocalUser,
	)
	if err != nil {
		l.lggr.Errorf("unable to create new session in ldap_sessions table %v", err)
		return "", fmt.Errorf("error creating local LDAP session: %w", err)
	}

	l.auditLogger.Audit(audit.AuthLoginSuccessNo2FA, map[string]any{"email": sr.Email})

	return session.ID, nil
}

func (l *ldapAuthenticator) validateUsersActive(emails []string) ([]bool, error) {
	validUsers := make([]bool, len(emails))
	// If active attribute to check is not defined in config, skip
	if l.config.ActiveAttribute() == "" {
		// fill with valids
		for i := range emails {
			validUsers[i] = true
		}
		return validUsers, nil
	}

// AuthenticateBySession authenticates the request by the session cookie.
//
// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
