### Title
Missing slippage control on ERC4626 vault deposits lets an unprivileged vault user inflate the share price and steal or socialize ProgrammableBorrower deposits - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower._depositToVault` calls `vault.deposit(_assetAmount, address(this))` and trusts the returned share count with no minimum-shares check [1](#0-0) . It is invoked on two externally triggerable paths: `onStartEpoch` parking the entire idle balance when a new epoch starts [2](#0-1) , and `_repay` redeploying every borrower repayment while an epoch is active [3](#0-2) . An unprivileged user of the same ERC4626 vault (an allowed actor class) can sandwich these calls with a direct-asset donation/share-inflation, so the borrower contract mints far fewer shares than the assets it paid in.

### Finding Description
ERC4626 `deposit` only guarantees the caller pays `_assetAmount`; the shares returned depend on the vault's live `totalAssets()`, which a donation inflates between mempool observation and execution. The borrower's accounting then records the full asset amount as principal (`epochDepositedToVault += _principalAssets`, line 382) while `_currentVaultAssets()` (line 546-549) reflects only the deflated share position. `_vaultNetInterest` turns that gap into a `loss` [4](#0-3) , which reduces `totalInterestDueNow()` read by `IdleCDOEpochVariant` at `stopEpoch` [5](#0-4) , directly lowering the interest minted/paid to tranche holders.

Two exploitation shapes:

1. **Empty/small vault first-depositor inflation**: if the configured vault has a small or zero supply when the facility is initialized or when all shares were redeemed during a buffer (via `emergencyExitVault`/`onStopEpoch` leaving shares = 0), the attacker mints 1 share, donates `D` underlying, and the borrower's next deposit of `A` mints `A / (D+1)` shares, possibly rounding to 0. The deposit is captured inside the vault and recovered by the attacker's redeem.
2. **Whale vault shareholder sandwich**: the attacker holds a large fraction of vault shares, frontruns `repay`/`onStartEpoch` with a donation, and redeems after the victim deposit. Profit = attacker share fraction × victim's lost value.

Neither path is stopped by existing guards: `nonReentrant` does not help (separate transactions), `borrow()`/`repay()` require only the borrower but `onStartEpoch`/`_repay`'s deposit executes regardless, and the `shortfall > _currentVaultAssets()` check in `onStopEpoch` (line 245) only covers the withdraw side, which pays out exact assets. There is no skim mechanism isolating donations because they land inside the external vault, not the borrower contract.

### Impact Explanation
Direct theft and loss socialization. In shape 1, nearly 100% of an epoch-start deposit or borrower repayment can be captured by the attacker once they redeem their vault shares — the pool records a `vaultLoss` equal to the deposit, wiping out epoch interest and eroding `epochStartVaultAssets`-denominated principal value that tranche holders price at `virtualPrice`. In shape 2, attacker profit is bounded by their vault ownership share but the pool still books a real loss that is socialized across AA/BB tranches via `totalInterestDueNow()`. Quantification example: borrower repays 1M USDC into a vault the attacker just made hold 1 share / 10M donated USDC → borrower mints ~0.1 share worth ~100k → ~900k booked as vault loss and largely recovered by the attacker.

### Likelihood Explanation
The attack requires no privilege: the attacker is simply a depositor in the same ERC4626 vault, and donation-based price manipulation costs the attacker only transient capital (recoverable via their shares). The trigger transactions (`IdleCDOEpochVariant.startEpoch` → `onStartEpoch`, and `borrower.repay` → `_depositToVault`) are publicly observable in the mempool, so timing is a standard sandwich. Shape 1 additionally needs a near-empty vault, which is reachable after `emergencyExitVault` redeems all shares or at first deployment. Cost is roughly the donation size in shape 1; in shape 2 it scales with required vault share ownership. This mirrors exactly the bug class fixed upstream in the referenced router (add `minShares`/`maxAssets` slippage params), which the report notes is hard to express in the ERC4626 signature — but here the caller (`ProgrammableBorrower`) can enforce a min-shares invariant internally since both caller and receiver are itself.

### Recommendation
Track vault assets by balance delta instead of trusting share conversion, and/or enforce a minimum acceptable share output:

```solidity
function _depositToVault(uint256 _assetAmount, uint256 _principalAssets) internal {
  if (_assetAmount == 0) return;
  uint256 sharesBefore = vault.balanceOf(address(this));
  vault.deposit(_assetAmount, address(this));
  uint256 shares = vault.balanceOf(address(this)) - sharesBefore;
  // revert if shares imply a price worse than the pre-call convertToShares quote
  if (shares < vault.convertToShares(_assetAmount) * MAX_SLIPPAGE_BPS / BPS) revert Slippage();
  ...
}
```

Since the caller is also the receiver, a cleaner fix is to compute expected shares via `previewDeposit(_assetAmount)` immediately before `deposit` and revert if the realized share delta deviates beyond a tolerance, neutralizing same-tx donation inflation. Apply the same check to `emergencyExitVault`/`onStopEpoch`/`_borrow` withdrawals via expected-asset deltas if the vault's withdraw semantics can ever return fewer assets.

### Proof of Concept
Foundry fork PoC (requires mainnet ERC4626 vault, e.g. a Yearn/Aave vault in the same asset):

```solidity
function test_depositSandwich() public {
  // Setup: epoch active, borrower owes 1_000_000 USDC, vault V with honest liquidity
  // Attacker (unprivileged vault user):
  uint256 attackerDeposit = 10_000_000e6;
  vm.startPrank(attacker);
  usdc.approve(address(vault), type(uint256).max);
  uint256 aShares = vault.deposit(attackerDeposit, attacker);   // own shares first
  usdc.transfer(address(vault), 50_000_000e6);                  // donation inflation
  vm.stopPrank();

  // Honest flow: borrower repays 1M USDC -> _repay -> _depositToVault
  vm.prank(borrower);
  borrowerContract.repay(1_000_000e6);

  // Borrower minted ~ dust shares; recorded epochDepositedToVault += ~1M
  uint256 bAssets = vault.convertToAssets(vault.balanceOf(address(borrowerContract)));
  assertLt(bAssets, 20_000e6);                                  // lost >98%
  assertGt(borrowerContract.vaultLoss(), 900_000e6);            // pool books the loss

  // Attacker redeems: shares now worth attackerDeposit + donation + victim's loss
  vm.prank(attacker);
  uint256 out = vault.redeem(aShares, attacker, attacker);
  assertGt(out, attackerDeposit + 50_000_000e6 + 900_000e6);    // attacker profits ~victim's deposit
}
```

The same sequence applies frontrunning `startEpoch` (`onStartEpoch` → `_depositToVault(balance, 0)`), where the loss lands inside `bufferedVaultDelta`/epoch accounting and is socialized at the next `stopEpoch`.
