### Title
Negative payload timestamp bypasses the gateway's stale-message check via unchecked `int64`→`uint` cast - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` in the Web API capability gateway handler validates message freshness by comparing `time.Now().Unix()` minus a configured max-age against the client-supplied `payload.Timestamp`. The comparison casts both `time.Now().Unix()` and the attacker-controlled `payload.Timestamp` to `uint` without checking for negative values first, exactly mirroring the Derby `int→uint` casting bug class: unvalidated signed values are explicitly converted to unsigned types, and a maliciously chosen negative value silently wraps into a huge number rather than causing a revert/error.

### Finding Description
The check is:
```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    ... return "stale message" error ...
}
``` [1](#0-0) 

`payload.Timestamp` comes directly from `webapicap.TriggerRequestPayload`, which is populated via `json.Unmarshal(body.Payload, &payload)` from a message body that originates from an unauthenticated/unprivileged external caller through the gateway connector (`HandleLegacyUserMessage`) [2](#0-1) . The only prior validation is `payload.Timestamp == 0` [3](#0-2)  — negative values are never rejected.

Because `payload.Timestamp` is a signed integer field decoded from attacker-supplied JSON, a caller can set it to a negative number. `uint(payload.Timestamp)` then wraps to a value close to `math.MaxUint64`, making the right-hand side of the comparison enormous. The left-hand side (`uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec`) is comparatively tiny, so the "stale message" branch is never taken — the negative-timestamp message is treated as fresh and processed normally, defeating the intended anti-replay/staleness guard.

This is the same root-cause pattern as the Derby report: a signed delta/timestamp value that can legitimately be negative is explicitly cast to an unsigned type without a preceding sign check, and instead of failing safe, the check silently passes with a corrupted (wrapped) value.

Elsewhere in the codebase, this exact bug class is proactively guarded against — e.g. `Uint64Param.UnmarshalPipelineParam` and `MaybeUint64Param.UnmarshalPipelineParam` explicitly reject negative inputs before casting [4](#0-3) , and `utils.NonNegativeInt64ToUint64` / `safe.IntToUint64` are dedicated safe-cast helpers [5](#0-4) [6](#0-5) . The staleness check in the gateway capabilities handler does not use any of these safe conversions.

### Impact Explanation
The staleness check is the only anti-replay/freshness control on this internet-facing handler path (the code comment even notes `// TODO: apply allowlist and rate-limiting here` immediately after it, indicating no other authorization control is applied at this stage) [7](#0-6) . An unprivileged external caller can bypass this control entirely by supplying a negative `Timestamp`, allowing replay of arbitrarily old/stale messages or crafted requests that should have been rejected as stale, which are then forwarded to all DON nodes to trigger a workflow (`req` is broadcast via `don.SendToNode`) [8](#0-7) . This is analogous to an "unauthorized job run" via bypass of a request-freshness guard.

### Likelihood Explanation
High: the field is fully attacker-controlled JSON input reachable by any unauthenticated user hitting the gateway's Web API trigger endpoint, requiring only setting a single JSON field to a negative number. No other precondition is needed since the only prior check is `Timestamp == 0`.

### Recommendation
Reject negative `payload.Timestamp` values explicitly before performing any unsigned comparisons (e.g., `if payload.Timestamp < 0 { return staleMessage/parseError }`), or perform the freshness check entirely in signed 64-bit arithmetic (`time.Now().Unix() - int64(h.config.MaxAllowedMessageAgeSec) > payload.Timestamp`) instead of casting to `uint`. Consider reusing the existing safe-conversion helpers (`utils.NonNegativeInt64ToUint64`, `safe.IntToUint64`) that already validate sign before conversion.

### Proof of Concept
1. Craft a `web_api_trigger` message body with `payload.Timestamp = -1` (or any negative int64) and send it to the gateway as an unauthenticated external client.
2. `HandleLegacyUserMessage` passes the `Timestamp == 0` check (since `-1 != 0`) [3](#0-2) .
3. `uint(payload.Timestamp)` evaluates to `18446744073709551615` (wrap of `-1`), so `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` is false, and the "stale message" branch is skipped [9](#0-8) .
4. The message is forwarded unchanged to `common.ValidatedRequestFromMessage` and broadcast to all DON members, bypassing the intended freshness/replay control [10](#0-9) .

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {

				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}
