## Analog Found

The reported bug class — a status that is recorded/derived at one point in time by one code path but consumed later by a different check without re-validating it against current authoritative state — has a direct analog in the multisig contract's confirmation-vs-membership accounting.

### Title
Stale confirmations from removed members count toward the K-of-N threshold, allowing a multisig request to execute below the required live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`confirm()` counts confirmations recorded in the `confirmations` set for a request and executes it once the count reaches `num_confirmations`, but `delete_member()` never purges a removed member's confirmations from requests they previously confirmed but did not author. This lets an already-cast confirmation from an account that is no longer a multisig member still count toward the threshold, so a request can execute with fewer live-member confirmations than `num_confirmations` requires.

### Finding Description
`confirm()` stores each confirming member's identity in a `HashSet<String>` keyed by `request_id` and executes the request once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

When a member is removed via `DeleteMember`, `delete_member()` only deletes *requests originated by that member* (`r.member == member`) and the member's own `num_requests_pk` entry — it does not scan `self.confirmations` for entries where the deleted member had confirmed a request *authored by someone else*: [2](#0-1) 

Because `remove_request()`/`delete_member()` clean up only by request ownership, not by confirmer identity, a confirmation cast by member A remains stored against a pending request even after A is removed from `self.members`. `confirm()` has no step that re-checks whether each address already present in the `confirmations` set is still a current member — it only checks the new caller's membership via `assert_valid_request`/`current_member()`: [3](#0-2) 

This is the same class of defect as the Monad report: one code path (`confirm`) derives/consumes a piece of authorization state ("this address's approval counts") at the time it was recorded, while another path (`delete_member`) mutates the authoritative set (`members`) without reconciling previously-derived state — producing an ordering-dependent mismatch between "confirmations counted" and "live members".

### Impact Explanation
This breaks the core custody binding of the multisig: `confirmations from currently valid members >= num_confirmations` before any request executes. An attacker (or a member later removed, e.g., a compromised/rotated key) can get a high-value request (e.g., `Transfer`) partially confirmed, wait for that confirming member to be removed through a legitimate `DeleteMember` request, and then have one remaining live member supply the final confirmation — causing the request to execute with only 1 live confirmation where `num_confirmations` (e.g., 2) was required. This is a "multisig request executed below threshold" — a Critical-impact custody-binding violation (funds moved, keys added, or contract deployed with fewer authorizations than the configured K-of-N policy).

### Likelihood Explanation
No privileged actor or redeploy is required — only a normal sequence of contract calls achievable by an existing/former member and any other member acting legitimately: (1) request created and partially confirmed, (2) unrelated legitimate `DeleteMember` request executed removing the confirming member, (3) remaining member(s) supply the last confirmation. Any multisig instance where membership changes over time while a partially-confirmed pending request exists is exposed; the sequence requires no timing race with block proposers, unlike the original report — this variant is strictly easier to trigger.

### Recommendation
When a member is removed in `delete_member()`, scrub that member's identity from every entry in `self.confirmations`, not just requests they authored. Alternatively, re-validate at execution time in `confirm()` that every identity present in the request's confirmation set is still a current member of `self.members`, discounting stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `MultiSigContract::new(members: [A, B, C], num_confirmations: 2)`.
2. `B` calls `add_request(R1)` where `R1` is `Transfer { amount }` to an attacker-controlled `receiver_id` (member of `R1` = `B`, `confirmations[R1] = {}`).
3. `A` calls `confirm(R1)` → `confirmations[R1].len() (0) + 1 < 2` → stores `confirmations[R1] = {A}`, does not execute (`multisig2/src/lib.rs` lines 299-314).
4. Separately, a legitimate request `R2 = DeleteMember{A}` is added and confirmed to completion by `B` and `C`, executing `delete_member(A)`. Because `R1.member == B`, not `A`, the cleanup loop at `multisig2/src/lib.rs` lines 362-371 does not touch `R1` or its confirmations; `A` is removed from `self.members` while `confirmations[R1] = {A}` remains.
5. `C` calls `confirm(R1)` → `confirmations[R1].len() (1) + 1 >= 2` → `remove_request` + `execute_request` runs the `Transfer`, even though only `C` (one live member) actually approved it post-removal of `A`. [4](#0-3) [5](#0-4)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
