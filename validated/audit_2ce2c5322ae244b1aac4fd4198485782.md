### Title
Stale confirmations from a removed multisig member still count toward `num_confirmations`, allowing execution below the live-member threshold - (File: multisig2/src/lib.rs / multisig/src/lib.rs)

### Summary
The Curve-DAO-style bug (removing a gauge without purging the per-user record referencing it) has a direct analog in the multisig contracts: when a member is removed via `DeleteMember` (multisig2) or a key via `DeleteKey` (multisig), the contract only purges **requests that the removed member/key created**, but not **confirmations that the removed member/key placed on other members' requests**. Those stale confirmations remain in the `confirmations` set/map and continue to count toward `num_confirmations` when later, still-valid members confirm the same request, letting a request execute with fewer *live* members' assent than the configured threshold.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` only removes requests keyed by the member being deleted: [1](#0-0) 

```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
```

`r.member` refers to `MultiSigRequestWithSigner.member` — the account/key that **added** the request via `add_request` [2](#0-1) 
— not the set of accounts/keys that have **confirmed** it. Confirmations are tracked separately, per request, in `self.confirmations: LookupMap<RequestId, HashSet<String>>` [3](#0-2) 
and are populated in `confirm()`: [4](#0-3) 

```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member()...;
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), "Already confirmed...");
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
```

The threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` simply counts entries in the `HashSet<String>`, with no re-validation that every previously recorded confirmer is still a current member of `self.members`. If member B confirms request R created by member A (leaving R at 1/`num_confirmations`), and B is subsequently removed from the multisig via a separate `DeleteMember` request (which only purges requests *created* by B, not R, since R was created by A), B's confirmation string remains inside `self.confirmations[R]`. Later confirmations by still-current members C, D, ... will be summed together with B's stale entry to reach `num_confirmations`, and `execute_request(R)` will run even though the number of genuinely current, still-authorized members who approved R is one less than `num_confirmations`.

The same pattern exists in the legacy `multisig/src/lib.rs`'s `DeleteKey` action, which purges requests whose `signer_pk == pk` (i.e., requests added by that key) but leaves that key's confirmation entries on requests added by other keys untouched: [5](#0-4) 

This breaks the intended equality: `count(confirmations recorded for request R) == count(live members who approved R)`. After a member/key removal, the left side can remain larger than the right side, so a request can be executed with fewer live approvals than `num_confirmations` mandates.

### Impact Explanation
This maps to the "Critical" category explicitly listed in scope: *a multisig request executed below threshold*. A multisig account typically custodies NEAR funds and controls privileged operations (transfers, deploying contracts, adding/removing keys). If a stale confirmation from a removed member allows a request to execute with one fewer live approver than configured, an attacker (or a set of colluding members below the intended threshold) can move funds or execute privileged actions (`Transfer`, `FunctionCall`, `AddKey`, further `DeleteMember`/`AddMember` actions) without the number of currently-authorized signers the account owner configured and trusted. This directly undermines the "K-out-of-N" security guarantee the multisig is designed to provide.

### Likelihood Explanation
This requires: (1) a request created by member A receiving a partial confirmation from member B (a normal operational flow — pending multi-step approvals are common while gathering signatures), and (2) a later, unrelated `DeleteMember`/`DeleteKey` action removing B (a routine key-rotation/membership-change operation, not a malicious act by governance). Both are ordinary operations that legitimate multisig owners perform. No collusion by the removed member is required — the "attacker" benefiting from the stale confirmation could simply be one of the remaining valid signers who is unaware their action combined with a stale entry crosses the threshold, or could be exploited deliberately by timing a member removal after obtaining an early confirmation. Likelihood is Medium-to-High given the naturalness of the sequence (partial confirmation → later member removal → additional confirmations reaching the stale-inflated count).

### Recommendation
When confirming a request, re-validate that every entry already present in `confirmations` for that `request_id` still belongs to `self.members` before counting it toward `num_confirmations` (e.g., filter stale entries out, or recompute `confirmations.len()` using only current members). Alternatively, when `DeleteMember`/`DeleteKey` executes, iterate over *all* `self.confirmations` entries (not only requests created by the removed member) and strip the removed member's string from every confirmation set, decrementing effective counts accordingly. The cleanest fix mirrors the report's own recommendation for GaugeController: fully purge all traces of a removed principal (here, a removed multisig member) from every piece of state that references it, not only the state keyed directly by that principal.

### Proof of Concept
Conceptual sequence (mirrors the original report's Alice/G1 scenario, translated to multisig2):
1. Multisig deployed with `num_confirmations = 3` and members `{A, B, C, D}` (4 members).
2. `A` calls `add_request` for a `Transfer` to some receiver → `request_id = 0`, `confirmations[0] = {}`.
3. `B` calls `confirm(0)` → `confirmations[0] = {B}` (1/3, request pending).
4. Members execute a separate, legitimate `DeleteMember { member: B }` request (requires `members.len() - 1 >= num_confirmations`, i.e., `4 - 1 = 3 >= 3`, allowed) — `delete_member` only purges requests where `r.member == B` (i.e., requests B *added*), so request `0` (added by A) is untouched, and `confirmations[0]` still contains `B`.
5. `C` calls `confirm(0)` → `confirmations[0].len() + 1 = 2 + 1 = 3 >= num_confirmations(3)` → `execute_request` fires and the transfer executes.
6. Result: the transfer executed with confirmations counted as 3 (`B`(stale) + `C` + the implicit final confirmer), but only `A`(creator, uncounted toward the confirm count in this flow) plus `C` are current, live members who explicitly confirmed — `B`'s stale approval let the request cross the threshold one confirmation early, i.e., the request executed with fewer live-member approvals than the account owner configured.     /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
