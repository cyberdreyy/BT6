## Title
Builder withdrawal commits an execution-layer payment larger than the actual balance deducted (Gwei paid ≠ Gwei deducted) - (File: `specs/gloas/beacon-chain.md`)

### Summary
`get_builder_withdrawals` emits a `Withdrawal` whose `amount` is the *requested* `builder_pending_withdrawals[i].amount`, taken verbatim, without capping it to the builder's actual `balance`. That withdrawal is placed into `state.payload_expected_withdrawals`, which the execution layer is required to honor as a real ETH payment to `withdrawal.fee_recipient`. Only later, in `apply_withdrawals`, is the *state* deduction capped: `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)`. This is structurally identical to the Velar `calc_fees` bug: one side of the ledger (what is paid out / committed) is not capped by available funds, while the other side (what is deducted from the payer) is capped — breaking the invariant `sum(amount_paid) == sum(amount_deducted)`.

### Finding Description
`get_builder_withdrawals` builds the committed withdrawal list directly from the requested amount with no balance check: [1](#0-0) 

`apply_withdrawals`, executed afterward, deducts only `min(withdrawal.amount, builder_balance)` from the builder's balance: [2](#0-1) 

So if `builder_pending_withdrawals[i].amount` (5 ETH, say) exceeds `state.builders[builder_index].balance` (1 ETH), the emitted `Withdrawal.amount` committed to the execution payload is still 5 ETH — the full requested amount — while only 1 ETH is actually removed from the builder's consensus-layer balance. The execution layer is bound to pay out the full 5 ETH to the fee recipient (per the withdrawal-processing note: "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals"), even though only 1 ETH was ever backed by the builder's balance. The remaining 4 ETH paid to the recipient corresponds to no debited Gwei anywhere in the beacon state — Gwei is created out of thin air and paid to the fee recipient.

This is confirmed as intended/tested behavior in the test suite, which explicitly documents the mismatch: [3](#0-2) 
and the corresponding assertion helper, which checks the balance is capped while the committed withdrawal amount is not: [4](#0-3) 

This mirrors the Velar `M-7` bug class exactly: `funding_paid` (deduction) is capped/limited by available collateral while `funding_received` (the payout side) is computed from a different, uncapped source, so `sum(paid) != sum(received)`. Here, the deduction (`builder.balance` decrease) is capped by `min()`, while the payout commitment (`Withdrawal.amount` sent to EL) is uncapped, so `sum(amount committed to EL) != sum(amount actually deducted from builder balances)`.

### Impact Explanation
This breaks the core equality that a `Withdrawal` amount recorded in `payload_expected_withdrawals` must equal the Gwei actually removed from the payer's balance — i.e., "a Gwei... paid to a non-owner" / "a payload or payment applied that the block did not commit to" in reverse: the block commits to a payment that exceeds what state removed. Since `process_withdrawals`/`apply_withdrawals` are consensus-critical and the execution layer must honor `payload_expected_withdrawals` verbatim (enforced via block validity, matching `withdrawals_root`), every node that reaches this state deterministically computes the same over-committed `Withdrawal.amount`, so this is not merely a local accounting bug — it is baked into the canonical state transition and will be replicated by all conforming nodes, resulting in ETH manufactured and paid to the builder's fee recipient beyond what was ever backed by builder collateral.

### Likelihood Explanation
This requires only a `builder_pending_withdrawals` entry whose requested `amount` exceeds the current `builders[index].balance` at processing time. Builder balance can decrease between the withdrawal request being queued and being processed (e.g. via slashing-adjacent penalty logic, other withdrawal processing, or bid payments being applied before this queue entry is serviced), so this is reachable through ordinary protocol operation, not merely adversarial or high-stake behavior.

### Recommendation
Cap the committed `Withdrawal.amount` in `get_builder_withdrawals` to the builder's actual balance at computation time — i.e., replace `amount=withdrawal.amount` with `amount=min(withdrawal.amount, state.builders[builder_index].balance)` (accounting for prior withdrawals against the same builder within the same block, similar to how `get_pending_partial_withdrawals` computes `get_balance_after_withdrawals`) — so the amount promised to the execution layer never exceeds what `apply_withdrawals` will actually deduct.

### Proof of Concept
1. Register builder `B` with `balance = 1 ETH`.
2. Enqueue `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=B, amount=5 ETH, fee_recipient=R)]`.
3. Call `get_expected_withdrawals(state)` → `get_builder_withdrawals` emits `Withdrawal(validator_index=convert(B), address=R, amount=5 ETH)` (per `specs/gloas/beacon-chain.md:1822-1829`, unconditional copy of `withdrawal.amount`).
4. This `Withdrawal` is placed in `state.payload_expected_withdrawals`, which the execution payload's `withdrawals` field/`withdrawals_root` must match, so the EL pays `R` 5 ETH.
5. `apply_withdrawals` runs: `state.builders[B].balance -= min(5 ETH, 1 ETH)` → balance becomes `0`, only 1 ETH deducted (per `specs/gloas/beacon-chain.md:1928-1929`).
6. Net effect: 5 ETH paid out on the execution layer, only 1 ETH removed from consensus state — 4 ETH created and paid to `R` with no corresponding debit anywhere, exactly matching the test's documented behavior in `test_builder_withdrawal_insufficient_balance` (`withdrawal.amount: 5 ETH (requested amount)`, `builders[0].balance: 0 (deduction capped to available balance)`).
