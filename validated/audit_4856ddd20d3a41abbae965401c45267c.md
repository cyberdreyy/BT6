### Title
External Initiator credentials satisfy the `isUser` check and can trigger arbitrary job runs via int32 job ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the int32-job-ID run path behind `isUser := auth.GetAuthenticatedUser(c)`, intending (per the code comment) to restrict this path to real users and exclude External Initiators (EIs). However, `AuthenticateExternalInitiator` explicitly sets `SessionUserKey` to a `*clsessions.User{Role: clsessions.UserRoleRun}`, so `GetAuthenticatedUser` returns `ok == true` for EI-authenticated requests as well, defeating the intended restriction.

### Finding Description
`PipelineRunsController.Create` first rejects UUID-formatted IDs (webhook jobs, since removed), then checks:

```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [1](#0-0) 

`GetAuthenticatedUser` merely checks for the presence of `SessionUserKey` in the gin context and type-asserts it to `*clsessions.User`: [2](#0-1) 

But `AuthenticateExternalInitiator`, the auth method used for EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers), sets exactly this key:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [3](#0-2) 

Since the runs routes are wired with `auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession, AuthenticateExternalInitiator)` and wrapped by `RequiresRunRole` (which only rejects `UserRoleView`, not `UserRoleRun`), an EI credential holder passes authentication, is granted a synthetic `User` with `Role: UserRoleRun`, and `isUser` evaluates to `true` in `Create`. The int32 branch therefore executes for EI-authenticated requests, directly contradicting the comment "EIs not allowed" and invoking `prc.App.RunJobV2(ctx, jobID, nil)` for any job ID the attacker supplies — not just jobs associated with that EI.

### Impact Explanation
An attacker holding only a valid EI access key/secret (not a user session or user API token) can trigger arbitrary job runs by numeric job ID for any job on the node, bypassing the intended restriction that EIs may only invoke jobs via their own webhook mechanism. This is an authorization/request-attribution bypass leading to unauthorized job execution, which can cause unintended on-chain transactions, unauthorized fund movement (for jobs that submit transactions), or resource exhaustion/DoS via repeated triggering of unrelated jobs.

### Likelihood Explanation
Preconditions are minimal: possession of any valid EI access key/secret pair registered on the node (a low-privilege credential by design, intended only to trigger a specific webhook job). No user session, no API token, no admin/edit role is required. The attack is a single unauthenticated-relative-to-user-role HTTP POST and is fully repeatable for any job ID.

### Recommendation
In `PipelineRunsController.Create`, distinguish real users from EI-derived pseudo-users. Do not rely solely on `GetAuthenticatedUser`; instead check `auth.GetAuthenticatedExternalInitiator(c)` and explicitly reject if an EI context is present, or use a dedicated boolean/flag set only by `AuthenticateBySession`/`AuthenticateByToken` (not by `AuthenticateExternalInitiator`) to gate the int32-ID run path.

### Proof of Concept
Handler-level integration test:
1. Set up a test app with an EI registered (access key/secret).
2. Create a job with an int32 ID (non-webhook), owned/created independent of the EI.
3. Send `POST /v2/jobs/<int32 ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no `X-API-KEY`).
4. Assert the response is `200 OK` with a pipeline run resource (i.e., `RunJobV2` was invoked) — demonstrating the "EIs not allowed" comment is not enforced.
5. Contrast with expected behavior: assert instead that the request should return `422 Unprocessable Entity` ("bad job ID") for EI-authenticated callers on non-UUID IDs.
