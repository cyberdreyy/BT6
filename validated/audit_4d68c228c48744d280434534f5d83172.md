### Title
Stale duplicate-tenure-change check in the v1 signer path allows a signer to sign two conflicting tenure-start blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The v1 (legacy/local-state) signer path's tenure-change duplicate check only looks for a **globally accepted** block already in the tenure, unlike the v2 path, which correctly also counts blocks the signer has itself already **signed** (locally accepted) but that have not yet reached global acceptance. This narrows the scope of an authorization/equality check exactly the way the Moodle CVE narrowed a capability check (a control meant to apply broadly was scoped to a subset of the relevant states), letting a competing tenure-start proposal bypass the "already signed one block in this tenure" guard at proposal time.

### Finding Description
`SortitionsView::validate_tenure_change_payload` in the v1 path performs the tenure-change duplicate-block check using only `get_last_globally_accepted_block`: [1](#0-0) 

This function only returns a hit if the block in this tenure has reached `GloballyAccepted` state; it misses blocks this very signer has already put a signature on (`LocallyAccepted`/`PreCommitted`, i.e. `mark_locally_accepted`) but that have not yet crossed the network-wide global-acceptance threshold.

The v2 path fixes exactly this gap by using `get_last_signed_block`, which also matches `LocallyAccepted`/`PreCommitted-then-signed` blocks: [2](#0-1) 

The codebase's own regression test for the v2 fix documents this as a previously real defect that is explicitly *not* backported to v1: [3](#0-2) 

and the design doc confirms the asymmetry is intentional-but-unaddressed in v1: [4](#0-3) 

Because `validate_tenure_change_payload`'s `DuplicateBlockFound` rejection only fires at proposal time and is never re-run at validate-ok or at signing time (per the same doc section), a v1 signer that has already signed block A (tenure-start, `LocallyAccepted`, not yet `GloballyAccepted`) will not early-reject a competing tenure-start block B for the same tenure. B is instead submitted to the node for validation and can accumulate pre-commits. The only remaining safety net is the freshness-gated own-tenure conflict check in `handle_block_pre_commit`: [5](#0-4) 

That check is explicitly designed to *stop* blocking once a conflicting signed block becomes stale (`last_endorsed <= freshness_cutoff`) so that a stalled tenure can recover. Once block A's own signature ages past `tenure_last_block_proposal_timeout`/`reorg_attempts_activity_timeout`, that backstop no longer treats A as blocking, and the same signer can then sign B — producing two signer signatures over two different, conflicting tenure-start blocks for the same tenure from a single signer. This breaks the "one signed tenure-start block per tenure per signer" equality that `validate_tenure_change_payload`'s `DuplicateBlockFound` check exists to enforce, and which v2 explicitly patched.

### Impact Explanation
A single one-slot miner, by delaying/re-proposing a second tenure-start block for the same tenure until the freshness window elapses, can get a v1-mode signer to sign a second, conflicting tenure-start block after it already signed a first one. This is a "signer signing a conflicting block" scenario (Critical category in the rubric): the equality broken is "signed vs. one signature per tenure per signer," and it stems purely from the scope of the in-repo duplicate check, not from any majority compromise, stolen key, or node-side flaw.

### Likelihood Explanation
This requires only: (1) the signer to be operating in the v1 (pre-global-state) protocol path — `check_block_against_state` routes to `check_block_against_local_state`/v1 `SortitionsView::check_proposal` whenever `!state_version.uses_global_state()` [6](#0-5) ; and (2) ordinary miner behavior — proposing a replacement tenure-start block after the first fails to reach full 70% signer-set consensus quickly, which is an expected, not adversarial-only, occurrence, and exactly the scenario the freshness/staleness mechanism is built to tolerate. No majority of signers, stolen keys, or auth token are needed — only the timing already contemplated by the protocol's own recovery design.

### Recommendation
Backport the v2 fix to `stacks-signer/src/chainstate/v1.rs`: replace `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` in `validate_tenure_change_payload` with `signer_db.get_last_signed_block(&block.header.consensus_hash)`, matching v2's semantics so the duplicate-tenure-change guard covers `LocallyAccepted` blocks this signer already committed to, not only `GloballyAccepted` ones.

### Proof of Concept
1. Run a signer in v1 (local-state) mode for a reward cycle.
2. Miner proposes tenure-start block A; the signer set pre-commits and this signer individually reaches `mark_locally_accepted` (signs A), but network-wide global acceptance (70% signatures) is not reached within `tenure_last_block_proposal_timeout`.
3. Miner proposes a different tenure-start block B for the same tenure (same `consensus_hash`, different transactions/timestamp).
4. `SortitionsView::check_proposal` → `validate_tenure_change_payload` calls `get_last_globally_accepted_block`, which returns `None` (A is only `LocallyAccepted`), so B is *not* rejected with `DuplicateBlockFound` at proposal time [1](#0-0) .
5. B is submitted for node validation and accumulates pre-commits; once A's signature ages past the freshness cutoff, the `handle_block_pre_commit` conflict check no longer blocks signing B [5](#0-4) , so the same signer produces a signature for both conflicting blocks A and B in the same tenure.
