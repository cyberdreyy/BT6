### Title
Blacklisted withdrawer can never claim matured withdraw receipts and cannot transfer the address-bound receipt, permanently freezing their underlying - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In `IdleCreditVault`, withdraw receipts are deliberately address-bound: `IdleCreditVault._transfer` reverts unless `msg.sender == idleCDO`, so a user cannot move their strategy-token receipt to another address [1](#0-0) . All claim paths (`claimWithdrawRequest`, `claimInstantWithdrawRequest`, `_claimFundedWithdrawRequest`, `_claimDefaultedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) pay out via `_transferFundedClaim`/`_transferDefaultRecovery`, which call `underlyingToken.safeTransfer(_user, _amount)` to the original requester with no alternative receiver parameter [2](#0-1) . `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest` pass `msg.sender` as `_user` (no `receiver` argument exists). Credit vaults target stablecoin underlyings (e.g., USDC), which implement address blacklists that revert transfers to blacklisted recipients.

### Finding Description
A KYC-passing lender calls `cdoEpoch.requestWithdraw(...)`, which mints an address-bound receipt and records `withdrawsRequests[_user]` / `lastWithdrawRequest[_user]` [3](#0-2) . After the epoch is funded, the claim clears the user's accounting and receipt tokens (`withdrawsRequests[_user] = 0`, `_burn(_user, ...)`) and then pushes underlyings to `_user` [4](#0-3) . If the underlying token (e.g., USDC) blacklists `_user` before they claim, `safeTransfer` reverts, the whole claim reverts, and the user has no recourse: they cannot specify a different receiver, and they cannot transfer the receipt to a clean address because `IdleCreditVault._transfer` only permits moves initiated by the CDO itself [1](#0-0) . The same applies to instant withdraw receipts (`claimInstantWithdrawRequest` → `_transferFundedClaim`) and to all default-recovery claims (`_transferDefaultRecovery`) [5](#0-4) .

### Impact Explanation
Permanent freezing of the blacklisted user's entire matured claim (principal plus interest, or their haircutted default-recovery share). The underlyings remain inside `IdleCreditVault` backing an unclaimable, untransferable receipt. Unlike a normal vault where tokens sit in the user's wallet, here the claim is forfeited: there is no admin rescue path for that user (token `rescue` functions would constitute privileged theft of user funds), and `setCanTransfer` can only ever set the flag to `false`, permanently disabling receipt transfers [6](#0-5) . This is the direct analog of the FixedStrikeOptionTeller bug: a fixed payout recipient blacklisted in a blacklistable payout token leaves funds stuck forever, with the added aggravation that receipt transferability is explicitly disabled by design.

### Likelihood Explanation
Moderate. The preconditions are realistic: credit vaults denominate in blacklistable stablecoins (USDC/USDT-class), and blacklistings happen after deposit but before claim through no action of the victim (sanctions, compliance sweeps). The user is an ordinary unprivileged lender, not a privileged role. No existing guard prevents it — KYC (`isWalletAllowed`) gates entry, not the payout address, and the address-binding of receipts removes the user's only self-help option.

### Recommendation
Allow claim functions to specify a payout `receiver` distinct from the receipt owner (e.g., `claimWithdrawRequest(address _receiver)` in `IdleCDOEpochVariant` forwarded to the vault), so a blacklisted receipt holder can redirect payout to a clean address without needing to transfer the receipt itself. Alternatively, enable a narrowly-scoped receipt transfer path (CDO-initiated only, as today) that lets the holder rebind the claim. Care must be taken that per-epoch mappings (`withdrawsRequestsByEpoch`, `apr0Users`, `lastWithdrawRequest`) move atomically with the receipt.

### Proof of Concept
Foundry fork PoC (against a USDC-like blacklistable underlying; e.g., use the existing blacklistable mock or a forked USDC and `vm.prank(usdcBlacklistAdmin)`):

```solidity
// test/foundry/BlacklistClaim.t.sol — run against the standard epoch variant
function testBlacklistedUserCannotClaimOrMoveReceipt() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address user = makeAddr("user");

    // user deposits (KYC allowed) and requests a normal withdraw
    _depositWithUser(user, amount, true);
    vm.prank(user);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(IERC20(address(strategy)).balanceOf(user), receipt);

    // epoch is funded and stopped, claim becomes mature
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // underlying token (e.g., USDC) blacklists the user
    vm.prank(usdcBlacklistAdmin);
    usdc.addToBlacklist(user); // or MockBlacklistable.setBlacklisted(user, true)

    // claim reverts inside _transferFundedClaim -> safeTransfer(user, ...)
    vm.prank(user);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();

    // receipt cannot be moved to a clean address: _transfer requires msg.sender == idleCDO
    address clean = makeAddr("clean");
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    IERC20(address(strategy)).transfer(clean, receipt);
    vm.prank(user);
    IERC20(address(strategy)).approve(clean, receipt);
    vm.prank(clean);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    IERC20(address(strategy)).transferFrom(user, clean, receipt);

    // manager cannot re-enable transfers either
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    IdleCreditVault(address(strategy)).setCanTransfer(true);

    // funds remain stranded in the vault
    assertEq(IERC20(address(underlying)).balanceOf(address(strategy)) >= receipt, true);
}
```

The same pattern applies to `claimInstantWithdrawRequest` and to default-recovery claims routed through `_transferDefaultRecovery` [7](#0-6) .

Uncertainty note: the grep results confirmed `claimWithdrawRequest`/`claimInstantWithdrawRequest` exist on `IdleCDOEpochVariant` without a receiver parameter (tests call `cdoEpoch.claimWithdrawRequest()` with no argument), but I could not display the exact wrapper lines before exhausting iterations. The claim entrypoint passing `msg.sender` as `_user` is inferred from the test call signatures and the vault's `_onlyIdleCDO` + `_user` design; if a receiver parameter exists there, it should be verified before finalizing severity.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
