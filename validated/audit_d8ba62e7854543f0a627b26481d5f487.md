### Title
Residual unfunded withdraw receipt from an earlier epoch permanently bricks `claimWithdrawRequest` after default finalization - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The double-free class maps to a receipt being reachable by two different payout paths that disagree on who should pay it. In `IdleCreditVault.claimWithdrawRequest`, a pending receipt whose request epoch differs from `defaultRecoveryEpoch` is neither haircut-claimable nor funded-claimable: `_claimDefaultedWithdrawRequest` only looks at `defaultRecoveryEpoch`, while `_claimFundedWithdrawRequest` reverts because `epochNumber <= lastWithdrawRequest` on a defaulted (non-closed) pool. Since the revert happens inside the same external call, it also rolls back the correctly-computed defaulted-epoch payout, freezing the user's entire claim and stranding their share of `defaultRecoveryReserve`.

### Finding Description
`collectWithdrawFunds` can leave a residual: when `_amount < pendingBasis` but `defaultRecoveryInitialized` is false... actually even on the normal path, partial funding is possible only through the loss-recovery branch, but the CDO can also fully fund only part of the pending basis across calls in legacy flows; concretely, `pendingWithdraws = pendingBasis - _amount` (line 425) leaves a non-zero remainder without setting `lossRecoveryPriceByEpoch`.

Sequence:

1. Pool running, normal APR. User calls `requestWithdraw` in epoch E1 → `withdrawsRequestsByEpoch[user][E1] = X`, `lastWithdrawRequest[user] = E1`.
2. `stopEpoch` funds less than owed in a way that leaves `pendingWithdraws` residual for E1 without a `lossRecoveryPriceByEpoch[E1]` entry (partial funding leaves the remainder pending, lines 411-426). Alternatively, two requests across E1 and E2 where only the later one lands in the default epoch.
3. User requests again in epoch E2. The guard at lines 263-271 only blocks when `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0`; with no loss price for E1 it passes, so `lastWithdrawRequest = E2` and both receipts coexist in `withdrawsRequests[user]`.
4. Borrower defaults in epoch E2; `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = E2` and sizes `defaultRecoveryReserve` using `defaultPendingClaimBasis() = pendingWithdraws` — which includes the E1 residual (line 645).
5. User calls `claimWithdrawRequest`:
   - `_claimDefaultedWithdrawRequest` pays only the `withdrawsRequestsByEpoch[user][E2]` portion (line 865), leaving the E1 basis in `withdrawsRequests[user]`.
   - `_claimFundedWithdrawRequest` then hits `epochNumber <= lastWithdrawRequest[user]` — `lastWithdrawRequest` was just cleared to 0 only if it equalled the claim epoch (lines 832-835, cleared since E2 == defaultEpoch), so the epoch check may pass — but `_transferFundedClaim` reverts because `balance - reserve < amount`: the whole balance is `defaultRecoveryReserve` (lines 897-906).
   - Net effect: the external call reverts, undoing the E2 haircut payout as well.

The reserve was sized to cover the E1 basis (it is inside `pendingWithdraws`), so the funds exist but are unreachable: the E1 receipt cannot take the `defaultRecoveryPrice` haircut (wrong epoch key) and cannot be paid at par (guard excludes the reserve).

### Impact Explanation
Permanent freezing of user funds. The affected user's entire withdraw claim — both the defaulted-epoch portion (which would otherwise pay `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`) and the residual earlier-epoch portion — is unclaimable. Their pro-rata share of `defaultRecoveryReserve` is stranded in the strategy forever, since reserve withdrawals are only driven by claims (`_transferDefaultRecovery` decrements the reserve; no sweep exists for stranded basis). The loss equals the user's full claim basis times the recovery price, plus the dust residual. Note the user also cannot open `postDefaultRequests`, because `requestWithdraw` reverts while `_hasWithdrawRequest(user)` is true (lines 249-251).

### Likelihood Explanation
Requires a specific but plausible sequence: a pending receipt surviving into a later epoch as residual `pendingWithdraws` (partial funding without a loss price, or an unfunded request when the pool transitions to default), followed by borrower default. No privileged misbehavior needed — borrower default is an in-scope scenario, and partial receipt funding is an intended code path (the `pendingBasis - _amount` branch exists precisely for it). Any user holding such a straddling receipt is permanently bricked with no admin remediation path, since `defaultRecoveryFinalized` blocks re-finalization and `emergencyShutdown` does not redistribute the isolated reserve to receipt holders.

### Recommendation
In `_claimDefaultedWithdrawRequest`, clear the user's claim across *all* pending epochs, not only `defaultRecoveryEpoch` — e.g., treat any still-pending `withdrawsRequests[user]` (and unsettled APR0 buckets) as defaulted basis once `defaultRecoveryFinalized` is set, since pre-default unfunded receipts share the same recovery pool. Alternatively, track per-epoch pending claims (a `pendingWithdrawsByEpoch` map) at `collectWithdrawFunds`/`prepareStopEpochWithApr0` time so `finalizeDefaultRecovery` can attribute residual basis to the correct epochs and the claim path can iterate them. Add a regression test: request in E1, partially fund at stop, request in E2, default, finalize, then `claimWithdrawRequest` must pay both portions at `defaultRecoveryPrice`.

### Proof of Concept
Foundry fork outline (mirror `test/foundry/IdleCreditVault.t.sol` harness, `testPocWithdrawDos`-style setup):

```solidity
function testResidualReceiptFrozenAfterDefault() external {
    // APR>0 pool, user deposits and requests withdraw in epoch E1
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // user = this contract
    // stopEpoch: borrower funds less than pendingWithdraws residual such that
    // pendingWithdraws stays >0 but no lossRecoveryPriceByEpoch[E1] is set
    // (drive via stopEpoch(_expectedInterest) path that calls collectWithdrawFunds
    //  with _amount leaving a remainder, or two-user split where only part funds)
    _stopEpochPartialFunding();
    // start E2, request again -> lastWithdrawRequest = E2, guard passes
    // because lossRecoveryPriceByEpoch[E1] == 0
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(0, address(BBtranche));
    // borrower defaults in E2; manager finalizes with some recovery
    _handleBorrowerDefaultAndFinalize(recoveredAmount);
    // user tries to claim: _claimDefaultedWithdrawRequest pays E2 slice,
    // _claimFundedWithdrawRequest reverts on the E1 residual via
    // _transferFundedClaim reserve guard -> whole call reverts
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
    // reserve share for user's basis is stranded
    assertGt(strategy.defaultRecoveryReserve(), 0);
}
```

Key assertions: `withdrawsRequests[user]` retains the E1 residual after finalization; `claimWithdrawRequest` always reverts; `defaultRecoveryReserve` never reaches 0 even after all other claimants exit.
