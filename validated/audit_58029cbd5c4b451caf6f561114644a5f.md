### Title
Signer re-validates only a narrow subset of chainstate checks at pre-commit/signing time, allowing a block that has become invalid (wrong miner, wrong consensus hash, bad bitvec, or bad tenure-extend) to still be signed - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`GlobalStateView::check_proposal` / `SortitionsView::check_proposal` perform the full set of proposal-validity checks (miner-pubkey-hash match, consensus-hash match, PoX bitvec, tenure-extend legality, miner-timeout/`InvalidMiner` detection, `DuplicateBlockFound`) exactly once, when a block proposal first arrives. The re-checks that run later — at block-validation-OK time and again at pre-commit-threshold/signing time — call only the narrower `check_block_against_signer_db_state`, which the code itself flags as incomplete. This is the same "presentation-layer filtering, no execution-layer enforcement" pattern as the referenced advisory: a full authorization decision is made once at the "list"/discovery step, but the step that actually spends the irreversible resource (a signature) only re-runs a subset of the guard.

### Finding Description
The full validity check lives in `check_proposal`: [1](#0-0) 
which enforces `InvalidMiner`, `ConsensusHashMismatch`, `PubkeyHashMismatch`, `InvalidBitvec`, tenure-extend legality, and (via `validate_tenure_change_payload`) `DuplicateBlockFound`: [2](#0-1) [3](#0-2) 

This full check is invoked exactly once, from `handle_block_proposal` via `check_block_against_state`, at the moment a proposal is first received: [4](#0-3) [5](#0-4) 

Every later re-verification point — at `handle_block_validate_ok` (after the node's async validation returns) and at `handle_block_pre_commit` (the point where the pre-commit threshold is reached and a signature is actually produced) — calls only `check_block_against_signer_db_state`, which the code's own doc-comment marks as incomplete and only checks `check_tenure_change_confirms_parent` / `check_latest_block_in_tenure`: [6](#0-5) [7](#0-6) [8](#0-7) 

The project's own design documentation confirms this is a deliberate but incomplete split, explicitly listing the checks that are "proposal path only" and "not re-run at validate-ok or at signing": [9](#0-8) 

Critically, `InvalidMiner` (miner-timeout detection inside `check_proposal`, lines 144-163 of `chainstate/v1.rs`) and `ConsensusHashMismatch`/`PubkeyHashMismatch`/`InvalidBitvec` (in `GlobalStateView::check_proposal`) are *not* in the documented "known, separately-mitigated" category the way `DuplicateBlockFound` is (the docs explicitly say the duplicate-block gap is covered by section 5's own-tenure conflict guard in `handle_block_pre_commit`). No equivalent statement or guard exists for the miner-status/consensus-hash/bitvec/tenure-extend checks. Separately, `check_miner_inactivity` (the periodic housekeeping timeout detector) only updates the signer's `local_state_machine`/`current_miner` view; it does not retroactively re-run `check_proposal` against a `BlockInfo` that has already been stored and moved to `PreCommitted`.

The consequence: a tenure-start block that legitimately passed `check_proposal` at time t0 (correct active miner, correct consensus hash, valid bitvec, legal tenure-extend) can still be signed at time t1, even if by t1 the signer's own state machine has since concluded the miner is inactive/invalid, or would otherwise reject the block under `check_proposal`'s stricter rules — because `handle_block_pre_commit`'s "chainstate checks still pass?" gate (`check_block_against_signer_db_state`) never re-runs those checks.

### Impact Explanation
This breaks the equality the state machine is supposed to maintain between "validated" and "about to be signed": the block that crosses the 70% pre-commit weight and gets signed is not the same thing that was fully re-verified — it only had the narrow tenure/height check re-run. In the worst case this lets a signer put its signature over a block belonging to a miner/tenure the signer has itself since deemed invalid, i.e., a signature over a block that would be rejected by a fresh proposal-time evaluation. Per the stated scope, this maps to the Critical bucket: a signer signing an invalid/non-canonical block due to a check that exists at the "list"/discovery layer but is not enforced at the "call"/signing layer.

### Likelihood Explanation
The scenario requires no majority collusion and no key compromise: it only requires (a) the natural gossip/network latency between "pre-commit weight crosses 70%" and "block was proposed", which the pre-commit design explicitly anticipates can be non-trivial ("time passes, the burn chain can fork... a signer takes one last look"), and (b) that a state transition invalidating the block's premises (miner timeout, e.g.) occurs in that window without a corresponding retroactive re-check. Because the retroactive re-check function itself is documented as "incomplete" and the gap for the other similar check (`DuplicateBlockFound`) is explicitly acknowledged and mitigated elsewhere, the absence of an equivalent mitigation for `InvalidMiner`/`ConsensusHashMismatch`/`PubkeyHashMismatch`/`InvalidBitvec` indicates it was not anticipated to need one.

### Recommendation
Re-run (or fold into `check_block_against_signer_db_state`) the miner-validity, consensus-hash, pubkey-hash, bitvec, and tenure-extend checks from `check_proposal` at both the validate-ok recheck and the pre-commit-threshold recheck in `stacks-signer/src/v0/signer.rs`, so that the same full check that gates the initial proposal also gates the point where the signature is actually produced.

### Proof of Concept
1. Miner M wins the sortition for tenure T and broadcasts tenure-start block `B0`. `handle_block_proposal` → `check_block_against_state` → `check_proposal` passes (`InvalidMiner`, `ConsensusHashMismatch`, `PubkeyHashMismatch`, bitvec, tenure-extend all pass); the node validates it OK; the signer calls `mark_pre_committed` and broadcasts a pre-commit (`stacks-signer/src/v0/signer.rs:1961-1983`).
2. Pre-commit weight accumulates slowly (network delay/partition) and stays below the 70% threshold for longer than `block_proposal_timeout`.
3. Independently of any new proposal for `B0`, the signer's periodic housekeeping (`check_miner_inactivity`) detects the miner has gone inactive/timed out for tenure T, since `has_signed_block_in_tenure` is still false (only pre-committed, not signed) — the signer's local state now considers tenure T's miner invalid.
4. Late-arriving pre-commit gossip finally pushes the weight over 70%. `handle_block_pre_commit`'s gate calls `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1345-1366`, implementation at `1799-1880`), which only checks tenure-confirms-parent/latest-block-in-tenure — it never re-checks `InvalidMiner`/`ConsensusHashMismatch`/`PubkeyHashMismatch`/bitvec — so the signer proceeds to `mark_locally_accepted` and broadcasts its signature over `B0` despite its own state machine having since invalidated that miner/tenure.

    /// in tenure changes, we need to check:
    /// if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    fn validate_tenure_change_payload(
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        parent_tenure_id: &ConsensusHash,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        config: &ProposalEvalConfig,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the signer's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            config.tenure_last_block_proposal_timeout,
            config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // We already confirmed in check miner activity that the current tenure is valid. So check we are not
        // reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count
        // here: a block we have merely pre-committed to carries no signature from us, so it is safe to
        // accept a competing tenure-start block in its place if it failed to reach consensus.
        let last_in_current_tenure = signer_db
            .get_last_signed_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }

or at signing:

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
  have already accepted a block in the tenure a tenure-change block is starting.

threshold long after it was proposed relies on section 5's own-tenure conflict
