### Title
Loss-adjusted withdraw receipts can be claimed at par because `lossRecoveryPriceByEpoch` is looked up under the user's stale request epoch instead of the epoch key written at `collectWithdrawFunds` — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2023-1989 is a use-after-free caused by `btsdio_remove` running while an unfinished job still references `hdev` — a stale-pointer/lifecycle bug where teardown frees a resource a pending user still dereferences. The closest analog in `IdleCreditVault` is the loss-adjusted withdrawal lifecycle in `collectWithdrawFunds` / `_claimLossAdjustedWithdrawRequest`: the haircut price is stored under the vault-global `epochNumber`, but each user later dereferences it through their own stale `lastWithdrawRequest` marker. A pending receipt that outlives the epoch boundary is resolved under the wrong key and is paid at par, breaking the loss-socialization invariant.

### Finding Description
When a `stopEpoch` realizes a loss, the CDO underfunds pending withdraw receipts and calls `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws`. The vault then writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws` (lines 411-421). The comment at line 322 states that `epochNumber` is increased at `stopEpoch`, so the haircut is keyed by the epoch counter at collection time, not by the epoch in which each receipt was requested.

Later, `claimWithdrawRequest` routes through `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789-792) — the user's request-epoch marker — and `_clearWithdrawClaimForEpoch` only clears `withdrawsRequestsByEpoch[_user][_claimEpoch]` for that single epoch (lines 811-836). If `lastWithdrawRequest[_user]` does not equal the key under which the price was stored (e.g., `epochNumber` is incremented inside `stopEpoch` before `collectWithdrawFunds` runs, or a receipt's request epoch diverges from the collection-epoch key), the lookup returns 0, the function exits early, and execution falls through to `_claimFundedWithdrawRequest`. That path only enforces `epochNumber > lastWithdrawRequest[_user]` (line 326), which is satisfied after the stop, and then pays the full `withdrawsRequests[_user]` aggregate at par via `_transferFundedClaim` (lines 338-349).

This mirrors the UAF shape exactly: the pending receipt (the "unfinished job") survives the epoch teardown, and the claim path dereferences its accounting through a stale epoch key, so the haircut that was priced into `pendingWithdraws` is never applied.

### Impact Explanation
`pendingToFund` computed by `previewLossAdjustedWithdrawFunds` (lines 440-459) sizes the borrower funding assuming *all* pending receipts absorb `pendingLoss`. If affected receipts instead claim at par from the strategy's underlying reserve, the reserve is drained beyond what was funded: the first claimants to hit `_claimFundedWithdrawRequest` take 100% while later claimants' loss-adjusted or funded claims revert on insufficient balance — direct theft of other users' claims and protocol insolvency, proportional to `pendingLoss` on the aggregate pending basis. No privileged misbehavior is required; the attacker's only action is calling `claimWithdrawRequest` (through the honest `IdleCDOEpochVariant`) on a receipt that predates the loss-adjusted stop.

### Likelihood Explanation
Requires a realized loss stop (`stopEpochWithDuration` / underfunded `collectWithdrawFunds`), which is a supported code path with dedicated accounting, plus a pending receipt whose `lastWithdrawRequest` epoch differs from the `epochNumber` key used at collection. Whether the divergence is systematic (increment-before-collect ordering, which would make *every* loss-adjusted receipt claimable at par) or situational (receipts spanning the funding boundary) depends on the exact ordering inside `IdleCDOEpochVariant.stopEpoch`, which should be verified — but in either case the dual-key design (`epochNumber` for write, `lastWithdrawRequest` for read) provides no binding between the haircut and the receipts it covers, and there is no guard that forces a user through the loss-adjusted path when their receipt was part of the haircut basis.

### Recommendation
Store the haircut keyed by the same epoch identifier users carry (e.g., write `lossRecoveryPriceByEpoch` under the request epoch recorded in `withdrawsRequestsByEpoch`, or record the funding epoch per receipt), and/or make `_claimLossAdjustedWithdrawRequest` iterate/mark receipts rather than dereference a single `lastWithdrawRequest` key. Additionally, `_claimFundedWithdrawRequest` should verify that no uncleared `withdrawsRequestsByEpoch` entry maps to an epoch with a nonzero `lossRecoveryPriceByEpoch` before paying at par.

### Proof of Concept
Foundry fork PoC sketch on `IdleCreditVault.t.sol` harness:
1. User A and B `depositAA`, epoch 0 runs and stops normally.
2. Both `requestWithdraw` during epoch 1 (receipts recorded under `lastWithdrawRequest = 1`, `pendingWithdraws = A + B`).
3. Manager calls `stopEpoch` with a loss so `collectWithdrawFunds` receives `_amount < pendingWithdraws`; `lossRecoveryPriceByEpoch[epochNumber]` is written under the post-stop `epochNumber` (verify via `strategy.epochNumber()` inside collect vs. users' `lastWithdrawRequest`).
4. Warp past buffer, call `cdoEpoch.claimWithdrawRequest()` as A.
5. Assert A received `amount` at par (`underlying` delta == `withdrawsRequests[A]` pre-claim) rather than `amount * lossRecoveryPrice / RECOVERY_FULL`, and that B's subsequent claim reverts or pays less than its haircut-adjusted entitlement.

Uncertainty note: exploitability hinges on whether `epochNumber` is incremented before `collectWithdrawFunds` within `stopEpoch` (making all receipts escape) or whether only boundary-spanning receipts escape; either ordering leaves receipts unbound to the haircut basis. Confirm by tracing `epochNumber` inside `IdleCDOEpochVariant.stopEpoch` and `IdleCreditVault` stop-epoch hooks relative to the `collectWithdrawFunds` call.
