### Title
Stale confirmations from removed multisig members still count toward `num_confirmations`, allowing request execution below the live-member threshold - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
When a multisig member (access key or account) is removed via `DeleteKey` (v1) / `DeleteMember` (v2), the contract only purges pending requests that were *originally submitted* by that member's key/account. It does not purge that member's confirmations recorded on other still-open requests. `confirm()` counts confirmations purely by set size (`confirmations.len() + 1 >= num_confirmations`) with no re-validation that every confirming entry still belongs to a live member. This lets a request execute with fewer live, currently-authorized confirmations than `num_confirmations` requires.

### Finding Description
`confirm()` in both versions blindly trusts the stored confirmation set size against `num_confirmations`: [1](#0-0) [2](#0-1) 

Membership removal only cleans up requests keyed by the removed signer as the *original requester* — it does not scan other requests' confirmation sets to strip the removed member's stale confirmation:

- v1 `DeleteKey` handling filters `self.requests` by `r.signer_pk == pk` (the request's original signer) and removes only those requests/confirmations, then deletes the key itself: [3](#0-2) 

- v2 `delete_member` does the analogous filter by `r.member == member`: [4](#0-3) 

In neither case is there any pass over `confirmations` for *other* requests where the removed member/key had already called `confirm()` but was not the original requester. Those entries remain in the `HashSet` and continue to satisfy the `confirmations.len() + 1 >= num_confirmations` check in `confirm()`.

This breaks the intended equality: `confirmations counted == live members who confirmed`. After a removal, `confirmations counted > live members who confirmed`, so a request can reach the threshold using fewer currently-authorized signers than `num_confirmations` mandates.

### Impact Explanation
This is a "multisig request executed below threshold" scenario, explicitly a Critical-severity custody-binding violation: funds can be transferred, keys/members added, contract code deployed, or arbitrary `FunctionCall` actions executed by the multisig account with effectively fewer live approvals than the configured K-of-N policy requires. Any pending request that received a confirmation from a member who is later removed retains that "ghost" confirmation indefinitely, silently lowering the effective threshold for that specific request.

### Likelihood Explanation
Requires: (1) a member confirms a request without it reaching threshold, (2) that member is later removed via a separate `DeleteKey`/`DeleteMember` request, and (3) the original pending request is still open and gets the remaining confirmations from the smaller set of live members. This is a plausible operational sequence (e.g., rotating out a compromised or departing member while other requests are in flight) and does not require any privileged bypass beyond the ordinary multisig workflow the remaining members already use — it is a latent state-consistency defect rather than a contrived attack requiring unusual privileges.

### Recommendation
On `DeleteKey`/`DeleteMember` execution, iterate all entries in `confirmations` (not just requests originated by the removed signer/member) and remove the removed signer's/member's public key or account id from every confirmation set, e.g.:
```rust
for (request_id, mut confs) in self.confirmations.iter() {
    if confs.remove(&removed_identity) {
        self.confirmations.insert(&request_id, &confs);
    }
}
```
Alternatively, validate on `confirm()` that the accumulated confirmation set only contains currently-valid members/keys before comparing against `num_confirmations`, rather than trusting historically inserted keys.

### Proof of Concept
1. Multisig initialized with members `A, B, C, D` and `num_confirmations = 3`.
2. `A` calls `add_request(R1)` (e.g., a `Transfer`). Confirmations for `R1` = `{}`.
3. `B` calls `confirm(R1)` → confirmations for `R1` = `{B}` (count 1), per `confirm()` logic. [1](#0-0) 
4. Separately, members agree via another request `R2` (`DeleteKey`/`DeleteMember` targeting `B`) and it executes, removing `B`'s access key/membership. This only removes requests where `B` was the *original signer* — `R1` was submitted by `A`, so it is untouched, and `R1`'s confirmation set still contains `B`. [3](#0-2) 
5. `C` calls `confirm(R1)` → confirmations = `{B, C}` (count 2).
6. `D` calls `confirm(R1)` → count becomes `3 >= num_confirmations`, and `R1` executes — even though `B` no longer holds a valid key/membership and never re-confirmed after removal. Only `C` and `D` (2 live members) actually authorized execution of a request meant to require 3 live confirmations.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/

        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);

        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
