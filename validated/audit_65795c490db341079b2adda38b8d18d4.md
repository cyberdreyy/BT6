### Title
Retroactive API-token lifetime extension via mutable `UserAPITokenDuration` config re-evaluated at validation time - ([File: core/sessions/oidcauth/oidc.go], [File: core/sessions/ldapauth/ldap.go])

### Summary
API tokens for LDAP and OIDC authentication are validated by comparing `created_at + UserAPITokenDuration()` against `now()`, where `UserAPITokenDuration()` is read from the **live, mutable** config at validation time rather than the value in effect when the token was issued [1](#0-0) . This is the same root-cause pattern as the reported `WITHDRAWAL_STAKE` bug: a per-request/per-token parameter is not persisted at creation time, so a later change to the global configuration retroactively changes the effective validity window for tokens that already exist.

### Finding Description
When an API token is created, `SetAuthToken` inserts only `created_at` into the `ldap_user_api_tokens` / `oidc_user_api_tokens` tables — it does not persist the duration that was in effect at creation time [2](#0-1) [3](#0-2) .

Later, `FindUserByAPIToken` re-derives token validity using the current value of `oi.config.UserAPITokenDuration()` / `l.config.UserAPITokenDuration()` fetched fresh from config at request time: [4](#0-3) [5](#0-4) 

If an operator changes `WebServer.OIDC.UserAPITokenDuration` or `WebServer.LDAP.UserAPITokenDuration` (e.g. from 240h to a shorter value to tighten security, or increases it), **every previously issued token** is affected retroactively:
- Increasing the duration extends the lifetime of tokens that were meant to have already expired under the old, shorter setting — an unpriveleged holder of an old/leaked token that should be dead gets to keep using it.
- Decreasing the duration can prematurely invalidate tokens that were still supposed to be valid under the policy in force when they were issued, an availability/DoS concern for legitimate users.

This directly parallels the report's core issue: a value fixed at "submission" time (token creation) should be locked in, but the code instead re-fetches a mutable global at "settlement" time (validation), producing gains (extended token lifetime = unauthorized continued access) or losses (premature invalidation) relative to the policy that was actually in force when the credential was issued.

### Impact Explanation
An attacker holding an old or leaked API token benefits if the operator raises `UserAPITokenDuration` for any reason (e.g. widening the value for legitimate users) — the attacker's stale token, which should already be dead under the original policy, becomes valid again without re-authentication, since expiry is computed purely from `created_at` + the current config value [1](#0-0) . This is a request-impersonation / authentication-bypass style issue reachable from any unprivileged API caller holding a previously valid token.

### Likelihood Explanation
Low-to-moderate: it requires an operator to change `UserAPITokenDuration` in `WebServer.OIDC` or `WebServer.LDAP` config while there are still tokens issued under the previous policy. This is a supported, documented configuration knob [6](#0-5) , so config changes over the lifetime of a node's operation are realistic, but exploitation additionally requires an attacker to already be holding a token that would otherwise have expired.

### Recommendation
Persist the effective expiry (or the duration in effect) alongside `created_at` at token-creation time in `ldap_user_api_tokens` / `oidc_user_api_tokens`, and validate against that stored value instead of re-reading the live config in `FindUserByAPIToken`. Alternatively, on any change to `UserAPITokenDuration`, force re-validation/revocation of all existing tokens so config changes cannot retroactively alter already-issued credentials' effective lifetime.

### Proof of Concept
1. Node configured with `WebServer.OIDC.UserAPITokenDuration = '1h'`.
2. User issues an API token via `SetAuthToken` at `T0`; row inserted with `created_at = T0` only [7](#0-6) .
3. At `T0 + 2h`, the token should be expired under the original 1h policy.
4. Operator updates `WebServer.OIDC.UserAPITokenDuration = '240h'` for unrelated reasons.
5. Attacker (who obtained the token, e.g. via leak) calls an authenticated API endpoint at `T0 + 2h`; `FindUserByAPIToken` computes validity as `created_at + 240h >= now()`, which is now true, so `Valid = true` is returned and the stale token is accepted [8](#0-7) , granting authenticated access that should have been rejected.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
