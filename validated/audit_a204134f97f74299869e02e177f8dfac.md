### Title
Owner-supplied `whitelist_account_id` + trust-any-callback `on_get_account_total_balance` let a lockup owner inflate `deposit_amount` and drain locked/unvested tokens - (File: `lockup-factory/src/lib.rs`, `lockup/src/owner_callbacks.rs`, `lockup/src/getters.rs`)

### Summary
`lockup-factory`'s `create()` lets the caller supply an arbitrary `whitelist_account_id` instead of the trusted NEAR Foundation whitelist, and `LockupContract::on_get_account_total_balance` blindly overwrites `staking_information.deposit_amount` with whatever value a "staking pool" contract's `get_account_total_balance` callback returns, with no bound tied to real transfers. Because `get_liquid_owners_balance()` is `min(get_owners_balance(), get_account_balance())`, once `deposit_amount` is inflated the `- get_locked_amount()` term in `get_owners_balance()` is neutralized and the owner can `transfer()` the contract's *entire real* account balance, including amounts still locked/unvested.

### Finding Description
The claimed binding is: `get_liquid_owners_balance() == real_account_balance - get_locked_amount()` (transferable funds must never include the locked/unvested portion).

Trace:
1. Anyone can call `LockupFactory::create()` and choose `whitelist_account_id: Option<ValidAccountId>` — if provided, it overrides the factory's own trusted whitelist and is stored as the new lockup's `staking_pool_whitelist_account_id`: [1](#0-0) . The `test_create_lockup_with_custom_whitelist_success` test confirms this path is fully supported for a caller-chosen whitelist contract: [2](#0-1) .
2. If no `vesting_schedule` is supplied, `foundation_account_id` is set to `None` on the deployed lockup, so `assert_no_termination`/termination logic can never engage: [3](#0-2) .
3. As owner of this self-created lockup, the attacker calls `select_staking_pool(fake_pool)`. The whitelist check is delegated to whatever contract is at `staking_pool_whitelist_account_id` — the attacker's own malicious whitelist, which always answers `true`: [4](#0-3) .
4. The attacker calls `refresh_staking_pool_balance()`, which queries `get_account_total_balance` on the attacker-controlled "pool" contract with no real funds ever having moved: [5](#0-4) .
5. `on_get_account_total_balance` unconditionally overwrites `deposit_amount` with the returned `#[callback] total_balance`, with no upper bound, no sanity check, and no verification that this reflects real assets: [6](#0-5) .
6. `get_known_deposited_balance()` now returns this attacker-chosen huge value: [7](#0-6) .
7. `get_owners_balance() = account_balance + known_deposited_balance - locked_amount` saturates far above `account_balance`: [8](#0-7) .
8. `get_liquid_owners_balance() = min(get_owners_balance(), get_account_balance())` collapses to the raw `account_balance` (minus storage minimum) — completely losing the `- locked_amount` subtraction, because the `min()` clamp compares against the un-adjusted account balance rather than re-applying the lock: [9](#0-8) .
9. `transfer()` only checks `get_liquid_owners_balance().0 >= amount.0`, so the owner can now transfer the entire real account balance — including tokens that were supposed to remain locked under `lockup_duration`/`release_duration`: [10](#0-9) .

None of the existing guards prevent this: `assert_owner` only confirms the caller is the lockup's own owner (which the attacker is, by design, for their self-created lockup); `assert_self()` on the callback only ensures it was called back by the contract itself via the promise chain it started; `is_promise_success()` isn't used in `on_get_account_total_balance` at all — the callback value is trusted unconditionally; `assert_no_termination` is a no-op since `vesting_information` is `None` when no vesting schedule was chosen.

### Impact Explanation
The lockup/vesting contract's core invariant — that `get_owners_balance()`/`get_liquid_owners_balance()` never exceed real assets minus the amount still locked — is broken. An owner can move real NEAR that is contractually still locked (per `lockup_duration`/`release_duration`) out to any address via `transfer()`. This is a Critical-class issue per the target severity model: "locked/unvested lockup tokens released to a party not entitled to them," achieved without any NEAR Foundation, multisig, or redeploy involvement — purely through the attacker's own factory-created contracts and self-controlled callback values. It is repeatable for any lockup the attacker creates for themselves, and scales to the full real balance of that lockup account each time.

### Likelihood Explanation
Preconditions are all attacker-controllable and consistent with the stated threat model (unprivileged actor using public factories): create a lockup with `vesting_schedule = None` (yields `foundation_account_id = None`) and a custom `whitelist_account_id` pointing at a self-deployed fake whitelist contract; deploy a fake staking-pool contract that answers `is_whitelisted` and `get_account_total_balance` with attacker-chosen values. Attacher cost is limited to the `MIN_ATTACHED_BALANCE` for the lockup creation and normal gas fees; no special privileges, keys, or foundation cooperation are needed. The attack is fully repeatable across any number of self-created lockups.

### Recommendation
- `on_get_account_total_balance` must not blindly overwrite `deposit_amount`; it should validate/bound the reported total against tracked real transfers (e.g., only allow it to increase up to a sane reward bound, or require the value to be corroborated against actual stake/unstake bookkeeping) and should verify `is_promise_success()`.
- `LockupFactory::create()` should not let the caller override the trusted whitelist account with an arbitrary contract for standard flows; if a custom whitelist is a legitimate feature, it must be gated (e.g., only foundation-approved custom whitelists) so lockups cannot self-select an attacker-controlled whitelist/staking-pool pairing.
- `get_liquid_owners_balance()` should not silently drop the lock enforcement when `deposit_amount` is inflated; it should be computed so the locked amount is always subtracted from the real, verifiable account balance rather than being bypassed via the `min()` against unadjusted `account_balance`.

### Proof of Concept
`cargo test` plan (near-sdk-sim / unit test style, mirroring existing `lockup/src/lib.rs` and `lockup-factory` tests):
1. Deploy `LockupFactory` normally, then call `create(owner, lockup_duration, None /* no vesting_schedule */, None, Some(attacker_whitelist))` from the attacker account, attaching `MIN_ATTACHED_BALANCE`. Assert the deployed lockup's `foundation_account_id` (via `new` args, or indirectly by confirming `assert_no_termination` never triggers) is `None`.
2. Deploy an attacker-controlled fake whitelist contract implementing `is_whitelisted(...) -> true` and a fake "staking pool" contract implementing `get_account_total_balance(...) -> U128(huge_value)`.
3. As owner, call `select_staking_pool(fake_pool)`; drive the promise callback `on_whitelist_is_whitelisted(true, fake_pool)` — assert it succeeds and `staking_information` is set with `deposit_amount = 0`.
4. Call `refresh_staking_pool_balance()`; drive `on_get_account_total_balance(huge_value.into())` — assert `get_known_deposited_balance().0 == huge_value`.
5. Assert `get_owners_balance().0` far exceeds `env::account_balance()`, and assert `get_liquid_owners_balance().0 == get_account_balance().0` (i.e., equals the full real balance minus storage, ignoring `get_locked_amount()` which should be > 0 since `lockup_duration`/timestamp has not elapsed).
6. Call `transfer(get_liquid_owners_balance(), attacker_receiver)` and assert it succeeds, moving real NEAR that `get_locked_amount()` reports as still locked — proving the binding `get_liquid_owners_balance() == real_balance - locked_amount` is violated (actual result: `get_liquid_owners_balance() == real_balance`, locked amount ignored).
