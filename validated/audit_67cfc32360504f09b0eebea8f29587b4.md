## Title
V1 Chainstate's `DuplicateBlockFound` Guard Uses `get_last_globally_accepted_block` Instead of `get_last_signed_block`, Allowing Double-Sign of Competing Tenure-Start Blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

## Summary
`v1.rs::validate_tenure_change_payload` guards against re-signing a tenure-start block by calling `signer_db.get_last_globally_accepted_block`, whereas `v2.rs::validate_tenure_change_payload` uses `signer_db.get_last_signed_block`, which additionally covers blocks that are only `LocallyAccepted`. On a mixed v1/v2 reward set this asymmetry means a v1-protocol signer can sign a second, competing tenure-change block for a tenure in which it (the same signer) already locally-accepted a different tenure-start block, whenever that first block has not yet reached global acceptance.

## Finding Description
The equality that must hold is: given identical local `SignerDb` state (a `LocallyAccepted`, not-yet-`GloballyAccepted` block already recorded for a tenure) and an identical second competing tenure-change proposal for that same tenure, every signer instance — regardless of which agreement protocol version it is running — must produce the same accept/reject verdict.

- `v1.rs::validate_tenure_change_payload` (lines 505-518) calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. If the previously accepted block is only `LocallyAccepted` (i.e., this signer already signed it, but the network as a whole has not yet reached the global-acceptance threshold), this query returns `None`, and the duplicate-block guard is skipped — the v1 code path proceeds to sign the second tenure-change block for the same tenure.
- `v2.rs::validate_tenure_change_payload` (lines 340-357) calls `signer_db.get_last_signed_block(&block.header.consensus_hash)`, which the code comment (lines 340-343) explicitly documents as covering "blocks we have signed (locally or globally accepted)" — deliberately excluding only pre-commits (which carry no signature). This correctly returns `Some(...)` for the locally-accepted block, and the v2 signer rejects the second proposal with `RejectReason::DuplicateBlockFound`.

Root cause: the v1 code was seemingly written against an older invariant (only global acceptance matters) and was not updated to match the v2 comment's rationale that a signer's own local signature on a tenure-start block must never be supersedable within the same tenure, even before the network reaches quorum. On a mixed-version reward set (e.g., mid-upgrade), a single attacker-controlled miner slot can win two sortitions/tenure-changes in quick succession (or otherwise get two competing tenure-change blocks proposed) for the same tenure boundary before the first proposal reaches global acceptance. v1-protocol signers, following `get_last_globally_accepted_block`, will each independently see `None` and sign the second, competing tenure-start block — producing two validly signed tenure-start blocks for the same tenure from the v1 subset of the signer set. v2 signers correctly refuse. No existing guard (auth token, transport, node validation) intervenes, since this is a signer-local chainstate check that both versions are relied upon to enforce identically.

## Impact Explanation
This breaks the uniqueness/equivocation-guard safety property for tenure-start blocks: a subset of the reward set (all v1 signers) can each contribute a valid signature to two different tenure-start blocks for the same tenure. If the v1 subset's aggregate signing weight is sufficient (combined with the miner's own actions) to reach threshold on both competing blocks, this finalizes two conflicting tenure-start blocks for one tenure — a chain-safety violation (Critical: a signer signing a conflicting block). Even short of full threshold, it weakens the equivocation guard and moves the mixed-version signer set closer to a fork, which is exactly the "signature valid across tenure boundaries" / "conflicting block" impact category. It is repeatable for every affected tenure boundary during the mixed-version upgrade window, at the cost of only one miner slot and the ability to gossip a second competing tenure-change proposal for the same slot's tenure.

## Likelihood Explanation
Preconditions: an active reward-set upgrade epoch where some signers run v1 chainstate logic and others run v2 (this is exactly the scenario the multiversion signer tests in `stacks-node/src/tests/signer/multiversion.rs` are built to exercise, confirming mixed v1/v2 reward sets are a real, tested-for state in this codebase). The attacker only needs to win a single miner slot (their own BTC), and must be fast enough to get a second, competing tenure-change block proposal in front of v1 signers before the first reaches global acceptance — a timing window that exists by construction whenever a block has only reached `LocallyAccepted` status. No majority-signer or privileged access is required; the attacker's action is limited to crafting/gossiping BlockProposals as an ordinary miner, matching the allowed threat model exactly.

## Recommendation
Change `v1.rs::validate_tenure_change_payload` (line 506) to call `signer_db.get_last_signed_block` instead of `signer_db.get_last_globally_accepted_block`, mirroring the v2 logic and its documented rationale (locally-accepted-but-not-yet-global blocks still carry this signer's own signature and must block a competing tenure-start proposal). Verify `get_last_signed_block` exists with the same semantics in the version of `SignerDb` used by v1 (it is defined in `stacks-signer/src/signerdb.rs`), and add a regression test asserting both `v1.rs` and `v2.rs` reject with `DuplicateBlockFound` given identical `SignerDb` state containing a `LocallyAccepted` prior block in the tenure.

    /// in tenure changes, we need to check:
    /// (1) if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    /// (2) if the parent tenure was a valid choice
    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }
