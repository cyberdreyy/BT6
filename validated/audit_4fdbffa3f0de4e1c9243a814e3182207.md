### Title
Post-default withdraw requests drain the fixed `defaultRecoveryReserve`, stealing recovery owed to defaulted-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The DMA reentrancy/use-after-free bug class (crafted writes to a shared resource while it is being consumed by in-flight operations) maps to concurrent claims against a shared, fixed-size accounting resource: `defaultRecoveryReserve`. After `finalizeDefaultRecovery`, the reserve is sized exactly to pay defaulted-epoch receipts at `defaultRecoveryPrice`. However, `requestWithdraw` in the `defaultRecoveryFinalized` branch creates *new* `postDefaultRequests` receipts that are paid **1:1 out of the same reserve**, with no new underlying ever added to it. Any unprivileged lender who requests a withdraw after finalization converts the haircut recovery pool into a first-come-first-served pool that pays them at par and leaves defaulted-epoch claimants underfunded.

### Finding Description
At `finalizeDefaultRecovery`, `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` [1](#0-0) . When `recoveryPrice < RECOVERY_FULL` (any real default haircut), the reserve covers `totalBasis * price`, i.e. it is exactly exhausted once every defaulted claimant receives their haircut share.

In the post-default branch of `requestWithdraw`, the CDO's strategy tokens are burned, the user is minted a 1:1 receipt, and `postDefaultRequests[_user] = _amount` is recorded — but no underlying is pulled and `defaultRecoveryReserve` is unchanged [2](#0-1) .

`_claimPostDefaultWithdrawRequest` then pays the full `amount` via `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= _amount` [3](#0-2) [4](#0-3) . Every post-default claim therefore consumes recovery capacity that accounting-wise belongs to defaulted-epoch receipts (`_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest`), which pay only `claimBasis * defaultRecoveryPrice` [5](#0-4) .

No guard stops this: the only check on the post-default path is that the user has no prior pending request (`_hasWithdrawRequest` / `instantWithdrawsRequests` / `postDefaultRequests` all zero), which any fresh attacker address trivially satisfies [6](#0-5) .

### Impact Explanation
Broken invariant: recovery reserve isolation. Quantified loss: up to the full post-default claim amount is taken at 1:1 while legitimate defaulted claimants only ever receive `defaultRecoveryPrice` of their basis — an attacker withdrawing X post-default effectively steals `X` of reserve that would otherwise pay `X / defaultRecoveryPrice` of defaulted basis. When the reserve underflows, later defaulted claims revert (Solidity 0.8 underflow on `defaultRecoveryReserve -= _amount`), permanently freezing unclaimed recovery for defaulted-epoch lenders.

### Likelihood Explanation
Trigger requires a finalized default with `defaultRecoveryPrice < 1` — the exact scenario the whole recovery accounting exists for. After finalization the attacker just needs to be a KYC'd lender holding tranche tokens, call the CDO's withdraw-request path (which mints a post-default receipt), wait for claimability per the normal epoch gating, and claim before other defaulted claimants. No privileged role misbehavior needed; sequencing is entirely around honest CDO/manager calls.

### Recommendation
Fund post-default receipts from a source other than `defaultRecoveryReserve`: either (a) require the borrower/CDO to transfer underlying into the strategy before `postDefaultRequests` is set and track it in a separate `postDefaultReserve` paid via `_transferFundedClaim`, or (b) apply `defaultRecoveryPrice` to post-default claims as well and account for them in `totalBasis`. At minimum, `_claimPostDefaultWithdrawRequest` should revert if paying at par would leave less than `totalDefaultBasis * defaultRecoveryPrice` unclaimed in the reserve.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
