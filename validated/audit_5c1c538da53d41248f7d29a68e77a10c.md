### Title
Token-2022 transfer fees not deducted before CPI deposit in Solend/Kamino/Drift/JupLend integration deposit paths causes Denial of Service - ([File: programs/marginfi/src/instructions/solend/deposit.rs])

### Summary
The `solend_deposit`, `kamino_deposit`, `drift_deposit`, and `juplend_deposit` instructions transfer a caller-supplied `amount` of the bank's underlying mint into the bank's intermediary `liquidity_vault`, then immediately attempt to move that same full `amount` out of the vault via a CPI into the external lending protocol (Solend/Kamino/Drift/JupLend). If the bank's mint is a Token-2022 mint with a `TransferFeeConfig` extension, the transfer into the vault delivers `amount - fee`, but the subsequent CPI call still requests the full `amount`, which the vault does not have. This mirrors the reported mtOFT bug class: a wrap/transfer operation's fee is not subtracted before the value is consumed downstream, causing the transaction to always revert.

### Finding Description
In the direct (non-integration) deposit path, marginfi explicitly compensates for Token-2022 transfer fees before transferring: [1](#0-0) 
using `calculate_pre_fee_spl_deposit_amount`, which computes the pre-fee amount to transfer so that the vault ends up receiving exactly `deposit_amount`: [2](#0-1) 

However, none of the integration deposit paths (Solend, Kamino, Drift, JupLend) apply this compensation. For example, `solend_deposit`: [3](#0-2) 
calls `cpi_transfer_user_to_liquidity_vault(amount)` (a plain `transfer_checked` for `amount`) and then `cpi_solend_deposit(amount, ...)`, which instructs Solend's `deposit_reserve_liquidity_and_obligation_collateral` CPI to pull the full `amount` out of `liquidity_vault`. If the mint charges a transfer fee, the vault only received `amount - fee` from the first transfer, so the CPI attempting to move `amount` out of the vault will fail due to insufficient funds.

The same pattern is present in:
- `kamino_deposit` (`cpi_transfer_user_to_obligation_owner(amount)` followed by `cpi_kamino_deposit(amount, ...)`): [4](#0-3) 
- `drift_deposit` (`cpi_transfer_user_to_liquidity_vault(amount)` followed by `cpi_drift_deposit(market_index, amount, ...)`): [5](#0-4) 
- `juplend_deposit` (`cpi_transfer_user_to_liquidity_vault(amount)` followed by `cpi_juplend_deposit(amount, ...)`): [6](#0-5) 

Notably, the withdraw side of these same integrations *does* correctly measure the actual amount moved via vault balance deltas rather than assuming it equals the requested amount (e.g., Kamino/Solend withdraw compute `received = post_transfer_vault_balance - pre_transfer_vault_balance`): [7](#0-6) [8](#0-7) 
This asymmetry confirms that the deposit paths were not designed with fee-bearing mints in mind, exactly analogous to the mtOFT report where the `wrap()` return value (post-fee amount) was ignored and the pre-fee amount was propagated downstream.

### Impact Explanation
If any admin configures a Solend/Kamino/Drift/JupLend integration bank backed by a Token-2022 mint that has a nonzero `TransferFeeConfig`, every unprivileged user's `solend_deposit`/`kamino_deposit`/`drift_deposit`/`juplend_deposit` call against that bank will revert, because the external protocol's CPI will attempt to pull more tokens out of the intermediary vault than it actually holds after the fee-bearing transfer. This is a complete, permanent Denial of Service for depositing into that specific integration bank — mirroring the "High" impact classification in the referenced report, where leverage functionality became permanently unusable for mtOFT collateral.

### Likelihood Explanation
The regular `lending_account_deposit` path already had to be hardened against Token-2022 transfer-fee mints (see the `calculate_pre_fee_spl_deposit_amount` compensation and dedicated T22 fee tests/fuzzing), indicating the protocol explicitly anticipates fee-bearing mints as a realistic configuration. The integration deposit instructions reuse the same bank/mint model but were not updated with the same compensation logic, so any future integration bank backed by a fee-bearing Token-2022 mint will trigger this DoS deterministically on every deposit attempt, with no adversarial input required beyond normal usage.

### Recommendation
Apply the same fee-compensation logic used in `lending_account_deposit` to all integration deposit paths (Solend, Kamino, Drift, JupLend):
1. Before transferring from the user into the intermediary vault/account, compute the pre-fee transfer amount via `calculate_pre_fee_spl_deposit_amount` (or equivalent) so the vault ends up holding exactly the intended `amount`.
2. Alternatively, measure the actual amount that landed in the vault (via balance deltas, as already done on the withdraw side) and use that measured amount as the argument to the external protocol's CPI deposit call, rather than assuming the requested `amount` is unaffected by the transfer.

### Proof of Concept
1. Admin creates a Solend (or Kamino/Drift/JupLend) integration bank whose `bank_mint` is a Token-2022 mint with `TransferFeeConfig` (nonzero `transfer_fee_basis_points`).
2. A user calls `solend_deposit(amount)` with `signer_token_account` funded with `amount` of the fee-bearing mint.
3. `cpi_transfer_user_to_liquidity_vault(amount)` executes a `transfer_checked`, but Token-2022 deducts the transfer fee, so `liquidity_vault` receives only `amount - fee`. [9](#0-8) 
4. `cpi_solend_deposit(amount, ...)` is then called, instructing Solend to pull the full `amount` from `liquidity_vault` (`source_liquidity_info: self.liquidity_vault`): [10](#0-9) 
5. Because `liquidity_vault` only holds `amount - fee`, the CPI transfer inside Solend's `deposit_reserve_liquidity_and_obligation_collateral` fails with an insufficient-funds error, reverting the entire transaction.
6. Every subsequent deposit attempt against this bank fails identically, permanently denying deposits for that integration bank.

pub fn calculate_pre_fee_spl_deposit_amount(
    mint_ai: AccountInfo,
    post_fee_amount: u64,
    epoch: u64,
) -> MarginfiResult<u64> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(post_fee_amount);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    match mint.get_extension::<TransferFeeConfig>() {
        Ok(transfer_fee_config) => {
            let epoch_fee = transfer_fee_config.get_epoch_fee(epoch);
            let pre_fee_amount = calculate_pre_fee_amount(epoch_fee, post_fee_amount).unwrap();
            Ok(pre_fee_amount)
        }
        Err(_) => Ok(post_fee_amount),
    }
}

impl<'info> SolendDeposit<'info> {
    pub fn cpi_transfer_user_to_liquidity_vault(&self, amount: u64) -> MarginfiResult {
        let program = self.token_program.to_account_info();
        let accounts = TransferChecked {
            from: self.signer_token_account.to_account_info(),
            to: self.liquidity_vault.to_account_info(),
            authority: self.authority.to_account_info(),
            mint: self.mint.to_account_info(),
        };
        let cpi_ctx = CpiContext::new(program.key(), accounts);
        let decimals = self.mint.decimals;
        transfer_checked(cpi_ctx, amount, decimals)?;
        Ok(())
    }

    pub fn cpi_solend_deposit(&self, amount: u64, authority_bump: u8) -> MarginfiResult {
        let accounts = DepositReserveLiquidityAndObligationCollateral {
            source_liquidity_info: self.liquidity_vault.to_account_info(),
            user_collateral_info: self.user_collateral.to_account_info(),
            reserve_info: self.integration_acc_1.to_account_info(),
            reserve_liquidity_supply_info: self.reserve_liquidity_supply.to_account_info(),
            reserve_collateral_mint_info: self.reserve_collateral_mint.to_account_info(),
            lending_market_info: self.lending_market.to_account_info(),
            lending_market_authority_info: self.lending_market_authority.to_account_info(),
            destination_deposit_collateral_info: self.reserve_collateral_supply.to_account_info(),
            obligation_info: self.integration_acc_2.to_account_info(),
            obligation_owner_info: self.liquidity_vault_authority.to_account_info(),
            pyth_price_info: self.pyth_price.to_account_info(),
            switchboard_feed_info: self.switchboard_feed.to_account_info(),
            user_transfer_authority_info: self.liquidity_vault_authority.to_account_info(),
            token_program_info: self.token_program.to_account_info(),
        };
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), authority_bump);

        // Create CPI context with signer
        let cpi_ctx =
            CpiContext::new_with_signer(self.solend_program.key(), accounts, signer_seeds);
        deposit_reserve_liquidity_and_obligation_collateral(cpi_ctx, amount)?;
        Ok(())
    }
}
