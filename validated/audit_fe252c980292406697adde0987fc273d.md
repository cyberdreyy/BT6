### Title
External-initiator credentials alone satisfy the `isUser` check in `PipelineRunsController.Create`, bypassing the "EIs not allowed" restriction on int-ID job runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
The comment in `PipelineRunsController.Create` claims "only users are allowed to run jobs using int IDs - EIs not allowed," but the `isUser` check it relies on cannot distinguish a real user session/token from an external-initiator (EI) authenticated request, because `auth.AuthenticateExternalInitiator` writes the *same* context key (`SessionUserKey`) that `AuthenticateByToken`/`AuthenticateBySession` use. This lets any valid EI credential holder trigger arbitrary int-ID job runs with no session-cookie forgery needed at all.

### Finding Description
`PipelineRunsController.Create` gates int-ID job execution solely on: [1](#0-0) 

`isUser` comes from `auth.GetAuthenticatedUser(c)`, which just checks for presence of the `SessionUserKey` context value: [2](#0-1) 

However, `AuthenticateExternalInitiator` — the method that validates `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers — also sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` object: [3](#0-2) 

Because `GetAuthenticatedUser` only checks for the existence of `SessionUserKey` and does not differentiate "real user" identity from this synthetic EI-derived identity, `isUser` evaluates to `true` for a request authenticated purely via valid EI credentials. No stolen/forged session cookie is required — a legitimate EI accessKey/secret pair alone is sufficient to satisfy the `isUser` branch and reach `prc.App.RunJobV2(ctx, jobID, nil)` with an attacker-supplied int32 job ID, which is exactly the behavior the code comment states should be blocked.

### Impact Explanation
This is an authorization-boundary bypass: an EI-restricted credential (intended only to trigger its own webhook/UUID-keyed job) can instead invoke `RunJobV2` against *any* int32 job ID on the node, triggering unauthorized job runs outside the EI's intended scope. This matches Chainlink's bounty impact class of unauthorized job run / execution-boundary bypass.

### Likelihood Explanation
Minimal precondition: possession of a single valid external-initiator accessKey/secret pair (a credential type explicitly issued to lower-trust integrators). No session theft, cookie forgery, or additional privilege is needed — the request only needs the two EI headers set and a guessed/known int32 job ID in the URL path. This is trivially repeatable via a single crafted HTTP POST.

### Recommendation
Distinguish real authenticated users from EI-derived pseudo-users, e.g., store EI authentication under a distinct context flag (or check `GetAuthenticatedExternalInitiator(c)` is absent) before allowing int-ID `RunJobV2` execution in `PipelineRunsController.Create`, rather than relying on the shared `SessionUserKey`/`GetAuthenticatedUser` presence check.

### Proof of Concept
Handler-level integration test:
1. Register an `ExternalInitiator` with a known accessKey/secret and a plain int-ID `job.Job` (non-webhook) in the test DB.
2. Send `POST /v2/jobs/:ID/runs` with `ID` = the int32 job ID, headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials, and no session cookie.
3. Assert the response is `200`/`201` with a `pipelineRun` resource returned (i.e., `RunJobV2` was invoked), proving the "EIs not allowed" restriction is bypassed.
4. Assert `auth.GetAuthenticatedExternalInitiator(c)` is non-nil in this flow (confirming the request was EI-authenticated, not user-authenticated) while `isUser` was still `true`.
