### Title
Stale-epoch APR0 withdraw receipt escapes the default-recovery haircut and permanently freezes the user's recovery claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` is the epoch-based credit strategy behind `IdleCDOEpochVariant`. The bug class of CVE-2022-1145 (use-after-free: a stale object is consumed through a code path that assumes it was already destroyed) maps here to a stale APR0 withdraw receipt whose `principalEpoch` no longer matches `defaultRecoveryEpoch`. When a borrower default is finalized in a later epoch than the one the APR0 receipt was requested in, `_claimDefaultedWithdrawRequest` cannot see the receipt (it only inspects `apr0Users[_user].principalEpoch == defaultRecoveryEpoch`), so the still-outstanding receipt falls through to `_claimFundedWithdrawRequest`, which treats it as an already-funded par claim. That breaks the "one receipt, one haircut" invariant in two ways: if any non-reserve underlyings remain, the receipt is paid at par while every other defaulted claimant is haircut; otherwise `_transferFundedClaim`'s reserve guard reverts and the user's entire claim — including the correctly-accounted defaulted portion already earmarked in `defaultRecoveryReserve` — is permanently frozen.

### Finding Description
In `requestWithdraw`, APR0-mode receipts (`unscaledApr == 0`) are recorded in `apr0Users[_user].principal`/`principalEpoch` and `apr0TotalPrincipal`, not in `withdrawsRequestsByEpoch` (lines 285-293). `pendingWithdraws` is still increased by the request amount (line 279), so `defaultPendingClaimBasis()` includes the APR0 principal when `finalizeDefaultRecovery` computes `recoveryPrice` and sizes `defaultRecoveryReserve` (lines 644-710).

Settlement of an APR0 receipt is lazy: `apr0Users[_user].principal` is only moved into `settledPrincipal`/`settledInterest` by `_settleApr0`, which runs inside `_claimFundedWithdrawRequest` or `_requestWithdrawApr0` (lines 545-565). A user who requests an APR0 withdraw in epoch E and simply waits — making no further request — keeps `principalEpoch == E` forever.

If a default occurs and `finalizeDefaultRecovery` runs in a later epoch D > E, it sets `defaultRecoveryEpoch = D`. The claim path in `claimWithdrawRequest` then does (lines 303-313):

1. `_claimDefaultedWithdrawRequest` → `_clearWithdrawClaimForEpoch(_user, D, true)` → `_withdrawClaimAmountsForEpoch(_user, D)` returns `claimBasis = 0` for this receipt, because `withdrawsRequestsByEpoch[_user][D] == 0` and `apr0User.principalEpoch == E != D` (lines 862-881). The APR0 receipt is invisible to the default haircut despite having been counted in the basis.
2. `_claimLossAdjustedWithdrawRequest` returns 0 (no `lossRecoveryPriceByEpoch`).
3. `_claimFundedWithdrawRequest` runs unconditionally. Its epoch gate `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]` cannot block the claim: `epochNumber` is already ≥ D > E = `lastWithdrawRequest[_user]`. `_settleApr0` then moves `principal` to `settledPrincipal` (since `E < epochNumber`), and the function burns receipt tokens and calls `_transferFundedClaim(_user, settledPrincipal + settledInterest)` (lines 326-349).

Two outcomes, both broken:

- **Escape at par:** if the strategy holds any underlyings beyond `defaultRecoveryReserve` (e.g., a fully-funded instant bucket that was excluded via `pendingInstantWithdraws == 0`, rounding dust, or direct-token-send donations), the stale APR0 receipt is paid 100% while all other defaulted-epoch claimants receive only `defaultRecoveryPrice`. The recovery ratio was diluted to include this receipt's basis, so other claimants' payouts were reduced to fund a claim that skips the haircut.
- **Permanent freeze:** when `balanceOf(this) == defaultRecoveryReserve` (the normal post-finalization state, since `reserveAmount` accounts for the whole `totalBasis`), `_transferFundedClaim` reverts via `balance - reserve < _amount` (lines 897-907). The revert rolls back the defaulted claim too, and the user can never claim: `requestWithdraw` post-default also reverts via `_hasWithdrawRequest` (lines 247-251). The user's share of `defaultRecoveryReserve` is locked forever — a use-after-destroy stale-pointer analog where the "destroyed" (haircut-assigned) receipt is dereferenced through the wrong path.

### Impact Explanation
Direct theft and/or permanent freezing of recovery funds, fully reachable by an unprivileged tranche-token holder. In the par-payment branch, the attacker extracts `apr0Principal + apr0Interest` at face value; quantified loss to other claimants equals the haircut they would have absorbed, i.e. `receipt * (1 - defaultRecoveryPrice)`, plus the dilution of `recoveryPrice` itself (the receipt's basis was included in `totalBasis` when the reserve was divided). In the freeze branch, the victim's entire claim — defaulted receipts plus APR0 receipt — is unrecoverable and its share of `defaultRecoveryReserve` is stranded permanently (no sweep function exists for it; `transferToken` is owner-only and ignoring it still leaves the claim blocked).

### Likelihood Explanation
Requires the APR0 mode (`unscaledApr == 0`, an advertised pool configuration exercised in the test suite) and a default finalized at least one epoch after the APR0 request epoch with the user not having re-requested or claimed in between — a normal "request and wait" user. No privileged attacker, no oracle manipulation, no timing race beyond an ordinary epoch boundary. Existing guards do not stop it: `_ensureDefaultRecoveryInitialized` is satisfied, the loss-receipt guard at lines 263-271 only blocks *new* requests, and the `defaultRecoveryEpoch` equality check in `_withdrawClaimAmountsForEpoch` is precisely the mismatched-stale-pointer condition that causes the bug.

### Recommendation
In `_claimDefaultedWithdrawRequest` (or `_withdrawClaimAmountsForEpoch`), treat any still-open APR0 receipt (`apr0User.principal != 0`) as defaulted regardless of `principalEpoch`, since `pendingWithdraws`/`defaultPendingClaimBasis` already counted it. Concretely: remove the `principalEpoch == _claimEpoch` condition for the default path (or compare `principalEpoch <= defaultRecoveryEpoch`), clear `apr0TotalPrincipal` accordingly, and route the payout through `_transferDefaultRecovery` at `defaultRecoveryPrice`. Equivalently, eagerly settle APR0 receipts inside `finalizeDefaultRecovery` so no stale `principalEpoch` can survive into the funded-claim path. Add a regression test: APR0 request in epoch E, epoch rollover, default finalized in epoch E+1, then `claimWithdrawRequest`.

### Proof of Concept
Foundry fork PoC outline (modeled on `testFinalizeDefaultHaircutsApr0PendingRedeemsWithAdjustedInterestBasis` in `test/foundry/IdleCreditVault.t.sol:4553`):

```solidity
function testStaleApr0ReceiptFreezesDefaultClaim() external {
    // setup: APR0 pool
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    address victim = makeAddr('victim');
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);

    // epoch 0 -> stop, epoch 1 starts; victim requests APR0 withdraw in epoch 1
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    vm.prank(victim);
    uint256 principal = cdoEpoch.requestWithdraw(type(uint256).max / 2, address(AAtranche));

    _startEpochAndCheckPrices(1);   // request lives in epoch 1
    // victim does NOT claim or re-request -> principalEpoch stays 1

    // epoch 1 ends with borrower default; epochNumber is now 2
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);       // borrower returns nothing -> default
    _checkDefault();

    // owner finalizes recovery in epoch 2 -> defaultRecoveryEpoch = 2 != 1
    uint256 recovered = /* 70% of totalBasis */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // victim's claim: defaulted path misses principalEpoch==1,
    // funded path settles APR0 and calls _transferFundedClaim -> revert on reserve guard
    vm.prank(victim);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();  // permanently frozen

    // If the strategy instead held stray non-reserve underlyings, the same call
    // pays `principal + settledInterest` at par while peers get defaultRecoveryPrice.
}
```

Uncertainty note: whether the strategy retains non-reserve underlyings post-finalization determines which branch (par theft vs. permanent freeze) executes; the freeze branch is the default outcome because `finalizeDefaultRecovery` sizes the reserve to cover the entire `totalBasis`. Either branch is a valid finding under the stated acceptance criteria.
