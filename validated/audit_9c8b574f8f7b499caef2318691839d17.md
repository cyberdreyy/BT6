### Title
Unauthenticated APR takeover before CDO binding inflates lender payouts - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

`IdleCreditVault.setApr`, `setAprs`, and `setAprsWithBuffer` are permissionless while `idleCDO == address(0)`. An attacker can alter both the scaled and unscaled APR during the deployment window before the strategy is bound to the credit-vault CDO. Once the honest owner completes setup, the attacker can deposit through the normal KYC path and receive the inflated borrower-funded yield.

### Finding Description

The authorization check in `setApr` is state-dependent: if `idleCDO` is unset, the function skips the caller check entirely [1](#0-0) . Both APR setters update `unscaledApr` before delegating to this function, so the pre-binding window can be used to set arbitrary APR values subject only to `maxApr` [2](#0-1) .

Initialization establishes a 20× scaled-APR cap [3](#0-2) . A value below the cap is later used by the epoch CDO as borrower-owed yield through `_calcInterest`, `startEpoch`, and `stopEpoch` accounting [4](#0-3) [5](#0-4) .

### Impact Explanation

An ordinary KYC-passing attacker can turn an intended yield rate into a borrower obligation approaching the configured cap. For example, replacing a 5% APR with a 1,700% APR produces approximately `34x` the intended epoch interest on the attacker’s deposit, before the buffer-period scaling logic.

If the borrower pays, excess value is transferred to depositors through the normal epoch accounting. If the borrower cannot pay, the withdrawal path becomes underfunded and may trigger default rather than simply reverting the malicious APR [6](#0-5) . This constitutes theft of borrower-provided yield and can create insolvency/freezing for other lenders.

### Likelihood Explanation

The attack requires only an unprivileged transaction during the setup window before `setWhitelistedCDO` assigns `idleCDO`. The code explicitly documents this unauthenticated state as “during the setup” but does not restrict it to owner, manager, factory, or deployer [7](#0-6) . Deployment and CDO binding are separate operations in the test harness, demonstrating that the intermediate state exists [8](#0-7) .

### Recommendation

Require `msg.sender == owner()` or `msg.sender == manager` whenever `idleCDO == address(0)`. After binding, retain the existing CDO-or-manager check. Equivalently, implement a dedicated `initializeApr` path callable only during initialization and make all later APR mutations explicitly authorized.

### Proof of Concept

A Foundry regression test can reproduce the missing authorization directly:

```solidity
// test/foundry/IdleCreditVault.t.sol
function testSetAprBeforeWhitelisting() external {
    address attacker = makeAddr("attacker");

    assertEq(strategy.idleCDO(), address(0));

    vm.prank(attacker);
    strategy.setAprsWithBuffer(17e18, 30 days, 5 days);

    assertEq(strategy.unscaledApr(), 17e18);
    assertEq(
        strategy.lastApr(),
        17e18 * (30 days + 5 days) / 30 days
    );
}
```

For the fund-impact path, run the existing credit-vault fixture with `strategy.idleCDO()` left unset immediately after strategy initialization, call `setAprsWithBuffer` from an attacker EOA, then bind the CDO, let a KYC-passing attacker deposit, have the honest manager start and stop the epoch with the borrower funded for the inflated obligation, and compare the attacker’s withdrawal proceeds against the intended APR.

    address _cdo = idleCDO;

    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
