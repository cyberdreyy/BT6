### Title
Stale tranche price after discounted mid-epoch deposit causes underpriced withdraw requests - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`depositDuringEpoch` mints tranche tokens at a discounted rate (`minted < _amount / price`) while crediting the full `_amount` to `lastNAV`. The next `_updateAccounting` sees `totalGain == 0` and takes the early return in `_virtualPriceAux`, leaving `priceAA`/`priceBB` stale. `requestWithdraw` then prices principal via `_trancheToUnderlyings` at the stale stored price, permanently underpaying withdrawers; the excess NAV is redistributed to remaining tranche holders at `stopEpoch`. This mirrors the DODO bug: the "no rebalancing needed" state (zero NAV delta) skips the target/price update even though supply changed.

### Finding Description
In `IdleCDOEpochVariant.depositDuringEpoch` a mid-epoch depositor is minted `(amount + trancheInterest) * supply / expectedFinal` shares — strictly less than `amount / tranchePrice` — but `_mintShares` adds the full `_amount` to `lastNAV{AA,BB}` [1](#0-0) .

Because NAV grew by exactly `_amount` together with the deposit, `getContractValue() == lastNAVAA + lastNAVBB` afterward, so every subsequent `_updateAccounting` computes `totalGain == 0` and `_virtualPriceAux` returns the stored price without recomputing NAV-per-share [2](#0-1) . The forced-recompute path only runs under `skipDefaultCheck` [3](#0-2) .

`requestWithdraw` calls `_updateAccounting` (which keeps the stale price) and then computes `principal = amount * _tranchePrice(tranche)` via `_trancheToUnderlyings` [4](#0-3) [5](#0-4) . The receipt is fixed and `_withdrawOps` removes only that understated `principal` from NAV [6](#0-5) .

### Impact Explanation
The true NAV-per-share after a mid-epoch deposit is `(lastNAV + amount) / (supply + minted) > storedPrice`, but withdrawal receipts are locked at `storedPrice`. Using the repo's own test numbers (`testDepositDuringEpochNumericalAA`): 1000 deposit at 1.0 price, then a 1000 mid-epoch deposit mints ~954.5 shares → true price ≈ 2000/1954.5 ≈ 1.0233 while `priceAA` stays 1.0. Any user calling `requestWithdraw` during the running epoch loses ~2.3% of principal; that residual NAV is captured by remaining tranche holders when `stopEpoch` finally reprices. An unprivileged attacker who holds tranche tokens can trigger the condition (the discounted deposit is itself a permitted user action once `isDepositDuringEpochDisabled` is cleared) and harvest the spread by remaining invested while others withdraw.

### Likelihood Explanation
Requires `isDepositDuringEpochDisabled == false` (owner-enabled, honest) and withdraw requests during the running epoch (`allowAAWithdrawRequest`/`allowBBWithdrawRequest`, enabled by `startEpoch`). Both are normal operating modes; no privileged misbehavior needed. Loss scales with mid-epoch deposit size and accrued discount.

### Recommendation
In `_virtualPriceAux` (or `_updateAccounting`), recompute `_virtualPrice = lastTrancheNAV * ONE_TRANCHE_TOKEN / trancheSupply` whenever `trancheSupply` changed relative to the saved price, instead of returning the stored price on `totalGain == 0` — i.e., add the missing "equilibrium" branch, exactly as the DODO report recommends adding the `RState == ONE` branch. Alternatively, have `requestWithdraw` price principal with `virtualPrice`/`_virtualBalance` instead of the stored `_tranchePrice`.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVault.t.sol` patterns):

```solidity
function testStalePriceUnderpaysWithdrawRequest() external {
    // 10% apr, 365-day epoch, no buffer (same setup as testDepositDuringEpochNumericalAA)
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    uint256 initialDeposit = 1000 * ONE_SCALE;
    idleCDO.depositAA(initialDeposit);
    _startEpochAndCheckPrices(0);

    // halfway through epoch, enable mid-epoch deposits
    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    // attacker/user makes discounted mid-epoch deposit (mints ~954.5 shares for 1000)
    address mid = makeAddr('mid');
    deal(defaultUnderlying, mid, 1000 * ONE_SCALE);
    vm.startPrank(mid);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), 1000 * ONE_SCALE);
    cdoEpoch.depositDuringEpoch(1000 * ONE_SCALE, address(AAtranche));
    vm.stopPrank();

    // stored price is stale: real NAV/share = 2000/1954.5 ≈ 1.0233, stored priceAA == 1.0
    assertEq(cdoEpoch.priceAA(), ONE_SCALE, 'stored price should be stale');
    assertGt(cdoEpoch.virtualPrice(address(AAtranche)), cdoEpoch.priceAA(), 'virtual > stored');

    // victim requests withdraw of 1000 tranche tokens during running epoch:
    // principal = 1000 * priceAA = 1000 instead of ~1023
    address victim = /* holder of 1000 AA tranche tokens */;
    vm.prank(victim);
    uint256 requested = cdoEpoch.requestWithdraw(1000 * ONE_TRANCHE, address(AAtranche));
    assertLt(requested, 1023 * ONE_SCALE, 'receipt priced at stale price - underpaid');

    // after stopEpoch the withdrawn discount remains in NAV and accrues to
    // remaining holders (attacker) -> redistribution of yield
}
```

Caveat: this conclusion rests on indexed code; I verified the early-return path, the discounted mint formula, and `requestWithdraw`'s use of the stored price, but could not fully trace `_withdrawOps` / claim settlement within the iteration budget. If `requestWithdraw` reprices principal at claim time from `virtualPrice`, the loss is avoided; as indexed, the receipt is fixed at request time using `tranchePrice`, so the staleness propagates.
