### Title
Instant-withdraw receipt basis is never released on funded claims, inflating default-recovery basis and diluting/locking recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2019-18807 is a resource-leak bug: allocations are acquired but never freed on certain paths, degrading the shared resource over time. The analog in `IdleCreditVault` is the per-epoch instant-withdraw claim ledger: `requestInstantWithdraw` allocates entries in `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (IdleCreditVault.sol:366-374), but the normal claim path `claimInstantWithdrawRequest` releases only the aggregate `instantWithdrawsRequests[_user]` and never clears the per-epoch allocations (IdleCreditVault.sol:387-392). The per-epoch ledger is freed only inside `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:847-853). This stale, never-freed basis is later consumed by `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery`, corrupting the recovery price (IdleCreditVault.sol:644-649, 685-696, 716-723).

### Finding Description
When a borrower default is finalized via `finalizeDefaultRecovery`, the strategy computes the total claim basis as `activeBasis + pendingBasis`, where `pendingBasis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (IdleCreditVault.sol:644-648). The recovery price is `reserveAmount * RECOVERY_FULL / totalBasis` (line 688), and every defaulted/post-default claim is paid out of `defaultRecoveryReserve` at that price.

`instantWithdrawClaimsByEpoch[epochNumber]` is incremented for every instant receipt minted in that epoch but is decremented **only** in `_claimDefaultedInstantWithdrawRequest`. A user who got funded before default (via `collectInstantWithdrawFunds`, which reduces `pendingInstantWithdraws` but not the per-epoch ledgers) and already claimed via `claimInstantWithdrawRequest` leaves a "ghost" basis in `instantWithdrawClaimsByEpoch`. At finalization:

1. `totalBasis` is inflated by the ghost amount, so `recoveryPrice` is lower than it should be — all active LPs and pending claimants are underpaid.
2. The ghost basis can never be claimed: for the already-claimed user, `_claimDefaultedInstantWithdrawRequest` does `instantWithdrawsRequests[_user] -= claimBasis`, which underflows (their aggregate is already 0), so no one ever consumes the reserve earmarked for the ghost basis — it stays locked in `defaultRecoveryReserve` forever.
3. `_defaultPrefundedInstantReserve` (lines 716-722) computes `instantBasis - pendingInstant` using the inflated `instantBasis`, overstating the prefunded reserve as well, further skewing `reserveAmount` vs. real claimants.

Attacker sequence (unprivileged, fixed-APR pool with instant withdrawals enabled): deposit AA, wait for APR to drop so `requestWithdraw` routes to `requestInstantWithdraw` (IdleCDOEpochVariant.sol:761-768), get the request funded during the buffer via `collectInstantWithdrawFunds` while other users' instant requests remain unfunded (`pendingInstantWithdraws != 0`), then call `claimWithdrawRequest`/`claimInstantWithdrawRequest` to take 100% at par — while leaving ghost basis behind. If the borrower then defaults in that same epoch and the manager finalizes, the attacker's fully-paid claim is counted a second time in `defaultPendingClaimBasis`, diluting every other claimant and permanently locking the corresponding slice of the recovery reserve.

### Impact Explanation
Direct theft via dilution plus permanent freezing: the attacker extracts their full instant claim at par before default while still inflating the recovery denominator, so every other defaulted receipt holder and active LP receives a strictly smaller payout; the reserve allocated to the ghost basis is unclaimable by anyone (any attempt reverts on underflow) and remains stuck in the strategy permanently. Loss scales with the attacker's instant-withdraw size relative to the epoch's instant bucket.

### Likelihood Explanation
Requires an epoch where instant withdrawals are partially funded (pendingInstantWithdraws > 0) and the borrower defaults in that epoch after at least one instant claimant already claimed. Partial funding is an acknowledged state (per the `_defaultPrefundedInstantReserve` comments), and the attacker controls only their own deposit/request/claim timing — no privileged cooperation needed. The borrower default itself is not attacker-caused, but defaults are a core designed-for scenario in this codebase, so the sequence is realistic rather than exotic.

### Recommendation
Mirror the per-epoch cleanup used for normal withdraws: in `claimInstantWithdrawRequest` (and/or in `collectInstantWithdrawFunds`), decrement `instantWithdrawsRequestsByEpoch[_user][requestEpoch]` and `instantWithdrawClaimsByEpoch[requestEpoch]` when the funded receipt is consumed, the same way `_claimDefaultedInstantWithdrawRequest` already does at IdleCreditVault.sol:847-853. Since `instantWithdrawsRequests` is aggregate, the claim path needs the request epoch recorded (e.g., a `lastInstantWithdrawRequest` marker or per-epoch iteration) to know which epoch entry to clear. Add a regression test: fund and claim an instant request, then default in the same epoch with residual `pendingInstantWithdraws`, and assert `instantWithdrawClaimsByEpoch[epochNumber]` equals only unfunded receipts.

### Proof of Concept
I was unable to fully verify `IdleCDOEpochVariant`'s default-entry path (`_handleBorrowerDefault`) timing within the search budget, so the exact orchestration calls below may need minor adjustment, but the Foundry fork PoC skeleton is:

```solidity
function testInstantClaimGhostBasisDilutesRecovery() external {
  // Setup: fixed-APR vault, instant withdrawals enabled, AA deposit by attacker and victim.
  uint256 amount = 100_000 * ONE_SCALE;
  uint256 attackerTranche = idleCDO.depositAA(amount);      // attacker
  _depositWithUser(victim, amount, true);                   // victim AA

  // Drop APR so requestWithdraw routes into requestInstantWithdraw.
  vm.prank(manager);
  strategy.setAprs(lowApr, lowAprScaled);
  vm.prank(manager); cdoEpoch.setLastEpochAprForTest(...); // or warp so lastEpochApr > apr + delta

  // Attacker requests instant withdraw; victim also requests (stays unfunded).
  cdoEpoch.requestWithdraw(attackerTranche, address(AAtranche)); // instant path
  vm.prank(victim);
  cdoEpoch.requestWithdraw(victimTranche, address(AAtranche));

  // Manager funds only attacker's instant request (partial funding).
  // -> collectInstantWithdrawFunds(attackerAmount) leaves pendingInstantWithdraws > 0.
  vm.prank(manager);
  // borrow/trigger the CDO collect path that calls collectInstantWithdrawFunds(attackerAmount)

  // Attacker claims at par; per-epoch ledgers are NOT cleared.
  uint256 epoch = strategy.epochNumber();
  cdoEpoch.claimInstantWithdrawRequest(); // attacker path via CDO
  assertEq(strategy.instantWithdrawsRequests(attacker), 0);
  assertGt(strategy.instantWithdrawsRequestsByEpoch(attacker, epoch), 0); // ghost
  assertGt(strategy.instantWithdrawClaimsByEpoch(epoch), victimPending);

  // Borrower defaults in the same epoch; manager finalizes recovery.
  _triggerBorrowerDefault();
  vm.prank(manager);
  cdoEpoch.finalizeDefault(recovered, recoverySource);

  // recoveryPrice is diluted by attacker's ghost basis.
  uint256 price = strategy.defaultRecoveryPrice();
  uint256 correctPrice = recovered * 1e18 / correctBasis; // without ghost
  assertLt(price, correctPrice);

  // Victim claim is underpaid; the ghost share of defaultRecoveryReserve is unclaimable.
  vm.prank(victim);
  cdoEpoch.claimInstantWithdrawRequest();
  assertGt(strategy.defaultRecoveryReserve(), 0); // permanently locked dust
}
```

Confidence caveat: the core defect (per-epoch instant ledgers never released on the funded-claim path while being consumed at default finalization) is confirmed in the code; the PoC's exact default-trigger mechanics should be validated against `_handleBorrowerDefault`/`finalizeDefault` in `IdleCDOEpochVariant`, which I could not fully read in this pass.
