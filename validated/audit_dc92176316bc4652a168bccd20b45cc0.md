### Title
Cross-user response hijacking via savedCallbacks MessageId collision in HandleLegacyUserMessage - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores an incoming user callback in `h.savedCallbacks[msg.Body.MessageId]` without checking whether that key already exists, and `handleWebAPITriggerMessage` looks up and deletes by the same key when a node response arrives. Because `MessageId` is fully attacker-chosen and there is no per-sender namespacing, an attacker can register a callback under the same `MessageId` a victim is about to use, causing the victim's DON trigger response to be delivered to the attacker's callback.

### Finding Description
`HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) validates the message payload for decode errors, empty/zero timestamp, and staleness against `MaxAllowedMessageAgeSec`, then unconditionally does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 
There is no existence check, no comparison of `msg.Body.Sender` against an owner recorded for that ID, and no per-sender namespacing of the map key — only `msg.Body.MessageId` (attacker-controlled, up to 128 bytes, validated only for length/null-suffix in `Message.Validate()`) is used as the key. [2](#0-1) 

When a DON node later responds with the trigger result, `handleWebAPITriggerMessage` looks the entry up purely by `MessageId` and delivers the response to whichever callback is currently stored there:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [3](#0-2) 

Exploit flow: attacker submits `HandleLegacyUserMessage` with `MessageId = "shared-id"` (valid signature from attacker's own key, since the signature only proves the sender is the attacker, not that the ID is unique to them). Shortly after, victim submits their own legitimate `web_api_trigger` request also using `MessageId = "shared-id"` (or an ID the attacker predicts/observes and races to overwrite first). Because the map write at line 412 is unconditional last-writer-wins, whichever callback is registered last for that key is the one invoked when the DON eventually responds — if attacker registers after victim (winning the race), attacker's callback receives the victim's trigger response payload, which may contain sensitive workflow output.

None of the existing checks stop this: the decode check, zero-timestamp check, and staleness check only validate the payload's `Timestamp` field, not `MessageId` uniqueness or ownership; the signature check (`Message.Validate`/`ExtractSigner`) only proves who sent the current message, it does not bind the `MessageId` namespace to the sender or reject collisions with another sender's in-flight `MessageId`.

### Impact Explanation
This is a cross-user response confusion / information-disclosure vulnerability: an unprivileged attacker who can send gateway messages (any client capable of invoking `HandleLegacyUserMessage`, e.g., any signed gateway/API caller) can hijack another workflow's `web_api_trigger` response and receive data intended for a different user's workflow. This matches the "cross-user response confusion" and unauthorized disclosure of workflow output bounty impact classes.

### Likelihood Explanation
Exploitability requires only: (1) ability to send a legacy user message to the gateway with an attacker-chosen `MessageId` (no special role/credential beyond being able to sign gateway messages, which any external client of `web_api_trigger` has), and (2) knowledge or prediction of the victim's `MessageId` and a timing window before the victim's node response arrives (since `handleWebAPITriggerMessage` deletes the entry after first use, and requests are pruned only after `CallbackMaxAgeSec`, default 120s, giving a wide race window). If `MessageId`s are attacker-predictable or reused/sequential in the calling client, this becomes trivially repeatable; even with random IDs, deliberate MessageId choice by a malicious client targeting a known victim workflow (e.g., where the ID is derived from a predictable source such as a workflow execution ID) makes this practically exploitable.

### Recommendation
Namespace `savedCallbacks` keys by `(sender, MessageId)` instead of `MessageId` alone, or reject `HandleLegacyUserMessage` requests whose `MessageId` already exists in `savedCallbacks` (returning a collision error) rather than silently overwriting. Additionally consider binding the stored callback to `msg.Body.Sender` and verifying the sender matches when the node response is later dispatched.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler via `NewHandler`.
2. Create two fake `Callback` implementations, `attackerCb` and `victimCb`, each recording the `UserCallbackPayload` they receive.
3. Build a valid `api.Message` for `web_api_trigger` with `MessageId = "shared-id"`, signed by `victimKey`; call `h.HandleLegacyUserMessage(ctx, victimMsg, victimCb)`.
4. Build a second valid message with the same `MessageId = "shared-id"`, signed by `attackerKey`; call `h.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)`.
5. Assert (current buggy behavior) that `h.savedCallbacks["shared-id"].Callback == attackerCb`, i.e., the victim's registration was overwritten — this should fail after a fix, or the second `HandleLegacyUserMessage` call should return a collision error.
6. Simulate the DON node response by calling `h.handleWebAPITriggerMessage(ctx, nodeRespMsg, nodeAddr)` with `MessageId = "shared-id"`.
7. Assert that `attackerCb.received` is populated with the victim's response payload while `victimCb.received` is nil — demonstrating the response hijack. After the fix, assert the call at step 4 either errors out (collision detected) or `victimCb` still receives its own response.
