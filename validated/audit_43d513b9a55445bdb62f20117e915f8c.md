### Title
Cross-tenant requestID collision allows any authorized workflow caller to deny (block) another workflow's HTTP trigger request - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The `httpTriggerHandler.callbacks` map is keyed solely by the caller-supplied `req.ID` string, with no per-workflow or per-caller namespacing. Any caller who is authorized for *any* registered workflow (i.e., holds a valid signed JWT for some workflow's authorized key) can pick an arbitrary `req.ID` and, by winning a race to `setupCallback`, occupy that slot before a victim (using the same or a predictable `req.ID` for a different workflow) submits their request, causing the victim's legitimate request to be rejected with `ErrConflict`.

### Finding Description
`setupCallback` at [1](#0-0)  guards the `h.callbacks` map only with an in-flight duplicate check keyed by `requestID`:
```go
if _, found := h.callbacks[requestID]; found {
    h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, ...)
    return nil, fmt.Errorf("in-flight request ID: %s", requestID)
}
```
There is no association between the map key and the workflow ID or the authorized signer/owner — `h.callbacks` is a single global `map[string]savedCallback` shared across all workflows and callers ( [2](#0-1) ).

Reaching `setupCallback` requires passing `validatedTriggerRequest` and `authorizeRequest`, which call `WorkflowMetadataHandler.Authorize` to verify a JWT signed by a key registered as an authorized signer for the *target* `workflowID` in the request ( [3](#0-2) ). So an attacker doesn't need to be authorized for the victim's workflow — only for *some* workflow they control. They can then submit a `workflows.execute` request with `Method=gateway_common.MethodWorkflowExecute` and an `ID` equal to (or predicted to equal) the victim's `req.ID`, targeting their own workflow.

If the attacker's request reaches `setupCallback` first, it registers `h.callbacks[requestID]` for their own workflow. When the victim's request (using the same ID, for a different workflow) later reaches `setupCallback`, the duplicate check fires and the victim receives `jsonrpc.ErrConflict` ("requestID: %s has already been used") via `handleUserError`, and the victim's real trigger request is never forwarded to the DON (`sendWithRetries` is never called for the victim).

Because responses from nodes in `HandleNodeTriggerResponse` are only produced for whatever request was actually forwarded on the wire (the attacker's own, since only their request passed `setupCallback` and reached `sendToShard`/`SendToNode`), the attacker cannot capture the victim's response content — the aggregator only ever aggregates responses to the attacker's own forwarded payload. The exploitable primitive is therefore blocking, not cross-user data leakage.

### Impact Explanation
This is a scoped denial-of-service: a caller with authorization on any single workflow can prevent a specific, chosen/predicted `req.ID` belonging to a *different* workflow/caller from being processed, causing that particular trigger invocation to fail with a conflict error instead of executing. This matches a limited "Denial of Service" impact class (blocking of a specific user-facing operation), not fund loss, key disclosure, or cross-user data exposure, since the map key namespace is not partitioned per workflow/owner as it logically should be.

### Likelihood Explanation
Requires: (1) attacker must already be authorized (hold a valid signed JWT) for at least one registered workflow — not unauthenticated, but low-privileged relative to the victim's workflow; (2) attacker must know or predict the victim's exact `req.ID` string and win the registration race by submitting first. Since `req.ID` values are entirely client-chosen with no server-side entropy requirement (`validateRequestID` only rejects empty IDs and IDs containing `/`, at [4](#0-3) ), predictable ID schemes (sequential counters, timestamps, well-known constants) used by victim clients make this feasible and repeatable per targeted ID.

### Recommendation
Scope the `callbacks` map key to include the workflow ID (and/or the authorized signer) in addition to `req.ID`, e.g. key by `workflowID + "/" + req.ID`, so that request-ID collisions across different workflows/tenants cannot interfere with each other.

### Proof of Concept
Handler-level Go test plan for `http_trigger_handler_test.go`:
1. Register two workflows, `workflowA` (victim) and `workflowB` (attacker), each with distinct authorized keys via `WorkflowMetadataHandler`.
2. Construct a `jsonrpc.Request` for `workflowB` with `Method=gateway_common.MethodWorkflowExecute`, `ID="shared-id"`, signed by the attacker's authorized key; call `HandleUserTriggerRequest` and confirm it succeeds and registers `h.callbacks["shared-id"]`.
3. Construct a second `jsonrpc.Request` for `workflowA` with the same `ID="shared-id"`, signed by the victim's authorized key; call `HandleUserTriggerRequest`.
4. Assert the victim's call returns an error and that the victim's `callback.SendResponse` was invoked with `jsonrpc.ErrConflict` (per `handleUserError`), and assert `sendWithRetries`/`SendToNode` was never invoked for the victim's payload — demonstrating the victim's request was dropped due to an ID collision originating from an unrelated workflow.

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}
```

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```
