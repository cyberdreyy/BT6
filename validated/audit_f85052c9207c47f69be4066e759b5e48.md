### Title
Stale Confirmations From Removed Multisig Members Are Still Counted Toward the Confirmation Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member()` only purges pending requests that were *originated* by the member being removed; it does not scrub that member's confirmation entries from *other* pending requests they had previously confirmed. As a result, a request can later be executed by `confirm()` while counting a confirmation from an account that is no longer a member, letting the request execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` decides whether to execute a request purely by comparing `confirmations.len()` (a stored `HashSet<String>` of member identifiers who previously called `confirm`) against `self.num_confirmations`: [1](#0-0) 

Membership removal is handled by `delete_member()`, which only deletes requests where `r.member == member`, i.e. requests *originated* by the removed member, and clears `num_requests_pk` for that member: [2](#0-1) 

It never inspects or removes entries in `self.confirmations` for requests originated by *other* members that the removed member had merely confirmed (added their identifier to the `HashSet` via the `else` branch of `confirm()` at lines 310-314). Consequently, a confirmation recorded from an account/key that has since been deleted from `self.members` remains present in `self.confirmations.get(&request_id)` and continues to count toward the `num_confirmations` threshold in the `if confirmations.len() as u32 + 1 >= self.num_confirmations` check.

This breaks the binding that the report's bug class hinges on: the multisig's execution decision should be equal to "confirmations from currently-live, currently-authorized members ≥ threshold." Instead the code allows "confirmations recorded historically (regardless of current membership) ≥ threshold" to trigger execution — exactly the "confirmations counted versus live members" divergence called out as in-scope.

### Impact Explanation
This crosses the Critical impact bucket "a multisig request executed below threshold." A pending request that has fewer confirmations from *currently* authorized members than `num_confirmations` can still be pushed to execution — including `Transfer`, `FunctionCall`, `AddKey`, `AddMember`/`DeleteMember` actions — because a stale confirmation from a departed member is silently counted. This can let a malicious or compromised action execute (e.g. draining funds via `Transfer`, or adding an attacker-controlled key/member) with effectively fewer live approvals than the multisig's own security parameter guarantees.

### Likelihood Explanation
This requires no exotic conditions: any normal operational sequence where (a) a member confirms a pending request that does not yet meet the threshold, and (b) that member is later removed via a legitimate `DeleteMember` action (itself confirmed through the normal multisig flow) triggers the bug — the stale confirmation is never cleaned up. Multisig membership changes (onboarding/offboarding signers) are an expected, routine multisig operation, making this readily reachable in normal usage rather than a purely theoretical edge case.

### Recommendation
When executing `DeleteMember`, also scan `self.confirmations` for every pending `request_id` and remove the deleted member's entry from each confirmation set (not just requests they originated). Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set against `self.members` (i.e., only count confirmations from accounts/keys still present in `self.members`) before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract` with members `{A, B, C, D, E}` and `num_confirmations = 3`.
2. Member `A` calls `add_request` to create request `R` (e.g. `Transfer` of funds), then `A` calls `confirm(R)` — `confirmations[R] = {A}`.
3. Member `B` calls `confirm(R)` — `confirmations[R] = {A, B}` (2 < 3, not yet executed).
4. Via a separate, properly-confirmed multisig request, `A` is removed (`DeleteMember { member: A }`) — `delete_member()` runs; since `R` was not originated by `A` (it was originated by `A` in this scenario — pick a variant where `A` confirmed but did not originate, e.g. request originated by `B`), `R` is untouched and `confirmations[R]` still contains `A`.
5. Member `C` (a live, legitimate member) calls `confirm(R)` — `confirmations[R].len() + 1 == 3 >= num_confirmations`, so `execute_request(R)` runs.
6. `R` executes with confirmations from `{A, B, C}`, but `A` is no longer a member — only 2 live members (`B`, `C`) actually authorized it, one below the required threshold of 3. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
