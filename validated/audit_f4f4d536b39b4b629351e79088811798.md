### Title
Miner can indefinitely refresh `last_activity_time` with rejected reorg proposals to suppress `is_timed_out`, wedging signers into never accepting the previous miner's tenure-extend - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionState::is_timed_out` (used by `check_miner_inactivity` to decide whether the previous miner may extend its tenure) treats a tenure as active as long as `signer_db.get_last_activity_time` is recent [1](#0-0) . That timestamp is refreshed inside `check_latest_block_in_tenure` whenever a proposal fails to confirm enough blocks, *unconditionally* if the last known block in the tenure hasn't reached `signed_group` (globally-signed) state yet [2](#0-1) . This mirrors the TrueFi report's pattern: a cheap, individually-legitimate-looking action (a short-lived loan / a re-proposed block) performed by a single privileged actor (an allowed borrower / the current sortition-winning miner) manipulates a shared, mutable state value (pool liquidity / `last_activity_time`) immediately ahead of the decision that reads it (`liquidExitPenalty` / `is_timed_out`), biasing that decision in the attacker's favor without breaking any single explicit validity rule.

### Finding Description
`check_latest_block_in_tenure` is the shared chainstate check run at proposal arrival, at validate-ok, and at signing time (see `docs/signer-flows.md` section 7) [3](#0-2) . When a proposed block's `chain_length` does not exceed the highest known signed block in the tenure, the function rejects it, but first decides whether to still count it as "miner activity":

```
if info.signed_group.is_none_or(|signed_time| {
    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
}) {
    // ... update_last_activity_time
}
``` [4](#0-3) 

`Option::is_none_or` returns `true` unconditionally when `signed_group` is `None`. Since a block only reaches `signed_group` once the network-wide signature threshold is met (a `LocallyAccepted`/`PreCommitted` block has no `signed_group` timestamp), any tenure that has not yet produced a *globally signed* block will treat **every** rejected reorg-style re-proposal as valid activity, with no freshness bound at all. The current sortition winner - a single actor requiring no majority, no signer collusion, and no extra key or auth-token access - can therefore keep sending doomed/duplicate proposals (chain length ≤ the last known one) purely to call `update_last_activity_time` and reset the clock `is_timed_out` reads [5](#0-4) .

This directly defeats the purpose of `block_proposal_timeout`/`check_miner_inactivity`: the mechanism exists specifically so the *previous* miner can extend its tenure once the new sortition's winner is judged inactive (see the `block_proposal_timeout_ms` documentation and `check_miner_inactivity`) [6](#0-5) . As long as the malicious current miner periodically resubmits a stale/rejected proposal faster than `block_proposal_timeout`, `is_timed_out` never returns `true`, so `check_miner_inactivity` never triggers reversion to the prior tenure, and the previous miner's `TenureChangeCause::Extended` block is never accepted. The chain stalls in the malicious miner's tenure until the next sortition, with no path for the honest previous miner to intervene - the exact `check_miner_inactivity`/tenure-extend fallback that the codebase's own changelog notes (`no-fallback-to-stopped-miner.fixed`, `precommit-suppresses-miner-timeout.fixed`) show is treated as a safety-critical liveness guarantee that has previously needed hardening [7](#0-6) .

### Impact Explanation
This is a liveness wedge triggerable by a single one-slot miner (the current sortition winner) via ordinary gossip of block proposals, requiring no majority of signers, no other signer's key, and no auth-token access. It fits the "signer wedged into never signing valid blocks" category: signers never mark the disruptive current miner as `InvalidatedBeforeFirstBlock`, so the honest previous miner's tenure-extend is perpetually rejected, and the chain cannot progress until the next Bitcoin sortition changes the miner set.

### Likelihood Explanation
The precondition ("tenure has not yet produced a globally-signed block") is common: it is true throughout any tenure until the very first block clears the 70% signature threshold, and it re-arises whenever a miner deliberately withholds/never proposes a block that reaches quorum. All the attacker needs is to be the legitimate sortition winner for that tenure and periodically broadcast any previously-known/stale proposal (which is trivially replayable and costs no stake) before `block_proposal_timeout` elapses.

### Recommendation
Bound the "no `signed_group`" branch with the same freshness window (`reorg_attempts_activity_timeout`) applied to the `Some(signed_time)` branch, e.g. compare against `approved_time`/`proposed_time` rather than unconditionally granting activity credit whenever `signed_group` is absent, so that a stream of rejected re-proposals cannot indefinitely suppress `is_timed_out`.

### Proof of Concept
1. Miner A wins the sortition for tenure T and locally proposes block N (only reaches `LocallyAccepted`/`PreCommitted`, never `GloballyAccepted`, e.g. by controlling network delivery so quorum is never reached).
2. Every `block_proposal_timeout - ε`, miner A rebroadcasts a stale proposal at height ≤ N (or re-sends N itself). Each time, `check_latest_block_in_tenure` rejects it for insufficient chain length but calls `signer_db.update_last_activity_time` because `info.signed_group` is `None` [4](#0-3) .
3. `SortitionState::is_timed_out` keeps observing a recent `last_activity_time` and returns `false` on every `check_miner_inactivity` pass [8](#0-7) .
4. The previous miner's tenure-extend proposal is therefore always rejected by `check_latest_block_in_tenure`/`check_proposal`, and tenure T never advances past N nor falls back to the previous miner, stalling the chain until the next sortition.

        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,

        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.

        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

            return Ok(false);

                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );

`check_latest_block_in_tenure` answers "does this block confirm the tip we
expect?" and it runs in three places: at proposal arrival (inside
`check_proposal`), at validate-ok, and at the moment of signing. _Which_ tenure
