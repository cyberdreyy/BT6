### Title
`ExportDKGResult` discloses DKG result package hex data for any InstanceID without verifying requester association with the ceremony - ([File: core/web/vault_controller.go])

### Summary
`VaultController.ExportDKGResult` looks up a DKG result package purely by the `instanceId` string supplied in the request body and returns the full hex-encoded `ReportWithResultPackage` to the caller, with no check that the authenticated session/user is tied to the DKG ceremony that produced that instance. Any authenticated edit-role user who can guess or enumerate `instanceId` values can exfiltrate another tenant's/ceremony's DKG result package.

### Finding Description
`ExportDKGResult` decodes the request body into `ExportDKGResultRequest{InstanceID}`, validates only that the field is non-empty, then calls `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage(ctx, dkgocrtypes.InstanceID(req.InstanceID))` and returns the package unconditionally to whoever made the request: [1](#0-0) 

There is no authorization check binding the `instanceId` to the requesting session/tenant — the handler only checks that the record exists (`v != nil`) before serializing `hexPackage := hex.EncodeToString(v.ReportWithResultPackage)` into the JSON response via `presenters.NewExportDKGResultResource`. Because the lookup key (`InstanceID`) is attacker-suppliable and no ownership/ACL predicate is applied on the ORM read, any caller who reaches this handler with a valid edit-role session can retrieve the result package for any instance ID they can guess or enumerate, regardless of whether they participated in or own that DKG ceremony. Note that `VerifyDKGResult` (same file) has the same unconditional lookup pattern, but only returns a SHA-256 hash, not the raw package — it does not leak the underlying secret material.

### Impact Explanation
This matches Chainlink's "sensitive information disclosure" / secret confinement violation bounty class: an edit-role user without any relationship to a given DKG ceremony can retrieve the raw `ReportWithResultPackage` bytes (potentially containing encrypted DKG key shares) for that ceremony by supplying its `instanceId`. This breaks tenant/ceremony isolation for Vault DKG artifacts.

### Likelihood Explanation
Exploitation only requires an authenticated session with edit role (no special privilege beyond what's needed to reach any other Vault route) and knowledge/guessability of an `instanceId` string. If `instanceId` values are predictable, sequential, or discoverable through other Vault/DKG API responses or logs, exploitation is straightforward and repeatable, since the endpoint performs no ownership check at all — it is deterministic and reproducible via a single POST request.

### Recommendation
Add an authorization check in `ExportDKGResult` (and audit `VerifyDKGResult`/other DKG-result-consuming handlers similarly) that verifies the authenticated caller/tenant is associated with the DKG ceremony identified by `instanceId` before returning `ReportWithResultPackage`. This could be implemented by storing an owner/tenant reference alongside the result package in the Vault ORM and comparing it against the caller's identity extracted from the session before serving the response.

### Proof of Concept
Go handler-level integration test plan:
1. Seed the Vault ORM directly (`vault.NewVaultORM(db).WriteResultPackage(ctx, "secret-instance", <bytes>)`) to simulate a DKG result belonging to Tenant A / Ceremony A.
2. Construct an HTTP test request as an authenticated edit-role user with no relation to `secret-instance` (Tenant B credentials/session), POST to `/v2/vault/dkg_results/export` with `{"instanceId": "secret-instance"}`.
3. Assert current behavior: response status 200 and JSON body's `attributes.hexPackage` equals the hex encoding of the seeded bytes — demonstrating unconditioned disclosure.
4. After the fix, assert the same request returns 403/404 (no ownership match) and the package bytes are never returned to Tenant B's session, using `core/web/vault_controller_test.go` as the existing test file to extend with this ownership-check scenario. [2](#0-1)

```go
func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
```
