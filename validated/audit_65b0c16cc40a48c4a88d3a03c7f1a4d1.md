### Title
Stale rejection weight is never retired when a signer flips to acceptance, letting phantom rejection weight force a false `SignersRejected` verdict - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side StackerDB listener tallies `total_weight_approved` and `total_weight_rejected` independently, with no mechanism to retract a signer's earlier rejection weight when that same signer later legitimately flips to acceptance (a transition the signer state machine explicitly permits and relies on for liveness). This breaks the aggregated-weight-vs-verified-current-view equality the coordinator depends on to decide whether a block is dead.

### Finding Description
On the signer side, `BlockInfo::check_state` explicitly allows a block to move `LocallyRejected -> LocallyAccepted` (and vice versa) as long as neither side is already global: [1](#0-0) 

This transition is not theoretical — it is the documented and tested mechanism by which a signer recovers liveness after rejecting a block due to a stale/conflicting sibling, then later signs the same block once the conflict resolves (`stale_sibling_replaced_when_canonical_tip_below`): [2](#0-1) 

Crucially, the signer's own `SignerDb` correctly reconciles the two sides: `add_block_signature` deletes any prior rejection row for that signer/block before inserting the acceptance, so a signer's local weight bookkeeping is never double-tallied across reject and accept: [3](#0-2) [4](#0-3) 

The node-side coordinator (`stackerdb_listener.rs`), however, tallies each `BlockResponse` into two *independent* counters with no cross-invalidation. When a `Rejected` message arrives, the slot is added to `responded_signers` (a `HashSet`) and its weight is permanently folded into `total_weight_rejected`: [5](#0-4) 

When an `Accepted` message later arrives from the *same* signer for the *same* block (the legitimate reject→accept flip described above), the code only checks `gathered_signatures.contains_key(&slot_id)` — not whether that slot previously rejected — and adds the weight to `total_weight_approved` as well, with nothing ever subtracted from `total_weight_rejected`: [6](#0-5) 

The `BlockStatus` struct backing this state has no field or logic to reconcile the two buckets — `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` are all independent, monotonically-increasing accumulators: [7](#0-6) 

The coordinator's wait loop then checks the (now-stale-inflated) rejection weight *before* the approval weight, and returns a hard failure the moment the rejection threshold is (spuriously) crossed: [8](#0-7) 

### Impact Explanation
This is a "miscounted response" bug explicitly in scope: the coordinator's aggregated rejection weight no longer equals the verified *current* set of rejecting signers, because it silently retains weight from signers who have since (correctly, per the signer's own state machine) switched to acceptance. Since the rejection check runs first and is terminal (`return Err(NakamotoNodeError::SignersRejected{...})`), a block that in reality already has ≥70% *current* acceptance can still be declared dead by the miner/coordinator purely because of accumulated historical (now-superseded) rejection weight from signers that have flipped sides. This wedges block production on a valid, canonical proposal that the signer set has actually converged on approving — a liveness break rooted directly in the coordinator's weight-tallying logic, not in requiring a majority of colluding signers or any StackerDB transport fault.

### Likelihood Explanation
The reject→accept flip is not an edge case requiring signer compromise: it is the documented, tested recovery path for the sibling/conflict-staleness scenario (`stale_sibling_replaced_when_canonical_tip_below`), which a single miner can trigger organically by proposing a block that conflicts with a stale sibling and then letting/forcing that conflict to go stale before the pre-commit/signature threshold is reached — entirely within the normal one-slot-miner + gossip timing that this analysis is scoped to. No majority of colluding signers, no auth token, and no StackerDB-transport tricks are needed; only ordinary timing of proposals relative to conflict staleness, which the codebase's own tests demonstrate as an expected occurrence.

### Recommendation
Track, per slot, whichever side (`Accepted`/`Rejected`) is most recent, and when a slot transitions from one side to the other, subtract its weight from the stale bucket before adding it to the new one — mirroring the reconciliation the signer already performs locally in `SignerDb::add_block_signature`/`add_block_rejection_signer_addr` (delete-then-insert on the opposite table). Concretely, `BlockStatus` should record a per-slot "current vote" enum instead of two independent weight accumulators, and both the `Accepted` and `Rejected` branches in `stackerdb_listener.rs` should look up and retract the slot's prior vote's weight before adding the new one.

### Proof of Concept
1. A miner proposes block `B1` at height `h` in tenure `T`, and simultaneously (or shortly after) a competing/conflicting sibling causes signer `S` (with weight `w`) to reject `B1` via `BlockResponse::Rejected` — this is folded into `total_weight_rejected` in `stackerdb_listener.rs` (`responded_signers.insert(slot_id)` succeeds, weight added).
2. Time passes; the conflicting sibling goes stale (per `conflict_still_blocks`/`stale_sibling_replaced_when_canonical_tip_below` logic), and signer `S` legitimately re-evaluates and signs `B1`, broadcasting `BlockResponse::Accepted`.
3. `stackerdb_listener.rs` sees `slot_id` is not yet in `gathered_signatures`, so it adds `w` to `total_weight_approved` — but `total_weight_rejected` is never decremented; `S`'s weight `w` now counts in *both* buckets permanently.
4. Repeat organically (or via miner-timed re-proposals) across enough signers whose weight sum exceeds the 30% blocking minority purely from stale rejections that have since flipped to acceptance.
5. In `signer_coordinator.rs::wait_for_block_signatures`, the `total_weight_rejected` check fires first and returns `NakamotoNodeError::SignersRejected`, even though `total_weight_approved` (computed from the same, now-updated votes) may simultaneously already be at or above `weight_threshold` — the miner is forced to abandon a block the signer set has actually converged on approving.
