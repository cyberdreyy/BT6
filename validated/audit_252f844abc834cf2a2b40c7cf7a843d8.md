### Title
Builder payment can be misdirected because `process_execution_payload_bid` never checks `bid.fee_recipient` against the proposer's `SignedProposerPreferences` - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_execution_payload_bid` unconditionally records whatever `fee_recipient` the *builder* put in the bid as the recipient of the builder payment. The only place the protocol checks that this address matches the proposer's declared preference is an advisory, non-authenticated `[IGNORE]` rule in gossip validation — it is never enforced by the state-transition function that all honest nodes run when applying a block.

### Finding Description
A builder constructs `bid.fee_recipient` itself (`specs/gloas/builder.md:134-139`) and signs the whole bid with its own key: [1](#0-0) 

The proposer is instructed to only accept bids that satisfy the conditions enumerated for `process_execution_payload_bid`: [2](#0-1) 

That list checks signature validity, self-build rules, builder balance, slot, `parent_block_hash`, `parent_block_root`, and `prev_randao` — it never requires `bid.fee_recipient == proposer's declared SignedProposerPreferences.fee_recipient`. Correspondingly, the state-transition function itself, `process_execution_payload_bid` in `specs/gloas/beacon-chain.md`, records the pending payment straight from the bid with no such assertion: [3](#0-2) 

This value is later paid out verbatim through `settle_builder_payment` / `apply_parent_execution_payload` to `bid.fee_recipient` as a `BuilderPendingWithdrawal`: [4](#0-3) 

The equality `fee_recipient == proposer's requested address` is checked *only* in the p2p gossip validator, and only as a soft `[IGNORE]` (not `[REJECT]`), meaning it is not a block-validity/consensus rule at all — it just throttles gossip relay: [5](#0-4) 

Because the validator spec explicitly permits obtaining the signed bid "by other off-protocol means" (bypassing gossip validation entirely) and because `process_execution_payload_bid`'s own verification list omits the fee-recipient equality, a bid whose builder-chosen `fee_recipient` diverges from what the proposer actually asked for in its `SignedProposerPreferences` is fully valid at the consensus layer and every honest node will accept and settle it. This is the exact analog of the reported bug class: an attacker-controlled field (`fee_recipient`, standing in for the unencoded path variable) is trusted and used to redirect an authenticated payment/action to a destination the field's real target (the proposer) never approved through any protocol-enforced channel — the equality "payment recipient == entity the block is supposed to compensate" is broken.

### Impact Explanation
This lets a builder pay itself (or any third party) instead of the proposer whose slot it is bidding for, while the bid still validates in `process_execution_payload_bid` and the payment is still settled by the state transition. That is a builder payment "misdirected" — the honest proposer that accepted a seemingly valid, well-signed, sufficiently-funded bid receives nothing (or a different amount to a different address than agreed), matching the "High" impact bucket ("a builder payment or withdrawal misdirected").

### Likelihood Explanation
Exploitability depends on how proposer client software sources bids: any implementation that follows the letter of `process_execution_payload_bid`'s conditions (as literally enumerated in `validator.md`) without independently re-verifying `fee_recipient` against its own preferences — or that accepts bids via non-gossip channels (explicitly allowed by the spec) where the gossip-layer `[IGNORE]` filter never runs — is exploitable by any single active builder with sufficient balance, with no coalition, no majority stake, and no client bug required.

### Recommendation
Add an explicit `assert bid.fee_recipient == <proposer's committed fee_recipient for this slot>` inside `process_execution_payload_bid` (or otherwise cryptographically bind the accepted `SignedProposerPreferences` into the block/state so the consensus rule — not just the optional gossip filter — enforces the equality), so that the payment recipient is a protocol-enforced invariant rather than an off-chain convention.

### Proof of Concept
1. Proposer P for slot `s` broadcasts `SignedProposerPreferences` with `fee_recipient = A`.
2. Malicious builder B constructs `bid` with `bid.fee_recipient = B_address` (its own address) instead of `A`, signs it correctly, and sends it directly to P off-gossip (permitted per `validator.md:201-203`), or P's software simply doesn't re-check the field before inclusion.
3. P includes `signed_execution_payload_bid` in its block. `process_execution_payload_bid` runs the checks in `specs/gloas/beacon-chain.md:2087-2141`; none of them compare `bid.fee_recipient` to `A`. The pending payment is recorded with `fee_recipient = B_address`.
4. `settle_builder_payment`/`apply_parent_execution_payload` later create a `BuilderPendingWithdrawal(fee_recipient=B_address, amount=bid.value, ...)` (`specs/gloas/beacon-chain.md:1764-1770`), and the withdrawal sweep pays `B_address`, not `A`. The block is fully valid to every spec-following node; the "equality" that the builder payment reaches the proposer who was promised it is broken.
