## Finding

### Title
Stale rejection weight from a signer that later accepts is never cleared, corrupting the aggregated-weight tally in the block coordinator - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
This is the same bug *class* as the reported `PolicyProposals.registerProposal` issue: a value (there, the registration fee; here, a signer's rejection weight) gets added into one aggregate tally and is never removed or reconciled when the underlying fact it represents changes, so it silently persists and gets counted alongside a later, contradictory tally for the same actor. Here, a signer's weight can end up counted in *both* `total_weight_rejected` and `total_weight_approved` for the same block, breaking the "aggregated-weight vs verified-accepts" equality that the mining coordinator relies on.

### Finding Description
`stackerdb_listener.rs` tracks per-block consensus via `BlockStatus`, which independently accumulates `total_weight_approved` and `total_weight_rejected` [1](#0-0) .

When a `Rejected` response arrives, the code gates on `responded_signers.insert(slot_id)` — i.e., "have we ever heard from this slot before at all" — and adds the signer's weight to `total_weight_rejected` [2](#0-1) .

When an `Accepted` response later arrives for the *same signer/same block*, the guard used is `!gathered_signatures.contains_key(&slot_id)` — a completely independent set from `responded_signers` — so the weight is added to `total_weight_approved` regardless of whether that slot previously contributed to `total_weight_rejected` [3](#0-2) . Nothing subtracts the stale weight out of `total_weight_rejected` when this happens.

This flip is not exotic — the signer protocol explicitly allows a signer to reconsider and change a prior rejection for certain reject reasons (`should_reevaluate_reject_reason`), so a single honest signer naturally produces "Reject → later Accept" traffic for the same block during normal operation [4](#0-3) .

The only place `total_weight_rejected` is ever cleared is `reset_rejections`, which is explicitly invoked only on a `SignatureTimeout` retry path — not on receipt of a superseding `Accepted` message from the same signer [5](#0-4) .

The coordinator polling loop in `signer_coordinator.rs` checks the rejection condition *before* the acceptance condition on every iteration: if `total_weight_rejected + weight_threshold > total_weight` it declares the block rejected outright — otherwise it checks the acceptance threshold [6](#0-5) . Because a signer's weight can now be double-booked (once as stale rejection, once as real acceptance), the sum of *other* signers' honest rejections plus this stale leftover weight can cross the blocking-minority line even while enough real, currently-valid signatures exist (or would soon exist) to legitimately accept the block.

### Impact Explanation
This corrupts the "aggregated-weight vs verified-accepts" equality the coordinator depends on to make binary accept/reject decisions about a block. A block that a supermajority of *current* signer weight is willing to sign can be wrongly declared globally rejected (`SignersRejected`) purely because of leftover weight from a signer who has since reconsidered — this is a liveness wedge on the mining side: valid tenure blocks get needlessly discarded/retried, and `permanently_excluded_txids`/`temporarily_excluded_txids` bans can be miscomputed based on the same corrupted per-txid weight bookkeeping pattern.

### Likelihood Explanation
Only a single signer needs to legitimately reconsider a prior rejection for the same block, which is an intended and documented behavior of the protocol (`should_reevaluate_reject_reason`), not a majority-collusion or externally-injected fault. No signing key compromise or auth_token access is required — normal signer message traffic triggers it.

### Recommendation
Track approval/rejection per slot_id using a single reconciled state (e.g., replace independent `responded_signers`/`gathered_signatures` bookkeeping with one map from `slot_id` to the signer's *current* vote), and when a slot transitions from Rejected to Accepted (or vice versa), subtract the stale weight from the superseded tally before adding to the new one, mirroring the existing intent already implemented on the `stacks-signer` side (see `CHANGELOG.md`: "Do not count both a block acceptance and a block rejection for the same signer/block") [7](#0-6) .

### Proof of Concept
1. Coordinator proposes block B; signer S sends `Rejected` (e.g., stale chainstate check) → `total_weight_rejected += weight(S)`.
2. Other signers push rejection weight close to (but not over) the blocking-minority line.
3. S re-evaluates B under `should_reevaluate_reject_reason` and now sends `Accepted` → `total_weight_approved += weight(S)` via the `gathered_signatures` guard; `total_weight_rejected` is untouched.
4. On the next poll, `total_weight_rejected` (still including S's stale weight) + `weight_threshold > total_weight` fires first, and the coordinator declares the block `SignersRejected` even though S's real, current vote is Accept and total legitimate approving weight may in fact reach 70%.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
