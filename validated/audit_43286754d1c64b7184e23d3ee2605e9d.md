## Title
Removing a multisig member does not revoke their existing confirmations, allowing a request to execute with fewer than `num_confirmations` live-member approvals - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges the outstanding *requests* that were created by the removed member; it never removes that member's already-recorded *confirmations* on requests created by other, still-active members. Because `confirm()` counts entries in the `confirmations` `HashSet<String>` without re-validating that each entry still corresponds to a current member, a confirmation cast by a member who is later deleted continues to count toward `num_confirmations`. This lets a coalition smaller than the configured threshold execute a request (e.g. a `Transfer`), i.e. a multisig request can execute below the intended threshold.

### Finding Description
`confirm()` determines whether to execute a request purely by comparing the size of the stored `confirmations` set to `self.num_confirmations`: [1](#0-0) 

The set is populated with `member.to_string()` for whichever member calls `confirm`, with no dependency on that member remaining in `self.members` at execution time.

`delete_member` (invoked only via the self-request `MultiSigRequestAction::DeleteMember`) is the only place that mutates `confirmations` in response to membership changes, but it only removes requests keyed by the removed member (i.e. requests *they authored*), not the removed member's *confirmation entries on other requests*: [2](#0-1) 

Compare this to `add_request`/`confirm`, which strictly gate participation on current membership via `current_member()`: [3](#0-2) 

So the binding that should hold is:
`confirmations.len() (of members that are still in self.members) == effective approvals counted in confirm()`

After a member is deleted, this equality breaks: a stale confirmation from a now-non-member is still counted in `confirmations.len()`, inflating the effective approval count above what live members actually granted — analogous to the report's pattern where an authorization check (`_whitelist`/membership) enforced in one path (`stake()`/`add_request`,`confirm`'s initial gate) is not re-enforced in a related path (`queueWithdrawal()`/subsequent counting after membership changes).

### Impact Explanation
This is a Critical-severity issue per the rubric ("a multisig request executed below threshold"): a request meant to require `K` live signatures can be executed with fewer than `K` currently-authorized approvals, because one or more of the counted confirmations belong to accounts/keys that have since been removed from the multisig. In the worst case this allows a smaller-than-quorum set of current members to move funds (`Transfer`) or otherwise act on behalf of the multisig account, breaking the fundamental K-of-N custody guarantee of the contract.

### Likelihood Explanation
The scenario requires only ordinary multisig operations, no external contract or malicious node:
1. A request `R` (e.g., `Transfer`) is created by member `A` and confirmed by member `M`, bringing `R`'s confirmation count to some value `c < num_confirmations`.
2. Separately (and later), the multisig, via a normal `DeleteMember` request, removes `M` (e.g., because a key was compromised, an employee left, or governance rotated members). `delete_member` clears requests authored by `M`, but `R` (authored by `A`) is untouched — `R`'s confirmation set still contains `M`.
3. Any current member confirms `R` again; because `confirmations.len() as u32 + 1 >= self.num_confirmations` only checks set size, the stale entry from removed member `M` plus one live confirmation can reach the threshold even though only 2 truly-live members (not `K`) approved.

This requires no special privilege beyond normal multisig membership and no attacker-controlled external call; it is a straightforward state-machine gap reachable through ordinary contract usage (create request → confirm → later remove a different member → confirm again).

### Recommendation
When executing `DeleteMember` (and symmetrically whenever membership changes), iterate over all outstanding requests' `confirmations` sets and remove any confirmation entries belonging to the removed member, not just requests they authored. Alternatively, revalidate confirmation set membership against `self.members` at `confirm()` time before comparing against `num_confirmations`, discarding stale entries so only currently-valid members' confirmations are counted.

### Proof of Concept
Given multisig with `num_confirmations = 3` and members `{A, B, M, C}`:
1. `A.add_request(Transfer{...})` → `request_id = R`.
2. `B.confirm(R)` → confirmations = `{B}` (len 1).
3. `M.confirm(R)` → confirmations = `{B, M}` (len 2, still `< 3`, so not yet executed).
4. Separately, members reach quorum on a `DeleteMember{member: M}` request and it executes: `delete_member` removes `M` from `self.members`, deletes requests where `r.member == M` (not `R`, which was authored by `A`), and removes `M`'s `num_requests_pk` entry — but leaves `R`'s `confirmations` set as `{B, M}` untouched.
5. `C.confirm(R)`: `confirmations.len() as u32 + 1 = 3 >= num_confirmations (3)` → `execute_request` runs `Transfer`, even though only `B` and `C` are current, live members who approved (2 live confirmations, not the required 3). [4](#0-3) [5](#0-4) 

Note: `multisig/src/lib.rs` (the older key-only multisig) has the analogous limitation in `DeleteKey` handling within `execute_request`, which likewise only purges requests authored by the deleted key, not that key's confirmations on other requests — the same root-cause pattern applies there as well. [6](#0-5)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
