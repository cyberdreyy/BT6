### Title
CostTracker::remove_transaction_cost() never evicts zero-cost entries from `cost_by_writable_accounts`, allowing unbounded per-slot HashMap growth - (File: cost-model/src/cost_tracker.rs)

### Summary
`CostTracker` tracks compute-unit cost per writable account in a `HashMap<Pubkey, u64>` (`cost_by_writable_accounts`) that is consulted on every transaction to enforce per-account and per-block compute limits. Entries are added via `entry(*account_key).or_insert(0)` whenever a transaction's cost is applied, but the corresponding removal path (`remove_transaction_cost` / `sub_transaction_execution_cost`) only decrements the stored value with `saturating_sub`, and never calls `HashMap::remove()` on the key. This is functionally the same defect pattern as the referenced `PP_Streaming_v1._findAddressInActiveStreams()` finding: an accounting map that only grows because removal logic clears the "value" but leaves the "key" behind forever.

### Finding Description
`add_transaction_execution_cost` inserts an entry per writable account touched by a transaction: [1](#0-0) 

The counterpart, `sub_transaction_execution_cost`, is supposed to reverse this when a transaction's cost is retracted (e.g. after a failed/retried transaction in banking stage or unified-scheduler cost accounting). It only zeroes the value via `saturating_sub`, but keeps the `Pubkey` key resident in the map indefinitely: [2](#0-1) 

Because the map's key set is never pruned, any code path that adds-then-removes a transaction's cost for a *new, unique* writable account (a normal part of transaction lifecycle — e.g., a transaction is tentatively costed, then reverted because it fails execution, is dropped for account-in-use, or fails other post-checks) leaves a permanent stale entry with value `0`. Only `find_costliest_account` and `find_number_of_contended_accounts` iterate the whole map, and `number_of_accounts()` filters for non-zero values, confirming that stale zero entries are expected to exist but are never cleaned up: [3](#0-2) [4](#0-3) 

The initial capacity hint of `WRITABLE_ACCOUNTS_PER_BLOCK = 4096` is only a pre-allocation hint, not an enforced cap: [5](#0-4) [6](#0-5) 

An ordinary user can drive this growth simply by submitting many transactions that each touch a distinct, never-before-seen writable account and that are subsequently reverted from the cost tracker (e.g. transactions that pass `would_fit`/get tentatively added by the scheduler and are later removed due to execution failure, conflict, or being dropped/retried). Each such add/remove round-trip nets zero effect on the enforced `block_cost`/`account_cost` budgets — so it does not consume the compute-unit limits that would otherwise bound the number of iterations — yet it permanently grows `cost_by_writable_accounts` for the lifetime of that `CostTracker` instance. Because `find_costliest_account`, `would_fit`'s per-account lookup path, and `find_number_of_contended_accounts` are called on the hot path for essentially every transaction, an inflated map degrades lookup/iteration performance and increases per-transaction memory pressure.

### Impact Explanation
This is a resource-exhaustion / performance-degradation issue rather than a fund-theft bug: an attacker who can cheaply generate large numbers of distinct pubkeys and get their costs added-then-reverted from a live `CostTracker` can inflate its backing `HashMap` far beyond the nominal `WRITABLE_ACCOUNTS_PER_BLOCK` sizing assumption, without ever being charged the corresponding compute-unit cost. This increases per-transaction processing latency (hash lookups, iteration in `find_costliest_account`/`find_number_of_contended_accounts`) and memory usage for as long as the affected `CostTracker` instance is retained, degrading throughput for the block-producing/replay path that depends on it. Impact severity depends on how long-lived the specific `CostTracker` instance is (per-bank instances reset each slot via `new_from_parent_limits`, limiting exposure to a single slot; longer-lived instances used for cross-slot QoS tracking would accumulate the bloat across many slots).

### Likelihood Explanation
Likelihood is moderate: reaching this path requires only ordinary, unprivileged transaction submission that results in a cost-tracker add followed by a remove for distinct accounts — a normal occurrence for failed/retried/dropped transactions in banking stage and the unified scheduler's cost accounting. No special privileges, deployed programs, or consensus-level access are required, though the practical DoS magnitude is bounded by how many "add-then-revert" cycles an attacker can force per `CostTracker` lifetime and by whatever instance-reset cadence applies to the particular `CostTracker` in question.

### Recommendation
In `sub_transaction_execution_cost` (and `remove_transaction_cost`), remove the account entry from `cost_by_writable_accounts` when its cost reaches zero (e.g., `if let Entry::Occupied(e) = self.cost_by_writable_accounts.entry(*account_key) { if *e.get() == 0 { e.remove(); } }` after the subtraction), mirroring the pattern already used in `runtime/src/prioritization_fee.rs::prune_irrelevant_writable_accounts`, which explicitly prunes zero/irrelevant entries to bound memory.

### Proof of Concept
1. Instantiate/observe a `CostTracker` used for a slot/block.
2. For N distinct, never-before-used `Pubkey`s, build a minimal-cost transaction writing to that pubkey and call `try_add`/`add_transaction_cost`, then immediately call `remove`/`remove_transaction_cost` for the same transaction (this mirrors what happens when a scheduled transaction is subsequently rejected/reverted).
3. Observe that `cost_by_writable_accounts.len()` (and thus map capacity/memory) grows monotonically with N even though `block_cost()` returns to its pre-test value each time, confirming the map key set is never pruned as demonstrated by the existing test `test_remove_transaction_cost`, which only asserts `block_cost`/`transaction_count` return to zero and never asserts `cost_by_writable_accounts.len() == 0`: [7](#0-6)

    fn find_costliest_account(&self) -> (Pubkey, u64) {
        self.cost_by_writable_accounts
            .iter()
            .max_by_key(|(_, cost)| **cost)
            .map(|(&pubkey, &cost)| (pubkey, cost))
            .unwrap_or_default()

    fn find_number_of_contended_accounts(&self) -> usize {
        // accounts has more than 95% of account_cu_limit is considered as highly contended
        let contended_cost_mark: u64 = self
            .limits
            .account_cost
            .saturating_mul(95)
            .saturating_div(100);

        self.cost_by_writable_accounts
            .values()
            .filter(|&&cost| cost >= contended_cost_mark)
            .count()
    }

    fn add_transaction_execution_cost(
        &mut self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
        adjustment: u64,
    ) -> u64 {
        let mut costliest_account_cost = 0;
        for account_key in tx_cost.writable_accounts() {
            let account_cost = self
                .cost_by_writable_accounts
                .entry(*account_key)
                .or_insert(0);
            *account_cost = account_cost.saturating_add(adjustment);
            costliest_account_cost = costliest_account_cost.max(*account_cost);
        }
        self.block_cost.fetch_add(adjustment);

        costliest_account_cost
    }
