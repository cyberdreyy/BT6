### Title
Stale confirmations from removed members count toward the confirmation threshold, allowing a `Transfer` request to execute with fewer than `num_confirmations` live approvers - (File: `multisig2/src/lib.rs`)

### Summary
`multisig2`'s `confirm()` counts entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` map to decide whether a request has reached `num_confirmations`. When a member is removed via `DeleteMember`, `delete_member()` only purges requests that the removed member *originated* (`r.member == member`); it never scrubs that member's approvals from the `confirmations` set of *other* still-pending requests. A confirmation cast by a member who is later removed therefore keeps counting toward the threshold, letting a currently live member finish and execute a `Transfer` (or any other request) with fewer genuinely-authorized approvals than `num_confirmations` requires. This is the same class of "recorded claim vs. actual entitlement" bug the external report flags in `CoverPool.addCover` (trusting a recorded value instead of verifying it against the real, current state) - here the recorded confirmation count diverges from the real, current set of authorized members.

### Finding Description
`confirm()` never re-validates that previously stored confirmations still belong to current members: [1](#0-0) 

`delete_member()` only cleans up requests *created by* the removed member, and removes that member's `num_requests_pk` bookkeeping entry, but does nothing to the `confirmations` map entries of other requests that the removed member previously confirmed: [2](#0-1) 

Because `confirmations` is a plain `HashSet<String>` keyed by request id, and membership is only checked at the moment a *new* confirmation is added (`assert(!confirmations.contains(&member.to_string())...)`), an old confirmation string that belonged to a now-deleted member is never invalidated. The threshold check in `confirm()` (`confirmations.len() as u32 + 1 >= self.num_confirmations`) treats that stale entry exactly like a confirmation from a live member.

The invariant that should hold is:
`num_confirmations_required == number of *currently authorized* members who approved`

but the code actually enforces:
`num_confirmations_required == |confirmations set|` (regardless of whether each entry is still a current member)

This is the "confirmations counted versus live members" custody binding explicitly called out as in-scope, and it is broken.

### Impact Explanation
This allows execution of any `MultiSigRequestAction`, including `Transfer` (moving NEAR out of the multisig account) or `AddKey`/`FunctionCall`, with only `num_confirmations - 1` (or fewer) truly live approvers, plus one stale confirmation from a member who has since been removed (e.g., because their key was compromised, or they left the organization). This is a "multisig request executed below threshold" - explicitly listed as a Critical-severity impact in the scope rules, since NEAR custody controlled by the multisig can be moved without the intended K-of-N live authorization.

### Likelihood Explanation
This requires no attacker-side exploitation of the removed member's key after removal - the stale confirmation was legitimately cast while that member was still authorized. The only precondition is the routine, expected lifecycle event of removing a member (`DeleteMember`) while a request that member had confirmed (but not created) is still pending. Given `REQUEST_COOLDOWN` is only 15 minutes and requests can remain outstanding, and member turnover (offboarding a departing or compromised signer) is a normal multisig operation, this scenario is readily reachable without any privileged or out-of-scope actor (foundation, owner, victim key theft, redeploy). Any remaining member can simply wait for a stale confirmation to exist and then supply the final confirmation.

### Recommendation
When a member is deleted, purge that member's entry from the `confirmations` set of every request they had confirmed, not just requests they authored, e.g. iterate `self.confirmations` (or maintain a reverse index) and remove `member.to_string()` from each set. Alternatively, when checking the threshold in `confirm()`, filter `confirmations` to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `multisig2` with `num_confirmations = 2` and members `M1, M2, M3`.
2. `M1` calls `add_request` with a `Transfer { amount }` request `R` sending funds to an `M1`-controlled account. `R.member = M1`; `confirmations[R] = {}`.
3. `M2` calls `confirm(R)`. `confirmations[R] = {M2}` (len 1 < 2, not executed yet).
4. Through the normal, legitimate multisig flow (a separate request + confirmations from `M1`/`M3`), `M2` is removed via `DeleteMember { member: M2 }`. `delete_member()` only removes requests where `r.member == M2` - since `R.member == M1`, `R` and its `confirmations[R] = {M2}` are left untouched. Now `members = {M1, M3}`, `num_confirmations` still `2`.
5. `M1` calls `confirm(R)`. `confirmations[R].len() == 1` (stale `M2`) `+ 1 == 2 >= num_confirmations(2)`, so `execute_request` runs `promise.transfer(amount)` immediately.
6. Result: the `Transfer` executes with approval from only one currently-authorized member (`M1`) plus one stale confirmation from the removed `M2`, violating the intended 2-of-N live-member authorization and moving NEAR out of the multisig account.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
