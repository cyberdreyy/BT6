### Title
CORS Origin Wildcard Suffix-Matching Allows Domain-Confusion Bypass of Gateway Allowlist - (File: core/services/gateway/network/httpserver.go)

### Summary
The Chainlink gateway's user-facing HTTP server (`UserServerConfig`, the internet-facing endpoint used by unprivileged clients to submit JSON-RPC requests) enforces an origin allowlist via `isAllowedOrigin`. The wildcard-matching branch uses a naive `strings.HasSuffix` string comparison without verifying a label/dot boundary, allowing an attacker-controlled domain that merely ends with the same characters as an allowed suffix (but is a completely different, unrelated domain) to be treated as an allowed origin. This is the same bug class as the external report: an origin-allowlist implementation with an insufficiently strict format/boundary check that lets unintended origins bypass the intended restriction.

### Finding Description
`isAllowedOrigin` in [1](#0-0)  parses the request `Origin` header and each configured allowed origin into scheme/host/port via `splitURL`, then does exact host matching, plus a wildcard case:

```go
// check for wildcard host match (e.g., *.remix.com)
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [2](#0-1) 

The problem: `strings.HasSuffix(originHost, allowedHost)` performs a raw character-suffix match with no check that the preceding character in `originHost` is a `.` (i.e., no label boundary enforcement). If the operator configures `CORSAllowedOrigins = ["https://*.ethereum.org"]`, intending to allow only actual subdomains of `ethereum.org`, an attacker who registers (or already controls) a domain such as `https://evilethereum.org` will have `originHost = "evilethereum.org"`, which satisfies `strings.HasSuffix("evilethereum.org", "ethereum.org") == true`, even though `evilethereum.org` is an entirely unrelated, attacker-owned domain and not a subdomain of `ethereum.org`.

This mirrors the reported bug class exactly: the origin-enforcement logic allows domains that are not legitimately covered by the intended allowlist rule because of a missing strict boundary/format check, exactly as the report criticized regex-based checks that "allow potentially insecure subdomains" and "invalid domains."

`isAllowedOrigin` is invoked from `handleRequest`, which is the entry point for every incoming request to the gateway's user-facing HTTP server: [3](#0-2) . This server is the `UserServerConfig` HTTP endpoint of the gateway, the component that receives unauthenticated/unprivileged client (e.g., browser dApp) JSON-RPC requests as shown in the integration test config with `CORSEnabled = true` / `CORSAllowedOrigins = ["https://remix.ethereum.org"]` [4](#0-3) .

The existing test suite only validates the intended/negative-adjacent cases (`https://ethereum.remix.org` correctly rejected because it doesn't end with `ethereum.org`), but it never tests the domain-confusion case (`https://evilethereum.org` vs. `*.ethereum.org`), so this gap is not caught by current tests: [5](#0-4)  and [6](#0-5) .

### Impact Explanation
When an operator configures wildcard CORS entries (a documented, supported feature — see the wildcard test cases at [7](#0-6) ), any attacker who registers a domain ending in the same character sequence as the allowed suffix (e.g., `evilethereum.org` for `*.ethereum.org`, or `notvalid.domain.com` for `*.valid.domain.com`) can have their site's browser-based requests treated as originating from an allowed origin. This results in `Access-Control-Allow-Origin: <attacker-origin>` being reflected back with `Access-Control-Allow-Credentials`-adjacent handling, enabling cross-origin browser clients from an unrelated attacker-controlled domain to interact with the gateway's user-facing API as if they were a trusted frontend — a concrete allowlist bypass enabling cross-user/cross-origin request impersonation against the gateway.

### Likelihood Explanation
Exploitability depends entirely on the operator's configured wildcard suffix strings. Any gateway deployment that uses a `*.` wildcard entry in `CORSAllowedOrigins` (a supported and tested configuration pattern) is subject to this bypass; the attacker only needs to register a domain that happens to share the suffix characters, which is often easy to obtain (e.g., registering `evil<name>.com` when the allowed suffix is `<name>.com`). No privileged access or node compromise is required — it is purely a client-side, internet-facing request from an unprivileged origin.

### Recommendation
In `isAllowedOrigin`, when performing wildcard matching, enforce a label boundary: after stripping the `*.` prefix, verify that `originHost` either equals `allowedHost` or ends with `"."+allowedHost`, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Additionally, consider validating the configured/incoming origin strictly (reject malformed/invalid domains) and avoid allowing scheme downgrade paths, consistent with the report's broader recommendation of strict format checks and no default subdomain allowance.

### Proof of Concept
Given gateway configuration:
```toml
CORSEnabled = true
CORSAllowedOrigins = ["https://*.ethereum.org"]
```
An attacker-controlled site hosted at `https://evilethereum.org` sends:
```
OPTIONS /user HTTP/1.1
Origin: https://evilethereum.org
```
Using `isAllowedOrigin`'s logic at [2](#0-1) : `originHost = "evilethereum.org"`, `allowedHost` (after stripping `*.`) `= "ethereum.org"`. `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, so the gateway responds with `Access-Control-Allow-Origin: https://evilethereum.org`, permitting the attacker's page to make authenticated cross-origin calls against the gateway's user API as if it were a trusted `*.ethereum.org` subdomain.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}

		[]string{"https://*.ethereum.org", "https://*.valid.domain.com", "http://*.gov"})

	handler.On("ProcessRequest", mock.Anything, mock.Anything, mock.Anything).Return([]byte("response"), 200)
