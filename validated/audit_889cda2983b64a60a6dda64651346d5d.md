### Title
Unrestricted `LockupFactory::create` lets anyone squat a victim's deterministic lockup address with an attacker-controlled whitelist - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` computes the new lockup's account id deterministically from `owner_account_id` alone and lets the caller supply an arbitrary `whitelist_account_id`, with no check that the caller is the account owner or the foundation. Because the lockup subaccount name depends only on `owner_account_id`, an unprivileged attacker can win the race to create that account first and permanently install a hostile whitelist contract as the lockup's trusted staking-pool source.

### Finding Description
The binding that must hold is: `deployed_lockup(owner_account_id).staking_pool_whitelist_account_id == canonical_whitelist_or_owner_authorised_whitelist`. In practice this reduces to "only the rightful creator (the account owner or the NEAR Foundation) determines the parameters of the lockup created for `owner_account_id`."

`create` is `#[payable]` and callable by any predecessor as long as `MIN_ATTACHED_BALANCE` is attached: [1](#0-0) 

There is no `assert_called_by_foundation` or `predecessor_account_id == owner_account_id` check anywhere in `create`. The lockup account id is fully deterministic — `sha256(owner_account_id)[..20]` concatenated with the factory's account id — so for any given `owner_account_id`, exactly one account name exists and the first successful `create_account()` promise for that name wins permanently: [2](#0-1) 

`whitelist_account_id` is an attacker-supplied optional parameter that, when present, overrides the factory's canonical `self.whitelist_account_id` and is baked directly into the deployed lockup's `LockupArgs.staking_pool_whitelist_account_id`: [3](#0-2) 

Exploit flow: the attacker observes (or predicts) that a legitimate creator (e.g., the NEAR Foundation) is about to call `create(owner_account_id = V, whitelist_account_id = None)` for victim `V`. The attacker submits their own `create(owner_account_id = V, whitelist_account_id = Some(attacker_whitelist), ...)` first (or in the same block with higher priority/gas), attaching only `MIN_ATTACHED_BALANCE`. Since the resulting account name is identical, this deploys a lockup contract at `V`'s deterministic address whose `staking_pool_whitelist_account_id` points at a contract the attacker controls (which can be coded to whitelist any staking pool). The legitimate creator's subsequent `create()` call for the same `owner_account_id` then fails at `create_account()` (account already exists), and `on_lockup_create` simply refunds the attached deposit to the legitimate predecessor: [4](#0-3) 

`assert_self()` and `is_promise_success()` in `on_lockup_create` only gate the refund-vs-success branching for the *caller's own* promise chain; they do nothing to prevent a different caller from squatting the account name first, and there is no whitelist-of-callers or owner-authorization check anywhere in `create`. The existing test `test_create_lockup_with_custom_whitelist_success` confirms the whitelist override parameter is exercised and accepted with no caller restriction: [5](#0-4) 

### Impact Explanation
The victim's canonical lockup address is permanently occupied by an attacker-deployed contract that lists `owner_account_id = V` but consults an attacker-controlled whitelist instead of the canonical/foundation whitelist. Any NEAR later sent to that address (directly, or by a party who assumes the factory-derived address is the genuine lockup) can be staked by the lockup's `select_staking_pool` logic into an arbitrary pool the attacker approved via the hostile whitelist, since the lockup contract trusts `staking_pool_whitelist_account_id` as the source of truth for approved pools. This matches "Critical - a lockup deployed with parameters its rightful creator never chose," and additionally can permanently deny the rightful creator the ability to ever deploy the correct lockup for that `owner_account_id` (the account name is unique and immutable). The attack is repeatable against any `owner_account_id` the attacker wants to target, for the cost of one `MIN_ATTACHED_BALANCE` deposit each time.

### Likelihood Explanation
The attacker needs only a funded NEAR account and knowledge (or prediction) of an `owner_account_id` that a legitimate creator intends to use — this is generally public/predictable (e.g., known token-sale participants, known Foundation grant recipients). No special privilege, key, or role is required; `create` performs no caller authorization check at all. The only cost is `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas, and winning the race is a matter of transaction ordering, which is well within reach of an unprivileged attacker (e.g., submitting ahead of a known, scheduled Foundation lockup creation).

### Recommendation
Restrict `create` so that only the foundation (`self.foundation_account_id`) or the `owner_account_id` itself (`env::predecessor_account_id() == owner_account_id.as_ref()`) may create a lockup for that owner, and/or remove the caller-supplied `whitelist_account_id` override entirely so the deployed lockup always uses `self.whitelist_account_id`. Additionally, consider making the lockup account name depend on a value not fully controllable/predictable ahead of the legitimate creator's transaction (e.g., include a nonce or require the call be co-signed), or check `env::state_exists` style pre-registration before allowing untrusted deposits.

### Proof of Concept
```rust
// cargo test -p lockup-factory
#[test]
fn test_whitelist_squat_front_run() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker calls create() for victim's owner_account_id with a hostile whitelist,
    // BEFORE the legitimate/foundation creation call.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE; // minimal cost
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(),      // victim's intended owner_account_id
        lockup_duration,
        None,
        None,
        None,
        Some(custom_whitelist_account_id()), // attacker-controlled whitelist
    );

    // Assert: the deployed LockupArgs.staking_pool_whitelist_account_id
    // != contract.whitelist_account_id (the canonical whitelist).
    // (Captured via the serialized function_call args to the deterministic
    // lockup_account_id, which equals sha256(account_tokens_owner())[..20] + factory id
    // regardless of which caller invoked create().)
    assert_ne!(custom_whitelist_account_id(), whitelist_account_id());

    // Legitimate/foundation creation for the SAME owner now fails at create_account()
    // (account already exists at the deterministic address) and only refunds the
    // deposit to the predecessor — it cannot overwrite the attacker's whitelist.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(foundation_account_id().as_ref()),
    );
    assert_eq!(res, false); // legitimate creation permanently blocked / refunded,
                             // attacker's hostile-whitelist lockup remains at that address
}
```
This demonstrates that `create` has no check tying `env::predecessor_account_id()` to `owner_account_id` or `foundation_account_id`, and that the deterministic lockup address for a given `owner_account_id` can be squatted by an unprivileged attacker with an arbitrary `whitelist_account_id`, breaking the invariant that the created lockup consults the canonical whitelist.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
