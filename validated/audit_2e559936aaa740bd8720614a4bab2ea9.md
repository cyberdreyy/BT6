### Title
Address-Prefunding Griefing Blocks Legitimate `SystemInstruction::CreateAccount` at a Predictable Address - ([File: programs/system/src/system_processor.rs])

### Summary
The reported vePEG bug lets an attacker use `create_lock_for()` to cheaply "occupy" a victim's capacity slot at a target address, so the victim's own account-creation transaction later reverts (`"dstRep would have too many tokenIds"`) until a long lock timer expires, with no self-service remedy. Agave has a structurally identical griefing primitive in the System Program's `create_account` path: any unprivileged actor can pre-fund an arbitrary address with as little as 1 lamport via a plain `Transfer`, and the address's legitimate owner can then no longer use `SystemInstruction::CreateAccount` at that address, failing with `SystemError::AccountAlreadyInUse`, with no remediation available to the address owner short of using a different address (which is often not possible for seed/PDA-derived addresses fixed by protocol convention, e.g. nonce accounts created with a seed).

### Finding Description
`create_account` in `system_processor.rs` rejects account creation whenever the target already holds any lamports: [1](#0-0) 

```
fn create_account(...) -> Result<(), InstructionError> {
    // if it looks like the `to` account is already in use, bail
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        if to.get_lamports() > 0 {
            ic_msg!(invoke_context, "Create Account: account {:?} already in use", to_address);
            return Err(SystemError::AccountAlreadyInUse.into());
        }
        ...
    }
}
```

Because a bare System `Transfer` to any pubkey requires no signature, owner check, or minimum amount from that pubkey, an attacker who knows (or can derive) the address a victim intends to use for `CreateAccount` — e.g. a nonce account derived via `create_with_seed(base, seed, system_program::id())`, or any other deterministically-derivable address a dApp/CLI flow depends on — can send it 1 lamport ahead of time. This is functionally the same "cheap on-behalf-of-victim occupation of a scarce resource" pattern as `create_lock_for()`: the attacker spends a trivial amount to make a state-check on the victim's target fail (`to.get_lamports() > 0` vs. the veToken contract's `dstRep would have too many tokenIds`). The CLI's own nonce-account-creation code demonstrates the reachability of this exact scenario for a legitimate, unprivileged user flow — it derives the address with `create_with_seed` and checks whether the account already "exists" before proceeding: [2](#0-1) [3](#0-2) 

Tests in the codebase explicitly confirm the `AccountAlreadyInUse` failure mode for pre-funded ("already has lamports") targets: [4](#0-3) 

The Agave maintainers themselves recognized this exact griefing pattern and mitigated it — but only for a new, gated instruction path, `SystemInstruction::CreateAccountAllowPrefund`, guarded by the `create_account_allow_prefund` feature flag: [5](#0-4) [6](#0-5) 

The comment explicitly documents the pattern: *"Intended for use where account has already had rent paid in whole or in part before creation."* This confirms the vulnerability class is real and previously unaddressed for the original `CreateAccount` instruction, which remains the widely used path invoked by system_instruction::create_account, create_nonce_account(_with_seed), and by countless programs performing CPI account initialization (e.g., stake account creation, any PDA-based account bootstrap using `CreateAccount`/`CreateAccountWithSeed`). Those callers get no mitigation, since the fix only applies to the new opt-in instruction.

### Impact Explanation
An attacker can, for a trivial fee (single lamport transfer, ~5000-lamport transaction fee), permanently deny a specific address from ever being initialized as an intended account type via `CreateAccount`, forcing the victim to either abandon that deterministic address (impossible for scripts/programs relying on `create_with_seed`/PDA-derived addresses which must match a specific base+seed+owner combination) or to work around it out-of-band. This is a state-mutation/availability impact on victim transactions (guaranteed on-chain revert of legitimate `CreateAccount` calls), analogous in severity/reachability to the original medium-severity DOS report: attacker-controlled, unprivileged, and cheap to execute, but the effect on the victim can be permanent (no expiry, unlike the vePEG lockup) since a plain lamport transfer never resolves itself.

### Likelihood Explanation
Likelihood is medium: any unprivileged user (or bot) can send an ordinary `SystemInstruction::Transfer` transaction to any pubkey with no special permission. Exploitation requires the attacker to know or predict the victim's target address ahead of time (e.g., derived nonce-account addresses via `create_with_seed`, or program-computed addresses shared over some off-chain protocol/UI flow before the on-chain creation transaction lands), which is realistic in workflows where the recipient address is computed deterministically and possibly front-runnable or observable in advance (e.g. via mempool/QUIC ingest visibility, or a publicly known seed convention).

### Recommendation
- Extend the prefunding-tolerant creation semantics (already implemented for `CreateAccountAllowPrefund`) to the standard `CreateAccount`/`CreateAccountWithSeed` instructions, or provide a low-friction, permissionless "reclaim already-prefunded, uninitialized system-owned account" path so that a victim can proceed with account creation despite attacker-injected lamports.
- Alternatively/additionally, gate the fix behind a feature so it can eventually replace the legacy `AccountAlreadyInUse` semantics for zero-data, System-Program-owned accounts uniformly, not only for the newly-introduced instruction variant.
- Document and encourage callers (CLI, SDK helpers like `create_nonce_account_with_seed`) to migrate to the prefund-tolerant instruction once broadly activated.

### Proof of Concept
1. Victim (e.g. via `solana-cli nonce create-nonce-account --seed <SEED>`) computes `nonce_address = create_with_seed(creator_pubkey, seed, system_program::id())` and plans to submit `CreateAccountWithSeed` at `nonce_address`, as implemented in [2](#0-1) .
2. Before the victim's transaction lands, an attacker (who can independently compute the same deterministic `nonce_address` from the publicly known `creator_pubkey`/`seed` convention, or simply observes it via RPC/QUIC ingest) submits an ordinary `SystemInstruction::Transfer` of 1 lamport to `nonce_address`. This requires no signature from the victim and is unrestricted.
3. The victim's `CreateAccountWithSeed`/`CreateAccount` transaction is submitted and reaches `system_processor::create_account`, where `to.get_lamports() > 0` now evaluates true, and the instruction fails with `SystemError::AccountAlreadyInUse`, matching the assertion pattern already verified by the repository's own test: [4](#0-3) 
4. The victim cannot use this address for account creation going forward through the standard instruction; only the newer, feature-gated `CreateAccountAllowPrefund` instruction bypasses this restriction, and only where callers have been updated to use it.

/// Create a new account without checking for 0 lamports. All other checks remain.
/// Intended for use where account has already had rent paid in whole or in part
/// before creation.
#[allow(clippy::too_many_arguments)]
fn create_account_allow_prefund(
    to_account_index: IndexOfAccount,
    to_address: &Address,
    from_and_lamports: Option<(IndexOfAccount, u64)>,
    space: u64,
    owner: &Pubkey,
    signers: &HashSet<Pubkey>,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    {
        let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
        allocate_and_assign(&mut to, to_address, space, owner, signers, invoke_context)?;
    }
    if let Some((from_account_index, lamports)) = from_and_lamports
        && lamports > 0
    {
        transfer(
            from_account_index,
            to_account_index,
            lamports,
            invoke_context,
            instruction_context,
        )?;
    }
    Ok(())
