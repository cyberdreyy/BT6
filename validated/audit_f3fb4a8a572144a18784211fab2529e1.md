### Title
Unfunded instant-withdraw receipts from prior epochs are dropped from `defaultPendingClaimBasis`/`instantWithdrawClaimsByEpoch` epoch lookup, so default recovery is overpaid to other claimants while stale instant receipts freeze or drain the reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the external bug — a table/mapping lookup that silently returns 0 for a missing key, causing a guard/accounting step to be skipped — `IdleCreditVault` keys instant-withdraw claim accounting by `epochNumber`. `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` read `instantWithdrawClaimsByEpoch[epochNumber]`, which only contains receipts requested in the *current* epoch. Instant receipts left unfunded from an earlier epoch live under the old epoch key and are invisible to default finalization, even though `pendingInstantWithdraws` still counts them.

### Finding Description
- `requestInstantWithdraw` records receipts under the current `epochNumber` (`instantWithdrawsRequestsByEpoch[user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) and bumps the global `pendingInstantWithdraws`. [1](#0-0) 
- If those receipts are not funded (manager does not call `getInstantWithdrawFunds`, or funding reverts mid-epoch), `pendingInstantWithdraws` survives into later epochs while `instantWithdrawClaimsByEpoch` entries remain under the old key.
- On borrower default and `finalizeDefaultRecovery`, `defaultPendingClaimBasis()` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — the lookup returns 0 for prior-epoch receipts, so their claim basis is excluded from `totalBasis`. [2](#0-1) 
- `_defaultPrefundedInstantReserve()` similarly returns 0 for the prefunded bucket keyed at the old epoch, understating `reserveAmount`. [3](#0-2) 
- After finalization, `_claimDefaultedInstantWithdrawRequest` looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — 0 for old-epoch receipts — and early-returns, so `claimInstantWithdrawRequest` falls through to paying `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`. [4](#0-3) [5](#0-4) 

Two bad outcomes, both breaking the fair-loss invariant:
1. If non-reserve underlying exists (e.g., partial prefunding counted under the old epoch key, or borrower dust), the stale instant claimant withdraws **unhaircutted**, spending funds that belong to the default recovery waterfall; the `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, which was itself understated because the prefunded portion was missed.
2. Otherwise the claim reverts (`balance - reserve < amount`), permanently freezing the legitimate unfunded instant receipt even though it was a real claim that should have shared in `defaultRecoveryPrice`.

Meanwhile `defaultRecoveryPrice = reserveAmount / totalBasis` is inflated because `totalBasis` omits the stale instant claims, so normal pending withdrawers and active LPs are overpaid at the expense of the omitted claimants.

### Impact Explanation
Recovery assets are distributed on a wrong (too-small) basis: defaulted-epoch claimants and tranche holders recover more than their pro-rata share while prior-epoch instant withdrawers recover nothing (frozen receipt) or, if stray balance exists, extract an unhaircutted payout from the waterfall. Broken invariant: fair loss socialization / one receipt one payout. Loss is up to the full value of the stale instant receipts.

### Likelihood Explanation
Requires an instant withdraw request to remain unfunded across an epoch boundary (borrower/manager never calls `getInstantWithdrawFunds` before the next `stopEpoch`), then a borrower default. Both are unprivileged-observable conditions; the attacker needs only hold an unfunded instant receipt or benefit as another claimant. Moderate likelihood, high impact when it occurs.

### Recommendation
- Track unfunded instant claims independently of `epochNumber` (e.g., carry a global `instantPendingClaims` counter) or roll `instantWithdrawClaimsByEpoch[old]` forward at `stopEpoch`.
- In `defaultPendingClaimBasis()`/`_defaultPrefundedInstantReserve()`, include all epochs with outstanding instant claims, not just `epochNumber`.
- In `_claimDefaultedInstantWithdrawRequest`, iterate/aggregate `instantWithdrawsRequestsByEpoch` across all epochs ≤ `defaultRecoveryEpoch` instead of reading only the finalized epoch key.
- Add a conformance test: instant request in epoch N left unfunded, `startEpoch`/`stopEpoch` to N+1, default, `finalizeDefaultRecovery`, assert the claim pays `claimBasis * defaultRecoveryPrice` and that `defaultPendingClaimBasis` included it.

### Proof of Concept
Foundry fork scenario (mirror `testFinalizeDefaultPrefundedInstantWithdrawIsReserved` in `test/foundry/IdleCreditVault.t.sol`):
1. Deposit AA, `startEpoch` (epoch 0), `stopEpoch` with lower APR → `requestWithdraw` routes to `requestInstantWithdraw` at `epochNumber = 0`.
2. `startEpoch` (epoch 1); do NOT call `getInstantWithdrawFunds` (receipt stays under epoch key 0, `pendingInstantWithdraws > 0`).
3. `stopEpoch` → `epochNumber = 1`; trigger default via failed `getInstantWithdrawFunds`, then `finalizeDefault(recovered, manager)`.
4. Assert `defaultPendingClaimBasis()` excludes the epoch-0 instant claim (`instantWithdrawClaimsByEpoch[1] == 0`), `defaultRecoveryPrice` is inflated vs. fair value, and `claimInstantWithdrawRequest` for the epoch-0 user either reverts (frozen claim) or pays unhaircutted.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
