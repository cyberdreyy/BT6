### Title
Missing Refund/Rollback in Multisig Factory Leads to Permanently Frozen Deposits on Account Creation Failure - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` in `multisig-factory/src/lib.rs` builds a batched promise (`create_account` → `deploy_contract` → `transfer(attached_deposit)` → `function_call("new", ...)`) using a caller-supplied, unvalidated `name: AccountId`, but — unlike its sibling factories — never attaches a callback to check whether the promise succeeded and refund the caller if it did not.

### Finding Description
`staking-pool-factory` and `lockup-factory` both follow the same "spawn a subaccount contract with an attached deposit" pattern, but each protects the depositor against creation failure with an explicit `ext_self::on_*_create` callback that inspects `is_promise_success()` and transfers the deposit back to the caller on failure: [1](#0-0) [2](#0-1) 

`multisig-factory/src/lib.rs` implements the exact same pattern, but omits the callback entirely: [3](#0-2) 

`create` also does not validate `name` the way `staking-pool-factory::create_staking_pool` explicitly rejects `.` in the user-supplied prefix and validates the resulting account ID: [4](#0-3) 

Because `name` in `multisig-factory::create` is an unchecked `AccountId` (a plain `String` alias in near-sdk 2.0), any of the following unprivileged-attacker-controlled conditions can make the outgoing batched receipt (`CreateAccount`, `DeployContract`, `Transfer`, `FunctionCall`) fail atomically as a unit:
- `name` produces an invalid account ID (empty, uppercase, disallowed characters, embedded dots that collide with reserved/edge naming rules, etc.), causing `is_valid_account_id` on the derived `account_id` to be violated at the protocol level.
- The target subaccount `"{name}.{current_account_id}"` already exists (e.g., attacker races to create the same name twice, or a name collision with a pre-existing account).
- `num_confirmations`/`members` cause the `new` function call within the batch to panic (e.g. `num_confirmations` exceeding member count causing `assert!` panics used elsewhere in multisig contracts).

When any action in that batched receipt fails, the entire receipt fails atomically — the new account is not created, the contract is not deployed, and the `Transfer` of `env::attached_deposit()` is not executed. Because there is no `on_create` callback, `multisig-factory` never checks for this failure and never issues a refund `Promise::new(caller).transfer(attached_deposit)`. The attached deposit remains as part of the factory contract's own account balance, with no code path to identify the original depositor or return the funds.

### Impact Explanation
Any user calling `create` with an attached deposit and a `name` that triggers a receipt failure permanently loses the deposited NEAR: it becomes indistinguishable general balance of the `multisig-factory` contract account, with no getter, no tracking of "pending" deposits, and no admin/foundation recovery method in this contract. This is a concrete, unauthorized loss of funds for the calling party — funds permanently frozen — matching the Critical impact class defined for this scan ("funds permanently frozen").

### Likelihood Explanation
This requires no privileged role, no owner, no multisig member, no redeploy, and no social engineering — any account can call `create` on the public `multisig-factory` with a `name` value under their control. Triggering the failure condition (e.g. duplicate subaccount name via front-running/racing another `create` call for the same `name`, or supplying an invalid/edge-case `name` string) is entirely within reach of a single unprivileged caller attaching their own deposit.

### Recommendation
Mirror the pattern already used in `staking-pool-factory` and `lockup-factory`:
1. Validate `name` (reject empty strings, embedded `.`, and validate the derived `account_id` with `env::is_valid_account_id`) before attempting subaccount creation.
2. Add an `ext_self::on_create` callback attached via `.then(...)` that checks `is_promise_success()` and refunds `env::attached_deposit()` to `env::predecessor_account_id()` when the account-creation batch fails, exactly as `on_staking_pool_create` and `on_lockup_create` already do.

### Proof of Concept
1. Attacker A calls `multisig-factory.create({"name": "shared", "members": [...], "num_confirmations": 1})` attaching `50 NEAR`, at nearly the same block height as another caller B who also calls `create` with `"name": "shared"`.
2. One of the two receipts succeeds in creating `shared.<factory>`; the other's `CreateAccount` action fails because the account already exists, causing the entire batched receipt (including the `Transfer` of the attacker's attached deposit) to fail atomically.
3. Because `multisig-factory::create` has no `on_create` callback (compare to `staking-pool-factory::on_staking_pool_create` / `lockup-factory::on_lockup_create`), the losing caller's attached NEAR is never returned — it remains stuck in the `multisig-factory` contract's balance permanently, with no method exposed to recover it.             false
        }

impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
