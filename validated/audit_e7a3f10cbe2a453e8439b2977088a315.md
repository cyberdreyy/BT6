### Title
`stopEpoch` hard-depends on the programmable borrower's ERC4626 vault being liquid/`convertToAssets` working — an unprivileged vault depositor can drain the shared vault and repeatedly block epoch settlement, freezing all tranche-holder funds (no owner off-switch while `isEpochRunning`) - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
Like `UniswapPriceAdaptor.getPrice()` hard-reverting when the emergency oracle is "off", `IdleCDOEpochVariant.stopEpoch()` hard-reverts whenever `ProgrammableBorrower`'s external ERC4626 valuation/liquidity path fails. There is no fallback to price the epoch without the vault, and the only toggle that would bypass the programmable borrower — `setIsProgrammableBorrower(false)` — explicitly reverts while `isEpochRunning`, i.e., exactly when the fallback would be needed.

### Finding Description
Two unguarded external reads/writes sit on the only epoch-settlement path:

1. `_resolveStopEpochInterest` calls `IProgrammableBorrower(_borrower()).totalInterestDueNow()` before any try/catch (`contracts/IdleCDOEpochVariant.sol:1004`). `totalInterestDueNow()` → `_vaultNetInterest()` → `_currentVaultAssets()` → `vault.convertToAssets(shares)` (`ProgrammableBorrower.sol:330-348, 546-549`). If `convertToAssets` reverts (vault paused/broken) the whole `stopEpoch` reverts. The codebase itself acknowledges this valuation view can be "unavailable during stress" — `onDefault()` deliberately avoids calling it (`ProgrammableBorrower.sol:295-297`) — yet the non-default stop path offers no such escape.

2. `onStopEpoch` does `vault.withdraw(shortfall, ...)` and reverts `StopEpochVaultLiquidityUnavailable` on failure (`ProgrammableBorrower.sol:246-253`). The revert bubbles through `stopEpoch` (the hook call at `IdleCDOEpochVariant.sol:398` is not in try/catch; the later try/catch only wraps `getFundsFromBorrower`). An unprivileged depositor of the *shared* ERC4626 vault can withdraw the vault's liquidity so that `vault.withdraw` reverts, making `stopEpoch` fail. Each time liquidity returns, the attacker can re-drain it, indefinitely postponing epoch settlement. Since withdrawals (`claimWithdrawRequest`) are only funded at `stopEpoch` and withdraw requests are disabled while `isEpochRunning` (`allowAAWithdrawRequest/allowBBWithdrawRequest = false`), the entire pool's exit path is frozen for as long as the attacker keeps the vault drained.

The JOJO recommendation (a `turnOffJOJOOracle` switch) maps directly: there is no way to stop an epoch without consulting the programmable borrower, because `setIsProgrammableBorrower` reverts on `isEpochRunning` (`IdleCDOEpochVariant.sol:176-180`) and `_checkProgrammableBorrowerMode`/`_resolveStopEpochInterest` force the programmable path in `_stopEpoch`.

### Impact Explanation
Temporary freezing of all LP funds (both tranches and pending withdraw receipts) for the duration of the griefing: `stopEpoch` cannot complete, `isEpochRunning` stays true, withdraw requests stay disabled, and matured `claimWithdrawRequest` receipts remain unfunded. Cost to the attacker is only gas plus capital temporarily deposited in the shared vault; impact scales with pool TVL frozen. No loss of principal, but denial of the only redemption path satisfies the temporary-freezing impact class.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault is shared with third-party depositors (the threat model explicitly includes "a user of the programmable borrower's ERC4626 vault"), or a vault whose `convertToAssets`/`withdraw` can revert. The attacker needs only to be a vault depositor — no privileged role. The blocking is repeatable every time liquidity is restored, so a motivated griefer can hold the epoch closed indefinitely.

### Recommendation
Give `stopEpoch` a programmable-borrower bypass analogous to the audit's `turnOffJOJOOracle`:
- Allow `setIsProgrammableBorrower(false)` (or a dedicated `disableProgrammableBorrower()`) while `isEpochRunning`, so owner/manager can stop the epoch using the explicit `_interest` override once the vault is unhealthy.
- Alternatively wrap `totalInterestDueNow()`/`onStopEpoch` in a fallback: on hook revert, let owner retry `stopEpoch` in a degraded mode that skips the vault read and treats the vault position via `emergencyExitVault`/`rescueTokens` recovery, instead of leaving the epoch unclosable.
- Rate-limit or reserve the vault sleeve (dedicated vault, or withdrawal queue) so third-party vault depositors cannot drain liquidity needed for epoch settlement.

### Proof of Concept
Foundry test extending `test/foundry/ProgrammableBorrowerCreditVault.t.sol` on a mainnet fork:

```solidity
// Setup as in existing tests: deposits, startEpoch() in programmable mode.
// Attacker = ordinary depositor of the same ERC4626 vault used by ProgrammableBorrower.

// 1) Attacker drains vault liquidity
vm.prank(vaultUser);
vault.redeem(vault.balanceOf(vaultUser), vaultUser, vaultUser); // removes underlying liquidity

// 2) Epoch ends; manager tries to settle
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
cdoEpoch.stopEpoch(0, 0); // reverts inside onStopEpoch -> vault.withdraw fails

// 3) Pool is frozen: requests still disabled, receipts unclaimable
assertTrue(cdoEpoch.isEpochRunning());
assertFalse(cdoEpoch.allowAAWithdrawRequest());
vm.expectRevert(); // no funds collected
creditVault.claimWithdrawRequest(user);

// 4) Owner cannot flip the off-switch mid-epoch
vm.prank(owner);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.setIsProgrammableBorrower(false);

// 5) Whenever attacker re-deposits and liquidity returns, they re-drain before the
//    next stopEpoch attempt -> repeatable indefinite freeze at gas cost only.
```
