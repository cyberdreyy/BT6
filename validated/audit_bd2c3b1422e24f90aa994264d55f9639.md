### Title
Default recovery reads only the current-epoch instant-withdraw slot, excluding older unfunded instant receipts from the recovery basis and inflating the recovery price for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The `acc_reader` bug class — reading a location that was never initialized for the actual data being queried — maps onto `IdleCreditVault`'s epoch-keyed receipt accounting. Instant-withdraw receipts are stored per request epoch (`instantWithdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`), but the default-recovery path reads **only** the slot for the *finalization* epoch (`epochNumber` / `defaultRecoveryEpoch`). Receipts created in an earlier epoch that remain unfunded at default time occupy storage slots that are never read during finalization, so their basis is silently dropped — the Solidity analog of reading uninitialized memory.

### Finding Description

Three functions all key on the *current* epoch instead of the epoch in which the receipts were recorded: [1](#0-0) [2](#0-1) [3](#0-2) 

`requestInstantWithdraw` keys both the per-user receipt and the aggregate under `epochNumber` at request time (lines 367-372). `pendingInstantWithdraws`, however, is a flat aggregate that persists across epochs — nothing at `stopEpoch`/`startEpoch` forces pending instant receipts to be funded before the next epoch begins, and `_ensureDefaultRecoveryInitialized` treats a non-zero `pendingInstantWithdraws` as a legitimate persistent state (line 926). So a request made in epoch `N` can still be pending when a default is finalized in epoch `M > N`.

At finalization:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., only epoch-`M` instant claims — to `pendingWithdraws`. The epoch-`N` aggregate slot is never read, so `totalBasis` is understated.
- `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (line 688) is therefore inflated: the same reserve is divided across a smaller basis.
- `_defaultPrefundedInstantReserve()` compares `pendingInstantWithdraws` (global, includes epoch-`N` claims) against `instantWithdrawClaimsByEpoch[epochNumber]` (epoch `M` only), so the prefunded-reserve component is also miscomputed whenever old receipts exist.
- When the victim later calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` = 0 (never written for epoch `M`) and returns without clearing. The user's real receipt (`instantWithdrawsRequests[user]`) then falls into the funded path, where `_transferFundedClaim` reverts because the entire balance is locked as `defaultRecoveryReserve` (lines 900-905) — and the reserve has already been over-distributed to other claimants at the inflated price.

The same one-slot-per-epoch assumption underlies `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` (lines 261-271, 789-799): the guard and the claim both read the slot keyed by the user's *last* request epoch, so any pending receipt whose epoch differs from the epoch in which `collectWithdrawFunds` recorded the price escapes the haircut entirely and claims at par via `_claimFundedWithdrawRequest`.

### Impact Explanation

Direct theft plus permanent freezing. The recovery reserve is finite; understating `totalBasis` by the excluded instant-claim basis `B` inflates `defaultRecoveryPrice` by a factor of `totalBasis / (totalBasis - B)`. Every other claimant — active AA/BB holders (via the `activeFinalNAV` mint/burn at lines 699-705) and defaulted-epoch receipt holders — is overpaid pro rata. An attacker holding any defaulted-epoch receipt or active tranche captures the victim's share. The victim's receipt is neither haircut-claimable (empty slot read) nor par-claimable (reserve guard), so its underlying is permanently locked in the strategy. Loss is exactly the excluded basis `B`, bounded only by the size of the stale instant request.

### Likelihood Explanation

Requires (a) instant withdrawals enabled and a request that remains unfunded across an epoch boundary — the CDO must simply not call `collectInstantWithdrawFunds` for one full epoch, which is operator behavior, not attacker-controlled, and (b) a subsequent borrower default. Condition (a) is plausible in normal operation (instant requests are only collected when the CDO has liquidity); condition (b) is the stress scenario the entire recovery module exists for. The bug needs no privileged misbehavior — all privileged actors act honestly; the loss materializes purely from the epoch-keyed slot mismatch.

### Recommendation

Track pending instant claims as a rolling basis rather than a current-epoch slot: maintain a `pendingInstantClaimBasis` aggregate (incremented in `requestInstantWithdraw`, decremented in `collectInstantWithdrawFunds`/claims) and use it in `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`. For per-user defaulted claims, iterate/accumulate the user's per-epoch instant receipts across all epochs ≤ `defaultRecoveryEpoch` (or store a per-user aggregate `instantWithdrawsRequests[user]`, which already exists, as the claim basis instead of the single-epoch slot). Apply the same audit to `lossRecoveryPriceByEpoch` lookups: verify the epoch key written in `collectWithdrawFunds` always equals the `lastWithdrawRequest` epoch of every receipt it covers.

### Proof of Concept

Foundry fork skeleton:

```solidity
// Setup: standard epoch variant with instant withdrawals enabled.
// Epoch N (running):
//   1. user V calls cdoEpoch.requestInstantWithdraw(amount) ->
//      instantWithdrawsRequestsByEpoch[V][N] = amount; pendingInstantWithdraws = amount.
//   2. CDO never calls collectInstantWithdrawFunds (no liquidity routed).
//   3. manager stopEpoch + startEpoch -> epochNumber = N+1, request stays pending.
// Epoch M > N (running): borrower defaults.
//   4. finalizeDefault(...) -> strategy.finalizeDefaultRecovery(recovered, source):
//      - defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[M]
//        -> misses V's epoch-N basis B = amount.
//      - recoveryPrice inflated by totalBasis / (totalBasis - B).
//   5. Attacker A (holds defaulted-epoch receipt or active tranche) claims:
//      paid (basis_A * inflatedPrice) / RECOVERY_FULL > fair share. The delta equals B's
//      pro-rata portion.
//   6. V calls claimInstantWithdrawRequest:
//      _claimDefaultedInstantWithdrawRequest reads slot [M] == 0 -> no-op;
//      funded path reverts at _transferFundedClaim because balance - reserve < amount.
// Assert: A's payout exceeds par-adjusted fair share by B's share; V permanently receives 0.
```

Caveat I could not fully resolve within the available context: whether a partial-loss `stopEpoch` writes `lossRecoveryPriceByEpoch` under the pre- or post-increment `epochNumber` (the increment occurs inside `deposit()` when the epoch is still flagged running, lines 607-611). If `collectWithdrawFunds` runs after that deposit within `stopEpoch`, the loss-price slot is mis-keyed for *every* pending receipt, which would make the loss-adjusted claim path unreachable entirely — that ordering in `IdleCDOEpochVariant.stopEpoch` should be confirmed during PoC development.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
