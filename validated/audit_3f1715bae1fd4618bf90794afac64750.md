### Title
Stale rejection weight is never cleared when a signer later accepts the same block, allowing a single signer's weight to be double-counted across `total_weight_rejected` and `total_weight_approved` - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies per-block signer responses into a `BlockStatus` struct with independent `total_weight_approved` and `total_weight_rejected` counters [1](#0-0) . When a signer's `Rejected` message arrives, its weight is added to `total_weight_rejected` guarded only by `block.responded_signers.insert(slot_id)` [2](#0-1) . When an `Accepted` message later arrives for the *same* block hash from the *same* signer, the guard checked is `!block.gathered_signatures.contains_key(&slot_id)` — not `responded_signers` — so a signer who previously rejected (and is therefore already in `responded_signers` but not in `gathered_signatures`) passes the guard and has its weight added a second time, now into `total_weight_approved` [3](#0-2) . `total_weight_rejected` is never decremented for that signer. This is structurally identical to the reported vault bug: a counter incremented on one path (`userDeposit`/reject) is never decremented on the reverse path (`processWithdrawDeposit`/accept), producing accounting that diverges from real state.

### Finding Description
`BlockStatus` intentionally never clears approvals (per the code comment, "an old approval could always be used to make a block reach the approval threshold") and explicitly only resets `total_weight_rejected` on a timeout via `reset_rejections()`, re-adding already-approved signers into `responded_signers` [4](#0-3) . However this reset only fires on the coordinator's own retry timeout; it does not fire when a signer organically flips its own vote from Rejected to Accepted for the same `block_sighash` outside of a timeout cycle. The signer side supports such reconsideration for certain reject reasons (the codebase's own comments reference re-evaluating and potentially reversing a rejection when a reject reason "allows us to reconsider" and re-proposals happen) [5](#0-4) . Consequently a signer that first rejects and later accepts the identical block leaves its rejected-weight contribution permanently stuck in `total_weight_rejected`, while its accepted-weight contribution is added to `total_weight_approved` — the same signer's weight is now counted in both pools simultaneously, breaking the invariant that `total_weight_approved + total_weight_rejected <= total_weight`.

### Impact Explanation
The miner's `get_block_status` loop treats crossing `total_weight_rejected.saturating_add(weight_threshold) > total_weight` (i.e., a blocking minority, ~30%+ of weight, in the reject pool) as a hard failure (`NakamotoNodeError::SignersRejected`), independent of whether `total_weight_approved` has already crossed the acceptance threshold [6](#0-5) . Because rejected weight from a signer who has since accepted is never purged outside of the timeout-triggered `reset_rejections`, stale rejection weight can accumulate toward the blocking-minority threshold even after the signers in question have moved on to approving the block. This can wedge block production for that proposal (a liveness issue): the miner may reject/abandon a block that in fact has (or would have) sufficient live approval weight, because the accounting is polluted by double-counted, stale rejection weight from signers who already reconsidered. This matches the "wedge the state machine" / liveness-break criteria (a signer state whose rejection is recounted as still active after being superseded by an accept), reachable by a single signer's own vote change plus normal timing (no majority collusion required to *create* the inconsistency, though a wider effect on the miner's decision depends on how much total rejected weight accumulates).

### Likelihood Explanation
Triggering the double count requires only one misbehaving or reconsidering signer sending `Rejected` then `Accepted` for the same `signer_signature_hash` — well within a single signer's control, with no majority or other signer's key needed. The scenario where a signer legitimately reconsiders a rejection (as referenced by in-code comments about reject reasons allowing reconsideration) makes this reachable even without malice, though a malicious signer could deliberately reject-then-accept specifically to keep pushing weight into both pools without any cleanup ever happening on the accept path.

### Recommendation
On the `Accepted` branch in `stackerdb_listener.rs`, guard on `responded_signers` (not just `gathered_signatures`) so a signer's earlier-counted `total_weight_rejected` contribution is subtracted (or the signer's slot is excluded from `total_weight_rejected`) before/when adding it to `total_weight_approved`, so the two weight pools remain mutually exclusive per signer, mirroring the fix pattern that was needed in the reported vault issue (keep the aggregate counter synchronized with the reverse operation).

### Proof of Concept
1. Miner proposes block B and calls `insert_block`, initializing `total_weight_approved = 0`, `total_weight_rejected = 0` [7](#0-6) .
2. Signer S (weight W) sends `Rejected` for B. `responded_signers.insert(S)` succeeds, `total_weight_rejected += W` [2](#0-1) .
3. Signer S later reconsiders (per legitimate reconsideration logic) and sends `Accepted` for the same block hash. `gathered_signatures.contains_key(S)` is false (S never accepted before), so the guard passes: `total_weight_approved += W`, and S is inserted into `gathered_signatures`/`responded_signers` again [3](#0-2) .
4. Now `total_weight_rejected` still includes S's weight W (never removed) and `total_weight_approved` also includes W — S's weight is counted in both pools, and `total_weight_approved + total_weight_rejected` can exceed `total_weight`. If enough such flips (or genuine rejectors) occur, `total_weight_rejected` can cross the blocking-minority threshold and cause `NakamotoNodeError::SignersRejected` even though the live/current vote set would otherwise have approved the block.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
