### Title
Multisig factory `create()` has no success callback, stranding attached NEAR on failed account creation - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds a single batched `Promise` (`create_account` → `deploy_contract` → `transfer` → `function_call`) and returns it directly, with no `.then()` callback that checks `is_promise_success()`. Both sibling factories in this repo (`staking-pool-factory` and `lockup-factory`) implement exactly this pattern but add a callback that refunds the caller if the account-creation batch fails; `multisig-factory` is missing that guard entirely.

### Finding Description
The broken binding: `attached_deposit()` transferred by the caller of `create` should equal either (a) the balance credited to the newly-created multisig account, or (b) the amount refunded to the predecessor if creation fails. In `multisig-factory/src/lib.rs`: [1](#0-0) 

`create` never checks the result of the batched promise nor schedules a callback to refund the depositor on failure, unlike the analogous flows in `staking-pool-factory::create_staking_pool` and `lockup-factory::create`, both of which chain `.then(ext_self::on_..._create(...))` and, inside the callback, call `is_promise_success()` before either whitelisting/finalizing or refunding: [2](#0-1) [3](#0-2) [4](#0-3) 

When the target `account_id = format!("{}.{}", name, env::current_account_id())` already exists (e.g., because it was already created earlier — by the attacker themselves, by a previous `create` call, or by any other means that left it funded), the `create_account` action in the batch fails since NEAR does not allow re-creating an existing account. Because the remaining actions in the batch (`deploy_contract`, `transfer`, `function_call`) execute against a receiver that already exists as a normal account, the `transfer` action still succeeds and delivers the caller's attached deposit into that account, while the overall receipt/promise chain reports failure. Since `multisig-factory` has no callback, nobody ever refunds the depositor and nothing ever reconciles the accounting — the factory has no persistent record of “funds sent, creation failed” the way `staking-pool-factory` cleans up `staking_pool_account_ids` on failure. The NEAR ends up sitting in an account the caller did not intend to fund and does not control (or an account with an existing owner), while the caller who attached the deposit receives nothing back and no on-chain state reflects that a refund is owed.

### Impact Explanation
NEAR attached by a caller of `create` can be stranded in a target account that is not the depositor's newly-intended multisig, with no automatic refund path and no accounting update in `multisig-factory` (which stores no state at all — `MultisigFactory` is an empty struct). This matches the "accounting value diverges from reality" / "funds frozen but recoverable only through off-chain intervention" category: value leaves the depositor's control and lands somewhere the depositor never authorized, and the protocol (the factory) has no record to correct it. The blast radius is any account name whose derived subaccount already exists and is funded, and is repeatable per attempt/name since the factory keeps no registry of used names to prevent this (contrast with `staking_pool_account_ids` set in `staking-pool-factory`).

### Likelihood Explanation
The precondition — a derived subaccount `name.<factory>` that already exists and holds a NEAR balance — is straightforward to engineer without any privileged access: an attacker can create that subaccount themselves in a prior transaction (e.g., by calling `create` successfully once, or by any other account-creation path under the factory's namespace), then call `create` again with the same `name`. This requires no foundation role, no multisig membership, and no victim key; cost is limited to gas and the deposit amount used for the second, failing call. It is fully repeatable across different `name` values.

### Recommendation
Add a `.then()` callback to `MultisigFactory::create`, mirroring `staking-pool-factory::on_staking_pool_create` / `lockup-factory::on_lockup_create`: use `assert_self()` and `is_promise_success()` in the callback, and if the creation failed, `Promise::new(predecessor_account_id).transfer(attached_deposit)` to refund the caller. Additionally, track already-created names (or otherwise assert the target account does not exist) to reduce redundant failed creations, matching the pattern already used in `staking-pool-factory::staking_pool_account_ids`.

### Proof of Concept
A `near-sdk-sim` test would: (1) deploy `multisig-factory`; (2) call `create("foo", members, n)` with deposit `D1` and let it succeed, producing account `foo.factory`; (3) call `create("foo", members2, n2)` again with deposit `D2` from a different predecessor; (4) assert the outer promise result is `ExecutionStatus::Failure`, assert `foo.factory`'s balance increased by `D2` (transfer landed despite failure), and assert the second caller's account balance is *not* refunded `D2` (no callback fires) — proving the invariant "a failed creation strands no NEAR" is violated because `D2` is stranded in `foo.factory` with no refund and no factory-side record.

Note: I could not execute this test in this environment (index is read-only); the above is a reproducible test plan against the exact code paths cited above, not a verified execution result. It is also worth flagging that the precise mechanics of NEAR runtime action-batch failure semantics (whether `transfer` genuinely still lands after a `create_account` failure in the same receipt) should be confirmed via `near-workspaces`/`near-sdk-sim` execution rather than assumed, since this determines whether the stranding is real or whether the whole batch aborts atomically — the code-level gap (missing callback/refund present in sibling factories) is confirmed regardless.

    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
