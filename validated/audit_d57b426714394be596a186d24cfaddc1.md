### Title

ERC4626 liquidity exhaustion blocks `stopEpoch` and freezes pending withdrawals - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary

In programmable-borrower mode, undrawn lender assets are deposited into an external ERC4626 vault when an epoch starts. A third-party vault user can remove the vault’s available liquidity so that `vault.withdraw()` reverts even though the borrower’s shares still economically cover the required withdrawal. The resulting `StopEpochVaultLiquidityUnavailable` revert propagates through `stopEpoch` without entering the borrower-default path, leaving pending withdrawal receipts and active lender funds frozen until external vault liquidity returns.

### Finding Description

`IdleCDOEpochVariant` supports programmable borrowers only with minted-interest accounting and no pending instant withdrawals. [1](#0-0) 

A user requesting a normal withdrawal has their tranche position converted into a strategy-token receipt, while `pendingWithdraws` records the amount that must be funded at the next `stopEpoch`. [2](#0-1) 

At epoch start, surplus underlying is sent to the borrower and `ProgrammableBorrower.onStartEpoch` deposits the borrower’s idle balance into the configured ERC4626 vault. [3](#0-2) [4](#0-3) 

At epoch end, `IdleCDOEpochVariant` calls `onStopEpoch` before the `try/catch` that handles a failed borrower transfer. [5](#0-4)  `ProgrammableBorrower` treats a shortfall larger than the vault-share value as coverable by the later `transferFrom` failure, but if the shares cover the shortfall and `vault.withdraw` reverts for liquidity or pause reasons, it reverts with `StopEpochVaultLiquidityUnavailable`. [6](#0-5) [7](#0-6) 

Because the hook reverts, `_handleBorrowerDefault` is not called and `isEpochRunning` remains true. [8](#0-7)  `epochNumber` only advances during the successful strategy `deposit` inside `stopEpoch`, so pending claimants remain blocked by the `epochNumber <= lastWithdrawRequest` check. [9](#0-8) [10](#0-9) 

The emergency controls do not provide an independent exit: `emergencyExitVault` still requires the same ERC4626 redemption liquidity, and `setVault` cannot be used while the borrower still holds vault shares. [11](#0-10) [12](#0-11) 

### Impact Explanation

Let `S = _amountToPullFromBorrower + pendingWithdraws` and `H` be the borrower’s on-hand underlying. An attacker who leaves `vault.maxWithdraw(programmableBorrower) < S - H` while `convertToAssets(vaultShares) >= S - H` makes every `stopEpoch` call revert. The temporarily inaccessible amount is `S - H`; in close-pool mode this can include the entire pool principal requested with `_interest == 1`. Pending withdrawers have already surrendered their tranche position for receipts but cannot receive underlying, while active lenders cannot create withdrawal requests because the epoch remains open. If the external vault remains paused or illiquid indefinitely, the freeze becomes permanent for the covered-but-unavailable vault position.

### Likelihood Explanation

The attacker does not need any privileged role in the credit vault. A large ERC4626 depositor can redeem enough shares to exhaust idle liquidity, or a borrower in an underlying lending market can borrow the available cash while the borrower adapter’s shares remain economically backed. The only requirements are programmable-borrower mode, a running epoch, and either pending withdrawals or a close-pool stop. Maintaining high utilization or low vault liquidity makes the failure repeatable on each `stopEpoch` attempt.

### Recommendation

Do not allow a covered external-vault liquidity failure to block epoch settlement indefinitely. `onStopEpoch` should support partial withdrawals up to `maxWithdraw`, expose a bounded external-liquidity failure state, or let the CDO enter an explicit recovery/default flow after a defined grace period. Pending-withdrawal reserves should preferably remain outside the ERC4626 vault, and an emergency recovery path should allow funded claims to be paid without requiring a successful `vault.withdraw` or `vault.redeem`.

function test_CoveredButIlliquidVaultBlocksStopEpoch() external {
    // Fixture: programmable borrower enabled, isInterestMinted = true,
    // strategy.borrower() == programmableBorrower, and a lending ERC4626 vault.

    uint256 depositAmount = 1_000_000 * ONE_SCALE;
    _depositWithUser(user, depositAmount, true);

    vm.prank(user);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Unprivileged external-vault action: the attacker borrows or redeems
    // enough ERC4626 liquidity to make the borrower adapter's withdrawal fail.
    uint256 shortfall = requested;
    vm.prank(attacker);
    externalLiquiditySource.borrowOrRedeem(shortfall);

    assertLt(vault.maxWithdraw(address(programmableBorrower)), shortfall);
    assertGe(
        vault.convertToAssets(vault.balanceOf(address(programmableBorrower))),
        shortfall
    );

    vm.warp(cdoEpoch.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());

    vm.prank(user);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimWithdrawRequest();
}

  /// @notice Handle borrower default
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
      IProgrammableBorrower(_borrower()).onDefault();
    }

    // deposits should be already prevented
    if (!paused()) {
      _pause();
    }

    // stop the current epoch
    isEpochRunning = false;

    // prevent withdrawals requests
    allowAAWithdrawRequest = false;
    allowBBWithdrawRequest = false;

    emit BorrowerDefault(funds);
  }
