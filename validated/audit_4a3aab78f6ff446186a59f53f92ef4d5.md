### Title
Signer weight double-counted in both approved and rejected tallies when a signer flips from Reject to Accept - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::handle_signer_message` (the miner-side tally used to decide whether a proposed block has been accepted or rejected by the signer set) maintains two independent counters, `total_weight_approved` and `total_weight_rejected`, inside `BlockStatus`. The guard that prevents double counting is asymmetric: the `Rejected` branch checks `responded_signers` before adding weight, but the `Accepted` branch only checks `gathered_signatures`, never checking (or clearing) a prior entry in `responded_signers`/`total_weight_rejected`. A signer that first rejects a block and later legitimately reconsiders and accepts the very same block (same `signer_signature_hash`) therefore has its weight counted in *both* buckets simultaneously, and the stale rejected weight is never removed.

### Finding Description
In [1](#0-0) , the `Accepted` handler only guards against double counting via `gathered_signatures`:

```rust
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block
        .total_weight_approved
        .saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```

It never inspects `total_weight_rejected` or removes this signer's weight from it, even though `responded_signers.insert(slot_id)` will already be `true` if this signer had previously sent a `Rejected` message for this same block hash.

Compare this to the `Rejected` handler at [2](#0-1) , which correctly uses `responded_signers.insert(slot_id)` as the sole gate before adding to `total_weight_rejected` — this protects the reverse order (accept-then-reject) from double counting, but the fix was not applied symmetrically to the accept path.

Sequence that triggers the bug:
1. Signer S sends `Rejected` for block B (hash `H`). `responded_signers` gains slot(S); `total_weight_rejected += weight(S)`.
2. S later reconsiders (the signer protocol explicitly allows a signer to change its vote on the same block when the reject reason permits reconsideration, and re-proposal of the identical block preserves the same `signer_signature_hash`) and sends `Accepted` for the same `H`.
3. In the `Accepted` branch, `gathered_signatures` does not yet contain S's slot, so the check passes and `total_weight_approved += weight(S)`.
4. Result: `weight(S)` is now counted in *both* `total_weight_approved` and `total_weight_rejected` for the same block; `total_weight_rejected` is never decremented.

This breaks the invariant that `total_weight_approved + total_weight_rejected` per distinct signer weight should never exceed the true, current set of votes — analogous to the reported bug where `senderBalance` retained `withdrawnShares` because the subtraction performed for `recipientBalance` was never reflected back into the calculation of `senderBalance`. Here, the weight "moved" to the approved bucket is never removed from the rejected bucket.

### Impact Explanation
This is consumed in `SignerCoordinator::watch_for_block_signatures`/`gather_signatures` in [3](#0-2) , which decides between three outcomes each poll: reject the block (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`), accept it (`total_weight_approved >= weight_threshold`), or keep waiting. Because a reconsidering signer's weight lingers permanently in `total_weight_rejected`, the miner's rejected tally can be inflated with stale, superseded rejections. In a scenario where enough weight to approach the 30% blocking minority participates in reject→accept flips, the miner can be driven to conclude `SignersRejected` for a block that in reality has (or would have) crossed the 70% approval threshold from currently valid votes — causing the miner to needlessly abandon a validly-supported block and rebuild, which is a liveness degradation on block production (repeated forced re-proposals / tenure stalls) rather than a signature-safety violation, since the bug lives in the miner's bookkeeping and not in the on-chain `verify_signer_signatures` check in `stackslib/src/chainstate/nakamoto/mod.rs`, which independently re-verifies real signatures and weight (see [4](#0-3) ).

### Likelihood Explanation
Triggerable by a single signer (no majority required) simply by rejecting and then reconsidering to accept the same block proposal — a normal, protocol-sanctioned behavior per the signer flow documentation. No forged signatures, no cross-context replay, and no cooperation from other signers is needed; only gossip of two legitimate signed messages from the same signer for the same block hash.

### Recommendation
In the `Accepted` branch of `handle_signer_message`, check whether `slot_id` is already present in `responded_signers` due to a prior rejection and, if so, subtract `signer_entry.weight` from `total_weight_rejected` (and clear any per-txid `failed_txids` weight attributed to that signer) before adding it to `total_weight_approved`, mirroring the symmetric guard already present in the `Rejected` branch.

### Proof of Concept
1. Miner proposes block B; `StackerDBListenerComms::insert_block` initializes `total_weight_approved = 0`, `total_weight_rejected = 0`.
2. Signer S (weight w) sends `BlockResponse::Rejected` for B → `total_weight_rejected = w`.
3. Signer S reconsiders and sends `BlockResponse::Accepted` for the identical B (same `signer_signature_hash`) → `total_weight_approved = w`, but `total_weight_rejected` remains `w` (never decremented).
4. Repeat with additional signers whose combined weight, added to the stale rejected weight, crosses `total_weight - weight_threshold` in `signer_coordinator.rs`'s rejection check, even though those same signers' current votes are `Accepted`. The miner incorrectly returns `NakamotoNodeError::SignersRejected` for block B.

    pub fn verify_signer_signatures(
        &self,
        reward_set: &RewardSet,
        epoch_id: StacksEpochId,
    ) -> Result<u32, ChainstateError> {
        let message = self.signer_signature_hash();
        let Some(signers) = reward_set.signers() else {
            return Err(ChainstateError::InvalidStacksBlock(
                "No signers in the reward set".to_string(),
            ));
        };

        // if this is a shadow block, then its signing weight is as if every signer signed it, even
        // though the signature vector is undefined.
        if self.is_shadow_block() {
            return Ok(self.get_shadow_signer_weight(reward_set)?);
        }

        let mut total_weight_signed: u32 = 0;
        // `last_index` is used to prevent out-of-order signatures
        let mut last_index = None;
        // Before Epoch 4.0, signature order check contained a bug, so gate the
        // strict ordering behavior on the epoch.
        let strict_order = epoch_id.enforces_strict_signature_order();

        let total_weight = reward_set
            .total_signing_weight()
            .map_err(|_| ChainstateError::NoRegisteredSigners(0))?;

        // HashMap of <PublicKey, (Signer, Index)>
        let mut signers_by_pk: HashMap<_, _> = signers
            .iter()
            .enumerate()
            .map(|(i, signer)| (&signer.signing_key, (signer, i)))
            .collect();

        for signature in self.signer_signature.iter() {
            let public_key = Secp256k1PublicKey::recover_to_pubkey_without_validating_low_s(
                message.bits(),
                signature,
            )
            .map_err(|_| {
                ChainstateError::InvalidStacksBlock(format!(
                    "Unable to recover public key from signature {}",
                    signature.to_hex()
                ))
            })?;

            let mut public_key_bytes = [0u8; 33];
            public_key_bytes.copy_from_slice(&public_key.to_bytes_compressed()[..]);

            let (signer, signer_index) = signers_by_pk.remove(&public_key_bytes).ok_or_else(|| {
                warn!(
                    "Found an invalid public key. Reward set has {} signers. Chain length {}. Signatures length {}",
                    signers.len(),
                    self.chain_length,
                    self.signer_signature.len(),
                );
                ChainstateError::InvalidStacksBlock(format!(
                    "Public key {} not found in the reward set",
                    public_key.to_hex()
                ))
            })?;

            // Enforce order of signatures
            if let Some(index) = last_index.as_ref() {
                if *index >= signer_index {
                    return Err(ChainstateError::InvalidStacksBlock(
                        "Signatures are out of order".to_string(),
                    ));
                }
                if strict_order {
                    last_index = Some(signer_index);
                }
            } else {
                last_index = Some(signer_index);
            }

            total_weight_signed = total_weight_signed
                .checked_add(signer.weight)
                .expect("FATAL: overflow while computing signer set threshold");
        }

        let threshold = Self::compute_voting_weight_threshold(total_weight)?;

        if total_weight_signed < threshold {
            return Err(ChainstateError::InvalidStacksBlock(format!(
                "Not enough signatures. Needed at least {} but got {} (out of {})",
                threshold, total_weight_signed, total_weight,
            )));
        }

        return Ok(total_weight_signed);
