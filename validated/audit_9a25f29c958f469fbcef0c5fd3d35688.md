### Title
Missing post-default guard in `requestInstantWithdraw` lets a new receipt drain the default recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` lacks the `defaultRecoveryFinalized` handling that `requestWithdraw` has. A receipt requested after default finalization is recorded under `instantWithdrawsRequestsByEpoch[user][epochNumber]`, where `epochNumber` equals `defaultRecoveryEpoch`, so the defaulted-claim path pays it out of `defaultRecoveryReserve` even though it was never part of `defaultPendingClaimBasis`/`totalBasis` — the same class of bug as CVE-2022-2327 (an operation missing its identity/accounting type produces an incorrect reference count and a double-free-style payout).

### Finding Description
- `requestWithdraw` explicitly branches on `defaultRecoveryFinalized`, forces the user to clear all prior receipts, and routes the request into `postDefaultRequests` paid 1:1 [1](#0-0) .
- `requestInstantWithdraw` has no such branch: it unconditionally appends to `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws` [2](#0-1) . After finalization, `epochNumber` is frozen at `defaultRecoveryEpoch` (it is only bumped by `deposit` while an epoch is running [3](#0-2) ), so the new receipt lands in the exact slot `_claimDefaultedInstantWithdrawRequest` reads.
- `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` and pays `claimBasis * defaultRecoveryPrice` via `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve` [4](#0-3) [5](#0-4) . `defaultRecoveryReserve` was sized at finalization to cover only `defaultPendingClaimBasis` = `pendingWithdraws` + pre-finalization `instantWithdrawClaimsByEpoch[epochNumber]` [6](#0-5) . The attacker's post-finalization receipt is outside that basis, so every unit it claims is a direct haircut on all legitimate defaulted-epoch claimants (reserve insolvency before later claimants withdraw).
- The receipt is also still counted in `instantWithdrawsRequests[user]`, so any remainder after the defaulted-epoch clear continues to the at-par funded path, compounding the miscounting.
- Reachability: default is finalized mid-epoch (`finalizeDefaultRecovery` requires `cdo.defaulted()` but the epoch need not have stopped [7](#0-6) ). If the pool's instant-withdraw window was enabled for that epoch, a tranche holder can still route an instant request through the CDO while `defaultRecoveryFinalized == true`; the strategy itself imposes no check. (Exact CDO-side gating of `requestInstantWithdraw` after `defaulted()` was not fully verified in this pass — the strategy-level gap is unconditional, so the guard should exist regardless.)

### Impact Explanation
Direct theft of the default recovery reserve. Loss is bounded by the attacker's tranche-token holdings times `defaultRecoveryPrice`; each claimed unit is subtracted from `defaultRecoveryReserve` [8](#0-7) , leaving honest defaulted-epoch withdraw/instant claimants unable to claim their full recovery (permanent loss to them, quantifiable as `min(attackerReceipt * defaultRecoveryPrice / 1e18, reserve)`).

### Likelihood Explanation
Requires (a) a borrower default that is finalized for recovery, and (b) the ability to submit an instant withdraw request after finalization — plausible whenever the epoch's instant-withdraw delay window was open at default time or the CDO does not gate instant requests on `defaulted()`. The attacker is any tranche holder (unprivileged). No privileged collusion needed.

### Recommendation
Mirror `requestWithdraw`: in `requestInstantWithdraw`, when `defaultRecoveryFinalized` is true, either revert or route the amount into the post-default path (`postDefaultRequests` / a parallel instant bucket) paid 1:1 — never write into `instantWithdrawsRequestsByEpoch[user][epochNumber]` once `epochNumber == defaultRecoveryEpoch`. Alternatively, key defaulted instant claims off a snapshot captured at finalization rather than the live per-epoch mapping.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
