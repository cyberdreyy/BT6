### Title
Permanent ETH Fund Lock When Bridge Recipient Is a Contract Without `receive()` — (`bridge/evm/contracts/BridgeVault.sol`)

---

### Summary

`BridgeVault.transferETH()` unwraps WETH and sends raw ETH to the recipient via a bare `.call{value: amount}("")`. If the recipient is a contract that lacks a `receive()` or `fallback()` function, the call returns `false`, the `require(success, "ETH transfer failed")` reverts the entire transaction, and the bridge message nonce is never marked processed. Because the recipient address is cryptographically fixed inside the committee-signed message, every subsequent replay of that message will revert identically. The user's ETH coins were already burned on Sui, so the corresponding WETH locked in the vault becomes permanently unclaimable.

---

### Finding Description

`BridgeVault.transferETH` is the sole path for releasing ETH from the vault to an Ethereum recipient during a Sui→ETH bridge withdrawal:

```solidity
// bridge/evm/contracts/BridgeVault.sol  lines 52-64
function transferETH(address payable recipientAddress, uint256 amount)
    external override onlyOwner nonReentrant
{
    wETH.withdraw(amount);                                    // unwrap WETH → ETH
    (bool success,) = recipientAddress.call{value: amount}(""); // bare ETH push
    require(success, "ETH transfer failed");                  // hard revert on failure
}
``` [1](#0-0) 

`SuiBridge._transferTokensFromVault` routes every ETH withdrawal through this function:

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 256-257
if (tokenID == BridgeUtils.ETH) {
    vault.transferETH(payable(recipientAddress), amount);
``` [2](#0-1) 

`transferBridgedTokensWithSignatures` (V1) and `transferBridgedTokensWithSignaturesV2` (V2) both call `_transferTokensFromVault` and only mark the nonce processed **after** the vault call returns successfully:

```solidity
// SuiBridge.sol lines 84-92
_transferTokensFromVault(...);
// mark message as processed
isTransferProcessed[message.nonce] = true;
``` [3](#0-2) [4](#0-3) 

Because the revert unwinds the entire transaction, `isTransferProcessed[message.nonce]` is never set. The message can be replayed indefinitely, but the recipient address is embedded in the committee-signed payload and cannot be changed without invalidating the signatures. Every replay reverts for the same reason.

---

### Impact Explanation

This matches the **permanent fund lock** impact class in the allowed gate.

1. The user's ETH `Coin` object is burned on Sui at the moment `send_token` / `send_token_v2` is called — that state change is final and irreversible on the Sui side.
2. The corresponding WETH in `BridgeVault` can never be released to the intended recipient.
3. There is no on-chain escape hatch: no alternative claim path, no WETH fallback, no admin rescue function in `BridgeVault` or `SuiBridge`.
4. The bridge is upgradeable, but a contract upgrade requires bridge committee governance action — this is not a user-accessible remedy and is explicitly out of scope as a mitigation.

The user permanently loses the bridged ETH value.

---

### Likelihood Explanation

Any user who specifies a smart-contract address as the Ethereum recipient when initiating a Sui→ETH transfer triggers this path. Common real-world cases include:

- Multisig wallets (e.g., Gnosis Safe) that do not implement `receive()`.
- Protocol treasury contracts.
- Any contract whose `receive()` reverts or consumes more than the default gas forwarded by `.call{}`.

No special privilege is required. The trigger is a single ordinary bridge transaction on Sui.

---

### Recommendation

Replace the hard-revert pattern in `BridgeVault.transferETH` with a WETH fallback, mirroring the standard `sendEthOrWeth` pattern:

```solidity
function transferETH(address payable recipientAddress, uint256 amount)
    external override onlyOwner nonReentrant
{
    wETH.withdraw(amount);
    (bool success,) = recipientAddress.call{value: amount}("");
    if (!success) {
        // Fallback: re-wrap and send WETH so funds are never stuck
        wETH.deposit{value: amount}();
        IERC20(address(wETH)).safeTransfer(recipientAddress, amount);
    }
}
```

Alternatively, document that only EOA addresses should be used as Ethereum recipients and enforce this at the Sui `send_token` entry point by rejecting 20-byte payloads that correspond to known contract patterns, or add a separate `rescueWETH` admin function that can redirect WETH to the original sender when an ETH push fails.

---

### Proof of Concept

1. Deploy a contract `NoReceive` on Ethereum with no `receive()` or `fallback()`.
2. On Sui, call `bridge::send_token` (or `send_token_v2`) specifying `NoReceive`'s address as `target_address` and `TOKEN_ID_ETH` as the token. The ETH `Coin` is burned on Sui.
3. The bridge committee observes the `TokenDepositedEvent`, signs the message, and submits `transferBridgedTokensWithSignatures` on Ethereum.
4. Inside `_transferTokensFromVault`, `vault.transferETH(payable(NoReceive), amount)` is called.
5. `wETH.withdraw(amount)` succeeds; `NoReceive.call{value: amount}("")` returns `(false, "")`.
6. `require(success, "ETH transfer failed")` reverts the transaction.
7. `isTransferProcessed[nonce]` remains `false`; the WETH stays in the vault.
8. Every subsequent replay of the same signed message reverts identically.
9. The user's ETH is permanently lost — burned on Sui, unclaimable on Ethereum.

        // transfer eth if token type is eth
