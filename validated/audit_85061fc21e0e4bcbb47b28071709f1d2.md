### Title
Deposit-before-preregistration processing order lets a same-payload front-run deposit steal a validator's withdrawal credentials, defeating EIP-8205's anti-front-running guarantee - (File: specs/_features/eip8205/beacon-chain.md)

### Summary
EIP-8205 introduces `PreregistrationRequest`/`StoredPreregistration` to bind a validator pubkey to specific withdrawal credentials *before* its first deposit is processed, explicitly to stop deposit front-running. However, `apply_parent_execution_payload` unconditionally processes all `deposits` before all `preregistrations` in the same execution payload, and a pubkey with a pending deposit cannot be preregistered. This ordering lets an attacker's malicious deposit (submitted in the same block as, or before, the legitimate preregistration) capture the pubkey's `withdrawal_credentials` and simultaneously block the legitimate preregistration from ever taking effect for that pubkey, which is exactly the front-running attack the feature claims to prevent.

### Finding Description
`process_preregistration_request` refuses to store a binding if the pubkey already has a pending deposit: [1](#0-0) 

`process_deposit_request` only enforces the withdrawal-credential binding if an *active, already-stored* preregistration exists for the pubkey at the time the deposit is processed; if none exists yet, the deposit is accepted unconditionally with whatever `withdrawal_credentials` the deposit request carries: [2](#0-1) 

Crucially, `apply_parent_execution_payload` processes **all** deposit requests before **any** preregistration requests, regardless of the actual chronological/transaction order in the execution-layer block, and the code comment explicitly acknowledges this is "deposit-first behavior": [3](#0-2) 

Consequence: if a legitimate depositor's `PreregistrationRequest` for pubkey `P` and an attacker's malicious `DepositRequest` for the same pubkey `P` (with the attacker's own `withdrawal_credentials`) are both included in the same execution payload — even if the preregistration transaction was submitted to the EL mempool *first* — the beacon-chain state transition always applies the deposit before the preregistration:
1. `process_deposit_request(state, malicious_deposit)` runs first. `get_active_preregistration(state, P)` returns `None` (nothing stored yet), so the credential-matching branch is skipped entirely and the malicious deposit is appended to `state.pending_deposits` unconditionally, with the attacker's withdrawal credentials.
2. `process_preregistration_request(state, legit_request)` then runs. `is_pending_validator(state.pending_deposits, P)` is now `True` because of the just-appended malicious deposit, so the function returns early — the legitimate preregistration is silently dropped.
3. At the next epoch boundary, `process_pending_deposits` (inherited from Electra, unmodified by this feature) will create the validator with the attacker's withdrawal credentials, since no binding exists to reject it.

Thus the ordering guarantee "preregistration wins if it lands before the malicious deposit" is broken specifically for the case that matters most — same-block inclusion — which is the canonical front-running scenario this feature exists to close. This is the direct analog of the external report's bug class: an authorization/permission state (`StoredPreregistration`, analogous to the persisted per-token `approve`) that should gate a sensitive action can be bypassed because of an ordering/state-timing gap, letting an unauthorized party (the front-running depositor) complete an action (claiming withdrawal credentials) that the rightful controller of the pubkey tried to prevent.

### Impact Explanation
This breaks the equality "a validator's withdrawal credentials are set by the party the deposited Gwei's owner intended, not by a non-owner attacker." A successful attack redirects the entire stake's withdrawal rights (32+ ETH, i.e., Gwei) to an address the depositor never authorized — this is "Gwei ... paid to a non-owner" / "a validator ... re-credentialed without its authority," both Critical/High-impact categories. Since `withdrawal_credentials` are immutable once a validator is created from a deposit (except via the one-time BLS-to-execution-change path for BLS-type credentials, which doesn't apply to a maliciously-set ETH1 credential), the loss is effectively permanent and requires no majority stake or coalition — a single attacker who observes the mempool can do it.

### Likelihood Explanation
This requires only that an attacker monitor the EL mempool for `PreregistrationRequest`/deposit transactions for a not-yet-registered pubkey (which is exactly the front-running condition the feature was designed to prevent) and submit a copy of the deposit-contract call with the observed pubkey/signature but their own `withdrawal_credentials`, ensuring it lands in the same execution payload as (or in any payload prior to) the legitimate preregistration. No special privileges, validator keys, or majority stake are needed; this is a single unprivileged actor exploiting a spec-level ordering rule, matching the "no malicious peer/coalition/client-bug required" bar.

### Recommendation
Do not gate preregistration admission on `is_pending_validator`, or restructure `apply_parent_execution_payload` so that preregistrations are applied (or at least so any deposit lacking a matching, freshly-created-in-block preregistration for a not-yet-registered pubkey is deferred/rejected) before same-payload deposits are finalized. Concretely: process preregistrations before deposits within a payload (reversing the current explicit "deposit-first" choice), or track "preregistration requests seen this payload" and apply them prior to admitting any deposit for the same pubkey, so a same-block preregistration always wins over a same-block front-running deposit.

### Proof of Concept
1. Alice controls pubkey `P` and wants delegated-staking withdrawal credentials `WC_alice`. She constructs a valid `PreregistrationRequest(pubkey=P, withdrawal_credentials=WC_alice, signature=sig)` and submits the corresponding EL transaction.
2. Attacker Mallory observes this pending transaction (and/or the deposit transaction) in the EL mempool before it is included in a block, and crafts a `DepositRequest(pubkey=P, withdrawal_credentials=WC_mallory, amount=..., signature=...)` (using a deposit signature Mallory can produce, or by reusing an observed signature over pubkey/credentials/amount if applicable to the network's deposit flow), and gets it included in the *same* execution payload as, or any payload before, Alice's preregistration.
3. During `apply_parent_execution_payload`, `for_ops(requests.deposits, process_deposit_request)` executes first: [2](#0-1)  — since `get_active_preregistration(state, P)` is `None`, Mallory's deposit with `WC_mallory` is appended to `state.pending_deposits` unconditionally.
4. `for_ops(requests.preregistrations, process_preregistration_request)` then executes: [1](#0-0)  — `is_pending_validator(state.pending_deposits, P)` is now `True`, so Alice's preregistration is silently discarded (no error, no revert).
5. At the next epoch's `process_pending_deposits`, validator `P` is created with `WC_mallory` — Alice's stake now has withdrawal credentials she never authorized, an irreversible transfer of validator control confirmed by state transition, with no way for Alice to have prevented it despite acting first.

```markdown
def process_preregistration_request(state: BeaconState, request: PreregistrationRequest) -> None:
    pubkey = request.pubkey

    # An active binding for this pubkey makes the new request a no-op,
    # whether the duplicate is exact or conflicting
    if get_active_preregistration(state, pubkey) is not None:
        return

    # A pubkey with an existing validator cannot be preregistered
    if pubkey in [validator.pubkey for validator in state.validators]:
        return

    # A pubkey with a valid pending deposit cannot be preregistered
    if is_pending_validator(state.pending_deposits, pubkey):
        return
```

def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)

    state.pending_deposits.append(
        PendingDeposit(
            pubkey=deposit_request.pubkey,
            withdrawal_credentials=deposit_request.withdrawal_credentials,
            amount=deposit_request.amount,
            signature=deposit_request.signature,
            slot=state.slot,
        )
    )

##### Modified `apply_parent_execution_payload`

*Note*: Preregistrations are processed last so that a deposit and a
preregistration for the same pubkey in one execution payload retain the
deposit-first behavior stated by EIP-8205.

```python
def apply_parent_execution_payload(
    state: BeaconState,
    requests: ExecutionRequests,
) -> None:
    parent_bid = state.latest_execution_payload_bid
    parent_slot = parent_bid.slot
    parent_epoch = compute_epoch_at_slot(parent_slot)

    assert len(requests.withdrawals) <= MAX_WITHDRAWAL_REQUESTS_PER_PAYLOAD
    assert len(requests.consolidations) <= MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_deposits) <= MAX_BUILDER_DEPOSIT_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_exits) <= MAX_BUILDER_EXIT_REQUESTS_PER_PAYLOAD
    # [New in EIP8205]
    assert len(requests.preregistrations) <= MAX_PREREGISTRATION_REQUESTS_PER_PAYLOAD

    # Process execution requests from parent's payload. The execution
    # requests are processed at state.slot (child's slot), not the parent's slot.
    def for_ops(operations: Sequence[Any], fn: Callable[[BeaconState, Any], None]) -> None:
        for operation in operations:
            fn(state, operation)

    for_ops(requests.deposits, process_deposit_request)
    for_ops(requests.withdrawals, process_withdrawal_request)
    for_ops(requests.consolidations, process_consolidation_request)
    for_ops(requests.builder_deposits, process_builder_deposit_request)
    for_ops(requests.builder_exits, process_builder_exit_request)
    # [New in EIP8205]
    for_ops(requests.preregistrations, process_preregistration_request)
```
