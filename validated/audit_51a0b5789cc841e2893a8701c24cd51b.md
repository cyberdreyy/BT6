### Title
Same-block deposit/withdraw guard keyed on `tx.origin` can be bypassed by using a second EOA, enabling intra-block price manipulation - (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO._deposit` records a fingerprint `keccak256(tx.origin, block.number)` via `_updateCallerBlock()`, and `_withdraw` calls `_checkSameBlock()` to revert when a deposit was made "by the same user" in the same block. The check is keyed on `tx.origin`, not `msg.sender`. Any attacker controlling two EOAs (or bundling transactions, e.g. via private orderflow/MEV) can deposit from EOA-1 and withdraw from EOA-2 inside the same block, defeating the only same-block mitigation intended to prevent flash-deposit price manipulation. This mirrors the reported Kibana "forged Origin header" bug class: a security decision based on a forgeable/misbinding origin identifier.

### Finding Description
In `contracts/IdleCDO.sol`:

- `_updateCallerBlock()` stores `keccak256(abi.encodePacked(tx.origin, block.number))` in `_lastCallerBlock` (lines ~1015-1018).
- `_checkSameBlock()` reverts only when the stored hash equals `keccak256(tx.origin, block.number)` of the *current* transaction (lines ~1020-1023).
- `_withdraw` relies on `_checkSameBlock()` before `_updateAccounting()` and payout of `toRedeem = _amount * _tranchePrice(_tranche) / ONE_TRANCHE_TOKEN` (lines ~477-507).

Because the equality key includes `tx.origin`, depositing from one EOA and withdrawing from a second EOA in the same block produces different hashes, so `_checkSameBlock()` passes. `msg.sender`-keyed accounting would also fail if the tranche tokens are simply transferred between the two attacker addresses before withdrawal; `tx.origin` is chosen precisely to catch "same human, same block" activity, but it fails the moment two distinct origins coordinate — which is trivial with bundled transactions and does not require any privileged role.

The practical impact depends on whether the tranche price (`_tranchePrice`/`_virtualPrice`) can be moved intra-block by an unprivileged actor. In the base IdleCDO, price moves through `_updateAccounting` (harvest/strategy price changes), donations to the contract balance, or deposit-time minting at stale prices. An attacker who can transiently raise the reported strategy price or contract value between the deposit-mint and the withdraw-burn in one block — e.g., via a strategy token balance manipulation or a direct donation counted by `_contractTokenBalance`/`getContractValue` before NAV/skimming runs — can mint cheap and redeem at the inflated price, extracting value from existing tranche holders. The `tx.origin` guard was meant to make exactly this unprofitable by forcing the round-trip across blocks; splitting origin defeats it. The same pattern exists in the variants listed (`IdleCDOEthenaVariant`, `IdleCDOPoLidoVariant`, `IdleCDOTruefiVariant`, `IdleCDOInstadappLiteVariant`, `GuardedLaunchUpgradable`, `IdleTokenFungible`).

Note: `_skimDonatedAssets()` in the epoch variant mitigates raw-donation inflation for `IdleCDOEpochVariant` paths, but the base `IdleCDO` deposit/withdraw path and variants that do not skim before pricing remain exposed to any transient value source that `_tranchePrice` reads.

### Impact Explanation
An unprivileged attacker with two funded EOAs can execute deposit→(manipulate)→withdraw within a single block, redeeming tranche tokens at a transiently inflated virtual price and draining the difference from the CDO's underlying balance. Loss is bounded by the achievable intra-block price manipulation times the attacker's tranche balance; repeated each block, it can drain a material fraction of pool NAV (senior/junior holders absorb it depending on which tranche is attacked). This breaks the fair mint/burn invariant the same-block check was designed to protect.

### Likelihood Explanation
Medium. Executing two transactions in the same block with different `tx.origin` requires either two EOAs landing in the same block (common on L2s and with builder/private bundles) or searcher infrastructure — feasible but not free. The exploit also requires an intra-block lever that moves `_tranchePrice` upward; where `_skimDonatedAssets` or equivalent donation-isolation runs before pricing, the lever narrows to strategy-price or reward-manipulation paths. The origin-misbinding flaw itself is unconditional: the guard provably fails against multi-origin coordination.

### Recommendation
Key the same-block guard on the actual token flow rather than `tx.origin`:
- Track per-`msg.sender` last deposit block (`mapping(address => uint256) lastDepositBlock`) and revert in `_withdraw` if `block.number == lastDepositBlock[msg.sender]` — and additionally record the block at which each tranche-token balance was acquired (checkpoint on `mint`/`_afterTokenTransfer`) so transfers between attacker EOAs do not reset the clock.
- Alternatively, enforce a minimum holding period for newly minted/acquired tranche tokens, or move to a queued withdrawal (as in `IdleCDOEpochVariant.requestWithdraw`) so redemption price is fixed at a later accounting checkpoint.

// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDO} from "../contracts/IdleCDO.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract SameBlockOriginBypassPoC is Test {
    IdleCDO cdo;
    IERC20Detailed underlying;
    address tranche; // e.g. cdo.AATranche()
    address eoa1 = makeAddr("attacker1");
    address eoa2 = makeAddr("attacker2");

    function testSameBlockBypassWithTwoOrigins() public {
        // ... fork setup: deploy/attach CDO, fund eoa1 with underlying ...

        uint256 depositAmount = 1_000_000e6;
        uint256 snap = vm.snapshotState();

        vm.startPrank(eoa1, eoa1); // msg.sender AND tx.origin = eoa1
        underlying.approve(address(cdo), depositAmount);
        cdo.depositAA(depositAmount);
        vm.stopPrank();

        // eoa2 receives tranche tokens and withdraws in the SAME block.
        // _checkSameBlock hashes (tx.origin, block.number): eoa2 != eoa1, so no revert.
        vm.prank(eoa1, eoa1);
        IERC20Detailed(tranche).transfer(eoa2, IERC20Detailed(tranche).balanceOf(eoa1));

        // intra-block price inflation primitive (e.g. transient strategy price
        // manipulation or a counted donation on paths without _skimDonatedAssets)
        // inflatePrice();

        vm.prank(eoa2, eoa2); // different tx.origin, same block.number
        uint256 redeemed = cdo.withdrawAA(0);
        assertGt(redeemed, depositAmount, "extracted profit in one block");

        vm.revertToState(snap);
    }
}

The origin-misbinding bypass itself is confirmed directly from `IdleCDO.sol` lines ~1015-1023, but the monetary impact hinges on that price-move primitive and should be confirmed with a forked PoC against the target deployment.
