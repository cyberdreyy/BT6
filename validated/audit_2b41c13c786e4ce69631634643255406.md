This confirms `create()` has no ownership or predecessor restriction whatsoever — any caller can specify any `owner_account_id`, `lockup_timestamp`, `lockup_duration`, and (whether or not) `vesting_schedule` [1](#0-0) . The resulting lockup account's address is deterministically derived only from `owner_account_id` via `sha256`, independent of who calls `create()` or what deposit/schedule they choose [2](#0-1) . The only self-check present is `assert_self()` in the `on_lockup_create` callback, which merely verifies the callback is invoked by the factory itself, not that the original caller was authorized [3](#0-2) [4](#0-3) . Since NEAR account creation is a one-time, exclusive action, whichever caller's `Promise::new(lockup_account_id).create_account()` lands first on that name permanently claims it; any later legitimate call to the same address fails and is merely refunded, never retried with the intended terms [5](#0-4) .

### Title
Permissionless `LockupFactory::create` allows front-running/squatting of a victim's deterministic lockup address with attacker-chosen zero-lockup parameters - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the new lockup contract's account ID solely from `sha256(owner_account_id)` and performs no check on who is allowed to create a lockup for a given `owner_account_id`, nor any bound on `lockup_timestamp`/`lockup_duration`/vesting parameters. An unprivileged attacker can pre-empt the legitimate grantor (e.g. NEAR Foundation) by calling `create("victim.near", 0, Some(0), None, None, None)` with only the minimum attached deposit, permanently occupying the deterministic address with a lockup contract that has no lockup and no vesting/foundation oversight, since `TRANSFERS_STARTED` is already in the past.

### Finding Description
The intended binding is: `lockup_account_id(owner) == deploy(owner, schedule_chosen_by_rightful_grantor)`. In reality, `lockup_account_id` is a pure function of `owner_account_id` [2](#0-1) , and `create()` lets **any caller**, not just the rightful grantor, supply the `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, and `release_duration` for that address, gated only by `MIN_ATTACHED_BALANCE` [1](#0-0) .

Exploit flow:
1. Attacker computes `lockup_account_id = sha256("victim.near")[..20] + "." + factory_account` (same formula as the contract) before the legitimate grantor submits its `create()` transaction.
2. Attacker calls `create(owner_account_id="victim.near", lockup_duration=0, lockup_timestamp=Some(0), vesting_schedule=None, release_duration=None, whitelist_account_id=None)` with `MIN_ATTACHED_BALANCE` (3.5 NEAR).
3. Inside `LockupContract::new`, `lockup_information.lockup_timestamp = Some(0)`, `lockup_duration = 0`, `transfers_information = TransfersEnabled { transfers_timestamp: TRANSFERS_STARTED }` (hardcoded `1602614338293769340`, already in the past) [6](#0-5) [7](#0-6) .
4. `get_locked_amount()` computes `lockup_timestamp = max(transfers_timestamp + lockup_duration, lockup_timestamp.unwrap_or(0)) = max(TRANSFERS_STARTED, 0) = TRANSFERS_STARTED`, which is already `<= block_timestamp`, so with no vesting schedule the function immediately returns `0` [8](#0-7) .
5. `Promise::new(lockup_account_id).create_account()` succeeds because the account did not previously exist; this permanently claims the name on-chain.
6. When the legitimate grantor later calls `create("victim.near", real_duration, real_timestamp, real_vesting, ...)`, `create_account()` on the now-existing account fails, the whole promise chain fails, and `on_lockup_create` merely refunds the grantor's deposit to itself [9](#0-8) . The grantor can never deploy the intended lockup/vesting terms at that address again, because the account name is now permanently occupied by the attacker's zero-lockup, no-vesting, no-foundation-oversight contract.

None of the existing guards prevent this: there is no `assert_owner`, `assert_called_by_foundation`, or any predecessor check inside `create()`; `assert_self()` only guards the internal callback, not the initial call [3](#0-2) .

### Impact Explanation
This produces "a lockup deployed with parameters its rightful creator never chose" - explicitly a Critical-severity outcome. The account nominally owned by `owner_account_id = "victim.near"` is deployed with no lockup period and no vesting/foundation termination controls, permanently pre-empting the Foundation's or any rightful grantor's ability to ever create the intended vesting/lockup contract at that deterministic address, since NEAR account names cannot be recreated once claimed. Any subsequent legitimate `create()` attempt for the same `owner_account_id` fails safely (refunded), but the intended contract configuration can never be established at that address — a permanent, irreversible loss of the intended lockup/vesting guarantees for that account name. The attack is repeatable against any `owner_account_id` the attacker can predict in advance (e.g. known upcoming employee/grantee account names), at a cost of only `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted address.

### Likelihood Explanation
The attacker needs no privileges: `create()` is a public, payable method requiring only `MIN_ATTACHED_BALANCE` attached deposit [10](#0-9) . The only precondition is knowing (or guessing) the target `owner_account_id` string before the legitimate grantor's transaction lands — feasible via mempool observation/front-running or by monitoring publicly known upcoming grantee/employee account names. The attack is fully deterministic (no race against other unknown state) and costs only the minimum deposit, which is not recoverable by the attacker (it becomes controlled by `owner_account_id`), but the actual damage (denial of proper lockup terms for that account name) is achieved regardless.

### Recommendation
Restrict `LockupFactory::create` so that only an authorized party (e.g. `foundation_account_id`, or requiring `predecessor_account_id() == owner_account_id`) can create a lockup for a given `owner_account_id`, and/or derive the lockup account name from a value not fully predictable/front-runnable by third parties (e.g. include a nonce or require the call to originate from the owner or foundation). Additionally, consider enforcing a minimum `lockup_timestamp`/`lockup_duration` or requiring `vesting_schedule`/`foundation_account_id` presence unless explicitly authorized by the foundation.

    pub fn get_locked_amount(&self) -> WrappedBalance {
        let lockup_amount = self.lockup_information.lockup_amount;
        if let TransfersInformation::TransfersEnabled {
            transfers_timestamp,
        } = &self.lockup_information.transfers_information
        {
            let lockup_timestamp = std::cmp::max(
                transfers_timestamp
                    .0
                    .saturating_add(self.lockup_information.lockup_duration),
                self.lockup_information.lockup_timestamp.unwrap_or(0),
            );
            let block_timestamp = env::block_timestamp();
            if lockup_timestamp <= block_timestamp {
                let unreleased_amount =
                    if let &Some(release_duration) = &self.lockup_information.release_duration {
                        let end_timestamp = lockup_timestamp.saturating_add(release_duration);
                        if block_timestamp >= end_timestamp {
                            // Everything is released
                            0
                        } else {
                            let time_left = U256::from(end_timestamp - block_timestamp);
                            let unreleased_amount = U256::from(lockup_amount) * time_left
                                / U256::from(release_duration);
                            // The unreleased amount can't be larger than lockup_amount because the
                            // time_left is smaller than total_time.
                            unreleased_amount.as_u128()
                        }
                    } else {
                        0
                    };

                let unvested_amount = match &self.vesting_information {
                    VestingInformation::VestingSchedule(vs) => self.get_unvested_amount(vs.clone()),
                    VestingInformation::Terminating(terminating) => terminating.unvested_amount,
                    // Vesting is private, so we can assume the vesting started before lockup date.
                    _ => U128(0),
                };
                return std::cmp::max(
                    unreleased_amount
                        .saturating_sub(self.lockup_information.termination_withdrawn_tokens),
                    unvested_amount.0,
                )
                .into();
            }
        }
        // The entire balance is still locked before the lockup timestamp.
        (lockup_amount - self.lockup_information.termination_withdrawn_tokens).into()
