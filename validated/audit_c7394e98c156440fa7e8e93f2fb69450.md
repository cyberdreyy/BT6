### Title
Async redeem requests can be self-solved via `solveRequestsDirect` to bypass the cancellation fee, cap, and toggle - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.cancelRequest` enforces a redeem-cancellation toggle (`_redeemCancellationsEnabled`), a size cap (`_redeemCancellationCapNumeraire`), and a cancellation fee when a user unwinds their own pending async redeem request before its deadline [1](#0-0) . However, the same economic outcome — recovering escrowed vault units without ever paying real tokens — can be reached through the public `solveRequestsDirect` path, which contains no check preventing the request owner from acting as their own "solver" and settles at a token amount the requester freely chose when creating the request, with no fee, cap, or toggle applied.

### Finding Description
A fixed-price redeem request is created with `requestRedeem`, which escrows `unitsIn` vault shares in the Provisioner and stores the user-supplied `minTokensOut` directly as the request's `tokens` field (only constrained to be non-zero by `_validateNonZeroAmounts`) [2](#0-1) .

`solveRequestsDirect` → `_solveRequestDirect` is a fully public function with no restriction that `msg.sender` differ from `request.user`/`request.receiver`, and it settles a redeem using exactly `request.tokens` and `request.units` with no oracle/price re-validation for the fixed-price branch: [3](#0-2) 

Because `request.tokens` is the user's own `minTokensOut` (which can be set to `1`), a request owner can call `solveRequestsDirect` on their own request: the contract sends the full escrowed `request.units` vault shares from the Provisioner back to `msg.sender`, while `token.safeTransferFrom(msg.sender, request.receiver, request.tokens)` is a self-to-self transfer of a nominal amount (net economic cost ≈ 0) when `msg.sender == request.receiver`. This recovers the entire escrowed position for free.

This bypasses the guards that `cancelRequest` enforces on the exact same "undo my redeem request" action:
- `_redeemCancellationsEnabled` toggle (can be disabled by admins to prevent self-unwinding) [4](#0-3) 
- `_redeemCancellationCapNumeraire` size cap on self-cancels [5](#0-4) 
- The pre-deadline cancellation fee computed via `_computeRedeemCancellationFeeUnits` [6](#0-5) 

The root cause mirrors the Ammplify pattern exactly: a penalty/guard is enforced on the canonical exit path (`cancelRequest`/`applyJITPenalties`) but is missing on an alternate public path (`solveRequestsDirect`/`collectFees`) that achieves the same economic effect (undoing a position early), because the fixed-price solve trusts the user-supplied `request.tokens` value without re-validating it or checking whether the caller is the request owner.

### Impact Explanation
This lets any user unwind large redeem requests for a nominal (near-zero) cost, regardless of whether admins have disabled redeem cancellations or configured a cancellation fee/cap to throttle self-unwinding and protect vault liquidity/epoch caps. Protocol fee revenue from cancellation fees is fully bypassed, and the admin-controlled cap/toggle protections against uncontrolled unwind behavior (designed to prevent liquidity drain / bank-run-like withdrawal patterns around the vault's sync redeem epoch caps) are defeated, which can contribute to freezing/loss for other depositors if liquidity is drained outside intended controls.

### Likelihood Explanation
No privileged role is required. Any ordinary user who can call `requestRedeem` (with `isFixedPrice=true` and a self-chosen minimal `minTokensOut`) and `solveRequestsDirect` can trigger this; the only extra step is a trivial self-approval of the settlement token for the nominal amount. This is deployed, in-scope production code reachable by any external account.

### Recommendation
In `_solveRequestDirect` (and the direct-solve entry point), either:
- Disallow `msg.sender == request.user` (or `request.receiver`) from directly solving their own request, or
- Re-validate the fixed `request.tokens` amount against a fresh oracle-derived bound before allowing a self-solve, or
- Route self-initiated unwinds exclusively through `cancelRequest`, ensuring the cancellation toggle/cap/fee are always applied regardless of which public function is used to reverse an escrowed request.

### Proof of Concept
1. Deploy/fork with `ProvisionerV2` configured: `asyncRedeemEnabled = true` for `token`, `_redeemCancellationsEnabled = false` (or a nonzero cancellation fee/cap configured).
2. As `alice`, call `requestRedeem(token, unitsIn = 1_000e18, minTokensOut = 1, solverTip = 0, deadline = block.timestamp + 1 hour, maxPriceAge = X, isFixedPrice = true, receiver = alice)`. Assert `1_000e18` vault units are transferred from `alice` into the Provisioner escrow.
3. As `alice`, `token.approve(alice, 1)` (self-allowance for the nominal fee-token amount).
4. As `alice`, call `solveRequestsDirect(token, [request])` with `request` matching the emitted hash parameters.
5. Assert: `alice` receives back the full `1_000e18` vault units, `alice`'s token balance decreases by only `1` wei (net self-transfer), no cancellation fee is charged, and the action succeeds even though `_redeemCancellationsEnabled == false` and/or the request size exceeds `_redeemCancellationCapNumeraire`. Compare against calling `cancelRequest` for the same request, which reverts with `Aera__RedeemRequestCancellationDisabled()` or `Aera__RequestAmountExceedsRefundCap()`.

    function _solveRequestDirect(IERC20 token, RequestV2 calldata request) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        if (_guardInvalidRequestHash(requestHash)) return;

        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;

        bool isDeposit = _isRequestTypeDeposit(request.requestType);

        if (request.deadline >= block.timestamp) {
            if (isDeposit) {
                // Interactions: pull units from sender(solver) to receiver
                IERC20(MULTI_DEPOSITOR_VAULT).safeTransferFrom(msg.sender, request.receiver, request.units);
                // Interactions: transfer tokens from provisioner to sender
                token.safeTransfer(msg.sender, request.tokens);

                // Log solved event
                emit DepositSolved(requestHash);
            } else {
                // Interactions: transfer units from provisioner to sender
                IERC20(MULTI_DEPOSITOR_VAULT).safeTransfer(msg.sender, request.units);
                // Interactions: pull tokens from sender(solver) to receiver
                token.safeTransferFrom(msg.sender, request.receiver, request.tokens);

                // Log solved event
                emit RedeemSolved(requestHash);
            }
