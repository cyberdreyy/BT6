### Title
Loss-adjusted withdraw receipts written under the post-increment epoch key are claimed at par, overpaying early claimants and draining the vault (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.collectWithdrawFunds` stores a stop-epoch loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but withdraw receipts record `lastWithdrawRequest[_user] = epochNumber` at *request* time, and `_claimLossAdjustedWithdrawRequest` looks the haircut up via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Because `deposit()` increments `epochNumber` inside `stopEpoch` before/alongside the funding collection, the haircut is persisted under epoch `N+1` while every affected receipt points at epoch `N`. The loss-adjusted claim path is therefore unreachable and `_claimFundedWithdrawRequest` pays the full un-haircut basis — even though the borrower only funded the reduced amount.

### Finding Description
The withdrawal flow keeps two clocks that are supposed to coincide but do not:

1. `requestWithdraw` saves `lastWithdrawRequest[_user] = currentEpoch` (the epoch `N` in which the request is made) and accumulates `withdrawsRequestsByEpoch[_user][N]` and `pendingWithdraws` (`IdleCreditVault.sol:282-294`).
2. During `stopEpochWithDuration(_lossAmount)`, the CDO funds only `pendingToFund = pendingBasis - pendingLoss` and calls `collectWithdrawFunds`, which writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws` (`IdleCreditVault.sol:411-421`).
3. `deposit()` — invoked during `stopEpoch` while `isEpochRunning()` is still true — executes `epochNumber += 1` (`IdleCreditVault.sol:607-611`). So by the time the epoch is fully stopped, `epochNumber == N+1`. `collectWithdrawFunds` reads the *current* `epochNumber` at call time; when the strategy deposit that bumps the counter precedes the collection call (the ordering the `deposit` comment describes — "deposit done on stopEpoch"), the haircut lands on key `N+1`, not `N`.
4. At claim time, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = `lossRecoveryPriceByEpoch[N]` = `0` and returns early (`IdleCreditVault.sol:789-792`).
5. `_claimFundedWithdrawRequest` then runs: `epochNumber (N+1) > lastWithdrawRequest (N)`, so the epoch-wait check passes, `withdrawsRequests[_user]` still holds the full pre-loss basis, and `_transferFundedClaim` pays it at par (`IdleCreditVault.sol:326-349`).

The write goes to a location the reader never consults — the direct analog of a temporary file written to a predictable-but-wrong shared path whose consumer reads a different key. Because `pendingWithdraws` was already cleared at step 2, nothing re-prices the payout.

### Impact Explanation
The borrower funds `pendingBasis * lossRecoveryPrice / 1e18`, but each pending receipt pays out the full `pendingBasis` share. Every claimant after a lossy `stopEpochWithDuration` withdraws `claimBasis` instead of `claimBasis * lossRecoveryPrice`. For a funded shortfall of `L = pendingLoss`, the vault pays out `L` more underlying than it received. Since `_transferFundedClaim` only checks the default-recovery reserve (`IdleCreditVault.sol:897-906`), this excess is drawn from strategy-held underlying earmarked for other withdrawers/instant-withdraw claims: early claimants are made whole at the expense of later claimants, whose claims then revert on insufficient balance — direct theft plus permanent freezing of the residual, quantified loss equal to the funded loss gap `pendingLoss` (up to the whole pending bucket minus the zero-price guard).

No guard stops it: `lossRecoveryPrice == 0` early-returns rather than reverting, the epoch-wait check passes normally, and `_clearWithdrawClaimForEpoch` is never reached so `withdrawsRequestsByEpoch`/`lastWithdrawRequest` cleanup runs on the funded path.

### Likelihood Explanation
It triggers whenever `stopEpochWithDuration` realizes a non-zero loss while `pendingWithdraws > 0` — an ordinary, honest-manager invocation, no attacker needed to create the condition; any receipt holder (unprivileged lender) then claims and is overpaid. The only precondition is that `epochNumber` is already incremented when `collectWithdrawFunds` executes — which follows directly from `deposit()`'s documented "deposit done on stopEpoch" increment. The zero-recovery revert (`lossRecoveryPrice == 0`) does not help because the stored key itself is wrong, not the price. If, on a given fork, the CDO ordering calls `collectWithdrawFunds` strictly before the epoch-incrementing `deposit`, the keys align and the bug is latent — that ordering should be verified in `IdleCDOEpochVariant.stopEpochWithDuration`/`_afterStopEpochWithDuration` (I could not fully trace the internal call order of those functions in this pass; the strategy-side key asymmetry above is confirmed regardless).

### Recommendation
Store the loss price under the *request* epoch, not the current counter: in `collectWithdrawFunds`, write `lossRecoveryPriceByEpoch[epochNumber - 1]` when a lossy collection runs after the epoch increment, or have the CDO pass the epoch the pending receipts belong to (e.g., `collectWithdrawFunds(_amount, _requestEpoch)`). Alternatively, record the loss under `pendingWithdrawEpoch` captured at `requestWithdraw` time. Add an invariant test: after `stopEpochWithDuration` with `loss > 0`, every `lastWithdrawRequest`-keyed lookup must return the stored price, and total claimed must equal total collected.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
function testLossEpochKeyMismatchPaysAtPar() external {
  uint256 amount = 10_000 * ONE_SCALE;
  idleCDO.depositAA(amount);
  _transferBurnedTrancheTokens(address(this), true);

  _startEpochAndCheckPrices(0);          // epoch 0 running
  // buffer of next epoch: request withdraw -> lastWithdrawRequest = 1
  uint256 requested = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)), address(AAtranche));
  _startEpochAndCheckPrices(1);

  // borrower returns only 70% of pending + interest: stopEpochWithDuration loss
  uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
  uint256 funded  = pending * 7e17 / 1e18;
  deal(defaultUnderlying, borrower, funded);
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(0, pending - funded); // realized loss

  // haircut was stored under the NEW epochNumber (2), receipt points at 1
  assertEq(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(1), 0);

  uint256 balPre = underlying.balanceOf(address(this));
  cdoEpoch.claimWithdrawRequest();       // pays full `requested`, not 70%
  assertEq(underlying.balanceOf(address(this)) - balPre, requested); // > funded
}
```
