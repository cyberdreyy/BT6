The reported bug class — an entry point that accepts attacker-controlled data and lets an unprivileged party invoke privileged/unintended state changes — has a stronger and more direct analog in this repository than the multisig `FunctionCall` action (which requires K-of-N confirmations and is therefore privileged, out of scope).

## Title
Unauthenticated arbitrary storage write/erase in `state-manipulation` contract lets any caller forge accounting state - (`state-manipulation/src/lib.rs`)

### Summary
`state-manipulation/src/lib.rs` exposes two exported wasm entry points, `replace()` and `clean()`, that write or delete arbitrary raw storage keys on the account the contract is deployed to. Neither function checks `predecessor_account_id`, `signer_account_id`, or any owner/self restriction before performing the storage mutation.

### Finding Description
`replace()` decodes attacker-supplied base64 key/value pairs from the call input and writes them directly into contract storage with `storage_write`, and `clean()` decodes attacker-supplied base64 keys and removes them with `storage_remove`. Both are bare `#[no_mangle]` exports with no caller authentication of any kind: [1](#0-0) [2](#0-1) 

Compare this to every privileged mutating method in the sibling contracts in this repo, which always gate on `assert_self()`, `assert_owner()`, or `assert_called_by_foundation()` before touching balances/shares, e.g. the lockup owner callbacks and whitelist mutators: [3](#0-2) [4](#0-3) 

The README documents the intended deployment pattern: `state-manipulation` is deployed onto an account that already hosts another contract (e.g. `staking-pool` or `lockup`) so that its storage can be directly repaired/migrated: [5](#0-4) 

Once this binary is live on that account (a documented, intended maintenance action), there is no restriction preventing *any* NEAR account — not just the deployer/foundation — from calling `replace` or `clean` on it. An attacker can therefore overwrite the raw Borsh-encoded state of the co-located contract, e.g. the staking-pool's `accounts: UnorderedMap` entries or `total_stake_shares`/`total_staked_balance` fields: [6](#0-5) 

This breaks the custody binding "claims (stake shares/unstaked balance) recorded versus NEAR actually held": the attacker can forge a large `unstaked` balance or stake-share count for their own account key without ever depositing NEAR, then call the co-located contract's real `withdraw`/`withdraw_all` to drain NEAR that was never deposited.

### Impact Explanation
Critical — an unprivileged party can move NEAR they are not entitled to and create claims (fabricated stake shares/unstaked balance) exceeding the NEAR actually held by the contract, by directly overwriting the accounting storage of any co-located contract via the unauthenticated `replace`/`clean` entry points.

### Likelihood Explanation
The precondition (temporary deployment of `state-manipulation` on top of a contract account for maintenance) is exactly the documented, intended use of this contract. Given that precondition, exploitation requires no privilege whatsoever — any account can call `replace`/`clean` during that window, since the entry points perform zero authentication checks. This differs from the excluded categories (it does not require the foundation/owner/multisig member to perform the malicious action itself, nor a malicious redeploy by the attacker — only the pre-existing, documented deployment of this tool by its legitimate operator).

### Recommendation
Add an authentication check (e.g. `assert_eq!(env::predecessor_account_id(), env::current_account_id())` or an explicit owner/foundation check) to both `replace()` and `clean()` in `state-manipulation/src/lib.rs` before performing any `storage_write`/`storage_remove`, so only the account itself (via a signed, single full-access-key-authorized transaction) — not an arbitrary third party — can invoke these state-mutating operations.

### Proof of Concept
1. Foundation deploys `state-manipulation.wasm` onto `staking-pool.near` (an existing, funded staking pool) to perform an intended state fix, per the documented workflow.
2. Attacker (any unprivileged account) calls:
```bash
near call staking-pool.near replace '{"entries":[["<base64 of the LookupMap "u" key for attacker.near>", "<base64 Borsh-encoded Account{unstaked: 1000000000000000000000000000, stake_shares:0}>"]]}' --accountId attacker.near
```
3. Attacker then calls the staking pool's real `withdraw` method to withdraw the forged unstaked balance:
```bash
near call staking-pool.near withdraw '{"amount":"1000000000000000000000000000"}' --accountId attacker.near
```
4. NEAR is transferred to `attacker.near` despite no prior deposit, because `replace()` at [1](#0-0)  performed no caller check.

#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    #[derive(serde::Deserialize)]
    struct ReplaceInput<'a> {
        #[serde(borrow)]
        entries: Vec<(&'a str, &'a str)>,
    }

    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}
```

pub fn clean() {
    #[derive(serde::Deserialize)]
    struct CleanInput<'a> {
        #[serde(borrow)]
        keys: Vec<&'a str>,
    }

    let input = input().unwrap();
    let args: CleanInput = serde_json::from_slice(&input).unwrap();
    for key in args.keys {
        storage_remove(&base64::decode(key).unwrap());
    }
}

# State Manipulation contract

This contract has been designed to put key value pairs into storage with `replace` and clear key/value pairs with `clean` from an account's storage.

Deploy this contract into the account that already has another contract deployed to it.
This contract on call `clean` will remove any items of the state specified (keys should be specified in base64). When compiled with `replace` feature, `replace` method can be called with an array of key/value tuple pairs to insert into state.

## Parameters

JSON format for `clean`:

```json
{"keys":["<base64 encoded key byte string>", "...", "..."]}
```

JSON format for `replace`:
```json
{"entries":[["<base64 key byte string>", "<base64 value byte string>"], ["...", "..."]]}
```
