### Title
Instant-withdraw claim released at par before defaulted-epoch receipt is detached — par payout of a haircut-bound claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` mirrors the lpfc bug class exactly: the "resource" (the user's `instantWithdrawsRequests` balance, which still aggregates the defaulted-epoch receipt) is paid out at par via `_transferFundedClaim`, while the per-epoch "context pointer" (`instantWithdrawsRequestsByEpoch[user][defaultEpoch]`) is only cleared inside `_claimDefaultedInstantWithdrawRequest` — which is skipped whenever `defaultRecoveryFinalized && !defaultInstantWithdrawsFinalized`. The correct pattern (detach the pointer under the lock, then release the buffer) is already used in `_claimDefaultedInstantWithdrawRequest`, but the enclosing claim path releases funds first.

### Finding Description
The claim flow at `IdleCreditVault.sol:380-393` is:

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);   // detaches the defaulted-epoch receipt
}
uint256 amount = instantWithdrawsRequests[_user];    // still INCLUDES defaulted basis
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);                 // paid at PAR
```

`_claimDefaultedInstantWithdrawRequest` (lines 842-856) is the only place that clears `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, subtracts it from `instantWithdrawsRequests`/`pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the isolated reserve.

If `defaultRecoveryFinalized == true` while `defaultInstantWithdrawsFinalized == false` (i.e. the finalization step that flips the instant flag has not yet run — the two flags are distinct state, so the finalize flow evidently permits this intermediate window, or a user claim can simply land before the manager/borrower-driven instant finalization), the defaulted-epoch instant receipt is paid at **par** from funded (non-reserve) balance instead of the haircut price from `defaultRecoveryReserve`. Afterward `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` still holds the stale basis; a later `_claimDefaultedInstantWithdrawRequest` re-reads it and underflows on `instantWithdrawsRequests[_user] -= claimBasis`, permanently reverting — the aggregate counters (`pendingInstantWithdraws`, `instantWithdrawClaimsByEpoch`, `defaultRecoveryReserve`) are left permanently inconsistent.

### Impact Explanation
- Direct theft / mispricing: the attacker (any unprivileged lender with an instant-withdraw receipt in the defaulted epoch) receives 100% of the claim instead of `defaultRecoveryPrice`-adjusted value, spending funded underlyings that belong to other funded claimants.
- Permanent freezing: after the par claim, the stale `instantWithdrawsRequestsByEpoch` entry makes the "correct" defaulted claim path revert, desyncing `pendingInstantWithdraws` vs actual reserve, blocking `collectInstantWithdrawFunds` accounting for the honest `idleCDO` caller.

### Likelihood Explanation
Requires a borrower default followed by finalization ordering in which `defaultRecoveryFinalized` is set before `defaultInstantWithdrawsFinalized` (or a gap between the two manager/borrower-driven calls — the honest privileged roles merely have to sequence their calls, per scope). The attacker only needs an outstanding instant-withdraw receipt in the default epoch and calls `claimInstantWithdrawRequest` through the CDO — no privileged action. The `_transferFundedClaim` reserve guard does not stop it: it only protects `defaultRecoveryReserve`, while the inflated par amount is spent from the non-reserve funded balance.

Caveat: I could not confirm within the available iterations whether `finalizeDefault`/`finalizeDefaultRecovery` in `IdleCDOEpochVariant.sol`/`IdleCreditVault.sol` always sets both flags atomically; if they are always toggled in the same transaction, the window collapses to zero and the ordering is still fragile-by-design but not exploitable.

### Recommendation
In `claimInstantWithdrawRequest`, when `defaultRecoveryFinalized` is set, always route defaulted-epoch basis through `_claimDefaultedInstantWithdrawRequest` — i.e. clear `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` from `instantWithdrawsRequests[_user]` **before** computing `amount` for the par payout, regardless of `defaultInstantWithdrawsFinalized`; or revert when `defaultRecoveryFinalized && !defaultInstantWithdrawsFinalized` so no funds are released while the defaulted pointer is still attached.
