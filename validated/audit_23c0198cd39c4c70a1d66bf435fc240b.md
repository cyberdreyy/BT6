### Title
Unprivileged view-role session can list CSA public keys via `GET /v2/keys/csa` lacking role wrapper - ([File: core/web/router.go])

### Finding Description
`core/web/router.go` line 310 registers `authv2.GET("/keys/csa", csakc.Index)` with no `auth.RequiresEditRole` or `auth.RequiresAdminRole` wrapper, while every other CSA key management route (`POST /keys/csa`, `POST /keys/csa/import`, `POST /keys/csa/export/:ID`) is wrapped with an explicit role check. `CSAKeysController.Index` (`core/web/csa_keys_controller.go:24-31`) calls `ctrl.App.GetKeyStore().CSA().GetAll()` and returns all CSA public keys via `presenters.NewCSAKeyResources`, with no internal role check of its own. The `authv2` group's only guard is `auth.Authenticate(..., auth.AuthenticateByToken, auth.AuthenticateBySession)`, which validates the session/token exists but performs no per-role check — that check is only applied when routes are explicitly wrapped with `auth.RequiresEditRole`/`auth.RequiresAdminRole`. Therefore, any authenticated session, including one with `UserRoleView`, can call `GET /v2/keys/csa` and receive `200 OK` with the CSA public key list, since Index does not check role.

However, note that this identical pattern (list endpoints unguarded by role, while write/delete endpoints require Edit/Admin) is applied uniformly across `ETHKeysController.Index`, `ExternalInitiatorsController.Index`, and `BridgeTypesController.Index` in the same file, indicating this is very likely an intentional design choice (any authenticated user, even view-role, can read key/bridge/EI listings, but cannot mutate them) rather than an accidental omission specific to CSA keys.

### Impact Explanation
Disclosure is limited to CSA **public** key material and metadata (`PublicKey`, `Version`) via `presenters.NewCSAKeyResources` — CSA public keys are used for OCR2 telemetry/mercury/DON peer identification and are not secret; no private key or credential material is exposed. This does not enable privilege escalation, fund movement, or unauthorized job execution. At most this is a minor information-disclosure of non-sensitive public key metadata to an authenticated low-privilege user, consistent with the codebase's own design pattern for list endpoints.

### Likelihood Explanation
Trivial to trigger for any account holding a valid session or API token (including `UserRoleView`), requiring only `POST /sessions` followed by `GET /v2/keys/csa`. However, because the exposed data is public-key metadata only, and because the same "read is open, write is gated" behavior is used consistently elsewhere in the router, this does not represent an unintended authorization-bypass bug distinct from the rest of the API's design.

### Recommendation
If the intent is that CSA key listing should be restricted like Create/Import/Export, wrap the route with `auth.RequiresEditRole` (or `RequiresRunRole`) for consistency: `authv2.GET("/keys/csa", auth.RequiresEditRole(csakc.Index))`. Otherwise, no change is needed since CSA public keys are not sensitive secrets and the behavior matches the established pattern for other key-listing endpoints.

func (ctrl *CSAKeysController) Index(c *gin.Context) {
	keys, err := ctrl.App.GetKeyStore().CSA().GetAll()
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}
	jsonAPIResponse(c, presenters.NewCSAKeyResources(keys), "csaKeys")
}
