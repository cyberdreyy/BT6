### Title
Instant-withdraw receipts can be claimed before they are funded, stealing underlying reserved for matured normal withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns the user's receipt and immediately transfers underlying from the strategy balance, without checking that the instant request was actually funded at `startEpoch` via `collectInstantWithdrawFunds`. The vault keeps no segregation between "funded normal withdraw reserves" and "unfunded instant requests": `pendingInstantWithdraws` is only decremented when the CDO pushes funds in. An unprivileged KYC'd lender can therefore mint an instant receipt and claim it in the same transaction, draining underlying that was collected for other users' matured `withdrawsRequests`, causing their later claims to revert (insolvency).

### Finding Description
Analog to the CVE bug class (a sample moved into the counts bucket without bounds/state validation — value counted where it does not belong): an unfunded instant receipt is treated as a funded claim.

- `requestInstantWithdraw` mints a 1:1 receipt to the user and increments `instantWithdrawsRequests`/`pendingInstantWithdraws` (lines 356-375). No funds move; the strategy only receives backing later, when `collectInstantWithdrawFunds` pulls `_amount` from the CDO and decrements `pendingInstantWithdraws` (lines 398-403).
- `claimInstantWithdrawRequest` performs no epoch gating and no check that `pendingInstantWithdraws` was reduced for the requester — it simply burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim` (lines 380-393).
- `_transferFundedClaim` only protects `defaultRecoveryReserve`; any other underlying sitting in the strategy — in particular reserves transferred by `collectWithdrawFunds` for matured normal withdraw receipts — is spendable (lines 897-907).
- The CDO-side wrapper `IdleCDOEpochVariant.claimInstantWithdrawRequest` only checks `allowInstantWithdraw` (IdleCDOEpochVariant.sol lines 975-979), so nothing blocks the premature claim.
- Reachability for an unprivileged attacker: the instant path is entered from `requestWithdraw` when `_isInstantWithdrawEnabled()` and `lastEpochApr > unscaledApr + instantWithdrawAprDelta` (IdleCDOEpochVariant.sol lines 761-770). This condition occurs naturally whenever the manager lowers APR for a new epoch (a routine, honest-manager operation); the attacker only needs `allowInstantWithdraw`/`allowAAWithdrawRequest` flags on and to pass `isWalletAllowed`.

### Impact Explanation
Direct theft / insolvency with quantified loss: the attacker receives underlying up to the strategy's liquid balance, which is exactly the funded reserve backing other users' matured normal withdraw receipts. Victims' subsequent `claimWithdrawRequest` calls underflow on the ERC20 `_burn` or revert inside `_transferFundedClaim`/the safeTransfer, permanently freezing their payouts until the reserve is replenished. Loss equals the attacker's instant receipt amount, bounded by the funded-but-unclaimed withdraw reserve.

### Likelihood Explanation
Requires (a) instant withdrawals enabled (`allowInstantWithdraw`), (b) an APR decrease exceeding `instantWithdrawAprDelta` — a normal parameter change by the honest manager — and (c) outstanding funded normal withdraw reserves, which accumulate whenever users do not claim immediately. No privileged collusion, no oracle manipulation, and no default is needed; the attacker is an ordinary allowed lender sequencing `requestWithdraw` + `claimInstantWithdrawRequest` in one transaction.

### Recommendation
Track funded vs unfunded instant claims: have `claimInstantWithdrawRequest` settle only against the funded portion (e.g., record per-epoch funded instant amounts when `collectInstantWithdrawFunds` runs, or require `pendingInstantWithdraws` coverage to have been delivered for the user's request epoch), and revert otherwise — mirroring the `epochNumber > lastWithdrawRequest` gating used for normal claims.

### Proof of Concept
Foundry fork sketch (pattern from `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: AA deposit by victim, epoch running, allowInstantWithdraw = true
// 1) victim requests normal withdraw; epoch ends; borrower funds it:
//    stopEpoch -> strategy.collectWithdrawFunds(pending) moves underlying
//    into the strategy. pendingWithdraws == 0, funds sit in vault.
// 2) manager lowers apr: strategy.setAprs(newApr, scaled) so that
//    lastEpochApr > unscaledApr + instantWithdrawAprDelta
// 3) attacker (KYC'd EOA) deposits AA, then:
cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche)); // instant path
cdoEpoch.claimInstantWithdrawRequest();                          // same tx
// attacker receives underlying == funded reserve of victim
// 4) victim.claimWithdrawRequest() reverts on insufficient strategy balance
```

Key assertions: `underlying.balanceOf(attacker)` increases by the instant amount before any `collectInstantWithdrawFunds` call, `pendingInstantWithdraws` remains > 0, and the victim's funded claim reverts.
