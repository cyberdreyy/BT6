### Title
Stale-epoch instant-withdraw receipts escape the default-claim basis yet remain payable at par after default finalization — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The CVE is a request-smuggling primitive: two interpreters disagree on where one request ends, letting a hidden payload ride through. The analog in `IdleCreditVault` is a dual-ledger disagreement between the aggregate `pendingInstantWithdraws` counter and the per-epoch `instantWithdrawClaimsByEpoch` map. An unfunded instant-withdraw receipt opened in epoch N is counted in `pendingInstantWithdraws` and `instantWithdrawsRequests[user]`, but `defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch. When a default is finalized in a later epoch M, the old receipt is smuggled past the recovery haircut: it is never included in the claim basis (so no reserve is allocated for it), yet `claimInstantWithdrawRequest` still pays the aggregate `instantWithdrawsRequests[user]` at par via `_transferFundedClaim`.

### Finding Description
1. Epoch N, instant mode (`allowInstantWithdraw`, APR dropped by `instantWithdrawAprDelta`): attacker calls `IdleCDOEpochVariant.requestWithdraw`, which routes to `requestInstantWithdraw` (IdleCreditVault.sol:356-375). The vault burns CDO strategy tokens, mints a receipt to the user, and increments `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][N]`, `instantWithdrawClaimsByEpoch[N]`, and `pendingInstantWithdraws`.
2. The borrower never prefunds the instant queue (honest borrower behavior — funds deployed mid-epoch). `pendingInstantWithdraws` stays > 0; nothing clears it across `stopEpoch`/`startEpoch` except `collectInstantWithdrawFunds`, which requires actual funding.
3. Epoch M: the borrower defaults. `finalizeDefaultRecovery` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` only when `pendingInstantWithdraws != 0` (lines 644-649). The epoch-N receipt is absent from `instantWithdrawClaimsByEpoch[M]`, so it receives **zero recovery basis**. Meanwhile `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` becomes true (line 696).
4. Attacker calls `claimInstantWithdrawRequest` (lines 380-393): `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[user][M]` (= 0 for this receipt), then the function falls through and pays the full aggregate `instantWithdrawsRequests[user]` **at par** through `_transferFundedClaim`.

The haircut logic "parses" the claim by epoch (`instantWithdrawsRequestsByEpoch[user][defaultEpoch]`), while the payout logic "parses" it by aggregate (`instantWithdrawsRequests[user]`) — the same class of boundary disagreement as the Squid Content-Length smuggling bug.

### Impact Explanation
Two outcomes, both harmful:

- **Theft / reserve dilution**: if the strategy holds any non-reserve underlying (previously funded instant claims of other users, recovery dust, borrower-send leftovers), `_transferFundedClaim` (lines 897-907) pays the unfunded receipt at par while every defaulted-epoch claimant is haircut by `defaultRecoveryPrice`. The attacker extracts a full-price payout for a receipt that contributed nothing to the recovery basis — direct theft from defaulted claimants and prefunded instant claimants.
- **Permanent freezing**: if the only strategy balance is `defaultRecoveryReserve`, the guard at line 904 reverts (`balance - reserve < _amount`), so the attacker's receipt — which `pendingInstantWithdraws` still treats as a real liability — can never be claimed and never entered the haircut. The invariant "one receipt, one deterministically-priced payout" is broken either way.

Loss magnitude equals the stale instant receipt amount, bounded only by how much was requested via instant mode before the default epoch.

### Likelihood Explanation
Requires: instant withdrawals enabled (non-programmable borrower), an unfunded instant request surviving across an epoch boundary, and a subsequent borrower default. The unfunded state is reachable whenever the borrower's returned liquidity at `startEpoch` doesn't cover the instant queue (`pendingInstantWithdraws` is explicitly documented as "the still-unfunded remainder"). No privileged collusion is needed; the attacker is an ordinary KYC'd lender. The window depends on honest-manager funding cadence, which the attacker cannot force but can passively exploit.

### Recommendation
In `defaultPendingClaimBasis()`, include all outstanding instant claims when `pendingInstantWithdraws != 0` — e.g., track a global `instantWithdrawClaims` aggregate rather than only `instantWithdrawClaimsByEpoch[epochNumber]` — or iterate per-user claim bases at finalization. Symmetrically, `_claimDefaultedInstantWithdrawRequest` should haircut *all* of a user's unfunded instant receipts (aggregate minus prefunded portion), not only `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, so the claim path and the basis path agree on the same "message boundary."

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test sketch against test/foundry/IdleCreditVault.t.sol harness
function test_StaleInstantReceiptEscapesDefaultHaircut() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 minted = idleCDO.depositAA(amount);

    // --- Epoch N: APR drops -> requestWithdraw routes to instant receipt ---
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, expected); // honest stop
    vm.prank(manager);
    strategy.setAprsWithBuffer(lastApr - instantDelta - 1, dur, buf); // trigger instant path
    uint256 receipt = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));
    // borrower does NOT prefund: pendingInstantWithdraws == receipt
    assertEq(strategy.pendingInstantWithdraws(), receipt);

    // --- Epoch M runs; borrower defaults ---
    _startEpochAndCheckPrices(1);
    // borrower repays insufficient amount -> CDO enters default, finalizeDefaultRecovery
    _triggerDefaultAndFinalize(recoveredAmount); // recovered < total basis

    // instantWithdrawClaimsByEpoch[epochM] does NOT include epoch-N receipt:
    // attacker's `receipt` is absent from defaultPendingClaimBasis()
    // but defaultInstantWithdrawsFinalized == true.

    // --- Attacker claims aggregate at par ---
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimInstantWithdrawRequest(); // -> strategy.claimInstantWithdrawRequest
    // Either: pays `receipt` at par, draining non-reserve strategy funds meant
    // for haircutted claimants (theft), or reverts NotAllowed at line 904
    // leaving pendingInstantWithdraws permanently unclaimable (freeze).
}
```

Uncertainty note: whether `startEpoch` can be configured by the honest manager to fully fund stale instant receipts was not fully verified; if it always does, the attack window requires a default occurring while prefunding is still incomplete — which is precisely the scenario `defaultInstantWithdrawsFinalized` was designed for, confirming the developers already treat partially-funded instant queues at default time as reachable.
