### Title
Under-scoped signature on `BlockRejection` lets any signer relabel another signer's vote reason (reason_code / RejectReason) while reusing that signer's genuine signature - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockRejection::hash()` (and thus the message the signature actually authenticates) covers only `signer_signature_hash` and `chain_id`; it does **not** cover `reason`, `reason_code`, `metadata`, or `response_data` (which carries `failed_txid`, `tenure_extend_timestamp`, `reject_reason`, etc). `stacks-signer/src/v0/signer.rs::handle_block_rejection` independently re-derives the sender identity from `rejection.recover_public_key()` (ignoring the already-authenticated StackerDB slot owner) and then feeds the *unauthenticated* `reason_code`/`response_data.reject_reason` into `store_and_process_block_rejection`, which persists `(block_hash, signer_address, reject_reason)` and uses accumulated per-reason weight (e.g. `RejectReasonPrefix::ReorgNotAllowed`) to flip `sortition_state.cur_sortition.miner_status = InvalidatedBeforeFirstBlock`. This is precisely the reported bug class: a field that should be authoritative/bound by the signature (the vote's *reason*) is instead freely substitutable by an unauthenticated party, exactly as query/body params overwrote the path-bound identifier in the gRPC advisory.

### Finding Description
`BlockRejection::hash()`:
```

    let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
    structured_data_message_hash(data, domain_tuple)
}
``` [1](#0-0) 

The signature (`sign`/`verify`/`recover_public_key`) is computed solely from this `hash()`, i.e. from `signer_signature_hash` + `chain_id`: [2](#0-1) 

But `BlockRejection` carries several additional fields that are *not* part of the signed payload — `reason`, `reason_code`, `metadata`, `response_data` (which includes `failed_txid`, `tenure_extend_timestamp`, `reject_reason`): [3](#0-2) 

On the signer side, `handle_block_rejection` authenticates the sender purely by `rejection.recover_public_key()` — it does not cross-check this against the already-verified StackerDB slot/public key that delivered the message in `handle_event_match`:
```
let Ok(public_key) = rejection.recover_public_key() else { ... };
let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
if !self.is_valid_signer(&signer_address) { ... }
...
self.store_and_process_block_rejection(
    sortition_state, &mut block_info, &signer_address,
    (&rejection.response_data.reject_reason).into(),
);
``` [4](#0-3) 

`store_and_process_block_rejection` persists the attacker-chosen `reject_reason` keyed to the recovered `signer_address`, and later tallies rejection reasons by weight; specifically `RejectReasonPrefix::ReorgNotAllowed` weight can flip miner validity: [5](#0-4) 

**Root cause / equality broken:** the code implicitly assumes "signature valid ⇒ entire message content (including `reason_code`/`response_data`) was authored by the recovered key." Because `hash()` only binds `signer_signature_hash`+`chain_id`, this assumption is false: *any* previously-observed valid `BlockRejection` signature from a victim signer for block-hash `H` remains valid when reused inside a new `BlockRejection` struct that swaps in a different `reason_code`/`response_data` for the same `H`. Since block rejections are broadcast in the clear over StackerDB for every proposal a signer disapproves of, an attacker (any single other registered signer, i.e. a "one-slot" party — no majority, no victim key needed) can trivially harvest a genuine signature/`signer_signature_hash` pair from a victim and re-emit a doctored `BlockRejection` (different `reason_code`, different `response_data.failed_txid`, different `reject_reason`) on the attacker's own StackerDB slot. `handle_block_rejection` will attribute this doctored reason to the *victim's* address and weight, not the attacker's.

### Impact Explanation
This lets a single malicious signer, with no knowledge of any other party's private key and without needing a majority, fabricate weighted votes with an arbitrary `RejectReasonPrefix`/`reject_reason` attributed to any other signer who has ever rejected the same block hash. Concretely:
- Forging enough `ReorgNotAllowed`-labeled rejections (attributed to victim signers who actually rejected for an unrelated reason) can cross the 30% threshold and flip `sortition_state.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock`, wedging the signer set against a legitimately valid miner/tenure — a signer-side liveness break ("signer wedged into never signing valid blocks" for that miner).
- The same primitive lets an attacker attribute a bogus `response_data.failed_txid`/`ProblematicTransaction` flag with a victim's weight, poisoning `failed_txids` weight accounting used by node/coordinator logic to decide which transactions to drop.

This meets the "High" bar defined in the prompt: a signer can be wedged out of validly signing a miner's blocks based on falsified, unauthenticated vote content attributed to peers.

### Likelihood Explanation
Requires only: (1) being one registered signer among the set (no majority, no other signer's key, no auth token/local access), and (2) having observed one genuine `BlockRejection` broadcast from the target victim for the block hash in question — which is the normal, expected behavior of the consensus-building StackerDB gossip protocol, so the precondition is met essentially every time any signer other than the attacker rejects a proposal. The construction (copy `signer_signature_hash`+`signature`, replace `reason_code`/`response_data`/`reason`) is trivial and entirely off-chain.

### Recommendation
Bind the entire semantically significant content of `BlockRejection` (and analogously `BlockAccepted`'s `response_data`) into the signed hash — include `reason_code`, `response_data` (and ideally `chain_id`, `metadata` as already done) in `BlockRejection::hash()`'s structured-data payload rather than only `signer_signature_hash`. Additionally, `handle_block_rejection`/`handle_block_pre_commit`-style handlers should not treat `recover_public_key()` as sufficient identity binding in isolation from the StackerDB slot's verified sender identity; cross-checking that the recovered address matches the slot owner (or simply trusting the already-verified sender from `handle_event_match` instead of re-deriving it) would close the impersonation/attribution vector even if the hash-scope issue is also fixed.

### Proof of Concept
1. Attacker registers as one of N signers for the active reward cycle (single slot, no special privileges).
2. Victim signer `V` rejects proposed block `H` for reason `RejectReason::ValidationFailed(BadTransaction)`, broadcasting `BlockRejection{signer_signature_hash: H, reason_code: ValidationFailed(BadTransaction), response_data:{failed_txid: Some(tx1), reject_reason: ...}, signature: sig_V}` over its StackerDB slot (`sig_V` = signature over `hash(H, chain_id)` only).
3. Attacker observes this broadcast (all signers observe all StackerDB traffic) and extracts `(H, sig_V)`.
4. Attacker crafts `BlockRejection'{signer_signature_hash: H (unchanged), reason_code: ValidationFailed(ReorgNotAllowed) or ProblematicTransaction, response_data:{failed_txid: Some(tx2), reject_reason: ReorgNotAllowed}, signature: sig_V (reused, unmodified)}` and writes it to the attacker's own StackerDB slot.
5. `rejection.verify(&V_pubkey)` / `rejection.recover_public_key()` on any receiving signer succeeds and returns `V`'s address (since `hash()` is unchanged), because `hash()` never depended on the swapped fields.
6. `handle_block_rejection` on every receiving signer calls `store_and_process_block_rejection(..., signer_address = V, reject_reason = ReorgNotAllowed)`, crediting `V`'s weight toward `RejectReasonPrefix::ReorgNotAllowed` and/or `tx2`'s `failed_txids` weight — content `V` never actually produced.
7. If enough such forged attributions (one per rejecting victim signer, all trivially harvestable) accumulate past the 30% threshold, `sortition_state.cur_sortition.miner_status` is set to `InvalidatedBeforeFirstBlock`, wedging the signer against that miner's subsequent valid proposals.

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }

    /// Recover the public key from the rejection signature
    pub fn recover_public_key(&self) -> Result<StacksPublicKey, &'static str> {
        if self.signature == MessageSignature::empty() {
            return Err("No signature to recover public key from");
        }
        let signature_hash = self.hash();
        StacksPublicKey::recover_to_pubkey_without_validating_low_s(
            signature_hash.as_bytes(),
            &self.signature,
        )
    }

    /// Handle an observed rejection from another signer
    fn handle_block_rejection(
        &mut self,
        rejection: &BlockRejection,
        sortition_state: &mut Option<SortitionsView>,
    ) {
        debug!("{self}: Received a block-reject signature: {rejection:?}");

        let block_hash = &rejection.signer_signature_hash;
        let signature = &rejection.signature;

        // recover public key
        let Ok(public_key) = rejection.recover_public_key() else {
            debug!("{self}: Received block rejection with an unrecovarable signature. Will not store.";
               "signer_signature_hash" => %block_hash,
               "signature" => %signature
            );
            return;
        };

        // authenticate the signature -- it must be signed by one of the stacking set
        let signer_address = StacksAddress::p2pkh(self.mainnet, &public_key);
        if !self.is_valid_signer(&signer_address) {
            debug!("{self}: Received block rejection with an invalid signature. Will not store.";
                "signer_public_key" => ?public_key,
                "signer_address" => %signer_address,
                "signer_signature_hash" => %block_hash,
                "signature" => %signature
            );
            return;
        }

        let Some(mut block_info) = self.block_lookup_by_reward_cycle(block_hash) else {
            if let Err(e) = self.signer_db.add_pending_block_rejection_response(
                block_hash,
                &signer_address,
                (&rejection.response_data.reject_reason).into(),
            ) {
                warn!("{self}: Failed to add pending block rejection response: {e:?}");
            }
            return;
        };

        info!("{self}: Received block rejection";
            "signer_pubkey" => public_key.to_hex(),
            "signer_signature_hash" => %block_hash,
            "consensus_hash" => %block_info.block.header.consensus_hash,
            "block_height" => block_info.block.header.chain_length,
            "reject_reason" => ?rejection.response_data.reject_reason,
        );

        self.store_and_process_block_rejection(
            sortition_state,
            &mut block_info,
            &signer_address,
            (&rejection.response_data.reject_reason).into(),
        );
