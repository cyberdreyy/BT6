### Title
Double-claim of instant-withdraw receipts after default finalization: already-paid `instantWithdrawsRequestsByEpoch` entries are never cleared, letting a user claim the same receipt a second time from the default recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The libssh2 double-free maps here to a double-payout of the same receipt. `claimInstantWithdrawRequest` pays a funded instant receipt and zeroes only the aggregate `instantWithdrawsRequests[_user]`, but never clears the per-epoch basis `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in that same epoch while `pendingInstantWithdraws != 0`, `finalizeDefaultRecovery` marks that epoch as `defaultRecoveryEpoch`, counts the stale basis into `defaultPendingClaimBasis`, and `_claimDefaultedInstantWithdrawRequest` pays the attacker a second time — at `defaultRecoveryPrice` — straight out of `defaultRecoveryReserve`, diluting and draining the reserve owed to honest defaulted claimants.

### Finding Description
In `IdleCreditVault.claimInstantWithdrawRequest` the funded path burns `instantWithdrawsRequests[_user]` and sets it to 0, but leaves `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` untouched (lines 380-392). Those per-epoch mappings are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` (lines 842-856) and are otherwise write-only.

Consequences once `finalizeDefaultRecovery` runs with `defaultRecoveryEpoch == epochNumber` of the stale entries:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis (line 644-649). Already-paid, already-burned receipts inflate `totalBasis`, so `recoveryPrice = reserveAmount / totalBasis` is lower than it should be — every legitimate claimant (pending withdraw receipts, unfunded instant receipts, active AA/BB holders via `activeFinalNAV`) is diluted.
2. `defaultInstantWithdrawsFinalized` is set true when `pendingInstantWithdraws != 0` (line 696). On the attacker's next `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, computes `claimBasis` from the already-paid receipt, burns... nothing extra is needed beyond the burned receipt — `_burn(_user, claimBasis)` — and transfers `claimBasis * defaultRecoveryPrice` from `defaultRecoveryReserve` (lines 842-855). This is the second payout for one receipt — the analog of the freed buffer being freed again and reallocated.

Because `defaultRecoveryReserve -= _amount` (line 915) draws on a fixed reserve sized at finalization, each double claim either directly steals recovered funds destined for other claimants or, once drained, makes later honest claims revert on underflow — permanently freezing unclaimed recovery yield.

The same stale-state shape does not exist on the normal-withdraw side: `_claimFundedWithdrawRequest` leaves `withdrawsRequestsByEpoch` non-zero too (lines 319-350), but `defaultRecoveryEpoch` is always the epoch of default finalization, which is strictly newer than any previously claimed epoch, so only instant receipts — claimable *inside* their request epoch — are re-readable.

### Impact Explanation
An unprivileged KYC-passing lender who made an instant withdrawal can be paid twice for a single receipt: once at par when funded, and again at `defaultRecoveryPrice` after default finalization. Quantified loss: the attacker receives up to an extra `instantWithdrawsRequestsByEpoch[user][defaultEpoch] * defaultRecoveryPrice / 1e18` underlying, and additionally depresses `defaultRecoveryPrice` for all claimants because their already-paid basis inflates `defaultPendingClaimBasis`. Funds are stolen directly from `defaultRecoveryReserve`; when the reserve is exhausted, remaining legitimate defaulted claimants' transactions revert, permanently freezing their recovery yield.

### Likelihood Explanation
Requirements are all attacker- or market-controllable:

- `allowInstantWithdraw` enabled and an epoch in the instant-withdraw window (running epoch phase, instant mode).
- Attacker requests an instant withdraw and claims it (funded via `collectInstantWithdrawFunds`), which is the intended UX.
- Another user's instant request in the same epoch remains partially unfunded so `pendingInstantWithdraws != 0` at finalization — trivially satisfied by a second request the attacker makes with a second address, or any organic request.
- Borrower default in that epoch with any positive recovered amount (`finalizeDefaultRecovery` is called by the honest CDO/manager flow, not by the attacker).

No privileged misbehavior needed; `idleCDO`, borrower, manager act honestly. The only guards — `_onlyIdleCDO`, `defaultRecoveryFinalized` gating — do not detect the stale basis.

### Recommendation
Clear the per-epoch instant receipt records on the funded claim path in `claimInstantWithdrawRequest`: after reading `amount`, zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the same amount (tracking each receipt's request epoch if multiple epochs can coexist, mirroring `withdrawsRequestsByEpoch` clearing in `_clearWithdrawClaimForEpoch`). Alternatively, have `_claimDefaultedInstantWithdrawRequest` derive its basis only from still-outstanding receipts rather than lifetime per-epoch records, and exclude already-funded instant claims from `defaultPendingClaimBasis`.

### Proof of Concept
Foundry fork PoC outline (against `test/foundry` harness style, e.g. `IdleCreditVault.t.sol` / `IdleCDOEpochQueue.t.sol` setup):

```solidity
function testDoubleClaimInstantReceiptAfterDefault() external {
    // 1. Deposit AA so the vault is funded; start epoch 0 (running).
    _depositWithUser(attacker, amountA);
    _depositWithUser(victim,   amountV);
    _startEpochAndCheckPrices(0);

    // enable instant withdraws
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(delay, minAprDelta, false);

    // 2. Attacker + victim both request instant withdraws in epoch N.
    cdoEpoch.requestInstantWithdraw(attackerAmt, AAtranche); // via CDO path
    cdoEpoch.requestInstantWithdraw(victimAmt,   AAtranche);

    // 3. Fund only the attacker's receipt: borrower/CDO calls
    //    collectInstantWithdrawFunds(attackerAmt) so pendingInstantWithdraws = victimAmt.
    //    Attacker claims at par.
    cdoEpoch.claimInstantWithdrawRequest(); // attacker paid; instantWithdrawsRequestsByEpoch[attacker][N] STALE

    // 4. Borrower defaults in epoch N. Manager runs _handleBorrowerDefault /
    //    finalizeDefault + finalizeDefaultRecovery(recovered, source).
    //    defaultPendingClaimBasis() includes instantWithdrawClaimsByEpoch[N]
    //    = attackerAmt + victimAmt  (attackerAmt already paid -> inflated basis,
    //    recoveryPrice pushed down for everyone).

    // 5. Attacker calls claimInstantWithdrawRequest() again:
    //    _claimDefaultedInstantWithdrawRequest reads stale basis, burns receipt,
    //    pays attackerAmt * defaultRecoveryPrice / 1e18 from defaultRecoveryReserve.
    uint256 balBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 secondPayout = underlying.balanceOf(attacker) - balBefore;
    assertGt(secondPayout, 0); // receipt paid twice

    // 6. Victim's defaulted-epoch instant claim now reverts on
    //    defaultRecoveryReserve underflow or pays less than its fair share.
}
```

Key assertions: `strategy.instantWithdrawsRequestsByEpoch(attacker, epochN)` remains non-zero after the funded claim; `defaultPendingClaimBasis()` counts it; the second claim transfers recovery reserve to the attacker.
