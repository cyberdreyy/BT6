### Title
`pause()` and `emergencyShutdown()` do not gate live user fund flows — `depositDuringEpoch`, `requestWithdraw` and claims remain callable while the vault is "paused" - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The Rubicon M-11 bug class is: a privileged "stop/close" function flips a flag that no state-changing path ever reads, so pausing is cosmetic. The same class exists in the epoch credit-vault runtime: `PausableUpgradeable._paused` is only enforced on `_deposit` via `whenNotPaused`, while every fund-moving path that is actually reachable during the phases where pausing matters — `depositDuringEpoch`, `requestWithdraw`, `claimWithdrawRequest`, `claimInstantWithdrawRequest` — never consults `paused()`. In the base `IdleCDOCreditVault`, `emergencyShutdown()`/`_emergencyShutdown()`/`restoreOperations()` are literal no-ops.

### Finding Description
- `IdleCDOCreditVault.emergencyShutdown()` delegates to `_emergencyShutdown(false)`, which is an empty function, and `restoreOperations()` is also an empty function in the base contract [1](#0-0) . Calling the advertised emergency entrypoint on the credit-vault runtime therefore changes nothing: it does not pause, does not set `skipDefaultCheck`, and does not touch withdraw flags.
- `pause()` only calls `_pause()` [2](#0-1) . The sole consumer of `paused()` is `whenNotPaused` on `_deposit` [3](#0-2) .
- `depositDuringEpoch` has no `paused()` check; it gates on `isDepositDuringEpochDisabled`, `skipDefaultCheck`, `isProgrammableBorrower`, `isAYSActive`, `isEpochRunning`, `epochEndDate` and `isWalletAllowed` [4](#0-3) . Since `startEpoch()` itself calls `_pause()` [5](#0-4) , the contract is permanently "paused" during every running epoch and `depositDuringEpoch` still executes — proof the flag is dead for this path. A guardian calling `pause()` mid-epoch therefore blocks nothing that wasn't already blocked.
- `requestWithdraw` gates only on `allowAAWithdrawRequest`/`allowBBWithdrawRequest` and KYC, never on `paused()` [6](#0-5) . `claimWithdrawRequest` and `claimInstantWithdrawRequest` likewise ignore `paused()` [7](#0-6) .
- The only way a privileged actor actually freezes these paths is `emergencyShutdown()` (which in `IdleCDOEpochVariant` sets `skipDefaultCheck` and clears the allow flags [8](#0-7) ) — but `emergencyShutdown` is a no-op in `IdleCDOCreditVault`, and on any deployment of the base runtime the guardian has no functioning "stop" for anything other than fresh `depositAA/depositBB` calls.

### Impact Explanation
During an emergency (strategy exploit, borrower distress, accounting mispricing), the guardian calls `pause()` or `emergencyShutdown()` expecting the market to halt. In `IdleCDOCreditVault` `emergencyShutdown` does literally nothing, so `depositAA/depositBB` continue to pull underlyings and route them to the strategy. In the epoch variant, a plain `pause()` leaves `requestWithdraw` live whenever the allow flags are set (buffer phase), so a KYC'd attacker can burn tranche tokens into fixed-value withdrawal receipts at the pre-incident tranche price, inflating `pendingWithdrawFees` and `pendingWithdraws` — obligations the borrower must repay at the next `stopEpoch` — while honest users' NAV absorbs the loss. Loss is bounded by the attacker's tranche balance valued at pre-incident price versus post-loss price (up to full principal when a loss that has occurred but not yet been crystallized).

### Likelihood Explanation
Requires only an unprivileged KYC-passing tranche holder acting during the window between an incident and successful loss crystallization, plus a guardian choosing the documented `pause()`/`emergencyShutdown()` response. `emergencyShutdown` on the base runtime fails unconditionally. Partial mitigation exists: `requestWithdraw` calls `_updateAccounting()`, which reverts `Default()` once a BB-wiping loss is detected, and the epoch variant's `_emergencyShutdown` does set effective flags — so the realized impact is strongest for the standalone `IdleCDOCreditVault` deployment and for sub-total losses where pause is invoked but accounting does not revert.

### Recommendation
Make the stop primitive real: have `_emergencyShutdown` in `IdleCDOCreditVault` actually call `_pause()` and set `skipDefaultCheck`, implement `restoreOperations()`, and add a `paused()` check (or fold `skipDefaultCheck`) into `depositDuringEpoch` and `requestWithdraw` so that `pause()` alone freezes all user fund flows, matching the guardian's documented intent.

```text
  function _emergencyShutdown(bool isAAWithdrawAllowed) internal override {
    // prevent deposits
    if (!paused()) {
      _pause();
    }
    // Preserve AA requests only if they were already open. This keeps a forced mid-epoch loss or
    // prior emergency from reopening them, while a normal explicit-loss stop can leave them open.
    if (!isAAWithdrawAllowed) {
      allowAAWithdrawRequest = false;
    }
    allowBBWithdrawRequest = false;
    // Persist the emergency state and let authorized forced accounting crystallize the loss.
    skipDefaultCheck = true;
  }
```
