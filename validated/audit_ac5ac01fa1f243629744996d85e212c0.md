### Title
Fee-on-transfer underlying causes `IdleCreditVault` to mint unbacked strategy tokens, insolventing later claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

`IdleCreditVault.deposit()` mints strategy tokens 1:1 with the *requested* `_amount` after pulling underlying via `safeTransferFrom`, never measuring the amount actually received. If the vault's underlying token charges a transfer fee (e.g., USDT with fee enabled, or any ERC20 with transfer fees chosen as the pool currency by `IdleCreditVaultFactory`), the strategy mints more claimable receipt tokens than it holds in underlying. The same face-value accounting appears in `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery`, which credit `defaultRecoveryReserve`/funded claims at the nominal pulled amount. The last claimers against a fixed pool of underlying are left unpaid — the direct analog of the Kairos fee-token insolvency.

### Finding Description

In `IdleCreditVault.deposit` (lines 596–617):

```solidity
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
_mint(msg.sender, _amount);
```

The IdleCDO layer is partially protected: `IdleCDOCreditVault._deposit` mints tranche tokens based on the balance delta (`_contractTokenBalance(_token) - _preBal`), so the user gets tranche tokens only for tokens actually received. But then `IIdleCDOStrategy(strategy).deposit(_amount)` is called with the *nominal* `_amount`, and the strategy (a) transfers `_amount` out of the CDO — more than the `_amount - fee` just received, draining pre-existing idle balance if present, else reverting — and (b) mints `_amount` strategy tokens to the CDO. The minted strategy-token supply (which backs `withdrawsRequests`, `instantWithdrawsRequests`, and active-NAV claims 1:1) therefore exceeds the underlying actually held by the strategy.

The same pattern repeats at claim funding:

- `collectWithdrawFunds` (line 428) pulls `_amount` and treats it as fully funding `pendingWithdraws`; with a fee, `_amount - fee` arrives but `pendingWithdraws` is decremented by `_amount`.
- `collectInstantWithdrawFunds` (line 402) decrements `pendingInstantWithdraws` by the face `_amount` while receiving less.
- `finalizeDefaultRecovery` (line 708) sets `defaultRecoveryReserve = _recoveredAmount + prefunded` but only `_recoveredAmount - fee` lands; `_transferDefaultRecovery` decrements the reserve against a thinner balance, so the final recovery claimant reverts.
- `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` (lines 139–149) pulls `_underlyings` and pays out `_underlyings - _totFee`; with a fee token it receives `_underlyings - transferFee` and reverts on the second transfer.

Broken invariant: strategy-token supply == underlying claimable balance (solvency / one receipt one payout). The `_transferFundedClaim` reserve guard (lines 899–906) only protects the *default recovery reserve* from funded claims; it does not prevent the reserve itself from being credited above the real balance.

### Impact Explanation

With a fee `f%` on transfers, each deposit of `A` mints `A` claimable strategy tokens while the strategy net-receives `A(1 - f)`. Across N depositors, the strategy is short `Σ A·f`. Claimants via `claimWithdrawRequest`/`claimInstantWithdrawRequest` are paid in FIFO-by-transaction order, so the tail claimants' transfers revert permanently — identical to the report's case 2 where the 10th of 10 equal claimants cannot withdraw. For a 5% fee token and equal deposits, the last ~5% of total claim value is unpayable. Alternatively, if the CDO has no surplus balance, `strategy.deposit(_amount)` reverts on the pull and the vault is unusable for deposits at all (permanent freezing of the deposit path). In the default path, `defaultRecoveryPrice` is computed against an inflated `reserveAmount`, so recovery claimants receive the promised price only until the real balance is exhausted; the last claimant reverts in `_transferDefaultRecovery` via `defaultRecoveryReserve -= _amount` or the raw `safeTransfer`.

### Likelihood Explanation

The credit vault is a generic factory-deployed strategy whose underlying is chosen per-deployment (`initialize` accepts any `_underlyingToken`). The design intent is institutional pool currencies (USDC/USDT); USDT supports a fee flag that is currently 0 but can be activated by Tether, and other fee-bearing stables or rebasing-with-fee tokens are valid deployment targets. No attacker action is needed beyond using the vault once it exists — the accounting defect is deterministic. If the underlying is confirmed fee-free at deploy time and forever, the issue does not trigger; it is conditional on token behavior, hence Medium-High rather than Critical. No existing guard (skim, `_checkDefault`, reserve checks) intercepts the mismatch because the protocol never measures received amounts.

### Recommendation

Measure actual received amounts at every inbound `transferFrom` boundary:

```solidity
// IdleCreditVault.deposit
uint256 before = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - before;
_mint(msg.sender, received);          // mint for what actually arrived
totEpochDeposits += received;
```

Apply the same balance-delta pattern in `collectWithdrawFunds`, `collectInstantWithdrawFunds`, and `finalizeDefaultRecovery` (credit `pendingWithdraws`/`defaultRecoveryReserve` by `received`, not `_amount`/`_recoveredAmount`), and in `IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` (compute `_totFee` on the received amount). Correspondingly, `IdleCDOCreditVault._deposit` should pass the received amount (`_contractTokenBalance(_token) - _preBal`) to `IIdleCDOStrategy(strategy).deposit(...)` instead of `_amount`. Alternatively, explicitly document/enforce that only non-fee tokens are supported and revert otherwise.

        super._transfer(f, address(0xdead), fee);

Expected result: `vault.balanceOf(cdo)` exceeds `fee.balanceOf(vault)` by `totalDeposits * feeBps`, so aggregate claims revert for the last claimants — quantified loss `Σ deposits * fee`.
