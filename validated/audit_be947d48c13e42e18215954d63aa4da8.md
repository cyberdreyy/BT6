### Title
Repeated `requestWithdraw` overwrites `lastWithdrawRequest`, letting a loss-epoch receipt escape `lossRecoveryPriceByEpoch` and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (CVE-2019-20792) is a missing uniqueness check on insertion: an object already in a list is added again, corrupting ownership tracking and producing a double free. The analog in `IdleCreditVault` is in `requestWithdraw`: a user can register a second withdrawal receipt while an earlier one is still unclaimed, and the single-slot marker `lastWithdrawRequest[_user]` is overwritten (`IdleCreditVault.sol:282`, `293`). When the earlier receipt belongs to an epoch that suffered a `stopEpochWithDuration` loss (`lossRecoveryPriceByEpoch`), `_claimLossAdjustedWithdrawRequest` only ever inspects `lastWithdrawRequest[_user]` (`IdleCreditVault.sol:790-791`), so the haircut-bearing epoch is never found and the entire aggregate `withdrawsRequests[_user]` is paid at par in `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:338-349`).

### Finding Description
`requestWithdraw` records each receipt in two places: the per-epoch map `withdrawsRequestsByEpoch[_user][currentEpoch]` and the aggregate `withdrawsRequests[_user]`, but stores only one epoch in `lastWithdrawRequest[_user]`:

- `IdleCreditVault.sol:282` — `lastWithdrawRequest[_user] = currentEpoch;`
- `IdleCreditVault.sol:292-293` — `withdrawsRequests[_user] += _amount; withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;`

There is no check that `lastWithdrawRequest[_user]` is zero or that the user has no uncleared loss-epoch receipt — the missing uniqueness check. On claim, `claimWithdrawRequest` (line 301) runs `_claimLossAdjustedWithdrawRequest` first, which derives the loss epoch solely from `lastWithdrawRequest[_user]`:

- `IdleCreditVault.sol:790-792` — `uint256 lossEpoch = lastWithdrawRequest[_user]; uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]; if (lossRecoveryPrice == 0) return amount;`

If the user re-requested in a later epoch, `lossEpoch` is the later (healthy) epoch, `lossRecoveryPrice` is 0, and the function returns without touching `withdrawsRequestsByEpoch[_user][E_loss]`. Execution then falls to `_claimFundedWithdrawRequest`, which pays `amount = withdrawsRequests[_user] + apr0 buckets` in full via `_transferFundedClaim` (lines 338-349). The epoch-`E_loss` portion, which should have paid `claimBasis * lossRecoveryPrice / RECOVERY_FULL` (line 799), is paid 1:1 instead.

Attack sequence (running/buffer phases, non-APR0 mode):

1. Attacker (KYC'd tranche holder) calls `requestWithdraw` during the buffer of epoch `E` — receipt recorded at `withdrawsRequestsByEpoch[user][E]`, `lastWithdrawRequest = E`.
2. Honest manager calls `stopEpochWithDuration(..., _lossAmount)`; borrower funds only `pendingToFund`, so `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[E] < RECOVERY_FULL` and clears `pendingWithdraws` (`IdleCreditVault.sol:411-421`). `epochNumber` becomes `E+1`.
3. In the new buffer, attacker calls `requestWithdraw` again with a small amount. Now `lastWithdrawRequest[user] = E+1` and `withdrawsRequestsByEpoch[user][E+1]` holds the dust receipt.
4. After another epoch boundary (so `epochNumber > lastWithdrawRequest`, passing the gate at line 326), attacker calls `cdoEpoch.claimWithdrawRequest()`. The loss lookup targets `E+1` (no price) → skipped; the funded path pays the whole aggregate, including the `E` receipt, at par.

The same shape repeats for the default path: `_claimDefaultedWithdrawRequest` clears only `defaultRecoveryEpoch` (line 773-774), but that is keyed on the strategy's epoch, not the user's marker, so the exploitable gap is specifically the loss-adjusted path's reliance on the single overwritten slot.

### Impact Explanation
Broken invariant: loss waterfall / fair burn. A pending-receipt holder whose epoch was haircut is paid at par, while the funded reserve only contains `pendingToFund = pendingBasis - pendingLoss` for that cohort. The excess paid out is `claimBasis_E * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`, drawn from strategy underlyings that back other funded claims and post-default/post-loss claimants — i.e., direct theft / insolvency of the claim pool proportional to the attacker's share of the loss epoch's pending basis. A whale holding most of the epoch's pending receipts escapes nearly the entire `pendingLoss`, which is then socialized onto remaining claimants and LPs.

### Likelihood Explanation
Requires (a) a `stopEpochWithDuration` with nonzero `_lossAmount`, which is a designed borrower-shortfall mode, and (b) the attacker making a second (arbitrarily small) `requestWithdraw` in a later epoch before claiming. Both are unprivileged actions available to any KYC'd tranche holder; no privileged cooperation, default, or timing edge is needed. The existing guards do not stop it: the epoch gate at line 326 only checks the *latest* marker, `_clearWithdrawClaimForEpoch` is never reached for the stale epoch, and `collectWithdrawFunds` correctly records the price — it is simply never looked up.

### Recommendation
In `requestWithdraw`, enforce uniqueness of the pending receipt epoch marker: revert if `lastWithdrawRequest[_user] != 0` and `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` (or more conservatively, if the user has any unsettled loss-adjusted receipt). Alternatively, store the user's loss-epoch receipts in a set/linked list and iterate all epochs with `lossRecoveryPriceByEpoch != 0` inside `_claimLossAdjustedWithdrawRequest` instead of relying on the single `lastWithdrawRequest` slot.

### Proof of Concept
Foundry fork PoC sketch (extends the harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossEscapeViaSecondRequest() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());

    // deposit and enter epoch 0, stop it so we can request in the buffer of epoch 1
    uint256 amount = 10000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // step 1: request withdraw of half in epoch 1
    uint256 req1 = cdoEpoch.requestWithdraw(minted / 2, address(AAtranche));

    // step 2: next stopEpoch realizes a loss via stopEpochWithDuration,
    // funding only pendingToFund < pendingBasis
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 totalBasis = pendingBasis + cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 loss = pendingBasis / 2; // 50% haircut on pending receipts
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(loss);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower);
    IERC20(defaultUnderlying).approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), loss);
    // lossRecoveryPriceByEpoch[epoch-of-req1] is now ~ RECOVERY_FULL/2

    // step 3: request a dust withdraw in the new epoch -> overwrites lastWithdrawRequest
    _transferBurnedTrancheTokens(address(this), true);
    uint256 req2 = cdoEpoch.requestWithdraw(1, address(AAtranche));

    // step 4: roll one full epoch and claim
    _startEpochAndCheckPrices(strategy.epochNumber());
    _stopEpochAndCheckPrices(strategy.epochNumber(), initialProvidedApr, _expectedFundsEndEpoch());

    uint256 balPre = IERC20(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = IERC20(defaultUnderlying).balanceOf(address(this)) - balPre;

    // expected fair payout: req1 * lossRecoveryPrice/RECOVERY_FULL + req2
    // actual: req1 + req2  -> attacker was paid at par on the loss-epoch receipt
    assertGt(got, req1 / 2 + req2); // haircut escaped
}
```

The assertion demonstrates the overpayment: `claimWithdrawRequest` returns `req1 + req2` at par because `_claimLossAdjustedWithdrawRequest` looked up the second request's epoch instead of the loss epoch.
