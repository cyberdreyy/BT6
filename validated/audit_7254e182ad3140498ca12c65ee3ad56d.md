### Title
Stale Confirmations From Deleted Members Still Count Toward Execution Threshold - (File: multisig2/src/lib.rs)

### Summary
The bug-class pattern is a validity check that is silently skipped in a specific branch, letting a party benefit from a value that should no longer be trusted (accrued fees not re-validated against slippage). The direct analog in this repository is in `multisig2/src/lib.rs`: when a member is deleted from a multisig, only the *requests that member created* are purged; confirmations that member previously placed on *other, still-pending requests* are never removed. Those stale confirmations continue to count toward `num_confirmations` in `confirm()`, breaking the binding "confirmations counted == confirmations from live members."

### Finding Description
`confirm()` reads the confirmation set for a request and executes it once the size threshold is reached, using only the set's cardinality, without validating that each entry in the set corresponds to a still-current member: [1](#0-0) 

`delete_member()` removes the member from `self.members` and deletes the *access key*, but the request/confirmation cleanup only targets requests **created by** that member (`r.member == member`), not requests where that member merely **confirmed**: [2](#0-1) 

Because `confirmations` is a `HashSet<String>` keyed by the serialized `MultisigMember`, a confirmation string left behind by a removed member is never invalidated, and `assert_valid_request()` never re-validates the confirmation set members either: [3](#0-2) 

The binding that should hold is:
```
executed_confirmations == confirmations from accounts/keys currently in self.members
```
Instead the actual binding is:
```
executed_confirmations == confirmations ever recorded (including from removed members)
```

### Impact Explanation
This matches the "Critical" bucket: a multisig request can be executed below the intended live-member threshold. For example, with `num_confirmations = 3` and members {A, B, C, D}: A creates a request, B confirms it (2/3), then D and the multisig itself agree to remove B (e.g. B's key was compromised, or B left the org) via `DeleteMember`. B's stale confirmation on A's pending request is never purged. Only 1 more confirmation from a currently-live member (e.g. C) is now needed to reach the "3" count, even though only 2 live members (A, C) actually approved — B is no longer a member. The contract will execute transfers, `FunctionCall`s, `AddKey`, or further `DeleteMember`/`AddMember` actions with insufficient live-member consensus, which can move funds or change multisig membership improperly.

### Likelihood Explanation
This requires no privileged access beyond being a normal multisig member creating/confirming a request before a membership change — a routine operational flow (member offboarding after partial confirmations exist). It does not require redeploys, foundation intervention, or exploiting a validator; any member set change (e.g., replacing a departing employee's key) while a request has outstanding confirmations from that departing member triggers the flaw. This is a realistic and likely-to-occur operational sequence for any long-lived multisig.

### Recommendation
When deleting a member, iterate over `self.confirmations` for *all* active requests (not just those the member authored) and remove that member's confirmation string from each set. Alternatively, re-validate on `confirm()`/execution that every entry in the confirmations set still corresponds to a current `self.members` entry before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. A calls `add_request` to transfer funds to attacker-controlled account, then `confirm` — confirmations = {A} (via `add_request_and_confirm`, size 1).
3. B calls `confirm(request_id)` — confirmations = {A, B}, size 2 (< 3, not yet executed). [1](#0-0) 
4. The remaining members submit and confirm a `DeleteMember { member: B }` request (a separate, self-request action) to remove B (e.g., because B is leaving or B's key is suspected compromised). [2](#0-1) 
5. Because `delete_member` only clears requests *authored* by B (`r.member == member`), the transfer request from step 2 (authored by A) still exists with confirmations = {A, B} intact, even though B is no longer in `self.members`.
6. C calls `confirm(request_id)` — confirmations size becomes 3, meeting `>= self.num_confirmations`, and `execute_request` fires the transfer — despite only 2 of the current 3 live members (A, C) having actually approved it. [4](#0-3)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
