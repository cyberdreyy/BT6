### Title
Anyone can force-fulfill a user's write-off request, front-running cancellation and capturing stale-price spread - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The CVE describes a forced action on behalf of a user: an unauthenticated request to a state-changing endpoint causes an effect (logout) the victim did not initiate. The analog in idle-tranches is `fullfillWriteOffRequest` in `IdleCreditVaultWriteOffEscrow`, which any EOA can call to execute a lender's write-off request, even while the lender is attempting to cancel it via `deleteWriteOffRequest`. Because the request price is fixed at creation time and never re-checked against the current tranche price, a fulfiller can capture any positive drift in tranche value at the requester's expense, and the requester is additionally charged the `exitFee`.

### Finding Description
A lender escrow tranche tokens and fixes `underlyingsRequested` via `createWriteOffRequest` [1](#0-0) . Cancellation is only possible via `deleteWriteOffRequest`, which returns the escrowed tranches [2](#0-1) . However, `fullfillWriteOffRequest` can be invoked by any wallet, requires only that `_tranches` equals the stored amount and `_underlyings` is at least the requested amount, and pays the escrowed tranche tokens to `msg.sender` [3](#0-2) . There is no staleness check between `userRequests[_user].underlyings` and the tranche's current value (`_tranchePrice` on the CDO), and no grace window or owner consent at fulfillment time.

Consequences:
1. Denial of cancellation: an attacker can front-run `deleteWriteOffRequest` with `fullfillWriteOffRequest`, forcing the trade the user is actively trying to abort (the direct analog of the forced logout — a state transition against the victim's will).
2. Stale-price extraction: requests are created during a running epoch [4](#0-3) ; tranche price drifts with `_updateAccounting` at `stopEpoch`, interest accrual, or `finalizeDefault` recovery repricing [5](#0-4) . If tranche value appreciates above the requested underlyings, the fulfiller buys below market and pockets the spread.
3. Forced fee: the victim pays `exitFee` (up to `MAX_EXIT_FEE = 1%`) on fulfillment even though they may have preferred to keep the tranches [6](#0-5) .

### Impact Explanation
An unprivileged attacker who observes a pending `WriteOffRequest` can, at any time the epoch is running, force-execute it. If the tranche's mark price has risen (or if the requester simply changed their mind / sees a better offer coming from the borrower), the attacker realizes `currentTrancheValue - underlyingsRequested` as a profit, extracted directly from the lender's escrowed position, plus the lender loses `exitFee` on the notional. The loss is bounded by the tranche's price drift but is a direct, quantifiable transfer of value: e.g., a request for 100k USDC against tranches now worth 110k USDC yields the attacker ~10k minus the 0.1–1% fee they do not pay (the fee is deducted from the user's proceeds [7](#0-6) ).

### Likelihood Explanation
Medium. Requests live in `userRequests` until filled or deleted and can only be created while an epoch is running, so they can sit stale for an entire epoch+buffer. Any EOA can fulfill; no KYC, role, or timing gate applies to the fulfiller [8](#0-7) . Profit materializes whenever tranche NAV drifts up relative to the stale ask, or purely as griefing by front-running `deleteWriteOffRequest`. No existing guard (nonReentrant, WrongRequest check, epoch gating) prevents it — the only validation is that the fulfiller pays at least the stored ask.

### Recommendation
- Add a deadline/TTL to `WriteOffRequest` so stale asks expire automatically, and/or store the request creation epoch and reprice `underlyings` against the current tranche price at fulfillment.
- Optionally require an opt-in flag or a short challenge window, or let the fulfiller pass a min-acceptance from the user's side (e.g., user-signed order) rather than a standing open order.
- At minimum, make `fullfillWriteOffRequest` unreachable in the same block as a pending `deleteWriteOffRequest` is less relevant than expiring orders — order expiry is the standard fix for this forced-execution class.

### Proof of Concept
Foundry fork PoC (scaffold, to run against a mainnet fork with an active epoch):

```solidity
// test/foundry/WriteOffEscrowForcedFulfill.t.sol
function test_ForcedFulfillCapturesStalePrice() public {
  // Setup: cdo = deployed IdleCDOEpochVariant, escrow = AA escrow, lender is KYC'd
  // 1. Epoch is running. Lender creates request:
  vm.startPrank(lender);
  tranche.approve(address(escrow), trancheAmt);
  escrow.createWriteOffRequest(trancheAmt, 100_000e6); // asks 100k USDC
  vm.stopPrank();

  // 2. Time passes / accounting updates push tranche price up.
  //    (e.g., warp through stopEpoch with interest so priceAA increases,
  //     making trancheAmt worth ~110k USDC)
  // ...

  // 3. Attacker front-runs lender's deleteWriteOffRequest in mempool:
  vm.prank(lender);
  // tx: escrow.deleteWriteOffRequest()  <- pending in mempool

  vm.startPrank(attacker);
  underlying.approve(address(escrow), 100_000e6);
  escrow.fullfillWriteOffRequest(lender, trancheAmt, 100_000e6);
  vm.stopPrank();

  // Lender's delete reverts (Is0), attacker holds trancheAmt worth ~110k
  // after paying 100k; lender received ~99.9k after exitFee.
  assertEq(tranche.balanceOf(attacker), trancheAmt);
  assertGt(trancheValueNow(trancheAmt), 100_000e6);
}
```

Confidence note: this is the closest available analog to the "unauthenticated forced action" bug class. Whether forced fulfillment of a standing sell order counts as a vulnerability depends on design intent — the code comment explicitly permits any-wallet fulfillment — but the absence of expiry/staleness protection makes the value extraction concrete.

  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;

  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
```

  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }
```
