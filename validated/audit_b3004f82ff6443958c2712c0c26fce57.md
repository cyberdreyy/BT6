### Title
Permanent stopEpoch DoS via lingering APR0 withdraw bucket when APR is changed off zero - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` reverts unconditionally whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`. An unprivileged lender can keep the global APR0 principal bucket non-zero by opening a withdraw request while the vault runs at `unscaledApr == 0`. Once the honest manager later sets a non-zero APR (a routine, permitted call), every subsequent `stopEpoch`/`stopEpochWithDuration` invocation reverts in the strategy hook, freezing epoch settlement and all queued withdraw claims until APR is returned to zero and a stop succeeds — and the attacker can re-arm the freeze each time APR is zero.

### Finding Description
The external report is a slice-triggered Denial of Service; the credit-vault analog is a state-triggered halt of the epoch settlement path. In `IdleCreditVault.requestWithdraw`, requests made while `unscaledApr == 0` are routed to `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` (`IdleCreditVault.sol:567-577`, called at `IdleCreditVault.sol:285-286`). At stop-epoch time the CDO calls `prepareStopEpochWithApr0`, which contains:

```solidity
// IdleCreditVault.sol:499-508
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`unscaledApr` is settable at any time by the manager/CDO via `setAprsWithBuffer`/`setApr` (`IdleCreditVault.sol:217-235`) — an honest privileged action, consistent with the threat model. The attacker is only a KYC-passed lender calling `requestWithdraw` during a zero-APR epoch. Because `prepareStopEpochWithApr0` is invoked inside the CDO's stopEpoch path (the call site lives in `IdleCDOEpochVariant.sol`), the revert propagates and the entire epoch stop reverts. The `apr0TotalPrincipal` bucket is only cleared inside `prepareStopEpochWithApr0` itself (`apr0TotalPrincipal = 0` at line 540) or piecewise via `_clearWithdrawClaimForEpoch` during default claims — so while APR stays non-zero and no default is finalized, there is no code path that drains it.

Broken invariant: epoch-state liveness — a single user's receipt must never be able to veto `stopEpoch` for the whole vault.

### Impact Explanation
Temporary freezing of all user funds with a quantified lower bound: while the freeze holds, no `stopEpoch` can execute, so no `pendingWithdraws` are funded by `collectWithdrawFunds`, `epochNumber` never advances, and every `claimWithdrawRequest` keeps reverting at the `epochNumber <= lastWithdrawRequest[_user]` gate (`IdleCreditVault.sol:326`). All queued withdrawers plus all active LPs are locked for the duration of the freeze. The freeze is recoverable only by the manager restoring `unscaledApr = 0` and completing a stop — and the attacker can immediately re-request an APR0 withdraw in that window to re-poison the bucket, repeating indefinitely. Denominator: total vault TVL plus pending receipts.

### Likelihood Explanation
Requires only: (1) an epoch configured at `unscaledApr == 0` (a supported mode — dedicated APR0 accounting exists), (2) any allowed lender requesting a withdraw during it, and (3) the manager later setting a non-zero APR before the APR0 bucket settles — a normal operational step, not attacker-controlled privilege. No race, no capital beyond the withdraw amount, no privileged collusion. The guard at line 506 explicitly encodes "APR0 principal is only valid while APR is 0" but enforces it by reverting the vault-wide settlement instead of settling or migrating the bucket.

### Recommendation
Do not revert on `unscaledApr != 0` with a non-zero `apr0TotalPrincipal`. Settle the APR0 bucket with zero net interest (skip the pro-rata allocation and just close `apr0TotalPrincipal = 0`, recording `apr0RateByEpoch[epochNumber] = 0`), or compute the split against the last APR=0 basis, so `stopEpoch` remains live regardless of APR transitions. Alternatively, route new `requestWithdraw` calls to the normal path (not `_requestWithdrawApr0`) once the APR for the settlement epoch is non-zero, preventing re-arming.

