### Title
Service container `user` executor option bypasses `AllowedUsers` restriction that build containers enforce - (File: executors/docker/docker.go)

### Summary
`ImageDockerOptions.Expand` lets a job (including via `inputs:` expansion) set an arbitrary `executor_opts.docker.user` for both build images and service images. The build-container path validates the resulting user against the runner's configured `AllowedUsers` allowlist, but the service-container path does not, letting a pipeline author run service containers as a user (e.g. `root`) that the runner admin explicitly disallowed.

### Finding Description
`ImageDockerOptions.User` is a job/input-controlled field with `inputs:"expand"`, expanded via `vars.ExpandValue` in `ImageDockerOptions.Expand`. [1](#0-0) 

For the **build** container, `executors/docker/docker.go`'s `getBuildContainerUser` computes the user string and then explicitly checks it against the runner-configured allowlist before use:
```go
func (e *executor) getBuildContainerUser(imageDefinition spec.Image) (string, error) {
	user := e.Config.Docker.User
	if user == "" {
		user = string(imageDefinition.ExecutorOptions.Docker.Expand(e.Build.GetAllVariables()).User)
	}
	if !e.Config.Docker.IsUserAllowed(user) {
		return "", fmt.Errorf("user %q is not an allowed user: %v", user, e.Config.Docker.AllowedUsers)
	}
	return user, nil
}
``` [2](#0-1) 

For **services**, `createServiceContainerConfig` takes the exact same job/input-controlled, expanded value and assigns it directly to `container.Config.User` with no `IsUserAllowed` check at all:
```go
config.User = string(definition.ExecutorOptions.Docker.Expand(e.Build.GetAllVariables()).User)
``` [3](#0-2) 

This is confirmed by the test suite exercising exactly this expansion path for services without any allowlist enforcement test: `TestExpandingInputs`'s "expand inputs in service docker user" subtest shows `${{ job.inputs.any_input }}` flowing straight into `Services[0].ExecutorOptions.Docker.User`, whereas `TestDockerImageWithUser` (which tests `AllowedUsers` enforcement) only exercises the build-image path via `createContainer`/`getBuildContainerUser`. [4](#0-3) [5](#0-4) 

An unprivileged pipeline author who controls a job's `services:` block (or a CI/CD input feeding into it via `${{ job.inputs.* }}`) can therefore set `executor_opts.docker.user` on a service image to any value, e.g. `root` or `0`, even when the runner administrator has configured `AllowedUsers` specifically to prevent jobs from running any runner-managed container as root/privileged UIDs. The allowlist check exists and is correctly wired for the build container, so this is not "restating a documented insecure admin choice" — it is a real, inconsistent enforcement gap between two code paths that use the same admin-configured control.

### Impact Explanation
A job can force a GitLab-managed service container to run as an operator-restricted user (e.g. root) despite the admin's `AllowedUsers` policy explicitly forbidding that user for containers spawned by the runner. This breaks the "Runner-enforced restrictions on images, services, pull policies, users, service accounts, namespaces, and volumes must hold against user-controlled input" invariant. Depending on the service image and any shared volumes/network with the build container, this can materially increase what an attacker-controlled service process can do (e.g., writing as root to shared bind-mounts, or exploiting service-image root-owned files) that the AllowedUsers policy was meant to prevent.

### Likelihood Explanation
This requires only a normal pipeline author's ability to define `services:` with `executor_opts.docker.user`, or to control an `inputs:` value that ExpandInputs plugs into that field — no special executor configuration is exploited beyond the fact that `AllowedUsers` is configured. It is fully reachable in any docker executor job. Repeatable deterministically.

### Recommendation
Apply the same `e.Config.Docker.IsUserAllowed(user)` check in `createServiceContainerConfig` (or a shared helper) before setting `config.User` for service containers, returning an error consistent with the build-container path, so the allowlist restriction covers both build and service images.

### Proof of Concept
Go unit test (parallel to `TestDockerImageWithUser`, but for services):
```go
func TestDockerServiceImageWithUser_BypassesAllowedUsers(t *testing.T) {
    dockerConfig := &common.DockerConfig{AllowedUsers: []string{"baba"}}
    serviceDefinition := spec.Image{
        Name: "postgres:latest",
        ExecutorOptions: spec.ImageExecutorOptions{
            Docker: spec.ImageDockerOptions{User: "root"},
        },
    }
    // exercise e.createServiceContainerConfig(...) with dockerConfig applied to e.Config
    cfg := e.createServiceContainerConfig("postgres", "latest", "imgid", serviceDefinition)
    // BUG: currently passes with cfg.User == "root" even though AllowedUsers=["baba"]
    assert.NotEqual(t, "root", cfg.User, "service container should not bypass AllowedUsers")
}
```
Expected (fixed) behavior: creating the service container config/container should fail with an error like `user "root" is not an allowed user: [baba]`, mirroring `TestDockerImageWithUser`'s `"is not an allowed user"` assertion. [6](#0-5)
