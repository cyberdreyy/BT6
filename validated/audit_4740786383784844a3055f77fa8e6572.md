### Title
Builder-controlled `fee_recipient` lets a builder misdirect (or burn) a proposer's payment with no on-chain enforcement - (File: `specs/gloas/beacon-chain.md`)

### Summary
The Gloas builder-payment mechanism records the destination of the builder's payment to the proposer using a `fee_recipient` field that is chosen entirely by the *builder* inside the signed bid. The consensus state-transition function that admits the bid, `process_execution_payload_bid`, never checks that this address corresponds to the actual proposer entitled to the payment, and the honest-proposer "MUST" checklist for accepting a bid in `validator.md` also omits this check. The only place the match is verified is a p2p gossip-level `IGNORE` rule, which is advisory and not part of block validity. As a result, a builder can set `fee_recipient` to any address — including the zero address — and a fully spec-compliant chain will accept, settle, and pay out the withdrawal to that address instead of to the proposer who is supposed to receive it. This is the direct analog of the QuickSwap M-06 report: a payment recipient address that is never validated by the code paying it out, so the payment can be silently misdirected or effectively burned.

### Finding Description
When a builder submits a `SignedExecutionPayloadBid`, `process_execution_payload_bid` records a `BuilderPendingPayment` whose `withdrawal.fee_recipient` is copied verbatim from `bid.fee_recipient`, a field fully controlled by the builder: [1](#0-0) 

There is no assertion anywhere in this function tying `bid.fee_recipient` to the actual proposer (`get_beacon_proposer_index(state)`, which is stored separately as `proposer_index` for weight/quorum bookkeeping, not for validating the recipient address): [2](#0-1) 

The `BuilderPendingWithdrawal` container stores `fee_recipient` as an independent field: [3](#0-2) 

Once quorum weight is reached, the payment is settled into `state.builder_pending_withdrawals` still carrying the builder-chosen `fee_recipient` (test fixtures explicitly show `fee_recipient` flowing through unchanged): [4](#0-3) 

Finally, `get_builder_withdrawals` turns this into a real `Withdrawal` whose `address` is exactly `withdrawal.fee_recipient`, with no re-validation against the proposer who actually received the block: [5](#0-4) 

`apply_withdrawals`/`process_withdrawals` then unconditionally decreases the builder's balance and credits the (attacker-chosen) address, exactly mirroring the "immediate push-payment to an unchecked address" pattern from the AlgebraPool report.

On the validator side, the only documented safeguard is a gossip-layer `IGNORE` check (not part of block validity, and not enforced by `process_execution_payload_bid`): [6](#0-5) 

The honest-proposer construction checklist in `validator.md`/`builder.md` likewise never requires the proposer to verify `bid.fee_recipient` against its own address before including the bid on-chain; it is only mentioned as an informational note: [7](#0-6) [8](#0-7) 

Because the state transition itself is the only thing that determines block validity for all spec-following nodes, any block that includes a bid with a mismatched/zero `fee_recipient` is fully valid and will be accepted network-wide — the payment is simply lost to the wrong address, with no path in the spec text to detect or reverse it.

### Impact Explanation
This breaks the equality "the proposer who accepted and included a builder's bid receives the builder's promised payment." Instead, an unprivileged, non-colluding builder (or a buggy/malicious builder implementation) unilaterally decides who receives Gwei that the protocol design intends for the actual block proposer. If `fee_recipient` is the zero address (or any address the builder does not control and cannot recover, mirroring "vault == address(0)"), the payment is effectively burned; if it is an address the builder itself controls, the builder pays itself instead of the proposer. This matches the listed High-impact category "a builder payment or withdrawal misdirected, doubled or escaped," and in the burn case approaches "Gwei ... destroyed."

### Likelihood Explanation
No coalition, forking, or protocol-level attack is required. The builder alone constructs and signs the bid, and the field it controls (`fee_recipient`) flows unmodified and unchecked through `process_execution_payload_bid` → `BuilderPendingPayment` → `BuilderPendingWithdrawal` → `Withdrawal.address`. Because this is a pure state-transition gap (the check is absent from consensus validity, not merely from gossip filtering or a client bug), any spec-compliant chain will accept such blocks; the only mitigation today is an advisory, non-binding gossip rule that a builder can trivially ignore by sourcing the bid off-gossip (which the spec explicitly permits: "The block proposer MAY obtain these signed messages by other off-protocol means").

### Recommendation
Enforce the fee-recipient/proposer binding at the consensus layer rather than relying on gossip-only advisory checks:
- In `process_execution_payload_bid`, derive the expected recipient from `get_beacon_proposer_index(state)`'s committed `SignedProposerPreferences.fee_recipient` for the bid's slot, and `assert bid.fee_recipient == expected_fee_recipient` before recording the `BuilderPendingPayment`.
- Alternatively, do not trust the builder-supplied `fee_recipient` at all: look up and use the proposer's own registered/committed fee recipient when constructing `BuilderPendingWithdrawal`, so the destination address is state-derived rather than builder-supplied.

### Proof of Concept
1. Builder `B` (registered, active, sufficient balance) constructs a `SignedExecutionPayloadBid` for slot `S` with `bid.value = 1_000_000_000` Gwei and `bid.fee_recipient = 0x00...00` (or any address `B` controls), instead of the real proposer `P`'s preferred `fee_recipient`.
2. All on-chain checks in `process_execution_payload_bid` (`is_active_builder`, `can_builder_cover_bid`, signature, slot/hash/randao matching) pass — none of them inspect `fee_recipient`. [9](#0-8) 
3. Proposer `P` (or `P`'s honest client, following only the documented "MUST" checklist) includes this bid in its block; the checklist never requires validating `fee_recipient`. [10](#0-9) 
4. `BuilderPendingPayment.withdrawal.fee_recipient` is set to the attacker-chosen address, with `proposer_index` correctly recorded as `P`'s index (proving the protocol *knows* who is owed the payment, yet does not use that knowledge for the payout address). [11](#0-10) 
5. Once weight quorum is reached, `process_builder_pending_payments` moves the payment into `state.builder_pending_withdrawals`, still carrying the wrong `fee_recipient`.
6. `process_withdrawals` → `get_builder_withdrawals` emits a `Withdrawal(address=fee_recipient, amount=bid.value)`, and `apply_withdrawals` decreases `B`'s balance by that amount, paying it to the wrong/zero address. [12](#0-11) 
7. Every step is valid under the state-transition function; a spec-following node has no basis to reject the block, yet proposer `P` never receives the 1 ETH payment it was owed for accepting the bid.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
