### Title
Post-default instant withdraw requests are folded into the defaulted epoch bucket and paid at the haircut recovery price — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The Xen bug class is an interface exposed to a less-privileged actor whose controlled regions are (a) unbounded and (b) not properly serialized against installation/removal. The analog in `IdleCreditVault` is `requestInstantWithdraw`: unlike `requestWithdraw`, it has no `defaultRecoveryFinalized` branch. Requests made after default recovery is finalized are serialized into `instantWithdrawsRequestsByEpoch[epochNumber]`, which is still equal to `defaultRecoveryEpoch`, and are then cleared by `_claimDefaultedInstantWithdrawRequest` at `defaultRecoveryPrice` instead of being tracked as new unfunded claims.

### Finding Description
`requestWithdraw` explicitly special-cases the post-default state: it rejects if the user has open requests and stores the receipt in `postDefaultRequests` so it is paid 1:1 from the recovery reserve (`requestWithdraw`, lines 247–257; `_claimPostDefaultWithdrawRequest`, lines 760–767). `requestInstantWithdraw` has no such branch — it unconditionally increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws` (lines 356–375). After `finalizeDefaultRecovery`, `epochNumber` no longer advances and stays equal to `defaultRecoveryEpoch` (set at line 693), so every post-default instant receipt is appended to the same per-epoch bucket used for default haircut accounting.

On claim, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest` (lines 382–385), which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — now containing both the true defaulted-epoch receipt *and* the post-default receipt — clears it entirely, decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws`, burns `claimBasis` receipt tokens and pays only `claimBasis * defaultRecoveryPrice / 1e18` from the reserve (lines 842–856). The user's post-default request, which was paid for at full tranche price and minted 1:1 receipt tokens, is settled at the default haircut.

### Impact Explanation
Two broken invariants:

1. **Fair claim / receipt-price isolation**: a post-default instant requester burns tranche tokens at full price but receives only `defaultRecoveryPrice` of the underlying. The shortfall remains in `defaultRecoveryReserve`, inflating payouts to other default claimants — a direct wealth transfer from post-default instant requesters to pre-existing default claimants. Quantified loss per request: `amount * (1 - defaultRecoveryPrice)`.

2. **Accounting serialization**: `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]` are mutated by new requests *after* `defaultInstantWithdrawsFinalized` was fixed at line 696. `defaultPendingClaimBasis` can no longer distinguish funded vs unfunded basis, and `_defaultPrefundedInstantReserve` semantics are violated retroactively.

### Likelihood Explanation
Requires a vault in the `defaulted + defaultRecoveryFinalized` phase with `allowInstantWithdraw` still enabled on the CDO so that `IdleCDOEpochVariant.requestInstantWithdraw` remains callable by an unprivileged tranche holder. `requestInstantWithdraw` itself is callable by anyone holding strategy tokens via the CDO (`_onlyIdleCDO` is the only guard, line 357), and there is no `defaulted`/`defaultRecoveryFinalized` check anywhere in the instant-request path — unlike the normal-request path which was explicitly hardened. If the CDO gates instant requests on `isEpochRunning` (not verifiable in the excerpted code), the residual impact is that claims permanently revert in `_transferFundedClaim`/`_transferDefaultRecovery` due to corrupted counters, freezing remaining claims — still an accepted impact class.

### Recommendation
Mirror the `requestWithdraw` fix: in `requestInstantWithdraw`, if `defaultRecoveryFinalized`, either revert, or route through a `postDefaultInstantRequests`-style bucket that is paid 1:1 from `defaultRecoveryReserve` only after the CDO has applied the haircut to `_amount`. At minimum, guard `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` so they cannot be written for `epochNumber == defaultRecoveryEpoch` once `defaultInstantWithdrawsFinalized` is set.
