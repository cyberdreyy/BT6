### Title
Loss-adjusted withdraw receipts can be claimed at par after a subsequent request shifts `lastWithdrawRequest` past the loss epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` using only `lastWithdrawRequest[_user]` — the user's *latest* request epoch. If a user holds a receipt in a loss-adjusted epoch (where `collectWithdrawFunds` collected less than `pendingBasis` and stored a haircut price) and then makes any new `requestWithdraw` in a later epoch, `lastWithdrawRequest[_user]` moves to the new epoch, `lossRecoveryPriceByEpoch` returns 0, and the entire aggregate `withdrawsRequests[_user]` — including the underfunded loss-epoch basis — is paid out at par by `_claimFundedWithdrawRequest`. This is the same bug class as the btrfs report: a claim amount is validated/consumed against the aggregate bound (`withdrawsRequests`, `lastWithdrawRequest`) rather than the actual per-epoch bound (`withdrawsRequestsByEpoch[user][lossEpoch]`), so the claim "walks past" what was actually funded.

### Finding Description
- `requestWithdraw` records `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) .
- On a partially-funded `stopEpochWithDuration`, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` [2](#0-1) . Only `pendingBasis * price` underlying is actually pulled into the strategy.
- `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` and returns early when `lossRecoveryPriceByEpoch[lossEpoch] == 0` [3](#0-2) .
- It then falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` (the aggregate, still containing the loss-epoch `withdrawsRequestsByEpoch` piece that was never cleared) at par once `epochNumber > lastWithdrawRequest[_user]` [4](#0-3) .

The mapping "user → loss-epoch basis" is preserved in `withdrawsRequestsByEpoch`, but the loss claim is gated solely on the *latest* request epoch. A dust-sized second request erases the haircut binding for the earlier loss-epoch receipt — analogous to seg_len passing the cbuf check while over-running `compressed_len`.

### Impact Explanation
The strategy only received `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` underlying for that epoch's receipts. Paying the loss-epoch basis at par transfers the missing `(1 - price)` portion from the claims of other users whose receipts remain correctly haircut-bound. First mover extracts par value from an underfunded bucket; later claimants' `safeTransfer` reverts once the balance is exhausted — direct theft plus permanent freezing of unclaimed withdrawal proceeds. `_transferFundedClaim` only guards `defaultRecoveryReserve` [5](#0-4) , not the loss-adjusted shortfall, so no existing guard stops it.

### Likelihood Explanation
Attacker is any KYC'd tranche holder. Requirements: a `stopEpochWithDuration`/`collectWithdrawFunds` partial funding occurs (owner/manager-triggered, honest — e.g., borrower repays with a real loss, an expected mode per `previewLossAdjustedWithdrawFunds`), and the attacker files a second small `requestWithdraw` in any subsequent epoch before claiming. Both actions are unprivileged. The window is one epoch boundary plus the claim-delay epoch; cost is gas and a dust tranche amount.

### Recommendation
Track loss-adjusted claim basis per epoch, not via the mutable `lastWithdrawRequest`. Either (a) iterate/check all epochs with `withdrawsRequestsByEpoch[_user][e] != 0` that have a non-zero `lossRecoveryPriceByEpoch[e]` before the funded-claim path, or (b) subtract the loss-epoch basis from `withdrawsRequests[_user]` at `collectWithdrawFunds` time per user (requires per-epoch aggregation, e.g. storing per-epoch totals and reconciling lazily), or (c) block `requestWithdraw` while the user has an uncleared receipt in an epoch with `lossRecoveryPriceByEpoch` set. Minimal fix: in `_claimFundedWithdrawRequest`, compute `amount` as `withdrawsRequests[_user]` minus the sum of bases in epochs with a non-zero `lossRecoveryPriceByEpoch`, and let `_claimLossAdjustedWithdrawRequest` scan those epochs rather than trusting `lastWithdrawRequest`.

```solidity
// test/foundry/IdleCreditVaultLossEpochBypass.t.sol — fork test sketch
function testLossEpochReceiptPaidAtPar() external {
    // setup: standard IdleCDOEpochVariant + IdleCreditVault, user A and user B deposit 100e6 each
    uint256 tranchesA = _depositWithUser(attacker, 100e6);
    uint256 tranchesB = _depositWithUser(victim,   100e6);

    vm.prank(manager); cdoEpoch.startEpoch();

    // epoch N: both request withdraw of full position
    _requestWithdrawWithUser(attacker, tranchesA);
    _requestWithdrawWithUser(victim,   tranchesB);

    // stopEpoch with a realized loss: borrower funds only 50% of pendingBasis
    // -> collectWithdrawFunds stores lossRecoveryPriceByEpoch[N] = 0.5e18 and pulls only half
    _stopEpochWithPartialFunding(0.5e18);

    // epoch N+1 (buffer): attacker files a dust request, moving lastWithdrawRequest to N+1
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(attacker, 1);           // dust; also bumps lastWithdrawRequest

    // wait until epochNumber > lastWithdrawRequest[attacker]
    _stopCurrentEpoch();

    // _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[N+1] == 0 -> skipped
    // _claimFundedWithdrawRequest pays full withdrawsRequests[attacker] at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdoEpoch.claimWithdrawRequest(0, attacker); // via CDO entrypoint
    uint256 got = underlying.balanceOf(attacker) - balPre;

    uint256 parBasis = 100e6 + 1;                    // includes loss-epoch 100e6 at par
    assertEq(got, parBasis, "attacker paid at par on underfunded epoch");

    // victim claims correctly through the loss-adjusted path at 0.5 price
    vm.prank(victim); cdoEpoch.claimWithdrawRequest(0, victim);
    // victim receives ~50e6; residual ~50e6 shortfall remains unbacked for
    // any other claimants -> their claims revert (permanent freeze of owed funds)
    assertLt(underlying.balanceOf(address(strategy)), owedToRemainingClaimants);
}
```

Caveat: I verified the claim-path logic but could not fully confirm, within tool limits, the exact `epochNumber` value used as the `lossRecoveryPriceByEpoch` key relative to the request epoch in `IdleCDOEpochVariant.stopEpoch` internals (the grep only returned match counts). If the key is the *post-increment* epoch while `lastWithdrawRequest` stores the request epoch, the loss-adjusted path is even more broadly bypassed and the same fix applies.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
