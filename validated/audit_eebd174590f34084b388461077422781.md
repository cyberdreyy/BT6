### Title
A single APR0 withdraw request permanently bricks `stopEpoch` once the manager sets a non-zero APR - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of the asn1c `_default_error_logger()` NULL-deref DoS: a code path that unconditionally reverts on an unguarded state combination. `prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` and `unscaledApr != 0`, and the only non-default paths that clear `apr0TotalPrincipal` are that same function (which is unreachable once it reverts) and default finalization. A user who files an APR=0 withdraw request and cannot cancel it therefore makes every subsequent `stopEpoch` revert if the honest manager has since moved the pool off APR 0, freezing all vault accounting and LP funds in the strategy.

### Finding Description
`requestWithdraw` mints a receipt and, when `unscaledApr == 0`, routes to `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` bucket (`IdleCreditVault.sol:285-286`, `567-577`). There is no way for a user to cancel a request, and a request made during the buffer phase cannot be claimed until `epochNumber` advances past `lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326-328`), which requires a successful `stopEpoch`.

At the next `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which contains:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:502-508
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

`apr0TotalPrincipal` is only zeroed at line 540 — after the revert check — or inside `_clearWithdrawClaimForEpoch` during default finalization (`IdleCreditVault.sol:822-831`). So once a pending APR0 receipt exists and `unscaledApr` has been set non-zero (a routine, honest `setAprs` call by the manager between epochs), `stopEpoch` reverts on every call. `epochNumber` cannot advance, pending receipts can never be claimed or settled, the borrower is never asked to repay, and tranche redemptions that route through `claimWithdrawRequest`/`claimInstantWithdrawRequest` stay blocked. The only recovery is for the manager to set the APR back to 0 (or force a default and finalization), so this is a user-triggered, admin-recoverable freeze of the entire pool TVL rather than a theft.

### Impact Explanation
Any single unprivileged tranche holder can place the vault into a state where the epoch state machine halts as soon as APR is changed away from 0 — a configuration change that is entirely expected over a pool's lifetime. All deposited TVL remains locked in the strategy/borrower, interest accrual and repricing stop, and every pending withdraw receipt (including those of other users) is frozen. Quantified loss: 100% of vault TVL is frozen for the duration until governance restores `unscaledApr == 0` or finalizes a default; if the borrower has drawn funds, recovered repayment cannot be routed to LPs during the freeze.

### Likelihood Explanation
Requires only (a) the pool being in APR0 mode when the attacker requests a withdraw (a supported, deliberately-used mode per the `unscaledApr == 0` branch), and (b) the manager later raising APR — a normal operational action. No malicious privileged role, oracle manipulation, or borrower default is needed; the revert is deterministic once both conditions hold.

### Recommendation
Decouple APR0 settlement from the live APR: either snapshot the APR at request time (store it in `Apr0UserData`/`apr0RateByEpoch` and settle on that), or settle/migrate the outstanding APR0 bucket to a normal `withdrawsRequests` entry inside `prepareStopEpochWithApr0` when `unscaledApr != 0` instead of reverting, or block `setAprs` from leaving 0 while `apr0TotalPrincipal != 0`.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testApr0PendingBlocksStopEpochAfterAprChange() external {
    // pool configured with unscaledApr == 0
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);

    // attacker files an APR0 withdraw request during buffer phase
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // mints receipt, apr0TotalPrincipal > 0

    // honest manager raises APR for the next epoch (routine config change)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(initialApr, initialApr);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // every stopEpoch now reverts: epoch machine is bricked
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(initialApr, 0);

    // neither the attacker nor any other pending receipt can claim;
    // epochNumber never advances past lastWithdrawRequest
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```

Key state assertions to add: `creditVault.apr0TotalPrincipal() == amount` (never cleared), `creditVault.epochNumber()` unchanged after the reverted `stopEpoch`, and `underlying` still sitting with the borrower/strategy with no path to LPs until the APR is restored to 0.
