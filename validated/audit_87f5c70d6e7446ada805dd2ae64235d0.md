### Title
Already-paid instant withdrawals stay in the per-epoch ledger and are counted twice at default finalization, inflating the recovery reserve and price - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays a funded instant-withdraw receipt and zeroes the aggregate `instantWithdrawsRequests[_user]`, but never clears the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the same epoch later defaults, `finalizeDefaultRecovery` counts those already-distributed underlyings a second time — once inside `_defaultPrefundedInstantReserve()` (phantom reserve) and once inside `defaultPendingClaimBasis()` (phantom basis) — while `_claimDefaultedInstantWithdrawRequest` re-processes the stale per-epoch receipt and underflows `instantWithdrawsRequests[_user]`. This is the credit-vault analog of CVE-2018-7480's double free: the same underlying resource is released to a user and then treated as still-owned accounting state.

### Finding Description
`requestInstantWithdraw` records three ledgers: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` [1](#0-0) . When the CDO funds the request, `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` [2](#0-1) . When the user then claims, `claimInstantWithdrawRequest` burns the receipt, sets `instantWithdrawsRequests[_user] = 0`, and transfers underlying — but leaves `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` untouched [3](#0-2) .

Unlike normal withdraw receipts — where `_clearWithdrawClaimForEpoch` explicitly zeroes `withdrawsRequestsByEpoch` and re-syncs the aggregate [4](#0-3)  — instant receipts have no symmetric clearing on the funded-claim path. Instant claims are designed to settle within the same epoch (no epoch-wait check exists in `claimInstantWithdrawRequest`), so this stale state survives into a same-epoch default.

When the borrower defaults in that epoch and `finalizeDefaultRecovery` runs:
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes the already-paid amounts [5](#0-4) .
- `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstantWithdraws` and treats the difference as underlying still held by the strategy, even though the claimed portion was already transferred out [6](#0-5) .
- Both phantom components feed `reserveAmount` and `totalBasis`, so `defaultRecoveryPrice` is set against underlying that no longer exists [7](#0-6) .
- Later, `_claimDefaultedInstantWithdrawRequest` re-reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and executes `instantWithdrawsRequests[_user] -= claimBasis`, which underflows for any user whose receipt was already claimed [8](#0-7) .

### Impact Explanation
Direct fund impact, two ways:

1. **Overpayment / insolvency of the recovery reserve.** `defaultRecoveryReserve` is credited with a `prefundedReserve` that includes underlying already sent to early instant claimants. `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore computed against a phantom balance. `_transferDefaultRecovery` decrements `defaultRecoveryReserve` and transfers real tokens [9](#0-8) : early recovery claimants (including `postDefaultRequests` claimants and defaulted normal-receipt claimants) are paid an inflated price, draining the reserve so that later claimants' transfers revert or the reserve is exhausted with unclaimable dust — a permanent loss/freezing of recovery funds for the claimants paid last.

2. **Permanent claim DoS.** Any user who claimed an instant receipt in the defaulted epoch has `instantWithdrawsRequests[_user] == 0` but a nonzero `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`; `instantWithdrawsRequests[_user] -= claimBasis` underflows and `claimInstantWithdrawRequest` reverts for them and, because `instantWithdrawClaimsByEpoch[defaultEpoch]` is only decremented inside the reverting function, the inflated basis can never be reconciled.

Quantified example: epoch E has 100 USDC of instant requests; 60 are funded and claimed, 40 remain pending (`pendingInstantWithdraws = 40`). Borrower defaults in epoch E. Finalization counts `instantBasis = 100` (not 40) in the claim basis and adds `prefundedReserve = 60` phantom units to the reserve. Every recovery claimant's payout is computed with 60 units of double-counted backing; the last claimant(s) to call `claimInstantWithdrawRequest`/`claimWithdrawRequest` find the reserve short by up to the phantom amount.

### Likelihood Explanation
Requires a partial instant-withdraw queue in the epoch that defaults: some instant requests funded and claimed, at least one still pending (`pendingInstantWithdraws != 0`, needed so `defaultInstantWithdrawsFinalized` is set and instant basis is included). This is the normal operating mode of instant withdrawals — claims are same-epoch and funding is sequential — so the stale-ledger condition arises organically whenever a default lands mid-queue. No privileged misbehavior is needed: the attacker role is a KYC-passing lender who requests and claims an instant withdrawal before a default, or simply any claimants in the queue. The bug is triggered by honest manager/borrower calls (`stopEpoch`, default finalization) around ordinary user actions.

### Recommendation
In `claimInstantWithdrawRequest` (or in the funded-claim path it invokes), clear the per-epoch ledgers symmetrically with the aggregate: zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]` for the epoch(s) being paid, mirroring how `_clearWithdrawClaimForEpoch` keeps `withdrawsRequestsByEpoch` consistent with `withdrawsRequests`. Alternatively, track funded-but-unclaimed instant amounts in a dedicated counter so `_defaultPrefundedInstantReserve` only counts funds actually still held. Add an invariant test: claim a funded instant receipt, default the same epoch, finalize recovery, and assert `instantWithdrawClaimsByEpoch[defaultEpoch]` equals only unclaimed amounts and all claimants can be paid to zero.

### Proof of Concept
Foundry fork sketch (against a live-forked `IdleCreditVault` + `IdleCDOEpochVariant` deployment, same harness style as `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testPhantomInstantReceiptInflatesDefaultRecovery() external {
    // 1. Epoch running with instant withdrawals enabled; users A and B deposit.
    _depositWithUser(A, 100e6);
    _depositWithUser(B, 100e6);

    // 2. A and B request instant withdrawals (60 and 40 USDC worth of strategy tokens).
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(delay, minDiff, false);
    _requestInstantWithdraw(A, 60e18);
    _requestInstantWithdraw(B, 40e18);

    // 3. Borrower/CDO funds the instant queue; A claims (funded claim path).
    //    -> instantWithdrawsRequests[A] == 0
    //    -> instantWithdrawsRequestsByEpoch[A][epoch] still == 60e18  (STALE)
    //    -> instantWithdrawClaimsByEpoch[epoch] still == 100e18       (STALE)
    _fundInstantQueue();
    cdoEpoch.claimInstantWithdrawRequest(A);
    assertEq(strategy.instantWithdrawsRequests(A), 0);
    assertGt(strategy.instantWithdrawsRequestsByEpoch(A, epoch), 0); // bug: never cleared

    // 4. Borrower defaults in the SAME epoch; manager finalizes recovery.
    _handleBorrowerDefault();
    strategy.finalizeDefaultRecovery(recovered, recoverySource);

    // 5. defaultRecoveryReserve includes _defaultPrefundedInstantReserve()
    //    = instantClaimsByEpoch(100) - pendingInstantWithdraws(40) = 60 phantom units
    //    already transferred to A. defaultRecoveryPrice is computed against it.
    uint256 reserve = strategy.defaultRecoveryReserve();
    uint256 realBacking = underlying.balanceOf(address(strategy));
    assertGt(reserve, realBacking); // reserve exceeds actual tokens by the claimed amount

    // 6a. A's stale receipt underflows: instantWithdrawsRequests[A] (0) - 60e18 reverts.
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest(A);

    // 6b. Recovery claimants are paid the inflated price; the last claimant's
    //     _transferDefaultRecovery transfer reverts for insufficient balance,
    //     leaving defaultRecoveryReserve stuck in the contract.
}
```

The assertion `reserve > realBacking` demonstrates the double-counted (double-freed) accounting; the reverting claim in step 6a demonstrates the stale per-epoch entry being processed a second time.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
