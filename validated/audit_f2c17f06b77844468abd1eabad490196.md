### Title
Path traversal in local cache "alternate" archive file path when `FF_HASH_CACHE_KEYS` is enabled - ([File: shells/abstract.go])

### Summary
`newCacheConfig` in `shells/abstract.go` computes two on-disk cache file paths per cache entry: a primary path keyed by a SHA-256 hash, and an "alternate" path used to support upgrading/downgrading between hashed and unhashed cache naming schemes. When `FF_HASH_CACHE_KEYS` is enabled, the human-readable key is used unsanitized, and this exact unsanitized value is reused as the *alternate* path's directory component without any hashing or traversal check, unlike the primary path (hashed) or the remote object path (which has an explicit `strings.HasPrefix` traversal guard in `cache.go`).

### Finding Description
In `newCacheConfig` (`shells/abstract.go:133-208`), when `featureflags.HashCacheKeys` is on, the sanitizer is replaced with an identity function: [1](#0-0) 
so `humanKey` retains any attacker-supplied path segments such as `../../../../` verbatim (cache keys come from the CI job's `cache:key` field or `CACHE_FALLBACK_KEY`, expanded via `build.GetAllVariables().ExpandValue`): [2](#0-1) 

The primary archive path is safe because it is built from `hashedKey = hasher(humanKey)`, always a 64-char sha256 hex string: [3](#0-2) 

However, `cacheAlternateKey` returns the raw, unhashed `humanKey` as the alternate key whenever hashing is enabled: [4](#0-3) 

This unsanitized `alternateKey` is fed straight into `getArchivePath`, which does `path.Join(build.CacheDir, key, "cache.zip")` with no traversal check, then makes it relative to `BuildDir` via `filepath.Rel`: [5](#0-4) 

`path.Join` lexically collapses `..` segments; a sufficiently deep `../../../..` sequence in the cache key walks the resulting path outside `build.CacheDir` entirely (confirmed by the "hashed" test case where `AlternateArchiveFile` is built directly from the raw `humanKey` with no traversal defense, e.g. `.../cache/dir/some-job/some-ref/cache.zip`): [6](#0-5) 

By contrast, the equivalent remote-object path construction in `cache.go`'s `GetAdapter` explicitly guards against this with a `strings.HasPrefix(fullPath, basePath+"/")` check and refuses to proceed if it fails: [7](#0-6) 
No analogous check exists for the local `AlternateArchiveFile`/`ArchiveFile` computation in `shells/abstract.go`.

This `AlternateArchiveFile` value is passed to the `cache-archiver` helper binary as `--alternate-file <path>`, which writes the cache zip to that local path — as shown by the test's expected arguments: [8](#0-7) 

Since `FF_HASH_CACHE_KEYS` is a feature flag readable from job/pipeline variables (`build.IsFeatureFlagOn` consults `build.GetAllVariables()` before falling back to runner config), an unprivileged pipeline author who can set `FF_HASH_CACHE_KEYS: "true"` and a crafted `cache:key` (or `CACHE_FALLBACK_KEY`) containing `../` sequences can control this "alternate" file path.

### Impact Explanation
An attacker-controlled cache key can cause `cache-archiver` to write a cache zip file (or `cache-extractor` to write/overwrite a downloaded archive) to a path outside the intended `build.CacheDir`/build directory tree, limited only by the filesystem permissions of the process running the helper. This is a break of the "file operations must stay within intended build/cache/artifact roots" invariant, and can lead to overwriting arbitrary writable files on shared build hosts/executors (e.g., other jobs' cache directories, shared temp locations), or information disclosure if the alternate path is later read back.

### Likelihood Explanation
Preconditions: `FF_HASH_CACHE_KEYS` must be enabled (settable via job/pipeline CI variables, not requiring runner-admin action), and the job must define a `cache:key` (or `CACHE_FALLBACK_KEY`) with attacker-chosen content. Both are normal, unprivileged pipeline-author capabilities. No image/service/executor-specific bypass is needed — this is pure Go string/path logic reachable on every executor that runs `cache-archiver`/`cache-extractor`.

### Recommendation
Do not use the raw/unsanitized `humanKey` (or its equivalent as `alternateKey`) directly as a filesystem path component. Either:
- Always hash the alternate key too (i.e. only use `cachekey.Sanitize`'d or hashed values when building any local filesystem path), or
- Add an explicit containment check (equivalent to `cache.go`'s `strings.HasPrefix` guard, but using `filepath.Clean`/`filepath.Rel` with a rooted comparison) in `getArchivePath` before returning the computed `ArchiveFile`/`AlternateArchiveFile`, rejecting/skipping any path that resolves outside `build.CacheDir`.

### Proof of Concept
Go unit test extending `TestNewCacheConfig` in `shells/abstract_test.go`:
```go
"hashed, alternate key path traversal": {
    cacheDir: "/some/cache/dir",
    buildDir: "/some/build/dir",
    userKey:  "../../../../../../etc/cron.d/evil",
    ffs: map[string]bool{
        featureflags.HashCacheKeys: true,
    },
    // assert cfg.AlternateArchiveFile does NOT escape build.CacheDir,
    // e.g. does not contain more ".." segments than needed to reach BuildDir's parent,
    // or resolves to a path outside "/some/cache/dir".
},
```
Expected (buggy) result: `AlternateArchiveFile` resolves to a path under `/etc/cron.d/evil/cache.zip` (or similar), outside `/some/cache/dir`, demonstrating the missing containment check. A fix should make this test assert the function returns an error or a clamped in-root path instead.

// cacheAlternateKey returns the "other" archive key relative to the current FF_HASH_CACHE_KEYS setting.
// When hashing is enabled, the alternate is the unhashed (human-readable) key.
// When hashing is disabled, the alternate is the SHA256-hashed key.
func cacheAlternateKey(humanKey string, hashEnabled bool) string {
	sha256Key := fmt.Sprintf("%x", sha256.Sum256([]byte(humanKey)))
	if hashEnabled {
		return humanKey
	}
	return sha256Key
}

		var err error
		file := path.Join(build.CacheDir, key, "cache.zip")
		if !build.IsFeatureFlagOn(featureflags.UsePowershellPathResolver) {
			file, err = filepath.Rel(build.BuildDir, file)
			if err != nil {
				return "", fmt.Errorf("inability to make the cache file path relative to the build directory (is the build directory absolute?)")
			}
		}
		return file, err
	}

	archiveFile, err := getArchivePath(hashedKey)
	if err != nil {
		return nil, warning, err
	}

	// alternateKey is always the "other" naming scheme relative to the current FF setting:
	// - FF ON:  primary=hashed, alternate=unhashed → enables upgrade of old unhashed artifacts
	// - FF OFF: primary=unhashed, alternate=hashed → enables downgrade of old hashed artifacts
	alternateKey := cacheAlternateKey(humanKey, build.IsFeatureFlagOn(featureflags.HashCacheKeys))
	alternateArchiveFile, err := getArchivePath(alternateKey)
	if err != nil {
		return nil, warning, err
	}
