### Title
Request ID reuse after `cleanupCallback` deletion allows stale/delayed node responses to be delivered to an unrelated later request with the same ID - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`h.callbacks` is keyed only by the client-supplied `requestID` string, and `setupCallback` only rejects a new registration if that ID is *currently* present in the map [1](#0-0) . Once `cleanupCallback` deletes an entry (e.g. after one shard reaches quorum) [2](#0-1) , the same `requestID` can immediately be reused for a brand-new, unrelated request. A response that is still in flight for the first request (e.g. from a shard that had not yet reached quorum) will then be matched by `HandleNodeTriggerResponse`'s `h.callbacks[resp.ID]` lookup [3](#0-2)  to the second request's freshly-created callback and aggregator, since there is no generation/version token binding a response to the exact registration instance.

### Finding Description
`setupCallback` stores a `savedCallback` under `h.callbacks[requestID]`, building fresh per-shard `IdenticalNodeResponseAggregator`s for whatever workflow the *current* caller specified [4](#0-3) . `HandleNodeTriggerResponse` cleans up the callback only after the first shard's aggregator reaches quorum and a response has been sent — other shards may still have retries/late responses in flight, since `sendToShard` only stops on `doneCh` closure, which races with node network latency [5](#0-4) .

Because `requestID` uniqueness is enforced only while an entry exists in the map (not across time), an attacker can:
1. Submit request A with `requestID = X` for a workflow assigned to shards `{S1, S2}`.
2. As soon as `S1` reaches quorum, `HandleNodeTriggerResponse` sends A's result and calls `cleanupCallback("X")`, deleting the map entry — while `S2`'s nodes are still processing/retrying and have not yet responded.
3. Immediately submit request B with the same `requestID = X` for a workflow that is also assigned to `S2` (an attacker fully controls this if it targets their own workflow(s), or can succeed against another party if that party's client uses a predictable/reused `requestID`, e.g. sequential counters). `setupCallback` accepts it because the map entry for `X` was already deleted, creating a brand-new aggregator for `S2` under key `X`.
4. `S2`'s delayed, genuine responses to request A now arrive and match `resp.ID == "X"` in `HandleNodeTriggerResponse`, routing into B's newly created aggregator for `S2` (`saved.responseAggregators[shard.donID]` lookup succeeds because the shard ID overlaps) [6](#0-5) . If enough of A's stale identical responses accumulate to reach B's aggregator threshold, `SendResponse` delivers A's execution result to B's callback, and `cleanupCallback("X")` then deletes B's entry — either leaking A's stale data to B or prematurely terminating B's own pending request.

No signature/authentication check ties a node response back to the specific registration instance that requested it; only the string `requestID` is used as the binding key, and that key space is fully attacker/client controlled and immediately reusable after cleanup.

### Impact Explanation
This is a cross-user response confusion bug: data intended for one workflow-trigger request can be delivered to a different, later request that reused the same `requestID`, and/or the later request's own callback can be prematurely deleted, causing it to never receive its real response (denial of service for that request). This matches the "cross-user response confusion" / "attacker-controlled data returned to another user" impact class.

### Likelihood Explanation
Exploitation requires: (1) attacker-controlled or predictable `requestID` collision between the stale and new registration, (2) the new request's workflow being assigned to a shard that still has an outstanding/delayed response for the old request, and (3) enough of those delayed responses to reach the new aggregator's quorum threshold. An attacker fully controls (1) and (2) when both requests are their own (self-directed proof), but cross-victim exploitation additionally requires the victim to reuse a guessable/predictable `requestID`, which is plausible for naive clients (sequential IDs, fixed IDs, timestamps) but not guaranteed. The race window depends on shard response latency, making it feasible but timing-sensitive.

### Recommendation
Bind each callback registration to a unique, unguessable, monotonically-non-reusable internal identifier (e.g., a UUID or a generation counter combined with `requestID`) that node responses must be matched against, rather than relying purely on the client-supplied `requestID` string, which can be a controlled/collided value. Alternatively, once a `requestID` has been used and cleaned up, keep a short-lived "recently retired" set with a TTL so a reused ID is rejected (mirrors `setupCallback`'s in-flight check but extended past the cleanup point), preventing legitimate-but-stale responses from binding to an unrelated new registration.

### Proof of Concept
Go handler-level test outline in `http_trigger_handler_test.go`:
1. Configure a fake `workflowMetadataHandler`/shard setup where workflow A and workflow B are both assigned to shard `S2` (and A also to `S1`).
2. Call `setupCallback(ctx, "X", callbackA, ..., workflowA)`.
3. Simulate `S1` reaching quorum: call `HandleNodeTriggerResponse` with enough node responses on `S1` to trigger `SendResponse` + `cleanupCallback("X")`; assert `h.callbacks["X"]` no longer exists.
4. Call `setupCallback(ctx, "X", callbackB, ..., workflowB)` — assert it succeeds (no `ErrConflict`).
5. Deliver `S2`'s delayed, genuine "for workflow A" node responses (same digest, from `S2` node addresses) via `HandleNodeTriggerResponse` with `resp.ID = "X"` until threshold is met.
6. Assert `callbackB.SendResponse` was invoked with A's stale response payload (not B's), and/or assert `callbackB`'s `doneCh`/entry was deleted before B's own genuine responses arrived — demonstrating cross-request response confusion.

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}

	// Build one response aggregator per shard the workflow is assigned to.
	assigned := h.workflowMetadataHandler.WorkflowShards(workflowID)
	if len(assigned) == 0 {
		// this shouldn't happen because we checked it in authorizeRequest()
		h.handleUserError(ctx, requestID, jsonrpc.ErrInternal, fmt.Sprintf("Workflow %s is not assigned to any DONs", workflowID), callback)
		return nil, errors.New("workflow is not assigned to any shards")
	}

	aggregators := make(map[string]*aggregation.IdenticalNodeResponseAggregator, len(assigned))
	for _, shard := range assigned {
		// (N+F)//2 + 1 threshold where N = number of nodes, F = number of faulty nodes
		threshold := (len(shard.members)+shard.f)/2 + 1
		agg, err := aggregation.NewIdenticalNodeResponseAggregator(threshold)
		if err != nil {
			return nil, errors.New("failed to create response aggregator: " + err.Error())
		}
		aggregators[shard.donID] = agg
	}

	doneCh := make(chan struct{})
	h.callbacks[requestID] = savedCallback{
		Callback:            callback,
		requestStartTime:    requestStartTime,
		createdAt:           time.Now(),
		responseAggregators: aggregators,
		doneCh:              doneCh,
	}
	return doneCh, nil
}

func (h *httpTriggerHandler) cleanupCallback(requestID string) {
	saved, exists := h.callbacks[requestID]
	if !exists {
		return
	}
	close(saved.doneCh)
	delete(h.callbacks, requestID)
}
