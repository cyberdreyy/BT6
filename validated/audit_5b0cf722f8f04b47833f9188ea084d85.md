### Title
No vulnerability — `use_global_contract`'s `account_id`/`account` are always bound to the receipt receiver, not attacker-suppliable via `contract_identifier` - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
The `contract_identifier: GlobalContractIdentifier::AccountId(id)` field inside `UseGlobalContractAction` is only used as a lookup key into the global, receiver-independent `TrieKey::GlobalContractCode` namespace to fetch bytecode previously published by account `id`. It is never used to resolve or mutate a different `Account` struct — the account whose `storage_usage` is mutated is always the one passed in as `account: &mut Account`, which is bound by the caller to `account_id`, the actual receiver of the action.

### Finding Description
`action_use_global_contract` in `runtime/runtime/src/global_contracts.rs` (lines 64-73) forwards to `use_global_contract(state_update, account_id, account, &action.contract_identifier, result)`. Inside `use_global_contract` (lines 75-108):
- `contract_identifier` is used solely to build `TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() }` [1](#0-0) , a read-only existence check on a global namespace keyed by code hash or publishing account id — not an `Account` state entry for account Y.
- The only mutations, `clear_account_contract_storage_usage(state_update, account_id, account)` and `account.set_storage_usage(...)` / `account.set_contract(...)`, operate exclusively on the `account_id`/`account` pair passed into the function [2](#0-1) .

This `account_id`/`account` pair is supplied by the runtime's generic action-dispatch loop in `runtime/runtime/src/actions.rs`, which — consistent with every other action handler (`action_transfer`, `action_deploy_contract`, etc.) — always binds `account_id` to the receiver account of the receipt being processed, and loads/persists exactly that `Account` struct. There is no code path where `contract_identifier`'s embedded `AccountId` is substituted for, or used to look up, a different `Account` object to mutate. The attacker's crafted `contract_identifier` can only reference (read) another account's published global contract code (which is explicitly a public, shareable resource by design of the `DeployGlobalContractAction { deploy_mode: AccountId }` feature), never write to or affect that other account's storage usage or balance.

### Impact Explanation
No impact — the receiver-confusion described in the audit question does not exist in this code path. `storage_usage` changes are strictly local to the receipt's own receiver account.

### Likelihood Explanation
Not applicable — not exploitable.

### Recommendation
No change needed. Optionally, add an explicit unit test to guard against future refactors, asserting that `use_global_contract`'s `account_id` parameter always equals `receipt.receiver_id()` and that no other account's `Account`/storage_usage is touched.

### Proof of Concept
1. Deploy a global contract as account Y with `DeployGlobalContractAction { deploy_mode: AccountId }`, publishing code under `GlobalContractIdentifier::AccountId(Y)`.
2. From account X (attacker), submit a receipt with `receiver_id = X` containing `UseGlobalContractAction { contract_identifier: GlobalContractIdentifier::AccountId(Y) }`.
3. Apply the receipt and assert: (a) `Account` state for Y is unchanged (same `storage_usage`, same `amount`); (b) `Account` state for X has its `storage_usage` incremented by `contract_identifier.len()` and `account.contract()` set to `AccountContract::GlobalByAccount(Y)`; (c) no `TrieKey` write occurs under Y's account namespace.
Expected result: only X's account state changes, confirming no receiver-confusion — matches actual runtime behavior described above.
