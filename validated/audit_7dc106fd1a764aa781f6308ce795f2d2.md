### Title
Reject-then-Accept sequence from a single signer double-counts its weight in both `total_weight_approved` and `total_weight_rejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies signer weight for a proposed block into two independent counters, `total_weight_approved` and `total_weight_rejected`, guarded against double-counting in only one direction. A signer that first rejects and later reconsiders and accepts the same block (a flow explicitly supported by the signer protocol) has its weight added to `total_weight_rejected` when it rejects, and then *also* added to `total_weight_approved` when it later accepts, because the "already counted" guard used on the accept path checks a different set (`gathered_signatures`) than the one the reject path populates (`responded_signers`). The reject weight is never retracted. The result is that a single one-slot signer can make its weight simultaneously present in both the approval and the rejection tallies, breaking the aggregated-weight vs. verified-accepts/rejects equality that the miner relies on to decide whether a block is approved or rejected.

### Finding Description
`BlockStatus` tracks per-block tallying state with two members: [1](#0-0) 

For an accepted (signed) response, the weight is added only if the signer's slot is not already present in `gathered_signatures`: [2](#0-1) 

`gathered_signatures.insert` and `responded_signers.insert` are then updated unconditionally.

For a rejected response, the weight is added only if the signer's slot was not already present in `responded_signers`: [3](#0-2) 

The guard on the accept path (`gathered_signatures.contains_key`) and the guard on the reject path (`responded_signers.insert`) are checking two different sets. Consider the message order **Reject → Accept** from the same signer/slot for the same block:

1. `Reject` arrives first: `responded_signers.insert(slot_id)` returns `true` (first insertion) → `total_weight_rejected += signer_entry.weight`.
2. `Accept` arrives afterward: `gathered_signatures.contains_key(&slot_id)` is `false` (this map was never touched by the reject path) → the accept branch adds the weight *again*: `total_weight_approved += signer_entry.weight`.

At no point is `total_weight_rejected` decremented when the signer flips to accept, so the same signer's weight now counts toward both totals permanently. Reject-then-accept transitions are an expected part of the protocol — a signer can reconsider and re-send a different verdict for a block it previously rejected (see `should_reevaluate_block` / `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`, and the changelog entry "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected"), so this is directly reachable without cooperation from other signers and without controlling a majority — a single signer's own StackerDB slot messages suffice.

The opposite order (Accept → Reject) is correctly guarded, because `responded_signers` is set by the accept branch too, so a later reject's `responded_signers.insert` returns `false` and its weight is not counted. The bug is one-directional.

### Impact Explanation
`SignerCoordinator` (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) evaluates the rejection condition before the approval condition using these two independent totals: [4](#0-3) 

Because a single signer's weight can be simultaneously present in both `total_weight_rejected` and `total_weight_approved`, the rejection threshold (`total_weight_rejected + weight_threshold > total_weight`) can be crossed using weight that does not represent genuinely distinct rejecting signers — that weight is "borrowed" from a signer who has since accepted. This can cause the miner to conclude a block has been rejected by a blocking minority even though the true, current distinct rejecting weight is below the 30% blocking-minority bar, while the true distinct approving weight may in fact have reached the 70% acceptance threshold. This is exactly the "aggregated-weight vs. verified-accepts equality" break called out as in-scope: a rejection is effectively double-counted/miscounted against a block that a verified majority actually accepted, producing either an incorrect global rejection of an approvable/canonical block (liveness wedge for that tenure) or, depending on timing, corrupting the accounting used to decide when to stop waiting for more signer responses.

### Likelihood Explanation
This requires only a single non-majority signer to (a) reject a proposal (e.g. due to a transient validation failure or connectivity issue) and (b) subsequently reconsider and accept the very same block — both of which are supported, documented signer behaviors (`should_reevaluate_reject_reason`), not an edge case requiring collusion. A malicious one-slot signer can trivially engineer this sequence deliberately by first broadcasting `BlockResponse::Rejected` and shortly after broadcasting `BlockResponse::Accepted` for the same `signer_signature_hash`, since a signer's own StackerDB slot is fully under its control.

### Recommendation
Use the same tracking set to guard both branches (or track per-signer verdict state instead of two independent additive counters), e.g. only add to `total_weight_rejected` if the slot is not already in `responded_signers` *and* not already in `gathered_signatures`, and symmetrically for the accept branch check `responded_signers` as well as `gathered_signatures`. More robust: maintain a single `HashMap<u32, Verdict>` per block and recompute `total_weight_approved`/`total_weight_rejected` from that map whenever a signer's verdict changes, so a flip in either direction removes the previous vote's weight before adding the new one.

### Proof of Concept
1. Reward set has signers `A` (weight w_A), `B`, `C`, ... such that honest signers other than `A` supply approve-weight just under the 70% threshold and reject-weight just under the 30% blocking minority.
2. Signer `A` (any single slot, no majority needed) pushes `BlockResponse::Rejected` for block `H`. `stackerdb_listener` records `total_weight_rejected += w_A` via `responded_signers.insert(A) == true`.
3. Other honest signers approve `H`, pushing `total_weight_approved` to (threshold − w_A) using their real signatures.
4. Signer `A` reconsiders and pushes `BlockResponse::Accepted` for the *same* `H`. Because `gathered_signatures` for slot `A` is still empty, `stackerdb_listener` adds `total_weight_approved += w_A` as well, reaching or exceeding `weight_threshold` — while `total_weight_rejected` still separately contains `w_A` from step 2 and is never decremented.
5. If other signers also contribute rejection weight up to just under blocking-minority minus w_A, `total_weight_rejected + w_A` (double counted) can now cross the blocking-minority line in `signer_coordinator.rs`'s `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` check even though genuinely distinct rejecting weight from other signers alone would not, causing the coordinator to treat block `H` — which independently reached genuine approval weight — as rejected.
