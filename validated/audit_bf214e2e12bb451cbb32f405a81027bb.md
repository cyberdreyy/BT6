### Title
EI-authenticated attacker can trigger runs on non-webhook jobs due to broken `isUser` check in `PipelineRunsController.Create` - (File: `core/web/pipeline_runs_controller.go`)

### Summary
`PipelineRunsController.Create` intends to block external-initiator (EI) credentials from triggering job runs via integer job IDs ("EIs not allowed"), but the guard it uses, `auth.GetAuthenticatedUser`, cannot distinguish a real user from an EI because `AuthenticateExternalInitiator` also populates the same session key with a synthetic `User{Role: UserRoleRun}`. As a result, an attacker holding only valid EI credentials satisfies `isUser == true` and can call `RunJobV2` on any numeric job ID, including non-webhook job types such as Cron or DirectRequest.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is authenticated with a chain of methods (session, API token, and external initiator) and wrapped with `auth.RequiresRunRole`, which only requires role `>= run` [1](#0-0) . `AuthenticateExternalInitiator` authenticates the EI credentials and then unconditionally sets the session's `SessionUserKey` to a fabricated `clsessions.User{Role: clsessions.UserRoleRun}`, explicitly commented as making EI endpoints "inherently assume the role of 'run'" [2](#0-1) .

Inside `Create`, the code attempts an additional restriction beyond role: `_, isUser := auth.GetAuthenticatedUser(c); if isUser { ... RunJobV2 ... }`, with the comment "only users are allowed to run jobs using int IDs - EIs not allowed" [3](#0-2) . However, `GetAuthenticatedUser` merely checks whether `SessionUserKey` is set in the gin context and can be type-asserted to `*clsessions.User` [4](#0-3) . Because `AuthenticateExternalInitiator` sets exactly that key with a real `*clsessions.User` struct (just with `Role: UserRoleRun`), `isUser` evaluates to `true` for EI-authenticated requests as well — there is no way to differentiate "real user" from "user-role synthesized for an EI" using this function.

Consequently, the `isUser` gate is a no-op with respect to its stated purpose: any request authenticated purely via EI credentials reaches `prc.App.RunJobV2(ctx, jobID, nil)` for arbitrary integer job IDs, with no check anywhere in `Create` that the target job is of a type intended to be triggered by an external initiator (e.g., legacy webhook jobs, whose UUID-based routing was explicitly removed per the code at lines 103-107). Cron, DirectRequest, or any other job type accessible by integer ID can be triggered by an EI credential holder.

### Impact Explanation
This is an authorization/role-binding bypass: unauthorized run of a job outside its intended trigger mechanism ("unauthorized job run"). An attacker who registered (or compromised) valid external-initiator credentials for one bridge/initiator can force pipeline execution of arbitrary jobs by numeric ID, regardless of job type — including jobs that may perform on-chain writes or interact with funded transmitter keys, causing unintended fund-moving transactions, unexpected task execution, or resource exhaustion via repeated forced runs.

### Likelihood Explanation
Preconditions are minimal and match the question: valid EI credentials for any registered external initiator (a low-privilege, non-operator credential type), plus knowledge/guessing of an arbitrary integer job ID (job IDs are small sequential integers, easily enumerable). No admin/operator access is needed. The bypass is deterministic and repeatable for any EI-authenticated caller.

### Recommendation
Replace the `isUser` boolean check with an explicit discriminator between real authenticated users and EI-derived sessions — e.g., check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present, rather than relying on `GetAuthenticatedUser`'s type assertion which EI authentication also satisfies. Additionally/alternatively, verify the target job's type explicitly permits EI-triggered runs before calling `RunJobV2`.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Create an application with one registered `ExternalInitiator` (valid access key/secret) and one non-webhook job (e.g., a `Cron` or `DirectRequest` job) with a known integer job ID.
2. Send `POST /v2/jobs/<jobID>/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's credentials (no session cookie, no API token).
3. Assert current (vulnerable) behavior: response is `200`/`201` and `App.RunJobV2` was invoked (mock expectation `mockApp.On("RunJobV2", ...)` called), returning a pipeline run resource for the non-webhook job.
4. Expected secure behavior after fix: response should be `401`/`403` and `RunJobV2` must never be called for EI-authenticated requests against non-EI-triggerable job types.

	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)

			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))

		}

			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
