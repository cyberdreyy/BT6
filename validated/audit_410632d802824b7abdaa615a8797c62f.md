### Title
Claimed instant-withdraw receipts remain in the default-epoch claim basis, inflating recovery reserve and diluting or freezing recoveries - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` balance. It leaves both `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` unchanged. If that user has already been paid and the borrower defaults later in the same epoch, default finalization treats the claimed receipt as outstanding. The stale amount is counted in `defaultPendingClaimBasis()` and can also be counted as a prefunded instant reserve, causing the recovery denominator and recorded reserve to include assets that are no longer claimable or no longer held by the strategy.

### Finding Description
At request time, the strategy records an instant receipt in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]`. [1](#0-0) 

A normal successful claim burns the receipt and clears only the aggregate request:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The per-epoch user and global claim records are not cleared. [2](#0-1) 

During default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws` is non-zero. [3](#0-2)  `_defaultPrefundedInstantReserve()` then treats `instantWithdrawClaimsByEpoch - pendingInstantWithdraws` as already-funded instant recovery collateral. [4](#0-3) 

Consequently, an already-paid instant receipt:

- remains in the default claim basis;
- can increase `prefundedReserve`;
- increases `reserveAmount` without corresponding strategy assets;
- lowers or corrupts `defaultRecoveryPrice` for all genuine claimants.

The finalization stores that inflated amount in `defaultRecoveryReserve` and uses the inflated basis to calculate `defaultRecoveryPrice`. [5](#0-4) 

The stale entry is also unsafe on the user side. `_claimDefaultedInstantWithdrawRequest()` later reads the stale per-epoch basis and subtracts it from `instantWithdrawsRequests[_user]`, which is already zero for the paid claimant. [6](#0-5) 

### Impact Explanation
This can permanently misallocate borrower-default recoveries.

For example, assume:

- Active claim basis: `900`.
- Genuine unfunded instant basis: `100`.
- Already-claimed instant basis retained in `instantWithdrawClaimsByEpoch`: `50`.
- Actual recovered cash: `200`.

Without the stale claim, total basis is `1,000` and the intended recovery price is `20%`.

With the stale claim:

- `instantWithdrawClaimsByEpoch` is `150` instead of `100`;
- `defaultPendingClaimBasis()` is inflated by `50`;
- `_defaultPrefundedInstantReserve()` records `50` of phantom prefunded collateral;
- `defaultRecoveryReserve` becomes `250` even though only `200` underlying was recovered.

The accounting therefore distributes `250` of claims against `200` of assets and computes the recovery ratio using a denominator containing a paid receipt. Early claimants can receive more than the actual reserve supports, while later claimants can be left unable to claim because `_transferDefaultRecovery()` first decrements `defaultRecoveryReserve` and then attempts to transfer underlying that is not there. [7](#0-6) 

This is not merely dust rounding: the stale amount is the full amount of any instant withdrawal claimed before default.

### Likelihood Explanation
An unprivileged KYC-passing lender can trigger the condition without controlling the borrower:

1. The APR drops enough to enable instant withdrawal.
2. The lender calls `IdleCDOEpochVariant.requestWithdraw`, which routes to `requestInstantWithdraw`. [8](#0-7) 
3. The honest manager starts the epoch and the instant withdrawal is funded.
4. The lender calls `claimInstantWithdrawRequest()` while `allowInstantWithdraw` is enabled. [9](#0-8) 
5. The honest manager calls `stopEpoch`; the borrower fails to return the requested funds, causing default handling.
6. `finalizeDefaultRecovery()` counts the paid receipt as an outstanding default-epoch receipt.

The only external precondition is a same-epoch borrower default with at least one other unfunded instant receipt so `pendingInstantWithdraws != 0`. The attacker does not need a malicious privileged action; the manager and borrower remain honest, with the borrower simply failing to satisfy its obligation.

### Recommendation
When an instant receipt is successfully claimed, clear all receipt accounting for its request epoch:

```solidity
uint256 requestEpoch = /* stored request epoch */;
instantWithdrawsRequestsByEpoch[_user][requestEpoch] -= amount;
instantWithdrawClaimsByEpoch[requestEpoch] -= amount;
```

This requires either recording each instant request’s epoch per user or preventing multiple instant-request epochs from being merged into one aggregate claim. The implementation should also ensure that `instantWithdrawClaimsByEpoch[epoch]` contains only unclaimed receipts before `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` use it.

A regression test should verify that after `claimInstantWithdrawRequest`, both per-epoch mappings and the epoch aggregate are zero for the claimed amount.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract ClaimedInstantInflatesDefaultRecoveryPoC is Test {
    // Existing test fixture/deployments from test/foundry/IdleCreditVault.t.sol:
    // cdoEpoch, strategy, AAtranche, underlying, borrower, manager.

    function testClaimedInstantReceiptInflatesDefaultRecovery() public {
        address attacker = makeAddr("paid-instant-user");
        address victim = makeAddr("unfunded-instant-user");

        uint256 attackerDeposit = 100 * ONE_SCALE;
        uint256 victimDeposit = 100 * ONE_SCALE;
        uint256 recovered = 50 * ONE_SCALE;

        // Both users are KYC-approved and deposit into the AA tranche.
        _depositWithUser(attacker, attackerDeposit, true);
        _depositWithUser(victim, victimDeposit, true);

        // Finish the current epoch, then lower APR enough to enable instant withdrawals.
        _startEpochAndCheckPrices(0);
        _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
        _forceLastEpochAprToZero();

        uint256 attackerTranches = AAtranche.balanceOf(attacker);
        uint256 victimTranches = AAtranche.balanceOf(victim);

        vm.prank(attacker);
        uint256 attackerInstant = cdoEpoch.requestWithdraw(
            attackerTranches / 2,
            address(AAtranche)
        );

        vm.prank(victim);
        uint256 victimInstant = cdoEpoch.requestWithdraw(
            victimTranches / 2,
            address(AAtranche)
        );

        // Honest manager starts the epoch. Instant-withdraw liquidity is collected.
        vm.prank(manager);
        cdoEpoch.startEpoch();

        // Attacker is paid normally, which clears only the aggregate receipt.
        vm.prank(attacker);
        cdoEpoch.claimInstantWithdrawRequest();

        uint256 epoch = strategy.epochNumber();
        assertEq(strategy.instantWithdrawsRequests(attacker), 0);

        // Bug: the paid receipt is still present in default-epoch accounting.
        assertEq(
            strategy.instantWithdrawsRequestsByEpoch(attacker, epoch),
            attackerInstant
        );
        assertEq(
            strategy.instantWithdrawClaimsByEpoch(epoch),
            attackerInstant + victimInstant
        );

        // Victim's instant receipt remains unfunded, so pendingInstantWithdraws != 0.
        assertGt(strategy.pendingInstantWithdraws(), 0);

        // Borrower fails repayment and manager honestly stops the epoch.
        deal(address(underlying), strategy.borrower(), 0);
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpoch(0, 0);

        // Manager supplies a recovery. Because the attacker's stale receipt is included
        // as prefunded basis, accounting records recovery that was never supplied.
        deal(address(underlying), manager, recovered);
        vm.startPrank(manager);
        underlying.approve(address(strategy), recovered);
        cdoEpoch.finalizeDefault(recovered, manager);
        vm.stopPrank();

        // The stale receipt caused phantom reserve/basis to be recorded.
        assertGt(strategy.defaultRecoveryReserve(), recovered);

        // The paid attacker cannot legitimately claim again; their stale epoch entry
        // underflows against instantWithdrawsRequests[attacker] == 0.
        vm.prank(attacker);
        vm.expectRevert();
        cdoEpoch.claimInstantWithdrawRequest();
    }
}
```
