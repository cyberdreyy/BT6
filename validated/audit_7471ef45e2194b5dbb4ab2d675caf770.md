### Title
Stale `lastWithdrawRequest` pointer lets a loss-epoch withdraw receipt be re-claimed at par, escaping the haircut - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` resolves the loss-adjusted claim epoch through the single scalar `lastWithdrawRequest[_user]` instead of iterating `withdrawsRequestsByEpoch`. A second `requestWithdraw` in a later epoch overwrites that pointer, so the epoch-keyed haircut `lossRecoveryPriceByEpoch[lossEpoch]` is never applied to the older receipt. The stale per-epoch entry in `withdrawsRequestsByEpoch[_user][lossEpoch]` remains inside the aggregate `withdrawsRequests[_user]` and is then paid out at par by `_claimFundedWithdrawRequest`. This is the codebase analog of a use-after-free: accounting state keyed to a "freed" pointer (`lastWithdrawRequest` reset/reassigned) is silently re-used through the aggregate counter.

### Finding Description
- `requestWithdraw` stores the request epoch in `withdrawsRequestsByEpoch[_user][currentEpoch]` and unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282,293`).
- When `stopEpochWithDuration(_lossAmount)` runs, the borrower funds only the haircut amount and the strategy records `lossRecoveryPriceByEpoch[epoch]`; the per-epoch receipt in `withdrawsRequestsByEpoch` is left in place for lazy claiming.
- On claim, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest(_user)`, which reads `lossEpoch = lastWithdrawRequest[_user]` and `lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]`, returning early when the price is 0 (`IdleCreditVault.sol:789-795`).
- If the user created a new request in epoch E+1 after the loss epoch E, `lastWithdrawRequest == E+1`, `lossRecoveryPriceByEpoch[E+1] == 0`, so the loss path returns 0 and never clears `withdrawsRequestsByEpoch[_user][E]` via `_clearWithdrawClaimForEpoch`.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still aggregates the loss-epoch receipt — at par once `epochNumber > lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326-349`), burning the full receipt amount.

Attack sequence (attacker is an ordinary KYC'd tranche holder):
1. Epoch E buffer: user calls `requestWithdraw` on tranche tokens.
2. `stopEpochWithDuration(_lossAmount)` ends epoch E with a loss; `lossRecoveryPriceByEpoch[E] < RECOVERY_FULL`; borrower funds only the haircut amount.
3. During buffer of epoch E+1 (or a subsequent epoch), the attacker calls `requestWithdraw` again with a small amount, overwriting `lastWithdrawRequest`.
4. After epoch E+1 stops, `claimWithdrawRequest` pays the aggregate receipt at par: the E-epoch portion escapes its haircut entirely.

### Impact Explanation
The loss-adjusted payout invariant is broken: a receipt that should be paid at `claimBasis * lossRecoveryPrice / RECOVERY_FULL` is paid at `claimBasis`. The overpayment is drawn from strategy underlyings funded for other pending claims — direct theft/pro-rata insolvency against other withdrawers. Loss magnitude is `(RECOVERY_FULL - lossRecoveryPrice) * claimBasis / RECOVERY_FULL`, i.e., up to the full receipt value for a total loss epoch.

### Likelihood Explanation
Requirements are all unprivileged: the attacker only needs a tranche position and two `requestWithdraw` calls straddling a loss epoch. The trigger is `stopEpochWithDuration` with `_lossAmount > 0`, which is an honest-manager action during borrower underperformance — a plausible, non-adversarial event. No existing guard stops it: `_clearWithdrawClaimForEpoch` is only invoked for the epoch currently stored in `lastWithdrawRequest`, and `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, not other users' funded claims.

### Recommendation
Track the loss-adjusted epoch per-receipt rather than via the mutable `lastWithdrawRequest` pointer: e.g., store the epoch inside `withdrawsRequestsByEpoch` processing by checking `lossRecoveryPriceByEpoch` for each epoch with a nonzero entry, or record a per-user `lastLossAdjustedEpoch`/`lossEpochOfRequest` mapping set at request time that cannot be overwritten by later requests. Alternatively, revert `requestWithdraw` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and the loss receipt is unclaimed.

### Proof of Concept
Foundry fork test sketch (contracts: `IdleCDOEpochVariant`, `IdleCreditVault`):

```solidity
// user deposits AA, epoch E runs, then stopEpochWithDuration(lossAmount)
// so strategy.lossRecoveryPriceByEpoch(E) = funded/basis < 1e18
cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));   // epoch E receipt
// manager: stopEpochWithDuration(loss)  -> epochNumber becomes E+1

// during buffer of epoch E+1, attacker requests again (small amount)
cdoEpoch.requestWithdraw(1, address(AAtranche));            // overwrites lastWithdrawRequest

// epoch E+1 stops normally
// now claim:
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
// loss-path lookup used epoch E+1 (price 0) -> skipped;
// funded path pays withdrawsRequests[user] (includes epoch E receipt) at par.
assertGt(underlying.balanceOf(user) - balPre,
         epochEBasis * lossPrice / 1e18); // haircut escaped
```

Note: full PoC validation (exact funding amounts in `stopEpochWithDuration` and whether any additional gating blocks a second `requestWithdraw` while a receipt is pending) could not be fully confirmed within the available context; the vulnerable ordering of the claim path and the pointer overwrite at `IdleCreditVault.sol:282` and `IdleCreditVault.sol:789-795` is verified directly from the code.
