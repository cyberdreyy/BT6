### Title
Unsanitized zip entry names allow arbitrary-path `os.Remove`/`os.OpenFile` (Zip Slip) during extraction - (File: `helpers/archives/zip_extract.go`)

### Summary
`extractZipFile`/`extractZipFileEntry`/`extractZipSymlinkEntry` use `file.Name` from a zip entry verbatim, with no path-traversal or absolute-path sanitization, to call `os.MkdirAll(filepath.Dir(file.Name), ...)`, `os.Remove(file.Name)`, and `os.OpenFile(file.Name, O_CREATE|O_TRUNC, ...)`. The only validation performed is `errorIfGitDirectory`, which only blocks paths whose first cleaned component is `.git` — it does nothing to stop `..`-relative or absolute paths. This is a classic Zip Slip pattern that lets an attacker-crafted archive delete/truncate/overwrite files anywhere the runner process has permission to write, outside the intended extraction root.

### Finding Description
`extractZipFile` (`helpers/archives/zip_extract.go:61-83`) dispatches on entry type and calls `extractZipFileEntry` for regular files: [1](#0-0) 

Before this, `os.MkdirAll(filepath.Dir(file.Name), 0o777)` is called with the raw entry name: [2](#0-1) 

The only guard applied per-entry is `errorIfGitDirectory`, which checks whether the *first path component* equals `.git` — it does not clean or reject `../` sequences or absolute paths: [3](#0-2) 

Because `zip.File.Name` is attacker-controlled (any string, including `../../some/file`, or an absolute path on platforms where `os.Remove`/`os.OpenFile` accept it), an archive entry named e.g. `../../../home/gitlab-runner/.gitlab-runner/config.toml` or a path pointing at another job's trace/cache file will cause:
1. `os.Remove(file.Name)` to unconditionally delete whatever file currently sits at that resolved path — no existence check, no ownership check, no confinement to the archive's extraction directory.
2. `os.OpenFile(..., O_CREATE|O_TRUNC, ...)` to then create/truncate a new file at that path and fill it with attacker-supplied content.

The same pattern applies to `extractZipSymlinkEntry`, which additionally lets the attacker point an arbitrary path to become a symlink to an attacker-chosen target.

This code path is reachable from `ExtractZipFile` → `ExtractZipArchive` → `extractZipFile`, invoked by `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`'s `Extract`, which is used by cache/artifact extraction (`commands/helpers/cache_extractor.go`, `artifacts_downloader.go`). Since job cache/artifact archives are attacker-influenced (a pipeline author controls what gets zipped into cache/artifact archives, and archive content — including arbitrary file names inside the zip — is not otherwise re-validated before extraction), a malicious job can craft a cache or artifact zip with traversal entry names.

Existing checks reviewed:
- `errorIfGitDirectory` — only blocks `.git`-prefixed top-level paths, irrelevant to traversal.
- No `filepath.Clean` + prefix-check against the extraction root is performed anywhere in `zip_extract.go`.
- No absolute-path rejection.
None of these stop path traversal; the invariant "extraction must never remove/write outside the archive's own root" is not enforced.

### Impact Explanation
An unprivileged pipeline author who controls the contents of a cache or artifact zip archive can cause the runner's extraction logic to delete or truncate/overwrite arbitrary files reachable by the extracting process's working directory and permissions — e.g., other jobs' cache/artifact files, trace buffers, or config files if they happen to be relative to the extraction CWD. This matches the described impact: helper state corruption / DoS affecting the job or runner, and in the write-then-truncate case, potential content injection into files outside the intended extraction tree (up to and including symlink creation via `extractZipSymlinkEntry`).

### Likelihood Explanation
Feasible and repeatable: any user able to define a job that produces or supplies a cache/artifact zip (or any code path that calls `ExtractZipFile`/`ExtractZipArchive` on user-influenced input) can embed a `zip.File` with a name containing `../` sequences. `archive/zip` does not sanitize `Name` on read, so `file.Name` reaches `extractZipFile` unmodified. The extraction root and the target file need only overlap by directory traversal reachable via relative path resolution from the extraction CWD — a low bar, especially since cache/artifact extraction happens in predictable, well-known runner working directories.

### Recommendation
Before performing any file-system operation with `file.Name`, resolve it against the intended extraction root and reject the entry if the cleaned, resolved path escapes that root (standard Zip Slip mitigation): e.g. `target := filepath.Join(root, file.Name); if !strings.HasPrefix(filepath.Clean(target)+string(os.PathSeparator), filepath.Clean(root)+string(os.PathSeparator)) { skip/error }`. Apply this check uniformly in `extractZipFile`/`extractZipDirectoryEntry`/`extractZipSymlinkEntry`/`extractZipFileEntry` prior to `os.MkdirAll`, `os.Remove`, `os.OpenFile`, and `os.Symlink`. Also reject absolute paths in entry names.

### Proof of Concept
```go
func TestExtractZipFile_PathTraversalDeletesOutsideFile(t *testing.T) {
    // Sentinel file OUTSIDE the intended extraction directory.
    outsideDir := t.TempDir()
    sentinel := filepath.Join(outsideDir, "sentinel.txt")
    require.NoError(t, os.WriteFile(sentinel, []byte("important-state"), 0o644))

    extractDir := t.TempDir()
    // Craft a zip entry whose name traverses out of extractDir back to sentinel.
    rel, _ := filepath.Rel(extractDir, sentinel) // e.g. ../../tmpXXXX/sentinel.txt

    tempFile, _ := os.CreateTemp("", "archive")
    defer os.Remove(tempFile.Name())
    zw := zip.NewWriter(tempFile)
    w, _ := zw.Create(rel)
    _, _ = w.Write([]byte("attacker-controlled"))
    zw.Close()
    tempFile.Close()

    wd, _ := os.Getwd()
    os.Chdir(extractDir)
    defer os.Chdir(wd)

    err := ExtractZipFile(tempFile.Name())
    require.NoError(t, err)

    // Assert the sentinel outside extractDir was NOT removed/overwritten.
    data, err := os.ReadFile(sentinel)
    require.NoError(t, err)
    assert.Equal(t, "important-state", string(data), "sentinel file must not be modified by traversal entry")
}
```
Expected (current, vulnerable) behavior: the assertion fails — `sentinel.txt` content becomes `"attacker-controlled"` because `os.Remove`/`os.OpenFile` operated on the resolved out-of-root path. After applying the recommended root-confinement check, the entry should be rejected/skipped and the sentinel content should remain unchanged.

```go
func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
```
