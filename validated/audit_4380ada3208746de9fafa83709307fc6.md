### Title
Windows job-object breakaway (`JOB_OBJECT_LIMIT_BREAKAWAY_OK`) lets a build spawn processes that survive job cancellation - ([File: helpers/process/job_windows.go])

### Summary
`CreateJobObject()` sets `JOB_OBJECT_LIMIT_BREAKAWAY_OK` on *every* job object it creates — both the runner-wide job created by `EnsureSubprocessTerminationOnExit` and the per-command job created in `osCmd.Start`. Because both the outer and inner jobs in this nested chain permit breakaway, a process spawned from within a job's descendants using `CREATE_BREAKAWAY_FROM_JOB` can detach from the entire job hierarchy, so closing the per-command job handle (which normally kills the whole subtree via `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`) no longer terminates it.

### Finding Description
`CreateJobObject` (`helpers/process/job_windows.go:86-108`) unconditionally sets `LimitFlags: JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK` and this same function is used both to build the top-level runner job in `EnsureSubprocessTerminationOnExit` (`helpers/process/job_windows.go:142-163`) and the per-command job assigned to the build process tree in `osCmd.Start` (`helpers/process/job_windows.go:25-48`). On Windows 8/Server 2012+ (the exact version gate the code checks for, `MinWindowsVersionSupportingNestedJobs`), nested job breakaway is honored end-to-end when every job in the ancestor chain allows it. Since both jobs here set `BREAKAWAY_OK`, a process created from inside the job tree with the `CREATE_BREAKAWAY_FROM_JOB` creation flag detaches from the per-command job *and* the runner-wide job simultaneously, leaving it as a fully unmanaged process on the host.

`Wait()`/`closeJobObject()` (`helpers/process/job_windows.go:50-74`) rely purely on `KILL_ON_JOB_CLOSE` semantics — closing the job handle terminates everything still associated with the job. A process that has broken away is, by definition, no longer associated with that job (or the outer one), so it is not affected by this termination path and keeps running after the build's cancellation/kill sequence completes.

This is gated behind the `FF_USE_WINDOWS_JOB_OBJECT` feature flag (`helpers/featureflags/flags.go:350-357`), default `false`, and applies to the shell/custom executors on Windows (`executors/shell/shell.go`, `executors/custom/custom.go`). Once an operator enables that flag, the exploit trigger is entirely within reach of an unprivileged CI job author: any job script capable of running a small native helper (compiled at build time or an already-present tool) that calls `CreateProcessW` with `CREATE_BREAKAWAY_FROM_JOB` can escape supervision.

### Impact Explanation
On a shared Windows runner host with `FF_USE_WINDOWS_JOB_OBJECT` enabled, a malicious/compromised job can leave behind a process that is not torn down when that specific job is cancelled or times out. Because the process also escapes the runner-wide job created by `EnsureSubprocessTerminationOnExit`, it also survives beyond the intended "no stale CI jobs linger" guarantee that function's own doc-comment promises. The escaped process can persist on the shared host across builds (potentially other tenants' jobs on the same runner), retaining access to the build directory/host resources, which violates the per-job isolation invariant that cancellation of one build should not leave live descendants.

### Likelihood Explanation
Requires: (1) the shell/custom executor on Windows, (2) `FF_USE_WINDOWS_JOB_OBJECT=true` set by the runner operator, and (3) the ability of the job script to run a program that invokes the Win32 `CreateProcess` API with `CREATE_BREAKAWAY_FROM_JOB` (trivial with a compiled helper, PowerShell P/Invoke, or a pre-existing tool that does this — e.g., tools designed to detach from parent job objects). Given (2) is an explicit opt-in, this is not exploitable against default configurations, but once enabled it is fully reachable by any unprivileged pipeline author without further preconditions.

### Recommendation
Do not set `JOB_OBJECT_LIMIT_BREAKAWAY_OK` on the per-command job created in `osCmd.Start`, or on the top-level runner job in `EnsureSubprocessTerminationOnExit`, unless a specific compatibility need is proven necessary; if breakaway support is required for compatibility with tools that create their own job objects, use `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` scoped only where strictly required, and ensure at least one job in the chain (ideally the per-command job) disallows breakaway so that job cancellation always terminates the full descendant tree regardless of what descendants request.

### Proof of Concept
Go integration test (Windows-only) extending `helpers/process/ensure_subprocess_termination_integration_test.go` and `helpers/process/killer_integration_test.go`:
1. Call `EnsureSubprocessTerminationOnExit()` to simulate the runner-wide job.
2. Start an `osCmd` with `UseWindowsJobObject: true` running a test helper (`helpers/process/testdata/...`) that itself spawns a grandchild process via `CreateProcess` with `CREATE_BREAKAWAY_FROM_JOB` (writing its own PID to a temp file for verification).
3. Assert the grandchild PID file is written (breakaway succeeded).
4. Kill/close the per-command job object (simulating build cancellation via `closeJobObject`/`Wait`).

func (c *osCmd) Start() error {
	setProcessGroup(c.internal, c.options.UseWindowsLegacyProcessStrategy)

	if c.options.UseWindowsJobObject {
		jobObj, err := CreateJobObject()
		if err != nil {
			return fmt.Errorf("starting OS command: %w", err)
		}
		c.jobObject = jobObj
	}

	err := c.internal.Start()
	if err != nil {
		return fmt.Errorf("starting OS command: %w", err)
	}

	if c.options.UseWindowsJobObject {
		// Any failures here are ignored, since we've already started the process running.
		if err := AssignPidToJobObject(c.internal.Process.Pid, c.jobObject); err != nil {
			c.options.Logger.Warn("assigning process to job object:", err)
		}
	}
	return nil
}

func CreateJobObject() (windows.Handle, error) {
	jobObj, err := windows.CreateJobObject(nil, nil)
	if err != nil {
		return 0, fmt.Errorf("creating job object: %w", err)
	}

	info := windows.JOBOBJECT_EXTENDED_LIMIT_INFORMATION{
		BasicLimitInformation: windows.JOBOBJECT_BASIC_LIMIT_INFORMATION{
			LimitFlags: windows.JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE |
				windows.JOB_OBJECT_LIMIT_BREAKAWAY_OK, // Allow subprocesses to explicitly avoid termination using CREATE_BREAKAWAY_FROM_JOB
		},
	}

	if _, err = windows.SetInformationJobObject(
		jobObj,
		windows.JobObjectExtendedLimitInformation,
		uintptr(unsafe.Pointer(&info)),
		uint32(unsafe.Sizeof(info))); err != nil {
		return 0, fmt.Errorf("setting job object information: %w", err)
	}

	return jobObj, nil
}

func EnsureSubprocessTerminationOnExit() error {
	const MinWindowsVersionSupportingNestedJobs uint32 = 9200 // Windows 8 / Server 2012

	// To support per-command Windows Job wrapping as well, we wrap the whole runner in a job only if nesting is supported.
	version := windows.RtlGetVersion()
	if version.BuildNumber < MinWindowsVersionSupportingNestedJobs {
		logrus.Warn("Windows version is too old, skipping process encapsulation.\nPlease upgrade to a supported windows version: https://docs.gitlab.com/runner/install/support-policy/#windows-version-support")
		return nil
	}

	jobObject, err := CreateJobObject()
	if err != nil {
		return fmt.Errorf("creating job object: %w", err)
	}

	if err := AssignProcessToJobObject(windows.CurrentProcess(), jobObject); err != nil {
		_ = windows.CloseHandle(jobObject)
		return fmt.Errorf("assigning process to job object: %w", err)
	}

	// Intentionally leak the job handle. It should only be closed on process termination.
	return nil
