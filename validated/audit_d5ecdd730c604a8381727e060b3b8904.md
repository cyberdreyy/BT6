### Title
Unchecked u64 subtraction in `L1BlockInfo::operator_fee_refund` can panic and halt block execution - (File: crates/common/evm/src/l1block.rs)

### Summary
`L1BlockInfo::operator_fee_refund` computes the gas actually used via a bare (non-checked, non-saturating) `u64` subtraction: `gas.limit() - (gas.remaining() + gas.refunded() as u64)`. This is exactly the same bug class flagged in the DODO report: an arithmetic operation ported without accounting for the checked-arithmetic semantics of the target environment, such that if the subtrahend can ever exceed the minuend, execution panics instead of reverting gracefully.

### Finding Description [1](#0-0)


This mirrors the DODO `_twapUpdate` pattern: plain subtraction that is safe only under an implicit invariant (`gas.remaining() + gas.refunded() <= gas.limit()`), with no `checked_sub`/`saturating_sub` guard and no `unchecked` opt-out documented for the (presumably) checked-by-default numeric path. Unlike Solidity 0.8's checked math, Rust's default release build wraps silently on overflow, but if the workspace enables `overflow-checks` (common for correctness-critical crates, and always enabled in `debug`/test builds), this subtraction panics whenever `gas.remaining() + gas.refunded()` exceeds `gas.limit()`.

This function is invoked from `reimburse_caller`, on the hot path of every non-deposit, post-Isthmus transaction: [2](#0-1) 

The unusual cast `gas.refunded() as u64` is also worth noting: `Gas::refunded()` is documented elsewhere in the codebase as a **signed** counter that "may be negative" (e.g. re-dirtying a slot a prior call cleared), as explicitly called out in the EIP-8130 path: [3](#0-2) 

If the standard-transaction `Gas` accounting can ever produce a negative `refunded()` value in this code path (e.g., through gas-refund interactions introduced by newer upgrades, or a currently-unanticipated edge case), casting it to `u64` would produce a value near `u64::MAX`, making `gas.remaining() + (huge number)` overflow the addition and/or making the subsequent subtraction from `gas.limit()` underflow — both scenarios cause an unrecoverable panic rather than a controlled error, unlike the neighboring `checked_add`/`checked_sub` discipline used throughout the rest of the file (e.g. `settle_fees` in `eip8130.rs`, which explicitly documents "never underflows" reasoning with `checked_sub`).

### Impact Explanation
A panic inside block/transaction execution on this path is not a contained revert — it is a Rust panic during EVM post-execution accounting invoked for essentially every ordinary transaction post-Isthmus. If triggered deterministically by a crafted transaction (once such a transaction is broadcast and included), every full node executing that block would panic identically, resulting in a chain-wide node halt/crash — a permanent liveness failure until a hotfix is deployed. This matches the "Permanent asset blocking / node halt" impact class called out in the rules (node halt via a single signed transaction reaching a core arithmetic invariant).

### Likelihood Explanation
Likelihood is **uncertain and not proven** with the tools available in this session:
- The invariant `gas.remaining() + gas.refunded() <= gas.limit()` should hold by EVM/EIP-3529 construction for a well-behaved `Gas` tracker, so under normal conditions this subtraction should not underflow.
- I was unable to locate the concrete `Gas`/`GasTracker` type definition (it appears to come from an external `revm`/`evm2` dependency not indexed here) to confirm whether `refunded()` can go negative on the standard-transaction path that feeds `operator_fee_refund`, or whether the crate builds with `overflow-checks = true` in release (which would turn a wrap into a hard panic in production).
- Because I could not confirm a concrete, reachable state where the subtraction underflows in this specific call site, I cannot assert exploitability with certainty. This is flagged as the closest structural analog to the reported bug class (bare arithmetic assumed always non-underflowing, later found to break due to changed invariants) rather than a confirmed, proven bypass.

### Recommendation
Replace the bare subtraction with `checked_sub`/`saturating_sub` and treat a violated invariant as a hard internal error surfaced through the existing `BaseTransactionError` machinery (as is already done elsewhere in `eip8130.rs`), rather than allowing a panic to escape into block execution:
```rust
let gas_used = gas
    .limit()
    .checked_sub(gas.remaining().saturating_add(gas.refunded().max(0) as u64))
    .ok_or_else(|| /* explicit internal-invariant error */)?;
let operator_cost_gas_used = self.operator_fee_charge_inner(U256::from(gas_used), spec_id);
```
Also audit whether `gas.refunded()` can be negative in the standard-transaction path before this cast, and add a unit/property test asserting the invariant holds across all reachable `Gas` states (including any negative-refund edge cases).

### Proof of Concept
Not reproducible with available tooling: a concrete transaction/state sequence causing `gas.remaining() + gas.refunded() > gas.limit()` at this call site was not found or constructed in this session, and the `Gas`/`GasTracker` implementation needed to determine reachability lives outside the indexed portion of the codebase. A Devin session with full repository and dependency access (including the `revm`/`evm2` `Gas` type source) would be needed to confirm or rule out reachability and to build a concrete PoC transaction.

```rust
    /// Calculate the operator fee for executing this transaction.
    ///
    /// Introduced in isthmus. Prior to isthmus, the operator fee is always zero.
    pub fn operator_fee_refund(&self, gas: &Gas, spec_id: BaseSpecId) -> U256 {
        if !spec_id.is_enabled_in(BaseUpgrade::Isthmus) {
            return U256::ZERO;
        }

        let operator_cost_gas_limit =
            self.operator_fee_charge_inner(U256::from(gas.limit()), spec_id);
        let operator_cost_gas_used = self.operator_fee_charge_inner(
            U256::from(gas.limit() - (gas.remaining() + gas.refunded() as u64)),
            spec_id,
        );

        operator_cost_gas_limit.saturating_sub(operator_cost_gas_used)
    }
```
