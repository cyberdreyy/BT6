### Title
Unbounded, unauthenticated flooding of `savedCallbacks` via `HandleLegacyUserMessage` causes premature eviction and dropped responses for legitimate users - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` inserts an entry into `h.savedCallbacks` for every incoming `MethodWebAPITrigger` request without any per-sender rate limiting or allowlist check (the code even contains a `// TODO: apply allowlist and rate-limiting here` comment). An attacker able to send arbitrary signed messages can flood the gateway with many distinct `MessageId`s that never receive a node response, growing the map until `pruneCallbacks` evicts the oldest entries — potentially including a legitimate, still-pending victim callback — causing that victim's eventual node response to be silently dropped.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) validates payload decoding, timestamp presence, and message staleness, but performs no rate limiting or allowlist check on the caller before writing to the shared map: [1](#0-0) 
Every accepted message unconditionally inserts a new `*savedCallback` keyed by `msg.Body.MessageId`: [2](#0-1) 

The only bound on map size is `pruneCallbacks`, run on a fixed timer (`CallbackPruneIntervalSec`, default 30s), which first deletes expired entries and then, if the map still exceeds `MaxSavedCallbacks` (default 20000), sorts all remaining entries by `createdAt` and deletes the oldest half regardless of whether they are still awaiting a legitimate response: [3](#0-2) 

The node-side rate limiter (`h.nodeRateLimiter`) only throttles outgoing node responses in `handleWebAPIOutgoingMessage`, not incoming user requests: [4](#0-3) 

Since an attacker (per the linked prior finding) can send messages with a fresh, unlisted key that pass signature validation without being on any allowlist, they can generate an effectively unlimited stream of distinct `MessageId`s that consume slots in `savedCallbacks` and are never cleared by `handleWebAPITriggerMessage` (because no node ever legitimately responds to them), forcing reliance on the size-based eviction path in `pruneCallbacks`. If the flood rate is high enough relative to `CallbackPruneIntervalSec`/`MaxSavedCallbacks`, a legitimate victim's callback — inserted before the flood and still awaiting a node response within `CallbackMaxAgeSec` (default 120s) — can be evicted as one of the "oldest" entries before the real response arrives.

Regarding the specific "cross-MessageId leakage" premise in the question: the map is keyed by exact `msg.Body.MessageId` string, and all reads/writes/deletes are correctly guarded by `h.mu.Lock()`/`Unlock()` in both `handleWebAPITriggerMessage` and `pruneCallbacks`. There is no code path where a response for one `MessageId` could be delivered to another `MessageId`'s callback — `handleWebAPITriggerMessage` looks up strictly by `msg.Body.MessageId` (`handler.go:150`) and returns silently if `found` is false. So the "mis-delivery"/leakage scenario as literally described (races causing responses to be misrouted to the wrong callback) is not supported by the code. The real, valid impact is **eviction-induced silent drop**, not misdelivery.

### Impact Explanation
This is a denial-of-service on correct response delivery: an unauthenticated attacker can cause the gateway to silently discard node responses intended for legitimate users' `MethodWebAPITrigger` requests by exhausting/pressuring the shared `savedCallbacks` map. This maps to Chainlink's "Denial of Service" bounty impact class (degraded availability/correctness of the gateway for other users), not to key/secret disclosure or fund movement. The affected callback simply never fires and the legitimate caller times out.

### Likelihood Explanation
Feasibility depends on the prior finding that unauthenticated senders with a fresh key can get past signature/timestamp checks in `HandleLegacyUserMessage` (no allowlist enforcement is present in this function — see the `TODO` at line 384). Given that, the attack requires only generating `MaxAllowedMessageAgeSec`-compliant, uniquely keyed messages at a rate sufficient to push `len(savedCallbacks)` past `MaxSavedCallbacks` (20000 by default) within a `CallbackPruneIntervalSec` window (30s default), which is a plausible flood rate for an attacker with network access to the gateway's legacy user-message endpoint. This is repeatable and does not require any special privilege.

### Recommendation
- Add per-sender rate limiting/quota enforcement in `HandleLegacyUserMessage` before inserting into `savedCallbacks` (the `TODO` at handler.go:384 should be implemented), so a single unauthenticated sender cannot monopolize map capacity.
- Consider per-sender bounded queues or a fairness-aware eviction policy in `pruneCallbacks` (e.g., evict based on per-sender occupancy rather than pure global age ordering) so one abusive sender cannot cause eviction of another sender's pending, still-valid callback.
- Optionally, reject new inserts (with an explicit "server busy" error) rather than silently evicting older still-valid entries when the map is at capacity.

### Proof of Concept
Go handler-level integration test plan (extending `handler_test.go`):
1. Configure `HandlerConfig{MaxSavedCallbacks: N, CallbackMaxAgeSec: T, CallbackPruneIntervalSec: I}` with small `N` (e.g., 10) for a fast, deterministic test.
2. Call `handler.HandleLegacyUserMessage` once with a legitimate victim `MessageId` and a mock `handlers.Callback` capturing whether `SendResponse` is invoked.
3. Immediately flood `HandleLegacyUserMessage` with `N` additional distinct `MessageId`s (unique keys, valid `Timestamp`/signature), each with a no-op callback, simulating an attacker who never elicits node responses.
4. Trigger `pruneCallbacks()` directly (or advance time and let the ticker fire) so the map exceeds `MaxSavedCallbacks` and the oldest half (including the victim's entry) is evicted.
5. Simulate a legitimate node response for the victim's `MessageId` via `HandleNodeMessage`/`handleWebAPITriggerMessage`.
6. Assert that the victim's captured callback's `SendResponse` was never called (i.e., `found == false` in `handleWebAPITriggerMessage`), confirming the response was silently dropped due to premature eviction caused by attacker flooding — despite the victim's request being well within `CallbackMaxAgeSec`.

	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {

		})

			delete(h.savedCallbacks, e.id)

		}
	}
