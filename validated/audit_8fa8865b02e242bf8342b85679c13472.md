### Title
Mid-epoch deposit over-mints tranche shares when `trancheExpected` clamps to zero, diluting existing LPs - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` prices new tranche shares against `expectedFinal = lastSavedNAV + trancheExpected`, where `trancheExpected` is floored to zero whenever `expectedEpochInterest <= pendingWithdrawFees`. The depositor's own `trancheInterest` is still added to the mint numerator, so when the expected-gain term silently clamps, shares are minted at a price that ignores the interest the vault will actually accrue. A KYC'd attacker can deposit mid-epoch, receive excess tranche tokens, and redeem them after `stopEpoch` for more underlying than a fair `amount / price` mint — a classic share-inflation/donation-style mint bug, analogous to the advisory's "failed bound check → write past the buffer": a defensive clamp produces a value outside the intended range and downstream math consumes it unchecked.

### Finding Description
In `depositDuringEpoch`:

```solidity
if (expectedInt > pendingFees) {
  trancheExpected = _calcTrancheInterestShare(
    _netGainAfterFees(expectedInt - pendingFees, ...), _tranche);
}
uint256 trancheInterest = _calcTrancheInterestShare(
  _netGainAfterFees(interest, _calculateManagementFee(_amount, remaining)), _tranche);
uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
``` [1](#0-0) 

`trancheExpected` is meant to be "existing holders' share of net expected interest". The zero-clamp treats `expectedInt <= pendingFees` as "no gain for tranches", but that condition is reachable while real per-unit tranche interest is still positive:

- `startEpoch` sets `expectedEpochInterest = pendingWithdrawFees + adjustedActiveInterest`, where `adjustedActiveInterest` is clamped to `0` when `interestForOverUnderPerformance` is sufficiently negative [2](#0-1) . Heavy BB withdrawal requests produce exactly this negative `diff` at `requestWithdraw` [3](#0-2) .
- In that state `expectedEpochInterest == pendingWithdrawFees`, so `trancheExpected = 0` and `expectedFinal = lastSavedNAV`.
- Yet `trancheInterest` for the new deposit is computed independently from `_calcInterest(_amount)` using the live strategy APR (positive — the underperformance adjustment only hit the accounting counter, not the borrower's owed interest). The mint numerator keeps `(_amount + trancheInterest)` while the denominator drops the existing-holders' interest entirely, so `_minted` exceeds the fair `amount / priceEnd`.

The same skew appears whenever `expectedInt < pendingFees` is reachable via fee accrual on additional requests, and more generally any case where the clamped `trancheExpected` underestimates the true end-of-epoch NAV per share.

Result: the mid-epoch depositor is minted shares as if the tranche would end flat, while the epoch actually ends with accrued interest on the higher NAV. At `stopEpoch`, `_updateAccounting` raises the tranche price on real NAV, so the attacker's tranche tokens redeem for strictly more than `deposit + fair prorated interest`. The excess is paid by diluting pre-existing tranche holders.

### Impact Explanation
Direct theft via unfair mint. The attacker deposits `_amount` mid-epoch and, after the next `stopEpoch` + `requestWithdraw`/`claimWithdrawRequest`, withdraws `_amount` plus their own prorated interest plus a slice of existing holders' interest. The over-mint fraction equals `trancheInterest / expectedFinal` priced against a NAV that omits realized holder interest; with large BB-request-driven negative `interestForOverUnderPerformance` the entire epoch's tranche interest is dropped from the denominator, so the depositor captures interest on the whole tranche NAV rather than only their deposit. Loss is bounded by roughly `trancheInterest * supply / NAV` worth of shares per deposit and repeats each epoch the condition holds.

### Likelihood Explanation
Requires `isDepositDuringEpochDisabled == false` (owner-enabled), a running epoch, non-AYS, non-programmable, non-APR0 mode, and wallet-KYC. The negative `interestForOverUnderPerformance` condition is reachable by any allowed BB holder via ordinary `requestWithdraw` before `startEpoch` — no privileged collusion. Once the counter clamps `adjustedActiveInterest` to zero at `startEpoch`, every `depositDuringEpoch` call in that epoch over-mints. Existing guards (`_guarded` limit, `_skimDonatedAssets`, epoch gating, KYC) do not check the fairness of the mint price, so nothing stops it.

### Recommendation
Remove the silent zero-clamp divergence between numerator and denominator. Either:
- compute `trancheExpected` without the `expectedInt > pendingFees` gate (use a signed/`max(0, expectedInt - pendingFees)` net-gain term consistently in both `trancheExpected` and the depositor's mint), or
- price mid-epoch mints against the realized current virtual price plus the depositor's own prorated interest only, i.e. `minted = _amount * supply / lastNAV` and credit `trancheInterest` separately at claim, so a stale or clamped `expectedEpochInterest` can never inflate the mint.

### Proof of Concept
Foundry fork PoC sketch (existing harness `test/foundry/IdleCreditVault.t.sol` provides `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testDepositDuringEpochOverMintsOnClampedExpected() external {
    uint256 amount = 10_000 * ONE_SCALE;
    // AA + BB deposits; enable mid-epoch deposits (fixed APR, non-AYS)
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);
    uint256 mintedAA = idleCDO.depositAA(amount);
    _depositWithUser(userBB, amount, false); // BB deposit

    // BB holder requests full withdraw -> negative interestForOverUnderPerformance
    vm.prank(userBB);
    cdoEpoch.requestWithdraw(0, address(BBtranche));
    // (repeat/top-up until adjustedActiveInterest clamps to 0 at startEpoch)

    _startEpochAndCheckPrices(0);
    assertEq(
        cdoEpoch.expectedEpochInterest(),
        cdoEpoch.pendingWithdrawFees(),
        "precondition: trancheExpected will clamp to 0"
    );

    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);

    address attacker = makeAddr("attacker"); // KYC-passed wallet
    deal(defaultUnderlying, attacker, amount);
    _whitelist(attacker);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), amount);
    uint256 minted = cdoEpoch.depositDuringEpoch(amount, address(AAtranche));
    vm.stopPrank();

    uint256 fairMint = amount * ONE_TRANCHE_TOKEN / cdoEpoch.virtualPrice(address(AAtranche));
    assertGt(minted, fairMint, "over-mint: numerator kept trancheInterest, denominator dropped holder interest");

    // stop epoch, attacker requests and claims; redeems more than amount + own interest
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(attacker) - balPre, amount, "attacker extracted existing holders' interest");
}
```

Note: the precondition depends on driving `interestForOverUnderPerformance` negative enough that `adjustedActiveInterest` clamps to 0; the test file already exercises this counter via BB `requestWithdraw` in `testRequestWithdraw*` cases. If the clamp cannot be reached in a given deployment configuration, the same over-mint applies to the gap between clamped `trancheExpected` and realized tranche interest, scaled down accordingly.
