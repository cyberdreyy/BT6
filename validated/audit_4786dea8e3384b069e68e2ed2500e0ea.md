### Title
Missing upper-bound check on `TriggerRequestPayload.Timestamp` allows indefinite replay of gateway user messages - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` only rejects messages whose `Timestamp` is too far in the *past*, never messages whose `Timestamp` is set arbitrarily far in the *future*. An attacker who signs a `web_api_trigger` message with an inflated `Timestamp` (or who captures such a signed message) can resubmit it indefinitely without ever tripping the staleness check.

### Finding Description
In `HandleLegacyUserMessage`, the only freshness check performed is: [1](#0-0) 

This computes `uint(time.Now().Unix()) - h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)`, which is only true (rejecting the message) when the payload's timestamp is older than the allowed window. There is no corresponding check such as `uint(payload.Timestamp) > uint(time.Now().Unix()) + someBound` to reject timestamps set in the future. Because `Timestamp` lives inside `webapicap.TriggerRequestPayload`, which is part of `msg.Body.Payload` and is covered by the ECDSA signature over the whole message body (see `msg.Sign`/`msg.Validate` used throughout `handler_test.go`), the signing party fully controls this field — the signature does not prevent them from setting `Timestamp` to `now + 1e9`.

Once `Timestamp` is inflated, `now - MaxAllowedMessageAgeSec > payload.Timestamp` will essentially never become true again (until real time catches up to the attacker-chosen value, which could be set arbitrarily far ahead), so the message is treated as fresh forever. This defeats the purpose of the freshness check, which is meant to bound how long a captured signed message remains valid/replayable (the "TODO: apply allowlist and rate-limiting here" comment right after this check further confirms no other anti-replay mechanism exists at this layer) [2](#0-1) .

The request reaches this code path directly from the gateway's user message handling on `MethodWebAPITrigger`, which is confirmed by `TestHandlerReceiveHTTPMessageFromClient`'s happy-path test that calls `handler.HandleLegacyUserMessage` with an attacker-supplied, self-signed `api.Message` and no additional gating before reaching the timestamp check [3](#0-2) .

### Impact Explanation
This is a message-freshness / replay-window bypass. Since the check enforces only a lower bound, a signed gateway message with a future timestamp is accepted indefinitely, so a single captured/leaked signed `web_api_trigger` message can be replayed to the DON repeatedly outside the intended freshness window, forwarded to all DON members via `don.SendToNode` for every replay [4](#0-3) . This maps to an authentication-soundness / request-impersonation weakness (unbounded replay of a previously valid signed request), rather than fund movement or secret disclosure directly, but it removes a designed defense-in-depth control against replay of stale/captured signed requests.

### Likelihood Explanation
Any holder of an ECDSA key that can produce a validly-signed `api.Message` (no gateway auth token needed, per the "no auth token" precondition and the test harness which signs with an arbitrary node key) can trivially set `Timestamp` to a large future value when constructing the payload. This requires no special privilege beyond what's already needed to send a signed message to `HandleLegacyUserMessage`, and is fully reproducible with a single crafted request.

### Recommendation
Add an explicit upper-bound check rejecting messages whose `Timestamp` is further in the future than a small allowed clock-skew tolerance, e.g.:
```go
now := uint(time.Now().Unix())
if now-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) || uint(payload.Timestamp) > now+h.config.MaxAllowedClockSkewSec {
    // reject as stale/invalid
}
```
Additionally consider tracking recently-seen message IDs/timestamps to reject exact replays within the freshness window.

### Proof of Concept
Add a Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go` alongside `TestHandlerReceiveHTTPMessageFromClient`:
1. Build `msg := triggerRequest(t, nodes[0].PrivateKey, []string{"topic"}, "", strconv.FormatInt(time.Now().Unix()+10_000_000, 10), "")` (timestamp 10,000,000s / ~115 days in the future).
2. Call `cb := hc.NewCallback(); err := handler.HandleLegacyUserMessage(ctx, msg, cb)`.
3. Assert `err` is `nil` and that `cb.Wait` does **not** yield a `"stale message"` `api.HandlerError` response — instead assert the message is forwarded to `don.SendToNode` for all DON members (i.e., treated as valid), demonstrating the freshness check fails to reject a timestamp far outside the intended window in either direction.

func TestHandlerReceiveHTTPMessageFromClient(t *testing.T) {
	handler, _, don, nodes := setupHandler(t)
	ctx := t.Context()
	msg := triggerRequest(t, nodes[0].PrivateKey, []string{"daily_price_update"}, "", "", "")
	codec := api.JsonRPCCodec{}

	t.Run("happy case", func(t *testing.T) {
		// sends to 2 dons
		don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Run(func(args mock.Arguments) {
			nodeReq := nodeRequest(msg)
			require.Equal(t, nodeReq, args.Get(2))
		}).Return(nil).Once()
		don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Run(func(args mock.Arguments) {
			nodeReq := nodeRequest(msg)
			require.Equal(t, nodeReq, args.Get(2))
		}).Return(nil).Once()

		cb := hc.NewCallback()
		err := handler.HandleLegacyUserMessage(ctx, msg, cb)
		require.NoError(t, err)

		resp, err := hc.ValidatedResponseFromMessage(msg)
		require.NoError(t, err)
		err = handler.HandleNodeMessage(ctx, resp, nodes[0].Address)
		require.NoError(t, err)

		r, err := cb.Wait(t.Context())
		require.NoError(t, err)
		require.Equal(t, handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError}, r)
	})
