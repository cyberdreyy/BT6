### Title
Gateway `HandleLegacyUserMessage` forwards unauthenticated user requests to the DON with allowlist/rate-limiting explicitly left unimplemented - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The gateway's `capabilities` handler contains an explicit `// TODO: apply allowlist and rate-limiting here` comment directly before the code that forwards every incoming legacy user request to all DON member nodes, with no allowlist check and no rate limiting applied to this code path.

### Finding Description
`HandleLegacyUserMessage` is called for every legacy (DON-ID-based) request that reaches the gateway's user-facing HTTP endpoint via `gateway.ProcessRequest` [2](#0-1) . Inside the handler, after basic payload/timestamp/staleness validation, the code explicitly marks the allowlist/rate-limit enforcement as not-yet-implemented and proceeds to broadcast the request to every DON member node unconditionally: [3](#0-2) 

Unlike the node-facing side of this same handler (`handleWebAPIOutgoingMessage`), which does enforce `h.nodeRateLimiter.Allow(nodeAddr)` [4](#0-3) , the user-facing `HandleLegacyUserMessage` path has no equivalent check — no allowlist verification of the caller/workflow, and no rate limiting of user-submitted requests before they are relayed to `don.SendToNode` for every DON member.

### Impact Explanation
Because there is no allowlist enforcement on this path, any unprivileged client able to reach the gateway's user HTTP port with a well-formed legacy JSON-RPC request (`web_api_trigger` method) can have that request forwarded to every node in the target DON, bypassing whatever authorization model (e.g., workflow-owner allowlisting used elsewhere in the vault/gateway paths, as seen in `IsGatewayNotAllowlistedError`/`allowlistRequest` patterns used by other handlers) is intended to gate DON-bound traffic. Combined with the absence of user-side rate limiting, this also creates a request-amplification/DoS vector against the DON, since a single unauthenticated caller can flood all DON member nodes without throttling at the gateway.

### Likelihood Explanation
The comment is not stale/dead commented-out code in the classic sense — it is a live, explicit acknowledgment in production code that a security control (allowlist + rate limiting) is missing on a path that is directly reachable from unprivileged internet clients through the gateway's public-facing `ProcessRequest`/`HandleLegacyUserMessage` flow. This is a "TODO"-style admission of a missing check on the exact family of controls (message envelopes, allowlist/handlers) called out as in-scope, making exploitation straightforward for any external caller who knows a valid DON ID and method name.

### Recommendation
Implement allowlist verification (i.e., confirm the caller/workflow is authorized against the DON's configured allowlist) and apply the existing rate-limiting primitives (or a dedicated user-facing limiter) inside `HandleLegacyUserMessage` before forwarding requests to `don.SendToNode`, mirroring the enforcement already present in `handleWebAPIOutgoingMessage`. Remove the TODO once the control is implemented, and add tests asserting that non-allowlisted/excessive requests are rejected before reaching DON nodes.

### Proof of Concept
1. Configure a gateway with the `capabilities` handler for a DON exposing `MethodWebAPITrigger`.
2. As an unauthenticated/unprivileged client, send a JSON-RPC request to the gateway's public user port with a valid `DonId`, `Method: "web_api_trigger"`, and a `TriggerRequestPayload` containing a fresh `Timestamp`.
3. Observe in `core/services/gateway/handlers/capabilities/handler.go` (`HandleLegacyUserMessage`) that the request passes payload/timestamp checks and is forwarded via `don.SendToNode` to every DON member node [5](#0-4)  with no allowlist or per-caller rate-limit check applied, confirming any caller able to reach the gateway can trigger DON-wide fan-out of arbitrary trigger payloads.

*Note: I was unable to fully trace whether an outer layer (e.g., a separate `MultiHandler` wrapper) reintroduces allowlist enforcement before dispatching to this specific `HandleLegacyUserMessage` implementation for legacy service configurations; the code path examined (`gateway.go` → `handlers.Handler.HandleLegacyUserMessage`) shows no such check in `capabilities/handler.go` itself, but I could not fully audit `multihandler.go` or `handler.dummy.go` wrapping behavior in this session.*
