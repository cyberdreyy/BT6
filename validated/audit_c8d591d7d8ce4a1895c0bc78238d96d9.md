## Finding

### Title
Missing rollback callback in `MultisigFactory::create` permanently strands attacker-griefed users' deposits - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create()` dispatches an account-creation batch (`create_account` + `deploy_contract` + `transfer` + `function_call`) to a deterministic subaccount name (`"{name}.{factory}"`) but, unlike the sibling factories (`lockup-factory`, `staking-pool-factory`), it attaches **no callback** to detect and refund a failed creation. An unprivileged attacker can front-run/squat the same `name` that a legitimate user is about to use, causing the victim's `create_account` action to fail (account already exists). NEAR then refunds the transferred deposit to the *predecessor of the failed receipt* — the factory contract itself — not to the original depositor. Because `MultisigFactory` has no state, owner, or withdrawal method, that NEAR becomes permanently unrecoverable inside the factory account.

### Finding Description
`create()` builds the target subaccount id deterministically from a caller-supplied `name`: [1](#0-0) 

Unlike `lockup-factory::create()` and `staking_pool_factory::create_staking_pool()`, which both attach a `.then(ext_self::on_..._create(...))` callback that checks `is_promise_success()` and explicitly refunds the original `predecessor_account_id` on failure: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) 

`MultisigFactory::create()` has no such callback at all — it simply returns the batch `Promise`: [6](#0-5) 

Because a subaccount name like `"alice.multisig-factory.near"` can only ever be created once, an attacker can observe a pending/likely `create` transaction (or simply pre-empt a predictable/desirable `name`) and submit their own `create` call with the same `name` first. When the victim's transaction executes, the `create_account` action fails ("Account already exists"), the whole receipt fails, and the attached NEAR deposit that was queued for `transfer` in that failed receipt is refunded — per NEAR protocol semantics — to the **predecessor of that receipt**, which is the factory contract's own account (`env::current_account_id()`), not the original `predecessor_account_id` who signed the top-level `create` call. `MultisigFactory` is a stateless struct with no owner and no withdrawal function, so those funds are stuck in the factory account balance with no code path to ever return them to the victim.

This is the same custody-binding violation the external report describes (an adversary blocking/colliding a deterministic deployment target to disrupt legitimate creation), mapped onto this repo's actual mechanism: instead of a `try/catch` revert, the missing refund callback turns a blocked deployment into **irrecoverably frozen funds** — recorded deposit intent versus NEAR actually returned to the depositor.

### Impact Explanation
Any user who calls `MultisigFactory::create` with a `name` an attacker has front-run loses their entire attached deposit permanently — it is trapped in the factory contract's balance with no admin, owner, or refund mechanism to retrieve it. This matches the Critical impact bucket: funds permanently frozen.

### Likelihood Explanation
Likelihood is high for any observable/desirable `name`: an attacker only needs to see a pending transaction in the mempool (or predict a commonly-chosen name) and submit a cheaper/faster `create` call with the identical `name` before the victim's transaction lands. No privileged access, victim key, or special timing beyond ordinary front-running is required.

### Recommendation
Add an `ext_self` callback to `MultisigFactory::create` (mirroring `lockup-factory`/`staking-pool-factory`), check `is_promise_success()` in the callback, and explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit)` on failure so the original depositor is refunded instead of losing funds to the factory's own unrecoverable balance.

### Proof of Concept
1. Victim intends to call `create({"name": "alice", "members": [...], "num_confirmations": 2})` on `MultisigFactory`, attaching deposit `D`.
2. Attacker observes this pending transaction (or simply front-runs a desirable name) and submits their own `create({"name": "alice", ...})` transaction first, which succeeds and creates `alice.multisig-factory.near`.
3. Victim's transaction executes: the `create_account` action for `alice.multisig-factory.near` fails because the account already exists; the whole receipt (including the `transfer(D)` action) fails.
4. Per NEAR refund semantics, `D` is returned to the predecessor of the failed receipt — the `MultisigFactory` contract account itself — not to the victim.
5. `MultisigFactory` has no state or method (see `multisig-factory/src/lib.rs` lines 22-49) to move that balance back out, so `D` is permanently stuck. [7](#0-6)

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
