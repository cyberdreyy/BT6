### Title
Unauthenticated user enumeration via distinguishable error bodies and timing in `CreateSession` / `NewORM` - ([File: core/sessions/localauth/orm.go])

### Summary
`POST /sessions` returns raw, distinguishable error strings and has a measurable timing gap between unknown-email and wrong-password login attempts, because `CreateSession` in `core/sessions/localauth/orm.go` short-circuits on `FindUser` failure and later surfaces the underlying error verbatim through `jsonAPIError`. This lets an unauthenticated client enumerate valid operator account emails before attempting credential attacks.

### Finding Description
`SessionsController.Create` (`core/web/sessions_controller.go:56-60`) calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and, on any error, forwards it unmodified to the client with `jsonAPIError(c, http.StatusUnauthorized, err)`. `jsonAPIError` (`core/web/helpers.go:21-29`) puts `err.Error()` directly into the JSON API response body when the error isn't a `*models.JSONAPIErrors`.

In `orm.CreateSession` (`core/sessions/localauth/orm.go:144-162`):
```go
user, err := o.FindUser(ctx, sr.Email)
if err != nil {
    return "", err   // raw sql.ErrNoRows-derived error surfaces to the client
}
...
if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
    o.auditLogger.Audit(audit.AuthLoginFailedPassword, ...)
    return "", pkgerrors.New("Invalid password")
}
```
`findUser` (line 55-59) runs `SELECT * FROM users WHERE lower(email) = lower($1)` and returns the raw `sql.ErrNoRows` when no row matches. That unwrapped error propagates straight back to the HTTP handler, producing a body like `"sql: no rows in result set"` for unknown emails, versus the custom string `"Invalid password"` for known emails with an incorrect password — a plainly distinguishable message.

There is also a timing side channel: the unknown-email path returns immediately after a DB miss with no further work, while the known-email/wrong-password path executes `utils.CheckPasswordHash` (bcrypt), which is deliberately CPU-expensive. This produces a consistent, measurable latency difference between the two cases in addition to the body-content difference.

By contrast, `AuthorizedUserWithSession` (session-cookie lookup, lines 87-107) already returns a uniform `sessions.ErrUserSessionExpired` for both "no such session" and "session found but user missing" cases, so the cookie-lookup path does not leak account existence. The enumeration issue is isolated to the `POST /sessions` login flow's error propagation.

### Impact Explanation
This is an information-disclosure / reconnaissance primitive, not a direct authentication bypass. It allows an unauthenticated attacker reaching the node's API port to enumerate valid operator emails via distinguishable `401` bodies (and secondarily via timing), which is a precondition for a subsequent credential-stuffing or brute-force attack against confirmed valid accounts. It does not by itself grant node takeover; it lowers the cost/precision of a follow-on credential attack. This maps to a lower-severity "sensitive information disclosure aiding further attack" class rather than the "Critical: node takeover" class claimed in the question — no code path here grants authentication bypass or session/token forgery on its own.

### Likelihood Explanation
Highly feasible and repeatable: it requires only network reachability to the node's `/sessions` endpoint and no credentials at all. A trivial table-driven script comparing response bodies for a known vs. unknown email, or measuring response latency, reliably distinguishes the two cases every time, since the behavior (`sql.ErrNoRows` string vs. `"Invalid password"` string, and bcrypt-vs-no-bcrypt timing) is deterministic in the current code.

### Recommendation
- In `orm.CreateSession`, normalize all authentication failures (unknown user, wrong password, invalid email) to a single generic error (e.g., `"invalid email or password"`) before returning, and never propagate raw `sql.ErrNoRows`/DB errors to the HTTP layer.
- Perform a constant-time-equivalent operation for unknown users (e.g., run `utils.CheckPasswordHash` against a fixed dummy hash) so the unknown-email path takes comparable time to the wrong-password path, closing the timing side channel.
- Apply the same generic-error treatment to `FindUserByAPIToken` failures and any other authentication comparison surfaced through `jsonAPIError`.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/sessions_controller_test.go`):
1. Create one real user via `app.AuthenticationProvider().CreateUser`.
2. Issue `POST /sessions` with:

   - `{knownEmail, wrongPassword}`
3. Assert both return `401`, but capture and compare response bodies — expect them to currently differ (`"sql: no rows in result set"` vs `"Invalid password"`), demonstrating the enumeration channel exists today.

```go
func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}
```

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
```

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```
