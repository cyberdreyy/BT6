### Title
Instant-withdraw receipts are never cleared per-epoch on a normal claim, so a defaulted-epoch cleanup pays them twice from the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` mirrors the kernel bug class: the receipt is "handed off" (burned and paid at par) but the per-epoch bookkeeping that the default-cleanup path later relies on — `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` — is never cleared. When a borrower default is later finalized for that same epoch, `_claimDefaultedInstantWithdrawRequest` frees the same receipt a second time, paying the user again out of `defaultRecoveryReserve` at the recovery price and draining funds owed to honest defaulted claimants.

### Finding Description
- `requestInstantWithdraw` records three counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, and `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) 
- The normal claim path only zeroes the aggregate: it burns the user's receipt tokens, sets `instantWithdrawsRequests[_user] = 0`, and transfers funded underlyings. It never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` [2](#0-1) 
- After default finalization, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` as the claim basis, subtracts it from `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws`, burns `claimBasis` receipt tokens, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the isolated reserve [3](#0-2) 

Attack trace (epoch E, running phase, default at `stopEpoch`):
1. Attacker calls `requestInstantWithdraw(X)`; `instantWithdrawsRequestsByEpoch[attacker][E] = X`, receipt tokens minted.
2. Borrower/manager funds instant withdrawals (`getInstantWithdrawFunds`/`collectInstantWithdrawFunds`); attacker calls `claimInstantWithdrawRequest` and is paid `X` at par. Per-epoch entries stay at `X`.
3. Borrower defaults; `finalizeDefault`/`finalizeDefaultRecovery` sets `defaultRecoveryEpoch = E`, `defaultInstantWithdrawsFinalized = true`, and sizes `defaultRecoveryReserve` partly from `instantWithdrawClaimsByEpoch[E]` — which still includes the attacker's already-paid `X`.
4. To satisfy the arithmetic guards, the attacker re-requests an instant withdraw `Y` in epoch E before the default stop (raises per-epoch to `X+Y`, aggregate to `Y`), and after finalization opens post-default requests (`requestWithdraw` minting `P` and `requestInstantWithdraw` minting `Z`) so that `Y + Z >= X + Y` (choose `Z = X`) and total minted receipt balance covers the burn of `X+Y`.
5. `claimInstantWithdrawRequest` runs `_claimDefaultedInstantWithdrawRequest` first: `claimBasis = X+Y`, burn succeeds against the post-default-minted balance, and `(X+Y) * defaultRecoveryPrice / RECOVERY_FULL` is transferred from `defaultRecoveryReserve`. The `X` component corresponds to a receipt already paid in full at step 2 — a double payout.

### Impact Explanation
Direct theft of the default recovery reserve: the attacker extracts `X * defaultRecoveryPrice / RECOVERY_FULL` more than they are owed, denominated in underlying, taken from the same reserve that honest defaulted-epoch receipt holders claim against (and the over-sized `instantWithdrawClaimsByEpoch[E]` accounting is exactly what funded that reserve). `defaultRecoveryReserve` is decremented on each payment [4](#0-3) , so legitimate claimants' `transfer` reverts or they receive nothing once it is drained — theft plus permanent freezing of unclaimed recovery. The "one receipt one payout" invariant is broken.

### Likelihood Explanation
Requires an epoch supporting instant withdrawals with funded liquidity, followed by a borrower default in the same `epochNumber`, plus post-default re-requests to clear the burn/subtraction guards. All attacker steps use unprivileged entry points (`requestInstantWithdraw`, `claimInstantWithdrawRequest`, `requestWithdraw`, `claimWithdrawRequest` via the IdleCDO); owner/manager/borrower actions (funding instant withdrawals, stopping epoch, finalizing default) are honest sequencing, not attacker behavior. The missing cleanup is unconditional — there is no skim, flag, or epoch gate that clears `instantWithdrawsRequestsByEpoch` on the funded-claim path — so whenever this sequence of events occurs, the phantom claim exists for every user who claimed an instant withdraw in the defaulted epoch.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers for the epoch(s) being claimed the same way `_claimDefaultedInstantWithdrawRequest` does — i.e., zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount (or track the funded epoch explicitly) before paying, so a receipt that was already paid at par can never be counted again in `defaultRecoveryEpoch` cleanup. Alternatively, key the defaulted-claim basis on `min(instantWithdrawsRequests[_user], instantWithdrawsRequestsByEpoch[_user][defaultEpoch])`, though explicit clearing on claim is the cleaner fix matching the per-epoch accounting model used by `withdrawsRequestsByEpoch`.

### Proof of Concept
Reproducible Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` instant-withdraw helpers):

```solidity
function testInstantClaimDoublePaidFromRecoveryReserve() external {
    // epoch E running; attacker deposits, then:
    vm.prank(attacker); cdo.requestInstantWithdraw(X, tranche);
    // manager funds instant withdrawals, borrower repays liquidity
    fundInstantWithdraws(X); // collectInstantWithdrawFunds moves underlying into vault
    vm.prank(attacker); cdo.claimInstantWithdrawRequest(); // paid X at par
    // NOTE: instantWithdrawsRequestsByEpoch[attacker][E] still == X

    vm.prank(attacker); cdo.requestInstantWithdraw(Y, tranche); // per-epoch now X+Y

    // borrower defaults at stopEpoch; manager finalizes recovery
    stopEpochDefault();
    finalizeDefaultRecovery(recovered); // reserve sized using stale instantWithdrawClaimsByEpoch[E]

    // post-default: mint enough receipts so burn(X+Y) succeeds
    vm.prank(attacker); cdo.requestWithdraw(P, tranche);      // postDefaultRequests
    vm.prank(attacker); cdo.requestInstantWithdraw(X, tranche); // Z = X, new epoch key

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker); cdo.claimInstantWithdrawRequest();
    // paid (X+Y) * defaultRecoveryPrice / RECOVERY_FULL, but only Y was truly pending;
    // X was already paid at par -> attacker stole X * recoveryPrice from the reserve.
    assertEq(underlying.balanceOf(attacker) - balPre,
             (X + Y) * strategy.defaultRecoveryPrice() / RECOVERY_FULL);
}
```

Uncertainty: the PoC assumes the IdleCDO still forwards `requestInstantWithdraw`/`requestWithdraw` after `defaultRecoveryFinalized` (the strategy itself does not block post-default instant requests; only `requestWithdraw` has an explicit post-default branch). If the CDO layer blocks post-default instant requests, the burn-supply step would need adjustment, but the stale-ledger defect itself is unconditional and also mis-sizes `defaultRecoveryReserve` via `instantWithdrawClaimsByEpoch` even without the double-claim.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

```text
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
```
