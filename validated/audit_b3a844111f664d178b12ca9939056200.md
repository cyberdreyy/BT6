### Title
Closed-pool `requestWithdraw` mints receipts for projected interest that is never funded - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
Analog of the ERC721Votes "first self-delegation doubles voting power" bug: a state transition credits value to the user without an offsetting debit. In `IdleCreditVault.requestWithdraw`, the strategy burns only `_principal` strategy tokens from the CDO but mints `_amount` (= principal + projected epoch interest − fees) of receipt tokens to the user. The interest component is meant to be funded later because `pendingWithdraws += _amount` forces the borrower to source it at `stopEpoch`. However, when the pool is already closed (`epochEndDate == 0`), the `pendingWithdraws` increment is skipped — so the projected-interest portion of the receipt is minted with no funding source at all, yet `claimWithdrawRequest` still pays the full `_amount` at par from the strategy's underlying balance, diluting every other funded claimant.

### Finding Description
In `IdleCreditVault.requestWithdraw`, the CDO passes `_underlyings = principal + interest - totalFees` (computed in `IdleCDOEpochVariant.requestWithdraw` via `_calcInterestWithdrawRequest`) as `_amount` and the raw `principal` separately: [1](#0-0) 

The vault burns only `_principal` from the CDO but mints `_amount` to the user and records `_amount` in `withdrawsRequests`/`withdrawsRequestsByEpoch`: [2](#0-1) 

The `pendingWithdraws += _amount` line is the debit side of the ledger: it is what obliges the borrower to fund the interest component at the next `stopEpoch` via `collectWithdrawFunds`. When `isClosed` is true (a successfully closed pool already recalled all principal, `epochEndDate == 0`), that increment is skipped — the comment itself states "a successfully closed pool already recalled all funds and has no later stopEpoch." But the mint of `_amount` and the `withdrawsRequests` record still happen unconditionally.

On the claim side, `_claimFundedWithdrawRequest` explicitly bypasses the one-epoch wait when `epochEndDate() == 0` and pays `withdrawsRequests[_user]` — the full `_amount` including the unfunded projected interest — via `_transferFundedClaim`, which transfers directly from the strategy's underlying balance: [3](#0-2) [4](#0-3) 

So in a closed pool the sequence is: `requestWithdraw` mints `principal + interest` receipts while burning only `principal`, records no funding obligation (`pendingWithdraws` unchanged), and `claimWithdrawRequest` immediately pays `principal + interest` in underlying from the strategy. The `interest` portion is backed by underlying belonging to other pending receipts and residual claimants — exactly the "increment without decrement" pattern of the reference bug (`_moveDelegateVotes` credits `_to` while skipping the `_from == address(0)` debit).

### Impact Explanation
A KYC-passed lender holding tranche tokens when the pool closes can request a withdrawal and be paid more underlying than their position is worth — up to the projected epoch interest on their principal (e.g., at 10% APR over a 30-day epoch, ~0.8% of NAV per request, repeatable across many addresses/positions since there is no per-user limit). The excess is stolen directly from underlyings reserved for other withdraw-request claimants, breaking the "one receipt, one funded payout" invariant and making the last claimants' requests unpayable (insolvency at claim time).

### Likelihood Explanation
Requires a closed pool (`epochEndDate == 0`) with `epochDuration != 0` so `_calcInterestWithdrawRequest` still returns nonzero projected interest, and residual underlying on the strategy (other pending claims). Both conditions arise naturally: closing a pool does not zero `epochDuration`, and any users who requested withdrawal before or after close leave claims payable from the strategy. The attacker needs only a normal tranche-token position; no privileged action is involved. The main uncertainty is whether callers zero the effective APR/duration during close, which would collapse `interest` to 0 — this should be confirmed in the PoC.

### Recommendation
In `requestWithdraw`, when `isClosed` is true either (a) mint/record only `principal` (set `_amount = principal`, i.e., do not add projected interest for receipts that can never be funded by a future epoch), or (b) revert/branch to a separate "closed pool redeem" path that pays only principal at par. Equivalently, the CDO should skip adding `_calcInterestWithdrawRequest` interest when `creditVault`'s `epochEndDate == 0`. Additionally, `_claimFundedWithdrawRequest` should cap a closed-pool claim at the actually-funded basis.

```solidity
// Foundry fork PoC sketch (place in test/foundry/IdleCreditVault.t.sol style harness)
function testClosedPoolRequestWithdrawUnfundedInterest() external {
    // setup: deposit, run epochs, then close the pool via manager stopEpoch
    // with the "repay all" sentinel so epochEndDate becomes 0.
    uint256 amount = 100_000 * ONE_SCALE;
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, amount, true);
    address victim = makeAddr("victim");
    _depositWithUser(victim, amount, true); // victim leaves a pending funded claim

    // victim requests withdraw before close (funded via pendingWithdraws at stop)
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // close pool: borrower repays everything; epochEndDate == 0 afterwards
    _closePool(); // stopEpoch(_interest = 1) path per harness helpers

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    assertEq(cdoEpoch.epochEndDate(), 0);

    // attacker requests withdraw on closed pool
    uint256 stratBalPre = IERC20Detailed(defaultUnderlying).balanceOf(address(vault));
    vm.startPrank(attacker);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    // requested includes projected interest: principal was the only thing burned
    cdoEpoch.claimWithdrawRequest(); // immediate: epochEndDate == 0 bypasses wait
    vm.stopPrank();

    // attacker was paid 'requested' which includes interest that was never funded:
    // vault underlying decreased by more than the principal that backed the receipt.
    assertGt(requested, /* principal only */, "receipt included unfunded interest");
    // victim's funded claim now reverts or is underpaid (insolvency):
    vm.prank(victim);
    vm.expectRevert(); // NotAllowed / transfer failure due to drained balance
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `vault.pendingWithdraws()` does not increase for the closed-pool request (IdleCreditVault.sol lines 277–280), while `vault.withdrawsRequests(attacker)` does increase by the interest-inclusive `_amount`, and `_transferFundedClaim` pays it from the shared underlying pool.

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
