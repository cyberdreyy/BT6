### Title
Legacy gateway callback registration allows request-ID collision to hijack or drop another user's in-flight response - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The legacy user-message path of the WebAPI gateway `handler` registers a pending callback keyed only by the caller-supplied `MessageId`, with no check for an existing in-flight entry with that ID, unlike the newer JSON-RPC v2 trigger path which explicitly rejects duplicate/in-flight request IDs. This lets an unprivileged client silently overwrite another in-flight request's callback registration, causing the original requester's response to be dropped and the DON's eventual response to be delivered to the attacker's callback instead — a cross-user response confusion analogous to the RandomDraw `redraw()` bug where swapping a pending request's ID silently discards/redirects the outcome tied to the old ID.

### Finding Description
`HandleLegacyUserMessage` unconditionally stores the caller's callback in a shared map keyed by `msg.Body.MessageId`, without verifying uniqueness/in-flight status first: [1](#0-0) 

The completion path, `handleWebAPITriggerMessage`, looks up and deletes whatever callback currently sits at that `MessageId` and delivers the (first) node response to it: [2](#0-1) 

This is the exact same root-cause shape as the RandomDraw bug: a mutable "current pending request" slot keyed by an ID that the requester controls, with no protection against a second request overwriting that slot while the first is still outstanding. In RandomDraw, `redraw()` swapped `request.currentChainlinkRequestId`, discarding the prior VRF request and letting the host choose which random response becomes canonical. Here, a second `HandleLegacyUserMessage` call with the same `MessageId` overwrites `savedCallbacks[msg.Body.MessageId]`, discarding the first caller's callback registration and repointing that ID's eventual DON response to the second (attacker) caller.

By contrast, the newer v2 HTTP trigger path was hardened against exactly this class of bug — `setupCallback` explicitly checks for and rejects in-flight/duplicate request IDs: [3](#0-2) 

and this is exercised by tests confirming the duplicate case is rejected: [4](#0-3) 

No equivalent guard exists in the legacy `handler.go` path.

`MessageId` on the legacy path originates from the caller-supplied JSON-RPC request ID (`jsonRequest.ID` / message body), which the gateway forwards essentially as-is into `HandleLegacyUserMessage` before any DON-side authorization of message content occurs: [5](#0-4) 

The only constraint enforced at the gateway boundary is a length cap, not uniqueness against other callers' in-flight IDs: [6](#0-5) 

### Impact Explanation
An unprivileged client that knows or guesses (or races) another client's in-flight `MessageId` can:
- Cause the victim's `HandleLegacyUserMessage` call to silently receive no response (its callback entry is deleted/overwritten and no error is surfaced to the original caller), effectively a denial of service against that specific request.
- Redirect the DON node's real response for that workflow execution to the attacker's own callback instead of the legitimate requester's, resulting in cross-user response confusion — the attacker observes execution results/data intended for another tenant.

This is a request/response-integrity violation of the internet-facing gateway similar in class to the confirmed High-severity RandomDraw finding: an ID-keyed "current" state that any caller can overwrite mid-flight, breaking the assumption that a dispatched request's eventual response is delivered only to its original requester.

### Likelihood Explanation
Exploitability requires only that the attacker submit a legacy gateway request (`HandleLegacyUserMessage`) with a `MessageId` matching a currently in-flight one from another caller. Because IDs are client-supplied and there is no per-tenant namespacing or uniqueness check on this path (as there explicitly is on the v2 path), collision can be achieved either by guessing predictable/short IDs or, more reliably, by an attacker deliberately re-using an ID they observed (e.g., replaying/echoing IDs seen in shared logs, or coordinating with another low-privilege identity). No special role or node compromise is needed — this is reachable purely from the gateway's public/unprivileged request-handling entrypoint.

### Recommendation
In `core/services/gateway/handlers/capabilities/handler.go`, before inserting into `savedCallbacks`, check whether an entry for `msg.Body.MessageId` already exists and is still in-flight; if so, reject the new request with a client error (mirroring `setupCallback`'s "in-flight request ID" rejection in `http_trigger_handler.go`) instead of silently overwriting it. Additionally, consider namespacing `savedCallbacks` keys by requester/session identity (not just the raw client-supplied ID) so that even non-colliding IDs from different callers cannot interact.

### Proof of Concept
1. Client A sends a legacy WebAPI trigger request with `MessageId = "X"`; `HandleLegacyUserMessage` stores A's callback at `savedCallbacks["X"]` and forwards the request to all DON members.
2. Before the DON responds, Client B (unprivileged, unrelated) sends its own legacy request reusing `MessageId = "X"`. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with B's callback — no uniqueness check exists on this path [1](#0-0) .
3. When a DON node responds for `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds B's callback, deletes the entry, and delivers the response to B [2](#0-1) .
4. Client A's original HTTP request hangs/times out with no response ever delivered, while Client B receives a response tied to Client A's originally dispatched request.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
