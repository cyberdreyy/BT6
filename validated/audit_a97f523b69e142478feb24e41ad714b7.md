### Title
Signer's node-validation trust bypasses header version/epoch consistency checks in `postblock_proposal.rs::validate()`

### Summary
The proposal-validation endpoint (`NakamotoBlockProposal::validate` in `stackslib/src/net/api/postblock_proposal.rs`) deliberately overwrites the freshly-mined block's `header.version` with the attacker-supplied proposal's version byte before comparing hashes, and never calls the epoch/version consistency checks (`NakamotoBlock::validate_header_static` / `validate_transactions_static` / `validate_problematic_txs`) that exist elsewhere in the codebase specifically to reject a version that does not match the tenure's epoch. A signer that trusts `BlockValidateOk` unconditionally for this rule can therefore be induced to sign a header whose version is wrong for its epoch.

### Finding Description
`NakamotoBlockProposal::validate` builds the block honestly via `builder.mine_nakamoto_block(...)` (which sets `header.version` to the node's own epoch-correct value, e.g. via `NakamotoBlockHeader::from_parent_empty`), then explicitly overrides it: [1](#0-0) 

The comparison that follows only checks that `computed_block_header_hash == expected_block_header_hash` — both computed from headers that now share the *same*, attacker-chosen, `version` byte: [2](#0-1) 

Nowhere in `validate()` is `NakamotoBlock::validate_header_static`, `validate_transactions_static`, or `validate_problematic_txs` invoked (confirmed by grep: zero matches in `postblock_proposal.rs`), even though these are exactly the functions the codebase uses elsewhere to enforce that `header.version & 0x7f == NakamotoBlockHeader::expected_version_for_epoch(epoch_id)`: [3](#0-2) [4](#0-3) 

Because `version` gates whether `problematic_txs` participates in the signature/block-hash preimage (`version_includes_problematic_txs`), a version mismatched to the tenure's real epoch changes what is actually signed vs. what the epoch's canonical rule requires: [5](#0-4) 

On the signer side, the only pre-signature checks performed are `check_static_valid_block` (integer-bound sanity only), the problematic-txs-not-empty check, and the v1/v2 sortition/global-state proposal checks — none of which re-verify `header.version` against the epoch: [6](#0-5) [7](#0-6) 

The equality the signer implicitly relies on — "node's `Ok` encodes every rule the signer would otherwise need to check, including version/epoch consistency" — is broken: `BlockValidateOk` is returned for a version/epoch-mismatched header, and the signer's own logic never independently re-derives that rule before pre-committing/signing (`handle_block_validate_response` moves straight to `mark_pre_committed` / `send_block_pre_commit` on `Ok`, only re-checking tenure/db-state conflicts, not header version): [8](#0-7) 

### Impact Explanation
This is a "rejection recounted as acceptance" at the node-validation boundary the signer relies on: a block that the chain's own static rules (`validate_header_static`/`validate_problematic_txs`) would reject for its epoch instead returns `BlockValidateOk`, letting an honest signer pre-commit and sign it. If enough independently-fooled single-slot proposals accumulate threshold signatures, the block is pushed with a signature over a header whose commitment (via the version-gated `problematic_txs` field) does not match the epoch's actual signing/hashing rule — a chain-safety break in the Critical category ("a signer signing an invalid, non-canonical block" / "signature valid across chain/epoch boundaries"). This is repeatable at any Epoch-4.0 boundary tenure and costs the attacker only one miner slot plus gossip of the crafted `BlockProposal`.

### Likelihood Explanation
Requires an attacker who wins a single miner slot (as stipulated) at (or near) an epoch boundary where `NakamotoBlockHeader::expected_version_for_epoch` changes value, and crafts a `BlockProposal` with a version byte belonging to the other epoch. No majority-signer collusion, no auth token, and no local access is required — the flaw is purely in the RPC validate path signers already call. Feasibility is high given the version override and hash-comparison logic is unconditional and always executed on every proposal.

### Recommendation
Add an explicit epoch/version consistency check inside `NakamotoBlockProposal::validate` (or immediately before it), calling `self.block.validate_header_static(epoch_id)` / `validate_transactions_static` / `validate_problematic_txs` against the block's actual tenure epoch, and reject with `ValidateRejectCode::InvalidBlock` before ever computing/comparing hashes with the overridden version. Additionally, harden the signer side (`check_block_against_state` or `check_block_against_signer_db_state`) to independently verify `header.version` against the tenure's epoch rather than trusting `BlockValidateOk` unconditionally for this rule.

impl NakamotoBlockHeader {
    /// Whether a header at the given `version` includes the `problematic_txs`
    /// field in its serialization and signature/block-hash preimages.
    ///
    /// This is the single source of truth shared by `consensus_serialize`,
    /// `consensus_deserialize`, and both signature-hash calculations, so the
    /// field's presence can never diverge between them. The field was added in
    /// Epoch 4.0; version-0 headers omit it entirely.
    pub fn version_includes_problematic_txs(version: u8) -> bool {
        // The high bit (0x80) of `version` is the shadow-block flag; the header
        // version number is the low 7 bits. Mask it off before comparing so a
        // pre-4.0 shadow block (version 0x80) isn't mistaken for a v1 header.
        (version & 0x7f) >= NAKAMOTO_BLOCK_VERSION_EPOCH_4
    }

    /// The Nakamoto block header version required for blocks in `epoch_id`.
    ///
    /// The header format (and therefore the version number, ignoring the
    /// shadow-block high bit) is fixed per epoch: Epoch 4.0+ uses
    /// [`NAKAMOTO_BLOCK_VERSION_EPOCH_4`]; earlier Nakamoto epochs use
    /// [`NAKAMOTO_BLOCK_VERSION`]. Used to reject blocks whose version does not
    /// match their epoch.
    pub fn expected_version_for_epoch(epoch_id: StacksEpochId) -> u8 {
        if epoch_id >= StacksEpochId::Epoch40 {
            NAKAMOTO_BLOCK_VERSION_EPOCH_4
        } else {
            NAKAMOTO_BLOCK_VERSION
        }
    }

    /// Static sanity checks on the block header that depend only on the epoch.
    /// Verifies:
    /// * the header version matches the epoch. The header version is fixed per
    ///   epoch and is what gates the `problematic_txs` field in the block hash,
    ///   so a block whose version doesn't match its epoch (ignoring the
    ///   shadow-block high bit) is rejected.
    pub fn validate_header_static(&self, epoch_id: StacksEpochId) -> bool {
        let expected_version = NakamotoBlockHeader::expected_version_for_epoch(epoch_id);
        if self.header.version & 0x7f != expected_version {
            warn!("Block has invalid header version for epoch";
                "consensus_hash" => %self.header.consensus_hash,
                "stacks_block_hash" => %self.header.block_hash(),
                "stacks_block_id" => %self.header.block_id(),
                "epoch_id" => %epoch_id,
                "version" => self.header.version,
                "expected_version" => expected_version
            );
            return false;
        }
        true
    }
