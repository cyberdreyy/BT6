## Title
Signer weight double-counted across `total_weight_approved` and `total_weight_rejected` when a signer changes its vote for a block - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The mining node's `StackerDBListener` tallies per-block signer weight into two separate buckets, `total_weight_approved` and `total_weight_rejected`, which `SignerCoordinator::get_block_status` uses to decide whether a block has crossed the 70% approval threshold or the >30% blocking-rejection threshold. The two buckets are gated by two *different* de-duplication sets (`gathered_signatures` for approvals, `responded_signers` shared/reused for rejections), so a signer that first rejects a block and later reconsiders and accepts the same block (the documented, supported "reconsider a rejected block" flow) has its weight counted into *both* buckets simultaneously, inflating the sum beyond `total_weight`.

### Finding Description
`BlockStatus` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82`) tracks `responded_signers: HashSet<u32>`, `gathered_signatures: BTreeMap<u32, MessageSignature>`, `total_weight_approved`, and `total_weight_rejected`.

On an `Accepted` message the code inserts into `responded_signers` unconditionally and gates the weight addition on `gathered_signatures`: [1](#0-0) 

On a `Rejected` message the code gates the weight addition on inserting into the *same* `responded_signers` set: [2](#0-1) 

Because `responded_signers` is shared between the two paths but the Accepted path's actual weight-add guard is `gathered_signatures` (a different set), the two guards are not mutually consistent:

- If a signer **rejects first**, `responded_signers.insert(slot_id)` succeeds and `total_weight_rejected += weight`.
- If that same signer **later accepts** the same `block_sighash` (signer.rs's own comment confirms a signer can revise a rejected block's vote to an acceptance once "the reject reason allows us to reconsider" and it validates the block), the Accepted branch checks `gathered_signatures.contains_key(&slot_id)`, which is still empty for this signer, so `total_weight_approved += weight` executes — even though `responded_signers` already contains this slot from the earlier rejection.

The result: this signer's weight is now counted in **both** `total_weight_approved` and `total_weight_rejected` for the same block, so `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, breaking the invariant that a signer's weight should count toward exactly one side of the aggregated-weight vs. total-weight equality.

### Impact Explanation
`SignerCoordinator::get_block_status` evaluates the reject condition before the accept condition: [3](#0-2) 

Because the stale rejection weight from a signer who has since reconsidered and accepted is never removed from `total_weight_rejected`, that stale weight can push `total_weight_rejected.saturating_add(weight_threshold) > total_weight` even when a legitimate super-majority has actually accepted the block. This causes the miner to declare the block rejected (`NakamotoNodeError::SignersRejected`), permanently or temporarily excluding transactions based on an inflated, stale rejection tally, and abandoning a block that in reality has enough approving weight. This is a liveness wedge on the block-production path: a fully valid, sufficiently-signed block can be discarded by the miner due to a single signer's vote-revision being double-counted rather than moved from one bucket to the other. It does not require a majority of signers to trigger — one signer flip-flopping (reject → accept) on a single proposal is sufficient to corrupt the coordinator's shared tally that every other signer's weight is being compared against.

### Likelihood Explanation
The reject → accept revision path is an intentional, documented signer behavior (per the code comment in `signer.rs`, signers may reconsider and later accept a previously rejected proposal for the same `signer_signature_hash` if the reject reason permits it and the block re-validates), so this is reachable in ordinary operation without any malicious majority — a single normal (or slightly delayed/out-of-order) signer response sequence is enough. The bug is a straightforward accounting gap (two different guard sets for what should be one mutually-exclusive vote-state machine) rather than a crafted attack requiring collusion, making the likelihood of accidental triggering non-trivial in real deployments with signer restarts, reconnects, or reconsideration flows.

### Recommendation
Use a single per-slot vote-state map (e.g., `HashMap<u32, VoteKind>` where `VoteKind` is `Accepted` or `Rejected`) instead of the separate `responded_signers` set and `gathered_signatures` map as independent weight-add guards. When a signer's vote flips from Rejected to Accepted (or vice versa), the existing weight must be subtracted from the old bucket before adding it to the new one, so `total_weight_approved + total_weight_rejected` never exceeds `total_weight` and a signer's current, most-recent decision is what is tallied.

### Proof of Concept
1. Miner proposes block B; `StackerDBListener` computes `total_weight` and `weight_threshold` (70%) from the reward set for the current cycle: [4](#0-3) 
2. Signer S (weight w) initially rejects B (e.g. transient validation hiccup); `handle` inserts S's slot into `responded_signers` and adds `w` to `total_weight_rejected`: [2](#0-1) 
3. Enough other signers accept B such that `total_weight_approved` alone (excluding S) is just under the 70% threshold, while the accumulated rejections (including S's `w`) are just under the 30% blocking threshold too.
4. S subsequently reconsiders (its earlier reject reason allowed reconsideration) and validates/accepts B, sending `BlockResponse::Accepted` for the *same* `signer_signature_hash`. The Accepted handler checks only `gathered_signatures`, which does not contain S's slot, so it adds `w` again: [1](#0-0) 
5. Now `total_weight_approved + total_weight_rejected > total_weight` (S's weight counted twice). Depending on ordering of events, `get_block_status`'s reject check (which runs before the accept check) can trip using the stale, double-counted rejection weight even though the "true" current votes would have crossed the acceptance threshold, causing the miner to treat a legitimately-approved block as rejected: [5](#0-4) 

Note: I was unable to fully trace, within the available index, the exact conditions in `stacks-signer/src/v0/signer.rs` under which a signer transitions from `mark_locally_rejected` back to sending an `Accepted` response for the identical `signer_signature_hash` (the grep only located references without full surrounding logic/line ranges retrievable before the tool budget ended); if a Devin session investigation shows that no such reject→accept transition is possible for an identical block hash in the current codebase, this specific double-count path would not be reachable and the finding should be downgraded accordingly.
