### Title
Stale instant-withdraw per-epoch counters dilute default recovery and permanently strand reserve — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`requestInstantWithdraw` increments three counters per request: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (the "refcount"). The funded claim path `claimInstantWithdrawRequest` only clears `instantWithdrawsRequests[_user]` — it never decrements the two per-epoch counters. Those stale entries are later read by `defaultPendingClaimBasis` (which adds `instantWithdrawClaimsByEpoch[epochNumber]` into the recovery basis) and by `_claimDefaultedInstantWithdrawRequest`, exactly like the missing `of_node_put()` in the reference bug: a resource is acquired on request but never released on the successful claim path. ### Finding Description
In `claimInstantWithdrawRequest` (lines 387–392) the user's aggregate counter is zeroed and funded underlyings are paid out, but `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` keep their values. `pendingInstantWithdraws` is decremented separately in `collectInstantWithdrawFunds` (line 401), so after a fully funded and claimed instant withdrawal the per-epoch "refcount" leaks.

The leak becomes exploitable if, **within the same epoch** (`epochNumber` only advances on `deposit`/epoch transitions, lines 607–610), a second user opens an *unfunded* instant request and the borrower then defaults:

1. `defaultPendingClaimBasis` returns `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644–649). The already-claimed amount is counted again, inflating `totalBasis` in `finalizeDefaultRecovery` (lines 679–688).
2. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore depressed below its fair value. The haircut is applied both to pending receipt claims *and* to active tranche NAV via `activeFinalNAV = activeBasis * recoveryPrice / RECOVERY_FULL` and the CDO's `_burn`/`_forceUpdateAccounting` (lines 699–705), so all LPs and genuine pending claimants recover less.
3. The reserve share attributed to the stale basis can never be claimed: `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and then does `instantWithdrawsRequests[_user] -= claimBasis` (lines 844–855), which underflows for the already-claimed user, so the excess reserve is permanently stranded in the strategy (owner `transferToken` is the only escape, and the rules exclude relying on owner rescue). ### Impact Explanation
Every defaulted or post-default claimant and all active AA/BB tranche holders receive a strictly smaller recovery than entitled, proportional to `staleAmount / totalBasis`. Example: stale claimed instant amount 100, genuine pending instant 50, active basis 850 → `totalBasis` is computed as 1000 instead of 900, so `recoveryPrice` is ~10% lower than fair; a 900-unit reserve pays out only 900·(900/1000) and the rest is locked forever. This is a direct, quantifiable wealth transfer from honest claimants to nobody (stranded funds / permanent freezing of unclaimed recovery), satisfying the impact bar without any privileged-role abuse — the attacker is only a KYC-passed instant-withdraw requester.

### Likelihood Explanation
Requirements: (a) an instant request is funded and claimed, (b) another instant request remains pending in the *same* epochNumber, (c) the borrower defaults before the epoch rolls over. Defaults are an explicit supported state machine path (`finalizeDefaultRecovery`, `defaulted`), and instant requests within one epoch are routine. The preconditions are narrow but entirely reachable by unprivileged users sequencing around honest borrower/manager calls; no owner, guardian, or queue misbehavior is needed.

### Recommendation
In `claimInstantWithdrawRequest`, mirror the funded decrement on the per-epoch counters:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
uint256 cur = epochNumber;
instantWithdrawsRequestsByEpoch[_user][cur] -= amount;   // release per-user ref
instantWithdrawClaimsByEpoch[cur] -= amount;             // release epoch ref
_transferFundedClaim(_user, amount);
```

Alternatively, recompute `defaultPendingClaimBasis` from `pendingInstantWithdraws` (the unfunded remainder) instead of the gross per-epoch claim total, so stale claims cannot inflate the basis.

### Proof of Concept
Foundry fork scenario (schematic):

```solidity
// Epoch N running; FASA = attacker KYC'd, BOB = victim KYC'd
cdoEpoch.requestInstantWithdraw(100e18, AATranche);      // FASA, via CDO
// borrower/CDO funds it -> collectInstantWithdrawFunds(100e18): pendingInstantWithdraws = 0
cdoEpoch.claimInstantWithdrawRequest();                  // FASA paid 100e18; per-epoch counters still 100e18

// same epochNumber: BOB requests instant withdraw, left unfunded
cdoEpoch.requestInstantWithdraw(50e18, AATranche);       // pendingInstantWithdraws = 50e18

// borrower defaults (stopEpoch pull fails) -> finalizeDefaultRecovery(recovered, source)
// basis = pendingWithdraws + instantWithdrawClaimsByEpoch[N]  // includes FASA's stale 100e18
assertGt(strategy.defaultPendingClaimBasis(), 50e18 + pendingWithdraws);
uint256 price = strategy.defaultRecoveryPrice();          // depressed vs fair

// BOB claims
cdoEpoch.claimInstantWithdrawRequest();                  // gets 50e18 * price, less than fair share
// FASA's stale 100e18 * price share of the reserve is unclaimable:
// _claimDefaultedInstantWithdrawRequest(FASA) reverts on underflow at line 848
// reserve remainder is stranded in IdleCreditVault permanently
```

Assertions: `defaultRecoveryPrice < fairPrice`, `underlyingToken.balanceOf(strategy)` retains the stale-attributed reserve after all legitimate claims, and active tranche `virtualPrice` is lower than under correct accounting.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
