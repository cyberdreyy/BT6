## Finding

### Title
Signer weight double-counted across accept and reject tallies when a signer transitions from Rejected to Accepted for the same block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies each signer's `BlockResponse` into either `total_weight_approved` or `total_weight_rejected`, and the miner's `SignCoordinator::get_block_status` uses these two aggregates as mutually-exclusive counters to decide, respectively, whether a block has reached the 70% signing threshold or is dead due to a >30% blocking minority. The guard that prevents double-counting is asymmetric: the `Accepted` handler only checks `gathered_signatures` (its own map) before adding weight, never checking whether that signer's weight was already counted in `total_weight_rejected`. A signer that legitimately (or maliciously) sends a `Rejected` response first and later an `Accepted` response for the same `signer_signature_hash` gets its weight added to *both* aggregates, breaking the "aggregated-weight vs verified-accepts" equality the coordinator relies on.

### Finding Description
In the `Accepted` arm: [1](#0-0) 

weight is only withheld from being re-added if `block.gathered_signatures.contains_key(&slot_id)` — i.e. if this exact signer already sent an `Accepted` before. It does **not** check `block.responded_signers`, which is the set meant to record "this signer has already spoken for this block" and is shared between the accept and reject code paths.

In the `Rejected` arm: [2](#0-1) 

weight is only added `if block.responded_signers.insert(slot_id)` returns `true`, i.e. only the first response from that signer (accept or reject) is counted here.

Combining the two: if signer `S` sends `Rejected` first (adds `S`'s weight to `total_weight_rejected`, inserts `S` into `responded_signers`), and later sends `Accepted` for the same block hash, the `Accepted` branch's guard (`gathered_signatures.contains_key`) is still `false` for `S` (this is `S`'s first `Accepted`), so `S`'s weight is *also* added to `total_weight_approved`. `S`'s weight is now counted in both aggregates simultaneously, even though a signer can only have one true, current verdict on a block.

This reject-then-accept transition is an explicitly supported, documented state path — `BlockInfo` in `stacks-signer` allows a `LocallyRejected` block to later be re-evaluated to `LocallyAccepted` as chain state changes: [3](#0-2) 

So a single, honestly-behaving signer whose earlier rejection reason becomes stale (e.g. a conflicting block it previously rejected against goes stale, letting it sign later) is enough to trigger the miscount — no majority or malicious collusion is required, only the ordinary behavior of one signer's own key/slot.

The consumer of this state, `SignCoordinator::get_block_status`, evaluates the reject condition **before** the approve condition: [4](#0-3) 

Because `total_weight_rejected` is never decremented when a signer flips to `Accepted`, the stale rejection weight persists and can push `total_weight_rejected + weight_threshold > total_weight` (the >30% blocking-minority condition) even after enough signers have validly reached the 70% approval threshold, or can otherwise present an aggregated tally that no longer corresponds to the set of signers' current, verified votes.

### Impact Explanation
This breaks the equality between the coordinator's aggregated weight counters and the actual set of verified accepts/rejects for a block — the exact class of bug flagged in scope ("aggregated-weight vs verified-accepts"). The concrete consequence is a liveness wedge: a block that has genuinely reached the real signing threshold can be miscounted as rejected (since the reject check runs first and stale reject weight from a since-flipped signer remains), causing the miner to abandon a validly-signable block and resubmit/stall, and generally corrupting the reject/accept bookkeeping the miner uses to make consensus-relevant decisions about the tenure.

### Likelihood Explanation
Triggerable by a single signer using only its own registered key/slot — no majority, no other signer's key, and no privileged access is needed. The reject-then-accept sequence is a normal, documented protocol path (`LocallyRejected --> LocallyAccepted: re-evaluated`), so this can occur even without malicious intent whenever validation timing or reorg staleness causes a signer to change its verdict, and can be deliberately provoked by a single misbehaving signer sending a `Rejected` followed by an `Accepted` for the same block.

### Recommendation
In the `Accepted` handler, check `block.responded_signers.contains(&slot_id)` (not just `gathered_signatures`) before adding to `total_weight_approved`, and if the signer had previously been counted in `total_weight_rejected`, subtract that weight from `total_weight_rejected` when moving them to the approved bucket (or otherwise ensure the two aggregates remain mutually exclusive per signer, e.g. by tracking a single per-signer verdict rather than two independently-guarded counters).

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListenerComms::insert_block` creates a fresh `BlockStatus` for `B`'s `signer_signature_hash`.
2. Signer `S` (holding only its own key) sends `BlockResponse::Rejected` for `B`. The listener adds `S`'s weight to `total_weight_rejected` and inserts `S`'s `slot_id` into `responded_signers`.
3. Circumstances change (e.g., the conflicting block `S` rejected against becomes stale, per the documented re-evaluation path), and `S` legitimately re-evaluates and sends `BlockResponse::Accepted` for the same `B`.
4. The `Accepted` handler checks only `gathered_signatures.contains_key(&slot_id)`, which is `false` (first acceptance from `S`), so it adds `S`'s weight to `total_weight_approved` as well — `S`'s weight is now double-counted across `total_weight_rejected` and `total_weight_approved`.
5. In `SignCoordinator::get_block_status`, the reject check `total_weight_rejected.saturating_add(weight_threshold) > total_weight` is evaluated before the approve check; with enough such flips, this stale rejection weight can push the block into `NakamotoNodeError::SignersRejected` even though the same signers' current, valid votes would otherwise clear the 70% approval threshold.
