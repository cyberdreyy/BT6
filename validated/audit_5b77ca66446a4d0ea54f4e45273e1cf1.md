### Title
ProgrammableBorrower assumes vault share value is withdrawable — an ERC4626 vault user can drain liquidity and permanently block `stopEpoch`, freezing all lender funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In the Chyrp Lite bug, a user-controlled "path" is dereferenced without validating that the underlying location is actually usable, turning a trusted pointer into arbitrary access. The analog here is `ProgrammableBorrower.onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:231-253): when `IdleCDOEpochVariant.stopEpoch` requests liquidity, the contract decides feasibility using `vault.convertToAssets(shares)` — the *valuation* path — instead of `vault.maxWithdraw(address(this))` — the actual withdrawable-liquidity path. If the ERC4626 vault (e.g. MetaMorpho) has its cash borrowed or withdrawn, `vault.withdraw` reverts and the whole `stopEpoch` call reverts with `StopEpochVaultLiquidityUnavailable`. Any unprivileged user of that shared external vault can put it in this state.

### Finding Description
`onStopEpoch` computes:

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;   // value check only
  try vault.withdraw(shortfall, address(this), address(this)) ... 
  catch { revert StopEpochVaultLiquidityUnavailable(); }
}
```

`_currentVaultAssets()` (line 546-549) is `convertToAssets(shares)` — a price oracle view, not a liquidity view. For MetaMorpho/ERC4626 vaults, `convertToAssets` values the shares, while `maxWithdraw` accounts for actually-available underlying. The code treats "the shares are worth enough" as "the withdrawal will succeed." Because this hook is called inside `IdleCDOEpochVariant.stopEpoch`, the revert propagates and the epoch cannot be stopped. There is no fallback path that works: `emergencyExitVault` calls `vault.redeem`, which fails identically when the vault has no cash; `rescueTokens` cannot pull vault shares' underlying; `setVault` reverts while `vault.balanceOf(address(this)) != 0` (line 165).

An attacker who is merely a user of the external ERC4626 vault (an explicitly allowed unprivileged role — a Morpho borrower or supplier) supplies collateral, borrows the market's idle liquidity, and holds the position. Every manager `stopEpoch` attempt then reverts. Since `stopEpoch` is the only way to settle an epoch and release `epochPendingWithdraws`/withdraw requests, all lender withdrawals through `claimWithdrawRequest` are blocked for as long as the liquidity stays drained. The attacker's cost is only the borrow interest on the drained amount plus locked collateral; if their position stays healthy there is no forced unwind, so the freeze can be extended indefinitely.

### Impact Explanation
Temporary-to-indefinite freezing of the entire facility's TVL. While the vault is drained, `stopEpoch` always reverts, the epoch never settles, pending withdraw requests are never funded, and tranche holders cannot exit — even at a loss-adjusted price. The freeze is quantifiable: 100% of vault-held lender funds (the portion parked via `_depositToVault` in `onStartEpoch`) are inaccessible for the duration the attacker maintains the borrow. Funds are not directly stolen, which keeps this at freezing severity rather than theft.

### Likelihood Explanation
- Attacker requirements: none beyond being a user of the external ERC4626 vault — no role, KYC, or tranche holdings needed.
- Cost: collateralization + borrow APR on the drained liquidity on the underlying Morpho market. On a partially-utilized vault the amount needed is only the idle-liquidity portion.
- Persistence: the borrow can be topped up/rolled indefinitely; the honest borrower, manager, and owner have no recovery path because every exit (`onStopEpoch`, `emergencyExitVault`, `setVault`) goes through the same illiquid vault.
- Front-running angle: the attacker only needs to sandwich `stopEpoch` calls during the window when `shortfall > 0`, i.e., whenever the CDO needs to pull more than the PB's on-hand cash.

### Recommendation
Check withdrawability, not valuation, before attempting the withdrawal: compare `shortfall` against `vault.maxWithdraw(address(this))` and return `true` (letting the CDO's `transferFrom` fail into the default path) instead of relying on `convertToAssets`. Alternatively, catch the withdraw failure without reverting and return a status the CDO can use to trigger the default path, so an illiquid external vault converts to a managed default rather than an unbounded freeze.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup, which already runs against a live MetaMorpho USDC vault):

```solidity
function testStopEpochFrozenByDrainedVaultLiquidity() external {
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);            // PB deposits idle cash into MetaMorpho vault

    // Attacker: an unprivileged Morpho user borrows the vault's idle liquidity.
    // Supply collateral on the underlying Morpho market(s) the vault allocates to,
    // then borrow available loan token so the vault's withdrawable cash ~ 0.
    _drainMorphoVaultLiquidity(vaultAddress); // helper: whale collateral + borrow to max LTV

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Any withdraw request large enough that shortfall <= convertToAssets but
    // > maxWithdraw makes onStopEpoch revert.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Repeatable: every retry reverts while the borrow position is maintained.
    vm.warp(block.timestamp + 30 days);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // No recovery: emergencyExitVault redeem fails on the same illiquidity;
    // setVault reverts because vault.shareBalance != 0.
    vm.prank(borrowerManager);
    vm.expectRevert(); // vault redeem insufficient liquidity
    programmableBorrower.emergencyExitVault(0);
}
```

Key assertion: `vault.maxWithdraw(address(programmableBorrower)) < shortfall <= vault.convertToAssets(shares)`, which is exactly the gap the `shortfall > _currentVaultAssets()` guard at line 245 fails to cover.
