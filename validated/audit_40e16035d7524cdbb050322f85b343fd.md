### Title
Transient failure of the borrower pull in `_stopEpoch`/`getInstantWithdrawFunds` permanently latches `defaulted`, leaving no status to retry from and forcing a solvent pool into the default-recovery path - (contracts/IdleCDOEpochVariant.sol:501-505)

### Summary
`IdleCDOEpochVariant._stopEpoch` and `getInstantWithdrawFunds` wrap the borrower pull (`this.getFundsFromBorrower`, a `transferFrom` from the borrower / programmable-borrower ERC4626 vault) in `try/catch`. Any revert falls into `_handleBorrowerDefault`, which irreversibly sets `defaulted = true`, clears `isEpochRunning`, pauses the vault and disables all withdraw requests. This mirrors the GMX report: a single failed external interaction moves the vault into a terminal status with no way back, so the operation can never be retried even when the funds are actually available.

### Finding Description
In `_stopEpoch` (`contracts/IdleCDOEpochVariant.sol:408-505`), the entire stop flow is gated on one external pull:

```solidity
try this.getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws) {
  ...
  isEpochRunning = false;
  ...
} catch {
  _handleBorrowerDefault(_amountToPullFromBorrower + _pendingWithdraws);
}
```

`getFundsFromBorrower` (line 550) is a plain `transferFrom` from the borrower. The same pattern exists in `getInstantWithdrawFunds` (lines 566-573). `_handleBorrowerDefault` (lines 577-599) then latches:

```solidity
defaulted = true;
...
isEpochRunning = false;
allowAAWithdrawRequest = false;
allowBBWithdrawRequest = false;
```

Once `defaulted` is set there is no exit back to normal operation:

- `restoreOperations` reverts unconditionally on `defaulted` (line 622: `_checkNotAllowed(defaulted || priceAA == 0)`).
- `_beforeUnpause` reverts on `defaulted` (line 636), so even `unpause()` cannot reopen the vault.
- `isEpochRunning` is already `false`, so `stopEpoch` cannot be re-executed to retry the pull against a now-solvent borrower.
- The only remaining path is `finalizeDefault`/`finalizeDefaultRecovery`/`DefaultDistributor.claim`, which applies the aggregate recovery multiplier — i.e. a haircut — to all active and pending claims.

This is exactly the stuck-status bug class: the vault is left in "defaulted" even though the failure may be transient (insufficient ERC4626 liquidity in the programmable-borrower vault at that block, a momentarily insufficient allowance, or a borrower whose `onStopEpoch` recall returned true but whose vault lacked instant liquidity). Unlike the `onStopEpoch` hook — where reverts are deliberately allowed to bubble "so transient ERC4626 liquidity failures can be retried" (line 397 comment) — the pull itself is swallowed by the catch and converts a transient failure into a permanent default.

Attacker vector (unprivileged): an attacker who is a shareholder of the programmable borrower's ERC4626 vault (explicitly in scope) can drain or borrow vault liquidity just before the manager's `stopEpoch`, causing `getFundsFromBorrower` to revert. Even if the borrower is fully solvent and repays the next block, the pool is permanently branded `defaulted`: lenders can only exit through the recovery/haircut path, `restoreOperations` is a permanent revert, and any difference between real recoverable value and the recovery-price claims is unrecoverable by users.

### Impact Explanation
Permanent misclassification of a solvent pool as defaulted. Consequences:

- All withdraw requests are disabled and claims are forced through the default recovery distributor, applying a haircut that did not economically occur — a direct loss to AA/BB holders and pending receipt holders.
- If the borrower repays fully after the latch, the repaid funds still cannot re-enter normal epoch accounting; they can only trickle through `finalizeDefaultRecovery`, and any residual is locked or misdistributed.
- `unpause`/`restoreOperations`/`stopEpoch` all become permanently unusable, so the stuck status can never be corrected — the same "can't pause again, can't resume again" deadlock as the GMX report.

### Likelihood Explanation
Requires a programmable-borrower deployment and an attacker able to reduce the ERC4626 vault's withdrawable liquidity (or a borrower funded to exactly `_amountToPullFromBorrower` while an attacker adds pending instant/normal withdraw requests that inflate the pull amount). The trigger is a single unprivileged transaction sequenced around an honest manager call, which fits the threat model. Because the latch is permanent, a single transient failure has full impact.

### Recommendation
Do not convert pull failures into an irrevocable default inside the same transaction. Either:

- let `getFundsFromBorrower` reverts bubble like `onStopEpoch` reverts so `stopEpoch`/`getInstantWithdrawFunds` can simply be retried, or
- introduce a `DefaultPending`/two-step path: record the failed pull in a resumable state that a later successful pull (or explicit owner confirmation) can clear before `defaulted = true` is committed.

At minimum, allow `restoreOperations` or a dedicated `cancelDefault` to unlatch `defaulted` when the borrower subsequently funds the full liability, mirroring the report's recommendation to "allow emergencyResume to be called again".

### Proof of Concept
Foundry fork scenario (sketch — I was unable to fully trace `pendingInstantWithdraws` gating after `instantWithdrawDeadline` and `finalizeDefaultRecovery` internals within the available iterations, so the claim-amount bookkeeping should be verified):

```solidity

//    ProgrammableBorrower's underlying ERC4626 vault so available liquidity <
//    _amountToPullFromBorrower + _pendingWithdraws at stopEpoch time.
// 3. Borrower still returns true from onStopEpoch (recall queued) but
//    getFundsFromBorrower's transferFrom reverts on insufficient balance.
// 4. warp past epochEndDate; manager calls stopEpoch(newApr, interest).
//    -> catch branch runs: _handleBorrowerDefault sets defaulted = true.
// 5. Next block, borrower vault liquidity is restored; borrower is fully solvent.
// Assertions:
assertTrue(cdoEpoch.defaulted());
assertFalse(cdoEpoch.isEpochRunning());
assertTrue(cdoEpoch.paused());
vm.expectRevert(NotAllowed.selector); vm.prank(owner); cdoEpoch.restoreOperations();
vm.expectRevert(NotAllowed.selector); vm.prank(owner); cdoEpoch.unpause();

// through finalizeDefault / DefaultDistributor with a recovery haircut,
// despite zero real shortfall.
```
