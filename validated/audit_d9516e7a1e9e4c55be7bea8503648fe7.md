### Title
Rejection weight in the block-signature coordinator is never invalidated once the same signer later Accepts, letting a signer's weight count in both `total_weight_approved` and `total_weight_rejected` simultaneously - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The miner-side signature coordinator (`StackerDBListener`) tallies `BlockResponse::Accepted` and `BlockResponse::Rejected` messages from signers into `total_weight_approved` / `total_weight_rejected` on a per-slot basis. The `Rejected` path is only idempotency-gated by inserting into a set (`responded_signers`) shared with the `Accepted` path, but the `Accepted` path itself gates its own weight addition on a *different* set (`gathered_signatures`), not on `responded_signers`. As a result, a signer that first Rejects and later changes its mind and Accepts the same block has its weight added to `total_weight_rejected` (from the reject) and later also added to `total_weight_approved` (from the accept), with no mechanism ever removing/invalidating the earlier tally. This is the same bug class as the reported Weblate issue: an old credential/state (the rejection) is not revoked/invalidated when a newer, superseding state (the acceptance) is recorded.

### Finding Description
In `stackerdb_listener.rs`:

- On `Accepted`, weight is added to `block.total_weight_approved` only `if !block.gathered_signatures.contains_key(&slot_id)`, then `block.responded_signers.insert(slot_id)` is called unconditionally [1](#0-0) .
- On `Rejected`, weight is added to `block.total_weight_rejected` only `if block.responded_signers.insert(slot_id)` (i.e. only the first time this slot appears in `responded_signers`, regardless of source) [2](#0-1) .

Because the `Accepted` branch's guard (`gathered_signatures`) is independent from the `Rejected` branch's guard (`responded_signers`), the following sequence produces inconsistent, un-invalidated state:
1. Signer S sends `Rejected` for block B → `total_weight_rejected += w`, `responded_signers` now contains S's slot.
2. Signer S changes its mind and sends `Accepted` for block B → since `gathered_signatures` does not yet contain S's slot, the guard passes: `total_weight_approved += w`, and S's slot is added to both `gathered_signatures` and `responded_signers`.

S's weight `w` is now counted in *both* `total_weight_rejected` and `total_weight_approved` for the same block, and there is no code path that decrements `total_weight_rejected` when a signer's opinion flips to acceptance (nor vice versa). The earlier rejection tally is stale/"not invalidated" exactly as in the CVE's password-change/token-revocation analogy — a superseded response is never revoked from its own weight bucket.

### Impact Explanation
This is a miscounted-response bug in the node-side coordinator that decides when a block has been signed (`total_weight_approved >= self.weight_threshold` triggers `cvar.notify_all()` to proceed with block assembly) and, by extension, feeds the miner's view of rejection weight used to judge whether a proposal is dead. A permanently inflated, never-decremented `total_weight_rejected` for a proposal that in fact has enough live rejections replaced by acceptances can cause the miner to treat a block as effectively rejected/blocked when it is not, or vice versa skew its internal bookkeeping about how much rejection weight actually still stands against a proposal. It does not directly let an invalid signature be embedded in the block (the on-chain `verify_signer_signatures` check is separate and re-validates real signatures), so this stays a coordinator-side accounting/liveness issue rather than a block-validity break; I could not fully confirm within available context whether `total_weight_rejected` is consumed anywhere to abandon/short-circuit a proposal (I found no `is_globally_rejected`-style consumer in the coordinator besides the approve-threshold notify), so the concrete liveness consequence could not be fully traced end-to-end from the available code.

### Likelihood Explanation
Triggerable by a single non-majority signer simply sending a `Rejected` message for a block sighash it is tracking and then later sending an `Accepted` for the same sighash — both are normal, validly-signed signer messages requiring no majority collusion, key compromise, or auth-token access, matching the "one signer (plus gossip)" threat model.

### Recommendation
Gate both `Accepted` and `Rejected` weight additions on the same idempotency key, and when a signer's vote flips (reject→accept or accept→reject), atomically move their weight between buckets (or track a single latest-response-per-slot map and recompute totals from it) rather than accumulating into independent, never-decremented counters guarded by different sets (`gathered_signatures` vs `responded_signers`).

### Proof of Concept
1. Miner proposes block B to signer set including signer S (weight w).
2. S sends `BlockResponse::Rejected` for B → coordinator: `total_weight_rejected += w`; `responded_signers = {S}`.
3. S (validly, on its own initiative) sends `BlockResponse::Accepted` for B → guard `!gathered_signatures.contains_key(S)` is true → coordinator: `total_weight_approved += w`; `gathered_signatures = {S}`; `responded_signers` still contains S.
4. Now `total_weight_rejected` includes w (from step 2, never removed) and `total_weight_approved` also includes w (from step 3): S's weight is counted in both aggregate buckets simultaneously, with no way to invalidate the stale reject tally. [3](#0-2)
