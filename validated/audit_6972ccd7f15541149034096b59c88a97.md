### Title
Rejection weight recounted as acceptance weight for the same signer in the miner's StackerDB listener - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The miner-side `StackerDBListener` aggregates per-signer block-response weight into `total_weight_approved` and `total_weight_rejected` using two independently-guarded checks. The "accept" path only checks whether the slot has already recorded a *signature* (`gathered_signatures`), while the "reject" path checks a shared `responded_signers` set. Because the two paths do not consult the same guard, a signer who has already been counted as a rejecter can later send an `Accepted` message for the same block and be counted again — this time toward the approval tally — inflating `total_weight_approved` beyond what genuinely-approving distinct weight supports.

### Finding Description
`BlockStatus` tracks, per proposed block, `responded_signers: HashSet<u32>`, `gathered_signatures: BTreeMap<u32, MessageSignature>`, `total_weight_approved`, and `total_weight_rejected`. [1](#0-0) 

On `BlockResponse::Accepted`, weight is only added to `total_weight_approved` when the slot is not already present in `gathered_signatures`; the code then unconditionally inserts into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` only when `responded_signers.insert(slot_id)` returns `true` (i.e., the slot was not previously present in `responded_signers`): [3](#0-2) 

The asymmetry: the accept branch's uniqueness guard is `gathered_signatures.contains_key(slot_id)`, not `responded_signers.contains(slot_id)`. If a signer first sends a `Rejected` message for a block (which inserts the slot into `responded_signers` and adds its weight to `total_weight_rejected`, but never touches `gathered_signatures`), and subsequently sends an `Accepted` message for the *same* block, the accept branch sees `gathered_signatures` does not yet contain the slot and therefore adds the same signer's weight a second time to `total_weight_approved`. The reverse order (accept-then-reject) is correctly guarded because `responded_signers` is already populated by the accept branch, so the reject branch's check prevents double counting — but the accept branch has no equivalent protection.

This mirrors the reported bug class exactly: an operation's uniqueness/return-value ("has this signer already responded?") is checked against the wrong/incomplete state (`gathered_signatures` instead of the unified `responded_signers`), letting one actor's action be recorded in two mutually-exclusive tallies.

### Impact Explanation
This lets a single malicious/misbehaving signer have its rejection "recounted as an acceptance" for the same block, directly matching the stated Critical impact category ("a rejection recounted as an accept"). The miner (and, through `SignCoordinator`/threshold checks such as `total_weight_approved >= self.weight_threshold`), may conclude that ≥70% weight approved the block when the aggregated approval weight actually double counts one signer, meaning the true distinct-signer approving weight can be lower than the required threshold. This can let a colluding miner + one malicious signer manufacture an apparent quorum and push a block whose real signer support falls short of consensus rules, without requiring a majority of signers or any additional privileged access — only one misbehaving signer's own StackerDB slot and private key, which they already legitimately control.

### Likelihood Explanation
Reachable by any single signer in the reward set (no majority needed) by simply broadcasting a `Rejected` message for a block followed by an `Accepted` message for the same `signer_signature_hash` — both messages are ordinary, individually valid v0 signer messages that pass their respective signature checks, since the miner's listener never rejects a signer for issuing contradictory responses across message types. It only requires control of one signer's stackerdb slot/key, which is within the threat model for this analysis (a single misbehaving signer, not requiring a majority or another signer's key).

### Recommendation
Use a single unified per-slot verdict guard shared by both branches (e.g., only add weight — approved or rejected — the first time a slot appears in `responded_signers`, and treat any subsequent contradictory response from the same slot as a no-op/ignored duplicate rather than re-tallying weight into the opposite bucket). Concretely, change the accept branch's condition from `!block.gathered_signatures.contains_key(&slot_id)` to `!block.responded_signers.contains(&slot_id)` (mirroring the reject branch's `responded_signers.insert(...)` check), so a signer's weight can be counted at most once, in the bucket corresponding to its first response.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (weight `w`) is part of the reward set.
2. `S` broadcasts `BlockResponse::Rejected` for `B` over its own StackerDB slot. The listener's reject branch inserts `slot_id` into `responded_signers` (first time → `true`) and adds `w` to `total_weight_rejected`. [3](#0-2) 
3. `S` then broadcasts `BlockResponse::Accepted` for the same `B` (a validly-signed acceptance message, e.g. because the signer software subsequently produced an accept or because a malicious variant deliberately double-sends). The listener's accept branch checks `!block.gathered_signatures.contains_key(&slot_id)`, which is `true` (the reject path never touched `gathered_signatures`), so it adds `w` to `total_weight_approved` again. [4](#0-3) 
4. Result: `total_weight_approved` includes `w` from `S` even though `S` also counts toward `total_weight_rejected`; `total_weight_approved + total_weight_rejected` can exceed the honest total by `w`, letting the approval threshold (`total_weight_approved >= self.weight_threshold`) be reached with less genuine distinct approving weight than required. [5](#0-4)
