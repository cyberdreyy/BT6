### Title
Unbounded JSON decode of attacker-controlled `DOCKER_AUTH_CONFIG` enables resource-exhaustion DoS in shared runner process - (File: helpers/docker/auth/auth.go)

### Summary
`getUserConfiguration` feeds the job-controlled `DOCKER_AUTH_CONFIG` variable directly into `readConfigsFromReader`, which calls `configfile.ConfigFile.LoadFromReader` with no size limit, no `io.LimitReader`, and no depth/complexity cap applied before decoding. Because this path runs inside the shared `gitlab-runner` process (used to resolve registry auth for every Docker-executor job on that runner), an attacker-controlled job can submit an oversized/deeply nested JSON payload to consume disproportionate CPU/memory relative to other concurrently running jobs.

### Finding Description
`Resolver.AllConfigs` (`helpers/docker/auth/auth.go:128-186`) is called per job/per image pull to resolve Docker registry credentials, and the first resolver invoked is `getUserConfiguration(dockerAuthConfig)` at line 134, where `dockerAuthConfig` is the raw value of the job variable `DOCKER_AUTH_CONFIG` — fully controlled by the pipeline/job author. [1](#0-0) 

That function wraps the string in a `bytes.Buffer` and hands it straight to `readConfigsFromReader`: [2](#0-1) 

There is no `io.LimitReader`, no pre-check on string length, and no JSON depth/complexity guard anywhere in this call chain — confirmed by the absence of any `LimitReader`/size-cap usage in `helpers/docker/auth/auth.go`. The Docker CLI's `configfile.ConfigFile.LoadFromReader` (external dependency, `github.com/docker/cli/cli/config/configfile`) uses `encoding/json` decoding without an imposed size or depth ceiling of its own. This is invoked synchronously within the same OS process that manages all concurrently executing jobs for that runner instance (the multi-job worker process), not in an isolated per-job sandbox, since `AllConfigs`/`ConfigForImage` execute in the runner's Go code (see call sites in `executors/docker/internal/pull/manager.go` and `shells/abstract.go`), prior to/independent of container isolation.

### Impact Explanation
A pipeline author can set `DOCKER_AUTH_CONFIG` to a large or deeply nested JSON blob. Every image pull/auth resolution for that job triggers a full JSON decode of that payload in the shared runner process. Because `gitlab-runner` typically services multiple concurrent jobs (potentially from different projects/tenants) in one process with a bounded worker pool, CPU and memory spent decoding an attacker-supplied oversized payload competes with resources needed by other jobs' registry-auth resolution and other runner operations, degrading or delaying unrelated jobs — a violation of the invariant that one job must not disrupt others sharing the runner.

### Likelihood Explanation
Preconditions are minimal: any pipeline author who can set CI/CD variables (including via `.gitlab-ci.yml` or the job's own variables, standard unprivileged capability) can set `DOCKER_AUTH_CONFIG` and trigger this path merely by running a job on a Docker-executor runner. Actual severity depends on external constraints not present in this file — e.g., whether GitLab's backend enforces a maximum CI variable value size before it reaches the Runner. This repository's Runner-side code (`helpers/docker/auth/auth.go`) itself enforces no cap, so the mitigation, if any, lives entirely outside this code path.

### Recommendation
Enforce a hard size cap (e.g., wrap the reader with `io.LimitReader` set to a small maximum, such as a few KB — enough for realistic multi-registry auth configs) and/or a JSON decode depth limit before calling `config.LoadFromReader` in `readConfigsFromReader` (`helpers/docker/auth/auth.go:323`). Reject/­log-and-skip the `DOCKER_AUTH_CONFIG` source with a clear error when the limit is exceeded, mirroring the existing error-handling pattern already used for malformed configs in `AllConfigs`.

### Proof of Concept
```go
func TestReadConfigsFromReader_LargePayloadDoS(t *testing.T) {
    // Build a deeply nested / oversized JSON payload simulating a malicious
    // DOCKER_AUTH_CONFIG value.
    nested := buildDeeplyNestedJSON(500_000) // or a multi-hundred-MB flat string
    start := time.Now()
    var memBefore, memAfter runtime.MemStats
    runtime.ReadMemStats(&memBefore)

    _, err := readConfigsFromReader(bytes.NewBufferString(nested))

    runtime.ReadMemStats(&memAfter)
    elapsed := time.Since(start)

    // Assert a hard cap: decoding should fail fast (e.g., with a size-limit
    // error) rather than scale unbounded with input size/nesting.
    assert.Error(t, err, "expected size/depth limit to reject oversized DOCKER_AUTH_CONFIG")
    assert.Less(t, elapsed, 100*time.Millisecond)
    assert.Less(t, memAfter.TotalAlloc-memBefore.TotalAlloc, uint64(10*1024*1024))
}
```
Run this alongside a benchmark comparing decode time/memory at increasing input sizes (1KB, 1MB, 100MB) to demonstrate unbounded scaling with no cap currently enforced.

func getUserConfiguration(dockerAuthConfig string) (string, []types.AuthConfig, error) {
	authConfigs, err := readConfigsFromReader(bytes.NewBufferString(dockerAuthConfig))
	if err != nil {
		return configSourceNameUserVariable, nil, err
	}
	if authConfigs == nil {
		return "", nil, nil
	}

	return configSourceNameUserVariable, authConfigs, nil
}

func readConfigsFromReader(r io.Reader) ([]types.AuthConfig, error) {
	config := &configfile.ConfigFile{}
	if err := config.LoadFromReader(r); err != nil {
		return nil, err
	}
	if !config.ContainsAuth() {
		// we can bail out early when there is no auth configured at all
		return nil, nil
	}
