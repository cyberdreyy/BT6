### Title
Missing per-build secret binding on suspend/resume EnvironmentKey allows cross-job instance takeover - ([File: common/environment_key.go], [File: executors/internal/autoscaler/executor.go])

### Summary
`ParseEnvironmentKey`/`validateEnvKey` binds an acquisition/resume request only to `RunnerID` and `SystemID`, both fixed, non-secret values shared by every job on a given runner. The actual capability-bearing secret, the `acquisition-key` field, is generated internally by the taskscaler/fleeting layer and is not scoped to the requesting job/project by any check in `validateEnvKey` or `prepareResume`, so possession of the string (however obtained) is sufficient to resume someone else's suspended instance.

### Finding Description
`common.EnvironmentKey.String()` serializes `RunnerID/SystemID/fields` [1](#0-0) , and this exact string is written straight into the job trace log by `Build.suspendEnvironment` (`"Job environment suspended:", s`) [2](#0-1)  and again on resume (`"Job environment resumed:", envKey`) [3](#0-2) . `validateEnvKey` only checks `key.RunnerID != runnerID` and `key.SystemID != systemID` [4](#0-3) ; there is no check binding the key to the originating job ID, project ID, or any per-build token. Since `RunnerID`/`SystemID` are identical for every job scheduled on a shared runner, the only thing distinguishing one suspended instance from another is the `acquisition-key` field, which `prepareResume` passes straight to `scaler.Resume(ctx, acqKey)` [5](#0-4) . `Build.EnvironmentKey()` — the value actually consumed by `Prepare` — is populated verbatim from `Job.SuspendOptions.EnvironmentKey` [6](#0-5) , and that field is part of the JSON job payload GitLab's backend sends the runner [7](#0-6) .

However, this field is populated and consumed by GitLab's backend orchestration (the server decides which follow-up job receives which suspended key, based on its own authorization of who may resume a given environment); it is not an attacker-supplied CI/YAML field, job variable, or artifact/cache content that an unprivileged pipeline author directly controls. The only realistic way an unprivileged actor obtains a *foreign* job's key value is by reading it out of that other job's trace log. Whether that is a genuine cross-tenant exposure depends entirely on GitLab.com/GitLab EE server-side authorization of who can view a job's trace and whether/how it re-injects a suspended key into a follow-up job scoped to a different, unauthorized project — none of which is implemented in this repository (gitlab-runner only). The runner-side code faithfully treats whatever `environment_key` the server hands it as authoritative; it does not claim to defend against a value the server itself should not have disclosed or reassigned to the wrong job.

Within `gitlab-runner`'s own code there is no brute-force/guessing path either: `acqKey` is an opaque taskscaler-managed identifier, not derived from any client-observable identifier that `validateEnvKey` could permit guessing of, and there's no enumeration primitive exposed to a pipeline (no API in this codebase lets a job list or probe valid acquisition keys).

### Impact Explanation
If the acquisition-key string leaks (e.g., visible in trace logs to any principal who can read job logs but not to the job whose environment was suspended), `prepareResume` would let that principal's later job attach to the original job's suspended instance, filesystem, cache, and artifacts, because the code enforces no ownership/project/job binding beyond runner/system identity. That is a genuine gap in the runner's own defense-in-depth if server-side controls around trace visibility or key issuance to unauthorized jobs are ever insufficient — but that boundary is server-side, not in the reachable Go path of `gitlab-runner` as reviewed here.

### Likelihood Explanation
Low, as scoped to this repository. Exploiting it requires either (a) GitLab's backend to erroneously disclose or re-target a suspended-environment key to a job not authorized to resume it (a server-side trust decision outside `gitlab-runner`), or (b) the attacker already having log/trace access to the victim job, which is itself an access-control question resolved by GitLab.com/GitLab EE, not by this runner code. There is no reachable path within `gitlab-runner` alone (no attacker-controlled CI field, cache, artifact, or image feeds `Job.SuspendOptions.EnvironmentKey`) that lets an unprivileged job forge or guess another job's key without first being handed it by the server.

### Recommendation
Not applicable as a runner-only fix given the trust boundary sits with the server. If defense-in-depth is desired, `EnvironmentKey`/`validateEnvKey` could additionally bind to a per-job/per-project opaque token issued by GitLab and checked in `prepareResume`, and the key should be redacted from trace output (`Infoln` calls in `common/build.go:306` and `executors/internal/autoscaler/executor.go:120`) rather than printed in cleartext, since it functions as a bearer credential for instance resume.

### Proof of Concept
Not reproducible as a self-contained Go test within `gitlab-runner`, because the described exploit requires cross-job key issuance/disclosure controlled by GitLab's backend, not by any code path in this repository. A PoC job plan would need: two jobs in different (unauthorized) projects, backend-side reuse or leakage of the same `environment_key` across them, and an assertion that `prepareResume`'s `RunnerID`/`SystemID` check alone does not prevent job 2 from resuming job 1's acquisition — this is testable at the unit level (as already covered by `TestExecutor_Resume_ValidateEnvKeyRejections` [8](#0-7) , which confirms `validateEnvKey` accepts any key with matching runner/system ID regardless of who "owns" it), but it does not by itself demonstrate an attacker-reachable path since the key must first be attacker-obtained through a mechanism outside this codebase.
