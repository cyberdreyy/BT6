### Title
Unauthenticated MessageId collision in `HandleLegacyUserMessage` allows cross-user callback overwrite - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores the user's response callback keyed only by the attacker-controlled `msg.Body.MessageId`, with no per-sender namespacing and no check for an existing in-flight entry. Any unauthenticated gateway client who can guess or observe a victim's in-flight `MessageId` can submit a second `MethodWebAPITrigger` request with the same ID, silently overwriting `h.savedCallbacks[msg.Body.MessageId]` and hijacking or dropping the victim's eventual node response.

### Finding Description
The gateway's HTTP entrypoint `gateway.ProcessRequest` decodes an incoming JSON-RPC request, and for legacy requests calls `msg.Validate()` (core/services/gateway/gateway.go:253) followed by `h.HandleLegacyUserMessage(ctx, msg, callback)` (core/services/gateway/gateway.go:269). `msg.Body.MessageId` is fully attacker-supplied — it comes directly from the JSON-RPC request ID and is never derived from or bound to the sender's identity [1](#0-0) . `Message.Validate()` verifies the signature over `MessageId || Method || DonId || Receiver || Payload` and extracts `m.Body.Sender` from the signature, but it never checks that the `MessageId` is unique or that it "belongs" to that sender — any signer can pick any `MessageId` value [2](#0-1) .

In `handler.HandleLegacyUserMessage`, after validating the payload, the handler unconditionally does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

There is no `if _, exists := h.savedCallbacks[msg.Body.MessageId]; exists { ... }` guard, so a second (attacker) request bearing the same `MessageId` as a victim's still-in-flight request simply replaces the map entry, discarding the victim's callback reference. When a node eventually responds with that `MessageId`, `handleWebAPITriggerMessage` looks the ID up once and delivers the *first* future response to whichever callback is currently stored:
```go
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [4](#0-3) 

Because the callback is overwritten, either:
- The victim's original HTTP request hangs until timeout (their callback reference is gone, so no node response reaches it) — a denial of service, or
- If the attacker's request is processed first and DON nodes reply to the attacker's message before the victim's, the attacker receives whatever comes back to that MessageId. Since node responses are correlated only by `MessageId` (not sender), the attacker can effectively intercept the response destined for the victim's trigger if IDs collide.

This is a genuine cross-user isolation break reachable purely from an unauthenticated/any signed gateway HTTP client — no operator or DON compromise needed. The Methods() allowlist and rate limiter (`nodeRateLimiter`) do not protect against this because the collision path is entirely on the inbound user-message side, not the outbound node-message side, and the `TODO: apply allowlist and rate-limiting here` comment confirms no allowlist currently exists for `HandleLegacyUserMessage` [5](#0-4) .

Note: exploitability depends on the attacker being able to predict or observe a victim's `MessageId` before the DON responds (the window is bounded by `CallbackMaxAgeSec`, default 120s [6](#0-5) ). If MessageIds are always high-entropy client-generated UUIDs unknown to other parties, this becomes hard to exploit in practice; but the code enforces no uniqueness or entropy requirement on `MessageId` (`MessageIdMaxLen` is the only constraint [7](#0-6) ), so nothing in this handler prevents the collision — it is a genuine root-cause gap in `handler.go`, contrasted with the newer v2 `httpTriggerHandler`, which explicitly rejects duplicate in-flight request IDs (`"in-flight request"` error) [8](#0-7)  — showing the legacy handler lacks a fix that already exists elsewhere in the codebase.

### Impact Explanation
Denial of service / response misdelivery against another user's gateway request: a victim's HTTP trigger request can be silently dropped (never receiving its DON response, timing out) or, in a race, its intended response can be redirected to an unrelated caller. This matches Chainlink's "unauthorized action on another user's job/request" and "cross-user response confusion" bounty impact class, though it does not constitute key/secret disclosure or fund movement.

### Likelihood Explanation
No privileges are required — any client capable of sending a validly-signed (but attacker-owned-key-signed) `web_api_trigger` message to the gateway can pick an arbitrary `MessageId`. The only precondition is knowledge of the victim's in-flight `MessageId` within the callback lifetime window (up to `CallbackMaxAgeSec`, default 120s). If `MessageId`s are predictable, sequential, or observable (e.g., logged, echoed in prior responses, or chosen by a client library in a non-random way), this is trivially and repeatably exploitable; if IDs are always cryptographically random UUIDs unknown to third parties, likelihood is low. The code itself provides no defense regardless of ID entropy.

### Recommendation
In `HandleLegacyUserMessage`, before inserting into `h.savedCallbacks`, check for an existing non-expired entry with the same `MessageId` and reject the new request (e.g., return an `api.HandlerError`/conflict response) rather than silently overwriting, mirroring the "in-flight request" duplicate-ID rejection already implemented in the v2 `httpTriggerHandler`. Additionally, consider deriving the map key from `(Sender, MessageId)` rather than `MessageId` alone to enforce per-sender isolation.

### Proof of Concept
Go handler-level test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two signed `api.Message` objects for `MethodWebAPITrigger` with different signer keys (`victimKey`, `attackerKey`) but identical `MessageId` (e.g., `"shared-id"`), each with a valid `TriggerRequestPayload` and current timestamp.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)`, then immediately `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)`.
3. Assert `handler.savedCallbacks["shared-id"].Callback == attackerCallback` (i.e., victim's callback was overwritten) — currently true, demonstrating the bug.
4. Simulate a DON node response for `"shared-id"` via `handler.HandleNodeMessage`, and assert that `victimCallback.Wait(ctx)` never resolves (times out) while `attackerCallback.Wait(ctx)` receives the response — proving cross-delivery/DoS.
5. After applying the fix, assert the second `HandleLegacyUserMessage` call returns an error/conflict response and `h.savedCallbacks["shared-id"].Callback` still equals `victimCallback`.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
