### Title
Missing role restriction on `/debug/vars` allows any authenticated session (including `UserRoleView`) to read internal Go runtime metrics - ([File: core/web/router.go])

### Summary
`debugRoutes` mounts `GET /debug/vars` behind only `auth.Authenticate(..., auth.AuthenticateBySession)`, with no `auth.RequiresAdminRole`/`RequiresEditRole` wrapper, unlike almost every other sensitive endpoint in `v2Routes` (e.g. `/v2/keys/*/export`, `/v2/config`). Any user holding a valid session cookie — including the lowest-privilege `UserRoleView` — can reach the standard library `expvar.Handler()` and read published runtime variables.

### Finding Description
`debugRoutes` in [1](#0-0) registers `/debug/vars` using only `auth.AuthenticateBySession`, with no role check, whereas comparable v2 routes consistently wrap handlers in `auth.RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` (see e.g. key export/import routes at [2](#0-1) ). The role-check helpers (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) live in [3](#0-2)  and are opt-in per-route wrappers — `debugRoutes` simply never applies one, so once `AuthenticateBySession` succeeds for any role (`UserRoleView`, `UserRoleRun`, `UserRoleEdit`, `UserRoleAdmin`), `c.Next()` proceeds straight to `expvar.Handler()`.

However, I found no `expvar.Publish`/`expvar.NewString`/custom var registration anywhere else in the `core/` tree — the only two references to `expvar` in `core/**/*.go` are the import and the route registration in `router.go` itself. This means the handler only serves the Go standard library's default published vars: `cmdline` (`os.Args`) and `memstats` (`runtime.MemStats`, i.e. GC/heap statistics). No DSNs, API keys, or other application secrets are published via `expvar` in this codebase.

### Impact Explanation
The concrete, provable impact is limited to disclosure of the process's `os.Args` and Go runtime memory/GC statistics to any authenticated user regardless of role, which is a minimum-role/authorization-exactness violation (a `UserRoleView` session should not be able to reach an operational/debug endpoint that every other comparable admin-adjacent route restricts). This does not, on the evidence available in this repo, rise to "DSN or key disclosure," since nothing sensitive is registered with `expvar`. Risk is bounded to potential exposure of command-line arguments (which could contain sensitive values only if an operator misconfigures the node to pass secrets via CLI flags — a misconfiguration-only path excluded by the rules) and low-sensitivity GC/memory telemetry.

### Likelihood Explanation
Trivial and fully reproducible: it only requires a valid session cookie for any role, including the default/lowest `UserRoleView` created via normal user management. No token, admin credential, or special network position is needed.

### Recommendation
Wrap the `/debug/vars` route with `auth.RequiresAdminRole` (consistent with other operational/debug-adjacent routes such as key export endpoints) in `debugRoutes`, e.g. `group.GET("/vars", auth.RequiresAdminRole(...))`, and audit whether any future `expvar.Publish` calls could introduce sensitive data before loosening this restriction.

### Proof of Concept
Handler-level integration test in `core/web`:
1. Build the router via `NewRouter` with a test `chainlink.Application`/`AuthenticationProvider`.
2. Create a session for a user with `Role: clsessions.UserRoleView` and set the session cookie (mirroring patterns in existing `core/web/*_test.go` session tests).
3. Issue `GET /debug/vars` with that session cookie.
4. Assert the response is `200 OK` (not `401`/`403`), demonstrating the role gap versus e.g. `GET /v2/keys/eth/export/:address` returning `403 Forbidden` for the same `UserRoleView` session.
5. Optionally assert the JSON body contains only `cmdline`/`memstats` keys to document that, in the current codebase, no secret material is exposed — supporting a scoped "missing role check" finding rather than a "secret disclosure" finding.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()

		}

			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
