### Title
Loss-adjusted pending withdrawals can still be claimed at par for receipts booked under a different epoch, draining the haircutted funding - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is a reward-debt accounting mismatch: a claim pays out rewards once, then a stale/unchecked cached balance lets the user claim the same reward again. The closest analog in this codebase is the loss-adjusted withdraw path in `IdleCreditVault`: `collectWithdrawFunds` applies a single `lossRecoveryPriceByEpoch[epochNumber]` haircut to the *aggregate* `pendingWithdraws` bucket, but `_claimLossAdjustedWithdrawRequest` only haircuts the per-epoch slice `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]`. Any receipt basis booked under a different epoch key survives intact in `withdrawsRequests[_user]` and is paid at par through `_claimFundedWithdrawRequest`, even though the underlying that was actually collected already assumed a haircut on the entire bucket. One receipt, two payouts — the same double-claim invariant break.

### Finding Description
When a stop settles a loss (`stopEpochWithDuration` path), IdleCDO calls `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` with `_amount < pendingWithdraws`. The vault then:

1. Computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the whole aggregate, sets `pendingWithdraws = 0`, and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` (`IdleCreditVault.sol:411-430`).
2. At claim time, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch`, paying `claimBasis * lossRecoveryPrice / RECOVERY_FULL` (`IdleCreditVault.sol:789-800`, `:811-837`).
3. `_claimFundedWithdrawRequest` then pays the *remaining* `withdrawsRequests[_user]` plus APR0 settled buckets fully at par, gated only by `epochNumber <= lastWithdrawRequest[_user]` (`IdleCreditVault.sol:319-350`).

The mismatch: `pendingBasis` is global and includes every user's pending receipts, while the haircut is keyed to a single epoch per user. `requestWithdraw` only blocks re-requesting when the *user's own* `lastWithdrawRequest` epoch has a nonzero `lossRecoveryPriceByEpoch` (`IdleCreditVault.sol:261-271`); nothing prevents a user (or different users) from holding pending receipts recorded under multiple epoch keys in the same `pendingWithdraws` aggregate. A user who requested in epoch N and again in epoch N+1 has `lastWithdrawRequest == N+1`; when the loss is recorded under epoch N+1, the epoch-N slice `withdrawsRequestsByEpoch[user][N]` is never haircutted — it remains in `withdrawsRequests[user]` and is paid at par by `_claimFundedWithdrawRequest`, while the funded `_amount` only covered `basis * recoveryPrice` for it. Symmetrically, if the recorded key does not match a user's request epoch, that user skips the haircut entirely and claims at par.

### Impact Explanation
The vault transfers out more underlying than it collected for the loss-adjusted epoch. The excess is paid from the same strategy balance that backs other funded receipts and the default-recovery reserve (`_transferFundedClaim` spends ahead of the reserve), so later claimants — other withdraw requesters or instant-withdrawers — are left underfunded: direct insolvency/theft of unclaimed yield up to `pendingBasis * (1 - lossRecoveryPrice)` for the mismatched receipts.

### Likelihood Explanation
Requires a stopEpoch that realizes a loss while `pendingWithdraws` contains receipts recorded under more than one epoch key — reachable when a user (or two users) requests during a running epoch and again during the following epoch/buffer without claiming, which `requestWithdraw` permits because no `lossRecoveryPriceByEpoch` exists yet for their marker. The attacker is an ordinary KYC-passed lender; loss realization is driven by honest manager/borrower calls. Likelihood is gated on a real loss event, but no privileged misbehavior is needed.

### Recommendation
Apply the loss haircut per-receipt rather than per-single-epoch-key: either store the haircut against every pending epoch that contributed to `pendingBasis` (or record a global pending recovery price), or have `_claimLossAdjustedWithdrawRequest` haircut the entire `withdrawsRequests[_user]` + APR0 claim basis — not just `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]` — and zero all per-epoch slices. At minimum, revert in `collectWithdrawFunds` when pending receipts span epochs that cannot all be keyed by the stored price.

### Proof of Concept
Foundry fork sketch (mirror `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. User deposits AA, requests withdraw in epoch N (receipt basis R1, marker N).
cdoEpoch.requestWithdraw(amount / 2, address(AAtranche));
// 2. Epoch N ends, epoch N+1 starts; user does NOT claim and requests again (marker N+1, basis R2).
_startEpochAndCheckPrices(N + 1);
cdoEpoch.requestWithdraw(amount / 4, address(AAtranche));
// 3. stopEpochWithDuration realizes a loss: collectWithdrawFunds receives
//    _amount = (R1 + R2) * price < pendingWithdraws and stores
//    lossRecoveryPriceByEpoch[epochNumber] = price, pendingWithdraws = 0.
// 4. User calls cdoEpoch.claimWithdrawRequest().
//    _claimLossAdjustedWithdrawRequest pays R2 * price (epoch N+1 slice),
//    _claimFundedWithdrawRequest then pays R1 at PAR.
// Expected: total paid = R2*price + R1  >  funded amount = (R1 + R2) * price.
// Assert vault underlying balance is short by R1 * (1 - price) for later claimants.
```

Uncertainty: I did not confirm the exact ordering of `epochNumber` increment relative to `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch` (grep returned only match counts); if the increment happens before collection, the recorded key can also mismatch single-epoch requesters whose `lastWithdrawRequest` was set pre-increment, which would strengthen the same finding rather than invalidate it. The multi-epoch-slice overpayment described above holds regardless of that ordering, since only one epoch slice per user is ever haircutted.
