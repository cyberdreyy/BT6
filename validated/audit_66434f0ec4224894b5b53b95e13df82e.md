### Title
Symlink-based workspace escape in `fileArchiver` allows archiving files outside the job working directory - (File: `commands/helpers/file_archiver.go`)

### Summary
`fileArchiver.process()` and `findRelativePathInProject()` validate artifact/cache paths using purely lexical operations (`filepath.Abs`/`filepath.Rel`) that never resolve symlinks, while `add()` calls `os.Lstat()` on the resulting path, which the OS transparently resolves through any symlinked intermediate directory components. A job that creates a symlink inside the workspace pointing to a directory outside `c.wd` (e.g., `/etc`) can supply `--path workspace/link/secret` and have the file physically located outside the job root added to `c.files` and archived.

### Finding Description
In `findRelativePathInProject` (`commands/helpers/file_archiver.go:191-222`) and `process` (`commands/helpers/file_archiver.go:65-101`), the "inside build directory" check is done by string-joining the path (`filepath.Abs`) and then checking whether `filepath.Rel(c.wd, abs)` starts with `..`. Both `filepath.Abs` and `filepath.Rel` operate purely on the textual path components; they never call `filepath.EvalSymlinks` or otherwise resolve intermediate symlinks. This means a path such as `workspace/link/secret`, where `link` is a symlink to `/etc`, is lexically computed as `<wd>/workspace/link/secret`, which resolves relative to `wd` without any `..` — so the "not supported: outside build directory" guard in `process` (line 86) and the "not a subpath of project directory" guard in `findRelativePathInProject` (line 215) are both bypassed.

The path then flows to `add()` (`commands/helpers/file_archiver.go:127-138`), which calls `os.Lstat(path)`. Unlike `filepath.Abs`/`Rel`, `os.Lstat` is a real filesystem syscall: the kernel resolves every intermediate path component (only the final component is not dereferenced by `Lstat`). So `os.Lstat("workspace/link/secret")` actually traverses through the `link` symlink to stat `/etc/secret`, and that `os.FileInfo` (and the literal path string) is stored in `c.files[path]`, keyed by the *lexical* path — which the archiver later reads from disk using that same path, again transparently following the symlink and reading the real file content from outside the job root.

`doublestar.FilepathGlob(rel, doublestar.WithNoFollow())` in `processPath` (line 160) only affects symlink-following during wildcard *glob expansion*; it does not prevent a non-wildcard literal path (or a match returned from `filepath.Walk`) from containing a symlink component that is later dereferenced by `Lstat`/file read. The project's own integration test (`commands/helpers/file_archiver_integration_test.go`) demonstrates that symlinks are followed and archived (its `symlinks` all point back inside `projectRoot`), confirming no protection exists against symlink targets that point *outside* the working directory — there is simply no test or guard for that case.

### Impact Explanation
An unprivileged job author can read and exfiltrate arbitrary host files reachable from the job's filesystem view (subject to the executor's mount namespace/permissions) by creating a symlink inside the workspace and passing a path through it via `--path` (artifacts) or cache paths, then downloading the resulting artifact/cache archive. This breaks the invariant that job-controlled paths must not cause file access outside the job root.

### Likelihood Explanation
Highly feasible: any pipeline author can run `ln -s /etc/passwd workspace/link` (or point to any directory) in their `script:`, then declare `artifacts.paths: [workspace/link]` or use `cache: paths:`, or invoke `cache-archiver`/`artifacts-uploader` helpers directly with `--path workspace/link/secret`. No special privileges are needed beyond normal job execution, and the behavior is deterministic/repeatable.

### Recommendation
Resolve the real path (e.g., via `filepath.EvalSymlinks`) for both the base directory and the final matched path, and verify the resolved absolute path is still within the resolved `c.wd`, before calling `add()`/`os.Lstat()`. Reject or skip any match whose resolved real path escapes the working directory, rather than relying solely on lexical `filepath.Rel` checks against unresolved paths.

### Proof of Concept
Go test in `commands/helpers/file_archiver_test.go` (or an integration test alongside the existing symlink test):
```go
func TestFileArchiver_SymlinkEscapesWorkingDirectory(t *testing.T) {
    wd := t.TempDir()
    outside := t.TempDir()
    secret := filepath.Join(outside, "secret.txt")
    require.NoError(t, os.WriteFile(secret, []byte("top-secret"), 0644))

    link := filepath.Join(wd, "link")
    require.NoError(t, os.Symlink(outside, link))

    origWd, _ := os.Getwd()
    require.NoError(t, os.Chdir(wd))
    defer os.Chdir(origWd)

    c := &fileArchiver{Paths: []string{"link/secret.txt"}}
    require.NoError(t, c.enumerate())

    for path, info := range c.files {
        real, _ := filepath.EvalSymlinks(filepath.Join(c.wd, path))
        assert.True(t, strings.HasPrefix(real, c.wd),
            "archived file %q resolves outside working directory: %s", path, real)
    }
}
```
Expected (current, buggy) result: `c.files` contains an entry for `link/secret.txt` whose real path resolves to `outside/secret.txt`, failing the assertion — proving the escape. After the fix, `processPath`/`add` should reject this path and `c.files` should be empty.
