### Title
Unauthenticated flood of `web_api_trigger` messages causes eviction of legitimate pending callbacks in `h.savedCallbacks`, leading to silent response loss - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` accepts any message with a syntactically valid signature from *any* self-generated ECDSA key — there is no allowlist or per-sender rate limit applied before the message is stored in `h.savedCallbacks`. An attacker who can reach the gateway's HTTP ingress can generate unlimited keypairs/`MessageId`s, flood the shared `savedCallbacks` map, and force `pruneCallbacks` to evict legitimate, still-unexpired callbacks before their DON response arrives, causing those users' responses to be silently dropped.

### Finding Description
`Message.Validate()` only checks structural constraints and that the signature recovers to *some* address via `ExtractSigner`; it never checks that address against a DON/user allowlist [1](#0-0) . `Message.Sign` shows any caller holding an arbitrary `*ecdsa.PrivateKey` can produce a valid signature [2](#0-1) . The gateway's `ProcessRequest` only calls `msg.Validate()` before routing to `HandleLegacyUserMessage` — no per-sender throttling or allowlist gate exists at this layer [3](#0-2) .

Inside `HandleLegacyUserMessage`, immediately before inserting into the map, there is an explicit acknowledgement that no protection exists: `// TODO: apply allowlist and rate-limiting here` [4](#0-3) . Every valid, non-stale, correctly-shaped `web_api_trigger` message is unconditionally stored keyed by attacker-chosen `MessageId`: [5](#0-4) .

`pruneCallbacks` runs only once per `CallbackPruneIntervalSec` (default 30s) [6](#0-5) . It first deletes entries older than `CallbackMaxAgeSec` (default 120s), then — if the map is still over `MaxSavedCallbacks` (default 20000) — sorts *all* remaining entries by `createdAt` and deletes the oldest ones down to half of `maxSize`, **regardless of whether those entries have expired**: [7](#0-6) . The map itself has no insertion-time cap between prune cycles (the constant comment even states "could briefly exceed under heavy load") [8](#0-7) .

Because eviction is purely insertion-order/count based rather than deterministic-expiry based, an attacker who inserts many entries within a prune interval can force eviction of a legitimate, still-valid (well under 120s old) callback simply because it is older than the flood of attacker-inserted entries. When the legitimate DON node eventually replies, `handleWebAPITriggerMessage` looks up the (now-evicted) `MessageId`, finds nothing, and silently drops the response — the user's `callback.Wait(ctx)` in `gateway.go` times out with no indication of what happened [9](#0-8) .

### Impact Explanation
This is a denial-of-service / isolation-violation of legitimate users' pending gateway requests: an unprivileged, unauthenticated (self-signed key, no DON membership) attacker can starve or evict other users' in-flight `web_api_trigger` callbacks, causing their DON responses to be dropped and their requests to time out. This matches Chainlink's "Denial of Service" bounty impact class scoped to the gateway service — it does not achieve fund loss, key disclosure, or cross-user response hijack, only response loss/starvation for legitimate users.

### Likelihood Explanation
Feasible and repeatable with minimal effort: the attacker needs only the ability to submit signed JSON-RPC requests to the gateway's `ProcessRequest` HTTP ingress (any generated ECDSA keypair suffices, no DON credential or allowlist entry required, per the explicit "TODO: apply allowlist and rate-limiting here" comment) [4](#0-3) . There is no per-sender rate limit on this ingest path (the `nodeRateLimiter` only throttles *outgoing* node messages in `handleWebAPIOutgoingMessage`, not incoming user triggers) [10](#0-9) . Generating enough distinct signed messages to exceed `MaxSavedCallbacks` (20000) within a 30s prune window is computationally trivial for an attacker with modest bandwidth.

### Recommendation
- Enforce the still-outstanding TODO: apply per-sender/IP rate limiting and/or an allowlist for `web_api_trigger` requests before inserting into `savedCallbacks`.
- Change eviction policy so pruning never removes an entry younger than `CallbackMaxAgeSec` regardless of map size; instead, reject/backpressure new insertions (return an error/`ServerOverloaded` response) when the map is at capacity, rather than silently evicting older still-valid entries.
- Consider bounding `savedCallbacks` growth synchronously at insertion time (e.g., reject inserts once at `MaxSavedCallbacks`) instead of only pruning periodically, to close the window where the map can "briefly exceed" its bound under heavy load.

### Proof of Concept
Go handler-level integration test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Construct a `handler` with small test-friendly config: `MaxSavedCallbacks = 10`, `CallbackMaxAgeSec = 120`, `CallbackPruneIntervalSec = 1`.
2. Insert one "legitimate" callback via `HandleLegacyUserMessage` with `MessageId = "legit-1"`, signed by a distinct key, timestamped `now`.
3. Immediately flood the handler: loop generating 100 new ECDSA keys, sign 100 distinct `web_api_trigger` messages with unique `MessageId`s, and call `HandleLegacyUserMessage` for each (simulating attacker traffic with no DON allowlist restriction).
4. Trigger `pruneCallbacks()` (or wait for the ticker) and then assert `legit-1` is no longer present in `h.savedCallbacks` even though `now.Sub(createdAt) < CallbackMaxAgeSec`.
5. Simulate the legitimate DON node's delayed response via `HandleNodeMessage` for `legit-1` and assert the callback never receives a response (i.e., `cb.Wait(ctx)` times out), demonstrating silent response loss caused purely by attacker-driven insertion volume rather than deterministic expiry.
6. Assert (negative control) that with attacker flood disabled, the same legitimate callback resolves normally — proving the eviction, not expiry, causes the loss.

func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {

	}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
