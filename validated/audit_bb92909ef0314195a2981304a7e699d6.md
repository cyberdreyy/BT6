### Title
`getLargestAccounts` RPC returns cached results across mismatched commitment levels - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_largest_accounts` caches its scan result keyed only by `RpcLargestAccountsFilter` and never incorporates the requested `CommitmentConfig` into the cache key or into the cache-hit validity check, so a cached result computed for one commitment level (e.g. `processed`) is served back for a completely different commitment level (e.g. `finalized`) requested shortly after, returning stale/wrong-slot data without recomputation.

### Finding Description
`get_largest_accounts` first resolves the requested bank via `self.bank(config.commitment)`, but the cache lookup that follows ignores `config.commitment` entirely: [1](#0-0) 

The cache itself, `LargestAccountsCache`, stores entries in a `HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>` — the key is only the optional circulating/non-circulating filter, with no commitment or slot dimension: [2](#0-1) 

When populating the cache, `set_cached_largest_accounts` is likewise called with only `config.filter`, `bank.slot()`, and the computed accounts — again omitting commitment: [3](#0-2) [4](#0-3) 

This is directly analogous to the reported bug class: a derived/cached value (`vaultUtilization`/`totalAvailableAssetsForVault` in the Fraxlend report, here the cached largest-accounts snapshot) is consumed without first validating/refreshing it against the caller's actual requested context (there: latest interest state; here: the requested commitment level). The result is that an unprivileged JSON-RPC caller can obtain a `getLargestAccounts` response whose returned `context.slot` and account balances correspond to a different commitment level's bank state than what was requested — e.g., requesting `commitment: "finalized"` shortly after another client requested `commitment: "processed"` returns the processed (potentially unrooted/optimistic, later-reverted) bank's account balances mislabeled under a slot that does not correspond to what "finalized" should return.

### Impact Explanation
This causes wrong data to be returned for a query without any consensus-state mutation, but with concrete user-facing incorrectness: a `finalized`-commitment request can silently return `processed`-commitment (potentially non-finalized/rollback-able) account balances and slot context, or vice versa. Consumers (exchanges, explorers, monitoring tools) relying on `getLargestAccounts` for supply/whale-monitoring under a specific commitment guarantee would receive incorrect, non-conforming data. This matches the "wrong-slot/fork/account data returned" acceptance criterion.

### Likelihood Explanation
The bug is trivially triggered by any two unprivileged RPC clients (or the same client) issuing `getLargestAccounts` calls with different `commitment` parameters within the cache TTL window (`LargestAccountsCache::duration`, default set at RPC service construction). No special privileges, race conditions, or multiple in-flight requests beyond ordinary usage are required — a single low-rate sequence of two calls to a public JSON-RPC endpoint is sufficient.

### Recommendation
Include the resolved commitment (or the resolved bank's slot/commitment level) as part of the cache key in `LargestAccountsCache`, or validate on cache-hit that the previously cached entry's originating commitment matches `config.commitment` before returning it — analogous to the report's recommendation to refresh the derived state (`whitelistUpdate`) before consuming it. Concretely, change `get_cached_largest_accounts`/`set_cached_largest_accounts` and the `LargestAccountsCacheValue` to key/store by `(filter, commitment)` and reject cache hits for a different commitment.

### Proof of Concept
1. Client A calls `getLargestAccounts` with `{"commitment": "processed"}`. This populates the cache for `filter = None` with the processed bank's slot/accounts via `set_cached_largest_accounts(&config.filter, bank.slot(), &accounts)` [4](#0-3) .
2. Within the cache TTL (`LargestAccountsCache::duration`), Client B calls `getLargestAccounts` with `{"commitment": "finalized"}` and the same (default/`None`) `filter`.
3. `get_cached_largest_accounts(&config.filter)` returns the cache entry from step 1 because the lookup key does not include commitment [5](#0-4) .
4. Client B receives the processed-bank's slot/account-balance data labeled as satisfying `finalized` commitment, even though that data was never finalized and could be rolled back if the corresponding fork is not eventually rooted.

#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }
