### Title
Front-runnable, permissionless `LockupFactory::create` lets an attacker permanently squat a victim owner's deterministic lockup address with attacker-chosen parameters - (`lockup-factory/src/lib.rs`, `LockupFactory::create` / `on_lockup_create`)

### Summary
`LockupFactory::create` derives `lockup_account_id` deterministically from `sha256(owner_account_id)` alone and has no restriction on who may call it or with what `lockup_duration`/`vesting_schedule`. Since the account address depends only on the target `owner_account_id`, any unprivileged caller can race the legitimate creator's transaction for the same `owner_account_id`, win the `create_account()` action on-chain, and permanently occupy that address with parameters (e.g. `lockup_duration = MAX_U64`) the victim never authorized.

### Finding Description
Binding as claimed: `refunded_deposit(loser) + balance_at(lockup_account_id) == attached_deposit(winner)` holds exactly (the `on_lockup_create` callback correctly refunds the losing caller's own deposit to their own `predecessor_account_id` via `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` at `lockup-factory/src/lib.rs:171-198`, and the winner's transferred deposit stays at the account it funded). No caller's NEAR is stolen by the other party through this callback logic — the refund-on-failure design in `on_lockup_create` correctly isolates each caller's own funds.

The real bug is upstream, in `create` itself:
- The address is computed purely from the target owner: `let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes()); let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());` [1](#0-0) 
- `create` is a fully public, unrestricted, `#[payable]` method — any account can call it for any `owner_account_id`, with any `lockup_duration`, `vesting_schedule`, `release_duration`, or custom `whitelist_account_id`, as long as `MIN_ATTACHED_BALANCE` is attached: [2](#0-1) 
- The promise batch unconditionally attempts `create_account()` at that deterministic address with no existence check: [3](#0-2) 

Because NEAR's `CreateAccount` action fails if the target account already exists, whichever caller's transaction is included first on-chain wins the address permanently. Since `owner_account_id` is the only input to the address derivation, an attacker with no special privilege can call `create(owner_account_id="victim.near", lockup_duration=MAX_U64, ...)` and, if it lands before the victim's/foundation's legitimate `create` call for `victim.near`, permanently claim that address with hostile parameters. The legitimate creator's subsequent call then fails `create_account()`, `is_promise_success()` returns `false`, and their deposit is refunded to themselves — so they lose no funds, but they can never deploy the intended lockup for `victim.near` again, because the address is fixed and now permanently occupied by attacker-chosen configuration (e.g. tokens effectively locked forever via `lockup_duration = MAX_U64`, or no vesting/whitelist restrictions the real creator intended).

No existing guard (`assert_owner`, `assert_called_by_foundation`, `assert_self`, `is_promise_success`, etc.) prevents this, because none of them constrain who may call `create` or check whether the target account is already reserved for a specific configuration before racing to claim it.

### Impact Explanation
This matches the explicitly listed Critical category: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The victim (`owner_account_id`) permanently receives a lockup contract configured with parameters the attacker chose rather than what the legitimate creator (e.g., the NEAR Foundation) intended — this is a one-time-per-victim-account griefing/parameter-hijack, but it is repeatable across any number of distinct victim `owner_account_id`s, at a cost of only `MIN_ATTACHED_BALANCE` (3.5 NEAR) per target, which the attacker can even reclaim if they design the lockup to allow withdrawal back to themselves (since they control the `staking_pool_whitelist_account_id`/`foundation_account_id` fields they pass in). The attacker does not steal the victim's or legitimate creator's deposit directly (the refund path correctly returns each party's own funds), but the address-squatting itself is the critical harm.

### Likelihood Explanation
Preconditions: attacker only needs to know (or predict) the target `owner_account_id` for which a legitimate lockup is about to be created, and to attach `MIN_ATTACHED_BALANCE`. This is fully within the "unprivileged attacker" capabilities described (send a transaction, attach a deposit, call any open method). Winning the race requires only submitting the transaction with sufficient gas/priority before the legitimate transaction is included — a standard front-running scenario on a public, permissionless call. It is trivially repeatable against any `owner_account_id` the attacker chooses to target ahead of time.

### Recommendation
Restrict `LockupFactory::create` so it cannot be invoked on behalf of an arbitrary `owner_account_id` by anyone, e.g., require `assert_called_by_foundation`/an allow-list of privileged creators, or bind the deterministic address to the caller (`predecessor_account_id`) as well as `owner_account_id`/a nonce so distinct callers cannot collide on the same address, or check `env::current_account_id()`/account existence before scheduling `create_account()` and reject/return the deposit immediately without letting an unauthorized configuration ever be attempted for a given owner.

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
