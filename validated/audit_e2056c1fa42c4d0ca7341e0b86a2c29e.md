### Title
Unauthenticated APR configuration left callable on `IdleCreditVault` until `idleCDO` is linked — anyone can set `lastApr`/`unscaledApr` up to `maxApr`, inflating withdraw receipts and forcing a borrower shortfall/default - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2018-7556 is an unauthenticated-exposure bug: `InstallerController.php` remained reachable after installation, letting remote attackers hit a surface that should have been locked once setup completed. The strongest analog in idle-tranches is `IdleCreditVault.setApr` (and its wrappers `setAprs`/`setAprsWithBuffer`), which skips its caller check entirely while `idleCDO == address(0)`. Any EOA can therefore write the vault's APR configuration during the post-`initialize` / pre-`setWhitelistedCDO` window — the exact "installer still reachable after install" pattern.

### Finding Description
`setApr` gates callers only when `idleCDO` is already set:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
function setApr(uint256 _apr) public {
  address _cdo = idleCDO;
  // if cdo is not yet set we skip the check (this can happen only during the setup)
  if (_cdo != address(0)) {
    if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  }
  uint256 _maxApr = maxApr;
  if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
  lastApr = _apr;
}
``` [1](#0-0) 

`setAprs` and `setAprsWithBuffer` are `external` and funnel into `setApr`, so an attacker can set both `unscaledApr` and `lastApr` to `DEFAULT_MAX_APR` (20%) — bounded only by `maxApr`, never by caller identity — at any time before the owner calls `setWhitelistedCDO`: [2](#0-1) [3](#0-2) 

The injected APR then feeds real accounting:
- `startEpoch` computes `expectedEpochInterest = pendingWithdrawFees + _calcInterest(getContractValue())`, where `_calcInterest` uses `_getStrategyApr()` — i.e. the attacker-set `lastApr`. [4](#0-3) 
- `requestWithdraw` calls `_calcInterestWithdrawRequest`, which prices each receipt's interest from the same APR, minting a strategy-token receipt for `principal + interest - fees`. [5](#0-4) [6](#0-5) 

### Impact Explanation
With APR pinned at the 20% cap instead of the intended rate, every pending-withdraw receipt is minted at an inflated basis and `expectedEpochInterest` / `pendingWithdraws` exceed what the honest borrower agreed to fund. At `stopEpoch`, `getFundsFromBorrower` pulls `expectedInterest + pendingWithdraws`; an honestly-provisioned borrower allowance covers only the real rate, the transfer reverts, and `_handleBorrowerDefault` fires — `defaulted = true`, deposits stay paused, withdraw requests are blocked, and the pool is frozen until the owner runs `finalizeDefault` with a recovery haircut that crystallizes a loss no borrower actually caused. Alternatively, receipts minted above funded value are haircut through `lossRecoveryPriceByEpoch`, socializing the phantom interest across pending claimants. Either path produces temporary freezing of all vault funds plus a quantified haircut equal to the APR delta over the epoch (up to ~1.9% of requested principal for a 35-day epoch+buffer at the 20% cap). [7](#0-6) [8](#0-7) 

### Likelihood Explanation
The exposure exists only while `idleCDO == address(0)` — between `initialize` and `setWhitelistedCDO`. If `IdleCreditVaultFactory` performs both atomically in one transaction there is no exploitable window and this collapses to a non-issue; if linking is a separate owner transaction (or a redeploy/migration leaves it unlinked), a mempool observer can front-run or back-run it in the same block. No KYC, deposit, or privileged role is needed. The `maxApr` cap bounds but does not prevent the damage. I could not confirm whether the factory links the CDO atomically, which is the deciding factor for exploitability.

### Recommendation
Move the caller check out of the `_cdo != address(0)` conditional: require `msg.sender == manager || msg.sender == owner()` when `idleCDO` is unset, or set `idleCDO` inside `initialize` / a factory-atomic call so the unauthenticated window never exists. Also consider recording the APR solely via `_setScaledApr` at `startEpoch`, making manual `setApr` unreachable for EOAs entirely.

pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// Fork: mainnet. Scenario: vault initialized, owner has NOT yet called setWhitelistedCDO.
contract SetAprOpenWindowTest is Test {
    IdleCreditVault vault;
    address attacker = address(0xBEEF);

    function setUp() public {
        vault = IdleCreditVault(/* deployed IdleCreditVault proxy */);
        // state: vault.initialize() done, vault.idleCDO() == address(0)
    }

    function test_AttackerSetsAprBeforeCdoLink() public {
        assertEq(vault.idleCDO(), address(0));
        vm.prank(attacker);
        // No caller check fires: _cdo == 0, only the maxApr cap (20e18) applies.
        vault.setAprsWithBuffer(vault.DEFAULT_MAX_APR(), 30 days, 5 days);
        assertEq(vault.lastApr(), vault.DEFAULT_MAX_APR());
        assertEq(vault.unscaledApr(), vault.DEFAULT_MAX_APR());
        // Owner then calls setWhitelistedCDO(cdo) — too late.
        // 1) lender.requestWithdraw() mints receipt priced at 20% epoch interest.
        // 2) startEpoch sets expectedEpochInterest = _calcInterest(TVL) at 20%.
        // 3) Borrower allowance (honest, e.g. 4%) underfunds getFundsFromBorrower.
        // 4) stopEpoch -> catch -> _handleBorrowerDefault: defaulted, paused,
        //    all deposits/requests frozen until finalizeDefault; claimants take
        //    a lossRecoveryPrice haircut equal to the unfunded phantom interest.
    }
}
```
Run with: `forge test --fork-url $MAINNET_RPC --match-test test_AttackerSetsAprBeforeCdoLink -vvv`. Expected outcome: the `setAprsWithBuffer` call succeeds from an arbitrary EOA, demonstrating the access-control gap; the downstream default/freeze follows the existing `stopEpoch` revert path.

  function _calcInterestWithdrawRequest(uint256 _amount, address _tranche) internal view returns (uint256 _interest, int256 _diff) {
    uint256 _duration = epochDuration;
    if (_duration == 0) {
      return (_interest, _diff);
    }

    uint256 _buffer = bufferPeriod;
    // calculate total vault interest (they don't get the interest for the buffer period for withdraw requests so 
    // we scale it back since _calcInterest is scaling the interest with tht buffer period),
    uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
    // calculate total tranche interest for the whole tranche supply
    uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
    // calculate interest for the given tranche and given amount
    uint256 _trancheBal = _lastSavedNAV(_tranche);
    _interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
    // calculate the interest that the _amount would have received if there was no split ratio (ie interest split based only on tvl).
    // This is used to calculate the interest that should be added to the expectedEpochInterest when 
    // withdrawing an AA tranche or the interest that should be removed from expectedEpochInterest when
    // withdrawing a BB tranche
    uint256 interestWithoutSplitRatio = _calcInterest(_amount) * _duration / (_duration + _buffer);
    // difference between total interest and tranche interest (positive for AA, negative for BB)
    _diff = int256(interestWithoutSplitRatio) - int256(_interest);
  }
