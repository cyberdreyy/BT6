### Title
Stale confirmations from a deleted-then-re-added member are counted toward `num_confirmations`, letting a request execute with fewer than `num_confirmations` continuously-live members - (File: multisig2/src/lib.rs)

### Summary
`confirm` counts entries in a request's `confirmations: HashSet<String>` toward `self.num_confirmations` purely by set size, without re-checking whether each stored member string still corresponds to a currently, continuously live member. `delete_member` only purges confirmations for requests whose *original requester* (`r.member`) is the removed member — it never scans and strips the removed member's string from the `confirmations` set of requests they merely *confirmed*. Because `MultisigMember::to_string()` is a deterministic serialization of the member's identity, a member who is deleted and later re-added with the same identity leaves their pre-removal confirmation intact and indistinguishable from a fresh, post-re-add confirmation.

### Finding Description
The claimed binding: `confirmations cast for request R at execution == confirmations cast by members holding continuous live membership through execution`. The code instead enforces only: `confirmations.len() >= num_confirmations`, where `confirmations` is a `HashSet<String>` keyed by `member.to_string()` [1](#0-0) .

Root cause:
- `add_request`/`confirm` insert `member.to_string()` into the request's confirmation set with no timestamp or membership-generation tag [2](#0-1) .
- `delete_member` cleans up requests **originated by** the removed member (`r.member == member`), and removes the member from `self.members` and its `num_requests_pk` entry, but does **not** scan `self.confirmations` to strip the removed member's string from confirmation sets of requests they had merely confirmed (as a non-originating confirmer) [3](#0-2) .
- `assert_valid_request`/`confirm` only check that the *current caller* is presently a member (`current_member().is_some()`); they never re-validate the *entire stored* confirmation set against the current `self.members` [4](#0-3) .
- `MultisigMember` (`Account{account_id}` variant) serializes deterministically via `ToString` [5](#0-4) , so a re-added member with the same `account_id` produces the exact same key as before removal, making the stale entry indistinguishable from a live one.

Exploit flow:
1. Member M confirms pending request R (not the originator) — `confirmations` set for R now contains M's string.
2. Governance (self-request, requires threshold) executes `DeleteMember{M}` — R is untouched because R's `r.member != M` (M didn't originate R), so R's confirmation set still holds M's stale entry.
3. Governance executes `AddMember{M}` — M rejoins with the identical string key, but the stale confirmation was never invalidated by the removal/re-add cycle.
4. Other live members confirm R until `stale_M + live_confirmations >= num_confirmations`, without M ever calling `confirm` again post re-add.
5. `execute_request` fires with fewer than `num_confirmations` members having continuously, currently endorsed R — M's endorsement predates its membership lapse.

None of the existing guards (`assert_valid_request`, `assert_self_request`, the "already confirmed" check in `confirm`) detect this, because they operate on the *current caller* only, never re-validating the whole historical confirmation set against present membership.

### Impact Explanation
A multisig request (e.g., `Transfer`, `AddKey`, `FunctionCall` moving funds or granting access) can execute while backed by fewer than `num_confirmations` members with continuous, current standing — this falls squarely into the defined Critical category: "a multisig request executed below `num_confirmations` live members." Funds or privileges controlled by the multisig can move without the intended live quorum's consent. Blast radius is any multisig2-based contract (including this project's use as an owner/whitelist controller) where membership changes occur while requests are pending.

### Likelihood Explanation
Preconditions require: (a) at least one pending request R that a member M confirmed without originating, (b) M is later removed and re-added (a legitimate, plausible governance action, e.g., key rotation, temporary suspension) before R executes, and (c) remaining live confirmations plus M's stale one reach the threshold. This requires control by legitimate multisig members over add/delete-member actions and does not require an unprivileged external attacker to directly trigger it — it is a self-inflicted governance-timing bug reachable through ordinary multisig operations (confirm, delete-member, add-member, confirm), all of which are normal, permitted call sequences within the contract's own state machine. No foundation, owner, or redeploy is needed beyond the multisig members' own standard actions.

### Recommendation
When executing `DeleteMember`, iterate all pending requests' `confirmations` sets (not just those originated by the removed member) and remove the deleted member's string entry from each. Alternatively, tag each confirmation with a membership generation/epoch counter incremented on every `AddMember`/`DeleteMember`, and only count confirmations whose recorded generation matches the current generation when checking the threshold in `confirm`.

### Proof of Concept
Using `multisig2/tests/general.rs` patterns (`near-sdk-sim`/`RuntimeStandalone`) [6](#0-5) :
1. Deploy multisig2 with 3 `Account` members `{A, B, M}`, `num_confirmations = 3`.
2. As A, `add_request_and_confirm` a `Transfer` request R to some receiver (A auto-confirms).
3. As M, call `confirm(R)` — R now has confirmations `{A, M}` (2/3).
4. As multisig (self-request path), create+confirm+execute `DeleteMember{M}` (requires 3 confirmations from remaining set incl. M before removal, or restructure so deletion request is separate and fully confirmed by A, B, M before R is touched) — assert `get_members()` no longer contains M, assert `get_confirmations(R)` still contains M's string (proving stale entry survives, since R's `r.member == A`, not M).
5. As multisig, create+confirm+execute `AddMember{M}` — M rejoins; assert `get_members()` contains M again.
6. As B (a live member who never confirmed R), call `confirm(R)` — this pushes `confirmations.len() == 3 == num_confirmations`, so `execute_request` fires.
7. Assert R executed (funds transferred / request removed from `requests`) while asserting the set of members who called `confirm` on R *after* M's re-add is only `{A, B}` — i.e., `2 < num_confirmations == 3` live, continuously-confirming members, proving execution occurred below the intended live threshold.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
