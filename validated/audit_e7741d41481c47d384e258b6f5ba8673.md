### Title
Missing per-sender authorization allows any signer with a valid DON ID to reach a DON's capability handler - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest` routes legacy messages to a DON's `Handler` purely by looking up `msg.Body.DonId` in `g.handlers`, with only a length/format check performed by `msg.Validate()`. There is no check that the message's signer is subscribed to, or authorized for, that specific DON before the message is forwarded to the DON's `HandleLegacyUserMessage`.

### Finding Description
In `ProcessRequest`, for any message with a non-empty `DonId`, the code sets `isLegacyRequest = true`, calls `msg.Validate()`, then does a direct map lookup: `handlerKey = msg.Body.DonId; h, ok = g.handlers[handlerKey]` [1](#0-0) . `msg.Validate()` only checks structural constraints (signature format recoverable, DonId length, etc.) — it does not check whether the recovered signer is permitted to target that DON.

The message is then dispatched to `h.HandleLegacyUserMessage(ctx, msg, callback)` [2](#0-1) . For the WebAPI-capabilities handler, `HandleLegacyUserMessage` explicitly has no sender-allowlist check — the code contains an unresolved `// TODO: apply allowlist and rate-limiting here` comment immediately before it validates only the method name, then broadcasts the request to all DON member nodes [3](#0-2) . The corresponding test file has a matching acknowledgment: `// TODO: Validate Senders and rate limit check, pending question in trigger about where senders and rate limits are validated` [4](#0-3) .

By contrast, the vault handler implements a proper authorization step (`allowListBasedAuth.AuthorizeRequest`) before processing a request [5](#0-4) , showing that per-DON/per-sender authorization is expected to be enforced by individual handlers — but it is missing for the legacy WebAPI-capabilities trigger path.

Any holder of a valid ECDSA key (unregistered with any DON) can craft a `Message` with `Method` = `webapi_trigger`/`MethodWebAPITrigger`, sign it, and set `DonId` to any real, existing DON ID configured on the gateway. `ProcessRequest` will find the DON's handler and forward the message to every member node of that DON, consuming node/DON processing resources, without ever validating that the signer is an authorized workflow node/sender.

### Impact Explanation
Any unprivileged signer can submit trigger-shaped requests that get broadcast to all member nodes of an arbitrary configured DON, consuming that DON's capability-processing resources (bandwidth, goroutines, node compute) — a resource-consumption/DoS-adjacent impact against a specific target DON, not merely against the gateway itself. Actual workflow execution requires further downstream topic/workflow matching, so this does not by itself trigger fund movement or job execution, but it does allow unauthorized request submission and resource consumption on a target DON's handler, which falls under an allowlist/authorization bypass class.

### Likelihood Explanation
Feasibility is high: the attacker only needs any ECDSA keypair (no registration, no DON membership) and the target DON's public ID (often discoverable in job/service configuration or observable from network traffic). The message format (`api.Message`) and signing routine are exercised directly in test helpers (`newSignedLegacyRequest`) [6](#0-5) , confirming the request is trivially constructible and repeatable.

### Recommendation
Implement sender authorization in `handlers/capabilities/handler.go`'s `HandleLegacyUserMessage` (resolving the existing TODO) — e.g., verify the recovered signer against a configured allowlist/workflow-registry membership for the target DON before forwarding to DON members, mirroring the pattern used in `core/capabilities/vault/allow_list_based_auth.go`. Alternatively/additionally, add a generic per-DON allowlist check in `gateway.ProcessRequest` before dispatching legacy messages.

### Proof of Concept
Go handler-level test plan (extending `core/services/gateway/handlers/capabilities/handler_test.go` patterns):
1. Set up a `handler` for DON `"workflow_don_1"` with `setupHandler(t)` as in existing tests.
2. Generate a fresh, unregistered ECDSA key (not among `nodes` used in `setupHandler`).
3. Build a `TriggerRequestPayload` and `api.Message` with `Method: MethodWebAPITrigger`, `DonId: "workflow_don_1"`, sign with the unregistered key, call `msg.Validate()` (expect success — no allowlist check exists).
4. Call `handler.HandleLegacyUserMessage(ctx, msg, cb)` and assert: (a) no error/rejection is returned, (b) `don.SendToNode` is invoked for every DON member (as in `TestHandlerReceiveHTTPMessageFromClient`), proving the message was forwarded despite the signer not being a DON member/subscriber.
5. Compare against vault handler behavior: build a similarly-shaped unauthorized JSON-RPC request and confirm `handler.HandleJSONRPCUserMessage` in `handlers/vault/handler.go` rejects it via `requestProcessor.ProcessRequest`/`AuthorizeRequest`, demonstrating the asymmetry and confirming the WebAPI-capabilities path is the gap.

// newSignedLegacyRequest creates a signed legacy request message for testing purposes.
// Legacy requests embed
func newSignedLegacyRequest(t *testing.T, messageID string, method string, donID string, payload []byte) []byte {
	msg := &api.Message{
		Body: api.MessageBody{
			MessageId: messageID,
			Method:    method,
			DonId:     donID,
			Payload:   payload,
		},
	}
	privateKey, err := crypto.GenerateKey()
	require.NoError(t, err)
	require.NoError(t, msg.Sign(privateKey))
	codec := api.JsonRPCCodec{}
	rawRequest, err := codec.EncodeLegacyRequest(msg)
	require.NoError(t, err)
	return rawRequest
}
