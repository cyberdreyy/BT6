- Route: `POST /v2/jobs/:ID/runs` is registered with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` then wrapped in `auth.RequiresRunRole(prc.Create)`. [1](#0-0)

- `GetAuthenticatedUser` simply reads `SessionUserKey` from context, with no way to distinguish a real DB-backed session/token user from a synthetic user object created for an EI. [3](#0-2) 
- In `PipelineRunsController.Create`, `isUser` is derived from `GetAuthenticatedUser(c)`, and the code comment explicitly claims "only users are allowed to run jobs using int IDs - EIs not allowed," but because EI auth populates the same `SessionUserKey`, `isUser` is `true` for EI credentials too. [4](#0-3) 

So an EI credential holder passing an integer job ID will hit the `isUser` branch and call `prc.App.RunJobV2(ctx, jobID, nil)` for **any** job ID, not just the bridge/job the EI is scoped to — there's no ownership/bridge-name check tying the EI to a specific job ID in this function. This contradicts the stated intent in the code comment. The UUID check for webhook jobs is not bypassed (that check happens first and is independent of auth), but the "EIs not allowed to use int IDs" restriction is effectively broken because the `isUser` flag can't distinguish EIs from real users.

### Title
External Initiator credentials bypass "EIs not allowed" restriction and can trigger runs of arbitrary jobs by integer ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` intends to block External-Initiator-only credentials from triggering job runs via integer job IDs (the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed"), relying on `auth.GetAuthenticatedUser(c)` to distinguish real users from EIs. However, `AuthenticateExternalInitiator` also sets the same `SessionUserKey` used by `GetAuthenticatedUser`, so an EI-authenticated request is indistinguishable from a genuine user session, defeating the intended restriction.

### Finding Description
The route `POST /v2/jobs/:ID/runs` accepts authentication via EI credentials, API token, or session cookie (`auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession`), gated only by `auth.RequiresRunRole`. [1](#0-0) 

`AuthenticateExternalInitiator`, upon successful EI credential validation, calls `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})` in addition to setting the EI key — explicitly to satisfy `RequiresRunRole`. [5](#0-4) 

In `Create`, the code does:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
```
Since `GetAuthenticatedUser` only checks whether `SessionUserKey` is present and of type `*clsessions.User`, and `AuthenticateExternalInitiator` populates exactly that key, `isUser` evaluates to `true` for a request authenticated purely as an EI. [4](#0-3) [3](#0-2) 

The developer comment indicates the intended security boundary ("EIs not allowed") is not enforced by the actual code — the check cannot distinguish an EI-only credential from a database-backed user/token session. The UUID/webhook-type check earlier in the function is unrelated and unaffected; it correctly rejects UUID-shaped IDs regardless of auth type. [6](#0-5) 

### Impact Explanation
An attacker holding only external-initiator credentials (not full node user credentials) can trigger `RunJobV2` for any job by supplying its integer job ID, regardless of whether that job belongs to their bridge/initiator. This is an authorization-exactness violation: EI credentials are meant to be scoped to triggering only their associated bridge/job, but the code's `isUser` gate does not enforce that scoping at all — it only rejects UUID-formatted IDs (the removed webhook path). This maps to Chainlink's "unauthorized job run" bounty impact class, since a restricted credential (EI) can invoke `RunJobV2` on arbitrary jobs, potentially causing unintended fund movement or oracle actions if the job triggers on-chain transactions.

### Likelihood Explanation
Feasibility is high: exploitation only requires valid EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) — no user/admin credentials needed — and knowledge or guessing of a target job's integer ID (job IDs are sequential/enumerable via `/v2/jobs`, though that listing endpoint requires full user/token/session auth, not EI). If EI credentials are the only thing available, the attacker would need to know or guess the target integer job ID, which somewhat limits blind exploitation but does not require any privilege beyond an EI credential of any bridge.

### Recommendation
Distinguish real user sessions/tokens from EI-authenticated pseudo-users. Instead of reusing `SessionUserKey` for EIs, introduce a separate context flag (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` for presence and reject/branch differently), so `PipelineRunsController.Create` can correctly implement: "if this is an EI-only session (no `SessionUserKey` from `AuthenticateByToken`/`AuthenticateBySession`), refuse int-ID job runs" as the comment intends. Alternatively, keep the `isUser` check but explicitly test `_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject }` before falling into the int-ID branch.

### Proof of Concept
Go handler-level integration test plan for `core/web/pipeline_runs_controller_test.go`:
1. Set up a test app with one EI (`bridges.ExternalInitiator`) and one non-webhook job (e.g., a Cron or DirectRequest job) not associated with that EI.
2. Send `POST /v2/jobs/:ID/runs` with `ID` = integer job ID of the unrelated job, authenticated only via EI headers (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`), no session cookie/API token.
3. Assert response is `200`/`201` with a `pipelineRun` resource (i.e., `RunJobV2` was actually invoked) — demonstrating the "EIs not allowed" comment is not enforced, rather than the expected `401`/`403`.
4. Compare against a control case sending a UUID-shaped ID with the same EI creds, expecting `422` with `ErrJobTypeRemoved`, to confirm only the UUID path is blocked while integer-ID job runs are not blocked for EIs.
