### Title
Registrar hardcodes `CertManager`/`NitroValidator` addresses resolved once at startup instead of re-querying the canonical `TEEProverRegistry` chain — ([File: crates/proof/tee/registrar/src/service.rs])

### Summary
The TEE prover registrar resolves `TEEProverRegistry.NITRO_VALIDATOR()` and `NitroValidator.certManager()` exactly once during service startup and then binds those addresses into `NitroValidatorContractClient`/`CertManagerContractClient` objects that live for the entire process lifetime [4](#0-3) . If governance rotates the `NitroValidator` or `CertManager` implementation on L1 (an intended upgrade path implied by the discovery-through-registry design documented in `nitro_validator.rs`) [5](#0-4) , the running registrar keeps calling the stale, no-longer-canonical `CertManager`/`NitroValidator` contracts for every subsequent certificate cache/revocation check and registration, exactly analogous to the reported Aave `POOL` immutable-address flaw where `PoolAddressesProvider.getPool()` should be re-queried rather than cached once.

### Finding Description
`RegistrarConfig::run` performs the discovery sequence `registry.nitro_validator()` → `NitroValidatorContractClient::new(...)` → `nitro_validator.cert_manager()` → `CertManagerContractClient::new(...)` a single time before constructing `SignerManager`, and these clients are then moved into `Arc<SignerManager>` and used for the full lifetime of the service without any re-resolution logic [6](#0-5) . `SignerManager` subsequently calls `self.cert_manager.is_revoked(...)`, `load_verified(...)`, `verify_ca_cert_with_hints(...)`, etc., always against this single fixed contract address bound at process start [7](#0-6) . Elsewhere in the same codebase, the equivalent staleness class is explicitly identified and fixed: `IntervalResolver`/`resolve_intervals` intentionally re-read the `AggregateVerifier` implementation address from the `DisputeGameFactory` on every call because "the factory's `gameImpls` entry can be swapped by an upgrade... Caching either one at startup makes the proposer stop finding — and stop creating — games" [3](#0-2) , and `AnchorUpdater` documents the same "cached at startup silently stops matching" failure mode as a known limitation [8](#0-7) . The registrar's `NitroValidator`/`CertManager` discovery has no equivalent re-resolution or refresh mechanism.

### Impact Explanation
If the `NitroValidator` or `CertManager` contract referenced by `TEEProverRegistry` is rotated on L1 after the registrar starts, every `verify_ca_cert_with_hints`/`verify_client_cert_with_hints`/`is_revoked`/`load_verified` call the registrar issues will keep targeting the old, no-longer-authoritative contract. Certificate caching against the stale `CertManager` will not be recognized by the on-chain `TEEProverRegistry.registerSigner()` path (which presumably consults the current, registry-configured validator/cert manager), so new TEE prover signers can never be successfully registered, and revocation checks against the stale `CertManager` will no longer reflect the canonical revocation state. This can permanently halt TEE-based prover registration/rotation until the registrar process is manually restarted — a denial-of-service on the TEE dispute-game proving pipeline, and in the CRL-revocation case, checking revocation against a defunct contract could mask genuinely revoked certificates if the new `CertManager` diverges in state.

### Likelihood Explanation
This requires only a legitimate governance action (rotating `NitroValidator`/`CertManager` on the `TEEProverRegistry`/`NitroValidator` contracts) — not an attacker-controlled transaction — combined with the registrar process staying up across that rotation, which is the normal long-running deployment mode for this service (it only re-resolves on restart). No malicious actor input is needed; it is triggered purely by expected protocol maintenance, matching the "valid addresses can change" root cause from the original report.

### Recommendation
Re-resolve `TEEProverRegistry.NITRO_VALIDATOR()` and `NitroValidator.certManager()` periodically (e.g., once per poll/discovery cycle, mirroring the pattern already used by `IntervalResolver`/`resolve_intervals` and `AggregateVerifier` implementation lookups) instead of only once at startup, and rebuild/redirect the `CertManagerContractClient`/`NitroValidatorContractClient` when the resolved address changes, or fail fast/alert when a mismatch between the cached and freshly-queried address is detected.

### Proof of Concept
1. Start the registrar with `TEEProverRegistry` pointing at `NitroValidator` V1, which in turn points at `CertManager` V1 — `RegistrarConfig::run` resolves and hardcodes both addresses at lines 179–194 of `service.rs`.
2. Governance rotates `NitroValidator` to a new address (or `NitroValidator.certManager()` returns a new `CertManager`) via a normal on-chain upgrade to the `TEEProverRegistry`/`NitroValidator` contracts — no restart of the registrar occurs.
3. All subsequent `SignerManager` calls (`ensure_cert_cached`, `validate_cached_cert`, `check_revocations`) continue to use `CertManagerContractClient` bound to the old `CertManager` V1 address [9](#0-8) , causing new registrations to fail against the actual on-chain `TEEProverRegistry` (which now expects certs cached in `CertManager` V2), halting new TEE prover registration until the registrar is restarted.
