### Title
No rate-limiting/lockout on `CreateAPIToken` password re-check allows session-hijack attacker to brute-force account password - ([File: core/web/resolver/mutation.go])

### Summary
`Resolver.CreateAPIToken` re-verifies the user's password via `TestPassword` before issuing an API token, but on failure it returns a normal GraphQL payload (`InputErrors`) rather than an error that trips any lockout mechanism. There is no per-user/per-session attempt counter, backoff, or lockout in this resolver path, so an attacker who has stolen only a session cookie (e.g., via XSS) can repeatedly call the `createAPIToken` mutation with different password guesses.

### Finding Description
`CreateAPIToken` first authenticates the GraphQL session via `authenticateUser(ctx)` and `webauth.GetGQLAuthenticatedSession(ctx)`, which only requires a valid session cookie [1](#0-0) . It then calls `r.App.AuthenticationProvider().TestPassword(ctx, dbUser.Email, args.Input.Password)`, and on mismatch, records an audit event and returns a structured `InputErrors` payload (`"password": "incorrect password"`) rather than terminating the session or throwing a hard error [2](#0-1) . The mutation is reachable through the standard `/query` GraphQL endpoint protected by `webauth`/session-cookie authentication (see `core/web/auth/auth.go` `AuthenticateBySession`), which validates only session validity, not recency of authentication or any step-up factor [3](#0-2) . I was unable to find any lockout/backoff/rate-limiting logic specific to this resolver path in `core/web/router.go` or `core/web/resolver/mutation.go`; the `TestPassword` methods in `core/sessions/localauth/orm.go`, `core/sessions/ldapauth/ldap.go`, and `core/sessions/oidcauth/oidc.go` are simple credential comparisons (bcrypt/LDAP bind/OIDC check) without attempt counters. Login-path lockouts (e.g., in `core/web/user_controller.go`) are separate from this GraphQL mutation and do not apply here.

### Impact Explanation
If XSS or another vector yields a live session cookie without the password, `CreateAPIToken` (and similarly `DeleteAPIToken`, which follows the identical pattern) becomes an oracle for offline/online password guessing without triggering an account lockout that would otherwise stop repeated failed logins. A successful guess allows the attacker to mint a durable API token/secret, which persists beyond the lifetime of the stolen session cookie, escalating a transient session compromise into long-lived credential theft. This matches a credential/secret-disclosure and authentication-soundness impact class, though it requires the attacker to actually guess the correct password to fully exploit — the missing lockout is what removes a mitigating control rather than being a bypass by itself.

### Likelihood Explanation
Preconditions: attacker needs only a stolen/hijacked live session cookie (no password knowledge required to reach the check). The request is a simple repeated GraphQL mutation call, fully scriptable, and each attempt returns a normal 200 response distinguishing "incorrect password" from success, enabling straightforward brute-force automation. However, the overall likelihood of a full password compromise is bounded by password strength/entropy and by the requirement of first having a stolen session cookie via a viable XSS or similar vector — the resolver-side lack of lockout is a compounding weakness, not a standalone full account takeover.

### Recommendation
Add a per-user/per-session failed-attempt counter with lockout/backoff for `CreateAPIToken`/`DeleteAPIToken` password verification (mirroring the login lockout logic), and consider requiring re-authentication (fresh login) rather than a raw password field for sensitive actions like minting API tokens.

### Proof of Concept
1. Handler-level integration test using the GraphQL test harness (as in `core/web/resolver/api_token_test.go`): establish an authenticated session for user `alice`, then invoke `createAPIToken` N times (e.g., 20) with incorrect passwords in a loop.
2. Assert each call returns HTTP 200 with `InputErrors{password: "incorrect password"}` (per `mutation.go:1010-1013`), with no increasing delay, error code change, or session invalidation across attempts.
3. Assert `TestPassword`/the mock authentication provider (`core/sessions/mocks/authentication_provider.go`) is invoked once per attempt with no counter/lockout state persisted between calls.
4. Optionally assert that after N failures, a subsequent correct-password call still succeeds immediately, confirming the absence of lockout.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
