## Finding [1](#0-0)  When a `DeleteMember` request executes, `delete_member` only purges confirmation state for requests **originated by** the removed member — not requests that member merely **confirmed**. This breaks the invariant that "confirmations counted == confirmations from currently-live members," letting a request execute with fewer live-member approvals than `num_confirmations` requires.

### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing execution below threshold - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` (multisig2) and the `DeleteKey` action handler (multisig v1) only remove pending requests and confirmation records for requests **authored** by the removed member/key. They never scan other still-open requests to strip that member's confirmation entry from those requests' `confirmations` sets. Because `confirm()` counts raw set size against `num_confirmations` without validating that every entry in the set still belongs to a current member, a member who confirmed a request and is later removed continues to count toward that request's threshold indefinitely.

### Finding Description
`confirm()` decides execution purely by set cardinality: [2](#0-1)  `confirmations.len() as u32 + 1 >= self.num_confirmations`. This set is only cleaned up in two places: `remove_request` (called on execution/deletion of that specific request) and `delete_member`'s targeted cleanup, which is scoped to `r.member == member`, i.e., requests the removed member created: [3](#0-2) 

If member B confirms request R (created by member A) and is later removed via a separate, properly-authorized `DeleteMember{B}` request, `delete_member` will not touch R (since `R.member == A`, not `B`). R's `confirmations` set still contains B's entry. Any subsequent live members confirming R will have their confirmation added on top of B's stale one, so `confirmations.len()` reaches `num_confirmations` with strictly fewer *live* confirmers than intended.

The identical pattern exists in the older `multisig` contract's `DeleteKey` handling: [4](#0-3)  which also filters only on `r.signer_pk == pk` (the request's original signer), leaving that key's confirmations on other requests intact after the key is deleted.

This is precisely the "confirmations counted versus live members" custody binding: the equality `len(confirmations set) == number of live members who confirmed` is violated after any `DeleteMember`/`DeleteKey` action, for any request the removed member did not personally create.

### Impact Explanation
This is Critical: it results in a multisig request being executed with fewer live-member confirmations than the configured `num_confirmations` threshold. Any action gated by the multisig — including `Transfer` (moving NEAR out of the account) — can be pushed through by a minority of the live membership as long as a to-be-removed member had previously confirmed the pending request. This directly undermines the entire threshold-security guarantee of the multisig contracts.

### Likelihood Explanation
Reaching this state does not require compromising the multisig itself — it only requires normal operational sequencing: a member confirms an in-flight request, and then, through the contract's own supported `DeleteMember`/`DeleteKey` flow (e.g., because that member is departing, or is suspected compromised and is being removed for that exact reason), their confirmation is never retracted from other pending requests. This is a realistic and even likely occurrence in normal multisig lifecycle management (member rotation), not a contrived edge case.

### Recommendation
When a member/key is deleted, iterate all open requests' `confirmations` sets (not just requests it authored) and remove that member's/key's entry, or alternatively re-validate at `confirm()`-time / execution-time that every recorded confirmer in the set is still a current member (filtering the set against `self.members` before comparing to `num_confirmations`).

### Proof of Concept
Using `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`:
1. `A` calls `add_request` to create `R1` (e.g. `Transfer`). `confirmations[R1] = {}`.
2. `B` calls `confirm(R1)` → `confirmations[R1] = {B}` (1+1=2 < 3, not yet executed) — see [2](#0-1) .
3. Separately, `A`, `C`, `D` create and confirm a `DeleteMember{B}` request to threshold and it executes, calling `delete_member(promise, B)` — see [3](#0-2) . Since `R1.member == A` (not `B`), `R1`'s confirmations are untouched; `confirmations[R1]` still contains `B`.
4. Live members are now `{A, C, D}`.
5. `C` calls `confirm(R1)` → `confirmations[R1] = {B, C}`, len 2, `2+1=3 >= 3` → `R1` executes immediately.

`R1` (the `Transfer`) executes with only two live-member confirmations (`B`'s is stale/from a removed member, `C` is the only live confirmer besides the implicit +1 from the current call) against a configured threshold of 3 live confirmations, violating the multisig's core security guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
