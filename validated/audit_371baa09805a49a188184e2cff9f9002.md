### Title
A single APR0 withdrawal request permanently bricks `stopEpoch` once the vault APR is set non-zero - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of CVE-2024-25581 (an unexpected request type crashes a request-processing pipeline, DoS-ing the service): an unprivileged KYC'd lender can leave a stale `apr0TotalPrincipal` bucket that makes `prepareStopEpochWithApr0` revert on every subsequent `stopEpoch` whenever the configured APR is non-zero, freezing epoch finalization until the vault is forced back to a 0% APR epoch.

### Finding Description
`requestWithdraw` routes a withdrawal into the APR0 accounting bucket whenever `unscaledApr == 0` at request time: `_requestWithdrawApr0` increments `apr0TotalPrincipal` (`IdleCreditVault.sol:567-577`). At `stopEpoch`, the CDO calls `prepareStopEpochWithApr0`, which reverts with `NotAllowed` whenever the bucket is non-empty but `unscaledApr != 0` (`IdleCreditVault.sol:502-508`):

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
// APR0 principal is only valid while APR is 0 for that request lifecycle.
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

The problematic ordering:

1. Vault is configured with `unscaledApr == 0` (a supported mode — the whole `apr0Users`/`apr0RateByEpoch` machinery exists for it).
2. During a buffer phase, any lender holding tranche tokens calls `cdoEpoch.requestWithdraw(...)`, which calls `IdleCreditVault.requestWithdraw`, mints a receipt and calls `_requestWithdrawApr0`, setting `apr0TotalPrincipal > 0` (`IdleCreditVault.sol:285-286, 567-577`).
3. The manager later (honestly, per role rules) raises the APR via `setAprs(_unscaledApr > 0, _apr > 0)` / `setAprsWithBuffer` for the next epoch (`IdleCreditVault.sol:206-220`).
4. From then on, every `stopEpoch`/`stopEpochWithDuration` reverts inside `prepareStopEpochWithApr0` — the epoch can never be closed at any non-zero APR while the stale bucket exists.

There is no user- or manager-facing path to clear `apr0TotalPrincipal` without executing `prepareStopEpochWithApr0` itself (it is only zeroed at `IdleCreditVault.sol:540`, after the revert check). The requesting user cannot cancel their request, and `withdrawsRequests`/`apr0Users` cannot be deleted externally. The guard at `IdleCreditVault.sol:263-271` (loss-adjusted receipts) and the `_onlyIdleCDO` checks do not prevent this state.

### Impact Explanation
- **Temporary freezing of all user funds**: the running epoch cannot be stopped, so no deposits, withdrawals, or claims settle until the manager capitulates and runs a 0% APR epoch. If governance/manager refuses or is slow, the freeze is indefinite.
- **Forced denial of yield**: even after recovery, the vault must burn one full epoch at `unscaledApr == 0` to clear the bucket, denying all LPs an epoch of interest. An attacker can repeat the attack each buffer phase (request withdraw while `unscaledApr == 0`), keeping the vault pinned at 0% APR indefinitely — a permanent denial of yield at negligible cost (management fee on a request they can later claim).
- The quantified loss per incident is one epoch of interest on the full TVL, e.g., at 10% APR on $10M TVL ≈ $27k per epoch-cycle of downtime, repeatable.

### Likelihood Explanation
- Attacker requirements are minimal: a KYC-passing lender (explicitly in-scope) with any tranche balance, acting during the buffer phase of an APR0 vault. The request is a normal, legitimate user call — the "unexpected request type" that breaks the pipeline, directly mirroring the AXFR-over-DoH bug class.
- It is **not permanent** in the strict sense: the manager can unstick the vault by setting `setAprs(0, 0)` for one epoch (the bucket then closes at `IdleCreditVault.sol:540` since `_apr0NetInterest` is zero when realized interest ≤ fees). The finding is therefore a temporary-freeze / forced-yield-denial, not insolvency.
- Uncertainty: I could not fully confirm the `stopEpoch` call site in `IdleCDOEpochVariant.sol` (grep returned only match counts, not line content), so the exact revert propagation path through the CDO is inferred from the `_onlyIdleCDO` guard on `prepareStopEpochWithApr0`. It is also unknown whether this APR-transition interaction was previously acknowledged in audit notes.

### Recommendation
Either disallow `setAprs`/`setAprsWithBuffer` to a non-zero `unscaledApr` while `apr0TotalPrincipal != 0` (revert at config time instead of inside `stopEpoch`, giving the manager immediate feedback), or migrate/expire the stale bucket: when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, treat the outstanding APR0 principal as settled at rate 0 (`apr0RateByEpoch[epochNumber] = 0; apr0TotalPrincipal = 0`) rather than reverting, so the epoch can close and users settle at their requested 0% terms.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testPocApr0StaleBucketBlocksStopEpoch() external {
  IdleCreditVault cv = IdleCreditVault(address(strategy));

  // Vault configured at APR 0
  vm.prank(manager);
  cv.setAprs(0, 0);

  // Attacker: KYC'd lender deposits during buffer, then requests withdraw
  address attacker = makeAddr("attacker");
  _depositWithUser(attacker, 1_000 * ONE_SCALE, true);
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(0, address(AAtranche));
  assertGt(cv.apr0TotalPrincipal(), 0, "apr0 bucket not seeded");

  // Honest manager raises APR for the next epoch
  vm.prank(manager);
  cv.setAprs(10e18, 10e18);

  _startEpochAndCheckPrices(0);

  // Every stopEpoch now reverts inside prepareStopEpochWithApr0 (NotAllowed)
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
  vm.prank(manager);
  cdoEpoch.stopEpoch(0, 0);

  // Vault is stuck: epoch cannot close while unscaledApr != 0 and apr0TotalPrincipal > 0
}
```
