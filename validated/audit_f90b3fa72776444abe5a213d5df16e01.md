### Title
Global (non-per-sender) `maxCacheSize` limit in `requestCache` allows any low-privileged sender to exhaust the shared cache and deny service to other senders - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces `maxCacheSize` as a single global counter (`len(c.cache) >= int(c.maxCacheSize)`) with no per-sender accounting, so any sender able to submit distinct `MessageId`s can fill the shared cache and cause `NewRequest` to fail for all other senders until entries time out. The test `TestRequestCache_MaxSize` in `core/services/gateway/handlers/common/requestcache_test.go:125-141` demonstrates the mechanics: two entries fill a `maxCacheSize=2` cache and any subsequent call (from the same or another sender) returns `"request cache is full"`.

### Finding Description
`requestCache.cache` is a single `map[globalId]*pendingRequest[T]` shared across all senders [1](#0-0) . `NewRequest` checks capacity with a single global comparison, `len(c.cache) >= int(c.maxCacheSize)`, before adding the new entry keyed by `{sender, id}` [2](#0-1) . There is no quota, weight, or limit applied per-sender inside this function - any caller who can produce enough distinct `(sender, messageId)` pairs can drive `len(c.cache)` up to `maxCacheSize`, after which every other caller's `NewRequest` (regardless of sender) returns `"request cache is full"` until entries are consumed/timed out.

However, `requestCache` itself does not perform any authentication, and reachability into it depends entirely on the calling handler. Searching the repo, `common.NewRequestCache`/`RequestCache[T]` is only referenced in `requestcache.go` and its own test file (`requestcache_test.go`) - no production gateway handler (e.g., `capabilities/handler.go`, `capabilities/v2/http_trigger_handler.go`, `vault/handler.go`) currently wires up and calls this generic cache. The handlers that are actually reachable from gateway/user-facing endpoints implement independent, purpose-built protections instead: e.g. `vault` and `capabilities` handlers use `ratelimit.RateLimiterConfig` with explicit `PerSenderRPS`/`PerSenderBurst` fields [3](#0-2) , and the HTTP Trigger handler (`capabilities/v2`) enforces per-workflow-owner rate limiting via `userRateLimiter.AllowErr` scoped by `contexts.WithCRE(ctx, contexts.CRE{Owner: ...})` before any shared resource is touched [4](#0-3) .

Because no live, attacker-reachable code path was found that invokes this `requestCache` implementation from an unauthenticated/low-privileged gateway or node-API request, the described exhaustion — while structurally real within the function's own logic (confirmed by the maxCacheSize/global-counter design and the existing `TestRequestCache_MaxSize` test) — cannot currently be tied to a concrete authenticated-attacker request path in this codebase snapshot. This is a design gap in a shared, generic caching primitive rather than a demonstrated exploitable route from an external, low-privileged client into a specific victim's request cache today.

### Impact Explanation
If/when a handler wires `requestCache` directly per-DON/service without adding its own per-sender limiting in front of it, the lack of per-sender quoting inside `NewRequest` means one sender's flood of distinct `MessageId`s can starve capacity for all other senders sharing that same `requestCache` instance, matching an availability/DoS impact class. This is scoped to denial-of-service on the shared cache resource, not privilege escalation, key disclosure, or fund movement.

### Likelihood Explanation
Exploitability is unproven against the current codebase because no production caller of `common.NewRequestCache` was located; all identified live handlers use separate per-sender rate limiters (`ratelimit.RateLimiterConfig`, `userRateLimiter`) that would throttle a sender long before `maxCacheSize` could be reached with attacker-controlled traffic. Without a concrete reachable entry point where an unauthenticated/low-privileged actor can call `NewRequest` directly and bypass those rate limiters, likelihood in the current shipped code is low/unconfirmed.

### Recommendation
Add per-sender accounting to `requestCache` (e.g., a `map[string]int` of in-flight requests per `sender`, enforced alongside the global `maxCacheSize`) so that no single sender can consume more than a configured share of total cache capacity, independent of whether upstream callers already apply rate limiting. This closes the gap defensively even if a future handler adopts this generic cache without its own per-sender limiter.

### Proof of Concept
Extend `core/services/gateway/handlers/common/requestcache_test.go` with a table test: create `NewRequestCache[T](timeout, maxCacheSize=N)`; loop `N` times calling `NewRequest` with a fixed attacker `Sender` and unique `MessageId`s; then call `NewRequest` with a distinct victim `Sender`/`MessageId` and assert it returns `"request cache is full"` — this confirms the global-counter behavior already visible in `TestRequestCache_MaxSize`. Note: this PoC validates the function-level design gap only; it does not by itself demonstrate an externally reachable exploit path, since no current production handler was found wiring unauthenticated/low-privileged traffic directly into a shared `requestCache` instance without its own per-sender rate limiter in front.

		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)

		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")

			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
