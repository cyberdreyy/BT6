### Title
Missing Zero-Address Validation on Sui Recipient in Bridge Deposit Functions — (`bridge/evm/contracts/SuiBridge.sol`, `bridge/evm/contracts/SuiBridgeV2.sol`)

### Summary

`bridgeERC20`, `bridgeETH`, `bridgeERC20V2`, and `bridgeETHV2` accept a `bytes memory recipientAddress` parameter representing the destination Sui address. The only validation performed is a length check (`recipientAddress.length == SUI_ADDRESS_LENGTH`). There is no check that the 32 bytes are not all zeros. A caller who passes 32 zero bytes as the recipient will lock their tokens in the vault permanently, because the resulting `TokensDeposited` event targets the Sui system address `@0x0`, which the Sui bridge cannot deliver to a normal user, and there is no EVM-side rollback mechanism.

### Finding Description

In `SuiBridge.sol`, both deposit functions validate only the byte-length of the Sui recipient address:

```solidity
// SuiBridge.sol L141-144
require(
    recipientAddress.length == SUI_ADDRESS_LENGTH,
    "SuiBridge: Invalid recipient address length"
);
```

A 32-byte all-zero payload (`bytes(new bytes(32))`) passes this check. The contract then:
1. Transfers the caller's tokens into the vault via `SafeERC20.safeTransferFrom`.
2. Emits `TokensDeposited` with the zero Sui address as `recipientAddress`.
3. Increments the nonce.

The same pattern is present in `SuiBridgeV2.sol` for `bridgeERC20V2` and `bridgeETHV2`.

By contrast, the internal `_transferTokensFromVault` (withdrawal path) does check `require(tokenAddress != address(0), ...)` for the EVM token contract address, but no analogous check exists for the Sui-side recipient on the deposit path.

### Impact Explanation

Once the `TokensDeposited` event is emitted with a zero Sui recipient, bridge validators observe it and attempt to execute the corresponding Sui-side mint/transfer to `@0x0`. The Sui system address `@0x0` is not a normal user account; tokens sent there are unrecoverable by any ordinary user. Because the EVM bridge has no refund or cancellation path for a deposited-but-undeliverable transfer, the deposited tokens remain permanently locked in the vault. This constitutes a **permanent fund lock** reachable from a public, unprivileged caller.

### Likelihood Explanation

Any user who calls `bridgeERC20` or `bridgeETH` (or their V2 equivalents) with a 32-byte zero `recipientAddress` triggers the issue. This can happen accidentally (e.g., a frontend bug that fails to populate the address field) or deliberately (griefing one's own funds). No special privilege is required.

### Recommendation

Add an explicit non-zero check on the `recipientAddress` bytes in all four deposit functions, for example:

```solidity
require(
    recipientAddress.length == SUI_ADDRESS_LENGTH,
    "SuiBridge: Invalid recipient address length"
);

bool isZero = true;
for (uint256 i = 0; i < SUI_ADDRESS_LENGTH; i++) {
    if (recipientAddress[i] != 0) { isZero = false; break; }
}
require(!isZero, "SuiBridge: Zero recipient address");
```

Apply the same guard in `SuiBridgeV2.sol`.

### Proof of Concept

```solidity
// Attacker (ordinary user) calls:
bridge.bridgeERC20(
    BridgeUtils.ETH,
    1 ether,
    new bytes(32),   // 32 zero bytes — passes length check, fails no zero check
    0                // supported destination chain
);
// Result:
// - 1 ETH worth of WETH transferred to vault (irreversible)
// - TokensDeposited emitted with recipientAddress = 0x000...000 (Sui zero address)
// - Nonce incremented; message cannot be cancelled
// - Sui validators attempt delivery to @0x0; transfer fails or goes to unrecoverable system address
// - Funds permanently locked in vault
