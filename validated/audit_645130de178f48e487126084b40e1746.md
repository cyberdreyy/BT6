### Title
Any caller of `LockupFactory::create` can override `whitelist_account_id` for vesting-locked lockups, letting the foundation's staking-pool safety guarantee be bypassed - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` accepts an unvalidated, caller-supplied `whitelist_account_id: Option<ValidAccountId>` and forwards it directly as the deployed lockup contract's `staking_pool_whitelist_account_id`, with no restriction requiring it to be the Foundation's official whitelist contract — even when a `vesting_schedule` is attached (i.e., when the NEAR Foundation retains a legal/economic claim over unvested tokens).

### Finding Description
The lockup contract's core safety invariant, as documented in `whitelist/README.md`, is: *"only approved (whitelisted) accounts of staking pool contracts can receive delegated tokens from lockup contracts,"* so that the lockup (and, in the vesting case, the Foundation) can always recover delegated funds. This guarantee is enforced entirely inside `LockupContract::select_staking_pool`, which calls `ext_whitelist::is_whitelisted` against `self.staking_pool_whitelist_account_id`: [1](#0-0) 

That field is set once at `new()` and never re-validated: [2](#0-1) 

The trust boundary is supposed to be: only the NEAR Foundation-controlled whitelist contract decides which staking pools are safe to delegate to. However, `LockupFactory::create` — callable by **any unprivileged account** that simply attaches the minimum deposit — lets the caller supply an arbitrary `whitelist_account_id`, which silently overrides the factory's own configured (presumably Foundation-vetted) whitelist: [3](#0-2) 

Critically, this override is accepted even when `vesting_schedule.is_some()`, i.e., even when the Foundation is set as the entity entitled to reclaim unvested tokens on termination: [4](#0-3) 

The equality that should hold is:
`staking_pool_whitelist_account_id used by lockup == the Foundation's official whitelist contract, whenever the lockup holds Foundation-reclaimable (vesting) funds`.

Because the factory copies the caller-supplied `whitelist_account_id` unchanged into `LockupArgs` and never asserts it equals the factory's own `self.whitelist_account_id` when `vesting_schedule.is_some()`, this equality is broken: any account can deploy a vesting lockup whose "whitelist" is a contract it fully controls (e.g., one that unconditionally returns `true` from `is_whitelisted`).

### Impact Explanation
This falls under "a wrongly whitelisted or wrongly parameterised deployment" (Critical). Once the owner of such a lockup calls `select_staking_pool` with an attacker-controlled "staking pool" account, the malicious contract passes the (attacker's own) whitelist check and becomes the trusted delegation target. The owner can then `deposit_and_stake` the entire lockup balance — including tokens still subject to the vesting schedule and the Foundation's termination rights — into that malicious "staking pool," which need not honor the staking-pool standard's guarantee that delegated tokens can always be recovered. When the Foundation later attempts `terminate`/withdrawal of unvested tokens, the funds are unrecoverable because they sit in a pool that was never actually vetted, permanently freezing/losing tokens that were meant to be reclaimable by the Foundation.

### Likelihood Explanation
Likelihood is high for any unprivileged actor: `LockupFactory::create` requires only the minimum attached deposit (`MIN_ATTACHED_BALANCE`) — no special permission — and the `whitelist_account_id` override parameter is a plain optional argument with zero validation against `vesting_schedule` or against the factory's configured whitelist.

### Recommendation
In `LockupFactory::create` (`lockup-factory/src/lib.rs`), disallow overriding `whitelist_account_id` whenever `vesting_schedule.is_some()` — force use of `self.whitelist_account_id` (the Foundation-configured whitelist) in that case — or remove the override parameter entirely and always use the factory's configured whitelist account ID for all lockups, matching the documented security guarantee.

### Proof of Concept
1. Attacker deploys a trivial "whitelist" contract exposing `is_whitelisted(staking_pool_account_id) -> bool` that always returns `true`, and a "staking pool" contract that accepts deposits/stake but withholds withdrawals.
2. Attacker calls `LockupFactory::create` with `owner_account_id = attacker`, `vesting_schedule = Some(...)` (making the Foundation the terminator), and `whitelist_account_id = Some(attacker_whitelist)`. [3](#0-2) 
3. The deployed `LockupContract` is initialized with `staking_pool_whitelist_account_id = attacker_whitelist` instead of the Foundation's whitelist.
4. As owner, attacker calls `select_staking_pool(attacker_pool)`; the call to `ext_whitelist::is_whitelisted` against `attacker_whitelist` returns `true`, so `on_whitelist_is_whitelisted` accepts it: [5](#0-4) 
5. Attacker calls `deposit_and_stake` to move the full (including unvested) lockup balance into `attacker_pool`.
6. When the Foundation later calls `terminate`, it cannot recover the unvested portion because the malicious pool refuses to release funds — the tokens are permanently frozen/lost from the Foundation's perspective, despite the vesting schedule's guarantee.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };
