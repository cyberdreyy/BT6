### Title
Pending junior withdrawals escape first-loss absorption through aggregate receipt accounting - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.requestWithdraw` removes tranche identity when it converts a withdrawal into a pending receipt, while `previewLossAdjustedWithdrawFunds` distributes a realized loss between the entire pending bucket and active positions pro rata. A BB lender can therefore convert junior exposure into an aggregate receipt before a loss is realized, receive most of the receipt back, and force the remaining loss onto active AA positions even when no active BB principal remains. [1](#0-0) [2](#0-1) 

### Finding Description
When a user requests a withdrawal, the strategy burns the CDO’s principal-backed strategy tokens and mints the user a receipt, but only records the aggregate receipt amount in `pendingWithdraws`, `withdrawsRequests`, and `withdrawsRequestsByEpoch`. [1](#0-0) 

During `stopEpochWithDuration`, `previewLossAdjustedWithdrawFunds` computes `pendingLoss = _lossAmount * pendingBasis / (activeBasis + pendingBasis)`, funds the pending bucket at the resulting common recovery ratio, and returns the remainder as `activeLoss`. [3](#0-2) 

`collectWithdrawFunds` then stores that common receipt price in `lossRecoveryPriceByEpoch[epochNumber]`, while `IdleCDOEpochVariant` burns only `activeLoss` and crystallizes it through the ordinary active-tranche waterfall. [4](#0-3) [5](#0-4) 

A receipt holder later receives `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, regardless of whether the receipt originally represented AA or BB exposure. [6](#0-5) 

For example, with 1,000 active AA units and one pending BB receipt for 100 units, a 100-unit loss produces approximately 9.09 units of pending loss and 90.91 units of active loss. The pending BB holder recovers approximately 90.91 units, while active AA NAV loses approximately 90.91 units; under the tranche waterfall, the junior BB receipt should absorb the entire 100-unit loss first and AA should remain whole. [7](#0-6) [8](#0-7) 

### Impact Explanation
This breaks the junior-first loss invariant and transfers value from active AA holders to pending BB receipt holders. In the example above, the attacker extracts approximately 90.91% of a junior position that should have been fully impaired, while senior holders absorb approximately 90.91 units of loss. [2](#0-1) 

The impact scales with the BB withdrawal size: a pending BB receipt for most of the junior NAV can convert nearly all of its first-loss exposure into a pro-rata claim against total pool basis. [1](#0-0) 

### Likelihood Explanation
The attacker only needs to be a permitted tranche holder and call the ordinary `requestWithdraw` path before the honest manager settles an epoch with a nonzero `_lossAmount`. [9](#0-8) 

The guards in the relevant path do not prevent this: the pending receipt is legally created, the loss is below total claim basis, and `previewLossAdjustedWithdrawFunds` intentionally treats all pending receipts as one identity-less bucket. [2](#0-1) 

Likelihood is conditional on the explicit-loss settlement path being used, but no malicious owner, manager, borrower, or privileged action is required. [10](#0-9) 

### Recommendation
Preserve tranche identity for pending withdrawal receipts, at minimum by tracking separate pending AA and BB bases per epoch. Apply realized losses to pending and active BB claims before pending or active AA claims, or otherwise define and implement a waterfall-equivalent ordering for receipt claims. [11](#0-10) 

The recovery price should therefore be recorded per tranche class or calculated from separate AA/BB pending bases, rather than using one `lossRecoveryPriceByEpoch` for all pending receipts. [12](#0-11) 

### Proof of Concept
The following Foundry scenario uses the existing `IdleCreditVault.t.sol` fixture assumptions: `attacker` and `victim` are KYC-passing users, fees are disabled for clarity, APR is zero, and the honest manager later records a realized loss.

```solidity
// test/foundry/IdleCreditVault.t.sol
function testPendingBBEscapesFirstLossThroughAggregateReceiptBucket() external {
    address victim = makeAddr("victim-aa");
    address attacker = makeAddr("attacker-bb");

    uint256 aaAmount = 1_000 * ONE_SCALE;
    uint256 bbAmount = 100 * ONE_SCALE;
    uint256 lossAmount = 100 * ONE_SCALE;

    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0);
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    _depositWithUser(victim, aaAmount, true);
    _depositWithUser(attacker, bbAmount, false);

    // Convert all junior exposure into an identity-less pending receipt.
    vm.prank(attacker);
    uint256 attackerBasis = cdoEpoch.requestWithdraw(0, address(BBtranche));
    assertEq(attackerBasis, bbAmount);

    _startEpochAndCheckPrices(0);

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    (uint256 pendingToFund,) =
        vault.previewLossAdjustedWithdrawFunds(lossAmount);

    // The aggregate formula gives the pending BB bucket a ~90.91% recovery.
    uint256 expectedPendingLoss =
        lossAmount * attackerBasis / (aaAmount + attackerBasis);
    assertEq(pendingToFund, attackerBasis - expectedPendingLoss);

    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest() + pendingToFund);

    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, 30 days, lossAmount);

    uint256 attackerBefore = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    uint256 attackerPayout = underlying.balanceOf(attacker) - attackerBefore;
    assertApproxEqAbs(attackerPayout, pendingToFund, 5);

    // Waterfall-consistent result would be:
    // attackerPayout == 0 and AA NAV/price unchanged after the junior loss.
    // Actual result: pending BB keeps ~90.91 units while active AA absorbs ~90.91.
    assertGt(attackerPayout, 0);
    assertLt(cdoEpoch.priceAA(), ONE_TRANCHE);
}
```

```text
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```

```text
  function requestWithdraw(uint256 _amount, address _tranche) external returns (uint256 _underlyings) {
    _checkTranche(_tranche);
    _checkNotAllowed(
      (_tranche == AATranche ? !allowAAWithdrawRequest : !allowBBWithdrawRequest) ||
      !isWalletAllowed(msg.sender)
    );
  
    // we check if there are donated assets to the pool and transfer them to the feeReceiver if any
    _skimDonatedAssets();

    // we trigger an update accounting to check for eventual losses
    _updateAccounting();

    IdleCreditVault creditVault = IdleCreditVault(strategy);
    if (_amount == 0) {
      _amount = _userTrancheBal(msg.sender, _tranche);
    }
    _underlyings = _trancheToUnderlyings(_amount, _tranche);

    // Programmable borrower deployments do not support instant withdrawals.
    // If apr decresed wrt last epoch, request instant withdraw and burn tranche tokens directly
    // we compare unscaled aprs
    if (_isInstantWithdrawEnabled()) {
      uint256 currentApr = creditVault.unscaledApr();
      if (lastEpochApr > (currentApr + instantWithdrawAprDelta)) {
        // burn strategy tokens from cdo and mint an equal amount to msg.sender as receipt
        creditVault.requestInstantWithdraw(_underlyings, msg.sender);
        // burn tranche tokens and decrease NAV
        _withdrawOps(_amount, _underlyings, _tranche);
        return _underlyings;
      }
    }

    uint256 principal = _underlyings;
    (uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
    uint256 totalFees = _totalWithdrawFees(principal, interest);
    // user is requesting principal + interest minus upfront management fee and net performance fee
    _underlyings = principal + interest - totalFees;
    // add expected fees to pending withdraw fees counter
    pendingWithdrawFees += totalFees;

    /// if there is an AA withdrawal the overperformance that the amount withdrawed would have generated for BB tranches
    /// is saved in interestForOverUnderPerformance. This is used to calculate the interest that should be added to the
    /// expectedEpochInterest at the startEpoch.
    /// If there is a BB withdrawal this amount is subtracted from the expectedEpochInterest
    interestForOverUnderPerformance += diff;

    // The receipt is fixed now and leaves live NAV. Charge management fees upfront
    // for the time it waits outside live NAV: remaining buffer plus the next epoch.
    creditVault.requestWithdraw(_underlyings, msg.sender, principal);
    // burn tranche tokens and decrease NAV without interest for the next epoch as it was not yet counted in NAV
    _withdrawOps(_amount, principal, _tranche);
```
