### Title
Transferable withdraw-request receipt tokens are functionally unspendable for anyone but the original requester - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
In `IdleCreditVault.requestWithdraw` and `requestInstantWithdraw`, the vault burns the CDO's strategy tokens and mints a fresh ERC20 strategy-token receipt to the requesting user (`_mint(_user, _amount)`), while the actual claim entitlement is recorded in per-user mappings (`withdrawsRequests[_user]`, `instantWithdrawsRequests[_user]`, `apr0Users[_user]`, `lastWithdrawRequest[_user]`). Because claimability is bound to the requester's ledger entries — not to possession of the receipt token — an attacker can transfer (sell, deposit as collateral, or send to a vendor/integration that credits `balanceOf`) receipt tokens that the recipient can never redeem. This is the direct analog of the Monero `locked_transfer` bug: a balance that verifies as valid but is functionally unspendable for its holder.

### Finding Description
- `requestWithdraw` mints a receipt including interest: `_burn(msg.sender, _principal)` then `_mint(_user, _amount)` where `_amount` is principal + expected interest (`IdleCreditVault.sol:271-275`).
- `requestInstantWithdraw` does the same for instant receipts (`IdleCreditVault.sol:360-375`).
- `claimWithdrawRequest` / `_claimFundedWithdrawRequest` compute the payout exclusively from per-user state — `withdrawsRequests[_user]`, `apr0Users[_user]`, `lastWithdrawRequest[_user]` — and burn the receipt from `_user` (`IdleCreditVault.sol:301-349`). `claimInstantWithdrawRequest` pays `instantWithdrawsRequests[_user]` and burns it (`IdleCreditVault.sol:380-393`).
- Consequence: whoever receives the receipt tokens by transfer has no ledger entry, so their claim pays 0 (or reverts); the original requester, having moved the tokens, can no longer pass `_burn(_user, normalAmount + apr0PrincipalAmount)` at line 343 — their own claim is bricked unless the tokens are returned. Meanwhile `pendingWithdraws` / `pendingInstantWithdraws` remain elevated forever, so each `stopEpoch` keeps reserving borrower funds for a receipt that can never be collected, permanently freezing that slice of vault liquidity (`collectWithdrawFunds`, `IdleCreditVault.sol:411-430`).
- The receipt minted in `requestWithdraw` includes accrued interest (`_amount > _principal`), so the attacker holds a token whose face value already exceeds what was burned — a transferable, inflated-yet-unspendable receipt, matching the "credit the balance, can't spend it" pattern.

### Impact Explanation
- Any integrator, OTC buyer, or lending market that values the strategy-token receipt at 1:1 underlying (it is indistinguishable from funded strategy tokens) can be given permanently unspendable tokens — the attacker extracts real value and leaves the counterparty holding locked receipts (CVSS-style impact: theft by deception / functional burning).
- Internally, orphaned `pendingWithdraws` permanently inflates the borrower-facing liability that `stopEpoch` must source; those underlyings sit in the vault backing a receipt whose burn path is dead — permanent freezing of the funded claim amount.
- Broken invariant: "one receipt, one payout" and fungibility of strategy tokens — the token implies a claim the ledger does not honor.

### Likelihood Explanation
- Requires only that `IdleCreditVault` strategy tokens are transferable like a normal ERC20 (i.e., `_transfer` does not block holder-to-holder moves). If the `_transfer` hook already restricts transfers to the CDO, the vector collapses — this must be confirmed; I was unable to fully verify the `_transfer` override in the available context.
- The attacker needs only to be an allowed (KYC'd) lender requesting a normal/instant withdrawal during a running epoch, then transferring the minted receipt. No privileged role involved; the honest borrower/manager keep funding `pendingWithdraws` each epoch.
- Caveat: if integrators treat the receipt as worthless or transfers are blocked, likelihood drops to a self-grief (still leaves locked `pendingWithdraws` if a user accidentally moves receipts).

### Recommendation
- Make withdraw-request receipts non-transferable (override `_transfer`/`_beforeTokenTransfer` to reject moves from users other than `idleCDO`/burn path), or
- Track claims by token ownership instead of by the original requester (transfer the ledger entries on `_transfer`, or issue a dedicated non-transferable receipt token), and
- Add a rescue path so orphaned receipts can be re-associated or burned by the ledger owner to release `pendingWithdraws`.

### Proof of Concept
Foundry fork sketch (standard epoch variant, APR0 disabled):

```solidity
// setup: deploy cdoEpoch, strategy (IdleCreditVault), AAtranche, underlying (USDC)
uint256 amount = 100_000e6;
// attacker is KYC-allowed
address attacker = makeAddr('attacker');
address victim   = makeAddr('victim'); // integrator / buyer of receipt tokens

deal(address(underlying), attacker, amount);
vm.startPrank(attacker);
underlying.approve(address(cdoEpoch), amount);
uint256 mintedAA = cdoEpoch.depositAA(amount);
vm.stopPrank();

// buffer -> epoch 0 running
vm.prank(manager); cdoEpoch.startEpoch();
// stop epoch 0
vm.warp(cdoEpoch.epochEndDate() + 1);
_dealAndApproveBorrower();
vm.prank(manager); cdoEpoch.stopEpoch(0, apr);

// attacker requests withdraw during buffer -> receipt minted (principal + interest)
vm.prank(attacker);
uint256 receiptAmt = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche));
// strategy-token receipt sits on attacker; ledger entry under attacker
assertGt(IERC20(strategyToken).balanceOf(attacker), 0);

// attacker "sells" the receipt to victim
vm.prank(attacker);
IERC20(strategyToken).transfer(victim, receiptAmt);

// epoch 1 runs and stops -> claim becomes available
vm.prank(manager); cdoEpoch.startEpoch();
vm.warp(cdoEpoch.epochEndDate() + 1);
_dealAndApproveBorrower();
vm.prank(manager); cdoEpoch.stopEpoch(0, apr);

// 1) victim holds valid balance but has no ledger entry -> receives 0 / reverts
vm.prank(victim);
cdoEpoch.claimWithdrawRequest(); // withdrawsRequests[victim] == 0

// 2) original requester cannot claim: _burn(attacker, ...) underflows
vm.prank(attacker);
vm.expectRevert(); // ERC20: burn amount exceeds balance
cdoEpoch.claimWithdrawRequest();

// 3) pendingWithdraws keeps the funded amount locked in the vault forever
assertEq(strategy.pendingWithdraws() >= receiptAmt, true);
```

If `strategyToken.transfer` reverts due to a `_transfer` restriction, the external-leg portion is invalid; the residual issue is that an accidental/forced receipt move permanently bricks the claim and freezes `pendingWithdraws`. Confirm `_transfer` behavior before severity assignment.
