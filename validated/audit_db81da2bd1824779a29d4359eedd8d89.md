### Title
Stale-epoch instant-withdraw receipts bypass the default recovery haircut and claim at par (or freeze) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug class is an inconsistent parse/keying: the same artifact is resolved under two different identities, so cached value is routed to the wrong principal. The analog lives in the instant-withdraw recovery path of `IdleCreditVault`. Receipts are recorded under the epoch in which they were requested (`instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`), but default finalization always reads the *current* `epochNumber`. Because `epochNumber` is incremented on every `stopEpoch` (inside `deposit()`, contracts/strategies/idle/IdleCreditVault.sol:607-611), an instant receipt requested in epoch N that is left unfunded across the epoch boundary becomes keyed to epoch N while `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` look only at epoch N+1. The receipt then falls through to the unfunded-agnostic claim path and is paid at par while genuine default-epoch claimants are haircut — or, if the strategy holds insufficient non-reserve balance, the claim permanently reverts.

### Finding Description
1. `requestInstantWithdraw` stores receipt basis under the epoch active at request time: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (lines 367-374). `pendingInstantWithdraws` is the still-unfunded remainder, and the code explicitly contemplates it staying non-zero across `stopEpoch` (comment at lines 636-640, `_defaultPrefundedInstantReserve()` at 715-722).
2. At default finalization, `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *finalization* epoch (line 647). A receipt minted in the prior epoch contributes to `pendingInstantWithdraws` (so `defaultInstantWithdrawsFinalized` is set, line 696) but contributes **zero** to `pendingBasis`, so it does not dilute `defaultRecoveryPrice`.
3. Symmetrically, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844), which is empty for the stale-epoch receipt. It returns 0, and execution continues at line 387: `amount = instantWithdrawsRequests[_user]; _burn(_user, amount); ... _transferFundedClaim(_user, amount)` — a full par payout with no recovery multiplier applied. The normal-request equivalent cannot straddle epochs because `collectWithdrawFunds` closes `pendingWithdraws` every `stopEpoch`; instant receipts have no such per-epoch cleanup.
4. `_transferFundedClaim` only protects `defaultRecoveryReserve` (lines 899-905); any other underlying held by the strategy (e.g., borrower repayments for the new epoch sent via `sendInterestAndDeposits`, or residual funded amounts) is spendable at par by the stale receipt holder.

Broken invariant: "one receipt, one haircut" — all unfunded claims against a defaulted epoch must share `defaultRecoveryPrice`. Here, an identical unfunded claim resolves under the wrong epoch key and either escapes the haircut entirely or is unclaimable if no non-reserve balance exists.

### Impact Explanation
Direct theft / unfair recovery distribution. If the strategy holds non-reserve underlying `B >= R` (stale receipt amount) after finalization, the attacker claims `R` at par instead of `R * defaultRecoveryPrice / 1e18`, extracting `(1 - recoveryPrice) * R` more than entitled. That excess is funded by balance that backs other claimants or active tranche holders. Conversely, if `balance - reserve < R`, `_transferFundedClaim` reverts and the receipt is permanently frozen (DoS with fund impact). Magnitude is bounded by the unfunded instant-withdraw amount crossing the epoch boundary, which can be the attacker's entire queued position.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled (`allowInstantWithdraw`, `_isInstantWithdrawEnabled` — i.e., APR dropped by more than `instantWithdrawAprDelta`, an unprivileged-observable state); (b) the attacker's instant receipt remains unfunded at `stopEpoch` (partial prefunding is explicitly supported, e.g., failed epoch-start funding); (c) the borrower later defaults and `finalizeDefault`/`finalizeDefaultRecovery` runs in a subsequent epoch. All steps sequence around honest privileged calls; the attacker is just an `isWalletAllowed`-passing tranche holder. Guards that do not stop it: the `pendingInstantWithdraws != 0` check in `_ensureDefaultRecoveryInitialized` only gates *first* initialization; `requestWithdraw`'s loss-epoch guard covers only `withdrawsRequestsByEpoch`/APR0, not instant receipts; nothing reconciles the epoch key drift.

### Recommendation
Key instant-receipt recovery by the request epoch actually stored, not the finalization epoch. Concretely: in `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest`, iterate/record the outstanding instant epochs (or fold any `pendingInstantWithdraws` remainder into `pendingWithdraws`/a dedicated stale-epoch bucket at `stopEpoch`), so every unfunded instant receipt is both counted in `totalBasis` and haircut by `defaultRecoveryPrice`. At minimum, track `lastInstantRequestEpoch[_user]` analogous to `lastWithdrawRequest` and route it through the recovery path.

### Proof of Concept
Foundry fork PoC (mainnet fork as in `test/foundry/IdleCreditVault.t.sol`, `vm.createSelectFork('mainnet', ...)`):

```solidity
function testStaleEpochInstantReceiptBypassesRecoveryHaircut() external {
    // Setup mirrors existing tests: deposit AA, enable instant withdraws, epoch running.
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    _depositWithUser(victim,   10_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 1. Epoch N: APR drops by > instantWithdrawAprDelta; attacker requests instant withdraw.
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(lowApr, lowApr); // triggers instant path
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attackerBal, address(AAtranche)); // routes to requestInstantWithdraw
    uint256 reqEpoch = strategy.epochNumber(); // N
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, reqEpoch), receiptAmt);

    // 2. stopEpoch N: borrower funds only part of pendingInstantWithdraws
    //    (collectInstantWithdrawFunds pulls less than the queue) -> epochNumber -> N+1,
    //    pendingInstantWithdraws > 0, receipt still keyed to N.
    _stopEpochPartialInstantFunding(); // attacker receipt left unfunded

    // 3. Epoch N+1: victim keeps funds in; borrower defaults at stopEpoch N+1.
    _stopEpochAndCheckPrices(1, apr, 0);
    _checkDefault();
    // owner finalizes with partial recovery, e.g. 70%
    _finalizeDefaultRecovery(7e17);

    // 4. Attacker's receipt was NOT counted in instantWithdrawClaimsByEpoch[N+1],
    //    so defaultPendingClaimBasis excluded it and recoveryPrice ignores it.
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.defaultRecoveryEpoch()), 0);

    // 5. Attacker claims: defaulted-path lookup misses (epoch key drift), falls through to
    //    funded path and pays receiptAmt at PAR instead of receiptAmt * 70%.
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - pre, receiptAmt); // should be receiptAmt * 7e17 / 1e18
}
```

Note: I did not fully verify whether `claimInstantWithdrawRequest`'s fall-through path decrements `pendingInstantWithdraws` or whether unfunded instant receipts can be left in `pendingInstantWithdraws` only via specific funding-failure orderings; the PoC asserts the accounting deltas to confirm both. If the strategy holds no non-reserve underlying at step 5, the same keying bug manifests as a permanent revert of the claim (frozen funds) rather than par theft — either outcome violates the recovery invariant.
