### Title
Loss-adjusted withdraw receipts are keyed to the wrong epoch, letting users claim haircutted receipts at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a missing-validation bug: an archive member's pathname is trusted, so a write escapes the intended directory. The closest analog in this codebase is in the delayed-withdrawal receipt bookkeeping of `IdleCreditVault`: the "path" (epoch key) under which a stop-epoch loss haircut is stored is not validated against the epoch key under which receipts are recorded and claimed. `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` using the epoch counter *after* it was incremented by `deposit()` inside `stopEpoch`, while every user-facing lookup — the re-request guard in `requestWithdraw`, `_claimLossAdjustedWithdrawRequest`, and `_clearWithdrawClaimForEpoch` — uses `lastWithdrawRequest[_user]`, which holds the *request* epoch (one less). The haircut entry is therefore unreachable: a receipt that absorbed a pro-rata loss is paid in full.

### Finding Description
- In `_stopEpoch` (`contracts/IdleCDOEpochVariant.sol:408-410`), the CDO calls `getFundsFromBorrower`, which routes through `IdleCreditVault.deposit`, incrementing `epochNumber` while `isEpochRunning` is still true (`IdleCreditVault.sol:607-610`). `collectWithdrawFunds` is then invoked and, on partial funding, writes `lossRecoveryPriceByEpoch[epochNumber]` — i.e., under the *new* epoch number (`IdleCreditVault.sol:421`).
- A user's receipt, however, is bound to `lastWithdrawRequest[_user]`, set at request time to the pre-increment epoch (`IdleCreditVault.sol:282`).
- `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:790-792`), finds zero, and returns early. Execution falls to `_claimFundedWithdrawRequest`, which pays the full aggregate `withdrawsRequests[_user]` at par (`IdleCreditVault.sol:338-349`) even though the strategy only received the haircutted `_amount` from the borrower.
- The same off-by-one key defeats the safety guard in `requestWithdraw` (`IdleCreditVault.sol:261-271`), which is meant to block new requests while a loss-adjusted receipt is unclaimed; because it reads the same mismatched key, the guard never fires, so the user can also stack a fresh request on top.

### Impact Explanation
Direct theft / insolvency. The strategy holds only `pendingBasis * lossRecoveryPrice / 1e18` for the haircutted epoch's receipts, but each claim pays the full basis. The first claimants drain funded underlyings that are earmarked for other pending receipts; the last claimants either overdraw other users' funds or revert once the strategy's balance (net of `defaultRecoveryReserve`) is exhausted (`_transferFundedClaim`, `IdleCreditVault.sol:897-906`). The loss that `stopEpochWithDuration(_lossAmount)` was designed to socialize across pending receipts is silently transferred to whoever claims last, or causes permanent claim failures for honest receipt holders. The broken invariant is "one receipt one (haircut-adjusted) payout."

### Likelihood Explanation
Requires only that a `stopEpochWithDuration` with non-zero `_lossAmount` partially funds `pendingWithdraws` while `defaultRecoveryInitialized` is true — an honest-manager action in a stressed epoch, not attacker orchestration. Any user with a pending receipt in that epoch then claims at par. The attacker needs no privilege beyond holding a normal withdraw receipt. Note: I could not execute a fork PoC within this session, so the epoch-key divergence rests on the call-ordering trace `deposit()` → `epochNumber += 1` → `collectWithdrawFunds` inside `_stopEpoch`; if the harness increments the counter elsewhere the conclusion should be re-verified.

### Recommendation
Key the loss bucket consistently. Either store `lossRecoveryPriceByEpoch` under the request epoch (e.g., `epochNumber - 1`, matching `lastWithdrawRequest`) in `collectWithdrawFunds`, or make `lastWithdrawRequest` record the post-increment epoch. The same canonical key must be used in `requestWithdraw`'s guard, `_claimLossAdjustedWithdrawRequest`, and `_clearWithdrawClaimForEpoch`, so that the "pathname" (epoch key) written at funding time is exactly the one validated at claim time.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
// Foundry fork test — extend the existing IdleCreditVault.t.sol harness
// (helpers _depositWithUser, _startEpochAndCheckPrices, _expectedFundsEndEpoch assumed).

function testLossAdjustedReceiptClaimedAtPar() external {
    // Epoch 0: two users deposit; epoch runs.
    uint256 amt = 10_000 * ONE_SCALE;
    address alice = makeAddr('alice');
    address bob   = makeAddr('bob');
    _depositWithUser(alice, amt, true);
    _depositWithUser(bob,   amt, true);
    _startEpochAndCheckPrices(0);

    // Both request full withdrawal during epoch 0 buffer.
    uint256 reqEpoch = IdleCreditVault(address(strategy)).epochNumber();
    vm.prank(alice); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(bob);   cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Stop epoch 1 with a realized loss: borrower funds only part of pendingWithdraws.
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 loss    = pending / 4; // 25% loss on pending bucket share
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() + pending);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, 7 days, loss);

    // BUG: haircut is stored under epochNumber (reqEpoch+1), claims read reqEpoch.
    assertEq(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(reqEpoch), 0);
    assertGt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(reqEpoch + 1), 0);

    // Alice claims: _claimLossAdjustedWithdrawRequest returns 0 (wrong key),
    // _claimFundedWithdrawRequest pays full basis despite the 25% haircut.
    uint256 aliceBasis = /* recorded withdrawsRequests[alice] at request time */;
    uint256 balPre = underlying.balanceOf(alice);
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(alice) - balPre,
             aliceBasis * 3 / 4, "alice paid above her haircut entitlement");

    // Bob's claim now reverts or is underpaid: the reserve was drained at par.
    vm.prank(bob);
    vm.expectRevert(); // NotAllowed from _transferFundedClaim balance check / OOG funds
    cdoEpoch.claimWithdrawRequest();
}
