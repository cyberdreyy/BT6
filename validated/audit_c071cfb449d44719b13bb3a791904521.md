### Title
Signer can equivocate within a single tenure because the legacy (`v1`) `SortitionsView` duplicate-block check only looks at *globally* accepted blocks, unlike the `v2` `GlobalStateView` check — ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (the pre-global-state signer path) rejects a tenure-change proposal as a duplicate only if the signer already has a **globally accepted** block for that tenure. The newer `GlobalStateView::validate_tenure_change_payload` was hardened to check for *any signed* block (local or global) for exactly this reason, per its own code comment. The `v1` path was left with the weaker check, so a single miner can get the same signer to sign two conflicting blocks for the same tenure.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` performs the duplicate-in-tenure check via: [1](#0-0) 

This calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which only returns a block once it has reached global (majority) acceptance — not merely once *this* signer has signed it.

Compare this to `stacks-signer/src/chainstate/v2.rs`'s `validate_tenure_change_payload`, which explicitly documents why the check must cover locally signed blocks too: [2](#0-1) 

The `v2` comment states: "check we are not reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count here... it is safe to accept a competing tenure-start block in its place if it failed to reach consensus" — the wording implies awareness that a check based solely on global acceptance is insufficient, yet the `v1` code path (still in scope and still used depending on `SortitionStateVersion`/protocol-version negotiation, see `check_block_against_state` dispatch in `stacks-signer/src/v0/signer.rs:865-869`) retains exactly that weaker check.

Concretely, for a signer still operating on the `v1`/local `SortitionsView` path:
1. The tenure's miner proposes a normal (non-tenure-change) block `B1` continuing the tenure. The signer validates and signs it (`create_block_acceptance`), moving it to at least `LocallyAccepted`, but before the rest of the signer set reaches the 70%+ global-acceptance threshold (e.g., due to network latency or a colluding subset of signers withholding responses).
2. The same miner (a "one-slot miner" — no other signer key or majority needed) proposes a second, conflicting block `B2` for the same tenure, this time containing a `TenureChangePayload` whose `prev_tenure_consensus_hash` legitimately matches the parent tenure and whose "confirmed parent" checks pass.
3. `validate_tenure_change_payload` looks up `get_last_globally_accepted_block` for the current tenure — this returns `None` because `B1` was only locally (not globally) accepted.
4. The `DuplicateBlockFound` rejection at `stacks-signer/src/chainstate/v1.rs:510-518` never fires, so the signer proceeds to also sign `B2`.

The signer has now produced two valid signatures for two conflicting blocks (`B1`, a continuation, and `B2`, a tenure-change that discards `B1`'s position) within the same tenure — an equivocation triggered purely by miner-controlled proposal timing/content and StackerDB gossip, no signer majority required.

### Impact Explanation
This breaks the "one-per-tenure / no-conflicting-signature" invariant that the `v1` (and `v2`) tenure-change duplicate check is meant to enforce. A signer that equivocates in this way contributes a valid signature to two mutually conflicting block sets, which is exactly the "signer signing a conflicting block" class this scan is scoped to flag — a Critical-severity condition per the report's impact criteria.

### Likelihood Explanation
Reachable by a single sortition-winning miner controlling proposal order/content and ordinary StackerDB gossip; it does not require compromising any signer's key, majority collusion, or `auth_token`/local access. It does depend on the signer network still negotiating/using the `v1` local-state protocol version rather than having activated `GlobalStateView` (`state_version.uses_global_state()` in `stacks-signer/src/v0/signer.rs:865`), and on the timing window before `B1` reaches global acceptance — both realistic conditions during protocol-version transition periods or under normal network latency.

### Recommendation
Change `SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use the same signed-block query as `v2` (`get_last_signed_block`, i.e., locally-or-globally accepted) instead of `get_last_globally_accepted_block`, so a signer refuses to sign a competing tenure-change block once it has already signed any block — local or global — in that tenure.

### Proof of Concept
Conceptual sequence (no majority or extra keys required):
1. Miner M wins the current sortition tenure T.
2. M proposes block `B1` (plain continuation, no tenure-change) for T; signer S validates via `SortitionsView::check_proposal` → passes → S signs `B1` (`create_block_acceptance`), stored as at least `LocallyAccepted` in `SignerDb`.
3. Before `B1` reaches global (majority) acceptance, M proposes block `B2` for T containing a `TenureChangePayload` with a valid `prev_tenure_consensus_hash` and a valid confirmed parent.
4. S's `SortitionsView::validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&T)` (`stacks-signer/src/chainstate/v1.rs:505-509`), which returns `None` since `B1` is only locally accepted.
5. The `DuplicateBlockFound` check is skipped; S proceeds to validate and sign `B2`, producing a second, conflicting signature for tenure T. [1](#0-0) [2](#0-1) [3](#0-2)
