## Title
Unchecked instruction account-index causes panic when JSON-parsing v0 transactions without loaded-address metadata - ([File: transaction-status/src/lib.rs])

### Summary
`parse_ui_instruction` and its helper `make_ui_partially_decoded_instruction` in `transaction-status/src/lib.rs` index directly into `account_keys` using `instruction.program_id_index` and `instruction.accounts[..]` with no bounds check, unlike every other instruction parser in the same crate (`parse_system`, `parse_stake`, `parse_vote`, `parse_token`, `parse_associated_token`, `parse_address_lookup_table`), which all explicitly validate `instruction.accounts.iter().max() < account_keys.len()` before indexing.

### Finding Description [1](#0-0) 

`make_ui_partially_decoded_instruction` and `parse_ui_instruction` index `account_keys[instruction.program_id_index as usize]` and `account_keys[i as usize]` unconditionally. Contrast this with the guarded pattern used throughout the rest of the crate, e.g.: [2](#0-1) [3](#0-2) 

The specific reachable path is `v0::Message::encode` (as opposed to `encode_with_meta`), which is invoked when JSON-parsed encoding is requested but no `TransactionStatusMeta` is supplied: [4](#0-3) 

Here, `AccountKeys::new(&self.account_keys, None)` builds an `AccountKeys` view containing **only the static account keys** of a v0 message — `LoadedAddresses::default()` (empty) is used instead of the mint's actual resolved address-lookup-table addresses. However, `self.instructions` for a v0 message can legitimately reference account indices beyond `self.account_keys.len()` (i.e., indices that resolve into the dynamically loaded lookup-table addresses). When `parse_ui_instruction`/`make_ui_partially_decoded_instruction` is subsequently called with this truncated `account_keys`, any instruction referencing a dynamic (lookup-table) account index will index past the end of the slice, panicking.

This differs from `encode_with_meta`, which correctly supplies `meta.loaded_addresses` and thus produces an `AccountKeys` containing the full static+dynamic set: [5](#0-4) 

### Impact Explanation
An index-out-of-bounds panic in a JSON-RPC-facing encoding path can crash the validator's JSON-RPC thread/process (or the entire process, depending on panic-handling configuration) when handling an unprivileged request — this matches the "decoder panic and misreporting" / "validator-process crash from one request" impact classes called out as in-scope. Because `encode()` (the meta-less path) is only reached when the caller has a v0 `VersionedTransaction` but no accompanying execution metadata, the most plausible unprivileged trigger is a client-submitted, unconfirmed/simulated v0 transaction containing address-table-lookup instructions that gets JSON-parsed for display/response purposes before or without full metadata being attached.

### Likelihood Explanation
I could not conclusively trace, within the available time and index limits, whether this "meta-less" `encode()` path is presently reachable from a live JSON-RPC endpoint such as `simulateTransaction` or `getTransaction` (the grep search for exact call sites in `rpc/src/rpc.rs` did not resolve before the iteration budget was exhausted). It is used from `ledger-tool` (an operator-only tool, out of scope) and from the trait definitions in `transaction-status/src/lib.rs`. Given the strict rule to keep only unprivileged-user analogs and to reject "theoretical-only" findings, and because I was **unable to confirm** a concrete unprivileged JSON-RPC call site that invokes `Encodable::encode` (rather than `encode_with_meta`) on a v0 message containing an address-table lookup instruction, I cannot assert this is definitely externally triggerable with certainty equal to the other analogs I ruled out. This is a real code-quality/robustness gap (missing bounds check that exists everywhere else in the file) but its exploitability via RPC is unverified.

### Recommendation
Regardless of the exact caller, add the same bounds-check pattern used elsewhere in the crate to `parse_ui_instruction` / `make_ui_partially_decoded_instruction` (verify `instruction.program_id_index` and all `instruction.accounts` entries are `< account_keys.len()` and return a `PartiallyDecoded`/raw fallback or error instead of panicking). Additionally, review all call sites of `Encodable::encode` (the meta-less variant) for `v0::Message` to ensure they are never invoked with a message that has non-empty `address_table_lookups`, or refuse to call it in that case.

### Proof of Concept
Not verified end-to-end due to inability to confirm a live unprivileged call site within the tool budget. Conceptually: construct a `VersionedTransaction` with a `v0::Message` containing one `address_table_lookups` entry and one `CompiledInstruction` whose `accounts` includes an index `>= self.account_keys.len()` (pointing into the dynamic/lookup portion). Call `Encodable::encode(&message, UiTransactionEncoding::JsonParsed)` directly (bypassing `encode_with_meta`) — this reproduces the out-of-bounds index panic in `parse_ui_instruction`.

Given the unresolved reachability question, I'm not fully confident this qualifies as a validated in-scope finding versus the closer, all-guarded pattern found in `parse_system.rs`/`parse_stake.rs`/`parse_vote.rs`/`parse_token.rs` (which are NOT vulnerable — they all perform bounds checks). If a Devin session with full codebase/terminal access is available, it should verify whether `Encodable::encode` on `v0::Message` is reachable from `rpc/src/rpc.rs` (e.g., via `simulateTransaction`, `getTransaction`, or `getBlock` with `jsonParsed` encoding) before treating this as confirmed.

pub fn parse_ui_instruction(
    instruction: &CompiledInstruction,
    account_keys: &AccountKeys,
    stack_height: Option<u32>,
) -> UiInstruction {
    let program_id = &account_keys[instruction.program_id_index as usize];
    if let Ok(parsed_instruction) = parse(program_id, instruction, account_keys, stack_height) {
        UiInstruction::Parsed(UiParsedInstruction::Parsed(parsed_instruction))
    } else {
        UiInstruction::Parsed(UiParsedInstruction::PartiallyDecoded(
            make_ui_partially_decoded_instruction(instruction, account_keys, stack_height),
        ))
    }
}
