### Title
Tranche virtual price floors to zero while NAV is non-zero, permanently locking residual and future-recovered funds — (File: contracts/IdleCDOCreditVault.sol)

### Summary
Analogous to the Ethos `F_Collateral` rounding bug — where `collFee * 1e18 / totalLQTYStaked` rounds to 0 so received rewards are never distributed — the credit vault computes per-tranche-token prices as `(lastTrancheNAV + gain) * ONE_TRANCHE_TOKEN / trancheSupply`. When a tranche's NAV is positive but smaller than `trancheSupply / 1e18`, `_virtualPrice` rounds down to exactly 0. The NAV remains tracked in `lastNAVAA`/`lastNAVBB` (and in `getContractValue()` via strategy tokens), but the tranche becomes unusable: `withdrawAA`/`withdrawBB` pay 0 while burning tokens, and `depositAA`/`depositBB` revert with division-by-zero inside `_mintSharesAtCurrPrice` (`_amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)`). Any funds later recovered for that tranche (borrower repayment, strategy price recovery, recovery deposit) only increase a NAV that still divides to a 0 price, so they are permanently locked — the same "received assets that can never be distributed per unit" bug class. ### Finding Description
In `IdleCDOCreditVault._virtualPriceAux` (and the identical expression in `IdleCDO._virtualPriceAux` at `contracts/IdleCDO.sol:429`), the final price is computed as:

```solidity
_virtualPrice = uint256(int256(_lastTrancheNAV) + _totalTrancheGain) * ONE_TRANCHE_TOKEN / trancheSupply;
```

`ONE_TRANCHE_TOKEN` is `1e18` while `trancheSupply` is in tranche-token wei (18 decimals). The division therefore returns 0 whenever `_lastTrancheNAV + _totalTrancheGain < trancheSupply / 1e18` — i.e., whenever fewer whole underlying units remain than there are whole tranche tokens outstanding. This is reachable without any privileged misbehavior:

- A strategy/price loss that nearly — but not fully — wipes the junior tranche leaves `lastNAVBB` as a small positive dust value while `BBTranche.totalSupply()` stays large. The explicit `return (0, -_juniorTVL)` full-wipe branch is not taken because `_newJuniorTVL > 0`, so `lastNAVBB` remains non-zero dust.
- Time-based `_accrueManagementFee` (`unclaimedFees` reduces `getContractValue`) and ordinary `_updateAccounting` gains/losses can also grind a tranche NAV into the sub-`supply/1e18` band.

Once `priceBB == 0` (or `priceAA == 0`):

- `requestWithdraw`/`withdrawBB` compute `_trancheToUnderlyings = _amount * 0 / 1e18 = 0` and burn the user's tokens paying nothing; `lastNAVBB` is not decreased to 0, so the underlying remains inside `getContractValue`.
- Any subsequent increase of the tranche NAV (borrower repays late, recovery is deposited, strategy value rebounds) is split into `_totalBBGain` via `_updateAccounting`, but `_virtualPrice` still evaluates to 0 because NAV remains `< supply/1e18` — identical to Ethos where `F_Collateral` stays flat while collateral accumulates in the contract.
- `depositBB` reverts (`_tranchePrice == 0` divisor), so the tranche cannot even be recapitalized.

There is no error-accumulator (no analog of `lastLQTYError`) and no rescue path: no function lets anyone sweep a tranche NAV whose price rounded to zero.

### Impact Explanation
Permanent freezing of yield/NAV. The entire residual tranche NAV — and unboundedly all subsequent recoveries or repayments credited to that tranche — become undistributable. Holders burning tokens receive 0; the strategy tokens backing `lastNAVBB`/`lastNAVAA` remain locked in the vault forever since withdrawals are the only path that releases them and they value the tranche at 0. For a BB tranche with, e.g., 1e24 supply (1M tokens) and a post-loss NAV of 5e5 units, 100% of remaining junior value plus any later borrower repayment attributable to juniors is locked. This matches the H-03 impact profile: assets sit in the contract and can never reach their owners.

### Likelihood Explanation
Requires a tranche NAV to end in the band `(0, totalSupply/1e18)` — plausible for junior tranches after large-but-not-total losses, after defaults with partial recovery, or after management-fee erosion on thin residual NAV. It does not require attacker action; like the LQTY bug it is triggered by ordinary protocol flow once the denominator (token supply) is large relative to the numerator (residual NAV per whole token). No existing guard prevents it: `_skimDonatedAssets` only moves raw underlying, the `Default` revert and `_emergencyShutdown` gates don't address a non-zero NAV with a zero price, and there is no minimum-NAV or dust check before saving `lastNAVBB`/`lastNAVAA`.

### Recommendation
Apply the Ethos fix pattern: track the division remainder. Either (a) keep NAV accounting in "per-share" form with an error accumulator, or (b) when `_lastTrancheNAV + _totalTrancheGain > 0` but the computed `_virtualPrice == 0`, treat it as a full wipe: set the saved tranche NAV to 0 and route the residual to the surviving tranche / `unclaimedFees` / feeReceiver so value is never stranded behind a zero price. Alternatively, revert early in `stopEpoch`/`finalizeDefault` paths when a non-zero NAV would produce a zero price, forcing explicit resolution instead of silent lock-up.

### Proof of Concept
Foundry fork sketch against the credit-vault test harness (`test/foundry/IdleCreditVault.t.sol` style):

```solidity
function testJuniorNavDustLocksWithZeroPrice() external {
    // 1. Deposit: AA small, BB large supply (e.g. 1_000_000e18 BB tokens => supply 1e24)
    idleCDO.depositAA(1_000 * ONE_SCALE);
    idleCDO.depositBB(1_000_000 * ONE_SCALE); // BB supply = 1e24 wei

    // 2. Run epoch, then create a loss leaving lastNAVBB = dust < supply/1e18 (=1e6 units)
    _startEpochAndCheckPrices(0);
    _createLoss(/* loss leaving lastNAVBB in (0, 1e6) */);
    vm.prank(owner);
    cdoEpoch.updateAccounting(); // forced accounting, BB survives with dust NAV

    // 3. priceBB == 0 while lastNAVBB > 0
    assertEq(cdoEpoch.virtualPrice(address(BBtranche)), 0);
    assertGt(cdoEpoch.lastNAVBB(), 0);

    // 4. Withdraw burns tokens, pays 0; NAV is not released
    uint256 balPre = underlying.balanceOf(address(this));
    uint256 navPre = cdoEpoch.lastNAVBB();
    cdoEpoch.requestWithdraw(BBtranche.balanceOf(address(this)), address(BBtranche));
    // receipt _underlyings == 0; lastNAVBB unchanged => locked

    // 5. Later borrower repayment / recovery credited to BB still yields price 0
    //    -> recovered funds are permanently locked, mirroring locked LQTY rewards.
}
```

The key assertion is `lastNAVBB > 0` together with `virtualPrice == 0`: value is on the books and backed by strategy tokens, but no code path can ever pay it out.
