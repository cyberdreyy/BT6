### Title
Post-default instant-withdraw receipts are paid at par from the shared recovery reserve because `requestInstantWithdraw`/`claimInstantWithdrawRequest` lack the post-default synchronization applied to normal requests - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Elasticsearch bug class is a shared resource (response buffer) consumed by concurrent users without proper synchronization, letting one user's request observe another user's data. The credit-vault analog is the strategy's shared underlying pool after default finalization: `defaultRecoveryReserve` is a common pool meant to back all defaulted-epoch receipts at `defaultRecoveryPrice`. The normal withdraw path synchronizes access to it — `requestWithdraw` reverts on stale receipts, mints post-default receipts through `postDefaultRequests`, and pays them only via `_claimPostDefaultWithdrawRequest`/`_transferDefaultRecovery`, which decrements the reserve. The instant-withdraw path has no equivalent synchronization: `requestInstantWithdraw` never checks `defaultRecoveryFinalized`, and `claimInstantWithdrawRequest` pays `instantWithdrawsRequests[_user]` in full through `_transferFundedClaim` (line 387-392), which sends raw strategy underlying without touching `defaultRecoveryReserve`. A post-default instant receipt therefore pulls un-haircut underlying out of the same balance that backs `defaultRecoveryPrice`-denominated recovery claims, i.e., one user's concurrent payout is funded by other users' recovery entitlement.

### Finding Description
- `requestWithdraw` (line 243-295) has an explicit post-default branch: it blocks users with open receipts, burns the CDO principal, mints the receipt, and routes payout through the reserve. `requestInstantWithdraw` (line 356-375) only calls `_onlyIdleCDO` and `_ensureDefaultRecoveryInitialized` — it contains no `defaultRecoveryFinalized` gate, no reserve routing, and unconditionally increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]` and `pendingInstantWithdraws`.
- `claimInstantWithdrawRequest` (line 380-393) handles `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` only for receipts created in `defaultRecoveryEpoch` via `_claimDefaultedInstantWithdrawRequest`. Any receipt recorded under a later `epochNumber` (i.e., created after finalization) falls through to `instantWithdrawsRequests[_user]` and is paid at par by `_transferFundedClaim`, which does not decrement `defaultRecoveryReserve`.
- `finalizeDefaultRecovery` (line 661-710) fixes `defaultRecoveryReserve` and `defaultRecoveryPrice` once. Every underlying token that later leaves the strategy through `_transferFundedClaim` without a reserve debit shrinks the real backing below the finalized price, so each subsequent legitimate `_claimDefaultedWithdrawRequest`/`_claimPostDefaultWithdrawRequest`/`DefaultDistributor.claim` is under-collateralized.
- The asymmetry is internally inconsistent: `requestWithdraw` explicitly reverts when `instantWithdrawsRequests[_user] != 0` post-default (line 249), showing the design treats open instant receipts as conflicting claims on the same recovery resource — yet the instant path itself is left open.

### Impact Explanation
Direct theft of other users' default-recovery proceeds. After `finalizeDefaultRecovery`, the strategy's underlying balance is (predominantly) `defaultRecoveryReserve`. Any instant receipt paid via `_transferFundedClaim` at face value consumes reserve backing without a haircut and without decrementing `defaultRecoveryReserve`, so the sum of remaining recovery claims exceeds the remaining balance. Last-come recovery claimants get stuck (transfer failure / shortfall), i.e., permanent loss of unclaimed recovery for honest defaulted-epoch receipt holders, quantified as the total post-default instant payouts drawn at par.

### Likelihood Explanation
Requires the pool to be defaulted and finalized (a supported, non-emergency state reachable via `stopEpochWithDuration` + `finalizeDefault` + `finalizeDefaultRecovery`), and requires the CDO to still route an instant withdraw post-default. No privileged role is the attacker — any tranche/token holder able to trigger `requestInstantWithdraw` through the CDO after finalization qualifies. The attacker does not need to race a single transaction; they only need their instant claim to execute before honest users' recovery claims, which is normal ordering, not MEV. The main residual uncertainty is the exact CDO-side entry point that still forwards instant withdraws while `defaulted()` — if every CDO instant path is blocked post-default, the strategy-level gap is unreachable. The missing guard in the strategy itself is verifiably absent (lines 356-393), and the strategy is supposed to be robust to `_onlyIdleCDO` callers rather than rely on the CDO for reserve isolation.

### Recommendation
- In `requestInstantWithdraw`, revert (or route through the post-default receipt path) when `defaultRecoveryFinalized` is true, mirroring `requestWithdraw`'s handling.
- Alternatively, in `claimInstantWithdrawRequest`, pay receipts whose request epoch is `> defaultRecoveryEpoch` through `_transferDefaultRecovery`/`postDefaultRequests` semantics so the reserve is debited consistently.
- Ensure every path that pays underlying out of the strategy post-finalization either decrements `defaultRecoveryReserve` or is provably funded outside it.

### Proof of Concept
Foundry-fork scenario (sketch — CDO call path assumes an instant-withdraw entry such as `withdrawInstant`/`getInstantWithdrawFunds` remains callable post-default; confirm against `IdleCDOEpochVariant` instant withdraw functions):

```solidity
// test/foundry/PostDefaultInstantDrain.t.sol
function testPostDefaultInstantClaimDrainsRecoveryReserve() external {
    // 1. Seed AA/BB deposits, start epoch, warp past epochEndDate.
    // 2. Borrower defaults: stopEpochWithDuration(_loss), then finalizeDefault.
    // 3. finalizeDefaultRecovery(partialRecovery, recoverySource)
    //    => defaultRecoveryFinalized = true, reserve R held in strategy underlying.

    uint256 reserve = strategy.defaultRecoveryReserve();
    assertGt(reserve, 0);

    // 4. Attacker (unprivileged holder) triggers an instant withdraw via the CDO.
    //    Strategy-side: requestInstantWithdraw(amount, attacker) — no defaultRecoveryFinalized check.
    vm.prank(address(cdoEpoch));
    strategy.requestInstantWithdraw(attackerReceiptAmount, attacker);

    // instantWithdrawsRequestsByEpoch[attacker] is recorded under a LATER epochNumber
    // than defaultRecoveryEpoch, so _claimDefaultedInstantWithdrawRequest skips it.

    // 5. Attacker claims. Pays face value via _transferFundedClaim — reserve untouched.
    vm.prank(address(cdoEpoch));
    strategy.claimInstantWithdrawRequest(attacker);

    // Reserve variable unchanged but underlying balance dropped:
    assertEq(strategy.defaultRecoveryReserve(), reserve);          // accounting unchanged
    assertLt(underlying.balanceOf(address(strategy)), reserve);    // real backing reduced

    // 6. Honest defaulted-epoch user claims at defaultRecoveryPrice — underfunded/reverts,
    //    i.e., the attacker's par payout leaked their recovery share.
    vm.prank(address(cdoEpoch));
    vm.expectRevert(); // or: receives < claimBasis * defaultRecoveryPrice
    strategy.claimWithdrawRequest(honestUser);
}
```

Key line references: `requestInstantWithdraw` lacking the default gate vs `requestWithdraw`'s post-default branch (IdleCreditVault.sol:243-295 vs 356-375), and the unguarded `_transferFundedClaim` payout (IdleCreditVault.sol:387-392).
