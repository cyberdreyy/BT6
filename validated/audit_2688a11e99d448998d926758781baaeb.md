### Title
Loss-adjusted withdrawal haircut is bypassed when a second withdraw request overwrites `lastWithdrawRequest`, letting the receipt holder claim the defaulted-loss amount at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` looks up the loss-adjusted epoch via `lastWithdrawRequest[_user]`, which only stores the user's *latest* request epoch. If a user has a receipt in a loss-adjusted epoch E1 and then makes a second withdraw request in epoch E2, `lastWithdrawRequest[_user]` becomes E2. Since `lossRecoveryPriceByEpoch[E2] == 0`, the loss-adjusted path is skipped, and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` (E1 + E2 basis) at par — even though only `E1 * lossRecoveryPrice` was ever funded for the E1 portion.

### Finding Description
When `stopEpochWithDuration` realizes a loss, `IdleCDOEpochVariant` calls `collectWithdrawFunds(_amount)` with `_amount < pendingWithdraws`. The strategy then stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws`, so the haircutted receipts should later be paid through `_claimLossAdjustedWithdrawRequest` at `claimBasis * lossRecoveryPrice / RECOVERY_FULL`.

However, `requestWithdraw` unconditionally sets `lastWithdrawRequest[_user] = currentEpoch` and adds to the aggregate `withdrawsRequests[_user]` (lines 282–293). `_claimLossAdjustedWithdrawRequest` only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789–794). A second request in a later epoch therefore orphans the E1 entry in `withdrawsRequestsByEpoch[_user][E1]`: it is never cleared, never haircut, and its basis remains inside `withdrawsRequests[_user]`, which `_claimFundedWithdrawRequest` pays in full at par (lines 338–349).

Broken invariant: the loss waterfall / "one receipt one payout" — a haircutted receipt is paid at par, and the excess is drained from funded claim reserves belonging to other users.

### Impact Explanation
Direct theft. An attacker who requests `X` underlyings of withdrawal before a loss-adjusted `stopEpochWithDuration` (lossRecoveryPrice = p < 1) recovers `X` instead of `X * p`, stealing `X * (1 - p)` from the strategy's funded-claim balance. The excess underlying was collected for *other* users' receipts via `collectWithdrawFunds`/`collectInstantWithdrawFunds`, so those users' claims become undercollateralized — the theft is realized as insolvency for later claimers (their `claimWithdrawRequest`/`claimInstantWithdrawRequest` reverts on insufficient balance or pays less). Attacker cost is limited to temporarily parking capital in a tranche and accepting the same epoch-wait as any redeemer; KYC-passing lenders qualify as attackers per scope.

### Likelihood Explanation
Requires: (1) an epoch that ends via `stopEpochWithDuration` with a partial-loss funding (a supported, tested mode — `previewLossAdjustedWithdrawFunds` and `lossRecoveryPriceByEpoch` exist precisely for it), and (2) the attacker holding a pending receipt in that epoch plus a second request in a later epoch. Both are unprivileged actions (`requestWithdraw` is called by the CDO on behalf of any tranche holder), and the comment at lines 323–324 explicitly documents re-requesting before claiming as a supported flow. No privileged misbehavior is needed; the loss itself can result from an ordinary borrower shortfall. The only mild requirement is timing: the attacker must hold a request open during a lossy stop, which they can cheaply maintain across many epochs.

### Recommendation
In `requestWithdraw` (or `_claimFundedWithdrawRequest`), iterate/clear all epochs with a recorded `lossRecoveryPriceByEpoch` for the user, not just `lastWithdrawRequest[_user]`. Concretely: when a new request is made, first settle any prior loss-adjusted epoch receipt (`_clearWithdrawClaimForEpoch(_user, priorEpoch, false)` and pay `claimBasis * lossRecoveryPriceByEpoch[priorEpoch] / RECOVERY_FULL`), or track a per-user list/flag of loss-adjusted epochs so `_claimLossAdjustedWithdrawRequest` cannot be skipped. Additionally, revert `requestWithdraw` if the user still has an unpaid loss-adjusted receipt, mirroring the "wait an extra epoch" semantics already documented.

### Proof of Concept
Foundry fork PoC sketch (extend `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `deal` for borrower funding):

```solidity
function testLossHaircutBypassViaSecondRequest() external {
    uint256 amountWei = 10000 * ONE_SCALE;
    uint256 mintedAA = idleCDO.depositAA(amountWei);
    idleCDO.depositBB(amountWei);

    // attacker deposit
    address eve = makeAddr('eve');
    _depositWithUser(eve, 1000 * ONE_SCALE, true); // AA tranche

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // E1: attacker requests full withdraw
    uint256 eveTranches = IERC20Detailed(address(AAtranche)).balanceOf(eve);
    vm.prank(eve);
    cdoEpoch.requestWithdraw(eveTranches, address(AAtranche));

    // E1 stops with a realized loss: borrower funds only part of pendingWithdraws
    _startEpochAndCheckPrices(1);
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 loss = pendingBasis / 2; // 50% haircut on pending receipts
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(loss);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(address(underlying), strategy.borrower(), repay, true);
    vm.prank(strategy.borrower());
    underlying.approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), loss);
    // lossRecoveryPriceByEpoch[E1] = 0.5e18-ish; E1 receipt is now haircut

    // E2: attacker makes a second (tiny) request, overwriting lastWithdrawRequest
    _depositWithUser(eve, 100 * ONE_SCALE, true);
    vm.prank(eve);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // lastWithdrawRequest[eve] = E2

    // E2 stops fully funded
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());

    // claim: loss path checks lossRecoveryPriceByEpoch[E2] == 0 -> skipped,
    // funded path pays withdrawsRequests[eve] = (E1 + E2) at PAR
    uint256 balPre = underlying.balanceOf(eve);
    vm.prank(eve);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(eve) - balPre;

    uint256 e1Basis = 1000 * ONE_SCALE; // approx; use recorded request values
    // attacker received E1 at par instead of ~half:
    assertGt(got, e1Basis, 'haircut bypassed: E1 paid at par');
    // the extra ~e1Basis/2 was taken from funds collected for other receipts
}
```

Expected: `got ≈ E1_basis + E2_basis` while the strategy only received `E1_basis * lossPrice + E2_basis`; the difference is drained from funded reserves, and subsequent users' claims revert or underpay.
