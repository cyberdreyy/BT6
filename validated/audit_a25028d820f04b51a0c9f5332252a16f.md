### Title
Stale per-epoch instant-withdraw receipts are re-counted in default recovery accounting, inflating the recovery reserve and diluting/insolventing the claim pool - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The CVE-2022-0458 use-after-free pattern (an object used after its logical lifetime ends) maps to `IdleCreditVault`'s instant-withdraw receipt bookkeeping: when a user claims a funded instant withdrawal, `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[user]` while leaving `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` populated. If the borrower defaults in that same epoch while another instant receipt remains unfunded, `finalizeDefaultRecovery` resurrects the dead receipt: it is counted in `defaultPendingClaimBasis`, its already-paid-out funds are counted again in `_defaultPrefundedInstantReserve`, and the claim path can be reached again via `_claimDefaultedInstantWithdrawRequest`. This is a stale-pointer/UAF analog standing entirely on idle-tranches code.

### Finding Description
`requestInstantWithdraw` writes three ledgers: `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch[user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (`IdleCreditVault.sol:366-374`).

On a successful funded claim, `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and sets it to 0, but never clears either per-epoch mapping (`IdleCreditVault.sol:387-392`). The receipt is logically freed but the per-epoch records still reference it.

Later, if `finalizeDefaultRecovery` runs with `epochNumber` equal to that epoch and `pendingInstantWithdraws != 0` (another user's unfunded instant request), the dead receipt is revived:

- `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes the already-claimed amount (`IdleCreditVault.sol:644-649`).
- `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant`, counting the claimed user's payout as if it were underlying still held by the strategy (`IdleCreditVault.sol:716-723`). That amount is added to `reserveAmount`/`defaultRecoveryReserve` at line 686 even though it was already transferred out, so the recovery price `reserveAmount * RECOVERY_FULL / totalBasis` is inflated by phantom funds.
- `defaultInstantWithdrawsFinalized = true`, so subsequent `claimInstantWithdrawRequest` calls route through `_claimDefaultedInstantWithdrawRequest`, which reads the stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` (`IdleCreditVault.sol:842-856`).

### Impact Explanation
Two concrete harms for an unprivileged user (no privileged attacker needed; the borrower defaulting is an honest-role event):

1. **Inflated recovery price / insolvency of the reserve**: `defaultRecoveryReserve` is credited with underlying that was already paid to the first claimant. The contract balance is lower than the recorded reserve. Early recovery claimants (e.g. the still-pending instant requester and defaulted normal withdrawers) withdraw at a price backed by non-existent funds; later claimants' `_transferDefaultRecovery` calls either drain the reserve below accounting or revert on insufficient balance — permanent loss/freezing of unclaimed recovery funds proportional to the stale claimed amount.
2. **Denial of claims**: when the already-claimed user calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate (line 848), reverting and blocking that user's entire instant-claim path (including any other funded remainder) until... the revert is unconditional.

### Likelihood Explanation
The trigger requires an epoch where (a) at least one instant withdraw was funded via `collectInstantWithdrawFunds` and claimed, (b) at least one other instant request remains unfunded (`pendingInstantWithdraws != 0`), and (c) the borrower defaults and `finalizeDefaultRecovery` executes while `epochNumber` is still that epoch. Instant withdrawals are a supported mode (`setInstantWithdrawParams`, `allowInstantWithdraw`), partial funding is explicitly contemplated by the prefunded-reserve comments, and defaults are a core flow. No malicious privileged action is needed — only a normal user claim followed by an honest borrower default.

### Recommendation
In `claimInstantWithdrawRequest` (and anywhere a funded instant receipt is consumed), also delete `instantWithdrawsRequestsByEpoch[_user]` entries for the relevant epochs and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Alternatively, track the claimed amount per epoch so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` only count outstanding receipts, and make `_claimDefaultedInstantWithdrawRequest` saturate (`claimBasis = min(stored, instantWithdrawsRequests[_user])`) as defense-in-depth.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCDOEpochQueue.t.sol` harness; standard `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// 1. Epoch N running; enable instant withdraws via manager:
cdoEpoch.setInstantWithdrawParams(delay, minAprDiff, false);

// 2. Alice deposits, requests instant withdraw (AA).
cdoEpoch.requestInstantWithdraw(aliceShares, address(trancheAA));

// 3. Borrower/CDO funds Alice's request -> strategy.collectInstantWithdrawFunds(amount);
//    (driven via the normal epoch-start / funding path)
// 4. Warp past instantDelay; Alice claims.
vm.prank(alice); cdoEpoch.claimInstantWithdrawRequest();
//    instantWithdrawsRequests[alice] == 0
//    instantWithdrawsRequestsByEpoch[alice][N] == amount   // STALE
//    instantWithdrawClaimsByEpoch[N]        == amount   // STALE

// 5. Bob requests an instant withdraw in the SAME epoch N; it stays unfunded
//    (pendingInstantWithdraws == bobAmount > 0).

// 6. Borrower defaults; manager/guardian drive default + finalizeDefaultRecovery
//    while strategy.epochNumber() == N.
//    defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[N]
//    -> includes Alice's already-paid amount.
//    _defaultPrefundedInstantReserve() = claimsByEpoch[N] - pendingInstant
//    -> counts Alice's payout as held reserve.

// Assertions demonstrating the bug:
assertEq(strategy.instantWithdrawsRequestsByEpoch(alice, N), aliceAmount); // freed receipt still live
uint256 reserve = strategy.defaultRecoveryReserve();
assertGt(reserve, underlying.balanceOf(address(strategy))); // phantom reserve
// Bob's recovery claim succeeds; the next claimant's transfer reverts / reserve underflows.
vm.prank(alice); vm.expectRevert(); cdoEpoch.claimInstantWithdrawRequest(); // stale-entry underflow DoS
```

Caveat: I could not fully trace `IdleCDOEpochVariant`'s funding path for `collectInstantWithdrawFunds` within the available iterations; the PoC assumes the standard honest flow where funded instant claims are payable during the same epoch that later defaults, consistent with the `_defaultPrefundedInstantReserve` comments describing exactly this partially-prefunded scenario.
