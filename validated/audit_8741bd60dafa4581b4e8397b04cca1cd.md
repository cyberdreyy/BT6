### Title
Peer signature acceptance bypasses the conflict/chainstate re-check that gates the signer's own signing path - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`store_and_process_block_signature` (`stacks-signer/src/v0/signer.rs:2442-2538`) can drive a signer to `mark_locally_accepted` and `broadcast_signed_block` a block purely because *other* signers' already-produced signatures accumulate to the 70% weight threshold. Unlike the local pre-commit→signature path (`handle_block_pre_commit`, `stacks-signer/src/v0/signer.rs:1250-1480`), which explicitly re-runs `check_block_against_signer_db_state` and the `get_signed_conflicts`/`conflict_still_blocks` guard immediately before producing/counting a signature, `store_and_process_block_signature` performs **no chainstate re-check at all** before broadcasting once weight from stored peer signatures crosses threshold.

### Finding Description
Two structurally different ways this signer's local acceptance state (`BlockInfo`) can reach `LocallyAccepted`/broadcast are documented in `docs/signer-flows.md` sections 5 and 6:

- Section 5 (`handle_block_pre_commit`, `stacks-signer/src/v0/signer.rs:1250-1480`): before signing, it re-runs `check_block_against_signer_db_state` (`RECHECK`) and then the own-signature conflict guard (`get_signed_conflicts` / `conflict_still_blocks` / `reorg_permit_stands`), specifically to catch the case where, between validation and reaching threshold, this same signer already signed a *different, conflicting* block at the same height (possibly in another tenure).
- Section 6 (`store_and_process_block_signature`, lines 2442-2538): when acceptances from peers accumulate weight ≥ threshold, the function goes straight from `mark_locally_accepted(true)` to `broadcast_signed_block` — no call to `check_block_against_signer_db_state`, no conflict-guard check.

Because `add_block_signature` persists every syntactically/cryptographically valid signature to the `block_signatures` table unconditionally (line 2454-2460), and `get_block_signatures` later re-reads *all* stored signatures for the hash (lines 2474-2477) to recompute `total_signature_weight`, a peer signature that arrived and was stored *before* this signer ever validated/pre-committed to the block (the "outdated peer" branch, lines 2462-2466) still counts toward the tally on a later pass, once this signer's own signature (or another peer's) is added. That later pass — the one that actually crosses the threshold and triggers `broadcast_signed_block` — never re-validates the block against this signer's current `signerdb` state.

This matches the report's bug class: state from one context (peer-observed acceptances, gathered without ever re-validating them against this signer's evolving local view) is merged/tallied into a threshold decision without re-checking the invariant that the dedicated pre-commit path enforces (no conflicting signed sibling, tenure-parent choice still valid, etc.), exactly as `setValidatorAddress` merged an old stake into a new address without re-checking `validatorMaxStake`.

### Impact Explanation
If, between the time this signer validated/pre-committed the block and the time enough peer acceptances land to cross 70% signature weight, this signer's own signerdb state changes such that the block would now fail `check_block_against_signer_db_state` (e.g., this signer itself has since signed a conflicting sibling at the same height, or the tenure-parent choice is no longer valid), the pre-commit path would catch and reject it — but the peer-signature-accumulation path does not. The signer would call `mark_locally_accepted(true)` and `broadcast_signed_block`/`handle_post_block` for a block its own logic considers stale/conflicting, undermining the "signature must not be superseded while fresh" invariant documented in section 5 (`docs/signer-flows.md:274-286`). This is a signer-side safety-relevant gap: the same signer instance can be made to relay/push a block it would otherwise refuse to sign, purely by timing peer acceptance messages so that the tally-crossing event happens in `store_and_process_block_signature` rather than in `handle_block_pre_commit`.

### Likelihood Explanation
This does not require a malicious majority — an attacker who controls network timing (delay a peer's pre-commit relative to their signature broadcast, or exploit the "outdated peer" fallback at lines 2462-2466) can arrange for the threshold-crossing event to occur inside `store_and_process_block_signature` instead of `handle_block_pre_commit`, for a block that this signer's local state has since flagged as conflicting. Because `add_block_signature`/`get_block_signatures` unconditionally persist and re-read every valid signature regardless of when it arrived relative to this signer's own pre-commit/validation timeline, the gap is reachable by ordinary gossip timing/ordering, one signer's local vantage point, and does not need a majority of malicious signers — it only needs enough total signature weight (from otherwise-honest peers) to cross 70%, arriving in the wrong order relative to this signer's local state transitions.

### Recommendation
Before calling `mark_locally_accepted(true)`/`broadcast_signed_block` in `store_and_process_block_signature`, re-run `check_block_against_signer_db_state` (and the same conflict-guard logic used in `handle_block_pre_commit`) exactly as the pre-commit path does, and reject/withhold broadcast if the checks no longer pass — regardless of whether the crossing signature came from this signer's own pre-commit flow or purely from tallying stored peer acceptances.

### Proof of Concept
1. Signer S validates and pre-commits block A at height H in tenure T (state `PreCommitted`, not yet `signed_self`).
2. Before pre-commit threshold is reached for A, S receives (and signs) block B, a conflicting sibling at height H in a different tenure T' that supersedes A per S's own signerdb state (S now has `signed_self` set on B).
3. Meanwhile, several other signers had already produced valid acceptance signatures over A (broadcast before they learned about B) and gossip delivers those signatures to S. Each arrival goes through `handle_block_signature` → `store_and_process_block_signature`; some of these arrive via the "outdated peer" branch (lines 2462-2466) and get parked as pre-commits, but their signatures are already persisted via `add_block_signature` at line 2454-2456.
4. A final peer's signature for A arrives after S already has `signed_self` set on B. `store_and_process_block_signature` recomputes `total_signature_weight` from all stored signatures for A (lines 2474-2496), crosses `min_weight`, and — with no call to `check_block_against_signer_db_state` or the conflict guard — calls `mark_locally_accepted(true)` and `broadcast_signed_block` for A (lines 2528-2538), even though S's own state already treats A as conflicting/superseded by B.

Note: I was not able to execute this scenario in a live cluster; the analysis is based on static code/flow-doc review of `stacks-signer/src/v0/signer.rs` and `docs/signer-flows.md` sections 5-6, and I could not fully confirm whether some upstream caller (e.g. `handle_event_match`) imposes an additional guard I did not locate. This should be validated against the actual runtime behavior before treating it as fully confirmed.
