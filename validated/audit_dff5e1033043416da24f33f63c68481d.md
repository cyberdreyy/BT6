### Title
Unbounded Zstd compression cost in `encode_ui_account`'s `Base64Zstd` path allows single-request CPU/memory cost scaling to max account size (10MB) - (File: account-decoder/src/lib.rs)

### Summary
`encode_ui_account` compresses the full account data with `zstd::stream::write::Encoder` whenever `UiAccountEncoding::Base64Zstd` is requested, with no length check or explicit compression-size cap before calling into zstd. Because `getAccountInfo`/`getMultipleAccounts` let an unprivileged client request this encoding for any account pubkey, a single request against an account holding maximum-size (`MAX_PERMITTED_DATA_LENGTH`, 10MB), incompressible data forces the RPC thread to perform a full-size zstd compression pass, with cost bounded only by on-chain account size rather than an RPC-specific limit.

### Finding Description
`encode_ui_account` in the `Base64Zstd` branch does:
```
UiAccountEncoding::Base64Zstd => {
    let mut encoder = zstd::stream::write::Encoder::new(Vec::new(), 0).unwrap();
    match encoder
        .write_all(slice_data(account.data(), data_slice_config))
        .and_then(|()| encoder.finish())
``` [1](#0-0) 

This is reached from `get_account_info` and `get_multiple_accounts` via `get_encoded_account` -> `encode_account` -> `encode_ui_account`, with no size check applied for the `Base64Zstd` case (only `Binary`/`Base58` have a `MAX_BASE58_BYTES` guard): [2](#0-1) [3](#0-2) 

Since compression cost/memory scales with input size and worst-case (incompressible/random) data does not shrink, and Solana account data can be as large as `MAX_PERMITTED_DATA_LENGTH` (10MB, enforced at the runtime/account-write layer, not at the RPC read layer), an attacker can pre-fund an account of near-maximum size filled with random bytes and then repeatedly query it via `getAccountInfo`/`getMultipleAccounts` with `encoding: "base64+zstd"`. Each call runs on `spawn_blocking` (a bounded thread pool), so this ties up an RPC worker thread doing full-size compression per request, unbounded by any RPC-specific data-size cap — the only bound is the protocol-level max account size, which is far larger than what would be reasonable for a per-request compression budget.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" category: a client issuing requests at ≤1 per `CLUSTER_SLOT_TIME_TARGET / 2` can force the validator's JSON-RPC service to repeatedly perform CPU/memory work proportional to a 10MB buffer per call, using only the account-size limit as the effective bound instead of an explicit RPC guard (as exists for Base58 via `MAX_BASE58_BYTES`). This degrades RPC responsiveness for other users hitting the same node (resource-exhaustion type impact on the JSON-RPC service), though it does not crash the validator process or affect consensus.

### Likelihood Explanation
Feasible and repeatable with modest precondition: the attacker must first author (in a single prior transaction/session) an account containing near-`MAX_PERMITTED_DATA_LENGTH` random bytes, owned by any program the attacker controls or targets an existing large account. Once created, any client (not necessarily the same one) can trigger the costly RPC call any number of times within the allowed request rate, at low cost to the attacker but proportionally high cost to the RPC node each time.

### Recommendation
Add an explicit RPC-side size/complexity cap for `Base64Zstd` similar to the `MAX_BASE58_BYTES` check used for `Binary`/`Base58` — e.g., reject or fall back to `Base64` when `account.data().len()` (post data-slice) exceeds a documented threshold well below 10MB, in `encode_account` (`rpc/src/rpc.rs`) before calling `encode_ui_account`, or inside the `Base64Zstd` branch of `encode_ui_account` itself (`account-decoder/src/lib.rs`).

### Proof of Concept
```rust
// account-decoder/src/lib.rs (integration-style benchmark test)
use std::time::Instant;
use solana_account::{Account, AccountSharedData};
use solana_account_decoder::{encode_ui_account, UiAccountEncoding};
use solana_pubkey::Pubkey;
use rand::RngCore;

#[test]
fn test_base64_zstd_cost_scales_with_max_account_size() {
    let mut rng = rand::thread_rng();
    let mut data = vec![0u8; solana_sdk::system_instruction::MAX_PERMITTED_DATA_LENGTH as usize];
    rng.fill_bytes(&mut data); // incompressible

    let account = AccountSharedData::from(Account { data, ..Account::default() });

    let start = Instant::now();
    let _ = encode_ui_account(
        &Pubkey::default(),
        &account,
        UiAccountEncoding::Base64Zstd,
        None,
        None,
    );
    let elapsed = start.elapsed();

    // Expected (currently failing) assertion: cost should be capped by an
    // explicit RPC-level limit well below the max account size, e.g. bounded
    // time/memory regardless of data being near MAX_PERMITTED_DATA_LENGTH.
    assert!(elapsed.as_millis() < 50, "compression cost scaled with uncapped account size: {:?}", elapsed);
}
```
Run this alongside a smaller-size case (e.g., 10KB) to demonstrate the near-linear scaling of CPU time up to the 10MB maximum, confirming the lack of an explicit cap independent of on-chain data size.

```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
