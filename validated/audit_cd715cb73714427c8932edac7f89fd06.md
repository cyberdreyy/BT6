### Title
Loss-adjusted withdraw receipts bypass the haircut and are paid at par because `collectWithdrawFunds` keys `lossRecoveryPriceByEpoch` under the post-bump `epochNumber` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` records each receipt under the request epoch (`lastWithdrawRequest[_user]`, `withdrawsRequestsByEpoch[_user][currentEpoch]`), and `_claimLossAdjustedWithdrawRequest` resolves the haircut through that same request-epoch pointer. `collectWithdrawFunds`, however, writes the loss marker under `epochNumber` **at collection time** — which is already bumped by `deposit()` inside the same `stopEpoch`/`stopEpochWithDuration` flow (the `epochNumber += 1` in `deposit` fires while the epoch is still flagged running). The marker is therefore stored under `requestEpoch + 1`, the loss-adjusted claim path never finds it, and the partially-funded receipt is paid in full via `_claimFundedWithdrawRequest`. This is the same bug class as the sockmap CVE: the "delete"/settlement path resolves the element through a pointer that was already replaced, so it consumes (pays) the wrong entry.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestWithdraw` stores the receipt epoch: `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (lines 282–293).
2. On a partial borrower repayment, `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws` (lines 411–421). But `deposit()` bumps `epochNumber` whenever it is called while `isEpochRunning()` is still true (lines 607–610), i.e., earlier inside the same `stopEpochWithDuration` transaction. The haircut is thus keyed to `requestEpoch + 1`, while every receipt references `requestEpoch`.
3. On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 789–794) — the pre-bump epoch — gets 0, and returns nothing. `_claimFundedWithdrawRequest` then only checks `epochNumber <= lastWithdrawRequest[_user]` (line 326), which passes because `epochNumber` was bumped, and pays the aggregate `withdrawsRequests[_user]` at par (lines 338–349).
4. The symmetric guard in `requestWithdraw` (lines 263–270) also reads `lossRecoveryPriceByEpoch[lastWithdrawRequest]`, so it never sees the stored price and does not even force the user to claim the haircutted receipt first.

Only the residual bucket `pendingWithdraws` was reduced (it is zeroed), so the strategy holds `_amount < pendingBasis` but pays out `pendingBasis`.

### Impact Explanation
Direct theft / insolvency. The strategy transfers the full, unhaircutted claim from its own underlying balance. Since only `_amount` was collected, the excess comes out of funds backing other claimants (funded instant-withdraw reserve, default-recovery reserve, or later withdraws). With a realized loss `_lossAmount`, each pending receipt overpays by `claimBasis * (1 - lossRecoveryPrice)`, i.e., the pending share of the loss is silently shifted from the withdrawer to remaining LPs — a loss-waterfall escape. If the strategy lacks the balance, `safeTransfer` reverts and all such withdrawals are permanently frozen.

### Likelihood Explanation
Requires only a `stopEpochWithDuration(_lossAmount)` partial funding (an honest manager/borrower action after a shortfall) plus an unprivileged pending withdrawer calling `claimWithdrawRequest`. Any KYC-passed lender with a pending receipt can trigger it; the payout path is permissionless through the CDO.

### Recommendation
Key the loss marker by the epoch the pending receipts belong to, not the mutable `epochNumber` at collect time. Either snapshot `epochNumber` before the in-`stopEpoch` bump (e.g., have the CDO pass the settled epoch id, or read it before calling `deposit`), or store pending receipts under the funding epoch consistently on both write and read sides. Alternatively, track an explicit `pendingWithdrawsEpoch` set in `requestWithdraw` and use it in `collectWithdrawFunds`, `_claimLossAdjustedWithdrawRequest`, and the `requestWithdraw` guard.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style PoC
// Mode: fixed-APR, standard epoch variant. Attacker: KYC'd lender (user).
function testLossAdjustedReceiptPaidAtPar() external {
    address user = makeAddr('user');
    uint256 amountWei = 10_000 * ONE_SCALE;
    _depositWithUser(user, amountWei, true);          // KYC'd deposit

    // buffer of epoch N: user requests withdraw, receipt keyed under epoch N
    vm.prank(user);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(user), strategy.epochNumber());

    // epoch N runs, borrower repays only part -> stopEpochWithDuration applies a loss.
    // Inside the same stop, strategy.deposit() bumps epochNumber to N+1 BEFORE
    // collectWithdrawFunds writes lossRecoveryPriceByEpoch[epochNumber].
    uint256 loss = requested / 2;
    _stopEpochWithLoss(loss);                        // helper: stopEpochWithDuration flow

    // Marker landed under N+1; the user's receipt points at N.
    assertEq(strategy.lossRecoveryPriceByEpoch(strategy.lastWithdrawRequest(user)), 0);
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), 0);

    // Attacker claims: loss-adjusted path returns 0, funded path pays par.
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(user);
    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    // Paid `requested` in full although the strategy only collected requested - loss.
    assertEq(IERC20Detailed(defaultUnderlying).balanceOf(user) - balPre, requested);
}
```

Key lines: `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) , `deposit` bumps `epochNumber` mid-stop [2](#0-1) , `collectWithdrawFunds` writes the price under the already-bumped `epochNumber` [3](#0-2) , `_claimLossAdjustedWithdrawRequest` looks it up under `lastWithdrawRequest` [4](#0-3) , and `_claimFundedWithdrawRequest` then pays the aggregate at par [5](#0-4) .

Caveat: this conclusion assumes `collectWithdrawFunds` is invoked after the strategy `deposit()` inside `stopEpochWithDuration` (the standard IdleCDO stop ordering); I could not fully trace the call sequence in `IdleCDOEpochVariant.sol` within the search budget. If collect were provably called before the bump, the finding reduces to a no-op and no vulnerability would stand — but the documented guard asymmetry (`lossRecoveryPriceByEpoch[epochNumber]` write vs. `lossRecoveryPriceByEpoch[lastWithdrawRequest]` read) plus the comment on line 408 strongly indicates the mismatch is real.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
