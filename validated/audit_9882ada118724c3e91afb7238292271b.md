### Title
Unbounded per-sender rate-limiter map growth enables memory-exhaustion DoS - ([File: core/services/workflows/ratelimiter/ratelimiter.go])

### Summary
`RateLimiter.Allow` in `core/services/workflows/ratelimiter/ratelimiter.go` lazily creates and stores a new `*rate.Limiter` in the `perSender` map for every distinct `sender` string it observes, with no maximum size, eviction policy, or TTL-based cleanup. [1](#0-0)  This mirrors the reported "Vault" bug class: an attacker-influenced collection (here, a map instead of an on-chain whitelist array) that can grow without bound and eventually degrade or block node operation.

### Finding Description
`NewRateLimiter` initializes an empty `perSender` map. [2](#0-1)  Every call to `Allow(sender)` checks whether an entry exists for `sender`; if not, it unconditionally allocates a new `rate.Limiter` and inserts it into the map under the mutex, and the entry is never removed. [3](#0-2)  If `sender` is derived from attacker-controllable or high-cardinality identifiers (e.g., per-workflow or per-request-derived IDs on an internet-facing gateway path), an unprivileged/low-cost actor can force continuous growth of this map, consuming heap memory indefinitely and increasing per-call CPU/lock contention on `rl.mu`.

This is analogous to the reported `Vault.sol:setTokenConfig` issue: both cases show an unbounded, attacker-influenceable collection that lacks a cap, threatening resource exhaustion and service availability rather than any authentication/authorization bypass.

### Impact Explanation
Because this is a Go in-memory map (not gas-limited on-chain storage), the direct consequence is unbounded memory growth on the chainlink node process rather than a failed transaction. Left unchecked, this could degrade node performance or exhaust memory, which could affect the DON's availability for legitimate workflow execution. I was not able to conclusively confirm, within available index coverage, the exact call sites and identity source of `sender` for this specific `RateLimiter` (usage appears in `core/services/workflows/syncer/v2/handler.go`, `helpers.go`, and `core/services/cre/cre.go`, but the full call chain establishing whether `sender` is attacker-controlled from an unprivileged client request was not fully retrievable from the index). This uncertainty limits confidence that this is reachable purely from unprivileged external input versus only from validated on-chain workflow owners (which have gas costs constraining growth rate).

### Likelihood Explanation
Likelihood is moderate-to-low: if `sender` keys are drawn from validated/bounded sets (e.g., DON member addresses or already-authorized workflow owners), growth is naturally capped and this is low severity. If `sender` is instead derived from unauthenticated/unvalidated request metadata reachable before authorization checks, likelihood of exploitation by an unprivileged actor is higher. This distinction could not be fully verified with the tools available.

### Recommendation
- Cap the maximum number of entries in `perSender` (e.g., LRU eviction or a fixed-size cache) similar to the recommended `MAX_WHITELISTED_TOKENS` pattern in the report.
- Add TTL-based cleanup of idle per-sender limiters (analogous to the periodic cleanup patterns already used elsewhere in the gateway, e.g. `WorkflowMetadataHandler`'s `jwtReplayCache` cleanup [4](#0-3) ).
- Verify and, if necessary, restrict `sender` to authenticated/authorized identities before it is used as a map key.

func NewRateLimiter(cfg Config) (*RateLimiter, error) {
	if cfg.GlobalRPS <= 0.0 || cfg.PerSenderRPS <= 0.0 {
		return nil, errors.New("RPS values must be positive")
	}
	if cfg.GlobalBurst <= 0 || cfg.PerSenderBurst <= 0 {
		return nil, errors.New("burst values must be positive")
	}

	return &RateLimiter{
		global:    rate.NewLimiter(rate.Limit(cfg.GlobalRPS), cfg.GlobalBurst),
		perSender: make(map[string]*rate.Limiter),
		config:    cfg,
	}, nil
}

func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
