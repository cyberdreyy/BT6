### Title
Double-decrement of `pendingWithdraws` permanently freezes loss-adjusted withdraw claims after default finalization - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The invalid-free bug class (releasing the same resource twice) maps to `IdleCreditVault.claimWithdrawRequest`: once a stop-epoch loss has already "freed" the `pendingWithdraws` bucket via `collectWithdrawFunds`, a later default finalization in the same epoch causes `_claimDefaultedWithdrawRequest` to decrement that already-zeroed bucket a second time, reverting and freezing the affected users' funded claims forever.

### Finding Description
`collectWithdrawFunds` is called by the CDO during `stopEpoch`/`stopEpochWithDuration`. When the borrower funds less than `pendingBasis`, the strategy records a haircut and clears the aggregate bucket:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:417-421
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
if (lossRecoveryPrice == 0) revert NotAllowed();
pendingWithdraws = 0;
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

Those receipts are meant to be paid later through `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-801`). However, if the same epoch is then finalized as a default (`finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` at `IdleCreditVault.sol:693` — `epochNumber` does not change between stop and finalization), `claimWithdrawRequest` routes through `_claimDefaultedWithdrawRequest` first (`IdleCreditVault.sol:303-312`). For any user whose receipt lives in that epoch, `_withdrawClaimAmountsForEpoch` returns a non-zero `claimBasis`, and then:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:778
pendingWithdraws -= claimBasis;
```

`pendingWithdraws` is already `0`, so the subtraction underflows (Solidity 0.8 checked arithmetic) and the whole call reverts. Because the defaulted-claim branch runs before the loss-adjusted branch on every call, the revert is permanent — the user can never reach `_claimLossAdjustedWithdrawRequest`, and the underlying already transferred in by `collectWithdrawFunds` is locked in the strategy.

### Impact Explanation
Permanent freezing of user funds. Every user who requested a normal/APR0 withdraw in the epoch that both (a) took a `stopEpoch`/`stopEpochWithDuration` loss (or zero-funding default stop that still recorded a `lossRecoveryPriceByEpoch`) and (b) was later finalized via `finalizeDefaultRecovery` loses access to their already-funded, loss-adjusted payout. The magnitude equals the sum of those receipts' `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, i.e. up to the full funded remainder of the epoch's pending withdrawals. The "one receipt, one payout" invariant is broken by freeing the `pendingWithdraws` bucket twice — once by clearing it at loss funding and again by decrementing it per-claim during default recovery.

### Likelihood Explanation
The sequence only requires unprivileged users holding pending withdraw receipts, plus ordinary honest-role actions: borrower fails to fully fund the epoch, manager calls `stopEpoch`/default flow, then `finalizeDefault`/`finalizeDefaultRecovery`. No existing guard stops it: `_ensureDefaultRecoveryInitialized` only runs once, `requestWithdraw`'s loss-receipt guard (`IdleCreditVault.sol:263-271`) protects the request path, not the claim path, and nothing in `_claimDefaultedWithdrawRequest` checks whether the claimBasis was already removed from `pendingWithdraws` by the loss branch of `collectWithdrawFunds`. Users only escape if they happen to claim in the window between loss funding and default finalization — a window that may not exist when the epoch stops directly into default.

### Recommendation
In `_claimDefaultedWithdrawRequest` (or inside `_clearWithdrawClaimForEpoch`), only decrement `pendingWithdraws` by the portion of `claimBasis` still present in the bucket, e.g. track per-epoch pending basis or clamp with `pendingWithdraws = claimBasis >= pendingWithdraws ? 0 : pendingWithdraws - claimBasis` in the same style used for `pendingInstantWithdraws` at `IdleCreditVault.sol:852`. Alternatively, have `_claimDefaultedWithdrawRequest` skip receipts whose epoch already has a `lossRecoveryPriceByEpoch` entry and let `_claimLossAdjustedWithdrawRequest` pay them.

// Foundry fork test against the real pool configuration
function testLossEpochThenDefaultFreezesClaim() external {
    address user = makeAddr('victim');
    uint256 amount = 10_000 * ONE_SCALE;

    // buffer phase: user deposits and requests a normal withdraw in epoch N
    _depositWithUser(user, amount, true);
    vm.prank(user);

    _startEpochAndCheckPrices(0);

    // sets lossRecoveryPriceByEpoch[lossEpoch] and pendingWithdraws = 0
    uint256 partial = _expectedFundsEndEpoch() / 2;
    _stopEpochAndCheckPrices(0, initialProvidedApr, partial);
    _checkDefault();

    // manager finalizes default recovery in the same epochNumber
    uint256 recovered = /* recovery amount */;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);

    // _claimDefaultedWithdrawRequest underflows on `pendingWithdraws -= claimBasis`
