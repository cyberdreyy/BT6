### Title
Global-only `maxCacheSize` enforcement in `requestCache.NewRequest` allows a single sender to exhaust the shared pending-request pool and deny service to other subscribers - ([File: core/services/gateway/handlers/common/requestcache.go])

### Summary
`requestCache.NewRequest` enforces only a single global counter (`len(c.cache) >= maxCacheSize`) with no per-sender/per-subscriber quota, so any one authenticated sender who keeps generating unique `MessageId` values can occupy the entire shared cache capacity, causing legitimate `NewRequest` calls from unrelated senders to fail with "request cache is full". The only pre-existing mitigation is the caller-configured per-sender rate limiter (`PerSenderRPS`/`PerSenderBurst`), which throttles request *rate* but does not cap the total number of *concurrently pending* entries a single sender can hold in the cache.

### Finding Description
`NewRequest` keys entries as `globalId{sender, id}` and only rejects a request when the exact `(sender, MessageId)` pair already exists (line 61); it then checks a single package-level `len(c.cache) >= int(c.maxCacheSize)` bound shared by all senders (line 64), with no accounting of how many entries belong to which sender: [1](#0-0) 

Entries remain in the cache until either a full response is aggregated (`ProcessResponse`/`deleteAndSendOnce`) or the per-request `timeout` timer fires, so an entry's lifetime is bounded by `timeout`, not by how quickly the sender issues requests: [2](#0-1) 

Even where callers configure a `PerSenderRPS`/`PerSenderBurst` rate limiter (seen in the v2 capabilities handler config schema) that throttles the *arrival rate* of new requests, it does not bound the *number of simultaneously outstanding (still-pending)* requests a sender can accumulate over the `timeout` window. Because `timeout` can be tens of seconds, a sender operating within any configured per-sender RPS can still steadily accumulate pending unique-`MessageId` entries until the shared `maxCacheSize` is reached, at which point *all* senders (including unrelated, paying subscribers) are rejected with "request cache is full", independent of their own request rate.

### Impact Explanation
This is a resource-exhaustion / quota-isolation bypass: one unprivileged sender with a single valid signing key can deny DON execution slots to other subscribers sharing the same `requestCache` instance, because the cache has no per-sender partitioning or fairness — it is a single shared bounded map. This matches a denial-of-service / quota-bypass impact class rather than data disclosure or fund movement, but it directly violates per-user quota isolation and can starve other paying subscribers' legitimate requests.

### Likelihood Explanation
Preconditions are minimal: only one valid signing identity/API credential capable of sending signed gateway requests is required, no privilege escalation or authentication bypass is needed. The attack is fully repeatable as long as the attacker can sustain a rate of unique `MessageId` submissions under the configured `PerSenderRPS`/`PerSenderBurst` limit (if any is even configured for the specific handler) long enough to accumulate `maxCacheSize` pending entries before earlier ones expire or get answered. Feasibility depends on the configured `maxCacheSize` and `timeout` values, which are deployment-specific, but the code path itself has no internal per-sender safeguard regardless of configuration.

### Recommendation
Add a per-sender (or per-subscription) limit inside `requestCache`, e.g., track counts per `sender` key and reject `NewRequest` when a sender's own outstanding-entry count exceeds a configured per-sender maximum, in addition to (or instead of relying solely on) the external RPS-based rate limiter. This ensures the global `maxCacheSize` acts as a backstop rather than the sole quota mechanism, and prevents any single sender's pending requests from crowding out others.

### Proof of Concept
Table test in `core/services/gateway/handlers/common/requestcache_test.go`:
1. Construct `cache := common.NewRequestCache[requestState](time.Hour, N)` with small `N` (e.g., 3).
2. From `sender = "attacker"`, issue `N` `NewRequest` calls with distinct `MessageId`s ("m1".."mN"), all succeeding (`require.NoError`).
3. From a different `sender = "victim"` with a new unique `MessageId`, call `NewRequest` and assert it fails with `"request cache is full"` (`require.ErrorContains(t, err, "request cache is full")`), demonstrating that one sender's requests can fully deny another sender's legitimate request despite no overlap in keys or duplicate `MessageId`s. func TestRequestCache_MaxSize(t *testing.T) {
	t.Parallel()

	cache := common.NewRequestCache[requestState](time.Hour, 2)
	callback := common.NewCallback()
	lggr := logger.Test(t)
	initialState := &requestState{}

	req := &api.Message{Body: api.MessageBody{MessageId: "aa", Sender: "0x1234"}}
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "bb"
	require.NoError(t, cache.NewRequest(lggr, req, callback, initialState))

	req.Body.MessageId = "cc"
	require.Error(t, cache.NewRequest(lggr, req, callback, initialState))
}
