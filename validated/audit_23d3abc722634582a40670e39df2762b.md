### Title
`base_insertValidatedTransaction` skips signature verification and trusts a caller-supplied `sender` address, letting any RPC caller inject spoofed-sender transactions into the pool - ([File: crates/execution/txpool/src/builder/rpc.rs])

### Summary
`base_insertValidatedTransaction` is a JSON-RPC method (namespace `base`) registered on builder/sequencer nodes via `BuilderApiExtension` [1](#0-0)  and mounted directly on the node's RPC module set (the same RPC server process used for the node's other JSON-RPC namespaces) [2](#0-1) . Its handler decodes the raw EIP-2718 bytes but constructs the pooled transaction with `Recovered::new_unchecked(consensus_tx, sender)`, where `sender` is a field taken verbatim from the caller's request payload rather than recovered from the transaction's ECDSA signature [3](#0-2) . The doc comment on the trait explicitly states the design intent: "allowing the builder to skip signature verification" because "the sender addresses are trusted from the forwarding mempool node" [4](#0-3) . There is no authentication, API key, or mTLS check inside this RPC handler itself — trust is enforced only by network-level isolation of the builder RPC port, which is the same "trust the caller, no code-level auth" pattern that caused CVE-2026-41473 (CyberPanel's unauthenticated AI-scanner webhook/callback endpoints trusting attacker-supplied data for DB writes).

### Finding Description
`insert_validated_transaction` takes a `ValidatedTransaction<E>` struct with a `sender: Address` field supplied directly by the RPC caller [5](#0-4) . After decoding the raw transaction bytes, it builds a `Recovered` value using `Recovered::new_unchecked`, which — unlike `recover_signer`/`recover_signer_unchecked` on `BasePooledTransaction` [6](#0-5)  — does **not** perform ECDSA recovery from the signature at all; it simply pairs the caller-supplied `sender` with the decoded transaction body. The resulting `BasePooledTransaction` is inserted straight into the pool via `add_external_transaction` (or `add_transaction` for extension-bearing transactions) [7](#0-6) .

Because `sender` is attacker-controlled and never checked against the transaction's actual signature (or checked for a valid signature at all — a transaction with a garbage/zero signature but valid EIP-2718 type framing will still decode), any caller who can reach this RPC method can:
- Attribute a transaction to an arbitrary address it does not control, without providing a valid signature for that address.
- Enter the pool under `TransactionOrigin::External`/`Private`, which is the same origin classification used for legitimately-forwarded transactions, so downstream logic (metrics, journaling, and eventual block building) treats these entries as fully validated.

The only protection against a hostile network client is that this RPC surface is *supposed to be* deployed on an internal-only port reachable solely by trusted mempool nodes doing legitimate forwarding — exactly the deployment/network-isolation assumption that failed for CyberPanel's `/api/ai-scanner/status-webhook` and `/api/ai-scanner/callback`, both also "internal" endpoints that ended up reachable by unauthenticated remote attackers. Unlike the ordinary `eth_sendRawTransaction` ingestion path, which does recover and validate signer via the pool validator [8](#0-7) , this path is explicitly designed to bypass that check.

### Impact Explanation
If `base_insertValidatedTransaction` is reachable by an untrusted caller (misconfiguration, missing network ACL, exposed builder RPC port, or an SSRF/pivot from another component), an attacker can:
- Insert transactions attributed to victim addresses without their signature, corrupting the pool's sender-indexed state and potentially causing nonce/fee bookkeeping confusion, pool eviction of legitimate transactions from the spoofed sender's slot, and misleading transaction-event journal entries (`TXPOOL_VALIDATED_INSERT_ACCEPTED`) that downstream systems and operators rely on for audit and block-inclusion decisions.
- Fill the pool with garbage entries under fabricated senders, a resource-exhaustion/DoS vector analogous to CyberPanel's "storage exhaustion" and "corrupt scan history records" impact, but here applied to consensus-relevant mempool state rather than an audit DB.
- Potentially reach block building/inclusion if pool insertion succeeds, since this API exists specifically to feed the builder's block-production path, unlike a monitoring sink.

This is a plausible High-severity issue if the RPC namespace is exposed without network isolation, matching the CVSS profile of the source report (unauthenticated write primitive with integrity impact). I was not able to confirm from the indexed code whether any deployment consistently binds this RPC port to a private/loopback interface only, versus binding on `0.0.0.0` alongside the public `eth_*` namespace on the same JSON-RPC server (as suggested by `ctx.modules.add_or_replace_configured`/`merge_configured` sharing one RPC module set with other node namespaces).

### Likelihood Explanation
Likelihood is moderate to low depending on operational network segmentation: the code intentionally omits any authentication and states in comments that senders are "trusted from the forwarding mempool node," but nothing in the RPC handler itself enforces that trust — it is an operational/deployment control, not a protocol/code guarantee. If the builder/sequencer RPC listens on the same host:port as the node's public `eth_*` API (the extension is applied to the shared `BaseRpcContext` module set), or if network ACLs are misconfigured, this becomes directly exploitable by any RPC client, matching the "reachable via public eth_*/RPC surface" scoping criterion.

### Recommendation
- Require `insert_validated_transaction` callers to supply a real signature and recover the sender via `recover_signer`/`recover_signer_unchecked` instead of trusting an unauthenticated `sender` field, or gate this RPC method behind mutual authentication (mTLS client cert / shared-secret HMAC) so trust is enforced in code, not just by network topology.
- If the "skip signature verification" design must be kept for performance, bind this RPC module to a dedicated internal-only listener (never merged into the same module set as public `eth_*` namespaces) and add an explicit authentication middleware check inside the handler itself, following the pattern already used for other "SECURITY: unauthenticated internal endpoint" services but hardened with an actual authentication layer rather than a documentation warning.
- Add defense-in-depth: reject `insert_validated_transaction` calls where the decoded transaction's own signature does not recover to the supplied `sender` (i.e., stop using `new_unchecked` unconditionally), even if slower.

    async fn insert_validated_transaction(&self, tx: ValidatedTransaction<E>) -> RpcResult<()> {
        debug!(
            sender = %tx.sender,
            "rpc::insert_validated_transaction"
        );
        let sender = tx.sender;
        let has_extensions = !tx.extensions.is_empty();

        if has_extensions && !self.accept_extensions {
            BuilderApiMetrics::extension_errors().increment(1);
            return Err(ErrorObjectOwned::owned(
                ErrorCode::InvalidParams.code(),
                "transaction extensions are disabled",
                None::<()>,
            ));
        }

        tx.extensions.validate(self.max_extension_items).map_err(|e| {
            BuilderApiMetrics::extension_errors().increment(1);
            ErrorObjectOwned::owned(ErrorCode::InvalidParams.code(), e.to_string(), None::<()>)
        })?;

        // Decode the EIP-2718 transaction bytes
        let consensus_tx =
            BaseTransactionSigned::decode_2718(&mut tx.raw.as_ref()).map_err(|e| {
                BuilderApiMetrics::decode_errors().increment(1);
                ErrorObjectOwned::owned(
                    ErrorCode::InvalidParams.code(),
                    format!("failed to decode transaction: {e}"),
                    None::<()>,
                )
            })?;
        let tx_hash = *consensus_tx.hash();
        let encoded_len = tx.raw.len();

        let recovered = Recovered::new_unchecked(consensus_tx, sender);
        let pool_tx = BasePooledTransaction::new(recovered, encoded_len);

    fn validate_one_with_state_inner(
        &self,
        origin: TransactionOrigin,
        transaction: Tx,
        state: &mut Option<Box<dyn AccountInfoReader + Send>>,
    ) -> TransactionValidationOutcome<Tx> {
        if transaction.is_eip4844() {
            return TransactionValidationOutcome::Invalid(
                transaction,
                InvalidTransactionError::TxTypeNotSupported.into(),
            );
        }

        if transaction.as_eip8130().is_some() {
            let validation = {
                let signed = transaction.as_eip8130().expect("checked above");
                self.validate_eip8130_structural(signed)
                    .and_then(|()| self.validate_eip8130_full(signed))
            };
            let state = match validation {
                Ok(state) => state,
                Err(err) => return TransactionValidationOutcome::Invalid(transaction, err),
            };
            let propagate =
                matches!(origin, TransactionOrigin::External | TransactionOrigin::Local);
            transaction.set_watch_set(state.watch_set.clone());
            transaction.set_watch_manifest(state.manifest.clone());
            transaction.set_limit_class(LimitClass {
                sender: state.sender,
                payer: state.payer,
                classification_generation: state.classification_generation,
                sender_locked: state.sender_locked,
                payer_locked: state.payer_locked,
                payer_trusted: state.payer_trusted,
                payer_balance: state.payer_balance,
                max_cost: state.payer_max_cost,
            });
            let outcome = TransactionValidationOutcome::Valid {
                balance: state.payer_balance_after_auth,
                state_nonce: state.sender_nonce,

                bytecode_hash: state.sender_bytecode_hash,
                authorities: (state.payer != state.sender).then_some(vec![state.payer]),
            };
            return self.apply_base_checks(outcome, state.payer_auth);
        }
