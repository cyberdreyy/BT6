### Title
Cross-epoch instant-withdraw receipt confusion pays unfunded pre-default claims at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE is a "confusable identity" bug: characters from disjoint namespaces are rendered as if they belonged to the same identity, letting a look-alike claim pass as a legitimate one. The structural analog in `IdleCreditVault` is that instant-withdraw receipts are tracked both per-epoch (`instantWithdrawsRequestsByEpoch`) and in an epoch-agnostic aggregate (`instantWithdrawsRequests`). During default finalization only the *current* epoch's basis is haircut, while the funded-claim path pays the *aggregate* at par. An unfunded instant receipt minted in an earlier epoch is therefore "confused" with a funded receipt and can be redeemed 1:1 after `finalizeDefaultRecovery`, stealing recovery/funded assets from the defaulted epoch's claimants.

### Finding Description
`requestInstantWithdraw` mints receipt strategy tokens to `_user` and records the claim under `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, but settlement accounting lives in the epoch-less `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` counters (`IdleCreditVault.sol:356-375`). `pendingInstantWithdraws` is only decremented when `collectInstantWithdrawFunds` pulls money (`:398-403`), so an instant request that the borrower never funds at `stopEpoch` survives into later epochs — the `epochNumber` key it was written under becomes stale.

At default finalization, `defaultPendingClaimBasis` only folds in `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — whenever `pendingInstantWithdraws != 0` (`:644-649`). Instant receipts keyed under older epochs are simply absent from the recovery basis, so `defaultRecoveryPrice` is computed against too small a `totalBasis`, inflating the price paid to current-epoch/active claimants and leaving no reserve slice for the stale receipt.

Then `claimInstantWithdrawRequest` runs: after clearing the current-epoch defaulted portion at `defaultRecoveryPrice`, it burns the *full* `instantWithdrawsRequests[_user]` aggregate — which still contains the stale, never-funded old-epoch receipt — and calls `_transferFundedClaim` (`:380-393`). `_transferFundedClaim` only guards `balance - defaultRecoveryReserve >= _amount` (`:897-907`); it has no notion that part of the aggregate was never funded by any epoch's `collectInstantWithdrawFunds`. Any underlying sitting in the strategy outside the recovery reserve (e.g., borrower repayments routed back through the vault, direct token sends, funds collected for other receipts) can be pulled at par by a claim that should have been haircut to `defaultRecoveryPrice` or left unclaimable.

### Impact Explanation
An unprivileged lender holding a tranche position requests an instant withdrawal in epoch N that goes unfunded (borrower remits less than `pendingInstantWithdraws`, or the CDO's available liquidity is insufficient). Epoch N+1 starts, the borrower defaults, `finalizeDefaultRecovery` runs with the stale receipt excluded from basis. The attacker then calls `claimWithdrawRequest`/`claimInstantWithdrawRequest` via the CDO and receives the stale receipt's face value at 1:1 instead of `defaultRecoveryPrice`, while true defaulted-epoch claimants receive `(claimBasis * defaultRecoveryPrice) / 1e18` from an already-diluted reserve. Loss equals `staleReceipt * (1 - defaultRecoveryPrice)` — direct theft of recovery/funded assets, breaking the "one receipt, one haircut-adjusted payout" invariant and the fairness of the loss waterfall.

### Likelihood Explanation
The path requires an unfunded instant-withdraw receipt surviving an epoch boundary followed by a borrower default — plausible in stressed epochs precisely when defaults occur, since unfunded instant queues and defaults correlate. Attacker needs only a KYC'd lending position (any permitted requester qualifies) and normal transaction ordering around honest owner/manager/borrower calls. The guards that exist (`_onlyIdleCDO`, `defaultRecoveryFinalized`, reserve check in `_transferFundedClaim`, address-bound receipts in `_transfer`) all operate on the aggregate/epoch keys separately and none reconcile the two namespaces, so the confusion is unblocked.

### Recommendation
Track funded vs unfunded instant basis per epoch instead of relying on `instantWithdrawClaimsByEpoch[epochNumber]`: include *all* epochs' outstanding instant basis in `defaultPendingClaimBasis` (e.g., keep a `totalInstantClaimBasis` or iterate a per-user epoch list), and in `claimInstantWithdrawRequest` only treat amounts whose epoch's funding was collected as par-payable. Alternatively, forbid new instant requests while `pendingInstantWithdraws` carries unfunded basis from a prior epoch, mirroring the `requestWithdraw` guard on `lossRecoveryPriceByEpoch`.

### Proof of Concept
Foundry fork outline:

```solidity
// test foundry fork against deployed IdleCDOEpochVariant + IdleCreditVault
function testStaleInstantReceiptPaidAtPar() public {
    // epoch N running, isInterestMinted mode, strategy holds liquidity
    deal(USDC, lender, 1_000_000e6);
    vm.prank(lender); cdo.depositAA(500_000e6);            // lender enters

    vm.prank(manager); cdo.startEpoch();                  // epoch N starts (epochNumber = n)

    // Attacker (KYC'd lender) requests instant withdraw; borrower/CdO funds only part
    vm.prank(attacker); cdo.requestInstantWithdraw(100_000e6); // receipt minted, epoch key = n
    // collectInstantWithdrawFunds called with 0 / less than 100k -> pendingInstantWithdraws stays > 0

    skip(epochDuration);
    vm.prank(manager); cdo.stopEpoch(interest);           // epochNumber -> n+1, stale receipt persists
    vm.prank(manager); cdo.startEpoch();                  // epoch n+1 running

    // borrower defaults; owner finalizes with partial recovery, say 50%
    vm.prank(manager); cdo.stopEpochWithDuration(0, loss);
    // finalizeDefaultRecovery pulls recovery funds; basis excludes attacker's epoch-n receipt
    // defaultRecoveryPrice inflated because stale claimBasis was omitted

    uint256 balBefore = usdc.balanceOf(attacker);
    vm.prank(attacker); cdo.claimInstantWithdrawRequest();
    uint256 got = usdc.balanceOf(attacker) - balBefore;

    // attacker is paid ~par on an unfunded receipt instead of recovery-price
    assertGt(got, 100_000e6 * strategy.defaultRecoveryPrice() / 1e18);
}
```

The assertion captures the broken invariant: an instant receipt whose "identity" (epoch key `n`) was never funded is paid as if it were a funded/current claim because the aggregate counter `instantWithdrawsRequests` flattens all epochs into one claimable number.
