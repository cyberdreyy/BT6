### Title
View-role users can read a bridge's plaintext `OutgoingToken` via unrestricted `GET /v2/bridge_types/:BridgeName` - ([File: core/web/router.go])

### Summary
The `GET /v2/bridge_types/:BridgeName` route is registered without any role-gate wrapper, unlike its sibling `Create`/`Update`/`Destroy` routes which require `auth.RequiresEditRole`. The handler serializes the bridge via `presenters.NewBridgeResource`, which unconditionally includes the plaintext `OutgoingToken` in the JSON response, so any authenticated user regardless of role (including view-role) can read this secret for any known bridge name.

### Finding Description
In `core/web/router.go` the bridge routes are: [1](#0-0) 

`bt.Show` (`authv2.GET("/bridge_types/:BridgeName", bt.Show)`) has no `auth.RequiresXRole` wrapper, while `Create`, `Update`, and `Destroy` are wrapped with `auth.RequiresEditRole`. The `authv2` group only requires successful authentication (`auth.Authenticate`), which succeeds for any valid session/token regardless of role, including `UserRoleView`.

`BridgeTypesController.Show` looks up the bridge and returns it directly: [2](#0-1) 

`presenters.NewBridgeResource` populates `OutgoingToken` from the stored `bridges.BridgeType.OutgoingToken` field, and the JSON tag has no `omitempty`, so it is always emitted: [3](#0-2) 

Note: `IncomingToken` is NOT leaked by this path — the persisted `bridges.BridgeType` struct only stores `IncomingTokenHash` (a salted hash), never the plaintext incoming token; the plaintext incoming token exists only transiently in `BridgeTypeAuthentication`, returned once at creation time via `Create`, and is never re-derivable from `FindBridge`/`Show`: [4](#0-3) 

So the confirmed exploitable leak is scoped to `OutgoingToken` only, not `IncomingToken`.

### Impact Explanation
A view-role authenticated user (the lowest-privilege node account role) can call `GET /v2/bridge_types/<bridgeName>` and read the bridge's plaintext `OutgoingToken`, a secret intended to be edit/admin-scoped (mutation of bridges requires `RequiresEditRole`). This is a role/authorization-gate gap allowing an under-privileged account to obtain adapter credential material it should not have access to, matching the "credential/secret disclosure" bounty impact class. The practical downstream effect depends on how the external adapter validates `OutgoingToken`; if the adapter trusts it to authenticate calls purportedly from the node, disclosure enables limited request forgery/impersonation toward that specific bridge adapter.

### Likelihood Explanation
Requires only a valid view-role session or API token (lowest privilege tier) and knowledge/guessing of a bridge name (bridge names are also enumerable via the unrestricted `GET /v2/bridge_types` index route). No admin/edit privileges, no host access, and no additional exploitation steps are needed — a single authenticated GET request is sufficient and fully repeatable.

### Recommendation
Wrap the `Show` route with `auth.RequiresEditRole` (or at minimum a role check consistent with the sensitivity of `OutgoingToken`) in `core/web/router.go`, e.g.:
`authv2.GET("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Show))`
Alternatively/additionally, redact `OutgoingToken` in `presenters.NewBridgeResource` for non-privileged callers, or split it into a separate admin/edit-only field mirroring the `IncomingToken` `omitempty` pattern.

### Proof of Concept
Go handler-level test plan:
1. In `core/web/bridge_types_controller_test.go`, extend `TestBridgeController_Show` to create an authenticated HTTP client scoped to `clsessions.UserRoleView` (rather than the default admin client used today).
2. Create a bridge via an admin/edit client (`app.BridgeORM().CreateBridgeType`).
3. Issue `client.Get("/v2/bridge_types/" + bt.Name.String())` using the view-role client.
4. Assert response status is `200 OK` (demonstrating no role gate blocks it) and parse the JSON body, asserting `resource.OutgoingToken == bt.OutgoingToken` (demonstrating secret disclosure).
5. Expected/desired fix assertion: after applying `auth.RequiresEditRole` to the route, the same request from a view-role client should return `401 Unauthorized`/`403 Forbidden` instead.

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
