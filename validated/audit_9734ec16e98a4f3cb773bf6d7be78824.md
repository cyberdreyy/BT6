### Title
Epoch-0 `epochNumber`/`lastWithdrawRequest` default-value collision permanently freezes all defaulted-epoch withdraw claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug is a NULL-pointer deref: `pi` is initialized to `NULL` and is only reassigned inside a loop, so when the first element of the input array is `NULL`, the initial (uninitialized) value is dereferenced. The idle-tranches analog is the use of default-zero storage as a sentinel for "no request" in the withdraw-claim epoch gate: `lastWithdrawRequest[_user]` and `epochNumber` both start at `0`, so a withdraw request made during the very first epoch is indistinguishable from "never requested" (`lastWithdrawRequest == 0 == epochNumber`). Because `claimWithdrawRequest` unconditionally falls through to `_claimFundedWithdrawRequest` after paying the defaulted-epoch claim, every recovery claim reverts when a borrower defaults before the first `stopEpoch` (while `epochNumber == 0` and `epochEndDate != 0`).

### Finding Description
`requestWithdraw` records the request epoch as `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` (`IdleCreditVault.sol:260,282`). `epochNumber` is only incremented inside `deposit()` when `isEpochRunning()` is true, i.e. during a `stopEpoch` (`IdleCreditVault.sol:607-611`). Therefore, throughout the entire first epoch — including a borrower default in that epoch — `epochNumber == 0`.

`claimWithdrawRequest` always executes the funded-claim path last (`IdleCreditVault.sol:312-313`):

```solidity
amount += _claimLossAdjustedWithdrawRequest(_user);
return amount + _claimFundedWithdrawRequest(_user);
```

Inside `_claimFundedWithdrawRequest` the epoch-wait gate is (`IdleCreditVault.sol:326-328`):

```solidity
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

This check is evaluated *before* any amount computation and reverts unconditionally — even when `withdrawsRequests[_user] == 0` and there is nothing to claim. When `epochNumber == 0` and `epochEndDate() != 0` (the vault is not in closed-pool mode), the condition `0 <= lastWithdrawRequest[_user]` is true for **every** user, including users whose `lastWithdrawRequest` was just cleared to `0` by `_clearWithdrawClaimForEpoch` (`IdleCreditVault.sol:832-835`).

Concretely, after a first-epoch borrower default and `finalizeDefaultRecovery` (which sets `defaultRecoveryEpoch = epochNumber = 0`, `IdleCreditVault.sol:693`), a lender with a pending epoch-0 receipt calls `claimWithdrawRequest`. `_claimDefaultedWithdrawRequest` correctly computes and pays the haircut claim — then execution reaches `_claimFundedWithdrawRequest`, which reverts with `NotAllowed`, rolling back the entire transaction including the just-completed defaulted payout. The same applies to instant receipts via `claimInstantWithdrawRequest`? No — instant claims use a separate function and are unaffected; but **all** normal/APR0 defaulted and loss-adjusted claims are bricked while `epochNumber == 0`.

Broken invariant: "one receipt, one payout" — the defaulted-epoch claim itself is correctly accounted (basis cleared, reserve debited) but can never be delivered because a later, unrelated gate reverts on uninitialized-looking state. This is exactly the kernel pattern: a variable retaining its initial default value is consumed by a check that cannot distinguish "first element" from "absent".

### Impact Explanation
Permanent freezing of all defaulted-epoch withdraw claims and of the `defaultRecoveryReserve` backing them, for the worst-case credit scenario: a borrower who never survives a single epoch. Every lender and write-off fulfiller with a pending epoch-0 receipt (normal or APR0) gets `NotAllowed` on `claimWithdrawRequest` forever, because `epochNumber` can no longer increase (no further `stopEpoch` deposits run on a defaulted vault) and `epochEndDate` is not zeroed by default finalization. Quantified loss: 100% of `defaultRecoveryReserve` plus the full claim basis of epoch-0 receipts — i.e., all funds that were recovered for pending redeemers.

### Likelihood Explanation
Requires the honest privileged sequence of a borrower default inside the first epoch (before the first `stopEpoch`), which is precisely the scenario the default-recovery machinery (`finalizeDefaultRecovery`, `defaultRecoveryEpoch`, `postDefaultRequests`) was built for — so the state is fully reachable via honest manager/borrower calls; the attacker is merely any affected lender attempting to claim. The trigger is not exotic: epoch-0 default is the canonical "borrower steals first loan" case. The only mitigating uncertainty is whether the CDO's default path sets `epochEndDate() == 0`; if it does, the gate is skipped and the issue reduces to medium. Note the same revert also blocks `_claimLossAdjustedWithdrawRequest` payouts for any user whenever a loss-adjusted `stopEpochWithDuration` occurs on epoch 0, independent of default.

### Recommendation
Distinguish "no request" from "request in epoch 0" instead of relying on the zero default — e.g., start `epochNumber` at 1 in `initialize`, or store `lastWithdrawRequest` as `epoch + 1`. Independently, make `_claimFundedWithdrawRequest` return early when there is nothing to claim (`withdrawsRequests[_user] == 0` and no APR0 balance) before applying the epoch-wait gate, so an already-completed defaulted/loss-adjusted claim cannot be DoS'd by an empty funded claim.

pragma solidity 0.8.10;

import "forge-std/Test.sol";
// Reuse the harness from test/foundry/ProgrammableBorrowerCreditVault.t.sol
// (IdleCreditVault + IdleCDOEpochVariant on a mainnet USDC fork).

contract EpochZeroDefaultClaimDoS is ProgrammableBorrowerCreditVaultTest {
  function test_epoch0_default_claims_revert() public {
    // 1. KYC lender deposits AA during buffer, then requests withdraw in epoch 0.
    _depositAA(lender, 100_000 * oneScale);
    _requestWithdrawAA(lender, 100_000 * oneScale); // lastWithdrawRequest[lender] = 0, epochNumber = 0

    // 2. Honest borrower defaults inside the first epoch; owner finalizes recovery
    //    with partial recovered funds. defaultRecoveryEpoch == 0, epochNumber still 0.
    _finalizeDefaultWithRecovery(/* recoveredAmount = */ 50_000 * oneScale);

    // 3. Lender claims the defaulted receipt: _claimDefaultedWithdrawRequest pays,
    //    then the unconditional _claimFundedWithdrawRequest hits
    //    epochEndDate() != 0 && epochNumber (0) <= lastWithdrawRequest (0) -> revert.
    vm.prank(address(cdoEpoch));
    vm.expectRevert(NotAllowed.selector);
    strategy.claimWithdrawRequest(lender);

    // defaultRecoveryReserve is permanently locked; no epoch-0 receipt can be paid.
    assertGt(strategy.defaultRecoveryReserve(), 0);
  }
}
