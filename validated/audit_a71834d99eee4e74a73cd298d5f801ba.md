### Title
EI credential holder can trigger arbitrary pipeline job runs unrelated to its bound bridge/EI - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` treats any valid EI access-key/secret as a fully-privileged run-role user by writing a synthetic `*clsessions.User{Role: UserRoleRun}` into the same `SessionUserKey` context slot that real user auth uses. `PipelineRunsController.Create` only checks `isUser := auth.GetAuthenticatedUser(c)` to gate the numeric-job-ID run path, so an EI-authenticated request passes that check identically to a real user and can trigger `RunJobV2` for any int32 job ID, with no check that the job is the one the EI/bridge was actually issued for.

### Finding Description
The router mounts `POST /v2/jobs/:ID/runs` behind `auth.Authenticate` with both `AuthenticateExternalInitiator` and user auth methods, wrapped by `auth.RequiresRunRole`: [1](#0-0) 

`AuthenticateExternalInitiator` verifies the EI's `X-Chainlink-EA-AccessKey`/`Secret` against the stored `ExternalInitiator` row, and on success sets both `SessionExternalInitiatorKey` and `SessionUserKey` to a synthetic run-role user: [2](#0-1) 

In `PipelineRunsController.Create`, the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed", and gates on `isUser`: [3](#0-2) 

However, `auth.GetAuthenticatedUser` simply reads whatever `*clsessions.User` object is stored at `SessionUserKey` [4](#0-3) , and since `AuthenticateExternalInitiator` populates that same key, `isUser` evaluates to `true` for EI-authenticated requests too. The intended EI/webhook-UUID binding path (`externalInitiators` list in the TOML spec, historically enforced via `external_initiator_webhook_specs`) only applied to the legacy webhook job type identified by UUID, which has since been removed — the UUID branch now unconditionally returns `job.ErrJobTypeRemoved` [5](#0-4) . That leaves only the int32-ID branch reachable, which performs no EI-to-job association check before calling `RunJobV2`.

The old changelog documents the intended invariant ("Only the External Initiators listed in the toml spec may trigger a run for that job") [6](#0-5) , but this binding is not enforced anywhere in the current `Create` handler for the surviving (int ID) code path.

### Impact Explanation
Any holder of a valid EI access-key/secret pair — issued for one specific bridge/external initiator — can trigger a pipeline run on any job in the node by numeric job ID, not just the job the EI was provisioned for. This is unauthorized triggering of arbitrary job runs (e.g., OCR, direct-request, or other jobs unrelated to the bridge), matching the "unauthorized job run" bounty impact class. Depending on job side effects (on-chain transactions, external requests, state changes), this can cause resource exhaustion, unintended on-chain actions, or interference with other jobs' pipelines using only a low-privilege EI credential.

### Likelihood Explanation
Preconditions are minimal: only a legitimately-issued EI access key/secret (no operator/admin access) is required. The request is a simple, unauthenticated-otherwise HTTP call (`POST /v2/jobs/<arbitrary-int-ID>/runs` with `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers). This is deterministic and repeatable for any target job whose numeric ID is known or guessable (IDs are sequential integers), making exploitation straightforward.

### Recommendation
In `PipelineRunsController.Create`, distinguish real user sessions from EI-derived sessions (e.g., check `auth.GetAuthenticatedExternalInitiator` separately, or have `AuthenticateExternalInitiator` set a distinct context key/flag rather than reusing `SessionUserKey`), and when the caller is an EI, verify the target job is actually associated with that specific `ExternalInitiator` (via the job's/bridge's EI binding) before invoking `RunJobV2`. Reject with 401/422 otherwise.

### Proof of Concept
Go handler-level integration test:
1. Start the app, create two jobs, `jobA` and `jobB` (e.g., two direct-request/OCR jobs with distinct int32 IDs), unrelated to any EI.
2. Create an `ExternalInitiator` `eiX` via `POST /v2/external_initiators`, not referenced by either job.
3. Using `eiX`'s `AccessKey`/`Secret` in `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, call `POST /v2/jobs/<jobA.ID>/runs`.
4. Assert current (buggy) behavior: response is `200 OK` with a `pipelineRun` resource created for `jobA`, and a row appended to `pipeline_runs` — i.e., `Create()` did not reject the request despite `eiX` having no relation to `jobA`.
5. Repeat for `jobB.ID` to confirm the EI can trigger any int32 job ID.
6. Add assertion that after the fix, the same request returns `401`/`422` because `eiX` is not bound to `jobA`/`jobB`.

```go
func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
```

```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
```
