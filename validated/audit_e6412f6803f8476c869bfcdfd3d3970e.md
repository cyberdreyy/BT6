### Title
Reorg-timing check silently treats "no local record" as "the tenure's block was late," letting a signer sign a conflicting/non-canonical block - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a signer may go along with a miner that is *not* building on the prior sortition (i.e., a tenure reorg). The rule is meant to be strict: a reorg of a tenure that produced a block is only permitted if that block's *first proposal* arrived suspiciously close to the next sortition (`first_proposal_burn_block_timing`). But when the local signer has no `approved_time` recorded for that block, the function does not treat this as "unknown" — it treats it as `0`, which always satisfies the "arrived late" condition and unconditionally grants the reorg permit.

`local_block_info` here comes from `SignerDb::get_first_approved_block_in_tenure`, which can return a `BlockInfo` for a tenure's first block that the *node* reported as globally accepted (via a `NewBlock` announcement), even though *this particular signer* never pre-committed to or locally accepted it itself. Per the docs, `approved_time` is only stamped at pre-commit or local acceptance — not at `mark_globally_accepted`. So a signer that:
- restarted or joined late and only ever learned of the tenure's block through the node's `NewBlock` event, or
- simply never received/processed the block proposal or pre-commit for that tenure (a signer's own local knowledge gap, or one deliberately engineered by whoever controls proposal delivery to that signer),

will have `local_block_info.approved_time == None`, and the code substitutes `proposal_to_sortition = 0`. Since `0 < first_proposal_burn_block_timing` is always true, the reorg is granted regardless of whether the tenure's block was actually well-established (i.e., regardless of the *real* timing, which the check exists specifically to police).

This is the direct analog of the reported bug class: a value meant to gate a critical, hard-to-reverse decision (here, permitting a reorg and recording the tenure as superseded via `mark_tenure_superseded`) is derived from "whoever gets there first" local state rather than a reliably-established fact, and the absence of that state is silently treated as the permissive case instead of the restrictive one. Just as the `initialize()` bug let a race (frontrunner) dictate the pool's foundational price, here a race/absence in delivering the *first* tenure's block-approval to a given signer dictates whether that signer will treat an already-globally-accepted tenure as fair game for replacement.

### Impact Explanation
This breaks the "approved-parent vs canonical" safety property: `check_parent_tenure_choice` is the gate that stops a signer from signing a block that reorgs an already-canonical, globally-accepted tenure. `refused_reorg_supersedes_nothing`/`check_parent_tenure_choice_reorg_timing_*` tests confirm the intended strictness of this timing check, but none of the visible tests cover the specific case where `local_block_info` exists (so the "no info at all" `None` path in `get_first_approved_block_in_tenure` is not hit) yet `approved_time` on it is `None`. If the permit is (incorrectly) granted, `record_superseded_tenure`/`mark_tenure_superseded` is called (`stacks-signer/src/chainstate/mod.rs` lines 290-315), which then makes the signer's own prior signature over the superseded tenure's block stop counting as a conflict (`stacks-signer/src/v0/signer.rs` `reorg_permit_stands`), letting the signer go on to sign the new, conflicting/non-canonical tenure-change block. This matches the "Critical" bar in scope: a signer signing a non-canonical/conflicting block. [2](#0-1) 

### Likelihood Explanation
No majority of signers is required — this is a per-signer, unilateral decision. The trigger only requires that a *single* signer's local `BlockInfo` for the tenure's first block lacks an `approved_time`, which happens whenever that signer learned about the block purely from the node's `NewBlock` announcement (not from proposing/pre-committing itself) — a state reachable by ordinary signer restart/resync timing, or by a winning miner (single sortition-slot actor) timing/withholding its block-proposal/pre-commit gossip to that specific signer. This requires only the miner that wins the relevant sortition (the "one-slot miner" scope) plus normal gossip-timing effects, matching the rules' allowed threat model.

### Recommendation
Do not substitute `0` for a missing `approved_time`. When `local_block_info.approved_time` is `None`, the signer has no reliable evidence about when the tenure's first block was actually proposed, so the timing check should fail closed (deny the reorg, or explicitly re-derive the timing from the node, e.g. via `get_tenure_tip`/block timestamp) rather than defaulting to the most permissive value. This mirrors how `get_first_approved_block_in_tenure` returning `None` entirely already fails closed (`Ok(false)`) a few lines above.

### Proof of Concept
1. Signer S is offline, resyncing, or otherwise did not process the proposal/pre-commit for tenure T's block B (only later learns B was globally accepted via a `NewBlock` node event), so `get_first_approved_block_in_tenure(T)` returns a `BlockInfo` for B with `approved_time = None`.
2. A miner wins the next sortition and proposes a tenure-change block that does not build on T (attempting to reorg T), with `previous_tenure_blocks` etc. constructed so `check_parent_tenure_choice` walks into the "already mined blocks" branch for T.
3. Because `globally_accepted_blocks` for T is exactly 1 (not `> 1`), and `local_block_info.approved_time` is `None`, `proposal_to_sortition` is forced to `0`, which is always `< first_proposal_burn_block_timing`.
4. `check_parent_tenure_choice` returns `Ok(true)`, `record_superseded_tenure` marks T as superseded, and S goes on to sign the new tenure-change block — even though the real proposal-to-sortition timing for T's block B may have been arbitrarily large (i.e., T was a long-established, canonical tenure that should never have been reorg-eligible).
