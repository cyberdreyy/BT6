### Title
`preTokenBalances`/`postTokenBalances` compute UI token amount without extension scaling while `getTokenAccountBalance`/`getAccountInfo` do — divergent formulas for the same conceptual value - (File: `runtime/src/transaction_balances.rs`)

### Summary
This is analogous to the `getBidValue()` report: the same conceptual quantity — a token account's "UI amount" — is computed by two different formulas in different unprivileged-facing RPC code paths, and the code's own comment acknowledges the divergence is deliberate rather than derived from a single source of truth, which is exactly the maintenance/consistency hazard the original report warns about.

### Finding Description
`svm_token_info_to_token_balance()` in `runtime/src/transaction_balances.rs` builds the `TransactionTokenBalance.ui_token_amount` field (used for `preTokenBalances`/`postTokenBalances` in `getTransaction`/`getConfirmedTransaction`/`simulateTransaction` responses and geyser transaction notifications) by calling: [1](#0-0) 

using only `SplTokenAdditionalDataV2::with_decimals(decimals)` — i.e., raw decimals, ignoring any `interest_bearing_config` or `scaled_ui_amount_config` mint extensions.

By contrast, `token_amount_to_ui_amount_v3()` in `account-decoder/src/parse_token.rs`, when given the *full* `SplTokenAdditionalDataV2` (including `interest_bearing_config`/`scaled_ui_amount_config`), applies interest/scaling math to compute `ui_amount`/`ui_amount_string`: [2](#0-1) 

That full-data path is what backs `getTokenAccountBalance` and `getAccountInfo`/`getProgramAccounts` with `jsonParsed` encoding: [3](#0-2) [4](#0-3) 

The `transaction_balances.rs` code explicitly documents that it intentionally diverges:
```
// NOTE: Same as parsed instruction data, ledger data always uses
// the raw token amount, and does not calculate the UI amount with
// any consideration for interest.
``` [5](#0-4) 

So for a token-2022 mint using `InterestBearingConfig` or `ScaledUiAmountConfig`, an unprivileged RPC caller querying the same account/mint at essentially the same slot via two different, equally "official" methods gets two different `ui_amount`/`ui_amount_string` values for what should be the same balance.

### Impact Explanation
This produces wrong/misleading data returned by a query (one of the accepted impact classes): `getTransaction` and `simulateTransaction` responses for interest-bearing or scaled-ui-amount token-2022 accounts will show `ui_amount`/`ui_amount_string` in `preTokenBalances`/`postTokenBalances` that do not match the `ui_amount` shown by `getTokenAccountBalance` or `jsonParsed` account encoding for that same account/mint. This can mislead wallets, block explorers, and downstream tooling that trust `preTokenBalances`/`postTokenBalances` as authoritative UI amounts, since only the raw `amount` field is guaranteed consistent between the two paths — the derived `ui_amount`/`ui_amount_string` are not.

### Likelihood Explanation
Likelihood is high for any transaction touching a token-2022 mint with `InterestBearingConfig` or `ScaledUiAmountConfig` extensions active — these are supported, documented mint extensions, not exotic/malicious configurations, and this is reachable by any unprivileged user simply sending a transaction and calling `getTransaction`/`simulateTransaction` plus `getTokenAccountBalance` for comparison. No attacker action is required; this is a query-response inconsistency, not an exploit against validator liveness.

### Recommendation
Decide on one canonical rule for "UI token amount" across all RPC surfaces (transaction status token balances, parsed account/token-balance encoding, and parsed instruction data), and apply the mint's full `SplTokenAdditionalDataV2` (including interest-bearing/scaled-ui-amount configs) consistently everywhere `token_amount_to_ui_amount_v3` is invoked, or explicitly document in every consuming RPC method's docs that `preTokenBalances`/`postTokenBalances.ui_amount` deliberately ignores extension scaling so client authors do not conflate it with `getTokenAccountBalance`'s value.

### Proof of Concept
Not independently reproduced (would require running a local validator with a token-2022 mint configured with `InterestBearingConfig` or `ScaledUiAmountConfig`, minting/transferring, then diffing `getTransaction`'s `preTokenBalances`/`postTokenBalances.ui_amount` against a concurrent `getTokenAccountBalance` call for the same account/mint). The divergence is demonstrated purely from code comparison: `runtime/src/transaction_balances.rs:53-59` explicitly notes the raw-decimals-only behavior versus `account-decoder/src/parse_token.rs:130-157`'s extension-aware calculation used by `rpc/src/rpc.rs:2013-2035` (`get_token_account_balance`).

pub fn token_amount_to_ui_amount_v3(
    amount: u64,
    additional_data: &SplTokenAdditionalDataV2,
) -> UiTokenAmount {
    let decimals = additional_data.decimals;
    let (ui_amount, ui_amount_string) = if let Some((interest_bearing_config, unix_timestamp)) =
        additional_data.interest_bearing_config
    {
        let ui_amount_string =
            interest_bearing_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else if let Some((scaled_ui_amount_config, unix_timestamp)) =
        additional_data.scaled_ui_amount_config
    {
        let ui_amount_string =
            scaled_ui_amount_config.amount_to_ui_amount(amount, decimals, unix_timestamp);
        (
            ui_amount_string
                .as_ref()
                .and_then(|x| f64::from_str(x).ok()),
            ui_amount_string.unwrap_or("".to_string()),
        )
    } else {
        let ui_amount = 10_usize
            .checked_pow(decimals as u32)
            .map(|dividend| amount as f64 / dividend as f64);
        (ui_amount, real_number_string_trimmed(amount, decimals))
    };
    UiTokenAmount {
        ui_amount,
        decimals,
        amount: amount.to_string(),
        ui_amount_string,
    }
}

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())
            .map_err(|_| Error::invalid_params("Invalid param: not a Token account".to_string()))?;
        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }
