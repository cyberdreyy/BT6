### Title
Missing local approval record for a reorged tenure's first block causes `check_parent_tenure_choice` to always treat the reorg as "poorly timed", letting a signer sanction reorg of an established tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a signer may sanction a miner's attempt to reorg a prior tenure. The rule is supposed to permit the reorg only if the reorged tenure's first (and only) block was "poorly timed" - i.e. produced too close to the next sortition for the miner to have RBF'd an outdated commit. When this signer has **no local approval record** for that block (`approved_time` is `None`), the code substitutes `proposal_to_sortition = 0` instead of failing safe, which unconditionally satisfies the "poorly timed" test and permits the reorg regardless of how much time actually passed.

### Finding Description
In `stacks-signer/src/chainstate/mod.rs`, `SortitionData::check_parent_tenure_choice` computes, for each tenure being reorged, how long elapsed between the tenure's first block being locally approved and the new sortition arriving: [1](#0-0) 

```rust
let checked_proposal_timing = if let Some(sortition_state_received_time) =
    sortition_state_received_time
{
    let proposal_to_sortition = if let Some(approved_at) =
        local_block_info.approved_time
    {
        sortition_state_received_time.saturating_sub(approved_at)
    } else {
        info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
        0
    };
    if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
        // ... treat as poorly timed, allow reorg, mark tenure superseded
    }
```

`local_block_info` is fetched via `get_first_approved_block_in_tenure`, whose SQL only returns a row when `signed_self`, `signed_group`, or `approved_time` is set: [2](#0-1) . Because `approved_time` is stamped only at `mark_pre_committed`/`mark_locally_accepted` [3](#0-2) , a block this particular signer never pre-committed or accepted locally (e.g. it timed out or was rejected on this node while the rest of the network globally accepted it) can still be returned as `local_block_info` (via a later `signed_group` observation) with `approved_time == None`. In that case the elapsed-time computation is skipped entirely and replaced by the constant `0`, which is always `< first_proposal_burn_block_timing`, so the branch that marks the tenure "poorly timed" (and thus reorg-permitted, recording it via `mark_tenure_superseded`) is taken unconditionally - even if the tenure's block was signed by the rest of the network minutes or hours before the sortition, i.e. even when the tenure was clearly *not* poorly timed.

This inverts the config's documented invariant: `sample/conf/signer/mainnet-signer-conf.toml` states the rule is "measures the time between when the first block of a tenure was signed and when the next burn block (sortition) arrived" and reorg should be denied once that gap is large [4](#0-3) . The fallback silently treats "we don't know" as "definitely poorly timed", the opposite of the safe default.

The equality broken is **approved-parent vs canonical**: the check exists precisely to stop a signer from approving a tenure-change/reorg block whose new parent tenure improperly discards an already-established, non-"poorly-timed" tenure. `check_parent_tenure_choice`'s `false` result maps directly to `RejectReason::ReorgNotAllowed` in `validate_tenure_change_payload` (v1/v2) [5](#0-4) ; a spurious `true` here removes that safety gate for this signer, letting it proceed to sign a block that builds off a tenure the honest majority (who did observe the earlier approval) would still refuse.

### Impact Explanation
A signer whose local `approved_time` for the victim tenure's first block is missing (dropped/late gossip, or a local validation timeout that produced a `ConnectivityIssues`/other local rejection while the rest of the network globally accepted the block via `signed_group`) will erroneously sanction a reorg of a tenure that was not actually poorly timed. That signer then proceeds past the `ReorgNotAllowed` gate and can sign/pre-commit a tenure-change block building on an improperly discarded parent - meeting the Critical bar "a signer signing an invalid/non-canonical/conflicting block." A miner racing its own tenure-change proposal specifically while it can observe (via public StackerDB `BlockResponse` gossip) that a target signer never approved/signed the prior tip locally can opportunistically trigger this on that signer without needing majority signer weight.

### Likelihood Explanation
The precondition - this signer having no `approved_time` for the reorged tenure's first block while the tenure still ended up with ≤1 globally accepted block - can arise from ordinary conditions already handled elsewhere in the codebase (validation timeout causing `mark_locally_rejected` via `check_submitted_block_proposal`, or the signer simply missing the gossip that would have caused `mark_pre_committed`). A miner (single sortition winner, using only public StackerDB gossip to time its own tenure-change proposal) can opportunistically exploit windows where this is true for one or more signers, without collusion or majority weight, making this a plausible, signer-local safety violation rather than a purely theoretical one.

### Recommendation
When `local_block_info.approved_time` is `None`, do not default `proposal_to_sortition` to `0` (which fabricates the most reorg-permissive outcome). Instead, fail closed: treat missing local timing knowledge the same way the code already treats a missing `local_block_info` entirely (`return Ok(false)` and log a warning), or conservatively fall back to a value derived from `signed_group`/`proposed_time` rather than assuming worst-case-for-security timing of `0`.

### Proof of Concept
1. Tenure T1's first (and only) block B is broadcast by the miner and signed/approved by a supermajority of signers, so B becomes `GloballyAccepted` network-wide well before the next sortition (i.e. genuinely *not* poorly timed).
2. Signer S, due to a local node validation timeout or dropped gossip, never locally pre-committed/accepted B (its `mark_pre_committed`/`mark_locally_accepted` never ran for B), so its `blocks` row for B has `approved_time = NULL`, even though it eventually observes `signed_group` and thus `get_first_approved_block_in_tenure` still returns B as a row.
3. A new sortition occurs quickly; the winning miner proposes a tenure-change block whose `parent_tenure_id` reorgs T1 instead of building on it.
4. On signer S, `check_parent_tenure_choice` is invoked: `globally_accepted_blocks <= 1` passes, `first_block_mined = Some(B)`, `local_block_info = Some(B)` but `local_block_info.approved_time = None`.
5. `proposal_to_sortition` is set to `0` instead of the true (large) elapsed time; `0 < first_proposal_burn_block_timing` is always true, so T1 is marked "poorly timed", pushed into `superseded_tenures`, and the reorg is permitted (`Ok(true)`).
6. Signer S proceeds to validate/sign the reorging tenure-change block, even though the rest of the network (with correct `approved_time` data) would correctly compute a large elapsed time and reject it via `RejectReason::ReorgNotAllowed`.

```text
# Reorg protection window. Measures the time between when the first block
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60
```
