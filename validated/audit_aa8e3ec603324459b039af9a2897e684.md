### Title
Miner-side StackerDB listener conflates a signer's stale acceptance with a later rejection, letting a revoked signature keep counting toward the block threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener`'s per-slot bookkeeping in `handle_signer_message` (the `BlockResponse::Accepted` / `BlockResponse::Rejected` arms) uses two independent guards — `gathered_signatures` for accept dedup and `responded_signers` for reject dedup — instead of a single "have we already tallied this slot's *current* vote" guard. This lets one signer's weight remain permanently booked as an approval even after that signer legitimately re-evaluates and rejects the same block, which the documented signer state machine explicitly allows (`LocallyAccepted --> LocallyRejected : re-evaluated`).

### Finding Description
`BlockStatus` tracks `total_weight_approved`, `total_weight_rejected`, `gathered_signatures` (keyed by `slot_id`) and `responded_signers` (a `HashSet<u32>` of slot ids) [1](#0-0) .

On `BlockResponse::Accepted`, weight is added only if the slot is not already in `gathered_signatures`:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 

On `BlockResponse::Rejected`, weight is added only if the slot is not already in `responded_signers`:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [3](#0-2) 

Sequence exploiting the mismatch:
1. Signer S sends `Accepted(block)` first. `gathered_signatures` gets S's slot+signature, `responded_signers` gets S's slot, `total_weight_approved += w`.
2. The signer-side state machine explicitly permits re-evaluating from `LocallyAccepted` to `LocallyRejected` (documented transition) — e.g. after learning of a conflicting/canonical sibling — and broadcasts a `Rejected` response for the *same* block hash (`handle_block_rejection` / `store_and_process_block_rejection`) [4](#0-3) .
3. The listener's `Rejected` arm checks `responded_signers.insert(slot_id)`. Since S's slot is already present (from step 1), `insert` returns `false`, so `total_weight_rejected` is **not** incremented and the rejection is silently dropped for tallying purposes.
4. Crucially, `gathered_signatures` still contains S's (now-revoked) signature, and `total_weight_approved` is never decremented. That stale, effectively-revoked signature remains eligible to be included in the final signature bundle: `block_status.gathered_signatures.values().cloned().collect()` once `total_weight_approved >= self.weight_threshold` [5](#0-4) .

This breaks the intended equality that the coordinator's aggregated approval weight should equal the weight of signers who *currently* endorse the block (verified-accepts), not a superset that includes signers who have since rejected it. It is exactly the "rejection recounted as an accept" class of break called out in scope: a rejection message is received and processed, yet the effective weight ledger still reflects acceptance.

Note also the mirror-image gap: if S rejects first then later legitimately re-evaluates to accept (also a documented transition, `LocallyRejected --> LocallyAccepted : re-evaluated`), the `Accepted` arm's guard (`gathered_signatures`) is empty for S, so the weight is added again on top of the still-unremoved `total_weight_rejected` entry, so `total_weight_approved + total_weight_rejected` can exceed `total_weight` — the numeric invariant analogous to the Burve report's uncontrolled sum-vs-target growth. Either direction shows the two tallies are not being kept as a consistent partition of "current vote per signer."

### Impact Explanation
The miner's `SignerCoordinator::get_block_status` uses `total_weight_approved` as the sole gate to decide a block has enough live signatures to be pushed to the node (`total_weight_approved >= self.weight_threshold` → `Ok(gathered_signatures...)`) [5](#0-4) . Because a revoked accept keeps contributing to that tally and its stale signature is still in `gathered_signatures`, the miner can assemble and submit a signer-signature set that includes a signature from a signer who has since rejected the block (e.g., because it conflicts with a canonical sibling they later observed). This is the "rejection recounted as acceptance" failure mode explicitly called out as Critical: the effective vote count used to finalize a block does not match the true set of current accepts, and a block that should not have reached threshold (or should have been abandoned once a signer flagged a conflict) can still be pushed and adopted.

### Likelihood Explanation
This requires no majority collusion and no signer-key compromise: it is triggered by a *single*, otherwise honest, signer that legitimately changes its vote on a block — a state transition (`LocallyAccepted → LocallyRejected` re-evaluation) that is a normal, documented part of the signer's local state machine (e.g., detecting a fresher conflicting/canonical sibling after having initially accepted). Any environment with even brief proposal/response reordering or re-evaluation after a chain-state change can produce this sequence, making it readily reachable via ordinary gossip timing rather than an engineered attack.

### Recommendation
Track a single "current vote + weight" per slot (e.g., an enum `{Accepted(sig), Rejected}` keyed by `slot_id`) instead of two independently-guarded structures. On receipt of a new vote for a slot that differs from the previously recorded vote, remove the old vote's weight from its bucket before adding the new vote's weight to the other bucket (and drop the signature from `gathered_signatures` if the signer moved to reject). This keeps `total_weight_approved` and `total_weight_rejected` as a true partition of currently-live votes.

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListener` begins tracking `BlockStatus` for `B`'s sighash.
2. Signer `S` (weight `w`) validates `B`, signs, and broadcasts `BlockResponse::Accepted`. Listener: `gathered_signatures[S]=sig`, `responded_signers={S}`, `total_weight_approved += w`.
3. Before `w` pushes the tally to threshold, `S` observes (via `check_block_against_signer_db_state` re-evaluation logic used elsewhere in `signer.rs`) that `B` now conflicts with a fresher/canonical sibling and legitimately transitions `LocallyAccepted → LocallyRejected`, broadcasting `BlockResponse::Rejected` for the same sighash via `store_and_process_block_rejection` [4](#0-3) .
4. Listener's `Rejected` arm: `responded_signers.insert(S)` returns `false` (already present) → `total_weight_rejected` is not incremented, and `S`'s stale `Accepted` weight/signature stay counted.
5. If other signers' weight plus `S`'s stale `w` clears `self.weight_threshold`, `get_block_status` returns `Ok(...)` including `S`'s revoked signature, and the miner pushes/broadcasts `B` with a signature from a signer who no longer endorses it [5](#0-4) .

Note: I was not able to fully trace, within the remaining tool budget, the exact call path in `stacks-signer/src/v0/signer.rs` that triggers an `Accepted → Rejected` re-evaluation broadcast for a block that was already locally accepted and signed (versus only pre-commit-stage re-checks); the doc-derived state diagram (`docs/signer-flows.md`, `LocallyAccepted --> LocallyRejected : re-evaluated`) and `BlockInfo::check_state`/`should_reevaluate_*` functions referenced in `signer.rs` strongly indicate this transition exists and is reachable, but confirming the precise triggering condition would need deeper reading of `signerdb.rs`'s `check_state`/`move_to` and `signer.rs`'s `should_reevaluate_block`/`should_reevaluate_reject_reason`, which the index did not surface in full.
