### Title
Unfunded instant-withdraw receipts are paid at par from the strategy balance, draining funds reserved for matured normal withdrawal claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the user's instant receipt and pays the full `instantWithdrawsRequests[_user]` amount via `_transferFundedClaim` without checking that the borrower actually funded the request through `collectInstantWithdrawFunds`. The only guard in `_transferFundedClaim` protects `defaultRecoveryReserve`; underlyings already pulled into the strategy to back matured normal withdraw claims (`pendingWithdraws` funded via `collectWithdrawFunds`) sit in the same unprotected balance. An attacker can therefore redeem an unfunded instant receipt at par and steal other claimants' funded withdrawals — an object/type-confusion analog of the memory-corruption bug class, where a receipt of one claim class is settled against backing belonging to another.

### Finding Description
The relevant flow in `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` mints the receipt and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` — but no underlying is collected at that point (lines 356–375).
- `collectInstantWithdrawFunds` is the only place that pulls underlying from the CDO and decrements `pendingInstantWithdraws` (lines 398–403). There is no per-user funded marker.
- `claimInstantWithdrawRequest` pays `instantWithdrawsRequests[_user]` unconditionally through `_transferFundedClaim` (lines 380–393). There is no check that `pendingInstantWithdraws` was reduced for this user's epoch, i.e., that the borrower's funds ever arrived.
- `_transferFundedClaim` only insulates `defaultRecoveryReserve`; any other underlying balance (funded normal withdraw claims, APR0 settlements, leftover liquidity) is spendable (lines 897–907).
- CDO-side gating (`IdleCDOEpochVariant.claimInstantWithdrawRequest`, `contracts/IdleCDOEpochVariant.sol:975`) checks only the `allowInstantWithdraw` flag, not funding status.

Attack sequence (epoch running, `allowInstantWithdraw` enabled):

1. Honest users' normal withdraw receipts from a prior epoch were funded at `stopEpoch`: `collectWithdrawFunds` transferred the underlying into the strategy; claimants have not yet claimed (claims are open-ended).
2. Attacker (KYC-passing lender) deposits, then requests an instant withdraw during the running epoch, receiving `instantWithdrawsRequests[attacker] = X` receipt tokens.
3. Before the borrower/manager funds instant withdrawals via `getInstantWithdrawFunds` → `collectInstantWithdrawFunds`, the attacker calls `claimInstantWithdrawRequest` through the CDO.
4. `_burn` + `_transferFundedClaim` pays `X` at par from the strategy balance, consuming funds earmarked for the funded normal claimants.

### Impact Explanation
Direct theft: the attacker receives underlyings that were collected to back matured normal withdraw receipts. When the honest claimants later call `claimWithdrawRequest`, `_transferFundedClaim` finds insufficient non-reserve balance and reverts or underpays — their funded claims are effectively stolen by the attacker. Loss is quantified as `min(instant receipt amount, strategy underlying balance excluding defaultRecoveryReserve)`, bounded by the attacker's deposit, and repeatable across epochs whenever the strategy holds funded-but-unclaimed withdrawal liquidity.

### Likelihood Explanation
Requirements are modest: `allowInstantWithdraw` must be enabled by the honest manager, and the strategy must hold funded underlying (a common state, since normal claims are claimable at any time after one epoch). The window is the entire running epoch up to `instantWithdrawDelay` funding; no privileged cooperation is needed. If the borrower fails to fund, the CDO's default path (`getInstantWithdrawFunds`) triggers, but the attacker front-runs or simply claims before that transaction. The absence of any funded/unfunded bookkeeping per instant receipt makes the theft deterministic whenever balance exists.

### Recommendation
- Gate `claimInstantWithdrawRequest` on actual funding: track a funded instant balance (e.g., `fundedInstantWithdraws` incremented in `collectInstantWithdrawFunds`) and pay only up to that amount, or record per-epoch funding status keyed to `instantWithdrawsRequestsByEpoch`.
- Alternatively, escrow funded normal-withdraw claims separately (as is done for `defaultRecoveryReserve`) so only borrower-pushed instant funds are payable to instant receipts.
- At minimum, revert in `claimInstantWithdrawRequest` when `pendingInstantWithdraws >= instantWithdrawsRequests[_user]` indicates the receipt is still unfunded.

### Proof of Concept
Foundry fork PoC sketch (against a live pool RPC, mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testUnfundedInstantClaimDrainsFundedWithdrawals() external {
    // 1. Honest user deposits and requests normal withdraw in epoch 0 buffer
    address honest = makeAddr('honest');
    _depositWithUser(honest, 10_000 * ONE_SCALE, true);
    vm.prank(honest);
    uint256 honestReq = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 2. Epoch 1 runs and stopEpoch funds the pending request:
    //    collectWithdrawFunds pulls `honestReq` underlying into the strategy
    _startEpochAndCheckPrices(1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0); // strategy balance now holds honestReq

    // honest user delays claiming (claims are open-ended)

    // 3. Attacker deposits, epoch 2 starts, attacker requests instant withdraw
    address attacker = makeAddr('attacker');
    _depositWithUser(attacker, 5_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(2);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // routed to instant path while allowInstantWithdraw

    // 4. Borrower has NOT funded instant withdraws. Attacker claims immediately.
    uint256 pre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = underlying.balanceOf(attacker) - pre;
    assertGt(stolen, 0); // paid from honestReq's funded balance

    // 5. Honest user's claim now reverts or underpays
    vm.prank(honest);
    vm.expectRevert(); // or balance check < honestReq
    cdoEpoch.claimWithdrawRequest();
}
```

Caveat: the exact CDO-side routing of `requestWithdraw` into `requestInstantWithdraw` vs the normal path (the flag/timing conditions that make a request "instant") could not be fully verified in this pass; the PoC assumes instant requests are available during the running epoch while `allowInstantWithdraw` is true, consistent with `claimInstantWithdrawRequest`'s docstring. If an additional guard elsewhere enforces "claim only after collectInstantWithdrawFunds," the finding would downgrade to a design fragility, but none was found in `IdleCreditVault` or the CDO claim wrapper.
