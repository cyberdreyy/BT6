### Title
Unchecked authority address allows accidental/malicious bricking of upgradeable program authority via `SetAuthority` - ([File: programs/bpf_loader/src/lib.rs])

### Summary
The `bpf_loader_upgradeable` program's legacy `SetAuthority` instruction lets the current buffer/program authority replace itself with an arbitrary `new_authority` pubkey without requiring that new authority to sign or validating that the pubkey is a real, controllable key (e.g. not `Pubkey::default()`, the all-zero address). This mirrors the reported "unchecked possible zero address" bug class: a privileged setter accepts an unvalidated address argument that can permanently lock out legitimate control.

### Finding Description
In `process_loader_upgradeable_instruction`, the `UpgradeableLoaderInstruction::SetAuthority` branch reads `new_authority` from the instruction accounts and, after checking the *current* authority signed, directly stores it as the new `authority_address` / `upgrade_authority_address` with no validation that `new_authority` is non-default or corresponds to a key anyone actually controls: [1](#0-0) [2](#0-1) 

Unlike `SetAuthorityChecked` (added later, and gated behind the `enable_bpf_loader_set_authority_checked_ix` feature) which forces the `new_authority_key` account to be a signer, proving the caller actually controls that key: [3](#0-2) 

`SetAuthority` performs no such proof-of-control check and no explicit rejection of `Pubkey::default()` (the zero address) or any other un-ownable pubkey. Because `authority_address` becomes `Some(new_authority)` (not `None`), the program is not marked `Immutable` by the `is_none()` checks used elsewhere in the same match arms, yet no private key exists to ever again exercise `Upgrade`, `Close`, or a subsequent `SetAuthority` — the account state and control is effectively locked while superficially appearing mutable.

### Impact Explanation
If a deployer (or a script/tool with a typo/blank input, exactly as in the referenced report) sends `SetAuthority` with a zero/burn/unowned pubkey as the new authority, the program's upgrade authority becomes permanently unusable. This is a state-mutation bug reachable by an ordinary deployed-program owner via a standard transaction to a builtin loader program, matching the "builtin programs and precompiles" scope. The severity is bounded (self-inflicted by the current authority, similar to the medium-severity classification in the original report) but is a genuine permanent loss of programmatic control/upgradeability, and can also be leveraged adversarially if an authority-transfer instruction is crafted by a compromised or malicious front-end/tool that a deployer blindly signs.

### Likelihood Explanation
Likelihood is moderate: it requires the current authority to submit a `SetAuthority` instruction with a bad `new_authority` account, which can happen via tooling bugs, copy-paste errors, or malicious dApp-generated transactions (the current authority only signs the instruction, but doesn't need to manually verify the exact bytes of the target pubkey the same way it would recognize an obviously wrong recipient in a transfer). The existence of the separate `SetAuthorityChecked` instruction, which was specifically introduced to require the new authority to co-sign, indicates this exact risk was already recognized as worth mitigating for that path, while the original unchecked `SetAuthority` instruction remains in place for backward compatibility.

### Recommendation
For `SetAuthority`, consider (a) documenting/CLI-enforcing that `new_authority` cannot be `Pubkey::default()`, or (b) encouraging migration to `SetAuthorityChecked` (which already requires the new authority to sign) as the preferred instruction, with tooling/wallets warning or refusing to build `SetAuthority` transactions when the target authority appears to be a zero/burn address.

### Proof of Concept
1. Deploy an upgradeable program; the deployer holds `upgrade_authority_address = Some(deployer_pubkey)`.
2. Deployer (or a malicious/faulty tool acting on their behalf) submits `UpgradeableLoaderInstruction::SetAuthority` with instruction account #2 (`new_authority`) set to `Pubkey::default()`.
3. `process_loader_upgradeable_instruction` validates only that the *current* authority signed (line 589 area) and then executes `account.set_state(&UpgradeableLoaderState::ProgramData { slot, upgrade_authority_address: new_authority.cloned() })`, storing `Some(Pubkey::default())`.
4. Any subsequent `Upgrade`, `Close`, or `SetAuthority` instruction now requires a signature from `Pubkey::default()`, which no one can produce — the program is permanently frozen at its current version despite not being formally marked `Immutable`.
