### Title
APR0 withdrawal receipts lose their loss-adjusted epoch tag once the bucket is settled, letting later claims bypass `lossRecoveryPriceByEpoch` and withdraw unfunded principal at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2021-33197 lets an attacker drop metadata (headers) while a request passes through a proxy layer. The analog here is `IdleCreditVault`, which tracks the loss-haircut "metadata" of a withdraw receipt indirectly through `lastWithdrawRequest[_user]` plus `lossRecoveryPriceByEpoch` and `apr0Users[_user].principal/principalEpoch`. When an APR0 receipt's epoch suffers a `stopEpochWithDuration` loss, the guard that blocks new requests only inspects the *open* `principal` field. Once `prepareStopEpochWithApr0` settles the bucket (moving `principal` into `settledPrincipal`/`settledInterest`), the guard sees a zero principal, the user opens a fresh request that overwrites `lastWithdrawRequest`, and the loss-epoch tag is "dropped" — exactly the header-stripping primitive. The subsequent claim then pays the haircutted receipt at par.

### Finding Description
`requestWithdraw` only refuses a new request when the epoch stored in `lastWithdrawRequest[_user]` has a nonzero `lossRecoveryPriceByEpoch` **and** the user still has `withdrawsRequestsByEpoch[user][lossEpoch] != 0` or an *open* (`principal != 0 && principalEpoch == lossEpoch`) APR0 position [1](#0-0) . For APR0 requests, the receipt is recorded via `_requestWithdrawApr0(_amount, _user)` and does **not** populate `withdrawsRequestsByEpoch` [2](#0-1) .

When `stopEpoch`/`stopEpochWithDuration` runs, `prepareStopEpochWithApr0` settles the APR0 bucket and `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` whenever the funded amount is below the pending basis [3](#0-2) . Settlement moves the APR0 position out of `principal` into `settledPrincipal`/`settledInterest`, so the `principal != 0` arm of the request guard no longer detects the haircutted epoch-N receipt.

The user then submits a new `requestWithdraw` in epoch N+1. `lastWithdrawRequest[_user]` is overwritten to `currentEpoch` [4](#0-3) . On `claimWithdrawRequest`, `_claimLossAdjustedWithdrawRequest` reads only `lastWithdrawRequest[_user]` (= N+1), finds `lossRecoveryPriceByEpoch[N+1] == 0`, and returns 0 [5](#0-4) . `_claimFundedWithdrawRequest` then pays `withdrawsRequests + settledPrincipal + settledInterest` at full face value through `_transferFundedClaim` [6](#0-5)  — even though the epoch-N bucket was only funded at `lossRecoveryPriceByEpoch[N]`. The same dropped-tag pattern is what the comment at line 268-270 explicitly tries to prevent ("otherwise `lastWithdrawRequest` would stop pointing to the epoch that stores its haircut"), but the guard misses settled APR0 positions.

### Impact Explanation
The attacker (any KYC-passed lender) redeems a haircutted APR0 receipt for its full un-haircut value. Because the shortfall was never funded by the borrower (`collectWithdrawFunds` only pulled `_amount < pendingBasis`), the excess payout comes directly from the IdleCreditVault's underlying balance, stealing from other users' funded withdrawal receipts or from `defaultRecoveryReserve`-adjacent funds. The broken invariant is "one receipt, one correctly-priced payout" / funded-claim solvency: the protocol pays out more than was collected, causing insolvency for remaining claimants, quantified as `claimBasis * (1e18 - lossRecoveryPriceByEpoch[N]) / 1e18`.

### Likelihood Explanation
Medium. It requires (a) a pool running with `unscaledApr == 0` (APR0 mode is a supported flow with dedicated accounting), (b) an owner/manager-invoked `stopEpochWithDuration` with `_lossAmount > 0` while APR0 receipts are pending, and (c) the attacker making a trivial second `requestWithdraw` of dust size in the following epoch before claiming. All attacker steps are unprivileged user calls (`requestWithdraw`, `claimWithdrawRequest` via the CDO). No guard stops it: the loss-epoch check in `requestWithdraw` only inspects `lastWithdrawRequest` and open `principal`, and the claim path unconditionally falls through to `_claimFundedWithdrawRequest` when the overwritten epoch has no loss price.

### Recommendation
In `requestWithdraw`, extend the loss-epoch guard to also reject when `apr0Users[_user].settledPrincipal != 0` or `apr0Users[_user].settledInterest != 0` belongs to an epoch with a nonzero `lossRecoveryPriceByEpoch` (store the epoch on settlement, or keep `principalEpoch` populated until claim). Alternatively, check `lossRecoveryPriceByEpoch` across all epochs recorded in `withdrawsRequestsByEpoch`/`apr0Users` rather than only `lastWithdrawRequest`. A defense-in-depth fix is to iterate the user's epochs in `_claimLossAdjustedWithdrawRequest` instead of trusting a single mutable pointer.

### Proof of Concept
Foundry fork PoC (against the mainnet-fork test harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Setup: deploy IdleCDOEpochVariant + IdleCreditVault with unscaledApr == 0 (APR0 mode).
// attacker = KYC-allowed EOA; manager/owner are honest.

// 1. Buffer period: attacker deposits AA and requests a withdraw.
idleCDO.depositAA(100_000e6);               // attacker
cdoEpoch.requestWithdraw(0, AATranche);     // apr0Users[attacker].principal = P, principalEpoch = 0

// 2. Manager starts epoch 0, warps past epochEndDate.
vm.prank(manager); cdoEpoch.startEpoch();
vm.warp(cdoEpoch.epochEndDate() + 1);

// 3. Manager calls stopEpochWithDuration with _lossAmount > 0.
//    prepareStopEpochWithApr0 moves P -> settledPrincipal/settledInterest,
//    collectWithdrawFunds stores lossRecoveryPriceByEpoch[0] = r < 1e18.
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(newApr, 0, newDuration, lossAmount);

// 4. Attacker opens a dust request in epoch 1. Guard passes because
//    apr0Users[attacker].principal == 0 and lastWithdrawRequest is overwritten to 1.
cdoEpoch.requestWithdraw(1, AATranche);     // lastWithdrawRequest[attacker] = 1

// 5. After epoch 1 ends (no loss), attacker claims.
vm.prank(manager); cdoEpoch.stopEpoch(newApr2, 0);
cdoEpoch.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[1] == 0 -> skip
// _claimFundedWithdrawRequest pays P + settledInterest at PAR, not P * r / 1e18.
// assertEq(underlying.balanceOf(attacker), P * r / 1e18) FAILS; attacker got P.
// The unpaid (P - P*r/1e18) is drained from other funded receipts -> insolvency.
```

Note: I was not able to read the body of `prepareStopEpochWithApr0`/`_settleApr0` to confirm whether `principal` is cleared to zero at settlement versus retained until claim; if settlement leaves `principal`/`principalEpoch` populated, the existing guard catches step 4 and this path is mitigated. That specific line-level confirmation (IdleCreditVault.sol, `_settleApr0` body) should be verified before finalizing the report.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
