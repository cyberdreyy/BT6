### Title
Re-requesting a withdrawal after a loss-adjusted epoch lets the old haircut receipt be paid at par, draining funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks withdraw receipts both per-epoch (`withdrawsRequestsByEpoch`) and in an aggregate (`withdrawsRequests`), and records loss haircuts per epoch in `lossRecoveryPriceByEpoch`. The loss-adjusted claim path (`_claimLossAdjustedWithdrawRequest`) only inspects the single epoch pointed to by `lastWithdrawRequest[_user]`. If a user whose epoch-N receipt was haircut at `stopEpochWithDuration` makes a new withdraw request in epoch N+1, `lastWithdrawRequest` moves to N+1, the N-epoch loss price is never applied, and `_claimFundedWithdrawRequest` pays the entire aggregate — including the underfunded haircut basis — at par. This is the vault analog of a use-after-free: the deallocated (haircut) claim basis remains reachable through the aggregate ledger.

### Finding Description
- `requestWithdraw` adds the request to `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]`, and sets `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282-293`). The strategy mints the user a receipt token for `_amount`.
- On `stopEpochWithDuration` with a loss, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`, but does **not** reduce `withdrawsRequests` / `withdrawsRequestsByEpoch` (`IdleCreditVault.sol:411-430`). The strategy only pulled `_amount < pendingBasis` underlyings.
- `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:789-800`). If the user's *latest* request epoch has no loss price, this returns 0 and the earlier loss epoch is never settled.
- `_claimFundedWithdrawRequest` then gates only on `epochNumber > lastWithdrawRequest[_user]` and pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` (`IdleCreditVault.sol:319-349`). `_clearWithdrawClaimForEpoch` — the only code that removes a loss-epoch basis from the aggregate — is never reached for the old epoch (`IdleCreditVault.sol:811-837`). The comment "Any remaining normal/APR0 receipt is older and already funded" is wrong: an older loss-adjusted receipt is only haircut-funded.

Attack sequence (running → stopped-with-loss → running → stopped):
1. Epoch N (APR > 0 mode): attacker calls `requestWithdraw` for a large tranche amount; receipt minted, basis recorded under epoch N.
2. `stopEpochWithDuration` realizes a loss; `collectWithdrawFunds` funds only `pendingBasis * (1 - pendingLoss/totalBasis)` and sets `lossRecoveryPriceByEpoch[N]`.
3. Epoch N+1 (buffer): attacker calls `requestWithdraw` again (even a dust amount). `lastWithdrawRequest` = N+1.
4. Epoch N+1 stops normally and is fully funded. `claimWithdrawRequest` skips the N-loss path (price lookup on N+1 returns 0) and pays `withdrawsRequests[user]` — epoch-N basis at **par** plus the N+1 request — from strategy underlyings that were only partially funded.

### Impact Explanation
Direct theft / insolvency. The attacker recovers the full pre-haircut basis although only `lossRecoveryPrice` was funded for epoch N. The shortfall is paid from underlyings held for other users' funded receipts and instant-withdraw claims, so later honest claimants cannot be paid in full. Loss magnitude ≈ `(1 - lossRecoveryPrice/RECOVERY_FULL) * epoch-N claim basis`, unbounded by request size.

### Likelihood Explanation
Requires only an unprivileged tranche holder: request a withdraw, wait for a loss epoch (borrower underpayment on `stopEpochWithDuration`, an honest-manager flow), place a dust follow-up request, claim. No privileged cooperation is needed; the trigger (a realized loss epoch) is a normal protocol state. Guard checks (epoch gating in `_claimFundedWithdrawRequest`, `_onlyIdleCDO`, `NotAllowed` on zero price) do not stop it.

### Recommendation
In `_claimFundedWithdrawRequest`, settle *all* epochs with `lossRecoveryPriceByEpoch[e] != 0` before paying the funded aggregate, or iterate user epochs. Simpler: in `requestWithdraw`, before recording the new request, force-settle any prior loss-adjusted receipt (`_claimLossAdjustedWithdrawRequest`) so `withdrawsRequests` never mixes haircut and fully-funded bases. Alternatively store per-epoch funding status and compute the claimable amount as `Σ min(basis_e, basis_e * lossPrice_e / RECOVERY_FULL)` instead of a single aggregate paid at par.

### Proof of Concept
Foundry fork sketch (pattern follows `test/foundry/IdleCDOEpochQueue.t.sol` and `IdleCreditVault.t.sol` helpers `_requestWithdrawWithUser`, `_stopCurrentEpochWithApr`):

```solidity
// setup: deposit, start epoch, requestWithdraw(attackerTranches) in epoch N
// stop epoch N with a loss so pending receipts are only partly funded
uint256 pendingBasis = strategy.pendingWithdraws();
uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
uint256 totalBasis   = activeBasis + pendingBasis;
uint256 lossAmount   = totalBasis / 2;              // 50% loss
(uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
deal(address(underlying), strategy.borrower(), repay, true);
vm.prank(strategy.borrower());
underlying.approve(address(cdoEpoch), repay);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, 0, cdoEpoch.epochDuration(), lossAmount);
// lossRecoveryPriceByEpoch[N] is now < RECOVERY_FULL, pendingWithdraws == 0,
// but withdrawsRequests[attacker] still holds the FULL pre-haircut basis

// epoch N+1: dust re-request moves lastWithdrawRequest off the loss epoch
cdoEpoch.startEpoch();
_requestWithdrawWithUser(attacker, 1);               // dust tranche amount
_stopCurrentEpochWithApr(apr);                        // fully funded stop

// claim: loss path skipped (price lookup on epoch N+1 == 0),
// funded path pays the aggregate at par
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();                      // via IdleCDO -> strategy
// attacker receives full epoch-N basis + dust, although only
// basis * lossRecoveryPrice was funded for epoch N
// assert: payout > pendingToFund portion attributable to attacker
```

The assertion that exposes the bug: `withdrawsRequests[attacker]` is burned/paid at par even though `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL` was never applied to the epoch-N component — the strategy transfers underlyings it never collected.
