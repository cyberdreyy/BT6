### Title
Stale-epoch over-read of instant-withdraw receipts in default finalization permanently freezes unfunded instant claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records instant-withdraw receipts under the request epoch (`instantWithdrawsRequestsByEpoch[user][epochNumber]`), but both the recovery-basis calculation (`defaultPendingClaimBasis`) and the defaulted-claim path (`_claimDefaultedInstantWithdrawRequest`) read those ledgers only at the *current* `epochNumber` / `defaultRecoveryEpoch`. An unfunded instant receipt created in an earlier epoch is invisible to both reads: it is excluded from `totalBasis` in `finalizeDefaultRecovery`, and it cannot be paid through `_claimDefaultedInstantWithdrawRequest`. The subsequent at-par payout in `claimInstantWithdrawRequest` then hits the reserve guard in `_transferFundedClaim` and reverts forever, permanently freezing the user's funds.

### Finding Description
The analog of the heap over-read (reading a deserialized structure at an attacker-influenced offset) is reading epoch-indexed receipt ledgers at the wrong index.

`requestInstantWithdraw` writes receipts under the epoch active at request time [1](#0-0) . `epochNumber` is incremented on each `stopEpoch`-triggered `deposit()` [2](#0-1) . `pendingInstantWithdraws` is only decremented when the borrower funds via `collectInstantWithdrawFunds` [3](#0-2) , so an instant receipt requested in epoch `N` can remain unfunded while the vault advances to epoch `M > N` — the test `testClaimInstantWithdrawRequestAfterAnEpoch` shows pending instant requests surviving across epochs [4](#0-3) .

When the pool later defaults in epoch `M` and `finalizeDefaultRecovery` runs:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (i.e., epoch `M`) whenever `pendingInstantWithdraws != 0` [5](#0-4) . The epoch-`N` receipt contributes nothing to `instantWithdrawClaimsByEpoch[M]`, so `totalBasis` is understated and `recoveryPrice` is inflated for all other claimants [6](#0-5) .
2. `_defaultPrefundedInstantReserve` reads `instantWithdrawClaimsByEpoch[epochNumber]` as well [7](#0-6) , so no prefunded amount is reserved for the stale receipt even though `pendingInstantWithdraws > 0` sets `defaultInstantWithdrawsFinalized = true` [8](#0-7) .
3. In `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — epoch `M` again — and returns 0 for the stale receipt [9](#0-8) . Execution falls through to the aggregate at-par path, which burns all receipt tokens and calls `_transferFundedClaim` [10](#0-9) . Since the reserve equals (or exceeds minus dust) the strategy's underlying balance after finalization, the guard `balance - reserve < _amount` reverts [11](#0-10) .

The receipt is therefore neither haircut-claimable nor par-claimable — it is permanently unclaimable. If any non-reserve underlying does sit in the strategy (e.g., other funded claims or donations), the same bug instead pays the unfunded receipt at par, bypassing the recovery haircut and stealing from other claimants' funded pool.

### Impact Explanation
Permanent freezing of the victim's instant-withdraw receipt value (the full requested underlying amount), plus an inflated `defaultRecoveryPrice` that can push recovery above par for remaining claimants using a basis that excludes the frozen receipts — i.e., the frozen user's share is effectively redistributed. Alternatively, when `balance - reserve >= amount`, the stale receipt drains funded underlyings at par instead of `defaultRecoveryPrice`, directly stealing the recovery haircut from the reserve-protection invariant (one receipt, one haircut-adjusted payout).

### Likelihood Explanation
Requires only: an unprivileged KYC'd lender requesting an instant withdrawal during a running epoch, the honest borrower/manager not fully funding it before the epoch advances (normal operation — `getInstantWithdrawFunds` does not force funding, and partial funding is explicitly supported), one `epochNumber` increment, and a later borrower default finalized via `finalizeDefault`. All roles involved behave honestly; the lender is the victim, not a privileged actor. The window is realistic because unfunded instant requests are designed to persist across epochs.

### Recommendation
Resolve receipt basis across all epochs with unfunded claims instead of indexing only `epochNumber`: track the earliest epoch with pending instant claims (or aggregate `pendingInstantWithdraws`-backed basis directly) so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` include stale-epoch receipts. In `_claimDefaultedInstantWithdrawRequest`, clear the user's aggregate unfunded instant basis rather than only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, or iterate recorded request epochs.

### Proof of Concept
Foundry fork/harness sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleEpochInstantReceiptFrozenOnDefault() external {
    // epoch 0 runs normally
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // attacker-as-victim (any lender) requests instant withdraw in epoch 1
    address user = makeAddr('stale-instant-user');
    uint256 shares = _depositWithUser(user, 10_000 * ONE_SCALE, true);
    vm.prank(user);
    uint256 req = cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path

    // epoch 1 starts; borrower funds nothing for the instant queue
    _startEpochAndCheckPrices(1);
    // do NOT call _getInstantFunds(); pendingInstantWithdraws stays > 0

    // epoch 1 ends -> epochNumber now 2, receipt still recorded under epoch 1
    _stopEpochAndCheckPrices(1, initialProvidedApr / 2, _expectedFundsEndEpoch());
    IdleCreditVault v = IdleCreditVault(address(strategy));
    assertGt(v.pendingInstantWithdraws(), 0);
    assertEq(v.instantWithdrawsRequestsByEpoch(user, v.epochNumber()), 0); // wrong-epoch read

    // epoch 2 ends in borrower default
    _startEpochAndCheckPrices(2);
    _toggleEpoch(false, initialProvidedApr / 2, 0);
    _checkDefault();

    // finalize recovery
    uint256 recovered = 1_000 * ONE_SCALE;
    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    underlying.approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // user's instant receipt is in epoch 1, defaultRecoveryEpoch is 3:
    // _claimDefaultedInstantWithdrawRequest returns 0, par path hits reserve guard
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(user);
    cdoEpoch.claimInstantWithdrawRequest(); // permanently frozen
}
```

Caveat: I could not fully trace `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` timing constraints, so the exact window for leaving `pendingInstantWithdraws > 0` across an epoch boundary should be confirmed in the PoC; the indexing mismatch itself is evident from the cited reads.
