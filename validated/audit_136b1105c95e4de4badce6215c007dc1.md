## Finding

A single `getSignaturesForAddress` RPC call for an address with few or no signatures can force the validator to scan large portions of the `address_signatures_cf` column family in Blockstore, well beyond the requested `limit`, because the reverse-iteration loop only terminates on `slot < lowest_slot` or iterator exhaustion — not when it encounters keys belonging to a *different* address.

### Title
Unbounded blockstore scan in `getSignaturesForAddress` when querying rarely-used addresses - (File: `ledger/src/blockstore.rs`)

### Summary
`Blockstore::get_confirmed_signatures_for_address2()` iterates the `address_signatures_cf` column family in reverse order to collect additional signatures once the initially-known slot's signatures are exhausted. The loop condition only checks the accumulated result count against `limit` and independently checks whether the current `slot` has dropped below `lowest_slot`; it does **not** stop when the iterator crosses into a different address's key range. For any address with a low or zero signature count, this can force the RPC thread to walk through the entire remaining portion of the index (potentially back to the first available block/genesis), touching signatures belonging to unrelated addresses, for a single unprivileged client request.

### Finding Description
`get_confirmed_signatures_for_address2` [1](#0-0)  sets up a reverse RocksDB iterator positioned at `(address, slot, 0, Signature::default())` [2](#0-1) , then loops:

```
while address_signatures.len() < limit {
    if let Some(((key_address, slot, transaction_index, signature), _)) = iterator.next() {
        if slot < lowest_slot {
            break;
        }
        if key_address == address {
            if self.is_root(slot) || confirmed_unrooted_slots.contains(&slot) {
                address_signatures.push((slot, signature, transaction_index));
            }
            continue;
        }
    }
    break;
}
``` [3](#0-2) 

Unlike `find_address_signatures_for_slot`, which explicitly `break`s the moment `address != pubkey` [4](#0-3) , this loop has no equivalent guard. When `key_address != address`, the branch that would `continue` is skipped, but execution simply falls through to the bottom of the `if let` block and the `while` loop repeats — it does not `break`. The only remaining termination conditions are: (1) `address_signatures.len() >= limit` (which never grows for a sparse/unused address), (2) `slot < lowest_slot` for whichever address's key is currently being visited, or (3) the iterator is exhausted. Because keys for *other* addresses can have arbitrary slots above `lowest_slot`, the loop can keep iterating through unrelated addresses' entries across the full remaining depth of the ledger's transaction-history index.

### Impact Explanation
This is reachable by any unprivileged RPC client (JSON-RPC handler, no special role required) issuing `getSignaturesForAddress` for an address that has never transacted or has few transactions, with `before`/`until` unset so `lowest_slot` defaults to `first_available_block()` [5](#0-4) . On a long-lived, busy cluster this index can be large, so a single such call can incur very large, unbounded RocksDB reads/CPU work compared to normal usage, degrading RPC availability disproportionately to the cost of issuing the request (analogous in root cause — unbounded work triggered by a single call whose cost scales with unrelated/attacker-influenced state — to the referenced `releaseOnEid` gas-exhaustion report, though here it manifests as RPC resource exhaustion rather than a stuck cross-chain transfer).

### Likelihood Explanation
Likelihood is high for triggering the pathological scan (any freshly generated pubkey with zero signatures qualifies, and the call requires no privileges, `before`, `until`, or unusual parameters), though the practical severity depends on the size/age of the validator's `address_signatures_cf` index at query time.

### Recommendation
Break out of the scan loop when a fixed multiple of the index has been traversed without progress, or track the last-seen `key_address` and terminate/short-circuit once the iterator has moved sufficiently far past the queried address's key range, mirroring the address-boundary check already used in `find_address_signatures_for_slot`.

### Proof of Concept
1. Populate a validator's ledger with a large number of `address_signatures_cf` entries for many distinct addresses over many slots (representative of long-lived mainnet-style history).
2. Call `getSignaturesForAddress` for a freshly generated `Pubkey` that has never appeared in any transaction, without `before`/`until`.
3. Observe that `get_confirmed_signatures_for_address2` performs a reverse iteration that traverses signatures for many unrelated addresses down toward `first_available_block`, rather than returning immediately, causing disproportionate RocksDB I/O/CPU for a single request relative to normal, targeted queries.
