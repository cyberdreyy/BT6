### Title
Unauthenticated `base_insertValidatedTransaction` RPC accepts caller-supplied sender without signature verification, enabling spoofed transaction injection into the block builder pool - (File: crates/execution/txpool/src/builder/rpc.rs)

### Summary
The Prefect advisory describes an unauthenticated WebSocket endpoint (`/api/events/in`) that lets any remote client inject events without proving identity. The analogous exposure in this codebase is the Base builder's `base_insertValidatedTransaction` JSON-RPC method, which accepts a caller-declared `sender` address paired with raw transaction bytes and inserts it into the builder's mempool while explicitly skipping ECDSA signature verification, trusting the caller's authentication claim implicitly.

### Finding Description
`BuilderApiServer::insert_validated_transaction` takes a `ValidatedTransaction<E>` containing an attacker-controlled `sender: Address` field and `raw: Bytes` (the EIP-2718 encoded transaction). The handler decodes the raw bytes and then constructs the recovered transaction with: [1](#0-0) 

using `Recovered::new_unchecked(consensus_tx, sender)` — this pairs the caller-supplied `sender` with the decoded transaction **without** recovering/verifying that the transaction's actual signature corresponds to that address. The trait doc itself acknowledges this design: "The transaction is EIP-2718 encoded with its sender address pre-recovered, allowing the builder to skip signature verification." [2](#0-1) 

This trust model is only safe if the RPC endpoint is reachable exclusively from an authenticated/trusted mempool-forwarding peer. The implementation comment reinforces the intended trust boundary: "since the sender addresses are trusted from the forwarding mempool node." [3](#0-2) 

However, the RPC module registration performed by `BuilderApiExtension` (and the in-process builder wiring) registers this method as a standard node RPC module with no application-level authentication, API-key check, or peer allow-list visible in the extension code: [4](#0-3) [5](#0-4) 

Unlike the standard `eth_sendRawTransaction` path, which relies on the transaction's own signature to derive `sender`, this endpoint lets any caller assert an arbitrary `sender`/`raw` pairing. If exposed over the node's public/default RPC transport (HTTP/WS) without an additional network-layer authentication control, any anonymous RPC client can submit a "validated" transaction attributed to any address of their choosing, mirroring the missing-authentication root cause in the Prefect advisory (CWE-287): an operation intended to be restricted to a specific trusted peer instead has no enforced credential check at the endpoint itself.

### Impact Explanation
If this method is reachable without a network- or transport-level authentication guard equivalent to what the doc comments assume, an attacker can:
- Inject transactions into the block builder's pool with a spoofed/arbitrary `sender`, bypassing normal signature-based sender derivation (`decode_2718` only validates transaction structure, not that `raw`'s embedded signature recovers to `sender`).
- Potentially get such spoofed transactions included via `add_external_transaction`/`add_transaction`, since the pool trusts the `Recovered` sender rather than re-deriving it, which could result in unauthorized operations executed as if authorized by a victim address (nonce/fee accounting corruption, unauthorized state-changing calls attributed to another account), corresponding to the "unauthorized operation" and "theft/freezing of funds" impact classes in the validation criteria.
- This is reachable directly from a single anonymous JSON-RPC call (no P2P gossip, no privileged deployment access required), matching the "anonymous RPC client" reachability bar.

The severity depends on deployment: if the method is *only* ever exposed on an internal, mutually-authenticated mempool→builder link (as the code comments assume), the real-world exposure requires that link to be reachable by an untrusted party — a network/deployment assumption the code itself does not enforce in-process.

### Likelihood Explanation
Medium: the vulnerable code path requires no special privilege and is a single JSON-RPC call reachable by anyone who can reach the RPC port where this module is registered. The likelihood of exploitation hinges entirely on whether an authentication/network-isolation layer sits in front of this specific RPC namespace in production Base builder deployments — nothing in the reviewed extension/registration code (`BuilderApiExtension::apply`, `in_process_builder.rs`) shows an authentication check enforced at the RPC-module level itself.

### Recommendation
- Enforce authentication (e.g., mutual TLS, JWT, or API-key) at the transport layer specifically for the `base_insertValidatedTransaction` RPC namespace, and verify this is not exposed on the node's default public RPC listener.
- Alternatively/additionally, re-derive and verify the sender from the transaction's actual signature (`consensus_tx.recover_signer()`) and reject the request if it does not match the caller-supplied `sender`, removing the implicit trust in caller-supplied identity.
- Add an explicit connection-level allow-list (peer certificate / mTLS identity / IP allow-list) check inside `BuilderApiImpl` or the RPC module registration, analogous to how `websocket-proxy`'s `Authentication`/API-key mechanism gates its endpoints (`crates/infra/websocket-proxy/src/auth.rs`), to close the gap between the documented trust assumption and the actual enforcement.

### Proof of Concept
1. Identify a Base builder node exposing the `base` RPC namespace (JSON-RPC over HTTP/WS) that has `BuilderApiExtension` / `insert_validated_transaction` registered without a separate mTLS/API-key gate.
2. Craft an arbitrary EIP-2718 transaction body (`raw`) — it does not need a valid signature matching a victim address; any well-formed but improperly-signed transaction bytes will decode successfully via `BaseTransactionSigned::decode_2718`.
3. Send a JSON-RPC call:
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "base_insertValidatedTransaction",
  "params": [{ "sender": "0xVictimAddress...", "raw": "0x02...", "extensions": {} }]
}
```
4. Observe that the handler bypasses signature verification via `Recovered::new_unchecked(consensus_tx, sender)` and forwards the transaction to `pool.add_external_transaction`, as shown at [6](#0-5) , attributing it to `0xVictimAddress` regardless of whether that address actually authorized/signed the transaction.

/// RPC interface for submitting pre-validated transactions to a block builder.
///
/// `E` is the wire extension payload; see [`ValidatedTransactionExtensions`].
#[rpc(server, namespace = "base")]
pub trait BuilderApi<E> {
    /// Inserts a single pre-validated transaction into the builder's pool.
    ///
    /// The transaction is EIP-2718 encoded with its sender address pre-recovered,
    /// allowing the builder to skip signature verification.
    ///
    /// Returns an error if decoding or pool insertion fails.
    /// Use JSON-RPC batch requests for efficient bulk submission.
    #[method(name = "insertValidatedTransaction")]
    async fn insert_validated_transaction(&self, tx: ValidatedTransaction<E>) -> RpcResult<()>;
}

///
/// Its configuration controls validity metadata acceptance, predicate limits, and shadow-only
/// validity injection. Ordinary validated transactions remain available in all modes.
#[derive(Debug, Default)]

    config: BuilderApiExtensionConfig,
}

impl BaseNodeExtension for BuilderApiExtension {
    fn apply(self: Box<Self>, builder: NodeHooks) -> NodeHooks {
        let config = self.config;
        builder.add_rpc_module(move |ctx: &mut BaseRpcContext<'_>| {
            let api = ShadowValidityBuilderApi::new(ctx.pool().clone(), config);
            ctx.modules.merge_configured(api.into_rpc())?;
            Ok(())
        })
    }
}
