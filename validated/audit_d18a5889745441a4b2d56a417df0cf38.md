## Finding

The multisig contracts (`multisig` and `multisig2`) implement a k-of-n confirmation scheme, but the "remove member" logic only cleans up requests that a removed member/key *originated*, not the confirmations that member cast on requests originated by *other* members. This is structurally the same class of bug as the reported oracle issue: a value that should represent "confirmations from currently-live members" is not actually re-validated against live membership, so a stale/removed signer's confirmation is still counted toward the quorum threshold.

### Root cause

In `multisig2/src/lib.rs`, `delete_member` only purges requests where the removed member is the *creator* of the request:

```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [1](#0-0) 

It never scans the `confirmations` sets of *other* pending requests to strip out the removed member's entry. `confirm()` then only validates that the *new* caller is a current member via `current_member()` / `assert_valid_request`, but blindly trusts every entry already stored in `confirmations` when comparing against `num_confirmations`:

```rust
let mut confirmations = self.confirmations.get(&request_id).unwrap();
...
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [2](#0-1) 

The identical pattern exists in the older `multisig/src/lib.rs`, where `DeleteKey` only removes requests whose `signer_pk` equals the deleted key, not confirmations by that key on other requests:

```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter(|(_k, r)| r.signer_pk == pk)
    .map(|(k, _r)| k)
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [3](#0-2) 

### Broken invariant

`confirmations.len() >= num_confirmations` is meant to equal `count(live members who confirmed) >= num_confirmations`. Because stale confirmations aren't purged when a member is removed, `confirmations.len()` can include confirmations from accounts/keys that are no longer members, so the equality breaks: a request can execute with fewer *currently authorized* confirmers than `num_confirmations`.

### Proof of concept (multisig2, `num_confirmations = 3`, members `{A, B, C, D}`)

1. `A` calls `add_request_and_confirm(R)` where `R` transfers funds to an attacker-controlled account — `confirmations(R) = {A}`.
2. `B` calls `confirm(R)` — `confirmations(R) = {A, B}` (2 < 3, not yet executed).
3. Separately, the group legitimately executes a `DeleteMember{B}` request (using 3 confirmations from `A, C, D`) to rotate `B` out of the multisig. `delete_member` removes `B` from `members`, but `R` was originated by `A`, not `B`, so `R`'s confirmation set is left untouched: `confirmations(R)` still equals `{A, B}`.
4. `C` (still a live member) calls `confirm(R)` — `confirmations(R) = {A, B, C}`, `len() == 3 >= num_confirmations`, so `execute_request(R)` fires and the transfer executes.

Only `A` and `C` are currently-valid members who approved `R` — a 2-of-4 execution of what is supposed to be a 3-of-4 request, because `B`'s stale confirmation from before removal is still counted. Funds move from the multisig with fewer live approvals than the configured threshold.

### Title
Multisig executes requests below the configured confirmation threshold because confirmations from removed members are not purged - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
`delete_member`/`DeleteKey` only clean up requests *originated* by the removed member/key, leaving that member's confirmation entries intact on requests originated by other members. `confirm()` never re-validates stored confirmations against current membership, so `confirmations.len() >= num_confirmations` can be satisfied using confirmations from accounts that are no longer members.

### Finding Description
See root-cause analysis above: `delete_member` (`multisig2/src/lib.rs`) and the `DeleteKey` action handler (`multisig/src/lib.rs`) both filter pending requests by `r.member == member` / `r.signer_pk == pk` — i.e., only requests that member *created* — and remove confirmations only for those. They never iterate other requests' confirmation sets to strip the removed member out. `confirm()` counts `confirmations.len()` directly against `num_confirmations` without re-checking that every prior confirmer is still a current member.

### Impact Explanation
This allows a multisig request (including a `Transfer` of funds, an `AddKey`/`AddMember` granting new access, or a `DeleteMember`) to execute with fewer live, authorized confirmations than `num_confirmations` requires — a multisig request executed below threshold, matching the Critical impact category (funds moved/authorized by fewer parties than the quorum mandates).

### Likelihood Explanation
Requires only ordinary multisig operation: a pending request with partial confirmations, followed by a routine member-rotation (`DeleteMember`/`DeleteKey`) of one of the partial confirmers, followed by one more legitimate confirmation. No compromised keys, no owner/foundation privilege, and no protocol-level assumption violation are needed — member rotation is a documented, expected operation.

### Recommendation
When removing a member/key, iterate all pending requests' `confirmations` sets (not just those the member created) and remove the departing member/key from each. Alternatively, validate every entry in `confirmations` against `self.members` (or the equivalent live-key set) at the time `confirm()` tallies the count, discarding stale entries before comparing against `num_confirmations`.
