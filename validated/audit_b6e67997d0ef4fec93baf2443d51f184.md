### Title
Duplicate settlement of the same builder execution-payload bid payment across `process_builder_pending_payments` and `apply_parent_execution_payload` allows Gwei to be created and paid to the builder's `fee_recipient` twice - ([File: specs/gloas/beacon-chain.md])

### Summary
`BuilderPendingPayment` entries can be settled by two independent, non-cross-checking code paths: the epoch-boundary quorum eviction in `process_builder_pending_payments` and the "older than previous epoch" fallback branch inside `apply_parent_execution_payload`. Neither path checks whether the other has already settled the same bid, so the same `parent_bid.value` can be queued twice as a `BuilderPendingWithdrawal` and paid out twice to the same `fee_recipient`, while the builder's balance debit is capped by `min()` in `apply_withdrawals`. This produces an uncapped, duplicated payment - Gwei created and paid to a non-owner - directly analogous to the ZeroLend bug where `distributeEx` distributed the main reward token to a gauge without resetting the `claimable` bookkeeping used by `distribute`, letting the same reward be paid out more than once.

### Finding Description
When a builder's bid is accepted, `process_execution_payload_bid` records a `BuilderPendingPayment` keyed by slot index, containing `withdrawal.amount = bid.value`: [1](#0-0) 

Weight accrues to that same payment entry via `process_attestation` for same-slot attestations, independent of whether the block that actually reveals/commits the parent's execution requests is ever produced promptly: [2](#0-1) 

There are two disjoint settlement paths for this same entry:

1. **Epoch-boundary quorum path** - `process_builder_pending_payments`, run every epoch, checks the first-half slots for `weight >= quorum` and if so appends `payment.withdrawal` to `state.builder_pending_withdrawals`, then always rotates/clears the array regardless of whether the entry was paid: [3](#0-2) 

2. **Late full-reveal fallback path** - inside `apply_parent_execution_payload`, when the parent's actual block (with the matching execution requests) is finally processed and its slot is *older than the previous epoch* (meaning its payment entry has already been evicted by (1) above, potentially after being paid out because it reached quorum), the code unconditionally re-creates a withdrawal straight from `parent_bid.value`: [4](#0-3) 

Because branch (2) is reached purely based on `parent_epoch` age and `parent_bid.value > 0` - with no check of whether the corresponding `BuilderPendingPayment` was already paid via quorum eviction in (1) - both paths can fire for the same bid: once when weight reaches quorum at an epoch boundary (before the reveal ever lands on-chain), and again when the delayed reveal is eventually included as the parent of some later block.

The resulting duplicate `BuilderPendingWithdrawal` entries are both processed by `apply_withdrawals`/`get_builder_withdrawals`. The Withdrawal presented to the execution layer for the `fee_recipient` uses the raw, uncapped `withdrawal.amount`: [5](#0-4) 

while the builder's on-chain balance debit is capped by `min(withdrawal.amount, builder_balance)`: [6](#0-5) 

So if the builder's balance is insufficient to cover the second (duplicate) withdrawal, the balance debit is truncated to whatever remains (or zero), but the `fee_recipient` (chosen by the builder in the bid, i.e., attacker-controlled) still receives the *full* second payment - Gwei paid out that was never actually backed by an equivalent balance reduction. This breaks the invariant that a single escrowed bid value is paid to its beneficiary exactly once, the same equality violated in the ZeroLend report (a reward is transferred to a beneficiary a second time without the bookkeeping that gated the first transfer being consulted).

### Impact Explanation
This falls under "Gwei created, destroyed or paid to a non-owner" and "a builder payment or withdrawal misdirected, doubled or escaped" (High/Critical impact category per the rules). The duplicated payment is realized as an actual `Withdrawal` executed on the EL side to an address the builder controls, while the builder's balance debit that is supposed to fund it is capped and can fall short - meaning value is manufactured rather than merely misdirected internally.

### Likelihood Explanation
The trigger condition - a parent block's canonical reveal being delayed past the two-epoch eviction window while attesters still accumulate quorum-level weight for that slot in the interim - does not require a coalition or majority stake attack; it only requires that (a) the specific slot's payload happens to receive quorum-level same-slot attestation weight (normal under high participation) and (b) the block that actually commits the parent's execution requests for that slot is included more than two epochs later (possible under normal missed-slot/reorg conditions, not necessarily attacker-orchestrated). The fee_recipient of the bid is fully attacker (builder)-controlled, so whenever this timing window is hit, the builder profits from the uncapped double payment.

### Recommendation
`apply_parent_execution_payload`'s `elif parent_bid.value > 0` fallback branch must not unconditionally re-create a withdrawal purely from `parent_bid.value`. It needs a way to know whether the corresponding `BuilderPendingPayment` was already settled (either via `settle_builder_payment` or via the quorum eviction in `process_builder_pending_payments`) before appending a new `BuilderPendingWithdrawal`. Options: persist a "settled" marker/nonce per bid/slot that survives the payment array's rotation and is checked by both settlement paths, or make `process_builder_pending_payments` itself responsible for creating the withdrawal for evicted-but-unsettled entries only, while the late-reveal path checks that marker instead of blindly trusting `parent_bid.value`.

### Proof of Concept
Conceptual state-transition trace (spec-level, no client/coalition required beyond normal validator attestation and a delayed reveal):
1. Builder submits a bid for slot `X` with `value = V`, `fee_recipient = attacker_address`. `process_execution_payload_bid` records `BuilderPendingPayment` at index `SLOTS_PER_EPOCH + X % SLOTS_PER_EPOCH` with `withdrawal.amount = V`.
2. Validators include attestations for slot `X` in blocks at `X+1, X+2, ...` (within normal inclusion delay), each incrementing `payment.weight` via `process_attestation`, until `weight >= quorum`.
3. No proposer ever builds directly on top of the block containing slot `X`'s bid with a matching, on-time reveal (e.g., due to missed slots); more than 2 epochs pass.
4. At an epoch boundary, `process_builder_pending_payments` sees `weight >= quorum` for the rotated-in entry and appends `BuilderPendingWithdrawal(amount=V, fee_recipient=attacker_address, builder_index=builder)` to `state.builder_pending_withdrawals`, then clears/evicts the entry.
5. Later, a proposer finally includes a block whose `parent_execution_requests` correctly hashes to the original bid's `execution_requests_root` for slot `X` (this is legal - nothing in `process_parent_execution_payload` rejects a stale reveal). `apply_parent_execution_payload` computes `parent_epoch` as older than `previous_epoch`, hits the `elif parent_bid.value > 0` branch, and appends a **second** `BuilderPendingWithdrawal(amount=V, fee_recipient=attacker_address, builder_index=builder)`.
6. Both withdrawals are eventually swept via `get_builder_withdrawals`/`apply_withdrawals`: the EL-facing `Withdrawal.amount` for each is the full, uncapped `V`, while `state.builders[builder_index].balance` is only debited `min(V, balance)` each time. If the builder's balance is less than `2V`, the second debit is truncated, yet `attacker_address` still receives `V` again in full - net Gwei created and paid to the attacker beyond what was ever actually escrowed.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
