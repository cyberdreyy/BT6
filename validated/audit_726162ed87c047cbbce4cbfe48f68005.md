### Title
`setEpochParams` changes `epochDuration`/`bufferPeriod` without rescaling the vault APR, corrupting all subsequent interest accounting - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The reported bug class is a privileged setter that mutates one element of a coupled configuration (curve length) while leaving a cached derived value (`unit`) stale, causing downstream indexing/math errors. The same pattern exists in `IdleCDOEpochVariant.setEpochParams`: it updates `epochDuration` and `bufferPeriod` but never calls `_setScaledApr`, even though the APR stored in `IdleCreditVault` is a duration/buffer-scaled value that must be recomputed whenever those parameters change.

### Finding Description
The credit-vault APR is not stored raw; it is scaled by the epoch parameters before being pushed into the strategy:

- At initialization, `_additionalInit` sets `epochDuration = 30 days` and `bufferPeriod = 5 days`, then calls `_setScaledApr(_getStrategyApr())` so the vault APR reflects those parameters (`IdleCDOEpochVariant.sol:72-89`).
- `_setScaledApr` delegates to `IdleCreditVault.setAprsWithBuffer(_newApr, epochDuration, bufferPeriod)`, i.e. the stored APR is a function of both duration and buffer (`IdleCDOEpochVariant.sol:544-546`).
- The privileged `stopEpochWithDuration` path respects this coupling: after `setEpochParams(_duration, bufferPeriod)` it immediately calls `_setScaledApr(_newApr)` (`IdleCDOEpochVariant.sol:520-528`).

However, `setEpochParams` is also a standalone `public` owner/manager function (`IdleCDOEpochVariant.sol:117-125`) that writes `epochDuration` and `bufferPeriod` and performs no APR rescale:

```solidity
function setEpochParams(uint256 _epochDuration, uint256 _bufferPeriod) public {
    _checkOnlyOwnerOrManager();
    _checkNotAllowed(defaulted || isEpochRunning || _epochDuration == 0 || epochDuration == 0);
    epochDuration = _epochDuration;
    bufferPeriod = _bufferPeriod;
}
```

Worse, the function's own natspec warns "bufferPeriod should not be changed once set otherwise interest calculations will be wrong", yet it accepts and stores a new `bufferPeriod` anyway. Because the check only blocks calls while `isEpochRunning`, the setter can be invoked during the buffer phase, after which `startEpoch` runs the next epoch with `epochDuration`/`bufferPeriod` inconsistent with the scaled APR already stored in `IdleCreditVault`. `startEpoch` (lines 233+) computes the funds the borrower must return and the `expectedEpochInterest` from the vault's stale scaled APR, so the interest demand and the interest credited to tranche holders are computed with mismatched parameters — the exact analog of `getMultiplier` indexing `curve` with a stale `unit`.

### Impact Explanation
After a `setEpochParams` call, the scaled APR embedded in `IdleCreditVault` no longer corresponds to the actual `epochDuration`/`bufferPeriod`:

- If `bufferPeriod` or `epochDuration` is shortened while the stored scaled APR assumed a longer period, the borrower is charged a lower effective rate than configured, so `expectedEpochInterest` understates real yield. The shortfall is borne by AA/BB tranche holders permanently — the yield is simply never accrued or demanded, and subsequent accounting crystallizes the lower NAV.
- If lengthened, the borrower is charged more than owed; `stopEpoch`'s pull of `expectedEpochInterest` can exceed what the borrower prepared, pushing the pool into the `_handleBorrowerDefault` catch path even though the borrower behaved honestly — freezing LP withdrawals and forcing the default/finalization flow.

Either direction breaks the solvency/fair-distribution invariant of the epoch accounting and produces permanent yield loss or forced default with frozen funds.

### Likelihood Explanation
No attacker action is required — analogous to the original report, the vulnerability is a self-contained state inconsistency triggered by an honest owner/manager invoking a legitimate governance function. `setEpochParams` is intended to be callable (e.g., to change epoch length between epochs), is unguarded during the buffer phase, and gives no warning or revert that the APR must be rescaled. Any routine parameter update silently misprices the next epoch. The codebase itself acknowledges the hazard in the natspec but enforces nothing in code.

### Recommendation
Mirror the fix from the original report — recompute the dependent value inside the setter. Either call `_setScaledApr(_getStrategyApr())` at the end of `setEpochParams`, or revert on `bufferPeriod` changes (since the natspec states it must never change) and rescale on `epochDuration` changes:

```solidity
function setEpochParams(uint256 _epochDuration, uint256 _bufferPeriod) public {
    _checkOnlyOwnerOrManager();
    _checkNotAllowed(defaulted || isEpochRunning || _epochDuration == 0 || epochDuration == 0);
    _checkNotAllowed(_bufferPeriod != bufferPeriod); // bufferPeriod is immutable per spec
    epochDuration = _epochDuration;
    bufferPeriod = _bufferPeriod;
    _setScaledApr(_getStrategyApr());
}
```

### Proof of Concept
Conceptual Foundry fork scenario (deploy vault + `IdleCDOEpochVariant` CDO with a funded borrower):

1. Deposit as AA/BB lenders during buffer phase; manager calls `startEpoch()`, epoch runs with scaled APR `R = f(apr, 30 days, 5 days)`.
2. Epoch ends, borrower repays; `stopEpoch` succeeds. During the new buffer phase, owner calls `setEpochParams(15 days, 5 days)` (or changes `bufferPeriod`). No revert — `isEpochRunning == false`.
3. The vault's stored scaled APR still reflects the 30-day scaling. `startEpoch()` computes `expectedEpochInterest` and the borrower pull amount using the stale rate while the epoch actually accrues over 15 days.
4. Assert `expectedEpochInterest != interest that _calcInterestWithApr would produce for (apr, 15 days, 5 days)` — the discrepancy is mispriced yield: either LPs are permanently underpaid, or the `stopEpoch` pull exceeds the borrower's obligation and the catch branch triggers `_handleBorrowerDefault`, freezing withdrawals.

Limitation: I did not read the full body of `IdleCreditVault.setAprsWithBuffer`/`_calcInterest` to confirm the exact scaling formula, so the sign/magnitude of the mispricing depends on that implementation, but the stale-derivation defect and its reachability are confirmed from `IdleCDOEpochVariant.sol` alone.
