### Title
Stale write-off requests let a fulfiller purchase appreciated tranches at an outdated price - (contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow` stores a fixed `underlyingsRequested` amount without an expiry, epoch binding, or execution-time valuation check. A lender can create a write-off order while the epoch is running, but any unprivileged account can fulfill it after the epoch ends and the tranche NAV has increased. The fulfiller pays the stale quote and receives tranches worth more than the payment, transferring the lender's accrued value to the fulfiller.

### Finding Description
`createWriteOffRequest` records only the seller's tranche amount and requested underlying amount, then escrows the tranche tokens. [1](#0-0) 

The request is not bound to the epoch in which it was created, does not expire, and does not record the tranche price at which the seller accepted the quote. [2](#0-1) 

`fullfillWriteOffRequest` can be called by any wallet and only checks that the supplied tranche amount matches the stored amount and that the supplied underlyings are at least the stale requested amount. [3](#0-2) 

Unlike request creation, fulfillment does not verify that the epoch is still running or that the quoted amount remains consistent with current tranche value. [4](#0-3) [5](#0-4) 

After a successful epoch, the lender's tranche tokens can be worth more underlying than when the order was created. A fulfiller can nevertheless execute the stale order at the old quote, pay the seller only `underlyingsRequested - fee`, and receive the appreciated tranche tokens. [6](#0-5) 

This is the credit-vault analogue of a stale signed strike price: the economically critical valuation parameter is fixed at request creation while execution occurs under changed market conditions.

### Impact Explanation
An unprivileged fulfiller can purchase tranche tokens below their post-accrual value. The loss is borne by the lender whose stale order is executed and equals approximately:

```text
loss = trancheAmount * currentTranchePrice / ONE_TRANCHE
     - underlyingsRequested
     + exitFeeOnUnderlyingsRequested
```

For example, if 10,000 tranche tokens were offered for 10,000 USDC and epoch interest raises their redeemable value to 10,500 USDC, the fulfiller pays 10,000 USDC and receives 10,500 USDC of tranche exposure, capturing approximately 500 USDC of lender value before the escrow fee.

The request owner can call `deleteWriteOffRequest`, but that only prevents future fills; it does not protect an already stale request from being fulfilled in a later transaction or block before cancellation. [7](#0-6) 

### Likelihood Explanation
Likelihood is medium because the vulnerable sequence requires only ordinary protocol progression:

1. A lender creates a write-off request during a running epoch.
2. The epoch completes and accrues positive interest, increasing tranche value.
3. Any account fulfills the stale request at its old fixed quote.

No privileged attacker, malicious borrower, oracle manipulation, or signature replay is required. The fulfiller is explicitly allowed to be any wallet. [8](#0-7) 

### Recommendation
Bind fulfillment to the economic state in which the request was created and provide an expiry mechanism:

```solidity
struct WriteOffRequest {
    uint256 tranches;
    uint256 underlyings;
    uint256 epoch;
    uint256 deadline;
    uint256 maxTranchePrice;
}
```

At minimum:

- Store the request epoch and expire requests at or before the end of that epoch.
- Add a user-supplied `deadline` and reject fulfillment after `block.timestamp > deadline`.
- Alternatively, price fulfillment at the current tranche value instead of a permanently stored quote.
- Require the lender to refresh the request to update its quote.

For example:

```solidity
if (
    currentRequest.tranches != _tranches ||
    currentRequest.underlyings != _underlyings ||
    currentRequest.epoch != IdleCreditVault(strategy).epochNumber() ||
    block.timestamp > currentRequest.deadline
) {
    revert WrongRequest();
}
```

A hard expiry is preferable to relying on lenders to cancel stale requests.

### Proof of Concept
Add this test to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`. It uses the existing mainnet-fork setup and `_stopCurrentEpochWithApr` helper.

```solidity
function testStaleWriteOffRequestCanBeFilledAfterTrancheAppreciates() external {
    uint256 requestedTranches = 10_000e18;
    uint256 staleQuote = 10_000e6;
    address buyer = makeAddr("stale-fill-buyer");

    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, staleQuote);

    uint256 priceBefore = cdoEpoch.virtualPrice(address(tranche));

    // Honest borrower repayment/accrual increases tranche value.
    _stopCurrentEpochWithApr(10e18);

    uint256 priceAfter = cdoEpoch.virtualPrice(address(tranche));
    assertGt(priceAfter, priceBefore, "tranche did not appreciate");

    uint256 currentValue = requestedTranches * priceAfter / ONE_TRANCHE;
    assertGt(currentValue, staleQuote, "stale quote is not below current value");

    deal(address(underlying), buyer, staleQuote);
    vm.startPrank(buyer);
    underlying.approve(address(escrow), staleQuote);
    escrow.fullfillWriteOffRequest(LP, requestedTranches, staleQuote);
    vm.stopPrank();

    assertEq(
        tranche.balanceOf(buyer),
        requestedTranches,
        "buyer did not receive appreciated tranches"
    );
    assertEq(
        underlying.balanceOf(buyer),
        0,
        "buyer paid more than stale quote"
    );

    uint256 exitFee = staleQuote * escrow.exitFee() / escrow.FULL_VALUE();
    assertEq(
        underlying.balanceOf(LP),
        staleQuote - exitFee,
        "seller was paid more than stale quote minus fee"
    );
}
```

The key assertion is `currentValue > staleQuote`: the buyer acquires tranche tokens whose post-epoch value exceeds the amount paid, while the seller receives only the stale fixed quote.

```text
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens

    // get tranche tokens from user

    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests

      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
```

```text
  function deleteWriteOffRequest() external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[msg.sender];
    // transfer tranche tokens back to the user
    IERC20Detailed(tranche).safeTransfer(msg.sender, currentRequest.tranches);
```

```text
  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
