### Title
Native-token withdrawal griefing in `EscrowDst._withdraw` via revert-on-receive maker/fee recipients - (File: contracts/EscrowDst.sol)

### Summary
`EscrowDst._withdraw` pushes the native destination asset directly to the maker, the integrator-fee recipient and the protocol-fee recipient using a hard-revert ETH transfer helper. Any of these unprivileged, order-supplied addresses can be a contract without a `receive`/accepting `fallback`, which permanently reverts the whole `withdraw`/`publicWithdraw` call for as long as the withdrawal window is open, mirroring the `forceCancelOrder()` ETH-griefing pattern from the external report.

### Finding Description
`_withdraw` in `EscrowDst.sol` performs three unconditional native transfers when the destination token is `address(0)`: [1](#0-0) 

Each of these calls `_uniTransfer` → `_ethTransfer`, which reverts the *entire* transaction if the low-level call fails: [2](#0-1) 

`maker`, `integratorFeeRecipient` and `protocolFeeRecipient` are all values taken from order/immutables data supplied by unprivileged parties (maker signs the order; integrator fee recipient is attacker-influenced in a fee-on-transfer/integrator flow), not privileged roles. If any of these addresses is a smart contract that reverts on receiving ETH (deliberately, or simply because it has no payable fallback), then both `withdraw` (private, `onlyCaller(taker)`) and `publicWithdraw` (public, `onlyAccessTokenHolder`) call the same internal `_withdraw` and will always revert: [3](#0-2) 

This is functionally identical to the reported `forceCancelOrder()` issue: a hard `.call{value:}` + `require`/`revert` pattern with no fallback claim mechanism, callable by an unprivileged party's chosen recipient address, that can block completion of the ETH-refund/withdrawal path for the duration of the relevant time window.

### Impact Explanation
While the taker eventually recovers their destination-chain tokens and safety deposit via `cancel()` once the cancellation timelock elapses (since `cancel()` sends the reclaimed native token back to `taker`/`msg.sender`, not the blocked `maker`), the maker can never receive their swap proceeds through `withdraw`/`publicWithdraw` for the entire withdrawal window, and the taker's committed dst-chain capital plus safety deposit remain locked until cancellation becomes available. This matches the bounty's High-severity bucket: "temporary freezing of funds during the live swap lifecycle."

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the maker (or an integrator/protocol fee recipient controlled by an adversarial integrator) to deliberately use a contract address that rejects plain ETH transfers, or for that address to accidentally be a non-payable contract. Since the maker controls their own recipient address, self-griefing has limited direct financial upside for the maker themselves, but it does impose real capital-lockup cost on the resolver/taker for the length of the withdrawal window, and can be used as leverage/blackmail exactly as in the source report.

### Recommendation
Replace the direct push-based native transfers to non-caller-controlled recipients (`maker`, `integratorFeeRecipient`, `protocolFeeRecipient`) in `EscrowDst._withdraw` (and any equivalent path) with a pull-based claim mechanism: on transfer failure, credit the amount to an internal `pendingWithdrawals[recipient]` mapping instead of reverting, and expose a separate `claim()` function for recipients to withdraw at their own convenience. This preserves the withdrawal/cancellation flow's liveness regardless of a recipient's ability/willingness to accept a raw ETH transfer.

### Proof of Concept
1. Maker signs a Fusion order with destination token = `address(0)` (native) and their own `maker` address set to a contract `M` with no `receive`/payable `fallback` (or one that explicitly reverts).
2. Resolver fills the order on the source chain, deploys `EscrowDst`, and funds it with the native destination amount + safety deposit via `createDstEscrow`.
3. Once the withdrawal window opens, the resolver calls `EscrowDst.withdraw(secret, immutables)`. Execution reaches `_uniTransfer(token, maker.get(), amount)` → `_ethTransfer` → `M.call{value: amount}("")` which reverts because `M` cannot accept ETH.
4. Because `_ethTransfer` reverts on failure (`contracts/BaseEscrow.sol:95-98`), the entire `withdraw` call reverts — this repeats for every call to `withdraw` or `publicWithdraw` throughout both the private and public withdrawal periods, since both invoke the same `_withdraw` internal function (`contracts/EscrowDst.sol:36-57`).
5. The swap can only be unwound via `cancel()` after the cancellation timelock, during which the resolver's destination-chain capital and safety deposit are frozen and the maker never receives their funds through the intended withdrawal path.

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```

```text
    function _uniTransfer(address token, address to, uint256 amount) internal {
        if (token == address(0)) {
            _ethTransfer(to, amount);
        } else {
            IERC20(token).safeTransfer(to, amount);
        }
    }

    /**
     * @dev Transfers native tokens to the recipient.
     */
    function _ethTransfer(address to, uint256 amount) internal {
        (bool success,) = to.call{ value: amount }("");
        if (!success) revert NativeTokenSendingFailure();
    }
```
