## Title
Gateway CORS allowlist wildcard check uses unanchored suffix match, allowing origin allowlist bypass - (File: `core/services/gateway/network/httpserver.go`)

### Summary
The Chainlink Gateway HTTP server's CORS origin-allowlist check (`isAllowedOrigin`) validates wildcard entries (e.g. `*.remix.com`) by stripping the `*.` prefix and then testing `strings.HasSuffix(originHost, allowedHost)`. This is the same class of bug as the DNSSEC report: it compares strings as raw substrings/suffixes instead of comparing DNS labels with a proper boundary, so an attacker-controlled hostname that merely *ends with* the allowed suffix — without being an actual subdomain (i.e., without a `.` separator) — is incorrectly treated as covered by the allowlist.

### Finding Description
In `isAllowedOrigin`, wildcard entries are handled as:

```go
// check for wildcard host match (e.g., *.remix.com)
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [1](#0-0) 

For a configured allowed origin `https://*.remix.com`, `allowedHost` becomes `remix.com`. The check `strings.HasSuffix(originHost, "remix.com")` is true not only for genuine subdomains such as `sub.remix.com`, but also for any unrelated host that happens to end with the same characters without a dot boundary, e.g. `evilremix.com` or `notremix.com`. This mirrors exactly the DNSSEC finding's root cause: label/subdomain containment was implemented as a raw string/byte-sequence comparison instead of verifying a label (here: a literal `.`) boundary before the suffix.

This logic is invoked from `handleRequest`, which is the entry point for all requests to the Gateway's internet-facing HTTP endpoint:
```go
if s.config.CORSEnabled {
    origin := r.Header.Get("Origin")
    if s.isAllowedOrigin(origin) {
        w.Header().Set("Access-Control-Allow-Origin", origin)
        w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
        w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
    }
    ...
``` [2](#0-1) 

The `Origin` header is fully attacker-controlled (any website can send any `Origin` value in a browser-initiated cross-origin request), so an unprivileged, unauthenticated client can trivially trigger this path by hosting a page on a domain crafted to satisfy the suffix check.

### Impact Explanation
When the suffix check incorrectly matches, the server reflects the attacker's `Origin` back in `Access-Control-Allow-Origin`, effectively granting a domain that was never intended to be trusted the same cross-origin access as a legitimate allowlisted origin. This is a concrete allowlist bypass on the Gateway's internet-facing HTTP endpoint (`handleRequest` → `s.handler.ProcessRequest`, which processes JSON-RPC message envelopes) [3](#0-2) . A victim browser visiting an attacker page on such a crafted domain could be induced to send cross-origin requests to the Gateway and have the response readable by the malicious page, undermining the operator's origin-based access control for the API. The existing test suite only exercises the intended positive/negative subdomain cases (`ethereum.remix.org` failing because it doesn't *end with* `ethereum.org`) and does not cover the boundary-less suffix collision case [4](#0-3) .

### Likelihood Explanation
Exploitability depends on an operator configuring a wildcard `CORSAllowedOrigins` entry (e.g. `https://*.example.com`) and an attacker being able to register or control a domain whose name ends with `example.com` without a `.` separator (e.g. `notexample.com`, `evilexample.com`). This is realistically achievable since domain registration is unrestricted and such names are easy to obtain, making this more practically exploitable than the original DNS-label report (which required crafting labels around DNS's 63-octet/lowercase-letter constraints).

### Recommendation
Anchor the wildcard suffix match on a label boundary instead of a raw string suffix, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures `evilremix.com` is rejected while `sub.remix.com` and `remix.com` itself are correctly matched.

### Proof of Concept
1. Configure the Gateway with `CORSAllowedOrigins = ["https://*.remix.com"]` and `CORSEnabled = true`.
2. From an unprivileged client (e.g., browser JS on an attacker-controlled site `https://evilremix.com`), send a request to the Gateway's configured `Path` with header `Origin: https://evilremix.com`.
3. `isAllowedOrigin` computes `allowedHost = "remix.com"`, `originHost = "evilremix.com"`, and `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`.
4. The server responds with `Access-Control-Allow-Origin: https://evilremix.com`, allowing the attacker's origin to read the response, despite not being a genuine subdomain of `remix.com`.
