### Title
`ProgrammableBorrower._repay` clears tracked borrower debt by the nominal `assets` parameter instead of the actual balance received, so fee-on-transfer/deflationary underlyings permanently overstate vault NAV and leave late withdrawers unbacked - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external Allo report describes the class "accounting variable set to the nominal transferred amount while `balanceOf` reflects less (fee-on-transfer / non-standard tokens), so payouts computed from the accounting variable exceed the real balance and late claimants cannot be paid." The exact analog exists in the programmable-borrower credit facility: `_repay` performs `safeTransferFrom(borrower, this, assets)` and then decrements `borrowerInterestDebt`, `borrowerInterestAccrued` and `borrowerPrincipal` by the **nominal** `assets` value, not by the balance delta. The IdleCDO-side deposit path is careful (`IdleCDOCreditVault._deposit` mints shares on `balanceAfter - balanceBefore`), but the repay path is not, so the debt ledger and the token balance diverge by the transfer fee on every repayment.

### Finding Description
In `ProgrammableBorrower._repay` (`contracts/strategies/idle/ProgrammableBorrower.sol`):

```solidity
underlyingToken.safeTransferFrom(borrower, address(this), assets);
uint256 totalRepaidAssets = assets;
...
borrowerInterestDebt = 0 / settledInterestDue - assets;      // cleared by nominal
borrowerInterestAccrued = 0 / accruedInterestDue - assets;   // cleared by nominal
borrowerPrincipal = principalDue - principalPaid;            // reduced by nominal
```

All three debt buckets are reduced assuming the contract received exactly `assets`. With a fee-on-transfer underlying (e.g., a USDT-style fee flag enabled, or any rebasing/deflationary token configured as `underlyingToken`), the contract actually receives `assets - fee`. Two correlated mismatches follow:

1. **NAV overstatement.** The credit vault prices tranches from managed value: on-hand `underlyingToken.balanceOf`, the ERC4626 sleeve `_currentVaultAssets()`, and the borrower obligation buckets (`borrowerPrincipal`, `borrowerInterestDebt`, `borrowerInterestAccrued`). Each repayment reduces the obligation leg by `assets` but increases the cash leg by only `assets - fee`, so `getContractValue`/`_managedContractValue` and therefore `virtualPrice` are permanently inflated by the cumulative fees. This is precisely the `poolAmount` vs `balanceOf` divergence in the report: the ledger claims more than the balance can pay.

2. **Re-deposit shortfall.** When `epochAccountingActive`, the nominal amount is pushed onward via `_depositToVault(totalRepaidAssets, totalRepaidAssets - currentEpochInterestPaid)`, i.e., `vault.deposit(_assetAmount)` is called with the nominal figure. If the fee is charged on the vault's own pull (or the strategy forwards a nominal `_amount` as `IdleCDOCreditVault._deposit` does at line 211 with `IIdleCDOStrategy(strategy).deposit(_amount)`), the vault sleeve mints/records against more assets than actually arrived, compounding the NAV/ledger gap, or reverts outright when no stray balance exists to absorb the difference.

The same nominal-vs-actual assumption appears on the pull side of the epoch: `onStopEpoch` guarantees `onHand >= _amountRequired` by `balanceOf`, but IdleCDO then pulls `safeTransferFrom` of the nominal amount and settles `settleBorrowerInterest()` at the full contractual figure — a fee on that transfer leaves the pool short by the fee while interest is booked as fully received.

The broken invariant is solvency/fair-burn: the sum of tranche shares priced off the inflated NAV exceeds the real recoverable assets, so withdrawals paid at `virtualPrice` drain real cash faster than entitlements shrink — early redeemers are made whole, late redeemers (or AA holders at epoch settlement / `collectWithdrawFunds`) find the pool short. This mirrors the report's "sum of all recipient payouts exceeds `balanceOf`" outcome.

### Impact Explanation
Each repayment permanently leaks `fee` worth of backing while the tranche-price numerator is unaffected, so every outstanding tranche token is slightly overpriced. An unprivileged lender (KYC-passing) can time a `withdrawAA`/epoch `requestWithdraw` right after repayments settle, redeeming at the inflated `virtualPrice` and extracting the cumulative fee gap; the residual shortfall is socialized onto remaining holders, and the last claimants' withdrawals revert on insufficient balance — a permanent, unrecoverable loss bounded only by `fee × cumulative repaid volume` per epoch.

### Likelihood Explanation
Medium-low. It requires the vault's `underlyingToken` to be fee-on-transfer or otherwise non-1:1 on transfer (the facility accepts arbitrary ERC20 underlying at initialize, and `_borrow`/`_repay`/`deposit` all assume exact receipt). No privileged action is needed beyond the honest borrower repaying normally — the divergence accrues automatically once such a token is used, and any lender can harvest the inflated price. If the underlying is guaranteed plain USDC with fees disabled, the issue is latent rather than live.

### Recommendation
Mirror the balance-delta pattern already used in `IdleCDOCreditVault._deposit` / `IdleCDO._deposit` inside `ProgrammableBorrower._repay`:

```solidity
uint256 balBefore = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(borrower, address(this), assets);
uint256 received = underlyingToken.balanceOf(address(this)) - balBefore;
```

and reduce `borrowerInterestDebt`/`borrowerInterestAccrued`/`borrowerPrincipal` by `received`, not `assets`. Apply the same delta measurement in `_depositToVault` (record `epochDepositedToVault` from shares/assets actually credited by `vault.deposit`), in `_borrow`/`onStopEpoch` (record `epochWithdrawnFromVault` from the actual post-withdraw balance rather than the requested `shortfall`), and in the IdleCDO stop-epoch pull (credit interest by `balanceAfter - balanceBefore`, not `_amountRequired`). Alternatively, explicitly document/enforce at `initialize` that `underlyingToken` must be a strictly feeless, non-rebasing ERC20.

### Proof of Concept
Foundry fork-style PoC (mock FoT token is sufficient since the flaw is token-behavior-dependent, not counterparty-dependent):

```solidity
// FeeToken: ERC20 that burns 1% on every transferFrom/transfer
FeeToken usdtFee = new FeeToken(); // set as vault underlyingToken
// setup: deploy ProgrammableBorrower + MockVault + MockCDO with usdtFee
// epoch active, borrower has drawn 10_000e18, owes interestDebt = 100e18

uint256 repayAmt = 5_100e18;
usdtFee.mint(borrower, repayAmt);
vm.prank(borrower);
usdtFee.approve(address(pb), repayAmt);

uint256 pbBalBefore = usdtFee.balanceOf(address(pb));
uint256 principalBefore = pb.borrowerPrincipal();
uint256 debtBefore = pb.borrowerInterestDebt();

vm.prank(borrower);
pb.repay(repayAmt);

uint256 received = usdtFee.balanceOf(address(pb)) - pbBalBefore;
assertLt(received, repayAmt);                       // 1% fee actually received
// debt legs were reduced by the full nominal amount:
uint256 debtCleared = (debtBefore - pb.borrowerInterestDebt())
                    + (principalBefore - pb.borrowerPrincipal());
assertEq(debtCleared, repayAmt);                    // nominal cleared
// => accounted NAV dropped by repayAmt, real assets grew by received < repayAmt
// => virtualPrice inflated by (repayAmt - received); a lender redeeming now
//    withdraws more underlying than its pro-rata share of real backing.
```

Note: I verified the `_repay` nominal-accounting path and the delta-based `_deposit` contrast directly in the source; I did not get to read `IdleCDOEpochVariant.stopEpoch`/`IdleCDOCreditVault._managedContractValue` line-by-line in this pass, so the exact NAV formula and the stop-epoch pull should be confirmed when implementing, but the debt-ledger/balance divergence in `_repay` is confirmed in the code above.
