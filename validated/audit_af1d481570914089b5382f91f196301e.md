### Title
Stale per-epoch instant-withdraw receipts inflate default recovery basis and prefunded reserve, enabling over-claims and insolvency of the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out the aggregate `instantWithdrawsRequests[_user]` and zeroes it, but never clears the per-epoch accounting `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. These per-epoch mappings are the "reference" that survives the receipt's destruction — the direct analog of nghttp2 keeping a stream reference after mod_http2 freed it. When default finalization later iterates them, the already-paid (destroyed) claims are re-read as live claim basis and as phantom prefunded reserve, corrupting `defaultRecoveryPrice`/`defaultRecoveryReserve` and enabling double-payment of one receipt.

### Finding Description
In `IdleCreditVault.claimInstantWithdrawRequest`, only the aggregate counter is cleared:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (written in `requestInstantWithdraw`) are never decremented on a successful funded claim; `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws`, not `instantWithdrawClaimsByEpoch`. The per-epoch records become dangling references to a receipt that no longer exists.

At `finalizeDefaultRecovery`, those stale records are re-consumed twice:
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the claim basis whenever `pendingInstantWithdraws != 0` (e.g. another user's unfunded instant request), so destroyed claims are counted as outstanding liabilities.
- `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` and adds it to `reserveAmount` as supposedly already-held underlying — but that underlying was already transferred to the claimer, so it is phantom collateral.

Two exploitable consequences for an unprivileged lender:

1. *Double payout of one receipt*: a user's stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` remains non-zero after they already claimed at par. In `claimInstantWithdrawRequest` after finalization, `_claimDefaultedInstantWithdrawRequest` reads the stale basis, pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from `defaultRecoveryReserve`, and `instantWithdrawsRequests[user] -= claimBasis` succeeds if the user has topped up `instantWithdrawsRequests[user]` with any new instant request. One funded receipt is paid twice.
2. *Insolvency of the recovery reserve*: the phantom prefunded amount inflates both basis and reserve equally, pushing `defaultRecoveryPrice` toward par while the underlying was already paid out. Early claimants are overpaid; later legitimate defaulted claims hit `defaultRecoveryReserve -= _amount` underflow/shortfall and revert — permanent freezing of others' recovery funds.

### Impact Explanation
Direct theft and insolvency: an attacker can recover a second, recovery-priced payout on an already-claimed instant receipt, and more generally the inflated basis/reserve mispricing drains `defaultRecoveryReserve`, leaving later honest claimants' funds permanently unclaimable. Loss is bounded by the attacker's stale claim size scaled by `defaultRecoveryPrice`, plus the systemic shortfall equal to all already-claimed instant receipts included in `instantWithdrawClaimsByEpoch[defaultEpoch]`.

### Likelihood Explanation
Requires a borrower default finalized via `finalizeDefaultRecovery` while `pendingInstantWithdraws != 0` in the default epoch, and an attacker who claimed an instant withdrawal earlier in the same epoch. Attacker is an ordinary KYC'd lender; sequencing is around honest owner/manager calls only. Preconditions are realistic in a pool with instant withdrawals enabled, but epoch overlap constraints make it conditional rather than trivial.

### Recommendation
Clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` inside `claimInstantWithdrawRequest` (or inside `collectInstantWithdrawFunds` per-epoch), so destroyed receipts cannot be re-read by default finalization. Alternatively, track funded-vs-unfunded per-epoch and only count the still-unclaimed portion in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`.

### Proof of Concept
Foundry fork PoC (skeleton; harness follows `test/foundry/IdleCreditVault.t.sol` conventions):

```solidity
function testStaleInstantReceiptDoubleClaim() public {
    // running epoch; LP deposits, borrower draws
    _depositWithUser(LP, 100_000 * ONE_SCALE, true);
    _depositWithUser(other, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // LP requests instant withdraw; CDO funds it via collectInstantWithdrawFunds; LP claims at par
    vm.prank(LP);
    cdoEpoch.requestInstantWithdraw(50_000 * ONE_SCALE, address(AAtranche));
    // ... manager/CDO routes funds: strategy.collectInstantWithdrawFunds(...)
    vm.prank(LP);
    cdoEpoch.claimInstantWithdrawRequest(); // paid at par

    // stale references remain
    assertGt(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0);
    assertGt(strategy.instantWithdrawsRequestsByEpoch(LP, strategy.epochNumber()), 0);

    // another user's instant request stays unfunded => pendingInstantWithdraws != 0
    // borrower defaults; owner finalizes recovery
    _checkDefault();
    // finalizeDefault(recovered, manager) — basis & prefunded reserve now include LP's paid claim

    // LP creates a small new instant request so the -= does not underflow, then claims again:
    vm.prank(LP);
    cdoEpoch.claimInstantWithdrawRequest(); // pays stale basis * defaultRecoveryPrice from reserve — second payout
}
```
