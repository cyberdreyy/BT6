Found a genuine on-chain analog to the VUSD "zero/blocking amount" bug class: an arithmetic-underflow single-point-of-failure in `EscrowDst._withdraw` that is reachable because `createDstEscrow` never validates the fee parameters it deploys with, unlike the sibling `_postInteraction` path which does perform that exact check.

### Title
Missing fee-amount validation in `createDstEscrow` lets an unprivileged taker deploy a permanently unwithdrawable `EscrowDst` via arithmetic underflow - (File: contracts/BaseEscrowFactory.sol)

### Summary
`BaseEscrowFactory._postInteraction` (source-chain escrow creation path) explicitly validates that `integratorFeeAmount + protocolFeeAmount < takingAmount` before proceeding [1](#0-0) . However `createDstEscrow`, the function that actually deploys `EscrowDst` and is called directly by an unprivileged taker with an arbitrary `IBaseEscrow.Immutables calldata dstImmutables` argument, performs no such validation at all [2](#0-1) . The `parameters` field (which encodes `protocolFeeAmount`/`integratorFeeAmount`) is fully attacker-controlled since `createDstEscrow` copies `dstImmutables` verbatim into the deployed clone's salt/hash.

### Finding Description
`EscrowDst._withdraw` computes the maker payout as an unchecked-looking subtraction that Solidity 0.8 will revert on underflow:
```solidity
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
``` [3](#0-2) 

Because `createDstEscrow` never checks `integratorFeeAmount + protocolFeeAmount < immutables.amount`, a taker can deploy an `EscrowDst` clone whose embedded fee parameters equal or exceed `immutables.amount`. Both `withdraw` and `publicWithdraw` funnel into `_withdraw`, so every withdrawal attempt for that escrow reverts with an arithmetic-underflow panic, for the entire withdrawal window [4](#0-3) . This mirrors the reported bug class: an unprivileged, non-owner-controlled numeric input (here fee amounts instead of a zero-transfer amount) reaches a code path with no guard, causing the affected operation (withdraw) to be permanently blocked for that instance, exactly as VUSD's `processWithdrawals` was permanently blocked by an unguarded zero-value transfer.

`cancel()` is unaffected because it transfers the full `immutables.amount` without subtracting fees [5](#0-4) , so funds are eventually recoverable — but only by the taker after the `DstCancellation` timelock, not by the maker who was supposed to receive them during the withdrawal window.

### Impact Explanation
This is a temporary freezing of funds during the live swap lifecycle: the maker cannot obtain their destination-chain tokens through the intended `withdraw`/`publicWithdraw` path for the full withdrawal + public-withdrawal duration, even though they hold the correct secret and call the correct function with correct-hash immutables — the transaction always reverts due to underflow. This matches the Medium/High bounty bucket for "smart contract unable to operate because required token/native balances can be broken by an unprivileged actor" / "temporary freezing of funds during the live swap lifecycle."

### Likelihood Explanation
Any taker calling `createDstEscrow` directly controls the full `Immutables` struct, including the encoded `parameters` bytes read by `protocolFeeAmountCd`/`integratorFeeAmountCd` [6](#0-5) . No signature, whitelist, or on-chain cross-check ties `dstImmutables.parameters` to a value legitimately derived from `FeeCalcLib.getFeeAmounts` or to the source-chain `DstImmutablesComplement.parameters` that was emitted in `SrcEscrowCreated`. This makes the trigger a single, low-cost, always-reachable public call.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`:
```solidity
if (dstImmutables.integratorFeeAmountCd() + dstImmutables.protocolFeeAmountCd() >= dstImmutables.amount) revert InvalidFeeAmounts();
```
placed before the escrow is deployed and funded, so a mis-parameterized escrow is never created in the first place.

### Proof of Concept
1. Taker (unprivileged caller) calls `createDstEscrow` with `dstImmutables.amount = X` and `parameters` encoding `protocolFeeAmount = X`, `integratorFeeAmount = 0` (or any combination where `protocolFeeAmount + integratorFeeAmount >= X`), sending the correct `msg.value`/token approval as required by `createDstEscrow` [2](#0-1) .
2. The clone is deployed and funded successfully — no check rejects the fee configuration.
3. Once inside the withdrawal window, the maker (or a public-withdraw caller with the access token) calls `withdraw`/`publicWithdraw` with the correct secret; `_withdraw` reverts every time on `immutables.amount - integratorFeeAmount - protocolFeeAmount` underflow [7](#0-6) .
4. Maker cannot claim destination funds during the entire withdrawal/public-withdrawal window; only the taker can eventually reclaim everything via `cancel()` after `DstCancellation`.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);

    function protocolFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x20) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(parameters.offset)
        }
    }

    /**
     * @notice Returns the integrator fee amount from the immutables (calldata version).
     * @param immutables The immutables to extract the fee from.
     * @return ret The integrator fee amount.
     */
    function integratorFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x40) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(add(parameters.offset, 0x20))
        }
    }
