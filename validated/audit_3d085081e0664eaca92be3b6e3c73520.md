### Title
Builder withdrawal amount sent to the execution layer is decoupled from the amount actually deducted from the builder's CL balance, minting unbacked Gwei - (File: `specs/gloas/beacon-chain.md`)

### Summary
In the Gloas builder-payment flow, a queued `BuilderPendingWithdrawal.amount` is copied verbatim into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` (i.e. the exact value the execution layer is committed to pay to `fee_recipient`), but the corresponding CL-side balance deduction in `apply_withdrawals` is capped with `min(withdrawal.amount, builder_balance)`. If the builder's tracked balance is smaller than the committed withdrawal amount at processing time, the execution layer still credits the full uncapped amount while the beacon state only removes the smaller, capped amount — creating Gwei that is not backed by any equivalent decrease anywhere in the system. This is the same bug class as the referenced AlgebraPool report: the amount actually enforced/committed downstream is silently decoupled from the amount computed/checked upstream.

### Finding Description
`get_builder_withdrawals` builds the `Withdrawal` entries for builders directly from the pending-withdrawal queue, without re-checking the builder's current balance: [1](#0-0) 

These withdrawals are merged into `get_expected_withdrawals` and become `state.payload_expected_withdrawals`, which the execution layer is required to honor by crediting `fee_recipient` with exactly `amount`: [2](#0-1) 

However, the CL-side balance deduction in `apply_withdrawals` silently caps the removal to the builder's currently available balance: [3](#0-2) 

This is the exact analog of the reported bug: the "amount required" that is externally committed (the value paid out at the execution layer) is not equal to the amount actually enforced by the internal accounting check (`min(withdrawal.amount, builder_balance)` on the CL side), just as `amountRequired` in `AlgebraPool` was forced to equal a balance delta that could never represent the true signed value needed for exact-output semantics.

The specification itself documents this exact discrepancy as expected behavior in its test helpers, confirming the capping is real and reachable: [4](#0-3) 
The test explicitly shows a withdrawal committed at 5 ETH (`withdrawal.amount`) while only 1 ETH of builder balance is actually deducted — the other 4 ETH is nevertheless paid out by the execution layer per the withdrawals list included in the block's execution payload.

### Impact Explanation
If `state.payload_expected_withdrawals` (and hence the block's execution-payload withdrawals list, which the EL executes unconditionally) contains a builder withdrawal whose `amount` exceeds that builder's tracked CL balance, the execution layer mints/pays the `fee_recipient` the full committed amount while the CL only reduces the builder's balance by the smaller, capped amount. The difference is Gwei created from nothing and paid to a non-owner (`fee_recipient`), directly matching the Critical impact category "Gwei created, destroyed, or paid to a non-owner."

### Likelihood Explanation
The `min()` cap is unconditional and unguarded by any assertion — the spec does not reject blocks whose committed withdrawal amount exceeds the builder's balance; it silently under-deducts instead. Reaching the exact `builder.balance < withdrawal.amount` state requires either multiple pending withdrawal/payment entries for the same builder whose sum exceeds the balance at the time the sweep is executed, or a balance reduction (e.g., another concurrent withdrawal or exit processed earlier in the same sweep) occurring between when the pending withdrawal amount was queued (at bid-acceptance time, validated by `can_afford`-style checks) and when it is actually applied. I was not able to fully trace, within the available context, every code path that inserts entries into `builder_pending_withdrawals` (`settle_builder_payment`, `process_builder_exit_request`) to conclusively determine whether the existing balance checks at enqueue time are sufficient to prevent this state from ever arising; this remains uncertain given the tool budget, but the code path and the test explicitly modeling amount > balance indicate the discrepancy is a recognized, reachable state in the spec's own design.

### Recommendation
Either (a) assert at withdrawal-construction time (`get_builder_withdrawals`/`get_expected_withdrawals`) that no withdrawal amount exceeds the associated builder's currently available balance, so an over-committed withdrawal can never be included in `payload_expected_withdrawals`, or (b) cap the amount placed into the `Withdrawal` object itself to `min(withdrawal.amount, builder_balance)` so that the value committed to (and paid by) the execution layer always matches the value actually removed from the builder's CL-tracked balance.

### Proof of Concept
1. Builder `B` has `state.builders[B].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals` contains an entry for `B` with `amount = 5_000_000_000` (5 ETH), as constructed via `test_builder_withdrawal_insufficient_balance` [5](#0-4) .
3. `get_builder_withdrawals` emits a `Withdrawal(amount=5_000_000_000, address=fee_recipient, ...)` unconditionally [6](#0-5) .
4. This withdrawal is placed into `state.payload_expected_withdrawals`, which the block's execution payload must match; the execution layer therefore credits `fee_recipient` with 5 ETH.
5. `apply_withdrawals` only executes `state.builders[B].balance -= min(5_000_000_000, 1_000_000_000)`, i.e. deducts just 1 ETH from the CL-tracked builder balance [7](#0-6) .
6. Net result: 4 ETH was paid out at the execution layer with no corresponding decrease anywhere in the beacon state — Gwei created and paid to `fee_recipient`.
