### Title
Instant-withdraw receipts from pre-default epochs are excluded from recovery basis but remain payable at par, draining funded claims — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a double free: the same resource is released twice because cleanup is done both on the error path and inside the deallocation routine. The analog in `IdleCreditVault` is an instant-withdraw receipt that lives in two accounting worlds at once: it is counted in the global `pendingInstantWithdraws` counter, but its claim basis is only recognized for the *current* epoch (`instantWithdrawsRequestsByEpoch[epochNumber]`). At `finalizeDefaultRecovery` a stale-epoch unfunded instant receipt is omitted from `defaultPendingClaimBasis` (no recovery reserve is sized for it), yet `claimInstantWithdrawRequest` still pays it at par from `_transferFundedClaim`, consuming underlyings that fund other users' receipts — a double-spend of the same funded-claim balance, or a permanent freeze when the guard kicks in.

### Finding Description
`requestInstantWithdraw` records the request three ways: `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]`, plus the global `pendingInstantWithdraws` [1](#0-0) . The global counter is only decremented when the CDO collects funds via `collectInstantWithdrawFunds` [2](#0-1) . If the borrower never returns that liquidity before default, the receipt stays pending forever while `epochNumber` advances.

At default finalization, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch's basis — whenever `pendingInstantWithdraws != 0` [3](#0-2) . A receipt created in an earlier epoch contributes to `pendingInstantWithdraws` (so `defaultInstantWithdrawsFinalized` is set [4](#0-3) ) but its per-epoch basis is stored under the old epoch key, so it is never included in `totalBasis` and no share of `defaultRecoveryReserve` is reserved for it [5](#0-4) .

After finalization, `claimInstantWithdrawRequest` runs `_claimDefaultedInstantWithdrawRequest`, which only looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — zero for the stale receipt [6](#0-5) . Execution then falls through to the par payout: `instantWithdrawsRequests[_user]` is burned and `_transferFundedClaim(_user, amount)` transfers the full basis [7](#0-6) . `_transferFundedClaim` only protects `defaultRecoveryReserve` itself [8](#0-7) , so the stale receipt is paid out of the strategy's funded-claim buffer that backs *other* users' normal withdraw receipts (`withdrawsRequests`, settled APR0 buckets). When the buffer is exhausted, the same claim instead reverts permanently — the unprivileged holder's receipt is frozen with no recovery path, since no reserve was ever sized for it.

### Impact Explanation
Two symmetric outcomes, both direct fund impact:

1. If the strategy holds funded-claim underlyings above `defaultRecoveryReserve` (funded `withdrawsRequests` / settled APR0 claims), the stale instant receipt is paid at par, stealing up to its full basis from those balances. Later legitimate claimants' `claimWithdrawRequest` calls then revert in `_transferFundedClaim` or `_transferDefaultRecovery` underflow — direct theft of their already-funded claims.
2. If no such buffer exists, the stale receipt's claim reverts (`balance - reserve < amount`), permanently freezing the user's claim. The tokens backing it were lost in the borrower default, yet finalization excluded the receipt from the recovery basis, so the holder is denied both par payment and the recovery haircut — an unrecoverable loss equal to the full receipt amount.

### Likelihood Explanation
Requirements: an instant-withdraw request is left unfunded (borrower does not return that portion at `startEpoch`, which the code explicitly contemplates — the comment in `defaultPendingClaimBasis` acknowledges partially covered instant queues [9](#0-8) ), the pool continues operating so `epochNumber` advances past the request epoch, and the borrower is later defaulted and finalized via `finalizeDefaultRecovery`. No attacker privilege or timing precision is needed — the attacker is simply an unprivileged holder of a stale instant receipt calling `claimInstantWithdrawRequest` before other claimants.

### Recommendation
Make recovery basis epoch-agnostic for instant receipts: in `defaultPendingClaimBasis`, include all outstanding instant claims (e.g., track a global `instantWithdrawClaimsTotal` incremented in `requestInstantWithdraw` and decremented on claim) rather than only `instantWithdrawClaimsByEpoch[epochNumber]` when `pendingInstantWithdraws != 0`. Correspondingly, `_claimDefaultedInstantWithdrawRequest` should clear every epoch with a non-zero `instantWithdrawsRequestsByEpoch` for the user (or iterate the aggregate), not only `defaultRecoveryEpoch`. Alternatively, track unfunded instant receipts per user and route them through `defaultRecoveryPrice` like normal pending receipts.

```text
  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
```

```text
    _onlyIdleCDO();

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);

    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
