### Title
Stale rejection weight is never cleared when a signer later accepts, breaking the aggregated-weight-vs-verified-accepts equality - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The mining-node's `StackerDBListener`, which tallies signer `BlockResponse` messages into `BlockStatus.total_weight_approved` / `total_weight_rejected`, uses two different membership maps to decide whether to add a signer's weight for the `Accepted` and `Rejected` cases. This asymmetry lets a single signer's weight remain counted in `total_weight_rejected` forever, even after that same signer later sends a valid `Accepted` response for the same block, mirroring the reported "tracking variable never reflects true state" bug class (`totalVaultDeposits` in the report) — except here the diverging counter is the on-chain-adjacent weight tally that gates whether the block is broadcast or abandoned.

### Finding Description
`BlockStatus` tracks three pieces of per-block state (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:70-82`):
- `responded_signers`: set of slot ids that have responded at all
- `gathered_signatures`: map of slot id → signature, populated only by the `Accepted` branch
- `total_weight_approved` / `total_weight_rejected`: weight counters

When a `Rejected` message is processed, weight is added only once per slot, guarded by `responded_signers.insert(slot_id)`: [1](#0-0) 

When an `Accepted` message is processed, however, the guard uses a *different* map — `gathered_signatures`, not `responded_signers`: [2](#0-1) 

Because `gathered_signatures` is only ever written by the `Accepted` branch, a signer who first sends `Rejected` (adding its weight to `total_weight_rejected` and inserting itself into `responded_signers`) and later sends a valid `Accepted` for the *same* block will pass the `!gathered_signatures.contains_key(&slot_id)` check (still empty for that slot) and get its weight added to `total_weight_approved` as well. Its weight is never removed from `total_weight_rejected`. The signer's weight is now double-booked: once as "rejected", once as "approved", and the stale rejected value is never corrected.

This breaks the invariant that `total_weight_approved` and `total_weight_rejected` are drawn from a strictly-partitioned, up-to-date view of "verified accepts" vs "verified rejects" for the current tally — an aggregated-weight-vs-verified-accepts equality. The coordinator that consumes these numbers checks the rejection condition first and unconditionally: [3](#0-2) 
followed by the acceptance check: [4](#0-3) 

Because `total_weight_rejected` retains stale weight from signers who have since switched to `Accepted`, the miner/coordinator can observe a rejection tally that no longer reflects the actual current voting state of the signer set — potentially causing the coordinator to declare `SignersRejected` (abandoning/blacklisting transactions, `stacks-node/src/nakamoto_node/signer_coordinator.rs:521-540`) for a block that in fact now has enough weight, and legitimate signers, currently supporting it.

Trigger path: a single signer (one slot, its own key) sends `BlockResponse::Rejected` for a block (e.g., because its own validation transiently failed, or due to network retry/reordering, or deliberately if malicious) and subsequently sends `BlockResponse::Accepted` for the identical `signer_signature_hash`. Both messages are individually valid and signed only by that one signer — no majority or other signer's key is required to trigger the miscount.

### Impact Explanation
This is a break of the "aggregated-weight vs verified-accepts" equality explicitly called out as in-scope: the coordinator's rejection/acceptance weight tallies no longer represent the true, current per-signer decision set once any signer flips its vote for a given block proposal. Depending on timing, this can cause the coordinator to wrongly treat a block as globally rejected (discarding it and permanently/temporarily banning transactions it contains) even though real signer support for it, by weight, is sufficient — a liveness-affecting miscount stemming from stale bookkeeping in the block-tallying state machine.

### Likelihood Explanation
Reachable by a single signer (its own slot) sending two ordinary protocol messages (`Rejected` then `Accepted`) for the same block hash; no coordination with other signers, no majority weight, and no privileged access is required. Vote flip-flopping can occur naturally (e.g., a signer's local validation state changes between polls) or be deliberately induced by one signer/miner via gossip replay of stored StackerDB chunks.

### Recommendation
Use a single canonical per-slot vote map (e.g., `responded_signers` alone, or a unified `slot_id -> Vote{Accepted|Rejected}` map) to gate weight updates in both the `Accepted` and `Rejected` branches, and when a signer's recorded vote changes, subtract its weight from the previous bucket before adding it to the new one, so `total_weight_approved` and `total_weight_rejected` always reflect the latest, non-overlapping, per-signer decision.

### Proof of Concept
1. Node's `StackerDBListener` requests signatures for block `B` (`insert_block`, `stacks-node/src/nakamoto_node/stackerdb_listener.rs:693-704`), initializing `total_weight_approved = total_weight_rejected = 0`.
2. Signer S (weight `w`) sends `BlockResponse::Rejected(B)`. `responded_signers.insert(S)` returns `true` ⇒ `total_weight_rejected += w` (`stackerdb_listener.rs:515-519`).
3. Signer S later sends `BlockResponse::Accepted(B)` with a valid signature. `gathered_signatures.contains_key(S)` is `false` (never touched by the reject path) ⇒ `total_weight_approved += w` (`stackerdb_listener.rs:443-446`). `total_weight_rejected` is left at `w`, unchanged.
4. Now `total_weight_approved + total_weight_rejected = 2w > total_weight` contribution from S's single weight, and `total_weight_rejected` still reports `w` worth of rejection even though S currently approves. If other signers' honest weight brings `total_weight_rejected` combined with this stale `w` past `total_weight - weight_threshold`, the coordinator's rejection branch (`signer_coordinator.rs:509-519`) fires and the block is treated as rejected, even though the true, current weight in favor of the block (including S) may already meet the approval threshold.
