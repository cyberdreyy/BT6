### Title
V1 `validate_tenure_change_payload` duplicate-tenure guard checks only global acceptance, letting a V1 signer sign two conflicting tenure-start blocks for the same tenure - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`SortitionsView::validate_tenure_change_payload` (v1) rejects a duplicate tenure-start proposal only when `SignerDb::get_last_globally_accepted_block` already returns a block for that tenure, whereas the v2 path (`GlobalStateView::validate_tenure_change_payload`) rejects on `SignerDb::get_last_signed_block`, which also covers the signer's own locally-signed-but-not-yet-globally-accepted block. Because `get_last_globally_accepted_block` ignores a block the signer itself already signed until network-wide acceptance is observed, a V1-configured signer can be induced to sign two different, conflicting tenure-start blocks for the same tenure.

### Finding Description
Both code paths gate the check on `block.get_tenure_change_tx_payload()` for the first block of a tenure: [1](#0-0) 

versus [2](#0-1) 

The v2 comment explicitly documents the intended semantics: "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us." This means v2's `get_last_signed_block` returns a block as soon as *this* signer has applied its own signature to it (state `LocallyAccepted` or `GloballyAccepted`), blocking that signer from ever signing a second, conflicting tenure-start block for the same tenure.

V1's check instead calls `get_last_globally_accepted_block`, which only returns a result once the *whole network* has reached the global-acceptance threshold for that block - a fact the signer cannot know instantaneously and that requires either node-side confirmation or gossip aggregation. Until that threshold is crossed, a V1 signer that has already signed tenure-start block `A` for consensus hash `CH` will still evaluate `get_last_globally_accepted_block(CH)` as `None` when a second, conflicting tenure-start block `B` (same `CH`, different content/signer_signature_hash) is proposed, and - if `B` otherwise passes the parent-tenure and burn-view checks - will sign it too.

Exploit flow (miner-only, one slot, gossip only):
1. Attacker wins a miner slot for sortition `CH`, builds tenure-start block `A`, and proposes it via `check_proposal` -> `validate_tenure_change_payload`. A V1 signer signs it (state `LocallyAccepted`); this does not yet cross network-wide global-acceptance in signerdb.
2. Before global acceptance propagates/records, the attacker crafts a second tenure-start block `B` for the same `CH` (e.g., different transaction set/parent choice satisfying `check_tenure_change_confirms_parent`/`check_parent_tenure_choice`) and proposes it to the same signer.
3. The V1 signer's `validate_tenure_change_payload` queries `get_last_globally_accepted_block(CH)`, finds nothing, and proceeds to sign `B` as well - producing two signatures from the same signer over two different blocks claiming the same tenure slot.

This is an equivocation: the same signer key validly signs two conflicting canonical candidates for the same tenure. No existing guard in the v1 path closes this - `has_signed_block_in_tenure` is used only inside `SortitionState::is_timed_out` (to decide if a miner has timed out), not inside `validate_tenure_change_payload`, so it never blocks this duplicate-sign path. The version selection itself (`SortitionStateVersion::from_protocol_version`, `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) is a per-signer/local-and-negotiated protocol version, not a Stacks-epoch-derived value, so any signer still on protocol version < 2 runs this weaker check regardless of what epoch the chain is in - this includes, but is not limited to, mixed v1/v2 fleets during an upgrade window.

### Impact Explanation
This breaks the "one signature per signer per tenure-start" equivocation guard that the v2 code explicitly restores; if enough weight is spread this way, honest weight can end up split (or, in the worst case, dual-committed) across two competing tenure-start blocks for the same tenure, undermining the canonicity/uniqueness of the signed block for that tenure - a Critical chain-safety issue (signer signing a conflicting block). This is repeatable per tenure/per V1 signer as long as the attacker can win consecutive relevant sortitions and race the global-acceptance timing window.

### Likelihood Explanation
The attacker needs nothing beyond a single miner slot (won with their own BTC) and the ability to gossip two conflicting `BlockProposal`s to the target signer before global acceptance for the first is recorded - exactly the unprivileged capability set assumed. The precondition is simply that the target signer is on signer protocol version < `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (2), which is the normal, expected, and currently supported state for any signer that has not yet completed the v0→v2 rollout (a realistic and long-lived window, not a corner case). It requires no majority signers, no compromised keys, and no auth_token.

### Recommendation
Backport the v2 semantics into the v1 path: change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to check `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, so that any block the signer has already signed (locally or globally accepted) blocks a conflicting duplicate proposal, consistent with the v2 fix and independent of network-wide acceptance timing.

### Proof of Concept
Rust test plan (in `stacks-signer/src/chainstate/tests/v1.rs`, mirroring fixtures already used in `stacks-signer/src/chainstate/tests/v2.rs`):
1. Build a `SignerDb` and insert tenure-start block `A` for consensus hash `CH` with state `LocallyAccepted` (simulate the signer having signed it, but not yet globally accepted - i.e., do not populate any globally-accepted record).
2. Construct competing tenure-start block `B` for the same `CH` (different signer_signature_hash, but passing `check_tenure_change_confirms_parent` / `check_parent_tenure_choice`).
3. Call `SortitionsView::validate_tenure_change_payload` (v1) with `B`; assert it returns `Ok(())` (i.e., NOT `Err(RejectReason::DuplicateBlockFound)`) - demonstrating the equivocation gap.
4. Repeat the same setup against `GlobalStateView::validate_tenure_change_payload` (v2); assert it returns `Err(RejectReason::DuplicateBlockFound)` because `get_last_signed_block` finds `A`.
5. Assert the divergence: identical DB state and identical proposal `B`, but v1 accepts while v2 rejects, proving the version-gated rule set - not epoch - determines the verdict, and that v1's rule permits the equivocation.
