### Title
Instant-withdraw receipts are payable at par without enforcing that the request was funded — unfunded instant claims can spend underlying reserved for funded withdraw receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the saml2-js flaw (assertion *conditions* not enforced for one assertion variant, allowing indefinite replay), `IdleCreditVault.claimInstantWithdrawRequest` pays an instant-withdraw receipt at par without enforcing the condition that the request was actually funded. Normal withdraw claims enforce a condition — `epochNumber > lastWithdrawRequest[_user]` ensures `stopEpoch` ran and `collectWithdrawFunds` pulled the borrower-funded underlying into the strategy before payout. Instant claims enforce no equivalent condition: there is no check that `collectInstantWithdrawFunds` was ever called for the request, only a global `pendingInstantWithdraws` counter that is never consulted on the claim path.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens and mints a user receipt, incrementing `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (IdleCreditVault.sol:356-375). Funding is a separate step: `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and transfers underlying from the CDO (IdleCreditVault.sol:398-403), invoked by `IdleCDOEpochVariant` during epoch processing.

`claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It pays `amount` 1:1 from the strategy's underlying balance without verifying that this request's share of `pendingInstantWithdraws` was collected. `_transferFundedClaim` (IdleCreditVault.sol:897-907) only protects `defaultRecoveryReserve` — it does not protect underlying that was collected via `collectWithdrawFunds` and is reserved for other users' funded (matured) normal withdraw receipts, nor underlying held for other purposes.

Concretely: a user requests an instant withdraw during a running epoch. If the epoch stops via a loss path (`stopEpochWithDuration` / partial `collectWithdrawFunds` at IdleCreditVault.sol:411-430, which explicitly tolerates underfunding by storing `lossRecoveryPriceByEpoch`) and instant receipts remain unfunded (`pendingInstantWithdraws > 0`), the user can still call `IdleCDOEpochVariant.claimInstantWithdrawRequest` — gated only by `allowInstantWithdraw` (IdleCDOEpochVariant.sol:975-979) — and be paid in full out of underlying that was collected to back *matured normal withdraw receipts* of other users. Those normal claimants then find the strategy undercollateralized and their claims revert or pay out late — a one-receipt-one-payout / solvency invariant break.

This mirrors the advisory: the "encrypted" variant path (instant claims) skips the condition enforcement that the normal path applies, allowing value extraction the protocol assumed was impossible.

### Impact Explanation
An unprivileged lender can receive underlying at par for an unfunded instant receipt, directly spending funds reserved for other users' funded withdraw claims. Loss is bounded by the unfunded instant receipt amount and results in insolvency for later legitimate claimants (theft of unclaimed payouts / temporary-to-permanent freezing of their claims until the strategy is refinanced).

### Likelihood Explanation
Requires a stop path that leaves `pendingInstantWithdraws` unfunded while the strategy holds underlying collected for other claims — i.e., a partial-funding/loss stop or a default in which instant funding was not fully collected. Whether `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` always fully collects instant funds before any loss could be realized was not fully verifiable within the indexed context; if instant funding is unconditionally pulled first, this collapses to no bug. The guard ordering in `claimInstantWithdrawRequest` (pay first, no funding check) and the explicit tolerance of underfunding in `collectWithdrawFunds`/`previewLossAdjustedWithdrawFunds` make the gap plausible but dependent on that sequencing.

### Recommendation
In `claimInstantWithdrawRequest`, track funded vs. unfunded instant claims per user/epoch (or decrement `pendingInstantWithdraws` only via `collectInstantWithdrawFunds` and reject claims whose basis exceeds the funded reserve), and apply the same loss-adjusted price used for normal receipts when funding was partial. Alternatively, settle instant claims through the same `lossRecoveryPriceByEpoch` mechanism used by `_claimLossAdjustedWithdrawRequest`.

### Proof of Concept
A Foundry PoC (scaffolded on `test/foundry/IdleCreditVault.t.sol`) would: deposit with two users; run epoch; have user A request a normal withdraw; have user B request an instant withdraw; stop the epoch through the loss path so normal receipts are funded but `pendingInstantWithdraws` remains > 0; call `cdoEpoch.claimInstantWithdrawRequest()` as user B and assert user B received underlying at par while `pendingInstantWithdraws` was still nonzero; then assert user A's `claimWithdrawRequest` reverts on insufficient strategy balance.
