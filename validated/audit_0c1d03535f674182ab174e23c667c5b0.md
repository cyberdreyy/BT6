### Title
Signer weight double-counted across conflicting Accept/Reject responses in the node's `StackerDBListener` block-status tally - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` maintains a per-block `BlockStatus` with `total_weight_approved` and `total_weight_rejected` counters that the coordinator compares against `weight_threshold` to decide whether a block is accepted or rejected [1](#0-0) . The two counters are gated by different, inconsistent keys: the `Accepted` arm gates its weight addition on `block.gathered_signatures.contains_key(&slot_id)`, while the `Rejected` arm gates its weight addition on `block.responded_signers.insert(slot_id)` [2](#0-1) [3](#0-2) . Because a signer that rejects first inserts its `slot_id` into `responded_signers` (not `gathered_signatures`), a subsequent Accept from the same signer for the same block is not blocked by this check and adds the signer's weight to `total_weight_approved` as well — the same signer's weight ends up counted toward both rejection and acceptance for one block.

### Finding Description
The relevant `BlockStatus` struct tracks:
- `responded_signers: HashSet<u32>`
- `gathered_signatures: BTreeMap<u32, MessageSignature>`
- `total_weight_approved: u32`
- `total_weight_rejected: u32` [1](#0-0) 

In the `Accepted` handling branch, the check that gates whether `total_weight_approved` is incremented is:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 

In the `Rejected` handling branch, the equivalent gate is:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [3](#0-2) 

Sequence that triggers the equality break for one signer `S` at `slot_id`:
1. `S` sends `BlockResponse::Rejected` for block `B`. `responded_signers.insert(slot_id)` succeeds → `total_weight_rejected += S.weight`.
2. `S` later sends `BlockResponse::Accepted` for the same block `B` (e.g., after re-evaluating a re-proposed/re-broadcast block, or simply retransmitting a stale StackerDB chunk version). `gathered_signatures.contains_key(&slot_id)` is `false` (S never accepted before) → the accept branch adds `total_weight_approved += S.weight`, and only afterward inserts `slot_id` into both `gathered_signatures` and `responded_signers` (the latter insert is a no-op since it is already present, but that does not gate anything on this branch).

Result: `S`'s weight is now counted in *both* `total_weight_rejected` and `total_weight_approved` for the same `block_sighash`. This breaks the intended equality that each signer's weight should count toward at most one side of the aggregated tally used by the coordinator's threshold decision in `SignerCoordinator` (`block_status.total_weight_rejected` vs `self.total_weight`, and `block_status.total_weight_approved >= self.weight_threshold`) [4](#0-3) .

### Impact Explanation
This directly maps to the "aggregated-weight vs verified-accepts" equality break called out in scope, and specifically to the enumerated impact "a rejection recounted as an accept." A single equivocating (or merely retransmitting/rebroadcasting) signer's weight can inflate `total_weight_approved` beyond what genuinely accepting signers contributed, moving the tally closer to (or over) `weight_threshold` without a corresponding increase in real acceptance weight. In a marginal scenario where legitimate acceptance weight is just below threshold, one signer's stale/duplicate Accept message (counted in addition to its already-tallied Reject) could push `total_weight_approved` over the line, causing the miner to treat the block as signed with a signature set that a threshold of *distinct, currently-agreeing* weight did not actually endorse. This is a Critical-class concern under the given impact list (miscounted response contributing to acceptance of a block that a valid weighted majority did not agree to).

### Likelihood Explanation
Triggering requires only one signer (no majority, no other signer's key) to emit both a Reject and later an Accept for the same `signer_signature_hash` — a scenario reachable through gossip/StackerDB replay, a signer's own re-evaluation logic after a re-proposed block, or a StackerDB chunk resend with a different message. The double counting depends purely on message ordering and per-slot state gating on two different maps (`gathered_signatures` vs `responded_signers`), not on a majority or byzantine key compromise. It is a straightforward implementation asymmetry, easily reachable but requires the specific ordering (reject-then-accept from the same signer, before that block's tally is finalized).

### Recommendation
Gate both the `Accepted` and `Rejected` arms on the same authoritative per-slot state (e.g., use a single `HashMap<u32, BlockResponseKind>` recording whether the signer has already contributed to approve or reject weight for this block, and refuse to add weight to the opposite bucket once a signer has already contributed to one side — or explicitly subtract/adjust when a signer flips their vote instead of only additively tallying). At minimum, the `Accepted` branch should check `responded_signers` (not `gathered_signatures`) before adding to `total_weight_approved`, mirroring the `Rejected` branch, and the code should decide (and document) whether a signer is allowed to flip their vote and, if so, correctly move their weight from one bucket to the other rather than allowing it to reside in both simultaneously.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (`slot_id` = k, weight = w) submits `BlockResponse::Rejected` for `B`. `StackerDBListener` sets `responded_signers = {k}`, `total_weight_rejected = w`. [3](#0-2) 
2. `S` (via re-evaluation, gossip replay, or a stale/duplicate chunk write) subsequently submits `BlockResponse::Accepted` for the same `B`. Since `gathered_signatures` does not yet contain `k`, the accept branch adds `total_weight_approved += w`. [2](#0-1) 
3. Now `block_status.total_weight_rejected = w` and `block_status.total_weight_approved = w` simultaneously for the same signer's weight `w`, inflating both sides of the threshold comparison performed in `SignerCoordinator`. [4](#0-3) 

Note: I was not able to fully trace whether any additional guard elsewhere in `stackerdb_listener.rs` (outside the excerpted ranges) prevents a signer from sending a second, conflicting `BlockResponse` for the same block before this tally is consumed; the codebase index did not surface such a guard in the reviewed sections, so this should be verified against the complete file in a full Devin session if further confirmation is needed.
