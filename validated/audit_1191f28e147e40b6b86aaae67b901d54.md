Based on my investigation, I found a plausible analog: the confidential relay gateway handler's `HandleJSONRPCUserMessage` accepts any user request for `MethodCapabilityExec`/`MethodSecretsGet` and unconditionally fans it out to the DON without any allowlist, authentication, or workflow-ownership check — unlike the sibling Vault gateway handler, which explicitly runs every sensitive method through `requestProcessor.ProcessRequest` → `Authorizer.AuthorizeRequest` before touching secrets.

### Title
Confidential Relay gateway handler forwards unauthenticated user requests to the DON with no allowlist/authorization check - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

### Summary
The Sherlock report's root cause is that `executeModule` executes attacker-fully-controlled parameters on behalf of an arbitrary victim because the function performs no caller/ownership validation before dispatching privileged logic. The closest reachable analog in this codebase is the gateway-side `confidentialrelay` handler, which is a public/internet-facing entry point (reached via `gateway.ProcessRequest` from any HTTP client) that immediately fans out the caller-supplied request to DON nodes with **no authorization check at all**, in contrast to the `vault` handler in the same package family which enforces `AuthorizeRequest`/allowlist checks for every sensitive method.

### Finding Description
`gateway.ProcessRequest` [1](#0-0)  routes any incoming JSON-RPC request from an unauthenticated HTTP client to the resolved handler's `HandleJSONRPCUserMessage`. For the confidential relay handler, this function performs only request-ID validation (non-empty, length limit) and then immediately calls `fanOutToNodes`, without ever invoking an authorizer, allowlist check, or caller-identity/ownership validation: [2](#0-1) 

Compare this to the Vault gateway handler in the same `core/services/gateway/handlers/` tree, which enforces `h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)` — which in turn calls `Authorizer.AuthorizeRequest` (allowlist- or JWT-based) — for every sensitive secrets method before any node dispatch occurs: [3](#0-2) [4](#0-3) 

The allowlist mechanism (`AllowListBasedAuth.AuthorizeRequest`) binds a specific request digest to a specific `workflowOwner`, preventing an attacker from submitting arbitrary requests on behalf of another owner: [5](#0-4) 

The confidential relay handler has no equivalent binding — `req.Params` (arbitrary caller-controlled `workflow_id`, capability parameters, etc., per `MethodCapabilityExec`) is forwarded verbatim to every DON node member: [6](#0-5) 

### Impact Explanation
Because `fanOutToNodes` dispatches on caller-supplied `req.Params` (e.g., `workflow_id`, capability inputs) with no ownership check, any unprivileged client reaching the gateway's confidential-relay endpoint can trigger capability execution or secret retrieval requests scoped to a `workflow_id`/owner they do not control — the same class of "any caller can operate on behalf of any victim" bug as the `executeModule` finding, since the receiving side trusts whatever identifier is embedded in the request body rather than verifying it belongs to the caller. This could enable cross-tenant request impersonation for `MethodCapabilityExec`/`MethodSecretsGet` against confidential-relay-enabled DONs.

### Likelihood Explanation
Likelihood is moderate-to-high in any deployment where the `confidential-relay` gateway handler is enabled (`ConfidentialRelayHandlerType` is a registered gateway handler type: [7](#0-6) ), since the gateway's HTTP-facing `ProcessRequest` requires no session/API-key authentication for JSON-RPC-style requests — this differs from the admin/CLI-facing routes protected by `web/auth` RBAC (`RequiresAdminRole`, `RequiresRunRole`, `AuthenticateExternalInitiator`), which do enforce role/session checks: [8](#0-7) 

### Recommendation
Route `MethodSecretsGet`/`MethodCapabilityExec` through the same authorization pipeline used by the Vault handler (`Authorizer.AuthorizeRequest` bound to `workflowOwner`/allowlist digest, or JWT-based auth) before `newActiveRequest`/`fanOutToNodes` is invoked, and verify that any owner/workflow identifier embedded in the relay request params matches the authorized caller.

### Proof of Concept
I could not construct a concrete end-to-end PoC because the params schema for `MethodCapabilityExec`/`MethodSecretsGet` and downstream node-side enforcement in `core/capabilities/confidentialrelay/handler.go` were only partially retrievable from the index within available iterations — node-side handling might independently re-validate ownership before acting on `MethodSecretsGet`/`MethodCapabilityExec`, which would mitigate this at the enclave layer rather than the gateway layer. This is a genuine gap I could not rule out with certainty; if such node/enclave-side validation exists and is the actual trust boundary (as suggested by the confidentialrelay bundler comment that "the enclave is the sole trust anchor"), then the missing gateway-side authorization may be an intentional design (gateway = dumb relay, enclave = authorization authority) rather than an exploitable bypass. I recommend a Devin session with full repository access to trace the enclave-side authorization logic for `MethodSecretsGet`/`MethodCapabilityExec` before treating this as a confirmed finding.

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {

		return errors.New("request ID cannot be empty")
	}

		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}

// AuthorizeRequest authorizes a request using AllowListBasedAuth.
// It does NOT check if the request method is allowed.
func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}

	if time.Now().UTC().Unix() > int64(allowlistedRequest.ExpiryTimestamp) {
		authorizedRequestStr := string(allowlistedRequest.RequestDigest[:])
		r.lggr.Debugw("AllowListBasedAuth authorization expired", "method", req.Method, "requestID", req.ID, "authorizedRequestStr", authorizedRequestStr, "expiryTimestamp", allowlistedRequest.ExpiryTimestamp)
		return nil, errors.New("request authorization expired")
	}

	digestKey := string(allowlistedRequest.RequestDigest[:])
	r.lggr.Debugw("AllowListBasedAuth authorization succeeded", "method", req.Method, "requestID", req.ID, "authorizedRequestStr", digestKey, "owner", allowlistedRequest.Owner.Hex(), "expiryTimestamp", allowlistedRequest.ExpiryTimestamp)
	return &AuthResult{
		workflowOwner: allowlistedRequest.Owner.Hex(),
		digest:        digestKey,
		expiresAt:     int64(allowlistedRequest.ExpiryTimestamp),
	}, nil
