### Title
Multisig executes below-threshold requests via stale confirmations from deleted members - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member()` in `multisig2/src/lib.rs` only purges the requests that a departing member *authored*; it never scans `confirmations` for requests authored by *other* members that the departing member had already confirmed. Those stale confirmation entries keep counting toward `num_confirmations`, so a request can later be executed with fewer genuinely live, authorized approvals than the configured threshold requires.

### Finding Description
`confirm()` compares the size of the `confirmations` set for a request against `self.num_confirmations` to decide whether to execute: [1](#0-0) 

Membership removal is handled by `delete_member()`, which is only invoked through `execute_request()` for a `DeleteMember` action: [2](#0-1) 

It filters `self.requests` for entries where `r.member == member` (i.e. requests *created by* the departing member) and removes their `requests`/`confirmations` entries, then removes the member from `self.members` and `num_requests_pk`. Crucially, it never iterates `self.confirmations` to strip the departing member's approval from *other* pending requests that the member confirmed but did not author.

`assert_valid_request()` and `confirm()` also never re-validate that every entry inside a request's `confirmations` set still belongs to a current `self.members` entry: [3](#0-2) 

So the invariant the K-of-N scheme is supposed to enforce — `len(confirmations) >= num_confirmations` implies that many *live, currently-trusted* members approved — silently degrades to `len(confirmations, including stale/removed members) >= num_confirmations`. The equality that should hold is:
`count(confirmations that belong to current self.members) == count required to authorize`,
but the code instead checks `count(all recorded confirmations, live or not) >= num_confirmations`.

The same pattern exists in the older, key-based `multisig/src/lib.rs`, where `DeleteKey` only purges requests where `r.signer_pk == pk` and likewise never removes that key's confirmation entries from requests authored by other keys: [4](#0-3) 

### Impact Explanation
This is a Critical-severity finding under the stated policy ("a multisig request executed below threshold"). Once a member is removed (e.g., for misbehavior or key rotation) after having confirmed a pending request they authored by someone else, that stale confirmation remains valid forever. Any remaining member(s) can later add just enough new confirmations to reach `num_confirmations`, executing transfers, key/member changes, or arbitrary function calls with strictly fewer *live* approvals than the multisig's configured security threshold — e.g., a 2-of-3 multisig can be reduced in practice to effectively 1 live approval plus one ghost approval from a removed member, moving funds or granting access keys without the intended quorum.

### Likelihood Explanation
Likelihood is moderate to high in any multisig that rotates membership (a normal operational event — removing a compromised, departing, or malicious signer) while requests are pending. No special privilege is needed to trigger the divergence beyond normal multisig membership; the flaw is purely in the bookkeeping performed during `DeleteMember`/`DeleteKey`, and it will silently persist until noticed, since `confirmations` are stored as plain strings/public keys with no cross-check against the live `members`/access-key set at execution time.

### Recommendation
When removing a member (or key), iterate all pending requests' `confirmations` sets and strip the departing member's entry from every one of them, not just requests they authored, e.g.:
```rust
for (request_id, mut confirmers) in self.confirmations.iter() {
    if confirmers.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confirmers);
    }
}
```
Alternatively (and more robustly), validate at `confirm()`/execution time that every account/key in the request's `confirmations` set is still present in `self.members`, and only count live members toward `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new` with members `[A, B, M]` and `num_confirmations = 2`.
2. `M` calls `add_request_and_confirm` with a `Transfer` request sending funds to `M`'s own account (this request now has 1 confirmation from `M`, itself the author).
3. The remaining members `A` and `B` legitimately confirm and execute a `DeleteMember { member: M }` request (satisfies `members.len() - 1 >= num_confirmations`, i.e. `3-1 >= 2`). `delete_member()` removes `M` from `self.members`, but since the pending Transfer request was authored by `M` itself it would normally get purged too — to construct the exploit, instead have `M` confirm a request *authored by A* (e.g., `A` creates a `Transfer` request to some third-party attacker-controlled account, `M` confirms it as the 1st confirmation, leaving it at 1/2). Then `M` is removed via `DeleteMember` as above; because the pending request was authored by `A`, `delete_member()`'s filter (`r.member == member`) does not touch it, so `M`'s stale confirmation remains.
4. Now only `A` and `B` are live members, `num_confirmations` is still `2`. `B` calls `confirm(request_id)`; `confirmations.len()` becomes `2` (the live `B` plus the stale, no-longer-authorized `M`), meeting `>= num_confirmations`, and `execute_request()` fires the `Transfer` — with only one truly live, current member (`B`) plus author `A`'s implicit initial confirmation, never a genuine second live approval from `M`, who has already been removed from the multisig.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();

            !confirmations.contains(&member.to_string()),

        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
