### Title
Loss-adjusted ("rejected") withdraw receipts from earlier epochs are still paid at par, draining the funded reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`collectWithdrawFunds` applies a haircut (`lossRecoveryPriceByEpoch`) to the *aggregate* `pendingWithdraws` basis when the borrower under-funds a `stopEpochWithDuration` loss. But `_claimLossAdjustedWithdrawRequest` only clears the receipt slice recorded under `lastWithdrawRequest[_user]`'s epoch; any receipt the same user has pending from an *earlier* epoch stays in `withdrawsRequests[_user]` and is then paid at 100% by `_claimFundedWithdrawRequest`. The vault therefore pays out more than it collected, leaving later claimants unable to withdraw (insolvency / theft of other users' claims).

### Finding Description
- `requestWithdraw` supports a user holding receipts across multiple epochs (the comment at `IdleCreditVault.sol:323-324` explicitly documents that a second request makes the user "wait for another epoch to claim both requests"). Each request adds to both the aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][epoch]`.
- On a lossy stop, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` where `pendingBasis` is the *global* `pendingWithdraws` — i.e., the haircut is meant to apply pro-rata to **all** pending receipts, regardless of their request epoch (`IdleCreditVault.sol:411-430`).
- However, `_claimLossAdjustedWithdrawRequest` → `_clearWithdrawClaimForEpoch` only zeroes `withdrawsRequestsByEpoch[_user][lossEpoch]` for the single epoch stored in `lastWithdrawRequest[_user]` and decrements `withdrawsRequests[_user]` by just that epoch's piece (`IdleCreditVault.sol:789-800`, `811-837`).
- `claimWithdrawRequest` then falls through to `_claimFundedWithdrawRequest`, which pays the *remaining* `withdrawsRequests[_user]` (the earlier-epoch receipts) in full via `_transferFundedClaim` (`IdleCreditVault.sol:319-350`).
- The anti-gaming guard in `requestWithdraw` (`IdleCreditVault.sol:261-271`) has the same blind spot — it only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, so it cannot detect or force-claim a loss-adjusted receipt recorded under an earlier epoch.

Broken invariant: after a lossy stop, `sum(payouts) == amount collected`. Here, `sum(payouts) = lossEpoch receipt × price + earlierEpoch receipts × 1.0`, while only `totalBasis × price` was funded. The difference is stolen from the shared funded reserve; the last claimants' transfers revert on insufficient balance.

### Impact Explanation
An attacker (any KYC-passing lender) who holds withdraw receipts spanning multiple request epochs can extract more underlying than the funded amount whenever `stopEpochWithDuration` realizes a loss while their receipts are pending. With a large old receipt and a dust new request, they recover ~100% of the old receipt instead of the haircutted value, directly stealing other users' withdrawal funds and leaving honest claimants permanently underpaid (reserve drained → their `_transferFundedClaim` reverts). Loss scales with the earlier-epoch pending basis.

### Likelihood Explanation
Requires: (a) a lender makes withdraw requests in two different epochs without claiming the first (explicitly supported flow, per in-code docs), and (b) a later epoch ends with a partial repayment via `stopEpochWithDuration`/`collectWithdrawFunds`. Both are normal, non-privileged-attacker-controlled sequencing around honest manager/borrower calls. No existing guard (skim, reserve check, epoch gating) stops it — `_transferFundedClaim`'s reserve check only protects `defaultRecoveryReserve`, not other claimants' funded withdrawals.

### Recommendation
Track the haircut per-user rather than per-"last epoch", or clear *all* of the user's pending receipts when a loss price exists for any of their request epochs. Concretely: in `_claimLossAdjustedWithdrawRequest`, iterate/clear all `withdrawsRequestsByEpoch[_user][*]` slices that were pending in the loss epoch (or maintain a per-user "pending at loss" snapshot at request time), and extend the `requestWithdraw` guard to check every epoch with a non-zero `withdrawsRequestsByEpoch`/`apr0Users` entry, not just `lastWithdrawRequest[_user]`.

### Proof of Concept
Foundry fork PoC (extend `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testLossEpochEarlierReceiptPaidAtPar() external {
    // Setup: deposit as LP, run epoch 1 normally (standard helpers in the test file).

    // Epoch A: LP requests withdraw of amountA (large, e.g. 90% of position).
    cdoEpoch.requestWithdraw(tranchesA, address(AAtranche));

    // Epoch B: epoch ends/startEpoch; LP does NOT claim, requests again (amountB, dust).
    // This is documented-supported: note at IdleCreditVault.sol:323-324.
    _stopEpochAndCheckPrices(1, apr, expected);
    _startEpochAndCheckPrices(2);
    cdoEpoch.requestWithdraw(dustTranches, address(AAtranche));

    // Epoch C stop: borrower under-funds; manager calls stopEpochWithDuration with loss.
    // previewLossAdjustedWithdrawFunds -> pendingToFund < pendingBasis.
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    // borrower repays interest + pendingToFund only
    cdoEpoch.stopEpochWithDuration(interest, 0, duration, lossAmount);
    // => lossRecoveryPriceByEpoch[C] = price < 1e18, pendingWithdraws = 0

    // LP claims: _claimLossAdjustedWithdrawRequest clears only epoch-C (lastWithdrawRequest)
    // slice at `price`; _claimFundedWithdrawRequest then pays withdrawsRequests[LP]
    // remainder (epoch-A amountA) at PAR.
    uint256 balPre = underlying.balanceOf(LP);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(LP) - balPre;

    // Expected by design: (amountA + amountB) * price
    // Actual: amountB * price + amountA  -> strictly greater
    assertGt(paid, (amountA + amountB) * strategy.lossRecoveryPriceByEpoch(epochC) / 1e18);

    // Solvency break: strategy balance < remaining obligations; a second user's
    // claimWithdrawRequest reverts inside _transferFundedClaim / safeTransfer
    // (insufficient funded balance).
}
```
