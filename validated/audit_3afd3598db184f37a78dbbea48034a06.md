### Title
Stale confirmations from removed multisig members allow request execution below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The bug-class hint in the report — "confirmations counted versus live members" — maps directly onto a defect in both multisig implementations in this repository. When a member is removed from the multisig (via `DeleteKey` in `multisig/src/lib.rs` or `DeleteMember` in `multisig2/src/lib.rs`), only the confirmations/requests that member *originated* are cleaned up. Confirmations that removed member previously cast on *other* still-outstanding requests (that they did not originate) are never purged. `confirm()` counts raw entries in the `confirmations` set/map without checking that each entry still corresponds to a live member, so a request can be pushed over `num_confirmations` using a confirmation from an account/key that is no longer a member — i.e., it can execute with fewer live confirmers than the configured threshold requires.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member` only removes requests originated by the deleted member: [1](#0-0) 
It never scans `self.confirmations` to strip entries belonging to the member being deleted from *other* requests. `confirm()` treats the confirmation count purely by set cardinality: [2](#0-1) 
There is no re-validation in `confirm()` (or anywhere else) that every account/key string stored in a request's `confirmations: HashSet<String>` is still present in `self.members`. The same pattern exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` only purges requests whose `signer_pk` equals the deleted key: [3](#0-2) 
and `confirm()` likewise counts raw `HashSet<PublicKey>` cardinality without revalidating live membership: [4](#0-3) 

This breaks the intended custody binding: `confirmations counted == confirmations from live members`. Once a member is removed, their earlier confirmation on any request they did not themselves create remains counted toward the execution threshold indefinitely, as long as that request stays outstanding.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." A transfer, `FunctionCall`, `DeployContract`, or key-management request can be pushed to execution by combining a stale confirmation from a now-removed member with confirmations from fewer than `num_confirmations` currently-live members. This effectively lowers the real security threshold of the multisig without anyone noticing, and can be exploited whenever a member is removed (e.g., for being compromised or malicious) after having confirmed an outstanding request — the removal does not retroactively invalidate that confirmation.

### Likelihood Explanation
Requires: (1) an outstanding, unconfirmed request that a member has partially confirmed, (2) that member later being removed via `DeleteMember`/`DeleteKey` (a routine multisig operation, e.g., key rotation or offboarding), and (3) the original request remaining in the `requests`/`confirmations` maps (no cooldown or expiry purges it automatically; `delete_request` requires 15 minutes but is not automatic). Given that member removal is an expected, non-adversarial multisig operation, and the stale-confirmation entry silently persists, this is realistically triggerable without any special privilege beyond being one of the legitimate multisig members (which is the actor set this contract is designed to constrain).

### Recommendation
On `DeleteMember`/`DeleteKey`, iterate all outstanding requests' `confirmations` sets and remove any entry matching the deleted member/key (not just requests originated by them). Alternatively, in `confirm()`, before counting, filter the stored confirmations set to only members still present in `self.members`, and use that filtered length for the threshold comparison and for persisting back to storage.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 2`.
2. Attacker-controlled or compromised member `B` calls `add_request` to create a malicious `Transfer` request `X` (not confirmed yet by anyone).
3. Member `D` (unaware of intent) calls `confirm(X)` → confirmations for `X` = `{D}` (1 confirmation, below threshold, request stays open).
4. Separately, legitimate governance removes member `D` from the multisig via a `DeleteMember{D}` request that reaches quorum from `A` and `C`. `delete_member` only clears requests where `request.member == D` — request `X` (originated by `B`) is untouched, so `X`'s confirmations set `{D}` survives even though `D` is no longer a member.
5. Attacker `B` (still a member) calls `confirm(X)`. Confirmation count becomes `{D, B}`.len() + comparison => `1 + 1 = 2 >= num_confirmations(2)` → `X` executes.
6. Result: request `X` executed with only one *live* member's confirmation (`B`), because the stale confirmation from removed member `D` was still counted — the threshold of 2 live confirmations was never actually met.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
