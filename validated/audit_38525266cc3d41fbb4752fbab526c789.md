### Title
Cross-Chain Nonce Collision in `isTransferProcessed` Enables Permanent Fund Lock — (File: `bridge/evm/contracts/SuiBridge.sol`)

---

### Summary

The replay-protection mapping `isTransferProcessed` in `SuiBridge.sol` is keyed only by `message.nonce` (`uint64`), not by `(message.chainID, message.nonce)`. Because every supported source chain maintains its own independent nonce counter starting at 0, nonces from different source chains naturally collide over time. The first chain to have a given nonce processed on the destination chain permanently "claims" that slot; any subsequent legitimate transfer from a different source chain carrying the same nonce is irrevocably rejected, locking the deposited funds forever.

---

### Finding Description

**Root-cause mapping to the seed bug.** The UMA bug's root cause was that a commitment was not cryptographically bound to its full context (voter address, round, price identifier). The exact same structural flaw exists here: the nonce used as a deduplication key is not bound to its source-chain context, so a nonce from chain A silently collides with — and permanently blocks — a nonce from chain B.

**Exact code path.**

`SuiBridge.sol` declares the processed-transfer guard as:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [1](#0-0) 

`transferBridgedTokensWithSignatures` checks and sets this mapping using only `message.nonce`:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
...
isTransferProcessed[message.nonce] = true;
``` [2](#0-1) 

The same pattern is repeated verbatim in `SuiBridgeV2.transferBridgedTokensWithSignaturesV2`: [3](#0-2) 

**Why the source chain ID is absent from the key.** The `verifyMessageAndSignatures` modifier in `MessageVerifier.sol` explicitly skips the chain-ID and sequential-nonce checks for `TOKEN_TRANSFER` messages:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID");
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
``` [4](#0-3) 

For token transfers the only chain-ID check is on the *target* chain inside the payload (`tokenTransferPayload.targetChain == config.chainID()`), not on the *source* chain. The source chain ID (`message.chainID`) is validated only by `onlySupportedChain`, which confirms the chain is supported but does not participate in nonce deduplication.

**Nonce counters are per-chain and start at 0.** On the Sui side, each deposit increments `nonces[BridgeUtils.TOKEN_TRANSFER]` from 0. On any other supported EVM source chain, the same counter starts at 0 independently. As both chains accumulate transfers, their nonce spaces overlap completely. The `BridgeUtils.Message` struct carries `chainID` as a field but it is never incorporated into the deduplication key: [5](#0-4) 

---

### Impact Explanation

**Permanent fund lock.** Once `isTransferProcessed[N] = true` is set by a transfer from source chain A, any committee-signed transfer from source chain B carrying nonce N is permanently rejected with `"SuiBridge: Message already processed"`. The flag cannot be unset. The tokens deposited on chain B are locked in the source-chain vault with no redemption path on the destination chain. This matches the "permanent fund lock" impact class.

---

### Likelihood Explanation

**Medium — occurs in normal operation without any adversarial action.** Both Sui and any other supported source chain start their nonce counters at 0 and increment monotonically. After the first transfer on each chain, nonce 0 is shared; after the second, nonce 1 is shared; and so on. No attacker capability is required: the collision is deterministic and grows with bridge usage. Any user who deposits on the "second" chain to reach a given nonce value suffers a permanent loss.

---

### Recommendation

Key `isTransferProcessed` by `(sourceChainID, nonce)`:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// After
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
```

Update all reads and writes accordingly:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
isTransferProcessed[message.chainID][message.nonce] = true;
```

Apply the same fix to `SuiBridgeV2`.

---

### Proof of Concept

1. The bridge is configured to accept transfers from Sui (chainID = 0) and a second supported chain B (chainID = 1).
2. A user on Sui deposits tokens; the Sui bridge emits a `TokensDeposited` event with `nonce = 5`. The committee signs the corresponding `BridgeUtils.Message{chainID: 0, nonce: 5, ...}`.
3. The signed message is submitted to `transferBridgedTokensWithSignatures` on Ethereum. The call succeeds; `isTransferProcessed[5] = true`.
4. Independently, a user on chain B deposits tokens; chain B's counter also reaches 5. The committee signs `BridgeUtils.Message{chainID: 1, nonce: 5, ...}`.
5. The signed message is submitted to `transferBridgedTokensWithSignatures`. The call reverts: `"SuiBridge: Message already processed"` — because `isTransferProcessed[5]` is already `true` from step 3.
6. The chain-B user's tokens are permanently locked. No retry, no alternative path, no admin override exists to clear the flag. [6](#0-5) [7](#0-6)

    function transferBridgedTokensWithSignatures(
        bytes[] memory signatures,
        BridgeUtils.Message memory message
    )
        external
        nonReentrant
        verifyMessageAndSignatures(message, signatures, BridgeUtils.TOKEN_TRANSFER)
        onlySupportedChain(message.chainID)
    {
        // verify that message has not been processed
        require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");

        IBridgeConfig config = committee.config();

        BridgeUtils.TokenTransferPayload memory tokenTransferPayload =
            BridgeUtils.decodeTokenTransferPayload(message.payload);

        // verify target chain ID is this chain ID
        require(
            tokenTransferPayload.targetChain == config.chainID(), "SuiBridge: Invalid target chain"
        );

        // convert amount to ERC20 token decimals
        uint256 erc20AdjustedAmount = BridgeUtils.convertSuiToERC20Decimal(
            IERC20Metadata(config.tokenAddressOf(tokenTransferPayload.tokenID)).decimals(),
            config.tokenSuiDecimalOf(tokenTransferPayload.tokenID),
            tokenTransferPayload.amount
        );

        _transferTokensFromVault(
            message.chainID,
            tokenTransferPayload.tokenID,
            tokenTransferPayload.recipientAddress,
            erc20AdjustedAmount
        );

        // mark message as processed
        isTransferProcessed[message.nonce] = true;

        emit TokensClaimed(
            message.chainID,
            message.nonce,
            config.chainID(),
            tokenTransferPayload.tokenID,
            erc20AdjustedAmount,
            tokenTransferPayload.senderAddress,
            tokenTransferPayload.recipientAddress
        );
    }
```
