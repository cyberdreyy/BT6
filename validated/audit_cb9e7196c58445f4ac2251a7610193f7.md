The premise of this question does not hold. There is no SIP-018 structured-data signature scheme used for `vote-for-aggregate-public-key` in `signers-voting.clar`, and thus no `make_structured_data_domain` call is involved in authenticating aggregate-key votes at all.

### Why the premise is false

`vote-for-aggregate-public-key` is a plain `define-public` Clarity function authenticated the same way any Clarity contract call is authenticated: via `tx-sender`, which is bound to the full signature of the enclosing `StacksTransaction` (covering nonce, chain-id, and all payload fields including `round` and `reward-cycle` as literal function arguments), not via an internal SIP-018 hash/signature tuple. [1](#0-0) 

The signer-index → tx-sender binding is enforced directly in `get-signer-weight`, and `round`/`reward-cycle` are consumed as ordinary uint arguments used to key the `votes`, `tally`, and `round-data` maps — there is no signature field, no domain tuple, and no call to `structured_data_message_hash`/`make_structured_data_domain` anywhere in this function or contract. [2](#0-1) 

This is confirmed by how the Rust side constructs these votes — both the test helper and the burn-op processing path build this as a normal `TransactionPayload::ContractCall`/direct `run_contract_call` with `signer_index`, `aggregate_public_key`, `round`, `reward_cycle` as plain arguments, never as a structured-data hash+signature pair: [3](#0-2) [4](#0-3) 

`make_structured_data_domain` and `structured_data_message_hash` (in `stackslib/src/util_lib/signed_structured_data.rs`) are used elsewhere for genuinely off-chain-signed artifacts — PoX-4/PoX-5 signer-key authorizations, mock-signing (`MockProposal`), and SIP voting in `stacks-signer/src/cli.rs` — none of which apply to aggregate-public-key voting. [5](#0-4) 

Since there is no replayable signature blob at all for this vote (the "signature" is simply the normal Stacks transaction signature over the specific nonce+round+reward-cycle payload), an attacker cannot take a signature produced for round R and reuse it to fabricate a vote for a different round: doing so would require forging a new valid transaction signature for the victim signer's key, which the attacker (holding only their own single signer slot and gossip capability, not the victim's private key) cannot do. Additionally, `update-last-round` and the `votes` map's `{reward-cycle, round, signer}` key independently prevent any double-counting of votes across rounds: [6](#0-5)
