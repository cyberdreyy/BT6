## Title
Unenforced Destination-Chain Fee Parameters Allow Permanent Loss of Protocol/Integrator Fee Revenue — (`File: contracts/BaseEscrowFactory.sol`)

### Summary
The reported NFT bug (`buy_spl::process_buy_legacy_spl`) let an unprivileged caller supply an `optional_royalty_pct` that was used verbatim instead of being cross-checked against the protocol-enforced value for the given `token_standard`. The same root cause — an unprivileged party supplying a fee-like value that is never validated against the canonically-computed value — exists in this repository's `createDstEscrow` flow, where destination-chain protocol/integrator fee amounts and recipients are fully attacker-controlled calldata with no on-chain link back to the fee amounts computed on the source chain.

### Finding Description
On the source chain, `BaseEscrowFactory._postInteraction` computes the canonical `protocolFeeAmount`/`integratorFeeAmount` via `FeeTaker._getFeeAmounts` (derived from the maker-signed order/extension) and only *emits* them inside `DstImmutablesComplement.parameters` in the `SrcEscrowCreated` event: [1](#0-0) 

However, `createDstEscrow` — the function that actually deploys the destination escrow and fixes the fee amounts/recipients that will later be paid out — takes the entire `Immutables` struct, including its `parameters` bytes (protocol fee amount, integrator fee amount, and both fee recipients), as fully attacker-supplied `calldata` with **no verification against the source-side computed values** and **no access restriction (no whitelist/resolver check)**: [2](#0-1) 

The only checks performed are that `msg.value` matches the declared `safetyDeposit` (+ amount for native token) and that the destination cancellation timelock does not exceed `srcCancellationTimestamp`: [3](#0-2) 

These fee amounts are later consumed verbatim at withdrawal time in `EscrowDst._withdraw`, which pays `integratorFeeAmountCd()`/`protocolFeeAmountCd()` to whatever recipients are embedded in `immutables`, and forwards the remainder to the maker: [4](#0-3) 

Because `parameters` is part of the hash used to salt/derive the escrow's deterministic address (`immutables.hashMem()`), nothing prevents any caller from deploying a legitimate, fully-funded destination escrow whose `parameters` field sets `protocolFeeAmount = 0` and `integratorFeeAmount = 0` (or diverts the fee recipients), while still transferring the exact token `amount` and `safetyDeposit` the maker expects. Since removing the fee only *increases* the amount the maker ultimately receives (`amount = immutables.amount - integratorFeeAmount - protocolFeeAmount`), the maker has no incentive or visible reason to reject such an escrow, and nothing on-chain forces the deployer to reproduce the fee values that were canonically computed during `_postInteraction`.

### Impact Explanation
This directly matches the "theft or permanent loss of unclaimed fee-like value" impact category. The protocol fee recipient and integrator fee recipient permanently and irrecoverably lose their entitled fee revenue for any swap whose destination escrow is deployed with zeroed/altered `parameters`, with no on-chain mechanism to detect, reject, or recover the loss. This is a High-severity, unprivileged, live-swap-lifecycle issue reachable purely through the public `createDstEscrow` entry point (no owner/governance/resolver privilege required — the function has no whitelist restriction at all).

### Likelihood Explanation
`createDstEscrow` is a completely public, unauthenticated function; any address (including the resolver who filled the source order, or any other willing funder) can call it with self-chosen `parameters`. No signature, Merkle proof, or cross-chain commitment ties the destination fee fields to the values computed by `FeeTaker._getFeeAmounts` on the source chain. Exploitation requires no special access and no interaction with governance/owner functions — only funding the escrow with the expected token amount and safety deposit, which the party already intends to do anyway.

### Recommendation
Bind the destination escrow's fee parameters cryptographically to the source-side computation, e.g., by having `_postInteraction` commit a hash of the expected `DstImmutablesComplement.parameters` (or the full expected dst `Immutables`) keyed by `orderHash`/`hashlock`, and have `createDstEscrow` require the caller-supplied `dstImmutables.parameters` to match that committed hash (reverting otherwise), instead of trusting caller-supplied fee fields unconditionally.

### Proof of Concept
1. Maker signs a Fusion order; resolver fills it via `fillOrderArgs`, triggering `_postInteraction`, which computes `protocolFeeAmount = X`, `integratorFeeAmount = Y` and emits `SrcEscrowCreated` with these values in `DstImmutablesComplement.parameters`.
2. Instead of replicating `X`/`Y`, the resolver (or any other unprivileged actor) calls `createDstEscrow` with `dstImmutables.parameters = abi.encode(0, 0, protocolFeeRecipient, integratorFeeRecipient)`, while still sending the correct `amount + safetyDeposit` in `msg.value`/token transfer.
3. Maker later calls `withdraw(secret, immutables)` on this deployed escrow (`contracts/EscrowDst.sol:36-43`); since `amount` received is `immutables.amount - 0 - 0`, the maker receives more than expected and has no reason to object.
4. `protocolFeeRecipient`/`integratorFeeRecipient` never receive any portion of the fee that was computed and expected on the source chain — the fee revenue is permanently lost with no on-chain recourse.

    /**
     * @notice See {IEscrowFactory-createDstEscrow}.
     */
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
