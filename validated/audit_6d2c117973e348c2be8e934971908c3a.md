### Title
Instant-withdraw receipts from earlier epochs are absent from `instantWithdrawClaimsByEpoch[epochNumber]` and silently default to zero during default finalization, permanently freezing those users' funds - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the axios bug — where a property absent from the merged config is silently resolved to a polluted/default value — `IdleCreditVault` reads `instantWithdrawClaimsByEpoch[epochNumber]` during default finalization and treats claims that are *absent for the current epoch key* as zero. Instant-withdraw receipts requested in an earlier epoch and only partially funded are invisible to `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, so they receive no recovery basis and no reserve attribution. Their subsequent claim is also blocked by the reserve guard in `_transferFundedClaim`, freezing their prefunded and unfunded balances permanently.

### Finding Description
`instantWithdrawClaimsByEpoch[currentEpoch]` accumulates receipts only under the epoch key active at request time (`contracts/strategies/idle/IdleCreditVault.sol:371-372`). `collectInstantWithdrawFunds` reduces `pendingInstantWithdraws` but never reduces the per-epoch claim mapping or the per-user `instantWithdrawsRequests` (`IdleCreditVault.sol:398-403`), so a partially funded receipt survives into later epochs.

At default finalization, `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch key — when `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`). Likewise `_defaultPrefundedInstantReserve()` computes `instantBasis - pendingInstant` using only the current-epoch basis (`IdleCreditVault.sol:716-723`), so an earlier-epoch claimant's already-collected cash is not counted as prefunded reserve.

On claim, `_claimDefaultedInstantWithdrawRequest` looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:843-844`), which is zero for the earlier-epoch user, so no haircutted recovery is paid. Execution then falls through to the par path in `claimInstantWithdrawRequest` (`IdleCreditVault.sol:387-392`), which calls `_transferFundedClaim`. That guard reverts when `balance - defaultRecoveryReserve < amount` (`IdleCreditVault.sol:900-905`), and because the reserve was finalized without the earlier claimant's basis or prefunded cash, the claim can never succeed once defaulted claimants have drawn the reserve.

### Impact Explanation
A user whose instant-withdraw receipt spans an epoch boundary has their funds permanently frozen: they get no recovery payout (zero basis in the default epoch) and cannot claim at par (reserve guard). Their already-prefunded underlying remains stranded in the strategy, recoverable only by the honest owner via `transferToken`, not by the user. This is permanent freezing of user funds caused by an "absent key defaults to zero" accounting read — the direct analog of reading a missing config property through the prototype chain.

### Likelihood Explanation
Requires a partially funded instant withdraw queue (a normal condition when `getInstantWithdrawFunds` sources less than the full queue) that remains unfunded across one `stopEpoch`/`startEpoch` boundary, followed by a borrower default and `finalizeDefaultRecovery`. All steps are normal protocol operations; no privileged misbehavior is needed.

### Recommendation
Track unfunded instant-withdraw basis globally (or carry forward per-epoch claim basis across epochs) instead of keying default basis on `instantWithdrawClaimsByEpoch[epochNumber]`. In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, include all outstanding instant claims — e.g., iterate or maintain a cumulative `totalInstantClaims` counter decremented on claim/funding — so older-epoch receipts join the recovery basis and their prefunded cash joins `defaultRecoveryReserve`.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
