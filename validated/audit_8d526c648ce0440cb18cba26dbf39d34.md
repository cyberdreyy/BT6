### Title
Race condition in `ldapAuthenticator.SetAuthToken` allows stale API token to remain valid after regeneration/role change - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`SetAuthToken` in `core/sessions/ldapauth/ldap.go` deletes a user's existing `ldap_user_api_tokens` row and inserts a new one to enforce the "one API token per user" invariant, but the DELETE/INSERT statements are executed against `l.ds` (the base datasource) rather than the `tx` handle supplied by `sqlutil.TransactDataSource`, and there is no `SELECT ... FOR UPDATE` row lock on the user's existing token row. Two concurrent `POST /v2/user/token` (`UserController.NewAPIToken`) requests for the same user can interleave their DELETE and INSERT statements, leaving more than one valid token row (old + new) for that user, so a previously issued/superseded token can continue to authenticate via `FindUserByAPIToken`.

### Finding Description
The reachable path is: HTTP `POST /v2/user/token` → `UserController.NewAPIToken` (`core/web/user_controller.go` lines 244-286) → after password re-verification, calls `u.App.AuthenticationProvider().SetAuthToken(ctx, &user, newToken)`, which for the LDAP auth provider dispatches to `ldapAuthenticator.SetAuthToken` (`core/sessions/ldapauth/ldap.go` lines 545-592).

Critically, the closure passed to `TransactDataSource` receives a `tx sqlutil.DataSource` parameter, but every query inside the closure — the existence check, the `DELETE FROM ldap_user_api_tokens`, and the `INSERT INTO ldap_user_api_tokens` — is executed via `l.ds`, not `tx`: [2](#0-1) 

Because `tx` is unused, these statements do not actually run inside the enclosing database transaction and acquire no row-level lock on the user's token row (no `SELECT ... FOR UPDATE`) before deleting/inserting. Two overlapping calls to `SetAuthToken` for the same user (e.g., two rapid `POST /v2/user/token` requests, or one triggered by an admin `UpdateRole`-driven re-issue and one by the user's own regeneration) can therefore interleave: request A's DELETE removes the current row, request B's DELETE finds nothing to remove (or removes A's not-yet-inserted new row depending on timing), and both A's and B's INSERT can then succeed independently, since each statement executes as its own autocommitted unit of work against `l.ds`. The result can be two (or more) live rows in `ldap_user_api_tokens` for the same `user_email`, one of which carries a stale/superseded `token_key`/role that should have been invalidated.

`FindUserByAPIToken` (`core/sessions/ldapauth/ldap.go` lines 205-236) has no notion of "only most recent token is valid" — it simply looks up whichever row matches the presented `token_key` and returns cached role/email, so a stale token surviving the race authenticates successfully with its (now superseded) role until its own TTL expires.

No auth middleware, presenter, or additional validation catches this: `TestPassword` only gates that the *caller* knows the current password, it does not serialize concurrent token mutations for the same user.

### Impact Explanation
Impact is temporary continued API-token authentication using a token that should have been invalidated on regeneration/role change (a `sessions.AuthenticationProvider` invariant violation: "user can have only one API token at a time"). This maps to Chainlink's "authentication bypass / stale credential reuse" bounty class — an attacker or a compromised low-privileged token holder can retain functioning API access with a stale role for longer than intended when a legitimate regeneration/role-change race occurs, undermining the security assumption that issuing a new token immediately revokes the old one.

### Likelihood Explanation
Requires two `SetAuthToken` invocations for the same user to overlap in time — achievable by an authenticated low-privileged user (holder of the current password, needed only for `TestPassword`) firing two near-simultaneous `POST /v2/user/token` requests, or by a role-change/regeneration racing with an in-flight token creation by the same or another party with access to the account. Since the requester must already know the account password to call `NewAPIToken`, exploitation is limited to legitimate-but-untrusted low-privileged accounts (or attackers with a leaked password/session) attempting to preserve a token across a role downgrade; it's reproducible deterministically in an integration test by issuing overlapping goroutine calls.

### Recommendation
Use the transaction handle `tx` for all statements inside the `TransactDataSource` closure (not `l.ds`), and take a row-level lock on the user's existing token row (e.g., `SELECT ... FROM ldap_user_api_tokens WHERE user_email = $1 FOR UPDATE`) before the DELETE/INSERT, or replace DELETE+INSERT with an atomic `UPDATE ... WHERE user_email = $1` (with `INSERT ... ON CONFLICT (user_email) DO UPDATE`), backed by a unique constraint on `user_email` in `ldap_user_api_tokens`, mirroring the atomic single-`UPDATE` approach used in `localauth/orm.go`'s `SetAuthToken`.

### Proof of Concept
Go integration test plan (in `core/sessions/ldapauth`):
1. Set up a real Postgres-backed `l.ds` (as existing `ldap_test.go` does) and an LDAP-enabled user with `UserApiTokenEnabled()` true.
2. Launch two goroutines simultaneously calling `l.SetAuthToken(ctx, &user, tokenA)` and `l.SetAuthToken(ctx, &user, tokenB)` with a small synchronization barrier (e.g., a shared start channel) to maximize interleaving; repeat many iterations under `-race`.
3. After both goroutines return without error, query `SELECT count(*) FROM ldap_user_api_tokens WHERE user_email = $1` and assert it is `1` — under the current implementation, occasional runs will show `2` rows.
4. Call `l.FindUserByAPIToken(ctx, tokenA.AccessKey)` and `l.FindUserByAPIToken(ctx, tokenB.AccessKey)` — assert that only the last-issued token authenticates; under the race, both may succeed in some runs, proving the "one token at a time" invariant is violated.
