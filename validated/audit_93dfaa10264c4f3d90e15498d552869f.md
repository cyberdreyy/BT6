### Title
Cross-user response hijacking via `MessageId` collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`handler.HandleLegacyUserMessage` stores each pending user request in `h.savedCallbacks` keyed **only** by the attacker-controlled `msg.Body.MessageId`, with no binding to the sender/tenant identity: [1](#0-0) 

`MessageId` is a plain string chosen entirely by the requesting client and is only constrained by length/format in `Message.Validate` (non-empty, ≤128 bytes, no trailing null byte) — it is **not** required to be unique, unpredictable, or bound to the signer: [2](#0-1) 

Because the assignment `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` unconditionally overwrites any existing entry (no "key already exists" check), a second `HandleLegacyUserMessage` call with the same `MessageId` — submitted by a completely different, differently-signed sender — silently replaces the first user's saved `Callback`.

When a DON node later replies for the original (victim) request, `handleWebAPITriggerMessage` looks the response up purely by `msg.Body.MessageId`: [3](#0-2) 

There is no cross-check that the responding message's method/sender/DonId corresponds to the same original submitter that registered the callback for that ID — `HandleNodeMessage` only checks `msg.Body.Sender != nodeAddr` (i.e., that the reply legitimately comes from a DON node), not that the *callback owner* matches the original requester: [4](#0-3) 

Exploit flow:
1. Victim submits a signed `web_api_trigger` legacy message with `MessageId = X`; gateway stores `savedCallbacks[X] = victimCallback` and forwards the request to all DON members.
2. Before the DON nodes respond, attacker submits their own signed legacy message (different signature/sender, arbitrary payload) also using `MessageId = X`. This overwrites `savedCallbacks[X]` with `attackerCallback`.
3. When a DON node responds for the victim's original trigger with `MessageId = X`, `handleWebAPITriggerMessage` looks up `savedCallbacks[X]`, finds the attacker's callback, deletes the entry, and delivers the victim's trigger response to the attacker instead of the victim.

Since `MessageId` is fully attacker-chosen (not a server-issued nonce), no cryptographic "collision" is needed — an attacker only needs to guess/observe/predict the ID a victim is using (e.g., low-entropy client-generated IDs, retried IDs, or ids that are otherwise observable/guessable) and race their own submission before the DON node responds.

### Impact Explanation
This breaks the isolation invariant between concurrent requesters of the gateway's legacy Web API trigger path: an unprivileged external caller can redirect another user's/workflow's trigger response to themselves, causing cross-user response disclosure (information disclosure of trigger execution results) and denial-of-service for the victim (whose request will now never receive a response and will time out). This matches Chainlink's "cross-user response confusion" / information-disclosure bounty class.

### Likelihood Explanation
Exploitability requires only: (1) attacker capability to submit arbitrary signed `HandleLegacyUserMessage` requests to the gateway (any external initiator/API caller — no special privilege), and (2) knowledge or prediction of a `MessageId` value in-flight for another party, plus winning a small race window between the victim's request being forwarded and the DON's response arriving. Because `MessageId` values are entirely client-supplied and unauthenticated relative to other tenants, this is feasible whenever clients use predictable, short, or reused IDs, and is trivially repeatable (attacker can flood many guesses/IDs to increase odds within the race window).

### Recommendation
Bind saved callbacks to a composite key that includes the message sender (`msg.Body.Sender`, verified via signature in `Validate()`) in addition to `MessageId`, e.g. `key = sender + ":" + MessageId`. Additionally, guard the insertion in `HandleLegacyUserMessage` to reject/replace only same-sender re-registrations, and validate on lookup in `handleWebAPITriggerMessage` that the responding node's data corresponds to a request originated by the same sender that registered the callback, rather than trusting `MessageId` alone as a global namespace.

### Proof of Concept
Go test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct handler with a mocked `handlers.DON`.
2. Sign message A (`MessageId = "X"`) with private key #1 (victim), call `HandleLegacyUserMessage`, capture `callbackA`.
3. Sign message B (`MessageId = "X"`) with a different private key #2 (attacker), call `HandleLegacyUserMessage`, capture `callbackB`.
4. Assert `h.savedCallbacks["X"].Callback == callbackB` (overwritten), demonstrating the map does not preserve/reject the first entry despite different `Sender`.
5. Simulate node response for `MessageId = "X"` (as if answering victim's original request) via `HandleNodeMessage`; assert that `callbackB.Wait()` receives the response (attacker gets victim's data) while `callbackA.Wait()` times out/never resolves — proving cross-wiring.
6. Expected (fixed) behavior: registration keyed by `(sender, MessageId)` should keep both callbacks independent, and each callback should only receive the response tied to its own original sender/request.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
