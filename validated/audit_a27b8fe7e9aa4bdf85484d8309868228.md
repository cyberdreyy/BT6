### Title
`List` decodes base64 with an embedded newline, letting `len(line) >= NonceSize()` while `len(msg) < NonceSize()`, causing an index-out-of-range panic on `msg[:s.c.NonceSize()]` - (File: commands/helpers/internal/store/store.go)

### Summary
`Store.List` validates record length by comparing the base64-encoded, newline-terminated `line` length to `s.c.NonceSize()` instead of the decoded `msg` length, at `commands/helpers/internal/store/store.go` lines 93-102. Because Go's `encoding/base64.StdEncoding.DecodeString` silently skips embedded `\r`/`\n` characters during decoding, the trailing `\n` that `bufio.ReadString('\n')` leaves attached to `line` inflates the length check's input without inflating the decoded payload, creating a gap where `len(line) >= NonceSize()` but `len(msg) < NonceSize()`.

### Finding Description
`List()` reads each record with `buf.ReadString('\n')`, which returns `line` including the trailing `\n` [1](#0-0) . It then decodes `line` (still containing the `\n`) into `msg`, and separately checks `len(line) < s.c.NonceSize()` before slicing `msg[:s.c.NonceSize()]` [2](#0-1) .

`NonceSize()` for `chacha20poly1305.NewX` is 24. Go's base64 decoder ignores `\r` and `\n` bytes rather than treating them as invalid input, so decoding `<24-char-base64><\n>` yields the same `msg` as decoding the 24 chars alone. For encoded (no-newline) lengths of 24 (which correspond to decoded payload lengths of 16, 17, or 18 bytes — all `ceil(n/3)*4 == 24`), `len(line)` becomes `24 + 1 = 25`, which is `>= 24` and passes the check, while `len(msg)` is only 16–18 bytes — less than 24. The subsequent `msg[:s.c.NonceSize()]` then slices past the end of `msg`, causing a runtime panic (index out of range).

The attacker-controlled input is the `phrase` argument to `Add`, which is written by `addmask.New`/the masking machinery when a job variable/mask value is registered; if a short phrase (or a corrupted/truncated store record of the right length) is ever persisted, the next `List()` call panics. This path is reachable inside `proxy-exec` (`commands/helpers/proxy_exec.go`), which is the trampoline wrapping the job's stdout/stderr for masking [3](#0-2) . A panic here crashes the helper process handling `cmd.Stdout`/`cmd.Stderr`, i.e., mid-command during the job.

None of the existing checks catch this: the length check operates on the wrong variable (`line` instead of `msg`), and there is no validation that `len(msg) >= NonceSize()` before slicing.

### Impact Explanation
A crash of the `proxy-exec` masking trampoline mid-job breaks the pipe wrapping the job's stdout/stderr, which can interrupt the shell script and leave the job’s output path in an unmasked/undefined state instead of failing closed. This matches the scoped impact: masking must fail closed, not crash open, and the failure mode here is a crash (panic), not a controlled error return — which risks the exact "unmasked leakage" scenario described in the invariant, since a panic aborts en route without guaranteeing that unwritten trace remains buffered/blocked.

### Likelihood Explanation
The precondition (a short phrase, e.g., an empty string or few-byte masked value) is plausible: any code path that calls `store.Add` with a phrase whose decoded-length falls in {16,17,18} bytes (which base64-encodes to exactly 24 chars) triggers it once `List()` re-reads the store. This is deterministic and repeatable — not a race or timing issue — and is fully reachable via normal masking value registration (no admin privileges, no filesystem corruption required, just a specific-length secret value).

### Recommendation
Fix the check to validate the **decoded** message length, not the encoded line length:
```go
msg, err := base64.StdEncoding.DecodeString(strings.TrimRight(line, "\n"))
if err != nil {
    return results, fmt.Errorf("decoding msg: %w", err)
}
if len(msg) < s.c.NonceSize() {
    return results, fmt.Errorf("encrypted message length too small")
}
```
This ensures the length check and the slice both operate on `msg`, eliminating the newline-skipping discrepancy, and returns a graceful error instead of panicking.

### Proof of Concept
Go unit test in `commands/helpers/internal/store/store_test.go`:
```go
func TestList_ShortDecodedMessageDoesNotPanic(t *testing.T) {
    dir := t.TempDir()
    db, err := Open(dir)
    require.NoError(t, err)

    // Craft a phrase whose ciphertext (nonce+ciphertext) decodes to exactly
    // 16-18 bytes, which base64-encodes to a 24-char line (>= NonceSize()),
    // but is itself shorter than NonceSize() once decoded.
    // Simplest reproduction: directly append a corrupted record with a
    // 24-char base64 payload + newline representing < 24 decoded bytes.
    require.NoError(t, db.f.Sync())
    // Write a record whose base64 (24 chars, no padding needed) decodes to 18 bytes.
    raw := make([]byte, 18)
    line := base64.StdEncoding.EncodeToString(raw) + "\n"
    _, err = db.f.WriteString(line)
    require.NoError(t, err)

    require.NotPanics(t, func() {
        _, _ = db.List()
    })
}
```
Expected assertion: `List()` must return an error (e.g., "encrypted message length too small") instead of panicking with "slice bounds out of range". A fuzz test iterating decoded lengths 0–31 bytes should assert the same graceful-error property for all lengths.
