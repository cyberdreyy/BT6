### Title
External ERC4626 liquidity drain permanently blocks `stopEpoch` and the borrower-default path in programmable-borrower mode - (File: `contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
The external report describes a flow (`buyNFT`) that assumes exclusive control over a shared resource (the NFT id range) and breaks when an outside minter occupies it first. The analog in idle-tranches is `ProgrammableBorrower.onStopEpoch`: it assumes the external ERC4626 vault will always honor `vault.withdraw(shortfall, ...)`. Any unprivileged user of that shared vault can drain its liquidity (withdraw or borrow the underlying, e.g. via MetaMorpho market borrowers), making `vault.withdraw` revert. The revert bubbles out of `_stopEpoch` uncaught, so the epoch cannot be stopped — and, critically, cannot be defaulted either — freezing all LP and pending-receipt funds for as long as the attacker keeps the vault illiquid.

### Finding Description
In programmable-borrower mode, `IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower(...).onStopEpoch(...)` before pulling funds [1](#0-0) . Inside `onStopEpoch`, when on-hand cash is insufficient the contract checks `shortfall > _currentVaultAssets()` (a solvency check only) and then calls `vault.withdraw(shortfall, ...)` inside a `try/catch` that reverts with `StopEpochVaultLiquidityUnavailable` on failure [2](#0-1) .

Two properties make this exploitable:

1. `convertToAssets` counts the position as fully covered even when the vault has zero redeemable liquidity — share price does not reflect currently withdrawable cash. So `shortfall <= _currentVaultAssets()` is satisfied, the `withdraw` is attempted, and it reverts on an ERC20 underflow inside the vault.
2. The revert propagates out of `_stopEpoch` (the comment "Hook reverts bubble so transient ERC4626 liquidity failures can be retried" confirms this is intentional [3](#0-2) ). The only default paths are `onStopEpoch` returning `false` (only on the close-pool borrower-debt check [4](#0-3) ) or the `getFundsFromBorrower` `transferFrom` failing [5](#0-4) . Neither is reached while the hook reverts, so the honest manager cannot even declare a default.

An unprivileged attacker (any ERC4626 vault user / Morpho market borrower, explicitly in scope) withdraws or borrows the vault's liquid underlying just before `stopEpoch` is called, and repeats this whenever liquidity returns (e.g., keep a large borrow position open on the underlying Morpho market). Each `stopEpoch` attempt reverts, `isEpochRunning` stays true, and `requestWithdraw`/claims remain frozen. Deposits are already blocked during a running epoch, and `depositDuringEpoch` reverts when `isProgrammableBorrower` is set [6](#0-5) , so no guard unlocks the pool.

### Impact Explanation
Temporary freezing of all pool funds with no recovery path while the condition holds: withdraw receipts cannot be funded, the epoch cannot be closed, and — uniquely — the default/finalization machinery (`_handleBorrowerDefault` → `finalizeDefault`/`DefaultDistributor`) cannot be triggered because the revert happens before `getFundsFromBorrower` is attempted. On a real MetaMorpho vault, an attacker with sufficient collateral can keep utilization near 100% on the relevant market indefinitely, so "temporary" can extend for the duration of the attacker's borrow, and protocol recovery depends entirely on third-party liquidity returning.

### Likelihood Explanation
Requires a programmable-borrower deployment (IdleCDOEpochVariant with `isProgrammableBorrower == true`) whose configured ERC4626 vault shares liquidity with other users — true by design, since the vault is a public yield venue. The attack cost is the cost of borrowing/withdrawing the vault's liquid assets, which for a MetaMorpho-style vault is routine market activity that can occur even unintentionally (organic utilization spikes also trigger the freeze; the attacker merely sustains it). No privileged role is needed.

### Recommendation
Treat vault liquidity unavailability as a distinct, non-fatal outcome in `onStopEpoch` instead of reverting: check `vault.maxWithdraw(address(this))` (or wrap `withdraw` in a `try` that returns a status) and either (a) withdraw what is available and let the shortfall hit the `transferFrom` → `_handleBorrowerDefault` path, or (b) return `false` so the CDO enters the default flow. Alternatively, add a manager escape that forces default after N failed stop attempts, so a sustained external liquidity drain cannot hold the epoch state machine hostage.

### Proof of Concept
Foundry fork sketch against the programmable-borrower deployment used in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`:

```solidity
function testStopEpochBlockedByVaultLiquidityDrain() external {
    uint256 amount = 10_000 * oneScale;
    idleCDO.depositAA(amount);            // LP deposits, buffer phase
    _startEpochAndCheckPrices(0);         // onStartEpoch -> _depositToVault(idle cash)

    // Attacker: any EOA withdraws/borrows all liquid underlying from the shared ERC4626 vault
    // (e.g., borrow on the MetaMorpho market so vault.totalAssets() liquid == ~0)
    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    morphoBorrow(attacker, morphoMarketId, vaultIdleLiquidity); // drain liquidity

    // Manager attempts to stop the epoch after epochEndDate
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Invariants: epoch still running, no default declared, funds stuck
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    // withdraw receipts remain unclaimable; retrying stopEpoch reverts identically
    // while the attacker keeps the vault drained
}
```

Key assertion: `stopEpoch` reverts rather than falling through to `_handleBorrowerDefault`, even though `ProgrammableBorrower`'s share balance still prices as fully covering the shortfall via `convertToAssets` [7](#0-6) . The freeze persists as long as the attacker maintains the drained-liquidity condition.

Caveat: the exact drain mechanism depends on the configured vault (withdraw vs. Morpho borrow); the PoC assumes a vault whose `withdraw` reverts on insufficient liquid assets, matching `MockStopEpochLiquidityVault.setWithdrawLimit` behavior already exercised in tests [8](#0-7) .
