### Title
Builder withdrawals mint Gwei on the execution layer beyond the builder's actual balance decrease - (File: specs/gloas/beacon-chain.md)

### Summary
In Gloas (EIP-7732), `apply_withdrawals` caps the *consensus-layer* deduction from a builder's balance at `min(withdrawal.amount, builder_balance)`, but the `Withdrawal.amount` field that is embedded in `state.payload_expected_withdrawals` (and ultimately in the `ExecutionPayload.withdrawals` list credited by the execution layer to `withdrawal.address`) is never reduced to match. The EL pays out the full requested amount while the CL only debits what the builder actually had, so any shortfall is minted as Gwei on the EL side with no corresponding CL-side origin — paid to the builder's/fee recipient's address, a non-owner relative to that excess value.

### Finding Description
`apply_withdrawals` (specs/gloas/beacon-chain.md) is:

```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
``` [1](#0-0) 

The `min(withdrawal.amount, builder_balance)` clamp only affects the internal state bookkeeping (`state.builders[builder_index].balance`). It does not clamp `withdrawal.amount` itself. That same `withdrawal.amount` was already placed, unclamped, into `state.payload_expected_withdrawals` when the pending withdrawal was converted to a `Withdrawal` object (`(in builder_pending_withdrawals) .amount`: "Requested amount. Actual = `min(amount, builder.balance)`" — i.e. the spec's own documentation acknowledges "requested" vs. "actual" diverge) [2](#0-1) . `state.payload_expected_withdrawals` is precisely the withdrawals list that the block's execution payload is required to match and that the execution layer applies as literal ETH credits to `withdrawal.address` [3](#0-2) .

This is confirmed directly by spec tests. In `test_builder_withdrawal_insufficient_balance`, a builder has only 1 ETH but a pending withdrawal requests 5 ETH:
```python
builder_index = 0
withdrawal_amount = spec.Gwei(5_000_000_000)
available_balance = spec.Gwei(1_000_000_000)
...
assert_process_withdrawals(
    spec, state, pre_state,
    withdrawal_count=1,
    builder_balances={builder_index: 0},
    builder_pending_delta=-1,
    withdrawal_index_delta=1,
    withdrawal_amounts_builders={builder_index: withdrawal_amount},
)
``` [4](#0-3) 

`builders[0].balance` goes from 1 ETH to 0 (only 1 ETH was actually decremented on the CL), yet the emitted `Withdrawal.amount` — the value the execution layer actually credits — is asserted to equal the full requested `withdrawal_amount` (5 ETH), not the 1 ETH that was actually deducted. The same pattern is exercised again with tighter, "realistic" numbers in `test_builder_withdrawal_insufficient_balance_realistic_bounds` [5](#0-4) , and again in `test_all_builder_withdrawals_zero_balance`, where builders with **zero balance** still produce withdrawals with the full requested (non-zero) amount, "capped to 0" only on the CL side while the withdrawal itself is "still processed" [6](#0-5) .

This is the direct analog of the Yield `buyFYToken`/`buyBase` bug: the contract validated a bounded/actual amount (`min(...)`) for its internal accounting but paid out (or failed to reconcile) a different, uncapped amount to the counterpart — leaving a mismatch that is never reimbursed or netted out. Here, the spec similarly computes a legitimately-bounded "actual" balance change (`min(withdrawal.amount, builder_balance)`) for CL state, but lets the unbounded "requested" amount flow through to the artifact (`Withdrawal.amount` in `payload_expected_withdrawals`) that the execution layer treats as an authoritative instruction to credit real ETH to an address.

### Impact Explanation
This breaks the fundamental equality that Gwei can only move by explicit issuance/burn rules — it must not be created from nothing and paid to an address that has no claim to it. If a builder's CL-tracked balance is insufficient to cover a pending/sweep withdrawal (whether due to a race with a concurrent slashing/exit, a modeling bug, or simply being emptied by a prior withdrawal in the same block), the execution layer will still credit the *full, uncapped* `withdrawal.amount` in ETH to `fee_recipient`/`builder.execution_address`. This manufactures ETH out of thin air on the EL that has no origin in any account's CL-tracked balance decrease — a critical, spec-level Gwei-creation bug (impact category: "Gwei created ... or paid to a non-owner").

### Likelihood Explanation
This is not a contrived edge case: the scenario (builder balance insufficient to cover a previously-recorded pending withdrawal amount) is exercised by three separate spec tests as an accepted, "successful" code path rather than being rejected by an assertion. It can arise naturally whenever a builder's balance is reduced (e.g., another withdrawal processed earlier in the same sweep, or the balance having been reduced between the time the `BuilderPendingWithdrawal`/`BuilderPendingPayment` was queued and when it is finally processed) such that `builder.balance < withdrawal.amount` at settlement time — a state the spec explicitly anticipates and tests for, rather than one requiring an adversarial coalition.

### Recommendation
`get_builder_withdrawals`/the withdrawal-construction helpers and `apply_withdrawals` must use the same clamped value everywhere: either (a) clamp `Withdrawal.amount` itself to `min(requested_amount, builder.balance)` at the point the `Withdrawal` object is constructed and placed into `payload_expected_withdrawals`, so the EL only ever credits what the CL actually debited, or (b) if the discrepancy is a deliberate design ("builder still owes fee_recipient the shortfall from elsewhere"), explicitly route the shortfall through an accounted mechanism (e.g., re-queue the remainder as a new pending withdrawal against future builder balance) rather than silently letting the EL pay an amount the CL never backed.

### Proof of Concept
Using the existing spec test as the PoC (already present in the repo, and passing under current spec semantics):

```python
builder_index = 0
withdrawal_amount = spec.Gwei(5_000_000_000)   # 5 ETH requested
available_balance = spec.Gwei(1_000_000_000)   # builder only has 1 ETH

prepare_process_withdrawals(
    spec, state,
    builder_indices=[builder_index],
    builder_withdrawal_amounts={builder_index: withdrawal_amount},
    builder_balances={builder_index: available_balance},
)

yield from run_gloas_withdrawals_processing(spec, state)

assert_process_withdrawals(
    spec, state, pre_state,
    withdrawal_count=1,
    builder_balances={builder_index: 0},          # only 1 ETH actually debited
    withdrawal_amounts_builders={builder_index: withdrawal_amount},  # but EL is told to pay 5 ETH
)
``` [4](#0-3) 

The resulting `state.payload_expected_withdrawals` entry has `.amount == 5 ETH`, which is exactly what the execution layer will add to the recipient's account balance, while the consensus-layer builder balance only ever decreased by 1 ETH — a 4 ETH gap created and paid out with no matching debit anywhere in the system.

**Uncertainty note:** I was unable to directly view the body of `get_builder_withdrawals` (the function that converts `BuilderPendingWithdrawal` entries into `Withdrawal` objects) in this session due to the final tool-call cutoff, so the exact line constructing `Withdrawal.amount` from the pending withdrawal's `amount` field is inferred from the spec's own documentation table and directly confirmed by the passing test assertions cited above, rather than from reading that helper's source directly.

@with_gloas_and_later
@spec_state_test
def test_all_builder_withdrawals_zero_balance(spec, state):
    """
    Builders with zero balance - withdrawals still processed but with zero deduction.

    Input State Configured:
        - state.builders[0,1]: Builders exist with zero balance
        - builder_pending_withdrawals: 2 entries requesting MIN_ACTIVATION_BALANCE each
        - validators[0].withdrawable_epoch: <= current_epoch (sweep eligible)

    Note: regular_index=0 intentionally overlaps with builder_index=0 to demonstrate
    that builder indices and validator indices are separate namespaces.

    Output State Verified:
        - payload_expected_withdrawals: Contains 3 withdrawals (2 builder + 1 sweep)
        - Builder withdrawals processed (deduction capped to 0)
        - builders[0,1].balance: 0 (unchanged)
        - balances[0]: 0 (full withdrawal processed)
        - Note: Builder withdrawals always processed, amount capped to available balance
    """

    builder_indices = [0, 1]
    withdrawal_amount = spec.MIN_ACTIVATION_BALANCE
    regular_index = (
        0  # Same numeric index as builder 0, but different entity (validator vs builder)
    )

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=builder_indices,
        builder_withdrawal_amounts=dict.fromkeys(builder_indices, withdrawal_amount),
        builder_balances=dict.fromkeys(builder_indices, 0),
        full_withdrawal_indices=[regular_index],
    )

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

    builder_validator_indices = [
        spec.convert_builder_index_to_validator_index(i) for i in builder_indices
    ]

    assert_process_withdrawals(
        spec,
        state,
        pre_state,
        withdrawal_count=3,
        withdrawal_order=builder_validator_indices + [regular_index],
        balances={regular_index: 0},
        builder_balances={0: 0, 1: 0},
        builder_pending_delta=-2,
        withdrawal_index_delta=3,
    )
