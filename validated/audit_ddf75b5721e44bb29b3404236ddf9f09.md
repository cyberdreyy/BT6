### Title
Unbounded decompression during tar+zstd extraction enables disk/inode exhaustion via attacker-controlled cache/artifact archives - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`extractor.Extract` in `tarzstd_extractor.go` decompresses a zstd stream and writes every tar entry to disk with no cap on total decompressed bytes or entry count, only checking `ctx.Err()` between entries. An attacker who controls a cache or artifact archive fetched via `cache-extractor`/`artifacts-downloader` can craft a small, highly-compressed `.tar.zst` file that expands to a very large tar stream, exhausting disk space and/or inodes on the runner/helper host.

### Finding Description
`Extract` opens the zstd reader with only `zstd.WithDecoderLowmem(true)`, which reduces decoder memory usage but does not limit output size [1](#0-0) . The loop then calls `tr.Next()` repeatedly, and for every regular file calls `os.Create` and `io.Copy(f, tr)` with no size or count accounting, only checking `ctx.Err()` per iteration (which does not detect resource exhaustion, only cancellation) [2](#0-1) . The path-traversal check (`filepath.Abs`/`HasPrefix`) only guards against escaping the extraction directory, not against volume/quantity of data [3](#0-2) . Both `CacheExtractorCommand.Execute` and `ArtifactsDownloaderCommand.Execute` call `extractor.Extract(context.Background())` directly on attacker/pipeline-controlled downloaded content with no pre-extraction size/entry budget enforced [4](#0-3) [5](#0-4) . Existing size limits in the codebase (`MaxUploadedArchiveSize`) only bound the *compressed upload* size, not the decompressed extraction output, so they do not mitigate this path [6](#0-5) .

### Impact Explanation
On shared executors (e.g., shell, or any executor where cache/build directories reside on a host-shared filesystem/volume), a single job can consume all available disk space or inodes while extracting a small (KB-sized) crafted cache/artifact archive that decompresses to a much larger size, since zstd bomb ratios can be very high. This can starve co-located jobs of disk space and cause job failures for unrelated tenants sharing the same host/volume, persisting after the malicious job is cancelled (already-written files remain until cleanup, and disk exhaustion affects other running jobs immediately).

### Likelihood Explanation
This requires only that the attacker (a normal pipeline author) control the contents of a project cache key/artifact that will later be restored/downloaded by the runner using `tarzstd` compression — enabled via `CACHE_COMPRESSION_FORMAT: tarzstd` job variable — which is straightforward for any user who can push cache. No special privileges are needed, and the attack is fully repeatable each time the job or a dependent job runs on a shared executor host.

### Recommendation
Enforce a maximum decompressed byte budget and/or maximum file-count limit while iterating tar entries in `Extract` (e.g., wrap the per-file `io.Copy` with `io.CopyN`/`io.LimitReader` against a running total, and abort with an error once a configurable threshold is exceeded). Apply the same limit to other extractors (`zip`, `zipzstd`) for consistency. Consider making the threshold configurable via a `runners.cache`/`runners.artifact` limit, mirroring `MaxUploadedArchiveSize` but for decompressed extraction size.

### Proof of Concept
Go unit test plan:
1. Build a small `.tar.zst` fixture where the tar payload contains many entries or one entry with a `Size` header claiming a large size but backed by highly compressible repeated data (e.g., all zero bytes), compressed with zstd at max level — resulting in a compressed artifact of a few KB expanding to multiple GB of tar+file content.
2. Call `extractor.Extract(context.Background())` against a `t.TempDir()` and monitor disk usage growth / assert that extraction does not complete unbounded (e.g., inject a `io.LimitReader`-wrapped `io.ReaderAt` upstream to detect total bytes written exceeds an expected safe bound before failing).
3. Assert that after the fix, `Extract` returns an error (e.g., `ErrExtractionSizeLimitExceeded`) once the configured budget is exceeded, and that partial extraction is bounded (no unbounded `os.Create`/`io.Copy` growth), instead of running to completion or exhausting the test's disk quota.
