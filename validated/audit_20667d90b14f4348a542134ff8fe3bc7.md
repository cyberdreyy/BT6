### Title
`getTokenAccountBalance` returns wrong decimals/UI amount from an unverified mint account - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_token_account_balance` validates that the queried account is owned by a known SPL Token program, but never validates that the `mint` field embedded in that account's data actually points to an account owned by the same (or any) SPL Token program. The mint-owner value returned by `get_mint_owner_and_additional_data` is silently discarded, so decimals/extension config used to compute the returned `UiTokenAmount` can come from arbitrary account data the caller fully controls.

### Finding Description
`get_token_account_balance` unpacks the queried account as a `TokenAccount`, extracts its `mint` pubkey, and calls `get_mint_owner_and_additional_data(&bank, mint)`: [1](#0-0) 

That helper fetches whatever account lives at `mint` and unpacks it as an SPL `Mint` (extracting `decimals`, `InterestBearingConfig`, `ScaledUiAmountConfig`), returning `(*mint_account.owner(), mint_data)`: [2](#0-1) 

In `get_token_account_balance`, the returned owner is bound to `_` and never checked, unlike its sibling functions `get_token_supply` and `get_token_largest_accounts`, which do call `is_known_spl_token_id(&mint_owner)` and reject non-token-program-owned mints: [3](#0-2) 

Because the token account's `mint` field is attacker-controlled data inside an account the attacker owns (they can create any SPL-token-program-owned account with `mint` pointing anywhere), and `StateWithExtensions::<Mint>::unpack` will happily parse any 82(+)-byte blob whose fields coincidentally satisfy the `Mint` layout (e.g., another program's account, or a purpose-built dummy account with `is_initialized = 1`), the `decimals` (and interest-bearing/scaled-UI multiplier extensions) used to compute `ui_amount`/`ui_amount_string` are effectively arbitrary and not tied to the real token program's mint state. This mirrors the PoolTogether bug class: a value coming from one asset/account context (the "wrong" mint) is trusted and mixed into a calculation for another context (the token balance) without verifying the two belong to the same authoritative source (the token program).

### Impact Explanation
Any unprivileged JSON-RPC caller invoking `getTokenAccountBalance` on such a crafted token account receives an incorrect `UiTokenAmount` (wrong `decimals`, `uiAmount`, `uiAmountString`), even though `amount` (raw base units) is accurate. This is "wrong account data returned" from a single RPC query — the exact impact class this scan accepts. Downstream consumers (wallets, exchanges, block explorers, other services) that trust `getTokenAccountBalance`'s UI amount for display or accounting can be misled about the true value of a token account, potentially causing financial decisions based on fabricated decimals/scaling.

### Likelihood Explanation
High. The precondition (an SPL-Token-program-owned account whose `mint` field points to a non-mint or foreign-mint account) is trivially creatable by any user with basic knowledge of the `Account` layout — no special privileges, consensus interaction, or multiple calls are required; a single `getTokenAccountBalance` RPC call triggers the flaw. The same missing check likely also affects `get_parsed_token_account`/`get_parsed_token_accounts` (`rpc/src/parsed_token_accounts.rs`) used for `jsonParsed` encoding of `getAccountInfo`/`getTokenAccountsByOwner`, though I was not able to fully confirm whether upstream filtering (e.g., `get_filtered_spl_token_accounts_by_owner`) constrains this path in all cases.

### Recommendation
In `get_token_account_balance` (and any other caller of `get_mint_owner_and_additional_data` that discards the owner), verify `is_known_spl_token_id(&mint_owner)` before using the returned `SplTokenAdditionalDataV2`, exactly as `get_token_supply` and `get_token_largest_accounts` already do, and return `Error::invalid_params` otherwise. Additionally, verify the mint account's owner matches the *specific* token program that owns the queried token account (not merely "any known SPL token id") to prevent cross-program (Token vs Token-2022) mint substitution.

### Proof of Concept
1. Using any signed transaction under the attacker's control, create/store an account owned by `spl_token_interface::id()` formatted as a valid `TokenAccount` (`state = Initialized`, `amount = X`) whose `mint` field is set to the pubkey of some other attacker-controlled account.
2. At that "mint" pubkey, store account data (owned by any program, e.g. attacker's own program) that happens to satisfy `spl_token_interface::state::Mint`'s packed layout with `is_initialized = 1` and an arbitrary `decimals` value (e.g., 0 or 18, instead of the real mint's decimals).
3. Call `getTokenAccountBalance` on the token account from step 1.
4. Observe the returned `decimals`/`uiAmount`/`uiAmountString` reflect the attacker-chosen values from the fake "mint" in step 2, rather than being rejected for pointing to a non-token-program-owned/invalid mint — confirmed by the code path in [1](#0-0)  where the mint owner check is absent compared to [4](#0-3) .

    pub fn get_token_account_balance(
        &self,
        pubkey: &Pubkey,
        commitment: Option<CommitmentConfig>,
    ) -> Result<RpcResponse<UiTokenAmount>> {
        let bank = self.bank(commitment);
        let account = bank.get_account(pubkey).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find account".to_string())
        })?;

        if !is_known_spl_token_id(account.owner()) {
            return Err(Error::invalid_params(
                "Invalid param: not a Token account".to_string(),
            ));
        }
        let token_account = StateWithExtensions::<TokenAccount>::unpack(account.data())
            .map_err(|_| Error::invalid_params("Invalid param: not a Token account".to_string()))?;
        let mint = &Pubkey::from_str(&token_account.base.mint.to_string())
            .expect("Token account mint should be convertible to Pubkey");
        let (_, data) = get_mint_owner_and_additional_data(&bank, mint)?;
        let balance = token_amount_to_ui_amount_v3(token_account.base.amount, &data);
        Ok(new_response(&bank, balance))
    }

/// Analyze a mint Pubkey that may be the native_mint and get the mint-account owner (token
/// program_id) and decimals
pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

fn get_additional_mint_data(bank: &Bank, data: &[u8]) -> Result<SplTokenAdditionalDataV2> {
    StateWithExtensions::<Mint>::unpack(data)
        .map_err(|_| {
            Error::invalid_params("Invalid param: Token mint could not be unpacked".to_string())
        })
        .map(|mint| {
            let interest_bearing_config = mint
                .get_extension::<InterestBearingConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            let scaled_ui_amount_config = mint
                .get_extension::<ScaledUiAmountConfig>()
                .map(|x| (*x, bank.clock().unix_timestamp))
                .ok();
            SplTokenAdditionalDataV2 {
                decimals: mint.base.decimals,
                interest_bearing_config,
                scaled_ui_amount_config,
            }
        })
}
