### Title
System Program `CreateAccount`/`CreateAccountWithSeed` DoS via lamport pre-funding griefing ("dust" transfer) - (File: programs/system/src/system_processor.rs)

### Summary
The `create_account` handler in the System Program requires the destination account to have exactly zero lamports before it will allocate space and assign an owner, exactly analogous to the CNote `getCashPrior() == 0` invariant that a griefer can break with a forced token transfer. Because any account can be pre-funded with lamports by an unrelated, unprivileged `SystemInstruction::Transfer` (or a raw lamport credit via CPI `transfer`), an attacker can permanently prevent legitimate `CreateAccount`/`CreateAccountWithSeed` calls to that address from succeeding.

### Finding Description
`create_account` first checks that the `to` account's lamport balance is `0`; if not, it returns `SystemError::AccountAlreadyInUse` before ever attempting to allocate/assign or add the requested funding: [3](#0-2) 

The companion function `transfer_verified`/`transfer` used to move lamports between accounts places no restriction on the recipient's owner, data, or existing state — it simply requires that `from` is empty of data and that the `from` signer authorized the debit, then unconditionally credits the destination: [4](#0-3) 

This means any user can call `SystemInstruction::Transfer` (or have another program CPI a lamport transfer/`checked_add_lamports`) to send even 1 lamport to a not-yet-created address (e.g., a PDA a protocol intends to `create_account` for a new user, vault, or config account) before the legitimate `CreateAccount` transaction lands. Once that dust lands, the address has `lamports() > 0`, and every subsequent `CreateAccount`/`CreateAccountWithSeed` targeting it will hit the `AccountAlreadyInUse` guard and revert — permanently, since nothing un-funds the account automatically. This is the same invariant-break pattern as the CNote bug: a public, low-cost, unprivileged transfer breaks a strict "must-be-zero" precondition that a critical function depends on.

Notably, the codebase itself acknowledges this exact class of problem: `create_account_allow_prefund` was added specifically to let privileged/internal call sites create an account "where account has already had rent paid in whole or in part before creation" and explicitly skips the zero-lamports check: [5](#0-4) 
However, this bypass is not exposed to ordinary users through the public `SystemInstruction::CreateAccount`/`CreateAccountWithSeed` instructions processed in the entrypoint dispatcher, which still call the strict `create_account`: [6](#0-5) 

### Impact Explanation
Any program or off-chain workflow that derives a deterministic address (PDA or `create_with_seed` address) and later calls `System::CreateAccount`/`CreateAccountWithSeed` to initialize it is vulnerable to permanent denial-of-service: a griefer front-runs the initialization by sending a trivial amount of lamports to the target address. This blocks account/state creation for that address indefinitely (the funds cannot be reclaimed by the intended creator, since only the account's own signature/owner can move its lamports out), directly matching the "functions requiring the pre-condition become permanently unusable" impact rated High in the reference finding.

### Likelihood Explanation
Likelihood is high: the prerequisite address is very often known in advance (deterministic PDAs, `create_with_seed` addresses, or addresses announced/broadcast prior to on-chain creation), the griefing transaction is a single ordinary `SystemInstruction::Transfer` costing only network fees plus 1 lamport, and it requires no special privileges, timing races beyond ordinary front-running, or protocol-specific knowledge beyond the target address.

### Recommendation
For the public `CreateAccount`/`CreateAccountWithSeed` path, avoid rejecting purely on `lamports() > 0`. Instead, treat an account as "not yet in use" if it is owned by the System Program, has empty data, and (optionally) has less than the rent-exempt minimum, mirroring the approach already implemented internally in `create_account_allow_prefund`. This allows legitimate creation to proceed by simply topping up the existing balance to the requested `lamports` value instead of unconditionally erroring out on any pre-existing balance.

### Proof of Concept
1. Attacker (or anyone) observes/derives the PDA/seeded address `X` that a protocol intends to initialize via `system_instruction::create_account(payer, X, lamports, space, owner)`.
2. Attacker submits `system_instruction::transfer(attacker, X, 1)` before the protocol's creation transaction lands; `transfer_verified` credits `X` with 1 lamport unconditionally [7](#0-6) .
3. The protocol's subsequent `CreateAccount`/`CreateAccountWithSeed` transaction now finds `to.get_lamports() == 1 > 0` and fails with `SystemError::AccountAlreadyInUse` [8](#0-7) , permanently blocking initialization of `X` through the normal `CreateAccount` path.

fn transfer_verified(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    let mut from = instruction_context.try_borrow_instruction_account(from_account_index)?;
    if !from.get_data().is_empty() {
        ic_msg!(invoke_context, "Transfer: `from` must not carry data");
        return Err(InstructionError::InvalidArgument);
    }
    if lamports > from.get_lamports() {
        ic_msg!(
            invoke_context,
            "Transfer: insufficient lamports {}, need {}",
            from.get_lamports(),
            lamports
        );
        return Err(SystemError::ResultWithNegativeLamports.into());
    }

    from.checked_sub_lamports(lamports)?;
    drop(from);
    let mut to = instruction_context.try_borrow_instruction_account(to_account_index)?;
    to.checked_add_lamports(lamports)?;
    Ok(())
}

fn transfer(
    from_account_index: IndexOfAccount,
    to_account_index: IndexOfAccount,
    lamports: u64,
    invoke_context: &InvokeContext,
    instruction_context: &InstructionContext,
) -> Result<(), InstructionError> {
    if !instruction_context.is_instruction_account_signer(from_account_index)? {
        ic_msg!(
            invoke_context,
            "Transfer: `from` account {} must sign",
            instruction_context.get_key_of_instruction_account(from_account_index)?,
        );
        return Err(InstructionError::MissingRequiredSignature);
    }

    transfer_verified(
        from_account_index,
        to_account_index,
        lamports,
        invoke_context,
        instruction_context,
    )
}
