## Finding

### Title
`fastzip` archiver/extractor pair lacks explicit cross‑platform name normalization and containment validation present in the sibling tar implementation — (File: `commands/helpers/archive/fastzip/zip_fastzip_archiver.go`)

### Summary
`archiver.Archive` in `zip_fastzip_archiver.go` forwards the `files map[string]os.FileInfo` produced upstream (OS-native relative paths, using `filepath.Separator`) directly into the third-party `saracen/fastzip` library with **no path normalization (`filepath.ToSlash`) and no chroot/containment check**, unlike its sibling `tarzstd_archiver.go`/`tarzstd_extractor.go`, which explicitly compute and validate paths against the archive root on both sides. [1](#0-0) 

### Finding Description
`archiver.Archive` receives `files` keyed by relative paths computed in `commands/helpers/file_archiver.go` via `filepath.Rel` / `filepath.FromSlash`, which uses the **host OS's native separator** (backslash on Windows, forward slash on Linux/macOS). [2](#0-1) 

These raw names are passed unmodified to `fastzip.NewArchiver(a.w, a.dir, opts...).Archive(ctx, files)` with no call to `filepath.ToSlash` and no verification that the resulting entry names stay under `a.dir`: [3](#0-2) 

Compare this to the sibling `tarzstd_archiver.go`, which computes `rel` via `filepath.Rel(a.dir, path)` **and** enforces `strings.HasPrefix(path, a.dir+string(filepath.Separator))` before writing the header: [4](#0-3) 

On the restore side, `tarzstd_extractor.go` re-validates every extracted path with `filepath.Abs(filepath.Join(e.dir, hdr.Name))` and rejects anything that escapes the chroot: [5](#0-4) 

`zip_fastzip_extractor.go`, however, performs **no equivalent check at all** — it hands the reader straight to `fastzip.NewExtractorFromReader(...).Extract(ctx)` and trusts the third-party library entirely for path safety: [6](#0-5) 

The exploit scenario the question describes follows from this asymmetry: a file or directory name legal on one OS (e.g., a Linux filename containing a literal backslash such as `foo\..\..\bar`, which is an ordinary single-byte-per-char filename on Linux) is packaged as a zip entry `Name` field without forward-slash normalization. If a *different* job/runner on Windows later restores that same artifact/cache archive, Windows-native path APIs (`filepath.Join`, `os.MkdirAll`) treat `\` as a path separator and can reinterpret the single "flat" Linux filename as a multi-segment path containing `..` traversal components — precisely the "packaged names interpreted differently on restore" scenario. Because `zip_fastzip_extractor.go` has no containment check of its own (unlike `tarzstd_extractor.go`), whether this is actually blocked depends entirely on internal behavior of the vendored `github.com/saracen/fastzip` package, whose source is **not present in this repository's index** and could not be inspected to confirm or rule out this specific behavior.

### Impact Explanation
If the underlying `saracen/fastzip` library does not itself normalize separators and validate containment (unverifiable here), a cross-platform artifact/cache restore could write files outside the intended extraction root, leading to cross-job overwrite or path-root escape as scoped. This is architecturally plausible given the confirmed absence of Runner-level defenses in the zip path, but not confirmed as concretely exploitable without the vendored library's source.

### Likelihood Explanation
Requires: (1) an unprivileged pipeline author controlling workspace filenames (trivial — `git commit` a filename containing a literal backslash on a Linux runner, or vice versa a name with `/` sequences from a Windows job), (2) a pipeline with heterogeneous runner OSes (a common real-world topology: build on Windows, later stage on Linux, or mixed fleet), and (3) the vendored `fastzip` library not independently sanitizing entry names/paths on either the pack or unpack side. Points 1–2 are fully attacker-controlled and easy; point 3 is unverified.

### Recommendation
Regardless of what `saracen/fastzip` internally does, add explicit defense-in-depth in Runner's own wrapper code, mirroring `tarzstd`:
- In `zip_fastzip_archiver.go`, normalize names with `filepath.ToSlash` before handing them to `fastzip.NewArchiver(...).Archive(...)`, and reject/skip any resulting name containing `\`, a leading `/`, or `..` path segments.
- In `zip_fastzip_extractor.go`, after (or instead of relying solely on) `fastzip`'s extraction, validate each extracted entry's target path with `filepath.Abs(filepath.Join(e.dir, name))` and confirm it remains under `e.dir`, exactly as done in `tarzstd_extractor.go`.

### Proof of Concept
Because the actual name-encoding/decoding logic lives in the vendored `saracen/fastzip` package (not available for inspection in this index), a definitive PoC requires validating that library's behavior directly:
1. On a Linux test host, create a file literally named `evil\..\..\pwn` inside the archive source directory.
2. Run `archiver.Archive` (from `zip_fastzip_archiver.go`) to produce a zip and inspect the raw `zip.File.Name` bytes in the resulting archive — assert whether the backslash is preserved literally (expected/safe) or converted.
3. Extract that same archive using `extractor.Extract` (from `zip_fastzip_extractor.go`) on a Windows test host, asserting the resulting file lands only under the target extraction directory and not two levels above it (`assert.NoFileExists` for the escaped location, `assert.FileExists` only within `e.dir`).

Given the tool constraints, this PoC could not be executed to confirm actual exploitability; the finding should be treated as an **unverified architectural gap** (missing containment check in the zip archiver/extractor pair vs. the tar pair) rather than a confirmed working exploit.

func (a *archiver) Archive(ctx context.Context, files map[string]os.FileInfo) error {
	tmpDir, err := os.MkdirTemp(os.Getenv(archiverStagingDir), "fastzip")
	if err != nil {
		return fmt.Errorf("fastzip archiver unable to create temporary directory: %w", err)
	}
	defer os.RemoveAll(tmpDir)

	opts, err := getArchiverOptionsFromEnvironment()
	if err != nil {
		return err
	}

	opts = append(opts, fastzip.WithStageDirectory(tmpDir))
	if a.level == archive.FastestCompression {
		opts = append(opts, fastzip.WithArchiverMethod(zip.Store))
	}

	if a.zstd {
		opts = append(opts, fastzip.WithArchiverMethod(zstd.ZipMethodWinZip))
	}

	fa, err := fastzip.NewArchiver(a.w, a.dir, opts...)
	if err != nil {
		return err
	}

	if a.level != archive.FastestCompression {
		if a.zstd {
			fa.RegisterCompressor(zstd.ZipMethodWinZip, fastzip.ZstdCompressor(zstdLevels[a.level]))
		} else {
			fa.RegisterCompressor(zip.Deflate, fastzip.FlateCompressor(flateLevels[a.level]))
		}
	}

	err = fa.Archive(ctx, files)

	if cerr := fa.Close(); err == nil && cerr != nil {
		return cerr
	}

	return err

func (c *fileArchiver) findRelativePathInProject(path string) (string, error) {
	slashPath := filepath.ToSlash(path)
	if filepath.Clean(slashPath) == filepath.Clean(c.wd) {
		return ".", nil
	}

	base, patt := slashPath, ""
	// check if path contains a glob pattern
	if strings.ContainsAny(slashPath, "*?[{") {
		base, patt = doublestar.SplitPattern(slashPath)
	}

	abs, err := filepath.Abs(base)
	if err != nil {
		return "", fmt.Errorf("could not resolve artifact absolute path %s: %w", path, err)
	}

	rel, err := filepath.Rel(c.wd, abs)
	if err != nil {
		return "", fmt.Errorf("could not resolve artifact relative path %s: %w", path, err)
	}

	// If fully resolved relative path begins with ".." it is not a subpath of our working directory
	if strings.HasPrefix(rel, ".."+string(filepath.Separator)) || rel == ".." {
		return "", fmt.Errorf("artifact path is not a subpath of project directory: %s", path)
	}

	// Relative path is needed now that our fsys "root" is at the working directory
	rel = filepath.Join(rel, patt)
	rel = filepath.FromSlash(rel)
	return rel, nil
}
