### Title
Miner-signature malleability lets gossip split signer voting weight across two hashes of the same block, wedging block production - (File: `stackslib/src/chainstate/nakamoto/mod.rs`)

### Summary
`NakamotoBlockHeader::signer_signature_hash_inner` includes the raw `miner_signature` bytes in the pre-image that signers sign over and that the node uses as the sole key for tallying signer votes. Because miner (not signer) ECDSA signatures are explicitly *not* required to be low-S — `check_proposal_accepts_high_s_miner_sign` documents that a negated-S miner signature is accepted as valid — the 65-byte `miner_signature` field admits two distinct, independently valid encodings for the exact same signed message (the standard `(r,s,recid)` and its malleated `(r,-s mod n, 1-recid)` counterpart). Since every other header field is identical, the resulting `signer_signature_hash()` (and thus `block_id()`) differs between the two encodings even though the blocks are content-identical and both carry a fully valid miner signature.

### Finding Description
`signer_signature_hash_inner` writes `self.miner_signature` verbatim into the digest: [1](#0-0) 

and the low-S check that would collapse malleated signatures to one canonical form is only enforced by `Secp256k1PublicKey::verify` for ordinary signed messages — the miner-signature verification path explicitly tolerates high-S: [2](#0-1) 

Every downstream signer data structure keys on this mutable hash rather than on any canonical content hash:
- The signer's own tracking table, `block_lookup_by_reward_cycle`, and all pending-response tables (`add_pending_block_pre_commit_response`, `add_pending_block_signature_response`, `add_pending_block_rejection_response`) are keyed by `signer_signature_hash`.
- The node-side vote tally in `stackerdb_listener.rs`'s `BlockStatus` map is also keyed by `block_sighash`/`signer_signature_hash`, with `total_weight_approved`/`total_weight_rejected` accumulated per-hash: [3](#0-2) [4](#0-3) 

The 70% acceptance/rejection threshold is evaluated strictly per-hash on both the signer side (`store_and_process_block_signature`) and the coordinator side (`get_block_status`): [5](#0-4) [6](#0-5) 

Because a StackerDB chunk carrying a `BlockProposal` is signed by the miner but the *contained block's* `miner_signature` can be malleated by anyone in the delivery path without invalidating anything (the signature still recovers to the correct miner pubkey hash), a party positioned to relay/duplicate the proposal chunk (or the miner itself, deliberately or via two independent proposal paths) can inject a byte-flipped variant `B` of the identical block `A` into the signer set's view. `A` and `B` have the same `chain_length`, `consensus_hash`, `parent_block_id`, `tx_merkle_root`, `state_index_root`, `timestamp`, `pox_treatment`, and `problematic_txs` — passing every static and chainstate check identically — but different `signer_signature_hash`/`block_id`.

Signers that receive `A` first commit their pre-commit/signature weight to hash_A; signers that receive `B` first commit to hash_B. Neither pool alone can reach the 70% weight threshold if the honest signer set is split between the two variants, even though the *combined* honest weight (which would sign either variant, since they are the same block) comfortably exceeds it. This is a liveness wedge that does not require a majority of malicious signers, a compromised key, or any privileged access — it only requires a single malleated copy of the proposal reaching part of the signer set via gossip/relay, which is explicitly in scope.

### Impact Explanation
This is a High-severity liveness issue: a signer/coordinator can be wedged into never reaching the 70% threshold on either hash of what is really one block, stalling tenure progress until the miner is forced to mine an entirely new (higher-timestamp) block, at which point the same malleability can recur. No signature forgery or double-signing of conflicting content occurs (the "content" is identical), but the equality the protocol relies on — "one proposal, one vote-tally bucket" — is broken by the choice to hash the mutable `miner_signature` bytes instead of a canonicalized/normalized form of the miner's authorization.

### Likelihood Explanation
Exploitability only requires observing a `BlockProposal` chunk on the wire (StackerDB replication is gossip-based) and re-signing/relaying a bit-flipped `(s, recid)` variant, which is a purely mechanical secp256k1 malleability operation requiring no private key. The existing test suite already demonstrates the specific negated-S miner-signature acceptance path (`check_proposal_accepts_high_s_miner_sign`), confirming both variants independently pass proposal validation.

### Recommendation
Normalize (low-S) the `miner_signature` before computing `signer_signature_hash`/`block_id`, or exclude the miner signature bytes from the digest entirely and instead have signers/coordinator key their vote tallies on a canonical content hash (all fields except both signature vectors). Alternatively, enforce low-S on miner signatures the same way it's enforced for signer/transaction signatures, removing the two-valid-encodings ambiguity at the source.

### Proof of Concept
1. Miner builds block `A` with header fields `F` and signs `F` with `miner_signature = (r, s, recid)`; `signer_signature_hash(A) = H_A`.
2. Attacker/relay observes the `BlockProposal` StackerDB chunk in flight and constructs `B` = same header fields `F`, but `miner_signature = (r, n-s, 1-recid)` — a standard ECDSA malleation that still recovers to the same miner pubkey hash and thus passes `check_miner_signature`/`check_proposal`. `signer_signature_hash(B) = H_B ≠ H_A`.
3. Relay delivers `A` to signer subset S1 and `B` to signer subset S2 (e.g., by racing the original chunk with a duplicate chunk, or by exploiting normal gossip propagation timing).
4. S1 pre-commits/signs against `H_A`; S2 pre-commits/signs against `H_B`. Both `stacks-signer`'s `store_and_process_block_signature` and the node's `SignerCoordinator::get_block_status` tally weight strictly per-hash, so neither `H_A` nor `H_B` reaches the 70% `weight_threshold`, and the tenure stalls until the miner produces a fresh, later-timestamped block.
