### Title
Builder withdrawal amount is not re-validated against current balance before payout, allowing Gwei to be paid to a builder's `fee_recipient` without being debited from stake — (File: `specs/gloas/beacon-chain.md`)

### Summary
`apply_withdrawals` in Gloas caps the *state* deduction for a builder withdrawal at `min(withdrawal.amount, builder_balance)`, but the `Withdrawal.amount` field that is placed into `state.payload_expected_withdrawals` (and thus paid out on the execution layer to `fee_recipient`) always uses the full, uncapped, previously-committed amount. If a builder's committed pending withdrawal ever exceeds its actual balance at settlement time, the execution layer credits the full committed amount while the consensus layer only debits the smaller, capped amount — creating Gwei that is not backed by any stake, exactly analogous to the BakerFi `removeStrategy()` bug where the caller assumed `undeploy()` always returns the full requested amount.

### Finding Description
Two functions cooperate to produce the withdrawal object and to apply it:

`get_builder_withdrawals` copies the *raw, uncapped* `withdrawal.amount` from `state.builder_pending_withdrawals` straight into the `Withdrawal` that is committed to `payload_expected_withdrawals` and sent to the execution layer: [1](#0-0) 

`apply_withdrawals`, however, deducts only `min(withdrawal.amount, builder_balance)` from the builder's on-chain balance: [2](#0-1) 

The spec's own generated test explicitly documents this asymmetry: the payload commits the full requested amount while the balance deduction is capped at whatever is available: [3](#0-2) 

The protocol's defense against this is `can_builder_cover_bid`, which is supposed to guarantee that a builder's balance always covers `MIN_DEPOSIT_AMOUNT` plus the sum of everything it has already committed to pay (`get_pending_balance_to_withdraw_for_builder`, which sums both `state.builder_pending_withdrawals` and `state.builder_pending_payments` for that builder): [4](#0-3) 

This accounting invariant is enforced only at the moment a *new* bid is submitted (`process_execution_payload_bid`): [5](#0-4) 

The gap: when a parent block's execution payload is confirmed very late — specifically when the parent's slot is now *older than the previous epoch* — its `builder_pending_payments` entry has already been rotated out by epoch processing before `settle_builder_payment` ever ran on it. `apply_parent_execution_payload` handles this by re-appending the withdrawal directly, bypassing the normal quorum-weighted settlement path and, crucially, without any fresh balance check: [6](#0-5) 

During the window between the payment being rotated out of `builder_pending_payments` (which `get_pending_balance_to_withdraw_for_builder` counts) and this direct re-append into `builder_pending_withdrawals` (which is also counted), the amount is briefly invisible to `get_pending_balance_to_withdraw_for_builder`. Even more importantly, once it is force-appended, nothing re-checks it against the builder's *current* balance — that check was only ever performed against the balance available at original bid-submission time, potentially epochs earlier. If, after the original bid was accepted, the same builder submitted and had accepted additional bids/payments whose sum together with this recovered commitment now exceeds the builder's real balance (a legitimate sequence, since each new bid is checked against the *state at that time*, which does not yet reflect commitments still sitting in the "evicted-but-not-yet-recovered" gap), then when `apply_withdrawals` eventually processes this recovered withdrawal, `builder_balance < withdrawal.amount` and the `min()` clamp engages — the execution layer still pays the *fee_recipient* the full uncapped amount, but the consensus layer stake is only reduced by the smaller, capped amount.

This breaks the core equality: **Gwei paid on the execution layer must equal Gwei debited on the consensus layer**. Here it does not — value is created and paid to a non-owner (the fee_recipient) that was never actually backed by the builder's stake.

### Impact Explanation
This is a Critical-severity issue under the stated impact model: Gwei is paid to a party (a builder's fee recipient) without a corresponding debit from any account — inflating the token supply on the execution layer relative to what the consensus layer believes was spent. This mirrors the "Gwei created ... paid to a non-owner" criterion directly. It also produces persistent state divergence between what the EL considers minted/paid and what the CL considers debited, which is the same category of impact as an invalid transition being silently accepted.

### Likelihood Explanation
Triggering this requires only a single unprivileged builder behaving normally: place multiple bids over time, none of which individually violate `can_builder_cover_bid` given the state visible at submission time, while one of its parent payloads happens to be confirmed with a delay exceeding roughly two epochs (a scenario the spec itself explicitly anticipates and handles with the "Parent is older than the previous epoch" branch, i.e., this is not a contrived edge case — it's a designed code path). No malicious peer, coalition, or client bug is required — only ordinary, permitted variance in confirmation timing combined with a sequence of otherwise-valid bids from one builder.

### Recommendation
Either (a) re-validate `builder_balance >= withdrawal.amount` at the moment the withdrawal is force re-appended in `apply_parent_execution_payload`'s "older than previous epoch" branch and clamp the committed `amount` there, or (b) make `get_builder_withdrawals` place `min(withdrawal.amount, state.builders[builder_index].balance)` into the `Withdrawal.amount` field so that the amount sent to the execution layer for payout is always identical to the amount actually deducted from the builder's balance in `apply_withdrawals` — eliminating any possibility of the two values diverging, analogous to the BakerFi fix of using the actually-received amount rather than the originally-requested amount.

### Proof of Concept
1. Builder B accepts bid₁ for slot N with `value = v₁`; `can_builder_cover_bid` passes because `balance ≥ MIN_DEPOSIT_AMOUNT + v₁` at that time. This creates a `BuilderPendingPayment` entry in `state.builder_pending_payments`.
2. The block containing bid₁'s parent confirmation is delayed (e.g., due to empty/skipped slots) such that by the time `apply_parent_execution_payload` processes it, `parent_epoch` is already older than `get_previous_epoch(state)`. Epoch processing (`process_builder_pending_payments`) has already rotated/cleared this payment slot before `settle_builder_payment` ran on it, so `get_pending_balance_to_withdraw_for_builder` no longer counts `v₁` against B.
3. During this window, B submits a new bid₂ with `value = v₂` such that `balance ≥ MIN_DEPOSIT_AMOUNT + v₂` passes `can_builder_cover_bid` (since `v₁` is temporarily untracked), even though `balance < MIN_DEPOSIT_AMOUNT + v₁ + v₂`.
4. `apply_parent_execution_payload`'s `elif parent_bid.value > 0` branch fires for bid₁'s parent, appending `BuilderPendingWithdrawal(amount=v₁, ...)` directly with no balance check: [6](#0-5) 
5. `process_withdrawals` eventually processes both `v₁` and `v₂` as builder withdrawals. `get_builder_withdrawals` places the full uncapped `v₁` and `v₂` into `payload_expected_withdrawals` (sent to EL): [1](#0-0) 
6. `apply_withdrawals` debits only `min(v₁, balance)` and then `min(v₂, remaining_balance)` from `state.builders[B].balance`, which sums to less than `v₁ + v₂`: [2](#0-1) 
7. Result: the execution layer credits `fee_recipient`s with `v₁ + v₂` Gwei total, while the consensus layer only ever debited `< v₁ + v₂` from B's stake — Gwei created out of thin air and paid to a non-owner.

#### New `get_pending_balance_to_withdraw_for_builder`

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
```

```python
def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
