### Title
Untyped, domain-separator-free message signing in the ed25519/secp256k1/secp256r1 precompiles enables cross-program, cross-cluster, and cross-application signature reuse - (File: `precompiles/src/ed25519.rs`, `precompiles/src/secp256k1.rs`, `precompiles/src/secp256r1.rs`)

### Summary
Agave's built-in ed25519, secp256k1, and secp256r1 precompile programs verify a raw, attacker-supplied `(pubkey, signature, message)` triple taken directly from instruction data, with zero binding to the program that will consume the "verified" result, zero binding to the cluster/genesis hash, and zero type/domain tag embedded in the signed payload. This is structurally identical to the reported "Untyped data signing" bug class: any downstream on-chain program that relies on these precompiles to authenticate off-chain-signed messages (a common bridge/oracle/governance pattern) inherits full exposure to signature replay across different programs, different clusters (mainnet/devnet/testnet), and even unrelated dApps that happen to use the same signed byte layout.

### Finding Description
The `verify` functions for all three signature precompiles parse `pubkey`, `signature`, and `message` byte ranges purely from offsets supplied in the precompile instruction data (`Ed25519SignatureOffsets`, `SecpSignatureOffsets`) and perform a bare cryptographic check: [1](#0-0) [2](#0-1) 

Nothing in the verified payload ties the signature to:
- the specific program that will later read the "signature verified" fact (there is no program-id / type hash mixed into the message),
- the specific cluster (no genesis hash / chain-id equivalent is included in the signed bytes),
- the specific instruction/function that is meant to consume it.

These precompiles are dispatched generically from the runtime for any transaction that includes a `secp256k1_program`/`ed25519_program`/`secp256r1_program` instruction, with the verification result made available to any invoked program via sysvar/instruction introspection: [3](#0-2) 

Because the message content is entirely program-defined and un-tagged, this mirrors exactly the four attack primitives from the referenced report:
1. **Reuse across different "projects" (programs)** — if two different on-chain programs both expect an off-chain-signed message with the same byte layout (e.g., `[u8;20] eth_address || u64 amount`), a signature intended for authorizing an action in program A can be replayed verbatim against program B, since neither the precompile nor the message itself encodes which program it was meant for.
2. **Reuse across chains** — since the signed bytes contain no genesis hash/chain-id, a message signed by a user/oracle for one cluster (e.g. devnet) remains valid and replayable on another cluster (e.g. mainnet-beta) as long as the consuming program's logic and account layout happen to line up.
3. **Reuse across functions** — a message crafted for one instruction handler of a program can be fed into a different instruction handler of the same program if both handlers rely on the same generic precompile-verified pubkey/message shape without an internal type discriminator.
4. **Cross-application phishing** — because the signed payload format is fully free-form (arbitrary bytes chosen by whichever program's SDK constructs it), a user could be tricked into signing a message for an unrelated, non-malicious dApp that happens to share the same byte layout as a sensitive Solana program's authorization message, and have that signature replayed against the sensitive program.

The root cause is identical to the Rigor finding: the validator/runtime supplies only raw cryptographic signature verification as a primitive, with **no enforced domain separator** (no equivalent of EIP-712's `contract address + chainId + typeHash`), leaving every consuming program independently responsible for manually prefixing/tagging its signed messages — a step that is easy to omit and not enforced anywhere in the precompile or SVM verification path (`precompiles/src/lib.rs::verify_if_precompile`).

### Impact Explanation
Any deployed program that authenticates off-chain messages via these precompiles (a widely-used pattern for bridges, price oracles, multisig/session-key schemes, and airdrop/allowlist claims) is exposed to signature replay that can lead to unauthorized state mutation or fund movement in that program if it does not itself add manual domain separation. Because this is the *only* signature-verification primitive the runtime exposes to programs for non-transaction-signer authentication, essentially the entire ecosystem of programs that consume it is exposed to this class of bug by default, with no protocol-level guardrail.

### Likelihood Explanation
High for any program that naively signs/verifies simple, unprefixed byte payloads (address + amount + nonce style messages) via these precompiles, which is a common and historically real pattern in Solana program development. The precompile path is reachable by any user submitting a transaction with a precompile instruction plus a call into the consuming program in the same transaction — no privileged access is required.

### Recommendation
While the precompiles themselves are meant to be generic signature-verification primitives, the runtime/SDK should:
1. Provide (and strongly recommend/document) a canonical domain-separated message-construction helper for `solana_ed25519_program`/`solana_secp256k1_program`/`solana_secp256r1_program` instruction builders that mixes in the consuming program's ID, the cluster genesis hash, and a type tag before hashing/signing, analogous to EIP-712's domain separator.
2. Emit warnings/lints in the SDK when message bytes passed to `new_ed25519_instruction_with_signature`/`new_secp256k1_instruction_with_signature` do not contain such a prefix.
3. Consider extending `Ed25519SignatureOffsets`/`SecpSignatureOffsets`-based verification with an optional mandatory domain-separator field checked by the precompile itself, rather than leaving 100% of the responsibility to downstream program authors.

### Proof of Concept
Using the existing precompile test helpers, the following demonstrates that the same `(pubkey, signature, message)` triple verified by `agave_precompiles::ed25519::verify` carries no notion of which program, instruction, or cluster it is intended for — the identical instruction bytes are valid input regardless of consumer: [4](#0-3) 
Because `verify` only checks `publickey.verify_strict(message, &signature)` with `message` being fully attacker/program-controlled raw bytes and no domain tag, any two programs (or the same program across two clusters) that accept a message of the same byte shape from this same precompile instruction can be made to accept each other's signed payloads, exactly reproducing the "signature reuse across projects/chains/functions" primitives from the referenced report.

/// Check that a program is precompiled and if so verify it
pub fn verify_if_precompile(
    program_id: &Pubkey,
    precompile_instruction: &CompiledInstruction,
    all_instructions: &[CompiledInstruction],
    feature_set: &FeatureSet,
) -> Result<(), PrecompileError> {
    for precompile in PRECOMPILES.iter() {
        if precompile.check_id(program_id, |feature_id| feature_set.is_active(feature_id)) {
            let instruction_datas: Vec<_> = all_instructions
                .iter()
                .map(|instruction| instruction.data.as_ref())
                .collect();
            return precompile.verify(
                &precompile_instruction.data,
                &instruction_datas,
                feature_set,
            );
        }
    }
    Ok(())
}
