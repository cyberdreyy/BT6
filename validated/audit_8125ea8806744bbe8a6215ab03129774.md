**Reasoning:**

The premise doesn't hold. `borrow_storage_slot_resource_mut` requires the caller to already possess a mutable reference `&mut StorageSlot<T>`, not just any `StorageSlot<T>` value or `&StorageSlot<T>`, as declared in both the native signature and the wrapping `borrow_mut` function [1](#0-0) . Move's bytecode verifier/borrow-checker enforces this at compile/verification time — a caller holding only an immutable `&StorageSlot<T>` (e.g., a value "passed as a read parameter") cannot obtain a `&mut` reference to call `borrow_mut`; there is no legal Move code path to escalate `&` to `&mut` without the callee explicitly exposing a `&mut` accessor. This guarantee is provided by the Move type system itself, independent of any role-check logic inside the native.

Additionally, `StorageSlot` is a generic, standalone data-structure primitive [2](#0-1)  — it is not wired into `stake.move`, `staking_contract.move`, `delegation_pool.move`, or `vesting.move` for beneficiary/commission/owner-role storage. Searches across the stake/vesting/staking_contract modules show beneficiary and role state (e.g., `BeneficiaryForOperator`, `VestingAccountManagement`) are stored as ordinary key resources guarded by explicit `verify_admin`/role checks [3](#0-2) , not through `StorageSlot`. There is no unprivileged entrypoint in stake/delegation/vesting logic that hands a `StorageSlot` "for read" to a caller who could then obtain a `&mut` on it — the scenario described (passing a read-only `StorageSlot` into a generic `borrow_mut` helper) is not achievable under Move's reference semantics and has no concrete wiring into the stake/lockup beneficiary/commission system in this codebase.

Since the exploit requires bypassing a language-level guarantee (not a missing application-level role check) and has no actual usage path in stake/delegation/vesting code, this does not meet the decision standard requiring a real unprivileged path that changes withdrawal/beneficiary/operator control.
