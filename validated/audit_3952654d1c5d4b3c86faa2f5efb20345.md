Interesting: `drift_claim_bad_debt`'s `cpi_transfer_to_destination` already guards against zero-value transfers [1](#0-0) , and `lending_pool_emissions_deposit` explicitly returns early on `amount == 0` [2](#0-1) . However, `drift_harvest_reward` and `kamino_harvest_reward` both lack this guard: they compute a `TransferChecked`/transfer amount from a live token-account balance (or a `post - pre` delta) and call `transfer_checked` **unconditionally**, even if that amount is `0` [3](#0-2) [4](#0-3) .

### Title
Permissionless `drift_harvest_reward` / `kamino_harvest_reward` perform unconditional zero-value token transfers, causing durable reverts for reward tokens that disallow zero-value transfers - (File: `programs/marginfi/src/instructions/drift/harvest_reward.rs`, `programs/marginfi/src/instructions/kamino/harvest_reward.rs`)

### Summary
Both `drift_harvest_reward` and `kamino_harvest_reward` are permissionless instructions that sweep whatever reward-token balance currently sits in an intermediary/ATA account to the protocol's global fee wallet, using `transfer_checked` without first checking if the amount is non-zero — the exact pattern flagged in the ConvexStakingWrapper report.

### Finding Description
In `drift_harvest_reward`, `cpi_transfer_to_destination` reads the entire current balance of `intermediary_token_account` via `accessor::amount` and calls `transfer_checked` on it unconditionally [3](#0-2) . Similarly, `kamino_harvest_reward` computes `received = post_transfer_balance - pre_transfer_balance` and always calls `cpi_transfer_obligation_owner_to_destination(received)`, which performs `transfer_checked` unconditionally regardless of whether `received` is `0` [4](#0-3) [5](#0-4) . If the reward mint is a Token-2022 mint whose transfer hook or extension logic rejects zero-value transfers, any call to these instructions made when there is nothing new to harvest (a very plausible/frequent case for a permissionless, anyone-can-call instruction) will revert. By contrast, marginfi's own maintainers already recognized and fixed this exact class of bug elsewhere: `drift_claim_bad_debt`'s sweep explicitly early-returns when `amount == 0` [1](#0-0) , and `lending_pool_emissions_deposit` explicitly no-ops on `amount == 0` [2](#0-1)  — but the harvest-reward paths were not given the same treatment.

### Impact Explanation
Unlike the original ConvexStakingWrapper report — where the bug blocked core user deposit/withdraw functionality — here the affected instructions (`drift_harvest_reward`, `kamino_harvest_reward`) are standalone, permissionless maintenance/sweep instructions, not something invoked as a mandatory side-effect of user deposits/withdraws. A revert only fails the harvest call itself; it does not lock user funds, does not block deposits/withdraws, and any legitimately harvestable balance (once new rewards actually accrue) can still be swept successfully on a subsequent call, since the underlying withdraw step (`cpi_withdraw_from_position` / `cpi_harvest_rewards`) will pull in new nonzero rewards before the transfer executes. There is no unauthorized state change, value redirection, or fund freeze — worst case is a permissionlessly-callable instruction becoming a no-op/revert until new rewards accumulate.

### Likelihood Explanation
Reachability requires reward mints configured as Token-2022 mints with a transfer-hook/extension that explicitly rejects zero-amount transfers, which is a mint-specific edge case rather than a default behavior of common Solana tokens. Marginfi does already reject transfer-fee/transfer-hook mints for `lending_pool_emissions_deposit` [6](#0-5) , but no equivalent mint-safety check exists for `reward_mint` in the harvest-reward instructions.

### Recommendation
Not warranted as a standalone finding given the limited, non-financial impact (a permissionless maintenance instruction reverting harmlessly), but as defense-in-depth, add the same `if amount == 0 { return Ok(()) }` guard used in `drift_claim_bad_debt::cpi_transfer_to_destination` to `DriftHarvestReward::cpi_transfer_to_destination` and `KaminoHarvestReward::cpi_transfer_obligation_owner_to_destination` before calling `transfer_checked`.

### Proof of Concept
Not applicable — this does not rise to a concrete, financially-impactful, unpermissioned exploit; it only causes a benign instruction-level revert for maintenance calls on a subset of unusual reward mints, and it does not affect deposits, withdraws, valuations, or user funds.

    pub fn cpi_transfer_to_destination(&self) -> MarginfiResult {
        let program = self.token_program.to_account_info();
        let accounts = TransferChecked {
            from: self.intermediary_token_account.to_account_info(),
            to: self.destination_token_account.to_account_info(),
            authority: self.liquidity_vault_authority.to_account_info(),
            mint: self.reward_mint.to_account_info(),
        };

        let bump = self.bank.load()?.liquidity_vault_authority_bump;
        let signer_seeds: &[&[&[u8]]] =
            bank_signer!(BankVaultType::Liquidity, self.bank.key(), bump);
        let cpi_ctx = CpiContext::new_with_signer(program.key(), accounts, signer_seeds);

        let decimals = self.reward_mint.decimals;
        // Transfer entire balance
        let amount = accessor::amount(&self.intermediary_token_account.to_account_info())?;
        transfer_checked(cpi_ctx, amount, decimals)?;
        Ok(())
    }

pub fn kamino_harvest_reward(

    reward_index: u64,
) -> MarginfiResult {

    ctx.accounts.cpi_harvest_rewards(reward_index)?;
    let post_transfer_balance = accessor::amount(&ctx.accounts.user_reward_ata.to_account_info())?;
    let received = post_transfer_balance - pre_transfer_balance;
    ctx.accounts

    Ok(())
}
