### Title
Delegate-vote share accounting uses delegator's *current* live share balance instead of the amount originally contributed, corrupting `DelegatedVotes.active_shares_next_lockup` for other delegators of the same voter - ([File: aptos-move/framework/aptos-framework/sources/delegation_pool.move])

### Summary
`delegate_voting_power` mutates the *aggregate* `active_shares_next_lockup` counter of a voter by adding/subtracting the calling delegator's **current** active-share balance, not the amount that was actually recorded when the delegator first pointed at that voter. Because a delegator's active-share balance can change between two `delegate_voting_power` calls (via `add_stake`/`unlock`/`reactivate_stake`), a second switch inside the same lockup cycle removes the wrong amount from the previous `pending_voter`'s aggregate — an amount that is shared across all delegators who point at that voter — corrupting the voting-power accounting of delegators who never touched their own delegation.

### Finding Description
`DelegatedVotes.active_shares_next_lockup` is a single aggregate value per voter, summed from contributions of every delegator that has `pending_voter == that voter` [1](#0-0) .

When a delegator re-targets their vote delegation, the code does:
```
let active_shares = get_delegator_active_shares(delegation_pool, delegator_address);
pending_delegated_votes.active_shares_next_lockup -= active_shares;
new_delegated_votes.active_shares_next_lockup += active_shares;
``` [2](#0-1) 

`active_shares` here is fetched fresh via `get_delegator_active_shares`, i.e. the delegator's **current** total active shares at call time — not the amount that was actually credited to the previous `pending_voter`'s aggregate when the delegator first delegated to it.

Concretely:
1. Delegator D (holding `X1` active shares) calls `delegate_voting_power(D, pool, A)`. This adds `X1` to `A.active_shares_next_lockup`.
2. D calls `add_stake`, minting additional active shares, so D's balance becomes `X2 > X1`. This does not retroactively rewrite `A.active_shares_next_lockup`.
3. Still inside the same lockup cycle, D calls `delegate_voting_power(D, pool, B)`. The code reads D's *current* balance `X2` and does `A.active_shares_next_lockup -= X2`, even though A's aggregate only ever received `X1` from D. This either:
   - underflows/aborts if `A`'s aggregate (sum of all delegators pointing at A) is smaller than `X2`, or
   - if other delegators also point at A, silently removes shares that were contributed by *those other delegators*, transferring their voting power to `B` even though they never delegated to `B`.

This is a direct accounting desync analogous to the external report's pattern: an action recorded against a shared aggregate uses a value captured at a different point in time (post-`add_stake`) than the value that was originally used to build that aggregate (pre-`add_stake`), producing wrong per-voter share totals that persist into governance voting power calculations (`calculate_total_voting_power` / `calculate_and_update_voter_total_voting_power`) [3](#0-2) .

### Impact Explanation
This corrupts the delegated-voting-power accounting shared by all delegators pointing to a given voter within a delegation pool — an unprivileged delegator D can silently reduce another honest delegator's contribution to voter A's aggregate and shift that voting power to a voter B of D's choosing, or cause a permanent abort of `delegate_voting_power` for that voter (denial of the delegate/undelegate path) if the subtraction underflows. This is "share-accounting corruption that credits the wrong account" against the voter role, within the required impact set, but it affects governance voting power rather than raw stake/coin custody, so it is not a direct fund-theft bug.

### Likelihood Explanation
The trigger sequence (delegate to A → add_stake → delegate to B, all within one lockup cycle) requires only the calling delegator's own signer and no special role, and is straightforward for any unprivileged user with an active delegation-pool position to execute (`add_stake`, `delegate_voting_power` are both public entry functions requiring only a signer). It requires `partial_governance_voting` to be enabled on the pool, which is expected on any governance-participating delegation pool.

### Recommendation
Track, per delegator, the exact number of active shares that were credited to the current `pending_voter`'s `active_shares_next_lockup` at the time of delegation (e.g., store it in `VoteDelegation`), and use that stored value — not a fresh call to `get_delegator_active_shares` — when reversing the contribution on a subsequent `delegate_voting_power` call. Alternatively, resynchronize/rebuild each `DelegatedVotes.active_shares_next_lockup` from actual delegator contributions before allowing a delegation switch, and validate that the amount subtracted never exceeds what was previously added by that specific delegator.

### Proof of Concept
1. Enable partial governance voting on delegation pool `P`; delegator `D` adds stake, receiving `X1` active shares.
2. `D` calls `delegate_voting_power(D, P, A)`. `GovernanceRecords.delegated_votes[A].active_shares_next_lockup += X1`.
3. `D` calls `add_stake(D, P, extra)`, increasing D's total active shares to `X2 = X1 + extra_shares`.
4. `D` calls `delegate_voting_power(D, P, B)` before the lockup cycle rolls over. Internally: `pending_voter == A` (unchanged), so the code executes `delegated_votes[A].active_shares_next_lockup -= X2` and `delegated_votes[B].active_shares_next_lockup += X2`.
5. If any other delegator E also has `pending_voter == A`, E's contribution is now partially or fully removed from `A`'s aggregate (or the subtraction aborts on underflow if A's aggregate is smaller than `X2`), even though E never took any action — demonstrable by comparing `calculate_and_update_voter_total_voting_power(P, A)` before and after step 4 against the sum of shares independently delegated to A by delegators other than D.

    /// Update DelegatedVotes of a voter to up-to-date then borrow_mut it.
    fun update_and_borrow_mut_delegated_votes(
        pool: &DelegationPool,
        governance_records: &mut GovernanceRecords,
        voter: address
    ): &mut DelegatedVotes {
        let pool_address = get_pool_address(pool);
        let locked_until_secs = stake::get_lockup_secs(pool_address);

        let delegated_votes_per_voter = &mut governance_records.delegated_votes;
        // By default, a delegator's voter is itself.
        // TODO: recycle storage when DelegatedVotes equals to default value.
        if (!delegated_votes_per_voter.contains(voter)) {
            let active_shares = get_delegator_active_shares(pool, voter);
            let inactive_shares = get_delegator_pending_inactive_shares(pool, voter);
            return delegated_votes_per_voter.borrow_mut_with_default(voter, DelegatedVotes {
                active_shares,
                pending_inactive_shares: inactive_shares,
                active_shares_next_lockup: active_shares,
                last_locked_until_secs: locked_until_secs,
            })
        };

        let delegated_votes = delegated_votes_per_voter.borrow_mut(voter);
        // A lockup period has passed since last time `delegated_votes` was updated. Pending voter takes effect.
        if (delegated_votes.last_locked_until_secs < locked_until_secs) {
            delegated_votes.active_shares = delegated_votes.active_shares_next_lockup;
            delegated_votes.pending_inactive_shares = 0;
            delegated_votes.last_locked_until_secs = locked_until_secs;
        };
        delegated_votes
    }

    }
