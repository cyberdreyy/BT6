### Title
Fee-on-transfer underlying tokens over-mint strategy tokens and over-credit funded withdraw receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` assumes `safeTransferFrom(_amount)` delivers exactly `_amount` underlying. Two paths credit the full `_amount` while a fee-on-transfer (FOT) token (e.g. USDT with fees toggled on) delivers less: `deposit()` mints `_amount` strategy tokens 1:1, and `collectWithdrawFunds`/`collectInstantWithdrawFunds` mark `_amount` of receipts as funded while only `_amount - fee` arrives. `IdleCDOCreditVault._deposit` correctly mints tranche shares from the balance delta, so the mismatch is pushed entirely into the strategy layer, breaking the 1 strategy token : 1 underlying invariant used by `price()`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
- In `IdleCreditVault.deposit(uint256 _amount)` (only callable by the CDO), the strategy pulls `_amount` from the CDO and mints `_amount` strategy tokens to it. With a FOT token, the strategy receives `_amount - fee` but mints `_amount`, so CDO-held strategy tokens grow faster than real backing. The CDO meanwhile minted the user tranche shares priced on the *received* amount (`_contractTokenBalance(_token) - _preBal`), so the user is not over-credited — instead the strategy-token supply becomes permanently inflated relative to underlying actually held or lent, diluting all LPs on withdrawal. [4](#0-3) 
- In `collectWithdrawFunds(_amount)` / `collectInstantWithdrawFunds(_amount)`, `pendingWithdraws`/`pendingInstantWithdraws` are decremented by `_amount` (or a loss price is computed from `_amount`) and the strategy pulls `_amount` from the CDO — but only `_amount - fee` lands. Funded receipts are then claimable at par via `_transferFundedClaim`, so the aggregate claims exceed the actual balance; the last claimant(s) revert on `safeTransfer`. [5](#0-4) [6](#0-5) 
- Same pattern in `finalizeDefaultRecovery`: `defaultRecoveryReserve` is increased by `_recoveredAmount` while the pull delivers less, so recovery claims priced by `defaultRecoveryPrice` are underfunded. [7](#0-6) 
- Note the base `IdleCDO._deposit`/`IdleCDOCreditVault._deposit` already defend the share-mint leg by measuring the balance delta, confirming the intended invariant; the strategy leg simply wasn't given the same treatment. [8](#0-7) 

### Impact Explanation
Insolvency and theft/freezing of unclaimed yield. Each deposit with an active transfer fee mints `fee` unbacked strategy tokens to the CDO; since `price()` is fixed at `oneToken`, withdrawal requests and claims denominated in those unbacked tokens can only be paid by draining other participants' backing. For the collect path, the shortfall hits funded withdraw receipts directly: `pendingWithdraws` is cleared against a gross `_amount` while the vault holds `fee` less, so the last claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert — permanent freezing of their unclaimed funds unless the fee is turned off or someone donates. Loss equals the aggregate transfer fees; for a 1% USDT-style fee on a vault cycling deposits/withdrawals this compounds every epoch. [9](#0-8) 

### Likelihood Explanation
Medium. It requires the vault underlying to be or become a fee-on-transfer token — USDT has a togglable fee (currently 0) and is a plausible credit-vault pool currency, and the protocol's docs/tests reference USDT-style pools. No privileged attacker is needed: an unprivileged KYC'd lender simply calls `depositAA`/`depositBB` while the fee is active, and honest manager/borrower epoch calls (`stopEpoch` → `collectWithdrawFunds`) propagate the shortfall to receipt holders automatically. Existing guards don't help: `_guarded`, `whenNotPaused`, `_onlyIdleCDO`, and the reserve check in `_transferFundedClaim` all reason about nominal amounts, not received amounts. If the token never enables fees, impact is zero — hence not High.

### Recommendation
Measure actual received amounts everywhere instead of trusting `_amount`:
- In `deposit()`: `uint256 pre = underlyingToken.balanceOf(address(this)); safeTransferFrom(...); uint256 received = balanceOf - pre; _mint(msg.sender, received);` and update `totEpochDeposits` by `received`.
- In `collectWithdrawFunds`/`collectInstantWithdrawFunds` and `finalizeDefaultRecovery`: compute the funded amount from the balance delta and use it for `pendingWithdraws`/`lossRecoveryPrice`/`defaultRecoveryReserve` accounting.
- Alternatively, enforce at CDO/initialize time that `token` is not a FOT token (document the requirement), matching the already-implemented balance-delta pattern in `IdleCDO._deposit`.

### Proof of Concept
Foundry fork test sketch (USDT-style FOT mock or mainnet token with fee enabled):

```solidity
// Mock ERC20 with fee: transferFrom delivers amount - amount*feeBps/10_000
FeeToken usdt = new FeeToken(100); // 1% fee
// Deploy IdleCDOCreditVault + IdleCreditVault with token = usdt
// Lender deposits 1000e6 via depositAA:
cdo.depositAA(1000e6);
// CDO receives 990e6, mints tranche shares for 990e6 (correct)
// strategy.deposit(1000e6) pulls... if CDO holds >=1000e6 buffer it succeeds and
// mints 1000e6 strategy tokens -> 10e6 unbacked supply created.
assertEq(strategy.balanceOf(address(cdo)), 1000e6);
assertLt(usdt.balanceOf(address(strategy)) + lentAmount, 1000e6 - 10e6 /*fee*/);

// Epoch runs, borrower repays, manager stopEpoch -> collectWithdrawFunds(1000e6):
// vault receives 990e6 but pendingWithdraws cleared by 1000e6.
// Two users with 500e6 receipts each:
vm.prank(cdo); vault.claimWithdrawRequest(user1); // gets 500e6
vm.prank(cdo);
vm.expectRevert(); vault.claimWithdrawRequest(user2); // only 490e6 left -> frozen
```

The PoC needs a CDO buffer or prior balance for the deposit leg to succeed; the collect-leg shortfall reproduces unconditionally once any funded receipts exist.

  /// @notice collect borrower-funded withdraw receipt funds
  /// @dev Only IdleCDO can call this function. When `_amount` is lower than the
  /// pending basis, the difference is a stopEpochWithDuration loss assigned to
  /// pending receipts and users later claim through `lossRecoveryPriceByEpoch`.
  /// Reverts if the resulting recovery price rounds to zero at `RECOVERY_FULL` precision.
  /// @param _amount number of funded tokens to collect
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
