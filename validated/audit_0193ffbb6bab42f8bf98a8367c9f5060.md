### Title
Authorization cached at request time is reused for claim, letting a de-whitelisted wallet withdraw funds - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The qSnapper bug caches an authentication/authorization result obtained for one polkit method and incorrectly reuses it for a different, more privileged method. The direct analog exists in `IdleCDOEpochQueue`: Keyring/KYC authorization is checked once in `requestWithdraw`/`requestDeposit` via `_checkAllowed`, but the separate claim methods `claimWithdrawRequest` and `claimDepositRequest` perform no authorization check at all. A wallet that was authorized when the request was queued, but whose credential is later revoked (or which acquired tranche tokens without ever passing KYC via the unprotected `createWriteOffRequest`/`fullfillWriteOffRequest` path in `IdleCreditVaultWriteOffEscrow`), can still pull underlyings out of the queue — an authorization decision made for one action ("queue a request") is silently reused for a different action ("take delivery of funds").

### Finding Description
`requestWithdraw` calls `_checkAllowed(msg.sender)`, which enforces `isEpochRunning()` and `cdoEpoch.isWalletAllowed(wallet)` (Keyring `checkCredential`). [1](#0-0) [2](#0-1) 

`claimWithdrawRequest` only validates epoch price/pending-claims state and the user's recorded request balance — it never calls `isWalletAllowed`. [3](#0-2)  `claimDepositRequest` has the same gap. [4](#0-3) 

The same split-check pattern exists one level up: `IdleCDOEpochVariant._deposit` and `depositDuringEpoch` enforce `isWalletAllowed(msg.sender)`, while `claimWithdrawRequest`/`claimInstantWithdrawRequest` forward to `IdleCreditVault` without a wallet check. [5](#0-4) [6](#0-5) 

Additionally, `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` and `fullfillWriteOffRequest` contain no `isWalletAllowed` check at all, so a non-KYC tranche holder can escrow tranche tokens and receive underlyings (minus `exitFee`) from any fulfiller — confirmed by the protocol's own test `testNonKeyringBuyerCanFulfillExistingRequestButCannotWithdraw`, which asserts the non-KYC buyer is only blocked on `requestWithdraw`, not on escrowed exits. [7](#0-6) [8](#0-7) 

### Impact Explanation
The access-control invariant ("only Keyring-credentialed wallets move value in/out of the vault") is broken because authorization is bound to the *request* transaction rather than the *settlement* transaction. Two concrete violations:

1. A lender whose Keyring credential is revoked or expires after `requestWithdraw` still executes `claimWithdrawRequest` and receives underlyings, even though `keyringAllowWithdraw`-style gating intends withdrawals to require standing credentials.
2. A never-authorized wallet holding tranche tokens (e.g., received via permissionless ERC20 `transfer`, which does not check `isWalletAllowed`) cannot call `requestWithdraw` but can fully exit via `createWriteOffRequest` + a third-party `fullfillWriteOffRequest`, converting tranche tokens into underlyings — i.e., the escrow is an unchecked alternative withdrawal rail.

Funds leaving the queue/escrow to non-credentialed addresses undermine the compliance perimeter the contract itself enforces on the deposit/request side.

### Likelihood Explanation
Requires only ordinary, unprivileged conditions: Keyring credentials are time-bounded and routinely revoked/expire between epoch request (during a running epoch) and claim (next buffer period), so scenario 1 triggers without any attacker sophistry. Scenario 2 requires a willing fulfiller, which the contract explicitly permits ("this function can be called by any wallet"), and the borrower is a standing fulfiller candidate. The gap is deterministic — there is no race or economic precondition, just a missing check.

### Recommendation
Re-validate authorization at settlement: call `IdleCDOEpochVariant(idleCDOEpoch).isWalletAllowed(msg.sender)` inside `claimWithdrawRequest` and `claimDepositRequest` in `IdleCDOEpochQueue` (honoring any `keyringAllowWithdraw` flag semantics used elsewhere), add the same check in `IdleCDOEpochVariant.claimWithdrawRequest`/`claimInstantWithdrawRequest`, and add `isWalletAllowed` checks to `IdleCreditVaultWriteOffEscrow.createWriteOffRequest` and `fullfillWriteOffRequest`. Do not let a credential validated for one method implicitly authorize a different method in a later epoch phase.

### Proof of Concept
Foundry fork PoC (mock Keyring as in existing tests):

```solidity
// Setup: epoch running, user is KYC'd (checkCredential -> true)
vm.prank(user);
queue.requestWithdraw(amount);          // _checkAllowed passes

// Epoch stops, processWithdrawRequests runs, epochWithdrawPrice set
_stopCurrentEpoch();

// Credential revoked before claim
vm.mockCall(keyring, abi.encodeWithSelector(IKeyring.checkCredential.selector), abi.encode(false));
assertFalse(cdoEpoch.isWalletAllowed(user));

// BUG: claim still succeeds — auth was cached at request time
vm.prank(user);
queue.claimWithdrawRequest(epoch);       // no isWalletAllowed check -> underlyings paid out
assertGt(underlying.balanceOf(user), balPre);
```

Escrow variant: `deal` tranche tokens to a non-KYC `buyer`, `buyer.createWriteOffRequest(...)`, third party calls `fullfillWriteOffRequest`, `buyer` receives underlyings despite `isWalletAllowed(buyer) == false`.

Caveat: I verified the missing checks in `IdleCDOEpochQueue`, `IdleCDOEpochVariant`, and `IdleCreditVaultWriteOffEscrow` directly, but did not read `IdleCreditVault.claimWithdrawRequest`'s internals in full (grep hit count only) — if that function enforces `isWalletAllowed` internally, the queue claim path may already be partially defended downstream, and the escrow path would remain the cleanest analog.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
