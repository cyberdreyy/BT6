### Title
Single-slot miner can perpetually forge "activity" via duplicate/stale block proposals to prevent signer fallback to a new miner, wedging the tenure-fallback state machine - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` records any proposal that fails to advance the tenure's known chain-length as valid "miner activity" whenever the tenure's last known block has not yet crossed the `signed_group`/global-acceptance freshness window. A miner can exploit this the same way the SiloAMO attacker exploited a permissionless `update()` call: cheaply and repeatedly re-broadcast a stale/duplicate proposal (an action that costs the attacker almost nothing and needs no majority) to keep resetting `last_activity_time` for its own tenure, thereby defeating `SortitionState::is_timed_out` and blocking the signer set's fallback to the prior miner indefinitely — a pure liveness wedge triggerable by a lone block-slot winner via gossip.

### Finding Description
`get_tenure_last_block_info` in `stacks-signer/src/chainstate/mod.rs` returns the tenure's last *signed* block only while it is "fresh" (within `tenure_last_block_proposal_timeout` of `signed_self`/`signed_group`) [1](#0-0) .

`check_latest_block_in_tenure` uses that result to decide whether an incoming proposal is stale (`chain_length <= info.chain_length`). When it is stale, the code decides whether to still count it as valid miner activity:

```
if info.signed_group.is_none_or(|signed_time| {
    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
}) {
    // Note if there is no signed_group time, this is a locally accepted block ...
    // Treat any attempt to reorg a locally accepted block as valid miner activity.
    ...
    signer_db.update_last_activity_time(&block.header.consensus_hash, get_epoch_time_secs())
}
return Ok(false);
``` [2](#0-1) 

Critically, `info.signed_group.is_none()` is true whenever the tenure's last known block is only **locally** accepted — i.e. it has not (yet, or ever) crossed the 70% signature threshold. In that branch the code unconditionally treats *any* stale/duplicate proposal from the current miner as fresh "activity," with no additional freshness bound.

`SortitionState::is_timed_out` (v1) determines whether the current miner has gone inactive by comparing `now` against `get_last_activity_time`, defaulting to the burn-block-receive time only if no activity record exists, and returns `false` (not timed out) whenever a signature already exists in the tenure — but a block that is only "locally accepted" (not globally) still updates the same activity clock via `check_latest_block_in_tenure` [3](#0-2) . `check_miner_inactivity` in `stacks-signer/src/v0/signer_state.rs` is the only path that falls back to the prior tenure's miner, and it only does so if `is_timed_out` returns true [4](#0-3) .

This mirrors the SiloAMO bug class exactly: a single actor (there, an attacker funding their own borrow; here, the block-slot-winning miner) can manipulate a state variable that gates a protective check (`totalBorrows`/interest rate there; `last_activity_time`/timeout here) using cheap, self-funded, non-majority actions (a borrow+repay in one block there; a duplicate/no-op block proposal broadcast here), baiting the system into a decision (deposit more funds there; treat the miner as "active" here) that then persists for an extended, disproportionate window (the `updateInterval`/1 day there; the full `block_proposal_timeout` window here, renewable indefinitely).

Concretely: if the miner's own last proposed block never gathers a 70%-weight signature quorum (e.g., because the miner deliberately withholds broadcasting it widely, some signers are slow/offline, or the miner just proposes then stops), `info.signed_group` stays `None` forever. The miner can then repeatedly re-broadcast the exact same (or any lower/duplicate) block proposal. Each such rejected proposal still calls `update_last_activity_time`, resetting the inactivity clock that `check_miner_inactivity`/`is_timed_out` rely on. As a result, `check_miner_inactivity` never observes an elapsed gap exceeding `block_proposal_timeout`, and the signer set never falls back to `last_sortition`'s miner, even though the current miner is not actually producing chain progress.

### Impact Explanation
This wedges the tenure-fallback path of the signer state machine: the current miner can hold signers hostage on a tenure that is not advancing (no new globally-signed blocks), while blocking the designed recovery mechanism (`check_miner_inactivity` → fallback to prior tenure/miner) that exists specifically to recover liveness when a miner stalls. This is a liveness bug within the allowed impact class "a signer wedged into never signing valid blocks" — here, wedged into never *considering* an alternate, live miner's blocks, since `check_proposal` in `chainstate/v1.rs` rejects proposals from anything other than `cur_sortition`/`last_sortition` unless the current miner is marked invalid via the inactivity fallback [5](#0-4) . The exploit requires no majority of signers, no other signer's key, and no auth token — only the current block-slot miner's own gossip of duplicate proposals, matching the required threat model.

### Likelihood Explanation
Likelihood is moderate-to-high for a malicious or compromised current-tenure miner: the action (re-sending a proposal that's already known and stale) is cheap, requires no chain interaction, and the vulnerable branch (`info.signed_group.is_none()`) is reached whenever a proposal has not yet been globally accepted — a normal and common state during any period of network partition, slow signer participation, or deliberate miner throttling of broadcast. No cryptographic or economic cost is incurred beyond the negligible cost of authoring/signing one block header once.

### Recommendation
Bound the "treat stale proposal as activity" branch by an independent, monotonically-advancing freshness check similar to `reorg_attempts_activity_timeout`, but keyed off of when the *tenure itself* was first observed (e.g., `get_burn_block_receive_time_ch`) rather than being re-armable indefinitely by the same-height duplicate proposals from the same miner. Concretely, only credit "activity" once per distinct proposed block height/hash per some minimum interval, or require that the proposal be for a strictly higher `chain_length` than any previously-credited "activity" proposal, so that the miner cannot indefinitely refresh the clock by re-sending the same non-advancing block.

### Proof of Concept
Conceptual reproduction (would need to be validated in a live/integration harness such as `stacks-node/src/tests/signer/v0/mod.rs`):
1. Miner wins a sortition, proposes block N (tenure T). Signers locally accept N but the 70% signature threshold is never reached (e.g., simulate 40% of signers offline or slow).
2. `get_tenure_last_block_info(T, ...)` returns `block_info` for N with `signed_group == None`.
3. Miner (or anyone able to gossip on its behalf under its signature) re-broadcasts the *same* block N (or another block with `chain_length <= N.chain_length`) as a "new" proposal repeatedly, spaced less than `block_proposal_timeout` apart.
4. Each time, `check_latest_block_in_tenure` hits `info.signed_group.is_none()` → true → calls `signer_db.update_last_activity_time(T, now)` and returns `Ok(false)` (rejected, but activity recorded).
5. `SortitionState::is_timed_out(T, ...)` never exceeds `block_proposal_timeout` because `last_activity_time` keeps advancing.
6. `check_miner_inactivity` therefore never falls back to `last_sortition`'s miner, even though tenure T is stalled and no new globally-accepted block has appeared for an arbitrarily long time.

Note: I was unable to fully trace the exact call site in `stacks-signer/src/v0/signer.rs` where `check_latest_block_in_tenure` is invoked during proposal handling due to reaching the tool-call limit; the semantics above are derived directly from `check_latest_block_in_tenure`'s own doc comment ("This updates the activity timer for the miner of `block`") and its callers/tests in `stacks-signer/src/chainstate/tests/v2.rs`, but a live-network confirmation of the exact broadcast/replay path would strengthen the PoC.

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
