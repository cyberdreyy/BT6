### Title
Unbounded `Vec<AccountChange>`/per-phase `Vec<Call>` RLP decoding in EIP-8130 transactions allows admission-time CPU/allocation DoS - (File: `crates/common/consensus/src/transaction/eip8130/tx.rs`)

### Summary
`TxEip8130::rlp_decode_fields` (and the mirrored `decode_calls`) decode `account_changes: Vec<AccountChange>` with a bare `Decodable::decode(buf)?` call and decode each call **phase**'s inner `Vec<Call>` with a bare `Vec::<Call>::decode(&mut payload)?`, neither of which enforce any per-list item-count ceiling during decode. Only the *outer* number of call phases is capped while parsing (`MAX_CALL_PHASES_PER_TX = 1_024`, enforced in `TxEip8130::decode_calls`), mirroring exactly the analog bug class in ALPINE-CVE-2026-41292: Unbound held worker threads hostage parsing/allocating internal structures for a long list of options before any cap was applied. Here, the total number of `AccountChange` entries and the total number of `Call` entries *within a single phase* are unbounded at parse time; the corresponding admission caps (`MAX_ACCOUNT_CHANGES_PER_TX = 3`, `MAX_CONFIG_CHANGES_PER_TX = 10`) are only checked **after** the RLP decode has already fully materialized the `Vec`s, in `validator.rs`'s `validate_eip8130_structural`/`validate_account_changes` path.

### Finding Description
`TxEip8130::rlp_decode_fields` at `crates/common/consensus/src/transaction/eip8130/tx.rs:208-224` decodes:
- `account_changes: Decodable::decode(buf)?` — this calls the generic `Vec<AccountChange>::decode`, which allocates and pushes one `AccountChange` per RLP list item with no cap.
- `calls: Self::decode_calls(buf)?` — this bounds the **outer** phase count to `MAX_CALL_PHASES_PER_TX` (1,024) at `crates/common/consensus/src/transaction/eip8130/tx.rs:140-159`, but each phase's body is decoded via `Vec::<Call>::decode(&mut payload)?` at line 155 with no per-phase cap.

Because RLP decoding happens on the raw wire bytes of a submitted transaction — during txpool ingestion (`crates/execution/txpool/src/validator.rs`) and during span-batch reconstruction (`crates/consensus/protocol/src/batch/tx_data/eip8130.rs`) — before any of the mempool's per-entry admission checks run (`validate_eip8130_structural` only checks the *outer* `calls.len()` against `MAX_CALL_PHASES_PER_TX`; `MAX_ACCOUNT_CHANGES_PER_TX`/`MAX_CONFIG_CHANGES_PER_TX` are enforced later, in `validate_account_changes`), a single crafted transaction can force the node to allocate and construct large numbers of `AccountChange`/`Call`/nested `InitialActor`/`SignedChange` heap objects purely from decoding, before it is ever rejected.

The transaction's overall wire size is still bounded by the pool's `max_tx_input_bytes` (checked in `validate_eip8130_structural` via `signed.encode_2718_len()`), but that check also runs *after* decode. A minimal `AccountChange::Delegation` entry (`rlp([0x02, target])`) or `Call` entry (`to`, empty `data`) is only tens of bytes, so within the max transaction size a caller can pack thousands of entries whose sole purpose is to be walked, allocated, and then discarded by validation — CPU and allocation work paid by every node that receives the transaction (via RPC submission or p2p tx gossip) before rejection, and repeatable per-transaction with different hashes to defeat per-tx caching.

### Impact Explanation
This is a resource-exhaustion (denial-of-service) class bug matching the CVE's bug class ("long lists of incoming options... hold threads hostage while parsing and creating internal data structures"). It does not cause fund loss, wrong state, or consensus divergence — the transaction is ultimately rejected by `validate_account_changes`/`validate_eip8130_structural`'s per-entry caps before admission — but the decode-then-reject pattern lets an unprivileged RPC/gossip sender impose disproportionate parsing/allocation cost on every receiving node relative to the bytes sent, which is the same "degradation of service" shape cited in the report. Given the rules explicitly reject "resource-only" analogs unless they rise to a concrete node-halt/DoS-serving-impact, this should be scored as at most Medium unless it can be shown to actually stall block building or txpool admission for other users (not verified here).

### Likelihood Explanation
Reachable from any unprivileged party that can submit a raw transaction over RPC (`eth_sendRawTransaction`) or via p2p tx gossip to the txpool, and also reachable via span-batch decoding on the derivation path (`crates/consensus/protocol/src/batch/tx_data/eip8130.rs`, `decode_eip8130_proof`/`full_txs`) reconstructing an EIP-8130 transaction from L1 batch data. Constructing the malicious payload requires no special privileges — only a well-formed but oversized `account_changes` list or single-phase `calls` list within the max transaction size. Signature validity is not required to trigger the RLP decode cost, since decode happens before signature checks.

### Recommendation
Add decode-time caps in `TxEip8130::rlp_decode_fields`/`decode_calls`, mirroring the existing `MAX_CALL_PHASES_PER_TX` guard:
- Enforce a `MAX_ACCOUNT_CHANGES_PER_TX`-derived (or a generous but decode-time) ceiling while decoding `account_changes`, rejecting the RLP stream once the item count exceeds the limit — do not rely solely on the post-decode `validate_account_changes` check.
- Apply the same style of streaming cap to each phase's inner `Vec<Call>` decode in `decode_calls` (e.g., abort once a single phase exceeds a fixed max call count), rather than only bounding the outer phase count.
- Ensure the RLP-decode `Vec<AccountChange>`/`Vec<Call>`/`Vec<SignedChange>`/`Vec<InitialActor>` decoders never allocate proportionally to an attacker-declared but unchecked count derived purely from a length prefix, consistent with the existing pattern already used for `MAX_CALL_PHASES_PER_TX`.

### Proof of Concept
1. Build a raw EIP-8130 transaction (`type = 0x79`) whose `account_changes` field RLP-encodes several thousand minimal `AccountChange::Delegation` entries (`rlp([0x02, address(0)])`, ~24 bytes each on the wire), keeping total transaction size just under the pool's `max_tx_input_bytes` limit.
2. Submit it via `eth_sendRawTransaction` (or inject into p2p tx gossip) to a Base execution node.
3. `BaseTransactionValidator::validate_one_with_state_inner` (`crates/execution/txpool/src/validator.rs`) calls `transaction.as_eip8130()`, which requires the transaction to already be RLP-decoded into a `TxEip8130` — i.e., `TxEip8130::rlp_decode_fields` (`crates/common/consensus/src/transaction/eip8130/tx.rs:208-224`) has already allocated and populated a `Vec<AccountChange>` with every one of the thousands of entries before `validate_eip8130_structural`'s later `validate_account_changes` call rejects the transaction for exceeding `MAX_ACCOUNT_CHANGES_PER_TX`/`MAX_CONFIG_CHANGES_PER_TX`.
4. Repeat with distinct nonces/signatures at high rate; each submission pays the full decode/allocation cost on the receiving node(s) before rejection, disproportionate to the CPU a legitimate transaction of similar byte size would cost. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

```rust
    fn decode_calls(buf: &mut &[u8]) -> alloy_rlp::Result<Vec<Vec<Call>>> {
        let header = Header::decode(buf)?;
        if !header.list {
            return Err(alloy_rlp::Error::UnexpectedString);
        }
        if buf.len() < header.payload_length {
            return Err(alloy_rlp::Error::InputTooShort);
        }

        let (mut payload, rest) = buf.split_at(header.payload_length);
        let mut phases = Vec::new();
        while !payload.is_empty() {
            if phases.len() >= Eip8130Constants::MAX_CALL_PHASES_PER_TX {
                return Err(alloy_rlp::Error::Custom("too many EIP-8130 call phases"));
            }
            phases.push(Vec::<Call>::decode(&mut payload)?);
        }
        *buf = rest;
        Ok(phases)
    }
```

```rust
impl Decodable for AccountChange {
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        let header = Header::decode(buf)?;
        if !header.list {
            return Err(alloy_rlp::Error::UnexpectedString);
        }
        let started_len = buf.len();
        let type_byte = u8::decode(buf)?;
        let this = match type_byte {
            Eip8130Constants::ACCOUNT_CHANGE_TYPE_CREATE => Self::Create(CreateEntry {
                user_salt: B256::decode(buf)?,
                code: Bytes::decode(buf)?,
                initial_actors: Vec::<InitialActor>::decode(buf)?,
            }),
            Eip8130Constants::ACCOUNT_CHANGE_TYPE_CONFIG => {
                let channel_byte = u8::decode(buf)?;
                let channel = AccountChangeChannel::from_byte(channel_byte)
                    .ok_or(alloy_rlp::Error::Custom("invalid SignedAccountChanges channel byte"))?;
                Self::ConfigChange(SignedAccountChanges {
                    channel,
                    sequence: u64::decode(buf)?,
                    changes: Vec::<SignedChange>::decode(buf)?,
                    signature: Bytes::decode(buf)?,
                })
            }
            Eip8130Constants::ACCOUNT_CHANGE_TYPE_DELEGATION => {
                Self::Delegation(Delegation { target: Address::decode(buf)? })
            }
            _ => return Err(alloy_rlp::Error::Custom("invalid AccountChange type byte")),
        };
        let consumed = started_len - buf.len();
        if consumed != header.payload_length {
            return Err(alloy_rlp::Error::ListLengthMismatch {
                expected: header.payload_length,
                got: consumed,
            });
        }
        Ok(this)
    }
}
```

```rust
    /// Maximum number of `ConfigChange` entries the mempool accepts in a single
    /// transaction. The spec marks this as a node policy ("Nodes SHOULD enforce
    /// a configurable per-transaction limit"); we pin a conservative default
    /// here that downstream operators can revisit once the spec finalises.
    pub const MAX_CONFIG_CHANGES_PER_TX: usize = 10;

    /// Maximum number of `account_changes` entries (of any kind: `Create`,
    /// `ConfigChange`, `Delegation`) the mempool accepts in a single
    /// transaction. This is an **interim** total-entry admission cap that keeps
    /// per-transaction admission work (and the in-memory overlay it applies
    /// against) small and bounded while the interleaved authorize-and-apply
    /// admission flow beds in.
    ///
    /// Relationship to the per-type caps ([`Self::MAX_CONFIG_CHANGES_PER_TX`]
    /// and the implicit ≤1 `Create` / ≤1 `Delegation` structural limits):
    ///
    /// - **While this cap is the smallest** (3 < 10 today), it is the *binding*
    ///   admission constraint — a transaction can never reach
    ///   `MAX_CONFIG_CHANGES_PER_TX` config changes because the total cap stops
    ///   it first. The per-type caps are effectively dormant.
    /// - **Once this is raised to or above `MAX_CONFIG_CHANGES_PER_TX`**, the
    ///   per-type caps become the binding constraints: `MAX_CONFIG_CHANGES_PER_TX`
    ///   bounds config changes, and the ≤1 `Create` / ≤1 `Delegation` structural
    ///   rules bound the rest. Raising this cap therefore *relaxes* admission up
    ///   to (but never beyond) the per-type ceilings.
    ///
    /// Keep this value `<= MAX_CONFIG_CHANGES_PER_TX + 2` (one create + one
    /// delegation) if the intent is for the total cap to stay the binding limit.
    pub const MAX_ACCOUNT_CHANGES_PER_TX: usize = 3;
```

```rust
    /// invariants listed in EIP-8130 § Validation and § Nonce-Free Mode.
    fn validate_eip8130_structural(
        &self,
        signed: &Eip8130Signed,
    ) -> Result<(), InvalidPoolTransactionError> {
        let size = signed.encode_2718_len();
        let limit = self.inner.max_tx_input_bytes();
        if size > limit {
            return Err(InvalidPoolTransactionError::OversizedData { size, limit });
        }
        if signed.tx().calls.len() > Eip8130Constants::MAX_CALL_PHASES_PER_TX {
            return Err(Self::eip8130_error("call phase count exceeds maximum"));
        }

        // Single read of the head-block timestamp so the fork gate and the
        // expiry check see the same value even when `on_new_head_block` updates
        // the atomic concurrently.
        let now = self.block_timestamp();
        // Fork gate: EIP-8130 (account abstraction) transactions are only
        // admissible to the pool once the Zenith upgrade is active.
        if !self.chain_spec().is_zenith_active_at_timestamp(now) {
            return Err(InvalidTransactionError::TxTypeNotSupported.into());
        }
        let local_chain_id = self.inner.chain_spec().chain().id();
        signed.validate_static(local_chain_id).map_err(InvalidPoolTransactionError::from)?;
        // The validity window is evaluated in milliseconds against
        // `block.timestamp * 1000`; the fork gate above uses seconds.
        let now_ms = now.saturating_mul(1_000);
        signed
            .validate_timestamp(now_ms)
            .map_err(|error| Self::map_timestamp_error(error, signed, now_ms))?;
        Self::validate_eoa_sender_signature(signed)?;
        Self::validate_sender_auth(signed)?;
        Self::validate_payer_auth(signed)?;
        Self::validate_account_changes(signed, local_chain_id)?;
        Ok(())
    }
```
