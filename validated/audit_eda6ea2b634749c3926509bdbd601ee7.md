### Title
`startEpoch` permanently reverts when the programmable borrower's ERC4626 vault deposit fails, freezing all pool funds in the buffer phase - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external report describes a bridge adapter whose `lzCompose` calls an uncaught `deposit()` on an exchange; if deposits are ever disabled, the message fails forever and the bridged funds stay frozen. The same bug class exists in the programmable-borrower path of idle-tranches: `IdleCDOEpochVariant.startEpoch` → `ProgrammableBorrower.onStartEpoch` → `_depositToVault` → `vault.deposit(...)` with no `try/catch`. An unprivileged user of that ERC4626 vault can make `deposit` revert (e.g., fill the vault's deposit cap, or inflate the share price so a small deposit mints zero shares), after which every `startEpoch` call reverts and the pool can never leave the buffer phase. All LP principal is frozen for as long as the condition persists.

### Finding Description
In `contracts/IdleCDOEpochVariant.sol`, `startEpoch` sends epoch deposits and interest to the strategy, then either (a) when `pendingInstant > totUnderlyings`, calls `_startEpochProgrammableBorrower(_pendingWithdraws)` bare at line 288, or (b) calls `this.sendFundsToBorrower(_toBorrower)` in a `try` and then `_startEpochProgrammableBorrower` inside the try block at lines 295–297 [1](#0-0) . Note the `try/catch` only wraps the external `sendFundsToBorrower` call; a revert inside the try block (from `onStartEpoch`) propagates and reverts the whole `startEpoch` — there is no catch path for the hook itself.

`_startEpochProgrammableBorrower` calls `IProgrammableBorrower(_borrower()).onStartEpoch(_pendingWithdraws)` [2](#0-1) . Inside `ProgrammableBorrower.onStartEpoch`, `_depositToVault(underlyingToken.balanceOf(address(this)), 0)` is invoked unconditionally, and `_depositToVault` performs a raw `vault.deposit(_assetAmount, address(this))` with no `try/catch` and no opt-out [3](#0-2) [4](#0-3) .

Unlike `onStopEpoch`, which deliberately wraps `vault.withdraw` in `try/catch` to keep `stopEpoch` retryable [5](#0-4) , `onStartEpoch` has no such guard. Any revert in `vault.deposit` therefore bricks `startEpoch` itself.

Concrete attacker path (buffer phase, programmable mode):
1. Pool finishes an epoch; owner/manager is expected to call `startEpoch` during the buffer. Idle cash sits on `ProgrammableBorrower` (or arrives via `sendFundsToBorrower`).
2. An unprivileged attacker — any user of the configured ERC4626 vault — deposits into the vault until its deposit cap/`maxDeposit` is reached (or donates underlying to inflate `convertToAssets` so the incoming deposit mints zero shares on vaults that revert on zero-share mints).
3. `startEpoch` is called: `sendFundsToBorrower` succeeds, then `onStartEpoch` → `vault.deposit` reverts → entire `startEpoch` reverts. Every retry reverts while the cap remains saturated. Because `isEpochRunning` was never set... actually `_pause()` and flag updates at lines 244–250 also roll back, so the pool stays in buffer — but no epoch can start, no interest accrues, and withdraw-request claims that require a started/stopped epoch are blocked.

The same freeze applies in the `pendingInstant > totUnderlyings` branch where the hook is called with no wrapper at all.

### Impact Explanation
Temporary freezing of funds equal to the entire pool TVL. While `startEpoch` reverts: LP principal cannot enter a new epoch, normal withdraw requests cannot be fulfilled (they settle at the next `stopEpoch`), and new deposits are pointless. The freeze lasts as long as the vault deposit reverting condition persists; recovery requires owner intervention via `setVault` (which itself is gated on `vault.balanceOf(address(this)) == 0` and inactive accounting) [6](#0-5) . This is exactly the report's impact class — funds stuck because an uncaught external deposit failure makes the orchestrating call permanently revertible.

### Likelihood Explanation
Likelihood depends on the chosen ERC4626 vault having a manipulable deposit failure mode: deposit caps, pausable vaults, or zero-share-mint reverts after a donation are all common and are reachable by an unprivileged vault user (explicitly in scope per the rules). The cost to the attacker is only temporarily parking capital in the vault's cap. No privileged role needs to misbehave — owner/manager remain honest and simply cannot get `startEpoch` through.

### Recommendation
Mirror the `onStopEpoch` pattern: wrap the vault deposit in `ProgrammableBorrower.onStartEpoch` (or wrap `_startEpochProgrammableBorrower` as an external self-call in `IdleCDOEpochVariant`) with `try/catch`. On deposit failure, keep the idle cash on the `ProgrammableBorrower` contract (it is already included in `totalUnderlying()`/`availableToBorrow()` accounting) and emit an event, so `startEpoch` can complete and the deposit can be retried later via a permissioned `depositIdleToVault`-style function.

### Proof of Concept
Foundry fork sketch:

```solidity
// Setup: IdleCDOEpochVariant (programmable mode) + ProgrammableBorrower + CappedVault (ERC4626 with maxDeposit cap)
// 1. Run one normal epoch so pool enters buffer with deposits/interest pending.
// 2. Attacker (unprivileged): cappedVault.deposit(cap - dust, attacker) — fills maxDeposit.
// 3. owner: cdo.startEpoch(duration) -> sendFundsToBorrower succeeds -> onStartEpoch ->
//    _depositToVault -> vault.deposit reverts (cap exceeded) -> startEpoch reverts.
vm.expectRevert(); // vault cap revert bubbles up
cdo.startEpoch(epochDuration);
// 4. Assert freeze: isEpochRunning == false after every retry while cap is saturated;
//    pending withdraw requests cannot be claimed; LP funds idle.
assertFalse(cdo.isEpochRunning());
```

The PoC reproduces cleanly whenever `vault.deposit` can revert under unprivileged influence; the missing `try/catch` is the defect, independent of which revert reason the vault uses.

  function setVault(address _vault) external {
    _checkOnlyOwnerOrManager();
    if (_vault == address(0) || IERC4626(_vault).asset() != address(underlyingToken)) {
      revert InvalidAddress();
    }
    // Switching the accounting source is only safe once the current epoch is fully settled and the

    if (epochAccountingActive || vault.balanceOf(address(this)) != 0) revert NotAllowed();
    underlyingToken.safeApprove(address(vault), 0);
    vault = IERC4626(_vault);
    _allowUnlimitedSpend(address(underlyingToken), _vault);
    emit VaultUpdated(_vault);
