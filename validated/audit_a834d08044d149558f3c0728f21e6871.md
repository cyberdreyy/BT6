## Finding

### Title
Multisig confirmation count is not revalidated against live membership, allowing requests to execute below the configured `K`-of-`N` threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` decides whether to execute a request purely by comparing the *size* of the stored confirmation set to `num_confirmations`. `delete_member` only purges confirmations/requests that were *authored* by the removed member; it does not scan other pending requests to strip out confirmations that the removed member previously cast. A confirmation recorded by a member who is later removed therefore keeps counting toward the threshold forever, letting a smaller set of *currently live* members execute a request that nominally required more signers.

### Finding Description
The relevant binding the multisig is supposed to enforce is:

```
confirmations(request) ⊆ members(now)  AND  |confirmations(request)| ≥ num_confirmations
```

`confirm()` only checks the second half of this equality/inequality: [1](#0-0) 

It never re-validates that every account/key already present in `confirmations` is still an element of `self.members`.

`delete_member` removes a departing member and cleans up only the *requests that member authored* (`r.member == member`), plus that member's `num_requests_pk` entry and access key. It does **not** iterate `self.confirmations` to strip the departing member's entry from confirmation sets of requests authored by *other* members: [2](#0-1) 

Confirmations are recorded as plain strings in a `HashSet<String>` keyed by `MultisigMember::to_string()`, with no timestamp or liveness check tied back to `self.members`: [3](#0-2) 

Consequently, a confirmation cast while a member was still active survives that member's removal and continues to satisfy the numeric threshold check in `confirm()`.

### Impact Explanation
This breaks the core custody guarantee of the multisig: "a multisig request executed below threshold" (Critical, per the impact taxonomy). A pending `Transfer`/`FunctionCall`/`DeployContract` request that has a stale confirmation from a now-removed member needs strictly fewer *live* confirmations than `num_confirmations` to execute — funds can move (or code can be deployed/keys added) with less real authorization than the configured `K` requires. Because `delete_member` still enforces `members.len() - 1 >= num_confirmations` (line 357-360) on the *membership count*, operators reasonably assume `K`-of-`N` is preserved after any removal; this stale-confirmation gap silently violates that assumption.

### Likelihood Explanation
This does not require any protocol-level forgery — it only requires normal multisig operation: a member confirms a pending request, is later removed through the (also-multisig-gated) `DeleteMember` action, and the remaining live members confirm the still-pending request. Because member turnover (key rotation, offboarding, compromise response) is an expected operational event for any long-lived multisig, and because nothing in the contract warns operators to manually purge stale confirmations, this is a realistic operational trap rather than a theoretical edge case.

### Recommendation
In `confirm()`, before counting/using `confirmations`, filter the set to members currently in `self.members` (or eagerly purge non-member entries), and use the filtered length against `num_confirmations`. Additionally, `delete_member` should scan `self.confirmations` for every open request and remove the departing member's entry, not just requests it authored.

### Proof of Concept
1. Initialize with members `{A, B, C, D}`, `num_confirmations = 3` via `MultiSigContract::new` (`multisig2/src/lib.rs:147-167`).
2. `B` calls `add_request(Transfer{...})` → request `R` created, confirmations `{}`.
3. `A` calls `confirm(R)` → confirmations `{A}` (1/3, not yet executed).
4. `B` calls `confirm(R)` → confirmations `{A, B}` (2/3, not yet executed) — `confirm` logic at `multisig2/src/lib.rs:294-315`.
5. Members `B, C, D` separately raise and confirm a `DeleteMember{member: A}` request (3 confirmations, satisfies the current threshold) which executes `delete_member` (`multisig2/src/lib.rs:356-379`). This removes `A` from `self.members` and deletes any requests *authored by* `A`, but `R` (authored by `B`) is untouched, and `R`'s confirmation set still contains `A`.
6. `C` calls `confirm(R)`. `confirmations.len() == 2`, `+1 == 3 >= num_confirmations(3)` → `execute_request(R)` runs the transfer.
7. Result: the transfer executed with confirmations from only `B` and `C` — two *live* members — while `A`'s stale, pre-removal confirmation was counted as the third, even though the multisig was configured to require 3 live signers.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
