### Title
Missing role guard on GET /v2/external_initiators leaks every ExternalInitiator's AccessKey and OutgoingToken to any authenticated user, including view-role - ([File: core/web/router.go], [File: core/web/external_initiators_controller.go])

### Summary
`ExternalInitiatorsController.Index` is registered without any role wrapper (`paginatedRequest(eia.Index)`), unlike `Create`/`Destroy` which require `auth.RequiresEditRole`. Because `bridges.ExternalInitiator` stores `OutgoingToken` (and `AccessKey`) in plaintext and `presenters.NewExternalInitiatorResource` serializes `OutgoingToken`/`AccessKey` for every record, any authenticated user - even the lowest-privileged `view` role - can list and read every external initiator's `AccessKey` and `OutgoingToken`, not just their own.

### Finding Description
The route is wired as: [1](#0-0) [1](#0-0) 

Compare `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` (no role check) with `authv2.POST("/external_initiators", auth.RequiresEditRole(eia.Create))` and `authv2.DELETE(..., auth.RequiresEditRole(eia.Destroy))`. `Index` is reachable by anyone who passes `AuthenticateByToken`/`AuthenticateBySession` regardless of role.

`Index` returns every external initiator record via the presenter, which includes `AccessKey` and `OutgoingToken` in plaintext for each entry: [2](#0-1) [3](#0-2) 

The underlying model stores `AccessKey`, `OutgoingSecret`, and `OutgoingToken` in plaintext (only `HashedSecret`/`Salt` are hashed), so nothing prevents them from being echoed back on read: [4](#0-3) 

The existing test confirms `OutgoingToken` and `AccessKey` are returned for both initiators in the paginated Index response with no per-role restriction and no ownership filtering: [5](#0-4) 

Note: `OutgoingSecret` itself is **not** included in `ExternalInitiatorResource` (only `ExternalInitiatorAuthentication`, returned once at `Create` time), so the specific claim that `OutgoingSecret` leaks via `Index` is not supported. `AccessKey`/`OutgoingToken` are what leak.

Also, external-initiator credentials (`X-Chainlink-EA-AccessKey`/`Secret`) cannot themselves authenticate this route: `authv2` only accepts `auth.AuthenticateByToken` (user API token) or `auth.AuthenticateBySession` (user session) — `auth.AuthenticateExternalInitiator` is not part of this group's chain: [6](#0-5) 

So the realistic unprivileged actor is a low-privileged node user (view or run role) with a valid API token/session, not a bare EI-credential holder.

### Impact Explanation
A `view`-role user (intended to be read-only/limited) can enumerate every external initiator configured on the node and obtain each one's `AccessKey` and `OutgoingToken` in plaintext. `OutgoingToken` is a credential the node sends outward to the external initiator's callback endpoint, so its disclosure to unrelated low-privileged users breaks the intended confinement between different EI integrations/users and is a credential-disclosure impact under Chainlink's bounty class for secret/credential exposure via authorization gaps.

### Likelihood Explanation
Any user with a valid low-privilege API token or session (view or run role) can trivially call `GET /v2/external_initiators?size=...&page=...` — no special conditions, no timing constraints, fully repeatable, and demonstrated by the existing integration test.

### Recommendation
Wrap `eia.Index` with `auth.RequiresEditRole` (or at minimum `RequiresRunRole`) to match `Create`/`Destroy`, and additionally stop returning `AccessKey`/`OutgoingToken` in the list presenter (only return them once at creation, as is already done for `OutgoingSecret`/`Secret`/`HashedSecret`).

### Proof of Concept
1. Extend `core/web/external_initiators_controller_test.go` `TestExternalInitiatorsController_Index`.
2. Create a node user with `UserRoleView` (or use `app.NewHTTPClient` variant that issues a view-role token, see `cltest` helpers for role-scoped clients).
3. Insert two `ExternalInitiator`s via `bridges.NewORM`.
4. Using the view-role client, `GET /v2/external_initiators`.
5. Assert response status is `200 OK` (not `401`/`403`), and that the returned `ExternalInitiatorResource` list contains `AccessKey` and `OutgoingToken` fields matching the DB-inserted values for both initiators — proving a view-role user can read another initiator's credentials.
6. Contrast with `POST`/`DELETE /v2/external_initiators` using the same view-role client, expecting `401 Unauthorized` from `RequiresEditRole`, to highlight the inconsistency.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
