### Title
Timing side-channel enables user enumeration in local login fallback due to bcrypt-only-on-match control flow - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`localLoginFallback` performs a fast DB lookup keyed on email and returns immediately if no row is found, before ever reaching `constantTimeEmailCompare` or `utils.CheckPasswordHash` (bcrypt). Since bcrypt verification is only executed when a user row exists, the response time for "email does not exist" is measurably shorter than for "email exists, wrong password," letting an attacker distinguish valid from invalid local admin emails via response timing.

### Finding Description
In `localLoginFallback` [1](#0-0) , the flow is:
1. `oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)` — if the email is not present, this returns an SQL "no rows" error immediately, and the function returns at line 583-585 without ever calling `constantTimeEmailCompare` or `utils.CheckPasswordHash`.
2. If the email exists, execution reaches `constantTimeEmailCompare` (line 586) — a cheap, effectively fixed-cost byte comparison — and then `utils.CheckPasswordHash` (line 591), which invokes bcrypt, a deliberately expensive (tens-to-hundreds of milliseconds) hashing operation [2](#0-1) .

The `constantTimeEmailCompare` helper itself [3](#0-2)  is only defending against timing leaks in the string-equality check (e.g., short-circuit `==` comparisons), but it does nothing to equalize the cost of the surrounding control flow. The dominant timing signal is not the email-string comparison — it's whether bcrypt is invoked at all. This exact same pattern (fast-fail lookup, then constant-time email compare, then bcrypt) also exists in the sibling implementation `core/sessions/localauth/orm.go` `CreateSession` [4](#0-3) , confirming this is a structural characteristic of the local-login code path rather than something unique to the OIDC fallback.

An unauthenticated attacker sending `POST /sessions` requests can observe: (a) fast rejections for emails absent from the `users`/OIDC session table, and (b) slower rejections (bcrypt cost) for emails that exist but have the wrong password. Averaging over many requests removes network jitter, allowing reliable enumeration of valid local admin emails.

### Impact Explanation
This is a user-enumeration timing side-channel against local login, matching the "user enumeration assisting credential-stuffing against local admin accounts" impact class described in the question. It does not by itself grant authentication bypass, key disclosure, or privilege escalation — it only helps an attacker build a list of valid usernames to target with credential-stuffing or brute-force attacks against the small set of local Chainlink node operator accounts.

### Likelihood Explanation
Exploitation requires only unauthenticated network access to the node's `/sessions` HTTP endpoint (no credentials or roles needed), matching the precondition in the question. It is a statistical timing attack — measurable in a benchmark/lab setting (few round trips per sample, hundreds of samples), but reliability degrades over the public internet or a busy production host due to network jitter, GC pauses, connection pooling, and load-balancer/proxy overhead. The signal size is the bcrypt cost (configurable, but typically tens of milliseconds), which is large relative to typical intra-datacenter jitter but can be masked by internet-scale noise.

### Recommendation
Equalize timing across the "email not found" and "email found but wrong password" branches:
- When the email lookup fails, perform a dummy `bcrypt.CompareHashAndPassword` call against a precomputed dummy hash before returning the "invalid email" error, so both branches always pay the bcrypt cost.
- Apply the same fix to `core/sessions/localauth/orm.go`'s `CreateSession` for consistency.
- Consider using a fixed, config-driven minimum response time for the whole login path.

### Proof of Concept
Go benchmark/table test plan:
1. Seed the test DB with one known local user (email `exists@test.com`, valid bcrypt hash).
2. Benchmark `localLoginFallback` (or the `/sessions` handler) with:
   - `sr.Email = "exists@test.com"`, `sr.Password = "wrongpassword"` → measure N=1000 latencies (expect bcrypt cost each time).
   - `sr.Email = "doesnotexist@test.com"`, `sr.Password = "wrongpassword"` → measure N=1000 latencies (expect fast SQL "not found" each time, no bcrypt).
3. Compute mean/median latency for each group; assert `mean(exists) - mean(notExists) > threshold` (e.g., > 5ms), demonstrating a statistically significant, reproducible timing gap correlated with email existence — i.e., that the invariant "response time independent of email existence" (AUTHENTICATION_SOUNDNESS w.r.t. enumeration) is violated.
4. After applying the dummy-bcrypt-call fix, re-run the same benchmark and assert the timing difference falls below the threshold.

```go
func (oi *oidcAuthenticator) localLoginFallback(ctx context.Context, sr clsessions.SessionRequest) (clsessions.User, error) {
	var user clsessions.User
	err := oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}
```

```go
func constantTimeEmailCompare(left, right string) bool {
	const constantTimeEmailLength = 256
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
```
