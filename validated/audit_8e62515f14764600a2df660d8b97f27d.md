### Title
Unprivileged view-role users can access `/debug/vars` (expvar) internal runtime state due to missing role gate - ([File: core/web/router.go])

### Summary
`debugRoutes` mounts `GET /debug/vars` behind only session authentication (`auth.AuthenticateBySession`) with no role-based authorization wrapper, unlike nearly every other sensitive endpoint in the router which is wrapped with `auth.RequiresEditRole` or `auth.RequiresAdminRole`. Any authenticated user, including one holding only the lowest `view` role, can therefore retrieve Go's `expvar` output containing `cmdline` (process command-line arguments) and `memstats` (detailed runtime memory/GC statistics).

### Finding Description
`debugRoutes` is defined as:
```go
func debugRoutes(app chainlink.Application, r *gin.RouterGroup) {
	group := r.Group("/debug", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	group.GET("/vars", expvar.Handler())
}
``` [1](#0-0) 

`auth.Authenticate` with only `auth.AuthenticateBySession` verifies that a valid session cookie exists and attaches the authenticated `User` to the context, but performs no check on `user.Role`. [2](#0-1) 

Compare this to the rest of `v2Routes`, where every route that returns internal operational data is wrapped in `auth.RequiresEditRole` or `auth.RequiresAdminRole`, which explicitly reject `UserRoleView` (and, for admin routes, `UserRoleRun`) with `401`/`403`: [3](#0-2) 

Because `debugRoutes` omits any such wrapper, a session belonging to a user with `Role: view` — the lowest privilege tier in the node — passes `AuthenticateBySession` and reaches `expvar.Handler()` unimpeded, returning the full expvar JSON payload (`cmdline`, `memstats`, and any other published vars) to a user who is not supposed to have any elevated visibility into node internals.

### Impact Explanation
This is an authorization-gap information-disclosure issue: it discloses internal runtime state (Go `memstats` — heap/GC stats useful for profiling/DoS timing analysis — and `cmdline` — the exact command-line invocation of the node, which can reveal file paths, flags, and configuration hints) to any authenticated user regardless of role. This matches Chainlink's "authorization bypass / unauthorized information disclosure to a lower-privileged authenticated user" impact class. It does not directly enable fund movement or key theft, so the severity is informational/low relative to full auth bypass, but it is a genuine break of the exact-authorization invariant enforced everywhere else in the router.

### Likelihood Explanation
Preconditions are minimal: attacker only needs a valid session cookie for any user account, including one explicitly provisioned with the `view` role. No token, no edit/run/admin privilege, and no additional exploitation steps are required — a single unauthenticated-role-check-bypassing `GET /debug/vars` request suffices. This is trivially and repeatably reproducible.

### Recommendation
Wrap the `/debug/vars` route with `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`), consistent with how other internal/operational routes (`/config`, `/log`, key export endpoints) are gated:
```go
group.GET("/vars", auth.RequiresAdminRole(func(c *gin.Context) { expvar.Handler().ServeHTTP(c.Writer, c.Request) }))
```

### Proof of Concept
Go handler-level integration test plan (in `core/web`):
1. Build the router via `NewRouter` with a test `chainlink.Application` and a seeded database containing a user with `Role: clsessions.UserRoleView`.
2. Authenticate as that view-role user via `POST /sessions` to obtain a valid session cookie (mirroring existing tests, e.g. those using `cltest.MustGenerateSessionCookie`/`multipleTraits` helpers already used in `core/web/*_test.go`).
3. Issue `httptest` `GET /debug/vars` with the view-role session cookie attached.
4. Assert:
   - Response status is `200 OK` (not `401`/`403`).
   - Response body is valid JSON containing top-level keys `"cmdline"` and `"memstats"`.
5. Contrast with a second table-test case hitting an edit/admin-gated route (e.g. `GET /v2/config`) with the same view-role cookie and assert it returns `401 Unauthorized` — demonstrating the inconsistency: `/debug/vars` lacks the role gate that equivalent internal-data routes enforce.

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
