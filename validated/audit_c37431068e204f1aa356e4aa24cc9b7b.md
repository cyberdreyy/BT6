### Title
Stale `lastWithdrawRequest` epoch pointer lets a user bypass a pending loss-adjusted receipt haircut and claim it at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The upstream bug is a NULL dereference caused by a pointer (`q->elevator`) that is assumed valid after a lock but was switched/cleared concurrently. The closest analog in this codebase is a stale-index bug in `IdleCreditVault._claimLossAdjustedWithdrawRequest`: loss-adjusted withdrawal receipts are looked up only via `lastWithdrawRequest[_user]`, the *latest* request epoch. A user who holds a receipt from an epoch where `stopEpochWithDuration` applied a loss can simply submit a new withdraw request in a later epoch. The new request overwrites `lastWithdrawRequest[_user]`, the `lossRecoveryPriceByEpoch` lookup hits an epoch with no haircut (`0`), the loss-adjusted path is skipped, and the old haircutted basis is folded into the aggregate `withdrawsRequests[_user]` and paid **at par** by `_claimFundedWithdrawRequest`.

### Finding Description
- `requestWithdraw` records per-epoch basis in `withdrawsRequestsByEpoch[_user][currentEpoch]`, adds to aggregate `withdrawsRequests[_user]`, and sets `lastWithdrawRequest[_user] = currentEpoch` (lines 281-294). The code comment even notes that making a new request before claiming is supported ("he will have to wait for another epoch to claim both requests").
- When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` clears `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` where `lossRecoveryPrice < RECOVERY_FULL` (lines 411-421).
- On claim, `_claimLossAdjustedWithdrawRequest` does `uint256 lossEpoch = lastWithdrawRequest[_user]; lossRecoveryPriceByEpoch[lossEpoch]` — it only ever inspects the **most recent** request epoch (lines 789-792). If the user re-requested in epoch N+1, `lossRecoveryPriceByEpoch[N+1] == 0` and the function returns 0 without ever touching the epoch-N haircut ledger.
- `_claimFundedWithdrawRequest` then computes `amount = withdrawsRequests[_user] + apr0PrincipalAmount + apr0InterestAmount` and pays the full aggregate at par via `_transferFundedClaim` (lines 338-349). The epoch-N receipt basis, which should have been paid `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, is paid 100%.
- `_clearWithdrawClaimForEpoch` would have cleared only one epoch's entry anyway; nothing re-links the orphaned epoch-N basis to its haircut.

Attack sequence (fixed-APR mode, normal — not APR0 — requests):
1. Victim-attacker (ordinary KYC'd tranche holder, unprivileged) calls `cdoEpoch.requestWithdraw` in epoch N.
2. Manager calls `stopEpochWithDuration(…, _lossAmount)`; `collectWithdrawFunds` funds less than `pendingWithdraws` and records `lossRecoveryPriceByEpoch[N] < RECOVERY_FULL`.
3. Attacker calls `requestWithdraw` again in epoch N+1 (any nonzero amount, or the rest of their position). `lastWithdrawRequest[attacker] = N+1`.
4. Epoch N+1 ends normally; `epochNumber` bumps past N+1 so the `epochNumber <= lastWithdrawRequest[_user]` gate in `_claimFundedWithdrawRequest` passes.
5. Attacker calls `claimWithdrawRequest`: loss-adjusted lookup hits epoch N+1 → 0 → funded claim pays `withdrawsRequests[attacker]` (N-basis + N+1-basis) at par.

### Impact Explanation
Broken invariant: loss socialization / one-receipt-one-(haircutted)-payout. The pool pays out `epochN_basis * (1 - lossRecoveryPrice/RECOVERY_FULL)` more than intended, directly from underlying held in the strategy that was reserved for other pending/funded claimants and the default-recovery reserve. This is direct theft quantified as the haircut the attacker dodged: with a 30% receipt loss on a 1M USDC pending receipt, the attacker extracts ~300k USDC belonging to other LPs/receipt holders, and the last claimants' funded payouts become unpayable (insolvency).

### Likelihood Explanation
Requires only an unprivileged tranche holder calling `requestWithdraw` twice across two epochs and `claimWithdrawRequest` once — no privileged action by the attacker. It triggers whenever a `stopEpochWithDuration` loss-adjusts pending receipts (a supported, non-default flow), and the honest manager's later `stopEpoch` enables the claim. No existing guard (`epochNumber` gating, `NotAllowed` reverts on zero recovery price, `_onlyIdleCDO`) prevents it because the funded-claim path legitimately pays the aggregate ledger at par — it has no knowledge that part of that ledger was haircutted. The only mitigation is user behavior: anyone who claims before re-requesting pays the haircut correctly, so the attacker must simply wait, which costs nothing.

### Recommendation
- In `_claimLossAdjustedWithdrawRequest`, iterate or track per-user loss-adjusted epochs rather than keying solely off `lastWithdrawRequest[_user]`; alternatively maintain a `lossAdjustedBasis[_user]` aggregate incremented in `collectWithdrawFunds`/`requestWithdraw` so the haircutted portion is always deducted before the funded path runs.
- Alternatively, in `requestWithdraw`, force-settle (or revert on) any outstanding receipt whose `withdrawsRequestsByEpoch[_user][e] != 0` and `lossRecoveryPriceByEpoch[e] != 0` for prior epochs, so a haircutted basis can never be merged into a fresh par claim.
- `_claimFundedWithdrawRequest` should subtract any basis belonging to epochs with a nonzero `lossRecoveryPriceByEpoch` from `amount` before paying at par.

### Proof of Concept
Foundry fork/unit PoC sketch (existing harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. user deposits and requests withdraw in epoch N
_depositWithUser(user, amount, true);
uint256 reqN = cdoEpoch.requestWithdraw(userTrancheBal / 2, address(AAtranche)); // prank user

// 2. epoch N stops with a realized loss -> lossRecoveryPriceByEpoch[N] < RECOVERY_FULL
_startEpochAndCheckPrices(0);
uint256 pendingBasis = strategy.pendingWithdraws();
uint256 loss = pendingBasis / 2; // 50% haircut on pending receipts (must be < totalBasis)
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(loss);
uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
deal(defaultUnderlying, borrower, repay);
vm.prank(borrower); underlying.approve(address(cdoEpoch), repay);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(10e18, 0, cdoEpoch.epochDuration(), loss);
assertLt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), RECOVERY_FULL);

// 3. user does NOT claim; makes a second withdraw request in epoch N+1
uint256 reqN1;
vm.prank(user);
reqN1 = cdoEpoch.requestWithdraw(0, address(AAtranche)); // or more tranche tokens

// 4. epoch N+1 runs and stops normally (borrower repays in full)
_startEpochAndCheckPrices(1);
_stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

// 5. claim: loss-adjusted path looks up epoch N+1 (price 0), funded path pays aggregate at par
uint256 balPre = underlying.balanceOf(user);
vm.prank(user);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;

// Expected (buggy): paid == reqN + reqN1  -> epoch-N receipt paid at PAR
// Correct:          paid == reqN * lossRecoveryPrice/RECOVERY_FULL + reqN1
assertEq(paid, reqN + reqN1); // demonstrates stolen haircut = reqN * (1 - price)
```
