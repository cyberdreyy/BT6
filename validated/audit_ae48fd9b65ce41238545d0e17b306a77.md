### Title
V1 signer's tenure-duplicate guard checks only globally-accepted state, letting a single signer sign two conflicting tenure-start blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`validate_tenure_change_payload` in the v1 chainstate path rejects a competing tenure-start proposal with `DuplicateBlockFound` only when the signer has already **globally accepted** a block in that tenure, whereas the v2 path (and the runtime signing-time guard) treats **any signed** block (locally or globally accepted) as the relevant state. This mismatch lets a v1 signer that has already signed (locally accepted) a tenure-start block, but whose node has not yet observed/processed it, pass a second, competing tenure-start proposal for the *same* tenure through the proposal-time duplicate check.

### Finding Description
For tenure-change (tenure-start) blocks, the shared chainstate check only validates the block against its **parent** tenure via `check_tenure_change_confirms_parent`/`check_latest_block_in_tenure`; it deliberately never checks the block's **own** tenure (documented in `docs/signer-flows.md`: "a tenure-change block is checked against its parent tenure, every other block against its own. Never both."). The only guard against a second tenure-start block for the *same* tenure is the `DuplicateBlockFound` check inside `validate_tenure_change_payload`, and it runs **only at proposal arrival**, never again at validate-ok or at signing.

In v1, that check queries only globally accepted state: [1](#0-0) 

In v2 the equivalent check instead uses "any signed" state (locally or globally accepted): [2](#0-1) 

Because the proposal-time duplicate check never re-runs, the only other backstop is the signing-time "own tenure" conflict guard in `signer.rs`, but that guard's veto is gated on the **node's own canonical tip height for the tenure**, not on the fact that the signer itself already signed a conflicting block: [3](#0-2) 

If the node hasn't yet processed/observed the first (already locally-accepted, i.e. signed) tenure-start block as its canonical tenure tip, `tip_height` stays below the second proposal's `chain_length`, so the code path logs "signing the replacement" and proceeds to sign the second, conflicting tenure-start block for the very same tenure - even though this same signer already signed the first one.

### Impact Explanation
This is a signer signing a conflicting block: the same v1 signer produces valid signatures over two mutually-exclusive tenure-start blocks for the same tenure/consensus hash. If both proposals independently gather 70% signer weight (plausible since different signer subsets may be lagging on node-tip visibility differently), this can produce two competing, fully-signed candidate blocks for the same tenure - a direct break of the "one signed block per tenure-start" invariant and a path toward a signer-endorsed fork. This matches the Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
This requires only a single miner (or a party able to get a second tenure-start proposal broadcast, e.g. via gossip/equivocation) plus ordinary network/processing lag between the signers reaching pre-commit threshold and the node ingesting/announcing the first block - no majority of signers, no other signer's key, and no local/auth-token access is needed. It is specific to the v1 protocol path (`get_last_globally_accepted_block` vs `get_last_signed_block`), so it applies only while v1 chainstate logic is in use.

### Recommendation
Make `validate_tenure_change_payload` in `chainstate/v1.rs` consult `get_last_signed_block` (or equivalently any locally-or-globally accepted/signed block) rather than `get_last_globally_accepted_block`, matching the v2 semantics. Additionally, consider re-running the duplicate/own-tenure check at validate-ok and at pre-commit/signing time rather than only at proposal arrival, and make the signing-time "replacement" guard in `signer.rs` also veto when the signer itself has already signed a conflicting block in the same tenure, independent of the node's currently-observed tip height.

### Proof of Concept
1. Signer S runs v1 chainstate logic.
2. Miner proposes tenure-start block A for tenure T; S and enough peers sign it (S calls `mark_locally_accepted`, i.e. `signed_self` is set) - block A is only *locally* accepted, not yet globally accepted, because the node has not yet ingested/announced it.
3. Before the node processes/announces block A, the miner (or an equivocating actor) proposes a second, conflicting tenure-start block B for the same tenure T (same `consensus_hash`, different content/parent choice).
4. `validate_tenure_change_payload` (v1) calls `get_last_globally_accepted_block(&T)` - returns `None` because A is only locally accepted, so `DuplicateBlockFound` is not raised; proposal B passes the proposal-time chainstate check.
5. B accumulates pre-commits and crosses the 70% threshold. In `signer.rs`'s signing-time replacement guard, `stacks_client.get_tenure_tip(T)` still returns a tip below B's `chain_length` (node hasn't processed A yet), so the guard does not block, and S signs B - despite having already signed conflicting block A for the same tenure T.
