### Title
Mixed-epoch withdraw receipts let a stale APR0 principal escape the stopEpoch loss haircut and claim at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` books every non-closed request into the single aggregate `pendingWithdraws` bucket, but the loss-recovery clearing logic attributes a haircut only to entries keyed to the *latest* request epoch (`withdrawsRequestsByEpoch[user][lossEpoch]` and `apr0Users[user].principalEpoch == lossEpoch`). A user holding an APR0 principal recorded in an earlier epoch, plus a normal request in the loss epoch, has both amounts inside the haircut basis yet only the normal amount gets the `lossRecoveryPrice` applied; the stale APR0 principal is then paid at par through `_claimFundedWithdrawRequest` in the same claim call. This is the same class as CVE-2019-20372: one "request" (the pending bucket) is interpreted two different ways — haircut basis at funding time vs. full funded claim at payout time — letting the attacker read out value the other interpretation said was impaired.

### Finding Description
Relevant code:

- `requestWithdraw` adds `_amount` to the global `pendingWithdraws` for every non-closed request [1](#0-0) , but only records per-epoch ownership for the normal path via `withdrawsRequestsByEpoch[_user][currentEpoch]` [2](#0-1) . APR0 requests go through `_requestWithdrawApr0`, which stores a single `principalEpoch` slot and bumps `apr0TotalPrincipal` [3](#0-2) .
- `collectWithdrawFunds` / `previewLossAdjustedWithdrawFunds` spread a realized loss pro-rata over the whole `pendingBasis`, i.e. over the sum of normal *and* stale APR0 principal [4](#0-3) [5](#0-4) .
- The guard in `requestWithdraw` only blocks a new request when the *stale* receipt sits in an epoch that already has a `lossRecoveryPrice` — it does not force the stale APR0 principal into `withdrawsRequestsByEpoch` for a *future* loss epoch [6](#0-5) .
- On claim, `_claimLossAdjustedWithdrawRequest` applies `lossRecoveryPrice` only to the basis returned by `_withdrawClaimAmountsForEpoch(user, lastWithdrawRequest[user])`, which includes `apr0User.principal` only when `principalEpoch == lossEpoch` [7](#0-6) [8](#0-7) . `_clearWithdrawClaimForEpoch` then resets `lastWithdrawRequest` to 0 [9](#0-8) , so `claimWithdrawRequest` falls through into `_claimFundedWithdrawRequest`, whose epoch-wait guard passes and which pays `settledPrincipal + principal + settledInterest` in full [10](#0-9) .

Attack sequence (fixed-APR → APR0 → fixed-APR vault, normal epoch mode):

1. Manager sets `unscaledApr = 0`. Attacker (KYC'd lender) deposits AA and calls `requestWithdraw` in epoch N → `pendingWithdraws += P`, `apr0Users[attacker] = {principal: P, principalEpoch: N}`. Attacker does not claim.
2. Epoch N stops honestly; epoch N+1 runs; manager later sets a non-zero APR.
3. In epoch M (> N), attacker calls `requestWithdraw` again with amount Q → `pendingWithdraws += Q`, `withdrawsRequestsByEpoch[attacker][M] = Q`, `lastWithdrawRequest[attacker] = M`. The guard at lines 263–271 does not revert because `lossRecoveryPriceByEpoch[M]` is still 0 and the stale `principalEpoch` is N.
4. Epoch M ends via `stopEpochWithDuration` with a loss funded below `pendingBasis` → `lossRecoveryPriceByEpoch[M] = r < RECOVERY_FULL` and only `r * (P + Q) / RECOVERY_FULL` underlying is collected (the funded amount is a pro-rata share of the aggregate pending bucket).
5. Attacker calls `IdleCDOEpochVariant.claimWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` pays `Q * r / RECOVERY_FULL` (APR0 principal is excluded because `principalEpoch == N ≠ M`) and clears `lastWithdrawRequest`; `_claimFundedWithdrawRequest` then settles the APR0 receipt (`_settleApr0` since `N < epochNumber`) and pays `P` plus any settled interest **at par**, from the same under-funded reserve.

The broken invariant is "one receipt, one haircut": the APR0 principal counted toward the loss basis is paid as if no loss occurred.

### Impact Explanation
Direct theft / insolvency: the attacker extracts `P * (1 - r)` underlying that was never funded, paid out of the same strategy balance that backs other users' loss-adjusted receipts, active tranche NAV, and `defaultRecoveryReserve` checks in `_transferFundedClaim`. With `P` comparable to the epoch's pending bucket, the last claimants (or AA/BB holders via `getContractValue`/`_virtualPriceAux`) absorb the shortfall — loss is bounded only by the attacker's deposited principal and is repeatable each loss epoch.

### Likelihood Explanation
Requires no privileged misbehavior: only an honest manager switching APR regimes (a supported configuration — `setAprsWithBuffer`, `prepareStopEpochWithApr0`) and a normal `stopEpochWithDuration` partial loss. The attacker controls deposit, both `requestWithdraw` calls and the claim. Existing guards do not stop it: the `lossRecoveryPrice != 0` revert only triggers for a *past* loss epoch, `_settleApr0` deliberately pays unsettled cross-epoch principal, and there is no code path that migrates a stale `apr0Users.principal` into `withdrawsRequestsByEpoch` when APR becomes non-zero.

### Recommendation
In `requestWithdraw`, before accepting a new request, force-settle any prior APR0 receipt into a normal per-epoch ledger entry (e.g. call `_settleApr0` unconditionally and move `settledPrincipal`/`settledInterest` into `withdrawsRequestsByEpoch[user][itsEpoch]` or a dedicated funded bucket that participates in `lossRecoveryPriceByEpoch` haircuts). Alternatively, extend `_withdrawClaimAmountsForEpoch`/`_claimLossAdjustedWithdrawRequest` to haircut *all* outstanding receipt basis (stale APR0 principal included) whenever the aggregate `pendingWithdraws` was loss-adjusted, or revert in `requestWithdraw` whenever the user has any unsettled APR0 principal and `unscaledApr != 0`.

### Proof of Concept

```solidity
function testStaleApr0EscapesLossHaircut() external {
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner); cdoEpoch.setIsAYSActive(false);
    vm.prank(manager); IdleCreditVault(address(strategy)).setAprs(0, 0); // APR0 mode

    uint256 P = 5000 * ONE_SCALE;
    uint256 minted = idleCDO.depositAA(P);
    _transferBurnedTrancheTokens(address(this), true);
    _startEpochAndCheckPrices(0);

    // 1) APR0 withdraw request in epoch N (P enters pendingWithdraws + apr0Users)
    cdoEpoch.requestWithdraw(minted, address(AAtranche));
    _stopEpochAndCheckPrices(0, 0, _expectedFundsEndEpoch()); // epoch N ends

    // 2) manager switches APR back on; attacker adds normal request in epoch M
    vm.prank(manager); IdleCreditVault(address(strategy)).setAprs(initialProvidedApr, 0);
    uint256 minted2 = idleCDO.depositAA(P);
    uint256 Q = cdoEpoch.requestWithdraw(minted2, address(AAtranche));
    _startEpochAndCheckPrices(1);

    // 3) epoch M ends with a partial loss: borrower funds only r < 1 of pendingWithdraws
    uint256 loss = /* e.g. 30% of TVL */;
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, loss); // sets lossRecoveryPriceByEpoch[M] = r

    // 4) single claim pays Q*r (haircut) AND P (full) -> more than funded
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 claimed = underlying.balanceOf(address(this)) - balPre;

    uint256 r = strategy.lossRecoveryPriceByEpoch(M_epoch);
    assertGt(claimed, (Q * r / 1e18) + (P * r / 1e18)); // received P at par
    // strategy underlying balance is now short P*(1-r) for remaining claimants
}
```

Expected result: `claimed ≈ Q*r + P` while only `(P+Q)*r` was collected via `collectWithdrawFunds`, leaving the strategy insolvent by `P*(1−r)` for other pending receipts and active tranche holders.

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _withdrawClaimAmountsForEpoch(address _user, uint256 _claimEpoch) internal view returns (uint256 claimBasis, uint256 burnAmount) {
    // We calculate what the user is owed in underlyings (claimBasis) and how many strategy tokens to burn (burnAmount).
    // the amount owned is the sum of the normal withdraw request and the APR0 principal and interest if any.
    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    Apr0UserData storage _apr0User = apr0Users[_user];
    uint256 apr0PrincipalAmount;
    uint256 apr0InterestAmount;
    uint256 principal = _apr0User.principal;
    uint256 principalEpoch = _apr0User.principalEpoch;
    if (principal != 0 && principalEpoch == _claimEpoch) {
      apr0PrincipalAmount = principal;
      uint256 rate = apr0RateByEpoch[principalEpoch];
      if (rate != 0) {
        // APR0 interest increases the user's default claim basis, but not the receipt burn amount.
        apr0InterestAmount += (principal * rate) / RECOVERY_FULL;
      }
    }
    claimBasis = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    burnAmount = normalAmount + apr0PrincipalAmount;
  }
