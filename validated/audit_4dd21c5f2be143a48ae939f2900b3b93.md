### Title
Missing withdrawal replay protection in `EscrowSrc.withdraw`/`withdrawTo` allows repeated safety-deposit and token drains from any post-withdrawal top-up - (File: `contracts/EscrowSrc.sol`)

### Summary
`EscrowSrc.withdraw`/`withdrawTo`/`publicWithdraw` all route to `_withdrawTo`, which is guarded only by `onlyCaller`, `onlyAfter(SrcWithdrawal)`, `onlyBefore(SrcCancellation)`, `onlyValidImmutables`, and `onlyValidSecret` [3](#0-2) . None of these checks consume the secret or otherwise mark the escrow as "already withdrawn." As a result, the same taker can call `withdraw(secret, immutables)` (or `withdrawTo`) multiple times within the same private-withdrawal window, and each call will unconditionally execute `safeTransfer(target, immutables.amount)` plus `_ethTransfer(msg.sender, immutables.safetyDeposit)` [4](#0-3) , as long as the clone's balances can cover it.

### Finding Description
The escrow clone is a persistent contract for the whole `SrcWithdrawal`→`SrcCancellation` window; it is never destroyed or flagged after a successful withdrawal. If any additional native ETH and/or maker-token balance reaches the clone's address after the first legitimate withdrawal (via a plain top-up transfer, an accidental resend, or any other unprivileged action that increases the clone's balance), the taker who already withdrew once can call `withdraw` again with the identical `secret` and `immutables` and receive another full payout cycle — including another `safetyDeposit` refund and, if enough ERC20 balance is present, another `amount` transfer — even though only one withdrawal was ever "due" per the escrow's economic design. Compare this with `cancel`, which has the same absence of a completion flag, so the same class of replay applies there too, but the source `withdraw` path is the one explicitly targeted here.

### Impact Explanation
This lets an unprivileged taker harvest a duplicate `safetyDeposit` (and any excess maker-token balance) that was never intended to belong to it, purely because the contract lacks bookkeeping to prevent re-execution of the payout logic. This falls under the "theft of coins/tokens meant for transaction fees or native refund paths" Medium-impact bucket, since the safety deposit is the fee-like incentive paid to the caller for executing the withdrawal.

### Likelihood Explanation
Exploitation strictly depends on the escrow's balance being topped up above what a single withdrawal already consumed — this doesn't happen in the intended, correctly-funded happy path where the clone holds exactly `amount` + `safetyDeposit` before the one legitimate withdrawal drains it to zero. The scenario requires an external event (a stray/duplicate transfer, a race with a resolver's automation re-funding retries, etc.) to leave spare balance in the clone before `SrcCancellation`. Likelihood is therefore low-to-moderate and opportunistic rather than attacker-triggerable at will, but the missing protection is a genuine design gap since nothing in the contract enforces the "one withdrawal per lifecycle" invariant that the accounting model relies on.

### Recommendation
Add explicit one-time-use state to the escrow (e.g., a `bool internal _withdrawn` or `_completed` flag set in `_withdrawTo`/`_cancel` and checked at the start of both, reverting on replay), or `selfdestruct`/self-disable the clone after a successful withdrawal/cancellation so no further balance movement is possible regardless of what native/token balance later reaches the address.

### Proof of Concept
1. Deploy and fund `EscrowSrc` clone normally with `amount` (ERC20) + `safetyDeposit` (native).
2. Warp to `SrcWithdrawal`, taker calls `withdraw(secret, immutables)` — clone balances drop to zero, taker receives `amount` ERC20 and `safetyDeposit` native, as shown in existing tests such as `test_RescueFundsSrc` in `test/unit/Escrow.t.sol` [5](#0-4) .
3. Before `SrcCancellation`, send `amount` ERC20 + `safetyDeposit` native directly to the clone address (any unprivileged sender can do this).
4. Taker calls `withdraw(secret, immutables)` again with the exact same `secret`/`immutables` — the call passes all modifiers (`onlyCaller`, time window, `onlyValidImmutables`, `onlyValidSecret` all still hold) and pays out `amount` ERC20 + `safetyDeposit` native a second time, confirming there is no invariant preventing more than one payout per escrow lifecycle.
