### Title
Gas under-charge for `yield_resume_byte` fee when payload is supplied via register in `promise_yield_resume_with_yield_id` - (File: runtime/near-vm-runner/src/logic/logic.rs)

### Finding Description
In `promise_yield_resume_with_yield_id`, the gas fee for the payload is charged with the raw, caller-supplied `payload_len` parameter before the actual payload bytes are fetched: `self.result_state.gas_counter.pay_per(yield_resume_byte, payload_len)?;` at logic.rs:3895, and only afterward is the payload retrieved via `get_memory_or_register!(self, payload_ptr, payload_len)` at logic.rs:3897 and the *real* length recomputed at logic.rs:3898 (`let payload_len = payload.len() as u64;`).

`get_memory_or_register!` supports two call conventions: a direct-memory read (where `payload_len` truly is the byte count read from guest memory, so the pre-charge is accurate), and a register read triggered when `payload_ptr == u64::MAX`, in which case the `payload_len` argument is repurposed as a register id rather than a byte length. In the register path, the number of bytes actually retrieved is determined solely by whatever content the attacker previously wrote into that register (via `write_register`) with `promise_yield_create_with_id`/other host calls — it is completely decoupled from the small `payload_len`/register-id value used to compute the `yield_resume_byte` fee.

The post-fetch recomputation of `payload_len` at logic.rs:3898 is used only for the `max_yield_payload_size` limit check (logic.rs:3899-3905); it is never fed back into the gas counter to correct the earlier under-charge. This violates metering totality: the runtime processes/stores a large payload (up to `max_yield_payload_size` bytes) while the contract is billed as if it supplied a payload no larger than the declared register-id-sized value.

Exploit flow: attacker deploys a contract that (1) creates a pending yield via `promise_yield_create_with_id`, (2) populates a register with a large payload (close to `max_yield_payload_size`) via a normal register-writing host call, then (3) calls `promise_yield_resume_with_yield_id` with `payload_ptr = u64::MAX` and `payload_len` set to the register id (a small integer, e.g. `0`), instead of the real payload length. The `pay_per(yield_resume_byte, payload_len)` call charges gas for the tiny declared value, while `submit_promise_resume_data_with_yield_id` at logic.rs:3911 is invoked with the full, large register payload.

### Impact Explanation
This is a fee-payment/metering bypass: the byte-processing cost of large yield-resume payloads (which drive receipt size, storage, and later callback execution cost) can be paid for at a fraction of its true `yield_resume_byte` cost by routing the payload through a register instead of memory and under-declaring the length parameter. This does not directly move NEAR tokens, but it lets an attacker submit disproportionately large payloads for cheap gas, undermining the fee model that other resource-consumption checks (`max_yield_payload_size`) assume is correctly priced — a "gas metering totality" violation rather than direct fund theft.

### Likelihood Explanation
Fully reachable by an unprivileged account: no special permissions are needed beyond deploying a contract and having a valid pending yield (`promise_yield_create_with_id`), both attacker-controlled actions. The exploit is deterministic and repeatable on every call using the register-based calling convention with a mismatched declared length.

### Recommendation
Charge `yield_resume_byte` based on the *actual* fetched payload length, not the pre-fetch parameter — mirror the safe pattern used elsewhere in the codebase (e.g. `sha256`) where the vector is retrieved first and `pay_per` is invoked with `payload.len()`. Apply the same fix to the sibling function `promise_yield_resume` (logic.rs:3856), which has the identical ordering issue.

### Proof of Concept
Add a test in `runtime/near-vm-runner/src/logic/tests/yield_resume.rs`:
1. Create a yield via `promise_yield_create_with_id`.
2. Write an N-byte payload (e.g., 1024 bytes, well under `max_yield_payload_size`) into a register using a register-populating host call.
3. Call `promise_yield_resume_with_yield_id` with `payload_ptr = u64::MAX`, `payload_len = <register_id>` (small integer), and record burnt gas `G_register`.
4. In a separate run, call `promise_yield_resume_with_yield_id` with the same payload placed in guest memory and `payload_len = 1024`, recording burnt gas `G_memory`.
5. Assert `G_memory - G_register ≈ yield_resume_byte_fee * 1024`, proving the register path was undercharged for an equivalent amount of processed data, while asserting via `submit_promise_resume_data_with_yield_id`'s recorded payload that the full 1024-byte payload was actually processed in both cases.
