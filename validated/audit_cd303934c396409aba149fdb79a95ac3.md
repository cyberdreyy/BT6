### Title
Stale confirmations from removed multisig members are not purged, allowing request execution below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both the `multisig` and `multisig2` contracts track confirmations for a pending request in a `HashSet` keyed by request ID [1](#0-0) . When a request accumulates `num_confirmations` entries in that set, it executes [2](#0-1) . When a member/key is removed, the contract only purges confirmation sets for requests that member *created*, not confirmations that member previously *cast* on other still-pending requests. This lets a request execute counting a vote from an account that is no longer a member, effectively executing below the real live-member threshold — a direct analog of the ERC721F issue where an alternate code path skips the access re-validation that the primary path performs.

### Finding Description
The binding that should hold is:
`confirmations counted toward num_confirmations == confirmations from currently-live members`

In `multisig2/src/lib.rs`, `confirm()` only re-validates that the *caller* is currently a member via `assert_valid_request` → `current_member()` [3](#0-2) . It never re-validates the *other* entries already stored in `self.confirmations.get(&request_id)` before comparing the set length to `num_confirmations` [4](#0-3) .

`delete_member()` only cleans up confirmations for requests the removed member *authored* (`r.member == member`, i.e., the request creator), and does not scan the `confirmations` map for other pending requests the member had merely confirmed: [5](#0-4) 

The identical pattern exists in the legacy `multisig` contract's `DeleteKey` handling, which only removes requests authored by the deleted `signer_pk`, not that key's confirmations recorded on other pending requests: [6](#0-5) 

So exactly like the ERC721F bug — where the overridden `transferFrom` access check is bypassed because the alternate `safeTransferFrom` path relies on `_safeTransfer` and never revisits the access list — here the `confirm` execution path relies on stale set membership counts and never revisits whether each already-recorded confirmer is still a valid member/key at the moment the threshold check (`execute_request`) fires.

### Impact Explanation
This matches the Critical impact category "a multisig request executed below threshold." A request can be executed (including a `Transfer` action moving NEAR out of the multisig account, per `execute_request`) with fewer *live* members' votes than `num_confirmations` requires, because one of the counted confirmations belongs to a member that has since been removed.

### Likelihood Explanation
This requires no privileged access beyond being (or having been) one of the multisig's own members/keys, and no compromise of the foundation, owner, or other members' keys — only the ordinary sequence of: confirm a pending request short of threshold, get removed as a member/key (a normal, expected multisig operation), then have any other member cast the final confirmation. This is a realistic operational sequence for any multisig doing routine membership rotation while a request is outstanding.

### Recommendation
When executing `delete_member` (or `DeleteKey` in the legacy contract), iterate all `requests`/`confirmations` and strip the removed member's/key's entry from every confirmation set, not only from requests they authored. Alternatively, re-validate at `confirm`/`execute_request` time that every entry in the confirmation set still corresponds to a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 5 members `[A,B,C,D,E]` and `num_confirmations = 3`.
2. `A` calls `add_request` for a `Transfer` action to some receiver, then `B` and `C` call `confirm` — confirmation set is now `{B, C}` (size 2, below threshold 3), request stays pending [4](#0-3) .
3. Separately, quorum approves a `DeleteMember { member: B }` request to remove `B` (e.g., legitimately, for key rotation). `delete_member` only removes confirmations for requests *authored by* `B`; the Transfer request from step 2 (authored by `A`) is untouched, so its confirmation set `{B, C}` still contains `B` [5](#0-4) .
4. `D` (a live member) calls `confirm` on the original Transfer request. `confirmations.len() + 1 = 3 >= num_confirmations (3)` — the request executes and NEAR is transferred, even though the vote set `{B, C, D}` includes `B`, who is no longer a member [2](#0-1) .

The transfer executes with only 2 live-member confirmations (`C`, `D`) effectively backing a 3-of-5 threshold, breaking the confirmations-vs-live-members binding.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
