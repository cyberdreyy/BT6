## Answer

The strongest analog to the ECG `totalBorrowedCredit` underflow bug in agave is the `getSupply` JSON-RPC handler, which computes `circulating supply` as a raw subtraction of two independently-computed values, unlike the equivalent code path used by the `/v0/circulating-supply` REST endpoint.

### Title
Unsaturated subtraction in `getSupply` RPC handler can underflow/panic or return wrong circulating supply - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_supply` computes `circulating` supply with a plain `-` operator: [1](#0-0) 
```
Ok(new_response(
    &bank,
    RpcSupply {
        total: total_supply,
        circulating: total_supply - non_circulating_supply.lamports,
        non_circulating: non_circulating_supply.lamports,
        non_circulating_accounts,
    },
))
```
where `total_supply` is `bank.capitalization()` and `non_circulating_supply.lamports` is derived by scanning stake accounts via `calculate_non_circulating_supply`: [2](#0-1) 

Notably, the sibling `/v0/circulating-supply` REST handler, which performs the *exact same* computation from the same two inputs, uses `saturating_sub` instead: [3](#0-2) 
```
async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    ...
    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
}
```
This asymmetry between the two call sites (one saturating, one raw `-`) for the identical calculation is a strong signal that the raw subtraction in `get_supply` is an oversight, exactly analogous to the ECG report's `targetTotalSupply() - redeemableCredit()` pattern where two values that are computed independently (and can drift out of the assumed ordering) are subtracted without a floor/guard.

### Finding Description
`non_circulating_supply.lamports` is the sum of `bank.get_balance(pubkey)` over a specific `HashSet` of stake/lockup/foundation-controlled accounts (hardcoded list plus indexed stake-program accounts matching lockup/withdraw-authority criteria): [4](#0-3) 

`total_supply` is `bank.capitalization()`, an atomically-maintained running counter updated on every lamport-changing account store via `store_account_and_update_capitalization`: [5](#0-4) 

Under the normal invariant, capitalization always equals the sum of all account balances on the bank, so the non-circulating subset's lamports should never exceed it — for a single, internally consistent `Arc<Bank>` snapshot. However, the code makes no defensive assumption here: it uses raw `-` rather than `checked_sub`/`saturating_sub`, mirroring exactly the ECG anti-pattern where the report's author showed that these two "should always be consistent" values can, under certain deployment/config states (e.g., manually configured `non_circulating_accounts()`/`withdraw_authority()` lists in `runtime/src/non_circulating_supply.rs`, or a stale/incorrectly initialized capitalization on a non-genesis cluster type), diverge in a way that isn't caught by any type-level or explicit runtime invariant enforcement at this specific call site.

### Impact Explanation
- In a build compiled with debug assertions/overflow-checks enabled, an underflow here would trigger an arithmetic-overflow `panic!`, crashing the RPC-serving validator process for a single, unprivileged `getSupply` call — a concrete validator-process crash from one request.
- In a standard release build without overflow-checks, the subtraction silently wraps to a near-`u64::MAX` value, causing `getSupply` to return a grossly incorrect `circulating` field to any caller — wrong data returned from a read-only query, without requiring any special privileges.
- Either outcome is caused entirely by a single `getSupply` RPC call and requires no elevated permissions, matching the "wrong data returned" / "crash from one request" impact classes.

### Likelihood Explanation
Likelihood is Low-to-Medium: on a healthy, standard mainnet-configuration bank, `capitalization()` should always be ≥ the sum of any account subset's balances, so triggering this in practice requires either a custom/private cluster configuration, an inconsistency introduced by the non-circulating account list becoming stale relative to actual balances, or another latent bug that causes the two independently-derived values to diverge — similar to how the ECG bug required a specific PSM mint/burn/loss sequence to manifest. This is directly analogous to the "confirmed but Medium severity, needs a fix" judgment: it's real and worth fixing but not trivially triggerable in every deployment.

### Recommendation
Change `rpc/src/rpc.rs`'s `get_supply` to use `total_supply.saturating_sub(non_circulating_supply.lamports)`, matching the pattern already used in `calculate_circulating_supply_async` in `rpc_service.rs`, so the RPC method can never panic or wrap regardless of how the two independently-computed values relate.

### Proof of Concept
A fully concrete PoC (i.e., demonstrating an actual on-chain state where `non_circulating_supply.lamports > bank.capitalization()`) could not be constructed from static analysis alone; this would require driving a live bank into a state where the non-circulating account set's summed balance exceeds capitalization (e.g., via a custom non-mainnet cluster/genesis configuration or a bug elsewhere that decrements capitalization without correspondingly decrementing balances in the non-circulating account set) and then issuing a single `getSupply` JSON-RPC call to observe the panic (debug build) or wrapped/garbage `circulating` value (release build). This is noted as an area of uncertainty: I verified the code-level absence of a saturating guard and the inconsistency with the sibling REST handler, but did not verify a concrete state-reachability path to underflow within this codebase's tests/tools.

pub fn calculate_non_circulating_supply(bank: &Bank) -> ScanResult<NonCirculatingSupply> {
    debug!("Updating Bank supply, epoch: {}", bank.epoch());
    let mut non_circulating_accounts_set: HashSet<Pubkey> = HashSet::new();

    for key in non_circulating_accounts() {
        non_circulating_accounts_set.insert(key);
    }
    let withdraw_authority_list = withdraw_authority();

    let clock = bank.clock();
    let stake_accounts = if bank
        .rc
        .accounts
        .accounts_db
        .account_indexes
        .contains(&AccountIndex::ProgramId)
    {
        bank.get_filtered_indexed_accounts(
            &IndexKey::ProgramId(stake::program::id()),
            // The program-id account index checks for Account owner on inclusion. However, due to
            // the current AccountsDb implementation, an account may remain in storage as a
            // zero-lamport Account::Default() after being wiped and reinitialized in later
            // updates. We include the redundant filter here to avoid returning these accounts.
            |account| account.owner() == &stake::program::id(),
            None,
        )?
    } else {
        bank.get_program_accounts(&stake::program::id())?
    };

    for (pubkey, account) in stake_accounts.iter() {
        let stake_account = account
            .deserialize_data::<StakeStateV2>()
            .unwrap_or_default();
        match stake_account {
            StakeStateV2::Initialized(meta)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            StakeStateV2::Stake(meta, _stake, _stake_flags)
                if (meta.lockup.is_in_force(&clock, None)
                    || withdraw_authority_list.contains(&meta.authorized.withdrawer)) =>
            {
                non_circulating_accounts_set.insert(*pubkey);
            }
            _ => {}
        }
    }

    let lamports = non_circulating_accounts_set
        .iter()
        .map(|pubkey| bank.get_balance(pubkey))
        .sum();

    Ok(NonCirculatingSupply {
        lamports,
        accounts: non_circulating_accounts_set.into_iter().collect(),
    })
}

    pub(crate) fn store_account_and_update_capitalization(

                std::cmp::Ordering::Greater => {
                    let diff = new_account.lamports() - old_account.lamports();
                    trace!("store_account_and_update_capitalization: increased: {pubkey} {diff}");
                    self.capitalization.fetch_add(diff, Relaxed);
                }
                std::cmp::Ordering::Less => {
                    let diff = old_account.lamports() - new_account.lamports();
                    trace!("store_account_and_update_capitalization: decreased: {pubkey} {diff}");
                    self.capitalization.fetch_sub(diff, Relaxed);
                }
                std::cmp::Ordering::Equal => {}
            }
            old_account.data().len()
