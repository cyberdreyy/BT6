## Finding: `staking_contract::distribute_internal` can be DoS'd for all stakeholders via an unregistered/opted-out recipient - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` pays out every pending shareholder (the staker, the operator/its beneficiary, and any other stakers who have requested withdrawals) in a single atomic loop by calling `aptos_account::deposit_coins` for each recipient in turn. `deposit_coins` will abort with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if a recipient has never registered a `CoinStore`/primary store for `AptosCoin` and has opted out of unsolicited coin transfers via `set_allow_direct_coin_transfers(false)` (a fully unprivileged, self-service setting in `aptos_account.move`). Because a single failing deposit reverts the whole `distribute()` transaction, one uncooperative/negligent shareholder blocks payout to every other legitimate shareholder in the same staking contract — mirroring the JOJO "blacklist blocks liquidation for everyone" bug class, adapted to Aptos's staking_contract distribution flow.

### Finding Description
`distribute_internal` withdraws all potentially-distributable coins from the stake pool and then loops over every shareholder recorded in `distribution_pool`, paying each one out with `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` auto-creates the account if missing, but if the account already exists and has never registered a `CoinStore`/primary store for `AptosCoin`, it checks `can_receive_direct_coin_transfers`, which is controlled per-account by `DirectTransferConfig.allow_arbitrary_coin_transfers` — settable unprivileged by the account owner via `set_allow_direct_coin_transfers`. If this flag is `false`, the deposit aborts: [2](#0-1) 

Because the `while` loop in `distribute_internal` pays out *all* pending recipients (multiple stakers who called `unlock_stake`, plus the operator/beneficiary) inside one transaction with no per-recipient error isolation, a single recipient in that unresolved state causes the entire `distribute()`/`request_commission()`/`unlock_stake()` call to abort (these all invoke `distribute_internal` first, per `staking_contract.move:582-586, 624-629, 690-695`): [3](#0-2) 

By contrast, `vesting.move`'s `set_beneficiary` explicitly guards against exactly this scenario by requiring the new beneficiary to already be registered for APT before it can be set, specifically to avoid this failure mode: [4](#0-3) 

`staking_contract.move` has no equivalent registration check anywhere in the `unlock_stake` → `add_distribution` → `distribute_internal` path for the staker, nor for `beneficiary_for_operator`, meaning the DoS-inducing precondition (unregistered account + opted-out `DirectTransferConfig`) can arise unprivileged, either intentionally or accidentally, for any of the staking-contract shareholders.

### Impact Explanation
Because `distribute_internal` is invoked as a mandatory prerequisite step inside `unlock_stake`, `request_commission`, and `update_commision` (all of which are called on shared staking-contract state), one shareholder in the unresolved state permanently blocks:
- The operator (or its beneficiary) from ever collecting commission,
- Every other staker who has unlocked stake from that same staker/operator pair from ever withdrawing,
- The staker from changing commission percentage or requesting further unlocks that trigger distribution.

This causes rewards/commission/principal belonging to unrelated accounts to become stuck indefinitely in the stake pool's distribution pool, a value-stranding condition matching the "Permanent lock or non-recoverable loss of claim rights" and "commission/beneficiary...corruption that... traps value" impact categories from the gate.

### Likelihood Explanation
Triggering the precondition requires no special privilege: any account can call `aptos_account::set_allow_direct_coin_transfers(signer, false)` on itself, and simply never registering for `AptosCoin` beforehand is the default state for a freshly created account (e.g. one created via `create_account` inside `deposit_coins` itself, or one that has never received APT). A malicious staker, operator, or beneficiary participating in a `staking_contract` could deliberately do this to grief co-shareholders, or it could occur accidentally.

### Recommendation
- In `distribute_internal`, isolate failures per-recipient (e.g., wrap each `aptos_account::deposit_coins` call so a failure for one recipient does not abort payouts to the others — e.g. skip and re-queue that recipient's shares, similar to how `vesting::set_beneficiary` pre-emptively requires registration).
- Alternatively, require registration/`assert_account_is_registered_for_apt`-style checks before adding a new distribution recipient (in `add_distribution`) or before allowing `set_beneficiary_for_operator`, so the DoS precondition can never be introduced through the staking_contract's own entry points.

### Proof of Concept
1. Staker `S` creates a staking contract with operator `O` and commission `10%` via `staking_contract::create_staking_contract`.
2. A second staker/beneficiary account `B` (distinct EOA, e.g. `O`'s beneficiary set via `set_beneficiary_for_operator`, or a co-staker sharing the same operator) is a fresh account that has never registered for `AptosCoin`, and calls `aptos_account::set_allow_direct_coin_transfers(&B_signer, false)`.
3. Stake pool earns rewards; `O` calls `staking_contract::request_commission(O, S, O)`; internally this calls `distribute_internal`, which iterates the `distribution_pool` shareholders including `B`.
4. When the loop reaches `B` and calls `aptos_account::deposit_coins(B, ...)`, it aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` since `B` is unregistered and has opted out.
5. The whole `distribute()`/`request_commission()` transaction reverts — so neither `O`'s commission nor any other staker's already-requested withdrawal in the same distribution pool can be paid out until `B` fixes its own config, even though `B`'s state is fully under `B`'s own control and unrelated parties have no way to force it.

I was not able to fully verify from the index whether `coin::is_account_registered<AptosCoin>` treats "primary store created with zero balance from an unrelated prior deposit" identically to "never interacted," nor whether `MAXIMUM_PENDING_DISTRIBUTIONS` or some other bound indirectly limits blast radius; a Devin session with full repo/test access should confirm the exact abort conditions end-to-end with a Move unit test before treating this as fully proven.

    /// This also triggers paying commission to the operator for accounting simplicity.
    public entry fun unlock_stake(
        staker: &signer, operator: address, amount: u64
    ) acquires Store, BeneficiaryForOperator {
        // Short-circuit if amount is 0.
        if (amount == 0) return;

        let staker_address = signer::address_of(staker);
        assert_staking_contract_exists(staker_address, operator);

        let store = borrow_global_mut<Store>(staker_address);
        let staking_contract = store.staking_contracts.borrow_mut(&operator);

        // Force distribution of any already inactive stake.
        distribute_internal(
            staker_address,
            operator,
            staking_contract,
        );

        // For simplicity, we request commission to be paid out first. This avoids having to ensure to staker doesn't
        // withdraw into the commission portion.
        let commission_paid =
            request_commission_internal(
                operator,
                staking_contract,
            );

        // If there's less active stake remaining than the amount requested (potentially due to commission),
        // only withdraw up to the active amount.
        let (active, _, _, _) = stake::get_stake(staking_contract.pool_address);
        if (active < amount) {
            amount = active;
        };
        staking_contract.principal -= amount;

        // Record a distribution for the staker.
        add_distribution(
            operator,
            staking_contract,
            staker_address,
            amount,
        );
