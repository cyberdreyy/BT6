### Title
Default recovery claims can be silently redirected to an arbitrary recipient - ([File: contracts/DefaultDistributor.sol](contracts/DefaultDistributor.sol))

### Summary
`DefaultDistributor.claim` always claims the caller’s entire tranche-token balance but sends the recovery payout to a caller-supplied `_to` address rather than binding it to `msg.sender`. A malicious frontend can therefore present an ordinary recovery claim while supplying an attacker-controlled recipient, causing the victim’s signed transaction to divert the full claim proceeds. The vulnerable behavior is in `claim`, which computes `trancheBal` from `msg.sender`, pulls that full balance, and transfers the underlying to `_to`. [1](#0-0) 

### Finding Description
After a borrower default, the honest owner activates the distributor and fixes the global redemption rate from its underlying balance and tranche-token supply. [2](#0-1)  Any tranche holder can then call `claim(_to)`, but the function contains no check that `_to == msg.sender` and no partial-amount parameter. [1](#0-0) 

In a finalized/defaulted distribution phase, a malicious dapp can request a transaction described as “claim recovery” while encoding the attacker as `_to`. If the victim signs that transaction, the contract:

1. Reads the victim’s full tranche balance.
2. Pulls all of those tranche tokens into the distributor.
3. Sends the entire proportional recovery amount to the attacker.

This is the protocol-level analogue of the signing-identity ambiguity: the economic sender and the payout beneficiary are separate, but the contract does not enforce that they are the same party.

### Impact Explanation
A victim can permanently lose 100% of their available default-recovery payout for that distributor. The transferred tranche tokens remain locked in the distributor, while the victim receives no underlying tokens. The loss equals `victimTrancheBalance * rate / 1e18`.

The broken invariant is “one receipt, one payout to the receipt holder”: the holder’s entire claim is consumed, but its proceeds are delivered to an independent address. The existing `isActive` check only establishes that claims are open; it does not constrain the payout recipient. [1](#0-0) 

### Likelihood Explanation
The attack requires victim interaction and a malicious frontend or transaction constructor, but no privileged role is compromised. The attacker can be any EOA or contract receiving `_to`; the owner remains honest and only activates the legitimate distribution. Recovery distributions are attractive phishing targets because victims expect to sign a claim transaction and may not inspect the low-level `_to` parameter.

### Recommendation
Bind the recovery payout to the authenticated claimant:

```solidity
function claim() external {
    require(isActive, '!ACTIVE');
    IERC20 tranche = IERC20(trancheToken);
    uint256 trancheBal = tranche.balanceOf(msg.sender);
    tranche.safeTransferFrom(msg.sender, address(this), trancheBal);
    IERC20(token).safeTransfer(msg.sender, trancheBal * rate / ONE_TRANCHE);
}
```

If third-party or smart-account beneficiaries must remain supported, require `_to == msg.sender` unless a separate, explicitly auditable beneficiary-authorization mechanism is added. The frontend should additionally display the exact beneficiary before signing.

### Proof of Concept
The following Foundry test can be run on a mainnet fork. It deploys the in-scope distributor with deterministic ERC20 fixtures, activates an honest recovery distribution, and shows a victim-signed claim sending the entire payout to an attacker.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "../contracts/DefaultDistributor.sol";

contract MockToken is ERC20 {
    constructor(string memory name, string memory symbol) ERC20(name, symbol) {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }
}

contract DefaultDistributorRecipientRedirectPoC is Test {
    MockToken internal underlying;
    MockToken internal tranche;
    DefaultDistributor internal distributor;

    address internal owner = makeAddr("owner");
    address internal victim = makeAddr("victim");
    address internal attacker = makeAddr("attacker");

    function setUp() public {
        // Required by the audit PoC format; the deterministic state is deployed below.
        vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

        underlying = new MockToken("Underlying", "UND");
        tranche = new MockToken("Defaulted Tranche", "TR");
        distributor = new DefaultDistributor(
            address(underlying),
            address(tranche),
            owner
        );
    }

    function testClaimRecipientRedirect() public {
        uint256 victimTranches = 100e18;
        uint256 recoveryAssets = 100e18;

        tranche.mint(victim, victimTranches);
        underlying.mint(address(distributor), recoveryAssets);

        vm.prank(owner);
        distributor.setIsActive(true);

        vm.prank(victim);
        tranche.approve(address(distributor), victimTranches);

        // Malicious frontend encodes the attacker as `_to`; the victim signs.
        vm.prank(victim);
        distributor.claim(attacker);

        assertEq(tranche.balanceOf(victim), 0);
        assertEq(underlying.balanceOf(victim), 0);
        assertEq(underlying.balanceOf(attacker), recoveryAssets);
    }
}
```

Run with:

```bash
MAINNET_RPC_URL=<rpc-url> forge test \
  --match-contract DefaultDistributorRecipientRedirectPoC \
  -vvvv
```
