### Title
EI-authenticated requests bypass the "EI not allowed" restriction in `PipelineRunsController.Create` due to `isUser` being derived only from `SessionUserKey` presence - ([File: core/web/pipeline_runs_controller.go], [File: core/web/auth/auth.go])

### Summary
`PipelineRunsController.Create` decides whether to allow int32-ID job runs based on `isUser := auth.GetAuthenticatedUser(c)` ok-bool, but `AuthenticateExternalInitiator` also sets `SessionUserKey` to a synthetic `UserRoleRun` user, so `isUser` is true for EI-authenticated requests too. This defeats the code comment's intent ("EIs not allowed") and lets an EI-credential holder call `App.RunJobV2` on any numeric job ID regardless of job type.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered under the `userOrEI` group with `auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession` and `auth.RequiresRunRole(prc.Create)`: [1](#0-0) 

`AuthenticateExternalInitiator` authenticates purely via EI access key/secret headers and then sets both `SessionExternalInitiatorKey` and, critically, `SessionUserKey` to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}`: [2](#0-1) 

`GetAuthenticatedUser` simply checks for the presence of `SessionUserKey` in the gin context, with no way to distinguish a real user session/token from a synthetic EI-derived user: [3](#0-2) 

In `PipelineRunsController.Create`, the comment states "only users are allowed to run jobs using int IDs - EIs not allowed", but the actual gate `isUser` is true for both real users and EI callers because both set `SessionUserKey`: [4](#0-3) 

Consequently, if the `:ID` path parameter parses as an int32 (rather than a UUID, which is now rejected because webhook jobs use UUID external IDs and that job type was removed for direct triggering), the handler calls `prc.App.RunJobV2(ctx, jobID, nil)` unconditionally for any job type — cron, flux monitor, OCR, VRF, etc. `RunJobV2` itself performs no EI-vs-user or job-type gating; it looks the job up by numeric ID and executes its pipeline spec directly: [5](#0-4) 

The only mitigating check in `RunJobV2` is a build-mode guard: manual job runs are rejected entirely in secure/production builds (`build.IsProd()`), but in non-prod (dev) builds this guard is absent, and the request succeeds.

### Impact Explanation
An attacker holding only an External Initiator credential (which is intended to be limited to triggering webhook job runs) can invoke `RunJobV2` against arbitrary non-webhook job types (cron, flux monitor, OCR bootstrap/VRF pipelines, etc.) by supplying that job's numeric database ID instead of a UUID. This is an authorization-bypass / unauthorized-job-run issue: EI credentials are meant to be scoped to webhook initiation, but the "EI not allowed" comment's intended restriction is not actually enforced because `isUser` cannot distinguish EI-origin from genuine user sessions. This could trigger unintended pipeline executions (side effects, fund-moving transaction tasks, VRF request replays, etc.) outside the EI's intended scope, in any node running a non-secure/dev build.

### Likelihood Explanation
Preconditions: only an EI access key/secret pair is required (unprivileged, non-admin credential) and the target node must not be built with the secure/production build tag (`build.IsProd()` must be false) for `RunJobV2` to proceed past its guard. Given that the EI route is explicitly wired to accept `AuthenticateExternalInitiator` for this exact endpoint, and the `isUser` check does nothing to actually filter it out, exploitation requires no special timing or race — it's a straightforward, repeatable HTTP call with a numeric job ID.

### Recommendation
Introduce an explicit `IsEI`/`IsExternalInitiator` flag distinct from `SessionUserKey` presence (e.g., check `auth.GetAuthenticatedExternalInitiator(c)` to detect EI origin), and reject EI-originated requests to `PipelineRunsController.Create` outright, or restrict `RunJobV2` calls sourced from EI auth to jobs of type `job.Webhook` only. Do not rely on `SessionUserKey` presence alone to differentiate "user" vs "EI" callers.

### Proof of Concept
1. In `core/web/pipeline_runs_controller_test.go`, create an EI credential via `bridges.NewExternalInitiator`/`app.BridgeORM().CreateExternalInitiator`, mirroring `TestTokenAuthRequired_TokenCredentials`.
2. Create a non-webhook job (e.g., the OCR job from `setupPipelineRunsControllerTests`) and note its int32 `jb.ID`.
3. Issue `POST /v2/jobs/<jb.ID>/runs` with headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to the EI's credentials (no session/API token).
4. Assert that in a non-prod test build the response is `200 OK` with a new pipeline run created (`RunJobV2` executed) — demonstrating an EI-only credential successfully triggered a non-webhook job run, contradicting the intended "EIs not allowed" restriction.
5. Add a fix-verifying assertion: after the recommended fix, the same request should return `422`/`401` with an error indicating EI credentials cannot trigger non-webhook or int-ID job runs.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}

func (app *ChainlinkApplication) RunJobV2(
	ctx context.Context,
	jobID int32,
	meta map[string]any,
) (int64, error) {
	if build.IsProd() {
		return 0, errors.New("manual job runs not supported on secure builds")
	}
	jb, err := app.jobORM.FindJob(ctx, jobID)
	if err != nil {
		return 0, errors.Wrapf(err, "job ID %v", jobID)
	}
	var runID int64

	// Some jobs are special in that they do not have a task graph.
	isBootstrap := jb.Type == job.OffchainReporting && jb.OCROracleSpec != nil && jb.OCROracleSpec.IsBootstrapPeer
	if jb.Type.RequiresPipelineSpec() || !isBootstrap {
		var vars map[string]any
		var saveTasks bool
		if jb.Type == job.VRF {
			saveTasks = true
			// Create a dummy log to trigger a run
			testLog := types.Log{
				Data: bytes.Join([][]byte{
					jb.VRFSpec.PublicKey.MustHash().Bytes(),  // key hash
					common.BigToHash(big.NewInt(42)).Bytes(), // seed
					evmutils.NewHash().Bytes(),               // sender
					evmutils.NewHash().Bytes(),               // fee
					evmutils.NewHash().Bytes(),
				}, // requestID
					[]byte{}),
				Topics:      []common.Hash{{}, jb.ExternalIDEncodeBytesToTopic()}, // jobID BYTES
				TxHash:      evmutils.NewHash(),
				BlockNumber: 10,
				BlockHash:   evmutils.NewHash(),
			}
			vars = map[string]any{
				"jobSpec": map[string]any{
					"databaseID":    jb.ID,
					"externalJobID": jb.ExternalJobID,
					"name":          jb.Name.ValueOrZero(),
					"publicKey":     jb.VRFSpec.PublicKey[:],
					"evmChainID":    jb.VRFSpec.EVMChainID.String(),
				},
				"jobRun": map[string]any{
					"meta":           meta,
					"logBlockHash":   testLog.BlockHash[:],
					"logBlockNumber": testLog.BlockNumber,
					"logTxHash":      testLog.TxHash,
					"logTopics":      testLog.Topics,
					"logData":        testLog.Data,
				},
			}
		} else {
			vars = map[string]any{
				"jobRun": map[string]any{
					"meta": meta,
				},
			}
		}
		runID, _, err = app.pipelineRunner.ExecuteAndInsertFinishedRun(ctx, *jb.PipelineSpec, pipeline.NewVarsFrom(vars), saveTasks)
	}
	return runID, err
}
