## Analysis Result

I found a concrete unbounded-scan analog in the RPC layer matching the reported bug class (cheap attacker-created state causing an unbounded iteration/DoS on a mandatory code path).

### Title
Unbounded memory allocation in `getProgramAccounts` RPC scan when secondary indexes are disabled, enabling attacker-funded account spam to crash/exhaust RPC nodes - (File: `rpc/src/rpc.rs`, `accounts-db/src/accounts.rs`)

### Summary
When a validator's JSON-RPC node does not have the `program-id` secondary account index enabled (the default configuration), `getProgramAccounts` requests are served via `Bank::get_filtered_program_accounts` → `Accounts::load_by_program_with_filter`, which performs a full accounts-db scan with **no size/byte limit and no abort mechanism**. This is unlike the sibling indexed path, which enforces `byte_limit_for_scan` and aborts the scan once results exceed `scan_results_limit_bytes`. An attacker can cheaply create a large number of small accounts owned by an arbitrary program ID and then repeatedly call `getProgramAccounts` for that program, forcing the node to materialize an unbounded `Vec<(Pubkey, AccountSharedData)>` in memory on every request.

### Finding Description
`JsonRpcRequestProcessor::get_filtered_program_accounts` branches on whether the `ProgramId` account index is configured: [1](#0-0) 

- If the index **is** enabled, it calls `get_filtered_indexed_accounts`, which passes `self.config.scan_results_limit_bytes` down to `Bank::get_filtered_indexed_accounts` → `Accounts::load_by_index_key_with_filter`, which tracks accumulated result size via `accumulate_and_check_scan_result_size` and aborts the scan (`ScanError::Aborted`) once the limit is exceeded: [2](#0-1) [3](#0-2) 

- If the index is **not** enabled (the default, since these indexes are opt-in and memory-expensive), the code explicitly documents that it skips any byte limit ("this path does not need to provide a mb limit because we only want to support secondary indexes") and calls `Bank::get_filtered_program_accounts`, which in turn calls `Accounts::load_by_program_with_filter` using a bare `ScanConfig::default()` with no abort/size tracking at all: [4](#0-3) [5](#0-4) [6](#0-5) 

Any user can create accounts owned by an arbitrary (even non-executable) program ID for the cost of the rent-exempt minimum balance, analogous to the "dust deposit" spam in the original report. Since ordinary Solana RPC deployments commonly run without the memory-heavy secondary indexes enabled, this unbounded path is the default one actually exercised in production for `getProgramAccounts`, `getTokenAccountsByOwner` (fallback), and `getTokenAccountsByDelegate` (fallback), all of which route through `get_filtered_program_accounts` when the corresponding index is absent: [7](#0-6) [8](#0-7) 

### Impact Explanation
Repeated calls against a program ID with a large number of attacker-created accounts force the RPC node to allocate unbounded memory per request (each matching account's full data plus overhead is collected into a `Vec`), with no per-scan cap. This can exhaust node memory and crash the RPC process (`RPC crash` under the allowed impact categories), degrading service for all clients of that node. Because RPC nodes typically run on the same host as (or closely coupled to) validator infrastructure, an OOM condition can also affect co-located validator processes, indirectly threatening liveness.

### Likelihood Explanation
High. No special privileges are required — anyone can create low-cost accounts owned by a chosen program ID and repeatedly issue `getProgramAccounts` calls. The condition (secondary indexes disabled) is the common/default operational posture, since enabling `--account-index program-id` is itself memory-intensive and not universally deployed. This mirrors the report's "spamming dust deposits" pattern: cheap, repeatable attacker actions build up unbounded state consumed by a mandatory, unguarded scan path.

### Recommendation
Apply the same `byte_limit_for_scan` / abort-on-exceed mechanism used in `Accounts::load_by_index_key_with_filter` (`accumulate_and_check_scan_result_size` + `ScanConfig::recreate_with_abort`) to the non-indexed `Accounts::load_by_program_with_filter` / `Bank::get_filtered_program_accounts` path, and thread `self.config.scan_results_limit_bytes` through `get_filtered_program_accounts` in `rpc/src/rpc.rs` regardless of whether the secondary index is enabled.

### Proof of Concept
1. Configure or use a validator RPC node without `--account-index program-id` enabled (default).
2. Create a large number (e.g., hundreds of thousands) of system-owned-then-reassigned or custom-owned accounts, each at the rent-exempt minimum, all owned by the same arbitrary `program_id`.
3. Call `getProgramAccounts(program_id)` via JSON-RPC repeatedly/concurrently.
4. Observe that `Accounts::load_by_program_with_filter` (via `scan_accounts` with `ScanConfig::default()`) collects every matching account into memory with no abort, unlike the indexed path which would trip `ScanError::Aborted` once `scan_results_limit_bytes` is exceeded — demonstrating the missing bound.

    fn calc_scan_result_size(account: &AccountSharedData) -> usize {
        account.data().len()
            + std::mem::size_of::<AccountSharedData>()
            + std::mem::size_of::<Pubkey>()
    }

    /// Accumulate size of (pubkey + account) into sum.
    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }

    fn maybe_abort_scan(
        result: ScanResult<Vec<KeyedAccountSharedData>>,
        config: &ScanConfig,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        if config.is_aborted() {
            ScanResult::Err(ScanError::Aborted(
                "The accumulated scan results exceeded the limit".to_string(),
            ))
        } else {
            result
        }
    }

    pub fn load_by_index_key_with_filter<F: Fn(&AccountSharedData) -> bool>(
        &self,
        ancestors: &Ancestors,
        bank_id: BankId,
        index_key: &IndexKey,
        filter: F,
        byte_limit_for_scan: Option<usize>,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let sum = AtomicUsize::default();
        let config = ScanConfig::default().recreate_with_abort();
        let mut collector = Vec::new();
        let result = self
            .accounts_db
            .index_scan_accounts(
                ancestors,
                bank_id,
                *index_key,
                |some_account_tuple| {
                    Self::load_while_filtering(&mut collector, some_account_tuple, |account| {
                        let use_account = filter(account);
                        if use_account
                            && Self::accumulate_and_check_scan_result_size(
                                &sum,
                                account,
                                &byte_limit_for_scan,
                            )
                        {
                            // total size of results exceeds size limit, so abort scan
                            config.abort();
                        }
                        use_account
                    });
                },
                &config,
            )
            .map(|_| collector);
        Self::maybe_abort_scan(result, &config)
    }
