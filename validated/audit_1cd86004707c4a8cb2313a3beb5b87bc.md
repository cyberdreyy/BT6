### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`, also `multisig/src/lib.rs`)

### Summary
In both `multisig` and `multisig2`, when a member/key confirms a pending request, that confirmation is stored independently of the member's continued membership. When a member is later removed via `DeleteMember` (`multisig2`) or `DeleteKey` (`multisig`), the contract only purges requests that the removed member **created**, but not the confirmations that member **cast on other still-pending requests**. Those stale confirmations continue to count toward `num_confirmations`, so a request can later execute after being approved by fewer live members than the configured threshold.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` stores each approving member's identity in a per-request `confirmations: HashSet<String>` and executes once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

Member removal is handled by `delete_member()`, which only cleans up requests where the removed member is the *original signer* (`r.member == member`) — i.e., requests that member created — and removes that member from `self.num_requests_pk` and `self.members`. It does **not** scan other pending requests to strip the removed member's confirmation from their `confirmations` set: [2](#0-1) 

So if member `B` confirms request `R` (created by `A`) without reaching quorum, and is later removed via a separate, properly-confirmed `DeleteMember` request, `R`'s `confirmations` set still contains `B`. When another live member (`A` or `C`) subsequently confirms `R`, `confirmations.len() + 1 >= num_confirmations` uses `B`'s stale entry to help satisfy the threshold, even though `B` is no longer a member and could not confirm anything today.

The binding that should hold is:
`confirmations counted for execution == confirmations from members that are live at execution time`

This is broken because the confirmation set is never re-validated or pruned against current membership, only the constructor invariant `members.len() >= num_confirmations` is checked at member-removal time (`delete_member`'s `self.members.len() - 1 >= self.num_confirmations` assert): [3](#0-2) 

The legacy `multisig` contract has the identical defect: `DeleteKey` removes requests created by the deleted public key but leaves that key's confirmations intact on other pending requests: [4](#0-3) [5](#0-4) 

### Impact Explanation
This lets a multisig execute a request (transfer of NEAR, key/member management, function calls, etc.) with fewer **live** confirmations than `num_confirmations` requires, because a removed member's stale approval is silently counted. This directly breaks the "K-of-N live members" custody guarantee the contract is documented to provide, and falls under the Critical impact class "a multisig request executed below threshold" — funds or privileged actions can move with less real authorization than the configured policy demands.

### Likelihood Explanation
Requires only ordinary operational activity: a member confirms a request that doesn't immediately reach quorum, and is later removed through a normal, correctly-authorized `DeleteMember`/`DeleteKey` request (e.g., an employee off-boarding, a compromised key rotation, or routine membership rebalancing). No malicious deployment, redeploy, or victim key theft is needed — the surviving members simply confirm the still-pending request afterward, unaware that a phantom vote from a removed member is being counted.

### Recommendation
When removing a member/key, iterate over **all** pending requests' `confirmations` sets (not just requests the member created) and strip the removed member's entry. Alternatively, validate at `confirm()`/execution time that every account/key in a request's `confirmations` set is still a current member (e.g., by intersecting the stored confirmation set with `self.members` before comparing against `num_confirmations`), so only live members' approvals are ever counted.

### Proof of Concept
1. Initialize `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request` to create request `R` (e.g., `Transfer` to some receiver) — `R.member = A`, `confirmations = {}`.
3. `B` calls `confirm(R)` → `confirmations.len() (0) + 1 = 1 < 2`, so `B` is added: `confirmations = {B}`. `R` stays pending.
4. Separately, members confirm a `DeleteMember { member: B }` request (created by, say, `C`, confirmed by `A`) reaching threshold 2, executing `delete_member` for `B`. This only removes requests where `r.member == B`; `R` (created by `A`) is untouched, so `R.confirmations` still contains `B`. `members` is now `{A, C}`, still satisfying `members.len() - 1 >= num_confirmations` check performed *before* removal (3-1=2 >= 2).
5. `A` calls `confirm(R)`. `confirmations.len() (1, containing removed member B) + 1 = 2 >= num_confirmations (2)` → `R` executes.
6. Result: `R` (e.g., a `Transfer`) executes with authorization from only one truly live member (`A`), because `B`'s stale confirmation—cast before removal—was counted as if `B` were still a member, defeating the 2-of-N live-member guarantee. The same flow applies to `multisig/src/lib.rs` using `DeleteKey` instead of `DeleteMember`.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
