### Title
Unsigned `response_data`/`metadata` fields in `BlockAccepted`/`BlockRejection` let a relay tamper with vote-influencing fields without invalidating the signer's signature - ([File: libsigner/src/v0/messages.rs])

### Summary
`BlockAccepted` and `BlockRejection` (the two variants of `BlockResponse` that carry a signer's cryptographic vote on a block) sign only the block's `signer_signature_hash`, not the `response_data` (`tenure_extend_timestamp`, `read_count_extend_timestamp`, `reject_reason`, `failed_txid`) or `metadata` (`server_version`) fields that ride alongside it in the same struct and same signed StackerDB chunk. This is structurally identical to the Keycloak flaw: a signed envelope carries extra fields that are not covered by the signature, so anyone who can touch the message in transit (StackerDB relay/read path) can rewrite those fields while the signature still verifies.

### Finding Description
`BlockAccepted::signature` is produced/verified purely over the block's `signer_signature_hash` bytes: [1](#0-0) 
and consumers such as `handle_block_signature` in the v0 signer recover the public key the same way, from `block_hash.bits()` and `signature` alone: [2](#0-1) 

`BlockRejection` is similar: its `hash()`/`sign()`/`verify()` only ever hash `self.signer_signature_hash` under the SIP-018 domain `"block-rejection"`: [3](#0-2) 

Yet both structs carry additional, unsigned fields — `metadata: SignerMessageMetadata` and `response_data: BlockResponseData` (which bundles `tenure_extend_timestamp`, `read_count_extend_timestamp`, `reject_reason`, and `failed_txid`): [4](#0-3) 

Both structs are serialized as one blob and both are read/verified as one blob by downstream consumers, so an attacker capable of intercepting/rewriting the StackerDB chunk before it reaches a peer signer or the node (a relay/gossip-path actor, in scope per the analog rules) can flip `response_data.reject_reason`, tamper with `response_data.failed_txid`, or change `tenure_extend_timestamp`/`read_count_extend_timestamp`, and the signature check performed by the receiver (`rejection.verify(pubkey)` / `signer_pubkey.verify(block_sighash.bits(), &signature)`) will still pass, because it never touches those bytes.

Downstream consumers trust these fields as if they were part of the signed statement:
- The node's `StackerDBListener` uses `rejected_data.response_data.failed_txid` and `rejected_data.reason_code` to accumulate per-txid rejection weight used to decide which transactions are "problematic" and should be dropped from future blocks: [5](#0-4) 
- Peer signers log and act on `rejection.response_data.reject_reason` when tallying rejections (`handle_block_rejection` → `store_and_process_block_rejection`), and on `accepted.response_data.tenure_extend_timestamp` when tallying acceptances (`handle_block_signature`): [6](#0-5) [7](#0-6) 

Because `reject_reason` also gates whether a signer's own past decision on a block is "re-evaluable" (`should_reevaluate_reject_reason`) once a re-proposal arrives, a tampered `reject_reason` value received from a peer and stored in pending-response tables can steer that peer's future re-evaluation path.

### Impact Explanation
This does not directly let an attacker forge an accept/reject vote for a block the signer never voted on — the block identity (`signer_signature_hash`) itself is signed. But it breaks the equality "the signed statement == the data acted upon" for every auxiliary field riding alongside it: a relay can change *why* a signer says it rejected a block (`reject_reason`, `failed_txid`) or *when* it says it's willing to extend a tenure (`tenure_extend_timestamp`/`read_count_extend_timestamp`) without invalidating that signer's genuine signature. That can cause the node to mis-attribute a "problematic transaction" weight to the wrong txid (affecting future block construction/censoring decisions) or cause peer signers to mis-tally tenure-extend willingness/reject-reason bookkeeping used in their re-evaluation and liveness logic — a manipulation of miscounted/misattributed signer intent rather than a forged signature, landing at the boundary of the "rejection recounted/miscounted" impact class described in the rules. It requires an on-path relay capability (StackerDB message tamperer) rather than a majority of signers or key compromise, consistent with the scope.

### Likelihood Explanation
Requires the ability to intercept and modify a StackerDB chunk in flight before it's independently re-verified by the receiver as an atomic signed blob (i.e., a malicious/compromised relay, gossip peer, or MITM on the StackerDB read/write path) — a "one-slot miner plus gossip"-class actor is not literally in this position (StackerDB writes are per-signer, authenticated at the transport layer separately), so exploitability depends on whether the transport-layer StackerDB chunk signature (out of scope per the rules) is the only thing standing between the attacker and mutating these fields. Within the signer-message layer alone, the fields are demonstrably unauthenticated, but turning this into a fielded exploit needs a channel that lets a party other than the honest signer rewrite the chunk contents post-signature — moderate likelihood, gated on transport assumptions outside this analysis's scope.

### Recommendation
Include `response_data` (and, if it must remain trusted, `metadata`) inside the signed digest for both `BlockAccepted` and `BlockRejection` — e.g., extend `BlockRejection::hash()` to hash `signer_signature_hash || response_data` (and similarly extend the signed message for `BlockAccepted`) so any downstream consumer that trusts `reject_reason`, `failed_txid`, `tenure_extend_timestamp`, or `read_count_extend_timestamp` is cryptographically guaranteed those values originated from the signer that produced the signature.

### Proof of Concept
1. Capture a genuine `SignerMessage::BlockResponse(BlockResponse::Rejected(rejection))` chunk as broadcast by an honest signer, where `rejection.response_data.failed_txid = Some(txid_A)` and `reason_code = ValidationFailed(BadTransaction)` (mirrors the manual test construction pattern used in the codebase): [8](#0-7) 
2. Deserialize it, mutate `response_data.failed_txid` to `txid_B` (or flip `reason_code`), and re-serialize — leaving `signature` and `signer_signature_hash` untouched.
3. Re-verify: `rejection.verify(&signer_pubkey)` still returns `Ok(true)` because `hash()` only covers `signer_signature_hash`: [9](#0-8) 
4. Deliver the tampered chunk; `StackerDBListener::process_signer_messages` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:501-543`) accepts it as authentic and attributes rejection weight to `txid_B` instead of `txid_A`, or a peer signer records the forged `reject_reason` for future re-evaluation decisions.

/// A rejection response from a signer for a proposed block
#[derive(Clone, Debug, PartialEq, Serialize, Deserialize)]
pub struct BlockAccepted {
    /// The signer signature hash of the block that was accepted
    pub signer_signature_hash: Sha512Trunc256Sum,
    /// The signer's signature across the acceptance
    pub signature: MessageSignature,
    /// Signer message metadata
    pub metadata: SignerMessageMetadata,
    /// Extra versioned block response data
    pub response_data: BlockResponseData,
}

impl StacksMessageCodec for BlockAccepted {
    fn consensus_serialize<W: Write>(&self, fd: &mut W) -> Result<(), CodecError> {
        write_next(fd, &self.signer_signature_hash)?;
        write_next(fd, &self.signature)?;
        write_next(fd, &self.metadata)?;
        write_next(fd, &self.response_data)?;
        Ok(())
    }

    fn consensus_deserialize<R: Read>(fd: &mut R) -> Result<Self, CodecError> {
        let signer_signature_hash = read_next::<Sha512Trunc256Sum, _>(fd)?;
        let signature = read_next::<MessageSignature, _>(fd)?;
        let metadata = read_next::<SignerMessageMetadata, _>(fd)?;
        let response_data = read_next::<BlockResponseData, _>(fd)?;
        Ok(Self {
            signer_signature_hash,
            signature,
            metadata,
            response_data,
        })
    }
}

impl BlockAccepted {
    /// Create a new BlockAccepted for the provided block signer signature hash and signature
    pub fn new(
        signer_signature_hash: Sha512Trunc256Sum,
        signature: MessageSignature,
        full_extend_ts: u64,
        read_count_extend_ts: u64,
    ) -> Self {
        Self {
            signer_signature_hash,
            signature,
            metadata: SignerMessageMetadata::default(),
            response_data: BlockResponseData::new(
                full_extend_ts,
                RejectReason::NotRejected,
                read_count_extend_ts,
                None,
            ),
        }
    }
}

    /// The signature hash for the block rejection
    pub fn hash(&self) -> Sha256Sum {
        let domain_tuple = make_structured_data_domain("block-rejection", "1.0.0", self.chain_id);
        let data = Value::buff_from(self.signer_signature_hash.as_bytes().into()).unwrap();
        structured_data_message_hash(data, domain_tuple)
    }

    /// Sign the block rejection and set the internal signature field
    fn sign(&mut self, private_key: &StacksPrivateKey) -> Result<(), String> {
        let signature_hash = self.hash();
        self.signature = private_key.sign(signature_hash.as_bytes())?;
        Ok(())
    }

    /// Verify the rejection's signature against the provided signer public key
    pub fn verify(&self, public_key: &StacksPublicKey) -> Result<bool, String> {
        if self.signature == MessageSignature::empty() {
            return Ok(false);
        }
        let signature_hash = self.hash();
        public_key
            .verify(&signature_hash.0, &self.signature)
            .map_err(|e| e.to_string())
    }
