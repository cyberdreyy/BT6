### Title
ERC20/ETH Decimal-Conversion Truncation Permanently Locks User Dust in BridgeVault - (File: bridge/evm/contracts/utils/BridgeUtils.sol)

### Summary

`BridgeUtils.convertERC20ToSuiDecimal` performs integer division to scale an EVM token amount down to Sui's decimal precision. The full EVM amount is transferred into `BridgeVault` before the conversion, but only the truncated (rounded-down) Sui-adjusted amount is recorded in the `TokensDeposited` event and subsequently minted on Sui. The remainder (`amount % factor`) is permanently locked in the vault with no recovery path.

### Finding Description

In `SuiBridge.bridgeERC20` and `SuiBridge.bridgeETH` (and their V2 counterparts), the deposit flow is:

1. The full user-supplied `amount` is transferred into `BridgeVault` via `safeTransferFrom` / `call{value: amount}`.
2. `BridgeUtils.convertERC20ToSuiDecimal` is called to produce `suiAdjustedAmount`.
3. Inside that function, integer division silently discards the sub-precision remainder:

```solidity
// bridge/evm/contracts/utils/BridgeUtils.sol L141-142
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
amount = amount / factor;   // dust = amount % factor is silently dropped
```

4. The `TokensDeposited` event is emitted with `suiAdjustedAmount` (the truncated value).
5. Bridge validators observe the event and mint exactly `suiAdjustedAmount` on Sui.
6. The dust (`original_amount % factor`) remains in `BridgeVault` forever.

`BridgeVault` exposes only `transferERC20` and `transferETH`, both `onlyOwner` and only callable by the `SuiBridge` contract when processing a verified committee-signed message. There is no admin sweep or dust-recovery function.

The worst-affected token is ETH/wETH: EVM decimals = 18, Sui decimals = 8, so `factor = 10^10`. Maximum dust per transaction = `10^10 − 1` wei ≈ **9.999 Gwei**.

### Impact Explanation

Every ETH bridge transaction whose amount is not an exact multiple of `10^10` wei permanently loses up to `9,999,999,999` wei to the vault. The funds are not burned (supply is unchanged on EVM) but are irrecoverable — a permanent fund lock. This matches the HackenProof High/Medium impact class: *permanent fund lock*.

### Likelihood Explanation

Any ordinary user who calls `bridgeETH` or `bridgeERC20` with a non-round ETH amount triggers the loss. Because ETH amounts are typically specified in ether or Gwei (and `10^10` wei = 10 Gwei), any amount that is not a multiple of 10 Gwei silently loses dust. This is a routine, high-frequency condition requiring no special privileges or adversarial setup.

### Recommendation

Truncate the user-supplied amount to the nearest representable unit **before** transferring it to the vault, so the deposited amount exactly equals what will be credited on Sui:

```solidity
// In bridgeERC20 / bridgeETH, before the safeTransferFrom:
uint256 factor = 10 ** (erc20Decimal - suiDecimal);
uint256 alignedAmount = (amount / factor) * factor;   // discard dust
// transfer alignedAmount, refund (amount - alignedAmount) to msg.sender
```

Alternatively, revert if `amount % factor != 0`, forcing callers to supply aligned amounts.

### Proof of Concept

**Setup:** ETH has 18 EVM decimals, 8 Sui decimals → `factor = 10^10`.

**Steps:**
1. User calls `bridgeETH{value: 10_000_000_001}(recipientSuiAddress, destinationChainID)`.
2. `SuiBridge.bridgeETH` transfers `10_000_000_001` wei to `BridgeVault` (line 210).
3. `convertERC20ToSuiDecimal(18, 8, 10_000_000_001)` computes `10_000_000_001 / 10^10 = 1`.
4. `TokensDeposited` is emitted with `suiAdjustedAmount = 1`.
5. Validators mint `1` unit on Sui (= 10 Gwei worth of ETH).
6. **1 wei is permanently locked in `BridgeVault`** — the user paid `10_000_000_001` wei but received credit for only `10_000_000_000` wei.

Maximum loss per call: `10^10 − 1 = 9,999,999,999` wei ≈ 9.999 Gwei. Over thousands of bridge transactions this accumulates into a material, irrecoverable balance.
