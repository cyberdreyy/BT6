### Title
Delegator rewards can become permanently stuck in a vote account with zero delegated stake - (File: `programs/vote/src/vote_state/mod.rs`)

### Summary
This is a valid analog to the EsEMBR `receive()` bug. The `DepositDelegatorRewards` vote instruction (SIMD-0123) lets any signer CPI-transfer lamports into a vote account and increment its `pending_delegator_rewards` counter, without checking whether the vote account has any delegated stake. If the target vote account has zero delegated stake, the reward-distribution logic that would normally consume `pending_delegator_rewards` (`calculate_block_reward`) is never invoked for that account, and the vote account's own `withdraw()` path refuses to release lamports reserved by `pending_delegator_rewards`. The deposited lamports become permanently unspendable, mirroring the "ETH stuck when `totalSupply == 0`" pattern in the report.

### Finding Description
`deposit_delegator_rewards` accepts a deposit from any signing source account, CPIs a System transfer into the vote account, and unconditionally increments `pending_delegator_rewards` — there is no check that the vote account currently has any delegated stake: [1](#0-0) 

The counter is incremented via a plain `checked_add`, with no linkage to whether any stake is (or ever will be) delegated to this vote account: [2](#0-1) 

On the reward-distribution side, `pending_delegator_rewards` is only ever consumed inside `calculate_block_reward`, which is called once per **existing stake delegation** to a vote account (iterated from `stake_delegations` in `calculate_stake_rewards_and_commissions`). If the vote account has zero delegated stake, `calculate_block_reward` is never invoked for it at all — there is no delegation to iterate over, so no rewards are ever computed from that `pending_delegator_rewards` balance: [3](#0-2) [4](#0-3) 

Even for vote accounts that do later gain stake, `calculate_block_reward` explicitly zeroes the result whenever `total_active_stake == 0` for the epoch being rewarded: [5](#0-4) 

Meanwhile, `withdraw()` treats `pending_delegator_rewards` as a hard reserve: partial withdrawals are capped so the remaining balance never drops below `rent_exempt_reserve + pending_delegator_rewards`, and full account closure is rejected outright while `pending_delegator_rewards > 0`: [6](#0-5) 

Combining these: any depositor can push lamports into `pending_delegator_rewards` on a vote account with no (or never-established) delegated stake. That balance can never be paid out through the epoch-reward mechanism (no delegation exists to trigger `calculate_block_reward`), and it can never be withdrawn by the vote account authority either, because `withdraw()` reserves exactly that amount. The lamports are permanently locked in the vote account — the same "funds sent, but the accounting path required to release them never fires" root cause described in the EsEMBR report.

### Impact Explanation
Deposited lamports become permanently unspendable/unrecoverable by anyone (not the depositor, not the vote account authority, and not distributable as staker rewards), which is a concrete stuck-funds / reward-corruption outcome. This is not a consensus-divergence or privilege-escalation bug, but it does match the report's "stuck value" bug class and the "stake or reward corruption" acceptance criterion, since inflation/reward accounting intended for delegators is permanently orphaned.

### Likelihood Explanation
Triggerable by a single, ordinary transaction: any account can sign a `DepositDelegatorRewards` instruction targeting a vote account that has no delegated stake (e.g., a brand-new or de-staked validator's vote account) — no special privileges are required, per the instruction dispatch and account setup: [7](#0-6) 

The main uncertainty is whether some other code path (not located during this investigation) drains/decrements `pending_delegator_rewards` outside of the `calculate_block_reward` epoch-reward flow; a repo-wide search found no subtraction of this field anywhere in the codebase, which is consistent with, but does not fully prove, permanent lock-up in the zero-stake case. This should be verified against the vote-account lamport accounting in `runtime/src/bank/partitioned_epoch_rewards/distribution.rs` (where `block_reward_lamports_distributed`/`burned` are tracked) to confirm no alternate release mechanism exists.

### Recommendation
- Reject `DepositDelegatorRewards` (or cap/refund it) when the target vote account currently has zero delegated stake, similar to the reporter's suggestion to revert `receive()` when `totalSupply == 0`.
- Alternatively, track deposited-but-undistributable amounts separately so they remain withdrawable by the vote account's authorized withdrawer once it's clear no stake will ever consume them.
- Audit all paths that read/write `pending_delegator_rewards` to confirm whether a legitimate decrement path exists for the zero-stake case, and add reward-recycling/refund logic if none does.

### Proof of Concept
1. Create a vote account (V4) with no stake delegated to it (a legitimate scenario: a new validator's vote account before any delegator stakes to it, or after all stake has fully deactivated).
2. Any signer submits a `DepositDelegatorRewards { deposit: N }` transaction naming that vote account and a funded source account as per `programs/vote/src/vote_processor.rs:409-426` and `programs/vote/src/vote_state/mod.rs:936-988`. The vote account's lamports increase by `N` and `pending_delegator_rewards` becomes `N`.
3. At each subsequent epoch boundary, `calculate_stake_rewards_and_commissions` iterates only over existing stake delegations (`runtime/src/bank/partitioned_epoch_rewards/calculation.rs:815-833`); since none exist for this vote account, `calculate_block_reward` is never invoked for it, so `pending_delegator_rewards` is never reduced.
4. The vote account authority attempts `Withdraw`; per `programs/vote/src/vote_state/mod.rs:1084-1122`, any amount up to `N` remains permanently reserved and cannot be withdrawn, and the account cannot be closed while `pending_delegator_rewards > 0`.

pub fn deposit_delegator_rewards<S: std::hash::BuildHasher>(
    invoke_context: &mut InvokeContext,
    vote_account_index: IndexOfAccount,
    sender_account_index: IndexOfAccount,
    deposit: u64,
    signers: &HashSet<Pubkey, S>,
) -> Result<(), InstructionError> {
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;

    let vote_address = *instruction_context.get_key_of_instruction_account(vote_account_index)?;
    let source_address =
        *instruction_context.get_key_of_instruction_account(sender_account_index)?;

    // Source account must sign the transfer.
    verify_authorized_signer(&source_address, signers)?;

    // SIMD-0123 states we must validate the vote account deserializes to a v4
    // *before* attempting CPI, then update the `pending_delegator_rewards`
    // field *last*.
    // We can deserialize it, and hold onto the deserialized payload in-memory.
    // This way, we can drop the account borrow but avoid re-deserializing
    // later, since we know only lamports will change.
    let mut vote_state = {
        let vote_account =
            instruction_context.try_borrow_instruction_account(vote_account_index)?;

        // Can't use `get_vote_state_handler_checked`, since it will convert
        // the underlying vote state to v4.
        // SIMD-0123 requires an *initialized v4*.
        let versioned = VoteStateVersions::deserialize(vote_account.get_data())?;
        if let VoteStateVersions::V4(vote_state_v4) = versioned {
            Ok(VoteStateHandler::new_v4(*vote_state_v4))
        } else {
            Err(InstructionError::InvalidAccountData)
        }
    }?;

    // CPI to System: Transfer from sender to vote account.
    invoke_context.native_invoke_signed(
        system_instruction::transfer(&source_address, &vote_address, deposit),
        &[],
    )?;

    // Update `pending_delegator_rewards`.
    let transaction_context = &invoke_context.transaction_context;
    let instruction_context = transaction_context.get_current_instruction_context()?;
    let mut vote_account =
        instruction_context.try_borrow_instruction_account(vote_account_index)?;

    vote_state.add_pending_delegator_rewards(deposit)?;
    vote_state.set_vote_account_state(&mut vote_account)
}

fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
