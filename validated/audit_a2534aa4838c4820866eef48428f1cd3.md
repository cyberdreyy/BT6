### Title
Sessions use sliding-window expiration with no maximum absolute lifetime, allowing indefinite persistence of a compromised session ID - ([File: core/sessions/localauth/orm.go])

### Summary
`findValidSession` only checks `last_used + sessionDuration >= now()`, and `AuthorizedUserWithSession` calls `updateSessionLastUsed` on every successful authenticated request, resetting `last_used` to `now()`. There is no `created_at`-based absolute cap, so a session ID that is periodically used before the sliding window expires never becomes invalid.

### Finding Description
The session validity check in `findValidSession` is purely sliding-window based: [1](#0-0) 

`AuthorizedUserWithSession`, invoked by `auth.AuthenticateBySession` on every session-cookie-authenticated request (used by routes like `sessionRoutes`, `debugRoutes`, and GQL auth), calls `updateSessionLastUsed` after successful validation, unconditionally resetting `last_used` to `now()`: [2](#0-1) [3](#0-2) 

The `sessions` table schema (as used here) has both `created_at` and `last_used` columns — `CreateSession` inserts both — but only `last_used` is checked against `sessionDuration`; `created_at` is never used to bound the session's absolute lifetime: [4](#0-3) 

Because the check and refresh both key off `last_used`, an attacker holding a stale-but-valid session ID (e.g., leaked via XSS or logs) can issue any authenticated request just under `sessionDuration` intervals to perpetually push `last_used` forward, keeping the session alive with no upper bound on total elapsed time, unless the legitimate user or an admin explicitly calls `DeleteUserSession`, `ClearNonCurrentSessions`, or `UpdateRole` (which purges sessions).

### Impact Explanation
This maps to Chainlink's authentication-soundness bounty class: a compromised session credential (of any role, including `view`) can be used to impersonate the victim user indefinitely as long as it is periodically "pinged," rather than being force-expired after a bounded absolute session lifetime. This is a persistence/authentication-hardening weakness rather than a one-shot privilege escalation — impact is bounded to whatever the underlying user's role permits, but the exposure window becomes unbounded in time instead of capped at `sessionDuration` from the original login.

### Likelihood Explanation
Precondition is possession of any valid (non-expired) session ID cookie, obtained out-of-band (XSS, log leak, etc. — not via network attack, as stated). Given that, the attack is trivial and fully repeatable: send one authenticated GET (e.g., to `/v2/sessions` DELETE is destructive, but any read-only authenticated route works, or `AuthenticateGQL`-protected GraphQL query) at an interval shorter than `sessionDuration` (configurable, default is minutes-to-hours scale). No credentials, tokens, or elevated role are needed beyond the leaked session ID itself.

### Recommendation
Add an absolute session lifetime check using `created_at` in addition to the sliding `last_used` window, e.g.:
```sql
SELECT email FROM sessions WHERE id = $1 AND last_used + $2 >= now() AND created_at + $3 >= now() FOR UPDATE
```
where `$3` is a configurable maximum absolute session lifetime (e.g., 24h), independent of activity. Optionally also force re-authentication (or re-verify WebAuthn/MFA) once the absolute cap is reached, and expose the setting via `WebServer().SessionOptions()`/`SessionTimeout` config.

### Proof of Concept
Go unit test plan in `core/sessions/localauth/orm_test.go`:
1. Create a user and insert a session row with `created_at = now() - 30 days` and `last_used = now()`.
2. Set `sessionDuration` short (e.g., 3 minutes, as done in existing `TestORM_AuthorizedUserWithSession`).
3. Loop N times (simulating renewal over an arbitrarily long span): call `orm.AuthorizedUserWithSession(ctx, sessionID)`, assert `err == nil`, then manually advance `last_used` backward by less than `sessionDuration` (or sleep) before the next iteration to simulate elapsed time between renewals.
4. Assert that even after simulating an arbitrarily large number of iterations / elapsed wall-clock time (e.g., using `db.Exec` to set `created_at` far in the past while keeping `last_used` recently updated), `AuthorizedUserWithSession` still succeeds — demonstrating no absolute-lifetime enforcement, contrasted with `ldapauth`/`oidcauth` authenticators which key expiry off `created_at` instead of `last_used`, as shown at `core/sessions/ldapauth/ldap.go:356-361` and `core/sessions/oidcauth/oidc.go:363-366` for comparison of a bounded design.

func (o *orm) findValidSession(ctx context.Context, sessionID string) (email string, err error) {
	if err := o.ds.GetContext(ctx, &email, "SELECT email FROM sessions WHERE id = $1 AND last_used + $2 >= now() FOR UPDATE", sessionID, o.sessionDuration); err != nil {

func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}
