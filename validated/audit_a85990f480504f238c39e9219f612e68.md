## Finding

The Sentry SAML bug is a context-binding failure: an assertion's org/identity binding wasn't cryptographically tied to the signed data, so it could be replayed across a different security context. The stacks-signer has a structurally identical gap: reward-cycle context binding for `BlockProposal` messages is enforced only by an **unauthenticated, self-declared field**, never independently re-derived from the block's own consensus-visible fields.

### Root cause

`BlockProposal` carries `burn_height` and `reward_cycle` as plain miner-supplied fields, not covered by any signature the block header carries: [1](#0-0) 

`Signer::handle_block_proposal` uses this field as the *sole* gate deciding whether this signer instance (bound to one specific reward cycle for its lifetime) should even look at the proposal: [2](#0-1) 

Crucially, `NakamotoBlockHeader::signer_signature_hash_inner` — the actual message that gets signed — never includes `reward_cycle` (or any reward-cycle-derived value) at all: [3](#0-2) 

And the chainstate `check_proposal` implementations that a signer runs before signing (`v1.rs`, `v2.rs`) never reference `reward_cycle` either — confirmed empty on grep — they only check miner pubkey-hash, consensus-hash-vs-current/last-sortition, tenure-extend rules, and bitvec, per `check_proposal_units`: [4](#0-3) 

So the *only* place "is this proposal for my reward cycle" is decided is the equality check on the miner-declared `reward_cycle` field — a field the miner is free to set to anything, independent of the `burn_height` it pairs with or the block's `consensus_hash`. Nothing in `handle_block_proposal` calls `burnchain.block_height_to_reward_cycle(block_proposal.burn_height)` to cross-check the declared value.

### Why this matters

The system explicitly designs for an overlap window where *both* the outgoing and incoming reward-cycle signer sets are simultaneously live (each running as a separate `Signer` instance pinned to its own `self.reward_cycle`), specifically so the protocol boundary is safe — the dedicated regression test spells out the required invariant: [5](#0-4) 

That invariant ("signers for an outgoing reward cycle do not sign blocks for the incoming reward cycle") is enforced *exclusively* by the `block_proposal.reward_cycle != self.reward_cycle` string/int compare shown above. Since a signer's own `SortitionsView` is fetched independently from its node's live state (not derived from the miner's message), a genuinely canonical, currently-valid block will pass `check_proposal` for *every* signer instance whose sortition view currently covers it — regardless of which `self.reward_cycle` that instance represents. A miner (a single actor, requiring no other signer's key or majority) that mislabels the `reward_cycle` field of an otherwise-canonical `BlockProposal` to match an *outgoing* signer's `self.reward_cycle` causes that outgoing-cycle signer to evaluate and potentially sign a block that the protocol intends it to ignore entirely. Because stackers commonly stack across consecutive cycles, an outgoing signer's key is frequently still a member of the *incoming* reward set that ultimately verifies the aggregated signature (`verify_signer_signatures`, keyed off the block's real burn-height-derived reward cycle, not the self-declared field): [6](#0-5) 

That signature then legitimately counts toward the incoming cycle's threshold — a signer produced a valid signature under a security context (reward cycle) its own state machine explicitly believes it is not participating in, purely because the context label was taken on faith from the block proposer.

### Title
Signer trusts a miner-supplied, unauthenticated `reward_cycle` field to gate reward-cycle participation, letting an outgoing-cycle signer sign for the incoming cycle - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`Signer::handle_block_proposal` decides whether a `BlockProposal` belongs to "its" reward cycle using the message's self-declared `reward_cycle` field, which is neither part of the signed `signer_signature_hash` nor cross-checked against the accompanying `burn_height`/the block's `consensus_hash`-derived sortition. A single malicious miner can mislabel this field to route a genuinely canonical block to an outgoing-cycle `Signer` instance that the protocol intends to have stopped participating at the reward-cycle boundary.

### Finding Description
The reward-cycle boundary safety property ("signers for an outgoing reward cycle do not sign blocks for the incoming reward cycle") is implemented as a single equality check in `handle_block_proposal` at stacks-signer/src/v0/signer.rs:1582 against a value the miner fully controls. Neither `NakamotoBlockHeader::signer_signature_hash_inner` (stackslib/src/chainstate/nakamoto/mod.rs:1028-1045) nor the shared `check_proposal` logic in `stacks-signer/src/chainstate/v1.rs`/`v2.rs` reference `reward_cycle` at all, so nothing downstream re-derives or validates it against the block's true tenure/burn height. During the documented overlap window where outgoing- and incoming-cycle signer sets run concurrently, an outgoing signer's own `SortitionsView` is fetched fresh from its node and will validate a genuinely current, canonical block exactly the same way an incoming signer's would — the *only* thing stopping the outgoing signer from evaluating and signing it is the spoof-able field.

### Impact Explanation
This breaks the equality "the signer set that is supposed to sign for reward cycle X is exactly and only the set of `Signer` instances configured with `self.reward_cycle == X`, verified independent of miner input." An outgoing signer can be misled into producing a valid `signer_signature_hash` signature for a block whose real, burn-height-derived reward cycle is the *next* cycle. If that signer's key is also a member of the incoming reward set (common, since stacking commonly spans multiple cycles), the resulting signature is a cross-context-valid signature that the node's `verify_signer_signatures` will happily count toward the incoming cycle's 70% threshold, undermining the explicit boundary invariant asserted by `outgoing_signers_ignore_block_proposals`.

### Likelihood Explanation
Reachable by a single miner with no cooperation from other signers, no auth token, and no majority: it only requires crafting one `BlockProposal` message with a mismatched `reward_cycle` field relative to the real `burn_height`/sortition, sent during the (deliberately supported) overlap window when both signer sets are live.

### Recommendation
In `handle_block_proposal`, independently derive the block's true reward cycle from `block_proposal.burn_height` (or from the sortition matching `block.header.consensus_hash`, as `find_nakamoto_block_reward_cycle` already does node-side) and reject/ignore the proposal if it disagrees with the declared `reward_cycle`, rather than trusting the declared field outright. Alternatively, bind `reward_cycle` into the signed message digest so a mismatched label cannot silently redirect a signature into the wrong context.

### Proof of Concept
1. Run the topology from `outgoing_signers_ignore_block_proposals` (stacks-node/src/tests/signer/v0/mod.rs:6249): outgoing-cycle-N and incoming-cycle-N+1 signer sets both active near the boundary, with overlapping stacked keys.
2. As the miner, build a genuinely canonical block for the current (N+1) tenure, but broadcast it as `SignerMessageV0::BlockProposal(BlockProposal { block, burn_height: <real N+1 height>, reward_cycle: N, .. })`.
3. Observe the outgoing (cycle-N) `Signer` instance passes the `block_proposal.reward_cycle != self.reward_cycle` check (stacks-signer/src/v0/signer.rs:1582), fetches its own live `SortitionsView`, passes `check_proposal` (since the block is genuinely canonical), and signs it — contrary to the intended invariant that outgoing signers "do not sign blocks for the incoming reward cycle."

    /// This includes all fields _except_ the stacker signature.
    fn signer_signature_hash_inner(&self) -> Result<Sha512Trunc256Sum, CodecError> {
        let mut hasher = Sha512_256::new();
        let fd = &mut hasher;
        write_next(fd, &self.version)?;
        write_next(fd, &self.chain_length)?;
        write_next(fd, &self.burn_spent)?;
        write_next(fd, &self.consensus_hash)?;
        write_next(fd, &self.parent_block_id)?;
        write_next(fd, &self.tx_merkle_root)?;
        write_next(fd, &self.state_index_root)?;
        write_next(fd, &self.timestamp)?;
        write_next(fd, &self.miner_signature)?;
        write_next(fd, &self.pox_treatment)?;
        if Self::version_includes_problematic_txs(self.version) {
            write_next(fd, &self.problematic_txs)?;
        }
        Ok(Sha512Trunc256Sum::from_hasher(hasher))
    }
