### Title
Path traversal in `BashWriter.Variable`/`TmpFile` allows a file-type CI variable `Key` to write outside `TemporaryPath` - (File: shells/bash.go)

### Summary
`BashWriter.TmpFile` builds the target path for file-type variables via `path.Join(b.TemporaryPath, name)` followed by `cleanPath`/`Absolute`, but neither step verifies the result stays under `TemporaryPath`. Because `path.Join` performs `path.Clean` on the joined string, a `Key` containing enough `../` segments collapses the path to a location outside the intended temp root, and `BashWriter.Variable` then unconditionally writes the variable's value there.

### Finding Description
`BashWriter.TmpFile` is defined as: [1](#0-0) 

`cleanPath` only calls `Absolute`, which merely checks whether the path is already absolute or `$PWD`-relative — it performs no containment/prefix check against `TemporaryPath`: [2](#0-1) 

For file-type variables, `BashWriter.Variable` computes the destination purely from `TmpFile(variable.Key)` and writes to it without any validation that the result is confined to the workspace: [3](#0-2) 

Note there *is* a containment helper, `isTmpFile`, which does a `strings.HasPrefix` check — but it is only used in the non-file branch to normalize `variable.Value` when it already looks like a tmp path; it is never applied to the file-write destination computed from `variable.Key`: [4](#0-3) 

Because `path.Join` (called inside `TmpFile`) calls `path.Clean`, a `Key` such as `../../../../etc/cron.d/x` combined with `TemporaryPath` (e.g. `/builds/project/0/tmp`) collapses to an absolute path outside the project directory (e.g. `/etc/cron.d/x`). Since the joined path is already absolute, `Absolute()` returns it unmodified — there is no re-basing or rejection.

The `spec.Variable{Key, Value, File}` type itself imposes no restriction on `Key` content: [5](#0-4) 

I could not find any key-format validation (e.g., a `^[A-Za-z_][A-Za-z0-9_]*$` check) enforced anywhere in this Runner codebase for job/file variables before they reach `BashWriter.Variable`; the only similar validation found (`isValidDotEnvKey`) is scoped to `.env` artifact parsing, not job variable keys from the job payload.

### Impact Explanation
If reachable with an attacker-controlled `Key` containing path traversal, the impact is a job-controlled arbitrary file write on the host/container filesystem outside the job's tmp/build root — e.g. overwriting files like `/etc/cron.d/x` (in shell executor) or other paths writable by the job process, which is precisely the "unauthorized file write outside job roots" scoped impact.

### Likelihood Explanation
The severity of this finding is contingent on a precondition this codebase does not resolve: whether the value that ultimately populates `spec.Variable.Key` for file-type variables is validated upstream (e.g., by GitLab Rails/API, which is documented to restrict CI/CD variable names to `^[a-zA-Z_][a-zA-Z0-9_]*$`) before the job payload reaches the Runner. If such validation is enforced server-side for every code path that can set `File: true` (regular job variables, triggered pipeline variables, `secure_files`/secrets-derived file variables, etc.), then Runner never actually receives a traversal-laden `Key` in practice. I was unable to find that validation logic inside this repository (it would live in GitLab Rails, not gitlab-runner), so I cannot confirm from this codebase alone whether the precondition ("attacker controls Key value reaching Runner without server-side sanitization") holds for all variable ingestion paths. This is a real, confirmed missing defense-in-depth check in `shells/bash.go` regardless, but its exploitability from an "unprivileged job author" depends on an external system (GitLab server) that is outside the Runner repository's control and thus outside what I can verify here.

### Recommendation
Add an explicit containment check in `BashWriter.TmpFile` (and equivalent logic in other shell writers, e.g. `powershell.go`) after computing the joined/cleaned path: reject or reject-and-fallback if `!strings.HasPrefix(path.Clean(resolved), path.Clean(b.TemporaryPath)+"/")`. Additionally, validate `variable.Key` against a strict identifier pattern (e.g. `^[A-Za-z_][A-Za-z0-9_]*$`) before it is used to construct any filesystem path, independent of whatever validation the GitLab server performs, so Runner does not rely solely on an external trust boundary.

### Proof of Concept
```go
// shells/bash_test.go
func TestBashWriter_Variable_FileKeyPathTraversal(t *testing.T) {
    w := &BashWriter{TemporaryPath: "/builds/project/0/tmp"}
    w.Variable(spec.Variable{
        Key:   "../../../../etc/cron.d/x",
        Value: "* * * * * root touch /tmp/pwned",
        File:  true,
    })
    script := w.String()

    // Assert the resolved destination stays within TemporaryPath.
    resolved := w.TmpFile("../../../../etc/cron.d/x")
    assert.True(t, strings.HasPrefix(resolved, w.TemporaryPath),
        "file-variable destination escaped TemporaryPath: %s", resolved)
}
```
Expected (current) result: the assertion fails because `resolved` evaluates to an absolute path outside `/builds/project/0/tmp` (e.g. `/etc/cron.d/x`), and the generated script contains a `printf ... > "/etc/cron.d/x"` line. A fuzz test iterating random `../` depths against varying `TemporaryPath` values would confirm the same escape for sufficiently deep traversal payloads.

func (b *BashWriter) Variable(variable spec.Variable) {
	if variable.File {
		variableFile := b.TmpFile(variable.Key)
		b.Linef("mkdir -p %q", helpers.ToSlash(b.TemporaryPath))
		b.Linef("printf '%%s' %s > %q", b.escape(variable.Value), variableFile)
		b.Linef("export %s=%q", b.escape(variable.Key), variableFile)
	} else {
		if b.isTmpFile(variable.Value) {
			variable.Value = b.cleanPath(variable.Value)
		}
		b.Linef("export %s=%s", b.escape(variable.Key), b.escape(variable.Value))
	}
}
