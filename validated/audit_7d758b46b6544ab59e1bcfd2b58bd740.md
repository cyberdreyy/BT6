### Title
`posix_escape` input downgrades control-character neutralization, enabling ANSI/terminal escape-sequence injection into trace/log output - ([File: functions/script_legacy/internal/escape.go])

### Summary
`TraceSectionWriter.escape` and `CommandFormatter.FormatLogLine` route through either `EscapeForAnsiC` or `EscapeForPosix` depending on the attacker-settable `posix_escape` step input. `EscapeForAnsiC` explicitly hex-escapes all control characters (including `ESC` 0x1b) to prevent terminal manipulation, but `EscapeForPosix` has no such handling at all, so a job author can flip `posix_escape=true` to bypass the control-character neutralization while keeping the shell-quote-breakout characters (`"`, `` ` ``, `\`, `$`) safely escaped.

### Finding Description
`ScriptGeneratorConfig.PosixEscape` is populated directly from the `posix_escape` step input read in `functions/script_legacy/script_legacy.go` (`posixEscapeInput, err := builtinCtx.GetInputWithDefault("posix_escape", ...)`), a boolean input defined in `Spec()` with no restriction on who can set it [1](#0-0) . This value is threaded into both `NewCommandFormatter(config.PosixEscape)` and `NewTraceSectionWriter(config.CheckForErrors, config.PosixEscape)` [2](#0-1) .

`TraceSectionWriter.escape` and `CommandFormatter.FormatLogLine` both branch on `posixMode`: when true they call `EscapeForPosix`, otherwise they call `EscapeForAnsiC` wrapped in `$'...'` [3](#0-2) [4](#0-3) .

`EscapeForAnsiC` hex-escapes every control character (`c < 0x20 || c == 0x7F || c > 0x7F`), explicitly to stop "jobs from clearing the screen or rewriting logs using ANSI escape sequences" [5](#0-4) . `EscapeForPosix`, by contrast, only special-cases a fixed set of shell metacharacters (`` ` " \ $ `` and a punctuation list) and copies every other rune — including raw `ESC` (0x1b) and other control bytes — verbatim into the double-quoted string via `buf.WriteRune(r)` in the `default` branch [6](#0-5) .

Because the command preview text is always prefixed with `commandPrefix = "$ "` (which contains a space, one of the quoting-trigger characters), `needsQuoting` is always `true` in practice, so the quote-boundary characters (`"`, `` ` ``, `\`, `$`) remain properly escaped and the resulting shell line stays syntactically valid — i.e. the literal "printf format string quote breakout / command injection" hypothesized in the question does **not** occur, since the metacharacters that could terminate the double-quoted argument are always escaped. What *does* leak through unmodified are raw ANSI/control-character sequences (e.g. `\x1b[2J`, `\x1b[8m`, cursor-repositioning codes) contained in job script text, which will be written verbatim by the generated `printf '%s\n' ...` line to the job trace.

### Impact Explanation
An attacker (pipeline author) who sets `posix_escape=true` for a `script_legacy`/`scriptv2` step can embed ANSI escape sequences in their own script commands so that, when the multi-line command preview or trace-section header is echoed, raw terminal-control codes reach the CI job log/terminal instead of being hex-escaped and rendered as inert text. This allows spoofing/erasing/rewriting portions of the CI trace (e.g., hiding a malicious command from a reviewer scrolling the log, or fabricating fake "success" output), which undermines log integrity — though it does not achieve shell command injection or sandbox escape, since the shell-quoting boundary characters remain escaped in both modes.

### Likelihood Explanation
Fully reachable and repeatable: `posix_escape` is a plain boolean step input with no authorization check beyond normal job/pipeline authorship, and multi-line commands containing ANSI codes are trivial to construct. No special privileges, race conditions, or external state are required — a single crafted `.gitlab-ci.yml`/step invocation with `posix_escape: true` and a command containing `\x1b[...]` sequences reproduces the discrepancy deterministically.

### Recommendation
Make `EscapeForPosix` neutralize control characters the same way `EscapeForAnsiC` does (hex-escape or otherwise render inert any byte `< 0x20`, `0x7F`, or non-ASCII) before/while wrapping content in double quotes, so both escaping modes provide the same terminal-manipulation protection regardless of which mode the job selects.

### Proof of Concept
```go
func TestEscapeForPosix_DoesNotNeutralizeControlChars(t *testing.T) {
    input := "\x1b[2J\x1b[H" // clear-screen / cursor-home ANSI sequence
    result := EscapeForPosix(input)
    // BUG: raw ESC bytes pass straight through unescaped.
    assert.Contains(t, result, "\x1b[2J\x1b[H")

    ansiCResult := EscapeForAnsiC(input)
    // Sanity: the ANSI-C path correctly neutralizes it.
    assert.NotContains(t, ansiCResult, "\x1b")
}
```
Expected assertions: `EscapeForPosix` output still contains the raw `ESC` byte sequence (proving lack of neutralization), while `EscapeForAnsiC` output contains the hex-escaped `\x1b` representation instead — demonstrating the security-relevant behavioral divergence introduced by flipping `posix_escape`.

func (f *CommandFormatter) FormatLogLine(command string) string {
	command = ansiGreen + commandPrefix + f.getDisplayCommand(command) + ansiReset

	if f.posixMode {
