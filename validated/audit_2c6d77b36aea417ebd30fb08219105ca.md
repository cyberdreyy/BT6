### Title
Preregistration binding does not stop a same-payload front-run of the bound deposit - ([File: specs/_features/eip8205/beacon-chain.md])

### Summary
EIP‑8205 introduces a pubkey→withdrawal‑credentials "preregistration" commitment explicitly to protect delegated‑staking deployments from deposit front‑running (`specs/_features/eip8205/beacon-chain.md:49-59`). Like the KinoAccount commit scheme, the binding only checks whether a commitment is *already active*, not whether it was committed strictly before the competing action. Because `apply_parent_execution_payload` deliberately processes all deposit requests before any preregistration requests in the very same execution payload, an attacker who controls the private key for a not‑yet‑bound pubkey can slip in a self‑serving deposit in the same block as the legitimate preregistration and have it accepted before the binding becomes active, permanently hijacking the validator's withdrawal credentials.

### Finding Description
`process_deposit_request` only defers to a binding that is already `get_active_preregistration(state, pubkey)`-visible at the moment the deposit is processed: [1](#0-0) 

`get_active_preregistration` / `is_active_preregistration` only look at the *stored* state, i.e. bindings from earlier blocks: [2](#0-1) 

Critically, `apply_parent_execution_payload` processes `requests.deposits` before `requests.preregistrations` **within the same execution payload**, and the spec explicitly documents this as intentional "deposit-first" behavior: [3](#0-2) 

So if a pool's `PreregistrationRequest` (binding `pubkey → pool_credentials`) and an attacker's `DepositRequest` for the *same* `pubkey` (with `attacker_credentials`, validly signed because the attacker holds the corresponding privkey — e.g. a dishonest node operator who generated the keypair for the pool) both land in the same execution payload:
1. `process_deposit_request` runs first; `get_active_preregistration` returns `None` because the binding for that pubkey has not been stored yet in this call.
2. The attacker's deposit is appended unconditionally to `state.pending_deposits` with `attacker_credentials`.
3. `process_preregistration_request` then runs and stores the pool's binding — but this happens *after* the competing deposit has already been queued, and the binding logic never inspects `pending_deposits` created in the same payload to invalidate them (only later `process_preregistration_request` calls check `is_pending_validator`, i.e. it protects future preregistrations, not this one).
4. During the next epoch's `process_pending_deposits`, since this is the pubkey's first deposit, `add_validator_to_registry` creates the validator using `attacker_credentials`, after `is_valid_deposit_signature` passes (which it does, since the attacker legitimately owns the pubkey's privkey).

The equality this scheme was supposed to preserve — "the first deposit for a preregistered pubkey uses the bound (pool) withdrawal credentials" — is broken: the withdrawal credentials of a brand-new validator, and hence the destination of all its future withdrawn Gwei, is unilaterally steerable by whoever also holds the deposit's signing key, as long as they can land a deposit in the same execution payload as the preregistration.

### Impact Explanation
This is exactly the exploit the feature exists to prevent, yet it survives: an operator who legitimately holds a validator's signing key (necessary to obtain a valid deposit signature) can redirect the validator's withdrawal credentials to an address the pool never authorized, simply by timing their deposit to land in the same execution payload as the pool's preregistration. All ETH ultimately staked to that validator (and its eventual full withdrawal) is paid to the attacker's address instead of the pool's — Gwei paid to a non-owner / a validator re-credentialed without the depositor's (pool's) authority. No coalition, client bug, or supermajority stake is required; only ordinary access to the execution-layer mempool to co-locate two transactions in one block.

### Likelihood Explanation
Requires the attacker to both hold the private key for the pubkey (realistic for the exact "delegated staking / dishonest node operator" scenario this feature targets) and to place a deposit transaction in the same execution payload as the pool's preregistration transaction — achievable by any party able to submit transactions to the execution layer, with no special timing precision beyond "same block," which is the easiest case to hit for a motivated party watching the mempool for the preregistration transaction.

### Recommendation
Do not let deposits in the same execution payload bypass a preregistration submitted in that same payload. Either:
- Process preregistrations before deposits within `apply_parent_execution_payload` (reversing the current explicit ordering), or
- Have `process_preregistration_request` retroactively invalidate/roll back any deposit already queued in `pending_deposits` for the same pubkey within the same payload when it does not match the binding, or
- Require a minimum age (e.g., an activation delay measured in slots, analogous to `COMMITMENT_REGISTRATION_DELAY` in EIP‑8321) before a preregistration binding becomes enforceable, and reject deposits for a pubkey that has a *pending* (not-yet-active but within-payload) preregistration.

### Proof of Concept
Conceptual sequence, expressible as a pyspec test analogous to `tests/core/pyspec/eth_consensus_specs/test/eip8205/block_processing/test_process_parent_execution_payload.py`:
1. Build `ExecutionRequests` with:
   - `preregistrations = [PreregistrationRequest(pubkey=P, withdrawal_credentials=POOL_CREDS, signature=sig_by_P)]`
   - `deposits = [DepositRequest(pubkey=P, withdrawal_credentials=ATTACKER_CREDS, amount=MIN_ACTIVATION_BALANCE, signature=sig_by_P_over_ATTACKER_CREDS)]`
   in the **same** payload (same `apply_parent_execution_payload` call).
2. Call `apply_parent_execution_payload(state, requests)`.
3. Observe: `state.pending_deposits` contains the attacker's deposit with `ATTACKER_CREDS` (since `get_active_preregistration` returned `None` when the deposit was processed), while `state.validator_preregistrations` now also has the pool's stored binding — too late.
4. Advance an epoch to trigger `process_pending_deposits`; observe the new validator is created with `withdrawal_credentials == ATTACKER_CREDS`, not `POOL_CREDS`, confirming the binding failed to protect the pool's intended deposit despite both being submitted "at the same time." ### Misc

*Note*: Implementations should maintain secondary pubkey indices over
`validator_preregistrations` and `pending_deposits` instead of the linear scans
shown here. Removals must preserve the remaining list order, which is
consensus-visible through the state root. Since the state root is only computed
after block processing, implementations SHOULD NOT rebuild the list once per
removed record: consumed records can be tombstoned during request processing and
the list compacted in a single pass per block, which produces an identical
post-state.

#### New `get_stored_preregistration_index`

```python
def get_stored_preregistration_index(state: BeaconState, pubkey: BLSPubkey) -> Optional[Uint64]:
    for index, preregistration in enumerate(state.validator_preregistrations):
        if preregistration.pubkey == pubkey:
            return Uint64(index)
    return None
```

#### New `get_active_preregistration`

```python
def get_active_preregistration(
    state: BeaconState, pubkey: BLSPubkey
) -> Optional[StoredPreregistration]:
    index = get_stored_preregistration_index(state, pubkey)
    if index is None:
        return None
    preregistration = state.validator_preregistrations[index]
    if not is_active_preregistration(state, preregistration):
        return None
    return preregistration
```

def process_deposit_request(state: BeaconState, deposit_request: DepositRequest) -> None:
    # [New in EIP8205]
    preregistration = get_active_preregistration(state, deposit_request.pubkey)
    if preregistration is not None:
        if deposit_request.withdrawal_credentials != preregistration.withdrawal_credentials:
            return

        if not is_valid_deposit_signature(
            deposit_request.pubkey,
            deposit_request.withdrawal_credentials,
            deposit_request.amount,
            deposit_request.signature,
        ):
            return

        remove_stored_preregistration(state, deposit_request.pubkey)

    state.pending_deposits.append(
        PendingDeposit(
            pubkey=deposit_request.pubkey,
            withdrawal_credentials=deposit_request.withdrawal_credentials,
            amount=deposit_request.amount,
            signature=deposit_request.signature,
            slot=state.slot,
        )
    )

##### Modified `apply_parent_execution_payload`

*Note*: Preregistrations are processed last so that a deposit and a
preregistration for the same pubkey in one execution payload retain the
deposit-first behavior stated by EIP-8205.

```python
def apply_parent_execution_payload(
    state: BeaconState,
    requests: ExecutionRequests,
) -> None:
    parent_bid = state.latest_execution_payload_bid
    parent_slot = parent_bid.slot
    parent_epoch = compute_epoch_at_slot(parent_slot)

    assert len(requests.withdrawals) <= MAX_WITHDRAWAL_REQUESTS_PER_PAYLOAD
    assert len(requests.consolidations) <= MAX_CONSOLIDATION_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_deposits) <= MAX_BUILDER_DEPOSIT_REQUESTS_PER_PAYLOAD
    assert len(requests.builder_exits) <= MAX_BUILDER_EXIT_REQUESTS_PER_PAYLOAD
    # [New in EIP8205]
    assert len(requests.preregistrations) <= MAX_PREREGISTRATION_REQUESTS_PER_PAYLOAD

    # Process execution requests from parent's payload. The execution
    # requests are processed at state.slot (child's slot), not the parent's slot.
    def for_ops(operations: Sequence[Any], fn: Callable[[BeaconState, Any], None]) -> None:
        for operation in operations:
            fn(state, operation)

    for_ops(requests.deposits, process_deposit_request)
    for_ops(requests.withdrawals, process_withdrawal_request)
    for_ops(requests.consolidations, process_consolidation_request)
    for_ops(requests.builder_deposits, process_builder_deposit_request)
    for_ops(requests.builder_exits, process_builder_exit_request)
    # [New in EIP8205]
    for_ops(requests.preregistrations, process_preregistration_request)
```
