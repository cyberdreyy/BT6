### Title
`Authorize` returns distinguishable error messages allowing unauthenticated workflow-ID/signer enumeration - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` returns three distinct, attacker-observable error strings depending on whether JWT verification fails, the `workflowID` does not exist, or the recovered signer is not in the authorized-key set for that workflow. Because the JWT scheme is self-signed (the "signer" is recovered directly from the request's own signature via `VerifyRequestJWT`/`GetSignersEthAddress`, not checked against any pre-registered credential), an unauthenticated attacker can trivially mint valid, freshly-signed JWTs with any key they generate and thereby reach the workflow-lookup and signer-lookup branches at will.

### Finding Description
`Authorize` first calls `utils.VerifyRequestJWT(token, *req)` [1](#0-0) . `VerifyRequestJWT` recovers the signer's Ethereum address directly from the token's own ECDSA signature (`GetSignersEthAddress`) and uses that recovered address as the verification key [2](#0-1) . There is no check that this address belongs to any known/registered identity — it is entirely attacker-chosen, since anyone can generate an ECDSA keypair, sign a well-formed JWT over the request digest, and pass verification. Thus JWT verification succeeding is *not* a privilege check; it only confirms the token is internally self-consistent.

After successful (self-signed) JWT verification and passing the replay-cache check, `Authorize` performs two more lookups:
- If `workflowID` is not in `h.authorizedKeys`, it returns `fmt.Errorf("workflow ID %s not found", workflowID)` [3](#0-2) .
- If the workflow exists but the recovered signer's key is not in the authorized set, it returns `fmt.Errorf("signer '%s' is not authorized for workflow '%s'...", ...)` [4](#0-3) .

These two error paths are textually distinct and depend solely on server-side state (workflow existence, authorized-key membership) rather than any secret held by the attacker. Since an attacker can generate valid signed tokens for arbitrary self-chosen keys at will (no registration needed to pass JWT verification), they can freely probe arbitrary `workflowID` values and observe which error is returned, allowing them to determine:
1. Whether a given `workflowID` exists (`"workflow ID %s not found"` vs. proceeding to the authorization check).
2. That the error is different for existing-but-unauthorized vs non-existing workflows.

I was not able to fully trace how the HTTP/gateway-facing route that calls `Authorize` (via `http_trigger_handler.go`) formats and returns these errors to the network caller in this pass — this should be verified by a background agent to confirm the raw error string (or a distinguishable error code) is propagated to the unauthenticated client's HTTP response, since this is the final link needed for the enumeration oracle to be network-exploitable end-to-end.

### Impact Explanation
If the distinguishing error text reaches the network caller, this constitutes an information-disclosure oracle: an unauthenticated attacker can enumerate which `workflowID`s are currently registered/active on the gateway. This does not by itself leak the authorized signer address (since matching an arbitrary signer address to "authorized" requires guessing a full Ethereum address, which is infeasible), but existence-enumeration of `workflowID`s can be used for reconnaissance to target specific workflow owners for further attacks (e.g., social engineering, or combining with other enumeration primitives). This matches an information-disclosure impact class rather than direct key/secret compromise.

### Likelihood Explanation
Preconditions are met per the audit scope: the attacker only needs network access to the gateway endpoint and the ability to generate an ECDSA keypair and self-sign a well-formed JWT (no credential registered on the node is required, since `VerifyRequestJWT` recovers the signer from the token's own signature). This is fully repeatable and scriptable (table-driven probing of candidate `workflowID` strings), assuming the caller of `Authorize` surfaces the error text/distinct error codes to the network response — this dependency should be confirmed.

### Recommendation
Return a single, uniform error (e.g., a generic `"unauthorized"` message/code) for both the "workflow not found" and "signer not authorized" cases in `Authorize`, and avoid echoing back the requested `workflowID` or `signer` address in the error. Ensure the caller in `http_trigger_handler.go` also normalizes/generalizes error responses sent to the network client so internal distinctions are not observable externally.

### Proof of Concept
Go table-driven test in `workflow_metadata_handler_test.go`:
1. Construct a `WorkflowMetadataHandler` with one authorized workflow ID `W1` and one authorized key `K1`.
2. For each of: (a) unknown `workflowID` + freshly self-signed JWT, (b) known `W1` + self-signed JWT from an unregistered key, (c) malformed JWT — call `Authorize` and capture the returned `error.Error()` string.
3. Assert that scenarios (a) and (b) currently produce different, workflowID/signer-specific text (demonstrating the oracle), then assert (after fix) that both return the same generic message/code, confirming non-distinguishability.
4. Additionally verify that generating a brand-new ECDSA key and self-signing a JWT (no prior registration) is sufficient to pass `VerifyRequestJWT` and reach the workflow-lookup branch, confirming the "no privilege needed" precondition via `utils.CreateRequestJWT`/`VerifyRequestJWT` round-trip test.
