### Title
`depositDuringEpoch` and `_deposit` credit the declared `_amount` instead of the actual tokens received, letting a fee-on-transfer/under-delivering pull drain other depositors' funds - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The Apache `ap_rwrite()` bug (CVE-2022-28614) is an over-length bug: the caller declares a buffer length larger than the data actually present, so the server reads/reflects memory it does not own. The closest structural analog in this codebase is a credit-length vs. received-length mismatch: `IdleCDOEpochVariant.depositDuringEpoch` pulls `_amount` from the depositor but then prices the mint, mints strategy-token receipts, and forwards `_amount` to the borrower entirely on the *declared* amount, never measuring the *actual* balance increase. `IdleCDOCreditVault._deposit` measures the received delta for share minting but still forwards the nominal `_amount` to the strategy. If the vault's underlying token takes a transfer fee or otherwise under-delivers on `transferFrom` (e.g. USDT with fee enabled, deflationary/rebasing-down pool currencies — `IdleCreditVault.token` is just an arbitrary ERC20 set at deploy time), the vault pays out more than it received, covering the gap from other depositors' principal.

### Finding Description
In `depositDuringEpoch` the flow is:

```solidity
// contracts/IdleCDOEpochVariant.sol:685
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
...
// :724 — shares priced on the DECLARED amount
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
_mintShares(_tranche, msg.sender, _minted, _amount);
// :730 — strategy tokens minted for the DECLARED amount
IdleCreditVault(strategy).mintStrategyTokens(_amount);
// :732 — borrower receives the DECLARED amount
_transferUnderlyings(_borrower(), _amount);
```

There is no `balanceOf` delta measurement anywhere in this path. Compare with the normal deposit path in `IdleCDOCreditVault._deposit`, which does measure:

```solidity
// contracts/IdleCDOCreditVault.sol:203-206
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
// :211 — but then still forwards the nominal _amount
IIdleCDOStrategy(strategy).deposit(_amount);
```

So even the guarded path mints correctly but pushes the nominal `_amount` into the strategy, and the epoch path doesn't even guard the mint. Invariant broken: one unit in = one unit credited. The vault "reads" `_amount` beyond the actual buffer of tokens delivered.

Concretely, with an underlying that burns `f` on transfer:
- Attacker calls `depositDuringEpoch(X, AATranche)` during a running epoch.
- Vault receives `X - f`, but mints AA tranche tokens worth `X + interest`, mints `X` strategy tokens, and sends `X` to the borrower.
- The `f` shortfall is absorbed by the vault's existing balance — i.e. by other tranche holders whose withdraw requests settle against `getContractValue`.
- Attacker's tranche tokens are still redeemable at full value (plus prorated interest) in the next epoch.

The same pattern exists for the minted-receipt path: `mintStrategyTokens(_amount)` creates claimable receipts for the attacker while the vault is `f` short. `_skimDonatedAssets` (called at :679) does not help — it only skims *excess* donations, and here the vault is in *deficit*, not surplus. `_guarded(_amount)` checks the declared limit, not the received amount. No revert path covers the discrepancy.

### Impact Explanation
Direct theft of other lenders' principal, bounded per call by the transfer fee but repeatable every `depositDuringEpoch`/`depositAA`/`depositBB` call. With a 1% fee token, a 1M-unit deposit steals ~10k units of NAV from existing holders per call; repeated calls drain the pool up to the deposit `limit`. Loss is quantifiable: `(declared - received)` per call, and the attacker exits at full tranche value via `requestWithdraw` after `stopEpoch`.

### Likelihood Explanation
Requires the credit vault's `token` to under-deliver on `transferFrom`. Deployed instances target stable pool currencies (USDC-class), which today charge no fee — but the contract imposes no such restriction: `token` is an arbitrary ERC20 chosen at factory/deploy time, USDT can enable fees by governance, and fee/rebase tokens are legitimate pool currencies. The asymmetric handling (delta measured for minting but nominal `_amount` forwarded, and no delta at all in `depositDuringEpoch`) means the code itself carries the vulnerability class regardless of current deployments.

### Recommendation
In `depositDuringEpoch`, measure `received = _contractTokenBalance(token) - _preBal` after `_transferUnderlyingsFrom` and use `received` (not `_amount`) for `_calcInterest`, the share-mint formula, `mintStrategyTokens`, and the borrower transfer — or revert if `received != _amount`. Apply the same fix in `IdleCDOCreditVault._deposit` (`strategy.deposit(received)`). Simplest robust option: revert on `received < _amount` to formally exclude fee-on-transfer underlyings.

### Proof of Concept
Foundry fork shape (schematic — exact harness depends on the repo's existing `IdleCreditVault.t.sol` setup which already forks mainnet and deploys `IdleCDOEpochVariant` + `IdleCreditVault`):

```solidity
// underlying = mock/mainnet token that burns 1% on transfer
uint256 X = 1_000_000e6;
uint256 fee = X / 100;

// honest liquidity already deposited pre-epoch, epoch started via startEpoch()
// attacker is a KYC-allowed wallet: isWalletAllowed(attacker) == true
uint256 navBefore = cdoEpoch.getContractValue();
uint256 cdoBalBefore = underlying.balanceOf(address(cdoEpoch));

vm.prank(attacker);
cdoEpoch.depositDuringEpoch(X, address(AAtranche));

// vault received X - fee but forwarded X to borrower
assertEq(underlying.balanceOf(address(cdoEpoch)), cdoBalBefore - fee);
// attacker was minted shares priced on X (+ interest), i.e. over-credited
// other holders' claimable NAV dropped by `fee`
assertEq(cdoEpoch.getContractValue(), navBefore - fee);
```

Then `stopEpoch`, attacker calls `requestWithdraw` and `claimWithdrawRequest` to realize ~full `X`, crystallizing the `fee`-sized loss on remaining depositors. I was unable to fully verify the test harness wiring within the available iterations, but the unchecked `_amount`-vs-received gap at `IdleCDOEpochVariant.sol:685-732` and `IdleCDOCreditVault.sol:204-211` is directly visible in the source.
