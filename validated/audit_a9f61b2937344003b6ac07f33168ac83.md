Confirmed: `delete_member()` at `multisig2/src/lib.rs:356-379` only purges requests whose *original submitter* (`r.member`) equals the removed member, and clears `num_requests_pk` for that member. It does **not** scan the `confirmations` map for entries where the removed member appears merely as a *confirmer* of someone else's still-pending request. Since `confirmations` is a raw `HashSet<String>` keyed by member identity string with no live-membership check performed in `confirm()` (`multisig2/src/lib.rs:294-315`, which only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`), a confirmation cast by a member who is later removed remains counted toward the threshold indefinitely.

### Title
Stale confirmations from removed multisig members remain counted toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member()` fails to purge the removed member's confirmation entries from other members' pending requests, so a request can execute with fewer *live* member confirmations than `num_confirmations` requires.

### Finding Description
When a `DeleteMember` request executes, `delete_member()` at [1](#0-0)  only removes requests that the removed member itself originally submitted (`r.member == member`), and it removes the member's own `num_requests_pk` counter. It never inspects `self.confirmations` for *other* pending requests where the removed member had previously added a confirmation as one of multiple signers.

`confirm()` at [2](#0-1)  only compares the size of the stored `HashSet<String>` of confirmer identities against `self.num_confirmations`; it never re-validates that each already-recorded confirmer is still `self.members.contains(...)`. `current_member()` at [3](#0-2)  is only invoked for the *new* confirming caller, not for previously stored confirmations.

Binding that should hold: `confirmations_counted(request) == live_member_confirmations(request)`. After a member is removed while they hold a lingering confirmation on someone else's pending request, this becomes `confirmations_counted(request) = live_member_confirmations(request) + 1`, i.e. the threshold can be satisfied with one fewer genuinely live, currently-authorized signer than `num_confirmations` mandates.

### Impact Explanation
This breaks the multisig authorization invariant: a request (including `Transfer`, `AddKey`, `FunctionCall`, or further `DeleteMember`/`AddMember` actions) can be executed by `confirm()` with effectively `num_confirmations - 1` live members, because one of the "confirmations" belongs to an account/key that is no longer a member and can no longer act on behalf of the multisig. This matches the report's "confirmations counted versus live members" custody binding and the "multisig request executed below threshold" Critical impact category.

### Likelihood Explanation
This requires no special privilege beyond being (or having been) a legitimate multisig member at some point — any member who confirms a multi-step/slow-moving request and is subsequently removed (e.g., in routine membership rotation, key compromise remediation, or employee offboarding) leaves a stale, still-counted confirmation behind on any other request they had confirmed. Since `add_request`/`confirm` allow requests to sit pending (bounded by `active_requests_limit` and no expiry other than a 15-minute minimum before deletion), the window for this to occur in normal operation is realistic.

### Recommendation
When deleting a member in `delete_member()`, iterate over `self.confirmations` for all requests and remove the string identity of the member being deleted from each confirmation set (not just from requests they originally submitted). Alternatively, revalidate every stored confirmer against current `self.members` at `confirm()` time before counting them toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `B` calls `add_request(R)` (some `Transfer` action) — `R` is pending with 0 confirmations, submitted by `B`.
3. `C` calls `confirm(R)` — confirmations for `R` = `{C}`.
4. Separately, members execute a fully-confirmed `DeleteMember { member: C }` request — `C` is removed from `self.members`; `delete_member()` only clears requests where `r.member == C` (i.e., requests `C` itself submitted), leaving `R`'s confirmation set `{C}` untouched since `R` was submitted by `B`.
5. `A` calls `confirm(R)` — confirmations for `R` becomes `{C, A}`, size 2, then `D` calls `confirm(R)` — size reaches 3 ≥ `num_confirmations`, and `R` executes via `execute_request()` even though `C` is no longer a member — only `B`(submitter, uncounted toward confirmations)/`A`/`D` are live confirmers actually authorizing it alongside a phantom confirmation from removed member `C`.     fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
