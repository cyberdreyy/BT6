### Title
Post-default withdraw receipts drain the fixed default-recovery reserve at par, starving defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefaultRecovery`, the recovery pool (`defaultRecoveryReserve`) is fixed and sized to cover only the claims that existed at finalization, each haircut by `defaultRecoveryPrice`. However, `requestWithdraw` still mints brand-new receipts post-default and books them in `postDefaultRequests`, and `_claimPostDefaultWithdrawRequest` pays them **1:1 out of the same reserve**. Any unprivileged lender can therefore inject fresh claims that consume reserve meant for defaulted-epoch claimants — the closest analog to the CVE-2021-47748 pattern of attacker-controlled input reaching a privileged executor (here, attacker-influenced claim basis reaching an un-refilled reserve).

### Finding Description
In `requestWithdraw`, when `defaultRecoveryFinalized` is true, the strategy burns `_amount` strategy tokens from the CDO and mints the same amount to the user as a receipt, recording `postDefaultRequests[_user] = _amount`. No underlying is collected and no accounting enlarges `defaultRecoveryReserve` — the comment says the CDO passes "an already-haircut amount because finalization lowered virtualPrice," but the *payout* path pays the full recorded amount.

Claims execute via `claimWithdrawRequest` → `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery(_user, amount)`, which does `defaultRecoveryReserve -= _amount` and transfers underlying at par.

Meanwhile, `finalizeDefaultRecovery` sets `defaultRecoveryReserve = reserveAmount` exactly equal to `recoveredAmount + prefundedReserve + prior reserve`, sized so that `totalBasis * recoveryPrice ≈ reserveAmount` for the defaulted claimants only. Every wei of reserve is already spoken for. A post-default claim of `X` therefore removes `X` that belongs to defaulted receipts, and once reserve hits zero, `_transferDefaultRecovery` underflows (0.8.x checked arithmetic) or the `safeTransfer` fails — defaulted claimants are left unpaid.

Attacker sequence (running post-default phase):
1. Vault defaults; owner finalizes via `finalizeDefaultRecovery` → `defaultRecoveryReserve = R`, `defaultRecoveryPrice = p < 1e18`.
2. Attacker (any KYC-passing lender holding tranche tokens) deposits/redeems so that `requestWithdraw(amount, attacker, principal)` runs the post-default branch: mints `amount` receipts and sets `postDefaultRequests[attacker] = amount`, with zero new funding.
3. Attacker calls `claimWithdrawRequest(attacker)` through the CDO → receives `amount` at par from `defaultRecoveryReserve`.
4. Repeat/dust — honest defaulted claimants calling `_claimDefaultedWithdrawRequest` now revert or receive nothing because reserve was spent.

### Impact Explanation
Direct theft of the recovery reserve by post-default requesters, and/or permanent freezing of defaulted-epoch claims once the reserve is exhausted. Loss quantified as `min(total postDefaultRequests claimed, defaultRecoveryReserve)` — up to the full recovery fund meant for existing claimants. The reserve-isolation invariant (each defaulted claim funded pro-rata) is broken because the post-default path adds claims without adding funding.

### Likelihood Explanation
Requires only that the vault defaults and recovery is finalized — a normal protocol phase — and that the attacker holds tranche tokens (any KYC'd lender). No privileged role is involved: the attacker transacts through the public CDO deposit/withdraw surface. The gate `requestWithdraw` only requires the CDO as `msg.sender`, which any user reaches via the CDO's withdraw path. Guards present (`_transferFundedClaim` reserve guard, `defaultRecoveryFinalized` checks) explicitly protect funded claims from spending the reserve, but `_transferDefaultRecovery` has no corresponding cap tying `postDefaultRequests` payouts to newly funded balance.

### Recommendation
Do not pay `postDefaultRequests` from `defaultRecoveryReserve`. Either:
- Route post-default claims through `_transferFundedClaim` and require the CDO to first fund them via `collectWithdrawFunds` (extend `collectWithdrawFunds` to track a post-default pending basis), or
- Track a separate `postDefaultReserve` credited only by actual borrower repayments, so post-default receipts can never consume pre-default recovery funds, or
- Disallow new withdraw requests entirely while `defaultRecoveryFinalized` is true.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import {IdleCreditVault} from "contracts/strategies/idle/IdleCreditVault.sol";

contract PostDefaultReserveDrainPoC is Test {
    // Setup: fork mainnet, deploy vault + CDO, lender deposits, epoch runs,
    // borrower defaults, owner calls finalizeDefaultRecovery -> reserve = R, price = p.

    function test_PostDefaultRequestDrainsRecoveryReserve() external {
        // Pre-state
        uint256 reserve = vault.defaultRecoveryReserve();
        assertGt(reserve, 0);
        assertEq(vault.defaultRecoveryPrice() < 1e18, true); // haircut > 0

        // 1. Attacker holds tranche tokens post-default and triggers requestWithdraw
        //    via the CDO withdraw path. Strategy mints receipts, books postDefaultRequests.
        vm.prank(address(cdo));
        vault.requestWithdraw(100e6, attacker, 100e6); // post-default branch
        assertEq(vault.postDefaultRequests(attacker), 100e6);

        // 2. No funding occurred, but claim pays 1:1 from the default recovery reserve.
        uint256 balBefore = underlying.balanceOf(attacker);
        vm.prank(address(cdo));
        uint256 paid = vault.claimWithdrawRequest(attacker);
        assertEq(paid, 100e6);
        assertEq(underlying.balanceOf(attacker) - balBefore, 100e6);
        assertEq(vault.defaultRecoveryReserve(), reserve - 100e6); // stolen from defaulted claimants

        // 3. Repeat until reserve < honest claim -> honest claim reverts (frozen funds).
    }
}
```

Caveat: if the intended design routes post-default repayments into the strategy before claims and the reserve is meant only as an accounting floor, the finding degrades to "post-default claims can still revert when reserve accounting lags actual balance" — a temporary-freeze variant rather than theft. A fork PoC against a live defaulted vault deployment is needed to confirm which behavior manifests.
