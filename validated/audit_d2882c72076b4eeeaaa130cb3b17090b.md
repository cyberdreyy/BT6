### Title
Stale confirmations from a deleted key remain counted toward the confirmation threshold - ([File: multisig/src/lib.rs])

### Summary
`MultiSigContract` never purges a signing key's already-cast confirmations from *other* pending requests when that key is removed via a `DeleteKey` action, allowing a request to reach `num_confirmations` using a phantom approval from a key that is no longer a member of the multisig.

### Finding Description
The contract tracks, per `request_id`, a `HashSet<PublicKey>` of keys that confirmed it, and a request executes once `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0) . The binding the protocol relies on is: `confirmations for request R == approvals from currently-valid multisig keys`. However, when a key is removed via `MultiSigRequestAction::DeleteKey`, the code only purges requests whose *creator* (`signer_pk`) equals the deleted key; it does not scan or clean the `confirmations` sets of other, unrelated requests that this key may have already confirmed: [2](#0-1) 

`assert_valid_request` (called from `confirm`) also does nothing to validate that the confirming keys stored in `confirmations` are still members of the contract — it only checks that the request/confirmation entries exist [3](#0-2) . Once a key is deleted (its access key removed on-chain and, if it was the creator of some requests, those requests purged), any confirmation it previously placed on a request created by a *different* key is left untouched in `self.confirmations`. That stale confirmation still counts toward `num_confirmations` on the next `confirm` call from a still-valid key, letting the request execute (including arbitrary `Transfer`, `AddKey`, `FunctionCall`, etc. to `receiver_id`) with fewer live-member approvals than the threshold nominally requires.

This is a structural analog of the reported `ongoing_soul_tx` bug class: a piece of state (`ongoing_soul_tx` recipient / here, the `confirmations` set) is trusted across a later, unrelated state transition (recipient swap / here, key removal) without re-validating that the originally recorded actor/target is still the one authorized at execution time.

### Impact Explanation
This breaks the authorisation threshold the multisig is designed to enforce: `confirmations counted != live members who approved`. An attacker who once held a key that later gets revoked (e.g., an employee offboarded, a compromised key rotated out) can leave behind confirmations on pending requests that later get combined with only one additional live confirmation to execute fund transfers, key additions, or arbitrary function calls — effectively executing a k-of-n request with fewer than k currently-authorized signers. Since `Transfer` and `AddKey`/`FunctionCall` actions can move NEAR or grant new full-access keys, this is a Critical-impact authorisation bypass (funds moved, or control ceded, without the required number of *current* signers).

### Likelihood Explanation
This does not require compromising the foundation, the contract owner, or the deployment process — it only requires normal multisig lifecycle operations (a key being confirmed on a pending request and later removed, which is an expected operational pattern, e.g. offboarding). No malicious redeploy or external party is needed; the flaw is purely in `MultiSigContract`'s own bookkeeping. Any multisig instance that ever removes a key while other requests are pending is exposed.

### Recommendation
When executing `DeleteKey`, iterate over all outstanding requests' `confirmations` sets and remove the deleted public key from each of them (not just requests the deleted key itself created), and re-check whether any request should now be considered "at risk" of stale approvals. Alternatively, on `confirm`, validate that every public key currently stored in a request's `confirmations` set is still a valid multisig key before counting it toward the threshold (e.g., intersect the confirmation set with the currently known key set at confirm/execute time rather than trusting a stale cached set).

### Proof of Concept
1. Deploy `MultiSigContract::new(2)` with two access keys, `A` and `B` (`num_confirmations = 2`).
2. Key `A` calls `add_request` to create request `R` transferring funds to an attacker-controlled `receiver_id` (created via `add_request`, not yet confirmed by `A`, `confirmations = {}`) [4](#0-3) .
3. Key `B` calls `confirm(R)`; since `confirmations.len()+1 (=1) < 2`, it is only recorded: `confirmations = {B}` [5](#0-4) .
4. Separately, via a legitimate/expected governance action, key `B` is removed by executing a `DeleteKey { public_key: B }` request (confirmed normally by `A` and another key). This purges only the requests `B` itself created — `R` (created by `A`) is untouched, and `B`'s confirmation on `R` is never removed [2](#0-1) .
5. Key `A` (the only remaining valid key at this point in a 2-key contract, or one of several remaining keys in a larger set) calls `confirm(R)` again. `confirmations.len()+1 (={B}.len()+1 = 2) >= num_confirmations (2)`, so `R` executes and transfers funds to the attacker's `receiver_id` — even though `B`'s key no longer exists as an authorized multisig member [6](#0-5) .

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
