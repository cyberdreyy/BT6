## Analog Found

I checked the marginfi program for the same bug class — a "set new authority/admin without a zero-address check" pattern in an unprivileged-user path — and found a direct hit in the account-migration instructions.

### Title
Missing zero-address check on `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` permanently locks migrated user funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let any marginfi account authority migrate their account's balances to a brand-new `MarginfiAccount` under a caller-supplied `new_authority`. This account is explicitly documented in the code as unchecked, and no instruction-level or state-level validation rejects `Pubkey::default()` (the zero address) as the new authority.

### Finding Description
The `new_authority` account is declared as a fully unchecked account: [1](#0-0) 

It is written directly into the new account's `authority` field via `initialize_migrated_account` → `new_account.initialize(...)`, with no validation performed anywhere in `transfer_to_new_account` or `transfer_to_new_account_pda`: [2](#0-1) [3](#0-2) 

`MarginfiAccount::initialize` sets `self.authority = authority` unconditionally: [4](#0-3) 

Once `new_account.authority == Pubkey::default()`, every future permissioned action on that account (`is_signer_authorized`) can only ever succeed if a signer's public key equals `Pubkey::default()`, which requires a private key that doesn't exist. So no signer can ever match the account authority again: [5](#0-4) 

At migration time, the *entire* `lending_account` (all deposit/borrow balances) is copied from the old account into the new one, and the old account is disabled/zeroed, meaning the funds live only on the new (now zero-authority) account: [6](#0-5) 

This is functionally the same bug class as the reported `Governable.transferGovernor()` issue: a privileged/self-controlled field is overwritten with an attacker-or-user-supplied address with no zero-address guard, permanently bricking access to the account and its authority-gated functions. Unlike the external report's admin-only context, this path is reachable by any regular, unprivileged marginfi account holder acting on their own account — matching the "unprivileged-user authority check" category this scan is scoped to.

Notably, the project's own CLI tooling (`p0-cli`) already treats this as a known risk and defensively checks for it client-side before building the same instruction, but the on-chain program itself performs no such check: [7](#0-6) 

That the CLI added a client-side zero-address guard, but the equivalent on-chain instruction did not, confirms this is a real gap rather than an intentional design choice.

### Impact Explanation
If `new_authority` is passed as `Pubkey::default()` (accidentally, e.g., due to a wallet/config bug on the caller's end, or a malicious front-end/integrator crafting the transaction), the resulting new `MarginfiAccount` receives all of the user's migrated balances (deposits and any liabilities) but has no controllable authority. The account becomes permanently unreachable: no withdraw, repay, close, or any authority-gated instruction can ever be executed against it again, since `is_signer_authorized` can never match a real signer. This constitutes a durable, unrecoverable freeze of user funds with direct financial effect.

### Likelihood Explanation
The instruction is permissionless from the perspective of "who can trigger it" (any account authority for their own account) and requires no privileged role. The only barrier is that a caller must supply `Pubkey::default()` for `new_authority`, which would typically happen through a bugged client, malicious/compromised front-end, or a mis-integrated third-party caller (the "third_party_id" flow in `transfer_to_new_account_pda` broadens the set of possible callers via CPI). Given the CLI code already anticipated and guarded against exactly this input, the likelihood of it occurring through some caller path is non-trivial.

### Recommendation
Add an explicit zero-address check in both `transfer_to_new_account` and `transfer_to_new_account_pda`, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority // or similar
);
```
placed before `initialize_migrated_account` is called, mirroring the guard already present in `p0-cli/src/processor/account.rs`.

### Proof of Concept
1. Create a `MarginfiAccount` with active deposit/borrow balances, `authority = A`.
2. `A` calls `transfer_to_new_account` (or `transfer_to_new_account_pda`), signing as `authority`, and passes `new_authority = Pubkey::default()`.
3. The instruction succeeds: `old_account` is disabled/zeroed (`ACCOUNT_DISABLED` flag set, `migrated_to` set), and `new_account` is initialized with `authority = Pubkey::default()` and inherits all of `old_account`'s `lending_account` balances.
4. Any subsequent instruction touching `new_account` (withdraw, repay, close, transfer again, etc.) fails `is_signer_authorized` for every possible signer, since no keypair can produce the `Pubkey::default()` public key — the funds are permanently frozen.
