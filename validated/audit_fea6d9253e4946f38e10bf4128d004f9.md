### Title
Rounded-down `epochPrice` over-distributes tranche tokens in `claimDepositRequest`, permanently freezing the last claimer's queued deposit - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The analog to the Solana `U64RatioFloor:reverse` round-up bug is in `IdleCDOEpochQueue`. `processDeposits` stores an implied deposit price as `epochPrice[_epoch] = _pending * ONE_TRANCHE / _trancheMinted`, which truncates toward zero. `claimDepositRequest` then performs the *reverse* conversion — underlying deposited → tranche shares — using `amount * ONE_TRANCHE / epochPrice[_epoch]`. Because the stored price is biased low, every claimer is paid slightly more tranche tokens than their exact pro-rata share of the shares actually minted to the queue. Each claim adds up to (just under) 1 wei of over-issuance. The queue only holds `_trancheMinted` shares, so once the cumulative rounding deficit reaches 1 wei, a later claimer's `safeTransfer` reverts — and since `deleteRequest` is blocked once `epochPrice` is set, that user's entire queued deposit is frozen permanently.

### Finding Description [1](#0-0)  computes the epoch price with floor division in the "forward" direction (underlying → price). Floor-rounding a denominator biases the subsequent inverse conversion at [2](#0-1)  upward: `amount * ONE_TRANCHE / epochPrice` returns at least the exact share, and up to ~1 wei more per claim, exactly like the report's `reverse` returning one extra lamport.

The queue is solvency-constrained: after `processDeposits`/`processPrefundedDeposits` it holds exactly the shares minted by `_cdo.depositAA(_pending)` (or `_mintSharesAtCurrPrice` for prefunded at [3](#0-2) ). Claims are processed FIFO at user discretion, so an attacker who claims first extracts the rounding surplus; the deficit is socialized onto whoever claims last.

There is no recovery path: `deleteRequest` reverts when `epochPrice[_epoch] != 0` ( [4](#0-3) ), `claimDepositRequest` pays an all-or-nothing fixed amount with no partial-claim option, and `userDepositsEpochs` is only cleared on a successful transfer. The same pattern in `processWithdrawRequests` is safe (withdraw price rounds down → users receive *less*), but the deposit-side inverse conversion rounds *in the user's favor*.

### Impact Explanation
Permanent freezing of user funds. Once ≥1 wei of tranche-token deficit exists in an epoch, a victim's `claimDepositRequest` reverts forever on the `safeTransfer`, and the deposit cannot be cancelled — the victim's entire queued underlying for that epoch is locked in the queue (its value was already converted into tranche shares held by the queue, which no one can now claim). Loss magnitude equals the victim's full epoch deposit; the attacker also gains up to ~1 wei of tranche per claim (theft is dust, but the freezing impact is not).

### Likelihood Explanation
Requires a queued-epoch deployment (`IdleCDOEpochVariant`/`...Prefunded` with `IdleCDOEpochQueue`) and at least two prior claims in the victim's epoch to accumulate ≥1 wei of over-issuance (each claim contributes <1 wei). An attacker needs two or more KYC-passing wallets (`_checkAllowed` enforces `isWalletAllowed`, [5](#0-4) ), makes small `requestDeposit`s during a running epoch, then claims first after `processDeposits` — provided the per-claim remainders sum to ≥1 wei, which an attacker can arrange by choosing deposit amounts that maximize truncation residue. Honest owner/manager merely calls `processDeposits`; no privileged misbehavior needed. Note: the invariant violation is real but the attacker setup (multiple KYC wallets, precise remainder engineering) makes it moderately unlikely per epoch; repeated epochs give repeated attempts.

### Recommendation
Round `epochPrice` *up* instead of down so the inverse claim conversion cannot over-distribute:

```solidity
// contracts/IdleCDOEpochQueue.sol
epochPrice[_epoch] = (_pending * ONE_TRANCHE + _trancheMinted - 1) / _trancheMinted;
```
and similarly for the prefunded path at [6](#0-5) . Alternatively, account claims against a recorded `epochSharesMinted[_epoch]` and pay `amount * sharesMinted / _pending` (floor, bounded by the actual balance). As a safety net, let the last claimer sweep `min(entitlement, queueBalance)` or allow `deleteRequest` of the share position when the queue is insolvent.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCDOEpochQueue.t.sol` helpers (`_depositWithUser`, `_stopCurrentEpochWithApr`, `queue.processDeposits`):

```solidity
function testEpochPriceRoundingFreezesLastClaim() external {
    // Epoch running; two attacker KYC wallets + victim queue deposits.
    // Choose amounts so floor(pending*1e18/minted) < exact price,
    // e.g. pending = 3 wei underlying split as 1 wei (attacker A), 1 wei (attacker B),
    // and victim deposit V (eg 1000e6 USDC) deposited via requestDeposit.
    _queueDepositWithUser(attackerA, 1);
    _queueDepositWithUser(attackerB, 1);
    _queueDepositWithUser(victim, 1000e6);

    _stopCurrentEpochWithApr(10e18);        // buffer period, epoch N
    vm.prank(manager);
    queue.processDeposits();                // sets epochPrice[N] rounded DOWN

    uint256 epoch = strategy.epochNumber(); // == N per queue indexing
    // Attackers claim first: each receives > exact pro-rata shares.
    vm.prank(attackerA); queue.claimDepositRequest(epoch);
    vm.prank(attackerB); queue.claimDepositRequest(epoch);

    // Queue tranche balance is now < victim entitlement (deficit >= 1 wei).
    vm.expectRevert(); // SafeERC20: transfer amount exceeds balance
    vm.prank(victim);
    queue.claimDepositRequest(epoch);

    // No escape: delete is blocked because epochPrice is set.
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(victim);
    queue.deleteRequest(epoch);
    // victim's 1000e6 USDC worth of tranche shares is permanently stuck.
}
```

Caveat: I could not fully verify the exact queue epoch indexing used in `claimDepositRequest` end-to-end (claim uses the epoch key recorded at `requestDeposit` time, i.e. `epochNumber + 1`), and the concrete deposit amounts that produce ≥1 wei aggregate deficit must be tuned against the live tranche price — the PoC should sweep small attacker deposits to find remainders that sum past 1 wei.

```text
  function deleteRequest(uint256 _requestEpoch) external {
    // if the epoch price is already set, deposits were already processed so
    // the deposit request can't be deleted.
    _checkNotAllowed(epochPrice[_requestEpoch] != 0 || epochPrefundedDeposits[_requestEpoch] != 0);

    uint256 amount = userDepositsEpochs[msg.sender][_requestEpoch];
    if (amount == 0) {
      return;
    }
    // reset user deposit for the epoch
    userDepositsEpochs[msg.sender][_requestEpoch] = 0;
    // update pending deposits
    epochPendingDeposits[_requestEpoch] -= amount;
    // transfer underlyings back to the user
    IERC20Detailed(underlying).safeTransfer(msg.sender, amount);
```
