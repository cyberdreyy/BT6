### Title
Deterministic account's `AccountContract` slot can be pre-occupied via `UseGlobalContract`/`DeployGlobalContract` before its rightful `DeterministicStateInitAction`, silently skipping state-init deployment - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
`action_deterministic_state_init` only calls `deploy_deterministic_account` when `account.contract().is_none()` [1](#0-0) , but `check_account_existence` permits `Action::UseGlobalContract`/`Action::DeployGlobalContract` to run against a deterministic account id as soon as it exists in any form, including the "uninit" state created by a bare `Transfer` [2](#0-1) . This lets a party that can act on the account before the legitimate `DeterministicStateInitAction` arrives set `AccountContract` to an arbitrary global contract identifier via `use_global_contract` [3](#0-2) , which permanently satisfies the `is_none()` gate and makes the state-init logic silently no-op instead of deploying the intended `state_init` code.

### Finding Description
`action_deterministic_state_init` treats "has `account.contract()` == None" as the sole signal that the deterministic account is still in the NEP-616 "uninit" state and therefore safe to initialize: [1](#0-0) 

The documented precondition for `deploy_deterministic_account` is explicit that "the account must not have any contract data stored" at the moment it is called [4](#0-3) . Nothing else marks the slot as "reserved for a specific state_init" — any code path that sets `AccountContract` to something other than `None` (not just `DeterministicStateInitAction`) will make this precondition check pass trivially and cause `action_deterministic_state_init` to skip step 1/2 of `deploy_deterministic_account` entirely.

`check_account_existence`, which gates `Action::UseGlobalContract` and `Action::DeployGlobalContract`, only requires that the account exist — it does not additionally require `account.contract().is_none()` be false/true in either direction, nor does it special-case deterministic accounts: [2](#0-1) 

Per `docs/DataStructures/Account.md`, a deterministic account id can exist in an "uninit" state (contract = `AccountContract::None`) purely as the result of a plain `Transfer`, which is far weaker than `DeterministicStateInit` (`Action::Transfer` case at `actions.rs:819-827` allows creation of the account with no contract set). Once such an "uninit" account exists, `use_global_contract` will happily rewrite `account.contract()`: [3](#0-2) 

Given the precondition established in the referenced prior analysis (that an attacker can obtain a receipt whose `actor_id` equals the deterministic account id itself, satisfying whatever actor-permission check gates `UseGlobalContract`/`DeployGlobalContract`), the exploit sequence is:
1. Attacker publishes/owns a global contract under an identifier they control (`GlobalContractIdentifier::AccountId(attacker_id)` or a code hash of their own wasm), via `action_deploy_global_contract` [5](#0-4) .
2. `Transfer(0, det_id)` is executed against the not-yet-existing deterministic id `det_id`, creating it in the "uninit" state with `contract = None`.
3. Before the rightful `DeterministicStateInitAction` receipt lands, the attacker executes `UseGlobalContractAction(attacker_identifier)` targeting `det_id` (permitted because the account now exists, satisfying `check_account_existence`, and by assumption `actor_id == det_id`). This runs `use_global_contract`, setting `account.contract()` to `AccountContract::GlobalByAccount(attacker_id)` (or `Global(code_hash)`), and bumping storage usage accordingly.
4. When the legitimate `DeterministicStateInitAction` receipt is later applied, `account.contract().is_none()` is now `false`, so `deploy_deterministic_account` is never invoked — the intended `state_init` code/data is never written. Execution falls straight through to the storage-staking/deposit-refund logic, and `result.result` is never set to an error, so the receipt is reported as successful.

The net effect: the account permanently ends up running the attacker's chosen global contract instead of the code the deterministic id was derived from, with no error surfaced anywhere in `ActionResult`.

### Impact Explanation
This breaks the authorization/metering-totality invariant documented at `deterministic_account_id.rs:116-120`: the state-init precondition ("no contract data stored") is supposed to be exclusive to the legitimate `DeterministicStateInitAction`, but it can be satisfied — and then permanently poisoned — by an unrelated action. Any protocol or application relying on NEP-616 deterministic derivation (id ⇒ code) to authorize funds transfer or cross-contract calls would instead interact with attacker-controlled code, enabling theft of any funds sent to `det_id` expecting the legitimate contract, or arbitrary logic substitution in contract-execution flows. This falls under the "authorization escalation across accounts" / "theft of user funds" NEAR bounty categories, scoped to Contracts execution flows as stated in the question.

### Likelihood Explanation
The finding is contingent on the precondition carried over from the referenced prior question — that an ordinary, unprivileged attacker can obtain `actor_id == det_id` for a `UseGlobalContract`/`DeployGlobalContract` receipt targeting the not-yet-initialized deterministic account. If that actor-spoofing precondition holds, the remainder of the attack requires only: (a) knowledge of the target `det_id` before its owner submits the `DeterministicStateInitAction` (a front-running/race condition, since deterministic ids are derivable off-chain by anyone who knows the intended state_init), (b) a cheap `Transfer(0, det_id)`, and (c) one `UseGlobalContract` action referencing any existing global contract (including one the attacker deploys themselves). No validator, node, or protocol-level access is required beyond what the prior question already assumes.

### Recommendation
Do not rely solely on `account.contract().is_none()` as the state-init gate. Either (a) reject `UseGlobalContract`/`DeployGlobalContract` (and any other contract-slot-mutating action) against accounts that are still in the NEP-616 "uninit" deterministic state until `DeterministicStateInitAction` has run, or (b) track an explicit "deterministic account initialized" flag independent of `AccountContract` so `deploy_deterministic_account`'s precondition cannot be satisfied by unrelated actions, and surface an explicit `ActionError` (rather than silently succeeding) when `DeterministicStateInitAction` finds the contract slot already occupied by non-matching content.

### Proof of Concept
Unit test in `runtime/runtime/src/deterministic_account_id.rs` (or a runtime-integration test alongside `test-loop-tests/src/tests/deterministic_account_id.rs`):
1. Create an account in "uninit" deterministic state (`Account::new(.., AccountContract::None, ..)`), simulating the post-`Transfer` state.
2. Deploy/register a global contract under `attacker_identifier` and call `use_global_contract(state_update, account_id, &mut account, &attacker_identifier, &mut result)`; assert `result.result` is `Ok` and `account.contract() == AccountContract::GlobalByAccount(attacker_id)` (or `Global(hash)`).
3. Call `action_deterministic_state_init` with a `DeterministicStateInitAction` whose `state_init` differs from `attacker_identifier`.
4. Assert: `result.result` is still `Ok` (no `ActionError` raised) and `account.contract()` still equals the attacker's identifier, not the one derived from `state_init` — demonstrating that the rightful state-init silently no-ops while `ActionResult` reports success.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

    Ok(())
}

pub(crate) fn use_global_contract(
    state_update: &mut TrieUpdate,
    account_id: &AccountId,
    account: &mut Account,
    contract_identifier: &GlobalContractIdentifier,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let key = TrieKey::GlobalContractCode { identifier: contract_identifier.clone().into() };
    if !state_update.contains_key(&key, AccessOptions::DEFAULT)? {
        result.result = Err(ActionErrorKind::GlobalContractDoesNotExist {
            identifier: contract_identifier.clone(),
        }
        .into());
        return Ok(());
    }
    clear_account_contract_storage_usage(state_update, account_id, account)?;
    if account.contract().is_local() {
        state_update.remove(TrieKey::ContractCode { account_id: account_id.clone() });
    }
    let contract = match contract_identifier {
        GlobalContractIdentifier::CodeHash(code_hash) => AccountContract::Global(*code_hash),
        GlobalContractIdentifier::AccountId(id) => AccountContract::GlobalByAccount(id.clone()),
    };
    account.set_storage_usage(
        account.storage_usage().checked_add(contract_identifier.len() as u64).ok_or_else(|| {
            StorageError::StorageInconsistentState(format!(
                "Storage usage integer overflow for account {}",
                account_id
            ))
        })?,
    );
    account.set_contract(contract).or_inconsistent_state(account_id)?;
    Ok(())
}
