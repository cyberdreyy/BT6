### Title
Double-decrement of `pendingWithdraws` / stale per-epoch counters after default finalization permanently freeze defaulted withdraw receipts — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The closest analog to a use-after-free is the reuse of aggregate and per-epoch accounting cells (`pendingWithdraws`, `withdrawsRequestsByEpoch`, `instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) after their epoch scope was already "freed" at default finalization. `claimWithdrawRequest` -> `_claimDefaultedWithdrawRequest` subtracts the user's `claimBasis` from `pendingWithdraws` even though the borrower-side debt for the defaulted epoch was already consumed when the recovery reserve was priced and funded. If `pendingWithdraws` was cleared or reduced below the sum of remaining claim bases during `finalizeDefault`/`finalizeDefaultRecovery`, every subsequent defaulted-receipt claim reverts on Solidity 0.8 checked arithmetic, permanently freezing each claimant's share of `defaultRecoveryReserve`. The same pattern exists in `_claimDefaultedInstantWithdrawRequest`, which decrements `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]` with saturating logic on one counter but a raw `-=` on the epoch counter.

### Finding Description
In `requestWithdraw`, `pendingWithdraws += _amount` tracks the global amount the borrower must source at `stopEpoch` for pending receipts [1](#0-0) . When the borrower defaults, finalization reprices those receipts through `defaultRecoveryPrice` and isolates repayment in `defaultRecoveryReserve`, which is then enforced as untouchable for funded claims [2](#0-1) . The claim path for a defaulted receipt then does `pendingWithdraws -= claimBasis` per user [3](#0-2) . This is a stale-lifetime bug: `pendingWithdraws` expresses a borrower obligation that no longer exists after the reserve was carved out; each claim subtracts a basis that was already accounted for once at finalization. If `pendingWithdraws` was zeroed or reduced at finalization (the closed-pool migration path `_ensureDefaultRecoveryInitialized` explicitly zeroes it, showing the counter is treated as terminable state [4](#0-3) ), the first or an intermediate claimant hits `pendingWithdraws - claimBasis < 0`, the subtraction reverts, and the claim can never succeed. Because `claimWithdrawRequest` is the only path that burns the receipt and pays `_transferDefaultRecovery`, the affected recovery reserve is permanently locked.

The symmetric issue is in `_claimDefaultedInstantWithdrawRequest`: `pendingInstantWithdraws` is clamped (`claimBasis >= pending ? 0 : pending - claimBasis`) but `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` is not [5](#0-4) . If the aggregate epoch counter was already reduced at finalization while an individual user's `instantWithdrawsRequestsByEpoch` entry persists, this `-=` underflows and reverts.

### Impact Explanation
Permanent freezing of unclaimed yield / recovery funds. Any lender or tranche-token holder holding a defaulted-epoch receipt (normal, APR0, or instant) whose claim is processed after `pendingWithdraws` (or `instantWithdrawClaimsByEpoch`) has dropped below their `claimBasis` can never recover their haircut share of `defaultRecoveryReserve`. The reserve tokens remain in the vault with no sweep path for user receipts; loss equals the sum of stranded claim bases, potentially the entire recovery reserve.

### Likelihood Explanation
Likelihood depends on whether `finalizeDefault`/`finalizeDefaultRecovery` resets `pendingWithdraws` and `instantWithdrawClaimsByEpoch` to the funded remainder rather than the full pre-default basis. I was not able to fully trace the finalization internals within the available search iterations — the 42 matches for these counters in `IdleCreditVault.sol` and `IdleCDOEpochVariant.sol` include the funding logic that determines whether the underflow triggers on the first claim or only after partial claims. The bug also requires a borrower default event, which is an exceptional but explicitly supported flow (the dedicated `_claimDefaulted*` machinery and `postDefaultRequests` show this path is live code, not dead code). If finalization leaves `pendingWithdraws` equal to the total defaulted claim basis, the counter self-consistently drains to zero and the finding degrades to a latent inconsistency; if it clears or nets it, the freeze is deterministic.

### Recommendation
Stop mutating `pendingWithdraws` inside `_claimDefaultedWithdrawRequest` — the defaulted-epoch basis should be considered settled at finalization, so either zero `pendingWithdraws`'s defaulted component once during `finalizeDefault` or track a separate `defaultedClaimBasisOutstanding` counter for informational purposes only. Apply the same saturating pattern used for `pendingInstantWithdraws` to `instantWithdrawClaimsByEpoch[defaultEpoch]`, or remove the decrement if the counter is not consumed elsewhere. Add a fork test that defaults mid-epoch with two claimant users and asserts both can claim regardless of order.

### Proof of Concept
A conclusive Foundry fork PoC could not be completed in the available iterations because the decisive behavior — whether `finalizeDefault`/`finalizeDefaultRecovery` leaves `pendingWithdraws` and `instantWithdrawClaimsByEpoch` at full pre-default basis or at a reduced funded value — sits in code I could not fully read. The required test shape is:

```solidity
// 1. deposit AA for userA and userB, start epoch
// 2. both users requestWithdraw during buffer
// 3. borrower defaults; owner/manager calls _handleBorrowerDefault + finalizeDefaultRecovery
// 4. userA.claimWithdrawRequest()  // observe pendingWithdraws / reserve before and after
// 5. userB.claimWithdrawRequest()  // expect success; currently reverts if
//    pendingWithdraws < userB claimBasis after step 4 or after finalization
```

Because the trigger condition could not be confirmed against the finalization code, I cannot assert the revert is reachable rather than masked by consistent finalization accounting — this finding should be treated as a strong candidate pending that single check.   function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }

  /// @notice Transfer default recovery reserve to a user.
  /// @param _user claim receiver
  /// @param _amount amount to transfer
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
