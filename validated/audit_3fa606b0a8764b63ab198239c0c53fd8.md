## Title
Multisig confirmation threshold can be satisfied using stale confirmations from removed members - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only clears confirmations for requests that the removed member *created*, but not confirmations that member *cast on other members' requests*. Since `confirm()` counts confirmations purely by `HashSet<String>.len()` without re-validating that each entry still corresponds to a current member, a request can be executed with confirmations from fewer live members than `num_confirmations` requires, breaking the "confirmations counted versus live members" binding.

### Finding Description
The contract stores confirmations as a `LookupMap<RequestId, HashSet<String>>` keyed by request id, where each `HashSet<String>` holds the string form of `MultisigMember` that confirmed [1](#0-0) .

When a member confirms a request, the code only checks the size of this set against `num_confirmations`, and never re-validates that the members recorded in the set are still current members: [2](#0-1) 

`delete_member` removes the member from `self.members`, clears their `num_requests_pk` entry, and deletes **requests they authored** (matched via `r.member == member`) along with those requests' confirmation sets — but it does not scan other requests' confirmation sets for stale entries belonging to the removed member: [3](#0-2) 

As a result, if member `C` confirms a request `R` that was *created by a different member* (e.g. `B`), and `C` is later removed from the multisig via `DeleteMember`, `C`'s confirmation string remains inside `R`'s confirmation `HashSet`. This is directly analogous to the reported `OrderBook`/`OrderNFT` bug, where `_burnToken()` cleared the NFT ownership mapping (`onBurn`) but failed to zero the parallel `owner` field on the order struct, leaving stale state that `ownerOf()` still trusted. Here, removing a member (the "burn") clears `members`/`num_requests_pk` but leaves a stale confirmation entry that `confirm()` still trusts when computing the threshold.

### Impact Explanation
This lets a multisig request execute with fewer *live* confirmations than the configured `num_confirmations` threshold, i.e., a multisig request executed below threshold — explicitly listed as a Critical impact. Since multisig requests include arbitrary `Transfer`, `FunctionCall`, `AddKey`, and `DeployContract` actions, an attacker who is (or colludes with) a subset of members smaller than the threshold can move funds or take administrative action that the n-of-m design was meant to prevent.

### Likelihood Explanation
Exploitation requires: (1) a member confirms a request they didn't create, (2) that member is later removed via a legitimate `DeleteMember` request, and (3) the original (now under-threshold) request is confirmed to completion afterward. All of these are ordinary multisig operations reachable by members with no special privilege beyond normal participation, and no code path currently prevents or detects the stale entry. The scenario does not require a compromised key, a redeploy, or any out-of-scope actor — only the normal member set changing over time, which is an expected multisig lifecycle event.

### Recommendation
When removing a member in `delete_member`, iterate over all active requests' confirmation sets (not just requests authored by the removed member) and strip the removed member's entry from each. Alternatively, change `confirm()`/execution-threshold logic to only count confirmation entries that are still present in `self.members` at confirmation-completion time, rather than trusting the raw `HashSet` length.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C, D], 3)`.
2. `B` calls `add_request(...)` creating request `R` (`R.member == B`).
3. `C` calls `confirm(R)` → `confirmations[R] = {C}` (1/3).
4. Members execute a separate `DeleteMember { member: C }` request (using A, B, D confirmations) to remove `C`. `delete_member` removes `C` from `members` and `num_requests_pk`, but since no request has `r.member == C`, `R`'s confirmation set `{C}` is left untouched.
5. `A` calls `confirm(R)` → set becomes `{C, A}` (2/3, still under threshold, so no execution yet).
6. `B` (the creator) calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so `remove_request`/`execute_request` fires.
7. `R` executes even though only `A` and `B` are genuinely live members who confirmed it — `C`'s stale confirmation was counted toward the 3-of-4 threshold after `C` had already been removed.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
