## #ValidVulnerability

### Title
Stale rejection weight is never cleared when a signer later accepts the same block, permanently inflating `total_weight_rejected` and wedging the node into falsely discarding valid blocks - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::handle_new_messages` (the node-side stackerdb tally used by `SignerCoordinator::get_block_status`) accumulates `total_weight_approved` and `total_weight_rejected` in a single shared per-block `BlockStatus`. When a signer first rejects a block and later re-evaluates and accepts the very same block (a documented, legitimate flow), the signer's weight is added to `total_weight_approved` but is **never subtracted** from the earlier `total_weight_rejected` accumulation. The signer's weight ends up counted on both sides of the tally simultaneously, permanently biasing the coordinator toward the rejection branch.

### Finding Description
In `StackerDBListener::handle_new_messages`, acceptance and rejection use two different, un-synchronized guards:

- Acceptance path gates on `gathered_signatures`: [1](#0-0) 

- Rejection path gates on the shared `responded_signers` set: [2](#0-1) 

If a signer's first message for a given `block_sighash`/`slot_id` is a `Rejected`, `responded_signers.insert(slot_id)` returns `true` and `total_weight_rejected` is incremented by that signer's weight. If that same signer later re-evaluates and sends `Accepted` for the identical block (per `docs/signer-flows.md` section 3, re-proposals/re-evaluations with `should_reevaluate_reject_reason` legitimately flip a prior rejection to an acceptance), the acceptance path checks only `gathered_signatures.contains_key(&slot_id)` — which is still empty for this signer — so `total_weight_approved` is *also* incremented by the same signer's weight. There is no code path that removes the earlier contribution from `total_weight_rejected` when the flip happens (contrast this with the signer-side `signerdb.rs::add_block_signature`, whose SQL layer *does* clear a stale rejection row when a signature for the same signer/block arrives, as covered by the `reject_then_accept` test): [3](#0-2) 

That correct clearing logic exists only in the signer's local `signerdb.rs`; the node-side coordinator's `BlockStatus.total_weight_rejected` has no analogous decrement, so it accumulates unbounded stale weight across re-evaluations.

The coordinator uses this un-corrected tally to decide the outcome: [4](#0-3) 

Because the rejection branch is checked first, a block that currently has real accepting weight ≥ threshold can still be treated as globally rejected (`NakamotoNodeError::SignersRejected`) if the accumulated phantom (stale) rejection weight from earlier flip-flops crosses `total_weight - weight_threshold`.

### Impact Explanation
This breaks the intended equality that a signer's weight should count toward exactly one side (accept XOR reject) of the tally at any time. The stale, un-decremented rejection weight can never be removed for the lifetime of the `BlockStatus` entry, so as ordinary re-evaluation churn occurs across a handful of signers over the block's lifetime, `total_weight_rejected` can cross the blocking-minority threshold even though the current, real rejecting weight is well under 30%. The result is the miner declaring a legitimately signable block "globally rejected" and discarding it — a liveness wedge on the mining/coordination path: valid blocks that would otherwise reach 70% real approval can be permanently treated as rejected. This matches the "wedge the state machine" / liveness-break criteria (a valid block never gets signed/accepted by the coordinator because of a miscounted rejection tally).

### Likelihood Explanation
Requires only ordinary, single-signer behavior explicitly supported by the protocol (reject a block, then re-evaluate and accept the same block hash after a state change) — no majority collusion, no key compromise, and no malicious signer is needed; it can occur from normal signer state re-evaluation (`should_reevaluate_block`/`should_reevaluate_reject_reason` in `signer.rs`) during ordinary chain activity. The more signers that flip reject→accept across the lifetime of a single proposal (e.g. during contested tenure/reorg windows), the more phantom weight accumulates, making the wedge increasingly likely under exactly the conditions (miner instability, reorg contention) where correctness matters most.

### Recommendation
Track a signer's outcome per `slot_id` as a single mutually-exclusive value (e.g. an enum `Accepted(weight)`/`Rejected(weight)` keyed by `slot_id`, mirroring `signerdb.rs`'s mutual exclusion between `block_signatures` and `block_rejection_signer_addrs`), and derive `total_weight_approved`/`total_weight_rejected` by summing over that map rather than via two independently-incrementing counters. Concretely, in the `Accepted` branch of `handle_new_messages`, if `slot_id` is present in a prior-rejection record, subtract that signer's weight from `total_weight_rejected` before adding it to `total_weight_approved` (and symmetrically for the `Rejected` branch).

### Proof of Concept
1. Coordinator opens `get_block_status` for `block_sighash` with `total_weight = 100`, `weight_threshold = 70`.
2. Signer A (weight 25) sends `Rejected` for `block_sighash` → `responded_signers.insert(A)` is `true` → `total_weight_rejected = 25`.
3. Local chain state changes (e.g. the conflict A rejected on becomes stale/resolved) and A legitimately re-evaluates, sending `Accepted` for the *same* `block_sighash` → `gathered_signatures.contains_key(A)` is `false` → `total_weight_approved += 25` → `total_weight_approved = 25`. `total_weight_rejected` remains `25` (never decremented).
4. Repeat with signers B, C, D similarly flipping reject→accept, each contributing weight to `total_weight_rejected` that is never cleared, while genuinely accepting signers push `total_weight_approved` toward 70.
5. Once accumulated stale `total_weight_rejected` (from signers who have already switched to accepting) plus `weight_threshold` exceeds `total_weight` (i.e. `total_weight_rejected > 30`), the check at `signer_coordinator.rs:509-520` fires and the coordinator returns `NakamotoNodeError::SignersRejected`, discarding the block — even though the *current* real rejecting weight (signers who still disagree) may be 0, and `total_weight_approved` may already be at or above 70.
