No zero-address validation exists anywhere in `contracts/BaseEscrowFactory.sol` (`createDstEscrow`), `contracts/EscrowDst.sol`, or `contracts/BaseEscrow.sol` for the `taker` field of `Immutables`. [1](#0-0) 

### Title
Missing zero-address check on `taker` in `createDstEscrow` permanently disables `cancel`/`rescueFunds` on the destination escrow - (File: contracts/BaseEscrowFactory.sol)

### Summary
`createDstEscrow` accepts an arbitrary caller-supplied `dstImmutables` struct, including the `taker` field, with no validation that `taker != address(0)`, mirroring the external report's root cause (a privileged/role address accepted without a zero-address guard). [1](#0-0)  On `EscrowDst`, both `cancel()` and the inherited `rescueFunds()` are gated exclusively by `onlyCaller(immutables.taker.get())`, with no alternate "public" recovery path analogous to `EscrowSrc.publicCancel`. [2](#0-1) [3](#0-2) 

### Finding Description
`createDstEscrow` deploys a deterministic clone and immediately funds it with native ETH (safety deposit and/or token amount) and/or ERC20 tokens, using immutables fully controlled by `msg.sender`: [1](#0-0) 

Once deployed, the only ways to move funds out of an `EscrowDst` clone are:
- `withdraw` / `_withdraw` — gated by `onlyCaller(immutables.taker.get())` for the private path, but `publicWithdraw` is gated by `onlyAccessTokenHolder()` and still works even if `taker == address(0)`. [4](#0-3) 
- `cancel` — gated exclusively by `onlyCaller(immutables.taker.get())`, with **no public-cancel equivalent** on the destination side (unlike `EscrowSrc.publicCancel`). [2](#0-1) [5](#0-4) 
- `rescueFunds` (inherited from `BaseEscrow`) — also gated by `onlyCaller(immutables.taker.get())`. [3](#0-2) 

Since `address(0)` can never be `msg.sender`, setting `taker = address(0)` when calling `createDstEscrow` makes `cancel()` and `rescueFunds()` permanently unreachable for that escrow instance for its entire lifetime. If the secret is never revealed (e.g., the maker never withdraws, or no access-token holder calls `publicWithdraw` during the public window before the cancellation stage begins), the ERC20 amount and native safety deposit locked in that clone become permanently stranded — no code path can ever move them out.

### Impact Explanation
This matches the Medium-scope criterion: an unprivileged actor (any caller of the permissionless `createDstEscrow`) can put the contract into a state where required token/native balances at that escrow address can never be recovered, because the `cancel`/`rescueFunds` recovery paths are permanently broken by an unchecked zero address in a security-critical role field — the same root cause as the reported Guardian zero-address issue (a role-bearing address accepted without validation, disabling access-controlled functions tied to that address forever). [2](#0-1) 

### Likelihood Explanation
Low-to-Medium likelihood: reaching a *permanent* freeze requires the escrow to also miss the `publicWithdraw` window (no access-token holder calls it while the secret is available), so a rational resolver would not normally set `taker = address(0)` since it forfeits their own private withdrawal/rescue rights and mainly griefs themselves. There is no clear path shown in the code by which an attacker can force a *victim's* funds into this state without the victim's own creation call also supplying `taker = address(0)`; the loss is bounded to funds the caller of `createDstEscrow` themselves deposited.

### Recommendation
Add a zero-address check in `createDstEscrow` (and/or in the `Immutables` validation path) requiring `dstImmutables.taker.get() != address(0)` before deployment, e.g.:
```solidity
require(dstImmutables.taker.get() != address(0), "EscrowFactory: zero taker");
```
Additionally, consider adding a `publicCancel` path to `EscrowDst` analogous to `EscrowSrc.publicCancel` so that funds are never solely gated behind a single, unchecked address.

### Proof of Concept
1. Attacker (or any caller) calls `EscrowFactory.createDstEscrow{value: safetyDeposit(+amount)}(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.taker = Address.wrap(0)`, funding the deterministic clone as required. [1](#0-0) 
2. The private withdrawal window passes without any access-token holder invoking `publicWithdraw` (or the secret is never disclosed to trigger it).
3. Once `block.timestamp` reaches `DstCancellation`, calling `cancel()` reverts for every possible `msg.sender` because `onlyCaller(immutables.taker.get())` compares against `address(0)`. [2](#0-1) 
4. Calling `rescueFunds()` after the rescue delay likewise reverts for every `msg.sender` for the same reason. [3](#0-2) 
5. The ERC20 `amount` and native `safetyDeposit` locked in the clone are permanently unrecoverable.

**Note on confidence**: I could not find any additional validation layer (e.g., in `ImmutablesLib` or elsewhere) that rejects a zero `taker`; my search of `taker.get()`/`InvalidCaller` usages across `contracts/**/*.sol` only turned up the gating call sites cited above, with no zero-address guard.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```
