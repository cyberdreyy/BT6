### Title
Unbounded, unrate-limited `savedCallbacks` map allows unprivileged flooding to evict legitimate pending user callbacks before their DON response arrives - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Finding Description
`HandleLegacyUserMessage` inserts every incoming trigger request into `h.savedCallbacks` keyed by `msg.Body.MessageId` with no per-user quota or rate limiting applied at this layer: the code contains an explicit `// TODO: apply allowlist and rate-limiting here` comment right before the map insert path [1](#0-0) , and the insertion itself is unconditional [2](#0-1) .

`pruneCallbacks` runs on a fixed interval (`defaultCallbackPruneIntervalSec = 30s`) and, if the map size exceeds `MaxSavedCallbacks` (default `20000`), sorts all entries strictly by `createdAt` and deletes the older half regardless of whether those entries are still within `CallbackMaxAgeSec` (default 120s) and regardless of whether a real DON response for them is imminent [3](#0-2) . Eviction is purely a `delete()` from the map — the associated `Callback` is dropped with no `SendResponse` call and no error surfaced to the handler that owns it [4](#0-3) .

When the DON eventually responds, `handleWebAPITriggerMessage` looks up the message ID; if it was evicted, `found` is `false` and the function silently returns `nil`, discarding the real response with no signal to the caller [5](#0-4) .

Exploit flow: an unprivileged (but allowed-to-submit) sender can submit a burst of >20000 low-cost `web_api_trigger` requests within a single ~30s prune window. Because eviction always removes the *oldest* half by `createdAt`, a victim's legitimate, still-valid, not-yet-expired trigger request — submitted slightly before the flood — gets evicted first, before the DON's real (in-time) response can be matched back through `handleWebAPITriggerMessage`. The victim's response is silently dropped even though the DON answered within the normal callback lifetime; the victim's own external wait/timeout logic (owned by the gateway mux/connector layer that calls `HandleLegacyUserMessage`, not shown in this file) will eventually time out, but only because the response was discarded, not because the DON failed to answer in time.

### Impact Explanation
This is an availability/denial-of-service issue: an unprivileged sender can force cross-user request failures by exhausting a shared, size-bounded map with no admission control, causing a legitimate concurrent user's otherwise-successful DON response to be silently discarded. This matches a Chainlink bounty "Denial of Service" impact class (temporary denial of legitimate node/user request-response for other users), not a fund-loss or key-disclosure class.

### Likelihood Explanation
Feasibility depends on how much filtering exists upstream of `HandleLegacyUserMessage` (allowlist/signature checks in the gateway mux are not shown here); the in-function TODO indicates no allowlist/rate-limit is enforced at this handler. If any minimally-permitted signer (e.g., a normal allowed job/user credential) can submit trigger messages without a per-sender quota, generating >10,000 messages within a 30-second window is cheap and fully repeatable, since each request only needs to pass basic payload/timestamp/method validation already present in `HandleLegacyUserMessage`. Repeated attacks amplify the DoS window across prune cycles.

### Recommendation
- Enforce per-sender rate limiting/allowlisting on incoming `web_api_trigger` messages before inserting into `savedCallbacks` (implement the existing TODO).
- Cap `savedCallbacks` insertions with backpressure (reject/queue new inserts once at capacity) instead of silently evicting older, still-valid entries.
- When evicting due to size pressure, call `SendResponse` with an explicit timeout/overload error on the evicted `Callback` instead of a bare `delete()`, so callers get a deterministic signal rather than relying on an unrelated external timeout.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks` set low (e.g., 10) for test speed.
2. Insert one "victim" `savedCallback` with `createdAt = now`, whose `Callback` is a mock recording whether `SendResponse` is called.
3. Insert `MaxSavedCallbacks*2` "attacker" `savedCallback` entries with `createdAt = now.Add(time.Millisecond)` (newer than victim), each with `CallbackMaxAgeSec` still valid.
4. Call `h.pruneCallbacks()`.
5. Assert the victim's entry was deleted from `h.savedCallbacks` (evicted) despite not being expired.
6. Simulate the DON responding to the victim's message ID via `handleWebAPITriggerMessage`; assert it returns `nil` and the victim's mock `Callback.SendResponse` was never invoked — demonstrating the response is silently dropped rather than producing an explicit timeout/error to the victim.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.

	return nil

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
