### Title
`LockupFactory::create` lets the caller override the staking-pool whitelist trusted by the deployed lockup - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` accepts an optional `whitelist_account_id` argument from the (unprivileged) caller and, if supplied, uses it verbatim as the `staking_pool_whitelist_account_id` baked into the newly deployed lockup contract, instead of always using the factory's canonical, foundation-configured `whitelist_account_id`.

### Finding Description
The binding that is supposed to hold is:
`lockup.staking_pool_whitelist_account_id == LockupFactory.whitelist_account_id` (the single, foundation-approved whitelist referenced in `whitelist/README.md`, which every lockup contract is supposed to defer to when deciding whether a staking pool may receive delegated tokens).

Instead, `create()` lets any caller substitute this value: [1](#0-0) [2](#0-1) 

```rust
// Defaults to the whitelist account ID given on init call.
let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
    account_id.into()
} else {
    self.whitelist_account_id.clone()
};
```

This value is forwarded unchecked into `LockupArgs.staking_pool_whitelist_account_id` and passed to the freshly deployed lockup contract's `new()`: [3](#0-2) 

There is no assertion restricting `whitelist_account_id` to the factory's own `self.whitelist_account_id`, and no assertion that `predecessor_account_id() == owner_account_id` either - `create()` is fully permissionless and can be called by anyone for any `owner_account_id`, paying only `MIN_ATTACHED_BALANCE`: [4](#0-3) 

The lockup contract itself unconditionally trusts whatever `staking_pool_whitelist_account_id` it was initialized with when later checking whether a staking pool the owner wants to delegate to is approved (`is_whitelisted` cross-contract call from `select_staking_pool`/`on_whitelist_is_whitelisted` in `lockup/src/lib.rs` and `lockup/src/owner.rs`). Nothing in the lockup contract re-derives or validates that this whitelist account is the canonical NEAR Foundation whitelist - it is a parameter accepted on faith from the factory that constructed it.

Because the lockup account address is deterministic (`sha256(owner_account_id)[..20]` + factory account), and creation is permissionless, an attacker can pre-create the lockup account for a target `owner_account_id` with an attacker-controlled `whitelist_account_id` before the legitimate foundation/HR flow does so. The attacker's fake whitelist contract can be built to answer `is_whitelisted(...) == true` for any staking pool account, including one the attacker fully controls.

### Impact Explanation
This directly matches the rubric's Critical category "a wrongly whitelisted or wrongly parameterised deployment." The security guarantee documented in `whitelist/README.md` - that delegated NEAR can only reach staking pools vetted by the NEAR Foundation - is silently broken for any lockup deployed (or front-run) this way. Once the real owner (e.g., an employee whose vesting lockup this is) later calls `select_staking_pool`/`deposit_and_stake` on what they believe is a foundation-secured lockup, the compromised whitelist will validate any pool as "whitelisted," letting locked/unvested NEAR be delegated to a malicious staking pool that can refuse to return funds - i.e., funds permanently frozen or moved to a party (the attacker's pool) not entitled to them.

### Likelihood Explanation
The attack requires only:
- Knowledge of the target `owner_account_id` (public, since lockup account names are derived deterministically from it), and
- The ability to be the first to call the permissionless `create()` method with that `owner_account_id` and a custom `whitelist_account_id`.

No multisig, factory-owner, or foundation privileges are needed - this is exploitable by any unprivileged NEAR account with `MIN_ATTACHED_BALANCE` (3.5 NEAR), making it a realistic front-running/parameter-injection attack rather than a theoretical one. The existing unit test `test_create_lockup_with_custom_whitelist_success` in `lockup-factory/src/lib.rs` (lines 391-425) confirms the override path is fully functional and intentionally supported by the current code, with no restriction on who can supply it.

### Recommendation
Remove the caller-supplied `whitelist_account_id` override entirely, or if it must remain for flexibility, restrict it so only the factory's owner/foundation (not an arbitrary caller) can specify an alternate whitelist, and/or require `predecessor_account_id() == owner_account_id` (or an explicit foundation-signed approval) before allowing a custom whitelist. At minimum, always fall back to `self.whitelist_account_id` for lockups intended to carry vesting/foundation-controlled schedules, since those are the accounts most likely to be victims of a spoofed deployment.

### Proof of Concept
1. Attacker deploys `EvilWhitelist` contract implementing `is_whitelisted(staking_pool_account_id) -> bool { true }` for every input, and deploys `EvilPool` (a "staking pool" that accepts deposits/stakes but never allows withdrawal).
2. Attacker learns/anticipates the target `victim_owner_account_id` that will eventually be used for a legitimate vesting lockup.
3. Attacker calls `lockup_factory.create(victim_owner_account_id, lockup_duration, ..., whitelist_account_id = Some(EvilWhitelist))` with `MIN_ATTACHED_BALANCE` attached, before the legitimate foundation flow creates the same deterministic lockup account for `victim_owner_account_id`.
4. The lockup contract is deployed at the deterministic address with `staking_pool_whitelist_account_id = EvilWhitelist` baked in via `LockupArgs` ( [5](#0-4) ).
5. When the victim later gains control of this lockup account and calls `select_staking_pool("EvilPool")`, the lockup's cross-contract call to `EvilWhitelist.is_whitelisted("EvilPool")` returns `true`, so the lockup accepts `EvilPool` as valid.
6. Victim's locked/unvested NEAR is staked into `EvilPool`, which never releases it - funds permanently frozen/stolen despite the lockup's documented guarantee that only NEAR Foundation-approved pools can receive delegated funds.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };
