### Title
Stale Confirmations From Removed Members Allow A Multisig Request To Execute Below The Live-Member Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges pending requests and confirmation sets that were *originated* by the member being deleted; it does not scrub that member's public key/account from the `confirmations` set of *other* still-pending requests that member had previously confirmed. Since `confirm()` counts entries in that stale set toward `num_confirmations`, a request can later execute with fewer live members having actually approved it than the configured threshold.

### Finding Description
The intended invariant is: `confirmations.len() (at execution) == number of distinct *current* members who approved the request`, and execution must only occur once that count reaches `num_confirmations`.

`confirm()` simply checks the size of the stored `HashSet<String>` of confirmers against `num_confirmations`, without re-validating that each confirmer is still a member: [1](#0-0) 

Membership removal (`delete_member`) removes the deleted member from `self.members`, and cleans up any request the deleted member *originated*, but it filters solely on `r.member == member` (the request's original signer), leaving that member's entry inside the `confirmations` set of any *other* request they had previously confirmed but did not originate: [2](#0-1) 

Contrast with `add_request`/`confirm`, where a confirmation is recorded simply by inserting `current_member.to_string()` into the confirmations set for that `request_id`, with no re-validation on later confirms of already-stored entries: [3](#0-2) 

So the on-chain ledger of "confirmations for a request" can contain identities that are no longer valid live members, and `confirm()` never re-checks the *existing* entries in the set — it only checks the *current* caller (`current_member`) and the aggregate count.

### Impact Explanation
This breaks the multisig custody binding "confirmations counted versus live members": a `Transfer`, `AddKey`, `DeployContract`, `FunctionCall`, or `DeleteMember`/`AddMember` action can be executed with a live-member confirmation count strictly below `num_confirmations`, because one or more of the counted confirmations come from an account/key that has since been removed from `self.members`. This is a direct match for the Critical impact category "a multisig request executed below threshold" — it can result in unauthorized fund transfers, unauthorized key/permission changes, or unauthorized contract upgrades approved by fewer live signers than the multisig's configured security threshold requires.

### Likelihood Explanation
No privileged action beyond ordinary multisig usage is required from an attacker's perspective — this is a latent accounting bug triggered by the completely legitimate, expected operational sequence of "member confirms request → that member is later removed via `DeleteMember` → remaining members confirm the still-pending request." Any multisig that rotates/removes members while requests are outstanding (a normal, encouraged operational practice) is exposed. A member who anticipates their own removal, or colludes with a soon-to-be-removed member, can pre-confirm sensitive requests to bank a stale approval that will still count after removal, lowering the effective threshold by one (or more, if several removed members had confirmed).

### Recommendation
When executing `DeleteMember`, iterate over every pending request's `confirmations` set (not just those the removed member originated) and drop entries matching the removed member's identity. Alternatively, at `confirm()` execution time, before comparing `confirmations.len()` against `num_confirmations`, filter the stored confirmation set to only members still present in `self.members`, and only proceed to execute if the *live* count reaches the threshold.

### Proof of Concept
1. Multisig initialized with `num_confirmations = 3` and members `{A, B, C, D}` via `MultiSigContract::new`.
2. `A` calls `add_request_and_confirm(request)` for a `Transfer` — request now has 1 confirmation (`A`).
3. `B` calls `confirm(request_id)` — 2 confirmations (`A`, `B`); `2+1 < 3`, so it doesn't execute yet.
4. Separately, members approve a `DeleteMember { member: A }` request and it executes via `execute_request` → `delete_member(promise, A)`. This removes `A` from `self.members`, but the pending `Transfer` request (originated by `A` via step 2) — wait, it *was* originated by `A`, so it would actually be purged by the `request_ids` filter in this particular ordering.
   - To bypass that filter, let `B` originate the request instead: `B` calls `add_request_and_confirm`, then `A` calls `confirm(request_id)` (2 confirmations: `B`, `A`). Now the request's `r.member == B`, not `A`.
5. `A` is removed via `DeleteMember`. `delete_member` filters `self.requests` for `r.member == A` — none match (the request's originator is `B`), so the pending request and its confirmations set (`{B, A}`) survive untouched.
6. `C` (still a live member) calls `confirm(request_id)`. `confirmations.len() (2) + 1 == 3 == num_confirmations`, so `execute_request` runs the `Transfer`.
7. Result: the transfer executed with confirmations from only `B` and `C` as genuinely live members plus a stale confirmation from removed member `A` — i.e., only 2 live-member approvals authorized a transaction that required 3, breaking the multisig threshold guarantee. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
