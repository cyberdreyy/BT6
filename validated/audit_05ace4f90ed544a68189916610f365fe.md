### Title
Non-atomic `CreateAccount` + `InitializeNonceAccount` allows front-running to hijack nonce authority and drain funds - (File: `programs/system/src/system_instruction.rs`)

### Summary
`SystemInstruction::InitializeNonceAccount` sets the nonce authority of a system-program-owned, `Uninitialized` account without requiring any signature from the account's keypair or from the party who created it. If the `CreateAccount` step (which funds/allocates the account and requires the new account's private key to sign) and the `InitializeNonceAccount` step (which sets the authority and needs no such signature) are submitted as separate, non-atomic transactions, any unprivileged attacker can race in an `InitializeNonceAccount` instruction naming themselves as `nonce_authority` before the legitimate owner's initialize instruction lands.

### Finding Description
`initialize_nonce_account` only checks that the target account is `is_writable`, `Uninitialized`, and rent-exempt; it performs no signer check on the account or on any "creator" key before writing `State::Initialized(Data { authority: *nonce_authority, .. })`: [1](#0-0) 

The processor dispatch for `InitializeNonceAccount` likewise requires only a single instruction account (the nonce account) and does not check that it's a transaction signer: [2](#0-1) 

This mirrors the Velodrome `Bribe.setGauge` pattern exactly: a permissionless "set once" call (`gauge = _gauge` / `authority = _nonce_authority`) that is expected to be invoked atomically as part of a two-step initialization (`Bribe` constructor → `Gauge` constructor calling `setGauge`, vs. `CreateAccount` → `InitializeNonceAccount`), but which has no access control tying it to the original creator. If the two steps land in separate transactions, anyone can win the race and claim the privileged role.

Once an attacker becomes the `authority`, they gain more than griefing: `withdraw_nonce_account` allows a full-balance withdrawal that is gated purely on `check_signer(&data.authority)` — no blockhash/durable-nonce check is required for a full withdrawal: [3](#0-2) 

So the attacker can later drain all lamports deposited into the "hijacked" nonce account to an address of their choosing.

### Impact Explanation
This is a concrete unauthorized fund-mutation vector, not merely griefing: an attacker who wins the race becomes the nonce authority and can call `WithdrawNonceAccount` to sweep the account's full balance whenever convenient (e.g., after the victim deposits rent-exempt funds or additional lamports expecting to use it as a durable nonce account). The legitimate owner's subsequent `InitializeNonceAccount` call also fails (`InstructionError::InvalidAccountData` because state is already `Initialized`), permanently bricking the intended account for its original purpose — the same "temporary system breaking impact" cited as Medium severity in the source report, but here compounded by direct loss of funds.

### Likelihood Explanation
Exploitability depends entirely on client/wallet behavior: the standard `create_nonce_account` instruction builders bundle `CreateAccount`/`Allocate`/`Assign`/`Transfer` and `InitializeNonceAccount` into one transaction so they execute atomically, which is why this is not commonly observed in practice. However, nothing in the on-chain program enforces atomicity — any tooling, custom integration, or multi-step wallet flow that submits `CreateAccount` and `InitializeNonceAccount` as separate transactions (e.g., due to fee-payer/signature collection across steps, or a UI that funds an account first and initializes it later) is exposed to front-running by anyone monitoring the mempool/QUIC ingest for the intermediate, `Uninitialized`, system-owned account.

### Recommendation
Require the `nonce_authority` (or a dedicated "creator" key established atomically with account creation) to sign the `InitializeNonceAccount` instruction, or bind initialization to the account's own signature so that only the party who created/owns the account can perform the one-time initialization. Alternatively, document and enforce (at the client/tooling level, and ideally via a lint/check in transaction construction helpers) that `CreateAccount` and `InitializeNonceAccount` must always be packaged in the same transaction.

### Proof of Concept
1. Victim submits transaction A: `SystemInstruction::CreateAccount` funding/allocating `nonce_pubkey`, owned by the system program, `State::Uninitialized`.
2. Before victim's transaction B (`SystemInstruction::InitializeNonceAccount(victim_authority)`) lands, attacker observes `nonce_pubkey` on-chain/in-flight and submits `SystemInstruction::InitializeNonceAccount(attacker_pubkey)` targeting the same `nonce_pubkey` — no signature from `nonce_pubkey`'s keypair or the victim is required, per `initialize_nonce_account` in `programs/system/src/system_instruction.rs` (lines 163-211).
3. Attacker's transaction is processed first; `nonce_pubkey` state becomes `Initialized(Data { authority: attacker_pubkey, .. })`.
4. Victim's transaction B now fails with `InstructionError::InvalidAccountData` (state already `Initialized`).
5. If lamports are later added to `nonce_pubkey` (e.g., victim funds it further believing initialization will still occur, or the original `CreateAccount` funded it beyond minimum rent), attacker calls `SystemInstruction::WithdrawNonceAccount(full_balance)` signed with `attacker_pubkey`, satisfying the `check_signer(&data.authority)` path in `withdraw_nonce_account` (lines 125-136), draining the account to an address they control.

pub(crate) fn initialize_nonce_account(
    account: &mut BorrowedInstructionAccount,
    nonce_authority: &Pubkey,
    rent: &Rent,
    invoke_context: &InvokeContext,
) -> Result<(), InstructionError> {
    if !account.is_writable() {
        ic_msg!(
            invoke_context,
            "Initialize nonce account: Account {} must be writeable",
            account.get_key()
        );
        return Err(InstructionError::InvalidArgument);
    }

    match account.get_state::<Versions>()?.state() {
        State::Uninitialized => {
            let min_balance = rent.minimum_balance(account.get_data().len());
            if account.get_lamports() < min_balance {
                ic_msg!(
                    invoke_context,
                    "Initialize nonce account: insufficient lamports {}, need {}",
                    account.get_lamports(),
                    min_balance
                );
                return Err(InstructionError::InsufficientFunds);
            }
            let durable_nonce =
                DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash);
            let data = nonce::state::Data::new(
                *nonce_authority,
                durable_nonce,
                invoke_context
                    .environment_config
                    .blockhash_lamports_per_signature,
            );
            let state = State::Initialized(data);
            account.set_state(&Versions::new(state))
        }
        State::Initialized(_) => {
            ic_msg!(
                invoke_context,
                "Initialize nonce account: Account {} state is invalid",
                account.get_key()
            );
            Err(InstructionError::InvalidAccountData)
        }
    }
}
