### Title
Node-keyed outgoing rate limiter in `handleWebAPIOutgoingMessage` allows a single workflow to exhaust a DON node's shared HTTP-egress quota and starve other tenants' requests through that node - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.handleWebAPIOutgoingMessage` gates all outbound HTTP capability traffic (webapi target / compute / workflow-syncer actions) with `h.nodeRateLimiter.Allow(nodeAddr)`, where the rate-limit key is the DON member's node address, not the requesting workflow or end user. Because every workflow assigned to the DON is fanned out to every DON member and shares that same per-node token bucket, an authorized sender of a single workflow can flood that workflow's actions to exhaust one node's quota and cause unrelated workflows' legitimate requests routed through the same node to be rejected with "rate limit exceeded for node".

### Finding Description
`HandleLegacyUserMessage` forwards every accepted webapi trigger message to **all** DON members without any incoming rate limiting (the code explicitly notes `// TODO: apply allowlist and rate-limiting here`): [1](#0-0) 

Each DON node that receives the trigger runs it through its own trigger handler (`core/capabilities/webapi/trigger/trigger.go`), which enforces a per-workflow, per-sender `rateLimiter.Allow(body.Sender)` check before firing the workflow: [2](#0-1) 

That per-workflow limiter only bounds how fast *one* sender can invoke *one* workflow's trigger — it does not protect the downstream, shared resource. When the triggered workflow performs a target/compute/http action, the node sends the outgoing request back through the gateway, and `handleWebAPIOutgoingMessage` checks the node-scoped limiter before actually issuing the HTTP call: [3](#0-2) 

The limiter is a single `*ratelimit.RateLimiter` instance per DON, created once in `NewHandler` and keyed only by `nodeAddr`: [4](#0-3) [5](#0-4) 

Because `nodeAddr` identifies a DON member, not the workflow/user that originated the request, this bucket is shared by every workflow that happens to be assigned to that DON and routed through that member. The underlying `ratelimit.RateLimiter.Allow(sender)` semantics (analogous to the sibling implementation) create one token bucket per key string and share it across all callers using that key: [6](#0-5) 

Production defaults configure this per-node bucket at 100 RPS / 100 burst (vs. 500 RPS / 100 burst global), confirming the per-node bucket, not the global one, is the binding constraint in normal operation: [7](#0-6) 

An attacker who is merely an authorized sender of one registered workflow (an "external-initiator credential holder" persona, not a DON/OCR peer) can repeatedly trigger that workflow's actions up to its own per-sender allowance, and each resulting outgoing HTTP action call decrements the shared per-node bucket for every DON member. Once exhausted, `handleWebAPIOutgoingMessage` returns `"rate limit exceeded for node %s"` for target/compute/sync requests belonging to any other workflow that is also routed through that same node — a form of cross-tenant denial of service that requires no DON-level trust, no operator access, and no exploitation of the trigger-level allowlist.

### Impact Explanation
This is a service-availability (Denial-of-Service) issue: a low-privilege, single-workflow-scoped attacker can degrade or block legitimate outgoing HTTP capability requests (target/compute/workflow-sync) belonging to *other* workflows/users that share a DON member, purely through normal, authorized use of their own trigger permission. It does not lead to fund loss, key disclosure, or authentication bypass, but it does allow one unprivileged tenant to deny service to unrelated tenants sharing DON infrastructure, which maps to a resource-exhaustion / availability-degradation impact class.

### Likelihood Explanation
- Requires only that the attacker be an authorized sender for one workflow registered on the shared DON (a normal, low-trust credential, not DON-node trust).
- The trigger fan-out (`HandleLegacyUserMessage`) has no incoming user rate limiting of its own, and the per-workflow trigger rate limiter (`trigger.rateLimiter.Allow`) is independent from, and does not account for, the shared per-node outgoing bucket.
- The attack is deterministic and repeatable: as long as the attacker keeps their own per-sender/per-workflow trigger rate within its own limiter's allowance while the workflow issues multiple outgoing HTTP actions per execution, the shared node bucket depletes predictably given fixed configured RPS/Burst values.

### Recommendation
Scope the outgoing rate limiter in `handleWebAPIOutgoingMessage` (and the equivalent v2 `perNodeRateLimiters`) by a composite key that includes the originating workflow ID (or DON-node + workflow-ID pair) in addition to, or instead of, bare `nodeAddr`, so that one workflow cannot consume another workflow's fair share of a node's outbound HTTP quota. Alternatively, add a dedicated per-workflow outgoing quota (mirroring the `OutgoingRateLimiter`/`DefaultWorkflowRPS` pattern already used in `core/capabilities/webapi/outgoing_connector_handler.go`) enforced at the gateway before the shared per-node check.

### Proof of Concept
Go table/integration test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build a `handler` with `NodeRateLimiter` configured with a small `PerSenderBurst`/`PerSenderRPS` (e.g., burst=2, rps=1), and a DON with a single node member (as in `setupHandler`).
2. Register/simulate two distinct "workflows" (workflow A controlled by the attacker, workflow B representing a legitimate unrelated user), both routed to the same node address.
3. Simulate workflow A sending `MethodComputeAction`/`MethodWebAPITarget` node messages (via `HandleNodeMessage` → `handleWebAPIOutgoingMessage`) rapidly enough to exhaust the per-node burst (2 calls should succeed, drain the bucket).
4. Immediately send a `HandleNodeMessage` for workflow B's outgoing action through the same `nodeAddr`.
5. Assert workflow B's call returns the error `"rate limit exceeded for node %s"` even though workflow B made no prior requests, demonstrating that an unrelated workflow was starved solely because it shares the node-keyed bucket with workflow A's traffic.
6. Repeat with distinct `nodeAddr` values to show that requests routed through a different DON member are unaffected, confirming the key granularity is per-node rather than per-workflow/user.

func (h *handler) handleWebAPIOutgoingMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.lggr.Debugw("handling webAPI outgoing message", "messageId", msg.Body.MessageId, "nodeAddr", nodeAddr)
	if !h.nodeRateLimiter.Allow(nodeAddr) {
		return fmt.Errorf("rate limit exceeded for node %s", nodeAddr)
	}

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```
