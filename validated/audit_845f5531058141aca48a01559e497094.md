### Title
Bridge outgoing token (credential secret) exposed to view-role users via `Bridge`/`Bridges` read query - ([File: core/web/resolver/query.go], [File: core/web/resolver/bridge.go])

### Summary
The `Bridge` and `Bridges` query resolvers only require `authenticateUser` (any authenticated session, minimum 'view' role) rather than a higher privilege check, yet the returned `BridgeResolver` exposes `OutgoingToken()`, which returns the raw bridge outgoing token credential used by the node to authenticate to the external adapter.

### Finding Description
`Chain`'s sibling read resolvers `Bridge` and `Bridges` in `core/web/resolver/query.go` gate access with `authenticateUser`, which only checks that a session exists ("presence of user inherently provides 'view' access") and does not check role level at all: [1](#0-0) [2](#0-1) 

Both resolvers return a `*BridgePayloadResolver`/`*BridgesPayloadResolver` wrapping `bridges.BridgeType`, whose GraphQL-exposed `OutgoingToken()` method returns the bridge's outgoing token verbatim, unredacted: [3](#0-2) 

This differs from `IncomingToken`, which is intentionally only exposed once, in the `CreateBridgeSuccessResolver` mutation payload (a one-time reveal), and is not queryable afterward: [4](#0-3) 

Since `outgoingToken` is a plain field on the `Bridge` GraphQL type returned by the `bridge(id)` and `bridges` root queries, any authenticated user — including one holding only the `view` role — can select it directly, e.g. `{ bridge(id: "foo") { outgoingToken } }` or `{ bridges { results { outgoingToken } } }`. No further role escalation check (`authenticateUserCanRun`/`authenticateUserCanEdit`/`authenticateUserIsAdmin`) is applied on this path.

By contrast, all other secret-bearing subsystems checked (CSA, Solana, Cosmos, StarkNet, Stellar, Sui, TON, Tron key resolvers, `ETHKeys`, `P2PKeys`, `OCRKeyBundles`, `OCR2KeyBundles`) only expose public key material/addresses/IDs, not private key bytes, based on the resolver methods present. [5](#0-4) 

### Impact Explanation
The bridge outgoing token is credential material the node uses to authenticate outbound calls to an external adapter/bridge; disclosure to a low-privilege 'view' user lets that user impersonate the node to the external adapter or replay/misuse the credential outside the node's control. This maps to a credential/secret disclosure impact, though it is a bridge-adapter credential rather than a blockchain private key, so it is a narrower instance of the "server credential/key theft" class than full private-key export.

### Likelihood Explanation
Exploitation only requires an authenticated session with the minimum 'view' role (the lowest privilege tier defined in `sessions.UserRole`), and a single GraphQL query selecting `outgoingToken` on `Bridge`/`Bridges`. No additional preconditions, timing, or race conditions are needed, and the query is trivially repeatable.

### Recommendation
Gate `Bridge`/`Bridges` (or at minimum the `outgoingToken` field) behind a higher role such as `authenticateUserCanEdit`/`authenticateUserIsAdmin`, or omit/redact `OutgoingToken()` from the `BridgeResolver` entirely for read queries, exposing it only at creation/rotation time similar to `IncomingToken`.

### Proof of Concept
Go handler-level integration test plan (in `core/web/resolver` test style, using the existing `gqlTestFramework`):
1. Seed a bridge via mocked `BridgeORM().FindBridge` returning a `bridges.BridgeType{OutgoingToken: "super-secret-token"}`.
2. Execute query as a session with `sessions.UserRoleView` (matching `unauthorizedTestCase`/role-based test helpers already used in this package, e.g. `api_token_test.go`).
3. Query: `{ bridge(id: "test-bridge") { name outgoingToken } }`.
4. Assert the GraphQL response returns `"outgoingToken": "super-secret-token"` for a view-role session — this should fail (be blocked) but currently succeeds, proving the vulnerability.
5. Add a schema-level assertion test enumerating all fields reachable transitively from `Query` and asserting no field named like `*token*`, `*secret*`, or key-bytes fields is reachable without an elevated role check, to prevent regressions.

func (r *Resolver) Bridge(ctx context.Context, args struct{ ID graphql.ID }) (*BridgePayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	name, err := bridges.ParseBridgeName(string(args.ID))
	if err != nil {
		return nil, err
	}

	bridge, err := r.App.BridgeORM().FindBridge(ctx, name)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return NewBridgePayload(bridge, err), nil
		}

		return nil, err
	}

	return NewBridgePayload(bridge, nil), nil
}
