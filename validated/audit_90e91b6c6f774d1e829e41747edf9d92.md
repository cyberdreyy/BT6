### Title
Cache key text can force protected-volume naming on an unprotected ref, enabling cache volume collision - ([File: executors/docker/volume.go], [File: executors/docker/internal/volumes/manager.go])

### Summary
`createVolumesManager` in `executors/docker/volume.go` sets `ManagerConfig.Protected` to `true` if the ref is protected **or** if any `Build.Cache[].Key` ends in the literal suffix `-protected` (and not `-non_protected`). Since `Cache[].Key` is fully attacker-controlled `.gitlab-ci.yml` text (it does not have to be derived from the real `CI_COMMIT_REF_PROTECTED` variable), an unprivileged pipeline author on a non-protected branch can hardcode a cache key ending in `-protected` and force `manager.withProtected()` to append the `-protected` suffix to the resulting Docker volume name.

### Finding Description
`createVolumesManager` (executors/docker/volume.go:14-28) computes:
```go
protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
    return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
})
...
Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
``` [1](#0-0) 

`e.Build.Cache` is populated from the job's `cache:` configuration in `.gitlab-ci.yml`, which any contributor able to open a merge request / push to a non-protected branch fully controls, including the literal string value of `key`. Nothing forces `key` to be derived from the real, GitLab-computed `CI_COMMIT_REF_PROTECTED` predefined variable — a user can simply write `key: "mycache-protected"` regardless of actual branch protection.

Downstream, `manager.createCacheVolume` (executors/docker/internal/volumes/manager.go:194-251) builds the reusable volume name as:
```go
name := m.config.UniqueName // per-project unique name, not per-ref
volumeName := m.withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))
``` [2](#0-1) 

and:
```go
func (m *manager) withProtected(s string) string {
    if !m.config.Protected {
        return s
    }
    return s + protectedSuffix
}
``` [3](#0-2) 

`UniqueName` (`e.Build.ProjectRealUniqueName()`) is scoped per **project**, not per **ref**. Because of this, two jobs in the same project — one on a genuinely protected ref, and one on a non-protected ref where the attacker fabricates a `-protected`-suffixed cache key with the same `cache:paths` destination — produce the **identical** Docker volume name (`UniqueName-cache-hash(destination)-protected`) with identical `hashedDestination`. Docker's `VolumeCreate` is idempotent by name, so the second job to run simply reuses (mounts) the already-existing volume rather than creating a new one. No existing check (allowed images, path validation, auth checks) inspects whether the caller is actually entitled to a protected-classified volume — the classification is trusted from job-controlled text.

### Impact Explanation
An unprivileged contributor able to run a pipeline on a non-protected branch/MR (default GitLab permission for most contributors) can, within the same project, cause their job's cache volume to reuse the same named Docker volume that a protected-branch job legitimately uses. This lets the attacker read the contents of a cache volume built by protected-branch pipelines (potential secrets, build artifacts, dependency caches) or write/poison it so that a subsequent protected-branch pipeline consumes attacker-controlled cache content — a supply-chain/cache-poisoning vector against protected branches, which is exactly the kind of privilege boundary GitLab's ref-protection feature is meant to preserve. Scope is per-runner-host with persistent docker volume caching enabled (`DisableCache=false`, `CacheDir` unset) and both pipelines scheduled onto the same runner/host.

### Likelihood Explanation
Preconditions are realistic and require no special GitLab or runner administrative access:
1. Runner uses the docker executor with volume-based (non host-path) cache, which is the common default.
2. Attacker has push/MR access sufficient to modify `.gitlab-ci.yml` on a non-protected branch (typical contributor permission).
3. Attacker knows or guesses the `cache:paths` destination used by the protected branch's job (often visible in the shared `.gitlab-ci.yml` since both protected and non-protected pipelines usually use the same CI file).
4. Both jobs land on the same runner instance sharing the docker volume storage — common for shared, non-autoscaled docker runners.

This is fully repeatable and does not depend on timing races beyond normal job scheduling; the underlying naming logic is deterministic.

### Recommendation
Do not derive `ManagerConfig.Protected` (and hence Docker volume naming) from arbitrary user-supplied `cache:key` text. Only use `e.Build.IsProtected()` (the actual, GitLab-computed ref protection state) to decide the `-protected` suffix/classification. If the "-protected"/"-non_protected" cache-key convention needs to be supported for a legitimate reason, it must be combined with a namespace that can't collide with real protected volumes (e.g., incorporate a value not spoofable by users, or namespace by ref instead of by project), and never allow a job-supplied string to escalate the trust classification of a shared, project-scoped volume name.

### Proof of Concept
Go unit test extending `manager_test.go` style coverage:
```go
func Test_CacheVolumeProtected_KeySuffixCollision(t *testing.T) {
    destination := "/cache/path"

    // Simulate a legitimate protected-ref job.
    protectedMgr := newTestManager(ManagerConfig{
        UniqueName: "runner-x-project-1-concurrent-0",
        Protected:  true, // IsProtected() == true
    })
    protectedName, err := protectedMgr.createCacheVolume(ctx, destination, true)
    require.NoError(t, err)

    // Simulate an unprivileged job on a NON-protected ref that fabricates
    // cache:key: "foo-protected" in .gitlab-ci.yml.
    spoofedMgr := newTestManager(ManagerConfig{
        UniqueName: "runner-x-project-1-concurrent-0",
        Protected:  hasProtectedCacheKeySuffix([]spec.Cache{{Key: "foo-protected"}}), // true, ref itself is NOT protected
    })
    spoofedName, err := spoofedMgr.createCacheVolume(ctx, destination, true)
    require.NoError(t, err)

    // BUG: names/labels collide even though only one job actually ran on a protected ref.
    assert.Equal(t, protectedName, spoofedName)
}
```
Expected assertion: `protectedName == spoofedName`, proving that a job on an unprotected ref can compute and mount the exact same Docker volume name (and `protected=true` label) as a genuinely protected-ref job, demonstrating the cache-namespace collision.
