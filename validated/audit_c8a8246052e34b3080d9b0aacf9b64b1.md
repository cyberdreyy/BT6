### Title
Builder-controlled `fee_recipient` in `ExecutionPayloadBid` is never checked against the proposer's committed preferences at the state-transition layer, allowing a builder payment to be redirected or burned - ([File: specs/gloas/beacon-chain.md])

### Summary
The "Zero Token" bug class (constructor accepts an unchecked address parameter, so a zero/attacker address can be used and funds sent there are permanently lost) maps onto `process_execution_payload_bid` in Gloas. The `ExecutionPayloadBid.fee_recipient` field, which determines who actually receives the builder's payment, is fully attacker(builder)-controlled and is *never* validated by the state-transition function against the proposer's declared `ProposerPreferences.fee_recipient`. The binding between a slot's proposer and the address that should receive the builder's payment exists only as a soft, non-authoritative check in the gossip layer (an `IGNORE`, not even a `REJECT`), and `ProposerPreferences` is not referenced anywhere in `specs/gloas/beacon-chain.md` at all.

### Finding Description
`process_execution_payload_bid` [1](#0-0)  records a pending payment using `bid.fee_recipient` verbatim:
```
pending_payment = BuilderPendingPayment(
    weight=Gwei(0),
    withdrawal=BuilderPendingWithdrawal(
        fee_recipient=bid.fee_recipient,
        amount=amount,
        builder_index=builder_index,
    ),
    proposer_index=get_beacon_proposer_index(state),
)
``` [2](#0-1) 

None of the assertions in this function check `bid.fee_recipient` against anything tied to the actual block proposer or their declared preference — they only check builder activity/version/funds/signature, slot/parent/hash/randao correctness [3](#0-2) . `ProposerPreferences`/`SignedProposerPreferences` do not appear anywhere in `specs/gloas/beacon-chain.md` (confirmed via search), meaning the state-transition function has no mechanism at all to enforce that the payment goes to the address the proposer actually asked for.

The intended binding is documented only as a builder-construction convention: "Set `bid.fee_recipient` to be an execution address to receive the payment. The proposer's preferred fee recipient is obtained from the `SignedProposerPreferences`..." [4](#0-3) . Validators are told to accept only bids matching their own `process_execution_payload_bid` verification conditions, but the fee-recipient match itself is not one of those verification conditions [5](#0-4) .

The only place `bid.fee_recipient == proposer_preferences.fee_recipient` is actually checked is in the p2p gossip validation rules, and even there it results in `GossipIgnore` (not `GossipReject`), i.e. it does not affect peer scoring/rejection semantics, only local relay behavior:
```
# [IGNORE] The bid's fee recipient matches the proposer's preference
if bid.fee_recipient != proposer_preferences.fee_recipient:
    raise GossipIgnore("bid's fee recipient does not match the proposer's preference")
``` [6](#0-5) 

Additionally, the spec explicitly permits bypassing gossip entirely: "The block proposer MAY obtain these signed messages by other off-protocol means" [7](#0-6) , so any bid a proposer receives (e.g., from a relay) that carries a mismatched `fee_recipient` is fully valid at the protocol level and will be accepted by every spec-following node.

The equality this breaks: the amount `bid.value` that the builder pays should reach the address the proposer for that slot actually committed to (`ProposerPreferences.fee_recipient`), but the protocol enforces no such equality — the builder alone determines the destination address of a payment that is supposed to belong to the proposer.

### Impact Explanation
This is the direct analog of the "Zero Token" report: because there is no address check tying `bid.fee_recipient` to any accountable party, a builder can set it to the zero address (or any other address of its choosing, including its own), causing the value intended for the proposer to be effectively destroyed or misdirected. This matches the defined High/Critical impact categories: "a builder payment or withdrawal misdirected, doubled or escaped" and, when the target is the zero address, "Gwei created, destroyed or paid to a non-owner." Every spec-following node accepts the resulting block identically, so there is no consensus split, but the economic invariant that the builder's payment reaches the proposer is broken at the protocol level rather than merely at a client/relay policy level.

### Likelihood Explanation
The likelihood depends on whether the block proposer independently re-validates `bid.fee_recipient` before including it (most reference/relay implementations following gossip rules would), but the specification itself provides no protocol-level guarantee, and explicitly allows off-protocol bid delivery. Any deployment that relies on the p2p `IGNORE` rule alone, or that accepts bids from relays/out-of-band channels without redoing that specific check, is exposed. Because the check is missing from the actual state-transition function, this is a specification gap rather than a client implementation detail, and cannot be relied upon to be caught by consensus rules.

### Recommendation
Add an explicit state-transition-level (or at minimum a normative validity condition referenced by `process_execution_payload_bid`) check binding `bid.fee_recipient` to the proposer's committed preference for that slot (e.g., by including a verified `ProposerPreferences` commitment as part of the block/bid processing, or by requiring the block body to carry a signed proposer preference that `process_execution_payload_bid` cross-checks against `bid.fee_recipient`). At minimum, promote the p2p-layer fee-recipient check from `GossipIgnore` to a `GossipReject`-equivalent binding enforced at the consensus layer so that no valid block can carry a bid whose payment destination was not authorized by the proposer.

### Proof of Concept
1. A builder (or a proposer's chosen relay) crafts a `SignedExecutionPayloadBid` with `bid.fee_recipient = ExecutionAddress(b"\x00" * 20)` (zero address) or an address the builder itself controls, while `bid.value = X > 0`.
2. This bid is delivered to the proposer via an off-protocol channel (explicitly permitted by `specs/gloas/validator.md`), bypassing the gossip `IGNORE` check in `specs/gloas/p2p-interface.md`.
3. The proposer includes `signed_bid` in `BeaconBlockBody.signed_execution_payload_bid` and produces the block.
4. `process_execution_payload_bid` executes all its assertions successfully (signature, builder active, funds available, slot/hash/randao correctness) — none of which reference `bid.fee_recipient` or any proposer commitment — and records `BuilderPendingWithdrawal(fee_recipient=bid.fee_recipient, amount=X, builder_index=builder_index)` [2](#0-1) .
5. Every spec-following node accepts this block as valid; the amount `X` is subsequently withdrawn to the attacker-chosen/zero `fee_recipient` instead of the proposer's actual declared address, with no protocol-level check ever having verified this destination.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))

    # Record the pending payment if there is some payment
    if amount > 0:
        pending_payment = BuilderPendingPayment(
            weight=Gwei(0),
            withdrawal=BuilderPendingWithdrawal(
                fee_recipient=bid.fee_recipient,
                amount=amount,
                builder_index=builder_index,
            ),
            proposer_index=get_beacon_proposer_index(state),
        )
        state.builder_pending_payments[SLOTS_PER_EPOCH + bid.slot % SLOTS_PER_EPOCH] = (
            pending_payment
        )

    # Cache the signed execution payload bid
    state.latest_execution_payload_bid = bid
