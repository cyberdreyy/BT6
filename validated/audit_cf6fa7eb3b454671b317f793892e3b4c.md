### Title
Unprotected overwrite of `savedCallbacks` keyed by client-supplied `MessageId` causes cross-user response confusion in the Gateway capabilities handler - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The Sherlock report's root cause is a state-tracking structure (`Checkpoints`) that is written to more than once for the same key (block number) without a guard, so a later read binds to the *wrong* prior write and the caller reads/receives a value that was not intended for it. The Gateway's `handler` (used for the WebAPI/HTTP legacy capability path) has the same structural flaw: it uses a single map, `savedCallbacks`, keyed by the externally-supplied `MessageId`, with no protection against the same key being written twice before it is consumed. When two different incoming user requests race with the same `MessageId`, the second `HandleLegacyUserMessage` call silently overwrites the first entry, and the eventual node response by that `MessageId` is delivered only to whichever callback happens to be the most recently stored one.

### Finding Description
`HandleLegacyUserMessage` unconditionally stores the caller's callback in a shared map keyed only by `msg.Body.MessageId`, with no check for an existing/unconsumed entry (i.e., no "checkpointProtection"-style guard): [1](#0-0) 

The response path, `handleWebAPITriggerMessage`, looks up and deletes-and-uses whatever is currently under that `MessageId` when the DON node responds, then routes the raw node response back to that one stored callback: [2](#0-1) 

Because the map write in `HandleLegacyUserMessage` (line 412) has no uniqueness/collision check analogous to the missing `checkpointProtection()` guard in `StakingModule._stake()`, if two legitimate (or malicious) requests arrive with the same `MessageId` before the first is resolved, the second overwrites the first's `*savedCallback` in the map. Once a node eventually responds with that `MessageId`, `handleWebAPITriggerMessage` finds only the second caller's callback and delivers the (first) node response to it — the first caller's request is silently dropped/orphaned, and if a later node response arrives for the same `MessageId` (whether from a stray retry, duplicate node broadcast, or an attacker deliberately colliding IDs), it can be delivered to a completely different requester's callback. This mirrors the report's core defect: an identifier/window that is assumed unique per write is not actually protected against being clobbered by a second write in the same window, and a downstream reader/consumer receives state that was not produced for it.

`MessageId` in `api.MessageBody` is part of the wire message and is effectively attacker/caller controlled at the point `HandleLegacyUserMessage` is invoked (it comes straight from the incoming, unauthenticated-relative-to-content JSON message), so an unprivileged client can deliberately choose or predict a `MessageId` to collide with another in-flight request.

### Impact Explanation
A colliding `MessageId` allows one user's HTTP trigger/legacy WebAPI response to be delivered to a different, unrelated caller's callback (cross-user response confusion), and causes the original caller's request to hang until callback pruning evicts it (`pruneCallbacks`, `CallbackMaxAgeSec`/`MaxSavedCallbacks`) — a denial of service for that specific request in addition to the confidentiality/integrity concern of one user potentially receiving a response payload that belongs to another user's request.

### Likelihood Explanation
Likelihood depends on how `MessageId` values are generated/validated upstream of `HandleLegacyUserMessage`; if IDs are not enforced to be cryptographically random/unique per caller (e.g., reused, predictable, or attacker-chosen), a malicious client can trivially trigger the race by submitting two requests with the same `MessageId` back-to-back. This mirrors "multiple writes in the same window" in the analog report and does not require any elevated privilege — only the ability to send WebAPI trigger requests through the gateway.

### Recommendation
Add a guard in `HandleLegacyUserMessage` analogous to `checkpointProtection()`: reject (or generate server-side, ignoring any caller-supplied value) requests whose `MessageId` already has an unresolved entry in `savedCallbacks`, and generate `MessageId` values server-side (e.g., UUID) rather than trusting caller-supplied identifiers, so collisions between concurrent, distinct requests are structurally impossible.

### Proof of Concept
1. Attacker A sends a WebAPI trigger user message with `MessageId = "X"`; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` (handler.go:412) and forwards the request to DON nodes.
2. Before a node responds, Attacker A (or a colluding party) sends a second WebAPI trigger message reusing `MessageId = "X"`; `HandleLegacyUserMessage` overwrites `savedCallbacks["X"] = callbackB` (handler.go:412), silently discarding the first entry.
3. A DON node responds to the *first* request with `MessageId = "X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and sends the first request's node response to `callbackB` (handler.go:150-159).
4. Result: the response intended for the first requester is delivered to the second requester's connection, and the first requester never receives a response (until it eventually times out via `pruneCallbacks`).

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
