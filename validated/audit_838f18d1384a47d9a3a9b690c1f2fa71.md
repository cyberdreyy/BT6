### Title
Loss-adjusted withdraw receipts are paid at par (or freeze claims) when the user re-requests in a later epoch — (`File: contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The kernel bug is an offload applied to both links when it must only apply to the primary one. The analog is the haircut on loss-adjusted withdraw receipts: `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` so receipts of the loss epoch are paid at a reduced price, but `_claimLossAdjustedWithdrawRequest` only inspects `lastWithdrawRequest[_user]`. When a user holds an unclaimed loss-adjusted receipt from epoch N and files a second `requestWithdraw` in epoch N+1, `lastWithdrawRequest` is overwritten to N+1, the epoch-N haircut is never applied, and the aggregate `withdrawsRequests[_user]` is settled at par through `_claimFundedWithdrawRequest`.

### Finding Description
In `collectWithdrawFunds`, a partial borrower funding writes `lossRecoveryPriceByEpoch[epochNumber]` and zeroes `pendingWithdraws`, so the strategy only holds `pendingToFund` for that epoch's receipts (`IdleCreditVault.sol:411-430`).

The claim path (`claimWithdrawRequest`, `IdleCreditVault.sol:301-314`) runs:

1. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:789-801`). It only ever checks the *latest* request epoch; per-epoch basis lives in `withdrawsRequestsByEpoch[_user][epoch]` but is never iterated.
2. `_claimFundedWithdrawRequest` then pays the whole aggregate `withdrawsRequests[_user]` — which still includes the never-haircutted epoch-N basis — at par, burning `normalAmount` and calling `_transferFundedClaim` (`IdleCreditVault.sol:319-349`).

`requestWithdraw` is allowed while a prior receipt is open (the code comment at `IdleCreditVault.sol:323-324` explicitly documents re-requesting), and each request overwrites `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:282`). The post-default guard that forces claiming open receipts first (`testPostDefaultWithdrawRequiresClaimingOpenPriorReceipt`) only applies after default finalization, not after a `stopEpochWithDuration` loss.

Broken invariant: loss waterfall / "one receipt one payout". The haircut must be applied to the loss-epoch receipt (the "primary link"); instead the par-price path is applied to both epochs' aggregated basis.

### Impact Explanation
Two outcomes depending on strategy balance:

- **Theft**: if the strategy holds enough funded underlying (e.g., other users' later-epoch funded receipts collected via `collectWithdrawFunds`), the attacker claims their epoch-N receipt at par plus epoch-N+1 at par, draining funds belonging to other claimants. Quantified gain = `claimBasis_N * (1 - lossRecoveryPriceByEpoch[N])`.
- **Permanent freezing**: if the strategy only holds `pendingToFund_N + fullFunding_{N+1}`, the par transfer underflows `underlyingToken.balanceOf` and reverts; the `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve` (`IdleCreditVault.sol:897-907`), not the haircut shortfall. The epoch-N loss claim is unreachable forever (its `lossRecoveryPriceByEpoch` entry is keyed to an epoch no longer referenced by `lastWithdrawRequest`), so affected users' claims are permanently frozen.

### Likelihood Explanation
Requirements: a `stopEpochWithDuration`/`stopEpoch` partial funding (borrower underpays `pendingWithdraws` — manager is honest but borrower funding can legitimately fall short, producing `lossRecoveryPriceByEpoch`), and an affected user who does not claim during the buffer and files a new `requestWithdraw` in a later epoch. Both are normal unprivileged user flows; no privileged misbehavior needed. The trigger is realistic whenever a haircut epoch occurs and users batch requests across epochs. Uncertainty: the PoC must confirm `requestWithdraw` in `IdleCDOEpochVariant` does not revert on an existing open request outside the post-default path — the in-code comment and `_claimFundedWithdrawRequest`'s NOTE indicate re-requesting is supported.

### Recommendation
- Iterate all epochs with nonzero `withdrawsRequestsByEpoch[_user][*]` in `claimWithdrawRequest`, or track a per-user list/set of open request epochs, so every loss-adjusted epoch clears through its `lossRecoveryPriceByEpoch` independently of `lastWithdrawRequest`.
- Alternatively, revert `requestWithdraw` when `withdrawsRequestsByEpoch[_user][epoch]` exists for an epoch with a nonzero `lossRecoveryPriceByEpoch` until it is claimed, mirroring the post-default open-receipt guard.
- Ensure `lastWithdrawRequest` being reset in `_clearWithdrawClaimForEpoch` cannot strand an older loss-epoch basis inside `withdrawsRequests[_user]`.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
