### Title
External Initiator credential holder bypasses "EIs not allowed" check in `PipelineRunsController.Create` and triggers `RunJobV2` on any job ID - ([File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` unconditionally injects a fake `&clsessions.User{Role: UserRoleRun}` into the same `SessionUserKey` context slot that real authenticated users use. `PipelineRunsController.Create` attempts to reject EI-authenticated requests with `_, isUser := auth.GetAuthenticatedUser(c)`, but since EI requests also populate `SessionUserKey`, this check always evaluates `isUser == true` for EIs, defeating its own comment ("only users are allowed to run jobs using int IDs - EIs not allowed") and allowing an EI credential holder to call `RunJobV2` for any numeric job ID.

### Finding Description
`AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) authenticates the EI access-key/secret headers, then does:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [1](#0-0) 

`RequiresRunRole` (`core/web/auth/auth.go:202-217`) only checks that the `SessionUserKey`-derived role is not `UserRoleView`, so the synthetic `UserRoleRun` user passes trivially. [2](#0-1) 

Inside `PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go:89-128`), the code explicitly intends to block EIs from running jobs by numeric ID:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [3](#0-2) 

But `auth.GetAuthenticatedUser` (`core/web/auth/auth.go:178-187`) simply reads the `SessionUserKey` context value — the same key that `AuthenticateExternalInitiator` populates with a fake user. There is no check of `GetAuthenticatedExternalInitiator` to exclude EI-authenticated requests. Consequently, `isUser` is `true` for both real session/token users and EI-authenticated callers, and the "EIs not allowed" guard is a no-op.

`RunJobV2` (`core/services/chainlink/application.go:1126-1189`) performs no check that the job has any `ExternalInitiator` binding — it only does `app.jobORM.FindJob(ctx, jobID)` and executes the pipeline. It runs any job type (OCR, VRF, direct-request, keeper, etc.) regardless of whether it was ever intended to be externally triggerable. [4](#0-3) 

Attack flow: an attacker holding valid EI access-key/secret (a low-privilege credential intended only for jobs explicitly bound to that EI via webhook specs) sends `POST /v2/jobs/<numeric-job-id>/runs` with the EI headers. Middleware chain resolves to `AuthenticateExternalInitiator` → `RequiresRunRole` (passes due to fake `UserRoleRun`) → `PipelineRunsController.Create`, where `isUser` is erroneously `true`, `RunJobV2` executes for any guessable/enumerable numeric job ID, including jobs the EI was never bound to.

### Impact Explanation
This is an authorization/isolation bypass: an EI credential (a narrow-scope, low-privilege credential meant only to trigger jobs it's explicitly bound to) can trigger pipeline runs of arbitrary jobs on the node, including non-webhook jobs (OCR, VRF, direct-request, etc.) that were never configured for external triggering. Depending on job task graphs, this can cause unauthorized job execution, resource exhaustion, unintended on-chain transaction submission (fund movement) for jobs with ETH/transaction tasks, or disclosure of pipeline execution results/data the attacker shouldn't see. This matches the "unauthorized job run" / "role or authorization bypass" bounty class.

### Likelihood Explanation
Precondition: attacker must already possess valid EI access-key/secret for *any* external initiator on the node (a credential of a much narrower intended scope than full user/API-token access). Given that credential, the exploit requires only a single crafted HTTP POST with a guessed/enumerated numeric job ID — no additional privilege escalation, timing, or race condition needed. It is deterministic and repeatable for any job ID on the node.

### Recommendation
In `PipelineRunsController.Create`, distinguish EI-authenticated requests from real user sessions by checking `auth.GetAuthenticatedExternalInitiator(c)` is absent (or by not setting `SessionUserKey` at all in `AuthenticateExternalInitiator`, and instead having `RequiresRunRole` explicitly recognize EI context via `SessionExternalInitiatorKey`). At minimum, `Create` should reject the request when `GetAuthenticatedExternalInitiator` returns `ok == true`, regardless of `isUser`.

### Proof of Concept
Go handler-level integration test plan:
1. Start a test `cltest.Application` and create a non-webhook job (e.g., a direct-request or simple pipeline job) with **zero** `ExternalInitiator` bindings via `app.AddJobV2`.
2. Create an `ExternalInitiator` record (`bridges.ORM`) unrelated to that job, and obtain its access key/secret.
3. Build an HTTP client that sets `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers (per `static.ExternalInitiatorAccessKeyHeader/SecretHeader`) instead of session/token auth.
4. `POST /v2/jobs/<jobID>/runs` with the EI headers.
5. Assert the response is `401 Unauthorized` (expected/fixed behavior) — currently the flawed code returns `200 OK` with a valid `pipelineRun` resource, proving `RunJobV2` executed for a job with no EI binding.
6. Additionally assert via `prc.App.JobORM()`/pipeline run count that a new `pipeline.Run` row was created for that job, confirming actual execution rather than a silent no-op.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
