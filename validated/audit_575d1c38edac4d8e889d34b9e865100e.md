### Title
Stale rejection weight is never retracted when a signer later accepts the same block, corrupting the miner's aggregated-weight tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` (node-side) tracks per-block approval/rejection weight in a single `BlockStatus` struct shared by both the `Accepted` and `Rejected` message handlers [1](#0-0) . The two handlers use different, uncoordinated guards to decide whether to add a signer's weight: the reject path gates on `responded_signers`, the accept path gates on `gathered_signatures`. A signer that legitimately re-evaluates a block from rejected to accepted — a state transition the signer protocol explicitly supports (`LocallyRejected --> LocallyAccepted : re-evaluated`, per `docs/signer-flows.md` section 2) — ends up with its weight counted in **both** `total_weight_rejected` and `total_weight_approved`, and the stale rejected weight is never removed.

### Finding Description
In `handle_block_response` (stackerdb_listener.rs), the `Rejected` branch only adds weight the first time a slot_id is inserted into `responded_signers`: [2](#0-1) 

The `Accepted` branch, however, checks a completely different set (`gathered_signatures`) before adding weight, ignoring whether that slot_id is already present in `responded_signers` from an earlier rejection: [3](#0-2) 

Sequence that breaks the invariant:
1. Signer S (weight `w`) sends `BlockResponse::Rejected` for block B. `responded_signers.insert(slot_S)` succeeds (first time) → `total_weight_rejected += w`.
2. S later re-evaluates (e.g., a conflicting sibling it had signed goes stale, or a chainstate re-check now passes — both are documented, legitimate paths in `stacks-signer/src/v0/signer.rs`'s pre-commit/re-proposal handling, see `handle_block_pre_commit` / `store_and_process_block_signature`) and sends `BlockResponse::Accepted` for the same block B.
3. In the accept handler, `gathered_signatures` does not yet contain `slot_S`, so the condition is true and `total_weight_approved += w` is executed unconditionally — with **no check or subtraction against `total_weight_rejected`**.

Result: S's weight `w` is now counted in both `total_weight_approved` and `total_weight_rejected` simultaneously, and remains permanently double-booked for the lifetime of that `BlockStatus` entry. Note that the signer-side database (`stacks-signer/src/signerdb.rs::add_block_rejection_signer_addr`) does contain the correct guard against the *opposite* direction (it refuses to record a rejection if a signature already exists for that signer/block [4](#0-3) ), confirming that the developers considered this an invariant to protect — but only enforced it in signerdb.rs, not in the node-side `stackerdb_listener.rs` aggregator that the mining coordinator actually consults.

This corrupts the equality the coordinator depends on in `signer_coordinator.rs::get_block_status`, which treats `total_weight_approved` and `total_weight_rejected` as two disjoint, mutually exclusive partitions of `total_weight`: [5](#0-4) 

### Impact Explanation
This is a break of the "aggregated-weight vs verified-accepts" equality explicitly called out as Critical/High in scope: the miner's decision of whether a block was rejected (`total_weight_rejected + weight_threshold > total_weight` → `NakamotoNodeError::SignersRejected`, aborting the proposal) is computed from a rejected-weight total that can contain **stale, retracted votes**. A signer who rejected for a transient reason (e.g. a fresh-conflict guard, per `docs/signer-flows.md` section 5) and later legitimately signed once the conflict went stale still counts against the 30%+ rejection threshold forever. If enough signers individually flip from an early, transient rejection to acceptance (each perfectly legitimate per the state machine), their stale rejected weight can push `total_weight_rejected` past the blocking-minority threshold even though the *current* signer set truly supports (and has signed) the block with ≥70% weight. This wedges block production: the miner gives up on and/or bans a block that in fact has legitimate supermajority signatures, a liveness break with no majority-of-signers or key-compromise requirement — only ordinary signer state transitions.

### Likelihood Explanation
No malicious collusion or majority is required. The trigger is a single signer transitioning `LocallyRejected → LocallyAccepted`, a transition the signer protocol explicitly documents and tests support (e.g. `stacks-signer/src/v0/tests.rs`'s sibling/re-proposal tests demonstrate blocks moving between rejected and accepted states as chain state evolves). Any signer whose earlier rejection reason becomes stale (timeout, conflict resolution, re-proposal) and who then signs will trigger this double counting during normal, honest operation — it does not require an adversarial signer, only ordinary network delay/reordering causing a reject message to arrive before a later accept for the same block hash.

### Recommendation
In `stackerdb_listener.rs`, make `total_weight_approved` and `total_weight_rejected` mutually exclusive per slot_id: before adding weight in the `Accepted` branch, check whether `slot_id` is already present due to a prior rejection and, if so, subtract that signer's weight from `total_weight_rejected` (or otherwise remove it from whatever set tracks rejecting signers) before adding it to `total_weight_approved` — mirroring the guard already implemented correctly in the opposite direction in `stacks-signer/src/signerdb.rs::add_block_rejection_signer_addr`. Concretely, track rejecting signer slot_ids in their own set (distinct from the shared `responded_signers`) so the accept handler can positively detect and reverse a prior rejection, keeping `total_weight_approved + total_weight_rejected <= total_weight` as an invariant.

### Proof of Concept
1. Start a signer set with signer S having weight `w` such that `total_weight_rejected` after S's rejection is close to, but not yet past, the blocking-minority threshold (`total_weight - weight_threshold`).
2. Have S send `BlockResponse::Rejected` for block B for a transient/re-evaluable reason (e.g. its own-tenure conflict guard, per `docs/signer-flows.md` section 5) — `stackerdb_listener.rs` records `total_weight_rejected += w`.
3. Let the transient condition resolve (conflict goes stale) so S's local state machine legitimately flips to `LocallyAccepted` and it broadcasts `BlockResponse::Accepted` for the same block hash.
4. Observe in `stackerdb_listener.rs::BlockStatus` that `total_weight_approved` now also includes `w`, while `total_weight_rejected` still includes `w` — the sum of the two now exceeds what a correct disjoint tally would show, and stale rejected weight from S persists indefinitely, able to push `total_weight_rejected` past the abort threshold in `signer_coordinator.rs::get_block_status` even after S has fully endorsed the block.

**Note on verification limits:** I was unable to conclusively trace how/when a fresh `BlockStatus` entry is created per block proposal attempt (e.g., whether a resubmission after `SignatureTimeout` creates a brand-new `BlockStatus` that would reset these counters) due to running out of search iterations; this could partially mitigate long-lived staleness on retries but does not fix the underlying double-counting within a single proposal's lifetime.
