### Title
Deleted multisig members' stale confirmations remain counted toward `num_confirmations`, allowing requests (including fund transfers) to execute below the configured live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` authorizes execution of any pending `MultiSigRequest` (including `Transfer`, `AddKey`, `FunctionCall`) purely by comparing the size of a stored confirmation set against `num_confirmations` [1](#0-0) . When a member is removed via `DeleteMember`/`DeleteKey`, the contract only purges requests that member itself *authored*, not the confirmations that member cast on *other* still-pending requests [2](#0-1) . Those stale confirmations keep counting toward the threshold, so a request can execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
The intended custody binding is:

`count(live members who confirmed request R) >= num_confirmations` before `R` executes.

Instead, the contract enforces:

`|confirmations[R]| + 1 >= num_confirmations`, where `confirmations[R]` is never pruned of entries belonging to members later removed from `self.members`.

`delete_member` only removes:
- outstanding requests where `r.member == member` (requests the removed member *added*), and
- the `num_requests_pk` counter for that member,

but never scans `self.confirmations` to strip votes the removed member cast on requests *added by someone else* [3](#0-2) . `confirm` then blindly trusts `confirmations.len()` without re-validating that every entry still belongs to a current `self.members` member [4](#0-3) .

The legacy `multisig/src/lib.rs` has the identical pattern: `DeleteKey` removes only requests whose `signer_pk` equals the deleted key, not that key's confirmations on other requests, while `confirm` again just checks set size [5](#0-4) [6](#0-5) .

### Impact Explanation
This is a Critical custody-binding violation: "a multisig request executed below threshold." A `Transfer` (or `AddKey`/`FunctionCall` to move funds) can be authorized and executed by fewer *currently trusted* members than `num_confirmations` mandates, because a removed (e.g., compromised, rotated-out, or malicious) member's earlier vote is never invalidated. This directly breaks the equality between "confirmations counted" and "live members," letting NEAR held by the multisig account be moved by a set of parties that no longer meets the configured signing policy.

### Likelihood Explanation
This requires no special privilege beyond normal multisig operation: any member can add and partially confirm a request, and member rotation (`DeleteMember`/`DeleteKey`) is a standard, expected operation. Any scenario where a member is removed after casting a confirmation on a request that has not yet reached threshold — a routine key-rotation or offboarding flow — leaves a stale vote that silently lowers the effective threshold for that pending request. No malicious redeploy, owner-only shortcut, or social engineering is needed; it is purely a bookkeeping gap in `delete_member`/`DeleteKey`.

### Recommendation
When removing a member (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` handling in `multisig/src/lib.rs`), iterate over `self.confirmations` for all pending requests and remove the entry corresponding to the member/public key being deleted, not just requests they authored. Alternatively, validate at `confirm`/execution time that every recorded confirming identity is still present in `self.members` (filtering stale entries) before comparing the count against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `D` (or any member) calls `add_request` with a `Transfer` action draining funds to an attacker-controlled account, producing request `R`.
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (1/3).
4. `B` calls `confirm(R)` → `confirmations[R] = {A, B}` (2/3, below threshold, request stays pending).
5. Through an unrelated, legitimately-confirmed `DeleteMember` request, `B` is removed from the multisig (e.g., normal key rotation). `delete_member` only inspects requests where `r.member == B` (requests `B` authored); it does not touch `confirmations[R]`, so `confirmations[R]` still contains `B` even though `B` is no longer in `self.members` [7](#0-6) .
6. Live members are now only `[A, C, D]`, so a legitimate 3-of-3 approval of `R` should require confirmations from all three. Instead, `C` simply calls `confirm(R)`: `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` triggers `execute_request(R)` immediately [8](#0-7) , transferring funds with approval from only `A` and `C` among the current members plus a stale vote from removed member `B` — one live confirmation short of the configured threshold.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
