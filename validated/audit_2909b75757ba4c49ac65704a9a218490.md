### Title
Unbounded-allocation DoS via `bincode::deserialize::<ConfigKeys>` on attacker-controlled Config account data - (File: account-decoder/src/parse_config.rs)

### Summary
`parse_config` calls `bincode::deserialize::<ConfigKeys>(data)` directly on raw account bytes owned by the Config program, with no length or size-hint validation before deserialization. Because `ConfigKeys` wraps a `Vec<(Pubkey,bool)>`, an attacker who deploys/writes a Config-owned account with a crafted 8-byte little-endian length prefix (used by bincode for `Vec`/`String` lengths) can make the deserializer attempt to pre-allocate a vector sized far beyond the actual account data, before bincode's `Read` implementation hits EOF and errors out.

### Finding Description
`parse_config` is reached from `parse_account_data_v3` in `account-decoder/src/parse_account_data.rs` (`ParsableAccount::Config => serde_json::to_value(parse_config(data, pubkey)?)?`), which in turn is invoked by RPC account/program-account decoding paths whenever `encoding=jsonParsed` is requested and the account owner matches `solana_sdk_ids::config::id()`. [1](#0-0) 

Inside `parse_config`, the very first operation on attacker-controlled `data` is:
```
let parsed_account = deserialize::<ConfigKeys>(data).ok().and_then(...)
``` [2](#0-1) 

`ConfigKeys` is `Vec<(Pubkey, bool)>`-backed (imported from `solana_config_interface::state`). Standard `bincode::deserialize` (the default, unbounded config used via `bincode::deserialize`) reads an 8-byte `u64` length prefix for the `Vec` and then, via serde's generic sequence-visitor logic, attempts to reserve capacity for that many elements (`Vec::with_capacity`/`reserve` sized according to the declared length) before it starts reading individual elements and discovers there isn't enough remaining data. An attacker can therefore write account bytes whose first 8 bytes encode an arbitrarily large `u64` (e.g., `u64::MAX` or any value chosen to exceed the account's real size by orders of magnitude) as the `Vec` length, causing the deserializer to attempt to allocate memory proportional to that attacker-chosen value multiplied by `size_of::<(Pubkey,bool)>()` (33 bytes per element) — independent of the true `data.len()`.

There is no guard in `parse_config` (or in `bincode::deserialize`'s default configuration, which this repo pins without a `with_limit`) checking that the declared vector length is consistent with `data.len()` before allocation is attempted. The only bound that exists in practice is Solana account size limits (`MAX_PERMITTED_DATA_LENGTH`, currently 10 MiB), meaning the attacker cannot request an allocation for more than roughly ~10MiB/33 bytes ≈ 317k `(Pubkey,bool)` entries worth of bytes as raw account data, but the *declared* length prefix is a full 64-bit value read from the account bytes and is not clamped to `data.len()` — so the allocation attempt size is decoupled from the actual data present and can be set to values that are enormous relative to the tiny account (e.g., a few hundred bytes of account data can declare a length of `u64::MAX >> few bits`), causing a very large allocation request per single decode call.

### Impact Explanation
This matches the "decoding panic/loop/unbounded allocation on attacker-authored account data" bounty category referenced in the audit scope for `validator/src/lib.rs`/account-decoder. A single unprivileged client can write such an account (Config program allows arbitrary owner-writable data, and any account owned by the config program ID is routed to `parse_config`) and then issue one `getAccountInfo`/`getProgramAccounts` RPC call with `encoding=jsonParsed` to trigger a large, uncontrolled memory-allocation attempt on the RPC/validator process handling the request — potential latency spikes or OOM/abort for every client/RPC node that later reads and jsonParsed-decodes that account, at a rate of one call per attacker action (well within the "no more than one call per CLUSTER_SLOT_TIME_TARGET / 2" scoping limit).

### Likelihood Explanation
Preconditions are minimal and fully within unprivileged attacker capability: (1) write/own an account with `owner = config::id()` containing an 8-byte crafted length prefix as the first bytes (trivial, no special permissions needed to create Config-owned accounts with arbitrary data via the config program's write instruction), and (2) issue one standard `getAccountInfo`/`getProgramAccounts` RPC call with `jsonParsed` encoding — a normal client operation. This is deterministic and repeatable on every subsequent decode of the same account by any RPC node, since decoding happens per-request with no caching of the parse failure.

### Recommendation
In `parse_config`, validate the declared `ConfigKeys` vector length against `data.len()` before calling `bincode::deserialize`, or use a bounded deserializer (e.g. `bincode::options().with_limit(data.len() as u64).deserialize(data)` / a custom bounded `Vec` deserialize) so that declared sequence lengths can never exceed the actual byte budget available, preventing over-sized `Vec::with_capacity` calls. Apply the same bounded-deserialize pattern to the nested `deserialize(get_config_data(data).ok()?)` call in `parse_config_data`.
