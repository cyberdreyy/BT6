## Finding: Asymmetric validation of the "last sortition" fallback path in `SortitionsView::check_proposal` (v1 chainstate)

### Title
Signer accepts block proposals from an already-timed-out "last sortition" miner because the fallback path's own invalidation flag is computed but never enforced - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
`stacks-signer/src/chainstate/v1.rs`'s `check_proposal` maintains two parallel miner-validity flags: `cur_sortition.miner_status` (current tenure) and `last_sortition.miner_status` (the fallback tenure signers may still sign for if the current miner never got a first block signed). Both flags are independently computed by the same `SortitionState::is_timed_out` check, but only the `CurrentSortition` branch of the final match enforces its flag before accepting a proposal. The `LastSortition` branch never inspects `last_sortition.miner_status`, so a proposal from a miner the signer has *itself already marked as timed out* is still accepted as long as the current miner was separately invalidated before its first block.

### Finding Description
In `check_proposal`: [1](#0-0) 
computes and persists `last_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock` whenever the previous tenure's miner has also been inactive past `block_proposal_timeout`. This mirrors the symmetric check for the current sortition at [2](#0-1) 

Later, the code decides whether a proposal is acceptable based on which sortition it was proposed by: [3](#0-2) 

The `ProposedBy::CurrentSortition` arm rejects when `sortition.miner_status != Valid`. The `ProposedBy::LastSortition(last_sortition)` arm, however, only checks `self.cur_sortition.miner_status != InvalidatedBeforeFirstBlock` — it never reads `last_sortition.miner_status`, even though that exact `SortitionState` value was mutated just a few lines earlier for precisely this purpose. The computed invalidation of the fallback sortition is dead: it is written but never consulted before the signer signs.

This is the same bug shape as the reported analog: a fallback resolution path (`last_sortition`, analogous to the tmp-dir fallback) is granted the same trust as the primary path (`cur_sortition`, analogous to the primary sandbox root) without re-applying the validation that gates the primary path, because the fallback's own "is this trustworthy" flag is silently dropped on the floor at the point of decision.

### Impact Explanation
Because `SortitionsView` is held across the signer's event loop (`sortition_state: &mut Option<SortitionsView>` in `stacks-signer/src/v0/signer.rs`), the timeout state for `last_sortition` accumulates over time and differs between signers depending on when each of them last evaluated a proposal. A signer can therefore end up signing (or pre-committing towards) a block proposed by a miner it had itself already flagged as abandoned/inactive, purely because the *current* miner also failed to get its first block signed. This:
- lets a stale/abandoned tenure be extended by signature even after this signer's own chainstate logic decided it should no longer be trusted, and
- can diverge from other signers whose `last_sortition.miner_status` was computed at a different wall-clock time (or from a freshly reset view where the flag defaults back to `Valid`), producing disagreement between signers about whether the same block/tenure is signable.

This falls under "a signer wedged into ... acting on a stale reward set/threshold" and edges toward "signing a non-canonical/conflicting block" since it permits building on a miner slot the signer's own logic determined to be dead, which is exactly the kind of state the pre-commit/global-acceptance machinery is designed to prevent.

### Likelihood Explanation
Reachable purely through the normal proposal flow: a miner (or a slow/idle tenure) triggers both timeouts naturally, and any signer or gossiped block proposal claiming to be from the last-sortition miner exercises the vulnerable branch — no majority collusion, no key compromise, and no StackerDB-transport trickery is required. It requires the fairly common real-world sequence of "current miner never got a first block signed, and the previous miner was also inactive long enough to have separately timed out" — a condition intensified during miner instability or repeated reorg attempts.

### Recommendation
In the `ProposedBy::LastSortition(last_sortition)` arm of `check_proposal`, also enforce `last_sortition.miner_status == SortitionMinerStatus::Valid` (mirroring the `CurrentSortition` arm) before accepting the proposal, rejecting with an appropriate `RejectReason` (e.g. `InvalidMiner` or a new dedicated reason) when the fallback sortition has itself timed out.

### Proof of Concept
1. Signer observes `cur_sortition` for tenure T2 (whose miner never gets a first block signed within `block_proposal_timeout`) — `check_proposal` marks `cur_sortition.miner_status = InvalidatedBeforeFirstBlock` (`stacks-signer/src/chainstate/v1.rs:144-163`).
2. On a later `check_proposal` call (same in-memory `SortitionsView`), enough time also elapses without a signed block in tenure T1 (`last_sortition`), so the code marks `last_sortition.miner_status = InvalidatedBeforeFirstBlock` too (`stacks-signer/src/chainstate/v1.rs:205-220`).
3. The T1 miner (now known-stale by this signer's own bookkeeping) submits/re-submits a block proposal with `consensus_hash == last_sortition.data.consensus_hash` and a valid signature.
4. `check_proposal` resolves `ProposedBy::LastSortition`, and the match arm at `stacks-signer/src/chainstate/v1.rs:301-316` only checks `self.cur_sortition.miner_status != InvalidatedBeforeFirstBlock` (which holds), never checking `last_sortition.miner_status` (which is already `InvalidatedBeforeFirstBlock`) — the proposal passes this gate and proceeds toward validation/signing, contradicting the signer's own determination that the T1 miner had timed out.
