### Title
Instant-withdraw receipts from prior epochs escape the default haircut and drain the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When a default is finalized, only the *current* epoch's instant-withdraw claims (`instantWithdrawClaimsByEpoch[epochNumber]`) are included in the recovery claim basis, even though `pendingInstantWithdraws` and each user's `instantWithdrawsRequests` are aggregates that can span multiple epochs. Unfunded instant receipts created in an earlier epoch therefore keep a full, at-par claim against the strategy, while the recovery reserve was sized only for current-epoch claims. The first claimants withdraw at par and later rightful claimants (including active LPs via `postDefaultRequests`) find the reserve depleted — a stale-index read analog of the buffer over-read in `do_core_note`, where the code reads only the "current record" while the real outstanding data extends beyond it.

### Finding Description
`defaultPendingClaimBasis` adds only the current epoch's instant claims when `pendingInstantWithdraws != 0`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:644-649
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber];
}
```

But instant receipts are never required to be claimed within one epoch:

- `requestInstantWithdraw` accumulates `instantWithdrawsRequests[_user]` (aggregate) and records per-epoch basis under the *current* `epochNumber` (`IdleCreditVault.sol:366-374`).
- If the borrower honestly cannot fully fund the instant queue at `startEpoch`/`getInstantWithdrawFunds` (liquidity is lent out), `collectInstantWithdrawFunds` only partially reduces `pendingInstantWithdraws` (`IdleCreditVault.sol:398-403`). The unfunded remainder rolls into the next epoch still recorded under the *old* epoch key.
- A user can then request instant withdrawals again, so `instantWithdrawsRequests[user]` contains basis under two epoch keys.

At finalization (`finalizeDefaultRecovery`), `totalBasis` includes only `instantWithdrawClaimsByEpoch[epochNumber]` for instant claims, and `_defaultPrefundedInstantReserve` compares the aggregate `pendingInstantWithdraws` against only the current-epoch basis, returning 0 whenever prior-epoch claims exist (`IdleCreditVault.sol:716-723`). `defaultRecoveryPrice = reserveAmount / totalBasis` therefore excludes the older claims entirely.

On claim, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (`IdleCreditVault.sol:842-856`). The remaining prior-epoch balance in `instantWithdrawsRequests[_user]` then flows into the funded-claim path of `claimInstantWithdrawRequest`, which burns and pays it **at par** via `_transferFundedClaim` — and `_transferFundedClaim` only protects the reserve when `balance - reserve < amount`, so it pays the unhaircutted claim out of unreserved/dust balance, while the recovery-price bookkeeping never accounted for it.

### Impact Explanation
Attacker with two-epoch instant receipts claims the old-epoch portion at par instead of `defaultRecoveryPrice`, extracting `(1 - recoveryPrice) * priorEpochClaim` more than entitled. Since `totalBasis` undercounted real claims, the reserve is exhausted early and later claimants (other defaulted receipt holders, post-default `postDefaultRequests` users, active LP recovery via the CDO) are left permanently underpaid — direct theft plus insolvency of the recovery reserve, quantified as `priorEpochInstantClaims * (1 - defaultRecoveryPrice)` shifted from honest claimants to the attacker.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled (instant mode), (b) an instant request left partially unfunded across an epoch boundary — a normal occurrence whenever lent-out liquidity is insufficient at `startEpoch`, achievable with an honest borrower/manager, and (c) a borrower default in a later epoch. The attacker only needs to be a tranche-token holder calling `requestInstantWithdraw` in two buffer periods and `claimInstantWithdrawRequest` after `finalizeDefault`. No privileged action, no oracle manipulation, and existing guards (`_onlyIdleCDO`, `_transferFundedClaim` reserve check, per-epoch clearing) do not stop it because the missing basis was never included in `totalBasis`.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for *all* outstanding instant claims when `pendingInstantWithdraws != 0`, not just `instantWithdrawClaimsByEpoch[epochNumber]` (e.g., track a global `totalInstantClaimBasis` incremented in `requestInstantWithdraw` and decremented in claim paths). Correspondingly, `_claimDefaultedInstantWithdrawRequest` should haircut the user's entire unfunded instant basis, not only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`.

### Proof of Concept
Foundry fork PoC sketch (instant-mode vault, honest borrower):

```solidity
// epoch 1 buffer: attacker requests instant withdraw of X
cdo.requestInstantWithdraw(X, AAtranche);          // instantWithdrawsRequestsByEpoch[attacker][1] += X
// epoch 1 runs; startEpoch funds only part of the instant queue
// (borrower legitimately has most liquidity lent out)
// -> pendingInstantWithdraws = X - fundedPart > 0
// epoch 2 buffer: attacker requests again Y
cdo.requestInstantWithdraw(Y, AAtranche);          // recorded under epoch 2
// epoch 2 runs, borrower defaults; owner calls finalizeDefault(recovered, src)
// totalBasis includes only instantWithdrawClaimsByEpoch[2] == Y
// defaultRecoveryPrice sized without the X basis
// attacker claims:
cdo.claimInstantWithdrawRequest();
// -> _claimDefaultedInstantWithdrawRequest clears only epoch-2 Y at haircut
// -> funded path then pays the epoch-1 X AT PAR from the strategy,
//    depleting defaultRecoveryReserve / balance that honest claimants need.
// assert: underlying.balanceOf(attacker) > X * defaultRecoveryPrice / 1e18 + Y * defaultRecoveryPrice / 1e18
// assert: a second defaulted-epoch claimant's claim now reverts/shortfalls
```

The assertion shows the attacker receiving `X` at par rather than `X * defaultRecoveryPrice`, with the shortfall materializing as insolvency for subsequent recovery claims.
