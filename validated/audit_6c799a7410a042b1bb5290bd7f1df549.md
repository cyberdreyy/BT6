### Title
Stale Confirmations from Removed Multisig Members Are Still Counted Toward the Approval Threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` counts all entries in the `confirmations` set for a request against `num_confirmations`, without validating that each confirming identity is still a current member. `delete_member` only purges pending requests *authored* by the removed member; it never scrubs that member's confirmations recorded on *other* members' pending requests. A request can therefore execute once `confirmations.len() + 1 >= num_confirmations` even though one or more of the recorded confirmations belong to members who have since been removed from the multisig, breaking the binding: **live confirming members ≥ num_confirmations**.

### Finding Description
`confirm()` computes the threshold purely from the size of the stored `confirmations: HashSet<String>` for a request: [1](#0-0) 

`assert_valid_request()` only checks that the *current caller* is a member; it performs no re-validation of previously stored confirmations against the current member set: [2](#0-1) 

`delete_member()` removes pending requests where `r.member == member` (i.e., requests *authored* by the removed member) and removes that member's `num_requests_pk` counter, but it does not scan `self.confirmations` to strip the removed member's prior confirmations from requests authored by *other* members: [3](#0-2) 

Because of this, a confirmation recorded by member `X` before `X` was deleted remains permanently counted in `confirmations.len()` for any request `X` confirmed but did not author. A later confirmation by a live member can push `confirmations.len() + 1` to meet `num_confirmations` and trigger `execute_request`, even though fewer than `num_confirmations` *currently valid* members actually approved it.

The same class of issue exists in the legacy `multisig/src/lib.rs` contract: `confirm()`/`assert_valid_request()`/`remove_request()` never invalidate confirmations recorded under a public key that was later removed via `DeleteKey`: [4](#0-3) [5](#0-4) 

### Impact Explanation
This breaks the K-of-N custody guarantee that the multisig is supposed to enforce: `num_confirmations` live, currently-authorized approvals should be required before any `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc. is executed. With stale confirmations counted, a request (e.g., a large `Transfer` of NEAR out of the multisig account) can be executed with fewer than `num_confirmations` *currently valid* signers behind it — i.e., "a multisig request executed below threshold," which is explicitly a Critical-severity outcome: funds can be moved by a party set that no longer meets the configured authorization threshold.

### Likelihood Explanation
The precondition — a member being confirmed on a pending request and later removed from the multisig before that request is finalized (deleted or executed) — is a realistic operational sequence for any multisig that rotates members (e.g., removing a departing employee or a compromised key) while other requests are in flight. No special exploit beyond normal multisig operation (adding requests, confirming, and later removing a member via a separate `DeleteMember` request) is required; the vulnerability lies purely in missing invalidation logic, not in any deployment misconfiguration.

### Recommendation
When a member is removed (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` handling in `multisig/src/lib.rs`), iterate over `self.confirmations` for all pending requests and remove any confirmation entry belonging to the removed member/public key, not just requests it authored. Alternatively, revalidate every confirming identity in `confirmations` against the current `members` set inside `confirm()` before comparing the count to `num_confirmations`, discarding stale entries lazily.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D, E}` and `num_confirmations = 3`.
2. Member `A` calls `add_request` with a `Transfer` action to an attacker-controlled receiver.
3. Member `B` calls `confirm(request_id)` → `confirmations = {B}` (1/3).
4. Member `C` calls `confirm(request_id)` → `confirmations = {B, C}` (2/3, not yet executed).
5. Via a separate, properly-authorized multisig flow, member `C` is removed (`DeleteMember` action reaches its own threshold and executes) — `C` is no longer a member, but the confirmation set for the pending Transfer request still contains `"C"` because `delete_member` only cleans requests authored by `C`, not confirmations it left on others' requests (`multisig2/src/lib.rs:355-379`).
6. Member `D` (or `B` again is blocked by re-confirmation check, so a different live member `D`) calls `confirm(request_id)` → `confirmations.len() + 1 = 3 >= num_confirmations(3)` → `execute_request` runs the `Transfer`.
7. Result: the Transfer executed with only `B` and `D` as currently-valid confirming members (2 live confirmations), not the 3 required by `num_confirmations`, because `C`'s stale confirmation was counted.

        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));

        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);

        } else {
            confirmations.insert(member.to_string());

        }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
