### Title
Removed Multisig Member's Confirmation Still Counts Toward Execution Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member()` only purges pending requests that were *submitted* by the removed member, but it never strips that member's confirmation from the `confirmations` set of *other* pending requests they had merely confirmed. `confirm()` later counts `confirmations.len()` against `num_confirmations` without re-validating that every confirmer is still a live member, so a request can execute with a confirmation from an account that is no longer part of the multisig — the same class of bug as the reported `executeMigration()` issue, where an insufficiently-checked quorum/threshold state allowed the guarded action to run without the true number of qualifying approvals.

### Finding Description
`confirm()` treats a request as approved once `confirmations.len() as u32 + 1 >= self.num_confirmations` [1](#0-0) . The `confirmations` set stores string identifiers of members that approved, but nothing re-checks at execution time whether those confirmers are still members of `self.members`.

`delete_member()` is the only place that reconciles member removal with pending state, and it does so incompletely: it deletes outstanding requests filtered by `r.member == member`, i.e. requests where the removed account was the *original submitter*, and clears `confirmations`/`num_requests_pk` only for those requests [2](#0-1) . It does **not** scan every pending request's `confirmations` HashSet to remove entries belonging to the member being deleted.

Consequently, if member `B` confirms a request `R` submitted by a different member `A`, and `B` is later removed from the multisig via a separate, correctly-threshold-approved `DeleteMember` request, `R`'s confirmation set still contains `B`. A subsequent confirmation from any other live member can push `confirmations.len()+1 >= num_confirmations` and execute `R` — even though only a genuine minority of *current* members ever confirmed it. The older `multisig/src/lib.rs` contract has the identical gap: `DeleteKey` removes only requests submitted by that key, not that key's confirmations recorded on other pending requests [3](#0-2) .

This is structurally the same defect as the `AdapterV1.executeMigration()` report: a state-changing, custody-affecting action (`execute_request`, which can be a `Transfer` of NEAR) is gated by a counter (`confirmations.len()`/`votesForMigration`) that is not kept consistent with the actual set of entities entitled to vote (live members/staked capital), so the guarded action fires without the intended quorum truly being met.

### Impact Explanation
`execute_request()` can perform `MultiSigRequestAction::Transfer`, moving NEAR out of the multisig account [4](#0-3) . If execution can be triggered using a stale confirmation from a removed member, the equality "confirmations counted == live members who approved" is broken: `confirmations_counted > live_members_who_approved`. This means a multisig `Transfer` (or `AddKey`/`FunctionCall`) request can be executed with fewer genuinely-current approvals than `num_confirmations` requires — a multisig request executed below the true threshold, directly moving NEAR under authorization that was never actually granted by the current member set. This matches the Critical impact bucket: "a multisig request executed below threshold."

### Likelihood Explanation
Requires the following ordinary, unprivileged-relative-to-the-bug sequence with no owner/redeploy/social engineering: (1) member `A` submits request `R` (e.g. a `Transfer`); (2) member `B` confirms `R` but total confirmations stay below `num_confirmations`; (3) the multisig legitimately (via its own normal threshold process) removes `B` as a member for any ordinary reason (key rotation, personnel change, compromised key remediation); (4) any remaining live member confirms `R`, pushing the stale confirmation count over threshold and executing the transfer. No malicious code deployment or foundation action is needed — it is a natural consequence of the existing `delete_member`/`confirm` code paths interacting on ordinary multisig operations, e.g. removing a member precisely because their key is no longer trusted, while their earlier confirmation still silently counts.

### Recommendation
When deleting a member, iterate all pending requests' `confirmations` sets (not just requests they submitted) and remove the deleted member's entry; if this drops a request below execution eligibility, leave it pending rather than let it later execute using the stale approval. Alternatively, validate at `confirm()`-time (immediately before triggering `execute_request`) that every account/key present in the `confirmations` set is still contained in `self.members`, discounting confirmations from accounts that are no longer members.

### Proof of Concept
```rust
// members: A, B, C, D ; num_confirmations = 3

// 1. A submits and self-confirms a Transfer request R
let request_id = multisig.add_request_and_confirm(transfer_request); // confirmations = {A}

// 2. B confirms R (not yet enough: len+1 = 2 < 3)
multisig.confirm(request_id); // confirmations = {A, B}

// 3. Separately, members legitimately vote to remove B (3 live confirmations from A, C, D)
//    delete_member() only purges requests where r.member == B (i.e. requests B *submitted*),
//    R was submitted by A, so R's confirmations set {A, B} is left untouched.
multisig.execute_request(delete_member_request_for_B); // B removed from self.members

// 4. C confirms R: confirmations.len() + 1 == 3 >= num_confirmations (3) -> executes
multisig.confirm(request_id); // Transfer executes using stale confirmation from removed member B
```
`R` executes and NEAR is transferred despite only `A` and `C` being current, valid members who ever approved it — one fewer live-member confirmation than `num_confirmations` requires. [2](#0-1) [1](#0-0)

        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();

            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
