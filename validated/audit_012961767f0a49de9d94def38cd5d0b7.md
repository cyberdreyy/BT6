### Title
Unfiltered GITLAB_ENV overlay lets a job inject LD_PRELOAD/BASH_ENV/PATH into runner-invoked git and helper subprocesses - ([File: functions/concrete/run/runner.go], [File: functions/concrete/run/env/env.go])

### Summary
`Runner.loadGitlabEnv` parses the `$GITLAB_ENV` file with a bare `KEY=VALUE` split and stores every key verbatim into `r.env.GitLabEnv`, with no denylist for interpreter/loader-affecting variables. `Env.Command` then unconditionally folds that overlay into the environ of every subsequent runner-invoked subprocess (bundled `git`, the runner/helper binary for cache/artifact stages), so a job-controlled `LD_PRELOAD=`, `BASH_ENV=`, or `PATH=` entry propagates into those process environments.

### Finding Description
`setupGitlabEnv` creates a writable file and exposes its path as `$GITLAB_ENV` to the job's own script (`functions/concrete/run/runner.go` lines 484-499). The job's `after_script`/`script` stage can freely append any line to this file — GitLab CI's documented mechanism for "dotenv"-style dynamic variables. `loadGitlabEnv` then reloads the file and stores every `KEY=VALUE` pair into `r.env.GitLabEnv` with no key allow/deny list: [1](#0-0) 

Later stages resolve their subprocess environment through `Env.Command`, which builds the child's `environ` by layering `os.Environ()`, then `e.Env`, then `e.GitLabEnv` (the attacker-influenced overlay), then any stage-specific extra vars, and hands that directly to `cmd.Env`: [2](#0-1) 

This function is reached by the `git()` helper used throughout `get_sources.go` for every git invocation (`git init`, `fetch`, `clone`, `checkout`, submodule handling, and the inline credential-helper `git config` calls), and by `CacheArchive.Run` via `e.RunnerCommand`, which is a thin wrapper over the same `Env.Command`: [3](#0-2) [4](#0-3) 

Because `LD_PRELOAD` (or `BASH_ENV`) is not normally present in the base process environment, there is no duplicate-key ambiguity to resolve: the attacker's line is simply merged in. When the next stage execs the bundled `git` binary (a dynamically linked ELF binary resolved via `e.BundledGit()`), the dynamic loader honors `LD_PRELOAD` from that environ at process start, loading an attacker-supplied shared object into the `git` process. Additionally, git's `credential.<host>.helper` mechanism (seeded by `writeCredentialHelperConfig`, itself using the same environ) invokes helper commands beginning with `!` through a shell (`sh -c`); a `BASH_ENV`/`ENV` entry in that same environ is honored by the shell for non-interactive invocation, giving direct arbitrary-code execution in that shell before the credential command even runs. No code in `loadGitlabEnv` or `Env.Command` filters or masks such keys — the sole invariant check that exists (`GITLAB_ENV` key itself is force-set) does not extend to any other key.

### Impact Explanation
An unprivileged job author can write `LD_PRELOAD=/path/in/build/dir/evil.so` or `BASH_ENV=/path/in/build/dir/payload.sh` into `$GITLAB_ENV`, then trigger a later stage (any subsequent `git` invocation via `GetSources`/submodules, or `CacheArchive`/artifact stages) to have the runner spawn `git` or the helper binary with that variable in its environment. This yields code execution inside the git/helper subprocess running under the runner/helper's OS identity — outside the confines of the job's own script process — matching the scoped impact of "privilege step to runner/helper process control."

### Likelihood Explanation
Preconditions are trivial and fully within an unprivileged pipeline author's control: writing a line to `$GITLAB_ENV` is the documented, supported mechanism for dynamic variables, and placing a payload shared object/script inside the job's own working/cache directory requires no special access. The exploit is deterministic and repeatable across any job that uses `after_script`/dotenv-style variable passing followed by a cache/artifact/get-sources stage.

### Recommendation
In `loadGitlabEnv`, reject or drop overlay keys that can influence interpreter/loader behavior of runner-invoked helper processes (e.g. `LD_PRELOAD`, `LD_LIBRARY_PATH`, `DYLD_*`, `BASH_ENV`, `ENV`, `PATH`, `IFS`, `PERL5LIB`, `PYTHONSTARTUP`, etc.), or switch `Env.Command` to use an explicit allowlist/denylist filter when merging `e.GitLabEnv` into `cmd.Env` for runner/helper-invoked subprocesses, so the overlay can only supply CI-style data variables, never process-control variables.

### Proof of Concept
```go
func TestLoadGitlabEnv_RejectsDangerousKeys(t *testing.T) {
    r := testRunner(t, &Config{})
    require.NoError(t, r.setupGitlabEnv())

    require.NoError(t, os.WriteFile(r.env.GitLabEnvFile,
        []byte("LD_PRELOAD=/tmp/evil.so\nBASH_ENV=/tmp/payload.sh\nSAFE=ok\n"), 0o600))
    r.loadGitlabEnv()

    // Expected (fix): dangerous keys must not reach the overlay.
    _, hasPreload := r.env.GitLabEnv["LD_PRELOAD"]
    _, hasBashEnv := r.env.GitLabEnv["BASH_ENV"]
    assert.False(t, hasPreload, "LD_PRELOAD must not be forwarded to helper/git subprocess environ")
    assert.False(t, hasBashEnv, "BASH_ENV must not be forwarded to helper/git subprocess environ")
    assert.Equal(t, "ok", r.env.GitLabEnv["SAFE"])
}
```
Currently this assertion fails: both `LD_PRELOAD` and `BASH_ENV` are present in `r.env.GitLabEnv` after `loadGitlabEnv`, and a follow-up call to `e.Command`/`git()`/`e.RunnerCommand` (e.g. via `TestPrepare_ReloadsGitlabEnvBetweenStages`-style flow) would place them into the subprocess `cmd.Env` for the next `git`/helper invocation, confirming the injection reaches the exec boundary.

func (e *Env) Command(ctx context.Context, name string, env map[string]string, args ...string) error {
	environ := os.Environ()
	for k, v := range e.Env {
		environ = append(environ, k+"="+v)
	}
	for k, v := range e.GitLabEnv {
		environ = append(environ, k+"="+v)
	}
	for k, v := range env {
		environ = append(environ, k+"="+v)
	}

	cmd := gracefulexitcmd.New(ctx, e.GracefulExitDelay, name, args...)
	cmd.Dir = e.WorkingDir
	cmd.Env = environ
	cmd.Stdout = e.Stdout
	cmd.Stderr = e.Stderr

	return normalizeExitError(cmd.Run(), cmd.ProcessState)
}
