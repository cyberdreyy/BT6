## Answer

Based on the code I was able to review, `findAllowlistedItemWithRetry` in `core/capabilities/vault/allow_list_based_auth.go` will indeed block synchronously for up to `allowListBasedAuthRetryCount` × `allowListBasedAuthRetryInterval` (10 × 3s = 30s) per unauthorized digest before returning `nil, nil, nil` ("not allowlisted"). [1](#0-0) 

The critical factor for whether this is exploitable as a real DoS is the concurrency model of the caller. On the node side, `GatewayVaultRequestProcessor.authorizeAndStamp` calls `AuthorizeRequest` synchronously [2](#0-1) 
and `GatewayHandler.HandleGatewayMessage` (the node-side gateway connector handler) invokes this pipeline directly, with **no goroutine spawned per request** (unlike the sibling `confidentialrelay` handler, which explicitly uses `h.eng.GoCtx` to decouple dispatch from processing, with an explicit comment/regression test — `TestHandler_ServesRequestsConcurrently` — noting that inline processing caused a head-of-line blocking bug). [3](#0-2) [4](#0-3) 

Crucially, this `HandleGatewayMessage` is invoked directly (not in a per-message goroutine) from `gatewayConnector.readLoop`, which is a **single goroutine per gateway connection** that sequentially reads from `gatewayState.conn.ReadChannel()` and calls `handler.HandleGatewayMessage` inline before looping back to read the next message: [5](#0-4) 

This means a burst of unauthorized vault requests routed to a node through a given Gateway connection can each block that connection's single read loop for up to 30 seconds, delaying delivery/processing of subsequent legitimate messages (including for other subscribers/workflow owners) forwarded over that same connection — a genuine head-of-line-blocking DoS, not merely a generic "slow handler" concern, since the interface contract documented in `handlers.Handler` explicitly states each user request should be processed by "a separate goroutine" [6](#0-5) 
but the vault node-side `GatewayHandler.HandleGatewayMessage` breaks that isolation guarantee by processing inline in the shared connector read loop.

I could not fully verify within tool budget whether there is an intervening dispatch layer (e.g., a worker pool) between `gatewayConnector.readLoop` and `handler.HandleGatewayMessage` for the vault path specifically, nor whether the attacker-reachable path is limited to gateway-authenticated DON traffic versus truly attacker-controlled unauthenticated input reaching this exact node-side handler (as opposed to the Gateway-side `core/services/gateway/handlers/vault/handler.go`, which uses per-HTTP-request goroutines via `gateway.ProcessRequest` and an async `callback.Wait(ctx)` pattern with its own timeout, which is not affected in the same way). [7](#0-6) 

### Title
Node-side vault gateway handler processes messages inline in the single-threaded connector read loop, allowing a burst of never-allowlisted requests to head-of-line-block the connection for up to 30s each - (File: core/capabilities/vault/allow_list_based_auth.go, core/capabilities/vault/gw_handler.go, core/services/gateway/connector/connector.go)

### Summary
`findAllowlistedItemWithRetry` blocks for up to 30 seconds (10 retries × 3s) before concluding a digest is "not allowlisted." `GatewayHandler.HandleGatewayMessage`, which calls into this retry loop via `AuthorizeRequest`, is invoked synchronously and inline from `gatewayConnector.readLoop`, a single per-gateway-connection goroutine that processes messages sequentially with no per-message goroutine dispatch — unlike the sibling `confidentialrelay.Handler`, which explicitly decouples dispatch from processing to avoid exactly this class of bug (per its own regression test comment). This allows an attacker who can route a burst of never-allowlisted digests through the Gateway to a DON node to stall that connection's message processing for extended periods, delaying authorization of concurrently-forwarded legitimate requests from other workflow owners multiplexed over the same connection.

### Finding Description
`findAllowlistedItemWithRetry` (`core/capabilities/vault/allow_list_based_auth.go:79-111`) retries up to `allowListBasedAuthRetryCount` (10) times with `allowListBasedAuthRetryInterval` (3s) sleeps between attempts, sleeping via `sleepWithContext` on every iteration except when found or context canceled. For any digest that is never allowlisted (trivial to produce — any `CreateSecrets`/`DeleteSecrets`/`ListSecretIdentifiers` request whose digest doesn't match a workflow-registry-known allowlisted request), the full ~30s is consumed before returning `nil, nil, nil`, which `AuthorizeRequest` converts into `"request not allowlisted"`.

This is invoked through `GatewayVaultRequestProcessor.authorizeAndStamp → AuthorizeRequest` (`gateway_vault_request_processor.go:222-238`), reached from `GatewayHandler.HandleGatewayMessage` (`gw_handler.go:180-211`) for `MethodSecretsCreate/Update/Delete/List`. That handler method runs synchronously to completion (no internal goroutine dispatch, no timeout wrapper such as the `serveTime.WithTimeout` used by `confidentialrelay.Handler`).

`GatewayHandler.HandleGatewayMessage` is registered as the method handler invoked directly, inline, from `gatewayConnector.readLoop` (`core/services/gateway/connector/connector.go:268-298`), which is one goroutine per gateway connection, looping on `<-gatewayState.conn.ReadChannel()` and calling `handler.HandleGatewayMessage(...)` before returning to read the next message. There is no worker pool or per-message goroutine spawn at this layer for the vault handler (contrast with `confidentialrelay.Handler.HandleGatewayMessage`, which explicitly wraps processing in `h.eng.GoCtx(...)` specifically to avoid blocking the dispatch path — with an explicit regression test, `TestHandler_ServesRequestsConcurrently`, documenting that this exact class of serialization bug was previously fixed for that handler).

### Impact Explanation
This maps to a service-disruption / partial-DoS impact against the DON node's vault gateway message pipeline: an attacker who can get several distinct never-allowlisted digests routed to a node via the Gateway can occupy that gateway connection's single read-loop goroutine for up to 30 seconds per request, in sequence. Legitimate, concurrently-forwarded vault requests from other workflow owners sharing that same Gateway↔node connection are queued behind the malicious ones and may be delayed well past their intended authorization window, effectively denying/degrading service availability for unrelated subscribers' Create/Update/Delete/List secret operations. This does not itself cause allowlist bypass or credential disclosure — it is an availability degradation of the authorization pipeline for other users.

### Likelihood Explanation
Low privilege is required — the ability to get a JSON-RPC vault request forwarded through the Gateway to the DON node with an arbitrary (garbage/unauthorized) digest is sufficient; no allowlisting, signature validity beyond structural JSON-RPC requirements, or special role is needed to trigger the retry loop (the request only needs to pass `ValidateStructureBeforeAuth`, not actual authorization). Repeating this with a handful of distinct request IDs/digests in quick succession is straightforward and fully attacker-controlled, requiring no timing races or privileged network position — but it does depend on how many concurrent Gateway connections/read loops exist per node and whether messages from different real users are actually multiplexed over the same single connection, which I could not fully confirm from available context.

### Recommendation
Dispatch node-side gateway vault message handling (`GatewayHandler.HandleGatewayMessage`) onto a per-request goroutine (or bounded worker pool) decoupled from `gatewayConnector.readLoop`, mirroring the pattern already used in `confidentialrelay.Handler` (`h.eng.GoCtx` plus `serveTime.WithTimeout`). Additionally, consider capping total retry-wait time more conservatively for known-invalid digests, or short-circuiting retries with a fast per-digest negative cache to avoid repeatedly incurring the full retry window for the same or similar unauthorized requests.

### Proof of Concept
Handler-level integration test plan:
1. Construct a fake `WorkflowRegistrySyncer` whose `GetAllowlistedRequests` never returns a matching digest for "attacker" requests but does for a "legit" digest injected mid-test.
2. Wire `gatewayConnector.readLoop`-equivalent test harness (or directly drive `GatewayHandler.HandleGatewayMessage` in a loop matching connector semantics) with a channel feeding N attacker requests followed by 1 legitimate request, all with distinct IDs/digests.
3. Reduce `retryCount`/`retryInterval` via test constructor injection (as already supported by the `allowListBasedAuth` struct fields) to keep the test fast while preserving the same 10-iteration blocking structure.
4. Assert: the legitimate request's response is not sent to the gateway connector until all preceding attacker requests have each consumed their full retry budget, demonstrating serialized, unbounded-relative-to-attacker-request-count blocking of the single dispatch path — i.e., total latency for the legit request ≈ N × (retryCount × retryInterval), confirming head-of-line blocking.
5. Contrast with a modified handler that dispatches via `eng.GoCtx`, showing the legitimate request completes promptly regardless of concurrent attacker requests (as in `TestHandler_ServesRequestsConcurrently` for `confidentialrelay`).

func (r *allowListBasedAuth) findAllowlistedItemWithRetry(ctx context.Context, req jsonrpc.Request[json.RawMessage], requestDigest string, requestDigestBytes32 [32]byte) (*workflow_registry_wrapper_v2.WorkflowRegistryOwnerAllowlistedRequest, []string, error) {
	for attempt := 0; attempt <= r.retryCount; attempt++ {
		allowedRequests := r.workflowRegistrySyncer.GetAllowlistedRequests(ctx)
		allowedRequestsStrs := make([]string, 0, len(allowedRequests))
		for _, rr := range allowedRequests {
			allowedReqStr := fmt.Sprintf("AuthorizedOwner: %s, RequestDigest: %s, ExpiryTimestamp: %d", rr.Owner.Hex(), hex.EncodeToString(rr.RequestDigest[:]), rr.ExpiryTimestamp)
			allowedRequestsStrs = append(allowedRequestsStrs, allowedReqStr)
		}
		r.lggr.Debugw("AllowListBasedAuth loaded allowlisted requests", "method", req.Method, "requestID", req.ID, "attempt", attempt+1, "allowedRequests", allowedRequestsStrs)

		allowlistedRequest := r.fetchAllowlistedItem(allowedRequests, requestDigestBytes32)
		if allowlistedRequest != nil {
			return allowlistedRequest, allowedRequestsStrs, nil
		}
		if attempt == r.retryCount {
			return nil, allowedRequestsStrs, nil
		}

		r.lggr.Debugw("AllowListBasedAuth request digest not yet allowlisted, retrying",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"attempt", attempt+1,
			"maxAttempts", r.retryCount+1,
			"retryInterval", r.retryInterval)
		if err := sleepWithContext(ctx, r.retryInterval); err != nil {
			r.lggr.Debugw("AllowListBasedAuth retry canceled", "method", req.Method, "requestID", req.ID, "error", err)
			return nil, nil, err
		}
	}

	return nil, nil, nil // unreachable: loop always returns
}

func (h *GatewayHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) (err error) {
	reqLggr := h.requestLogger(req, gatewayID)
	reqLggr.Debugw("received message from gateway", "req", req)

	var response *jsonrpc.Response[json.RawMessage]
	var authResult *AuthResult

	switch req.Method {
	case vaulttypes.MethodSecretsCreate, vaulttypes.MethodSecretsUpdate:
		publicKey, pkErr := h.getMasterPublicKey(ctx)
		if pkErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pkErr)
			break
		}
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, publicKey)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodSecretsDelete, vaulttypes.MethodSecretsList:
		authorized, pipelineErr := h.requestProcessor.ProcessRequest(ctx, req, nil)
		if pipelineErr != nil {
			response = h.gatewayErrorResponse(ctx, gatewayID, req, pipelineErr)
			break
		}
		authResult = authorized.AuthResult
	case vaulttypes.MethodPublicKeyGet:
		response = h.handlePublicKeyGet(ctx, gatewayID, req)
	default:
		response = h.errorResponse(ctx, gatewayID, req, api.UnsupportedMethodError, errors.New("unsupported method: "+req.Method))
	}

func (h *Handler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	h.lggr.Debugw("received message from gateway", "gatewayID", gatewayID, "requestID", req.ID)

	// GoCtx ties the goroutine to the handler's service lifecycle, so Close waits
	// for in-flight requests instead of abandoning them mid-vault-call.
	h.eng.GoCtx(ctx, func(ctx context.Context) {
		ctx, done, err := h.serveTime.WithTimeout(ctx)
		if err != nil {
			h.lggr.Errorw("failed to apply serve timeout, dropping request", "gatewayID", gatewayID, "requestID", req.ID, "err", err)
			return
		}
		defer done()
		h.serveGatewayMessage(ctx, gatewayID, req)
	})

	return nil
}

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
