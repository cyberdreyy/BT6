### Title
Missing zero-address / validity check on `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` permanently locks migrated funds - (File: `programs/marginfi/src/instructions/marginfi_account/transfer_account.rs`)

### Summary
`transfer_to_new_account` and `transfer_to_new_account_pda` let an account's own `authority` migrate its `MarginfiAccount` (balances, flags, emissions destination) to a brand-new account under an arbitrary `new_authority` pubkey, with no validation that `new_authority` is non-zero or otherwise usable. This mirrors the C4 finding in `AccountantDelegate.initialize()`, where a critical address parameter (`treasury_`) was settable to the zero address with no `require()` check, causing an unrecoverable, high-impact misconfiguration.

### Finding Description
Both migration entrypoints accept `new_authority` as a completely unchecked account: [1](#0-0) [2](#0-1) 

The instruction logic uses `ctx.accounts.new_authority.key()` directly to initialize the new account's authority, with no `check!`/`require!` guarding against `Pubkey::default()` or any other non-controllable value: [3](#0-2) 

Immediately after, the old account is irreversibly finalized: its `lending_account` is zeroed out and it is flagged `ACCOUNT_DISABLED`, permanently pointing at the new (possibly inaccessible) account via `migrated_to`: [4](#0-3) 

Notably, the off-chain CLI client (`p0-cli`) explicitly recognizes this risk and defends against it client-side, proving the danger is understood but not enforced on-chain: [5](#0-4) 

The test suite for this instruction also documents the lack of protection: [6](#0-5) 

### Impact Explanation
If `new_authority` is mistakenly set to `Pubkey::default()` (or any pubkey the caller does not actually control), the newly created `MarginfiAccount` — which now holds all of the migrated `lending_account` balances (deposits/borrows) and `emissions_destination_account` — becomes permanently uncontrollable, since no private key exists for the zero pubkey. Simultaneously the old account is disabled and its `lending_account` zeroed, with `migrated_to` set and a `check_eq!` on `migrated_to == Pubkey::default()` that prevents any re-migration or recovery attempt. This produces a durable freeze of user funds with no on-chain remediation path, analogous to the report's "loss of funds" and "inability to easily fix" concerns that drove the Medium severity rating.

### Likelihood Explanation
This is directly reachable by any unprivileged user acting on their own account (`authority` is simply the current account owner, a `Signer`) — no special privileges are required. A GUI/SDK integration bug, fat-fingered CLI invocation without the client-side guard, or a buggy third-party integrator building on `transfer_to_new_account_pda` (which is explicitly designed for third-party/CPI use, see `third_party_id` and `is_allowed_cpi_for_third_party_id`) could pass a zero or garbage `new_authority`, permanently bricking the migrated account.

### Recommendation
Add an on-chain `require!(ctx.accounts.new_authority.key() != Pubkey::default(), MarginfiError::InvalidAuthority)` (or equivalent) check in both `transfer_to_new_account` and `transfer_to_new_account_pda` before finalizing the migration, mirroring the safeguard already present in the `p0-cli` client but currently absent from the program itself.

### Proof of Concept
1. Caller (account `authority`) invokes `transfer_to_new_account` with `new_authority = Pubkey::default()`.
2. `initialize_migrated_account` sets `new_account.authority = Pubkey::default()`, copying over all balances: [7](#0-6) 
3. `finalize_migrated_old_account` disables the old account and zeros its `lending_account`, setting `migrated_to` to the new account irreversibly: [4](#0-3) 
4. No subsequent instruction can act as `authority` on the new account since `Pubkey::default()` has no signer — deposits/borrows recorded there are permanently unreachable.
