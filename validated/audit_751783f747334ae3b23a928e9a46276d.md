Based on the investigation, I've identified a solid analog to the "pendingWithdrawals just increments" bug class in the node-side signer coordination logic.

### Title
Stale rejection weight is never decremented when a signer reconsiders and accepts a block, letting inflated `total_weight_rejected` block a validly-signed block or ban txids on stale minority opinions - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run_loop` maintains two independent monotonic accumulators per proposed block, `total_weight_approved` and `total_weight_rejected`, guarded by two different `HashSet`s (`gathered_signatures` and `responded_signers`). The guard that prevents double counting is asymmetric: it stops an already-approved signer from also being counted as a rejecter, but does **not** stop a signer who rejected first from later being counted as an approver while their earlier rejection weight is still counted. Just like `pendingWithdrawals` in the referenced report, `total_weight_rejected` (and the per-txid `failed_txids` weights) only ever increases and nothing in the accept path removes the stale contribution, so the derived threshold checks operate on a value that no longer reflects the signer's current vote.

### Finding Description
On `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))`: [1](#0-0) 
`block.responded_signers.insert(slot_id)` succeeds the first time a signer's reject is seen, and `total_weight_rejected` is bumped by `signer_entry.weight`.

On `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the *same* block/slot arriving afterward: [2](#0-1) 
the guard checked is `!block.gathered_signatures.contains_key(&slot_id)`, which is unrelated to `responded_signers`. Since this is the signer's first *accept*, the condition is true, so `total_weight_approved` is also bumped by the same signer's weight — while the earlier rejection weight already added to `total_weight_rejected` is never subtracted.

The reverse order (accept, then later reject) *is* correctly guarded, because the accept path also inserts into `responded_signers`, so a later reject's `responded_signers.insert(slot_id)` returns `false` and is skipped. Only the reject-then-accept order is unguarded.

Reconsideration after an initial rejection is an explicitly supported, normal flow in this codebase (not adversarial): the signer changelog documents "For some rejection reasons, a signer will reconsider a block proposal that it previously rejected" and `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs` implements exactly this. So a single, honest signer reconsidering its own vote is enough to trigger the double count — no majority or malicious key is required.

The same unguarded accumulation pattern also affects the per-txid `failed_txids` map: [3](#0-2) 
`info.total_weight` and `info.problematic_weight` are only ever added to per rejecting signer and never reduced when that signer later accepts the block (which implicitly means they no longer consider the flagged tx a problem).

### Impact Explanation
`SignerCoordinator::wait_for_signer_signatures_or_timeout` checks the rejection condition before the approval condition: [4](#0-3) 
If enough signers reject and then reconsider/accept, `total_weight_rejected` can still be stuck at or above the >30% blocking threshold from stale weight even though the genuine, current rejecting weight is below it and genuine current approving weight has legitimately reached 70%. Because the rejection branch is checked (and returned on) first, the miner wrongly treats an already validly-signed block as globally rejected (`NakamotoNodeError::SignersRejected`), and — via the `failed_txids` tally computed from the same stale per-txid weights — can temporarily or **permanently** exclude transactions (`permanently_excluded_txids`) based on an opinion a signer no longer holds. This is a liveness wedge in the mining/coordination path: the node can be made to discard blocks it already has sufficient real signatures for, and to durably ban transactions, based on outdated signer state that the code's own bookkeeping never retracts.

### Likelihood Explanation
This requires only one signer to reject a proposal and subsequently reconsider and accept it — an explicitly supported, common, non-adversarial code path (`should_reevaluate_reject_reason`). No majority, no key compromise, and no malicious behavior is needed; ordinary signer reconsideration during normal operation is sufficient to leave `total_weight_rejected`/`failed_txids` weights permanently inflated for that block.

### Recommendation
When processing an `Accepted` response for a signer whose slot is already present in `responded_signers` due to a prior `Rejected` response (or vice versa), subtract the signer's weight from the stale counter (`total_weight_rejected` and the relevant `failed_txids` entries) before/while adding it to the new counter, so `total_weight_approved` and `total_weight_rejected` always reflect only each signer's *current* vote, and their sum never exceeds `total_weight`.

### Proof of Concept
1. Miner proposes block `B`; signer `S` (weight `w`) initially rejects `B` with `RejectCode::ValidationFailed(BadTransaction)` for txid `T` — `total_weight_rejected += w`, `failed_txids[T].total_weight += w`.
2. `S` reconsiders (a legitimate, supported flow) and sends `BlockResponse::Accepted` for the same `B` — `total_weight_approved += w`, while `total_weight_rejected` still includes `S`'s stale `w`.
3. If other signers' genuine current approvals now total ≥70% weight, and the stale `total_weight_rejected` (including `S`'s already-retracted rejection) plus `weight_threshold` still exceeds `total_weight`, `wait_for_signer_signatures_or_timeout` returns `SignersRejected` before ever reaching the approval branch, discarding a block that has legitimately reached the signing threshold, and potentially permanently banning `T` if `info.problematic_weight` similarly clears the blocking-minority bar with stale weight.
