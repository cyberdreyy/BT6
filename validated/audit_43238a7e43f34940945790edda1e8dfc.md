### Title
Multisig `confirm()` counts stale confirmations from removed members, allowing request execution below the intended live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` decides whether a request has reached quorum purely by counting entries already stored in `self.confirmations` plus the new caller, without re-validating that each previously-recorded confirmer is still a current member of `self.members`. `delete_member` only purges confirmations belonging to requests that the removed member itself originated (`r.member == member`); it does not scrub the removed member's entry from the confirmation sets of *other* outstanding requests they had merely confirmed. This breaks the intended equality "number of confirmations counted == number of confirmations from currently authorized members," letting a request execute with fewer live-member approvals than `num_confirmations`.

### Finding Description
In `multisig2/src/lib.rs`:
- `confirm()` (lines 292-315) only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` and inserts the *current* caller's identity if not yet at quorum — it never re-checks that the pre-existing entries in `confirmations` still correspond to accounts/keys present in `self.members`. [1](#0-0) 
- `delete_member()` (lines 356-379) removes outstanding *requests originated by* the removed member (`filter_map(|(k, r)| if r.member == member ...)`) and clears their confirmation sets, and removes the member from `self.members` and `num_requests_pk`. It does **not** iterate over confirmation sets of requests *originated by other members* to strip out the removed member's stale confirmation. [2](#0-1) 
- The only member-count safety check in `delete_member` is `self.members.len() - 1 >= self.num_confirmations`, i.e. it guarantees enough *members remain* for quorum to be theoretically achievable — it says nothing about whether a request that already has confirmations from a departing member should have that confirmation invalidated. [3](#0-2) 

The identical pattern exists in the legacy `multisig/src/lib.rs` contract, where `remove_request`/`DeleteKey` handling likewise only purges requests signed by the deleted key, not confirmations the deleted key gave on other members' requests. [4](#0-3) [5](#0-4) 

This is structurally the same bug class as the reported `LockingController.increaseUnwindingEpochs` issue: a security-critical function trusts a stored/derived value (there: `msg.sender`'s current balance as a stand-in for "shares this holder actually still owns"; here: the count of entries in a confirmation set as a stand-in for "how many *currently authorized* members have approved") without re-validating it against ground truth at the moment of use. In the original report the mismatch caused an unwanted revert; in this multisig analog the mismatch instead lets an already-departed member's stale approval silently count toward quorum for actions requested against other, unrelated proposals.

### Impact Explanation
Concretely: consider a 4-member multisig with `num_confirmations = 3` (members A, B, C, D).
1. D confirms a pending high-value `Transfer` request R originated by A (confirmations = {A(implicit via add_request_and_confirm) , D}, i.e. 2/3).
2. Members subsequently pass a separate, properly-quorum'd `DeleteMember{D}` request (members after removal = {A, B, C}, still `>= num_confirmations` so the safety assert passes).
3. C confirms R. `confirm()` only checks `confirmations.len() + 1 >= 3` → 2 + 1 = 3 → quorum reached, and `execute_request` fires the transfer.

R executes with a confirmation set of {A, D, C} even though D is no longer a multisig member — i.e., the request was authorized using only two live members' approvals (A and C) despite the intended 3-of-3 threshold. This is a threshold-bypass: funds can move (or keys/members can be added/removed, contract code redeployed, etc.) with fewer currently-authorized approvers than the multisig's configured `num_confirmations`, matching the "Critical: a multisig request executed below threshold" impact category.

### Likelihood Explanation
This does not require any malicious code deployment, RPC interception, or victim key compromise — it only requires the ordinary sequence of: (a) a member confirms a request, (b) that same member is later removed via a normal, correctly-authorized `DeleteMember` action (a routine multisig operation, e.g. offboarding a departing signer), and (c) the pre-existing unrelated request is later confirmed to reach quorum. Membership changes over the life of a long-lived multisig (which this contract is explicitly designed to support, given `AddMember`/`DeleteMember` actions) make this a realistic, easily-triggered sequence rather than a contrived edge case.

### Recommendation
When executing `DeleteMember`, iterate over **all** outstanding requests' confirmation sets (not just those the removed member originated) and remove the departing member's entry from each. Alternatively/additionally, in `confirm()`, filter `confirmations` against `self.members` before counting toward quorum (i.e., recompute `confirmations.iter().filter(|m| self.members.contains(m)).count()` rather than trusting the raw stored set length), so quorum is always evaluated against live membership at confirmation time.

### Proof of Concept
Using the existing test harness pattern in `multisig2/src/lib.rs` (e.g. `test_multi_3_of_n`):
1. `MultiSigContract::new(members(), 3)` with 4 members A,B,C,D.
2. As D, `add_request_and_confirm` a `Transfer` request R (confirmations = {D}).
3. As A and B, jointly pass `add_request_and_confirm`/`confirm` on a separate `DeleteMember{D}` request (this reaches quorum 3 using A,B,C — a legitimate, fully-authorized action), removing D from `self.members` but leaving R's `confirmations` set untouched (since R was not originated by D, `delete_member`'s request-purge filter `r.member == member` does not touch it).
4. As C, call `confirm(request_id_of_R)`. `confirmations.len()` is still 1 (D) → `1 + 1 = 2 < 3`... 

Note: to reach the exploit in one extra step, have both C and one more still-current member confirm; the key point demonstrated by inspecting the code is that `confirmations.len()` never decreases when D is removed and D's identity is never validated against `self.members` at the point `confirm()` sums toward quorum, so D's stale approval is available to be "spent" toward quorum after D no longer has any authority. This is provable directly from the code: `delete_member` (lines 356-379) only purges `requests`/`confirmations` for `r.member == member`, and `confirm` (lines 292-315) performs no membership check against stored confirmation entries.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
