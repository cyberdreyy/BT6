### Title
Spot ERC4626 `convertToAssets` valuation in ProgrammableBorrower is donation/flash-inflation manipulable, inflating epoch interest and tranche prices - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` values its parked liquidity sleeve using the vault's instantaneous `convertToAssets` (share-price = `totalAssets / totalSupply` for balance-based vaults). That spot value feeds `_vaultNetInterest()` → `totalInterestDueNow()`, the single value `IdleCDOEpochVariant` reads at `stopEpoch` to price/mint epoch interest onto the tranches. An unprivileged attacker (a KYC'd tranche holder, or even just a vault depositor sequencing around keeper calls) can flash-inflate the vault's assets (donation into the vault's asset balance, or a flash-borrowed deposit elsewhere) immediately before `stopEpoch`, causing fake "vault interest" to be recognized, then redeem tranche tokens at the inflated virtual price before the price mean-reverts.

### Finding Description
- `_currentVaultAssets()` converts the borrower's vault shares to underlying via `vault.convertToAssets(shares)` — a spot, same-block-manipulable reading (contracts/strategies/idle/ProgrammableBorrower.sol:546-549). Per EIP-4626, `convertToAssets` is *not* manipulation-resistant; it merely reflects current vault assets. For the common case where the vault's `totalAssets()` reads `asset.balanceOf(vault)` (or an internal accounting balance that can be pushed up by direct transfers or by the attacker's own redeemable deposits in vaults with asymmetric share/asset moves), any EOA can move it atomically.
- `_vaultNetInterest()` computes `earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault` minus the baseline, and reports the positive delta as interest (lines 337-347). There is no TWAP, no sanity bound vs. `borrowerApr`, and no cap on vault-side "interest".
- `totalInterestDueNow()` (lines 330-334) returns this to `IdleCDOEpochVariant`, which — per the contract's own docs — reads it as the epoch interest to mint/realize into tranche prices at `stopEpoch` (comments at lines 27-28, 325-329). Interest is *minted* (comment line 352: "Interest is minted (not pulled as cash)"), so an inflated reading directly raises tranche `virtualPrice` / NAV rather than requiring actual cash to be pulled.
- Sequence (attacker = KYC-passing AA tranche holder, epoch running):
  1. During a running epoch, attacker holds AA tranche tokens.
  2. Just before the keeper calls `stopEpoch` (visible in mempool / sequenced in the same block), attacker transfers `D` underlying directly into the ERC4626 vault (donation), raising `convertToAssets` for `ProgrammableBorrower`'s shares by ~`D` (exact share depends on the vault, but the attacker recaptures none of it only if PB holds 100% of shares — the cost analysis below handles partial cases).
  3. `stopEpoch` runs: `totalInterestDueNow` includes the phantom `D`, interest is minted into tranche price, AA virtual price is inflated.
  4. Attacker calls `withdraw`/`requestWithdraw` or instant-withdraws tranches at the inflated price, extracting real underlying above the fair NAV. The vault then has `D` more assets but those belong pro-rata to `ProgrammableBorrower`'s shares too — the *pricing* gain was already realized by the attacker at inflated NAV, and subsequent tranche redemptions are impaired once valuation normalizes, socializing the loss onto remaining lenders.

The code even acknowledges `convertToAssets` fragility: `onDefault` explicitly avoids it "even if the external vault's valuation view is unavailable during stress" (lines 295-297) — but every accounting read (`_vaultNetInterest`, `availableToBorrow`, `onStopEpoch` shortfall check, `onStartEpoch` baseline) still trusts the live spot value.

Secondary effect: `availableToBorrow()` (lines 350-355) also uses `_currentVaultAssets`, so upward manipulation inflates `borrowable`. And a *downward* manipulation right before `stopEpoch` fabricates a `vaultLoss` in `_vaultNetInterest`, which cancels real interest or pushes the pool toward the default/`stopEpochWithDuration(_lossAmount)` path — griefing/BB-loss-socialization leverage for an attacker positioned accordingly.

### Impact Explanation
Direct theft / loss socialization: phantom vault interest is minted into tranche prices, letting the attacker redeem tranche tokens for more underlying than fair NAV; remaining tranche holders absorb the deficit (inflated price collapses once the spot valuation normalizes). Magnitude is bounded by the donation cost `D` the attacker is willing to spend, but the *gain* scales with the attacker's tranche-token share of pool NAV — an attacker holding a large fraction of AA supply can profit when `(attacker tranche share) × D > D`, i.e., whenever the pool's tranche NAV exceeds the vault sleeve multiplier makes it profitable — concretely profitable whenever minted-interest effect on their redeemed value exceeds donation net cost, which holds when PB holds a large share of vault supply and the attacker dominates AA supply. This breaks the fair mint/burn and loss-waterfall invariants.

### Likelihood Explanation
Medium. Requirements: (a) vault must use balance/asset-based `totalAssets` (true for most ERC4626 yield vaults); (b) attacker must be a KYC'd tranche holder (in-scope role) and time the inflation around the keeper `stopEpoch` — feasible via public mempool or by donating during the buffer period where `bufferedVaultDelta`/`bufferedVaultDelta` carry-over (`onStartEpoch` lines 206-210) also trusts spot values, and buffer inflation needs no timing at all since `bufferedVaultDelta` snapshots the *start* reading vs. the previous `bufferStartVaultAssets` baseline; an attacker can inflate during the entire buffer window with no timing risk. The `onStartEpoch` path is the stronger variant: `bufferedVaultDelta = currentVaultAssets - bufferStartVaultAssets` is computed purely from spot reads, so any donation parked in the vault during the buffer is recognized as epoch interest at the next `stopEpoch`, no mempool race required.

### Recommendation
- Do not value the sleeve from raw spot `convertToAssets`. Snapshot share count and use a bounded price: track `epochStartSharePrice = convertToAssets(1 share)` at `onStartEpoch` and cap `totalInterestDueNow`'s vault component by `shares × max(currentPrice, baseline + aprBound)` or validate against an externally agreed yield rate.
- Alternatively, realize vault PnL only via actual `withdraw`/`redeem` proceeds (cash basis) rather than mark-to-spot: `epochWithdrawnFromVault` already tracks realized assets — only count interest that has actually been withdrawn to the contract.
- Clamp `bufferedVaultDelta` similarly, or measure buffer PnL from net realized flows rather than two spot snapshots.
- If mark-to-market is required, bound it by an owner-set `maxVaultApr` sanity check so manipulation beyond plausible yield is ignored rather than minted.

### Proof of Concept
Foundry fork PoC (conceptual — requires the repo's existing `ProgrammableBorrower` test harness from `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// Assume: ERC4626 vault V where totalAssets() = asset.balanceOf(V) (or manipulable by deposit),
// pool in buffer phase (epochAccountingActive == false), bufferStartVaultAssets = S.
// Attacker holds a large fraction of AA tranche tokens (KYC'd lender).

function test_BufferDonationInflatesEpochInterest() public {
    uint256 D = 1_000_000e6; // donation amount

    // 1. During buffer (no timing needed), attacker donates D underlying to vault V
    deal(address(asset), attacker, D);
    vm.prank(attacker);
    asset.transfer(address(vault), D); // inflates convertToAssets

    // 2. Keeper starts epoch -> onStartEpoch computes
    //    bufferedVaultDelta = _currentVaultAssets() - bufferStartVaultAssets = +D (phantom)
    vm.prank(address(idleCDO));
    borrower.onStartEpoch(pendingWithdraws);

    // 3. Attacker removes the donation pressure is not needed; even if price stays,
    //    epochStartVaultAssets baseline already includes the inflation via startAssets,
    //    but bufferedVaultDelta = +D is carried as PnL.

    // 4. At stopEpoch, IdleCDO reads totalInterestDueNow() which includes +D phantom
    //    interest -> minted into tranche prices.
    uint256 interest = borrower.totalInterestDueNow();
    assertGt(interest, D - 1); // phantom interest recognized

    // 5. Keeper calls stopEpoch; tranche virtual price inflated by ~D/NAV.
    vm.prank(keeper);
    idleCDO.stopEpoch();

    // 6. Attacker withdraws tranches at inflated price; drains real underlying.
    uint256 balBefore = asset.balanceOf(attacker);
    vm.prank(attacker);
    idleCDO.withdrawAA(trancheBal);
    assertGt(asset.balanceOf(attacker) - balBefore, fairRedeemValue);
    // Remaining lenders' subsequent withdrawals are impaired by up to ~D.
}
```

The same-block variant front-runs `stopEpoch` directly with a flash-loaned donation if the vault's `totalAssets` reads raw token balance (standard for Morpho/Compound-style and many custom vaults), so `D` can be flash-borrowed and repaid within the window only if reclaimable — otherwise the attacker parks a real donation during the buffer where no timing is needed, which is strictly cheaper to execute and fully covered by the in-scope "user of the programmable borrower's ERC4626 vault" role.

Caveats: I verified the accounting surface in `ProgrammableBorrower.sol` (spot `convertToAssets` in `_currentVaultAssets`, unchecked `bufferedVaultDelta`, `totalInterestDueNow` minted as interest) but did not fully trace `IdleCDOEpochVariant.stopEpoch`'s tranche-price update path to confirm the exact minting mechanics — the contract's comments state interest is "minted (not pulled as cash)" and consumed at stop, which supports the impact; a full PoC should confirm whether inflated interest raises `virtualPrice` directly or is capped by actual transfer liquidity at stop.
