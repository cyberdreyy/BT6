### Title
Time-bound equivocation guard uses a fixed local staleness window that real gossip/validation latency can exceed, letting a signer sign a conflicting sibling block at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The signer's double-sign ("equivocation") guard treats a previously signed/pre-committed sibling block as no longer blocking once a fixed wall-clock window (`tenure_last_block_proposal_timeout`, default 30s) has elapsed since that signature was last endorsed. Like the API3 24h heartbeat assumption, this hard-coded freshness window can be exceeded by ordinary propagation delay (StackerDB gossip across the signer set, node validation round-trips, or a slow/partitioned peer) rather than by any malicious majority action, causing the guard to treat a still-live conflicting signature as stale and allow the signer to sign a second, conflicting block at the same height.

### Finding Description
`Signer::store_and_process_block_pre_commit` computes a `freshness_cutoff` purely from the local wall clock and the configured `tenure_last_block_proposal_timeout`: [1](#0-0) 

Only a conflict whose `last_endorsed` timestamp is *after* `freshness_cutoff` is allowed to block signing (subject to `reorg_permit_stands` and `conflict_still_blocks`). Once `last_endorsed` falls behind the cutoff, the conflict is no longer treated as fresh and, per the code path at line 1432 onward, is only re-checked against the node's tenure tip for same-tenure conflicts - a stale conflict in a *different* tenure "no longer speaks for us" at all: [2](#0-1) 

The design doc for this exact mechanism acknowledges the tension: freshness is what allows a dead signature to eventually stop blocking (needed for reorg recovery), but the same mechanism means a signature "must not... outlive the block it protects" while also implicitly assuming it *won't expire while the block is still live*. The window is a fixed timeout, not tied to actual propagation/consensus completion: [3](#0-2) 

The same staleness pattern recurs in `SortitionData::get_tenure_last_block_info`, which drops the last signed block in a tenure from consideration purely because `signed_self.max(signed_group) + tenure_last_block_proposal_timeout <= now`, again a bare wall-clock comparison with no confirmation that the node/network has actually caught up: [4](#0-3) 

In both cases the semantics mirror the reported bug class: a protocol-level guarantee ("we will not sign a second block at this height while our first signature could still be aggregated toward 70%") is protected by a value ("has `tenure_last_block_proposal_timeout` elapsed since we last endorsed a conflicting block") that is assumed to accurately reflect liveness within a fixed interval, but which can silently exceed that interval under normal delay - StackerDB replication across dozens of signers, a slow-to-respond `stacks-node`, or a busy validation queue - without any malicious quorum involved.

### Impact Explanation
If the local freshness window elapses while the earlier signature is still capable of being aggregated to the 70% threshold by other signers (e.g., other signers are still slowly gossiping their acceptance of the first block, or the node has not yet processed it), `conflict_still_blocks`'s "not yet globally accepted, different tenure" branch and the freshness check above can both fail to hold the conflict, letting this signer place a second signature on a sibling block at the same height. If enough signers independently experience the same timing skew, two conflicting blocks at the same Stacks height could each accumulate signatures - a signer signing a conflicting block, which is explicitly listed as a Critical-severity outcome in the rules.

### Likelihood Explanation
This requires no majority of signers, no other signer's key, and no node/auth-token access - only ordinary network/gossip latency (which a single miner delaying/re-timing its proposals, combined with normal StackerDB propagation jitter, can influence) exceeding the fixed `tenure_last_block_proposal_timeout`/`reorg_attempts_activity_timeout` windows (default 30s and 200s respectively, per `sample/conf/signer/mainnet-signer-conf.toml`). The system explicitly documents that these are trade-off values chosen to balance reorg recovery against the equivocation guard, indicating the designers were aware such a race is possible but did not close it with an explicit consensus-confirmation gate.

### Recommendation
Do not let the equivocation guard's freshness window expire based solely on a local wall-clock deadline while the earlier signature could still be canonicalized. Before treating a same-height conflict as stale, confirm via the node (or peer signer state) that the earlier block has either been superseded on-chain or definitively cannot reach the 70% threshold, rather than relying on `tenure_last_block_proposal_timeout` alone as a proxy for "the conflict is dead." At minimum, document and bound the assumption analogous to the heartbeat report: state explicitly that `tenure_last_block_proposal_timeout`/`reorg_attempts_activity_timeout` must be set comfortably larger than worst-case StackerDB propagation + node validation latency, and treat values close to real-world propagation times as unsafe.

Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.

outlive the block it covers: a Bitcoin reorg can kill the block, and a dead
signature must not stall the chain restarting beneath it until it goes stale. So
`conflict_still_blocks` derives, per evaluation, whether the conflict could still
end up in the chain. Deriving this here — instead of recording it when a fork is
observed — is deliberate: the node's view mid-reorg is a moving target (burn

    /// Get the last signed block from the given tenure if it has not timed out.
    /// Even globally accepted blocks are allowed to be timed out, as that
    /// triggers the signer to consult the Stacks node for the latest globally
    /// accepted block. This is needed to handle Bitcoin reorgs correctly.
    ///
    /// The timeout window is measured from the last time a signature actually covered the
    /// block: our own (`signed_self`) or the observed group/global acceptance
    /// (`signed_group`), whichever is later, matching how `get_signed_conflicts` measures
    /// endorsement freshness. `approved_time` is deliberately not used: it is stamped at
    /// pre-commit, which carries no signature, so it would close the window early. This also
    /// means a globally accepted block we never signed ourselves gets a full window from the
    /// time its acceptance was observed, rather than timing out instantly for lack of a
    /// timestamp.
    pub fn get_tenure_last_block_info(
        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
