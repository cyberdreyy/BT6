### Title
Stale confirmations from removed members are not pruned, allowing a multisig request to execute below the live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in the `multisig2` contract only removes pending requests that were *originated* by the deleted member; it never scans other requests' `confirmations` sets to strip a confirmation the deleted member gave on a request originated by someone else. Because `confirm()` counts raw set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without re-validating that every entry in the set still belongs to a current member, a request can be executed using a confirmation from an account that is no longer a multisig member — i.e., "confirmations counted" diverge from "live members," breaking the multisig's authorization equality `confirmations.len() == count(live members who confirmed)`.

### Finding Description
`add_request` records the request together with the `member` that created it [1](#0-0) . `confirm` simply checks the calling member isn't already in the confirmation set and, once the size threshold is hit, executes the request; otherwise it inserts the confirming member into the set [2](#0-1) .

`delete_member`, which is the only cleanup path executed when a member is removed, filters and deletes requests **by matching `r.member == member`** — i.e., only requests the removed member itself originated — and clears confirmations for exactly those requests: [3](#0-2) 

It does not iterate `self.confirmations` to purge the removed member's entry from confirmation sets belonging to *other* members' pending requests. As a result, if member `B` had already confirmed a request originated by member `A`, and `B` is later removed via a `DeleteMember` request, `B`'s stale confirmation stays in that request's `confirmations` set and continues to count toward `num_confirmations` in any future `confirm()` call.

### Impact Explanation
This lets a request execute (e.g., a `Transfer` draining the multisig-controlled account, an `AddKey`/`AddMember` granting a new signer, or a `FunctionCall`) with fewer *live* confirmations than the configured `num_confirmations` threshold, because one or more of the counted confirmations belong to accounts that are no longer members. This directly matches the Critical impact category "a multisig request executed below threshold," since the effective K-of-N guarantee is broken — the request is authorized by fewer than K currently-trusted signers.

### Likelihood Explanation
Exploitation requires no special privilege beyond being (or having been) a legitimate member at confirmation time — a normal operational sequence (member confirms a request, then is later removed for routine reasons such as key rotation or offboarding) is sufficient to leave a stale confirmation in place. No malicious collusion, redeploy, or foundation/owner privilege beyond standard multisig membership management is needed; only the ordering of an ordinary `DeleteMember` execution relative to an outstanding request's confirmations.

### Recommendation
When executing `DeleteMember` (and the equivalent `DeleteKey`/`AddKey`-replacement flows in `multisig`), iterate all outstanding `confirmations` entries and remove the departing member's confirmation from every request, not just requests it originated. Alternatively, re-validate at `confirm()`/execution time that every account in a request's confirmation set is still a current member (e.g., by intersecting the stored set with `self.members`) before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig deployed with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(R)` for a `Transfer` request — `R` now has 1 confirmation (`A`).
3. `B` calls `confirm(R)` — `R` now has 2 confirmations (`A`, `B`); execution still withheld (2 < 3).
4. Separately, `C` and `D` (and one more confirmation) execute a `DeleteMember { member: B }` request, removing `B` from `self.members`. `delete_member` only removes requests where `r.member == B`; since `R.member == A`, `R`'s confirmations set (`{A, B}`) is left untouched [4](#0-3) .
5. `C` (a genuine, still-live member) calls `confirm(R)`. The set becomes `{A, B, C}`, size 3, which satisfies `confirmations.len() as u32 + 1 >= self.num_confirmations` check path and `R` executes the `Transfer` [5](#0-4) .
6. The transfer executes with only 2 live-member confirmations (`A`, `C`) plus one stale confirmation from removed member `B`, even though the contract's live-member threshold is 3.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);

        self.members.remove(&member);

        }
