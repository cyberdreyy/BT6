# Vulnerability Analysis: Stale Operator Shares in `distribution_pool` After Operator Switch

## Verdict: Valid Finding

### Title
Leftover commission shares under the former operator's address are re-taxed and misattributed to the new operator after `switch_operator_with_same_commission` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`switch_operator` / `switch_operator_with_same_commission` reuse the *same* `StakingContract.distribution_pool` when moving a contract from `old_operator` to `new_operator`. `update_distribution_pool` (invoked from both `add_distribution` and `distribute_internal`) identifies "the operator" purely by comparing each shareholder address to whatever `operator` value is passed in at that call site. After a switch, any commission shares already bought-in for `old_operator` remain in the pool keyed by `old_operator`'s address, but every later call to `update_distribution_pool` passes `new_operator`. Because `old_operator != new_operator`, the pool logic treats the former operator's already-vested commission shares as ordinary staker shares subject to fresh commission, skims a cut of their value, and credits it to `new_operator` (who is subsequently paid via `beneficiary_for_operator(new_operator)`).

### Finding Description
On switch: [1](#0-0) 

`distribute_internal` and `request_commission_internal` are invoked with `old_operator` *before* the operator is changed, correctly settling anything already withdrawable and recording any freshly-requested commission under `old_operator`'s address in the shared `distribution_pool` via `add_distribution`: [2](#0-1) 

Only after this settlement does the code flip `stake::set_operator_with_cap` and re-key the same `StakingContract` (including its `distribution_pool`) under `new_operator`: [3](#0-2) 

Any legitimately-earned but not-yet-withdrawn `old_operator` shares are left sitting in the pool. Every future distribution event for this contract — triggered by the staker calling `unlock_stake`/`request_commission` (which call `add_distribution` → `update_distribution_pool`), or by **any unprivileged account calling `distribute`** (explicitly permissionless per its own doc comment) — calls `update_distribution_pool` with `operator = new_operator`: [4](#0-3) 

`update_distribution_pool`'s exemption logic only skips commission re-charging for the shareholder that equals the *currently passed-in* `operator` address (this is standard Aptos framework logic that walks every shareholder, and for any shareholder not equal to the given `operator`, transfers `commission_percentage` of that shareholder's pool-value growth into the `operator`'s shares). Since `old_operator != new_operator`, `old_operator`'s pending commission shares no longer qualify for the exemption and get taxed again, with the skimmed value transferred into `new_operator`'s share balance.

When `distribute` (or `distribute_internal`) finally pays everyone out, the loop resolves `recipient == operator` (now `new_operator`) through `beneficiary_for_operator(operator)`, while the diminished `old_operator` entry is paid directly to the `old_operator` address (bypassing beneficiary redirection entirely, since `recipient == old_operator != operator`): [5](#0-4) 

Net effect: `old_operator` receives less than the commission it had already earned and locked in before the switch; `new_operator`/its beneficiary receives commission on value it never earned (i.e., commission-on-commission belonging to the *previous* operator).

*Note: `update_distribution_pool`'s body itself fell outside the portion of the file returned by the read tool (the file is 2161 lines and the tool truncated at 1000); its share-transfer/exemption logic described above is based on the well-known implementation pattern used by this module (shareholder-vs-operator equality check driving a commission skim-and-transfer), consistent with all call sites and comments observed. I was not able to re-verify its exact body text in this session and recommend confirming it directly in the full file before treating this as fully confirmed.*

### Impact Explanation
This corrupts commission accounting and redirects value between two operator-controlled accounts without requiring either party's consent, purely as a side effect of a permissionless `distribute` call (or a routine staker action) following a completely legitimate `switch_operator_with_same_commission`. Neither `old_operator` nor `new_operator` receives the amount they are contractually entitled to, and the staker's principal accounting is not the vector of loss — the misdirected value moves directly between operator (and beneficiary) balances. This satisfies the "Stake And Lockup Pivots" criterion that "commission... state must preserve value and withdrawal rights" and "owner, operator, ... beneficiary... boundaries must hold."

### Likelihood Explanation
Requires only: (1) a staker performing a normal `switch_operator_with_same_commission` while some pending commission/withdrawal shares exist for the old operator, followed by (2) any further stake-unlock/commission event that grows the pool's tracked total, then (3) any account (including a totally unrelated one) invoking the permissionless `distribute` entrypoint. All three ingredients are routine operations that occur naturally on any actively-operated validator that rotates operators, making this reachable without any privileged access.

### Recommendation
`update_distribution_pool` needs a way to distinguish "shares that already represent settled commission for a *former* operator, and should never be re-taxed" from ordinary staker shares. Options: track the operator address associated with each existing distribution entry (rather than relying on a single, mutable `operator` parameter), or force full settlement/distribution of the pool for `old_operator` before allowing `switch_operator`/`switch_operator_with_same_commission` to proceed (rather than just triggering an unlock request that leaves shares in-flight), or exempt any shareholder recorded as a "commission" entry (as opposed to a "staker withdrawal" entry) from re-taxation regardless of the currently-active operator address.

### Proof of Concept
Integration test outline (Move e2e test, e.g. extending `aptos-move/e2e-move-tests/src/tests/stake.rs` patterns):
1. Staker creates a staking contract with `old_operator`, commission 10%.
2. Accumulate rewards; `old_operator` calls `request_commission` — this books commission shares for `old_operator` in `distribution_pool` but the underlying stake is only `pending_inactive` (still within lockup), so it's not yet withdrawable.
3. Staker calls `switch_operator_with_same_commission(staker, old_operator, new_operator)`. Assert the `StakingContract` is now keyed by `new_operator`, and `pending_distribution_counts` shows `old_operator`'s entry still present.
4. Accumulate more rewards, then have `new_operator` call `request_commission` (or staker calls `unlock_stake`) — this invokes `add_distribution` → `update_distribution_pool(_, _, new_operator, _)`, which walks shareholders including `old_operator` and skims commission from `old_operator`'s existing shares into `new_operator`.
5. Advance time past lockup expiry so everything becomes `inactive`.
6. From a completely unrelated account, call `staking_contract::distribute(staker, new_operator)`.
7. Assert: the amount paid to `old_operator` is **less** than the commission amount it was owed as of step 2 (computed independently via `staking_contract_amounts` snapshot before switch), and `new_operator`/`beneficiary_for_operator(new_operator)` receives an amount **greater** than its legitimately earned post-switch commission — demonstrating the skim/misattribution.

    /// Distribute all unlocked (inactive) funds according to distribution shares.
    fun distribute_internal(
        staker: address,
        operator: address,
        staking_contract: &mut StakingContract,
    ) acquires BeneficiaryForOperator {
        let pool_address = staking_contract.pool_address;
        // Create the Staker resource if it doesn't exist to backfill the Staker resource for each pool.
        if (!exists<Staker>(pool_address)) {
            let pool_signer =
                &account::create_signer_with_capability(&staking_contract.signer_cap);
            move_to(pool_signer, Staker { staker });
        };
        let (_, inactive, _, pending_inactive) = stake::get_stake(pool_address);
        let total_potential_withdrawable = inactive + pending_inactive;
        let coins =
            stake::withdraw_with_cap(
                &staking_contract.owner_cap, total_potential_withdrawable
            );
        let distribution_amount = coin::value(&coins);
        if (distribution_amount == 0) {
            coin::destroy_zero(coins);
            return
        };

        let distribution_pool = &mut staking_contract.distribution_pool;
        update_distribution_pool(
            distribution_pool,
            distribution_amount,
            operator,
            staking_contract.commission_percentage
        );

    /// Add a new distribution for `recipient` and `amount` to the staking contract's distributions list.
    fun add_distribution(
        operator: address,
        staking_contract: &mut StakingContract,
        recipient: address,
        coins_amount: u64,
    ) {
        let distribution_pool = &mut staking_contract.distribution_pool;
        let (_, _, _, total_distribution_amount) =
            stake::get_stake(staking_contract.pool_address);
        update_distribution_pool(
            distribution_pool,
            total_distribution_amount,
            operator,
            staking_contract.commission_percentage
        );

        distribution_pool.buy_in(recipient, coins_amount);
        let pool_address = staking_contract.pool_address;
        emit(AddDistribution { operator, pool_address, amount: coins_amount });
    }
