### Title
Staleness Check Bypass via Unsigned Integer Wraparound in `HandleLegacyUserMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The Web API Capabilities gateway handler's replay/staleness gate mixes a signed, client-controlled timestamp with unsigned arithmetic in a single comparison, exactly the bug class described in the external report (unsafe timestamp-difference comparison assuming well-behaved inputs from two different sources). Here the "two sources" are the gateway's local clock and an attacker-supplied `Timestamp` field, and the unsafe cast lets an unprivileged client trivially defeat the staleness check.

### Finding Description
`HandleLegacyUserMessage` decodes an unprivileged, internet-facing user message into `webapicap.TriggerRequestPayload` and then performs the staleness check: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    ...
    "stale message"
}
``` [2](#0-1) 

`payload.Timestamp` is client-controlled (JSON field parsed from the raw user-supplied payload, tests construct it as an `int64`) [3](#0-2) , while `h.config.MaxAllowedMessageAgeSec` is a `uint` [4](#0-3) .

Only `payload.Timestamp == 0` is rejected [5](#0-4) ; any other value — including a negative one — is accepted and converted with `uint(payload.Timestamp)`. Converting a negative `int64` to `uint` wraps around to a value near `math.MaxUint64`. Since the left-hand side (`uint(time.Now().Unix()) - MaxAllowedMessageAgeSec`) is always a small, ordinary Unix-time-scale number, the comparison `LHS > RHS` can never be true when `RHS` is near `MaxUint64`, so the "stale message" branch is always skipped regardless of the message's real age.

This mirrors the reported bug class exactly: an unguarded subtraction/comparison of two timestamp-like values that assumes both operands are well-formed, non-adversarial, and in a consistent numeric domain. Here the flaw is worse than the original report because the second operand is fully attacker-controlled, turning a staleness *check* into a trivially bypassable no-op.

### Impact Explanation
The staleness gate is the only control on message age in this legacy handler before the message is forwarded to every DON member [6](#0-5) . Bypassing it lets an unprivileged client submit (or replay) trigger messages with fabricated/negative timestamps that are always treated as fresh, defeating the intended anti-replay/age-bounding defense on this internet-facing gateway path (`web_api_trigger`). This is a concrete allowlist/quota-style validation bypass on an unprivileged, gateway-facing endpoint.

### Likelihood Explanation
High. The condition requires only sending a single negative integer in the JSON `Timestamp` field of an otherwise normal request; no authentication bypass, race condition, or special node privileges are needed — any client able to reach the gateway's user-facing HTTP/websocket endpoint for the `web-api-capabilities` handler can trigger it.

### Recommendation
Compare timestamps using a single consistent signed type (or `time.Time`/`time.Duration` with `Sub`), reject negative/implausible `payload.Timestamp` values explicitly, and avoid casting attacker-controlled `int64` values to `uint` before arithmetic comparisons. E.g., validate `payload.Timestamp > 0` and `payload.Timestamp <= time.Now().Unix()`, then use `time.Now().Unix()-payload.Timestamp > int64(h.config.MaxAllowedMessageAgeSec)` (all signed), analogous to the recommended `timestamp() > publish_time + TIMEOUT` style fix in the original report.

### Proof of Concept
1. Craft an `api.Message` whose `Body.Payload` JSON-encodes a `webapicap.TriggerRequestPayload` with `"Timestamp": -1` (any negative value works) and a valid signature.
2. Submit it to the gateway targeting the `web-api-capabilities` handler's `web_api_trigger` method, invoking `HandleLegacyUserMessage`.
3. The `payload.Timestamp == 0` check passes through (value is `-1`, not `0`).
4. In the staleness check, `uint(payload.Timestamp)` becomes `18446744073709551615` (wrapped from `-1`), so `uint(time.Now().Unix()) - MaxAllowedMessageAgeSec > 18446744073709551615` is always `false`.
5. The message is accepted as "fresh" and forwarded to all DON members regardless of its actual timestamp, confirming the staleness control is bypassed.

func (h *handler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback handlers.Callback) error {
	body := msg.Body
	var payload webapicap.TriggerRequestPayload
	codec := api.JsonRPCCodec{}
	err := json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw(ErrDecodingPayload, "err", err)
		return callback.SendResponse(handlers.UserCallbackPayload{
			RawResponse: codec.EncodeNewErrorResponse(
				msg.Body.MessageId,
				api.ToJSONRPCErrorCode(api.UserMessageParseError),
				ErrDecodingPayload+" "+err.Error(),
				nil,
			),
			ErrorCode: api.UserMessageParseError,
		})
	}
