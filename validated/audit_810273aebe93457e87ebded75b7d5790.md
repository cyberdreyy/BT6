### Title
Symlink target (`Linkname`) is not validated and pre-existing symlinks are followed by `os.Create`, allowing cross-extraction arbitrary-file-write via a persisted symlink in a reused cache/artifact directory - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`extractor.Extract` only validates that the resolved *entry path* (`hdr.Name`) stays inside `e.dir`; it never validates the symlink *target* (`hdr.Linkname`), and it creates regular-file entries with `os.Create`, which transparently follows any pre-existing symlink at that path rather than refusing or replacing it. Because cache/artifact extraction directories are reused across job/pipeline runs without being wiped by default, an attacker can plant a symlink in one extraction and have a later extraction's "regular file" write dereference through it to an arbitrary filesystem location.

### Finding Description
The path-escape check only covers `hdr.Name`: [1](#0-0) 

Symlink entries are deferred and created later with no restriction on `hdr.Linkname` (the symlink target): [2](#0-1) [3](#0-2) 

Regular files are written with plain `os.Create`, which on Unix follows an existing symlink at that path instead of rejecting it or replacing it atomically (`O_NOFOLLOW`/`os.Lstat` pre-check is absent): [4](#0-3) 

Within a single `Extract()` call, if a symlink and a regular-file entry share the same resolved path, the ordering matters but does not enable a silent bypass as literally described in the question: if the symlink entry comes first, it is only recorded in `deferred` (not yet created on disk), so a same-run `os.Create` for the same path just creates a normal file; the later `os.Symlink` call in the finalize loop then fails with `EEXIST` because a real file already occupies the path, aborting extraction. So the "deferred map silently overwritten within one archive" framing in the question is not accurate for a single extraction pass.

The real, exploitable variant is across separate extraction cycles into the *same* directory, which is exactly how cache extraction works: cache archives are downloaded and extracted into `info.Build.CacheDir` keyed by cache key, and the directory is **not** cleared before extraction by default - it is only removed on a *failed* extraction, and only when `FF_CLEAN_UP_FAILED_CACHE_EXTRACT` is enabled (default `false`): [5](#0-4) 

Given that precondition, the exploit flow is:
1. Job N (attacker-controlled pipeline) pushes/extracts a cache archive containing a symlink entry `Name: "foo"`, `Linkname: "/some/outside/target"` (or a `../../` escaping relative target). The `hdr.Name` check only inspects where `foo` will be created (inside `e.dir`), never `Linkname`, so `os.Symlink(hdr.Linkname, path)` succeeds and leaves a real symlink `foo -> /some/outside/target` on disk after `Extract()` returns.
2. A later extraction into the same cache directory (a later job/pipeline run reusing the same cache key, or a fallback-cache extraction) contains a regular file entry also named `foo`. `os.Create(path)` for `foo` dereferences the pre-existing symlink and writes the attacker-supplied file content through it into `/some/outside/target`.

Existing protections do not stop this: the chroot check only bounds `hdr.Name`, not `hdr.Linkname`; there is no `os.Lstat`/`O_NOFOLLOW` guard before `os.Create`; and cache directories are not wiped between successful extractions.

### Impact Explanation
An unprivileged pipeline author who controls two extraction cycles into the same cache/artifact directory (trivial, since caches are keyed and reused by design) can achieve an arbitrary-file-write outside the intended cache/build root, limited to paths writable by the job/runner user. This is a genuine break of the "file operations must stay within intended build/cache/artifact roots" invariant.

### Likelihood Explanation
Feasible and repeatable: creating a cache with a symlink entry and later a cache (or fallback cache) with a same-named regular file is fully within a normal user's control via `.gitlab-ci.yml` cache configuration and job scripts staging arbitrary files under the cache paths before the cache-archiver runs. No admin action or timing race is required - it only depends on the cache directory not being wiped between runs, which is the default behavior.

### Recommendation
- Validate `hdr.Linkname` for symlink entries the same way `hdr.Name` is validated (resolve and require the final target to stay within `e.dir`, or reject absolute/`..`-escaping targets outright).
- Before writing a regular file, `os.Lstat` the destination path and, if it is a symlink (or any non-regular file) left over from a prior extraction, remove it first (or open with `O_NOFOLLOW`) instead of letting `os.Create` transparently follow it.
- Apply the equivalent fix to the deferred-symlink finalize loop so re-extraction into a stale directory can't leave/inherit unexpected filesystem entries.

### Proof of Concept
Go test in `tarzstd` package:
```go
func TestExtract_SymlinkPersistsAcrossRuns(t *testing.T) {
    dir := t.TempDir()
    outside := filepath.Join(t.TempDir(), "victim")
    require.NoError(t, os.WriteFile(outside, []byte("original"), 0644))

    // Run 1: archive containing only a symlink foo -> outside
    buf1 := buildTarZstd(t, []tarEntry{{name: "foo", symlink: outside}})
    ext1, _ := NewExtractor(bytes.NewReader(buf1), int64(len(buf1)), dir)
    require.NoError(t, ext1.Extract(context.Background()))

    fi, err := os.Lstat(filepath.Join(dir, "foo"))
    require.NoError(t, err)
    require.True(t, fi.Mode()&os.ModeSymlink != 0) // symlink persisted

    // Run 2 (simulating cache reuse, no cleanup): archive with regular file foo
    buf2 := buildTarZstd(t, []tarEntry{{name: "foo", content: "attacker-content"}})
    ext2, _ := NewExtractor(bytes.NewReader(buf2), int64(len(buf2)), dir)
    require.NoError(t, ext2.Extract(context.Background()))

    // Assert the write went through the symlink to the outside target
    got, _ := os.ReadFile(outside)
    require.NotEqual(t, "attacker-content", string(got), "extractor must not write through a pre-existing symlink to a path outside the extraction root")
}
```
Expected (fixed) behavior: the second `Extract` either rejects the stale symlink at `foo`, removes it and creates a fresh regular file inside `dir`, or errors out - and `outside` retains its original content in all cases.
