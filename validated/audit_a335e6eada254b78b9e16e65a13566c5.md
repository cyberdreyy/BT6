### Title
Loss-adjusted withdraw funding is haircut only for the funding epoch, letting earlier-epoch receipts claim at par and leaving later claimants unpayable - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
When a `stopEpochWithDuration`-style loss is realized, `collectWithdrawFunds` computes a single `lossRecoveryPrice` over the *aggregate* `pendingWithdraws` basis — which includes receipts created in many different request epochs — but stores it under `lossRecoveryPriceByEpoch[epochNumber]` (the funding epoch). At claim time, `_claimLossAdjustedWithdrawRequest` looks up the recovery price by the user's *own* `lastWithdrawRequest` epoch. Only users whose last request was made in the exact funding epoch are haircut; every user whose pending receipt was created in an earlier epoch falls through to `_claimFundedWithdrawRequest` and is paid at par. The strategy therefore pays out more underlying than the borrower actually funded, so the reserve drains early and the remaining (correctly haircut) claimants' transfers revert.

### Finding Description
In `IdleCreditVault.collectWithdrawFunds`, a partial funding sets `pendingWithdraws = 0` and records `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, where `pendingBasis` is the aggregate of *all* pending receipts across all epochs [1](#0-0) .

At claim time, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the user's request epoch, not the funding epoch [2](#0-1) . `lastWithdrawRequest[_user]` is set to `currentEpoch` at request time [3](#0-2) , so a user who requested in epoch E1 and never re-requested sees `lossRecoveryPriceByEpoch[E1] == 0`, skips the loss path entirely, and claims the full par amount via `_claimFundedWithdrawRequest` (the gate `epochNumber <= lastWithdrawRequest` passes since `epochNumber` is already E2) [4](#0-3) .

Additionally, `_clearWithdrawClaimForEpoch` only clears `withdrawsRequestsByEpoch[_user][_claimEpoch]` and decrements `withdrawsRequests[_user]` by that single epoch's amount [5](#0-4) . A user with receipts in both E1 and E2 (allowed — a second request is permitted since no loss price existed at E1 at that time; the block in `requestWithdraw` only fires when `lossRecoveryPriceByEpoch[lastWithdrawRequest] != 0` [6](#0-5) ) receives the haircut only on the E2 piece and par on the E1 piece.

Since `_amount` transferred in by `collectWithdrawFunds` equals `lossRecoveryPrice * pendingBasis` — i.e., funding sized assuming *every* pending receipt is haircut — paying any receipt at par overpays relative to funded backing. The par-paid claimants are favored (an unprivileged user can deliberately hold an older-epoch receipt to capture this), and the last claimants' `_transferFundedClaim` calls revert on insufficient balance [7](#0-6) .

### Impact Explanation
Broken invariant: solvency of the funded-withdraw reserve. The aggregate funded amount is `recoveryPrice * pendingBasis`, but payouts are `recoveryPrice * (claims from funding epoch) + 1.0 * (claims from earlier epochs)`. Every earlier-epoch receipt drains `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL` more than was funded. Result: direct theft of the funded reserve by early claimants and permanent freezing of the remaining haircut claims (revert on every `claimWithdrawRequest` until the shortfall is covered externally). The shortfall equals the total basis share of non-funding-epoch receipts times the haircut — e.g., with a 50% recovery price and half the pending basis in earlier epochs, ~25% of pending receipts become unpayable.

### Likelihood Explanation
Requires: (a) a borrower repayment shortfall at `stopEpochWithDuration` so `collectWithdrawFunds` is called with `_amount < pendingWithdraws` — an honest manager action sequencing a real credit loss, which is the designed purpose of the loss path; and (b) at least one pending receipt whose `lastWithdrawRequest` epoch differs from the funding epoch, which is the normal case whenever a user requested a withdrawal and did not re-request in the same epoch the loss lands (receipts routinely span multiple epochs per the "wait for another epoch to claim both requests" note). No attacker privilege is needed beyond holding a tranche token and calling `requestWithdraw`/`claimWithdrawRequest`. The existing guards do not stop it: the epoch-marker check in `requestWithdraw` only blocks new requests *after* a loss price exists, and `epochEndDate` gating in `_claimFundedWithdrawRequest` passes because `epochNumber` has already advanced. Like the referenced CVE, exploitation difficulty is moderate (AC:H — depends on a loss epoch and epoch alignment), matching a Medium rating.

### Recommendation
Apply the loss-recovery haircut to the aggregate claim, not only to the funding-epoch slice. Concretely, either store the recovery price keyed by a global "pending bucket" marker (e.g., `lossRecoveryPrice` applied to `withdrawsRequests[_user]` and open `apr0Users` principal regardless of request epoch), or in `claimWithdrawRequest` first check whether `pendingWithdraws` was cleared via a loss epoch and route *all* outstanding per-epoch claims for the user through the haircut path, clearing every `withdrawsRequestsByEpoch` entry and APR0 bucket. Alternatively, track pending receipts per request epoch globally so `collectWithdrawFunds` can compute a per-epoch price and store it under each contributing epoch.

### Proof of Concept
Foundry fork scenario (against `contracts/strategies/idle/IdleCreditVault.sol` and `contracts/IdleCDOEpochVariant.sol`):

```solidity
// Setup: USDC underlying, AA tranche, standard epoch variant.
// attacker = KYC'd lender, manager = honest.

// 1) Epoch E1: attacker and victim each deposit 100k USDC AA.
//    Manager startEpoch(). During buffer both call requestWithdraw(full, AA).
//    Neither claims after stopEpoch #1 (claims wait one epoch).
//    epochNumber == E1+1 at this point; both have
//    withdrawsRequestsByEpoch[user][E1] = amount, lastWithdrawRequest = E1.

// 2) Victim re-requests in E2 buffer (allowed:
//    lossRecoveryPriceByEpoch[E1] == 0), moving
//    lastWithdrawRequest[victim] -> E2 while his E1 receipt also remains
//    if he had a second tranche position; attacker keeps lastWithdrawRequest = E1.

// 3) Epoch E2 runs; borrower repays only 50% of pendingWithdraws at
//    stopEpochWithDuration -> collectWithdrawFunds(_amount = pendingBasis/2):
//    lossRecoveryPriceByEpoch[E2] = RECOVERY_FULL/2, pendingWithdraws = 0.
//    Strategy received only pendingBasis/2 underlying.

// 4) attacker.claimWithdrawRequest():
//    _claimLossAdjustedWithdrawRequest: lossRecoveryPriceByEpoch[E1] == 0 -> skips.
//    _claimFundedWithdrawRequest: epochNumber (E2) > lastWithdrawRequest (E1)
//    -> pays FULL par amount.
//    Attacker receives ~2x what the reserve funded for him.

// 5) victim.claimWithdrawRequest(): his E2 receipt pays haircut*E2_basis,
//    then _claimFundedWithdrawRequest tries to pay his par E1 receipt ->
//    safeTransfer reverts (balance < amount) once reserve is drained.
//    Remaining claimants' withdrawals are permanently frozen.

// Assert: attacker.balanceOf(underlying) == full request amount (not half);
// assert: victim claim reverts on underlying transfer.
```

Note: exact exploit arithmetic depends on `pendingBasis` composition (normal vs APR0 buckets) and on how `stopEpochWithDuration` computes `pendingToFund` via `previewLossAdjustedWithdrawFunds`; I verified the claim-side keying mismatch (`lossRecoveryPriceByEpoch` stored under `epochNumber` vs read under `lastWithdrawRequest`) directly in the source, but the precise CDO-side funding call sequence should be confirmed when writing the runnable test.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
