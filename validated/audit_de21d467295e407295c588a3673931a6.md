### Title
Missing fee-amount validation in `createDstEscrow` causes underflow revert freezing destination withdrawals - (File: contracts/BaseEscrowFactory.sol / contracts/EscrowDst.sol)

### Summary
The external report describes `maxDeposit` reverting from an unchecked subtraction (`mintCap - totalSupply`) that can go negative. The same root cause — an unchecked subtraction of admin/caller-supplied values used later in a critical path — exists in the destination-escrow withdrawal flow of this repo. `EscrowDst._withdraw` computes `immutables.amount - integratorFeeAmount - protocolFeeAmount` without ever validating that the fee amounts don't exceed the escrowed amount, and the `createDstEscrow` entry point that seeds these values does not perform the same guard that exists on the source path.

### Finding Description
On the source path, `BaseEscrowFactory._postInteraction` explicitly guards against fee amounts exceeding the swap amount: [1](#0-0) 

However, `createDstEscrow` takes `dstImmutables` directly from calldata — including the `parameters` field that encodes `protocolFeeAmount` and `integratorFeeAmount` — and performs **no equivalent check**: [2](#0-1) 

Any caller (an unprivileged taker/resolver) invoking `createDstEscrow` can supply `Immutables.parameters` encoding `integratorFeeAmount + protocolFeeAmount > immutables.amount`. The factory only checks `msg.value`/token transfer for `immutables.amount`; it never cross-checks the embedded fee parameters.

Later, when anyone attempts to withdraw from that destination escrow, `EscrowDst._withdraw` performs: [3](#0-2) 

Since `integratorFeeAmount + protocolFeeAmount > immutables.amount`, line 92 (`immutables.amount - integratorFeeAmount - protocolFeeAmount`) underflows and reverts under Solidity 0.8's checked arithmetic — for every call, in both the private (`withdraw`) and public (`publicWithdraw`) windows, since both funnel into `_withdraw`.

### Impact Explanation
Once a destination escrow is deployed with a corrupted fee/amount relationship, the maker can never successfully call `withdraw`/`publicWithdraw` — every attempt reverts due to underflow. The only remaining path is `cancel`, which returns funds to the taker after the cancellation timelock elapses, meaning the maker's expected receipt of destination funds is blocked for the entire withdrawal window of the swap lifecycle. This matches the bounty's Medium/High category of "smart contract unable to operate ... broken by an unprivileged actor" / "temporary freezing of funds during the live swap lifecycle," since the taker who deploys the escrow controls the malformed `parameters` and can grief the maker's leg of the swap.

### Likelihood Explanation
Likelihood is bounded by the fact that the taker (who deploys `createDstEscrow` and funds it) is generally the same party whose own capital would be tied up, so a purely selfish attacker gains nothing directly — however, they can still deliberately corrupt a specific counterparty's (maker's) expected withdrawal, since `cancel()` returns the amount to the taker/resolver, not the maker, making it a viable griefing vector against makers with no cost recovery beyond delay. The absence of any validation in `createDstEscrow` — while an equivalent check exists on the source side — indicates this is a genuine, reachable, unprivileged-triggerable gap rather than a theoretical one.

### Recommendation
Add a check in `createDstEscrow` mirroring the source-side guard, e.g.:
```solidity
(uint256 protocolFeeAmount, uint256 integratorFeeAmount,,) = abi.decode(dstImmutables.parameters, (uint256, uint256, address, address));
if (protocolFeeAmount + integratorFeeAmount >= dstImmutables.amount) revert InvalidFeeAmounts();
```
Alternatively, harden `EscrowDst._withdraw` to clamp/return early (or revert with a clear, recoverable error before fund transfers) rather than allowing an unchecked subtraction to underflow, and consider validating consistency between the fee parameters emitted from `_postInteraction` (`immutablesComplement.parameters`) and what is ultimately submitted to `createDstEscrow`.

### Proof of Concept
1. A resolver (unprivileged taker) calls `createDstEscrow` directly with `dstImmutables.amount = 100`, `dstImmutables.parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (sum `120 > 100`), and correct safety deposit/token transfer amounts to satisfy the `msg.value`/`safeTransferFrom` checks in `createDstEscrow`.
2. `createDstEscrow` succeeds because it never validates the encoded fee amounts against `immutables.amount`. [2](#0-1) 
3. Once the withdrawal window opens, any call to `EscrowDst.withdraw`/`publicWithdraw` reaches `_withdraw`, where `immutables.amount - integratorFeeAmount - protocolFeeAmount` (`100 - 60 - 60`) underflows and reverts. [4](#0-3) 
4. The maker can never withdraw; the only recovery is `cancel()` after the cancellation timelock, which returns funds to the taker — not the maker — freezing the maker's expected receipt for the entire live-swap withdrawal period.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);

        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
