## Analysis

The external report's bug class is: a settlement mechanism that is supposed to gate a payout on a validated/attested quantity computed "at the right time," but falls back to an unconditional value when the normal window has elapsed due to delay — silently dropping the validation gate instead of pinning to a safe stored value.

The `gloas` fork's builder-payment settlement in `specs/gloas/beacon-chain.md` reproduces exactly this pattern.

### Title
Builder payment quorum gate is silently bypassed when parent-payload settlement is delayed beyond one epoch - (File: specs/gloas/beacon-chain.md)

### Summary
`process_builder_pending_payments` only pays a builder if enough attester weight (`payment.weight >= quorum`) accumulated for that slot within the epoch window. But `apply_parent_execution_payload`, which is called when a parent block's payload is finally imported, only routes through this quorum check if the parent is at most one epoch old. If the parent is older (its `builder_pending_payments` entry has already been evicted by `process_builder_pending_payments`), the code unconditionally creates a `BuilderPendingWithdrawal` for the full `parent_bid.value`, with no reference to `payment.weight` or the quorum threshold at all.

### Finding Description
`get_builder_payment_quorum_threshold` and `process_builder_pending_payments` define the intended rule: a builder's payment is only settled if the weight of same-slot attestations that saw the payload meets a quorum computed from total active balance. [1](#0-0) [2](#0-1) 

`apply_parent_execution_payload` settles the payment for the previous block's payload. When the parent is in the current or previous epoch, it calls `settle_builder_payment`, which pays out only if `payment.withdrawal.amount > 0` was already gated by the epoch-processing quorum check above: [3](#0-2) 

But when the parent's payload is imported after the payment entry has aged out of the `builder_pending_payments` buffer (i.e. `parent_epoch` is older than `get_previous_epoch(state)`), the code takes a third branch that pays the builder's full bid value directly, with **no weight/quorum check whatsoever**: [4](#0-3) 

The quorum check exists specifically to require that a sufficient fraction of the active validator set actually attested to (i.e., confirms availability/inclusion of) the payload before the builder is paid. The fallback branch removes that requirement entirely as soon as import of the parent payload is delayed by two or more epochs — which happens naturally whenever consecutive blocks are missed (the very "keeper/network outage" scenario the external report describes), since `process_parent_execution_payload` defers importing the payload of the *previous non-empty block* to the *next block whose parent hash matches*, however far away that is: [5](#0-4) 

The existing test suite documents this exact behavior and its rationale, but only from the perspective of "guaranteeing the builder gets paid" — it does not consider that this simultaneously guarantees payment with **zero** attestation weight: [6](#0-5) 

In that test, the pending payment's `weight` is `0` (no attestations were ever recorded against it, since blocks were missed), which is far below any nonzero quorum threshold — yet after the 2-epoch gap, `apply_parent_execution_payload`'s third branch pays the builder the full bid value regardless.

### Impact Explanation
This breaks the intended equality that a builder is paid `bid.value` **only if** `payment.weight >= get_builder_payment_quorum_threshold(state)`. Under the eviction/fallback path, `bid.value` is paid unconditionally, i.e. for `weight` as low as `0`. This is a builder payment made without the safety condition the protocol commits to elsewhere in the same mechanism — a payment "escaping" its quorum gate, matching the High-severity class "a builder payment ... misdirected, doubled or escaped."

Practically: any proposer/attester coalition (or just naturally missed slots from network conditions) that causes a gap of ≥2 epochs between a builder's payload commitment and its next canonical child block guarantees that builder's payment regardless of whether the network actually confirmed the payload was delivered with quorum support. This removes the economic backstop the quorum mechanism was designed to provide, silently, exactly the same "silent fallback to an unchecked value after a delay" pattern flagged in the external report.

### Likelihood Explanation
No malicious coordination is strictly required — any period of two or more consecutive missed epochs (which does happen on ethereum mainnet, and is explicitly the scenario the external report calls out: "keepers offline" / "network halted") triggers this branch for whatever parent payload was last pending. A single proposer choosing to build on a stale FULL parent after a 2+ epoch gap can also deliberately trigger it. This makes the condition plausible without requiring a large-stake coalition.

### Recommendation
Do not unconditionally pay out `parent_bid.value` in the "evicted" branch of `apply_parent_execution_payload`. Instead, before the payment record is evicted from `builder_pending_payments` in `process_builder_pending_payments`, either (a) extend the retention window so aged-out entries are never possible before settlement, or (b) persist enough information (weight vs. quorum outcome) alongside the eviction so that `apply_parent_execution_payload`'s fallback branch can honor the same quorum condition rather than defaulting to "always pay."

### Proof of Concept
1. Builder submits a bid with nonzero `value` for slot `N`; block `N` is proposed and the payload is FULL, creating a `BuilderPendingPayment` with `weight = 0` (matching `test_builder_payment_after_missed_epochs`).
2. No attestations are recorded for slot `N`'s payload (e.g., due to missed subsequent blocks), so `weight` stays at `0`, far below `get_builder_payment_quorum_threshold(state)`.
3. Two epoch boundaries pass with no blocks importing the payment (`process_builder_pending_payments` rotates and then evicts the entry, since `weight < quorum`).
4. A later block (slot `N + 2*SLOTS_PER_EPOCH + 1` or later) is built with `parent_block_hash` matching the original FULL parent; `process_parent_execution_payload` → `apply_parent_execution_payload` runs, `parent_epoch` is older than `get_previous_epoch(state)`, so the `elif parent_bid.value > 0` branch fires and appends a `BuilderPendingWithdrawal` for the full `value` — with no reference to the quorum outcome from step 3.
5. The builder is paid in full despite `weight = 0`, directly reproducible via `tests/core/pyspec/eth_consensus_specs/test/gloas/sanity/test_blocks.py::test_builder_payment_after_missed_epochs`.

def get_builder_payment_quorum_threshold(state: BeaconState) -> Uint64:
    """
    Calculate the quorum threshold for builder payments.
    """
    per_slot_balance = get_total_active_balance(state) // Uint64(SLOTS_PER_EPOCH)
    quorum = per_slot_balance * BUILDER_PAYMENT_THRESHOLD_NUMERATOR

def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def process_parent_execution_payload(state: BeaconState, block: BeaconBlock) -> None:
    bid = block.body.signed_execution_payload_bid.message
    parent_bid = state.latest_execution_payload_bid
    requests = block.body.parent_execution_requests

    if bid.parent_block_hash != parent_bid.block_hash:
        # Parent was EMPTY -- no execution requests expected
        assert requests == ExecutionRequests.empty()
        return

    # Parent was FULL -- verify the bid commitment and apply the payload
    assert hash_tree_root(requests) == parent_bid.execution_requests_root
    apply_parent_execution_payload(state, requests)
