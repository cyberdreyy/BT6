### Title
Write-call boundary can desynchronize `URLSanitizer`'s key matcher, causing `x-amz-security-token` (and any max-length token key) to leak unmasked - ([File: common/buildlogger/internal/urlsanitizer/urlsanitizer.go])

### Summary
`URLSanitizer.Write` maintains cross-call state in `s.match`, and resets it only at the top of its scan loop when `len(s.match) == cap(s.match)`. If a `Write` call ends exactly when the byte-by-byte key-accumulation path pushes `len(s.match)` to `cap(s.match)` (which happens only for the longest known key, `x-amz-security-token`, 20 chars + leading `?`/`&` = 21 = cap), the `for n < len(p)` loop exits via its outer condition without re-entering the body, so the reset check never runs in that call. The *next* `Write` call's very first loop iteration performs that reset unconditionally, before it has a chance to see the `=` that immediately follows in the new buffer, discarding the fully-buffered key name and causing the STS session-token value to be written to the trace unmasked.

### Finding Description
`New()` sizes `s.match`'s capacity to `max(len(token)) + 1` [1](#0-0)  — for the current `tokenParamKeys` set this is `len("x-amz-security-token")+1 = 21`, exactly the length of `"?"+"x-amz-security-token"`.

In `Write`, when no `=?&` is found in the remainder of the current chunk, characters are appended to `s.match` one at a time via the `off == -1` branch, with the `len(s.match) == cap(s.match)` reset check only evaluated at the *top* of each loop iteration: [2](#0-1) 

If a chunk boundary falls exactly after the last character of `x-amz-security-token` (before its `=`), the byte-by-byte loop appends the final character, bringing `len(s.match)` to 21, then increments `n` to `len(p)`; the outer `for n < len(p)` condition becomes false and the loop exits **without** re-executing the reset check. `s.match` (a struct field, persisted across `Write` calls) is left holding the complete, un-resolved key candidate at exactly `cap`.

On the next `Write` call — whose buffer begins with `=SECRETVALUE...` — the very first thing executed is the unconditional reset at line 82-84, which discards the buffered `"?x-amz-security-token"` candidate *before* the code can see that `=` is the very next byte. The state machine then falls into the fast path (`len(s.match)==0`) and simply scans for the next `?`/`&`, writing the intervening `=SECRETVALUE...` straight to the underlying writer unmasked. In a single, unsplit write of the same bytes, `bytes.IndexAny(p[n:], "=?&")` would find the `=` immediately (at offset 20 from the byte after `?`), taking the direct-match branch instead of the byte-by-byte path, so the token would be correctly recognized and masked (lines 104-141). Splitting therefore produces different output than an unsplit write of identical content — the exact divergence the existing `TestMasking` split-tests (with `|`) do not probe, because none of the crafted `|`-split cases land exactly on this `cap`-boundary for `x-amz-security-token`.

This bug is specific to `x-amz-security-token` (the only entry whose `len(token)+1` equals `cap(s.match)`); shorter keys like `private_token` or `x-amz-credential` never reach `cap` while their own name is being accumulated, so they are not affected by this exact mechanism.

`URLSanitizer` sits directly in the job trace write path (`Logger.wrap`), applied to every stream written through the executor's stdout/stderr wiring: [3](#0-2) . Any output that reaches the trace — including job stdout/stderr echoed by `docker`/`kubernetes`/`shell` executors, or Runner-emitted debug/error text containing a presigned S3 URL — is chunked into `Write` calls by whatever reader relays the underlying stream, and the byte offset of that chunking is influenced by how much output the job itself produces before the sensitive URL (e.g., padding stdout so the pipe/log-stream read boundary lands on the vulnerable offset).

### Impact Explanation
If a GitLab-managed S3-compatible cache/artifact backend uses AWS STS temporary credentials for presigned upload/download URLs (which include `x-amz-security-token` alongside `x-amz-credential`/`x-amz-signature`), and that URL is echoed into the job trace (e.g., via a failed cache/artifact operation's error text, or a job's own debug output of a URL it obtained), triggering this exact write-split leaves the STS session token unmasked in the persisted trace while the surrounding `x-amz-credential`/`x-amz-signature` params (shorter keys, unaffected by this bug) remain masked. Depending on how the presigned URL's credentials are scoped, an attacker capturing the leaked session token could gain unauthorized read/write access to cache or artifact objects.

### Likelihood Explanation
This requires (1) a presigned URL containing `x-amz-security-token` to appear in job trace output, and (2) the read/write chunking of that output to align to the specific byte offset where `s.match` fills to exactly `cap(s.match)=21` at a `Write()` boundary. Condition (2) is influenceable by an unprivileged job that controls the volume/timing of its own stdout output preceding the sensitive text, though exact byte-level control depends on the executor's stdout piping/buffering behavior and isn't guaranteed on every code path. This is a real, deterministic logic bug in the state machine (independent of any single Write-chunk trick), reproducible in a unit test with full control over chunk boundaries, though real-world exploitation requires condition (1) plus practical control (or repeated attempts) over condition (2).

### Recommendation
Only reset `s.match` when it is known to be unresolved (i.e., re-check for `=?&` immediately upon entering a new `Write` call before applying the `len==cap` reset), or move the cap-reset decision to occur only after confirming no `=` immediately follows in the new buffer — e.g., attempt the key-name/`=` lookup first using the carried-over `s.match`, and only reset to `[:0]` if that lookup fails to find `=` within the newly available bytes and the combined length still exceeds `cap`. Add a targeted unit test that feeds `?x-amz-security-token` and `=SECRET` as two separate `Write()` calls (i.e., split precisely after the key name, before `=`) and asserts the output equals the masked single-write result.

### Proof of Concept
```go
func TestMasking_SplitAtCapBoundary(t *testing.T) {
    input := "?x-amz-security-token=SECRETVALUE"
    // split exactly after "x-amz-security-token" (21 bytes incl. leading '?'), before '='
    part1 := input[:21] // "?x-amz-security-token"
    part2 := input[21:] // "=SECRETVALUE"

    buf := new(bytes.Buffer)
    m := New(internal.NewNopCloser(buf))

    n, err := m.Write([]byte(part1))
    require.NoError(t, err)
    assert.Equal(t, len(part1), n)

    n, err = m.Write([]byte(part2))
    require.NoError(t, err)
    assert.Equal(t, len(part2), n)

    require.NoError(t, m.Close())
    assert.Equal(t, "?x-amz-security-token=[MASKED]", buf.String())
}
```
Expected: this test fails on the current implementation (the token value `SECRETVALUE` is written unmasked) while the equivalent single-write call (`m.Write([]byte(input))`) correctly masks it — demonstrating output divergence between split and unsplit writes of identical content.

// New returns a new URL Sanitizer.
func New(w io.WriteCloser) *URLSanitizer {
	var max int
	for token := range tokenParamKeys {
		if len(token) > max {
			max = len(token) + 1
		}
	}

	return &URLSanitizer{w: w, match: make([]byte, 0, max)}
}

// wrap wraps the underlying writer with "filters". Order here somewhat
// matters, and the order they're instantiated in is the reverse order in which
// writes are processed, e.g. last added filter is the first to process data.
//
// order:
// - sync writer to ensure that multiple writes cannot happen concurrently
// - mask phrases (masker.New)
// - mask sensitive URL parameters (urlsanitizer.New)
// - mask secrets with a prefixed token (tokentanitizer.New)
// - split log lines and add timestamps (timestamper.New)
func (l *Logger) wrap(w io.WriteCloser, streamID int, streamType StreamType) io.WriteCloser {
	if l.timestamping {
		w = timestamper.New(w, timestamper.StreamType(streamType), uint8(streamID), true)
	}

	w = tokensanitizer.New(w, l.maskTokenPrefixes)
	w = urlsanitizer.New(w)
	w = masker.New(w, l.maskPhrases)
	w = internal.NewSync(w)

	return w
}
