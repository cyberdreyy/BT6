### Title
Unbounded `getProgramAccounts` result set via secondary-indexed scan when `scan_results_limit_bytes` is unset by default - ([File: rpc/src/rpc.rs])

### Summary
When an operator enables a secondary account index (`AccountIndex::ProgramId` or `AccountIndex::SplTokenOwner`), `JsonRpcRequestProcessor::get_filtered_indexed_accounts` passes `self.config.scan_results_limit_bytes` as the `byte_limit_for_scan` to `Bank::get_filtered_indexed_accounts` / `Accounts::load_by_index_key_with_filter`. This value is an `Option<usize>` that is `None` unless the operator explicitly also passes `--accounts-index-scan-results-limit-mb`, so by default a single `getProgramAccounts` call can force the validator to materialize a `Vec<KeyedAccountSharedData>` sized to however many attacker-created accounts exist under the indexed program/owner key, with no cap applied before the RPC response is built.

### Finding Description
The relevant call chain is:
`rpc/src/rpc.rs::get_program_accounts` → `get_filtered_program_accounts` / `get_filtered_spl_token_accounts_by_owner` → `JsonRpcRequestProcessor::get_filtered_indexed_accounts` (`rpc/src/rpc.rs:309-347`) → `Bank::get_filtered_indexed_accounts` (`runtime/src/bank.rs:5134-5147`) → `Accounts::load_by_index_key_with_filter` (`accounts-db/src/accounts.rs:396-433`) → `AccountsDb::index_scan_accounts` (`accounts-db/src/accounts_db.rs:3358-3421`).

`get_filtered_indexed_accounts` in `rpc.rs` reads the limit as `let byte_limit_for_scans = self.config.scan_results_limit_bytes;` [1](#0-0)  and forwards it unchanged into the scan. Inside `Accounts::load_by_index_key_with_filter`, the enforcement is entirely gated on this being `Some`: [2](#0-1) 
If `byte_limit_for_scan` is `None`, `accumulate_and_check_scan_result_size` always returns `false`, so `config.abort()` is never called and the scan never aborts, meaning `index_scan_accounts` iterates every pubkey returned by `self.accounts_index.get_index_key_pubkeys(&index_key)` [3](#0-2)  and loads/collects every matching account into `collector` with no cap.

Whether `byte_limit_for_scans` is `Some` or `None` depends entirely on the CLI flag `--accounts-index-scan-results-limit-mb`, which has no `.default_value(...)` set, so `value_t!(matches, "accounts_index_scan_results_limit_mb", usize).ok()` yields `None` unless the operator explicitly supplies it: [4](#0-3) [5](#0-4) 

Since the audited scope explicitly starts from "when `AccountIndex::ProgramId` or `SplTokenOwner` is enabled" (a legitimate, documented feature independent of the scan-size limit flag), and the scan-size limit is a separate, non-default flag, a validator running with secondary indexing enabled but without also setting `--accounts-index-scan-results-limit-mb` (the out-of-the-box behavior) has no bound on the number of accounts a single `getProgramAccounts` call can pull into memory. The existing test `test_get_filtered_indexed_accounts_limit_exceeded` confirms the abort logic is exercised only when an explicit `Some(limit)` is supplied [6](#0-5) ; the companion `test_get_filtered_indexed_accounts` uses `None` and shows no bound is applied in that case [7](#0-6) .

An unprivileged attacker who can create on-chain accounts owned by (or SPL-token accounts owned by) a key that is indexed can create an arbitrarily large number N of such accounts over time (each account creation is itself a normal transaction, not a rate-limited RPC call), then issue a single `getProgramAccounts` call. The resulting scan work, memory allocation (`Vec<KeyedAccountSharedData>` sized ~N), and encoding cost in `get_program_accounts` (`rpc/src/rpc.rs:603-671`, which iterates `keyed_accounts` and calls `encode_account` for every item) scale with attacker-controlled N, not with any per-request cap, until the process spawn_blocking task completes.

### Impact Explanation
This falls under the "RPC DoS" bounty category for a single low-rate call producing unbounded cost, matching the rules' allowed category ("unbounded cost for a single low-rate call"). Because the byte-limit check is off by default, a validator operator who enables secondary indexing (a supported, documented feature) without separately hardening it with `--accounts-index-scan-results-limit-mb` is exposed to memory/CPU blow-up and potential OOM/latency spikes from one client request, scaling with attacker-created on-chain state rather than any built-in cap.

### Likelihood Explanation
Preconditions: operator enables `AccountIndex::ProgramId` or `AccountIndex::SplTokenOwner` (as stipulated by the question's scope) and does not separately set `--accounts-index-scan-results-limit-mb` (the default, since the flag has no default value). The attacker only needs to author N on-chain accounts under an indexed program/owner (ordinary transactions, not rate-limited RPC calls) and issue one `getProgramAccounts` call. This is fully reproducible and repeatable, and does not require validator/operator collusion beyond the documented indexing feature itself.

### Recommendation
Give `scan_results_limit_bytes` (and its CLI flag `accounts_index_scan_results_limit_mb`) a sane non-`None` default so that `byte_limit_for_scan` is always enforced unless an operator explicitly opts out, rather than requiring an explicit opt-in to get any protection.

### Proof of Concept
```rust
// runtime/src/bank/tests.rs - extend existing coverage
#[test]
fn test_get_filtered_indexed_accounts_unbounded_without_explicit_limit() {
    let (genesis_config, _mint_keypair) = create_genesis_config(500);
    let mut account_indexes = AccountSecondaryIndexes::default();
    account_indexes.indexes.insert(AccountIndex::ProgramId);
    let bank_config = BankTestConfig {
        accounts_db_config: AccountsDbConfig {
            account_indexes: Some(account_indexes),
            ..ACCOUNTS_DB_CONFIG_FOR_TESTING
        },
    };
    let bank = Arc::new(Bank::new_with_paths_for_tests(
        &genesis_config, Some(bank_config), vec![], None,
    ));

    let program_id = Pubkey::new_unique();
    const N: usize = 100_000; // attacker-controlled, unbounded
    for _ in 0..N {
        let address = Pubkey::new_unique();
        let account = AccountSharedData::new(1, 128, &program_id);
        bank.store_account(&address, &account);
    }

    // Simulates rpc.rs calling with default (None) scan_results_limit_bytes
    let result = bank
        .get_filtered_indexed_accounts(&IndexKey::ProgramId(program_id), |_| true, None)
        .unwrap();

    // Demonstrates result scales linearly with attacker-created N, unbounded
    assert_eq!(result.len(), N);
}
```
Expected: with `byte_limit_for_scan = None` (the out-of-the-box default absent `--accounts-index-scan-results-limit-mb`), the call succeeds and returns a `Vec` of size `N` with no abort, while the same call with `Some(small_limit)` (per `test_get_filtered_indexed_accounts_limit_exceeded`) aborts — demonstrating the cap only applies when explicitly configured.

    /// Return true iff sum > 'byte_limit_for_scan'
    fn accumulate_and_check_scan_result_size(
        sum: &AtomicUsize,
        account: &AccountSharedData,
        byte_limit_for_scan: &Option<usize>,
    ) -> bool {
        if let Some(byte_limit_for_scan) = byte_limit_for_scan.as_ref() {
            let added = Self::calc_scan_result_size(account);
            sum.fetch_add(added, Ordering::Relaxed)
                .saturating_add(added)
                > *byte_limit_for_scan
        } else {
            false
        }
    }
