### Title
Missing refund callback in `MultisigFactory::create` silently consumes deposit on failed deployment - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` schedules a create-account/deploy/transfer/function_call promise chain and returns it without any `.then()` callback to itself. If the deployment fails (e.g. `num_confirmations` invalid, malformed `members`, insufficient gas, or account name collision), the attached NEAR is transferred to the newly created (or existing) account inside the failed batch, is not refunded, and no state is updated on the factory — the caller's deposit is silently lost.

### Finding Description
Binding claimed by the invariant: `refund_to_payer_on_failure == true`, i.e. `predecessor_balance_after_failed_create == predecessor_balance_before_create` (minus gas). In `multisig-factory/src/lib.rs`, `create` (lines 29-49) builds a single promise batch — `create_account().deploy_contract(CODE.to_vec()).transfer(env::attached_deposit()).function_call(...)` — and returns it directly as the function's result [4](#0-3) . There is no `ext_contract` self-callback, no `is_promise_success()` check, and no `Promise::new(predecessor).transfer(...)` anywhere in the file. By contrast, `staking-pool-factory/src/lib.rs::create_staking_pool` and `lockup-factory/src/lib.rs::create` both chain `.then(ext_self::on_..._create(...))`, whose callback bodies call `assert_self()`, `is_promise_success()`, and on failure execute `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` [5](#0-4) [6](#0-5) .

An attacker calls `create(name, members, num_confirmations)` with `num_confirmations` deliberately invalid (e.g. `0` or greater than `members.len()`, which the deployed `multisig2` contract's `new` rejects), or with a `name` that collides with an existing account, or with insufficient `prepaid_gas` so the `function_call` action fails. In every one of these cases, the individual actions within the promise batch on the newly created account (`create_account`, `deploy_contract`, `transfer`) still execute and the deposit lands on the target sub-account or is otherwise consumed, and even where the whole receipt fails, since no refund promise exists at all, the near host simply has nothing to give the deposit back to the payer. No caller-side guard (`assert_self`, `is_promise_success`, `assert_one_yocto`) exists in this contract to prevent it, because none is ever invoked.

### Impact Explanation
Every failed `create` call permanently transfers the attacker's (or any user's) attached NEAR into an account that never becomes a valid, controlled multisig — the deposit is not credited to anyone entitled to it and not returned to the payer. This is repeatable indefinitely across distinct derived `name` values (each producing a distinct `account_id = format!("{}.{}", name, current_account_id())`), so an attacker (or, more relevant to real users making a mistake) loses the deposit on each attempt with no recourse, and the factory's implicit "accounting" of deposits-to-multisigs diverges from reality since deposits vanish with no on-chain multisig created. This matches the High impact category: "an accounting value diverging from reality where another party settles on it" (whoever ends up holding the created-but-unusable account, or the leftover balance itself, receives value never authorized by anyone).

### Likelihood Explanation
No special privileges are required — any unprivileged account can call `create` with any `name`, `members`, and `num_confirmations`, attaching any deposit. Triggering a failing deployment is trivial and low-cost: e.g. supplying `num_confirmations` larger than the number of members (rejected by `multisig2`'s `new`), or reusing a `name` that already exists as an account. This is fully reproducible without any privileged party, and repeatable across arbitrarily many derived ids.

### Recommendation
Add an `ext_contract` self-callback analogous to `on_staking_pool_create` / `on_lockup_create`: chain `.then(ext_self::on_multisig_create(account_id, env::attached_deposit().into(), env::predecessor_account_id(), &env::current_account_id(), NO_DEPOSIT, gas::CALLBACK))` after the deployment promise, and in that callback call `assert_self()`, check `is_promise_success()`, and on failure execute `Promise::new(predecessor_account_id).transfer(attached_deposit.0)`.

### Proof of Concept
Using `near-sdk`'s `testing_env!`/`MockedBlockchain` (as done in the sibling factories' test modules):
1. Set up `VMContextBuilder` with `current_account_id = factory`, `predecessor_account_id = attacker`, `attached_deposit = N`.
2. Call `MultisigFactory::create(name, invalid_members_or_num_confirmations, ...)`.
3. Simulate the deployed `multisig2::new` call failing (`PromiseResult::Failed`), as done via `testing_env_with_promise_results` in `staking-pool-factory`'s and `lockup-factory`'s `test_create_*_rollback` tests [7](#0-6) .
4. Assert: unlike `LockupFactory::on_lockup_create`/`StakingPoolFactory::on_staking_pool_create`, `MultisigFactory` exposes no callback function at all to invoke, so there is no code path returning the deposit to `predecessor_account_id`; assert the factory contract source contains no `Promise::new(predecessor_account_id).transfer(...)` call, confirming `attacker_balance_after == attacker_balance_before - deposit - gas_fees` with no `deposit` returned, breaking the equality `refund_on_failure == true`.
