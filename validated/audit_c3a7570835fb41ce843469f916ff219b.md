### Title
Unsynchronized concurrent map access in `Authorize` races with `syncMetadata`'s map swap - (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

### Summary
`WorkflowMetadataHandler.Authorize` reads `h.authorizedKeys[workflowID]` at line 92 without acquiring `h.mu` at all, while `syncMetadata` replaces the entire `h.authorizedKeys` map under `h.mu.Lock()`. This is a genuine unsynchronized concurrent map read/write in Go, not merely a logical TOCTOU window.

### Finding Description
`Authorize` is invoked on every incoming gateway/HTTP-trigger request carrying a signed JWT (reachable by any unauthenticated/unprivileged client that can submit a signed request to the gateway's trigger endpoint via `http_trigger_handler.go`). It reads the shared field directly: [1](#0-0) 
with no `h.mu.RLock()`/`RUnlock()` around it — unlike other read paths such as `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`, which all correctly take `h.mu.RLock()`.

Meanwhile, `syncMetadata` runs periodically on a ticker (`h.runTicker(..., h.syncMetadata)`) and performs a full map swap under the write lock: [2](#0-1) 

Because `Authorize`'s read of `h.authorizedKeys` at line 92 is completely unguarded by `h.mu`, this is not just a logical staleness/TOCTOU issue — it is an actual **Go runtime data race**: a concurrent unsynchronized map read (in `Authorize`) racing with a map write (the pointer/field assignment `h.authorizedKeys = authorizedKeys` in `syncMetadata`, executed while holding `h.mu.Lock()`, but that lock is never taken by the reader). Go's runtime actively detects concurrent map access and calls `fatalthrow`("concurrent map read and map write"), which is unrecoverable and crashes the entire process — this is not a `panic` that can be caught by `recover()`.

An unprivileged attacker who can trigger gateway trigger requests (which invoke `Authorize`) can flood the gateway with requests timed to coincide with the periodic `syncMetadata` aggregation tick, reliably hitting this race window and crashing the node process.

### Impact Explanation
This matches a **denial-of-service** impact class: the unsynchronized field access can cause the Go runtime to abort the process with a fatal, unrecoverable error ("concurrent map read and map write"), taking down the entire gateway node — not just failing a single request. This is more severe than the "inconsistent authorization snapshot" framing in the question; the map swap here is a whole-field replacement (`h.authorizedKeys = authorizedKeys`), not an in-place mutation, so a reader that races with it will either see the old map or the new map in its entirety (Go pointer/interface-header writes are not atomic without synchronization, so partial/torn reads of the map header are possible, which is exactly what triggers the runtime's race detection or corrupted map header dereference). There is no plausible path by which this crash-inducing race grants an attacker admission with a revoked key, because the swap is atomic-in-content (whole map replacement, no partial merge) — the exploitable consequence is process crash / DoS, not authorization bypass admitting a stale signer.

### Likelihood Explanation
- No special privileges are required — any client able to send a signed gateway trigger request can cause `Authorize` to execute.
- The race window opens once per `MetadataAggregationIntervalMs` tick, and is trivially reproducible by sending a burst of concurrent requests during that window in a tight loop.
- Under Go's `-race` build, this is deterministically detected; in production builds, the race can manifest as sporadic runtime crashes under load, which is highly repeatable given a busy gateway.

### Recommendation
Add proper synchronization to `Authorize`'s read path — acquire `h.mu.RLock()` before reading `h.authorizedKeys[workflowID]` and release it after copying out the needed value (or lock for the full lookup and signer-check region), mirroring the pattern already used in `WorkflowShards`, `GetWorkflowID`, and `GetWorkflowReference`:

```go
func (h *WorkflowMetadataHandler) Authorize(...) (*gateway.AuthorizedKey, error) {
    ...
    h.mu.RLock()
    keys, exists := h.authorizedKeys[workflowID]
    h.mu.RUnlock()
    if !exists { ... }
    ...
}
```

### Proof of Concept
Go test plan (`workflow_metadata_handler_test.go`), run with `go test -race`:
1. Construct a `WorkflowMetadataHandler` with a shard/aggregator configured so `syncMetadata` can be invoked directly (as existing tests in the same file already do).
2. Seed `h.authorizedKeys` with a workflow ID and a valid signer key, and construct a valid signed JWT/request for that signer (reuse helpers from `workflow_metadata_handler_test.go`).
3. Launch two goroutines in a loop (e.g., 1000 iterations):
   - Goroutine A: repeatedly calls `h.syncMetadata(ctx)` with aggregator data alternating between including and excluding the signer's key (simulating revocation).
   - Goroutine B: repeatedly calls `h.Authorize(workflowID, token, req)`.
4. Run under `go test -race`; expect the race detector to report "DATA RACE" on `h.authorizedKeys` between the `syncMetadata` write at line 178 and the `Authorize` read at line 92, proving the missing lock.
5. After adding `h.mu.RLock()`/`RUnlock()` to `Authorize`, re-run and assert `-race` reports no data race, and separately assert that once a revocation sync completes, subsequent `Authorize` calls consistently return the "signer not found" error (no admission of the revoked key).
