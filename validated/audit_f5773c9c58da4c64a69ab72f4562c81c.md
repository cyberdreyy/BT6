### Title
Builder withdrawal amount stated in `Withdrawal` can exceed the amount actually deducted from builder balance, minting free Gwei to `fee_recipient` — ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` and `get_builders_sweep_withdrawals` place the *full, uncapped* requested amount into the `Withdrawal.amount` field that is committed into the execution payload (and unconditionally credited to `fee_recipient`/`execution_address` on the execution layer), while `apply_withdrawals` only decreases the corresponding builder's `balance` by `min(withdrawal.amount, builder_balance)`. Because a builder can accumulate more `BuilderPendingWithdrawal` obligations than its balance can cover (via the untracked-eviction gap described below), the amount actually paid out on the EL side can exceed the amount ever debited from the builder — creating Gwei that is not backed by any decrease in stake and crediting it to a non-owner (the `fee_recipient`).

### Finding Description
`get_builder_withdrawals` builds each `Withdrawal` straight from `state.builder_pending_withdrawals[i].amount` with no clamping to `builder.balance`: [1](#0-0) 

`apply_withdrawals`, however, caps the actual balance decrease: [2](#0-1) 

The test suite explicitly documents and asserts this asymmetry — the committed `Withdrawal.amount` is the *requested* (uncapped) value, while the balance is only reduced by the capped value: [3](#0-2) 

Normally, `can_builder_cover_bid` is supposed to prevent a builder from over-committing beyond its balance by summing *all* currently tracked obligations: [4](#0-3) 

But `get_pending_balance_to_withdraw_for_builder` only sums `state.builder_pending_withdrawals` and `state.builder_pending_payments`: [5](#0-4) 

There is a window where a promised payment exists but is counted in *neither* list: when a parent block's payment slot is evicted from `builder_pending_payments` (quorum not reached / entry aged out after 2+ epochs) but the corresponding withdrawal has not yet been appended (that only happens later, when a descendant block finally processes that specific parent via `apply_parent_execution_payload`): [6](#0-5) 

During this gap, `can_builder_cover_bid` under-counts the builder's true outstanding obligations (the evicted-but-still-owed `parent_bid.value` is invisible to `get_pending_balance_to_withdraw_for_builder`), so the same builder can be authorized for *additional* bids that, combined with the eventually-reinstated withdrawal, sum to more than `builder.balance`. This exact "delayed reinstatement" path is exercised (and asserted as correct/expected behavior) by: [7](#0-6) 

When the accumulated `builder_pending_withdrawals` are eventually processed, each individual `Withdrawal.amount` retains its full uncapped stated value (per `get_builder_withdrawals`), while `apply_withdrawals` can only debit the builder down to zero once, not fully backing every withdrawal in the list. The execution layer, however, unconditionally credits every `fee_recipient` the amount stated in the committed `Withdrawal` — so the sum of Gwei credited on the EL side across these withdrawals can exceed the Gwei ever removed from the builder's CL balance.

### Impact Explanation
This breaks the fundamental Gwei-conservation invariant between the consensus layer and execution layer: Gwei is credited to a `fee_recipient` address on the execution layer that was never actually debited from any validator/builder balance on the consensus layer. This matches the Critical impact class explicitly listed in scope: "Gwei created ... paid to a non-owner." It requires no client bug, no coalition, and no foreign key — a single builder unilaterally exploiting normal missed-block / quorum-eviction conditions (which the spec itself treats as ordinary, non-adversarial behavior, per the fix referenced in `test_builder_payment_after_missed_epochs`) can walk balance-coverage checks into a state where committed withdrawal amounts exceed real backing balance.

### Likelihood Explanation
The precondition (payment slot eviction after 2+ epochs of the parent not being built upon, i.e. missed blocks/slots) is a normal, expected chain condition that the spec explicitly handles as a first-class case (the "older than previous epoch" branch and its accompanying test). A builder only needs to time its bids so that a `builder_pending_payments` entry ages out of the tracked window while it opportunistically places additional bids against its now-under-counted "pending" balance. No malicious peer, partition, or coalition is required — only ordinary missed-slot conditions and a builder controlling its own bid timing/content.

### Recommendation
Either:
1. Make `get_pending_balance_to_withdraw_for_builder` (and thus `can_builder_cover_bid`) account for evicted-but-not-yet-withdrawn parent bid payments (e.g., by never fully evicting the obligation, only migrating it), or
2. Make `get_builder_withdrawals`/`get_builders_sweep_withdrawals` clamp `Withdrawal.amount` to `min(requested_amount, builder.balance_after_prior_withdrawals_in_this_call)` so the committed `Withdrawal.amount` (which the EL will unconditionally honor) can never exceed what is actually being debited from the builder in `apply_withdrawals`.

### Proof of Concept
1. Builder `B` has balance `X`. `B` bids `X - MIN_DEPOSIT_AMOUNT` for slot `S` (parent block, value `V1 ≈ X - MIN_DEPOSIT_AMOUNT`), which passes `can_builder_cover_bid` and is recorded in `builder_pending_payments`.
2. No block builds on `S` for 2+ epochs (ordinary missed slots) — `process_builder_pending_payments` evicts the `V1` payment slot from `builder_pending_payments` (weight below quorum). `get_pending_balance_to_withdraw_for_builder(B)` now returns `0` even though `V1` is still logically owed once `S` eventually gets built upon.
3. While `V1` is untracked, `B` submits a fresh bid `V2` for a new proposer building directly on `S`'s parent (or another compatible fork), sized so `V2 ≈ X - MIN_DEPOSIT_AMOUNT` again passes `can_builder_cover_bid` (since the check does not see `V1`).
4. Eventually a descendant block processes `S` as its parent: `apply_parent_execution_payload` takes the "older than previous epoch" branch and appends a fresh `BuilderPendingWithdrawal(amount=V1, ...)` directly to `state.builder_pending_withdrawals` (per [8](#0-7) ), on top of whatever withdrawal `V2` produces.
5. When `process_withdrawals` runs, `get_builder_withdrawals` emits two `Withdrawal` objects with amounts `V1` and `V2` (sum ≈ `2X - 2·MIN_DEPOSIT_AMOUNT`), both committed to the payload. `apply_withdrawals` can only debit `B.balance` (== `X`) down to `0` in total (per [2](#0-1) ), but the execution layer credits both `fee_recipient`s the full stated amounts `V1` and `V2` — crediting roughly `X - 2·MIN_DEPOSIT_AMOUNT` more Gwei than was ever removed from `B`.

#### New `get_pending_balance_to_withdraw_for_builder`

```python
def get_pending_balance_to_withdraw_for_builder(
    state: BeaconState, builder_index: BuilderIndex
) -> Gwei:
    balance = Gwei(0)
    for withdrawal in state.builder_pending_withdrawals:
        if withdrawal.builder_index == builder_index:
            balance += withdrawal.amount
    for payment in state.builder_pending_payments:
        if payment.withdrawal.builder_index == builder_index:
            balance += payment.withdrawal.amount
    return balance
```

```python
def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount

@with_gloas_and_later
@spec_state_test
def test_builder_payment_after_missed_epochs(spec, state):
    """
    Test that a builder is correctly charged when their canonical payload
    is processed after 2+ epochs of missed blocks.
    """
    # Advance to get finalization
    for _ in range(4):
        next_epoch_with_full_participation(spec, state)
    assert state.finalized_checkpoint.epoch == 2

    # Build Block 1 with a non-zero value bid from a builder
    block_1 = build_empty_block_for_next_slot(spec, state)
    builder_index = 0
    value = spec.Gwei(1000000)  # 0.001 ETH
    fee_recipient = b"\xab" * 20
    block_hash = spec.Hash32(b"\x42" * 32)

    bid = block_1.body.signed_execution_payload_bid.message
    bid.block_hash = block_hash
    bid.builder_index = builder_index
    bid.value = value
    bid.fee_recipient = fee_recipient
    bid.execution_requests_root = spec.hash_tree_root(spec.ExecutionRequests())

    # Sign the bid with the builder's private key
    signature = spec.get_execution_payload_bid_signature(
        state, bid, builder_privkeys[builder_index]
    )
    block_1.body.signed_execution_payload_bid = spec.SignedExecutionPayloadBid(
        message=bid,
        signature=signature,
    )

    # Ensure builder can cover the bid
    state.builders[builder_index].balance = spec.MIN_DEPOSIT_AMOUNT + value

    yield "pre", state

    # Process Block 1 — creates a pending payment for the builder
    signed_block_1 = state_transition_and_sign_block(spec, state, block_1)

    # Verify pending payment was created
    payment_idx = spec.SLOTS_PER_EPOCH + block_1.slot % spec.SLOTS_PER_EPOCH
    payment = state.builder_pending_payments[payment_idx]
    assert payment.withdrawal.amount == value
    assert payment.withdrawal.builder_index == builder_index
    assert payment.weight == 0

    pre_builder_balance = state.builders[builder_index].balance

    # Build Block 2 with 2+ epochs of missed slots. During the slot advancement,
    # process_builder_pending_payments runs at each epoch boundary:
    #   1st boundary: shifts payment from second half to first half
    #   2nd boundary: checks quorum on first half — weight 0 < quorum → evicted
    # When Block 2 is processed, parent is FULL so apply_parent_execution_payload
    # runs. Since parent_epoch is older than previous_epoch, payment_index is None.
    # The fix creates the withdrawal directly from the bid in this case.
    block_1_epoch = spec.compute_epoch_at_slot(block_1.slot)
    block_2_slot = spec.compute_start_slot_at_epoch(block_1_epoch + 2) + 1
    block_2 = build_empty_block(spec, state, slot=block_2_slot)
    block_2.body.signed_execution_payload_bid.message.parent_block_hash = block_hash
    signed_block_2 = state_transition_and_sign_block(spec, state, block_2)

    yield "blocks", [signed_block_1, signed_block_2]
    yield "post", state

    # Verify apply_parent_execution_payload actually ran (parent was FULL)
    parent_slot_index = bid.slot % spec.SLOTS_PER_HISTORICAL_ROOT
    assert state.execution_payload_availability[parent_slot_index]

    # Verify the builder was charged — balance decreased by the bid value
    assert state.builders[builder_index].balance == pre_builder_balance - value
