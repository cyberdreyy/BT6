### Title
Post-default withdraw requests pay 1:1 from `defaultRecoveryReserve`, draining the haircut recovery owed to default-epoch claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel analog is a lock detached from `lock_list` whose error/cleanup paths only iterate the lists — the detached object is leaked and a shared free site is missing. In `IdleCreditVault`, post-default withdraw receipts are detached from the default-epoch claim basis (`postDefaultRequests` instead of `withdrawsRequestsByEpoch`), yet they are paid from the same `defaultRecoveryReserve` that was sized exactly to cover default-epoch claims at `defaultRecoveryPrice`. There is no separate funding source and no reserve bound, so post-default claimants are paid at par while default-epoch claimants later find the reserve depleted.

### Finding Description
In `requestWithdraw`, once `defaultRecoveryFinalized` is set, a requester with no pending receipt gets a fresh strategy-token receipt recorded in `postDefaultRequests[_user]` at the full requested `_amount` [1](#0-0) . The comment says the haircut was already applied via the lowered `virtualPrice`, but that haircut applies to the CDO's tranche price, not to the strategy reserve that actually pays these claims.

`finalizeDefaultRecovery` computes `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + prior reserve` and `defaultRecoveryPrice = reserveAmount * 1e18 / totalBasis`, where `totalBasis` includes only default-epoch receipts plus active basis [2](#0-1) . The reserve is therefore sized exactly so every default-epoch claimant can recover `claimBasis * defaultRecoveryPrice / 1e18`. No headroom for future post-default requests is added.

`_claimPostDefaultWithdrawRequest` pays `postDefaultRequests[_user]` at 1:1 by calling `_transferDefaultRecovery`, which simply decrements `defaultRecoveryReserve` and transfers [3](#0-2) [4](#0-3) . Each post-default claim consumes reserve that was earmarked for default-epoch receipts — the same "detached from the list the cleanup iterates" shape as the ksmbd bug: the receipt left the `pendingWithdraws`/`withdrawsRequestsByEpoch` accounting but still draws on the shared pool.

Because `defaultRecoveryReserve -= _amount` reverts on underflow, once post-default claims consume the slack, remaining default-epoch claimants (and later post-default claimants) cannot claim at all: `claimWithdrawRequest` reverts in `_claimDefaultedWithdrawRequest`/`_claimPostDefaultWithdrawRequest`, permanently freezing their recovery.

### Impact Explanation
After a default is finalized with `defaultRecoveryPrice < 1` (the common case), any KYC-passing tranche holder can call `requestWithdraw` then `claimWithdrawRequest` and pull underlying at par from the reserve. Each such claim directly reduces what default-epoch receipt holders can recover below their promised `claimBasis * defaultRecoveryPrice`, and the tail of claimants is permanently frozen by the underflow revert in `_transferDefaultRecovery`. Quantified loss: up to the full `defaultRecoveryReserve`, i.e. the entire recovered fund for the pool. This is direct theft of unclaimed recovery proceeds plus permanent freezing of the remainder.

### Likelihood Explanation
Requires only a finalized default, which is a supported, tested mode (`finalizeDefaultRecovery`, `DefaultDistributor`). The attacker needs a tranche position and a post-default `requestWithdraw`/`claimWithdrawRequest` pair — no privileged role. Any user racing to claim post-default before default-epoch claimants executes it in two ordinary transactions. The only mitigating factor is that the post-default requester must hold tranche tokens whose CDO-side value was already haircut — but the strategy-side reserve payout is at par, so the theft margin is exactly `1 - defaultRecoveryPrice` per unit requested, bounded by reserve size.

### Recommendation
Pay post-default requests from the same recovery ratio instead of par, or fund them from a source outside `defaultRecoveryReserve`. Concretely: in `_claimPostDefaultWithdrawRequest`, either multiply by `defaultRecoveryPrice` when decrementing the reserve, or route the payout through `_transferFundedClaim` so the reserve guard (`balance - reserve < _amount → revert`) protects default-epoch claimants, and only allow post-default requests when the strategy holds excess underlying beyond the reserve.

### Proof of Concept
Foundry fork sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testPostDefaultClaimDrainsRecoveryReserve() external {
    // 1. epoch running, borrower defaults: stopEpoch with insufficient repayment
    deal(address(underlying), borrower, principal + expectedInterest);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 1);          // partial repay -> defaulted

    // user1 has a pending default-epoch withdraw receipt
    vm.prank(user1);
    cdoEpoch.requestWithdraw(user1Tranches, address(AAtranche));

    // 2. owner finalizes default with recovery < 100%, e.g. 50%
    uint256 recovered = strategy.defaultPendingClaimBasis() / 2;
    deal(address(underlying), recoverySource, recovered);
    cdoEpoch.finalizeDefault(..., recovered, recoverySource); // sets defaultRecoveryPrice ~0.5e18

    // 3. attacker (user2) requests post-default withdraw, then claims at par
    vm.prank(user2);
    cdoEpoch.requestWithdraw(user2Tranches, address(AAtranche));
    vm.prank(user2);
    cdoEpoch.claimWithdrawRequest();
    // user2 received user2Tranches-worth of underlying 1:1 from defaultRecoveryReserve

    // 4. user1's haircut claim now reverts or is short: reserve was consumed
    vm.expectRevert();                 // defaultRecoveryReserve underflow
    vm.prank(user1);
    cdoEpoch.claimWithdrawRequest();
}
```

Key assertions: `strategy.defaultRecoveryReserve()` drops by the full post-default amount while `defaultRecoveryPrice` for `defaultRecoveryEpoch` claimants is unchanged; the sum of all claims exceeds the reserve, proving default-epoch claimants are underpaid by exactly the post-default payout.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    // Every defaulted or post-default claim consumes the isolated recovery reserve.
    defaultRecoveryReserve -= _amount;
    underlyingToken.safeTransfer(_user, _amount);
  }
