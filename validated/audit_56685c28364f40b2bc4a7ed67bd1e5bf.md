### Title
Reorg legitimacy check in `check_parent_tenure_choice` decides on unsynchronized local timestamps, letting signers diverge on whether a tenure reorg is valid - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a new tenure is allowed to reorg away a previous tenure's already-mined block by comparing two **purely local, per-signer** timestamps — `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` (when *this* signer's node happened to receive the burn block that starts the new tenure) and `local_block_info.approved_time` (when *this* signer happened to locally approve the earlier tenure's block). Neither value is derived from consensus-visible chain data (unlike the TWAP-protected check the report recommends); they are wall-clock timestamps stamped as each signer processes gossip/RPC events at its own pace. Because these local clocks can legitimately differ across signers (network latency, load, restart timing), different signers can compute different `proposal_to_sortition` deltas for the *same* pair of blocks, and therefore reach opposite `check_parent_tenure_choice` verdicts. This is the same "manipulable local value used for an equality/threshold decision" defect pattern as the AMM report — there, the AMM pool's raw, flash-loanable spot state was substituted for a manipulation-resistant TWAP; here, an unsynchronized per-signer local timestamp is substituted for a value that should be identical and reproducible across the signer set.

### Finding Description
`check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`) is the gatekeeper that lets a new miner's tenure legitimately replace ("reorg") a previous tenure's mined blocks. The rule is: a reorg is permitted only if the reorged tenure produced zero blocks, or its first/only block was mined "very close to the burn block transition" (line 259: `Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing`).

`proposal_to_sortition` (lines 247-258) is computed as:
```
sortition_state_received_time.saturating_sub(local_block_info.approved_time)
```
- `sortition_state_received_time` comes from `signer_db.get_burn_block_receive_time(&self.burn_block_hash)` — stamped locally, whenever *this* signer's process happened to receive/process the `NewBurnBlock` event for the sortition that starts the new (reorging) tenure.
- `local_block_info.approved_time` is stamped locally at pre-commit or local acceptance (per `docs/signer-flows.md` section 2: "`approved_time` is stamped at pre-commit or local acceptance (first wins)") of the earlier, competing block.

Both values are wall-clock timestamps recorded independently by each signer as events reach it, not chain-derived or agreed-upon quantities. Signer A, which received the burn block quickly (well-connected to the relay network) and/or approved the earlier block slowly, computes a large delta and rejects the reorg (`ReorgNotAllowed`). Signer B, which received the burn block late relative to when it approved the earlier block, computes a small delta and permits the reorg, ultimately signing a block built on top of a tenure that Signer A still considers canonical/protected. This is exactly the class of bug flagged in the report: a decision that gates an action ("is this reorg allowed" / "how much do I need to trade") is computed from a value that is not guaranteed to be consistent between observers, rather than from a chain-anchored, TWAP-like quantity.

The result: the equality "approved-parent vs canonical" that the signer set is supposed to agree on breaks — some signers will sign the block continuing the reorg (marking the earlier tenure superseded via `record_superseded_tenure`), while others reject it, producing conflicting/non-canonical signatures across the signer set for the same height.

### Impact Explanation
This falls into the Critical category: "a signer signing an invalid, non-canonical, or conflicting block." A single miner who wins two consecutive tenures (or colludes/times its proposal broadcast) can exploit natural or engineered propagation-delay skew across signers so that the signer set is not unanimous on whether a reorg is legitimate. Because the decision is per-signer and not derived from a value every signer computes identically, the miner does not need to compromise a majority of signers or their keys — they only need normal network jitter (or deliberately delayed proposal broadcast/burn-block relay) to widen the gap between signers' local clocks around the `first_proposal_burn_block_timing` threshold. Once the threshold is crossed differently for different signers, the "permitted" set signs a competing chain history against the earlier tenure's signers, producing conflicting valid signatures for mutually exclusive tenures at the same height — the Critical-tier "conflicting block" outcome.

### Likelihood Explanation
The relevant flag in the code comment itself ("this value *should* always be some, but try to do the best we can if it isn't") acknowledges the timestamp is best-effort/local. `first_proposal_burn_block_timing` is a narrow window (short duration, matching the intent of "very close to the burn block transition"), so realistic network latency variance between signers (which routinely differs by seconds during Bitcoin block propagation and StackerDB gossip) is plausible without any active manipulation, and a miner controlling proposal broadcast timing can deliberately push the delta close to the threshold to increase the chance of a split decision. This does not require compromising the majority of signers, a signer's key, or node access — only ordinary or lightly-influenced timing variance, matching the "one-slot miner plus gossip" trigger constraint.

### Recommendation
Replace the local receive/approval timestamps with a consensus-derived measure of timing, e.g., the actual burn-block timestamp (`burn_header_timestamp`, already present on `SortitionData`) compared against a block-inclusion-derived, chain-anchored timestamp (or burn height delta) rather than signer-local wall-clock stamps. If a local fallback must remain for resiliency, it should be bounded so that ambiguous cases near the threshold are treated conservatively (reject the reorg) rather than defaulting to whichever side of the local clock happens to win, and the threshold comparison should be based on values that are provably identical for every signer (e.g., derived from the sortition's `burn_header_timestamp` and the miner's own signed proposal timestamp inside the block header, both consensus-visible) instead of `get_burn_block_receive_time`/`approved_time`.

### Proof of Concept
1. Miner M wins tenure T1 and tenure T2 (two consecutive sortitions — no signer collusion required, just consecutive leader wins, which single miners routinely achieve).
2. In T1, M mines exactly one block and delays broadcasting the proposal until near the very end of T1's window (broadcast is entirely within M's control).
3. Signer A has fast connectivity to M's relay and its own StackerDB polling loop; it processes/approves the T1 block quickly relative to when it later receives the T2 burn block (`get_burn_block_receive_time`), yielding a large `proposal_to_sortition` → `check_parent_tenure_choice` returns `false` → Signer A treats a T2 reorg proposal as `ReorgNotAllowed` and refuses to sign it.
4. Signer B, on a slower or more congested connection, receives/approves the T1 block later relative to its own receipt of the T2 burn block, yielding a small `proposal_to_sortition` below `first_proposal_burn_block_timing` → `check_parent_tenure_choice` returns `true` → Signer B accepts M's T2 tenure-change block that reorgs away T1's block, and signs it (`record_superseded_tenure` marks T1 superseded in B's local `signer_db`).
5. The signer set is now split: A holds a valid signature over T1's block; B (and any similarly-lagged signers) holds a valid signature over a conflicting T2 tenure-change block that discards T1. If enough signers land on B's side of the timing race, M gets a globally-signed reorg that other signers consider illegitimate — a conflicting/non-canonical signature outcome achieved purely through propagation-timing skew, not through compromising signer majority or keys.     pub fn check_parent_tenure_choice(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
            }

            // disallow reorg if more than one block has already been signed
            let globally_accepted_blocks =
                signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
            if globally_accepted_blocks > 1 {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already more than one globally accepted block.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => ?tenure.first_block_mined,
                    "globally_accepted_blocks" => globally_accepted_blocks,
                );
                return Ok(false);
            }

            let Some(first_block_mined) = &tenure.first_block_mined else {
                // The node saw no blocks in this tenure, so the reorg takes nothing away from
                // the canonical chain. We may still hold a signature over a block in it that
                // the node has never seen (a block we accept locally is not handed to the node
                // until the whole signer set has signed it), so the reorg must still be
                // recorded if it is permitted.
                superseded_tenures.push(tenure);
                continue;
            };
            let Some(local_block_info) =
                signer_db.get_first_approved_block_in_tenure(&tenure.consensus_hash)?
            else {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks, and there is no local knowledge for that tenure's block timing.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => %first_block_mined,
                );
                return Ok(false);
            };

            let checked_proposal_timing = if let Some(sortition_state_received_time) =
                sortition_state_received_time
            {
                // how long was there between when the proposal was received and the next sortition started?
                let proposal_to_sortition = if let Some(approved_at) =
                    local_block_info.approved_time
                {
                    sortition_state_received_time.saturating_sub(approved_at)
                } else {
                    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
                    0
                };
                if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
                    info!(
                        "Miner is not building off of most recent tenure. A tenure they reorg has already mined blocks, but the block was poorly timed, allowing the reorg.";
                        "parent_tenure" => %self.parent_tenure_id,
                        "last_sortition" => %self.prior_sortition,
                        "violating_tenure_id" => %tenure.consensus_hash,
                        "violating_tenure_first_block_id" => %first_block_mined,
                        "violating_tenure_proposed_time" => local_block_info.proposed_time,
                        "new_tenure_received_time" => sortition_state_received_time,
                        "new_tenure_burn_timestamp" => self.burn_header_timestamp,
                        "first_proposal_burn_block_timing_secs" => first_proposal_burn_block_timing.as_secs(),
                        "proposal_to_sortition" => proposal_to_sortition,
                    );
                    superseded_tenures.push(tenure);
                    continue;
                }
                true
            } else {
                false
            };

            warn!(
                "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks.";
                "parent_tenure" => %self.parent_tenure_id,
                "last_sortition" => %self.prior_sortition,
                "violating_tenure_id" => %tenure.consensus_hash,
                "violating_tenure_first_block_id" => %first_block_mined,
                "checked_proposal_timing" => checked_proposal_timing,
            );
            return Ok(false);
        }
        // Every reorged tenure cleared the rules, so the reorg is permitted.
        for tenure in superseded_tenures {
            self.record_superseded_tenure(signer_db, tenure);
        }
        Ok(true)
    }
