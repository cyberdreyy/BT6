### Title
Loss-adjusted withdraw receipts keyed to the wrong epoch escape the haircut and are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` stores the realized haircut under the strategy's *current* `epochNumber` (`lossRecoveryPriceByEpoch[epochNumber]`, line 421), but user receipts are looked up by `lastWithdrawRequest[_user]`, which was snapshotted to `epochNumber` at request time (line 282) — one epoch earlier. `epochNumber` is incremented inside `deposit()` whenever a deposit lands while `isEpochRunning()` is true (lines 607-611), i.e. during `stopEpoch` processing. If `collectWithdrawFunds` is reached after that increment (or if requests are made in the buffer epoch N and the loss stop runs while the counter is already N+1), the haircut is written under a key no receipt points to — the exact libpng desync: the "header" (loss flag) is discarded under the wrong offset, and the leftover "body" (the pending receipt) is reinterpreted on the next call as an ordinary, fully-funded claim.

### Finding Description
Three paths consume `lossRecoveryPriceByEpoch` via `lastWithdrawRequest`:

- `requestWithdraw` guard (lines 261-271): `lossEpoch = lastWithdrawRequest[_user]`; reverts only if `lossRecoveryPriceByEpoch[lossEpoch] != 0`. With the price stored at `lossEpoch + 1`, the guard reads 0 and lets the user stack new requests.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801): reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`; on the mis-keyed epoch it returns 0, so the receipt is never haircut or cleared there.
- `claimWithdrawRequest` then falls through to `_claimFundedWithdrawRequest` (lines 319-349), which pays `withdrawsRequests[_user] + apr0 settled buckets` **at par** via `_transferFundedClaim`.

The borrower actually funded only `pendingToFund < pendingBasis` (the haircut amount, `previewLossAdjustedWithdrawFunds`, lines 440-459). Paying receipts at par therefore over-draws the strategy's funded underlying.

### Impact Explanation
Every pending withdraw receipt in a loss-adjusted `stopEpochWithDuration` is paid 100% while only the haircut amount was collected. The shortfall is taken from other funded claims and post-default reserves held in the strategy (`_transferFundedClaim` only guards `defaultRecoveryReserve`, lines 897-907): first claimants drain the reserve and later claimants' funded receipts become unpayable — direct insolvency and theft of unclaimed yield. Additionally, because the loss flag is never consumed, `lossRecoveryPriceByEpoch[realEpoch]` sits permanently non-zero, and the `requestWithdraw` guard may permanently block or mis-gate future requests for any user whose `lastWithdrawRequest` ever equals that epoch (permanent freezing).

### Likelihood Explanation
Triggering requires only a `stopEpoch`/`stopEpochWithDuration` where the realized loss causes partial funding of `pendingWithdraws` — an ordinary manager/borrower flow, no malicious privileged role needed. Any unprivileged lender with a pending request in that epoch then claims at par or frontruns other claimants. The precondition is the epoch-key off-by-one created by `deposit()` bumping `epochNumber` during the same stop that calls `collectWithdrawFunds`; that ordering should be confirmed against `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` (the strategy only sees `epochNumber` at call time, so if the increment precedes funding collection, every loss epoch is mis-keyed by construction, not just in edge cases).

### Recommendation
Key the loss price to the epoch the receipts belong to: pass the request epoch explicitly (e.g. `collectWithdrawFunds(_amount, _requestEpoch)` or snapshot `epochNumber` before the stop-time deposit/increment), or store the haircut against `pendingWithdraws`-epoch derived from receipt bookkeeping rather than the mutable counter. Alternatively, have `_claimLossAdjustedWithdrawRequest` iterate/record the epoch at request time into `withdrawsRequestsByEpoch` and match on the epoch for which the price was written. Add a regression test: request in buffer epoch N, `stopEpochWithDuration` with partial funding, assert `lossRecoveryPriceByEpoch[N] != 0` and that claims pay `claimBasis * price`.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVaultLossEpochDesync.t.sol
function testLossKeyedToWrongEpochPaysAtPar() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    _depositWithUser(user1, amount, true);
    _depositWithUser(user2, amount, true);

    _startEpochAndCheckPrices(0);

    // user1 requests withdraw during epoch 0 -> lastWithdrawRequest = 0
    vm.prank(user1);
    cdoEpoch.requestWithdraw(trancheAmt1, address(AAtranche));

    // borrower repays only enough to realize a loss on pending receipts
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 partial = pendingBasis * 60 / 100; // 40% loss on pending bucket
    deal(defaultUnderlying, borrower, principalActive + partial);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, interest); // loss-adjusted funding path

    uint256 reqEpoch = IdleCreditVault(address(strategy)).lastWithdrawRequest(user1);
    // desync: haircut stored under epochNumber (incremented during stopEpoch deposit),
    // not under the request epoch the claim path reads
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0, "haircut lost");
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), 0, "mis-keyed");

    // user1 claims at par instead of ~60%
    uint256 balPre = underlying.balanceOf(user1);
    vm.prank(user1);
    cdoEpoch.claimWithdrawRequest();
    assertGt(underlying.balanceOf(user1) - balPre,
             trancheAmt1 * 60 / 100, "paid above funded haircut");

    // user2's funded claim (or other pending claimants) is now underfunded / reverts
}
```

Note: I could not inspect `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` call ordering (iteration limit reached); the finding stands on the strategy-side keying mismatch between `lossRecoveryPriceByEpoch[epochNumber]` (write) and `lastWithdrawRequest` (read), which the PoC assertions verify directly on a fork.
