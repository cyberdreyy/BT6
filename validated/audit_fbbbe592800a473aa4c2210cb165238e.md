The report describes a duplicate-token-registration flaw in `CustomSetOracle._registerTokens`, which is an owner/admin-only function (no `allowUpdate` guard against duplicates in an unsorted list). Searching Aera's production code, the closest analogs are all similarly privileged, access-controlled functions: `AeraVaultAssetRegistry.addAsset` (guarded by `onlyOwner`, with an explicit duplicate check `Aera__AssetIsAlreadyRegistered`) [1](#0-0) , `OracleRegistry.addOracle`/`scheduleOracleUpdate` (guarded by `requiresAuth`, with explicit `AeraPeriphery__OracleAlreadySet`/`AeraPeriphery__OracleUpdateAlreadyScheduled` checks) [2](#0-1) , and `ProvisionerV2.setTokenDetails`/`removeToken` (guarded by `requiresAuth`) [3](#0-2) .

Unlike `CustomSetOracle`, these Aera registries already include explicit duplicate-registration guards where relevant, and in all cases registration/removal is restricted to privileged roles (`onlyOwner`/`requiresAuth`), not reachable by an ordinary user. Since the task requires an exploit reachable through an ordinary-user transaction sequence — and this pattern only manifests through admin/guardian misconfiguration, which is explicitly excluded — there is no valid in-scope analog.
