A promising analog surfaced: a dust deposit into an empty tranche changes the gain split in `_virtualPriceAux`/`_trancheGain`. Let me verify the mint path and guards.### Title
Dust deposit into an empty tranche captures the entire partner tranche's yield share — (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault._virtualPriceAux` gives 100% of a gain to a tranche when it is the only class with saved NAV (`_lastNAV == _lastTrancheNAV`). An unprivileged, KYC-passed user can deposit dust into the empty partner tranche during the buffer period, setting its `lastNAV*` to a nonzero value. From then on, gains are split by `trancheAPRSplitRatio`, so the dust position captures the entire empty tranche's share of the whole vault's interest — a payout proportional to total vault gain, not to the dust deposited. This is the direct analog of the Y2K "dust deposit prevents null epoch" bug: a zero-TV side is a favorable terminal state for the funded side, and a minimal deposit by an opportunistic user defeats it while extracting an outsized reward.

### Finding Description
In `contracts/IdleCDOCreditVault.sol`, gain routing is NAV-based, not supply-proportional:

```solidity
// contracts/IdleCDOCreditVault.sol:319-328
if (_lastTrancheNAV == 0) {
  _totalTrancheGain = 0;
} else if (_lastNAV == _lastTrancheNAV) {
  _totalTrancheGain = totalGain;   // sole funded class gets everything
} else {
  if (totalGain > 0) {
    int256 totalBBGain = totalGain * int256(FULL_ALLOC - _trancheAPRSplitRatio) / int256(FULL_ALLOC);
    _totalTrancheGain = _isAATranche ? (totalGain - totalBBGain) : totalBBGain;
```

Once `lastNAVBB` is nonzero — even 1 wei — BB's gain is `totalGain * (FULL_ALLOC - splitRatio) / FULL_ALLOC`, taken over the *entire vault's* gain since the last accounting update. A symmetric path exists in `contracts/IdleCDOUsualVariant.sol:145-151` (empty partner tranche ⇒ sole tranche gets all gain; non-empty BB gets *all* yield when `totalGain > 0`) and in the view-side `IdleCreditVaultImpliedPrice._trancheGain` (`contracts/IdleCreditVaultImpliedPrice.sol:94-99`), so the same dust-deposit flips both real and implied accounting.

Attack sequence (fixed-APR mode, buffer phase):
1. Vault runs AA-only (`lastNAVAA > 0`, `lastNAVBB == 0`, `BBTranche.totalSupply() == 0`). An epoch accrues interest; all of it belongs to AA because `_lastNAV == _lastNAVAA`.
2. Before the buffer ends, the attacker calls `depositBB(1)` (or the smallest allowed unit). Deposits are only blocked while the epoch is running (`_pause()` in `startEpoch`), so the buffer window is open. `_deposit` requires only `isWalletAllowed(msg.sender)` (`contracts/IdleCDOEpochVariant.sol:644-649`) — the attacker is a KYC-passing lender. `_skimDonatedAssets` does not apply; this is a real deposit. The mint path `_mintSharesAtCurrPrice` (`contracts/IdleCDOCreditVault.sol:344-347`) prices the empty tranche at `oneToken` because `_virtualPriceAux` returns `(oneToken, 0)` for zero supply (`:296-297`), so the mint succeeds.
3. `lastNAVBB` becomes 1. At the next `_updateAccounting` (any subsequent deposit/withdraw/stopEpoch), BB receives `totalGain * (FULL_ALLOC - splitRatio) / FULL_ALLOC` — e.g., with an 80/20 split the dust deposit books 20% of all accrued vault interest. AA's gain drops from `totalGain` to `totalGain - totalBBGain`.
4. The attacker redeems the now-inflated BB position, extracting real underlying.

No existing guard prevents this: `_trancheSupply == 0` handling in `_virtualPriceAux` only covers the *empty* state; `depositDuringEpoch`'s `_trancheTotSupply == 0` check (`contracts/IdleCDOEpochVariant.sol:675-677`) explicitly acknowledges this pricing discontinuity mid-epoch but the equivalent first-deposit-into-empty-tranche path during the buffer is unprotected.

### Impact Explanation
Direct theft of yield: the attacker steals the entire empty tranche's contractual share of interest (up to `FULL_ALLOC - trancheAPRSplitRatio` of total gains) with a dust deposit, diluting the funded tranche's holders. Loss is bounded by the empty-tranche share of accrued interest but requires essentially zero capital. On `IdleCDOUsualVariant`, the theft is worse — a dust BB deposit captures *all* yield (`_totalTrancheGain = totalGain` for junior when AA exists, `:149-151`).

### Likelihood Explanation
Requires a vault where one tranche is empty — common for newly launched pools, pools after a one-sided exit, or AA-only credit vaults where BB deposits are not yet enabled/funded. The attacker only needs Keyring clearance and a buffer-period transaction; the deposit can be made at the last moment of the buffer to minimize exposure. One caveat I could not fully verify in the available index: whether `isBBDepositEnabled` or a minimum-deposit/`_guarded` cap restricts an ordinary `depositBB` into a never-used tranche — `isBBDepositEnabled` is enforced inside `depositDuringEpoch` (`contracts/IdleCDOEpochVariant.sol:659`), and no minimum was observed, but `_guarded`'s full checks were not retrieved. If BB deposits are globally disabled the same attack applies symmetrically to an empty AA tranche funded by dust, where the AA branch `totalGain - totalBBGain` rounding still lets the dust tranche capture BB's full share via the BB side of the split.

### Recommendation
Treat a tranche whose NAV is below a minimum (e.g., a configurable dust threshold or a percentage of total NAV) as "empty" for gain-split purposes, mirroring the fix suggested in the original report (an acceptable-ratio requirement). Alternatively, when `_lastTrancheNAV` was 0 at the start of the accrual window, attribute gains proportionally to contributed NAV rather than flipping to the split ratio retroactively, or block first deposits into a zero-NAV tranche while accrued undistributed gain exists — the same protection already applied mid-epoch via `_checkNotAllowed(_trancheTotSupply == 0)`.
