### Title
Unchecked NEAR transfer promise in `internal_withdraw` lets the ledger become insolvent relative to real NEAR held - (File: `staking-pool/src/internal.rs`)

### Summary
The external report's bug class — debiting an accounting balance based on the assumption that an outgoing token transfer succeeded, without verifying the actual transfer outcome — has a direct analog in `staking-pool/src/internal.rs`. `internal_withdraw` fires `Promise::new(account_id).transfer(amount)` and unconditionally decrements both the delegator's `unstaked` balance and the pool's `last_total_balance` in the same call, without attaching a callback that checks whether the transfer promise actually succeeded.

### Finding Description
`internal_withdraw` performs: [1](#0-0) 

The sequence is: assert sufficient `unstaked` balance and epoch delay, decrement `account.unstaked -= amount`, persist the account, schedule `Promise::new(account_id).transfer(amount)`, and decrement `self.last_total_balance -= amount` — all before the transfer promise is actually executed and with no `.then()` callback attached to verify success (contrast with every other staking-pool/lockup cross-contract action in this codebase, e.g. `on_staking_pool_withdraw` in `lockup/src/owner_callbacks.rs:105-145`, which explicitly checks `is_promise_success()` before updating state). If the outgoing `Promise::new(account_id).transfer(amount)` fails (e.g., because `account_id` was deleted between the `withdraw` call submission and promise execution — a scenario the contract's own README acknowledges), the ledger has already committed the debit: `account.unstaked` and `self.last_total_balance` are permanently reduced even though the NEAR was never delivered to the delegator.

This breaks the custody binding: `sum(delegator.unstaked) + total_staked_balance` (the claims recorded in state) should equal the actual NEAR balance held by the staking pool contract minus locked/staked amount. After a failed transfer with no rollback, the recorded claims are permanently lower than the NEAR that objectively remains in the contract's account (the refunded amount from the failed promise lands back on the contract but is never re-credited to the specific account whose withdrawal failed) — an accounting divergence where a party (any other delegator, or the pool owner via reward distribution) benefits from value that rightfully should have stayed attributed to the withdrawing account.

### Impact Explanation
This matches the "High" impact bucket: an accounting value (`last_total_balance` / individual `unstaked`) diverges from reality, and another party (the reward-distribution mechanism, which redistributes any unaccounted contract balance growth to active stakers in the next epoch per `staking-pool/README.md:90-94`) settles on the wrong figure. The affected delegator permanently loses the withdrawn amount from their recorded balance without receiving the NEAR, while the surplus NEAR sitting in the contract is silently absorbed into the next `ping`/reward cycle and distributed to other participants — a fund reallocation the affected party never authorized.

### Likelihood Explanation
The triggering condition (destination account being deleted or otherwise unable to receive a plain `Promise::transfer` between call submission and promise execution) is a known, narrow race acknowledged directly in the project's own documentation for the withdraw-by-owner path, indicating this exact failure mode is a real, previously-considered edge case rather than a purely theoretical one. However, it requires the receiving account to become non-existent/unable to receive funds during the async gap, which is a specific, low-frequency condition, not an attacker-controlled state on an already-established account under normal operation.

### Recommendation
Attach a `.then()` callback to the withdrawal transfer (mirroring the pattern already used everywhere else in this codebase, e.g. `on_staking_pool_withdraw`) that checks `is_promise_success()`; only decrement `account.unstaked` and `self.last_total_balance` after confirming success, or re-credit the account's `unstaked` balance if the transfer promise fails.

### Proof of Concept
1. Delegator deposits and later unstakes `amount`, waits the required epochs, then calls `withdraw(amount)`, which invokes `internal_withdraw`.
2. `internal_withdraw` decrements `account.unstaked` and `self.last_total_balance` immediately and schedules `Promise::new(account_id).transfer(amount)`.
3. Between transaction submission and promise execution, `account_id` is deleted (e.g., via `near delete`), causing the `transfer` action to fail and the NEAR to be refunded back to the staking-pool contract.
4. No callback exists to detect the failure or restore `account.unstaked`/`last_total_balance`.
5. The delegator's recorded `unstaked` balance is now permanently short by `amount` while the actual NEAR sits unaccounted in the contract, subsequently swept into the next epoch's reward distribution per `internal_ping` behavior described in `staking-pool/README.md:90-94` — benefiting other stakers/the owner instead of the original delegator.     pub(crate) fn internal_withdraw(&mut self, amount: Balance) {
        assert!(amount > 0, "Withdrawal amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);
        assert!(
            account.unstaked >= amount,
            "Not enough unstaked balance to withdraw"
        );
        assert!(
            account.unstaked_available_epoch_height <= env::epoch_height(),
            "The unstaked balance is not yet available due to unstaking delay"
        );
        account.unstaked -= amount;
        self.internal_save_account(&account_id, &account);

        env::log(
            format!(
                "@{} withdrawing {}. New unstaked balance is {}",
                account_id, amount, account.unstaked
            )
            .as_bytes(),
        );

        Promise::new(account_id).transfer(amount);
        self.last_total_balance -= amount;
    }

    pub fn on_staking_pool_withdraw(&mut self, amount: WrappedBalance) -> bool {
        assert_self();

        let withdraw_succeeded = is_promise_success();
        self.set_staking_pool_status(TransactionStatus::Idle);

        if withdraw_succeeded {
            {
                let staking_information = self.staking_information.as_mut().unwrap();
                // Due to staking rewards the deposit amount can become negative.
                staking_information.deposit_amount.0 = staking_information
                    .deposit_amount
                    .0
                    .saturating_sub(amount.0);
            }
            env::log(
                format!(
                    "The withdrawal of {} from @{} succeeded",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        } else {

                    "The withdrawal of {} from @{} failed",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
