### Title
Loss-adjusted withdraw haircut applies only to the latest request epoch, letting multi-epoch requesters drain the funded receipt pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

CVE-2017-5443 is an out-of-bounds write caused by decoding improperly formed records: a stale/undersized index corrupts adjacent data. The analog in IdleCreditVault is the stale single-epoch index `lastWithdrawRequest[_user]`: `collectWithdrawFunds` funds all pending receipts at one `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` only haircuts the receipt stored under `lastWithdrawRequest` (the most recent epoch). A user holding receipts from multiple epochs gets the older receipt paid at par via `_claimFundedWithdrawRequest`, over-draining the fixed funded reserve and leaving other loss-adjusted claimants unpaid. [1](#0-0) [2](#0-1) 

### Finding Description

When `stopEpoch` collects less than `pendingWithdraws`, `collectWithdrawFunds` sets `pendingWithdraws = 0`, stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`, and pulls only the haircut-funded `_amount` into the strategy. The reserve therefore covers `price * (sum of ALL pending receipt bases across ALL epochs)`. [3](#0-2) 

Claim routing, however, is keyed on a single epoch pointer: `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and calls `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)`, which clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` (and the matching APR0 bucket), decrementing `withdrawsRequests[_user]` by just that epoch's amount. [4](#0-3) 

`requestWithdraw` records both `withdrawsRequests[_user]` (aggregate) and `withdrawsRequestsByEpoch[_user][currentEpoch]`, and overwrites `lastWithdrawRequest[_user] = currentEpoch` on every request. The contract's own comment confirms multiple unclaimed requests are legal ("if a user does not claim ... he will have to wait for another epoch to claim both requests"), and the existing guard only blocks a new request when a *previous* loss epoch's receipt is still unclaimed — it does not prevent two pending receipts when a *new* loss epoch crystallizes. [5](#0-4) [6](#0-5) 

Result for a user with receipts in epochs N and N+1 when the loss lands in epoch N+1:
- `_claimLossAdjustedWithdrawRequest` pays `basis_{N+1} * price` and clears only epoch N+1.
- `_claimFundedWithdrawRequest` then pays the remaining `basis_N` **at par** from the same reserve.
- Total received = `basis_N + basis_{N+1} * price`, while the reserve was sized for `(basis_N + basis_{N+1} + others) * price`.

### Impact Explanation

Direct theft / insolvency of the funded receipt pool. An unprivileged KYC'd lender needs no privileged role: they simply make two `requestWithdraw` calls in consecutive buffer periods and do not claim the first. When a partial `stopEpochWithDuration(_lossAmount)`/`collectWithdrawFunds` occurs (honest manager action, no attacker control needed beyond normal loss), the attacker claims before honest requesters and withdraws `basis_older * (1 - price)` more than their fair share. Every subsequent loss-adjusted claimant's `_transferFundedClaim` then reverts or underpays because the strategy's underlying balance was sized for the aggregate haircut — the excess is taken directly from other users' funded claims. For example, with `price = 0.5`, attacker basis 1000 (epoch N) + 1000 (epoch N+1): fair payout 1000, actual payout 1500; a later claimant with identical basis receives at most the residual or reverts. [7](#0-6) 

### Likelihood Explanation

Likelihood is moderate-to-high: it requires (a) a partial funding event (`_amount < pendingBasis`), which is exactly the designed loss-socialization path via `stopEpochWithDuration`/`previewLossAdjustedWithdrawFunds`, and (b) a requester holding receipts across two epochs, which the code explicitly permits and even documents. No privileged attacker, oracle manipulation, or timing race is needed — the attacker only chooses not to claim between epochs, a zero-cost action. The broken invariant ("one receipt one haircut") is deterministic once both preconditions hold. [8](#0-7) 

### Recommendation

Apply the epoch loss haircut to **all** of a user's pending receipt bases, not just the one under `lastWithdrawRequest`. Options:
- Track per-user a list/bitmap of epochs with pending receipts (or store a single `pendingEpochs` range), and in `_claimLossAdjustedWithdrawRequest` iterate/clear every epoch whose basis was included in the funded `pendingBasis` at `collectWithdrawFunds` time.
- Simpler and consistent with the existing design: extend the `requestWithdraw` guard so that a user with any unclaimed pending normal receipt (`withdrawsRequests[_user] != 0` or unsettled `apr0Users[_user].principal != 0`) cannot open a new request at all, not only when a prior loss epoch exists. This guarantees `pendingBasis` never aggregates multiple epochs per user, so the single-epoch `lastWithdrawRequest` pointer is always sufficient.
- Alternatively, store the haircut price per *user* (`lossRecoveryPriceByUser`) computed at fund time, eliminating the epoch-indexed lookup entirely.

Also verify the symmetric APR0 path (`apr0Users[_user].principalEpoch` vs `lossEpoch`) cannot leave an older APR0 bucket un-haircut under the same sequence. [9](#0-8)

function testMultiEpochReceiptSkipsHaircut() external {
  // Setup: attacker (KYC'd) deposits AA, epoch running normally.
  uint256 amount = 10000 * ONE_SCALE;
  idleCDO.depositAA(amount);           // attacker + other LPs
  cdoEpoch.requestWithdraw(attackerReq1, address(AAtranche)); // epoch N buffer request, do NOT claim
  _startEpochAndCheckPrices(N);        // honest manager
  _stopEpochAndCheckPrices(...);       // epoch N settles fully funded

  // epoch N+1 buffer: attacker still has unclaimed receipt -> allowed to request again
  cdoEpoch.requestWithdraw(attackerReq2, address(AAtranche)); // overwrites lastWithdrawRequest = N+1
  // honest user Bob also has a pending receipt contributing to pendingWithdraws
  _startEpochAndCheckPrices(N+1);

  // manager stops epoch N+1 with a real loss: collectWithdrawFunds(partial)
  vm.warp(cdoEpoch.epochEndDate() + 1);
  deal(defaultUnderlying, borrower, partialFunding);
  cdoEpoch.stopEpochWithDuration(_lossAmount, epochDuration, newApr); // sets lossRecoveryPriceByEpoch[N+1] = p < 1

  uint256 balPre = underlying.balanceOf(attacker);
  cdoEpoch.claimWithdrawRequest();     // attacker path: loss-adjusted on epoch N+1 only + epoch N at par
  uint256 attackerGot = underlying.balanceOf(attacker) - balPre;

  // fair share is (req1 + req2) * p ; attacker actually gets req1 + req2 * p
  assertGt(attackerGot, (attackerReq1 + attackerReq2) * price / RECOVERY_FULL);

  // Bob claims afterwards: _transferFundedClaim underpays or reverts — insolvency of funded reserve
  vm.expectRevert(); // or assertLt(bobGot, bobBasis * price / RECOVERY_FULL)
  bobCdo.claimWithdrawRequest();
}

      revert NotAllowed();

  /// @notice Claim a funded non-default withdraw request at par.
  /// @param _user address of the user
  /// @return amount amount claimed
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
