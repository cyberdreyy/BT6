### Title
Backward-compatibility redirect in `store_and_process_block_signature` can permanently drop already-signed peer signatures from the group-signature tally, wedging a signer that has already signed from ever broadcasting the block - (File: stacks-signer/src/v0/signer.rs)

### Summary
`store_and_process_block_signature` (the handler for a peer's `BlockResponse::Accepted` signature) contains a backward-compatibility shortcut: if the sender hasn't yet been recorded as having pre-committed, the function stores the signature and then *redirects* processing into `handle_block_pre_commit` instead of continuing to tally the actual signature weight. `handle_block_pre_commit`, however, bails out immediately if this signer has already signed the block itself (`signed_self.is_some()`), without ever recomputing the real signature-weight tally that would trigger `broadcast_signed_block`.

### Finding Description
In `stacks-signer/src/v0/signer.rs`, `store_and_process_block_signature` first persists the incoming signature: [1](#0-0) 

If the sender is not `self` and has not previously sent an explicit `BlockPreCommit` (`has_committed` is false — true for any signer still on the pre-pre-commit "old" protocol, or simply the first time we see their vote), the function returns *before* reaching the actual signature-threshold computation (`total_signature_weight`, `min_weight`, `broadcast_signed_block`) at lines 2472–2537, diverting instead into `handle_block_pre_commit`.

`handle_block_pre_commit` immediately returns without recomputing anything if we have already signed the block ourselves: [2](#0-1) 

So the sequence: (1) this signer signs the block itself (`signed_self` becomes `Some`); (2) a peer's genuine acceptance signature later arrives for the first time from an address we haven't recorded a pre-commit from; (3) the signature is durably stored via `add_block_signature` (so it *is* in the DB), but the code path that would recompute `total_signature_weight` over all stored signatures and call `broadcast_signed_block` is never reached — it is short-circuited by the "already signed, do nothing" early return inside `handle_block_pre_commit`. Because `add_block_signature` returns `false` on a duplicate for that same address on any resend/retry (line 2454–2459), the diversion-then-early-return outcome for that peer's signature is final: nothing about a later arriving message from that same address will ever re-trigger the tally.

The only path that does recompute `total_signature_weight` from all stored signatures is a signature arrival for an address that already `has_committed` (i.e., self's own signing call, or a signer that had previously sent an explicit `BlockPreCommit`). If enough of the remaining weight needed to cross the 70% threshold comes from addresses that (a) had not yet pre-committed when their `Accepted` message arrives and (b) arrive *after* this local signer has already signed itself, the local signer's DB will contain enough total signature weight to cross the broadcast threshold, but no code path on this node will ever execute the recompute that discovers this and calls `broadcast_signed_block`.

### Impact Explanation
This is a liveness wedge on the affected signer for a specific block: it has already produced a valid signature (so it isn't wedged out of signing overall), but it can be prevented from ever recognizing that group consensus was reached and thus never assembles/broadcasts the aggregated signed block for the node to adopt. If a large fraction of the signer set is in this situation (each one signed early, then received the remaining acceptances only via the "not yet pre-committed" diversion), the block may never get pushed to the node by anyone even though enough weight exists, stalling tenure progress until a timeout/retry mechanism (e.g., re-proposal) intervenes. This matches the "signer wedged... acting on stale... losing ability to finalize" liveness category described in scope.

### Likelihood Explanation
Triggering requires only ordinary gossip timing plus at least one legitimate signer that either runs the older pre-commit-less protocol or whose explicit `BlockPreCommit` message is delayed/dropped relative to its `Accepted` signature — both are realistic, no majority collusion or key compromise needed, and a "one-slot miner plus gossip" can easily produce such timing by nature of normal network jitter (no attacker action is even required for the underlying condition, only the ordering of message arrival). The affected signer's own broadcast of the assembled block is what is lost; other signers who have not yet self-signed would still go through `handle_block_pre_commit`'s full logic and could still sign/broadcast, so the practical severity depends on how many signers hit the same early-self-signed race — this bounds the worst case but does not eliminate the per-node correctness gap.

### Recommendation
In `store_and_process_block_signature`, don't return unconditionally after diverting to `handle_block_pre_commit`; after that call, or instead of an early return, still perform the group signature-weight tally (or have `handle_block_pre_commit`'s "already signed" branch fall through to also invoke the group-threshold/broadcast check) so that a newly stored, genuine signature always causes a recomputation of `total_signature_weight` and a `broadcast_signed_block` attempt when threshold is reached, regardless of whether this local signer has already signed the block itself.

### Proof of Concept [1](#0-0) [3](#0-2) 

1. Signer S validates and signs block B itself (`signed_self` set, `store_and_process_block_signature` runs to completion for S's own signature, tallying whatever is in the DB at that time).
2. Peer signer P (running the older, pre-commit-less protocol, or simply whose `BlockPreCommit` message hasn't arrived yet) broadcasts `BlockResponse::Accepted` for B. On S, `store_and_process_block_signature` stores P's signature via `add_block_signature` (returns `true`, first time), then since `has_committed(B, P)` is false, calls `handle_block_pre_commit` and returns.
3. `handle_block_pre_commit` sees `block_info.signed_self.is_some()` is true and returns immediately (line 1316–1321) without recomputing `total_signature_weight`/checking the broadcast threshold.
4. Enough such peer signatures accumulate in S's DB (via step 2/3, repeated) to exceed the 70% signing threshold, but S never re-executes lines 2472–2537 of `store_and_process_block_signature` for any of them, so S never calls `broadcast_signed_block` for B even though its own signerdb has sufficient signature weight recorded.

            );
