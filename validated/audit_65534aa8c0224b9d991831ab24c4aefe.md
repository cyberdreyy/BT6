## Title
Stale confirmations from deleted multisig members are still counted toward the execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` removes a departing member from the member set and cancels only the *requests that member originally created*, but it never scrubs that member's entry out of the `confirmations` `HashSet<String>` of *other, still-pending* requests that the member had merely confirmed. Because `confirm()` compares `confirmations.len() + 1 >= self.num_confirmations` without re-validating that every stored confirmation still belongs to a current member, a stale confirmation left behind by a removed member can be combined with confirmations from fewer *live* members to push a pending request past the configured threshold and execute it — a multisig request executed below the real, live-member threshold.

### Finding Description
`confirm` records confirmations as `member.to_string()` strings in a per-request `HashSet<String>` and executes the request once the recorded count reaches `num_confirmations`: [1](#0-0) 

`delete_member` is the only place that mutates confirmation state when a member leaves. It cancels requests whose *original adder* (`r.member`) matches the removed member, and clears that member's `num_requests_pk` counter, but it does not walk `self.confirmations` to strip the removed member's string from confirmation sets of requests added by *other* members: [2](#0-1) 

Because `MultisigMember` membership is checked only in `current_member()`/`assert_valid_request` at the time a *new* confirmation is submitted, not retroactively over already-stored confirmations, a confirmation cast by an account/key that is later removed remains permanently counted in `confirmations.len()` for that request.

### Impact Explanation
This breaks the binding between "confirmations counted" and "live members" that the multisig's security model depends on. A request can execute (e.g. `Transfer`, `AddKey` with full access, `FunctionCall`, `DeleteMember`/`AddMember`) with fewer genuinely authorized, currently-valid confirmations than `num_confirmations` requires, because one or more counted confirmations belong to accounts/keys that have since been removed from the multisig. This is a multisig request executed below threshold, which is explicitly a Critical-impact scenario — it can be leveraged to move funds or grant an access key with fewer live approvals than the multisig's documented security guarantee.

### Likelihood Explanation
No attacker-controlled deployment, foundation privilege, or key compromise is required. Membership changes (`DeleteMember`) are a normal, documented multisig operation (e.g., rotating out a compromised or departing signer) that any legitimate multisig will perform over its lifetime. Any pending request that received a confirmation from a member before that member is later removed will silently retain the stale confirmation, so this can occur in ordinary operational usage, not just via a crafted attack.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests added by that member) and remove the departing member's string from each `HashSet<String>`. Alternatively, revalidate at `confirm()`/execution time that every string in the confirmations set still corresponds to a current member (filtering the set against `self.members` before comparing its length to `num_confirmations`).

### Proof of Concept
1. Initialize multisig with members `A, B, C, D` and `num_confirmations = 3`.
2. `A` calls `add_request` with a `Transfer` request (`request_X`) to an attacker-controlled account. (`add_request` only records `A` as the adder; it does not auto-confirm.)
3. `B` calls `confirm(request_X)` → `confirmations = {B}`.
4. `C` calls `confirm(request_X)` → `confirmations = {B, C}` (2 < 3, stored, not executed).
5. Separately, members legitimately vote (via `A`, `B`, `D`) to remove `C` from the multisig using `DeleteMember`. `delete_member` only cancels requests originally added *by C* — since `request_X` was added by `A`, its confirmations set `{B, C}` is left untouched even though `C` is no longer a member.
6. `D` calls `confirm(request_X)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so `request_X` executes the `Transfer`.
7. Result: the transfer executed with only two currently-valid confirmations (`B`, `D`); the third "confirmation" (`C`) came from an account/key that had already been removed from the multisig, violating the K-of-N guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
