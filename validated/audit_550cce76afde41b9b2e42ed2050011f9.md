This confirms the key point: cache restore failures are explicitly non-fatal by design at the orchestration layer. `runner.go`'s `prepare()` calls `cache.Run(ctx, e)` for each `CacheExtract` and on error only logs a warning via `r.logWarningf` — the returned error from `r.section(...)` is deliberately discarded (`_ = r.section(...)`), and `prepare()` unconditionally `return nil` [1](#0-0) . `TestPrepare_NonFatalFailures` explicitly asserts this: cache-restore failures (and artifact-download failures) never cause `prepare()` to return an error, and the job proceeds to the script stage regardless [2](#0-1) .

This matches exactly the scoped concern: a truncated/malformed archive can plant some files in the job's working directory (`wd`) via `Extract` before failing at `tr.Next()` or `io.Copy`, and the job's `script` stage still executes afterward using whatever partial, attacker-influenced state was left behind.

### Title
Cache-extractor treats extraction failure as non-fatal, allowing partial attacker-controlled archive contents to persist into job script execution - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go, functions/concrete/run/runner.go)

### Summary
`tarzstd.extractor.Extract` writes files to `e.dir` incrementally as it walks tar entries and returns immediately on the first error (corrupt header, truncated stream, `io.Copy` failure) without removing files already created [3](#0-2) . At the orchestration layer, `Runner.prepare` explicitly swallows cache/artifact extraction errors and always returns `nil`, so the job's `script` stage runs regardless of whether the cache/artifact restore succeeded, fully or partially [4](#0-3) .

### Finding Description
An attacker who controls the bytes of a cache/artifact archive (e.g., via cache poisoning from a shared cache key, or a job that later downloads its own previously-poisoned artifact) can craft a `tar.zst` stream whose first N entries are valid, followed by a corrupted tar header, truncated compressed stream, or a regular-file entry whose body is cut short mid-`io.Copy`.

In `extractor.Extract`:
- Each loop iteration calls `tr.Next()`, and on any non-EOF error it does `return err` immediately, without ever removing already-created files/dirs from previous iterations [5](#0-4) .
- For regular files, `os.Create(path)` followed by `io.Copy(f, tr)`; on copy failure the file handle is closed but the (possibly truncated) file is left on disk [6](#0-5) .
- There is no temp-file-then-rename pattern and no deferred cleanup/rollback of `e.dir` on error.

This means a crafted archive that fails partway through extraction leaves a predictable set of attacker-authored files in the job's working directory (`wd`, passed as `e.dir` from `CacheExtractorCommand.Execute` via `archive.NewExtractor(format, f, size, wd)` [7](#0-6) ).

Critically, at the caller side (`functions/concrete/run/runner.go`), `prepare()` runs cache restoration inside a section whose returned error is discarded (`_ = r.section(...)`), and any per-source `cache.Run` error is only logged via `r.logWarningf`, never propagated [8](#0-7) . `prepare()` then unconditionally returns `nil` [9](#0-8) , so `Runner.Run` proceeds straight to `r.executeSteps(jobCtx)` (the job script) regardless of cache/artifact restore outcome [10](#0-9) . This non-fatal behavior is intentional and explicitly tested by `TestPrepare_NonFatalFailures`, which asserts `prepare()` returns no error even when cache/artifact restoration fails [2](#0-1) .

Note: in the legacy `commands/helpers/cache_extractor.go` standalone helper command, an `Extract` error does call `logrus.Fatalln(err)` which exits the helper process nonzero [11](#0-10) . However, in the newer `functions/concrete/run` orchestration path, the failure of this whole helper invocation (or in-process extraction) is exactly what gets swallowed and logged only as a warning before the script stage runs — this is the reachable path that matches the question's described impact.

### Impact Explanation
A malicious/truncated cache or artifact archive can leave partially-extracted, attacker-controlled files in the build working directory, and the job script subsequently executes against that partial, "trusted-looking" workspace without any indication (other than a log warning) that the restore was incomplete. This is a concrete cache/artifact poisoning primitive: an attacker who can influence a shared cache key's content (e.g., a prior malicious job or MITM of an unauthenticated cache backend) can plant a subset of files — e.g., a `.bashrc`, `Makefile`, `package.json` script hook, or a binary on `PATH` inside the extraction dir — that the always-run script step will pick up, without needing the entire archive to be valid.

### Likelihood Explanation
Preconditions are realistic within the stated attacker model: an unprivileged pipeline author/job controls cache/artifact key content in scenarios such as shared/group-level cache keys or artifacts consumed by a downstream job in the same pipeline. Truncating or corrupting a valid `tar.zst` at an arbitrary offset is trivial and fully attacker-controlled; no special server-side condition is needed beyond the archive being fetched and passed to `Extract`. The non-fatal-by-design cache/artifact restore behavior is confirmed by an explicit unit test, so it is not a corner-case race but a deliberate, always-reachable code path.

### Recommendation
- In `tarzstd.extractor.Extract`, perform extraction into a temporary staging directory (or write files with a `.tmp` suffix and rename only after the whole archive has been read successfully), and roll back / discard the staging area on any error from `tr.Next()`, `io.Copy`, or header validation, so a failed extraction never leaves partial attacker content in `e.dir`.
- Alternatively/additionally, track all paths created during `Extract` and remove them on any returned error before propagating.
- At the orchestration layer (`functions/concrete/run/runner.go`), consider surfacing (not necessarily failing the job on) partial-extraction distinctly from "cache not found" — e.g., ensure any files written before a failure are removed by the extractor itself rather than relying on job authors to notice a warning, since the current design intentionally allows the script stage to proceed after a restore failure.

### Proof of Concept
Go test in `commands/helpers/archive/tarzstd` package:
1. Build a valid `tar.zst` stream with 2-3 regular file entries (e.g., `a.txt`, `b.txt` with known content), then corrupt the underlying tar bytes (e.g., truncate mid-way through the 3rd file's body, or flip bytes in the 3rd header) before zstd-compressing.
2. Call `extractor.Extract(context.Background())` with `dir` = a fresh temp directory.
3. Assert: `Extract` returns a non-nil error (`tr.Next()` or `io.Copy` failure).
4. Assert: `a.txt` and `b.txt` (fully-written prior entries) exist on disk in `dir` with attacker content — demonstrating no rollback occurred.
5. (Orchestration-level PoC) In `functions/concrete/run`, construct a `Config.CacheExtract` whose source resolves to this corrupted archive, run `Runner.prepare`, and assert it returns `nil` (matching `TestPrepare_NonFatalFailures`) while the partial files remain in the job's working directory — confirming the job's `script` stage will run against the poisoned partial state.
