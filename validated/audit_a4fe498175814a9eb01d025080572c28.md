### Title
Mid-epoch deposits credit unbacked shares for fee-on-transfer tokens in `depositDuringEpoch` - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.depositDuringEpoch` pulls the underlying with `_transferUnderlyingsFrom` but prices the minted tranche tokens, the minted strategy tokens, and the borrower transfer on the nominal `_amount` parameter rather than the amount actually received. If the vault's underlying token charges a transfer fee (e.g., USDT with fees enabled, PAXG, STA), the vault mints shares for the full `_amount` while only `_amount - fee` arrives, and then forwards the full `_amount` to the borrower. The shortfall is taken from the vault's existing token balance (other LPs' funds sitting in the buffer), so the depositor mints unbacked shares at the expense of all other tranche holders. ### Finding Description
In `depositDuringEpoch` (IdleCDOEpochVariant.sol:656-733):

```solidity
// Get underlyings from user
_transferUnderlyingsFrom(msg.sender, address(this), _amount);   // L685: receives _amount - fee
...
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;  // L724: priced on nominal _amount
_mintShares(_tranche, msg.sender, _minted, _amount);
expectedEpochInterest += interest;
IdleCreditVault(strategy).mintStrategyTokens(_amount);          // L730: backing on nominal _amount
_transferUnderlyings(_borrower(), _amount);                     // L732: sends full _amount out
```

Unlike the normal `_deposit` path — which correctly measures the balance delta (`_contractTokenBalance(_token) - _preBal`) before minting in `IdleCDOCreditVault._deposit` (IdleCDOCreditVault.sol:203-206) and `IdleCDO._deposit` (IdleCDO.sol:250-253) — `depositDuringEpoch` never compares pre/post balances. Three quantities are computed on the nominal value:

1. **Tranche tokens minted**: `_minted` uses `_amount` plus the pro-rata `trancheInterest`, so the attacker is credited principal shares (and the interest component) on funds never received.
2. **Strategy tokens**: `mintStrategyTokens(_amount)` inflates the strategy-token balance that backs `getContractValue`/NAV, so `_updateAccounting` treats the missing fee as real NAV.
3. **Borrower forwarding**: `_transferUnderlyings(_borrower(), _amount)` pushes the full nominal amount out; since only `_amount - fee` came in, the `fee` deficit is drained from the vault's residual token balance (queued buffer deposits, repayments awaiting `startEpoch`). If the vault holds no buffer the call reverts (harmless), but whenever buffer liquidity exists — the normal state during the buffer period — the deficit is silently socialized.

The same pattern exists in `IdleCDOEpochQueue.requestDeposit` (IdleCDOEpochQueue.sol:121-126) which records `epochPendingDeposits[nextEpoch] += amount` on the nominal amount, but the strongest in-scope instance is `depositDuringEpoch` since it directly mints shares.

### Impact Explanation
Direct theft / dilution of other LPs, quantified: with a fee `f` on a deposit of `A`, the attacker receives tranche tokens redeemable for ~`A + trancheInterest` while contributing only `A - f`. Net extraction of `f` per deposit from the vault's token balance backing other tranche holders' NAV, plus the `trancheInterest` credited on the unbacked amount. Repeatable every time the epoch is running, `isDepositDuringEpochDisabled == false`, AYS is off, and the vault holds buffer liquidity — conditions met during every running epoch of a standard credit vault. There is no skim/guard to correct it: `_skimDonatedAssets` runs before the transfer and the surplus stays inside NAV accounting, so the loss is permanent for remaining depositors.

### Likelihood Explanation
Requires the vault's `token` to be a fee-on-transfer or deflationary ERC20. The codebase supports arbitrary underlyings (`token` is set at init) and credit vaults are designed around USDC/USDT; USDT has a built-in (currently disabled but toggleable) fee mechanism, and tokens like PAXG carry a mandatory fee. Medium likelihood — it is a real, reachable minting-path mismatch rather than a theoretical one, gated only by token choice.

### Recommendation
Measure the actual received amount with a pre/post balance check and use it everywhere downstream:

```solidity
address _token = token;
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(_token) - _preBal;
// use _received instead of _amount for minted calc, mintStrategyTokens and _transferUnderlyings(borrower)
```

Apply the same fix to `requestDeposit`/`processDepositsToBorrower` in `IdleCDOEpochQueue` so `epochPendingDeposits` and the prefunded borrower transfer reflect the received amount.

### Proof of Concept
Foundry fork test against a deployed `IdleCDOEpochVariant` whose underlying is replaced by a FoT mock (or USDT with fees enabled via storage on mainnet fork):

```solidity
function test_FoTDepositDuringEpochDilutesLPs() public {
    // setup: FoT token with 1% fee as vault `token`; LP_A and LP_B deposit normally,
    // epoch 0 started by manager (isEpochRunning == true), buffer liquidity present.

    uint256 amount = 1_000_000e6;
    FoTToken fot = FoTToken(idleCDO.token());
    fot.mint(attacker, amount);

    uint256 vaultBalPre  = fot.balanceOf(address(idleCDO));
    uint256 navPre       = idleCDO.getContractValue();

    vm.startPrank(attacker);
    fot.approve(address(idleCDO), amount);
    uint256 minted = idleCDO.depositDuringEpoch(amount, idleCDO.AATranche());
    vm.stopPrank();

    // vault only received 990_000e6 but forwarded 1_000_000e6 to borrower
    assertEq(fot.balanceOf(address(idleCDO)), vaultBalPre - 10_000e6); // buffer drained by fee

    // attacker was minted shares + trancheInterest on the full 1_000_000e6
    // NAV was inflated by mintStrategyTokens(amount) -> attacker withdraws ~1M worth,
    // the missing 10k is borne by LP_A / LP_B on their next requestWithdraw.
}
```

Run after epoch stop/buffer reopen and let the attacker `requestWithdraw`/`withdrawAA`: the attacker redeems ~`amount` worth of underlying while having supplied `amount - fee`; the residual shortfall reduces `virtualPrice` for the remaining LPs — direct theft quantified at `fee * amount / 100` per deposit.
