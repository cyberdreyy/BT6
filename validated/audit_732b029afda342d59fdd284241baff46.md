### Title
Unvalidated `field.Size` in `readZipExtraField` allows unbounded per-entry allocation during zip extraction - ([File: helpers/archives/zip_extra.go])

### Summary
`readZipExtraField` allocates `make([]byte, field.Size)` using an attacker-controlled 16-bit value read directly from the zip Extra field, without checking it against the number of bytes actually remaining in the reader. Because `ExtractZipArchive` calls `processZipExtra` for every entry in an attacker-supplied artifact/cache zip, an archive containing many entries with truncated/oversized Extra fields forces the runner to repeatedly allocate large (up to 64KB) buffers, causing avoidable memory/GC pressure that scales with entry count.

### Finding Description
`readZipExtraField` reads a 4-byte `ZipExtraField{Type, Size}` header from `r` (a `bytes.Reader` wrapping `file.Extra`), then does `data = make([]byte, field.Size)` followed by a single `r.Read(data)`, with no check that `field.Size` is less than or equal to the bytes remaining in `r`: [1](#0-0) 

This is invoked from `processZipExtra`, which loops over `file.Extra` for every file in the archive during `ExtractZipArchive`: [2](#0-1) 

Because `field.Size` is a `uint16`, an attacker can craft a 4-byte Extra header declaring `Size = 65535` while supplying far fewer actual bytes. `readZipExtraField` will still allocate a 65535-byte buffer before `r.Read` returns a short/zero read, and this pattern can be repeated once per zip entry. A malicious artifact/cache zip with a large number of entries (each requiring only a few dozen bytes of local/central-directory overhead plus a 4-byte crafted Extra header) can drive many such allocations during extraction, well beyond what the legitimate archive content requires — this is reachable purely from artifact/cache content the job author controls, with no authentication or privilege beyond running a pipeline. No existing check (path validation, overwrite guards, etc.) constrains the size of the `make()` call relative to actual remaining Extra bytes.

### Impact Explanation
Each crafted entry can force one ~64KB allocation that is immediately discarded (since the field type won't match `ZipUIDGidFieldType`/`ZipTimestampFieldType`), so the primary effect is transient allocation/GC churn proportional to entry count rather than a single unbounded allocation or sustained heap growth. With a sufficiently large entry count (tens or hundreds of thousands, achievable in a modestly sized zip since each malicious entry adds only a few bytes of overhead), this produces measurable extra CPU/GC pressure during extraction on the runner host. It does not, however, allow retaining gigabytes of live memory simultaneously — the buffers are per-iteration and short-lived, which limits (but does not eliminate) the severity of the described "memory exhaustion" scenario on a shared host.

### Likelihood Explanation
The precondition (attacker controls artifact/cache zip content via a normal CI job) is realistic and requires no elevated privilege. Constructing a zip with many small entries with truncated/oversized Extra headers is straightforward. The bug is deterministically reachable via `ExtractZipArchive` → `processZipExtra` → `readZipExtraField` whenever cache/artifacts are extracted.

### Recommendation
In `readZipExtraField`, bound `field.Size` by the bytes actually remaining in `r` before allocating (e.g., using `r.Len()` for `*bytes.Reader`, or wrapping with `io.LimitReader`), and reject/skip fields whose declared size exceeds the remaining Extra bytes instead of allocating and then failing on a short read. Additionally, use `io.ReadFull` instead of a single `r.Read` call to detect truncation reliably.

### Proof of Concept
```go
func TestReadZipExtraField_OversizedDeclaredSize(t *testing.T) {
    // 4-byte header declaring Size=65535 but with zero actual payload bytes
    header := make([]byte, 4)
    binary.LittleEndian.PutUint16(header[0:2], 0x9999) // unknown type
    binary.LittleEndian.PutUint16(header[2:4], 65535)  // Size >> remaining (0) bytes

    r := bytes.NewReader(header)
    field, data, err := readZipExtraField(r)

    // Current behavior: a 65535-byte buffer is allocated even though 0 bytes
    // of payload actually existed, before err becomes io.EOF.
    assert.Equal(t, uint16(65535), field.Size)
    assert.Equal(t, 65535, len(data)) // demonstrates unchecked allocation
    assert.Error(t, err)              // io.EOF, since payload was truncated
}
```
A follow-up fuzz/integration test can construct a zip with N (e.g. 200,000) entries, each with a 4-byte Extra field declaring `Size=65535`, and measure allocation counts/GC pause time during `ExtractZipArchive` to assert an upper bound is enforced (i.e., a fixed cap or rejection) once the fix is applied.

func readZipExtraField(r io.Reader) (field ZipExtraField, data []byte, err error) {
	err = binary.Read(r, binary.LittleEndian, &field)
	if err != nil {
		return
	}

	data = make([]byte, field.Size)
	_, err = r.Read(data)
	if err != nil {
		return
	}
	return
}
