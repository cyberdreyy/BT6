### Title
`onStopEpoch` validates liquidity with `convertToAssets` but executes `vault.withdraw` — check-then-act mismatch permanently blocks `stopEpoch` (rebinding-style TOCTOU) — ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
The DNS-rebinding bug class is "validate a remote resource with one resolution, then fetch it with a second resolution that answers differently." In `ProgrammableBorrower.onStopEpoch`, the solvency guard resolves vault liquidity via `_currentVaultAssets()` (`convertToAssets`), but the actual fetch uses `vault.withdraw(shortfall)`, which is bound by `maxWithdraw` (real-time vault liquidity / limits), not by `convertToAssets`. When `convertToAssets` overstates instantly-withdrawable liquidity — the normal state of a fully-utilized MetaMorpho/ERC4626 vault — the check passes, `withdraw` reverts, and `stopEpoch` throws `StopEpochVaultLiquidityUnavailable` forever while the condition holds, instead of entering the default path.

### Finding Description
`onStopEpoch` first decides whether the vault position economically covers the recall shortfall:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:240-253
if (_amountRequired > onHand) {
    uint256 shortfall = _amountRequired - onHand;
    // If the vault shares do not economically cover the shortfall, let IdleCDO's later
    // transferFrom fail and use the existing default path.
    if (shortfall > _currentVaultAssets()) return true;
    try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
        ...
    } catch {
        revert StopEpochVaultLiquidityUnavailable();
    }
}
```

`_currentVaultAssets()` is `vault.convertToAssets(shares)` — the *accounting* value of the position. `vault.withdraw` is bound by `maxWithdraw` — the *redeemable* value. For lending vaults (MetaMorpho), `convertToAssets` counts assets lent out to Morpho markets; `maxWithdraw` reflects only idle market liquidity. These are deliberately different "resolutions" of the same position, exactly like the two DNS answers in the reference advisory.

This is a known, deliberate design choice: the codebase explicitly rejects `maxWithdraw` because Gauntlet's `maxWithdraw` returned 0 on the fork (`testProgrammableBorrowerStopEpochDoesNotTrustBrokenMaxWithdraw`). The consequence is the inverse failure mode is unhandled: when `maxWithdraw < shortfall <= convertToAssets`, the guard passes, `withdraw` reverts inside `stopEpoch`, the revert is retryable (does **not** trigger `defaulted`), and no default/loss path is ever entered because IdleCDO's `transferFrom` is only reached after the hook succeeds. Per the hook's own comment, `totalInterestDueNow()` is read by `IdleCDOEpochVariant` *before* the hook, so the epoch interest snapshot, the liquidity guard, and the `withdraw` fetch are three separate resolutions of vault state in one flow.

Broken invariant: the epoch state machine must always be able to terminate — either settle (success + `settleBorrowerInterest`) or default (`transferFrom` failure → `onDefault`). This creates a third, unintended terminal state: running forever with a revert.

### Impact Explanation
Temporary freezing of the entire pool. While the vault's instant liquidity is below `shortfall` but its share value covers it, `stopEpoch` reverts on every retry. All pending withdraw requests (`epochPendingWithdraws`/strategy `pendingWithdraws`) and tranche holders' funds remain locked in the running epoch; `requestWithdraw` claims cannot be serviced because the epoch never stops. Magnitude: up to the full pool NAV (all deposited tranche assets) frozen for the duration of vault illiquidity. No privileged actor can unstick it: `emergencyExitVault`/`redeem` face the same vault liquidity constraint, and `setVault` reverts while `epochAccountingActive` or shares remain.

### Likelihood Explanation
Moderate. No malicious action is required — a fully-utilized MetaMorpho vault (utilization ≈ 100%) naturally has `convertToAssets >> maxWithdraw`. An unprivileged user of the programmable borrower's ERC4626 vault (explicitly in-scope) can force this state at will: borrow/withdraw the vault's idle liquidity right before `stopEpoch`, raising utilization so `withdraw(shortfall)` reverts. The attacker pays only gas/borrow costs; griefing persists until vault liquidity returns.

### Recommendation
Resolve liquidity once and act on that same resolution — the equivalent of pinning the resolved IP for the fetch:

- Replace the `convertToAssets`-based guard with `vault.maxWithdraw(address(this))`, and call `vault.withdraw(min(shortfall, maxWithdraw))`; treat any residual unmet `shortfall` as a real shortfall that flows into the existing default/`transferFrom`-failure path rather than reverting.
- Alternatively, attempt `withdraw` unconditionally inside the `try`, and on `catch` fall through so IdleCDO's `transferFrom` fails and the default path is taken, instead of reverting `StopEpochVaultLiquidityUnavailable`.
- If `maxWithdraw` is untrusted (as with the Gauntlet fork), query it inside the same call that performs `withdraw` semantics, or clamp the withdraw amount to it, so the guard and the fetch can never disagree.

### Proof of Concept
Reproducible Foundry PoC sketch (extends the existing `MockStopEpochLiquidityVault` harness in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testStopEpochFrozenByConvertVsMaxWithdrawMismatch() external {
    MockStopEpochLiquidityVault limitedVault = new MockStopEpochLiquidityVault(USDC);
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);
    vm.prank(manager);
    programmableBorrower.setVault(address(limitedVault));

    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0);

    uint256 pending = strategy.pendingWithdraws();
    // Economic coverage holds: shares are worth more than the shortfall...
    assertGe(limitedVault.convertToAssets(limitedVault.balanceOf(address(programmableBorrower))), pending);
    // ...but instantly-withdrawable liquidity is 1 wei short of the shortfall.
    limitedVault.setWithdrawLimit(pending - 1);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Every stopEpoch attempt reverts; default is never entered; epoch stays running.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertFalse(cdoEpoch.defaulted(), "default path unreachable while convertToAssets covers shortfall");
    assertTrue(cdoEpoch.isEpochRunning(), "epoch permanently running while vault liquidity < convertToAssets value");
    // Pending withdraw requests cannot be claimed: funds frozen until the external vault regains liquidity.
    assertGt(strategy.pendingWithdraws(), 0);
}
```

Uncertainty note: I confirmed the guard/fetch mismatch in `ProgrammableBorrower.sol:240-253` and the read-ordering comment at line 256 ("`totalInterestDueNow()` was already read by IdleCDO before calling this hook"), but I could not pull the full body of `IdleCDOEpochVariant.stopEpoch` to verify every surrounding guard; the finding assumes only the behavior documented in the contract's own comments and the existing tests.
