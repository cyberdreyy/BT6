`max_timestamp` Overwrite Instead of Maximize Allows Stale-Price Inclusion in MetaOracle Median — (File: `crates/sui-oracle/move/oracle/sources/meta_oracle.move`)

---

### Summary

`MetaOracle.add_simple_oracle` unconditionally **overwrites** `max_timestamp` with each newly added oracle's timestamp instead of keeping the running maximum. Because `combine` anchors the entire freshness window to `max_timestamp`, an adversary who controls the order in which `SimpleOracle` objects are passed can shift the window arbitrarily, causing genuinely stale readings to survive the staleness filter and be fed into the median calculation.

---

### Finding Description

`MetaOracle` is a transient (no `key`/`store`) aggregator struct that collects readings from multiple `SimpleOracle` shared objects and returns a median `TrustedData<T>`. Its freshness logic works in two steps:

**Step 1 – accumulation** (`add_simple_oracle`, line 41):

```move
public fun add_simple_oracle<T: copy + drop + store>(
    meta_oracle: &mut MetaOracle<T>,
    oracle: &SimpleOracle
) {
    let oracle_data = oracle::simple_oracle::get_latest_data(oracle, meta_oracle.ticker);
    if (option::is_some(&oracle_data)) {
        meta_oracle.max_timestamp = data::timestamp(option::borrow(&oracle_data)); // ← BUG
    };
    vector::push_back(&mut meta_oracle.oracle_data, oracle_data);
}
```

`max_timestamp` is **replaced** by each oracle's timestamp. After N calls the field holds the timestamp of the **last oracle added that had data**, not the true maximum across all oracles.

**Step 2 – filtering** (`combine`, lines 52-60):

```move
let min_timestamp = max_timestamp - time_window_ms;
...
if (data::timestamp(&oracle_data) > min_timestamp) {
    // accepted as fresh
}
```

The freshness window is `(max_timestamp − time_window_ms, ∞)`. Because `max_timestamp` is wrong, so is `min_timestamp`.

**Root-cause invariant broken**: the field named `max_timestamp` is supposed to be `max(ts₁, ts₂, …, tsₙ)` so that the window is anchored to the most recent observation. The assignment on line 41 violates this invariant whenever oracles are not added in strictly ascending timestamp order.

**Concrete manipulation**: suppose `time_window_ms = 60 000 ms` and three oracles have timestamps:

| Oracle | Timestamp |
|--------|-----------|
| A (fresh, manipulated) | 1 000 000 |
| B (legitimate) | 990 000 |
| C (stale) | 800 000 |

If the caller adds them in order **A → B → C**:
- After A: `max_timestamp = 1 000 000`
- After B: `max_timestamp = 990 000`
- After C: `max_timestamp = 800 000`
- `min_timestamp = 800 000 − 60 000 = 740 000`
- All three pass (`1 000 000 > 740 000`, `990 000 > 740 000`, `800 000 > 740 000`)

With the correct `max_timestamp = 1 000 000`, `min_timestamp = 940 000`, and oracle C (800 000) would be **excluded**. The stale reading C is now included in the median, diluting or shifting the result toward the attacker's preferred value.

---

### Impact Explanation

Any caller can construct a `MetaOracle` within a single transaction (the struct is transient), choose which `SimpleOracle` shared objects to pass, and choose their order. By placing a stale oracle last the caller lowers `max_timestamp`, widens the effective freshness window, and forces stale readings into the median. Downstream protocols that consume `TrustedData<T>` from `median()` — e.g., for pricing, liquidation thresholds, or settlement — receive a price that does not reflect the intended freshness guarantee. This constitutes **harmful smart-contract behavior** (Medium impact under the allowed-impact gate).

---

### Likelihood Explanation

- `MetaOracle` is a public API with no access control on `add_simple_oracle` or `median`.
- `SimpleOracle` objects are shared objects readable by any address.
- The attacker needs only to call the downstream protocol's entry function and supply oracle arguments in a chosen order — no privileged role, no key, no governance quorum required.
- The bug is triggered by any non-ascending timestamp ordering, which can occur naturally or be forced deliberately.

---

### Recommendation

Replace the unconditional assignment on line 41 with a maximum:

```move
// Before (buggy)
meta_oracle.max_timestamp = data::timestamp(option::borrow(&oracle_data));

// After (correct)
let ts = data::timestamp(option::borrow(&oracle_data));
if (ts > meta_oracle.max_timestamp) {
    meta_oracle.max_timestamp = ts;
};
```

`sui::math::max` can also be used directly:

```move
meta_oracle.max_timestamp = sui::math::max(
    meta_oracle.max_timestamp,
    data::timestamp(option::borrow(&oracle_data))
);
```

Additionally, consider anchoring `min_timestamp` to the on-chain `Clock` rather than to oracle-supplied timestamps, so the freshness window cannot be shifted by data the oracles themselves report.

    fun combine<T: copy + drop>(meta_oracle: MetaOracle<T>, ): (vector<T>, vector<address>) {
        let MetaOracle { mut oracle_data, threshold, time_window_ms, ticker: _, max_timestamp } = meta_oracle;
        let min_timestamp = max_timestamp - time_window_ms;
        let mut values = vector<T>[];
        let mut oracles = vector<address>[];
        while (vector::length(&oracle_data) > 0) {
            let oracle_data = vector::remove(&mut oracle_data, 0);
            if (option::is_some(&oracle_data)) {
                let oracle_data = option::destroy_some(oracle_data);
                if (data::timestamp(&oracle_data) > min_timestamp) {
                    vector::push_back(&mut values, *data::value(&oracle_data));
                    vector::push_back(&mut oracles, *data::oracle_address(&oracle_data));
                };
            };
        };
        assert!(vector::length(&values) >= threshold, EValidDataSizeLessThanThreshold);
        (values, oracles)
    }
