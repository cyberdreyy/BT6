### Title
Stale rejection weight is never retracted when a signer flips to acceptance, letting one signer's weight be double-counted in both tallies - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tracks, per proposed block, `total_weight_approved` and `total_weight_rejected` from `BlockResponse` messages, and `SignerCoordinator` uses these two sums to decide whether a block is globally accepted or globally (>30%-weight) rejected. The two code paths that update these sums are gated by independent conditions instead of a single "current vote" invariant, so a signer that first rejects and later re-evaluates to accept the same block gets its weight counted in *both* tallies simultaneously.

### Finding Description
In `handle_signer_message`/`process_event` of `StackerDBListener::run` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`):

- The `Rejected` branch adds `signer_entry.weight` to `total_weight_rejected` gated on `block.responded_signers.insert(slot_id)` returning `true` (i.e., "first time we've seen a response from this slot"): [1](#0-0) 

- The `Accepted` branch adds `signer_entry.weight` to `total_weight_approved` gated only on `!block.gathered_signatures.contains_key(&slot_id)`, i.e. "we have not yet recorded a signature for this slot" — it never checks or clears `responded_signers`, and never subtracts anything from `total_weight_rejected`: [2](#0-1) 

Consequence: if a signer at `slot_id` first sends `Rejected` (its weight is added to `total_weight_rejected` and the slot is recorded in `responded_signers`), and the same signer later legitimately flips its decision and sends `Accepted` for the same block, the `Accepted` branch's gate (`gathered_signatures.contains_key`) is still `false`, so the signer's weight is *also* added to `total_weight_approved`. The stale reject weight is never removed. The same one signer is now counted in both `total_weight_approved` and `total_weight_rejected`.

This flip is not a hypothetical or malicious-only path — it is a first-class, gossip/re-evaluation-driven behavior of the v0 signer: `BlockState` explicitly allows `LocallyRejected --> LocallyAccepted` on re-evaluation, and the signer's own test suite exercises exactly this transition (a signer that rejects a block because of a conflicting sibling, and later signs it once the conflict is proven stale/non-canonical): [3](#0-2) [4](#0-3) 

`SignerCoordinator::wait_for_signatures` (the consumer of these two sums) checks the rejection threshold *before* the acceptance threshold: [5](#0-4) 

Because `total_weight_rejected` is a strictly-increasing accumulator that a flip can never reduce, a block that legitimately reaches ≥70% real acceptance weight can still trip the `>30%`-rejected branch first if the inflated (double-counted) rejected sum crosses `total_weight - weight_threshold`, since one signer's weight is present in both sides of the sum at once. This breaks the intended equality "aggregated approved/rejected weight == the current, single vote of each signer" and can cause the coordinator to declare `SignersRejected` (and exclude txids based on `failed_txids` weight, which uses the same non-retracted rejected pool) for a block that in reality has enough live signatures, wedging block production for that tenure.

### Impact Explanation
This is a liveness-affecting miscount: a signer's outdated rejection is never retracted from the aggregate tally used by the miner-side coordinator to decide global acceptance/rejection, so genuine accepting weight can be neutralized or overridden by stale, double-counted rejection weight from the very same signers who changed their mind. This matches the "aggregated-weight vs verified-accepts" equality break called out in scope, and can wedge a valid, ready-to-sign block from ever being pushed (a High-severity liveness consequence), triggered by ordinary gossip/re-evaluation from a single signer — no majority collusion required.

### Likelihood Explanation
The reject→accept flip is a documented, tested, and reachable state transition of the v0 signer state machine (`LocallyRejected → LocallyAccepted` on re-evaluation, e.g. when a conflicting sibling block becomes stale/non-canonical). Any signer whose earlier rejection is later superseded by an acceptance for the same block hash will trigger the double count; a malicious signer can trivially and deliberately reproduce it by broadcasting `Rejected` then `Accepted` for the same `signer_signature_hash`, since neither message is checked against the other.

### Recommendation
Track a single current vote per slot (e.g., an enum `Option<Vote::Accepted(sig)/Rejected>` per `slot_id` in `BlockStatus`) instead of two independently-gated accumulators. When a slot's vote changes, subtract the old weight contribution from whichever tally it was previously counted in before adding the new one, so `total_weight_approved` and `total_weight_rejected` always reflect only the latest response from each `slot_id`.

### Proof of Concept
1. Node starts `wait_for_signatures` for a proposed block `B` with signer weight threshold 70%.
2. Signer `S` (weight `w`) broadcasts `BlockResponse::Rejected` for `B`. `StackerDBListener` sets `responded_signers.insert(S)` and `total_weight_rejected += w`.
3. `S` later re-evaluates (e.g., its previously-signed conflicting sibling goes stale, per `stale_sibling_replaced_when_canonical_tip_below`) and broadcasts `BlockResponse::Accepted` for `B`.
4. `StackerDBListener`'s `Accepted` branch checks only `!gathered_signatures.contains_key(S)` (true) and adds `total_weight_approved += w`, without touching `total_weight_rejected`.
5. `S`'s weight `w` is now counted in both `total_weight_approved` and `total_weight_rejected`. If enough other signers behave similarly (or a single high-weight signer does this), `total_weight_rejected + weight_threshold > total_weight` can become true even though the real, current, per-signer vote count would show ≥70% acceptance, causing `SignerCoordinator::wait_for_signatures` to return `Err(NakamotoNodeError::SignersRejected)` for a block that should have been accepted.
