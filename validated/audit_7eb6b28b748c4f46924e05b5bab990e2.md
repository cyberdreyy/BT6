### Title
Unselected blocking send on `errCh` in `kubernetesLogProcessor.attach` can permanently leak the log-processor goroutine - (File: executors/kubernetes/log_processor.go)

### Summary
In `attach`, once `processStream` returns `outputLogFileNotExistsExitCode`, the goroutine performs an unconditional, unselected `errCh <- fmt.Errorf(...)` send (line 183) instead of racing it against `ctx.Done()`. If the consumer of `errCh` has already stopped reading (e.g., because it exited its own select loop on `ctx.Done()`), this send blocks forever, permanently leaking the goroutine spawned in `Process()`.

### Finding Description
`attach`'s main loop only checks `ctx.Done()` in the `select` that gates entry into each iteration (line 170-174); once inside the iteration, `l.processStream(ctx, outCh)` is called and, on `outputLogFileNotExistsExitCode`, the error is sent to `errCh` with a plain blocking send with no `select`/`ctx.Done()` fallback: [1](#0-0) 

The comment block at lines 154-158 confirms this exit code is a *normal, expected* condition — it fires whenever the job transitions to the "cleanup variables" step, which recreates `output.log`: [2](#0-1) 

So virtually any job reaching the cleanup-variables stage will exercise this exact branch — it's not an exotic trigger. The `errCh` is unbuffered (`make(chan error)`, line 133), and the goroutine that runs `attach` is fired-and-forgotten inside `Process()`: [3](#0-2) 

Critically, `Finalize()` only waits on `l.wg`: [4](#0-3) 

but `l.wg.Add(1)`/`Done()` is only used inside `scan()` for the line-scanning sub-goroutine, not for the top-level `attach` goroutine itself: [5](#0-4) 

This means the `attach` goroutine's lifetime is entirely untracked by `Finalize()`. If the caller's consumption loop (in `kubernetes.go`) stops reading `outCh`/`errCh` after `ctx` is cancelled — a normal pattern where the caller's own `select` races `errCh`/`outCh` against `ctx.Done()` and returns on cancellation — then the next time `attach` hits `outputLogFileNotExistsExitCode` and tries to send on `errCh`, there is no reader and no timeout/cancellation guard on that specific send, so it blocks indefinitely.

### Impact Explanation
Each job that (a) triggers the cleanup-variables log-file recreation path and (b) has its caller stop draining `errCh` around the same time (e.g. due to an earlier failure/cancellation) leaves one goroutine permanently blocked on the channel send. Because `Finalize()` does not join this goroutine, repeated occurrences across many jobs/projects accumulate leaked goroutines in the shared runner process, consuming memory and goroutine-table slots over the runner's lifetime — a resource-exhaustion condition reachable by ordinary job cancellation/failure timing, without any privileged access.

### Likelihood Explanation
The `outputLogFileNotExistsExitCode` branch is hit on essentially every job during the normal cleanup-variables step, per the code's own comment. The only additional precondition is that the caller has already stopped reading `errCh`/`outCh` (typically because it exited on `ctx.Done()` due to job cancellation, timeout, or an earlier step failure) before the recreated log file is detected. This is a plausible timing race in normal operation — no crafted payloads or special privileges are required, only ordinary job cancellation timing — making it moderately likely to occur over the lifetime of a busy runner, though not deterministic on every job.

### Recommendation
Wrap the `errCh <- err` send in a `select` with `ctx.Done()` (and/or a done-channel signaled by the consumer) so the goroutine can exit instead of blocking forever, e.g.:
```go
select {
case errCh <- fmt.Errorf("output log file deleted, cannot continue %w", err):
case <-ctx.Done():
    return
}
```
Additionally, register the top-level `attach` goroutine with `l.wg` in `Process()` so `Finalize()` actually joins it, ensuring the leak is at least observable/blocking on shutdown rather than silently permanent.

### Proof of Concept
Go unit test sketch for `log_processor_test.go`:
```go
func TestAttach_ErrChSendDoesNotBlockAfterCtxCancel(t *testing.T) {
    logger, _ := test.NewNullLogger()
    lp := &kubernetesLogProcessor{
        backoff: &mockBackoff{}, // returns 0 duration
        logger:  logger,
        logStreamer: &mockStreamerReturningExitCode{
            exitCode: outputLogFileNotExistsExitCode,
        },
    }

    ctx, cancel := context.WithCancel(context.Background())
    outCh := make(chan string)
    errCh := make(chan error) // unbuffered, deliberately unread

    done := make(chan struct{})
    go func() {
        lp.attach(ctx, outCh, errCh)
        close(done)
    }()

    // Simulate consumer giving up right after cancellation, without draining errCh
    cancel()

    select {
    case <-done:
        // expected: attach returns promptly
    case <-time.After(2 * time.Second):
        t.Fatal("attach() goroutine leaked: blocked on errCh send after ctx cancellation")
    }
}
```
Expected current behavior: the test times out/fails, demonstrating `attach()` never returns because it is stuck on the unselected `errCh <-` send at line 183, confirming the goroutine leak.
