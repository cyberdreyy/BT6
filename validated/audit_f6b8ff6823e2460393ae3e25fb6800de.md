### Title
JsonRpcRequestProcessor::bank() silently falls back to root_bank() when the commitment-resolved slot is missing, returning wrong-slot account/state data - (File: rpc/src/rpc.rs)

### Summary
Analogous to the reported use of Chainlink's deprecated, unchecked `latestAnswer()` (which returns a value without validating that it is fresh/valid data), the `JsonRpcRequestProcessor::bank()` helper resolves a bank for a given `CommitmentConfig` and, if the resolved slot is not present in `BankForks`, silently substitutes the root bank instead of surfacing an error. Callers and downstream RPC consumers cannot distinguish this substituted response from a valid one, so a caller can be given state for an unexpected slot without any signal that the requested slot's data was unavailable.

### Finding Description
`bank()` resolves a `Bank` for a given commitment level: for `confirmed` it clones the optimistically-confirmed bank, and for `processed`/`finalized` it looks up a slot number via `block_commitment_cache.slot_with_commitment(...)` and then calls `r_bank_forks.get(slot)`. [1](#0-0) 

When `r_bank_forks.get(slot)` returns `None` (e.g., due to a known snapshot-creation bug or a race between an old bank being purged and `BlockCommitmentCache` not yet reflecting the new state), the code does not propagate an error to the RPC caller. Instead it logs a `warn!` and returns `r_bank_forks.root_bank()` — a bank for a different (older) slot than the one that was actually requested/resolved by commitment: [2](#0-1) 

This helper is invoked throughout `rpc.rs` (16 call sites for `self.bank(commitment)`/`self.bank(Some(...))`) to service standard, unprivileged JSON-RPC read methods (e.g., account/balance/supply/epoch queries) that accept a `commitment` parameter but not `min_context_slot`. Unlike `get_bank_with_config`, which explicitly validates `min_context_slot` and returns a `MinContextSlotNotReached` error when the bank is stale, the `bank(commitment)` path has no such validation and returns the wrong bank transparently as if it fully satisfied the requested commitment level.

### Impact Explanation
Because the substitution is silent, RPC clients querying with `processed` or `finalized` commitment can receive a response computed against `root_bank()` — i.e., data for a slot different than what the commitment resolution intended — with no error or contextual slot field indicating a fallback occurred. Callers building applications on top of this RPC (balance checks, account state reads, epoch data, etc.) may act on stale/wrong-slot data believing it reflects the requested commitment level, which is a wrong-slot/account data return triggered purely by an unprivileged, single RPC request (no special access needed).

### Likelihood Explanation
The code comment itself acknowledges this is a known, reachable condition: it explicitly documents two triggering conditions — a known snapshot-creation bug where the bank at a given slot is not included in a snapshot, and a race window after an old bank is purged from `BankForks` before `BlockCommitmentCache` is updated. Both can occur during normal validator operation without any adversarial validator/peer behavior required, making this reachable by any unprivileged client issuing ordinary read RPC requests during those windows.

### Recommendation
Do not silently substitute `root_bank()` when the resolved slot is missing from `BankForks`. Instead, propagate an explicit RPC error (consistent with how `get_bank_with_config` handles `min_context_slot` mismatches) so clients can detect and retry rather than silently consuming data for an unexpected slot. At minimum, the response should be tagged/annotated with the actual slot served, so callers can validate it matches their expectations.

### Proof of Concept
1. An RPC client sends a standard request (e.g. `getBalance`, `getAccountInfo`, `getEpochSchedule`) with `commitment: "finalized"` (or `"processed"`).
2. Internally, `JsonRpcRequestProcessor::bank(Some(commitment))` computes `slot = block_commitment_cache.slot_with_commitment(...)`. [3](#0-2) 
3. If that particular bank has since been purged from `BankForks` (race with cache update) or was excluded from a snapshot at startup, `r_bank_forks.get(slot)` returns `None`.
4. The processor returns `r_bank_forks.root_bank()` instead of an error, and this bank is used to answer the RPC call as if it correctly satisfied the client's `finalized` (or `processed`) commitment request, with only a `warn!` log on the validator side (invisible to the client) indicating the substitution occurred. [4](#0-3)

    #[allow(deprecated)]
    fn bank(&self, commitment: Option<CommitmentConfig>) -> Arc<Bank> {
        debug!("RPC commitment_config: {commitment:?}");

        let commitment = commitment.unwrap_or_default();
        if commitment.is_confirmed() {
            let bank = self
                .optimistically_confirmed_bank
                .read()
                .unwrap()
                .bank
                .clone();
            debug!("RPC using optimistically confirmed slot: {:?}", bank.slot());
            return bank;
        }

        let slot = self
            .block_commitment_cache
            .read()
            .unwrap()
            .slot_with_commitment(commitment.commitment);

        match commitment.commitment {
            CommitmentLevel::Processed => {
                debug!("RPC using the heaviest slot: {slot:?}");
            }
            CommitmentLevel::Finalized => {
                debug!("RPC using block: {slot:?}");
            }
            CommitmentLevel::Confirmed => unreachable!(), // SingleGossip variant is deprecated
        };

        let r_bank_forks = self.bank_forks.read().unwrap();
        r_bank_forks.get(slot).unwrap_or_else(|| {
            // We log a warning instead of returning an error, because all known error cases
            // are due to known bugs that should be fixed instead.
            //
            // The slot may not be found as a result of a known bug in snapshot creation, where
            // the bank at the given slot was not included in the snapshot.
            // Also, it may occur after an old bank has been purged from BankForks and a new
            // BlockCommitmentCache has not yet arrived. To make this case impossible,
            // BlockCommitmentCache should hold an `Arc<Bank>` everywhere it currently holds
            // a slot.
            //
            // For more information, see https://github.com/solana-labs/solana/issues/11078
            warn!(
                "Bank with {:?} not found at slot: {:?}",
                commitment.commitment, slot
            );
            r_bank_forks.root_bank()
        })
    }
