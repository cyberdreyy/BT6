### Title
`bt.Show` discloses bridge `OutgoingToken` secret to any authenticated role (view/run) with no edit/admin gate - ([File: core/web/router.go])

### Summary
The `GET /v2/bridge_types/:BridgeName` route is registered without any role wrapper, while the sibling `PATCH`/`POST`/`DELETE` routes require `auth.RequiresEditRole`. `BridgeTypesController.Show` serializes the bridge via `presenters.NewBridgeResource`, which copies `BridgeType.OutgoingToken` in plaintext into the JSON response, so any authenticated session/API token — including view-only — can read the bridge's outgoing secret token.

### Finding Description
The route table shows the asymmetry directly: [1](#0-0) 

`Show` fetches the bridge and renders it with no role check at all: [2](#0-1) 

`NewBridgeResource` unconditionally copies `OutgoingToken` from the persisted `BridgeType` into the response resource, and this same resource type is used for `Index`, `Update`, and `Destroy` as well: [3](#0-2) 

The underlying `BridgeType` model persists `OutgoingToken` in plaintext (unlike `IncomingTokenHash`, which is a salted hash and therefore never reversible/disclosable via `Show`): [4](#0-3) 

Because `Show` (and `Index`) sit behind only `auth.Authenticate` in `authv2` with no `auth.RequiresEditRole`/`RequiresAdminRole` wrapper, a session or API token with the lowest privilege level (view or run) that can authenticate to the node's `/v2` API can call `GET /v2/bridge_types/:BridgeName` and receive `OutgoingToken` in the JSON:API response body, whereas mutating the same resource requires an edit-role credential. This is an inconsistent authorization model: write access is role-gated but read access to the same secret-bearing resource is not.

Note: `IncomingToken` (the token external adapters must present to call *into* the bridge) is safe from this specific issue because only its hash is stored (`IncomingTokenHash`) and `NewBridgeResource` never populates `IncomingToken` from a `BridgeType`, so it can't leak via `Show`. The confirmed leak is `OutgoingToken`.

### Impact Explanation
`OutgoingToken` is a bridge secret token stored in plaintext and returned by `Show`/`Index`/`Update`/`Destroy` responses regardless of caller role. Any authenticated user (down to view-role, per Chainlink's role model of admin/edit/run/view) or a restricted API token holder can enumerate/read this secret for any configured bridge without needing edit/admin privileges. This matches a credential/secret-disclosure impact class: a low-privileged, authenticated user obtains a node-held bridge secret that a stricter role boundary (mirroring `Update`'s `RequiresEditRole`) was clearly intended to protect from write access, and by extension from casual read access as well, given the sensitivity of bridge auth tokens.

### Likelihood Explanation
Precondition is only a valid view-role (or run-role) session or API token authenticated via `auth.Authenticate` — the lowest privilege tier in the node's role hierarchy. No additional exploitation steps are required: a single `GET /v2/bridge_types/<name>` call returns the token in the response body. This is trivially reproducible and repeatable for every bridge configured on the node.

### Recommendation
Redact `OutgoingToken` (and any other bridge secret) from `presenters.NewBridgeResource` for read paths (`Show`/`Index`), or gate `GET /v2/bridge_types/:BridgeName` and `GET /v2/bridge_types` behind `auth.RequiresEditRole` (or a dedicated role check) consistent with the mutating routes. Prefer omitting the secret entirely from `Show`/`Index` responses (similar to how `IncomingToken` is only ever returned once at creation time) rather than relying on role gating alone.

### Proof of Concept
1. Go handler-level integration test in `core/web/bridge_types_controller_test.go`:
   - Create an application (`cltest.NewApplication`), create a bridge via `app.BridgeORM().CreateBridgeType`.
   - Issue an HTTP client scoped to a view-role (or run-role) session/API token (mirroring how other tests build role-scoped clients, e.g. via `app.NewHTTPClient` with a role parameter).
   - Call `GET /v2/bridge_types/<name>` as that low-privilege client.
   - Assert `resp.StatusCode == http.StatusOK` and parse `presenters.BridgeResource`.
   - Assert `resource.OutgoingToken == bt.OutgoingToken` (proves disclosure) even though this same client would get `http.StatusForbidden` calling `PATCH /v2/bridge_types/<name>`.
   - Compare against an admin-role call to the same endpoint and show the token value is identical/always present — confirming redaction is not role-gated at all (invariant SECRET_CONFINEMENT violated).

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
