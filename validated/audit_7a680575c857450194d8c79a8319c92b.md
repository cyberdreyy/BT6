### Title
Reverting `safeTransfer` to `feeReceiver` inside the `stopEpoch` try block is misclassified as a borrower default, freezing the entire vault — (`contracts/IdleCDOEpochVariant.sol`)

### Summary
`_stopEpoch` wraps not only the borrower pull (`this.getFundsFromBorrower`) but also `collectWithdrawFunds`, both `_transferFeeUnderlyings` pushes, `_updateAccounting`, fee-share minting, and `strategy.deposit` in a single `try/catch`. The `catch` unconditionally calls `_handleBorrowerDefault`. Therefore a *push*-side token transfer failure — e.g. `underlying.safeTransfer(feeReceiver, _fees)` reverting because `feeReceiver` is blacklisted by a token like USDC, or because the token reverts on a zero/dust transfer — causes an honest, fully-paid `stopEpoch` to be recorded as a borrower default. This is the same bug class as the Blueprint report (a push transfer revert blocks a critical settlement flow), but here the consequence is amplified: the revert is escalated into a protocol-wide default flag.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the success path of the `try this.getFundsFromBorrower(...)` call contains `_transferFeeUnderlyings(_pendingWithdrawFees)` and later `_transferFeeUnderlyings(_fees)`, both pushing underlying tokens to `feeReceiver`/`owner` [1](#0-0) [2](#0-1) . Any revert in that whole block lands in `catch { _handleBorrowerDefault(...) }` [3](#0-2) , which sets `defaulted = true`, pauses the contract, stops the epoch, and disables AA/BB withdraw requests [4](#0-3) . There is no `try/catch` or pull-pattern fallback for the fee pushes (contrast `sendFundsToBorrower`, which does have a fallback for the borrower leg [5](#0-4) ). The same misclassification applies to `_skimDonatedAssets` → `_transferUnderlyings(feeReceiver, ...)` reverts in `startEpoch`, `_deposit`, `requestWithdraw`, and `finalizeDefault` [6](#0-5) , though only `stopEpoch` converts the revert into a false default.

Once `defaulted = true`, `restoreOperations` permanently reverts [7](#0-6)  and the only exit is `finalizeDefault`, which applies a recovery haircut to all active LPs — an unwarranted loss since the borrower actually repaid.

### Impact Explanation
Permanent freezing plus unwarranted loss socialization: every active LP position is locked behind `defaulted`, and recovery only proceeds via `finalizeDefault`, which reprices tranches with the recovery multiplier even though the borrower transferred `amountToPullFromBorrower + pendingWithdraws` correctly. Withdraw *receipts* funded before the revert remain claimable, but all active NAV is frozen pending governance action and takes a haircut determined by whatever `_recoveredAmount` is supplied — funds that were in fact received sit idle in the CDO. Loss: effectively 100% of active NAV is frozen and repriced by a governance-chosen recovery number.

### Likelihood Explanation
Low-to-medium. The trigger is not directly attacker-controlled: it requires `feeReceiver` (or `owner` in the minted-fee path is safe since minting can't revert, but `feeReceiver` is a raw token push) to be blacklisted by the underlying token issuer (e.g. USDC), or the underlying to revert on zero/dust transfers, or `collectWithdrawFunds`/`mintStrategyTokens`/`deposit` on the strategy to revert for any reason. `feeReceiver` is honest but honesty does not prevent an external blacklist entry, and the escrow's `feeReceiver` pattern shows the deployment expects arbitrary addresses there. Any single revert in the large success block — not just token pushes — produces a catastrophic false default, making the blast radius disproportionate to the trigger probability.

### Recommendation
Narrow the `try` scope: keep only `this.getFundsFromBorrower(...)` (or additionally `collectWithdrawFunds`, with a revert interpreted as default) inside the `try`, and move all subsequent pushes outside it. Better, adopt the pull pattern for fees as the report suggests: accrue `unclaimedFees` and let `feeReceiver` claim, rather than pushing inside epoch settlement. At minimum, wrap `_transferFeeUnderlyings` calls in their own `try/catch` that leaves the fee accrued in `unclaimedFees` instead of escalating to `_handleBorrowerDefault`.

### Proof of Concept
Reproducible Foundry fork PoC (no code execution available in this mode — outline):

1. Fork mainnet at a block where the vault's `token` is USDC. Deploy/`vm.etch` `IdleCDOEpochVariant` + `IdleCreditVault`, set `feeReceiver` to a fresh address `FR`.
2. Seed AA/BB deposits in the buffer, call `startEpoch()` so the borrower holds funds; warp past `epochEndDate`.
3. On the fork, `vm.prank` USDC's `blacklister` (StorageSlot/`blacklist(address)` via the real USDC contract) to blacklist `FR`. Alternatively use a mock underlying that reverts on `transfer` to `FR`.
4. Borrower approves and repays; call `stopEpoch(newApr, 0)`.
5. Observe: `getFundsFromBorrower` succeeds (USDC balance of CDO increases), then `safeTransfer(FR, _fees)` reverts → `catch` runs → `defaulted == true`, `paused() == true`, `allowAAWithdrawRequest == false`.
6. Assert `restoreOperations()` reverts with `NotAllowed`, and tranche holders cannot exit except through `finalizeDefault` with a haircut — demonstrating freezing plus forced loss despite full borrower repayment.

```text
  function _handleBorrowerDefault(uint256 funds) internal {
    defaulted = true;
    // Do not reopen instant claims here. They remain disabled when funding is pending;
    // successful full funding is the only path that enables them before finalization.

    if (isProgrammableBorrower) {
      IProgrammableBorrower(_borrower()).onDefault();
    }

    // deposits should be already prevented
    if (!paused()) {
      _pause();
    }

    // stop the current epoch
    isEpochRunning = false;

    // prevent withdrawals requests
    allowAAWithdrawRequest = false;
    allowBBWithdrawRequest = false;

    emit BorrowerDefault(funds);
  }
```
