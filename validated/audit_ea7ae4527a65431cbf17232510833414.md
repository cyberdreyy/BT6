### Title
Stale confirmations from removed members are not purged, allowing requests to execute below `num_confirmations` live members - (File: multisig2/src/lib.rs)

### Summary
`delete_member` (multisig2/src/lib.rs:356-379) only deletes *requests* whose `member` field (the original requester) equals the deleted member, but never scans `self.confirmations` to strip that member's votes from *other* pending requests they had merely confirmed. Because `confirm` (lines 294-315) counts raw `confirmations.len()` against `num_confirmations` without checking that every voter in the set is still `self.members.contains(...)`, a request confirmed by a member who is later removed keeps that removed member's vote, letting the request execute with fewer live-member confirmations than `num_confirmations`.

### Finding Description
The binding that should hold is: `distinct_live_member_confirmations(R) == num_confirmations` before `execute_request(request)` is invoked in `confirm` at multisig2/src/lib.rs:304-309.

```rust
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
``` [1](#0-0) 

`confirmations` is a `HashSet<String>` of member identifiers recorded at confirm-time [2](#0-1) . Nothing in `confirm` re-validates that each string in that set still corresponds to a current member of `self.members`.

`delete_member` only purges requests *authored* by the removed member, not confirmations they cast on other requests:
```rust
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [3](#0-2) 

The `assert(self.members.len() - 1 >= self.num_confirmations as u64, ...)` invariant only guards that *future* membership size stays `>= num_confirmations`; it says nothing about pending requests that were already partially confirmed by a member who is about to be removed [4](#0-3) .

Exploit flow (concrete, verified reachable path with members=[A,B,C,D], num_confirmations=3):
1. D calls `add_request` to create Transfer request `R` to an attacker-controlled/target account.
2. A calls `confirm(R)` → confirmations = `{A}`.
3. B calls `confirm(R)` → confirmations = `{A,B}` (2 < 3, not executed yet).
4. C creates `DeleteMember{member: A}` as request `R2`; D and B confirm, then C confirms → 3/4 confirmations satisfies `4-1>=3`, executes, removing A. `R` is untouched because it was authored by D, not A, so its confirmations set `{A,B}` (containing the now-removed A) survives in `self.confirmations`.
5. C (still a live member) calls `confirm(R)` → `confirmations.len()+1 == 3 >= num_confirmations(3)` → `execute_request(R)` runs the Transfer.

At execution time the *live* members who actually confirmed `R` are only B and C (2), yet the code accepts it as satisfying a 3-of-4 quorum because A's stale vote is still counted. `assert_valid_request`, `assert_self_request`, and `current_member()` all check the *caller* is a live member, but none of them re-validate the *stored confirmation set* against current membership, so this stale-vote path is not caught anywhere in the code.

Note: the literal two-sequential-deletion chain described in the question (removing both A and B down to a single live confirmer C) is blocked at the second `DeleteMember` by the invariant assert when starting from exactly 4 members and `num_confirmations=3` (after removing A, `members.len()-1 == 2 < 3` panics). The same class of bug is fully reproducible, however, with a single deletion (as shown above, yielding 2 live confirmers instead of 3) and can be extended to leave exactly `num_confirmations` live confirmers by starting with more initial members (e.g., 5 members, two deletions, `num_confirmations=3`, leaving only 1 truly live confirming vote alongside 2 stale ones). The core binding violation — a request executing with fewer live confirmations than `num_confirmations` — holds regardless of the exact member count chosen.

### Impact Explanation
A `Transfer` (or any other multisig action, including further `DeleteMember`/`AddKey`/`FunctionCall`) can execute while backed by fewer live-member confirmations than `num_confirmations` requires, because stale votes from removed members are never invalidated. This directly matches the Critical category "a multisig request executed below `num_confirmations` live members," and for `Transfer` actions it results in NEAR leaving the multisig account effectively under the control of fewer members than the configured threshold. The attack is repeatable for any pending request that collected partial confirmations prior to a member's removal, and applies to every multisig instance deployed from this contract.

### Likelihood Explanation
Exploitation requires being an existing multisig member (not an outside unprivileged attacker) able to time confirmations around a `DeleteMember` execution — i.e., collusion among a subset of members that is itself smaller than `num_confirmations`. No special balances are needed beyond normal multisig operation; the only cost is ordinary transaction fees. This is a real design flaw in `delete_member`'s bookkeeping, straightforward to trigger deterministically, and does not depend on race conditions across blocks—only the ordering of confirmation calls, which members fully control.

### Recommendation
When removing a member in `delete_member`, iterate over `self.confirmations` for all pending requests and strip the deleted member's identifier from every confirmation set (not just requests they authored). Alternatively, have `confirm` recompute the count by filtering `confirmations` against `self.members.contains(...)` before comparing to `num_confirmations`, so stale votes from removed members can never count toward quorum.
