## Finding: Stale confirmations from removed multisig members still count toward the execution threshold

### Title
Removed multisig member's prior confirmation is never purged, letting a request execute with fewer than `num_confirmations` *live* approvals - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only deletes requests that the removed member *originated*, but never scrubs that member's *confirmations* on requests originated by other members. Because `confirm()` only checks the size of the stored confirmation `HashSet<String>` against `num_confirmations`, a confirmation cast by a member before removal keeps counting toward the threshold after that member is no longer part of the multisig — the exact same class of bug as the external report, where a message validated against a stale/rotated signer set is still accepted after the signer set changes.

### Finding Description
`confirm()` enforces the K-of-N threshold purely by comparing the *count* of entries already in `self.confirmations` against `self.num_confirmations`, with no re-validation that every entry in that set still corresponds to a `MultisigMember` currently in `self.members`: [1](#0-0) 

`delete_member` removes the departing member from `self.members` and deletes access keys/requests *they created*, but it filters only on `r.member == member` (the requester field of `MultiSigRequestWithSigner`) — it never walks `self.confirmations` to strip that member's vote from requests created by *other* members: [2](#0-1) 

So the equality that should hold is:
```
confirmations_counted(request) == confirmations_by_current_live_members(request)
```
After a `DeleteMember` executes, this breaks: `confirmations_counted(request)` can include one or more accounts/keys that are no longer in `self.members`, while `confirmations_by_current_live_members(request)` is strictly smaller. `confirm()` only checks the former, so a request can be pushed over the `num_confirmations` bar by live members even though fewer than `num_confirmations` *currently authorized* members ever approved it.

`current_member()` correctly blocks a removed member from *adding a new* confirmation (`self.members.contains(&member)` gate), but it does nothing to invalidate confirmations that member already cast before removal: [3](#0-2) 

The legacy `multisig/src/lib.rs` has the same structural gap: `DeleteKey` only purges requests where `r.signer_pk == pk`, never confirmations by that key on requests created by others. [4](#0-3) [5](#0-4) 

### Impact Explanation
This is a multisig request executed below the intended threshold of currently authorized members — an explicitly listed Critical impact. A `Transfer`, `AddKey`, `DeployContract`, or arbitrary `FunctionCall` action can be executed on the multisig account after only `num_confirmations - 1` (or fewer, if multiple members are removed after confirming) *live* members approved, because a removed member's leftover confirmation silently fills the remaining slot. This directly undermines the custody guarantee the K-of-N scheme is meant to provide: NEAR (or access) can be moved by a set of parties smaller than the configured threshold.

### Likelihood Explanation
No privileged action beyond normal multisig operation is required beyond what the contract already allows: any member can `add_request`/`confirm` in the ordinary course of business, and `DeleteMember` is a normal governance action (e.g., rotating out a departing team member or a member whose key is suspected compromised — the same benign trigger as a Wormhole guardian-set rotation). The bug is triggered purely by the *ordering* of routine operations (confirm-then-remove-member-then-confirm), not by any attacker needing special access, and the flaw is deterministic — it reproduces on every occurrence of that ordering.

### Recommendation
When a member is deleted, iterate `self.confirmations` (not just `self.requests`) and remove the departing member's `to_string()` entry from every pending request's confirmation set, or alternatively re-validate at `confirm()` time that every entry in the confirmation set still corresponds to a member present in `self.members` before comparing the count to `num_confirmations`. The same fix should be applied to `multisig/src/lib.rs`'s `DeleteKey` handling.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. Member `A` calls `add_request_and_confirm(R)` for a sensitive `MultiSigRequestAction::Transfer` — confirmations = `{A}`.
3. Member `B` calls `confirm(R)` — confirmations = `{A, B}` (2/3).
4. Separately, members execute a `DeleteMember { member: B }` request (a normal, routine rotation) — `self.members` becomes `{A, C, D}`; `delete_member` only scans/deletes requests where `r.member == B`, so `R` (created by `A`) and its confirmation set `{A, B}` are untouched.
5. Member `C` calls `confirm(R)` — confirmations = `{A, B, C}`, size `3 >= num_confirmations`, so `execute_request(R)` runs the `Transfer`, even though only `A` and `C` — 2 of the 3 currently live members — ever actually approved it. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
