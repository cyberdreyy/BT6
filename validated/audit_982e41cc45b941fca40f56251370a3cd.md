### Title
Post-default withdraw requests drain `defaultRecoveryReserve` at par, starving defaulted-epoch claimants - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug (CVE-2021-32028) lets an authenticated user read bytes belonging to other contexts via a crafted command on a shared table. The credit-vault analog is a crafted claim against a shared accounting bucket: after `finalizeDefaultRecovery`, `requestWithdraw` creates "post-default" receipts and `_claimPostDefaultWithdrawRequest` pays them 1:1 out of `defaultRecoveryReserve` — a reserve sized only to cover defaulted-epoch claimants at `defaultRecoveryPrice`. Any user can deposit, request, and claim in the same transaction and consume the isolated reserve at par, permanently freezing other users' unclaimed recovery.

### Finding Description
`finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` and stores it as `defaultRecoveryReserve` (`IdleCreditVault.sol:686-692`). That reserve is sized exactly to satisfy defaulted claims at the recovery ratio.

After finalization, `requestWithdraw` takes an early return path (`IdleCreditVault.sol:247-257`): it burns the CDO's strategy tokens and mints the user a receipt recorded in `postDefaultRequests[_user]`, justified by "the CDO passes an already-haircut amount because finalization lowered virtualPrice first." Then `claimWithdrawRequest` routes to `_claimPostDefaultWithdrawRequest` (`IdleCreditVault.sol:760-767`), which pays `postDefaultRequests[_user]` at par via `_transferDefaultRecovery`, which decrements the shared `defaultRecoveryReserve` (`IdleCreditVault.sol:912-916`).

Two broken invariants:

1. **No epoch gating.** Unlike the normal path (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest`, line 326), post-default receipts are claimable in the same transaction they were requested. Deposit → requestWithdraw → claimWithdrawRequest is atomic.
2. **Unbounded par draw on a haircut-priced reserve.** The reserve contains `recoveryPrice * totalBasis`. Paying post-default claims 1:1 consumes reserve at a ratio *above* `defaultRecoveryPrice` relative to what that capital's claimants contributed (their basis entered at post-haircut virtualPrice). Every post-default claim dilutes the pro-rata pool owed to users whose receipts defaulted in `defaultRecoveryEpoch`. Once the reserve is exhausted, `_transferDefaultRecovery` underflows/reverts for remaining defaulted claimants — permanent freezing of unclaimed yield.

The attacker only needs to be a KYC-passing lender (`isWalletAllowed`); no privileged role is required. The guards at lines 899-905 protect the reserve from *funded* claims but deliberately allow post-default claims to spend it without limit or cap (`postDefaultRequests` is never bounded against the reserve share attributable to post-default deposits).

### Impact Explanation
Direct theft / permanent freezing of unclaimed recovery. A lender who waited and holds a defaulted-epoch receipt expects `claimBasis * defaultRecoveryPrice / 1e18`. An attacker cycling deposit→request→claim after finalization converts post-haircut capital into par payouts from the same reserve, exhausting it; honest defaulted claimants' `_transferDefaultRecovery` then reverts (subtraction underflow / insufficient balance), permanently freezing their recovery. Quantified loss: up to `defaultRecoveryReserve - Σ(post-default claims)` drained ahead of rightful claimants — i.e., up to the whole reserve is first-come-first-served instead of pro-rata.

### Likelihood Explanation
Requires a borrower default followed by `finalizeDefaultRecovery` — a real but infrequent state. Once in that state, any whitelisted lender (or vault user routed through the CDO) can execute the cycle atomically with no lock-up, so whoever acts first after finalization wins the race. No privileged role, oracle, or timing manipulation is needed.

### Recommendation
Either (a) fund post-default claims from a separate accounting path — pay them from strategy liquidity/`pendingWithdraws`-style funding rather than `defaultRecoveryReserve`, or (b) apply `defaultRecoveryPrice` to post-default payouts as well and/or track a dedicated post-default reserve segment so they cannot consume the defaulted claimants' pro-rata share. At minimum, post-default claims should be capped so `Σ defaulted claims × defaultRecoveryPrice` remains reserved.

### Proof of Concept
Foundry fork PoC sketch (on a mainnet fork with a live `IdleCreditVault`/CDO pair, mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testPostDefaultReserveDrain() public {
    // 1. Setup: victim deposits into AA tranche pre-default.
    _depositWithUser(victim, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // 2. Victim requests withdraw during the epoch.
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 3. Epoch ends with borrower default; owner/manager finalize recovery
    //    with partial recoveredAmount so defaultRecoveryPrice < 1e18.
    _stopEpochDefaulted();
    vm.prank(manager);
    creditVault.finalizeDefaultRecovery(recoveredAmount, recoverySource);

    uint256 reserveBefore = creditVault.defaultRecoveryReserve();

    // 4. Attacker (whitelisted lender) atomically deposits dust,
    //    requests withdraw, and claims at par in the same tx.
    vm.startPrank(attacker);
    idleCDO.depositAA(attackAmount);          // post-haircut virtualPrice
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    cdoEpoch.claimWithdrawRequest();          // _claimPostDefaultWithdrawRequest pays 1:1
    vm.stopPrank();

    // 5. Reserve shrunk by the attacker's par payout.
    uint256 reserveAfter = creditVault.defaultRecoveryReserve();
    assertLt(reserveAfter, reserveBefore);

    // 6. Repeat until reserve exhausted; victim's defaulted claim now reverts
    //    in _transferDefaultRecovery (underflow) — permanent freeze.
    vm.prank(victim);
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
}
```

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }

    if (_amount == 0) return;
