### Title
Deleting a multisig key does not purge its stale confirmations from other pending requests, allowing a request to execute below the intended `num_confirmations` threshold - (`multisig/src/lib.rs`)

### Summary
`MultiSigRequestAction::DeleteKey` only removes requests that were *authored* by the deleted key and clears that key's `num_requests_pk` counter, but it never scrubs the deleted key's public key out of the `confirmations` sets of *other* pending requests that it had merely confirmed. `confirm()` counts confirmations purely by set size (`confirmations.len() + 1 >= self.num_confirmations`) without verifying that each entry in the confirmation set still corresponds to a currently valid access key on the account. This lets a request execute after being "confirmed" by fewer live keys than `num_confirmations` actually requires, because a stale confirmation from an already-revoked key still counts toward the threshold.

### Finding Description
In `multisig/src/lib.rs`, `execute_request`'s `DeleteKey` branch only cleans up requests where the deleted key was the *submitter*: [1](#0-0) 

It does not iterate over `self.confirmations` to strip the deleted key from confirmation sets of requests submitted by other keys. Meanwhile, `confirm()` treats the size of the stored confirmation set as ground truth for the live authorization threshold: [2](#0-1) 

Because NEAR access-key deletion is asynchronous relative to the multisig contract's own state (the contract only updates its bookkeeping in the `DeleteKey` branch shown above, and only for requests it authored), a key that confirmed some other request `R` and is later deleted still has its public key recorded in `R`'s confirmation `HashSet`. When a *different*, still-valid key later calls `confirm(R)`, the count includes the dead key's stale entry, so `confirmations.len() + 1 >= num_confirmations` can become true with fewer *currently valid* signers than `num_confirmations` actually requires.

The binding that should hold is:
```
confirmations_counted_toward_threshold(request) == live_members_who_confirmed(request)
```
This binding is broken: `confirmations_counted_toward_threshold(request)` can include keys that are no longer members, so `confirmations_counted_toward_threshold(request) > live_members_who_confirmed(request)` after any `DeleteKey` execution against a key that had previously confirmed (but not authored) other pending requests.

The same pattern exists in `multisig2/src/lib.rs`'s `delete_member`, which likewise only purges requests where `r.member == member` (the deleted member's own authored requests), leaving that member's confirmations on other pending requests intact: [3](#0-2) 

### Impact Explanation
This crosses an authorization-threshold boundary: a multisig request (e.g., a `Transfer` of NEAR, an `AddKey`/`AddMember` granting new access, or a `FunctionCall`) can be executed with fewer live, currently-authorized confirmers than `num_confirmations` mandates. This maps directly to the Critical impact category "a multisig request executed below threshold," since NEAR (or authority over the account) can move/be granted to a party not entitled to it under the account's own K-of-N policy.

### Likelihood Explanation
Exploitation requires only ordinary, unprivileged use of the multisig's own documented flow — no owner/foundation/redeploy is needed beyond what any member is already authorized to do:
1. Any member can submit and get a first confirmation on a request.
2. Separately, the members can (as part of normal key rotation) execute a `DeleteKey` request removing the confirming key for an unrelated reason.
3. Any remaining member can then call `confirm` on the original pending request; the stale confirmation is silently counted, allowing execution with one fewer live confirmer than intended.

Key rotation/removal is an expected, routine operation for this contract (it's the whole point of `DeleteKey`), so the precondition is easily reached in practice, not a contrived edge case.

### Recommendation
When executing `DeleteKey` (or `DeleteMember` in `multisig2`), iterate over `self.confirmations` for *all* pending requests (not just ones authored by the deleted key/member) and remove the deleted key/member's entry from each confirmation set. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set to public keys/members that are still valid members of the multisig before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 2` and access keys `A`, `B`, `C`.
2. Key `B` calls `add_request` with a `Transfer` request `R` (receiver = attacker-controlled or malicious payload). `confirmations[R] = {}`.
3. Key `A` calls `confirm(R)`. Now `confirmations[R] = {A}` (1 < 2, not yet executed).
4. Independently, keys `B` and `C` submit and confirm a `DeleteKey{public_key: A}` request (2-of-3, legitimate rotation of `A` out of the multisig). This executes `execute_request`'s `DeleteKey` branch: it removes any requests *authored* by `A` (none, since `A` didn't author `R`) and calls `promise.delete_key(A)`. `confirmations[R]` is untouched and still equals `{A}`.
5. Key `C` calls `confirm(R)`. `confirmations[R].len() + 1 == 2 >= num_confirmations (2)`, so `R` executes — despite `A`'s key having been deleted and only `C` being a currently live confirmer besides the original stale entry from `A`. The `Transfer` (or other action) in `R` is executed with effectively 1 live confirmation instead of the required 2.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
