### Title
Stale confirmations from a deleted multisig member/key are not purged from other pending requests, allowing execution below the effective live-member threshold - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
When a multisig key (v1 `multisig`) or member (v2 `multisig2`) is removed via a `DeleteKey`/`DeleteMember` governance action, the contract only deletes the *requests that the removed signer originally created* — it never scans and strips that signer's confirmation entry from the `confirmations` map of *other, still-pending* requests they had confirmed. The count used by `confirm()` to decide whether a request has reached `num_confirmations` therefore includes confirmations cast by keys/members that are no longer part of the multisig, letting a request execute with fewer genuinely live approvals than the configured threshold.

### Finding Description
In `multisig/src/lib.rs`, `execute_request()`'s `DeleteKey` handler only removes requests where the removed key was the *creator* (`r.signer_pk == pk`); confirmations that key cast on requests created by *other* signers are left untouched in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map: [1](#0-0) 

`confirm()` simply counts entries in that `HashSet` without validating that each entry still corresponds to a key currently permitted on the account: [2](#0-1) 

`assert_valid_request()` only checks predecessor==current account and that the request/confirmation records exist — it performs no per-key membership re-validation: [3](#0-2) 

The same pattern exists in `multisig2/src/lib.rs`. `delete_member()` filters outstanding requests by `r.member == member` (i.e. requests *created* by the removed member) and removes that member from `num_requests_pk`, but never walks other requests' `confirmations` sets to drop the removed member's entry: [4](#0-3) 

`confirm()` in v2 has the identical threshold-counting logic, counting any string key present in the `HashSet<String>` regardless of current membership: [5](#0-4) 

Binding broken: `confirmations counted for request R == live members who confirmed R`. After a member is removed, this equality no longer holds for any request R that member had confirmed before removal but which had not yet reached quorum — the left side stays the same while the true count of currently-authorized approvers on the right side drops by one, without the request being invalidated.

### Impact Explanation
This lets a `MultiSigRequest` (e.g. a `Transfer` draining the multisig account, an `AddKey`/`AddMember` granting unauthorized control, or a `FunctionCall`) execute with fewer live, currently-authorized confirmations than `num_confirmations` requires. Concretely: with `num_confirmations = 2` and members A, B, C — B confirms a request R created by A (1/2 confirmations, pending). B is later removed (routine rotation, suspected compromise, or a deliberately malicious member who confirms damaging requests before being removed). R is untouched by the removal. C later confirms R, reaching `2 >= num_confirmations`, and R executes — even though at execution time only A and C are valid members and B's stale approval was counted as if still legitimate. This is a "multisig request executed below threshold" outcome (funds moved/keys added with effectively 1 live approval where 2 were configured as required).

### Likelihood Explanation
Requires no attacker privilege beyond normal multisig operation: any member confirming a request that does not immediately reach quorum, followed by a routine or malicious key/member removal before quorum is met, triggers the stale state. Key rotations and member removals are a documented, expected multisig operation (the `DeleteKey`/`DeleteMember` action exists specifically for this), so the precondition is easily reached in normal contract lifecycle, not a contrived edge case.

### Recommendation
When executing `DeleteKey` (v1) / `DeleteMember` (v2), iterate over *all* pending requests' `confirmations` entries (not just requests created by the removed signer) and remove the deleted key's/member's entry from each. Alternatively, revalidate every confirmation against current membership inside `confirm()` before counting it toward `num_confirmations` (e.g., filter the `HashSet` against `self.members`/live access keys at execution time rather than trusting the persisted set).

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. A calls `add_request_and_confirm` with a `Transfer` request to an attacker-controlled account → request `R` has 1 confirmation (A).
3. B calls `confirm(R)` is *not* called yet (kept pending, e.g. B is compromised or colluding but waits).
4. The remaining members execute a `DeleteMember { member: B }` request through normal governance (e.g. A+C confirm it) — this only removes requests *created* by B, leaving B's future potential confirmation slot in `confirmations` for R untouched (in this scenario B hasn't confirmed R yet, so illustrate the inverse ordering below for the actual exploit):
   - Reorder: B confirms `R` first (2nd confirmation not yet reached, e.g. `num_confirmations=3`, members A,B,C,D). Confirmations on R = {A, B}.
   - B is removed via `DeleteMember` — `delete_member` deletes requests where `r.member == B` (B created none of relevance) and removes B from `num_requests_pk`/`members`, but does not touch `confirmations[R]`.
   - Now only A, C, D are valid members (3 required), but `confirmations[R]` still contains `{A, B}`.
   - C calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations(3)` → `execute_request(R)` runs the `Transfer`, even though only A and C (2 live members) actually approved it — B's stale confirmation was counted as the third. [6](#0-5)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
