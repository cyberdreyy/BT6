### Title
Stale per-epoch instant-withdraw ledgers are never cleared on funded claims, inflating default recovery basis and permanently stranding recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` releases the user's aggregate receipt (`instantWithdrawsRequests[_user]`) but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. If the borrower later defaults in that same epoch, `defaultPendingClaimBasis()` still counts those already-claimed-and-paid receipts as defaulted claim basis. The recovery price computed in `finalizeDefaultRecovery` is therefore diluted across "phantom" claims, and the reserve share attributable to them can never be paid out, permanently freezing part of the recovery.

### Finding Description
The instant-withdraw lifecycle writes three ledgers at request time (`contracts/strategies/idle/IdleCreditVault.sol:366-374`):

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

On a funded claim (`contracts/strategies/idle/IdleCreditVault.sol:380-393`), only the aggregate is released:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` leak — the exact analog of the CVE-2021-47193 pattern (allocated bookkeeping never freed on teardown of the request).

These stale entries become live debt at default. `defaultPendingClaimBasis()` (`:644-649`) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`. On borrower default `epochNumber` is not bumped (see `_prefundedEpochToProcess` in `contracts/IdleCDOEpochQueue.sol:290`), so an instant request made, funded via `collectInstantWithdrawFunds` (`:398-403`, which only decreases `pendingInstantWithdraws`), and fully claimed still contributes its full amount to the defaulted basis. `finalizeDefaultRecovery` (`:661-710`) then computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over this inflated `totalBasis`, diluting every legitimate claimant, and stores `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (`:696`).

The stale per-user entry also bricks the user's later claims: `_claimDefaultedInstantWithdrawRequest` (`:842-856`) reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, computes `instantWithdrawsRequests[_user] -= claimBasis` (underflow revert since the aggregate is already 0) and `_burn(_user, claimBasis)` (revert, receipt already burned).

### Impact Explanation
Two quantified harms, both triggered by an unprivileged tranche-token holder making and claiming an instant withdrawal before a default:

1. **Recovery dilution (theft-by-dilution).** If the attacker claimed X instant withdrawals in the defaulted epoch, `totalBasis` is inflated by X. Every genuine defaulted claimant (normal withdrawers, unfunded instant requesters, active AA/BB holders via `activeFinalNAV`) recovers `reserveAmount / (realBasis + X)` instead of `reserveAmount / realBasis`. With X equal to the real pending basis, all claimants lose ~50% of their recovery.
2. **Permanent freezing of reserve.** The phantom basis is never claimed (attempting it reverts), so `defaultRecoveryReserve` retains the phantom share forever; `_transferDefaultRecovery` (`:912-917`) only decrements on real claims and there is no sweep of the stranded portion to legitimate claimants.

### Likelihood Explanation
Requires: an epoch with instant withdrawals enabled, at least one instant request that is funded and claimed, at least one still-unfunded instant request (`pendingInstantWithdraws != 0`, needed for the basis inclusion and `defaultInstantWithdrawsFinalized`), and a borrower default in the same epoch. Defaults are an in-scope, designed-for scenario (`_handleBorrowerDefault`, `finalizeDefaultRecovery`, `DefaultDistributor`), and instant requests are a normal user flow reachable by any KYC'd tranche holder, so no privileged misbehavior is needed. No existing guard stops it: `_ensureDefaultRecoveryInitialized` only normalizes normal/APR0 counters and explicitly never touches instant ledgers (`:923` comment: "Pending instant withdrawals are never cleared automatically"), and `_transferFundedClaim`'s reserve guard (`:900-905`) does not prevent the basis inflation.

### Recommendation
In `claimInstantWithdrawRequest`, after determining the claimed `amount`, clear the per-epoch ledgers for the funded receipt: locate the request's epoch entry (`instantWithdrawsRequestsByEpoch[_user][epoch]`), zero it, and subtract the claimed amount from `instantWithdrawClaimsByEpoch[epoch]`. This mirrors how `_claimDefaultedInstantWithdrawRequest` already cleans up (`:847-853`) and how `_clearWithdrawClaimForEpoch` clears normal per-epoch receipts (`:811-837`). Alternatively, decrement `instantWithdrawClaimsByEpoch` inside `collectInstantWithdrawFunds` so the epoch claim ledger only ever represents unfunded basis.

### Proof of Concept
Foundry fork sketch against `test/foundry` fixtures (e.g., `IdleCreditVault.t.sol` setup with `cdoEpoch`, `strategy`, `tranche`, `underlying`, manager, borrower):

```solidity
// Epoch N running, instant withdrawals enabled
vm.prank(attacker); // KYC'd tranche holder
cdoEpoch.requestInstantWithdraw(X, address(AATranche)); // -> strategy.requestInstantWithdraw
vm.prank(otherUser);
cdoEpoch.requestInstantWithdraw(Y, address(AATranche));

// Manager collects funds for attacker's request only
vm.prank(manager);
cdoEpoch.collectInstantWithdrawFunds(X); // pendingInstantWithdraws = Y

// Attacker claims at par; per-epoch ledgers stay stale
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // pays X, leaves instantWithdrawClaimsByEpoch[N] = X+Y

// Warp to epoch end; borrower defaults instead of repaying
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(0, 1, duration, 0); // borrower sends nothing -> default path
// ... _handleBorrowerDefault ...

// Finalize with recovered amount R sized to real basis (active + Y + pending normal)
vm.prank(manager);
cdoEpoch.finalizeDefaultRecovery(R, recoverySource);

// Assert: defaultRecoveryPrice < R * RECOVERY_FULL / realBasis
// because totalBasis included the phantom X
assertLt(strategy.defaultRecoveryPrice(), R * RECOVERY_FULL / realBasis);

// Attacker cannot even re-claim: stale entry makes the call revert,
// and the phantom share of defaultRecoveryReserve is stranded forever
vm.prank(attacker);
vm.expectRevert();
cdoEpoch.claimInstantWithdrawRequest();
```

Expected assertion: `strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber())` still equals `X + Y` after the attacker's funded claim, and `defaultRecoveryReserve` retains ≈ `R * X / (realBasis + X)` unreachable by any claimant.

Caveat: I traced the CDO-side default flow only through the queue comment confirming `epochNumber` is not bumped on default; the exact `stopEpoch`/default entry point names in `IdleCDOEpochVariant` should be confirmed when writing the PoC, but the stale-ledger invariant in `IdleCreditVault` is directly verifiable from the cited lines.
