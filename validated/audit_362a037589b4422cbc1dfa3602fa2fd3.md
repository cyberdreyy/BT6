### Title
Unverified token receipt in `LendingAccountDeposit`/`LendingAccountWithdraw` allows share/liability mis-accounting for Token-2022 mints with balance-reducing transfer hooks (burn-on-transfer analog) - (File: programs/marginfi/src/instructions/marginfi_account/deposit.rs, programs/marginfi/src/instructions/marginfi_account/withdraw.rs)

### Summary
Marginfi's core deposit and withdraw instructions credit/debit share amounts based on the *nominal* instruction `amount`, adjusted only for the known, quantifiable Token-2022 `TransferFeeConfig` extension via `calculate_pre_fee_spl_deposit_amount`. They never compare the vault's token balance before and after the CPI transfer to confirm the actual amount received/sent, unlike the Drift and JupLend integration paths in this same codebase, which explicitly do pre/post balance diffs (`pre_transfer_vault_balance`/`post_transfer_vault_balance`, `pre_withdraw_intermediary_ata_balance`/`post_withdraw_intermediary_ata_balance`). This is exactly the bug class in the report: a token whose effective transferred amount can be reduced by mechanisms other than the accounted-for fee (e.g. a Token-2022 transfer hook that burns or redirects part of the transfer) will cause the bank's recorded shares/liquidity to diverge from the token balance actually held in the vault.

### Finding Description
In `lending_account_deposit` [1](#0-0) , shares are minted for `deposit_amount` (the user-requested amount, only adjusted for `TransferFeeConfig` via `calculate_pre_fee_spl_deposit_amount`), and then `amount_pre_fee` tokens are transferred via `bank.deposit_spl_transfer`. There is no check afterward that the liquidity vault's balance actually increased by `deposit_amount`.

Symmetrically, in `lending_account_withdraw` [2](#0-1) , the withdrawn share amount is computed from `amount_pre_fee` (again only adjusted for `TransferFeeConfig`), and `bank.withdraw_spl_transfer` is invoked without verifying how many tokens the destination account actually received.

The fee-adjustment helper only accounts for the `TransferFeeConfig` extension: [3](#0-2) . It does not account for arbitrary balance-reducing behavior introduced by a `TransferHook` extension (which can execute arbitrary CPI logic during transfer, including burning tokens — the on-chain analog of "burn-on-transfer" / deflationary ERC-20 tokens described in the report).

Critically, marginfi's own test suite demonstrates that Token-2022 mints with an *active* `TransferHook` extension are a supported/tested configuration for the core deposit/withdraw/liquidation paths (not just an inert extension) — see `marginfi_account_liquidation_success_with_extension` exercising `SupportedExtension::TransferHook` [4](#0-3)  and the deposit helper that wires up `add_extra_account_metas_for_execute` for T22 transfer-hook mints [5](#0-4) . By contrast, the *emissions deposit* instruction explicitly rejects any mint with a non-zero fee or an active transfer hook before crediting share value, precisely to avoid this class of bug: [6](#0-5) . The main user-facing deposit/withdraw paths have no equivalent guard, and no post-transfer balance reconciliation either (which would be the alternative mitigation, and is exactly what the Drift/JupLend integration withdraw code already implements: [7](#0-6)  and [8](#0-7) ).

The protocol's own fuzz-test invariants acknowledge that transfer-fee (and by extension, hook-driven) token flows are "non-conserving" and explicitly relax strict conservation checks for such banks rather than reject them: [9](#0-8) .

### Impact Explanation
If a bank is backed by a Token-2022 mint with an active transfer hook that burns or diverts a portion of the transferred amount (a deflationary/burn-on-transfer token), depositors are credited `assetShares` corresponding to the full nominal `amount`, while the liquidity vault only receives the reduced amount. This inflates `total_asset_shares`/`asset_share_value` relative to real backing liquidity, allowing the depositor (and by extension any other holder of shares in that bank) to withdraw more real value than was ever deposited — a durable insolvency/misvaluation of the bank that can be drained via subsequent withdrawals, echoing the report's warning that `emergencyWithdraw`-style operations fail or eat into other depositors' funds once the shortfall is discovered. On the withdraw side, a symmetric hook could cause a user to receive less than debited, but the more severe (financially exploitable) direction is the deposit-side over-crediting.

### Likelihood Explanation
This requires a bank to be created (admin action) for a Token-2022 mint that carries a `TransferHook` extension. This is a supported configuration explicitly tested by the codebase for the standard deposit/withdraw/liquidation instructions (as opposed to being blocked, the way `TransferFee`-driven emissions deposits are blocked), so it is a state the protocol accepts, not a purely theoretical/mocked-only scenario. Any transfer hook whose logic burns or redirects value (which the SPL Token-2022 hook interface fully permits) reaches this gap purely through a normal, unprivileged `lending_account_deposit`/`lending_account_withdraw` call — no special authority is required by the depositor.

### Recommendation
Either (a) reject banks/mints whose Token-2022 extensions include an active `TransferHook` for the standard deposit/withdraw instructions, mirroring the `has_transfer_hook` check already used in `lending_pool_emissions_deposit` [6](#0-5) , or (b) compute the actual amount received/sent by diffing the liquidity vault's (or destination's) token balance before and after the CPI transfer — the same pattern already implemented for the Drift and JupLend integration withdraw paths [10](#0-9)  — and use that verified amount (not the caller-supplied nominal amount) to compute `share_amount` in `lending_account_deposit`/`lending_account_withdraw`.

### Proof of Concept
1. Group admin creates a bank (`lending_pool_add_bank`) backed by a Token-2022 mint that has an active `TransferHook` extension pointing to a hook program that burns X% of every transferred amount (test infrastructure already provides `SupportedExtension::TransferHook` and a `test_transfer_hook` program to model this: [11](#0-10) , [12](#0-11) ).
2. An unprivileged user calls `lending_account_deposit` with `amount = 1000`. `calculate_pre_fee_spl_deposit_amount` returns `1000` unchanged (no `TransferFeeConfig`), so `bank_account.deposit(1000)` mints shares for the full 1000, then `deposit_spl_transfer` moves 1000 tokens through the hook, which burns e.g. 5% — the liquidity vault only receives 950 [1](#0-0) .
3. No post-transfer balance check exists to detect or correct this discrepancy, so the bank's `asset_share_value` is now backed by less liquidity than its shares represent.
4. Any depositor can subsequently withdraw against the inflated share value, extracting more real tokens than were ever actually deposited, at the expense of other depositors in the same bank.

pub fn calculate_pre_fee_spl_deposit_amount(
    mint_ai: AccountInfo,
    post_fee_amount: u64,
    epoch: u64,
) -> MarginfiResult<u64> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(post_fee_amount);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    match mint.get_extension::<TransferFeeConfig>() {
        Ok(transfer_fee_config) => {
            let epoch_fee = transfer_fee_config.get_epoch_fee(epoch);
            let pre_fee_amount = calculate_pre_fee_amount(epoch_fee, post_fee_amount).unwrap();
            Ok(pre_fee_amount)
        }
        Err(_) => Ok(post_fee_amount),
    }
}

pub fn calculate_post_fee_spl_deposit_amount(
    mint_ai: AccountInfo,
    input_amount: u64,
    epoch: u64,
) -> MarginfiResult<u64> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(input_amount);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    let fee = if let Ok(transfer_fee_config) = mint.get_extension::<TransferFeeConfig>() {
        transfer_fee_config
            .calculate_epoch_fee(epoch, input_amount)
            .unwrap()
    } else {
        0
    };

    let output_amount = input_amount
        .checked_sub(fee)
        .ok_or(MarginfiError::MathError)?;

    Ok(output_amount)
}

/// Processes a
/// [InitializeExtraAccountMetaList](enum.TransferHookInstruction.html)
/// instruction.
pub fn process_initialize_extra_account_meta_list(
    program_id: &Pubkey,
    accounts: &[AccountInfo],
    extra_account_metas: &[ExtraAccountMeta],
) -> ProgramResult {
    let account_info_iter = &mut accounts.iter();

    let extra_account_metas_info = next_account_info(account_info_iter)?;
    let mint_info = next_account_info(account_info_iter)?;
    let authority_info = next_account_info(account_info_iter)?;
    let _system_program_info = next_account_info(account_info_iter)?;

    // check that the one mint we want to target is trying to create extra
    // account metas
    #[cfg(feature = "forbid-additional-mints")]
    if *mint_info.key != crate::mint::id() {
        return Err(ProgramError::InvalidArgument);
    }

    // check that the mint authority is valid without fully deserializing
    let mint_data = mint_info.try_borrow_data()?;
    let mint = StateWithExtensions::<Mint>::unpack(&mint_data)?;
    let mint_authority = mint
        .base
        .mint_authority
        .ok_or(TransferHookError::MintHasNoMintAuthority)?;

    // Check signers
    if !authority_info.is_signer {
        return Err(ProgramError::MissingRequiredSignature);
    }
    if *authority_info.key != mint_authority {
        return Err(TransferHookError::IncorrectMintAuthority.into());
    }

    // Check validation account
    let (expected_validation_address, bump_seed) =
        get_extra_account_metas_address_and_bump_seed(mint_info.key, program_id);
    if expected_validation_address != *extra_account_metas_info.key {
        return Err(ProgramError::InvalidSeeds);
    }

    // Create the account
    let bump_seed = [bump_seed];
    let signer_seeds = collect_extra_account_metas_signer_seeds(mint_info.key, &bump_seed);
    let length = extra_account_metas.len();
    let account_size = ExtraAccountMetaList::size_of(length)?;
    invoke_signed(
        &system_instruction::allocate(extra_account_metas_info.key, account_size as u64),
        std::slice::from_ref(extra_account_metas_info),
        &[&signer_seeds],
    )?;
    invoke_signed(
        &system_instruction::assign(extra_account_metas_info.key, program_id),
        std::slice::from_ref(extra_account_metas_info),
        &[&signer_seeds],
    )?;

    // Write the data
    let mut data = extra_account_metas_info.try_borrow_mut_data()?;
    ExtraAccountMetaList::init::<ExecuteInstruction>(&mut data, extra_account_metas)?;

    Ok(())
}
