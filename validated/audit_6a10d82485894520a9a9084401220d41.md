### Title
Unfunded instant-withdraw receipts can be claimed at any later time and drain underlying reserved for other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays any outstanding instant-withdraw receipt at par from the strategy's entire underlying balance, with no check that the caller's receipt was ever funded by `collectInstantWithdrawFunds`. A user whose instant request was not funded (because `pendingInstantWithdraws` was never fully collected for their epoch) can wait indefinitely and claim whenever the strategy happens to hold enough underlying — including underlying that `collectInstantWithdrawFunds`/`collectWithdrawFunds` collected to back *other* users' receipts. The analog to the reported bug is that there is no epoch- or funding-scoped validation on claim time, so late/unfunded claims are settled first-come-first-served out of a shared pot, inflating one claim at the direct expense of other claimants.

### Finding Description
Instant withdraws are tracked only as a per-user aggregate and a global unfunded remainder:

- `requestInstantWithdraw` mints the user a 1:1 strategy-token receipt and bumps `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]`, and `pendingInstantWithdraws` [1](#0-0) .
- Funding arrives only via `collectInstantWithdrawFunds`, which decreases `pendingInstantWithdraws` and pulls tokens from the CDO — but it does not record *which* receipts were funded [2](#0-1) .
- `claimInstantWithdrawRequest` then burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)` unconditionally, for receipts of any age and any funding state [3](#0-2) .
- The only isolation check is in `_transferFundedClaim`: the balance must exceed `defaultRecoveryReserve` by the claim amount. Nothing reserves the funded portion for the specific users it was collected for [4](#0-3) .

Normal (non-instant) receipts get haircut accounting when the borrower underfunds via `collectWithdrawFunds` → `lossRecoveryPriceByEpoch`, and `_claimLossAdjustedWithdrawRequest` pays them proportionally [5](#0-4) . Instant receipts have no equivalent mechanism: when `pendingInstantWithdraws != 0`, the contract explicitly treats the balance minus that remainder as already-held reserve (`_defaultPrefundedInstantReserve`), confirming that balance and claims are decoupled [6](#0-5) .

Attack sequence (running/prefunded epoch, normal mode):
1. User A and attacker B each call `requestInstantWithdraw` (via the CDO) for 100 tokens; `pendingInstantWithdraws` = 200.
2. The borrower only returns 100; the CDO calls `collectInstantWithdrawFunds(100)` — `pendingInstantWithdraws` = 100, strategy balance = 100. That 100 was collected for the queue as a whole, but A is the honest user expected to claim.
3. B simply calls `claimInstantWithdrawRequest` through the CDO first — there is no per-epoch funding gate and no timestamp/epoch validation — and receives the 100. A's claim later reverts on `safeTransfer` (insufficient balance). B stole A's funded claim; equivalently, B could wait arbitrarily many epochs and claim the moment any underlying lands in the strategy (e.g., `deposit` pulling funds in before `sendInterestAndDeposits` pushes them out [7](#0-6) ).

### Impact Explanation
Direct theft of funded claim proceeds: an unprivileged holder of an *unfunded* instant receipt can extract underlying that was collected to satisfy other users' receipts. The invariant "one funded receipt, one payout" is broken because funding is pooled while claims are par-value and unordered; loss amount is bounded by the strategy's claimable balance (up to `balance - defaultRecoveryReserve`).

### Likelihood Explanation
Requires a partially funded instant-withdraw queue (`pendingInstantWithdraws > 0` while the strategy holds underlying), which occurs whenever the borrower returns less than the instant queue or funding is split across transactions. The attacker needs only a tranche position and an instant request of their own; timing the claim before the legitimate claimant is a single transaction in any later block/epoch. The code comments even acknowledge the aggregate design ("we record both per-user and per-epoch ... to distinguish default-epoch pending receipts from old funded receipts"), but that distinction is only enforced inside the default-finalization path, not in the normal claim path.

### Recommendation
Track a funded watermark for instant claims (e.g., a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds`), and have `claimInstantWithdrawRequest` pay at most the funded FIFO portion — or apply the same `lossRecoveryPrice`-style haircut used for normal receipts when the instant queue is underfunded. Alternatively, attribute instant funding per epoch so a receipt from epoch N can only draw down funds collected against epoch N.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
