### Title
Cross-user response hijacking via unvalidated MessageId collision in savedCallbacks map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each pending user callback in `h.savedCallbacks` keyed only by `msg.Body.MessageId` [1](#0-0) , with no check for an existing entry or binding to the requester's identity. Since `MessageId` is attacker-supplied (it originates from the JSON-RPC request ID set by the caller in `ValidatedMessageFromReq`) [2](#0-1) , an unprivileged second caller can submit a message reusing a victim's in-flight `MessageId` and silently overwrite the victim's saved callback before the DON responds.

### Finding Description
The gateway's public HTTP entrypoint `gateway.ProcessRequest` accepts an arbitrary, caller-chosen JSON-RPC request `ID`, which is validated only for length (max 200 chars) [3](#0-2)  and then forwarded unchanged into `msg.Body.MessageId` via `ValidatedMessageFromReq`/`msg.Validate()` [4](#0-3) . It routes to `HandleLegacyUserMessage` on the capabilities handler through `MultiHandler.HandleLegacyUserMessage` [5](#0-4) .

Inside `HandleLegacyUserMessage`, after validating payload/timestamp/method, the handler does:
```
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [1](#0-0) 
This unconditionally overwrites any existing entry for the same `MessageId` — there is no `found` check, no rejection of duplicate IDs, and no association with `msg.Body.Sender`. When a node later replies, `handleWebAPITriggerMessage` looks the callback up purely by `MessageId`, deletes it, and delivers the response to whichever callback is currently stored:
```
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
...
return savedCb.SendResponse(...)
``` [6](#0-5) 

Exploit flow: victim sends a `web_api_trigger` request with a chosen/predictable ID `X` (attacker can predict this if the client uses sequential/timestamp-based IDs, or the attacker simply races with a batch of guesses); before the DON nodes respond, the attacker sends its own self-signed `web_api_trigger` message with the same `MessageId = X` to the same DON/handler. The attacker's call to `HandleLegacyUserMessage` overwrites `h.savedCallbacks[X]` with the attacker's own `callback`. When the DON node's genuine response for the victim's request `X` arrives at `HandleNodeMessage` → `handleWebAPITriggerMessage`, it is delivered to the attacker's stored callback instead of the victim's, and the victim's original HTTP call in `gateway.ProcessRequest` blocks on `callback.Wait(ctx)` until timeout [7](#0-6) , receiving nothing (or a subsequent unrelated response if the roles are reversed).

No existing check prevents this: node message validation (`msg.Body.Sender != nodeAddr`) only validates that the *node* response comes from the expected node address [8](#0-7) , but this has nothing to do with which *user* callback the response is routed to — that routing depends solely on the colliding `MessageId` key in `savedCallbacks`.

### Impact Explanation
This allows cross-user response hijacking: an unprivileged gateway client can redirect another user's workflow trigger response to itself, or deny a victim's response, matching the "cross-user response confusion" impact class described. Because the `TriggerRequestPayload` may include response data forwarded from the DON, this could leak information intended for the victim's request or allow the attacker to observe capability execution results not meant for them.

### Likelihood Explanation
The attack requires only that the attacker be a client capable of sending arbitrary self-signed messages to the same DON/handler (no admin/operator access needed), and that the attacker can obtain or predict the victim's in-flight `MessageId` within the request's outstanding window (up to `MaxAllowedMessageAgeSec`/until the DON's response returns, typically sub-second to a few seconds). Feasibility depends on how MessageIds are generated by real clients (if truly random/high-entropy, guessing is hard; if sequential, timestamp-based, or otherwise observable/leaked, it's trivial). The race window and requirement to guess/observe the exact ID before the node responds reduce reliability, but repeated attempts are possible without any rate-limit blocking the write path itself (only `nodeRateLimiter` restricts node->gateway outgoing traffic, not incoming user requests here per the `// TODO: apply allowlist and rate-limiting here` comment [9](#0-8) ).

### Recommendation
Reject writes to `savedCallbacks` when a non-expired entry already exists for the same `MessageId` (return a duplicate-ID error to the second caller instead of overwriting), and/or bind the saved callback to `msg.Body.Sender` so that node responses are only routable to the callback registered by the same sender, and/or generate/prefix `MessageId` server-side (e.g., combine with sender address) rather than trusting client-supplied IDs verbatim as the sole map key.

### Proof of Concept
Go handler-level integration test (extending `TestHandlerReceiveHTTPMessageFromClient` in `core/services/gateway/handlers/capabilities/handler_test.go`):
1. Build `msgVictim := triggerRequest(t, victimKey, ...)` with `MessageId = "X"`.
2. Build `msgAttacker := triggerRequest(t, attackerKey, ...)` also with `MessageId = "X"` (modify `triggerRequest` helper to accept a custom message ID).
3. Call `cbVictim := hc.NewCallback(); handler.HandleLegacyUserMessage(ctx, msgVictim, cbVictim)`.
4. Immediately call `cbAttacker := hc.NewCallback(); handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)`.
5. Assert (expected fix behavior): the second call returns an error (duplicate MessageId) OR `savedCallbacks["X"]` still references `cbVictim`.
6. Simulate the DON node responding to `MessageId = "X"` via `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
7. Assert `cbVictim.Wait(ctx)` receives the correct response, and `cbAttacker.Wait(ctx)` times out or receives an explicit rejection — proving isolation is preserved.
Currently (pre-fix), step 5 will show `savedCallbacks["X"]` overwritten by the attacker's callback, and step 7 will show `cbAttacker` receiving the victim's response while `cbVictim` times out, confirming the vulnerability.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
