## Finding [1](#0-0) 

The bug-class from the report — *"the whole batch operation fails because of a single malfunctioning member of the batch"* — has a direct analog in Agave's account-returning JSON-RPC handlers (`getProgramAccounts`, `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, `getMultipleAccounts`). Each of these iterates a set of accounts and encodes them with `.collect::<Result<Vec<_>>>()?`; a single account that cannot be encoded in the requested encoding aborts the *entire* response instead of only affecting that one account.

### Title
Single oversized account aborts an entire multi-account RPC response (`getProgramAccounts`/`getMultipleAccounts`/`getTokenAccountsBy*`) - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_program_accounts`, `get_token_accounts_by_owner`, `get_token_accounts_by_delegate`, and `get_multiple_accounts` map every matched account through `encode_account`/`get_encoded_account` and collect the results with `collect::<Result<Vec<_>>>()?` (sync path) or propagate the first `Err` via `?` inside a loop (async path). `encode_account` returns an `Err` whenever the requested encoding is `Binary` (the *default* for `getProgramAccounts`) or `Base58` and the account's data (after slicing) exceeds `MAX_BASE58_BYTES` (128 bytes). Because a single failing account propagates the error for the whole call, one large/malformed account among many well-formed ones causes the caller to receive a complete failure instead of the accounts that were perfectly fine to encode.

### Finding Description
- `get_program_accounts` (`rpc/src/rpc.rs:603-666`) defaults `encoding` to `UiAccountEncoding::Binary` when the caller supplies no encoding: [2](#0-1)  Every returned account is then encoded with `encode_account(&account, &pubkey, encoding, data_slice_config)?` inside `.collect::<Result<Vec<_>>>()?`: [3](#0-2) 
- `encode_account` (`rpc/src/rpc.rs:2575-2601`) rejects any account whose sliced data is larger than `MAX_BASE58_BYTES` (128 bytes) for `Binary`/`Base58` encodings, returning `Err(error::Error{code: InvalidRequest, ...})`: [4](#0-3) 
- The same `.collect::<Result<Vec<_>>>()?` pattern (which aborts on the first `Err`) is used in `get_token_accounts_by_owner` and `get_token_accounts_by_delegate`: [5](#0-4) [6](#0-5) 
- `get_multiple_accounts` (`rpc/src/rpc.rs:562-592`) has the equivalent behavior: it loops over the caller-supplied `pubkeys`, and for each one calls `get_encoded_account(...)?`, so one bad pubkey aborts the whole batch response: [7](#0-6) 

This is exactly the pattern described in the external report: an operation that logically operates over a *collection* of independent items (plugins in the report; accounts here) is implemented so that one bad/oversized item poisons the result for the entire collection, rather than being handled/reported independently (e.g., returning `null`/error only for that entry, as `getMultipleAccounts` already does for genuinely missing accounts).

### Impact Explanation
Any unprivileged RPC caller performing `getProgramAccounts` (with default or Base58 encoding), `getTokenAccountsByOwner`/`getTokenAccountsByDelegate` (Base58/Binary), or `getMultipleAccounts` (Base58/Binary) against a program/owner/address set that happens to include just one account with data > 128 bytes will receive a complete `InvalidRequest` error for the whole call — even though the RPC could otherwise return correct, non-error data for every other matched account. This silently denies correct information to legitimate callers and forces retries with different encoding, degrading RPC usability; anyone can trivially create an account with >128 bytes owned by an arbitrary program to poison `getProgramAccounts` results for that program under default encoding.

### Likelihood Explanation
High. `getProgramAccounts`'s default encoding is `Binary` (base58), and most real on-chain accounts (token accounts, program accounts, etc.) commonly exceed 128 bytes of data, so this triggers unintentionally in ordinary usage, not just via adversarial construction. No special privileges are required; a single unprivileged JSON-RPC call is sufficient.

### Recommendation
Do not let one account's encoding failure abort the whole collection. Options:
1. Encode each account independently and, on a per-account encoding error (e.g., data too large for base58), substitute a per-item error/placeholder (similar to how missing accounts already yield `null` in `getMultipleAccounts`) instead of using `collect::<Result<Vec<_>>>()?`.
2. For `getProgramAccounts`/`getTokenAccountsBy*`, consider rejecting the base58/binary encoding for such calls more explicitly up-front (as is already done for `simulate_transaction`'s account config), or fall back to Base64 automatically for oversized accounts, and document this behavior.

### Proof of Concept
1. Deploy/store one account owned by program `P` whose data length exceeds `MAX_BASE58_BYTES` (128 bytes), alongside several other normal-size accounts also owned by `P`.
2. Call `getProgramAccounts(P)` with no `encoding` field (defaults to `Binary`) or `encoding: "base58"`.
3. Observe the RPC returns a JSON-RPC error (`InvalidRequest`, "Encoded binary (base 58) data should be less than 128 bytes...") for the *entire* call, rather than returning the accounts that could be encoded fine and erroring only on the oversized one — mirroring `rpc/src/rpc.rs`'s existing test `test_encode_account_throws_when_data_too_large_to_base58_encode` (rpc.rs:5728-5741) but shown here to poison an entire multi-account result set instead of a single-account call. ```rust
fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
