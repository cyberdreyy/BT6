### Title
Stale confirmations from removed members still count toward the confirmation threshold, allowing execution below the required number of live signers - (File: `multisig2/src/lib.rs`)

### Summary
`confirm` executes a pending `MultiSigRequest` once the number of entries in its `confirmations` set reaches `num_confirmations`, without re-validating that each confirming entry still belongs to a current multisig member. `delete_member` only purges requests *created* by the removed member; it does not scan or purge that member's *confirmations* left on other pending requests created by someone else. Consequently a stale confirmation from a now-removed member is still tallied, letting a request execute with fewer than `num_confirmations` live, authorized signers.

### Finding Description
The multisig's core invariant should be: a request executes only when `num_confirmations` *current* members have confirmed it — i.e. `|confirmations ∩ current_members| >= num_confirmations`. The implementation instead checks only `confirmations.len() + 1 >= num_confirmations` in `confirm`: [1](#0-0) 

`current_member()` is only used to validate the account making the *current* `confirm`/`add_request` call — it is never used to filter the confirmations that already exist in the set for other, unrelated confirmers: [2](#0-1) 

When a member is deleted via `DeleteMember`, `delete_member` removes outstanding requests *authored* by that member (`r.member == member`, i.e. the request creator), and removes the deleted member's `num_requests_pk` entry, but does nothing to any `confirmations` sets belonging to requests created by *other* members that the deleted member may have already confirmed: [3](#0-2) 

So if a removed member had previously confirmed a still-pending request created by someone else, that confirmation remains present in `self.confirmations` for that request indefinitely, and is still counted the next time any remaining live member confirms — even though the removed member no longer holds any key or authorization over the account.

### Impact Explanation
This breaks the multisig's core authorization binding — "confirmations counted" no longer equals "confirmations from live/current members." A request can be pushed over the `num_confirmations` threshold and executed (transferring NEAR, deploying a contract, adding a full-access key, etc.) with fewer than `num_confirmations` *currently authorized* signers actually agreeing. This matches the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
This requires no privileged/attacker capability beyond being an existing member of the multisig at the time of confirming (a normal, expected role) and simply exploits an ordering that any member-removal workflow can trigger: confirm a pending request, then get removed (or have another member removed) before the request accumulates the remaining confirmations. Multi-member multisigs with membership rotation (a supported, documented feature via `AddMember`/`DeleteMember`) will routinely hit this ordering.

### Recommendation
When deleting a member in `delete_member`, iterate over `self.confirmations` for *all* pending requests (not only ones authored by the removed member) and remove the deleted member's entry from each confirmation set. Alternatively, when tallying confirmations in `confirm`, filter the stored confirmation set against `self.members` before comparing its length to `num_confirmations`, ensuring only live members' confirmations count toward the threshold.

### Proof of Concept
1. Deploy multisig with members `[A, B, C, D]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(request)` — creates request with 1 confirmation (from `A`).
3. `B` calls `confirm(request_id)` — now 2 confirmations (`A`, `B`); request still pending (2 < 3).
4. A request to `DeleteMember { member: B }` is separately raised and confirmed by 3 members (e.g. `A, C, D`), executing and removing `B` from `self.members` and deleting `B`'s own outstanding requests — but `B`'s confirmation on the request from step 2/3 is untouched because that request was created by `A`, not `B`.
5. `C` (a live, current member) calls `confirm(request_id)` on the original request. `confirmations.len() + 1 == 3 >= num_confirmations`, so the request executes — using `A`, `B` (removed), and `C` as its 3 "confirmations," even though only 2 currently-authorized members (`A`, `C`) actually agreed at execution time.     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);

            .unwrap_or_else(|| env::panic_str("Must be validated above"));

        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************

            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
