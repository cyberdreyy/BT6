## Title
`block_rejection_signer_addrs` table keys on `signer_addr` alone, so a signer's rejection of one block silently overwrites (and disappears from) the rejection tally of a different, earlier block - (File: stacks-signer/src/signerdb.rs)

### Summary
The `block_rejection_signer_addrs` table is used exactly like the UNION `voucherIndexes`/`voucheeIndexes` arrays in the report: it is supposed to record a per-`(block, signer)` fact so that later reads (`get_block_rejection_signer_addrs`) can reconstruct an accurate weight tally for *that specific block*. Instead its schema declares `PRIMARY KEY (signer_addr)` only, with `signer_signature_hash` as a plain, non-key column. Just like the vouch report's stale array slot getting overwritten by unrelated data, a signer's rejection row is a *single global slot per signer address* that gets clobbered by whatever block that signer most recently rejected, corrupting the recorded state for any earlier block that same signer rejected.

### Finding Description
`CREATE_BLOCK_REJECTION_SIGNER_ADDRS_TABLE` is defined as: [1](#0-0) 

```
CREATE TABLE IF NOT EXISTS block_rejection_signer_addrs (
    signer_signature_hash TEXT NOT NULL,
    signer_addr TEXT NOT NULL,
    PRIMARY KEY (signer_addr)
) STRICT;
```

The primary key is `signer_addr` alone, not `(signer_signature_hash, signer_addr)`. Every write for this table is an `INSERT OR REPLACE` keyed on that lone primary key: [2](#0-1) 

`store_and_process_block_rejection` calls `signer_db.add_block_rejection_signer_addr(block_hash, signer_address, reject_reason)`, then immediately reads back `get_block_rejection_signer_addrs(block_hash)` to compute `total_reject_weight` and decide whether the *globally-rejected* threshold has been crossed for that block: [3](#0-2) 

Because the primary key is only `signer_addr`, if the same signer rejects **any other block** (a normal, expected event — a signer routinely rejects/accepts different competing proposals at the same or different heights during a tenure), the `INSERT OR REPLACE` on `block_rejection_signer_addrs` overwrites that signer's *only* row, rewriting its `signer_signature_hash` to point at the new block and erasing the fact that it ever rejected the first block. Any subsequent call to `get_block_rejection_signer_addrs(old_block_hash)` will silently omit that signer, understating `total_reject_weight` for the old block.

This exactly parallels the referenced UNION Finance bug: an index/record that is supposed to be maintained per-relationship (borrower×staker there, block×signer here) is instead only tracked in a single slot that later activity overwrites, producing stale/incorrect data for the entity that lost its slot.

### Impact Explanation
This breaks the "rejection tally == verified accepts/rejects" equality for the *older* block: a signer's genuine rejection vote for block A silently vanishes from A's rejection count as soon as that signer casts a rejection for block B. Because `handle_block_rejection`/`store_and_process_block_rejection` uses this table as the source of truth for the 30%-blocking-minority "globally rejected" decision (and the associated `ReorgNotAllowed` miner-invalidation logic), this can:
- Prevent block A from ever reaching the "globally rejected" state even though a sufficient weighted minority actually rejected it (a rejection is silently dropped/recounted as if it never happened) — a signer being wedged into an inconsistent, understated tally is the kind of miscount the rules classify as impactful (a rejection recounted incorrectly).
- Cause different signers to reach different conclusions about whether block A was globally rejected, depending on the order/timing in which each observed rejections locally versus other blocks — a state-machine equality break across signers rather than merely a local UI counter.
- Because `mark_globally_rejected` and downstream reorg-permit logic depend on this weight, an incorrect (lower) `total_reject_weight` could delay or block correct rejection accounting, contributing to liveness or safety inconsistency in cross-block/cross-tenure evaluation of conflicting proposals.

This satisfies the "High"/rejection-recounted-as-acceptance-adjacent bug class: a legitimate rejection is lost/miscounted due to a keying defect, not because of any attacker action, malicious signer, or majority collusion — it can happen during entirely normal signer activity (rejecting two different competing block proposals in sequence).

### Likelihood Explanation
High likelihood of being triggered in ordinary operation: any signer that rejects more than one distinct block signature hash during its runtime (which is common — miners regularly re-propose blocks after timeouts, and different candidate blocks at the same or adjacent heights are routinely rejected for different reasons) will overwrite its own prior rejection row. No majority collusion, no other signer's key, and no special network conditions are required — it is a single-signer, single-node defect triggered by normal multi-block rejection traffic (which itself can be triggered by a one-slot miner proposing/re-proposing competing blocks).

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)` (matching the pattern already used correctly for `block_pre_commits`, `block_signatures`, and the pending-response tables), and add a migration to reshape any existing rows. Ensure `add_block_rejection_signer_addr` performs `INSERT OR REPLACE`/`INSERT OR IGNORE` against the composite key rather than the signer address alone, so that a signer's rejection of block B cannot overwrite its still-relevant rejection record for block A.

### Proof of Concept
1. Reward cycle with signer S (weight W) and two competing/successive block proposals with distinct `signer_signature_hash` values H_A and H_B (e.g., an initial proposal and a later re-proposal after a timeout, or two different tenure-start candidates).
2. Signer S locally rejects block A: `store_and_process_block_rejection` calls `add_block_rejection_signer_addr(H_A, S, reason)` → row `(H_A, S)` inserted, PK = `S`.
3. `get_block_rejection_signer_addrs(H_A)` returns `[S]`; tally for A includes weight W.
4. Before the network reaches the 30% threshold on block A, block B is proposed/re-proposed and S rejects it too: `add_block_rejection_signer_addr(H_B, S, reason)` executes `INSERT OR REPLACE INTO block_rejection_signer_addrs (signer_signature_hash, signer_addr) VALUES (H_B, S)`. Because the table's only key is `signer_addr = S`, this **replaces** the existing row rather than adding a new one.
5. `get_block_rejection_signer_addrs(H_A)` is now called again (e.g., triggered by another signer's later rejection of block A) and no longer returns S — `total_reject_weight` for H_A is short by W, even though S genuinely rejected H_A and never retracted that vote. [1](#0-0) [4](#0-3)
