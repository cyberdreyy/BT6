### Title
`setTrancheAPRSplitRatio`/`setFeeParams` retroactively apply the new parameters to accrued-but-unsplit yield, letting one tranche class (or the fee recipient) capture interest earned under the old parameters - (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO.setTrancheAPRSplitRatio` and `IdleCDO.setFeeParams` update yield-splitting parameters without first calling `_updateAccounting()`. Because `_virtualPriceAux` splits *all* gains accrued since the last accounting update using the *current* `trancheAPRSplitRatio`/`fee`, the new parameters are applied retroactively to yield that accrued under the old ones — the exact same bug class as the `V3Vault.setReserveFactor` finding.

### Finding Description
The bug-class analog is a rate parameter that changes without checkpointing accrued interest. Two instances exist in `contracts/IdleCDO.sol`:

1. `setTrancheAPRSplitRatio` (IdleCDO.sol:899-903):
```solidity
function setTrancheAPRSplitRatio(uint256 _trancheAPRSplitRatio) external virtual {
    _checkOnlyOwner();
    _checkAmountTooHigh((trancheAPRSplitRatio = _trancheAPRSplitRatio) > FULL_ALLOC);
}
```

2. `setFeeParams` (IdleCDO.sol:860-864):
```solidity
function setFeeParams(address _feeReceiver, uint256 _fee) external {
    _checkOnlyOwner();
    _checkIs0((feeReceiver = _feeReceiver) == address(0));
    _checkAmountTooHigh((fee = _fee) > MAX_FEE);
}
```

In `_updateAccounting`/`_virtualPriceAux` (IdleCDO.sol:273-311, 359-390; IdleCDOCreditVault.sol:287-337), `totalGain = nav - lastNAV` covers *all* yield accrued since the last deposit/withdraw/harvest. That gain is fee-reduced with the *current* `fee` and split AA/BB with the *current* `trancheAPRSplitRatio`:

```solidity
int256 totalBBGain = totalGain * int256(FULL_ALLOC - _trancheAPRSplitRatio) / int256(FULL_ALLOC);
_totalTrancheGain = _isAATranche ? (totalGain - totalBBGain) : totalBBGain;
```

So when the owner changes either parameter, the next `_updateAccounting` (triggered by any user's deposit/withdraw/harvest) re-prices the entire pending gain under the new parameters. The same retroactivity applies to `setMinAprSplitAYS`/`setIsAYSActive` (IdleCDOCreditVault.sol:450-453, 479-482), since `_updateSplitRatio` only runs on user interactions and rewrites `trancheAPRSplitRatio` before the pending gain is split. By contrast, `setFeeParams` in `IdleCDOCreditVault.sol:461-470` correctly checkpoints the *management* fee via `_accrueManagementFee()` before mutating `managementFee` — but still does not run `_updateAccounting`, so the performance `fee` remains retroactive.

### Impact Explanation
Yield accrued over the whole period since the last accounting update is redistributed differently than holders were promised at accrual time:

- Raising `trancheAPRSplitRatio` transfers part of BB holders' already-earned yield to AA holders; lowering it steals from AA holders in favor of BB holders. With a long accrual period and a large pending gain, a 10% ratio change on e.g. 100k USDC of pending gain moves ~10k USDC between classes.
- Raising `fee` retroactively skims the new percentage off gains that accrued under the old fee, sending unearned assets to `feeReceiver`/`owner`.

An unprivileged tranche holder on the favored side captures yield they did not earn; a holder anticipating an unfavorable change cannot avoid the retroactive hit, because the gain only crystallizes on the next `_updateAccounting` *after* the parameter is already changed. This is theft/misallocation of accrued yield — the invariant "each epoch's interest is split per the parameters in force while it accrued" is broken.

### Likelihood Explanation
These are ordinary admin operations (parameter tuning), executed whenever governance adjusts APR split or fees — not edge cases. Every such call made while a nonzero gain sits unsplit (the common case between harvests/deposits) produces the misallocation; loss magnitude grows with time since last accounting update and pending gain size. No guard prevents it: `_updateAccounting` is internal to user flows, and the owner-only `updateAccounting()`/`_forceUpdateAccounting` exists but is never invoked by the setters. The exploitable window requires only that `nav > lastNAVAA + lastNAVBB`, which holds whenever the strategy has earned anything since the last interaction.

### Recommendation
Call `_updateAccounting()` (or `_forceUpdateAccounting()` in CreditVault, to avoid `Default()` reverts blocking parameter changes) at the top of `setTrancheAPRSplitRatio`, `setFeeParams`, `setMinAprSplitAYS`, `setIsAYSActive`, and any other setter that mutates parameters consumed by `_virtualPriceAux`, so pending gains are crystallized under the old parameters before the new ones take effect:

```solidity
function setTrancheAPRSplitRatio(uint256 _trancheAPRSplitRatio) external virtual {
    _checkOnlyOwner();
    _forceUpdateAccounting();
    _checkAmountTooHigh((trancheAPRSplitRatio = _trancheAPRSplitRatio) > FULL_ALLOC);
}
```

### Proof of Concept
Foundry fork PoC on `IdleCDOCreditVault` (fixed-APR epoch mode), mirroring the external report's structure:

```solidity
function testRetroactiveSplitRatio() public {
    // AA and BB deposit equal amounts; epoch runs
    _depositAA(1000e18); _depositBB(1000e18);
    // strategy accrues yield (warp / simulated borrower interest payment)
    _accrueYield(100e18);

    // Scenario A: owner updates accounting first, then changes ratio
    vm.prank(owner); cdo.updateAccounting();
    uint256 bbBefore = cdo.virtualPrice(BB);
    vm.prank(owner); cdo.setTrancheAPRSplitRatio(newRatio);
    assertEq(cdo.virtualPrice(BB), bbBefore); // no retroactive effect

    // Scenario B (bug): ratio changed without accounting update
    // reset state, accrue same 100e18 yield
    vm.prank(owner); cdo.setTrancheAPRSplitRatio(newRatio);
    // any unprivileged user interaction crystallizes the pending gain under newRatio
    vm.prank(attacker); cdo.depositAA(1);
    // BB price reflects newRatio applied to the ENTIRE accrued gain, not just post-change yield
    assert(cdo.virtualPrice(BB) != bbBefore);
}
```

Both scenarios start from identical accrued state; only ordering differs, demonstrating that `setTrancheAPRSplitRatio` retroactively reprices past yield. The identical test with `setFeeParams` shows `unclaimedFees` jumping by `(newFee - oldFee) * pendingGain / FULL_ALLOC` on the next `_updateAccounting`. Note: I confirmed the setter code paths and the `_virtualPriceAux` split logic in `IdleCDO.sol`/`IdleCDOCreditVault.sol`; the exact PoC numbers depend on fork state and were not executed in this session.
