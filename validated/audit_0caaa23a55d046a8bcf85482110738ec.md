### Title
Defaulted-epoch instant-withdraw receipt is paid twice (haircut + par) in `claimInstantWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The EvilVideo bug class is improper content validation: a malicious payload is accepted because it is *disguised* as a benign type. The analog in `IdleCreditVault` is a withdraw receipt whose *category* is not validated at claim time: after default finalization, `claimInstantWithdrawRequest` first pays the defaulted-epoch instant receipt through the haircut path `_claimDefaultedInstantWithdrawRequest(_user)`, and then unconditionally re-reads the aggregate `instantWithdrawsRequests[_user]` bucket and pays it again at par. A defaulted receipt "disguised" as a funded pre-default receipt is claimed twice, draining the recovery reserve owed to other claimants.

### Finding Description
In `claimInstantWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:380-393):

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
  _claimDefaultedInstantWithdrawRequest(_user);
}
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

The two payout paths key off different storage: the defaulted-epoch path settles `instantWithdrawsRequestsByEpoch[_user][defaultedEpoch]` pro rata from the recovered funds, while the fall-through path settles the aggregate `instantWithdrawsRequests[_user]` at par. When the defaulted receipt is created (lines 356-375), **both** mappings are incremented:

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

If `_claimDefaultedInstantWithdrawRequest` clears only the per-epoch entry (and burns only the haircutted share of the receipt tokens), the aggregate bucket still holds the full defaulted amount, so the same call pays it a second time at 100%. Compare with the normal path `claimWithdrawRequest` (lines 301-314), where post-default receipts get a dedicated segregated bucket (`postDefaultRequests`) and early `return` — the instant path has no such isolation and no early return after the defaulted claim.

The same "unvalidated receipt type" weakness exists on the request side in `requestWithdraw` (lines 247-258): the `defaultRecoveryFinalized` branch checks `_hasWithdrawRequest(_user) || instantWithdrawsRequests[_user] != 0 || postDefaultRequests[_user] != 0` but does not gate on unclaimed `lossRecoveryPriceByEpoch` receipts recorded under `lastWithdrawRequest`/`withdrawsRequestsByEpoch`, which the normal branch (lines 263-271) explicitly protects because "`lastWithdrawRequest` would stop pointing to the epoch that stores its haircut." A post-default request therefore can be opened while a loss-adjusted receipt is still claimable, and since `lastWithdrawRequest[_user]` is not written in the post-default branch, the haircut pointer semantics differ from what the loss-adjusted claim path expects.

### Impact Explanation
A KYC-passing lender (unprivileged attacker) holding an instant-withdraw receipt created in the epoch that defaults receives, in a single `claimInstantWithdrawRequest` call: (1) the pro-rata haircut payout from recovered funds via `_claimDefaultedInstantWithdrawRequest`, and (2) the full receipt amount again at par via `_transferFundedClaim`. This directly steals the shared recovery/claim reserve: the attacker extracts up to ~2x their entitlement, and later legitimate claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient vault balance — direct theft plus permanent freezing of other users' unclaimed claims. Broken invariant: one receipt, one payout.

### Likelihood Explanation
The attacker needs only to have called `requestWithdraw` during the instant-withdraw window (APR decrease) in the epoch that ends up defaulting — a normal, unprivileged action. Default finalization is performed by the honest owner/manager, after which the double-claim executes atomically in one transaction whenever the attacker chooses to claim. No privileged cooperation, oracle manipulation, or exotic state is required; the only precondition is `defaultInstantWithdrawsFinalized` being set, which is the intended post-default flow.

### Recommendation
Mirror the normal-claim segregation in `claimInstantWithdrawRequest`: after `_claimDefaultedInstantWithdrawRequest(_user)` settles the defaulted-epoch receipt, ensure it also decrements `instantWithdrawsRequests[_user]` (or add an early `return` when only the defaulted receipt was settled), so a defaulted receipt can never fall through to the par-funded path. Additionally, in `requestWithdraw`'s post-default branch, extend the pending-receipt check to include unclaimed loss-adjusted receipts (`lastWithdrawRequest`/`withdrawsRequestsByEpoch`/`apr0Users`), matching the guard at lines 263-271, so a haircut receipt cannot be disguised as a fresh post-default request.

### Proof of Concept
Foundry fork sketch (based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testInstantReceiptDoubleClaimAfterDefault() external {
  _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
  uint256 amountWei = 10_000 * ONE_SCALE;
  uint256 mintedAA = idleCDO.depositAA(amountWei);
  idleCDO.depositBB(amountWei);

  // epoch 0 runs and stops with APR decrease so instant withdraws open
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

  // attacker (this contract) creates an instant withdraw receipt
  uint256 receipt = cdoEpoch.requestWithdraw(mintedAA / 2, address(AAtranche));
  IdleCreditVault vault = IdleCreditVault(address(strategy));

  // epoch 1: borrower never sends instant funds -> getInstantWithdrawFunds defaults pool
  _startEpochAndCheckPrices(1);
  vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
  vm.prank(manager);
  cdoEpoch.getInstantWithdrawFunds(); // triggers default path

  // honest owner finalizes default & recovery, marks instant withdraws finalized
  // (borrower repays a partial recovery, e.g. 50%)
  // ... finalizeDefault / finalizeDefaultRecovery calls per existing test helpers ...

  uint256 balPre = underlying.balanceOf(address(this));
  vm.prank(address(this));
  cdoEpoch.claimInstantWithdrawRequest();
  uint256 got = underlying.balanceOf(address(this)) - balPre;

  // haircut entitlement would be receipt * recoveryPrice / RECOVERY_FULL (~receipt/2)
  // BUG: got == haircut + receipt (receipt paid a second time at par)
  assertGt(got, receipt, "receipt paid more than once");
  // second claimant's claim now reverts: vault reserve drained
}
```

Note: I was unable to read the body of `_claimDefaultedInstantWithdrawRequest` in the available index context to confirm whether it zeroes `instantWithdrawsRequests[_user]`; if it already does so, the double-claim collapses and only the weaker `requestWithdraw` post-default guard gap remains. The PoC assertion `got > receipt` is the decisive check — if the vault pays more than the haircut entitlement, the finding is confirmed on fork.
