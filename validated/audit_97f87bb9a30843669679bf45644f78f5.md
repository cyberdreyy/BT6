### Title
External ERC4626 vault illiquidity permanently bricks `stopEpoch`, locking all pool funds - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
Like the Loihi assimilator finding, `IdleCDOEpochVariant.stopEpoch` depends on unguarded calls into an external system — the `ProgrammableBorrower` adapter and its ERC4626 vault. If `vault.withdraw` reverts, `onStopEpoch` reverts with `StopEpochVaultLiquidityUnavailable`, the revert bubbles out of `stopEpoch` before the default-handling `try/catch`, and the pool is stuck mid-epoch with no path to stop, default, or recover the funds held in the vault.

### Finding Description
In `_stopEpoch`, the programmable-borrower hook is called outside the `try/catch` that protects `getFundsFromBorrower`: [1](#0-0) 

The comment says "Hook reverts bubble so transient ERC4626 liquidity failures can be retried," but there is no fallback: every `stopEpoch` call reverts as long as the vault cannot satisfy the withdrawal. In `ProgrammableBorrower.onStopEpoch`, a failed `vault.withdraw(shortfall,...)` is converted into a hard revert: [2](#0-1) 

The external-vault dependency also exists earlier in the same call: `_resolveStopEpochInterest` calls `totalInterestDueNow()`, which reads `vault.convertToAssets` via `_currentVaultAssets()` — also unguarded: [3](#0-2) [4](#0-3) [5](#0-4) 

While `stopEpoch` cannot execute:
- `isEpochRunning` stays true, deposits/withdraw requests stay disabled (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` false).
- `pendingWithdraws` receipts from the previous epoch are never funded via `collectWithdrawFunds`, so `claimWithdrawRequest` never pays out.
- Recovery paths all depend on the same vault: `emergencyExitVault` calls `vault.redeem` and reverts identically, `setVault` is blocked while `epochAccountingActive` is true (cleared only inside `onStopEpoch`/`onDefault`), and `repay` redeposits into the vault rather than freeing it.
- The default path is unreachable: `_handleBorrowerDefault` is only invoked inside the `try/catch` or on a `false` return — a reverting hook skips both.

This is the exact Loihi pattern: one malfunctioning/illiquid external dependency bricks the whole pool because the call is on the critical settlement path and its revert is propagated.

### Impact Explanation
All pool principal parked in the vault sleeve is frozen for as long as the external ERC4626 vault cannot service withdrawals — for an illiquid lending vault (100% utilization) this can be indefinite, effectively permanent if the vault is impaired or pauses. Loss is the full strategy-token backing (all LP NAV) plus pending withdraw receipts, which can never be claimed. The invariant broken is "liveness of the epoch state machine": the pool cannot transition to stopped/closed/defaulted, and no privileged escape exists because every escape also touches the vault.

### Likelihood Explanation
An unprivileged attacker only needs to be a user of the shared ERC4626 vault (explicitly in scope). If the vault is a lending market, the attacker borrows all available liquidity, driving utilization to 100% so `vault.withdraw(shortfall)` reverts. They keep liquidity drained (re-borrowing any repayments or new deposits — including the CDO's own epoch-start redeposit in `onStartEpoch`/`_depositToVault`). This works even though the borrower honestly approves repayment, because the revert occurs before `getFundsFromBorrower` is reached. Cost is the interest on the attacker's borrow; the freeze persists as long as they maintain utilization.

### Recommendation
Do not let external vault failures propagate out of `stopEpoch`. Options:
- Wrap `onStopEpoch`/`totalInterestDueNow` in try/catch inside `_stopEpoch`; on failure, route to `_handleBorrowerDefault` so the pool enters the defaulted state and users can later claim recoveries per-asset instead of freezing.
- Provide a pool-level "partitioned"/end-of-life escape (as in the Loihi fix) allowing the owner to mark the vault position as defaulted and let LPs claim whatever the CDO/strategy actually holds.
- Let `setVault`/`emergencyExitVault` proceed (or force-clear `epochAccountingActive`) even when the old vault is unresponsive, so funds can be unwound through an alternate path.

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";
import {IERC4626} from "../contracts/interfaces/IERC4626.sol";

contract StopEpochVaultLockupPoC is Test {
    // Foundry fork test (mainnet). Setup: an IdleCDOEpochVariant pool with
    // isProgrammableBorrower = true, isInterestMinted = true, and a
    // ProgrammableBorrower whose `vault` is a real lending-style ERC4626
    // (e.g. a Morpho/Yearn vault holding the CDO underlying).

    IdleCDOEpochVariant cdo;
    ProgrammableBorrower pb;
    IERC4626 vault;
    IERC20Detailed underlying;
    address manager;
    address attacker = address(0xA77ACC);

    function test_vaultIlliquidityBricksStopEpoch() external {
        // --- buffer phase: LPs deposit, one LP requests a withdrawal ---
        // (cdo.depositAA/BB, cdo.requestWithdraw — KYC'd LPs)

        // --- manager starts the epoch; idle cash is parked in the vault ---
        vm.prank(manager);
        cdo.startEpoch();
        assertGt(vault.balanceOf(address(pb)), 0);

        // --- attacker (ordinary ERC4626 vault user) drains vault liquidity ---
        // For a lending vault: attacker supplies collateral and borrows all
        // available underlying, pushing utilization to ~100%.
        vm.startPrank(attacker);
        // vault-specific borrow or withdraw-all call, e.g.:
        // lendingMarket.borrow(underlying.balanceOf(address(vault)));
        vm.stopPrank();
        // vault now has ~0 liquid underlying; vault.withdraw will revert.

        // --- epoch end passes; manager honestly tries to stop the epoch ---
        vm.warp(cdo.epochEndDate() + 1);
        vm.prank(manager);
        // onStopEpoch -> vault.withdraw(shortfall) reverts
        // -> StopEpochVaultLiquidityUnavailable bubbles out of stopEpoch
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(0, 0);

        // --- retrying does not help; revert happens BEFORE the try/catch
        //     around getFundsFromBorrower, so _handleBorrowerDefault is
        //     never reached and `defaulted` stays false ---
        vm.prank(manager);
        vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
        cdo.stopEpoch(0, 0);
        assertFalse(cdo.defaulted());
        assertTrue(cdo.isEpochRunning());

        // --- privileged escapes also fail because they touch the vault ---
        vm.prank(pb.owner());
        vm.expectRevert(); // vault.redeem reverts on illiquidity
        pb.emergencyExitVault(0);

        vm.prank(pb.owner());
        vm.expectRevert(NotAllowed.selector); // epochAccountingActive still true
        pb.setVault(address(0xBEEF));

        // --- consequence: pending withdraw receipts unfundable,
        //     deposits/requests stay disabled, LP NAV locked in the vault
        //     as long as the attacker keeps utilization at 100% ---
    }
}
```
