### Title
Stale confirmations from removed multisig members allow request execution below effective live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both the v1 (key-based) and v2 (member-based) multisig contracts remove a departing signer's *own outstanding requests* when that signer/member is deleted, but never scrub that signer's *confirmations already cast on other members' requests*. A confirmation cast by a member who is later removed remains counted toward `num_confirmations` for any request it was applied to, so a request can execute after it has genuinely been approved by fewer currently-live members than the configured threshold — a "confirmations counted versus live members" binding violation, directly analogous to the ENS `NameWrapper` bug where stale authorization state (a fuse) survives a state transition (unwrap/rewrap) that should have invalidated it.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` decides execution purely from the size of the stored `confirmations: HashSet<String>` for a request versus the static `num_confirmations` threshold: [1](#0-0) 

Membership removal, `delete_member()`, only purges requests *created by* the removed member and that member's `num_requests_pk` entry — it does not scan other members' pending requests to strip out confirmations the removed member had already cast on them: [2](#0-1) 

So the binding the contract is supposed to maintain — `confirmations.len() >= num_confirmations` should mean "at least `num_confirmations` distinct **current** members approved" — is broken. After removal, it degrades to "at least `num_confirmations` distinct approvals were **ever** cast, including by since-removed members."

The identical gap exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` only removes requests where `r.signer_pk == pk` (i.e., requests the deleted key itself created), and `confirm()` again just checks `confirmations.len() as u32 + 1 >= self.num_confirmations`: [3](#0-2) [4](#0-3) 

### Impact Explanation
This lets a request execute (fund transfer, key/member addition, contract deploy, etc.) with fewer genuinely-authorized signers than `num_confirmations` mandates. Concretely: with a 2-of-3 multisig, if member A confirms a pending request created by B, and A is subsequently removed (compromised key rotation, offboarding, etc.) before the request reaches threshold and before it is deleted/expired, A's confirmation nonetheless still counts. A single additional confirmation from any remaining live member (C) then executes the request with only one truly current live approval (C) plus one stale, revoked approval (A) — i.e., a request authorized below the intended threshold of live signers. This matches the report's "Critical: a multisig request executed below threshold" impact category, since arbitrary `Transfer`, `FunctionCall`, `AddKey`/`AddMember` actions can move funds or grant access with insufficient current authorization.

### Likelihood Explanation
No privileged action beyond ordinary multisig operation is required — this only needs a normal membership-rotation event (removing a compromised/departing signer) to occur while a request confirmed by that signer is still pending, which is a routine operational scenario for any long-lived multisig, not an edge case requiring the foundation, an owner key, or a redeploy.

### Recommendation
On `DeleteMember`/`DeleteKey`, iterate all pending `requests`/`confirmations` entries and remove the departing member's public key/account from every confirmations set (not only requests it authored), or alternatively re-validate at `confirm()` time / execution time that every recorded confirming identity is still a current member before counting it toward the threshold.

### Proof of Concept
1. Deploy multisig with `num_confirmations = 2`, members `{A, B, C}`.
2. B calls `add_request` to transfer funds to an external account (request stays unconfirmed by threshold).
3. A calls `confirm(request_id)` → `confirmations = {A}`, `1 < 2`, request stays pending.
4. Members confirm and execute a `DeleteMember { member: A }` request (A is offboarded/compromised) — this only cleans up requests A *created*, not A's confirmation stored on B's transfer request.
5. C calls `confirm(request_id)` → `confirmations.len() + 1 = 2 >= num_confirmations(2)` → request executes, funds move, even though only C is a currently live confirming member; A's stale confirmation was counted toward the threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
