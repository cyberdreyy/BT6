### Title
Claimed instant-withdraw receipts are never removed from `instantWithdrawsRequestsByEpoch` / `instantWithdrawClaimsByEpoch`, leaving a stale claim basis that bricks post-default claims and strands `defaultRecoveryReserve` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` burns the user's receipt tokens and zeroes the aggregate `instantWithdrawsRequests[user]`, but it never clears the per-epoch entries `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` that `requestInstantWithdraw` recorded. This is the storage analog of CVE-2016-5131's use-after-free: receipt state that was already consumed ("freed") remains live in the per-epoch maps and is later re-read by the default-recovery path as if the claim were still pending.

### Finding Description
On request, both the aggregate and per-epoch accounting are written: `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`. [1](#0-0)  On a successful funded claim, only the aggregate is cleared — `instantWithdrawsRequests[_user] = 0` — while both per-epoch mappings retain the full basis. [2](#0-1) 

If the pool later defaults and is finalized, two stale-state effects occur:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the recovery basis whenever `pendingInstantWithdraws != 0`, so already-paid instant claims inflate the finalized basis and wrongly dilute `defaultRecoveryPrice` while receiving no recoverable funds. [3](#0-2) 
2. `_claimDefaultedInstantWithdrawRequest` re-reads `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` as a live claim, then performs `instantWithdrawsRequests[user] -= claimBasis`. Because the aggregate was zeroed on the first claim, any new instant request the user makes in the same epoch keeps the by-epoch value strictly larger than the aggregate (stale X + new Y > Y), so the subtraction always underflows and the whole `claimInstantWithdrawRequest` reverts. [4](#0-3) 

Every call to `claimInstantWithdrawRequest` runs the defaulted-epoch claim first once `defaultInstantWithdrawsFinalized` is set, so the revert permanently blocks the affected user. [5](#0-4)  The reserve consumed pro-rata for the stale basis in `defaultRecoveryPrice` can never be paid out — `_transferDefaultRecovery` only moves on a successful claim — so that share of `defaultRecoveryReserve` is stranded for all other claimants. [6](#0-5) 

No existing guard stops this: `_ensureDefaultRecoveryInitialized` refuses to run while `pendingInstantWithdraws != 0` but does not normalize the per-epoch maps, and the stale entries only manifest at default finalization, long after the claim that produced them. [7](#0-6) 

### Impact Explanation
Two quantified losses, both with direct fund impact:

- **Permanent freezing of user funds and recovery reserve.** A user who claimed an instant withdrawal and then re-requested an instant withdrawal in the same epoch number can never claim again once the pool defaults and `defaultInstantWithdrawsFinalized` is true — `_claimDefaultedInstantWithdrawRequest` underflows on `instantWithdrawsRequests[user] -= claimBasis` because `claimBasis` includes the already-paid stale amount. Their new receipt tokens are locked, and the reserve share priced for the phantom claim is permanently stranded inside the strategy.
- **Recovery dilution for all claimants.** The stale `instantWithdrawClaimsByEpoch[epochNumber]` inflates `defaultPendingClaimBasis`, lowering `defaultRecoveryPrice` for every legitimate defaulted receipt holder — value that is then never distributed, effectively destroying part of the recovered funds. [8](#0-7) 

### Likelihood Explanation
The trigger requires (a) an instant-withdraw request that is funded and claimed, (b) a subsequent instant-withdraw request by the same user recorded under the same `epochNumber` (which only advances inside `deposit()` during a running epoch, i.e. at `stopEpoch`), and (c) a borrower default finalized while that epoch number is still current and `pendingInstantWithdraws != 0`. [9](#0-8)  Sequence (a)→(b) is achievable in the buffer phase or while the epoch is running, entirely with unprivileged actions. Step (c) depends on honest-manager/borrower default timing, which is in scope. One caveat I could not fully verify within the available context: whether `epochNumber` at `finalizeDefaultRecovery` always equals the request epoch of same-cycle instant requests (it depends on `IdleCDOEpochVariant`'s ordering of the epoch counter increment relative to default finalization); if the counter increments before finalization in every default path, the stale basis instead manifests only as dilution of `instantWithdrawClaimsByEpoch`, which still permanently strands recovery value.

### Recommendation
Clear the per-epoch instant receipt accounting on every successful claim, mirroring `_clearWithdrawClaimForEpoch` for normal requests:

- In `claimInstantWithdrawRequest`, before zeroing the aggregate, record the request epoch(s) covered and set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Since instant requests are already keyed by the epoch at request time, a per-epoch clear like `instantWithdrawClaimsByEpoch[epochNumber] -= amount` (plus clearing the user entry) keeps the aggregate consistent.
- Alternatively, make `_claimDefaultedInstantWithdrawRequest` and `defaultPendingClaimBasis` trust only the aggregate `instantWithdrawsRequests`/`pendingInstantWithdraws` and not the additive per-epoch maps, so consumed receipts cannot re-enter recovery accounting.

### Proof of Concept
Foundry-style PoC (built on `test/foundry/IdleCreditVault.t.sol` helpers such as `_depositWithUser`, `_startEpochAndCheckPrices`, and the existing `deal(defaultUnderlying, borrower, ...)` pattern):

```solidity
function testStaleInstantReceiptBlocksRecoveryClaim() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    uint256 amount = 10_000 * ONE_SCALE;

    // 1. Attacker deposits and requests an instant withdrawal (epoch N).
    _depositWithUser(attacker, amount, true);
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(amount / 2, address(AAtranche));

    // 2. CDO funds the instant queue; attacker claims at par.
    //    instantWithdrawsRequests[attacker] -> 0, but
    //    instantWithdrawsRequestsByEpoch[attacker][N] stays at amount/2 (STALE).
    _fundInstantWithdraws(); // borrower/CDO provides liquidity, collectInstantWithdrawFunds runs
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(creditVault.instantWithdrawsRequests(attacker), 0);
    assertEq(
        creditVault.instantWithdrawsRequestsByEpoch(attacker, creditVault.epochNumber()),
        amount / 2 // stale basis survives the "freed" claim
    );

    // 3. Attacker re-requests an instant withdraw in the SAME epoch number.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(amount / 4, address(AAtranche));
    // by-epoch now = 3*amount/4 while aggregate = amount/4.

    // 4. Borrower defaults; manager/CDO finalizes recovery for epoch N.
    _defaultAndFinalizeRecovery(); // _handleBorrowerDefault -> finalizeDefaultRecovery
    assertTrue(creditVault.defaultInstantWithdrawsFinalized());

    // 5a. Attacker's claim reverts: _claimDefaultedInstantWithdrawRequest computes
    //     claimBasis = 3*amount/4 > instantWithdrawsRequests = amount/4 -> underflow.
    vm.prank(attacker);
    vm.expectRevert();
    cdoEpoch.claimInstantWithdrawRequest();

    // 5b. instantWithdrawClaimsByEpoch[N] also inflated defaultPendingClaimBasis(),
    //     so defaultRecoveryPrice was diluted by the phantom amount/2, stranding
    //     that reserve share for every other defaulted receipt holder.
}
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
