### Title
Loss-adjusted withdraw receipts are paid at par after a subsequent `requestWithdraw` overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` maps a user's loss-adjusted (haircutted) withdraw receipt to a single epoch marker, `lastWithdrawRequest[_user]`. When a `stopEpochWithDuration`-style loss funds pending receipts only partially, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and transfers only the reduced amount. If the user then makes a new `requestWithdraw` in a later epoch, `lastWithdrawRequest[_user]` is overwritten, `_claimLossAdjustedWithdrawRequest` can no longer find the haircut, and `_claimFundedWithdrawRequest` pays the aggregate `withdrawsRequests[_user]` — including the haircutted receipt — at par. The vault only holds the reduced amount for that receipt, so the payout is funded by other claimants' reserves.

### Finding Description
The claim dispatch in `claimWithdrawRequest` is: [1](#0-0) 

`_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]`: [2](#0-1) 

On a loss stop, `collectWithdrawFunds` funds only `_amount < pendingBasis` and records the haircut keyed by the *strategy* epoch: [3](#0-2) 

But `requestWithdraw` unconditionally rewrites `lastWithdrawRequest[_user] = currentEpoch` and accumulates into the aggregate `withdrawsRequests[_user]`: [4](#0-3) 

The NatSpec explicitly blesses multiple outstanding receipts: "if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests" (lines 323–324). So the sequence is reachable:

1. Epoch N: attacker (any KYC'd lender / tranche holder) calls `requestWithdraw` via the CDO. `lastWithdrawRequest[attacker] = N`, `withdrawsRequests` = P.
2. `stopEpoch` realizes a loss; `collectWithdrawFunds(L < pendingBasis)` sets `lossRecoveryPriceByEpoch[N] = L*RECOVERY_FULL/pendingBasis` and pulls only L. The vault now holds L for all epoch-N receipts.
3. Buffer: attacker calls `requestWithdraw` again (any nonzero amount). `lastWithdrawRequest[attacker] = N+1`; aggregate grows.
4. Epoch N+1 stops fully funded.
5. `claimWithdrawRequest`: `lossRecoveryPriceByEpoch[N+1] == 0` → loss path returns 0 without clearing epoch N's `withdrawsRequestsByEpoch` share. `_claimFundedWithdrawRequest` sees `epochNumber (N+2) > lastWithdrawRequest (N+1)`, and pays `withdrawsRequests[attacker]` = P + new receipt **at par** via `_transferFundedClaim`.

The haircutted epoch-N receipt is paid at 100% while only `L * (attacker share)` was funded — the excess comes directly out of other epoch-N claimants' earmarked underlyings. The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not loss-adjusted pools.

### Impact Explanation
Broken invariant: loss waterfall / one-receipt-one-payout. Each epoch-N receipt is backed only by `lossRecoveryPrice * basis`; paying one at par leaves a shortfall of `P * (1 - lossRecoveryPrice/RECOVERY_FULL)` absorbed by remaining claimants, who then find the vault underfunded (insolvency / permanent freezing of the tail claimant's payout). The attacker steals `P * (1 - recoveryPrice)` with only principal at risk. Under a 50% loss recovery and 1000 USDC receipt, the attacker extracts ~500 USDC belonging to other users.

### Likelihood Explanation
Requires a realized (non-default) loss epoch — a supported, non-emergency code path (`collectWithdrawFunds` partial funding, `lossRecoveryPriceByEpoch`, `previewLossAdjustedWithdrawFunds` all exist precisely for this). After that, the attacker only needs two ordinary `requestWithdraw` calls across two epochs, both unprivileged. No privileged actor misbehavior is required; sequencing is entirely around honest `stopEpoch`/`collectWithdrawFunds` calls. One caveat: the full top of `requestWithdraw` was not inspected, so if an unseen guard reverts when a loss-adjusted receipt is pending, likelihood drops — however the documented "claim both requests" behavior and the absence of any per-epoch loss marker besides `lastWithdrawRequest` make the overwrite path the intended one.

### Recommendation
Track the loss-adjusted claim per epoch like the default path does: iterate or store the epoch of each pending receipt (e.g., reuse `withdrawsRequestsByEpoch` with a `lossRecoveryPriceByEpoch` lookup per epoch rather than keying off `lastWithdrawRequest`), or revert in `requestWithdraw` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[msg.sender]] != 0` until the haircutted receipt is claimed.

### Proof of Concept
Foundry fork PoC sketch:

```solidity
function testLossReceiptPaidAtPar() public {
    // epoch N running, attacker + victim both hold pending receipts of P each
    _requestWithdrawWithUser(attacker, P);
    _requestWithdrawWithUser(victim,   P);
    // borrower funds only half at stopEpochWithDuration loss
    // -> collectWithdrawFunds(L = P) with pendingBasis = 2P, lossRecoveryPriceByEpoch[N] = RECOVERY_FULL/2
    _stopEpochWithLoss(L);

    // buffer: attacker files a second request (unclaimed receipts allowed per NatSpec)
    _requestWithdrawWithUser(attacker, 1);
    _startEpoch(); _stopCurrentEpoch(); // epoch N+1 fully funded

    uint256 pre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    // attacker received P at par + 1, but only P/2 was funded for his epoch-N receipt
    assertEq(underlying.balanceOf(attacker) - pre, P + 1 + epsilon);

    // victim's claim now underfunded / reverts or pays less than P/2
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest(); // receives < P/2
}
```

Fix verification: after the change, the attacker's claim must return `P * lossRecoveryPrice / RECOVERY_FULL` and the victim's full `P/2` remains available.

  function claimWithdrawRequest(address _user) external returns (uint256 amount) {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized) {
      // Post-default requests are already priced after the haircut and backed by the reserve,
      // so they must not fall through to the defaulted-epoch receipt logic.
      amount = _claimPostDefaultWithdrawRequest(_user);
      if (amount != 0) return amount;
      // Only receipts created in the defaulted epoch are haircutted here; old fulfilled
      // receipts are handled below at par if they were already funded before default.
      amount = _claimDefaultedWithdrawRequest(_user);
    }
    amount += _claimLossAdjustedWithdrawRequest(_user);
    return amount + _claimFundedWithdrawRequest(_user);
  }

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
