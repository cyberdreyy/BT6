### Title
Already-claimed instant-withdraw receipts keep inflating `defaultPendingClaimBasis`, diluting `defaultRecoveryPrice` and stranding recovery funds — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Royal exploit inflated a claim-basis ledger through a path that did not move real funds, then a second contract paid out pro-rata on the phantom balance. The same bug class exists in `IdleCreditVault`: the funded-claim path in `claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch ledger `instantWithdrawsRequestsByEpoch[_user][epoch]` nor the epoch total `instantWithdrawClaimsByEpoch[epoch]`. Those per-epoch counters are exactly what `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest()` read after a hard default, so already-paid receipts are counted again as live claim basis.

### Finding Description
In `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) the funded path does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It does **not** touch `instantWithdrawsRequestsByEpoch[_user][epochNumber]` or decrement `instantWithdrawClaimsByEpoch[epochNumber]`, even though both were incremented in `requestInstantWithdraw` (IdleCreditVault.sol:366-374) and even though `collectInstantWithdrawFunds` (IdleCreditVault.sol:398-403) decrements `pendingInstantWithdraws`. The per-epoch ledgers therefore permanently retain basis for receipts that were fully paid.

That stale basis is read in two places after a default:

- `defaultPendingClaimBasis()` (IdleCreditVault.sol:644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` — including already-claimed amounts — to the recovery denominator whenever `pendingInstantWithdraws != 0` at finalization.
- `_claimDefaultedInstantWithdrawRequest()` (IdleCreditVault.sol:842-856) reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and computes `instantWithdrawsRequests[_user] -= claimBasis`. For a user who already claimed, `instantWithdrawsRequests[_user] == 0 < claimBasis`, so the subtraction underflows and `claimInstantWithdrawRequest` permanently reverts for them, blocking even legitimate residual claims.

Attack sequence (instant-withdraw mode, epoch N running):

1. Attacker (a KYC'd lender holding tranche tokens) calls `requestInstantWithdraw` → `instantWithdrawsRequestsByEpoch[attacker][N] += A`, `instantWithdrawClaimsByEpoch[N] += A`.
2. `collectInstantWithdrawFunds` funds the request; attacker calls `claimInstantWithdrawRequest` and is paid in full. Per-epoch entries still equal `A`.
3. Borrower fails to repay at `stopEpoch` → `_handleBorrowerDefault`. `epochNumber` remains `N`.
4. Manager calls `finalizeDefault` → `finalizeDefaultRecovery` computes `recoveryPrice = reserveAmount * 1e18 / totalBasis` where `totalBasis` includes the phantom `A` via `instantWithdrawClaimsByEpoch[N]` (provided at least one other instant receipt stays unfunded, i.e. `pendingInstantWithdraws != 0`, which also sets `defaultInstantWithdrawsFinalized = true`).

### Impact Explanation
`defaultRecoveryPrice` is understated by the factor `realBasis / (realBasis + phantomBasis)`. Every defaulted pending receipt and all active AA/BB LPs (via the `activeFinalNAV` rebalance at IdleCreditVault.sol:699-705) are paid at the diluted price, while the excess recovered funds remain locked in `defaultRecoveryReserve` — claimable by no user and removable only via owner `transferToken` (IdleCreditVault.sol:963-965). Quantified loss: honest claimants lose `phantom / (real + phantom)` of their recovery; with a large claimed instant withdrawal relative to remaining basis this approaches total forfeiture of the reserve for other users. Additionally, every user who claimed an instant receipt in the defaulted epoch is permanently unable to call `claimInstantWithdrawRequest` (underflow revert), freezing any residual claims.

### Likelihood Explanation
Requires: instant-withdraw mode enabled (manager flag, not attacker-controlled but a supported configuration), at least one funded+claimed instant receipt in the epoch that defaults, and one unfunded instant receipt at finalization. All are normal protocol states during a credit event — the default scenario this code path exists for. No privileged misbehavior is needed; the attacker only uses `requestInstantWithdraw`/`claimInstantWithdrawRequest` as an ordinary lender. The missing per-epoch cleanup also means the inflated `instantWithdrawClaimsByEpoch` can never be corrected, since nothing else decrements it for funded claims.

### Recommendation
In `claimInstantWithdrawRequest`, after computing `amount`, clear the user's per-epoch basis and decrement the epoch total:

```solidity
uint256 currentEpochBasis = instantWithdrawsRequestsByEpoch[_user][epochNumber];
// or clear all epochs' entries for the user; at minimum:
instantWithdrawsRequestsByEpoch[_user][epochNumber] -= /* claimed portion */;
instantWithdrawClaimsByEpoch[epochNumber] -= /* claimed portion */;
```

Concretely, mirror the accounting in `_claimDefaultedInstantWithdrawRequest`: deduct the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` whenever a funded claim is paid, so only genuinely unfunded receipts remain in the default-time claim basis.

### Proof of Concept
Foundry fork/standalone test sketch (against the repo's existing `IdleCreditVault.t.sol` harness):

```solidity
function testClaimedInstantReceiptInflatesDefaultBasis() external {
    // manager enables instant withdraws
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, 0, false);

    address attacker = makeAddr("attacker");
    address victimInstant = makeAddr("victim-instant");
    uint256 amount = 10_000 * ONE_SCALE;

    _depositWithUser(attacker, amount, true);
    _depositWithUser(victimInstant, amount, true);
    _startEpochAndCheckPrices(0);
    uint256 epoch = strategy.epochNumber();

    // attacker requests instant withdraw and gets funded
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(amount / 2, address(AAtranche)); // per harness API
    // victim requests too but is only partially funded
    vm.prank(victimInstant);
    cdoEpoch.requestInstantWithdraw(amount / 2, address(AAtranche));

    // manager funds partially via getInstantWithdrawFunds / collectInstantWithdrawFunds
    // ...fund only attacker's receipt...
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest(); // paid in full

    // stale basis still present
    assertEq(
        strategy.instantWithdrawsRequestsByEpoch(attacker, epoch),
        amount / 2,
        "per-epoch instant basis not cleared on funded claim"
    );
    assertGt(
        strategy.instantWithdrawClaimsByEpoch(epoch),
        strategy.pendingInstantWithdraws(),
        "epoch claim total exceeds unfunded remainder"
    );

    // borrower defaults; manager finalizes
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _checkDefault();

    uint256 basis = strategy.defaultPendingClaimBasis();
    // basis includes attacker's already-paid amount/2 -> recoveryPrice diluted
    // attacker claimInstantWithdrawRequest now permanently reverts (underflow)
    vm.expectRevert();
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Expected: `instantWithdrawClaimsByEpoch[epoch]` retains the paid receipt, `defaultPendingClaimBasis()` overstates pending claims, `defaultRecoveryPrice` is diluted, recovery funds strand in `defaultRecoveryReserve`, and the attacker's (and any claimed user's) `claimInstantWithdrawRequest` reverts forever.
