### Title
Queued withdrawals become permanently locked if instant withdrawals are disabled before `processWithdrawalClaims` clears `pendingClaims` - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The FrankenDAO finding shows tokens can stay locked because a stale "active" state is only removed by a separate `clear()` call. The closest idle-tranches analog is worse: in `IdleCDOEpochQueue`, once `processWithdrawRequests` marks an epoch as instant (`isEpochInstant[_epoch] = true`) and sets `pendingClaims = true`, the only way to clear that flag is `processWithdrawalClaims`, which routes to `IdleCDOEpochVariant.claimInstantWithdrawRequest()`. That claim reverts whenever `allowInstantWithdraw` is false, so if instant withdrawals are disabled (or the instant claim otherwise reverts) before the flag is cleared, `pendingClaims` can never be reset. All queued users' tranche tokens and underlyings are then frozen permanently, and no future epoch's withdrawals can ever be processed.

### Finding Description
`processWithdrawRequests` snapshots whether the epoch settled as instant via the delta in `instantWithdrawsRequests` and sets `pendingClaims = true` [1](#0-0) . `pendingClaims` is only reset inside `processWithdrawalClaims`, and only after a successful `claimInstantWithdrawRequest()` / `claimWithdrawRequest()` call [2](#0-1) . While it is set, `processWithdrawRequests` reverts [3](#0-2)  and `claimWithdrawRequest` reverts because `epochPendingClaims[_epoch] != 0` [4](#0-3) .

The instant-claim path is gated by a *current-state* flag: `claimInstantWithdrawRequest` reverts with `NotAllowed` when `allowInstantWithdraw` is false at claim time [5](#0-4) . Nothing ties that flag check to the historical `isEpochInstant[_epoch]` classification, and `deleteWithdrawRequest` is also blocked once `epochWithdrawPrice[_epoch]` is set [6](#0-5) . So a stale `isEpochInstant`/`pendingClaims` combination has no clearing path — exactly the FrankenDAO bug class (state that should be clearable but locks funds until an explicit cleanup call), except here the cleanup call can become permanently impossible.

### Impact Explanation
Permanent freezing of funds: every user with a `userWithdrawalsEpochs` balance for the stuck epoch can never claim (their tranche tokens are held by the queue, underlying sits claimable in `IdleCreditVault` but unreachable). Additionally `pendingClaims` permanently bricks `processWithdrawRequests`, so the entire withdrawal queue is dead for all subsequent epochs — a protocol-wide freeze, not just one user. Loss is bounded by total queued tranche value plus all future withdrawals through that queue.

### Likelihood Explanation
Requires the honest manager/owner to call `setInstantWithdrawParams(..., allowInstantWithdraw = false)` (or upgrade) while an instant-classified epoch has `epochPendingClaims > 0`. There is no guard preventing disabling instant withdrawals while instant receipts are outstanding, and toggling the flag is a legitimate operational action (tests show it being enabled mid-lifecycle). An unprivileged user only needs an ordinary queued withdrawal in that epoch to be affected; no attacker action is required for the freeze to occur.

### Recommendation
In `processWithdrawalClaims`, fall back to `claimWithdrawRequest()` when `claimInstantWithdrawRequest()` is unavailable, or decouple the claim path from the live `allowInstantWithdraw` flag (check `isEpochInstant[_epoch]` semantics inside the vault's `claimInstantWithdrawRequest` instead of the CDO flag). Alternatively, allow `deleteWithdrawRequest`/force-clearing of `epochPendingClaims` and `pendingClaims` when the underlying claim reverts, mirroring FrankenDAO's `clear()`.

### Proof of Concept
```solidity
// Foundry, standard epoch variant with instant withdrawals enabled
function testPendingClaimsPermanentlyStuck() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);              // epoch #1 buffer

    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, true); // enable instant withdraws

    address user = makeAddr('user');
    uint256 tranches = _depositWithUser(user, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();                        // epoch #1 running

    _requestWithdrawWithUser(user, tranches);     // queue requestWithdraw

    _stopCurrentEpochWithApr(1e18);               // instant-withdraw settlement, epoch #2
    uint256 epoch = strategy.epochNumber();

    vm.prank(manager);
    queue.processWithdrawRequests();              // isEpochInstant[epoch]=true, pendingClaims=true

    // Honest manager disables instant withdrawals before claims are processed
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    // Clearing call now always reverts: claimInstantWithdrawRequest checks allowInstantWithdraw
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    queue.processWithdrawalClaims(epoch);

    // Users permanently locked: epochPendingClaims[epoch] != 0
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(user);
    queue.claimWithdrawRequest(epoch);

    // Withdrawal queue bricked forever
    assertTrue(queue.pendingClaims());
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    vm.prank(manager);
    queue.processWithdrawRequests();
}
```

Uncertainty I could not fully resolve within available context: the exact revert condition inside `IdleCreditVault.claimInstantWithdrawRequest` relative to epoch-running state (a variant of this bug may also trigger if the epoch ends before `processWithdrawalClaims` is called, making instant claims time-impossible even while the flag stays enabled). Both paths converge on the same root cause — `pendingClaims`/`epochPendingClaims`/`isEpochInstant` is only cleared by a call that can become permanently reverted.
