### Title
LDAP CreateSession accepts empty password causing unauthenticated ("anonymous simple") bind to be treated as successful authentication - ([File: core/sessions/ldapauth/ldap.go])

### Summary
`ldapAuthenticator.CreateSession` in `core/sessions/ldapauth/ldap.go` forwards the caller-supplied `SessionRequest.Password` directly into `conn.Bind(searchBaseDN, sr.Password)` with no check that the password is non-empty. Per RFC 4513 §5.1.2, an LDAP simple bind with a valid DN and a zero-length password is defined as an "unauthenticated bind," which most directory servers accept as successful (`err == nil`) without validating any credential at all. Because the code treats a nil error from `conn.Bind` as a fully authenticated login, an attacker who knows (or guesses) a valid target username/email can submit an empty password to `POST /sessions` and be issued a valid session.

### Finding Description
`CreateSession` builds the bind DN from the attacker-supplied `sr.Email` and calls: [1](#0-0) 

There is no check anywhere in this function, in `sessions.SessionRequest`, or upstream in the HTTP handler layer that rejects an empty or whitespace-only `Password` before it reaches `conn.Bind`. If the configured directory implements the LDAP standard "unauthenticated bind" behavior (RFC 4513), `conn.Bind(dn, "")` returns success for any syntactically valid DN, regardless of whether the caller knows the real password. The code interprets this as "user and credentials are present in LDAP directory" and proceeds to call `l.FindUser` to resolve the user's role, then creates a persisted `ldap_sessions` row and returns a valid session ID to the caller: [2](#0-1) 

Because role assignment (`FindUser`/group lookup) is independent of whether the bind was a real credential check, an attacker only needs to know a valid target email (e.g., a known/guessable admin account name) to obtain a session with that user's role — including admin — via `POST /sessions` with an empty `password` field. This is the entrypoint documented at `AuthenticationProvider.CreateSession` in `core/sessions/authentication.go`: [3](#0-2) 

Note: the local (non-LDAP) `orm.CreateSession` implementation is not vulnerable, since it does an explicit `utils.CheckPasswordHash(sr.Password, ...)` comparison: [4](#0-3) 

This confirms that the local auth path guards against empty passwords by design (a hash comparison against an empty string will fail), but the LDAP path relies entirely on the directory server's bind semantics and does not perform an equivalent pre-check, so it inherits the RFC-4513 unauthenticated-bind pitfall.

### Impact Explanation
If the deployment uses `LDAPAuth` (a supported, documented `AuthenticationProviderName`) and the backing directory follows standard LDAP unauthenticated-bind semantics, an unauthenticated network attacker who only knows a valid user's email (often discoverable, e.g. common admin naming conventions or from other leaked info) can log in as that user without any password, including as an admin. This matches the "Critical - node takeover" impact class: full admin session hijack enabling API token creation, key export, and job/transaction control.

### Likelihood Explanation
Preconditions: the node must be configured with `LDAPAuth` as its `AuthenticationProviderName`, and the target LDAP/AD server must implement or not explicitly reject unauthenticated (zero-length password) simple binds — which is the RFC-4513 default behavior for many directory implementations unless explicitly disabled by the LDAP server operator. Given those preconditions, exploitation requires no credentials at all beyond a valid email string and is trivially repeatable (a single POST /sessions request). The severity is fully contingent on the LDAP auth provider being enabled and the directory server's bind policy; it does not affect deployments using `LocalAuth` or `OIDCAuth`.

### Recommendation
In `ldapAuthenticator.CreateSession` (and `TestPassword`), explicitly reject empty/whitespace-only passwords before calling `conn.Bind`, e.g.:
```go
if strings.TrimSpace(sr.Password) == "" {
    return "", errors.New("password cannot be empty")
}
```
Apply the same guard in `TestPassword` (`core/sessions/ldapauth/ldap.go` line 504-514) since it has an identical pattern. Additionally, consider validating this invariant centrally in the `sessions.SessionRequest` construction or in the HTTP session controller so all `AuthenticationProvider` implementations are protected uniformly.

### Proof of Concept
Table-based unit test in `core/sessions/ldapauth/ldap_test.go` (mirroring existing test structure using `mocks.NewLDAPClient`/`mocks.NewLDAPConn`):
1. Set up `ldapAuthProvider` via `setupAuthenticationProvider`.
2. Mock `mockLdapConnProvider.On("Bind", mock.Anything, "").Return(nil)` to simulate an LDAP server accepting an unauthenticated bind for an empty password.
3. Mock `FindUser`/search calls so a valid user+role is resolved for `cltest.APIEmailAdmin`.
4. Call `ldapAuthProvider.CreateSession(ctx, sessions.SessionRequest{Email: cltest.APIEmailAdmin, Password: ""})` and similarly with `" "` (whitespace).
5. Expected (post-fix) assertion: `require.Error(t, err)` and no session ID returned, with the mock `Bind` call for empty/space password never asserted as reached (or an explicit pre-check error message).
6. Current (pre-fix) behavior: the call succeeds (`err == nil`), returning a valid session ID and inserting a row into `ldap_sessions`, demonstrating the vulnerability.
