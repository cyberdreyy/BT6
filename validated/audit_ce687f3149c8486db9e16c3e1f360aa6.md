### Title
Deactivated LDAP/OIDC users retain valid sessions and API tokens until the next periodic upstream sync - (File: `core/sessions/ldapauth/sync.go`, `core/sessions/ldapauth/ldap.go`, `core/sessions/oidcauth/oidc.go`)

### Summary
The external report describes a class of bug where removing/disabling an entity from an "approved" set does not immediately invalidate data/results already derived from it — stale, invalid state continues to be trusted until an out-of-band re-sync happens. The same pattern exists in the chainlink node's LDAP and OIDC authentication providers: once a user is authenticated and a local `ldap_sessions`/`ldap_user_api_tokens` (or `oidc_sessions`) row is created, that session/token is treated as valid purely from local state and is **not re-validated against the upstream identity provider on each request**. Upstream deactivation only takes effect once the periodic `LDAPServerStateSyncer.Work`/OIDC reaper sync runs.

### Finding Description
For session-cookie and API-token authentication, the local ORM methods trust the locally cached row without contacting the upstream server: [1](#0-0) 

This function only checks the local `ldap_user_api_tokens` table for expiry (`created_at + duration >= now()`), never re-validating the user's active/group-membership status upstream. The same applies to `AuthorizedUserWithSession` in the OIDC provider, which reads `oidc_sessions` purely from the local DB: [2](#0-1) 

The package-level doc comment for the LDAP authenticator explicitly documents this design: "Changes to the upstream identity server will propagate through and update local tables (web sessions, API tokens) by either removing the entries or updating the roles. This sync happens for every auth endpoint hit, and via the defined sync interval." [3](#0-2) 

The actual purge/downgrade of stale sessions/tokens for users removed from upstream is only performed by the periodic sync job: [4](#0-3) [5](#0-4) 

This mirrors the oracle bug's root cause precisely: the "approved" check (`FindUser`, which does call `validateUsersActive` live) is only exercised on login/`FindUser` calls, but the higher-frequency, request-path validators (`AuthorizedUserWithSession`, `FindUserByAPIToken`) skip the live approval check and instead trust cached/stale local state — comparable to `_getOracleData` returning stale (or invalid) `optimisedOracles[i]` output because the up-to-date approval state hasn't propagated yet.

### Impact Explanation
If an administrator removes a user from the upstream LDAP/OIDC group (revoking access, e.g., due to an incident or off-boarding), that user's already-issued session cookie and/or API token continues to authenticate successfully against `core/web/auth/auth.go`'s `AuthenticateBySession`/`AuthenticateByToken` methods until the next `UpstreamSyncInterval` tick. Depending on operator configuration, this could allow continued privileged API access (job creation, key management, run triggering) for a window after revocation was believed to take effect immediately. This is a role/authentication bypass in the sense that revocation is not enforced at the point of use.

### Likelihood Explanation
Requires (a) LDAP or OIDC auth to be configured (not the default local auth), and (b) an admin believing a session/token is dead immediately upon upstream deactivation, when in fact it persists until `UpstreamSyncInterval` elapses (or `UpstreamSyncRateLimit` further delays checks). This is a real but narrower condition than default deployments, giving it lower likelihood, similar to the original report's "rare occurrence, but possible" framing.

### Recommendation
Re-validate session/API-token holders' active status against the upstream directory on the request path (or shorten/bound the enforced staleness window), rather than relying solely on the periodic reaper/sync job to purge revoked users. At minimum, document and default `UpstreamSyncInterval` to a safe minimum, and consider validating active status inline in `AuthorizedUserWithSession`/`FindUserByAPIToken` similar to how `FindUser` calls `validateUsersActive`.

### Proof of Concept
1. Configure chainlink node with LDAP authentication and a non-zero `UpstreamSyncInterval`.
2. Authenticate a user via `AuthenticateBySession` (session created and role cached in `ldap_sessions`).
3. Remove/deactivate that user in the upstream LDAP directory (or from group membership).
4. Before the next `LDAPServerStateSyncer.Work` tick, continue calling authenticated endpoints with the existing session cookie/API token — `AuthorizedUserWithSession`/`FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` (lines 204-236) return success because they never re-check upstream status, only local expiry.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

func (oi *oidcAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (clsessions.User, error) {
	if len(sessionID) == 0 {
		return clsessions.User{}, errors.New("session ID cannot be empty")
	}
	var foundUser clsessions.User
	err := sqlutil.TransactDataSource(ctx, oi.ds, nil, func(tx sqlutil.DataSource) error {
		// Query the oidc_sessions table for given session ID, user role and email are saved after the id claims is provided and validated
		var foundSession struct {
			UserEmail string
			UserRole  clsessions.UserRole
			Valid     bool
		}
		if err := tx.GetContext(ctx, &foundSession,
			"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM oidc_sessions WHERE id = $1",
			sessionID, oi.config.SessionTimeout().Duration(),
		); err != nil {
			if errors.Is(err, sql.ErrNoRows) {
				return clsessions.ErrUserSessionExpired
			}
			return err
		}
		if !foundSession.Valid {
			// Sessions expired, purge
			return clsessions.ErrUserSessionExpired
		}
		foundUser = clsessions.User{
			Email: foundSession.UserEmail,
			Role:  foundSession.UserRole,
		}
		return nil
	})
	if err != nil {
		if errors.Is(err, clsessions.ErrUserSessionExpired) {
			if _, execErr := oi.ds.ExecContext(ctx, "DELETE FROM oidc_sessions WHERE id = $1", sessionID); execErr != nil {
				oi.lggr.Errorf("error purging stale OIDC session: %v", execErr)
			}
		}
		return clsessions.User{}, err
	}
	return foundUser, nil
}
