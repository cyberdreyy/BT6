### Title
Permissionless APR manipulation before CDO whitelisting — `setApr`/`setAprs` skip the caller check while `idleCDO` is unset - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault.setApr` skips its only access check when `idleCDO == address(0)`, i.e., between strategy `initialize` and `setWhitelistedCDO`. During that window any EOA can call `setApr`/`setAprs`/`setAprsWithBuffer` and overwrite `lastApr`/`unscaledApr` up to the `DEFAULT_MAX_APR` cap (2000%), permanently corrupting the vault's interest accounting until the manager notices and overwrites it — with no event and no "initialized" safeguard. This mirrors the reported bug class: a state-mutating function callable before initialization/wiring completes, producing wrong accounting that cannot be cleanly undone once consumers rely on it.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol:225-235`:

```solidity
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`idleCDO` is only assigned by `setWhitelistedCDO` (line 954-957), which is `onlyOwner` and is *not* called inside `initialize`. Therefore the permissionless window is not just "during deployment" — it lasts until the owner wires the CDO. During the entire window:

- `setApr(uint256)` — anyone sets `lastApr` to any value up to `maxApr` (`DEFAULT_MAX_APR = 20e18`, i.e. 2000%/yr scaled).
- `setAprs(uint256,uint256)` (line 206-210) — anyone sets both `unscaledApr` and `lastApr`.
- `setAprsWithBuffer` (line 217-220) — anyone sets `unscaledApr` plus a scaled `lastApr` of their choosing.

`lastApr`/`unscaledApr` drive `expectedEpochInterest`, the borrower repayment amount at `stopEpoch`, the `apr0Users` flow (`unscaledApr == 0` routing in `requestWithdraw`, line 285), and `prepareStopEpochWithApr0` (which *reverts* if `apr0TotalPrincipal != 0 && unscaledApr != 0`, line 506-508). The factory path (`IdleCreditVaultFactory._configureCreditVault`, lines 304-306) calls `setAprs` then `setWhitelistedCDO` in the same transaction, but nothing in the strategy enforces that ordering — a vault deployed or migrated outside the factory, or any gap between `initialize` and `setWhitelistedCDO`, exposes the window.

### Impact Explanation
Concrete attacker path (attacker = any EOA / KYC'd lender):

1. Strategy proxy is deployed and `initialize` runs; owner has not yet called `setWhitelistedCDO` (e.g., manual deployment, ownership migration, or a re-setup of `idleCDO`).
2. Attacker calls `setAprs(20e18, 20e18)` (or `setApr(20e18)`), setting `unscaledApr = lastApr = 2000%`.
3. CDO is whitelisted and `startEpoch` runs with the poisoned APR. `expectedEpochInterest` is computed from `lastApr`; at `stopEpoch` the borrower owes ~20x principal in interest for a full-year epoch (proportionally for shorter epochs). If the borrower cannot pay, the epoch cannot close normally → the pool is pushed toward `stopEpochWithDuration` loss/default; if the borrower does pay, attacker-LPs (or the AA tranche per `trancheAPRSplitRatio`) capture inflated interest.
4. Alternatively, with `unscaledApr` poisoned, `prepareStopEpochWithApr0` reverts `NotAllowed()` for any vault holding APR0 principal (line 506-508), freezing `stopEpoch` and the pending withdrawals behind it until a privileged fix.

Unlike the Scroll report (irreversible because messages can't be removed), here a later `setAprs` by the manager overwrites the value — but only if detected before an epoch is started/stopped on the corrupted value, and there is no event emitted or initialization gate to flag it. The loss is bounded by `maxApr` (20e18), which is still a >20x overstatement of a typical credit APR.

### Likelihood Explanation
Medium-low but non-trivial. The factory deploy path is atomic, so the window only exists for non-factory deployments, manual proxy wiring, or any operational gap where `initialize`/`setWhitelistedCDO` are separate transactions — exactly the "setup" gap the code comment acknowledges. No privileged action is needed by the attacker; the only mitigation is operational ordering by the honest owner. Once `idleCDO` is set, the functions are properly gated (`msg.sender == idleCDO || msg.sender == manager`).

### Recommendation
Guard `setApr`/`setAprs`/`setAprsWithBuffer` with an explicit "not yet wired" state rather than skipping the check when `idleCDO == address(0)`. Options:

- Require `msg.sender == owner()` (or `manager`) when `idleCDO == address(0)`:
  ```solidity
  if (_cdo == address(0)) {
    if (msg.sender != owner() && msg.sender != manager) revert NotAllowed();
  } else if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
  ```
- Or set `idleCDO` inside `initialize` (it is immutable per vault) so the permissionless window cannot exist.
- Emit an event on `lastApr`/`unscaledApr` changes so off-chain monitoring can catch a poisoned setup.

### Proof of Concept
Foundry fork-style test against `contracts/strategies/idle/IdleCreditVault.sol`:

```solidity
function test_PermissionlessAprBeforeWhitelisting() public {
    // Deploy proxy + initialize, mimicking a manual deployment where
    // setWhitelistedCDO is a separate later owner transaction.
    IdleCreditVault strat = IdleCreditVault(
        address(new TransparentUpgradeableProxy(
            address(new IdleCreditVault()),
            proxyAdmin,
            abi.encodeWithSelector(
                IdleCreditVault.initialize.selector,
                address(underlying), owner, manager, borrower, "Borrower", 5e16
            )
        ))
    );

    // Attacker EOA (no role) front-runs owner's setWhitelistedCDO
    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    strat.setAprs(20e18, 20e18);   // succeeds: idleCDO == address(0)

    assertEq(strat.unscaledApr(), 20e18);
    assertEq(strat.getApr(), 20e18); // 2000% vs intended ~5%

    // Owner wires the CDO; poisoned APR persists and drives expectedEpochInterest
    vm.prank(owner);
    strat.setWhitelistedCDO(address(cdo));
    // startEpoch -> stopEpoch now charges the borrower ~20x principal interest,
    // or prepareStopEpochWithApr0 reverts for vaults holding apr0 principal.
}
```

Key PoC assertions: `setAprs` from an EOA succeeds while `idleCDO == address(0)`; after `setWhitelistedCDO`, the same call reverts `NotAllowed()`, confirming the unguarded pre-wiring window is the root cause.
