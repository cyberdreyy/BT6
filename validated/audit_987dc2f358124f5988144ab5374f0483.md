### Title
Symlink-target-not-validated in tar+zstd extractor allows path traversal write on retry - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`extractor.Extract` validates that a tar entry's own *path* stays within `e.dir`, but never validates the *target* (`hdr.Linkname`) of symlink entries before calling `os.Symlink`. A malicious artifact archive can plant a symlink at `e.dir/foo` pointing outside the extraction root; a subsequent extraction of a regular file named `foo` then calls `os.Create(path)`, which follows the pre-existing symlink and writes attacker-controlled content outside `e.dir`.

### Finding Description
In `Extract`, only the destination path derived from `hdr.Name` is checked against the chroot prefix: [1](#0-0) 
Symlink entries are deferred and later created with `os.Symlink(hdr.Linkname, path)` with no validation of `hdr.Linkname` at all: [2](#0-1) [3](#0-2) 
Regular files are written with a plain `os.Create(path)`, which follows symlinks rather than rejecting them: [4](#0-3) 

This means:
1. Attempt 1: an archive entry `foo` with `typeflag=symlink` and `Linkname=/etc/foo` (or any absolute/`../`-relative path) passes the source-path chroot check (since `foo` itself resolves inside `e.dir`), and is created as a real dangling symlink `e.dir/foo -> /etc/foo`.
2. If extraction returns an error afterward (e.g., a later entry in the same stream fails, or the overall command exits non-zero for any reason), `ArtifactDownload.Run` retries by re-invoking the `artifacts-downloader` subprocess against the same `WorkingDir` when `DownloadAttempts > 1`: [5](#0-4) 
3. Attempt 2 re-extracts into the same directory. A regular-file entry named `foo` passes the same path check (its own name is `e.dir/foo`), then `os.Create(path)` follows the existing symlink and writes/truncates the attacker-chosen target path (`/etc/foo`) instead of a file inside `e.dir`.

No cleanup of `e.dir` occurs between retries in this code path, and there is no `os.Lstat`/`O_NOFOLLOW` guard before `os.Create`, so the dangling symlink from attempt 1 survives into attempt 2.

### Impact Explanation
This allows an attacker who controls artifact content (e.g., a pipeline author uploading a crafted artifact from an earlier stage) to write arbitrary file content to an arbitrary path outside the job's artifact/build root on the machine running the Runner's `artifacts-downloader` helper, provided the process has permission to write there. This breaks the "file operations must stay within intended build/cache/artifact roots" invariant.

### Likelihood Explanation
Requires: (a) the victim job's artifact archive to be attacker-influenced content, and (b) a retry (`DownloadAttempts > 1`, which is a common Runner config `artifact_download_attempts` default >1) actually occurring so `Extract` runs twice against the same `WorkingDir`. Triggering a retry deterministically (e.g., forcing a transient network/extraction error on attempt 1 while still leaving the symlink written) is the main practical hurdle, but not implausible — a truncated/corrupt archive after the symlink entry, or a second decompression error, would cause `Extract` to return non-nil after the symlink was already persisted, triggering the retry loop. This is a real, exploitable logic gap, not purely theoretical, since GitLab's own tar extractors elsewhere in the codebase are known to require symlink-target validation for exactly this reason.

### Recommendation
- Validate `hdr.Linkname` the same way `hdr.Name` is validated: resolve it relative to `path`'s directory (for relative links) and reject any target that resolves outside `e.dir` (and reject absolute Linknames outright).
- Before writing a regular file, `Lstat` the destination path; if it is a symlink (or any non-regular file) left over from a prior partial extraction, remove it before calling `os.Create`, or open with `O_NOFOLLOW`/refuse if it's a symlink.
- Consider clearing/recreating `e.dir` (or a fresh temp subdirectory swapped in atomically) on each retry rather than re-extracting into the same directory that may contain attacker-planted state from a failed prior attempt.

### Proof of Concept
Go unit test in `commands/helpers/archive/tarzstd/tarzstd_extractor_test.go`:
1. Build a tar+zstd stream: header `foo` as symlink to `../outside/target` (or absolute `/tmp/outside_target`), no further entries; call `Extract` once into `tmpDir/dir`. Assert `os.Lstat(filepath.Join(tmpDir, "dir", "foo"))` mode has `ModeSymlink` set and `Linkname` resolves outside `dir`.
2. Build a second tar+zstd stream with a regular file entry `foo` containing marker content `"PWNED"`; call `Extract` a second time into the same `dir`.
3. Assert that the file at the resolved symlink target (`tmpDir/outside/target` or `/tmp/outside_target`) now exists and contains `"PWNED"`, proving escape of `e.dir`.
4. Expected (fixed) behavior: `Extract` should return an error on step 1 (invalid Linkname escaping chroot) or on step 2 refuse to follow the pre-existing symlink, and the outside file must never be created.
