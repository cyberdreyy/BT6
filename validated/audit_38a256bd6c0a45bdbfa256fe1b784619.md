### Title
Vault KV-v2 `dataPath`/`metadataPath` do not sanitize the job-controlled secret path, allowing directory traversal outside the operator-configured mount prefix - (File: helpers/vault/secret_engines/kv_v2/engine.go)

### Summary
`engine.dataPath` and `engine.metadataPath` build the Vault request path with `path.Join(e.path, "data"/"metadata", p)`, where `p` originates from `spec.Secret.Vault.Path`, a field that is expanded from CI/CD variables under the job author's control. Because `path.Join` lexically cleans `..` segments, a value such as `../../otherapp/creds` can cancel out both the `data`/`metadata` literal and the operator-configured `e.path` prefix, letting the resulting Vault key request reach paths outside the intended per-project scope.

### Finding Description
The call chain is: `resolver.Resolve` (helpers/secrets/resolvers/vault/resolver.go) reads `v.secret.Vault` (a `spec.Secret` populated from job-supplied CI/CD variable expansion) and calls `s.GetField(secret, secret)` → `defaultVault.GetField` (helpers/vault/service/vault.go:97) → `getSecretEngine` (constructs the `kv_v2` engine with `engineDetails.EnginePath()`, itself derived from job config) → `engine.Get(secretDetails.SecretPath())` (helpers/vault/secret_engines/kv_v2/engine.go:29) → `e.dataPath(p)` (line 55-57):

```go
func (e *engine) dataPath(p string) string {
	return path.Join(e.path, "data", p)
}
```

`path.Join` internally calls `path.Clean`, which lexically resolves `..` segments without regard to a fixed root. If `p` (the job-supplied secret path) contains enough `../` segments, it can consume not only the literal `"data"` component but also the mount/project prefix `e.path` itself, producing a path that points to a sibling location in the shared Vault mount rather than one scoped under `e.path/data/...`. The same issue applies to `metadataPath` used by `Delete`.

No path-containment check exists anywhere in this call chain — `Get`, `Put`, `Delete`, `dataPath`, and `metadataPath` never verify that the resolved path remains prefixed by `e.path`. The only thing standing between a job and cross-tenant secrets is the Vault ACL configured for the runner's authentication token. The threat model given explicitly states this ACL is a mount-wide wildcard (e.g. `secret/data/*`) rather than a per-project exact-path policy — exactly the precondition under which the runner's own path handling is the last line of defense, and it provides none.

### Impact Explanation
Under the stated precondition (wildcard Vault policy for the runner token, per-project isolation relying only on the `path` segment), an unprivileged pipeline author who can influence the variable expanded into the Vault secret's `Path` can construct a value containing `../` sequences that cause `engine.Get`/`engine.dataPath` to resolve to a Vault key outside their own project's designated prefix, resulting in cross-project secret exfiltration through the runner's normal Vault secret-resolution feature. This directly matches the scoped impact: cross-tenant secret access via the runner's Vault integration, without any executor breakout being required.

### Likelihood Explanation
Exploitability is high once the two stated preconditions hold: (1) the job author can control/override the variable used to populate `VaultSecret.Path` (a supported, documented pattern for parameterizing secret paths, e.g. via `CI_VAULT_PATH`-style variables consumed by the `secrets:` keyword), and (2) the Vault token used by the runner is authorized via a broad wildcard policy over the mount rather than a policy scoped to the exact per-project path. Both are realistic operator configurations, especially when Vault paths are meant to be templated per-project without per-path ACLs (relying instead on the runner enforcing the path prefix, which it does not). The exploit requires no special privileges beyond normal pipeline authoring rights (editing `.gitlab-ci.yml` or overriding a project/group CI/CD variable that feeds the templated path).

### Recommendation
After computing `dataPath`/`metadataPath` (and any other engine path builder), verify that the cleaned result remains lexically rooted under `e.path` (e.g., using `filepath.Rel`/prefix comparison after `path.Clean`, or building the path from validated segments rather than joining a raw user-controlled string). Reject or error out the secret resolution if the job-supplied `p` would otherwise cause the request to escape the operator-configured mount prefix. Apply the same containment check to `Put`, `Delete`, and any other secret engine implementation with similar path-joining logic.

```go
func TestDataPathTraversalEscapesMountPrefix(t *testing.T) {
	e := &engine{path: "myapp"}

	got := e.dataPath("../../otherapp/creds")

	// Expected (fixed) behavior: result must remain rooted under "myapp/"
	assert.True(t, strings.HasPrefix(got, "myapp/"),
		"dataPath escaped configured mount prefix: got %q", got)
}

func FuzzDataPathContainment(f *testing.F) {
	f.Add("../../otherapp/creds")
	f.Add("..%2f..%2fotherapp")
	f.Add("/otherapp/creds")
	f.Add("foo\x00../../otherapp")

	e := &engine{path: "myapp"}
	f.Fuzz(func(t *testing.T, p string) {
		got := e.dataPath(p)
		if !strings.HasPrefix(got, "myapp/") && got != "myapp" {
			t.Errorf("dataPath escaped mount prefix for input %q: got %q", p, got)
		}
	})
}
```

```go
func (e *engine) Get(path string) (map[string]interface{}, error) {
	secret, err := e.client.Read(e.dataPath(path))
	if err != nil {
		return nil, fmt.Errorf("reading from Vault: %w", err)
	}

	if secret == nil {
		return nil, nil
	}

	data := secret.Data()
	if data == nil {
		return nil, nil
	}

	if raw, ok := data["data"]; !ok || raw == nil {
		return nil, nil
	}

	result, ok := data["data"].(map[string]interface{})
	if !ok {
		return nil, fmt.Errorf("data for key %s cannot be coerced to 'map[string]any'", path)
	}
	return result, nil
}
```

```go
func (v *defaultVault) GetField(engineDetails Engine, secretDetails Secret) (interface{}, error) {
	engine, err := v.getSecretEngine(engineDetails)
	if err != nil {
		return nil, err
	}

	secret, err := engine.Get(secretDetails.SecretPath())
	if err != nil {
		return nil, fmt.Errorf("reading secret: %w", err)
	}

	field := secretDetails.SecretField()
	for key, data := range secret {
		if key != field {
			continue
		}

		return data, nil
	}

	return nil, nil
}

func (v *defaultVault) getSecretEngine(engineDetails Engine) (vault.SecretEngine, error) {

	if err != nil {
		return nil, fmt.Errorf("requesting SecretEngine factory: %w", err)
	}

	engine := engineFactory(v.client, engineDetails.EnginePath())

	return engine, nil
}
```

```go
func (v *resolver) Resolve() (string, error) {
	if !v.IsSupported() {
		return "", secrets.NewResolvingUnsupportedSecretError(resolverName)
	}

	secret := v.secret.Vault

	url := secret.Server.URL
	namespace := secret.Server.Namespace

	s, err := newVaultService(url, namespace, secret)
	if err != nil {
		return "", classifyError(err)
	}

	data, err := s.GetField(secret, secret)
	if err != nil {
		return "", classifyError(err)
	}

	if data == nil {
		return "", common.ErrSecretNotFound
	}

	return fmt.Sprintf("%v", data), nil
}
```
