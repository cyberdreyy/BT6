### Title
Blocklisting ERC20 (e.g. USDC/USDT) receiver DoS/censors batched redeem/deposit solves - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.requestRedeem`/`requestDeposit` let any ordinary user set an arbitrary `receiver` for their async request [1](#0-0) . When solvers later batch-process requests via `solveRequestsVault`/`solveRequestsDirect`, the per-request token payout on the "solved" (non-refund) path is a plain `safeTransfer`/`safeTransferFrom` with no fallback, executed inside an un-isolated loop over the whole batch [2](#0-1) . If the token is a blocklisting stablecoin (USDC/USDT) and the malicious request's `receiver` is (or becomes) blocked, this single transfer reverts and aborts the entire batch transaction, DoSing every other legitimately co-batched user's request — the same pattern as the referenced Gravity Bridge finding.

### Finding Description
An ordinary user calls `requestRedeem(token, unitsIn, minTokensOut, solverTip, deadline, maxPriceAge, isFixedPrice, receiver)`, which only validates non-zero amounts and generic request params via `_validateRequest`, imposing no restriction that `receiver` be a benign/approved address [3](#0-2) . The attacker sets `receiver` to an address they know is (or will be) blacklisted by the token issuer.

When a solver later calls `solveRequestsVault(token, requests, ...)`, execution flows into `_solveRequestsVault`, which iterates the full `requests` array in a single loop with no try/catch isolation per request [2](#0-1) . For a redeem that is not expired, `_solveRedeemVaultFixedPrice`/`_solveRedeemVaultAutoPrice` perform `token.safeTransfer(request.receiver, request.tokens)` directly — unlike the refund/cancel paths, which explicitly use `_transferWithFallback` (try/fallback-to-requester) precisely to avoid this class of bug [4](#0-3) . The same unguarded pattern exists in `solveRequestsDirect`'s `_solveRequestDirect`, where the solved (non-refund) branch calls plain `safeTransfer`/`safeTransferFrom` to/from `request.receiver` inside a loop over `requests` [5](#0-4) [6](#0-5) .

Because a blocklisting ERC20 reverts on transfer to a blocked address, the single malicious request causes the entire multi-request batch call to revert, denying processing to every other request bundled in the same transaction, and wasting the solver's gas.

### Impact Explanation
Other users' legitimate redeem/deposit requests bundled in the same batch cannot be solved while the poisoned request remains in the batch; their tokens/units stay escrowed in the Provisioner (temporary freeze of funds/yield), and any solver who submits such a batch pays gas for a reverted transaction. This matches an Immunefi Medium severity: temporary freezing of user funds caused by griefing via batch DoS, plus solver/relayer gas griefing, mirroring the cited report's impact.

### Likelihood Explanation
Requires only: (1) a deployed, bounty-listed deposit/redeem token that implements an issuer blocklist (e.g. USDC, USDT — commonly supported stable tokens), and (2) any unprivileged user submitting `requestRedeem`/`requestDeposit` with `receiver` set to an address that is or becomes blocklisted. No guardian/solver/treasury collusion is needed — solvers naturally batch multiple pending requests together via `solveRequestsVault`/`solveRequestsDirect`, and cannot reliably predict blocklist membership (which can change at any time, is issuer-controlled, and off-chain-driven) before including a request in a batch.

### Recommendation
Apply the existing `_transferWithFallback` (try/catch with fallback to `request.user`) pattern to the token-out transfer in `_solveRedeemVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, and to the solved-path transfers in `_solveRequestDirect`, exactly as already done for the refund paths, so a single blocked/failing receiver only fails that individual request instead of reverting the whole batch.

### Proof of Concept
1. Fork mainnet; deploy `MultiDepositorVault` + `ProvisionerV2`, register real USDC as an async-redeem-enabled token in `tokensDetails`.
2. User A deposits and obtains vault units, then calls `requestRedeem(USDC, unitsIn, minTokensOut, 0, deadline, maxPriceAge, true, receiverA)` where `receiverA` is an address you have USDC's blacklister (or a known blacklisted address on the fork) block.
3. User B independently calls `requestRedeem(USDC, unitsIn2, minTokensOut2, 0, deadline, maxPriceAge, true, receiverB)` with a normal `receiverB`.
4. A solver calls `solveRequestsVault(USDC, [requestA, requestB], "", "")`.
5. Assert the whole call reverts (USDC transfer to `receiverA` reverts), and assert `asyncRequestHashes[hash(requestB)]` is still `true` afterward — proving user B's valid redeem could not be processed solely because of A's blocked receiver in the same batch, and the solver's gas was burned.

    function _solveRequestsVault(IERC20 token, RequestV2[] calldata requests) internal {
        // Requirements: vault is not paused in the priceAndFeeCalculator
        require(!PRICE_FEE_CALCULATOR.isVaultPaused(MULTI_DEPOSITOR_VAULT), Aera__PriceAndFeeCalculatorVaultPaused());

        // Interactions: get price age
        uint256 priceAge = block.timestamp - PRICE_FEE_CALCULATOR.getVaultPriceTimestamp(MULTI_DEPOSITOR_VAULT);

        uint256 solverTip;
        RequestV2 calldata request;

        uint256 length = requests.length;
        TokenDetailsV2 memory tokenDetails = tokensDetails[token];
        bool depositsExist;
        for (uint256 i = 0; i < length; i++) {
            request = requests[i];
            if (_isRequestTypeDeposit(request.requestType)) {
                // Requirements: async deposit is enabled
                if (!tokenDetails.asyncDepositEnabled) {
                    // Log async deposit disabled event
                    emit AsyncDepositDisabled(i);
                    continue;
                }

                if (!depositsExist) {
                    depositsExist = true;
                    token.forceApprove(MULTI_DEPOSITOR_VAULT, type(uint256).max);
                }

                if (_isRequestTypeAutoPrice(request.requestType)) {
                    // Requirements + Effects + Interactions: solve auto price deposit
                    solverTip += _solveDepositVaultAutoPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                } else {
                    // Requirements + Effects + Interactions: solve fixed price deposit
                    solverTip += _solveDepositVaultFixedPrice(
                        token, tokenDetails.asyncDepositMultiplier, request, priceAge, i
                    );
                }
            } else {
                // Requirements: async redeem is enabled
                if (!tokenDetails.asyncRedeemEnabled) {
                    // Log async redeem disabled event
                    emit AsyncRedeemDisabled(i);
                    continue;

    function _solveRequestDirect(IERC20 token, RequestV2 calldata request) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        if (_guardInvalidRequestHash(requestHash)) return;

        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;

        bool isDeposit = _isRequestTypeDeposit(request.requestType);

        if (request.deadline >= block.timestamp) {
            if (isDeposit) {
                // Interactions: pull units from sender(solver) to receiver
                IERC20(MULTI_DEPOSITOR_VAULT).safeTransferFrom(msg.sender, request.receiver, request.units);
                // Interactions: transfer tokens from provisioner to sender
                token.safeTransfer(msg.sender, request.tokens);

                // Log solved event
                emit DepositSolved(requestHash);
            } else {
                // Interactions: transfer units from provisioner to sender
                IERC20(MULTI_DEPOSITOR_VAULT).safeTransfer(msg.sender, request.units);
                // Interactions: pull tokens from sender(solver) to receiver
                token.safeTransferFrom(msg.sender, request.receiver, request.tokens);

                // Log solved event
                emit RedeemSolved(requestHash);
            }
