### Title
Unvalidated symlink target (`hdr.Linkname`) allows extraction of symlinks pointing outside the job's extraction root - (File: commands/helpers/archive/tarzstd/tarzstd_extractor.go)

### Summary
`extractor.Extract` validates that a tar entry's `Name`-derived `path` stays within `e.dir` (the chroot-like extraction root) but never validates `hdr.Linkname`, the target of a symlink entry. An attacker who controls the content of a cache or artifact archive can therefore create a symlink whose name resolves inside `e.dir` but whose target is an absolute path or a `../`-traversal pointing anywhere on the filesystem.

### Finding Description
The first loop computes `path` from `hdr.Name` and checks it against the `e.dir` prefix at [1](#0-0) , which correctly blocks `Name`-based traversal. For symlink entries (`fi.Mode()&os.ModeSymlink != 0`), the header is simply deferred to a second pass at [2](#0-1) . In the deferred loop, `os.Symlink(hdr.Linkname, path)` is called directly at [3](#0-2)  with no check that `hdr.Linkname` — fully attacker-controlled — stays under `e.dir`. Only the symlink's own location (`path`) is chroot-checked; its target is not. This is the classic "tar symlink" escape pattern: creating the link itself is safe (it lands inside `e.dir`), but dereferencing it later is not, because the link can point to `/etc/passwd`, `../../other-project/secrets`, or any other path reachable by the process.

The same missing-validation pattern exists in `helpers/archives/zip_extract.go`'s `extractZipSymlinkEntry` (`os.Symlink(string(data), file.Name)` with no target check), confirming this is a systemic gap in the archive extractors rather than a single typo. [4](#0-3) 

Exploit flow: attacker-controlled job creates/uploads a cache or artifact archive containing a symlink entry `Name="evil"`, `Linkname="/etc/passwd"` (or a `../../` traversal). This archive is later extracted by the runner's `extract-cache`/`extract` helper command into a job's build directory (`e.dir`). After extraction, `evil` is a dangling/valid symlink sitting inside the job workspace but pointing outside it. If the job's own script (or a subsequent artifact/cache extraction step, or another helper action) opens, reads, or writes through `evil`, the operation is silently redirected to the attacker-chosen target instead of staying inside the sandboxed build directory.

### Impact Explanation
This lets a job that controls cache/artifact content plant a symlink that, when later traversed by any process operating on the workspace (the job's own script, `git`, artifact packaging, or another extraction step within the same or a subsequent pipeline reusing the cache), reads or writes files outside the intended build/cache/artifact root — violating the "file operations must stay within intended build/cache/artifact roots" invariant. Concrete impact ranges from information disclosure (reading arbitrary files reachable by the runner/job process, e.g. secrets mounted elsewhere in the container, or paths on a shared shell-executor host) to file overwrite in write scenarios (e.g. a later `io.Copy`/artifact write following the same name).

### Likelihood Explanation
This is fully attacker-controlled and easily reproducible: any GitLab user who can push a `.gitlab-ci.yml` defining a cache or artifact upload can construct or influence archive contents containing a symlink entry with an arbitrary `Linkname`, since `NewExtractor`/`Extract` is exactly the code path used to restore caches and artifacts. No special privileges are required beyond standard pipeline authorship, and the bug triggers deterministically on every extraction of such a crafted archive.

### Recommendation
Before calling `os.Symlink(hdr.Linkname, path)`, resolve the symlink target relative to `path`'s directory (for relative `Linkname`) or reject absolute `Linkname` outright, then verify with the same `filepath.Abs` + `strings.HasPrefix(..., e.dir+string(filepath.Separator))` check already used for `Name` at line 62. Reject the entry (return an error) if the resolved target escapes `e.dir`. Apply the equivalent fix to `helpers/archives/zip_extract.go`'s `extractZipSymlinkEntry`.

### Proof of Concept
Go unit test in `commands/helpers/archive/tarzstd`:
1. Build an in-memory tar+zstd stream containing a single header: `Name: "evil"`, `Typeflag: tar.TypeSymlink`, `Linkname: "/etc/passwd"`.
2. Call `NewExtractor(reader, size, tmpDir).Extract(ctx)`.
3. Assert either: `Extract` returns a non-nil error rejecting the entry, OR after extraction `os.Lstat(filepath.Join(tmpDir, "evil"))` followed by `os.Readlink` shows a target that (after resolving) still lies under `tmpDir` — currently it will show `/etc/passwd`, proving the escape.
4. A second variant with `Linkname: "../../../../etc/passwd"` (relative traversal) should be similarly asserted/rejected.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
