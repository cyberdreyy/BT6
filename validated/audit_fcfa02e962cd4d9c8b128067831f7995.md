### Title
Block revenue rewards (`pending_delegator_rewards`) are pooled and redistributed by current stake share instead of being attributed to the stake that actually earned them - ([File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs])

### Summary
The vote program lets anyone deposit block-revenue-sharing rewards into a vote account's `pending_delegator_rewards` pool via the permissionless `DepositDelegatorRewards` instruction. This pool accumulates over time from many separate deposits, but at epoch-reward time the *entire accumulated pool* is split among the vote account's current delegators proportionally to their present stake share, with no bookkeeping of which stake was actually active when each deposit was made. This is structurally the same root cause as the Sherlock M-1 report: a fee/reward pool (`feesOwed`/`pending_delegator_rewards`) that accrues from multiple contributions over time is later divided by a *current* pro-rata ratio (`holdTokenDebt/borrowedAmount` vs. `stake/total_active_stake`), rather than being credited to the party whose activity actually generated it.

### Finding Description
`DepositDelegatorRewards` transfers lamports into the vote account and increments `pending_delegator_rewards` unconditionally, with no linkage to which delegators are staked at deposit time: [1](#0-0) 
The pool is only additive; there is no analog subtracting a fraction back out based on who contributed: [2](#0-1) 

Later, at epoch reward calculation, `calculate_block_reward` divides the *whole* `pending_delegator_rewards` pool among each stake delegation proportional to that delegation's stake versus `total_active_stake`, evaluated only at the reward epoch: [3](#0-2) 

This is called for every stake delegation to the vote account during `calculate_stake_rewards_and_commissions`: [4](#0-3) 

Because the pool has no memory of which stake accounts were delegated when each deposit occurred, any stake that is active at the rewarded epoch's snapshot receives a slice of rewards that were deposited before that stake existed or was activated, diluting the rightful share of the delegators who were actually staked when the block-revenue deposits happened - exactly the "fees distributed among all participants instead of credited to the one who earned it" flaw described in M-1.

### Impact Explanation
Long-standing stake delegators to a vote account lose part of the block-revenue rewards they should be entitled to whenever new stake is activated on that same vote account between reward-triggering deposits and the epoch reward calculation, since the pool is split by an updated stake ratio rather than tracking accrual per-depositor-period. This is a reward/stake accounting corruption: it does not create unsigned lamports out of thin air, but it misallocates already-collected lamports among stakers, which can be systematically exploited by a validator/staker who times new delegations to capture a disproportionate share of previously-accumulated `pending_delegator_rewards`, at the expense of the honest, long-term delegators. Over many epochs and many vote accounts this compounds, matching the "medium, builds up over time" impact profile that Sherlock ultimately assigned to M-1.

### Likelihood Explanation
Reaching this path only requires: (1) a `DepositDelegatorRewards` instruction, which is permissionless and requires only the source account's signature (no vote-account authority needed), and (2) normal `DelegateStake`/stake activation by any user before the next epoch's reward calculation. Both are ordinary, unprivileged single-transaction operations available to any user, so the precondition is trivially reachable. The magnitude of any single dilution is bounded by stake activation warm-up dynamics (`delegation_effective_stake`/`StakeHistory`), which somewhat throttles how much new stake can influence an imminent reward split, but does not eliminate the structural mis-distribution — it can still occur across normal epoch-to-epoch stake churn without any attacker needing to game the warmup window at all.

### Recommendation
Do not treat `pending_delegator_rewards` as a single fungible pool split by the delegators' state at redemption time. Instead, either (a) distribute each `DepositDelegatorRewards` deposit immediately/pro-rata to the stake set active *at the time of deposit* (analogous to earmarking each entrance fee to the lender who was owed it), or (b) track a per-stake-account accrual index (similar to a reward-per-share checkpoint pattern used for inflation rewards' `credits_observed`) so that a stake account's share of `pending_delegator_rewards` only reflects the portion of deposits that occurred while it was actively delegated.

### Proof of Concept
1. Stake account A delegates 100 stake to vote account V. No other stake is delegated to V.
2. Anyone calls `DepositDelegatorRewards` on V, depositing 1,000 lamports, raising `pending_delegator_rewards` to 1,000 (owed entirely to A). [1](#0-0) 
3. Before the next epoch reward calculation, a new stake account B delegates 100 stake to V (B was not staked when the deposit happened and did nothing to earn it).
4. At the epoch boundary, `calculate_block_reward` computes each delegation's share as `pending_delegator_rewards * stake / total_active_stake`: [5](#0-4) 
With `total_active_stake = 200` (A=100, B=100), A receives 500 lamports and B receives 500 lamports, even though B contributed nothing toward the 1,000-lamport deposit and A alone should have received the full 1,000.

/// Calculates block reward for a stake account based on SIMD-0123
fn calculate_block_reward(
    rewarded_epoch: Epoch,
    delegation: &Delegation,
    stake_history: &StakeHistory,
    distribution_epoch_vote_accounts: &VoteAccounts,
    ag_epoch_type: &AlpenglowEpochType,
    new_warmup_cooldown_rate_epoch: Option<Epoch>,
    use_fixed_point_stake_math: bool,
) -> u64 {
    let vote_pubkey = delegation.voter_pubkey;
    let Some(vote_account) = distribution_epoch_vote_accounts.get(&vote_pubkey) else {
        debug!("could not find vote account {vote_pubkey} in cache");
        return 0;
    };
    let vote_state = vote_account.vote_state_view();
    let pending_delegator_rewards = vote_state.pending_delegator_rewards();
    // NOTE: during recalculation, `distribution_epoch_vote_accounts` already
    // includes updated stake activation values from after the new epoch
    // calculation, so we need to use `RewardEpochDelegatedStakes` for the exact
    // values at the end of the reward epoch.
    let (AlpenglowEpochType::Alpenglow {
        reward_epoch_delegated_stakes,
        ..
    }
    | AlpenglowEpochType::MigrationEpoch {
        reward_epoch_delegated_stakes,
        ..
    }) = ag_epoch_type
    else {
        debug!("Alpenglow must be enabled for block reward calculation");
        return 0;
    };
    let total_active_stake = reward_epoch_delegated_stakes
        .delegated_stakes
        .get(&vote_pubkey)
        .copied()
        .unwrap_or(0);
    if total_active_stake == 0 {
        0
    } else {
        let stake = delegation_effective_stake(
            delegation,
            rewarded_epoch,
            stake_history,
            new_warmup_cooldown_rate_epoch,
            use_fixed_point_stake_math,
        );
        // During recalculation, if stake account has already received rewards,
        // it's possible to have `stake > total_active_stake`. If
        // `pending_delegator_rewards` is a huge number, we could potentially
        // overflow a `u64`. We can also have individual rewards look greater
        // than the pending rewards. This is harmless in practice, but we
        // clamp it just to be safe
        (pending_delegator_rewards as u128 * stake as u128 / total_active_stake as u128)
            .try_into()
            .unwrap_or(u64::MAX)
            .min(pending_delegator_rewards)
    }
}
