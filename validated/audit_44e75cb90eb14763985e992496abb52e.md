### Title
A single APR0 withdraw request permanently bricks `stopEpoch` if the manager later sets a non-zero APR - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` uses the *current* `unscaledApr` — not the APR recorded at the request epoch — to decide whether outstanding `apr0TotalPrincipal` is valid. If an unprivileged lender requests a withdrawal while `unscaledApr == 0`, and the manager later calls `setAprs`/`setApr` (or `setAprsWithBuffer` via a queued start flow) to set a non-zero APR before the next `stopEpoch`, every `stopEpoch`/`stopEpochWithDuration` call reverts with `NotAllowed()`. The `apr0TotalPrincipal` bucket is only cleared inside the same function that reverts, so the freeze is permanent and all lender funds are locked.

### Finding Description
When a user requests a withdrawal during a buffer period where `unscaledApr == 0`, `requestWithdraw` routes to `_requestWithdrawApr0`, which increments `apr0TotalPrincipal` and stores `principalEpoch` [1](#0-0) [2](#0-1) .

At the end of the following epoch, `IdleCDOEpochVariant._stopEpoch` calls `prepareStopEpochWithApr0`, which reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` [3](#0-2) . Analogous to the sighash bug, the check consumes the *wrong contextual input*: it validates the bucket against the live `unscaledApr` rather than the APR state that existed at `principalEpoch`. `setApr`/`setAprs` is a routine, documented manager operation to fix the epoch APR [4](#0-3) , and there is no guard preventing it from being called while `apr0TotalPrincipal > 0`.

Once the revert condition holds, there is no recovery path:
- `apr0TotalPrincipal` is reset only at the end of `prepareStopEpochWithApr0`, which is unreachable [5](#0-4) .
- The APR0 claim-clearing path (`_clearWithdrawClaimForEpoch`) only adjusts `apr0TotalPrincipal` inside `_claimDefaultedWithdrawRequest`, which requires `defaultRecoveryFinalized` — unreachable because `stopEpoch` can never succeed to trigger default/finalization [6](#0-5) .
- `stopEpoch` reverting means `isEpochRunning` stays true, blocking deposits, withdrawal requests (`allowAA/BBWithdrawRequest` remain false), and `startEpoch` (`block.timestamp < epochEndDate + bufferPeriod` check fails permanently since `epochEndDate` is stale) [7](#0-6) [8](#0-7) .

No existing guard stops this: `setApr` only checks caller and `maxApr`; nothing couples APR changes to `apr0TotalPrincipal`. The epoch gating, `onlyIdleCDO`, and KYC checks are all satisfied along this path.

### Impact Explanation
Permanent freezing of all lender principal and yield in the vault. Once `apr0TotalPrincipal > 0` coincides with `unscaledApr != 0`, the epoch can never be stopped, so no withdraw request can ever be funded or claimed, no default can be declared through the normal flow, and deposits remain paused. Loss = 100% of vault TVL plus owed pending withdrawals, permanently locked (absent a contract upgrade).

### Likelihood Explanation
Medium. It requires (a) any unprivileged user making a normal withdraw request while `unscaledApr == 0` — a legitimate, documented APR0 flow — and (b) the honest manager setting a non-zero APR via `setAprs`/`setAprsWithBuffer` while the bucket is open, which is a routine per-epoch operation with no warning or on-chain guard. A single small dust withdrawal request (e.g. 1 wei principal during a zero-APR buffer) is sufficient to arm the trap.

### Recommendation
Record the APR validity at request-epoch granularity instead of reading the live `unscaledApr`: e.g., store `apr0EpochApr` alongside `apr0TotalPrincipal` (or keep per-epoch buckets keyed by `principalEpoch`) and settle APR0 claims using the APR that applied during `principalEpoch`. Alternatively, guard `setApr`/`setAprs`/`setAprsWithBuffer` to revert while `apr0TotalPrincipal != 0`, or allow `prepareStopEpochWithApr0` to gracefully settle APR0 principal at zero interest rather than reverting.

### Proof of Concept
```solidity
// Foundry fork test against the deployed IdleCDOEpochVariant + IdleCreditVault
function testApr0RequestThenAprChangeFreezesStopEpoch() external {
    // 1. Pool is between epochs with unscaledApr == 0 (APR0 buffer period).
    //    Attacker (any KYC-passed lender) deposits and requests a withdraw.
    idleCDO.depositAA(100e18);
    cdoEpoch.requestWithdraw(50e18, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // 2. Honest manager sets a non-zero APR for the coming epoch (routine op).
    vm.prank(manager);
    strategy.setAprs(10e18, 10e18); // unscaledApr != 0 while apr0TotalPrincipal > 0

    // 3. Epoch starts and ends normally.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, owed);

    // 4. Every stopEpoch reverts forever: apr0TotalPrincipal != 0 && unscaledApr != 0.
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(10e18, 0);

    // Re-setting APR back to 0 also cannot help if the manager ever wants a
    // non-zero APR epoch; and no user/guardian action can clear the bucket.
    // isEpochRunning stays true -> deposits, requests, and claims remain blocked.
    assertTrue(cdoEpoch.isEpochRunning()); // permanent freeze of all TVL
}
```
