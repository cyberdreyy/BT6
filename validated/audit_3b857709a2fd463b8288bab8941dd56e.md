### Title
Multisig executes requests using confirmations from members that have already been removed - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts entries in the `confirmations` set for a request purely by size (`confirmations.len() as u32 + 1 >= self.num_confirmations`), without re-validating that every account/key that previously confirmed is still a current member. `delete_member` only purges confirmations for requests that the removed member *authored* (`r.member == member`), not confirmations the removed member *cast on other members' requests*. A confirmation left behind by a member who has since been removed therefore still counts toward the execution threshold, letting a request execute with fewer live, currently-authorized approvals than `num_confirmations` requires.

### Finding Description
`confirm` in `multisig2/src/lib.rs` [1](#0-0)  adds the calling member's identity to the request's `confirmations: HashSet<String>` and executes the request once `confirmations.len() + 1 >= self.num_confirmations`. It never checks whether the strings already stored in `confirmations` still correspond to accounts/keys present in `self.members`.

`delete_member` [2](#0-1)  removes outstanding *requests authored by* the deleted member:
```
let request_ids: Vec<u32> = self
    .requests
    .iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
```
It filters solely on `r.member` (the request's original author, stored in `MultiSigRequestWithSigner.member` [3](#0-2) ), and only clears `self.confirmations` for those requests. It never scans other requests' `confirmations` sets to strip out an entry belonging to the member being deleted. So if the deleted member had confirmed (but not authored) a *different* pending request, that stale confirmation string remains stored under that request's `confirmations` set.

The binding the multisig is supposed to enforce is:
```
confirmations_counted_toward_threshold == confirmations_from_currently_live_members
```
Because stale confirmations from removed members are never purged and `confirm` never filters against `self.members`, this equality breaks: a request can reach `num_confirmations` confirmations while containing one or more entries from accounts/keys that are no longer members at execution time.

### Impact Explanation
This crosses exactly the threshold/authorization boundary called out as Critical impact: "a multisig request executed below threshold." A pending `Transfer`, `FunctionCall`, `AddKey`, or `DeployContract` request can be executed with fewer genuinely-current approvals than the contract's configured `num_confirmations`, because one of the counted confirmations belongs to a member who has already been removed (e.g., for being compromised, malicious, or simply rotated out). This lets funds move, keys be added, or code be deployed on the multisig account without the intended live quorum of authorization.

### Likelihood Explanation
This requires no external state or foreign contract, only ordinary sequencing of in-scope, standard multisig operations:
1. A member confirms a pending request (but does not push it to execution).
2. That same member is later removed via a normal `DeleteMember` request (a routine, expected multisig lifecycle operation, not requiring any bug elsewhere).
3. The original request (authored by someone else) still holds the removed member's confirmation, uncleaned.
4. Additional confirmations from currently-live members subsequently push the count to `num_confirmations` and the request executes, effectively 1 live-member confirmation short of the intended quorum.

No special privilege beyond being (or having been) an ordinary multisig member is required, and the sequence of add/confirm/delete-member/confirm operations is part of documented multisig usage, not an edge case requiring a compromised owner or foundation action.

### Recommendation
When removing a member in `delete_member`, iterate all pending requests' `confirmations` sets (not just requests authored by that member) and strip the removed member's identity from every set. Alternatively, have `confirm`/`execute_request` re-validate, at confirmation-count time, that every entry in the `confirmations` set is still contained in `self.members`, and only count those that are.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `A` calls `add_request` to create request `X`: `Transfer { amount, receiver_id: X_receiver }`.
3. `B` calls `confirm(X)` — confirmations for `X` = `{B}` (size 1).
4. Separately, members create and confirm a `DeleteMember { member: B }` request (a normal, otherwise-legitimate operation) and it executes, removing `B` from `self.members`. Per `delete_member`, only requests where `r.member == B` (i.e., authored by `B`) are purged; request `X` (authored by `A`) is untouched, so `X`'s confirmations set still contains `B`.
5. `C` calls `confirm(X)` — confirmations for `X` become `{B, C}` (size 2); `2 + 1 >= 3` is true, so `execute_request` runs and the transfer executes.
6. Result: request `X` executed with `num_confirmations = 3` satisfied by only two currently-live members (`A` as requester is not itself a confirmation, `C`) plus one stale confirmation from `B`, who was no longer a member at execution time — i.e., the request executed below the real live-member threshold.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
