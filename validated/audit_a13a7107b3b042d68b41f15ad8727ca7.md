### Title
Stale confirmations from removed multisig members/keys are still counted toward the approval threshold, allowing a request to execute below the effective live-signer threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
Both multisig contract versions let a member/key confirm a request, get removed from the multisig, and still have that confirmation counted when a later `confirm()` call tallies votes for a *different, still-pending* request. `confirm()` only checks `confirmations.len() + 1 >= self.num_confirmations` [1](#0-0)  without re-validating that every account/key in that `HashSet` is still a live member. `delete_member`/`DeleteKey` only purge confirmations for requests that the *removed* member originally created, not confirmations they placed on other members' requests [2](#0-1) [3](#0-2) .

### Finding Description
The invariant that should hold is: **live confirmations on a request == count used to reach `num_confirmations`**. Instead, the contract's confirmation set is append-only per request and is only cleaned up for requests *authored by* the departing signer:

- `delete_member` (multisig2) filters `self.requests` for entries where `r.member == member` (i.e., requests the removed member created) and clears those, but does nothing to `self.confirmations` entries for *other* requests that this member had already confirmed: [4](#0-3) 
- The v1 equivalent, `DeleteKey`, has the identical pattern: it only removes requests where `r.signer_pk == pk`, leaving that key's confirmations on unrelated requests intact: [3](#0-2) 
- `confirm()` counts raw set size against `num_confirmations` with no live-membership re-check: [5](#0-4)  and [6](#0-5) 

So the equality that should hold — `confirmations counted == confirmations by currently authorized members` — is broken; a stale confirmation from a departed member/key can silently make up part of the quorum.

### Impact Explanation
This crosses the threshold/authorisation boundary explicitly called out as Critical: "a multisig request executed below threshold." A `Transfer` (or `FunctionCall`, `AddKey`, etc.) request can execute with fewer *live* signer approvals than `num_confirmations` nominally requires, because a stale confirmation from a removed member/key still counts. Since `Transfer` moves NEAR out of the multisig account directly via `promise.transfer(amount.into())` [7](#0-6) , this can result in NEAR moved by a party set that does not meet the intended quorum.

### Likelihood Explanation
Exploitability requires only ordinary lifecycle events, not an ignored deployment or foundation/attacker collusion:
1. A pending request `R` exists and has been confirmed by member `A` (one of `n` legitimate confirmations, threshold not yet met).
2. Independently — for entirely unrelated, legitimate reasons (key rotation, offboarding, compromised-key rotation) — the multisig later executes a `DeleteMember`/`DeleteKey` action removing `A`. This removal succeeds and only clears `A`'s own *authored* requests, not `A`'s confirmation on `R`.
3. `R` remains pending with `A`'s stale confirmation still counted.
4. Sufficient additional *live* members confirm `R` to reach `num_confirmations` when combined with the stale entry — but the number of genuinely live signers who approved is one less than intended.
5. `execute_request` runs on the last confirming call, moving funds/executing the action with a live-signer quorum below `num_confirmations`.

Because members/keys are commonly rotated over the life of a multisig (this is the normal, documented way to remove a compromised or departing signer), and confirmations frequently sit pending across many transactions (subject only to `REQUEST_COOLDOWN` for deletion, not for confirmation), the window for this stale-confirmation condition to arise is realistic and does not require any privileged or out-of-scope action beyond normal governance.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey`), iterate over **all** active requests (not just those authored by the removed member/key) and strip that member's/key's entry from each request's confirmation set, re-checking whether the remaining confirmation count would already meet threshold. Alternatively, `confirm()` should recompute the live-confirmation count by filtering the stored set against current `self.members` (or valid keys) before comparing to `num_confirmations`, rather than trusting the raw stored-set length.

### Proof of Concept
Using `multisig2::MultiSigContract` semantics (analogous PoC applies to `multisig` with `signer_pk`s):

1. `new(members: [A, B, C, D], num_confirmations: 3)`.
2. `A` calls `add_request_and_confirm(Transfer{amount})` targeting `receiver_id` — confirmations = `{A}` (1/3).
3. Through normal governance, members confirm and execute a separate `DeleteMember{member: A}` request (requires 3 live confirmations of B, C, D or similar) — `A` is removed from `self.members`, but the `Transfer` request's confirmation set in step 2 still contains `A`'s entry because `delete_member` only purged requests where `r.member == A` (the delete-member request itself was authored by someone else) [4](#0-3) .
4. `B` calls `confirm(request_id)` → confirmations = `{A, B}` (2/3, no execution yet).
5. `C` calls `confirm(request_id)` → `confirmations.len() + 1 == 3 >= num_confirmations(3)` → `execute_request` runs the `Transfer`, even though only `B` and `C` (2 live members) plus one stale, no-longer-authorized entry `A` approved it — one fewer live approver than the configured 3-of-n threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
