### Title
Missing signer check in `InitializeBuffer` allows front-running/authority hijack of upgradeable-loader buffer accounts - ([File: programs/bpf_loader/src/lib.rs])

### Summary
`process_loader_upgradeable_instruction`'s `InitializeBuffer` arm sets the buffer account's authority to whatever pubkey is passed as instruction account 1, without requiring that account to sign, and without requiring the buffer account itself to sign. This mirrors the reported `UXDController.sol::initialize()` bug class: an unprotected "claim ownership" call that can be front-run by any unrelated transaction once the target account exists on-chain but is still `Uninitialized`.

### Finding Description
The `InitializeBuffer` instruction only checks that the account is currently `Uninitialized` and then unconditionally assigns the authority from account index 1: [1](#0-0) 

Neither the buffer account (index 0) nor the proposed authority (index 1) is required to be a signer for this instruction — this is confirmed by the test that exercises the success path with both accounts marked `is_signer: false`: [2](#0-1) 

A buffer account only becomes a candidate for `InitializeBuffer` after it's been created via `system_instruction::create_account` (assigned to `bpf_loader_upgradeable`), which is a *separate* instruction requiring only the new account keypair's signature — not any binding to who is later allowed to initialize it. The atomicity between `CreateAccount` and `InitializeBuffer` is enforced purely by client convention (bundling both instructions into one signed message), as seen in the CLI's buffer-creation flow: [3](#0-2) 

and in the test helper that composes `create_buffer_instructions` into a single `Transaction`: [4](#0-3) 

Nothing at the protocol level prevents `CreateAccount` and `InitializeBuffer` from being submitted as two separate transactions. If they are (e.g., due to a wallet/tool that splits them, a dropped/delayed second transaction, or simply an attacker racing the mempool), any third party can submit their own `InitializeBuffer` instruction against the still-`Uninitialized` buffer account before the legitimate deployer's `InitializeBuffer` lands — exactly analogous to front-running `UXDController.sol`'s unprotected `initialize()`.

### Impact Explanation
Once the attacker's `InitializeBuffer` transaction lands first, the account state becomes `Buffer { authority_address: Some(attacker_key) }`. Subsequent legitimate `InitializeBuffer` calls fail with `AccountAlreadyInitialized` (DOS on the deployment), and — more importantly — the attacker now holds the sole `authority_address` needed to call `Write` and `SetAuthority` on that buffer (both of which check authority via `authority_address == present_authority_key` plus signer, per `programs/bpf_loader/src/lib.rs` lines 177-190 and 555-576). The attacker can write arbitrary bytecode into the account the victim already paid rent for, or transfer/lock the authority, hijacking a resource the victim funded and intended to control — an authority/privilege takeover reachable from a single unprivileged transaction.

### Likelihood Explanation
Exploitability depends on the two instructions landing in separate transactions, which is not guaranteed to always happen (well-formed CLI flows bundle them atomically), so likelihood is lower than a guaranteed hijack, but the protocol itself provides no signer-based protection to prevent it — the vulnerability is a genuine missing-signature-check gap in `InitializeBuffer`, consistent with the reported bug class.

### Recommendation
Require the buffer account (index 0) to be a signer for `InitializeBuffer` (binding creation and initialization to the same signer/transaction), or otherwise cryptographically bind buffer creation to its initializer (e.g., require the payer/creator of the `CreateAccount` to also be present/sign in `InitializeBuffer`), removing reliance on client-side transaction bundling as the only defense against front-running.

### Proof of Concept
1. Victim submits `system_instruction::create_account(payer, buffer_pubkey, ..., owner=bpf_loader_upgradeable::id())` in transaction T1, intending to follow up with `InitializeBuffer` naming themselves as authority.
2. Before T1's follow-up `InitializeBuffer` transaction lands, attacker observes buffer_pubkey now owned by `bpf_loader_upgradeable` and still `Uninitialized`, and submits `UpgradeableLoaderInstruction::InitializeBuffer` with `buffer_pubkey` (index 0, `is_writable: true`, `is_signer: false`) and `attacker_pubkey` (index 1, `is_signer: false`) — matching the exact account-meta shape validated to succeed in the test at `programs/bpf_loader/src/lib.rs:1417-1449`.
3. `process_loader_upgradeable_instruction` sets `buffer.set_state(&UpgradeableLoaderState::Buffer { authority_address: Some(attacker_pubkey) })` (lines 169-171), succeeding because the account was still `Uninitialized`.
4. Victim's original `InitializeBuffer` now fails with `AccountAlreadyInitialized`; attacker is the sole authority able to `Write`/`SetAuthority` on the rent-funded buffer account.
