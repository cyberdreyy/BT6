This confirms the hypothesis directly: `requestCache.ProcessResponse` keys entries by the composite `globalId{sender, id}` (for requests, `{request.Body.Sender, request.Body.MessageId}`; for responses, `{response.Body.Receiver, response.Body.MessageId}`), not by `MessageId` alone.

### Title
No exploitable vulnerability: MessageId collisions across DONs/senders cannot cause cross-user response confusion - ([File: core/services/gateway/handlers/common/message_util.go])

### Summary
`ValidatedResponseFromMessage`/`ValidatedRequestFromMessage` in `core/services/gateway/handlers/common/message_util.go` only check `msg.Body.MessageId == ""` for emptiness, not global uniqueness, but this is by design: uniqueness/ownership is enforced downstream by `requestCache` using a composite key of sender/receiver plus `MessageId`, so a MessageId collision across different senders/DONs cannot cause cross-request confusion.

### Finding Description
`ValidatedResponseFromMessage` (`core/services/gateway/handlers/common/message_util.go:61-80`) and `ValidatedRequestFromMessage` (`core/services/gateway/handlers/common/message_util.go:83-105`) both reject only empty `MessageId`, and are purely format-conversion helpers between the legacy `api.Message` type and JSON-RPC request/response objects. They do not attempt to bind or verify request ownership themselves, because that is not their responsibility — request/response binding happens in `RequestCache` (`core/services/gateway/handlers/common/requestcache.go`).

`RequestCache.NewRequest` stores a pending request under `key := globalId{request.Body.Sender, request.Body.MessageId}` [1](#0-0)  and `RequestCache.ProcessResponse` looks up the entry using `key := globalId{response.Body.Receiver, response.Body.MessageId}` [2](#0-1) . Because `globalId` is a struct of `{sender, id}` [3](#0-2) , a response with a colliding `MessageId` but a different `Receiver` (which must match the original request's `Sender`, cryptographically bound via `msg.ExtractSigner()`/signature verification in `api.Message.Validate()` [4](#0-3) ) will simply not match any cache entry and `ProcessResponse` returns `"request not found"` [5](#0-4) .

Additionally, the `Sender`/`Receiver` fields in `api.Message` are populated from the cryptographically verified signer of the message (`m.Body.Sender = utils.StringToHex(string(signerBytes))` after `ExtractSigner()` succeeds) [4](#0-3) , so an attacker cannot forge an arbitrary `Sender`/`Receiver` value to collide with another legitimate DON/sender's pending request — this would require forging that party's signature, which is out of scope for an unprivileged attacker.

The equivalent remote executable capability path (`core/capabilities/remote/executable/server.go`) goes further, combining `messageID` with a hash of the payload into `requestID := messageID + hex.EncodeToString(msgHash[:])` [6](#0-5) , and `ClientRequest.OnMessage` tracks per-sender response state via `c.responseReceived[sender]`, rejecting unexpected or duplicate senders [7](#0-6) .

### Impact Explanation
None. `message_util.go`'s emptiness check is not the sole binding mechanism; the composite `globalId{sender/receiver, MessageId}` key in `RequestCache` and signature-derived sender/receiver binding in `api.Message.Validate()` together prevent cross-DON/cross-sender response confusion from a bare `MessageId` collision.

### Likelihood Explanation
Not applicable — no viable attack path exists for an unprivileged attacker to achieve cross-user/cross-DON response confusion purely via `MessageId` collision, since forging the matching `Sender`/`Receiver` requires a valid signature from the victim's key, which is outside the unprivileged attacker's capabilities.

### Recommendation
No fix required for `message_util.go`. If defense-in-depth is desired, `ValidatedResponseFromMessage`/`ValidatedRequestFromMessage` could optionally validate that `Sender`/`Receiver` fields are also non-empty before conversion, but this does not address any demonstrated vulnerability since ownership binding already exists at the `RequestCache` layer.

### Proof of Concept
Not applicable (no vulnerability). Existing tests such as `TestRequestCache_MultiResponse` in `core/services/gateway/handlers/common/requestcache_test.go:53-103` already demonstrate that multiple pending requests sharing the identical `MessageId` "abcd" but different `Sender` values are correctly disambiguated by `ProcessResponse` matching against `Receiver`, confirming the composite key prevents the described collision scenario [8](#0-7) .
