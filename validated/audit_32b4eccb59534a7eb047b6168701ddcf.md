### Title
Unprivileged instant withdrawal requests block `stopEpoch` and can force borrower default — (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In `IdleCDOEpochVariant`, `stopEpoch` reverts whenever `_pendingInstant() != 0`, i.e. whenever any instant withdrawal request is still unfunded. Instant withdrawal requests are created by ordinary tranche holders through `requestWithdraw`. The only way to clear them before stopping the epoch is the privileged `getInstantWithdrawFunds` call, which pulls the full pending amount from the borrower — and if that `transferFrom` fails, the pool is pushed into `_handleBorrowerDefault`. This mirrors the reported Astaria bug: an unprivileged user's leftover state (expired lien / unfunded instant request) halts epoch processing until a monitored privileged call runs, and executing that call can crystallize a default.

### Finding Description
`_stopEpoch` enforces:

```solidity
// contracts/IdleCDOEpochVariant.sol:338-351
_checkNotAllowed(
  !isEpochRunning ||
  block.timestamp < epochEndDate ||
  _pendingInstant() != 0 ||               // unfunded instant withdraws block the stop
  (_interest > 1 && (_interest < _pendingWithdrawFees || _newApr != 0)) ||
  (_isRequestingAllFunds && _lossAmount != 0)
);
```

`getInstantWithdrawFunds` is owner/manager-only, gated on `block.timestamp >= instantWithdrawDeadline`, and on success calls `IdleCreditVault.collectInstantWithdrawFunds`; on failure of `getFundsFromBorrower` it calls `_handleBorrowerDefault(_instantWithdraws)`, which sets `defaulted = true`, pauses the pool, stops the epoch, and disables new withdraw requests (lines 577–599).

A KYC'd tranche holder can therefore request an instant withdrawal (the instant path is taken when instant withdraws are enabled and the APR drops; programmable-borrower mode is excluded since `getInstantWithdrawFunds`/`requestWithdraw` reject it — confirmed by `testProgrammableBorrowerRequestWithdrawNeverCreatesInstantWithdraws` and `testProgrammableBorrowerGetInstantWithdrawFundsIsUnsupported`). If the manager does not call `getInstantWithdrawFunds` before epoch end, every subsequent `stopEpoch` reverts indefinitely — epoch accounting, interest accrual, pending normal-withdrawal funding, and APR rollover all stall. If the manager does call it and the borrower lacks sufficient approved liquid balance to cover `_instantWithdraws` (borrowers hold the pool's principal for deployment), the honest borrower is defaulted even though it is not actually insolvent, triggering loss socialization through the default/recovery path.

Broken invariant: epoch liveness should not depend on an optional privileged cleanup call whose failure converts a user-triggered liquidity demand into a pool-wide default.

### Impact Explanation
- Temporary freezing of the entire epoch state machine: no `stopEpoch` → no interest accrual, no funding of pending (non-instant) withdrawal receipts, no next epoch, user funds locked until the privileged call succeeds.
- Permanent/structural impact via forced default: if `getFundsFromBorrower` fails inside `getInstantWithdrawFunds`, `defaulted = true` is set, instant claims stay disabled, and all LPs must go through the default-claim flow, realizing whatever recovery basis results from the shortfall.

### Likelihood Explanation
Trigger requires only a tranche position and an instant-withdraw-eligible window (instant withdraws enabled, non-programmable borrower). The cost to the attacker is limited to interest/fees on the requested amount during the delay window. The stall itself only needs manager inaction; the default escalation needs the borrower to be illiquid against the instant amount at that moment, which is plausible since borrower capital is deployed (only programmable borrowers park funds in an ERC4626 sleeve, and they are exempt from this path).

Caveats/limitations: the manager can resolve the freeze at any time by funding the instant requests, and `stopEpoch`'s failure path also exists to catch borrower insolvency rather than only griefing. The pure "halt until someone calls X" portion is a liveness/ops dependency; the fund-impact portion (forced default of a liquid-but-not-yet-repaid borrower) is the stronger claim, but whether a real deployment permits instant requests at scale depends on `disableInstantWithdraw`/APR-drop gating I did not fully trace in `requestWithdraw` inside `IdleCreditVault.sol`.

### Recommendation
- Decouple epoch stop from instant-withdraw funding: on `stopEpoch`, either convert unfunded instant requests into normal pending withdrawals for the next epoch, or fund them from contract underlyings already held (as `startEpoch` does at lines 279–294) instead of reverting.
- If borrower funding of instant claims is required, treat failure as a targeted shortfall on the instant-claim bucket rather than a full `_handleBorrowerDefault`, or bound the instant-withdraw queue to liquidity the borrower is contractually required to keep.
- Add keeper/monitoring around `instantWithdrawDeadline` so `getInstantWithdrawFunds` is guaranteed to run before `epochEndDate`.

### Proof of Concept
```solidity
// Foundry fork test sketch against IdleCDOEpochVariant + IdleCreditVault (non-programmable mode)
function testInstantWithdrawBlocksStopEpoch() public {
    // setup: deposit AA/BB, startEpoch with instant withdraws enabled
    idleCDO.depositAA(10_000e6);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // attacker (KYC'd tranche holder) creates an instant withdraw request
    // when instant path is active (apr drop / disableInstantWithdraw == false)
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche));
    vm.stopPrank();
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // manager never calls getInstantWithdrawFunds; epoch end passes
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // every stopEpoch reverts on _pendingInstant() != 0 -> epoch halted
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(newApr, 0);

    // escalation: borrower illiquid -> forced default instead of clean stop
    // (borrower spends approved allowance / lacks balance covering pendingInstant)
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // getFundsFromBorrower fails -> _handleBorrowerDefault
    assertTrue(cdoEpoch.defaulted());
}
```
