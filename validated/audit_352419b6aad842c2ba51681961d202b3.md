### Title
Front-running `MultisigFactory::create` with a colliding `name` permanently strands the victim's attached NEAR deposit - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` derives the new multisig's account ID solely from an attacker-observable, user-supplied `name` parameter and immediately kicks off an async `Promise` chain (`create_account → deploy_contract → transfer → function_call`) with no completion callback. If any other actor creates `{name}.{factory}` first (e.g. by front-running the pending transaction with the same `name`), the victim's promise chain fails at the `create_account` step, and because there is no `.then()` callback to detect the failure and refund the depositor, the victim's attached deposit is refunded by the protocol to the *predecessor of the failed receipt* — the `MultisigFactory` contract itself — which exposes no withdrawal method. The funds are permanently unrecoverable.

### Finding Description
`create()` computes the target account deterministically from caller-supplied input and dispatches a single un-monitored promise: [1](#0-0) 

Unlike its sibling factories, `MultisigFactory` has no `on_create` callback. Compare with `LockupFactory::create`, which chains an explicit callback that inspects `is_promise_success()` and manually returns the deposit to `predecessor_account_id` on failure: [2](#0-1) 

and `StakingPoolFactory::create_staking_pool`/`on_staking_pool_create`, which additionally guards against name collisions synchronously via a persisted set (`self.staking_pool_account_ids.insert(...)`) before ever spending the deposit, and also refunds on async failure: [3](#0-2) [4](#0-3) 

`MultisigFactory::create` has neither protection: no pre-check that `{name}.{factory}` is free, and no callback to recover funds if the underlying `create_account` action fails. Since account creation for `{name}.{factory}` can only be performed by the factory contract itself as predecessor, an attacker cannot pre-create the exact same account through any other path — but they can win the race by simply calling `create()` with the same `name` first (their own transaction, observed via the target `name` becoming public in the pending/broadcast transaction, or simply guessed since names are often predictable, e.g. sequential or organization-chosen). When the victim's later `create()` call's async receipt executes against an already-existing account, the `create_account` action fails, the batched `transfer` action never executes, and the protocol-level refund for that failed receipt is sent to the receipt's predecessor — the `MultisigFactory` account — not to the original caller. `MultisigFactory` defines no method to move that balance back out, so the deposit is permanently frozen inside the factory contract.

### Impact Explanation
This breaks the custody binding "NEAR attached by the caller for their intended new multisig == NEAR eventually held by that caller or their multisig." The attacker gains nothing directly (no theft), but the victim's deposited NEAR becomes permanently inaccessible, matching the Critical category "funds permanently frozen." This can occur either through a malicious front-runner or benign name collision, but the underlying code defect — missing failure-path refund present in every other factory in this repo — is what turns a simple naming collision into an unrecoverable loss.

### Likelihood Explanation
Any unprivileged account can call `create()` with an arbitrary `name`; no authorization or whitelist is required. Colliding on a specific `name` requires only observing/predicting the victim's chosen `name` and submitting a transaction that lands first, which is realistic given NEAR's transaction propagation and lack of any reservation/pre-check in this contract.

### Recommendation
Add a completion callback to `MultisigFactory::create` (mirroring `LockupFactory::on_lockup_create` / `StakingPoolFactory::on_staking_pool_create`) that checks `is_promise_success()` and refunds `env::attached_deposit()` to `env::predecessor_account_id()` on failure. Optionally also maintain a persisted set of in-use names and reject duplicates synchronously before spending the deposit, as `StakingPoolFactory` does.

### Proof of Concept
1. Alice submits `create(name: "team", members: [...Alice's key], num_confirmations: N)` with attached deposit `D`.
2. Bob observes the pending call (or predicts the popular name "team") and submits his own `create(name: "team", members: [...Bob's key], num_confirmations: 1)` with a small deposit, which lands first and successfully creates `team.<factory>` as Bob's multisig.
3. Alice's transaction executes: the async receipt's `create_account` action for `team.<factory>` fails because the account already exists; the batched `transfer` of `D` never happens.
4. Per NEAR protocol refund rules, `D` is refunded to the predecessor of the failed receipt, i.e., the `MultisigFactory` contract account, not Alice.
5. `MultisigFactory` (`multisig-factory/src/lib.rs`) exposes no withdrawal function, so `D` is permanently stuck in the factory's balance, unrecoverable by Alice or anyone else.

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }

    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids

                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
