### Title
View-role authenticated user can read AccessKey/OutgoingToken secrets for all External Initiators via unrestricted GET /v2/external_initiators - (File: core/web/external_initiators_controller.go)

### Summary
The route `GET /v2/external_initiators` is registered without any role-gating middleware (`RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole`), unlike its sibling `POST`/`DELETE` routes on the same resource. Any authenticated user — including one with the lowest `view` role, or a `run`-role external-initiator-derived session — can call `Index` and receive `presenters.ExternalInitiatorResource` entries that include the plaintext `AccessKey` and `OutgoingToken` fields for every External Initiator registered on the node.

### Finding Description
In `core/web/router.go`, the external initiator routes are registered as: [1](#0-0) 
Only `Create` and `Destroy` are wrapped with `auth.RequiresEditRole`; `Index` is wrapped only with `paginatedRequest`, which does not perform any role check — it merely parses pagination params before invoking the handler.

The `authv2` group itself only requires that the caller be authenticated (`auth.AuthenticateByToken` or `auth.AuthenticateBySession`), with no minimum role, per: [2](#0-1) 
Thus a session/token belonging to a `view`-role user passes the `Authenticate` middleware and reaches `ExternalInitiatorsController.Index` unimpeded.

`Index` fetches all external initiators from the ORM and converts each one via `presenters.NewExternalInitiatorResource`, with no redaction: [3](#0-2) 

The presenter directly copies the sensitive `AccessKey` and `OutgoingToken` fields from the `bridges.ExternalInitiator` domain object into the JSON response: [4](#0-3) 

These are genuine secrets: `AccessKey`/`OutgoingToken` are generated per-EI credential material used by the node to authenticate outbound calls to the external initiator and used by the initiator to authenticate inbound job-run trigger requests: [5](#0-4) 

No role check, ownership check, or field-level redaction exists anywhere in this path to stop a `view`-role user (or a `run`-role principal, which per `AuthenticateExternalInitiator` is the role automatically assigned to any successfully-authenticated external initiator session) from retrieving this data: [6](#0-5) 

### Impact Explanation
This is a credential/secret disclosure to an unprivileged authenticated user (matches Chainlink's "sensitive data exposure"/"unauthorized secret disclosure" bounty class). Obtaining another EI's `AccessKey`/`OutgoingToken` allows the attacker to impersonate that External Initiator toward the node's outbound webhook calls (using `OutgoingToken`) or otherwise gain material that facilitates further impersonation/job-run triggering abuse, without requiring `edit`/`admin` privileges. It does not directly move funds, but it breaks the intended privilege-separation between `view` and `edit`/`admin` roles for credential material, which the codebase explicitly protects on the `Create`/`Destroy` routes for the same resource.

### Likelihood Explanation
Trivial and fully reproducible: any account/token with the lowest privilege role (`view`) — or any credential holder able to reach the `authv2` group (including an external-initiator-derived `run` session) — can call the endpoint directly. No race conditions, no special network position, and no additional bypass is needed; the missing middleware wrapper is the sole gate.

### Recommendation
Wrap the `Index` route with at least `auth.RequiresEditRole` (matching `Create`/`Destroy`), i.e. `authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))`. Additionally, consider not returning `AccessKey`/`OutgoingToken` from list endpoints at all (only return them once, at creation time, as is already done via `ExternalInitiatorAuthentication` in `Create`), so that `ExternalInitiatorResource` used by `Index` never re-exposes long-lived secret material.

### Proof of Concept
Go handler-integration test (in `core/web/external_initiators_controller_test.go` style):
1. Create a node with an admin user; use admin API to create an External Initiator via `POST /v2/external_initiators`, capturing the returned `AccessKey`/`OutgoingToken`.
2. Create a second user with role `view` (`clsessions.UserRoleView`) and obtain its authenticated session/API token.
3. As the `view` user, issue `GET /v2/external_initiators`.
4. Assert: response status is `200 OK` (not `401`/`403`), and the JSON body contains a non-empty `accessKey` and `outgoingToken` field matching the value created in step 1.
5. Expected secure behavior (currently failing): the request should be rejected with `401 Unauthorized` (mirroring `RequiresEditRole` behavior on `POST`/`DELETE`), or the response should never include non-empty `accessKey`/`outgoingToken`.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,

}
```
