### Title
Unauthenticated auth middleware leaks raw internal error messages (including DB errors) to the client - ([File: core/web/auth/auth.go], [File: core/web/auth/helpers.go])

### Summary
The `Authenticate` gin middleware in `core/web/auth/auth.go` forwards the raw `error` returned by `AuthenticateBySession`/`AuthenticateByToken` directly to `jsonAPIError`, which serializes `err.Error()` into the HTTP response body via `models.NewJSONAPIErrorsWith(err.Error())` whenever the error is not a `*models.JSONAPIErrors`. Any error other than the sentinel `auth.ErrorAuthFailed` (e.g. a raw DB/driver error surfaced by `AuthorizedUserWithSession` or `FindUserByAPIToken`) is therefore returned verbatim to an unauthenticated caller.

### Finding Description
`jsonAPIError` unconditionally falls back to embedding `err.Error()` in the JSON response when the error is not already a `*models.JSONAPIErrors`: [1](#0-0) 

`AuthenticateBySession` propagates whatever error `AuthorizedUserWithSession` returns without wrapping or sanitizing it: [2](#0-1) 

`AuthenticateByToken` only maps `sql.ErrNoRows`/`ErrUserSessionExpired` to the generic `auth.ErrorAuthFailed`; any other error from `FindUserByAPIToken` or `clsessions.AuthenticateUserByToken` (e.g. a raw SQL/driver error) is returned unmodified: [3](#0-2) 

The `Authenticate` middleware loop breaks out and reports the error as soon as it is anything other than `auth.ErrorAuthFailed`, then hands it straight to `jsonAPIError` with a 401 status: [4](#0-3) 

Because this middleware runs before any authentication succeeds, an unauthenticated caller can trigger it on every protected route simply by sending a request with a bad/absent session cookie or API key/secret header while the underlying data-store call fails for an unrelated reason (e.g. DB connection drop, context timeout, driver-level error, malformed UUID causing a scan error, etc.). Whatever text the DB driver / ORM produces for that failure (which can include query fragments, column/table names, or driver-specific diagnostic text) is not filtered before being placed in the HTTP response body returned to the attacker.

### Impact Explanation
This is an information-disclosure issue: unauthenticated clients can potentially learn implementation details (query structure, driver error text, occasionally connection-related diagnostic strings) from a 401 response body, aiding further attacks (e.g., fingerprinting the DB or crafting targeted requests) but does not by itself grant authentication bypass, privilege escalation, or fund movement. Genuine secrets such as full DB connection strings, hashed passwords, or private keys are not part of `AuthorizedUserWithSession`'s normal error paths, so the practical severity is limited to descriptive internal error text leakage rather than credential/secret disclosure — this maps to a low-severity information disclosure class rather than a high-severity secret/key exposure.

### Likelihood Explanation
No credentials or special role are required — a plain unauthenticated request to any authenticated node endpoint is sufficient to invoke the code path. However, actually triggering a non-`auth.ErrorAuthFailed` error requires the underlying data-store call to fail (DB outage, timeout, transient connectivity issue, or a data anomaly causing a scan/parse error) rather than the common "no such session/user" case, which is already normalized to `auth.ErrorAuthFailed`. This makes it opportunistic/intermittent rather than reliably reproducible on demand by an attacker with no other access.

### Recommendation
In `jsonAPIError` (or in `Authenticate`/`AuthenticateBySession`/`AuthenticateByToken`), never surface the raw underlying error text for authentication failures. Log the original error server-side and always return a generic message (e.g. "unauthorized") to the client unless the error is explicitly a recognized, safe-to-display type such as `*models.JSONAPIErrors`. Concretely, wrap/normalize any error that isn't `auth.ErrorAuthFailed` to a fixed sentinel before it reaches `jsonAPIError` in `core/web/auth/auth.go`.

### Proof of Concept
1. In `core/web/auth/auth_test.go`, create a mock `Authenticator` (`sessions/mocks` already exists) whose `AuthorizedUserWithSession` returns a raw error, e.g. `errors.New("pq: dial tcp 10.0.0.5:5432: connect: connection refused")`.
2. Build a gin router with the `Authenticate(store, AuthenticateBySession)` middleware wrapping a no-op handler.
3. Send a request with a session cookie set (so `AuthenticateBySession` reaches the `AuthorizedUserWithSession` call) but no valid session.
4. Assert the HTTP response status is 401 and parse the JSON body; assert that the error message field does **not** contain the raw driver string ("pq:", "connect:", host/IP, etc.) and instead equals a generic constant message.
5. Repeat for `AuthenticateByToken` using a mock `FindUserByAPIToken` that returns a non-`sql.ErrNoRows` error, asserting the same generic-message expectation.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
