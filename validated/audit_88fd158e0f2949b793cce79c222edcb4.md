### Title
Legacy gateway requests bypass DON sender allowlisting due to missing authorization check in `msg.Validate()` and `HandleLegacyUserMessage` - ([File: core/services/gateway/gateway.go])

### Summary
`gateway.ProcessRequest`'s legacy-request branch only calls `msg.Validate()`, which verifies message format and that *some* valid ECDSA signature exists, then looks up the handler purely by `Body.DonId` string. It never checks whether the recovered `Sender` (via `ExtractSigner`) is registered or allowlisted for that DON, and the downstream capabilities `HandleLegacyUserMessage` handler has an explicit unimplemented TODO for this check, so any self-signed key can address requests to any real DON handler.

### Finding Description
In `core/services/gateway/gateway.go`, when a legacy request (non-empty `Body.DonId`) arrives, `ProcessRequest` does: [1](#0-0) 
It calls `msg.Validate()` and, if it passes, uses `msg.Body.DonId` directly as `handlerKey` to fetch `h, ok = g.handlers[handlerKey]` — no sender-to-DON authorization check is performed here.

`Message.Validate()` in `core/services/gateway/api/message.go` only checks field lengths/format and that `ExtractSigner()` succeeds (i.e., the signature is cryptographically valid for *some* recoverable address), then sets `m.Body.Sender` to that recovered address: [2](#0-1) 
It does not verify the recovered Sender against any per-DON allowlist/registration — any freshly generated key can self-sign a message with an arbitrary `Body.DonId` set to a real, existing handler key.

The request is then routed to `h.HandleLegacyUserMessage(ctx, msg, callback)`. For the capabilities handler (the primary legacy-message handler, used e.g. for workflow triggers), the implementation explicitly defers sender authorization: [3](#0-2) 
This TODO is confirmed by the handler's own test suite, which documents the gap as unresolved: [4](#0-3) 

So the full path — signature format check → DonId string lookup → handler dispatch — never verifies that the Sender is a member of, or allowlisted for, the target DON. Any attacker holding an arbitrary private key can sign a message naming any live `don_id` and have it accepted and forwarded to all DON member nodes as a legitimate trigger request.

### Impact Explanation
This allows request impersonation / allowlist bypass: an unauthenticated/unprivileged attacker can inject workflow trigger requests (`MethodWebAPITrigger`) into any configured DON's handler without being a registered/allowlisted sender for that DON, since only cryptographic-signature-format validity (not sender authorization) gates routing. This falls under Chainlink's "unauthorized job run" / authorization bypass impact class, since it can trigger workflow executions on a DON the attacker was never granted access to.

### Likelihood Explanation
Feasibility is high: the attacker only needs any ECDSA keypair (no registration, no allowlisting, no special role) and knowledge of a target `don_id` string, which is often not secret (referenced in configs/docs or discoverable via `UnsupportedDONIdError` messages that leak valid vs. invalid DON IDs, see `core/services/gateway/gateway.go:260`). This is fully reproducible and repeatable — no race conditions or privileged state required.

### Recommendation
Enforce sender-to-DON authorization before or immediately after `msg.Validate()` in `gateway.ProcessRequest`, or inside each handler's `HandleLegacyUserMessage`, by checking the recovered `msg.Body.Sender` against the DON's configured/allowlisted node or workflow-owner set before dispatching, matching the intent of the still-open TODO in `core/services/gateway/handlers/capabilities/handler.go:384`.

### Proof of Concept
Table test in `core/services/gateway/gateway_test.go`:
1. Set up a gateway with a real `handlers[testDON]` (capabilities handler) as in `TestGateway_LegacyRequest_HandlerResponse`.
2. Generate a fresh, never-registered/never-allowlisted ECDSA key `attackerKey`.
3. Build `msg := &api.Message{Body: api.MessageBody{MessageId: "x", Method: MethodWebAPITrigger, DonId: "testDON", Payload: validTriggerPayload}}`, call `msg.Sign(attackerKey)`.
4. Call `gw.ProcessRequest(ctx, encode(msg), "")`.
5. Assert the handler's `HandleLegacyUserMessage` is invoked and returns a successful/forwarded response (via mocked `don.SendToNode`) rather than an authorization error — demonstrating that `msg.Validate()` and the handler accept any signer for an existing DON ID with no allowlist enforcement.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
