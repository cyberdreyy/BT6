### Title
Node URLs (WSURL/HTTPURL) containing embedded RPC provider API keys are exposed to view-role users via GET /v2/chains/:network/:ID/nodes - ([File: core/web/router.go], [File: core/web/nodes_controller.go], [File: core/web/presenters/chain.go])

### Summary
The `chains.GET("/:network/:ID/nodes", paginatedRequest(nodesController.Index))` route is registered on the `authv2` group without any `auth.RequiresEditRole`/`auth.RequiresAdminRole` wrapper, so it is reachable by any authenticated user including `view` role. The response is built via `presenters.NewNodeResource`, whose `Config` field is the raw TOML node configuration (including `WSURL`/`HTTPURL`), with no redaction applied.

### Finding Description
`nodesController.Index` (`core/web/nodes_controller.go` lines 44-79) fetches `types.NodeStatus` from relayers and converts each into a `presenters.NodeResource` via `newResource`, which is bound to `presenters.NewNodeResource`. That function copies `node.Config` verbatim into the JSON-serialized `Config` field: [1](#0-0) 
The `node.Config` string is the full TOML block for the node, which includes `WSURL` and `HTTPURL` as plain fields (confirmed by the reference test output showing `Config: Name = 'Blue' WSURL = 'wss://primaryfoo.bar/ws' HTTPURL = 'https://primaryfoo.bar' ...`): [2](#0-1) 
No redaction step strips API keys or credentials embedded in these URLs (e.g. `https://mainnet.infura.io/v3/<API_KEY>` style RPC endpoints) before they are serialized into the resource.

On the routing side, the nodes route is grouped only under the base `authv2` authentication gate (session or token), with no role-based wrapper applied, unlike mutating endpoints elsewhere in the same file that explicitly call `auth.RequiresEditRole`/`auth.RequiresAdminRole`: [3](#0-2) 
Because `RequiresEditRole`/`RequiresAdminRole`/`RequiresRunRole` are the only role gates in the codebase (`core/web/auth/auth.go` lines 202-255), and none of them is applied to this GET route, a `view`-role authenticated user passes straight through to `nodesController.Index` and receives the unredacted `Config` string containing the node's WSURL/HTTPURL.

### Impact Explanation
A `view`-role user (the lowest privilege authenticated role) can retrieve the full RPC endpoint URLs for any chain's nodes, including any API keys embedded in those URLs (common for hosted RPC providers). This is a credential/secret disclosure to an under-privileged authenticated principal — matching Chainlink's "sensitive data exposure / secret leakage" bounty impact class. An attacker with only view-level credentials could use the leaked provider API key to impersonate the node's RPC access, incur costs against the victim's RPC provider account, or use it as a pivot for further reconnaissance.

### Likelihood Explanation
Exploitation requires only a valid `view`-role session or API token — the lowest authenticated privilege tier in the system — and a single unauthenticated-role-check GET request. No additional bypass, timing, or race condition is needed; this is deterministic and repeatable on every request as long as the operator's node config uses a key-bearing RPC URL (a common real-world configuration pattern).

### Recommendation
Either (a) restrict `chains.GET("/:network/:ID/nodes")` (and the sibling `nodes.GET("")`/`nodes.GET("/:network")`) to `auth.RequiresEditRole` or `auth.RequiresAdminRole`, or (b) redact secrets from the `Config`/URL fields in `presenters.NewNodeResource` before serialization (e.g., strip userinfo/query-string credentials from WSURL/HTTPURL, or omit `Config` entirely for `view`-role responses), consistent with how other credential-bearing presenters redact secrets.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, following existing patterns in `core/web/presenters/node_test.go` and `core/cmd/node_commands_test.go`):
1. Configure an EVM chain with a node whose `HTTPURL`/`WSURL` embeds an API key, e.g. `https://mainnet.example.com/v3/SECRET_API_KEY`.
2. Start the test application/router with a `view`-role session or API token (using existing `cltest` helpers for creating a view-role authenticated client).
3. Issue `GET /v2/chains/evm/<chainID>/nodes` using the view-role client.
4. Assert HTTP 200 (not 401/403), then parse the JSON:API response and assert that `data[].attributes.config` contains the literal string `SECRET_API_KEY` — proving the raw URL/API key reaches the view-role response instead of being redacted or rejected by a role check.
