### Title
Token masking (`tokenSanitizer.Write`) terminates on the first byte outside its hardcoded `alphabet` bitmap and flushes the remainder of the secret unmasked - (`common/buildlogger/internal/tokensanitizer/token_masker.go`)

### Summary
`tokenSanitizer.Write` treats any character not present in the hardcoded `alphabet` table as the end of a token and immediately emits `[MASKED]` for the bytes matched so far, then resumes unmasked scanning from that exact byte. If the real secret being printed legitimately contains a character outside this fixed alphabet (e.g. standard base64 `+`/`/`, or any charset used by a custom `TokenMaskPrefixes` entry), the tail of the secret is written to the trace in cleartext instead of being masked.

### Finding Description
In `tokenSanitizer.Write` (`common/buildlogger/internal/tokensanitizer/token_masker.go:104-203`), once the prefix has fully matched (`m.matching == len(m.prefix)`), each subsequent byte is checked against the fixed `alphabet` bitmap: [1](#0-0) 
The `alphabet` bitmap only allows `0-9`, `A-Z`, `a-z`, `-`, `.`, `_`, `=`: [2](#0-1) 
As soon as a byte outside this set is seen, `m.masked` is flushed to `[MASKED]`, `m.matching` resets to `0`, and the writer immediately restarts an `IndexByte` search for the prefix's first byte starting **at that same offending byte**: [3](#0-2) 
If the prefix's first character is not found again before the end of the write buffer, all of `p[last:n]` — including the offending byte and every byte after it — is written to the next writer completely unmodified: [4](#0-3) 
This is a hard "one strike and you're out" boundary: the sanitizer never resumes masking mid-secret after a non-alphabet byte, it only looks for a brand-new prefix occurrence. If the trailing bytes are still part of the same real secret (not a coincidental new prefix occurrence), they leak verbatim.

The critical question is whether a *real* protected secret can legitimately contain a byte outside this alphabet. It can: `tokensanitizer` is used not only for the fixed `glpat-`/`gloas-`/etc. GitLab-issued token formats, but also for job-configurable `Features.TokenMaskPrefixes`, wired in via `getNewLogger`: [5](#0-4) 
and exercised in tests with arbitrary custom prefixes/tokens such as `mytoken:` and `foobar-`: [6](#0-5) 
Additionally, the built-in `_gitlab_session=` prefix is meant to catch Rails/Rack session cookie values, which are typically standard base64 (using `+` and `/`), neither of which is in the `alphabet` table (only `=` padding is included): [7](#0-6) 
So any legitimate secret matched by this heuristic masker whose real encoding uses characters outside `-._=` and alphanumerics (standard base64 `+`/`/`, or any characters used by a custom prefix's token format) will have its tail flushed in cleartext the moment such a character appears, exactly matching the failure mode described in the question — independent of whether the "boundary" byte is attacker-injected or is simply a legitimate character of the real secret's own encoding.

Contrast this with the general-purpose exact-value `masker` package used for `MaskPhrases` (job `Masked` variables), which matches arbitrary byte sequences with no such alphabet restriction: [8](#0-7) 
`tokenSanitizer` provides no equivalent fallback/backstop; it is a pure heuristic scanner with a fixed, incomplete charset.

### Impact Explanation
Any secret whose value happens to be picked up by the prefix+alphabet heuristic (default GitLab token prefixes, or job-configured `TokenMaskPrefixes`) but whose actual content includes a character outside `[A-Za-z0-9\-._=]` will only be partially masked in the job trace: the portion before the offending character becomes `[MASKED]`, but everything after it (up to the next prefix-start byte or end of buffer) is written to the trace unmodified. This exposes the tail of a token/secret to anyone with read access to the job log — a scoped log-sanitization bypass leaking protected credential material.

### Likelihood Explanation
No special privileges are required. A pipeline author who controls job scripts can:
- Print HTTP response headers/cookies (e.g. via `curl -v`) that include a `_gitlab_session=` value containing standard base64 `+`/`/` characters, or
- Use a custom `TokenMaskPrefixes` entry (a supported Runner/job feature) for a secret whose real format includes characters outside the fixed alphabet.

In both cases the byte causing early termination is a normal, expected character of the secret's real encoding, not a contrived/invalid byte — making this readily reachable in ordinary job output, not just a crafted edge case.

### Recommendation
Either (a) make the "end of token" detection resilient to characters that occur inside the real target token's encoding by expanding `alphabet` to cover standard base64 (`+`, `/`) and any charset used by supported/custom prefixes, or (b) change the masking behavior on early termination so that instead of resetting to a fresh `IndexByte` scan from the terminating byte, it continues attempting a bounded look-ahead for possible token continuation (or conservatively masks a fixed-width tail) rather than unconditionally flushing all subsequent unmatched bytes verbatim.

### Proof of Concept
Add to `common/buildlogger/internal/tokensanitizer/token_masker_test.go`:
```go
func TestTokenMasking_NonAlphabetByteLeaksTail(t *testing.T) {
    buf := new(bytes.Buffer)
    m := New(internal.NewNopCloser(buf), internal.Unique([]string{"_gitlab_session="}))

    // realistic base64 session cookie value containing '+' and '/'
    input := "Set-Cookie: _gitlab_session=abcDEF012+xyz/moreSecretTail=="
    n, err := m.Write([]byte(input))
    require.NoError(t, err)
    require.Equal(t, len(input), n)
    require.NoError(t, m.Close())

    out := buf.String()
    // Expect full masking of the token value
    assert.NotContains(t, out, "xyz/moreSecretTail")
    assert.Contains(t, out, "_gitlab_session=[MASKED]")
}
```
Running this against current `token_masker.go` fails: the output contains `_gitlab_session=[MASKED]+xyz/moreSecretTail==`, i.e. the `+xyz/moreSecretTail==` tail of the session token leaks in cleartext, confirming the bug.

```go
func (m *masker) Write(p []byte) (n int, err error) {
	if len(p) == 0 {
		return 0, nil
	}

	// fast path: if the write is "[MASKED]" from an upper-level, don't bother
	// processing it, send it to the next writer.
	if bytes.Equal(p, mask) {
		return m.next.Write(p)
	}

	var last int
	for n < len(p) {
		// optimization: use the faster IndexByte to jump to the start of a
		// potential phrase and if not found, advance the whole buffer.
		if m.matching == 0 {
			off := bytes.IndexByte(p[n:], m.phrase[0])
			if off < 0 {
				n += len(p[n:])
				break
			}
			if off > -1 {
				n += off
			}
		}

		// find out how much data we can match: the minimum of len(p) and the
		// remainder of the phrase.
		min := len(m.phrase[m.matching:])
		if len(p[n:]) < min {
			min = len(p[n:])
		}

		// try to match the next part of the phrase
		if bytes.HasPrefix(p[n:], m.phrase[m.matching:m.matching+min]) {
			// send any data that we've not sent prior to our match to the
			// next writer.
			_, err = m.next.Write(p[last:n])
			if err != nil {
				return n, err
			}

			m.matching += min
			n += min
			last = n

			// if we've tracked each byte of our phrase, we can replace it
			if m.matching == len(m.phrase) {
				_, err := m.Write(mask)
				if err != nil {
					return n, err
				}
				m.matching = 0
			}

			continue
		}

		// if we didn't complete a phrase match, send the tracked bytes of
		// the phrase to the next writer unmodified.
		if m.matching > 0 {
			_, err = m.next.Write(m.phrase[:m.matching])
			if err != nil {
				return n, err
			}

			// if the end of this phrase matches the start of it, try again
			if m.phrase[0] == p[n] {
				m.matching = 1
				last++
				n++
				continue
			}
		}
		m.matching = 0

		n++
	}
```
