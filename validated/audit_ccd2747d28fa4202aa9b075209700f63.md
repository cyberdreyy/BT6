### Title
RequiresAdminRole leaks session validity and account email via forbidden-* headers to any low-privileged authenticated caller - ([File: core/web/auth/auth.go])

### Summary
`RequiresAdminRole` responds with `403 Forbidden` plus `forbidden-required-role`, `forbidden-provided-role`, and `forbidden-provided-email` headers whenever a request carries a *valid* session/token that is not admin, while any invalid/missing credential is rejected earlier by `Authenticate` with a generic `401` and no headers. This status/header difference lets a holder of a candidate cookie determine whether it belongs to a live account (and that account's role and email) without needing valid admin credentials.

### Finding Description
Routes wrapped with `RequiresAdminRole` first pass through the `Authenticate` middleware [1](#0-0) , which tries `AuthenticateBySession`/`AuthenticateByToken`/etc. and aborts the request with `401` and a generic JSON error if none succeed - no forbidden headers are set in this path [2](#0-1) .

If authentication succeeds (i.e., the cookie/token maps to a real, non-expired user via `AuthorizedUserWithSession`/`FindUserByAPIToken`), the user is stored in the gin context via `c.Set(SessionUserKey, &user)` [3](#0-2) . Control then reaches `RequiresAdminRole`, which calls `GetAuthenticatedUser` (now returning `ok=true`), checks `user.Role != clsessions.UserRoleAdmin`, and if the role isn't admin, calls `addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)` before returning `403` [4](#0-3) . That helper sets three response headers directly disclosing the required role, the caller's actual role, and the caller's email address [5](#0-4) .

The net effect: `401` + no headers means "the credential is not valid/live"; `403` + `forbidden-provided-role`/`forbidden-provided-email` headers means "the credential is valid and belongs to a live account with that email/role." This is a clean session/credential validity oracle, and additionally discloses the victim account's email address to whoever is holding (or has guessed) the cookie/token — information the attacker would not otherwise be entitled to see, since a stolen/guessed low-privilege session cookie does not by itself imply knowledge of the associated account's email.

### Impact Explanation
This is an information-disclosure issue: it provides (1) an oracle to distinguish invalid vs. valid-but-low-privileged session cookies/API tokens (useful to triage brute-forced or intercepted session identifiers), and (2) direct disclosure of the account email tied to a captured/guessed credential via HTTP response headers. It does not by itself grant privilege escalation or admin access — `RequiresAdminRole` still correctly blocks the request with `403`. The impact is limited to reconnaissance value for an attacker already in possession of a stolen or brute-forced session artifact, not authentication bypass.

### Likelihood Explanation
Requires the attacker to already possess a candidate session cookie or API key/secret pair of unknown validity (e.g., obtained via network capture, log leakage, or a low-effort guess), and requires the node operator to expose an admin-only route. Given that precondition, the technique is trivial and fully repeatable: a single HTTP request per candidate credential against any admin-gated endpoint (see the many `RequiresAdminRole`-wrapped routes registered in `core/web/router.go`) is enough to classify it.

### Recommendation
Do not include `forbidden-provided-email` (and arguably `forbidden-provided-role`) in the `403` response for role-mismatch failures; these values are only useful to a legitimate, already-authenticated client debugging its own request, not to a third party holding a possibly-stolen credential. At minimum, omit the email header, and consider returning a uniform `403`/`401` without role/email details, or logging the details server-side instead of returning them in headers.

### Proof of Concept
Go handler-level test in `core/web/auth` (or `core/web` using `web.Router`):
1. Set up three request cases against a `RequiresAdminRole`-wrapped test route:
   - (a) No `clsession` cookie / no `X-API-KEY`/`X-API-SECRET` headers.
   - (b) A cookie/token that does not map to any user (invalid).
   - (c) A valid, persisted session/API token for a user with `Role: clsessions.UserRoleView`.
2. Assert (a) and (b) both return `http.StatusUnauthorized` with no `forbidden-*` headers present.
3. Assert (c) returns `http.StatusForbidden` and that `resp.Header.Get("forbidden-provided-role")=="view"` and `resp.Header.Get("forbidden-provided-email")` equals the test user's email.
4. Document that (a)/(b) are indistinguishable from each other but distinguishable from (c) purely by status code and header presence, confirming the oracle and email disclosure.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
```

func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
```

func addForbiddenErrorHeaders(c *gin.Context, requiredRole string, providedRole string, providedEmail string) {
	c.Header("forbidden-required-role", requiredRole)
	c.Header("forbidden-provided-role", providedRole)
	c.Header("forbidden-provided-email", providedEmail)
}
