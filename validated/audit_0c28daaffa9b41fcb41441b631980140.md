### Title
v1 `validate_tenure_change_payload` uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, letting a v1 signer sign a duplicate tenure-start block a v2 signer would reject - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`v1::validate_tenure_change_payload`'s duplicate-tenure-start guard queries `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`, which returns `None` for any block that is only `LocallyAccepted` (signed by the local signer, or a minority, but not yet a 70% threshold). The `v2` implementation of the identical check was fixed to use `get_last_signed_block`, which additionally covers `LocallyAccepted` blocks, specifically to close this exact gap (see the regression test `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs`). `v1` never received the equivalent fix.

### Finding Description
The equality that must hold is: "the set of blocks counted as already-signed/committed in a tenure for the `DuplicateBlockFound` check must be identical regardless of which signer's chainstate implementation (`v1` or `v2`) evaluates the proposal." This equality is broken.

- `v1::validate_tenure_change_payload` ( [1](#0-0) ) checks `get_last_globally_accepted_block`, which only matches blocks in `BlockState::GloballyAccepted` ( [2](#0-1) -style state filtering, contrast with the `GloballyAccepted`-only query used at line 505-506).
- `v2::validate_tenure_change_payload` checks `get_last_signed_block`, which matches both `GloballyAccepted` and `LocallyAccepted` states ( [3](#0-2)  and [4](#0-3) ).

Root cause: a v1 signer that has locally signed (`LocallyAccepted`) a tenure-start block for tenure `T` — because it individually approved it but the 70% global threshold has not yet been reached — has already put a real signature on a block for `T`. When a second, conflicting tenure-start proposal for the same tenure `T` arrives (same `tenure_consensus_hash`/`consensus_hash`, different content, e.g. a miner or attacker resubmitting a modified tenure-change+coinbase block), the v1 signer's `get_last_globally_accepted_block` lookup returns `None` because the first block hasn't reached global acceptance, so the `DuplicateBlockFound` guard is skipped and the check passes. A v2 signer evaluating the same second proposal correctly finds the `LocallyAccepted` block via `get_last_signed_block` and rejects with `DuplicateBlockFound`.

Attacker action: an attacker who wins a single miner slot can craft two competing tenure-change+coinbase `BlockProposal`s for the same tenure and broadcast the second one before the first reaches 70% global acceptance. No majority of signers, no auth token, and no local access is required — only a miner slot and the ability to gossip a `BlockProposal`. This exactly matches the scenario the v2 regression test (`check_tenure_change_rejects_when_locally_accepted_block_exists`, `stacks-signer/src/chainstate/tests/v2.rs:756-850`) was written to prevent, and confirms the underlying class of bug is understood and previously fixed — only in `v2`, not `v1`.

Because `SortitionStateVersion::from_protocol_version` selects `v1` for any signer negotiating a protocol version below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION` (2) ( [5](#0-4) ), this is not dead code: mixed-version rollouts and version-downgrade scenarios are explicitly exercised in test infrastructure (`stacks-node/src/tests/signer/multiversion.rs`, `stacks-node/src/tests/signer/v0/mod.rs::downgrade_signer_protocol_version`), confirming v1 chainstate logic runs in live multi-version signer sets.

### Impact Explanation
This breaks the **UNIQUENESS** safety property: a single signer can be induced to place a valid signature on two conflicting tenure-change ("tenure-start") blocks for the same tenure. In a mixed v1/v2 signer set, v1 signers may sign the duplicate while v2 signers correctly refuse, producing divergent, non-overlapping signature sets across the signer population for competing blocks in the same tenure — a chain-safety violation matching the "Critical: signer signing an invalid/conflicting block (UNIQUENESS)" category. The exploit is repeatable against every v1-negotiated signer independently, for any tenure, as long as the first block hasn't yet globally settled.

### Likelihood Explanation
Preconditions: at least one signer in the active signer set is running (or has negotiated down to) protocol version 1 chainstate logic — realistic in mixed-version rollouts, which the codebase explicitly supports and tests (protocol-version negotiation via `StateMachineUpdate`/`GlobalStateEvaluator`, `downgrade_signer_protocol_version` test). The attacker needs only their own miner slot and the ability to gossip two competing `BlockProposal`s for the same tenure before the first is globally accepted — a narrow but achievable timing window during every tenure-start. It is repeatable across tenures for the lifetime of the mixed-version rollout.

### Recommendation
Change `v1::validate_tenure_change_payload`'s duplicate check (`stacks-signer/src/chainstate/v1.rs:505-506`) to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the `v2` fix, so the duplicate-tenure-start guard is consistent across chainstate versions.

### Proof of Concept
Add a Rust test analogous to the existing v2 regression test, but against the v1 path, in `stacks-signer/src/chainstate/tests/v1.rs`:
1. Set up a v1 `SortitionsView`/`SortitionState` test environment (mirroring `setup_test_environment` used in `v2.rs`).
2. Insert a `BlockInfo` for the current tenure's consensus hash and call `mark_locally_accepted(false)` on it (never `mark_globally_accepted`), then `signer_db.insert_block(&existing_block_info)`.
3. Build a second, distinct tenure-change+coinbase `NakamotoBlock` proposal for the same `consensus_hash`/tenure.
4. Call `v1::SortitionsView::check_proposal` (or directly `validate_tenure_change_payload`) on the second proposal.
5. Assert `matches!(result, Err(RejectReason::DuplicateBlockFound))` — this assertion currently **fails** (the call incorrectly returns `Ok(())`), proving v1 accepts a duplicate tenure-change block that `get_last_signed_block` (and v2) would reject.
6. As a control, add the mirrored assertion using `get_last_signed_block` directly to show it would detect the conflict that `get_last_globally_accepted_block` misses.
