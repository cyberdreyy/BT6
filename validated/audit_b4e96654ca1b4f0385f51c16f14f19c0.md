### Title
Cross-user response hijacking via predictable/attacker-chosen MessageId key collision in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`h.savedCallbacks` is keyed solely by `msg.Body.MessageId`, a value that originates from the caller-supplied JSON-RPC request ID (`ValidatedMessageFromReq` sets `m.Body.MessageId = req.ID`), with no binding to the sender's identity or DON. Any signed caller who registers a request with the same `MessageId` as a victim's in-flight request overwrites the victim's callback entry, so the first DON node response for that `MessageId` is delivered to the attacker instead of (or in a race, in place of) the legitimate requester.

### Finding Description
`HandleLegacyUserMessage` (handler.go:341-421) stores the caller's callback unconditionally: [1](#0-0) 
There is no check for an existing entry under the same key and no compound key involving `msg.Body.Sender`/`DonId` — only `msg.Body.MessageId` is used as the map key.

`handleWebAPITriggerMessage` (handler.go:148-162) later looks the callback up purely by `MessageId` and routes the first DON response there: [2](#0-1) 

Critically, `MessageId` is not gateway-generated or derived from an unforgeable value; it is taken directly from the caller's own JSON-RPC request ID: [3](#0-2) 

Because the ID is attacker-supplied and the map has no per-sender partition, an attacker who can predict or observe a victim's `MessageId` (e.g., because other call sites deterministically derive IDs from workflow ID + trigger event ID) can send their own signed request using that same `MessageId`. Since `HandleLegacyUserMessage` writes to the map unconditionally (last write wins) and `handleWebAPITriggerMessage` does not verify that the response is being routed to the same sender who registered the callback, the DON's first response for that `MessageId` is delivered to whichever caller is currently registered — potentially the attacker, hijacking a response intended for another user's workflow trigger.

### Impact Explanation
This breaks per-request isolation between unrelated callers of the same DON's gateway handler: an attacker can redirect or intercept the capability response (which may contain workflow execution data returned via the web-api trigger) intended for another user's job/workflow. This matches Chainlink's bounty impact class of cross-user data disclosure/request-response confusion at the DON gateway boundary.

### Likelihood Explanation
Exploitability requires: (1) the attacker can send a signed legacy request to the same DON handler (a normal capability of any signed gateway client, not privileged), and (2) the attacker can predict/observe the victim's `MessageId`, which per the question is plausible since ID formats are deterministic in some call sites (workflow ID + trigger event ID). No admin/operator access or protocol-level compromise is required, only knowledge of the ID-generation scheme and timing to race the registration before the DON responds — feasible and repeatable given a network position that lets the attacker fire the request quickly after observing/predicting the ID.

### Recommendation
Bind `savedCallbacks` entries to a compound key that includes `Sender` and `DonId` (or a gateway-generated random correlation ID unrelated to caller input), reject registration if an entry already exists for the same key, and verify in `handleWebAPITriggerMessage` that the DON response's originating request context matches the sender that registered the callback before returning the response.

### Proof of Concept
1. Unit/handler-integration test in `core/services/gateway/handlers/capabilities/handler_test.go`:
   - Construct a `handler` with a mock `handlers.DON`.
   - Call `HandleLegacyUserMessage` with `msg.Body.MessageId = "shared-id"` and `callback = victimCallback` (mock capturing `SendResponse` calls).
   - Before the DON responds, call `HandleLegacyUserMessage` again with the same `MessageId = "shared-id"` but `callback = attackerCallback`.
   - Simulate the DON node response by invoking `HandleNodeMessage`/`handleWebAPITriggerMessage` with `msg.Body.MessageId = "shared-id"`.
   - Assert `attackerCallback.SendResponse` was invoked and `victimCallback.SendResponse` was NOT invoked, proving the response meant for the first (victim) registrant was delivered to the attacker.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response

	}
	return nil
