## Finding: Lockup owner can supply their own malicious "whitelist" account at creation time, bypassing the staking-pool safety guarantee

This is a valid analog to the "genes are overrideable" bug class: the report's underlying issue is that a value which is *supposed to be an immutable, trust-anchored reference* (the gene implementation) is actually attacker-suppliable, breaking the binding "trusted implementation used == implementation the system was designed to trust." The same pattern exists in `lockup-factory`.

### Title
Lockup owner can bypass the staking-pool whitelist safety guarantee by supplying an attacker-controlled whitelist account at lockup creation - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` accepts an optional `whitelist_account_id` parameter directly from the caller and, if provided, uses it verbatim as the new lockup contract's `staking_pool_whitelist_account_id`, instead of always using the factory's own foundation-configured `whitelist_account_id`.

### Finding Description
The lockup system's entire staking-safety guarantee rests on the binding: "the staking pool contract that a lockup owner selects must be approved by the (foundation-controlled) whitelist contract," as documented in `lockup/README.md:81-82`: [1](#0-0) . The lockup contract itself validates this by calling `ext_whitelist::is_whitelisted` against `self.staking_pool_whitelist_account_id` before accepting a staking pool selection: [2](#0-1) .

However, `LockupFactory::create()` lets **any caller** (no `assert_called_by_foundation` check, no owner check) override the whitelist account that gets baked into the newly-deployed lockup contract: [3](#0-2) 

Only account-ID format validity is checked (`ValidAccountId`); there is no restriction that `whitelist_account_id` must equal the factory's canonical, foundation-vetted whitelist. The resulting `staking_pool_whitelist_account_id` is passed straight into the deployed lockup's `new()` and stored as-is: [4](#0-3) .

This is structurally identical to the gene bug: a value that the protocol's guarantees assume is fixed to a trusted authority (the whitelist / the gene) is instead settable per-instance by an unprivileged party at (or after) creation time, so "trusting this whitelist" and "trusting whatever the caller passed in" become indistinguishable. The existing test suite even demonstrates this is an intended, unrestricted code path (`test_create_lockup_with_custom_whitelist_success`), with no privileged-caller assertion: [5](#0-4) .

### Impact Explanation
The person paying for/creating the lockup (typically the future owner) can deploy their own "whitelist" contract that unconditionally returns `is_whitelisted = true`, then point `create()`'s `whitelist_account_id` at it. Their lockup contract will then accept `select_staking_pool` for a fully attacker-controlled "staking pool" contract, which is not required to implement the safe staking-pool spec at all. Once `deposit_and_stake` moves locked/unvested NEAR into that malicious pool, the pool contract (controlled by the owner) can immediately transfer those funds anywhere, completely circumventing the lockup/vesting timelock that is supposed to keep them locked until `lockup_timestamp`/`release_duration`/vesting completion. This breaks the documented guarantee "The owner can not withdraw tokens locked due to lockup period, disabled transfers, or vesting schedule" (`lockup/README.md:105`), matching the Critical impact category "locked or unvested tokens released early" / "a wrongly whitelisted or wrongly parameterised deployment."

### Likelihood Explanation
High likelihood: `create()` is a public, unprivileged, payable method; no special role is required to supply `whitelist_account_id`, and deploying a trivial "always whitelisted" contract plus a "steal on deposit" pool contract requires no special access, only the standard attached deposit for lockup creation.

### Recommendation
Remove the caller-suppliable `whitelist_account_id` override in `LockupFactory::create()` (or restrict it to be settable only by the foundation account), and always use the factory's own immutable, foundation-configured `whitelist_account_id` when constructing `LockupArgs`.

### Proof of Concept
1. Attacker deploys `FakeWhitelist` contract exposing `is_whitelisted` that always returns `true`.
2. Attacker deploys `MaliciousStakingPool` contract mimicking the staking-pool interface for `deposit_and_stake`, but on receiving funds simply forwards/keeps them for the attacker instead of implementing safe stake/unstake/withdraw semantics.
3. Attacker calls `lockup-factory::create(owner_account_id=attacker, ..., whitelist_account_id=Some(FakeWhitelist))`, per `lockup-factory/src/lib.rs:107-133`.
4. As owner, attacker calls `select_staking_pool(MaliciousStakingPool)` on their new lockup (`lockup/src/owner.rs:12-41`) — it passes because `FakeWhitelist.is_whitelisted` always returns true.
5. Attacker calls `deposit_and_stake` to move locked/unvested NEAR into `MaliciousStakingPool`, which is not obligated to ever return the funds — the lockup's timelock/vesting is bypassed.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

    #[init]
    pub fn new(
        owner_account_id: AccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        transfers_information: TransfersInformation,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        staking_pool_whitelist_account_id: AccountId,
        foundation_account_id: Option<AccountId>,
    ) -> Self {
        assert!(
            env::is_valid_account_id(owner_account_id.as_bytes()),
            "The account ID of the owner is invalid"
        );
        assert!(
            env::is_valid_account_id(staking_pool_whitelist_account_id.as_bytes()),
            "The staking pool whitelist account ID is invalid"
        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,
        } = &transfers_information
        {
            assert!(
                env::is_valid_account_id(transfer_poll_account_id.as_bytes()),
                "The transfer poll account ID is invalid"
            );
        }
        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,
            release_duration: release_duration.map(|d| d.0),
            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {
            None => {
                assert!(
                    foundation_account_id.is_none(),
                    "Foundation account can't be added without vesting schedule"
                );
                VestingInformation::None
            }
            Some(VestingScheduleOrHash::VestingHash(hash)) => VestingInformation::VestingHash(hash),
            Some(VestingScheduleOrHash::VestingSchedule(vs)) => {
                VestingInformation::VestingSchedule(vs)
            }
        };
        assert!(
            vesting_information == VestingInformation::None ||
                env::is_valid_account_id(foundation_account_id.as_ref().unwrap().as_bytes()),
            "Foundation account should be added for vesting schedule"
        );

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
