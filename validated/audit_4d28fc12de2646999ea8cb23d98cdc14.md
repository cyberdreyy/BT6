### Title
BB tranche holder escapes BB-first loss waterfall by frontrunning an honest `stopEpochWithDuration` loss call with a withdraw request — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The oracle-quorum bug class is: an honest privileged actor changes a parameter (quorum/loss amount), and an unprivileged party observes the pending transaction and re-orders their own state-dependent action so the new parameter resolves favorably for them. In `IdleCreditVault` / `IdleCDOEpochVariant`, the manager's honest `stopEpochWithDuration(_lossAmount)` call is the analog of a quorum change, and a BB tranche holder's `requestWithdraw` is the analog of an oracle member's deciding vote. Converting an active BB position into a pending-withdraw receipt before the loss is applied moves the position from the BB-first active waterfall into the pro-rata pending-receipt bucket, diluting the BB holder's loss across `pendingWithdraws`.

### Finding Description
`stopEpochWithDuration` splits a realized loss between active LPs and pending withdraw receipts via `previewLossAdjustedWithdrawFunds`: `pendingLoss = _lossAmount * pendingBasis / totalBasis`, `activeLoss = _lossAmount - pendingLoss`, and the funded pending amount is `pendingToFund = pendingBasis - pendingLoss` (contracts/strategies/idle/IdleCreditVault.sol:440-460). The haircut for pending receipts is stored per epoch as `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` inside `collectWithdrawFunds` (lines 411-421), i.e. every pending receipt in that bucket shares the pending loss pro rata.

The `activeLoss` remainder, by contrast, is applied to active tranche positions through the ordinary IdleCDO BB-first waterfall: BB NAV absorbs the loss before AA. So the same nominal exposure suffers a materially different haircut depending on which bucket it sits in at the moment `stopEpochWithDuration` executes:

- As an **active BB** position: the loss hits BB NAV first; a BB holder can lose up to 100% of their position while AA remains whole.
- As a **pending receipt**: the position takes only `lossRecoveryPriceByEpoch` haircut — a share diluted across the whole `pendingWithdraws` bucket — regardless of tranche seniority. Receipt accounting is explicitly aggregate and "does not retain tranche identity" (line 436 comment).

`requestWithdraw` (lines 243-295) has no check that the vault is not about to be stopped: it only reverts on post-default double requests, an unclaimed loss-adjusted receipt, or closed-pool edge cases. `epochEndDate == 0` merely changes accounting (no `pendingWithdraws` increment); during a running epoch a request entered in the same block as — and immediately before — the manager's `stopEpochWithDuration` call joins `pendingBasis` and is haircut at `lossRecoveryPrice` instead of the BB-first waterfall.

### Impact Explanation
Broken invariant: **BB-first loss waterfall**. BB exists to absorb losses before AA; this is the core tranche guarantee. A BB holder who frontruns an honest loss realization converts a position that should bear up to 100% of `activeLoss` into one bearing only `pendingLoss * (theirReceipt / pendingBasis)`, where `pendingLoss = _lossAmount * pendingBasis / totalBasis`. Concretely, with `pendingBasis` ≈ `activeBasis`, a 50% loss means the pending bucket takes ~25% haircut while an active BB takes up to 100%. The escaped loss is pushed onto remaining BB and then AA holders and onto other pending receipts. Loss is quantified: up to `activeLossBBS` minus the pro-rata pending share, capped by the attacker's BB position.

### Likelihood Explanation
Requirements: (1) the attacker holds BB tranche tokens (a KYC-passing lender, in scope); (2) the manager submits `stopEpochWithDuration(_lossAmount)` — an honest privileged call, in scope; (3) the mempool exposes `_lossAmount`, or the attacker infers the loss from public borrower state (e.g. defaulted loan visible on-chain, missed repayment). A normal withdraw request is a routine lender action, not an anomalous privilege, so the frontrun is a standard gas-bid ordering. The caveat: this requires the loss transaction to be observable/exploitable in the window before `stopEpoch` commits `epochNumber`/`lossRecoveryPriceByEpoch` — after `stopEpoch` increments `epochNumber`, a new request lands in the next epoch and does not dodge the haircut. This matches the report's narrow "backrun the admin's parameter change" window.

### Recommendation
Adopt the same fix pattern as the oracle report (clear volatile state / make the parameter change atomic):

1. Snapshot `pendingWithdraws` at a point the attacker cannot race — e.g. compute the loss split using `pendingBasis` as of the epoch-end boundary rather than the mutable value at `stopEpoch` execution, or block `requestWithdraw` once `block.timestamp >= epochEndDate` (i.e. after the epoch nominally ended but before `stopEpoch` is executed).
2. Alternatively, preserve tranche identity in pending receipts so a converted BB receipt continues to absorb losses BB-first instead of sharing the aggregate pending haircut pro rata.
3. As a mitigation consistent with the report's recommendation, document and enforce the invariant off-chain: a loss realization must not accept same-epoch requests created after the loss became knowable.

    IdleCDOEpochVariant cdo;      // deployed via factory/initialize per test suite

    address manager = address(0xM);
    address borrower = address(0xB);
    address attackerBB = address(0xA11);

        underlying = new MockUnderlying();
        // Deploy + initialize IdleCDOEpochVariant and IdleCreditVault:
        // vault.initialize(underlying, owner, manager, borrower, "X", 0);
        // cdo initialized with AA/BB tranches, strategy = vault
        underlying.mint(attackerBB, 1_000_000e6);
        underlying.mint(passiveLP, 1_000_000e6);
    }

    function testBBEscapesLossViaPendingBucket() public {
        // --- Epoch running phase ---
        // attackerBB deposits into BB tranche, passiveLP deposits AA + BB.
        // A pre-existing pending withdraw queue exists (other users requested
        // withdraw earlier in the epoch), so pendingBasis > 0.

        uint256 bbNavBefore = cdo.tranchePrice(cdo.BBTranche());
        uint256 lossAmount = /* realized loss manager will apply */;

        // --- Attacker observes manager's pending tx ---
        // Mempool shows: cdo.stopEpochWithDuration(interest, lossAmount)
        // Attacker frontruns:
        vm.prank(attackerBB);
        cdo.requestWithdraw(attackerBBBalance, attackerBB); // joins pendingWithdraws

        // --- Honest manager call lands ---
        vm.prank(manager);
        cdo.stopEpochWithDuration(0, lossAmount);

        uint256 lossPrice = vault.lossRecoveryPriceByEpoch(vault.epochNumber());

        // Attacker's receipt is haircut by lossPrice (pro-rata across the whole
        // pending bucket), NOT by the BB-first waterfall. Assert escaped loss:
        //   haircutPending = 1e18 - lossPrice            // e.g. ~25%
        //   haircutBB      = 1 - bbNavAfter/bbNavBefore  // up to 100%
        assertLt(1e18 - lossPrice, /* BB waterfall haircut, e.g. up to 1e18 */);

        // Attacker claims diluted recovery while honest BB holders ate the full loss.
        vm.prank(attackerBB);
        cdo.claimWithdrawRequest();

    }
}

**Note on verification limits:** I was able to fully trace the strategy-side mechanics in `IdleCreditVault.sol` (the pending-vs-active pro-rata split in `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` and the gate-free `requestWithdraw`), but could not re-read `IdleCDOEpochVariant.sol` within the tool-call budget to confirm that `requestWithdraw` is callable in the exact window between the loss becoming knowable and `stopEpochWithDuration` executing (e.g. no `epochEndDate`-vs-`block.timestamp` cutoff). If the CDO already blocks withdraw requests after `epochEndDate` passes, the attack window shrinks to requests made before epoch end based on advance knowledge of an upcoming loss call — a weaker but still valid ordering exploit. A Foundry fork PoC pinning a deployed vault and replaying the sequence above is required to confirm the window exists.
