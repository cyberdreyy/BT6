### Title
Stale confirmations from removed multisig members allow request execution below the configured threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges pending requests and confirmations for requests *created by* the member being removed, but never scans other pending requests for confirmations *cast by* that member. `confirm()` later counts confirmations purely by set size (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without re-validating that every confirming identity is still a current member. This lets a stale confirmation from a removed member count toward the threshold, so a request can execute with fewer live, currently-authorized confirmers than `num_confirmations` requires.

### Finding Description
`confirm()` binds authorization to a request purely via the `confirmations: LookupMap<RequestId, HashSet<String>>` set: [1](#0-0) 

When a request is created (`add_request`), a member confirms it, and the confirmation is only ever removed by `remove_request` (on execution or deletion) or by `delete_member`, but `delete_member` scopes its cleanup only to requests whose *creator* (`r.member`) equals the member being removed: [2](#0-1) 

Crucially, this loop filters `self.requests` by `r.member == member` (the requester), not by whether `member` appears inside any request's `confirmations` set. Confirmations are stored in a separate map (`self.confirmations`) that is never cross-checked against `self.members` at execution time. `assert_valid_request`, called from both `confirm()` and `delete_request()`, only checks that the *caller* is currently a member and that the request/confirmations records exist — it does not validate the historical confirmers of the set: [3](#0-2) 

**Binding that should hold:** `execute_request` should only run when `|{live members who confirmed}| >= num_confirmations`.
**Binding that actually holds:** `execute_request` runs when `|confirmations set| >= num_confirmations`, where the set can contain members who have since been deleted.

Concrete break sequence:
1. Multisig has members `{A, B, C, D}`, `num_confirmations = 3`.
2. `D` calls `add_request` to create request `R` (e.g., a `Transfer` or `FunctionCall` action) — `R.member = D`.
3. `A` and `B` call `confirm(R)` — `confirmations[R] = {A, B}` (2 of 3, not yet executed).
4. Separately, the multisig executes a `DeleteMember { member: A }` request (via its own K-of-N process) to remove `A`. `delete_member` only removes requests where `r.member == A` (i.e., requests *created by* A); it does not touch `confirmations[R]`, which still contains `A` even though `A` is no longer in `self.members`.
5. `C` (still a legitimate member) calls `confirm(R)`. `confirmations[R].len() + 1 == 3 >= num_confirmations`, so `execute_request(R)` fires.

The request executes with confirmations effectively "signed" by `A` (removed), `B`, and `C` — i.e., only 2 currently-live members actually authorized it (`B`, `C`), one fewer than the required 3-of-N threshold. This is structurally the same class of bug as the reported issue: a partial/stale authorization artifact (the session call signature in the report; here, a dangling confirmation from a de-authorized signer) that was never invalidated when the underlying entitlement was revoked, letting an attacker-influenced or coincidental sequence of operations execute a privileged action without the intended live quorum.

### Impact Explanation
This breaks the fundamental K-of-N custody guarantee of the multisig: `MultiSigRequestAction::Transfer`, `FunctionCall`, `AddKey`, `AddMember`, `DeleteMember`, and `DeployContract` can all be executed by the contract's own account with a confirmation set that includes a party no longer trusted to authorize spends or governance changes on the account. Per the stated impact classes, this is a multisig request executed below threshold — Critical, since it can move NEAR held by the multisig account or grant unauthorized keys/members without the intended number of live approvers.

### Likelihood Explanation
No privileged actor, redeploy, or victim key compromise is required beyond ordinary, permitted multisig operations: any legitimate member confirming a request before another member is later removed, followed by removal of that confirming member through the normal `DeleteMember` flow, and then one more live confirmation, reproduces the stale-count. This can happen organically (a member departs the organization and is removed) or be deliberately orchestrated by any subset of members who want to push through an action with intentionally reduced live quorum, since the contract exposes no method to detect or purge stale confirmations, and `confirm()`/`assert_valid_request()` never revalidate the membership of already-recorded confirmers.

### Recommendation
When executing `delete_member`, iterate over all pending requests and prune the deleted member's identity from every `confirmations` set (not only from requests they authored), or alternatively, at confirmation-count time in `confirm()`, filter `confirmations` down to identities still present in `self.members` before comparing against `num_confirmations`. Equivalently, re-validate membership of every confirming identity right before invoking `execute_request`.

### Proof of Concept
Not directly executable without the full crate/test harness (JSON test fixtures and build tooling are out of scope per rules), but the exploit path is fully specified above using only the public multisig2 API and requires no modification of contract logic:

1. `new(members: [A,B,C,D], num_confirmations: 3)`
2. `D` (as predecessor/signer) → `add_request({receiver_id: multisig_account, actions: [Transfer{amount}]})` → returns `request_id = R`.
3. `A` → `confirm(R)` (records confirmation, count = 1).
4. `B` → `confirm(R)` (count = 2, below threshold, no execution).
5. Via a separate, properly-confirmed 3-of-4 request, execute `DeleteMember{ member: A }` — this calls `delete_member`, which removes only requests created by `A`, leaving `confirmations[R] = {A, B}` untouched (`multisig2/src/lib.rs:355-379`).
6. `C` → `confirm(R)`: `confirmations[R].len() + 1 == 3 >= num_confirmations`, triggering `execute_request(R)` and transferring `amount` out of the multisig account, despite only `B` and `C` being live members who actually approved it. [1](#0-0) [2](#0-1)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
