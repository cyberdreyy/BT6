### Title
Paid instant-withdraw receipts stay in `instantWithdrawClaimsByEpoch` / `instantWithdrawsRequestsByEpoch`, corrupting default-recovery pricing and draining the recovery reserve — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2019-2213 is a use-after-free: a transaction object is freed while references to it still exist. The analog in `IdleCreditVault` is a paid ("freed") instant-withdraw receipt whose per-epoch accounting references are never cleared. `claimInstantWithdrawRequest` zeroes only the aggregate `instantWithdrawsRequests[_user]`; it never decrements `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults in that same epoch while `pendingInstantWithdraws != 0`, `finalizeDefaultRecovery` counts already-paid receipts in both the claim basis (`defaultPendingClaimBasis`) and the prefunded reserve (`_defaultPrefundedInstantReserve`), understating `defaultRecoveryPrice` and overstating `defaultRecoveryReserve` relative to underlying actually held.

### Finding Description
In `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`), a funded instant claim burns the user's receipt tokens, sets `instantWithdrawsRequests[_user] = 0`, and pays at par via `_transferFundedClaim`, but leaves two stale references alive:

- `instantWithdrawsRequestsByEpoch[_user][epochNumber]` keeps the user's paid basis.
- `instantWithdrawClaimsByEpoch[epochNumber]` keeps the epoch's aggregate basis.

At default finalization (`finalizeDefaultRecovery`, `IdleCreditVault.sol:661-710`), when `pendingInstantWithdraws != 0`:

- `defaultPendingClaimBasis` (`:644-649`) adds the full `instantWithdrawClaimsByEpoch[epochNumber]`, including amounts already paid out at par.
- `_defaultPrefundedInstantReserve` (`:716-723`) computes `prefundedReserve = instantBasis - pendingInstant`, crediting underlying that already left the contract.

So `reserveAmount` (line 686) is inflated by funds no longer held, while `totalBasis` (line 680) is inflated by already-satisfied claims. `defaultRecoveryPrice` is set from both (`:688`), and `defaultInstantWithdrawsFinalized` is set true (`:696`).

Consequences:

1. Every genuine defaulted-epoch claimant (normal withdraw receipts, unfunded instant receipts, active AA/BB tranche holders via the forced NAV reduction at `:699-705`) is priced against an inflated basis, so `defaultRecoveryPrice` is lower than solvency supports.
2. `defaultRecoveryReserve` is set to a value larger than the strategy's actual underlying balance. `_transferDefaultRecovery` spends down the real balance; once it is exhausted, later legitimate `_claimDefaultedWithdrawRequest` / `_claimDefaultedInstantWithdrawRequest` calls revert — permanently freezing the tail of the recovery payouts.
3. The attacker's stale `instantWithdrawsRequestsByEpoch` entry also makes their own `_claimDefaultedInstantWithdrawRequest` underflow (`instantWithdrawsRequests[_user] -= claimBasis` at `:848`, and `_burn(_user, claimBasis)` at `:854` on tokens they no longer hold), permanently DoS-ing any subsequent instant receipts they hold — freezing their new requests as well.

The "freed" receipt is thus still referenced by the epoch-aggregates, exactly the UAF pattern: the object was consumed but the accounting pointers to it were not released.

### Impact Explanation
Unprivileged attacker who is a KYC'd tranche holder with instant-withdraw access:

1. During running epoch N, calls `requestInstantWithdraw` on the CDO for amount A.
2. After `collectInstantWithdrawFunds` funds it, calls `claimInstantWithdrawRequest` and receives A underlying at par. `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` still contain A.
3. Honest borrower defaults on the epoch-N loan; guardian/manager runs the default flow. Finalization requires `pendingInstantWithdraws != 0`, satisfied by any other user's unfunded instant request in epoch N (or partial prefunding of the attacker's own request).
4. `defaultRecoveryPrice` is computed over a `totalBasis` inflated by A and a `reserveAmount` that counts A's already-paid funds via `prefundedReserve`.

Loss is quantified as: the recovery pool must pay `claimBasis * price` over an inflated basis from a balance short by A — honest claimants and active tranche holders lose up to `A * (1 - effectivePrice)` of recovery, and the last claimants' transactions revert once the real reserve is depleted, permanently freezing their share. Attacker gain is the par payout A that should have shared the default loss.

### Likelihood Explanation
Requires an epoch where (a) instant withdrawals are enabled and at least one request is funded and claimed within the epoch, and (b) the borrower defaults in that same epoch while some instant basis remains unfunded. Instant-withdraw requesters can only be KYC-allowed tranche holders, and the default itself is honest-manager driven, so the attacker cannot force timing — but the flow needs no privileged misbehavior: a normal funded instant claim followed by an ordinary borrower default suffices. The missing cleanup is unconditional in the code.

### Recommendation
In `claimInstantWithdrawRequest`, clear per-epoch references when paying a funded receipt: decrement `instantWithdrawClaimsByEpoch[epoch]` and zero `instantWithdrawsRequestsByEpoch[_user][epoch]` for the epoch(s) being paid (tracking each request's epoch at request time, or clearing the current-epoch entry when the aggregate is consumed). Equivalently, in `_claimDefaultedInstantWithdrawRequest`, derive the claim basis from the live `instantWithdrawsRequests[_user]` balance rather than the never-cleared per-epoch mapping, and in `_defaultPrefundedInstantReserve`, cap `prefundedReserve` at the strategy's actual underlying balance attributable to current-epoch receipts.

### Proof of Concept
Foundry fork PoC sketch (place under `test/foundry/`):

```solidity
function testStaleInstantReceiptCorruptsRecovery() public {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);          // enter epoch 1

    // enable instant withdrawals
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    uint256 tranchesA = _depositWithUser(attacker, 100e6);
    uint256 tranchesV = _depositWithUser(victim,   100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();                    // epoch 1 running

    // both request instant withdraws in epoch 1
    _requestInstantWithdrawWithUser(attacker, tranchesA);
    _requestInstantWithdrawWithUser(victim,   tranchesV);

    // CDO funds and attacker claims at par inside epoch 1
    // (collectInstantWithdrawFunds for attacker's share, then claim)
    // -> instantWithdrawsRequestsByEpoch[attacker][1] stays nonzero

    // victim's instant request left unfunded => pendingInstantWithdraws != 0
    // borrower defaults in epoch 1; guardian triggers default flow
    // finalizeDefaultRecovery runs:
    //   instantWithdrawClaimsByEpoch[1] still counts attacker's paid A
    //   -> totalBasis inflated, prefundedReserve inflated
    assertEq(
        strategy.instantWithdrawsRequestsByEpoch(attacker, strategy.epochNumber()),
        tranchesA,
        'stale paid receipt still referenced'
    );
    // assert defaultRecoveryPrice < expectedPrice and that
    // victim/last claimant claimWithdrawRequest reverts once reserve is exhausted
}
```

Key assertion: after the attacker is paid at par, `instantWithdrawsRequestsByEpoch[attacker][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` remain non-zero, and post-finalization `defaultRecoveryReserve` exceeds the strategy's actual underlying balance attributable to unresolved claims.

Caveats: I could not fully verify the CDO-side entry points (`IdleCDOEpochVariant` request/claim wrappers and whether instant claims are permitted to settle inside the same running epoch on the deployed variant) within the search budget; the stale-mapping behavior itself is confirmed in `IdleCreditVault.sol:371-392, 644-649, 716-723, 842-856`. If the CDO variant restricts same-epoch instant claims such that a paid receipt can never coexist with an in-epoch default under `pendingInstantWithdraws != 0`, the practical severity drops to accounting dead-state rather than loss.
