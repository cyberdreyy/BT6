### Title
Unvalidated slot value from websocket subscription causes panic in `RecentLeaderSlots::estimate_current_slot` via integer-overflow wraparound - ([File: tpu-client-next/src/node_address_service/recent_leader_slots.rs])

### Summary
`RecentLeaderSlots::estimate_current_slot` computes `max_reasonable_current_slot` by unchecked addition of `MAX_SLOT_SKIP_DISTANCE` to a value derived directly from an externally-supplied slot number, with no bounds checking on the raw slot. A single `SlotEvent` carrying a `Slot` close to `u64::MAX` causes this addition to wrap around, which then causes the subsequent `.expect("no reasonable slot")` to panic deterministically (in both debug and release builds) because no element in the (single-element) buffer can satisfy the post-wraparound filter.

### Finding Description
The slot value flows unchecked from the network to this function: `map_websocket_update_to_slot_event` in `tpu-client-next/src/websocket_node_address_service.rs:138-144` converts an RPC `SlotUpdate::FirstShredReceived`/`Completed` payload's `slot: u64` field directly into a `SlotEvent::Start`/`End` with no range validation. This event is pushed into `RecentLeaderSlots` via `record()` at [1](#0-0)  and then `SlotUpdateService::run`'s main loop immediately calls `estimate_current_slot()` on every incoming event at [2](#0-1) .

Inside `estimate_current_slot`: [3](#0-2) 

If a single (or an otherwise minimal) `SlotEvent` carries `slot = Slot::MAX` (or any value within `MAX_SLOT_SKIP_DISTANCE` of it), `expected_current_slot` ends up close to `u64::MAX`, and `expected_current_slot + MAX_SLOT_SKIP_DISTANCE` wraps around to a small value (e.g. `u64::MAX + 48` wraps to `47`). The `#[allow(clippy::arithmetic_side_effects)]` attribute only suppresses the clippy lint; it does not add saturating/checked arithmetic. Because `max_reasonable_current_slot` is now a small number while the only recorded slot is near `u64::MAX`, `recent_slots.iter().rposition(|e| e.slot() <= max_reasonable_current_slot)` finds no matching element and `.expect("no reasonable slot")` unconditionally panics — this occurs independent of `debug_assertions`/`overflow-checks`, because the wraparound itself (not the overflow-checked arithmetic) causes the logical failure.

This is reachable purely by a client subscribing to `slotUpdatesSubscribe` on an RPC node that returns (or is coerced into returning, e.g. via a compromised/malicious RPC endpoint the client connects to) a bogus large slot number — no validator, leader, gossip, or staked-node control is required from the attacker's perspective relative to this client library; the untrusted input is simply whatever the connected websocket server sends.

### Impact Explanation
The panic unwinds/aborts the async task running `SlotUpdateService`'s main loop (and, depending on the runtime's panic behavior/`panic = "abort"` profile, can abort the whole process). This causes denial of service for any application built on `tpu-client-next`'s `WebsocketNodeAddressService`/`NodeAddressService`, matching the scoped impact "denial of a legitimate client's tpu-client-next instance" via a single crafted slot-update event, with no need for multiple calls or attacker infrastructure beyond controlling/spoofing one websocket response.

### Likelihood Explanation
Highly feasible and deterministic: the client only needs to receive one `SlotUpdate` notification (via `slotUpdatesSubscribe`, one subscription, well within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` limit) with `slot` near `u64::MAX`. No cryptographic proof, staking, or special privilege is needed to control the content of a websocket message sent to the subscribing client (e.g., a malicious/compromised RPC endpoint operator, or an on-path/rogue server the client mistakenly connects to). The bug is 100% reproducible given that input.

### Recommendation
Use saturating arithmetic throughout `estimate_current_slot` (`median_recent_slot.saturating_add(...)`, `expected_current_slot.saturating_add(MAX_SLOT_SKIP_DISTANCE)`), matching the pattern already used elsewhere in the file (`slot_event.slot().saturating_add(1)`), and replace the `.expect("no reasonable slot")` with a fallback (e.g., return the last event's slot) so that no malformed/adversarial input can cause a panic.
