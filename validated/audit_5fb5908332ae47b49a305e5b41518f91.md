### Title
Unbounded per-request O(n) scan of the shared Vault replay-guard map allows an authenticated Vault client to degrade authorization for all users - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
The Vault gateway handler's `Authorizer` uses a single, node-wide `RequestReplayGuard` whose `seen` map is scanned in full on *every* Vault request authorization (allowlist- or JWT-based). Because entries persist until their JWT-derived expiry, an authenticated (but otherwise unprivileged/untrusted) client can inflate this map by sending many distinct, validly-authorized requests with far-future expirations, causing every subsequent authorization call from any user to perform an ever-growing linear scan. This is structurally the same bug class as the referenced pSTAKE `_calculatePendingRewards` report: a history/record collection that grows without bound and is fully iterated on every hot-path call.

### Finding Description
`Authorizer.AuthorizeRequest` calls `a.replayGuard.CheckAndRecord(...)` for every Vault JSON-RPC request that passes allowlist or JWT authorization: [1](#0-0) 

`RequestReplayGuard.CheckAndRecord` unconditionally calls `clearExpiredLocked()`, which iterates over the *entire* `seen` map on every single call, before checking/inserting the current digest: [2](#0-1) 

The guard is instantiated once per `Authorizer` and is shared across all callers/owners on the node — it is not partitioned per user: [3](#0-2) 

Entries are keyed by request digest (which differs per distinct request payload/params) and are retained until `expiresAt`, which for the JWT path is derived directly from the client-supplied JWT's `exp` claim plus a fixed leeway: [4](#0-3) 

For the allowlist path, `expiresAt` comes from the on-chain `ExpiryTimestamp` of the allowlisted request, which an owner controls when registering an allowlist entry: [5](#0-4) 

Since any legitimately-authorized (but not privileged/trusted) Vault caller — a workflow owner via JWT or allowlist — can vary request parameters to produce distinct digests, and can choose long-lived JWT `exp` values or long on-chain expiry windows, they can grow `seen` to an arbitrary size within their authorized window. Every subsequent authorization request from *any* user on the node then pays the cost of scanning the full map under a single mutex (`g.mu`), which serializes all Vault authorization globally.

This directly parallels the STokens bug class: a stored, ever-growing history collection (`_rewardRate` array / `seen` map) that is iterated in full on each hot-path operation, with no partial-update, cap, or amortized cleanup mechanism, causing per-call cost to scale with the number of past entries rather than being bounded.

### Impact Explanation
The map scan happens under a single global lock (`g.mu`) shared by all Vault requests routed through this node's `GatewayHandler`/`Authorizer`. As the map grows, CPU time (and lock hold time) for `CheckAndRecord` grows linearly, and because the lock is global, this serializes and slows down authorization for *every* Vault caller on the node — not just the one growing the map. In the worst case (large map, sustained request rate), this can starve the authorization path, causing legitimate Vault secret operations (create/update/delete/list/get) from unrelated workflow owners to time out or be delayed — a denial-of-service condition on a security-critical authentication component, reachable without any special privilege beyond normal, valid Vault-request authorization (a valid JWT or a valid on-chain allowlist entry, both of which describe ordinary/unprivileged workflow-owner usage, not compromised or malicious insiders).

### Likelihood Explanation
Likelihood is moderate: exploitation requires the attacker to already hold a valid authorization credential (a legitimately-issued Auth0 JWT for the Vault audience, or an on-chain allowlisted request as any workflow owner) — this is the intended "unprivileged client" trust boundary the analog rules target, not a compromised node or peer. Given a valid credential, generating many distinct digests is trivial (vary any request field), and setting a long expiry is within the caller's control (JWT `exp` claim, or long on-chain `ExpiryTimestamp`). No rate limiting is applied specifically to the replay-guard's insertion path independent of the standard per-request rate limiters, so sustained request volume from one authorized identity can grow the shared map significantly before expiry-based cleanup catches up.

### Recommendation
- Partition the replay guard's storage by owner/tenant (or bound total entries per owner) so one caller cannot inflate a globally-shared structure.
- Cap the maximum number of live entries (e.g., LRU eviction) and/or cap the maximum allowed expiry window independent of caller-supplied JWT `exp` / on-chain expiry, so `seen` cannot grow unbounded within a single window.
- Avoid a full linear scan on every call: use a min-heap or time-bucketed expiry structure so cleanup is amortized (O(log n) or O(1) instead of O(n)) instead of walking the whole map each time.
- Consider moving cleanup off the hot request path into a periodic background sweep instead of doing it synchronously under the shared lock on every authorization call.

### Proof of Concept
1. Obtain a valid Vault JWT (or on-chain allowlist entry) for workflow owner A with an `exp` far in the future (bounded only by JWT/allowlist issuance policy).
2. Send many `SecretsList`/`SecretsCreate` requests with varying `Params` (e.g., different `Namespace`/`Key`) using the same JWT/allowlist window — each produces a distinct `req.Digest()`, so each is inserted into the shared `seen` map via `CheckAndRecord` [6](#0-5) .
3. Because all entries share the same long expiry, `clearExpiredLocked()` cannot reclaim them, and the map keeps growing with each new distinct request [7](#0-6) .
4. Concurrently, have workflow owner B (an unrelated legitimate user) send normal Vault requests; because `AuthorizeRequest` for *every* method funnels through the same `a.replayGuard.CheckAndRecord` call under one mutex [8](#0-7) , B's authorization latency increases proportionally to the size of the map grown by A, demonstrating cross-user resource-exhaustion/denial-of-service caused entirely by an unprivileged authorized caller.

Note: I was not able to find a rate limiter that specifically bounds insertions into `RequestReplayGuard.seen` independent of general request throttling; if such a limiter exists elsewhere in the request pipeline and effectively caps the achievable map size, it would reduce the severity of this finding, but no such bound was found in the reviewed code (`core/capabilities/vault/*`).

func (a *authorizer) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	authResult, err := a.authorizeRequest(ctx, req)
	if err != nil {
		return nil, err
	}
	if authResult == nil {
		err = errors.New("auth mechanism returned nil auth result")
		a.lggr.Errorw("auth mechanism returned nil auth result", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "")
		return nil, err
	}
	if err := a.replayGuard.CheckAndRecord(authResult.Digest(), authResult.ExpiresAt()); err != nil {
		a.lggr.Debugw("replay guard rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "", "error", err)
		return nil, err
	}
	if ownerErr := validateSecretOwnersMatchAuthorized(req, authResult.AuthorizedOwner()); ownerErr != nil {
		a.lggr.Errorw("owner binding rejected request", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "hasAuth", req.Auth != "", "error", ownerErr)
		return nil, ownerErr
	}
	a.lggr.Debugw("request authorized", "method", req.Method, "requestID", req.ID, "owner", authResult.AuthorizedOwner(), "digest", authResult.Digest(), "expiresAt", authResult.ExpiresAt(), "hasAuth", req.Auth != "")
	return authResult, nil
}

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

// ClearExpired removes all entries whose expiry timestamp is in the past.
// Call this to eagerly reclaim memory even when CheckAndRecord is not invoked.
func (g *RequestReplayGuard) ClearExpired() {
	g.mu.Lock()
	defer g.mu.Unlock()
	g.clearExpiredLocked()
}

func (g *RequestReplayGuard) clearExpiredLocked() {
	now := g.nowFunc().UTC().Unix()
	for digest, expiry := range g.seen {
		if now > expiry {
			delete(g.seen, digest)
		}
	}
}
