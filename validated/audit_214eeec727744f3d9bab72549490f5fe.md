### Title
Missing zero-address validation on `new_authority` in `transfer_to_new_account` / `transfer_to_new_account_pda` permanently freezes migrated account funds - ([File: programs/marginfi/src/instructions/marginfi_account/transfer_account.rs])

### Summary
The account-migration instructions `TransferToNewAccount` and `TransferToNewAccountPda` accept an arbitrary `new_authority` account with no validation that it is not the zero/default `Pubkey`, mirroring the reported bug class where an address parameter is used to set critical state without checking `address(0)`. Since all lending positions are moved from the old account to the newly created account whose `authority` field is set to whatever `new_authority` was supplied, setting it to `Pubkey::default()` durably and irrecoverably locks the migrated account and its balances.

### Finding Description
`transfer_to_new_account` (and its PDA variant) initializes the new `MarginfiAccount` using `ctx.accounts.new_authority.key()` directly, with the account itself annotated as completely unchecked: [1](#0-0) [2](#0-1) 

The same unchecked pattern exists for the PDA-based migration path: [3](#0-2) [4](#0-3) 

There is no check anywhere in `transfer_to_new_account`/`transfer_to_new_account_pda` that `new_authority != Pubkey::default()`. Once the instruction succeeds, the old account is disabled and its `lending_account` is zeroed out (`LendingAccount::zeroed()`), while the new account inherits the old account's full `lending_account` (all deposit/borrow balances): [5](#0-4) 

Notably, the only place in the codebase that guards against this exact scenario is the off-chain CLI helper — not the on-chain program: [6](#0-5) 

This confirms the zero-address case is a recognized hazard, but the check exists only in a client tool. Any direct program call (integrator, custom frontend, or CPI) bypasses this guard entirely, just as the analog report describes an `update` function that fails to check `to != address(0)` before mutating account-linked state.

### Impact Explanation
If `new_authority` is set to `Pubkey::default()`, the newly created `MarginfiAccount` holds all of the migrated lending positions but has an `authority` field equal to the System Program's default public key, for which no private key exists. Because every downstream instruction (`withdraw`, `borrow`, `repay`, `close_balance`, further transfers) requires `is_signer_authorized`/`Signer<'info>` validation against this `authority`, the new account becomes permanently unusable — a durable freeze of the migrated deposits and liabilities. This is a real financial-effect impact (loss of access to funds), consistent in severity (Low impact / High likelihood, self-triggerable) with the referenced NFT report.

### Likelihood Explanation
The instruction is directly reachable by any account owner (`old_marginfi_account`'s `authority`, verified via `is_signer_authorized`) with no special privileges required: [7](#0-6) 
Because `new_authority` is a completely unchecked account (explicitly documented as such in the code) and only the CLI — not the program — filters out the zero address, any integrator, malformed frontend transaction, or user error passing `Pubkey::default()` as `new_authority` will trigger the freeze. Likelihood is high given how trivially reachable and easy to trigger (accidentally or via malicious frontend) this is.

### Recommendation
Add an explicit on-chain check in both `transfer_to_new_account` and `transfer_to_new_account_pda` rejecting `Pubkey::default()` (and ideally the program ID itself) for `new_authority`, mirroring the CLI's existing guard, e.g.:
```rust
check!(
    ctx.accounts.new_authority.key() != Pubkey::default(),
    MarginfiError::InvalidAuthority
);
```
placed before `initialize_migrated_account` is called in both instruction handlers.

### Proof of Concept
1. User creates a `MarginfiAccount` and deposits/borrows to build lending positions.
2. User (or a malicious/buggy integrator) invokes `transferToNewAccount`/`transferToNewAccountPda` directly against the on-chain program (bypassing the CLI's `marginfi_account_transfer` guard), passing `new_authority = Pubkey::default()`.
3. The instruction succeeds: `old_account` is disabled (`ACCOUNT_DISABLED`, `lending_account` zeroed) and `new_account` is initialized with `authority = Pubkey::default()`, carrying over all balances (see `initialize_migrated_account`/`finalize_migrated_old_account`).
4. Any subsequent instruction on `new_account` (withdraw, repay, close_balance, further transfer) requires a `Signer` matching `Pubkey::default()`, which cannot exist — the account and its funds are permanently locked, with no admin-level recovery instruction available for this specific state in the reviewed code paths.

fn initialize_migrated_account(
    new_account: &mut MarginfiAccount,
    old_account: &MarginfiAccount,
    new_authority: Pubkey,
    current_timestamp: u64,
    old_account_key: Pubkey,
) {
    new_account.initialize(old_account.group, new_authority, current_timestamp);
    new_account.lending_account = old_account.lending_account;
    new_account.emissions_destination_account = old_account.emissions_destination_account;
    new_account.account_flags = old_account.account_flags;
    new_account.migrated_from = old_account_key;
    new_account.indexer_flags = old_account.indexer_flags;
    new_account.sync_indexer_flags();
}

fn finalize_migrated_old_account(
    old_account: &mut MarginfiAccount,
    new_account_key: Pubkey,
    current_timestamp: u64,
) {
    old_account.migrated_to = new_account_key;
    old_account.last_update = current_timestamp;
    old_account.lending_account = LendingAccount::zeroed();
    old_account.set_flag(ACCOUNT_DISABLED, true);
    old_account.sync_indexer_flags();
}
