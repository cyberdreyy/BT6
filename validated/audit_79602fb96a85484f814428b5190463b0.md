### Title
Signer weight double-counted toward both acceptance and rejection tallies in `StackerDBListener` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`BlockStatus::total_weight_approved` and `BlockStatus::total_weight_rejected` are meant to be mutually-exclusive, disjoint tallies of signer weight for a proposed block, gated against a single `responded_signers` set so each signer contributes weight to only one side. The `Accepted` handling path, however, gates its weight addition on a *different* set (`gathered_signatures`) instead of `responded_signers`, so a signer who has already been counted as a rejector can later also be counted as an accepter, inflating the combined weight beyond what any single signer set should produce.

### Finding Description
`BlockStatus` carries a single `responded_signers: HashSet<u32>` that is documented as tracking "signers who have responded," and is used by the `Rejected` branch to gate weight accrual: [1](#0-0) 
i.e. `if block.responded_signers.insert(slot_id) { total_weight_rejected += weight }` — insertion into `responded_signers` returns `false` on a repeat call, so a slot that has already voted (in either direction) should not be double counted.

But the `Accepted` branch guards its weight accrual with a **different** collection, `gathered_signatures` (a `BTreeMap<u32, MessageSignature>`), not `responded_signers`: [2](#0-1) 

Sequence that breaks the invariant:
1. Signer `S` (slot `k`) sends `BlockResponse::Rejected` first. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w_k`.
2. Signer `S` later sends `BlockResponse::Accepted` for the same block (a signer can legitimately re-evaluate and flip its vote, or a malicious/buggy signer can simply emit both messages over StackerDB). The accept branch checks `!gathered_signatures.contains_key(k)`, which is still `true` (nothing has touched `gathered_signatures` yet for this slot) → `total_weight_approved += w_k` is executed. `responded_signers.insert(k)` is then called unconditionally on line 465, but this is now a no-op for the invariant already broken above.

The result: `w_k` is now counted in **both** `total_weight_approved` and `total_weight_rejected` simultaneously for the same block, coming from a single signer/slot. This breaks the "aggregated-weight vs verified-accepts" equality that `SignerCoordinator::retrieve_block_response` relies on to decide the miner-side outcome: [3](#0-2) 

Because the rejection check (`total_weight_rejected + weight_threshold > total_weight`) is evaluated before the approval check in that loop, a single equivocating (or simply order-flipping) signer can inflate `total_weight_rejected` using weight that "should" already belong to `total_weight_approved` (or vice-versa), letting one signer's weight count on both sides of the 70%/30% split. This can push the combined tally across a threshold that would not otherwise be reached by the honest weight of the signer set, causing the miner to declare a block globally rejected (`SignersRejected`) or accepted based on an artificially inflated count that does not correspond to the true number of distinct signer weights on that side.

### Impact Explanation
This is a Critical-class analog per the rubric: a "rejection recounted as an accept" (and the mirror direction, an accept recounted as a reject) via a single one-slot signer's messages, without needing a majority of signers or another signer's key — only the reporting signer's own two legitimate messages (or a compromised/buggy signer replaying both response kinds) are needed to corrupt the miner's tally for that block. It can cause the miner to make an incorrect global-accept/global-reject decision on a block based on a corrupted weight sum, which is exactly the "aggregated-weight vs verified-accepts" equality the rubric calls out.

### Likelihood Explanation
Requires only one signer to emit both a `Rejected` and (later) an `Accepted` `BlockResponse` for the same `signer_signature_hash` — StackerDB gossip alone reaches the miner's `StackerDBListener`. This is plausible under normal operation because signers are documented elsewhere in this codebase (`docs/signer-flows.md` §6) to reconsider and change votes for certain rejection reasons, so a legitimate vote-flip from reject→accept (or the reverse ordering) is a realistic sequence, not merely a contrived adversarial case.

### Recommendation
Gate the `Accepted` branch's weight accrual on the same `responded_signers` set used by the `Rejected` branch (or otherwise track, per slot, which single tally the slot's weight has already been applied to) so a slot's weight can only ever be added to exactly one of `total_weight_approved` / `total_weight_rejected`, e.g. change the condition at stacks-node/src/nakamoto_node/stackerdb_listener.rs:443 from checking `gathered_signatures.contains_key(&slot_id)` to checking/inserting into `responded_signers` before adding to `total_weight_approved`.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`; signer set includes signer `S` at slot `k` with weight `w_k`.
2. `S` sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`. `StackerDBListener` processes it: `responded_signers.insert(k)` → true, `total_weight_rejected += w_k`.
3. `S` (per the documented reconsideration flow) later sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `H`, with a valid signature.
4. `StackerDBListener` processes the accept message: `gathered_signatures.contains_key(&k)` is `false` (never populated by the reject path) → `total_weight_approved += w_k` executes, and `gathered_signatures.insert(k, signature)` / `responded_signers.insert(k)` follow.
5. Now `w_k` has been added to both `total_weight_rejected` and `total_weight_approved`. `SignerCoordinator::retrieve_block_response`'s combined thresholds (`total_weight_rejected + weight_threshold > total_weight` checked first, `total_weight_approved >= weight_threshold` checked second) are evaluated against sums that double-count `w_k`, which can flip the outcome relative to what the true, non-overlapping signer weights would produce.
