### Title
Missing role floor on `GET /v2/external_initiators` allows view-role users to enumerate External Initiator AccessKeys - ([File: core/web/router.go])

### Summary
`authv2.GET("/external_initiators", paginatedRequest(eia.Index))` is only gated by `auth.Authenticate` (any valid session or API token), unlike `Create`/`Destroy` which require `auth.RequiresEditRole`. Any authenticated user, including one with the minimum `view` role, can list all external initiators and obtain their `Name`, `URL`, `AccessKey`, and `OutgoingToken`.

### Finding Description
`authv2` group requires only `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)` for a base session/token; individual routes then optionally add a role floor via `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` [1](#0-0) . `eia.Index` has no such wrapper, while `Create`/`Destroy` do [2](#0-1) . The handler `ExternalInitiatorsController.Index` fetches all initiators and serializes them through `presenters.NewExternalInitiatorResource`, which includes `AccessKey` and `OutgoingToken` fields [3](#0-2) [4](#0-3) .

Importantly, this pattern (no role wrapper on GET/Index endpoints, `RequiresEditRole`/`RequiresAdminRole` only on mutating endpoints) is consistent across almost every controller in `v2Routes` — e.g. `bridge_types` Index, `keys/ocr`, `keys/ocr2`, `keys/p2p`, `keys/vrf`, `tx_attempts`, `transactions`, `jobs` all lack role wrappers on their `GET`/`Index` routes while their `Create`/`Update`/`Delete` routes are wrapped [5](#0-4) [6](#0-5) . This indicates the intended minimum access floor for read-only resource listing in this codebase is simply "any authenticated user" (view role included), not a per-route role check — so the absence of a role wrapper here is consistent with the established design rather than a unique bypass.

Additionally, the exposed `AccessKey` is only the identifier half of the two-part External Initiator credential; the `Secret`/`HashedSecret` are never returned by `Index` (only by `Create`, to the creator, once) [7](#0-6) . `AuthenticateExternalInitiator` still requires the corresponding secret to be verified via `bridges.AuthenticateExternalInitiator`, so knowledge of `AccessKey` alone does not grant the ability to impersonate an initiator [8](#0-7) .

### Impact Explanation
A `view`-role authenticated user (already possessing valid node credentials) can enumerate `AccessKey`/`OutgoingToken`/`Name`/`URL` values for all configured external initiators. This narrows the search space for brute-forcing the initiator `Secret` (since the attacker no longer needs to guess valid `AccessKey`s) and leaks `OutgoingToken` values used for outbound initiator traffic. This is an information-disclosure issue bounded to identifiers, not a full authentication bypass, since the secret component remains protected by salted hashing in `bridges.AuthenticateExternalInitiator`.

### Likelihood Explanation
Requires the attacker to already hold a valid `view`-role session or API token (i.e., they must be a legitimate, low-privileged authenticated node user) — not an unauthenticated party. Given that precondition, the request is trivially repeatable: a single `GET /v2/external_initiators` call returns the full initiator list with no additional checks.

### Recommendation
Given that this mirrors the codebase-wide convention of gating only mutating operations, this is best treated as a design decision rather than a bug unique to this route. If tighter access control is desired, wrap `eia.Index` with `auth.RequiresEditRole` (matching `Create`/`Destroy`) and/or redact `AccessKey`/`OutgoingToken` from the `Index` response for `view`-role callers, since those fields are effectively part of the external initiator's authentication surface.

### Proof of Concept
Integration test plan (mirrors `TestExternalInitiatorsController_Index` in `core/web/external_initiators_controller_test.go`): create an app with a `view`-role authenticated `HTTPClient`, insert an external initiator via `cltest.MustInsertExternalInitiatorWithOpts`, then `GET /v2/external_initiators`; assert `http.StatusOK` and that the parsed `presenters.ExternalInitiatorResource` list contains the initiator's `AccessKey`/`OutgoingToken`, confirming no role floor is enforced (as opposed to `POST`/`DELETE` which return 401/403 for the same role).

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}
