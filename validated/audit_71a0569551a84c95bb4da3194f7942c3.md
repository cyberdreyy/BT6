### Title
ERC4626 liquidity withdrawal can temporarily block epoch settlement - ([File: contracts/strategies/idle/ProgrammableBorrower.sol])

### Summary
A programmable-borrower deployment can be prevented from completing `stopEpoch` when the configured ERC4626 vault reports sufficient asset value but cannot currently withdraw enough liquid underlying. An unprivileged ERC4626 vault user who withdraws available vault liquidity before settlement can make `onStopEpoch` revert with `StopEpochVaultLiquidityUnavailable`, leaving the epoch running and temporarily freezing pending withdrawals and tranche redemptions. [1](#0-0) 

### Finding Description
`IdleCDOEpochVariant._stopEpoch` calls `IProgrammableBorrower.onStopEpoch` before pulling borrower funds, and hook reverts deliberately bubble up so liquidity failures can be retried later. [2](#0-1) 

Inside `onStopEpoch`, the adapter compares the requested cash amount with its wallet balance, then calls `vault.withdraw` for the shortfall whenever `_currentVaultAssets()` economically covers it. [3](#0-2)  A failed ERC4626 withdrawal is not treated as borrower default or liquidity shortfall; it reverts the entire CDO stop transaction. [4](#0-3) 

The vault's fungible share valuation is therefore separated from its immediately withdrawable liquidity: `_currentVaultAssets` uses `convertToAssets`, while actual settlement depends on `vault.withdraw` succeeding. [5](#0-4)  An ERC4626 vault participant can create that gap by withdrawing currently available cash immediately before the manager calls `stopEpoch`.

Because `isEpochRunning` remains true after the reverted call, ordinary deposits and withdrawal requests remain disabled by the epoch state. [6](#0-5)  The manager cannot complete the normal stop until the vault again permits the required withdrawal.

### Impact Explanation
This is a temporary freezing-of-funds issue with a direct fund impact. The amount frozen is at least the CDO settlement requirement `_amountToPullFromBorrower + _pendingWithdraws`, because settlement cannot proceed until that amount is either withdrawn by the adapter or pulled from the borrower. [7](#0-6) 

Normal withdrawal receipts remain unclaimable while `epochNumber` does not advance, because `claimWithdrawRequest` reverts while `epochNumber <= lastWithdrawRequest[user]` in a non-closed pool. [8](#0-7)  The freeze persists for the duration that vault liquidity is unavailable and can be repeated around successive `stopEpoch` attempts if the attacker can keep draining newly returned vault liquidity.

### Likelihood Explanation
Likelihood depends on the configured vault's liquidity profile and whether unprivileged vault users control enough shares to withdraw the cash needed for CDO settlement. The attacker does not need to impersonate the borrower, owner, manager, or CDO; causing an ordinary ERC4626 withdrawal failure is sufficient because the success path is not separated from the path that detects an economically uncovered shortfall. [1](#0-0) 

The impact is not permanent, and honest operators retain recovery options such as retrying after liquidity returns or redeeming through `emergencyExitVault`. [9](#0-8)  This bounds the issue to temporary availability loss rather than direct theft or permanent insolvency.

### Recommendation
Return `false` or a dedicated insufficient-liquidity result when covered vault shares cannot be converted into cash, allowing `IdleCDOEpochVariant` to choose an explicit default or operational path instead of reverting indefinitely. [2](#0-1) 

Alternatively, use `vault.maxWithdraw(address(this))` or an equivalent liquidity-aware check before `convertToAssets`, cap the requested withdrawal at immediately available liquidity, and expose a deterministic partial-liquidity/default path. The fix should distinguish “share value is insufficient” from “share value is sufficient but cash is temporarily unavailable” so honest managers can choose between retry, loss accounting, or default handling rather than receiving only a revert.

### Proof of Concept
The following Foundry-style sequence is reproducible on a programmable-borrower fork fixture with an ERC4626 vault whose liquid assets can be withdrawn by a third-party shareholder while `convertToAssets` still values the adapter's shares above the shortfall:

```solidity
function testVaultLiquidityBlocksStopEpoch() external {
    // Arrange: configure ProgrammableBorrower against a forked ERC4626 vault,
    // deposit into the CDO, and start an epoch.
    uint256 lpDeposit = 10_000_000e6;
    deal(address(underlying), lp, lpDeposit);
    vm.startPrank(lp);
    underlying.approve(address(cdo), lpDeposit);
    cdo.depositAA(lpDeposit);
    vm.stopPrank();

    vm.prank(manager);
    cdo.startEpoch();

    // Arrange an unprivileged ERC4626 shareholder outside the CDO/borrower
    // with enough shares to consume the vault's currently liquid cash.
    address vaultUser = makeAddr("vaultUser");
    uint256 attackerDeposit = underlying.balanceOf(address(vault));
    deal(address(underlying), vaultUser, attackerDeposit);
    vm.startPrank(vaultUser);
    underlying.approve(address(vault), attackerDeposit);
    vault.deposit(attackerDeposit, vaultUser);

    // After the CDO funds are parked, withdraw all cash available to the user.
    // The adapter retains share value, but the vault cannot satisfy its shortfall.
    uint256 maxCash = vault.maxWithdraw(vaultUser);
    vault.withdraw(maxCash, vaultUser, vaultUser);
    vm.stopPrank();

    vm.warp(cdo.epochEndDate() + 1);

    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdo.stopEpoch(newApr, 0);

    assertTrue(cdo.isEpochRunning());
    assertEq(strategy.epochNumber(), epochBefore);

    // A prior normal withdrawal request remains frozen because the epoch did not advance.
    vm.prank(requester);
    vm.expectRevert(NotAllowed.selector);
    cdo.claimWithdrawRequest();
}
```

The PoC requires `shortfall <= _currentVaultAssets()` while `vault.withdraw(shortfall)` reverts. That state reproduces the exact guard ordering in `onStopEpoch`: the adapter accepts the liability as economically covered, attempts the withdrawal, catches the ERC4626 failure, and then reverts the whole settlement.
