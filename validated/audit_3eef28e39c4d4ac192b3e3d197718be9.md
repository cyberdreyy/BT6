### Title
ERC4626 deposit-cap saturation bricks epoch starts and borrower repayments - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
`ProgrammableBorrower` treats every idle underlying balance as deployable vault liquidity and unconditionally calls `vault.deposit()` during `onStartEpoch()` and active-epoch repayments. An unprivileged ERC4626 vault depositor can saturate the vault’s deposit cap, causing those calls to revert. Because `IdleCDOEpochVariant.startEpoch()` invokes the borrower hook after transferring the epoch surplus, the whole start-epoch transaction reverts and the pool remains frozen in its buffer phase.

### Finding Description
`IdleCDOEpochVariant.startEpoch()` first sends all surplus underlying to the configured borrower and then calls `_startEpochProgrammableBorrower()`; there is no fallback path when the programmable borrower hook fails [1](#0-0) .

The programmable borrower then snapshots its position and unconditionally deposits its entire underlying balance into the configured ERC4626 vault [2](#0-1) . `_depositToVault()` directly calls `vault.deposit()` without a `try/catch`, liquidity check, deposit-limit check, or option to leave cash undeployed [3](#0-2) .

The same assumption exists in `_repay()`: after receiving borrower funds while epoch accounting is active, it redeploys the full repayment into the vault before returning [4](#0-3) .

An attacker who is only an ordinary ERC4626 vault user can deposit directly into that vault until `maxDeposit()` is zero, for example by consuming a public supply cap. Any subsequent `startEpoch()` attempt with borrower-bound or idle funds reverts at `vault.deposit()`. If the attacker also sends dust directly to `ProgrammableBorrower`, `onStartEpoch()` attempts a deposit even when the CDO has no surplus to transfer. While the cap remains saturated, the attacker can repeatedly refill capacity released by other vault withdrawals.

The vulnerable sequence is:

1. A normal epoch stops successfully, leaving the credit pool in the buffer phase.
2. The attacker deposits into the configured ERC4626 vault until no further deposit is accepted.
3. Optionally, the attacker directly transfers 1 wei of underlying to `ProgrammableBorrower`.
4. The honest manager calls `IdleCDOEpochVariant.startEpoch()`.
5. `ProgrammableBorrower.onStartEpoch()` calls `vault.deposit()`, which reverts because its cap is saturated.
6. The entire start transaction reverts, so the epoch never becomes running.
7. During an already-running epoch, the same cap prevents an honest borrower repayment because `_repay()` redeploys the received assets into the vault.

This is the same bug class as a killed external deposit integration: withdrawal liquidity may still exist, but an unconditional redeposit prevents the wrapper/core flow from completing.

### Impact Explanation
All principal scheduled for the next epoch is temporarily frozen. Pending withdrawal receipts cannot become claimable through a new epoch while `startEpoch()` cannot complete, and active tranche holders cannot use ordinary epoch withdrawals while the pool remains in the prior state. For a pool attempting to deploy `A` underlying, maintaining the attack freezes approximately `A`, plus any idle borrower balance, for as long as the attacker keeps the vault deposit cap saturated.

During an active epoch, a borrower repayment can also be forced to revert after the borrower has approved the repayment amount. If the deposit outage persists through epoch end, `stopEpoch()` may be unable to obtain the expected repayment through the normal path, increasing the likelihood of a default and delayed receipt recovery.

The impact is temporary rather than necessarily permanent because an honest owner or manager can redeem existing vault shares with `emergencyExitVault()` and can switch vaults only while epoch accounting is inactive and the old share balance is zero [5](#0-4) [6](#0-5) . Nevertheless, this requires privileged recovery and does not prevent an attacker from repeatedly saturating a new capped vault.

### Likelihood Explanation
Likelihood is conditional on the configured ERC4626 vault exposing a public deposit cap or another public condition under which deposits can be exhausted. ERC4626 vaults commonly enforce supply, market, or allocator caps, and the attacker needs no role in IdleCDO or `ProgrammableBorrower`; ordinary vault-depositor access is sufficient. The attacker must keep capital deposited while the attack is active, but retains the vault shares and can resume the attack after withdrawals create capacity.

The attack does not require the vault itself to be malicious, an oracle error, a depeg, or a privileged operator mistake. The vulnerable behavior is the credit vault’s lack of a graceful cash-holding path when an otherwise legitimate external vault refuses deposits.

### Recommendation
Do not make epoch lifecycle or repayment settlement depend on successful redeposit into the ERC4626 vault.

In `ProgrammableBorrower.onStartEpoch()` and the active-epoch path of `_repay()`:

- Check `vault.maxDeposit(address(this))` before depositing.
- Deposit only the accepted amount and retain the remainder as underlying.
- Alternatively, wrap `vault.deposit()` in `try/catch` and leave the funds on hand when the deposit fails.
- Include both on-hand underlying and vault assets in the epoch-start accounting baseline so undeployed funds are not mistaken for vault profit.
- Emit an event when funds remain undeployed because of external deposit limits.
- Preserve the existing revert behavior for failed withdrawals, since a withdrawal failure can represent an actual inability to satisfy IdleCDO liabilities.

A resilient `onStartEpoch()` should be able to start the epoch with idle underlying retained locally instead of reverting solely because the yield vault is temporarily full or deposits are disabled.

### Proof of Concept
The following Foundry-style PoC demonstrates the cap-saturation sequence using a minimal ERC4626-like vault. The attacker is only a vault depositor and direct token sender.

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import {IERC20Detailed} from
    "../../contracts/interfaces/IERC20Detailed.sol";
import {ProgrammableBorrower} from
    "../../contracts/strategies/idle/ProgrammableBorrower.sol";

contract MockERC20 is ERC20 {
    constructor() ERC20("Mock USDC", "mUSDC") {}

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }
}

/// @notice Minimal capped ERC4626-like vault.
contract CappedVault is ERC20 {
    IERC20Detailed public immutable assetToken;
    uint256 public immutable depositCap;

    constructor(IERC20Detailed asset_, uint256 cap_)
        ERC20("Capped Vault", "CV")
    {
        assetToken = asset_;
        depositCap = cap_;
    }

    function asset() external view returns (address) {
        return address(assetToken);
    }

    function convertToAssets(uint256 shares) external view returns (uint256) {
        uint256 supply = totalSupply();
        if (supply == 0) return shares;
        return shares * assetToken.balanceOf(address(this)) / supply;
    }

    function maxDeposit(address) external view returns (uint256) {
        uint256 assets = assetToken.balanceOf(address(this));
        return assets >= depositCap ? 0 : depositCap - assets;
    }

    function deposit(uint256 assets, address receiver)
        external
        returns (uint256 shares)
    {
        require(
            assetToken.balanceOf(address(this)) + assets <= depositCap,
            "deposit cap"
        );

        uint256 assetsBefore = assetToken.balanceOf(address(this));
        uint256 supply = totalSupply();
        shares = supply == 0 || assetsBefore == 0
            ? assets
            : assets * supply / assetsBefore;

        assetToken.transferFrom(msg.sender, address(this), assets);
        _mint(receiver, shares);
    }

    function withdraw(
        uint256 assets,
        address receiver,
        address owner_
    ) external returns (uint256 shares) {
        uint256 supply = totalSupply();
        uint256 assetsBefore = assetToken.balanceOf(address(this));
        shares = supply == 0 || assetsBefore == 0
            ? assets
            : assets * supply / assetsBefore;

        _burn(owner_, shares);
        assetToken.transfer(receiver, assets);
    }

    function redeem(
        uint256 shares,
        address receiver,
        address owner_
    ) external returns (uint256 assets) {
        uint256 supply = totalSupply();
        assets = shares * assetToken.balanceOf(address(this)) / supply;
        _burn(owner_, shares);
        assetToken.transfer(receiver, assets);
    }
}

contract ProgrammableBorrowerDepositCapTest is Test {
    MockERC20 internal usdc;
    CappedVault internal vault;
    ProgrammableBorrower internal borrower;

    address internal idleCDO = makeAddr("idleCDO");
    address internal manager = makeAddr("manager");
    address internal attacker = makeAddr("attacker");

    uint256 internal constant CAP = 1_000_000e6;
    uint256 internal constant POOL_FUNDS = 100_000e6;

    function setUp() external {
        usdc = new MockERC20();
        vault = new CappedVault(IERC20Detailed(address(usdc)), CAP);

        borrower = new ProgrammableBorrower();
        borrower.initialize(
            address(usdc),
            address(vault),
            idleCDO,
            makeAddr("realBorrower"),
            manager
        );

        usdc.mint(attacker, CAP);
        usdc.mint(idleCDO, POOL_FUNDS);
    }

    function testStartEpochBrickedByDepositCapSaturation() external {
        // Ordinary permissionless vault depositor consumes the whole cap.
        vm.startPrank(attacker);
        usdc.approve(address(vault), CAP);
        vault.deposit(CAP, attacker);
        vm.stopPrank();

        assertEq(vault.maxDeposit(address(borrower)), 0);

        // Even if IdleCDO has no surplus, a direct dust transfer forces the
        // unconditional deposit path. The pool-funded amount is also shown.
        usdc.mint(address(borrower), 1);
        vm.prank(idleCDO);
        usdc.transfer(address(borrower), POOL_FUNDS);

        vm.prank(idleCDO);
        vm.expectRevert(bytes("deposit cap"));
        borrower.onStartEpoch(0);

        // The epoch remains inactive and the borrower-held pool funds remain
        // undeployed while the attacker keeps the vault cap saturated.
        assertFalse(borrower.epochAccountingActive());
        assertEq(usdc.balanceOf(address(borrower)), POOL_FUNDS + 1);
    }
}
```
