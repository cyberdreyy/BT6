### Title
Default recovery price is inflated by excluding unfunded prior-epoch instant-withdraw receipts, letting early claimants drain the reserve and freezing late claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug-class analog (an attacker-influenced key selecting which record participates in a sensitive operation) maps to `defaultPendingClaimBasis`, which decides which receipt epochs enter the default-recovery denominator. When `pendingInstantWithdraws != 0` it adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch bucket — while `pendingInstantWithdraws` and `instantWithdrawsRequests` are aggregates across all request epochs. Unfunded instant receipts requested in earlier epochs are silently dropped from `totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed against a too-small denominator and comes out too high. [1](#0-0) 

### Finding Description
`finalizeDefaultRecovery` computes `recoveryPrice` from `reserveAmount / totalBasis`, where `totalBasis = activeBasis + pendingBasis` and `pendingBasis = defaultPendingClaimBasis()`. [2](#0-1)  That function counts only the current epoch's instant claims even though `pendingInstantWithdraws` can contain receipts from earlier epochs (a partial `collectInstantWithdrawFunds` leaves the remainder pending across `startEpoch`s, and `instantWithdrawsRequestsByEpoch[user][oldEpoch]` stays non-zero until claimed). [3](#0-2) 

Two consequences:

1. **Inflated `defaultRecoveryPrice`.** Default-epoch claimants (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) and post-default requesters are each paid `claimBasis * defaultRecoveryPrice / 1e18` from the fixed `defaultRecoveryReserve`. Because the denominator excluded the old-epoch instant basis, each payment is oversized and the reserve is exhausted before all valid claims are paid; the last claimants revert in `_transferDefaultRecovery` (reserve underflow / insufficient balance) — permanent freezing of unclaimed recovery.
2. **Inflated active-LP NAV.** `activeFinalNAV = activeBasis * recoveryPrice / RECOVERY_FULL` is minted to the CDO, so active tranche holders also receive an over-generous crystallized price paid for by pending-receipt claimants.

The honest manager/borrower sequence that triggers this requires no privileged misbehavior: instant requests partially unfunded in epoch N (borrower liquidity shortfall at `startEpoch`), epoch N+1 runs, borrower defaults, `finalizeDefaultRecovery` runs with whatever recovery is supplied.

### Impact Explanation
Broken invariant: fair loss socialization / "one receipt one payout". Direct quantified effect: every defaulted claim is paid at `price' = R / (B - X)` instead of `R / B`, where `X` is the excluded old-epoch instant basis; total payouts are capped at `R`, so roughly an `X/B` fraction of claim value is redistributed from late claimants (whose claims then revert and freeze) to early claimants and active LPs. This is permanent freezing of unclaimed recovery yield for the claimants who come after the reserve drains.

### Likelihood Explanation
Medium-low. It needs (a) an epoch with instant withdrawals only partially funded so `pendingInstantWithdraws` and an old `instantWithdrawClaimsByEpoch` entry survive into a later epoch, and (b) a subsequent borrower default finalized with partial recovery. Both are ordinary protocol states, not attacker-engineered exotics — the attacker is simply any holder of an old unfunded instant receipt plus any claimant ordering; no privileged role acts maliciously.

### Recommendation
In `defaultPendingClaimBasis`, include the full outstanding instant claim basis, not only the current epoch — e.g., iterate/aggregate all epochs with `instantWithdrawClaimsByEpoch[e] != 0`, or maintain a `totalInstantClaimBasis` counter updated in `requestInstantWithdraw`/`_claimDefaultedInstantWithdrawRequest`/`claimInstantWithdrawRequest` and use it directly. Correspondingly, `_defaultPrefundedInstantReserve` should measure prefunded cash against the aggregate instant basis rather than only `instantWithdrawClaimsByEpoch[epochNumber]`.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
