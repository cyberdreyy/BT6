### Title
Rate-limit bucket disparity allows faster credential/token brute-forcing via `/v2/ping` (and other token/EI-gated routes) than via `/sessions` - (File: core/web/router.go)

### Summary
`/v2/ping` and all other `authv2`/`userOrEI` routes are nested inside the `api` router group, which is wrapped only by the "Authenticated" rate limiter (`rl.AuthenticatedPeriod()`/`rl.Authenticated()`, default 1000 req/min) at `core/web/router.go:78-85`. `POST /sessions`, the only route explicitly intended for unauthenticated credential submission, is deliberately wrapped in the much stricter "Unauthenticated" bucket (default 5 req/20s) at `core/web/router.go:210-215`. Because `auth.AuthenticateByToken` / `auth.AuthenticateExternalInitiator` (`core/web/auth/auth.go:78-151`) simply return a 401 on invalid `X-API-KEY`/`X-API-SECRET` or EI headers without any additional throttling, an unauthenticated attacker sending garbage token/EI headers to `/v2/ping` is bound by the looser 1000/min bucket instead of the 5/20s bucket, allowing roughly 66x more credential-guessing attempts per unit time than the intentionally-protected `/sessions` login path.

### Finding Description
- `NewRouter` mounts the entire `api` group with the "Authenticated" limiter applied at the group level: [1](#0-0) .
- `v2Routes` defines `userOrEI := r.Group("/v2", auth.Authenticate(..., auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession))` and registers `GET /v2/ping` under it, inheriting only the group-level (Authenticated) rate limiter — no additional per-route or per-credential-attempt limiter is applied: [2](#0-1) .
- By contrast, `sessionRoutes` explicitly re-wraps `POST /sessions` in a separate, stricter "Unauthenticated" limiter group: [3](#0-2) .
- `auth.AuthenticateByToken` and `auth.AuthenticateExternalInitiator` treat any invalid/missing/garbage credential as `auth.ErrorAuthFailed` and simply return 401, with no lockout, backoff, or reclassification into the unauthenticated bucket: [4](#0-3)  and the generic `Authenticate` wrapper just aborts with 401 on failure: [5](#0-4) .
- Default configuration confirms the magnitude of the disparity: `Authenticated = 1000` req per `AuthenticatedPeriod = '1m'` vs `Unauthenticated = 5` req per `UnauthenticatedPeriod = '20s'` (≈15/min): [6](#0-5) .

Since an attacker sending invalid `X-API-KEY`/`X-API-SECRET` or EI headers to `GET /v2/ping` never actually authenticates, they are, from a security standpoint, an "unauthenticated" actor probing credentials — yet the router only classifies them by which URL group they hit, not by whether their request actually succeeded in authenticating. This lets such probing traffic ride the "Authenticated" bucket (1000/min) rather than the "Unauthenticated" bucket (5/20s) that the routing design intends for exactly this kind of credential-guessing traffic.

### Impact Explanation
This is a rate-limit/quota-bypass issue (Chainlink bounty class: "allowlist/quota bypass") that increases the practical throughput of API-token and external-initiator credential brute-forcing by roughly 66x compared to the session-login path, using an endpoint (`/v2/ping`) that is otherwise low-value from a data standpoint but reachable by any unauthenticated network client. It does not by itself grant privilege, but it materially weakens the AUTHENTICATION_SOUNDNESS guarantee for token/EI-based auth relative to what the node's own rate-limit design intends (stricter limiter for unauthenticated credential submission). Any endpoint using `auth.AuthenticateByToken`/`auth.AuthenticateExternalInitiator` inherits the same looser bucket, not just `/v2/ping`.

### Likelihood Explanation
No privileges are required — only unauthenticated network access to the node's HTTP API. The attack is trivial to reproduce: send GET requests to `/v2/ping` with varying `X-API-KEY`/`X-API-SECRET` (or EI headers) at up to the "Authenticated" limiter's rate (1000/min by default, configurable) and observe 401 responses without being blocked until that much higher threshold is hit, versus `/sessions` where only 5 attempts per 20s are permitted before 429s. This is deterministic and repeatable given default or typical rate-limit configuration values.

### Recommendation
Apply a stricter, dedicated rate limiter (equivalent to or stricter than the `Unauthenticated` bucket) to routes that accept credential material from potentially-unauthenticated callers before their authenticity has been verified — e.g., wrap `userOrEI`/`authv2` token-authenticating routes (or the `auth.Authenticate` middleware itself) with a rate limiter keyed on failed-authentication attempts, separate from the general "Authenticated" traffic bucket, so that repeated invalid-credential attempts against `/v2/ping` and similar endpoints are throttled at the same strict rate as `/sessions`.

### Proof of Concept
Handler-level Go test plan (using `httptest`/gin test harness similar to existing `core/web/sessions_controller_test.go` and router tests):
1. Build the router via `NewRouter` with `WebServer.RateLimit.Authenticated = N1`/`AuthenticatedPeriod = P1` and `Unauthenticated = N2`/`UnauthenticatedPeriod = P2` set to distinct small values (e.g., Authenticated=50/1m, Unauthenticated=5/20s) for deterministic testing.
2. Fire `N2+1` `POST /sessions` requests with invalid email/password within `P2`; assert the `(N2+1)`th request returns `429 Too Many Requests` (confirms `/sessions` is bound by the Unauthenticated bucket).
3. Fire `N2+1` `GET /v2/ping` requests with garbage `X-API-KEY`/`X-API-SECRET` headers within the same window `P2`; assert these requests all return `401 Unauthorized` and do NOT hit `429` until the request count instead approaches `N1` (the Authenticated bucket), proving `/v2/ping` is bound by the looser Authenticated limiter rather than the Unauthenticated one.
4. Assert `N1 > N2` under default config (`1000` vs `5`/`20s` ≈ `15`/min), demonstrating the quota-bypass magnitude.

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}
