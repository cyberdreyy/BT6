## Title
Signer can double-sign two conflicting tenure-start blocks in the same tenure due to a missing same-tenure duplicate recheck at pre-commit time - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The signer's pre-commit-to-signature path re-validates a tenure-change block via `check_block_against_signer_db_state`, but for tenure-change blocks this recheck only re-verifies the *parent*-tenure confirmation and returns early (`Ok(true) => return None`) without re-running the "already signed a block in this tenure" (`DuplicateBlockFound`) check that `validate_tenure_change_payload` performs only once, at proposal time. The fallback "own-tenure conflict guard" that is supposed to cover this gap is itself conditioned on the stacks-node already having observed the earlier signed block as the tenure's canonical tip — a condition that is false until that earlier block collects a full 70% signature threshold and is pushed to the node. A single equivocating miner can exploit this timing window to get one signer to sign two different, conflicting tenure-start blocks for the same tenure/height.

### Finding Description
`validate_tenure_change_payload` (the proposal-time check) rejects a tenure-start block with `RejectReason::DuplicateBlockFound` if `signer_db.get_last_signed_block` already finds a signed block in that tenure: [1](#0-0) 

This check only counts blocks that carry a signature (`LocallyAccepted`/`GloballyAccepted`); a `PreCommitted` block is deliberately excluded because a pre-commit carries no signature yet.

The recheck run at validate-ok time and again at pre-commit-threshold time is `check_block_against_signer_db_state`. For a tenure-change block it *only* checks parent-tenure confirmation and returns immediately without re-running the own-tenure duplicate check: [2](#0-1) 

This function is invoked directly from the pre-commit-threshold signing path: [3](#0-2) 

The only remaining safeguard is the own-tenure conflict guard that follows, which asks the stacks-node whether its tenure tip is already at or above the proposed height: [4](#0-3) 

If the node hasn't processed the earlier conflicting block yet (normal, since pushing to the node requires the *whole* signer set, not just this one signer, to have signed), or the node lookup errors, the guard does not block and the signer proceeds to `mark_locally_accepted` and sign: [5](#0-4) 

This mirrors the reported analog exactly: like Mango's `HealthRegion`, a check that is normally enforced once ("is the account healthy" / "is there already a signed block in this tenure") is skipped during an intermediate step, and the compensating "end of region" check (`conflict_still_blocks`/node-tip lookup) can be bypassed because the state it depends on (the node having observed the earlier block) has not yet caught up.

### Impact Explanation
This is a Critical-class finding under the stated rubric: a signer signing a conflicting block. If a single signer ends up with valid signatures over two distinct tenure-start blocks at the same height in the same tenure, this breaks the "one signature per height/tenure" invariant the whole pre-commit/conflict-guard machinery (`get_signed_conflicts`, `reorg_permit_stands`, `conflict_still_blocks`) exists to protect, documented in `docs/signer-flows.md` as the guard against "the double-sign this guard exists for." A miner able to induce this on enough signers, or even on one signer whose signature later gets aggregated toward a rival block's 70% threshold, undermines the assumption that a signer's signature commits it to a single fork at that height.

### Likelihood Explanation
Triggerable by a single equivocating miner (a one-slot actor) plus normal gossip timing — no majority of signers or additional keys are required. The race window is realistic: block B's validation/pre-commit can complete and reach threshold before the node has processed/pushed A (which requires collecting signatures from the *entire* signer set, not just this signer), especially under network delay or when signers are unevenly paced.

### Recommendation
Re-run the full same-tenure duplicate check (`get_last_signed_block` against the block's own `consensus_hash`) inside `check_block_against_signer_db_state` for tenure-change blocks, instead of relying solely on the node-tip-based own-tenure conflict guard whose safety depends on the node already having ingested the earlier block.

### Proof of Concept
1. Miner proposes tenure-start block A for tenure T. Signer S validates A (`check_proposal` passes; no prior signed block in T), reaches `PreCommitted`.
2. Before S signs A, miner proposes a different tenure-start block B for the same tenure T (different tx set/signature hash). `check_proposal` for B also passes because A is still only `PreCommitted` (unsigned), so `get_last_signed_block` finds nothing.
3. S's pre-commit threshold for A is reached first; S signs A (`mark_locally_accepted`), per `handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs:1467`).
4. Shortly after, S's pre-commit threshold for B is reached. `check_block_against_signer_db_state` for B only checks the parent tenure (`stacks-signer/src/v0/signer.rs:1809-1826`) and passes. The own-tenure conflict guard queries `stacks_client.get_tenure_tip(T)`; since A has not yet collected the full signer-set signature threshold to be pushed to the node, the node's tenure tip for T is still below B's height (or the RPC call fails), so the guard does not block.
5. S signs B too (`mark_locally_accepted` at line 1467), producing two signatures from the same signer over two conflicting blocks at the same height in tenure T.

    fn check_block_against_signer_db_state(
        &mut self,
        stacks_client: &StacksClient,
        proposed_block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = proposed_block.header.signer_signature_hash();
        // If this is a tenure change block, ensure that it confirms the correct number of blocks from the parent tenure.
        if let Some(tenure_change) = proposed_block.get_tenure_change_tx_payload() {
            // Ensure that the tenure change block confirms the expected parent block
            match SortitionData::check_tenure_change_confirms_parent(
                tenure_change,
                proposed_block,
                &mut self.signer_db,
                stacks_client,
                self.proposal_config.tenure_last_block_proposal_timeout,
                self.proposal_config.reorg_attempts_activity_timeout,
            ) {
                Ok(true) => return None,
                Ok(false) => {
                    return Some(self.create_block_rejection(
                        RejectReason::SortitionViewMismatch,
                        proposed_block,
                    ))
                }
                Err(e) => {
                    warn!("{self}: Error checking block proposal: {e}";
                        "signer_signature_hash" => %signer_signature_hash,
                        "block_id" => %proposed_block.block_id()
                    );
                    return Some(self.create_block_rejection(
                        RejectReason::ConnectivityIssues(
                            "error checking block proposal".to_string(),
                        ),
                        proposed_block,
                    ));
                }
            }
        }
