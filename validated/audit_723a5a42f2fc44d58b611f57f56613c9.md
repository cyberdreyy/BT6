### Title
Case-sensitive email key comparison in LDAP upstream sync causes revoked users' sessions/tokens to never be purged - ([File: core/sessions/ldapauth/sync.go])

### Summary
`LDAPServerStateSyncer.Work` builds `upstreamUserStateMap` keyed by the raw, non-lowercased `uid=` value parsed from LDAP `uniqueMember` entries, while `ldap_sessions`/`ldap_user_api_tokens` rows are created and keyed by `strings.ToLower(sr.Email)` at login. Because the purge/role-update comparisons use exact Go map lookups (`upstreamUserStateMap[ldapSession.UserEmail]`), any casing mismatch between the directory's `uid` value and the lower-cased DB email causes the sync logic to treat an upstream-revoked user as still present, permanently skipping deletion of their session/API token row.

### Finding Description
- At login, `CreateSession` (core/sessions/ldapauth/ldap.go) inserts `strings.ToLower(sr.Email)` into `ldap_sessions.user_email`: [1](#0-0) 
- During the periodic/interval sync, `ldapGroupMembersListToUser` parses the `uid=` component directly out of the `uniqueMember` DN string without any case normalization and stores it as `Email` in the returned `sessions.User`: [2](#0-1) 
- `Work` then keys the source-of-truth map by this un-normalized email: [3](#0-2) 
- The purge and role-sync logic performs exact map lookups against DB rows that are always stored lower-case, with no `strings.ToLower` normalization applied to either side of the comparison: [4](#0-3)  and [5](#0-4) 

If the directory's `uid` attribute for a user contains any uppercase characters (a legitimate, common occurrence in real LDAP/AD deployments where `uid`/`sAMAccountName` case is not normalized), the corresponding `ldap_sessions`/`ldap_user_api_tokens` row (stored lower-case) will never match a key in `upstreamUserStateMap`. Consequently:
1. Even after the user is fully removed from all role groups upstream (real revocation), `emailsToPurge`/`apiTokenEmailsToPurge` never contain that user's row because `upstreamUserStateMap` was already never keyed consistently with the DB — but more critically, once removed upstream the row is *supposed* to be purged and normally would be, EXCEPT prior to removal, the mismatched casing also means role escalations/de-escalations from `UPDATE ldap_sessions SET user_role = CASE ...` are silently skipped, since `sessionOk`/`tokenOk` lookups (line 251-252) never match.
2. Net effect: cached role and continued session validity for a mixed-case-uid user are never reconciled with the upstream source of truth by the syncer, independent of whether the user was removed or downgraded upstream, because the syncer can never find the DB row's email in its map.

### Impact Explanation
This is an authorization/session-revocation bypass: a valid session or long-lived API token created by `CreateSession`/`SetAuthToken` continues to be honored by `AuthorizedUserWithSession` / `FindUserByAPIToken` (which trust the cached `ldap_sessions`/`ldap_user_api_tokens` rows without re-querying LDAP) even after the account is removed from all upstream groups, because the reconciliation job in `Work` can never locate the matching DB row to delete it or downgrade its role. This matches "undeletable access" / stale-session persistence after revocation — a real node compromise vector via retained unauthorized access to the node's job/API surface at the previously granted role.

### Likelihood Explanation
The precondition is simply that the LDAP/AD `uid` (or equivalent `BaseUserAttr`) value for an account contains uppercase characters — a routine occurrence in many directory configurations (this is not attacker-crafted privilege escalation, but a naturally occurring code defect that silently disables revocation for any such account). No special LDAP write access or attacker manipulation of their own uid casing is required beyond having been provisioned with a mixed-case identifier, which is common in real deployments (e.g. `uid=John.Doe@Example.com`). The bug is deterministic and 100% reproducible for any account whose `uid` casing differs from lower-case.

### Recommendation
Normalize casing consistently on both sides of every comparison in `sync.go`'s `Work`: lower-case `userEmail` when populating `sessions.User.Email` in `ldapGroupMembersListToUser` (core/sessions/ldapauth/ldap.go line 764), and/or apply `strings.ToLower` when building `upstreamUserStateMap` keys and when comparing against `existingSessionsMap`/`existingAPITokensMap` keys in `sync.go`. Also fix `validateUsersActive`'s email-to-active map key comparisons (`sync.go` lines 355-366) for the same reason.

### Proof of Concept
1. Mock `LDAPConn.Search` so a group query returns a single `uniqueMember` value `uid=Attacker@Example.COM,ou=users,dc=example,dc=com` for e.g. the Admin group, and empty results for the other three role groups.
2. Seed the test DB with an `ldap_sessions` row where `user_email = 'attacker@example.com'` (lower-cased, as `CreateSession` would store) and `localauth_user = false`.
3. Call `LDAPServerStateSyncer.Work(ctx)`.
4. Assert:
   - `upstreamUserStateMap` contains key `"Attacker@Example.COM"` (not lower-cased) — demonstrating the mismatch.
   - After `Work` completes, the `ldap_sessions` row for `attacker@example.com` still exists (was not purged) and its role was not updated, even when the group query is changed to return zero uniqueMembers for that user in a follow-up sync call (simulating real revocation) — showing the purge silently fails to find/delete the row due to case mismatch.
