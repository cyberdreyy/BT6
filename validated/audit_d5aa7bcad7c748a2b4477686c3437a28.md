### Title
Claimed instant-withdraw receipts are never cleared from `instantWithdrawsRequestsByEpoch`, enabling a post-default double claim and recovery-reserve insolvency - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` records receipt basis in two places: `instantWithdrawsRequests[_user]` (aggregate) and `instantWithdrawsRequestsByEpoch[_user][epoch]` plus `instantWithdrawClaimsByEpoch[epoch]` (per-epoch). The normal claim path `claimInstantWithdrawRequest` clears only the aggregate, never the per-epoch entries — the same bug class as CVE-2024-53077 (an `xa_init_flags` allocation without a matching `xa_destroy`). If the pool defaults in that epoch while any instant basis is still unfunded (`pendingInstantWithdraws != 0`), the already-paid receipt is (a) counted again in `defaultPendingClaimBasis`, (b) counted as still-held prefunded reserve in `_defaultPrefundedInstantReserve`, and (c) claimable a second time through `_claimDefaultedInstantWithdrawRequest`.

### Finding Description
- `requestInstantWithdraw` accrues `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` [1](#0-0) .
- `claimInstantWithdrawRequest` burns the receipt and zeroes only `instantWithdrawsRequests[_user]`; neither per-epoch mapping is touched [2](#0-1) . The only cleanup of `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` lives in `_claimDefaultedInstantWithdrawRequest` [3](#0-2) , which runs only after default finalization.
- At finalization, `defaultPendingClaimBasis` adds the full `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) , including the attacker's already-claimed receipt.
- `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying still held by the strategy [5](#0-4) , but the attacker already withdrew that portion, so `defaultRecoveryReserve` is set higher than the real balance [6](#0-5) .
- After finalization, `claimInstantWithdrawRequest` routes through `_claimDefaultedInstantWithdrawRequest`, which reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and pays `claimBasis * defaultRecoveryPrice` again [7](#0-6) .

### Impact Explanation
Two compounding effects in the `defaulted → finalized` phase:

1. **Double payout / reserve inflation.** The attacker is paid once at par and again at the recovery price. Simultaneously, `reserveAmount` overstates actual holdings by the already-claimed amount, so `defaultRecoveryReserve` exceeds `underlyingToken.balanceOf`. Every `_transferDefaultRecovery` decrements the reserve [8](#0-7) ; once real tokens run out, later honest claimants' recovery claims revert on `safeTransfer` — permanent freezing/theft of their unclaimed recovery, quantified as the attacker's claim basis (up to the full instant-claim bucket for that epoch).
2. **Dilution.** `instantWithdrawClaimsByEpoch` keeps the claimed basis, inflating `totalBasis` and lowering `defaultRecoveryPrice` for every defaulted claimant, socializing an extra loss equal to the phantom basis.

### Likelihood Explanation
Requires: an epoch where some instant withdrawals are funded/collected and claimed (per-epoch state left stale), at least one instant request left unfunded so `pendingInstantWithdraws != 0`, and a borrower default finalized in that epoch. The attacker needs only to be a KYC'd lender able to call `requestInstantWithdraw`/`claimInstantWithdrawRequest` via the CDO — no privileged role. Honest manager/borrower calls (collect, default, `finalizeDefaultRecovery`) supply the sequencing. The funding shortfall needed to keep `pendingInstantWithdraws != 0` occurs naturally whenever instant liquidity only partially covers the queue.

### Recommendation
In `claimInstantWithdrawRequest`, delete the per-epoch state just like `_claimDefaultedInstantWithdrawRequest` does: locate the user's request-epoch entry (or iterate/record it at request time) and set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and `instantWithdrawClaimsByEpoch[epoch] -= amount`. Equivalently, ensure every per-epoch allocation made in `requestInstantWithdraw` has a matching cleanup on the normal claim path — the `xa_init_flags`/`xa_destroy` pairing.

### Proof of Concept
Foundry fork PoC (against a live Clearpool-style credit vault pool, using the existing `IdleCreditVault.t.sol` harness):

```solidity
function testStaleInstantReceiptDoubleClaim() external {
    // --- epoch E running; attacker is a KYC'd AA/BB holder ---
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _depositWithUser(victim,   100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);
    uint256 epoch = IdleCreditVault(address(strategy)).epochNumber();

    // 1) attacker requests instant withdraw; CDO funds it fully
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(50_000 * ONE_SCALE, address(AAtranche));
    // CDO collects funding (honest manager path)
    // collectInstantWithdrawFunds(50_000 * ONE_SCALE) via idleCDO ...
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();   // paid at par
    // stale: instantWithdrawsRequestsByEpoch[attacker][epoch] still == 50_000e18

    // 2) victim requests instant withdraw; only partially funded so
    //    pendingInstantWithdraws != 0 at default time
    vm.prank(victim);
    cdoEpoch.requestInstantWithdraw(80_000 * ONE_SCALE, address(AAtranche));
    // (fund only part of it via collectInstantWithdrawFunds)

    // 3) borrower defaults; owner/manager finalize recovery (honest calls)
    _handleBorrowerDefaultAndFinalize(/* recoveredAmount */);

    // 4) stale entry pays the attacker a second time at recovery price
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = underlying.balanceOf(attacker) - balPre;
    assertGt(stolen, 0); // == 50_000e18 * defaultRecoveryPrice / 1e18

    // 5) reserve now exceeds real balance: victim's recovery claim reverts
    vm.prank(victim);
    vm.expectRevert(); // safeTransfer fails: reserve inflated by prefundedReserve
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Key assertions to wire in the harness: after step 1, `strategy.instantWithdrawsRequestsByEpoch(attacker, epoch) != 0` while `strategy.instantWithdrawsRequests(attacker) == 0`; after finalization, `strategy.defaultRecoveryReserve() > underlying.balanceOf(address(strategy))` minus pre-existing obligations, demonstrating the phantom reserve.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```

```text
  function _transferDefaultRecovery(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
```
