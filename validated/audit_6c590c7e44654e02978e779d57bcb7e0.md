### Title
Stop-epoch loss haircut keyed to post-increment `epochNumber` lets pending withdraw receipts claim at par, draining the vault - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The credit vault keys the stop-epoch loss haircut (`lossRecoveryPriceByEpoch`) to `epochNumber`, but `epochNumber` is incremented inside `deposit()` during `stopEpoch`, while user receipts are keyed to `lastWithdrawRequest`, which still points at the request epoch. The mismatch makes the loss-adjusted claim path a no-op, so the un-haircutted funded path pays full basis while the strategy only holds the haircutted funding — a bookkeeping race between the epoch counter mutation and the pending-receipt accounting, analogous to iterating a list concurrently with its mutation in the kernel report.

### Finding Description
`requestWithdraw` records the receipt epoch as `lastWithdrawRequest[_user] = epochNumber` (request epoch N) and accumulates `withdrawsRequestsByEpoch[_user][N]` (`IdleCreditVault.sol:282,293`). During `stopEpoch`, the CDO calls `deposit()`, which detects `isEpochRunning()` still true and executes `epochNumber += 1` before the flag clears (`IdleCreditVault.sol:607-611`). `collectWithdrawFunds` then stores the realized-loss price under `lossRecoveryPriceByEpoch[epochNumber]`, i.e. under the already-incremented epoch N+1 (`IdleCreditVault.sol:417-421`).

At claim time, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — epoch N — finds `0`, and returns without clearing or haircutting (`IdleCreditVault.sol:789-792`). Execution falls through to `_claimFundedWithdrawRequest`, whose gating passes because `epochNumber (N+1) > lastWithdrawRequest (N)` (`IdleCreditVault.sol:326`), and it transfers the full un-haircutted `withdrawsRequests[_user]` via `_transferFundedClaim` (`IdleCreditVault.sol:338-349`).

The same key mismatch also disables the `requestWithdraw` guard at `IdleCreditVault.sol:261-270`, so users may stack new requests on top of the "lost" haircut receipt.

### Impact Explanation
`collectWithdrawFunds` only pulls `pendingBasis - pendingLoss` underlying into the strategy when `_amount < pendingBasis` (`IdleCreditVault.sol:411-430`). Every receipt holder then claims 100% of basis instead of `claimBasis * lossRecoveryPrice`. The shortfall is socialized: early claimants drain the haircutted balance plus any other underlyings held (default recovery reserve is protected by the `_transferFundedClaim` guard, but the funded bucket itself is under-collateralized), and later claimants revert on transfer — insolvency. Loss equals `pendingLoss` (the portion of `_lossAmount` allocated to pending receipts by `previewLossAdjustedWithdrawFunds`), directly borne by the last claimants and, via the burned/short NAV, by remaining LPs.

### Likelihood Explanation
Triggering requires only the normal epoch lifecycle: an unprivileged lender calls `requestWithdraw` during a running epoch, then the honest manager calls `stopEpochWithDuration` (or `stopEpoch`) realizing a loss such that `collectWithdrawFunds` receives less than `pendingWithdraws`. No attacker timing, reentrancy, or privileged collusion is needed — the ordering of `deposit()`/epoch increment before `collectWithdrawFunds` inside the CDO's `stopEpoch` is deterministic. The only precondition is a non-zero realized loss while `pendingWithdraws > 0`, which is exactly the scenario `lossRecoveryPriceByEpoch` was built for. Caveat: the exploit depends on the CDO invoking `deposit()` (incrementing `epochNumber`) before `collectWithdrawFunds` inside `stopEpoch`; that call ordering is in `IdleCDOEpochVariant.stopEpoch` and should be confirmed when building the PoC — the vault code itself guarantees the key divergence whenever funding happens after the increment.

### Recommendation
Key the loss haircut to the request epoch, not the post-increment counter. Concretely, in `collectWithdrawFunds` store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or capture the epoch before `deposit()` bumps it), or have the CDO call `collectWithdrawFunds` before the deposit that increments `epochNumber`. Alternatively, track pending receipts by a stable `requestEpoch` id and pass the request epoch explicitly into the loss-bookkeeping call so the lookup key in `_claimLossAdjustedWithdrawRequest` and `requestWithdraw` matches the stored slot.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
// test/foundry/IdleCreditVaultLossEpoch.t.sol
function testLossAdjustedReceiptClaimsAtPar() public {
    // Setup: epoch running, Alice deposits 100e6 USDC via CDO (AA or BB)
    uint256 amt = 100e6;
    _depositAsLender(alice, amt);

    // Alice requests withdraw of the full position during epoch N
    uint256 reqEpoch = vault.epochNumber();          // N
    vm.prank(address(cdo));
    vault.requestWithdraw(amt, alice, amt);
    assertEq(vault.lastWithdrawRequest(alice), reqEpoch);

    // Borrower returns less than owed: manager calls stopEpochWithDuration(loss)
    // Inside stopEpoch: CDO -> vault.deposit(...) bumps epochNumber to N+1,
    // then vault.collectWithdrawFunds(funded < pendingWithdraws) stores
    // lossRecoveryPriceByEpoch[N+1] instead of [N].
    uint256 loss = 20e6;
    _stopEpochWithLoss(loss);                        // honest manager call

    // Haircut slot for Alice's epoch is empty -> loss-adjusted path skipped
    assertEq(vault.lossRecoveryPriceByEpoch(reqEpoch), 0);
    assertGt(vault.lossRecoveryPriceByEpoch(reqEpoch + 1), 0);

    // Funded-claim path passes the epoch gate (N+1 > N) and pays full basis,
    // while the strategy only received pendingBasis - pendingLoss
    uint256 balBefore = usdc.balanceOf(alice);
    vm.prank(address(cdo));
    uint256 paid = vault.claimWithdrawRequest(alice);
    assertEq(paid, amt);                             // full amount, no haircut
    assertGt(paid, amt * vault.lossRecoveryPriceByEpoch(reqEpoch + 1) / 1e18);
    // Strategy underlyings now short by pendingLoss: a second claimant reverts
    // or LP NAV silently absorbed the loss.
}
```
