### Title
Unbuffered `waitCh` in custom-executor `command` causes permanent goroutine + zombie-process leak when `KillAndWait` times out - (File: executors/custom/command/command.go)

### Summary
`KillAndWait` in `helpers/process/killer.go` returns a `KillProcessError` after `forceKillTimeout` elapses without ever cancelling the `cmd.Wait()` goroutine that owns the same `waitCh`. In the shell executor this is harmless because `waitCh` is buffered (`make(chan error, 1)`), but in the custom executor's `command.Run()` the channel is unbuffered (`waitCh: make(chan error)`), so if the target process never actually exits (e.g., it is left in an uninterruptible D-state or self-SIGSTOPped so SIGKILL cannot be delivered/processed), the `waitForCommand` goroutine blocks forever inside `c.cmd.Wait()` and then blocks forever again trying to send on an unbuffered channel with no reader.

### Finding Description
`KillAndWait` (helpers/process/killer.go:66-92) sends SIGTERM via `Terminate()`, waits `gracefulKillTimeout`, sends SIGKILL via `ForceKill()`, waits `forceKillTimeout`, and if `waitCh` never fires, gives up and returns `&KillProcessError{pid: process.Pid}` [1](#0-0) . Neither `Terminate` nor `ForceKill` in `helpers/process/killer_unix.go` do anything beyond issuing `syscall.Kill`; if the target is stopped (SIGSTOP) or stuck in D-state, the signal is queued but never actually terminates the process, so `waitCh` is never written by the real owner of that channel [2](#0-1) .

The custom executor creates `waitCh` unbuffered and starts a dedicated goroutine that calls the blocking `c.cmd.Wait()` and then sends the result on `c.waitCh`: [3](#0-2) [4](#0-3) 
`Run()` selects on `c.waitCh` or `ctx.Done()`, and on cancellation calls `KillAndWait(c.cmd, c.waitCh)`, which returns `KillProcessError` once `forceKillTimeout` elapses [5](#0-4) . At that point `Run()` returns to its caller, but the `waitForCommand` goroutine started at line 87 is still blocked inside `c.cmd.Wait()`. Since the underlying OS process is stuck (D-state/self-stopped) and was never actually reaped, `Wait()` never returns; if it eventually does return (process later resumes/finishes), the goroutine then tries `c.waitCh <- err` on an unbuffered channel with no receiver (nothing in the codebase reads `c.waitCh` after `Run()` has returned), permanently blocking that goroutine.

This differs from the shell executor, where the equivalent goroutine writes to a buffered channel (`waitCh := make(chan error, 1)` at `executors/shell/shell.go:108`), so the send never blocks even without a reader — that path does not leak in the same way [6](#0-5) . No cancellation, timeout, or `context` is wired into `c.cmd.Wait()` itself in the custom executor, and there is no code anywhere that detaches/cancels the `waitForCommand` goroutine after `KillAndWait` gives up.

### Impact Explanation
Each job that (a) is cancelled/times out and (b) puts its process into a signal-undeliverable state (self-SIGSTOP, or heavy uninterruptible I/O producing D-state) leaves behind one goroutine permanently blocked on `c.cmd.Wait()`/channel send in the custom executor, and one un-reaped OS process. Repeated across many jobs this accumulates goroutines and, more importantly, un-reaped process-table entries, which is a real, bounded-but-cumulative resource leak on the runner host. This matches the "resource/goroutine leak" portion of the scoped impact. However, the claim that this also blocks "executor concurrency slots" for subsequent jobs is not supported: `Run()` returns normally (with `KillProcessError`) once `KillAndWait` times out, so the job's build finishes from the Runner's scheduling perspective and the concurrency slot is freed — only the shell executor's buffered-channel behavior and this custom-executor unbuffered-channel goroutine/process leak are concretely verifiable, not a persistent slot block.

### Likelihood Explanation
Reachable only through the custom executor (`executors/custom/command/command.go`), which requires the runner to be configured with `executor = "custom"`. Preconditions match the question: an unprivileged job author running a custom-executor job can self-SIGSTOP or trigger a D-state process (e.g. via NFS/heavy I/O) before/at cancellation time, causing `Terminate`/`ForceKill` to be ineffective and `KillAndWait` to time out. This is reproducible deterministically with a test process that ignores/stops itself, following the pattern already used in `helpers/process/killer_integration_test.go`.

### Recommendation
In `executors/custom/command/command.go`, make `c.waitCh` buffered (`make(chan error, 1)`), mirroring `executors/shell/shell.go`, so the `waitForCommand` goroutine can always complete its send and exit even if nobody reads it after `KillAndWait` gives up. Additionally, consider detaching/logging or metrics-tracking processes that outlive `KillProcessError` so operators can detect accumulating zombies/D-state processes, since the underlying OS process itself is not forcibly reclaimed by this fix (SIGKILL cannot forcibly clear D-state).

### Proof of Concept
Go integration test (extend `helpers/process/killer_integration_test.go` pattern, then apply to `executors/custom/command`):
1. Build a test binary that, on start, sends itself SIGSTOP (or performs an uninterruptible syscall) so it ignores SIGTERM/SIGKILL delivery.
2. Construct a `command` via `command.New` with a short `gracefulKillTimeout`/`forceKillTimeout`, `Start()` it, then cancel its context immediately.
3. Assert `Run()` returns a `KillProcessError`-wrapped error within the configured timeouts.
4. Capture `runtime.NumGoroutine()` before the test and, after `Run()` returns and a short settle period, assert goroutine count has returned to baseline — expect it does **not**, demonstrating the leaked `waitForCommand` goroutine blocked on `c.cmd.Wait()`/unbuffered channel send.
5. Repeat steps 2-4 in a loop (e.g., 50 iterations) and assert goroutine count grows roughly linearly with iterations, confirming accumulation rather than a one-off leak.

func (pk *unixKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGTERM)
	if err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}

func (pk *unixKiller) ForceKill() {
	if pk.cmd.Process() == nil {
		return
	}

	err := syscall.Kill(pk.getPID(), syscall.SIGKILL)
	if err != nil {
		pk.logger.Warn("Failed to force-kill:", err)
	}
}

func (c *command) waitForCommand() {
	err := c.cmd.Wait()

	eerr, ok := err.(*exec.ExitError)
	if ok {
		exitCode := getExitCode(eerr)
		switch {
		case exitCode == BuildFailureExitCode:
			err = c.parseBuildFailure(eerr)
		case exitCode != SystemFailureExitCode:
			err = &ErrUnknownFailure{Inner: eerr, ExitCode: exitCode}
		}
	}

	c.waitCh <- err
}
