### Title
`ExtractZipArchive` writes files using raw zip entry names without path validation, allowing absolute-path/path-traversal writes outside the extraction root - (File: helpers/archives/zip_extract.go)

### Summary
`ExtractZipArchive` and its helpers (`extractZipFile`, `extractZipFileEntry`, `extractZipDirectoryEntry`, `extractZipSymlinkEntry`) use the attacker-controlled `zip.File.Name` field directly as a filesystem path argument to `os.Mkdir`, `os.MkdirAll`, `os.OpenFile`, and `os.Symlink`, with no check for absolute paths, drive-qualified paths, or `..` traversal segments. The only pre-write validation performed is `errorIfGitDirectory`, which solely detects a leading `.git` path component and has nothing to do with path confinement.

### Finding Description
`ExtractZipArchive` iterates `archive.File` and, for each entry, calls `extractZipFile(file)` (helpers/archives/zip_extract.go:93), which in turn:
- Calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` (helpers/archives/zip_extract.go:63)
- Dispatches to `extractZipDirectoryEntry` (`os.Mkdir(file.Name, ...)`, line 13), `extractZipSymlinkEntry` (`os.Symlink(data, file.Name)`, line 37), or `extractZipFileEntry` (`os.OpenFile(file.Name, ...)`, line 51)

None of these functions call `filepath.Clean`, check `filepath.IsAbs`, strip volume names (Windows drive letters, UNC paths), or otherwise confine `file.Name` to a caller-supplied restore root. The only sanitation applied anywhere in the extraction path is `errorIfGitDirectory` (helpers/archives/path_check_helper.go:13-31), which only rejects entries whose first cleaned path component is `.git` — it does not reject absolute paths, drive letters, or `..` segments.

Go's `archive/zip` package does **not** sanitize `File.Name` for direct field access; the standard library's path-traversal protections (added to `zip.Reader.Open`) only apply when using the `fs.FS`-style `Open` method, which `ExtractZipArchive` does not use — it iterates `archive.File` directly and calls `file.Open()` to get a reader, then applies `file.Name` verbatim as a destination path. Consequently, a crafted zip archive with an entry name such as `/etc/passwd`, `C:\Windows\System32\...` (drive-qualified on Windows), or `../../../outside/file` will be written exactly to that absolute/traversed path when `ExtractZipFile`/`ExtractZipArchive` is invoked, regardless of the intended extraction root the caller assumed was enforced.

This function is reachable from job-controlled inputs: cache and artifact archives supplied by a pipeline are downloaded and extracted via this code path (`commands/helpers/cache_extractor.go`, `commands/helpers/archive/ziplegacy/zip_legacy_extractor.go` call into `ExtractZipFile`/`ExtractZipArchive`). Since cache/artifact archive *contents* (including entry names) are attacker-controlled by the job/pipeline author, this satisfies the "attacker controls archive bytes, entry names, absolute paths" precondition in the question.

### Impact Explanation
An unprivileged pipeline author who can produce/upload a cache or artifact archive (e.g., building it in an earlier job stage, or via a job that fetches/creates such an archive) can craft entry names that are absolute or traversal paths. When Runner restores that cache/artifact in a later job on the same host/executor (e.g., shared shell executor runner, or same container reused across restores), the extraction writes outside the intended cache/build directory, potentially overwriting files elsewhere on the executor's filesystem that the job process has write permission to. This matches "cross-job state tampering or stronger-context file overwrite" — for example, overwriting shared runner configuration/scripts, tampering with files used by subsequent jobs on the same host, or corrupting files outside the build directory that other jobs/tooling on that host trust.

### Likelihood Explanation
Feasibility is high: creating a zip file with absolute-path entry names is trivial (either via a small Go/Python script using `archive/zip` semantics, or manually crafting the zip central directory since the format has no restriction on entry name content). The only precondition is that the runner extracts a cache/artifact archive whose bytes the attacker controls, which is a normal, documented capability of GitLab CI (custom cache paths, artifact paths) — no special privilege is required. The vulnerability is deterministic and repeatable on every extraction of a malicious archive.

### Recommendation
Before using `file.Name` for any filesystem operation in `zip_extract.go`, validate and confine it to the intended extraction root:
- Reject entries where `filepath.IsAbs(file.Name)` is true, or where the cleaned path begins with a volume/UNC prefix (`filepath.VolumeName(file.Name) != ""`).
- Join `file.Name` against the destination root, `filepath.Clean` the result, and verify (via `filepath.Rel` or a prefix check with a trailing separator) that the resulting path is still inside the destination root before calling `os.Mkdir`, `os.MkdirAll`, `os.OpenFile`, or `os.Symlink`.
- Apply the same validation for symlink targets in `extractZipSymlinkEntry`, since the link target itself is also attacker-controlled data and can point outside the root.
- Extend `errorIfGitDirectory`-style pre-checks into a general `validateEntryPath` function applied to every `file.Name` prior to any filesystem mutation, and treat violations as fatal (or skip the entry) rather than merely logging a warning like the `.git` case.

### Proof of Concept
```go
package archives

import (
    "archive/zip"
    "bytes"
    "os"
    "path/filepath"
    "testing"

    "github.com/stretchr/testify/require"
)

func TestExtractZipArchive_AbsolutePathEscapesRoot(t *testing.T) {
    // Build a malicious zip in memory with an absolute-path entry.
    var buf bytes.Buffer
    zw := zip.NewWriter(&buf)
    target := filepath.Join(os.TempDir(), "zipslip_poc_outside_root.txt")
    f, err := zw.Create(target) // absolute path used directly as entry name
    require.NoError(t, err)
    _, err = f.Write([]byte("attacker controlled content"))
    require.NoError(t, err)
    require.NoError(t, zw.Close())

    zr, err := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    require.NoError(t, err)

    // Simulate extraction into an isolated "root" working directory.
    workDir := t.TempDir()
    cwd, _ := os.Getwd()
    require.NoError(t, os.Chdir(workDir))
    defer os.Chdir(cwd)

    defer os.Remove(target)
    err = ExtractZipArchive(zr)
    require.NoError(t, err)

    // Assert: the file must NOT have been written outside workDir.
    _, statErr := os.Stat(target)
    require.True(t, os.IsNotExist(statErr),
        "expected absolute-path entry to be rejected/confined, but file was written outside the extraction root at %s", target)
}
```
Expected (secure) behavior: the assertion passes because the absolute-path entry is rejected or rewritten to stay inside `workDir`. Current behavior: the file is created at the absolute path outside `workDir`, and the test fails, confirming the escape.
