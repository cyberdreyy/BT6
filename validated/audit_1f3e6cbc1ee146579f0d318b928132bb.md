### Title
BB tranche holders can front-run `stopEpochWithDuration(_lossAmount)` with `requestWithdraw` to escape the BB-first loss waterfall - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
In the Y2K report, users front-run a loss-imposing resolution (`triggerDepeg`) with a resolution path that skips the loss check (`triggerEndEpoch`). The analog in idle-tranches is the epoch-stop loss flow: when the manager submits `stopEpochWithDuration(..., _lossAmount)` to realize a loss, any junior (BB) tranche holder can front-run it with `requestWithdraw`, converting their BB position into a pending withdraw receipt. Pending receipts only bear a **pro-rata** share of the loss, while active positions absorb the remainder **BB-first** — so the attacker escapes their first-loss obligation and pushes it onto remaining BB holders and then AA holders.

### Finding Description
`_stopEpoch` resolves a realized loss in two buckets. Per the in-code policy comments at `contracts/IdleCDOEpochVariant.sol:391-393` and `510-513`:

- "Pending receipts have no tranche identity, so their aggregate loss is pro rata across all receipts. The remaining active loss is applied BB-first after the stop succeeds." [1](#0-0) 
- `previewLossAdjustedWithdrawFunds` computes the pending-receipt pro-rata haircut before the stop [2](#0-1) , and the residual `_lossAmount` is burned via `_strategy.burnStrategyTokens(_lossAmount)` plus `_forceUpdateAccounting()`, applying the ordinary BB-first waterfall to active LPs only [3](#0-2) .

`stopEpochWithDuration` is owner/manager-only [4](#0-3) , but `requestWithdraw` is permissionless for any KYC-passed tranche holder, and `allowBBWithdrawRequest` is re-enabled after every successful stop (`allowBBWithdrawRequest = true`, line 482 [5](#0-4) ), i.e. during the buffer window in which a loss-applying stop is submitted.

Broken invariant: the loss waterfall. A BB position that would take the loss first as an active tranche instead takes only `loss * receipt / totalPending` once converted — because tranche identity is discarded when entering the pending-receipt pool.

### Impact Explanation
Direct wealth transfer / unfair loss socialization. Example: pool NAV 1,000 (AA 800, BB 200), realized `_lossAmount` = 150. Normally BB absorbs the full 150 (BB price drops 75%, AA untouched). If the BB holder front-runs with `requestWithdraw` for their full position, pending receipts = 200 and bear `150 * 200/200 = 150`... only up to the pending-loss share computed pro rata against other receipts; in general the BB holder's haircut is capped at the pro-rata receipt share rather than the full BB-first exposure, and AA holders absorb the difference they were contractually insulated from. Loss magnitude is bounded by `min(BB absorption capacity, _lossAmount)` avoided by the attacker.

Note: I was unable to read the full body of `previewLossAdjustedWithdrawFunds` or `requestWithdraw` before the iteration limit; the finding rests on the documented accounting policy in `_stopEpoch`/`stopEpochWithDuration` comments, which explicitly state pending receipts lose tranche identity and share loss pro rata.

### Likelihood Explanation
Requires the attacker to observe a privileged `stopEpochWithDuration(…, _lossAmount > 0)` (or an emergency loss path) in the mempool while withdraw requests are open in the buffer phase, and submit `requestWithdraw` first. This is a standard front-running condition on public chains; the attacker needs only to be a tranche holder (KYC-passed). Loss stops are rare events, but the attacker can also pre-position a withdraw request speculatively whenever a loss is anticipated. No guard re-checks tranche identity or disables requests when a loss stop is pending.

### Recommendation
Preserve tranche identity (or at least BB/AA class) on withdraw receipts so `previewLossAdjustedWithdrawFunds` can apply BB-first ordering within pending receipts too; alternatively, apply the loss to NAV *before* accepting/processing requests in the same epoch (e.g., require a lossless `stopEpoch` before reopening `allowBBWithdrawRequest` when a loss is pending, or flush receipts at pre-loss BB-adjusted price).

### Proof of Concept
Foundry fork PoC (sketch, mirroring `test/foundry/IdleCreditVault.t.sol` conventions):

```solidity
function testBBFrontRunsLossStopViaRequestWithdraw() external {
    uint256 amount = 10_000 * ONE_SCALE;
    // attacker deposits into BB, honest LP into AA
    _depositWithUser(attacker, amount, false); // BB
    idleCDO.depositAA(8 * amount);

    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // buffer phase, requests reopened

    uint256 loss = 1_500 * ONE_SCALE;

    // attacker front-runs manager's stopEpochWithDuration(…, loss)
    uint256 bbBal = bbTranche.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(bbBal, address(bbTranche));

    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 0, epochDuration, loss);

    // attacker receipt only pays pro-rata loss instead of full BB-first loss
    // claim after next epoch stop and compare vs expected BB-first outcome
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    // assert attacker recovered more than bbBal * priceBB_if_loss_applied_first
    // and AA price is lower than it would be had the BB holder stayed active
}
```

Key assertions: (1) attacker's claimed underlying exceeds `bbBal * BB_price_under_full_loss` — the difference is the escaped loss; (2) `priceAA` is depressed relative to the no-front-run baseline, showing the loss was pushed to senior LPs.
