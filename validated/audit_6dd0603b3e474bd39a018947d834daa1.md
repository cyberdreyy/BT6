### Title
Settled APR0 withdraw receipts bypass the `lossRecoveryPriceByEpoch` haircut and are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` applies `stopEpochWithDuration`-style realized losses to pending withdraw receipts by storing a per-epoch recovery ratio in `lossRecoveryPriceByEpoch`. The loss-adjusted claim path (`_claimLossAdjustedWithdrawRequest` → `_withdrawClaimAmountsForEpoch`) only recognizes an APR0 receipt while `apr0Users[user].principal != 0` and `principalEpoch == claimEpoch`. Once `_settleApr0` runs, it zeroes `principal`/`principalEpoch` and moves the amount to `settledPrincipal`, so the receipt's epoch linkage — the only pointer to its haircut — is dereferenced as null and the claim falls through to `_claimFundedWithdrawRequest`, which pays full principal plus settled interest at par.

### Finding Description
In `requestWithdraw`, APR0 requests (`unscaledApr == 0`) are tracked only via `apr0Users[user]` and `apr0TotalPrincipal`; `withdrawsRequestsByEpoch[user][epoch]` is never written for them (lines 285–294). `lastWithdrawRequest[user]` is still set to the request epoch (line 282).

When a loss-adjusted stop occurs, `collectWithdrawFunds` computes `pendingBasis = pendingWithdraws`, which *includes* APR0 principal (added at line 279), and stores `lossRecoveryPriceByEpoch[epochNumber] = fundedAmount / pendingBasis` (lines 411–421). The loss is therefore priced over a basis that assumes APR0 receipts will be haircut too.

At claim time, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest` (line 312), which reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` and finds the non-zero price. But `_withdrawClaimAmountsForEpoch` computes the APR0 component only when `principal != 0 && principalEpoch == claimEpoch` (lines 869–878). After `_settleApr0` (lines 545–565) has run — which happens automatically inside `_claimFundedWithdrawRequest` or on any subsequent `requestWithdraw` — `principal` and `principalEpoch` are zero, so `claimBasis` is 0 and the loss-adjusted path silently returns 0. Execution then reaches `_claimFundedWithdrawRequest`, which pays `settledPrincipal + settledInterest` in full via `_transferFundedClaim` (lines 339–349), with no reserve guard active in the non-default flow (`defaultRecoveryReserve == 0`, lines 897–906).

The same null-pointer-like gap exists in the re-request guard (lines 263–271): the check `apr0Users[user].principal != 0 && apr0Users[user].principalEpoch == lossEpoch` fails for a settled APR0 user and `withdrawsRequestsByEpoch` is empty for them, so the user can also open a new request, overwriting `lastWithdrawRequest` and permanently discarding the haircut reference for the old receipt.

### Impact Explanation
Direct theft/insolvency. The borrower only funds `pendingBasis * lossRecoveryPrice`, while settled-APR0 receipts are paid `principal + interest` at par. Each bypassing claim consumes underlyings that were accounted for as haircutted, so the shortfall — approximately `apr0Principal * (1 - lossRecoveryPrice)` plus full settled interest — is socialized onto other pending claimants, who are left permanently unable to withdraw the funded remainder. This breaks the loss-waterfall invariant that all pending receipts in the loss epoch share the haircut pro rata.

### Likelihood Explanation
Requires an APR0-mode vault (`unscaledApr == 0`), an epoch ending with `collectWithdrawFunds` funded below `pendingWithdraws` (a borrower shortfall / `stopEpochWithDuration` loss), and an APR0 requester whose receipt settles before claiming — a normal sequence triggered by the honest borrower/manager stop flow plus one ordinary claim by any unprivileged lender. No privileged misbehavior is needed.

### Recommendation
Preserve the epoch linkage for APR0 receipts after settlement — e.g., store `principalEpoch` alongside `settledPrincipal` (a `settledEpoch` field) — and make `_withdrawClaimAmountsForEpoch`, `_claimLossAdjustedWithdrawRequest`, and the re-request guard treat settled APR0 amounts of the loss epoch as haircuttable basis (`claimBasis` reduced by `lossRecoveryPrice`, while `burnAmount` still covers receipt principal). Alternatively, disallow settling APR0 receipts until the loss epoch's recovery claim is processed.

### Proof of Concept
Foundry fork outline:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
// Setup: fork chain with an APR0-mode IdleCDOEpochVariant + IdleCreditVault (unscaledApr == 0).

contract Apr0LossBypassPoC is Test {
    // cdo, strategy (IdleCreditVault), lenderA (apr0 requester), lenderB (normal requester)

    function test_apr0SettledReceiptSkipsHaircut() public {
        // 1. lenderA and lenderB deposit into AA tranche during buffer.
        // 2. Both call requestWithdraw in epoch N (unscaledApr == 0 so apr0Users is used).
        //    pendingWithdraws = A + B; lastWithdrawRequest = N for both.
        // 3. Honest manager stops epoch with a loss: borrower repays only
        //    pendingBasis * 0.8 -> collectWithdrawFunds stores
        //    lossRecoveryPriceByEpoch[N] = 0.8e18.
        // 4. Trigger settlement for lenderA: any call that runs _settleApr0
        //    (e.g., a claim attempt or a second requestWithdraw after epoch bump)
        //    moves principal -> settledPrincipal and zeroes principalEpoch.
        // 5. cdo.claimWithdrawRequest(lenderA):
        //    - _claimLossAdjustedWithdrawRequest sees lossRecoveryPriceByEpoch[N] != 0
        //      but _withdrawClaimAmountsForEpoch returns claimBasis == 0
        //      (principal == 0, withdrawsRequestsByEpoch[A][N] == 0) -> pays 0.
        //    - _claimFundedWithdrawRequest transfers settledPrincipal + settledInterest
        //      at 100% via _transferFundedClaim (no defaultRecoveryReserve guard).
        // 6. lenderB claims: receives only 0.8 * B, but vault balance is now
        //    underfunded by A * 0.2 (+ settledInterest) -> lenderB's transfer
        //    reverts on insufficient balance or drains funds owed to other claimants.
        assertEq(strategy.lossRecoveryPriceByEpoch(N), 0.8e18);
        assertApproxEqAbs(underlying.balanceOf(lenderA), apr0PrincipalA, 1); // paid at par
        // vault balance < remaining haircutted obligations => insolvency
    }
}
```

Uncertainty note: I could not read `IdleCDOEpochVariant.stopEpoch` to confirm the ordering of the `epochNumber` increment (in `deposit()`, line 610) relative to the `collectWithdrawFunds` call. If the increment happens before `collectWithdrawFunds`, `lossRecoveryPriceByEpoch` would be keyed one epoch later than `lastWithdrawRequest`, which would disable the haircut for *all* receipts rather than only settled APR0 ones — either way the loss-adjustment accounting is bypassed, but the exact mechanism should be confirmed on the fork.
