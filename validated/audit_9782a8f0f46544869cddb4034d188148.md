### Title
Unsanitized cache key reaches `AlternateFile` rename path via `cacheArchivePath`, enabling path traversal outside `CacheDir` - ([File: functions/concrete/run/stages/cache_archive.go])

### Summary
When `FF_HASH_CACHE_KEYS` is enabled, `builder.cacheKey` skips `cachekey.Sanitize` and returns `humanKey = rawKey` unsanitized. `builder.buildCacheArchive` sets `CacheArchive.AlternateKey = humanKey` (the unsanitized value) whenever the FF is on, and this flows unhashed into `cacheArchivePath`, producing a filesystem path that `filepath.Join`/`filepath.Rel` do not confine to `e.CacheDir`/`e.WorkingDir`. The helper's `cache-archiver --alternate-file <path>` then performs `os.Stat`/`os.Rename` on that attacker-influenced path.

### Finding Description
`b.cacheKey` computes `resolvedKey` (used as `CacheArchive.Key`) as a sha256 hash whenever `HashCacheKeys` is on [1](#0-0) , so the primary `Key` path is safe (hex digest, no traversal chars).

However, `buildCacheArchive` computes the **alternate** key differently:
```go
alternateResolved := humanKey
if !b.isFeatureFlagOn(featureflags.HashCacheKeys) {
    alternateResolved = fmt.Sprintf("%x", sha256.Sum256([]byte(humanKey)))
}
``` [2](#0-1) 

When `HashCacheKeys` is **on**, `alternateResolved` is left as `humanKey` — and `humanKey` itself was set to `rawKey` with `cachekey.Sanitize` skipped entirely:
```go
if b.isFeatureFlagOn(featureflags.HashCacheKeys) {
    humanKey = rawKey
} else {
    sanitized, err := cachekey.Sanitize(rawKey)
    ...
}
``` [3](#0-2) 

`rawKey` comes directly from `cache.Key` (job's `cache:key` in `.gitlab-ci.yml`) expanded through CI variables — fully attacker-controlled: `rawKey = b.variables.ExpandValue(name)` [4](#0-3) . A value such as `../../../../tmp/evil` passes through untouched as `humanKey`, then becomes `archive.AlternateKey` [5](#0-4) .

`CacheArchive.Run` passes this to the helper only if `AlternateKey != Key`:
```go
if s.AlternateKey != "" && s.AlternateKey != s.Key {
    args = append(args, "--alternate-file", s.alternateArchivePath(e))
}
``` [6](#0-5) 
Since `Key` is a sha256 hex digest and `AlternateKey` is the raw traversal string, they will always differ, so the check does not block the attack.

`alternateArchivePath` calls the shared, unguarded `cacheArchivePath`:
```go
func cacheArchivePath(e *env.Env, key string) string {
    absPath := filepath.Join(e.CacheDir, key, "cache.zip")
    rel, err := filepath.Rel(e.WorkingDir, absPath)
    ...
}
``` [7](#0-6) 
`filepath.Join` lexically cleans `..` segments without validating they stay under `e.CacheDir`; with enough `../` segments the resulting `absPath`/`rel` can point outside `CacheDir` and even outside `WorkingDir`.

That path is then handed to the `cache-archiver` helper as `--alternate-file`, which the helper uses in `tryRenameAlternateFile`:
```go
if _, err := os.Stat(c.AlternateFile); err != nil { ... }
...
if err := os.MkdirAll(filepath.Dir(c.File), 0o700); err != nil { ... }
if err := os.Rename(c.AlternateFile, c.File); err != nil { ... }
``` [8](#0-7) 
The rename source (`c.AlternateFile`) is fully attacker-influenced. If a file exists at the attacker-chosen path (reachable within the job container/executor filesystem) and the primary cache file does not yet exist, the helper renames (moves) that arbitrary file into the job's cache directory. `os.Stat`/`os.Rename` are also performed on the traversal path itself, meaning the helper touches paths outside the intended `CacheDir` scope.

Note: `cache_extract.go`'s `AlternateKey` is used only for `--alternate-url`/`--alternate-gocloud-url` (remote descriptors), never as a filesystem path [9](#0-8) , so the extract path is not affected by this issue — only the archive (upload) stage's alternate-file path is.

### Impact Explanation
An unprivileged pipeline author who sets `cache:key` (or `CACHE_FALLBACK_KEY`) to a traversal payload, combined with the runner having `FF_HASH_CACHE_KEYS=on`, can cause the `cache-archiver` helper subprocess to `os.Stat` and potentially `os.Rename` a file at a path outside the job's designated `CacheDir`/`WorkingDir` cache scope. This breaks the invariant that cache archive operations stay confined to `CacheDir`, potentially moving/renaming files elsewhere within the executor's filesystem that the job process can reach (e.g., other directories on a shared shell-executor host, or paths within a container mount). This is a path-confinement/logic bug, not a sandbox escape by itself, but it is a genuine violation of "file operations must stay within intended build/cache/artifact roots."

### Likelihood Explanation
Requires `FF_HASH_CACHE_KEYS=on` (a runner-level feature flag, not attacker controlled, but increasingly used since it's the migration-path flag for cache keys) and requires the attacker to control `cache:key`/`CACHE_FALLBACK_KEY`, which is standard `.gitlab-ci.yml` content fully controlled by any pipeline author. No special permissions beyond authoring a pipeline are needed. The exploit is deterministic and repeatable — it does not depend on races or admin misconfiguration beyond the FF being on.

### Recommendation
Apply `cachekey.Sanitize` (or an equivalent path-confinement check) to `humanKey`/`AlternateKey` regardless of the `HashCacheKeys` feature-flag state before it is used to construct any filesystem path (i.e., before assignment to `CacheArchive.AlternateKey`). Alternatively, harden `cacheArchivePath` itself to reject/clamp keys whose resulting path is not a lexical descendant of `e.CacheDir` (e.g., verify `strings.HasPrefix(filepath.Clean(absPath), filepath.Clean(e.CacheDir)+string(filepath.Separator))` and error out otherwise), so no caller-supplied key — hashed or not — can ever escape `CacheDir`.

### Proof of Concept
Go unit test in `functions/concrete/run/stages` (or a fuzz test) asserting confinement:
```go
func TestCacheArchivePath_StaysUnderCacheDir(t *testing.T) {
    e := &env.Env{CacheDir: "/builds/cache", WorkingDir: "/builds/proj"}
    payload := "../../../../tmp/evil"
    got := cacheArchivePath(e, payload)
    abs := filepath.Join(e.WorkingDir, got) // resolve rel result back to absolute
    cleanCache := filepath.Clean(e.CacheDir) + string(filepath.Separator)
    if !strings.HasPrefix(filepath.Clean(abs)+string(filepath.Separator), cleanCache) {
        t.Fatalf("cacheArchivePath escaped CacheDir: got %q", abs)
    }
}
```
Also add a builder-level test mirroring `functions/concrete/builder/builder_test.go`'s `FF_HASH_CACHE_KEYS` cases: set `cache.Key` to `"../../../../tmp/evil"`, enable `HashCacheKeys`, call `buildCacheArchive`, and assert `archive.AlternateKey` does not contain `..` segments (or that `cacheArchivePath(e, archive.AlternateKey)` remains under `CacheDir`). Expected current behavior: test fails, showing `AlternateKey` equals the raw traversal string and `cacheArchivePath` result escapes `CacheDir`.

```go
func (c *CacheArchiverCommand) tryRenameAlternateFile() {
	if c.AlternateFile == "" || c.AlternateFile == c.File {
		return
	}

	_, err := os.Stat(c.File)
	if err == nil {
		logrus.Debugln("Primary cache file already exists locally, skipping rename from alternate")
		return
	}
	if !errors.Is(err, fs.ErrNotExist) {
		logrus.WithError(err).Warningln("Failed to stat primary cache file")
		return
	}

	if _, err := os.Stat(c.AlternateFile); err != nil {
		logrus.Debugln("Alternate cache file not found locally, nothing to rename")
		return
	}

	if err := os.MkdirAll(filepath.Dir(c.File), 0o700); err != nil {
		logrus.WithError(err).Warningln("Failed to create directory for cache file rename")
		return
	}

	if err := os.Rename(c.AlternateFile, c.File); err != nil {
		logrus.WithError(err).Warningln("Failed to rename alternate cache file to primary")
		return
	}

	logrus.Infoln("Renamed alternate cache file to primary")
}
```
