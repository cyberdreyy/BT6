### Title
`CostTracker.allocated_accounts_data_size` only estimates growth from top-level System Program instructions, letting a CPI/`sol_realloc`-based program grow account data without being metered - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` (invoked from both `calculate_cost` and `calculate_cost_for_executed_transaction`) only inspects the transaction's top-level instructions and only assigns a non-zero size when the target program is the System Program (`CreateAccount`/`Allocate`/`AllocateWithSeed`/`CreateAccountWithSeed`/`CreateAccountAllowPrefund`). Any account-size growth performed by a custom program directly via the `sol_realloc`/`AccountInfo::realloc` syscall (with or without further CPI) is not System-Program traffic and is classified `SystemProgramAccountAllocation::None`, so it contributes `0` to `allocated_accounts_data_size` regardless of how much the account actually grew.

### Finding Description
`CostModel::calculate_transaction_cost` computes `allocated_accounts_data_size` via `calculate_allocated_accounts_data_size(instructions, feature_set)` [1](#0-0) , which is called from both the pre-execution estimate `calculate_cost` and the post-execution "actual" cost `calculate_cost_for_executed_transaction` [2](#0-1) . Note that `calculate_cost_for_executed_transaction`'s `actual_loaded_accounts_data_size_bytes` parameter is only used for the unrelated `loaded_accounts_data_size_cost` (a CU-cost metric for bytes *loaded*, not bytes *grown*) [3](#0-2) ; `allocated_accounts_data_size` itself is always recomputed statically from `transaction.program_instructions_iter()`, never from what actually happened during execution.

`calculate_account_data_size_on_instruction` explicitly gates on `program_id == &system_program::id()`; for any other top-level program it returns `SystemProgramAccountAllocation::None`, contributing zero [4](#0-3) . `calculate_allocated_accounts_data_size` sums only the `Some(..)` cases and clamps to `MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION` [5](#0-4) .

Meanwhile, the actual account-size delta produced during execution is tracked separately and correctly via `AccountsDeltas::accounts_resize_delta`/`get_uninitialized_accounts_size` in `TransactionAccountStateInfo` [6](#0-5) , and this delta is only fed into `Bank::update_accounts_data_size_delta_on_chain` (the global on-chain accounts-data-size accounting) [7](#0-6) , not into `CostTracker.allocated_accounts_data_size`. The `CostTracker` value that gates `would_fit`/`WouldExceedAccountDataBlockLimit` is populated purely from `tx_cost.allocated_accounts_data_size()`, i.e., the static System-Program-only estimate [8](#0-7) [9](#0-8) .

An unprivileged attacker can deploy their own SBPF program, allocate one or more owned accounts at a small initial size, and repeatedly invoke that program's instruction to call `sol_realloc`/`AccountInfo::realloc` directly (not via a System Program CPI) to grow the account close to the per-instruction cap. Because the top-level instruction targets the attacker's own program (not the System Program), `calculate_allocated_accounts_data_size` reports `0` for that instruction, so `CostTracker.allocated_accounts_data_size` is never incremented for this growth, even though the account's real, persisted data size increased. This diverges from `AccountsDeltas`/`get_uninitialized_accounts_size`, which do correctly reflect the real change (used only for the separate on-chain-total accounting, not for the per-block `CostTracker` limit).

### Impact Explanation
This is a metering/accounting bypass (VALUE_ACCOUNTING/METERING divergence) against the block-level `allocated_data_size` limit enforced by `CostTracker::would_fit`/`WouldExceedAccountDataBlockLimit`. That limit is intended to bound the total account-data growth admitted into a single block, protecting against state-growth-driven resource exhaustion (larger snapshots, more account-data I/O, more validator disk/memory pressure per slot). Because the CPI/`sol_realloc` growth path is invisible to the cost model, an attacker can pack many such transactions into a block while the tracked `allocated_accounts_data_size` stays at (or near) zero for those transactions, defeating the intended per-block ceiling on accounts-data growth. This maps to Solana's "compute/cost metering bypass" bounty category. The growth is still bounded by other, independent constraints (rent-exemption lamports the attacker must pay, per-instruction realloc size cap, and overall block CU budget), so it is not literally unbounded, but the specific `CostTracker` control this question asks about is bypassable as described.

### Likelihood Explanation
Fully reachable by an unprivileged actor: deploying an SBPF program and submitting ordinary transactions are both within the standard attacker capability set (no special config, no privileged role, no dependency bug). The only cost to the attacker is rent-exemption lamports for the larger accounts and normal transaction/compute fees — both of which an attacker willingly pays to achieve the effect. The bypass is deterministic and repeatable across every block since it stems from a structural property of `calculate_account_data_size_on_instruction` (top-level-instruction-only, System-Program-only check), not a timing or race condition.

### Recommendation
Base `allocated_accounts_data_size` (at least for the post-execution/"actual" cost path used by `check_block_cost_limits`) on the real `AccountsDeltas` growth (`accounts_resize_delta`/`get_uninitialized_accounts_size`) already computed in `TransactionExecutionDetails`, instead of re-deriving it from a static, System-Program-only scan of top-level instructions. If a purely static pre-execution estimate must be retained for scheduling/estimation, it should be treated as a lower bound and reconciled with the actual observed delta before feeding `CostTracker.allocated_accounts_data_size` in `get_transaction_costs`/`check_block_cost_limits`.

```rust
// cost-model/src/cost_model.rs (illustrative unit test)
// Demonstrates that a non-System-Program instruction that (conceptually) reallocs
// account data via a direct syscall is scored 0 by the cost model, regardless of size.
#[test]
fn test_custom_program_realloc_not_metered() {
    let (mint_keypair, start_hash) = test_setup();
    let custom_program_id = Pubkey::new_unique();
    let account_to_grow = Keypair::new();

    // Top-level instruction targets attacker's own program, not system_program::id().
    let ix = Instruction::new_with_bincode(
        custom_program_id,
        &(), // instruction data irrelevant to this program's own realloc logic
        vec![AccountMeta::new(account_to_grow.pubkey(), false)],
    );
    let message = Message::new(&[ix], Some(&mint_keypair.pubkey()));
    let tx = Transaction::new(&[&mint_keypair], message, start_hash);
    let sanitized = RuntimeTransaction::from_transaction_for_tests(tx);

    let cost = CostModel::calculate_cost(&sanitized, &FeatureSet::all_enabled());
    // Even though the program (at runtime, via sol_realloc/AccountInfo::realloc)
    // may grow `account_to_grow`'s data by up to MAX_PERMITTED_DATA_INCREASE bytes,
    // the cost model reports zero allocated data size for this instruction because
    // `program_id != system_program::id()`.
    assert_eq!(cost.allocated_accounts_data_size(), 0);
}
```
Expected assertion: `allocated_accounts_data_size() == 0` for the custom-program instruction, while the account's real on-disk size after execution (verifiable via `AccountsDeltas`/`get_uninitialized_accounts_size` or by re-reading the account post-transaction) increases by the realloc amount — demonstrating the divergence between what `CostTracker.allocated_accounts_data_size` tracks and the account's actual data-size delta.

```rust
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }
```

```rust
    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
        }

        // check each account against account_cost_limit,
        for account_key in tx_cost.writable_accounts() {
            match self.cost_by_writable_accounts.get(account_key) {
                Some(chained_cost) => {
                    if chained_cost.saturating_add(cost) > self.limits.account_cost {
                        return Err(CostTrackerError::WouldExceedAccountMaxLimit);
                    } else {
                        continue;
                    }
                }
                None => continue,
            }
        }

        Ok(())
    }
```
