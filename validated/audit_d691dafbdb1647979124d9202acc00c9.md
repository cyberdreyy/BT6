### Title
Stale confirmations from removed multisig members/keys still count toward the confirmation threshold, allowing execution below live-signer quorum - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The multisig contracts (`multisig` and `multisig2`) let any current member co-sign a pending request via `confirm()`. When a member/key is later removed through the `DeleteKey`/`DeleteMember` action, the removal logic (`execute_request`'s `DeleteKey` branch in `multisig/src/lib.rs:198-216`, and `delete_member` in `multisig2/src/lib.rs:356-379`) only deletes requests that the removed member *authored*; it never strips that member's confirmation out of the `confirmations` set of other still-pending requests they had merely co-signed. `confirm()` (`multisig/src/lib.rs:246-266`, `multisig2/src/lib.rs:292-315`) counts `confirmations.len()` against `num_confirmations` without ever validating that each recorded confirmer is still a live member/key. As a result, a request can reach and cross the confirmation threshold and execute even though one or more of its "confirmations" belong to a party that has since been removed from the multisig.

### Finding Description
The intended custody binding is: **confirmations counted == confirmations from currently live members**. The confirmation set for a request is a `HashSet<PublicKey>` (or `HashSet<String>` for members in `multisig2`) that is populated purely by public-key/member identity at the time of `confirm()`, with no re-validation at execution time (`multisig/src/lib.rs:246-266`; `multisig2/src/lib.rs:292-315`).

The `DeleteKey`/`DeleteMember` cleanup path was written assuming a removed signer's influence is only relevant for requests *they created* (filtered by `r.signer_pk == pk` / `r.member == member`), so it deletes requests keyed to that assumption and clears the corresponding `confirmations` entry outright. It does not iterate over all outstanding requests' `confirmations` sets to remove the departing signer's vote from requests authored by someone else. Consequently, once a key/member is removed, any request that they had previously confirmed as co-signer retains that stale vote permanently in state.

This is structurally the same class of bug as the reported `executeTransactionFromOutside` nonce issue: a state-changing action (removal of a signer) fails to update all of the bookkeeping (`confirmations`) that another code path (`confirm`/threshold check) relies on for its authorization decision, letting a future call succeed on data that no longer reflects reality.

### Impact Explanation
If `num_confirmations` requires, say, 3-of-5 signers, and a request already has 2 confirmations (from Member A and Member B) when Member B is removed from the multisig (e.g., because a key was compromised or a member departed), the request still shows 2 confirmations. A single additional confirmation from any remaining live member now crosses the 3-confirmation threshold and executes the request — even though only 2 of the votes (the new confirmer and Member A) are current members, i.e., quorum is met without genuine live-member agreement. This lets a request be executed below the intended live-signer threshold, matching the "multisig request executed below threshold" Critical impact category, since the removed member's stale vote is effectively being spent by an account no longer entitled to any say over the multisig's funds/actions.

### Likelihood Explanation
This requires no special privilege beyond being (or having been) a normal multisig member — a routine, expected operational event (member offboarding, key rotation) combined with an already-partially-confirmed request. No attacker needs foundation/owner rights beyond what any co-signer already holds, and the sequence (confirm → later remove that signer → get one more live confirmation) is a natural admin workflow, making this a realistic occurrence rather than a purely theoretical one.

### Recommendation
When removing a key/member via `DeleteKey`/`DeleteMember`, iterate over all pending requests' `confirmations` sets and remove the departing signer's entry wherever present (not just requests they authored), or alternatively re-validate at `confirm()`/execution time that every public key/member in the stored `confirmations` set is still present in the current member/key set before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy a multisig with `num_confirmations = 3` and members {A, B, C, D, E}.
2. A calls `add_request` to create Request X.
3. B calls `confirm(X)` → `confirmations = {A, B}` (2/3).
4. The multisig later executes a separate, fully-confirmed request containing `MultiSigRequestAction::DeleteMember { member: B }` (or `DeleteKey` for the v1 contract) to remove B — a normal admin action, not requiring any special attacker privilege beyond being a member proposing/confirming that removal.
5. `delete_member`/`DeleteKey` branch only removes requests where `r.member == B` / `r.signer_pk == B`'s key; Request X, authored by A, is untouched, and its `confirmations` set still contains B.
6. C (a live member) calls `confirm(X)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)`, so Request X executes, even though B — one of the three "confirming" identities — is no longer a member of the multisig.
