## Analog Found

### Title
Flat per-signature base fee does not scale with the differentiated real verification cost of secp256k1/ed25519/secp256r1 precompiles, causing systemic underpayment for leader compute work - (File: `cost-model/src/block_cost_limits.rs`, `fee/src/lib.rs`)

### Summary
The Perennial bug root cause is that keeper compensation is calculated from one resource dimension (L2 execution gas) while the real cost incurred (L1 rollup fee) is a separate, differently-weighted dimension that isn't reflected in the compensation formula. The nearest reachable analog in Agave is the mismatch between the block **cost model**, which correctly assigns differentiated, heavily-weighted CU costs to precompile signature verification, and the **fee model**, which charges every "signature" (regular tx signature, ed25519, secp256k1, secp256r1 precompile signature) at the identical flat `lamports_per_signature` rate regardless of its true computational cost.

### Finding Description
The cost model assigns very different per-signature CU weights depending on signature type: [1](#0-0) 

These weights are consumed when computing a transaction's `signature_cost` for block-inclusion/leader-side accounting purposes: [2](#0-1) 

However, the fee actually charged to (and, by extension, the compensation basis derived from) the transaction sender treats every signature — whether it's a cheap standard Ed25519 transaction signature or an expensive secp256k1/secp256r1/ed25519 precompile verification — identically, at the flat `lamports_per_signature` rate: [3](#0-2) 

This is the fee function actually invoked on the bank's execution/commit path: [4](#0-3) 

The number of "signatures" counted for both the fee and the cost model comes from the same single declared byte in the precompile instruction data (`data[0]`), which an unprivileged transaction sender fully controls when constructing the instruction: [5](#0-4) [6](#0-5) 

Because `SECP256K1_VERIFY_COST` (6,690 CU) is ~9.3x `SIGNATURE_COST` (720 CU), and `SECP256R1_VERIFY_COST` (4,800 CU) is ~6.7x, a sender can construct a transaction dominated by secp256k1/secp256r1 precompile signature checks and pay the exact same `lamports_per_signature` per verification as an ordinary, cheap transaction signature — despite consuming several times more leader compute per lamport paid. This is structurally identical to the Perennial issue: compensation (fee) is derived from one flat unit price while the true resource cost varies by type/dimension and is not reflected back into the price paid.

### Impact Explanation
This does not directly drain protocol funds the way the Perennial keeper-drain scenario does, but it produces the same underlying economic failure mode: the party doing the real work (the leader/validator executing precompile verification) is not compensated proportionally to the true cost of the work it performs, while the party paying (the transaction sender) gets several times more expensive cryptographic verification "for free" relative to the base price. This falls into the "free execution" / "leader-side cost limits" categories explicitly in scope: a sender can cheaply force disproportionate CPU-bound verification work onto leaders without paying a fee that reflects it, which is an available lever for cheap, fee-underpriced congestion of block execution against `secp256k1_program`/`secp256r1_program` verification specifically.

### Likelihood Explanation
This is trivially reachable by any unprivileged transaction sender: constructing a transaction with multiple secp256k1/secp256r1 precompile instructions (each with a declared signature count up to 255) requires no special privilege, no CPI escalation, and no cluster-state assumptions — it only requires normal instruction construction, which is always available in the current fee-calculation design (`fee/src/lib.rs::calculate_signature_fee`).

### Recommendation
Weight the base signature fee by precompile signature type (or otherwise fold the cost-model's differentiated `SIGNATURE_COST`/`SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST` weights into `calculate_signature_fee`), so that the price paid by the sender scales with the real verification cost incurred by the leader, analogous to how the Perennial fix required folding L1 rollup cost into the keeper compensation formula.

### Proof of Concept
1. Construct a transaction whose instructions consist mostly of `secp256k1_program`/`secp256r1_program` precompile instructions, each declaring the maximum practical signature count in `data[0]` (bounded only by transaction size limits).
2. Compare: `fee = num_signatures * lamports_per_signature` (per `fee/src/lib.rs::calculate_signature_fee`) versus the CU cost actually billed against block/account cost limits: `signature_cost = num_secp256k1_instruction_signatures * SECP256K1_VERIFY_COST` (per `cost-model/src/cost_model.rs::get_signature_cost`, weights from `cost-model/src/block_cost_limits.rs`).
3. Observe the ~9.3x (secp256k1) / ~6.7x (secp256r1) / ~3.3x (ed25519) gap between CU cost incurred by the leader and the flat per-signature lamport fee charged, versus an equivalent-fee transaction using only ordinary transaction signatures.

/// Calculate fees from signatures.
pub fn calculate_signature_fee(
    SignatureCounts {
        num_transaction_signatures,
        num_ed25519_signatures,
        num_secp256k1_signatures,
        num_secp256r1_signatures,
    }: SignatureCounts,
    lamports_per_signature: u64,
) -> u64 {
    let signature_count = num_transaction_signatures
        .saturating_add(num_ed25519_signatures)
        .saturating_add(num_secp256k1_signatures)
        .saturating_add(num_secp256r1_signatures);
    signature_count.saturating_mul(lamports_per_signature)
}
