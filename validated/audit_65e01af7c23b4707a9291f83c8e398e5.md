### Title
Shared, unpartitioned `sortition_state` cache lets a stale/overlapping-cycle signer instance invalidate the active signer's view of the current miner - ([File: stacks-signer/src/runloop.rs])

### Summary
The runloop holds a single, process-wide `Option<SortitionsView>` cache (`RunLoop::sortition_state`) that is passed by mutable reference to **every** `ConfiguredSigner` in `stacks_signers` on each pass, regardless of which reward cycle that signer instance belongs to. This is the same "cache keyed by the wrong identity" pattern as the reported `clientCache` bug: instead of partitioning the cached view by the signer instance/reward-cycle context that produced it, one shared object is mutated by whichever `ConfiguredSigner` runs first and then blindly consumed by the others.

### Finding Description
`RunLoop` keeps at most two `ConfiguredSigner` instances simultaneously — one for the current reward cycle and one for the next, during the prepare-phase overlap window: [1](#0-0) 

Both are driven from a single shared `sortition_state` in the main loop: [2](#0-1) 

Inside `process_event`, `capitulate_viewpoint` is invoked **unconditionally** for every configured signer — even one whose `reward_cycle` has not started yet (the check that gates further processing for a not-yet-active cycle happens *after* this call): [3](#0-2) 

`capitulate_viewpoint` mutates the shared `sortition_state` based on that particular signer's own `local_state_machine`, marking `cur_sortition.miner_status` as `InvalidatedBeforeFirstBlock` if that signer's view of `current_miner_pkh` mismatches the cached sortition's miner: [4](#0-3) 

Because each `ConfiguredSigner`'s `local_state_machine` is created independently (fresh, via `Signer::new` in `refresh_signer_config`), the not-yet-active next-cycle signer's view of "current miner" can lag or diverge from the active current-cycle signer's converged view during the overlap window. When it does, its call to `capitulate_viewpoint` will overwrite the *shared* `sortition_state.cur_sortition.miner_status`, poisoning the exact object the active current-cycle signer relies on in `check_block_against_local_state` / `SortitionsView::check_proposal` to decide whether to sign the legitimate current miner's blocks: [5](#0-4) [6](#0-5) 

This is structurally identical to the reported bug class: a cache (`sortition_state`) that should be scoped per-context (per signer instance / reward cycle) is instead a single shared slot, so state derived under one context (the idle/next-cycle "wallet") contaminates consumption under a different context (the active/current-cycle "wallet").

### Impact Explanation
The mutation is monotonic toward `InvalidatedBeforeFirstBlock` (I found no code path that resets it back to `Valid` from this call), so the concrete consequence is that the currently active reward-cycle's signer can be made to treat the legitimate, canonical current miner as invalid and reject that miner's valid block proposals purely because of a transient inconsistency in an *unrelated*, not-yet-active signer instance's local state machine. This matches the High-severity class in scope: "a signer wedged into never signing valid blocks" for the remainder of that sortition, degrading liveness for that node without requiring any majority collusion or key compromise — a single miner/gossip-driven timing condition during the reward-cycle overlap window is sufficient to trigger it locally.

### Likelihood Explanation
The overlap window (both current- and next-cycle `ConfiguredSigner`s live at once) occurs on every reward cycle boundary by design (`is_in_next_prepare_phase`), so the precondition for two signer instances sharing `sortition_state` is routine, not exceptional. Whether the next-cycle signer's freshly-initialized state machine actually diverges from the converged current-cycle view during that window depends on timing/ordering of burn-block and miner-message processing, which I was not able to fully trace to a guaranteed deterministic trigger within the remaining investigation budget — this reduces confidence from "certain" to "plausible, timing-dependent."

### Recommendation
Scope `sortition_state` per `ConfiguredSigner` (i.e., store it inside each signer instance rather than as a single field on `RunLoop`), or key it explicitly by `reward_cycle` (e.g., `HashMap<u64, SortitionsView>`), mirroring the report's suggested fix of keying `clientCache` by both chain id and address. Additionally, `capitulate_viewpoint` should not be invoked for a `ConfiguredSigner` whose `reward_cycle` has not yet started (move the `self.reward_cycle > current_reward_cycle` gate before the capitulation call), so an idle/future signer instance can never mutate the active signer's sortition view.

### Proof of Concept
I could not construct a fully deterministic, minimal-step PoC within the remaining time/tooling; the exploitability hinges on precise timing of when the next-cycle signer's `local_state_machine` diverges from the active signer's converged view during the prepare-phase overlap, which would require tracing `handle_pending_update`/`update_and_return_state` and the message ordering across `stacks-node` gossip more deeply than I was able to verify here. I flag this explicitly as unverified: the code path sharing `sortition_state` across signer instances (as cited above) is confirmed, but a concrete triggering sequence (specific miner/gossip messages and timing) was not fully worked out.

    fn check_block_against_local_state(

        stacks_client: &StacksClient,
        sortition_state: &mut Option<SortitionsView>,
        block: &NakamotoBlock,
    ) -> Option<BlockRejection> {
        let signer_signature_hash = block.header.signer_signature_hash();
        let block_id = block.block_id();
        // Get sortition view if we don't have it
        if sortition_state.is_none() {
            *sortition_state =
                SortitionsView::fetch_view(self.proposal_config.clone(), stacks_client)

                        warn!(

                            "signer_signature_hash" => %signer_signature_hash,
                            "block_id" => %block_id,
                        )
                    })
                    .ok();
        }

        // Check if proposal can be rejected now if not valid against sortition view
        if let Some(sortition_state) = sortition_state {
            match sortition_state.check_proposal(
                stacks_client,
                &mut self.signer_db,
                block,
                true,
                self.global_state_evaluator
                    .get_global_tx_replay_set()
                    .unwrap_or_default(),
            ) {
                // Error validating block
                Err(RejectReason::ConnectivityIssues(e)) => {

                        "reject_code" => ?reject_code,

                }
