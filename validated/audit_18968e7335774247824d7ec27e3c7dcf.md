### Title
Loss-adjusted withdraw receipts can evade their haircut by re-requesting in a later epoch, paying the receipt at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The openjpeg CVE is an infinite loop in a conversion routine (`convert_32s_C1P1`) that writes past the end of a buffer — i.e., a per-element conversion keyed by the wrong bound corrupts adjacent state. The credit-vault analog is the epoch-keyed conversion of withdraw receipts into payouts: `lossRecoveryPriceByEpoch` haircuts are applied per *request epoch*, but the claim path derives the epoch to haircut from a single mutable pointer, `lastWithdrawRequest[_user]`. By issuing a second withdraw request in a later epoch, a lender moves that pointer forward so their earlier loss-adjusted receipt is never haircut and is instead paid at par through the funded-claim path — the payout "overflows" the funded reserve into value belonging to other claimants.

### Finding Description
`stopEpochWithDuration` / `_beforeStopEpoch` record a haircut for unfunded receipts in `lossRecoveryPriceByEpoch[requestEpoch]`, and the borrower only funds the reduced amount (`pendingWithdraws` is cleared against the haircutted sum). Claims are then supposed to go through `_claimLossAdjustedWithdrawRequest`, which pays `claimBasis * lossRecoveryPrice`.

The flaw: `_claimLossAdjustedWithdrawRequest` looks up the loss epoch exclusively via `lastWithdrawRequest[_user]` (contracts/strategies/idle/IdleCreditVault.sol:790-791). When a user calls `requestWithdraw` again in a later epoch, `lastWithdrawRequest[_user]` is overwritten with the new `currentEpoch` (line 282), while the old receipt remains in `withdrawsRequestsByEpoch[_user][oldEpoch]` and in the aggregate `withdrawsRequests[_user]`.

The guard intended to prevent exactly this (lines 263-271) only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the *latest* epoch. It never iterates `withdrawsRequestsByEpoch` over older epochs. So:

- If the loss epoch is `E1` but the user's `lastWithdrawRequest` is `E2`, the guard sees `lossRecoveryPriceByEpoch[E2] == 0` and lets the new request in.
- On claim, `_claimLossAdjustedWithdrawRequest` computes `lossEpoch = lastWithdrawRequest[_user] = E2`, finds `lossRecoveryPriceByEpoch[E2] == 0`, and returns 0 — the haircutted `E1` receipt is never settled through the loss path.
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still aggregates the `E1` basis — **at par**, burning the receipt tokens and calling `_transferFundedClaim`.

### Impact Explanation
The borrower (or prefunded reserve) only transferred `claimBasis * lossRecoveryPrice` for `E1` receipts. Paying that receipt at par (`claimBasis`) over-draws the strategy's funded balance by `claimBasis * (1 - lossRecoveryPrice)`. That excess comes directly out of underlying tokens backing other users' funded claims and post-default recovery reserves — a direct theft / insolvency of honest claimants proportional to the haircut size (e.g., a 50% loss epoch lets the attacker double their recovery). One-receipt-one-payout and the loss waterfall invariant are both broken.

### Likelihood Explanation
Only an unprivileged KYC'd lender is needed. Requirements: (1) the user has an open withdraw receipt in an epoch that later takes a `stopEpochWithDuration` loss; (2) the pool keeps operating; (3) the user submits a second `requestWithdraw` in a subsequent epoch (explicitly supported — the comment at line 323-324 notes stacking requests just delays claiming). `requestWithdraw` is reachable in buffer phase, the guard only inspects the newest epoch, and no other check (skim, flags, epoch gating) blocks the sequence. The par payout then lands in `_claimFundedWithdrawRequest`, which does not consult `lossRecoveryPriceByEpoch` for the older epoch.

### Recommendation
Track the loss epoch per receipt instead of relying on the single `lastWithdrawRequest` pointer:

- In `requestWithdraw`, revert if the user has *any* `withdrawsRequestsByEpoch`/`apr0Users.principal` entry in an epoch with a nonzero `lossRecoveryPriceByEpoch` (or store the earliest unsettled request epoch per user).
- In `claimWithdrawRequest`, resolve the haircut per stored epoch: iterate/settle `withdrawsRequestsByEpoch[_user][e]` against `lossRecoveryPriceByEpoch[e]` before paying the funded remainder at par, rather than keying the loss claim off `lastWithdrawRequest`.
- Alternatively, persist a per-user `pendingLossEpoch` that is only cleared by `_claimLossAdjustedWithdrawRequest`, so later requests cannot mask it.

// SPDX-License-Identifier: MIT
// Foundry fork test, pool in epoch mode (IdleCDOEpochVariant + IdleCreditVault)
function testLossReceiptEvadesHaircut() public {
    // 1. Alice (KYC'd lender) deposits AA and requests withdraw in epoch E1 buffer
    idleCDO.depositAA(100_000e6);
    vm.prank(alice);
    cdoEpoch.requestWithdraw(aliceTrancheBal / 2, address(AAtranche)); // receipt R1, epoch E1

    // 2. Epoch E1 runs; at stopEpoch the manager applies a loss via stopEpochWithDuration
    //    -> lossRecoveryPriceByEpoch[E1] = e.g. 5e17 (50%), borrower funds only 50% of R1
    _startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(_lossAmount); // sets lossRecoveryPriceByEpoch[E1]

    // 3. In the next buffer, Alice files a second request -> lastWithdrawRequest[alice] = E2
    vm.prank(alice);
    cdoEpoch.requestWithdraw(remainingBal, address(AAtranche)); // receipt R2, epoch E2
    // guard at L263 only checks lossRecoveryPriceByEpoch[E2] == 0 -> passes

    // 4. E2 ends normally and funds pendingWithdraws
    _startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, pendingWithdraws + interest);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr, interest);

    // 5. Alice claims once: loss-claim path sees E2 (price 0, returns 0),
    //    funded path pays R1 + R2 fully at par.
    uint256 pre = underlying.balanceOf(alice);
    vm.prank(alice);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(alice) - pre;

    // R1 was funded at only 50%, yet paid 100%:
    assertEq(paid, R1_basis + R2_basis);            // haircut evaded
    // vault underlying is now short R1_basis * 50% vs. remaining funded claims
}
