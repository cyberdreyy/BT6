### Title
EI credentials satisfy `isUser` check via shared `SessionUserKey`, allowing External-Initiator holders to reach the int-ID `RunJobV2` path meant for real users - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates the numeric-job-ID run path with `_, isUser := auth.GetAuthenticatedUser(c)`, with a comment stating "only users are allowed to run jobs using int IDs - EIs not allowed." However, `AuthenticateExternalInitiator` also calls `c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})`, so `GetAuthenticatedUser` returns `(user, true)` identically for genuine session/token users and for External-Initiator (EI) credential holders. The `isUser` check therefore fails to distinguish EI callers from real users, contradicting the code's own stated intent.

### Finding Description
`GetAuthenticatedUser` simply reads whatever was stored under `SessionUserKey`: [1](#0-0) 

Three authentication methods populate that key:
- `AuthenticateBySession` sets it to the real, DB-backed user. [2](#0-1) 
- `AuthenticateByToken` sets it to the real, DB-backed user. [3](#0-2) 
- `AuthenticateExternalInitiator` sets it to a synthetic `&clsessions.User{Role: clsessions.UserRoleRun}` after validating only the EI's access key/secret against `bridges.ExternalInitiator` — it does **not** carry any binding back to a specific job/webhook UUID. [4](#0-3) 

`PipelineRunsController.Create` uses this ambiguous signal as its authorization gate for the numeric-job-ID branch: [5](#0-4) 

Because `isUser` is `true` for EI-authenticated requests exactly as it is for session/token users, an attacker holding only EI access-key/secret credentials can hit the `strconv.ParseInt` branch and call `prc.App.RunJobV2(ctx, jobID, nil)` with an arbitrary `jobID`, with no check that the job is the EI's associated webhook job. `RunJobV2` itself performs no EI-to-job binding check either — it just does `app.jobORM.FindJob(ctx, jobID)` and executes the pipeline for whatever job that ID resolves to: [6](#0-5) 

This confirms REQUEST_BINDING is bypassed: the EI's authorization is scoped only to "is this a valid EI credential," not "is this EI allowed to run job X."

However, `RunJobV2` is explicitly gated to non-production builds: [7](#0-6) 
The comment "Only used for local testing, not supported by the UI" and the `build.IsProd()` early return mean that on secure/production Chainlink node builds, this code path always returns an error before any job execution occurs, regardless of which caller reached it. I was unable to fully confirm from the available index the exact router wiring (i.e., which gin route group in `core/web/router.go` chains `AuthenticateExternalInitiator` together with `AuthenticateBySession`/`AuthenticateByToken` onto the `POST /v2/jobs/:ID/runs` route that maps to `Create`); the `GET` routes for `PipelineRunsController` shown in the router are session/token-only, and the POST registration was not located in the excerpts retrieved. This is a genuine gap in verification — a Devin session with full repo/build access would be needed to confirm the exact route-to-middleware mapping and the default value of `build.IsProd()` in release builds.

### Impact Explanation
The logical flaw is real: the `isUser` check in `Create` cannot actually distinguish EI credential holders from genuine dashboard/API users, defeating its own stated purpose ("EIs not allowed"). If reachable in a build where `build.IsProd()` is false (e.g., non-release/dev/test builds, or any build path that doesn't set the prod flag), an EI credential holder could trigger execution of arbitrary jobs by numeric ID with attacker-supplied `nil` metadata — this is an authorization/role-boundary bypass (EI acting with more privilege than an EI should have), matching a "role bypass / unauthorized job execution" impact class. On correctly built production nodes, the `build.IsProd()` guard in `RunJobV2` neutralizes the practical impact, since manual job runs are unconditionally rejected before any pipeline execution.

### Likelihood Explanation
Precondition: attacker must possess valid EI access-key/secret for the target node (a low-privilege credential class, consistent with the "unprivileged attacker" scope: EI credential holder). No user session, API token, or elevated role is required. The exploitability is fully gated by whether the target binary was built with `build.IsProd()` returning `false` — in official production release builds this branch is dead, sharply reducing real-world likelihood. I could not verify from the indexed files whether all officially distributed binaries set this flag, or whether some deployment paths (custom builds, LOOP plugins, etc.) leave it unset.

### Recommendation
Fix the check to only recognize genuine session/token users, not EI-derived synthetic users — e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` and rejecting if present, or by not reusing `SessionUserKey` for EI authentication (introduce a distinct marker/type so `GetAuthenticatedUser` cannot be satisfied by EI credentials). This restores the intended invariant stated in the code comment independent of the `build.IsProd()` gate in `RunJobV2`, which should not be relied upon as the sole enforcement point.

### Proof of Concept
Table-driven handler test in `core/web/pipeline_runs_controller_test.go` style:
1. Set up a gin router with `Authenticate(authr, AuthenticateBySession, AuthenticateByToken, AuthenticateExternalInitiator)` in front of `PipelineRunsController.Create`, using a stub `Authenticator` that returns a valid EI for a known access key/secret and a valid user for session/token.
2. Case A: authenticate via `AuthenticateBySession`/`AuthenticateByToken` with a real user, POST `/v2/jobs/<intID>/runs` → assert `isUser` true and `RunJobV2` invoked (existing behavior, expected).
3. Case B: authenticate via `AuthenticateExternalInitiator` headers only (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret`), POST `/v2/jobs/<intID>/runs` for a job the EI is *not* associated with → assert that today `auth.GetAuthenticatedUser(c)` returns `isUser == true` and `App.RunJobV2` is invoked (mock `Application.RunJobV2` and assert `.Called`), demonstrating the bypass; the desired/fixed behavior is `isUser == false` and a `422 bad job ID` response.
4. Add regression assertion: `auth.GetAuthenticatedExternalInitiator(c)` returns `ok == true` simultaneously with `isUser == true` in the current code, proving the two signals are conflated.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)

	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
