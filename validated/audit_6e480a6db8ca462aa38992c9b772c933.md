### Title
Pending APR0 withdraw request permanently bricks `stopEpoch` when APR becomes non-zero - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.prepareStopEpochWithApr0` unconditionally reverts with `NotAllowed` whenever `unscaledApr != 0` while `apr0TotalPrincipal != 0`. Any unprivileged tranche holder can open a dust APR0 withdraw request during an APR=0 epoch; afterwards, once the manager (honestly) sets a non-zero APR for the next epoch, every subsequent `stopEpoch` call reverts, permanently freezing the entire pool.

### Finding Description
`requestWithdraw` routes requests to the APR0 bucket whenever `unscaledApr == 0` and the pool isn't closed, incrementing the global `apr0TotalPrincipal` (contracts/strategies/idle/IdleCreditVault.sol:285-286, 567-577). On `stopEpoch`, `IdleCDOEpochVariant` calls `prepareStopEpochWithApr0`, which early-returns only when `_principal == 0` and otherwise reverts if `unscaledApr != 0` (IdleCreditVault.sol:499-508):

```solidity
uint256 _principal = apr0TotalPrincipal;
if (_principal == 0) { return (...); }
if (unscaledApr != 0) { revert NotAllowed(); }
```

`apr0TotalPrincipal` is only ever cleared at the end of this same function (line 540) — i.e., it can only be zeroed by a successful `stopEpoch` executed while `unscaledApr == 0`. Per-user settlement (`_settleApr0`, lines 545-565) clears `apr0Users[user].principal` but never decrements `apr0TotalPrincipal`, and it only settles once `epochNumber > principalEpoch`, which itself requires a successful `stopEpoch`. There is no escape path: no user or privileged call can reduce `apr0TotalPrincipal` outside of `prepareStopEpochWithApr0`.

Attack sequence:
1. Epoch is running with `unscaledApr == 0` (APR0 mode). Attacker, an ordinary tranche holder, calls `cdoEpoch.requestWithdraw(1 wei, tranche)` → `_requestWithdrawApr0` sets `apr0TotalPrincipal = 1`.
2. Epoch ends; manager sets a non-zero APR for the next epoch (`setApr`/`setAprsWithBuffer` — a normal honest operation).
3. Manager calls `stopEpoch` → `prepareStopEpochWithApr0` reverts `NotAllowed` because `apr0TotalPrincipal != 0` and `unscaledApr != 0`.
4. `stopEpoch` can never succeed again: setting APR back to 0 would allow the stop, but that is only a workaround — if the vault is intended to run at a non-zero APR, the epoch is permanently stuck; and even setting APR to 0 still requires the borrower to repay `pendingWithdraws` which includes the attacker's now-unpriceable bucket.

### Impact Explanation
Permanent freezing of all funds in the credit vault. `stopEpoch` is the only path that increments `epochNumber`, funds pending withdraw receipts (`collectWithdrawFunds`), and unlocks claims (`claimWithdrawRequest` requires `epochNumber > lastWithdrawRequest`). With `stopEpoch` bricked, no lender can ever withdraw: active deposits, pending withdraw receipts, and strategy-held underlying are all frozen. Cost to the attacker is 1 wei of withdraw request plus gas. Loss magnitude: the entire pool TVL.

### Likelihood Explanation
Low attacker cost (one `requestWithdraw` transaction during any APR0 epoch) and requires no privileged collusion — it only depends on the manager later setting a non-zero APR, which is the normal way the vault exits APR0 mode. The main uncertainty is deployment-dependent: it only applies to pools that operate in APR0 mode at some point and later return to a positive APR. If a pool is permanently APR0 or never APR0, the bug is unreachable. I did not fully verify whether `IdleCDOEpochVariant.stopEpoch` wraps the `prepareStopEpochWithApr0` call in a try/catch (which would neutralize the revert); the match count in that file suggests it is called directly, but this should be confirmed during PoC development — the Foundry PoC will demonstrate it either way.

### Recommendation
Decouple the APR0 guard from a hard revert. Options:
- Instead of reverting when `unscaledApr != 0` with pending APR0 principal, settle the APR0 bucket at zero interest (skip the pro-rata split and just clear `apr0TotalPrincipal`), letting `stopEpoch` proceed.
- Alternatively, block `setApr`/`setAprs` from raising `unscaledApr` above 0 while `apr0TotalPrincipal != 0`, shifting the revert to the APR-setting call so the freeze can never be armed — though this lets an attacker repeatedly veto APR increases with dust requests, so the first option (forgive APR0 interest on transition) is safer.
- Additionally, decrement `apr0TotalPrincipal` inside `_settleApr0`/claim paths so outstanding buckets aren't sticky.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style, mainnet fork
function testPocApr0StopEpochDos() external {
    // Pool configured with unscaledApr == 0 (APR0 mode).
    // 1. Honest LPs deposit.
    idleCDO.depositAA(10000e6);
    idleCDO.depositBB(10000e6);

    // 2. Start APR0 epoch.
    _startEpochAndCheckPrices(0);

    // 3. Attacker (any tranche holder) opens a dust withdraw request.
    address attacker = makeAddr('attacker');
    uint256 t = _depositWithUser(attacker, 10e6);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche)); // apr0TotalPrincipal = 1

    // 4. Manager honestly moves the vault to a non-zero APR for next epoch.
    vm.prank(manager);
    strategy.setAprs(initialProvidedApr, scaledApr); // unscaledApr != 0

    // 5. Borrower repays; manager tries to stop the epoch -> always reverts.
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.prank(borrower);
    underlying.transfer(address(strategy), _expectedFundsEndEpoch());
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // 6. No path clears apr0TotalPrincipal: claims can't settle because
    //    epochNumber never advances; stopEpoch is bricked -> all funds frozen.
    vm.prank(attacker);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();
}
```
