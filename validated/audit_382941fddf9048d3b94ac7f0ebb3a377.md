### Title
Unbounded per-sender rate-limiter map growth enables gateway-triggered memory exhaustion DoS - (File: `core/capabilities/webapi/trigger/trigger.go`)

### Summary
The `triggerConnectorHandler.processTrigger` function calls `trigger.rateLimiter.Allow(body.Sender)` for every incoming gateway trigger message, where `body.Sender` is an attacker-controlled string taken directly from the untrusted message body [1](#0-0) . The underlying `RateLimiter.Allow` implementation lazily inserts a new `*rate.Limiter` into a `perSender` map keyed by that same attacker-controlled sender string, and there is no mechanism anywhere in the type to evict, expire, or bound the size of this map [2](#0-1) .

### Finding Description
This mirrors the VTVL `vestingRecipients` bug class: a storage structure (here, an in-memory `map[string]*rate.Limiter`) grows monotonically with each new unique key supplied by an unprivileged/untrusted actor, and the codebase provides no "withdraw"-style disposal path to remove stale entries.

`NewTrigger`/`RegisterTrigger` constructs a `ratelimit.RateLimiter` per registered workflow trigger with a `perSender` map, initialized empty [3](#0-2) . Each time `HandleGatewayMessage` dispatches an incoming trigger event to `processTrigger`, the code calls `trigger.rateLimiter.Allow(body.Sender)` [4](#0-3) . In `RateLimiter.Allow`, if the sender key does not already exist, a brand-new `rate.Limiter` is created and permanently stored in `perSender[sender]` — there is no TTL, LRU eviction, or size cap, and no code path ever calls `delete()` on this map [5](#0-4) .

Critically, `body.Sender` originates from the gateway message body, which is attacker-influenced input arriving over the internet-facing gateway connector — not restricted to a fixed allowlist of legitimate senders (the `allowedSenders` check happens separately and rejects the *trigger delivery*, but `Allow` is still invoked with the raw sender value before/around that check in the loop) [6](#0-5) . An attacker can therefore submit a stream of trigger messages using a large number of distinct (spoofed) sender identifiers, each one permanently allocating a new `rate.Limiter` entry.

Compare this to other rate-limiter/cache implementations in the same codebase (e.g., `core/services/gateway/handlers/capabilities/v2/response_cache.go`, `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`'s `jwtReplayCache`, `core/capabilities/vault/request_replay_guard.go`, `core/services/gateway/handlers/capabilities/handler.go`'s `savedCallbacks`), all of which implement periodic pruning/eviction with TTL and/or max-size enforcement [7](#0-6) . The `RateLimiter` in `core/services/workflows/ratelimiter/ratelimiter.go` has no such safeguard, and it is directly wired to the unprivileged, internet-facing gateway trigger path via `core/capabilities/webapi/trigger/trigger.go`.

### Impact Explanation
Continued receipt of trigger messages carrying unique sender values causes the `perSender` map inside each registered workflow's `RateLimiter` to grow without bound, consuming heap memory indefinitely for the lifetime of the process (workflow triggers are typically long-lived/persistent registrations). Left unmitigated this leads to increasing memory pressure and, at scale, an out-of-memory condition or severe GC degradation on the node hosting the capability — a denial-of-service impacting all workflows on that node, not just the targeted one. This matches the Medium-severity classification given to the analogous VTVL finding, where the judge and sponsor agreed unbounded growth without a disposal mechanism is a legitimate (if slow-burn) DoS vector.

### Likelihood Explanation
Reachability requires only sending gateway trigger messages, which is the expected unprivileged entry point for the Web API trigger capability; the `body.Sender` value used as the map key is attacker-supplied and not validated to be from a small, fixed set before `Allow` is invoked. No special privileges, node compromise, or malicious-peer capability is needed — an external client interacting with the gateway's message-handling surface can drive this growth. Likelihood is moderated only by the fact that exploitation requires sustained traffic over time to accumulate enough map entries to matter.

### Recommendation
Bound the `perSender` map in `core/services/workflows/ratelimiter/ratelimiter.go`, mirroring the eviction/pruning patterns already used elsewhere in the codebase (e.g., `handler.pruneCallbacks` in `core/services/gateway/handlers/capabilities/handler.go`, or the TTL-based `jwtReplayCache`/`responseCache` cleanup routines). Concrete options:
- Add a periodic reaper goroutine that evicts `perSender` entries whose limiter has been idle (no recent `Allow` calls) beyond a configurable TTL.
- Enforce a hard maximum number of tracked senders, evicting the least-recently-used entries once the limit is exceeded.
- Alternatively, validate `body.Sender` against `allowedSenders` *before* calling `rateLimiter.Allow`, so unauthorized/spoofed senders never cause a map insertion in the first place.

### Proof of Concept
1. Register a Web API trigger workflow via `RegisterTrigger`, which creates a `ratelimit.RateLimiter` with an empty `perSender` map [8](#0-7) .
2. From the gateway side, repeatedly invoke `HandleGatewayMessage` → `processTrigger` with trigger request payloads whose `body.Sender` field is set to a freshly generated, unique address string on every call [9](#0-8) .
3. Each call reaches `RateLimiter.Allow(sender)`, which inserts a new `*rate.Limiter` into `perSender[sender]` because the key was never seen before [10](#0-9) .
4. Repeating this with N unique sender strings causes `perSender` to grow to N entries with no expiry; there is no code path that ever shrinks this map, so memory usage is proportional to the total number of distinct (possibly spoofed) senders ever observed by the process.

func (h *triggerConnectorHandler) RegisterTrigger(ctx context.Context, req capabilities.TriggerRegistrationRequest) (<-chan capabilities.TriggerResponse, error) {
	cfg := req.Config
	if cfg == nil {
		return nil, errors.New("config is required to register a web api trigger")
	}

	reqConfig, err := h.ValidateConfig(cfg)
	if err != nil {
		return nil, err
	}

	if len(reqConfig.AllowedSenders) == 0 {
		return nil, errors.New("allowedSenders must have at least 1 entry")
	}

	h.mu.Lock()
	defer h.mu.Unlock()
	_, errBool := h.registeredWorkflows[req.TriggerID]
	if errBool {
		return nil, fmt.Errorf("triggerId %s already registered", req.TriggerID)
	}

	rateLimiterConfig := reqConfig.RateLimiter
	commonRateLimiter := ratelimit.RateLimiterConfig{
		GlobalRPS:      rateLimiterConfig.GlobalRPS,
		GlobalBurst:    int(rateLimiterConfig.GlobalBurst),
		PerSenderRPS:   rateLimiterConfig.PerSenderRPS,
		PerSenderBurst: int(rateLimiterConfig.PerSenderBurst),
	}

	rateLimiter, err := ratelimit.NewRateLimiter(commonRateLimiter)
	if err != nil {
		return nil, err
	}

	allowedSendersMap := map[string]bool{}
	for _, k := range reqConfig.AllowedSenders {
		allowedSendersMap[k] = true
	}

	allowedTopicsMap := map[string]bool{}
	for _, k := range reqConfig.AllowedTopics {
		allowedTopicsMap[k] = true
	}

	ch := make(chan capabilities.TriggerResponse, defaultSendChannelBufferSize)

	h.registeredWorkflows[req.TriggerID] = webapiTrigger{
		workflowID:     req.Metadata.WorkflowID,
		allowedTopics:  allowedTopicsMap,
		allowedSenders: allowedSendersMap,
		ch:             ch,
		config:         *reqConfig,
		rateLimiter:    rateLimiter,
	}

	return ch, nil
}

// Wrapper around Go's rate.Limiter that supports both global and a per-sender rate limiting.
type RateLimiter struct {
	global    *rate.Limiter
	perSender map[string]*rate.Limiter
	config    Config
	mu        sync.Mutex
}

type Config struct {
	GlobalRPS      float64 `json:"globalRPS"`
	GlobalBurst    int     `json:"globalBurst"`
	PerSenderRPS   float64 `json:"perSenderRPS"`
	PerSenderBurst int     `json:"perSenderBurst"`
}

func NewRateLimiter(cfg Config) (*RateLimiter, error) {
	if cfg.GlobalRPS <= 0.0 || cfg.PerSenderRPS <= 0.0 {
		return nil, errors.New("RPS values must be positive")
	}
	if cfg.GlobalBurst <= 0 || cfg.PerSenderBurst <= 0 {
		return nil, errors.New("burst values must be positive")
	}

	return &RateLimiter{
		global:    rate.NewLimiter(rate.Limit(cfg.GlobalRPS), cfg.GlobalBurst),
		perSender: make(map[string]*rate.Limiter),
		config:    cfg,
	}, nil
}

func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}

func (h *handler) pruneCallbacks() {
	h.mu.Lock()
	defer h.mu.Unlock()

	// First, remove expired callbacks.
	maxAge := time.Duration(h.config.CallbackMaxAgeSec) * time.Second
	now := time.Now()
	var expired int
	for id, cb := range h.savedCallbacks {
		if now.Sub(cb.createdAt) > maxAge {
			delete(h.savedCallbacks, id)
			expired++
		}
	}

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}

	if expired > 0 || evicted > 0 {
		h.lggr.Infow("Pruned savedCallbacks", "expired", expired, "evicted", evicted, "remaining", len(h.savedCallbacks))
	}
}
