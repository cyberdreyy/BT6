### Title
Missing method-allowlist check in `confidentialrelay` handler allows unsupported/arbitrary JSON-RPC methods to be sent to live DON nodes before rejection - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`handler.HandleJSONRPCUserMessage` validates only `req.ID` (non-empty, ≤200 chars) and then immediately creates persistent state via `newActiveRequest` and fans the request out to every DON node via `fanOutToNodes`, without ever checking `req.Method` against `h.Methods()`. The only method-allowlist enforcement (`errUnknownMethod` inside `bundler.Bundle`) happens later, after the raw request has already been transmitted to nodes over the wire.

### Finding Description
`HandleJSONRPCUserMessage` at [1](#0-0)  only validates `req.ID` length/emptiness, then unconditionally calls `h.newActiveRequest(req, callback)` followed by `h.fanOutToNodes(ctx, l, ar)`. `fanOutToNodes` sends `&ar.req` — containing the caller-supplied `req.Method` verbatim — to every configured DON member via `h.don.SendToNode` [2](#0-1) , with no prior check that `req.Method` is one of `MethodSecretsGet`/`MethodCapabilityExec` returned by `Methods()` [3](#0-2) . The allowlist check (`errUnknownMethod`) exists only inside `bundler.Bundle`, which runs after node responses arrive (`HandleNodeMessage`) or on expiry/grace paths (`removeExpiredRequests`, `forwardAfterGrace`) — i.e., strictly after the wire send already happened.

Critically, this handler is normally reached through `multiHandler.getHandler`, whose fast path bypasses the method-to-handler allowlist entirely whenever only one handler type is registered:
```go
if len(m.typeToHandler) == 1 {
    for _, handler := range m.typeToHandler {
        return handler, nil
    }
}
``` [4](#0-3)  This means for any gateway/DON configuration where `confidentialrelay` is the sole registered handler (a supported, non-misconfiguration deployment shape), `req.Method` is never checked against the `methodToHandler` map before being routed into `handler.HandleJSONRPCUserMessage`. Combined with the handler's own lack of method validation, an unprivileged caller can submit `req.Method = "bogus"` and have it forwarded verbatim to every live DON node before any rejection occurs.

Regarding the specific scenario in the question — `fanOutToNodes` erroring out for all/most nodes — the `SendToNode` calls (and thus the network transmission of the bogus method) occur inside the `errgroup.Group` loop before the post-loop error-rate check `remainingPossibleResponses < h.donConfig.F+1` is even evaluated [5](#0-4) . So even in the "all sends fail" case, each node's `SendToNode` is invoked with the unvalidated method first; the subsequent `FatalError` response only reflects transport failure, not method rejection, and `bundler.Bundle`'s `errUnknownMethod` check is never reached in this path because the request is terminated via the transport-error branch, not via bundling.

This contrasts with the sibling `vault` handler, which explicitly validates `req.Method` against `vaulttypes.IsGatewaySecretsMethod` (or `MethodPublicKeyGet`) before creating any active request or contacting nodes [6](#0-5) , confirming that method pre-validation before external side effects is the established pattern that `confidentialrelay` fails to follow.

### Impact Explanation
Arbitrary, unsupported method strings from an unprivileged caller reach live DON node connections over the wire (`SendToNode`) regardless of eventual gateway-side rejection. This is a request-processing/allowlist bypass: it lets an unauthenticated/unprivileged gateway client cause the gateway to relay attacker-chosen `Method` values to every DON node in a given DON, consuming node-side bandwidth/processing and DON rate-limit budget (`perNodeRateLimiters`/`globalNodeRateLimiter` on the response path are irrelevant here since this is outbound), and creating persistent server-side state (`activeRequests` entries) for requests that can never legitimately be fulfilled. This matches an allowlist-bypass / unauthorized-request class impact rather than fund loss or key disclosure, but it is a genuine authorization-gating defect: the method allowlist is enforced only in a downstream response-processing stage, not at the point where the external side effect (network call to DON nodes) occurs.

### Likelihood Explanation
Reachable by any unprivileged caller of the gateway's JSON-RPC user-message endpoint who can supply an arbitrary `Method` field with a valid, non-empty, ≤200-char `ID`; no authentication/authorization beyond normal gateway request submission is required by `HandleJSONRPCUserMessage` itself. The `multiHandler` bypass additionally requires the deployment to have only one registered handler type for the DON in question (a legitimate, supported single-handler configuration, not a misconfiguration), which determines whether the multihandler-level allowlist is skipped as well. Repeatable per request; each call creates a fresh `activeRequest` (bounded by `req.ID` uniqueness) and triggers a full fan-out to the DON.

### Recommendation
In `handler.HandleJSONRPCUserMessage`, validate `req.Method` against `h.Methods()` (or the `relaytypes` method constants) immediately after the ID checks and before calling `newActiveRequest`/`fanOutToNodes`, returning `api.UnsupportedMethodError` synchronously — mirroring the `vault` handler's `IsGatewaySecretsMethod` check pattern. Additionally, remove or gate the single-handler bypass in `multiHandler.getHandler` so that method-allowlist enforcement is not skipped even when only one handler is registered, or ensure the enforcement happens equivalently inside each handler regardless of how it is invoked.

func (m *multiHandler) getHandler(method string) (handlers.Handler, error) {
	// If there's only one handler, return it directly.
	// This preserves backwards compatibility for cases where the method
	// isn't specified on responses (and for cases where only one handler is registered more generally).
	if len(m.typeToHandler) == 1 {
		for _, handler := range m.typeToHandler {
			return handler, nil
		}
	}

	handler, ok := m.methodToHandler[method]
	if !ok {
		return nil, errors.New("no handler found for method " + method)
	}

	return handler, nil
}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

	if !vaulttypes.IsGatewaySecretsMethod(req.Method) {
		return h.sendImmediateUserResponse(ctx, req, callback, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method))
	}
