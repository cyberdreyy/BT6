### Title
`GlobalStateEvaluator::reached_agreement` uses a floored 70% threshold while block-signature verification uses a ceiled 70% threshold, allowing the global signer state (current miner / burn view / protocol version) to be "agreed" on less real weight than the block-signing threshold requires - ([File: `libsigner/src/v0/signer_state.rs`])

### Summary
The external report's bug class is "two supposedly-equal quantities computed with different rounding/units, causing one side to be wrong (excess not returned, or insufficient causing revert)." The equivalent equality that must hold in the signer here is: *the weight required for "global state agreement" (which gates whether a signer will validate/sign a block at all) must be at least as strict as the weight required to actually accept/sign a block (`NakamotoBlockHeader::compute_voting_weight_threshold`)*. They diverge because one path ceils and the other floors.

### Finding Description
`NakamotoBlockHeader::compute_voting_weight_threshold` (used both by the node's `verify_signer_signatures` consensus check and by `stacks-signer`'s `store_and_process_block_signature`/`handle_block_pre_commit` to gate signing) computes the 70% threshold with an explicit **ceiling**: [1](#0-0) 

By contrast, `GlobalStateEvaluator::reached_agreement`, which gates `determine_global_state`, `determine_global_burn_view`, and `determine_latest_supported_signer_protocol_version` (i.e., which miner is "the" current miner, which burn view is canonical, and which tx-replay set/protocol version is active for block validation), uses plain integer division with **no ceiling**: [2](#0-1) 

`determine_global_state` feeds directly into `check_block_against_global_state`, which is the gate that decides whether a signer will even attempt to validate/sign a proposed block under the "global state" protocol path: [3](#0-2) 

and `capitulate_viewpoint`/`capitulate_miner_view` use the same `reached_agreement` threshold to decide when a signer flips its local view of the "current miner," directly influencing which miner's blocks it will subsequently sign: [4](#0-3) 

For any `total_weight` where `total_weight * 7` is not a multiple of 10 (i.e., most possible weight totals), `floor(total_weight*7/10) < ceil(total_weight*7/10)`. A miner/current-miner-view or burn-view "agreement" can therefore be reached with strictly less than the 70%-rounded-up weight that the block-acceptance/pre-commit machinery (`store_and_process_block_signature`, `handle_block_pre_commit`, `verify_signer_signatures`) requires to actually sign or accept a block. This is directly analogous to the report's core defect: an amount ("weight required") is assumed to be interchangeable between two code paths that in fact compute it with different rounding, so one path's notion of "enough" is looser than the other's.

### Impact Explanation
This breaks the intended equality between "the amount of weight considered sufficient to declare a global view (current miner / burn tip / protocol version)" and "the amount of weight actually required to sign/accept a block." A set of signers just under the true ceiled 70%-of-total threshold (e.g., weight distributions where the floor and ceil differ) can cause the `GlobalStateEvaluator` to flip the recognized "current miner" or accepted burn view with less real support than the signing threshold demands. Since `capitulate_miner_view`/`capitulate_viewpoint` use this looser threshold to change a signer's own local miner viewpoint (which subsequently governs which proposals it treats as coming from the legitimate miner and votes/signs accordingly), a signer can be steered into treating a non-canonical/incoming miner as canonical on the basis of under-threshold agreement, i.e., acting on a state that has not actually cleared the real (ceiled) approval bar. This lines up with the allowed High-impact category: "a signer... acting on a stale reward set/threshold," since the signer is acting on a threshold determination that is inconsistent with (weaker than) the threshold used elsewhere in the same protocol for the same nominal 70% bar.

### Likelihood Explanation
This requires no majority and no key compromise — it is a straightforward consequence of the total signer weight total not being a multiple of 10 (which is the common case for a live signer set of arbitrary weights), combined with an adversarial/naturally-partitioned minority landing between the floor and ceil bounds (e.g., total_weight = 13, ceil(13*7/10)=10, floor=9 — a set with exactly weight 9 reaches "agreement" under `reached_agreement` while it would not meet the block-signing threshold of 10). Any gossiping signer set can trigger this by natural weight distribution; it does not need a majority of signers, just a weight total for which floor != ceil at the 70% mark, which is the general case.

### Recommendation
Make `reached_agreement` (and its complement `reached_disagreement`) use the same ceiling-based computation as `NakamotoBlockHeader::compute_voting_weight_threshold`, ideally by calling that function directly instead of re-implementing the threshold math with floor division in `libsigner/src/v0/signer_state.rs`. This ensures "global state agreement" can never be reached with less weight than would be required to actually sign/accept a block under the same nominal threshold.

### Proof of Concept
1. Construct a reward set/`address_weights` map whose `total_weight` sums to a value where `total_weight * 7 % 10 != 0`, e.g. `total_weight = 13` (three signers with weights 5, 4, 4).
2. Compute the two thresholds:
   - `NakamotoBlockHeader::compute_voting_weight_threshold(13)` → `ceil(91/10) = 10`.
   - `GlobalStateEvaluator::reached_agreement` internal threshold → `floor(13*7/10) = 9`.
3. Have signers whose weights sum to exactly `9` (e.g., weights 5+4) broadcast `StateMachineUpdate`s pointing to a new/incoming miner and a new burn view.
4. `GlobalStateEvaluator::determine_global_state`/`determine_global_burn_view` report agreement (`reached_agreement(9)` is `true` since `9 >= 9`), causing `check_block_against_global_state` and `capitulate_miner_view`/`capitulate_viewpoint` to flip the local signer's view of the canonical miner/burn tip.
5. Meanwhile, the same weight of `9` is insufficient to satisfy `compute_voting_weight_threshold(13) = 10` for actually signing a block under `store_and_process_block_signature`/`handle_block_pre_commit`, demonstrating the two "70%" thresholds are not equivalent — global-state agreement is reachable with less weight than block-signing agreement, exactly mirroring the external report's core flaw of assuming a 1:1 correspondence between two independently rounded quantities.     pub fn compute_voting_weight_threshold(total_weight: u32) -> Result<u32, ChainstateError> {
        let threshold = NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD;
        let total_weight = u64::from(total_weight);
        let ceil = if (total_weight * threshold) % 10 == 0 {
            0
        } else {
            1
        };
        u32::try_from((total_weight * threshold) / 10 + ceil).map_err(|_| {
            ChainstateError::InvalidStacksBlock(
                "Overflow when computing nakamoto block approval threshold".to_string(),
            )
        })
    }
