### Title
Local Cache AlternateKey Path Lacks Traversal Guard Present in Remote Cache Path Construction - ([File: functions/concrete/run/stages/cache_archive.go])

### Summary
`CacheArchive.alternateArchivePath` (and the equivalent primary `archivePath`) build the local on-disk archive path by joining a job-supplied string directly into `e.CacheDir` with no traversal check, unlike the distributed-cache object path built in `cache.GetAdapter`, which explicitly rejects any resulting path that doesn't stay under `basePath`. The framing in the question ("sha256 hash collision") is not the real mechanism — SHA-256 collisions are not practically achievable — but there is a genuine, reachable asymmetry: under `FF_HASH_CACHE_KEYS=true`, the `AlternateKey` value used for the local archive path is the raw, **unsanitized** job-supplied cache key, not the sanitized/hashed form.

### Finding Description
In `functions/concrete/builder/builder.go:570-603` (`cacheKey`), when `featureflags.HashCacheKeys` is on, `humanKey = rawKey` is used verbatim — `cachekey.Sanitize` is skipped entirely: [1](#0-0) 

In `buildCacheArchive` (`functions/concrete/builder/builder.go:361-370`), the `AlternateKey` for the archive is computed as:
```
alternateResolved := humanKey
if !b.isFeatureFlagOn(featureflags.HashCacheKeys) {
    alternateResolved = sha256(humanKey)
}
``` [2](#0-1) 

So when `FF_HASH_CACHE_KEYS=true`, `s.Key` (primary) is the safe sha256 hex digest, but `s.AlternateKey` is the **raw, unsanitized** job-supplied cache key string (`cache.key`, expanded via `b.variables.ExpandValue`) — attacker-controlled, and can contain `../` sequences.

`CacheArchive.alternateArchivePath` then builds the local path with no bounds check: [3](#0-2) 

`e.CacheDir` is set once per build to a project-scoped directory (`b.CacheDir = path.Join(cacheDir, b.ProjectUniqueDir(false))`, `common/build.go:511`), and documented as `<working-directory>/cache/<namespace>/<project-name>` for shell executor or `<cache-dir>/runner-.../` for Docker host-bound cache. Because `filepath.Join` cleans `..` segments, a sufficiently crafted `AlternateKey` (e.g. `../../../<other-namespace>/<other-project>/pwned`) can walk out of the current project's `CacheDir` into a sibling project's cache directory that resides on the same host filesystem.

This is asymmetric with the equivalent remote/object-storage code path in `cache.GetAdapter`, which explicitly guards against exactly this class of escape: [4](#0-3) 
No equivalent `strings.HasPrefix(fullPath, e.CacheDir+string(filepath.Separator))` check exists for the local archive path in `cache_archive.go` or `cache_extract.go`.

### Impact Explanation
On shared-host setups (shell executor, or Docker/Kubernetes executors configured with a host-bound `cache_dir`, both explicitly documented layouts where multiple projects' cache trees are siblings under one working directory), a job can set `AlternateKey`-affecting cache key to traverse out of its own project's cache subtree and cause `cache-archiver --alternate-file <escaped-path>` to write a `cache.zip` into another project's cache directory location. This is local filesystem cache poisoning across project boundaries — a concrete violation of the "file operations must stay within intended cache root" invariant — even though it is not the SHA-256-collision mechanism hypothesized in the question.

### Likelihood Explanation
Requires: (1) a shared-host runner configuration where cache directories for different projects are co-located on the same filesystem tree (shell executor, or Docker/K8s with host-bound `cache_dir` — both documented, common configurations), and (2) `FF_HASH_CACHE_KEYS=true` on the runner. Given these preconditions, any unprivileged pipeline author fully controls `cache.key` and can trigger this deterministically and repeatably — no privilege escalation or race condition needed.

### Recommendation
Add the same containment check used in `cache.GetAdapter` to the local archive path builder `cacheArchivePath` in `functions/concrete/run/stages/cache_archive.go` (and the analogous helper in `cache_extract.go`): after `filepath.Join(e.CacheDir, key, "cache.zip")`, verify the resulting absolute path has `e.CacheDir` as a strict prefix, and fail/skip the cache operation (similar to `nopAdapter` fallback) if not. Additionally, consider sanitizing/rejecting `..` segments in `AlternateKey`/`humanKey` even when `FF_HASH_CACHE_KEYS` is enabled, rather than only skipping sanitization for the primary hashed key.

### Proof of Concept
```go
func TestCacheArchive_AlternateKeyPathTraversalEscapesCacheDir(t *testing.T) {
    e := &env.Env{
        WorkingDir: "/builds/group-a/project-a",
        CacheDir:   "/cache/group-a/project-a",
    }
    s := CacheArchive{
        Key:          "abcd1234", // safe sha256 hex (primary, FF on)
        AlternateKey: "../../group-b/project-b/pwned", // raw job-controlled key, FF on
    }
    got := s.alternateArchivePath(e)
    abs := filepath.Join(e.WorkingDir, got)
    // Assert the resolved alternate archive path never escapes the current
    // project's cache namespace (mirrors cache.GetAdapter's basePath check).
    assert.True(t, strings.HasPrefix(abs, e.CacheDir+string(filepath.Separator)),
        "alternate archive path %q escaped CacheDir %q", abs, e.CacheDir)
}
```
This test currently fails against the existing implementation (the resolved path lands under `/cache/group-b/project-b/pwned/cache.zip`, outside `/cache/group-a/project-a`), demonstrating the missing containment check.

func cacheArchivePath(e *env.Env, key string) string {
	absPath := filepath.Join(e.CacheDir, key, "cache.zip")
	rel, err := filepath.Rel(e.WorkingDir, absPath)
	if err != nil {
		return absPath
	}
	return rel
}
