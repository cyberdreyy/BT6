### Title
Rejection-tracking table keyed only by `signer_addr` lets a later rejection of a different block silently erase/overwrite an earlier rejection record, causing local under-counting of the >30% global-rejection threshold - ([File: stacks-signer/src/signerdb.rs])

### Summary
The Fuel report's root cause is that different storage layouts (variable hashing vs. `StorageMap` key hashing) can be made to collide, so one write silently clobbers another logically-unrelated slot. The `stacks-signer` local SQLite schema exhibits the same class of defect in `block_rejection_signer_addrs`: the table's primary key is declared over `signer_addr` alone, not `(signer_signature_hash, signer_addr)`, even though the column comment states the sighash is what "uniquely identif[ies] the block." Two logically distinct records — "signer X rejected block A" and "signer X rejected block B" — collide on the same storage row keyed only by `signer_addr`, so recording the second silently destroys the first.

The table is declared as: [1](#0-0) 

Note the comment directly above explicitly states the sighash alone is sufficient to uniquely identify a block, yet the `PRIMARY KEY` clause covers only `signer_addr`. A later `CREATE INDEX` is added purely as a secondary lookup aid, not a uniqueness constraint:
this is consistent with the live schema never enforcing uniqueness on `(signer_signature_hash, signer_addr)`.

The per-block rejection weight used to decide "global rejection" is recomputed fresh from this table on every incoming rejection: [2](#0-1) 

and consumed in `handle_block_rejection`, where `total_reject_weight` is summed from whatever rows currently exist for `block_hash` and compared against the >30%-blocking-minority threshold to decide `mark_globally_rejected`: [3](#0-2) [4](#0-3) 

Because the row is keyed only by `signer_addr`, once this local signer observes `signer_addr` rejecting some other, unrelated block `B` (e.g. a sibling proposal at a different height/tenure, or a re-proposal that supersedes a stalled block `A`), the earlier row recording `signer_addr`'s rejection of block `A` is overwritten/lost. Any subsequent call to `get_block_rejection_signer_addrs(A)` on this signer's local database will under-report the true set of addresses that rejected `A`, permanently losing that vote's weight for `A` unless `signer_addr` rejects `A` again.

The unit test `duplicate_block_rejections` only exercises overwrite behavior *within the same block_id*, and never exercises the cross-block-collision case (two different `signer_signature_hash` values with the same `signer_addr`), so the collision is not caught by existing tests: [5](#0-4) 

### Impact Explanation
This breaks the equality between "the true aggregated rejected weight for block A" and "what `get_block_rejection_signer_addrs`/the summed weight computation actually returns" on the affected signer's local view. A stale/dead block that has genuinely accumulated ≥30% weight in rejections (enough to make 70% approval impossible) can be silently under-counted on some signers because one or more rejecting addresses' rows were reassigned to a later, unrelated block. That signer never calls `mark_globally_rejected` for `A`, so it never converges to the terminal "globally rejected" state for that block even though the objective network fact (aggregate weight) supports it — a liveness wedge on this signer's local state machine for that stale proposal, matching the "High" impact bucket ("a signer wedged" state, here specifically wedged around a stale/pending block resolution rather than reaching the correct terminal state).

### Likelihood Explanation
This is fully triggerable by a single one-slot miner (plus ordinary gossip) without needing a majority of signers, another signer's key, or any privileged access: the miner (or any byzantine actor) only needs to cause two distinct invalid/conflicting block proposals to be rejected in sequence by the same honest signer address, observed by a third-party signer's local DB, e.g. via re-proposing a competing/sibling block after an initial rejected proposal. No majority collusion, no forged signatures, and no StackerDB/transport exploit is required — it is a pure local-storage keying defect in `signerdb.rs`.

### Recommendation
Change the primary key of `block_rejection_signer_addrs` to the composite `(signer_signature_hash, signer_addr)` (matching the pattern already used correctly for `blocks` and other per-block tables), and add a corresponding schema migration. Audit other per-block/per-address tracking tables in `signerdb.rs` for the same "hash comment says one thing, PRIMARY KEY says another" mismatch.

### Proof of Concept
1. Local signer S observes and stores `add_block_rejection_signer_addr(sighash_A, addr_X, reason)` for block `A` (e.g. `InvalidParentBlock`).
2. `get_block_rejection_signer_addrs(A)` correctly returns `[(addr_X, InvalidParentBlock)]`, contributing `addr_X`'s weight toward `A`'s reject tally as computed in `handle_block_rejection` (`stacks-signer/src/v0/signer.rs:2297-2306`).
3. Before `A` reaches the rejection threshold, a competing/sibling block `B` is proposed and also rejected by `addr_X`; S observes this and calls `add_block_rejection_signer_addr(sighash_B, addr_X, reason)`.
4. Because the table's `PRIMARY KEY` is `(signer_addr)` only (`stacks-signer/src/signerdb.rs:514-524`), this `INSERT OR REPLACE` overwrites the row for `addr_X`, changing its `signer_signature_hash` from `sighash_A` to `sighash_B`.
5. `get_block_rejection_signer_addrs(A)` on S no longer returns `addr_X`; `A`'s locally-computed `total_reject_weight` permanently drops by `addr_X`'s weight, potentially keeping `A` below the >30% global-rejection threshold on S even though the network's true rejecting weight (including `addr_X`) exceeds it.

**Uncertainty note:** I was unable to view the exact SQL body of `add_block_rejection_signer_addr` (the tool budget was exhausted before that call returned), so I cannot 100% confirm the write uses `INSERT OR REPLACE` rather than a two-step delete/insert guarded by an explicit `(hash, addr)` check elsewhere in code not surfaced by search. The schema evidence (`PRIMARY KEY (signer_addr)` plus a separate non-unique index on `signer_signature_hash`) and the existing `duplicate_block_rejections` test (which shows same-block overwrite is real) support the conclusion, but full confirmation of the cross-block overwrite path would require reading `add_block_rejection_signer_addr`'s implementation directly, which was not completed in this session.

    /// Get all signer addresses that rejected the block (and their reject codes)
    pub fn get_block_rejection_signer_addrs(
        &self,
        block_sighash: &Sha512Trunc256Sum,
    ) -> Result<Vec<(StacksAddress, RejectReasonPrefix)>, DBError> {
        let qry =
            "SELECT signer_addr, reject_code FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1";
        let args = params![block_sighash];
        let mut stmt = self.db.prepare(qry)?;

        let rows = stmt.query_map(args, |row| {
            let addr: String = row.get(0)?;
            let addr = StacksAddress::from_string(&addr).ok_or(SqliteError::InvalidColumnType(
                0,
                "signer_addr".into(),
                rusqlite::types::Type::Text,
            ))?;
            let reject_code: i64 = row.get(1)?;

            let reject_code = u8::try_from(reject_code)
                .map_err(|_| {
                    SqliteError::InvalidColumnType(
                        1,
                        "reject_code".into(),
                        rusqlite::types::Type::Integer,
                    )
                })
                .map(RejectReasonPrefix::from)?;

            Ok((addr, reject_code))
        })?;

        rows.collect::<Result<Vec<_>, _>>().map_err(|e| e.into())
    }
