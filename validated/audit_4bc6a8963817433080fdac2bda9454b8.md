### Title
Withdrawal receipts charge a full epoch-plus-buffer upfront management fee that is never refunded when the actual out-of-NAV wait is shorter (early claim, shortened epoch, or pool close) - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`requestWithdraw` deducts an upfront management fee sized for the *worst-case* custody time of the receipt — the full `epochDuration` plus any remaining buffer — but the claim path only requires a single `stopEpoch` (epoch number bump). When the next epoch is set shorter via `stopEpochWithDuration`, or the pool is closed (`_interest == 1`, which zeroes `epochDuration`/`epochEndDate` and makes claims immediate), users still paid the full-duration fee. There is no refund or reconciliation mechanism, so `feeReceiver` collects fees for time the funds never spent outside live NAV — the same "overcharge without refund" bug class as the Wormhole report.

### Finding Description
In `requestWithdraw`, the user's receipt amount is reduced by `totalFees` computed by `_totalWithdrawFees`, which calls `_calculateManagementFee(_principal, _withdrawRequestManagementFeeDuration())` [1](#0-0) . The duration is `epochDuration + (bufferEnd - block.timestamp)`, i.e. it always assumes the receipt will sit outside live NAV for a full next epoch [2](#0-1) .

However, the claimability gate in `IdleCreditVault._claimFundedWithdrawRequest` only requires `epochNumber > lastWithdrawRequest` (or `epochEndDate == 0`) [3](#0-2) . Two legitimate manager flows make the real wait strictly shorter than the charged duration:

1. `stopEpochWithDuration(_newApr, _interest, _duration, _lossAmount)` sets an arbitrary `_duration` for the next epoch [4](#0-3) . If `_duration < epochDuration` (e.g. the pool migrates to shorter epochs, or the manager stops the following epoch right after its shorter `epochEndDate`), the receipt was claimable after less time than the fee paid for.
2. Closing the pool (`_interest == 1`) sets `epochDuration = 0` and `epochEndDate = 0` [5](#0-4) , making receipts claimable immediately — yet the requester was still charged a full `epochDuration + buffer` management fee at request time.

The charged fee is booked into `pendingWithdrawFees` [6](#0-5)  and paid out to `feeReceiver`/owner at the next stop [7](#0-6) , with no code path that credits back the unused portion. Notably, the codebase already waives accrued management fees on default (`testStopEpochDefaultWaivesAccruedManagementFees`), showing the protocol recognizes the "pay only for elapsed time" invariant for live NAV — but the upfront withdrawal fee violates it.

### Impact Explanation
Withdrawers are overcharged by `principal * managementFee * (chargedDuration - actualWait) / FULL_ALLOC / 365 days`, permanently transferred to `feeReceiver`. In the pool-close scenario the entire upfront fee corresponds to zero actual wait: a user requesting withdrawal during the buffer pays `managementFee * (epochDuration + remainingBuffer)` yet can claim in the same block the close-stop lands. With a 1% management fee, a 30-day epoch and a request made at buffer start, that is ~`principal * 0.01 * 35/365` ≈ 9.6 bps of principal taken as a pure overcharge, scaled arbitrarily higher by larger `managementFee`/`epochDuration` configurations.

### Likelihood Explanation
Triggering requires only honest manager operations that are part of normal protocol lifecycle: shortening the next epoch via `stopEpochWithDuration`, or closing the pool (`stopEpoch` with `_interest == 1`). Any KYC-passing lender who requested withdrawal in the prior buffer/epoch is affected; no privileged misbehavior, no timing luck, and no attacker action is needed beyond holding a withdrawal receipt when the manager legitimately shortens or closes the epoch. Every such receipt is deterministically overcharged because no refund accounting exists anywhere in the claim path.

### Recommendation
Track the fee basis per request (or per epoch) and reconcile at claim or at the next `stopEpoch`: compute the actual out-of-NAV duration (`min(charged, realized until claimable)`) and credit the difference back to the receipt amount before it is released to `pendingWithdrawFees`/feeReceiver. Concretely, store the charged management fee per epoch alongside `withdrawsRequestsByEpoch`, and in `stopEpoch`/`collectWithdrawFunds` — where the actual elapsed duration is known — return `fee * (chargedDuration - actualDuration) / chargedDuration` to the pending-withdrawal pool before splitting fees, so `claimWithdrawRequest` pays the corrected amount.

### Proof of Concept
Foundry fork PoC (close-pool variant, deterministic):

```solidity
function testUpfrontMgmtFeeNotRefundedOnPoolClose() external {
    _setManagementFee(1_000); // 1% annualized
    uint256 amt = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amt);
    _startEpochAndCheckPrices(0);

    // epoch 0 ends, epoch 1 (buffer) begins
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    // request withdraw during buffer: fee charged for epochDuration + remaining buffer
    uint256 feeDuration = cdoEpoch.epochDuration() +
        (cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() - block.timestamp);
    uint256 expectedMgmtFee = amt * cdoEpoch.managementFee() * feeDuration / FULL_ALLOC / 365 days;
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertApproxEqAbs(amt - requested, expectedMgmtFee, 1, 'upfront fee');

    // manager legitimately closes the pool: epochDuration = epochEndDate = 0, claims immediate
    _toggleEpoch(false, initialProvidedApr, 1); // _interest == 1 sentinel
    assertEq(cdoEpoch.epochEndDate(), 0);

    // receipt claimable right away — zero time spent outside live NAV
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(address(this)) - balPre;

    // user paid a full epoch+buffer fee for a zero-length wait; nothing is refunded
    assertApproxEqAbs(requested - paid, 0, 1);
    assertGt(expectedMgmtFee, 0, 'overcharge kept by feeReceiver');
}
```

The same overcharge reproduces by replacing the close with `stopEpochWithDuration(..., _duration < epochDuration)` and warping to the shorter `epochEndDate` before claiming.
