## Analysis

The claim is valid. `createDstEscrow` performs **no validation whatsoever** on the `dstImmutables.parameters` blob supplied by the caller — it takes the full `Immutables` struct (including `parameters`) as-is, uses it to derive the CREATE2 salt, and deploys the clone funded with the caller's own tokens/ETH. [1](#0-0) 

`EscrowDst._withdraw` (shared by both `withdraw` and `publicWithdraw`) unconditionally decodes fee fields from `immutables.parameters` before transferring the maker's payout: [2](#0-1) 

`ImmutablesLib`'s calldata decoders each impose a minimum length requirement and revert with `IndexOutOfRange()` if not met: `protocolFeeAmountCd` needs `>= 0x20`, `integratorFeeAmountCd` needs `>= 0x40`, and `integratorFeeRecipientCd`/`protocolFeeRecipientCd` need `>= 0x80`. [3](#0-2) 

If the escrow creator supplies a 64-byte `parameters` blob (`0x40`) whose last 32 bytes decode to a non-zero `integratorFeeAmount`, then in `_withdraw`: `integratorFeeAmountCd()` succeeds (needs `0x40`), but the subsequent `integratorFeeRecipientCd()` call (needs `0x80`) reverts with `IndexOutOfRange()`. Since `withdraw()` and `publicWithdraw()` both funnel through the identical `_withdraw` internal function, **both the private and public withdrawal paths revert identically** — there is no fallback. [4](#0-3) 

Because `onlyValidImmutables` binds the call to the exact immutables (including `parameters`) used at CREATE2 deployment, any caller — private taker or public access-token holder — must resupply the same malformed `parameters`, and will hit the same revert. The only surviving path is `cancel()`, which does not decode fees and returns the entire `amount` to the taker (not the maker): [5](#0-4) 

This defeats the specific purpose of `publicWithdraw` — a permissionless fallback intended to let any access-token holder finalize the payout to the maker when the taker fails to act. With attacker-chosen `parameters`, this safety valve is provably disabled, and the maker's payout can only be resolved via cancellation, which sends the full amount back to the taker instead of the maker.

### Title
Unvalidated `parameters` blob in `createDstEscrow` lets the escrow creator permanently brick both `withdraw` and `publicWithdraw` fee decoding, freezing the maker's destination payout - (File: `contracts/EscrowDst.sol`, `contracts/libraries/ImmutablesLib.sol`, `contracts/BaseEscrowFactory.sol`)

### Summary
`createDstEscrow` accepts an entirely creator-controlled `parameters` byte blob with zero length/format validation. `EscrowDst._withdraw`, shared by both `withdraw` and `publicWithdraw`, decodes fee fields from this blob using `ImmutablesLib` functions that revert on insufficient length. A creator can fund a destination escrow with a 64-byte `parameters` blob encoding a non-zero integrator fee but omitting the fee-recipient words, guaranteeing `integratorFeeRecipientCd()` reverts in every future withdrawal attempt — private or public.

### Finding Description
`createDstEscrow` uses caller-supplied `dstImmutables` directly, including `parameters`, with no cross-check against the src-chain `SrcEscrowCreated`/`DstImmutablesComplement.parameters` data and no length assertion. [1](#0-0) 
`_withdraw` always calls `integratorFeeAmountCd()` and `protocolFeeAmountCd()`, and conditionally calls the recipient decoders when the amount is non-zero. [6](#0-5) 
With a 64-byte blob, `integratorFeeAmountCd()` (needs `0x40`) succeeds and can return any attacker-chosen value, but `integratorFeeRecipientCd()` (needs `0x80`) always reverts. [7](#0-6) 
Both `withdraw` and `publicWithdraw` route through this same internal function, so the bug affects the public fallback identically to the private path. [8](#0-7) 

### Impact Explanation
The maker's destination-chain payout becomes permanently unreachable through any withdrawal mechanism once the secret is known — both the intended private path and the permissionless public fallback revert deterministically. Only `cancel()` remains viable, but it returns the full amount to the taker, not the maker, so the maker never receives the swap proceeds despite the secret having been correctly revealed. This matches "Temporary freezing of funds during the live swap lifecycle" (and effectively total loss of the intended payout for the maker, since cancellation reroutes funds to the taker).

### Likelihood Explanation
The escrow creator (any unprivileged caller of `createDstEscrow`, typically acting as taker/resolver) fully controls `parameters` with no on-chain validation. No special privilege or race condition is required — the attacker simply crafts calldata during `createDstEscrow`.

### Recommendation
Enforce a strict length/format check on `parameters` in `createDstEscrow` (e.g., require `parameters.length == 0` or exactly the expected fee-encoding size `0x80`), and/or validate `integratorFeeAmount + protocolFeeAmount < amount` and that recipient words are present whenever a fee amount is non-zero, mirroring the `InvalidFeeAmounts` check already used on the source side. [9](#0-8) 

### Proof of Concept
1. Attacker calls `createDstEscrow` with `dstImmutables.parameters = abi.encode(uint256(0), uint256(hugeIntegratorFee))` (64 bytes total), funding the required `amount` + `safetyDeposit` themselves. [1](#0-0) 
2. Warp past `DstWithdrawal` and call `withdraw(secret, immutables)` as taker — reverts with `IndexOutOfRange()` inside `integratorFeeRecipientCd()`.
3. Warp past `DstPublicWithdrawal` and call `publicWithdraw(secret, immutables)` as any access-token holder — reverts identically since it calls the same `_withdraw`. [10](#0-9) 
4. Only `cancel()` succeeds after `DstCancellation`, returning the full `amount` to the taker and leaving the maker unpaid. [5](#0-4)

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
