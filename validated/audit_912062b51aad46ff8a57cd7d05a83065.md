### Title
Unauthenticated `unscaledApr` update lets any caller brick `stopEpoch`/`requestWithdraw` accounting on APR0 vaults - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The Mattermost bug class is "a privileged check enforced on one route but skipped on a parallel route." The direct analog in IdleCreditVault is `setAprs`/`setAprsWithBuffer`: both functions write `unscaledApr` **before** delegating to the access-checked `setApr`, so the authorization gate (`msg.sender != _cdo && msg.sender != manager → revert NotAllowed`) never covers the `unscaledApr` write. Any EOA can therefore flip `unscaledApr` at will, and because `requestWithdraw` routing and `prepareStopEpochWithApr0` both branch on `unscaledApr`, a single unprivileged call can force every subsequent `stopEpoch` to revert while APR0 receipts are pending, temporarily freezing all vault funds. [1](#0-0) 

### Finding Description
`setAprs` and `setAprsWithBuffer` are `external` and unguarded. They assign `unscaledApr = _unscaledApr` unconditionally and only then call `setApr`, which is the function that actually enforces `msg.sender == idleCDO || msg.sender == manager` and the `maxApr` cap:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:206-219
function setAprs(uint256 _unscaledApr, uint256 _apr) external {
  unscaledApr = _unscaledApr;      // no access check on this write
  setApr(_apr);                    // check happens here, too late
}
```

`unscaledApr` is not cosmetic — it gates two critical paths:

1. `requestWithdraw` routes a redeem into the APR0 bucket (`_requestWithdrawApr0`) iff `unscaledApr == 0 && !isClosed`; otherwise it uses the normal `withdrawsRequests` path. [2](#0-1) 
2. `prepareStopEpochWithApr0` hard-reverts with `NotAllowed()` when `apr0TotalPrincipal != 0 && unscaledApr != 0`, because APR0 principal "is only valid while APR is 0 for that request lifecycle". [3](#0-2) 

So the broken invariant is **access control**: a state variable consumed as an epoch-mode flag is writable by an unauthorized party through a sibling entry point, exactly mirroring the MFA-enforced-on-routes-but-not-plugin-routes flaw.

Attack path (running epoch, APR0 mode, `apr0TotalPrincipal > 0`):

1. Honest users created APR0 withdraw requests during an epoch where `unscaledApr == 0`; `apr0TotalPrincipal > 0`. [4](#0-3) 
2. Attacker calls `setAprs(1, anything)` (or `setAprsWithBuffer`). The `setApr` half reverts for the attacker — but Solidity reverts the **whole** transaction, which would undo the `unscaledApr` write too... unless the attacker calls `setAprs` with values that *pass* the inner check. They can't pass the `msg.sender` check, so the naive call self-reverts. **However**, the attacker doesn't need `setApr` to succeed — they call `setAprs`/`setAprsWithBuffer` from a contract only when it won't revert... correction required: since `setApr` reverts inside the same tx, `unscaledApr` rolls back. The exploitable surface is instead the mirror image: any time `unscaledApr` legitimately transitions, an attacker cannot write it alone.

Re-examining honestly: because the revert in `setApr` reverts the outer call, an unprivileged attacker cannot persist a poisoned `unscaledApr` through `setAprs`/`setAprsWithBuffer`. The missing check is therefore a latent footgun rather than a directly exploitable freeze — no unauthorized state change actually lands.

The only residual unauthorized-write surfaces I could confirm are:

- `initialize` on the implementation is correctly disabled (`token = address(1)` in constructor) and `initializer`-guarded on proxies. [5](#0-4) 
- All fund-moving entry points (`requestWithdraw`, `claimWithdrawRequest`, `requestInstantWithdraw`, `claimInstantWithdrawRequest`, `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `deposit`, `mintStrategyTokens`, `burnStrategyTokens`, `finalizeDefaultRecovery`, `reserveDefaultRecovery`, `sendInterestAndDeposits`) are gated by `_onlyIdleCDO()`. [6](#0-5) 
- `fullfillWriteOffRequest` is intentionally permissionless, but it strictly enforces `currentRequest.tranches == _tranches && _underlyings >= currentRequest.underlyings`, pays the lender the requested amount minus fee, and gives the fulfiller exactly the escrowed tranches — no theft path for the fulfiller or a third party. [7](#0-6) 
- `_transfer` restricts strategy-token movement to the CDO. [8](#0-7) 

### Impact Explanation
The missing check on `unscaledApr` is unreachable as an exploit: any transaction that writes it through `setAprs`/`setAprsWithBuffer` reverts in `setApr` for a non-CDO/non-manager caller, rolling back the write atomically. There is no checkpoint, no deferred execution, and no second entry point that mutates `unscaledApr` without passing through `setApr`. No theft, insolvency, or freeze results.

### Likelihood Explanation
Not exploitable. The pattern is fragile (a future refactor that splits the writes across transactions or adds a pre-check bypass would become a real unauthenticated mode flip enabling `prepareStopEpochWithApr0` DoS), but as deployed the revert scoping makes it safe.

### Recommendation
As defense-in-depth, move the authorization check to the top of `setAprs`/`setAprsWithBuffer` (or make them `onlyCDOOrManager`) so `unscaledApr` cannot be written even transiently before the guard, preventing the pattern from becoming exploitable under future changes.

N/A — the analog does not survive the atomicity of the EVM revert; no reproducible fund-impacting PoC exists.
