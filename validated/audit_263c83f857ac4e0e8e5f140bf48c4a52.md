### Title
Instant-withdraw path in `requestWithdraw` skips all management/performance fees - (File: contracts/IdleCDOEpochVariant.sol)

### Summary

The external bug is a branch-dependent fee skip: the swap fee is re-added to `deltaInput` only when `remainder <= maxInput`, so when `remainder > maxInput` the user swaps fee-free. The direct analog in idle-tranches is `requestWithdraw` in `contracts/IdleCDOEpochVariant.sol` (lines 739-791). It has two branches: the normal queued path, which computes `totalFees = _totalWithdrawFees(principal, interest)`, nets them out of the receipt, and tracks them in `pendingWithdrawFees`; and the instant-withdraw path (lines 761-770), which fires when `lastEpochApr > currentApr + instantWithdrawAprDelta` and calls `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` on the **full** principal, deducting nothing and crediting nothing to `pendingWithdrawFees`. The fee that was assessed on the queued path is silently dropped in the instant path — the same "fee not re-added in the >-branch" defect class.

### Finding Description

The code's own comment establishes the invariant: receipts leave live NAV at request time and wait outside it, so management fees are "charged upfront for the time it waits outside live NAV" (line 786-787, `_withdrawRequestManagementFeeDuration` at lines 925-931 returns `epochDuration` plus remaining buffer). An instant-withdraw receipt also sits outside live NAV for `instantWithdrawDelay` before it is claimable, and the principal it redeems accrued management fees while inside NAV during the elapsed epoch (`maxWithdrawable` at line 913 explicitly deducts `_calculateManagementFee(currentUnderlyings, block.timestamp - latestHarvestBlock)`). Yet the instant branch burns `_amount` tranche tokens and decreases NAV by the gross `principal` via `_withdrawOps`, with no fee deducted anywhere — neither for elapsed-epoch accrual nor for the delay the instant receipt spends outside NAV.

So two users holding identical principal in the same epoch pay different fees purely based on which branch of `requestWithdraw` executes: the queued user is haircut by `mgmtFee + perfFee` (and `pendingWithdrawFees` later flows to `unclaimedFees`/`feeReceiver`/`owner` in `stopEpoch`, lines 431-459), while the instant user redeems principal at 100% and contributes zero.

### Impact Explanation

- feeReceiver/owner permanently lose the management fee (and any performance-fee-equivalent accounting) on every instantly-withdrawn principal. Quantified loss per withdrawal: `principal * managementFee * (block.timestamp - latestHarvestBlock) / 365 days` (elapsed accrual) plus `principal * managementFee * instantWithdrawDelay / 365 days` (time the receipt waits outside NAV), i.e. roughly `principal * mgmtFeeRate * (elapsedEpoch + instantWithdrawDelay) / 365d`. With a 1% mgmt fee and a mid-epoch instant exit this is ~0.5-1%+ of principal per event, and it is repeatable every time the APR drops by more than `instantWithdrawAprDelta`.
- The loss is socialized: NAV is decreased by the full principal while `pendingWithdrawFees`/`unclaimedFees` never see the fee, so remaining AA/BB holders effectively fund the fee-free exit relative to the queued path.
- Broken invariant: uniform fee assessment on capital leaving the vault (fair burn / fee-collection invariant).

### Likelihood Explanation

- Attacker is an unprivileged KYC-passing lender: `requestWithdraw` only requires `isWalletAllowed(msg.sender)` and the per-tranche allow flag (lines 741-744), both satisfiable by any whitelisted user.
- The trigger is not privileged: instant mode activates whenever `lastEpochApr > unscaledApr + instantWithdrawAprDelta` after a `stopEpoch` — an ordinary, manager-honest epoch transition. The attacker simply times `requestWithdraw` into the instant window instead of the queued window.
- No existing guard stops it: `_skimDonatedAssets` and `_updateAccounting` run before the branch and don't compensate; `pendingWithdrawFees` is untouched on the instant path; the Default/closed-pool gates don't apply during normal buffer epochs.
- Caveat: if the protocol intentionally exempts instant withdraws from management fees (trading no-interest for no-fee), this is a design decision rather than a bug — but the code comments frame the upfront fee as compensation for time spent outside live NAV, which applies equally to instant receipts (`instantWithdrawDelay`), and elapsed-epoch accrual is independent of exit path. At minimum the elapsed-accrual component (`block.timestamp - latestHarvestBlock`) is unambiguously owed per `maxWithdrawable`'s own accounting and is never collected.

### Recommendation

- Apply the same fee-assessment logic to the instant branch: compute `_totalWithdrawFees(principal, 0)` (or a duration-scaled `_calculateManagementFee` covering elapsed time plus `instantWithdrawDelay`), deduct it from the amount passed to `requestInstantWithdraw`, and add it to `pendingWithdrawFees` so `stopEpoch` routes it to `unclaimedFees`.
- Concretely, before `creditVault.requestInstantWithdraw(...)`: `uint256 instantFee = _calculateManagementFee(_underlyings, block.timestamp - latestHarvestBlock + instantWithdrawDelay); creditVault.requestInstantWithdraw(_underlyings - instantFee, msg.sender); pendingWithdrawFees += instantFee;` while still burning NAV by the gross principal via `_withdrawOps`.
- Add a fork test asserting `pendingInstantWithdraws == grossPrincipal - instantFee` and that `feeReceiver`/`owner` balances reflect the fee after `stopEpoch`.

### Proof of Concept

Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantWithdrawSkipsManagementFee() external {
    uint256 amount = 100_000 * ONE_SCALE;
    uint256 mgmtFeeRate = 1_000; // 1%/yr
    _setFeeParams(TL_MULTISIG, 10_000, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(mgmtFeeRate);

    address eve = makeAddr('eve');
    _depositWithUser(eve, amount, true);          // KYC'd AA lender

    _startEpochAndCheckPrices(0);

    // Half the epoch elapses: Eve's principal has accrued management fees
    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);

    // Honest manager stops epoch with APR drop large enough to enable instant withdraw
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    uint256 principal = AAtranche.balanceOf(eve) * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
    uint256 expectedFee = principal * mgmtFeeRate
        * (block.timestamp - cdoEpoch.latestHarvestBlock())
        / FULL_ALLOC / 365 days;

    uint256 feesBefore = cdoEpoch.pendingWithdrawFees();
    vm.prank(eve);
    uint256 requested = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // BUG: instant path took the full principal — no fee charged
    assertEq(cdoEpoch.pendingWithdrawFees(), feesBefore, "no fees tracked for instant withdraw");
    assertEq(requested, principal, "receipt is gross of management fee");

    // After next epoch settles, feeReceiver/owner never receive Eve's accrued fee
    _startEpochAndCheckPrices(1);
    uint256 feeRecvBefore = underlying.balanceOf(TL_MULTISIG);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    // invariant violation: expectedFee never materializes in unclaimedFees payout
}
```
