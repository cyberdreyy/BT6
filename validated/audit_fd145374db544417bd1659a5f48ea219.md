### Title
Unprivileged job can spoof the "protected" cache/volume namespace via a crafted cache key suffix - (executors/docker/volume.go)

### Summary
`createVolumesManager` derives `config.Protected` from either `e.Build.IsProtected()` (server-controlled) or from the presence of any `.gitlab-ci.yml` cache `key` ending in `-protected` (user-controlled), per work item 494478's stated logic. Because `Cache.Key` is a fully attacker-controlled, expanded string field from the job spec, an unprivileged pipeline author on an unprotected branch can set `key: "foo-protected"` in their own `.gitlab-ci.yml` to force `config.Protected = true` for their job, even though `e.Build.IsProtected()` is false.

### Finding Description
`createVolumesManager` computes:
```go
protectedKeyIdx := slices.IndexFunc(e.Build.Cache, func(c spec.Cache) bool {
    return strings.HasSuffix(c.Key, "-protected") && !strings.HasSuffix(c.Key, "-non_protected")
})
...
Protected: e.Build.IsProtected() || protectedKeyIdx >= 0,
``` [1](#0-0) 

`Cache.Key` is defined as `Key string `json:"key" inputs:"expand"`` on the `spec.Cache` struct, part of the job payload built from the pipeline's `.gitlab-ci.yml`, and is subject to variable expansion — fully within the pipeline author's control regardless of branch protection status. [2](#0-1) 

The `Protected` flag is then consumed by `volumes.Manager.withProtected`, which appends the literal suffix `-protected` to cache-volume/host-cache directory names derived from `UniqueName` (project-scoped, not branch-scoped) and a hash of the destination path:
```go
func (m *manager) withProtected(s string) string {
    if !m.config.Protected {
        return s
    }
    return s + protectedSuffix
}
``` [3](#0-2) 

This suffix is used both for host-based cache dirs (`createHostBasedCacheVolume`) and Docker named volumes (`createCacheVolume`), where the volume/dir name is `UniqueName-cache-hash[-protected]`: [4](#0-3) [5](#0-4) 

Since `UniqueName` (`e.Build.ProjectRealUniqueName()`) is per-project rather than per-branch or per-job, the resulting cache path/volume name for a "protected" cache is identical for any job in the same project that also triggers `config.Protected = true` — whether that protection state was legitimately derived from an actual protected ref, or spoofed via the `-protected` key suffix. Nothing in `createVolumesManager` or `withProtected` ties the "protected" volume namespace to the actual ref protection state at the point the volume is created/reused; it only checks the boolean once it's already been (potentially) forged by the attacker's own cache key. This defeats the stated purpose of work item 494478 — namespacing protected-ref caches away from unprotected-ref caches — because an unprotected job can voluntarily "opt into" the protected namespace and thereby read from or write to the same cache volume/directory that legitimate protected-branch jobs use.

### Impact Explanation
An unprivileged contributor pushing to (or opening an MR against) an unprotected branch can craft `.gitlab-ci.yml` with a cache `key` ending in `-protected` to make their job share the exact same cache volume/host directory namespace as jobs run on protected branches for the same project. This allows:
- Reading cache contents that were only ever meant to be populated by trusted, protected-branch jobs (potential secret/config exposure written into cache by CI scripts).
- Writing/poisoning that same cache, so that a subsequent protected-branch job pulls attacker-controlled cache contents — a cache-poisoning path leading to code execution in a protected pipeline context.

This directly violates the invariant that caches must not leak or be cross-contaminated across trust boundaries (protected vs. unprotected refs), which is the explicit security goal referenced by the code comment (work item 494478).

### Likelihood Explanation
- Preconditions: attacker only needs push/MR access sufficient to run a pipeline job on an unprotected branch and control `.gitlab-ci.yml` cache configuration — a very common, low-privilege capability.
- Feasibility: trivial — just set `cache.key: "<anything>-protected"`.
- Repeatability: fully deterministic; same volume/dir name is derived every time from `UniqueName` + hash, so cache sharing/collision with protected jobs is consistent, not probabilistic.

### Recommendation
Do not let user-controlled cache key content influence the `Protected` decision at all, or if the "opt-in protected" behavior is intentional for some other purpose, use a separate namespace that never collides with the one derived from `e.Build.IsProtected()`. Concretely: derive the protected-cache-volume suffix solely from `e.Build.IsProtected()` (or another server-verified signal), and if per-cache-key protection is a desired feature, incorporate a value the user cannot forge into the namespace (e.g., combine both actual-protection state and the user's cache-key protected flag into two distinct suffixes: `-protected` only for `IsProtected()`, and something like `-protected-key` for `protectedKeyIdx>=0` that does not collide with the ref-protected path).

### Proof of Concept
Go unit test targeting `createVolumesManager` (in `executors/docker/volume_test.go`, mirroring existing style):
```go
func TestCreateVolumesManager_UnprotectedJobCanForceProtectedNamespace(t *testing.T) {
    e := &executor{}
    e.Build = &common.Build{
        JobResponse: common.JobResponse{
            GitInfo: common.GitInfo{ /* Protected not set / false */ },
            Cache: common.Caches{
                {Key: "malicious-protected"}, // attacker controlled, unprotected branch
            },
        },
    }
    // ... wire minimal e.Config, e.dockerConn, e.volumeParser mocks as in existing tests

    require.False(t, e.Build.IsProtected(), "branch must be unprotected")

    vm, err := createVolumesManager(e)
    require.NoError(t, err)

    // Assert internal config.Protected became true purely due to the cache key,
    // producing the same volume-name suffix ("-protected") used by real protected-ref jobs
    // for the same project (same UniqueName), i.e. cross-trust-boundary volume collision.
}
```
Assertions: `config.Protected == true` despite `IsProtected() == false`; and that the computed cache volume/host-dir name for a given destination matches (collides with) the name that would be produced when `e.Build.IsProtected() == true` for the same project `UniqueName`/destination — demonstrating the namespace collision between unprotected and protected jobs.

func (m *manager) createHostBasedCacheVolume(destination string) error {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return fmt.Errorf("updating managed volumes list: %w", err)
	}

	// The leaf directory dir has a name with a length of:
	//	- 42 chars when protected
	//	- 32 chars when not protected (the length of the md5sum only)
	dir := m.withProtected(hashPath(destination))
	hostPath := m.parser.Path().Join(m.config.CacheDir, m.config.UniqueName, dir)

	m.appendVolumeBind(&parser.Volume{
		Source:      hostPath,
		Destination: destination,
	})

	return nil
}

func (m *manager) createCacheVolume(
	ctx context.Context,
	destination string,
	reusable bool,
) (string, error) {
	destination, err := m.absolutePath(destination)
	if err != nil {
		return "", fmt.Errorf("defining absolute path: %w", err)
	}

	err = m.managedVolumes.Add(destination)
	if err != nil {
		return "", fmt.Errorf("updating managed volumes list: %w", err)
	}

	hashedDestination := hashPath(destination)
	name := m.config.TemporaryName
	if reusable {
		name = m.config.UniqueName
	}

	// volumeName might get quite long. Docker is however happy to create volumes with long names. There is the "myth"
	// that volume names are treated like DNS labels, and thus only allow a length of 63 chars, however that does not hold
	// true. In fact, we already create way longer names, and would catch those issues in various integration tests.
	volumeName := m.withProtected(fmt.Sprintf("%s-cache-%s", name, hashedDestination))

	vBody := client.VolumeCreateOptions{
		Name:       volumeName,
		Driver:     m.config.Driver,
		DriverOpts: m.config.DriverOpts,
		Labels: m.labeler.Labels(map[string]string{
			"destination": destination,
			"protected":   strconv.FormatBool(m.config.Protected),
			"reusable":    strconv.FormatBool(reusable),
			"type":        "cache",
		}),
	}

	v, err := m.client.VolumeCreate(ctx, vBody)
	if err != nil {
		return "", fmt.Errorf("creating docker volume: %w", err)
	}

	if m.permissionSetter != nil {
		err = m.permissionSetter.Set(ctx, v.Name, m.labeler.Labels(map[string]string{"type": "cache-init"}))
		if err != nil {
			return "", fmt.Errorf("set volume permissions: %w", err)
		}
	}

	m.appendVolumeBind(&parser.Volume{
		Source:      v.Name,
		Destination: destination,
	})
	m.logger.Debugln(fmt.Sprintf("Using volume %q as cache %q...", v.Name, destination))

	return volumeName, nil
}
