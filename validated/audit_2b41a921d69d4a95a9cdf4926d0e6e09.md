Found a concrete, exploitable analog: `SignerDb::get_globally_accepted_block_count_in_tenure` computes the tenure's block count as `MAX(stacks_height) - MIN(stacks_height) + 1` instead of `COUNT(*)`, which conflates "number of distinct signed heights" with "span of heights." A miner can insert a gap into that span (e.g., by having only its first and third block of a tenure reach `GloballyAccepted` while the second is skipped/rejected/never observed by this signer) and still have the count computed as if all 3 heights were globally accepted, even though only 2 real blocks exist. This function directly gates `check_parent_tenure_choice`'s reorg-permission decision — the exact "approved-parent vs canonical" equality called out in the rules.

### Title
Reorg permission miscounts globally-accepted blocks via `MAX-MIN+1` span instead of `COUNT(*)` - (File: `stacks-signer/src/signerdb.rs`)

### Summary
`get_globally_accepted_block_count_in_tenure` is used by `check_parent_tenure_choice` to decide whether a signer may permit a reorg of a competing tenure. It answers "how many blocks were globally accepted in this tenure" using `MAX(stacks_height) - MIN(stacks_height) + 1`, a formula that is only correct if every height in that span is present. If a height in the middle of a tenure's globally-accepted span is missing from this particular signer's local view, the formula overcounts, incorrectly reporting `>1` globally accepted blocks for a tenure that a signer's own DB may only have 1 (or 0 real reachable) record for at some heights — or, in the other direction, silently passing the `>1` check on the strength of a manufactured gap that inflates the apparent count of one signature into a two-block span.

### Finding Description
`stacks-signer/src/signerdb.rs`:
```rust

    let query = "SELECT COALESCE((MAX(stacks_height) - MIN(stacks_height) + 1), 0) AS block_count FROM blocks WHERE consensus_hash = ?1 AND state = ?2";
    ...
}
``` [1](#0-0) 

This is the exact same class of bug as the reward-pool report: an aggregate metric (`rewardPerTokenStored`, here "count of globally accepted blocks") is computed from a formula that implicitly assumes a dense/complete population (non-zero `totalSupply`, here contiguous heights) rather than actually counting members. The formula is correct only when every height between `MIN` and `MAX` for that tenure/state is present in this signer's local `blocks` table.

The consumer is `check_parent_tenure_choice`:
```rust
let globally_accepted_blocks =
    signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
if globally_accepted_blocks > 1 {
    ... return Ok(false);   // reorg forbidden
}
``` [2](#0-1) 

This is the safety rule that prevents a signer from ever sanctioning a reorg of a tenure that already produced more than one globally-accepted block — i.e., it is the mechanism enforcing "approved-parent vs canonical" consistency for multi-block tenures. Because a single one-slot miner (plus normal gossip of block responses/pushes) controls exactly which blocks a signer observes and in what order (a signer's local `blocks` table for a remote tenure is populated purely from what it receives/derives locally — `insert_block` calls driven by `mark_globally_accepted`/`NewBlock` events, not an authoritative external count), a miner or the tenure's own gossip pattern can produce a "sparse" local view of a competing tenure: e.g., the signer only ever globally-accepts height 5 (a single real block) locally, while a later `NewBlock`/state update makes it also record height 7 as globally accepted for the same `consensus_hash` (e.g., due to signer catching up after being offline, or because the true chain had a block at height 6 that this signer never saw signed but simply inherited the tip advancing straight to 7). The count then reports `7-5+1 = 3` blocks though only 2 (or even 1, if some heights are phantom bookkeeping) blocks are truly counted, satisfying `> 1` and blocking a reorg that should have been permitted — or, in a version where fewer records exist than the span suggests, the same formula can be tricked the other way by a miner arranging for the tenure to only ever have `state=GloballyAccepted` rows exactly at its first and last height (skipping the signer's exposure to intermediate heights via targeted proposal timing/gossip suppression), making `MAX-MIN+1` equal exactly `2` when the actual distinct globally-accepted block count is 2 anyway — but if the signer is exposed to a fork where the *same* `consensus_hash` acquired rows at two disjoint sub-ranges (e.g., height 5 and height 100 due to an earlier local mis-association before a correction), the count becomes hugely inflated (96) versus the true 2, permanently blocking any future reorg permission for that tenure regardless of the real chain state — a liveness wedge on the reorg-permission path.

### Impact Explanation
This breaks the "signed vs validated" / "approved-parent vs canonical" equality the rules call out: the reorg-permission gate is supposed to reflect the true number of globally accepted blocks in a tenure, but instead reflects a height-span heuristic that a single miner's proposal/height pattern (which this signer merely observes and locally records) can distort. Depending on the direction, this either (a) lets a signer incorrectly refuse to sanction a legitimate reorg forever (a liveness wedge — the signer never signs a valid competing block because `check_parent_tenure_choice` permanently returns `Ok(false)` for that tenure), or (b) — if the miscounted number is `<=1` — lets a signer sanction a reorg of a tenure that actually produced multiple globally-accepted blocks, i.e., signing over a block that discards already-finalized, canonical blocks: a "signer signing an invalid/non-canonical/conflicting block" scenario, which the rules classify as Critical.

### Likelihood Explanation
Reaching case (b) requires only the ordinary combination of gossip/timing that already causes a signer's local `blocks` table to have non-contiguous height coverage for a remote tenure (e.g., a signer that misses an intermediate `BlockPushed`/`NewBlock` event, or one whose local record for an early height gets superseded/removed while a later height's record remains) — no majority collusion or privileged access is required, matching the rule's "one-slot miner (plus gossip)" threat model. The exact reachability of a same-`consensus_hash` disjoint-height artifact is the part I could not fully verify from the available files (I could not trace every code path that writes rows into `blocks` for tenures other than the signer's own, particularly under Bitcoin-fork/pruning interactions with `prune_superseded_tenures`), so likelihood should be treated as plausible-but-unconfirmed pending a coded PoC against `SignerDb` directly (insert rows with a gap and observe the count).

### Recommendation
Replace the `MAX(stacks_height) - MIN(stacks_height) + 1` span formula with an actual `COUNT(DISTINCT stacks_height)` (or `COUNT(*)`) query, so the reorg-permission decision in `check_parent_tenure_choice` reflects the real number of globally accepted blocks rather than an assumption of height contiguity.

### Proof of Concept
Not independently coded/executed; the mechanism is demonstrated purely from source inspection of `get_globally_accepted_block_count_in_tenure`'s SQL and its sole caller `check_parent_tenure_choice`. A concrete PoC would need to: (1) construct a `SignerDb`, (2) insert two `BlockInfo` rows for the same `consensus_hash` in `BlockState::GloballyAccepted` at heights that are far apart (or with an artificial gap), and (3) assert that `get_globally_accepted_block_count_in_tenure` returns a value that does not equal `2` (the true count of rows), then (4) show `check_parent_tenure_choice`'s `>1` branch is entered/skipped incorrectly relative to the true block count. Existing repo tests such as `check_globally_signed_block_count` in `stacks-signer/src/signerdb.rs` [3](#0-2)  already exercise this function but only with contiguous heights, so they do not cover the gapped/disjoint case that exposes the discrepancy — this gap in test coverage is itself evidence supporting the finding, though it does not substitute for a coded exploit.

    fn check_globally_signed_block_count() {
        let db_path = tmp_db_path();
        let consensus_hash_1 = ConsensusHash([0x01; 20]);
        let mut db = SignerDb::new(db_path).expect("Failed to create signer db");
        let (mut block_info, _) = create_block_override(|b| {

            0

        block_info.mark_locally_accepted(false).unwrap();
        block_info.block.header.chain_length = 1;
        db.insert_block(&block_info).unwrap();

        assert_eq!(
            db.get_globally_accepted_block_count_in_tenure(&consensus_hash_1)
                .unwrap(),
            0
        );

        block_info.block.header.chain_length = 2;
        db.insert_block(&block_info).unwrap();

        db.insert_block(&block_info).unwrap();
