### Title
Unauthenticated workflow existence oracle via distinct "not found" vs "auth failure" error messages - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`HandleUserTriggerRequest` calls `resolveWorkflowID` before `authorizeRequest`, and no signature/JWT verification happens anywhere prior to that point. An unauthenticated caller can therefore probe arbitrary `workflowID` or `(workflowOwner, workflowName, workflowTag)` combinations and distinguish "workflow exists" from "workflow doesn't exist" purely from the returned JSON-RPC error message, without ever presenting a valid `req.Auth` signature.

### Finding Description
`HandleJSONRPCUserMessage` in `core/services/gateway/handlers/capabilities/v2/http_handler.go` forwards every incoming request directly to `h.triggerHandler.HandleUserTriggerRequest(ctx, &req, callback, time.Now())` with no upfront authentication check: [1](#0-0) 

`HandleUserTriggerRequest` then runs, in order: `validatedTriggerRequest` (structural/format validation only), `resolveWorkflowID` (workflow lookup), and only afterward `authorizeRequest` (signature/JWT check): [2](#0-1) 

`resolveWorkflowID` looks up the workflow by ID or by owner/name/tag and, if not found, returns a distinct error message: `"Workflow not found. 'workflowID' %s is not a valid workflow ID"` or `"Workflow not found. Provide either a valid 'workflowID' or a valid combination of..."`: [3](#0-2) 

If the workflow *is* found, execution proceeds to `authorizeRequest`, which verifies `req.Auth` against `workflowMetadataHandler.Authorize` and returns a different message, `"Auth failure: " + err.Error()`, on any signature/authorization problem: [4](#0-3) 

Both error paths funnel through `handleUserError`, which sends the message and a JSON-RPC error code directly back to the (unauthenticated) requester via `callback.SendResponse`: [5](#0-4) 

Because `resolveWorkflowID` runs strictly before `authorizeRequest`, and no signature check happens before it, an attacker can send an unsigned or garbage-`Auth` request (only needing to satisfy the trivial structural checks in `validateWorkflowFields`/`validateHexInput`) and unambiguously learn, per response message, whether a given `workflowID` or `(owner, name, tag)` triple exists on the gateway — this is confirmed by the existing test suite, e.g. `TestHttpTriggerHandler_HandleUserTriggerRequest_JWTAuthorization`'s `"invalid JWT token"` and `"unauthorized signer"` sub-tests both return `jsonrpc.ErrInvalidRequest` with `"auth failure"` only for workflows that already exist and were registered, versus `"workflow not found"` for ones that are not, which are literally distinguishable text and demonstrate the oracle: [6](#0-5) 

This lets an unauthenticated attacker enumerate valid `workflowID` values or `(workflowOwner, workflowName, workflowTag)` combinations belonging to other users, without presenting any valid signature at all.

### Impact Explanation
This is an information-disclosure vulnerability: it discloses the existence and validity of another user's `workflowID` / `workflowOwner`+`name`+`tag` combination to any unauthenticated network caller of the gateway. While it does not directly expose secrets or bypass authorization to execute a workflow (the subsequent `authorizeRequest` signature check still gates actual triggering), it materially aids reconnaissance for targeted attacks: an attacker can enumerate active workflows/owners on the gateway (e.g., by brute-forcing owner addresses, names, and tags) and use the confirmed existing `workflowID` to focus further attacks (e.g., stolen-key replay, social engineering, or JWT forgery attempts) against a specific real target rather than guessing blind. This maps to Chainlink's "Information disclosure of sensitive information" / oracle-based enumeration impact class, generally lower severity than direct auth bypass since it requires no privileged action and yields no direct fund/key compromise by itself.

### Likelihood Explanation
Highly likely and trivially reproducible: the attacker needs no credentials, no valid signature, and no special network position — just the ability to send JSON-RPC `workflows.execute` requests to the public gateway endpoint. The only precondition is producing a syntactically valid request (`workflowID` correctly hex-formatted, or `workflowOwner`/`workflowName`/`workflowTag` correctly formatted) to pass `validateWorkflowFields`/`validateHexInput`, which is trivial and requires no knowledge of secrets. This can be automated at scale to enumerate many candidate identifiers.

### Recommendation
Perform authentication/authorization checks before revealing found/not-found status, or normalize error responses so that "workflow not found" and "auth failure" are indistinguishable to an unauthenticated caller — e.g., always return a generic error code/message (such as a single "authorization failed" response) for both cases pre-authentication, and only reorder so that `authorizeRequest` (or at least signature format/validity verification) happens before, or concurrently with, `resolveWorkflowID`'s existence check. Concretely: move the JWT/signature format validation ahead of `resolveWorkflowID`, and collapse the "workflow not found" and "auth failure" paths into one uniform error message/code returned to the client, with the detailed distinction only available in logs.

### Proof of Concept
Add a table-driven Go test in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler_test.go`:
1. Set up a `httpTriggerHandler` with one workflow registered (`workflowID` A) and one *not* registered (`workflowID` B).
2. For each case, send `HandleUserTriggerRequest` with:
   - No `req.Auth` (or a garbage/unsigned `Auth` string) and `WorkflowSelector{WorkflowID: A}` (exists) — assert the error message returned via `callback.Wait` contains `"Auth failure"`.
   - Same garbage `Auth`, `WorkflowSelector{WorkflowID: B}` (doesn't exist) — assert the error message contains `"Workflow not found"`.
   - Same for owner/name/tag combos, one existing one not.
3. Assert that in both "exists" and "doesn't exist" cases, without ever presenting a valid signature, the returned `jsonrpc.WireError.Message` differs (`"Auth failure..."` vs `"Workflow not found..."`), proving pre-auth existence leakage. A fixed implementation should assert these messages are identical (or otherwise non-distinguishing) for unauthenticated requests.

func (h *httpTriggerHandler) resolveWorkflowID(ctx context.Context, triggerReq *jsonrpc.Request[gateway_common.HTTPTriggerRequest], requestID string, callback handlers.Callback) (string, error) {
	h.lggr.Debugw("resolving workflow ID", "workflowID", triggerReq.Params.Workflow.WorkflowID, "workflowOwner", triggerReq.Params.Workflow.WorkflowOwner, "workflowName", triggerReq.Params.Workflow.WorkflowName, "workflowTag", triggerReq.Params.Workflow.WorkflowTag, "requestID", requestID)
	workflowID := triggerReq.Params.Workflow.WorkflowID
	if workflowID != "" {
		workflowID = normalizeHex(workflowID, workflowIDLength)
		_, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
		if !found {
			h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, fmt.Sprintf("Workflow not found. 'workflowID' %s is not a valid workflow ID", workflowID), callback)
			return "", errors.New("workflow not found")
		}
		return workflowID, nil
	}
	workflowOwner := normalizeHex(triggerReq.Params.Workflow.WorkflowOwner, workflowOwnerLength)
	workflowName := "0x" + hex.EncodeToString([]byte(workflows.HashTruncateName(triggerReq.Params.Workflow.WorkflowName)))
	workflowID, found := h.workflowMetadataHandler.GetWorkflowID(
		workflowOwner,
		workflowName,
		triggerReq.Params.Workflow.WorkflowTag,
	)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. Provide either a valid 'workflowID' or a valid combination of 'workflowOwner', 'workflowName', and 'workflowTag'", callback)
		return "", errors.New("workflow not found")
	}
	return workflowID, nil
}

	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)

	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}

func (h *httpTriggerHandler) handleUserError(ctx context.Context, requestID string, code int64, message string, callback handlers.Callback) {
	switch code {
	case jsonrpc.ErrInternal, jsonrpc.ErrServerOverloaded, jsonrpc.ErrUnknown, jsonrpc.ErrLimitExceeded, jsonrpc.ErrConflict:
		h.lggr.Errorw("returning error to user", "code", code, "message", message, "requestID", requestID)
	default:
		h.lggr.Warnw("returning error to user", "code", code, "message", message, "requestID", requestID)
	}
	resp := &jsonrpc.Response[json.RawMessage]{
		Version: "2.0",
		ID:      requestID,
		Error: &jsonrpc.WireError{
			Code:    code,
			Message: message,
		},
	}
	rawResp, err := json.Marshal(resp)
	if err != nil {
		h.lggr.Errorw("failed to marshal error response", "err", err, "requestID", requestID)
		return
	}
	errorCode := api.FromJSONRPCErrorCode(code)
	h.metrics.IncrementRequestErrors(ctx, code, h.lggr)
	err = callback.SendResponse(handlers.UserCallbackPayload{
		RawResponse: rawResp,
		ErrorCode:   errorCode,
	})
	if err != nil {
		h.lggr.Errorw("failed to send user callback", "err", err, "requestID", requestID)
		return
	}
}
