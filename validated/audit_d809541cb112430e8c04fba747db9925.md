### Title
Unsanitized alternate cache key path traversal via `cacheAlternateKey` when `FF_HASH_CACHE_KEYS` is enabled - (File: shells/abstract.go)

### Summary
When `FF_HASH_CACHE_KEYS` is enabled, `newCacheConfig` deliberately bypasses `cachekey.Sanitize` for the human-readable key on the assumption that only the hashed key is ever used to build filesystem paths. That assumption is false: `cacheAlternateKey` returns the *raw, unsanitized* `humanKey` as the alternate key in that mode, and this raw value is fed straight into `getArchivePath`, which builds a path with `path.Join(build.CacheDir, key, "cache.zip")` without any traversal check.

### Finding Description
`newCacheConfig` (shells/abstract.go:133-208) selects sanitization behavior based on the feature flag: [1](#0-0) 

When `FF_HASH_CACHE_KEYS` is on, `sanitizer` becomes a no-op (`func(s string) (string, error) { return s, nil }`), so `humanKey` is set to the raw, attacker-influenced `rawKey` (derived from `cache.key`/fallback keys/`CACHE_FALLBACK_KEY`, expanded via `ExpandValue`) without ever running `cachekey.Sanitize`, which is the only component that neutralizes `../` sequences by resolving them against a virtual root: [2](#0-1) 

The primary path is safe in hash mode because `hashedKey` is a SHA-256 hex digest of `humanKey`, not the raw string: [3](#0-2) 

However, `cacheAlternateKey` returns the *raw* `humanKey` — not a hashed or sanitized value — as the alternate key whenever hashing is enabled: [4](#0-3) 

This raw alternate key is then passed straight into `getArchivePath`, which builds the path with `path.Join(build.CacheDir, key, "cache.zip")`: [5](#0-4) 

`path.Join` internally calls `path.Clean`, which lexically resolves `../` segments. Because `key` here was never passed through `cachekey.Sanitize` (which is the only place that neutralizes traversal by prepending a virtual root before calling `Clean`), a `cache.key`/`CACHE_FALLBACK_KEY` value such as `../../../../other-project/cache-key` can cause the joined+cleaned path to walk upward past `build.CacheDir` before the `filepath.Rel(build.BuildDir, file)` re-relativization step, yielding an `AlternateArchiveFile` value that no longer resolves under `build.CacheDir`.

The `blockProtectedFallback` check on `CACHE_FALLBACK_KEY` (shells/abstract.go:320-329) only blocks a specific `-protected` suffix and does nothing to validate path-traversal content, so it does not stop this.

### Impact Explanation
`AlternateArchiveFile`/`AlternateKey` exist specifically to interoperate with the "other" naming scheme (upgrade/downgrade between hashed and unhashed cache object layouts). If this value is consumed for any local file operation (the struct explicitly stores it as a file path for that purpose), an attacker-controlled key can point that operation outside the job's own `CacheDir`, toward another project's/job's cache namespace or an arbitrary path reachable from `build.BuildDir`, violating the stated invariant that cache archive paths must remain confined under `build.CacheDir/<project-scoped-key>`. This is a targeted violation of tenant isolation for the cache subsystem — an unprivileged pipeline author only needs to control `cache.key`, a fallback key, or `CACHE_FALLBACK_KEY`, all of which are ordinary job-level CI inputs.

### Likelihood Explanation
Preconditions: `FF_HASH_CACHE_KEYS=true` on the runner/job (a supported, documented feature flag, not an unusual admin misconfiguration), and an unprivileged job author supplying a crafted `cache.key`/fallback key/`CACHE_FALLBACK_KEY` value containing `../` sequences. No special executor privileges or admin-side settings are required beyond enabling the flag, which is intended to become the default in future GitLab Runner versions per the changelog/feature-flag docs. Given the flag is opt-in today but forward-looking, and the crafted-key input path is trivial to control from `.gitlab-ci.yml`, this is realistically reproducible.

### Recommendation
Route the alternate key through the same sanitization boundary as the human key, regardless of `FF_HASH_CACHE_KEYS` state, before it is used to build any filesystem path. Concretely, in `cacheAlternateKey`, when returning the raw/unhashed alternate key, ensure it was already sanitized via `cachekey.Sanitize` (or run it through `Sanitize` again) before it flows into `getArchivePath`; alternatively, restrict `getArchivePath` to reject any key whose cleaned/joined result does not have `build.CacheDir` as a path prefix, and return an error rather than silently returning an escaped path.

### Proof of Concept
Go unit test targeting `newCacheConfig` in shells/abstract.go:

```go
func TestNewCacheConfig_AlternateKeyEscapesCacheDir(t *testing.T) {
    build := &common.Build{
        CacheDir: "/builds/project-42/cache",
        BuildDir: "/builds/project-42",
        // ... minimal JobInfo/GitInfo/Runner setup with
        // FF_HASH_CACHE_KEYS=true via build.Runner.FeatureFlags or JobInfo.Variables
    }

    maliciousKey := "../../../../project-99/secret-cache-key"

    cfg, _, err := newCacheConfig(build, maliciousKey)
    require.NoError(t, err)

    // AlternateArchiveFile must resolve under build.CacheDir once
    // re-joined against build.BuildDir; assert it does not.
    resolved := filepath.Clean(filepath.Join(build.BuildDir, cfg.AlternateArchiveFile))
    assert.True(t, strings.HasPrefix(resolved, build.CacheDir),
        "AlternateArchiveFile escaped CacheDir: %s", resolved)
}
```

Expected (buggy) result: the assertion fails — `resolved` points outside `build.CacheDir` (e.g. into `/builds/project-99/...`), proving the alternate-key path can escape the per-project cache namespace when `FF_HASH_CACHE_KEYS` is enabled. A fuzz test over `userKey` (traversal sequences, absolute paths, mixed encodings) with `FF_HASH_CACHE_KEYS` toggled true/false should additionally confirm the primary `ArchiveFile` stays confined (currently true) while `AlternateArchiveFile` does not (currently false), isolating the bug to `cacheAlternateKey`'s unsanitized raw-key return path.

```go
func cacheAlternateKey(humanKey string, hashEnabled bool) string {
	sha256Key := fmt.Sprintf("%x", sha256.Sum256([]byte(humanKey)))
	if hashEnabled {
		return humanKey
	}
	return sha256Key
}
```

```go
func Sanitize(cacheKey string) (string, error) {
	if cacheKey == "" {
		return "", nil
	}

	// Decode percent-encoded chars and normalise separators, then
	// resolve traversals against a virtual root so ".." can never
	// escape beyond the root.
	cleaned := path.Clean("/" + normaliser.Replace(cacheKey))

	// Strip the leading "/" we added, split into segments, then walk
	// backwards trimming trailing whitespace from the rightmost
	// segments—dropping any that become empty.
	parts := strings.Split(cleaned[1:], "/")
	n := len(parts)
	for n > 0 {
		parts[n-1] = strings.TrimRightFunc(parts[n-1], unicode.IsSpace)
		if parts[n-1] != "" {
			break
		}
		n--
	}
```
