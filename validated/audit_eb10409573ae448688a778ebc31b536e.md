### Title
Instant-withdraw receipts are re-executed at par even when only partially funded — first claimant drains other users' funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` is the analog of the UAF re-execution: a stored withdraw "receipt" (`instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`) is replayed at par against a shared funded pool, even though the funding ledger (`pendingInstantWithdraws`) is tracked independently and is never consulted at claim time. When instant requests are only partially funded via `collectInstantWithdrawFunds`, the first claimant is paid the full aggregate receipt, consuming backing that belongs to other users' receipts — leaving them permanently unpayable.

### Finding Description
- At request time, `requestInstantWithdraw` mints receipt tokens and increments three ledgers: the per-user aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]`, and the global unfunded counter `pendingInstantWithdraws` (lines 356-375). [1](#0-0) 
- At funding time, `collectInstantWithdrawFunds` decrements only `pendingInstantWithdraws` and pulls that amount of underlying from the CDO into the strategy (lines 398-403). The user's receipt balance is untouched — funding status is per-global-bucket, not per-receipt. [2](#0-1) 
- At claim time, `claimInstantWithdrawRequest` burns and pays the *entire* `instantWithdrawsRequests[_user]` at par through `_transferFundedClaim`, with no check that this user's requests were actually funded (lines 380-393). [3](#0-2) 

The broken invariant is "one receipt, one funded payout": the receipt references underlying that was "freed" (never collected / collected for a different epoch's requests) yet is still re-executed — precisely the dangling-reference pattern of the reported bug class. The default-recovery path (`_claimDefaultedInstantWithdrawRequest`, lines 842-856) already acknowledges that per-epoch instant receipts can be partially funded, but that decomposition only exists after `defaultInstantWithdrawsFinalized`; before any default the aggregate claim path pays par regardless of `pendingInstantWithdraws`. [4](#0-3) 

### Impact Explanation
Direct theft + insolvency: with two users holding instant receipts and the CDO/manager having funded only part of the queue (partial `collectInstantWithdrawFunds`, e.g. limited liquidity returned by the borrower at `startEpoch`), the first `claimInstantWithdrawRequest` call pays user1's full receipt from the strategy's underlying balance, which includes backing earmarked for user2's receipt. User2's subsequent claim either reverts on insufficient balance or must wait for new borrower funds — a permanent freeze if no further funding arrives. Quantified loss: up to `pendingInstantWithdraws` (the unfunded remainder) is overpaid to early claimants; equivalently, later claimants lose the same amount. Caveat: I could not read `IdleCDOEpochVariant.claimInstantWithdrawRequest`'s caller-side gating or the body of `_transferFundedClaim` in this session; the finding stands if, as the code structure suggests, the CDO gates only on `instantDelay` elapsed and the strategy balance sufficing rather than on full per-user funding.

### Likelihood Explanation
Requires: instant-withdraw mode enabled on the vault, an epoch in which the CDO collects only part of `pendingInstantWithdraws` (partial borrower repayment / insufficient available liquidity — a normal running-mode condition, not a default), and an unprivileged KYC'd lender racing to claim first. No privileged misbehavior needed; the overpayment is mechanical once partial funding exists. Likelihood is moderate: it needs the partial-funding window plus a claim ordering race, but no price manipulation or admin error.

### Recommendation
Make the claim path funding-aware, mirroring the default-recovery decomposition:
- Track funded vs. unfunded instant receipts per epoch (or per user), and in `claimInstantWithdrawRequest` cap the payout at the funded portion of `_user`'s receipts rather than the raw `instantWithdrawsRequests[_user]` aggregate.
- Alternatively, revert the claim while the caller's receipt epoch still has `instantWithdrawClaimsByEpoch[epoch] > collectedForEpoch`, or decrement the user's receipt as it is funded so claims are intrinsically bounded.
- Preserve the post-default haircuit path unchanged.

### Proof of Concept
Foundry fork sketch (mode: instant withdraws enabled, running epoch):

```solidity
// Setup: vault with AA tranche, users A and B KYC'd; instantDelay elapsed after startEpoch.
uint256 amt = 100e6;

// Epoch N running: A and B each request instant withdraw of 100e6.
cdoEpoch.requestInstantWithdraw(trancheBalA, AAtranche); // as A
cdoEpoch.requestInstantWithdraw(trancheBalB, AAtranche); // as B
assertEq(strategy.pendingInstantWithdraws(), 2 * amt);

// CDO collects only A's share (partial borrower repayment at startEpoch).
// Internally: strategy.collectInstantWithdrawFunds(amt) -> pendingInstantWithdraws = amt.
// strategy underlying balance now = amt (should back A OR B, not both).

// A claims: burns receipt of amt, paid amt at par. OK so far.
cdoEpoch.claimInstantWithdrawRequest(); // as A

// B claims: instantWithdrawsRequests[B] == amt, paid at par from strategy,
// but strategy holds only (amt - amt) = 0 for B. Either:
//  a) claim reverts -> B permanently frozen while pendingInstantWithdraws>0, or
//  b) if any other funded withdraw deposits sit in the strategy, B steals them.
vm.prank(B_cdo);
strategy.claimInstantWithdrawRequest(B); // overdraws shared funded pool
```

The assertion to encode: total underlying paid out by `claimInstantWithdrawRequest` must never exceed `(totalRequested − pendingInstantWithdraws)` plus explicitly reserved balances; today the aggregate per-user payout ignores `pendingInstantWithdraws`, so the funded pool can be overdrawn by up to the unfunded remainder.

```text
  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
