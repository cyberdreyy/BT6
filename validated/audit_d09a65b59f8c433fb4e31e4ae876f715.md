## Finding

### Title
Signer fails open (signs a conflicting own-tenure block) when `get_tenure_tip` errors during the pre-commit conflict guard - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
In `Signer::handle_block_pre_commit`, the guard that prevents a signer from placing a second signature on a *conflicting* block within the same tenure at the same/higher height queries the node for that tenure's canonical tip via `stacks_client.get_tenure_tip(...)`. When that RPC call succeeds, the tip height is compared against the proposed block's height to decide whether to refuse. But when the call *errors*, the code logs a warning and falls through as if the tenure were simply "unconfirmed" — i.e., it treats an RPC failure the same as "the tip has not reached this height yet," and proceeds to sign. Every other ambiguity branch in the same conflict-resolution logic (the freshness/liveness questions a few lines earlier, per `docs/signer-flows.md` section 5) explicitly resolves "could not ask" to *hold/refuse*, not to sign. Only this one branch fails open.

### Finding Description
The relevant code: [1](#0-0) 

```rust
if conflicts.iter().any(|conflict| {
    conflict.consensus_hash == block_info.block.header.consensus_hash
        && !self.reorg_permit_stands(stacks_client, conflict)
}) {
    match stacks_client.get_tenure_tip(&block_info.block.header.consensus_hash) {
        Ok(tip) => {
            let tip_height = tip.anchored_header.height();
            if tip_height >= block_info.block.header.chain_length {
                // refuse to sign
                return;
            }
        }
        Err(e) => {
            warn!("... Treating the tenure as unconfirmed.");
            // falls through — no `return` here
        }
    }
}
// ... proceeds to mark_locally_accepted / sign
```

This branch only fires when: (a) the signer already has a *stale* conflicting signature at ≥ this height in the *same* tenure (the "own-tenure conflict" reorg-recovery case documented in `docs/signer-flows.md`, section 5, `OWN` branch), and (b) no reorg permit covers it. In that state, `get_tenure_tip` is the only remaining oracle that tells the signer whether the node has already built past this height in this tenure (which would make the new proposal a duplicate/conflicting block the node has already superseded). If that RPC call fails for any reason (timeout, node busy, transient error), the code does not `return` — it silently continues to the sign path, producing a second signature over a conflicting block in the same tenure that the "DuplicateBlockFound"/one-per-tenure invariant was designed to prevent (see `docs/signer-flows.md` lines 425-437, which documents that the duplicate check "never runs again" after proposal time and that this own-tenure conflict guard is the *only* remaining backstop).

By contrast, the sibling questions in the same flow (`get_sortition_by_burn_hash`, `get_tenure_tip` for the *other*-tenure conflict path) explicitly resolve "could not ask" to the hold/refuse branch: [2](#0-1) 

This shows the intended fail-closed design pattern that the own-tenure branch above violates.

### Impact Explanation
This breaks the "one signed block per height per tenure" equality that the signer is supposed to enforce as the last backstop against duplicate/conflicting signatures (Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block"). If the signer's own local validation call happens to fail exactly when it is re-evaluating a stale own-tenure conflict at pre-commit threshold, it will sign a second, conflicting block in the same tenure — undermining consensus safety guarantees that rely on each signer never double-signing within a tenure once its earlier signature is genuinely still canonical.

### Likelihood Explanation
The trigger requires (1) a legitimate stale own-tenure conflict scenario — which does arise naturally from the documented reorg-recovery flow (a miner re-proposing a tenure-start block after a timeout) — combined with (2) a transient failure of the signer's RPC call to its own node (`get_tenure_tip`). Condition (1) is reachable by a single miner simply re-proposing a block after a signature timeout, a normal and expected occurrence per the documented flow. Condition (2) depends on node/RPC reliability rather than direct attacker control, which lowers the likelihood versus a fully attacker-controlled trigger, but does not require a majority of signers, another signer's key, or local access — only ordinary network/RPC flakiness coincident with a miner's legitimate re-proposal.

### Recommendation
Change the `Err(e)` branch in the own-tenure conflict check to refuse signing (`return`) rather than falling through, matching the fail-closed behavior used elsewhere in this same function for `SORT`/`LIVE` "could not ask" cases. An RPC failure should never be treated as evidence the block is safe to sign.

### Proof of Concept
1. Miner proposes tenure-start block A; signer validates and signs A (`LocallyAccepted`).
2. A's signature times out (per `tenure_last_block_proposal_timeout`) without the node ever building past A's height in that tenure.
3. Miner re-proposes a conflicting block B at the same height in the same tenure; signer pre-commits B, and pre-commits cross the 70% threshold, entering `handle_block_pre_commit`.
4. `get_signed_conflicts` returns A as a stale own-tenure conflict; the code calls `stacks_client.get_tenure_tip(consensus_hash)` to check whether the node's tenure tip already reached A's/B's height.
5. If this RPC call errors (e.g., due to a transient node hiccup), the `Err(e)` branch is taken with no `return`, and the signer proceeds to `mark_locally_accepted` and sign B — producing two signed, conflicting blocks (A and B) at the same height in the same tenure from a single signer.
