### Title
Instant-withdraw receipts from pre-default epochs escape the recovery haircut and are paid at par, permanently skewing `pendingInstantWithdraws` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records instant-withdraw receipt basis per request epoch (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`), but default finalization only includes the **current** epoch's instant bucket in the recovery basis via `defaultPendingClaimBasis()` (`instantWithdrawClaimsByEpoch[epochNumber]`). If an instant-withdraw request is made in epoch N, is only partially funded, and the pool then rolls into epoch N+1 where the borrower defaults, the stale-epoch receipt is neither haircutted at finalization nor cleared by `_claimDefaultedInstantWithdrawRequest` (which only touches `defaultRecoveryEpoch` entries). It is paid at par through the funded path, and its basis is never removed from `pendingInstantWithdraws`, corrupting recovery accounting for all other claimants.

### Finding Description
When `requestInstantWithdraw` is called, the receipt is recorded under `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws += _amount` (lines 366–374). Funding is pulled lazily by `collectInstantWithdrawFunds`, so `pendingInstantWithdraws` can remain non-zero across a `stopEpoch`/`startEpoch` boundary, after which `epochNumber` increments while the claim stays under the old epoch key.

On `finalizeDefaultRecovery`, `defaultPendingClaimBasis()` computes:

```solidity
basis = pendingWithdraws;
if (pendingInstantWithdraws != 0) {
  basis += instantWithdrawClaimsByEpoch[epochNumber]; // current epoch only
}
```

The `prefundedReserve` from `_defaultPrefundedInstantReserve()` likewise uses `instantWithdrawClaimsByEpoch[epochNumber]`. So an under-funded instant receipt from epoch N defaults in epoch N+1 with:

1. Its basis excluded from `totalBasis` → `recoveryPrice = reserveAmount / totalBasis` is computed on a smaller denominator than the true claim set.
2. `_claimDefaultedInstantWithdrawRequest` uses `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — returns 0 for the stale-epoch claimant, so no haircut and no decrement of `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`.
3. Execution falls through in `claimInstantWithdrawRequest` to `amount = instantWithdrawsRequests[_user]; _burn(...); _transferFundedClaim(...)`, paying the full amount at par from strategy-held underlying (the reserve guard in `_transferFundedClaim` passes because the prefunded portion of the stale claim was never added to `defaultRecoveryReserve`).

Two concrete harms:

- **At-par overpayment**: the stale-epoch claimant receives 100% while identical current-epoch instant claimants and normal pending redeemers receive `recoveryPrice` cents on the dollar — a direct transfer of value from the recovery pool.
- **Permanent accounting corruption**: `pendingInstantWithdraws` is never decremented for the stale claim (the at-par path doesn't touch it, and the defaulted path only subtracts `defaultEpoch` claims). The inflated `pendingInstantWithdraws` permanently overstates unfunded instant liabilities, polluting `defaultPendingClaimBasis` views and any subsequent loss/funding computations (`previewLossAdjustedWithdrawFunds` interactions aside, `pendingInstantWithdraws` gating in `_defaultPrefundedInstantReserve` and `defaultInstantWithdrawsFinalized` persists wrongly).

### Impact Explanation
An unprivileged attacker (any KYC-passing lender / tranche holder) requests an instant withdrawal late in epoch N such that it is only partially funded before the epoch rolls. After default in a later epoch, the attacker claims at par while all same-class claimants are haircutted. Loss is quantified as `staleClaimBasis * (RECOVERY_FULL - defaultRecoveryPrice) / RECOVERY_FULL` — e.g., a 100k USDC stale instant receipt at a 70% recovery price extracts an extra ~30k USDC that economically belongs to other claimants. Additionally `pendingInstantWithdraws` retains a permanently inflated, unclaimable remainder.

### Likelihood Explanation
Requires: instant withdrawals enabled (`setInstantWithdrawParams`), an instant request that remains partially unfunded across an epoch boundary, and a subsequent borrower default. All steps use only honest privileged actors (manager start/stop, borrower default) sequenced around one attacker transaction. No reentrancy, malicious roles, or oracle dependence. The gap is structural: `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` are keyed strictly to `epochNumber`/`defaultRecoveryEpoch`, while unfunded instant claims can legitimately span epochs.

### Recommendation
Make default handling epoch-agnostic for instant receipts:

- In `defaultPendingClaimBasis()` / `_defaultPrefundedInstantReserve()`, aggregate `instantWithdrawClaimsByEpoch` over all epochs with outstanding basis (or maintain a global `totalInstantClaims` counter alongside `pendingInstantWithdraws`) instead of indexing only `epochNumber`.
- In `_claimDefaultedInstantWithdrawRequest`, clear the user's **entire** `instantWithdrawsRequests[_user]` balance at `defaultRecoveryPrice` when `defaultInstantWithdrawsFinalized` is true, zeroing all per-epoch entries and decrementing `pendingInstantWithdraws` by the full claim; or iterate per-epoch entries ≤ `defaultRecoveryEpoch`.
- Ensure every path that pays or clears an instant claim decrements `pendingInstantWithdraws` so no phantom remainder survives.

### Proof of Concept
```solidity
// Foundry fork PoC (schematic; mirrors test/foundry/IdleCreditVault.t.sol helpers)
function testStaleEpochInstantClaimEscapesHaircut() external {
    // Setup: instant withdrawals enabled, user deposits AA in epoch N buffer.
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(instantDelay, minAprDiff, false);
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);

    // Attacker requests instant withdraw in epoch N.
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(ATTACKER_TRANCHES, address(AAtranche));

    // Epoch stops; only PART of the instant claim is funded
    // (collectInstantWithdrawFunds pulls less than pendingInstantWithdraws).
    _stopCurrentEpoch();               // epochNumber -> N+1
    // ... partial funding leaves pendingInstantWithdraws > 0 ...
    _startEpochAndCheckPrices(1);      // stale claim still keyed to epoch N

    // Borrower defaults in epoch N+1; manager finalizes at 70% recovery.
    _checkDefault();
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);   // ~0.7e18 recovery price
    vm.stopPrank();

    // Attacker claims: defaulted path misses epoch-N key, falls to funded path -> par payout.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // Attacker was paid 100% while defaultRecoveryPrice ~ 70%.
    assertEq(paid, attackerClaimBasis, "stale instant claim paid at par, not haircut");
    // And pendingInstantWithdraws still counts the settled claim.
    assertGt(strategy.pendingInstantWithdraws(), 0, "phantom pending instant remainder");
}
```
