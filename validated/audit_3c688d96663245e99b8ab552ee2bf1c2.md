### Title
Bridge `OutgoingToken` credential disclosed to view-role users via unguarded `GET /v2/bridge_types/:BridgeName` - ([File: core/web/router.go])

### Summary
The route `authv2.GET("/bridge_types/:BridgeName", bt.Show)` is registered with no role wrapper, unlike the sibling `Create`/`Update`/`Destroy` routes which use `auth.RequiresEditRole`. Any authenticated user — including the lowest-privilege `view` role — can call `Show` and receive the bridge's `OutgoingToken` in the JSON response.

### Finding Description
In `v2Routes` (core/web/router.go), the bridge routes are: [1](#0-0) . `GET /bridge_types/:BridgeName` has no `auth.Requires*Role` wrapper, so it is reachable by any of `UserRoleView`, `UserRoleRun`, `UserRoleEdit`, `UserRoleAdmin` as long as authentication succeeds via session or API token, per the auth methods on the group: [2](#0-1) .

`BridgeTypesController.Show` loads the bridge and serializes it via `presenters.NewBridgeResource(bt)` with no role-based filtering: [3](#0-2) .

`BridgeResource` includes `OutgoingToken` as a normal (non-omitempty) JSON field, always populated from the stored `BridgeType.OutgoingToken`: [4](#0-3) . This is confirmed by the presenter test, which shows `outgoingToken` always present in serialized JSON: [5](#0-4) .

The `OutgoingToken` is a real credential: it is generated as a 24-byte secret at bridge creation time (`utils.NewSecret(24)`) and is stored in plaintext (unlike `IncomingToken`, which is hashed) specifically so it can be used to authenticate callbacks/webhooks from the external adapter back to the node: [6](#0-5) . Knowledge of `OutgoingToken` allows an attacker to forge authenticated resumption/callback requests to the bridge's associated pipeline (e.g., via `/v2/resume/:runID`, an unauthenticated endpoint that likely validates against this secret), effectively enabling unauthorized pipeline-run manipulation.

By contrast, `Index` (list) also returns the same unguarded field to any role, and `Create`/`Update`/`Destroy` are correctly gated by `auth.RequiresEditRole`, showing the missing gate on `Show`/`Index` GET routes is inconsistent with the intended security posture (an under-gating pattern, matching the DKG recipient keys route which is also registered without a role check, though that route only exposes public key material rather than a secret token): [7](#0-6)  and [8](#0-7) .

Regarding the other part of the question — `GET /v2/jobs/:ID/runs` and job spec errors — the only job-spec-error route exposed is `DELETE /pipeline/job_spec_errors/:ID`, gated by `auth.RequiresEditRole`; there is no GET endpoint for spec errors independent of the job show endpoint that leaks bridge tokens: [9](#0-8) . I could not locate evidence that `jc.Show` (`/jobs/:ID`) embeds bridge credentials in its response; that would require inspecting the job presenter, which was not conclusively found to include bridge tokens. So the confirmed, exploitable disclosure is specifically via `bridge_types` GET routes, not the jobs/spec-errors routes.

### Impact Explanation
A `view`-role (read-only) authenticated user, or a restricted API token intended only for read access, can retrieve the plaintext `OutgoingToken` for any bridge on the node by calling `GET /v2/bridge_types/:BridgeName` or `GET /v2/bridge_types` (paginated Index). This token is meant to authenticate the node's own outbound bridge task callbacks; leaking it to a low-privilege user breaks secret confinement, matches Chainlink's "key/secret disclosure" bounty impact class, and can enable forging bridge-related requests that the node trusts.

### Likelihood Explanation
Preconditions are minimal: any valid authenticated session or API token with `view` role is sufficient (the lowest privilege tier in the node). No additional exploitation complexity — a single unauthenticated-role-gated GET request against a known or enumerable bridge name discloses the secret. This is trivially repeatable and requires no race conditions or timing.

### Recommendation
Add `auth.RequiresEditRole` (or a dedicated `RequiresAdminRole`) wrapper to `authv2.GET("/bridge_types", ...)` and `authv2.GET("/bridge_types/:BridgeName", bt.Show)`, matching the write-route gating. Alternatively, keep the routes accessible to all roles but strip/redact `OutgoingToken` from `presenters.NewBridgeResource` for callers below `edit`/`admin` role, mirroring how `IncomingToken` is only injected on `Create` and never persisted/returned on subsequent `Show`/`Index` calls.

### Proof of Concept
Go handler-level integration test plan (extends `core/web/bridge_types_controller_test.go`):
1. Start app via `cltest.NewApplication`, create a bridge with `app.BridgeORM().CreateBridgeType(ctx, bt)` where `bt.OutgoingToken` is set to a known value.
2. Create a user/session with `clsessions.UserRoleView` (see helpers used in other role-gating tests, e.g. `cltest.MustGenerateSession` or similar with `Role: view`).
3. Issue `GET /v2/bridge_types/{bt.Name}` using the view-role session/token.
4. Assert `resp.StatusCode == http.StatusOK` and parse the JSON:API response into `presenters.BridgeResource`.
5. **Expected (secure) assertion**: `resource.OutgoingToken == ""` or request returns `401/403` for view role.
6. **Current (vulnerable) behavior**: `resource.OutgoingToken == bt.OutgoingToken` (the real secret), and status is `200 OK`, demonstrating the disclosure.
7. Repeat for `GET /v2/bridge_types` (Index, paginated) to confirm the same leak across the list endpoint.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

type BridgeType struct {
	Name                   BridgeName
	URL                    models.WebURL
	Confirmations          uint32
	IncomingTokenHash      string
	Salt                   string
	OutgoingToken          string
	MinimumContractPayment *assets.Link
	CreatedAt              time.Time
	UpdatedAt              time.Time
	UseConnectionManager   bool `json:"useConnectionManager"`
}

// NewBridgeType returns a bridge type authentication (with plaintext
// password) and a bridge type (with hashed password, for persisting)
func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error,
) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)
	salt := utils.NewSecret(24)

	hash, err := incomingTokenHash(incomingToken, salt)
	if err != nil {
		return nil, nil, err
	}

	return &BridgeTypeAuthentication{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingToken:          incomingToken,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, &BridgeType{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingTokenHash:      hash,
		Salt:                   salt,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, nil
}
