### Title
APR=0 withdrawal receipts are unfunded and can steal other users’ funded claims - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

Normal withdrawal requests add their full claim amount to `pendingWithdraws`, causing the borrower to fund both principal and interest at epoch stop. APR=0 requests instead call `_requestWithdrawApr0`, which records the principal only in `apr0Users` and `apr0TotalPrincipal`, without adding it to `pendingWithdraws`. `prepareStopEpochWithApr0` later adds only realized APR0 interest to `pendingWithdraws`; the principal remains unfunded.

When the user later claims, `_claimFundedWithdrawRequest` burns the APR0 receipt and pays principal plus settled interest through `_transferFundedClaim`. That function pays from the strategy’s aggregate underlying balance and does not verify that the caller’s principal was actually funded. An attacker can therefore consume cash reserved for older funded withdrawal receipts.

### Finding Description

For a normal request, `requestWithdraw` mints the user a strategy-token receipt and increases `pendingWithdraws`, which represents borrower cash that must be collected at epoch stop. [1](#0-0) 

In the APR=0 branch, the request does not increase `pendingWithdraws`; it records the request only in `_requestWithdrawApr0`. [2](#0-1)  `_requestWithdrawApr0` adds the amount to `apr0Users` and `apr0TotalPrincipal`, but not to the borrower-funded withdrawal liability. [3](#0-2) 

At stop, `prepareStopEpochWithApr0` adds `_apr0NetInterest` to `pendingWithdraws`, but never adds the APR0 principal bucket. [4](#0-3)  Consequently, `IdleCDOEpochVariant._stopEpoch` pulls only the funded normal-withdrawal amount plus interest, while the APR0 principal remains with the borrower. [5](#0-4) 

The claim path nevertheless treats APR0 principal as funded cash: it includes `apr0User.principal` in the payout and transfers it from the strategy’s aggregate balance. [6](#0-5)  `_transferFundedClaim` only protects `defaultRecoveryReserve`; it does not reserve or attribute normal funded withdrawal cash to its original claimant. [7](#0-6) 

### Impact Explanation

An unprivileged KYC-approved lender can create an unfunded APR0 receipt and, after its request epoch finishes, claim principal from cash collected for another user’s matured withdrawal request.

For example:

1. Victim makes a normal withdrawal request of 10,000 underlying.
2. The epoch stops and the borrower funds the 10,000 receipt to the strategy.
3. The next epoch uses APR=0.
4. Attacker requests withdrawal of 9,000 underlying. The request does not increase `pendingWithdraws`.
5. The following epoch stops without collecting the attacker’s 9,000 principal.
6. Attacker claims 9,000 anyway, draining most of the victim’s funded 10,000 reserve.
7. Victim’s claim reverts or is underpaid by the stolen amount.

This breaks the “one receipt, one payout” invariant and creates reserve insolvency. The attacker’s profit is capped by the lesser of their APR0 receipt principal and the strategy’s unrelated funded cash, but can be repeated across epochs while APR=0 and funded reserves coexist.

### Likelihood Explanation

Likelihood depends on the vault operating in APR=0 mode. No privileged malicious behavior is required: the attacker is only an allowed lender making a normal withdrawal request. The attack becomes exploitable whenever APR is zero and the strategy contains funded cash for another receipt, such as a previously funded normal withdrawal that has not yet been claimed.

The absence of a principal component in APR0 `pendingWithdraws` is systematic rather than a rounding edge case. Existing guards do not prevent it because `requestWithdraw`, `prepareStopEpochWithApr0`, and the funded-claim path each update different accounting buckets without checking that APR0 principal was collected.

### Recommendation

Include APR0 principal in the borrower-funded withdrawal liability when the request is created, or when `prepareStopEpochWithApr0` closes the epoch bucket. For example, the APR0 branch in `requestWithdraw` should account for the request principal in `pendingWithdraws`, while `prepareStopEpochWithApr0` should add only the incremental realized interest.

Additionally, track funded withdrawal reserves separately by user or epoch so `_transferFundedClaim` cannot use one claimant’s funded balance to pay an unfunded receipt. Add regression coverage asserting that:

- an APR0 request increases the borrower’s `pendingWithdraws` liability by its principal;
- a successful stop funds principal plus settled APR0 interest;
- an APR0 claimant cannot spend another user’s previously funded withdrawal reserve.

### Proof of Concept

The following Foundry test can be added to `test/foundry/IdleCreditVault.t.sol`, which already provides the deployment variables and helpers used below.

```solidity
function testApr0ReceiptStealsFundedWithdrawReserve() external {
    address victim = makeAddr("victim");
    address attacker = makeAddr("attacker");

    uint256 victimDeposit = 10_000 * ONE_SCALE;
    uint256 attackerDeposit = 9_000 * ONE_SCALE;

    // Both users hold AA shares while APR is non-zero.
    _depositWithUser(victim, victimDeposit, true);
    _depositWithUser(attacker, attackerDeposit, true);

    // Victim creates a normal funded withdrawal receipt.
    vm.prank(victim);
    uint256 victimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);

    // This funds the victim's normal receipt and sets the next unscaled APR to 0.
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    // Attacker creates an APR0 request. Its principal is not added to pendingWithdraws.
    vm.prank(attacker);
    uint256 attackerBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Run the APR0 epoch. No principal is collected for the attacker's receipt.
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    uint256 attackerBefore = underlying.balanceOf(attacker);
    uint256 strategyBefore = underlying.balanceOf(address(strategy));

    // The unfunded APR0 receipt consumes cash reserved for the victim's funded claim.
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    assertEq(underlying.balanceOf(attacker) - attackerBefore, attackerBasis);
    assertEq(strategyBefore - underlying.balanceOf(address(strategy)), attackerBasis);
    assertLt(underlying.balanceOf(address(strategy)), victimBasis);

    // The victim's previously funded receipt is now under-collateralized.
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest();
}
```
