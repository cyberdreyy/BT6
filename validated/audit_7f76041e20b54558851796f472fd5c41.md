### Title
Partial-batch failure lets a staking pool be created, funded, and deployed while the factory believes creation failed and refunds the deposit - (File: staking-pool-factory/src/lib.rs)

### Summary
`create_staking_pool` schedules a single batched promise (`create_account` → `transfer` → `deploy_contract` → `function_call("new", …)`) followed by a callback `on_staking_pool_create` that decides success/failure using `is_promise_success()`. That helper only inspects `env::promise_result(0)`, i.e. the outcome of the **last** action in the chain (the `function_call` to `new`), not the earlier actions. If the batch fails at the `function_call` step (e.g. by supplying just enough gas for `create_account`/`transfer`/`deploy_contract` to succeed but too little for `new()` to finish), the account is nevertheless created, funded with the full attached deposit, and has the staking-pool code deployed - yet the callback treats the whole thing as "nothing happened," removes the id from `staking_pool_account_ids`, and refunds the same deposit a second time to the caller.

### Finding Description
The binding claimed by the invariant is: `attacker_balance_after == attacker_balance_before - gas_costs` whenever `is_promise_success() == false` in `on_staking_pool_create` (i.e., a failed creation must leave no NEAR and no state behind). The code path: [1](#0-0) 

builds one promise with four chained actions and attaches the callback via `.then(...)`. The callback: [2](#0-1) 

relies on `is_promise_success()`: [3](#0-2) 

which only reads `promise_result(0)` - the result of the final action (`function_call("new", …)`) in the batch. Actions within a single NEAR receipt are not atomic across each other: `create_account`, `transfer`, and `deploy_contract` commit their effects even if a later action in the same receipt (the `function_call`) subsequently fails (e.g., due to insufficient `gas::STAKING_POOL_NEW`, or any panic inside `new()`). When this happens:

- The target account `staking_pool_id.factory_account` is created and holds the full `MIN_ATTACHED_BALANCE`+ deposit.
- The staking-pool wasm is deployed to it.
- `new()` never completed, so the contract has no initialized state.
- `is_promise_success()` returns `false`, so the factory removes the id from `staking_pool_account_ids` and refunds the entire `attached_deposit` back to `predecessor_account_id`.

The result: the attacker gets their deposit back in full, while an identical amount of NEAR is simultaneously sitting on the newly created (deployed but uninitialized) account, untracked by the factory and unlisted on the whitelist. The factory's bookkeeping (`staking_pool_account_ids`, and by extension anyone relying on `get_number_of_staking_pools_created` / the whitelist) diverges from the true on-chain state - a pool exists and holds funds that the factory has "forgotten." None of the existing guards catch this: `assert_self()` only checks the caller of the callback is the contract itself; `is_promise_success()` is exactly the mechanism at fault since it inspects only the last action's result; the synchronous `assert!(self.staking_pool_account_ids.insert(&staking_pool_account_id), ...)` in `create_staking_pool` only prevents re-using an id that is *currently* tracked, and by the time of the exploit the id has already been evicted from the set by the callback, so a second call is free to re-insert it.

### Impact Explanation
NEAR ends up permanently sitting on an account that is deployed but never initialized, while the factory has already "settled" the matter by refunding the deposit and dropping the id from its tracked set - so the on-chain NEAR balance diverges from the factory's own accounting of "how much was created / how many pools exist." Depending on whether the deployed-but-uninitialized `new()` entrypoint on the orphaned pool account can later be invoked by any caller (it is a public, non-self-restricted init function typical of `near_bindgen` contracts), a third party could subsequently call `new()` on the orphaned, already-funded account and become its owner, walking away with the leftover balance that was never theirs - this would escalate the impact to funds leaving the account to a party never entitled to them. At minimum, this is a High-severity accounting divergence: value that the factory's tracked set says doesn't exist is nonetheless real NEAR resting on a named account, and the deposit was already refunded to the original caller, so no other party can be made whole from factory logic alone.

### Likelihood Explanation
The precondition is fully within the unprivileged attacker's control: they choose `staking_pool_id`, the attached deposit (must satisfy `MIN_ATTACHED_BALANCE`), and critically the **attached gas** for the transaction, which determines how much of `gas::STAKING_POOL_NEW` is available to the batched `function_call("new", …)`. By under-provisioning gas (or by crafting `stake_public_key`/`reward_fee_fraction` values that pass the factory's own validation but still cause `new()` to fail on the staking-pool side, if any such path exists), the attacker can reliably force the batch to fail only at the final action while the earlier `create_account`/`transfer`/`deploy_contract` actions still commit. This requires no privileged role, no victim key, and is repeatable across arbitrarily many `staking_pool_id` values, each attempt costing only gas since the attached NEAR deposit is refunded to the attacker every time.

### Recommendation
Do not rely solely on the result of the last chained action to decide whether "nothing happened." Either (a) split account creation into a separate, self-contained promise from the `deploy_contract`/`function_call("new", …)` step so that a failure of `new()` can be cleanly followed by a `Promise::new(staking_pool_account_id).transfer(...)` recovery of the stranded balance instead of assuming no funds moved, or (b) keep the id in `staking_pool_account_ids` (or a separate "orphaned" set) whenever `create_account` is known/likely to have succeeded, and add a maintenance/admin (or automatic) path to detect and sweep such orphaned, already-funded, uninitialized accounts back to the depositor rather than blindly refunding the same amount again from the factory's own balance while leaving the duplicate on the new account untouched.

```
// staking-pool-factory/src/lib.rs tests module
#[test]
fn test_partial_batch_failure_leaves_funds_behind() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = StakingPoolFactory::new(account_whitelist());

    context.predecessor_account_id = account_tokens_owner();
    context.attached_deposit = ntoy(31);
    testing_env!(context.clone());
    contract.create_staking_pool(
        staking_pool_id(),
        account_pool_owner(),
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".try_into().unwrap(),
        RewardFeeFraction { numerator: 10, denominator: 100 },
    );

    // Simulate: create_account/transfer/deploy_contract already committed on-chain
    // (account_pool() now holds ntoy(31)), but the trailing function_call("new", ..)
    // failed (e.g. ran out of gas), so promise_result(0) == Failed.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    // In reality account_pool()'s balance is now ntoy(31) on-chain even though
    // the callback below treats it as if nothing happened.
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_staking_pool_create(account_pool(), ntoy(31).into(), account_tokens_owner());
    assert!(matches!(res, PromiseOrValue::Value(false)));

    // Binding check: factory believes 0 pools exist / id untracked...
    context.is_view = true;
    testing_env!(context.clone());
    assert_eq!(contract.get_number_of_staking_pools_created(), 0);

    // ...yet ntoy(31) NEAR is still sitting on account_pool() on-chain (would require
    // a near-workspaces / near-sdk-sim integration test to observe the real account
    // balance post-receipt, since unit tests here cannot execute the actual batched
    // create_account+transfer+deploy_contract+function_call receipt to show the
    // divergence between "tracked=false" and "on-chain balance=31 NEAR").
}
```
Note: a full end-to-end demonstration (showing the real account balance of `staking_pool_id.factory` remaining non-zero after the callback drops it from `staking_pool_account_ids` and refunds the deposit) requires a `near-workspaces` test that executes the actual batched receipt with constrained gas so that `create_account`/`transfer`/`deploy_contract` succeed but `function_call("new", …)` fails - this cannot be fully reproduced in a `testing_env!` unit test since the unit test mocks the promise result rather than executing real batched receipt semantics.

```rust
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
```

```rust
pub fn is_promise_success() -> bool {
    assert_eq!(
        env::promise_results_count(),
        1,
        "Contract expected a result on the callback"
    );
    match env::promise_result(0) {
        PromiseResult::Successful(_) => true,
        _ => false,
    }
```
