### Title
Global-state approval threshold uses floor rounding while block-signature verification uses ceiling rounding, letting signers agree on a "global state" (miner view, protocol version, tx-replay set) that never reaches the true 70% supermajority - (File: `libsigner/src/v0/signer_state.rs`)

### Summary
`GlobalStateEvaluator::reached_agreement` (used by every signer to decide the agreed miner view, active signer protocol version, burn view, and tx-replay set) computes the 70%-of-weight threshold with **floor** division, while `NakamotoBlockHeader::compute_voting_weight_threshold` (the authoritative threshold enforced by the node/consensus layer when verifying a block's signature set) computes the same nominal threshold with **ceiling** division. For any `total_weight` where `total_weight * 7` is not a multiple of 10, these two "70%" thresholds disagree by exactly one unit of weight. This is the same bug class as the reported VotingEscrow issue: two code paths that are supposed to represent one invariant (a 70% supermajority) diverge because of inconsistent rounding, so state that one component considers "agreed" is not actually backed by the number of votes the other component (the one that matters for consensus) requires.

### Finding Description

This is the threshold used everywhere a block's actual signature weight is checked against consensus rules, including `verify_signer_signatures`: [2](#0-1) 

By contrast, `GlobalStateEvaluator::reached_agreement` — the function every v0 signer uses to decide whether a supermajority agrees on the current miner view, protocol version, burn view, or tx-replay set — rounds **down**: [3](#0-2)

```
pub fn reached_agreement(&self, vote_weight: u32) -> bool {
    u64::from(vote_weight)
        >= u64::from(self.total_weight).strict_mul(NAKAMOTO_SIGNER_BLOCK_APPROVAL_THRESHOLD)
            / 10
}
```
No `ceil` adjustment is applied. For `total_weight = 11` (a realistic reward-set weight distribution), the ceiling threshold used by consensus is `ceil(11*7/10) = 8`, but `reached_agreement` will return `true` at a vote weight of only `7` (`77/10 = 7` after floor). The same asymmetry exists in `reached_disagreement` for the 30% blocking-minority side (`>` vs. what should be a `>=`/ceiling-consistent complement): [4](#0-3) 

`reached_agreement`/`GlobalStateEvaluator` is not decorative bookkeeping — it directly drives what a signer believes is the canonical miner and tenure state, feeding `check_block_against_global_state`: [5](#0-4) 
and the miner-inactivity/timeout logic used to decide when to fall back to a different miner: [6](#0-5) 
as well as the protocol-version-consensus gate (`determine_active_signer_protocol_version`) that decides whether the signer evaluates a proposal via the v1 (`SortitionsView`) or v2 (`GlobalStateView`) code path, and whether it signs at all vs. returns `NoSignerConsensus`: [7](#0-6) [8](#0-7) 

Because `reached_agreement` under-counts the required weight by up to one signer's weight relative to the on-chain threshold `compute_voting_weight_threshold`, a set of signers whose combined weight is below what the network's consensus rule (`verify_signer_signatures`) would require can nonetheless conclude "we have global agreement" on a miner/tenure/protocol-version view, and act on it (accepting proposals, deciding tenure timeouts, switching miner state) as if a true 70% supermajority had spoken.

### Impact Explanation
This breaks the equality that is supposed to hold between "the weight the signer set believes has reached supermajority agreement" and "the weight the node's consensus rule (`compute_voting_weight_threshold`/`verify_signer_signatures`) would actually require to approve a block." A signer can be steered (via `check_block_against_global_state`, `is_timed_out`, protocol-version consensus) into treating a miner/tenure view as canonical, and thus sign or reject blocks, based on a quorum that is smaller than the number of votes needed for the corresponding on-chain guarantee. Depending on the weight distribution this can push a signer toward either: signing a proposal built on a miner/tenure view that a true 70% has not actually endorsed (moving toward "signer signing a non-canonical block" under a state that looks locally valid but isn't backed by the required weight), or getting wedged in disagreement with signers using the correctly-rounded on-chain threshold, since `reached_disagreement`'s complementary rounding can likewise diverge from the true blocking-minority boundary. This lands in the High/Critical band described by the rules (miscounted supermajority tally feeding into what a signer signs or how it evaluates canonicity), though it is a local/gossip-derived quorum rather than a signature verified on-chain, so its severity is bounded by how much other chainstate checks (`check_latest_block_in_tenure`, node validation) independently constrain the outcome.

### Likelihood Explanation
The trigger condition is purely arithmetic and depends only on the reward-set weight distribution: any `total_weight` where `total_weight * 7` isn't divisible by 10 (the overwhelming majority of possible weight totals) produces a one-unit discrepancy between the two thresholds. No adversarial signer action, majority, or special access is required — this is a deterministic inconsistency present in every reward cycle whose total weight isn't a multiple of 10. It requires only ordinary gossip traffic (`StateMachineUpdate` messages) among the reward set, which is explicitly in scope.

### Recommendation
Make `GlobalStateEvaluator::reached_agreement`/`reached_disagreement` use the exact same ceiling-rounding formula as `NakamotoBlockHeader::compute_voting_weight_threshold` (ideally by having both call into a single shared helper), so the "70%" invariant used to decide global signer-state agreement is byte-for-byte consistent with the threshold the node enforces on-chain.

### Proof of Concept
Arithmetic demonstration (no simulation needed, pure integer math from the two functions):
- `total_weight = 11`
- `compute_voting_weight_threshold(11)`: `(11*7)/10 = 7`, remainder `77 % 10 = 7 != 0` → `ceil = 1` → threshold = `8`.
- `GlobalStateEvaluator::reached_agreement(7)` with `total_weight = 11`: `7 >= (11*7)/10 = 7` → `true`.

So with 4 signers weighted e.g. `[4,3,2,2]` (total 11), a subset with combined weight 7 (e.g., `[4,3]`) is judged by `reached_agreement` to have reached the "global agreement" supermajority used to pick the active miner view/protocol version/tx-replay set, while the same weight would be rejected by `compute_voting_weight_threshold`/`verify_signer_signatures` as insufficient (needs 8) to actually approve a block. This can be exercised entirely by observing/crafting `StateMachineUpdate` gossip from any subset of already-registered signers reaching weight 7 out of 11; no majority or key compromise is needed to demonstrate the discrepancy itself.

```rust
    /// Check if the sortition identified by the ConsensusHash is timed out based on
    /// the blocks within the signer db and the block proposal timeout
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        signer_db: &SignerDb,
        eval: &GlobalStateEvaluator,
        local_address: &StacksAddress,
        timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = signer_db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) =
            signer_db.get_burn_block_received_time_from_signers(eval, sortition, local_address)?
        else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = signer_db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };
        if elapsed > timeout {
            info!("Sortition has timed out";
                "sorition" => %sortition,
                "timeout" => %timeout.as_secs(),
                "elapsed" => %elapsed.as_secs()
            )
        }
        Ok(elapsed > timeout)
    }
```
