### Title
Deny List Bypass via `coin::redeem_funds` Accumulator Path — (`crates/sui-framework/packages/sui-framework/sources/coin.move`)

### Summary

A denied address for regulated coin type `T` can bypass the deny list restriction entirely by redeeming a `Withdrawal<Balance<T>>` PTB argument through `coin::redeem_funds` → `balance::redeem_funds` → `funds_accumulator::redeem`. No deny list check exists anywhere in this call chain, allowing the denied address to convert accumulator-held `Balance<T>` into a live, spendable `Coin<T>` object within the same PTB.

---

### Finding Description

The deny list enforcement in Sui operates at the **transaction input loading** layer: the runtime rejects transactions where a denied address presents a `Coin<T>` object as a transaction input. This check is type-specific — it applies to `Coin<T>` objects, not to `Withdrawal<Balance<T>>` values.

The `Withdrawal<phantom T: store>` struct has only `drop` ability and is not a storable object: [1](#0-0) 

It is created fresh in a PTB as a call argument for the transaction sender, with the runtime validating only that `limit <= balance` at signing time — no deny list check is performed: [2](#0-1) 

The full public call chain has no deny list guard at any level:

**Step 1** — `coin::redeem_funds` is public, no deny list check: [3](#0-2) 

**Step 2** — `balance::redeem_funds` is public, no deny list check: [4](#0-3) 

**Step 3** — `funds_accumulator::redeem` calls the native `withdraw_impl`, no deny list check: [5](#0-4) 

Funds can be deposited into a denied address's accumulator by any non-denied party via `balance::send_funds`: [6](#0-5) 

Or via `coin::send_funds` (which also has no deny list check on the recipient): [7](#0-6) 

---

### Impact Explanation

The deny list invariant — that denied addresses cannot interact with regulated coin type `T` — is violated. A denied address can:

1. Receive `Balance<T>` into their accumulator (the "cannot receive" restriction applies to `Coin<T>` object transfers, not accumulator deposits).
2. Submit a PTB with a `Withdrawal<Balance<T>>` call argument (no `Coin<T>` input, so the deny list input check does not fire).
3. Call `coin::redeem_funds` and obtain a live `Coin<T>` object.
4. Use that `Coin<T>` in subsequent PTB commands within the same transaction (it is a PTB result, not a pre-existing input, so the deny list input check still does not fire).

This completely nullifies the regulatory freeze for any denied address that has or can receive accumulator balance, constituting **harmful smart-contract behavior** that undermines the core security guarantee of regulated coins.

---

### Likelihood Explanation

- No special privileges are required. Any ordinary address can call `coin::send_funds` to deposit into a denied address's accumulator.
- The denied address only needs to construct a standard PTB with a `Withdrawal` call argument and call the public `coin::redeem_funds`.
- The attack is repeatable and requires no coordination beyond a single transaction.

---

### Recommendation

Add a deny list check inside `balance::redeem_funds` (or `coin::redeem_funds`) that aborts if the withdrawal owner is currently denied for coin type `T`. Specifically, before executing the redemption, verify:

```move
// In balance::redeem_funds or coin::redeem_funds
assert!(
    !deny_list.v2_contains_next_epoch<T>(withdrawal.owner()),
    EDeniedAddress
);
```

Additionally, consider adding a symmetric check in `balance::send_funds` to prevent accumulator deposits to denied addresses, mirroring the existing "cannot receive" restriction for `Coin<T>` transfers.

---

### Proof of Concept

1. Deploy a regulated coin type `T` with `create_regulated_currency_v2`.
2. Deny address `A` via `deny_list_v2_add<T>`.
3. From any non-denied address `B`, call `coin::send_funds(some_coin_T, @A)` — this deposits `Balance<T>` into `A`'s accumulator with no deny list check on the recipient.
4. From address `A`, submit a PTB:
   - Provide a `Withdrawal<Balance<T>>` call argument with `owner = @A` and `limit = deposited_amount`.
   - Call `coin::redeem_funds(withdrawal, ctx)` → returns `Coin<T>`.
   - Transfer the resulting `Coin<T>` to any address.
5. Assert: the transaction succeeds, `A` has effectively moved regulated coin `T` despite being on the deny list, violating the invariant that denied addresses cannot interact with coin type `T`.
