### Title
`Terminate()` unconditionally downgrades to `ForceKill()` on any `taskTerminate` error, bypassing the graceful-timeout window - (File: `helpers/process/killer_windows.go`)

### Summary
`windowsKiller.Terminate()` calls `ForceKill()` immediately whenever `taskTerminate()` returns *any* error, without distinguishing between "target process truly unresponsive" and a transient kernel32 console-API failure. [1](#0-0)  Because `taskTerminate()`'s legacy strategy (`FF_USE_WINDOWS_LEGACY_PROCESS_STRATEGY`) manipulates the *calling runner process's* console state via `FreeConsole`/`AttachConsole`/`SetConsoleCtrlHandler` - a single, process-wide (not per-job) OS resource - concurrent `Terminate()` calls for two different jobs running under the same `gitlab-runner` process can race on this shared state. [2](#0-1) 

### Finding Description
`taskTerminate()` is only invoked with the legacy strategy path when `UseWindowsLegacyProcessStrategy` is enabled, in which case it calls `FreeConsole` (detach current process from its console), `AttachConsole(pid)` (attach current process to target's console), sends `CTRL_C_EVENT`, then `FreeConsole`/`AttachConsole(ATTACH_PARENT_PROCESS)`/`SetConsoleCtrlHandler` again to restore state. [3](#0-2)  All of these Win32 console APIs operate on the console of the *calling process* (i.e., the single `gitlab-runner.exe` process host), which is process-global state, not job-scoped. If two jobs on the same runner host are cancelled at nearly the same time, their goroutines can interleave these calls (e.g., one job's `AttachConsole` succeeding just as another job's `FreeConsole`/`SetConsoleCtrlHandler` runs), and `kernel32Function` treats any non-zero-return-code call as a hard error via `multierror.Append`. [4](#0-3) 

`Terminate()` treats *any* such error - regardless of whether it stems from real inability to signal the target process or a benign race with an unrelated job's concurrent console call - as grounds to immediately invoke `ForceKill()`, which runs `taskkill /F /T` and closes the job object. [5](#0-4)  This bypasses the intended two-phase shutdown design in `osKillWait.KillAndWait`, where `ForceKill()` is normally only triggered after `gracefulKillTimeout` (10 minutes) elapses without the process exiting. [6](#0-5)  A spurious error inside `taskTerminate` short-circuits that timeout entirely, force-killing the process tree immediately.

### Impact Explanation
If a force-kill via `taskkill /F /T` happens while cache/artifact-writing helper processes are mid-flush, the resulting archive can be truncated or corrupted, and this upload would be scoped to whichever job's process happened to be racing at that moment - not necessarily the job that was actually being cancelled with intent. This matches the described scoped impact of a corrupted/truncated artifact or cache for one or more unrelated projects sharing the runner host.

### Likelihood Explanation
This requires: (1) `FF_USE_WINDOWS_LEGACY_PROCESS_STRATEGY=true` (this flag defaults to `false` since GitLab Runner 16.10, and its documentation explicitly recommends `false` "to successfully and gracefully drain a Windows Runner"), [7](#0-6)  and (2) two jobs on the same Windows runner process being cancelled within a very small time window such that their `FreeConsole`/`AttachConsole`/`SetConsoleCtrlHandler` calls interleave. This is a real, self-contained concurrency bug in Runner's own termination logic (not an attacker-controlled exploit): it is triggered by ordinary job cancellation timing, not by any job-supplied input (variables, cache/artifact names, image definitions, etc.). No CI-job-controlled data path reaches this code; the trigger condition depends purely on runner host scheduling of two Terminate() calls, which an unprivileged pipeline author cannot directly control or reliably force since they don't control other tenants' job timing or the racing OS state.

### Recommendation
- Avoid treating any `taskTerminate` error as equivalent to "process cannot be signaled." Distinguish between errors on the restore-state calls (`FreeConsole`/`AttachConsole`/`SetConsoleCtrlHandler` at lines 99-104, which are best-effort cleanup for the runner's own console and not indicative of target-process failure) versus the actual signal-delivery call (`GenerateConsoleCtrlEvent`).
- Serialize access to the shared console state across concurrent `Terminate()` invocations with a package-level mutex, since `AttachConsole`/`FreeConsole` operate on process-wide state and must not be called concurrently from multiple goroutines.
- Only fall back to `ForceKill()` when the actual `GenerateConsoleCtrlEvent` call fails, not on failures of the surrounding console attach/detach/restore housekeeping calls.

### Proof of Concept
```go
// helpers/process/killer_windows_test.go (new)
func TestTerminate_ConcurrentJobs_NoSpuriousForceKill(t *testing.T) {
    // Start N long-running child processes representing N different jobs
    // on the same runner process, with UseWindowsLegacyProcessStrategy=true.
    // Cancel all N jobs concurrently (goroutines calling Terminate() simultaneously).
    // Assert: taskkill (ForceKill) invocation count does not spike compared to
    // sequentially cancelling the same N jobs one at a time.
    // Assert: each job's designated "artifact writer" child process, which
    // writes a marker file at completion, finishes cleanly (marker present,
    // file not truncated) in >=99% of concurrent runs.
}
```
Expected assertion: force-kill rate and artifact-truncation rate under concurrent cancellation should not measurably exceed the rate under serialized cancellation; a fix passes this test, the current code intermittently fails it when legacy strategy is enabled and cancellations race tightly.

**Caveat / uncertainty:** I could not run this scenario directly (no execution environment), so the race has not been empirically reproduced here - the finding is based on static analysis of the shared, process-global nature of the Win32 console APIs used and the unconditional error-to-ForceKill fallback in `Terminate()`. Since the affected code path is gated behind a flag defaulting to `false` in current versions, real-world exposure is limited to runners that still opt into `FF_USE_WINDOWS_LEGACY_PROCESS_STRATEGY=true`.
