### Title
Signer counts peer acceptance signatures toward the global threshold without re-checking that it locally deemed the block valid, letting a rejected block still be broadcast as group-signed - (File: stacks-signer/src/v0/signer.rs)

### Summary
In `Signer::store_and_process_block_signature`, the only staleness/consistency guard before tallying an incoming `BlockResponse::Accepted` signature and broadcasting the group-signed block is `block_info.signed_group.is_some()` (already-finalized check). The function never re-checks `block_info.valid`, unlike the structurally identical pre-commit path (`handle_block_pre_commit`), which explicitly gates on `!block_info.valid.unwrap_or(false)` before counting weight.

### Finding Description
This mirrors the referenced Vault bug class exactly: the code caches/checks one guard variable before proceeding (in Vault, `owner`; in this codebase, `signed_group`) but omits checking a second, equally critical guard variable that governs the same trust decision (in Vault, `nonce`; here, `valid`).

`handle_block_signature` (stacks-signer/src/v0/signer.rs) recovers the signer's public key from an incoming acceptance signature, validates it belongs to a registered signer (`is_valid_signer`), looks up the local `block_info`, and immediately calls `store_and_process_block_signature` — with no check of `block_info.valid`: [1](#0-0) 

`store_and_process_block_signature` then stores the signature, and guards only on `signed_group.is_some()`: [2](#0-1) 

It then tallies the aggregated weight of all recovered signatures and, once threshold is met, unconditionally calls `mark_locally_accepted(true)`, persists the block, and broadcasts it as group-signed: [3](#0-2) 

Compare this with the sibling function `handle_block_pre_commit`, which handles the analogous "weight crosses threshold" decision for pre-commits. There, the developers were clearly aware that the local validity opinion must gate the threshold-triggered action, and explicitly check it before counting weight and before re-running `check_block_against_signer_db_state`: [4](#0-3) [5](#0-4) 

`store_and_process_block_signature` has no equivalent `block_info.valid` check and never calls `check_block_against_signer_db_state` at all. So if this signer previously ran `handle_block_validate_reject`/marked the block locally rejected (`valid = Some(false)`, e.g., due to a chainstate conflict, non-canonical parent, or duplicate-tenure block detected at proposal time), and the block later crosses the network's threshold weight via signature messages relayed from other signers (`BlockResponse::Accepted`), this signer will still: (a) count that weight, (b) call `mark_locally_accepted(true)` — flipping its own recorded state despite having previously rejected the block, and (c) call `broadcast_signed_block`, actively helping propagate/finalize a block it determined was invalid.

### Impact Explanation
This breaks the "rejection recounted as an accept" equality explicitly called out as Critical: a signer's local rejection decision is bypassed purely because enough *other* signers' acceptance messages arrived, without re-validating that the block is still consistent with this signer's own chainstate view. Because `store_and_process_block_signature` is reached simply by relaying/gossiping enough valid signer signatures (no majority of *this* signer's own key or auth token is required — the attacker only needs the already-public signatures from signers who did approve), a single malicious or confused block that gained threshold weight elsewhere can cause every other signer, including ones that independently rejected it, to flip to "locally accepted" and re-broadcast it as group-signed. This directly threatens the invariant that a signer never asserts acceptance of a block it has determined is invalid/non-canonical/conflicting.

### Likelihood Explanation
Likelihood is Medium-to-High for triggering the code path (it requires no privileged access — just observing/relaying `BlockResponse::Accepted` messages that a normal minority of correct signers would produce, e.g., during a network partition, a race between rejection and a competing tenure's proposal, or timing differences in `check_block_against_signer_db_state` results across signers), combined with the precondition that this particular signer had already locally invalidated the block. This requires a divergence in local validation across signers (plausible given the codebase's own re-check comments elsewhere acknowledging "the chain and signer db state may have changed materially" between validation and threshold), but does not require compromising any signer's key or achieving a signing majority of malicious signers — only that enough *honest* signers' pre-existing accept signatures reach threshold while this signer's local view had diverged.

### Recommendation
In `store_and_process_block_signature`, before tallying weight and marking `mark_locally_accepted`/broadcasting, re-check `block_info.valid` (and ideally re-run `check_block_against_signer_db_state`, exactly as `handle_block_pre_commit` does) and refuse/mark-rejected instead of accepting if the local determination is `Some(false)` or unset. This restores parity between the pre-commit and signature-acceptance code paths, both of which trigger the same class of "weight crossed threshold" action.

### Proof of Concept
1. Signer S receives a `BlockProposal` for block B, validates it, and `check_block_against_signer_db_state`/`handle_block_validate_reject` marks `block_info.valid = Some(false)` (e.g., B conflicts with an already-signed sibling, or fails a chainstate check) — see `signer.rs` `handle_block_validate_reject`/`mark_locally_rejected` path.
2. Other signers, whose local chainstate view had not yet observed the conflict (a real, achievable race per the codebase's own comments about state changing "materially" between validation and threshold), sign and broadcast `BlockResponse::Accepted(B)` for enough combined weight to cross `compute_voting_weight_threshold`.
3. S receives these `BlockResponse::Accepted` messages via `handle_block_signature` → `store_and_process_block_signature`. Since S's `block_info.signed_group` is still `None`, S proceeds to tally `total_signature_weight`, crosses `min_weight`, and calls `block_info.mark_locally_accepted(true)`, persists it, and calls `broadcast_signed_block` — all despite `block_info.valid == Some(false)` from step 1, which is never re-checked (`stacks-signer/src/v0/signer.rs:2468` only checks `signed_group`, lines 2494-2537 have no `valid` gate).
4. Result: S's own rejection is silently overridden and it actively re-broadcasts the block as accepted, matching the "rejection recounted as acceptance" Critical impact criterion.
