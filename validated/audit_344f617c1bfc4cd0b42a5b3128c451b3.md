### Title
Signer permanently refuses to re-sign a pre-committed block once a conflict check fails, with no periodic re-evaluation (analogous to the "stuck presumptive state" bug) - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit` can leave a block wedged in `PreCommitted` state forever if the fresh-conflict guard fires once and no further external event (a new `BlockPreCommit` message or a miner re-proposal) ever re-triggers evaluation of that block. Unlike `check_submitted_block_proposal`, which has an explicit time-based sweep to break the "waiting for a response that may never come" wedge, the "refuse to sign for now" path in the pre-commit/conflict logic has no analogous timer-driven re-check.

### Finding Description
When a block B reaches the pre-commit weight threshold, `handle_block_pre_commit` re-checks chainstate and then checks for a fresh conflicting signature (block A) via `get_signed_conflicts` / freshness cutoff / `conflict_still_blocks`: [1](#0-0) 

If a fresh conflict is found, the function simply `return`s — a deliberately silent, non-broadcast "refusal for now", intended to be revisited "once the conflicting signature has gone stale": [2](#0-1) 

The block is left in `BlockState::PreCommitted` with `signed_self == None`. The only two paths that ever re-invoke `handle_block_pre_commit` for this block afterward are:
1. Receipt of a *new* `BlockPreCommit` message from a signer (`process_event` → `handle_block_response`/`handle_block_pre_commit`), documented in section 5 of `docs/signer-flows.md`.
2. A miner re-proposal of the same block, which routes through `should_reevaluate_block`, explicitly re-running the pre-commit evaluation: [3](#0-2) 

There is no periodic, time-based sweep (analogous to `check_submitted_block_proposal`, which is called every `process_event` cycle and forcibly resolves a stalled validation submission after `block_proposal_validation_timeout`): [4](#0-3) 

If neither a new pre-commit message nor a re-proposal ever arrives for block B (e.g., the last pre-commit needed to cross the threshold was this signer's own, so all other signers' pre-commit chunks were already broadcast and won't be resent, and the miner does not re-propose B because it has moved on to a different block), the signer's own timer-driven maintenance path never revisits B. Even though the freshness cutoff on the competing signature A would eventually make the conflict stale (`last_endorsed > freshness_cutoff` becomes false), nothing calls `handle_block_pre_commit` again to notice that, so B stays stuck as `PreCommitted`/unsigned indefinitely — exactly the "presumptive, but no rival ever arrives" pattern from the report: a state is reached that is supposed to be transient pending an external condition, but the condition's re-check is event-triggered only, with no fallback poll.

### Impact Explanation
This falls under the report's "High" category: a signer can be wedged into never signing a block it should eventually be willing to sign (once a conflicting signature it holds becomes stale). This is a liveness defect local to the affected signer/block pair rather than a safety violation — it does not cause the signer to sign an invalid/conflicting block, but it can prevent that signer from ever contributing its pre-commit-turned-signature to a legitimate reorg/replacement block, mirroring the source report's statement that the underlying bug class "does not allow the dishonest party to win" but "prevents progression."

### Likelihood Explanation
Triggering the initial "refuse to sign for now" state requires only ordinary miner behavior available to a single (potentially adversarial) miner: proposing two conflicting blocks at the same height in overlapping tenures (a normal occurrence during miner takeover/reorg-timing scenarios that the code already anticipates, per `stacks-signer/src/v0/tests.rs` sibling-conflict tests). The scenario in which the wedge becomes *permanent* — no further pre-commit gossip and no re-proposal — depends on external message/timing conditions that are plausible in production (e.g., the miner never re-proposes the losing block, and the peer whose pre-commit crossed the threshold does not re-send). This makes it a real but timing-dependent liveness gap rather than a guaranteed break; the exact frequency in production could not be fully confirmed from the indexed code alone.

### Recommendation
- **Short term:** Have `process_event`'s periodic housekeeping (alongside `check_submitted_block_proposal`/`check_pending_block_validations`) also re-run the pre-commit/conflict evaluation for any block sitting in `PreCommitted` with `signed_self == None` whose recorded conflicts have gone stale, instead of relying solely on inbound `BlockPreCommit` messages or re-proposals.
- **Long term:** Document the full set of conditions under which each `BlockState` transition can be re-triggered (as already partly captured in `docs/signer-flows.md`), and explicitly identify/close any state where progression depends purely on an external message that is not guaranteed to be resent.

### Proof of Concept
1. Miner proposes block A (tenure 1, height h). All signers validate and sign A (`LocallyAccepted`), per `handle_block_pre_commit`'s normal `SIGN` path (`stacks-signer/src/v0/signer.rs:1466` onward).
2. Miner (or a competing miner after a Bitcoin fork) proposes block B, a sibling at the same height h in a different tenure.
3. Signer S validates B, marks it `PreCommitted`, and broadcasts its pre-commit; by coincidence, S's own pre-commit is the one that pushes the aggregate weight over threshold (`stacks-signer/src/v0/signer.rs:1290-1338`).
4. `handle_block_pre_commit` re-runs chainstate checks (pass) and then evaluates `get_signed_conflicts`: A is found, still fresh (`last_endorsed > freshness_cutoff`) and `conflict_still_blocks` returns true, so S returns without signing (`stacks-signer/src/v0/signer.rs:1403-1421`).
5. No other signer sends a further `BlockPreCommit` for B (their chunks are already on StackerDB, unchanged), and the miner does not re-propose B (e.g., it abandons tenure 2 for a different fork).
6. Time passes beyond `tenure_last_block_proposal_timeout`; A's conflict is now stale in principle, but `handle_block_pre_commit` for B is never invoked again, so S never notices and never signs B — B is stuck in `PreCommitted` on signer S indefinitely, with no periodic mechanism to revisit it (contrast with `check_submitted_block_proposal`, which *does* sweep on every event loop iteration).

    /// Check the current tracked submitted block proposal to see if it has timed out.
    /// Broadcasts a rejection and marks the block locally rejected if it has.
    fn check_submitted_block_proposal(&mut self) {
        let Some((proposal_signer_sighash, block_submission)) =
            self.submitted_block_proposal.take()
        else {
            // Nothing to check.
            return;
        };
        if block_submission.elapsed() < self.block_proposal_validation_timeout {
            // Not expired yet. Put it back!
            self.submitted_block_proposal = Some((proposal_signer_sighash, block_submission));
            return;
        }
        // For mutability reasons, we need to take the block_info out of the map and add it back after processing
        let mut block_info = match self.signer_db.block_lookup(&proposal_signer_sighash) {
            Ok(Some(block_info)) => {
                if block_info.has_reached_consensus() {
                    // The block has already reached consensus.
                    return;
                }
                block_info
            }
            Ok(None) => {
                // This is weird. If this is reached, its probably an error in code logic or the db was flushed.
                // Why are we tracking a block submission for a block we have never seen / stored before.
                error!("{self}: tracking an unknown block validation submission.";
                    "signer_signature_hash" => %proposal_signer_sighash,
                );
                return;
            }
            Err(e) => {
                error!("{self}: Failed to lookup block in signer db: {e:?}",);
                return;
            }
        };
        // We cannot determine the validity of the block, but we have not reached consensus on it yet.
        // Reject it so we aren't holding up the network because of our inaction.
        warn!(
            "{self}: Failed to receive block validation response within {} ms. Rejecting block.", self.block_proposal_validation_timeout.as_millis();
            "signer_signature_hash" => %proposal_signer_sighash,
        );
        let rejection = self.create_block_rejection(
            RejectReason::ConnectivityIssues(
                "failed to receive block validation response in time".to_string(),
            ),
            &block_info.block,
        );
        block_info.reject_reason = Some(rejection.response_data.reject_reason.clone());
        if let Err(e) = block_info.mark_locally_rejected() {
            if !block_info.has_reached_consensus() {
                warn!("{self}: Failed to mark block as locally rejected: {e:?}");
            }
        };
        self.send_block_response(&block_info.block, rejection.into());

        self.signer_db
            .insert_block(&block_info)
            .unwrap_or_else(|e| self.handle_insert_block_error(e));
    }
