## Title
Builder payment `fee_recipient` is never validated against the proposer's committed preference in `process_execution_payload_bid` — ([File: specs/gloas/beacon-chain.md])

### Summary
`process_execution_payload_bid` in `specs/gloas/beacon-chain.md` accepts the builder-signed `bid.fee_recipient` and unconditionally uses it as the destination of the builder's payment (recorded in `BuilderPendingWithdrawal.fee_recipient`), which later is paid out via `get_builder_withdrawals`/`apply_withdrawals` [1](#0-0) . The requirement that "the bid's fee recipient matches the proposer's preference" is only enforced as a gossip-layer `IGNORE` rule in `specs/gloas/p2p-interface.md`, never in the authoritative state-transition validity checks of `process_execution_payload_bid` [2](#0-1) . This is the "missed depositary check" analog: a destination/authorization field that a manual/ancillary mechanism is supposed to police, but which the canonical state-transition function never re-verifies, so a block that satisfies every consensus rule can still misdirect the builder's payment.

### Finding Description
`process_execution_payload_bid` validates that the builder is active, can cover the bid, and that the bid signature is valid, along with slot/parent/randao/blob-count checks [3](#0-2) . It never checks `bid.fee_recipient` against anything tied to the block's proposer. The only place `fee_recipient` is cross-checked against "the proposer's preference" is in the gossip validation logic for `execution_payload_bid` messages:

```
# [IGNORE] The bid's fee recipient matches the proposer's preference
if bid.fee_recipient != proposer_preferences.fee_recipient:
    raise GossipIgnore("bid's fee recipient does not match the proposer's preference")
``` [4](#0-3) 

Gossip `IGNORE` rules only affect whether a *message* is relayed on the p2p network; they are not part of the state-transition function and are not consulted by `process_block`/`process_execution_payload_bid` when validating a block that already contains a `SignedExecutionPayloadBid`. Once a bid is embedded in a proposed block, its acceptance is governed solely by `process_execution_payload_bid`, and the amount is later settled straight to `bid.fee_recipient` when the payment weight reaches quorum [5](#0-4)  or when `apply_parent_execution_payload` settles it directly [6](#0-5) .

This mirrors the reported bug class: the "depositary"-equivalent field (`fee_recipient`, i.e. who actually receives the payment) is only checked by an out-of-band/soft mechanism (gossip `IGNORE`), while the authoritative acceptance path (the state-transition assertions) has no equivalent check and will happily accept and settle a payment to an arbitrary address.

### Impact Explanation
The amount recorded in `BuilderPendingWithdrawal.fee_recipient`/`BuilderPendingPayment.withdrawal.fee_recipient` represents Gwei that the builder is paying out as part of the PBS auction — economically intended for the proposer/validator that accepted the bid. Because the state-transition function does not bind `fee_recipient` to the block's proposer (or any committed proposer preference), a builder (in collusion with, or via a compromised/naively-implemented relay talking to, the block-producing validator) can set `fee_recipient` to an address it controls itself. The block remains fully valid under `process_block`, the builder's balance is decreased as expected by `settle_builder_payment`/`process_builder_pending_payments`, but the payout goes to the builder's own address rather than to the proposer who was promised the payment — a Gwei payment that the "buyer" (proposer) is owed is instead paid to a non-owner. This matches the "builder payment ... misdirected" High-impact category (and can rise to Critical-adjacent effect for the specific proposer whose block reward was diverted, at the scale of one auction's `bid.value`), because the loss lands on a third party (the proposer), not just the acting entity's own stake.

### Likelihood Explanation
Exploitability does not require any client bug, network partition, or majority stake — only that the party assembling `block.body.signed_execution_payload_bid` (the builder or a builder-controlled relay feeding an honest proposer) sets an arbitrary `fee_recipient` in a bid that it signs itself; `verify_execution_payload_bid_signature` only checks the BLS signature of the builder over its own message, and it will still validate [7](#0-6) . The gossip check exists precisely because this scenario is anticipated as a possible manipulation vector, but it is advisory (`IGNORE`, not `REJECT`, and not part of block validity), so it provides no consensus-level guarantee once the bid is bundled directly into a block rather than propagated as a standalone gossip message.

### Recommendation
Add an assertion in `process_execution_payload_bid` (the state-transition function) that `bid.fee_recipient` matches a value the proposer has committed to in-protocol (e.g., the proposer's most recent signed `ProposerPreferences` message referenced by slot/root, analogous to how `SignedBLSToExecutionChange` or `WithdrawalRequest.source_address` are checked against validator-owned state elsewhere in the spec). This closes the gap between the advisory gossip-layer check and the actual consensus validity rule, ensuring `fee_recipient` cannot be freely chosen by the builder outside of what the proposer authorized.

### Proof of Concept
1. A validator `P` is scheduled to propose slot `N` and broadcasts `SignedProposerPreferences` with `fee_recipient = A_p` (its own address) as required by the p2p spec.
2. A colluding/careless relay or builder `B` (who may or may not go through gossip) constructs `SignedExecutionPayloadBid` with `bid.fee_recipient = A_b` (attacker-controlled) instead of `A_p`, signs it with the builder key, and supplies it to `P`'s validator software for inclusion (bypassing/ignoring the gossip `IGNORE` rule, which only affects p2p relaying, not local block-building input).
3. `P` includes this bid in its block. `process_execution_payload_bid` runs all its checks (builder active, `can_builder_cover_bid`, signature valid, slot/parent/randao correct) — all pass — and caches `state.latest_execution_payload_bid = bid` with `fee_recipient = A_b` [1](#0-0) .
4. Once payment weight reaches quorum, `process_builder_pending_payments` (epoch processing) or `apply_parent_execution_payload` appends a `BuilderPendingWithdrawal{fee_recipient=A_b, amount=bid.value, builder_index=B}` [5](#0-4) .
5. `get_builder_withdrawals` later produces a `Withdrawal` paying `bid.value` to `A_b` [8](#0-7) , even though the entire block-state-transition history never verified `A_b` against anything proposer-`P`-owned. The state transition accepted an invalid recipient because no equivalent of a "depositary check" exists at the consensus layer.

def process_builder_pending_payments(state: BeaconState) -> None:

    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:

    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)

    # Verify commitments are under limit
    assert (
        len(bid.blob_kzg_commitments)
        <= get_blob_parameters(get_current_epoch(state)).max_blobs_per_block
    )

    # Verify that the bid is for the current slot
    assert bid.slot == state.slot
    assert state.slot > GENESIS_SLOT
    # Verify that the bid is for the right parent block
    assert bid.parent_block_hash == state.latest_block_hash
    # Verify that the bid's block hash differs from its parent block hash
    assert bid.block_hash != bid.parent_block_hash
    assert bid.parent_block_root == get_block_root_at_slot(state, state.slot - 1)
    assert bid.prev_randao == get_randao_mix(state, get_current_epoch(state))
