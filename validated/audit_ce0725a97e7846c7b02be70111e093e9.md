### Title
Stale rejection weight never cleared on signer flip Reject→Accept, wedging the miner coordinator on a legitimately-approved block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` maintains two independent, monotonically-increasing weight counters per block — `total_weight_approved` and `total_weight_rejected` — that the mining coordinator (`signer_coordinator.rs`) treats as mutually exclusive to decide whether a block is globally accepted or globally rejected. The de-duplication logic that gates each counter uses two *different* sets (`gathered_signatures` for Accepted, `responded_signers` for Rejected), so a single signer that first sends a `Rejected` response and later a legitimate `Accepted` response for the *same* block has its weight counted in **both** buckets simultaneously, and the rejected weight is never rolled back.

### Finding Description
In the `SignerMessageV0::BlockResponse` handling loop:

- On `Rejected`, the dedup gate is `block.responded_signers.insert(slot_id)`; if that succeeds, `total_weight_rejected` is bumped once and never reduced later. [1](#0-0) 

- On `Accepted`, the dedup gate for adding weight is `!block.gathered_signatures.contains_key(&slot_id)` — a completely separate map from `responded_signers` — and `responded_signers.insert(slot_id)` is only called *after* the weight has already been added. [2](#0-1) 

Consequence: if the same signer slot first delivers a `Rejected` message (adding its weight to `total_weight_rejected` and inserting into `responded_signers`) and subsequently delivers an `Accepted` message for that identical `signer_signature_hash` (a normal, documented occurrence — the signer flow explicitly treats "a rejection [as] a revocable opinion" that can be re-evaluated), the `Accepted` branch does not consult `responded_signers` at all before adding weight; it only checks the unrelated `gathered_signatures` map, which is still empty for that slot. The signer's weight is therefore added to `total_weight_approved` as well, while its earlier contribution to `total_weight_rejected` is never subtracted.

This breaks the invariant the coordinator relies on — that `total_weight_approved` and `total_weight_rejected` partition (not overlap) the responding signers' weight — used here: [3](#0-2) 

Because `total_weight_rejected` is sticky and never decremented, a block can accumulate rejection weight from signers who later change their mind and accept, yet the coordinator continues to treat that stale weight as still blocking. Once `total_weight_rejected.saturating_add(weight_threshold) > total_weight` becomes true from transient/no-longer-valid rejections, the coordinator permanently returns `NakamotoNodeError::SignersRejected` for that block — even if, at the same or a later poll, `total_weight_approved` would independently reach `weight_threshold` from the very same (and other) signers. The reject-check is evaluated first and unconditionally aborts the wait loop, so the miner never gets the chance to observe the resulting acceptance.

### Impact Explanation
This is a liveness wedge triggerable without any majority of malicious signers: a single signer whose local chainstate transiently rejects a block (e.g. a raced/late chainstate re-check, per the documented "silence keeps the door open to sign later" design) and then legitimately reconsiders and accepts, permanently pollutes the miner's rejection tally for that specific block proposal. Combined with ordinary network jitter across a handful of signers near the 30% blocking-minority boundary, this can cause the coordinator to abort a block that would otherwise have reached the 70% signing threshold, forcing the miner to discard/retry the tenure. This matches the "High" impact class: a wedge that stalls legitimate block finalization at the node/coordinator layer.

### Likelihood Explanation
No collusion or majority stake is required — a single signer's own ordinary reject→accept transition (something the signer-side state machine is explicitly designed to allow) is sufficient to trigger the double count. The condition is purely a bookkeeping bug in `stackerdb_listener.rs`, reachable any time a signer's local view of a proposal changes between its first and second response for the same `signer_signature_hash`, which happens routinely under normal network timing (e.g., a `Reject` sent before a pending validation completes, followed by an `Accept` once validation/pre-commit conditions are satisfied).

### Recommendation
Make `total_weight_approved` and `total_weight_rejected` mutually exclusive per signer slot by gating both branches on the same authoritative "already responded" set (`responded_signers`), checked *before* adding weight in either branch, and by moving/re-adjusting weight correctly when a signer's response for a given block changes category (or simply latching each slot's final response and computing both totals from that latched state rather than incrementally in two independently-gated counters).

### Proof of Concept
1. Miner proposes block `B` (hash `H`) and the coordinator begins tallying via `StackerDBListener`.
2. Signer `S` (weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`. `responded_signers` now contains `S`'s slot; `total_weight_rejected += w`.
3. `S` re-evaluates (e.g. after its own pre-commit/validation completes) and sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `H`.
4. In the `Accepted` handler, `block.gathered_signatures.contains_key(&slot_id)` is `false` (this map was never touched by the earlier `Rejected` branch), so `total_weight_approved += w` is executed — `w` is now counted in both totals.
5. `total_weight_rejected` is never reduced. If enough other signers' natural jitter pushes `total_weight_rejected.saturating_add(weight_threshold) > total_weight` at any coordinator poll (checked in `signer_coordinator.rs` lines 509–519), the coordinator returns `SignersRejected` and abandons block `B`, even though `total_weight_approved` (inflated by the same double-counted `w`) may independently have reached `weight_threshold` had the check order been reversed or the tally been correct.
