### Title
Unbounded `savedCallbacks` flooding lets an attacker evict a victim's pending legacy trigger callback via age-only pruning - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`(*handler).HandleLegacyUserMessage` stores every legacy `web_api_trigger` request in a shared `map[string]*savedCallback` keyed only by `MessageId`, with no per-sender rate limiting or fairness (explicitly marked `// TODO: apply allowlist and rate-limiting here`). `(*handler).pruneCallbacks` evicts entries purely by `createdAt` ordering once `len(savedCallbacks) > MaxSavedCallbacks`, so an attacker able to submit `MaxSavedCallbacks` cheap, well-formed, differently-`MessageId`d requests can force eviction of an older, still-valid victim entry before the victim's DON response arrives.

### Finding Description
`HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) accepts any message that passes basic payload decoding, a `Timestamp` staleness check, and method validation, then unconditionally inserts a `savedCallback{id, createdAt: time.Now(), callback}` into `h.savedCallbacks[msg.Body.MessageId]` (line 412). There is no allowlist or rate limit applied at this layer (the TODO comment at line 384 confirms this is intentionally deferred). The only rate limiting in the handler, `nodeRateLimiter`, is applied in `handleWebAPIOutgoingMessage` for DON node-to-gateway outgoing messages, not for inbound user trigger requests.

`pruneCallbacks` (lines 299-339) runs on a fixed ticker (`CallbackPruneIntervalSec`) and:
1. First removes entries older than `CallbackMaxAgeSec`.
2. If the map still exceeds `MaxSavedCallbacks`, it sorts all remaining entries strictly by `createdAt` and deletes the oldest half (`entries[:len(entries)-maxSize/2]`), with zero consideration of sender identity, origin, or request legitimacy.

Because eviction is purely a function of insertion order/time, an attacker who submits `MaxSavedCallbacks` distinct, validly-signed legacy trigger messages (each just needs a unique `MessageId`, valid timestamp, and correct method) immediately after a victim's legitimate request is stored will cause the victim's entry to be the oldest in the map at the next prune cycle, and it gets silently `delete`d. When the DON nodes eventually respond via `handleWebAPITriggerMessage` (lines 148-162), the lookup `h.savedCallbacks[msg.Body.MessageId]` fails (`found == false`), and the response is silently dropped — the victim's callback is never invoked and their client-facing request times out with no error surfaced.

### Impact Explanation
This breaks per-request/per-user isolation and delivery guarantees for the gateway's legacy trigger callback mechanism: a single unprivileged/unauthenticated caller with only a throwaway signing key can cause another legitimate, in-flight, well-formed request to never receive its response. This matches a request-starvation / cross-user denial-of-service impact — the victim's request silently fails despite being valid and already accepted by the gateway, and the victim has no way to detect why.

### Likelihood Explanation
Exploitability depends on the attacker being able to push `MaxSavedCallbacks` (default 20,000) messages into the map within one `CallbackPruneIntervalSec` window (default 30s) or before the natural `CallbackMaxAgeSec` (default 120s) expiry, using only valid signatures (any signer is accepted at this layer since no allowlist/rate-limit is applied in `HandleLegacyUserMessage`). This requires meaningful throughput (~667 msgs/sec sustained for 30s to hit the default cap) but no privileged credentials, and is entirely repeatable since the map size and prune behavior are deterministic and unbounded per-sender. The severity/likelihood is dampened by the need for sustained high-rate signed traffic and default cap size, but nothing in the code prevents it structurally.

### Recommendation
Add per-sender quotas/allowlisting on inbound legacy user messages (the code already has a TODO marking this gap), and change `pruneCallbacks` eviction to be fairness-aware (e.g., cap callbacks per sender, or prioritize preserving unexpired, distinct-sender entries) rather than pure global age-ordering across all senders.

### Proof of Concept
Go unit test, modeled on the existing `TestPruneCallbacks` test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with `MaxSavedCallbacks = N` (small, e.g. 10) via `NewHandler`.
2. Insert one "victim" `savedCallback` into `h.savedCallbacks` with `createdAt = time.Now()`, wrapping a callback whose `SendResponse` sets a `victimCalled` flag.
3. Immediately insert `N` "attacker" `savedCallback` entries with later `createdAt` timestamps and distinct `MessageId`s (simulating flooding via repeated `HandleLegacyUserMessage` calls with valid signed messages and unique `MessageId`s).
4. Call `h.pruneCallbacks()` directly.
5. Assert the victim's `MessageId` key is no longer present in `h.savedCallbacks` (`_, found := h.savedCallbacks[victimID]; require.False(t, found)`).
6. Simulate the DON response by calling `h.handleWebAPITriggerMessage` with the victim's `MessageId` and assert `victimCalled` remains `false`, confirming the response is silently dropped.
