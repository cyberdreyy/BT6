### Title
`L2Client::block_by_hash` accepts an unverified block from the L2 RPC without checking the returned header hash matches the requested hash - (File: crates/proof/rpc/src/l2_client.rs)

### Summary
`L2Client::block_by_hash` in `crates/proof/rpc/src/l2_client.rs` fetches a block "by hash" from the L2 RPC endpoint and returns/caches it without ever comparing the block header's hash against the hash that was requested. This is the same bug class as the reported regclient advisory: a client pins content by digest/hash, but the response is trusted without verifying that the returned content actually hashes to the pinned value, allowing a malicious or compromised RPC endpoint to substitute different content under a trusted digest.

### Finding Description
`L2Client::block_by_hash` requests a block keyed by a specific hash and, once received, immediately caches and returns it with no equality check between the requested `hash` and `block.header.hash`: [1](#0-0) 

Contrast this with every other hash-pinned RPC accessor in the same codebase, which explicitly re-verify the returned hash before trusting the response:
- `AlloyChainProvider::header_by_hash` / `block_info_and_transactions_by_hash` call `self.verify_header_hash(&header, hash)` before caching: [2](#0-1) [3](#0-2) 
- `AlloyL2ChainProvider::block_info_by_id` calls `self.verify_block_hash(b.header.hash, hash.block_hash)` for hash-based lookups: [4](#0-3) 
- `OutputValidator::compute_output_root_with_hash` explicitly recomputes and compares the header hash returned by the L2 RPC as "defense-in-depth… against a compromised or buggy RPC node": [5](#0-4) 
- `DelayedL1OriginSelectorProvider::prepared_by_hash` explicitly rejects on hash mismatch: [6](#0-5) 

`L2Client` implements the same `L2Provider` trait as used to feed the fault-proof/output-root-validation pipeline (`crates/proof/rpc/src/traits.rs::L2Provider::block_by_hash`), yet its implementation is the one accessor in this family that skips the hash-equality check entirely: [7](#0-6) 

### Impact Explanation
An L2 RPC endpoint that is malicious, compromised, or simply buggy could return a block whose actual contents (transactions, receipts root, state root, etc.) do not correspond to the pinned block hash requested by `L2Client::block_by_hash`. Because there is no hash-equality assertion (unlike the sibling accessors in the same codebase), the mismatched block would be cached and treated as authoritative by any downstream consumer of `L2Provider::block_by_hash` (e.g. fault-proof/output-root computation paths that rely on `L2Provider`). This can lead to computing or validating a wrong provable output root or otherwise operating on forged L2 block data, which is explicitly an in-scope, accepted impact ("wrong provable output root").

### Likelihood Explanation
Exploitation requires an untrustworthy or compromised L2 RPC backend behind `L2Client` (as opposed to a local trusted execution client). Given the codebase's own pattern — every other by-hash accessor added an explicit `verify_header_hash`/`verify_block_hash` check specifically to guard against "a compromised or buggy RPC node" — this omission in `L2Client::block_by_hash` is a genuine, reachable gap rather than a defense-in-depth nicety; it is the exact analog of the regclient digest-pinning bug where a single code path forgot the verification step present everywhere else.

### Recommendation
Add a hash-verification step to `L2Client::block_by_hash` (and the analogous `header_by_number`/`block_by_number` cache-then-trust flows if they are ever used to key by an externally-pinned hash) mirroring `AlloyChainProvider::verify_header_hash`/`AlloyL2ChainProvider::verify_block_hash`: after fetching the block, assert `block.header.hash == hash` and return a typed error (e.g. `RpcError::HeaderHashMismatch`) on mismatch before inserting into `blocks_cache`/`headers_cache` or returning the block to the caller.

### Proof of Concept
1. Point `L2Client` at a malicious/compromised L2 RPC endpoint.
2. Call `L2Provider::block_by_hash(hash)` for some pinned `hash`.
3. Have the malicious endpoint respond to `eth_getBlockByHash(hash, true)` with a well-formed block whose actual header hash differs from `hash` (e.g., a different transaction set/state root) while still returning HTTP 200 with `result.hash` matching-looking JSON.
4. Observe `L2Client::block_by_hash` in `crates/proof/rpc/src/l2_client.rs:288-312` returns and caches this block without any check — unlike `AlloyChainProvider::block_info_and_transactions_by_hash`, which would reject the same forged response via `verify_header_hash` (`crates/consensus/providers/src/chain_provider.rs:261-262`).

    async fn block_by_hash(&self, hash: B256) -> RpcResult<BaseBlock> {
        // Check cache first
        if let Some(block) = self.blocks_cache.get(&hash).await {
            return Ok(block);
        }

        let backoff = self.retry_config.to_backoff_builder();

        let block = (|| async {
            self.provider.get_block(BlockId::Hash(hash.into())).full().await.map_err(RpcError::from)
        })
        .retry(backoff)
        .when(|e| e.is_retryable())
        .notify(|err, dur| {
            tracing::debug!(error = %err, delay = ?dur, "Retrying L2Client::block_by_hash");
        })
        .await?
        .ok_or_else(|| RpcError::BlockNotFound(format!("Block not found for hash {hash}")))?;

        // Cache the result
        self.blocks_cache.insert(hash, block.clone()).await;
        self.headers_cache.insert(hash, block.header.clone()).await;

        Ok(block)
    }
