## Title
Malicious taker can brick `EscrowDst.withdraw()`/`publicWithdraw()` via an unconditionally-reverting fee recipient, permanently freezing/stealing the maker's destination funds - (File: `contracts/EscrowDst.sol`)

### Summary
`EscrowDst._withdraw()` performs three sequential, unconditional external transfers (`integratorFeeRecipient`, `protocolFeeRecipient`, `maker`) with no try/catch, exactly the same fragile pattern that caused the referenced BvbProtocol H-3 bug (a single reverting external call in a settlement function blocks the entire settlement). Here, the fee-recipient addresses embedded in the escrow's `Immutables.parameters` are supplied entirely by the taker/resolver when calling `createDstEscrow()`, with no on-chain cross-check against the commitment made on the source chain. A malicious taker can set a fee recipient to a contract that unconditionally reverts on receiving native ETH, which permanently blocks `withdraw()` and `publicWithdraw()` for everyone, and after `RESCUE_DELAY` lets only the taker reclaim the locked funds via `rescueFunds()` — denying the maker their destination-chain payout while the taker keeps the maker's source-chain collateral.

### Finding Description
`EscrowDst._withdraw()` transfers fees and principal in one atomic sequence with no fault isolation: [1](#0-0) 

Each transfer goes through `_uniTransfer`, which for native tokens calls `_ethTransfer`, and reverts the whole transaction (`NativeTokenSendingFailure`) if the low-level call fails: [2](#0-1) 

The fee recipients are extracted from `immutables.parameters`, a value baked into `Immutables` at escrow-clone deploy time: [3](#0-2) 

Crucially, on the destination chain, the entire `Immutables` struct — including `parameters` (protocol/integrator fee amounts and recipients), `token`, and `amount` — is supplied directly by the caller of `createDstEscrow()`: [4](#0-3) 

There is no on-chain validation tying these values back to the `DstImmutablesComplement` committed during the source-chain `_postInteraction` (that data is only emitted in an event, not enforced): [5](#0-4) 

Attack path (analog of BvbProtocol's `settleContract` grief, mapped onto the destination-escrow lifecycle):
1. Attacker acts as taker/resolver on a swap where `dstToken == address(0)` (native ETH destination).
2. Attacker calls `createDstEscrow()` supplying `Immutables.parameters` where `integratorFeeAmount > 0` and `integratorFeeRecipient` is a contract with `receive()`/`fallback()` that always reverts.
3. When any party (taker via `withdraw`, or any access-token holder via `publicWithdraw`) later calls `_withdraw()`, the mandatory native-ETH transfer to the malicious fee recipient always reverts, so the function can never complete — the maker can never receive `immutables.amount`: [6](#0-5) 
4. After `RESCUE_DELAY`, only the taker (`onlyCaller(immutables.taker.get())`) can call `rescueFunds()`, which unconditionally sends the escrow's native balance to `msg.sender` — the attacker themselves: [7](#0-6) 

The existing test suite already documents that this exact failure mode reverts the whole withdrawal instead of degrading gracefully: [8](#0-7) [9](#0-8) 

### Impact Explanation
This meets Critical/High criteria under the stated bounty scope: the maker's destination funds are permanently frozen because no code path can ever complete `_withdraw()`, and the same unprivileged attacker (the taker who created the escrow) is the only one able to later sweep those exact funds to themselves via `rescueFunds()` once the rescue delay passes. Combined with the standard atomic-swap flow where the taker also withdraws the maker's source-chain collateral using the same secret, this is a direct theft-of-user-funds / permanent-freezing scenario caused entirely by an unprivileged party (the resolver/taker), not an owner/governance/privileged-resolver assumption — the resolver role here is simply "whoever deploys `createDstEscrow`", which has no access control tying it to a trusted whitelist for this call.

### Likelihood Explanation
High. No special privileges are required — any taker calling `createDstEscrow()` fully controls the `Immutables.parameters` field (fee amounts/recipients) with zero on-chain cross-validation against the source-chain commitment. Deploying a 1-line "always revert on receive" contract and setting a non-zero fee (even 1 wei) is trivial and cheap, and the ETH-denominated destination-token path (`dstToken == address(0)`) is a normal, supported configuration.

### Recommendation
- Wrap the fee-recipient and maker transfers in `_withdraw()` in try/catch (mirroring the BvbProtocol fix pattern), falling back to a pull-payment/`withdrawableAmount` bookkeeping mapping when a push transfer fails, so a hostile recipient cannot block the whole settlement.
- Alternatively/additionally, enforce on-chain that `createDstEscrow()`'s `dstImmutables.parameters` (fee recipients/amounts, token, amount) match a hash committed during the source-chain `_postInteraction` (e.g., store `keccak256(immutablesComplement)` and require `createDstEscrow` to prove equality), preventing a malicious taker from injecting arbitrary fee recipients unilaterally.

### Proof of Concept
1. Deploy `MaliciousReceiver` with `receive() external payable { revert(); }`.
2. Taker calls `createDstEscrow{value: amount+safetyDeposit}(immutables, srcCancellationTimestamp)` where `immutables.token == address(0)` and `immutables.parameters = abi.encode(0 /*protocolFeeAmount*/, 1 /*integratorFeeAmount*/, address(0) /*protocolFeeRecipient*/, address(MaliciousReceiver) /*integratorFeeRecipient*/)`.
3. After `dstTimelocks.withdrawal`, call `dstClone.withdraw(secret, immutables)` — reverts with `NativeTokenSendingFailure` (confirmed by existing test pattern `test_NoFailedNativeTokenTransferWithdrawalDstNative`, `test/unit/Escrow.t.sol:762-789`).
4. Confirm `publicWithdraw` also reverts for any other caller during the public window.
5. After `RESCUE_DELAY`, taker calls `rescueFunds(address(0), amount, immutables)` and receives the locked ETH themselves, while the maker never received any destination funds.

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
