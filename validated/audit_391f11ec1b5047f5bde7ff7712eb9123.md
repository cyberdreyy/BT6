### Title
Unfunded pre-default instant-withdraw receipts are paid at par after default finalization, stealing the funded-claim balance - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The GTKWave bug is an index-driven arbitrary write: a crafted `.vcd` makes a binary search return a wrong slot and the code writes/reads through the wrong index. The idle-tranches analog is the same class of bug in `IdleCreditVault`'s per-epoch receipt ledgers: `instantWithdrawsRequestsByEpoch` is indexed by request epoch, but `claimInstantWithdrawRequest` only clears the `defaultRecoveryEpoch` slot and then pays the *aggregate* `instantWithdrawsRequests[_user]` at par. Instant receipts recorded in a *different* epoch than the default epoch are "looked up at the wrong index" — they escape the recovery haircut and are paid in full through `_transferFundedClaim`, spending underlying that belongs to legitimately funded claims.

### Finding Description
`requestInstantWithdraw` records receipts per epoch:

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

(`contracts/strategies/idle/IdleCreditVault.sol:366-374`)

After a default, `finalizeDefaultRecovery` computes the recovery basis as `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — i.e., only the *current* (default) epoch's instant claims enter the haircut basis via `defaultPendingClaimBasis` (lines 644-649). On claim, `claimInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and decrements the aggregate by that amount (lines 842-856), then unconditionally pays whatever remains in `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` (lines 387-392).

An attacker who has an instant receipt booked in `instantWithdrawsRequestsByEpoch[user][E]` for an earlier epoch `E != defaultRecoveryEpoch` (e.g., requested during a running epoch, never funded, and never claimed before epochs rolled over) passes through `_claimDefaultedInstantWithdrawRequest` with `claimBasis = 0`, leaving `instantWithdrawsRequests[user]` intact. That never-funded receipt is then paid 1:1 from the strategy's underlying balance. `_transferFundedClaim` only protects `defaultRecoveryReserve` (`balance - reserve < amount` reverts), so the payout silently consumes funds earmarked for other users' funded withdraw/instant claims.

### Impact Explanation
Direct theft / insolvency with a quantified loss: an attacker holding a stale unfunded instant receipt of size `A` withdraws `A` underlying at par while legitimate claimants with funded receipts later revert on insufficient balance. The broken invariant is "one receipt one payout, at the correct recovery price": receipts that were never funded and never included in the recovery basis are settled at 100% using other users' funded-claim liquidity.

### Likelihood Explanation
The attacker is an ordinary KYC'd lender. Steps: request an instant withdrawal that cannot be (or is deliberately timed not to be) collected before the epoch stops; let the epoch roll over (`stopEpoch` bumps `epochNumber` without clearing `instantWithdrawsRequests`); wait for a borrower default and `finalizeDefaultRecovery`; call `claimInstantWithdrawRequest` via the CDO. Feasibility depends on an instant request surviving an epoch boundary unfunded, which the per-epoch ledger design explicitly anticipates (requests are bucketed per epoch, and `pendingInstantWithdraws` tracks a still-unfunded remainder). No privileged misbehavior is required.

### Recommendation
In `claimInstantWithdrawRequest`, iterate/clear all per-epoch buckets (or track and deduct the full aggregate across `instantWithdrawsRequestsByEpoch`), and only pay at par receipts that were actually funded before default. Alternatively, include all outstanding `instantWithdrawsRequests` epochs (not just `epochNumber`) in `defaultPendingClaimBasis`, and reject at-par payment of any receipt whose epoch bucket was unfunded at finalization.

### Proof of Concept
Foundry fork PoC outline:

```solidity
// 1. Lender (attacker) deposits AA, epoch starts.
// 2. Attacker calls cdoEpoch.requestInstantWithdraw(...) -> strategy burns CDO
//    tokens, mints receipt, records instantWithdrawsRequestsByEpoch[attacker][E].
// 3. Borrower repays only partially / instant queue is not collected; manager
//    calls stopEpoch -> epochNumber becomes E+1, attacker receipt persists.
// 4. New epoch runs; borrower defaults (stopEpoch with shortfall), owner/manager
//    calls finalizeDefault(recovered, manager) -> defaultRecoveryFinalized,
//    basis includes only instantWithdrawClaimsByEpoch[E+1].
// 5. Attacker calls cdoEpoch.claimInstantWithdrawRequest():
//    _claimDefaultedInstantWithdrawRequest clears epoch E+1 slot (0 for attacker),
//    then instantWithdrawsRequests[attacker] = A is burned and paid at par via
//    _transferFundedClaim, consuming underlying reserved for other funded claims.
// Assert: attacker received A underlying; a subsequent legitimate funded claim
// reverts or the strategy balance < defaultRecoveryReserve + funded obligations.
```
