### Title
Multi-epoch withdraw receipts bypass `stopEpochWithDuration` loss haircut and drain funded claims at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` applies a single aggregate haircut (`lossRecoveryPriceByEpoch[epochNumber]`) over **all** pending receipts in `pendingWithdraws`, regardless of which epoch each receipt was requested in. However, `_claimLossAdjustedWithdrawRequest` only applies the haircut to receipts stored under `lastWithdrawRequest[_user]` — i.e., only the user's *latest* request epoch. Receipts a user opened in earlier epochs are paid out at par through `_claimFundedWithdrawRequest`, even though the funding collected at `stopEpoch` already assumed they were haircut. Early claimants can therefore withdraw more than their loss-adjusted share, leaving the strategy underfunded for later claimants (insolvency / permanent freezing of remaining claims).

### Finding Description
SQL injection is an unsanitized-input bug class: attacker-controlled data reaches a sensitive sink without validation. The analog here is epoch-scoped receipt data flowing into claim settlement without consistent keying — the "filter" (`lastWithdrawRequest`) does not match the "query" (aggregate `pendingWithdraws`).

In `collectWithdrawFunds`, when the borrower underfunds, the whole `pendingWithdraws` aggregate is haircut and `pendingWithdraws` is zeroed, storing the price under the *current* `epochNumber`:

- `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis`, then `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` [1](#0-0) 

The guard in `requestWithdraw` only blocks a new request when the user's `lastWithdrawRequest` epoch has an unclaimed loss price:

- `lossEpoch = lastWithdrawRequest[_user]; lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch]` and the revert only fires if receipts exist *in that epoch* [2](#0-1) 

But `withdrawsRequestsByEpoch[_user][e]` can be non-zero for several epochs `e`. At claim time, `_claimLossAdjustedWithdrawRequest` clears only the `lastWithdrawRequest` epoch at the haircut price, then `_claimFundedWithdrawRequest` pays the remaining `withdrawsRequests[_user]` — including earlier-epoch receipts that were part of the haircutted `pendingBasis` — at par:

- `claimBasis` is epoch-scoped via `_clearWithdrawClaimForEpoch(_user, lossEpoch, false)` [3](#0-2) 
- `amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount` pays the full residual aggregate [4](#0-3) 

### Impact Explanation
The funding invariant — total claimable ≤ `_amount` collected at `stopEpoch` — is broken. Suppose pending receipts of `P` are funded with `P * price` after a loss. A user holding receipts across two epochs receives `(latest epoch receipt) * price + (earlier receipts) * 1.0`, exceeding their `receipt * price` entitlement. The excess comes directly out of the strategy's funded balance, so later claimants' `safeTransfer` calls revert on insufficient balance — permanent freezing of other lenders' unclaimed, already-funded withdrawals. Broken invariant: one receipt, one loss-adjusted payout; aggregate funding solvency.

### Likelihood Explanation
Requires a `stopEpochWithDuration` partial-loss event (honest manager action) with at least one user holding pending receipts from multiple request epochs — achievable by any KYC-passing lender requesting withdrawals in consecutive epochs. No malicious privileged role needed; the attacker is an ordinary lender. Caveat I could not fully verify within this analysis: whether `epochNumber` increments (in `deposit()` during `stopEpoch`) before `collectWithdrawFunds` runs, which determines the exact key stored in `lossRecoveryPriceByEpoch` — if the stored key differs from the request epoch, the haircut is skipped entirely (`lossRecoveryPrice == 0` → early return), making the over-claim even broader. Either ordering leaves at least one under-priced claim path.

### Recommendation
Track the haircutted basis per epoch, not per user's last request. Options:
- Store the set of request epochs covered by each loss price (or iterate all `withdrawsRequestsByEpoch[_user][*]` entries and apply `lossRecoveryPriceByEpoch` per matching epoch), and subtract every cleared basis from a per-epoch funded pool.
- Alternatively, key `lossRecoveryPriceByEpoch` handling by summing `claimBasis` over all epochs for the user whenever any loss price exists, rather than relying on `lastWithdrawRequest`.
- Reject or settle all pre-loss receipts across every epoch in `_claimLossAdjustedWithdrawRequest` before allowing `_claimFundedWithdrawRequest` to run.

// Setup: lender L (KYC'd) deposits via IdleCDOEpochVariant during running epoch N-1.
// 1. L calls requestWithdraw -> withdrawsRequestsByEpoch[L][N-1] = a1, lastWithdrawRequest[L] = N-1

//    withdrawsRequestsByEpoch[L][N] = a2, lastWithdrawRequest[L] = N
// 3. Borrower underfunds: manager calls stopEpochWithDuration(_lossAmount) with
//    0 < _lossAmount < totalBasis. collectWithdrawFunds stores
//    lossRecoveryPriceByEpoch[epochNumber] = funded/(a1+a2+...) and zeroes pendingWithdraws.
// 4. L calls claimWithdrawRequest:
//    - _claimLossAdjustedWithdrawRequest pays a2 * price (epoch keyed by lastWithdrawRequest)
//    - _claimFundedWithdrawRequest then pays a1 at par  <-- over-claim
// 5. Other lenders' claims revert: strategy underlying balance exhausted.
// Invariant violated: sum(claims) > funded amount == pendingBasis * price.
```

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
