## Analysis

This is a real, reproducible bug rooted in an inconsistency between `BaseEscrowFactory.createDstEscrow` and `ImmutablesLib`'s calldata fee-decoding helpers.

**Root cause**

`createDstEscrow` has no access control and does not validate the format of `dstImmutables.parameters` at all — it only checks the funded native/ERC20 amounts and the cancellation timelock ordering: [1](#0-0) 

`ImmutablesLib`'s calldata getters each perform an **independent** minimum-length check instead of enforcing the full expected 0x80-byte (4-word) layout up front: [2](#0-1) 

`EscrowDst._withdraw` (used by both `withdraw` and `publicWithdraw`) reads `integratorFeeAmountCd()` (needs ≥0x40) and, if non-zero, immediately calls `integratorFeeRecipientCd()` (needs ≥0x80): [3](#0-2) 

With a crafted 96-byte (`0x60`) `parameters` blob whose second word (integrator fee amount) is non-zero, `protocolFeeAmountCd()` and `integratorFeeAmountCd()` both succeed (0x60 ≥ 0x20/0x40), but `integratorFeeRecipientCd()` reverts with `IndexOutOfRange` because 0x60 < 0x80. Since `_withdraw` is the single internal function shared by both `withdraw()` (taker-only) and `publicWithdraw()` (any access-token holder), **both paths revert identically** — there is no fallback that lets the public path succeed where the private path fails. [4](#0-3) 

The only surviving recovery routes are `cancel()` and `rescueFunds()`, both gated by `onlyCaller(immutables.taker.get())` — i.e., only the same account that created the malformed escrow can recover the funds, and `cancel()` sends `immutables.amount` back to the taker, not the maker: [5](#0-4) 

### Title
Unvalidated `parameters` length in `createDstEscrow` bricks both private and public `EscrowDst` withdrawal paths - (File: contracts/EscrowDst.sol, contracts/libraries/ImmutablesLib.sol, contracts/BaseEscrowFactory.sol)

### Summary
`createDstEscrow` accepts an attacker-controlled, arbitrary-length `parameters` byte blob without validating that it encodes a self-consistent 128-byte fee-metadata structure. `ImmutablesLib`'s per-field length checks (`0x20`/`0x40`/`0x60`/`0x80`) are independent rather than holistic, so a 96-byte blob can pass the fee-amount check while failing the corresponding fee-recipient check. Because `EscrowDst._withdraw` is shared by both `withdraw()` and `publicWithdraw()`, this single malformed-parameters escrow permanently reverts on both the private and the "public safety-net" withdrawal path.

### Impact Explanation
Once such a destination escrow is deployed and funded, maker payout can never be finalized via `withdraw()` or `publicWithdraw()` even with a valid secret — defeating the entire purpose of `publicWithdraw` as an unprivileged fallback. Funds remain locked until `DstCancellation`, and even then only the original taker (escrow creator) can recover them via `cancel()` — which sends the destination amount back to the taker, not the maker — or via `rescueFunds()`. This fits the "High: temporary freezing of funds during the live swap lifecycle" bucket at minimum; because recovery funnels tokens back to the taker rather than the maker, it can also be viewed as a mechanism for a malicious taker to keep destination funds that were supposed to go to the maker.

### Likelihood Explanation
`createDstEscrow` has no access-control restricting who can call it or what `parameters` bytes are supplied, so any unprivileged actor funding a destination escrow themselves controls this field entirely. No further privilege (owner/governance/off-chain trust) is required to trigger the on-chain revert condition described.

### Recommendation
In `ImmutablesLib`, replace the four independent minimum-length checks with a single validation that `parameters.length` is either `0` (no fees) or exactly `0x80` (full fee metadata), and reject any other length as invalid immutables — ideally enforced once in `createDstEscrow` (or in `_validateImmutables`) rather than lazily per-field inside `_withdraw`.

### Proof of Concept
1. Attacker (any unprivileged address) calls `createDstEscrow` with `dstImmutables.amount`/`safetyDeposit` correctly funded, but `parameters = abi.encode(protocolFeeAmount, integratorFeeAmount)` truncated/padded to exactly 96 bytes (e.g. via manual calldata crafting) where `integratorFeeAmount > 0`.
2. `createDstEscrow` deploys and funds the clone without validating `parameters` shape: [1](#0-0) 
3. Warp to `DstWithdrawal`; call `withdraw(secret, immutables)` as taker → reverts `IndexOutOfRange` in `integratorFeeRecipientCd()`.
4. Warp to `DstPublicWithdrawal`; call `publicWithdraw(secret, immutables)` as any access-token holder → identical revert, since both funnel through `_withdraw`: [6](#0-5) 
5. Maker payout is unreachable until `DstCancellation`, at which point only the taker can reclaim funds via `cancel()`.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function protocolFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;
        if (parameters.length < 0x20) revert IndexOutOfRange();
        assembly ("memory-safe") {
            ret := calldataload(parameters.offset)
        }
    }
