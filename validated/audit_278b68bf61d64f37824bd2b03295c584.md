### Title
Builder payment destination (`fee_recipient`) is never bound to the proposer's committed preference, allowing payment to be misdirected - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_execution_payload_bid` accepts and honors an arbitrary `bid.fee_recipient` supplied and signed solely by the builder, with no state-transition check binding it to the address the proposer actually requested via `SignedProposerPreferences`. The spec text that lists what a compliant proposer/validator "MUST" verify before including a bid also omits this check. As a result, the Gwei amount the builder commits to pay for the slot can be routed to any address the builder chooses (including the zero address or a third party) instead of the proposer who is supposed to receive it — an equality (`payment.fee_recipient == proposer's declared/authorized address`) that the protocol never actually enforces on-chain.

### Finding Description
In `specs/gloas/beacon-chain.md`, `process_execution_payload_bid` records the pending payment using `bid.fee_recipient` exactly as provided by the builder in the signed bid, with `proposer_index` only used for bookkeeping/weight accrual, not for validating the payment address: [1](#0-0) 

Neither this function nor `settle_builder_payment` / `apply_parent_execution_payload` ever compares `fee_recipient` against anything tied to the block's proposer: [2](#0-1) [3](#0-2) 

The intended binding is described only as off-protocol guidance to the *builder* when constructing the bid: the builder is told to look up the proposer's `SignedProposerPreferences` and copy the preferred `fee_recipient`, but this is advisory, not enforced: [4](#0-3) 

Crucially, the list of conditions a proposer/validator MUST verify before including a bid in `validator.md` mirrors exactly the asserts in `process_execution_payload_bid` and does **not** include verifying `bid.fee_recipient` against the proposer's own preferences: [5](#0-4) 

Gossip validation for `execution_payload_bid` likewise never checks `fee_recipient` against the current proposer's preferences — it only checks signature validity, builder activity/version, balance coverage, and bid compatibility: [6](#0-5) 

`SignedProposerPreferences` (the only on-chain-adjacent record of the proposer's intended `fee_recipient`) is purely a gossip-layer artifact, validated only by gossip rules, never referenced or asserted against inside `process_execution_payload_bid`: [7](#0-6) 

So the equality that should hold — "the amount the builder owes for this slot is paid to the address the block's proposer designated" — is never checked by the state-transition function. A builder that is otherwise fully spec-compliant (correct signature, sufficient balance, correct slot/parent/hash fields) can set `bid.fee_recipient` to any address, and `process_execution_payload_bid` will accept it and queue the withdrawal to that address once settled.

### Impact Explanation
This falls under "a builder payment or withdrawal misdirected" (High impact per the given criteria). The Gwei that should be paid to the block's proposer for accepting the bid can instead be sent to an address of the builder's own choosing (including the zero address, which destroys the payment, or the builder's own address, which effectively cancels the payment while still consuming the proposer's inclusion). This is not merely the builder losing its own stake — it is the proposer's earned/expected payment being diverted without their authorization, since the spec provides no mechanism for the proposer or the chain to detect or reject this at inclusion time via the defined MUST-verify list.

### Likelihood Explanation
No coalition, client bug, or network partition is required. Any single active builder can submit a validly signed, otherwise fully-conforming `SignedExecutionPayloadBid` with a `fee_recipient` that does not match the proposer's broadcast `SignedProposerPreferences`. Because neither gossip validation nor `process_execution_payload_bid` nor the validator.md "MUST" checklist verifies this field against the preferences, a proposer implementing the spec exactly as written (relying on the documented MUST-list) has no spec-mandated basis to reject such a bid.

### Recommendation
Add an explicit binding in the protocol: either (a) include `fee_recipient` verification as an additional MUST condition in `validator.md`'s bid-selection checklist and as a gossip-validation REJECT condition against the proposer's most recent valid `SignedProposerPreferences` for the slot, or (b) have `process_execution_payload_bid` derive/assert the payment address from state rather than trusting the builder-supplied field, so the payment destination is provably tied to the slot's actual proposer.

### Proof of Concept
1. Proposer P for slot `S` broadcasts `SignedProposerPreferences` with `fee_recipient = X`.
2. Builder B, who is active, has sufficient balance, and behaves correctly on every other field, constructs `ExecutionPayloadBid` with `fee_recipient = 0x00...00` (or any address `Y != X`), correct `parent_block_hash`, `parent_block_root`, `prev_randao`, `slot`, and signs it validly.
3. Per `validate_execution_payload_bid_gossip` (specs/gloas/p2p-interface.md:991-1036) the bid passes all REJECT/IGNORE checks — `fee_recipient` is never inspected.
4. Proposer P selects this (e.g., highest-value) bid and includes it, satisfying every condition in `validator.md`'s checklist (lines 204-219), none of which reference `fee_recipient`.
5. `process_execution_payload_bid` (specs/gloas/beacon-chain.md:2084-2141) accepts the bid, records `BuilderPendingWithdrawal(fee_recipient=Y, amount=bid.value, builder_index=B)`.
6. When the payment settles (`settle_builder_payment`, specs/gloas/beacon-chain.md:1518-1527 and `apply_parent_execution_payload`, specs/gloas/beacon-chain.md:1754-1770), `amount` is paid out to `Y`, not to `X` — the proposer's actual designated address — with no assertion anywhere in the state transition catching the mismatch.

##### Signed execution payload bid

To obtain `signed_execution_payload_bid`, a block proposer building a block on
top of a `state` MUST take the following actions in order to construct the
`signed_execution_payload_bid` field in `BeaconBlockBody`:

- Listen to the `execution_payload_bid` gossip global topic and save an accepted
  `signed_execution_payload_bid` from a builder. The block proposer MAY obtain
  these signed messages by other off-protocol means.
- The `signed_execution_payload_bid` MUST satisfy the verification conditions
  found in `process_execution_payload_bid` with the alias
  `bid = signed_execution_payload_bid.message`, that is:
  - For external builders, the signature MUST be valid.
  - For self-builds, set `bid.builder_index` to `BUILDER_INDEX_SELF_BUILD`.
  - For self-builds, the signature MUST be `bls.G2_POINT_AT_INFINITY` and the
    `bid.value` MUST be zero.
  - The builder balance can cover the `bid.value`.
  - The `bid.slot` is for the proposal block slot.
  - The `bid.parent_block_hash` equals
    `state.latest_execution_payload_bid.block_hash` if
    `should_build_on_full(store, head, get_current_slot(store))` is true,
    otherwise `state.latest_execution_payload_bid.parent_block_hash`.
  - The `bid.parent_block_root` equals the current block's `parent_root`.
  - The `bid.prev_randao` equals
    `get_randao_mix(state, get_current_epoch(state))`.
- Select one bid and set
  `block.body.signed_execution_payload_bid = signed_execution_payload_bid`.

*Note*: The execution address encoded in the `fee_recipient` field in the
`signed_execution_payload_bid.message` will receive the builder payment.
