### Title
Loss haircut from `stopEpochWithDuration` only applies to the user's latest request epoch; older pending receipts escape the haircut and claim at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to `partial_sha256_var_start` silently ignoring the trailing bytes that don't fill a full block, `IdleCreditVault` tracks a user's loss-adjusted withdrawal receipts through the single-epoch marker `lastWithdrawRequest`. When `collectWithdrawFunds` under-funds `pendingWithdraws`, it records one `lossRecoveryPriceByEpoch[epochNumber]` for the whole aggregate pending bucket, but `_claimLossAdjustedWithdrawRequest` only clears the receipts stored under `withdrawsRequestsByEpoch[user][lastWithdrawRequest[user]]`. Receipts the same user opened in earlier epochs and never claimed stay in the aggregate `withdrawsRequests[user]` and are later paid at par via `_claimFundedWithdrawRequest`, even though the funding for them was haircut. The user is overpaid and the funded balance is drained at the expense of other pending receipt holders.

### Finding Description
`requestWithdraw` records the request amount both in the aggregate `withdrawsRequests[_user]` and per-epoch in `withdrawsRequestsByEpoch[_user][currentEpoch]`, and overwrites `lastWithdrawRequest[_user] = currentEpoch` on every request (contracts/strategies/idle/IdleCreditVault.sol:282-293). Nothing forces a user to claim a matured receipt before opening a new one; the only pre-claim guard is the loss-epoch check at lines 263-271, which only inspects the single epoch pointed to by `lastWithdrawRequest`.

When an epoch stops with a loss (`stopEpochWithDuration` / under-funded `collectWithdrawFunds`), `lossRecoveryPriceByEpoch[epochNumber] = funded / pendingBasis` is stored once for the entire pending bucket and `pendingWithdraws` is zeroed (lines 411-421). The bucket, however, can contain receipts from multiple request epochs for the same user.

At claim time, `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` and clears only `withdrawsRequestsByEpoch[user][lossEpoch]` via `_clearWithdrawClaimForEpoch` (lines 789-800, 811-820). It then calls `_claimFundedWithdrawRequest`, which pays out the whole remaining `withdrawsRequests[user]` aggregate at par (lines 338-349). So the earlier-epoch "tail" of the user's pending basis — which was funded at the haircut price — is paid at 100%.

Concretely: funded balance = `price * (A_old + B_new)`. The user receives `B_new * price + A_old`, i.e. an excess of `A_old * (1 - price)` over what was funded. With multiple users doing this, or one user and other honest claimants, the strategy's funded balance is exhausted before all receipts are paid — later claimants' `_transferFundedClaim` either underpays or reverts, producing insolvency/permanent freezing of unclaimed funded withdrawals.

APR0 receipts amplify the same gap: an `apr0Users[user].principal` bucket whose `principalEpoch` differs from `lastWithdrawRequest` is never cleared by `_claimLossAdjustedWithdrawRequest` and is also paid at par in `_claimFundedWithdrawRequest` (line 339).

### Impact Explanation
Direct theft/insolvency: a KYC-passing lender (or any tranche holder) receives more underlying than the loss-adjusted funding provided for their receipts. The excess is paid from the strategy balance that backs other users' pending receipts and the default recovery reserve, so honest withdrawers suffer a shortfall or their claims freeze. Loss scales with `A_old * (1 - lossRecoveryPrice)`; with a 50% haircut and equal-sized requests the attacker extracts 25% of their total pending basis on top of their fair share.

### Likelihood Explanation
Requires an epoch ending with under-funded pending withdrawals (`stopEpochWithDuration` with `_lossAmount > 0`, i.e. a partial borrower repayment). The attacker only needs to (a) request a withdrawal in epoch N and deliberately not claim it, (b) request again in epoch N+1, then (c) claim after the lossy stop. No privileged action is needed; not claiming a receipt is a normal, permitted state (the code explicitly supports delayed claims: "Once the epoch is over user can withdraw at any time"). The existing guard at lines 263-271 does not catch this because it only inspects `lastWithdrawRequest`, which the second request has already overwritten to the new epoch.

### Recommendation
Apply the recovery price to the entire pending basis of the user, not only the `lastWithdrawRequest` epoch. Options:
- In `_claimLossAdjustedWithdrawRequest`, iterate/clear all per-epoch receipt entries contributing to `withdrawsRequests[user]` (and open APR0 buckets) and pay each at `lossRecoveryPrice`, since `collectWithdrawFunds` haircut the aggregate bucket; or
- Track per-epoch pending basis (e.g. `pendingWithdrawsByEpoch`) and store the loss price for every epoch that contributed to the cleared `pendingWithdraws`; or
- Revert in `requestWithdraw` whenever the user still has any unclaimed receipt (`_hasWithdrawRequest(_user)`), not only when the latest epoch has a loss price — forcing users to settle the "tail" before opening a new request.

### Proof of Concept
Foundry fork PoC sketch (two epochs, one lossy stop):

```solidity
function testLossHaircutSkipsOlderEpochReceipt() external {
    // setup: deposit AA, epoch running, then stopped normally (epochNumber = 1)
    idleCDO.depositAA(10_000e18);
    _transferBurnedTrancheTokens(attacker, true);
    _startEpoch(); 
    _stopEpoch(0, 0); // epoch 1 ends fully funded

    // Request A in epoch 1's aftermath; do NOT claim (deliberately delayed claim)
    uint256 reqA = cdoEpoch.requestWithdraw(amountA, AAtranche); // lastWithdrawRequest = 1

    _startEpoch(); // epoch 2 running
    _stopEpoch(0, 0); // epoch 2 ends; receipt A is now claimable but still unclaimed

    // Request B now; lastWithdrawRequest overwritten to epoch 2
    uint256 reqB = cdoEpoch.requestWithdraw(amountB, AAtranche); // lastWithdrawRequest = 2

    _startEpoch(); // epoch 3 running; pendingWithdraws = reqA + reqB

    // Borrower only returns half -> stopEpochWithDuration loss path
    uint256 pending = strategy.pendingWithdraws(); // = reqA + reqB
    uint256 funded = pending / 2;
    deal(underlying, borrower, funded + expectedInterest);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, expectedInterest); // collectWithdrawFunds(funded) -> lossRecoveryPriceByEpoch[2] = 0.5e18

    // Attacker claims once:
    // _claimLossAdjustedWithdrawRequest pays reqB * 0.5 (only epoch-2 piece)
    // _claimFundedWithdrawRequest then pays reqA at PAR
    uint256 balPre = underlying.balanceOf(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    uint256 fair = (reqA + reqB) * strategy.lossRecoveryPriceByEpoch(2) / 1e18;
    assertEq(paid, reqA + reqB / 2);        // actual payout
    assertGt(paid, fair);                    // attacker overpaid by reqA * (1 - price)
    // Strategy funded balance now insufficient for other pending receipts -> insolvency
}
```

Key invariant violation: `collectWithdrawFunds` applied `lossRecoveryPrice` to the whole `pendingWithdraws` aggregate, but `_claimLossAdjustedWithdrawRequest` only debits `withdrawsRequestsByEpoch[user][lastWithdrawRequest[user]]`, leaving the older-epoch remainder claimable at par.
