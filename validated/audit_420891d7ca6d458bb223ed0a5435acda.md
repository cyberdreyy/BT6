### Title
`confirm` executes requests using stale confirmations from removed multisig members - (File: `multisig2/src/lib.rs`)

### Summary
The `confirm` function's execution threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` counts every entry ever inserted into the request's `HashSet<String>`, without verifying those entries still correspond to accounts in `self.members`. `delete_member`'s cleanup only purges requests authored by the removed member (`r.member == member`) and never scans the `confirmations` sets of other pending requests for stale entries from that member, so a request confirmed by members who are later removed can still execute counting their stale votes.

### Finding Description
The broken binding is: **number of confirming entries counted at execution == number of DISTINCT CURRENT members who confirmed**. In reality, `confirm` at [2](#0-1)  only checks `confirmations.len() as u32 + 1 >= self.num_confirmations`, where `confirmations` is the raw `HashSet<String>` fetched from storage, with no filter against `self.members`.

`assert_valid_request`, invoked at the top of `confirm`, at [3](#0-2)  only validates that the *caller* is a current member (`self.current_member().is_some()`) and that the request/confirmations entries exist — it never re-validates that pre-existing entries in `confirmations` are still members.

`delete_member`, at [4](#0-3) , enforces `self.members.len() - 1 >= self.num_confirmations` only against the removal at hand, and its cleanup loop `self.requests.iter().filter_map(|(k, r)| if r.member == member { Some(k) } else { None })` only removes requests *authored* by the removed member — it never scans other requests' `confirmations: HashSet<String>` to strip out the removed member's stale confirmation entry.

Exploit flow (4 members M1,M2,M3,M4; `num_confirmations=3`):
1. M1 calls `add_request(R)` (e.g. a `Transfer`), M1 and M2 call `confirm(R)` — `confirmations = {M1, M2}`, 2 < 3, not executed yet.
2. Members submit and confirm a `DeleteMember{M1}` request; when it executes, `delete_member` checks `4-1=3 >= 3` — passes. Members now `{M2,M3,M4}`. R's stale `confirmations` set still contains `M1` (untouched, since R was not authored by M1).
3. To remove a second member, `delete_member`'s own assert would need `3-1=2 >= num_confirmations`. Members first approve a `SetNumConfirmations{2}` request (requires the current 3-of-3 threshold, achievable using the 3 live members), lowering `num_confirmations` to 2.
4. Members approve `DeleteMember{M2}`; now `3-1=2 >= 2` passes. Members become `{M3,M4}`. R's `confirmations` set still contains stale `{M1, M2}`.
5. M3 (a live member) calls `confirm(R)`. `assert_valid_request` passes (M3 is current member). `confirmations.len() as u32 + 1 = 2 + 1 = 3 >= self.num_confirmations (2)` → true → R executes immediately via `execute_request`, backed by only **one** live confirmer (M3) plus two stale confirmations from removed members M1 and M2.

This directly executes a multisig request below the number of live confirming members required, satisfying the "Critical" impact category explicitly listed in scope ("a multisig request executed below `num_confirmations` live members").

### Impact Explanation
An attacker who is (or becomes, through legitimate membership changes) one of the surviving members can get an arbitrary pending request — including a `Transfer` of the multisig's NEAR balance, an `AddKey` granting full access, or a `FunctionCall` — executed while only a minority of *current* live members actually approved it in its final membership configuration. This moves NEAR out of the multisig account without genuine authorization from the required threshold of live signers, matching the Critical severity bucket. The bug is repeatable on any multisig instance deployed via the public `multisig-factory` wherever membership can be rotated over the lifetime of a pending request.

### Likelihood Explanation
The attack requires the attacker (or colluding members) to control enough of the membership-change approval flow to remove confirmers of a target request and to potentially lower `num_confirmations` via a separate approved `SetNumConfirmations` request — both are normal, in-scope multisig operations reachable by members controlling the required threshold at each step, no protocol bug is needed to perform them, only patience and sequencing. No special privileges beyond being a multisig member are needed, and it requires no exploitation of overflow or storage corruption — purely business-logic sequencing. Given multisig membership rotation (onboarding/offboarding signers) is an expected real-world operation, and pending requests can be long-lived (`REQUEST_COOLDOWN` and `active_requests_limit` gate deletion but not confirmation), this is practically reachable.

### Recommendation
On `confirm`, filter (or reconstitute) the `confirmations` set against current `self.members` before comparing against `self.num_confirmations`, e.g., recompute `confirmations.iter().filter(|c| self.members.contains(&member_from_string(c))).count()`. Additionally, `delete_member` should scan all pending requests' `confirmations` sets (not just requests authored by the removed member) and strip any entry matching the removed member's `to_string()`, so stale votes cannot silently persist and later count toward execution.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
