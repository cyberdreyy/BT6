## Title
LockupFactory lets the lockup owner supply an arbitrary "staking pool whitelist" contract, letting them bypass the foundation-approved whitelist and drain locked/unvested NEAR to a self-controlled staking pool - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` accepts an optional `whitelist_account_id: Option<ValidAccountId>` from the caller and, if present, uses it verbatim as the `staking_pool_whitelist_account_id` embedded in the newly deployed lockup contract's arguments, instead of forcing the foundation-controlled whitelist account. [1](#0-0) 

### Finding Description
The whitelist contract's entire purpose is to guarantee that a lockup only delegates to staking pools that are "faithfully implement[ing] the spec," so that delegated (including unvested/locked) tokens cannot be lost or diverted, and only the NEAR Foundation (or a foundation-whitelisted factory) may add entries to it. [2](#0-1) [3](#0-2) 

However, `LockupFactory::create` lets the account calling `create` (the future lockup owner) choose *its own* `whitelist_account_id` instead of the factory's configured, foundation-approved `whitelist_account_id`: [4](#0-3) 

This attacker-chosen account ID is placed straight into `LockupArgs.staking_pool_whitelist_account_id`, which is passed to the lockup contract's `new` constructor with no validation that it is the legitimate whitelist: [5](#0-4) 

Inside the deployed lockup contract, `select_staking_pool` trusts whatever `is_whitelisted` result comes back from `self.staking_pool_whitelist_account_id` and, if `true`, unconditionally records the given `staking_pool_account_id` as the trusted staking pool for all future deposits/stake/withdraw operations - there is no cross-check that this whitelist account is the canonical foundation whitelist: [6](#0-5) [7](#0-6) 

Because the caller of `create` fully controls `whitelist_account_id`, an attacker can deploy their own contract at an arbitrary account exposing an `is_whitelisted` view method that always returns `true` for any staking pool they name, and pass that account as `whitelist_account_id` to `create`. The resulting lockup will trust an attacker-chosen malicious "staking pool" account as if it had been vetted by the foundation. The lockup owner can then `select_staking_pool` on their evil pool, `deposit_and_stake` locked/unvested tokens into it, and have that contract simply keep the funds (never returning them on `unstake`/`withdraw`), permanently diverting tokens that - for vesting lockups - the foundation is entitled to reclaim on termination.

This breaks the custody binding the whitelist system is meant to enforce: **an account trusted as a staking pool should equal an account actually vetted via the foundation's whitelist**, not an account supplied ad hoc by the very party (the lockup owner) whose access to those funds the whitelist is supposed to constrain.

### Impact Explanation
For vesting/lockup deployments, the tokens held by the lockup contract are not unconditionally the owner's - unvested tokens are subject to the foundation's termination/reclaim rights, and the whitelist mechanism exists specifically so that locked/unvested balances cannot be moved to pools that could withhold them. By supplying a self-controlled fake whitelist account at `create` time, the (otherwise unprivileged, non-owner-of-the-funds-yet) lockup creator/owner can whitelist an arbitrary malicious "staking pool," delegate locked/unvested NEAR to it, and have that malicious contract retain the funds. This is a "wrongly whitelisted or wrongly parameterised deployment" leading to locked/unvested tokens being released/diverted early and outside the foundation's control - a Critical impact per the scope's own definition ("a wrongly whitelisted or wrongly parameterised deployment ... locked or unvested tokens released early").

### Likelihood Explanation
Any account can call `LockupFactory::create` and simply supply the `whitelist_account_id` parameter pointing at a contract they deployed themselves; no special privilege, foundation approval, victim key, or redeploy of in-scope code is required-only deploying an auxiliary attacker-controlled account. This is directly reachable through the public, documented API of `lockup-factory`.

### Recommendation
Remove the caller-suppliable `whitelist_account_id` parameter from `LockupFactory::create`, and always use the factory's own configured `whitelist_account_id` (set at factory `new` / owned by the foundation) when constructing `LockupArgs`, so lockup contracts can never be initialized with a whitelist that wasn't approved by the foundation.

### Proof of Concept
1. Attacker deploys `EvilWhitelist` account whose `is_whitelisted(staking_pool_account_id)` always returns `true`.
2. Attacker deploys `EvilPool` staking pool account that accepts deposits/stake but never returns funds on `unstake`/`withdraw`.
3. Attacker calls `lockup-factory.create(owner_account_id: attacker, ..., vesting_schedule: Some(...), whitelist_account_id: Some(EvilWhitelist))`, satisfying `MIN_ATTACHED_BALANCE`. [1](#0-0) 
4. The deployed lockup is initialized with `staking_pool_whitelist_account_id = EvilWhitelist`.
5. Attacker (as lockup owner) calls `select_staking_pool(EvilPool)`; the lockup queries `EvilWhitelist.is_whitelisted(EvilPool)`, gets `true`, and stores `EvilPool` as the trusted staking pool. [6](#0-5) [7](#0-6) 
6. Attacker calls `deposit_and_stake` to move locked/unvested NEAR to `EvilPool`, which never returns it - permanently diverting funds the foundation should have been able to reclaim on vesting termination.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

# Whitelist contract for staking pools

The purpose of this contract is to maintain the whitelist of the staking pool contracts account IDs that are approved
by NEAR Foundation.

In order for the lockup contracts to be able delegate to a staking pool, the staking pool should faithfully implement the spec.
The staking pool should guarantee that the delegated tokens can not be lost or locked, such as the lockup contract should be
able to recover delegated tokens back to the lockup from a staking pool. In order to enforce this, only approved (whitelisted)
accounts of staking pool contracts can receive delegated tokens from lockup contracts.

If NEAR Foundation has to approve every single staking pool account it might lead to a bottleneck and centralization
To address this NEAR Foundation can whitelist the account IDs of staking pool factory contracts.

The whitelisted staking pool factory contract will be able to whitelist accounts of staking pool contracts.
A factory contract creates and initializes a staking pool contract in a secure and permissionless way.
This allows anyone on the network to be able to create a staking pool contract for themselves without needing approval from the NEAR
Foundation. This is important to maintain the decentralization of the decision making and network governance.

To be able to address mistakes, NEAR Foundation has the ability to remove staking pools and staking pool factories from the whitelists.

        if !self

        }

    pub fn select_staking_pool(&mut self, staking_pool_account_id: AccountId) -> Promise {
        self.assert_owner();
        assert!(
            env::is_valid_account_id(staking_pool_account_id.as_bytes()),
            "The staking pool account ID is invalid"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();

        env::log(
            format!(
                "Selecting staking pool @{}. Going to check whitelist first.",
                staking_pool_account_id
            )
            .as_bytes(),
        );

        ext_whitelist::is_whitelisted(
            staking_pool_account_id.clone(),
            &self.staking_pool_whitelist_account_id,
            NO_DEPOSIT,
            gas::whitelist::IS_WHITELISTED,
        )
        .then(ext_self_owner::on_whitelist_is_whitelisted(
            staking_pool_account_id,
            &env::current_account_id(),
            NO_DEPOSIT,
            gas::owner_callbacks::ON_WHITELIST_IS_WHITELISTED,
        ))
    }

    /// Called after a given `staking_pool_account_id` was checked in the whitelist.
    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,
        staking_pool_account_id: AccountId,
    ) -> bool {
        assert_self();
        assert!(
            is_whitelisted,
            "The given staking pool account ID is not whitelisted"
        );
        self.assert_staking_pool_is_not_selected();
        self.assert_no_termination();
        self.staking_information = Some(StakingInformation {
            staking_pool_account_id,
            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
        });
        true
    }
