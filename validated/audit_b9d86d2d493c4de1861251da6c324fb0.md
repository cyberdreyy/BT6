### Title
Excess `msg.value` in `withdrawAA`/`withdrawBB` is permanently locked in the per-request `EthenaCooldownRequest` clone - (File: contracts/IdleCDOEthenaVariant.sol)

### Summary
`IdleCDOEthenaVariant._withdraw` forwards `msg.value` into a freshly created `EthenaCooldownRequest` clone via `ClonesWithImmutableArgs.clone(..., msg.value)`. The clone has no ETH withdrawal path — its `rescue()` only sweeps ERC20 balances and only `TL_MULTISIG` can call it — so any ETH sent along with a tranche withdrawal is permanently locked in the clone. This mirrors the GluexRouter bug where excess `msg.value` is forwarded to a contract that cannot return it.

### Finding Description
Tranche withdrawals enter through `IdleCDO.withdrawAA`/`withdrawBB`, which are `payable` (otherwise the `msg.value` forwarded at line 84 would always be zero and the clone-call parameter would be dead code). `_withdraw` then executes:

```solidity
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
    abi.encodePacked(address(this), msg.sender),
    msg.value
));
``` [1](#0-0) 

ETH has no role in the withdrawal flow: the user burns tranche tokens and receives sUSDe proceeds via `clone.unstake()` which calls `IStakedUSDeV2.unstake(_getUser())` — an ERC20 transfer to the user, not ETH. [2](#0-1) 

The clone contract exposes only `startCooldown()`, `unstake()`, and `rescue(address _token)`. `rescue` performs `IERC20Detailed(_token).transfer(...)`, which cannot move the native ETH balance, and is restricted to `TL_MULTISIG` anyway. [3](#0-2) 

Because `ClonesWithImmutableArgs.clone` forwards value at `CREATE` time, no `receive()`/`fallback` is required for the ETH to be accepted — it simply sits in the clone's balance forever.

### Impact Explanation
Any user who attaches ETH to a `withdrawAA`/`withdrawBB` call (e.g., batching through a multicall or an integration that forwards `msg.value`) permanently loses that ETH. There is no privileged or unprivileged recovery path for native balance in `EthenaCooldownRequest`, so the loss is unrecoverable — worse than the GluexRouter case, where a permissionless executor could still move the funds. Loss is bounded by the ETH attached to each withdrawal call.

### Likelihood Explanation
The code path is live in the Ethena variant whenever `cooldownDuration() != 0` (the normal operating mode for sUSDe). [4](#0-3)  Likelihood depends on a user errantly sending ETH, so it is user-error driven rather than attacker-driven; however smart-wallet/router integrations that forward call value make accidental ETH attachment plausible, and the `payable` signature provides no guard.

### Recommendation
Do not forward value into the clone, and reject ETH on withdrawals:

```diff
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
-    abi.encodePacked(address(this), msg.sender),
-    msg.value
+    abi.encodePacked(address(this), msg.sender)
));
```

and add `require(msg.value == 0)` in `_withdraw` (or make `withdrawAA`/`withdrawBB` non-payable for this variant).

### Proof of Concept
A Foundry fork test (mainnet, since `cooldownImpl` and `SUSDE` are hardcoded mainnet addresses) would:

```solidity
// fork mainnet; vm.deal(user, 1 ether)
// deposit sUSDe-backed underlying, receive AA tranche tokens
// then:
vm.prank(user);
cdo.withdrawAA{value: 0.5 ether}(amount); // payable entry
// predicted clone address = Clones.predictDeterministicAddress(cooldownImpl, args)
assertEq(clone.balance, 0.5 ether);
// clone.rescue cannot move ETH; unstake only returns sUSDe to user
// ETH is unrecoverable
```

Uncertainty note: the index returned no line contents for `IdleCDO.sol`, so I could not directly cite the `payable` keyword on `withdrawAA`/`withdrawBB`. The `msg.value` forwarding at `IdleCDOEthenaVariant.sol:84` strongly implies the withdraw entry point is payable; if it were not, this issue reduces to dead code and the finding would not be valid.
