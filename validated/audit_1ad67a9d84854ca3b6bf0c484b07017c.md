### Title
Late-epoch deposit followed by `requestWithdraw` locks a full epoch of unearned interest into a fixed claim, leaving the pool short - (contracts/IdleCDOEpochVariant.sol)

### Summary
In JOJO, a trader could withdraw collateral up to the liquidation boundary against a temporary mark-to-market gain, leaving the protocol with bad debt when the gain reverted. The closest analog in `idle-tranches` is the fixed withdrawal receipt created by `requestWithdraw`: the receipt is priced at request time as `principal + projected interest`, and the interest component is always the **full epoch** tranche interest share, independent of how long the requester's tranche tokens existed or when in the epoch the request is made. Combined with `depositDuringEpoch`, which mints shares at a price that only credits the depositor for the *remaining* epoch time, an attacker can deposit late in an epoch, immediately request a withdrawal, and lock a receipt that pays a full epoch of interest on capital that was only deployed for a fraction of the epoch.

### Finding Description
`_calcInterestWithdrawRequest` (contracts/IdleCDOEpochVariant.sol:856-878) computes:

```solidity
uint256 totInterest = _calcInterest(_managedContractValue()) * _duration / (_duration + _buffer);
uint256 totTrancheInterest = _calcTrancheInterestShare(totInterest, _tranche);
uint256 _trancheBal = _lastSavedNAV(_tranche);
_interest = _trancheBal == 0 ? 0 : _amount * totTrancheInterest / _trancheBal;
```

`_duration` is `epochDuration`, i.e. the whole epoch. There is no scaling by `(epochEndDate - block.timestamp)`, no per-user accrual checkpoint, and no record of when the shares backing the request were minted. Every request — whether made on day 1 or in the buffer period after `epochEndDate` — is entitled to the same full-epoch interest share.

In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791) the receipt is then fixed in underlying terms:

```solidity
_underlyings = principal + interest - totalFees;
creditVault.requestWithdraw(_underlyings, msg.sender, principal);
```

and `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:271-294) mints the user a strategy-token receipt for the interest-inclusive `_amount` and adds it to `pendingWithdraws`, a cash liability the borrower must fund at the next `stopEpoch` (`getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)`, contracts/IdleCDOEpochVariant.sol:408).

Meanwhile the epoch deposit path (the `depositDuringEpoch`-style mint, contracts/IdleCDOEpochVariant.sol:691-733) deliberately prices mid-epoch deposits so they only earn interest for the *remaining* time:

```solidity
uint256 interest = _calcInterest(_amount) * (remaining + buffer) / (epochDuration + buffer);
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
```

So a share minted with `(remaining + buffer)/(epochDuration + buffer)` of an epoch of interest is redeemable, via `requestWithdraw`, for a share priced with a *full* epoch of interest. The receipt is denominated in underlyings, is enforced against the borrower at `stopEpoch`, and is only haircut if the manager passes a `_lossAmount` through `stopEpochWithDuration`/`previewLossAdjustedWithdrawFunds` or the borrower hard-defaults — neither of which applies to an honest borrower that simply pays the inflated `pendingWithdraws`. The excess is extracted directly from the pool's NAV/borrower repayment, i.e. from the other tranche holders, mirroring JOJO's "withdraw against a gain the account didn't really have, socialize the shortfall" bug.

### Impact Explanation
The attacker's claim basis exceeds the interest their capital actually accrued. If the borrower funds `pendingWithdraws` at `stopEpoch`, the borrower overpays relative to the promised APR and the excess over active NAV is socialized across remaining tranche holders at the next `_updateAccounting` — the protocol's books show the same "bad debt" shape as the JOJO report: a withdrawal that consumed value the position never earned. The extractable amount scales with `(epochDuration - timeInPool)` of interest and with the attacker's share of the tranche NAV, i.e. up to nearly a full epoch of the tranche's interest entitlement per cycle, repeatable every epoch (deposit late → request → claim next epoch → repeat). This is direct theft of yield / pool insolvency, satisfying the impact bar.

### Likelihood Explanation
Requirements are mild: the attacker only needs `isWalletAllowed` (KYC'd lender, in the allowed attacker set), deposits to be accepted late in the epoch via the discounted mint path, and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` to permit the request (these flags are enabled at epoch stop, and requests during the buffer still resolve through the same full-`_duration` formula since `_calcInterestWithdrawRequest` only early-returns when `epochDuration == 0`). No privileged cooperation, no oracle manipulation, no default is needed — an honest borrower funding the epoch makes the extraction atomic to the pool. One caveat I could not fully verify within the search budget: the exact windows in which `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are false (the flag-clearing assignments were not located); if requests are strictly gated to a window where deposits are impossible, the attack requires holding newly minted shares across the stop boundary, which is still possible since minted shares are unrestricted ERC20 tranche tokens.

### Recommendation
Scale the interest baked into a withdrawal receipt by the share's actual accrual period — e.g. multiply `totTrancheInterest` in `_calcInterestWithdrawRequest` by `(epochEndDate - shareMintTime) / epochDuration` using a per-user mint timestamp/checkpoint, or at minimum by the elapsed fraction of the epoch at request time — so a request can never lock interest for time the capital was not deployed. Alternatively, value mid-epoch requests at the same discounted price used by the deposit mint (`expectedFinal`-consistent pricing) so the deposit and withdraw paths cannot be arbitraged against each other.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_calcInterestWithdrawRequest`):

```solidity
function testLateDepositFullEpochInterest() external {
    uint256 amount = 100_000 * ONE_SCALE;
    // honest LPs seed the pool and the epoch runs
    _depositWithUser(honestUser, amount, true);   // AA
    _startEpochAndCheckPrices(0);

    // attacker deposits near epoch end via the discounted mid-epoch mint
    vm.warp(cdoEpoch.epochEndDate() - 1 hours);
    _depositWithUser(attacker, amount, true);      // minted shares priced for ~1h of interest

    // attacker requests withdraw; receipt locks full-epoch interest share
    vm.prank(attacker);
    uint256 receipt = cdoEpoch.requestWithdraw(0, address(AAtranche));

    uint256 honestShare = _calcInterestWithdrawRequest(amount, address(AAtranche));
    // receipt - amount ≈ attacker share of FULL epoch interest, not ~1h of interest
    assertGt(receipt, amount + honestShare * 9 / 10, 'receipt should not contain near-full epoch interest');

    // borrower honestly funds stopEpoch; the overpayment is socialized
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    // attacker profit = receipt + interest - (amount + prorated interest priced into the mint)
    // honestUser's claimable NAV is reduced by the same amount
}
```
