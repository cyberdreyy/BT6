### Title
Builder payment double-paid (or force-paid without quorum) via the "evicted payment" fallback in `apply_parent_execution_payload` - (File: specs/gloas/beacon-chain.md)

### Summary
`apply_parent_execution_payload` settles a proposer's builder payment for the *parent* slot every time a new block is processed. If the parent's payment bucket in `state.builder_pending_payments` is no longer indexable (because it "aged out" more than one epoch), the function falls back to unconditionally appending a fresh `BuilderPendingWithdrawal` built from the cached `parent_bid`. This fallback does not check whether the same payment was already settled by the routine, block-independent epoch-boundary sweep in `process_builder_pending_payments`. When enough slots are skipped (a normal occurrence, not an attack), the same builder payment can be paid out twice, or paid out even though the PTC quorum required to confirm the payload was never reached.

### Finding Description
`apply_parent_execution_payload` decides how to settle the payment owed for the block at `parent_slot`: [1](#0-0) 

```python
    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        # Parent is older than the previous epoch, its payment entry has been
        # evicted from builder_pending_payments. Append the withdrawal directly.
        state.builder_pending_withdrawals.append(
            BuilderPendingWithdrawal(
                fee_recipient=parent_bid.fee_recipient,
                amount=parent_bid.value,
                builder_index=parent_bid.builder_index,
            )
        )
```

The `elif parent_bid.value > 0` branch fires purely based on epoch arithmetic ("parent is older than the previous epoch"), assuming the corresponding slot in `builder_pending_payments` has necessarily been evicted and therefore needs to be paid "directly." But `builder_pending_payments` is *not* only cleared by this function — it is swept unconditionally on every epoch boundary by `process_builder_pending_payments`, which runs as part of ordinary epoch processing regardless of whether any block was produced: [2](#0-1) 

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
```

`settle_builder_payment` only mutates the specific index it is given, appending the withdrawal and clearing the slot; it never marks the underlying `parent_bid`/payment as "already settled" in a way `apply_parent_execution_payload` can later consult: [3](#0-2) 

```python
def settle_builder_payment(state: BeaconState, payment_index: Uint64) -> None:
    assert payment_index < len(state.builder_pending_payments)
    payment = state.builder_pending_payments[payment_index]
    if payment.withdrawal.amount > 0:
        state.builder_pending_withdrawals.append(payment.withdrawal)
    state.builder_pending_payments[payment_index] = BuilderPendingPayment.empty()
```

**Concrete state walk-through:**
1. At slot `S` (epoch `E`), a full block is proposed and a builder payment of `V > 0` is recorded at `builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH]`, with `state.latest_execution_payload_bid.value = V`.
2. Suppose the network then produces **no blocks for more than one full epoch** (all slots from `S+1` through well into epoch `E+2` are missed — a routine liveness gap, no attacker required).
3. During this gap, `process_slots` still advances the state through epoch boundaries, and `process_epoch` still calls `process_builder_pending_payments` every epoch transition irrespective of blocks. On the epoch `E→E+1` boundary this entry rotates into the first half of the buffer; on the `E+1→E+2` boundary it is swept: if `payment.weight >= quorum` it is appended to `builder_pending_withdrawals` (payment made), and either way the slot is zeroed to `BuilderPendingPayment.empty()`.
4. When a block finally arrives (parent slot `S`, now in epoch `E`, with `get_current_epoch(state)` at `E+2` or later), `parent_epoch` no longer equals `current_epoch` or `previous_epoch`, so the `elif parent_bid.value > 0` branch executes. It appends **another** `BuilderPendingWithdrawal` of amount `V` for the same builder/fee recipient, entirely independent of whatever `process_builder_pending_payments` already did in step 3.

Two outcomes are both wrong:
- If the payment already reached quorum and was forwarded in step 3, the builder is paid `V` **twice** for a single payload commitment — Gwei is created/duplicated and paid out beyond what the chain committed to.
- If the payment never reached quorum (i.e., the PTC never confirmed the payload was revealed on time) and was discarded in step 3, the fallback branch **still pays** the builder `V` based only on the cached `parent_bid`, i.e., a payment the attesters/block did not commit to.

### Impact Explanation
This breaks the equality that a builder is paid exactly once, and only when quorum-confirmed, for a given execution payload commitment. It matches the Critical/High impact categories: "Gwei created, destroyed or paid to a non-owner" / "a payload executed or paid that the block did not commit to" / "a builder payment or withdrawal misdirected, doubled." The duplicated withdrawal is a direct, unauthorized transfer of stake to the builder's `fee_recipient`, decoupled from actual payload delivery or PTC confirmation.

### Likelihood Explanation
No malicious collusion, equivocation, or coalition is required — only a liveness gap of roughly 2+ epochs with no blocks built on top of a slot that had a non-zero builder bid, which can occur from ordinary proposer downtime or network partitions/naturally missed slots. Any node following the spec literally would independently derive the double payment, so it is a genuine, deterministic spec-transition bug rather than a client bug.

### Recommendation
Do not resettle a payment "directly" from the cached bid once it may have already been processed by `process_builder_pending_payments`. Either:
- Track settlement state explicitly (e.g., a flag or sentinel indicating the epoch-boundary sweep already consumed the payment for that slot), and have the `elif` branch check it before appending; or
- Make `process_builder_pending_payments` the single authoritative path for aged-out payments (i.e., extend its sweep window instead of relying on `apply_parent_execution_payload`'s epoch-distance heuristic), removing the redundant "evicted" fallback entirely.

### Proof of Concept
1. Build and finalize a chain such that a proposer at slot `S` includes a bid with `value = V > 0`; this records a pending payment at `builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH]`.
2. Advance `state.slot` via `process_slots` alone (no new blocks) through at least two additional epoch boundaries, letting `process_builder_pending_payments` sweep and clear/forward that payment entry per its own quorum logic.
3. Produce the next actual block whose parent is still slot `S` (i.e., the chain had no blocks in between). Process it through `process_parent_execution_payload` → `apply_parent_execution_payload`.
4. Observe `parent_epoch` is neither `get_current_epoch(state)` nor `get_previous_epoch(state)`, so the `elif parent_bid.value > 0` branch executes and appends a second `BuilderPendingWithdrawal(amount=V, ...)` to `state.builder_pending_withdrawals`, in addition to whatever `process_builder_pending_payments` already appended (or correctly withheld) in step 2 — demonstrating the duplicate/unauthorized payment.
