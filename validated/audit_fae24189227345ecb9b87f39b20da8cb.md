### Title
Reward swap in `_redeemRewards` uses `block.timestamp` as deadline, allowing validator to hold the harvest swap until it is maximally disadvantageous - ([File: contracts/strategies/euler/IdleLeveragedEulerStrategy.sol](contracts/strategies/euler/IdleLeveragedEulerStrategy.sol))

### Summary
`IdleLeveragedEulerStrategy._redeemRewards` sells claimed EUL rewards through Uniswap V3 `exactInput` with `deadline: block.timestamp`. This is the identical bug class as the external report: because the deadline is evaluated at execution time, it is always satisfied, so a validator/sequencer can withhold the transaction from inclusion and execute it later, at the worst price still permitted by `minAmountOut`.

### Finding Description
In `_redeemRewards` (called from `redeemRewards`, which is invoked by the `IdleCDO` during harvest), the strategy claims EUL via the merkle distributor and swaps the full EUL balance for underlying:

```solidity
// contracts/strategies/euler/IdleLeveragedEulerStrategy.sol
_router.exactInput(
    ISwapRouter.ExactInputParams({
        path: path,
        recipient: address(this),
        deadline: block.timestamp,   // always "now" at execution -> never expires
        amountIn: amountIn,
        amountOutMinimum: minAmountOut
    })
);
```

The `deadline` field is the mechanism Uniswap provides so that a swap cannot be "saved for later". Setting it to `block.timestamp` makes the check `require(deadline >= block.timestamp)` trivially true whenever the transaction is eventually included. The swap therefore has no temporal protection: once the harvest/redeem transaction is broadcast, any block producer (or a sequencer on L2 variants) can delay inclusion until pool prices move against the strategy, then include it when the extracted value (slippage up to `minAmountOut`) is maximal.

### Impact Explanation
The strategy swaps its entire accrued EUL reward balance in one call. A validator can hold the transaction while moving or waiting for the EUL/underlying price to deteriorate, then execute it at the maximum tolerated slippage. The difference between the fair price at broadcast time and the executed price is extracted as MEV and is a direct loss of yield that would otherwise be credited to tranche holders through `_setMintPrice()`/`price()`. Loss is bounded by `minAmountOut` but can be the full slippage band on every harvest.

### Likelihood Explanation
- The transaction is initiated by an honest keeper/owner via `harvest` -> `redeemRewards`, so it is broadcast publicly; a validator does not need any privilege to delay it — this is standard block-producer MEV, available to any unprivileged validator/sequencer.
- EUL is a low-liquidity reward token, so single-block price moves against the swap are plausible.
- The only mitigation is `minAmountOut` supplied in `data`, which bounds but does not prevent the loss; there is no on-chain deadline guard that would cause a stale transaction to revert.

### Recommendation
Allow a real deadline to be supplied by the caller in `data` (or use `block.timestamp + deadlineDelta`), e.g.:

```solidity
(uint256 claimable, bytes32[] memory proof, uint256 minAmountOut, uint256 deadline) =
    abi.decode(data, (uint256, bytes32[], uint256, uint256));
...
deadline: deadline,
```

Alternatively, set `deadline: block.timestamp + N` with a small `N` so the swap reverts if not included promptly, complementing the `minAmountOut` slippage bound.

### Proof of Concept
Foundry fork test (mainnet, block where EUL distributor + UniV3 pool are live):

```solidity
// test/foundry/DeadlineSwap.t.sol
function testDelayedHarvestSwap() public {
    // strategy = IdleLeveragedEulerStrategy attached to an IdleCDO
    // 1) Build redeemRewards calldata: claimable, proof, minAmountOut
    bytes memory data = abi.encode(claimable, proof, minAmountOut);

    // 2) Keeper broadcasts harvest -> redeemRewards at t0. Record fair quote:
    uint256 fairOut = quoter.quoteExactInput(path, eulBalance); // at t0

    // 3) Validator withholds the tx. Warp forward and move the pool price
    //    against the strategy (swap underlying->EUL in the pool, or just warp):
    vm.warp(block.timestamp + 1 hours);
    _movePoolAgainstEUL(); // push EUL price down within minAmountOut band

    // 4) Include the delayed tx — it still succeeds because
    //    deadline == block.timestamp evaluated at execution:
    vm.prank(address(idleCDO));
    strategy.redeemRewards(data); // does NOT revert

    uint256 actualOut = underlying.balanceOf(address(strategy));
    assertLt(actualOut, fairOut); // loss up to (fairOut - minAmountOut)
}
```

Key assertion: `redeemRewards` succeeds after a long delay and adverse price movement, whereas a literal user-supplied deadline would have reverted, capping loss to zero. Note this finding concerns the leveraged Euler strategy in `contracts/strategies/euler/`; if that file is considered legacy/out of scope for this audit, the same `deadline: block.timestamp` pattern would need re-checking against the chain-variant `IdleCDO*` reward-sale paths, which I was not able to fully confirm within the available iterations.
