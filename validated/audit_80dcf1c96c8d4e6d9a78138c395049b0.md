### Title
Stale confirmations from removed multisig members allow request execution below the configured threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only purges confirmations for requests that were *originated* by the member being removed. It never scans the `confirmations` map for other pending requests where the removed member had already cast a confirmation. Because `confirm()` counts raw entries in that set (`confirmations.len() as u32 + 1 >= self.num_confirmations`) without checking that every counted confirmer is still a current member, a stale confirmation from a deleted member can be combined with confirmations from remaining live members to execute a request with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
The custody binding that must hold is: `confirmations counted at execution == confirmations from accounts that are live members at execution time`. `delete_member` breaks this equality by only cleaning up requests it authored: [1](#0-0) 

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
```

Only requests whose `r.member` (the originating/adding member) equals the member being deleted are cleaned up. Any *other* pending request that the removed member had merely **confirmed** (but did not create) keeps that member's entry in `self.confirmations`, since nothing iterates the `confirmations` map to strip entries belonging to the deleted member.

`confirm()` then counts confirmations purely by set size, with no liveness check against `self.members` for the already-stored confirmers: [2](#0-1) 

```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self
        .current_member()
        .unwrap_or_else(|| env::panic_str("Must be validated above"));
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(
        !confirmations.contains(&member.to_string()),
        "Already confirmed this request with this key",
    );
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
```

`assert_valid_request` only validates that the *current caller* is a live member and that the request/confirmations map entries exist; it never re-validates the liveness of members already recorded in the `confirmations` set: [3](#0-2) 

The identical structural flaw exists in the older `multisig/src/lib.rs`, where `DeleteKey` only removes requests where `r.signer_pk == pk` and clears confirmations solely for those requests: [4](#0-3) 

This mirrors the report's root cause class: a state-changing/blocking action (pause / member removal) is applied inconsistently across the two code paths that must both honor it (`_blockingLzReceive` vs `_nonblockingLzReceive` in the report; `delete_member`'s own-request cleanup vs. `confirm`'s raw-count check here), leaving a "replay" surface — replaying an old confirmation from a no-longer-authorized party lets a privileged action execute.

### Impact Explanation
This directly breaks the multisig's threshold guarantee: a request can execute with fewer confirmations from *currently live* members than `num_confirmations` mandates. Since `execute_request` can perform `Transfer`, `DeployContract`, `AddKey`/`AddMember` etc. on the contract's own funds and access keys, this allows a request to be pushed through with an effectively lowered quorum — matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
This requires no attacker-privileged action beyond ordinary multisig operation: (1) a request is added and partially confirmed by several members, one of whom is later removed via a normal `DeleteMember` action (a routine governance operation, e.g., rotating out a compromised or departing member), and (2) a remaining member later confirms the still-pending request. No owner bypass, redeploy, or key compromise is needed — only the natural sequence of "confirm request → later remove one of its confirmers → confirm again," which is a foreseeable operational pattern for any long-lived multisig membership change.

### Recommendation
When a member is deleted, iterate all pending requests' confirmation sets (not just requests they authored) and remove the deleted member's entry from every one of them; alternatively, have `confirm()` re-validate that every account in the stored `confirmations` set is still present in `self.members` before counting it toward the threshold.

### Proof of Concept
1. Initialize multisig with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` for a sensitive action (e.g., `Transfer` or `AddKey`), then `B` and `C` call `confirm` — `confirmations = {B, C}`, size 2, one short of 3.
3. Members execute a separate, legitimately-approved `DeleteMember { member: C }` request. `delete_member` only removes requests where `r.member == C` (i.e., requests *added* by `C`); the pending transfer request from step 2 was added by `A`, so its `confirmations = {B, C}` is left untouched even though `C` is no longer in `self.members`.
4. `D` calls `confirm(request_id)`. `confirmations.len() (=2) + 1 (D) = 3 >= num_confirmations (3)` → `execute_request` runs, even though only `B` and `D` are actually live members who confirmed (2 live confirmations versus the required 3). [5](#0-4) [6](#0-5)
