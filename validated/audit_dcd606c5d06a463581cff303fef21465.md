### Title
Accidentally transferred ERC20 tokens are permanently unrecoverable from IdleCDO - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant` has no privileged recovery function for tokens sent directly to the contract. For the vault underlying, `_skimDonatedAssets` irreversibly forwards the entire raw contract balance to `feeReceiver` during deposits, withdrawal requests, epoch transitions, accounting updates, and default finalization. Other ERC20 tokens sent directly to the CDO remain locked indefinitely unless the implementation is upgraded.

### Finding Description
The CDO treats every raw underlying balance as a donation:

```solidity
function _skimDonatedAssets() internal {
    _transferUnderlyings(feeReceiver, _contractTokenBalance(token));
}
```

This is invoked by user-facing paths including `_deposit`, `depositDuringEpoch`, and `requestWithdraw`, as well as privileged paths such as `startEpoch`, `_stopEpoch`, `updateAccounting`, `writeOffDeposit`, and `finalizeDefault`.

An unprivileged user can accidentally call `underlying.transfer(address(idleCDO), amount)` instead of depositing through `depositAA`/`depositBB`. No tranche tokens or withdrawal receipt are created for that transfer. On the next deposit or withdrawal request, the full balance is transferred to `feeReceiver`, not the sender. The CDO also lacks a generic `rescueToken`/`transferToken` function for unrelated ERC20 tokens. While `IdleCreditVault` implements `transferToken`, that function only rescues tokens held by the strategy contract and cannot access tokens held by the CDO.

### Impact Explanation
The sender permanently loses the full transferred amount. For underlying tokens, the loss is crystallized by the next skim trigger; for other ERC20 tokens, the balance remains locked in the CDO. For example, an accidental transfer of `1,000 USDC` results in `1,000 USDC` being assigned to `feeReceiver` and zero claimable shares or receipts being issued to the sender.

### Likelihood Explanation
This requires user error rather than attacker action, so the likelihood is lower than an exploit that can be initiated deliberately. However, direct `transfer` calls to vault addresses are a common operational mistake, and the loss is deterministic once the tokens reach `IdleCDOEpochVariant`.

### Recommendation
Add an owner-controlled recovery function to the CDO for non-accounting tokens. It should either:

- allow recovery of arbitrary ERC20 tokens other than `token` and `strategyToken`; and
- for `token`, recover only an explicitly tracked or provably donated surplus rather than indiscriminately sweeping operational balances.

Alternatively, keep the underlying skim for donation isolation but add an admin function that can return an identified accidental transfer to a specified recipient before the next accounting/user action.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "../contracts/IdleCDOEpochVariant.sol";
import "../contracts/interfaces/IERC20Detailed.sol";

contract AccidentalUnderlyingTransferPoC is Test {
    // Replace with the deployed fork addresses used by the existing suite.
    IdleCDOEpochVariant internal cdo;
    IERC20Detailed internal underlying;
    address internal allowedDepositor;
    address internal mistakenSender;

    function setUp() public {
        // Fork mainnet and initialize:
        // cdo = IdleCDOEpochVariant(<deployed IdleCDOEpochVariant>);
        // underlying = IERC20Detailed(cdo.token());
        // allowedDepositor = <KYC-passed depositor>;
        // mistakenSender = makeAddr("mistakenSender");
    }

    function testAccidentalUnderlyingTransferIsSkimmedToFeeReceiver() public {
        uint256 accidentalAmount = 1_000e6;
        uint256 depositAmount = 100e6;

        deal(address(underlying), mistakenSender, accidentalAmount);
        deal(address(underlying), allowedDepositor, depositAmount);

        address feeReceiver = cdo.feeReceiver();
        uint256 senderBefore = underlying.balanceOf(mistakenSender);
        uint256 feeReceiverBefore = underlying.balanceOf(feeReceiver);

        // User sends underlying directly instead of calling depositAA/depositBB.
        vm.prank(mistakenSender);
        underlying.transfer(address(cdo), accidentalAmount);

        assertEq(underlying.balanceOf(mistakenSender), senderBefore - accidentalAmount);
        assertEq(underlying.balanceOf(address(cdo)), accidentalAmount);

        // Any later ordinary deposit invokes _skimDonatedAssets().
        vm.startPrank(allowedDepositor);
        underlying.approve(address(cdo), depositAmount);
        cdo.depositAA(depositAmount);
        vm.stopPrank();

        // The mistaken sender received no tranche tokens and the donation was sent away.
        assertEq(underlying.balanceOf(feeReceiver), feeReceiverBefore + accidentalAmount);
        assertEq(underlying.balanceOf(address(cdo)), 0);
        assertEq(cdo.AATranche().balanceOf(mistakenSender), 0);
        assertEq(cdo.BBTranche().balanceOf(mistakenSender), 0);
    }
}
```
