Based on my research, I found a plausible lockup analog in `vesting::distribute()`, but I was unable to fully verify one critical implementation detail due to index truncation. Let me present findings transparently.

### Title
Unbounded distribution loop in `vesting::distribute` can be permanently griefed by a single shareholder, freezing all shareholders' vested/reward coins - (File: `aptos-move/framework/aptos-framework/sources/vesting.move`)

### Summary
`vesting::distribute` iterates over every shareholder of a vesting contract and calls `aptos_account::deposit_coins` for each one with no failure isolation, similar in structure to the `VUSD#processWithdrawals` pattern where a per-recipient transfer failure affects the whole batch. Unlike the Solidity report (where a failed low-level `call` is silently swallowed and funds are lost), Move aborts the entire transaction on failure — but because the loop has no per-recipient skip/retry logic, a single shareholder can make the abort permanent and repeatable, blocking distribution to every other shareholder indefinitely.

### Finding Description
`distribute()` extracts all withdrawable coins from the vesting contract's stake pool via `withdraw_stake`, then loops over `grant_pool.shareholders()` and sends each shareholder's share to `get_beneficiary(vesting_contract, shareholder)` using `aptos_account::deposit_coins`: [1](#0-0) 

`aptos_account::deposit_coins` is documented to enforce a recipient's `DirectTransferConfig`, aborting with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` if the recipient has disabled arbitrary coin transfers and has not explicitly registered a store for the coin type: [2](#0-1) 

Any account can opt out of unsolicited coin transfers via the public entry function `set_allow_direct_coin_transfers`, which any shareholder or beneficiary (an unprivileged party who is nonetheless a legitimate participant of the vesting contract) can call on their own account: [3](#0-2) 

Since `distribute()` has no try/skip logic around each shareholder's payout — unlike `staking_contract`'s `distribution_pool` design, which records failed/pending distributions per-recipient via `pool_u64` shares that can be claimed independently — a single shareholder who disables direct transfers (and never explicitly registers for `AptosCoin`) causes `distribute()` to abort every time it's called, for every shareholder in that contract, not just the griefing party. Because `terminate_vesting_contract` also calls `distribute` internally before finalizing termination, admin termination and fund recovery via `admin_withdraw` are similarly blocked: [4](#0-3) 

### Impact Explanation
If confirmed, this would permanently lock reward and vested-coin distribution rights for every shareholder in the affected vesting contract, and could also block admin termination/withdrawal — matching the "Permanent lock or non-recoverable loss of claim rights ... in vesting flows" impact category. This is high severity because it affects all co-shareholders of a pool, not just the party who opts out.

### Likelihood Explanation
**I could not fully confirm this finding and it should not be treated as verified.** My tool access was index-limited and I was unable to read the actual body of `aptos_account::deposit_coins` past line ~120 (the read returned blank content), so I cannot confirm whether the `DirectTransferConfig`/`EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` abort path still applies to `AptosCoin` after the Fungible Asset (FA) migration referenced in the same file (`primary_fungible_store`, `fungible_transfer_only`). If AptosCoin transfers now go through the FA path (which appears to bypass legacy `CoinStore`/`DirectTransferConfig` checks based on the `fungible_transfer_only` spec being a "temporary mockup"), the abort condition this finding relies on may not actually trigger for APT deposits, which would invalidate the root cause.

### Recommendation
This cannot responsibly be finalized without confirming, by reading the full body of `aptos_account::deposit_coins` (and `fungible_transfer_only`), whether `AptosCoin` deposits via `vesting::distribute` can actually abort due to a recipient's `DirectTransferConfig`. I recommend a Devin session with full file access to `aptos-move/framework/aptos-framework/sources/aptos_account.move` to verify this precisely before treating it as a valid, high-severity finding.

### Proof of Concept
Not constructed — pending confirmation of the abort path described above. A valid PoC would require: (1) a vesting contract with ≥2 shareholders, (2) one shareholder or beneficiary calling `set_allow_direct_coin_transfers(false)` without ever registering `AptosCoin`, (3) demonstrating `vesting::distribute` reverts on every subsequent call including after rewards accumulate, permanently blocking the other shareholder's withdrawal.

    public entry fun terminate_vesting_contract(admin: &signer, contract_address: address) acquires VestingContract {
        assert_active_vesting_contract(contract_address);

        // Distribute all withdrawable coins, which should have been from previous rewards withdrawal or vest.
        distribute(contract_address);

        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        verify_admin(admin, vesting_contract);
        let (active_stake, _, pending_active_stake, _) = stake::get_stake(vesting_contract.staking.pool_address);

        // Unlock all remaining active stake.
        vesting_contract.state = VESTING_POOL_TERMINATED;
        vesting_contract.remaining_grant = 0;
        unlock_stake(vesting_contract, active_stake);

        emit(
            Terminate {
                admin: vesting_contract.admin,
                vesting_contract_address: contract_address,
            },
        );

    /// Set whether `account` can receive direct transfers of coins that they have not explicitly registered to receive.
    public entry fun set_allow_direct_coin_transfers(
        account: &signer, allow: bool
    ) acquires DirectTransferConfig {
        let addr = signer::address_of(account);
        if (exists<DirectTransferConfig>(addr)) {
            let direct_transfer_config = borrow_global_mut<DirectTransferConfig>(addr);
            // Short-circuit to avoid emitting an event if direct transfer config is not changing.
            if (direct_transfer_config.allow_arbitrary_coin_transfers == allow) { return };

            direct_transfer_config.allow_arbitrary_coin_transfers = allow;

            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
        } else {
            let direct_transfer_config = DirectTransferConfig {
                allow_arbitrary_coin_transfers: allow,
                update_coin_transfer_events: new_event_handle<
                    DirectCoinTransferConfigUpdatedEvent>(account)
            };
            emit(
                DirectCoinTransferConfigUpdated {
                    account: addr,
                    new_allow_direct_transfers: allow
                }
            );
            move_to(account, direct_transfer_config);
        };
    }
