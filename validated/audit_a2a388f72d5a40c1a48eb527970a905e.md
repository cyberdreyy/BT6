This confirms the vulnerability. The `staking-pool-factory` demonstrates the correct pattern with a callback (`on_staking_pool_create`) that checks `is_promise_success()` and refunds the attached deposit to the predecessor if the batch failed. The `multisig-factory::create` has **no such callback** — it fires the batch and returns the `Promise` directly to the caller, with no `.then()` self-callback to detect failure and refund.### Title
Attached deposit stranded when `MultisigFactory::create` targets an already-existing/over-length account - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds a single multi-action `Promise` (`create_account` → `deploy_contract` → `transfer` → `function_call`) targeting `format!("{}.{}", name, env::current_account_id())`, but never validates that `account_id` with `env::is_valid_account_id`, never checks that the derived account doesn't already exist, and — critically — never attaches a `.then()` callback to itself to detect failure and refund the deposit. Compare this to `staking-pool-factory/src/lib.rs`, whose `create_staking_pool` schedules the identical batch but attaches `ext_self::on_staking_pool_create` as a callback, which checks `is_promise_success()` and explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure.

### Finding Description
The broken binding: `attacker_attached_deposit == refunded_to_attacker_on_failure` should hold for any failed creation, i.e. a failed `create` must strand no NEAR. In `multisig-factory/src/lib.rs::create` (lines 29-49):

```rust
let account_id = format!("{}.{}", name, env::current_account_id());
Promise::new(account_id)
    .create_account()
    .deploy_contract(CODE.to_vec())
    .transfer(env::attached_deposit())
    .function_call(...)
```

there is no validation of `account_id`'s length/validity via `env::is_valid_account_id`, and no bookkeeping (no `UnorderedSet` of created account ids as in `staking-pool-factory`), and — most importantly — no `.then(ext_self::on_create(...))` callback attached to the returned promise. The function simply returns the raw batch `Promise` to the runtime.

An attacker can:
1. Pick/deploy any target account that already exists under `<name>.<factory>` and holds a NEAR balance (they can create such an account themselves, or target another party's pre-existing account under the factory's namespace), or pick a `name` long enough that `format!("{}.{}", name, factory)` exceeds NEAR's 64-byte account-id limit.
2. Call `create(name, members, num_confirmations)` with an attached deposit.
3. `create_account()` fails at the protocol level (account already exists, or resulting id is invalid/over-length), which causes the entire action batch in that single receipt to fail. Depending on exact runtime handling of already-executed prior actions in the same receipt, the attached NEAR transferred via `.transfer(env::attached_deposit())` is at risk of being deposited into (or lost against) an account that never receives the expected `new()` initialization, while the factory contract has no callback to detect the failure and pull the deposit back.
4. Because there is no `assert_self()`/`is_promise_success()` callback like `staking-pool-factory::on_staking_pool_create`, the factory contract has no mechanism to notice the failure and issue `Promise::new(predecessor_account_id).transfer(...)` to return the funds to the caller.

This breaks the invariant "a failed creation strands no NEAR" purely due to a missing callback and missing input validation — both of which the sibling `staking-pool-factory` contract already implements correctly.

### Impact Explanation
NEAR attached by the caller can end up parked on/lost to an account the caller does not control as a validly initialized multisig, with no automatic refund path from the factory. This matches the "accounting value diverging from reality" / funds-frozen category: the caller's attached deposit is unaccounted for by the multisig factory (no record, no refund), and if the deposit lands on an account already owned/controlled by another party (e.g., the attacker's own pre-created account, or one they subsequently take over), that party can settle on/spend the stranded balance while the intended multisig was never created. This is repeatable for every `name` collision or over-length name, at attacker's own gas/deposit cost.

### Likelihood Explanation
The precondition (a pre-existing account at `<name>.<multisig-factory>` holding a balance, or a `name` chosen at the account-id length boundary) is entirely attacker-controlled — an unprivileged caller can pre-create the colliding sub-account itself (e.g. via a prior `create` call or a direct account creation under the factory namespace) or choose a maximal-length `name` to force `format!` to exceed the 64-byte NEAR account id limit. No special privilege, foundation role, or victim key is required, and the attack is repeatable across arbitrary names.

### Recommendation
Mirror the `staking-pool-factory` pattern in `multisig-factory/src/lib.rs`:
- Validate `account_id` with `env::is_valid_account_id(account_id.as_bytes())` before scheduling any promise.
- Track created account ids (e.g., an `UnorderedSet`) and reject duplicate `name`s the factory already knows about.
- Attach a `.then(ext_self::on_create(...))` callback that asserts `assert_self()`, checks `is_promise_success()`, and on failure explicitly refunds `env::attached_deposit()` to `env::predecessor_account_id()`.
