### Title
Unbounded per-sender `map[string]*rate.Limiter` growth in `workflows/ratelimiter.RateLimiter` allows unprivileged callers to permanently grow gateway/workflow memory (rent/DoS griefing analog) - ([File: core/services/workflows/ratelimiter/ratelimiter.go])

### Summary
The `RateLimiter.Allow` function used to rate-limit incoming workflow trigger/gateway senders creates a new `*rate.Limiter` entry keyed by the caller-supplied `sender` string on first use, and never evicts or expires that entry. Every distinct sender value an unprivileged client can present (e.g. an EVM address in a web API trigger payload, or a p2p sender ID in dispatcher messages) permanently adds one entry to an in-memory map for the lifetime of the process. This mirrors the reported bug class: an unprivileged actor forces monotonic, unbounded growth of a per-identity data structure that a Chainlink component (the node/gateway) must pay to hold in memory forever, with no pruning mechanism, unlike the Reaper mechanisms that exist elsewhere in the codebase for job runs.

### Finding Description
`RateLimiter.Allow` in [1](#0-0)  unconditionally allocates and stores a `*rate.Limiter` for any new `sender` key:

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()
	...
}
```

There is no TTL, LRU, or periodic cleanup of `perSender` anywhere in this type — unlike comparable caches in the codebase (`responseCache.DeleteExpired`, `jwtReplayCache.cleanupOldEntries`, `RequestReplayGuard.clearExpiredLocked`), all of which are invoked on a ticker to bound memory. This rate limiter is instantiated and driven directly by external, attacker-influenced input in at least two reachable, unprivileged paths:

1. `core/capabilities/webapi/trigger/trigger.go` — `processTrigger` calls `trigger.rateLimiter.Allow(body.Sender)` at [2](#0-1) , where `body.Sender` comes from an incoming gateway message body that is only checked against an allow-list of `topics`/`allowedSenders` for actually executing the trigger — the rate-limit check (and thus the map insertion) happens on essentially every processed message regardless of whether the sender is authorized, since matching logic runs before the per-sender-limiter check for whichever workflows share a topic.
2. `core/services/cre/cre.go` instantiates a similarly-structured `ratelimiter.NewRateLimiter` as `workflowRateLimiter` at [3](#0-2) , keyed by workflow/owner-controlled sender identifiers coming from workflow execution requests.

Because `sender` is an attacker-controlled string (an address format is expected but any string is technically accepted before validation elsewhere, and even valid but never-reused addresses are sufficient), an attacker can enumerate a large number of distinct sender values and force the node to allocate a `*rate.Limiter` object per sender permanently, since nothing ever calls `delete(rl.perSender, ...)`.

### Impact Explanation
This is a memory-growth / resource-exhaustion vector analogous to the reported `TrackerAccount.issuances` bug: it lets an unprivileged, low-cost attacker impose unbounded, non-reclaimable resource cost on the node/gateway operator. Over time, sustained abuse can grow the `perSender` map to a size that increases GC pressure and memory footprint of the workflow/gateway service, degrading availability for legitimate senders and potentially leading to OOM on the affected node process — a liveness impact consistent with "eventual DoS" described in the report, though the specific `Vec` reallocation/rent mechanics from the Solana report obviously don't apply verbatim to a Go in-memory map.

### Likelihood Explanation
Likelihood is moderate: reaching `Allow` requires only sending gateway/trigger messages with varying sender identifiers, which is exactly the kind of traffic these components are designed to accept from external/unprivileged callers. No authentication bypass is needed to cause the map growth itself (only to have the trigger actually fire), because the vulnerable code path (`Allow`) is invoked before/independent of the full authorization decision in `processTrigger`. The severity is bounded by config-level global RPS caps but not by any bound on distinct-sender cardinality, so growth is unbounded in the size dimension even if rate-limited in the throughput dimension.

### Recommendation
Add periodic cleanup or an LRU/bounded-size cache to `RateLimiter.perSender`, mirroring the pattern already used elsewhere in the codebase (e.g. `jwtReplayCache.cleanupOldEntries` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`, and `RequestReplayGuard.clearExpiredLocked` in `core/capabilities/vault/request_replay_guard.go`). Concretely: track last-access time per sender limiter and evict entries idle longer than some TTL on a ticker, or cap the map to a maximum number of distinct senders with LRU eviction, so an attacker cannot force unbounded memory growth by cycling through sender identifiers.

### Proof of Concept
Conceptual PoC (no execution environment available to run Go tests here):
```go
rl, _ := ratelimiter.NewRateLimiter(ratelimiter.Config{
    GlobalRPS: 1000, GlobalBurst: 1000,
    PerSenderRPS: 30, PerSenderBurst: 30,
})
for i := 0; i < 10_000_000; i++ {
    sender := fmt.Sprintf("attacker-sender-%d", i) // unique, attacker-chosen each call
    rl.Allow(sender)
}
// rl.perSender now holds 10,000,000 permanent *rate.Limiter entries;
// nothing in RateLimiter ever removes them.
```
Driving this through `triggerConnectorHandler.processTrigger` (`core/capabilities/webapi/trigger/trigger.go`) with gateway messages carrying distinct `body.Sender` values reproduces the same growth against a live node/gateway process without requiring the message to pass full authorization.
