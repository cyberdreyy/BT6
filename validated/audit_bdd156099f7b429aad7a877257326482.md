### Title
Unclaimed older-epoch withdraw receipts escape `stopEpochWithDuration` loss haircut and drain funded reserves - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`collectWithdrawFunds` applies a single `lossRecoveryPriceByEpoch[epochNumber]` haircut to the *entire* global `pendingWithdraws` bucket, but `_claimLossAdjustedWithdrawRequest` only clears the request recorded in the user's `lastWithdrawRequest` epoch. Any earlier, still-unclaimed receipt of the same user stays in `withdrawsRequests`/`withdrawsRequestsByEpoch` and is later paid **at par** through `_claimFundedWithdrawRequest`, even though the borrower only funded the haircut amount. An attacker can therefore escape the loss socialization and over-draw the strategy's funded claim reserve.

### Finding Description
When an epoch is stopped with a realized loss via `stopEpochWithDuration`, the borrower funds only `pendingBasis - pendingLoss` and the vault records a recovery ratio:

`lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` in `collectWithdrawFunds` (IdleCreditVault.sol:411-421).

On claim, `_claimLossAdjustedWithdrawRequest` uses `lastWithdrawRequest[_user]` as the loss epoch and clears only that epoch's per-epoch basis via `_clearWithdrawClaimForEpoch` (lines 789-800, 811-836). The aggregate `withdrawsRequests[_user]` is reduced only by that epoch's `normalAmount` (line 819). The remainder is then paid 1:1 by `_claimFundedWithdrawRequest` (lines 338-349).

Attack sequence (unprivileged KYC'd lender):

1. Epoch N running: attacker calls `requestWithdraw(A, ...)` via the CDO. `withdrawsRequestsByEpoch[user][N] = A`, `lastWithdrawRequest[user] = N`, `pendingWithdraws += A` (lines 260-293).
2. Attacker does not claim. Epoch N+1: attacker calls `requestWithdraw(B, ...)` with dust `B`. No loss price exists for epoch N, so the guard at lines 263-271 passes. `lastWithdrawRequest[user] = N+1`, `withdrawsRequestsByEpoch[user][N+1] = B`, `pendingWithdraws = A + B`.
3. Manager calls `stopEpochWithDuration(_lossAmount)`; borrower funds `(A+B) * price`. `lossRecoveryPriceByEpoch[N+1] = price < 1e18`.
4. Attacker calls `claimWithdrawRequest`. `epochNumber` (N+2) > `lastWithdrawRequest` (N+1), so no revert. `_claimLossAdjustedWithdrawRequest` clears only epoch N+1: pays `B * price`. `_claimFundedWithdrawRequest` then pays the remaining `withdrawsRequests[user] = A` **at par** via `_transferFundedClaim`.
5. Total paid out ≈ `A + B*price` while only `(A+B)*price` was funded → attacker extracts `A*(1 - price)` more than the loss-adjusted entitlement.

The "session identifier" here is `lastWithdrawRequest`: it is a single-slot pointer overwritten on every request, so receipts keyed to older epochs lose their association with the haircut that was applied to the aggregate bucket.

### Impact Explanation
The haircut computed by `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` is applied pro rata to the *whole* pending bucket, but the escaping portion `A` is paid at par, stealing `(1 - price) * A` from the funded reserve held for other pending-receipt holders (and from `defaultRecoveryReserve` ordering in `_transferFundedClaim`). With `A = 1M` and `price = 0.5`, the attacker receives ~1M against ~0.5M funded, directly draining other users' claims — a quantified direct theft/insolvency, not a rounding artifact. Broken invariant: loss waterfall / fair burn (every pending receipt must bear the same epoch loss).

### Likelihood Explanation
Requires only two `requestWithdraw` calls in consecutive epochs before a loss epoch ends, plus a `stopEpochWithDuration` with `_lossAmount > 0` executed by the honest manager/borrower — a normal protocol path for realized losses. No privileged cooperation, no timing race beyond letting one request roll into a second epoch. Existing guards do not stop it: the line 263-271 check only inspects `lastWithdrawRequest` (the *latest* epoch), and `_clearWithdrawClaimForEpoch` intentionally leaves older basis in `withdrawsRequests`.

### Recommendation
When clearing a loss-adjusted claim, iterate (or accumulate) over *all* epochs with non-zero `withdrawsRequestsByEpoch[user][e]` that have a non-zero `lossRecoveryPriceByEpoch[e]`, rather than only `lastWithdrawRequest[user]`. Cheaper alternative: on `requestWithdraw`, if any earlier `withdrawsRequestsByEpoch` entry maps to an epoch whose `lossRecoveryPriceByEpoch` is set, force the user to claim first (extend the existing guard to scan the user's open epochs, or track a `firstPendingRequestEpoch` pointer), so no funded-at-par receipt can coexist with a haircut epoch.

### Proof of Concept
Foundry fork PoC outline (place in `test/foundry/`, reuse the harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossEscapeViaOlderEpochReceipt() external {
    // epoch N running
    _depositWithUser(attacker, 1_000_000 * ONE_SCALE, true);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // request A in epoch N

    // roll into epoch N+1 (startEpoch -> stopEpoch healthy)
    _stopCurrentEpoch(); // funds pending? use stopEpoch that does NOT fund, or deposit again to keep pending
    vm.prank(manager);
    cdoEpoch.startEpoch();

    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // request B (dust) in epoch N+1

    // stopEpochWithDuration with realized loss -> lossRecoveryPriceByEpoch[N+1] = price < 1e18
    uint256 loss = strategy.pendingWithdraws() / 2; // 50% haircut on pending bucket
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(loss, /*...*/);

    // attacker claims: pays B*price (loss path) + A at par (funded path)
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    uint256 funded = (A + B) * price / 1e18;       // what borrower actually funded
    uint256 paid   = underlying.balanceOf(attacker) - balPre;
    assertGt(paid, funded, "attacker escaped the loss haircut");
}
```

Key assertion: `paid ≈ A + B*price > funded = (A+B)*price`, with the excess `A*(1-price)` sourced from the strategy's funded-claim balance reserved for other receipt holders.
