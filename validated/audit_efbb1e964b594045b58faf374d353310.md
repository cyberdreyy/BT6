### Title
Unfunded APR0 interest is committed to `pendingWithdraws` before the borrower-funding check in `stopEpoch`, inflating default claim basis - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug is a resource leak on an error return path: cleanup is skipped when an intermediate call fails. The analog in this codebase is in `IdleCDOEpochVariant._stopEpoch`: `prepareStopEpochWithApr0` mutates strategy state (adds APR0 net interest to `pendingWithdraws`, writes `apr0RateByEpoch`, closes `apr0TotalPrincipal`) *before* the borrower-funding checks. If funding then fails and `_handleBorrowerDefault` runs, that interest increment is "leaked" into the default claim basis even though no funds ever arrived.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch` (contracts/IdleCDOEpochVariant.sol:362-404), the order of operations is:

1. `_strategy.prepareStopEpochWithApr0(_interest)` executes first. Inside `IdleCreditVault.prepareStopEpochWithApr0` (contracts/strategies/idle/IdleCreditVault.sol:532-540), when APR0 requests exist and `_interest > 1`, it computes `_apr0NetInterest` and immediately persists:
   ```solidity
   pendingWithdraws += _apr0NetInterest;
   apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;
   apr0TotalPrincipal = 0;
   ```
2. Only afterwards does the CDO check whether the borrower can actually fund: `onStopEpoch(...)` returning `false` (line 398) or the `try this.getFundsFromBorrower(...)` failing (line 408) both route into `_handleBorrowerDefault` and return early.

The "allocation" (APR0 interest booked into `pendingWithdraws`) happens before the "acquisition" (borrower cash). On the default path, neither the CDO nor the strategy ever reverts or compensates for the leaked `pendingWithdraws` increase. Later, `finalizeDefaultRecovery` (IdleCreditVault.sol:661-710) computes `pendingBasis = defaultPendingClaimBasis()`, which is `pendingWithdraws` plus instant claims (lines 644-649) — now including unfunded APR0 interest. `_claimDefaultedWithdrawRequest` then pays `claimBasis * defaultRecoveryPrice` where the user's `claimBasis` includes that same APR0 interest via `_withdrawClaimAmountsForEpoch` (lines 777-780, 862+).

This mirrors the kernel bug: state was committed on the happy path and never freed on the error path, so the leaked object (here, unfunded claim basis) persists.

### Impact Explanation
- The default recovery denominator `totalBasis` is inflated by `_apr0NetInterest` while `reserveAmount` is unchanged, so `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is lower than it should be.
- Every honest claimant (active AA/BB LPs and other pending withdrawers) receives a haircut strictly larger than warranted; the APR0 requester who caused the inflation claims pro-rata on basis that was never funded.
- Quantified: dilution factor is `_apr0NetInterest / (activeBasis + pendingBasisBefore)`. With an APR0 bucket that is large relative to TVL, the leaked basis can be a material fraction of total claims; the stolen amount is exactly `recoveryPrice * _apr0NetInterest` redirected from honest claimants to APR0 requesters, plus permanent trapped dust if claims exceed reserve.
- This is a theft/dilution of recovery value, not merely freezing, so it is in scope.

### Likelihood Explanation
- Attacker profile: any KYC-passing lender who makes a `requestWithdraw` while `unscaledApr == 0` lands in the APR0 bucket — an ordinary unprivileged user action.
- Trigger: requires `stopEpoch` to be called with override `_interest > 1` (manager-provided realized interest) and the borrower to then fail funding (returns false or `getFundsFromBorrower` reverts). The borrower default itself is an honest environmental event, not attacker-controlled, which lowers likelihood; but the inflated claim accrues automatically to the APR0 requester whenever it occurs — no privileged misbehavior needed.
- Medium likelihood: conditional on a default with an active APR0 bucket and override interest, the leak is deterministic.

### Recommendation
Move the APR0 state mutation off the pre-funding path, or make it reversible on default:

- Option A: split `prepareStopEpochWithApr0` into a pure `preview` (computes `_apr0NetInterest`, adjusted fees) called before the funding check, and a `commit` (writes `pendingWithdraws`, `apr0RateByEpoch`, clears `apr0TotalPrincipal`) invoked only inside the `try` success branch alongside `collectWithdrawFunds`.
- Option B: on the `_handleBorrowerDefault` paths, call a strategy rollback that subtracts the just-added `_apr0NetInterest` from `pendingWithdraws`, deletes `apr0RateByEpoch[epochNumber]`, and restores `apr0TotalPrincipal`.
- Also verify the non-APR0 path: any mutation of `pendingWithdraws`/`expectedEpochInterest`/`pendingWithdrawFees` persisted before the funding result should be rolled back or excluded from `defaultPendingClaimBasis`.

### Proof of Concept
```solidity
// test/foundry/ — conceptual PoC, Foundry fork
// Setup: CDO with IdleCreditVault strategy, unscaledApr == 0 (APR0 epoch),
// isProgrammableBorrower or mocked borrower that will fail funding.

function testApr0InterestLeaksIntoDefaultBasis() external {
    // 1. Lender deposits AA during buffer period.
    idleCDO.depositAA(100_000 * ONE_SCALE);

    // 2. While APR == 0, attacker requests withdraw -> lands in apr0Users / apr0TotalPrincipal.
    cdoEpoch.requestWithdraw(attackerShares, address(AAtranche));
    assertGt(strategy.apr0TotalPrincipal(), 0);

    // 3. Manager starts epoch; warp past epochEndDate.
    vm.prank(manager); cdoEpoch.startEpoch();
    vm.warp(cdoEpoch.epochEndDate() + 1);

    uint256 pendingBefore = strategy.pendingWithdraws();

    // 4. Manager calls stopEpochWithDuration with override _interest > 1.
    //    prepareStopEpochWithApr0 adds _apr0NetInterest to pendingWithdraws.
    //    Borrower then fails funding -> onStopEpoch returns false -> _handleBorrowerDefault.
    //    (Configure borrower/vault so onStopEpoch returns false.)
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, overrideInterest, duration, 0);

    assertTrue(cdoEpoch.defaulted());
    uint256 leaked = strategy.pendingWithdraws() - pendingBefore;
    assertGt(leaked, 0, "APR0 interest persisted despite no funding");

    // 5. Owner finalizes default with recovered amount R.
    vm.prank(owner);
    cdoEpoch.finalizeDefault(recoveredAmount, recoverySource);

    // 6. Show dilution: defaultRecoveryPrice is lower than
    //    reserveAmount * RECOVERY_FULL / (totalBasis - leaked).
    //    Honest claimant's payout is reduced by recoveryPrice * leaked / totalBasis,
    //    and the attacker's _claimDefaultedWithdrawRequest pays on basis including `leaked`.
}
```
