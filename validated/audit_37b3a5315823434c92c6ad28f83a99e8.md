### Title
Builder withdrawal `Withdrawal.amount` is not capped to actual balance decrease, causing the execution layer to mint Gwei uncommitted by the beacon chain - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` copies the raw, uncapped `BuilderPendingWithdrawal.amount` into the `Withdrawal.amount` field that is committed to the execution layer, while `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from the builder's CL-side balance. When a builder's balance is insufficient to cover a pending withdrawal, the CL commits an EL withdrawal for the full requested amount but only destroys the builder's actual (smaller) balance, breaking the invariant that Gwei paid out to an address must equal Gwei destroyed on the CL side.

### Finding Description
`get_builder_withdrawals` builds the `Withdrawal` object directly from the pending withdrawal's requested `amount`, without capping it to the builder's balance: [1](#0-0) 

This `Withdrawal` (with the *uncapped* `amount`) becomes part of `state.payload_expected_withdrawals`, which the execution layer is required to honor by minting/crediting that exact amount to `fee_recipient`.

Meanwhile, `apply_withdrawals` deducts only the *capped* amount from the builder's CL balance: [2](#0-1) 

The test suite explicitly documents and asserts this exact mismatch as intended behavior: when a builder's balance is less than the requested withdrawal amount, the balance deduction is "capped to available balance" but the emitted `withdrawal.amount` is still the full, uncapped "requested amount": [3](#0-2) [4](#0-3) 

Concretely: builder balance = 1 ETH, pending withdrawal amount = 5 ETH.
- Before: builder.balance = 1 ETH, EL has not yet minted anything.
- After `process_withdrawals`: builder.balance = 0 (deducted `min(5, 1)=1` ETH), but `payload_expected_withdrawals` contains a `Withdrawal(amount=5 ETH)` which the execution layer is bound to pay to `fee_recipient` in the corresponding execution payload.

The equality broken is: `Gwei destroyed on CL == Gwei paid out on EL`. Here only 1 ETH is destroyed on the CL side while 5 ETH is paid out on the EL side — 4 ETH of Gwei is effectively created out of thin air and paid to the builder's `fee_recipient`, a non-owner in the sense that no corresponding stake backs that extra payment.

This is analogous to the reported stETH bug: the contract records/commits to the requested amount without verifying/adjusting for the amount that is actually available/transferred, and the mismatch is silently accepted rather than causing a rejection or being capped consistently in both places.

### Impact Explanation
This falls under "Gwei created ... or paid to a non-owner": the execution layer will mint value to `fee_recipient` that is not backed by an equivalent balance reduction on the beacon chain, inflating supply and rewarding whichever address the pending withdrawal names, disconnected from actual builder stake. This is a valid Critical/High-tier equality-break per the given impact categories, not merely a DoS.

### Likelihood Explanation
This condition is reachable whenever a `BuilderPendingWithdrawal.amount` (recorded via `process_execution_payload_bid`/`settle_builder_payment`) exceeds the builder's `balance` at the time `get_builder_withdrawals`/`apply_withdrawals` run. Because `builder.balance` can decrease between when a payment is queued (bid time) and when it is settled/withdrawn (e.g., via other withdrawals, exits, or additional payments consuming the same balance), and `can_builder_cover_bid` checks are only performed at bid-acceptance time (not re-verified at withdrawal-application time), this scenario is a normal consequence of protocol-permitted state transitions rather than requiring a malicious actor. Multiple pending payments/withdrawals for the same builder can be queued and settle later against a balance that has since shrunk, e.g. via `get_pending_balance_to_withdraw_for_builder` accounting being bypassed by subsequent decreases from other builder-balance-reducing paths.

### Recommendation
Ensure `Withdrawal.amount` emitted to the execution layer for builder withdrawals is capped to the same `min(withdrawal.amount, builder_balance)` value that is actually deducted from `state.builders[builder_index].balance`, computed at the point the withdrawal is generated in `get_builder_withdrawals`, so that CL-side balance destruction and EL-side payment always agree.

### Proof of Concept
Using the existing spec test harness (`prepare_process_withdrawals` / `run_gloas_withdrawals_processing`):
1. Register builder 0 with `balance = 1_000_000_000` (1 ETH).
2. Queue `builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000)]` (5 ETH).
3. Call `process_withdrawals(state)`.
4. Observe: `state.builders[0].balance == 0` (only 1 ETH deducted), while `state.payload_expected_withdrawals[0].amount == 5_000_000_000` (5 ETH committed to the EL for `fee_recipient`).
This exact scenario is already codified in `test_builder_withdrawal_insufficient_balance` [3](#0-2) , which asserts `withdrawal_amounts_builders={builder_index: withdrawal_amount}` (the uncapped 5 ETH) simultaneously with `builder_balances={builder_index: 0}`, confirming the CL/EL payment mismatch as current spec behavior.

def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
        - next_withdrawal_index: Incremented by 1
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=[builder_index],
        builder_withdrawal_amounts={builder_index: withdrawal_amount},
        builder_balances={builder_index: available_balance},
    )

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

    assert_process_withdrawals(
        spec,
        state,
        pre_state,
        withdrawal_count=1,
        builder_balances={builder_index: 0},
        builder_pending_delta=-1,
        withdrawal_index_delta=1,
        withdrawal_amounts_builders={builder_index: withdrawal_amount},
    )
