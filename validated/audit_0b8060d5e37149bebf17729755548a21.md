### Title
Builder withdrawals commit the full requested amount to the execution layer while the beacon state only deducts the capped (available) amount, minting Gwei out of thin air — ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` builds the `Withdrawal` objects that are committed to `state.payload_expected_withdrawals` (and which the execution layer is required to honor/mint in full), using the *uncapped* requested `amount` from `state.builder_pending_withdrawals`. The consensus-layer balance deduction in `apply_withdrawals`, however, caps the actual decrease to `min(withdrawal.amount, builder_balance)`. When a builder's pending withdrawal request exceeds its actual balance, the CL "marks off" only part of the shortfall (analogous to unrecognized bad debt), while the committed/minted amount sent to the EL stays at the full, uncapped figure — creating Gwei that is paid out to the fee recipient without any corresponding balance decrease anywhere in the state.

### Finding Description
`get_builder_withdrawals` (specs/gloas/beacon-chain.md, "New `get_builder_withdrawals`") constructs each `Withdrawal` as: [1](#0-0) 

using `amount=withdrawal.amount` directly from `state.builder_pending_withdrawals`, with no capping against `state.builders[builder_index].balance`.

This uncapped list feeds `get_expected_withdrawals` → `state.payload_expected_withdrawals`: [2](#0-1) 

Per the spec's own note on `process_withdrawals`, any block whose parent commits to these withdrawals requires the execution layer to honor them (i.e., mint/pay the committed amount): [3](#0-2) 

Meanwhile, the actual CL-side balance mutation in `apply_withdrawals` caps the deduction to the builder's real balance: [4](#0-3) 

So if `state.builder_pending_withdrawals` contains an entry whose `amount` exceeds `state.builders[builder_index].balance`, the beacon state commits (and the EL mints/pays) the full requested amount, but the builder's balance is only reduced to zero — the difference is never subtracted from anyone. This is the exact "bad-debt not marked off" pattern from the reference report: the "total committed/liability" (the withdrawal amount promised to the EL) is higher than the actual backing asset (the builder's real balance), and nothing in the state transition reconciles the gap. Instead of "last lender loses," here it's "no one loses" — the excess Gwei is simply created and paid to the `fee_recipient`, breaking the invariant that a Gwei paid out must come from a debited balance.

This is not a hypothetical edge case invented by the analysis — the spec's own test suite explicitly exercises and asserts this exact behavior as the intended, spec-conformant outcome: [5](#0-4) 
and the accompanying test documentation states plainly that the requested amount, not the capped amount, is what appears in `payload_expected_withdrawals`: [6](#0-5) 

Note the contrast with how the spec authors *did* address the analogous risk for ordinary validator withdrawals: the `process_withdrawals` note explicitly explains that immediate (same-slot) balance deduction was chosen specifically to avoid `decrease_balance` saturating at zero while the EL mints the full committed amount, calling out that such saturation "creates a net supply inflation" for validators. No equivalent safeguard or even an accepted-risk note exists for the builder path, where the identical saturation (via `min(withdrawal.amount, builder_balance)`) is applied to the CL-side deduction but not to the EL-committed `Withdrawal.amount`.

I was not able to fully trace, within the given iteration budget, whether the bid-acceptance checks in `process_execution_payload_bid`/`settle_builder_payment` guarantee that `builder_pending_withdrawals` entries can never exceed the builder's balance at settlement time (e.g., via races between multiple pending payments/withdrawals or via `process_builder_exit_request`/sweep withdrawals interacting with pending entries in the same slot). The explicit unit test that directly constructs this insufficient-balance state and asserts it as valid output strongly suggests the state-transition function is expected to tolerate (not prevent) this condition, which is the root of the issue regardless of how the state is reached.

### Impact Explanation
If `state.builder_pending_withdrawals` can contain (through any reachable sequence of blocks/bids/exits) an entry whose amount exceeds the builder's current balance, the resulting block commits a withdrawal amount to the execution layer that is larger than what was actually debited from the builder. Since the execution layer is required to honor the full committed amount, Gwei is effectively minted and paid to the `fee_recipient` without being backed by any balance decrease in the beacon state — a direct, unauthorized Gwei-creation event paid to a party (the fee recipient) that was not entitled to the shortfall. This matches the "Critical: Gwei created ... paid to a non-owner" impact class.

### Likelihood Explanation
Likelihood depends on whether the state-transition function elsewhere enforces that `builder_pending_withdrawals` entries can never exceed the corresponding builder's balance at settlement time. The spec includes tests that directly construct and validate the insufficient-balance case as legitimate input/output, indicating the code path is considered reachable and is treated as "capped deduction, uncapped commitment" by design rather than as an invariant violation to reject. This raises likelihood, though full confirmation of an end-to-end reachable sequence via bids/settlement (rather than directly injected test state) was not completed here.

### Recommendation
Cap the `Withdrawal.amount` constructed in `get_builder_withdrawals` (and any other builder-withdrawal constructors) to `min(withdrawal.amount, state.builders[builder_index].balance)` at the point the `Withdrawal` is built and committed to `payload_expected_withdrawals`, so the amount promised to (and minted by) the execution layer always matches the amount actually deducted from the builder's balance — mirroring the treatment already given to `get_builders_sweep_withdrawals`, which correctly withdraws `builder.balance` (the real, available amount) rather than a separately tracked requested amount.

### Proof of Concept
1. Set `state.builders[0].balance = 1_000_000_000` (1 ETH).
2. Append `BuilderPendingWithdrawal(fee_recipient=X, amount=5_000_000_000, builder_index=0)` to `state.builder_pending_withdrawals`.
3. Call `process_withdrawals(state)`.
4. `get_builder_withdrawals` produces `Withdrawal(amount=5_000_000_000, address=X, ...)`, which is placed in `state.payload_expected_withdrawals` and must be honored by the EL (X receives 5 ETH on the execution layer).
5. `apply_withdrawals` only decrements `state.builders[0].balance` by `min(5_000_000_000, 1_000_000_000) = 1_000_000_000`, leaving it at 0.
6. Net effect: 4 ETH was paid out on the execution layer with no corresponding balance debited anywhere in the beacon state — Gwei created and paid to a non-owner. [7](#0-6)
