### Title
Unbounded per-notification account-data serialization/clone in `check_commitment_and_notify`/`filter_account_result` allows a single accountSubscribe on a large account to impose unbounded CPU/memory cost per notification tick - ([File: rpc/src/rpc_subscriptions.rs])

### Summary
`filter_account_result` in `rpc_subscriptions.rs` calls `encode_ui_account` directly on the full `AccountSharedData` returned from `bank.get_account_modified_slot`, with no upfront size check comparable to the one used by the plain `getAccountInfo`/`getProgramAccounts` RPC path. Every commitment tick that touches a modified large account, the pubsub thread clones and encodes the entire account payload (up to the runtime's max account size) before any size guard can reject it, and for `Base64`/`Base64Zstd`/`JsonParsed` encodings there is no cap at all.

### Finding Description
The call chain is: `notify_subscribers(CommitmentSlots)` → `enqueue_notification` → `notify_watchers` (`rpc/src/rpc_subscriptions.rs:908-994`) → for each `SubscriptionParams::Account` subscription → `check_commitment_and_notify` (`rpc/src/rpc_subscriptions.rs:136-175`) with `bank_method = |bank, params| bank.get_account_modified_slot(&params.pubkey)` and `filter_results = filter_account_result`.

Inside `check_commitment_and_notify`, `bank_method(&bank, params)` (line 156) unconditionally fetches/clones the full `AccountSharedData` for the subscribed pubkey — there is no size cap here; the cost is exactly the size of whatever data the attacker stored in that account.

`filter_account_result` (`rpc/src/rpc_subscriptions.rs:370-392`) then calls `encode_ui_account(&params.pubkey, &account, params.encoding, None, None)` directly, with **no pre-check equivalent to `rpc.rs`'s `encode_account`**, which for `getAccountInfo`/`getProgramAccounts` rejects (`Err`) `Binary`/`Base58` encodings whose data exceeds `MAX_BASE58_BYTES` (128 bytes) *before* attempting to encode (`rpc/src/rpc.rs:2575-2601`). In the pubsub path:
- For `Binary`/`Base58` encoding, `encode_ui_account` → `encode_bs58` (`account-decoder/src/lib.rs:34-44`) only checks size *after* `slice_data` has already referenced/operated on the full account buffer, and it simply substitutes the string `"error: data too large for bs58 encoding"` — it does not reject the subscription or bound the earlier clone/serialization cost.
- For `Base64`/`Base64Zstd`/`JsonParsed`, there is **no size cap whatsoever** — `encode_ui_account` (`account-decoder/src/lib.rs:63-91`) will base64-encode (or zstd-encode, or JSON-parse) the entire account data on every matching notification tick.

Since `account_subscribe` in `rpc_pubsub.rs` defaults `encoding` to `UiAccountEncoding::Binary` (`rpc/src/rpc_pubsub.rs:436-441`) but allows the caller to explicitly request `Base64`, an unprivileged client can subscribe with `{"encoding": "base64"}` to an account it fully controls (e.g., a large PDA/account it created and repeatedly writes to, sized up to the runtime maximum account size), and every commitment-slot notification will clone the full account and base64-encode it on the shared pubsub notification thread, with cost proportional to attacker-chosen on-chain data size rather than any fixed protocol limit.

This differs from the synchronous RPC methods (`getAccountInfo`, `getMultipleAccounts`, `getProgramAccounts`), which route through `encode_account` (`rpc/src/rpc.rs:2575-2601`) and reject over-limit `Binary`/`Base58` requests before performing costly work, and are also throttled by the RPC request-rate model. The subscription path bypasses that check entirely and, once established, re-executes the unbounded-cost encode on every commitment update without additional client requests.

### Impact Explanation
A single low-rate `accountSubscribe` (one WebSocket subscribe call) on an attacker-controlled account causes the shared pubsub notification thread (`notify_watchers`, used by all subscribers via `rayon`'s `into_par_iter`) to perform an unbounded clone + serialization/encoding proportional to the account's data size on every commitment tick that touches that account, without any explicit per-subscription byte cap. This matches the "unbounded cost for a single low-rate call" scoped-impact category: sustained CPU/memory cost imposed on validator RPC infrastructure by one subscriber controlling its own account size, independent of any explicit protocol limit designed to bound per-subscription cost.

### Likelihood Explanation
Fully feasible with attacker-only capabilities: the attacker creates/owns an account of large size (bounded only by account size limits enforceable via ordinary transactions, e.g. `system_instruction::allocate`/CPI-based account growth), issues a single `accountSubscribe` with `encoding: "base64"` (or default `Binary`, which still incurs the pre-check clone cost even though bs58 encoding is skipped), and then triggers or waits for any transaction modifying the account. Each subsequent commitment-slot notification re-triggers the unbounded encode with no additional requests needed — well within the "one call per `CLUSTER_SLOT_TIME_TARGET / 2`" constraint since the subscription itself is one WebSocket call.

### Recommendation
Add an explicit per-subscription/per-notification size guard in `filter_account_result` (and analogously in `filter_program_results`) before calling `encode_ui_account`/`get_parsed_token_account`, mirroring or reusing `rpc.rs`'s `encode_account` size check for `Binary`/`Base58`, and additionally enforce a maximum notification payload size cap for `Base64`/`Base64Zstd`/`JsonParsed` encodings (e.g., skip/degrade notification or send an explicit error/oversized marker instead of performing full serialization) so that the cost of a single subscription notification is bounded by a fixed limit rather than by attacker-controlled account size.

```rust
// rpc/src/rpc_subscriptions.rs (test module)
#[test]
fn test_account_subscribe_large_account_unbounded_encode() {
    let GenesisConfigInfo { genesis_config, mint_keypair: alice, .. } =
        create_genesis_config(1_000_000_000);
    let bank = Bank::new_for_tests(&genesis_config);
    let bank_forks = BankForks::new_rw_arc(bank);
    let bank0 = bank_forks.read().unwrap().get(0).unwrap();
    let bank1 = Bank::new_from_parent(bank0, SlotLeader::default(), 1);
    bank_forks.write().unwrap().insert(bank1);

    let target = Keypair::new();
    // Attacker-controlled: store a ~10MiB account directly via bank API
    // (represents result of attacker-authored transactions growing their own account).
    let big_data = vec![0u8; 10 * 1024 * 1024];
    let account = AccountSharedData::create_from_existing_shared_data(
        1, Arc::new(big_data), system_program::id(), false, 0,
    );
    bank_forks.read().unwrap().get(1).unwrap().store_account(&target.pubkey(), &account);

    let subscriptions = Arc::new(RpcSubscriptions::new_for_tests(
        Arc::new(AtomicBool::new(false)),
        Arc::new(AtomicU64::default()),
        bank_forks.clone(),
        Arc::new(RwLock::new(BlockCommitmentCache::default())),
        OptimisticallyConfirmedBank::locked_from_bank_forks_root(&bank_forks),
    ));
    let (rpc, mut receiver) = rpc_pubsub_service::test_connection(&subscriptions);

    rpc.account_subscribe(
        target.pubkey().to_string(),
        Some(RpcAccountInfoConfig {
            commitment: Some(CommitmentConfig::processed()),
            encoding: Some(UiAccountEncoding::Base64), // no size cap for this encoding
            data_slice: None,
            min_context_slot: None,
        }),
    ).unwrap();

    let start = std::time::Instant::now();
    subscriptions.notify_subscribers(CommitmentSlots { slot: 1, ..CommitmentSlots::default() });
    let response = receiver.recv();
    let elapsed = start.elapsed();

    // EXPECTED (if fixed): notification should be size-capped / rejected / degraded
    // ACTUAL (current behavior): full ~10MiB base64 string (~13.3MB) is produced per tick,
    // demonstrating unbounded memory/CPU cost with no explicit protocol limit.
    assert!(response.len() < 1_000_000, "notification payload should be capped, got {} bytes in {:?}", response.len(), elapsed);
}
```
Expected assertion failure on current code demonstrates the payload is not size-capped; a fix should either reject the subscription/encoding combination up front (as `encode_account` does for Binary/Base58) or cap/degrade oversized notification payloads before serialization.
