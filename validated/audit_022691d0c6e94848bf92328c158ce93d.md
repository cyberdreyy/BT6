### Title
`InitializeBuffer` on the BPF Upgradeable Loader sets an unsigned, unverified authority on an already-created account, enabling front-run hijack of program-deploy buffers - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The upgradeable BPF loader's `InitializeBuffer` instruction transitions a buffer account from `Uninitialized` to `Buffer { authority_address }` and sets the `authority_address` from whatever pubkey is passed at account index 1, with **no signer check on that account and no signer check on the buffer account itself**. Because Agave's own program-deploy workflow explicitly creates the buffer account (via `system_instruction::create_account`, owned by `bpf_loader_upgradeable`) and only later calls `InitializeBuffer`/`Write` — and even documents resuming this across process restarts — there is a real, exploitable window between account creation and initialization where any third party can call `InitializeBuffer` first and claim the authority for themselves.

### Finding Description
`process_loader_upgradeable_instruction` handles `InitializeBuffer` as follows: [1](#0-0) 

Only `check_number_of_instruction_accounts(2)` is performed — there is no `is_instruction_account_signer` check for either the buffer account (index 0) or the authority account (index 1), unlike the `Write` handler right below it which explicitly requires the authority to sign: [2](#0-1) 

This means *any* transaction — sent by an unrelated party who merely knows the buffer account's public key — can call `InitializeBuffer` on that account and set an arbitrary `authority_address`, as long as the account is currently `Uninitialized` and owned by the upgradeable loader.

The Agave CLI's own deploy flow separates account creation from initialization into a workflow that is explicitly designed to be resumable across transactions (and even process crashes), which creates exactly the front-runnable gap the external report describes: [3](#0-2) [4](#0-3) 

The buffer keypair/mnemonic is reported specifically "so that users always have a way to resume in case of process crash," confirming that `CreateAccount` and `InitializeBuffer` are not guaranteed to be atomic in the same transaction. Once the `CreateAccount` transaction lands on-chain (buffer account now exists, owned by `bpf_loader_upgradeable`, state `Uninitialized`), the account's pubkey and existence are public. Any attacker can race the legitimate depoyer's next transaction (which would normally send `InitializeBuffer` with the real authority) and submit their own `InitializeBuffer` naming themselves as `authority_address`.

Once the attacker is set as the buffer authority, they can:
- Cause the legitimate `Write`/`DeployWithMaxDataLen`/`Upgrade` calls to fail with `IncorrectAuthority`, permanently freezing the deploy flow using that specific buffer account (DoS on the deploy, and the rent-exempt lamports already deposited into the buffer become effectively stuck unless the attacker cooperates), and
- Call `Close` (using themselves as the recognized authority) to drain the buffer account's rent-exempt lamports to a recipient of their choosing, since `Close` only validates the stored authority and its signature, not who originally intended it: [5](#0-4) 

This is the direct analog of the reported bug class: an externally callable "initialize" function that sets a privileged field (an admin/authority) with no ownership binding to the account creator, making it front-runnable for fund theft or DoS.

### Impact Explanation
An attacker who front-runs `InitializeBuffer` gains full control (`authority_address`) over a buffer account that a legitimate user funded with rent-exempt lamports for a program deployment. Depending on attacker action, this results in:
- Loss of the rent-exempt lamports deposited into the buffer account (attacker can `Close` it to their own account), and/or
- A denial of service on the intended program deployment/upgrade, since all subsequent loader operations require the (now attacker-controlled) authority to sign.

This is a Medium-severity issue: it requires the attacker to observe and race a specific, predictable workflow (a buffer account created but not yet initialized), and the value at risk is limited to the rent-exempt deposit of the buffer account plus deployment disruption, not core validator/consensus safety.

### Likelihood Explanation
Likelihood is moderate. The scenario requires: (1) a user creating the buffer account and (2) sending `InitializeBuffer` in a separate transaction (as opposed to bundling both in one atomic transaction via the standard `create_buffer` helper). Agave's own CLI explicitly supports and documents this non-atomic, resumable flow (`--buffer <SIGNER>` "used to resume a failed deploy", and mnemonic reporting for crash recovery), so the vulnerable window is a supported, real-world usage pattern rather than a contrived edge case. An attacker monitoring the network for newly created, loader-owned, `Uninitialized` buffer accounts can race to claim them.

### Recommendation
Require that `InitializeBuffer`'s buffer account be a signer (proving the caller controls the keypair used to create it), or otherwise bind buffer creation and initialization atomically (e.g., require the fee payer/creator of the account to also be checked, or enforce that `InitializeBuffer` can only be processed as part of the same transaction that created the account). At minimum, document and encourage always bundling `CreateAccount` + `InitializeBuffer` in a single atomic transaction (as `solana_loader_v3_interface::instruction::create_buffer` already does), and consider deprecating/hardening the CLI's resumable, non-atomic buffer-creation flow to close the front-running window.

### Proof of Concept
1. Legitimate user submits transaction A: `system_instruction::create_account(payer, buffer_pubkey, lamports, size, bpf_loader_upgradeable::id())`, creating an `Uninitialized` buffer account owned by the upgradeable loader.
2. Before the user's follow-up transaction B (`InitializeBuffer` naming themselves as authority) lands, an attacker observes transaction A on-chain/in the mempool and submits transaction C: `InitializeBuffer` on the same `buffer_pubkey`, naming the attacker's own pubkey as `authority_address`. As shown in `process_loader_upgradeable_instruction`, neither the buffer account nor the authority account is required to sign, so this succeeds: [1](#0-0) 
3. The legitimate user's transaction B now fails because the buffer's state is already `Buffer { authority_address: Some(attacker) }` (`AccountAlreadyInitialized` if resent as `InitializeBuffer`, or `IncorrectAuthority`/`MissingRequiredSignature` if resent as `Write`).
4. The attacker, now the recognized authority, calls `UpgradeableLoaderInstruction::Close` with themselves as the recipient, draining the buffer account's rent-exempt lamports. [5](#0-4)
