### Title
External-initiator credential holder can trigger a run of ANY job by numeric ID via POST /v2/jobs/:ID/runs, bypassing initiator-to-job binding - ([File: core/web/auth/auth.go], [File: core/web/pipeline_runs_controller.go])

### Summary
`AuthenticateExternalInitiator` sets both `SessionExternalInitiatorKey` and a synthetic `SessionUserKey` (`&clsessions.User{Role: clsessions.UserRoleRun}`) on the gin context. `PipelineRunsController.Create` then branches on `auth.GetAuthenticatedUser(c)` (`isUser`) to decide whether to allow numeric-job-ID runs, but that check cannot distinguish a real session/token user from an external-initiator credential, since both populate `SessionUserKey`. As a result, any external-initiator credential can invoke `RunJobV2` for an arbitrary numeric job ID, not just the job(s)/webhook associated with that initiator.

### Finding Description
- `AuthenticateExternalInitiator` (`core/web/auth/auth.go:119-151`) validates only the EI access key/secret against `bridges.ExternalInitiator`; it does not bind the credential to a specific job ID. It sets:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [1](#0-0) 

- Route wiring in `core/web/router.go` allows `POST /v2/jobs/:ID/runs` to be reached via `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession`, guarded only by `auth.RequiresRunRole`:
```go
userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateExternalInitiator,
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
``` [2](#0-1) 

`RequiresRunRole` only checks `user.Role != UserRoleView` [3](#0-2) , and since the EI-set user has `Role: UserRoleRun`, it passes.

- In `PipelineRunsController.Create` (`core/web/pipeline_runs_controller.go:89-128`), the code comments state "only users are allowed to run jobs using int IDs - EIs not allowed," but the actual gate is:
```go
_, isUser := auth.GetAuthenticatedUser(c)
if isUser {
    jobID64, err := strconv.ParseInt(idStr, 10, 32)
    if err == nil {
        jobID = int32(jobID64)
        jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
        ...
    }
}
``` [4](#0-3) 

Since `GetAuthenticatedUser` (`core/web/auth/auth.go:178-187`) simply reads `SessionUserKey` from context — which `AuthenticateExternalInitiator` always populates — `isUser` is `true` for any successfully authenticated external initiator, defeating the intended "EIs not allowed" restriction. `RunJobV2` (`core/services/chainlink/application.go:1126-1189`) takes only a bare `jobID int32` and performs no check that the job is bound to, or was created by/for, the calling external initiator — it will execute whatever job matches that ID (OCR, cron, VRF, etc.), as long as manual runs aren't disabled by `build.IsProd()`.

The webhook-UUID path (job's own external-initiator UUID binding) is explicitly rejected early (`uuid.Parse(idStr)` branch returns 422 because that job type was removed), so the only reachable job-run path for EI credentials is the numeric-ID path, which has no initiator-to-job binding check at all.

### Impact Explanation
An attacker holding a legitimately-issued but restricted external-initiator credential (meant only to trigger a specific webhook-type job) can instead trigger execution of arbitrary jobs owned by other configurations/initiators on the same node by guessing/enumerating small integer job IDs. This is an authorization/binding bypass ("cross-initiator job run") — matches Chainlink bounty categories for unauthorized job run / access control bypass. Actual severity depends on `build.IsProd()`: if this flag disables manual runs in production hardened builds, the concrete impact is confined to non-`IsProd` deployments; this could not be fully confirmed from available code, so this caveat should be verified.

### Likelihood Explanation
- Precondition: attacker must already hold a valid external-initiator access key/secret pair (issued by an admin/edit-role user for one specific job/initiator).
- No knowledge of which job the credential is "supposed" to trigger is required beyond guessing sequential integer job IDs, which are commonly small and predictable.
- No additional privilege escalation step is needed; a single POST request suffices.
- Feasibility is high assuming the node runs with `build.IsProd()` false (development/staging configurations, or however that flag is actually gated) — this is the main open uncertainty.

### Recommendation
- Do not set `SessionUserKey` in `AuthenticateExternalInitiator`; instead track EI authentication solely via `SessionExternalInitiatorKey`, and have `PipelineRunsController.Create` explicitly check `auth.GetAuthenticatedExternalInitiator(c)` to reject (or properly scope) EI-authenticated numeric-ID run requests, matching the existing code comment's intent.
- Alternatively, when authenticated via `AuthenticateExternalInitiator`, verify that the target job's `ExternalInitiatorWebhookSpecs`/binding actually references the authenticated initiator before invoking `RunJobV2`.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/pipeline_runs_controller_test.go` / `core/services/job/runner_integration_test.go` patterns):
1. Start a `TestApplication`; create two external initiators `eiA`, `eiB` via `cltest.CreateExternalInitiatorViaWeb`.
2. Create Job A (e.g. a cron or OCR job unrelated to any webhook) via the authenticated user session (`cltest.CreateJobViaWeb`), record `jobA.ID`.
3. Authenticate as `eiB` (headers `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` set to eiB's credentials, not tied to jobA at all).
4. POST to `/v2/jobs/{jobA.ID}/runs` using eiB's credentials.
5. Assert: expected behavior is `401`/`403` (initiator not bound to job) but current code returns `200` with a `pipelineRun` resource, and `pipeline_runs` count for jobA increases — confirming the binding bypass.
6. Repeat with eiA's own job to show it also can run any other job it wasn't created for, proving no per-job scoping exists for external initiators.

func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
