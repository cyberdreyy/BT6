### Title
Write-off escrow accepts requests with zero/insufficient underlying price, letting anyone seize escrowed tranche tokens for free - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` enforces only `amount != 0` on the tranche leg and performs no validation on `underlyingsRequested`. A request with `underlyingsRequested == 0` (or a value far below the tranche tokens' market/redemption value) is accepted and locked in escrow. `fullfillWriteOffRequest` then lets any EOA satisfy such a request by paying only `_underlyings < currentRequest.underlyings` → with a zero-price request the fulfiller pays literally nothing and receives the victim's tranche tokens. This is the credit-vault analog of CWE-521 (weak password requirements): a user-supplied "protection" parameter is accepted at a trivially weak value, converting a security check into an empty one and enabling theft by an unprivileged attacker.

### Finding Description
In `createWriteOffRequest` the only guards are `isEpochRunning()` and `amount == 0` reverting; `underlyingsRequested` is stored verbatim into `userRequests[msg.sender].underlyings` and accumulated into `pendingUnderlyings` with no lower bound and no sanity check against the current tranche price (`virtualPrice`). [1](#0-0) 

`fullfillWriteOffRequest` is explicitly callable by "any wallet". It requires `currentRequest.tranches == _tranches` and `_underlyings >= currentRequest.underlyings`. When `underlyings` is `0`, the `_underlyings < currentRequest.underlyings` check passes with `_underlyings == 0`, the safeTransferFrom pulls 0 underlying, the exit-fee branch computes `_totFee == 0`, the user receives 0 underlying, and the fulfiller receives all `_tranches` tranche tokens for free. [2](#0-1) 

The broken invariant is fair exchange / one receipt one payout: escrowed tranche tokens are supposed to be released only in exchange for the lender-specified consideration, but the contract permits that consideration to be zero, so the escrow effectively gifts the tokens. The same applies to dust-priced requests (e.g., `underlyingsRequested == 1` wei on a request worth thousands of USDC): the "price" requirement exists but is so weak it provides no protection — exactly the Modoboa `password = "1"` pattern.

Epoch phase: running epoch only (`EpochNotRunning` guard), any mode. Attacker requirements: none — any EOA can call `fullfillWriteOffRequest`. Existing guards do not stop it: `nonReentrant` is irrelevant, `WrongRequest` passes trivially, and no owner/manager action is involved.

### Impact Explanation
Direct theft of user funds. A lender who creates a write-off request with a missing, zero, or fat-fingered `underlyingsRequested` (e.g., forgetting decimals, passing underlying in tranche units) permanently loses the full escrowed tranche position to the first caller — a bot can monitor `userRequests` creation events and fulfill in the same block. Loss is quantified as the full redemption value of the escrowed tranche tokens (`currentRequest.tranches` worth of tranche tokens, claimable via `withdrawAA/withdrawBB` or default claims), with zero cost to the attacker.

### Likelihood Explanation
Medium. It requires a victim to submit a weak/zero price, which is a user error — but it is a realistic one (the function takes two bare `uint256`s with no event or UI-enforced floor, and a request can also be topped up repeatedly, compounding a bad price). No privileged cooperation is needed and fulfillment is atomic and anonymous. Mitigating factors: the victim can call `deleteWriteOffRequest` to reclaim tokens before fulfillment, so the window closes if they notice; this caps the exploit window but does not remove the vulnerability since fulfillment can happen in the same block as creation.

### Recommendation
Add minimum-strength validation to the request price, mirroring a password policy:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol, createWriteOffRequest
if (underlyingsRequested == 0) revert NotAllowed();
// optionally enforce a floor vs current tranche value, e.g.
// require(underlyingsRequested >= amount * minPriceBps * virtualPrice(tranche) / (FULL_VALUE * ONE_TRANCHE));
```

At minimum revert on `underlyingsRequested == 0`; ideally enforce a configurable `minPriceBps` relative to the current tranche `virtualPrice` so requests cannot be priced below, e.g., 50–90% of redemption value. Also emit an event with `tranches` and `underlyings` so monitors/victims can detect bad requests before fulfillment.

### Proof of Concept
Foundry fork test sketch (assumes a deployed vault `cv`, escrow `escrow`, tranche token, underlying `usdc`, and a whitelisted/KYC'd lender):

```solidity
function testWriteOffEscrowZeroPriceTheft() external {
    // Epoch running: cv.startEpoch() already called by manager
    uint256 trancheAmt = 10_000e18;          // victim's tranche tokens
    deal(tranche, lender, trancheAmt);

    // Victim creates request with weak price: 0 underlyings
    vm.startPrank(lender);
    IERC20(tranche).approve(address(escrow), trancheAmt);
    escrow.createWriteOffRequest(trancheAmt, 0);   // accepted: no min price
    vm.stopPrank();

    // Attacker (any EOA) fulfills paying nothing
    address attacker = makeAddr("attacker");
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(lender, trancheAmt, 0);

    // Attacker got all tranche tokens for free; lender got 0 underlying
    assertEq(IERC20(tranche).balanceOf(attacker), trancheAmt);
    assertEq(usdc.balanceOf(lender), 0);
}
```

Notes/uncertainty: a request priced *above* zero but far below fair value is equally exploitable and needs no user error beyond a decimals mistake; the PoC is reproducible against the unit-test harness in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol` rather than requiring a mainnet fork, since the escrow's logic is self-contained.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);

    // If the fulfiller is the borrower, they can then choose to either keep the tranche tokens or write them off via
    // IdleCDOEpochVariant.writeOffDeposit method.
  }
```
