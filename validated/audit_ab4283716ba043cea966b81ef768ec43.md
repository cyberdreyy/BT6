Now I need the ordering of `collectWithdrawFunds` vs `epochNumber` increment in `stopEpoch`.### Title
Loss-adjusted withdraw receipts can escape their haircut when `lossRecoveryPriceByEpoch` is keyed to a different epoch than `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` keys each pending withdraw receipt to the epoch stored in `lastWithdrawRequest[_user]` (set at request time), but keys the realized-loss haircut to `epochNumber` at `collectWithdrawFunds` time. If those two values diverge — i.e. `epochNumber` is incremented inside the same `stopEpoch`/`stopEpochWithDuration` flow before `collectWithdrawFunds` runs — the haircut is written to the new epoch while every receipt still points at the old one. `lossRecoveryPriceByEpoch[oldEpoch]` then reads as `0`, so the receipt is treated as fully funded and pays out at par via `_claimFundedWithdrawRequest`, even though the strategy only collected the haircut amount. The overpayment is drained from underlyings that back other claimants and LPs.

### Finding Description
At request time, the receipt is bound to the epoch in which it was opened:

- `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` in `requestWithdraw`. [1](#0-0) 

At funding time, a partial borrower repayment stores the haircut under the *current* `epochNumber`:

- `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` in `collectWithdrawFunds`. [2](#0-1) 

`epochNumber` is incremented inside `deposit()` whenever `isEpochRunning()` is still true — the comment explicitly notes this branch is taken by the deposit performed *during* `stopEpoch`. [3](#0-2) 

The haircut is only ever applied through `lastWithdrawRequest[_user]`:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and returns 0 if unset. [4](#0-3) 
- The re-request guard in `requestWithdraw` only blocks when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`. [5](#0-4) 
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` at par once `epochNumber > lastWithdrawRequest[_user]`. [6](#0-5) 

So if `collectWithdrawFunds` executes after the `deposit` that bumps `epochNumber` inside the same `stopEpochWithDuration(_lossAmount)` call, the loss price is stored under epoch `N+1` while all receipts carry `lastWithdrawRequest == N`. The directory-traversal analog holds: the claim lookup "traverses" out of the epoch that owns the haircut into the funded-claim path, breaking the one-receipt-one-(haircut)-payout invariant.

### Impact Explanation
Each affected receipt claims its full face amount while the strategy only received `pendingBasis * recoveryPrice / RECOVERY_FULL` in underlying. The first claimant(s) to call `claimWithdrawRequest` drain underlyings that economically belong to the remaining haircut claimants; later claimants either receive less than their haircut-adjusted entitlement or revert on insufficient balance — a direct wealth transfer plus potential insolvency of the claim reserve. The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`, not the loss-adjusted bucket, so it does not stop this. [7](#0-6) 

### Likelihood Explanation
Attacker is an ordinary KYC'd lender who opened a normal `requestWithdraw` during the buffer of epoch `N`. The trigger is a `stopEpochWithDuration` with `_lossAmount > 0` and `pendingWithdraws > 0` — an honest manager/borrower path, not attacker-controlled privileged input. The exploit requires no attacker action beyond holding a receipt and claiming first. The one caveat I could not fully verify within the search iteration limit: the exact call order inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` — specifically whether the `deposit`/repayment that bumps `epochNumber` precedes `collectWithdrawFunds`. If `collectWithdrawFunds` runs before the increment (or the increment happens in a later transaction), the haircut and receipts share the same epoch and the bug collapses. This ordering must be confirmed before treating the finding as exploitable.

### Recommendation
Key the loss price to the epoch the pending receipts actually belong to rather than to `epochNumber` at collection time — e.g. store `lossRecoveryPriceByEpoch[pendingEpoch]` where `pendingEpoch` is captured when `pendingWithdraws` became non-zero, or snapshot `epochNumber` at the top of `stopEpochWithDuration` and pass it into `collectWithdrawFunds`. Alternatively, in `_claimLossAdjustedWithdrawRequest` and the `requestWithdraw` guard, check `lossRecoveryPriceByEpoch` for *every* epoch that has a nonzero `withdrawsRequestsByEpoch[_user][e]`/`apr0Users[_user].principalEpoch` entry, not just `lastWithdrawRequest[_user]`, so a mis-keyed haircut cannot be bypassed.

### Proof of Concept
Precondition: confirm via `IdleCDOEpochVariant.sol` that `epochNumber += 1` (inside `deposit`, while `isEpochRunning()` is still true) executes before `collectWithdrawFunds` in the same `stopEpochWithDuration` transaction.

function testLossReceiptEscapesHaircut() external {
    // epoch N: user deposits, epoch runs
    _depositWithUser(attacker, 100_000 * ONE_SCALE, true);
    _startEpochAndCheckPrices(0);

    // buffer of epoch N: attacker requests withdraw -> lastWithdrawRequest = N
    uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // borrower repays short: stopEpochWithDuration(_lossAmount) partially funds pending
    // collectWithdrawFunds stores lossRecoveryPriceByEpoch[N+1] (post-increment)
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() - LOSS);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(LOSS, 0); // or stopEpoch path that realizes a loss

    IdleCreditVault vault = IdleCreditVault(address(strategy));
    // haircut recorded under the *new* epoch
    assertGt(vault.lossRecoveryPriceByEpoch(vault.epochNumber()), 0);
    // attacker's lookup key still points at epoch N -> reads 0
    assertEq(vault.lossRecoveryPriceByEpoch(vault.lastWithdrawRequest(attacker)), 0);

    // funded claim path pays face value even though only haircut amount was collected
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, basis, "unhaircut par payout");

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
