### Title
Stale per-epoch instant-withdraw basis inflates default recovery reserve, causing recovery insolvency — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements the aggregate `instantWithdrawClaimsByEpoch[epoch]`. That stale basis is later read by `_defaultPrefundedInstantReserve`/`defaultPendingClaimBasis` during `finalizeDefaultRecovery`, which counts underlying that was already paid out as "prefunded reserve". The phantom backing inflates `defaultRecoveryPrice`, so the recovery reserve is promised more than it holds: early claimants are overpaid and later claimants' claims permanently revert on an empty reserve.

### Finding Description
`requestInstantWithdraw` records three pieces of state (IdleCreditVault.sol:356-375):

```solidity
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

`claimInstantWithdrawRequest` (lines 380-393) pays the user but only resets `instantWithdrawsRequests[_user]`:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Neither `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` nor `instantWithdrawClaimsByEpoch[currentEpoch]` is cleared. The per-epoch entries are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` (lines 847-853), which runs exclusively after a default finalization.

If the same epoch then defaults with partially unfunded instant requests (`pendingInstantWithdraws != 0`), `finalizeDefaultRecovery` calls `_defaultPrefundedInstantReserve` (lines 716-723):

```solidity
uint256 pendingInstant = pendingInstantWithdraws;
if (pendingInstant == 0) return prefundedReserve;
uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
if (instantBasis > pendingInstant) {
  prefundedReserve = instantBasis - pendingInstant;
}
```

`instantBasis` still includes the already-claimed (i.e., already-paid-out) amount. The comment states the intent: `instantBasis - pendingInstant` is "already-held underlying reserved for those claims". That invariant is broken for claimed receipts — the corresponding underlying left the strategy via `_transferFundedClaim` at claim time. The phantom amount is added to `reserveAmount` (line 686), inflating `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`.

Later, `_claimDefaultedInstantWithdrawRequest` and `_claimDefaultedWithdrawRequest` pay `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` out of `defaultRecoveryReserve` via `_transferDefaultRecovery` (lines 909-917), which underflows/reverts once the real balance is exhausted. Total reserve obligations equal `reserveAmount`, but the strategy only holds `reserveAmount - phantomAmount`.

Additionally, a user whose funded receipt was already claimed has a stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch] != 0` while `instantWithdrawsRequests[user] == 0`; if `_claimDefaultedInstantWithdrawRequest` is invoked for them, `instantWithdrawsRequests[_user] -= claimBasis` (line 848) underflows and permanently DoSes the whole `claimInstantWithdrawRequest` path for any account sharing that call.

### Impact Explanation
- **Direct loss / insolvency:** the recovery reserve is over-committed by the stale claimed amount. In a default with partial instant funding, every 1 wei claimed instant receipt in the default epoch that is still counted in `instantWithdrawClaimsByEpoch` creates 1 wei of phantom reserve. Early recovery claimants (an attacker among them) withdraw at the inflated `defaultRecoveryPrice` and drain the reserve; remaining claimants' claims revert permanently — unclaimed yield/recovery is permanently frozen/stolen. Loss is quantified as the total claimed-but-stale instant basis in the defaulted epoch.
- The guards do not stop it: `_ensureDefaultRecoveryInitialized` only gates `pendingWithdraws`, `defaultPendingClaimBasis` deliberately includes `instantWithdrawClaimsByEpoch[epochNumber]`, and nothing distinguishes "funded and claimed" receipts from "funded but unclaimed" ones.

### Likelihood Explanation
Requires: instant withdrawals enabled, at least two instant requests in one epoch where the strategy funds only part of them at `startEpoch` (`pendingInstantWithdraws` stays non-zero), the funded user claims before default, and the borrower then defaults in the same epoch with `defaultInstantWithdrawsFinalized` set. All attacker actions are unprivileged: request instant withdraw via `requestWithdraw`, claim via `claimInstantWithdrawRequest`. Borrower default itself is an honest-party event the attacker sequences around; the accounting corruption is entirely in strategy code.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch accounting alongside the aggregate:

```solidity
uint256 currentEpoch = epochNumber; // track each receipt's request epoch, or clear all epochs for the user
instantWithdrawsRequestsByEpoch[_user][epochOfRequest] -= amount; // or delete
instantWithdrawClaimsByEpoch[epochOfRequest] -= amount;
```

Since receipts aren't keyed by epoch at claim time, store the request epoch per user (e.g., a `lastInstantRequestEpoch` mapping analogous to `lastWithdrawRequest`) or maintain a separate "claimed basis" counter that `_defaultPrefundedInstantReserve` subtracts from `instantWithdrawClaimsByEpoch`.

### Proof of Concept
Foundry fork PoC sketch (fixed-APR mode, instant withdrawals enabled):

```solidity
// Epoch N buffer: attacker (user1) and victim (user2) both hold AA tranches.
// 1. user1/user2 requestWithdraw -> requestInstantWithdraw(A) and requestInstantWithdraw(B)
//    instantWithdrawClaimsByEpoch[N] = A + B; pendingInstantWithdraws = A + B.
// 2. owner starts epoch with only A underlying available:
//    collectInstantWithdrawFunds(A) -> pendingInstantWithdraws = B; CDO sends A to strategy.
// 3. user1 calls cdoEpoch.claimInstantWithdrawRequest() -> receives A underlying.
//    BUG: instantWithdrawsRequestsByEpoch[user1][N] == A, instantWithdrawClaimsByEpoch[N] == A + B (unchanged).
// 4. Borrower fails to repay at epoch end -> manager stopEpoch triggers default.
// 5. owner calls finalizeDefault(R, recoverySource):
//    _defaultPrefundedInstantReserve() = (A + B) - B = A  // phantom: A was already paid out
//    defaultRecoveryReserve = R + A + reserve  // only R + reserve actually held
//    defaultRecoveryPrice inflated by A / totalBasis.
// 6. attacker calls claimInstantWithdrawRequest()/claimWithdrawRequest() early:
//    receives claimBasis * inflatedPrice, draining reserve.
// 7. victim's remaining recovery claim reverts: underlyingToken.safeTransfer fails
//    or defaultRecoveryReserve underflows -> permanent freeze of victim's recovery.
// Assert: strategy.underlying balance < defaultRecoveryReserve after step 5 by exactly A.
```

Note: I was unable to fully confirm the CDO-side `claimInstantWithdrawRequest` wrapper and `_handleBorrowerDefault` call ordering in this pass, but the stale-ledger root cause in `IdleCreditVault` is self-contained and the phantom-reserve path is reachable exactly when `pendingInstantWithdraws != 0` at finalization — a case the code comments explicitly anticipate.
