### Title
Stale confirmations from deleted multisig members are still counted toward the confirmation threshold, allowing request execution below the effective live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
In `multisig2/src/lib.rs`, the `delete_member` function only purges outstanding *requests* that were originally created by the removed member, but it never purges that member's existing *confirmations* on requests created by other members. Once a member is removed, any confirmations they previously cast remain in the `confirmations` set for those other requests and continue to count toward `num_confirmations`, even though that account/key is no longer a member of the multisig.

### Finding Description
`confirm()` computes whether a request should execute purely from the size of the stored `confirmations` set: [1](#0-0) 

`delete_member()` is the only place that mutates state when a member is removed. It filters and removes *requests* whose `member` field (the request's original submitter) equals the removed member, and removes that member's `num_requests_pk` entry and the member itself from `self.members`. It does **not** scan `self.confirmations` to strip the removed member's identifier from confirmation sets belonging to requests created by *other* members: [2](#0-1) 

`current_member()` is only used to identify signers when a *new* confirmation is added, so once a member's confirmation string is inside a `HashSet<String>` for a request, it stays there indefinitely regardless of later removal: [3](#0-2) 

This breaks the binding "confirmations counted versus live members": `confirmations.len()` used in the threshold check in `confirm()` should equal the number of *currently live* members who approved the request, but after a `DeleteMember` action it can include confirmations from accounts/keys that are no longer members.

### Impact Explanation
This falls under the "Critical" impact bucket explicitly called out in scope: *a multisig request executed below threshold*. A request can be executed with fewer live-member approvals than `num_confirmations` requires, because a stale confirmation from a removed member is still counted. Since multisig request actions include `Transfer`, `DeployContract`, `AddKey`/`AddMember`/`DeleteMember`, this can lead to unauthorized transfers of NEAR or unauthorized privilege changes (e.g., adding a new full-access key) with an effective confirmation count below the configured K-of-N threshold.

### Likelihood Explanation
Requires a normal, expected multisig workflow: (1) a request is added by member B, (2) member A confirms it (leaving it under the execution threshold), (3) the multisig later executes a `DeleteMember` action removing A (a legitimate governance action, e.g. rotating a compromised or departing signer), (4) any remaining live member confirms the still-pending request. Step 4's confirmation will erroneously combine with A's stale confirmation to reach the threshold, even though only new-member confirmations plus one stale one are present. No attacker privilege beyond being a legitimate but possibly malicious-in-intent current member is required, and no code path currently prevents it — the bug is in `delete_member`'s incomplete cleanup, not in caller behavior. This is a realistic and likely-to-occur scenario in normal multisig lifecycle management (member rotation), not a contrived edge case.

### Recommendation
In `delete_member`, when removing a member, also iterate all pending requests' confirmation sets and strip the removed member's identifier (`member.to_string()`) from each, e.g.:
```rust
let ids: Vec<u32> = self.requests.keys().collect();
for request_id in ids {
    if let Some(mut confirmations) = self.confirmations.get(&request_id) {
        if confirmations.remove(&member.to_string()) {
            self.confirmations.insert(&request_id, &confirmations);
        }
    }
}
```
This should be done in addition to (not instead of) the existing removal of requests originally created by the removed member.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and members `{A, B, C, D}`.
2. `B` calls `add_request` for a `Transfer` request `X` (receiver arbitrary attacker-controlled account).
3. `A` calls `confirm(X)` → `confirmations = {A}` (1/3, below threshold, not executed) — see `confirm()` at [1](#0-0) .
4. The multisig (via a separate, properly-confirmed 3-of-4 request) executes a `DeleteMember{ member: A }` action, removing `A` from `self.members` via `delete_member()` at [2](#0-1) . Since request `X` was created by `B`, not `A`, it is **not** removed, and `A`'s entry is not stripped from `confirmations[X]`.
5. `C` calls `confirm(X)` → `confirmations.len() == 1 (stale A) + 1 (new C) = 2`; check `2 + 1 (D's upcoming) ...` — actually with just `C` confirming: `confirmations.len() as u32 + 1 = 2` which is still `< 3`, so add `C`: `confirmations = {A, C}`.
6. `D` calls `confirm(X)` → `confirmations.len() as u32 + 1 = 3 >= num_confirmations (3)` → `execute_request` fires the `Transfer`.
7. At execution time, live members are `{B, C, D}` (3 total), yet only `C` and `D` (2 live members) ever confirmed `X` — `A`'s stale confirmation supplied the third count. The transfer executes with only 2-of-3 live-member approval instead of the required 3-of-3 (equivalently 3-of-4 including the removed member never re-confirming), demonstrating execution below the intended live threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
