### Title
Front-running KYC/whitelist revocation to lock in a withdrawal request that remains claimable after de-whitelisting - ([File: contracts/IdleCDOEpochVariant.sol])

### Summary
The analog of `addBlackList()` front-running exists: `isWalletAllowed` gates new deposits and withdraw *requests* via a live Keyring credential check, but `claimWithdrawRequest` performs no wallet check. A lender who sees a revocation transaction (`KeyringIdleWhitelist.setWhitelistStatus(entity, false)` or an upstream Keyring credential revocation) in the mempool can front-run it with `requestWithdraw`, and the queued request remains fully claimable afterward because the claim path never re-checks credentials. Revocation therefore fails to freeze the user's exit, mirroring the reported blacklist-evasion bug.

### Finding Description
`IdleCDOEpochVariant.isWalletAllowed` resolves credentials dynamically through `IKeyring.checkCredential`, and `KeyringIdleWhitelist.checkCredential` returns `whitelist[entity] || Keyring(keyring).checkCredential(...)`, so an admin flipping `whitelist[entity]` to `false` via `setWhitelistStatus` (or the Keyring operator revoking the credential) instantly turns `isWalletAllowed` false for that wallet [1](#0-0) [2](#0-1) [3](#0-2) 

All *entry/request* paths enforce this check: `_deposit` reverts via `_checkNotAllowed(!isWalletAllowed(msg.sender))` [4](#0-3) , `depositDuringEpoch` includes `!isWalletAllowed(msg.sender)` in its revert condition [5](#0-4) , and `IdleCDOEpochQueue.requestWithdraw`/`requestDeposit` call `_checkAllowed(msg.sender)` [6](#0-5) . `requestWithdraw` on the CDO also reverts for non-credentialed wallets, as confirmed by `testOnlyKeyringUsersCanInteract` [7](#0-6) .

However, `claimWithdrawRequest` forwards directly to the strategy with no credential check whatsoever [8](#0-7) . The intended freeze surface (block new requests) is therefore only enforced at request time, and revocation is an on-chain, mempool-visible transaction that can be front-run.

Attack sequence (buffer period, epoch running or not):
1. Malicious lender M holds tranche tokens and is about to be de-whitelisted (insider knowledge or mempool monitoring of `setWhitelistStatus(M, false)` / Keyring policy revocation tx).
2. M front-runs the revocation tx with `requestWithdraw(amount, tranche)` (allowed while `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are true). The request is recorded under M's address in `lastWithdrawRequest`/epoch accounting.
3. Revocation lands; `isWalletAllowed(M)` is now false and M can no longer deposit or request.
4. After the epoch stops and funds are pulled from the borrower, M calls `claimWithdrawRequest()`, which does not consult `isWalletAllowed`, and receives the underlyings.

The broken invariant is access control: revocation is designed to prevent a flagged wallet from moving value out of the vault, but the gating is only on request creation, not on the claim that actually releases funds, so the freeze is only effective if the revocation transaction is not front-run.

### Impact Explanation
A wallet identified for removal (sanctions, fraud, expired KYC) can guarantee exit of its full position by sandwiching the revocation: front-run with `requestWithdraw`, then claim post-revocation. Loss magnitude is the user's entire tranche position escaping the intended freeze — the same "funds not locked despite blacklist" impact as the reference issue. It is not theft from other users, but it defeats the compliance control at the exact moment it is exercised.

### Likelihood Explanation
Requires that the deployment uses the Keyring/whitelist gate and that revocation happens via a public-mempool transaction. Both conditions hold in the standard factory deployment (`setWhitelistStatus` is a normal admin tx; `checkCredential` is read live). Mempool monitoring is trivial, and during buffer periods `requestWithdraw` is open to any still-allowed wallet. Likelihood is moderate: it depends on an admin revocation being pending and the target acting before it confirms, but no privileged collusion or special epoch state is needed.

### Recommendation
Treat revocation as effective immediately for pending claims as well: add an `isWalletAllowed` check (or a `keyringAllowWithdraw`-style flag consult) inside `IdleCreditVault.claimWithdrawRequest`/`claimInstantWithdrawRequest` or in `IdleCDOEpochVariant.claimWithdrawRequest`, so that a front-run request cannot be claimed after de-whitelisting. Alternatively, submit revocations through a private mempool and/or make `requestWithdraw` snapshot a per-epoch allowlist at `startEpoch` so pre-revocation queued requests remain consistent with post-revocation claimability. If revocation is intentionally not meant to block exits, document that claims are always permissionless and revocation only blocks new deposits/requests.

### Proof of Concept
Foundry fork/test sketch (buffer period between epochs; AA tranche; whitelist gate active):

```solidity
// setup: cdoEpoch with keyring set, `victim` whitelisted & holding AA tranche tokens
KeyringIdleWhitelist wl = KeyringIdleWhitelist(cdoEpoch.keyring());

// --- tx ordering simulation: victim front-runs revocation ---
vm.prank(victim);
cdoEpoch.requestWithdraw(victimTrancheBal, address(AAtranche)); // succeeds, still allowed

// admin revocation lands
vm.prank(admin);
wl.setWhitelistStatus(victim, false); // or mock Keyring.checkCredential -> false

assertFalse(cdoEpoch.isWalletAllowed(victim));

// victim can no longer request or deposit
vm.prank(victim);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.requestWithdraw(1, address(AAtranche));

// epoch stops; borrower repays; funds available for claims
_stopEpochAndCheckPrices(0, apr, expectedFunds);

// BUG: claim succeeds despite revocation -> freeze defeated
vm.prank(victim);
cdoEpoch.claimWithdrawRequest();
assertGt(underlying.balanceOf(victim), balPre);
```

Note: verification pending that `IdleCreditVault.claimWithdrawRequest` performs no `isWalletAllowed` check internally — the wrapper at `IdleCDOEpochVariant.sol:967-971` shows none, and the queue/requests are keyed to `msg.sender`, but the strategy-level claim internals were not fully read. If the strategy does check credentials on claim, the analog weakens and reduces to a known/inherent mempool front-running property of any on-chain allowlist rather than a distinct vulnerability.
