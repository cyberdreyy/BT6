### Title
`lossRecoveryPriceByEpoch` is only checked for `lastWithdrawRequest[_user]` — a second request in a later epoch lets a user claim a loss-adjusted receipt at par and drain other claimants' funded withdrawals - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug (`copy_verifier_state()` forgetting to copy `loop_entry`, letting a stale field from an unrelated state poison the current state) maps to per-epoch receipt state in `IdleCreditVault` that is keyed by a single stale-able field. `_claimLossAdjustedWithdrawRequest` looks up the haircut price using only `lastWithdrawRequest[_user]`, which is overwritten on every `requestWithdraw`. A user whose epoch-N receipt was haircutted by `collectWithdrawFunds` can make a new request in a later epoch, after which the epoch-N haircut is never applied and the full aggregate `withdrawsRequests[_user]` is paid at par through `_claimFundedWithdrawRequest`, while `withdrawsRequestsByEpoch[_user][N]` is never cleared.

### Finding Description
1. `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user] += _amount` plus `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` [1](#0-0) .
2. On a partial `stopEpochWithDuration` repayment, `collectWithdrawFunds` zeroes `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` [2](#0-1) . The strategy then holds only `price × basis` for those receipts.
3. `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which reads the haircut **only** at `lossEpoch = lastWithdrawRequest[_user]` [3](#0-2) . If the user's newest request epoch has no stored price (`lossRecoveryPriceByEpoch[newEpoch] == 0`), it returns 0 without touching the older epoch's entry.
4. Execution then falls to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` — still containing the haircutted epoch-N amount — in full and sets it to 0 [4](#0-3) .
5. `withdrawsRequestsByEpoch[_user][N]` and `lossRecoveryPriceByEpoch[N]` remain set but are permanently unreachable for that user, since `lastWithdrawRequest` can never return to N.

The "stale field" is the epoch-N entry in `withdrawsRequestsByEpoch`/`lossRecoveryPriceByEpoch`: once `lastWithdrawRequest` is overwritten, the haircut state is orphaned and the receipt is treated as fully funded.

### Impact Explanation
Broken invariant: loss waterfall / one-receipt-one-haircut. The attacker recovers `amount_N × (1 − lossRecoveryPriceByEpoch[N])` more than entitled, paid directly out of underlyings funded for *other* users' withdraw receipts (or default-recovery-adjacent balances), since the contract only ever received `price × basis` for epoch N. This is direct theft of a quantified amount equal to the haircut that should have been applied — e.g., with a 50% loss price and a 1,000-token epoch-N request, the user extracts an extra 500 tokens from funds earmarked for other claimants, potentially leaving later claims unpayable (insolvency of the funded-receipt pool).

### Likelihood Explanation
Requires an unprivileged lender to (a) have a pending receipt in an epoch where the manager stops the epoch with a partial repayment (`stopEpochWithDuration` with `_lossAmount` such that `collectWithdrawFunds` is called with `_amount < pendingBasis` — a designed, non-default code path), and (b) make a second `requestWithdraw` in a subsequent epoch and wait one epoch. Both steps are normal user actions; no privileged cooperation beyond the honest loss-stop is needed. Any user can be the first to claim and capture the haircut difference of their own receipt; users with large haircutted receipts have the strongest incentive.

### Recommendation
In `_claimLossAdjustedWithdrawRequest`, iterate or track all epochs with `lossRecoveryPriceByEpoch != 0` for the user rather than only `lastWithdrawRequest[_user]` — e.g., keep a per-user set/bitmap of loss epochs, or check every epoch in which `withdrawsRequestsByEpoch[_user][e] != 0` against `lossRecoveryPriceByEpoch[e]` before falling through to `_claimFundedWithdrawRequest`. Alternatively, reject a new `requestWithdraw` while `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]] != 0 && lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`, forcing the user to claim the haircutted receipt first.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// setup: AA deposit for attacker (user1) and victim (user2); epoch running
uint256 req = 1_000 * ONE_SCALE;

// 1) both users request withdraw in epoch E1
_requestWithdrawWithUser(user1, req);
_requestWithdrawWithUser(user2, req);

// 2) manager stops E1 with a partial repayment (loss): borrower funds 50% of pendingBasis
uint256 pendingBasis = strategy.pendingWithdraws();          // = 2*req (+interest)
uint256 funded = pendingBasis / 2;
// borrower repays active interest + funded; call stopEpochWithDuration(apr, 0, duration, loss)
// -> collectWithdrawFunds(funded) sets lossRecoveryPriceByEpoch[E1] = RECOVERY_FULL/2, pendingWithdraws = 0

// 3) epoch E2 starts; attacker requests again (fresh tranche balance needed)
_requestWithdrawWithUser(user1, req2);   // sets lastWithdrawRequest[user1] = E2

// 4) stop E2 fully funded (loss = 0): lossRecoveryPriceByEpoch[E2] == 0
//    epochNumber is now E2+1 (> lastWithdrawRequest) so funded-claim gate passes

// 5) attacker claims: _claimLossAdjustedWithdrawRequest checks only epoch E2 -> 0,
//    then _claimFundedWithdrawRequest pays withdrawsRequests[user1] (= req + req2) at par
vm.prank(user1);
cdoEpoch.claimWithdrawRequest();
// assert attacker received req + req2 instead of req*0.5 + req2,
// and strategy balance is short req*0.5 for user2's claim
```

Key assertions: `underlying.balanceOf(user1)` increases by `req + req2` (not `req * price / RECOVERY_FULL + req2`), and `strategy.withdrawsRequestsByEpoch(user1, E1)` remains non-zero after the claim while the corresponding haircut funds were already consumed.

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
