### Title
Loss-adjusted withdraw receipts escape the haircut when a newer request overwrites `lastWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`IdleCreditVault` tracks a user's loss-adjusted withdraw receipt by a single mutable slot, `lastWithdrawRequest[_user]`. If a user makes a second `requestWithdraw` after a `stopEpochWithDuration` loss but before claiming, the loss-epoch marker is overwritten, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch` for the wrong epoch, and the stale (already haircut) receipt is paid at par through `_claimFundedWithdrawRequest`. This is the vault analog of the kernel UAF: the per-epoch receipt object is "freed" (its epoch pointer overwritten) while a pending claim still references it.

### Finding Description
On `requestWithdraw`, the strategy records the request per-epoch and also stores `lastWithdrawRequest[_user] = currentEpoch` (`IdleCreditVault.sol:281-294`). When the epoch ends with a realized loss, `collectWithdrawFunds` stores a haircut `lossRecoveryPriceByEpoch[epochNumber]` and clears `pendingWithdraws` (`IdleCreditVault.sol:411-430`). Claim order in `claimWithdrawRequest` is: defaulted claim → `_claimLossAdjustedWithdrawRequest` → `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:301-314`).

The bug: `_claimLossAdjustedWithdrawRequest` resolves the loss epoch via `lossEpoch = lastWithdrawRequest[_user]` (`IdleCreditVault.sol:789-792`). If the user re-requested a withdraw in the buffer after the loss epoch, `lastWithdrawRequest` now points to the newer epoch where `lossRecoveryPriceByEpoch` is 0, so the haircut branch is skipped. Nothing clears `withdrawsRequestsByEpoch[user][lossEpoch]`, so `withdrawsRequests[user]` still contains the haircut receipt. Once `epochNumber > lastWithdrawRequest`, `_claimFundedWithdrawRequest` pays the entire aggregate `withdrawsRequests[user]` at par (`IdleCreditVault.sol:338-349`), including the amount that should have been paid at `lossRecoveryPrice < RECOVERY_FULL`.

### Impact Explanation
`collectWithdrawFunds` only pulls `pendingToFund = pendingBasis - pendingLoss` from the borrower, so the strategy holds less underlying than the sum of un-haircut receipt bases. An attacker who double-requests escapes their pro-rata share of the loss and withdraws at par, draining the loss-adjusted funding pool. Honest claimants of the same loss epoch then find insufficient funds (transfers revert on `SafeERC20` or their claim basis is effectively unpaid) — direct theft of the unfunded loss portion, proportional to `claimBasis * (1 - lossRecoveryPrice)`, up to insolvency of that epoch's claim bucket.

### Likelihood Explanation
Requires only a KYC'd lender (unprivileged per scope): deposit, `requestWithdraw`, let a `stopEpochWithDuration` loss land (honest manager action), then `requestWithdraw` again in the next buffer and claim after one more epoch. No privileged misbehavior needed; the sequence relies on honest manager `startEpoch`/`stopEpochWithDuration` calls and an ordinary partial-loss event.

### Recommendation
Track pending loss-epoch claims per epoch rather than inferring the loss epoch from `lastWithdrawRequest`. Options: iterate `_claimLossAdjustedWithdrawRequest` over all epochs with nonzero `withdrawsRequestsByEpoch[_user][e]` where `lossRecoveryPriceByEpoch[e] != 0`, or store a per-user set of loss epochs; also prevent `requestWithdraw` (or require claim) while an uncleared loss-adjusted receipt exists for the user.

### Proof of Concept
Foundry fork sketch (extends `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// Pool running, attacker = KYC'd lender holding AA tranche tokens.
uint256 req1 = cdoEpoch.requestWithdraw(attackerTrancheBal, address(AAtranche)); // epoch N request

// Honest manager: borrower repays with a realized loss.
(uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
// borrower approves fundsToRepay = expectedEpochInterest + pendingToFund
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount); // sets lossRecoveryPriceByEpoch[N] < 1e18
assertLt(strategy.lossRecoveryPriceByEpoch(N), 1e18);

// Attacker re-requests in the new buffer (epoch N+1), overwriting lastWithdrawRequest.
vm.prank(attacker);
cdoEpoch.requestWithdraw(dust, address(AAtranche));
assertEq(strategy.lastWithdrawRequest(attacker), N + 1); // loss-epoch pointer "freed"

// Honest manager runs/stops the next epoch normally.
// ... startEpoch(); warp; stopEpoch(apr, 0); ...

// Claim: loss-adjusted branch skipped (lossRecoveryPriceByEpoch[N+1] == 0),
// funded branch pays req1 + dust at par instead of req1 * lossRecoveryPrice.
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(attacker) - balPre;

uint256 shouldPay = req1 * strategy.lossRecoveryPriceByEpoch(N) / 1e18 + dustEntitlement;
assertGt(paid, shouldPay); // attacker escapes the loss haircut; pool short for other claimants
```

Expected result: `paid` equals the full par claim, and subsequent honest claims for epoch N revert on insufficient underlying in the strategy.
