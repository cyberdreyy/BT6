### Title
Node-local, in-memory Vault replay guard allows the same authorized secrets-management request to be re-executed on other nodes or after a restart, before its on-chain authorization actually expires - ([File: core/capabilities/vault/request_replay_guard.go])

### Summary
The reported PoolTogether bug (`[H-03]`) is a "range/one-time-use check is bound only to the natural time expiry of the outer object, not to whether the specific claim/action has already been consumed" class of bug: `_calculateRewardAmount()` only checked `block.timestamp > _epochEndTimestamp`, never whether `_epochId` was still a valid, not-yet-consumed epoch, so the same conceptual "already used" action could be repeated. The Chainlink Vault gateway/node authorization pipeline has a structurally analogous gap: single-use enforcement for an already-authorized, unprivileged-reachable request is delegated entirely to an in-memory, per-process, non-persistent map (`RequestReplayGuard.seen`), while the actual authorization source (`AllowListBasedAuth`) is explicitly designed to keep returning "authorized" for the same request as long as its on-chain expiry has not passed.

### Finding Description
`AllowListBasedAuth.AuthorizeRequest` (`core/capabilities/vault/allow_list_based_auth.go:34-77`) authorizes a Vault JSON-RPC request purely based on whether its digest is present in the on-chain allowlist and whether `time.Now().UTC().Unix() > allowlistedRequest.ExpiryTimestamp`. By design it does **not** enforce single use — the test explicitly documents this: "Same request is still authorized here; replay protection lives in the generic Authorizer" (`core/capabilities/vault/allow_list_based_auth_test.go:186`). [1](#0-0) 

The only thing preventing an already-processed `vault.secrets.create` / `vault.secrets.update` / `vault.secrets.delete` request from being executed a second time is `authorizer.AuthorizeRequest` calling `a.replayGuard.CheckAndRecord(digest, expiresAt)`: [2](#0-1) 

`RequestReplayGuard` is a plain in-process `map[string]int64` guarded by a mutex, created fresh via `NewRequestReplayGuard()` inside `NewAuthorizer` (`core/capabilities/vault/authorizer.go:90-97`), with no persistence, no cross-node sharing, and entries pruned only when the local clock passes the recorded expiry: [3](#0-2) 

Every node in a Vault DON runs `GatewayHandler`/`NewGatewayHandler` with its own `Authorizer`/`RequestReplayGuard` instance (`core/capabilities/vault/gw_handler.go:84-141`), and the gateway forwards each incoming JSON-RPC request from the internet-facing gateway to node handlers via `HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go:180-236`). Because the "already seen" state lives only in each node's local memory, the same previously-authorized request (a valid, unexpired allowlist entry + a captured/replayed JSON-RPC payload) will be treated as brand new and re-executed by:
- any node that has since restarted (map wiped on restart), or
- any node whose replay guard has not yet observed that specific digest (e.g., newly joined node, or if requests aren't uniformly broadcast to all nodes), or
- the same node after the entry was pruned early relative to intended semantics if clock skew/backdated expiry causes premature deletion.

This mirrors the report's root cause exactly: the code checks *time-based validity of the umbrella authorization* (epoch-over / on-chain-expiry) but not *whether this specific one-time action has already been consumed*, and the "already consumed" bookkeeping is not authoritative/durable — it's held in a place that can be reset or bypassed (node restart / other node instance) while the umbrella authorization (the on-chain allowlist expiry) remains valid.

### Impact Explanation
An unprivileged network observer/relay who can capture a legitimately authorized Vault management JSON-RPC request sent through the internet-facing gateway (`core/services/gateway/handlers/vault/handler.go`) can resend the identical request to the gateway before its on-chain `ExpiryTimestamp` elapses. If it reaches a node whose in-memory replay guard has not recorded that digest (freshly restarted node, node added to DON, or any node other than the one that originally processed it), the node will re-authorize and re-execute the create/update/delete of an encrypted secret — i.e., cause an unauthorized repeat of a secret-management state change using a previously-authorized-but-already-consumed credential. This is analogous to the reward being claimable multiple times: the "single claim" invariant is not durably enforced, only the umbrella time window is.

### Likelihood Explanation
This requires the attacker to be able to capture/replay a JSON-RPC request en route to the gateway (network-observable but not requiring any privileged role or key compromise, since the request itself is not bound to a single execution once it passes the allowlist-digest + expiry check), and for the resend to land on a node lacking prior state for that digest — which is a normal operational occurrence (node restarts, node set changes, and any lack of atomic/synchronized dedup across a distributed gateway/DON) rather than an exotic scenario, but it does depend on infrastructure/routing behavior of the gateway to a specific node, which is not verified in the indexed code.

### Recommendation
Move single-use enforcement for allowlisted Vault requests to a durable, DON-wide/consensus-backed check rather than an in-process map: e.g., track consumed request digests on-chain in `WorkflowRegistry` (mark allowlisted requests as spent) or require the node-side capability's `SecretsService` execution path to be idempotent/deduplicated centrally (persisted, or coordinated via OCR aggregation) so that node restarts or per-node divergence cannot cause re-execution of an already-consumed authorization. At minimum, persist `RequestReplayGuard` state to disk across restarts and ensure identical replay-guard state is required across the DON quorum before the underlying secret action is committed.

### Proof of Concept
Conceptual PoC (cannot be executed against source only):
1. Workflow owner allowlists request digest `D` on-chain with `ExpiryTimestamp = now + 300s` for a `vault.secrets.create` request.
2. Owner submits the JSON-RPC request through the gateway; it is authorized and processed successfully by Node A (whose `RequestReplayGuard` now has `D → expiry`).
3. An observer captures the exact same signed/allowlisted JSON-RPC payload.
4. Node A restarts (or the observer resends the payload and it happens to route to Node B, which never processed `D`).
5. `AllowListBasedAuth.AuthorizeRequest` succeeds again (digest still on-chain, not expired) → `RequestReplayGuard.CheckAndRecord` on the fresh/uninitialized node returns `nil` (not `ErrRequestAlreadySeen`) → `vault.secrets.create` is executed a second time, analogous to claiming the same reward epoch multiple times. 	if err != nil {
		return nil, err
	}

type RequestReplayGuard struct {
	mu      sync.Mutex
	seen    map[string]int64 // digest → unix expiry timestamp
	nowFunc func() time.Time // injectable for testing
}

// NewRequestReplayGuard creates a replay guard for authorized Vault requests.
func NewRequestReplayGuard() *RequestReplayGuard {
	return &RequestReplayGuard{
		seen:    make(map[string]int64),
		nowFunc: time.Now,
	}
}

// CheckAndRecord returns ErrRequestAlreadySeen if the digest was previously
// recorded and has not yet expired. Otherwise it records the digest with
// the given expiry timestamp (unix seconds, UTC).
//
// Expired entries are cleaned up on every call.
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
