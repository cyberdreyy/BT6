## Finding

### Title
Pending-inactive stake unlocked while a validator is `pending_active` bypasses the lockup period entirely - ([File: aptos-move/framework/aptos-framework/sources/stake.move])

### Summary
`stake.move` was modified to "settle" a validator's `pending_inactive` stake into `inactive` whenever `locked_until_secs` has already expired, applied both synchronously in `join_validator_set_internal` and again for all `pending_active` validators inside `on_new_epoch`, *before* the lockup-renewal step runs for those same validators. Because delegators can call `unlock` (via `delegation_pool`/`staking_contract`) at any time an active stake exists — regardless of validator status — stake unlocked while the validator is transitioning `inactive -> pending_active -> active` with a stale, already-expired `locked_until_secs` gets swept straight into `inactive` at the very next epoch boundary, without ever completing a full lockup cycle.

### Finding Description
`join_validator_set_internal` contains: [1](#0-0) 
This merges `pending_inactive` into `inactive` synchronously whenever the validator's (possibly stale) lockup has expired, before the validator has even rejoined the active set.

The same pattern is repeated unconditionally for every `pending_active` validator in `on_new_epoch`, immediately before those validators are appended into `active_validators`: [2](#0-1) 

Lockup is only renewed afterward, in the loop over `active_validators` (which now includes the just-activated ones), and only for the validators being iterated in this same epoch transition: [3](#0-2) 

Sequence that breaks the lockup invariant:
1. A validator (backed by a `delegation_pool` or `staking_contract`) is `INACTIVE` with an expired `locked_until_secs` (e.g., it left the set earlier, or its lockup was never renewed while inactive).
2. The operator calls `stake::join_validator_set(operator, pool_address)` (a plain, unprivileged operator action) which moves it to `pending_active` and — via the code at lines 1098-1109 — immediately drains any existing `pending_inactive` into `inactive`.
3. Before the next epoch boundary, any delegator calls `unlock` on `delegation_pool`/`staking_contract`. `stake::unlock_with_cap` only checks `coin::value(&stake_pool.active)`; it does not check validator state, so this succeeds and creates fresh `pending_inactive` stake: [4](#0-3) 
4. At the next `on_new_epoch`, the validator is still `pending_active` and `locked_until_secs` is still the old, expired value (renewal has not run yet for it). The block at lines 1361-1376 unconditionally sweeps *all* `pending_inactive` — including the stake that was unlocked only moments earlier in step 3 — into `inactive`.
5. Only after this sweep does the validator get appended to `active_validators` and have its lockup renewed (lines 1448-1464).

The net effect: stake that was unlocked during the `pending_active` window becomes `inactive` (and hence withdrawable, e.g. via `stake::withdraw`, `delegation_pool::withdraw`, `staking_contract::distribute`) in the very next epoch, without ever having spent a full lockup cycle as `pending_inactive`. This violates the core protocol invariant documented in `delegation_pool.move` itself: unlocking/unlocked stake must go through a real lockup cycle before becoming withdrawable, and unlocking/unlocked stake from different real lockups is never supposed to be conflated: [5](#0-4) 

### Impact Explanation
This breaks the fundamental accounting/withdrawal invariant across `pending_active`, `pending_inactive`, and `inactive` states required by the task's pivots ("Unlock, reactivate, withdraw ... paths must not redirect value or strand it permanently" and "Accounting across active, pending_active, pending_inactive, inactive ... must preserve value and withdrawal rights"). Delegators (and any staker) can withdraw stake essentially instantly after unlocking simply by timing their `unlock` call to coincide with their validator's `inactive -> pending_active` transition with a stale expired lockup, defeating the lockup-period security guarantee that underlies validator set stability and voting-power stickiness. This is a protocol-level invariant break reachable by fully unprivileged actors (any delegator, plus an operator who already legitimately holds the operator role), not merely a cosmetic issue, so it meets the bar for a real vulnerability under the stated impacts.

### Likelihood Explanation
The sequence requires no special privilege beyond roles the actors already legitimately hold (operator calling `join_validator_set`, delegator calling `unlock`), and the state needed (an inactive validator with an already-expired lockup) arises naturally whenever a validator leaves the set and stays out for one lockup period, or is evicted for insufficient stake and later re-funded. The window between `join_validator_set` and the next epoch boundary is exactly one epoch, which is easily targetable. Likelihood is Medium-High.

### Recommendation
Renew (or refuse to settle) the lockup for a validator before or atomically with the `pending_active -> active` settle step, and/or gate the settle-merge in both `join_validator_set_internal` and the `on_new_epoch` `pending_active` loop so it only sweeps `pending_inactive` stake that existed strictly *before* the validator re-entered `pending_active` (e.g., snapshot the pre-existing `pending_inactive` balance at the time `join_validator_set` is called, rather than sweeping whatever balance exists at settle time). Alternatively, disallow `unlock` while a stake pool's validator is `pending_active` with an unrenewed/expired lockup, or force a lockup renewal as part of `join_validator_set_internal` itself before it becomes possible to accept new unlocks.

### Proof of Concept
1. Validator `V`'s stake pool is `INACTIVE`, `locked_until_secs` has already passed.
2. Operator calls `stake::join_validator_set(operator, V)` → `join_validator_set_internal` merges existing `pending_inactive` into `inactive` (lines 1098-1109) and pushes `V` into `pending_active`.
3. A delegator immediately calls `delegation_pool::unlock(delegator, V, amount)` → internally calls `stake::unlock`, creating new `pending_inactive` stake on `V`'s pool (no validator-state check exists in `unlock_with_cap`, lines 1149-1166).
4. Epoch ends, `on_new_epoch` runs: since `V` is still `pending_active` and `locked_until_secs` is still expired, the block at lines 1361-1376 merges the delegator's just-unlocked stake straight into `inactive`.
5. `V` is then appended to `active_validators` and only now has its lockup renewed (lines 1448-1464) — too late, the delegator's stake is already `inactive`.
6. The delegator immediately calls `delegation_pool::withdraw` (or `stake::withdraw`) and receives their funds back — despite having unlocked them only one epoch earlier, never having completed a real lockup cycle.

    public fun unlock_with_cap(amount: u64, owner_cap: &OwnerCapability) acquires StakePool {
        assert_reconfig_not_in_progress();
        // Short-circuit if amount to unlock is 0 so we don't emit events.
        if (amount == 0) { return };

        // Unlocked coins are moved to pending_inactive. When the current lockup cycle expires, they will be moved into
        // inactive in the earliest possible epoch transition.

        let stake_pool = borrow_global_mut<StakePool>(pool_address);
        // Cap amount to unlock by maximum active stake.

        let unlocked_stake = coin::extract(&mut stake_pool.active, amount);
        coin::merge<AptosCoin>(&mut stake_pool.pending_inactive, unlocked_stake);

        event::emit(UnlockStake { pool_address, amount_unlocked: amount });
    }
