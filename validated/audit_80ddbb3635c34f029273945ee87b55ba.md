### Title
Cleanup() re-checks feature flag instead of relying on `perBuild` state, causing dangling per-build networks - ([File: executors/docker/internal/networks/manager.go])

### Summary
`manager.Cleanup` gates the network removal call on `m.build.IsFeatureFlagOn(featureflags.NetworkPerBuild)` in addition to the `m.perBuild` flag that was already set by `Create`. If the flag's evaluated value differs between the `Create` and `Cleanup` calls in the same job lifecycle, `Cleanup` returns `nil` early and never calls `NetworkRemove`, even though a real network was created and `m.perBuild == true`.

### Finding Description
`Create` decides whether to allocate a per-build network by checking the feature flag once, and if it creates the network it sets `m.perBuild = true` and stores the network in `m.buildNetwork`: [1](#0-0) 

`Cleanup`, however, independently re-evaluates the same feature flag before consulting `m.perBuild`: [2](#0-1) 

The correct invariant is: resource cleanup should be driven purely by whether the resource was actually allocated (`m.perBuild`), not by a flag re-read at cleanup time. Since `m.perBuild` and `m.buildNetwork.ID` are the manager's own authoritative record of what it created, re-checking the feature flag at `Cleanup` is redundant at best and a correctness hazard at worst — if the flag's runtime value can differ between the two calls, cleanup silently no-ops while `m.perBuild` remains `true` and `m.buildNetwork.ID` still holds a live network ID.

Feasibility caveat: `IsFeatureFlagOn` is normally resolved from job-scoped configuration/variables that are fixed for the duration of a single job's execution, so under typical GitLab Runner operation the flag value should not change between `Create` and `Cleanup` calls within the same job. I could not fully verify the exact resolution/caching behavior of `IsFeatureFlagOn` in `common/build.go` within this session, so I cannot confirm a concrete, attacker-triggerable mechanism (e.g., config reload, variable override) that flips the flag mid-job under normal Runner operation. This is a real code smell / latent bug, but proving attacker-reachability of the flag-flip precondition requires further verification of `IsFeatureFlagOn`'s implementation.

### Impact Explanation
If the flag value differs between `Create` and `Cleanup`, the created Docker network is never removed via `NetworkRemove`, leaking a network resource on the host tied to the build. Because `m.buildNetwork` and `m.perBuild` are not reset in this path, the manager's internal state becomes inconsistent with reality, and the leaked network could remain discoverable/name-collidable for subsequent builds using `m.build.GetNetworkName()`.

### Likelihood Explanation
The exploit depends entirely on the ability to make `m.build.IsFeatureFlagOn(featureflags.NetworkPerBuild)` return different values across the `Create`→`Cleanup` window of a single job. This requires either a race in flag evaluation or a config reload that mutates the effective flag value used by a build already in flight. I was unable to confirm within this repository whether such a runtime flip is reachable by an unprivileged pipeline author versus being solely an operator/admin-controlled runner-config action. Without confirming that the flag is genuinely mutable mid-job by a normal user's job inputs, this remains a *logic defect with uncertain attacker-reachability* rather than a confirmed unprivileged-triggerable vulnerability.

### Recommendation
Remove the redundant feature-flag check in `Cleanup` and rely solely on `m.perBuild` (and `m.buildNetwork.ID != ""`) to decide whether `NetworkRemove` should be called, matching the resource-allocation record rather than a potentially-changing flag:
```go
func (m *manager) Cleanup(ctx context.Context) error {
	if !m.perBuild {
		return nil
	}
	...
}
```

### Proof of Concept
Unit test in `executors/docker/internal/networks/manager_test.go` style:
```go
func TestCleanup_FlagFlipAfterCreate(t *testing.T) {
	client := new(docker.MockClient)
	build := &common.Build{ /* flag=true initially */ }
	m := NewManager(logger, client, build, labeler).(*manager)

	client.On("NetworkCreate", ...).Return(...)
	client.On("NetworkInspect", ...).Return(network.Inspect{ID: "net123"}, nil)
	_, err := m.Create(ctx, "", false)
	require.NoError(t, err)
	require.True(t, m.perBuild)

	// simulate flag flip
	setFeatureFlag(build, featureflags.NetworkPerBuild, false)

	client.On("NetworkRemove", ctx, "net123").Return(nil)
	err = m.Cleanup(ctx)
	require.NoError(t, err)
	client.AssertCalled(t, "NetworkRemove", ctx, "net123")
}
```
Expected assertion with the current code: `NetworkRemove` is **not** called (test fails), demonstrating the leak; after applying the recommended fix, the assertion passes.

```go
func (m *manager) Cleanup(ctx context.Context) error {
	if !m.build.IsFeatureFlagOn(featureflags.NetworkPerBuild) {
		return nil
	}

	if !m.perBuild {
		return nil
	}

	m.logger.Debugln("Removing network: ", m.buildNetwork.ID)

	err := m.client.NetworkRemove(ctx, m.buildNetwork.ID)
	if err != nil {
		return fmt.Errorf("docker remove network %s: %w", m.buildNetwork.ID, err)
	}

	return nil
}
```
