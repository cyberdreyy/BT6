## Finding [1](#0-0) 

### Title
Missing fee-amount validation in `createDstEscrow` allows resolver to permanently freeze/steal maker funds on the destination chain - (File: `contracts/BaseEscrowFactory.sol`)

### Summary
`_postInteraction` (used for source-chain escrow creation) explicitly guards against oversized fees with `if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();`. `createDstEscrow`, the sibling entry point that creates the destination-chain escrow, accepts a fully caller-supplied `Immutables.parameters` blob (which encodes `protocolFeeAmount`, `integratorFeeAmount`, fee recipients) with no equivalent check. This is the same root-cause class as the reported bug: one setter/creator validates a percentage/amount bound while an analogous sibling function omits it, and the state that is skipped-checked later causes the contract to revert during fund distribution.

### Finding Description
`createDstEscrow` takes `dstImmutables` entirely from `msg.sender` (the resolver/taker) and only validates the native value sent and the cancellation-timelock ordering: [1](#0-0) 

There is no check that `protocolFeeAmount + integratorFeeAmount <= amount`, unlike the source-side path which enforces `InvalidFeeAmounts()`: [2](#0-1) 

The fee values are later consumed in `EscrowDst._withdraw`: [3](#0-2) 

`uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;` will underflow and revert (Solidity 0.8 checked arithmetic) whenever the resolver supplied `protocolFeeAmount + integratorFeeAmount > immutables.amount` at `createDstEscrow` time. Because this check is absent at creation time, both `withdraw` and `publicWithdraw` become permanently unusable for that escrow — the maker can never receive the destination-chain funds. The only remaining path is `cancel()`, callable by the taker after the cancellation timelock, which returns the entire escrowed `amount` back to the taker itself: [4](#0-3) 

Since a resolver already obtains the maker's source-chain tokens by revealing the same secret to withdraw the `EscrowSrc` (a separate, already-funded escrow), a malicious resolver can: (1) deploy the destination escrow with a deliberately invalid `parameters` field (fees > amount), (2) withdraw the maker's tokens on the source chain using the secret, and (3) after the destination cancellation timelock, call `cancel()` on the destination escrow to reclaim their own deposited destination funds — leaving the maker with nothing on the destination side despite having paid on the source side.

### Impact Explanation
This breaks the fundamental fund-distribution invariant of the swap lifecycle: the destination escrow must be able to pay the maker once a valid secret is provided. An unprivileged filler (resolver) can permanently freeze — and in the combined sequence effectively steal — maker funds meant to be received on the destination chain, matching "direct theft of user funds at rest or in motion" / "permanent freezing of funds" in the bounty's Critical/High impact bands.

### Likelihood Explanation
The attacker is any resolver/taker calling the public, unprivileged `createDstEscrow` entry point with a crafted `parameters` payload — no special privilege, governance, or malicious infrastructure role is required, matching the "unprivileged user … entering through destination escrow creation" attacker model exactly.

### Recommendation
Add the same guard used in `_postInteraction` to `createDstEscrow`:
```solidity
if (dstImmutables.protocolFeeAmount() + dstImmutables.integratorFeeAmount() >= dstImmutables.amount) revert InvalidFeeAmounts();
```
before deploying the destination escrow clone, so the invariant `protocolFeeAmount + integratorFeeAmount < amount` is enforced symmetrically on both the source and destination creation paths.

### Proof of Concept
1. Resolver constructs `IBaseEscrow.Immutables dstImmutables` with `amount = X` but encodes `parameters` such that `protocolFeeAmount + integratorFeeAmount > X` (both values are ABI-encoded directly into `parameters` by the caller, per `ImmutablesLib` layout, and are never cross-checked against `amount` in `createDstEscrow`).
2. Resolver calls `escrowFactory.createDstEscrow{value: ...}(dstImmutables, srcCancellationTimestamp)` — succeeds, no fee validation exists.
3. Resolver separately withdraws the maker's tokens from the corresponding `EscrowSrc` using the revealed secret (normal flow).
4. Anyone calling `EscrowDst.withdraw`/`publicWithdraw` with the correct secret reverts due to underflow in `immutables.amount - integratorFeeAmount - protocolFeeAmount`.
5. After the `DstCancellation` timelock elapses, the resolver calls `cancel()` and reclaims the full `amount` they deposited, while the maker never receives destination funds.

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
