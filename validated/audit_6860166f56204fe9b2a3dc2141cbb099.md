### Title
Unauthenticated `createWriteOffRequest` lets any tranche holder register arbitrarily large `underlyingsRequested` claims, inflating `pendingUnderlyings` and freezing epoch settlement - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` is permissionless and imposes no relationship between the tranche tokens escrowed and the `underlyingsRequested` recorded. An attacker holding a dust amount of tranche tokens can register a `WriteOffRequest` claiming an arbitrarily large amount of underlying, which is unconditionally added to the global `pendingUnderlyings` counter used by `IdleCDOEpochVariant` when sizing the borrower repayment required to stop the epoch. This is the on-chain analog of unauthenticated worker registration: an unprivileged caller registers an arbitrary claim into shared accounting, forcing the honest borrower to either overpay or be unable to settle the epoch.

### Finding Description
In `createWriteOffRequest` the only checks are `isEpochRunning()` and `amount != 0`; `underlyingsRequested` is user-controlled and unbounded:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol:86-102
if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
if (amount == 0) revert NotAllowed();
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
pendingUnderlyings += underlyingsRequested;
```

The escrowed `tranches` and the demanded `underlyings` are completely decoupled: a request backed by 1 wei of tranche tokens can demand `type(uint256).max` underlyings. `pendingUnderlyings` therefore becomes attacker-controlled shared state. `IdleCDOEpochVariant` reads this counter when computing what the borrower must return to close the epoch (write-off claims must be covered alongside expected interest), so an inflated `pendingUnderlyings` makes `stopEpoch`/`stopEpochWithDuration` require a repayment the honest borrower cannot or will not make.

`fullfillWriteOffRequest` and `deleteWriteOffRequest` do not mitigate this: fulfillment requires `currentRequest.tranches == _tranches` and `_underlyings >= currentRequest.underlyings` (lines 123-135), so no honest fulfiller will ever clear the malicious request, and only the attacker can delete it. The owner cannot purge a specific user's request either — `emergencyWithdraw` only moves token balances, not `userRequests`/`pendingUnderlyings` state.

### Impact Explanation
Permanent freezing of all lender funds. With `pendingUnderlyings` inflated beyond what the borrower will repay, the epoch can never be stopped: `stopEpoch`/`stopEpochWithDuration` revert or demand an impossible repayment, so AA and BB tranche holders' principal and accrued interest remain locked in the vault indefinitely. All funds deposited for the running epoch are affected; the attacker's cost is a negligible amount of tranche tokens (which are retrievable at will via `deleteWriteOffRequest`).

### Likelihood Explanation
The attacker only needs to be a tranche-token holder during a running epoch — an explicitly in-scope unprivileged role. No privileged cooperation, no oracle manipulation, and no race is required; a single transaction suffices. The only constraint is that the call must land while `isEpochRunning()` is true, which is the normal operating state for most of the pool's lifetime. There is no cap, no sanity check tying `underlyingsRequested` to tranche price, and no privileged escape hatch to clear a malicious request.

### Recommendation
Bound `underlyingsRequested` by the value of the escrowed tranches, e.g. require `underlyingsRequested <= amount * tranchePrice / ONE_TRANCHE` (using the current `virtualPrice`/`contractValue` of the tranche), or split the request into a fixed price-per-tranche so the demanded underlyings scale linearly with deposited tranches. Alternatively, allow the owner/manager to forcibly delete a `WriteOffRequest` and decrement `pendingUnderlyings`, refunding the escrowed tranches to the requester.

// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOEpochVariant} from "../contracts/IdleCDOEpochVariant.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract PendingUnderlyingsInflationPoC is Test {
    IdleCDOEpochVariant cdoEpoch;
    IdleCreditVaultWriteOffEscrow escrow;
    IERC20Detailed tranche;
    address attacker = address(0xA77AC);
    address borrower;

    function setUp() public {
        // fork mainnet at a block where the credit vault epoch is running
        // cdoEpoch = IdleCDOEpochVariant(<deployed IdleCDOEpochVariant>);
        // escrow = IdleCreditVaultWriteOffEscrow(<deployed escrow for AA tranche>);
        // tranche = IERC20Detailed(escrow.tranche());
        borrower = escrow.borrower();
        deal(address(tranche), attacker, 1); // 1 wei of tranche tokens
    }

    function testInflatePendingUnderlyings() public {
        assertTrue(cdoEpoch.isEpochRunning(), "epoch must be running");

        vm.startPrank(attacker);
        tranche.approve(address(escrow), 1);
        // register a claim for an absurd amount of underlyings
        // backed by a single wei of tranche tokens
        escrow.createWriteOffRequest(1, type(uint128).max);
        vm.stopPrank();

        // shared accounting is now attacker-controlled
        assertEq(escrow.pendingUnderlyings(), type(uint128).max);

        // honest borrower cannot ever fulfill: fullfillWriteOffRequest requires
        // _tranches == currentRequest.tranches (1 wei) and
        // _underlyings >= currentRequest.underlyings (type(uint128).max)
        vm.prank(borrower);
        vm.expectRevert(); // WrongRequest / insufficient balance
        escrow.fullfillWriteOffRequest(attacker, 1, type(uint128).max - 1);

        // owner cannot clear the request; only the attacker can, and won't.
        // stopEpoch now demands repayment covering pendingUnderlyings -> reverts,
        // permanently freezing all lender funds in the vault.
    }
}
