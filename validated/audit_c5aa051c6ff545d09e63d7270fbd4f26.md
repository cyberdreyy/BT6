### Title
Claimed instant-withdraw receipts remain in per-epoch claim accounting, inflating default recovery basis and reserve with phantom funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` when paying a funded instant claim, but never removes the per-epoch entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . If a default is later finalized in the *same* epoch, `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` reuse this stale ("freed") receipt data, counting already-paid claims as both recovery basis and already-held reserve [2](#0-1) . The result is an inflated `defaultRecoveryPrice`: early claimants are overpaid from real recovery funds while later claimants' transfers revert — direct theft plus permanent freezing.

### Finding Description
The bug class of CVE-2019-13224 is use-after-free: state that was logically released is later reused. The analog lives in the instant-withdraw receipt lifecycle:

1. `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[_user][epoch] += _amount` and `instantWithdrawClaimsByEpoch[epoch] += _amount` [3](#0-2) .
2. `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls underlying into the strategy [4](#0-3) .
3. `claimInstantWithdrawRequest` burns the receipt and pays at par, clearing only `instantWithdrawsRequests[_user]`. Neither `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` is reduced — the paid receipt is "freed" but its per-epoch record survives [1](#0-0) .
4. Later in the same epoch, a new unfunded instant request keeps `pendingInstantWithdraws != 0` at default time. `finalizeDefaultRecovery` then computes `pendingBasis += instantWithdrawClaimsByEpoch[epochNumber]` — including the already-claimed amount — and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying held in the strategy, although it was already transferred to the first claimant [5](#0-4) .
5. `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` is therefore overstated by the claimed amount, and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on a phantom reserve [6](#0-5) .

Because `defaultRecoveryReserve` is set to the inflated `reserveAmount` while the contract actually holds less, claims against the reserve (`_transferDefaultRecovery` decrements and transfers [7](#0-6) ) pay early claimants more than their pro-rata share and leave the last claimants with a reverting `safeTransfer`. The same stale per-epoch entry also lets `_claimDefaultedInstantWithdrawRequest` attempt a second burn/payout path for the already-claimed user [8](#0-7)  (blocked only by the user's empty receipt balance, so the primary loss is the reserve inflation).

### Impact Explanation
Direct theft and permanent freezing. In an epoch where some instant claims were funded and paid while others remain pending at default finalization, the recovery price is inflated by `claimedInstant / totalBasis`. An attacker holding a genuine defaulted-epoch instant (or normal pending) receipt is overpaid; the shortfall falls on honest pending-receipt holders and on active LPs whose `activeFinalNAV` mint used the same inflated price [9](#0-8) . Once the real balance is exhausted, all remaining `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert, permanently freezing the rest of the recovery reserve.

### Likelihood Explanation
Requires instant withdrawals enabled (`setInstantWithdrawParams`), at least one funded-and-claimed instant receipt, and a borrower default in the same epoch — all achievable by an unprivileged KYC'd lender plus ordinary protocol sequencing (the manager's `getInstantWithdrawFunds`/`stopEpoch` calls are honest actions, not attacker-controlled). No privileged misbehavior is needed; the accounting flaw triggers on the normal claim path. The window is one epoch, which is the designed horizon for instant withdrawals, making the scenario routine rather than exotic.

### Recommendation
In `claimInstantWithdrawRequest`, when the claim is satisfied from funded balances (not via `_claimDefaultedInstantWithdrawRequest`), also clear the per-epoch records: determine the user's request epoch entries (or track them at request time) and decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the paid amount. Alternatively, make `collectInstantWithdrawFunds`/`claimInstantWithdrawRequest` decrement `instantWithdrawClaimsByEpoch` so that `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` only ever see receipts that are still owed. Add a regression test that claims a funded instant receipt, defaults mid-epoch, and verifies the recovery price and reserve exclude the paid claim.

function testClaimedInstantReceiptInflatesDefaultRecovery() external {
    // epoch running, instant withdraws enabled via setInstantWithdrawParams(delay, minAprDiff, false)

    // 1) Alice deposits, requests instant withdraw of amount A.
    // 2) Manager calls getInstantWithdrawFunds() -> collectInstantWithdrawFunds(A)
    //    pendingInstantWithdraws: A -> 0; strategy holds A underlying.
    // 3) Alice claims at par. instantWithdrawsRequests[alice] = 0,
    //    BUT instantWithdrawsRequestsByEpoch[alice][N] == A
    //    and  instantWithdrawClaimsByEpoch[N]         == A   (stale).
    uint256 aAlice = 100 * ONE_SCALE;
    // ... drive request/fund/claim for Alice ...

    // 4) Bob requests instant withdraw of amount B in the SAME epoch N.
    uint256 bBob = 100 * ONE_SCALE;
    // pendingInstantWithdraws = B; instantWithdrawClaimsByEpoch[N] = A + B.

    // 5) Borrower returns nothing; stopEpoch(apr, 0) -> default, pendingInstantWithdraws = B != 0.
    // finalizeDefault(recovered, source):
    //   pendingBasis  = pendingWithdraws + instantWithdrawClaimsByEpoch[N]  // includes phantom A
    //   prefundedReserve = (A + B) - B = A                                  // not actually held
    //   reserveAmount = recovered + A (+ prior reserve)                     // overstated by A
    //   recoveryPrice = reserveAmount * 1e18 / totalBasis                   // inflated
    // Claim order: Bob claims first and is overpaid (or Alice's stale
    // instantWithdrawsRequestsByEpoch[alice][N] re-enters the defaulted-claim
    // path); the last claimant's safeTransfer reverts because the strategy is
    // short exactly A underlying -> recovery dust is permanently frozen.

    uint256 balance = underlying.balanceOf(address(strategy));
    uint256 reserve = IdleCreditVault(address(strategy)).defaultRecoveryReserve();
    assertLt(balance, reserve, "reserve exceeds real balance by claimed receipt amount");
}

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
