### Title
Instant-withdraw receipts created after `getInstantWithdrawFunds` can claim against funds reserved for earlier claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class in the external report is "missing check on an operation's result → a null/invalid value is used downstream". The analog in idle-tranches is in `IdleCreditVault.claimInstantWithdrawRequest`: the function never verifies that the caller's instant-withdraw receipt was actually *funded*. Funding is tracked only by the global flag `allowInstantWithdraw` (set on the CDO when `getInstantWithdrawFunds` collects the then-current `pendingInstantWithdraws` total) and by the global counter `pendingInstantWithdraws`. A request created *after* that collection increases `instantWithdrawsRequests[user]` and `pendingInstantWithdraws` but has no backing funds — yet `claimInstantWithdrawRequest` happily burns the receipt and pays out from underlying that was collected to satisfy earlier, honest claimants.

### Finding Description
Relevant code:

- `getInstantWithdrawFunds` pulls `_instantWithdraws = pendingInstantWithdraws()` from the borrower, calls `collectInstantWithdrawFunds`, and unconditionally sets `allowInstantWithdraw = true` (`contracts/IdleCDOEpochVariant.sol:558-574`).
- `requestWithdraw` routes to `creditVault.requestInstantWithdraw(_underlyings, msg.sender)` whenever the APR dropped (`lastEpochApr > unscaledApr + instantWithdrawAprDelta`) and instant mode is enabled — this works while the epoch is still running (`contracts/IdleCDOEpochVariant.sol:761-770`).
- `requestInstantWithdraw` mints the receipt and bumps `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`contracts/strategies/idle/IdleCreditVault.sol:356-375`).
- `claimInstantWithdrawRequest` only checks `defaultInstantWithdrawsFinalized`, then burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim` — there is no per-request/per-epoch funded check, no `epochNumber` maturity gate like `_claimFundedWithdrawRequest` has (`epochNumber <= lastWithdrawRequest[_user]` → revert at `IdleCreditVault.sol:326`), and no check that `pendingInstantWithdraws` was collected for this receipt (`contracts/strategies/idle/IdleCreditVault.sol:380-393`).
- `_transferFundedClaim` only guards the default-recovery reserve, not the instant-withdraw funding status (`contracts/strategies/idle/IdleCreditVault.sol:897-907`).

Attack sequence (running epoch, non-programmable borrower, instant mode active because the manager lowered APR at the last `stopEpoch`):

1. Honest users hold instant-withdraw receipts totalling `P`; `pendingInstantWithdraws == P`.
2. After `instantWithdrawDeadline`, the manager calls `getInstantWithdrawFunds()`: `P` underlyings move borrower → CDO → `IdleCreditVault`; `pendingInstantWithdraws` becomes 0; `allowInstantWithdraw = true`.
3. Attacker (KYC-passed tranche holder, `isWalletAllowed` passes) calls `requestWithdraw(...)`. Because the APR decreased, it takes the instant branch: tranche tokens burned via `_withdrawOps`, receipt minted, `pendingInstantWithdraws += amount` — but no `collectInstantWithdrawFunds` will run again this epoch (`getInstantWithdrawFunds` can be called again, but the borrower is honest and the point is the attacker can claim *before* any second collection).
4. Attacker calls `claimInstantWithdrawRequest()`: receipt is burned and `_transferFundedClaim` transfers `amount` of the `P` underlyings that belong to honest claimants.
5. When honest users later call `claimInstantWithdrawRequest`, `underlyingToken.safeTransfer` reverts on insufficient balance — their funded claims are frozen/stolen.

### Impact Explanation
Direct theft of funds reserved for other users' instant withdrawals. The strategy's underlying balance after step 2 is earmarked 1:1 for existing `instantWithdrawsRequests`; the attacker's unfunded receipt drains it, leaving honest receipts permanently unclaimable in that epoch (loss equal to the attacker's claimed amount, up to the full collected balance). This breaks the "one receipt one funded payout" invariant.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled (`!disableInstantWithdraw`, non-programmable borrower), (b) an APR decrease larger than `instantWithdrawAprDelta` at the previous epoch boundary so `requestWithdraw` takes the instant path, (c) a window between `instantWithdrawDeadline` and `epochEndDate` after the manager's `getInstantWithdrawFunds` call, and (d) withdraw requests being open during the running epoch (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` are set true at `stopEpoch` and remain so until a default/emergency). All conditions are reachable by an ordinary KYC'd lender in a normal epoch; the only timing dependency is acting after the manager's funding call, which is publicly observable on-chain.

### Recommendation
Track funded status per request (e.g., record `instantWithdrawsRequestsByEpoch[user][epoch]` and only allow claims for epochs whose funds were collected, similar to `lossRecoveryPriceByEpoch` / the `lastWithdrawRequest` maturity check), or have `claimInstantWithdrawRequest` verify that the claimable amount is backed: e.g., snapshot `fundedInstantWithdraws` in `collectInstantWithdrawFunds` and decrement it on claims instead of relying solely on `allowInstantWithdraw`. Alternatively, block `requestInstantWithdraw` (the instant branch in `requestWithdraw`) once `allowInstantWithdraw` is true for the current epoch.

### Proof of Concept
Foundry-fork PoC sketch (against the `IdleCreditVault.t.sol` harness conventions):

```solidity
// Setup: depositAA for honestUser and attacker; run epoch 0; manager lowers APR at
// stopEpoch so lastEpochApr > unscaledApr + instantWithdrawAprDelta.

// 1. honestUser requests instant withdraw (buffer)
vm.prank(honestUser);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // instant path, receipt minted

// 2. epoch 1 starts; instant deadline passes; manager collects funds
_startEpochAndCheckPrices(1);
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
vm.prank(manager);
cdoEpoch.getInstantWithdrawFunds();              // allowInstantWithdraw = true

// 3. attacker creates an unfunded instant receipt mid-epoch
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // pendingInstantWithdraws += amt, unfunded

// 4. attacker claims immediately, draining the honest user's funded balance
uint256 pre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();          // pays out from reserved funds
assertGt(underlying.balanceOf(attacker) - pre, 0);

// 5. honest user's funded claim now reverts (insufficient strategy balance)
vm.prank(honestUser);
vm.expectRevert();                               // safeTransfer insufficient balance
cdoEpoch.claimInstantWithdrawRequest();
```

Uncertainty: the exploit requires `allowAAWithdrawRequest`/`allowBBWithdrawRequest` to remain enabled during a running epoch so step 3 succeeds. The code shows these flags are set at `stopEpoch` (`IdleCDOEpochVariant.sol:481-482`) and only cleared on default/emergency, and `pendingWithdraws` is designed to accrue during the epoch for funding at the next `stopEpoch`, which strongly suggests mid-epoch requests are permitted — but I did not read `startEpoch` to confirm the flags are not cleared there. If mid-epoch requests are disabled, the same gap still applies to a request made in the buffer of the *next* epoch before `allowInstantWithdraw` is reset (it is only reassigned at the next `stopEpoch`, line 486), though that window is narrower.
