### Title
`depositDuringEpoch` never calls `_updateSplitRatio`, leaving `trancheAPRSplitRatio` stale and misallocating epoch interest between AA and BB tranches - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
The NOYA bug class — balance/state-changing connector functions that omit the required `_updateTokenInRegistry()` bookkeeping call, leaving stored state inconsistent with real balances — maps directly onto `IdleCDOEpochVariant.depositDuringEpoch`. Every other state-changing entry point keeps `trancheAPRSplitRatio` synchronized with the actual AA/BB NAV ratio: `_deposit` calls `_updateSplitRatio(_getAARatio(true))` after minting shares (`IdleCDOCreditVault.sol:208`), and the minted-fee path in `_stopEpoch` does the same (`IdleCDOEpochVariant.sol:448`). `depositDuringEpoch` mints tranche shares and mints backing strategy tokens (`IdleCDOEpochVariant.sol:725-730`) but never refreshes the split ratio, so the APR split used by `_updateAccounting`/`_virtualPriceAux` no longer reflects post-deposit TVL.

### Finding Description
In `depositDuringEpoch` (`contracts/IdleCDOEpochVariant.sol:656-733`) the flow is:

1. `_updateAccounting()` is called at line 682 — splitting accrued interest with the *current* `trancheAPRSplitRatio`.
2. Shares are minted via `_mintShares` at line 725 and strategy tokens are minted 1:1 at line 730, so the tranche's NAV/TVL grows.
3. `expectedEpochInterest` is bumped at line 728.
4. **No `_updateSplitRatio(_getAARatio(true))` call exists**, unlike `_deposit` (`IdleCDOCreditVault.sol:207-208`) and the minted-fee path (`IdleCDOEpochVariant.sol:448`).

`trancheAPRSplitRatio` is the variable that determines what fraction of the epoch gain each tranche receives in `_virtualPriceAux`/`_calcTrancheInterestShare` (`IdleCDOEpochVariant.sol:883-886`). Because it is frozen at its pre-deposit value, the interest split at `stopEpoch` (which calls `_updateAccounting` at line 436) and in every subsequent `requestWithdraw`/`_calcInterestWithdrawRequest` is computed against a stale ratio while NAVs already include the new deposit.

Concrete sequence (fixed-APR mode, buffer phase → running epoch):

1. Vault holds AA and BB deposits; `trancheAPRSplitRatio` is high (AA-favored, e.g. 90%).
2. Manager enables `isDepositDuringEpochDisabled = false` and starts an epoch.
3. Attacker — an AA holder — calls `depositDuringEpoch(X, BBTranche)` mid-epoch (allowed when `block.timestamp < epochEndDate`, BB supply > 0, `isBBDepositEnabled`). BB TVL grows substantially, which under the normal `_deposit` flow would lower the AA split ratio.
4. The ratio stays at 90%. At `stopEpoch`, `_virtualPriceAux` splits `totalGain` giving BB only `(FULL_ALLOC - 0.9)` of the interest despite BB now representing a much larger share of TVL. The attacker's AA position absorbs yield that economically belongs to BB holders.
5. Equivalently, the reverse direction works when the stale ratio is BB-favorable: an attacker holding BB deposits AA mid-epoch and over-earns at AA holders' expense.

The deviation is quantifiable: `excessGain = |staleRatio − _getAARatio(true)| × epochInterest / FULL_ALLOC`, which scales linearly with the attacker's deposit size and the epoch interest.

Existing guards do not stop it: `isAYSActive`, `isProgrammableBorrower`, and `skipDefaultCheck` checks (lines 658-669) are unrelated to split-ratio freshness; `_updateAccounting` at line 682 uses — but does not correct — the stale ratio.

### Impact Explanation
Direct theft of yield: tranche holders of the over-favored class receive a larger share of epoch interest than the TVL-consistent ratio entitles them to, paid for by holders of the other tranche. The attacker controls the deposit size and timing (any point during a running epoch), so the extracted amount scales with deposited principal up to the pool limit (`_guarded`).

### Likelihood Explanation
Requires the manager-enabled `depositDuringEpoch` path (`isDepositDuringEpochDisabled = false`), a running epoch, and a Keyring-passing wallet. All are normal operating conditions for vaults that use this feature. No privileged attacker is needed — the attacker is an ordinary KYC'd lender.

### Recommendation
Call `_updateSplitRatio(_getAARatio(true))` in `depositDuringEpoch` after minting the strategy tokens (after line 730), mirroring `_deposit` and the minted-fee branch of `_stopEpoch`, so `trancheAPRSplitRatio` always tracks the actual AA/BB NAV ratio before interest is next split.

### Proof of Concept
Foundry-style sketch (extend `test/foundry/IdleCreditVault.t.sol` patterns; enables mid-epoch deposits and compares the split ratio actually used against the TVL-consistent ratio):

```solidity
function testDepositDuringEpochStaleSplitRatio() external {
    // buffer phase: seed both tranches so AA ratio is high
    idleCDO.depositAA(900_000 * ONE_SCALE);
    idleCDO.depositBB(100_000 * ONE_SCALE); // trancheAPRSplitRatio ~= 90%

    vm.prank(manager);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    _startEpochAndCheckPrices(0);

    // attacker: large BB deposit mid-epoch, well inside epochEndDate
    address attacker = makeAddr("attacker");
    _depositWithUser(attacker, 0); // whitelist + fund
    uint256 bbDep = 900_000 * ONE_SCALE;
    deal(defaultUnderlying, attacker, bbDep);
    vm.startPrank(attacker);
    underlying.approve(address(cdoEpoch), bbDep);
    cdoEpoch.depositDuringEpoch(bbDep, cdoEpoch.BBTranche());
    vm.stopPrank();

    // BUG: ratio unchanged despite BB TVL now ~50% of pool
    uint256 staleRatio = cdoEpoch.trancheAPRSplitRatio();
    uint256 fairRatio  = cdoEpoch.getCurrentAARatio(); // reflects new TVL
    assertGt(staleRatio, fairRatio); // e.g. 0.9e5 vs ~0.5e5

    // at stopEpoch the stale ratio over-pays AA: quantified excess
    // excessAA = (staleRatio - fairRatio) * epochInterest / FULL_ALLOC
}
```
