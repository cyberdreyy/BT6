### Title
Cache size guard checks only compressed size, allowing zstd decompression-bomb caches to bypass `CACHE_MAX_UPLOADED_ARCHIVE_SIZE` and exhaust extractor resources on any consumer of the shared cache - ([File: commands/helpers/cache_archiver.go])

### Summary
`CacheArchiverCommand.Execute` calls `createZipFile` then `uploadArchiveIfNeeded(size)`, where `size` is the size of the *compressed* archive file on disk, and this is the only value compared against `MaxUploadedArchiveSize`. Because `tarzstd`/`zipzstd` formats can achieve extreme compression ratios on attacker-crafted, highly-repetitive file content, an attacker can build a cache archive that stays far under the configured byte limit while decompressing to an enormous size, and no code path in `CacheExtractorCommand` (or the underlying `tarzstd`/`fastzip`/`ziplegacy` extractors) enforces any bound on decompressed output size.

### Finding Description
`c.createZipFile` writes the archive using the archiver selected by `c.CompressionFormat` and returns `info.Size()` — the size of the file on disk after compression [1](#0-0) . `Execute` then passes that compressed size directly to `uploadArchiveIfNeeded`, which is the sole point of enforcement for `MaxUploadedArchiveSize` [2](#0-1) [3](#0-2) . The attacker fully controls the job's cache `paths` contents (files checked into the repo or generated by build scripts before the cache step runs), so they can populate the workspace with highly compressible content (e.g., large sparse/zero-filled files, or many files with identical repeated byte patterns) and select `CACHE_COMPRESSION_FORMAT: tarzstd` or `zipzstd`, both user-settable job variables [4](#0-3) .

On the consuming side, `CacheExtractorCommand.Execute` downloads the archive and calls `extractor.Extract(context.Background())` with no size ceiling of any kind [5](#0-4) . The `tarzstd` extractor opens a `zstd.NewReader` over the whole stream and does an unbounded `io.Copy(f, tr)` per file with no limit on the number of tar entries or bytes written [6](#0-5) . The `fastzip`/`ziplegacy` extractors delegate to third-party libraries that similarly stream-decompress without any decompressed-size ceiling [7](#0-6) [8](#0-7) . Neither extraction path uses `io.LimitReader`, a running byte counter with a ceiling, nor consults `MaxUploadedArchiveSize` (which is archiver-side only, and never propagated to the extractor invocation).

The docs already acknowledge that `MaxUploadedArchiveSize` "can [be] work[ed] around" and recommend enforcing it server-side via the GCS `X-Goog-Content-Length-Range` header [9](#0-8) , but that guidance addresses bypassing the *compressed*-size cap (e.g., chunked/streamed uploads exceeding the intended cap), not the decompression-bomb scenario where the compressed size is genuinely small and legitimately passes the check, yet the decompressed payload is disproportionate. No mitigation — server-side or client-side — targets decompressed-size at all.

### Impact Explanation
Any job (or pipeline author) that can set `CACHE_COMPRESSION_FORMAT` and control cached path contents can produce a cache object that is small on the wire/storage but explodes in size or file-count on extraction. Any other job — potentially on another branch, MR, or project sharing the same cache key/bucket path (`Shared: true` cache config) — that later runs `cache-extractor` against that object will attempt to fully decompress it in-process with `io.Copy`, consuming disk space, inodes, and CPU disproportionate to the stored/transferred size, degrading or crashing the runner host/container for unrelated tenants. Because the bomb is stored as a persistent cache object, this effect recurs on every subsequent job that restores the cache until the object is evicted or the key changes, matching the "persistent multi-tenant disruption" impact.

### Likelihood Explanation
Feasible and repeatable: the attacker only needs standard job-level control (setting `CACHE_COMPRESSION_FORMAT`/`CACHE_COMPRESSION_LEVEL` env vars and crafting cache file contents), both of which are ordinary, unprivileged CI configuration capabilities. No special runner or admin privileges are required. The exploit is deterministic (zstd ratios on synthetic repetitive data are well understood and reproducible), and the "shared cache key" precondition (matching keys/paths across branches or a `Shared: true` object storage bucket) is a common, documented GitLab Runner cache configuration, not an exotic edge case.

### Recommendation
Enforce an independent, extractor-side limit on decompressed output (total bytes written and/or total entry count), e.g., wrap the tar/zip content reader in a counting `io.Writer`/`io.LimitReader` inside `tarzstd`, `fastzip`, and `ziplegacy` extractors and abort with an error once a configurable ceiling (analogous to `CACHE_MAX_UPLOADED_ARCHIVE_SIZE`, e.g. `CACHE_MAX_EXTRACTED_ARCHIVE_SIZE`) is exceeded. Additionally, record the uncompressed size in cache metadata at archive time and validate it in `CacheExtractorCommand.Execute` before calling `extractor.Extract`.

### Proof of Concept
Go unit test outline for `commands/helpers/archive/tarzstd`:
1. Create a temp directory containing a single file of highly repetitive content (e.g., 2 GiB of zero bytes), sufficient to compress to well under 1 MiB with zstd `slowest` level.
2. Archive it with the `tarzstd` archiver (`archive.NewArchiver(archive.TarZstd, ...)`), assert the resulting file size is below a representative `CACHE_MAX_UPLOADED_ARCHIVE_SIZE` (e.g., < 5 MiB), demonstrating the upload guard would pass it.
3. Call `tarzstd.NewExtractor` and `Extract(ctx)` against the crafted archive, with an instrumented `dir` (e.g., a filesystem quota or a wrapped `os.Create`/`io.Copy` counter) and assert that decompressed bytes written exceed the compressed-size limit by multiple orders of magnitude, with no error returned and no ceiling enforced — proving the missing invariant ("stored cache objects must not allow disproportionate decompression resource impact").
4. Optionally repeat with `zipzstd`/`fastzip` extractor for the same content to confirm the gap is not tarzstd-specific.

func (e *extractor) Extract(ctx context.Context) error {
	zr, err := zstd.NewReader(io.NewSectionReader(e.r, 0, e.size), zstd.WithDecoderLowmem(true))
	if err != nil {
		return err
	}
	defer zr.Close()

	tr := tar.NewReader(zr)

	deferred := map[string]*tar.Header{}
	for {
		hdr, err := tr.Next()
		if err == io.EOF {
			break
		}
		if err != nil {
			return err
		}

		fi := hdr.FileInfo()
		if fi.Mode()&irregularModes != 0 {
			continue
		}

		var path string
		path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))
		if err != nil {
			return err
		}
		if !strings.HasPrefix(path, e.dir+string(filepath.Separator)) && path != e.dir {
			return fmt.Errorf("%s cannot be extracted outside of chroot (%s)", path, e.dir)
		}

		if err := os.MkdirAll(filepath.Dir(path), 0777); err != nil {
			return err
		}

		if ctx.Err() != nil {
			return ctx.Err()
		}

		switch {
		case fi.Mode()&os.ModeSymlink != 0:
			deferred[path] = hdr
			continue

		case fi.Mode().IsDir():
			deferred[path] = hdr

			err := os.Mkdir(path, 0777)
			if err != nil && !os.IsExist(err) {
				return err
			}

		case fi.Mode().IsRegular():
			f, err := os.Create(path)
			if err != nil {
				return err
			}

			if _, err := io.Copy(f, tr); err != nil {
				f.Close()
				return err
			}
			if err := f.Close(); err != nil {
				return err
			}
