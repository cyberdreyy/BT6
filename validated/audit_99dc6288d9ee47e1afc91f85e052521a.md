### Title
Unauthenticated-role privilege gap: `/v2/debug/pprof/*` requires only base authentication, not any minimum role, exposing full process memory/heap/goroutine/CPU profiles to view-role and run-role users - ([File: core/web/router.go])

### Summary
`metricRoutes(authv2)` mounts `net/http/pprof` handlers (`heap`, `goroutine`, `profile`, `trace`, `cmdline`, `allocs`, `block`, `mutex`, `threadcreate`) under the `authv2` group, which only requires successful authentication (`auth.AuthenticateByToken` or `auth.AuthenticateBySession`) with no role wrapper such as `auth.RequiresEditRole` or `auth.RequiresAdminRole`. Every other sensitive route in `v2Routes` (key export/import, admin user management, transfers) is wrapped in a role check, but the pprof endpoints are not, so a `view`-role user or API token is sufficient to pull full heap/goroutine dumps.

### Finding Description
In `core/web/router.go`, `v2Routes` builds `authv2` with only base authentication: [1](#0-0) 

At the end of the authenticated block it calls `metricRoutes(authv2)` directly, with the misleading comment "Debug routes accessible via authentication": [2](#0-1) 

`metricRoutes` registers the full standard-library pprof handler set with no additional wrapper: [3](#0-2) 

Contrast this with every other route in the same function, which is wrapped with `auth.RequiresRunRole`, `auth.RequiresEditRole`, or `auth.RequiresAdminRole` depending on sensitivity — e.g. key export requires admin, job runs require at least run role: [4](#0-3) [5](#0-4) 

The `Authenticate` middleware only verifies identity, not role, and simply calls `c.Next()` on success: [6](#0-5) 

The role-check helpers (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) exist and are the mechanism the codebase uses elsewhere to gate sensitive functionality by role, but none is applied to the pprof group: [7](#0-6) 

Since `UserRoleView` is the lowest role and is not filtered out anywhere in the pprof path, a view-role session or API token (or any restricted token with only view privileges) can call `GET /v2/debug/pprof/heap`, `/goroutine`, `/profile`, etc., and receive a 200 response with full profiling data — including raw process memory content via heap profiles, which can contain decrypted key material, session tokens, or other secrets currently resident in memory.

### Impact Explanation
This is an authorization-bypass / secret-disclosure class issue: a low-privilege authenticated caller (view role) can obtain data intended to require an elevated administrative capability, because there is no role check comparable to `RequiresAdminRole`/`RequiresEditRole` guarding pprof. Heap and goroutine dumps of a Go process can contain decrypted private keys, unencrypted session cookies, in-flight database credentials, and other transient secrets held in memory by the running node, materially escalating what a view-role credential can extract beyond its intended read-only scope.

### Likelihood Explanation
Minimal precondition: any valid authenticated session or API token, including the lowest `view` role, is sufficient — no edit/run/admin privilege is required. The request is a single unauthenticated-in-role GET call (`GET /v2/debug/pprof/heap`) and is fully repeatable at will since there is no additional gate, rate limit specific to this endpoint, or role check beyond generic authentication.

### Recommendation
Wrap `metricRoutes(authv2)` (or each route inside it) with `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`) consistent with how other sensitive/administrative endpoints are protected in `v2Routes`, e.g.:
```go
metricRoutes(authv2.Group("", ), ...) // apply auth.RequiresAdminRole to each handler
```
or more directly, change each `pprofGroup.GET(...)` registration in `metricRoutes` to wrap the handler with `auth.RequiresAdminRole(...)`.

### Proof of Concept
Go handler-level integration test plan (using existing `internal/cltest` router-setup helpers used by other `core/web` tests):
1. Create a test app and a user with `Role: clsessions.UserRoleView` (or generate a view-scoped API token via the existing test helpers used in `core/web/*_test.go`).
2. Build the router via `web.NewRouter(app, nil)`.
3. Issue `GET /v2/debug/pprof/heap` with the view-role session cookie or `X-API-KEY`/`X-API-SECRET` headers set to the view-role token.
4. Assert the response status is `200 OK` (not `401`/`403`), and that the body is non-empty pprof binary data (e.g., check `Content-Type: application/octet-stream` or successfully parse with `runtime/pprof` profile reader).
5. Repeat for `/v2/debug/pprof/goroutine` and `/v2/debug/pprof/profile?seconds=1`, confirming each returns 200 for the view-role credential.
6. As a control, assert that `/v2/keys/eth/export/:address` (wrapped by `auth.RequiresAdminRole`) returns `403 Forbidden` for the same view-role credential, demonstrating the inconsistency in role enforcement between pprof and other sensitive routes.

func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least

func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
