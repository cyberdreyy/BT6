### Title
Multisig-factory account creation is unauthenticated, allowing an attacker to squat the target account name with malicious parameters - ([File: multisig-factory/src/lib.rs])

### Summary
`MultisigFactory::create` derives the new multisig's account id purely from a caller-supplied `name` string, and lets *any* unprivileged caller execute the full `create_account` → `deploy_contract` → `transfer` → `new(...)` chain for that name with arbitrary `members`/`num_confirmations`. There is no binding between the intended owner and the name they plan to use, and no reservation/signature check tying the resulting account to whoever "should" own it. This is the direct NEAR analog of the Squads `create_key`-derived PDA issue: the identity of the to-be-created multisig is public and unauthenticated, so whoever's `create` transaction lands first wins the name, regardless of who "intended" to own it. [1](#0-0) 

### Finding Description
`create` computes the target account deterministically as `{name}.{current_account_id}` and immediately chains account creation, code deployment, deposit transfer, and multisig initialization in one call — with the `members` and `num_confirmations` fully controlled by whoever calls `create`: [2](#0-1) 

Nothing in this instruction verifies that the caller is the legitimate/expected owner of `name`, nor is there any prior reservation step binding a specific identity to that account name before the privileged initialization happens. Because NEAR account names for a given `name.factory` are a single, first-come-first-served scarce resource (exactly like the Squads PDA derived from an unauthenticated `create_key`), an attacker who learns the `name` a legitimate user intends to use (e.g., by observing the pending transaction before it is included, or simply by pre-emptively squatting an expected/common team name) can submit their own `create` call with the same `name` but with `members` set to keys they control. If the attacker's transaction lands first, the resulting multisig at `name.factory` is fully controlled by the attacker's member set/threshold instead of the intended owner's — this is the "wrongly parameterised deployment" analog: the on-chain multisig's authorization set diverges from what the legitimate depositor believes it to be.

The equality that should hold and is broken:
`members/threshold configured on name.factory == members/threshold intended by the party who chose "name"`
but instead becomes:
`members/threshold configured on name.factory == whichever caller's create() transaction for "name" is included first`

Unlike the batched Promise actions inside a single `create` call (which execute atomically and cannot be interleaved by another party), the *race* is between two entirely separate `create` calls targeting the same account id — nothing in the contract prevents this.

### Impact Explanation
If a team or organization later transfers funds into `name.factory` under the assumption that it is their own properly-configured multisig (with their intended threshold/members), an attacker who won the account-name race can authorize and execute `Transfer` requests from that account using their own keys, since they are the (sole) members with the threshold they set. This matches the "wrongly parameterised deployment" Critical-impact category: value ends up custodied under member/threshold parameters that were never actually agreed to or verified by the intended owner, and NEAR sent to that account can be moved by parties never entitled to it.

### Likelihood Explanation
Likelihood is Low-to-Medium: the attacker needs to win a race for a specific human-readable account name, either by observing a pending `create` transaction before inclusion or by pre-squatting a name they anticipate a target will use. This mirrors the "Low difficulty" rating of the original Squads report, since it relies on a race condition rather than any cryptographic or logic break, but it requires no privileged access, redeploy, or victim key — only unprivileged transaction submission against `multisig-factory`.

### Recommendation
Require the intended owner to prove control of the target identity before privileged parameters (`members`, `num_confirmations`) are committed — e.g., require a signed/attested reservation from a specific `predecessor_account_id` or public key that is echoed into `members`, or require the `create` caller's own account/key to be included in `members` so an attacker cannot squat a name with a member set the real owner never authorized. At minimum, document/enforce that depositors must independently verify `get_members`/`get_num_confirmations` on-chain before treating `name.factory` as their multisig, and consider adding a two-step reserve-then-confirm flow analogous to requiring the `create_key` signer in the original recommendation.

### Proof of Concept
1. Alice intends to create a team multisig via `multisig-factory` with `name = "team-multisig"`, `members = [Alice's key, ...]`, `num_confirmations = 3`, and submits her `create` transaction with an attached deposit.
2. Eve observes/anticipates the name `"team-multisig"` and submits her own call to `MultisigFactory::create` with the same `name` but `members = [Eve's keys]`, `num_confirmations = 1`, attaching her own deposit, and gets it included first: [2](#0-1) 
3. The account `team-multisig.factory` is now created and initialized under Eve's control (`Multisig::new` sets `members`/`num_confirmations` from Eve's call — see multisig2's `new`): [3](#0-2) 
4. Alice's subsequent `create` call for the same name fails at `create_account` (account already exists), and her attached deposit is returned — but the name `team-multisig.factory` is now permanently under Eve's control.
5. If Alice's team, believing `team-multisig.factory` is their properly configured multisig, deposits NEAR into it, Eve (as the sole member with `num_confirmations = 1`) can call `add_request_and_confirm` to transfer those funds out at will.

#[near_bindgen]
impl MultisigFactory {
    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
