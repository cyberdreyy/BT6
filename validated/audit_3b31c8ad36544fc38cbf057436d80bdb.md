### Title
Cache-key path traversal via unhashed `AlternateArchiveFile` when `FF_HASH_CACHE_KEYS` is enabled - ([File: shells/abstract.go])

### Summary
When `FF_HASH_CACHE_KEYS` is on, `newCacheConfig` skips `cachekey.Sanitize` and derives `AlternateKey`/`AlternateArchiveFile` directly from the unsanitized, attacker-controlled `humanKey`, allowing `../`-style traversal segments to reach `path.Join`/`filepath.Rel` unfiltered, while the primary `ArchiveFile` remains safe because it is built from the SHA-256 `hashedKey`.

### Finding Description
`newCacheConfig` builds `rawKey` from the user-controlled `key`/`CACHE_FALLBACK_KEY` CI value (`build.GetAllVariables().ExpandValue(userKey)`) at [1](#0-0) . Normally `cachekey.Sanitize` is applied, which cleans `../`/`.` traversal segments against a virtual root before they can be used in any path [2](#0-1) . However, when `FF_HASH_CACHE_KEYS` is on, the sanitizer is replaced by an identity function that returns the raw key unchanged: [3](#0-2) .

`humanKey` (now unsanitized) is used to compute `alternateKey` via `cacheAlternateKey(humanKey, true)`, which — when hashing is enabled — returns `humanKey` itself (unhashed) as the "alternate" key for the legacy/unhashed naming scheme: [4](#0-3)  and [5](#0-4) .

That `alternateKey` is fed into `getArchivePath`, which builds the file path with `path.Join(build.CacheDir, key, "cache.zip")` and then `filepath.Rel(build.BuildDir, file)`: [6](#0-5) . `path.Join`/`path.Clean` resolve `..` segments lexically, without any filesystem-aware root confinement, so a key such as `../../etc/x` will move the resulting path outside `build.CacheDir`. The primary `ArchiveFile` is safe because it is built from `hashedKey = sha256(humanKey)` (hex digest, no path metacharacters) [7](#0-6) , but `AlternateArchiveFile` bypasses that protection entirely when hashing is on.

The resulting `cacheConfig.AlternateArchiveFile`/`AlternateKey` are subsequently used by the cache-extractor/archiver flow (`addExtractCacheCommand` uses `AlternateKey` for `getAlternateCacheDownloadURL`, and `AlternateArchiveFile` would be used analogously on the archiving side) as a real file/object path, so no other check re-validates it. There is no existing check that re-applies `Sanitize` or otherwise restricts the alternate key to remain inside `CacheDir`/`BuildDir`.

### Impact Explanation
Because `AlternateArchiveFile`/`AlternateKey` are derived from unsanitized attacker input under `FF_HASH_CACHE_KEYS=true`, a pipeline author who controls the `cache: key` (or `CACHE_FALLBACK_KEY`) value can craft a key with `../` segments to shift the "alternate" cache archive file location outside of `build.CacheDir` (and potentially outside `build.BuildDir`, since `filepath.Rel` does not clamp the result — a `..`-prefixed relative path is a valid, unrestricted return value). This is a legitimate path-confinement violation for the "upgrade"/legacy compatibility mechanism, though the practical blast radius depends on what consumes `AlternateArchiveFile`/`AlternateKey` downstream (e.g., cache-archiver/extractor helper binary) and whether that consumer performs its own additional path validation, which is not visible in `shells/abstract.go`.

### Likelihood Explanation
Preconditions are attacker-reachable: `FF_HASH_CACHE_KEYS` must be enabled (an increasingly common/default-track feature flag, not an admin-only opt-in restricted to trusted operators), and the attacker only needs to control a job's `cache: key` or `CACHE_FALLBACK_KEY` CI/CD value — both are standard, unprivileged pipeline-author-controlled inputs. The bug is deterministic and repeatable: any job with a crafted key reliably produces an out-of-root `AlternateArchiveFile` value.

### Recommendation
Always run `cachekey.Sanitize` (or an equivalent path-traversal-safe normalization) on `rawKey`/`humanKey` regardless of `FF_HASH_CACHE_KEYS`, since sanitization protects path construction, not just human-readability; keep the hashing step orthogonal to sanitization. Alternatively, harden `getArchivePath` itself to reject/clamp any resulting path that (after `filepath.Rel`) starts with `..` or escapes `build.CacheDir`, independent of which key (hashed or alternate) is passed in.

### Proof of Concept
```go
func TestNewCacheConfig_AlternateArchiveFile_PathTraversal_HashingOn(t *testing.T) {
	build := &common.Build{
		CacheDir: "/builds/cache",
		BuildDir: "/builds/project",
		// ... minimal JobInfo/GitInfo/Runner setup with FF_HASH_CACHE_KEYS=true
	}
	build.Variables = append(build.Variables, common.JobVariable{
		Key: "FF_HASH_CACHE_KEYS", Value: "true",
	})

	cc, _, err := newCacheConfig(build, "../../etc/x")
	require.NoError(t, err)

	// Primary path stays safe (hashed key)
	rel, err := filepath.Rel(build.BuildDir, filepath.Join(build.CacheDir, cc.HashedKey, "cache.zip"))
	require.NoError(t, err)
	assert.False(t, strings.HasPrefix(rel, ".."))

	// Alternate path must also stay confined -- assert this FAILS pre-fix
	assert.False(t, strings.HasPrefix(cc.AlternateArchiveFile, ".."),
		"AlternateArchiveFile escaped CacheDir via unsanitized humanKey: %s", cc.AlternateArchiveFile)
}
```
Expected (pre-fix): the assertion fails, showing `cc.AlternateArchiveFile` resolves outside `build.CacheDir`/`build.BuildDir` (e.g., contains a leading `../` sequence), confirming the traversal. After applying the recommended fix (always sanitizing `humanKey` before deriving `AlternateKey`/`AlternateArchiveFile`), the assertion should pass.

```go
// cacheAlternateKey returns the "other" archive key relative to the current FF_HASH_CACHE_KEYS setting.
// When hashing is enabled, the alternate is the unhashed (human-readable) key.

func cacheAlternateKey(humanKey string, hashEnabled bool) string {
	sha256Key := fmt.Sprintf("%x", sha256.Sum256([]byte(humanKey)))
	if hashEnabled {
		return humanKey
	}
	return sha256Key
}
```

```go
func Sanitize(cacheKey string) (string, error) {
	if cacheKey == "" {
		return "", nil
	}

	// Decode percent-encoded chars and normalise separators, then
	// resolve traversals against a virtual root so ".." can never
	// escape beyond the root.
	cleaned := path.Clean("/" + normaliser.Replace(cacheKey))

	// Strip the leading "/" we added, split into segments, then walk
	// backwards trimming trailing whitespace from the rightmost
	// segments—dropping any that become empty.
	parts := strings.Split(cleaned[1:], "/")
	n := len(parts)
	for n > 0 {
		parts[n-1] = strings.TrimRightFunc(parts[n-1], unicode.IsSpace)
		if parts[n-1] != "" {
			break
		}
		n--
	}
```
