### Title
proxy-exec's `cmd.WaitDelay` bound allows a detached grandchild process to outlive job cancellation - ([File: commands/helpers/proxy_exec.go])

### Summary
`ProxyExecCommand.Execute` runs the user-supplied command with `cmd.Stdout`/`cmd.Stderr` wired to `proxy.Stdout()`/`proxy.Stderr()` and sets `cmd.WaitDelay = time.Second` purely to stop `cmd.Run()` hanging when a backgrounded child inherits the pipe FDs. This bound only affects `os/exec`'s internal FD-copy goroutines; it does not send any signal to, or wait on, a detached/double-forked grandchild, so such a process keeps running as an orphan after `Execute` returns and the job is reported complete or cancelled.

### Finding Description
In `commands/helpers/proxy_exec.go`, `Execute` builds `cmd := exec.Command(args[0], args[1:]...)`, pipes stdout/stderr through the `addmask` proxy, and sets `cmd.WaitDelay = time.Second` before calling `cmd.Run()` [1](#0-0) . `WaitDelay` in Go's `os/exec` only bounds how long `Wait()` will block on the stdio-copying goroutines after the *direct* child process has exited; it neither kills descendant processes nor establishes a process group. The comment above it confirms this is only meant to unblock a hung `Run()` when "background processes have inherited the stdout/stderr pipe FDs" [2](#0-1) . The existing regression test, `TestProxyExecBackgroundProcess`, demonstrates exactly this scenario — a `(sleep 30 &)` double-forked child inherits the FDs — and confirms `Execute` returns promptly ("done" is printed) while the grandchild (`sleep 30`) is left running unmanaged [3](#0-2) .

Unlike other execution paths in the runner (`executors/shell/shell.go` via `helpers/process`, and `shells/proxy_exec.go`'s use of the killer/process-group machinery), `commands/helpers/proxy_exec.go` sets no `SysProcAttr{Setpgid: true}` and registers no `Cancel`/kill hook — a grep of `commands/helpers/**` for `SysProcAttr`/`Setpgid` returned no matches. Compare this to the SSH stub server, which explicitly sets `Setpgid: true` and a `cmd.Cancel` that sends `SIGKILL` to the negative PID (the whole process group) [4](#0-3) , and to the shell executor's `Run`, which relies on `helpers/process.osCmd.Start` calling `setProcessGroup` (`Setpgid: true`) so that job cancellation's `syscall.Kill(-pid, SIGTERM/SIGKILL)` reaches the whole group [5](#0-4) [6](#0-5) . `ProxyExecCommand.Execute` has none of this: it's a single `exec.Command`/`cmd.Run()` call with no `Setpgid`, so a job script that runs something like `(malicious_binary &)` (or any double-fork/`setsid`-based detach) produces a grandchild that is reparented outside the direct child's process tree and outside any process group the runner tracks for cancellation.

Whether this is exploitable at the full job-cancellation level depends on what invokes `proxy-exec` and how. Per the docs and code, normal job scripts (shell, docker, kubernetes executors) are terminated via SIGTERM/SIGKILL to the *build script's* process group, established by `setProcessGroup`/job-object logic in `helpers/process`, not via `proxy-exec` [7](#0-6) . `commands/helpers/proxy_exec.go` (`ProxyExecCommand`) is a separate helper binary command, referenced from `shells/proxy_exec.go`, used in some executor cache/artifact/masking-related internal invocations (e.g., referenced in `executors/docker/docker_command.go`, `common/buildtest/masking.go`), not as the primary job-script runner. I could not fully confirm from the available index which stage(s) route the actual job command through `proxy-exec` versus through the standard shell/process-group path — this needs verification in a live checkout, since the index only shows references, not full call sites in `shells/proxy_exec.go`.

### Impact Explanation
If `proxy-exec` is on any path where user/job-controlled command lines are executed (directly or via a generated script), an attacker who controls job input can leave an unbounded-lifetime orphaned process running on the runner host/container after the job is reported cancelled/completed. Scoped impact: violation of the "processes terminated at job boundary" invariant — resource exhaustion, continued execution of attacker code post-cancellation, and (in shared-runner/shell-executor-like contexts) potential collision with subsequent jobs reusing the same working directory/host. This is bounded by the same trust model as any shell-executor job (attacker already runs arbitrary code within the job), but the specific bug is that the *cancellation/cleanup* invariant is not enforced for this particular execution path, unlike the shell executor's SIGTERM-to-process-group mechanism.

### Likelihood Explanation
Feasibility is high in isolation: the existing `TestProxyExecBackgroundProcess` test already proves a backgrounded/double-forked child survives `Execute` returning, using a totally generic shell primitting `(cmd &)`. The precondition is that `ProxyExecCommand.Execute` be reachable with attacker-influenced `args`, e.g., a job-controlled command string. I could not verify from the index alone that ordinary job scripts route through this exact `ProxyExecCommand.Execute` code path rather than the standard shell/process-group-based executor path — `shells/proxy_exec.go` (not fully read) appears to be the caller-side wiring and would need to be inspected to confirm whether the command line passed to `proxy-exec` is attacker-controlled job content or a fixed/internal helper invocation (e.g., masking/cache/artifact helper commands with fixed arguments).

### Recommendation
If `proxy-exec` can run attacker-influenced command lines, apply the same containment used elsewhere in the codebase: set `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}` before `Start()`/`Run()`, and after `cmd.Run()` (or on cancellation/signal), kill the negative PID (`syscall.Kill(-cmd.Process.Pid, syscall.SIGKILL)`) to terminate the whole process group, mirroring `helpers/process/killer_unix.go` and `helpers/ssh/stub_ssh_server_unix.go`. If `proxy-exec` is only used for fixed, non-job-controlled internal helper invocations, then the scoped impact does not apply and this should be documented as intentional trusted-input behavior — this distinction should be confirmed by inspecting `shells/proxy_exec.go` and its callers.

### Proof of Concept
Extend `commands/helpers/proxy_exec_test.go`:
```go
func TestProxyExecOrphanedGrandchildOutlivesJob(t *testing.T) {
    dir := t.TempDir()
    marker := filepath.Join(dir, "still-running")
    shellCmd := []string{"sh", "-c",
        "(sleep 5; touch " + marker + " &); echo done"}
    args := append([]string{os.Args[0], "proxy-exec", "--temp-dir", dir}, shellCmd...)

    app := newProxyExecTestApp()
    buf := new(bytes.Buffer)
    defer captureOutput(buf)()

    require.NoError(t, app.Run(args))
    // Execute returned (WaitDelay unblocked Run()) but the marker file must
    // not exist yet -- the grandchild (sleep 5; touch) is still running,
    // proving it outlived cmd.Run().
    require.NoFileExists(t, marker, "grandchild should still be running after Execute returned")
    time.Sleep(6 * time.Second)
    require.FileExists(t, marker, "grandchild ran to completion, unmanaged, after job boundary")
}
```
Expected assertions: `Execute`/`app.Run` returns promptly (bounded by `WaitDelay`), the marker file does not exist immediately after return (proving the grandchild is still alive past the "job boundary"), and it appears later (proving the grandchild was never terminated). A companion PoC job step would be `(sleep 300 &)` in `script:`, followed by immediate `cancel()` of the pipeline; the assertion is that the orphaned `sleep 300` PID remains listed in `/proc` (or `ps`) after the job status transitions to canceled and after `WaitDelay` has elapsed.

```go
// TestProxyExecBackgroundProcess regression-tests that proxy-exec returns
// promptly when the executed command spawns a backgrounded subprocess that
// inherits stdout/stderr. The `(sleep 30 &)` subshell double-forks sleep so
// it's reparented away from sh, but sleep still inherits sh's stdout/stderr
// file descriptors. With the previous cmd.Stdout = proxy.Stdout() approach,
// os/exec's internal copy goroutine would block on EOF until sleep exited.
func TestProxyExecBackgroundProcess(t *testing.T) {
	if runtime.GOOS == "windows" {
		t.Skip("relies on POSIX shell double-fork semantics")
	}

	dir := t.TempDir()
	shellCmd := []string{"sh", "-c", "(sleep 30 &); echo done"}
	args := append([]string{os.Args[0], "proxy-exec", "--temp-dir", dir}, shellCmd...)

	app := newProxyExecTestApp()
	buf := new(bytes.Buffer)
	defer captureOutput(buf)()

	done := make(chan error, 1)
	go func() {
		done <- app.Run(args)
	}()

	select {
	case err := <-done:
		require.NoError(t, err)
		require.Contains(t, buf.String(), "done")
	case <-time.After(5 * time.Second):
		t.Fatal("proxy-exec did not return within 5s — likely blocked on inherited stdout/stderr FDs")
	}
}
```
