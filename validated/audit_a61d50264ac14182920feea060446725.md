### Title
Removed Multisig Member's Stale Confirmation Still Counts Toward Threshold, Allowing Requests to Execute Below the Live Threshold - (File: multisig2/src/lib.rs)

### Summary
The `confirm()` function in `MultiSigContract` counts confirmations stored in a `HashSet<String>` keyed by `request_id`, but never re-validates that each entry in that set still belongs to a currently active member of `self.members`. When a member is removed via `DeleteMember`, any confirmation that member previously cast on a still-pending request remains in the `confirmations` map and continues to count toward `num_confirmations`, even though that member no longer has any authority over the account.

### Finding Description
`confirm()` only checks that the *new* confirming party is a current member (`current_member()` checks `self.members.contains(&member)`), then adds their confirmation to the set and compares the set's cardinality to `self.num_confirmations`: [1](#0-0) 

Confirmations already stored in `self.confirmations` for a request are never revisited or invalidated when membership changes. `execute_request()` handles `DeleteMember` by simply removing the member from the `members` set / removing the access key or account — it does not iterate over `self.requests`/`self.confirmations` to strip that member's prior confirmations from any still-open request: [2](#0-1) 

The struct definitions show `confirmations: LookupMap<RequestId, HashSet<String>>` is entirely decoupled from `members: UnorderedSet<MultisigMember>`; there is no linkage that purges stale entries on membership change: [3](#0-2) 

This mirrors the external report's bug class exactly: a validation/consolidation path allows a state value (here, "number of confirmations for a request") to be computed from stale/inherited data rather than being freshly re-validated against the current authoritative state (here, the *live* member set), letting the guarded action (`execute_request`) fire without the intended live-K-of-N authorization.

**Binding that should hold:**
`confirmations_counted(request) == |{m ∈ confirmations(request) : m ∈ live_members}|`

**What actually holds:**
`confirmations_counted(request) == |confirmations(request)|` (includes members removed after they confirmed).

### Impact Explanation
If a member is removed from the multisig (routine key rotation, revoking a compromised key, offboarding, etc.) after having confirmed a still-pending request, that stale confirmation continues to count. A single additional confirmation from one remaining live member can then push the count to `num_confirmations`, causing `execute_request()` to run a `Transfer`, `DeployContract`, `AddKey`, `FunctionCall`, etc., with only `num_confirmations - 1` (or fewer) *live* authorizations. This is a "multisig request executed below threshold" — explicitly listed as a Critical-impact custody-binding violation, since NEAR can move (`Transfer`) or the account's authority can be altered (`AddKey`/`AddMember`) without genuine live-member consensus.

### Likelihood Explanation
This does not require exploiting a compromised key or a privileged attacker beyond the ordinary operational lifecycle of a multisig: any pending request combined with a routine, legitimate member-removal action (which does not itself need to be malicious) is enough to leave a stale confirmation counted. It is a realistic sequencing bug rather than a theoretical one: multisig deployments regularly rotate/remove keys/members while other requests may be pending, and no code path purges or re-checks confirmations on membership change.

### Recommendation
When executing `DeleteMember` (and equivalently `AddKey`/key-based removal in `multisig/src/lib.rs`), iterate all pending requests' confirmation sets and remove the departing member's entry, or — more robustly — have `confirm()` recompute the count by filtering `confirmations.get(&request_id)` against `self.members.contains(...)` before comparing to `self.num_confirmations`, so stale confirmations from removed members never count.

### Proof of Concept
1. Deploy `MultiSigContract::new([A, B, C], 2)` (2-of-3 threshold).
2. Member `A` calls `add_request_and_confirm` with a malicious `Transfer` request `R` targeting an attacker-controlled account. `confirmations[R] = {A}` (1 of 2 needed).
3. Separately, members `B` and `C` legitimately execute a `DeleteMember{A}` request (e.g., because `A`'s key was compromised or `A` left the organization) via `confirm()` — this succeeds and removes `A` from `self.members`. `confirmations[R]` is untouched, still `{A}`.
4. `B` calls `confirm(R)`. `current_member()` validates `B` is still live. `confirmations.len() (1, from A) + 1 (B) = 2 >= num_confirmations (2)` → `execute_request(R)` runs, transferring funds to the attacker's account.
5. Result: the transfer executed with confirmations from only one live member (`B`) plus one stale confirmation from a removed, no-longer-authorized member (`A`) — i.e., below the true 2-of-3 live threshold.

Note: I was unable to directly view the body of `delete_member`/`add_member` helper functions (only their call sites in `execute_request`) within the available context; this analysis assumes — consistent with all code paths reviewed — that no confirmation-purging logic exists elsewhere in the file. This should be verified against the full `delete_member` implementation before remediation.

    fn execute_request(&mut self, request: MultiSigRequest) -> PromiseOrValue<bool> {
        let mut promise = Promise::new(request.receiver_id.clone());
        let receiver_id = request.receiver_id.clone();
        let num_actions = request.actions.len();
        for action in request.actions {
            promise = match action {
                MultiSigRequestAction::Transfer { amount } => promise.transfer(amount.into()),
                MultiSigRequestAction::CreateAccount => promise.create_account(),
                MultiSigRequestAction::DeployContract { code } => {
                    promise.deploy_contract(code.into())
                }
                MultiSigRequestAction::AddMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.add_member(promise, member)
                }
                MultiSigRequestAction::DeleteMember { member } => {
                    self.assert_self_request(receiver_id.clone());
                    self.delete_member(promise, member)
                }
                MultiSigRequestAction::AddKey {
                    public_key,
                    permission,
                } => {
                    self.assert_self_request(receiver_id.clone());
                    if let Some(permission) = permission {
                        promise.add_access_key(
                            public_key.into(),
                            permission
                                .allowance
                                .map(|x| x.into())
                                .unwrap_or(DEFAULT_ALLOWANCE),
                            permission.receiver_id,
                            permission.method_names.join(","),
                        )
                    } else {
                        // wallet UI should warn user if receiver_id == env::current_account_id(), adding FAK will render multisig useless
                        promise.add_full_access_key(public_key.into())
                    }
                }
                MultiSigRequestAction::FunctionCall {
                    method_name,
                    args,
                    deposit,
                    gas,
                } => promise.function_call(
                    method_name,
                    args.into(),
                    deposit.into(),
                    Gas::from(gas.0),
                ),
                // the following methods must be a single action
                MultiSigRequestAction::SetNumConfirmations { num_confirmations } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.num_confirmations = num_confirmations;
                    return PromiseOrValue::Value(true);
                }
                MultiSigRequestAction::SetActiveRequestsLimit {
                    active_requests_limit,
                } => {
                    self.assert_one_action_only(receiver_id, num_actions);
                    self.active_requests_limit = active_requests_limit;
                    return PromiseOrValue::Value(true);
                }
            };
        }
        promise.into()
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
