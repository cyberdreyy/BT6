### Title
Cross-job Ctrl-C/Ctrl-Break disruption via process-global Win32 console state in `taskTerminate` - ([File: helpers/process/killer_windows.go])

### Summary
`taskTerminate` manipulates process-wide Win32 console state (`FreeConsole`/`AttachConsole`/`SetConsoleCtrlHandler`/`GenerateConsoleCtrlEvent`) from a single, multi-goroutine `gitlab-runner` process that runs many concurrent jobs. Because these APIs operate on the calling process as a whole (not per-goroutine or per-job), and because non-legacy children are placed in a new process group while legacy-mode children inherit the runner's own console/process group, terminating one job can broadcast a Ctrl signal into, or transiently detach the console for, an unrelated concurrently running job.

### Finding Description
`taskTerminate` (helpers/process/killer_windows.go:60-111) is invoked per-job from `windowsKiller.Terminate` [1](#0-0) . When `UseWindowsLegacyProcessStrategy` is true, it calls `FreeConsole()` (detaching the *runner process*, not just the job, from its current console), then `AttachConsole(pid)` (attaching the *runner process* to the target job's console), then disables the Ctrl handler for the whole runner process, then fires `GenerateConsoleCtrlEvent` and re-attaches back to `MaxUint32` (parent console) [2](#0-1) .

Crucially, `FreeConsole`, `AttachConsole`, and `SetConsoleCtrlHandler` are documented Win32 APIs whose effects apply to the *calling process*, not to a specific job/goroutine. `gitlab-runner` runs many jobs concurrently as goroutines inside one OS process, so a concurrent call to `taskTerminate` for job A temporarily rewires the *entire runner process's* console attachment and disables its Ctrl handler while job B's termination/monitoring logic (or job B's own console-owning children) may be relying on the previous console state. There is no mutex/lock serializing calls to `taskTerminate`, so two terminations (or a termination racing with normal execution) can interleave arbitrarily.

In the legacy path, `setProcessGroup` only assigns `CREATE_NEW_PROCESS_GROUP` when `UseWindowsLegacyProcessStrategy` is *false* [3](#0-2) . This means legacy-mode child processes do **not** get their own process group ID and inherit the group ID of their parent (the runner process). `GenerateConsoleCtrlEvent(CTRL_C_EVENT, pid)` in the legacy branch delivers the event to every process sharing that process group attached to the target console [4](#0-3)  — which, for legacy-mode jobs sharing the runner's inherited console/group, is not limited to job A's process tree.

`UseWindowsLegacyProcessStrategy` is a `Commander`/`CommandOptions` field wired from executor configuration (shell/custom executors) [5](#0-4) , but it is a runner/executor-side configuration flag, not something a pipeline author controls per-job. A job script can still influence the shared console state simply by spawning its own console-owning subprocesses (calling `AllocConsole`, its own `AttachConsole`, or `SetConsoleCtrlHandler`) — ordinary, unprivileged behavior available to any Windows shell-executor job — creating the race described.

### Impact Explanation
If reachable, the impact is a cross-job disruption: cancelling/terminating job A on a shared Windows host could send `CTRL_C_EVENT`/`CTRL_BREAK_EVENT` into an unrelated job B's console-attached process group, or transiently break job B's console I/O due to the runner-wide `FreeConsole`/`AttachConsole` toggling. This matches "termination of one job affecting another job's console/process" — a genuine cross-job interference issue, though it is a denial-of-service/interruption of another job rather than data exfiltration, privilege escalation, or sandbox escape.

### Likelihood Explanation
This requires: (1) the shell executor running on a shared Windows host, (2) `UseWindowsLegacyProcessStrategy` enabled (this is an executor-configured legacy behavior, generally used for compatibility, not attacker-selectable), (3) two jobs running concurrently in the same runner process on the same host, and (4) one job cancelled while another is in the vulnerable console-manipulation window (a small race window between the paired Free/Attach calls). This is a real concurrency hazard rooted in Win32 API semantics (console state is process-global) combined with `gitlab-runner`'s multi-job-per-process model, but triggering it reliably needs configuration control (legacy strategy on) that is typically an operator/executor setting rather than something a normal pipeline author flips per job, and the race window is narrow. I could not verify from the available code whether `UseWindowsLegacyProcessStrategy` can be influenced by job-level CI configuration (e.g., a `.gitlab-ci.yml` field) as opposed to only runner `config.toml`/executor defaults — this determines whether an "unprivileged pipeline author" can actually opt into the vulnerable legacy path, which affects how directly attacker-controlled this precondition is.

### Recommendation
- Serialize all `taskTerminate` calls process-wide with a mutex so only one legacy-mode termination sequence (Free/Attach/SetConsoleCtrlHandler/GenerateConsoleCtrlEvent/restore) can run at a time across the whole runner process.
- Avoid running legacy-mode (no `CREATE_NEW_PROCESS_GROUP`) processes concurrently with the console-swapping termination logic; prefer always assigning each spawned process its own process group (as already done in the non-legacy path) so `GenerateConsoleCtrlEvent` cannot reach unrelated jobs' groups.
- Consider deprecating/removing the legacy strategy path in favor of the process-group-based approach, which does not require mutating the runner's own console attachment.

### Proof of Concept
Extend `helpers/process/killer_windows_integration_test.go` style tests: start two `Commander`s with `UseWindowsLegacyProcessStrategy: true`, each running a helper binary that installs a `SetConsoleCtrlHandler` and logs any received `CTRL_C_EVENT`/`CTRL_BREAK_EVENT` to a file. Concurrently call `Terminate()` on the first process's killer while the second process sleeps. Assert:
- The second process's log file shows **no** Ctrl event was received.
- The second process exits normally (via its own sleep completion), not via a Ctrl signal.

Run the two `taskTerminate` invocations back-to-back with a small sleep between `FreeConsole`/`AttachConsole` calls (instrumented via a test hook) to force the race window and check for cross-delivery.

func (pk *windowsKiller) Terminate() {
	if pk.cmd.Process() == nil {
		return
	}

	if err := taskTerminate(pk.cmd.Process().Pid, pk.cmd.options.UseWindowsLegacyProcessStrategy); err != nil {
		pk.logger.Warn("Failed to terminate process:", err)

		// try to kill right-after
		pk.ForceKill()
	}
}
