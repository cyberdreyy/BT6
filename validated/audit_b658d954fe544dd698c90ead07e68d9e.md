### Title
Unsynchronized status check-then-set in `InitiateForcefulShutdown`/`forcefulShutdown` allows concurrent calls to exceed the 2-SIGINT forceful-shutdown budget on Windows - ([File: helpers/runner_wrapper/wrapper_windows.go])

### Summary
`Wrapper.InitiateForcefulShutdown` (`helpers/runner_wrapper/wrapper.go`) reads the process pointer, calls the platform-specific `forcefulShutdown`, and only afterward calls `w.setStatus(api.StatusInShutdown)`. On Windows, `forcefulShutdown` (`helpers/runner_wrapper/wrapper_windows.go`) checks `w.Status()` to decide whether to send one or two `SIGINT`s, but that check-then-act sequence is not atomic with the final status write, so two concurrent invocations can each observe a non-`InShutdown` state and each send two `SIGINT`s, exceeding the documented "at most 2" budget before the wrapped process ever transitions status.

### Finding Description
- `InitiateForcefulShutdown` (`helpers/runner_wrapper/wrapper.go:239-258`) takes an `RLock` only to read `w.process`, releases it, then calls `w.forcefulShutdown(p)` with no lock held for the duration, and finally calls `w.setStatus(api.StatusInShutdown)` after `forcefulShutdown` returns.
- On Windows, `forcefulShutdown` (`helpers/runner_wrapper/wrapper_windows.go:15-48`) sends a first `SIGINT`, then checks `gracefulShutdownAlreadyStarted := w.Status() == api.StatusInShutdown`. If false, it sleeps 10ms and sends a second `SIGINT`.
- The invariant the code relies on ("send at most 2 SIGINTs total across all shutdown paths, because a 3rd SIGINT causes Windows to kill the process instantly without cleanup") depends on the state transition to `StatusInShutdown` happening *before* any other concurrent caller's status check. But the status is only set at the very end of `InitiateForcefulShutdown`, well after both `SIGINT`s have already been sent inside `forcefulShutdown`.
- If two goroutines/gRPC calls both enter `InitiateForcefulShutdown` while status is still `StatusRunning`, each independently executes the full `forcefulShutdown` body (1st SIGINT → 10ms sleep → status check → 2nd SIGINT) before either one calls `setStatus(StatusInShutdown)`. This yields 4 `SIGINT`s total, not ≤2.
- The gRPC endpoint `InitForcefulShutdown` (`helpers/runner_wrapper/api/server/server.go:95-111`) performs no authentication/session/token check and directly calls `s.wrapper.InitiateForcefulShutdown()`, and the listener defaults to unauthenticated `tcp://localhost:7777` (`commands/wrapper.go:23,44-56`). gRPC serves each RPC on its own goroutine, so two near-simultaneous `InitForcefulShutdown` RPCs naturally produce the two racing goroutines described.
- No mutex/lock is held to make "check status, send signals, set status" atomic; the `sync.RWMutex` in `Wrapper` only guards individual field reads/writes, not the whole operation. There is also no existing test covering `InitiateForcefulShutdown` (confirmed — `wrapper_test.go` only tests `InitiateGracefulShutdown`, `Run`, `Status`, `FailureReason`), indicating this race path is untested.

### Impact Explanation
On Windows, a third `SIGINT` to the wrapped multi-runner process causes immediate termination without graceful cleanup (per the code's own comment), killing the whole wrapped `gitlab-runner` process and all in-flight jobs across all projects/runners it manages — a persistent, cross-tenant disruption triggered by a race that a single unprivileged caller with two near-simultaneous requests to the local gRPC endpoint can produce, without needing any credential.

### Likelihood Explanation
Preconditions: the wrapper's gRPC listener must be reachable (default `tcp://localhost:7777`, unauthenticated) and the caller must be able to fire two `InitForcefulShutdown` RPCs close enough together to land within the 10ms sleep window in `forcefulShutdown`. This is trivially reproducible from any process with network access to that port (e.g., two goroutines/two quick sequential dials), and is fully deterministic under `-race`/tight timing in a unit test using a fake process/commander, since the racing window is explicit (`time.Sleep(10 * time.Millisecond)`) and not protected by any mutex spanning the whole call.

### Recommendation
Make the "check-and-set" sequence atomic under a single critical section covering the whole `InitiateForcefulShutdown`/`forcefulShutdown` flow: acquire the wrapper's lock for the duration of the status check + signal-sending + status update (e.g., use a dedicated shutdown mutex or an atomic compare-and-swap `Status` transition from non-`InShutdown` to `InShutdown` *before* sending any signals), and have subsequent concurrent callers short-circuit (no-op or return the current status) once the CAS fails, so only one caller ever sends the SIGINT sequence.

### Proof of Concept
```go
// helpers/runner_wrapper/wrapper_windows_test.go
func TestForcefulShutdown_ConcurrentCallsExceedTwoSIGINTs(t *testing.T) {
    p := newMockProcess(t)
    var sigintCount atomic.Int32
    p.EXPECT().Signal(syscall.SIGINT).Return(nil).Run(func(mock.Arguments) {
        sigintCount.Add(1)
    })

    w := New(logrus.StandardLogger(), "", nil)
    w.process = p
    w.status = api.StatusRunning

    var wg sync.WaitGroup
    for i := 0; i < 2; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            _ = w.InitiateForcefulShutdown()
        }()
    }
    wg.Wait()

    assert.LessOrEqual(t, sigintCount.Load(), int32(2),
        "wrapper must never send more than 2 SIGINTs to avoid Windows' 3rd-signal instant kill")
}
```
Run with `go test -race`; the assertion fails (count == 4) demonstrating the violation of the ≤2-SIGINT invariant.
