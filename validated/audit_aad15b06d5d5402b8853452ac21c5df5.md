### Title
Stale confirmations from removed multisig members are still counted toward `num_confirmations`, allowing request execution below the intended signer threshold - (File: multisig2/src/lib.rs)

### Summary
`MultiSigContract::confirm` in `multisig2/src/lib.rs` authorizes execution of a pending request purely by comparing the *size* of the stored `confirmations` set to `num_confirmations`, without re-validating that every entry in that set still corresponds to a currently active `MultisigMember`. `delete_member` only purges confirmations for requests that were *created by* the removed member; it never scans other pending requests to strip confirmations the removed member had *cast* on requests created by someone else. This breaks the intended equality `confirmations.len() == count(live members who approved this request)` and lets a request execute with fewer live-member approvals than `num_confirmations`.

### Finding Description
The custody binding the multisig is supposed to enforce is: *a request executes only if at least `num_confirmations` of the contract's **current** members approved it* — i.e. `|{live members} ∩ {confirmers}| >= num_confirmations`.

In `multisig2/src/lib.rs`:
- `confirm()` (lines 292-315) checks only `confirmations.len() as u32 + 1 >= self.num_confirmations` — a raw cardinality check on the stored `HashSet<String>` of member identifiers, with no cross-check against `self.members`. [1](#0-0) 
- `delete_member()` (lines 356-379) removes outstanding *requests created by* the deleted member (`r.member == member`) and their confirmation sets, and clears `num_requests_pk` for that member — but it does **not** iterate over `self.confirmations` for requests created by *other* members to remove any confirmation the deleted member may have previously cast on those requests. [2](#0-1) 

Consequently, if member `M` confirms a request `R` created by a different member, and `M` is later removed from the multisig via a legitimate `DeleteMember` action (unrelated to `R`), `M`'s confirmation entry for `R` is never cleaned up. It remains in `confirmations[R]` and continues to count toward the `num_confirmations` threshold even though `M` is no longer a member. The `assert_valid_request`/`current_member` checks (lines 322-339, 406-423) gate *who may call* `confirm`/`delete_request` on the current member set, but they do not re-validate historically stored confirmations against the current member set. [3](#0-2) 

The legacy `multisig/src/lib.rs` contains the analogous pattern for its `DeleteKey` action, which likewise only removes requests/confirmations tied to requests *signed by* the deleted key, not confirmations that key placed on other members' requests. [4](#0-3) 

This is the same class of bug as the external report's core theme: a recorded authorization claim (`tokensOwed`/an ERC-6909 balance entitlement, or here a stored confirmation) is not invalidated/decremented when the underlying entitlement it represents (fee balance / collateral ownership, or here membership) is revoked, so later logic that trusts the stale record produces an outcome that violates the intended invariant (transfer amount exceeding real balance, or here a request executing with fewer than `num_confirmations` *live* signers).

### Impact Explanation
This directly maps to the Critical impact bucket "a multisig request executed below threshold": funds can be transferred, keys/members added, or arbitrary `FunctionCall`s executed by the multisig account with fewer than the intended number of currently-authorized approvers, because one or more of the counted approvals belongs to an account/key that has since been removed from `members`. Any of the multisig-controlled `NEAR`/state (including lockup contracts controlled via multisig, per the `Overview` diagram showing `Multisig -- "manages" --> Lockup`) is therefore at risk of an unauthorized move.

### Likelihood Explanation
This does not require any privileged access beyond being (or having been) a multisig member — a normal, expected occurrence in these contracts, since membership rotation (removing compromised or departing signers) is an explicitly supported and encouraged operation (`DeleteMember`/`DeleteKey`). Any request that remains pending (which is easy to arrange — requests have no expiry, only a 15-minute cooldown before they *can* be deleted, and nothing forces deletion) while membership changes will carry forward stale confirmations. This is a realistic operational sequence, not a contrived edge case, and requires no code besides the already-existing `AddMember`/`DeleteMember`/`confirm` flows.

### Recommendation
- When executing `DeleteMember` (or `DeleteKey` in v1), iterate over **all** entries in `self.confirmations` (not just requests created by the removed member) and remove the removed member's identifier from every confirmation set.
- Alternatively/additionally, when counting confirmations in `confirm()`, filter `confirmations` to only those entries whose corresponding member is still present in `self.members` before comparing against `num_confirmations`, e.g. `confirmations.iter().filter(|m| self.members.contains(m)).count() + 1 >= self.num_confirmations`.
- Consider adding an expiry to pending requests so long-lived stale confirmations cannot accumulate across membership changes.

### Proof of Concept
Using the existing test harness in `multisig2/src/lib.rs` (`members()`, `context_with_key`, etc.):

```rust
#[test]
fn test_stale_confirmation_counts_after_member_removal() {
    // members(): alice(account), bob(account), key1, key2 -> 4 members, threshold 3
    let amount = 1_000;
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    let mut c = MultiSigContract::new(members(), 3);

    // 1. bob creates a malicious transfer request (not yet confirmed).
    testing_env!(context_with_account(bob(), amount));
    let steal_request = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let request_id = c.add_request(steal_request);

    // 2. key1 (a legitimate member at this time) confirms it.
    testing_env!(context_with_key(
        PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
        amount
    ));
    c.confirm(request_id); // confirmations = {key1}

    // 3. Separately, key1 is removed from the multisig via a normal DeleteMember flow
    //    (unrelated governance action, e.g. key1 was compromised).
    let key1_member = MultisigMember::AccessKey {
        public_key: PublicKey::from("Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap()),
    };
    let del_request = MultiSigRequest {
        receiver_id: alice(), // current_account_id in this harness
        actions: vec![MultiSigRequestAction::DeleteMember { member: key1_member }],
    };
    testing_env!(context_with_account(bob(), amount));
    let del_id = c.add_request(del_request);
    // confirm with the remaining members to remove key1 (threshold 3, using bob + key2 + alice, etc.)
    // ... (drive confirmations to execute DeleteMember)

    // 4. key1's stale confirmation on `request_id` is still present in c.confirmations,
    //    despite key1 no longer being in c.members. Only 2 *live* members (bob, key2)
    //    now need to confirm to reach the nominal count of 3 and trigger execution,
    //    effectively lowering the real threshold from 3-of-remaining-members to 2.
    testing_env!(context_with_account(bob(), amount));
    c.confirm(request_id); // count = 2 (bob) + stale key1 = 2, not yet 3
    // key2 confirms -> count reaches 3 (bob, key2, and stale key1), request executes
    // even though only 2 CURRENT members (bob, key2) actually approved it.
}
```

Because `delete_member` never scans `request_id`'s confirmation set for `key1`'s entry, the stale confirmation persists and is counted, so the malicious transfer executes with only 2 live approvals against a configured 3-of-N threshold — a concrete violation of the multisig's confirmation-threshold guarantee.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
