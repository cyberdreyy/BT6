### Title
CORS wildcard origin matching lacks subdomain boundary check, allowing non-subdomain lookalike origins to pass `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

### Summary
`httpServer.isAllowedOrigin` implements wildcard host matching (`*.domain.com`) using a raw `strings.HasSuffix` check without requiring a `.` boundary before the matched suffix. This lets an attacker-controlled origin such as `https://evilremix.com` or `https://attacker-remix.com` (which is NOT a subdomain of `remix.com`) be treated as allowed when the operator configures `CORSAllowedOrigins: ["https://*.remix.com"]`, causing `handleRequest` to reflect `Access-Control-Allow-Origin` for an unrelated domain.

### Finding Description
In `core/services/gateway/network/httpserver.go`, `isAllowedOrigin` (lines 142-178) strips the `*.` prefix from a wildcard allowed-origin entry and then checks:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [1](#0-0) 

This performs a pure string-suffix comparison with no requirement that the character preceding the matched suffix in `originHost` be a `.` (i.e., an actual label/domain boundary). Consequently any origin host that merely ends with the literal characters of the allowed base domain — even without being a true subdomain — passes the check. For example, with configured `CORSAllowedOrigins: ["https://*.remix.com"]`, an attacker serving a malicious page from `https://evilremix.com` or `https://notarealremix.com` sends a cross-origin fetch with `Origin: https://evilremix.com`. `splitURL` parses `originHost = "evilremix.com"`, and `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, so `handleRequest` (lines 180-194) sets `Access-Control-Allow-Origin: https://evilremix.com` and the standard CORS headers, incorrectly granting the attacker's page cross-origin read access via `fetch()` (with credentials, if the response also sets `Access-Control-Allow-Credentials`, or simply reading JSON responses that may contain session/job data returned by the gateway `ProcessRequest` handler). [2](#0-1) 

No existing validation compensates for this: `splitURL` only normalizes scheme/host/port and does not enforce domain-label boundaries, and none of the existing tests (`TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`) cover a lookalike domain without a dot separator — they only test legitimate subdomains and mismatched scheme/port cases. [3](#0-2) 

### Impact Explanation
This is a cross-origin isolation bypass (CORS allowlist bypass). An attacker who controls a domain that happens to end with the same characters as the configured base domain (e.g. registering `evilremix.com` when the operator intends to allow only `*.remix.com`) can have their page granted read access to gateway HTTP responses that would otherwise be restricted to legitimate subdomains, potentially exposing job/session data returned in gateway responses to an unauthorized cross-origin actor. This matches the "unauthorized data disclosure via CORS/allowlist misconfiguration bypass" impact class rather than remote key extraction, since only response bodies reachable via the gateway's own request/response flow are exposed, and no server-side secret material is inherently placed in these responses by this code path.

### Likelihood Explanation
Exploitation requires: (1) the gateway operator enables CORS with at least one wildcard entry (`CORSEnabled: true`, `CORSAllowedOrigins` containing a `*.domain` entry) — a supported and documented configuration in `core/scripts/gateway/sample_config.toml`; and (2) the attacker registers or controls any domain whose name happens to end with the same suffix string as the allowed base domain (no subdomain relationship required, and no authentication needed to send the CORS preflight/request). This is a plausible-but-config-dependent scenario: the bug is triggered purely by domain-name collision, not by any special credential, so likelihood is moderate — it depends on wildcard CORS being configured, which is an intended feature of this file.

### Recommendation
Enforce a label boundary when matching wildcard origins: after stripping `*.`, verify that `originHost` either equals `allowedHost` or ends with `"." + allowedHost`, e.g.:
```go
if strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost {
    return true
}
```

### Proof of Concept
Add a table-driven unit test for `isAllowedOrigin` (via the existing `startNewServer`/`sendRequest` harness) with:
- `CORSAllowedOrigins = []string{"https://*.remix.com"}`
- Send request with `Origin: https://evilremix.com` (no dot before "remix.com")
- Assert `resp.Header.Get("Access-Control-Allow-Origin")` is currently `"https://evilremix.com"` (demonstrating the bypass) and should be empty after the fix.
- Repeat with `Origin: https://legit.remix.com` to confirm legitimate subdomains still pass after the fix.

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
```
