### Title
Owner-supplied `whitelist_account_id` in `lockup-factory` lets the lockup owner forge a fake "whitelisted" staking pool and permanently divert unvested/terminated tokens away from the NEAR Foundation - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` lets the *caller* (the future lockup owner) override the trusted, foundation‑controlled `staking_pool_whitelist_account_id` with an arbitrary `whitelist_account_id` parameter, which is baked unchecked into the deployed lockup contract's state. [1](#0-0)  The lockup contract's `select_staking_pool` then treats a `true` answer from *that* whitelist contract as sufficient proof that a given `staking_pool_account_id` is a safe custodian of delegated funds. [2](#0-1) [3](#0-2)  Because the owner can point `whitelist_account_id` at a contract they themselves control (which always returns `is_whitelisted == true`), the "trusted whitelist" binding — *whitelist contract used == whitelist contract the Foundation vetted* — is broken. The owner can then "select" a fully attacker‑controlled fake staking pool and route the lockup's real NEAR balance to it via `deposit_to_staking_pool`/`deposit_and_stake`, which is a real `Promise` transfer of the account's liquid NEAR out of the lockup contract. [4](#0-3) 

### Finding Description
1. `LockupFactory::create` accepts an optional `whitelist_account_id: Option<ValidAccountId>` from the caller (who becomes the lockup owner) with no restriction on which account it may be, and no requirement to match the factory's own vetted `self.whitelist_account_id` — even when a `vesting_schedule` is supplied (i.e., when the Foundation has a real financial interest in the account via early-termination clawback): [5](#0-4) 
This value is serialized straight into `LockupArgs.staking_pool_whitelist_account_id` and used to initialize the deployed lockup contract. [6](#0-5) 

2. Inside the lockup contract, the *only* gate for accepting a `staking_pool_account_id` is a cross-contract call to whatever `staking_pool_whitelist_account_id` was configured at init time: [2](#0-1) 
The callback blindly trusts the boolean result: [3](#0-2) 
There is no on-chain verification that `staking_pool_whitelist_account_id` is itself the Foundation's whitelist (or an account added to the Foundation's `factory_whitelist`) — see the *real* whitelist's authorization model, which only lets the Foundation or its approved factories add pools: [7](#0-6) . The lockup contract has no equivalent check against `whitelist/src/lib.rs`; it accepts any account ID supplied at `new()` as "the" whitelist authority.

3. Once `select_staking_pool` succeeds (trivially, since the attacker's own fake whitelist contract always answers `true`), the owner calls `deposit_to_staking_pool`/`deposit_and_stake`, which performs a real `Promise` transfer of NEAR from the lockup account to the attacker-chosen `staking_pool_account_id`: [4](#0-3) 
Because this "staking pool" is a contract the owner fully controls, it need not behave like a real staking pool at all.

4. This breaks custody accounting specifically for the Foundation's termination/clawback path. When the Foundation later calls `terminate_vesting`, it computes `deficit = unvested_amount - liquid_account_balance`, and because the owner has already drained the liquid balance into the fake pool, `deficit > 0`, so the flow proceeds through `termination_prepare_to_withdraw`: [8](#0-7) 
This step asks the (attacker-controlled) "staking pool" `get_account_staked_balance`, and trusts whatever value it returns via `#[callback]` to drive `unstake`, again against the same attacker-controlled contract: [9](#0-8) 
and then `get_account_unstaked_balance` / `withdraw`, again against the attacker-controlled contract: [10](#0-9) 
Since the attacker controls this "pool" contract, it can simply never return the real NEAR (e.g., have `withdraw` return success without transferring funds, or report a staked/unstaked balance and let the promise fail/succeed as desired), while the lockup's own accounting (`termination_withdrawn_tokens`, `deposit_amount`) is only updated by trusting `is_promise_success()` and the attacker-controlled return values — the "recorded claims" never actually corresponded to NEAR the Foundation can recover.

The equality that should hold — `NEAR actually recoverable by the Foundation from the selected "staking pool" == unvested_amount recorded in the lockup contract` — is broken the moment the owner is allowed to nominate their own whitelist authority for their own lockup.

### Impact Explanation
This falls under **Critical**: "locked or unvested tokens released early" / "NEAR moved by a party not entitled to it." The lockup owner (an unprivileged party relative to the Foundation) can, prior to any termination event, siphon the lockup's real NEAR balance into a contract they control under the guise of "staking pool delegation," self-certified as safe via a whitelist contract they also control (permitted directly by `lockup-factory`'s `create` API). When the Foundation later attempts `terminate_vesting`/`termination_prepare_to_withdraw`/`termination_withdraw` to recover unvested tokens, it depends entirely on responses from that same attacker-controlled contract, giving the owner full ability to prevent recovery of the Foundation's unvested share — effectively releasing/keeping tokens that were supposed to be clawed back.

### Likelihood Explanation
Any account can call `LockupFactory::create` and attach the minimum deposit; supplying a custom `whitelist_account_id` requires no special privilege and is explicitly supported by the API (also exercised in the existing test `test_create_lockup_with_custom_whitelist_success`). [11](#0-10)  No foundation, multisig, or validator collusion is needed — only that the lockup be created with a `vesting_schedule` (so the Foundation has a stake to lose) and the owner deploy one extra contract acting as the fake whitelist + fake staking pool.

### Recommendation
- In `lockup-factory/src/lib.rs::create`, disallow `whitelist_account_id` overrides entirely, or restrict it to the factory's own vetted `whitelist_account_id` (or a Foundation-approved list) whenever a `vesting_schedule` is provided, since that is exactly the scenario where the Foundation has a recoverable interest.
- Alternatively/additionally, have the lockup contract itself validate at `new()` that `staking_pool_whitelist_account_id` is a subset of / equals a Foundation-controlled whitelist root (e.g., checked against `foundation_account_id`), rather than accepting any caller-supplied account ID as an authoritative whitelist source.
- Add a foundation-side invariant/verification step in `terminate_vesting`/`termination_prepare_to_withdraw` that cross-checks the configured `staking_pool_whitelist_account_id` against the canonical Foundation whitelist before trusting balances reported by the "selected" staking pool.

### Proof of Concept
1. Attacker deploys `FakeWhitelist` contract exposing `is_whitelisted(staking_pool_account_id) -> bool { true }` and `FakePool` contract exposing the staking-pool interface (`deposit`, `deposit_and_stake`, `get_account_staked_balance`, `get_account_unstaked_balance`, `unstake`, `withdraw`) but never actually transferring NEAR back out.
2. Attacker calls `lockup-factory.create(owner_account_id=attacker, ..., vesting_schedule=Some(...), whitelist_account_id=Some(FakeWhitelist))` with the minimum attached deposit, per `lockup-factory/src/lib.rs::create`. [12](#0-11) 
3. Once the lockup is deployed with `staking_pool_whitelist_account_id = FakeWhitelist`, attacker (as owner) calls `select_staking_pool(FakePool)`; `FakeWhitelist.is_whitelisted` returns `true`, so `on_whitelist_is_whitelisted` accepts it. [2](#0-1) [3](#0-2) 
4. Attacker calls `deposit_and_stake(full_balance)`, transferring the lockup's real NEAR (including the still-unvested portion) to `FakePool`. [4](#0-3) 
5. Foundation later calls `terminate_vesting`, sees `deficit > 0`, and calls `termination_prepare_to_withdraw` repeatedly; each step queries and acts on data from `FakePool`, which the attacker crafts to either fail, report zero, or otherwise avoid transferring real NEAR back. [13](#0-12) [14](#0-13) 
6. The Foundation is unable to recover the unvested NEAR it was owed; the owner has effectively released/retained the locked tokens early.

    /// FOUNDATION'S METHOD
    ///
    /// Requires 175 TGas (7 * BASE_GAS)
    ///
    /// When the vesting is terminated and there are deficit of the tokens on the account, the
    /// deficit amount of tokens has to be unstaked and withdrawn from the staking pool.
    /// Should be invoked twice:
    /// 1. First, to unstake everything from the staking pool;
    /// 2. Second, after 4 epochs (48 hours) to prepare to withdraw.
    pub fn termination_prepare_to_withdraw(&mut self) -> Promise {
        self.assert_called_by_foundation();
        self.assert_staking_pool_is_idle();

        let status = self.get_termination_status();

        match status {
            None => {
                env::panic(b"There is no termination in progress");
            }
            Some(TerminationStatus::UnstakingInProgress)
            | Some(TerminationStatus::WithdrawingFromStakingPoolInProgress)
            | Some(TerminationStatus::WithdrawingFromAccountInProgress) => {
                env::panic(b"Another transaction is already in progress.");
            }
            Some(TerminationStatus::ReadyToWithdraw) => {
                env::panic(b"The account is ready to withdraw unvested balance.")
            }
            Some(TerminationStatus::VestingTerminatedWithDeficit) => {
                // Need to unstake
                self.set_termination_status(TerminationStatus::UnstakingInProgress);
                self.set_staking_pool_status(TransactionStatus::Busy);
                env::log(b"Termination Step: Going to unstake everything from the staking pool");

                ext_staking_pool::get_account_staked_balance(
                    env::current_account_id(),
                    &self
                        .staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id,
                    NO_DEPOSIT,
                    gas::staking_pool::GET_ACCOUNT_STAKED_BALANCE,
                )
                .then(
                    ext_self_foundation::on_get_account_staked_balance_to_unstake(
                        &env::current_account_id(),
                        NO_DEPOSIT,
                        gas::foundation_callbacks::ON_GET_ACCOUNT_STAKED_BALANCE_TO_UNSTAKE,
                    ),
                )
            }
            Some(TerminationStatus::EverythingUnstaked) => {
                // Need to withdraw everything
                self.set_termination_status(
                    TerminationStatus::WithdrawingFromStakingPoolInProgress,
                );
                self.set_staking_pool_status(TransactionStatus::Busy);
                env::log(b"Termination Step: Going to withdraw everything from the staking pool");

                ext_staking_pool::get_account_unstaked_balance(
                    env::current_account_id(),
                    &self
                        .staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id,

                        NO_DEPOSIT,
                        gas::foundation_callbacks::ON_GET_ACCOUNT_UNSTAKED_BALANCE_TO_WITHDRAW,

                )

    /// Called after the given amount is unstaked from the staking pool contract due to vesting
    /// termination.
    pub fn on_staking_pool_unstake_for_termination(&mut self, amount: WrappedBalance) -> bool {
        assert_self();

        let unstake_succeeded = is_promise_success();
        self.set_staking_pool_status(TransactionStatus::Idle);

        if unstake_succeeded {
            self.set_termination_status(TerminationStatus::EverythingUnstaked);
            env::log(
                format!(
                    "Termination Step: Unstaking of {} at @{} succeeded",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        } else {
            self.set_termination_status(TerminationStatus::VestingTerminatedWithDeficit);
            env::log(
                format!(
                    "Termination Step: Unstaking {} at @{} has failed",
                    amount.0,
                    self.staking_information
                        .as_ref()
                        .unwrap()
                        .staking_pool_account_id
                )
                .as_bytes(),
            );
        }
        unstake_succeeded
    }
