### Title
Loss-adjusted withdraw receipts escape the `stopEpochWithDuration` haircut because `lossRecoveryPriceByEpoch` is keyed by the post-bump `epochNumber`, while claims look it up under the pre-bump request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The kernel analog is a shared field published and consumed under different "versions": `notify_page` is written into `context` mid-operation, so a concurrent teardown frees a half-initialized pointer. The vault equivalent is `epochNumber` acting as the shared key between write and read of a loss haircut. `IdleCreditVault.deposit()` increments `epochNumber` when invoked during `stopEpoch` (`isEpochRunning()` still true) [1](#0-0) , and `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` [2](#0-1) . Receipts created during the buffer record `lastWithdrawRequest[_user] = currentEpoch` (pre-bump N) [3](#0-2) , but claims read `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [4](#0-3) . Because `deposit` (which pulls borrower repayments and bumps `epochNumber`) precedes `collectWithdrawFunds` in the stop flow, the price lands under N+1 and is never found.

### Finding Description

In `stopEpochWithDuration(_lossAmount)` the CDO first pulls borrower funds via `IdleCreditVault.deposit`, which executes `epochNumber += 1` while `isEpochRunning()` is still true [5](#0-4) . It then calls `collectWithdrawFunds(pendingToFund)` where `pendingToFund < pendingBasis`; this clears `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber]` — now N+1 [6](#0-5) .

A user's claim calls `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` (still N) and finds `lossRecoveryPriceByEpoch[N] == 0`, returning 0 [7](#0-6) . Execution falls into `_claimFundedWithdrawRequest`, where the maturity gate `epochNumber <= lastWithdrawRequest[_user]` is now N+1 <= N = false, so it pays the **full un-haircut basis** `withdrawsRequests[_user]` at par via `_transferFundedClaim` [8](#0-7) . The same wrong key also disables the guard in `requestWithdraw` (lines 263-271) that is supposed to force claiming a loss-adjusted receipt before opening a new request [9](#0-8) .

### Impact Explanation

Broken invariant: loss waterfall / fair burn. Pending receipts absorb their pro-rata share of `pendingLoss = _lossAmount * pendingBasis / totalBasis` only through `lossRecoveryPriceByEpoch` [10](#0-9) . With the haircut stored under the wrong epoch key, each early claimant receives `claimBasis` instead of `claimBasis * lossRecoveryPrice / 1e18` from a strategy that only collected `pendingToFund`. The first claimants drain the funded balance at par; the excess is stolen from later claimants and from the recovery/funded reserve, and subsequent claims revert on insufficient balance — quantified loss equals `pendingBasis - pendingToFund` (the whole pending share of the realized loss), which can reach the full loss amount when the pending bucket dominates TVL.

### Likelihood Explanation

Requires a `stopEpochWithDuration` loss with nonzero `pendingWithdraws` and `defaultRecoveryInitialized` — an unprivileged tranche holder simply calls `claimWithdrawRequest` after the lossy stop; no privileged misbehavior needed. One caveat I could not fully verify within the available context: the exact ordering inside `IdleCDOEpochVariant.stopEpochWithDuration`/`_afterStopEpoch` between the bumping `deposit` call and `collectWithdrawFunds`. The code comments strongly imply deposit-then-collect ("deposit done on stopEpoch … we reset the counter", `_prefundedEpochToProcess` treating `epochNumber` as already bumped when not defaulted) [11](#0-10) [12](#0-11) ; if `collectWithdrawFunds` were invoked before the bumping deposit, the keys would match and the issue would not materialize. The PoC below determines this definitively.

### Recommendation

Key the haircut by the epoch in which the receipts were requested, not the post-bump counter: in `collectWithdrawFunds`, store `lossRecoveryPriceByEpoch[epochNumber - (isEpochRunning-was-true ? 1 : 0)]`, or pass the target epoch from the CDO, or write the price before any `deposit` that increments `epochNumber`. Symmetrically, harden `_claimLossAdjustedWithdrawRequest`/the `requestWithdraw` guard to also check `lossRecoveryPriceByEpoch[epochNumber]` for receipts whose `lastWithdrawRequest` was recorded pre-stop, and add a regression test asserting the stored key equals the request epoch.

```solidity
// Fork test on contracts/strategies/idle/IdleCreditVault.sol + IdleCDOEpochVariant
function testLossReceiptEscapesHaircut() external {
    uint256 amount = 10_000 * ONE_SCALE;
    idleCDO.depositAA(amount);                       // attacker LP
    _transferBurnedTrancheTokens(address(this), true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, apr, _expectedFundsEndEpoch()); // epochNumber = 1, buffer

    // request withdraw during buffer: lastWithdrawRequest[user] = 1
    cdoEpoch.requestWithdraw(trancheBal, address(AAtranche));
    _startEpochAndCheckPrices(1);

    // borrower repays only partially -> stopEpochWithDuration(_lossAmount)
    // flow: strategy.deposit(repaid) bumps epochNumber to 2,
    // then collectWithdrawFunds(pendingToFund < pendingBasis) stores
    // lossRecoveryPriceByEpoch[2] instead of [1]
    uint256 pendingBasis = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 loss = pendingBasis / 2;                 // 50% loss on pending bucket
    deal(defaultUnderlying, borrower, _expectedFundsEndEpochLossy());
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(duration, loss);  // or stopEpoch(duration, loss) variant

    // haircut is keyed under epoch 2; user's receipt points at epoch 1
    assertEq(strategy.lossRecoveryPriceByEpoch(1), 0);
    assertGt(strategy.lossRecoveryPriceByEpoch(2), 0);

    // claim pays FULL basis at par instead of 50% haircut
    uint256 balPre = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    assertEq(underlying.balanceOf(address(this)) - balPre, pendingBasis); // should be pendingBasis/2
}
```

If the assertion `lossRecoveryPriceByEpoch(2) > 0` holds while `lossRecoveryPriceByEpoch(1) == 0`, the claim pays the full basis, confirming the theft/insolvency.

```text
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
