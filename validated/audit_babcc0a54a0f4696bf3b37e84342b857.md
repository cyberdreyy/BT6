### Title
JWT replay-cache check-then-act race in HTTP Trigger `Authorize` allows one-time JWT tokens to be reused - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
The ZeroLend report describes a bug where a distribution function performs an accounting operation (crediting a gauge) without atomically resetting the `claimable` state that is supposed to prevent double-crediting, letting an attacker repeat the operation before the state is corrected. The Chainlink Gateway's HTTP-trigger JWT anti-replay mechanism has an analogous non-atomic check-then-act flaw: the "is this JWT already used" check and the "mark this JWT as used" update are two separate, unsynchronized calls with authorization work happening in between, so a JWT that is meant to authorize exactly one workflow trigger can be used more than once by an unprivileged external caller.

### Finding Description
`WorkflowMetadataHandler.Authorize` is the entry point that authenticates inbound, unprivileged HTTP trigger requests using a JWT: [1](#0-0) 

The flow is:
1. `claims, signer, err := utils.VerifyRequestJWT(token, *req)` — verifies the signature only.
2. `h.jwtCache.isReplay(claims.ID)` — checks (read) whether this JWT ID (`jti`) has been seen before.
3. Workflow/key lookup logic executes (`h.authorizedKeys[workflowID]`, signer membership check) — unrelated work performed with no lock held across the whole sequence.
4. `h.jwtCache.recordUsage(claims.ID)` — only now is the JWT ID marked as used.

The `jwtReplayCache` struct backing this stores state under its own mutex: [2](#0-1) 

Because `isReplay` and `recordUsage` are invoked as two independent operations rather than a single atomic "check-and-set", concurrent HTTP trigger requests submitted with the *same* signed JWT can both pass step 2 before either reaches step 4. This mirrors the ZeroLend root cause exactly: the code path that is supposed to consume/gate a one-time credential does not atomically pair the check with the state update, so the guard can be bypassed by racing requests from a single unprivileged actor.

### Impact Explanation
An external, unauthenticated-beyond-JWT caller (any client that can reach the gateway's HTTP trigger endpoint, per the process flow documented for this handler: "Authentication: Verifies JWT token (ECDSA signature) and checks authorized keys") can trigger the same workflow execution more than once using a single JWT that was only meant to authorize a single trigger. This is a concrete authentication/one-time-token bypass reachable from an unprivileged client, potentially causing duplicate/unauthorized job (workflow) runs, resource exhaustion of the DON, or bypass of intended request quotas tied to JWT uniqueness — directly analogous to "unauthorized job run" and "allowlist/quota bypass" categories.

### Likelihood Explanation
Exploitation only requires an attacker (or any legitimate caller wanting to bypass the one-shot guarantee) to send the identical HTTP trigger request/JWT concurrently (e.g., two near-simultaneous HTTP POSTs). No privileged access, node compromise, or special timing beyond ordinary network race conditions is needed, making this practically achievable by an unprivileged client.

### Recommendation
Make the check-and-record operation atomic under a single critical section: acquire the cache's write lock once, check for existence of `claims.ID`, and if absent, insert it immediately (single `if _, exists := cache[jti]; exists { return replayErr }; cache[jti] = now`) before releasing the lock and only afterward doing the (non-mutating) workflow/key authorization checks. Alternatively, use a `sync.Map`'s `LoadOrStore` (or equivalent) to guarantee the read-and-mark step is a single atomic operation, closing the race window entirely.

### Proof of Concept
Not independently reproduced against a running gateway (no runtime access), but the race is demonstrable conceptually from the code path itself:
1. Attacker obtains one valid signed JWT for a workflow HTTP trigger.
2. Attacker fires two (or more) HTTP trigger requests carrying the same JWT to the gateway at effectively the same time.
3. Both requests execute `VerifyRequestJWT` successfully, then both call `h.jwtCache.isReplay(claims.ID)` before either has called `h.jwtCache.recordUsage(claims.ID)` (steps 2–4 in `Authorize` above are not guarded by a shared lock spanning the whole check-then-act sequence).
4. Both requests pass authorization and both trigger the workflow, defeating the intended "used once" JWT replay protection. [1](#0-0)

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
