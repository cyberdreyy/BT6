I have enough evidence to identify a valid analog now. Let me confirm the mechanics with one final targeted look at how this asymmetry can be reached by a single miner without needing a majority of signers.### Title
`SortitionsView::validate_tenure_change_payload` (v1) checks only `GloballyAccepted` state, missing a self-signed `LocallyAccepted` block in the same tenure — a single miner can get a signer to double-sign two conflicting tenure-start blocks - (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
The v1 tenure-change duplicate-block guard in `SortitionsView::validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(...)` [1](#0-0)  to decide whether the signer has already signed a block in the current tenure before accepting a *second* tenure-start (`BlockFound`) proposal for the same tenure. This mirrors exactly the "consistency check bypassed under a specific condition" pattern from the external report: the check only fires against one particular sub-state (`GloballyAccepted`) instead of against the full "already signed" predicate (`LocallyAccepted` OR `GloballyAccepted`), so a block that this very signer already self-signed (`mark_locally_accepted`) but that has not yet reached the network-wide 70% threshold is invisible to the guard.

The v2 path already fixed this by switching to `get_last_signed_block`, which returns rows in state `GloballyAccepted` OR `LocallyAccepted` [2](#0-1) , and there is an explicit regression test proving the old behavior was wrong for v2 [3](#0-2) . The v1 code path, however, still uses the narrower `get_last_globally_accepted_block` [4](#0-3)  and has no analogous regression test.

### Finding Description
`validate_tenure_change_payload` in `chainstate/v1.rs` is the only place (proposal-arrival time only, per the docs: "the `DuplicateBlockFound` check ... lives in `check_proposal` and runs only at proposal arrival, never again") that enforces "don't sign a second, competing tenure-start block for a tenure we already signed one for":

```
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)?;
if let Some(last_in_current_tenure) = last_in_current_tenure {
    return Err(RejectReason::DuplicateBlockFound);
}
``` [1](#0-0) 

`get_last_globally_accepted_block` only matches rows with `state = GloballyAccepted` [4](#0-3) . A block this signer has already signed itself (`mark_locally_accepted`, which sets `signed_self`) but which has not yet crossed the 70% global-signature threshold sits in state `LocallyAccepted` [5](#0-4) , and is therefore *not* returned. So the equality this check is supposed to enforce — "signed a tenure-start block for this tenure" — is broken into "signed AND globally confirmed," which a single miner (with no other signer's key or majority) can exploit simply by re-proposing a second, different tenure-start block for the same tenure before the first one's signatures aggregate to 70%.

By contrast, the v2 implementation was patched to use `get_last_signed_block`, which explicitly covers both `GloballyAccepted` and `LocallyAccepted` [6](#0-5) , [2](#0-1) , with a dedicated regression test noting: "previously, the check used `get_last_globally_accepted_block`, which would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change" [7](#0-6) . The v1 code was left unfixed and lacks any comparable test, per the docs anchor explicitly documenting the asymmetry: "v2 counts locally or globally accepted blocks (`get_last_signed_block`); v1 counts only globally accepted ones (`get_last_globally_accepted_block`)" [8](#0-7) .

Because this proposal-time `DuplicateBlockFound` check never runs again (it is proposal-arrival only), the only remaining backstop is the pre-commit-time "own tenure" conflict guard, `get_signed_conflicts` + node's `get_tenure_tip` [9](#0-8) . That guard only blocks signing if the *node's* canonical tip in the tenure is already at or above the proposed height. If the first (already self-signed but not-yet-globally-accepted) block has not yet been pushed to the node — which is the normal state right after a signer locally signs but before 70% is reached — the node's tenure tip is still below the second proposal's height, so the pre-commit-time guard does not block it either. The v1 signer can then pre-commit to, and ultimately sign, a *second, conflicting* tenure-start block in the same tenure.

### Impact Explanation
This breaks the "one-per-tenure/no equivocation" equality the `DuplicateBlockFound` guard exists to enforce for v1 signers: a single signer instance can end up producing signatures over two different, conflicting tenure-start blocks for the very same tenure (its own equivocation), which is exactly the "signer signing a conflicting block" class the rules call Critical. Since a v1-protocol signer is a valid deployed configuration (v1 remains the fallback before global-state activation, per `determine_active_signer_protocol_version`/`uses_global_state()` gating in `stacks-signer/src/v0/signer.rs`), this is reachable in production without needing any other signer's key, a majority, or the auth token — only a miner (one slot) re-proposing a competing tenure-start block quickly, before the first tenure-start block's signature reaches 70% weight.

### Likelihood Explanation
Triggering the narrow window (self-signed `LocallyAccepted`, not yet 70% `GloballyAccepted`) is entirely plausible in normal network conditions: it is the exact gap between an individual signer's local signature and the collective threshold being reached, which can take multiple gossip round-trips. A miner controlling the block-proposal path can deliberately race a second tenure-start proposal into that window.

### Recommendation
Change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` to use `signer_db.get_last_signed_block(&block.header.consensus_hash)` (the same helper already used by v2), instead of `get_last_globally_accepted_block`, so the duplicate check covers any block this signer has already self-signed (`LocallyAccepted`) as well as globally-accepted ones. Add a v1 regression test mirroring `check_tenure_change_rejects_when_locally_accepted_block_exists` in `stacks-signer/src/chainstate/tests/v2.rs` to lock in the fix.

### Proof of Concept
1. Miner proposes tenure-start block `A` (tenure `T`, height `h`). Signer validates it, pre-commits, and reaches its own signature threshold locally — `A` transitions to `LocallyAccepted` via `mark_locally_accepted` (per `stacks-signer/src/signerdb.rs:280-289`), but the network-wide 70% signature aggregation has not completed yet (e.g., other signers are slow/partitioned), so `A` never reaches `GloballyAccepted`, and the node has not yet been handed the block, so its tenure tip for `T` is still below `h`.
2. Before `A` is globally accepted, the miner proposes a second tenure-start block `B` for the same tenure `T` (different transactions/coinbase), with a valid tenure-change payload referencing the same `prev_tenure_consensus_hash`.
3. `SortitionsView::check_proposal` → `validate_tenure_change_payload` (v1) calls `get_last_globally_accepted_block(T)`, which returns `None` because `A` is only `LocallyAccepted`, not `GloballyAccepted` (`stacks-signer/src/chainstate/v1.rs:505-518`). No `DuplicateBlockFound` rejection is issued.
4. `B` proceeds to validation, pre-commit, and — because the node's tenure tip for `T` is still below `A`'s height (the node never received `A`) — the pre-commit-time "own-tenure" conflict guard in `handle_block_pre_commit` also does not veto it (`stacks-signer/src/v0/signer.rs:1432-1457`).
5. The signer ends up signing `B` as well, having already self-signed `A` in the same tenure — two conflicting signatures produced by the same signer for the same tenure, driven entirely by the miner's re-proposal timing.
