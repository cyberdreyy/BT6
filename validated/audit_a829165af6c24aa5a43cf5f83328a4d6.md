## Title
Stale confirmations from removed multisig members allow request execution below the configured confirmation threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

## Summary
When a multisig member is removed via `DeleteMember` (v2) or `DeleteKey` (v1), the contract only purges *requests originated by* that member, but never scans `self.confirmations` to strip that member's confirmations from *other, still-pending requests* they had merely confirmed. Those stale confirmations continue to count toward `num_confirmations`, so a request can later be executed with fewer live, authorized confirmers than the configured threshold.

## Finding Description
`delete_member` in `multisig2` filters `self.requests` for entries whose *original signer* (`r.member`) equals the member being removed, and only removes confirmations for those requests: [1](#0-0) 

If a different member created a request and the soon-to-be-removed member merely added a confirmation to it (without being the originator), that confirmation entry is never touched by `delete_member`. It remains in `self.confirmations` for that `request_id`.

`confirm()` then counts confirmations purely by size of the set, without validating that every confirmer is still a current member: [2](#0-1) 

So after removal, a subsequent live member's confirmation can push `confirmations.len() + 1 >= self.num_confirmations` to true using the stale, no-longer-authorized confirmation, and `execute_request` fires.

The same class of bug exists in the legacy `multisig` (v1) contract's `DeleteKey` handling, which likewise only removes confirmations for requests whose `signer_pk == pk`, not confirmations that `pk` added to other requests: [3](#0-2) 
and its `confirm()` similarly just compares set size to `num_confirmations` with no live-membership re-validation of already-recorded confirmations: [4](#0-3) 

The binding that should hold is: `confirmations counted == confirmations from members who are members at execution time`. This is violated — `confirmations counted > live confirming members` is achievable.

## Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An attacker/compromised member's stale confirmation persists as valid authorization weight even after being removed from the multisig, letting the remaining members execute a sensitive request (e.g. `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, `DeployContract`) with fewer genuinely-authorized signers than `num_confirmations` requires. This can enable unauthorized fund transfers or privilege escalation on the multisig account.

## Likelihood Explanation
This requires only ordinary multisig operations, no special privilege beyond being (or having been) a legitimate member — exactly the kind of insider/compromised-key scenario multisig contracts are meant to defend against. It does not require any deployment misconfiguration, foundation action, or protocol-level flaw; it's reachable purely through the documented `add_request`/`confirm`/`DeleteMember` (or `DeleteKey`) flow.

## Recommendation
When removing a member (`DeleteMember`/`DeleteKey`), iterate all pending requests in `self.requests` and strip the removed member's entry from `self.confirmations` for every request (not just requests they originated). Alternatively, re-validate at `confirm()` time (and, ideally, before actually deriving `PromiseOrValue` execution) that every entry in the confirmations set still corresponds to a current member, discarding stale ones so the true live count is used for the threshold comparison.

## Proof of Concept
Multisig contract initialized with members `{A, B, C, D}`, `num_confirmations = 3`:
1. `A` calls `add_request_and_confirm(R1)` (e.g. a `Transfer`). `confirmations[R1] = {A}`.
2. `D` calls `confirm(R1)`. `confirmations[R1] = {A, D}` (2/3, not yet executed).
3. Members `A, B, C` execute a separate self-request `DeleteMember{ member: D }` (reaching threshold 3 among themselves) to remove `D` — perhaps because `D`'s key was compromised. `delete_member` only removes requests where `r.member == D` (i.e., requests `D` created); `R1` was created by `A`, so it is untouched, and `D`'s confirmation on `R1` is **not** removed.
4. `B` calls `confirm(R1)`. `confirmations[R1] = {A, D, B}`, `len() == 3 >= num_confirmations`, so `execute_request(R1)` fires and the `Transfer` executes — despite only 2 genuinely live members (`A`, `B`) having actually authorized it, one short of the required 3.

        self.assert_valid_request(request_id);

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
