### Title
Zip extraction places symlinks with attacker-controlled, unvalidated targets - ([File: helpers/archives/zip_extract.go])

### Summary
`extractZipSymlinkEntry` reads the symlink target directly from the zip entry content and passes it unmodified to `os.Symlink(string(data), file.Name)`, with no check that the target is relative or contained within the extraction root. Since cache archives (and other zip-based transfers) are built and consumed by job-controlled tooling and extracted via `ExtractZipArchive`/`ExtractZipFile`, a job can craft a zip whose symlink entry points to an absolute path or a `../`-escaping path.

### Finding Description
`extractZipFile` dispatches entries with `os.ModeSymlink` to `extractZipSymlinkEntry`: [1](#0-0) 

`extractZipSymlinkEntry` reads the entry's file content as the link target and creates the symlink with no validation: [2](#0-1) 

Compare this to `helpers/archives/path_check_helper.go`, which only checks whether the entry *name* is inside `.git` — it never validates symlink *targets* or file names for `..`/absolute-path escape: [3](#0-2) 

`ExtractZipArchive` iterates all entries, running `errorIfGitDirectory` and `extractZipFile`, with no target-containment check anywhere in the loop: [4](#0-3) 

By contrast, the tar/zstd extractor used for artifacts does validate destination paths against a chroot directory (though only for entry `Name`, not explicitly for symlink `Linkname` targets which are written unresolved via `os.Symlink(hdr.Linkname, path)`): [5](#0-4) [6](#0-5) 

For the zip path specifically (used by cache extraction, `commands/helpers/cache_extractor.go`, via `archive.NewExtractor`/`ExtractZipFile`), an attacker who controls the archive contents (e.g., by crafting a cache archive uploaded from their own job, or any zip consumed via `ExtractZipFile`) can create a symlink entry named e.g. `link` whose file content is `/etc/passwd` or `../../other-job-workspace/secrets.env`. `os.Symlink` places this symlink at `file.Name` within the extraction root pointing to that external/traversal target — this is a "dangling"/planted symlink creation, not itself a write.

### Impact Explanation
Creating the symlink alone does not write to the external path — it only plants a symlink. The described "cross-project or host file read/write" impact requires a *subsequent* step (the victim's own build script or another extraction/upload step) to write through that symlink, e.g. `echo secret > link`. This is symlink-planting, and Runner's known risk model already tolerates that build steps run arbitrary attacker-supplied shell/scripts within the executor sandbox — the actual write occurs because the job's own script writes to a path, not because Runner itself performed a write outside the root. The genuinely Runner-owned bug here is narrower: Runner will silently place a symlink whose target resolves outside the job/cache directory, without warning or rejecting it, which is a real gap relative to the invariant "file operations must stay within intended build/cache/artifact roots" for the *symlink creation* itself. Concrete impact is limited to: (a) subsequent operations by the *same* job that dereference the planted symlink (self-inflicted, since the same job authored the archive) can write/read outside its own directory, and (b) if a shared cache/artifact key can be poisoned and later restored into a *different* job's workspace (e.g., a shared/group-level cache key reused across projects, or an artifact passed to a downstream job in a different context), the symlink is planted in that victim's workspace and a later step in the *victim's* own pipeline that writes into the same-named path could write outside its intended directory. That second scenario requires cache/artifact key collision across trust boundaries, which is a precondition outside this specific code's control.

### Likelihood Explanation
Feasible and repeatable: constructing a zip with a `ModeSymlink` header whose data is an absolute path or `../` sequence is trivial with Go's `archive/zip` package or common zip tools, and `extractZipSymlinkEntry`/`ExtractZipArchive` apply no target validation. The main constraint on severity is that the practical blast radius depends on whether the resulting symlink is later dereferenced by a write, and whether the archive crosses a trust boundary (shared cache key across projects/branches) rather than being extracted only within the same job/pipeline that created it.

### Recommendation
In `extractZipSymlinkEntry`, validate the decoded target before calling `os.Symlink`: reject absolute targets and resolve `filepath.Join(filepath.Dir(file.Name), target)` against the extraction root, rejecting any target whose cleaned relative path (via `filepath.Rel`) escapes the root (starts with `..` or is absolute), consistent with the guard already used for tar/zstd extraction entry names in `tarzstd_extractor.go`. Apply the same relative/absolute containment check to `file.Name` itself in `extractZipFile`/`ExtractZipDirectoryEntry`/`extractZipFileEntry`, since none of those currently sanitize the entry name.

### Proof of Concept
```go
func TestExtractZipSymlinkEntry_RejectsEscapingTarget(t *testing.T) {
    dir := t.TempDir()
    zipPath := filepath.Join(dir, "evil.zip")

    f, _ := os.Create(zipPath)
    zw := zip.NewWriter(f)
    hdr := &zip.FileHeader{Name: "evil-link"}
    hdr.SetMode(os.ModeSymlink | 0777)
    w, _ := zw.CreateHeader(hdr)
    w.Write([]byte("/etc/passwd")) // or "../../outside/secret.env"
    zw.Close()
    f.Close()

    extractDir := t.TempDir()
    wd, _ := os.Getwd()
    os.Chdir(extractDir)
    defer os.Chdir(wd)

    err := archives.ExtractZipFile(zipPath)
    require.NoError(t, err) // current behavior: no error, symlink created

    target, err := os.Readlink(filepath.Join(extractDir, "evil-link"))
    require.NoError(t, err)
    // Assert fix: target must resolve within extractDir
    require.False(t, filepath.IsAbs(target), "symlink target must not be absolute")
    resolved := filepath.Join(extractDir, target)
    rel, err := filepath.Rel(extractDir, resolved)
    require.NoError(t, err)
    require.False(t, strings.HasPrefix(rel, ".."), "symlink target must stay within extraction root")
}
```
This currently fails the containment assertions (extraction succeeds and the symlink target is outside the root), demonstrating the missing check. It does not by itself prove file-content exfiltration/write, since that requires an additional dereferencing write step outside the scope of this file.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}
