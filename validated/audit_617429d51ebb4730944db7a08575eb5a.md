Looking at the bridge code carefully, I need to trace the replay-protection path for token transfers on the EVM side.

### Title
Cross-Chain Nonce Collision in `isTransferProcessed` Enables Permanent Fund Lock — (File: bridge/evm/contracts/SuiBridge.sol)

---

### Summary

The `isTransferProcessed` replay-protection mapping in `SuiBridge.sol` is keyed solely by `message.nonce` (uint64), omitting `message.chainID`. Because the bridge explicitly supports multiple source chains and each source chain maintains its own independent nonce counter starting at 0, transfers from two different source chains will inevitably share the same nonce values. The first transfer processed on the EVM side permanently marks that nonce as consumed, making the second transfer permanently unclaimable and locking the user's funds forever.

---

### Finding Description

**Broken invariant — nonce uniqueness across source chains**

`SuiBridge.sol` declares:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [1](#0-0) 

Both `transferBridgedTokensWithSignatures` (v1) and `transferBridgedTokensWithSignaturesV2` (v2) guard against replay with:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
// ... transfer tokens ...
isTransferProcessed[message.nonce] = true;
``` [2](#0-1) [3](#0-2) 

The key is `message.nonce` alone. `message.chainID` (the source chain) is present in the message struct but is **not** part of the key.

**Why the sequential-nonce guard does not help**

`MessageVerifier.verifyMessageAndSignatures` explicitly skips the sequential nonce check for `TOKEN_TRANSFER` messages:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
``` [4](#0-3) 

Token transfers therefore rely **entirely** on `isTransferProcessed[message.nonce]` for replay protection.

**Multiple source chains are a supported and tested configuration**

`BridgeConfig` stores a `mapping(uint8 chainId => bool isSupported) public supportedChains` and accepts an array of source chains at initialization. [5](#0-4) 

The `BridgeLimiterTest` explicitly deploys the bridge with **two** source chains (IDs 11 and 12):

```solidity
uint8[] memory supportedChains = new uint8[](2);
supportedChains[0] = 11;
supportedChains[1] = 12;
``` [6](#0-5) 

**Nonce collision is inevitable**

On the Sui Move side, each source chain's nonce counter is independent and starts at 0, incremented by `get_current_seq_num_and_increment`:

```move
fun get_current_seq_num_and_increment(bridge: &mut BridgeInner, msg_type: u8): u64 {
    if (!bridge.sequence_nums.contains(&msg_type)) {
        bridge.sequence_nums.insert(msg_type, 1);
        return 0
    };
    ...
}
``` [7](#0-6) 

Both chain A and chain B will produce transfers with nonces 0, 1, 2, … independently. The `BridgeMessageKey` on the Sui side correctly includes `source_chain`:

```move
public struct BridgeMessageKey has copy, drop, store {
    source_chain: u8,
    message_type: u8,
    bridge_seq_num: u64,
}
``` [8](#0-7) 

But the EVM side discards `source_chain` from the processed-nonce key, breaking the invariant.

---

### Impact Explanation

When two source chains are configured, the first transfer from chain A with nonce N sets `isTransferProcessed[N] = true`. Any subsequent transfer from chain B with nonce N is permanently rejected with `"SuiBridge: Message already processed"`. The user on chain B has already burned or locked their tokens on the source chain (via `send_token_internal` → `treasury.burn`), but can never claim the corresponding ERC-20 tokens on the EVM side. The funds are permanently locked with no recovery path. This matches the **permanent fund lock** impact class. [9](#0-8) 

---

### Likelihood Explanation

The bridge code and its tests explicitly support multiple source chains. Once two source chains are configured (a legitimate, non-malicious governance action), the collision is **structurally guaranteed** — both chains start at nonce 0 and increment monotonically. No adversarial action is required; the first ordinary user whose transfer from chain A is processed before chain B's transfer with the same nonce triggers the lock. The attacker model is an ordinary bridge user.

---

### Recommendation

Key `isTransferProcessed` by both source chain ID and nonce:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// After
mapping(uint8 chainID => mapping(uint64 nonce => bool isProcessed)) public isTransferProcessed;
```

Update all read/write sites in `SuiBridge.sol` and `SuiBridgeV2.sol`:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
// ...
isTransferProcessed[message.chainID][message.nonce] = true;
``` [10](#0-9) [11](#0-10) 

---

### Proof of Concept

1. Deploy `SuiBridge` with `BridgeConfig` listing two source chains: chain A (ID = 11) and chain B (ID = 12).
2. User on chain A calls `send_token` → assigned nonce 0 by `get_current_seq_num_and_increment`. Tokens burned on chain A.
3. User on chain B calls `send_token` → also assigned nonce 0 (independent counter). Tokens burned on chain B.
4. Bridge validators sign both messages. Both are valid committee-signed `TOKEN_TRANSFER` messages with `nonce = 0` but different `chainID` fields.
5. Chain A's message is submitted to `transferBridgedTokensWithSignatures` first → `isTransferProcessed[0] = true`. Chain A user receives ERC-20 tokens.
6. Chain B's message is submitted → `require(!isTransferProcessed[0])` reverts with `"SuiBridge: Message already processed"`.
7. Chain B user's tokens are permanently lost: burned on Sui, unclaimable on Ethereum.

fun get_current_seq_num_and_increment(bridge: &mut BridgeInner, msg_type: u8): u64 {
    if (!bridge.sequence_nums.contains(&msg_type)) {
        bridge.sequence_nums.insert(msg_type, 1);
        return 0
    };

    let entry = &mut bridge.sequence_nums[&msg_type];
    let seq_num = *entry;
    *entry = seq_num + 1;
    seq_num
}
