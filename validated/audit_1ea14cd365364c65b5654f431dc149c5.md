### Title
Stale cross-tenure conflicts bypass the node-liveness check in the pre-commit conflict guard, allowing a signer to double-sign siblings at the same height - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The pre-commit conflict guard in `handle_block_pre_commit` is the only mechanism that stops a signer from putting a second signature over a block that conflicts with one it already signed at the same or higher Stacks height in a different tenure (the chainstate re-check only verifies a tenure-change block against its *parent* tenure, never against sibling tenures). That guard is supposed to keep blocking a conflict "until staleness *or* node-derived death" clears it, but for conflicts in a tenure other than the one being evaluated, staleness alone clears it: the node-truth check (`conflict_still_blocks`) is never invoked once the conflict's `last_endorsed` timestamp is older than a purely local wall-clock cutoff. A miner-controlled delay between two competing tenure-change proposals is therefore sufficient to make an already-signed, still-canonical block invisible to the guard, and the signer signs the competing sibling unconditionally.

### Finding Description
`check_block_against_signer_db_state` (called from `handle_block_pre_commit` at the RECHECK step) only validates a tenure-change block against its **parent** tenure's last signed block [1](#0-0) . It never compares two *sibling* tenures against each other, so two different tenure-change blocks that both build on the same parent tenure at the same height pass this check independently. The only remaining defense against such cross-tenure double-signing is the conflict guard that runs afterward.

That guard first tries to find a conflict that is both **fresh** and **still live** (verified against the node via `conflict_still_blocks`): [2](#0-1) 

Because Rust's `&&` short-circuits, `conflict_still_blocks` — the only code path that asks the node whether the conflicting block is still real chain state — is **never called** once `conflict.last_endorsed <= freshness_cutoff`, i.e. once more than `tenure_last_block_proposal_timeout` seconds have elapsed since the signer signed (or observed group-signature on) the conflicting block. `freshness_cutoff` is a purely local wall-clock value: [3](#0-2) 

The fallback path that runs for stale/dead conflicts only re-derives node truth for conflicts in the **same tenure** as the block currently being evaluated: [4](#0-3) 

The `conflicts.iter().any(...)` filter at line 1432 checks `conflict.consensus_hash == block_info.block.header.consensus_hash`; a stale conflict recorded under a *different* tenure never matches this filter, so it receives no scrutiny at all. Execution simply falls through to the logging statement and then to `SIGN`: [5](#0-4) 

The design intent documented alongside `get_signed_conflicts`/`conflict_still_blocks` is explicit that "only staleness or node-derived death clears a conflict" [6](#0-5) , but the implementation clears cross-tenure conflicts on staleness **without ever asking for node-derived death**. This contradicts the guard's own stated invariant and breaks the "signer signs only one block per height" equality: `signed_self`/`signed_group` over block A is not re-verified against the still-canonical chain before the same signer signs sibling block B.

### Impact Explanation
This is a **Critical** finding under the rubric: it lets a single miner slot (no majority of signers, no key compromise, no auth token) cause an individual signer to sign a second, conflicting/non-canonical block at a height it already endorsed. If a large enough fraction of the signer set experiences the same staleness window in the same way (which is likely, since all signers use the same `tenure_last_block_proposal_timeout` config and observe roughly the same wall-clock elapsed time since the first block's signature), the second sibling can also cross the group signature threshold, producing two aggregately-signed, competing Nakamoto blocks at the same height in different tenures — an equivocation at the signer-set level rather than merely at the miner level.

### Likelihood Explanation
The trigger requires only:
1. Winning (or controlling) two competing tenure-change proposals that build off the same parent tenure at the same height (achievable normally via burnchain forks or the existing `first_proposal_burn_block_timing` reorg-timing allowance that `check_parent_tenure_choice` already accepts as legitimate).
2. Waiting past `tenure_last_block_proposal_timeout` (a signer-configured value, typically tens of seconds) between the first block being signed and the second block reaching the pre-commit threshold.

Both conditions are fully within a miner's control and require no coordination with signers, no stolen keys, and no majority — matching the "one-slot miner plus gossip" threat model.

### Recommendation
Do not gate the node-truth query (`conflict_still_blocks`) behind the freshness check for cross-tenure conflicts. At minimum, before signing, re-derive liveness for *every* remaining conflict (fresh or stale) that is not covered by a standing reorg permit, not just same-tenure ones — i.e. remove the tenure-scoped restriction at the `conflicts.iter().any(...)` check (line 1432) so any stale, non-permitted conflict (regardless of tenure) is also asked whether the node's chain still reaches it (or was globally accepted) before falling through to `SIGN`.

### Proof of Concept
1. Sortition winner M1 proposes tenure-change block A (tenure T1, height h, parent tenure P). Signers validate, pre-commit, and sign A; A becomes `GloballyAccepted` and is real, canonical chain state.
2. A different sortition winner M2 (or M1 again) proposes tenure-change block B (tenure T2 ≠ T1, height h, also declaring parent tenure P — permitted by the existing reorg-timing window). `check_tenure_change_confirms_parent` for B only checks P's last block, so it passes independently of A.
3. M2 waits until `now - signed_self(A) > tenure_last_block_proposal_timeout` before letting B accumulate pre-commits (e.g. by slow-rolling propagation or simply waiting).
4. B crosses the pre-commit threshold. `get_signed_conflicts(h, B_hash)` returns A, but `A.last_endorsed <= freshness_cutoff`, so the `.find()` at `stacks-signer/src/v0/signer.rs:1403-1411` skips calling `conflict_still_blocks` for A entirely. The same-tenure fallback at line 1432 does not match (`A.consensus_hash == T1 != T2 == B.consensus_hash`), so A receives no live/dead determination at all.
5. The signer logs "none of those conflicts still blocks it. Signing the replacement." and signs B, even though A remains fully live and canonical on the node the entire time — producing two independently signed, conflicting blocks at height h.
