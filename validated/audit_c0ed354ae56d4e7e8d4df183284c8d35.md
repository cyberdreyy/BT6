### Title
Post-default instant withdraw receipts are recorded under the finalized default epoch and repaid at the haircut price, double-charging users and draining `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The zstd-jni UAF is a "closed-but-still-referenced shared resource" bug: a dictionary is freed while a stream still points at it. The vault analog is `epochNumber`-keyed recovery accounting. After `finalizeDefaultRecovery`, `epochNumber` stays equal to `defaultRecoveryEpoch` and the epoch's claim basis is logically "closed." `requestWithdraw` correctly diverts post-default requests into `postDefaultRequests`, but `requestInstantWithdraw` has no such branch — it keeps writing into `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`, so a brand-new, fully-funded receipt references the already-finalized ("freed") default-epoch bucket and is later claimed at `defaultRecoveryPrice` instead of par.

### Finding Description
- `finalizeDefaultRecovery` sets `defaultRecoveryFinalized = true`, `defaultRecoveryEpoch = epochNumber`, `defaultRecoveryPrice`, and `defaultInstantWithdrawsFinalized = pendingInstantWithdraws != 0` (`IdleCreditVault.sol:661-710`).
- `requestWithdraw` explicitly handles the post-default state, burning/minting at the already-haircut amount and storing the receipt in `postDefaultRequests` (`IdleCreditVault.sol:247-257`).
- `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) has **no** `defaultRecoveryFinalized` check: it mints a par receipt and increments `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` — where `epochNumber == defaultRecoveryEpoch`, i.e., the closed epoch.
- On `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`), when `defaultInstantWithdrawsFinalized` is true, `_claimDefaultedInstantWithdrawRequest` clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — which now includes the *new* post-default request — and pays only `claimBasis * defaultRecoveryPrice / 1e18` from `defaultRecoveryReserve` (`IdleCreditVault.sol:842-856`).
- Result: the post-default requester loses `(1 - recoveryPrice)` of a fully-funded claim, and the payout consumes `defaultRecoveryReserve` that is earmarked for defaulted-epoch claimants, directly reducing other users' recovery.

### Impact Explanation
Theft of unclaimed yield / insolvency of the recovery reserve. If `defaultRecoveryPrice` is e.g. 0.4e18, a post-default instant withdrawer who was funded 100% by the CDO receives only 40% (a 60% loss on a claim that was never part of the default), while that 40% is subtracted from the reserve owed to genuine defaulted-epoch claimants — so either the new requester is underpaid or prior victims are left unpayable. Loss equals `claimBasis * (1 - defaultRecoveryPrice)` plus reserve misallocation of `claimBasis * defaultRecoveryPrice`.

### Likelihood Explanation
Requires a finalized default with `pendingInstantWithdraws != 0` at finalization (so `defaultInstantWithdrawsFinalized` is true) and an unprivileged user submitting an instant withdraw post-default. `requestInstantWithdraw` imposes no post-default gating, and the honest CDO/manager sequence around `stopEpoch`/`finalizeDefaultRecovery` is all that is needed to reach the state. Caveat: this analysis assumes the CDO's instant-withdraw path remains callable after `defaulted()` is set; if `IdleCDOEpochVariant` hard-reverts instant requests post-default, the unreachable path reduces this to defense-in-depth. That gating could not be fully verified within the search budget, but the asymmetric handling vs. `requestWithdraw` (which does have an explicit post-default branch) indicates instant receipts were an overlooked path rather than a deliberately blocked one.

### Recommendation
Mirror the `requestWithdraw` post-default handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized`, route the request into `postDefaultRequests`-style par accounting (or revert), so new receipts are never written into `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` after that epoch is closed.
