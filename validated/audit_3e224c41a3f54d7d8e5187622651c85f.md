### Title
Fee-on-transfer underlying breaks write-off fulfillment and underpays lenders - ([File: `contracts/IdleCreditVaultWriteOffEscrow.sol`](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` assumes the escrow receives exactly `_underlyings` from a fulfiller and then sends the full nominal amount as exit fee plus lender proceeds. With a fee-on-transfer underlying, the escrow receives less than `_underlyings`, so fulfillment either reverts or, if the shortfall is covered by a prior donation, completes while the lender and `feeReceiver` receive less than accounted. This maps directly to the reported two-transfer collateral flaw: an inbound transfer is recorded at face value and outbound transfers reuse that same nominal amount. The escrow takes its underlying token directly from the configured credit vault, without rejecting fee-on-transfer assets. [1](#0-0) [2](#0-1) 

### Finding Description
A lender calls `createWriteOffRequest`, which escrows tranche tokens and records `underlyingsRequested` in `userRequests` and `pendingUnderlyings`. [3](#0-2) 

Any wallet may then call `fullfillWriteOffRequest`. The function clears the request and pulls `_underlyings` from the fulfiller, but it never measures the escrow’s balance delta. It calculates the exit fee on the nominal `_underlyings`, transfers `_totFee` to `feeReceiver`, then transfers `_underlyings - _totFee` to the requester. [4](#0-3) 

For an underlying token charging an inbound fee `f`, `safeTransferFrom(msg.sender, address(this), _underlyings)` increases escrow balance by only approximately `_underlyings * (1 - f)`. The subsequent outbound transfers still require `_underlyings` in aggregate. The invariant “one fulfilled request pays the requested underlying amount, minus only the configured exit fee” is therefore broken. `nonReentrant` does not correct the balance/accounting mismatch, and no balance-delta check or supported-token validation exists. [5](#0-4) 

### Impact Explanation
Without pre-existing escrow balance, fulfillment reverts on the fee or lender transfer because the escrow lacks the nominal `_underlyings`, making the tranche write-off market unusable for that underlying.

An unprivileged fulfiller or direct token sender can first donate enough underlying to cover the inbound fee. The next fulfillment can then succeed atomically, but the fee-on-transfer mechanics cause the lender and `feeReceiver` to receive less than `_underlyings - _totFee` and `_totFee`, respectively. For example, with a 1% transfer fee and a 10,000-unit request, the escrow receives only 9,900 units. A donation of at least 100 units can complete the nominal 10,000-unit payout, while each outbound recipient can still lose the token’s outbound transfer fee. The request is nevertheless deleted and the fulfiller receives all `_tranches`, so the lender has permanently exchanged the receipt for less than the requested consideration. [6](#0-5) 

### Likelihood Explanation
Likelihood depends on deploying a credit vault whose `token` is fee-on-transfer or whose token later enables transfer fees. The escrow blindly adopts `IdleCDOEpochVariant.token()` as its underlying and places no compatibility restriction on it. [7](#0-6) 

Fulfillment is permissionless, and direct donations are possible because there is no balance reservation or donation-isolation logic in the escrow. A fulfiller does not need a privileged role; the documented interface explicitly allows any wallet to fulfill a request. [8](#0-7) 

### Recommendation
Either explicitly reject fee-on-transfer underlyings during vault/escrow deployment or make fulfillment balance-based:

1. Record `balanceBefore = underlyingToken.balanceOf(address(this))`.
2. Pull `_underlyings`.
3. Set `received = balanceAfter - balanceBefore`.
4. Require `received >= currentRequest.underlyings`.
5. Calculate the exit fee and lender payment from `received`, or require `received == _underlyings` if fee-taking assets are unsupported.
6. Ensure unsolicited escrow balances cannot subsidize fulfillment, such as by reserving/deducting known balances or reverting when `received != _underlyings`.

The same balance-delta pattern is already used elsewhere in the codebase when accounting for actual received value. [9](#0-8) 

### Proof of Concept
A reproducible Foundry test can use a fee-on-transfer ERC20 configured as the vault `token`:

```solidity
function testFeeOnTransferWriteOffUnderpaysLender() public {
    uint256 tranches = 10_000e18;
    uint256 requested = 10_000e6;

    vm.prank(lender);
    escrow.createWriteOffRequest(tranches, requested);

    address fulfiller = makeAddr("fulfiller");
    feeToken.mint(fulfiller, requested);

    // Without a donation, the nominal outbound payments exceed the amount
    // actually received after the inbound transfer fee.
    vm.startPrank(fulfiller);
    feeToken.approve(address(escrow), requested);
    vm.expectRevert();
    escrow.fullfillWriteOffRequest(lender, tranches, requested);
    vm.stopPrank();

    // A direct sender can cover the inbound fee shortfall.
    feeToken.mint(attacker, requested);
    vm.prank(attacker);
    feeToken.transfer(address(escrow), requested);

    uint256 lenderBefore = feeToken.balanceOf(lender);
    uint256 fulfillerTranchesBefore = tranche.balanceOf(fulfiller);

    vm.prank(fulfiller);
    escrow.fullfillWriteOffRequest(lender, tranches, requested);

    // The request is consumed and the fulfiller receives the tranches,
    // but outbound transfer fees leave the lender below the requested payout.
    assertEq(tranche.balanceOf(fulfiller) - fulfillerTranchesBefore, tranches);
    assertLt(
        feeToken.balanceOf(lender) - lenderBefore,
        requested - (requested * escrow.exitFee() / escrow.FULL_VALUE())
    );
}
```

The test should use a fee-on-transfer token implementation where both `transfer` and `transferFrom` deduct a fixed percentage from the delivered amount.

  /// @notice create a write-off request by depositing tranche tokens and setting the amount of underlyings requested
  /// @param amount of tranche tokens to deposit
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
```

  /// @notice fulfill the write-off request by buying the escrowed tranche tokens
  /// @param _user address of the user that made the write-off request
  /// @param _tranches amount of tranche tokens to transfer
  /// @param _underlyings amount of underlyings to transfer
  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```
