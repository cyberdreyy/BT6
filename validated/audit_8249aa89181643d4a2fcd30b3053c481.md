### Title
Post-default `requestInstantWithdraw` lacks the recovery-finalized guard, corrupting `defaultRecoveryReserve` accounting and permanently freezing or draining claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Electron advisory maps to the class "a seemingly benign handler performs a more dangerous action": a "reveal" action silently executed the file. The vault analog is `requestInstantWithdraw` in `IdleCreditVault`. `requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes post-default requests through `postDefaultRequests` and refuses to run while stale receipts exist. `requestInstantWithdraw` has no such branch: after default recovery is finalized it still mints a receipt, books it into `instantWithdrawsRequestsByEpoch[_user][epochNumber]` — where `epochNumber` still equals `defaultRecoveryEpoch` because no new epoch ever starts after default — and increments `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[defaultEpoch]`. A later `claimInstantWithdrawRequest` then either spends the isolated `defaultRecoveryReserve` or reverts in `_transferFundedClaim`, depending on `defaultInstantWithdrawsFinalized`.

### Finding Description
In `IdleCreditVault.sol:356-375`, `requestInstantWithdraw` performs `_ensureDefaultRecoveryInitialized()` but never checks `defaultRecoveryFinalized`:

```solidity
function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    _burn(msg.sender, _amount);
    _mint(_user, _amount);
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;              // == defaultRecoveryEpoch after finalization
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    pendingInstantWithdraws += _amount;
}
```

Compare `requestWithdraw` (`IdleCreditVault.sol:247-257`), which detects `defaultRecoveryFinalized` and books the receipt into `postDefaultRequests` instead.

Two broken paths result in `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`):

1. `defaultInstantWithdrawsFinalized == true` (there was an unfunded instant bucket at finalization): `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`) reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`, which now includes the attacker's brand-new post-default receipt, and pays `claimBasis * defaultRecoveryPrice` out of `defaultRecoveryReserve` via `_transferDefaultRecovery` (`IdleCreditVault.sol:912-917`). The reserve was sized at finalization exactly for the legitimate defaulted-epoch claimants (`finalizeDefaultRecovery`, `IdleCreditVault.sol:686-692`); the extra basis is paid at the expense of those claimants. It also decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and clamps `pendingInstantWithdraws` to 0, corrupting the finalized counters.

2. `defaultInstantWithdrawsFinalized == false` (instant bucket was fully funded at finalization): the defaulted-claim branch is skipped, so `_transferFundedClaim` (`IdleCreditVault.sol:897-907`) attempts to pay the new receipt at par. The request was never funded — post-default there is no epoch lifecycle that would call `collectInstantWithdrawFunds` — so once the non-reserve balance is exhausted the `balance - reserve < _amount` guard reverts. The user's tranche tokens were already burned at request time and the receipt can never be paid or unwound: permanent freeze.

The CDO keeps `allowInstantWithdraw` enabled after default in the funded-instant scenario (see `testStopEpochWithDefault` asserting `allowInstantWithdraw() == true` and `testFundedInstantWithdrawRemainsClaimableAfterStopEpochDefault` exercising post-default instant claims), so `IdleCDOEpochVariant.requestWithdraw` can still route into `requestInstantWithdraw` for an unprivileged tranche holder.

### Impact Explanation
- Path 1: direct theft from `defaultRecoveryReserve`. Each post-default instant receipt of size `X` withdraws `X * defaultRecoveryPrice` from a reserve earmarked for pre-default claimants. If `defaultRecoveryPrice` exceeds the post-default tranche price paid by the attacker (e.g. above-par recovery noted in the `finalizeDefaultRecovery` comment, or AA vs BB price asymmetry where the attacker burns the cheaper tranche), the theft is net-positive; even at par it front-runs and reduces what legitimate claimants can later withdraw, since the reserve is depleted first-come-first-served.
- Path 2: permanent freezing — the requester's tranche tokens are burned, the receipt is unfundable, and every claim reverts on the reserve guard.

Broken invariant: donation/reserve isolation of `defaultRecoveryReserve` and "one receipt one payout" — a receipt created after finalization consumes accounting slots (`instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, `instantWithdrawClaimsByEpoch[defaultEpoch]`) that the finalization logic assumed were immutable.

### Likelihood Explanation
Requires only an unprivileged tranche holder calling `cdoEpoch.requestWithdraw` while instant withdrawals are enabled after default finalization — a mode the protocol explicitly supports (funded instant claims remain claimable post-default). No privileged actor misbehavior, no oracle manipulation. The profitability of path 1 depends on the gap between `defaultRecoveryPrice` and the post-default tranche price; path 2 (permanent freeze) requires no price gap at all.

### Recommendation
Mirror the `requestWithdraw` post-default branch in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert outright or route the request through the `postDefaultRequests` flow so it is paid 1:1 from a properly accounted bucket rather than mutating `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]` and `pendingInstantWithdraws`. Additionally, in `claimInstantWithdrawRequest`, cap the defaulted-epoch claim at the claim basis that existed at finalization time.
