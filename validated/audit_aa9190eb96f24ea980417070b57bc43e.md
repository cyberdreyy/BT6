Confirmed: there is no `catch_unwind`/panic-recovery boundary anywhere in the real Bank transaction execution path (`runtime/src/bank.rs`, `runtime/src/transaction_execution.rs`, `program-runtime/src/invoke_context.rs`). The only panic-recovery wrapper (`std::panic::catch_unwind`) in the whole codebase around program execution lives in `program-test/src/lib.rs::invoke_builtin_function`, which is test-only tooling for `ProgramTest`, not the production validator path.

### Title
Unrecovered panic in builtin-program instruction processing crashes the validating node during block replay — ([File: program-runtime/src/invoke_context.rs])

### Summary
IoTeX's fix wraps `ValidateBlock`'s action-processing loop in a panic recovery so a malformed/adversarial transaction in a proposed block cannot crash the validating process; the working set is simply discarded and the block rejected. Agave's real transaction-execution path has no equivalent panic boundary: a panic raised while executing a builtin (native) program instruction propagates uncaught through the entire call stack used both for leader-side execution and for replay/validation of blocks received from other nodes, crashing the process instead of failing the transaction.

### Finding Description
Builtin programs (System, Vote, Stake, Address Lookup Table, BPF Loader management, Compute Budget, etc.) are invoked through `process_executable_chain` in `program-runtime/src/invoke_context.rs`, which looks up the builtin's registered Rust function and calls it directly via `vm.invoke_function(function)`: [1](#0-0) 
This call chain is reached from `InvokeContext::process_instruction` → `process_executable_chain`, with no `catch_unwind` anywhere in between: [2](#0-1) 

The builtin function bodies are generated by the `declare_process_instruction!` macro, which runs arbitrary program logic (`process_instruction_inner`) directly against caller-influenced accounts/instruction data with no panic guard: [3](#0-2) 

This is invoked, ultimately, from `Bank::load_and_execute_transactions` via the SVM's `TransactionBatchProcessor`, and from `execute_batch` — the function used both by `banking_stage::Consumer` (leader path) and by `blockstore_processor`'s `process_entries`/`process_single_slot` when replaying and validating blocks received from peers: [4](#0-3) [5](#0-4) 

By contrast, the only place in the codebase that wraps program execution in `std::panic::catch_unwind` is the mock builtin-invocation helper used exclusively by `ProgramTest` (a testing harness), which is never part of the production replay/validation path: [6](#0-5) 

Because a program's process-instruction function can contain `unwrap()`, direct slice indexing, integer arithmetic overflow (in debug builds), or `assert!`/`debug_assert!` on attacker-influenced account state or instruction data, any such panic anywhere in a builtin program's instruction processing during real block replay is unrecovered — it unwinds straight out of `process_executable_chain`, `process_instruction`, `load_and_execute_transactions`, `execute_batch`, `process_entries`, and up through `blockstore_processor::process_single_slot`, aborting the validator thread/process rather than being turned into an `InstructionError` for the offending transaction.

### Impact Explanation
If an unprivileged transaction sender can construct account state / instruction data that triggers a Rust panic inside a builtin program's native instruction handler (System, Vote, Stake, Address Lookup Table, Config, Compute Budget, or the BPF loader's own management-instruction dispatch), that single transaction — once included in *any* block, whether it is being replayed at startup, validated during normal replay of another leader's block, or processed at the leader's own banking stage — will crash every node's validating thread/process that executes it. This is a transaction-triggered cluster-wide halt/DoS: because the same deterministic transaction execution runs on every validator, one crafted transaction can simultaneously bring down every validator that processes the block, unlike a single-node crash.

### Likelihood Explanation
Likelihood depends on whether an exploitable, reachable panic condition currently exists in one of the builtin programs' instruction-processing code paths (e.g., an `unwrap()`/indexing/overflow bug reachable with attacker-controlled account data). I was not able to enumerate and audit every builtin program's instruction handler within the scope of this pass to confirm a live, concrete panic trigger; I can only confirm structurally that **no panic-recovery boundary exists** in the production execution path, so *if* such a bug exists (or is later introduced) in any builtin, it is immediately a cluster-halting vulnerability with no defense-in-depth, exactly the gap the IoTeX commit closed for its own block-validation path.

### Recommendation
Add a panic-recovery boundary around builtin-program instruction execution in the production path (analogous to the IoTeX fix and to the existing test-only `catch_unwind` in `program-test/src/lib.rs`), most naturally in `InvokeContext::process_executable_chain` / `process_instruction` in `program-runtime/src/invoke_context.rs`, converting a caught panic into `InstructionError::ProgramFailedToComplete` (or similar) so the transaction fails deterministically instead of crashing the process. Ensure the working set/accounts touched by the failed transaction are discarded exactly as on any other `InstructionError`, preserving commit/PutBlock-equivalent paths (`Bank::commit_transactions`) as still-fatal on divergence, matching the IoTeX design of "recover on validate, stay fatal on commit."

### Proof of Concept
Not constructed — no concrete panic-triggering bug inside a specific builtin program's instruction handler was identified/verified within this pass. Demonstrating exploitability would require auditing each builtin program (System, Vote, Stake, Address Lookup Table, Config, Compute Budget, BPF Loader management instructions) for an `unwrap()`/array-index/overflow/`assert!` that is reachable with attacker-controlled instruction data or account state, then crafting a single transaction invoking it, and confirming it panics rather than returning `InstructionError` when run through `Bank::load_and_execute_transactions`/`execute_batch`.
