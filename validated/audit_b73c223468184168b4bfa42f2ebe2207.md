### Title
Distinguishable "workflow not found" vs "auth failure" error messages enable workflowID/owner-name-tag enumeration - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
`resolveWorkflowID` and `authorizeRequest` both return `jsonrpc.ErrInvalidRequest` but with distinguishable `Message` text ("Workflow not found..." vs "Auth failure: signer '...' is not authorized for workflow '...'"). Because `resolveWorkflowID` runs and succeeds *before* `authorizeRequest` is ever invoked, reaching the "Auth failure" branch is itself proof that the guessed `workflowID` (or `workflowOwner`/`workflowName`/`workflowTag` triple) exists, letting an unauthenticated caller enumerate valid workflows and their existence/ownership without needing any real credentials for them.

### Finding Description
In `HandleUserTriggerRequest` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:88-102) the flow is: `resolveWorkflowID` → `authorizeRequest` → `checkRateLimit`. `resolveWorkflowID` (lines 335-359) looks up the workflow by ID or by owner/name/tag via `h.workflowMetadataHandler.GetWorkflowReference`/`GetWorkflowID`. If not found, it calls `handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "Workflow not found. ...", callback)` [1](#0-0) .

Only if the workflow is found does the code proceed to `authorizeRequest` (lines 361-369), which calls `WorkflowMetadataHandler.Authorize`. An attacker can trivially satisfy the "well-formed, self-signed JWT" requirement (`utils.VerifyRequestJWT` only validates that the token is well-formed and signed by the recovered signer — it does not require the signer to be pre-registered) with their own throwaway key. Since `resolveWorkflowID` already guaranteed the workflowID exists (it is present in `workflowIDToRef`, and `authorizedKeys` is populated in lock-step with `workflowIDToRef` in `syncMetadata`), the request will practically always hit the "signer not authorized" branch: `fmt.Errorf("signer '%s' is not authorized for workflow '%s'. ...", signer.Hex(), workflowID)` [2](#0-1) , which `handleUserError` reports back verbatim as `"Auth failure: "+err.Error()` with the same `jsonrpc.ErrInvalidRequest` code [3](#0-2) .

Both paths use the identical JSON-RPC error code (`jsonrpc.ErrInvalidRequest`), but the `Message` text is different and directly indicates whether the workflow exists ("Workflow not found" vs "Auth failure: signer ... is not authorized for workflow ..."). Crucially, `checkRateLimit` — the only rate-limiting step — runs *after* both `resolveWorkflowID` and `authorizeRequest` succeed [4](#0-3) , so failed lookups/auth attempts are not throttled by the per-workflow rate limiter, allowing high-volume automated probing.

### Impact Explanation
An attacker with no relationship to a workflow can determine (a) whether a specific `workflowID` exists, and (b) whether a specific `workflowOwner`/`workflowName`/`workflowTag` combination resolves to a real, DON-assigned workflow — without possessing any authorization for it. This maps to the "workflow existence and ownership enumeration enabling targeted unauthorized-trigger attempts" impact class described in the question: once a valid triple/ID is confirmed, the attacker can focus further effort (credential/key guessing, social engineering, monitoring) specifically on that real target rather than blindly guessing, and can build an inventory of live owner/name/tag combinations across the gateway.

### Likelihood Explanation
Feasibility is high for the mechanics (distinguishing the two messages requires only comparing response text, no special access), but exploitation value is bounded by keyspace size: `workflowID` is a 32-byte value (lines 35 `workflowIDLength = 66`), so blind brute force of IDs is infeasible; however, the owner/name/tag path is far more guessable — `workflowOwner` is a public 20-byte EVM address (often already known/public), and `workflowName`/`workflowTag` are human-chosen short strings (≤64/≤32 chars, lines 37 and 39), which are realistically dictionary-guessable. No pre-existing authorization or valid signature over the target workflow is required to obtain the "Auth failure" signal — only a self-signed JWT with an attacker-controlled key. There is no rate limiting applied before this oracle is reached.

### Recommendation
Return an identical, generic error message and code (e.g., "Workflow not found or not authorized") for both the "workflow not found" and "signer not authorized" cases in `resolveWorkflowID` and `authorizeRequest`, so the two conditions are indistinguishable to the caller. Additionally, apply a coarse, unauthenticated-request rate limit (e.g., keyed by request source) prior to `resolveWorkflowID`/`authorizeRequest` so that failed lookups/auth attempts cannot be used for fast automated enumeration.

### Proof of Concept
Go handler-level test plan (in `core/services/gateway/handlers/capabilities/v2`):
1. Set up a `httpTriggerHandler` with a `WorkflowMetadataHandler` pre-populated (via `syncMetadata`/test helpers) with one known workflow (`workflowID`, `workflowOwner`, `workflowName`, `workflowTag`, and one authorized signer key).
2. Case A ("not found"): call `HandleUserTriggerRequest` with a random/unregistered `workflowID` and a validly self-signed JWT (own throwaway key). Assert the callback receives `jsonrpc.ErrInvalidRequest` with message containing `"Workflow not found"`.
3. Case B ("found, unauthorized"): call `HandleUserTriggerRequest` with the real registered `workflowID` but the same throwaway (unauthorized) key/JWT. Assert the callback receives `jsonrpc.ErrInvalidRequest` with message containing `"Auth failure: signer ... is not authorized"`.
4. Assert that Case A and Case B messages differ, demonstrating that an attacker can distinguish "workflow does not exist" from "workflow exists, I'm unauthorized" using only the response `Message`, without ever passing authorization — confirming the enumeration oracle.
5. Repeat steps 2-3 using the owner/name/tag resolution path (`workflow.WorkflowOwner/WorkflowName/WorkflowTag` instead of `WorkflowID`) to show the oracle also confirms valid owner/name/tag triples.

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
