### Title
Bridge `OutgoingToken` secret disclosed to view-role users via `GET /v2/bridge_types/:BridgeName` - ([File: core/web/bridge_types_controller.go])

### Summary
The `BridgeTypesController.Show` route is registered without `auth.RequiresEditRole`, unlike the sibling `Create`/`Update`/`Destroy` routes, so any authenticated user regardless of role (including `UserRoleView`) can call `GET /v2/bridge_types/:BridgeName`. The `presenters.BridgeResource` returned by this endpoint unconditionally includes the bridge's `OutgoingToken` in plaintext.

### Finding Description
In `core/web/router.go` the bridge routes are registered as: [1](#0-0) 
Only `Create`, `Update`, and `Destroy` are wrapped in `auth.RequiresEditRole`; `Show` (`bt.Show`) is reachable by any authenticated session that passes the outer `authv2` group's `auth.Authenticate` middleware, which accepts `UserRoleView`, `UserRoleRun`, `UserRoleEdit`, and `UserRoleAdmin` alike (see `auth.RequiresEditRole` for contrast, which explicitly rejects `UserRoleView`/`UserRoleRun`): [2](#0-1) 

`BridgeTypesController.Show` fetches the bridge from the ORM and serializes it via `presenters.NewBridgeResource`, with no field-level redaction based on caller role: [3](#0-2) 

The presenter always populates `OutgoingToken` (no `omitempty`, no conditional gating), unlike `IncomingToken` which is `omitempty` and only ever set manually by the `Create` handler (from the one-time creation response), never from `FindBridge`: [4](#0-3) 

So a view-role user's `GET` request returns `OutgoingToken` in the JSON body, while the write operations that would otherwise require possessing this secret (Update/Destroy) are gated behind Edit role. This is confirmed as reachable (not blocked) by the existing RBAC route matrix test, which explicitly marks this route `viewOnlyAllowed: true`: [5](#0-4) 

### Impact Explanation
`OutgoingToken` is the credential the Chainlink node attaches to outbound requests it makes to the external bridge/adapter, used by the adapter to authenticate that a request truly originated from the node. Any authenticated view-role user (the lowest privilege API role) can retrieve this token for any configured bridge and could use it to forge requests to that external adapter as if they came from the node, or otherwise gain unauthorized access to a system the view-role user should not have credential access to. This matches a credential/secret-disclosure impact class — a privilege inconsistency where a read-only role obtains a secret gated for edit-role elsewhere in the same resource's API surface.

### Likelihood Explanation
Trivial and fully repeatable: any user provisioned with `UserRoleView` (the lowest role that can hold an API session/token) can issue a single authenticated `GET /v2/bridge_types/:BridgeName` for any known bridge name and receive `outgoingToken` in the response body. No additional bypass, timing, or race condition is required — the omission of `auth.RequiresEditRole` on the `Show` route is the sole precondition.

### Recommendation
Wrap the `Show` route with `auth.RequiresEditRole` (matching Create/Update/Destroy), or, if view-role access to bridge metadata must remain available, redact `OutgoingToken` from the presenter for non-edit/admin callers (e.g., pass caller role into `NewBridgeResource` and omit/blank the token unless the caller has edit-or-above privilege).

### Proof of Concept
1. In a `bridge_types_controller_test.go`-style test, start the app, create a bridge via `app.BridgeORM().CreateBridgeType` (recording its `OutgoingToken`).
2. Create an HTTP client authenticated as a `sessions.UserRoleView` user (`cltest.User{Role: sessions.UserRoleView}` + `app.NewHTTPClient(u)`, mirroring the pattern in `TestRBAC_Routemap_Edit`).
3. Issue `client.Get("/v2/bridge_types/" + bridgeName)`.
4. Assert `resp.StatusCode == http.StatusOK` (not 401/403).
5. Parse response JSON and assert `data.attributes.outgoingToken` equals the bridge's stored `OutgoingToken` value — demonstrating disclosure to a view-role, non-edit session.
6. Contrast with `client.Patch("/v2/bridge_types/"+bridgeName, ...)` from the same view-role client, expecting `403 Forbidden`, to show the read/write authorization inconsistency for the same secret.

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
