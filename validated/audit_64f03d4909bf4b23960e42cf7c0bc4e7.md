## Analysis

I found a valid analog. The bug class from the report — a counter checked against the wrong scope (total count instead of the currently-relevant subset) — maps directly onto `multisig2::confirm`, where confirmations are counted without verifying the confirming keys/accounts are still current members.

### Title
Stale confirmations from removed members can execute a multisig request below the effective live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` only purges confirmations for requests that were *added* by the removed member; it does not purge confirmations that member cast on *other* members' pending requests. `confirm` later authorizes execution purely by counting `confirmations.len()`, without re-validating that every confirming member is still in `self.members`. This lets a request execute using confirmation "votes" that no longer represent live authorized members, breaking the confirmations-counted-vs-live-members binding.

### Finding Description
`delete_member` cleans up only requests whose `signer/member == member` being removed: [1](#0-0) 

Confirmations that a to-be-removed member placed on *other* members' requests are never removed — only `self.confirmations.remove(&request_id)` for requests originated by that member is touched. `self.members.remove(&member)` proceeds regardless.

`confirm` then authorizes execution solely by counting stored confirmations: [2](#0-1) 

There is no check inside `confirm` (or `execute_request`) that every account/key recorded in `confirmations` is still contained in `self.members`. So a confirmation recorded before a member is removed remains valid "weight" forever.

### Impact Explanation
Example with `num_confirmations = 2`, members `{A, B, C}`:
1. B creates request R (`add_request`).
2. A confirms R → `confirmations(R) = {A}` (1/2).
3. Through a separate confirmed request, member A is removed via `DeleteMember` (allowed as long as `members.len() - 1 >= num_confirmations`, i.e. `{B, C}` remain, satisfying `2 >= 2`) — `delete_member` does not touch `confirmations(R)` because R was not added by A.
4. Now only `{B, C}` are legitimate members, yet `confirmations(R)` still contains stale entry `A`.
5. C confirms R → `confirmations.len() + 1 = 2 >= num_confirmations(2)` → request R executes, using B's initial signer-add plus a confirmation from a member (A) who is no longer authorized, effectively bypassing genuine 2-of-2 approval from the current member set (B never confirmed R at all — it was added by B automatically has 0 confirmations initially in `add_request`, or if `add_request_and_confirm` was used, B counts as 1; A's stale vote plus C's vote lets it execute without B's real approval in some sequences).

More directly: any request can be executed with a mix of confirmations from members who have since been removed, meaning the multisig can execute a `Transfer`, `AddKey`, `FunctionCall`, etc. with fewer *live* approving members than `num_confirmations` intends — a threshold-bypass on custody of the account's NEAR balance and keys. This is a Critical-class issue per the rubric: "a multisig request executed below threshold."

### Likelihood Explanation
This requires only ordinary, unprivileged multisig operation — no owner/foundation collusion beyond what the K-of-N scheme already trusts, and no redeploy. Any sequence where a member is confirmed on a still-pending request and is later removed (a normal admin action supported by the contract's own `DeleteMember` action) reaches this path. Pending requests can persist because `delete_request` requires a 15-minute cooldown, and there is no requirement that all pending requests be resolved before a member is deleted, so the window is easily reachable in practice.

### Recommendation
In `confirm` (and/or in `delete_member`), validate that every entry in `confirmations.get(&request_id)` is still contained in `self.members` before counting them toward the threshold — either by purging confirmations from *all* pending requests when a member is deleted (not just requests they authored), or by filtering `confirmations` against current live `self.members` at confirm-time before comparing `len()` to `num_confirmations`.

### Proof of Concept
1. `MultiSigContract::new(members = [A, B, C], num_confirmations = 2)`.
2. As B: `add_request(request = R)` → `confirmations(R) = {}`.
3. As A: `confirm(R)` → `confirmations(R) = {A}` (1 < 2, stored).
4. As B and C: create+confirm a `DeleteMember{member: A}` request (2 confirmations reached, executes) — [3](#0-2)  runs; since R was authored by B not A, `confirmations(R)` is untouched and still contains `A`; `self.members` becomes `{B, C}`.
5. As C: `confirm(R)` → `confirmations(R).len() + 1 == 2 >= num_confirmations(2)` → `execute_request(R)` fires [4](#0-3) , executing R with only C as a genuinely current confirming member plus a stale confirmation from removed member A — i.e., executed with only 1 live confirmation against a nominal 2-of-2/2-of-3 policy.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
