### Title
`replace`/`clean` lack any caller check, letting an unprivileged attacker race and overwrite an operator's migration - (File: `state-manipulation/src/lib.rs`)

### Summary
The `replace` and `clean` `#[no_mangle]` exports in `state-manipulation/src/lib.rs` write/remove arbitrary storage keys and values supplied in the call's JSON input with no predecessor, owner, or self-call check whatsoever. Any account that knows the target account currently has this contract deployed (e.g. during a legitimate migration performed by the account's operator) can call `replace` in the same block, and since both writes hit the same storage keys, whichever transaction is applied last determines final state, breaking the invariant that only the operator driving the migration controls the outcome.

### Finding Description
The binding that should hold is: `predecessor_account_id == current_account_id (or an explicitly authorised operator)` for every call to `replace`/`clean`. In the actual code:

```rust
#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    ...
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(&base64::decode(key).unwrap(), &base64::decode(value).unwrap());
    }
}
``` [1](#0-0) 

and the analogous `clean`: [2](#0-1) 

Neither function calls `env::predecessor_account_id()`, `assert_self()`, or any owner/whitelist check before performing raw `storage_write`/`storage_remove` on `ATOMIC_OP_REGISTER`/`EVICTED_REGISTER`. This means once this WASM is deployed on an account (its intended, documented use per `state-manipulation/README.md`, which instructs deploying it "into the account that already has another contract deployed to it" during a manual migration), the exported methods are fully public: any transaction sender — including an unprivileged attacker — can invoke `replace` with an arbitrary `entries` array of base64 key/value pairs, or `clean` with arbitrary `keys`, and it will succeed unconditionally.

Exploit flow: while the operator's transaction calling `replace` with the intended migrated state is included in a block, the attacker submits their own `replace` call (potentially with thousands of entries) targeting the same account in the same block. Because NEAR applies transactions to an account in receipt order within a block/shard, and both calls hit the same underlying trie keys with no versioning/nonce/guard on the "migration" concept, the last-applied write wins — which can be the attacker's, not the operator's. There is no `assert_self()`, `assert_owner`, or any of the other guard patterns (`assert_one_yocto`, `is_promise_success`, etc.) present anywhere in this file to prevent it.

### Impact Explanation
An attacker who wins the race can overwrite the account's state with arbitrary key/value pairs (e.g. staking-pool `total_staked_balance`, lockup `owner_account_id`, `vesting_information`, or multisig confirmation state) directly through raw storage writes, without going through any of the target contract's business logic or invariants. This is a direct path to theft of the account's funds or bypass of vesting/ownership invariants, matching the "Critical - direct manipulation of contract state, enabling theft of the account's funds" impact category. The blast radius is any account on which this migration tool is deployed during the (however brief) window it remains active before being redeployed with the intended target contract.

### Likelihood Explanation
The precondition is that the `state-manipulation` contract is currently deployed on the target account — this happens only during an operator-initiated migration, so the attack window is limited to that period, but during that window no privilege beyond "send a transaction calling an open method" is required, which is squarely within the defined unprivileged-attacker capability set. The attacker's cost is a normal transaction fee/gas; the entries array can carry base64 payloads sized to overwrite exactly the storage rows they intend to corrupt (e.g. the fixed `STATE` key layout of the real target contract), so this is a targeted, repeatable, low-cost attack for anyone monitoring the mempool/block for a `replace` call to the target account.

### Recommendation
Add a caller check to both `replace` and `clean` before performing any storage mutation — e.g. assert `near_sys::predecessor_account_id()` equals `near_sys::current_account_id()` (self-call only, since only the account itself, via a full-access key, should invoke migration tooling on itself), or otherwise require a signature/key check that only the legitimate operator satisfies. Alternatively, treat this migration tool as fully untrusted-input-safe only when deployed transiently by a key holder who signs the call directly with a full-access key already scoped to that account (which is the near-cli usage pattern in the README) and document/enforce that no other transaction is allowed to reach `replace`/`clean` while this code is deployed, e.g., by fencing calls behind an `assert_self()`-equivalent check as shown.

### Proof of Concept
```rust
// cargo test in state-manipulation, extending the existing `workspaces_test`
#[tokio::test]
async fn attacker_races_operator_replace() -> anyhow::Result<()> {
    let wasm = fs::read("res/state_manipulation.wasm").await?;
    let worker = workspaces::sandbox().await?;
    let contract = worker.dev_deploy(&wasm).await?;

    // operator's legitimate migration entries
    let operator_entries = vec![(base64::encode(b"STATE"), base64::encode(b"operator_value"))];
    // attacker's malicious entries targeting the same key
    let attacker_entries = vec![(base64::encode(b"STATE"), base64::encode(b"attacker_value"))];

    // Attacker account has no relationship to contract owner/operator
    let attacker = worker.dev_create_account().await?;

    // Fire both calls "in the same block" (submit concurrently)
    let op_call = contract.call(&worker, "replace")
        .args_json(&serde_json::json!({ "entries": &operator_entries }))?
        .max_gas().transact();
    let atk_call = attacker.call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": &attacker_entries }))?
        .max_gas().transact();

    let _ = tokio::join!(op_call, atk_call);

    let state_items = contract.view_state(&worker, None).await?;
    // Binding under test: final "STATE" value == operator_value (expected)
    // vs what actually lands, demonstrating attacker can determine final state
    assert_eq!(state_items.get(&b"STATE".to_vec()).unwrap(), &b"attacker_value".to_vec());
    Ok(())
}
```
This demonstrates that `replace` performs `storage_write` for any caller with no predecessor check [3](#0-2) , so an unprivileged attacker's call can determine final on-chain state instead of the operator's.
