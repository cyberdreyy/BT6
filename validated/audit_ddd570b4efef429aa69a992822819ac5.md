### Title
Public WebSocket proxy server has no HTTP header read timeout, enabling Slowloris DoS - ([File: crates/infra/websocket-proxy/src/server.rs])

### Summary
`Server::listen` in `crates/infra/websocket-proxy/src/server.rs` binds a `tokio::net::TcpListener` and serves it directly with `axum::serve(...)`, without any `tower_http::timeout::TimeoutLayer`, hyper header-read timeout, or connection-count limit applied at the accept/parse layer. This mirrors the exact CVE-2025-53634 bug class in chall-manager's HTTP gateway: an HTTP(S) server that processes headers with no timeout, letting a remote attacker hold many connections open via a Slowloris-style slow-header attack and exhaust server resources.

### Finding Description
The `listen` method builds the axum `Router`, binds the listener, and calls `axum::serve(listener, ...).with_graceful_shutdown(...)`: [1](#0-0) 

No timeout middleware (e.g., `tower_http::timeout::TimeoutLayer`) or `hyper` header timeout is configured anywhere in this crate — the only timeout-related matches in the crate are unrelated business logic in `registry.rs`/`subscriber.rs`, not server transport timeouts.

Crucially, the per-IP/global rate limiting via `RateLimit::try_acquire` is only invoked inside `websocket_handler`, i.e. *after* axum/hyper has already fully parsed the incoming HTTP request headers and matched a route: [2](#0-1) 

This means the TCP-accept-to-headers-parsed phase — which is exactly the phase Slowloris attacks target by sending headers one byte at a time — is completely unguarded. The rate limiter provides no protection here because it never executes until headers are already complete.

The public/unauthenticated route (`/ws`) is enabled whenever `authentication` is `None` or `public_access_enabled` is `true`: [3](#0-2) 

so any anonymous RPC/WebSocket client can open a raw TCP connection to this endpoint and trickle header bytes indefinitely, tying up a hyper connection/task and a file descriptor per connection with no server-side timeout to reclaim it. This is the same root cause described in GHSA-ggmv-j932-q89q: "processes headers, but with no timeout set," enabling a Slowloris DoS without requiring authentication.

### Impact Explanation
An unauthenticated, unauthorized remote client can open a large number of slow/incomplete HTTP connections to the public WebSocket proxy, exhausting the process's file descriptors, connection slots, or worker capacity. Because the affected component serves live flashblock/pending-state data to external subscribers, sustained exploitation causes denial of service to legitimate WebSocket subscribers, satisfying the "node/service halt" bar for impact (CWE-770, CWE class matches the referenced advisory). No funds/state integrity is impacted; the impact is availability-only, matching the original advisory's own CVSS vector (`C:N/I:N/A:H`).

### Likelihood Explanation
Likelihood is high: the endpoint is intentionally public/anonymous-facing per the code (`public_access_enabled` / unauthenticated route), requires no authentication, no special privileges, and Slowloris tooling is trivial and widely available. The only mitigating control (per-IP/global rate limiter) executes too late in the request lifecycle to prevent this specific attack.

### Recommendation
Wrap the axum service with an explicit read/header timeout (e.g., `tower_http::timeout::TimeoutLayer` applied at the connection/service level, or use `hyper`'s `Builder::http1_header_read_timeout` if migrating off `axum::serve`'s default hyper server), and bound total concurrent accepted-but-not-upgraded connections independent of the existing per-IP WebSocket rate limiter, similar to the `max_connections`/`TimeoutLayer` pattern already used for the internal RPC actor in `crates/consensus/service/src/actors/rpc/actor.rs`.

### Proof of Concept
1. Deploy `websocket-proxy` with `public_access_enabled = true` (or no `authentication`), exposing `GET /ws` anonymously.
2. From an attacker host, open thousands of raw TCP connections to the listener and send HTTP request headers one byte every few seconds (classic Slowloris), never completing the header block.
3. Each connection is accepted by `axum::serve` and held by hyper waiting for headers; since no header-read timeout exists, none of these connections are ever closed by the server.
4. Repeat until file descriptors / connection capacity on the host process are exhausted, preventing legitimate WebSocket subscribers from connecting — reproducing the Slowloris DoS described in GHSA-ggmv-j932-q89q against this analogous public server.

fn websocket_handler(
    state: ServerState,
    ws: WebSocketUpgrade,
    addr: SocketAddr,
    headers: HeaderMap,
    filter: FilterType,
) -> Response {
    let connect_addr = addr.ip();
    let client_addr = state.trusted_proxy_config.client_ip(connect_addr, &headers);

    let ticket = match state.rate_limiter.try_acquire(client_addr) {
        Ok(ticket) => ticket,
        Err(RateLimitError::Limit { reason, limit_type }) => {
            match limit_type {
                RateLimitType::PerIp => {
                    info!(
                        message = "per-IP rate limit exceeded",
                        client_ip = client_addr.to_string(),
                        reason = reason
                    );
                    Metrics::per_ip_rate_limited_requests().increment(1);
                }
                RateLimitType::Global => {
                    Metrics::global_rate_limited_requests().increment(1);
                }
            }

            return Response::builder()
                .status(StatusCode::TOO_MANY_REQUESTS)
                .body(Body::from(json!({"message": reason}).to_string()))
                .unwrap();
        }
    };
