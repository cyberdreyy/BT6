### Title
Deterministic per-email WebAuthn challenge key in `WebAuthnSessionStore` allows concurrent `BeginWebAuthnLogin` calls to overwrite one another, causing MFA login denial-of-service / cross-user challenge confusion - ([File: core/sessions/webauthn.go])

### Summary
`BeginWebAuthnLogin` stores its `webauthn.SessionData` challenge under the key `user.Email + "-authentication"` with no per-request nonce or session-ID binding, and `WebAuthnSessionStore.put` unconditionally overwrites any existing entry for that key. Because the store is a single shared, long-lived instance held by `SessionsController` and `WebAuthnController`, two concurrent WebAuthn-login attempts for the same email (e.g. the legitimate user and anyone who knows/guesses their password) collide on the same key, and the second overwrites the first's challenge before it is consumed.

### Finding Description
`POST /sessions` is handled by `SessionsController.Create` (`core/web/sessions_controller.go:29-68`), which forwards the request to `orm.CreateSession` (`core/sessions/localauth/orm.go:144-230`). That function first validates email and password via `constantTimeEmailCompare` and `utils.CheckPasswordHash` (lines 154-162) — so a caller must already possess the correct password for the target email to reach the WebAuthn stage. If the user has MFA enrolled and `sr.WebAuthnData == ""`, `sessions.BeginWebAuthnLogin(user, uwas, sr)` is invoked (`core/sessions/localauth/orm.go:184-198`), which calls `webAuthn.BeginLogin` and then:
```go
userLoginIndexKey := user.Email + "-authentication"
err = sr.SessionStore.SaveWebauthnSession(userLoginIndexKey, sessionData)
``` [1](#0-0) 

`SaveWebauthnSession` → `store.put` simply overwrites the map entry keyed only by email, with no per-request/session token component: [2](#0-1) 

`FinishWebAuthnLogin` later performs `store.take(userLoginIndexKey)`, which returns and deletes whatever is currently stored under that key — not necessarily the challenge that was actually issued to the caller completing the flow: [3](#0-2) [4](#0-3) 

The `WebAuthnSessionStore` instance is created once and shared across all requests (`NewSessionsController` / `NewWebAuthnController`), so it is not scoped per HTTP session/cookie: [5](#0-4) 

If an attacker who already knows the victim's password (or the victim themselves retries/refreshes) issues a second `BeginWebAuthnLogin` for the same email while the first challenge is outstanding, the second call's `sessionData` silently replaces the first in the map. Whichever party (attacker or legitimate user) later submits a signed assertion for the now-discarded challenge will fail `webAuthn.ValidateLogin`, because the stored `Challenge`/`AllowedCredentialIDs` no longer match what their authenticator signed.

### Impact Explanation
This does not allow authentication bypass: `ValidateLogin` still cryptographically verifies the assertion against whatever challenge is currently stored, and an attacker without the victim's physical security key cannot forge a valid response. The concrete impact is denial of service / cross-user state confusion of the MFA login flow — a legitimate user's in-flight WebAuthn login can be invalidated by a second `BeginWebAuthnLogin` call for the same email, forcing them to retry. This matches the "cross-user response confusion" category but does not rise to credential disclosure, privilege escalation, or unauthorized fund/job action.

### Likelihood Explanation
Exploitation requires the attacker to already pass the email+password check in `CreateSession` (`core/sessions/localauth/orm.go:154-162`) before reaching `BeginWebAuthnLogin`, i.e. knowledge of the victim's valid password (e.g., via a credential leak/reuse) is a hard precondition. Given that precondition, the race is trivial and fully repeatable (no rate limiting or per-request binding observed in this path), since the store key depends only on email.

### Recommendation
Bind the WebAuthn challenge to a per-request/session identifier rather than the bare email — e.g., derive the store key from a random nonce returned to the caller alongside the challenge (and required on `FinishWebAuthnLogin`), or scope the entry to the specific login attempt/session cookie so concurrent `BeginWebAuthnLogin` calls for the same email cannot clobber each other's session data.

### Proof of Concept
1. In `core/sessions/webauthn_test.go` (or a new test), create one `WebAuthnSessionStore` and one enrolled `User`/`WebAuthn` credential.
2. Call `BeginWebAuthnLogin(user, uwas, sr)` twice in sequence for the same `user.Email`, capturing `options1`/`sessionData1` (via the store's internal state before/after) and `options2`.
3. Assert that `store.GetWebauthnSession(user.Email + "-authentication")` returns the second call's `SessionData` (matching `options2`'s challenge), proving the first challenge was silently discarded.
4. Attempt `FinishWebAuthnLogin` with a (mock) assertion crafted against `options1`'s challenge and assert it fails with `ValidateLogin` error due to challenge mismatch, demonstrating the legitimate first requester's flow is denied.

func (store *WebAuthnSessionStore) SaveWebauthnSession(key string, data *webauthn.SessionData) error {
	marshaledData, err := json.Marshal(data)
	if err != nil {
		return err
	}
	store.put(key, string(marshaledData))
	return nil
}

func (store *WebAuthnSessionStore) put(key, val string) {
	store.mu.Lock()
	defer store.mu.Unlock()
	store.inProgressRegistrations[key] = val
}
```

// take returns the val for key, as well as removing it.
func (store *WebAuthnSessionStore) take(key string) (val string, ok bool) {
	store.mu.Lock()
	defer store.mu.Unlock()
	val, ok = store.inProgressRegistrations[key]
	if ok {
		delete(store.inProgressRegistrations, key)
	}
	return
}

// GetWebauthnSession unmarshals and returns the webauthn session information
// from the session cookie, which is removed.
func (store *WebAuthnSessionStore) GetWebauthnSession(key string) (data webauthn.SessionData, err error) {
	assertion, ok := store.take(key)
	if !ok {
		err = pkgerrors.New("assertion not in challenge store")
		return
	}
	err = json.Unmarshal([]byte(assertion), &data)
	return
}
