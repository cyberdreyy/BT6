### Title
Deterministic lockup address permits front-running/squatting of a victim owner's lockup deployment - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` computes `lockup_account_id` deterministically as `hex::encode(sha256(owner_account_id)[..20]).<factory>` with no binding to `predecessor_account_id`, so any unprivileged caller can pre-create a lockup for a victim `owner_account_id` with attacker-chosen parameters before the legitimate grant-issuer does, permanently occupying that address.

### Finding Description
The binding that should hold is: `LockupArgs deployed at hex::encode(sha256(owner_account_id)[..20]).<factory>` == `LockupArgs submitted by the legitimate/authorized creator for that owner_account_id`. This is broken because `create()` derives the target account solely from `owner_account_id`: [1](#0-0) 

and never checks `env::predecessor_account_id()` against anything, nor does it require any authorization tied to `owner_account_id` — `create` is a public, unprivileged, `#[payable]` method callable by anyone who attaches at least `MIN_ATTACHED_BALANCE`: [2](#0-1) 

The deploy sequence chains `create_account().deploy_contract(...).transfer(...).function_call("new", LockupArgs)`: [3](#0-2) 

If an attacker calls `create(owner_account_id=<victim>, ...)` first with self-chosen `lockup_duration`, `vesting_schedule`, `release_duration`, and `whitelist_account_id`, the `Promise::create_account()` succeeds because no account exists yet at that deterministic address, and the attacker's `LockupArgs` are permanently deployed. When the legitimate creator later calls `create()` for the same `owner_account_id`, `create_account()` in their promise chain fails (account already exists), `is_promise_success()` returns `false` in `on_lockup_create`, and the deposit is refunded to the legitimate caller — but the attacker's lockup contract, with attacker-chosen terms, remains permanently in place for that owner: [4](#0-3) 

No guard (`assert_self`, `is_promise_success`, ownership check, or allowlist of creators) prevents an arbitrary predecessor from targeting any `owner_account_id`; `assert_self()` only protects the callback from external callers, it does nothing to restrict who may call `create`.

### Impact Explanation
The victim owner ends up permanently bound to a lockup contract whose `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `staking_pool_whitelist_account_id` were chosen by an attacker rather than the legitimate grant issuer (e.g., NEAR Foundation), and the legitimate issuer can never redeploy at that address since the account already exists. This matches the Critical category: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." It is repeatable across any `owner_account_id` that has not yet had a lockup deployed, at a cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted address, which is refundable-nullified only for the legitimate creator, not recoverable by the attacker either (the attacker's deposit stays locked in the deployed contract) — but the attacker still achieves the goal of controlling lockup terms for the victim.

### Likelihood Explanation
The only preconditions are: (1) knowledge of the target `owner_account_id` (typically public/predictable, e.g. sequential or known grant recipient names), (2) attaching at least `MIN_ATTACHED_BALANCE` (3.5 NEAR), and (3) submitting the transaction before the legitimate creator does. This is fully within the capabilities of an unprivileged attacker as defined, requires no special permissions, and is straightforwardly reproducible/repeatable for any not-yet-created lockup address — the main constraint is a race against the legitimate creator's transaction, which is plausible given `owner_account_id`s for grants are often known or guessable in advance of the actual creation transaction.

### Recommendation
Bind the deployed lockup's authorization to a verified creator. Options: require `create` to be called only by an allowlisted set of creator accounts (e.g., `foundation_account_id` or an explicit allowlist checked via `assert_called_by_foundation`-style guard) rather than being fully open, and/or incorporate `predecessor_account_id` into the authorization check so only accounts entitled to create a lockup for a given `owner_account_id` can do so; alternatively, require the `owner_account_id` itself (or its designated key) to co-sign/initiate the lockup creation.

### Proof of Concept
Add a `near-sdk-sim`-style test (unit test using `testing_env!`/`MockedBlockchain` as in existing `lockup-factory/src/lib.rs` tests) that:
1. Sets predecessor to `attacker_account_id`, attaches `MIN_ATTACHED_BALANCE`, calls `contract.create(victim_owner_account_id, attacker_lockup_duration, None, attacker_vesting_schedule, None, Some(attacker_whitelist_account_id))`.
2. Simulates `create_account` success via `testing_env_with_promise_results(context, PromiseResult::Successful(vec![]))` and calls `on_lockup_create`, asserting it returns `true` and that the deployed `LockupArgs` (captured via the `function_call` args in the promise batch, or by asserting on `lockup_account()` state in an integration-style `near-workspaces` test) match the attacker's chosen parameters.
3. Sets predecessor to `legitimate_creator_account_id`, attaches deposit, calls `contract.create(victim_owner_account_id, real_lockup_duration, None, real_vesting_schedule, None, None)` for the same `owner_account_id`.
4. Simulates `create_account` failure via `PromiseResult::Failed` and calls `on_lockup_create`, asserting it returns `false` and that the refund `Promise::new(legitimate_creator_account_id).transfer(attached_deposit)` is issued — confirming the legitimate creator's `LockupArgs` were never deployed and the attacker's remain permanently in place at `hex::encode(sha256(victim_owner_account_id)[..20]).<factory>`.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
