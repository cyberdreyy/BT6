### Title
Builder withdrawal amount not capped to builder balance before being committed to the execution payload, allowing Gwei to be created - (File: specs/gloas/beacon-chain.md)

### Summary
In the Gloas builder-payment model, `state.builder_pending_withdrawals[i].amount` (the requested withdrawal amount) is copied verbatim into the `Withdrawal` objects placed in `payload_expected_withdrawals`, which is the value the execution layer is required to credit to `fee_recipient`. Only the *internal* accounting update in `apply_withdrawals` caps the deduction to what the builder actually has: `state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)` [1](#0-0) . Because the cap is applied only to the ledger decrement and not to the `Withdrawal.amount` field that the EL will honor, a builder whose queued withdrawal request exceeds its balance causes more Gwei to be paid out on the execution layer than is ever deducted from the beacon state — this is precisely the same "cap applied at the wrong layer, discrepancy silently dropped" bug class as the reported `_safeRewardsTransfer` issue, except here it manifests as unbacked Gwei creation instead of an unpaid shortfall.

### Finding Description
The Gloas withdrawal-sweep spec table itself documents the split: the `.amount` field of a `BuilderPendingWithdrawal` is described as the "Requested amount," while the internal decrement is separately noted as "Actual = `min(amount, builder.balance)`" [2](#0-1) . This confirms that the `Withdrawal` object queued for the execution payload carries the raw, uncapped requested amount, while `apply_withdrawals` only caps the ledger side:

```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
``` [3](#0-2) 

The spec's own test suite verifies this behavior end to end: with a builder balance of 1 ETH and a queued withdrawal request of 5 ETH, the resulting `Withdrawal.amount` committed to the payload is the full 5 ETH ("requested amount"), while the builder's internal balance is only reduced to 0 (i.e., only 1 ETH was ever backed): [4](#0-3) 

Since `Withdrawal.amount` is exactly the value the execution layer is obligated to credit to the destination address (this is the same field/semantics used for ordinary validator withdrawals via `decrease_balance`, and for builders the destination is `fee_recipient`, an address independent of the builder's own `execution_address` per the field table [5](#0-4) ), any block that includes such a withdrawal causes the execution layer to mint/pay 4 ETH that was never removed from any account in the consensus-layer state. This breaks the fundamental equality that a `Withdrawal` credited on the EL must equal a corresponding decrease of the same amount from the source's CL balance — the very invariant the spec's own comments describe for validator withdrawals ("Deferring the deduction ... would break the total supply invariant") [6](#0-5) .

### Impact Explanation
This is a Critical-severity finding under the stated rubric: Gwei is created out of nothing and paid to an address (`fee_recipient`) that has no entitlement to the uncapped portion. A builder (or any actor able to enqueue a `builder_pending_withdrawal` request, e.g. via `process_builder_withdrawal_request` or equivalent, exceeding its own balance) can cause spec-following block production to commit to an execution payload that pays out more ETH than the beacon state ever debited, permanently minting value with no corresponding CL-side decrease — a total-supply violation.

### Likelihood Explanation
The scenario requires only that a builder's `builder_pending_withdrawals` entry request more than the builder's current `balance` — which can trivially happen if a builder withdraws/loses balance (e.g., via slashočka-like penalties, other withdrawals, or simply requesting withdrawal of an amount before top-up) between the time the withdrawal is queued and the time it is swept. No malicious peer, coalition, or client bug is needed; this is a straightforward, spec-conformant sequence of builder actions and is exercised directly by the spec's own test suite (`test_builder_withdrawal_insufficient_balance`), indicating it is a realistic, reachable state.

### Recommendation
Cap `Withdrawal.amount` to `min(requested_amount, builder.balance)` at the point the `Withdrawal` object is constructed in `get_builder_withdrawals` (i.e., before it is placed into `payload_expected_withdrawals`), rather than only capping the subsequent internal ledger decrement in `apply_withdrawals`. This ensures the amount committed to the execution layer never exceeds the amount actually deducted from the builder's balance, preserving the total-supply invariant.

### Proof of Concept
1. Builder `B` has `state.builders[B].balance = 1 ETH`.
2. A `BuilderPendingWithdrawal` entry exists with `amount = 5 ETH`, `fee_recipient = X`.
3. During `get_expected_withdrawals`, this entry becomes a `Withdrawal(validator_index=convert_builder_index_to_validator_index(B), address=X, amount=5 ETH)` and is placed into `state.payload_expected_withdrawals` — the value the block commits the EL to pay.
4. `apply_withdrawals` executes `state.builders[B].balance -= min(5 ETH, 1 ETH)` → `state.builders[B].balance = 0`.
5. The execution layer, per the committed payload, credits address `X` with 5 ETH, while only 1 ETH was ever removed from any consensus-layer account — 4 ETH has been created with no offsetting reduction, exactly as reproduced by `test_builder_withdrawal_insufficient_balance` in the spec's own test suite [4](#0-3) .

def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
        - next_withdrawal_index: Incremented by 1
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=[builder_index],
        builder_withdrawal_amounts={builder_index: withdrawal_amount},
        builder_balances={builder_index: available_balance},
    )

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

    assert_process_withdrawals(
        spec,
        state,
        pre_state,
        withdrawal_count=1,
        builder_balances={builder_index: 0},
        builder_pending_delta=-1,
        withdrawal_index_delta=1,
        withdrawal_amounts_builders={builder_index: withdrawal_amount},
    )
