This confirms the finding. The gateway's `ProcessRequest` performs no per-message-ID uniqueness check across concurrent requests — `msg.Body.MessageId` comes straight from the client-supplied `message_id` field, is only validated for length/null-suffix in `Message.Validate()` [1](#0-0) , and `HandleLegacyUserMessage` stores the callback in `h.savedCallbacks` keyed solely by that attacker-controlled ID with no binding to `msg.Body.Sender` [2](#0-1) .

### Title
Cross-user response confusion via attacker-chosen colliding `MessageId` in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` stores each user's response callback in the shared `h.savedCallbacks` map keyed only by the client-supplied, unauthenticated `msg.Body.MessageId`, with no binding to the sender's signer. An attacker can choose the same `message_id` as a pending legitimate request, overwrite the map entry with their own callback, and receive the DON's response intended for the original user when `handleWebAPITriggerMessage` looks the callback up and deletes it by ID alone.

### Finding Description
The attacker-reachable entry point is `gateway.ProcessRequest` → `handler.HandleLegacyUserMessage` (dispatched via `multiHandler.HandleLegacyUserMessage`) [3](#0-2) . `MessageId` is fully attacker-controlled at request time: it is taken from the message body / JSON-RPC ID and only checked for length bounds and a null-byte suffix in `Message.Validate()` — never checked for uniqueness or tied to the signer [4](#0-3) .

In `HandleLegacyUserMessage`, after validating the payload, the handler does:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [2](#0-1) 
This blindly overwrites any existing entry for the same `MessageId`, discarding the original caller's callback reference without notifying or failing that caller.

Later, `handleWebAPITriggerMessage` resolves whichever callback is currently stored under that ID and deletes it:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()

if found {
    return savedCb.SendResponse(...)
}
``` [5](#0-4) 

Since the lookup key is only `msg.Body.MessageId` (echoed back by the DON node from the original triggering request) and never cross-checked against a sender identity, if an attacker submits `HandleLegacyUserMessage` with the same `MessageId` as a victim's still-pending request, the attacker's callback silently replaces the victim's in `h.savedCallbacks`. When the DON eventually responds to the *victim's* original message, `handleWebAPITriggerMessage` delivers that response to the attacker's callback instead, because the map only tracks the most recent registrant for that ID.

Note: `handler.HandleNodeMessage` does validate `msg.Body.Sender != nodeAddr` [6](#0-5) , but that only ensures the *node's* signature matches the connecting node address — it does nothing to bind the saved callback to the original *user's* signer, since the callback lookup key space (`MessageId`) is shared across all unauthenticated users hitting the same DON/handler.

### Impact Explanation
This is a cross-user response confusion / capability-execution response hijack: an unauthenticated attacker can redirect another user's web API trigger response (which may include their request execution output, potentially containing sensitive workflow trigger data) to themselves by simply guessing/choosing a colliding `message_id` while the victim's request is in flight (default in-flight window: up to `defaultCallbackMaxAgeSec` = 120 seconds, or until pruned). It also causes a denial of service for the victim, whose original request will never receive a response (their callback reference is discarded, so their HTTP call blocks until `callback.Wait` times out in `gateway.ProcessRequest`).

### Likelihood Explanation
No privileges or authentication are required beyond the ability to send a request through the gateway's public `/user` HTTP endpoint with a self-chosen `message_id` matching a value the attacker can observe or predict (e.g., if the calling application uses low-entropy/sequential/predictable IDs, or the attacker controls both requests in an intentional race). The attacker needs only to win a race between their `HandleLegacyUserMessage` call and the arrival of the DON's response to the victim's original message — a reasonably feasible race window given the multi-hop network round trip to DON nodes and back.

### Recommendation
Bind saved callbacks to more than just the raw `MessageId`: key `h.savedCallbacks` by a composite key that includes the original sender's verified signer (`msg.Body.Sender`) or DON ID plus MessageId, and reject/error (rather than silently overwrite) `HandleLegacyUserMessage` calls whose `(sender, MessageId)` pair collides with an existing pending entry. Additionally, when overwriting would occur under the current scheme, either reject the second request outright or ensure the first caller's `callback.Wait` fails explicitly rather than hanging.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct two signed `TriggerRequestPayload` messages, `msgA` (victim, key A) and `msgAttacker` (attacker, key B), both with identical `Body.MessageId == "X"` but distinct payloads/senders.
2. Call `handler.HandleLegacyUserMessage(ctx, msgA, cbA)` — assert `handler.savedCallbacks["X"].Callback == cbA` under lock.
3. Call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)` — assert `handler.savedCallbacks["X"].Callback` has now become `cbAttacker` (overwrite proven).
4. Simulate the DON node responding to the *original* message A by constructing a `jsonrpc.Response` with `ID == "X"` and `Sender` matching a configured DON node address, and call `handler.HandleNodeMessage(ctx, resp, nodeAddr)`.
5. Assert `cbAttacker.Wait(ctx)` returns the response (attacker receives victim A's data) while `cbA.Wait(ctx)` times out/never resolves — demonstrating cross-user response delivery to the wrong (attacker) callback.
