### Title
V1 signer's tenure-change duplicate-block guard uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, allowing double-signing of conflicting tenure-start blocks - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in `v1.rs` guards against re-signing a conflicting tenure-start block for the same `consensus_hash` by querying `signer_db.get_last_globally_accepted_block`, which only returns a block once it has reached the reward-weight threshold of global acceptance. The `v2.rs` equivalent explicitly uses `get_last_signed_block` instead, with an inline comment stating that both locally- and globally-signed blocks must count to prevent reorging blocks this signer has already committed a signature to.

### Finding Description
In `stacks-signer/src/chainstate/v1.rs`, `validate_tenure_change_payload` performs the duplicate/reorg check as: [1](#0-0) 

This is the last defense against a competing tenure-change block being approved for a `consensus_hash` this signer already signed for. Compare with `v2.rs`, which computes the same check but explicitly documents and uses `get_last_signed_block`: [2](#0-1) 

The v2 comment explains the intended equality precisely: "Only blocks we have signed (locally or globally accepted) count here: a block we have merely pre-committed to carries no signature from us, so it is safe to accept a competing tenure-start block in its place if it failed to reach consensus." This means the correct equality is: *blocks counted as "already committed to" = blocks this signer has already signed (locally-signed OR globally-accepted)*. V1 narrows this set to only globally-accepted blocks, dropping locally-signed-but-not-yet-globally-accepted blocks from the guard.

Attack flow: an attacker (a miner-slot holder) can craft a tenure-change block A for consensus hash T that a v1 signer locally signs (satisfies all preceding checks: parent tenure match, `check_tenure_change_confirms_parent`, `check_parent_tenure_choice`), but which does not reach the reward-weight threshold for global acceptance (e.g., because the attacker only gets minority signer support, or the node hasn't yet reported the aggregate signature back to signerdb). The signer's local signature for block A is thus recorded, but `get_last_globally_accepted_block(T)` still returns `None`. The attacker (or another party) then proposes a second, sibling tenure-change block B also for consensus hash T. `validate_tenure_change_payload` re-runs the same duplicate check, again finds `None` from `get_last_globally_accepted_block`, and lets block B proceed to be signed — even though this signer already signed A for the same tenure start.

### Impact Explanation
This breaks the uniqueness safety property: a single signer can be induced to produce valid signatures on two conflicting tenure-start blocks (A and B) for the same `(tenure, height=start)` slot. If enough signers are similarly tricked (each independently satisfying the same non-global-but-locally-signed precondition), the aggregate of signatures across A and B could allow both to reach thresholds in different views, or at minimum this signer's own signature is a genuine safety violation regardless of whether the fork is finalized — the code path that is supposed to prevent one signer from co-signing two mutually exclusive tenure starts fails to do so. This matches the Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block (chain safety)."

### Likelihood Explanation
Preconditions are narrow but realistic: the signer set must be running under `SortitionStateVersion::V1` (an older/fallback sortition-view mode), and there must exist a window where a first tenure-change block for `T` has been locally signed by the victim signer but has not yet been recorded as globally accepted in `signerdb` (e.g., below reward-weight threshold, or the node hasn't reported it back yet). The attacker needs only their own miner slot (to legitimately win a sortition and construct block proposals) plus standard StackerDB gossip to submit the second competing proposal — no majority-signer collusion, no compromised keys, and no auth_token are required. This is repeatable per-tenure whenever the timing window exists.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to query `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, matching the `v2.rs` behavior and its documented equality (locally-signed OR globally-accepted blocks both count as "already committed to").

### Proof of Concept
Rust test plan (place in `stacks-signer/src/chainstate/tests/v1.rs`, mirroring the structure of `tests/v2.rs`):
1. Set up a `SortitionsView` (v1) with `cur_sortition` for consensus hash `T`, and a `SignerDb` in a temp dir.
2. Construct tenure-change block `A` for `T` (valid parent tenure, valid `prev_tenure_consensus_hash`), and call `signer_db` methods to record it as **locally signed only** (i.e., insert a block record with a signature but do NOT mark/insert it via the path that sets global acceptance — e.g. use whatever `signerdb.rs` API inserts a local signature, such as the one backing `has_signed_block_in_tenure`, without calling the global-acceptance insertion API).
3. Assert `signer_db.get_last_globally_accepted_block(&T)` returns `None` (confirms the precondition) while `signer_db.get_last_signed_block(&T)` returns `Some(A)`.
4. Construct sibling tenure-change block `B` for the same `T` with a different `signer_signature_hash` but otherwise valid tenure-change payload/parent linkage.
5. Call `view.validate_tenure_change_payload(&proposed_by, tenure_change_of_B, &B, &mut signer_db, &client)`.
6. **Current (buggy) behavior**: assert the call returns `Ok(())` — i.e., `RejectReason::DuplicateBlockFound` is NOT raised, wrongly permitting a second tenure-start block for `T` to be signed.
7. **Expected (fixed) behavior**: after changing v1 to use `get_last_signed_block`, assert the same call returns `Err(RejectReason::DuplicateBlockFound)`, matching v2's stricter guard. [1](#0-0) [2](#0-1)
