### Title
Re-proposal of an identical block resets `BlockInfo` decision state, discarding a signer's own vote/validity record - (File: stacks-signer/src/v0/signer.rs)

### Summary
The pattern mirrors the ArcadeTreasury bug: a stateful record meant to persist a decision is unconditionally overwritten by a later "approve"-style call instead of preserving/merging it, undermining an equality the caller relies on. In `handle_block_proposal`, when a proposal for a signature hash the signer has already evaluated is deemed reconsiderable, the code builds a brand-new `BlockInfo` and stores it, explicitly documented as overwriting `validity`, `signed_timestamps`, etc. [1](#0-0) 

### Finding Description
`handle_block_proposal` looks up any prior `BlockInfo` for the incoming proposal's `signer_signature_hash`, and calls `should_reevaluate_block` to decide whether to proceed [2](#0-1) . When re-evaluation is allowed (e.g., because the stored `reject_reason` is considered reconsiderable, per the log message "our rejection reason allows us to reconsider" [3](#0-2) ), the code proceeds to construct a fresh `BlockInfo` via `BlockInfo::from(block_proposal.clone())`, which — per the inline comment — "will overwrite any prior proposal info on the block if it exists, e.g. validity, signed_timestamps, etc." [1](#0-0) . This fresh `block_info` is then persisted via `self.signer_db.insert_block(&block_info)`, which performs `INSERT OR REPLACE` on the full row, wiping fields such as `valid`, `state`, `signed_self`, `vote`, and `reject_reason` for that hash [4](#0-3) .

Because `signer_signature_hash` is derived from the full (miner-signed) block header, a byte-identical re-proposal is the only way to hit the same hash, so the discarded fields describe this signer's own prior handling of that exact block — not competing content. The risk is that separate accumulator tables (`add_block_pre_commit`, `add_block_signature`) are keyed independently by hash and are *not* reset by this overwrite, while the local decision fields *are* reset. This creates a window where the signer's local status (e.g., "already signed", "already decided") is inconsistent with the durable, non-reset tallies of pre-commits/signatures recorded elsewhere in the DB, potentially causing the signer to re-run validation/pre-commit logic (`handle_block_pre_commit` checks `block_info.signed_self.is_some()`) against a block it previously already locally accepted, since `signed_self` was cleared by the overwrite.

### Impact Explanation
I could not fully verify the guard conditions in `should_reevaluate_block` (the portion prior to line 1560) that gate when this overwrite path is reachable — in particular whether it is blocked once `block_info.has_reached_consensus()` is true. Without full visibility into that gate, I cannot confirm whether this can be driven into a state where a signer re-signs or re-processes a block after already reaching a terminal (globally accepted/rejected) decision, which would be the concrete safety break required (a rejection recounted as an acceptance, or duplicated processing corrupting the local invariant that a `BlockInfo`'s decision fields are append-only once set).

### Likelihood Explanation
Reachable by any single miner or relayed gossip re-sending an existing block proposal, since only `should_reevaluate_block`'s gating (largely built around specific "reconsiderable" reject reasons) constrains this path.

### Recommendation
Confirm and, if necessary, tighten `should_reevaluate_block` to guarantee it can never permit the overwrite once `has_reached_consensus()` is true or `signed_self`/`signed_group` is set, and consider merging into rather than replacing decision-carrying fields on re-proposal, analogous to fixing `approve()` to increment/merge rather than overwrite an allowance.

### Proof of Concept
Not established as a concrete exploit given the incomplete view of `should_reevaluate_block`'s full gating logic (lines preceding 1560 in `stacks-signer/src/v0/signer.rs`) — this would need to be traced further (e.g., via a Devin session with full file access) to confirm whether a terminal/consensus-reached `BlockInfo` can actually reach the overwrite path at line 1653-1654.
