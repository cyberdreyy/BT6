## Title
`gatewayHandler.mtlsConcurrencyLimiter` is a single global pool with no per-owner/per-key isolation, allowing one attacker to exhaust the concurrency budget for all mTLS action requests - (File: `core/services/gateway/handlers/capabilities/v2/http_handler.go`)

### Summary
`gatewayHandler.send` creates a throwaway mTLS `HTTPClient` per `OutboundHTTPRequest`, but every such client shares the exact same `h.mtlsConcurrencyLimiter` instance regardless of which node/owner/certificate submitted the request. The limiter (`limits.MakeResourcePoolLimiter(lf, cresettings.Default.GatewayHTTPActionMtlsConcurrencyLimit)`) enforces only a global slot count via `concurrencyLimitedClient.Do` → `limiter.Wait(ctx, 1)`, with no per-owner/per-key partitioning.

### Finding Description
In `gatewayHandler.send` (`core/services/gateway/handlers/capabilities/v2/http_handler.go:297-337`), when `req.Mtls != nil`, a new client is built via `h.httpClientFactory` with `ConcurrencyLimiter: h.mtlsConcurrencyLimiter` — the same single struct field on `gatewayHandler` for every request from every node/owner [1](#0-0) . That limiter is instantiated once at handler construction as a single global `limits.ResourcePoolLimiter[int]` with no keying by owner, workflow, or certificate [2](#0-1) . In `network/httpclient.go`, `concurrencyLimitedClient.Do` simply calls `c.limiter.Wait(req.Context(), 1)` before delegating to the transport — the limiter has no identity/tenant argument, so it cannot distinguish which requester holds each of the acquired slots [3](#0-2) . A comment in `send` explicitly acknowledges this is a shared budget and rationalizes it as acceptable because of three other layered controls: the global node rate limiter, per-node rate limiters, and "per-owner rate limits in the action capability in the workflow node" [4](#0-3) .

### Impact Explanation
Because the concurrency limiter is a single shared pool, one attacker-controlled node/workflow submitting N concurrent `OutboundHTTPRequest`s with distinct `Mtls.PrivateKey`/`Certificate` targeting slow endpoints can occupy all available slots and starve legitimate mTLS action requests from unrelated users/workflows — this is a genuine resource-isolation gap (no per-owner accounting exists in this code), matching a cross-user availability/DoS impact class. However, whether this is *practically* exploitable depends entirely on the layered mitigations the code comments cite: (1) `h.globalNodeRateLimiter` and `h.perNodeRateLimiters`, which bound how fast any single node can emit HTTP action requests into the gateway at all [5](#0-4) , and (2) `h.mtlsRequestRateLimiter`, a further global rate limit applied specifically to mTLS requests before the request is sent [6](#0-5) , and (3) an upstream per-owner rate limit enforced in the workflow-node action capability (outside this file, not verifiable from this codebase view) that is claimed to bound how many mTLS requests a single workflow owner can originate. These layers are rate limits, not concurrency limits, so they throttle *request initiation rate* but do not prevent a burst of already-admitted concurrent requests targeting a slow/hanging external endpoint from occupying concurrency slots for the duration of their (attacker-controlled, up to `req.TimeoutMs`-capped) timeout, denying slots to other tenants' concurrent mTLS calls during that window.

### Likelihood Explanation
Exploitation requires only the documented "attacker controls a workflow/node submitting outbound HTTP mTLS actions" precondition — i.e., an unprivileged, but legitimate, workflow/node capable of issuing `HTTPAction`/mTLS outbound requests, which matches the allowed unprivileged-attacker model. The attack is straightforward to reproduce: submit multiple concurrent `OutboundHTTPRequest`s with distinct throwaway mTLS certs against slow/unresponsive endpoints, each held open up to its `TimeoutMs`. The rate limiters reduce burst size/frequency but do not eliminate the shared-pool starvation window, and the pool size is a fixed global constant (`cresettings.Default.GatewayHTTPActionMtlsConcurrencyLimit`), so a sufficiently sized burst (bounded by the rate limiters' burst allowance) can still saturate it for the duration of the slow requests.

### Recommendation
Partition `mtlsConcurrencyLimiter` per owner/workflow (e.g., using `limits.MultiResourcePoolLimiter` combining a global cap with a per-owner cap, similar to the pattern already used for `ExecutionConcurrency` in `core/services/workflows/v2/config.go`), so that no single owner can consume the entire shared mTLS concurrency budget. Alternatively/additionally, tighten the interaction between `mtlsRequestRateLimiter` and `mtlsConcurrencyLimiter` so that pending slow in-flight requests count against a per-owner ceiling rather than a single global counter.

### Proof of Concept
1. In `http_handler_test.go`, construct a `gatewayHandler` with a small `mtlsConcurrencyLimiter` (e.g., pool size 2) and a stub `httpClientFactory` returning a client whose `Send` blocks until a channel is closed (simulating a slow external endpoint).
2. Concurrently invoke `h.send(ctx, httpReq, reqA)` and `h.send(ctx, httpReq, reqB)` with distinct `Mtls.PrivateKey`/`Certificate` values from two different (attacker vs. legitimate) simulated owners, saturating the pool with attacker requests first.
3. Assert that a legitimate third request (`reqC`, different owner) blocks/times out on `mtlsConcurrencyLimiter.Wait` despite having no relationship to the attacker's in-flight requests — demonstrating no per-owner fairness/isolation exists at the `send`/`mtlsConcurrencyLimiter` layer.
4. Document that this is mitigated only by the rate limiters upstream (`mtlsRequestRateLimiter`, per-node/global rate limiters, and the workflow-node's per-owner rate limiter), not by any accounting inside `mtlsConcurrencyLimiter` itself.

func (h *gatewayHandler) send(ctx context.Context, httpReq network.HTTPRequest, req gateway_common.OutboundHTTPRequest) (*network.HTTPResponse, error) {
	if req.Mtls == nil {
		return h.httpClient.Send(ctx, httpReq)
	}

	if h.httpClientFactory == nil {
		return nil, errors.New("nil http client factory, cannot make mtls request")
	}

	// Instantiate a throwaway HTTP client with the provided Mtls client certificate provided.
	// We do this to ensure that we don't accidentally leak auth'd connections to other users.
	// Note: this isn't a DOS vector because
	// a) we have a global rate limit above which limits abuse
	// b) we apply rate limits limiting the ability of sending nodes to spam requests
	// c) we apply per-owner rate limits in the action capability in the
	// workflow node limiting the ability of users to abuse this flow by spamming Mtls requests.
	// The client enforces the mtls concurrency limit internally (on the request's
	// capped-timeout context) before delegating to the underlying transport.
	client, err := h.httpClientFactory(network.HTTPClientConfig{
		Mtls: &gateway_common.MtlsAuth{
			PrivateKey:  req.Mtls.PrivateKey,
			Certificate: req.Mtls.Certificate,
		},
		ConcurrencyLimiter: h.mtlsConcurrencyLimiter,
	})
	if err != nil {
		return nil, fmt.Errorf("failed to instantiate http client for mtls request: %w", err)
	}

	// We don't have access to the org here, so this will fall back to the environment default (=false).
	// That's appropriate because all fields set on the request come from untrusted nodes.
	// The capability separately applies an org-specific check.

	// Note: we intentionally consume the rate-limit after instantiating the client so that a malicious user
	// can't send requests with invalid mtls credentials and thus cheaply consume global tokens.
	if !h.mtlsRequestRateLimiter.Allow(ctx) {
		return nil, fmt.Errorf("global mtls request rate limit exceeded: %w", network.ErrBlockedRequest)
	}

	return client.Send(ctx, httpReq)
}

func (c *concurrencyLimitedClient) Do(req *http.Request) (*http.Response, error) {
	free, err := c.limiter.Wait(req.Context(), 1)
	if err != nil {
		return nil, fmt.Errorf("mtls concurrency limit exceeded: %w", ErrBlockedRequest)
	}
	defer free()
	return c.client.Do(req)
}
