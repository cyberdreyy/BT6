### Title
Loss-adjusted withdraw receipts are paid at par when a newer request overwrites `lastWithdrawRequest`, letting users escape the epoch-loss haircut - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The `gh attestation verify` bug is a *filter mismatch returning success*: when no attestation matches the requested predicate type, the function returns `nil` instead of an error and the process exits 0, i.e. a check that should fail silently passes. The analog in `IdleCreditVault.claimWithdrawRequest` is `_claimLossAdjustedWithdrawRequest`: it looks up `lossRecoveryPriceByEpoch` using only the user's *latest* request epoch (`lastWithdrawRequest[_user]`). If a user has an older receipt from a loss epoch but a newer withdraw request pushes `lastWithdrawRequest` to a different epoch, the loss-price lookup misses (`lossRecoveryPriceByEpoch[wrongEpoch] == 0`), the function silently returns 0 instead of applying the haircut, and the same claim basis is then paid in full by `_claimFundedWithdrawRequest` at par. A receipt that should have been haircut "verifies" at full value.

### Finding Description
`claimWithdrawRequest` composes three internal claim paths (`contracts/strategies/idle/IdleCreditVault.sol:301-314`). The loss-adjusted path resolves the epoch to haircut like this:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```
(IdleCreditVault.sol:789-792)

So only the epoch stored in `lastWithdrawRequest[_user]` is ever checked against `lossRecoveryPriceByEpoch`. The epoch-keyed receipt, however, lives in `withdrawsRequestsByEpoch[_user][epoch]` and in the aggregate `withdrawsRequests[_user]` (set in `requestWithdraw`, lines 292-293), and `lastWithdrawRequest[_user]` is overwritten on every new request (line 282).

Attack sequence (fixed-APR mode, loss-adjusted epoch):
1. Epoch N running: attacker calls `requestWithdraw`, creating a receipt in `withdrawsRequestsByEpoch[attacker][N]` and `withdrawsRequests[attacker]`, `lastWithdrawRequest = N`.
2. Manager calls `stopEpochWithDuration(..., _lossAmount)`; the strategy records `lossRecoveryPriceByEpoch[N]` and funds only the haircut amount. The attacker's epoch-N receipt is now loss-adjusted.
3. In a later buffer phase (epoch M > N), the attacker calls `requestWithdraw` again. `lastWithdrawRequest[attacker]` becomes M.
4. After epoch M ends (`epochNumber > M`), attacker calls `claimWithdrawRequest`:
   - `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[M] == 0` and returns 0 — the epoch-N haircut is silently skipped ("no matching attestation" → nil error).
   - `_claimFundedWithdrawRequest` passes its gate (`epochNumber > lastWithdrawRequest`), then pays `withdrawsRequests[attacker]`, which still includes the full un-haircut epoch-N basis, at par via `_transferFundedClaim`.

The attacker receives `claimBasis` instead of `claimBasis * lossRecoveryPriceByEpoch[N] / RECOVERY_FULL`, paid out of the strategy's funded underlying reserve that backs *other* pending claimants.

A secondary symptom: an honest user whose latest request epoch differs from their loss epoch can likewise skip the loss path; conversely the single-epoch-only lookup means the loss-adjusted accounting can be permanently stranded if the aggregate is ever cleared first.

### Impact Explanation
Direct theft / insolvency: the excess paid is `claimBasis * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`, drawn from funded reserves earmarked for other pending withdraw claims. Each exploiting user drains up to the haircut percentage of their receipt, and late claimants can be left unable to withdraw (permanent freezing of their payouts once the reserve is depleted).

### Likelihood Explanation
Requires a loss epoch (`stopEpochWithDuration` with `_lossAmount > 0` or equivalent `lossRecoveryPriceByEpoch` write) — an honest-manager action, consistent with the rules — plus an attacker holding a tranche position who makes a second withdraw request in a later epoch before claiming. No privileged attacker role is needed. Caveat I could not fully verify within the available context: the exact lines in `stopEpochWithDuration`/`collectWithdrawFunds` that retain the epoch-N `withdrawsRequests`/`withdrawsRequestsByEpoch` entries and receipt tokens until claim; if those entries were deleted at funding time the par claim would not fire — a PoC should confirm the receipt survives funding as the code comments (`pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount`, line 797) strongly suggest.

### Recommendation
Do not key loss recovery solely off `lastWithdrawRequest`. Either iterate/record all epochs with nonzero `withdrawsRequestsByEpoch` for the user, or store a per-user set of loss epochs (e.g., `lossEpochsOf[user]`) at funding time and clear each through `_clearWithdrawClaimForEpoch`, so a loss-adjusted receipt can never fall through to `_claimFundedWithdrawRequest` at par.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (contracts/strategies/idle/IdleCreditVault.sol)
// Setup: deposit -> startEpoch; during running epoch N:
uint256 receiptN = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));
// manager: stopEpochWithDuration(apr, 0, duration, lossAmount) with lossAmount > 0
//      -> lossRecoveryPriceByEpoch[N] < RECOVERY_FULL, haircut funded.
// Attacker (same user) in buffer of epoch N+1 requests again:
cdoEpoch.requestWithdraw(trancheBal / 4, address(AAtranche)); // lastWithdrawRequest = N+1
// run epoch N+1 to completion (startEpoch -> warp -> stopEpoch, borrower repays).
// Attacker claims:
uint256 pre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 got = underlying.balanceOf(attacker) - pre;
// Expect bug: got includes full receiptN (no haircut) instead of
// receiptN * lossRecoveryPriceByEpoch[N] / RECOVERY_FULL
assertGt(got, receiptN * strategy.lossRecoveryPriceByEpoch(N) / RECOVERY_FULL + receiptN1);
```
Assert additionally that `strategy.lossRecoveryPriceByEpoch(N) < RECOVERY_FULL` and that the excess withdrawn equals `receiptN * (RECOVERY_FULL - price) / RECOVERY_FULL`, demonstrating haircut escape paid from other claimants' funded reserve.
