### Title
Unprivileged instant-withdraw request permanently/epoch-long blocks all withdrawals on non-initialized vaults via `_ensureDefaultRecoveryInitialized` revert - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._ensureDefaultRecoveryInitialized()` reverts whenever `pendingInstantWithdraws != 0` and `defaultRecoveryInitialized == false`. Because both `requestWithdraw` and `requestInstantWithdraw` call this initializer first, any user who can open an instant-withdraw receipt can force every subsequent withdraw request of every user to revert until the instant receipt is fully funded and claimed. On a freshly deployed vault the flag is set on the first request, but on upgraded vaults (the stated purpose of the lazy initializer) the flag starts `false`, so the griefing window is real and repeatable.

### Finding Description
The lazy initializer added for the default-recovery migration path contains:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:924-935
function _ensureDefaultRecoveryInitialized() internal {
  if (defaultRecoveryInitialized) return;
  if (pendingInstantWithdraws != 0) revert NotAllowed();
  ...
  defaultRecoveryInitialized = true;
}
```

It is invoked at the top of both withdrawal entry points:

- `requestWithdraw` at `IdleCreditVault.sol:245` (`_ensureDefaultRecoveryInitialized();`)
- `requestInstantWithdraw` at `IdleCreditVault.sol:358`

`requestInstantWithdraw` increases `pendingInstantWithdraws` at `IdleCreditVault.sol:374` (`pendingInstantWithdraws += _amount;`), and `pendingInstantWithdraws` is only decreased in `collectInstantWithdrawFunds` (`IdleCreditVault.sol:401`), i.e. when the CDO collects borrower-funded underlying at epoch start/stop — an action driven by honest manager/borrower flow, outside the attacker's control.

Attack sequence (epoch running, `defaultRecoveryInitialized == false`, instant withdrawals enabled and APR dropped so `_isInstantWithdrawEnabled` path triggers in `IdleCDOEpochVariant.sol:761-768`):

1. Attacker (a KYC-passing tranche holder) calls `IdleCDOEpochVariant.requestWithdraw` for even a dust tranche amount. The CDO routes to `creditVault.requestInstantWithdraw`, minting the attacker a receipt and setting `pendingInstantWithdraws > 0`.
2. From that point, every call to `requestWithdraw` or `requestInstantWithdraw` by any user reverts with `NotAllowed` at `IdleCreditVault.sol:926`, because `defaultRecoveryInitialized` is still `false` and the initializer can never run while `pendingInstantWithdraws != 0`.
3. The freeze persists until the honest manager starts the epoch, borrower funds the instant bucket, `collectInstantWithdrawFunds` drains `pendingInstantWithdraws`, and the attacker (or anyone) claims. Only then can a normal request finally execute `_ensureDefaultRecoveryInitialized` and set the flag.
4. Since an unclaimed/just-funded instant bucket keeps `pendingInstantWithdraws != 0` across the whole buffer+epoch cycle, and the attacker can re-open an instant receipt whenever the APR-drop condition recurs, the DoS is repeatable each epoch while the flag remains unset.

This is the same bug class as CVE-2015-7702: an incomplete fix. The migration guard was added to protect legacy receipts, but it lets an unprivileged receipt-holder hold the initialization gate closed, converting a lazy-init edge case into a withdrawal-wide liveness failure.

### Impact Explanation
Temporary freezing of funds with quantified scope: while `pendingInstantWithdraws != 0` and `defaultRecoveryInitialized == false`, **no user can create a normal withdraw request or an instant withdraw request** — both entry points revert before touching accounting. All LP principal in the vault is effectively locked in the request queue for at least one full epoch cycle (buffer + epoch duration, plus claim processing), and the lock is renewable by the attacker whenever instant-withdraw conditions recur. The cost to the attacker is one dust-sized instant receipt, which is later redeemable at par — so the attack is nearly free.

### Likelihood Explanation
Preconditions: (a) vault was upgraded so `defaultRecoveryInitialized` is still `false` (exactly the case the lazy initializer was written for), (b) `allowInstantWithdraw` is enabled and `lastEpochApr > currentApr + instantWithdrawAprDelta` so `IdleCDOEpochVariant.sol:761-768` routes to `requestInstantWithdraw`. Both are normal operating states — APR decreases between epochs are routine, and instant withdrawals are a supported feature. No privileged or colluding role is needed; the attacker is an ordinary tranche holder. Likelihood is therefore moderate-to-high on qualifying deployments and zero otherwise (once the flag flips, the bug is dead).

### Recommendation
Do not gate initialization on `pendingInstantWithdraws == 0`. Either:

- Set `defaultRecoveryInitialized = true` in the upgrade/initializer path (or on the first `stopEpoch`/`startEpoch` after upgrade) so the flag cannot be held closed by user receipts, or
- In `_ensureDefaultRecoveryInitialized`, tolerate pending instant withdrawals — instant receipts mint strategy tokens 1:1 to the user and are fully represented by `instantWithdrawsRequests`/`instantWithdrawClaimsByEpoch`, so the per-epoch ownership data the migration needs (`defaultPendingClaimBasis` at `IdleCreditVault.sol:644-649`) already exists for them.

### Proof of Concept
```solidity
// Foundry fork test sketch — vault upgraded, defaultRecoveryInitialized == false,
// allowInstantWithdraw enabled, epoch running with APR lower than lastEpochApr - delta.

// 1. Attacker (any allowed tranche holder) opens an instant withdraw receipt.
vm.prank(attacker);
cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche)); // routes to requestInstantWithdraw
assertGt(IdleCreditVault(strategy).pendingInstantWithdraws(), 0);
assertFalse(IdleCreditVault(strategy).defaultRecoveryInitialized());

// 2. Any normal withdraw request now reverts for all users.
vm.prank(victim);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.requestWithdraw(victimTrancheAmount, address(AAtranche));

// 3. Instant withdraw requests also revert (same initializer at line 358).
vm.prank(victim2);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.requestWithdraw(victim2TrancheAmount, address(AAtranche));

// 4. Freeze persists across the buffer until manager startEpoch + borrower funding
//    + collectInstantWithdrawFunds drains pendingInstantWithdraws and the receipt
//    is claimed — only then can the first request succeed and set the flag.
```

Note: the exact revert surfaces on line `IdleCreditVault.sol:926`; the gating calls are at `IdleCreditVault.sol:245` and `IdleCreditVault.sol:358`. The assumption that an upgraded deployment leaves `defaultRecoveryInitialized == false` follows from the function's own lazy-init design comments at `IdleCreditVault.sol:919-935`.
