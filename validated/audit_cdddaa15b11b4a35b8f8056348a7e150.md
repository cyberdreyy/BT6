### Title
Missing duplicate MessageId check in legacy WebAPI Gateway handler allows cross-user response hijacking - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
The legacy WebAPI capability handler's `HandleLegacyUserMessage` stores each incoming user request's callback in a shared `savedCallbacks` map keyed by the client-supplied `MessageId`, without checking whether that ID is already in use by another in-flight request. This is analogous to the Sherlock finding: instead of "refund sent to the wrong user," here a DON node's *response* to one user's request can be delivered to a different, unrelated user's callback because the map is silently overwritten by whichever request last set that key.

### Finding Description
`HandleLegacyUserMessage` unmarshal's the trigger payload and then unconditionally writes: [1](#0-0) 
There is no check for an existing entry at `msg.Body.MessageId` before overwrite, unlike the sibling implementations for the same class of problem in `confidentialrelay` (`"request ID already exists"`) and `vault` (`"request was already authorized previously"`) handlers, and the v2 HTTP trigger handler (`"in-flight request"`), all of which explicitly guard against this: [2](#0-1) 

The `MessageId` used as the map key is fully attacker-controlled: it comes straight from the JSON-RPC request `ID` field supplied by any unprivileged client hitting the internet-facing Gateway's user-facing HTTP port, via `ValidatedMessageFromReq`: [3](#0-2) 
and is routed to the handler from `gateway.ProcessRequest`, the public request-handling entrypoint: [4](#0-3) 

When a node later returns a `MethodWebAPITrigger` response, the gateway looks up (and deletes) whatever callback is currently stored under that `MessageId` and forwards the response to it: [5](#0-4) 

Attack flow:
1. Victim sends a legitimate `web_api_trigger` request with `MessageId = "X"`; the handler stores victim's callback under key `"X"` and forwards the request to DON nodes.
2. Before the DON responds, an unprivileged attacker sends another `web_api_trigger` request also using `MessageId = "X"` (this ID is entirely attacker-chosen and unvalidated for uniqueness). The handler overwrites `savedCallbacks["X"]` with the attacker's callback.
3. When a DON node responds to the victim's original request (still carrying `MessageId = "X"`, since nodes echo the message ID from the original request), `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds the attacker's callback (the victim's was overwritten and lost), and delivers the victim's response data to the attacker instead of to the victim.
4. The victim's original HTTP request instead times out or receives no response, while the attacker receives a response payload originating from the victim's request/DON interaction.

This mirrors the root cause of the Sherlock M-1 finding: a shared/overwritable state slot intended to route a value (fee refund / response) back to the correct originator is not scoped/keyed reliably per-request, so a race between two independent, unprivileged actors' requests can redirect output meant for one to the other.

### Impact Explanation
This is a cross-user response confusion within the Gateway's internet-facing message-handling path, reachable from any unprivileged client. Depending on payload content (e.g., data returned from a `web_api_trigger` computation), this could leak workflow output intended for the victim to the attacker, and/or deny the victim their expected response (denial of service via request-id collision). Given the Gateway is meant to isolate per-request state for concurrent unprivileged users, this breaks that isolation guarantee.

### Likelihood Explanation
Likelihood is high: `MessageId` is directly attacker-controlled (arbitrary string up to 200 chars, no format constraints beyond length/null-byte checks in `Message.Validate()`), requires no authentication beyond whatever the endpoint normally requires, and only requires timing a second request with the same ID while the first is still in flight (a window of up to `CallbackMaxAgeSec`, default 120s). No brute-force of secrets is needed — the attacker simply reuses a guessed or observed `MessageId`.

### Recommendation
Add an explicit "already in flight" check before inserting into `savedCallbacks`, consistent with the pattern already used in the `confidentialrelay`, `vault`, and v2 `http_trigger_handler` implementations — reject (with a JSON-RPC conflict/error response) any request whose `MessageId` collides with an existing unexpired entry rather than silently overwriting it: [1](#0-0) 

### Proof of Concept
1. Send `POST` to the Gateway user HTTP port with a legacy JSON-RPC request: `{"jsonrpc":"2.0","id":"X","method":"web_api_trigger","params":{<valid signed api.Message body with message_id "X">}}` as the victim — the request is forwarded to DON nodes and `savedCallbacks["X"]` is set to the victim's callback (see `HandleLegacyUserMessage`, lines 411-414).
2. Before the DON node responds, send another well-formed request with the same `message_id = "X"` signed by the attacker's own key — this overwrites `savedCallbacks["X"]` with the attacker's callback (no uniqueness check exists in this code path, unlike `vault`/`confidentialrelay`/v2 trigger handlers, which explicitly test for and reject `"duplicate request ID"`, as seen in `http_trigger_handler_test.go` lines 317-355).
3. When the DON node's response for the victim's request arrives (still tagged with `MessageId = "X"`), `handleWebAPITriggerMessage` (lines 148-162) retrieves `savedCallbacks["X"]`, now bound to the attacker's callback, and sends the victim's response there.
4. The attacker's HTTP call returns response content generated from the victim's request/DON interaction; the victim's original HTTP call times out.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
