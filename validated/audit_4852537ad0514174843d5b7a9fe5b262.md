### Title
Loss-epoch withdraw receipts escape their haircut when `lastWithdrawRequest` is overwritten by a newer request — (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault` indexes `lossRecoveryPriceByEpoch` by `lastWithdrawRequest[_user]`, a single storage slot that is overwritten on every new `requestWithdraw`. A user holding a receipt from a loss-adjusted epoch (`stopEpochWithDuration(_lossAmount)`) can make any subsequent withdraw request, which moves `lastWithdrawRequest` to an epoch with no loss price. The old receipt then skips `_claimLossAdjustedWithdrawRequest` entirely while remaining in the `withdrawsRequests[_user]` aggregate, and is paid at par by `_claimFundedWithdrawRequest`. This is the vault analog of a path-traversal escape: a claim "walks out" of its containing epoch boundary and is settled under a different (full-price) bucket than the one it was funded for.

### Finding Description
In `requestWithdraw`, the vault writes `lastWithdrawRequest[_user] = currentEpoch` unconditionally [1](#0-0) . When an epoch ends with a loss, `lossRecoveryPriceByEpoch[lossEpoch]` is set and `pendingWithdraws` is cleared after the borrower funds only the haircut-adjusted amount [2](#0-1) . But `_claimLossAdjustedWithdrawRequest` only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the latest epoch — and `_clearWithdrawClaimForEpoch` clears only the piece for that keyed epoch, leaving the loss-epoch amount inside `withdrawsRequests[_user]` [3](#0-2) . On the next claim after `epochNumber > lastWithdrawRequest[_user]`, `_claimFundedWithdrawRequest` computes `normalAmount = withdrawsRequests[_user]`, which still includes the un-haircutted loss-epoch basis, burns it, and transfers it at par [4](#0-3) . The `_transferFundedClaim` reserve guard only protects `defaultRecoveryReserve`; it does not constrain the funded bucket to the haircut-adjusted amount actually sourced from the borrower [5](#0-4) .

### Impact Explanation
The attacker withdraws (at par) funds that were funded only at `lossRecoveryPrice` for their epoch. The excess is paid out of strategy underlyings belonging to other funded claimants, instant-withdraw reserves, or new depositors, breaking the loss-waterfall invariant (loss socialization is bypassed for that receipt) and causing direct insolvency/loss for other users equal to `receipt × (1 − lossRecoveryPrice/RECOVERY_FULL)`.

### Likelihood Explanation
Requires an unprivileged tranche holder who (a) requested withdraw in the epoch that ends via `stopEpochWithDuration` with `_lossAmount > 0`, and (b) places a second withdraw request in any later epoch before claiming. No privileged role is needed; sequencing is entirely attacker-controlled. One caveat I could not fully verify within the available context: whether a post-loss vault still accepts new `requestWithdraw` calls and continues epochs normally (i.e., the vault is not defaulted or closed); if new requests are blocked after a loss epoch, the escape path is unreachable and this reduces to a permanent-freeze of the orphaned receipt instead.

### Recommendation
Key loss-adjusted claims by the epoch each receipt was created in (already tracked in `withdrawsRequestsByEpoch`) rather than by `lastWithdrawRequest`. Either iterate the user's request epochs, or store a per-user loss-epoch marker, so a loss-adjusted receipt can never be re-settled at par via the funded-claim path.

### Proof of Concept
Foundry fork PoC sketch: deposit via `idleCDO.depositAA`, `startEpoch`, `requestWithdraw` (epoch N). Manager calls `stopEpochWithDuration` with `_lossAmount > 0` so `lossRecoveryPriceByEpoch[N]` is set. Attacker calls `requestWithdraw` again in epoch N+1 (overwrites `lastWithdrawRequest`). Let epoch N+1 end normally (`epochNumber > lastWithdrawRequest`). Attacker calls `cdoEpoch.claimWithdrawRequest()`; `_claimLossAdjustedWithdrawRequest` returns 0 (no loss price at N+1), then `_claimFundedWithdrawRequest` pays `withdrawsRequests[user]` — including the epoch-N basis — at par. Assert `underlyingReceived > basis_N × lossRecoveryPriceByEpoch[N] / RECOVERY_FULL`.

I was unable to read the `lossRecoveryPriceByEpoch` setter and the post-loss epoch-transition logic within my tool-call budget, so reachability under all vault modes is not fully confirmed.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;

      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
