### Title
Loss-adjusted withdraw receipts misclaim at par because `lossRecoveryPriceByEpoch` is keyed by the post-`stopEpoch` epoch while `lastWithdrawRequest` stores the request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the realized loss-recovery price under `lossRecoveryPriceByEpoch[epochNumber]`, but `_claimLossAdjustedWithdrawRequest` looks it up under `lastWithdrawRequest[_user]`, which was set to the epoch in which the user called `requestWithdraw`. Because `epochNumber` is incremented inside `deposit()` while the epoch is still running (i.e., during `stopEpoch` processing), the stored key is `requestEpoch + 1` while the lookup key is `requestEpoch`. The loss-adjusted claim path therefore never matches and the receipt falls through to `_claimFundedWithdrawRequest`, which pays the full un-haircutted `withdrawsRequests[_user]` basis at par.

### Finding Description
The Linux bug class is "consume a report's fields without validating that they belong to the expected item". The analog here is epoch-indexed claim data consumed under the wrong index:

- `requestWithdraw` records `lastWithdrawRequest[_user] = epochNumber` (request epoch) and accrues `withdrawsRequests[_user]`.
- On `stopEpoch`, `IdleCDOEpochVariant` calls `strategy.deposit(...)`, which executes `epochNumber += 1` while `isEpochRunning()` is still true (IdleCreditVault.sol:607-611), and later calls `collectWithdrawFunds(_amount)`.
- When the borrower under-funds (`_amount < pendingWithdraws`), the loss price is stored at `lossRecoveryPriceByEpoch[epochNumber]` — the already-incremented epoch (IdleCreditVault.sol:417-421).
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (IdleCreditVault.sol:790-791), i.e., the pre-increment epoch, finds `0`, and returns without clearing anything.
- `claimWithdrawRequest` then proceeds to `_claimFundedWithdrawRequest`, whose gate `epochNumber <= lastWithdrawRequest[_user]` passes once one further epoch elapses, and pays `withdrawsRequests[_user]` — the full pre-haircut basis — at par, burning only that amount of receipt tokens (IdleCreditVault.sol:319-349).

The epoch that actually carries the loss price is unreachable for that user unless they submit a *new* withdraw request in epoch `requestEpoch + 1`, which would overwrite `lastWithdrawRequest` to the correct key but also roll their receipt into a fresh wait period.

### Impact Explanation
The realized loss that `stopEpoch` assigned to pending receipts is never applied. Affected users claim their full basis at par while the strategy only collected `pendingToFund < pendingBasis` underlyings. The shortfall is paid out of strategy-held underlying that backs other claims (funded receipts, default reserve, APR0 buckets), transferring the haircut loss to later claimants. Once the strategy balance is drained below remaining funded claims, `_transferFundedClaim` reverts, permanently freezing the residual claims. Quantified loss: `pendingBasis - pendingToFund` = the entire loss share that `previewLossAdjustedWithdrawFunds` allocated to pending receipts, stolen or rendered unclaimable.

### Likelihood Explanation
Trigger conditions are ordinary protocol operation: a `stopEpoch` in which the borrower funds less than `pendingWithdraws` (i.e., any `stopEpochWithDuration`-style loss while withdraw receipts are pending). Any unprivileged user with a pending withdraw receipt in that epoch then claims at par. No privileged misbehavior is required; the honest manager/borrower sequence alone creates the mispriced claim. Caveat: I could not execute a fork test in this session, so the exact call ordering inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` (specifically whether `deposit`/`epochNumber` increment precedes `collectWithdrawFunds` in all paths) should be confirmed on a fork before treating this as final.

### Recommendation
Key `lossRecoveryPriceByEpoch` by the same epoch the receipts were created in — i.e., store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or capture the pre-increment epoch) inside `collectWithdrawFunds`, mirroring how `withdrawsRequestsByEpoch[_user][currentEpoch]` is written at request time. Alternatively, validate in `_claimLossAdjustedWithdrawRequest` that a non-zero loss price exists for any epoch present in `withdrawsRequestsByEpoch[_user]`, not just `lastWithdrawRequest[_user]`, so no receipt can silently bypass its haircut.
