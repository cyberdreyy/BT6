### Title
Deleverage withdraw-limit bypass via price=0 when group rate limiter is disabled - ([File: programs/marginfi/src/instructions/kamino/withdraw.rs])

### Summary
In `kamino_withdraw`, the oracle price used to value a withdrawal is only fetched when the account is in receivership/order-execution **or** the group's rate limiter is enabled; the `ACCOUNT_IN_DELEVERAGE` flag is not included in that condition. When the rate limiter is disabled, `price` defaults to `I80F48::ZERO`, so the subsequent deleverage outflow check computes `withdrawn_equity = calc_value(collateral_amount, 0, ...) = 0`, trivially satisfying `group.check_deleverage_withdraw_limit`.

### Finding Description
The price-fetch gate is: [1](#0-0) 

Note that `in_receivership_or_order_execution` checks only `ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION`, and the zero-price safety assertion (`check!(price > I80F48::ZERO, ...)`) is likewise gated only on that condition, not on `ACCOUNT_IN_DELEVERAGE`. If `group.rate_limiter.is_enabled()` is `false` and the account is only flagged `ACCOUNT_IN_DELEVERAGE` (not receivership/order-execution), `price` stays `I80F48::ZERO` with no zero-price guard applied.

Downstream, the deleverage outflow cap explicitly relies on this same `price` variable: [2](#0-1) 

With `price == 0`, `calc_value` returns `0` regardless of `collateral_amount`, so `check_deleverage_withdraw_limit(0, ...)` is satisfied for arbitrarily large withdrawals, defeating the cap the check is meant to enforce. The account-authority gate (`is_signer_authorized`) permits the normal account authority to sign this instruction; there is no indication that `ACCOUNT_IN_DELEVERAGE` alone freezes the account for its own authority the way receivership/order-execution flags do, so a user whose account carries only the `ACCOUNT_IN_DELEVERAGE` flag can repeatedly call `kamino_withdraw` with `flags=0` (skipping `withdraw_all`) to drain collateral without the outflow limiter ever recording a non-zero USD value.

The same pattern (identical price-gating logic) appears to be duplicated across the other integration withdraw instructions (`drift/withdraw.rs`, `juplend/withdraw.rs`, `solend/withdraw.rs`, `marginfi_account/withdraw.rs`), which use the same `ACCOUNT_IN_DELEVERAGE` flag; I was not able to fully re-verify each of those files line-by-line in this pass, but the same class of gap likely exists there since they share the flag list.

### Impact Explanation
The deleverage withdraw limiter exists specifically to bound how much USD value can be extracted from a bank while an account is being force-unwound. Bypassing it lets the account holder pull far more value out during deleverage than the protocol's guardrail intends, corrupting expected bank/group outflow accounting and potentially extracting bank liquidity beyond the amount the deleverage process was designed to permit — a direct value-extraction and accounting-integrity issue, not merely a liquidity or oracle-freshness concern.

### Likelihood Explanation
The trigger conditions are fully attacker-controllable/observable and require no privileged access to exploit once the account is already `ACCOUNT_IN_DELEVERAGE` and the group rate limiter is disabled (`group_rate_limiter.is_enabled() == false` is a normal/likely group configuration, not an edge case). The exploit is simply calling `kamino_withdraw(amount, flags=0)` repeatedly with the account's own authority — no special account metas, oracle manipulation, or admin action needed at call time.

### Recommendation
Include `ACCOUNT_IN_DELEVERAGE` in the price-fetch and zero-price-guard condition, e.g. change:
```rust
let in_receivership_or_order_execution =
    marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION);
```
to also OR in `ACCOUNT_IN_DELEVERAGE` (or introduce a combined "requires real price" flag set), so that whenever the deleverage-outflow check will run, a real oracle price is fetched and validated non-zero (`check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice)`) regardless of the group rate limiter's enabled state. Apply the same fix consistently to `drift/withdraw.rs`, `juplend/withdraw.rs`, `solend/withdraw.rs`, and `marginfi_account/withdraw.rs` if they share this pattern.

### Proof of Concept
Rust unit/integration test plan:
1. Set up a `MarginfiGroup` with `rate_limiter.is_enabled() == false`.
2. Create a `MarginfiAccount` with a Kamino collateral balance and set `ACCOUNT_IN_DELEVERAGE` flag (without `ACCOUNT_IN_RECEIVERSHIP`/`ACCOUNT_IN_ORDER_EXECUTION`).
3. Call `kamino_withdraw` with a large `amount` and `flags = 0`.
4. Assert that `price` computed inside the instruction is `I80F48::ZERO` (verifiable via emitted `DeleverageWithdrawFlowEvent.outflow_usd == 0`).
5. Assert `group.check_deleverage_withdraw_limit` succeeds despite the large token amount withdrawn, and that repeated calls never accumulate any nonzero outflow in the deleverage tracker — demonstrating the cap is not enforced.
6. Compare against expected behavior: outflow tracker should accumulate `collateral_amount * real_oracle_price` and eventually reject withdrawals once the deleverage cap is exceeded.
