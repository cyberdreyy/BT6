### Title
Stale confirmations from removed multisig members/keys count toward the confirmation threshold, allowing requests to execute with fewer live approvals than required - (File: multisig2/src/lib.rs, multisig/src/lib.rs)

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` implement a K-of-N confirmation scheme where a request executes once `confirmations.len() >= num_confirmations`. When a member/key is removed via `DeleteMember`/`DeleteKey`, the code only purges *requests originated by* that member, but does not strip that member's prior *confirmations* recorded on other still-pending requests. Those stale confirmations remain in the `confirmations` set and continue to count toward the threshold, breaking the invariant that `confirmations counted == confirmations from currently live members`.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [2](#0-1) 

`delete_member()` removes a member from `self.members` and deletes outstanding requests, but the filter only matches requests where `r.member == member`, i.e. requests the removed member *originated* — not requests the removed member merely *confirmed*: [3](#0-2) 

Consequently, if member B confirms request X (created by member A) while B is still a live member, and later B is removed from the multisig via a separate `DeleteMember` request, request X's `confirmations` set still contains B's identifier. When a third live member later confirms request X, B's stale confirmation still counts toward `num_confirmations`, so the request can execute having received explicit approval from only 2 *live* members even though the multisig is configured to require 3.

The equivalent flaw exists in the original `multisig/src/lib.rs`, where `DeleteKey` purges only requests signed (originated) by the removed key, leaving that key's confirmations on other requests intact: [1](#0-0) [4](#0-3) 

The binding that should hold is: `confirmations counted toward threshold == confirmations from accounts currently in self.members`. After a `DeleteMember`/`DeleteKey` action, this equality is violated for any request that the removed member had confirmed before removal but that had not yet reached the threshold.

### Impact Explanation
This crosses an authorisation boundary: a multisig configured for K-of-N approval from *current* members can end up executing a request (including `Transfer`, `AddKey`/`AddMember`, `DeployContract`, `FunctionCall`) with fewer than K live approvals. A member removed for being compromised, malicious, or simply offboarded can still have their earlier vote count toward passing a pending malicious/contentious request, effectively allowing NEAR transfers or privilege changes (e.g. adding a full access key) to be executed below the intended threshold. This matches the "multisig request executed below threshold" Critical impact category.

### Likelihood Explanation
Exploitation requires only ordinary multisig operation: a member confirms a request, is later removed via a normal `DeleteMember`/`DeleteKey` governance action (no owner or foundation privilege beyond being an existing member, which is the standard operating model of this contract), and the pending request is later confirmed by remaining members. No malicious deployment or redeploy is needed — it's a natural consequence of the existing `delete_member`/`DeleteKey` cleanup logic being incomplete.

### Recommendation
When removing a member/key, iterate over all pending requests' `confirmations` sets (not just requests originated by that member) and remove the departing member's/key's confirmation entry from each. Alternatively, recompute `confirmations.len()` in `confirm()` by intersecting with the current `self.members` set before comparing against `num_confirmations`, ensuring stale confirmations from removed members never count toward the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `X` (e.g. `Transfer` of funds to an attacker-controlled account), then `A` calls `confirm(X)` → `confirmations = {A}` (1/3).
3. `B` calls `confirm(X)` → `confirmations = {A, B}` (2/3, threshold not met, request stays pending).
4. Separately, member `B` is removed via a `DeleteMember` request (`add_request_and_confirm` reaching threshold with the then-current members) — see `delete_member` at `multisig2/src/lib.rs:356-379`, which only clears requests where `r.member == B`, so request `X`'s confirmation set `{A, B}` is untouched.
5. Now only `A, C, D` are live members, and the multisig still requires 3 confirmations, i.e. all 3 live members should be needed for any future request.
6. `C` calls `confirm(X)` → `confirmations.len() + 1 == 3 >= num_confirmations`, so request `X` executes — even though only `A` and `C` are live members who explicitly approved it; `B`'s stale, now-invalid confirmation supplied the missing vote, letting the transfer execute with only 2 of 3 required live approvals.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {

        // delete outstanding requests by public_key
