### Title
Loss-adjusted withdraw receipts keyed by a stale epoch index let claimants withdraw at par after a realized loss - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary

The external report describes a heap buffer over-read: code reads state through an index outside the data actually written. The analog in `IdleCreditVault` is a stale-epoch index read: loss-adjusted withdraw receipts are *written* under `lossRecoveryPriceByEpoch[epochNumber]` inside `collectWithdrawFunds`, but *read* through `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` in `_claimLossAdjustedWithdrawRequest` and in the `requestWithdraw` guard. `epochNumber` is incremented inside `deposit()` during `stopEpoch`, while `lastWithdrawRequest` was stamped with the pre-increment epoch. If the CDO calls `collectWithdrawFunds` after the epoch-bumping deposit, the haircut is stored under an epoch no user maps to, and every haircutted receipt is subsequently paid at par from underfunded reserves.

### Finding Description

Relevant code paths:

- `requestWithdraw` stamps `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` read during the buffer phase (IdleCreditVault.sol:260-282).
- `deposit()` increments `epochNumber` when it is invoked while `isEpochRunning()` is still true, i.e. inside `stopEpoch` (IdleCreditVault.sol:607-611).
- `collectWithdrawFunds(_amount)` stores the haircut as `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` when `_amount < pendingBasis` (IdleCreditVault.sol:411-421).
- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — the epoch stamped *before* the increment (IdleCreditVault.sol:789-801).
- `requestWithdraw`'s re-request guard performs the same keyed read (IdleCreditVault.sol:261-271).

If in `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration` the ordering is `deposit()` (which bumps `epochNumber` to N+1) before `collectWithdrawFunds`, then the loss price is stored at index N+1 while all affected receipts carry `lastWithdrawRequest = N`. The claim path then sees `lossRecoveryPrice == 0`, skips the haircut path entirely, and falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` in full at par (IdleCreditVault.sol:319-349, 897+) even though only the haircutted `_amount` was collected.

The same misalignment affects `apr0RateByEpoch[epochNumber]` written in `prepareStopEpochWithApr0` (line 537) versus `apr0RateByEpoch[_reqEpoch]` read in `_settleApr0` (line 558): if `prepareStopEpochWithApr0` runs before the `deposit()` bump, the rate is written at N and read at N (correct); the ordering-sensitive inconsistency across the two flows is the fragility.

### Impact Explanation

Direct insolvency/theft of reserve: users with loss-adjusted receipts claim their un-haircutted principal at par, paying out more underlying than the borrower funded in `collectWithdrawFunds`. Early claimants drain underlying belonging to other pending receipts, default recovery reserve, or LPs; later claimants' claims revert on insufficient balance (permanent freezing of the residual claims). Loss realized via `stopEpochWithDuration` is silently re-socialized onto unrelated claims instead of the pending withdraw bucket.

### Likelihood Explanation

The trigger is a single ordering decision inside `stopEpochWithDuration` in `IdleCDOEpochVariant.sol` (call `deposit`/accounting before `collectWithdrawFunds`). I was unable to fully confirm the intra-`stopEpoch` call ordering in `IdleCDOEpochVariant.sol` within this session — the grep matched the file but did not return the body — so this finding is conditional on `collectWithdrawFunds` executing after the `epochNumber += 1` in `deposit()`. If the order is reversed (collect before bump), the keys align and the bug does not manifest; conversely, if `collectWithdrawFunds` runs after the bump, no existing guard detects the mis-keyed write because `requestWithdraw`'s own guard uses the same stale index.

### Recommendation

Key the loss record by the request epoch rather than the post-increment counter. Either capture `epochNumber` before the `deposit()` bump and pass it to `collectWithdrawFunds`, or have `collectWithdrawFunds` accept an explicit epoch parameter from the CDO that equals `lastWithdrawRequest` semantics (the epoch requests were made in). Add an invariant test: after `stopEpochWithDuration` with a partial loss, `lossRecoveryPriceByEpoch[user's lastWithdrawRequest] != 0` for every user with a pending receipt in that epoch.

### Proof of Concept

```solidity
// SPDX-License-Identifier: AGPL-3.0
pragma solidity 0.8.10;

import {IdleCreditVault} from "../../contracts/strategies/idle/IdleCreditVault.t.sol"; // reuse fixtures

contract LossEpochMiskeyPoC is IdleCreditVaultTest {
    function testLossReceiptPaysParAfterEpochBump() external {
        uint256 amountWei = 10_000 * ONE_SCALE;
        idleCDO.depositAA(amountWei);
        _startEpochAndCheckPrices(0);              // epoch 0 running

        // buffer phase: user requests withdraw, lastWithdrawRequest[user] = 1
        _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());
        cdoEpoch.requestWithdraw(0, address(AAtranche));
        IdleCreditVault strat = IdleCreditVault(address(strategy));
        uint256 reqEpoch = strat.lastWithdrawRequest(address(this));
        uint256 basis = strat.withdrawsRequests(address(this));

        _startEpochAndCheckPrices(1);

        // stopEpochWithDuration with a partial loss: borrower funds < pendingBasis
        uint256 pendingBasis = strat.pendingWithdraws();
        uint256 funded = pendingBasis / 2;
        deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
        vm.warp(cdoEpoch.epochEndDate() + 1);
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(initialProvidedApr, pendingBasis - funded);

        // BUG: haircut was stored at the bumped epoch, not reqEpoch
        assertEq(strat.lossRecoveryPriceByEpoch(reqEpoch), 0, "receipt epoch not keyed");

        uint256 balPre = underlying.balanceOf(address(this));
        cdoEpoch.claimWithdrawRequest();
        // BUG: paid at par instead of basis * 50%
        assertEq(
            underlying.balanceOf(address(this)) - balPre,
            basis,
            "loss-adjusted receipt overpaid at par"
        );
    }
}
```

Note: this PoC assumes `collectWithdrawFunds` executes after the `epochNumber` increment inside `stopEpoch`/`stopEpochWithDuration`. If on inspection the order is reversed, the finding collapses to a latent fragility rather than an active bug; verify the call ordering in `IdleCDOEpochVariant.stopEpochWithDuration` before finalizing severity.
