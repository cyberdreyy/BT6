### Title
Demoted user's cached-role API token retains original elevated role until next `Work()` sync cycle - ([File: core/sessions/ldapauth/ldap.go], [File: core/sessions/ldapauth/sync.go])

### Summary
`FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` returns the `user_role` stored in `ldap_user_api_tokens` at token-creation time, with no per-request revalidation against the upstream LDAP directory. Role correction only happens inside `LDAPServerStateSyncer.Work()`'s CASE-WHEN UPDATE, which runs on a timer/interval, and `deleteStaleAPITokens` only purges rows by `created_at` age, never by staleness of role. This lets a token minted while the holder was Admin continue authorizing Admin-level API requests after the upstream role is downgraded, until the next successful `Work()` cycle completes.

### Finding Description
`CreateAndSetAuthToken`/`SetAuthToken` (`core/sessions/ldapauth/ldap.go:532-592`) snapshot `user.Role` into `ldap_user_api_tokens.user_role` at creation time. `AuthenticateByToken` (`core/web/auth/auth.go:78-112`) calls `FindUserByAPIToken` (`core/sessions/ldapauth/ldap.go:205-236`), which does a single SQL lookup: [1](#0-0) 

This query returns the cached `user_role` and only checks token *age* (`created_at + duration >= now()`) for expiry — it performs no upstream LDAP call and no comparison against a "last known good" role state. The role in the returned `sessions.User` is then trusted directly by `RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` in `core/web/auth/auth.go:200-255` to authorize the request.

The only mechanism that corrects a stale role is the CASE-WHEN `UPDATE ldap_user_api_tokens` statement inside `LDAPServerStateSyncer.Work()`: [2](#0-1) 

This only executes as part of the periodic/interval-driven `Work()` call (via `run()`'s ticker or a one-time `Start()` invocation), not per-request. The comment block at the top of `ldap.go` claims "This sync happens for every auth endpoint hit, and via the defined sync interval" — but no such per-request sync call exists in `AuthenticateByToken` or `FindUserByAPIToken`; the sync is exclusively interval-driven.

Additionally, `deleteStaleAPITokens` purges only by `created_at` age against `UserAPITokenDuration`: [3](#0-2) 

It performs no check tied to a role-downgrade event, so a token minted just before this age threshold retains its original elevated role snapshot for its entire remaining lifetime unless a `Work()` cycle happens to run and match/update it.

### Impact Explanation
This is a revocation-lag / stale-privilege authorization bypass: a user who is demoted upstream (e.g., Admin → View) keeps working Admin-scoped API access via their existing token for the duration between the demotion and the next successful `Work()` sync cycle. Depending on `UpstreamSyncInterval`/`UpstreamSyncRateLimit` configuration, this window can be long, during which the token can be used to call admin-gated routes (job management, key management, etc.), matching the "role/authorization bypass" and "stale privileged credential usable past revocation" impact classes.

### Likelihood Explanation
Preconditions: the holder must have previously been granted a valid `ldap_user_api_tokens` row while at a higher role (via `CreateAndSetAuthToken`) and subsequently be demoted upstream. No admin/host/database access is required — only possession of a previously-issued, still-cryptographically-valid token. This is fully reproducible: it depends solely on the deterministic gap between demotion and the next `Work()` invocation, which is entirely feasible in any deployment using non-zero `UpstreamSyncInterval`/`UpstreamSyncRateLimit`.

### Recommendation
Revalidate role (or at minimum re-check upstream/DB state) on every `FindUserByAPIToken` call, or shrink/eliminate the gap by triggering an on-demand sync for the specific user on token lookup instead of relying purely on the interval-based `Work()` job. Alternatively, track a "last verified" timestamp per token and force a synchronous re-check against `ldap_sessions`/upstream state if the cached role's verification is older than a small threshold, decoupled from the full `UserAPITokenDuration` expiry window.

### Proof of Concept
1. Unit test in `core/sessions/ldapauth/ldap_test.go`: seed `ldap_user_api_tokens` with `user_email='alice@example.com'`, `user_role=UserRoleAdmin`, valid `token_key`/`token_hashed_secret`, `created_at=now()`.
2. Call `ldapAuthenticator.FindUserByAPIToken(ctx, token)` and assert returned `sessions.User.Role == UserRoleAdmin`.
3. Mock the LDAP client (`LDAPClient`/`LDAPConn` mocks already present in the package) so that `ldapGroupMembersListToUser` for the Read/View group returns `alice@example.com` and Admin group returns empty (simulating upstream demotion), without invoking `Work()`.
4. Re-call `FindUserByAPIToken` — assert it still returns `UserRoleAdmin`, proving no per-request revalidation occurs.
5. Now invoke `LDAPServerStateSyncer.Work(ctx)` against the same DB/mock LDAP client, then re-call `FindUserByAPIToken` — assert role is now `UserRoleView`, confirming the correction only happens through the interval-driven `Work()` path and never in the auth request path itself.
