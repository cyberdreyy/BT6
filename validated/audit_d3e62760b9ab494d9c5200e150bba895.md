### Title
Loss-adjusted withdraw receipts can be claimed at par in a later epoch, letting an unbacked claim drain funded vault assets - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Secret Network analog is "the contract asks whether the denom is supported, not whether the packet is authorized." Here, `claimWithdrawRequest` asks only whether the *latest* request epoch carried a loss (`lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`), not whether *each* epoch's receipts were actually funded. If a user's receipt belongs to an epoch that was only partially funded by the borrower via `collectWithdrawFunds` (a `stopEpochWithDuration` loss), a subsequent withdraw request in a later, fully-funded epoch moves `lastWithdrawRequest` forward. The old loss-epoch basis remains inside the aggregate `withdrawsRequests[_user]` and is then paid at par by `_claimFundedWithdrawRequest`, even though the strategy only received the haircut amount.

### Finding Description
In `IdleCreditVault.sol`:

- When the borrower underfunds pending receipts, `collectWithdrawFunds(_amount)` with `_amount < pendingBasis` stores `lossRecoveryPriceByEpoch[epoch]` and clears `pendingWithdraws`, but it does **not** touch `withdrawsRequests[_user]` or `withdrawsRequestsByEpoch[_user][epoch]`. Each user's nominal claim basis survives.
- `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which only inspects `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — a single epoch, the user's *most recent* one.
- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch`, overwriting the pointer. Any earlier loss-epoch basis becomes unreachable by `_claimLossAdjustedWithdrawRequest` and is silently folded into the funded path.
- `_claimFundedWithdrawRequest` then pays `amount = withdrawsRequests[_user] + apr0Principal + apr0Interest` in full via `_transferFundedClaim`, which performs no per-epoch funding check — it only guards against spending `defaultRecoveryReserve`.

So a receipt that should be paid at `claimBasis * lossRecoveryPrice / RECOVERY_FULL` is instead paid at `claimBasis`, i.e., `(1 - lossRecoveryPrice) * claimBasis` of unbacked underlying is transferred out.

Sequence (epoch phases, unprivileged tranche holder):

1. Epoch N running → borrower defaults partially → `stopEpochWithDuration` collects less than `pendingWithdraws`; `lossRecoveryPriceByEpoch[N] = r < 1`. User had requested a withdraw in epoch N (basis `B`).
2. Epoch N+1 buffer: user calls `requestWithdraw` again (or the CDO calls it on their behalf via the queue) with any amount → `lastWithdrawRequest[user] = N+1`.
3. Epoch N+2 (after `epochNumber > N+1`): user calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` sees `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0; `_claimFundedWithdrawRequest` pays `B + newBasis` at par, burning only the minted receipt tokens.
4. The `(1 - r) * B` shortfall is taken from strategy-held underlyings belonging to other claimants / the pool, since `_burn` only destroys the user's receipt tokens, not the funding gap.

Guards that do not stop it: `_onlyIdleCDO` is satisfied via `IdleCDOEpochVariant.claimWithdrawRequest`; the epoch-wait check in `_claimFundedWithdrawRequest` passes because `epochNumber > N+1`; the reserve guard in `_transferFundedClaim` is irrelevant pre-default-finalization. There is no per-epoch funding verification anywhere in the funded-claim path.

### Impact Explanation
Direct theft / insolvency: the attacker extracts `(1 - lossRecoveryPrice) * claimBasis` more underlying than their receipt was funded for. The strategy's actual funded cash for that epoch was only `r * pendingBasis`; paying full basis to one user drains underlying backing other users' receipts, breaking solvency and the one-receipt-one-funded-payout invariant. Loss scales linearly with the attacker's loss-epoch claim size, up to the entire unfunded gap.

### Likelihood Explanation
Requires only an unprivileged tranche holder with a pending receipt in a partially-funded epoch (a `stopEpochWithDuration` loss is a normal, supported code path — `lossRecoveryPriceByEpoch` exists precisely for it) and the ability to make one more `requestWithdraw` in a later epoch, which the code explicitly supports ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch"). No privileged cooperation needed.

### Recommendation
Track loss-adjusted claims per epoch rather than keying off `lastWithdrawRequest`. Options: store the loss-epoch pointer per user (e.g., a separate `lossEpochByUser` that `requestWithdraw` does not overwrite until the loss claim is cleared), or have `_claimFundedWithdrawRequest` subtract any `withdrawsRequestsByEpoch[user][e]` whose `lossRecoveryPriceByEpoch[e] != 0` before paying at par, or iterate/clear all epochs with nonzero `lossRecoveryPriceByEpoch` in `_claimLossAdjustedWithdrawRequest`. Minimal fix: in `_clearWithdrawClaimForEpoch`/`_withdrawClaimAmountsForEpoch`, exclude epochs with a stored recovery price from the aggregate funded amount.

### Proof of Concept
```solidity
// Foundry fork-style PoC sketch (vault = IdleCDOEpochVariant + IdleCreditVault strategy)
// Setup: deposit as user, request withdraw in epoch N; borrower underfunds at stop.

// epoch N: user requests withdraw of basis B
vm.prank(user);
cdo.requestWithdraw(trancheAmt, AAtranche); // mints B receipt tokens to user
// stop epoch with partial funding: funded = r * pendingBasis
vm.prank(manager);
cdo.stopEpochWithDuration(duration, interest, fundedAmount); // lossRecoveryPriceByEpoch[N] = r

// epoch N+1 buffer: user files any new withdraw request
vm.prank(user);
cdo.requestWithdraw(dust, AAtranche);       // lastWithdrawRequest[user] = N+1

// run epoch N+1 to completion (fully funded or small)
// epoch N+2:
vm.prank(user);
cdo.claimWithdrawRequest();
// expected (correct): B * r / 1e18 + newClaim
// actual: B + newClaim -> excess = B * (1 - r) pulled from strategy balance
assertGt(underlying.balanceOf(user), B * r / 1e18 + newClaim);
```
Caveat I could not fully verify within the iteration limit: whether `requestWithdraw` is callable while a loss-adjusted receipt from a prior epoch is still pending (there may be a `_hasWithdrawRequest`-style gate I did not see). If such a gate exists, the attack surface narrows to paths that create a second request on the user's behalf (e.g., the epoch queue's `processWithdrawRequests`, which calls `_cdo.requestWithdraw` for the queue contract).
