### Title
Deposit cancellation fee can be trivially bypassed by choosing a minimal `deadline` - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.cancelRequest` only charges the deposit/redeem cancellation fee when `block.timestamp < request.deadline`, and `_validateRequest` places no lower bound on the user-supplied `deadline` beyond `deadline > block.timestamp`. An ordinary user can create an async deposit request with the minimum possible deadline, wait for the deadline to elapse, then call `cancelRequest` (or the fully permissionless `refundRequest`) to reclaim 100% of the escrowed tokens with zero cancellation fee, defeating the fee mechanism entirely — the same class of bug as the Y2K report, where a user routes a "would-be-fee-charged" action through an alternate, fee-free code branch that is gated only by a value the user fully controls.

### Finding Description
`requestDeposit` (`v3/src/core/ProvisionerV2.sol:764-809`) calls `_validateRequest`, which only requires `deadline > block.timestamp` and `deadline - block.timestamp <= MAX_SECONDS_TO_DEADLINE` [1](#0-0) . There is no minimum deadline window enforced, so a user can pick `deadline = block.timestamp + 1`.

In `cancelRequest`, the deposit cancellation fee is only applied when `block.timestamp < request.deadline` at the time of cancellation [2](#0-1) . Because the user fully controls `deadline` and can simply wait one block/second for it to elapse, they can guarantee this branch is skipped and receive `refundAmount = request.tokens` in full — no fee ever transferred to `MULTI_DEPOSITOR_VAULT`. The permissionless `refundRequest` function has the identical effect once `request.deadline < block.timestamp`, requiring no special authorization at all [3](#0-2) .

This mirrors the Y2K root cause: an intended fee (there, the vault deposit fee; here, the deposit/redeem cancellation fee) is only charged on one code path, while a functionally-equivalent alternate path — reachable by any ordinary user by manipulating a parameter they fully control (there, `_id`; here, `deadline`) — skips the fee guard entirely.

### Impact Explanation
Any user can request-then-cancel deposits (or redeems, via the analogous `_computeRedeemCancellationFeeUnits` branch guarded the same way) repeatedly while never paying the configured `_depositCancellationFeeNumeraire`/`_redeemCancellationFeeNumeraire`, denying the vault (and thus other unit holders) the fee revenue the mechanism is designed to collect. This is a fee-bypass rather than direct fund theft; the practical loss is unclaimed protocol/vault fee revenue that should have accrued to unit holders.

### Likelihood Explanation
Requires only that deposit (or redeem) cancellations are enabled with a non-zero cancellation fee — no privileged role, oracle manipulation, or third-party dependency needed. Any user can trivially set `deadline = block.timestamp + 1` and wait a single block before calling `cancelRequest`, or rely on the fully public `refundRequest` once the deadline has passed. This is deterministic and repeatable.

### Recommendation
Decouple the fee determination from `deadline` expiry games: e.g., always charge the cancellation fee for any self-initiated `cancelRequest`/`refundRequest` occurring before the request has actually been considered by a solver, enforce a protocol-wide minimum deadline window (`MIN_SECONDS_TO_DEADLINE`) large enough that "waiting out the deadline" is not a viable free-cancellation strategy, or charge the cancellation fee based on request creation time rather than the user-chosen deadline.

### Proof of Concept
1. Admin enables deposit cancellations with `depositCancellationFeeNumeraire > 0` via `setCancellationDetails`.
2. Attacker calls `requestDeposit(token, tokensIn, 1, 0, deadline = block.timestamp + 1, maxPriceAge, true, attacker)`. Tokens are escrowed in the provisioner.
3. `vm.warp(block.timestamp + 2)` (simulate the next block, deadline now elapsed).
4. Attacker calls `cancelRequest(token, request)`. Assert: `refundAmount == request.tokens` (full refund) and no `IERC20.safeTransfer` to `MULTI_DEPOSITOR_VAULT` occurred, i.e., no fee charged, compared to calling `cancelRequest` before the deadline where `refundAmount < request.tokens`.

Note: I was unable to fully confirm whether this fee-skip-after-deadline behavior is an accepted design trade-off (i.e., the fee is only meant to penalize cancellation of a request that is still "live" and solvable) versus an unintended bypass, since I do not have access to Aera's own threat model/documentation for this fee. This uncertainty should be resolved before treating it as conclusively exploitable under the bounty's Medium severity bar.
