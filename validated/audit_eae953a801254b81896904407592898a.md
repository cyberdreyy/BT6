### Title
Permanent freeze of `stopEpoch` via ERC4626 coverage/withdraw mismatch in `ProgrammableBorrower.onStopEpoch` - (contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The external advisory is a boundary-crossing bug: a value that looks valid inside the trusted context fails (throws) the moment it is materialized across the bridge, and the exception smuggles execution into the privileged side. The analog in idle-tranches is `ProgrammableBorrower.onStopEpoch`, where the ERC4626 vault's *reported* coverage (`convertToAssets`, i.e. `_currentVaultAssets()`) and its *executable* liquidity (`vault.withdraw`) are two different "serializations" of the same value. When they diverge — shares report enough coverage but the withdrawal reverts — the hook reverts with `StopEpochVaultLiquidityUnavailable` before returning `false`, so `IdleCDOEpochVariant` can never reach `_handleBorrowerDefault` and `stopEpoch` is bricked for as long as the vault stays illiquid.

### Finding Description
In `ProgrammableBorrower.onStopEpoch`, when `IdleCDO` needs more cash than the borrower holds, the contract decides the failure mode by comparing the shortfall to the vault's *valued* assets: [1](#0-0) 

Two paths exist:
- `shortfall > _currentVaultAssets()` → return `true`, let the subsequent `transferFrom` inside `this.getFundsFromBorrower` fail, which `IdleCDOEpochVariant` catches and routes to `_handleBorrowerDefault` — the clean, terminal default path.
- `shortfall <= _currentVaultAssets()` but `vault.withdraw` reverts → `revert StopEpochVaultLiquidityUnavailable()`.

The second path bubbles a raw revert out of `onStopEpoch`. On the caller side, `IdleCDOEpochVariant.stopEpoch` invokes the hook before the `try this.getFundsFromBorrower(...)` guard: [2](#0-1) 

Because the hook reverts instead of returning `false`, `_handleBorrowerDefault` is never invoked and the whole `stopEpoch` transaction reverts. The comment claims this makes the failure "retryable", but retryability depends entirely on the external vault becoming liquid again — which is exactly what the attacker controls.

A generic ERC4626 (e.g. a MetaMorpho-style vault allocating into lending markets) can simultaneously satisfy:
- `convertToAssets(shares) >= shortfall` (share price/NAV intact), and
- `withdraw`/`redeem` reverts for lack of underlying liquidity (all supplied liquidity borrowed out of the underlying markets, or a market in bad-debt/withdrawal-queue state).

`_currentVaultAssets()` is a pure `convertToAssets` valuation with no liquidity check, so the accounting says "covered" while the transfer cannot execute — the same shape as the Electron bug: a return value that is representable in one context but throws when materialized in the other. `onDefault` explicitly avoids `convertToAssets` for stress robustness (contracts/strategies/idle/ProgrammableBorrower.sol:295-297), confirming the codebase recognizes this class — but `onDefault` is only reachable *through* `onStopEpoch`'s return value, which the revert prevents.

### Impact Explanation
While `stopEpoch` is bricked:
- `isEpochRunning` stays true, `epochEndDate` is in the past, and the pool cannot transition to buffer/stopped state. No new epoch can start (`startEpoch` requires the buffer check against `epochEndDate`), no withdraw requests can be filed (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` are false during the epoch), and `claimWithdrawRequest`/`claimInstantWithdrawRequest` settle nothing because no funds are ever collected from the borrower.
- Tranche principal and accrued yield — the entire pool NAV — remain frozen in the borrower/vault for the duration of the illiquidity. A motivated attacker (any user of the ERC4626 vault's underlying markets) can borrow out the vault's liquidity and refuse to repay, keeping `withdraw` reverting indefinitely while `convertToAssets` still reports full coverage. On a Morpho-type deployment this requires no privileged role: the attacker simply opens/maintains a borrow position in the markets the vault allocates to.
- The honest escape hatches do not help: `emergencyExitVault` calls `vault.redeem`, which hits the same liquidity wall; manager/owner cannot force the default path because `_handleBorrowerDefault` is gated behind the hook's boolean return, not behind vault liquidity.

This is temporary (potentially indefinite) freezing of the full pool NAV — an accepted impact class — with the frozen amount equal to the entire `getContractValue()` of the CDO.

### Likelihood Explanation
Requires a deployment in `isProgrammableBorrower` mode (minted-interest, prefunded variants with an ERC4626 sleeve) and a shortfall at stop time — i.e., any epoch where `expectedEpochInterest + pendingWithdraws` exceeds the borrower's on-hand balance, which is the normal case since idle funds are parked in the vault by `onStartEpoch`/`_depositToVault`. The attacker only needs to keep the underlying markets illiquid around the epoch end (publicly known `epochEndDate`, and `stopEpoch` is called openly by the manager). The cost is an open borrow position; on chains with public mempools the attacker can also front-run `stopEpoch` calls. The window need not be long to qualify — repeated `StopEpochVaultLiquidityUnavailable` reverts during a stressed epoch freeze all exits.

### Recommendation
Do not let vault liquidity failures veto the state transition. Options:
- In `onStopEpoch`, treat a failed `vault.withdraw` the same as insufficient coverage: return `false` (or a tri-state) so `IdleCDOEpochVariant` enters `_handleBorrowerDefault`, or
- Catch the withdraw failure and proceed with whatever liquidity was obtained, accounting the residual shortfall as a vault loss via `epochWithdrawnFromVault`/loss accounting, or
- Add an owner/manager escape on `IdleCDOEpochVariant` that forces `_handleBorrowerDefault` when `stopEpoch` has reverted N times or after a grace period past `epochEndDate`.
- At minimum, base the coverage check on real liquidity (e.g. `vault.maxWithdraw(address(this))`) rather than `convertToAssets`, so the reported value cannot diverge from what can actually cross the boundary.

### Proof of Concept
Foundry fork test (mirroring `test/foundry/ProgrammableBorrowerCreditVault.t.sol` setup):

```solidity
function testStopEpochFrozenWhenVaultIlliquidButCovered() external {
    uint256 amount = 10_000 * oneScale;

    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0);   // all funds parked into the ERC4626 vault

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Attacker (any vault-market borrower / vault user) makes the vault illiquid:
    // borrow out all underlying liquidity in the vault's markets so that
    // convertToAssets(shares) still reports full coverage but withdraw reverts.
    _drainMorphoVaultLiquidity();   // e.g. attacker borrows all market liquidity

    // Sanity: accounting says the position is covered
    assertGe(
        morphoVault.convertToAssets(morphoVault.balanceOf(address(programmableBorrower))),
        1,
        "shares report coverage"
    );
    // but the withdrawal itself cannot execute
    vm.expectRevert();
    morphoVault.withdraw(1, address(this), address(this));

    // stopEpoch reverts forever: onStopEpoch reverts StopEpochVaultLiquidityUnavailable
    // instead of returning false, so _handleBorrowerDefault is unreachable.
    vm.prank(manager);
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    assertTrue(cdoEpoch.isEpochRunning(), "epoch stuck running");
    assertFalse(cdoEpoch.defaulted(), "default path never entered");

    // Retry after further delay: still frozen while attacker keeps markets illiquid
    vm.warp(block.timestamp + 30 days);
    vm.prank(manager);
    vm.expectRevert(ProgrammableBorrower.StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);
}
```
