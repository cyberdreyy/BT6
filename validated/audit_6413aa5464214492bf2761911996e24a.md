### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing a request to execute below the required number of live confirmations - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` decides whether a request has reached quorum purely by counting entries in the `confirmations` set for that request id (`confirmations.len() as u32 + 1 >= self.num_confirmations`). When a member is removed via `DeleteMember` (multisig2) or a key is removed via `DeleteKey` (multisig v1), the cleanup logic only purges *requests added by* that member/key — it never removes that member's/key's confirmation entries from *other* still-open requests that they had already confirmed. This breaks the equality the contract is supposed to enforce: `confirmations counted == confirmations from currently live members`. A stale confirmation from a removed member can push an otherwise under-confirmed request over the `num_confirmations` threshold.

### Finding Description
In `multisig2/src/lib.rs`, `delete_member()` only cleans up requests that the removed member itself created: [1](#0-0) 

```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
```

It filters on `r.member == member`, i.e. requests where the removed member was the *original submitter*. It does not scan the `confirmations` map for entries where the removed member had *confirmed* (but not submitted) some other open request. Those confirmation entries remain in the `HashSet<String>` for the affected `request_id`.

`confirm()` never validates that every already-recorded confirmation still belongs to a current member — it just trusts `confirmations.len()`: [2](#0-1) 

```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member().unwrap_or_else(|| env::panic_str("Must be validated above"));
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), "Already confirmed this request with this key");
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
```

So the count used to reach quorum (`confirmations.len()`) is not guaranteed to be a count of *live* members — it can include confirmations from members that were deleted afterward.

The identical pattern exists in the legacy `multisig/src/lib.rs`: `DeleteKey` only purges requests signed (added) by that key, not confirmations by that key on other open requests: [3](#0-2) 

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding for a fund-moving multisig account. Concretely:
1. Multisig is `K` of `N`. Member `A` submits request `R1` (e.g. `Transfer` of the account's NEAR).
2. Member `B` confirms `R1` (1 confirmation, `B`'s string is recorded in `confirmations[R1]`).
3. Later, `B` is legitimately removed from the multisig via a separately-confirmed `DeleteMember { member: B }` request. `delete_member()` only removes requests where `r.member == B` (i.e., requests `B` itself submitted) — `R1` (submitted by `A`) is untouched, and `B`'s stale confirmation stays in `confirmations[R1]`.
4. Now only `K-2` additional *current* members need to call `confirm()` on `R1` to reach `confirmations.len() + 1 >= K`, because `B`'s stale entry is still counted. `R1` executes (e.g., transfers funds) with fewer than `K` live confirmations.

This matches the Critical impact category "a multisig request executed below threshold" — funds can be moved, keys added/removed, or contract code deployed with fewer live approvals than the configured security threshold implies, undermining the entire trust model of the K-of-N scheme.

### Likelihood Explanation
Member/key rotation (via `DeleteMember`/`DeleteKey`) is a normal, expected operational action (e.g., removing a departing employee or a compromised key) — not a rare edge case. Any time a member who has an outstanding confirmation on some open request is removed, this staleness is triggered automatically without any special crafting; the remaining members do not even need to be aware that a stale confirmation exists to accidentally execute a request below the intended threshold, and a malicious remaining member could deliberately exploit it once aware.

### Recommendation
When a member (or key) is deleted, iterate over all open requests' `confirmations` sets (not just requests submitted by that member) and remove the deleted member's/key's entry from any request they had confirmed. Alternatively, validate at `confirm()`-time (and before counting) that every entry in `confirmations[request_id]` still corresponds to a `self.members`-contained (or `num_requests_pk`-valid) member, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}`, `num_confirmations = 2`.
2. `A` calls `add_request(R1 = Transfer{...})` (not yet confirmed).
3. `B` calls `confirm(R1)` → `confirmations[R1] = {B}` (1 confirmation, below threshold of 2).
4. Members execute a separate 2-of-3 approved request `DeleteMember{ member: B }` (e.g. confirmed by `A` and `C`) — via `execute_request` → `delete_member(promise, B)`. This removes `B` from `self.members`, but `confirmations[R1]` still equals `{B}` because `delete_member` only filters `self.requests` by `r.member == member`, and `R1.member == A`, not `B`.
5. `A` now calls `confirm(R1)`. `confirmations.len() (1, from stale B) + 1 >= num_confirmations (2)` → true. `R1` executes with only `A`'s live confirmation and `B`'s stale, no-longer-valid confirmation — i.e., a 2-of-3 multisig transfer executed with just 1 live confirmation, below the required threshold.
