## Finding: Confirmed — ID reuse allows a late node response to be merged into a different request's bundle

### Title
Active-request ID reuse after expiry lets a late/in-flight node response bleed into an unrelated newer request's bundle - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`activeRequests` is keyed only by the client-supplied JSON-RPC request `ID` string, with no per-instance binding (nonce/generation counter) between a fan-out and the responses it can accept. Once an expired request is cleared from the map, the same ID is immediately reusable, and `getActiveRequest`/`addResponseForNode` cannot distinguish a stale, late-arriving node response addressed to the old (already-completed) request from one belonging to the new request that reused the same ID.

### Finding Description
- `newActiveRequest` rejects an ID only if it is *currently* present in the map: `if h.activeRequests[req.ID] != nil { ... }`, both keyed and guarded solely by `h.mu` [1](#0-0) .
- `sendResponseAndClearRequest` — invoked from the expiry path (`removeExpiredRequests` → `forwardBundleOrTerminateIfReady`), the quorum-grace path, and the node-message path — is the only place that deletes the entry from `h.activeRequests`, and it does so as soon as the request is claimed/completed, independent of whether every node has actually replied yet [2](#0-1) .
- Once that delete happens, the ID `X` is free to be reused by any subsequent `HandleJSONRPCUserMessage` call; the only validation on the ID is non-empty and ≤200 chars, and the ID itself is taken directly from the client-supplied JSON-RPC `Request.ID` [3](#0-2) [4](#0-3) .
- `HandleNodeMessage` resolves the target request purely by `getActiveRequest(resp.ID)`, a plain map lookup with no check that the returned `*activeRequest` is the same logical instance that was actually sent to the DON in the fan-out that produced this response [5](#0-4) .
- `addResponseForNode` only guards against a *duplicate* response from the same node for the *current* `ar` instance; a freshly created `ar` has an empty `responses` map, so a stale response for the same node address is accepted without complaint [6](#0-5) .

Because of this, if request `X` expires and is forwarded/cleared (`removeExpiredRequests`, `handler.go:306-339`), and a new request also using ID `X` is registered before an in-flight/delayed node response for the *old* `X` arrives, `HandleNodeMessage` will attach that stale response to the new request's bundle via `addResponseForNode` and `h.bundler.Bundle(ar.req, copiedResponses, l)` [7](#0-6) . There is no per-request nonce/generation tag on either the outbound `jsonrpc.Request` sent to nodes or the tracked `activeRequest` to reject cross-generation responses.

### Impact Explanation
This is a "cross-request response bleed" at the gateway layer: a stale, delayed node response can be silently folded into a different (later) request's response bundle sharing the same ID, mixing data across request lifecimes. The comment in the code explicitly documents that the gateway defers actual signature/content verification to the downstream enclave ("the enclave remains responsible for signature and quorum verification") [8](#0-7) , which is likely to reject a response that does not match the new request's content, bounding worst-case impact (e.g., secret disclosure) to the extent that downstream verification catches the mismatch. Within the gateway's own responsibility, however, this still constitutes cross-request/cross-user response confusion and an isolation violation between request lifecycle transitions.

### Likelihood Explanation
Exploitation requires: (1) control or influence over request expiry timing (attacker can trivially trigger this on their own requests by simply not causing quorum and letting `requestTimeout` elapse), and (2) the new request reusing the *exact same* ID string as the expired one, which in practice requires either the ID being attacker-chosen for both requests (only exploitable against a victim if IDs are predictable/shared/sequential rather than random per-client UUIDs) or a genuine attacker-vs-attacker self-collision, which has no cross-user impact. Practical cross-user exploitation is therefore constrained by how request IDs are generated by legitimate clients — I could not fully verify ID generation on the client side within this repo, so the "attacker forces a specific victim ID collision" leg of the scenario is not conclusively demonstrated from code alone.

### Recommendation
Bind each `activeRequest` to a unique internal generation token (e.g., combine ID with a monotonically-increasing counter or UUID stored on the `activeRequest`, and stamp outbound requests-to-nodes with that same token so `HandleNodeMessage` can reject responses whose token doesn't match the current live instance for that ID). Alternatively, do not permit reuse of an `ID` until some cooldown period after clearing, or track cleared IDs to explicitly drop any responses referencing already-finalized IDs rather than silently doing nothing (`getActiveRequest` returning nil vs. matching a *new* request are currently indistinguishable to the caller).

### Proof of Concept
Go handler-level integration test plan:
1. Instrument a fake clock (`clockwork.FakeClock`, already used via `h.clock`) and fake `DON`.
2. Create request `R1` with ID `"X"` via `HandleJSONRPCUserMessage`; do not deliver enough node responses to reach quorum.
3. Advance the fake clock past `requestTimeout`; invoke the cleanup goroutine logic (`removeExpiredRequests`) to force expiry and confirm `sendResponseAndClearRequest` clears `X` from `h.activeRequests` (assert via a test hook or by successfully re-registering the same ID next).
4. Immediately call `HandleJSONRPCUserMessage` again with the same ID `"X"` (simulating the "victim" reusing the ID) — assert it succeeds (no "ID already exists" error), producing a new `activeRequest` object.
5. Deliver a `HandleNodeMessage` call with `resp.ID == "X"` from a node address, using response content associated with the *original* `R1` context (i.e., simulate the "late" in-flight response).
6. Assert this stale response is accepted into the new `activeRequest`'s `responses` map (via `copiedResponses()`), i.e., `addResponseForNode` returns `true` and the bundle sent to the second caller's callback includes/considers this response — demonstrating the isolation break; then assert (as the desired fix) that late responses for a since-pruned generation are instead dropped.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	l := logger.With(h.lggr, "method", resp.Method, "requestID", resp.ID, "nodeAddr", nodeAddr)
	l.Debugw("handling node response")

	nodeRateLimiter, ok := h.perNodeRateLimiters[nodeAddr]
	if !ok {
		return fmt.Errorf("received message from unexpected node %s", nodeAddr)
	}
	if !nodeRateLimiter.Allow(ctx) {
		l.Debugw("node is rate limited", "nodeAddr", nodeAddr)
		return nil
	}
	if !h.globalNodeRateLimiter.Allow(ctx) {
		l.Debug("global relay rate limit exceeded")
		return nil
	}

	ar := h.getActiveRequest(resp.ID)
	if ar == nil {
		l.Debugw("no pending request found for ID")
		return nil
	}

	added := ar.addResponseForNode(nodeAddr, resp)
	if !added {
		l.Errorw("duplicate response from node, ignoring", "nodeAddr", nodeAddr)
		return nil
	}

// sendResponseAndClearRequest claims the request, sends payload, and removes it from
// activeRequests. Concurrent completion paths (node-message forward,
// terminal-state forward, quorum grace, expiry) may all race here; only the first
// claimer sends. Metrics are recorded only after a successful send so losers do not
// double-count.
func (h *handler) sendResponseAndClearRequest(ctx context.Context, ar *activeRequest, payload gwhandlers.UserCallbackPayload) error {
	if !ar.completed.CompareAndSwap(false, true) {
		// Another path already answered this request.
		return nil
	}

	sendErr := ar.SendResponse(payload)

	h.mu.Lock()
	delete(h.activeRequests, ar.req.ID)
	h.mu.Unlock()

	if sendErr != nil {
		h.lggr.Errorw("error sending response to user", "requestID", ar.req.ID, "error", sendErr)
		return sendErr
	}

	h.recordMetrics(ctx, payload.ErrorCode)
	h.lggr.Debugw("response sent to user", "requestID", ar.req.ID, "errorCode", payload.ErrorCode)
	return nil
}
