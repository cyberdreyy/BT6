### Title
`getMultipleAccounts` / `getProgramAccounts` abort the entire batch when a single account's data is too large for the requested encoding - ([File: rpc/src/rpc.rs])

### Summary
`encode_account()` returns an `Err` when a single account's data (or configured data slice) exceeds `MAX_BASE58_BYTES` for `Binary`/`Base58` encoding. Both `get_multiple_accounts()` and `get_program_accounts()` call this per-item inside a loop and propagate the error with `?`, so one oversized/incompatible account in a batch aborts the whole RPC response instead of only affecting that item — the shared `encoding`/`data_slice` configuration is applied uniformly to a heterogeneous batch, exactly mirroring the reported bug class of a single shared parameter causing an all-or-nothing failure for a multi-item request.

### Finding Description
`encode_account` is the shared encoding routine used for every account returned by account-info RPC endpoints: [1](#0-0) 

It explicitly errors out (rather than degrading gracefully like `encode_ui_account`/`encode_bs58` do for pubsub, which just embed an `"error: data too large for bs58 encoding"` string) when the sliced data length exceeds `MAX_BASE58_BYTES` (128 bytes) and the caller requested `Binary` or `Base58` encoding.

`get_multiple_accounts()` calls `get_encoded_account` (which calls `encode_account`) once per pubkey inside a loop, and uses `?` on each result: [2](#0-1) 

Because `?` short-circuits the whole async function, if any single pubkey in the batch resolves to an account whose data (post data-slice) is larger than 128 bytes and the caller asked for Base58/Binary encoding, the entire `getMultipleAccounts` call fails — even though the other pubkeys in the same batch would have encoded successfully on their own.

The same pattern exists in `get_program_accounts()`, where `encode_account` is called inside a `.map()` over every keyed account and errors are collected via `.collect::<Result<Vec<_>>>()?`: [3](#0-2) 

Here the blast radius is worse: `getProgramAccounts` can return an arbitrarily large set of accounts for a program, and a single oversized account anywhere in that set will invalidate the entire (potentially large, expensive-to-compute) result set.

This is directly analogous to the reported Tapioca `_liquidateUser()` bug class: a single shared value/config (there, `minAssetAmount`; here, `encoding`/`data_slice`) is applied indiscriminately across a batch of heterogeneous items (loans vs. accounts), and one "unlucky" item in the batch (too big to swap at that price / too big to base58-encode) causes the entire batched operation to revert, denying valid processing to all the other items in the same call — the "second scenario" from the report (revert of the whole batch due to one bad element).

### Impact Explanation
An unprivileged JSON-RPC client calling `getMultipleAccounts` or `getProgramAccounts` with `encoding: "base58"` (or the legacy default `"binary"`) against a set/program that contains even one account whose data exceeds 128 bytes gets an `InvalidRequest` error for the *entire* call, instead of the expected partial/degraded response. This is a functional correctness bug reachable with a single low-rate RPC call: legitimate account data that would normally be returned (for `getMultipleAccounts`) or an entire program's account set (for `getProgramAccounts`) becomes unfetchable via this encoding, silently breaking downstream tooling/wallets that batch pubkeys together and forcing them to fall back to one-by-one `getAccountInfo` calls (or switch encoding, if they even understand the cause). It is not a crash/DoS/consensus issue, but it is a genuine wrong-result/availability defect in an unprivileged JSON-RPC read path caused by uniformly applying one config value across a batch, matching the required "wrong … account data returned" outcome bar for a single request.

### Likelihood Explanation
High: any account with `data.len() > 128` bytes (i.e., almost any non-trivial account, since 128 bytes is a very small threshold) combined with a `getMultipleAccounts`/`getProgramAccounts` request using default/base58 encoding triggers this. No special privileges or timing are needed — a single call from any RPC client hits the codepath.

### Recommendation
For `get_multiple_accounts()` and `get_program_accounts()`, do not propagate the base58-size error with `?` for individual accounts in a batch. Instead, mirror the graceful degradation already used by `encode_ui_account`/`encode_bs58` in `account-decoder/src/lib.rs` (embedding an `"error: data too large for bs58 encoding"` string for just the offending account) so the rest of the batch still succeeds, or return an explicit per-item error/null entry rather than failing the whole response.

### Proof of Concept
1. Store two accounts on a bank: `pubkey_a` with 4 bytes of data, `pubkey_b` with 200 bytes of data.
2. Call `getMultipleAccounts([pubkey_a, pubkey_b], {"encoding": "base58"})` (or omit encoding, defaulting to `Binary`).
3. Observe that `get_multiple_accounts()` (rpc/src/rpc.rs:579-590) calls `get_encoded_account` for each pubkey; for `pubkey_b`, `encode_account` (rpc/src/rpc.rs:2575-2601) returns `Err(InvalidRequest, "Encoded binary (base 58) data should be less than 128 bytes...")`, which is propagated via `?` at line 588.
4. The entire RPC call fails with an error, even though `pubkey_a`'s data would have encoded fine — the caller gets nothing back for either account.
5. The same demonstration applies to `getProgramAccounts` against a program owning both small and >128-byte accounts (rpc/src/rpc.rs:656-666), where the whole program-account scan is discarded due to one oversized account.

fn encode_account<T: ReadableAccount>(
    account: &T,
    pubkey: &Pubkey,
    encoding: UiAccountEncoding,
    data_slice: Option<UiDataSliceConfig>,
) -> Result<UiAccount> {
    if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)
        && data_slice
            .map(|s| min(s.length, account.data().len().saturating_sub(s.offset)))
            .unwrap_or(account.data().len())
            > MAX_BASE58_BYTES
    {
        let message = format!(
            "Encoded binary (base 58) data should be less than {MAX_BASE58_BYTES} bytes, please \
             use Base64 encoding."
        );
        Err(error::Error {
            code: error::ErrorCode::InvalidRequest,
            message,
            data: None,
        })
    } else {
        Ok(encode_ui_account(
            pubkey, account, encoding, None, data_slice,
        ))
    }
}
