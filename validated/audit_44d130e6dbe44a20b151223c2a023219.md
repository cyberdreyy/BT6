### Title
Post-default withdraw requests drain the fixed default-recovery reserve at par, leaving defaulted claimants permanently underfunded - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is an out-of-bounds write: attacker-controlled input corrupts memory outside the intended region. The vault analog is a "claim outside the funded region": `finalizeDefaultRecovery` sizes `defaultRecoveryReserve` exactly to cover a fixed set of claims (`totalBasis * recoveryPrice`), but `requestWithdraw` lets any tranche holder create *new* post-default claims (`postDefaultRequests`) that are paid 1:1 out of that same bounded reserve — claims that were never part of the provisioning basis. Each post-default claim is an out-of-bounds spend against the recovery budget, so the reserve underflows and later legitimate claimants can never be paid.

### Finding Description
`finalizeDefaultRecovery` computes a bounded recovery pool:

- `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis`, where `totalBasis = activeBasis + pendingBasis` [1](#0-0) 

So the reserve exactly covers: pending receipts at `recoveryPrice`, and the CDO's active strategy tokens (written down to `activeFinalNAV = activeBasis * recoveryPrice / RECOVERY_FULL`) whose holders redeem via the default distribution at the same ratio. There is no slack — every unit of reserve is spoken for.

After finalization, `requestWithdraw` takes the post-default branch:

- It burns `_amount` of CDO-held strategy tokens, mints an equal receipt to the user, and records `postDefaultRequests[_user] = _amount` — with **no underlying transferred in** [2](#0-1) 

The claim path pays this receipt **at par** from the recovery reserve:

- `_claimPostDefaultWithdrawRequest` calls `_transferDefaultRecovery(_user, amount)` with the full `amount` [3](#0-2) 
- `_transferDefaultRecovery` does `defaultRecoveryReserve -= _amount` and transfers underlying [4](#0-3) 

Two compounding errors:

1. **Unpriced payout.** The burned strategy tokens were only worth `recoveryPrice` per unit (active NAV was written down in `finalizeDefaultRecovery`), yet the claim pays full face value. When `recoveryPrice < 1`, each post-default claim withdraws `amount` of reserve for basis that was only provisioned `amount * recoveryPrice` — and in fact was provisioned *to active tranche holders*, not to the claimant at all.
2. **Unbounded claim creation.** `postDefaultRequests` are created after `totalBasis` was fixed, so they are outside the funded region entirely. Any KYC'd lender holding tranche tokens can mint one unboundedly (subject only to their balance), directly converting other claimants' recovery into their own par payout.

The comment "The CDO passes an already-haircut amount because finalization lowered virtualPrice first" confuses the receipt *denomination* with its *funding*: denominating the request in post-haircut units does not transfer any new underlying into the reserve.

### Impact Explanation
Direct theft and insolvency with quantified loss. Let `recoveryPrice = p < 1`. A post-default claim of `A` removes `A` underlying from `defaultRecoveryReserve` while the reserve contains only `p` per unit of aggregate basis. The theft per claim is `(1 - p) * A` relative to fair value, and the aggregate reserve drains `1/p` faster than provisioned. Once cumulative post-default payouts exceed the unclaimed slack, `defaultRecoveryReserve -= _amount` underflows and every remaining defaulted-epoch claim (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) and post-default claim reverts permanently — recovery funds are either stolen or frozen forever. Loss magnitude: up to the entire `defaultRecoveryReserve`, bounded by post-default tranche supply.

### Likelihood Explanation
Requires only a realized borrower default with `recoveryPrice < 1` (the scenario the whole recovery machinery exists for), followed by any unprivileged tranche holder calling `IdleCDOEpochVariant.requestWithdraw` post-finalization. The guard at line 249 (`_hasWithdrawRequest`) only blocks users with *existing* pending receipts; a holder with no prior withdraw request — or one who claims first — qualifies immediately. No privileged or malicious-role action is needed; sequencing is entirely around honest manager/borrower calls. The revert-on-underflow outcome is deterministic once total post-default claims exceed available reserve.

### Recommendation
Do not pay post-default receipts from `defaultRecoveryReserve` at par. Either:

- Apply the same haircut: pay `amount * defaultRecoveryPrice / RECOVERY_FULL` and add `postDefaultRequests` basis into the recovery accounting, or
- Require post-default requests to be funded by new borrower/strategy inflows (track them in a separate bucket paid only from non-reserve balance, enforced by the same `balance - reserve >= amount` check used in `_transferFundedClaim`), or
- Disallow `requestWithdraw` entirely once `defaultRecoveryFinalized` is true until the reserve is fully claimed.

The receipt mint should also not burn CDO strategy tokens 1:1 without a corresponding value transfer, since that erodes the active-side recovery share.

### Proof of Concept
Foundry fork sketch (against an `IdleCDOEpochVariant` + `IdleCreditVault` deployment):

```solidity
function testPostDefaultReserveDrain() external {
    // --- setup: epoch running, alice holds AA tranches, bob holds BB tranches ---
    _depositWithUser(alice, 100_000e6);
    _depositWithUser(bob,   100_000e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // --- alice files a normal withdraw request mid-epoch ---
    vm.prank(alice);
    cdoEpoch.requestWithdraw(aliceTrancheBal / 2, AA);

    // --- borrower defaults; owner stops epoch with loss path ---
    _defaultBorrower();                    // borrower fails to repay
    vm.prank(owner); cdoEpoch.stopEpoch(); // defaulted() == true

    // --- finalize recovery with 50% recovered => recoveryPrice = 0.5e18 ---
    deal(USDC, recoverySource, recovered);
    vm.prank(owner);
    cdoEpoch.finalizeDefaultRecovery(recovered, recoverySource);
    assertEq(strategy.defaultRecoveryPrice(), 0.5e18);

    uint256 reserveBefore = strategy.defaultRecoveryReserve();

    // --- ATTACK: bob (still holding tranches) files a post-default withdraw ---
    uint256 bobTranche = BB.balanceOf(bob);
    vm.prank(bob);
    cdoEpoch.requestWithdraw(bobTranche, BB);   // postDefaultRequests[bob] = amount

    uint256 bobPre = IERC20(USDC).balanceOf(bob);
    vm.prank(bob);
    cdoEpoch.claimWithdrawRequest(BB);           // pays bob AT PAR from reserve
    uint256 stolen = IERC20(USDC).balanceOf(bob) - bobPre;

    // bob's receipt was only provisioned at 50c on the dollar
    assertGt(stolen, bobTranche * cdoEpoch.virtualPrice(BB) / 1e18,
        "post-default claim paid above recovery value");

    // --- victim: alice's defaulted-epoch claim now underflows/reverts ---
    vm.prank(alice);
    vm.expectRevert(); // defaultRecoveryReserve -= amount underflows
    cdoEpoch.claimWithdrawRequest(AA);

    assertLt(strategy.defaultRecoveryReserve(), reserveBefore - stolen,
        "reserve drained by out-of-basis claim");
}
```

Uncertainty note: I verified the strategy-side code paths but did not fully trace `IdleCDOEpochVariant.requestWithdraw`/`_transferFundedClaim`'s CDO-side bookkeeping post-default; if the CDO separately pulls underlying equal to `postDefaultRequests` into the strategy at request time (none is visible in `IdleCreditVault.requestWithdraw` lines 247–257), the drain would instead manifest as that funding failing or being double-counted — either way the par payout from a fixed reserve is not provisioned.

  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];

    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.

    if (_amount == 0) return;
