### Title
Builder payment quorum check bypassed when parent execution payload is applied more than one epoch late - ([File: specs/gloas/beacon-chain.md])

### Summary
`apply_parent_execution_payload` settles a builder's payment for a revealed payload through two different code paths. When the parent slot is within the current or previous epoch, `settle_builder_payment` pays out unconditionally as soon as `payment.withdrawal.amount > 0`. When the parent slot is older than the previous epoch (i.e. the deferred settlement was delayed by 2+ epoch boundaries), the payment entry has already been rotated out of `state.builder_pending_payments` by `process_builder_pending_payments`, which only forwards the payment to `builder_pending_withdrawals` **if `payment.weight >= quorum`** (i.e., only if enough PTC/attesters confirmed payload availability). The fallback branch in `apply_parent_execution_payload` ignores this quorum outcome entirely and unconditionally re-creates the withdrawal from `parent_bid.value` whenever `parent_bid.value > 0`.

### Finding Description
`process_builder_pending_payments` [1](#0-0)  is the mechanism that decides, once per epoch, whether a builder should be paid for a payload that was not promptly settled by the very next block: it only appends `payment.withdrawal` to `state.builder_pending_withdrawals` if the accumulated PTC/attestation `weight` reached `quorum = get_builder_payment_quorum_threshold(state)`. If the weight is below quorum, the payment slot is simply zeroed out and the builder receives nothing for that slot's entry.

However, `apply_parent_execution_payload` [2](#0-1)  re-derives the builder's payment independently when the block that finally reveals/consumes the parent's full payload arrives after that quorum decision has already been made and the entry evicted:

```
elif parent_bid.value > 0:
    # Parent is older than the previous epoch, its payment entry has been
    # evicted from builder_pending_payments. Append the withdrawal directly.
    state.builder_pending_withdrawals.append(
        BuilderPendingWithdrawal(
            fee_recipient=parent_bid.fee_recipient,
            amount=parent_bid.value,
            builder_index=parent_bid.builder_index,
        )
    )
```

Unlike `settle_builder_payment` and `process_builder_pending_payments`, this fallback performs no check of `payment.weight`/quorum at all — it pays the builder in full purely because `parent_bid.value > 0`, regardless of whether the PTC ever attested the payload's availability. This directly contradicts the two other settlement paths, which encode "the builder is paid only if the network confirmed the payload was actually delivered" as the governing equality.

This is confirmed by the test `test_builder_payment_after_missed_epochs` [3](#0-2) , whose own comments state: "2nd boundary: checks quorum on first half — weight 0 < quorum → evicted... The fix creates the withdrawal directly from the bid in this case," and then asserts the builder's balance is decreased by `value` anyway — i.e. the builder is paid even though the quorum check (weight 0 < quorum) had already rejected the payment.

### Impact Explanation
This breaks the equality "a builder is paid only if a quorum of validators attested that its payload was actually delivered/available." A proposer (or a proposer colluding with a builder) can withhold building on a builder's revealed payload for more than one epoch (skipping/empty-building over it), causing the associated `BuilderPendingPayment` to be evicted with insufficient weight (i.e., formally rejected), and then later build a child block whose `parent_execution_requests` finally commits to that same old, previously-rejected payload. When that block is processed, `apply_parent_execution_payload` takes the "older than previous epoch" branch and pays the builder the full bid value unconditionally, resurrecting a payment that the quorum mechanism had already discarded. This is a builder payment "escaped" from (or duplicated past) the quorum gate that the protocol places on it — matching the High-impact class "a builder payment or withdrawal misdirected, doubled, or escaped."

### Likelihood Explanation
The triggering condition (a payload not built upon by the immediate or next-epoch child, but built upon later once it is 2+ epochs stale) is an explicitly-handled branch in the spec rather than a hypothetical corner case, and there is a dedicated spec test exercising exactly this path. It requires control over proposer duties across several slots/epochs (to defer building on the payload) without needing majority stake or an execution-layer bug, making it reachable by a single proposer (or proposer+builder colluding), which is within the scope of unprivileged/single-participant analogs.

### Recommendation
Make the "older than previous epoch" fallback in `apply_parent_execution_payload` consistent with `process_builder_pending_payments`: either (a) never allow the deferred settlement of the parent to introduce a *new* payment once the payment window has passed without quorum (i.e., simply drop it, since the quorum decision already occurred), or (b) track the quorum outcome for each slot so this fallback can only re-emit a withdrawal that was legitimately approved by quorum and never re-emit one that was rejected, avoiding both look-alike double payment and unconditional escape-the-quorum payment.

### Proof of Concept
Concrete state walk (conceptual, mirrors the existing spec test `test_builder_payment_after_missed_epochs`):
1. Builder B submits a bid of value `V` for slot `S`, recorded as `BuilderPendingPayment(weight=0, withdrawal=W(amount=V, builder_index=B))` at `builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH]` via `process_execution_payload_bid` [4](#0-3) .
2. No/insufficient PTC attestations occur for slot `S`'s payload (weight stays `0`, below quorum).
3. Two epoch boundaries pass without any child block committing to this payload as parent (empty blocks / no builder on top), so `process_builder_pending_payments` runs at each boundary: at the boundary where this entry reaches the first half, `weight (0) < quorum`, so no withdrawal is appended and the entry is zeroed out [5](#0-4) .
4. Later, a block is finally built whose `parent_execution_requests` matches the (still-available) old full payload for slot `S`. `process_parent_execution_payload` verifies the commitment root and calls `apply_parent_execution_payload` [6](#0-5) .
5. Since `parent_epoch` is now older than `get_previous_epoch(state)`, the fallback branch executes and unconditionally appends `BuilderPendingWithdrawal(amount=V, builder_index=B, ...)` to `state.builder_pending_withdrawals` [7](#0-6) .
6. The builder is paid `V` despite the quorum mechanism having already determined (at step 3) that this payload's payment should not be honored — confirmed by the test's final assertion that the builder's balance decreases by `value` [8](#0-7) .

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments

def process_parent_execution_payload(state: BeaconState, block: BeaconBlock) -> None:
    bid = block.body.signed_execution_payload_bid.message
    parent_bid = state.latest_execution_payload_bid
    requests = block.body.parent_execution_requests

    if bid.parent_block_hash != parent_bid.block_hash:
        # Parent was EMPTY -- no execution requests expected
        assert requests == ExecutionRequests.empty()
        return

    # Parent was FULL -- verify the bid commitment and apply the payload
    assert hash_tree_root(requests) == parent_bid.execution_requests_root
    apply_parent_execution_payload(state, requests)

@with_gloas_and_later
@spec_state_test
def test_builder_payment_after_missed_epochs(spec, state):
    """
    Test that a builder is correctly charged when their canonical payload
    is processed after 2+ epochs of missed blocks.
    """
    # Advance to get finalization
    for _ in range(4):
        next_epoch_with_full_participation(spec, state)
    assert state.finalized_checkpoint.epoch == 2

    # Build Block 1 with a non-zero value bid from a builder
    block_1 = build_empty_block_for_next_slot(spec, state)
    builder_index = 0
    value = spec.Gwei(1000000)  # 0.001 ETH
    fee_recipient = b"\xab" * 20
    block_hash = spec.Hash32(b"\x42" * 32)

    bid = block_1.body.signed_execution_payload_bid.message
    bid.block_hash = block_hash
    bid.builder_index = builder_index
    bid.value = value
    bid.fee_recipient = fee_recipient
    bid.execution_requests_root = spec.hash_tree_root(spec.ExecutionRequests())

    # Sign the bid with the builder's private key
    signature = spec.get_execution_payload_bid_signature(
        state, bid, builder_privkeys[builder_index]
    )
    block_1.body.signed_execution_payload_bid = spec.SignedExecutionPayloadBid(
        message=bid,
        signature=signature,
    )

    # Ensure builder can cover the bid
    state.builders[builder_index].balance = spec.MIN_DEPOSIT_AMOUNT + value

    yield "pre", state

    # Process Block 1 — creates a pending payment for the builder
    signed_block_1 = state_transition_and_sign_block(spec, state, block_1)

    # Verify pending payment was created
    payment_idx = spec.SLOTS_PER_EPOCH + block_1.slot % spec.SLOTS_PER_EPOCH
    payment = state.builder_pending_payments[payment_idx]
    assert payment.withdrawal.amount == value
    assert payment.withdrawal.builder_index == builder_index
    assert payment.weight == 0

    pre_builder_balance = state.builders[builder_index].balance

    # Build Block 2 with 2+ epochs of missed slots. During the slot advancement,
    # process_builder_pending_payments runs at each epoch boundary:
    #   1st boundary: shifts payment from second half to first half
    #   2nd boundary: checks quorum on first half — weight 0 < quorum → evicted
    # When Block 2 is processed, parent is FULL so apply_parent_execution_payload
    # runs. Since parent_epoch is older than previous_epoch, payment_index is None.
    # The fix creates the withdrawal directly from the bid in this case.
    block_1_epoch = spec.compute_epoch_at_slot(block_1.slot)
    block_2_slot = spec.compute_start_slot_at_epoch(block_1_epoch + 2) + 1
    block_2 = build_empty_block(spec, state, slot=block_2_slot)
    block_2.body.signed_execution_payload_bid.message.parent_block_hash = block_hash
    signed_block_2 = state_transition_and_sign_block(spec, state, block_2)

    yield "blocks", [signed_block_1, signed_block_2]
    yield "post", state

    # Verify apply_parent_execution_payload actually ran (parent was FULL)
    parent_slot_index = bid.slot % spec.SLOTS_PER_HISTORICAL_ROOT
    assert state.execution_payload_availability[parent_slot_index]

    # Verify the builder was charged — balance decreased by the bid value
    assert state.builders[builder_index].balance == pre_builder_balance - value
