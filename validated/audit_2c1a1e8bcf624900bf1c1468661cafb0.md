### Title
Funded instant-withdraw claims leak their per-epoch receipt basis, inflating the default recovery reserve and diluting/freezing other claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
Like the kernel adapter reference that is acquired and never released, `requestInstantWithdraw` records a per-epoch receipt reservation (`instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`), but the normal funded claim path `claimInstantWithdrawRequest` never releases it. Only the defaulted-claim path clears those ledgers. The leaked reservation is later counted again by `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve` during `finalizeDefaultRecovery`, overstating both the claim basis and the prefunded reserve.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw`, each request increments three counters: the aggregate `instantWithdrawsRequests[_user]`, the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and the epoch total `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . When the request is funded and the user claims, `claimInstantWithdrawRequest` zeroes only the aggregate and transfers the funds [2](#0-1)  — the per-epoch ledgers keep the stale amount forever (compare `_claimDefaultedInstantWithdrawRequest`, which does clear them [3](#0-2) ).

At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held by the strategy [5](#0-4) . `finalizeDefaultRecovery` then sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and computes the recovery price over the inflated `totalBasis` [6](#0-5) . Amounts already paid out are thus counted both as outstanding basis and as phantom prefunded backing — the acquired reference is never released.

### Impact Explanation
Two direct losses, quantified by the leaked amount `C`:

1. **Reserve inflation / insolvency**: `prefundedReserve` includes `C` even though those tokens left the contract when the user claimed. `defaultRecoveryReserve` is set above the actual token balance. Claims pay out via `_transferDefaultRecovery`, which decrements the reserve but transfers real tokens [7](#0-6)  — so early claimants (including the attacker, who can front-run) drain the reserve, and the last ~`C` of legitimate defaulted/post-default claims revert permanently on `safeTransfer`, freezing recovery funds.
2. **Recovery dilution**: `totalBasis` is inflated by `C`, lowering `defaultRecoveryPrice` for every honest claimant — a pro-rata theft of recovered funds.

The `_transferFundedClaim` guard does not help: it protects the reserve from funded claims, not the reserve from being set above the real balance [8](#0-7) . No guard re-derives the actual instant backing at finalization.

### Likelihood Explanation
Requirements: (a) a user makes an instant-withdraw request, the CDO funds it via `collectInstantWithdrawFunds`, and the user claims while the epoch is still current — the intended instant UX; (b) at least one other instant request remains unfunded (`pendingInstantWithdraws != 0`) when the borrower defaults and `finalizeDefaultRecovery` runs. The attacker can be an unprivileged lender performing (a) and the second unfunded requester can be anyone; the borrower default is an external market event, not attacker-controlled. Any pre-default instant activity creates the leak with no timing edge required beyond claiming before finalization.

### Recommendation
In `claimInstantWithdrawRequest`, release the per-epoch reservation exactly like `_claimDefaultedInstantWithdrawRequest` does: for the epoch key(s) covering `amount`, set `instantWithdrawsRequestsByEpoch[_user][epoch]` to 0 and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed basis, so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` only see live receipts. Add a regression test asserting `instantWithdrawClaimsByEpoch` reaches zero after all current-epoch instant claims are paid.

### Proof of Concept
```solidity
// Foundry fork-style PoC against IdleCreditVault + IdleCDOEpochVariant
function testInstantClaimLeakInflatesRecovery() public {
    // epoch N running with instant withdrawals enabled
    uint256 amt = 1000e6;
    _depositWithUser(alice, amt);
    _depositWithUser(bob, amt);

    // alice requests instant withdraw; CDO funds it via collectInstantWithdrawFunds
    _requestInstantWithdraw(alice, amt);
    _fundInstantWithdraw(amt); // borrower/manager path -> pendingInstantWithdraws -= amt
    _claimInstant(alice);      // funded claim: instantWithdrawsRequestsByEpoch NOT cleared

    // bob requests instant withdraw but it stays unfunded
    _requestInstantWithdraw(bob, amt); // pendingInstantWithdraws = amt

    // borrower defaults in same epoch; manager triggers default + finalizeDefaultRecovery
    _defaultAndFinalize(recovered);

    // instantWithdrawClaimsByEpoch[N] = 2*amt although only bob is owed
    uint256 reserve = strategy.defaultRecoveryReserve();
    assertGt(reserve, underlying.balanceOf(address(strategy)),
        "reserve exceeds real balance by alice's leaked basis");

    // bob's claim reverts once reserve bookkeeping outruns real tokens,
    // or earlier claimants drained more than funded -> funds frozen/diluted
}
```

Note: I could not fully trace `IdleCDOCreditVault`'s funding/claim wrapper calls to confirm the exact sequencing of `collectInstantWithdrawFunds` vs `claimInstantWithdrawRequest` ordering edge cases, so the PoC skeleton should be validated in a Devin session; the state-leak itself is directly visible in the strategy code cited above.

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }
