### Title
Default recovery basis reads only the current epoch's instant-withdraw slot, letting stale-epoch instant receipts bypass the haircut and drain the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The QEMU bug class is an out-of-bounds access driven by a stale/unchecked index into a buffer. The analog in `IdleCreditVault` is an epoch-index confusion: default finalization computes the claim basis with `instantWithdrawClaimsByEpoch[epochNumber]` — a lookup into only the *current* epoch slot — while `claimInstantWithdrawRequest` pays out the *aggregate* `instantWithdrawsRequests[_user]` at par. Instant receipts recorded under a different (earlier) epoch index are invisible to the recovery accounting but are still paid in full.

### Finding Description
- `requestInstantWithdraw` records per-epoch basis under the *request-time* epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (IdleCreditVault.sol:367-374).
- `epochNumber` is bumped at every epoch transition via `deposit()` (IdleCreditVault.sol:610).
- On default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *new* current epoch — to the recovery basis (IdleCreditVault.sol:644-649), and `finalizeDefaultRecovery` sets `defaultRecoveryEpoch = epochNumber` (IdleCreditVault.sol:693).
- The defaulted-claim path `_claimDefaultedInstantWithdrawRequest` likewise only reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (IdleCreditVault.sol:844), so an instant receipt created under a *previous* epoch index is never cleared and never haircutted.
- After that path returns 0, `claimInstantWithdrawRequest` still pays `instantWithdrawsRequests[_user]` — the full aggregate across all epochs — at par via `_transferFundedClaim` (IdleCreditVault.sol:387-392).

So a receipt indexed under epoch N, surviving unfunded into epoch N+1 where the borrower defaults, is excluded from `totalBasis` (inflating `defaultRecoveryPrice` for everyone) and is then redeemed at 100% anyway, paid out of funds that belong to the recovery reserve and other claimants.

### Impact Explanation
An attacker holding unfunded instant-withdraw receipts from a prior epoch claims them at par post-default instead of at `defaultRecoveryPrice`. This directly transfers value from the capped `defaultRecoveryReserve` and strategy balance to the attacker: legitimate defaulted-epoch claimants and active LPs receive less than the finalized recovery ratio, i.e. theft plus reserve insolvency. The recovery-price inflation additionally overpays every earlier claimant, compounding the shortfall for later ones.

### Likelihood Explanation
The attacker only needs to be a KYC-passing lender who calls `requestInstantWithdraw` during a running epoch and simply does not claim. No privileged cooperation is required; the trigger is an ordinary borrower default in a later epoch, which the protocol explicitly supports (`defaultInstantWithdrawsFinalized` exists precisely for unfunded instant receipts). The exploit fails only if every unfunded instant receipt is guaranteed to be collected within its own epoch — nothing in `claimInstantWithdrawRequest`/`collectInstantWithdrawFunds` enforces that at the strategy level, and the receipt ledger persists across `epochNumber` increments. This mechanism has not been fully verified against the CDO's stopEpoch sequencing (whether `pendingInstantWithdraws` is forced to zero at every epoch boundary); if the CDO hard-forces collection, the window collapses.

### Recommendation
In `defaultPendingClaimBasis()` and `_claimDefaultedInstantWithdrawRequest`, account for *all* outstanding instant receipt basis, not just the current epoch slot — e.g. track a global `instantWithdrawClaimsTotal`, or iterate/aggregate `instantWithdrawsRequestsByEpoch` across open epochs. Alternatively, require `pendingInstantWithdraws == 0` (all instant receipts funded or claimed) before allowing `epochNumber` to advance, and revert `claimInstantWithdrawRequest`'s par payout for receipts not covered by a funded epoch slot.

### Proof of Concept
Foundry fork sketch (modeled on `test/foundry/IdleCreditVault.t.sol` / `IdleCDOEpochQueue.t.sol` helpers):

```solidity
function testStaleEpochInstantReceiptDrainsRecovery() external {
  // Epoch N running, instant withdrawals enabled
  _stopCurrentEpochWithApr(10e18);
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(100, 1e18, false);
  uint256 tranches = _depositWithUser(attacker, 100e6);
  vm.prank(manager);
  cdoEpoch.startEpoch();

  // Attacker opens an instant withdraw in epoch N and never claims
  vm.prank(attacker);
  cdoEpoch.requestInstantWithdraw(tranches, address(aaTranche));
  assertGt(strategy.instantWithdrawsRequests(attacker), 0);

  // Epoch N stops unfunded for the instant bucket; epochNumber -> N+1
  _stopCurrentEpochWithApr(10e18);

  // Epoch N+1 runs; borrower defaults (stopEpoch(0,0) after expiry, no repayment)
  vm.prank(manager);
  cdoEpoch.startEpoch();
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(cdoEpoch.owner());
  cdoEpoch.stopEpoch(0, 0);
  assertTrue(cdoEpoch.defaulted());

  // Finalize with partial recovery; attacker's epoch-N instant basis is NOT in totalBasis
  vm.prank(manager);
  cdoEpoch.finalizeDefault(recovered, manager);

  // instantWithdrawClaimsByEpoch[N+1] == 0 so _claimDefaultedInstantWithdrawRequest
  // returns 0, then attacker is paid the full aggregate at par:
  uint256 balPre = underlying.balanceOf(attacker);
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();
  assertEq(underlying.balanceOf(attacker) - balPre, fullAmount); // not fullAmount * defaultRecoveryPrice / 1e18
}
```

The asserted par payout on an unfunded receipt — versus the haircutted `defaultRecoveryPrice` every other claimant receives — demonstrates the broken loss-waterfall invariant.
