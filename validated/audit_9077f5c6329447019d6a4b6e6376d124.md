### Title
Instant-withdraw receipt counters are never decremented on claim, enabling a double-counted default-recovery payout - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestInstantWithdraw` increments three counters: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (the latter two are the per-epoch "refcounts"). The normal claim path `claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never releases the per-epoch basis. Those stale counters are later consumed by `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` and by `_claimDefaultedInstantWithdrawRequest`, so an already-paid receipt is counted a second time during default finalization — the same class as the missing `of_node_put()` refcount leak in the advisory.

### Finding Description
Relevant code:

- `requestInstantWithdraw` (lines 356-375): increments `instantWithdrawsRequestsByEpoch[user][epoch]`, `instantWithdrawClaimsByEpoch[epoch]` and `pendingInstantWithdraws`.
- `claimInstantWithdrawRequest` (lines 380-393): burns `instantWithdrawsRequests[_user]` and sets it to 0, then `_transferFundedClaim` pays underlying. It never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch` — the "put" is missing.
- Only `_claimDefaultedInstantWithdrawRequest` (lines 842-856) decrements those per-epoch counters.

Attack trace (instant-withdraw mode enabled, unprivileged KYC'd user):

1. Epoch N running. User calls `requestInstantWithdraw(X)`. `instantWithdrawsRequestsByEpoch[u][N] = X`, `instantWithdrawClaimsByEpoch[N] = X`, `pendingInstantWithdraws = X`.
2. CDO funds the request via `getInstantWithdrawFunds` → `collectInstantWithdrawFunds(X)`: `pendingInstantWithdraws → 0`, strategy now holds X underlying earmarked for the user.
3. User calls `claimInstantWithdrawRequest` and receives X at par. `instantWithdrawsRequestsByEpoch[u][N]` and `instantWithdrawClaimsByEpoch[N]` still equal X (leak).
4. Still inside epoch N, the user calls `requestInstantWithdraw(Y)`. Now `instantWithdrawClaimsByEpoch[N] = X + Y`, `instantWithdrawsRequestsByEpoch[u][N] = X + Y`, `pendingInstantWithdraws = Y`.
5. `stopEpoch` fails / borrower defaults with the Y instant pending unfunded. `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[N] = X + Y`, and `_defaultPrefundedInstantReserve()` returns `instantBasis - pendingInstant = X` — phantom cash, because the X underlying already left the contract at step 3.
6. `finalizeDefaultRecovery` computes `recoveryPrice` over the inflated basis and a reserve that does not actually contain the claimed X portion for others. The user then calls `claimWithdrawRequest`/`claimInstantWithdrawRequest`, and `_claimDefaultedInstantWithdrawRequest` pays `(X + Y) * defaultRecoveryPrice` from `defaultRecoveryReserve`, even though X was already paid in full.

Broken invariant: one receipt, one payout. The reserve is finite, so every extra unit paid to the attacker is taken directly from the recovery share of other pending claimants and active LPs.

### Impact Explanation
Direct theft of default-recovery funds up to the attacker's previously claimed instant amount `X` (scaled by `defaultRecoveryPrice`). The attacker can repeat steps 1-4 with multiple claim-then-request cycles in the same epoch to compound the inflated basis. Because `_transferDefaultRecovery` debits `defaultRecoveryReserve`, other claimants' payouts are reduced or the last claimants' claims revert on underflow — quantified loss equal to `X * defaultRecoveryPrice` stolen per leaked receipt.

### Likelihood Explanation
Requires (a) instant withdrawals enabled by the manager, (b) funding of the first request within the same epoch so it can be claimed, and (c) a borrower default while a second same-epoch instant request is still pending. All steps use only unprivileged user calls; the default is an ordinary protocol event, not attacker-controlled privilege. The missing decrement exists unconditionally in `claimInstantWithdrawRequest`, so no race or precision edge is needed — only the honest epoch flow.

### Recommendation
Mirror the decrement already present in `_claimDefaultedInstantWithdrawRequest`: in `claimInstantWithdrawRequest`, zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (and subtract it from `instantWithdrawClaimsByEpoch[epochNumber]`) for the epoch(s) being claimed, so paid receipts are released from per-epoch accounting exactly like the kernel fix releases the node refcount with `of_node_put()`. Care is needed to attribute the claim to the correct request epoch if receipts can span epochs.

### Proof of Concept
A Foundry fork test would: enable instant withdrawals via `setInstantWithdrawParams`; deposit with a user; `startEpoch`; `requestInstantWithdraw` X; trigger `getInstantWithdrawFunds`; `claimInstantWithdrawRequest` (assert `instantWithdrawClaimsByEpoch[epoch]` remains nonzero — the leak); `requestInstantWithdraw` Y in the same epoch; stop epoch with insufficient borrower funds to force default; `finalizeDefault` with a partial recovery; show `defaultPendingClaimBasis()` includes X+Y and the user's defaulted claim pays on the X+Y basis, while the reserve lacks the already-paid X — leaving later claimants short. (Note: I was unable to fully verify the exact timing window for a second same-epoch instant request against `setInstantWithdrawParams` delay gating and the `getInstantWithdrawFunds` flow in `IdleCDOEpochVariant.sol`, which should be confirmed when writing the PoC.)
