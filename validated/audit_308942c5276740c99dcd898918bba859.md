### Title
Missing minimum-output / maximum-shares-burned protection in JupLend and Drift withdraw CPI integrations - ([File: programs/marginfi/src/instructions/juplend/withdraw.rs])

### Summary
`juplend_withdraw` and `drift_withdraw` compute the amount of shares (fTokens / scaled balance) to burn from a freshly-fetched, mutable exchange rate/oracle price, then perform the withdrawal without any user-supplied bound on how many shares/scaled-balance units may be consumed. This is the same bug class as the reported SEuroOffering issue: the caller has no way to cap the "price" they're willing to pay (in shares burned) for a fixed amount of underlying, exposing them to unfavorable execution if the rate moves between transaction construction and landing.

### Finding Description
`juplend_withdraw` refreshes the JupLend `token_exchange_price` via `cpi_update_rate()` immediately before computing `shares_to_burn = expected_shares_for_withdraw_from_rate(amount, lending.token_exchange_price)` [1](#0-0) [2](#0-1) . The function signature only accepts `amount: u64` and `withdraw_all: Option<bool>` — there is no `min_amount_out` or `max_shares_to_burn` parameter [3](#0-2) . The `withdraw_all` branch similarly recomputes `token_amount`/`shares_to_burn` from the live exchange price with no bound the caller can enforce [4](#0-3) .

Notably, the underlying JupLend Earn program that marginfi integrates with *does* expose slippage-protected variants — `deposit_with_min_amount_out` and `redeem_with_min_amount_out`, both of which take an explicit `min_amount_out: u64` argument [5](#0-4) [6](#0-5) . Marginfi's `juplend_withdraw`/`juplend_deposit` CPI wrappers do not use or expose this protection to marginfi account owners.

The Drift integration follows the identical pattern: `drift_withdraw` also takes only `amount: u64` and `withdraw_all: Option<bool>`, fetches a fresh oracle price for rate-limiting purposes only (not for slippage protection), and computes `expected_scaled_balance_change` from current bank state without a caller-supplied bound [7](#0-6) .

### Impact Explanation
If the JupLend `token_exchange_price` (interest rate model output) or Drift's spot market accounting shifts unfavorably between the time a user/keeper signs the transaction and when it lands on-chain — due to interest accrual, another party's deposit/withdraw in the same slot, or admin rate-model updates — the marginfi account will burn more shares (fTokens or scaled balance) than the user intended for the same requested underlying `amount`. This is a direct, quantifiable value loss to the marginfi account owner with no on-chain mechanism to prevent it, unlike the JupLend program itself which supports this exact protection via `min_amount_out`.

### Likelihood Explanation
Interest-bearing/rate-model integrations like JupLend routinely update `token_exchange_price` via `update_rate`, and marginfi explicitly triggers this refresh (`cpi_update_rate()`) immediately before computing the burn amount, meaning the rate used is deliberately the freshest — but still not bounded — value at execution time [1](#0-0) . Any transaction that takes multiple slots to land (common on Solana under load, or when composed with other instructions/CPIs) is exposed. This does not require a privileged actor — any account owner calling withdraw is affected.

### Recommendation
Add an optional `min_amount_out` (for deposit, minting shares) or `max_shares_to_burn` (for withdraw) parameter to `juplend_withdraw`, `juplend_deposit`, `drift_withdraw`, and `drift_deposit`, and add a `require!`/`check!` after computing `shares_to_burn`/`expected_scaled_balance_change` that reverts if the computed value exceeds (for burns) or falls short of (for outputs) the caller-specified bound. Where possible, prefer routing through the underlying protocol's native slippage-protected CPI instructions (e.g., JupLend's `redeem_with_min_amount_out`, `deposit_with_min_amount_out`) instead of the unprotected variants.

### Proof of Concept
1. User calls `juplend_withdraw(amount = 1000)` intending to redeem 1000 underlying tokens, expecting to burn approximately `shares_to_burn_A` fTokens based on the exchange rate at transaction-build time.
2. Before the transaction lands, `token_exchange_price` decreases (e.g., due to another user's large withdrawal/rate-model recalculation or a delayed `update_rate` catching up on stale interest).
3. `juplend_withdraw` refreshes the rate via `cpi_update_rate()` [1](#0-0)  and recomputes `shares_to_burn = expected_shares_for_withdraw_from_rate(1000, new_lower_price)` [8](#0-7) , which is now larger than `shares_to_burn_A`.
4. The transaction proceeds and succeeds, burning more fTokens than the user expected for the same 1000 underlying tokens received — with no `min_amount_out`/`max_shares_to_burn` check available to abort the transaction.

pub fn drift_withdraw<'info>(
    ctx: Context<'info, DriftWithdraw<'info>>,
    amount: u64,
    withdraw_all: Option<bool>,
) -> MarginfiResult {
    let withdraw_all = withdraw_all.unwrap_or(false);
    let authority_bump: u8;
    let market_index: u16;

    ctx.accounts.cpi_update_spot_market_cumulative_interest()?;

    let clock = Clock::get()?;

    let bank_key = ctx.accounts.bank.key();
    let bank_mint = ctx.accounts.bank.load()?.mint;
    let group = ctx.accounts.group.load()?;
    let (token_amount, expected_scaled_balance_change, share_amount) = {
        let mut marginfi_account = ctx.accounts.marginfi_account.load_mut()?;
        let mut bank = ctx.accounts.bank.load_mut()?;
        authority_bump = bank.liquidity_vault_authority_bump;

        validate_bank_state(&bank, InstructionKind::FailsInPausedState)?;

        // Fetch oracle price for rate limiting and deleverage tracking
        let in_receivership_or_order_execution =
            marginfi_account.get_flag(ACCOUNT_IN_RECEIVERSHIP | ACCOUNT_IN_ORDER_EXECUTION);
        // When group rate limiter is enabled, oracle is required
        let group_rate_limit_enabled = group.rate_limiter.is_enabled();
        let price = if in_receivership_or_order_execution || group_rate_limit_enabled {
            let price = fetch_asset_price_for_bank_low_bias(
                &bank_key,
                &bank,
                &clock,
                ctx.remaining_accounts,
            )?;

            // Validate price is non-zero during liquidation/deleverage to prevent exploits with stale oracles
            if in_receivership_or_order_execution {
                check!(price > I80F48::ZERO, MarginfiError::ZeroAssetPrice);
            }

            price
        } else {
            I80F48::ZERO
        };
