I've confirmed the vulnerability in `multisig2/src/lib.rs`. Let me finalize the analysis.

**Root cause confirmed:** `delete_member` (line 356-379) only cleans up requests where the deleted member is the *original signer* (`r.member == member`, line 365), removing those requests and their confirmations. But it does **not** scan `self.confirmations` for entries where the deleted member appears as a *confirmer* on requests they didn't originate. Those stale confirmation strings remain in the `HashSet<String>` stored per `request_id`. `confirm()` (line 294-315) then counts `confirmations.len() as u32 + 1 >= self.num_confirmations` without ever re-validating that each entry in the confirmations set still belongs to `self.members` — so a removed member's confirmation keeps counting toward the threshold.

### Title
Stale Confirmations From Deleted Multisig Members Allow Request Execution Below Live Threshold - (multisig2/src/lib.rs)

### Summary
`MultiSigContract::delete_member` in [1](#0-0)  only removes requests and confirmations where the removed member is the request's original creator (`r.member == member`). It never scans the `confirmations` map for other outstanding requests on which the removed member had already cast a confirmation as a co-signer. `confirm()` at [2](#0-1)  counts `confirmations.len() + 1 >= self.num_confirmations` without validating that stored confirmer identities are still in `self.members`.

### Finding Description
This is the same bug class as the reported `applyDiffToCounters` issue: a counter (bucket value / confirmation count) is not reset/cleaned when the underlying entity it tracks changes state (expiry moved to new bucket / member removed from multisig), so the counter retains stale contributions and no longer reflects reality.

Binding broken: `confirmations.len() == count of currently-live members who approved` should always hold. After a `DeleteMember` action executes, this equality breaks for any request the deleted member had confirmed but did not create — the confirmation is counted, but the member no longer exists.

Concretely:
1. Multisig has `num_confirmations = 3`, members `{A, B, C, D}`.
2. `A` creates request `R` (`add_request`), `D` confirms `R` (`confirm`) — `confirmations[R] = {D}`, len 1.
3. Separately, members execute a `DeleteMember { member: D }` request (reaching threshold via other, valid confirmations). `delete_member` iterates `self.requests` filtering on `r.member == D` — but `R.member == A`, not `D`, so `R` is untouched and `confirmations[R]` still contains `D`.
4. `D` is now removed from `self.members` and its access key deleted.
5. `B` confirms `R`: `confirmations[R].len() (1) + 1 = 2 < 3` → stored, `confirmations[R] = {D, B}`.
6. `C` confirms `R`: `confirmations[R].len() (2) + 1 = 3 >= 3` → `R` executes.

`R` executed with confirmations from `{D, B, C}`, but `D` is no longer a member — only 2 live members (`B`, `C`) plus the original creator `A` (who never re-confirmed) actually authorized it. The threshold of 3 live-member approvals was never met.

### Impact Explanation
This directly matches the "Critical" category: *a multisig request executed below threshold*. An attacker who is about to be removed (or colludes with someone who will be removed) can pre-confirm arbitrary pending requests (transfers, `AddKey`, `DeployContract`, etc.) before leaving/being removed, and that phantom confirmation persists to help push through unrelated future actions with fewer live approvers than configured, undermining the K-of-N custody guarantee the contract exists to provide.

### Likelihood Explanation
No special privilege is required beyond being a legitimate member at the time of confirming — this is exactly the trust boundary "an account trusted as a multisig member versus the code that enforces that trust" the scope calls out. The only precondition is that a `DeleteMember` action is executed at some point (a normal, expected multisig operation, not requiring the foundation or an owner outside the multisig's own governance) while the removed member has outstanding confirmations on other pending requests — a realistic operational scenario (e.g., removing a compromised or departing member).

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` (not just requests originated by the member) and remove the deleted member's entry from every confirmation set, e.g.:
```rust
for (request_id, mut confs) in self.confirmations.iter() {
    if confs.remove(&member.to_string()) {
        self.confirmations.insert(&request_id, &confs);
    }
}
```
Alternatively, validate in `confirm()` that every stored confirmer is still present in `self.members` before counting it toward the threshold.

### Proof of Concept
See step sequence in Finding Description: `add_request` by A → `confirm` by D → execute `DeleteMember{D}` request → `confirm` by B → `confirm` by C causes execution with only 2 confirmations from currently-live members against `num_confirmations = 3`, reproducible directly against [3](#0-2)  and [4](#0-3) .

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
