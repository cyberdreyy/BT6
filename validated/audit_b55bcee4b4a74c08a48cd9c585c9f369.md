### Title
Unfunded instant-withdraw receipts from earlier epochs are excluded from the default-recovery claim basis, permanently freezing them and diluting the recovery price — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Derby bug class is a cumulative ledger that keeps growing while its counterpart resets each cycle, so the two are compared inconsistently. The idle-tranches analog is in `IdleCreditVault`'s instant-withdraw accounting: `pendingInstantWithdraws` is a cumulative aggregate spanning all epochs, while `instantWithdrawClaimsByEpoch` (the basis used at default finalization) is per-epoch. When `pendingInstantWithdraws` carries an unfunded remainder from a previous epoch into the default epoch, `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` mix the aggregate remainder with the current-epoch-only basis. Old unfunded instant receipts end up in neither the recovery basis nor the funded bucket: their recovery claim clears nothing, and their funded claim reverts on the reserve guard.

### Finding Description
`requestInstantWithdraw` increments both the per-user aggregate `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawClaimsByEpoch[epochNumber]`, plus the global `pendingInstantWithdraws` (`IdleCreditVault.sol:366-374`). At `startEpoch`, `IdleCDOEpochVariant` calls `collectInstantWithdrawFunds(min(pendingInstant, totUnderlyings))`, which decrements `pendingInstantWithdraws` by only what was actually collected (`IdleCreditVault.sol:398-403`, `IdleCDOEpochVariant.sol:279-290`). If the CDO's cash covered only part of the queue, a positive remainder survives.

That remainder can persist across epochs: it is only funded at `startEpoch`, and claims are paid from strategy balance via `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`), which pays `instantWithdrawsRequests[_user]` — the cumulative aggregate — 1:1.

At default finalization, `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch only — to the basis whenever `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`). The stale remainder from epoch N is counted in `pendingInstantWithdraws` (driving `defaultInstantWithdrawsFinalized = true` and suppressing `prefundedReserve` via `_defaultPrefundedInstantReserve`, lines 716-723) but the epoch-N receipts themselves are *not* in the basis. Consequences:

1. An epoch-N claimant calling `claimInstantWithdrawRequest` gets `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch] = 0` in `_claimDefaultedInstantWithdrawRequest` (line 844), so nothing is cleared; then `amount = instantWithdrawsRequests[_user]` hits `_transferFundedClaim`'s reserve guard (`balance - reserve < amount → revert`, lines 899-905) because all underlying was swept into `defaultRecoveryReserve` at finalization. The receipt is permanently frozen.
2. `defaultRecoveryPrice = reserveAmount / totalBasis` (line 688) is computed over a basis that omits the old instant claims, so every included claimant is overpaid relative to the fair pro-rata share — the frozen claimant's recovery is effectively redistributed to others.
3. `_claimDefaultedInstantWithdrawRequest` line 852 (`pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis`) clamps the aggregate when a current-epoch claim exceeds the remaining pending, masking the cross-epoch overlap rather than correcting it.

Sequence (all attacker actions unprivileged): epoch N — users request instant withdrawals; pool cash at `startEpoch` covers only part (borrower drawn, honest), remainder R stays pending. Epoch N+1 buffer — requests resume; a new instant request lands in epoch N+1. Borrower defaults and recovery is finalized. Epoch-N claimant's R is frozen; recovery claimants are diluted/overpaid by the same R.

### Impact Explanation
Permanent freezing of the stale instant receipts' recovery value (quantified loss = the unfunded remainder R, up to the entire instant queue), plus mispricing of `defaultRecoveryPrice` that shifts that value to other claimants — a direct solvency/fair-payout invariant break, matching "permanent freezing + theft of unclaimed recovery."

### Likelihood Explanation
Requires a partial instant-withdraw funding at `startEpoch` (happens whenever pool cash < pending instant requests — normal when the borrower is fully drawn), the remainder surviving until a later epoch that itself has instant requests, and a subsequent default. Each step is reachable through ordinary usage; none requires a privileged or malicious actor. The window is narrow but the state, once created, is irreversible.

### Recommendation
Make the default basis epoch-agnostic for unfunded instant receipts: have `defaultPendingClaimBasis()` include the full `pendingInstantWithdraws` remainder (or track a cumulative unfunded instant basis), and let `_claimDefaultedInstantWithdrawRequest` settle receipts from *any* epoch whose basis was never funded — e.g., iterate/aggregate `instantWithdrawsRequestsByEpoch` or keep a global `unfundedInstantBasis` that `collectInstantWithdrawFunds` decrements alongside `pendingInstantWithdraws`.

### Proof of Concept
Reproducible Foundry fork PoC sketch: (1) deposit via `IdleCDOEpochVariant`, `startEpoch` with borrower fully drawn; (2) `requestInstantWithdraw` for amount A > available cash → `pendingInstantWithdraws = A`, partial collect; (3) `stopEpoch`, buffer, new instant request B in epoch N+1; (4) trigger `_handleBorrowerDefault`/`finalizeDefault` + `finalizeDefaultRecovery`; assert `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch] == B` while `pendingInstantWithdraws` included A; (5) `claimInstantWithdrawRequest` for the epoch-N user reverts in `_transferFundedClaim` (balance == reserve) — permanent freeze of A, and `defaultRecoveryPrice` is inflated by excluding A from `totalBasis`.
