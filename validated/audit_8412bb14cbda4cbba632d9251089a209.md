Let me look at the APR0 and instant-withdraw alias accounting in `IdleCreditVault`.Let me check whether instant withdraw requests can persist unfunded across epochs and whether repeat requests are allowed.### Title
Unfunded instant-withdraw receipts from prior epochs bypass the default-recovery haircut through the aggregate `instantWithdrawsRequests` alias - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks instant-withdraw receipts under two aliases: a per-epoch mapping (`instantWithdrawsRequestsByEpoch[user][epoch]` / `instantWithdrawClaimsByEpoch[epoch]`) and a per-user aggregate (`instantWithdrawsRequests[user]`). On borrower default, `finalizeDefaultRecovery` sizes the haircut basis using only the *current* epoch alias (`instantWithdrawClaimsByEpoch[epochNumber]`), and `_claimDefaultedInstantWithdrawRequest` only clears the `defaultRecoveryEpoch` bucket. Any instant receipt recorded under an earlier epoch key is never haircut — it survives in the aggregate alias and is later paid 1:1 by `claimInstantWithdrawRequest` via `_transferFundedClaim`, directly analogous to `sourceConfig`/`runtimeConfig` surviving `config.get` redaction in GHSA-8372-7vhw-cm6q.

### Finding Description
- `requestInstantWithdraw` writes both aliases: `instantWithdrawsRequests[_user] += _amount` and `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` plus `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (`IdleCreditVault.sol:366-374`). Receipts are not burned at request time; they persist until claimed, and `pendingInstantWithdraws` is only decremented when the CDO calls `collectInstantWithdrawFunds` (`:398-403`). An instant receipt that is not funded before `stopEpoch` therefore carries into the next epoch under its original epoch key.
- `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — to the recovery basis (`:644-649`). Receipts filed under earlier epoch keys are excluded from `totalBasis`, so `defaultRecoveryReserve` is sized as if they did not exist.
- `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` and pays `defaultRecoveryPrice` (`:842-856`).
- `claimInstantWithdrawRequest` then pays whatever remains in the aggregate alias: `amount = instantWithdrawsRequests[_user]; _burn(_user, amount); _transferFundedClaim(_user, amount)` — at par, un haircut (`:387-392`).

Attack sequence (instant mode, fixed-APR variant):
1. Epoch N running: attacker calls `cdoEpoch.requestInstantWithdraw` for X. It is not funded before epoch end (`collectInstantWithdrawFunds` never called for it), so `pendingInstantWithdraws` stays > 0 across `stopEpoch` and `startEpoch` into epoch N+1. The receipt sits under `instantWithdrawsRequestsByEpoch[attacker][N]`.
2. During epoch N+1 the borrower defaults; manager/owner call the default flow and `finalizeDefaultRecovery` runs with `defaultRecoveryEpoch = N+1`. `defaultPendingClaimBasis` counts only `instantWithdrawClaimsByEpoch[N+1]`; the attacker's epoch-N receipt contributes zero basis and zero haircut.
3. `defaultInstantWithdrawsFinalized` is set (`:696`); attacker calls `cdoEpoch.claimInstantWithdrawRequest()`. `_claimDefaultedInstantWithdrawRequest` finds `instantWithdrawsRequestsByEpoch[attacker][N+1] == 0` and returns; the fallback then pays the full aggregate `instantWithdrawsRequests[attacker] = X` at par from strategy-held underlying — i.e., from `defaultRecoveryReserve`.

### Impact Explanation
The recovery reserve is sized for basis that excludes the stale receipt, but the payout path honors it at 100%. Every such receipt is paid X instead of `X * defaultRecoveryPrice / 1e18`, overdrawing `defaultRecoveryReserve` (enforced only implicitly by the token balance in `_transferDefaultRecovery`). Concretely, with a 50% recovery price the attacker doubles their claim; the shortfall is socialized onto defaulted-epoch claimants and active tranche holders whose recovery payouts revert or are reduced — direct theft of recovery funds, quantified as `X * (1 - recoveryPrice)` per stale receipt.

### Likelihood Explanation
Requires only that an instant-withdraw receipt remain unfunded across one epoch boundary (a routine outcome when instant liquidity is insufficient at epoch end — the code explicitly supports partially-funded instant queues via `_defaultPrefundedInstantReserve`) and a subsequent borrower default, which is a designed-for state. The attacker is an ordinary KYC'd lender; no privileged role is needed. One caveat I could not fully verify within the search budget: whether `IdleCDOEpochVariant.requestInstantWithdraw` reverts when a prior unfunded receipt exists — even if repeat requests are blocked, a single unfunded request made in epoch N-1 and surviving into default epoch N triggers the same bypass, since only the *current* epoch key is haircut.

### Recommendation
In `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest`, iterate (or accumulate) `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` across all epochs with pending receipts — or maintain a single aggregate `pendingInstantClaimBasis` that all unfunded instant receipts share — so every unfunded instant receipt receives `defaultRecoveryPrice`, not just those keyed to `defaultRecoveryEpoch`. Equivalently, in `claimInstantWithdrawRequest`, route the aggregate remainder through the recovery price whenever `defaultRecoveryFinalized` and the underlying tokens come from `defaultRecoveryReserve`.
