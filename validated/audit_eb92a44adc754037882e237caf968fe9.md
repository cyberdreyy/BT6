## Analysis

`check_block_against_signer_db_state` confirms my analysis: for a tenure-change block (block B, the tenure-start block of T2), the only chainstate re-check performed is `check_tenure_change_confirms_parent`, which validates against the **parent tenure that B's tenure-change payload claims** — not against a sibling tenure T1 that forked independently off the same grandparent. [1](#0-0)  Two sibling tenure-start blocks built off the same common ancestor (the classic same-sortition-race scenario) never have one checked against the other by this re-check.

That means the *only* protection against signing both A (tenure T1) and B (tenure T2) at the same height is the `get_signed_conflicts` / `conflict_still_blocks` guard in `handle_block_pre_commit`. [2](#0-1)  Tracing that guard:

- The fresh-conflict branch (lines 1403–1421) only blocks when `conflict.last_endorsed > freshness_cutoff` **and** `conflict_still_blocks` returns true — i.e., staleness short-circuits the chain-liveness check entirely for cross-tenure conflicts. [3](#0-2) 
- The only fallback for a **stale** conflict is the second block (lines 1432–1457), and it is explicitly scoped to `conflict.consensus_hash == block_info.block.header.consensus_hash` — i.e., it only re-checks a stale conflict in the **same tenure** as the proposed block via `get_tenure_tip`. [4](#0-3) 

So a stale conflict in a **different** tenure gets zero re-verification against the node's actual chain state — it is unconditionally treated as no-longer-blocking, based purely on the wall-clock `last_endorsed` timestamp. The code comment even states the (incorrect) assumption that "whether this block may replace what another tenure built is settled by the chainstate checks above," but as shown, the chainstate re-check (`check_tenure_change_confirms_parent`) does not examine a non-parent sibling tenure at all. [5](#0-4) 

Critically, the existing test suite confirms this gap is untested: every `run_cross_tenure_scenario` test uses a wide-open freshness window (`Duration::from_secs(100_000)`) so A's signature is fresh throughout, and `conflict_whose_sortition_is_canonical_still_blocks_signing` only proves the guard works correctly *while fresh*. [6](#0-5) [7](#0-6)  None of the "stale" tests (`stale_sibling_still_refused_when_canonical_tip_at_height`, `stale_sibling_replaced_when_canonical_tip_below`) use `run_cross_tenure_scenario`; they only use `run_sibling_scenario`, i.e., same-tenure siblings. [8](#0-7)  There is no test proving a stale cross-tenure conflict whose underlying chain is still live/canonical gets refused — and per the code trace, it would not be refused.

### Title
Stale cross-tenure conflicting signature is signed without any chain-liveness recheck, enabling a same-height chain split - (`stacks-signer/src/v0/signer.rs`)

### Summary
`handle_block_pre_commit`'s conflict guard only calls `conflict_still_blocks` (the node-derived liveness check) for conflicts that are still "fresh" by wall-clock (`last_endorsed > freshness_cutoff`). Once a conflicting signature in a **different** tenure goes stale, the code falls into a branch that only re-verifies same-tenure conflicts via `get_tenure_tip`, silently treating any stale cross-tenure conflict as dead with no chain-state verification at all.

### Finding Description
The intended invariant (documented in `docs/signer-flows.md` and in the code comments) is that a conflicting signature should only stop blocking when it is proven stale by the node — via burn-chain orphan proof or chain-reach proof (`conflict_still_blocks`) — never merely by local wall-clock timeout for a genuinely live conflict in another tenure.

In `handle_block_pre_commit`, the freshness cutoff is `get_epoch_time_secs() - tenure_last_block_proposal_timeout` [9](#0-8) , and the guard is:
```rust
if let Some(conflict) = conflicts.iter().find(|conflict| {
    conflict.last_endorsed > freshness_cutoff
        && !self.reorg_permit_stands(stacks_client, conflict)
        && self.conflict_still_blocks(...)
}) { ... refuse ... }
```
`conflict_still_blocks` — the function that asks the node whether the conflicting tenure's sortition is still canonical and whether the conflicting block is still reachable — is only invoked when the `last_endorsed > freshness_cutoff` condition is true (short-circuit `&&`). For any conflict with `last_endorsed <= freshness_cutoff` (stale by the local clock), this per-evaluation liveness check is skipped entirely.

The only remaining check (lines 1432–1457) filters to `conflict.consensus_hash == block_info.block.header.consensus_hash`, i.e., it only re-verifies stale conflicts that are in the **same tenure** as the proposal being evaluated. A stale conflict from a **sibling tenure** (e.g., A in tenure T1, B a tenure-start block for T2, both children of the same parent) is excluded from both checks and falls straight through to "SIGN."

The comment justifying this ("whether this block may replace what another tenure built is settled by the chainstate checks above") is incorrect for this case: `check_block_against_signer_db_state` → `check_tenure_change_confirms_parent` only validates B against **B's own tenure-change parent tenure**, never against an unrelated sibling tenure T1. [1](#0-0) 

**Attacker's exact message sequence** (single miner slot, BTC timing only):
1. Win a sortition/tenure T1 at height h-1's tip, propose block A at height h; get it signed by (some/most) signers (`signed_self`/`signed_group` recorded).
2. Time the next BTC block / tenure T2 sortition win, and propose a competing tenure-start block B at height h off the same parent, such that by the time B's pre-commits cross the 70% weight threshold, `tenure_last_block_proposal_timeout` seconds have elapsed since each relevant signer's `last_endorsed` time on A.
3. For each signer whose freshness cutoff has passed, `conflict_still_blocks` is never invoked; `reorg_permit_stands`/tip-check for T1 is never invoked either (since T1 ≠ B's own consensus_hash). The signer signs B unconditionally.
4. Because A's signature is a "bearer instrument" per the code's own documentation (rejection doesn't clear it), if enough signers (or even the same signer set at slightly different times) already signed A and now also sign B, both blocks can reach ≥70% weight, producing two validly-signed, conflicting blocks at height h.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property that the "conflict must remain live whenever the underlying chain could still finalize it." A single unprivileged miner-slot holder can induce signers to place valid signatures on two conflicting blocks at the same height in different tenures, which is exactly the double-sign scenario the guard exists to prevent — matching the Critical impact category ("a signer signing an invalid, non-canonical, or conflicting block; chain safety"). This is repeatable each time a miner wins two consecutive/competing tenure slots and can control proposal timing relative to `tenure_last_block_proposal_timeout`.

### Likelihood Explanation
Preconditions: the attacker needs to win a single miner slot for T1 (get A signed), then win a subsequent slot for T2 and propose a competing tenure-start block B at the same height, timing B's pre-commit-threshold crossing to occur after `tenure_last_block_proposal_timeout` has elapsed relative to individual signers' `last_endorsed` timestamps for A. This requires no signer collusion, no auth_token, and no privileged access — only control over BTC block/proposal timing, which is explicitly listed as attacker-controlled in the preconditions. `tenure_last_block_proposal_timeout` on mainnet is a bounded, known duration, making the timing achievable without needing "one tick" precision — the attacker merely needs B's threshold-crossing to occur any time after the window elapses.

### Recommendation
Remove the short-circuit that skips `conflict_still_blocks`/`reorg_permit_stands` for stale conflicts, or at minimum extend the same-tenure-only re-check at lines 1432–1457 to also cover conflicts in **other** tenures: for any conflict that is stale but whose tenure/block state cannot be proven dead by the node (per the same two questions used in `conflict_still_blocks`), keep the conflict blocking rather than allowing an unconditional fallthrough to `SIGN`. In other words, `conflict_still_blocks` should be evaluated for every conflict regardless of freshness, and freshness should only be used as a fast-path optimization (to skip the node round-trip when we already know a conflict is fresh) — not as a bypass that suppresses the liveness check altogether once a conflict goes stale in a foreign tenure.

### Proof of Concept
Add a test (mirroring `run_cross_tenure_scenario`, but with a short freshness window instead of the current `Duration::from_secs(100_000)`) to `stacks-signer/src/v0/tests.rs`:

```rust

    // tenure_last_block_proposal_timeout so A's signature goes stale before B's pre-commit
    // threshold is reached, while the node still proves tenure 1's sortition canonical and/or
    // its tip still reaches A.
    let (info_a, info_b) = run_cross_tenure_scenario_with_timeout(
        TenureAFate::SortitionStillCanonical,
        Duration::from_secs(1), // freshness window
        Duration::from_secs(2), // delay before B's pre-commit threshold is reached
    );
    assert_a_signed(&info_a);
    // EXPECTED (per the uniqueness invariant): B must NOT be signed, because the node still
    // proves A's tenure is live/canonical -- staleness alone must not clear a genuinely live
    // conflict.
    assert_b_refused(
        &info_b,
        "conflict is stale by wall-clock but still canonical per the node -- must stay blocked",
    );
    // ACTUAL (per current code): conflict_still_blocks/reorg_permit_stands are never invoked
    // for this cross-tenure stale conflict, so B is signed -- demonstrating the split.
```

This requires adding a variant of `run_cross_tenure_scenario` (or a parameterized version) that accepts a configurable `tenure_last_block_proposal_timeout` and an artificial delay before B's pre-commit threshold is reached (analogous to how `run_sibling_scenario` parameterizes the timeout), then asserts `info_b.signed_self.is_none()`. Running it against current code should reveal `info_b.signed_self.is_some()`, confirming the vulnerability.
