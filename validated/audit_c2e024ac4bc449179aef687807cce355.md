### Title
Missing role check on `GET /v2/external_initiators` allows low-privileged authenticated users to enumerate external initiator configurations - ([File: core/web/router.go])

### Summary
The route `authv2.GET("/external_initiators", paginatedRequest(eia.Index))` is registered inside the `authv2` group, so it requires a valid session/API token, but unlike the sibling `POST`/`DELETE` routes on the same resource it is not wrapped in `auth.RequiresEditRole` (or any role check). `ExternalInitiatorsController.Index` itself performs no additional authorization check before returning the full list of configured external initiators.

### Finding Description
In `core/web/router.go`, the external initiator routes are: [1](#0-0) 
`Create` and `Destroy` are explicitly gated with `auth.RequiresEditRole`, but `Index` is only gated by the generic `authv2` authentication middleware (`auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)`), which merely verifies the caller has *some* valid session or API key - it does not check role at all.

`ExternalInitiatorsController.Index` performs no role/permission check of its own; it simply queries `BridgeORM().ExternalInitiators` and returns a paginated list of presenter resources: [2](#0-1) 

Because the Chainlink node RBAC model treats "view"/"run" as lower-privilege roles than "edit"/"admin" (consistent with the pattern used for every other resource in `v2Routes`, e.g. bridge types, jobs, keys, where read endpoints are sometimes open but mutation endpoints are always role-gated), the asymmetry here means any authenticated user regardless of role - including a view-only user or a run-role API token holder, both explicitly listed as in-scope unprivileged attackers for this audit - can call `GET /v2/external_initiators` and enumerate every configured external initiator's name, URL, and incoming access key metadata, even though creating or deleting that same resource is restricted to edit-role users.

### Impact Explanation
This is an authorization-scoping gap: a caller who should only have read/run-level access is able to retrieve the full external initiator configuration inventory of the node (names, callback URLs, incoming access keys) via `presenters.NewExternalInitiatorResource`. This is information disclosure of node integration configuration to a lower-privileged principal than intended, and could aid further attacks (e.g., targeting or fingerprinting the external initiator integrations) even though the plaintext outgoing/incoming secrets themselves are only ever returned once at creation time (`presenters.NewExternalInitiatorAuthentication` in `Create`), and are not exposed by `Index`. It maps to the "authorization bypass / unauthorized access to another privilege tier's data" bounty class rather than full credential compromise, since the highest-value secret fields do not appear to be part of the `Index` presenter.

### Likelihood Explanation
Exploitation only requires possession of any valid, low-privilege authenticated session or API token (e.g., a view-role or run-role user) - no special role, admin access, or social engineering is needed. The request is a single unauthenticated-role `GET /v2/external_initiators` call, fully reproducible and repeatable.

### Recommendation
Wrap the `Index` route with the same minimum role required for managing this resource, e.g. `auth.RequiresEditRole(eia.Index)` (or a dedicated `RequiresViewOfSensitiveConfig` role check), to make read access consistent with write access for external initiators, in `core/web/router.go` line 264.

### Proof of Concept
Handler-level integration test plan (Go):
1. Set up a test app via `cltest.NewApplicationWithConfig` with a seeded external initiator (via `BridgeORM().CreateExternalInitiator`).
2. Create two users: one with `sessions.UserRoleView` (or a run-role API token) and one with `sessions.UserRoleAdmin`.
3. As the view/run-role user, call `GET /v2/external_initiators` with a valid session cookie/API token.
4. Assert HTTP 200 (not 401/403) and that the response body contains the external initiator's `name`/`url`/`incomingAccessKey`, confirming the low-privileged user obtained data intended to be edit/admin-scoped.
5. Contrast with `POST /v2/external_initiators` and `DELETE /v2/external_initiators/:Name` under the same view-role session, asserting HTTP 401/403 (`RequiresEditRole` blocks them), demonstrating the inconsistency between read and write authorization on the same resource.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```
