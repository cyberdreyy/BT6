This confirms the vulnerability: `delete_member` at `multisig2/src/lib.rs:356-379` only purges requests where the deleted member was the original *requester* (`r.member == member`), but never scrubs that member's entries from `self.confirmations` on *other* requests they had already confirmed. `confirm()` at `multisig2/src/lib.rs:294-315` counts raw `confirmations.len()` against `self.num_confirmations` without re-validating that each string in the `HashSet<String>` still corresponds to a current entry in `self.members`.

### Title
Stale confirmations from removed multisig members are still counted toward execution threshold - (File: multisig2/src/lib.rs)

### Summary
A member's confirmation on a pending request is stored as a plain string in the `confirmations: LookupMap<RequestId, HashSet<String>>` map [1](#0-0)  and is never invalidated when that member is later removed via `DeleteMember`. `confirm()` executes a request once `confirmations.len() as u32 + 1 >= self.num_confirmations` [2](#0-1) , counting these stale confirmations as if they came from a live member.

### Finding Description
The binding this contract is supposed to maintain is: *"a request executes only if the number of confirmations from **current** members ≥ `num_confirmations`."* The code instead maintains: *"a request executes if the number of confirmation strings ever recorded ≥ `num_confirmations`,"* regardless of whether the confirming identity is still a member at execution time.

`delete_member` only cleans up requests that the removed member itself originally created:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [3](#0-2) 

It does not scan `self.confirmations` for entries where the removed member appears merely as a *confirmer* on someone else's still-pending request. Those confirmations remain in the `HashSet<String>` for that request.

`confirm()` then trusts the raw set size:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [4](#0-3) 

There is no check that each string in `confirmations` still corresponds to an entry in `self.members` (an `UnorderedSet<MultisigMember>` [5](#0-4) ) at the time of counting.

### Impact Explanation
This breaks the custody/authorization binding directly: *confirmations counted versus live members*. A request can be executed — including a `Transfer` moving NEAR out of the multisig account, an `AddKey`/`AddMember` granting new signing power, or a `FunctionCall` — with fewer genuinely-authorized, currently-valid confirmations than `num_confirmations` requires. This matches the Critical impact category: "a multisig request executed below threshold."

### Likelihood Explanation
No privileged role is required beyond being (or having been) an ordinary multisig member — the same class of actor the multisig is designed to constrain. The sequence only requires: a pending request partially confirmed, then a separate, legitimately-passed `DeleteMember` request removing one of the confirmers, after which the stale confirmation is still honored. This is a normal operational sequence (member rotation) rather than a contrived edge case, making the likelihood high in any multisig that rotates membership while requests are in flight.

### Recommendation
When counting confirmations in `confirm()` (and ideally also when displayed via `get_confirmations`), filter `confirmations` to only those entries where `self.members.contains(&member)` is true, or alternatively have `delete_member` scan all `self.confirmations` entries (not just requests it authored) and remove the deleted member's string from every set, decrementing effectively-cached counts as needed.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3` (`MultiSigContract::new`, `multisig2/src/lib.rs:147-167`).
2. `A` calls `add_request_and_confirm(Transfer{amount: X})` on request `R1` → `confirmations[R1] = {A}`.
3. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (2 of 3, not yet executed, per `multisig2/src/lib.rs:304-314`).
4. Separately, `C` and `D` pass and execute a `DeleteMember{member: A}` request (their own 3-of-4 confirmations, unrelated to `R1`), invoking `delete_member` (`multisig2/src/lib.rs:356-379`). This only removes requests *authored* by `A`; `R1` was authored by `A` too in this specific case — so to keep `A`'s confirmation alive while removing `A` as author, have `B` author `R1` instead of `A` in step 2 (`B` calls `add_request_and_confirm`, then `A` confirms). Now `R1.member == B`, so `delete_member(A)` does not touch `R1`, and `confirmations[R1] = {A, B}` survives A's removal.
5. Members are now `{B, C, D}`, still with `num_confirmations = 3`.
6. `C` calls `confirm(R1)`. `confirmations.len() + 1 == 3 >= num_confirmations`, so `execute_request` fires the `Transfer`, even though only `B` and `C` are *currently valid* confirmers plus a stale confirmation from the removed member `A` — i.e., the request executed with fewer than 3 confirmations from members that are members at execution time.
