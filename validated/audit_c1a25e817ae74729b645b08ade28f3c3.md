### Title
Zip extraction (`ExtractZipArchive`/`lchmod`) permits path-traversal writes and chmod on arbitrary filesystem paths via unsanitized `zip.File.Name` - (File: helpers/archives/zip_extract.go)

### Summary
`ExtractZipArchive` writes and then `lchmod`s every entry using the raw `file.Name` from the zip header with no path-containment check, so a crafted entry such as `../../etc/foo` or an absolute path is passed directly to `os.MkdirAll`, `os.OpenFile`/`os.Symlink`, and then `unix.Fchmodat` (`lchmod`). Unlike the `tarzstd` extractor, which explicitly validates `path` against `e.dir` before any filesystem operation, this legacy zip path has no equivalent root-containment check anywhere in the call chain.

### Finding Description
`extractZipFile` (helpers/archives/zip_extract.go:61-83) computes `filepath.Dir(file.Name)` and calls `os.MkdirAll` on it, then dispatches to `extractZipDirectoryEntry`, `extractZipSymlinkEntry`, or `extractZipFileEntry`, all of which operate on `file.Name` verbatim [1](#0-0) . The only pre-check applied is `errorIfGitDirectory`, which merely rejects paths whose first cleaned path segment is `.git` — it performs no `..`, absolute-path, or root-containment validation [2](#0-1) . `ExtractZipArchive` then runs a second loop that calls `lchmod(file.Name, file.Mode())` on every entry, again using the same raw, unsanitized name, independent of whether the first loop's write actually created that path [3](#0-2) . `lchmod` on unix directly calls `unix.Fchmodat(unix.AT_FDCWD, name, ...)` with no path validation of its own [4](#0-3) .

This code path is reachable from `ExtractZipFile` (opens an arbitrary zip file and calls `ExtractZipArchive`) and from the `ziplegacy` extractor package, which wraps `archives.ExtractZipArchive(zr)` with no directory/chroot argument at all [5](#0-4) . Contrast this with the `tarzstd` extractor, which computes `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` and explicitly rejects anything outside `e.dir` before performing any `Mkdir`/`Create`/`Symlink`/chmod operation [6](#0-5) . The zip legacy path has no analogous guard, so it is a real, exploitable gap relative to the invariant that "no filesystem metadata operation should touch paths outside the extraction root regardless of earlier failures."

Because `extractZipFileEntry`/`extractZipSymlinkEntry` first `os.Remove(file.Name)` before creating, and `extractZipDirectoryEntry` ignores "already exists" errors, the write step can fail for a pre-existing file it doesn't own (e.g., permission denied) while the second loop's `lchmod` call still executes against that same traversal path — chmod does not require write permission on the target file's contents, only appropriate ownership/permission on the metadata operation itself, and as the job/runner user this can still succeed on files the job process can already chmod (e.g., group-writable or user-owned credential/token files shared with other job steps or cached in predictable locations).

### Impact Explanation
An attacker who controls the contents of an artifact/cache zip (or any zip fed to `ExtractZipFile`/`ziplegacy`) can supply an entry name with `../` segments to have `lchmod` invoked against a path outside the intended extraction root. If that path corresponds to a file the runner-invoked process has permission to chmod (e.g., a token/credential file owned by the same user, or with permissions allowing this), the attacker can widen or narrow its permission bits, which could enable other processes/users on a shared host to read the token, or make it unreadable/unusable as a denial-of-service against subsequent job auth. The scoped impact is real given the code is confirmed to lack any containment check, but its severity is bounded by standard OS permission enforcement — it cannot chmod files the runner process lacks permission to modify, and typical single-tenant executors mitigate cross-job impact.

### Likelihood Explanation
Feasibility is high for repeatability (a simple malicious zip is deterministic) but the "not created by this extraction" pre-write success is not required — `lchmod` runs unconditionally after the first loop regardless of whether `extractZipFile` succeeded, confirmed by the loop structure at lines 98-107 [7](#0-6) . The main uncertainty (not fully resolved from index alone) is which real runner code paths actually route job-controlled artifact/cache zips into `ExtractZipFile`/`ziplegacy` versus the `fastzip` extractor (which uses the external `saracen/fastzip` library and may have its own protections) — this selection logic (in `commands/helpers/archiver.go`) was not fully inspected before the tool budget was exhausted, so whether `ziplegacy`/`ExtractZipFile` is reachable by default versus only as a fallback/feature-flagged path is uncertain.

### Recommendation
Add explicit path-containment validation in `extractZipFile` (and before the `lchmod`/`processZipExtra` loop) analogous to the `tarzstd` extractor: resolve each `file.Name` against the intended extraction root with `filepath.Join`+`filepath.Abs`, and reject/skip any entry whose resolved path is not a descendant of that root, before performing any `Mkdir`, `OpenFile`, `Symlink`, or `lchmod` operation. Consider tracking the set of successfully-written paths in the first loop and only chmod'ing those exact paths in the second loop rather than iterating raw `file.Name` again.

### Proof of Concept
```go
// helpers/archives/zip_extract_traversal_test.go
func TestExtractZipArchive_RejectsTraversalChmod(t *testing.T) {
    tmp := t.TempDir()
    outside := filepath.Join(tmp, "outside", "secret_token")
    require.NoError(t, os.MkdirAll(filepath.Dir(outside), 0755))
    require.NoError(t, os.WriteFile(outside, []byte("token"), 0600))

    extractDir := filepath.Join(tmp, "extract_root")
    require.NoError(t, os.MkdirAll(extractDir, 0755))

    buf := new(bytes.Buffer)
    zw := zip.NewWriter(buf)
    fh := &zip.FileHeader{Name: "../outside/secret_token"}
    fh.SetMode(0777)
    fw, _ := zw.CreateHeader(fh)
    fw.Write([]byte("attacker data"))
    zw.Close()

    // simulate extraction rooted at extractDir (caller would chdir or pass dir)
    origWD, _ := os.Getwd()
    defer os.Chdir(origWD)
    os.Chdir(extractDir)

    zr, _ := zip.NewReader(bytes.NewReader(buf.Bytes()), int64(buf.Len()))
    _ = ExtractZipArchive(zr)

    info, err := os.Stat(outside)
    require.NoError(t, err)
    // Assert mode was NOT changed to attacker-supplied 0777
    assert.NotEqual(t, os.FileMode(0777), info.Mode().Perm(),
        "lchmod must not modify files outside the extraction root")
}
```
Expected result with current code: the assertion fails because `lchmod("../outside/secret_token", 0777)` succeeds and changes the mode, proving the traversal-chmod bug; after adding root-containment validation, the entry should be skipped/rejected and the assertion passes.

```go
func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}
```

```go
func lchmod(name string, mode os.FileMode) error {
	var flags int

	if runtime.GOOS == "linux" {
		// Linux does not support changing modes on symlinks.
		if mode&os.ModeSymlink != 0 {
			return nil
		}
	} else {
		flags = unix.AT_SYMLINK_NOFOLLOW
	}

	err := unix.Fchmodat(unix.AT_FDCWD, name, uint32(mode.Perm()), flags)
	if err != nil {
		return &os.PathError{Op: "lchmod", Path: name, Err: err}
	}
	return nil
}
```
