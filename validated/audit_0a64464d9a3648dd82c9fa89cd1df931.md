## Title
Missing re-initialization guard in `LockupContract::new` allows anyone to reset owner and release schedule, unlocking custodied NEAR early - (File: `lockup/src/lib.rs`)

## Summary
`LockupContract::new` is annotated `#[init]` but, unlike every other constructor in this repository, does not check `env::state_exists()` before writing state. `near-sdk`'s `#[init]` attribute does not itself enforce single-call semantics on this SDK version — that guard is added manually in every sibling contract. Because it is missing here, any account can call `new` on an already-initialized lockup contract at any time and overwrite `owner_account_id`, `lockup_information` (lockup/release schedule), `vesting_information`, `staking_pool_whitelist_account_id`, and `foundation_account_id`.

## Finding Description
Compare the constructors across the repo:
- `staking-pool/src/lib.rs` `new`: `assert!(!env::state_exists(), "Already initialized");` [1](#0-0) 
- `staking-pool-factory/src/lib.rs` `new`: `assert!(!env::state_exists(), "The contract is already initialized");` [2](#0-1) 
- `whitelist/src/lib.rs` `new`: `assert!(!env::state_exists(), "Already initialized");` [3](#0-2) 
- `lockup-factory/src/lib.rs` `new`: `assert!(!env::state_exists(), "The contract is already initialized");` [4](#0-3) 
- `multisig/src/lib.rs` `new`: `assert!(!env::state_exists(), "Already initialized");` [5](#0-4) 

`lockup/src/lib.rs`'s `new` has no equivalent check anywhere in its body — it validates the account IDs and vesting arguments, but never checks whether the contract state already exists before constructing and returning `Self { .. }`: [6](#0-5) 

Because `near_bindgen`/`#[init]` on this SDK version only wires up the exported ABI entrypoint and persists whatever `Self` the function returns — it does not itself refuse to run if state already exists (that is why every sibling contract adds the explicit assert). Consequently, `new` on a live `LockupContract` can be called again by anyone, at any time, fully overwriting the previous state, including:
- `owner_account_id` — the exclusive holder of `owner`-only privileges (see `assert_owner` in `lockup/src/internal.rs`) [7](#0-6) 
- `lockup_information.lockup_timestamp` / `release_duration` / `transfers_information` — the schedule binding how much of the custodied NEAR is releasable at any given time
- `vesting_information` and `foundation_account_id` — which govern whether NEAR Foundation can claw back unvested tokens

The binding this breaks is: `releasable_balance(t) == f(lockup_schedule, t)` where `lockup_schedule` is meant to be fixed at deployment. An attacker can redefine `lockup_schedule` post-deployment (e.g., set `transfers_information = TransfersEnabled{transfers_timestamp: 0}`, omit `lockup_timestamp`/`release_duration`, omit `vesting_schedule`, and set `owner_account_id` to their own account), making `releasable_balance(now) == full_account_balance` immediately, while `owner_account_id` is now attacker-controlled.

## Impact Explanation
This is Critical: locked/unvested NEAR tokens can be released early to an attacker who reassigns `owner_account_id` to themselves via a call to `new`, then withdraws/transfers the full account balance using the owner-only `transfer` method, bypassing the intended lockup/vesting schedule entirely and stealing custodied funds from the legitimate beneficiary/foundation.

## Likelihood Explanation
Likelihood is high for any lockup contract account whose account ID is known (lockup contract account IDs are deterministically derived from the owner's account ID via `sha256(owner_account_id)` in `lockup-factory/src/lib.rs`, so they are easily computed/enumerated by anyone). No special privileges, keys, or race condition against deployment are required — the call can be made against a contract that has been live and holding funds for any length of time, since the missing check is a permanent absence, not a narrow front-running window.

## Recommendation
Add the same initialization guard used by every other contract in this repository to `LockupContract::new`:
```rust
#[init]
pub fn new(...) -> Self {
    assert!(!env::state_exists(), "The contract is already initialized");
    ...
}
``` [8](#0-7) 

## Proof of Concept
1. Wait for (or locate) a deployed, funded `LockupContract` at account `lockup1` with legitimate `owner_account_id = owner1` and a multi-year vesting/lockup schedule.
2. From attacker account `evil`, call:
```
near call lockup1 new '{
  "owner_account_id": "evil",
  "lockup_duration": "0",
  "lockup_timestamp": null,
  "transfers_information": {"TransfersEnabled": {"transfers_timestamp": "0"}},
  "vesting_schedule": null,
  "release_duration": null,
  "staking_pool_whitelist_account_id": "staking-pool-whitelist",
  "foundation_account_id": null
}' --accountId=evil --gas=25000000000000
```
3. Because `new` performs no `state_exists` check, this call succeeds and overwrites the contract state: `owner_account_id` becomes `evil`, transfers are enabled from timestamp 0, and there is no lockup/vesting restriction.
4. `evil` then calls the owner-only `transfer` method to move the full custodied NEAR balance out of `lockup1`, well before the original schedule would have permitted any release.

    pub fn new(

        );
        if let TransfersInformation::TransfersDisabled {
            transfer_poll_account_id,

                "The transfer poll account ID is invalid"

        let lockup_information = LockupInformation {
            lockup_amount: env::account_balance(),
            termination_withdrawn_tokens: 0,
            lockup_duration: lockup_duration.0,

            lockup_timestamp: lockup_timestamp.map(|d| d.0),
            transfers_information,
        };
        let vesting_information = match vesting_schedule {

        assert!(

        Self {
            owner_account_id,
            lockup_information,
            vesting_information,
            staking_information: None,
            staking_pool_whitelist_account_id,
            foundation_account_id,
        }
    }
