### Title
V1 tenure-change duplicate-block guard checks only global acceptance, letting a signer sign two tenure-start blocks for the same tenure - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` (v1 chainstate path, active for signers below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) rejects a proposed tenure-change block as `DuplicateBlockFound` only if `SignerDb::get_last_globally_accepted_block` finds a prior block in that tenure. This mirrors the "incomplete fix" pattern of CVE-2018-18625: the v2 implementation of the identical check was later hardened to use `get_last_signed_block` (which also matches `LocallyAccepted`), with an explicit comment explaining that a block "we have signed (locally or globally accepted)" must count, but the v1 code retains the old, narrower predicate.

### Finding Description
The proposal-time guard against equivocating on the tenure-start block is:

```rust
// stacks-signer/src/chainstate/v1.rs:505-518
let last_in_current_tenure = signer_db
    .get_last_globally_accepted_block(&block.header.consensus_hash)?;
if let Some(last_in_current_tenure) = last_in_current_tenure {
    ...
    return Err(RejectReason::DuplicateBlockFound);
}
``` [2](#0-1) 

`GloballyAccepted` requires the 70% signature threshold to have been reached and broadcast/observed — a much stronger condition than simply having put our own signature on a block (`LocallyAccepted`) [3](#0-2) . Between the moment a signer signs a first tenure-start block for a tenure (`mark_locally_accepted`, `signed_self` is set) and the moment that block is globally accepted, this v1 check sees "no globally accepted block in this tenure" and passes a *second*, different tenure-change proposal straight through the proposal-time duplicate check.

By contrast, the v2 path uses `get_last_signed_block`, which is satisfied by either `LocallyAccepted` or `GloballyAccepted` [4](#0-3) , and its own code comment states the rationale directly: "Only blocks we have signed (locally or globally accepted) count here" [5](#0-4) . This is the same shape as the Grafana bug: a security-relevant equality check ("have I already signed a block in this tenure?") was fixed in one code path but the earlier, weaker version of that check survives in a sibling path that is still reachable.

The proposal-time gap is not fully closed by downstream checks:
- `check_block_against_state`/`check_block_against_local_state` for a fresh proposal calls `check_proposal` again, which re-enters the same v1 `validate_tenure_change_payload` with the same weak predicate at validate-ok/pre-commit re-evaluation time (`check_block_against_signer_db_state` also flows through `check_proposal`) [6](#0-5) .
- The independent backstop that exists for *height*-based conflicts, `get_signed_conflicts`/`conflict_still_blocks`, is invoked at the pre-commit-threshold stage [7](#0-6) , and is documented as a general safety net — but the DuplicateBlockFound check is explicitly called out in the docs as the *only* place a second tenure-start block in the very same tenure is caught pre-signature ("the `DuplicateBlockFound` check ... lives in `check_proposal` and runs only at proposal arrival, never again ... A block that crosses the pre-commit threshold minutes later has no other guard, which is what the own-tenure branch above covers") — but that "own-tenure" backstop in `handle_block_pre_commit` is height-based, keyed off `get_signed_conflicts` at or above the block's own height in *any* tenure, which will still catch two same-height tenure-start blocks. So the practical exploitation window is narrow but real: the v1-only bug only matters as the *first* line of defense being weaker than intended (the doc's own description of v2's guarantee does not hold for v1), and it is only a genuine safety break if the height-based backstop can itself be sidestepped or delayed (e.g. via `reorg_permit_stands`/staleness logic covered in section 5 of `docs/signer-flows.md`), which requires further protocol-level analysis I could not fully verify within this pass.

### Impact Explanation
If the height-based `get_signed_conflicts`/`conflict_still_blocks` guard at pre-commit time is bypassed or times out (e.g. the first block's signature goes stale per `tenure_last_block_proposal_timeout`, or the conflicting block is deemed non-canonical per the node's tenure-tip lookup, both of which the guard explicitly treats as clearing the conflict), a v1-protocol signer could end up placing its signature over two distinct tenure-start blocks for the same tenure. That is a concrete instance of the "equivocation guard lost" / "signer signing a conflicting block" class called Critical in the rules, because it breaks the "one tenure-start block per tenure per signer" equality that the `DuplicateBlockFound` check exists to enforce, using only the narrower stale check.

### Likelihood Explanation
This requires no majority of malicious signers and no key compromise — only a single miner (or attacker with StackerDB write access to the miner slot) proposing two competing tenure-change blocks for the same tenure while the first is only locally, not yet globally, accepted, and timed to have the height-based conflict guard clear (staleness/timeout window, or the node's tenure-tip reporting the first block as not yet canonical). This is version-gated (only reachable on signers still running below `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`, i.e. the pre-global-state protocol), which limits current exploitability as networks migrate to v2, but any live v1-protocol deployment or fallback path remains exposed.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `SignerDb::get_last_signed_block` instead of `SignerDb::get_last_globally_accepted_block`, matching the already-fixed v2 implementation, so that a locally-accepted (self-signed) tenure-start block also blocks a second tenure-change proposal for the same tenure at proposal time.

### Proof of Concept
1. Configure a signer running the v1 (pre-`GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`) protocol.
2. Miner proposes tenure-change block `A` for tenure `T`; the signer validates it, pre-commits, and — once the pre-commit threshold observed at this signer alone reaches signing conditions — signs it (`mark_locally_accepted`, `signed_self` set), but the network-wide 70% signature threshold has not yet been reached, so `A` is not yet `GloballyAccepted`.
3. Before `A` reaches global acceptance, the same or a colluding miner proposes a second, different tenure-change block `B` also for tenure `T` (same consensus hash).
4. In `check_proposal` → `validate_tenure_change_payload`, `signer_db.get_last_globally_accepted_block(&T)` returns `None` (since `A` is only `LocallyAccepted`), so the `DuplicateBlockFound` rejection at proposal time is skipped for `B`.
5. `B` proceeds to node validation and pre-commit; whether it ultimately gets signed depends on the separate height-based `get_signed_conflicts`/`conflict_still_blocks` guard in `handle_block_pre_commit` clearing the conflict (e.g., due to `A`'s signature going stale per `tenure_last_block_proposal_timeout`, or the node reporting `A` as not confirmed) — reproducing this end-to-end requires further test-harness verification of the staleness/canonical-tip timing, which was not completed in this analysis.

    /// Return the last signed block in a tenure (identified by its consensus hash).
    /// A block is considered signed if it is locally or globally accepted. Blocks that
    /// have only been pre-committed are excluded, because a pre-commit does not put a
    /// signature over the block and may be safely superseded by a competing proposal.

    pub fn get_last_signed_block(
        &self,
        tenure: &ConsensusHash,
    ) -> Result<Option<BlockInfo>, DBError> {
        let query = "SELECT block_info FROM blocks WHERE consensus_hash = ?1 AND state IN (?2, ?3) ORDER BY stacks_height DESC LIMIT 1";
        let args = params![
            tenure,
            &BlockState::GloballyAccepted.to_string(),
            &BlockState::LocallyAccepted.to_string(),
        ];
        let result: Option<String> = query_row(&self.db, query, args)?;

        try_deserialize(result)
    }
