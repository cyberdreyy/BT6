### Title
Miner double-counts a signer's weight in both `total_weight_rejected` and `total_weight_approved` when a signer flips from Reject to Accept, causing a spurious global rejection of an approved block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener` tallies signer weight for a proposed block into two independent counters, `total_weight_approved` and `total_weight_rejected`, inside `BlockStatus` [1](#0-0) . The `Rejected` branch only adds weight when `block.responded_signers.insert(slot_id)` first sees this slot [2](#0-1) , and the `Accepted` branch adds weight when `!block.gathered_signatures.contains_key(&slot_id)` [3](#0-2) . Because `responded_signers` is shared and updated by both branches, an Accept-after-Reject sequence from the same signer for the same block is *not* protected: `gathered_signatures` never contained that slot yet, so the later Accept is added on top of the earlier already-counted Reject weight — the signer's weight ends up counted in both totals simultaneously, and `total_weight_rejected` is never decremented.

### Finding Description
A signer is explicitly allowed by the signer-side state machine to change its position from reject to accept on the *same* block: `SignerDb::add_block_signature` deletes the earlier `block_rejection_signer_addrs` row for that signer before recording the new acceptance signature [4](#0-3) , and `BlockInfo::check_state` permits the `LocallyRejected -> LocallyAccepted` transition [5](#0-4) . The design doc even documents that a signer only "does not change [its] vote on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider" — implying such reconsideration, and the resulting Accept broadcast, is an intended, reachable flow [6](#0-5) .

On the miner/coordinator side that consumes these StackerDB messages, `stackerdb_listener.rs` does not track a single "final vote" per signer slot; it keeps two separate accumulators that are only ever incremented, never decremented or reconciled against each other:
- `Rejected` handler: weight added iff `responded_signers.insert(slot_id)` succeeds (first response ever) [7](#0-6) .
- `Accepted` handler: weight added iff `!gathered_signatures.contains_key(&slot_id)` — a check against the *acceptance* map only, ignoring whether that slot already contributed to `total_weight_rejected` [8](#0-7) .

Sequence: signer S (weight w) sends `Rejected` for block B → `total_weight_rejected += w`, `responded_signers = {S}`. S later reconsiders and sends `Accepted` for the same B → `gathered_signatures` does not contain S yet, so `total_weight_approved += w` as well. Now `total_weight_rejected + total_weight_approved` exceeds what a single, consistent per-signer vote should ever contribute, i.e. S's weight `w` is present in *both* buckets. Note the reverse order (Accept-then-Reject) is correctly guarded, since `responded_signers` already contains S from the accept step, so the later Reject is dropped — this asymmetry indicates an oversight rather than intended semantics.

### Impact Explanation
The consuming logic in `SignerCoordinator::begin_sign_v0` checks the rejection bucket first: `total_weight_rejected.saturating_add(weight_threshold) > total_weight` triggers `NakamotoNodeError::SignersRejected` (globally rejecting the block for that mining attempt), and only checks `total_weight_approved >= weight_threshold` afterward [9](#0-8) . Because a stale rejection contributed by a signer who has since switched to acceptance is never removed from `total_weight_rejected`, a block that legitimately reaches the 70% acceptance threshold (real, current votes) can still be treated by the miner as having crossed the blocking-minority-rejection threshold first (using the union of ever-seen rejections, including outdated ones), causing the miner to give up on a block the signer set actually approved. This is a liveness wedge (miner spuriously abandons/rejects an otherwise-approved block, forcing timeouts/retries or missed tenures) driven purely by ordinary, permitted signer message traffic — no majority collusion required.

### Likelihood Explanation
Only requires a single signer to legitimately reconsider a rejection into an acceptance for the same block hash (a flow the signer state machine and docs explicitly allow) and for the miner to observe both messages via normal StackerDB gossip. No cryptographic forgery, no majority of signers, and no privileged access are needed — an honest signer's normal reconsideration is sufficient to induce the double count, and a single well-timed message pair from one signer can flip the miner's `SignersRejected` vs `Ok` outcome for a genuinely-approved block.

### Recommendation
Track a single authoritative vote (and its weight) per `slot_id` rather than two independently-incrementing totals. On receiving an `Accepted` message, if the slot previously contributed to `total_weight_rejected`, subtract that weight before/while adding it to `total_weight_approved` (and symmetrically for `Rejected` overriding a prior `Accepted`, if that transition is ever intended to be allowed). Concretely, replace the ad-hoc `responded_signers` / `gathered_signatures` membership checks in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` with a single `HashMap<u32, Vote>` (Accepted/Rejected + weight) per `BlockStatus`, and recompute `total_weight_approved`/`total_weight_rejected` from that map, or explicitly decrement the opposing bucket whenever a slot's recorded vote changes.

### Proof of Concept
1. Reward set with signers S1 (weight 40) and S2 (weight 30), `total_weight = 70`, `weight_threshold` computed for 70% (≈ 49).
2. Miner proposes block B. `stackerdb_listener` initializes `BlockStatus::default()` for B (`total_weight_approved = 0`, `total_weight_rejected = 0`, `responded_signers = {}`, `gathered_signatures = {}`).
3. S1 rejects B (e.g. transient validation issue): `Rejected` handler runs — `responded_signers.insert(1)` succeeds → `total_weight_rejected = 40`.
4. Node re-validates / conditions change; S1's local signer logic legitimately reconsiders and sends `Accepted` for the same B (permitted by `add_block_signature`'s deletion of the prior rejection row and by `check_state`'s `LocallyRejected -> LocallyAccepted` transition).
5. `Accepted` handler runs for S1: `gathered_signatures.contains_key(&1)` is `false` (S1 never accepted before) → `total_weight_approved = total_weight_approved.saturating_add(40) = 40`; `gathered_signatures.insert(1, sig)`; `responded_signers.insert(1)` (no-op, already present).
6. S2 accepts B: `total_weight_approved = 40 + 30 = 70 ≥ weight_threshold (49)` — block should legitimately be treated as accepted.
7. `SignerCoordinator::begin_sign_v0` polls `BlockStatus`: `total_weight_rejected (40).saturating_add(weight_threshold 49) = 89 > total_weight (70)` is checked **first** and is `true`, even though only S1 ever "currently" rejects and S1's later Accept plus S2's Accept together reach the true 70% threshold. The miner returns `NakamotoNodeError::SignersRejected`, discarding a block that the signer set actually approved, purely because S1's earlier (superseded) rejection weight was never cleared from `total_weight_rejected`.
