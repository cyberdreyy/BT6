### Title
Already-claimed instant-withdraw receipts remain counted in `instantWithdrawsClaimsByEpoch`, so a same-epoch re-request makes a default-finalized recovery basis pay one claim twice and dilute all other recovery claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Squid collapsed-forwarding bug delivered a private response to multiple clients because a shared cache key was reused after the private data was consumed. The analog in `IdleCreditVault` is `claimInstantWithdrawRequest`: it clears the aggregate receipt `instantWithdrawsRequests[_user]` but never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. A user who claims a funded instant withdrawal and then requests a new instant withdrawal inside the same epoch gets their already-paid receipt counted a second time in the epoch claim basis, which `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` later treat as an outstanding, recovery-claimable amount.

### Finding Description
`requestInstantWithdraw` records both the aggregate `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . The funded claim path only resets the aggregate: it burns `instantWithdrawsRequests[_user]` and zeroes it, leaving both per-epoch counters untouched [2](#0-1) . By contrast, the defaulted claim path does clear them (`instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0`, `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis`) [3](#0-2) .

Consequences when a default is finalized in that same epoch:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (which still includes the already-paid first claim) to the recovery basis whenever `pendingInstantWithdraws != 0` [4](#0-3) . `defaultRecoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is therefore diluted by a phantom claim that was already paid out at par [5](#0-4) .
2. `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — old claimed amount plus new request — while the user only holds receipt tokens for the new request, so `_burn(_user, claimBasis)` underflow-reverts and the user's legitimate new claim is permanently frozen [6](#0-5) .

The epoch guard does not stop this: the non-default `claimInstantWithdrawRequest` has no "wait one epoch" check (instant claims are processed after `instantDelay` within the running epoch, exactly as `processWithdrawalClaims`/`isEpochInstant` in `IdleCDOEpochQueue` allow) [7](#0-6) , and `requestInstantWithdraw` has no same-epoch re-request guard [8](#0-7) .

### Impact Explanation
Two distinct harms, both reachable by an unprivileged KYC'd lender:

- **Recovery dilution (theft-like loss socialization):** the inflated `totalBasis` lowers `defaultRecoveryPrice` for every defaulted-epoch and active claimant. The phantom basis was already paid at par and is backed by nothing in `defaultRecoveryReserve`, so every other claimant (normal withdrawers, other instant withdrawers, active AA/BB holders priced off the same recovery ratio) permanently receives less than their fair recovery share. The excess is effectively a double-counted payout served to a claim that was already delivered.
- **Permanent freezing:** the re-requesting user's new instant receipt can never be claimed post-default (`_burn` underflow), and their basis contribution also permanently distorts `defaultRecoveryPrice`.

### Likelihood Explanation
Requires instant withdrawals enabled (a supported, manager-configured mode), an instant claim processed mid-epoch (the designed flow: claim after `instantDelay`), a same-epoch re-request (no guard prevents it), and a borrower default in that epoch. Defaults are a modeled protocol state with dedicated recovery machinery, not an exotic edge. Attacker cost is only an extra deposit/withdraw cycle; the dilution scales with the size of the re-requested claim.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch ledgers for the epoch(s) being claimed the same way `_claimDefaultedInstantWithdrawRequest` does — i.e., subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` (or track the claim epoch per user). Alternatively, forbid a new `requestInstantWithdraw` while `instantWithdrawsRequestsByEpoch[_user][epochNumber]` is non-zero for the current epoch, mirroring the `requestWithdraw` guard that blocks re-requests when a loss-adjusted receipt is still pending [9](#0-8) .

### Proof of Concept
Foundry fork PoC outline (setup mirrors `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_toggleEpoch`, instant-withdraw params via `cdoEpoch.setInstantWithdrawParams`):

```solidity
function testPocInstantClaimDoubleCountsEpochBasis() external {
    // 1. alice (attacker) and bob deposit AA; manager enables instant withdraws.
    _depositWithUser(alice, 100_000e6);
    _depositWithUser(bob, 100_000e6);
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(1 days, 0, true);

    // 2. startEpoch, alice requests instant withdraw.
    _startEpochAndCheckPrices(0);
    vm.prank(alice);
    cdoEpoch.requestInstantWithdraw(0, address(AAtranche)); // full balance

    // 3. after instantDelay, manager/keeper processes the instant claim;
    //    alice receives underlyings. instantWithdrawsRequests[alice] == 0
    //    but instantWithdrawsRequestsByEpoch[alice][epoch] and
    //    instantWithdrawClaimsByEpoch[epoch] still hold the claimed amount.
    skip(1 days + 1);
    cdoEpoch.claimInstantWithdrawRequest(); // via CDO path as in tests

    // 4. alice deposits again and requests a new instant withdraw IN THE SAME EPOCH.
    _depositWithUser(alice, 50_000e6);
    vm.prank(alice);
    cdoEpoch.requestInstantWithdraw(0, address(AAtranche));
    // now instantWithdrawClaimsByEpoch[epoch] == old claimed + new request

    // 5. borrower defaults this epoch with another user's instant request
    //    still unfunded so pendingInstantWithdraws != 0.
    _handleBorrowerDefault(); // CDO default flow

    // 6. finalizeDefaultRecovery: defaultPendingClaimBasis() returns
    //    pendingWithdraws + instantWithdrawClaimsByEpoch[epoch] inflated by
    //    alice's already-paid claim -> defaultRecoveryPrice is diluted.
    uint256 price = strategy.defaultRecoveryPrice();
    assertLt(price, expectedFairPrice); // all other claimants underpaid

    // 7. alice's legitimate new instant claim is permanently frozen:
    vm.expectRevert(); // _burn underflow: receipt balance < claimBasis
    cdoEpoch.claimInstantWithdrawRequest();
}
```

The broken invariant is one-receipt-one-payout / donation isolation of the recovery reserve: a receipt already satisfied at par is re-served into the shared default-recovery basis, exactly the collapsed-forwarding class of serving consumed private data to additional claimants.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
