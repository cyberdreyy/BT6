### Title
Miner's rejection weight is never revoked when a signer flips its vote to Accepted, causing valid blocks to be treated as rejected off a stale aggregate - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run`'s message handler tracks `total_weight_approved` and `total_weight_rejected` per block in `BlockStatus`. When a signer's `BlockResponse::Rejected` arrives, its weight is added to `total_weight_rejected` and the slot is marked in `responded_signers`. If that same signer later legitimately reconsiders and sends `BlockResponse::Accepted` for the *same* block hash, the code adds the signer's weight to `total_weight_approved` (keyed only off `gathered_signatures`, not `responded_signers`) but never subtracts the signer's earlier contribution from `total_weight_rejected`. The two aggregates are supposed to represent disjoint, mutually-exclusive current opinions of each signer, but they can now both contain the same signer's weight simultaneously, corrupting the miner's threshold accounting.

### Finding Description
`BlockStatus` in [1](#0-0)  maintains `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` as the miner's live tally of signer opinions on a proposed block.

On `Rejected`, the code gates the weight addition on `block.responded_signers.insert(slot_id)` returning `true` (first response from that slot): [2](#0-1) 

On `Accepted`, the code instead gates the weight addition on `block.gathered_signatures.contains_key(&slot_id)`, not on `responded_signers`: [3](#0-2) 

Because a signer can legitimately reject a block once (e.g. due to a transient validation failure or an initially-invalid state) and later flip to signing it — the signer-side state machine explicitly allows the `LocallyRejected -> LocallyAccepted` transition as long as the block has not reached global consensus, per `BlockInfo::check_state`: [4](#0-3) 

when that flip happens, the `Accepted` message for the same `signer_signature_hash` is processed by the miner: since the slot was never in `gathered_signatures`, the miner adds the signer's weight to `total_weight_approved` — but `total_weight_rejected` is never decremented, and there is no code path that removes a slot from `responded_signers`/adjusts `total_weight_rejected` when a later acceptance supersedes an earlier rejection. The only place rejection weight is cleared is `reset_rejections`, which is called solely on a full poll timeout, not on a targeted per-signer vote flip: [5](#0-4) 

The consuming loop in the coordinator evaluates the reject condition using this stale `total_weight_rejected`: [6](#0-5) 

Because `total_weight_rejected` and `total_weight_approved` are no longer disjoint after a flip, a stale/phantom weight contribution can push `total_weight_rejected + weight_threshold > total_weight` and trip `NakamotoNodeError::SignersRejected`, aborting the block even though the actual live set of signers (correctly reflected in `gathered_signatures`, which does hold real verified signatures) may already have enough weight to reach `weight_threshold` for acceptance.

### Impact Explanation
This breaks the aggregated-weight vs. verified-accepts equality that the coordinator relies on: `total_weight_rejected` should represent the current weight of signers whose most recent verified stance is "reject," but after a flip it retains stale weight from signers who have since produced valid signatures. This can cause the miner to declare a block rejected (and exclude/ban transactions, per the `failed_txids` bookkeeping tied to the same rejection event) purely because of accounting staleness, not because a genuine blocking minority (>30% weight) currently opposes the block. This is a liveness wedge on block production driven by a stale threshold count, matching the "acting on a stale... threshold" impact category, since legitimate blocks can be spuriously aborted by the miner and their construction retried, degrading throughput and potentially causing repeated stalls if signers routinely reconsider (e.g., during validation races or reprocessing scenarios exercised by the signer's own reconsideration tests).

### Likelihood Explanation
Reconsideration (`LocallyRejected -> LocallyAccepted`) is an explicitly supported and tested signer behavior (the repo carries `stacks-node/src/tests/signer/v0/reprocess_block_proposals.rs` covering related reconsideration flows), so a single-slot signer flipping its opinion for the same block hash is a normal, reachable event without requiring a majority or any other signer's key — it needs only one honest signer that revalidates and changes its own mind, plus the ordinary flow of `Rejected` then `Accepted` messages reaching the miner over StackerDB.

### Recommendation
Track live-per-signer vote state (e.g. a `HashMap<slot_id, Vote>` instead of independently-incrementing counters) or, at minimum, when processing `Accepted`, check `responded_signers` for a prior rejection of the same slot and subtract that signer's weight from `total_weight_rejected` before adding it to `total_weight_approved`, so the two aggregates remain mutually exclusive and reflect only the current opinion of each signer.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`.
2. Signer `S` (weight `w_S`) initially rejects `B` due to a recoverable condition (e.g. `ConnectivityIssues`/transient chainstate mismatch), sending `BlockResponse::Rejected` for `H`. The miner's `StackerDBListener` adds `w_S` to `total_weight_rejected` and marks `S`'s slot in `responded_signers` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-519`).
3. `S` revalidates `B` (still hash `H`) and now sees it as valid, producing a legitimate `BlockResponse::Accepted` with a valid signature for `H`.
4. The miner receives this `Accepted` message; since `S`'s slot is absent from `gathered_signatures`, `total_weight_approved` is incremented by `w_S` (`stackerdb_listener.rs:443-465`), while `total_weight_rejected` still includes `w_S` from step 2 — no code removes it.
5. If enough other signers also reject `B` for legitimate independent reasons, `total_weight_rejected` (inflated by `S`'s stale contribution) can cross `self.total_weight - self.weight_threshold` in `signer_coordinator.rs:509-520`, causing the miner to return `NakamotoNodeError::SignersRejected` and abort block `B`, even though the true, current live-vote weight opposing `B` may be below the actual blocking-minority threshold once `S`'s flip is correctly accounted for.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
