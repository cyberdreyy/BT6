### Title
`check_block_has_valid_parent` accepts a tenure-start block whose parent belongs to a locally-known but non-canonical tenure - (File: `stackslib/src/net/api/postblock_proposal.rs`)

### Summary
For tenure-start proposals, `NakamotoBlockProposal::check_block_has_valid_parent` resolves the parent header with a plain, non-canonical-aware chainstate lookup and then validates the *parent's* tenure only through `find_highest_known_block_header_in_tenure`, never through the canonical-restricted `SortitionHandleConn` used elsewhere. This lets a crafted tenure-start block validate `Ok` even though its parent's tenure is not an ancestor of the current canonical sortition tip.

### Finding Description
`validate()` performs exactly one canonicity check, `check_block_has_valid_tenure`, and only against the *proposed block's own* `consensus_hash`, using the canonical-tip-restricted handle: [1](#0-0) 

That check passes trivially for any attacker who has won the current miner slot, since their own tenure's consensus hash is by definition on the canonical Bitcoin fork.

The parent-linkage check is delegated to `check_block_has_valid_parent`. For a well-formed tenure-start block, the code fetches the parent header directly from local storage with no canonical filter at all: [2](#0-1) 

`NakamotoChainState::get_block_header(chainstate.db(), &block.header.parent_block_id)` is a raw local lookup — it returns any header the node has ever stored, including one belonging to a tenure that was later orphaned by a Bitcoin reorg or by a sortition winner that lost the canonical race. The subsequent call, `check_block_builds_on_highest_block_in_tenure`, is passed `&sortdb: &SortitionDB` (the full, unrestricted sortition view) rather than the canonical-tip-scoped `SortitionHandleConn` (`db_handle`) that `check_block_has_valid_tenure` uses: [3](#0-2) 

Nowhere in this path is the parent tenure's consensus hash checked against `db_handle.has_consensus_hash(...)` (the canonical-fork-aware check). The only two canonical checks performed in `validate()` are the single `check_block_has_valid_tenure` call for the block's own hash, and implicit checks buried in downstream burn-accounting/tenure-building logic that were not confirmed to reject orphaned parent tenures (their exact behavior in this codebase could not be fully verified due to tool-call limits reached while inspecting `find_highest_known_block_header_in_tenure`).

**Exploit flow:**
1. A Bitcoin/Stacks reorg (or a previous miner-slot win) leaves a non-canonical tenure and its blocks present in the victim signer/node's local `chainstate.db()`, even though the sortition for that tenure is no longer on the canonical Bitcoin fork.
2. The attacker wins a single sortition slot on the *current* canonical fork.
3. The attacker crafts a well-formed tenure-start `NakamotoBlock` whose `parent_block_id` points to the highest known block in the orphaned tenure (not the true canonical parent).
4. The attacker submits this as a `BlockProposal` / signs and gossips it to signers.
5. `check_block_has_valid_tenure` passes (attacker's own tenure is canonical). `check_block_has_valid_parent` resolves the orphaned parent locally and validates against `find_highest_known_block_header_in_tenure`, which is not restricted to the canonical fork, so it can also pass.
6. If the burn-accounting/tenure-building steps downstream do not independently re-derive and enforce that the parent's tenure sortition is an ancestor of the canonical tip (unverified due to tool budget), `validate()` returns `Ok(BlockValidateOk)`. A signer that trusts this result would sign a block that extends a non-canonical chain.

### Impact Explanation
If confirmed end-to-end, this breaks the **canonicity** safety property: a signer could produce a valid signature over a block extending an orphaned/non-canonical tenure, i.e., a signature valid across a chain-history boundary that should have been rejected. This matches the Critical category ("a signer signing an invalid, non-canonical, or conflicting block"). The bug is repeatable any time a locally-stored orphaned tenure with a full block history is available and the attacker holds a single sortition win.

### Likelihood Explanation
The precondition — a non-canonical tenure's headers/blocks still resident in a node's local chainstate storage — is a realistic residual state after Bitcoin/Stacks reorgs, since stale Nakamoto block data is not proactively purged. Beyond that, the attacker needs only their normal capability (win one miner slot, craft/gossip one `BlockProposal`), matching the unprivileged threat model. However, I was unable to fully verify whether downstream steps in `validate()` (burn-expectation checks, `NakamotoBlockBuilder::load_tenure_info`/`tenure_begin`) independently re-establish canonicity of the parent's tenure before returning `Ok` — this could still close the gap, and I could not confirm the behavior of `find_highest_known_block_header_in_tenure` (in `stackslib/src/chainstate/nakamoto/mod.rs`) before running out of tool calls.

### Recommendation
In `check_block_has_valid_parent`'s tenure-start branch, explicitly re-check the parent's `consensus_hash` against the canonical-tip-restricted `SortitionHandleConn` (the same `db_handle` used in `check_block_has_valid_tenure`), e.g. call `Self::check_block_has_valid_tenure(&db_handle, &parent_header.consensus_hash)` before or in addition to `check_block_builds_on_highest_block_in_tenure`, and pass a canonical-restricted handle (not a raw `&SortitionDB`) into `find_highest_known_block_header_in_tenure`.

    pub(crate) fn check_block_has_valid_tenure(
        db_handle: &SortitionHandleConn,
        tenure_id: &ConsensusHash,
    ) -> Result<(), BlockValidateRejectReason> {
        // Verify that the block's tenure is on the canonical sortition history
        if !db_handle.has_consensus_hash(tenure_id)? {
            warn!(
                "Rejected block proposal";
                "reason" => "Block's tenure consensus hash is not on the canonical Bitcoin fork",
                "consensus_hash" => %tenure_id,
            );
            return Err(BlockValidateRejectReason {
                reason_code: ValidateRejectCode::NonCanonicalTenure,
                reason: "Tenure consensus hash is not on the canonical Bitcoin fork".into(),
                failed_txid: None,
            });
        }
        Ok(())
    }
