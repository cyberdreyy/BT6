### Title
Signer places its irreversible signature on a block without re-verifying it belongs to the currently-active miner/tenure - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`GlobalStateView::check_proposal` (v2 chainstate) is the only place that verifies a proposed block's `consensus_hash` matches the signer's *currently active* tenure and that the block's miner public-key-hash matches the *currently active* miner. This check runs exactly once, at fresh-proposal time. It is never re-invoked at validate-ok time or at the pre-commit-threshold/signing moment, where a narrower check (`check_block_against_signer_db_state`) only re-verifies tenure-tip/latest-block consistency, not miner/consensus identity. Because a signer's view of "who the active miner is" can change between proposal-time and signature-time (new burn blocks, state-machine capitulation), a signer can end up placing its one irreversible signature on a block that its own state machine no longer considers to belong to the canonical/active miner or tenure.

### Finding Description
`check_proposal` in `stacks-signer/src/chainstate/v2.rs` enforces the equality "block.consensus_hash == active tenure_id" and "block miner pubkey hash == active miner pubkey hash" against `self.signer_state.current_miner`, rejecting with `ConsensusHashMismatch` / `PubkeyHashMismatch` otherwise [1](#0-0) . Per the codebase's own decision map, this wrapper — including the miner-pubkey-hash, consensus-hash, and bitvec checks — is explicitly documented as belonging only to the initial proposal path and is **not re-run** at validate-ok or at signing time [2](#0-1) .

The two places that do run again later only re-check tenure/parent confirmation, not miner/consensus identity:
- At validate-ok, `handle_block_validate_ok` calls `check_block_against_signer_db_state`, and only marks the block pre-committed or rejected based on that narrower check [3](#0-2) .
- At the pre-commit threshold (the actual signing decision), `handle_block_pre_commit` re-runs chainstate/conflict checks (`check_block_against_signer_db_state`, `get_signed_conflicts`, `reorg_permit_stands`, `conflict_still_blocks`) but never calls back into `check_proposal` to re-verify the block still matches the signer's current `MinerState::ActiveMiner` [4](#0-3) , before finally signing at `mark_locally_accepted` / `create_block_acceptance` [5](#0-4) .

Meanwhile, the signer's `current_miner` view is independently and continuously updated out-of-band by burn-block/gossip processing (`capitulate_miner_view`, `update_parent_tenure_last_block`, tenure timeout fallback) — a flow that runs on a separate timeline from any single block's proposal/validation/pre-commit lifecycle [6](#0-5) . The re-proposal (`should_reevaluate_block`) path confirms the same gap: when a block is already `PreCommitted`, a re-proposal is routed straight back into `handle_block_pre_commit` (the pre-commit/signing path), never back through `check_block_against_state`/`check_proposal` [7](#0-6) .

The result: the "active-miner equality" that gates whether a signer is even willing to *consider* a block is enforced once, at intake, but the state it depends on (`current_miner`) is free to drift before the moment that actually produces a signature. This is the same bug class as the reported CVE — a value is correctly validated/computed in one code path but never re-applied at the actual point where the consequential action (binding a socket / placing a signature) occurs.

### Impact Explanation
If the signer's active-miner/tenure view changes between validate-ok and pre-commit-threshold crossing (via ordinary burn-block or StackerDB gossip processing, not requiring a signer majority or extra keys), a signer can sign a block whose miner/consensus-hash identity is stale relative to its own current state-machine view — i.e., it can sign a non-canonical block per its own logic, without ever re-running the check that exists specifically to prevent that. This is a Critical-class outcome under the stated rubric: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
The trigger requires only ordinary network conditions a single miner plus gossip can create: proposal → validation round-trip latency (during which a new sortition/burn block can arrive and shift `current_miner`), or a pre-commit re-proposal after a timeout. No majority of signers, no other signer's key, and no auth token access are required — only the natural timing gap between "I validated/pre-committed to this block" and "70% of weight has pre-committed, so I sign," which the code and its own documentation acknowledge as a live window ("Between validation and threshold ... the world must be re-checked" — but only the tenure/conflict portion of the world, not the active-miner portion).

### Recommendation
Re-run (or a cheap equivalent of) the `check_proposal` active-miner/consensus-hash/pubkey-hash equality check inside `handle_block_pre_commit` immediately before `mark_locally_accepted`/`create_block_acceptance`, in addition to the existing tenure/conflict re-checks in `check_block_against_signer_db_state`, so a signature can never be produced for a block whose consensus_hash/miner no longer matches the signer's current `MinerState::ActiveMiner`.

### Proof of Concept
1. Miner M1 wins sortition for tenure T1 and proposes tenure-start block B (`consensus_hash = T1`). The signer's `current_miner` is `{pkh: M1, tenure_id: T1}`; `check_proposal` passes, B is submitted for validation and pre-committed (`handle_block_validate_ok` → `mark_pre_committed`) [8](#0-7) .
2. Before B's pre-commit weight crosses 70%, a new burn block/StateMachineUpdate causes the signer's own state machine to capitulate to a different active miner/tenure view (section 8 flow) [6](#0-5) .
3. Delayed pre-commits for B (gossip lag) still arrive and cross the 70% threshold. `handle_block_pre_commit` re-runs only `check_block_against_signer_db_state` and conflict checks — neither of which re-validates B against the now-updated `current_miner` [4](#0-3) .
4. If those narrower checks pass, the signer proceeds to `mark_locally_accepted` and produces a signature over B via `create_block_acceptance`, even though B is stale/non-canonical per the signer's own current active-miner view [5](#0-4) .

        // re-proposed tenure-start block after the first failed to reach consensus), but a
