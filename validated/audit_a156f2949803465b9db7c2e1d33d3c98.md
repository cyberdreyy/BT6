### Title
Stale confirmations from removed multisig members/keys still count toward the confirmation threshold, allowing requests to execute below the intended live-member quorum - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both the `multisig` and `multisig2` contracts allow a member/key to be removed from the multisig via `DeleteKey`/`DeleteMember`, but the cleanup logic only purges requests and confirmation sets for requests *created by* the removed member/key. Confirmations that the removed member/key previously cast on requests created by *other* members are never purged, so they continue to count toward `num_confirmations` even though that signer is no longer a live member of the multisig.

### Finding Description
The confirmation-counting logic in `confirm()` treats `confirmations.len()` as a proxy for the number of distinct, currently-authorized signers: [1](#0-0) 

However, the invariant "confirmations recorded == confirmations from currently live members" is never re-validated. When a member is removed via `DeleteMember` (multisig2) or a key via `DeleteKey` (multisig), the cleanup only removes requests/confirmations that member *created*: [2](#0-1) [3](#0-2) 

Both use a filter keyed on the *request's creator* (`r.member == member` / `r.signer_pk == pk`), not on entries inside `confirmations` where that member/key previously voted on a request created by someone else. `assert_valid_request()` also only checks that the *caller* is currently a member; it never revalidates that previously stored confirmation entries still belong to live members: [4](#0-3) 

As a result, a confirmation cast by a member while they were still authorized remains permanently embedded in the `confirmations` set for any request they didn't create, even after that member/key is deleted. This breaks the binding "confirmations counted == live-member confirmations": the recorded count includes signers no longer part of the multisig, so a request can reach `num_confirmations` with strictly fewer *live* signers than required.

### Impact Explanation
This directly matches the "Critical" impact criterion "a multisig request executed below threshold." A transfer, `AddKey`, `DeployContract`, or any other multisig action can be executed with fewer live-member confirmations than `num_confirmations` mandates, effectively lowering the security threshold of the multisig without anyone's consent, and can be leveraged to move funds or change control of the account with less-than-configured authorization.

### Likelihood Explanation
This requires no attacker privilege beyond normal, expected multisig lifecycle operations: member/key churn (revoking a compromised or departing signer) is a routine, foundation-independent action available to any set of members reaching the existing threshold. It does not require a malicious member, a redeploy, or any out-of-scope precondition — it is a systemic bug that manifests whenever (a) a member confirms an open request they didn't create, and (b) that member is later removed before the request is otherwise fully confirmed/executed or deleted. Both are plausible, unprivileged sequences of normal multisig operation.

### Recommendation
When removing a member/key (`DeleteMember`/`DeleteKey`), also scan the `confirmations` map for all pending requests and strip out entries belonging to the removed member/key, not just requests that member/key created. Alternatively, when counting confirmations in `confirm()`, filter the confirmation set to only members currently present in `self.members` (multisig2) or `num_requests_pk`/access key set (multisig) before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with 4 members (Alice, Bob, Carol, Dave) and `num_confirmations = 3`.
2. Bob creates a `Transfer` request (`add_request`) — `confirmations = {}`.
3. Dave confirms it (`confirm`) — `confirmations = {Dave}` (len 1, `1+1 < 3`, not executed).
4. Separately, the multisig legitimately removes Dave (e.g., due to key rotation) via a `DeleteMember{Dave}` self-request that reaches 3 confirmations and executes — `delete_member` only cleans requests Dave *created*, so the Transfer request's `confirmations = {Dave}` is untouched: [5](#0-4) .
5. Now only Alice, Bob, Carol are live members (3 total, exactly meeting `num_confirmations`).
6. Alice confirms the Transfer request — `confirmations = {Dave, Alice}`, len 2, `2+1 >= 3`? No, 2+1=3>=3 → the request executes immediately after only 2 *live* confirmations (Alice + the stale Dave entry), instead of requiring 3 live signers.
7. The transfer executes with only 2 out of 4 (now 3) live members having actually approved it in real time, violating the configured `num_confirmations = 3` threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
