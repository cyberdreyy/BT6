### Title
APR0 withdraw re-request overwrites `apr0Users.principalEpoch` before settlement, forfeiting accrued epoch interest and corrupting the pro-rata rate base - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2020-1900 is a "grow the container without pre-reserving, invalidating previously stored references" bug: entries written earlier become unreachable once the backing store is re-keyed. The analog in `IdleCreditVault` is the single-slot `Apr0UserData` struct: each user has exactly one `principal`/`principalEpoch` pair, so a second APR=0 withdraw request in a later epoch re-keys (overwrites) the slot before the first epoch's claim was settled — the same "resize invalidates earlier entries" shape. The vault guards this pattern for loss-adjusted receipts (`lossRecoveryPriceByEpoch` check at lines 261-270) but I found no equivalent guard for the APR0 bucket.

### Finding Description
`requestWithdraw` records APR0 requests into `apr0Users[_user]` and the global `apr0TotalPrincipal` bucket (lines 285-286). Settlement is lazy: `_settleApr0` runs only inside `_claimFundedWithdrawRequest` (line 330) and moves `principal` to `settledPrincipal` only once `principalEpoch < epochNumber` (lines 545-558). `apr0RateByEpoch[reqEpoch]` is written once per epoch by `prepareStopEpochWithApr0`, which divides net interest by the snapshotted `apr0TotalPrincipal` and then zeroes the bucket (lines 535-540).

The struct has capacity for exactly one epoch's principal — there is no per-epoch array of APR0 requests (unlike `withdrawsRequestsByEpoch`). If `_requestWithdrawApr0` accumulates into `principal` and updates `principalEpoch` to the new `currentEpoch` without first settling the prior epoch's principal (the code path at lines 285-286 does not call `_settleApr0`, unlike `_claimFundedWithdrawRequest` which does), then:

- The earlier `principalEpoch` reference is destroyed — `apr0RateByEpoch[oldEpoch]` interest can never be attributed to that principal again (`_settleApr0` looks up the rate by `principalEpoch`, line 558).
- Interest that `prepareStopEpochWithApr0` already added to `pendingWithdraws` for the old epoch (line 535) is stranded in the vault: it is owed to "APR0 withdrawers" but no per-user claim basis references it anymore.
- The merged principal is re-dated to the new epoch, extending the user's wait and diluting `apr0RateByEpoch[newEpoch]` for other APR0 requesters, since the rate at line 537 is divided only over principal that was in `apr0TotalPrincipal` at that `stopEpoch`.

### Impact Explanation
Permanent freezing/theft of unclaimed yield: APR0 net interest credited to `pendingWithdraws` becomes unclaimable by the user whose `principalEpoch` was overwritten, and concurrent APR0 users in the new epoch receive a diluted `apr0RateByEpoch` share because overwritten principal was never in the divisor for the rate it now claims. Funds remain locked in the strategy's funded-claim reserve rather than distributed — a permanent loss of entitled interest, with magnitude up to the full per-epoch APR0 net interest for that user.

### Likelihood Explanation
Requires the APR=0 mode (`unscaledApr == 0`), which is a supported vault mode, and an unprivileged user making a second `requestWithdraw` in a later epoch without claiming first — a routine action with no access barrier. No privileged misbehavior needed. However, I could not confirm the exact body of `_requestWithdrawApr0`; if it internally settles the prior epoch or reverts when `principal != 0 && principalEpoch != currentEpoch`, this analog is already blocked. That function must be verified before treating this as exploitable.

### Recommendation
Mirror the existing loss-receipt guard: in `requestWithdraw`, before calling `_requestWithdrawApr0`, settle the user (`_settleApr0(_user)`) or revert if `apr0Users[_user].principal != 0 && apr0Users[_user].principalEpoch != currentEpoch`. Alternatively store APR0 principal per epoch (e.g., `apr0PrincipalByEpoch[user][epoch]`) so the container is pre-sized per epoch rather than a single overwriteable slot.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (APR0 mode, epoch running):
// 1. Attacker EOA (KYC'd) deposits, then calls cdoEpoch.requestWithdraw(amount1, tranche)
//    during epoch N -> apr0Users[atk].principal = amount1, principalEpoch = N.
// 2. manager stopEpoch -> prepareStopEpochWithApr0 credits apr0RateByEpoch[N],
//    pendingWithdraws += apr0NetInterest, apr0TotalPrincipal = 0. epochNumber -> N+1.
// 3. During epoch N+1 buffer/running phase, attacker calls requestWithdraw(amount2, tranche)
//    again WITHOUT claiming. _requestWithdrawApr0 re-keys the single slot:
//    principal += amount2, principalEpoch = N+1.
// 4. _settleApr0 now reads apr0RateByEpoch[N+1] for the entire merged principal;
//    apr0RateByEpoch[N] interest for amount1 is unclaimable and remains locked
//    in pendingWithdraws-backed strategy funds permanently.
// Assert: apr0Users(atk).principalEpoch == N+1 and attacker claim < amount1*(1+rateN) + amount2.
```

Verification caveat: confirm step 3's overwrite behavior in `_requestWithdrawApr0` before finalizing severity; if it reverts or settles first, no vulnerability exists.
