The report's root-cause pattern — "a small marginal action triggers a time-lock that blocks the *entire* pre-existing balance, not just the marginal amount involved" — maps precisely onto the `userUnitsRefundableUntil` refund-lock mechanism in `ProvisionerV2` / `MultiDepositorVault`.

### Title
Sync deposit refund-lock freezes a user's entire unit balance, not just the newly minted units - ([File: v3/src/core/ProvisionerV2.sol], [File: v3/src/core/MultiDepositorVault.sol])

### Summary
`ProvisionerV2._syncDeposit` unconditionally overwrites `userUnitsRefundableUntil[receiver]` with `block.timestamp + depositRefundTimeout` on every sync `deposit()`/`mint()` call [1](#0-0) . This single per-user timestamp is then checked as an all-or-nothing balance lock in `redeem()`, `withdraw()` [2](#0-1) [3](#0-2) , and in `MultiDepositorVault._update`, which blocks *all* outgoing unit transfers for the address, regardless of amount [4](#0-3) . A user with a large, fully-unlocked/mature unit balance who performs even a trivially small new sync deposit has their *entire* balance re-frozen for the whole `depositRefundTimeout` window, exactly mirroring the reported pattern where deallocating a small amount blocks funds that were never allocated/at risk.

### Finding Description
The exact path: an ordinary user holds a large balance of vault units acquired long ago (already past any refund window). They call `deposit(token, tokensIn, minUnitsOut, receiver=self)` with a small `tokensIn` amount. Internally this calls `_syncDeposit`, which sets `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout` [5](#0-4) . This mapping is keyed only by user address, with no tracking of which specific units are tied to the refundable deposit. Both `redeem()`/`withdraw()` guard checks and the `MultiDepositorVault._update` transfer-hook check `userUnitsRefundableUntil[msg.sender]`/`[from]` against `block.timestamp` for the **entire** balance, not for the specific `unitsOut` amount minted by the triggering deposit [6](#0-5) [7](#0-6) . The guard fails to distinguish "units that are subject to the refund window" from "units already fully settled," so it blocks funds that were never part of the refundable deposit — the same broken invariant as the reported issue (blocking unallocated/unrelated funds due to a lock meant to cover only a specific, smaller sub-amount).

### Impact Explanation
This causes a temporary freeze of a user's entire vault unit balance (transfers, sync redeems, and sync withdrawals all reverting with `Aera__UnitsLocked`) triggered merely by making an additional small deposit, for the duration of `depositRefundTimeout`. This is a self-inflicted but user-facing temporary freeze of funds not intended to be locked, consistent with a Medium-severity temporary freeze of user funds.

### Likelihood Explanation
Highly feasible: any depositor holding units can trigger this simply by calling the public, unauthenticated `deposit()`/`mint()` sync functions with `receiver = msg.sender` (self-deposit requires no special approval) [8](#0-7) . No privileged role, oracle manipulation, or malicious third party is required — it is an ordinary sequence of standard user actions (large deposit long ago + small deposit now).

### Recommendation
Track refund-eligible units per-deposit (e.g., per deposit hash or a separate "locked units" counter incremented/decremented by exact deposit/refund amounts) instead of a single per-user timestamp gating the whole balance. `redeem`/`withdraw`/transfer checks should only restrict the specific units still within their refund window, not the account's full balance.

### Proof of Concept
1. Fork mainnet with a deployed `MultiDepositorVault`/`ProvisionerV2` pair with sync deposits enabled and `depositRefundTimeout > 0`.
2. As user A, call `deposit()` with a large `tokensIn`, then advance `block.timestamp` past `depositRefundTimeout` so `userUnitsRefundableUntil[A] < block.timestamp` (units unlocked).
3. Call `deposit()` again with a minimal `tokensIn` (e.g., 1 wei equivalent) as the same user A.
4. Assert `areUserUnitsLocked(A) == true` immediately after step 3.
5. Attempt `redeem()`/`withdraw()` or an ERC20 `transfer` of the units minted in step 2 (the large, mature balance) — assert it reverts with `Aera__UnitsLocked()`, proving that funds unrelated to the small new deposit are frozen.

    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }
