### Title
Vault-liquidity starvation lets any ERC4626 vault user block `stopEpoch` and freeze all pool funds - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` calls `vault.withdraw(shortfall, ...)` inside a `try/catch` that reverts with `StopEpochVaultLiquidityUnavailable` whenever the external ERC4626 vault cannot honor the withdrawal. `IdleCDOEpochVariant._stopEpoch` deliberately lets that revert bubble up. Any unprivileged user of the configured ERC4626 vault can therefore grief `stopEpoch` by draining the vault's *liquid* underlying balance (while the programmable borrower still holds shares nominally covering the shortfall), forcing every `stopEpoch` call to revert and temporarily freezing all tranche-holder withdrawals.

### Finding Description
The vulnerability is in `onStopEpoch`:

```solidity
// contracts/strategies/idle/ProgrammableBorrower.sol:240-253
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The solvency pre-check `shortfall > _currentVaultAssets()` only verifies that the borrower's *share position* is worth more than the shortfall — it does not verify that the vault has enough *redeemable liquidity*. For yield-bearing ERC4626 vaults (lending markets, strategies with lockups/utilization), `convertToAssets(shares)` can exceed `maxWithdraw`/`maxRedeem`, so `vault.withdraw` reverts.

`IdleCDOEpochVariant._stopEpoch` propagates the hook revert:

```solidity
// contracts/IdleCDOEpochVariant.sol:395-404
if (isProgrammableBorrower) {
  // Hook reverts bubble so transient ERC4626 liquidity failures can be retried.
  if (!IProgrammableBorrower(_borrower()).onStopEpoch(...)) { ... }
}
```

So the whole `stopEpoch` transaction reverts. Since the epoch state machine requires `stopEpoch` to set `isEpochRunning = false`, increment `epochNumber`, unpause the contract, and clear `pendingWithdraws` before `claimWithdrawRequest` can succeed (`epochNumber <= lastWithdrawRequest[_user]` reverts otherwise), every queued withdrawal, buffer deposit claim, and the next `startEpoch` are frozen for as long as the vault stays illiquid.

The attacker needs no privilege: they only need to be a depositor/user of the external ERC4626 vault. During an active epoch they redeem/borrow the vault's available underlying down to (or below) the level where `ProgrammableBorrower`'s required `shortfall` can no longer be satisfied. When the manager calls `stopEpoch`, the withdraw reverts and the epoch cannot close. The attacker can re-drain whenever liquidity reappears, extending the freeze, or combine with a lending vault's interest-rate spikes to keep utilization at 100%.

This mirrors CVE-2015-8734's class — a mishandled external input path crashing the caller — mapped onto the epoch state machine: an external vault failure mode (insufficient liquidity despite nominally sufficient shares) is converted into a hard revert that crashes the stop flow rather than degrading gracefully.

### Impact Explanation
Temporary freezing of all funds in the credit vault. While the vault is starved:
- pending withdraw receipts cannot be claimed (`_claimFundedWithdrawRequest` requires `epochNumber > lastWithdrawRequest[_user]`, and `epochNumber` only advances inside `stopEpoch`),
- buffer deposits for the next epoch cannot be claimed (`startEpoch` reverts until `epochEndDate + bufferPeriod` of a *stopped* epoch passes, which never happens),
- the pool cannot be closed or defaulted through the normal path.

The freeze lasts as long as the attacker keeps vault liquidity exhausted and can be repeated indefinitely at the cost of capital parked/rotated in the vault. There is also a loss-of-yield component: borrower interest keeps accruing on `borrowerPrincipal` while tranche holders cannot exit. The only escapes are privileged (`emergencyExitVault` by owner/manager, or `rescueTokens`), so unprivileged LPs are entirely dependent on operator intervention.

### Likelihood Explanation
- Requires the programmable-borrower mode (`isProgrammableBorrower`) with a nontrivial shortfall at stop time — i.e., `_amountToPullFromBorrower + _pendingWithdraws > onHand`. This is the normal case, since idle funds are parked in the vault by design.
- Requires the external ERC4626 vault to support liquidity exhaustion (utilization-based lending vaults, queued-withdrawal vaults, or vaults where a large co-depositor can redeem the float). The attacker is explicitly an in-scope actor ("user of the programmable borrower's ERC4626 vault").
- Cost to the attacker is opportunity cost / borrow fees in the external vault, not capital destruction. If the vault is a lending market, driving utilization to 100% is a standard, cheap manipulation for a whale.
- No existing guard prevents it: the `shortfall > _currentVaultAssets()` check uses share *value*, not vault liquidity; `_skimDonatedAssets`, KYC gating, and `nonReentrant` are irrelevant; the catch block converts recoverable illiquidity into a hard revert by design.

### Recommendation
- In `onStopEpoch`, do not revert when the shares are nominally sufficient but the vault lacks liquidity. Instead, withdraw what is redeemable (e.g., `vault.maxWithdraw(address(this))` / `maxRedeem`) and return `false` or transfer the partial amount, letting `IdleCDO`'s existing `getFundsFromBorrower` `try/catch` route the shortfall into `_handleBorrowerDefault` with a real loss number instead of freezing the epoch.
- Alternatively, precompute the pull amount as `min(required, onHand + maxWithdraw)` and treat any uncovered remainder as a partial loss/default through `previewLossAdjustedWithdrawFunds`, so tranche holders crystallize a bounded loss rather than an open-ended freeze.

### Proof of Concept
Foundry fork PoC sketch (programmable-borrower deployment; attacker is a co-depositor of the external ERC4626 vault):

```solidity
function testVaultLiquidityStarvationBlocksStopEpoch() external {
  // Setup: programmable borrower mode, epoch started, LP withdraw requests pending.
  _startEpochAndCheckPrices(0);                       // onStartEpoch parks idle cash in vault
  // borrower draws some principal so a shortfall exists at stop
  vm.prank(borrower);
  IProgrammableBorrower(pb).borrow(0);                // draws availableToBorrow()

  // some LPs queue normal withdraws during buffer/epoch
  // (done pre-start or via queue depending on variant)

  // ATTACKER: whale depositor of the external ERC4626 vault withdraws
  // all liquid underlying so vault.withdraw() will revert for the shortfall.
  vm.prank(attacker);                                 // attacker = vault share holder
  vault.redeem(vault.balanceOf(attacker), attacker, attacker); // drains vault liquidity
  // vault.convertToAssets(pbShares) still > shortfall (shares are fine,
  // only liquidity is gone), so the solvency pre-check does not bail out.

  // Warp past epoch end and fulfill instant withdraws as manager normally would.
  vm.warp(cdoEpoch.epochEndDate() + 1);

  // stopEpoch reverts -> epoch can never close while attacker keeps vault dry
  vm.prank(manager);
  vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
  cdoEpoch.stopEpoch(newApr, 0);

  // Funds frozen: pending receipts unclaimable, epochNumber stuck.
  vm.expectRevert(NotAllowed.selector);
  cdoEpoch.claimWithdrawRequest();

  // Attacker can keep griefing: redeposit briefly, re-drain before each stop.
}
```

Key assertion: `vault.maxWithdraw(pb) < shortfall <= vault.convertToAssets(vault.balanceOf(pb))` — shares cover on paper, withdraw reverts in practice. The PoC demonstrates that one unprivileged vault user forces repeated `stopEpoch` reverts, freezing all LP principal and pending withdrawals until the attacker (or honest liquidity) restores vault liquidity.
