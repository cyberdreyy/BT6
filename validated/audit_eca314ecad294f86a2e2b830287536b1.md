## Title
Stale cross-tenure signature loses all liveness verification, allowing the signer to sign two conflicting siblings at the same height across tenures - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_pre_commit`'s conflict guard checks `conflict_still_blocks` (a node-derived liveness question) only for conflicts that are still *fresh* (`last_endorsed > freshness_cutoff`). Once a cross-tenure conflicting signature goes stale, the code path that re-checks node state for same-tenure conflicts (`get_tenure_tip`) is never invoked for a conflict in a *different* tenure, so a stale cross-tenure signature is dropped from consideration entirely, with no verification that the conflicting block might still be canonical.

### Finding Description
In `Signer::handle_block_pre_commit` [1](#0-0) , conflicts returned by `SignerDb::get_signed_conflicts` [2](#0-1)  are filtered by a single `find` predicate:

```
conflict.last_endorsed > freshness_cutoff
    && !self.reorg_permit_stands(...)
    && self.conflict_still_blocks(...)
```

Because Rust's `&&` short-circuits, `conflict_still_blocks` (the only place that asks the node whether the conflicting tenure's sortition is still canonical or whether its chain still reaches the block, see `Signer::conflict_still_blocks` [3](#0-2) ) is never even called once `last_endorsed <= freshness_cutoff`.

Immediately after, a second, independent check re-derives node state for conflicts, but only for conflicts whose `consensus_hash` equals `block_info`'s own tenure [4](#0-3) . This second check queries `get_tenure_tip` and refuses to sign if the tenure's canonical tip is already at or above the proposed height — but it explicitly excludes cross-tenure conflicts (`conflict.consensus_hash == block_info...consensus_hash`).

The result: for a conflict in a *different* tenure, once its `last_endorsed` timestamp crosses `tenure_last_block_proposal_timeout` (`freshness_cutoff`), it is dropped from both checks with **zero** further liveness verification — no `get_tenure_tip`, no `get_sortition_by_burn_hash`, no `reorg_permit_stands`. This differs from the same-tenure case, where staleness alone does not clear a conflict (the tip-height check still applies), and it differs from the fresh cross-tenure case, which is explicitly tested and blocks (`fresh_conflict_in_another_tenure_blocks_signing` [5](#0-4) ).

The code comment at line 1425-1426 asserts "whether this block may replace what another tenure built is settled by the chainstate checks above" [6](#0-5) , but `docs/signer-flows.md` explicitly documents that the chainstate re-check (`check_block_against_signer_db_state`) only ever inspects *one* tenure — a tenure-change block's parent, or a block's own tenure — and that "a signed sibling at the same height in a third tenure is invisible to it" [7](#0-6) . This is a direct contradiction between the code's stated rationale and the actual coverage of the chainstate re-check, meaning that once staleness is reached, **no** mechanism verifies the cross-tenure conflict is actually dead before a second signature is placed.

**Attack flow:** As sole miner, the attacker wins two competing tenures X and Y (a genuine Bitcoin fork or reorg scenario, which `check_parent_tenure_choice`/`first_proposal_burn_block_timing` is designed to police at proposal time, not at pre-commit time) both extending the same globally-accepted parent, and proposes conflicting blocks at the same `chain_length` h. The victim signer signs tenure X's block (`signed_self` set, fresh). The attacker delays tenure Y's proposal's pre-commit-threshold crossing until just after `tenure_last_block_proposal_timeout` has elapsed on X's endorsement. At that instant, `handle_block_pre_commit` for Y's block sees X's conflict as stale, skips `conflict_still_blocks`, skips the tip-height check (different tenure), and signs Y — even though X's block may still be pending group signature and could still become canonical.

### Impact Explanation
This breaks the equivocation guard that is supposed to guarantee a given signer never has `signed_self` set on two conflicting `signer_signature_hash` values at the same height across tenures. If enough signers can be timed this way (an attacker only needs the aggregate signer set's individual freshness windows to lapse around the crossing of the pre-commit threshold for Y), both X and Y could simultaneously accumulate enough distinct-but-overlapping signatures to reach the 70% threshold, producing two competing, signer-approved blocks at the same Stacks height — an equivocation/chain-safety violation. This matches the Critical category: "a signer signing an invalid, non-canonical, or conflicting block (chain safety)". It is repeatable per tenure-height race.

### Likelihood Explanation
Preconditions require: (1) the signer already holds a fresh `signed_self` on X's block at height h; (2) Y's competing sibling block at height h reaches the pre-commit weight threshold; (3) precise timing so that crossing happens just after X's `last_endorsed` ages past `tenure_last_block_proposal_timeout`. The attacker needs only a single miner slot (or two competing tenures via a natural/engineered Bitcoin-level fork) plus the ability to gossip `BlockProposal`/`BlockPreCommit` messages — consistent with the allowed unprivileged-miner threat model. The precise timing requirement (racing a local timeout against a network-relayed weight-threshold crossing) is the main feasibility constraint, but `tenure_last_block_proposal_timeout` is a known, static configuration value the attacker can measure and target, making the race achievable with reasonable engineering effort, and it can be retried once per fork opportunity.

### Recommendation
Do not let a conflict's staleness alone drop it from consideration when the conflict is in a different tenure. Extend the cross-tenure branch to independently query node liveness (`get_tenure_tip`/`get_sortition_by_burn_hash` via `conflict_still_blocks`) for stale cross-tenure conflicts as well, mirroring the same-tenure tip-height check, so that a stale cross-tenure conflict can only be cleared once the node's chainstate proves the conflicting tenure's block is actually dead (orphaned sortition, or globally-accepted-then-reorged), not merely because the local freshness timer expired.

### Proof of Concept
Add a new test in `stacks-signer/src/v0/tests.rs` alongside `run_cross_tenure_scenario`, reusing its harness but with a zero/near-zero `tenure_last_block_proposal_timeout` (mirroring `run_sibling_scenario(Duration::ZERO, ...)`) and `TenureAFate::Live` (node knows nothing about either tenure — the ambiguous/unconfirmed case that currently blocks when fresh):

```rust

fn stale_conflict_in_another_tenure_no_longer_blocks_signing_even_when_live() {
    // Same as `fresh_conflict_in_another_tenure_blocks_signing`, but the fresh window is
    // effectively zero: A's signature is stale by the time B reaches pre-commit threshold.
    // TenureAFate::Live means the node has NO evidence A is dead (no orphan record, not
    // globally accepted+reorged, no reorg permit) -- yet with the freshness guard defeated,
    // B is signed anyway.
    let (info_a, info_b) = run_cross_tenure_scenario_with_timeout(
        TenureAFate::Live,
        Duration::ZERO, // tenure_last_block_proposal_timeout
    );
    assert_a_signed(&info_a);
    // EXPECTED (per current guard's intent): info_b should remain refused/PreCommitted,
    // since the node has no proof A is dead.
    assert_eq!(
        info_b.state, BlockState::PreCommitted,
        "block B must not be signed while A's conflicting tenure is still unconfirmed, got: {}",
        info_b.state
    );
    assert!(
        info_b.signed_self.is_none(),
        "both info_a.signed_self and info_b.signed_self must never both be Some at the same height across tenures"
    );
}
```

This requires adding a `run_cross_tenure_scenario_with_timeout` variant (or parameterizing `run_cross_tenure_scenario`) that accepts the `tenure_last_block_proposal_timeout` value instead of the hardcoded `Duration::from_secs(100_000)` used in the existing `run_cross_tenure_scenario` [8](#0-7) . Running this test against the current code is expected to fail the final assertion — `info_b.signed_self.is_some()` — demonstrating that `info_a.signed_self.is_some() && info_b.signed_self.is_some()` both hold for conflicting same-height blocks in different tenures once the timing race described above is hit.

    fn conflict_still_blocks(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
        proposed_height: u64,
    ) -> bool {
        if let Ok(burn_block) = self
            .signer_db
            .get_burn_block_by_ch(&conflict.consensus_hash)
        {
            match stacks_client.get_sortition_by_burn_hash(&burn_block.block_hash) {
                Ok(_) => {
                    // The tenure's sortition is still canonical: the conflict is live at the
                    // burn chain level, so fall through to the block-level questions.
                }
                Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                    // A 404 only proves the sortition was orphaned if the node's burnchain
                    // view actually covers the burn block's height: a node still catching up
                    // 404s canonical burn blocks it hasn't processed yet (and the
                    // endpoint also 404s on internal data misses). Only trust it once the
                    // node's burnchain tip is at or past the stored burn block.
                    match stacks_client.get_peer_info() {
                        Ok(peer_info) if peer_info.burn_block_height >= burn_block.block_height => {
                            info!("{self}: A conflicting block's tenure was orphaned by a burnchain fork. The conflict no longer blocks.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "conflicting_block_height" => conflict.stacks_height,
                                "burn_block_hash" => %burn_block.block_hash,
                            );
                            return false;
                        }
                        Ok(peer_info) => {
                            info!("{self}: The node does not know a conflicting block's burn block, but its burnchain tip has not reached that height, so this does not prove the tenure was orphaned. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                                "burn_block_hash" => %burn_block.block_hash,
                                "burn_block_height" => burn_block.block_height,
                                "node_burn_block_height" => peer_info.burn_block_height,
                            );
                            return true;
                        }
                        Err(e) => {
                            warn!("{self}: Failed to fetch the node's burnchain tip while checking a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                                "conflicting_consensus_hash" => %conflict.consensus_hash,
                            );
                            return true;
                        }
                    }
                }
                Err(e) => {
                    warn!("{self}: Failed to check whether a conflicting block's tenure is still canonical: {e:?}. Leaving the conflict in place.";
                        "conflicting_consensus_hash" => %conflict.consensus_hash,
                    );
                    return true;
                }
            }
        }
        let node_reaches_conflict = match stacks_client.get_tenure_tip(&conflict.consensus_hash) {
            Ok(tip) => tip.anchored_header.height() >= conflict.stacks_height,
            // A 404 is an answer, not a failure: the node has no blocks in that tenure at all.
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => false,
            Err(e) => {
                warn!("{self}: Failed to fetch the canonical tip of a conflicting block's tenure: {e:?}. Leaving the conflict in place.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "conflicting_block_height" => conflict.stacks_height,
                );
                return true;
            }
        };
        node_reaches_conflict
            || (!conflict.globally_accepted && conflict.stacks_height <= proposed_height)
    }

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
