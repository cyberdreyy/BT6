### Title
Performance-fee accounting only books positive NAV moves and never refunds `unclaimedFees` after losses, so fees are paid out of lender principal - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDO` / `IdleCDOCreditVault` accrue performance fees into `unclaimedFees` only when `nav > lastNAV`, exactly like the external report's `pendingRevenue` bucket. When the NAV later drops below `lastNAV`, `_updateAccounting` does not reduce `unclaimedFees` by any part of the loss. The stale fee accrual is excluded from tranche NAV via `getContractValue()` and is eventually paid to `feeReceiver`/`owner` — either as cash at `stopEpoch` or as freshly minted AA shares in minted-interest mode — even though the vault's net performance no longer justifies that fee. The excess comes out of lender principal. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
In `IdleCDOCreditVault._updateAccounting()`:

```solidity
uint256 nav = getContractValue();
// If gain is > 0, then collect some fees in `unclaimedFees`
if (nav > _lastNAV) {
  unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
}
```

The identical pattern exists in `IdleCDO.sol:280-282` and `IdleCDOLeveregedEulerVariant.sol:186-188`. Three observations:

1. `unclaimedFees` is a monotonically increasing accumulator for performance fees. There is no `else` branch that reduces it when `nav < _lastNAV`.
2. `getContractValue()` subtracts `unclaimedFees` from tranche NAV (`IdleCDOCreditVault.sol:127`, `IdleCDO.sol:186`), so the accrued fee is reserved against the pool the moment it is booked — tranche holders bear it immediately.
3. The fee is then paid out in `IdleCDOEpochVariant`'s stop-epoch path: in cash mode capped only by current-epoch gross interest (`_fees > _availableForFees` clamp at line 452-455), and in minted-interest mode (`_mintInterest`) **uncapped** — `_mintSharesAtCurrPrice(feeReceiverAmount, feeReceiver, AATranche)` and the remainder to `owner()` at lines 442-448 — minting AA shares whose value is backed by tranche NAV.

Concrete scenario (numbers in underlying, `fee = 10%`, `managementFee = 0`, minted-interest credit vault):

1. Epoch runs; AA+BB NAV = 1000. Strategy/borrower repays interest: NAV = 1200. Next interaction calls `_updateAccounting`: `unclaimedFees += (1200-1000)*10% = 20`, `lastNAVAA+lastNAVBB` updated to `1200 - 20` netted through the tranches.
2. Before stop, the position loses 150 (e.g. vault loss on a programmable borrower's ERC4626 sleeve surfaced through `vaultLoss`/`totalInterestDueNow`, or `stopEpochWithDuration(_lossAmount)` burning strategy tokens and calling `_forceUpdateAccounting`). NAV = 1050; `unclaimedFees` still = 20, even though net epoch PnL is only +50 and the fair performance fee is 5.
3. At the next `stopEpoch`, `_fees = unclaimedFees = 20` is paid: in minted mode 20 worth of AA shares are minted to `feeReceiver`/`owner`; in cash mode up to `grossInterest` is transferred. The extra 15 over the fair 5 is principal backing tranche tokens, mislabeled as fee revenue — identical mechanics to the external `pendingRevenue` bug.

Note `_virtualPriceAux` also removes `fee` from positive `totalGain` (`IdleCDOCreditVault.sol:312-314`) and never adds it back on losses, so the overcharge is applied consistently in both the fee bucket and the tranche price split.

### Impact Explanation
Tranche holders permanently lose the over-accrued fee amount to `feeReceiver`/`owner`. The broken invariant is the separation between principal backing and yield-derived fees: after a loss, `unclaimedFees` exceeds `fee%` of net lifetime PnL, and the difference is paid from principal. The minted-interest path is worst-case: the over-accrual is converted into AA tranche shares at `priceAA`, i.e. a direct claim on vault assets senior to BB. Quantified: any loss `L` following a gain `G` over-accrued `fee% * min(L, G)` (bounded by `unclaimedFees`); e.g. +200 gain then −150 loss with 10% fee overpays 15 underlying.

### Likelihood Explanation
Requires a NAV decline after a gain was checkpointed — a routine occurrence: `stopEpochWithDuration(_lossAmount)` (manager, honest) burns strategy tokens and force-updates accounting, and programmable-borrower vault losses flow through `totalInterestDueNow`/`vaultLoss`. Any unprivileged lender or vault user can be positioned while honest manager/borrower calls sequence the gain-then-loss. No malicious privileged role needed; the payout is executed by the protocol's own honest `stopEpoch`. Not blocked by `_skimDonatedAssets`, `Default` revert (loss need not exhaust BB), or fee caps (minted-mode fee payout is uncapped; cash-mode cap uses gross current-epoch interest, which does not offset prior-period over-accrual on the carried balance... though the carried balance itself is what gets reduced only by payout, never by losses).

### Recommendation
Make `unclaimedFees` loss-adjusted, mirroring the external fix. In `_updateAccounting` (all three variants) and in `virtualPrice`/preview paths, when `nav < _lastNAV` reduce `unclaimedFees` by `loss * fee / FULL_ALLOC` (or equivalently recompute the fee claim as `fee%` of net cumulative gain), flooring at 0, before updating `lastNAVAA`/`lastNAVBB`:

```solidity
if (nav > _lastNAV) {
  unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;
} else if (nav < _lastNAV) {
  uint256 rebate = (_lastNAV - nav) * fee / FULL_ALLOC;
  unclaimedFees = rebate >= unclaimedFees ? 0 : unclaimedFees - rebate;
}
```

Care is needed for the management-fee component accrued by `_accrueManagementFee` (`IdleCDOCreditVault.sol:552-555`), which is time-based and legitimately accrues through losses — only the performance-fee portion should be rebated, so the two fee types may need separate buckets.

### Proof of Concept
Foundry test against `IdleCDOEpochVariant` (minted-interest mode) in `test/foundry/IdleCreditVault.t.sol` style:

```solidity
function testUnclaimedFeesNotRebatedAfterLoss() external {
    uint256 amount = 10_000 * ONE_SCALE;
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, 0); // feeReceiver=TL_MULTISIG, fee=10%, mgmtFee=0
    idleCDO.depositAA(amount);                   // NAV = 10_000

    // Epoch 1: gain +2_000 (borrower repays principal + interest)
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setApr(initialProvidedApr);
    cdoEpoch.startEpoch();
    vm.stopPrank();
    uint256 gain = 2_000 * ONE_SCALE;
    deal(defaultUnderlying, borrower, gain);
    vm.warp(cdoEpoch.epochEndDate());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, gain);
    // unclaimedFees == 200 (10% of 2000), paid or carried depending on mode

    // Epoch 2: loss of 1_500 via stopEpochWithDuration
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    cdoEpoch.startEpoch();
    vm.stopPrank();
    vm.warp(cdoEpoch.epochEndDate());
    uint256 loss = 1_500 * ONE_SCALE;
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, 365 days, loss); // burns strategy tokens, _forceUpdateAccounting

    // Net lifetime PnL = +500 -> fair fee = 50, but accrued fee bucket still reflects
    // the un-rebated 10% of the +2000 gain minus nothing for the loss.
    // Assert: unclaimedFees (and/or shares minted to feeReceiver) exceeds 50 worth,
    // i.e. ~150 of principal was booked as fees.
    assertGt(cdoEpoch.unclaimedFees(), 50 * ONE_SCALE, "fee bucket not reduced by loss");
}
```

Extend by performing a subsequent profitable `stopEpoch` in minted mode and asserting `IdleCDOTranche(AATranche).balanceOf(feeReceiver)` exceeds the fair net-yield fee — demonstrating principal conversion to feeReceiver shares.
