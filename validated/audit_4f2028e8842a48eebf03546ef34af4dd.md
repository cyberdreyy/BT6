### Title
Unauthenticated `PATCH /v2/resume/:runID` allows any unprivileged client to inject arbitrary pipeline task results - (File: `core/web/router.go`, `core/web/pipeline_runs_controller.go`)

### Summary
The external report describes `offer(uint,ERC20,uint,ERC20)` and `insert(uint,uint)` as functions that are documented/intended to be restricted to authorized keepers, but ship with no actual access-control check, letting any caller invoke them and manipulate protocol state. The closest analog in this codebase is the node's `Resume` pipeline-run endpoint: it is registered on an explicitly unauthenticated router group and performs no session, API-token, or external-initiator check before mutating pipeline execution state, relying solely on knowledge of an opaque UUID as the "authorization."

### Finding Description
`v2Routes` registers the resume endpoint on the `unauthedv2` group, which has no authentication middleware attached at all, unlike every other mutating route in the file which is wrapped in `auth.Authenticate(...)` combined with `auth.RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`: [1](#0-0) 

Compare this to the `userOrEI` group a few lines below, which does require authentication (`AuthenticateExternalInitiator`, `AuthenticateByToken`, `AuthenticateBySession`) even for creating a job run: [2](#0-1) 

The handler itself performs no authorization check of its own — it only parses the `runID` path parameter as a UUID and directly calls `ResumeJobV2` with attacker-supplied result data: [3](#0-2) 

The audit event name `audit.UnauthedRunResumed` confirms this lack of authentication is a recognized, deliberate property of the endpoint rather than an oversight, but the only protection against abuse is the difficulty of guessing a valid pending task UUID — there is no token, HMAC, or credential check comparable to the `AuthenticateExternalInitiator`/`AuthenticateByToken` mechanisms used elsewhere in the router.

### Impact Explanation
Any unauthenticated network client that can determine or observe a pending task's UUID (e.g., via a leaked external adapter callback URL, application logs, or a compromised downstream service that received the callback URL) can submit arbitrary `pipeline.ResumeRequest` result data to complete that pipeline task. This is functionally equivalent to the reported bug class: an operation that should be gated to an authorized party (in Chainlink's case, the specific external adapter/bridge that owns the pending async task) has no explicit access control, and can be invoked by anyone who possesses the identifier — closely mirroring how `insert(uint,uint)`/`offer(uint,ERC20,uint,ERC20)` could be invoked by anyone possessing knowledge of the order ID. A successful call here can inject falsified data into a job pipeline result, which may ultimately be reported on-chain by the oracle job.

### Likelihood Explanation
Likelihood is moderated by the fact that `runID` is a randomly-generated UUID (v4, 128 bits of entropy) rather than a small integer, making blind brute force infeasible. Exploitation therefore requires the attacker to first obtain a valid task UUID through some other channel (log exposure, callback URL leakage from a compromised external adapter, network capture of the callback request, etc.), which is a plausible but non-trivial precondition. It is not a purely coincidental bypass like the Rubicon offer/insert functions (which have no secret component at all), but the endpoint remains categorically "no authentication implemented" for a state-mutating operation on the node's job-pipeline execution.

### Recommendation
- Require that resume callbacks be authenticated, e.g., by binding the task to a per-request signed token or HMAC (rather than relying solely on UUID secrecy), or by requiring the external adapter to present the external-initiator or bridge-specific credentials already used elsewhere in the router (`auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`).
- At minimum, rate-limit and audit-log every failed resume attempt distinctly (not just successes) to detect enumeration/guessing attempts.
- Confirm this design decision is intentional and documented; if bridge/external-adapter authentication is feasible for this callback path, migrate it off the `unauthedv2` group.

### Proof of Concept
1. Observe or leak a valid pending task UUID (`runID`) associated with an in-flight bridge/async pipeline task (e.g. from adapter logs, network traffic, or a misconfigured webhook target).
2. Without any session cookie, API token, or external-initiator header, send:
```
PATCH /v2/resume/<leaked-task-uuid>
Content-Type: application/json

{"value": "<attacker-controlled result>"}
```
3. The node's `PipelineRunsController.Resume` accepts the request (no auth check present in the `unauthedv2` route group) and calls `App.ResumeJobV2` with the attacker-supplied result, completing the pipeline task with falsified data.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}
