### Title
Stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` lets a funded instant-withdraw receipt be counted again in default recovery, stealing recovery reserve and freezing legitimate claims - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` zeroes the aggregate `instantWithdrawsRequests[user]` but never clears the per-epoch mappings `instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` [1](#0-0) . This mirrors the Hats `_swapSigner` bug: a counter keyed to old state stays "warm" after the balance it represented was already paid. If the borrower later defaults in a different epoch and the stale entry's epoch equals `defaultRecoveryEpoch` (or the user accrues fresh receipts so the aggregate no longer underflows), `_claimDefaultedInstantWithdrawRequest` pays the already-claimed amount a second time from `defaultRecoveryReserve`, and `defaultPendingClaimBasis` inflates `totalBasis`, diluting every other recovery claimant [2](#0-1) .

### Finding Description
Analog of the "outdated counter incremented/used incorrectly" bug class, mapped to the instant-withdraw receipt surface:

1. In `requestInstantWithdraw`, the vault records the same amount three ways: `instantWithdrawsRequests[user]`, `instantWithdrawsRequestsByEpoch[user][epochNumber]`, and `instantWithdrawClaimsByEpoch[epochNumber]` [3](#0-2) .
2. In `claimInstantWithdrawRequest`, only `instantWithdrawsRequests[user]` is reset to 0. The two per-epoch mappings are left untouched, unlike the normal-withdraw path which explicitly clears `withdrawsRequestsByEpoch` inside `_clearWithdrawClaimForEpoch` [4](#0-3) [5](#0-4) .
3. On default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`, and `defaultRecoveryEpoch` is set to the current `epochNumber` [6](#0-5) [7](#0-6) .
4. `_claimDefaultedInstantWithdrawRequest` then computes `claimBasis` from the stale per-epoch mapping, decrements the aggregate, decrements `instantWithdrawClaimsByEpoch`, burns `claimBasis` receipt tokens, and pays `claimBasis * defaultRecoveryPrice` out of the isolated `defaultRecoveryReserve` [2](#0-1) .

Attack sequence (instant mode, epoch E):

- User A (any tranche holder) calls `requestInstantWithdraw(X)`: per-epoch entries = X, `pendingInstantWithdraws` = X.
- CDO funds it via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds(X)`; A claims X at par. `instantWithdrawsRequests[A]` = 0, but `instantWithdrawsRequestsByEpoch[A][E]` and `instantWithdrawClaimsByEpoch[E]` still hold X.
- A calls `requestInstantWithdraw(Y)` in the same epoch E: per-epoch = X+Y, `pendingInstantWithdraws` = Y (left unfunded).
- Borrower fails to repay; `finalizeDefaultRecovery` runs while `epochNumber == E` and `pendingInstantWithdraws != 0`, so `defaultRecoveryEpoch = E` and `defaultInstantWithdrawsFinalized = true`. `defaultPendingClaimBasis` counts X+Y although only Y is real — recovery price is diluted by X for all claimants.
- In a later epoch E+1 (or post-default operations), A calls `requestInstantWithdraw(Z)` again: `instantWithdrawsRequests[A]` = Y+Z while `instantWithdrawsRequestsByEpoch[A][E]` stays X+Y.
- A calls `claimInstantWithdrawRequest`: `claimBasis` = X+Y, aggregate = Y+Z. As long as `Z >= X` (and A holds `>= X+Y` receipt tokens, which it does since it received minted receipts for Y and Z), the subtraction and burn succeed and A receives `(X+Y) * defaultRecoveryPrice` from the reserve — X is paid a second time.

The mirror-image DoS also exists: if A cannot top up the aggregate to cover the stale basis, `instantWithdrawsRequests[A] -= claimBasis` underflows and A's legitimate Y/Z claims revert permanently, freezing their recovery payout [8](#0-7) .

### Impact Explanation
Direct theft from `defaultRecoveryReserve`: the already-paid X is claimed again at `defaultRecoveryPrice`, and because the stale X inflated `totalBasis`, every honest defaulted-epoch and active claimant receives a lower `recoveryPrice`. Quantified loss ≈ `X * defaultRecoveryPrice` stolen plus proportional dilution of all other claims. Secondary impact: permanent freezing of the attacker's own/other users' instant claims when the aggregate underflows instead.

### Likelihood Explanation
Requires the instant-withdraw flow to be enabled, the borrower to default while an epoch has unfunded `pendingInstantWithdraws`, and the same user to have claimed a funded instant receipt earlier in the default epoch. These are all reachable through normal, unprivileged user actions (request/claim) sequenced around honest privileged calls (funding, default finalization). No guard prevents `requestInstantWithdraw` after a prior funded claim or after default finalization.

### Recommendation
Clear the per-epoch accounting when a funded instant receipt is claimed, matching the normal-withdraw path:

```solidity
// in claimInstantWithdrawRequest
uint256 currentEpochClaim = instantWithdrawsRequestsByEpoch[_user][lastOrStoredEpoch];
instantWithdrawsRequestsByEpoch[_user][epoch] = 0;
instantWithdrawClaimsByEpoch[epoch] -= amount;
```

This requires tracking the request epoch per user for instant receipts (e.g. a `lastInstantWithdrawRequestEpoch` mapping), or decrementing `instantWithdrawClaimsByEpoch` by the claimed amount in `collectInstantWithdrawFunds`/claim so funded receipts are removed from the per-epoch basis. Alternatively, make `_claimDefaultedInstantWithdrawRequest` cap `claimBasis` at `instantWithdrawsRequests[_user]` so stale per-epoch entries can never exceed the live aggregate.

### Proof of Concept
Reproducible Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness, instant-withdraw mode):

```solidity
// 1. Epoch E running, instant withdraws enabled.
vm.prank(userA);
cdoEpoch.requestInstantWithdraw(X);           // per-epoch[A][E] = X

// 2. Manager/CDO funds instant queue; userA claims at par.
//    -> collectInstantWithdrawFunds(X); pendingInstantWithdraws = 0
vm.prank(userA);
cdoEpoch.claimInstantWithdrawRequest();       // pays X; per-epoch[A][E] stays X (BUG)

// 3. userA requests Y again in same epoch; stays unfunded.
vm.prank(userA);
cdoEpoch.requestInstantWithdraw(Y);           // per-epoch[A][E] = X+Y, pendingInstantWithdraws = Y

// 4. Borrower defaults; finalizeDefaultRecovery with epochNumber == E.
//    defaultRecoveryEpoch = E; basis includes X+Y (inflated by stale X).

// 5. Epoch advances (or post-default). userA requests Z >= X.
vm.prank(userA);
cdoEpoch.requestInstantWithdraw(Z);           // aggregate = Y+Z

// 6. userA claims: claimBasis = X+Y paid from recovery reserve — X paid twice.
uint256 balPre = underlying.balanceOf(userA);
vm.prank(userA);
cdoEpoch.claimInstantWithdrawRequest();
// assert underlying.balanceOf(userA) - balPre includes ~X * defaultRecoveryPrice extra,
// and other claimants' recoveryPrice was diluted by X in step 4.
```

Caveat: exact CDO entry points (`requestInstantWithdraw`, epoch advancement after default) depend on `IdleCDOEpochVariant` wrappers not fully inspected here; the core stale-mapping under-clearing and double-payment path in `IdleCreditVault` is verified directly in the source above.

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.

    _burn(_user, amount);

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
