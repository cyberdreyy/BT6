## Analysis

The external report describes an ERC-4626 `maxRedeem` function that can revert when it shouldn't, because a share/asset ratio calculation didn't account for a degenerate state (zero total). The closest analog in this NEAR repository is not a division-by-zero, but a structurally similar "stale accounting vs. current reality" bug in the `multisig` contract: confirmations recorded for a request are never invalidated when the confirming key is later removed from the account, so a request can execute with fewer *actually authorized* confirmations than `num_confirmations` requires.

### Title
Multisig executes requests below the real confirmation threshold because confirmations from deleted keys are never purged - (File: `multisig/src/lib.rs`)

### Summary
`DeleteKey` only removes *requests originated by* the deleted key [1](#0-0) , but it does not scrub that key's public key out of the `confirmations` set of *other* still-pending requests. `confirm()` counts confirmations purely by `HashSet<PublicKey>` length and compares against `self.num_confirmations` [2](#0-1)  without ever re-validating that each recorded public key is still an active access key on the account.

### Finding Description
When a key confirms a request, its `PublicKey` is inserted into `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` for that specific request [3](#0-2) . If that key is later revoked via a `DeleteKey` action, the cleanup logic only removes *requests whose `signer_pk` (the request creator) equals the deleted key*, and clears `num_requests_pk` for that key [4](#0-3) . It does **not** iterate over `self.confirmations` to strip the deleted key's entry from confirmation sets of requests created and confirmed by other keys.

Consequently, a confirmation recorded from a key that is no longer a valid signer on the account remains counted forever. `confirm()`'s threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` [5](#0-4)  treats that stale entry exactly like a live confirmation, so the binding "confirmations counted == live authorized keys that approved" is broken: `count(confirmations) > count(live keys who actually approved)`.

### Impact Explanation
This lets a multisig request execute with fewer real (currently-authorized) approvals than the configured `num_confirmations` threshold — i.e., a request can be executed below threshold, which can move funds (`Transfer`), add attacker-controlled keys (`AddKey`), or deploy/upgrade contract code with less than the intended quorum of live signers. This matches the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
Key rotation/removal is a normal, expected multisig operation (e.g., replacing a compromised or departing signer). Any request that received a confirmation from a key prior to that key's removal, and that has not yet reached quorum, will silently retain that now-invalid confirmation. No special privilege beyond the ordinary multisig key-holder workflow is required to trigger the condition (only ordinary confirm/delete-key operations that the contract already exposes to key holders); an attacker who has since lost/had their key revoked still gets permanent "credit" toward all not-yet-executed requests they had confirmed.

### Recommendation
When executing `DeleteKey`, iterate `self.confirmations` and remove the deleted public key from every request's confirmation set (or re-validate, at `confirm()` execution time, that each recorded public key still corresponds to an access key currently present on the account) before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize multisig with `num_confirmations = 3` and keys A, B, C, D.
2. B calls `add_request` (or A does) creating request `R`; B calls `confirm(R)` → `confirmations[R] = {B}`, count = 1 (< 3).
3. Owner submits and confirms a separate request that performs `DeleteKey { public_key: B }` to rotate out B. This removes B's access key and any requests B itself created, but `confirmations[R]` still contains `B`.
4. C calls `confirm(R)` → `confirmations[R] = {B, C}`, count = 2 (< 3).
5. D calls `confirm(R)` → count becomes 3, `count + 1 >= 3` is satisfied one confirmation early relative to real state, and `execute_request` runs — even though only C and D are currently valid signers who approved (2 live approvals), not 3. [1](#0-0) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
