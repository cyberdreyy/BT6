### Title
Malicious operator can permanently freeze a staker's unlockable/inactive stake by setting a beneficiary that rejects direct coin transfers - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::set_beneficiary_for_operator` lets an operator redirect their commission payout to any address without validating that the address can actually receive `AptosCoin` [2](#0-1) . That beneficiary address is later paid inside `distribute_internal`, which loops over **all** shareholders of the shared `distribution_pool` (both the operator/beneficiary and the staker) using a push-based `aptos_account::deposit_coins` call inside a `while` loop, and aborts the whole transaction on the first failed deposit [3](#0-2) . Since `distribute_internal` is invoked unconditionally at the start of `request_commission`, `unlock_stake`, `switch_operator`, and `update_commision` [4](#0-3) [5](#0-4) [6](#0-5) , a beneficiary that reverts the deposit blocks every one of these entry points — including the staker's own ability to withdraw already-unlocked stake — exactly mirroring the external report's push-based fee-distribution DoS pattern.

### Finding Description
`aptos_account::deposit_coins` reverts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS` when the recipient is an existing account that is not yet registered for the coin type and has explicitly called `set_allow_direct_coin_transfers(false)` [7](#0-6) . `set_beneficiary_for_operator` in `staking_contract.move` performs no equivalent of `assert_account_is_registered_for_apt`, unlike the analogous `vesting::set_beneficiary`, which explicitly enforces this check with the comment "This is a requirement so distribute() wouldn't fail and block all other accounts from receiving APT" [8](#0-7) . That protective check was never mirrored in `staking_contract.move`'s own `set_beneficiary_for_operator`.

`distribute_internal` unconditionally redeems all shares from the shared `distribution_pool` (which mixes the operator/beneficiary's commission shares and the staker's unlocked-stake shares) and pushes coins to each recipient in a loop; any single failed `aptos_account::deposit_coins` call aborts the entire transaction, including the coins destined for legitimate stakers [9](#0-8) . Because `distribute_internal` is a mandatory precondition inside `request_commission`, `unlock_stake`, `switch_operator`, `switch_operator_with_same_commission`, and `update_commision`, none of these can succeed once the beneficiary is unable to receive funds.

### Impact Explanation
A malicious or compromised operator can call `set_beneficiary_for_operator` (a permissionless, self-authorizing call requiring only the operator's own signer) to point their beneficiary at an address that has opted out of direct coin transfers. This permanently strands the staker's already-unlocked (`inactive`/`pending_inactive`) stake in the pool and blocks all future `unlock_stake`, `request_commission`, `switch_operator`, and `update_commision` calls for that staking contract, since they all force a `distribute_internal` that will keep reverting. The staker has no way to recover their withdrawal rights without operator cooperation (only the operator can reset their own beneficiary). This matches the "Permanent lock or non-recoverable loss of claim rights in stake ... vesting flows" impact category, and is comparable in severity to the external report's high-severity classification since it traps genuine third-party (staker) funds, not just the malicious actor's own share.

### Likelihood Explanation
Low-to-medium likelihood: it requires the operator to be malicious or compromised and to deliberately configure an unreceiving beneficiary (an easily reversible, self-inflicted, or targeted griefing action), similar to the "low likelihood, high impact" classification in the original report. It does not require any privileged/governance access — only the operator role, which the staker voluntarily delegated stake management to, and the impact goes beyond the operator's own funds to the staker's stake.

### Recommendation
Mirror the protection already present in `vesting::set_beneficiary`: require `aptos_account::assert_account_is_registered_for_apt(new_beneficiary)` (or equivalently check `can_receive_direct_coin_transfers`) inside `staking_contract::set_beneficiary_for_operator` before allowing the change. Additionally, consider decoupling the operator/beneficiary distribution from the staker's distribution — e.g., using separate `pool_u64` pools per recipient class, or a pull-based `claim` pattern for beneficiary payouts as recommended in the original report — so a single recipient's failed deposit cannot block distributions owed to other, unrelated shareholders.

### Proof of Concept
1. Staker creates a staking contract with `operator` via `create_staking_contract`, `commission_percentage = 10`.
2. `operator` calls `staking_contract::set_beneficiary_for_operator(operator, victim_beneficiary)` where `victim_beneficiary` is an address that already exists and has called `aptos_account::set_allow_direct_coin_transfers(&victim_signer, false)` while never registering `CoinStore<AptosCoin>` (e.g., a fresh account created only via `account::create_account` and never funded/registered for AptosCoin, then opts out of arbitrary transfers).
3. Stake pool accrues rewards; operator becomes owed commission, and/or staker calls `unlock_stake` to unlock part of their principal.
4. Once the stake becomes `inactive`/`pending_inactive`, any subsequent call to `staking_contract::distribute`, `unlock_stake`, `request_commission`, `switch_operator`, or `update_commision` triggers `distribute_internal`, which attempts `aptos_account::deposit_coins(victim_beneficiary, ...)` for the operator's commission share — this call aborts with `EACCOUNT_DOES_NOT_ACCEPT_DIRECT_COIN_TRANSFERS`.
5. Because the abort happens inside the shared distribution loop, the staker's own unlocked-stake payout in the same transaction also fails to be delivered, and the transaction reverts entirely — permanently blocking the staker from withdrawing their already-unlocked funds unless the operator voluntarily resets the beneficiary.

Note: I was unable to fully verify within available context whether every conceivable account-creation path in the current framework guarantees `CoinStore<AptosCoin>` registration (the `is_account_registered` / fungible-asset migration interplay in `coin.move` was not directly inspected), so the exact minimal steps to get a "registered-but-non-accepting" beneficiary account may vary; however, the core control-flow bug — an entirely unchecked, operator-controlled beneficiary address gating a shared, all-or-nothing distribution loop — is confirmed directly in the cited `staking_contract.move` code.
