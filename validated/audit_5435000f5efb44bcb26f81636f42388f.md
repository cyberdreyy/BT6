### Title
Fee-on-transfer / deflationary underlying causes `IdleCreditVault.deposit` to mint unbacked strategy tokens, breaking the 1:1 backing invariant — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external report's bug class — crediting the nominal `amount` argument instead of the actual balance increase after `transferFrom` — exists in the credit-vault surface of this repo. `IdleCDO`/`IdleCDOCreditVault._deposit` and the wrappers all correctly measure `_contractTokenBalance(_token) - _preBal` before minting shares, but the credit vault strategy `IdleCreditVault.deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery` all pull underlying with `safeTransferFrom` and book the nominal `_amount`, never the received delta.

### Finding Description
In `IdleCreditVault.deposit`, the strategy pulls `_amount` underlying from the CDO and mints `_amount` strategy tokens to the CDO unconditionally:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:596-617
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
_mint(msg.sender, _amount);
``` [1](#0-0) 

If the underlying is a fee-on-transfer or deflationary ERC20 (e.g. USDT with its fee toggled on, or any rebasing/fee token accepted as pool currency), the strategy receives `_amount - fee` but mints `_amount` strategy tokens and adds `_amount` to `totEpochDeposits`. The same pattern exists in:

- `collectWithdrawFunds` / `collectInstantWithdrawFunds` — `pendingWithdraws`/`pendingInstantWithdraws` is reduced by the nominal `_amount`, and `lossRecoveryPriceByEpoch` is computed from the nominal funded amount, while less underlying actually arrives. [2](#0-1) 
- `finalizeDefaultRecovery` — `defaultRecoveryReserve` is set to `reserveAmount` including the nominal `_recoveredAmount`, not the received amount. [3](#0-2) 

By contrast, the sibling deposit path `IdleCDOCreditVault._deposit` (and `IdleCDO._deposit`) already implements the correct mitigation — `_mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, ...)` — confirming the intended invariant. [4](#0-3) 

### Impact Explanation
Strategy tokens are the claim unit for `claimWithdrawRequest`, `claimInstantWithdrawRequest`, and default-recovery payouts (`_transferFundedClaim`, `_transferDefaultRecovery`). Minting more strategy tokens than underlying held, or recording funded/reserved amounts larger than received, makes aggregate claims exceed the vault balance. The last claimants' `safeTransfer` reverts — a permanent freeze of unclaimed yield/principal for honest withdrawers — or, in the default path, `defaultRecoveryReserve` overstates actual holdings so `_transferDefaultRecovery` underflows/reverts for later claimants. Loss equals the cumulative transfer fees (up to the full fee-taxed amount on each pull).

### Likelihood Explanation
Requires the vault's underlying to be a fee-on-transfer token. USDT (a supported pool currency for Clearpool-style credit vaults) has a built-in fee mechanism currently set to zero that Tether can enable; any other fee token accepted by the owner triggers it. All deposit/funding flows route through the honest CDO, so no privileged misbehavior is needed — any ordinary deposit, epoch funding, or recovery pull leaks value. Likelihood is low-to-medium (token-dependent), impact is insolvency/frozen claims proportional to the fee.

### Recommendation
In `IdleCreditVault.deposit`, `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery`, measure `balanceOf(address(this))` before and after `safeTransferFrom` and mint/account/reserve the delta (or `require` it equals the nominal amount if fee-on-transfer tokens are unsupported, documented explicitly). Same for `fullfillWriteOffRequest` in `IdleCreditVaultWriteOffEscrow`, which pays out the full nominal `_underlyings`. [5](#0-4) 

### Proof of Concept
Foundry fork PoC sketch:

```solidity
// Mock FoT token: transferFrom credits dst with amount - 1% fee
MockFeeOnTransfer USDT-like token as `token`.

1. User calls idleCDO.depositAA(100e6) during buffer epoch.
   - CDO._deposit measures delta correctly → mints shares for 99e6 received.
   - CDO calls strategy.deposit(99e6): strategy receives 98.01e6 but mints
     99e6 strategy tokens and totEpochDeposits += 99e6.
   assert(IERC20(strategy).balanceOf(cdo) == 99e6);
   assert(underlying.balanceOf(strategy) == 98.01e6); // unbacked ~0.99e6

2. startEpoch; borrower repays at stopEpoch; user requestWithdraw + claim.
   - funded claims total minted basis (99e6) > strategy balance (98.01e6 + repayments);
     the final claimant's `_transferFundedClaim` safeTransfer reverts → funds frozen.
```

Note: severity depends on whether fee-on-transfer underlyings are in scope for deployment; if the protocol intends to exclude them, an explicit `require(received == amount)` check still hardens the invariant.

  /// @dev Only IdleCDO can call this function. When `_amount` is lower than the
  /// pending basis, the difference is a stopEpochWithDuration loss assigned to
  /// pending receipts and users later claim through `lossRecoveryPriceByEpoch`.
  /// Reverts if the resulting recovery price rounds to zero at `RECOVERY_FULL` precision.
  /// @param _amount number of funded tokens to collect
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
