### Title
Loss-adjusted withdraw receipts are skipped and later paid at par when `lastWithdrawRequest` moves past the loss epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug iterates SMB sessions and dereferences one that is being torn down (`ses_status == SES_EXITING`), skipping the teardown check. The analog here is a stale-teardown read: `_claimLossAdjustedWithdrawRequest` locates the loss-adjusted receipt only via `lastWithdrawRequest[_user]` (line 790), so if the user opens a new withdraw request in a later epoch, the loss-epoch receipt is silently skipped by the haircut path and is later paid at par by `_claimFundedWithdrawRequest`, breaking the loss-socialization invariant.

### Finding Description
`requestWithdraw` records both `withdrawsRequests[_user] += _amount` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, and sets `lastWithdrawRequest[_user] = currentEpoch` (lines 282-293). When `stopEpochWithDuration` realizes a loss, `lossRecoveryPriceByEpoch[lossEpoch]` is set and the borrower funds only the haircut amount; per-user entries in `withdrawsRequests`/`withdrawsRequestsByEpoch` remain until `_clearWithdrawClaimForEpoch` clears them (lines 794-800, 815-820).

The claim dispatch in `claimWithdrawRequest` calls `_claimLossAdjustedWithdrawRequest`, which reads `lossEpoch = lastWithdrawRequest[_user]` and applies the haircut only if `lossRecoveryPriceByEpoch[lossEpoch] != 0` (lines 790-792). If the user made a second `requestWithdraw` in a newer, non-loss epoch before claiming, `lastWithdrawRequest` points at the new epoch, the loss-epoch lookup is skipped, and `_claimFundedWithdrawRequest` then pays the entire aggregate `withdrawsRequests[_user]` at par (lines 338-349) — including the receipt basis that was only funded at `lossRecoveryPriceByEpoch[E] < 1e18`. `_clearWithdrawClaimForEpoch` can never clear the stale epoch because it is only reached through the loss/default paths keyed to `lastWithdrawRequest` or `defaultRecoveryEpoch`, and the funded path zeroes the aggregate without honoring the per-epoch haircut.

### Impact Explanation
The attacker (any tranche holder) receives `claimBasis_E * 1e18` instead of `claimBasis_E * lossRecoveryPriceByEpoch[E]` for the loss-epoch receipt. The overpaid delta `(1 - lossRecoveryPrice) * claimBasis_E` is drawn from underlying that belongs to other claimants and active LPs, causing direct theft / insolvency proportional to the realized loss. In a 50% loss epoch this is up to half the attacker's defaulted receipt basis paid twice — once funded at the haircut by `stopEpochWithDuration`, then again at par.

### Likelihood Explanation
Only requires: (1) an epoch where `stopEpochWithDuration` sets `lossRecoveryPriceByEpoch` (honest borrower underperformance — a normal code path, not a default), (2) the attacker holds a pending receipt that epoch, and (3) the attacker calls `requestWithdraw` again in a subsequent running epoch before claiming. All actions are unprivileged; the gate `epochNumber <= lastWithdrawRequest[_user]` (line 326) still passes once the newer epoch ends, and no guard re-checks older per-epoch entries in the funded path.

### Recommendation
In `_claimFundedWithdrawRequest`, iterate or otherwise exclude any request epochs with a non-zero `lossRecoveryPriceByEpoch` before paying `withdrawsRequests[_user]` at par — e.g., track a list of pending request epochs per user, or in `_claimLossAdjustedWithdrawRequest` scan all epochs with a recorded loss price rather than only `lastWithdrawRequest[_user]`. Alternatively, when a user submits a new `requestWithdraw`, force-settle any pending loss-adjusted receipt first, mirroring how `_requestWithdrawApr0` calls `_settleApr0` before updating the bucket.

pragma solidity 0.8.17;
// Foundry fork PoC sketch (test/foundry style harness as in IdleCreditVault.t.sol)

function testLossReceiptSkippedAfterSecondRequest() public {
    // epoch E0: user deposits, epoch starts
    _stopCurrentEpoch();
    uint256 tranches = _depositWithUser(attacker, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // request withdraw -> receipt basis recorded in epoch E1
    _requestWithdrawWithUser(attacker, tranches);
    uint256 lossEpoch = strategy.epochNumber();

    // borrower underperforms: stopEpochWithDuration realizes 50% loss
    _stopCurrentEpochWithLoss(50e16 /* lossBps -> lossRecoveryPriceByEpoch[lossEpoch] = 0.5e18 */);

    // attacker does NOT claim; next epoch runs, attacker requests again
    vm.prank(manager); cdoEpoch.startEpoch();
    _depositWithUser(attacker, 10e6); // fresh principal for second request
    _requestWithdrawWithUser(attacker, tranche.balanceOf(attacker));
    _stopCurrentEpoch(); // lastWithdrawRequest[attacker] now == lossEpoch + 2

    // claim: _claimLossAdjustedWithdrawRequest looks up the NEW epoch only,
    // finds lossRecoveryPriceByEpoch == 0, returns 0.
    // _claimFundedWithdrawRequest then pays withdrawsRequests[attacker] at par,
    // including the 50%-haircutted lossEpoch basis.
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker); // via IdleCDO redeem/claim path
    cdoEpoch.claimWithdrawRequest(attacker);
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    // BUG: paid == full basis, expected == basis*0.5 for the lossEpoch piece
    assertGt(paid, expectedHaircuttedAmount, "loss-adjusted receipt paid at par");
}
