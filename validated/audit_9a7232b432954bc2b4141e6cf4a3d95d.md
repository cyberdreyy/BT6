### Title
Stale-epoch instant-withdraw receipts escape default recovery accounting and drain other users' funded claims - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The analog of CVE-2018-12600's "attacker-controlled index reaches an out-of-bounds write" is an instant-withdraw receipt whose claim basis is keyed to a *stale* epoch index. `requestInstantWithdraw` records basis under `instantWithdrawsRequestsByEpoch[user][epochNumber]`, but `finalizeDefaultRecovery` only folds `instantWithdrawClaimsByEpoch[epochNumber]` (the *current* epoch) into the recovery basis/reserve, and `_claimDefaultedInstantWithdrawRequest` only clears the `defaultRecoveryEpoch` slot. An unfunded instant receipt created in an earlier epoch is therefore outside every reserve/basis index, yet `claimInstantWithdrawRequest` still burns and pays the full aggregate `instantWithdrawsRequests[user]` at par through `_transferFundedClaim`.

### Finding Description
- `requestInstantWithdraw` increments `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]`, plus the aggregate `pendingInstantWithdraws` [1](#0-0) .
- `pendingInstantWithdraws` is only decremented by `collectInstantWithdrawFunds` [2](#0-1) . If `getInstantWithdrawFunds` is never called (manager is honest but simply doesn't fund, or borrower lacks allowance) the receipt survives across `stopEpoch`/epoch bumps unchanged.
- At default finalization, `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` for the *defaulting* epoch [3](#0-2) , and `_defaultPrefundedInstantReserve` derives prefunded cash as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` [4](#0-3) . A stale-epoch instant claim inflates `pendingInstantWithdraws` but contributes nothing to `instantWithdrawClaimsByEpoch[epochNumber]`, so it is excluded from both `totalBasis` and the prefunded reserve — the recovery price and `defaultRecoveryReserve` are computed as if the claim did not exist.
- After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which only zeroes `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` and pays that slice at `defaultRecoveryPrice` [5](#0-4) . The stale receipt remains in `instantWithdrawsRequests[user]`, is burned in full, and is paid **at par** via `_transferFundedClaim` [6](#0-5) .
- `_transferFundedClaim` only refuses to spend `defaultRecoveryReserve`; any strategy balance above the reserve — e.g., already-funded normal withdraw receipts of other users awaiting `claimWithdrawRequest` — is fair game [7](#0-6) .

### Impact Explanation
An unprivileged tranche holder who filed an instant-withdraw request in an old epoch that was never funded can, after `finalizeDefault`, redeem it at par and consume underlyings earmarked for other users' funded withdraw claims, directly causing insolvency for later claimants equal to the stale receipt amount. Equivalently, because the stale basis was never included in `totalBasis`, the reserve is under-provisioned: honest defaulted-epoch claimants' aggregate payout is diluted by exactly the attacker's par payout.

### Likelihood Explanation
Requires (a) an instant-withdraw request left unfunded through an epoch boundary — possible whenever the manager does not call `getInstantWithdrawFunds` and the pool keeps running — and (b) a subsequent hard borrower default with `finalizeDefault`. Both are plausible operational states; the attacker only needs an ordinary deposit and an instant request. Caveat: if the strategy balance minus reserve is insufficient, `_transferFundedClaim` reverts, converting theft into permanent freezing of that claimant and any claims sequenced behind them — still a fund-impact invariant break.

### Recommendation
Track pending instant receipts per epoch consistently: either settle/expire unfunded `pendingInstantWithdraws` at `stopEpoch`, or in `claimInstantWithdrawRequest` route any `instantWithdrawsRequests[user]` portion not yet funded through the `defaultRecoveryPrice` haircut (or revert) rather than paying it at par. `defaultPendingClaimBasis` should sum `instantWithdrawClaimsByEpoch` over all epochs with unfunded receipts, not only `epochNumber`.

### Proof of Concept
Foundry-fork scenario (mirroring `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
// 1. Attacker deposits AA, epoch 0 starts, instant withdraws enabled.
_depositWithUser(attacker, amount, true);
_startEpochAndCheckPrices(0);
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(amount / 2, address(AAtranche)); // or equivalent instant entrypoint
// 2. Manager never calls getInstantWithdrawFunds -> pendingInstantWithdraws stays nonzero.
//    Warp, stopEpoch, startEpoch (epoch 1). Victim deposits and files a normal withdraw.
_depositWithUser(victim, amount, true);
_startEpochAndCheckPrices(1);
vm.prank(victim);
cdoEpoch.requestWithdraw(0, address(AAtranche));
// 3. Epoch 2: borrower fully funds pendingWithdraws (victim receipt now funded, cash in strategy),
//    then borrower defaults in a later epoch.
//    finalizeDefault(recovered, manager): defaultPendingClaimBasis() misses attacker's
//    stale instant basis -> reserve/price computed without it.
cdoEpoch.finalizeDefault(recovered, manager);
// 4. Attacker claims: _claimDefaultedInstantWithdrawRequest clears only
//    instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] == 0,
//    then full instantWithdrawsRequests[attacker] is paid at par via _transferFundedClaim,
//    spending the victim's funded cash above defaultRecoveryReserve.
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// assert: attacker received par payout; victim's subsequent claimWithdrawRequest reverts or is short.
```

Uncertainty: I could not fully verify whether the CDO-layer `allowInstantWithdraw` gating permits `claimInstantWithdrawRequest` after default finalization, and whether any stop-epoch path force-settles stale instant receipts (none was found — `pendingInstantWithdraws` is only reduced by `collectInstantWithdrawFunds`). The PoC should confirm both before relying on the theft outcome; in the worst case the bug manifests as permanent freezing of the stale claimant plus an under-provisioned recovery reserve.

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
