### Title
Claimed instant-withdraw receipts remain in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, corrupting default-finalization basis and reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears only the aggregate `instantWithdrawsRequests[_user]` and burns the receipt, but never clears the per-epoch markers `instantWithdrawsRequestsByEpoch[_user][epoch]` and never decrements `instantWithdrawClaimsByEpoch[epoch]`. These per-epoch markers are exactly what `defaultPendingClaimBasis`, `_defaultPrefundedInstantReserve`, and `_claimDefaultedInstantWithdrawRequest` consume during default finalization. A receipt that was already fully paid therefore remains "in-flight" in the teardown accounting - the same bug class as the Node.js HTTP/2 report, where memory still owned by in-flight CONTINUATION frames is left behind when the session is torn down.

### Finding Description
In `claimInstantWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:380-393) only `instantWithdrawsRequests[_user]` is zeroed; `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws` are untouched (the latter is only reduced in `collectInstantWithdrawFunds`).

When a default is later finalized in the same epoch while `pendingInstantWithdraws != 0`:

- `defaultPendingClaimBasis` (line 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still contains already-claimed amounts → `totalBasis` in `finalizeDefaultRecovery` (line 679-680) is inflated.
- `_defaultPrefundedInstantReserve` (line 716-723) computes `instantBasis - pendingInstant`, treating funds that already left the strategy via the claim as "already-held" reserve → `defaultRecoveryReserve` (line 691) overstates the real token balance.
- When the already-paid user calls `claimInstantWithdrawRequest` post-finalization, `_claimDefaultedInstantWithdrawRequest` (line 844) reads the stale `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, then executes `instantWithdrawsRequests[_user] -= claimBasis` (line 848) on a zeroed slot → underflow revert, permanently bricking claims for that user, and the ghost basis/reserve stays locked in the accounting.

### Impact Explanation
Two concrete loss paths, both satisfying direct fund impact:

1. Recovery mispricing: `recoveryPrice = reserveAmount / totalBasis` is computed with both numerator and denominator inflated by the ghost (already-claimed) amount. Since the ghost claim will never actually be paid (its claim reverts), the inflated `defaultRecoveryReserve` bookkeeping makes later claimants' `_transferDefaultRecovery` payouts exceed the strategy's real balance → insolvency and permanent freezing of the tail claimants' recovery.
2. Permanent freeze: any user who claimed a funded instant receipt before finalization can never execute the defaulted-epoch claim path (`0 - claimBasis` underflow), permanently blocking any other receipts routed through `claimInstantWithdrawRequest` for them.

Quantified: for a pool with I total same-epoch instant claims of which C was already claimed at par and P = pendingInstantWithdraws unfunded, the ghost basis is C and the ghost reserve is also C, so roughly `C` underlying of recovery is earmarked for a claim that can never execute - stuck in the strategy while real claimants are diluted or reverted.

### Likelihood Explanation
Attacker is unprivileged: any EOA can call `requestInstantWithdraw` via the CDO when `allowInstantWithdraw` is enabled, get funded during `startEpoch`/`getInstantWithdrawFunds`, claim at par, and then simply wait for (or, in the programmable-borrower mode, help trigger by legitimately withdrawing liquidity from the borrower's ERC4626 vault so `onStopEpoch`/`transferFrom` fails) a borrower default in the same epoch. No privileged cooperation is required; the only precondition is a same-epoch default with `pendingInstantWithdraws != 0`, which the code explicitly anticipates (the entire prefunded-instant-reserve logic exists for this case). Honest owner/manager calls sequence the transition; the attacker only needs ordinary user actions.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch receipt accounting the same way `_claimDefaultedInstantWithdrawRequest` does: set `instantWithdrawsRequestsByEpoch[_user][epochNumber]` to 0 and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount, so finalization basis and prefunded-reserve math only reflect genuinely unpaid receipts. Alternatively, exclude claimed amounts when computing `instantWithdrawClaimsByEpoch[epochNumber]` in `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`.
