### Title
Withdraw and instant-withdraw receipts are irrevocable by the user — principal is locked until the pool voluntarily funds the claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` and `IdleCreditVault.requestInstantWithdraw` burn the caller's strategy tokens and mint a non-transferable receipt, but the vault exposes **no user-facing cancel/rollback path**. The receipt can only be turned back into underlying when the IdleCDO (via the manager-driven `stopEpoch` / `startEpoch` flow and borrower repayment) calls `collectWithdrawFunds` / `collectInstantWithdrawFunds`. This is the same lock-in class as the reported `removeBoostDelegation` bug: the user's committed position is releasable only by the counterparty, never by the user who created it.

### Finding Description
In `requestWithdraw` (IdleCreditVault.sol:243-295) the CDO's strategy tokens are burned and a receipt (`withdrawsRequestsByEpoch`) plus `lastWithdrawRequest` is recorded for `_user`. In `requestInstantWithdraw` (IdleCreditVault.sol:356-375) the same burn/mint happens and `pendingInstantWithdraws` is incremented. Neither function has a counterpart that lets `_user` undo the request and get the tranche exposure back:

- `claimWithdrawRequest` → `_claimFundedWithdrawRequest` (IdleCreditVault.sol:319-350) reverts `NotAllowed` while `epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]`, i.e. until a manager-called `stopEpoch` bumps `epochNumber` and `collectWithdrawFunds` pulls underlying from the IdleCDO/borrower into the strategy.
- `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) burns the receipt and calls `_transferFundedClaim`; if the strategy's underlying balance has not yet been funded via `collectInstantWithdrawFunds` (callable only by the IdleCDO, :398-403), the transfer reverts and the user stays locked with tranche tokens already burned.
- The escrow/queue periphery shows the intended pattern — `IdleCDOEpochQueue.deleteWithdrawRequest` and `IdleCreditVaultWriteOffEscrow.deleteWriteOffRequest` both let the user revoke — but `IdleCreditVault` itself has no equivalent, so a request made against the vault directly is irreversible.

Compounding the lock-in, `requestWithdraw` reverts `NotAllowed` (:263-271) if the user's `lastWithdrawRequest` epoch has a `lossRecoveryPriceByEpoch` entry with an unclaimed receipt, so a user who cannot or does not want to claim the haircutted amount cannot even open a new request.

### Impact Explanation
- **Temporary freezing with quantified loss**: the full requested principal (arbitrary size, e.g. a lender's entire position) is frozen for the remainder of the epoch — from request time until the next manager `stopEpoch` plus borrower funding. During a buffer period request this can be up to `bufferPeriod + epochDuration`.
- **Lock-in dependency on the counterparty**: identical to the reported bug — the user is entirely dependent on the pool (manager + borrower repayment through `collectWithdrawFunds`/`collectInstantWithdrawFunds`) to release their receipt. If the borrower underfunds at `stopEpoch` (a `stopEpochWithDuration` loss), the user is forced onto the `lossRecoveryPriceByEpoch` haircut path with no opt-out, even though at request time no loss had occurred.
- A user who requested an instant withdraw under `allowInstantWithdraw` but whose request was not funded before the flag flipped (`disableInstantWithdraw` set on the "request all funds" path, IdleCDOEpochVariant.sol:488-493) holds a receipt claimable only through the defaulted/epoch-end flow, again with no self-serve exit.

### Likelihood Explanation
Any KYC-passing lender triggers it trivially: one call to `IdleCDOEpochVariant.requestWithdraw`/`requestInstantWithdraw` commits the position irreversibly. The lock materializes in every epoch where a user wants to back out (APR change, better opportunity, or fear of an impending `stopEpochWithDuration` loss). The freezing duration is bounded by epoch mechanics under honest manager/borrower behavior, so the impact is temporary freezing rather than theft — but the receipt is also forced through whatever loss/recovery terms are set at the next stop, which the user cannot avoid once committed. Note: full claim payout additionally depends on borrower funding, which is guaranteed only by honest-actor assumption; the absence of a cancel is unconditional.

### Recommendation
Add a user-initiated cancel (e.g. `cancelWithdrawRequest` / `cancelInstantWithdrawRequest`) that, while the request epoch is still unfunded (`epochWithdrawPrice`/funding not yet collected and no `lossRecoveryPriceByEpoch` recorded for the user's epoch), burns the user's receipt tokens back into the CDO bucket — i.e. burns the user-minted receipt and re-mints the equivalent strategy tokens to the IdleCDO — decrementing `pendingWithdraws`/`pendingInstantWithdraws` and clearing `withdrawsRequestsByEpoch`/`instantWithdrawsRequestsByEpoch`. This mirrors `IdleCDOEpochQueue.deleteWithdrawRequest` and removes the one-directional dependence on the pool to release the position.

### Proof of Concept
Foundry fork test sketch (mainnet fork, e.g. block ~23032567 as in `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`):

```solidity
function testCannotCancelWithdrawRequest() public {
    // setup: deposit as LP during buffer, epoch started by manager
    uint256 amount = 100_000e6;
    uint256 tranches = _depositWithUser(LP, amount);   // helper exists in test suite

    // LP requests withdraw -> strategy tokens burned, receipt minted
    vm.prank(LP);
    cdoEpoch.requestWithdraw(tranches, address(tranche));

    // LP changes mind: there is NO cancel function on IdleCreditVault.
    // Any attempt to claim reverts while epochEndDate != 0 and
    // epochNumber <= lastWithdrawRequest[LP]:
    vm.prank(LP);
    vm.expectRevert(); // NotAllowed via _claimFundedWithdrawRequest
    cdoEpoch.claimWithdrawRequest();

    // LP's tranche position is gone; principal frozen until manager calls
    // stopEpoch AND borrower funds collectWithdrawFunds. Even a later
    // second requestWithdraw is blocked if a lossRecoveryPrice epoch is pending.
}
```

The PoC demonstrates: after `requestWithdraw`, (a) no function on `IdleCreditVault`/`IdleCDOEpochVariant` lets the user recover the burned tranche position, (b) `claimWithdrawRequest` reverts until privileged epoch-boundary calls occur, and (c) if the next `stopEpochWithDuration` posts a loss, the already-committed receipt is forcibly haircut via `lossRecoveryPriceByEpoch` with no exit — exactly the reported "dependent on the pool to release" lock-in.
