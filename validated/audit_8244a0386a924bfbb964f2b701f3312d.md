### Title
Unfunded instant-withdraw receipts claim at par and drain funds backing other requests - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out the full recorded `instantWithdrawsRequests[_user]` balance at par, regardless of how much underlying has actually been collected for the instant-withdraw bucket. `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws` and there is no per-epoch funding check on the claim path, so an instant receipt is effectively a "length" larger than the allocated backing: early claimants read the full claim amount while the strategy only holds a fraction of it, paying themselves out of funds reserved for funded normal withdraw receipts (`pendingWithdraws` claims) or the `defaultRecoveryReserve`. This mirrors CVE-2023-45896's bug class: a length/claim value larger than the memory/funds actually allocated.

### Finding Description
In `contracts/strategies/idle/IdleCreditVault.sol`:

- `requestInstantWithdraw` mints a 1:1 strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (lines 356-375).
- `collectInstantWithdrawFunds(_amount)` can be called for any `_amount <= pendingInstantWithdraws`; it only pulls `_amount` from the CDO and decrements the global counter (lines 398-403). The code itself acknowledges partial funding: `_defaultPrefundedInstantReserve` documents `pendingInstantWithdraws` as "the still-unfunded remainder" (lines 716-723).
- `claimInstantWithdrawRequest` then does `amount = instantWithdrawsRequests[_user]; _burn(_user, amount); _transferFundedClaim(_user, amount)` (lines 387-392) with no check that this user's receipt was funded. There is no haircut like `lossRecoveryPriceByEpoch` for normal receipts and no solvency gate tying claims to collected instant funds.
- The CDO-side gate `IdleCDOEpochVariant.claimInstantWithdrawRequest` only checks the `allowInstantWithdraw` flag (lines 975-979), which signals claim availability, not that the strategy balance covers all instant receipts.

The strategy's underlying balance is a shared pool backing (a) collected instant funds, (b) funded normal withdraw claims, and (c) `defaultRecoveryReserve`. `_transferFundedClaim` pays from that common balance, so an unfunded instant claim consumes value allocated to other claimants — a broken solvency / "one receipt one funded payout" invariant.

### Impact Explanation
When the instant bucket is only partially funded, the first users to call `claimInstantWithdrawRequest` receive 100% of their receipt, draining underlying reserved for funded `withdrawsRequests` claims (collected via `collectWithdrawFunds`) or other instant claimants. Later claimants' transactions revert on insufficient balance — direct theft and/or permanent freezing of their matured claims, quantified as up to the unfunded remainder (`instantWithdrawClaimsByEpoch[epoch] - collected amount`). The broken invariant is "a claimable receipt is fully backed by collected funds"; here the claimable length exceeds the allocated backing.

### Likelihood Explanation
Partial funding is a designed-for state (prefunded instant reserve logic exists precisely because `pendingInstantWithdraws` can remain non-zero after collection, e.g. when epoch-start cash only partially covered the queue). The attack only needs an unprivileged receipt holder to call `claimInstantWithdrawRequest` while `allowInstantWithdraw` is true and the instant bucket is underfunded — no privileged misbehavior required. The main uncertainty is how easily the honest-manager sequence produces a durable underfunded-but-claimable window outside of default handling; if `allowInstantWithdraw` is always toggled off until fully funded, reachability drops. Some of this surface may overlap previously acknowledged instant-withdraw funding assumptions.

### Recommendation
Track funded instant claims per epoch (analogous to `lossRecoveryPriceByEpoch`/`withdrawsRequestsByEpoch`), e.g. a `instantFundedPriceByEpoch` or a collected-basis counter, and pay `min(instantWithdrawsRequests[_user], fundedShare)` while decrementing a funded bucket on each claim. Alternatively, gate `claimInstantWithdrawRequest` (or `allowInstantWithdraw` in the CDO) so claims are only possible once `pendingInstantWithdraws` for the relevant epoch is zero.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style PoC (fork of existing suite)
function testInstantClaimExceedsFundedBacking() external {
    _stopCurrentEpochWithApr(10e18);          // epoch 1
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address user1 = makeAddr('user1');
    address user2 = makeAddr('user2');
    uint256 tranches1 = _depositWithUser(user1, 100e6);
    uint256 tranches2 = _depositWithUser(user2, 100e6);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Both request instant withdrawals (APR drop triggers instant path)
    _requestWithdrawWithUser(user1, tranches1);
    _requestWithdrawWithUser(user2, tranches2);

    // Epoch stop/start leaves instant bucket partially funded:
    // collectInstantWithdrawFunds pulled only part of pendingInstantWithdraws
    // (e.g. CDO cash covered only user1's share; pendingInstantWithdraws > 0).
    _stopCurrentEpochWithApr(1e18);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    skip(101); // past instantDelay
    assertGt(strategy.pendingInstantWithdraws(), 0); // still unfunded remainder

    // Normal funded claims exist in the same strategy balance (collected via
    // collectWithdrawFunds during stopEpoch), so the vault holds underlying,
    // just not *for* user2's instant receipt.

    // user2 claims full par receipt even though his bucket was never funded,
    // consuming underlying reserved for funded normal withdraw claims.
    vm.prank(user2);
    cdoEpoch.claimInstantWithdrawRequest();

    // user1 (or a matured normal receipt holder) can no longer claim:
    // strategy balance is drained below the funded obligation.
    vm.prank(user1);
    vm.expectRevert(); // insolvent payout
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Note: the exact partial-funding sequence depends on how `startEpoch`/`stopEpoch` collect instant funds in this variant (I could not fully trace `startEpoch`'s instant-funding path within the available context); the PoC assumes the underfunded-remainder state described by `_defaultPrefundedInstantReserve` is reachable with `allowInstantWithdraw` enabled.
