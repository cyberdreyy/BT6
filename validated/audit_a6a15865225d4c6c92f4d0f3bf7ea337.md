### Title
Path traversal in local cache archive path via unsanitized `AlternateKey` when `FF_HASH_CACHE_KEYS` is enabled - ([File: shells/abstract.go])

### Summary
When `FF_HASH_CACHE_KEYS` is enabled, `newCacheConfig` computes the primary cache key via SHA256 hashing (safe), but the `AlternateArchiveFile` is derived from `cacheAlternateKey(humanKey, true)`, which returns the raw, **unsanitized** `humanKey` directly. Because `humanKey` is fully attacker-controlled (from the job's `cache: key:` field, expanded via `ExpandValue`) and is never passed through `cachekey.Sanitize` in this mode, a key containing `../` segments causes `path.Join(build.CacheDir, key, "cache.zip")` to resolve outside the intended cache directory, and this path is later used as a real local file write target by the cache-archiver.

### Finding Description
In `shells/abstract.go`, `newCacheConfig` (lines 133-208) selects the sanitizer based on the `FF_HASH_CACHE_KEYS` flag: [1](#0-0) 

When the flag is on, `sanitizer` becomes a no-op (`return s, nil`), so `humanKey` retains any `../` or `..\` sequences from the raw, user-supplied cache key (`build.GetAllVariables().ExpandValue(userKey)`): [2](#0-1) 

The primary `hashedKey` is `sha256(humanKey)` — always a safe hex string. However, `cacheAlternateKey` returns `humanKey` itself, unmodified, as the alternate key when hashing is enabled: [3](#0-2) 

`getArchivePath` then builds the local archive file path from this unsanitized alternate key: [4](#0-3) 

`path.Join` internally calls `path.Clean`, which resolves `..` segments arithmetically — enough `../` segments walk past `build.CacheDir` and clamp at filesystem root, then continue into attacker-chosen directories (e.g., `path.Join("/cache", "../../../../etc/cron.d/evil", "cache.zip")` → `/etc/cron.d/evil/cache.zip`). If `FF_USE_POWERSHELL_PATH_RESOLVER` is off (default), the result is passed through `filepath.Rel(build.BuildDir, file)`, which re-expresses the same absolute location as a `../../etc/cron.d/evil/cache.zip`-style relative path — it does not block the escape, only re-encodes it.

This `AlternateArchiveFile` is passed as `--alternate-file` to the `cache-archiver` helper command in `addCacheUploadCommand`, which the helper process actually writes a `cache.zip` archive to, both for the primary and alternate paths: [5](#0-4) 

Unlike the S3/GoCloud remote object path, which is explicitly protected against traversal in `cache.GetAdapter` via a `strings.HasPrefix(fullPath, basePath+"/")` check: [6](#0-5) 

there is no equivalent boundary check on the local filesystem path built in `getArchivePath`. The `cachekey.Sanitize` function does perform this exact traversal-resolution defense, but it is deliberately skipped whenever `FF_HASH_CACHE_KEYS` is on: [7](#0-6) 

### Impact Explanation
An unprivileged pipeline author who can set `cache: key:` (and, absent runner-admin pinning of feature flags, also set `FF_HASH_CACHE_KEYS: "true"` as a job variable) can direct the helper process to write a `cache.zip` archive file to an arbitrary path outside the intended `build.CacheDir`/`build.BuildDir` tree. This violates the invariant that "file operations must stay within intended build/cache/artifact roots." Depending on the executor (e.g., shell executor writing directly to host paths, or a container executor where the escape still lands within the container's own filesystem/mounts), this is an arbitrary file write of attacker-controlled archive content to an attacker-chosen path.

### Likelihood Explanation
This is fully reachable by any pipeline author: they need only set a `cache: key:` value containing `../` traversal sequences and (if not already the runner default) set `FF_HASH_CACHE_KEYS: "true"`. No admin privileges or special access are required. The bug is deterministic and repeatable given the same cache key.

### Recommendation
Route `AlternateKey`/`AlternateArchiveFile` through the same traversal-safe treatment used for the remote path (`cache.GetAdapter`'s `HasPrefix` boundary check) or through `cachekey.Sanitize` regardless of `FF_HASH_CACHE_KEYS`, before constructing any local filesystem path in `getArchivePath`. At minimum, validate that the resolved `getArchivePath` result stays within `build.CacheDir` (e.g., via `filepath.Rel` combined with a check that the result doesn't start with `..`) before it is used as a helper command argument.
