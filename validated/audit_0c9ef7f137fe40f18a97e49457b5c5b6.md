### Title
Legacy web_api_trigger handler lacks allowlist/subscriber authorization, allowing any signed request to trigger a free DON-wide broadcast - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`HandleLegacyUserMessage` in the v1 capabilities handler contains an explicit `// TODO: apply allowlist and rate-limiting here` comment and performs no allowlist, subscription, or per-caller authorization check before saving a callback and broadcasting the message to every DON member via `don.SendToNode`. The only gates applied are payload-decodability and message staleness (`MaxAllowedMessageAgeSec`), both trivially satisfiable by any party capable of generating an ECDSA keypair.

### Finding Description
The request path is: HTTP POST → `httpServer.handleRequest` (`core/services/gateway/network/httpserver.go:180-230`) → `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`) → `msg.Validate()` (`core/services/gateway/api/message.go:54-88`) → `handler.HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`).

`msg.Validate()` only checks structural field lengths and that the signature is a well-formed 65-byte ECDSA signature over the message body; `ExtractSigner` (`core/services/gateway/api/message.go:124-134`) merely recovers *whatever* address produced that signature — it does not check that address against any allowlist of registered/paying subscribers. Since generating an ECDSA keypair and signing arbitrary data is free and requires no credential (`crypto.GenerateKey()` as used throughout the test suite, e.g. `core/services/gateway/gateway_test.go:410-428`), "signed" is not equivalent to "authorized."

Inside `HandleLegacyUserMessage`, after payload decoding (`handler.go:343-357`) and the staleness check (`handler.go:372-383`), the code proceeds directly to the method-name check with the TODO comment immediately preceding it: [1](#0-0) 
No call is made to any allowlist, rate limiter (the `nodeRateLimiter` field is only used in `handleWebAPIOutgoingMessage` for DON→gateway traffic, never for user-facing legacy requests), or subscription check. It then stores the callback and fans the request out to every DON member: [2](#0-1) 

### Impact Explanation
Any caller who can sign a well-formed message (trivial, free, anonymous) can force the gateway to broadcast a `web_api_trigger` request to every member of a DON, consuming DON compute/execution resources and callback-table capacity (`savedCallbacks`, bounded by `MaxSavedCallbacks`) at the expense of legitimate, allowlisted or paying subscribers. This matches the "allowlist/quota bypass — unauthorized DON execution / resource consumption" bounty impact class rather than direct fund theft, since no funds move directly from this handler, but it enables free-riding on DON compute and potential denial-of-service against the callback map and node rate limits.

### Likelihood Explanation
No preconditions beyond network access to the gateway's user-facing HTTP endpoint are required. The attacker needs no account, API key, or prior relationship with the DON — only the ability to generate an ECDSA keypair and sign a payload (both trivial, demonstrated throughout the existing test suite, e.g. `newSignedLegacyRequest` in `core/services/gateway/gateway_test.go:410-428`). The bug is fully repeatable and stateless; each request can use a freshly generated key and a unique `MessageId`, so there is no realistic rate-limiting deterrent at this layer for legacy requests.

### Recommendation
Implement the allowlist/subscription check called out in the TODO before processing `MethodWebAPITrigger` requests in `HandleLegacyUserMessage` — verify `msg.Body.Sender` (the recovered signer, populated by `Validate()`) against a configured allowlist of authorized workflow owners/subscribers for the target DON, and apply a per-sender rate limiter (reusing or extending `ratelimit.RateLimiter` similarly to `nodeRateLimiter`) prior to writing to `h.savedCallbacks` and calling `don.SendToNode`.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go` (or a new integration test alongside `core/services/gateway/gateway_test.go`), construct a `handler` via `NewHandler` with a `donConfig` containing several DON members and a mock `handlers.DON`.
2. Generate an arbitrary, never-before-seen ECDSA key (`crypto.GenerateKey()`), sign a legacy `api.Message` with `Method: MethodWebAPITrigger`, a valid current `Timestamp` in the `webapicap.TriggerRequestPayload`, and an arbitrary `MessageId` — do not set any `Authorization` header or associate the key with any known subscriber.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, callback)` directly, or route the raw signed bytes through `httpServer.handleRequest`/`gateway.ProcessRequest` end-to-end.
4. Assert: (a) `don.SendToNode` (mocked) is invoked once per DON member, (b) `h.savedCallbacks[msg.Body.MessageId]` is populated, and (c) no error/rejection occurs due to lack of allowlist membership — proving that message staleness (`MaxAllowedMessageAgeSec`) is the only functional gate, and it is trivially satisfied by using `time.Now().Unix()` as the timestamp.
