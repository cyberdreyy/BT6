### Title
Withdraw-request interest is priced against the shrinking tranche NAV, so later requesters receive inflated interest at the expense of remaining LPs - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` prices each receipt's projected epoch interest as `_amount * totTrancheInterest / _trancheBal`, where `_trancheBal` is the tranche's *current* saved NAV. Every earlier request burns tranche tokens and shrinks that NAV, so the per-unit interest rate quoted to each subsequent requester ratchets upward. The receipt minted in `IdleCreditVault.requestWithdraw` is a hard claim that `stopEpoch` forces the borrower to fund in full via `pendingWithdraws`, meaning the ordering-dependent over-allocation is paid out in real underlyings and socialized onto the LPs who stay in the pool.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw` the interest attached to a withdraw receipt is computed by `_calcInterestWithdrawRequest`: [1](#0-0) 

`totTrancheInterest` is the tranche's projected share of epoch interest, and it is divided by `_trancheBal = _lastSavedNAV(_tranche)`, the live tranche NAV *at the moment of this request*. Immediately afterwards `_withdrawOps` burns the requester's tranche tokens and decreases that NAV: [2](#0-1) 

The analogy to the NICR-ordering bug is exact: the priority/price metric used for each successive withdrawal is recomputed on state mutated by previous withdrawals in the same phase, instead of on a fixed pre-request snapshot. If tranche NAV is `N` and the tranche's fair epoch interest share is `I`, the first requester for amount `a` gets interest `a * I / N`. If half the tranche exits first, the NAV drops to `N/2` and an identical request now earns `a * I / (N/2)` — double the rate for the same principal. As NAV approaches zero the quoted interest diverges toward `totTrancheInterest` per unit requested.

The over-allocated amount is not merely accounting: `creditVault.requestWithdraw` mints the user a receipt for `principal + interest - fees` and adds it to `pendingWithdraws`, and `_stopEpoch` pulls exactly `pendingWithdraws` from the borrower and calls `collectWithdrawFunds`: [3](#0-2) [4](#0-3) 

`interestForOverUnderPerformance` only compensates for the AA/BB split-ratio distortion (`diff`), not for the shrinking denominator; nothing re-normalizes the quoted interest against the original tranche supply. `pendingWithdraws` can therefore exceed the true accrued epoch interest, and the excess is funded by the borrower and realized as an NAV loss for non-exiting LPs at `_updateAccounting`/`_forceUpdateAccounting`.

### Impact Explanation
An attacker can extract underlyings above the fair epoch interest by sequencing requests late in the buffer: the smaller the remaining tranche NAV, the larger the interest multiplier on their receipt. In the extreme (attacker is the last remaining AA holder after others request), their receipt can claim close to the tranche's entire `totTrancheInterest` on a small principal. The excess is paid by the borrower at `stopEpoch` and burned out of active NAV via `_updateAccounting`, i.e. direct theft socialized across remaining LPs. Broken invariant: fair burn/receipt pricing and solvency of `pendingWithdraws` vs. actual accrued interest.

### Likelihood Explanation
Requires no privileged role — any KYC-passed tranche holder can call `requestWithdraw` during the buffer. The attacker's only requirement is that other holders of the same tranche request withdrawals first (predictable at epoch rollover, especially when APR drops and requests cluster). Cost is only gas and holding the tranche position. The gain scales with the fraction of the tranche that exits before the attacker.

### Recommendation
Fix the interest denominator to a snapshot taken at the start of the buffer/epoch (e.g. tranche NAV at `stopEpoch` before any requests), or compute interest per tranche-token using `totalSupply`-at-epoch-start rather than the live `lastNAV` that shrinks as requests burn tokens. Alternatively, accrue a per-share rate once per epoch (`interestPerShare = totTrancheInterest / supplySnapshot`) and multiply by each request's amount.

### Proof of Concept
Foundry fork test sketch (deployed `IdleCDOEpochVariant` + `IdleCreditVault` on mainnet fork):

```solidity
function testRequestWithdrawOrderingInflatesInterest() external {
    // buffer phase: users A (large) and B (attacker) hold AA tranches
    uint256 navPre = cdoEpoch.lastNAVAA();

    // A requests withdrawal of most of the AA tranche
    vm.prank(userA);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(userA), address(aaTranche));

    // NAV used as denominator has now shrunk via _withdrawOps
    uint256 navPost = cdoEpoch.lastNAVAA();
    assertLt(navPost, navPre);

    // B requests the same underlying amount; quoted interest uses smaller NAV
    vm.prank(attackerB);
    uint256 receipt = cdoEpoch.requestWithdraw(amountB, address(aaTranche));

    // receipt interest per unit > fair share computed against navPre
    uint256 fairInterest = amountB * totTrancheInterest / navPre;
    uint256 actualInterest = receipt - amountB + fees;
    assertGt(actualInterest, fairInterest);

    // after startEpoch + stopEpoch, pendingWithdraws funded by borrower exceed true interest;
    // attacker claims inflated amount via claimWithdrawRequest, remaining LPs absorb the loss
}
```

Caveat: the exact magnitude depends on `trancheAPRSplitRatio` updates inside `_withdrawOps` and the `interestForOverUnderPerformance` compensation; the PoC should assert the divergence between `receipt - principal` and the interest computed against the pre-request NAV snapshot.
