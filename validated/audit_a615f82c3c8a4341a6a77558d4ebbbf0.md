### Title
Failed `resumeDependencies` still triggers destructive `Cleanup()` of adopted volumes/network, breaking the "environment stays intact on failure" invariant - (File: executors/docker/docker.go)

### Summary
`resumeDependencies` in `executors/docker/docker.go` calls `networksManager.Adopt` and `volumesManager.Adopt` on a borrowed build container's real network/volume state *before* calling `resumeServices`. If `resumeServices` fails (e.g. because a supplied `service-ids` entry is invalid), `resumeDependencies` returns an error without ever appending anything to `e.temporary`, but the already-populated `volumesManager`/`networksManager` internal state (`temporaryVolumes`, `buildNetwork`/`perBuild`) is not rolled back. Because `Cleanup()` only skips destructive removal when `e.suspended == true` (which is never set on a failed resume), the failure path proceeds to call the volume/network cleanup routines, which actually remove the adopted volumes/network belonging to the borrowed (possibly another project's) suspended environment.

### Finding Description
`resumeDependencies` (`executors/docker/docker.go:1515-1577`) performs, in order:
1. `ContainerInspect` on `fields.buildContainerID` / `fields.helperContainerID` [1](#0-0) 
2. `e.createNetworksManager()` then `e.networksManager.Adopt(e.Context, buildInspect.HostConfig.NetworkMode)` [2](#0-1) 
3. `e.createVolumesManager()` then `e.volumesManager.Adopt(e.Context, buildInspect.Mounts)`, which records every non-`reusable`-labeled mount name into `m.temporaryVolumes` [3](#0-2) 
4. `e.resumeServices(fields.serviceContainerIDs)` [4](#0-3) 
5. Only after all of the above succeed does it append `buildInspect.ID, fields.helperContainerID` to `e.temporary` [5](#0-4) 

`resumeServices` (`executors/docker/services.go:106-138`) has the identical pattern: services are only pushed into `e.temporary` in a loop that runs *after* the main inspect/start loop, so if one `service-ids` entry is invalid or fails to start, any earlier legitimately-started services are left in `e.services` but never reach `e.temporary` [6](#0-5) , confirmed by `TestResumeDependencies_serviceStartFails` which only asserts the returned error, not any cleanup/temporary state [7](#0-6) .

When `resumeDependencies` returns an error, that error propagates through `Prepare()` [8](#0-7)  and through the autoscaler wrapper's `prepareResume` [9](#0-8) , ultimately failing the job. The job-failure path still invokes `Executor.Cleanup()`. In `docker.go`'s `Cleanup()`, the *only* guard against destructive teardown is `e.suspended` [10](#0-9) , which is exclusively set inside `Suspend()`, never on a failed `resumeDependencies`/`Prepare`. Consequently `Cleanup()` proceeds to remove `e.temporary` containers (empty/partial here, so the borrowed containers survive) and then unconditionally calls the volume/network cleanup routines, which use `volumesManager.RemoveTemporary` — deleting every volume recorded via `Adopt()` unless labeled `reusable` [11](#0-10)  — and the equivalent network cleanup on the adopted per-build network.

So the code comment "the environment stays intact on the VM for retry" is only true for the *build/helper/service containers* (because they're gated behind the final `e.temporary` append), but false for *volumes and per-build networks*, whose adoption bookkeeping happens earlier and is never rolled back on failure.

### Impact Explanation
If a job resumes with a real (borrowed) `buildContainerID`/`helperContainerID` pointing to another suspended environment on a shared autoscaler VM, plus a bad `service-ids` value, the resume flow will adopt and then destructively remove the victim environment's non-`reusable` volumes (and potentially its custom per-build network), while leaving the containers themselves untouched. This breaks the invariant that a failed/cancelled resume must not affect another job/project's state: the original owner's environment becomes non-resumable (missing volumes/data, broken network) even though its containers still exist, and the attacking job never gets blamed via `e.temporary` because nothing was tracked for the deleted resources.

### Likelihood Explanation
This requires the `EnvironmentKey`/`SuspendOptions.EnvironmentKey` string (format `.../build-container-id=X&helper-id=Y&service-ids=Z`) to be attacker-influenced, and for the attacker to know or guess a real, currently-suspended `buildContainerID`/`helperContainerID` from another job sharing the same autoscaler VM. I could not confirm within this investigation whether `EnvironmentKey` is fully server-controlled (assigned by GitLab on suspend and opaque to the pipeline author) or whether any part of it can be influenced by job/pipeline input; this is a load-bearing precondition I was unable to verify with available tools. Container IDs on a shared VM are also not inherently secret/guessable-resistant identifiers, but discovering another tenant's live suspended container ID from the runner side is nontrivial without additional information disclosure. Given the identified logic gap is real and reachable from a normal (non-admin) failure path, but the attacker-control precondition on `EnvironmentKey` remains unconfirmed, likelihood is moderate rather than fully proven.

### Recommendation
- Track adopted resources for potential rollback independently of "success only" tracking: record adopted volumes/networks the moment `Adopt()` succeeds, and set a distinct "adoption failed" flag if any subsequent resume step fails.
- On `resumeDependencies` failure, do not run destructive `Cleanup()` logic against resources that were merely *adopted* (borrowed) rather than *created* by this job — differentiate between "adopted-but-not-owned" and "created-and-owned" resources, and never call `RemoveTemporary`/network cleanup for the former unless the resume fully completed.
- Alternatively, treat any `resumeDependencies` failure the same as `e.suspended = true` for `Cleanup()` purposes (i.e., skip volume/network teardown entirely on resume failure), matching the documented intent that "the environment stays intact on the VM for retry."

```go
func TestResumeDependencies_partialAdoptionNotCleanedDestructively(t *testing.T) {
    c := docker.NewMockClient(t)
    e := executorWithMockClient(c)
    require.NoError(t, e.dockerConnector.Connect(t.Context(), common.ExecutorPrepareOptions{}, e))
    e.Config = common.RunnerConfig{}
    e.Config.Docker = &common.DockerConfig{}
    e.Build = &common.Build{Runner: &common.RunnerConfig{}}
    e.Build.Variables = append(e.Build.Variables,
        spec.Variable{Key: featureflags.SuspendableEnvironments, Value: "true"},
    )
    // valid borrowed build/helper container IDs, invalid service id
    e.Build.Job.SuspendOptions.EnvironmentKey =
        "1/system-id/build-container-id=victim-build&helper-id=victim-helper&service-ids=bad-svc"

    buildInspect := container.InspectResponse{
        ID:         "victim-build",
        HostConfig: &container.HostConfig{NetworkMode: container.NetworkMode(network.NetworkDefault)},
        Mounts: []container.MountPoint{
            {Type: mount.TypeVolume, Name: "victim-vol", Source: "/var/lib/docker/volumes/victim-vol/_data", Destination: "/builds"},
        },
    }
    c.On("ContainerInspect", mock.Anything, "victim-build").Return(buildInspect, nil).Once()
    c.On("ContainerInspect", mock.Anything, "victim-helper").Return(container.InspectResponse{ID: "victim-helper"}, nil).Once()
    c.On("VolumeInspect", mock.Anything, "victim-vol").Return(volume.Volume{Name: "victim-vol"}, nil).Once()
    c.On("ContainerInspect", mock.Anything, "bad-svc").Return(container.InspectResponse{}, errdefs.ErrNotFound).Once()

    err := e.resumeDependencies()
    require.Error(t, err)

    // BUG: victim-build/victim-helper are NOT tracked (expected: preserved) - OK
    assert.NotContains(t, e.temporary, "victim-build")
    assert.NotContains(t, e.temporary, "victim-helper")

    // BUG: but volumesManager already adopted victim-vol as temporary,
    // and nothing prevents Cleanup() from removing it since e.suspended == false.
    e.Config.Docker = &common.DockerConfig{}
    c.On("VolumeRemove", mock.Anything, "victim-vol", true).Return(nil).Once() // should NOT be expected/called
    c.On("Close").Return(nil).Maybe()

    e.Cleanup() // asserts VolumeRemove("victim-vol") is called, proving destructive teardown of borrowed volume
}
```
Expected (post-fix) assertion: `VolumeRemove` for `victim-vol` must never be called when `resumeDependencies` fails, since that volume belongs to another (still-suspended) environment that must remain intact for retry.

```go
// RemoveTemporary will remove all the volumes that are marked as temporary. If
// the volume is not found the error is ignored, any other error is returned to

func (m *manager) RemoveTemporary(ctx context.Context) error {
	for _, v := range m.temporaryVolumes {
		err := m.client.VolumeRemove(ctx, v, true)
		if docker.IsErrNotFound(err) {
			m.logger.Debugln(fmt.Sprintf("volume not found: %q", v))
			continue
		}
		if err != nil {
			return err
		}
	}

	return nil
}
```

```go
func (e *executor) resumeServices(serviceIDs []string) error {
	for _, svcID := range serviceIDs {
		svcInspect, err := e.dockerConn.ContainerInspect(e.Context, svcID)
		if err != nil {
			return fmt.Errorf("service container %s not found: %w", svcID, err)
		}
		if err := e.dockerConn.ContainerStart(e.Context, svcInspect.ID, client.ContainerStartOptions{}); err != nil {
			return fmt.Errorf("service container %s failed to start: %w", svcInspect.ID, err)
		}
		ip, ports, err := e.getContainerIPAndExposedPorts(svcInspect.ID)
		if err != nil {
			return fmt.Errorf("getting service container %s IP and ports: %w", svcInspect.ID, err)
		}
		e.services = append(e.services, &serviceInfo{
			ID:    svcInspect.ID,
			Name:  svcInspect.Name,
			IP:    ip,
			Ports: ports,
		})
	}

	if len(serviceIDs) > 0 {
		e.waitForServices()
	}

	// Track for cleanup only after all services started successfully.
	// If any step above fails, Cleanup won't destroy the preserved environment.
	for _, svc := range e.services {
		e.temporary = append(e.temporary, svc.ID)
	}

	return nil
```
