### Title
CORS wildcard-origin bypass via missing subdomain boundary check in `isAllowedOrigin` allows attacker-controlled origin to be reflected in `Access-Control-Allow-Origin` - ([File: core/services/gateway/network/httpserver.go])

### Summary
`(*httpServer).isAllowedOrigin` validates wildcard-configured origins (e.g. `*.remix.com`) using `strings.HasSuffix(originHost, allowedHost)` without requiring a `.` boundary before the suffix. This lets an attacker register any domain whose name string simply ends in the configured suffix (e.g. `evilremix.com` for allowed origin `*.remix.com`), which is not actually a subdomain of the allowed domain, causing `handleRequest` to reflect the attacker's `Origin` header into `Access-Control-Allow-Origin`.

### Finding Description
In `httpServer.isAllowedOrigin`, the wildcard branch strips the `*.` prefix from the configured allowed host and then checks `strings.HasSuffix(originHost, allowedHost)`: [1](#0-0) 

This is a classic "missing dot boundary" suffix-match flaw: `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, even though `evilremix.com` is a completely independent, attacker-registrable domain — not a subdomain of `remix.com`. The correct check should require the origin host equal the allowed host or end with `"."+allowedHost`.

This function is invoked directly in the CORS handling path of `handleRequest`, which unconditionally reflects the raw `Origin` header value back to the client when `isAllowedOrigin` returns true: [2](#0-1) 

The exact-match branch (`originHost == allowedHost`) is safe, but any gateway deployment that configures a wildcard entry in `CORSAllowedOrigins` (a documented, intended feature, not a misconfiguration) is vulnerable to this bypass for hosts that merely share the suffix string.

### Impact Explanation
An attacker who registers a domain ending in the same character sequence as a configured wildcard allowed origin (e.g. `notactuallyremix.com` when `*.remix.com` is allowed) can have their `Origin` reflected in `Access-Control-Allow-Origin`. If a victim's browser is directed (e.g., via a link or embedded script) to issue a request to the gateway HTTP endpoint from the attacker's page, and the browser attaches session/authorization state used by the gateway (e.g. via same-site cookies, browser extension, or any automatically-attached credential mechanism), the attacker's origin can read the JSON response returned by `HTTPRequestHandler.ProcessRequest`, including handler-produced authenticated results. This breaks the intended cross-origin isolation invariant of the CORS allowlist and corresponds to a cross-user response-confusion/data-disclosure class impact.

### Likelihood Explanation
Exploitability requires only that the gateway operator has configured at least one wildcard entry in `CORSAllowedOrigins` (an intended, documented feature of this code) — no operator error is needed to introduce the bug itself, only to enable the vulnerable code path. Registering a suffix-colliding domain name is trivial and cheap for an attacker (any domain name whose end matches the configured suffix string qualifies), and the check is triggered on every request via `handleRequest`, making it repeatable and low-cost.

### Recommendation
Fix the wildcard suffix check to require a proper subdomain boundary, e.g.:
```go
if strings.HasPrefix(allowed, "*.") {
    suffix := allowedHost
    if originHost == suffix || strings.HasSuffix(originHost, "."+suffix) {
        return true
    }
}
```
This ensures only true subdomains of the allowed base domain (`x.remix.com`, `a.b.remix.com`) match, and prevents unrelated domains like `evilremix.com` from passing.

### Proof of Concept
Add a table-driven Go unit test for `isAllowedOrigin` in `core/services/gateway/network/httpserver_test.go`:
1. Construct `httpServer{config: &HTTPServerConfig{CORSAllowedOrigins: []string{"https://*.remix.com"}}}`.
2. Assert `isAllowedOrigin("https://sub.remix.com")` returns `true` (legitimate subdomain).
3. Assert `isAllowedOrigin("https://evilremix.com")` currently returns `true` (bypass) — demonstrating the flaw — and after the fix should return `false`.
4. Assert `isAllowedOrigin("https://attacker.com")` returns `false` in both cases.
5. Optionally add an HTTP integration test invoking `handleRequest` with `Origin: https://evilremix.com` and assert the response header `Access-Control-Allow-Origin` is absent after the fix, whereas before the fix it reflects the attacker origin.
