The node's `reset_rejections` in `stackerdb_listener.rs` is a direct structural analog to `AssetManager.removeToken()`: it clears a rejection tally without checking whether that outstanding "balance" (the rejecting weight backing a live 30% blocking-minority veto) is still zero, letting a miner-triggered resend silently discard genuine, currently-valid signer rejections and letting the same block clear the approval threshold on stale signatures alone.

### Title
Resending a timed-out block proposal wipes valid signer rejections via `reset_rejections`, letting stale approvals alone clear the threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`SignCoordinator::get_block_status` calls `stackerdb_comms.reset_rejections(block_signer_sighash)` whenever it times out waiting on a block's signer responses, in order to retry the proposal. `reset_rejections` unconditionally zeroes `total_weight_rejected` and clears `responded_signers` for that block hash, without checking whether the previously-recorded rejections are still outstanding/valid rejections that should keep blocking the block.

### Finding Description
`reset_rejections` is defined as: [1](#0-0) 

It clears `block.total_weight_rejected = 0` and `block.responded_signers.clear()`, then re-adds only the slots present in `gathered_signatures` (i.e. approvals) back into `responded_signers`. This is invoked from two call sites in `signer_coordinator.rs`, both on a rejection/response timeout: [2](#0-1) [3](#0-2) 

The comment at the definition ("Block approvals cannot be cleared because an old approval could always be used to make a block reach the approval threshold") explicitly acknowledges that stale acceptances remain valid and are deliberately preserved forever. But the same argument applies symmetrically to rejections: once a signer signs a `BlockResponse::Rejected` (a bearer message, exactly like an acceptance signature per the codebase's own stated invariant that "a rejection... is a revocable opinion" only from the *signer's* perspective, not from the coordinator's), that rejection is still a valid, verifiable statement from that signer about that exact block hash. The coordinator throws it away and, on the retried round, will accept the *same* previously-gathered approvals (which are re-seeded into `responded_signers` and whose weight was never reset) to cross `weight_threshold` even though the true, still-valid state of the network may include enough rejection weight to make that impossible.

Concretely: if a set of signers exceeding 30% weight reject a proposal for a substantive reason (e.g. `ReorgNotAllowed`, `RejectedInPriorRound`, or any `BadTransaction`), and the timeout window elapses before the node reads the final rejection that would have crossed the `total_weight_rejected + weight_threshold > total_weight` line 512 check, the node calls `reset_rejections`, which erases all rejection weight. If those same rejecting signers do not immediately resend a message (there is no guaranteed re-broadcast trigger on the signer side purely because of a resend by the coordinator) while a slower path lets more approvals from unrelated signers accumulate against the now-zeroed rejection counter, the coordinator can cross `total_weight_approved >= self.weight_threshold` and treat the block as accepted, even though a blocking minority genuinely rejected it and never retracted that rejection.

This mirrors `AssetManager.removeToken()`: the routine resets a tracked quantity (`total_weight_rejected`, the "balance" backing the safety veto) without first checking whether it is still owed/outstanding — i.e., without checking whether the underlying rejections are still valid, unretracted signer statements that must keep counting toward the 30% blocking minority.

### Impact Explanation
This breaks the aggregated-weight-vs-verified-accepts equality that the coordinator relies on for its `>= weight_threshold` decision: the accepted signature set no longer reflects the true, currently valid opinion of the signer set, because genuine rejection weight was administratively discarded rather than derived from signer state. In the worst case this lets the node accept and broadcast a block that a valid (still-standing) 30%+ blocking minority rejected, i.e. a rejection recounted as an accept, matching the Critical impact class in the rules (a rejection whose weight is silently dropped so the same round can be pushed over the acceptance line).

### Likelihood Explanation
This requires no signer misbehavior or majority collusion — it is triggered purely by ordinary timeout/retry behavior that any single miner (running the coordinator) experiences whenever a `SignatureTimeout` fires while genuine rejections are outstanding, which is a normal operational condition (e.g. network delay, a miner deliberately resending a proposal quickly to shrink the rejection window). No signer key or majority control is needed; it only requires that the miner control when the retry/timeout fires, which a one-slot miner does by controlling proposal timing.

### Recommendation
Do not unconditionally zero `total_weight_rejected` and clear `responded_signers` on retry. Instead, either: (a) keep the rejection tally and treat a retried round as additive rather than resetting the veto counter, only allowing a signer's rejection to be superseded by a fresh, later message from that same signer for the (possibly re-proposed) block hash; or (b) require the coordinator to re-derive rejection status from the latest known per-signer response state rather than blanket-clearing it, so a signer that already rejected the block continues to count against the threshold until it explicitly changes its vote.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
