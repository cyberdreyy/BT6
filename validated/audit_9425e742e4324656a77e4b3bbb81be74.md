### Title
Non-injective `linkage_table` in publish transaction triggers `UNKNOWN_INVARIANT_VIOLATION_ERROR` instead of user-facing error — (`external-crates/move/crates/move-vm-runtime/src/runtime/mod.rs`)

### Summary
A package publisher can supply a `SerializedPackage` whose `linkage_table` maps two distinct `original_id`s to the same `version_id`. `MoveRuntime::validate_package` passes this table directly to `LinkageContext::new`, which detects the collision and returns `UNKNOWN_INVARIANT_VIOLATION_ERROR`. The code's own documented contract states that no user input should produce an invariant violation; this input violates that contract.

### Finding Description
`MoveRuntime::validate_package` (runtime/mod.rs:261) constructs a `LinkageContext` directly from the user-supplied `pkg.linkage_table` before any injectivity check is performed at the deserialization or verification layer. `LinkageContext::new` (linkage_context.rs:37-47) is the first and only place that checks injectivity, and it returns `UNKNOWN_INVARIANT_VIOLATION_ERROR` on failure. Because this check fires on user-controlled data, the resulting error is misclassified as an invariant violation rather than a `VMVerificationOrDeserializationError`.

### Impact Explanation
**Low.** The error is caught by Sui's execution layer, which aborts the transaction; the validator does not crash or panic. No funds are at risk, no state is corrupted, and no bridge assets are affected. The impact is limited to wrong error classification and a validator invariant-violation error reachable from public input, which falls within the Low bounty tier.

### Likelihood Explanation
Any ordinary package publisher can trigger this by crafting a `SerializedPackage` with a non-injective `linkage_table`. No special privileges, leaked keys, or malicious validators are required.

### Recommendation
Add an injectivity check on `pkg.linkage_table` early in `deserialization::translate::package` (or at the `SerializedPackage` deserialization boundary), returning a `VMVerificationOrDeserializationError` (e.g., `StatusCode::INVALID_MAIN_FUNCTION_SIGNATURE` or a dedicated `INVALID_LINKAGE_TABLE` code) rather than delegating the check to `LinkageContext::new` where the only available error code is `UNKNOWN_INVARIANT_VIOLATION_ERROR`.

### Proof of Concept
```
1. Construct a SerializedPackage with:
     linkage_table = { 0xAAAA => 0xCCCC, 0xBBBB => 0xCCCC }
   (two distinct original_ids mapping to the same version_id 0xCCCC)
2. Submit a publish transaction containing this package.
3. MoveRuntime::validate_package calls LinkageContext::new(pkg.linkage_table.clone()).
4. LinkageContext::new detects 0xCCCC appears twice, returns UNKNOWN_INVARIANT_VIOLATION_ERROR.
5. Assert: the returned VMError has status UNKNOWN_INVARIANT_VIOLATION_ERROR,
   not VMVerificationOrDeserializationError — confirming the misclassification.
```
