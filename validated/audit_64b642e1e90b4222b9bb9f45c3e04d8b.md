### Title
Unprivileged vault-side liquidity drain makes `stopEpoch` permanently retryable-revert, freezing pending withdraw requests - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The SSRF class maps here as a trusted-component-reaches-an-attacker-influenced-endpoint bug: `IdleCDOEpochVariant.stopEpoch` unconditionally routes through `ProgrammableBorrower.onStopEpoch`, which performs a live `vault.withdraw(shortfall, ...)` against an external, shared ERC4626 vault. Any unprivileged actor who can drain that vault's withdrawable liquidity (e.g., a collateralized borrower on the Morpho markets backing the vault) forces the `try/catch` to revert with `StopEpochVaultLiquidityUnavailable`, which propagates out of `stopEpoch` and leaves the epoch running and all `pendingWithdraws` unfunded for as long as liquidity stays drained.

### Finding Description
In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:231-253), when the amount IdleCDO will pull exceeds on-hand balance, the shortfall is recalled via `vault.withdraw`. If that external call reverts for any liquidity reason — even though `shortfall <= _currentVaultAssets()` i.e. the shares are economically covered — the hook reverts with `StopEpochVaultLiquidityUnavailable` instead of letting IdleCDO proceed to the default path:

```solidity
if (shortfall > _currentVaultAssets()) return true;
try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
  ...
} catch {
  revert StopEpochVaultLiquidityUnavailable();
}
```

`convertToAssets` coverage is checked, not `maxWithdraw`/real liquidity, so a liquidity-starved-but-solvent vault always takes the revert branch. Because `stopEpoch` reverts atomically, `epochAccountingActive`, `epochPendingWithdraws`, and `strategy.pendingWithdraws()` are all unchanged (confirmed by `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable`), and there is no alternate path — no forced default, no partial stop — to unstick the epoch. The attacker needs no role: they interact only with the shared third-party vault (deposit/borrow to consume its withdrawable liquidity) while an epoch is running with pending withdraw requests queued.

Broken invariant: liveness of the epoch state machine / timely payout of queued withdraw requests. Existing guards don't help: the try/catch only distinguishes "economically uncovered" vs "withdraw reverted", and in the covered-but-illiquid case it chooses a revert that the honest manager can only retry, never resolve.

### Impact Explanation
Temporary freezing of lender funds: all `pendingWithdraws` (lender principal + yield already requested via `requestWithdraw`) remain unfunded, and tranche holders cannot redeem while `isEpochRunning` stays true, for exactly as long as the attacker keeps the vault's withdrawable liquidity below the shortfall. Loss = the full `strategy.pendingWithdraws()` amount plus interest accrual opportunity cost; in the test scenario scale this is ~half of a 10k USDC deposit per request, scaling linearly with TVL.

### Likelihood Explanation
Medium. It requires the attacker to control enough capital to absorb the vault's free liquidity during the stop window (e.g., borrowing all available liquidity across the Morpho markets underlying the vault, which needs collateral ≥ the drained amount). No privileged role, timing beyond "epoch running with pending withdraws", or protocol cooperation is needed; the attack is repeatable each retry. It does not require the vault to be insolvent — shares remain fully covered, which is precisely why the code path reverts instead of defaulting.

### Recommendation
Distinguish liquidity failure from insolvency more carefully and bound the freeze: e.g., attempt `vault.withdraw(vault.maxWithdraw(address(this)), ...)` and treat any residual uncovered shortfall through the existing default/`_isRequestingAllFunds` path rather than reverting, or allow a manager-guarded `stopEpoch` bypass flag that lets IdleCDO proceed to default accounting when the vault is demonstrably illiquid (withdraw reverts while `convertToAssets` covers the shortfall) after a grace period, so an external vault's liquidity state cannot indefinitely hold the epoch state machine hostage.

### Proof of Concept
Reproducible on the existing Foundry fork harness `test/foundry/ProgrammableBorrowerCreditVault.t.sol`. Extend `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` to show the attacker-side primitive with a real vault: use the Steakhouse/Gauntlet USDC Morpho vault setup, deposit AA, call `requestWithdraw` for ~half the position, `startEpoch`, then have an unprivileged EOA drain the vault's withdrawable liquidity (on the real Morpho vault: post collateral and borrow the free liquidity in each underlying market, or on `MockStopEpochLiquidityVault` call `setWithdrawLimit(0)` as a stand-in for a liquidity-drained state). Then `vm.warp(cdoEpoch.epochEndDate() + 1)` and repeat `stopEpoch(0,0)` from the manager: every call reverts `StopEpochVaultLiquidityUnavailable`, `defaulted()` stays false, `isEpochRunning()` stays true, and `pendingWithdraws` remains > 0 indefinitely — demonstrating attacker-controlled freezing of queued withdrawals at zero protocol-level cost beyond the drained-liquidity position.
