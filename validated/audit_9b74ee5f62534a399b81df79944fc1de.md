### Title
Unbounded per-request secondary-index enumeration cost via attacker-created stale index entries bypasses `byte_limit_for_scan` - ([File: accounts-db/src/accounts_db.rs])

### Summary
`AccountsDb::index_scan_accounts` iterates every pubkey returned by `AccountsIndex::get_index_key_pubkeys(&index_key)` and calls `do_load` on each one *before* the byte-size limit check runs. The byte-limit accumulation (`accumulate_and_check_scan_result_size`) is only invoked when the post-load filter (e.g. owner match) returns `true`; if the filter returns `false` the loop never aborts and keeps iterating and loading every remaining pubkey in that index bucket. An attacker can populate a single secondary-index key with an arbitrarily large number of stale entries whose accounts no longer pass the RPC's filter, forcing the enumeration loop to perform unbounded `do_load` work in one RPC call regardless of the configured `scan_results_limit_bytes`.

### Finding Description
`load_by_index_key_with_filter` ( [1](#0-0) ) drives `AccountsDb::index_scan_accounts`, which for a given `IndexKey` first fetches **all** pubkeys mapped to that key via `self.accounts_index.get_index_key_pubkeys(&index_key)` and then loops over them: [2](#0-1) 

`get_index_key_pubkeys` eagerly materializes the *entire* set of pubkeys under that key into a `Vec<Pubkey>` ( [3](#0-2) , backed by `SecondaryIndex::get` which collects the whole inner `HashSet` [4](#0-3) ), so the enumeration cost (and the eager `Vec` allocation) scales directly with how many pubkeys the attacker has caused to be registered under that one index key — with no cap independent of scan results.

The only early-exit in the loop is `config.is_aborted()`, which is only set by `config.abort()` inside the RPC's filter/size-check closure in `load_by_index_key_with_filter`: [5](#0-4) 

Critically, `accumulate_and_check_scan_result_size` — the code that actually enforces `byte_limit_for_scan` — is only called `if use_account` (i.e. only if `filter(account)` returned `true`). If the filter (e.g. `account.owner().eq(&program_id)` in `get_filtered_indexed_accounts`, [6](#0-5) ) returns `false` for every remaining entry, `config.abort()` is never called, so `is_aborted()` never becomes true, and `index_scan_accounts` will `do_load` **every single pubkey** registered under that index key regardless of `byte_limit_for_scan`/`scan_results_limit_bytes`.

The codebase itself documents that secondary index entries become stale (mapped to a pubkey whose current on-chain data no longer matches the original index key) and are *not* cleaned up when an account is rewritten under a different owner while remaining alive — this is explicitly called out as the reason RPC needs a "redundant post-processing filter": [7](#0-6) 

and in the secondary-index update comment: [8](#0-7) 

An attacker who deploys their own program and controls accounts it owns can:
1. Create N small accounts owned by `program_id` (each gets a `ProgramId(program_id)`/`SplTokenMint`/`SplTokenOwner` secondary-index entry).
2. Reassign ownership of each account away from `program_id` (a normal on-chain operation the owning program is permitted to perform), while keeping the accounts alive (non-zero lamports) so they are never treated as "dead keys" and never purged from the secondary index (`handle_dead_keys`/`purge_secondary_indexes_for_dead_keys` only fire on removal from the primary index, not on live ownership changes).
3. Issue a single `getProgramAccounts` (with `ProgramId` secondary index) or `getTokenAccountsByOwner`/`getTokenAccountsByMint` call targeting `program_id`.

Because every one of the N stale pubkeys fails the post-load owner filter, `accumulate_and_check_scan_result_size` is never invoked, `config.abort()` is never called, and the scan performs N full `do_load` calls (and N filter evaluations) in a single request — cost that is proportional to attacker-authored on-chain data cardinality rather than to any configured byte/size limit.

### Impact Explanation
This is a single-request CPU/IO cost-amplification bug scoped to secondary-index-enabled `getProgramAccounts`/`getTokenAccountsByOwner`/`getTokenAccountsByMint` RPC calls, matching the Agave bounty category of "unbounded cost for a single low-rate call." The documented invariant — that request cost is bounded by explicit limits (`scan_results_limit_bytes`/`byte_limit_for_scan`), not by attacker-authored on-chain data — is violated because the limit check is gated behind a filter predicate that the attacker can make permanently false for the stale entries they created.

### Likelihood Explanation
Preconditions are modest and fully within attacker capability: a secondary index (`ProgramId`, `SplTokenMint`, or `SplTokenOwner`) must be enabled by the validator operator (a common RPC configuration, not attacker-controlled, but a normal deployment choice covered by the scoped precondition "secondary index enabled for the key"). Given that, the attacker only needs ordinary transaction submission rights to create accounts and change their ownership — no special privileges, no validator/gossip control, and only a single RPC call is needed to trigger the cost. This is straightforward and repeatable.

### Recommendation
Bound the enumeration itself, not just the accumulated result size: track a hard cap on the number of pubkeys/do_load calls processed by `index_scan_accounts` per scan (independent of whether the filter passes), and/or account for `calc_scan_result_size`-style cost against every candidate pubkey examined (not only those that pass the filter), aborting once a configured enumeration-cost ceiling is reached. Additionally, consider purging/updating secondary index entries when an account's owner (or mint/owner-relevant field) changes while the account remains alive, rather than only on primary-index removal.

### Proof of Concept
```rust
// accounts-db/src/accounts_db/tests/impl.rs (new test)
#[test]
fn test_index_scan_accounts_stale_entries_bypass_byte_limit() {
    let db = Arc::new(AccountsDb {
        account_indexes: program_id_index_enabled(), // enable ProgramId secondary index
        ..AccountsDb::new_for_tests_with_config(Vec::new(), DEFAULT_ACCOUNTS_DB_CONFIG)
    });

    let program_id = Pubkey::new_unique();
    let other_program_id = Pubkey::new_unique();
    const N: usize = 200_000; // large cardinality under one index key

    // 1. Create N accounts owned by `program_id` (each indexed under program_id).
    let pubkeys: Vec<Pubkey> = (0..N).map(|_| Pubkey::new_unique()).collect();
    for pk in &pubkeys {
        let account = AccountSharedData::new(1, 0, &program_id);
        db.store_for_tests((0, &[(pk, &account)][..]));
    }
    db.add_root_and_flush_write_cache(0);

    // 2. Re-store all accounts under `other_program_id` (still alive, non-zero lamports),
    //    leaving stale ProgramId(program_id) secondary-index entries behind.
    for pk in &pubkeys {
        let account = AccountSharedData::new(1, 0, &other_program_id);
        db.store_for_tests((1, &[(pk, &account)][..]));
    }
    db.add_root_and_flush_write_cache(1);

    // Confirm the stale entries still exist under the original key.
    let stale = db.accounts_index.get_index_key_pubkeys(&IndexKey::ProgramId(program_id));
    assert_eq!(stale.len(), N);

    // 3. Single scan with byte_limit_for_scan set very low: filter (owner == program_id)
    // fails for every entry, so accumulate_and_check_scan_result_size never fires and the
    // scan should still enumerate/do_load all N entries -- assert this by timing/counting.
    let load_count = AtomicUsize::new(0);
    let start = std::time::Instant::now();
    let config = ScanConfig::default().recreate_with_abort();
    db.index_scan_accounts(
        &Ancestors::default(),
        1,
        IndexKey::ProgramId(program_id),
        |maybe_account| {
            if let Some((_, account, _)) = maybe_account {
                load_count.fetch_add(1, Ordering::Relaxed);
                assert_ne!(account.owner(), &program_id); // filter would reject all
            }
        },
        &config,
    )
    .unwrap();

    // FAIL: with a byte_limit_for_scan of e.g. 1 account's worth of bytes, we'd expect
    // the enumeration to abort quickly; instead all N stale pubkeys get do_load'd.
    assert_eq!(load_count.load(Ordering::Relaxed), N);
    println!("Enumerated {N} stale entries in {:?}", start.elapsed());
}
```
Expected result on the current code: the assertion `load_count == N` passes and elapsed time scales linearly with `N`, demonstrating that a single RPC-equivalent scan call incurs enumeration cost proportional to attacker-controlled on-chain data cardinality, independent of `byte_limit_for_scan`/`scan_results_limit_bytes`.

        &self,
        bank: &Arc<Bank>,
        index_key: &IndexKey,
        program_id: &Pubkey,
        filters: Vec<RpcFilterType>,
        sort_results: bool,
    ) -> ScanResult<Vec<KeyedAccountSharedData>> {
        let bank = Arc::clone(bank);
        let index_key = index_key.to_owned();
        let program_id = program_id.to_owned();
        let byte_limit_for_scans = self.config.scan_results_limit_bytes;
        let mut accounts = self
            .runtime
            .spawn_blocking(move || {
                bank.get_filtered_indexed_accounts(
                    &index_key,
                    |account| {
                        // The program-id account index checks for Account owner on inclusion.
                        // However, due to the current AccountsDb implementation, an account may
                        // remain in storage as a zero-lamport AccountSharedData::Default() after
                        // being wiped and reinitialized in later updates. We include the redundant
                        // filters here to avoid returning these accounts.
                        account.owner().eq(&program_id)
                            && filters
                                .iter()
                                .all(|filter_type| filter_allows(filter_type, account))
                    },
                    byte_limit_for_scans,
                )
            })
            .await
            .expect("Failed to spawn blocking task")?;
