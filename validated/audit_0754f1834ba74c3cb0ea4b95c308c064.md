### Title
External Initiator authentication is not bound to the specific job/webhook it was registered for, allowing any valid EI credential to trigger runs on any webhook job - ([File: core/web/auth/auth.go])

### Summary
The `AuthenticateExternalInitiator` middleware validates an External Initiator's (EI) access key/secret pair as a *global* credential and, on success, unconditionally grants the request `UserRoleRun` privileges. Nothing in the authentication path ties the verified credential to the specific job/webhook the request is targeting, mirroring the ParaSpace `Credit` structure bug where a valid signature for one context (marketplace order) could be replayed against a different, unintended context (a different order/marketplace). Here, a credential intended only for triggering a specific webhook job (as declared via `externalInitiators` in that job's TOML spec, persisted in the `external_initiator_webhook_specs` join table) is not re-checked against the target job ID at request time.

### Finding Description
`AuthenticateExternalInitiator` looks up the EI purely by `AccessKey`/`Secret` and, if valid, sets the session role to `run` without reference to which job is being invoked: [1](#0-0) 

The authentication check itself (`bridges.AuthenticateExternalInitiator`) only compares hashed secrets — it has no job/webhook parameter at all: [2](#0-1) 

Lookup by `access_key` alone, with no scoping to a job: [3](#0-2) 

The intended design, per the changelog, is that "Only the External Initiators listed in the toml spec may trigger a run for that job," enforced by a dedicated join table (`external_initiator_webhook_specs`) that records which EI is authorized per webhook job: [4](#0-3) 

However, searching the run-creation path (`core/web/pipeline_runs_controller.go`, `core/web/router.go`) for any reference to `ExternalInitiatorName` or the `external_initiator_webhook_specs` join table returns no matches — those identifiers only appear in `core/web/auth/auth.go`, the ORM/migration, and unit tests, not in the controller that actually creates a run for a given `jobID`. This indicates that once an EI is authenticated (as *any* registered EI in the system), it is granted the generic `run` role and is not re-validated against the specific job's authorized-initiator list at the point where `/v2/jobs/:ID/runs` creates the pipeline run — exactly analogous to the missing "MarketplaceAddress" binding in the ParaSpace `Credit` struct.

### Impact Explanation
If confirmed, this would let an attacker who has legitimately obtained credentials for External-Initiator "A" (e.g., a benign, low-privilege integration) use them to trigger job runs for a `webhook` job that only lists External-Initiator "B" in its spec. Because webhook-triggered jobs can execute pipeline tasks (including bridge calls, on-chain transactions, or other side effects configured in `observationSource`), this is an unauthorized job-run/request-impersonation issue: it violates the documented guarantee that "Only the External Initiators listed in the toml spec may trigger a run for that job."

### Likelihood Explanation
Likelihood depends on whether the binding is actually enforced elsewhere in the run-creation controller (e.g., `pipeline_runs_controller.go`) — a file I could not fully inspect due to the tool-call limit reached this session. The absence of any `ExternalInitiatorName`/join-table references in the controller and router search results is suggestive but not conclusive proof of a bypass; it is possible the enforcement is done implicitly via a different code path (e.g., a job-lookup helper) that wasn't captured by these specific search terms.

### Recommendation
Verify, in `core/web/pipeline_runs_controller.go` (job run creation handler), that the authenticated `SessionExternalInitiatorKey` value is cross-checked against the `external_initiator_webhook_specs` (or equivalent) association for the target `jobID` before permitting a run to be created. If this check is missing, add it so that EI identity is validated per-job, not just globally, consistent with the ParaSpace mitigation pattern of tying the credential to the specific target context.

### Proof of Concept
Not able to construct a concrete, verified PoC within this session — I was unable to read `core/web/pipeline_runs_controller.go` before the tool budget was exhausted, so I cannot confirm definitively whether the job-run creation endpoint independently re-validates the EI-to-job binding via the `external_initiator_webhook_specs` table. This is a significant gap: the finding above is based on strong circumstantial evidence (the global nature of `AuthenticateExternalInitiator`, and the absence of job-scoping identifiers in the controller/router search results), but should be confirmed by directly reading `core/web/pipeline_runs_controller.go`'s job-run-creation handler and any helper functions it calls (e.g., checking `job.ExternalInitiatorWebhookSpecs` or similar) to see if it filters/validates against `c.MustGet(auth.SessionExternalInitiatorKey)`.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// AuthenticateExternalInitiator compares an auth against an initiator and
// returns true if the password hashes match
func AuthenticateExternalInitiator(eia *auth.Token, ea *ExternalInitiator) (bool, error) {
	hashedSecret, err := auth.HashedSecret(eia, ea.Salt)
	if err != nil {
		return false, err
	}
	return subtle.ConstantTimeCompare([]byte(hashedSecret), []byte(ea.HashedSecret)) == 1, nil
}

// FindExternalInitiator finds an external initiator given an authentication request
func (o *orm) FindExternalInitiator(ctx context.Context, eia *auth.Token) (*ExternalInitiator, error) {
	exi := &ExternalInitiator{}
	err := o.ds.GetContext(ctx, exi, `SELECT * FROM external_initiators WHERE access_key = $1`, eia.AccessKey)
	return exi, err
}
