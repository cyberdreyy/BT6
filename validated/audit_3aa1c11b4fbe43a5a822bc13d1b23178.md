### Title
Unfunded instant-withdraw receipts are paid at par from commingled strategy funds, stealing underlying reserved for normal withdraw claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` burns the user's full instant receipt (`instantWithdrawsRequests[_user]`) and pays it out 1:1 via `_transferFundedClaim`, without checking that the borrower's funding for instant requests (`pendingInstantWithdraws`, decreased only by `collectInstantWithdrawFunds`) actually covers the claim. Strategy underlying is commingled: borrower funds pulled in by `collectWithdrawFunds` to back normal `pendingWithdraws` receipts sit in the same balance. An unprivileged lender with an unfunded (or partially funded) instant receipt can therefore drain underlying collected for other users' funded receipts — the XXE analog: unauthenticated/under-authorized access to internal resources (funds earmarked for a different claim class).

### Finding Description
- `requestInstantWithdraw` mints a strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` [1](#0-0) .
- `collectInstantWithdrawFunds` only decreases `pendingInstantWithdraws`; it never reduces `instantWithdrawsRequests[_user]`, so the receipt's claimable amount is independent of whether it was funded [2](#0-1) .
- `claimInstantWithdrawRequest` burns the whole receipt and calls `_transferFundedClaim(_user, amount)`, which only protects `defaultRecoveryReserve` — it does not segregate funds collected for `pendingWithdraws` [3](#0-2) [4](#0-3) .
- The code itself acknowledges unfunded instant receipts exist: `defaultPendingClaimBasis` treats `pendingInstantWithdraws` as the unfunded remainder of `instantWithdrawClaimsByEpoch[epochNumber]`, and `_defaultPrefundedInstantReserve` computes the already-funded part [5](#0-4) [6](#0-5) . Yet pre-finalization (and pre-default entirely) the par claim path has no such distinction.

Broken invariant: one receipt one payout — an instant receipt is paid at par regardless of its funding status, spending underlying collected to satisfy other users' normal withdraw receipts.

### Impact Explanation
Direct theft / insolvency. Concrete sequence (running → stopped, fixed-APR with instant mode enabled):

1. APR drops by more than `instantWithdrawAprDelta`; lender A calls `IdleCDOEpochVariant.requestWithdraw`, which routes to `requestInstantWithdraw` and mints A an instant receipt (e.g. 100k underlyings) [7](#0-6) .
2. At the epoch boundary the borrower only partially funds instant requests, so `pendingInstantWithdraws` remains > 0, while `collectWithdrawFunds` pulls borrower underlying into the strategy to back normal `pendingWithdraws` receipts of user B [8](#0-7) .
3. A (or CDO on A's behalf — `_onlyIdleCDO` is satisfied via the CDO's claim wrapper) calls `claimInstantWithdrawRequest`; the full receipt is burned and A receives the full par amount from the commingled balance, consuming funds collected for B.
4. B's later `claimWithdrawRequest` reverts or is underpaid — funded receipts become unpayable; loss equals up to the unfunded instant balance.

The same hole applies in the window between a declared default and `finalizeDefaultRecovery`: `defaultRecoveryFinalized` is false, so the par path still runs and can drain prefunded/reserve-bound underlying before recovery accounting crystallizes.

### Likelihood Explanation
Requires instant mode to be active (`!disableInstantWithdraw && !isProgrammableBorrower`), an APR decrease triggering the instant path, and the instant queue being underfunded relative to claims — a scenario the codebase explicitly models (`pendingInstantWithdraws` unfunded remainder). No privileged collusion needed; any KYC-passing lender holding an instant receipt can trigger it as soon as the strategy holds any claimable underlying.

### Recommendation
Track per-user (or per-epoch) funded instant claim balances: decrement `instantWithdrawsRequests[_user]` proportionally in `collectInstantWithdrawFunds`, or gate `claimInstantWithdrawRequest` so only the funded portion of a user's receipt is payable at par, with the remainder routed through `lossRecoveryPriceByEpoch`/default recovery like normal receipts.

### Proof of Concept

```solidity
function test_unfundedInstantClaimStealsFundedReceipts() public {
    // setup: epoch running, instant withdraw enabled, APR dropped to trigger instant path
    // userA: requestWithdraw -> instant receipt of 100e18 (pendingInstantWithdraws = 100e18)
    // userB: normal requestWithdraw of 200e18 (pendingWithdraws = 200e18)
    vm.prank(borrower);
    underlying.approve(address(cdo), type(uint256).max);
    // stopEpoch: borrower funds B's receipts via collectWithdrawFunds(200e18)
    // instant queue left unfunded (collectInstantWithdrawFunds not called / partial)
    uint256 balBefore = underlying.balanceOf(userA);
    // userA claims instant receipt at par through the CDO wrapper
    cdo.claimInstantWithdrawRequest(); // or per CDO API
    assertEq(underlying.balanceOf(userA) - balBefore, 100e18);
    // userB's funded claim now fails / underpays
    vm.expectRevert();
    cdo.claimWithdrawRequest();
}
```

Caveat: I could not fully verify the CDO-side wrapper gating for `claimInstantWithdrawRequest` within the available search budget; the strategy-level missing segregation/funding check itself is confirmed by the code above.

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```
