### Title
Gateway forwards MethodWebAPITrigger legacy messages from any signer to all DON members with no allowlist enforcement - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` verifies only that the message is well-formed, has a `Timestamp`, and is not stale before forwarding it to every DON member via `don.SendToNode`. Immediately above the method check there is an explicit `// TODO: apply allowlist and rate-limiting here` comment with no corresponding code, meaning the gateway itself performs no allowlist check on the message sender for `MethodWebAPITrigger` requests.

### Finding Description
`HandleLegacyUserMessage` (`core/services/gateway/handlers/capabilities/handler.go:341-421`) processes a legacy user message: it unmarshals the payload into `webapicap.TriggerRequestPayload`, checks `payload.Timestamp != 0`, checks the message isn't stale relative to `h.config.MaxAllowedMessageAgeSec`, and then—right after the `// TODO: apply allowlist and rate-limiting here` comment at line 384—only checks that `msg.Body.Method == MethodWebAPITrigger`. There is no check anywhere in this function that verifies `msg.Body.Sender` (the signer, recovered/validated elsewhere via `msg.Validate()`) is a member of any per-workflow or per-target allowlist. After passing these checks, the request is converted via `common.ValidatedRequestFromMessage` and forwarded to **every** DON member (`for _, member := range h.donConfig.Members { don.SendToNode(...) }`, lines 416-419), and a callback is registered so the requester receives the first node's response.

The upstream validation (`api.Message.Validate()`, invoked in `common.ValidatedMessageFromReq`/`ValidatedMessageFromResp`) only confirms the message is well-formed and that the signature is self-consistent with `msg.Body.Sender` — it establishes *who* signed the message but not *whether that signer is authorized* to trigger any particular workflow. I was not able to fully trace whether the DON connector/router layer (`gateway.go`, `multihandler.go`) enforces any additional check before dispatching into `HandleLegacyUserMessage`, but nothing in this handler file itself performs authorization based on the sender's identity against a target-workflow allowlist. [1](#0-0) [2](#0-1) [3](#0-2) 

Downstream, `core/capabilities/webapi/trigger/trigger.go` does contain allowlist-related logic (6 matches for "allowlist"), suggesting the workflow-side trigger capability may perform its own allowlist check on received trigger events before actually executing a workflow. However, by the time a request reaches that point, the gateway has already: (1) accepted the request from an arbitrary un-allowlisted signer, (2) fanned it out to all DON members' network stacks, and (3) consumed DON node processing/network resources — regardless of whether the trigger capability ultimately rejects it. This matches the described exploit: the gateway layer itself imposes no allowlist/rate-limit check at this call site, only the method-name check remains, exactly as the TODO comment states.

### Impact Explanation
This is unauthorized triggering of DON compute: any holder of a valid signing keypair (no allowlist membership required) can submit `MethodWebAPITrigger` messages with attacker-controlled topics/payload that get broadcast to every member of a DON. Even if `core/capabilities/webapi/trigger/trigger.go` rejects the message afterward based on its own allowlist, the gateway has already dispatched the request to all DON nodes' handlers, consuming node-side network and processing resources for an unauthorized submission — corresponding to a resource-consumption / DoS-adjacent and authorization-bypass class impact rather than a full workflow-execution bypass (which depends on whether `trigger.go`'s allowlist is authoritative and always enforced).

### Likelihood Explanation
Preconditions are minimal: any valid signing keypair capable of producing a syntactically valid, correctly signed, non-stale `api.Message` with `Method = "web_api_trigger"`. No DON/allowlist membership, no special role, and no additional secret is required to reach `don.SendToNode` for every DON member — the only gates in `HandleLegacyUserMessage` are payload decodability, non-zero timestamp, and message freshness. This is fully repeatable and requires no privileged access, consistent with the "unprivileged attacker with signing keypair" threat model.

### Recommendation
Implement the allowlist check described by the TODO before forwarding: verify `msg.Body.Sender` (or the workflow/target identified in `payload`) against the DON's or workflow's configured allowlist, and apply per-sender rate-limiting (the `h.nodeRateLimiter` pattern used in `handleWebAPIOutgoingMessage` is a reusable model) before entering the `don.SendToNode` loop in `HandleLegacyUserMessage`. Reject and respond with an authorization error for non-allowlisted senders instead of relying solely on downstream enforcement in `trigger.go`.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, construct a `handler` with a `donConfig` and a mock `handlers.DON`.
2. Build an `api.Message` with `Body.Method = MethodWebAPITrigger`, a valid non-stale `Timestamp`, a well-formed `webapicap.TriggerRequestPayload`, and sign it with an arbitrary keypair that is deliberately NOT present in any allowlist configuration for the target workflow.
3. Call `handler.HandleLegacyUserMessage(ctx, msg, mockCallback)`.
4. Assert that `mockDON.SendToNode` is invoked once per member in `donConfig.Members` (i.e., the request is forwarded to all DON nodes) and that no error/rejection response was sent via the callback for authorization reasons — demonstrating the gateway performed no allowlist check before forwarding.
5. Contrast with expected behavior: add an assertion that after fixing (adding the allowlist check), the same non-allowlisted signer's message results in `callback.SendResponse` being called with an authorization/allowlist error and `mockDON.SendToNode` never being invoked.

// ValidatedMessageFromReq validated and extracts a legacy Gateway Message
// from params field of JSON-RPC request
func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageId = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil
}
