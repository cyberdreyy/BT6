### Title
`Archive` writes OS/consumer-ambiguous tar member names (literal backslash treated as separator only by the extracting OS) that collide at restore time - ([File: commands/helpers/archive/tarzstd/tarzstd_archiver.go])

### Summary
`archiver.Archive` in `commands/helpers/archive/tarzstd/tarzstd_archiver.go` writes tar header names taken verbatim from `filepath.Rel(a.dir, path)` without canonicalizing path separators or rejecting separator/case-ambiguous filenames. Because Linux/macOS permit a literal backslash character inside a single filename while `filepath.Join`/`filepath.Rel` on Windows treat `\` as a directory separator, a workspace file whose name is `a\b` (one file) and a legitimately nested `a/b` (directory `a` + file `b`) are archived as two distinct, valid tar headers, but resolve to the identical filesystem path when the archive is later extracted on a different-OS consumer via `tarzstd_extractor.go`'s `Extract`.

### Finding Description
`Archive` computes `rel, err := filepath.Rel(a.dir, path)` and assigns it directly to `hdr.Name` [1](#0-0) . `filepath.Rel`/`filepath.Abs` use the OS-native separator (`filepath.Separator`), so on POSIX runners the resulting `hdr.Name` uses `/`, but a file whose *own name* legitimately contains a literal `\` character (perfectly valid on Linux/macOS, and trivially attacker-controlled via a git-committed file or an `artifacts:paths`/`cache:paths` selection in `.gitlab-ci.yml`) is written into the tar stream with that backslash preserved as a literal character in the header string, not escaped or rejected.

No sanitization step in `Archive` (or its caller `fileArchiver.add`/`process` in `commands/helpers/file_archiver.go`, which itself only normalizes to slashes for its own map keys) rejects filenames containing `\`, and the chroot check at lines 72-74 only validates the source `path` is inside `a.dir` — it does nothing to canonicalize the outgoing member name against how a different OS will interpret it.

On the restore side, `tarzstd_extractor.go`'s `Extract` computes `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name))` [2](#0-1) . If extraction happens on Windows, `filepath.Join` treats `\` as a path separator, so a header name that was a single literal filename `a\b` on the packaging (Linux) side is silently reinterpreted as directory `a`, file `b` — the exact same final path as a genuinely nested `a/b` entry packaged from a real subdirectory. Two source items that were distinct and individually passed all packaging checks (chroot containment, exclude-pattern matching, symlink/hardlink handling) therefore land on the same filesystem path only at restore time, letting the later-processed tar entry silently overwrite the other.

Because GitLab Runner's cache/artifact archives are portable blobs that can be produced by one shell/machine executor and consumed by another (including Windows shell/PowerShell executors), this is a genuinely reachable cross-job/cross-runner path, not merely a same-machine round trip where the filesystem itself would already prevent the ambiguity.

### Impact Explanation
An unprivileged pipeline author who controls workspace contents (a committed file literally named with a backslash) and the `artifacts:paths`/`cache:paths` selection can produce an archive whose member list is fully valid and passes every current containment/exclude check, yet is guaranteed to overwrite a differently-named, legitimate member the moment the archive is restored on a Windows-based consumer. This lets an attacker plant content that clobbers a trusted file (e.g., a dependency file, build script, or output artifact a later job trusts) purely through the packaging/restore separator mismatch — no image, auth, or sandbox bypass is needed, only differing canonicalization rules between packaging and restore.

### Likelihood Explanation
Requires only: (1) a workspace file with a backslash in its name (trivial to create/commit on Linux), (2) that file and a colliding nested path both matched by the job's artifact/cache path patterns, and (3) restore happening on/through a Windows-based extractor consumer of the same tar/zstd archive format. Given GitLab Runner supports mixed-OS runner fleets sharing the same distributed cache, this is a realistic and repeatable condition, not a purely theoretical one.

### Recommendation
In `Archive`, always emit tar member names using forward slashes (`filepath.ToSlash(rel)`) and reject or escape any filename component containing the alternate separator character (`\` on POSIX, or explicitly detect and refuse names containing `/` where inappropriate on Windows) before calling `tw.WriteHeader`. Symmetrically, `Extract` should split incoming tar names strictly on `/` (per the tar spec) via `path.Clean`/manual splitting rather than `filepath.Join`, so a literal `\` in a stored member name is never reinterpreted as a directory separator regardless of the extracting OS.

### Proof of Concept
Go unit test in `commands/helpers/archive/tarzstd` package:
```go
func TestArchive_SeparatorAliasProducesAmbiguousNames(t *testing.T) {
    dir := t.TempDir()
    require.NoError(t, os.MkdirAll(filepath.Join(dir, "a"), 0755))
    require.NoError(t, os.WriteFile(filepath.Join(dir, "a", "b"), []byte("legit"), 0644))
    // valid on Linux: literal backslash in a single filename
    require.NoError(t, os.WriteFile(filepath.Join(dir, `a\b`), []byte("attacker"), 0644))

    files := map[string]os.FileInfo{}
    for _, p := range []string{filepath.Join(dir, "a"), filepath.Join(dir, "a", "b"), filepath.Join(dir, `a\b`)} {
        fi, err := os.Lstat(p)
        require.NoError(t, err)
        files[p] = fi
    }

    var buf bytes.Buffer
    arc, err := NewArchiver(&buf, dir, archive.FastestCompression)
    require.NoError(t, err)
    require.NoError(t, arc.Archive(context.Background(), files))

    // Read back tar headers and assert both "a/b" and `a\b` are present as distinct entries
    names := readTarNames(t, buf.Bytes())
    require.Contains(t, names, "a/b")
    require.Contains(t, names, `a\b`)

    // Simulate a Windows-style filepath.Join canonicalization of each name against a root:
    // both entries resolve to the same path, proving the collision that Archive fails to prevent.
    windowsJoin := func(root, name string) string {
        return filepath.Join(root, strings.ReplaceAll(name, `\`, "/"))
    }
    require.Equal(t, windowsJoin("C:\\dest", "a/b"), windowsJoin("C:\\dest", `a\b`))
}
```
Expected assertions: both `a/b` and `a\b` appear as distinct tar header names written by `Archive` (proving no canonicalization/rejection occurs at packaging time), and a Windows-style join of the two distinct names yields an identical destination path (proving the downstream collision described in the finding).
