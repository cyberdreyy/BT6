### Title
Unauthenticated-role-checked pprof debug routes leak internal process data to any authenticated view/run-role user - (core/web/router.go)

### Summary
`metricRoutes(authv2)` mounts the full `net/http/pprof` handler set (`/v2/debug/pprof/*`) onto the `authv2` route group without wrapping any handler in `auth.RequiresEditRole` or `auth.RequiresAdminRole`. Since `authv2` itself only requires successful authentication (session or API token) via `auth.Authenticate`, any authenticated user regardless of role — including the lowest-privilege `UserRoleView` and `UserRoleRun` — can reach pprof endpoints such as `/heap`, `/goroutine`, `/cmdline`, and `/trace`.

### Finding Description
`v2Routes` creates `authv2` guarded only by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` [1](#0-0) , which sets the authenticated user in context but performs no role check — any successfully authenticated user (view, run, edit, or admin role) passes through. Every other sensitive route on this group is explicitly wrapped with `auth.RequiresEditRole` or `auth.RequiresAdminRole` (e.g. keys, jobs, bridges) [2](#0-1) , but `metricRoutes(authv2)` at line 446 registers `pprof.Index`, `pprof.Cmdline`, `pprof.Profile`, `pprof.Symbol`, `pprof.Trace`, and the `allocs`/`block`/`goroutine`/`heap`/`mutex`/`threadcreate` handlers directly, with no role wrapper at all [3](#0-2) [4](#0-3) .

The role hierarchy in `core/web/auth/auth.go` confirms `RequiresRunRole` only blocks `UserRoleView`, and `RequiresEditRole` blocks `UserRoleView`/`UserRoleRun`, and `RequiresAdminRole` requires exactly `UserRoleAdmin` [5](#0-4) . Because `metricRoutes` handlers apply none of these wrappers, a user holding the lowest `view` role (created via `RequiresAdminRole`-gated `/users` endpoint with role "view") can call `GET /v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine`, `/v2/debug/pprof/cmdline`, etc., and receive full memory/goroutine dumps and command-line arguments (which can include secrets passed via flags/environment reflected in `/cmdline`), along with CPU/heap profiling data.

### Impact Explanation
This matches Chainlink's "sensitive data disclosure via authenticated but under-privileged access" impact class: heap and goroutine dumps can contain in-memory secrets (private keys, API tokens, DB connection strings) held by the node process, and `/debug/pprof/cmdline` can reveal process invocation arguments. This is an authorization-exactness violation — a `view`-role account, which per design should only have read access to non-sensitive resources, gains access to internal runtime introspection endpoints intended for operators/admins.

### Likelihood Explanation
Exploitability requires only a valid `view` or `run` role user/API token — the lowest privilege tier a Chainlink node administrator can grant. No additional exploitation steps, race conditions, or timing are needed; a single authenticated `GET` request to any `metricRoutes` path succeeds. This is trivially repeatable and requires no special network position.

### Recommendation
Wrap each handler registered in `metricRoutes` with `auth.RequiresAdminRole` (consistent with other sensitive operational endpoints like `/log` PATCH and key export/import routes), e.g.:
```go
pprofGroup.GET("/", auth.RequiresAdminRole(ginHandlerFromHTTP(pprof.Index)))
```
for all pprof sub-routes, or apply an admin-role-requiring middleware at the `pprofGroup` level via `r.Group("/debug/pprof", auth.RequiresAdminRoleMiddleware)` if such a group-level wrapper exists/is added.

### Proof of Concept
Go handler-level integration test plan:
1. Set up the router via `NewRouter` with a test `chainlink.Application` and seed three users: `admin`, `edit`, `view` (and one `run`-role API token).
2. For each of the `metricRoutes` paths (`/v2/debug/pprof/`, `/cmdline`, `/profile`, `/symbol` (GET/POST), `/trace`, `/allocs`, `/block`, `/goroutine`, `/heap`, `/mutex`, `/threadcreate`), issue authenticated requests using `view`-role and `run`-role session cookies / API tokens.
3. Assert current (vulnerable) behavior: response status is `200` (or handler-specific success, e.g., pprof stream) rather than `401`/`403`, demonstrating the missing role check.
4. After applying the fix (wrapping handlers with `auth.RequiresAdminRole`), re-run the same requests and assert `403 Forbidden` for `view`/`run`/`edit` roles and `200` only for `admin` role.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
