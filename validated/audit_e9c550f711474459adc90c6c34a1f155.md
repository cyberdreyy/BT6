### Title
Unguarded U256-to-u128 truncation in shadow-sequencer funding deposit mint amount - (File: crates/consensus/service/src/actors/sequencer/shadow_funding.rs)

### Summary
`ShadowFunding::transaction` builds a synthetic `TxDeposit` and sets its `mint` field via `self.amount.to::<u128>()`, where `self.amount` is a `U256` with no prior bound check against `u128::MAX`. If `amount` exceeds `u128::MAX`, `alloy_primitives::U256::to::<u128>()` silently truncates rather than saturating or erroring, so the minted amount injected into the L2 state via the deposit transaction would not match the configured `amount`.

### Finding Description
`ShadowFunding` is a struct holding a `U256` `amount` field with no validated upper bound [1](#0-0) . Its `transaction` method constructs a `TxDeposit` whose `mint` field (a `u128`) is populated by `self.amount.to::<u128>()`, a narrowing conversion that truncates high bits rather than rejecting or saturating out-of-range values [2](#0-1) . This is analogous to the reported Solidity pattern of unsafe `uint256`→`uint128` downcasting: the accounting value fed into a critical mutation (here, the amount of ETH minted on L2 via a deposit) can be silently truncated, causing the actually-credited balance to diverge from the intended configured amount. Compare this to the disciplined pattern used elsewhere in this codebase for supply-affecting balance mutations, e.g. `settle_fees`/`prepay` in `crates/common/evm/src/eip8130.rs`, which use `checked_add`/`checked_mul` and explicit overflow errors instead of raw truncating casts [3](#0-2) , and the guarded narrowing conversion in `AssetV2::update_ui_multiplier`, which explicitly bounds `new_multiplier <= MAX_UI_MULTIPLIER` (`u128::MAX`) before calling `.to::<u128>()` [4](#0-3) . `ShadowFunding` has no equivalent bound check on `amount`.

### Impact Explanation
If `ShadowFunding::amount` is ever configured or computed as a `U256` value exceeding `u128::MAX` (e.g., a misconfiguration, an intermediate computation error, or any code path that derives this amount from external/attacker-influenceable arithmetic), the deposit's `mint` amount silently wraps to `amount % 2^128` instead of failing loudly. This can result in the L2 crediting a wildly different (and generally much smaller) ETH amount than intended — a form of unbacked/incorrect L2 balance creation or loss relative to the intended synthetic funding, undermining deposit accounting integrity for shadow-sequencer funding.

### Likelihood Explanation
This code path is reachable only through the shadow-sequencer's own funding configuration; the underlying `amount` field is set via `ShadowFunding::new` and is not shown here to be derived from unprivileged/user-controlled transaction input in the traversed code. I was not able to fully trace all callers/config sources for `ShadowFunding::new` within the available index to determine whether the `amount` can be influenced by an external, unprivileged actor or is strictly an operator-configured constant; this materially affects the actual likelihood/severity of the finding.

### Recommendation
Replace the unchecked `self.amount.to::<u128>()` with a checked conversion (e.g., `u128::try_from(self.amount)` or `U256::MAX`-style bound check) that returns an error or asserts before constructing the deposit transaction, mirroring the guarded pattern used in `AssetV2::update_ui_multiplier` and the `checked_add`/`checked_mul` discipline used throughout `crates/common/evm/src/eip8130.rs`.

### Proof of Concept
Not independently verifiable from the indexed code alone: the `amount` field's provenance (whether it can reach a value exceeding `u128::MAX`) could not be fully confirmed. Conceptually: construct a `ShadowFunding { amount: U256::from(u128::MAX) + U256::from(1) }` and call `.transaction(...)` — the resulting `TxDeposit.mint` will be `0` (wrapped), rather than the intended larger amount, and this transaction is otherwise accepted and injected into the block without any rejection or error, as confirmed by inspection of `crates/consensus/service/src/actors/sequencer/shadow_funding.rs:33-43`.
