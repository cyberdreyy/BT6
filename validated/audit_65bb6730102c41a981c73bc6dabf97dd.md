### Title
Asymmetric per-slot bookkeeping lets a single signer's weight be double-counted across both `total_weight_approved` and `total_weight_rejected` - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` tallies signer weight for a proposed block using two different "already counted" guards for the two `BlockResponse` variants: `gathered_signatures` (a map) for `Accepted` and `responded_signers` (a set) for `Rejected`. Because these are two distinct collections instead of one shared per-slot gate, a signer who first rejects and later accepts the same block has their weight added to `total_weight_rejected` *and* (independently) to `total_weight_approved`, breaking the invariant that the two aggregate tallies represent disjoint partitions of signer weight.

### Finding Description
In `handle`/message-processing loop of `StackerDBListener` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`), the `Accepted` branch gates weight addition on `gathered_signatures`: [1](#0-0) 

while the `Rejected` branch gates weight addition on the separate `responded_signers` set: [2](#0-1) 

and (per the earlier-observed reject-processing code) increments `total_weight_rejected` guarded only by `block.responded_signers.insert(slot_id)`.

The `Accepted` branch *also* unconditionally inserts into `responded_signers` after adding weight (`block.responded_signers.insert(slot_id);`), but the `Rejected` branch never touches `gathered_signatures`. This creates an asymmetry:

- Accept → Reject (same slot_id): the reject path's `responded_signers.insert(slot_id)` returns `false` (already inserted by the accept path), so weight is *not* added to `total_weight_rejected`. No double count.
- Reject → Accept (same slot_id): the reject path only touches `responded_signers`, not `gathered_signatures`. When the later `Accepted` message arrives, `gathered_signatures.contains_key(&slot_id)` is still `false`, so the accept path's guard passes and the signer's weight is added to `total_weight_approved` — even though that same slot's weight was *already* counted in `total_weight_rejected` from the earlier rejection.

The result is that `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, i.e. a single legitimately-signed slot's weight is counted on both sides of the state machine's threshold bookkeeping. This is exactly the "aggregated-weight vs verified-accepts" equality the review rules flag: the coordinator's weight tallies (used to decide `notify_all` for both the acceptance path, line ~467, and the rejection path, line ~567) no longer correspond 1:1 to distinct, non-overlapping verified per-signer votes.

### Impact Explanation
This does not forge signatures — the cryptographic 70% threshold check on the final `NakamotoBlockHeader` (`verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs`) is independent and still requires real per-slot signatures. The impact is confined to the node-side coordinator's *internal* liveness bookkeeping in `StackerDBListener`: because a signer's weight can land in both totals, the rejection-threshold condition (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) can fire concurrently with, or independently of, the real approval state, causing the waiting coordinator thread to be woken/decide based on an accounting state that no longer reflects a true partition of signer weight. Depending on how the consumer of `self.blocks` interprets simultaneous/overlapping signals (code not fully traced in this pass), this can wedge or mis-drive the block-await logic — e.g., prematurely declaring a block dead (rejected) while distinct signers are still actively signing it, stalling tenure progress until timeout/retry.

### Likelihood Explanation
Trivial to trigger: any single signer (or a signer replaying/gossiping a state change) can send a `Rejected` `BlockResponse` for a block and later send a legitimately-signed `Accepted` `BlockResponse` for the same `signer_signature_hash`. No majority, no other signer's key, and no StackerDB-sync trickery is required — only the ordinary gossip path already handled by `handle` in `stackerdb_listener.rs`.

### Recommendation
Use a single, shared per-slot "already counted" gate for both branches (e.g., check-and-insert into `responded_signers` before adding weight in the `Accepted` branch as well, rather than gating on `gathered_signatures`), or track accepted/rejected exclusively via one `HashMap<u32, Vote>` so a slot's weight is attributed to exactly one bucket at a time and re-votes update rather than duplicate the tally.

### Proof of Concept
1. Node runs `StackerDBListener` awaiting responses for block `B` from `N` signers, with `weight_threshold` computed against `total_weight`.
2. Signer `S` (slot `k`) first broadcasts `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `B`. `responded_signers.insert(k)` succeeds → `total_weight_rejected += weight_k`.
3. The same signer `S` later broadcasts a legitimately-signed `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for `B` (e.g., after reconsidering, or a malicious signer deliberately sequencing both to manipulate the tallies).
4. Because `gathered_signatures` was never touched in step 2, the accept-path guard `!block.gathered_signatures.contains_key(&k)` is true, so `total_weight_approved += weight_k` as well.
5. Now `total_weight_approved + total_weight_rejected > total_weight`, with `weight_k` counted on both sides — confirmable by instrumenting/logging the two counters, which are already emitted in the existing `info!`/`warn!` logs at those call sites.
