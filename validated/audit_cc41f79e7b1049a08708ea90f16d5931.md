### Title
`refresh_signer_config` silently overwrites a still-active, unprocessed-block-holding `ConfiguredSigner` before `cleanup_stale_signers` can protect it, discarding retiring-cycle proposal state on a slot collision - ([File: stacks-signer/src/runloop.rs])

### Summary
`RunLoop::refresh_signer_config` unconditionally calls `self.stacks_signers.insert(reward_index, ...)` keyed by `reward_cycle % 2`, with no check of the occupant's pending-validation state. In `refresh_runloop`, this insert for the *next* reward cycle happens before `cleanup_stale_signers` runs in the same pass, so a still-live cycle-N `ConfiguredSigner` (kept alive specifically because it has an unresolved/`Unprocessed` block) is unconditionally dropped and replaced by the cycle-(N+2) signer that shares its `% 2` slot, instead of being retired only once `has_unprocessed_blocks()` is false.

### Finding Description
The equality that should hold is: a `ConfiguredSigner` is only removed from `stacks_signers` once its DB state shows no `Unprocessed` blocks (`cleanup_stale_signers`, [1](#0-0) ), i.e. removal is gated on `signer.has_unprocessed_blocks()` for `ConfiguredSigner::RegisteredSigner` [2](#0-1) , which itself queries the SignerDB for any row still in `BlockState::Unprocessed` [3](#0-2) .

`refresh_signer_config`, however, has no such gate:
```
fn refresh_signer_config(&mut self, reward_cycle: u64) {
    let reward_index = reward_cycle % 2;
    ...
    self.stacks_signers.insert(reward_index, new_signer_config);
}
``` [4](#0-3) 

`refresh_runloop` calls `refresh_signer_config(next_reward_cycle)` for the colliding-parity next cycle *before* calling `cleanup_stale_signers(current_reward_cycle)` in the same invocation:
```
if is_in_next_prepare_phase
    && !Self::is_configured_for_cycle(&self.stacks_signers, next_reward_cycle)
{
    self.refresh_signer_config(next_reward_cycle);
}

self.cleanup_stale_signers(current_reward_cycle);
``` [5](#0-4) 

Because `stacks_signers` is keyed only by `reward_cycle % 2` [6](#0-5) , cycle N and cycle N+2 share the same slot. If an attacker keeps cycle-N's `ConfiguredSigner` permanently `has_unprocessed_blocks() == true` (e.g., a crafted `BlockProposal` whose validation response is never observed by the runloop before rollover — the attack surface named in the question, reachable purely by an unprivileged single-slot miner gossiping a proposal), then:

1. When current reward cycle advances to N+1, cycle N becomes "stale" (`reward_cycle < current_reward_cycle`) but `cleanup_stale_signers` skips it because `has_unprocessed_blocks()` is still true.
2. Later, once the runloop enters the prepare phase for N+2 (while `current_reward_cycle` is still N+1), `is_configured_for_cycle(&self.stacks_signers, N+2)` is false (slot holds cycle-N's config, not N+2's), so `refresh_signer_config(N+2)` fires and unconditionally overwrites/drops the cycle-N `ConfiguredSigner` via `HashMap::insert`.
3. `cleanup_stale_signers` runs afterward in the same call, but by then the stale entry is already gone — it never gets the chance to detect/preserve it, and the drop happened without checking `has_unprocessed_blocks()` at all.

The net effect: the retiring signer's still-`Unprocessed`/`PreCommitted` proposal state and any per-tenure guard the `Signer` struct tracks in memory for that cycle (constructed fresh in `Signer::new` for the new `SignerConfig` [7](#0-6) ) is discarded rather than resolved, while the SignerDB row for that block remains `Unprocessed`/`PreCommitted` on disk (verified via `has_unprocessed_blocks` query semantics [3](#0-2) ). This is a "silent replace instead of clean retire" bug: the existing stale-cleanup gate (`cleanup_stale_signers`) is bypassed by ordering, not honored.

I was not able to fully trace, within available context, precisely what in-memory "conflict-guard" state (beyond DB rows) is held per-tenure in the new `Signer` struct fields (e.g. `SignedConflictInfo`, `RecentlyProcessedBlocks`) to confirm the exact scope of state lost beyond the DB-tracked block remaining unresolved — this would need direct inspection of `Signer`'s remaining fields and `local_state_machine`/conflict-tracking logic in `stacks-signer/src/v0/signer.rs`.

### Impact Explanation
This breaks the liveness/cleanup invariant that a `ConfiguredSigner` is retired only after its pending validations resolve. The practical effect is bounded to losing in-memory bookkeeping for the discarded cycle's signer instance (its `Signer` object is dropped) while the underlying SignerDB rows persist un-mutated in `Unprocessed`/`PreCommitted` state. Whether this constitutes a High-severity "lost equivocation guard on restart" as framed in the question depends on whether any UNIQUENESS/conflict-guard logic keys off of the in-memory `Signer` object rather than the persisted SignerDB rows — I could not confirm this distinction with the code read so far. If the guard is DB-backed (as `SignerDb::has_unprocessed_blocks`/`BlockInfo` suggests), the safety property may survive a process restart re-reading the DB; if any guard is purely in-memory on the `Signer` struct, it is lost when the object is dropped by `insert`.

### Likelihood Explanation
The precondition (miner-controlled attacker with one slot proposing near a burn-block boundary so the node's validation response is not observed before rollover) is plausible for a single unprivileged party who can win a miner slot and gossip a `BlockProposal`, and the slot-collision condition (`N % 2 == (N+2) % 2`, always true) is deterministic and not probabilistic. However, the described dependency — a proposal remaining permanently unresolved across an entire reward cycle boundary, not merely timed out — requires the validation response to never reach the runloop for a very long window (an entire reward cycle), which is a strong precondition not fully substantiated in the code reviewed; I did not verify whether `block_proposal_validation_timeout`/`check_pending_block_validations` would eventually force resolution of a pending validation well before a full cycle elapses.

### Recommendation
In `refresh_signer_config`, before inserting the new `ConfiguredSigner` into a slot, check whether the existing occupant (if any) still has unprocessed blocks; if so, either defer the insert, log/alert, or explicitly hand off/merge any in-memory state relevant to conflict-guard tracking before dropping the old `Signer`. Alternatively, reorder `refresh_runloop` to call `cleanup_stale_signers` before `refresh_signer_config(next_reward_cycle)`, and additionally have `refresh_signer_config` refuse (or force a delayed) overwrite of a slot occupied by a signer that `has_unprocessed_blocks()`.

### Proof of Concept
Rust test plan (in `stacks-signer/src/runloop.rs` test module or an integration test using `TEST_SKIP_SIGNER_CLEANUP`/mocked `StacksClient`):
1. Construct a `RunLoop` with a fake `Signer` implementation whose `has_unprocessed_blocks()` returns `true` unconditionally (simulating a permanently pending `BlockProposal` for reward cycle N).
2. Call `refresh_signer_config(N)` to populate slot `N % 2`.
3. Advance `current_reward_cycle_info` to simulate rollover to `N+1`, call `refresh_runloop`, assert the cycle-N `ConfiguredSigner` is still present in `self.stacks_signers` (since `has_unprocessed_blocks()` is true) — confirming `cleanup_stale_signers` correctly retains it.
4. Advance further to simulate entering the prepare phase for `N+2` while `current_reward_cycle` is `N+1`; call `refresh_runloop` again.
5. Assert `self.stacks_signers.get(&(N % 2))` now reports `reward_cycle() == N+2`, i.e., the cycle-N `ConfiguredSigner` instance is gone — replaced, not retired — while a corresponding `SignerDb::has_unprocessed_blocks(N)` check (against a DB seeded with an `Unprocessed`/`PreCommitted` block for cycle N) still returns `true`, proving the DB-tracked block was orphaned by the in-memory replace.

    fn cleanup_stale_signers(&mut self, current_reward_cycle: u64) {
        #[cfg(any(test, feature = "testing"))]
        if TEST_SKIP_SIGNER_CLEANUP.get() {
            warn!("Skipping signer cleanup due to testing directive.");
            return;
        }
        let mut to_delete = Vec::new();
        for (idx, signer) in &mut self.stacks_signers {
            let reward_cycle = signer.reward_cycle();
            if reward_cycle >= current_reward_cycle {
                // We are either the current or a future reward cycle, so we are not stale.
                continue;
            }
            match signer {
                ConfiguredSigner::RegisteredSigner(signer) => {
                    if !signer.has_unprocessed_blocks() {
                        debug!("{signer}: Signer's tenure has completed.");
                        to_delete.push(*idx);
                    }
                }
                ConfiguredSigner::NotRegistered { .. } => {
                    debug!("{signer}: Unregistered signer's tenure has completed.");
                    to_delete.push(*idx);
                }
            }
        }
        for idx in to_delete {
            self.stacks_signers.remove(&idx);
        }
    }

    /// Determine if there are any unprocessed blocks
    pub fn has_unprocessed_blocks(&self, reward_cycle: u64) -> Result<bool, DBError> {
        let query = "SELECT block_info FROM blocks WHERE reward_cycle = ?1 AND state = ?2 LIMIT 1";
        let result: Option<String> = query_row(

            query,
            params!(

                &BlockState::Unprocessed.to_string()
            ),
        )?;
