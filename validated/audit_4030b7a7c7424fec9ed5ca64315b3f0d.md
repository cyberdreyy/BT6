### Title
Post-default withdraw requests mint receipts that can never be paid, permanently locking user funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
After `finalizeDefault` runs, `IdleCreditVault.requestWithdraw` accepts new withdraw requests, mints receipt tokens to the user, and records `postDefaultRequests[_user]`. But no underlying ever backs these receipts: the only funding sources for `defaultRecoveryReserve` (`finalizeDefaultRecovery` and `reserveDefaultRecovery`) are closed once `defaultRecoveryFinalized` is true. The corresponding claim path `_claimPostDefaultWithdrawRequest` pays exclusively out of `defaultRecoveryReserve`, which is already fully reserved for pre-finalization claims (reserve = `totalBasis * recoveryPrice`, consumed exactly by defaulted/post-finalization claimants). Any post-finalization request therefore creates an unbacked receipt whose claim reverts forever, permanently locking the user's redeemed principal.

### Finding Description
`IdleCDOEpochVariant.requestWithdraw` always calls `creditVault.requestWithdraw(_underlyings, msg.sender, principal)` and burns the user's tranche tokens via `_withdrawOps`, so the user's position is converted into a vault receipt [1](#0-0) . Post-finalization, `IdleCreditVault.requestWithdraw` takes the `defaultRecoveryFinalized` branch: it burns the CDO's strategy tokens, mints receipts to the user, and sets `postDefaultRequests[_user] = _amount` without pulling or reserving any underlying [2](#0-1) . The claim then routes to `_claimPostDefaultWithdrawRequest`, which calls `_transferDefaultRecovery`, decrementing `defaultRecoveryReserve` and transferring from it [3](#0-2) .

`finalizeDefaultRecovery` sets `defaultRecoveryReserve = _recoveredAmount + prefundedReserve + defaultRecoveryReserve`, which is sized exactly to pay `totalBasis * recoveryPrice` to pre-finalization claimants [4](#0-3) . After finalization `reserveDefaultRecovery` reverts (`if (defaultRecoveryFinalized) revert NotAllowed()`), so the reserve can never grow [5](#0-4) . Since claims burn the reserve to zero (`defaultRecoveryReserve -= _amount` underflows on excess), a post-default request of any size has zero backing and its claim permanently reverts [6](#0-5) .

This mirrors the reported bug class exactly: a deposit (`requestWithdraw` after `finalizeDefault`) is accepted — tranche tokens are irrevocably burned — but the corresponding withdrawal path has no funding source and no escape hatch, so the assets are permanently locked.

### Impact Explanation
Any tranche holder who calls `IdleCDOEpochVariant.requestWithdraw` after a hard default has been finalized loses their entire position: tranche tokens are burned in `_withdrawOps`, strategy tokens are burned/minted as receipts, and `claimWithdrawRequest` reverts in `_transferDefaultRecovery` either via `defaultRecoveryReserve` underflow or insufficient vault balance. Loss equals the full haircut-adjusted value of the request (e.g., 50,000 USDC for a 100,000 USDC position finalized at `defaultRecoveryPrice = 0.5e18`). The freeze is permanent: there is no ownerless path to add to the reserve, and honest privileged roles cannot fix already-burned positions without a contract upgrade. Even the normal exit path is broken, because post-default `requestWithdraw` is the intended redemption flow (it reverts if the user has any other pending request, making it the only sanctioned exit).

### Likelihood Explanation
The sequence requires only unprivileged actions after a legitimate state: (1) borrower fails to repay and `stopEpoch` enters the catch path (`_handleBorrowerDefault` sets `defaulted = true`) [7](#0-6) ; (2) owner/manager finalizes via `finalizeDefault`, which deliberately re-enables `allowAAWithdrawRequest`/`allowBBWithdrawRequest` so users can exit [8](#0-7) ; (3) a KYC'd lender holding AA or BB tranches calls `requestWithdraw`, then `claimWithdrawRequest`, which reverts. Recovery at exactly par (`recoveryPrice == RECOVERY_FULL`) still drains the reserve to zero, so requests revert in every case except over-par recovery. No existing guard prevents this: `_skimDonatedAssets` is unrelated, `_hasWithdrawRequest` only blocks repeat requests, and `_transferFundedClaim`'s reserve guard does not apply on the reserve path.

### Recommendation
Either fund post-default receipts or forbid them. Concretely: in `IdleCreditVault.requestWithdraw`'s `defaultRecoveryFinalized` branch, revert `NotAllowed()` unless new underlying accompanies the request (e.g., pull `principal`-equivalent underlying from the CDO/borrower into `defaultRecoveryReserve`), or pay post-default receipts from a separate accounting bucket funded at request time. At minimum, gate `IdleCDOEpochVariant.requestWithdraw` on a check that post-default claims are actually payable, so users are not induced to burn tranche tokens into unbacked receipts.

```solidity
// Foundry fork PoC (test/foundry/IdleCreditVault.t.sol harness style)
function testPostDefaultRequestLocked() external {
    // Setup: deposit, run epoch, borrower defaults at stopEpoch
    uint256 amount = 100_000 * ONE_SCALE;
    _depositWithUser(user1, amount, true);        // KYC'd lender, AA tranche
    _startEpochAndCheckPrices(0);

    // borrower does not repay -> stopEpoch catches -> defaulted = true
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    assertTrue(cdoEpoch.defaulted());

    // manager finalizes recovery at 50%
    uint256 recovered = amount / 2;
    deal(defaultUnderlying, recoverySource, recovered);
    vm.prank(recoverySource);
    IERC20(defaultUnderlying).approve(address(strategy), recovered);
    vm.prank(manager);
    cdoEpoch.finalizeDefault(recovered, recoverySource); // defaultRecoveryReserve = recovered

    // pre-finalization claimants (or active NAV burn) consume reserve proportionally;
    // a user who had a pending receipt claims their haircut share, draining reserve to 0.

    // Now user2 (or same user with fresh tranches) requests withdraw post-finalization.
    // Tranche tokens are burned, postDefaultRequests set, but nothing funds the reserve.
    vm.startPrank(user2);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    // claim reverts: defaultRecoveryReserve -= amount underflows (reserve exhausted)
    vm.expectRevert();
    cdoEpoch.claimWithdrawRequest();
    vm.stopPrank();

    // The user's tranches are burned and the receipt can never be paid -> permanent lock.
}
```

```text
  function _claimPostDefaultWithdrawRequest(address _user) internal returns (uint256 amount) {
    amount = postDefaultRequests[_user];
    if (amount == 0) return amount;
    postDefaultRequests[_user] = 0;
    // Post-default receipts are paid 1:1 because the haircut was applied when the request was made.
    _burn(_user, amount);
    _transferDefaultRecovery(_user, amount);
  }
```
