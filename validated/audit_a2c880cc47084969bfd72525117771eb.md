### Title
Signed cache URL `Expires` is derived unclamped from job-supplied build timeout, allowing long-lived URLs to outlive the job - (File: cache/gcs/adapter.go)

### Summary
`gcsAdapter.presignURL` sets `Expires: time.Now().Add(a.timeout)` where `a.timeout` is the raw `timeout` argument passed to `gcs.New(config, timeout, objectName)` via the `cache.Factory` interface, with no minimum/maximum clamping applied in the adapter itself. `cache.GetAdapter(config, timeout, ...)` forwards this value directly to `createAdapter`/`New` without any cap. ### Finding Description
`gcsAdapter.presignURL` builds `storage.SignedURLOptions{Expires: time.Now().Add(a.timeout)}` where `a.timeout` is set verbatim in `New` from its `timeout time.Duration` parameter, with no upper bound check. [4](#0-3)  The `Adapter` `Factory` signature (`func(config *cacheconfig.Config, timeout time.Duration, objectName string) (Adapter, error)`) and `cache.GetAdapter` simply pass the caller-supplied `timeout` through to `createAdapter` -> the registered factory (`gcs.New`) with no clamping logic anywhere in this package. [5](#0-4) [6](#0-5)  I could not locate, within the indexed portion of the repository, the exact call site that supplies `build.GetBuildTimeout()` as this `timeout` argument to `cache.GetAdapter`; that wiring lives outside `cache/` (likely in the build/executor code invoking cache push/pull), and I was unable to confirm it in this session due to tool-call limits. However, the `cache` package itself provides no independent cap — whatever duration is handed to `GetAdapter` becomes the signed URL's validity window unmodified.

Once a signed URL is generated, GCS signed URLs are self-contained, offline-verifiable bearer credentials backed by the service account key/HMAC signature; GCS has no mechanism to revoke an individual signed URL early, and revoking a GitLab job token or cancelling a job does not affect an already-minted GCS signed URL. So if the value fed into `a.timeout` is large (whether that's the job's configured build timeout or any other caller-controlled duration), the resulting cache GET/HEAD/PUT URL remains valid, and exploitable, for that entire window regardless of job/token state.

### Impact Explanation
An attacker who controls (directly or indirectly) the duration value flowing into `cache.GetAdapter`'s `timeout` parameter obtains a signed URL to their own project's cache object that stays valid, and unauthenticated by any GitLab-side check, for that whole duration — including after the job finishes, is cancelled, or its CI/job token is revoked. This allows prolonged unauthorized read/write against that cache object outside the job's lifetime, and (if combined with a separate path-traversal bug affecting `objectName`) could extend to another project's object.

### Likelihood Explanation
Exploitability depends entirely on whether the value passed as `timeout` to `cache.GetAdapter`/`gcs.New` is (a) attacker-influenceable and (b) unbounded server-side. I could not verify the exact call site or confirm that GitLab's server-side project/group maximum-job-timeout enforcement is bypassed or absent in this Runner-side code path within this session — the question's stated precondition ("no server-side cap on job timeout") is external to `cache/gcs/adapter.go` and could not be validated from the files reviewed. What is confirmed is that `cache/gcs/adapter.go` and `cache/cache.go` perform zero independent clamping of the `timeout` value before using it as `Expires`, so if the precondition holds, the bug is real and trivially repeatable per job.

### Recommendation
In `gcsAdapter.presignURL` (and the analogous S3/Azure adapters), clamp `a.timeout` to a fixed, Runner-configured maximum (e.g., a small constant such as a few minutes) independent of the job-configured build timeout, so the signed URL's `Expires` cannot be inflated by job input. Apply the same cap centrally in `cache.GetAdapter` before dispatching to any adapter factory, so all adapters benefit uniformly.

### Proof of Concept
Add a Go unit test in `cache/gcs/adapter_test.go`:
```go
func TestPresignURL_TimeoutIsClamped(t *testing.T) {
    var captured storage.SignedURLOptions
    a := &gcsAdapter{
        timeout: 1000 * time.Hour, // attacker-supplied extreme build timeout
        config:  &cacheconfig.CacheGCSConfig{BucketName: "bucket"},
        credentialsResolver: &fakeResolver{credentials: fakeCreds},
        generateSignedURL: func(bucket, name string, opts *storage.SignedURLOptions) (string, error) {
            captured = *opts
            return "https://example.com/signed", nil
        },
    }
    a.presignURL(context.Background(), http.MethodGet, "")

    maxAllowed := time.Now().Add(15 * time.Minute) // expected server-enforced cap
    assert.True(t, captured.Expires.Before(maxAllowed),
        "signed URL Expires should be capped independent of job-supplied timeout, got %v", captured.Expires)
}
```
Expected current behavior: assertion fails because `captured.Expires` reflects the full 1000-hour input, confirming the absence of clamping in `presignURL`.

		objectName:             objectName,
		maxUploadedArchiveSize: config.MaxUploadedArchiveSize,

		credentialsResolver:    cr,
	}

	return a, nil
}
