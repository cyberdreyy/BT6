### Title
`get_accounts` index-based pagination skips accounts because `internal_save_account` removes zero-balance rows via swap-remove, causing accounts with positive claims to be omitted across paginated enumeration — (File: `staking-pool/src/lib.rs`, `staking-pool/src/internal.rs`)

### Summary
`get_accounts(from_index, limit)` reads the current length of the `accounts` `UnorderedMap`'s backing vector on every call and returns the slice `from_index..min(from_index+limit, keys.len())`. Because `internal_save_account` deletes any account whose `unstaked` and `stake_shares` both fall to zero, and `near_sdk::collections::UnorderedMap::remove` is index-based (it swap-removes the last element into the freed slot to keep the vector contiguous), the position of every account after the removed one shifts by one and the total length shrinks. An attacker who fully withdraws an account between two paginated `get_accounts` calls made by an integrator can cause a still-funded account to be shifted out of the range that either page covers, so it is never returned by the enumeration even though its claim is real and untouched.

### Finding Description
The binding the enumeration must satisfy is:

`⋃_{page} get_accounts(from_index_page, limit_page) == { account_id : accounts[account_id].unstaked > 0 OR accounts[account_id].stake_shares > 0 }`

for a paginated scan where `from_index` advances by `limit` each call, bounded by `get_number_of_accounts()`.

`get_accounts` is implemented purely against the vector's current length at call time: [1](#0-0) 

`internal_save_account` deletes a row entirely once both balances hit zero: [2](#0-1) 

`internal_withdraw` (reachable from the public `withdraw` / `withdraw_all` methods) drives `account.unstaked` to zero and calls `internal_save_account`, which then removes the row from the underlying `UnorderedMap`: [3](#0-2) 

The `UnorderedMap`'s `keys_as_vector`/`values_as_vector` are backed by an append-and-swap-remove `Vector` (near-sdk semantics): removing an entry moves the last element into the freed index and shrinks the length by one. Because `get_accounts` computes its window relative to the vector's *current* length on every independent view call, this is fine for a single call, but an integrator reconciling a whole pool must paginate across multiple separate view calls (each a separate query, non-atomic with respect to state changes). Any account holder can submit a state-changing transaction between two of the integrator's paginated calls.

Exploit flow, right after a pool is created via `create_staking_pool` (so the account count is small and the boundary is trivial to control):
1. Attacker calls `deposit_and_stake` as account A → `accounts = [A]` (index 0), `len = 1`.
2. Attacker calls `deposit_and_stake` as account B → `accounts = [A, B]` (index 1), `len = 2`.
3. Integrator calls `get_number_of_accounts()` → 2, then paginates with `limit = 1`.
4. Integrator calls `get_accounts(0, 1)` → returns `[A]`.
5. Before the integrator's next call, attacker calls `withdraw_all`/`unstake_all` sequence as A to drive A's `unstaked` and `stake_shares` to 0. `internal_save_account` removes A: the swap-remove moves B into index 0 and `len` becomes 1.
6. Integrator calls `get_accounts(1, 1)` → range is `1..min(2,1) = 1..1`, i.e. empty.

B — which still holds its full staked claim the entire time — is never returned by any page: it wasn't at index 0 in step 4 (A was), and it isn't reached in step 6 because the vector shrank and B is now sitting at index 0, below the new `from_index`. The count returned across pages (1 total, matching a fresh `get_number_of_accounts() == 1`) looks self-consistent, but the *identity* is wrong: the enumerated account (A) has no funds left, while the account holding real funds (B) is silently dropped from the reconciliation.

None of the existing guards (`internal_ping`'s balance assert, `assert_owner`, U256 rounding, `is_valid_account_id`) address this because the flaw is in the enumeration contract itself, not in balance accounting math — `total_staked_balance` and `total_stake_shares` remain internally correct; only the per-account view enumeration used by external integrators diverges from them.

### Impact Explanation
No NEAR is moved incorrectly by the contract itself; `total_staked_balance`/`total_stake_shares` stay accurate. The impact is that any third party relying on `get_accounts` pagination to reconcile per-account claims against the pool total (e.g., an exchange, custodian, or auditor verifying delegator balances) will compute a claim set that omits a funded account while still matching the reported `get_number_of_accounts()` cardinality, causing an accounting value to diverge from reality that another party settles on — matching the "High" impact category. This is repeatable by any delegator, on any pool, at any time an integrator paginates across more than one view call, and is trivially staged "moments after" pool creation since a fresh pool has few accounts and simple index boundaries to target.

### Likelihood Explanation
Preconditions are minimal: the attacker only needs to be a delegator (or control two delegator accounts) in a pool created through the public `create_staking_pool`/`StakingPoolFactory`, and to time one full-withdrawal transaction between two of the integrator's paginated `get_accounts` calls. No special balances, no owner privilege, and no cooperation from the pool owner are required. The only real-world constraint is that the integrator must fetch the account list across more than one call (necessary for any pool with more accounts than fit in a single view call's gas/size budget), which is the standard way `get_accounts` is meant to be used given its `from_index`/`limit` signature.

### Recommendation
Do not rely on raw vector index stability for pagination when entries can be removed. Options: (a) never delete account rows on zero balance (keep a persistent Account record, marking it zero rather than removing it, so indices remain stable), (b) expose a stable cursor (e.g., paginate by `account_id` lexical order rather than vector index, using `iter_from`), or (c) document and enforce that `get_accounts` callers must complete their full reconciliation atomically within a single call, and provide a size-bounded "get all" method instead of open-ended pagination combined with mutation-permitting concurrent access.

### Proof of Concept
```rust
// cargo test in staking-pool/src/lib.rs test module (using existing Emulator harness)
#[test]
fn test_pagination_skips_funded_account_after_withdraw() {
    let mut emulator = Emulator::new(
        owner(),
        "KuTCtARNzxZQ3YvXDeLjx83FDqxv2SdQTSbiq876zR7".to_string(),
        zero_fee(),
    );

    // Account A stakes.
    emulator.update_context(alice(), ntoy(100));
    emulator.contract.deposit_and_stake();
    emulator.amount += ntoy(100);
    emulator.simulate_stake_call();

    // Account B stakes.
    emulator.update_context(bob(), ntoy(100));
    emulator.contract.deposit_and_stake();
    emulator.amount += ntoy(100);
    emulator.simulate_stake_call();

    assert_eq!(emulator.contract.get_number_of_accounts(), 2);

    // Integrator page 1: expects account at index 0.
    let page1 = emulator.contract.get_accounts(0, 1);
    assert_eq!(page1[0].account_id, alice());

    // Attacker (alice) fully unstakes and withdraws between integrator pages,
    // deleting her row via internal_save_account -> swap_remove shifts bob to index 0.
    emulator.update_context(alice(), 0);
    emulator.contract.unstake_all();
    emulator.simulate_stake_call();
    emulator.skip_epochs(4);
    emulator.update_context(alice(), 0);
    emulator.contract.withdraw_all();

    assert_eq!(emulator.contract.get_number_of_accounts(), 1);

    // Integrator page 2: expects the "second" account, but bob has moved to index 0.
    let page2 = emulator.contract.get_accounts(1, 1);
    assert_eq!(page2.len(), 0, "bob is skipped entirely across the two pages");

    // Yet bob still holds a real staked claim.
    assert!(emulator.contract.get_account_staked_balance(bob()).0 > 0);
}
```
Both sides of the binding: LHS = `{alice, bob}` (accounts with positive claim before alice's withdrawal, and `{bob}` after); RHS = union of `get_accounts` pages = `{alice}` (page1, stale/zero-balance at read time of reconciliation) — `bob`, the only account with a real balance, is absent from the union of all pages fetched. `get_number_of_accounts()` still reports a count consistent with page sizes (1), masking the discrepancy from the "fast validation" check while the actual funded account is missing from enumeration.

    /// Inner method to save the given account for a given account ID.
    /// If the account balances are 0, the account is deleted instead to release storage.
    pub(crate) fn internal_save_account(&mut self, account_id: &AccountId, account: &Account) {
        if account.unstaked > 0 || account.stake_shares > 0 {
            self.accounts.insert(account_id, &account);
        } else {
            self.accounts.remove(account_id);
        }
    }
