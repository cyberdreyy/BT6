### Title
Bundle metering's affordability check omits the post-Isthmus operator fee, understating a transaction's total cost - (File: crates/execution/metering/src/transaction.rs)

### Summary
The Tokemak `totalAssets()` bug is a class of "incomplete aggregate accounting" defect: a function that is supposed to sum *all* components of a value (there, `totalIdle + totalDebt - fees`) instead omits one required component, silently producing a wrong total that downstream logic relies on. The analogous pattern on Base is `validate_tx` in `crates/execution/metering/src/transaction.rs`, which computes a transaction's total required balance ("cost") to gate `eth_callBundle`/bundle-metering simulation, but only adds the L1 data fee component and omits the Isthmus/Jovian operator fee component that Base's own execution path (and the real txpool admission path) charges.

### Finding Description
`validate_tx` builds the transaction's total cost as `value + gas_limit*max_fee_per_gas`, then adds only `l1_block_info.calculate_tx_l1_cost(...)`: [1](#0-0) 

This mirrors the vault bug's shape exactly: a "total cost" aggregate that should sum *every* fee component actually charged during execution but drops one. Base's real fee accounting includes a third, mandatory component — the post-Isthmus (and Jovian-scaled) operator fee — computed via `L1BlockInfo::tx_cost`, which adds `operator_fee_charge` on top of the L1 cost when Isthmus is active: [2](#0-1) 

Every other cost-affordability check in the codebase that gates transaction admission correctly uses `tx_cost` (which includes the operator fee), not `calculate_tx_l1_cost` alone:
- The production txpool admission path explicitly calls out that using only the L1 cost is a known bug pattern to avoid ("Must mirror the execution-side cost in `BaseHandler`... otherwise operator-fee-underfunded txs get admitted but never execute"): [3](#0-2) 
- The bundle-building/proposer validator has a regression test specifically asserting that a sender funded for `l1_only_cost` but not the operator fee must be rejected: [4](#0-3) 
- The actual EVM handler charges (and later refunds/settles) the operator fee as a first-class fee component alongside the L1 cost and base fee: [5](#0-4) [6](#0-5) 

`validate_tx` is the sole affordability gate used inside `meter_bundle`, which the metering RPC surface (`eth_callBundle`-style simulation, `MeteringApiImpl`) uses to pre-validate each transaction in a submitted bundle before executing it against real chain state derived from an anonymous RPC caller's bundle submission: [7](#0-6) [8](#0-7) 

Because `validate_tx`'s "total cost" omits the operator fee, it under-calculates the true required balance for any post-Isthmus (or Jovian) transaction, exactly as `LMPVault.totalAssets()` under/over-calculated the vault's true backing by omitting the fee subtraction.

### Impact Explanation
This is a Medium-severity incorrect-calculation defect, matching the reported bug class: `validate_tx` will pass an affordability check for a bundle transaction whose sender cannot actually cover the full on-chain cost (value + gas cost + L1 fee + operator fee). Practically:
- `meter_bundle` will proceed to execute a transaction that `validate_tx` incorrectly deemed affordable. The subsequent real EVM execution (which does enforce the full cost via `BaseHandler::validate_against_state_and_deduct_caller`) will diverge from the metering path — metering can silently pass/execute transactions or report gas/fee metrics that do not reflect the transaction's true failure mode on-chain, corrupting the metering/simulation results that operators or tooling rely on to decide whether a bundle is includable.
- This is a genuine "incorrect calculation" defect reachable via an RPC client submitting a bundle for metering, matching the report's fee-omission bug class, though its blast radius is confined to the metering/simulation surface rather than consensus-critical state (the block-building/execution paths correctly include the operator fee, per the code cited above), so it does not cause unbacked supply or theft — it produces incorrect metering output, matching Medium severity for an accounting bug in a used-but-non-consensus-critical helper.

### Likelihood Explanation
Likelihood is high given reachability: any Isthmus/Jovian-era Base network processes bundles through `meter_bundle`/`validate_tx` whenever bundle metering is invoked, and the operator fee is always non-zero post-Isthmus whenever the L1 attributes deposit has seeded non-default `operator_fee_scalar`/`operator_fee_constant`. No special privilege is needed beyond submitting a bundle for metering.

### Recommendation
In `crates/execution/metering/src/transaction.rs`, replace the `l1_block_info.calculate_tx_l1_cost(...)` call in `validate_tx` with `l1_block_info.tx_cost(&data, U256::from(txn.gas_limit()), spec)`, mirroring `apply_base_checks` in `crates/execution/txpool/src/validator.rs` and `BaseHandler::validate_against_state_and_deduct_caller`, so the metering path's affordability check includes the operator fee exactly like the real execution and admission paths.

### Proof of Concept
1. Configure a chain post-Isthmus with non-zero `operator_fee_scalar`/`operator_fee_constant` (as in `crates/common/evm/src/l1block.rs` tests, e.g. `operator_fee_scalar: 1_000`, `operator_fee_constant: 10`).
2. Fund a sender with exactly `value + gas_limit*max_fee_per_gas + l1_data_fee` (no headroom for the operator fee) — analogous to the txpool regression test `rejects_tx_underfunded_for_operator_fee_post_isthmus` at [9](#0-8) , but instead submit this transaction inside a bundle to `meter_bundle`.
3. Observe that `validate_tx` (`crates/execution/metering/src/transaction.rs:27-53`) returns `Ok(())` because it never adds the operator fee, whereas the real `BaseHandler`/txpool path would reject or fail the same transaction for insufficient funds — demonstrating the metering path's "total cost" calculation is incomplete relative to the true on-chain cost.

    /// Calculate additional transaction cost.
    #[inline]
    pub fn tx_cost(&mut self, enveloped_tx: &[u8], gas_limit: U256, spec: BaseSpecId) -> U256 {
        // compute L1 cost
        let mut additional_cost = self.calculate_tx_l1_cost(enveloped_tx, spec);

        // compute operator fee
        if spec.is_enabled_in(BaseUpgrade::Isthmus) {
            let operator_fee_charge = self.operator_fee_charge(enveloped_tx, gas_limit, spec);
            additional_cost = additional_cost.saturating_add(operator_fee_charge);
        }

        additional_cost
    }

    #[tokio::test]
    async fn rejects_tx_underfunded_for_operator_fee_post_isthmus() {
        let chain_config = ChainConfig::mainnet();
        let chain_spec = Arc::new(BaseChainSpec::mainnet());

        let signer = Account::Alice.signer();
        let sender = signer.address();
        let tx = TxEip1559 {
            chain_id: chain_config.chain_id,
            nonce: 0,
            gas_limit: 50_000,
            max_fee_per_gas: 1_000,
            max_priority_fee_per_gas: 0,
            to: TxKind::Call(Address::random()),
            value: U256::ZERO,
            access_list: Default::default(),
            input: bytes!("FACADE"),
        };
        let gas_limit = tx.gas_limit;
        let signature = signer.sign_hash_sync(&tx.signature_hash()).unwrap();
        let envelope = BaseTxEnvelope::Eip1559(tx.into_signed(signature));
        let recovered_tx = envelope.clone().try_into_recovered().unwrap();
        let encoded = recovered_tx.encoded_2718();

        let isthmus_data = decode(ISTHMUS_L1_INFO_DATA_HEX).expect("valid hex fixture");
        let mut l1_block_info = base_execution_evm::parse_l1_info(&isthmus_data).unwrap();

            &mut l1_block_info,
            Arc::clone(&chain_spec),
            chain_config.isthmus_timestamp,
            &encoded,
            false,
        )
        .unwrap();
        let full_additional_cost = l1_block_info.tx_cost(
            &encoded,
            U256::from(gas_limit),

        );
