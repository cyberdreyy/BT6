### Title
Instant-withdraw claims pay the aggregate `instantWithdrawsRequests` receipt counter, letting a user who re-requests in a later epoch drain other users' funded claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external report describes a TOCTOU bug where a per-item view limit is enforced by a counter that is checked and only later incremented, so concurrent access bypasses the limit. The on-chain analog is a check-then-act mismatch in `IdleCreditVault.claimInstantWithdrawRequest`: the claim pays out the *aggregate* per-user receipt balance `instantWithdrawsRequests[_user]` — which accumulates requests across epochs — while funding is tracked per-epoch (`pendingInstantWithdraws`, `instantWithdrawClaimsByEpoch`) and collected later via `collectInstantWithdrawFunds`. A user who stacks an unfunded newer request on top of an already-funded receipt can claim the full sum immediately, spending funded liquidity reserved for other users' receipts.

### Finding Description
`requestInstantWithdraw` burns the CDO's strategy tokens, mints a 1:1 receipt to the user, and increases both `instantWithdrawsRequests[_user]` and the epoch-scoped `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]` / `pendingInstantWithdraws` counters [1](#0-0) .

Funding is asynchronous: `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` and pulls underlying from the IdleCDO only when the borrower/manager funds the epoch [2](#0-1) .

The claim path, however, ignores the per-epoch bookkeeping entirely:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [3](#0-2) 

`amount` is the lifetime aggregate receipt balance, not "receipts whose epoch was funded". The strategy's underlying balance is the shared funded reserve for *all* users' instant claims. So:

1. Epoch N ends with a decreased APR; user A calls `requestWithdraw` on `IdleCDOEpochVariant`, taking the instant path (`lastEpochApr > currentApr + instantWithdrawAprDelta`) and receiving receipt R₁ [4](#0-3) .
2. Epoch N+1 starts, `instantWithdrawDelay` passes, `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` funds the reserve covering R₁ and other users' receipts (e.g., user B's receipt).
3. A does not claim. At a later epoch stop with another APR decrease, A submits a second instant request R₂. `instantWithdrawsRequests[A]` is now R₁ + R₂, but `pendingInstantWithdraws` includes the unfunded R₂.
4. A calls `claimInstantWithdrawRequest` (via the CDO) before R₂ is funded. The claim burns R₁ + R₂ receipts and `_transferFundedClaim` sends R₁ + R₂ underlying from the shared reserve — paying the still-unfunded R₂ out of B's (and others') funded balance.

This is exactly the reported bug class: the "view limit" is `pendingInstantWithdraws`/per-epoch funded status, checked only implicitly by reserve solvency, while the *use* — the burn-and-pay — reads a stale aggregate counter that was already incremented.

### Impact Explanation
Direct theft / insolvency: A is paid for a receipt that was never funded, and the shortfall materializes when the last legitimately-funded claimant (B) tries to claim and the reserve is empty — `safeTransfer` reverts or B is underpaid. Quantified loss = the size of the attacker's second (unfunded) request, bounded only by their tranche balance. The "one receipt, one payout against funded reserves" invariant is broken.

### Likelihood Explanation
Requires two instant-withdraw windows (an APR decrease vs `lastEpochApr` in two separate buffer periods) and that the attacker holds tranche tokens to re-request — both achievable by an ordinary KYC-passed lender with no privileged role. No guard blocks it: `_onlyIdleCDO` passes via the public CDO claim, no per-epoch funded check exists in the claim path, and `claimInstantWithdrawRequest` is callable at any time after the delay, including across subsequent epochs (tests confirm claims remain valid in later epochs). Uncertainty: the CDO-side `claimInstantWithdrawRequest` gating (IdleCDOEpochVariant) could not be fully re-verified within the available iterations; if it separately restricts claims to the currently funded epoch's receipts, the exploit window narrows but the strategy-level aggregate accounting would still be the weak check for any cross-epoch receipt holder.

### Recommendation
In `claimInstantWithdrawRequest`, pay only receipts whose epoch has been funded — e.g., iterate/settle `instantWithdrawsRequestsByEpoch[_user]` against funded epochs (tracked when `collectInstantWithdrawFunds` runs), or record a per-user `instantWithdrawsFunded` watermark incremented on collection and pay `min(instantWithdrawsRequests[_user], fundedWatermark)`, decrementing it on claim. Alternatively, reset/claim receipts atomically per epoch so an unfunded newer request can never be swept into an older funded claim.

### Proof of Concept
Foundry fork, standard (non-programmable, non-prefunded) variant, building on `test/foundry/IdleCreditVault.t.sol` instant-withdraw tests:

```solidity
function testInstantClaimDrainsOtherUsersFundedReserve() external {
    // Epoch 1: users A and B deposit AA
    uint256 mintedA = _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    uint256 mintedB = _depositWithUser(victim, 10_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);
    // stopEpoch with APR decreased below lastEpochApr - instantWithdrawAprDelta
    _stopEpochAndCheckPrices(0, lowerApr, _expectedFundsEndEpoch());

    // Buffer: both request instant withdraw
    vm.prank(attacker); cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);   cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Epoch 2: funds collected for both receipts
    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    vm.prank(manager); cdoEpoch.getInstantWithdrawFunds();

    // Epoch 2 ends with another APR decrease -> new instant window
    _stopEpochAndCheckPrices(1, lowerApr2, _expectedFundsEndEpoch());

    // Attacker requests AGAIN (unfunded receipt R2) using fresh tranches
    uint256 mintedA2 = _depositWithUser(attacker, 10_000 * ONE_SCALE, true);
    vm.prank(attacker); cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Epoch 3 starts, delay passes, but R2 is NOT yet funded
    _startEpochAndCheckPrices(2);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);

    // Attacker claims: pays instantWithdrawsRequests[attacker] = R1 + R2
    uint256 balPre = underlying.balanceOf(attacker);
    uint256 agg = strategy.instantWithdrawsRequests(attacker);
    vm.prank(attacker); cdoEpoch.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, agg, "paid incl. unfunded R2");

    // Victim's funded claim now reverts/underpays: reserve drained
    vm.prank(victim);
    vm.expectRevert(); // ERC20 transfer exceeds strategy balance
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Expected: attacker receives R₁ + R₂ while only R₁ was funded; the victim's funded instant receipt can no longer be paid in full from the strategy reserve.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
