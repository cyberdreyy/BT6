### Title
Mid-epoch deposit shifts `epochNumber`, detaching withdraw receipts from `lossRecoveryPriceByEpoch` — pending withdrawers escape the stop-epoch loss and over-claim funded underlyings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records a withdraw request against `epochNumber` at request time (`withdrawsRequestsByEpoch[_user][currentEpoch]`, `lastWithdrawRequest[_user] = currentEpoch`), but `collectWithdrawFunds` stores a realized stop-epoch loss under `lossRecoveryPriceByEpoch[epochNumber]` at stop time. Because `deposit()` increments `epochNumber` when called while the epoch is running, any mid-epoch deposit desynchronizes the two keys: the receipt is looked up in a "stale" epoch where no loss price exists, so the loss-adjusted claim path is skipped and the funded-claim path pays the full par amount. This is the credit-vault analogue of CVE-2023-31248: an object (the epoch's loss record) is retrieved through a stale identifier without verifying it is still the correct/active record — the lookup silently misses and the caller is treated as if no loss was ever applied.

### Finding Description
In `requestWithdraw` the vault binds the receipt to the epoch counter read at request time:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:281-293
lastWithdrawRequest[_user] = currentEpoch;
...
withdrawsRequests[_user] += _amount;
withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
```

In `deposit()`, when a deposit arrives while the epoch is running, the same counter is bumped:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:607-610
if (IIdleCDOEpochVariant(idleCDO).isEpochRunning()) {
  totEpochDeposits = 0;
  epochNumber += 1;
}
```

When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` books the haircut under the *current* `epochNumber`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:417-421
uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
...
lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
```

At claim time, `_claimLossAdjustedWithdrawRequest` resolves the loss epoch via the *stale* request-time marker:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:789-800
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
...
amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
_transferFundedClaim(_user, amount);
```

If a mid-epoch deposit raised `epochNumber` from `N` to `N+1` between the request and the stop, the loss is stored at index `N+1` while the receipt marker still says `N`. `lossRecoveryPriceByEpoch[N] == 0`, the loss-adjusted path returns 0, and execution falls into `_claimFundedWithdrawRequest`, whose only gating check is:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:326-328
if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
  revert NotAllowed();
}
```

With `epochNumber == N+1 > N`, the check passes immediately after the epoch stops, the user's `withdrawsRequests[_user]` is paid **at par** from the underfunded strategy balance, and the pro-rata loss that `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds` assigned to pending receipts is silently escaped. The same key mismatch exists for `withdrawsRequestsByEpoch`/`instantWithdrawsRequestsByEpoch` indexing and `apr0RateByEpoch`/`apr0Users[_user].principalEpoch`, so APR0 interest settlement and per-epoch default-claim reconstruction are keyed on an epoch counter that mid-epoch deposits can move.

Notably, the defensive guard added in `requestWithdraw` (revert when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`) only protects the *same-key* case; it cannot see a loss stored under a different epoch index, so it does not mitigate this.

### Impact Explanation
- Direct theft / loss escape: a pending withdrawer receives 100% of `withdrawsRequests[_user]` instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`. The difference is paid out of underlying that `collectWithdrawFunds` funded only to cover `lossRecoveryPrice`-adjusted receipts, so the shortfall is socialized onto active tranche holders and any other pending claimants (insolvency of the funded-receipt pool for exactly `pendingBasis - pendingToFund` per affected request, up to the full assigned `pendingLoss`).
- An unprivileged tranche holder can trigger this deterministically: request a withdraw during the buffer, wait for (or arrange, via any KYC'd depositor/`depositDuringEpoch` flow) a mid-epoch deposit that bumps `epochNumber`, then take a partial loss at `stopEpochWithDuration` and claim at par.
- The same desync can permanently freeze claims in the opposite direction when the stale marker lands on an epoch whose `lossRecoveryPriceByEpoch` was set for a *different* loss event (wrong haircut applied to the wrong receipts), breaking the "one receipt, one correct payout" invariant both ways.

### Likelihood Explanation
- Preconditions are all reachable by unprivileged actors: (1) hold tranche tokens and call `requestWithdraw` while `epochNumber = N`; (2) any mid-epoch deposit through `mintStrategyTokens`/`deposit()` during the running epoch increments `epochNumber`; (3) the epoch ends with a partial loss via `stopEpochWithDuration`/`collectWithdrawFunds` shortfall — routine when the borrower under-funds, not requiring borrower collusion since loss epochs are a normal failure mode the code explicitly supports.
- No privileged misbehavior is needed; the manager/borrower calls that realize the loss are honest and correctly parameterized — the bug is purely the stale epoch-key lookup.
- Existing guards do not stop it: `epochNumber <= lastWithdrawRequest[_user]` is *satisfied* (that's the problem), the `lossRecoveryPriceByEpoch[lossEpoch] == 0` early-return silently skips the haircut, and `_transferFundedClaim` only verifies the reserve covers the transfer, which it does because funded-receipt underlyings were collected.

### Recommendation
Key all loss/default records by the request epoch, not the mutable counter: in `collectWithdrawFunds` (and default finalization), derive the epoch index consistently with how receipts are stored — e.g., store the loss under `epochNumber` *and* have `requestWithdraw` snapshot a dedicated `requestEpoch` that is only advanced at epoch boundaries, or maintain a monotonic `lossEpoch`/`withdrawEpoch` counter that `deposit()` may not increment mid-epoch. At minimum, in `collectWithdrawFunds` write `lossRecoveryPriceByEpoch` for every epoch index that has live pending receipts (or store the loss under a global "latest loss" pointer that claims dereference regardless of epoch drift), and add an invariant test: request → mid-epoch deposit → loss stop → claim must pay `claimBasis * lossRecoveryPrice / RECOVERY_FULL`.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;

import "forge-std/Test.sol";
// imports: IdleCDOEpochVariant, IdleCreditVault, IERC20Detailed, AAtranche...

contract StaleLossEpochTest is Test {
    // reuse existing fixture vars: cdoEpoch, creditVault, underlying, AAtranche,
    // owner, manager, borrower, user1, user2, ONE_SCALE, initialApr

    function testMidEpochDepositDetachesLossEpoch() public {
        uint256 amount = 10_000 * ONE_SCALE;
        address attacker = makeAddr("attacker");

        // 1. Buffer phase: attacker deposits via AA tranche and requests withdraw.
        //    requestWithdraw stores lastWithdrawRequest[attacker] = epochNumber = N
        //    and withdrawsRequestsByEpoch[attacker][N] = amount.
        _depositWithUser(attacker, amount, true);
        vm.prank(attacker);
        uint256 basis = cdoEpoch.requestWithdraw(0, address(AAtranche));
        uint256 reqEpoch = creditVault.epochNumber();

        // 2. Epoch starts (N running).
        _startEpochAndCheckPrices(reqEpoch);

        // 3. Mid-epoch deposit by any KYC'd user bumps epochNumber to N+1.
        //    (deposit() path: isEpochRunning() -> epochNumber += 1)
        _depositWithUser(makeAddr("mid-depositor"), amount, true);
        assertEq(creditVault.epochNumber(), reqEpoch + 1, "epoch drift");

        // 4. Honest manager stops epoch with a partial loss via stopEpochWithDuration.
        //    collectWithdrawFunds(funded < pendingBasis) writes
        //    lossRecoveryPriceByEpoch[N+1], NOT [N].
        vm.warp(cdoEpoch.epochEndDate() + 1);
        uint256 funded = basis / 2; // 50% loss on pending receipts
        deal(address(underlying), borrower, funded + _expectedFundsEndEpoch());
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(0, funded);

        assertGt(creditVault.lossRecoveryPriceByEpoch(reqEpoch + 1), 0, "loss recorded");
        assertEq(creditVault.lossRecoveryPriceByEpoch(reqEpoch), 0, "stale epoch key");

        // 5. Attacker claims: _claimLossAdjustedWithdrawRequest reads
        //    lossRecoveryPriceByEpoch[lastWithdrawRequest=N] == 0 -> skipped.
        //    _claimFundedWithdrawRequest: epochNumber(N+1) <= lastWithdrawRequest(N)
        //    is false -> paid at PAR.
        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdoEpoch.claimWithdrawRequest();
        uint256 got = underlying.balanceOf(attacker) - balPre;

        // Expected fair payout = basis * 0.5e18 / 1e18; attacker instead gets ~basis.
        assertGt(got, basis * 6e17 / 1e18, "attacker escaped the haircut");
        // The stolen delta == pendingLoss share meant to be borne by the receipt.
    }
}
```

Run against the existing `test/foundry/IdleCreditVault.t.sol` fixture on a mainnet fork (`forge test --match-test testMidEpochDepositDetachesLossEpoch --fork-url $ETH_RPC`). The assertion demonstrates that the haircut stored under the post-drift epoch index is never applied to the receipt created under the pre-drift index.
