### Title
Masked CI/CD variables leak in cleartext through `run:`-step dispatch because `buildRunRequest` drops the `Masked` flag before the nested step-runner call, and `Logger.StepRunnerStream` skips its own masker for step-runner output - ([File: common/buildlogger/build_logger.go], [File: functions/concrete/run/run_steps.go])

### Summary
`Logger.StepRunnerStream` (common/buildlogger/build_logger.go) deliberately skips the outer masker/tokensanitizer/urlsanitizer chain for output it classifies as "pre-stamped," on the documented assumption that step-runner already masked the content ("step-runner masked upstream"). This trust is broken for the `run:` keyword: `functions/concrete/run/run_steps.go`'s `buildRunRequest` forwards job variables to the nested step-runner dispatch without the `Masked` field, unlike the top-level dispatch in `steps/steps.go`'s `addVariables`, which does set it. As a result, a masked secret echoed inside a `run:` step is never marked as maskable to the nested step-runner and reaches the job trace in cleartext.

### Finding Description
The attack path is real, but the specific "forged 28-byte header" mechanism in the question is not: the header bytes inspected by `isPreStamped` ( [1](#0-0) ) are populated from step-runner's own trusted timestamper/protocol metadata (real timestamps, stream id, stream/line type), not from attacker-controlled script text, so a user cannot embed a self-forged header plus secret inside the first 28 bytes of a single `Write()` call to fake pre-stamped status.

The actual, verifiable bug is upstream of that check. At the top level, `steps/steps.go`'s `addVariables` forwards `Masked: v.Masked` for every job variable to the step-runner dispatch that produces the pre-stamped lines Runner trusts: [2](#0-1) 

But when a job uses the `run:` keyword, `functions/concrete/run`'s builtin dispatches a *nested* step-runner job via `runUserSteps`/`buildRunRequest`, which builds `client.Variable{Key: key, Value: value.GetStringValue()}` from `r.env.JobVars` with no `Masked` field set at all: [3](#0-2) 

The nested step-runner instance therefore has no way to know which values are masked and cannot mask them in its own output. That output is stripped of its inner timestamp header by `innerstream.New` and re-emitted as plain body via `r.env.Stdout`/`Stderr`: [4](#0-3) 

This becomes the "concrete" builtin step's own stdout, which the *outer*, real step-runner instance re-stamps with a genuine, valid 28-byte header before it reaches Runner. Runner's `Logger.StepRunnerStream` classifies this as pre-stamped and, since `Timestamping` is on, passes it straight through the `passthrough` writer with no masking applied at all: [5](#0-4) 

This exact gap is what the shipped test documents as expected behavior ("pre-stamped passthrough does not mask (step-runner masked upstream)"): [6](#0-5) 

The invariant "masked values must never reach the trace unmasked regardless of framing" is violated because the masking responsibility was silently dropped one hop earlier (missing `Masked` propagation into `buildRunRequest`), and the consuming side (`StepRunnerStream`) has no independent verification — it unconditionally trusts anything with a valid-looking header.

### Impact Explanation
A masked CI/CD variable echoed by a `run:`-based step is written to the job's own trace log in cleartext, visible to anyone with access to that job's log (any pipeline author/maintainer able to trigger the job in that project). This is a masking-bypass secret disclosure scoped to the job's own project, matching the question's scoped impact.

### Likelihood Explanation
Fully attacker-controlled and trivially reproducible: any job defining a masked variable and a `run:` step that echoes it (e.g. `run: - script: echo "$MASKED_VAR"`) triggers this path with no forged bytes or special crafting required — the bug fires on ordinary variable interpolation, not on constructing a fake header. It requires `FF_USE_NATIVE_STEPS`/native-steps `run:` usage and `Timestamping` enabled (default in current tracing), both realistic configurations.

### Recommendation
In `functions/concrete/run/run_steps.go`'s `buildRunRequest`, forward the `Masked` flag for each variable to the nested `client.Variable{..., Masked: ...}` the same way `steps/steps.go`'s `addVariables` does, so the nested step-runner instance can mask matching secrets before they are written to `r.env.Stdout`/`Stderr`. As a defense-in-depth measure, `Logger.StepRunnerStream`'s passthrough path should not unconditionally skip Runner's own `maskPhrases`/token/url sanitizer chain — at minimum the masker should still scan pre-stamped bodies for known job masked-variable values even in passthrough mode, rather than relying solely on step-runner's own masking.

### Proof of Concept
Go unit test in `functions/concrete/run/run_steps_test.go`:
```go
func TestBuildRunRequest_ForwardsMaskedFlag(t *testing.T) {
    name, script := "step", "true"
    r := &Runner{
        config: &Config{ID: 42},
        env: &env.Env{
            WorkingDir: "/work",
            Env:        map[string]string{"PATH": "/usr/bin"},
            JobVars: map[string]*structpb.Value{
                "MASKED_KEY": structpb.NewStringValue("MASKED_VALUE"),
            },
        },
    }

    req, err := r.buildRunRequest([]schema.Step{{Name: &name, Script: &script}})
    require.NoError(t, err)

    for _, v := range req.Variables {
        if v.Key == "MASKED_KEY" {
            assert.True(t, v.Masked, "masked job variables must be forwarded as Masked to the nested step-runner dispatch")
        }
    }
}
```
Expected today: the assertion fails (`v.Masked` is `false`), proving the flag is dropped. End-to-end PoC job: define a masked variable `MASKED_KEY`, add a `run:` step `echo "$MASKED_KEY"`, run the job, and assert the resulting trace via `common/buildtest/masking.go`-style helper `assert.NotContains(t, traceContents, "MASKED_VALUE")` — expected to fail on the current code, confirming cleartext leakage.

func (r *Runner) runUserSteps(ctx context.Context, steps []schema.Step) error {
	req, err := r.buildRunRequest(steps)
	if err != nil {
		return err
	}

	dialer := unixSocketDialer(socketPath())
	cli, err := extended.New(dialer)
	if err != nil {
		return fmt.Errorf("dialing step-runner: %w", err)
	}
	//nolint:errcheck
	defer cli.CloseConn()

	splitter := innerstream.New(r.env.Stdout, r.env.Stderr)
	out := &extended.FollowOutput{Logs: splitter}

	status, err := cli.RunAndFollow(ctx, req, out)
	// Flush any line whose continuation marker we never saw.
	flushErr := splitter.Flush()

	return interpretRunResult(status, err, flushErr)
}

func (r *Runner) buildRunRequest(steps []schema.Step) (*client.RunRequest, error) {
	stepsYAML, err := buildStepsYAML(steps)
	if err != nil {
		return nil, fmt.Errorf("marshalling user steps: %w", err)
	}

	// Merge Env and GitLabEnv with the same precedence as env.Command, so the
	// nested job sees $GITLAB_ENV (and any KEY=VALUE lines written by earlier
	// stages) just like a local stage would.
	mergedEnv := maps.Clone(r.env.Env)
	maps.Copy(mergedEnv, r.env.GitLabEnv)

	variables := make([]client.Variable, 0, len(r.env.JobVars))
	for key, value := range r.env.JobVars {
		variables = append(variables, client.Variable{Key: key, Value: value.GetStringValue()})
	}

	req := &client.RunRequest{
		Id:        strconv.FormatInt(r.config.ID, 10) + "-run",
		WorkDir:   r.env.WorkingDir,
		BuildDir:  r.env.WorkingDir,
		Env:       mergedEnv,
		Variables: variables,
		Steps:     stepsYAML,
	}
