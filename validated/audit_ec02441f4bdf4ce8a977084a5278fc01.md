### Title
Donated withdraw-receipt strategy tokens are double-counted as CDO NAV, inflating tranche prices and stealing other LPs' funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The bug class in the external report is a single attacker-supplied artifact being interpreted in two different security contexts (a file served as both data and executable HTML/JS). The analog in `idle-tranches` is that the ERC20 `strategyToken` is interpreted as two different things depending on who holds it: a withdraw receipt when held by a user (`requestWithdraw` mints receipt tokens and records `withdrawsRequestsByEpoch`), and live NAV backing when held by the CDO (`getContractValue` counts `_contractTokenBalance(strategyToken)`). Because receipts are freely transferable ERC20 tokens and `_skimDonatedAssets` only skims `token` (underlying), an attacker can donate receipt tokens back to the CDO and have one economic claim counted twice — once as inflated CDO NAV and once as borrower-funded `pendingWithdraws`.

### Finding Description
In `IdleCreditVault.requestWithdraw`, the strategy burns `_principal` strategy tokens from the CDO but mints `_amount` (principal + interest) strategy tokens to the user as a receipt, and adds `_amount` to `pendingWithdraws` (contracts/strategies/idle/IdleCreditVault.sol:272-280). These receipt tokens are the same `strategyToken` ERC20 whose balance at the CDO defines `getContractValue()` — the same accounting variable that prices AA/BB tranches via `_virtualPriceAux` (contracts/IdleCDOCreditVault.sol:227,336).

`_skimDonatedAssets` in `IdleCDOEpochVariant` transfers only `token` (the underlying) to `feeReceiver` — it does not touch `strategyToken` (contracts/IdleCDOEpochVariant.sol:794-796). There is no mechanism to distinguish a "real" strategy-token balance from donated receipt tokens.

Attack sequence (buffer phase, fixed-APR mode, non-programmable):
1. Attacker deposits AA (or BB), holding tranche tokens alongside a victim LP.
2. Attacker calls `requestWithdraw` for part of their position. The strategy burns `principal` from the CDO, mints `_amount` (principal + fixed-epoch interest) receipt tokens to the attacker, and records `pendingWithdraws += _amount`.
3. Attacker `transfer`s the receipt tokens directly to the CDO contract address.
4. `getContractValue()` now includes the donated `_amount`, so `_updateAccounting` / `_tranchePrice` treat it as live NAV — even though `_amount` is still owed by the borrower as `pendingWithdraws` and will be funded again at `stopEpoch`. The same claim is counted twice.
5. Attacker calls `withdraw` on their remaining tranche tokens at the inflated price, extracting more underlying than fair share.

After the donation the attacker's recorded claim (`withdrawsRequests`, `withdrawsRequestsByEpoch`) still exists, but `claimWithdrawRequest` will revert at `_burn(_user, amount)` because the attacker no longer holds the receipt tokens — so the borrower-funded repayment stays locked in the strategy as unclaimable value, which is precisely what makes the CDO's donated-token NAV a pure double count rather than a transfer of the claim.

### Impact Explanation
Direct theft / insolvency: every donated receipt unit inflates tranche prices by ~1 underlying unit while creating no new backing (the backing is the same `pendingWithdraws` obligation that already funded the receipt). The attacker redeems remaining tranches at the inflated price; the loss is socialized onto remaining LPs, whose tranches become undercollateralized — the last withdrawer is insolvent up to the donated amount (bounded only by the attacker's own deposit size, i.e., attacker profit ≈ donation amount × victim share). Quantified: donating a receipt worth `R` steals `R` from the pool net of the attacker's own residual claim.

### Likelihood Explanation
Requires only an unprivileged KYC'd tranche holder (`isWalletAllowed` gate) and two transactions outside a running epoch: `requestWithdraw` then an ERC20 `transfer` of `strategyToken` to the CDO. No privileged cooperation, no oracle, no flash loan. The guards that exist — `_skimDonatedAssets` (underlying only), `_checkSameBlock`, `_checkDefault`, KYC — do not cover `strategyToken` transfers to the CDO. The main residual uncertainty is whether any deployed `strategyToken` imposes transfer restrictions; `canTransfer` is deprecated and the code mints receipts directly to user wallets, so transfers appear unrestricted.

### Recommendation
Exclude non-CDO-minted strategy tokens from NAV: track the CDO's legitimate strategy-token balance in a state variable updated only by `deposit`/`mintStrategyTokens`/`_burn` flows, or skim donated `strategyToken` the same way underlying donations are skimmed (e.g., burn them via a strategy-side sink so the corresponding `pendingWithdraws` claim is also voided). Alternatively, make receipt tokens non-transferable, or burn receipt tokens and track claims purely in `withdrawsRequestsByEpoch`.

// Setup: victim and attacker each deposit 10_000e6 AA.
uint256 attackerTranche = IERC20(AAtranche).balanceOf(attacker);

// 1) Attacker requests withdraw of half their tranches.
vm.prank(attacker);
uint256 receipt = cdoEpoch.requestWithdraw(attackerTranche / 2, AAtranche);
// receipt > principal (includes epoch interest); pendingWithdraws += receipt

// 3) Attacker withdraws remaining tranches at inflated price.

vm.prank(attacker);
