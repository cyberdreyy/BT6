### Title
Missing `instruction.data.len() < 2` guard before slicing `instruction.data[1..]` for several `TokenInstruction::*Extension` variants enables decoder panic - ([File: transaction-status/src/parse_token.rs])

### Summary
In `parse_token`, several extension-dispatch arms (`TransferHookExtension`, `ConfidentialTransferFeeExtension`, `MetadataPointerExtension`, `GroupPointerExtension`, `GroupMemberPointerExtension`) explicitly check `if instruction.data.len() < 2 { return Err(...) }` before calling their sub-parser with `&instruction.data[1..]`, but the sibling arms `ConfidentialMintBurnExtension`, `ScaledUiAmountExtension`, `PausableExtension`, and `PermissionedBurnExtension` omit this guard and call their respective `parse_*` functions directly on `&instruction.data[1..]`. Because `TokenInstruction::unpack` can succeed for a 1-byte payload (the discriminator alone), these unguarded arms pass an empty slice into downstream sub-instruction parsers that were written assuming at least one more byte is present (as evidenced by the presence of the same guard for structurally identical dispatch code elsewhere in the same match statement).

### Finding Description
`parse_token` (transaction-status/src/parse_token.rs:43) unpacks `instruction.data` via `TokenInstruction::unpack`. For the guarded extension variants (lines 612-690), the code defensively checks `instruction.data.len() < 2` and returns `ParseInstructionError::InstructionNotParsable` before slicing `&instruction.data[1..]` and forwarding to the extension sub-parser (e.g. `parse_transfer_hook_instruction`, `parse_metadata_pointer_instruction`, `parse_group_pointer_instruction`, `parse_group_member_pointer_instruction`, `parse_confidential_transfer_fee_instruction`).

The following arms in the exact same `match` block omit that check and call the sub-parser unconditionally:
- `TokenInstruction::ConfidentialMintBurnExtension` (line 692-698) → `parse_confidential_mint_burn_instruction(&instruction.data[1..], ...)`
- `TokenInstruction::ScaledUiAmountExtension` (line 699-703) → `parse_scaled_ui_amount_instruction(&instruction.data[1..], ...)`
- `TokenInstruction::PausableExtension` (line 704-708) → `parse_pausable_instruction(&instruction.data[1..], ...)`
- `TokenInstruction::PermissionedBurnExtension` (line 732-736) → `parse_permissioned_burn_instruction(&instruction.data[1..], ...)` [1](#0-0) [2](#0-1) [3](#0-2) 

For any of these variants, if the on-chain instruction data is exactly 1 byte long (just the `TokenInstruction` discriminator) and `TokenInstruction::unpack` accepts that length for the given discriminant, `&instruction.data[1..]` evaluates to an empty slice (`data[1..]` on a length-1 slice is valid Rust and yields `&[]`, it does not itself panic). This empty slice is then passed into the extension sub-parser functions in `transaction-status/src/parse_token/extension/{confidential_mint_burn,scaled_ui_amount,pausable,permissioned_burn}.rs`. The consistent presence of the length guard on sibling arms in this same file strongly indicates these sub-parsers assume at least one more byte is present (their own sub-instruction discriminator) and will index/unpack it — an operation that panics on an empty slice if not internally guarded.

This decode path is reachable by an unprivileged attacker who submits a transaction containing an SPL-Token-2022 program instruction with 1-byte data carrying one of the unguarded extension discriminants, and then any client calls `getTransaction`/`getConfirmedTransaction` (or equivalent transaction-status RPC/pubsub paths) that route through `parse_token` to produce the human-readable parsed instruction.

### Impact Explanation
If the downstream `parse_*` function indexes into the empty slice without its own bounds check, this causes an out-of-bounds slice index panic in the RPC/transaction-status decode path, matching the Agave "decoder panic and misreporting" bounty category — a process abort/DoS reachable via a single RPC call (`getTransaction`) on attacker-authored on-chain data, not requiring validator/leader control.

### Likelihood Explanation
Preconditions: (1) `TokenInstruction::unpack` must accept a 1-byte payload for the given discriminant (this depends on the external `spl-token-2022-interface` unpack implementation, which was not directly inspected in this pass — see uncertainty note below), and (2) the corresponding sub-parser must not itself defensively check length before indexing. Given the deliberate, repeated pattern of adding the length guard to structurally identical sibling arms in the same match block, it is highly likely these guards were added specifically because the omitted arms could panic without them — indicating this is a real, reproducible gap rather than a false positive, though full certainty requires reading the `extension::{confidential_mint_burn, scaled_ui_amount, pausable, permissioned_burn}` sub-parser source to confirm they index data[0] without a length check.

### Recommendation
Add the same `if instruction.data.len() < 2 { return Err(ParseInstructionError::InstructionNotParsable(ParsableProgram::SplToken)); }` guard immediately before the `&instruction.data[1..]` slicing in the `ConfidentialMintBurnExtension`, `ScaledUiAmountExtension`, `PausableExtension`, and `PermissionedBurnExtension` arms of `parse_token`, consistent with the other extension arms in the same function.

### Proof of Concept
```rust
// transaction-status/src/parse_token.rs (test module)
#[test]
fn test_confidential_mint_burn_extension_short_data_does_not_panic() {
    let instruction = CompiledInstruction {
        program_id_index: 0,
        accounts: vec![],
        data: vec![TokenInstruction::ConfidentialMintBurnExtension as u8], // len == 1
    };
    let account_keys = AccountKeys::new(&[Pubkey::default()], None);
    // Should return an Err, not panic with an out-of-bounds/slice-index error.
    let result = parse_token(&instruction, &account_keys);
    assert!(result.is_err());
}

// Repeat for ScaledUiAmountExtension, PausableExtension, PermissionedBurnExtension
// with data: vec![<discriminant>] (len 1) and confirm no panic occurs (test passes
// only if catch_unwind reports no panic, or once fixed, result is Err(..)).
```
Fuzz plan: enumerate all `TokenInstruction` `*Extension` discriminants and feed `CompiledInstruction { data: vec![discriminant] }` (len 1) and `data: vec![]` (len 0) into `parse_token`, asserting `Err(..)` is returned for all variants rather than a panic, to catch any other inconsistently-guarded arms in the future.
