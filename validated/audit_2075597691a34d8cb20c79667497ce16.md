### Title
Unprivileged front-running of the deterministic lockup account address in `LockupFactory::create` allows a lockup to be deployed with schedule parameters its rightful grantor never chose - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the lockup contract's account name deterministically from `sha256(owner_account_id)` alone, and can be called by any account that attaches `MIN_ATTACHED_BALANCE`, with no check that the caller is the NEAR Foundation or any authorized grantor. An attacker can therefore call `create` first for a victim's `owner_account_id`, choosing an arbitrary `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration` and `staking_pool_whitelist_account_id`, permanently occupying the address the real grantor would have used and locking in attacker-chosen terms.

### Finding Description
The broken binding: `lockup_account_id = f(owner_account_id)` should be created **only** by the grantor with the grantor's chosen `(lockup_duration, lockup_timestamp, vesting_schedule, release_duration, staking_pool_whitelist_account_id)`; instead `create(...)` lets `predecessor_account_id == ANY` supply all of those fields: [1](#0-0) [2](#0-1) 

`create` only asserts `env::attached_deposit() >= MIN_ATTACHED_BALANCE`; it never checks `env::predecessor_account_id()` against `self.foundation_account_id` or anything else, so any unprivileged account can invoke it. The target account name is computed purely as `sha256(owner_account_id)[..20] + "." + current_account_id` — it depends only on the (attacker-suppliable) `owner_account_id`, not on the caller or any of the schedule fields: [3](#0-2) 

Because NEAR account names are globally unique, whichever party's `create` call executes first wins that deterministic address. An attacker can front-run the real grantor by calling `create` with `owner_account_id = <victim>`, attaching only the `MIN_ATTACHED_BALANCE` (3.5 NEAR) from their own funds, and freely choosing `lockup_duration`, `lockup_timestamp`, `vesting_schedule` (or a hidden `VestingHash`), `release_duration`, and `staking_pool_whitelist_account_id` (e.g. pointing at a staking-pool whitelist contract the attacker controls): [4](#0-3) [5](#0-4) 

The resulting lockup contract lists the victim as `owner_account_id`, but every schedule/whitelist field is attacker-chosen. When the real grantor later attempts to `create` the legitimate lockup for the same `owner_account_id` (with the intended full deposit), the `create_account()` action in the batched promise fails because the account already exists; the whole batch fails atomically, and `on_lockup_create` refunds the deposit to the real grantor: [6](#0-5) 

So the legitimate deposit is not stolen, but the deterministic lockup address for that `owner_account_id` is now permanently squatted with attacker-chosen `release_duration`/`lockup_duration`/`vesting_schedule`/whitelist — the address can never again be used for a correctly-parameterized lockup through this factory. No guard (`assert_owner`, `assert_called_by_foundation`, `assert_self`, etc.) exists on `create` to prevent this, and none of the listed invariant checks apply because `create` has no caller restriction at all.

Note: in this codebase's `create`, `transfers_information` is hardcoded to `TransfersInformation::TransfersEnabled` with a fixed constant timestamp — it is not attacker-selectable, so the specific "naming a transfer poll contract" variant described in the question does not apply here; the exploitable surface is the full set of schedule/whitelist parameters plus the deterministic-address squat.

### Impact Explanation
This falls under the Critical category explicitly listed: "a lockup deployed with parameters its rightful creator never chose." The victim's canonical lockup address ends up permanently bound to attacker-chosen `lockup_duration`, `release_duration`, `vesting_schedule`, and `staking_pool_whitelist_account_id` (which can point to a staking-pool whitelist the attacker controls), while the real grantor can never deploy the intended lockup at that address again through the factory. This is repeatable against any `owner_account_id` the attacker wants to target, for the cost of `MIN_ATTACHED_BALANCE` per victim account, and blocks/mis-parameterizes the grant flow for that identity indefinitely.

### Likelihood Explanation
No privileged role is required — `create` is `#[payable]` and open to any predecessor account. The attacker only needs to know (or predict) the intended grant recipient's `owner_account_id` and front-run the Foundation's `create` call with `MIN_ATTACHED_BALANCE` (3.5 NEAR). Since account names for lockups are deterministic and public knowledge (`sha256(owner_account_id)` + factory account), this is trivially computable off-chain before the real grant is even issued, making the attack fully feasible and cheap to repeat across many target accounts.

### Recommendation
Restrict `create` to be callable only by `self.foundation_account_id` (or another explicitly authorized grantor list), analogous to `assert_called_by_foundation` patterns used elsewhere in the repo, so that unprivileged accounts cannot pre-register lockup addresses for arbitrary `owner_account_id`s with attacker-chosen schedules.

```rust
// cargo test in lockup-factory
#[test]
fn test_frontrun_lockup_address_squat() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());
    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    // Attacker (not the foundation, not the victim) calls create() naming the victim
    // as owner_account_id, with attacker-chosen (malicious) schedule fields.
    context.predecessor_account_id = String::from("attacker.near");
    context.attached_deposit = MIN_ATTACHED_BALANCE; // attacker's own minimal funds
    testing_env!(context.clone());

    let malicious_release_duration: WrappedDuration = 1.into(); // near-instant release
    contract.create(
        account_tokens_owner(),          // victim's account id
        1.into(),                        // malicious lockup_duration
        None,
        None,
        Some(malicious_release_duration),
        Some(custom_whitelist_account_id()), // attacker-controlled whitelist
    );
    // Assert: lockup_account_id == sha256(account_tokens_owner()) + "." + factory
    // is now occupied with attacker-chosen terms, before the real grantor ever calls create.

    // Real grantor later attempts the legitimate create() for the same owner:
    context.predecessor_account_id = String::from(account_tokens_owner_grantor());
    context.attached_deposit = ntoy(1_000_000); // real grant amount
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), LOCKUP_DURATION.into(), None, None, None, None);
    // In a real environment this create_account() action fails because the account
    // already exists; on_lockup_create refunds the grantor but the squatted address
    // permanently retains the attacker's chosen schedule -- demonstrating the broken
    // binding: lockup_account_id(owner) params == grantor's intended params.
}
```

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
