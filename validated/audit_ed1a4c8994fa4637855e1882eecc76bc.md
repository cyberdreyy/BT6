### Title
Unescaped attacker-controlled variable name flows through `TmpFile` into `%q`-quoted shell text, enabling command substitution injection - (File: shells/bash.go)

### Summary
`BashWriter.TmpFile` builds a temp-file path by directly joining the caller-supplied `name` into `TemporaryPath` with no shell-safety sanitization, and its main caller (`Variable`) embeds the resulting path into generated bash using Go's `%q` format verb rather than proper shell escaping. Because `%q` (Go's quoting) does not neutralize `$()`/backtick command substitution inside double quotes, an attacker who controls a `File`-type CI variable's key can inject arbitrary shell commands that execute when the generated job script is `eval`'d.

### Finding Description
`TmpFile` performs no escaping at all: [1](#0-0) 

Its most exploitable caller is `Variable`, which for `File`-type variables builds the temp path from the attacker-controlled variable `Key` and writes it into the script using `%q`, not `b.escape`: [2](#0-1) 

`b.escape` (used correctly for `variable.Key` as the export identifier and for `variable.Value`) calls a real POSIX-safe shell escaper: [3](#0-2) 

But `variableFile := b.TmpFile(variable.Key)` is instead inserted via `fmt`'s `%q` verb in `Linef`, e.g. `b.Linef("export %s=%q", b.escape(variable.Key), variableFile)`. Go's `%q` produces a double-quoted Go-string literal: it backslash-escapes quotes, backslashes and non-printable characters, but it does **not** escape `$` or backtick characters, which remain command-substitution metacharacters inside bash double quotes. Since `TmpFile` never strips or rejects such characters from `name` (it only does `path.Join` + `Absolute`, which just checks for an absolute-path prefix), a `Key` such as `` `touch /tmp/pwned` `` or `$(id>/tmp/pwned)` survives untouched into the constructed path and is written verbatim between the double quotes generated by `%q`. When the runner's generated script is later executed (`eval` in `Finish`), bash performs command substitution on that embedded payload before the `export`/`printf` lines even run.

The left-hand side of the `export` (the variable name itself) is safely single-quoted via `b.escape`, but that only protects the environment-variable identifier — it does not protect the temp-file path string used as the value/target on the right-hand side, which is the vector actually under attacker control here.

### Impact Explanation
Command execution occurs inside the job's shell context when the generated script is evaluated, at the point the temp variable-file export/write statements run — before the job's own script body executes. This lets an attacker who can define a `File`-type CI/CD variable smuggle a runner-context shell command that runs with the same privileges as the rest of the job script, i.e. stronger-context command execution beyond simply setting an environment variable value, matching the scoped "stronger-context command execution" impact.

### Likelihood Explanation
Precondition: the attacker needs to control a `File`-type variable's `Key` value that reaches the runner without the coordinator enforcing strict identifier validation (e.g., via dynamically generated/child-pipeline variables, trigger-API-supplied variables, or other paths that don't pass through GitLab Rails' standard `^[A-Za-z_][A-Za-z0-9_]*$` key validation). Where such a path exists, the bug is deterministic and repeatable: any `Key` containing backticks or `$(...)` will be command-substituted every time the generated bash script's `Variable()` block is emitted and evaluated.

### Recommendation
Make `TmpFile` (and its PowerShell equivalent) itself responsible for rejecting/sanitizing unsafe characters in `name`, or ensure every caller quotes the returned path with the shell's own escaping function (`b.escape`) instead of Go's `%q`. Specifically, replace `b.Linef("printf '%%s' %s > %q", ..., variableFile)` and `b.Linef("export %s=%q", ..., variableFile)` with `b.escape(variableFile)`, and audit other `TmpFile` callers (`DotEnvVariables`, `SourceEnv`, `MkTmpDir`) for the same `%q`/`%s`-vs-`escape` inconsistency.

### Proof of Concept
Go unit test idea in `shells/bash_test.go`:
```go
func TestBashWriter_VariableFileKeyInjection(t *testing.T) {
    w := NewBashWriter(&common.Build{...}, "bash")
    w.Variable(spec.Variable{
        Key:   "SAFE`touch /tmp/pwned`",
        Value: "secret",
        File:  true,
    })
    script := w.String()
    // Assert the raw backtick payload is NOT present unescaped in a
    // double-quoted context, i.e. it must be neutralized (single-quoted
    // or backslash-escaped) rather than passed through %q verbatim.
    assert.NotContains(t, script, "`touch /tmp/pwned`")
}
```
Executing the generated script in bash (`bash -c "$(script)"`) in a sandbox and checking for the creation of `/tmp/pwned` demonstrates the injection concretely.

```go
func (b *BashWriter) Variable(variable spec.Variable) {
	if variable.File {
		variableFile := b.TmpFile(variable.Key)
		b.Linef("mkdir -p %q", helpers.ToSlash(b.TemporaryPath))
		b.Linef("printf '%%s' %s > %q", b.escape(variable.Value), variableFile)
		b.Linef("export %s=%q", b.escape(variable.Key), variableFile)
	} else {
		if b.isTmpFile(variable.Value) {
			variable.Value = b.cleanPath(variable.Value)
		}
		b.Linef("export %s=%s", b.escape(variable.Key), b.escape(variable.Value))
	}
}
```
