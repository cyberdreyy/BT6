### Title
Signer equivocation lets one signer's weight be double-counted toward both accept and reject tallies — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
In `StackerDBListener`'s block-status tracking, an `Accepted` `BlockResponse` is de-duplicated against `block.gathered_signatures` (a map populated only by the Accept branch), while a `Rejected` `BlockResponse` is de-duplicated against the shared `block.responded_signers` set. Because the two branches use different gating structures for the same underlying "has this signer already voted?" question, a single signer that first rejects and then accepts (or the reverse, depending on code path) can have its weight added to `total_weight_approved` even though it is already counted in `total_weight_rejected`, breaking the invariant that a signer's weight can only count toward one side of the vote.

### Finding Description
`StackerDBListenerComms::blocks` stores a `BlockStatus` per `signer_signature_hash` containing `gathered_signatures: HashMap<slot_id, signature>`, `responded_signers: HashSet<slot_id>`, `total_weight_approved`, and `total_weight_rejected` [1](#0-0) .

When an `Accepted` message arrives, the weight is only added if the slot is **not already in `gathered_signatures`**:
```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
``` [2](#0-1) 

When a `Rejected` message arrives, the weight is only added if the slot is **not already in `responded_signers`**:
```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
``` [3](#0-2) 

If the same signer slot first sends `Rejected` (setting `responded_signers` and incrementing `total_weight_rejected`) and later sends `Accepted` for the same `signer_signature_hash`, the `Accepted` branch's guard (`gathered_signatures.contains_key`) is still `false` — because `gathered_signatures` is only ever populated on the Accept path — so the signer's weight is *also* added to `total_weight_approved`. The same slot's weight is now counted on both sides of the tally simultaneously, i.e. `total_weight_approved + total_weight_rejected` can exceed what a set of distinct, single-voting signers should be able to produce. This is exactly the class of "aggregated-weight vs verified-accepts" mismatch called out as in-scope: a signer's rejection gets effectively "recounted" as (also) an acceptance in the running tally used to decide whether the miner should push the block.

This directly parallels the Lighthouse "seen caches" race: two separate data structures (`gathered_signatures` map and `responded_signers` set) are each used as the sole gate for "have we already counted this voter," but they are not kept consistent with each other across the two response types, so the dedup guarantee that holds within one message type does not hold across both.

### Impact Explanation
This breaks the equality that the miner's threshold decision (`total_weight_approved >= self.weight_threshold` at `signer_coordinator.rs:541` and the rejection check at `signer_coordinator.rs:509-513`) relies on: that no single signer's weight can be simultaneously present in the approval and rejection weight pools. A single misbehaving (or buggy/racing) signer that flips its vote can inflate `total_weight_approved` without ever being removed from `total_weight_rejected`, and vice versa. In borderline scenarios (weight distribution near the 70%/30% thresholds), this lets the miner's local `SignerCoordinator` reach a decision (accept-and-push, or reject-and-retry) that does not reflect a real 70%/30% supermajority of distinct signers, i.e. a rejection being effectively recounted toward acceptance in the aggregated tally used by the miner to decide whether to broadcast the block. This maps to the "rejection recounted as an accept" impact category.

### Likelihood Explanation
Reaching this requires only one signer (or a compromised/buggy node under one signer's control) to emit both an `Accepted` and a `Rejected` `BlockResponse` for the same `signer_signature_hash` — no majority collusion, no other party's key, and no auth-token access is needed. The `stacks-signer` reference implementation itself has code paths where a signer can transition between decisions for the same block hash across different messages over time (e.g., re-evaluation after a proposal is re-sent, or `handle_block_signature`'s outdated-peer fallback path) [4](#0-3) , though whether the reference signer itself would naturally emit both an Accept and Reject for the identical `signer_signature_hash` is not fully confirmed from the code inspected — a non-reference or malicious signer implementation could trivially do so. The consequence of a successful flip is bounded by weight (a single signer's weight, not enough alone to flip the outcome except near threshold boundaries), so likelihood of a security-relevant outcome is moderate rather than high.

### Recommendation
Use a single, shared per-slot "already responded" gate that records *which* verdict (`Accepted` or `Rejected`) was recorded, and refuse to let the aggregate weight for a slot appear in both `total_weight_approved` and `total_weight_rejected`. Concretely, in `stackerdb_listener.rs`, check `block.responded_signers` (or a unified `slot_id -> Verdict` map) in the `Accepted` branch instead of `gathered_signatures`, and if a slot has already voted the opposite way, either ignore the later message or subtract the previous weight before adding the new one, to preserve the invariant that a signer's weight counts toward exactly one side.

### Proof of Concept
1. Miner proposes a block; `StackerDBListener` creates `BlockStatus` for `signer_signature_hash = H`.
2. Signer S (slot `k`, weight `w`) broadcasts `BlockResponse::Rejected` for `H`. `responded_signers.insert(k)` succeeds → `total_weight_rejected += w`.
3. Signer S later broadcasts `BlockResponse::Accepted` for the same `H` (e.g., after re-evaluating a re-proposed block, or via a malicious/non-conforming signer process).
4. In the `Accepted` handler, `block.gathered_signatures.contains_key(&k)` is `false` (this map was never touched by the Reject path), so `total_weight_approved += w` is executed.
5. Result: `total_weight_approved` and `total_weight_rejected` both include weight `w` from the same signer `k`, violating the intended one-vote-per-signer accounting that `SignerCoordinator` relies on for its accept/reject threshold decision [5](#0-4) .
