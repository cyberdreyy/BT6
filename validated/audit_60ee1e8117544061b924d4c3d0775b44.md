### Title
Signer can be induced to sign two conflicting tenure-change blocks for the same tenure when `get_tenure_tip` errors during the pre-commit conflict check - ([File: stacks-signer/src/v0/signer.rs])

### Summary
`handle_block_pre_commit`'s same-tenure conflict guard treats an RPC failure from the local stacks-node (`get_tenure_tip`) as "tenure unconfirmed" and falls through to sign, rather than refusing to sign. Combined with `SortitionsView::validate_tenure_change_payload` (v1) only detecting duplicate tenure-change blocks via `get_last_globally_accepted_block` (missing `LocallyAccepted` blocks) at proposal time only, a single malicious miner can get a signer to place a second, conflicting signature on a different tenure-change block for a tenure it has already locally accepted a block for.

### Finding Description
The Ladle-analog constraint here is "only one tenure-change (`BlockFound`) block may ever be signed per tenure" — the signer-protocol equivalent of "only one Join Ether per batch." This is enforced in three places, and the report's bug class ("implicit constraint enforced only at one layer, not defense-in-depth throughout") shows up as a real gap between them:

1. At proposal time, `SortitionsView::validate_tenure_change_payload` (v1) rejects a duplicate tenure-change block only if `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` returns a hit [1](#0-0) . This only checks `BlockState::GloballyAccepted`, unlike the v2 equivalent, which explicitly also counts `LocallyAccepted` blocks via `get_last_signed_block`, with the comment "Only blocks we have signed (locally or globally accepted) count here" [2](#0-1) . So under v1, a competing tenure-change block for the same tenure passes proposal-time checks as long as the signer's earlier block for that tenure is only `LocallyAccepted` (signed but not yet observed globally accepted).
2. This proposal-time duplicate check is never re-run at validate-ok or at signing time, per the documented design [3](#0-2) ; the only remaining safety net is the conflict check inside `handle_block_pre_commit`.
3. That final safety net, `get_signed_conflicts`, does correctly return same-tenure `LocallyAccepted` blocks as conflicts [4](#0-3) . But when a same-tenure conflict is found and no reorg permit stands, the code queries the node's tenure tip and only refuses to sign if that RPC call *succeeds* and reports a height at or above the proposal: [5](#0-4) 

If `stacks_client.get_tenure_tip(...)` returns `Err` — e.g. because the signer's own node has not yet processed/relayed the earlier locally-accepted block for that tenure (a scenario the code and comments elsewhere explicitly acknowledge: "the signer DB can be out-of-sync with the node" [6](#0-5) ) — the code only logs a warning ("Treating the tenure as unconfirmed") and falls through. Immediately after, if no conflict "still blocks," the code proceeds straight to `mark_locally_accepted` and signs: [7](#0-6) 

So the only thing standing between "sign one tenure-change block" and "sign two conflicting tenure-change blocks for the same tenure" is whether the node's `/v3/tenures/tip`-style RPC happens to already reflect the first block at the moment the second reaches pre-commit threshold — a timing/availability condition entirely under the control of network conditions and, ultimately, exploitable by a miner who races two competing tenure-start proposals.

### Impact Explanation
This breaks the Critical-tier invariant "a signer signing an invalid/non-canonical/conflicting block" — specifically, it is a same-signer equivocation: the signer key ends up on two different, height-conflicting tenure-start blocks for the same tenure. Such double-signing by even a fraction of signers materially undermines the safety assumptions of the signer set (a block that should be uniquely identified per tenure now has two independently signed candidates), and can contribute to competing candidate blocks and undefined behavior in the same way the referenced Ladle report describes: violating the implicit "exactly one Join-Ether-equivalent op per batch" invariant leads to failing/undefined protocol behavior, here manifesting as broken block-uniqueness-per-tenure guarantees.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires (a) a signer that already locally-accepted a tenure-change block for a tenure but whose own node has not yet observed/relayed it, and (b) a second competing tenure-change proposal for the same tenure reaching pre-commit threshold before the node's tenure-tip view catches up, and (c) the RPC call to fail/return not-found rather than definitively resolving. All of these are node-signer desync conditions that are plausible in ordinary operation (node restart, catching-up node, network delay in relaying the first block) and can be provoked/timed by a single malicious miner proposing a duplicate tenure-start block quickly, without requiring collusion from a majority of signers.

### Recommendation
Treat an RPC failure/ambiguous result from `get_tenure_tip` in the same-tenure conflict branch of `handle_block_pre_commit` as "refuse to sign" (fail closed) rather than "treat as unconfirmed and sign" (fail open), mirroring the fail-safe default used elsewhere for cross-tenure conflicts. Additionally, align v1's `validate_tenure_change_payload` duplicate check with v2's: use `get_last_signed_block` (covers both `LocallyAccepted` and `GloballyAccepted`) instead of `get_last_globally_accepted_block`, so the early proposal-time rejection catches this case before it ever reaches the pre-commit race window.

### Proof of Concept
1. Malicious/faulty miner proposes tenure-change block `A` for tenure `T` at height `h`. A supermajority of signers pre-commit and reach threshold; each such signer calls `handle_block_pre_commit`, marks `A` `LocallyAccepted` (`signed_self` set) and broadcasts its acceptance signature (`stacks-signer/src/v0/signer.rs:1467-1478`), but block `A` has not yet been relayed to / processed by the signers' own stacks-node (so `get_tenure_tip(T)` still errors).
2. Same miner immediately proposes a different tenure-change block `B` for the same tenure `T` (same `consensus_hash`), e.g. with a different transaction set. Because a v1 signer's `validate_tenure_change_payload` only checks `get_last_globally_accepted_block`, and `A` is only `LocallyAccepted`, block `B` is not rejected as a duplicate at proposal time (`stacks-signer/src/chainstate/v1.rs:505-518`).
3. `B` proceeds through validation and pre-commit; when a supermajority pre-commits to `B`, `handle_block_pre_commit` finds `A` as a same-tenure conflict via `get_signed_conflicts`, calls `stacks_client.get_tenure_tip(T)`, which errors because the node still hasn't processed `A`.
4. Per `stacks-signer/src/v0/signer.rs:1436-1457`, the error path only logs and falls through; the signer proceeds to sign `B` (`stacks-signer/src/v0/signer.rs:1467-1478`), producing a second signature over a conflicting tenure-change block for tenure `T` — an equivocation.
