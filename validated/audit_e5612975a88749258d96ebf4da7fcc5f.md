## Title
Malicious Token-2022 transfer-hook mint can permanently block permissionless `handle_bankruptcy`, freezing bad-debt socialization for all depositors - (File: `programs/marginfi/src/instructions/marginfi_group/handle_bankruptcy.rs`)

### Summary
Any Token-2022 mint listed on a marginfi bank may carry a `TransferHook` extension whose hook program is invoked on *every* transfer of that mint, regardless of which accounts are the source/destination. `lending_pool_handle_bankruptcy` (and several other permissionless/critical maintenance paths) move tokens via `Bank::withdraw_spl_transfer`, which for Token-2022 mints calls `spl_token_2022::onchain::invoke_transfer_checked` [1](#0-0) , unconditionally executing the mint's registered transfer-hook program. Unlike `lending_pool_emissions_deposit`, which explicitly rejects hooked mints before transferring [2](#0-1) , `handle_bankruptcy` performs no such check. A hook program that reverts (permanently, or conditionally as a ransom/griefing mechanism) will cause the insurance-fund transfer inside `handle_bankruptcy` to always fail, making it impossible to ever discharge bad debt for that bank - an on-chain analog of the Augur `disavowCrowdsourcers`/ERC777-hook freeze.

### Finding Description
`lending_pool_handle_bankruptcy` is designed to be callable permissionlessly when a bank sets `PERMISSIONLESS_BAD_DEBT_SETTLEMENT_FLAG` [3](#0-2) . It resolves the bank's mint via `maybe_take_bank_mint` and, if the token program is Token-2022, moves funds from the insurance vault to the liquidity vault with `bank.withdraw_spl_transfer(...)` [4](#0-3) .

`withdraw_spl_transfer` for Token-2022 mints calls `spl_token_2022::onchain::invoke_transfer_checked`, which is the SPL client-side helper that automatically resolves and invokes the mint's `TransferHook` extra accounts and CPIs into the hook program's `Execute` instruction [1](#0-0) . This is the exact mechanism the repo's own test harness uses to exercise transfer-hook mints (`test_transfer_hook` program, `SupportedExtension::TransferHook` fixtures) [5](#0-4) [6](#0-5) , confirming hooked T22 mints are an intentionally supported bank asset type.

The codebase already recognizes that hooks are a hazard in at least one place: `lending_pool_emissions_deposit` explicitly checks `utils::has_transfer_hook` and `utils::nonzero_fee` and rejects hooked mints before transferring [2](#0-1) , using the helper defined at [7](#0-6) . No equivalent guard exists in `lending_pool_handle_bankruptcy`, `lending_pool_collect_bank_fees`, or `lending_pool_withdraw_fees_permissionless`, all of which route through `withdraw_spl_transfer`/`deposit_spl_transfer` and can therefore invoke an attacker-controlled hook program.

Because the `TransferHook` extension's `program_id` can be set (and, unless authority is explicitly set to `None` at mint init, later updated) by an address that has no relationship to the marginfi group admin, an attacker who controls that authority can point the hook at a program that unconditionally reverts, or that reverts selectively (e.g., only once bad debt has accrued, to extract a ransom). Every call to `handle_bankruptcy` for that bank will then fail, exactly mirroring the Augur report's mechanism: a token-transfer side-effect hook, controlled by a party that is not the protocol admin, is exploited to block a critical, otherwise-permissionless cleanup instruction that other users depend on.

### Impact Explanation
Per the project's own documentation, failure to run `handle_bankruptcy` means "remaining depositors can never withdraw the whole balance in the bank" and "the last few depositors who try to withdraw will find there are not enough funds" [8](#0-7) . If the mint's hook is weaponized to always revert during the insurance-vault-to-liquidity-vault transfer, the bad debt can never be settled, the insurance fund allocated to that bank is effectively locked, and depositors permanently lose access to a proportional share of their funds. This is a durable, protocol-wide freeze with direct financial impact - not merely a griefing nuisance - since bankruptcy resolution is a one-way, mandatory step with no alternative code path (the bank cannot be "finalized" or otherwise unblocked without this transfer succeeding, similar to Augur markets being unable to finalize in a forking universe without `disavowCrowdsourcers` succeeding).

### Likelihood Explanation
Exploitability requires only that: (1) a bank exists for a Token-2022 mint with an active `TransferHook` extension, and (2) that hook's authority (not the marginfi admin) is or becomes malicious. Since marginfi explicitly supports Token-2022 hooked mints (as evidenced by the dedicated `test_transfer_hook` fixture program and test infrastructure) and guards against exactly this hazard in `lending_pool_emissions_deposit` but not in `handle_bankruptcy`/fee-withdrawal paths, this is a realistic gap rather than a purely theoretical one. Bankruptcy is described as "rare" but is the guaranteed correction mechanism once bad debt occurs, so any bank with a maliciously-hooked mint that accrues bad debt is guaranteed to hit this dead end.

### Recommendation
Apply the same defense used in `lending_pool_emissions_deposit` uniformly: reject (at bank-add/configure time) or explicitly disallow transfer-hook-bearing mints for any bank whose liquidity/insurance vault transfers are relied upon by permissionless/critical maintenance instructions, or refactor `handle_bankruptcy`/`collect_bank_fees`/`withdraw_fees_permissionless` to update all accounting state and mark the debt as settled *before* attempting the external transfer, and use a pull-style claim for the actual token movement so a reverting hook cannot block the state transition that other depositors depend on.

### Proof of Concept
1. Admin creates a bank backed by a Token-2022 mint with a `TransferHook` extension whose authority is attacker-controlled (or admin unknowingly lists such a mint, matching `SupportedExtension::TransferHook` test fixtures already used in this repo [6](#0-5) ) and enables `PERMISSIONLESS_BAD_DEBT_SETTLEMENT_FLAG`.
2. Attacker updates (or from the start configures) the hook program to unconditionally return an error from its `Execute` instruction handler (contrast with the benign no-op test hook at [9](#0-8) ).
3. A user's position becomes bankrupt (bad debt on that bank).
4. Any caller invokes `lending_pool_handle_bankruptcy`; the instruction reaches `bank.withdraw_spl_transfer(...)` [4](#0-3) , which triggers `invoke_transfer_checked` and CPIs into the malicious hook, reverting the entire transaction.
5. Every subsequent attempt to resolve this bank's bad debt fails identically; the bank remains permanently in a state where remaining depositors cannot fully withdraw, as documented in `BANKRUPTCY.md`.

```rust
/// Returns `true` if the given mint has an active transfer hook program.
/// If the hook is present but no program is active it would return false.
pub fn has_transfer_hook(mint_ai: AccountInfo) -> MarginfiResult<bool> {
    if mint_ai.owner.eq(&Token::id()) {
        return Ok(false);
    }

    let mint_data = mint_ai.try_borrow_data()?;
    let mint = StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

    if let Ok(hook) = mint.get_extension::<TransferHook>() {
        let program_id: Option<Pubkey> = Option::from(hook.program_id);
        return Ok(program_id.is_some());
    }

    Ok(false)
}
```
