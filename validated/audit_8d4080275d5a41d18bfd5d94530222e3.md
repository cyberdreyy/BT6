### Title
Stale per-epoch instant-withdraw records are reused by default finalization, letting a claimed receipt corrupt the recovery price and drain the recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` writes cumulative per-epoch accounting (`instantWithdrawsRequestsByEpoch[user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`), but the normal funded-claim path `claimInstantWithdrawRequest` never clears them — only the default path `_claimDefaultedInstantWithdrawRequest` does. If a borrower default is finalized in the same epoch after a user already claimed a funded instant receipt, `defaultPendingClaimBasis()` counts the already-paid ("freed") receipt again, inflating the recovery basis, diluting `defaultRecoveryPrice`, and — if the attacker opens a new instant request — paying the stale basis a second time out of `defaultRecoveryReserve`.

### Finding Description
Use-after-free analog: a receipt whose payout was already executed remains recorded in the per-epoch structures and is later consumed by a different accounting path.

1. `requestInstantWithdraw` mints a receipt and increments both per-epoch trackers (`IdleCreditVault.sol:366-374`):
   ```solidity
   instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
   instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
   pendingInstantWithdraws += _amount;
   ```
2. `claimInstantWithdrawRequest` (lines 380-393) burns `instantWithdrawsRequests[_user]`, zeroes the aggregate, and transfers funds via `_transferFundedClaim`. It never touches `instantWithdrawsRequestsByEpoch` or `instantWithdrawClaimsByEpoch`. Those are only cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 844-853), which runs solely after `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`.
3. `defaultPendingClaimBasis()` (lines 644-649) computes the default recovery basis as `pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`. A receipt that was already funded via `collectInstantWithdrawFunds` and already claimed still sits in `instantWithdrawClaimsByEpoch[epochNumber]`, so it is counted twice: once as paid cash, once as defaulted basis.
4. `finalizeDefaultRecovery` (lines 679-692) divides `reserveAmount * RECOVERY_FULL / totalBasis`. The phantom basis lowers `defaultRecoveryPrice` for every real claimant.
5. Double-spend path: `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`, subtracts it from `instantWithdrawsRequests[user]`, burns `_user` receipt tokens, and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from the reserve. If the attacker opens a fresh instant request of size `Z >= X` after finalization (`requestInstantWithdraw` is not gated on `defaultRecoveryFinalized` — only `requestWithdraw` is, lines 247-258), `instantWithdrawsRequests[user] = Z`, the stale `X` basis is paid out of the recovery reserve a second time, and the remaining `Z - X` then proceeds through the funded-claim path in the same call.

### Impact Explanation
Two concrete harms:

- **Recovery dilution / permanent freeze**: the phantom basis `X` inflates `totalBasis`, so `defaultRecoveryPrice` is smaller than warranted. Honest defaulted claimants (normal receipts and other instant receipts) each receive `claimBasis * price` with a depressed price; the reserve share earmarked for the attacker's phantom basis is never claimable (the attacker already got the underlying), so it sits locked in `defaultRecoveryReserve` forever. Quantified loss ≈ `X * trueRecoveryPrice` — bounded by the attacker's instant-withdraw size, which is bounded only by their deposit.
- **Direct theft**: if the attacker submits a new instant request `Z >= X` post-finalization, they are paid `X * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` for a receipt that was already settled, directly draining funds owed to honest defaulted claimants.

### Likelihood Explanation
Requirements: instant withdraws enabled (`allowInstantWithdraw`), an attacker request funded via `getInstantWithdrawFunds`/`collectInstantWithdrawFunds` while another user's instant request remains unfunded in the same epoch, the attacker claims before the epoch stops, and the borrower defaults at `stopEpoch`. None of this needs a privileged attacker — any KYC-passed lender can do it, and the borrower default is the honest-failure trigger the code explicitly supports (unfunded `pendingInstantWithdraws` at finalization is the designed-for case guarded by `defaultInstantWithdrawsFinalized`). Guards that fail to stop it: the funded-claim path does not check per-epoch staleness, and `requestInstantWithdraw` lacks the open-receipt check that `requestWithdraw` enforces post-default (line 249).

### Recommendation
- In `claimInstantWithdrawRequest`, clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` whenever a receipt is paid through the funded path (or track claims per epoch and subtract paid amounts).
- In `requestInstantWithdraw`, mirror the `requestWithdraw` guard: after `defaultRecoveryFinalized`, revert if stale `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` is non-zero, forcing users to resolve defaulted receipts before opening new ones.
- Alternatively, snapshot instant claim basis at funding time (`collectInstantWithdrawFunds`) so claimed amounts cannot linger in `instantWithdrawClaimsByEpoch`.

### Proof of Concept
Foundry fork test against `IdleCreditVault` / `IdleCDOEpochVariant` (modeled on `testFinalizeDefaultHaircutsPendingInstantRedeems` in `test/foundry/IdleCreditVault.t.sol:4435`):

```solidity
function testStaleInstantBasisInflatesDefaultRecovery() external {
    // setup: instant withdraws enabled (setInstantWithdrawParams(delay, delta, false))
    uint256 amount = 10_000 * ONE_SCALE;
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim,   amount, true);

    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

    // epoch 1 (running): attacker and victim both request instant withdraws
    vm.prank(attacker);
    uint256 X = cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(BBtranche));

    _startEpochAndCheckPrices(1);
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    // borrower funds only enough for attacker's receipt (partial funding -> pendingInstantWithdraws > 0)
    _getInstantFundsPartial(X);

    // attacker claims funded receipt: instantWithdrawsRequests[attacker] -> 0
    // BUG: instantWithdrawsRequestsByEpoch[attacker][epoch] and
    //      instantWithdrawClaimsByEpoch[epoch] still contain X
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();

    // borrower defaults at stopEpoch, owner finalizes recovery
    _checkDefault();
    IdleCreditVault vault = IdleCreditVault(address(strategy));
    uint256 basis = vault.defaultPendingClaimBasis();
    // basis wrongly includes the already-paid X
    assertGt(basis, vault.pendingInstantWithdraws() + vault.pendingWithdraws(), 'stale basis');

    // finalize: phantom X dilutes defaultRecoveryPrice
    uint256 recovered = /* activeBasis + realBasis */ 0 /* compute, excluding X */;
    deal(defaultUnderlying, manager, recovered);
    vm.prank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);

    // optional theft leg: attacker opens new instant request Z >= X post-finalization,
    // claims, and receives X * defaultRecoveryPrice / RECOVERY_FULL from the reserve again,
    // while victim's claim is paid at the diluted price and X's share stays locked.
}
```

Uncertainty: the exact revert/allow behavior of `requestInstantWithdraw` post-finalization and the funding granularity in `_transferFundedClaim` could not be fully read in this session; the dilution leg (impact 1) stands regardless, since `defaultPendingClaimBasis` demonstrably reads the never-cleared `instantWithdrawClaimsByEpoch[epochNumber]`.
