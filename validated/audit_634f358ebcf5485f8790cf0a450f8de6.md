### Title
Node-scoped `nodeRateLimiter` in `handleWebAPIOutgoingMessage` allows one workflow's outgoing HTTP flood to exhaust the shared node's rate budget and deny another workflow's requests - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handleWebAPIOutgoingMessage` calls `h.nodeRateLimiter.Allow(nodeAddr)` keyed exclusively on `nodeAddr` [1](#0-0)  with no dimension for workflow ID, request sender, or capability. Since a single DON node executes many independent workflows and relays all of their `web_api_target`/`compute_action`/`workflow_syncer` outgoing calls through this same handler, one workflow's high-volume outgoing HTTP traffic exhausts the per-node token bucket and causes `handleWebAPIOutgoingMessage` to reject a co-located victim workflow's legitimate requests routed via the same node.

### Finding Description
`HandleNodeMessage` dispatches `MethodWebAPITarget`, `MethodComputeAction`, and `MethodWorkflowSyncer` messages to `handleWebAPIOutgoingMessage(ctx, msg, nodeAddr)`, where `nodeAddr` is the DON node's address validated against `msg.Body.Sender` [2](#0-1) . The rate limiter's only key is `nodeAddr`, `h.nodeRateLimiter.Allow(nodeAddr)` [3](#0-2) , and `ratelimit.RateLimiter.Allow` internally buckets purely by that string key with a global+per-key limiter [4](#0-3) . The message payload carries only `MessageId`, `Method`, `DonId`, and the HTTP request body [5](#0-4)  - there is no workflow or requester identifier available to the limiter, so all outgoing requests relayed by a given node share one rate budget regardless of which workflow produced them.

A DON node typically runs multiple workflows for different users; each workflow's `web_api_target`/`compute_action` executions on that node get forwarded to the gateway as `MethodWebAPITarget`/`MethodComputeAction` messages signed by the node. An unprivileged attacker who can deploy/run a workflow with a tight loop of outgoing HTTP actions (a normal capability available to any workflow owner) can cause that node to emit outgoing-message traffic fast enough to saturate `nodeRateLimiter`'s per-`nodeAddr` bucket, so subsequent legitimate outgoing calls from a different, unrelated workflow scheduled on the same node are rejected with `"rate limit exceeded for node %s"` [3](#0-2) .

No isolation mechanism exists here to separate tenants: there is no per-workflow, per-user, or per-message-sender quota alongside the node-level one (contrast with `core/services/workflows/ratelimiter` which explicitly implements combined global+per-sender limiting used elsewhere, but the capabilities handler's `HandlerConfig.NodeRateLimiter` is applied only against `nodeAddr`) [6](#0-5) .

### Impact Explanation
This is a shared-infrastructure denial-of-service: any workflow with sufficient outgoing HTTP action volume scheduled on a node can starve that node's outgoing-message rate budget, causing the gateway to drop (`rate limit exceeded`) unrelated workflows' outgoing target/action/compute messages relayed through the same node. This is cross-workflow/cross-tenant DoS at the gateway layer, not a data-confidentiality or fund-movement issue - impact is scoped to availability degradation for co-scheduled workflows on the same node.

### Likelihood Explanation
Preconditions are modest: the attacker needs only the ability to deploy and run a workflow whose outgoing HTTP actions get scheduled on a node that also serves the victim's workflow — a normal, unprivileged workflow-owner capability, not any elevated node/gateway access. The attack is straightforward to repeat (simply issue a burst of outgoing target/compute actions) and does not require compromising the node, gateway, or DON consensus. However, the actual exploitability depends on DON node-assignment/scheduling behavior (whether a single node indeed executes both attacker and victim workflows) which is outside `handler.go` and wasn't verified in this review.

### Recommendation
Add an additional rate-limiting dimension keyed by workflow/requester identity (e.g., workflow ID or an owner/sender field carried in the message payload) in addition to (or instead of) the pure `nodeAddr` key, so that one workflow cannot exhaust another's share of a shared node's outgoing-message budget. At minimum, expose per-workflow sub-limits under the per-node budget, mirroring the global+per-sender pattern already implemented in `core/services/workflows/ratelimiter`.

### Proof of Concept
Go unit test plan (extending `handler_test.go`):
1. Configure `setupHandler` with a small `NodeRateLimiter` (e.g., `GlobalRPS: 1000, PerSenderRPS: 2, PerSenderBurst: 2`) so the per-`nodeAddr` bucket saturates quickly.
2. Build two distinct `api.Message`s with `Method: MethodWebAPITarget`, both signed by the same node key (`nodes[0].PrivateKey`) but with different `MessageId`s to simulate two different workflows executing on the same node.
3. Call `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)` repeatedly (e.g., 3 times) for the "attacker workflow" messages until `Allow(nodeAddr)` returns false, asserting the returned error is `"rate limit exceeded for node ..."`.
4. Immediately submit the "victim workflow" message via the same `nodeAddr` and assert it is also rejected with the same rate-limit error — demonstrating the limiter has no per-workflow isolation and one workflow's traffic denies another's.
5. As a contrast case, submit the victim message via a different `nodeAddr` (`nodes[1].Address`) and assert it succeeds, confirming the limiter is scoped purely to `nodeAddr` and shared across all workflows relayed by that node.

```go
func (h *handler) handleWebAPIOutgoingMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.lggr.Debugw("handling webAPI outgoing message", "messageId", msg.Body.MessageId, "nodeAddr", nodeAddr)
	if !h.nodeRateLimiter.Allow(nodeAddr) {
		return fmt.Errorf("rate limit exceeded for node %s", nodeAddr)
	}
	var payload Request
	err := json.Unmarshal(msg.Body.Payload, &payload)
	if err != nil {
		return err
	}

	timeout := time.Duration(payload.TimeoutMs) * time.Millisecond
	req := network.HTTPRequest{
		Method:           payload.Method,
		URL:              payload.URL,
		Headers:          payload.Headers,
		Body:             payload.Body,
		MaxResponseBytes: payload.MaxResponseBytes,
		Timeout:          timeout,
	}
```

```go
func (h *handler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	msg, err := common.ValidatedMessageFromResp(resp)
	if err != nil {
		return err
	}
	if msg.Body.Sender != nodeAddr {
		return errors.New("message sender mismatch when reading from node ")
	}
	start := time.Now()
	switch msg.Body.Method {
	case MethodWebAPITrigger:
		err = h.handleWebAPITriggerMessage(ctx, msg, nodeAddr)
	case MethodWebAPITarget, MethodComputeAction, MethodWorkflowSyncer:
		err = h.handleWebAPIOutgoingMessage(ctx, msg, nodeAddr)
	default:
		err = fmt.Errorf("unsupported method: %s", msg.Body.Method)
	}
	h.metrics.recordHandleDuration(ctx, time.Since(start), msg.Body.Method, err == nil)
	return err
```

```go
func (rl *RateLimiter) Allow(sender string) (senderAllow bool, globalAllow bool) {
	rl.mu.Lock()
	senderLimiter, ok := rl.perSender[sender]
	if !ok {
		senderLimiter = rate.NewLimiter(rate.Limit(rl.config.PerSenderRPS), rl.config.PerSenderBurst)
		rl.perSender[sender] = senderLimiter
	}
	rl.mu.Unlock()

	senderAllow = senderLimiter.Allow()
	globalAllow = rl.global.Allow()
	return senderAllow, globalAllow
}
```
