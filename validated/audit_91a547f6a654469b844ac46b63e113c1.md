### Title
Unfunded instant-withdraw receipts can be claimed against unrelated strategy balances (buffer deposits / other users' funded claims) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the LangChain path traversal (validating the *starting directory* but not the *resolved target* of the request), `IdleCreditVault.claimInstantWithdrawRequest` validates only that the caller owns an instant-withdraw receipt (`instantWithdrawsRequests[_user] != 0`) but never verifies that the receipt's funds were actually collected into the strategy. The resolved payout source is simply whatever `underlyingToken` balance the contract happens to hold — including newly pooled epoch deposits awaiting `startEpoch` forwarding and funds reserved for other users' funded receipts. The only "boundary" enforced is `defaultRecoveryReserve`, so everything outside that isolated reserve is a sibling resource that the claim can traverse into.

### Finding Description
Instant withdrawals are a two-step flow in `contracts/strategies/idle/IdleCreditVault.sol`:

1. `requestInstantWithdraw` burns CDO strategy tokens, mints a receipt to the user and increments `pendingInstantWithdraws` — the *unfunded* remainder owed by the borrower.
2. `collectInstantWithdrawFunds` (called by the CDO at `startEpoch`) pulls the underlying from the CDO and decrements `pendingInstantWithdraws`, marking the funded portion.
3. `claimInstantWithdrawRequest` burns `instantWithdrawsRequests[_user]` and calls `_transferFundedClaim(_user, amount)`, whose only guard is:

```solidity
uint256 reserve = defaultRecoveryReserve;
if (reserve != 0) {
  uint256 balance = underlyingToken.balanceOf(address(this));
  if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
}
underlyingToken.safeTransfer(_user, _amount);
``` [1](#0-0) 

There is no check that `pendingInstantWithdraws` no longer covers this user's receipt, i.e., that `collectInstantWithdrawFunds` already ran. Meanwhile `deposit()` parks underlying inside this strategy between epochs (`totEpochDeposits` accounting, lines 595–617), so during the buffer phase the contract holds real underlying that belongs to depositors/borrower funding — a sibling pool the claim can spend. The user-facing entry point `IdleCDOEpochVariant.claimInstantWithdrawRequest` only checks `allowInstantWithdraw`, adding no funding gate either. [2](#0-1) 

### Impact Explanation
An unprivileged tranche holder with a pending (still-unfunded) instant receipt can call `claimInstantWithdrawRequest` during the buffer window and receive underlying immediately, paid out of pooled deposits sitting in the strategy rather than out of funds collected from the borrower. Direct theft quantified as the full receipt amount; the theft materializes later as an equivalent shortfall when `startEpoch` tries to forward deposits or when other funded claimants withdraw (insolvency of the instant-withdraw funding bucket).

### Likelihood Explanation
Requires the instant-withdraw mode to be enabled and an APR decrease larger than `instantWithdrawAprDelta` versus `lastEpochApr` so a request is routed to `requestInstantWithdraw` — an honest manager action — plus attacker-held tranche tokens and a claim executed while the strategy holds buffer deposits before the next `collectInstantWithdrawFunds`. All attacker steps are unprivileged; privileged roles only perform their normal duties.

### Recommendation
Track funded vs. unfunded instant receipts per user (or block claims while `pendingInstantWithdraws` covers them): e.g., require `instantWithdrawsRequests[_user]` to be backed by collected funds by recording a funded-epoch marker in `collectInstantWithdrawFunds`, and have `claimInstantWithdrawRequest` only pay out receipt amounts whose epoch was funded — the same "confine the resolved target to the intended root" fix as the advisory's canonicalize-and-verify approach.

### Proof of Concept
```solidity
// Foundry fork PoC (sketch) — contracts/strategies/idle/IdleCreditVault.sol
// Setup: CDO (IdleCDOEpochVariant) + IdleCreditVault, running epoch, allowInstantWithdraw = true.
function test_UnfundedInstantClaimStealsBufferDeposits() public {
    // 1. Honest manager lowers APR so lastEpochApr > unscaledApr + instantWithdrawAprDelta.
    vm.prank(manager);
    vault.setAprs(newUnscaledApr, newScaledApr); // APR drop enables instant path

    // 2. Attacker (KYC'd tranche holder) requests withdraw -> routed to requestInstantWithdraw.
    vm.prank(attacker);
    cdo.requestWithdraw(attackerTrancheBal, AATranche);
    assertGt(vault.instantWithdrawsRequests(attacker), 0);
    assertEq(vault.pendingInstantWithdraws(), receiptAmount); // still UNFUNDED

    // 3. Epoch stops; buffer starts. New depositor deposits -> underlying sits in the vault.
    vm.prank(manager); cdo.stopEpoch(...);
    vm.prank(depositor); cdo.depositAA(depositAmount); // underlying now held by strategy
    assertGe(underlying.balanceOf(address(vault)), depositAmount);

    // 4. Attacker claims BEFORE collectInstantWithdrawFunds funds the receipt.
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest(); // pays from buffer deposits, not borrower funds

    // 5. Invariant broken: paid claim == unfunded receipt; pendingInstantWithdraws unchanged.
    assertEq(underlying.balanceOf(attacker), receiptAmount);
    assertEq(vault.pendingInstantWithdraws(), receiptAmount); // borrower still "owes" it
    // -> deposit funds forwarded at next startEpoch are short by receiptAmount.
}
```

Uncertainty noted: this conclusion rests on the observed code paths — `claimInstantWithdrawRequest` has no `pendingInstantWithdraws`/funding check and `_transferFundedClaim` only protects `defaultRecoveryReserve` — and on `deposit()` parking underlying in the strategy between epochs. I was unable to confirm the exact `startEpoch` sequencing of `collectInstantWithdrawFunds`/`sendInterestAndDeposits` in `IdleCDOEpochVariant.sol` within the available iterations; if the CDO always funds instant receipts atomically before the vault can hold unrelated underlying, the window narrows but the missing confinement check in the strategy remains.
