### Title
Missing role authorization on `/debug/vars` allows any authenticated session (including view-role) to access process runtime introspection data - ([File: core/web/router.go])

### Summary
`debugRoutes` in `core/web/router.go` wraps `/debug/vars` only with `auth.Authenticate(..., auth.AuthenticateBySession)`, with no `RequiresEditRole`/`RequiresAdminRole` wrapper, unlike nearly every other privileged route in `v2Routes`. Any user who can establish a session — including a view-role user — can hit `GET /debug/vars` and read Go's `expvar` output (`cmdline`, `memstats`, and any other registered vars).

### Finding Description
`debugRoutes` registers the group with only a session/token identity check: [1](#0-0) 

Compare this to every other authv2 route, which explicitly wraps handlers with `auth.RequiresEditRole` or `auth.RequiresAdminRole` after the base `Authenticate` middleware, e.g.: [2](#0-1) 

`AuthenticateBySession` only verifies that a valid session cookie exists and populates the authenticated user without checking `user.Role`: [3](#0-2) 

The role-gating functions (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`) exist precisely to prevent `UserRoleView` users from reaching sensitive handlers: [4](#0-3) 

Since `debugRoutes` never calls any of these role-check wrappers, a `view`-role authenticated user (the lowest privilege session role in the node) can successfully call `GET /debug/vars` and receive a 200 response with the standard Go `expvar.Handler()` payload.

However, a search of the codebase found no application-level `expvar.Publish`/`expvar.NewString`/`expvar.NewMap` calls that register custom variables (config values, secrets, etc.) into the default expvar map. The handler therefore only exposes the Go runtime's built-in `cmdline` (the process's `os.Args`) and `memstats` (heap/GC statistics) — not application secrets, API keys, DB credentials, or node config values, since Chainlink loads secrets/config via TOML/env/DB rather than CLI flags reflected in `cmdline`.

### Impact Explanation
This is a real, confirmed missing-authorization gap: every other sensitive/administrative route explicitly requires at least edit or admin role, while `/debug/vars` requires none beyond a valid session, letting the lowest-privileged (view-role) authenticated user reach it. The concrete disclosed data (Go runtime memory statistics and process `cmdline` args) is low-sensitivity given this codebase does not register custom expvar variables or pass secrets via CLI arguments. This maps to an "Information Disclosure — low/informational" bounty class (unauthorized access to non-critical internal diagnostics), not "secret disclosure" or "privilege escalation to move funds," since no keys, tokens, or job/spec secrets are exposed through this path.

### Likelihood Explanation
Any actor holding a valid, even view-role, session cookie can trigger this with a single unauthenticated-role-check `GET /debug/vars` request — no additional preconditions, timing, or race conditions are required, and the behavior is fully repeatable. The minimal precondition is possessing any authenticated session, which is the lowest bar in the system (view role).

### Recommendation
Wrap `/debug/vars` with a role-check middleware consistent with the rest of the authenticated routes, e.g. `group.GET("/vars", auth.RequiresAdminRole(expvar.Handler()))` (or `RequiresEditRole` at minimum), aligning it with the pattern used throughout `v2Routes` in `core/web/router.go`.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, alongside existing router tests):
1. Build a test app via existing test harness (`cltest.NewApplicationEVMDisabled`/`cltest.NewMockApplication` style used in `core/web` tests) and get the router via `NewRouter`.
2. Create a session-authenticated user with `Role: clsessions.UserRoleView` (lowest privilege) and log in via `POST /sessions` to obtain the session cookie, mirroring existing `TestUsers_*` test patterns in `core/web`.
3. Issue `GET /debug/vars` with the view-role session cookie attached.
4. Assert `resp.StatusCode == http.StatusOK`.
5. Decode the JSON body and assert presence of `cmdline` and `memstats` keys, confirming successful access to Go runtime introspection data using only a view-role session, with no `RequiresEditRole`/`RequiresAdminRole` check having fired (contrast by testing an admin-only route like `GET /v2/users` with the same view-role session, expecting `403 Forbidden`, to demonstrate the double standard).
6. Document that no custom/application `expvar` values were found in the codebase (no secrets in the response), scoping the finding to informational-level runtime disclosure rather than secret leakage.

func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
