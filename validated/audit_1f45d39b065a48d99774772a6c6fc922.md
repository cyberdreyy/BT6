### Title
Stale attester weight in `builder_pending_payments` is not decreased when a contributing validator's effective balance drops, allowing a builder payment to reach quorum on outdated weight - (File: `specs/gloas/beacon-chain.md`)

### Summary
`process_attestation` in Gloas increments a per-slot builder payment's `weight` field by a validator's *current* `effective_balance` the moment the validator's attestation is first counted. That recorded weight is a permanent snapshot: nothing in the spec ever decreases it again, even if the contributing validator's `effective_balance` later drops (e.g. via slashing or inactivity-leak balance decreases processed by `process_effective_balance_updates`) before `process_builder_pending_payments` checks the weight against the quorum threshold. This is the same bug class as the reported Olympus finding: an "endorsement" (here, attestation weight) is cached at time-of-vote and is never revoked/decremented when the underlying balance backing it is reduced, so a quorum decision made later compares against a stale, inflated aggregate.

### Finding Description
In `specs/gloas/beacon-chain.md`, `process_attestation` accrues weight for a pending builder payment: [1](#0-0) 

```python
if (
    will_set_new_flag
    and had_no_participation
    and is_attestation_same_slot(state, data)
    and payment.withdrawal.amount > 0
):
    payment.weight += state.validators[index].effective_balance
```

This snapshot value is written into `state.builder_pending_payments[...]` and stays there, untouched, until `process_builder_pending_payments` runs at an epoch boundary and compares it to the quorum: [2](#0-1) 

```python
def process_builder_pending_payments(state: BeaconState) -> None:
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    ...
```

Because a payment is created in the "next epoch" half of the `builder_pending_payments` array (index `SLOTS_PER_EPOCH + slot % SLOTS_PER_EPOCH`) and is only rotated into the checked half (`[:SLOTS_PER_EPOCH]`) one epoch later, there is a full epoch boundary — and therefore one run of `process_effective_balance_updates` — between when the weight is recorded and when it is checked against `quorum`: [3](#0-2) 

```python
def process_epoch(state: BeaconState) -> None:
    ...
    process_slashings(state)
    process_eth1_data_reset(state)
    process_pending_deposits(state)
    process_pending_consolidations(state)
    process_builder_pending_payments(state)
    process_effective_balance_updates(state)
    ...
```

If, during that intervening epoch, the attesting validator is slashed (immediate balance penalty via `decrease_balance` in `process_slashings`, later reflected in `effective_balance` at the following `process_effective_balance_updates`) or its balance otherwise falls (inactivity leak penalties), `state.validators[index].effective_balance` decreases — but `payment.weight`, which already "spent" the old, larger effective balance, is never adjusted downward. The quorum check therefore still credits the payment with stake that no longer exists at the time it decides whether to settle the builder's withdrawal: [4](#0-3) 

```python
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)
```

This exactly mirrors the Olympus root cause: `endorseProposal` records `userVotes` once and `totalEndorsementsForProposal` is only decremented when the same user calls `endorseProposal` again — never when `revokeVotesFrom`/`VOTES.burnFrom` independently reduces the user's balance. In Gloas, `payment.weight` is recorded once per attester and is never decremented when the attester's `effective_balance` independently drops.

### Impact Explanation
The quorum check in `process_builder_pending_payments` is the safeguard that gates whether a builder's payment for a slot is actually released into `state.builder_pending_withdrawals` (from which it is later paid out in `process_withdrawals`/`apply_withdrawals`). Because the weight backing that decision can be stale relative to the real, current effective balance of the attesters who "confirmed" the slot, a payment can be released to a builder even though the up-to-date honest attesting weight is below the intended threshold. This is a builder payment being escaped/misdirected through a threshold check that no longer reflects reality — matching the "a builder payment or withdrawal misdirected, doubled or escaped" High-impact category. No node disagrees on the *rules* (all spec-following nodes compute the same stale weight deterministically), but the safety property the quorum mechanism is meant to enforce (payment only when the current honest active stake actually attested) is broken.

### Likelihood Explanation
The trigger condition — a validator whose attestation contributed weight to a pending builder payment subsequently having its effective balance reduced (via slashing evidence included in a later block, or inactivity-leak-driven balance decreases) before the payment's quorum check one epoch later — requires no coalition, no malicious peer, and no client bug; it can occur through entirely ordinary, spec-following state transitions (e.g., any validator slashing report processed in the intervening epoch). It is deterministic and reproducible in the reference implementation.

### Recommendation
Do not permanently bake a validator's `effective_balance` into `payment.weight` at attestation time. Either (a) recompute weight from the current attester set's live `effective_balance` at the moment `process_builder_pending_payments` evaluates the quorum (requiring the attester set, not just an aggregate integer, to be retained), or (b) when a contributing validator's `effective_balance` is reduced (in `process_slashings` / `process_effective_balance_updates`), walk any `builder_pending_payments` entries the validator contributed to (analogous to remembering an "endorser list") and subtract the delta from `payment.weight` before the quorum check runs.

### Proof of Concept
Conceptual state-transition trace using existing spec functions:

1. At slot `S` in epoch `N`, validator `V` (say `effective_balance = E`) attests for the payload of a builder bid; `process_attestation` executes:
   `state.builder_pending_payments[SLOTS_PER_EPOCH + S % SLOTS_PER_EPOCH].weight += E`
   (see `specs/gloas/beacon-chain.md:2389`).
2. Suppose `E` alone (or combined with a few other attesters) is `>= get_builder_payment_quorum_threshold(state)`.
3. Before the payment bucket is checked (one epoch later), `V` is slashed via a `ProposerSlashing`/`AttesterSlashing` included in a subsequent block in epoch `N`. `process_slashings` immediately calls `decrease_balance(state, V, slashing_penalty)`. At the end of epoch `N`, `process_effective_balance_updates` lowers `state.validators[V].effective_balance` to reflect the new, much smaller balance (see `specs/gloas/beacon-chain.md:1228-1245`), executed only after `process_builder_pending_payments` has already rotated but not yet quorum-checked this payment (`specs/gloas/beacon-chain.md:1577-1599`).
4. At the boundary of epoch `N+1`, `process_builder_pending_payments` evaluates:
   `payment.weight >= quorum` — using the *original*, pre-slashing `E`, which is still `>= quorum`, even though `V`'s current `effective_balance` (and hence its real contribution) has collapsed.
5. The withdrawal is appended to `state.builder_pending_withdrawals` and eventually paid out, even though the up-to-date attesting weight no longer meets quorum — demonstrating that `payment.weight` and the validator's live `effective_balance` are out of sync at the moment the quorum decision is made, exactly as `userEndorsementsForProposal`/`totalEndorsementsForProposal` and `VOTES.balanceOf` were out of sync in the referenced Olympus bug.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
