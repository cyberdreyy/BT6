### Title
JWT replay-cache check-then-act race allows a single replayed token to pass `Authorize` twice - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Finding Description
`WorkflowMetadataHandler.Authorize` verifies a JWT and enforces single-use semantics via `jwtCache`, but the "check" and "record" operations are two separate, independently-locked calls instead of one atomic operation: [1](#0-0) [2](#0-1) 

`isReplay` takes an `RLock`, checks map membership, and releases the lock; `recordUsage` is only called after signer/authorized-key validation succeeds, and it independently takes a write `Lock`: [3](#0-2) 

If the same signed JWT (same `jti`) is submitted twice concurrently, both goroutines can execute `isReplay(claims.ID)` before either has called `recordUsage(claims.ID)`, so both see `exists == false` and both pass the replay check, both pass signer authorization, and both call `recordUsage` (a data race on map writes is also possible without `-race` synchronization guarantees beyond the mutex, but functionally both calls succeed sequentially since `recordUsage` is mutex-protected — the vulnerability is that both *complete successfully* rather than the second being rejected). This is a classic TOCTOU (check-then-act) bug: the invariant "a `jti` can only ever pass `Authorize` once" is not upheld under concurrency.

However, `Authorize` is only reachable via `httpTriggerHandler.HandleUserTriggerRequest` → `authorizeRequest`, which is called before `setupCallback`: [4](#0-3) [5](#0-4) 

`setupCallback` independently deduplicates requests by `requestID` under its own mutex (`callbacksMu`), rejecting a second request with the same `req.ID` with a `jsonrpc.ErrConflict`: [6](#0-5) 

Because the JWT is bound to the exact request digest (verified via `utils.VerifyRequestJWT`, and confirmed by the "JWT digest mismatch" test which fails when `req.ID`/params differ), a verbatim replay of the same signed JWT necessarily means the attacker resubmits the identical JSON-RPC request, including the identical `req.ID`. Consequently, even though the `Authorize` race genuinely allows both concurrent calls to pass the JWT-replay check, the downstream `setupCallback` requestID-uniqueness gate (properly synchronized under a single mutex, not subject to the same TOCTOU flaw) prevents a second pipeline execution from actually being triggered.

### Impact Explanation
The race in `jwtReplayCache.isReplay`/`recordUsage` is a real correctness bug in the replay-protection mechanism (violates the intended invariant that a `jti` is single-use), but the scoped impact claimed — "duplicate on-chain workflow execution" — is not achievable through the code path that actually reaches `Authorize`, because `setupCallback`'s `requestID` dedup (which is atomic under `callbacksMu`) blocks the second identical request before a duplicate execution can be dispatched to a shard. This does not meet the bar for "unauthorized job run or fund movement" as no duplicate execution actually occurs.

### Likelihood Explanation
Low/none as a standalone exploit for triggering duplicate pipeline execution, since it is neutralized by the requestID dedup check. The underlying race itself is trivially reproducible (two goroutines calling `Authorize` with the same token), but it does not translate into the claimed scoped impact given the current call graph.

### Recommendation
Even though the immediate scoped impact is not exploitable end-to-end, the TOCTOU pattern should still be fixed defensively (e.g., in case any other caller relies on `Authorize`/`jwtCache` without a downstream requestID dedup): combine `isReplay` and `recordUsage` into a single atomic check-and-set operation under one lock (e.g., `if _, exists := cache.cache[jti]; exists { return false }; cache.cache[jti] = time.Now(); return true`).

### Proof of Concept
Not applicable as a valid end-to-end exploit — a unit test can demonstrate the internal `jwtReplayCache` race (two goroutines calling `isReplay`/`recordUsage` concurrently and both succeeding), but a handler-level integration test replaying the same signed JWT via `httpTriggerHandler.HandleUserTriggerRequest` twice concurrently would show only one execution reaches shard dispatch because the second request is rejected by `setupCallback`'s `requestID` uniqueness check.

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```

```go
func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	key, err := h.authorizeRequest(ctx, workflowID, req, callback)
	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
```

```go
func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
```
