### Title
`LockupFactory::create` permits front-running the deterministic lockup address with `vesting_schedule=None`, deploying a lockup that can never be foundation-controlled - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` derives the lockup's account id purely from `sha256(owner_account_id)[..20]` and derives `foundation_account_id` purely from whether the *caller-supplied* `vesting_schedule` is `Some`, with no check on who the caller is. Because both the address and the `foundation_account_id`/`vesting_schedule` binding are entirely attacker-controllable for any `owner_account_id`, an unprivileged party can call `create()` first with `vesting_schedule=None`, permanently claiming the deterministic address before the legitimate grant issuer's transaction lands, so the intended vesting/foundation-controlled lockup for that owner is never deployable.

### Finding Description
The binding that should hold is: for a given `owner_account_id`, the deployed lockup at `sha256(owner_account_id)[..20].<factory>` has `foundation_account_id == Some(foundation)` iff the rightful issuer's intended `vesting_schedule` is `Some(...)`. In code: [1](#0-0) 

`create()` takes `owner_account_id` and `vesting_schedule` as plain, unauthenticated function arguments — there is no `assert_called_by_foundation`, owner check, or any restriction on who may call it, and the README explicitly documents this as intentional ("No need to have access to the foundation keys to create lockup... Lockups can be funded from any account"). [2](#0-1) 

The lockup account id is fully deterministic from `owner_account_id` alone: [3](#0-2) 

The deploy is via `create_account()` on that fixed name, and the resulting `foundation_account_id` field only exists if the caller passed a `vesting_schedule`: [4](#0-3) 

Exploit flow: attacker (unprivileged, needs no relationship to the victim) learns/guesses the victim `owner_account_id` intended to receive a foundation grant, and calls `create(owner_account_id=victim, vesting_schedule=None, ...)` with `MIN_ATTACHED_BALANCE` attached, before the real issuer's `create()` transaction (with `vesting_schedule=Some(VestingHash(...))`) is included. Because NEAR account names are globally unique and `create_account()` on an already-existing name fails, the attacker's transaction — if it lands first — creates the lockup at that deterministic address with `foundation_account_id=None` baked into the deployed lockup's state. The legitimate issuer's later `create()` call for the same `owner_account_id` then fails at `create_account()`, its whole promise chain fails, and `on_lockup_create`'s `is_promise_success()` check refunds the attached deposit to the issuer: [5](#0-4) 

No existing guard prevents this: `assert_self()` only protects the callback from being called by someone other than the factory itself, and does nothing about who may call `create()`; there is no `is_valid_account_id`-style ownership check, no signature/allow-list check tying `owner_account_id` to a specific caller, and no reservation/lock mechanism for lockup slots. The permission model of the factory ("anyone can fund anyone's lockup") is precisely what makes the address squattable with attacker-chosen (weaker) parameters.

### Impact Explanation
This matches the "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" Critical category: the address reserved for the victim's grant is permanently deployed as a lockup contract lacking `foundation_account_id`, meaning the NEAR Foundation loses the ability to ever terminate/claw back vesting-conditional tokens intended for that `owner_account_id`, because that specific account name can never be recreated with the correct parameters (NEAR account names are unique and the account now exists with attacker-chosen code/state). The real issuer's actual (large) deposit never lands in a lockup at all — it's refunded to the issuer, not stolen by the attacker — so no NEAR leaves anyone's control to the attacker's benefit; the direct harm is a permanent inability for the foundation to enforce vesting conditions on that owner's lockup, not fund theft, since the victim's real grant deposit is refunded and never released early either. The attack is repeatable across any number of prospective owner_account_ids that the attacker can guess or that are publicly known in advance (e.g., published grant recipient lists), and the attacker's cost is only the `MIN_ATTACHED_BALANCE` (~3.5 NEAR) per squatted address, most of which stays locked in the now-permanently-existing lockup account (not directly recoverable by the attacker either, since it becomes an actual deployed lockup contract owned by the victim, with no vesting condition, i.e. immediately spendable by the victim — not the attacker).

### Likelihood Explanation
Feasibility requires only knowing (or correctly guessing) the target `owner_account_id` before the real grant transaction is submitted/confirmed, and beating it to inclusion — a standard front-running/mempool-race condition on NEAR, achievable by any account holder with ~3.5 NEAR and no special privilege. Because grant/vesting recipient identities are often known or announced ahead of the funding transaction (e.g., internally at the foundation, or via public HR/token-sale communications), the precondition "no account yet exists at the deterministic address" is realistically satisfiable by an attacker monitoring for such announcements or racing a known schedule.

### Recommendation
Require that only the NEAR Foundation (or an explicitly authorized caller) may set `vesting_schedule`/cause `foundation_account_id` to be populated, and/or require the lockup account to be pre-reserved/pre-created via a privileged path before third parties can fund it — e.g., separate "reserve" and "fund" steps gated by `assert_called_by_foundation` equivalent, or require the `owner_account_id`'s full-access key to co-sign the grant creation transaction so an unrelated third party cannot pre-empt the deterministic address with weaker parameters.

### Proof of Concept
```rust
// cargo test -p lockup-factory
// Simulate: attacker calls create() with vesting_schedule=None for `victim`
// before the legitimate issuer's create() with Some(vesting_schedule) can land.

#[test]
fn test_frontrun_squats_deterministic_address_without_foundation() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (unprivileged) calls create() for victim's owner_account_id
    // with vesting_schedule = None.
    context.is_view = false;
    context.predecessor_account_id = String::from("attacker.testnet");
    context.attached_deposit = MIN_ATTACHED_BALANCE;
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, /* vesting_schedule */ None, None, None);

    // Simulate successful account creation at the deterministic address.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = 0;
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    contract.on_lockup_create(lockup_account(), MIN_ATTACHED_BALANCE.into(), String::from("attacker.testnet"));

    // LHS: what got deployed at the deterministic address -> foundation_account_id == None
    // (verify by inspecting the LockupArgs constructed in create(), since
    //  vesting_schedule was None => foundation_account = None per lines 123-126)

    // RHS (never realized): real issuer's later create() with Some(vesting_schedule)
    // for the SAME owner_account_id now fails at create_account() because the
    // account already exists, and its deposit is refunded via on_lockup_create's
    // is_promise_success() == false branch, never reaching the lockup with
    // foundation_account_id == Some(foundation_account_id()).

    // Assert the broken binding: deployed foundation_account_id (None) !=
    // what the real issuer's intended vesting_schedule=Some(...) would have produced
    // (Some(foundation_account_id())).
    assert_ne!(None::<AccountId>, Some(foundation_account_id().as_ref().to_string()));
}
```
This demonstrates the address-squatting path and the divergence between the deployed lockup's `foundation_account_id` and the value the legitimate issuer's `vesting_schedule=Some(...)` call would have produced, with the legitimate transaction guaranteed to fail and refund per the existing `on_lockup_create` logic.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
