### Title
Unbounded `batchMint` recipient array allows a mint-role holder to force unmetered, unbounded iteration inside the B20 asset precompile - (File: `crates/common/precompiles/src/b20_asset/logic/v1.rs` / `v2.rs`)

### Summary
The B20 asset precompile's `batch_mint` logic mints tokens to an arbitrary-length `recipients`/`amounts` pair supplied directly from calldata, with only a length-match and non-empty check — no maximum batch-size cap exists, mirroring the "unbounded whitelist iteration" bug class described in the external report (`Vault.sol:setTokenConfig`).

### Finding Description
`batch_mint` in both precompile logic versions accepts caller-controlled `Vec<Address>`/`Vec<U256>` and loops over every pair with no upper bound on length: [1](#0-0) [2](#0-1) 

The only validations performed are a length-mismatch check and an empty-batch check; there is no `MAX_BATCH_SIZE`-style constant bounding `recipients.len()`, unlike other admission paths in this codebase that do bound similarly-shaped inputs (e.g., EIP-8130's `MAX_ACCOUNT_CHANGES_PER_TX` cap on `account_changes.len()`): [3](#0-2) 

and the precompile input-size caps applied to other precompiles (bn254/BLS) via the `capped_precompile!` macro: [4](#0-3) 

The dispatcher only records a metric for the batch size before executing it — it does not reject oversized batches: [5](#0-4) 

Each iteration performs a full `mint` (role/pause checks already done once, but per-recipient balance/allowance/supply storage writes and event emission still occur per entry), so the actual EVM work scales linearly with `recipients.len()`, bounded in practice only by the maximum calldata size a single transaction can carry and by the transaction's declared `gas_limit`/block gas limit. I was not able to fully verify (within the tool budget) whether per-iteration work inside `mint` is metered against `GasTracker` proportionally to guarantee the declared gas_limit always reflects true iteration cost, so it remains uncertain whether this can be exploited purely as a gas-accounting bypass versus "merely" an expensive-but-correctly-priced operation.

### Impact Explanation
If per-iteration gas is not fully metered against the precompile's `GasTracker`/EVM gas cost, a mint-role holder (an already-privileged but still transaction-driven actor, reachable via a single signed transaction hitting the precompile dispatch path) could submit a `batchMint` with an extremely large `recipients` array sized only by calldata/transaction size limits, causing execution time and storage-write volume that is disproportionate to gas charged. This could degrade block building/validation performance for the sequencer/validating nodes (a node-halt/liveness risk) even though it does not directly create unbacked supply (the pause/role/length checks remain intact). If metering *is* proportional, the primary residual risk is a DoS/service-blockage similar to the original report: an oversized but "affordable" batch could still push a single transaction's execution time or state growth (unpacked `Vec` storage writes per recipient, `crates/common/precompile-storage/src/types/vec.rs`) high enough to affect block-building latency.

### Likelihood Explanation
`batch_mint` requires the `B20TokenRole::Mint` role, so this is not exploitable by an arbitrary unauthenticated sender — likelihood depends on a mint-role key being available to a party with either malicious intent or a compromised operator key. Because the role guard is legitimate access control, this is a medium- rather than high-likelihood analog, but the report's rules explicitly allow role-guard-reachable paths as in-scope.

### Recommendation
Introduce an explicit `MAX_BATCH_MINT_RECIPIENTS` (or similarly named) constant in `crates/common/precompiles/src/b20_asset/logic/v1.rs` and `v2.rs`, and reject `batch_mint` calls whose `recipients.len()` exceeds it before entering the mint loop — analogous to the existing `MAX_ACCOUNT_CHANGES_PER_TX` pattern used for EIP-8130's `account_changes` and the `capped_precompile!` input-size guards used for bn254/BLS precompiles. Additionally, verify (or add) gas metering inside the `mint` loop that scales with the number of iterations so the declared transaction `gas_limit` always bounds the real work performed.

### Proof of Concept
Not independently reproduced; based on static code review of `batch_mint` (`crates/common/precompiles/src/b20_asset/logic/v1.rs:665-693`, `logic/v2.rs:788-816`) and the dispatcher (`crates/common/precompiles/src/b20_asset/dispatch.rs:439-447`), which show no maximum-length check on `recipients`/`amounts` before iterating. A concrete PoC would require confirming the actual gas-metering behavior of the `mint` function under many iterations, which I could not fully trace within the available tool budget — a Devin session with full repo/test access would be needed to construct and run a reproducing test (e.g., a golden test analogous to `crates/common/precompiles/tests/b20_asset_v2_golden.rs:golden_batch_mint`, but with an oversized `recipients` vector) to measure actual vs. charged gas.

    fn batch_mint(
        &self,
        token: &mut B20AssetToken<S, A>,
        caller: Address,
        recipients: Vec<Address>,
        amounts: Vec<U256>,
        privileged: bool,
    ) -> Result<()> {
        // The pause and role guards below are the sole authorization gate for the batch: the inner
        // mints run privileged to avoid re-checking per recipient. Do not remove or conditionalize
        // these guards. Check order: PAUSE -> ROLE -> INPUT -> BUSINESS.
        B20Guards::ensure_not_paused(token, IB20::PausableFeature::MINT)?;
        if !privileged {
            B20Guards::ensure_token_role(token, caller, B20TokenRole::Mint)?;
        }
        if recipients.len() != amounts.len() {
            return Err(BasePrecompileError::revert(IB20Asset::LengthMismatch {
                leftLen: U256::from(recipients.len()),
                rightLen: U256::from(amounts.len()),
            }));
        }
        if recipients.is_empty() {
            return Err(BasePrecompileError::revert(IB20Asset::EmptyBatch {}));
        }
        for (recipient, amount) in recipients.into_iter().zip(amounts) {
            self.mint(token, caller, recipient, amount, true)?;
        }
        Ok(())
    }
