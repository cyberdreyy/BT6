### Title
Stale confirmations from removed members are not purged, allowing requests to execute below the live-member confirmation threshold - (File: `multisig2/src/lib.rs`, also present in `multisig/src/lib.rs`)

### Summary
`delete_member()` in the multisig contract only removes pending requests that were *created* by the removed member; it does not scrub that member's entries out of the `confirmations` map for requests created by other members that the removed member had already confirmed. A confirmation recorded by a member who is later removed remains valid and keeps counting toward `num_confirmations`, so a request can later reach the required threshold and execute using a "confirmation" from an account that is no longer a member of the multisig.

### Finding Description
The contract's core invariant is: a request executes only once it has confirmations from `num_confirmations` **current, trusted** members. `confirm()` enforces membership only at the moment a member calls it, but that state is never re-validated later.

`delete_member()` is the only place that reacts to member removal, and it cleans up state selectively: [1](#0-0) 

It filters `self.requests` by `r.member == member` — i.e., requests the removed member *authored* — and deletes those requests along with their confirmations. It does not iterate `self.confirmations` to strip the removed member's confirmation from requests authored by *other* members that this member had also confirmed.

Meanwhile, `confirm()` and the execution-threshold check (shown in `execute_request`/`confirm` flow) simply compare the size of the stored confirmation set against `self.num_confirmations`: [2](#0-1) 

Because the stale confirmation is never removed, the equality the protocol relies on:

`confirmations_from_current_members(request) == confirmations_recorded(request)`

is broken — `confirmations_recorded(request)` can exceed `confirmations_from_current_members(request)` once a confirming (but non-authoring) member is deleted.

The identical pattern exists in the older `multisig` contract, where `DeleteKey` only clears requests filtered by `r.signer_pk == pk` (the request's creator), not confirmations by that key on other requests: [3](#0-2) 

This is structurally the same bug class as the referenced Gondi finding: a derived/aggregated security value (`getMinTimeBetweenWithdrawalQueues` there, the confirmation count here) is not recalculated/revalidated when the underlying trusted set changes (`getUnderwriter` swap there, member/key removal here), allowing the protocol's custody/authorization binding to be violated using stale state.

### Impact Explanation
This crosses the authorization-threshold boundary explicitly called out as in-scope ("a multisig request executed below threshold"). A request can be approved and executed (including `Transfer`, `AddKey`/`AddMember` granting full access, or `FunctionCall`) using a confirmation from an account that has since been removed as untrusted, effectively lowering the live K-of-N requirement without any of the remaining members intending or being able to prevent it. Funds or full access keys can be moved/granted by a coalition smaller than the configured threshold of *current* trusted members — a Critical-severity custody violation.

### Likelihood Explanation
Requires only ordinary multisig operations: an existing pending request confirmed by a member who is subsequently removed via `DeleteMember`/`DeleteKey`, followed by enough additional live-member confirmations to reach `num_confirmations`. No special privileges beyond normal multisig member actions are needed, and the sequence (confirm → remove that confirmer as member → confirm again to cross threshold) is straightforward and likely to occur naturally in any long-lived multisig that rotates membership while requests are outstanding.

### Recommendation
When a member/key is removed, iterate all pending requests' confirmation sets and remove any confirmation belonging to the removed member/key (not just requests they authored). Alternatively, revalidate at execution time (and ideally at every `confirm()` call) that every account/key in the stored confirmation set for a request is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize multisig with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(Transfer{...})` → request `R` has confirmations `{A}` (count 1).
3. `B` calls `confirm(R)` → confirmations `{A, B}` (count 2, still below threshold 3).
4. Members `A, C, D` create and confirm a separate `DeleteMember{member: B}` request; it reaches 3 confirmations and executes, removing `B` from `self.members` via `delete_member()`.
   - `delete_member()` only removes requests where `r.member == B` (requests *authored* by `B`); it does **not** touch `R`'s confirmation set, so `R.confirmations` still contains `{A, B}`.
5. `C` calls `confirm(R)` → confirmations `{A, B, C}` (count 3) → threshold met → `R` (the `Transfer`) executes.
6. Result: `R` executed with confirmations counted as 3, but only 2 live members (`A`, `C`) actually authorized it at that point — `B`'s stale confirmation, from an account no longer trusted by the group, was decisive. [1](#0-0) [2](#0-1) [3](#0-2)

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
