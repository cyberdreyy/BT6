### Title
Builder-withdrawal `Withdrawal.amount` sent to the EL is uncapped while the CL-side balance deduction is capped, minting Gwei not backed by any balance decrease - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` builds the `Withdrawal` objects that go into `state.payload_expected_withdrawals` — the canonical list the execution layer is committed to and required to honor (mint) exactly — using the *raw, uncapped* `builder_pending_withdrawals[].amount`. The CL-side balance deduction performed later by `apply_withdrawals`, however, explicitly caps the same withdrawal at `min(withdrawal.amount, builder_balance)`. If a builder's actual balance is smaller than the queued withdrawal amount, the EL still mints/credits the full, uncapped `withdrawal.amount` to `fee_recipient`, while the CL only burns the smaller, capped amount from the builder's balance. This is the same bug class as the CoreDAO `SystemReward.receiveRewards` finding: the "amount actually paid out" and "amount debited from the internal ledger" are allowed to diverge, silently minting/losing funds.

### Finding Description
`get_builder_withdrawals` iterates `state.builder_pending_withdrawals` and appends a `Withdrawal` whose `amount` field is set directly to the pending withdrawal's `.amount`, with no comparison to the builder's balance: [1](#0-0) 

That withdrawal list is folded into `get_expected_withdrawals` and then written verbatim into `state.payload_expected_withdrawals` via `update_payload_expected_withdrawals`, which is the value the execution layer is obligated to honor for the corresponding parent block: [2](#0-1) [3](#0-2) 

Meanwhile, the *only* place the builder's own CL-tracked balance is reduced for that same withdrawal is `apply_withdrawals`, which explicitly caps the deduction to the available balance: [4](#0-3) 

So for a `builder_pending_withdrawals` entry whose `.amount` exceeds `state.builders[builder_index].balance` at settlement time:
- EL side: credits `fee_recipient` with the full, uncapped `withdrawal.amount` (this is what is written into `payload_expected_withdrawals`, and standard EIP-4895-style withdrawal semantics guarantee the EL mints exactly the committed amount — there is no "transfer can fail" concept on this side, unlike the Solidity `.send()` in the original CoreDAO report).
- CL side: only decreases `builders[builder_index].balance` by `min(withdrawal.amount, balance)`.

The delta (`withdrawal.amount - balance`) is Gwei that is paid out on the execution layer but never subtracted from any account on the consensus layer — a violation of the "total Gwei minted equals total Gwei burned from validator/builder balances" invariant. This is documented (and unit-tested) as intentional "capped" behavior rather than being flagged as a discrepancy between the committed payload amount and the CL bookkeeping amount: [5](#0-4) [6](#0-5) 

### Impact Explanation
If reachable, this is a Critical-class issue per the rules ("Gwei created ... a payload or payment applied that the block did not commit to" — here inverted: the block commits to paying more than it actually burns). It would mean the execution layer mints Gwei to a `fee_recipient` address that is not backed by any corresponding decrease in the beacon state, silently inflating total supply and creating funds out of nothing for that address.

### Likelihood Explanation
This is the residual uncertainty: whether `builder.balance < builder_pending_withdrawals[i].amount` can actually occur through normal, spec-following state transitions. `process_execution_payload_bid` validates at bid-submission time via `can_builder_cover_bid` that the builder can cover the new bid *plus* existing pending payments/withdrawals: [7](#0-6) 

This check is designed to prevent oversubscription, and the codebase's own tests (`test_builder_withdrawal_insufficient_balance*`) construct the mismatched-balance scenario only by directly mutating test state rather than by driving it through the full bid → payment → withdrawal pipeline. I was not able to fully trace `can_builder_cover_bid` / `get_pending_balance_to_withdraw_for_builder` to conclusively prove or disprove that a legitimate sequence of spec-compliant blocks can still leave a `builder_pending_withdrawals` entry whose amount exceeds the builder's balance at settlement time (e.g., via ordering/timing gaps between when a payment is queued and when the balance check for a *later* bid is performed, or interactions with `MIN_DEPOSIT_AMOUNT` floor logic). Given the explicit `min()` capping and the dedicated tests describing this as expected/handled behavior, this may be an already-accepted defensive fallback rather than a reachable inflation bug — but the structural mismatch between the *committed* (uncapped) `Withdrawal.amount` and the *applied* (capped) balance deduction is real and present in the spec text.

### Recommendation
Cap the `Withdrawal.amount` produced by `get_builder_withdrawals` (and equivalently in `get_builders_sweep_withdrawals` if analogous gaps exist) to `min(withdrawal.amount, state.builders[builder_index].balance)` *before* it is written into `state.payload_expected_withdrawals`, so the amount the execution layer is committed to paying out can never exceed the amount actually deducted from the builder's CL-tracked balance. Alternatively, strengthen `can_builder_cover_bid` / the payment-queuing path with an invariant/assertion that guarantees `builder_pending_withdrawals[].amount <= builder.balance` always holds at the time a withdrawal is dequeued, and add a test that exercises this purely through the standard block-processing pipeline (bid → `builder_pending_payments` → `builder_pending_withdrawals` → `apply_withdrawals`) rather than directly injecting a pre-decoupled state.

### Proof of Concept
Not fully constructible from spec text alone: reproducing the divergence requires demonstrating a spec-compliant sequence of blocks/bids that drives `state.builders[i].balance` below the sum of that builder's already-queued `builder_pending_withdrawals` amounts despite `can_builder_cover_bid`'s check at each bid. The existing repository unit tests demonstrate the *mechanical* consequence (capped balance deduction vs. uncapped `withdrawal.amount` recorded in the committed withdrawals list) by directly setting `builder_balances` lower than `builder_withdrawal_amounts` in test state, e.g.: [8](#0-7) 
but do not drive this state through the full bid-validation pipeline, so full end-to-end reachability from a legitimate block sequence was not verified.

##### Modified `process_withdrawals`

*Note*: This is modified to only take the `state` as parameter. Withdrawals are
deterministic given the beacon state, any execution payload that has the
corresponding block as parent beacon block is required to honor these
withdrawals in the execution layer. `process_withdrawals` must be called after
`process_parent_execution_payload` (which updates `state.latest_block_hash`) and
before `process_execution_payload_bid` as the latter function affects validator
balances.

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.

def process_execution_payload_bid(
    state: BeaconState, signed_bid: SignedExecutionPayloadBid
) -> None:
    bid = signed_bid.message
    builder_index = bid.builder_index
    amount = bid.value

    # For self-builds, amount must be zero regardless of withdrawal credential prefix
    if builder_index == BUILDER_INDEX_SELF_BUILD:
        assert amount == 0
        assert signed_bid.signature == bls.G2_POINT_AT_INFINITY
    else:
        # Verify that the builder is active
        assert is_active_builder(state, builder_index)
        # Verify that the builder is a payload builder
        assert state.builders[builder_index].version == PAYLOAD_BUILDER_VERSION
        # Verify that the builder has funds to cover the bid
        assert can_builder_cover_bid(state, builder_index, amount)
        # Verify that the bid signature is valid
        assert verify_execution_payload_bid_signature(state, signed_bid)
