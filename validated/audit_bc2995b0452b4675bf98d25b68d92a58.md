### Title
Miner can keep resetting `last_activity_time` via repeated non-advancing pre-commits to permanently defer inactivity fallback - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` treats any block proposal that conflicts with a *fresh pre-committed* (not yet signed) block as "miner activity" and unconditionally refreshes `last_activity_time` for the tenure, exactly like the Wildcat bug where calling `setAnnualInterestBips()` refreshed a temporary protective window every time it was invoked. Because the sole write-holder of a tenure's `BlockProposal` StackerDB slot is the current sortition winner, that single miner can keep issuing distinct low/non-advancing proposals faster than `tenure_last_block_proposal_timeout` to keep this "activity" signal alive indefinitely, which starves `is_timed_out`/`check_miner_inactivity` of the elapsed time it needs to declare the miner inactive and fall back to the prior tenure — a liveness wedge triggered by one signer/miner alone.

### Finding Description
`check_latest_block_in_tenure` in [1](#0-0)  looks at the last block the signer has only *pre-committed to* (`get_last_accepted_block`). If that pre-commit is still fresh (`approved_time + tenure_last_block_proposal_timeout > now`) and the new proposal does not confirm more blocks than it, the function does **not** reject it outright for inactivity purposes — it instead calls `signer_db.update_last_activity_time(...)` unconditionally, explicitly to "count this invalid block proposal towards valid miner activity."

`update_last_activity_time`'s value is the sole input (aside from the tenure's burn-block-receive timestamp) to `SortitionState::is_timed_out`, in both the v1 and v2 chainstate implementations: [2](#0-1)  and [3](#0-2) . `is_timed_out` computes `elapsed = now - last_activity` and only trips (`elapsed > block_proposal_timeout`) once no activity has been observed for the whole timeout window.

`check_miner_inactivity` in [4](#0-3)  is the only path that reverts the active miner to the prior tenure, and it is gated entirely on `is_timed_out` returning true.

Because `approved_time` is refreshed to "now" every time the signer pre-commits a *new* proposal (each distinct proposal — e.g. same chain height, bumped timestamp — is a new `signer_signature_hash` and gets its own pre-commit), the current tenure's miner (the only entity permitted to write to that tenure's `BlockProposal` slot) can keep sending a stream of proposals at a cadence faster than `tenure_last_block_proposal_timeout`. Each one:
1. Re-arms `is_fresh_pre_commit` (extends the window another `tenure_last_block_proposal_timeout`).
2. Calls `update_last_activity_time`, resetting the `is_timed_out` clock to zero.

The miner never needs to reach a globally- or even locally-accepted block; a merely pre-committed, non-advancing proposal is enough. This mirrors the reported bug class exactly: a single, repeatable, cheap action (an interest-rate reduction there; a proposal resend here) is defined to refresh a *temporary* protective window (90% reserve ratio there; "still counts as activity" here), but nothing stops the same actor from refreshing it forever, defeating the intended eventual fallback/expiry.

### Impact Explanation
This is a liveness wedge matching the accepted High-impact class: "a signer wedged into never signing valid blocks." A malicious current-tenure miner can indefinitely suppress the signer's own inactivity fallback (`check_miner_inactivity`), so the signer set never reverts to the prior (honest) miner's tenure, and the malicious miner is never forced to produce a signable, chain-advancing block. The chain stalls at the current tenure's tip until the next Bitcoin sortition, entirely at the current miner's discretion, without needing cooperation from any other signer or a majority.

### Likelihood Explanation
Reachable by exactly one actor — whichever miner currently holds the sortition-winning `BlockProposal` StackerDB slot — with no signer collusion, no majority, and no special key access beyond normal mining. It only requires repeatedly broadcasting cheap, non-advancing block proposals at a cadence under `tenure_last_block_proposal_timeout` (default 30s per `sample/conf/signer/mainnet-signer-conf.toml`), which is well within a miner's control.

### Recommendation
Cap how much a repeated pre-commit-conflict can extend the inactivity window — e.g., track the *first* observed conflicting-pre-commit time per tenure rather than continuously resetting `approved_time`/`last_activity_time` on every new pre-commit, or bound the total extension to a fixed multiple of `tenure_last_block_proposal_timeout` regardless of how many distinct proposals arrive, so `is_timed_out` can still trip once the miner has demonstrably failed to produce a signed, advancing block within a bounded overall period.

### Proof of Concept
1. Miner M wins the current tenure's sortition and holds the `BlockProposal` StackerDB write slot for it.
2. M sends proposal P1 (chain_length = h, timestamp = t1). Signers pre-commit; `approved_time` is set to t1.
3. Before `tenure_last_block_proposal_timeout` elapses, M sends P2 with the same chain_length h but timestamp t2 (a distinct `signer_signature_hash`). Signers see this as a conflicting proposal against P1's fresh pre-commit → `check_latest_block_in_tenure` ( [5](#0-4) ) marks it fresh, does not veto, and calls `update_last_activity_time(now)`.
4. Repeat step 3 indefinitely (P3, P4, …), always resending before `tenure_last_block_proposal_timeout` expires.
5. `SortitionState::is_timed_out` ( [6](#0-5) ) never observes `elapsed > block_proposal_timeout`, so `check_miner_inactivity` never reverts to the prior tenure — the tenure stalls indefinitely under M's control.

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
