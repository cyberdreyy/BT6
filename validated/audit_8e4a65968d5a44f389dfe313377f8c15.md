## Analog Found

### Title
Front-runnable, unauthenticated `init_global_fee_state` allows arbitrary actor to seize global fee admin/wallet roles - (File: `programs/marginfi/src/instructions/marginfi_group/init_global_fee_state.rs`)

### Summary
The Rigor report describes a class of bugs where initialization functions that set critical protocol addresses (treasury, admin, HomeFi reference, etc.) have no check on *who* is allowed to call them, allowing anyone to front-run deployment and seize control or redirect funds. The marginfi-v2 program contains a structurally identical pattern in `init_global_fee_state`, the one-time instruction that sets the program-wide `global_fee_admin` and `global_fee_wallet`.

### Finding Description
`initialize_fee_state` is invoked via `InitFeeState`, whose accounts require only an arbitrary `payer: Signer<'info>` — there is no check that `payer` is any pre-authorized/privileged key (e.g. the program's upgrade authority or a hardcoded pubkey): [1](#0-0) 

The handler blindly writes attacker-controlled arguments (`admin_key`, `fee_wallet`) into the newly-created `FeeState` PDA: [2](#0-1) 

Crucially, the `fee_state` PDA is derived from a single constant seed (`FEE_STATE_SEED`) with no group- or admin-specific component, and only ever exists once for the entire program deployment (`init` — first successful call wins the address permanently): [3](#0-2) 

This is exactly the failure mode described in the Rigor report: a permissionless, unauthenticated initializer for a security-critical singleton, where an attacker who observes the deployment (mempool/explorer) can race the legitimate initialization transaction and become the sole caller, setting `global_fee_admin` and `global_fee_wallet` to attacker-controlled keys. Once initialized, this state is cached into every `MarginfiGroup` on creation (`marginfi_group.fee_state_cache.global_fee_wallet = fee_state.global_fee_wallet`) and is used downstream to route protocol fees: [4](#0-3) 

### Impact Explanation
If the attacker wins the race, they gain: (1) the `global_fee_admin` role, which per `lib.rs` comments controls program-wide fee configuration (`init_global_fee_state`/`config_group_fee` "the global admin sets fees that are assessed to the protocol"), and (2) redirection of `global_fee_wallet`, the destination cached into every group and used for protocol fee collection thereafter. This mirrors the "Loss of funds" scenario in the source report (attacker becomes treasury/admin recipient of ongoing protocol fees) and constitutes a durable, hard-to-reverse capture of a protocol-wide singleton, since the PDA cannot be re-initialized once created. [5](#0-4) 

### Likelihood Explanation
Exploitation requires only observing the deployment transaction stream and submitting a competing transaction with the attacker's own pubkeys as `admin_key`/`fee_wallet` before the legitimate call lands — no special privilege, staked collateral, or insider access is needed, matching the "unprivileged-user" criterion. This is lower likelihood in practice than typical in-production bugs because it is a narrow deployment-time race window, consistent with why the original Rigor finding was downgraded to Medium severity by the C4 judge (impact real, but window of exploitation limited to a single deploy event).

### Recommendation
Bundle `init_global_fee_state` into the same atomic deployment transaction/script as the program deploy, or add an explicit authority check (e.g., require the payer/admin to equal a hardcoded upgrade authority or a value passed at build/deploy time and verified against `Program<'info, ...>` upgrade authority) so the instruction cannot be front-run by an arbitrary signer. Alternatively, add a guard instruction that fails loudly (rather than silently succeeding for an unintended caller) and have off-chain tooling immediately verify the resulting `admin_key`/`fee_wallet` match expectations before proceeding with further deployment steps.

### Proof of Concept
1. Operator prepares deployment and is about to send `init_global_fee_state(admin, fee_wallet, ...)` as the first post-deploy instruction.
2. Attacker monitors the mempool/RPC for transactions invoking the `marginfi` program's `init_global_fee_state` discriminator, or simply polls immediately after the program's on-chain deploy slot.
3. Attacker submits their own `init_global_fee_state` transaction with `payer = attacker`, `admin_key = attacker_admin`, `fee_wallet = attacker_wallet`, targeting the same deterministic `FEE_STATE_SEED` PDA.
4. Because there is no authorization check in `InitFeeState`/`initialize_fee_state`, if the attacker's transaction lands first, the PDA is created with attacker-controlled `global_fee_admin` and `global_fee_wallet`; the legitimate operator's transaction subsequently fails with an "account already in use" error (Anchor `init` constraint).
5. All future `MarginfiGroup`s created afterward cache `fee_state_cache.global_fee_wallet = attacker_wallet` at `initialize.rs:30`, and the attacker retains `global_fee_admin` rights to further reconfigure fees via `config_group_fee`/related admin-only instructions, requiring a full protocol redeploy to remediate.

pub fn initialize_fee_state(
    ctx: Context<InitFeeState>,
    admin_key: Pubkey,
    fee_wallet: Pubkey,
    bank_init_flat_sol_fee: u32,
    liquidation_flat_sol_fee: u32,
    order_init_flat_sol_fee: u32,
    program_fee_fixed: WrappedI80F48,
    program_fee_rate: WrappedI80F48,
    liquidation_max_fee: WrappedI80F48,
    order_execution_max_fee: WrappedI80F48,
) -> Result<()> {
    let mut fee_state = ctx.accounts.fee_state.load_init()?;
    fee_state.global_fee_admin = admin_key;
    fee_state.global_fee_wallet = fee_wallet;
    fee_state.key = ctx.accounts.fee_state.key();
    fee_state.bank_init_flat_sol_fee = bank_init_flat_sol_fee;
    fee_state.bump_seed = ctx.bumps.fee_state;
    fee_state.program_fee_fixed = program_fee_fixed;
    fee_state.program_fee_rate = program_fee_rate;
    fee_state.liquidation_max_fee = liquidation_max_fee;
    fee_state.liquidation_flat_sol_fee = liquidation_flat_sol_fee;
    fee_state.order_execution_max_fee = order_execution_max_fee;
    fee_state.order_init_flat_sol_fee = order_init_flat_sol_fee;

    Ok(())
}
