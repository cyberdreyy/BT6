### Title
Attacker can frontrun `IdleCDOFactory.deployCDO`/`IdleCreditVaultFactory` proxy deployments and steal funds pre-approved to the predicted vault address - (File: contracts/IdleCDOFactory.sol)

### Summary
`IdleCDOFactory.deployCDO` is permissionless and deploys each `TransparentUpgradeableProxy` with plain `CREATE` (`new TransparentUpgradeableProxy(...)`), so proxy addresses are a pure function of the factory's nonce, not of the deployer or the vault params. The same pattern exists in `IdleCreditVaultFactory._deployProxy`, reached via the permissionless `deployCreditVault` and `deployRevolvingCreditVault`. Anyone who can predict the next factory nonce can predict the next deployed vault/proxy address. An unprivileged attacker can frontrun a victim's deployment with their own deployment carrying attacker-chosen `implementation`, `admin`, and init `data`, occupy the predicted address, and capture any tokens the victim (or a relying party) sent or approved to that address.

### Finding Description
The bug class from the external report maps directly onto the deployment path of idle-tranches: a permissionless factory that (a) uses `CREATE` (predictable, caller-independent address) and (b) lets the caller fully control the deployed contract's implementation, proxy admin, and initializer payload.

- `IdleCDOFactory.deployCDO` at contracts/IdleCDOFactory.sol:9-12 — `function deployCDO(address implementation, address admin, bytes memory data) public` with `new TransparentUpgradeableProxy(implementation, admin, data)`. No access control, no salt binding to `msg.sender`.
- `IdleCreditVaultFactory.deployCreditVault` (contracts/IdleCreditVaultFactory.sol:92-124) and `deployRevolvingCreditVault` (lines 126-166) are `external` with no `msg.sender` check; all proxies go through `_deployProxy` (lines 280-286), which again uses raw `CREATE`.

Attack scenario (IdleCDOFactory):
1. A deployer/integrator computes the address of the CDO proxy that will be created by their pending `deployCDO` call at factory nonce `N` (`keccak256(rlp(factory, N))`), and in a prior or separate transaction approves underlying tokens to that address (e.g., to seed the strategy/vault, or a lender approves the "soon-to-be" vault for deposits).
2. Attacker sees the deployment tx in the mempool and front-runs it with their own `deployCDO(maliciousImpl, attackerAdmin, attackerData)`. The attacker's proxy lands at nonce `N` — the victim's predicted address — while the victim's deployment shifts to nonce `N+1`.
3. All funds/approvals the victim directed at the nonce-`N` address now apply to a proxy whose implementation and upgrade admin the attacker chose. The attacker upgrades to (or directly uses) logic that sweeps the approved/balanced tokens.

The deployed-vault case is strictly worse: the attacker picks `implementation` freely in both factories, so the contract at the predicted address is fully attacker-controlled from block one — the honest `transferOwnership(treasury)` in `deployCreditVault` only affects proxies deployed from the *legit* call, not the attacker's.

### Impact Explanation
Direct theft of any ERC20 balance or allowance directed at the predicted deployment address, plus a deeper trust break: any off-chain party whitelisting/approving the predicted vault address (e.g., a Keyring whitelist admin pre-allowing the vault, a treasury pre-seeding liquidity, or a lender approving the vault for `depositAA`) would be approving an attacker-controlled contract. Loss is bounded only by what was pre-funded/pre-approved, which for vault bootstrap flows can be the full initial liquidity.

### Likelihood Explanation
Requires a user/integration flow that relies on a precomputed deployment address (predict the next `CREATE` output, then fund/approve it before or between transactions). This is exactly the sequence the original JOJO finding relied on and is a realistic ops pattern for vault bootstrapping (predict address → approve underlying/whitelist → deploy). The nonce-hijack itself is trivially executable by any mempool observer since both deploy functions are permissionless and the CREATE input contains no `msg.sender` binding. Mitigating factor: exploitation needs the victim to act on a counterfactual address rather than using the address returned by the transaction.

### Recommendation
Deploy with `CREATE2` using a salt that binds the deployment to the caller and params, e.g. `new TransparentUpgradeableProxy{salt: keccak256(abi.encode(msg.sender, implementation, admin, data))}(...)`, applied in `IdleCDOFactory.deployCDO` and `IdleCreditVaultFactory._deployProxy`. Additionally, restrict `deployCreditVault`/`deployRevolvingCreditVault`/`deployCDO` to a trusted role (e.g., `treasury`) so that nonce consumption cannot be driven by an attacker, and document that consumers must never approve or send tokens to a predicted address before it exists.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCDOFactory} from "../contracts/IdleCDOFactory.sol";
import {TransparentUpgradeableProxy} from "@openzeppelin/contracts/proxy/transparent/TransparentUpgradeableProxy.sol";
import {ERC20} from "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MockUnderlying is ERC20 {
    constructor() ERC20("mTKN", "mTKN") { _mint(msg.sender, 1_000_000e18); }
}

// attacker-controlled implementation: arbitrary call() to drain approvals/balances
contract EvilImpl {
    function sweep(address token, address to) external {
        uint256 bal = ERC20(token).balanceOf(address(this));
        if (bal > 0) ERC20(token).transfer(to, bal);
        uint256 allowance = ERC20(token).allowance(tx.origin /*victim*/, address(this));
        if (allowance > 0) ERC20(token).transferFrom(tx.origin, to, allowance);
    }
}
contract DummyImpl {}

contract FactoryFrontrunTest is Test {
    IdleCDOFactory factory;
    MockUnderlying token;
    address victim = address(0xA11CE);
    address attacker = address(0xBAD);

    function testFrontrunPredictedAddress() public {
        token = new MockUnderlying();
        factory = new IdleCDOFactory();

        // victim predicts the address the factory will create at current nonce
        address predicted = computeCreateAddress(address(factory), vm.getNonce(address(factory)));

        // victim pre-approves the predicted vault address (e.g. to fund it)
        token.transfer(victim, 100e18);
        vm.prank(victim);
        token.approve(predicted, 100e18);

        // attacker frontruns victim's deployCDO with own implementation/admin/data
        vm.prank(attacker);
        factory.deployCDO(address(new EvilImpl()), attacker, "");
        address attackerProxy = computeCreateAddress(address(factory), vm.getNonce(address(factory)) - 1);
        assertEq(attackerProxy, predicted); // attacker occupied the predicted address

        // victim's own deployment lands one nonce later at a different address
        vm.prank(victim);
        factory.deployCDO(address(new DummyImpl()), victim, "");

        // attacker drains the victim's allowance via the proxy at `predicted`
        vm.prank(attacker, attacker);
        (bool ok,) = predicted.call(abi.encodeWithSignature("sweep(address,address)", address(token), attacker));
        assertTrue(ok);
        assertEq(token.balanceOf(attacker), 100e18);
        assertEq(token.balanceOf(victim), 0);
    }
}
```
