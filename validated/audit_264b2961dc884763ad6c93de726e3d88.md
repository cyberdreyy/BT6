### Title
Confirmations from a removed multisig member remain counted toward `num_confirmations`, allowing a request to execute below the live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` only purges the *requests* whose original submitter (`r.member`) is the removed member, but it does not scrub that member's `confirmations` entries from *other* pending requests they had previously confirmed. Since `confirm()` counts `confirmations.len()` against `self.num_confirmations` without re-validating that each stored confirmer is still in `self.members`, a request that was confirmed in part by a since-removed member can still reach the threshold and execute, even though the number of *currently live* members who approved it is below `num_confirmations`.

### Finding Description
`confirm()` checks the threshold purely by set size: [1](#0-0) 

`delete_member()` removes stale requests only for the ones the removed member originally created, and removes `num_requests_pk`, `members` entry, and (if key-based) the access key — but never touches `self.confirmations` maps belonging to *other* request IDs that this member had already confirmed: [2](#0-1) 

`assert_valid_request()` (invoked by `confirm`) only validates that the *caller* is a current member; it never re-validates the *existing* stored confirmers: [3](#0-2) 

Consequently the binding "number of confirmations counted == number of currently live, distinct members who approved" is broken. Concretely:
1. Members {A, B, C, D}, `num_confirmations = 3`.
2. A creates request R and confirms (confirmations = {A}).
3. B confirms R (confirmations = {A, B}).
4. Members execute a separate, already-fully-confirmed `DeleteMember{B}` request, removing B from `self.members` (this only cleans up requests where `r.member == B`, not R, since R was created by A).
5. C now calls `confirm(R)`. `confirmations.len() + 1 == 3 == num_confirmations`, so R executes — but B is no longer a live member; only A and C are live confirmers (2 out of 4 remaining live members), i.e., R executed with an effective quorum of 2 live signers though the contract believes it received 3.

This is the same class of bug as the reported EIP-4626 `maxMint`/`maxDeposit` issue: a value the contract trusts as an up-to-date limit/count (`confirmations.len()`, analogous to `maxSupply`-derived caps) silently diverges from the actual live state (`self.members`, analogous to `totalSupply`) because the accounting function does not filter stale entries.

### Impact Explanation
This falls under the Critical impact bucket "a multisig request executed below threshold" explicitly listed in scope. It can allow a transfer, key addition, or contract upgrade to execute with fewer live-member approvals than `num_confirmations` requires, undermining the K-of-N custody guarantee of the multisig and potentially enabling fund movement or privilege escalation with insufficient authorization.

### Likelihood Explanation
Requires no privileged actor to exploit once the precondition (partial confirmation followed by removal of one confirmer) occurs — it can happen through completely legitimate multisig operation (e.g., an employee/key is removed for routine reasons after having confirmed a pending request). No malicious deployment, redeploy, or social engineering is needed; it's a straightforward sequencing of standard, permitted multisig calls (`add_request`, `confirm`, `DeleteMember` request, `confirm`). This is a realistic, unprivileged-reachable ordering rather than a purely theoretical concern.

### Recommendation
When counting confirmations in `confirm()` (and in `get_num_confirmations`/`get_confirmations` views), filter `confirmations` to only those entries that are still present in `self.members` before comparing against `self.num_confirmations`. Alternatively, `delete_member` should iterate all `confirmations` maps and drop the removed member's entry from every entry it appears in, not just the requests it authored.

### Proof of Concept
Not independently executed in this session (no sandbox/terminal access); the trace below is derived directly from reading the contract logic cited above:
1. `new(members: [A,B,C,D], num_confirmations: 3)`.
2. `A.add_request_and_confirm(R)` → `R.confirmations = {A}`, `R.member = A`.
3. `B.confirm(R_id)` → `R.confirmations = {A,B}` (still `< 3`, so pending).
4. Separately, a fully-confirmed `DeleteMember{B}` request executes via `execute_request` → `delete_member(promise, B)`. This removes B from `self.members` and from `num_requests_pk`, but only deletes requests where `r.member == B` — `R` (authored by A) is untouched, so `R.confirmations` still contains B's entry.
5. `C.confirm(R_id)` → `assert_valid_request` passes (C is a live member); `confirmations.len() + 1 == 3 >= num_confirmations` → `execute_request(R)` runs immediately, even though B (one of the two "confirmers") is no longer a member, and only A and C are live approvers. [4](#0-3) [5](#0-4)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
