### Title
Stale confirmations from removed multisig keys allow a request to execute below the configured confirmation threshold - ([File: multisig/src/lib.rs])

### Summary
The `PriorityPool` report describes a state-desync bug where an internal accounting value (`accountQueuedTokens` / `getQueuedTokens()`) no longer matches the real, spendable resource because part of a state transition (the burn from the staking pool) was skipped while the rest of the operation (crediting/queue bookkeeping) proceeded. The closest reachable analog in this repository is in `multisig/src/lib.rs`, where the `confirmations` set used to satisfy `num_confirmations` is never cleaned up when a confirming key is removed — so the "confirmations counted" diverges from "confirmations by live members," letting a request execute with fewer currently-authorized keys than the configured threshold.

### Finding Description
`MultiSigContract::confirm()` counts entries in `self.confirmations.get(&request_id)` (a `HashSet<PublicKey>`) and executes the request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

When a key is removed via the `DeleteKey` multisig action, the cleanup logic only removes **requests originally created by** that public key (matched via `r.signer_pk == pk`), and only clears `confirmations` for *those* requests: [2](#0-1) 

It never scans other pending requests' `confirmations` sets to strip out entries where the deleted key was merely a **confirmer** (not the original requester). Since `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` stores raw public keys with no separate validity check against currently active keys, a stale confirmation from an already-deleted key remains counted toward the threshold for any other still-pending request: [3](#0-2) 

The equality that should hold is:
`count(confirmations[request_id]) == count(currently-live keys that confirmed request_id)`

After a `DeleteKey` action removes a member who had already confirmed some other pending request, this becomes:
`count(confirmations[request_id]) > count(currently-live keys that confirmed request_id)`

so a request can reach `num_confirmations` with one fewer live, currently-trusted signer than intended.

### Impact Explanation
This falls under the explicitly listed Critical impact category: "a multisig request executed below threshold." The multisig's entire security model relies on requiring `num_confirmations` *currently valid* keys to authorize sensitive actions such as `Transfer`, `AddKey` (full access key), or `FunctionCall`. If a removed/former key's stale confirmation still counts, an attacker who is (or was) one of the multisig signers can pre-stage a confirmation on a request, get removed from the signer set through a normal `DeleteKey` action, and the pending request can still be finalized by fewer live signers than the contract's configured quorum — enabling a transfer or privilege-escalating action that should not have been authorized under the current, up-to-date signer set.

### Likelihood Explanation
This requires no privileged/foundation access beyond being (or having been) one of the multisig's own key holders — a normal, in-scope actor for this contract. The sequence (confirm a request, then have/cause that key removed via a separate `DeleteKey` request, then let the remaining live signers push the original request over threshold) is straightforward and uses only the contract's public `add_request`/`confirm`/`execute_request` flow; no reliance on documented-away edge cases or third-party infrastructure.

### Recommendation
On `DeleteKey` (or any member-removal action), iterate over all entries in `self.confirmations` and remove the deleted public key from every confirmation set, not only from requests it originally created. Alternatively, validate confirmer keys against the currently active key set at the time a request is finalized in `confirm()`, discarding stale confirmations before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(3)` (3-of-n) with keys `K1, K2, K3, K4`.
2. `K1` calls `add_request` to create `RequestId=0` (e.g., a `Transfer`).
3. `K2` calls `confirm(0)` → `confirmations[0] = {K2}` (len=1, `1+1 < 3`, not yet executed).
4. Separately, `K1, K3, K4` create and confirm a `DeleteKey { public_key: K2 }` request to remove `K2` (e.g., because `K2` is compromised/departing) — this executes and calls `promise.delete_key(K2)`. Per `multisig/src/lib.rs:198-216`, this only removes requests where `signer_pk == K2` (i.e., requests *created* by K2); it does **not** touch `confirmations[0]`, so `confirmations[0]` still contains `K2`.
5. `K3` now calls `confirm(0)` → `confirmations.len() (1, containing removed K2) + 1 = 2 < 3` — not yet enough with only 2 real live confirmations, but the stale `K2` entry is still silently occupying one of the three required slots.
6. `K4` calls `confirm(0)` → `1 (stale K2) + 1 (K4 just added implicitly via check) ... reaching count 3` executes the `Transfer` even though only `K1(creator)`, `K3`, `K4` are currently valid signers who actively participated — `K2`'s confirmation, from a key that no longer exists on the account, was counted toward the 3-of-n threshold.

This demonstrates `num_confirmations` being satisfied using a confirmation from a key that is no longer a live member, breaking the threshold guarantee.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
