### Title
Loss-adjusted withdraw receipt is paid at par after a later defaulted-epoch claim clears `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug class is a teardown path where the "leftover cleanup" path (`ida_destroy`) races the per-object cleanup path (`nvme_delete_ctrl`): either you double-free or you wait forever for cleanup that another path was supposed to run. The analog lives in `IdleCreditVault.claimWithdrawRequest`, which chains three cleanup paths over the same per-user receipt ledger: `_claimDefaultedWithdrawRequest` → `_claimLossAdjustedWithdrawRequest` → `_claimFundedWithdrawRequest`. The loss-adjusted path is keyed on `lastWithdrawRequest[_user]`, but the defaulted path unconditionally clears that marker when it consumes the defaulted epoch, orphaning any older loss-adjusted receipt. That receipt then falls through to the funded path, which pays `withdrawsRequests[_user]` **at par**, even though the borrower only funded it at the `lossRecoveryPrice` haircut. One receipt is effectively paid more than once what was funded for it.

### Finding Description
`stopEpochWithDuration` with a loss calls `collectWithdrawFunds(_amount)` where `_amount < pendingBasis`; the strategy then sets `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws` (`IdleCreditVault.sol:411-430`). Each user's claim for that epoch stays in `withdrawsRequestsByEpoch[user][E]` and `withdrawsRequests[user]`, to be paid later at the haircut price via `_claimLossAdjustedWithdrawRequest`, which locates the epoch solely through `lastWithdrawRequest[user]` (`IdleCreditVault.sol:789-801`).

Now let the same user request a second withdrawal in a later epoch `D`, which sets `lastWithdrawRequest[user] = D` (`IdleCreditVault.sol:282`). If the borrower then defaults and `finalizeDefaultRecovery` runs with `defaultRecoveryEpoch = D`, the user's next `claimWithdrawRequest` executes `_claimDefaultedWithdrawRequest`, which calls `_clearWithdrawClaimForEpoch(user, D, true)` and hits `IdleCreditVault.sol:832-836`: since `lastWithdrawRequest[user] == D`, it sets `lastWithdrawRequest[user] = 0`. Control returns and `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = 0`, `lossRecoveryPriceByEpoch[0] == 0`, and returns 0 — the epoch-`E` loss-adjusted claim is silently skipped. `_claimFundedWithdrawRequest` then pays the residual `withdrawsRequests[user]` (still containing the full un-haircutted epoch-`E` basis, since `_clearWithdrawClaimForEpoch` only subtracted the epoch-`D` piece) at 1:1 par through `_transferFundedClaim` (`IdleCreditVault.sol:338-349`).

### Impact Explanation
Broken invariant: loss waterfall / fair burn. The borrower funded the epoch-`E` receipts only to `lossRecoveryPrice` (e.g. 80%), intentionally socializing the 20% shortfall across pending receipts. The attacker instead collects 100% of the epoch-`E` claim basis. The overpayment equals `claimBasis_E * (RECOVERY_FULL - lossRecoveryPrice_E) / RECOVERY_FULL` and is paid out of strategy-held underlying, i.e., directly from other lenders' and claimants' funds (or from `defaultRecoveryReserve` only after `_transferFundedClaim`'s reserve guard, so in practice from the funded pool). This is direct theft of a quantifiable amount: with a 100k USDC receipt and a 20% haircut, the attacker extracts ~20k USDC that was never funded.

### Likelihood Explanation
Fully attacker-controlled and unprivileged: the attacker is a KYC-passing lender who (1) requests a withdraw in the epoch that ends with a `stopEpochWithDuration` loss, (2) does not claim, (3) requests another withdraw in the epoch that ends in borrower default, then (4) calls `claimWithdrawRequest` once after `finalizeDefaultRecovery`. No privileged actor misbehaves; manager/owner calls (`stopEpochWithDuration`, `finalizeDefaultRecovery`) are honest. The only precondition is that the user holds receipts in both a loss-adjusted epoch and a later defaulted epoch — a routine usage pattern for any lender who stays in the pool across a lossy epoch and a subsequent default. No guard prevents it: the code comments at `IdleCreditVault.sol:832-835` even assume any remaining receipt is "already funded," which is false for partially funded loss-adjusted receipts.

### Recommendation
Do not derive the loss-adjusted claim epoch from the mutable `lastWithdrawRequest` marker. Either iterate/mark the specific epochs that have `lossRecoveryPriceByEpoch` entries per user (e.g., store a per-user loss-adjusted epoch list), or have `_clearWithdrawClaimForEpoch` check whether an older `lossRecoveryPriceByEpoch` claim exists before zeroing `lastWithdrawRequest` and leave the marker pointing at the loss epoch so `_claimLossAdjustedWithdrawRequest` runs before the funded path in the same call.

### Proof of Concept
Foundry fork PoC (scaffold, `test/foundry/` style of `IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptPaidAtParAfterDefault() public {
    // epoch E: user deposits (KYC'd), then requests withdraw
    uint256 amount = 100e6; // 100 USDC
    _depositWithUser(USER, amount);
    vm.prank(manager); cdoEpoch.startEpoch();
    _requestWithdrawWithUser(USER, strategyTokenBal); // receipt in epoch E

    // stopEpochWithDuration with loss: borrower funds only 80% of pendingWithdraws
    uint256 lossEpoch = strategy.epochNumber() + 1;
    uint256 lossAmount = /* 20% of total basis */;
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    _fundBorrowerAndApprove(cdoEpoch.expectedEpochInterest() + pendingToFund);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(10e18, 0, duration, lossAmount);
    assertGt(strategy.lossRecoveryPriceByEpoch(lossEpoch), 0);

    // epoch D: start new epoch, user requests a second withdraw -> lastWithdrawRequest = D
    vm.prank(manager); cdoEpoch.startEpoch();
    _depositWithUser(USER2, 50e6); // attacker adds a second receipt (or re-deposits)
    _requestWithdrawWithUser(USER, moreTokens);
    uint256 defaultEpoch = strategy.epochNumber() + 1;

    // borrower defaults; owner finalizes recovery at e.g. 50%
    _triggerDefaultAndFinalizeRecovery(defaultEpoch);

    // attacker claims once
    uint256 balPre = underlying.balanceOf(USER);
    vm.prank(address(cdoEpoch));
    strategy.claimWithdrawRequest(USER); // via IdleCDO call path
    uint256 received = underlying.balanceOf(USER) - balPre;

    // BUG: epoch-E component paid at PAR instead of lossRecoveryPrice
    uint256 eClaim = /* epoch-E withdrawsRequestsByEpoch[USER][E] */;
    uint256 expectedE = eClaim * strategy.lossRecoveryPriceByEpoch(lossEpoch) / 1e18;
    // received includes eClaim at par + defaulted epoch at recovery price
    assertGt(received, expectedE, "epoch-E receipt overpaid at par");
    // strategy balance is now short by eClaim - expectedE versus funded amounts
}
```

Key assertions: after `claimWithdrawRequest`, `strategy.withdrawsRequestsByEpoch(USER, lossEpoch)` remains nonzero (never cleared), `lastWithdrawRequest[USER] == 0`, and the underlying paid exceeds `Σ (basis_i * price_i)` by exactly the un-applied haircut on the loss epoch.
