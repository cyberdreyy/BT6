### Title
A Signer With No Local Approval Record For a Reorged Tenure's First Block Defaults To Treating It As "Poorly Timed," Always Permitting an Otherwise-Disallowed Reorg - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary

### Finding Description
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to build on (reorg) a prior tenure that already produced a block. The rule is: a reorg is only permitted if every reorged tenure has at most one globally-accepted block, *and* that block was proposed "close enough" to the next sortition (`first_proposal_burn_block_timing`). Timing is computed as `sortition_state_received_time - local_block_info.approved_time`. [1](#0-0) 

The bug is in how `local_block_info.approved_time` is handled when it is `None`: instead of treating "we have no local timing information" as unknown/unsafe (which should conservatively *reject* the reorg, matching the existing `local_block_info` == `None` branch a few lines above that already fails safe with `return Ok(false)`), the code falls back to `proposal_to_sortition = 0`:

```
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    ... superseded_tenures.push(tenure); continue; // reorg permitted for this tenure
}
```

Since `proposal_to_sortition = 0` is always less than any positive `first_proposal_burn_block_timing`, this branch *unconditionally* satisfies the "poorly timed" condition and marks the tenure as legitimately supersedable — regardless of what the real-world proposal-to-sortition timing actually was. This is structurally identical to the MarginSwap bug class: a piece of state that has not yet been locally established (the local "price"/timing baseline, i.e. `approved_time`) is substituted with a default value that trivially satisfies a downstream inequality check, instead of causing the check to fail closed.

The precondition for hitting this path is that `local_block_info` is present (the signer knows about the block, since `get_first_approved_block_in_tenure` returned `Some`) but that record's `approved_time` was never stamped — i.e., this particular signer never pre-committed/locally-accepted that specific block itself (the block reached global consensus through other signers' signatures while this signer had, e.g., rejected it, was still validating a competing proposal, or otherwise never individually approved it). Per `docs/signer-flows.md`, `approved_time` is stamped "at pre-commit or local acceptance (first wins)" — a signer that is a little behind, busy signing a sibling block, or otherwise never personally pre-committed to that particular tenure's first block will have `approved_time == None` even though the block is fully known and globally accepted.

### Impact Explanation
This directly breaks the intended safety property enforced by `check_parent_tenure_choice`/`validate_tenure_change_payload`: a signer whose local DB lacks a personal approval timestamp for a superseded tenure's first block will sign/pre-commit a tenure-change block that reorgs a tenure that was **not** actually poorly timed. That is a signer approving (signing) a **non-canonical/invalid reorg**, which falls squarely under the "Critical" impact category ("a signer signing an invalid, non-canonical, or conflicting block"). Because the miner fully controls when it proposes the reorging tenure-change block, and because "did not personally pre-commit to the sibling block" is a normal, single-signer-local condition (busy signing a competing proposal, temporarily behind on gossip, etc.) rather than something requiring cooperation from any other signer, this can be triggered without needing a majority of the signer set to misbehave or collude.

### Likelihood Explanation
Likelihood is moderate: it requires a specific but plausible local condition (a signer's own DB has no `approved_time` for the block being reorged, even though the block is known and reached global consensus) coinciding with a miner's attempt to reorg that tenure. This condition is a natural consequence of everyday signer/gossip asynchrony (each signer independently decides when/whether to pre-commit) rather than a rare edge case, and a miner can simply keep re-attempting the reorg proposal against every signer, exploiting whichever signers happen to have the gap. I was not able to fully trace every possible caller path that would set `approved_time` for a `GloballyAccepted` block that a signer never personally signed (this would require deeper review of `mark_globally_accepted`/`insert_block` semantics in `stacks-signer/src/signerdb.rs`), so the exact frequency of the precondition is not fully confirmed from the excerpts inspected here.

### Recommendation
Change the `None` branch for `local_block_info.approved_time` to fail closed rather than defaulting to `0`: if this signer never personally recorded an approval time for the reorged tenure's block, it should not be able to conclude anything about how "poorly timed" that block was, and the reorg should be rejected (`return Ok(false)`) or, at minimum, the signer should first fetch authoritative timing from the stacks-node (as is already done elsewhere in this function via `client.get_tenure_forking_info`) before deciding, rather than substituting a value that trivially satisfies the inequality.

### Proof of Concept
1. Signer S is a member of the active signer set. A miner proposes tenure T1's first (and only) block; S, for whatever reason (busy validating a sibling proposal, momentarily lagging on gossip), never itself pre-commits or locally-accepts that block, so its local `BlockInfo.approved_time` for that block stays `None`, even though other signers do sign it and it becomes globally accepted. [2](#0-1) 
2. A new sortition occurs and a miner (possibly the same or a colluding one) proposes a tenure-change block whose `parent_tenure_id` does not match T1's continuation (i.e., an attempt to reorg T1) while T1 still has only one globally accepted block.
3. `check_parent_tenure_choice` is invoked on S. `local_block_info` is found (S knows the block), but `approved_time` is `None`, so `proposal_to_sortition` is forced to `0`.
4. `Duration::from_secs(0) < first_proposal_burn_block_timing` is true, so S treats T1 as "poorly timed" and marks it superseded, permitting the reorg — even though, per the node's actual tenure-forking data (`tenures_reorged`) and the real-world clock, T1's block was proposed well outside the allowed window. [1](#0-0) 
5. S proceeds to pre-commit/sign a tenure-change block that reorgs a tenure it should have refused to reorg, i.e., it signs a non-canonical/invalid reorg from the network's perspective.
