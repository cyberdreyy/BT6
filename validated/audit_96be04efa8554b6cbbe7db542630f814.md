Based on my investigation, I found a real analog in the codebase matching the report's root-cause pattern: an admin setter that swaps a reference to an external "calculator/factory" contract while leaving state stranded/desynced in the old contract.

### Title
`FeeVault::setFeeCalculator()` strands accrued vault/protocol fees in the old fee calculator, permanently freezing them - (File: v3/src/core/FeeVault.sol)

### Summary
`FeeVault.setFeeCalculator()` overwrites the vault's `feeCalculator` pointer with a new address and registers the vault with the new calculator, but never claims or migrates the `accruedFees`/`accruedProtocolFees` that had built up in `_vaultAccruals[vault]` on the old calculator. `claimFees()`/`claimProtocolFees()` on `FeeVault` always call the *current* `feeCalculator`, so any fees accrued under the previous calculator become permanently unreachable. This mirrors the disclosed `StakingRewardManager::setStakingRewardsFactory()` pattern where re-pointing a factory/registry reference desyncs parallel state that only the old contract retained.

### Finding Description
`PriceAndFeeCalculatorV2` (an `IFeeCalculator` implementation used as `feeCalculator`) accrues TVL/performance fees per vault into `VaultAccruals` inside `BaseFeeCalculator._vaultAccruals[vault]`, updated by `_accrueFees()` on every `setAnchorPrice`/`unpauseVault` call [1](#0-0) . These accrued amounts are only claimable through `IFeeCalculator.claimFees(uint256)`, which is invoked exclusively by the vault currently pointing to that calculator, via `FeeVault.claimFees()` [2](#0-1) .

`FeeVault.setFeeCalculator()` is a `requiresAuth` admin function that simply overwrites the `feeCalculator` storage pointer and registers the vault on the new calculator, with no interaction with the old calculator to claim, forward, or reserve outstanding `accruedFees`/`accruedProtocolFees`: [3](#0-2) 

Once the pointer is switched, `claimFees()`/`claimProtocolFees()` only ever call `feeCalculator.claimFees(...)` (the new one) [4](#0-3) , so the `VaultAccruals` entry keyed by the vault address on the *old* calculator becomes orphaned — there is no external path back to it since `claimFees`/`claimProtocolFees` in `BaseFeeCalculator` key off `msg.sender` (the vault) [5](#0-4) , and only the vault itself can trigger a claim on a calculator.

Notably, `AeraVaultV2` (v2) guards its analogous `setHooks`/`setGuardianAndFeeRecipient` functions with a `reserveFees` modifier before changing state [6](#0-5) , showing the protocol's own established pattern of reserving/settling fee state before an address swap — a step that is absent from v3's `setFeeCalculator()`.

### Impact Explanation
Any already-accrued but unclaimed `accruedFees` (owed to `feeRecipient`) and `accruedProtocolFees` (owed to the protocol) at the time of a calculator swap become permanently frozen/unclaimable — the tokens remain physically in the vault (`FEE_TOKEN` balance) but the accounting record needed to claim them lives on a calculator the vault no longer talks to. This is a freezing of legitimately earned, unclaimed yield/fees, consistent with a live Medium-severity temporary/permanent freeze-of-funds impact.

### Likelihood Explanation
This requires the vault's authorized role (`requiresAuth` on `setFeeCalculator`) to call it — the same "admin re-points an external reference" precondition as the original disclosed report (`setStakingRewardsFactory` also required `MAINTAINER_ROLE`). This is a plausible, even likely, operational scenario (e.g., protocol upgrading/migrating to a new `PriceAndFeeCalculatorV2` deployment for parameter changes) with no code path providing recovery, making it a foreseeable operational hazard rather than a purely theoretical one.

### Recommendation
In `setFeeCalculator()`, before switching, call the old `feeCalculator.claimFees(...)`/`claimProtocolFees(...)` (or an explicit `migrateFees`/`reserveFees` mechanism) to flush the vault's outstanding `accruedFees` and `accruedProtocolFees` from the old calculator, transferring them to `feeRecipient` and the protocol fee recipient, before pointing to the new calculator — mirroring the `reserveFees` pattern already used in `AeraVaultV2`.

### Proof of Concept
1. Deploy `PriceAndFeeCalculatorV2` (`calcA`) and a `FeeVault`-derived vault pointed at `calcA`; set `vaultFees` (tvl/performance) via `setVaultFees`.
2. Call `setAnchorPrice` repeatedly (as accountant) over time so `_accrueFees` builds nonzero `accruedFees`/`accruedProtocolFees` in `calcA._vaultAccruals[vault]`; confirm via `getVaultState(vault)` that `accruedFees > 0`.
3. As the vault's authorized role, call `vault.setFeeCalculator(calcB)` (a freshly deployed calculator) — assert this succeeds without reverting and without any interaction with `calcA`.
4. Call `vault.claimFees()` — assert it only reads/claims from `calcB` (fresh state, `accruedFees == 0`), and that `calcA.claimFees(...)` can never again be invoked on behalf of `vault` (no external caller can spoof `msg.sender == vault`).
5. Assert `calcA._vaultAccruals[vault].accruedFees` remains permanently nonzero and unreachable, while the corresponding `FEE_TOKEN` balance sits idle in the vault — demonstrating frozen, unclaimable fees.

    function _accrueFees(address vault, uint256 price, uint256 timestamp) internal {
        VaultPriceStateV2 storage vaultPriceState = _vaultPriceStates[vault];

        uint256 timeDelta;
        unchecked {
            timeDelta = timestamp - vaultPriceState.anchorTimestamp + vaultPriceState.accrualLag;
        }

        // Interactions: get the current total supply
        uint256 currentTotalSupply = IERC20(vault).totalSupply();
        uint256 minTotalSupply = Math.min(currentTotalSupply, uint256(vaultPriceState.lastTotalSupply));
        uint256 minUnitPrice = Math.min(price, uint256(vaultPriceState.anchorPrice));

        uint256 tvl = Math.mulDiv(minUnitPrice, minTotalSupply, UNIT_PRICE_PRECISION);

        VaultAccruals storage vaultAccruals = _vaultAccruals[vault];
        uint256 vaultFeesEarned = _calculateTvlFee(tvl, vaultAccruals.fees.tvl, timeDelta);

        uint256 protocolFeesEarned = _calculateTvlFee(tvl, protocolFees.tvl, timeDelta);

        if (price > vaultPriceState.highestPrice) {
            uint256 profit = Math.mulDiv(price - vaultPriceState.highestPrice, minTotalSupply, UNIT_PRICE_PRECISION);
            vaultFeesEarned += _calculatePerformanceFee(profit, vaultAccruals.fees.performance);
            protocolFeesEarned += _calculatePerformanceFee(profit, protocolFees.performance);

            // Effects: update the highest price
            vaultPriceState.highestPrice = uint128(price);
        }

        // Effects: update the accrued fees
        vaultAccruals.accruedFees += vaultFeesEarned.toUint112();
        vaultAccruals.accruedProtocolFees += protocolFeesEarned.toUint112();

        // Effects: update the last total supply and last fee accrual
        vaultPriceState.lastTotalSupply = currentTotalSupply.toUint128();
        vaultPriceState.accrualLag = 0;
    }

    function claimFees() external onlyFeeRecipient returns (uint256 feeRecipientFees, uint256 protocolFees) {
        address protocolFeeRecipient;

        // Interactions: claim the fees
        (feeRecipientFees, protocolFees, protocolFeeRecipient) =
            feeCalculator.claimFees(FEE_TOKEN.balanceOf(address(this)));

        // Requirements: check that the fee recipient has earned fees
        require(feeRecipientFees != 0, Aera__NoFeesToClaim());

        // Interactions: transfer the fees to the fee recipient
        FEE_TOKEN.safeTransfer(msg.sender, feeRecipientFees);
        // Log the fees claimed event
        emit FeesClaimed(msg.sender, feeRecipientFees);

        if (protocolFees != 0) {
            // Interactions: transfer the protocol fees to the protocol fee recipient
            FEE_TOKEN.safeTransfer(protocolFeeRecipient, protocolFees);
            // Log the protocol fees claimed event
            emit ProtocolFeesClaimed(protocolFeeRecipient, protocolFees);
        }
    }
