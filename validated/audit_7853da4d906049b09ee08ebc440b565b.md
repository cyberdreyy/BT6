### Title
JWT single-use guarantee can be bypassed by replaying a token after `cleanupOldEntries` evicts its `jti`, if `JWTReplayPeriodMs` is configured shorter than the JWT's `exp` lifetime - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` enforces JWT single-use solely via an in-memory `jti` cache (`jwtReplayCache`), and `cleanupOldEntries` evicts entries based on `h.jwtCache.cleanupPeriod` (derived from `ServiceConfig.JWTReplayPeriodMs`), independent of the JWT's own `exp` claim. Because `VerifyRequestJWT` in `core/utils/jwt.go` only rejects tokens whose `exp` has actually lapsed, a JWT can be replayed successfully after its `jti` is evicted from the cache but before its `exp` timestamp, if the operator configures a replay-cache cleanup period shorter than the maximum allowed JWT lifetime (`maxJWTExpiryDuration` = 5 minutes).

### Finding Description
`Authorize` (workflow_metadata_handler.go:80-108) calls `utils.VerifyRequestJWT` to validate signature, digest, `iat`, and `exp`, then separately checks `h.jwtCache.isReplay(claims.ID)` for single-use enforcement, and finally calls `h.jwtCache.recordUsage(claims.ID)`. The replay cache is a simple `map[string]time.Time` keyed by `jti`, cleaned up periodically by `cleanupOldEntries` (workflow_metadata_handler.go:415-426), invoked every `h.jwtCache.cleanupPeriod` from a ticker in `Start` (workflow_metadata_handler.go:298-304) with `cutoff = now - cleanupPeriod`.

Crucially, `cleanupPeriod` is fully decoupled from the JWT's own `exp` claim: `VerifyRequestJWT` (core/utils/jwt.go:284-298) only validates that `exp - iat <= maxJWTExpiryDuration` (5 minutes) and that the token hasn't actually expired — it never consults or bounds itself to `JWTReplayPeriodMs`. If the gateway operator sets `ServiceConfig.JWTReplayPeriodMs` to a value shorter than a token's actual lifetime (e.g., 1 minute, while tokens can legitimately carry up to a 5-minute `exp`), then:
1. A signer creates a valid JWT with `iat=T`, `exp=T+5min` and uses it once — `Authorize` succeeds, `recordUsage` stores `jti -> T`.
2. On the next cleanup tick (period ≈ 1 min), `cleanupOldEntries(now - 1min)` deletes the entry because `createdAt.Before(cutoff)`.
3. The exact same JWT token (signature, digest, `jti`) is replayed to `Authorize` before `T+5min`. `VerifyRequestJWT` passes (exp not yet lapsed, digest matches), and `isReplay(claims.ID)` returns `false` because the cache no longer holds the `jti`. The request is authorized a second time.

This breaks the single-use invariant purely as a function of configuration and timing (`JWTReplayPeriodMs` vs. token TTL), not of any external attacker action against the cache itself — but it is attacker-exploitable in that the attacker (who intercepted or otherwise obtained a previously-used valid JWT for a workflow they are authorized to sign for, or an intercepted signed request) can deliberately time the replay to land after a cleanup cycle and before `exp`.

### Impact Explanation
Impact is scoped to duplicate authorization of a single previously-used JWT-signed trigger request within its remaining validity window — corresponding to a "duplicate/replay of authenticated request" class rather than full authentication bypass, since the attacker still needs a valid, previously-issued JWT signed by an authorized workflow signer (not something they can forge). If such a JWT is intercepted or reused, the second authorization can trigger a duplicate workflow-owner-initiated action (e.g., re-triggering a workflow execution), which is undesirable request-impersonation/replay behavior but requires possession of the original signed token.

### Likelihood Explanation
This is contingent on gateway configuration: `JWTReplayPeriodMs` must be set materially shorter than the max JWT lifetime the deployment allows tokens to carry (up to `maxJWTExpiryDuration` = 5 minutes) for the exploit window to be non-trivial. I was unable to fully verify what default value `JWTReplayPeriodMs` is configured to in `http_handler.go`/deployment configs within the remaining budget, so whether this is realistically reachable under default settings (vs. only under an operator misconfiguration) is uncertain. If defaults set `JWTReplayPeriodMs` >= `maxJWTExpiryDuration`, the exploit window would not exist under default configuration, making this effectively a configuration-dependent design gap rather than a directly exploitable default-configuration bug.

### Recommendation
Decouple replay-cache retention from a fixed cleanup period tied only to `JWTReplayPeriodMs`; instead retain each `jti` at least until its own `exp` claim (store `exp` alongside `jti` and only evict once `now > exp`), or enforce at startup that `JWTReplayPeriodMs >= maxJWTExpiryDuration` so the cache can never evict a still-valid token's `jti` before its `exp`.

### Proof of Concept
Go unit test in `workflow_metadata_handler_test.go`:
1. Construct a `WorkflowMetadataHandler` with `jwtCache = newJWTReplayCache(1 * time.Second)` and a workflow with one authorized signer.
2. Create a JWT via `utils.CreateRequestJWT` with `WithExpiry(5 * time.Second)` (exp well beyond the 1s cleanup period).
3. Call `Authorize(workflowID, token, req)` — assert success.
4. Manually invoke `h.jwtCache.cleanupOldEntries(time.Now())` (or wait slightly and use `time.Now().Add(-cleanupPeriod)` per production ticker logic) to simulate the cleanup tick evicting the just-used `jti`.
5. Call `Authorize(workflowID, token, req)` again with the same token, before the 5-second `exp` elapses.
6. Assert: if the fix is not applied, the second call unexpectedly returns `(key, nil)` (replay succeeds); after the fix (retention tied to `exp` or enforced `JWTReplayPeriodMs >= maxJWTExpiryDuration`), the second call must return the "JWT token has already been used" error.
