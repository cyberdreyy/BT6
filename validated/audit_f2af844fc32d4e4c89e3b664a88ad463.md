### Title
Repeated proposal timeouts let a single signer inflate per-txid rejection weight past the "blocking minority" threshold - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListenerComms::reset_rejections` is called by the mining coordinator every time a block proposal round times out without reaching either the accept or reject threshold, so the same block can be retried repeatedly against the same signer set [1](#0-0) . This reset clears `responded_signers` (the gate that prevents a signer's weight from being double-counted) and zeroes `total_weight_rejected`, but it never touches `failed_txids`, the per-txid weight map fed by rejection messages [2](#0-1) .

### Finding Description
`BlockStatus` tracks, per proposal, a `HashMap<Txid, FailedTxInfo>` where `FailedTxInfo::total_weight`/`problematic_weight` accumulate the weight of every signer who reported a given transaction as bad [3](#0-2) . The accumulation is gated by `block.responded_signers.insert(slot_id)`, i.e. each signer's weight is meant to be added to `failed_txids` at most once per block [4](#0-3) .

When a proposal round times out, the coordinator calls `reset_rejections`, which clears `responded_signers` and zeroes `total_weight_rejected` so the *same* proposal can be retried, explicitly noting only approvals can't be cleared "because an old approval could always be used to make a block reach the approval threshold" [2](#0-1) . However, `failed_txids` is not part of this reset. Since the re-count gate (`responded_signers`) is cleared but the accumulator it protects (`failed_txids[txid].total_weight/problematic_weight`) is not, a signer who rejects the same re-proposed block with the same txid complaint on every retry round has their weight added to `failed_txids` again each round, even though `total_weight_rejected` itself is correctly reset and recomputed fresh.

`get_block_status` uses this weight, once a real rejection majority is eventually reached in some later round (via correctly-reset `total_weight_rejected`), to decide whether to *permanently* ban a txid from all future block templates, gated on `info.problematic_weight > blocking_minority` (i.e., >30% of total weight) [5](#0-4) . Because `failed_txids` weight is never reset across retries while the gate protecting it is, a single low-weight signer (well under 30%) can cause their own repeated single-signer complaint to be counted N times across N timeout/retry cycles, exceeding `blocking_minority` purely through repetition rather than through distinct signer weight — an "aggregated weight" that no longer reflects the real distinct signer set that support it.

### Impact Explanation
This is a miscounted-response bug analogous to the external report's failure to decrement a counter that gates repeatable state (there: `rewardsUnclaimed`; here: `failed_txids` weight vs. the `responded_signers` gate). It lets a signer far below the 30% blocking-minority weight force the miner to treat a transaction as if a blocking minority reported it, causing the transaction to be permanently excluded from future block templates network-wide based on inflated, repeat-counted weight rather than genuine distinct-signer support.

### Likelihood Explanation
Triggerable by any single signer (no majority required) simply by continuing to reject the same re-proposed block/txid across multiple timeout rounds, which is a normal occurrence whenever a proposal repeatedly times out (e.g. due to slow signers or contested transactions) — no colluding majority or privileged access is needed.

### Recommendation
Clear (or otherwise properly decrement) `failed_txids` for a given block in `reset_rejections` alongside `responded_signers`/`total_weight_rejected`, or key the per-txid weight accumulation to the current round rather than accumulating indefinitely across retries.

### Proof of Concept
1. Miner proposes block `B` containing txid `T`.
2. Signer `S` (weight `w` < 30% of total) rejects `B`, reporting `T` as `ProblematicTransaction`; `failed_txids[T].total_weight = w`, `problematic_weight = w`.
3. Round times out (not enough weight to cross accept/reject thresholds); coordinator calls `reset_rejections`, clearing `responded_signers` and `total_weight_rejected` but leaving `failed_txids[T]` at `w`.
4. Miner retries the same proposal `B`. `S` rejects again with the same reason; since `responded_signers` was cleared, the gate re-fires and `failed_txids[T].total_weight`/`problematic_weight` become `2w`.
5. Repeat steps 3–4 enough times that `problematic_weight` exceeds `blocking_minority` (30% of total weight), even though only `S`'s single-signer weight `w` (< 30%) ever actually objected.
6. Once any round's genuine rejection majority is reached (unrelated signers, or eventually `S` plus others), `get_block_status` sees `info.problematic_weight > blocking_minority` and permanently excludes `T` from all future proposals, based on inflated repeat-counted weight rather than true distinct-signer support.

    /// Reset rejections for a block proposal.
    /// This is used when a block proposal times out and we need to retry it by
    /// clearing the block's rejections. Block approvals cannot be cleared
    /// because an old approval could always be used to make a block reach
    /// the approval threshold.
    pub fn reset_rejections(&self, signer_sighash: &Sha512Trunc256Sum) {
        let (lock, _cvar) = &*self.blocks;
        let mut blocks = lock.lock().expect("FATAL: failed to lock block status");
        if let Some(block) = blocks.get_mut(signer_sighash) {
            block.responded_signers.clear();
            block.total_weight_rejected = 0;

            // Add approving signers back to the responded signers set
            for (slot_id, _) in block.gathered_signatures.iter() {
                block.responded_signers.insert(*slot_id);
            }
        }
    }
