### Title
TVL deposit limit checked against declared `_amount` but shares minted on actual received balance delta, allowing limit bypass - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDO._deposit` enforces the guarded-launch TVL cap via `_guarded(_amount)`, which validates only the user-supplied `_amount` parameter against `getContractValue() + _amount > limit`. However, tranche shares are actually minted against the measured balance delta `_contractTokenBalance(_token) - _preBal` (IdleCDOCreditVault.sol:196,206). This mirrors the zkSync bug where the deposit limit was verified on `_l2Value` while ETH was minted on `msg.value`: the value that is checked and the value that is credited diverge.

### Finding Description
In `contracts/IdleCDOCreditVault.sol`:

```solidity
// line 196 - limit checked on the declared parameter
_guarded(_amount);
...
// line 203-206 - shares minted on the ACTUAL received amount
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
_minted = _mintSharesAtCurrPrice(_contractTokenBalance(_token) - _preBal, msg.sender, _tranche);
```

The credited amount is the post-transfer balance delta, which is `>= _amount` if the vault's underlying balance increases by more than the transferred `_amount` within the same transaction. An attacker can inflate the delta two ways:

1. **Same-tx direct transfer:** atomically `token.transfer(cdo, X)` then call `depositAA(1 wei)` / `depositBB(1 wei)`. `_guarded(1)` passes trivially regardless of `limit`, while `_minted` is computed over `X + 1` because the donation lands between `_preBal` and the post-transfer balance read.
2. **Balance-increasing tokens:** any underlying whose `transferFrom`/balance accrues more than the requested amount (rebasing or reward-accruing tokens) inflates the delta without any corresponding `_guarded` check.

The same pattern exists in `IdleCDO.sol`'s own `_deposit` for standard CDOs, since `GuardedLaunchUpgradable._guarded` (GuardedLaunchUpgradable.sol:45-50) only sees the parameter, not the realized inflow.

`strategy.deposit(_amount)` (line 211) only pushes `_amount` to the strategy, so the excess stays as stray balance at the CDO — but the attacker still holds shares minted against it at fair price.

### Impact Explanation
The guarded-launch TVL cap (`limit`) — the mechanism intended to bound protocol exposure to a new credit vault/CDO — is unenforceable. An unprivileged, KYC-passing attacker can push `getContractValue()` arbitrarily above `limit` in one transaction. Consequences:

- The risk cap is permanently defeated for that vault; the attacker controls share supply far beyond the governance-set bound.
- Once `getContractValue() > limit`, every subsequent legitimate `depositAA`/`depositBB` reverts with `ContractLimitReached()` — deposits for all other users are frozen for as long as the cap is exceeded (temporary freezing of the deposit path).
- In the credit-vault context, an oversized deposit inflates `totEpochDeposits`/epoch principals the borrower is expected to service, degrading the solvency guarantees the cap was meant to protect.

The attacker pays fair value for the minted shares (no direct theft of existing NAV), which bounds the severity to the bypassed cap itself — consistent with the external report's impact class.

### Likelihood Explanation
Low-to-medium: requires only a funded attacker (any EOA/contract; KYC only if the deployment enforces `isWalletAllowed`). The same-tx donation path works with any standard ERC20 underlying and no privileged role, no timing dependency, and no oracle manipulation. It is constrained only by the attacker's capital.

### Recommendation
Compute the limit check on the realized amount, not the parameter:

```solidity
uint256 _preBal = _contractTokenBalance(_token);
_transferUnderlyingsFrom(msg.sender, address(this), _amount);
uint256 _received = _contractTokenBalance(_token) - _preBal;
_guarded(_received);              // check what was actually credited
_minted = _mintSharesAtCurrPrice(_received, msg.sender, _tranche);
```

Alternatively, skim any non-requested balance increase (donations) into `unclaimedFees`/`_skimDonatedAssets` accounting before minting, and explicitly revert if `_received > _amount` for non-rebasing underlyings.

### Proof of Concept
Foundry fork PoC sketch (running/buffer epoch phase, fixed-APR mode, `limit = 1000e6` USDC):

```solidity
function test_DepositLimitBypass() public {
    // limit = 1000 USDC, vault already at 999 USDC TVL
    uint256 limit = 1000e6;
    // attacker funds
    deal(USDC, attacker, 2_000_000e6);

    vm.startPrank(attacker);
    // Step 1: direct transfer — lands on CDO before the deposit's balance read
    IERC20(USDC).transfer(address(cdo), 500_000e6);
    // Step 2: deposit dust — _guarded(1) passes since 999e6 + 1 <= limit? (see note)
    // For the pure mismatch, deposit within the declared bound:
    IERC20(USDC).approve(address(cdo), 1);
    uint256 minted = cdo.depositAA(1);
    vm.stopPrank();

    // minted corresponds to 500_000e6 + 1 worth of shares at priceAA,
    // while _guarded only ever validated "1" against the limit.
    assertGt(cdo.getContractValue(), limit);
    // all subsequent honest deposits now revert
    vm.expectRevert(); // ContractLimitReached()
    cdo.depositAA(1e6);
}
```

Variant for the more realistic case where TVL is already below the cap by only `D`: donate `L` via `transfer`, then `depositAA(D)` — `_guarded(D)` passes (`TVL_before_donation + D <= limit` reads the pre-donation `getContractValue` inside `_guarded`, which is evaluated before `_updateAccounting`/transfer), while the delta credits `D + L`. Either way, `getContractValue() > limit` and the cap is broken.

**Caveat:** where `getContractValue()` reads the raw token balance, the pre-donation already raises TVL before `_guarded` runs, so the cleanest exploit path is donation-in-the-same-tx *before* the deposit call combined with a nominal deposit, or vaults whose `getContractValue` derives from strategy-side accounting that excludes idle CDO balance (in which case the donation is invisible to the check entirely). The mint-on-delta accounting confirmed in the code makes the mismatch real; the exact bypass magnitude depends on the specific `getContractValue()` implementation of the deployed variant, which I did not fully trace within this pass.
