### Title
Loss-adjusted withdraw receipt is paid at par after a re-request shifts `lastWithdrawRequest` past the loss epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Jetspeed traversal relies on a caller-controlled identifier escaping the intended container (`../../webapps/x.jsp` escapes the extraction dir). The analog here: `IdleCreditVault._claimLossAdjustedWithdrawRequest` uses `lastWithdrawRequest[_user]` — the *latest* request epoch — as the sole index into `lossRecoveryPriceByEpoch`. A second `requestWithdraw` in a later epoch overwrites that marker, so a receipt that was loss-adjusted in epoch N is silently "re-rooted" into epoch N+1 and paid out at par by `_claimFundedWithdrawRequest`. This breaks the one-receipt-one-priced-payout invariant and drains funded reserves owed to other claimants.

### Finding Description
`requestWithdraw` records both a per-epoch basis and a running aggregate, and sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) . When the borrower under-funds a stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and clears only the *global* `pendingWithdraws` — per-user `withdrawsRequests`/`withdrawsRequestsByEpoch` keep the full un-haircut basis [2](#0-1) .

At claim time, `claimWithdrawRequest` first calls `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [3](#0-2) . If the user made a *new* request in a later (fully funded) epoch, `lastWithdrawRequest` points at that epoch, the lookup returns 0, and the loss path is skipped entirely. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the aggregate that still contains the epoch-N basis — at par [4](#0-3) . Re-requesting without claiming is an explicitly supported flow ("he will have to wait for another epoch to claim both requests"), and the only guard (`epochNumber <= lastWithdrawRequest` while epoch is running) does not prevent it [5](#0-4) .

### Impact Explanation
Direct theft / insolvency. For a loss epoch with recovery price `p`, the attacker extracts `(1 − p) × requestBasis` more than owed. The excess is paid from the same strategy-held funded balance that backs other users' pending claims, so honest claimants are left unpayable (insolvency). On a 50% loss epoch with a 100k USDC request, the attacker steals 50k USDC of reserve.

### Likelihood Explanation
Requires only that the attacker held a pending receipt in a `stopEpochWithDuration` loss epoch (borrower under-funding) and that a subsequent epoch funds normally — both are ordinary, non-privileged market conditions (a KYC'd lender as attacker). No privileged cooperation is needed; sequencing is entirely within attacker control.

### Recommendation
Track the loss-adjusted epoch per receipt rather than per user-latest: either store `lossEpoch` alongside each request, or iterate `withdrawsRequestsByEpoch` for *any* epoch with a nonzero `lossRecoveryPriceByEpoch` (e.g., persist the earliest pending epoch), clearing the basis at `claimBasis × lossRecoveryPrice` before the funded claim pays the remainder at par.

function testLossEpochReceiptPaidAtParAfterReRequest() external {
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount * 2); // attacker + other liquidity
    _startEpochAndCheckPrices(0);

    // 1. attacker requests withdraw in epoch N
    uint256 basis = cdoEpoch.requestWithdraw(
        AAtranche.balanceOf(attacker), address(AAtranche));

    // 2. epoch N ends under-funded: collectWithdrawFunds stores
    //    lossRecoveryPriceByEpoch[N] = p < 1e18 (stopEpochWithDuration loss)
    _stopEpochWithPartialFunding(); // e.g. p = 0.5e18

    // 3. attacker does NOT claim; requests again in epoch N+1
    //    lastWithdrawRequest[attacker] = N+1,
    //    withdrawsRequests[attacker] still contains epoch-N basis
    _startEpochAndCheckPrices(1);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    _stopEpochFullyFunded(); // lossRecoveryPriceByEpoch[N+1] == 0

    // 4. claim: loss path skipped, funded claim pays full aggregate at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 paid = underlying.balanceOf(attacker) - balPre;

    uint256 expected = basis * strategy.lossRecoveryPriceByEpoch(N) / 1e18;
    assertGt(paid, expected + 1); // stolen = basis * (1 - p)
    // later honest claimant reverts/shortfall on _transferFundedClaim reserve check
}
```

Key mechanics confirmed in code: `collectWithdrawFunds` never decrements per-user `withdrawsRequests` [6](#0-5) , and the funded claim pays the aggregate `withdrawsRequests[_user]` then zeroes it [4](#0-3) .

Uncertainty: exact helper names for the fork setup (`_stopEpochWithPartialFunding`) are schematic; the claim-ordering logic in `claimWithdrawRequest` (lines 301-314) and the `lastWithdrawRequest` overwrite in `requestWithdraw` (line 282) are verified in source.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
