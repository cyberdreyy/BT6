This confirms the guard exists exactly where the question predicts a proof would go. The `verify_signer_signatures` function in `stackslib/src/chainstate/nakamoto/mod.rs` derives the reward set independently from the block's own sortition (via `reward_set` passed in, tied to `sn_rc`/consensus hash), while the signer's own gate in `stacks-signer/src/v0/signer.rs::handle_block_proposal` rejects any proposal whose `reward_cycle` doesn't match its own configured `self.reward_cycle` before doing any signing work.

#### No vulnerability found for this question.

**Why the claimed equality break doesn't hold:**

`Signer::handle_block_proposal` in [1](#0-0)  explicitly checks `block_proposal.reward_cycle != self.reward_cycle` and returns immediately (ignoring the proposal) before any weight/threshold logic runs. `self.reward_cycle` is fixed at construction time from `SignerConfig.reward_cycle` [2](#0-1) , which itself came from the reward cycle the runloop explicitly requested via `get_signer_config(reward_cycle)` / `get_parsed_reward_set(reward_cycle)` [3](#0-2) . So the signer never applies cycle-N weights (`self.signer_weights`) to a proposal carrying `reward_cycle = N+1`; it drops it outright.

`block_proposal.reward_cycle` itself is set by the miner from the sortition's burn height via `burnchain.block_height_to_reward_cycle(election_sortition.block_height)` [4](#0-3) , i.e., it is tied to the winning sortition's burn height, not to when the RPC happened to be polled. A signer running two `ConfiguredSigner` instances (one per parity, keyed by `reward_cycle % 2`, per `stacks_signers: HashMap<u64, ConfiguredSigner<...>>` in `runloop.rs`) only signs with the instance whose `reward_cycle` field matches the proposal's declared cycle.

On the node side, `verify_signer_signatures` in [5](#0-4)  takes a `reward_set: &RewardSet` argument that callers resolve from the block's own sortition/consensus hash — e.g. `stackslib/src/net/relay.rs` resolves `sn_rc` from the sortition tied to the block before calling `verify_signer_signatures(reward_set, epoch_id)` [6](#0-5) , and `unsolicited.rs::check_nakamoto_block_signer_signature` similarly takes `reward_cycle` as an explicit parameter tied to the block's sortition [7](#0-6) . There is no path by which the node uses a reward cycle other than the one implied by the block's own sortition/consensus hash, and no path by which the signer signs under a mismatched cycle — the explicit equality check in `handle_block_proposal` is a hard gate, not a race-prone comparison. Winning a single miner slot at a cycle boundary does not let an attacker force a mismatch: it only lets them submit a proposal whose declared `reward_cycle` is checked against each signer's own fixed configuration, and any signer not configured for that cycle simply ignores it rather than mis-tallying weights.

The premise that "a signer signs using `signer_weights` for N while the node validates against N+1" is not supported by the code: the guard at `handle_block_proposal`'s reward-cycle check [8](#0-7)  forecloses exactly the scenario the question describes.
