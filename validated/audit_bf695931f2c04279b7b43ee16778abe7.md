### Title
Instant-withdraw receipts keyed to their request epoch are skipped by default-recovery accounting when default finalizes in a later epoch — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug reused a timer object by label across two revisions, where the second revision's fields were never initialized for that object. The analog here is a key/label reuse across two "modes" of the same receipt namespace: `requestInstantWithdraw` records a user's claim basis under `instantWithdrawClaimsByEpoch[epochNumber]` / `instantWithdrawsRequestsByEpoch[_user][epochNumber]` at request time (IdleCreditVault.sol:371-372), but default finalization (`defaultPendingClaimBasis`, line 647) and defaulted-claim payout (`_claimDefaultedInstantWithdrawRequest`, lines 843-844) both read those mappings only at `epochNumber`/`defaultRecoveryEpoch` — the epoch in which default is *finalized*, not the epoch in which the receipt was created. An unfunded instant receipt that straddles an epoch boundary is therefore invisible to both the recovery basis and the claim path.

### Finding Description
1. Attacker (any KYC'd lender/tranche holder) calls `requestInstantWithdraw` late in epoch N. The CDO has insufficient liquidity, so the receipt is minted to the user and `pendingInstantWithdraws += _amount`, `instantWithdrawsRequestsByEpoch[user][N] += _amount`, `instantWithdrawClaimsByEpoch[N] += _amount` (lines 360-374). Nothing in `stopEpoch`/`startEpoch` clears `pendingInstantWithdraws` or the per-epoch claim mappings — funding is lazy, via `collectInstantWithdrawFunds` when the borrower repays.
2. Epoch N ends, `epochNumber` increments to N+1 (line 610). The receipt remains unfunded.
3. Borrower defaults during epoch N+1; `finalizeDefaultRecovery` runs. `defaultPendingClaimBasis()` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` where `epochNumber = N+1`. The attacker receipt lives under key `N`, so its basis is excluded. Likewise `_defaultPrefundedInstantReserve()` (lines 716-723) reads `instantWithdrawClaimsByEpoch[N+1]`, so no reserve is attributed to it.
4. `defaultRecoveryEpoch = N+1` is stored (line 693). When the user later calls `claimInstantWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch=N+1] = 0` and returns early (lines 843-846). The stale receipt basis under epoch N is never cleared and never paid through the recovery path.

The broken invariant is "one receipt, one payout": the user's strategy-token receipt still exists (`instantWithdrawsRequests[user] != 0`) but the default-recovery machinery addressed it by the wrong label (finalization epoch instead of request epoch), exactly paralleling `mod_timer()` being applied to a label-created object of a different type.

### Impact Explanation
The unfunded receipt's underlying claim is permanently unpayable through the recovery path: `instantWithdrawsRequestsByEpoch[user][N]` can never equal `defaultRecoveryEpoch`, so the haircut payout is skipped, while `pendingInstantWithdraws` was already decremented only via `_claimDefaultedInstantWithdrawRequest`/`collectInstantWithdrawFunds` — neither fires for the stale key. The corresponding recovery-reserve share stays trapped in the strategy contract (permanent freezing of user funds, and the remaining `instantWithdrawsRequests[user]` balance can also wedge later claims because `_burn` is executed against a receipt whose funded backing was never reserved). Loss equals the full unfunded instant-request amount of any holder whose request crossed the epoch boundary before default.

### Likelihood Explanation
Requires: instant withdrawals enabled by the honest manager, a request made near epoch end that remains partially/un funded into the next epoch, and a borrower default finalized in that later epoch. Instant-withdraw illiquidity at epoch boundaries is an ordinary condition (borrower repayment timing), so the key-mismatch window is realistic, though it needs a default to crystallize — hence High-impact but moderate likelihood.

### Recommendation
Track pending instant receipts across epochs for recovery purposes: e.g., keep a global `totalInstantClaimBasis` (or iterate `instantWithdrawsRequests` aggregates) rather than reading `instantWithdrawClaimsByEpoch[epochNumber]` at finalization, and in `_claimDefaultedInstantWithdrawRequest` clear the user's basis under whichever epoch(s) hold it — or migrate stale-epoch instant basis forward at `stopEpoch`/`startEpoch` when `pendingInstantWithdraws != 0`. Alternatively, make defaulted instant claims key off the user's request epoch stored in a `lastInstantWithdrawRequest[user]` marker, mirroring `lastWithdrawRequest`.

### Proof of Concept
Foundry fork PoC sketch (unverified end-to-end — I was unable to confirm `IdleCDOEpochVariant` instant-withdraw funding internals in the iterations available, specifically whether any stop/start path already reconciles `instantWithdrawClaimsByEpoch` keys):

```solidity
function testStaleEpochInstantReceiptSkippedInRecovery() public {
    _stopCurrentEpoch();                    // buffer epoch N begins
    uint256 amt = 100e6;
    address user = makeAddr('user');
    uint256 tranches = _depositWithUser(user, amt);

    // enable instant withdraws with min-apr-delta so requestInstantWithdraw path is used
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // force low realized apr so instant withdraw triggers, with no liquidity to fund it
    _requestWithdrawWithUser(user, tranches); // instant path: pendingInstantWithdraws>0, keyed at epoch N
    uint256 reqEpoch = strategy.epochNumber();
    assertGt(strategy.instantWithdrawsRequestsByEpoch(user, reqEpoch), 0);

    // roll epoch: stop + start, receipt still unfunded
    _stopCurrentEpochWithApr(1e18);
    vm.prank(manager);
    cdoEpoch.startEpoch();
    assertEq(strategy.epochNumber(), reqEpoch + 1);
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // borrower defaults; finalize recovery in epoch reqEpoch+1
    _handleBorrowerDefaultAndFinalize(); // calls finalizeDefaultRecovery via CDO

    // basis under defaultRecoveryEpoch does not include the user's stale-epoch receipt
    vm.prank(address(cdoEpoch));
    strategy.claimInstantWithdrawRequest(user);
    // BUG: user received 0 from recovery reserve while instantWithdrawsRequestsByEpoch[user][reqEpoch] remains uncleared
    assertGt(strategy.instantWithdrawsRequestsByEpoch(user, reqEpoch), 0);
}
```

Uncertainty note: confirm in `IdleCDOEpochVariant.sol` that `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` are not reconciled at `stopEpoch`/`startEpoch` — if the CDO already migrates or settles all instant receipts at epoch end, this finding collapses to a non-issue.
