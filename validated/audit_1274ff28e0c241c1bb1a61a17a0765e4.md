### Title
GET /v2/external_initiators lacks role restriction and leaks plaintext AccessKey to any view/run-role user - ([File: core/web/router.go])

### Summary
The `GET /v2/external_initiators` route is registered with only `paginatedRequest(eia.Index)`, requiring merely a valid authenticated session/token (any role), while the sibling `POST`/`DELETE` routes require `auth.RequiresEditRole`. The `Index` handler returns `presenters.ExternalInitiatorResource`, which includes the plaintext `AccessKey` for every external initiator in the system.

### Finding Description
In `core/web/router.go`, external initiator routes are registered as: [1](#0-0) 
Note that `GET /external_initiators` is wrapped only in `paginatedRequest`, while `POST`/`DELETE` are wrapped in `auth.RequiresEditRole`. All three routes sit under `authv2`, which only requires successful authentication via token or session (`auth.AuthenticateByToken`/`auth.AuthenticateBySession`), with no role check applied afterward for `Index`.

`ExternalInitiatorsController.Index` fetches all external initiators and maps them via `presenters.NewExternalInitiatorResource`: [2](#0-1) 

The presenter includes the `AccessKey` field in the JSON response: [3](#0-2) 

`AccessKey` is the credential used as the username-equivalent half of `AuthenticateExternalInitiator` (paired with a secret) — it is treated as sensitive material generated alongside a `Secret`/`OutgoingSecret` when the EI is created (see `presenters.NewExternalInitiatorAuthentication`, which returns `AccessKey` and `Secret` together at creation time). Any authenticated user regardless of role (view or run role) can call this endpoint and enumerate every external initiator's `AccessKey`, `Name`, `URL`, and `OutgoingToken` in the system — information intended to only be exposed to users with edit/admin privileges, consistent with the create/delete endpoints requiring `RequiresEditRole`.

This constitutes a role/authorization bypass: the read endpoint should logically carry the same or stricter access control as the write endpoints that manage the same sensitive credential material, but it does not enforce any role check beyond authentication.

### Impact Explanation
An attacker holding only a low-privilege (view or run role) session/token can retrieve `AccessKey` values for all external initiators configured on the node via a single unauthenticated-for-role GET request. While `AccessKey` alone is not the full secret (the `Secret`/`OutgoingSecret` pairing is required for `AuthenticateExternalInitiator`), disclosure of `AccessKey` reduces the external initiator authentication scheme's effective security to the secrecy of the corresponding secret alone, and combined with any other credential leak or brute-force vector materially aids an attacker in impersonating an external initiator's webhook caller. This matches Chainlink's "sensitive information disclosure" / "insufficient authorization" bounty impact class — read access is not properly scoped to the intended privilege tier.

### Likelihood Explanation
Minimal precondition: any authenticated user or API token with `view` or `run` role (the lowest node roles) can trigger this immediately; no admin/edit privileges are required. The request is a single unauthenticated-for-role `GET /v2/external_initiators?size=...&page=...` call, trivially repeatable and scriptable.

### Recommendation
Wrap the `GET /v2/external_initiators` route with `auth.RequiresEditRole` (or at minimum `RequiresRunRole` if intentionally exposed to job-running consumers) to match the authorization level of `POST`/`DELETE` on the same resource, i.e.:
```go
authv2.GET("/external_initiators", auth.RequiresEditRole(paginatedRequest(eia.Index)))
```
Additionally, consider redacting `AccessKey` from `ExternalInitiatorResource` in list/show responses entirely, since it is credential material that should only ever be returned once at creation time (as already done in `ExternalInitiatorAuthentication`).

### Proof of Concept
Go handler-level integration test (extending `core/web/external_initiators_controller_test.go`):
1. Set up an app/test client as in existing `TestExternalInitiatorsController_*` tests, creating an admin session and one external initiator (capturing its `AccessKey`).
2. Create a second test client authenticated with a `sessions.UserRoleView` (or `UserRoleRun`) session/user.
3. Using the view-role client, call `client.Get("/v2/external_initiators")`.
4. Assert (current behavior, demonstrating the bug): response status is `200 OK` and the JSON body's `data[].attributes.accessKey` field is populated and matches the previously created external initiator's `AccessKey`.
5. Expected/fixed behavior assertion: response should be `401 Unauthorized` or `403 Forbidden` for the view-role client, matching the behavior already tested for `POST /v2/external_initiators` and `DELETE /v2/external_initiators/:Name` against non-edit roles.

```go
func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
```

```go
func NewExternalInitiatorResource(ei bridges.ExternalInitiator) ExternalInitiatorResource {
	return ExternalInitiatorResource{
		JAID:          NewJAID(strconv.FormatInt(ei.ID, 10)),
		Name:          ei.Name,
		URL:           ei.URL,
		AccessKey:     ei.AccessKey,
		OutgoingToken: ei.OutgoingToken,
		CreatedAt:     ei.CreatedAt,

	}
}
```
