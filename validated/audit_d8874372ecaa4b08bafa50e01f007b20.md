### Title
Unchecked u64 addition on attacker-derived L1 deposit opaque-data length can panic node derivation - (File: crates/consensus/protocol/src/deposits.rs)

### Summary
`Deposits::decode` parses the ABI-encoded `TransactionDeposited` log emitted by the L1 `OptimismPortal`/deposit contract. This log's `opaqueData` length field is fully attacker-controlled (any account can call `depositTransaction` on L1 with arbitrary calldata that ends up in this log). The code computes `64 + opaque_content_len as usize` using plain (non-checked) `u64`/`usize` addition in two places, even though the adjacent `padding_end` computation in the same function explicitly uses `checked_add` to guard against exactly this overflow. This is analogous to CVE-2020-0430's root cause: an unchecked length/offset computation derived from external/untrusted data leading to unsafe memory access, here manifesting as an unguarded arithmetic overflow on attacker-supplied length data during consensus-critical derivation.

### Finding Description
In `Deposits::decode`: [1](#0-0) 
`opaque_content_len` is parsed as a `u64` from 32 bytes of the L1 log (`log.data.data[32..64]`), bounded only by fitting into a `u64` (i.e., up to `u64::MAX`), via `.try_into()`.

It is then used in two raw additions: [2](#0-1) 
- `64_u64.checked_add(opaque_data_ceil_32)` is explicitly checked (line 107), showing the authors were aware overflow is possible for values derived from `opaque_content_len`.
- However, `64 + opaque_content_len as usize` (line 113, inside `.get(64..64 + opaque_content_len as usize)`) is **not** checked.
- Similarly, `(64 + opaque_content_len) as usize` is used again at: [3](#0-2) 

`log.data.data` originates from an L1 event log that is parsed during L1→L2 derivation of deposit transactions — a path reachable by any L1 account calling the deposit contract with attacker-chosen calldata (`depositTransaction`), i.e., exactly the class of "derivation of attacker-written L1 deposit ... data" the scope explicitly calls out as in-scope.

If `opaque_content_len` is close to `u64::MAX` (e.g., `u64::MAX - 10`), `64 + opaque_content_len` overflows the `u64`/`usize` addition. In a build compiled with overflow checks enabled (debug builds, and any release build that opts into `overflow-checks = true`, which is common for consensus-critical software), this triggers an unconditional Rust panic ("attempt to add with overflow") rather than returning the intended `DepositDecodeError`. Because this code executes as part of mandatory L1 derivation (every node must process every L1 deposit log to build the L2 chain), a single malicious L1 deposit transaction can crash every node performing derivation — a chain-wide DoS/halt.

Even absent a panic (e.g. release build with default wrapping arithmetic), the two-'s-complement wraparound silently produces a nonsensical `64 + opaque_content_len` (a small value smaller than the real length that overflowed), which is then fed into `.get(64..wrapped_value)`. Because `.get()` returns `None` for an invalid range instead of panicking, in practice this specific `.get()` usage does not itself cause OOB memory access — but it does change control flow away from the length actually intended, and is a symptom of the same missing-bounds-validation root cause as the CVE (arithmetic on a length field taken directly from untrusted/attacker data without validating it against safe bounds before use).

### Impact Explanation
If overflow checks are compiled in (a routine safety hardening choice for blockchain nodes, and already partially reflected in this same function via `checked_add`), any L1 account can submit a deposit transaction whose opaque data declares a length near `u64::MAX`. When this log is derived by an L2 node (mandatory step for chain progress), the node panics, resulting in node crash/halt — a chain-wide denial of service reachable purely from an L1 deposit, satisfying the "node halt" impact criterion.

### Likelihood Explanation
High reachability: submitting a deposit with a crafted 32-byte length field costs only L1 gas and requires no special privileges — any anonymous L1 account can trigger it via the standard deposit path. The only uncertainty is whether the specific compiled binaries used in production enable `overflow-checks`; this could not be conclusively verified from the repository (no explicit `[profile.release] overflow-checks = true` was found in the top-level `Cargo.toml`, though nested crate Cargo.tomls were not all individually inspected). If overflow checks are disabled, the direct panic does not occur, but the underlying missing-bounds-check on `opaque_content_len` before arithmetic remains an unaddressed root-cause defect relative to the `checked_add` used two lines below for the same class of value.

### Recommendation
Replace the raw `64 + opaque_content_len as usize` additions at both call sites with `checked_add`/`saturating_add`, consistent with the existing `padding_end` computation, and return `DepositDecodeError::OpaqueDataOverflow` (already defined but apparently unused) on overflow rather than allowing unchecked arithmetic on an attacker-controlled `u64`.

### Proof of Concept
1. Craft an L1 `TransactionDeposited` log with topics matching `EVENT_ABI_HASH`/valid `from`/`to`, and log `data`:
   - bytes `[0..32]` = `32` (opaque data offset, must pass the `InvalidOpaqueDataOffset` check),
   - bytes `[32..64]` = `u64::MAX - 10` encoded as a 32-byte big-endian value (passes `try_into::<u64>()` since it fits in 64 bits).
2. Call `Deposits::decode(block_hash, index, &log)`.
3. Execution reaches: `let opaque_data = &log.data.data.get(64..64 + opaque_content_len as usize)` where `64 + (u64::MAX - 10)` overflows `u64`/`usize` addition.
4. In an overflow-checked build this panics with "attempt to add with overflow" instead of returning a decode error, crashing the derivation pipeline for any node processing this L1 deposit.
