### Title
`Session.Kill` does not prevent a concurrent `/exec` request from creating a new terminal connection - (File: session/session.go)

### Summary
`Session.Kill` only closes and nils `s.terminalConn`; it does not clear `s.interactiveTerminal` or set any "killed"/terminal state flag. A concurrent `execHandler` call that is blocked waiting on `s.terminalSetCh`/`ctx.Done()` (session.go:164-167) or that simply races the mutex can still call `newTerminalConn()` after `Kill()` has run, and because `s.terminalConn` was set back to `nil` by `Kill`, `newTerminalConn` will happily invoke `s.interactiveTerminal.TerminalConnect()` again, spawning a brand-new shell/exec process on the executor.

### Finding Description
`Session.Kill` (session.go:263-275) does:
```go
func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()
	if s.terminalConn == nil {
		return nil
	}
	err := s.terminalConn.Close()
	s.terminalConn = nil
	return err
}
``` [1](#0-0) 

It closes the *current* connection and resets the field, but leaves `s.interactiveTerminal` set and provides no "session is being torn down" flag. `newTerminalConn` (session.go:200-216) only guards against a connection already being in use:
```go
func (s *Session) newTerminalConn() (terminal.Conn, error) {
	s.lock.Lock()
	defer s.lock.Unlock()
	if s.terminalConn != nil {
		return nil, connectionInUseError{}
	}
	conn, err := s.interactiveTerminal.TerminalConnect()
	...
	s.terminalConn = conn
	return conn, nil
}
``` [2](#0-1) 

Because `Kill()` sets `s.terminalConn` back to `nil`, any `execHandler` goroutine that reaches `newTerminalConn()` after (or concurrently with) `Kill()` sees an available slot and proceeds to call `TerminalConnect()` on the underlying executor - e.g. `commandExecutor.TerminalConnect()` in `executors/docker/terminal.go:49-88`, which performs `ContainerExecCreate`/`ContainerExecAttach` on the build container, or the shell executor's `TerminalConnect()` in `executors/shell/shell_terminal.go:38-56`, which calls `pty.Start(cmd)` to spawn a new OS process. Both of these use the executor's own `s.Context`, which is expected to already be canceled/being torn down by the time `Kill()` runs (job cancellation/timeout path in `common/build.go` calls `Session.Kill()` as part of teardown). `execHandler` (session.go:146-191) has an inherent race window: it waits on `s.terminalSetCh`/`ctx.Done()` at lines 164-167, and its subsequent `s.terminalAvailable()` check (line 169) and `s.newTerminalConn()` call (line 175) are separate lock acquisitions from `Kill()`'s, so nothing prevents `Kill()` and a subsequent `execHandler` invocation from interleaving in the order: `Kill()` closes old conn → sets `terminalConn=nil` → releases lock → `execHandler` acquires lock in `newTerminalConn` → creates a **new** exec/shell process on an executor that is otherwise being destroyed by the job cancellation path.

There is no check that stops this: `terminalAvailable()` only checks `interactiveTerminal != nil`, which `Kill()` never clears; there's no "killed" boolean, and the executor-side `TerminalConnect()` implementations don't validate that the executor's context/container is still alive before attaching (docker's version does check container running state via `watchForRunningBuildContainer`, but that only checks the container is running, which it may still be for a brief window during teardown, and the shell version does no such check at all - it will freely `pty.Start` a new process).

### Impact Explanation
A user-triggered `/exec` (interactive web terminal) request that races job cancellation/timeout can cause the runner to spawn a new shell process (shell executor) or a new `exec` session inside the build container (docker executor) after the job's session was supposed to be killed. This is a dangling command execution outside of the job's intended lifecycle: the process/exec session is not tracked by the job's cancellation logic and can outlive the job, potentially continuing to run commands (with the job's original permissions/container) after the job has been marked as finished/canceled/timed out. This is a genuine isolation/lifecycle boundary violation, though the created process is still confined to the same container/host resources the job already had access to (no privilege escalation to another job/project).

### Likelihood Explanation
This requires only an unprivileged pipeline author who has access to the job's session endpoint (browser terminal feature) sending `/exec` WebSocket upgrade requests concurrently with job cancellation or timeout - both are fully attacker-controlled/triggerable (a user can cancel their own job, or let it hit `timeout`, while simultaneously flooding `/exec`). The race window is small but `execHandler`'s up-to-1-minute wait on `s.terminalSetCh`/`ctx.Done()` (session.go:156-167) and the fact that `Kill()`/`newTerminalConn()` are two independently-locked critical sections make the race realistically reproducible with a tight loop of concurrent requests around the cancellation point.

### Recommendation
Add an explicit terminated/killed state to `Session` (e.g., a `killed bool` or an `interactiveTerminal = nil` reset) inside `Kill()`, guarded by the same lock, so that `newTerminalConn()`/`terminalAvailable()` refuse to create any further connections once `Kill()` has executed:
```go
func (s *Session) Kill() error {
	s.lock.Lock()
	defer s.lock.Unlock()
	s.killed = true
	s.interactiveTerminal = nil
	if s.terminalConn == nil {
		return nil
	}
	err := s.terminalConn.Close()
	s.terminalConn = nil
	return err
}
```
and check `s.killed` in `terminalAvailable()`/`newTerminalConn()`, returning an error/404 instead of proceeding.

### Proof of Concept
Go race/integration test in `session/session_test.go`:
1. Create a `Session` with a mocked `terminal.InteractiveTerminal` whose `TerminalConnect()` increments a counter and returns a mock `Conn`.
2. Call `SetInteractiveTerminal(mockTerminal)`.
3. Start N goroutines calling `execHandler`/`newTerminalConn()` in a tight loop.
4. Concurrently call `s.Kill()`.
5. After `Kill()` returns, assert that `s.newTerminalConn()` (or the exec handler) never succeeds again - i.e., `mockTerminal.TerminalConnect` call count does not increase after `Kill()` has completed, and `terminalAvailable()`/subsequent `execHandler` requests return an error rather than establishing a new connection.

Expected failing assertion today: `TerminalConnect()` count increases (a new terminal conn is created) even after `Kill()` has already run, proving processes can be spawned mid-teardown.
