### Title
`cleanPath`/`resolvePath` in PowerShell writer let attacker-controlled variable keys inject a live `$(...)` subexpression into generated PowerShell - ([File: shells/powershell.go])

### Summary
`PsWriter.cleanPath` (and `TmpFile`, which calls it) return a raw, unescaped path string, and the only quoting applied afterward at the call sites that consume it (`p.resolvePath`, used for the file-variable temp path) is `psDoubleQuote`, which does **not** escape `$`. Because PowerShell double-quoted strings interpolate both `$var` and `$(...)` subexpressions, a variable Key containing `$( ... )` characters that ends up embedded in a `cleanPath`-derived temp file path is executed as live PowerShell code when the generated script runs, rather than being treated as literal text.

### Finding Description
`cleanPath` itself does no escaping at all: [1](#0-0) 
It simply forwards through `Absolute`/`fromSlash`, which also do not escape or quote: [2](#0-1) 

`TmpFile` builds a temp-file path from `p.TemporaryPath` joined with a caller-supplied `name` and passes it straight through `cleanPath`, without any escaping: [3](#0-2) 

The only place this raw path gets embedded into the generated PowerShell text for File-type variables is via `resolvePath`, which wraps the string with `psDoubleQuote`: [4](#0-3) [5](#0-4) 

`psDoubleQuote` escapes backticks, quote characters, and control characters, but crucially does **not** escape `$`: [6](#0-5) 
Contrast this with `psQuoteVariable`, which is used elsewhere and explicitly escapes `$` after double-quoting so that literal dollar signs stay literal: [7](#0-6) 

Because PowerShell's double-quoted strings support both `$name` variable interpolation and `$(...)` subexpression evaluation, any attacker-controlled text that flows into a `psDoubleQuote`-wrapped, `cleanPath`-derived path — most directly `variable.Key` for a `File: true` variable — retains its `$(...)` syntax unescaped in the final script text: [5](#0-4) 
When the runner-generated script is executed by `pwsh`/`powershell`, that subexpression is evaluated as live PowerShell code at that point in the script, i.e. attacker-supplied "data" (a variable name) turns into "shell syntax" that executes.

I was unable to fully verify within this session whether `variable.Key` for File-type variables (e.g. `id_tokens`, secure files, or other dynamically named File variables sent from GitLab to Runner) is validated upstream to disallow `$`, parentheses, or other PowerShell-significant characters before reaching this code path. On the bash side there is an analogous `isValidDotEnvKey` regex gate for dotenv-report variable keys (`^[A-Za-z_][A-Za-z0-9_]*$`) that would block this class of attack for that specific channel, but that check is dotenv-specific and does not appear to run for all `File: true` variable sources that reach `PsWriter.Variable`. Confirming exactly which upstream code paths populate `spec.Variable{Key: ..., File: true}` and whether any of them permit non-identifier key characters would require deeper tracing than was possible here (this is a note of uncertainty, not a claim of confirmed exploitability).

### Impact Explanation
If an attacker can control the `Key` of a `File: true` variable with characters outside `[A-Za-z0-9_]` (in particular `$(`...`)`), the generated PowerShell script executes attacker-chosen PowerShell code inside the runner's job-execution shell context at script-generation/execution time — i.e., arbitrary command execution in the "stronger runner context" that runs the generated stage script (shell/custom/kubernetes executor host or container), matching the "stronger-context command execution" impact class this question targets.

### Likelihood Explanation
Exploitability hinges entirely on whether any reachable, unprivileged-user-controlled path can set an arbitrary `File: true` variable `Key` containing PowerShell-significant characters (especially `$(`). If GitLab's backend/API already restricts variable/token names to identifier-safe characters for every channel that produces File-type variables, this is not practically triggerable even though the Runner-side quoting is technically inconsistent (`psDoubleQuote` vs `psQuoteVariable`). This should be treated as a defense-in-depth gap in Runner rather than a confirmed end-to-end exploit until the exact upstream key-validation for all File-variable sources is confirmed.

### Recommendation
Make `resolvePath`/`psDoubleQuote` escape `$` the same way `psQuoteVariable` does (or route all `cleanPath`/`TmpFile`-derived strings that get embedded into PowerShell double-quoted contexts through `psQuoteVariable`-equivalent escaping), so that no code path can produce a `$`-bearing string inside an unescaped double-quoted PowerShell literal. Independently, validate `variable.Key` for `File: true` variables against a strict identifier pattern (mirroring `isValidDotEnvKey`) before it is used to build any temp-file path, regardless of its origin.

### Proof of Concept
Go unit test target: `shells/powershell_test.go`, exercising `PsWriter.Variable`.
```go
func TestPsWriter_Variable_FileKeyDollarSubexpressionNotEscaped(t *testing.T) {
    w := &PsWriter{Shell: SNPwsh, EOL: "\n", TemporaryPath: `C:\tmp\build`}
    w.Variable(spec.Variable{
        Key:   `SAFE$(calc)NAME`, // simulate an unvalidated File-variable key
        Value: "token-value",
        File:  true,
    })
    out := w.String()
    // Assertion: the raw, unescaped "$(calc)" subexpression syntax must not
    // appear inside the generated double-quoted path literal; it must be
    // escaped (e.g. "`$(calc)") so PowerShell treats it as literal text.
    assert.NotContains(t, out, `$(calc)`)
}
```
Expected today: the test fails because `psDoubleQuote` leaves `$(calc)` intact inside the `[System.IO.File]::WriteAllText(...)` path argument, demonstrating that the produced PowerShell would evaluate `$(calc)` as a live subexpression rather than literal path text.

func psDoubleQuote(text string) string {
	text = psReplaceSpecialChars(text)
	text = strings.ReplaceAll(text, "“", "`“")
	text = strings.ReplaceAll(text, "”", "`”")
	text = strings.ReplaceAll(text, "„", "`„")
	return doubleQuote(text)
}

	text = psDoubleQuote(text)

	text = strings.ReplaceAll(text, "``e", "`e")
	return text
}

func (p *PsWriter) Variable(variable spec.Variable) {
	if variable.File {
		variableFile := p.TmpFile(variable.Key)
		p.MkDir(p.TemporaryPath)
		p.Linef(
			"[System.IO.File]::WriteAllText(%s, %s)",
			p.resolvePath(variableFile),
			psQuoteVariable(variable.Value),
		)
		p.Linef("${%s}=%s", variable.Key, p.resolvePath(variableFile))
	} else {
		if p.isTmpFile(variable.Value) {
			variable.Value = p.cleanPath(variable.Value)
		}

		p.Linef("${%s}=%s", variable.Key, psQuoteVariable(variable.Value))
	}

	p.Linef("${env:%s}=${%s}", variable.Key, variable.Key)
}
