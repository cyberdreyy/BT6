Based on my investigation, this is a genuine, well-formed analog of the reported bug class.

### Title
Stale ACCEPT signature is never cleaned up when a signer later REJECTs the same block, letting an outdated positive vote keep contributing weight toward the acceptance threshold - (File: stacks-signer/src/signerdb.rs)

### Summary
The C4 report's root cause is that `register_domain` writes a new "current" state (a fresh expiry) without deleting the stale reverse mapping created by the previous owner, so a later query mixes fresh authority (re-registration) with stale data (old address). The stacks-signer analog is `add_block_rejection_signer_addr` / `add_block_signature` in [1](#0-0) , which store a signer's vote for a block in two independent tables, `block_signatures` and `block_rejection_signer_addrs`, with cleanup enforced in only one direction.

### Finding Description
`add_block_signature` deletes any prior rejection row for the same `(signer_signature_hash, signer_addr)` before inserting the acceptance: [2](#0-1) 

But the reverse direction, `add_block_rejection_signer_addr`, only *checks* whether a signature already exists (to refuse turning an ACCEPT into a REJECT) — it never deletes a stale ACCEPT row when inserting a REJECT: [3](#0-2) 

This asymmetry is only half a fix. If the guard at line 1930-1940 is bypassed or if the two rows are written by different code paths/timings (e.g., an older/duplicate acceptance message from a peer arrives and is written to `block_signatures` after this signer's rejection has already been recorded, or a peer that first accepted later has its rejection message dropped/lost while a stale acceptance from an earlier retry is replayed), the acceptance mapping in `block_signatures` is never purged. Every later weight tally for acceptance reads directly from `block_signatures` via `get_block_signatures`: [4](#0-3) 

and this is fed straight into the threshold computation in `store_and_process_block_signature`: [5](#0-4) 

There is no equivalent "if a rejection now exists for this signer, drop their old acceptance row" step on the accept-tallying path. The two tables (`block_signatures`, `block_rejection_signer_addrs`) are two independent "mappings" keyed by `(block hash, signer address)`, exactly like `name_to_addr`/`addr_to_name` in the C4 report, and only one direction of transition (reject→accept) is guaranteed to clean up the other side.

### Impact Explanation
If a stale acceptance row survives in `block_signatures` for a signer who has since rejected the block, `compute_signature_signing_weight(addrs_to_sigs.keys())` in [6](#0-5)  will keep counting that signer's weight toward the 70% acceptance threshold even though that signer's current, valid opinion is REJECT. This can push a block's aggregated ACCEPT weight past the threshold using a vote that is no longer live, i.e. an aggregated-weight vs. verified-current-accepts equality violation — the same class of bug as the report's "expired ownership still returns old values" (Impact category: rejection/stale state recounted as an accept toward a safety-relevant threshold).

### Likelihood Explanation
The guard in `add_block_rejection_signer_addr` (checking `block_signatures` before allowing a rejection insert) does prevent the straightforward case of accept-then-reject-in-order from a single signer. The risk is in message reordering/duplication over StackerDB gossip: a delayed or replayed old acceptance chunk landing in `block_signatures` *after* a rejection has already been recorded for that signer is not blocked by any symmetric check on the accept-insert path (`add_block_signature` only clears rejections, it does not check for or refuse an insert when a rejection already exists). This requires only network-level message reordering/replay from a single non-majority signer plus normal gossip, not control of other signers' keys — consistent with a one-slot-miner/gossip-triggerable analog.

### Recommendation
Make the cleanup symmetric: when inserting/updating a rejection in `block_rejection_signer_addrs`, also delete any existing row for that `(block_sighash, signer_addr)` in `block_signatures` (mirroring what `add_block_signature` already does for rejections), so at all times at most one of the two tables holds a live vote per signer per block, and both tally paths (`store_and_process_block_signature`, `store_and_process_block_rejection`) read a consistent, non-stale state.

### Proof of Concept
1. Signer A validates and accepts block B; its acceptance is written into `block_signatures` (via `add_block_signature`) and gossiped over StackerDB.
2. Before threshold is reached, Signer A's chainstate re-check (as described in `check_block_against_signer_db_state`, referenced in `docs/signer-flows.md`) flips to reject B, and a rejection row is inserted into `block_rejection_signer_addrs` via `add_block_rejection_signer_addr` (no pre-existing signature row present at that instant, so the guard at line 1930 passes).
3. A delayed/duplicate copy of Signer A's original acceptance message (from network retry/replay) is now processed by another signer and calls `add_block_signature`, re-inserting (`INSERT OR IGNORE`) Signer A's row into `block_signatures`.
4. `get_block_signatures` now returns Signer A's stale acceptance alongside `block_rejection_signer_addrs` also containing Signer A's current rejection; `compute_signature_signing_weight` in the acceptance path counts Signer A's weight toward the 70% threshold even though the authoritative decision for Signer A is REJECT — mirroring the report's stale `name_to_addr`/`addr_to_name` entries being read as current after the "domain" (vote) has effectively changed hands.

Note: I could not fully trace every ordering/timing guarantee that StackerDB message delivery provides (e.g., whether chunk versioning strictly prevents an older acceptance chunk from being reprocessed after a newer rejection chunk for the same slot); this reordering path is the main assumption behind the exploit and should be independently verified against `stacks-signer/src/client` chunk-versioning logic before treating this as fully confirmed.

    pub fn add_block_signature(
        &self,
        block_sighash: &Sha512Trunc256Sum,
        signer_addr: &StacksAddress,
        signature: &MessageSignature,
    ) -> Result<bool, DBError> {
        // Remove any block rejection entry for this signer and block hash
        let del_qry = "DELETE FROM block_rejection_signer_addrs WHERE signer_signature_hash = ?1 AND signer_addr = ?2";
        let del_args = params![block_sighash, signer_addr.to_string()];
        self.db.execute(del_qry, del_args)?;

        // Insert the block signature
        let qry = "INSERT OR IGNORE INTO block_signatures (signer_signature_hash, signer_addr, signature) VALUES (?1, ?2, ?3);";
        let args = params![
            block_sighash,
            signer_addr.to_string(),
            serde_json::to_string(signature).map_err(DBError::SerializationError)?
        ];
        let rows_added = self.db.execute(qry, args)?;

        let is_new_signature = rows_added > 0;
        if is_new_signature {
            debug!("Added block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        } else {
            debug!("Duplicate block signature.";
                "signer_signature_hash" => %block_sighash,
                "signer_address" => %signer_addr,
                "signature" => %signature
            );
        }
        Ok(is_new_signature)
    }
