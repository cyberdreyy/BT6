### Title
Service-alias generation in `SplitNameAndVersion` can leak masked variable values into trace logs, bypassing exact-substring masking - (`helpers/container/services/services.go`)

### Summary
`SplitNameAndVersion` derives Docker network aliases from the service name by replacing `/` with `__` or `-`. If a pipeline author sets `Build.Services[i].Name` to a masked/protected CI variable reference (e.g. `services: [{name: $MASKED_VAR}]`) whose expanded value contains `/`, the resulting alias is a transformed string that no longer matches the literal secret value the log masker searches for. When this alias is subsequently written to the job trace (e.g. via the alias-collision warning in `executors/docker/services.go`), it evades masking and discloses the (lightly transformed but still highly recoverable) secret content in the job log.

### Finding Description
`SplitNameAndVersion` computes `service.Service` from the parsed image reference and then builds aliases via [1](#0-0) . These transformations only touch `/` characters; everything else in the masked value (which may include long secret substrings without `/`) passes through unmodified into `service.Aliases`.

These aliases flow into `createFromServiceDefinition` in `executors/docker/services.go`, where the raw derived alias (`linkName`) is written directly to the build trace on an alias collision: [2](#0-1) . A pipeline author fully controls all `services` entries, so they can trivially force this branch — e.g. define two services both referencing the same masked variable (or one service using the variable and another with an explicit `alias` equal to the transformed value) — guaranteeing `linksMap[linkName] != nil` and triggering the `Warningln`.

GitLab Runner's log masking operates by searching the trace byte stream for exact occurrences of known secret values (masked variables) and replacing them (see `common/buildlogger/internal/masker`). Because the alias string differs from the original secret by having its `/` characters replaced with `__` or `-`, it no longer matches the literal string the masker looks for. Any contiguous run of the secret between slashes remains untouched in the alias and is emitted to the trace unmasked. The author does not need to know the secret value in advance — they only need to reference the CI variable by name in the service definition; the runner performs variable expansion and the vulnerable code path handles the raw expanded value without re-checking it against the masker before logging.

Existing protections that fail to catch this:
- `verifyAllowedImage`/`AllowedServices` in `executors/docker/services.go` only restrict which image names may be used; they do not inspect or sanitize the value for masking purposes: [3](#0-2) .
- The trace masker only rewrites known literal secret substrings in the output stream — it does not track derived/transformed copies of secret values produced elsewhere in the runner.

### Impact Explanation
An unprivileged-but-authorized job author (someone able to trigger a pipeline that receives a masked/protected CI variable, e.g. via a merge request or protected-branch job) can cause the runner to write a transformed-but-substantially-reconstructable form of that secret into the job trace log, which may be visible to other project members who have log-view access but not variable-view access. This breaks the core invariant that masked/protected variable values must not leak into job traces.

### Likelihood Explanation
- Requires the job to actually receive the masked variable (so the attacker needs standard permission to run a job where the variable is injected — no admin or cluster compromise needed).
- Requires the variable's value to contain at least one `/` character (common for tokens/URLs/paths, e.g. deploy tokens, registry credentials).
- Forcing the warning branch is trivial and fully within pipeline-author control (just define a colliding alias/service).
- No exploitation of Docker/Kubernetes internals is needed — purely a `.gitlab-ci.yml` change.

### Recommendation
- Do not log raw, potentially secret-derived alias strings; log only sanitized identifiers (e.g., service index) in the collision warning.
- Ensure any string derived from CI variables that is emitted to the trace passes through the same masking pipeline used for regular job output before being written, or alternatively, refuse to build aliases directly from values that match currently-registered masked variables.
- Add masking-awareness to alias construction so that `strings.ReplaceAll` transformations don't let partial-secret substrings survive into log output unmasked.

### Proof of Concept
Go unit test outline for `executors/docker` package:
```go
func TestServiceAliasCollisionLeaksMaskedValue(t *testing.T) {
    secret := "sec/ret-token-1234567890"
    // simulate a masked variable whose value contains '/'
    build := newTestBuildWithMaskedVariable("MASKED_VAR", secret)
    build.Services = common.Services{
        {Name: "$MASKED_VAR"},
        {Name: "$MASKED_VAR"}, // second reference forces alias collision
    }

    trace := &common.Trace{} // wraps BuildLogger with masking enabled for `secret`
    executor := newTestDockerExecutor(build, trace)

    err := executor.createServices()
    require.NoError(t, err)

    // Assert the literal secret never appears (masking works normally)
    assert.NotContains(t, trace.Buffer(), secret)

    // But assert the transformed alias (with '/' replaced) DOES appear,
    // proving the underlying secret content leaked in altered form.
    transformedAlias := strings.ReplaceAll(secret, "/", "__")
    assert.Contains(t, trace.Buffer(), transformedAlias, "masked value leaked via alias transformation")
}
```
Expected result on the current code: the assertion on `transformedAlias` passes, demonstrating that the masking is bypassed because the alias transformation changes the string away from the exact masked value the masker searches for.
