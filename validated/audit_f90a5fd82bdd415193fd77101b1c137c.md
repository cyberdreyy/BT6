### Title
`simulateTransaction` "accounts" config returns full raw account bytes with no size cap distinct from on-chain account size, causing per-request cost to scale with attacker-controlled account size - ([File: rpc/src/rpc.rs])

### Summary
The `simulate_transaction` RPC handler's optional `accounts` config lets a caller request up to `number_of_accounts` (the number of account keys referenced by the submitted transaction) post-simulation accounts to be fetched and base64/base58/jsonParsed-encoded into the response, with no `dataSlice` option and no independent response-size ceiling. Since Solana account data can be up to ~10MB, a single `simulateTransaction` call referencing several large attacker-written accounts forces the validator to clone and encode tens of megabytes of account data synchronously in one request.

### Finding Description
In `simulate_transaction` (`rpc/src/rpc.rs`), when `config.accounts` is supplied, the code:
1. Bounds `config_accounts.addresses.len()` only by `number_of_accounts`, i.e. the number of account keys in the transaction being simulated [1](#0-0) .
2. For each requested address, calls `get_encoded_account(bank, &pubkey, accounts_encoding, None, Some(&post_simulation_accounts_map))`, which fetches the account and encodes its full data buffer (base64/jsonParsed; base58 is explicitly rejected only for being "not supported", not for size) [2](#0-1) .

Unlike other RPC config types (e.g. `getAccountInfo`) that expose a `dataSlice` for partial reads, `RpcSimulateTransactionAccountsConfig` only exposes `encoding` and `addresses` — there is no `dataSlice` field to bound the returned bytes per account [3](#0-2) .

The only structural limit on the number of returned accounts is the transaction's own account-key count, which is itself bounded by wire-transaction size limits enforced during `decode_and_deserialize` (packet-size-based), not by any RPC-specific "max accounts to return" or "max response bytes" setting. Since Solana permits individual accounts up to the maximum permitted account data length (~10MB, enforced in `accounts-db/src/append_vec.rs`), an attacker who first writes one or more large accounts (via ordinary system/program instructions, no privileged access needed) can then submit a single `simulateTransaction` call whose `accounts.addresses` list references those large accounts. The handler will fetch and base64-encode their full raw bytes into the JSON-RPC response body, with cost (memory allocation, base64 encoding CPU, JSON serialization) scaling directly with the sum of the referenced accounts' sizes — bounded only by "number of accounts a transaction can reference" × "max account size", not by any explicit response-size guard.

### Impact Explanation
A single, low-rate, unprivileged `simulateTransaction` call can force the validator's JSON-RPC handling thread to allocate, copy, and base64-encode potentially tens of megabytes of account data in one synchronous request, because there is no explicit per-request response-size cap independent of attacker-controlled on-chain account size. This matches the "unbounded cost for a single low-rate call" category — a memory/CPU cost amplification scoped to a single request, without any additional guard (no `dataSlice`, no explicit byte ceiling) beyond the intrinsic account-size limit itself.

### Likelihood Explanation
Fully attacker-controlled and requires no privileges: the attacker only needs to (1) write a large account on-chain using normal, permissionless transactions (allocating account space up to the protocol maximum), and (2) issue one `simulateTransaction` JSON-RPC call with an `accounts.addresses` list referencing that account, well within the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` constraint. This is straightforward and repeatable against any public RPC node that exposes `simulateTransaction`.

### Recommendation
Add a `dataSlice` option to `RpcSimulateTransactionAccountsConfig` (mirroring `getAccountInfo`/`getMultipleAccounts`), and/or enforce an explicit maximum total response byte budget across all requested `accounts` in `simulate_transaction`, independent of the transaction's account-key count and the account's actual on-chain size.

### Proof of Concept
Integration test plan (Rust, in `rpc/src/rpc.rs` test module using `RpcHandler`):
1. Store an account (e.g. via `bank.store_account`) with data size close to the maximum permitted account data length (~10MB) at a known pubkey.
2. Build/sanitize a transaction whose message references that pubkey among its account keys (e.g. as a readonly account) so `number_of_accounts` in `simulate_transaction` is satisfied.
3. Issue a `simulateTransaction` JSON-RPC request with `accounts: { encoding: "base64", addresses: [<large_account_pubkey>, ...] }`.
4. Assert: the handler completes and the JSON response's `accounts[i].data` field contains a base64 string whose decoded length equals the stored account's full data size (no truncation or slicing applied).
5. Measure wall-clock time / peak memory of the `simulate_transaction` call for increasing account sizes (e.g. 1MB, 5MB, 10MB) and assert the cost scales roughly linearly with account size, with no configured ceiling encountered before hitting the account's own size limit.
