### Title
Silent field-mislabeling in `ConfidentialBurn` parsing when account count doesn't match proof-offset flags - ([File: transaction-status/src/parse_token/extension/permissioned_burn.rs])

### Summary
`parse_permissioned_burn_instruction`'s `PermissionedBurnInstruction::ConfidentialBurn` branch walks optional proof-related accounts using a running `offset` bounded only by `account_indexes.len().saturating_sub(2)` / `saturating_sub(1)`, without ever validating that `account_indexes.len()` actually equals the number of accounts implied by the three `*_proof_instruction_offset` flags. An attacker who forges a transaction with a self-inconsistent combination (proof-offset flags claiming more optional accounts than are actually present) causes the parser to silently skip one or more of the `instructionsSysvar`/`*ProofContextStateAccount` fields and instead advance to labeling whatever account is at the current `offset` as `permissionedBurnAuthority`, then hand the next index to `parse_signers` as `authority`/`multisigAuthority`.

### Finding Description
The relevant code is: [1](#0-0) [2](#0-1) 

`offset` starts at 2 (after `account`/`mint`), and is optionally incremented for `instructionsSysvar`, `equalityProofContextStateAccount`, `ciphertextValidityProofContextStateAccount`, and `rangeProofContextStateAccount`, each gated by both a data-derived boolean (`has_sysvar`, `*_proof_instruction_offset == 0`) and a length guard `offset < account_indexes.len().saturating_sub(2)`. Finally `permissionedBurnAuthority` is populated if `offset < account_indexes.len().saturating_sub(1)`, and the remainder is handed to `parse_signers` for `authority`/`multisigAuthority`.

The true number of "optional" accounts that should exist between `mint` and `authority` is determined entirely by the proof-offset flags (1 for the sysvar if any offset is instruction-based, plus 1 for each proof whose offset is `0`, meaning a context-state account is used instead). Nothing in this function checks that `account_indexes.len()` equals `4 + (expected optional count)`. `check_num_token_accounts(account_indexes, 4)` only enforces a minimum of 4 accounts, regardless of what the offset flags declare.

Because the length guard is only `offset < len.saturating_sub(2/1)`, when an attacker supplies fewer accounts than the flags imply (e.g. `account_indexes.len() == 5` while flags declare both a sysvar requirement — `ciphertext_validity_proof_instruction_offset != 0` — and an equality context account — `equality_proof_instruction_offset == 0` — which together need 2 optional slots, but only 1 slot fits before the guard trips), the code:
1. Consumes the single available optional slot for `instructionsSysvar` (first branch in program order), using `account_indexes[2]`.
2. Skips the `equalityProofContextStateAccount` branch entirely because `offset < len.saturating_sub(2)` is now false, even though `equality_proof_instruction_offset == 0` says an equality context account should be present.
3. Falls through to the `permissionedBurnAuthority` assignment using `account_indexes[3]` — an index the attacker intended (per the declared flags) to be a proof context account — and `parse_signers` then labels `account_indexes[4]` as `authority`.

All array accesses stay in-bounds (no panic), but the resulting JSON silently mismaps which pubkey is `instructionsSysvar` vs. which should have been `equalityProofContextStateAccount`, and shifts `permissionedBurnAuthority`/`authority` onto accounts one or more positions earlier than the attacker's declared proof layout implies. `check_num_token_accounts(4)` and the `saturating_sub` guards prevent panics but do not detect or reject this self-inconsistent input — no code path returns `InstructionNotParsable` when the declared flags and account count disagree.

This is reachable by an unprivileged attacker: parsing in `transaction-status` runs against raw instruction bytes and the account list of any transaction that lands in a block (`getTransaction` with `jsonParsed` encoding), independent of whether program execution succeeds. An attacker only needs a single self-submitted transaction (which may even fail at runtime in the real `spl_token_2022_interface` program, since the account list is inconsistent) to have this instruction included in a block and later fetched.

### Impact Explanation
This falls in the "decoder panic and misreporting" accepted category, specifically wrong-data-returned-by-RPC: `getTransaction`/`jsonParsed` clients (wallets, explorers, indexers) may display an account never intended as a signer/authority as `permissionedBurnAuthority` or `authority`, or omit a genuine proof-context account, misleading downstream consumers about who authorized/could authorize the burn. It does not affect consensus or cause a crash — the bug is confined to `transaction-status` RPC JSON formatting logic.

### Likelihood Explanation
Fully attacker-controlled: the attacker only needs to construct raw `ConfidentialBurn` instruction bytes (setting `equality_proof_instruction_offset`, `ciphertext_validity_proof_instruction_offset`, `range_proof_instruction_offset` to any desired zero/nonzero combination) and choose `account_indexes.len()` to be inconsistent with those flags (e.g. exactly `4` or `5`, below what the combination of flags would require), pass the minimal `check_num_token_accounts(4)` gate, and submit the transaction once. It reproduces deterministically for every applicable combination, so it is fully repeatable with a single low-rate RPC call.

### Recommendation
Before walking optional accounts, compute the exact expected optional-account count from the three offset flags (`has_sysvar as usize + (eq==0) as usize + (val==0) as usize + (range==0) as usize`) and require `account_indexes.len() == 4 + expected_optional_count` (or at least `>=`), returning `ParseInstructionError::InstructionNotParsable` if not. Alternatively, replace the ad-hoc `saturating_sub` bound checks with a single explicit length validation up front so mismatched declared-flags/account-count combinations are rejected rather than silently mis-consumed in flag-priority order.

### Proof of Concept
```rust
// Rust unit test to add in transaction-status/src/parse_token/extension/permissioned_burn.rs
#[test]
fn test_confidential_burn_mislabels_accounts_on_flag_length_mismatch() {
    use spl_token_2022_interface::extension::confidential_mint_burn::instruction::BurnInstructionData as ConfidentialBurnInstructionData;
    // Construct raw ConfidentialBurn instruction data with:
    //   equality_proof_instruction_offset = 0   (declares an equality CONTEXT account is needed)
    //   ciphertext_validity_proof_instruction_offset = <nonzero> (declares sysvar usage)
    //   range_proof_instruction_offset = 0      (declares a range CONTEXT account is needed)
    // True required optional accounts = sysvar(1) + eq_ctx(1) + range_ctx(1) = 3
    // => expected account_indexes.len() == 4 (fixed) + 3 = 7
    // Attacker instead submits account_indexes.len() == 5.

    let account_indexes: Vec<u8> = (0..5).collect();
    let account_keys = /* 5 unique Pubkeys wrapped in AccountKeys */;

    let parsed = parse_permissioned_burn_instruction(
        &confidential_burn_instruction_bytes_with(/* eq=0, val=nonzero, range=0 */),
        &account_indexes,
        &account_keys,
    ).unwrap();

    let info = parsed.info;

    // Bug: equalityProofContextStateAccount is silently dropped even though
    // equality_proof_instruction_offset == 0 declared it should exist.
    assert!(info.get("equalityProofContextStateAccount").is_none());

    // Bug: permissionedBurnAuthority ends up pointing at account_indexes[3],
    // which per the declared flags should have been a proof-context account,
    // not the burn authority.
    assert_eq!(info["permissionedBurnAuthority"], json!(account_keys[3].to_string()));

    // Bug: "authority" is populated from account_indexes[4], one slot earlier
    // than the true layout (sysvar, eq_ctx, range_ctx, authority, owner) would
    // require (index 6), demonstrating the mismapping.
    assert_eq!(info["authority"], json!(account_keys[4].to_string()));
}
```
Fuzz/invariant plan: iterate `account_indexes.len()` in `4..=8` × all 8 combinations of `(eq_offset, val_offset, range_offset)` zero/nonzero flags; for each, compute the mathematically correct expected account-to-field mapping from the accounts-order contract, and assert the parser either (a) returns `InstructionNotParsable` when `len` doesn't match the flag-implied count, or (b) produces the exact expected mapping when it does — currently case (a) never triggers, confirming the vulnerability.
