### Title
Asymmetric response guard lets a rejecting signer's later Accepted message be recounted as new approval weight - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The mining coordinator's `StackerDBListener` tallies per-block approval/rejection weight from `BlockResponse` messages gossiped by signers over StackerDB. The `Accepted` branch and the `Rejected` branch use two different guards to decide whether a signer's weight has "already been counted," and those guards are not kept in sync, so a signer that has already been tallied as a rejecter can later have its weight tallied again as an approver for the very same block.

### Finding Description
For `BlockResponse::Rejected`, the weight is added only once, gated on insertion into the shared `responded_signers` set: [1](#0-0) 

For `BlockResponse::Accepted`, however, the weight-add guard checks a *different*, accept-only set, `gathered_signatures`, not `responded_signers`: [2](#0-1) 

Only after the weight has already been added does the accept branch insert into `responded_signers` (line 465). This means:
- If a signer sends `Rejected` first: `responded_signers` gets the slot id and `total_weight_rejected` is bumped, but `gathered_signatures` is untouched.
- If that same signer later sends `Accepted` for the same block (a legitimate, self-signed, cross-context-valid message it is fully entitled to produce with its own key — no majority or other signer's key needed): the accept branch's guard `!block.gathered_signatures.contains_key(&slot_id)` is still `true` (since only `responded_signers`, not `gathered_signatures`, was touched by the earlier rejection), so `total_weight_approved` is incremented by that signer's full weight a second time.

The reverse ordering is correctly guarded (an already-`Accepted` signer's later `Rejected` message is blocked, because the accept path already inserted the slot into `responded_signers`, so `responded_signers.insert(slot_id)` in the reject branch returns `false` and the reject weight is not added). The bug is specifically the missing symmetric check in the accept branch.

The net effect is that the same signer's weight is simultaneously present in both `total_weight_approved` and `total_weight_rejected` for one block, breaking the intended invariant that `total_weight_approved + total_weight_rejected + (weight of signers who have not yet responded) == total_weight`. A signer's earlier rejection vote is effectively "recounted as an accept" once it later emits (or re-emits, via normal StackerDB message replay/gossip) an `Accepted` message, since nothing in the accept path checks that the slot already delivered a final verdict.

### Impact Explanation
This falls under the "a rejection recounted as acceptance" impact category. While a single equivocating signer's own weight alone typically cannot single-handedly push `total_weight_approved` past the 70% `weight_threshold` used in `signer_coordinator.rs` (`stacks-node/src/nakamoto_node/signer_coordinator.rs:541`), it corrupts the coordinator's bookkeeping invariant that each signer contributes at most once to the vote tally. This is exploitable by any signer that changes its verdict (whether due to a bug in the signer state machine's re-evaluation path, or by a deliberately Byzantine signer crafting conflicting `Accepted`/`Rejected` messages for the same `signer_signature_hash`), without needing a majority of the signer set or anyone else's key. Combined with even a modest set of genuinely-approving signers, a small number of such flip-flopping signers can make the tally cross the acceptance threshold using weight that has already been logically "spent" on a rejection, undermining the correctness of the miner's decision to broadcast a block as validly signed.

### Likelihood Explanation
Triggering this requires only a single signer (one-slot actor, plus normal StackerDB gossip delivery of two of its own messages) sending a `Rejected` message for a block followed later by an `Accepted` message for that same `signer_signature_hash`. This is a state that can arise either through byzantine behavior (trivial: the signer's own operator crafts both messages) or through legitimate re-evaluation paths in `stacks-signer` where a previously-rejected block can later be reconsidered and signed (see `docs/signer-flows.md` sections on `should_reevaluate_block`/`should_reevaluate_reject_reason`), meaning honest signer implementations can produce exactly this sequence during normal reorg/pre-commit re-evaluation. No cryptographic or state-machine majority is required to reach the vulnerable code path.

### Recommendation
Use a single guard for weight-accounting on both paths. Specifically, gate the `Accepted` branch's weight increment on the same `responded_signers` set used by the `Rejected` branch (i.e., check `!block.responded_signers.contains(&slot_id)` before adding to `total_weight_approved`, mirroring the reject branch's `insert`-based check), so that once a signer's weight has been counted toward either tally for a given block, it can never be added to the other tally as well.

### Proof of Concept
1. Node proposes block `B` with `signer_signature_hash = H`; miner coordinator initializes `BlockStatus` for `H` with `total_weight_approved = 0`, `total_weight_rejected = 0`, empty `gathered_signatures` and `responded_signers`.
2. Signer `S` (weight `w`) broadcasts `BlockResponse::Rejected` for `H`. In `stackerdb_listener.rs` (lines 486-519), `responded_signers.insert(slot_id)` succeeds, `total_weight_rejected += w`.
3. Signer `S` later broadcasts `BlockResponse::Accepted` for the same `H` (e.g., after a local re-evaluation flips its verdict, or a byzantine signer simply emits both). In the `Accepted` branch (lines 386-465), the check `!block.gathered_signatures.contains_key(&slot_id)` is `true` (this set was never touched by step 2), so `total_weight_approved += w` is executed and the signature is stored.
4. Result: `total_weight_approved` and `total_weight_rejected` both include `S`'s weight `w` for the same block `H`, violating the tally invariant and letting `S`'s weight count toward crossing `weight_threshold` in `signer_coordinator.rs` even though that same weight is simultaneously recorded as a rejection.
