## Finding

The external Nouns report's core invariant is: **when an accounting pointer/role is changed (e.g., `ds.timelock`), any pending balance/entitlement still tracked under the *old* pointer must still be correctly settled — otherwise funds/accounting silently diverge from the new pointer.** The Aptos analog exists in `staking_contract::switch_operator` combined with `distribute_internal`'s beneficiary-redirect logic.

### Title
Stale distribution-pool recipient key causes commission to bypass an operator's configured beneficiary after `switch_operator` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

### Summary
`staking_contract::distribute_internal` only redirects a payout to `beneficiary_for_operator(operator)` when the share-pool recipient address equals the **current** `operator` parameter passed in by the caller. When a staker calls `switch_operator`, any commission that becomes distributable *because of* the switch is recorded in the `distribution_pool` under the **old** operator's address, but the `StakingContract` struct is thereafter stored (and later `distribute()`d) under the **new** operator's key. Consequently, the redirect check `recipient == operator` never matches for that old-operator entry, and the funds are paid directly to the old operator's raw address instead of the beneficiary that operator had configured.

### Finding Description
- `switch_operator` forcibly calls `request_commission_internal(old_operator, &mut staking_contract)` before re-keying the contract to `new_operator`: [1](#0-0) 
- `request_commission_internal` records the pending commission via `add_distribution(operator, staking_contract, operator, commission_amount)`, i.e. the share-pool recipient key is the **old operator's address**: [2](#0-1) 
- After the switch, the `StakingContract` (with its `distribution_pool` still containing the old-operator-keyed share) is stored under `new_operator` in the `Store` map: [3](#0-2) 
- When `distribute()`/`distribute_internal` is later invoked, it is called with `operator = new_operator` (the map key), and the redirect only fires `if (recipient == operator)`: [4](#0-3) 
- Because `recipient` (old operator) never equals `operator` (new operator) in this scenario, `beneficiary_for_operator(operator)` is never resolved for the old operator's pending share; the money is deposited straight to the old operator's own account instead of the beneficiary that operator explicitly configured via `set_beneficiary_for_operator`: [5](#0-4) 

This directly contradicts the documented guarantee of the beneficiary feature ("all existing unpaid commission rewards will be paid to the new beneficiary") whenever a staker-initiated operator switch is the event that unlocks the pending commission.

### Impact Explanation
Any operator that has configured a beneficiary (for custody, compliance, or key-hygiene reasons) will have commission silently misdirected to their own raw operator address instead of the beneficiary any time a staker switches operators while commission is outstanding — which is guaranteed to happen since `switch_operator` itself forces a `request_commission_internal` call. This is an "operator commission / beneficiary payout ... corruption that credits the wrong account" as scoped by the task's required impacts, and can result in commission being sent to an address the operator does not intend to receive funds directly (e.g., a hot validator key rather than the secured beneficiary wallet).

### Likelihood Explanation
High likelihood in normal operation: no attacker privilege is required beyond the staker performing a routine, legitimate `switch_operator` call, and the misdirection triggers deterministically whenever the old operator has any accrued/unpaid commission at switch time (which `switch_operator` itself generates) and has previously set a beneficiary.

### Recommendation
Track the true "owner operator" per distribution entry (not just the recipient address, which is also the amount key) so that `distribute_internal` can correctly resolve `beneficiary_for_operator` for stale/old-operator entries regardless of the current map key `operator` passed into the function — e.g., always attempt `beneficiary_for_operator(recipient)` when `recipient` is itself an operator/beneficiary-eligible key, rather than gating the redirect on `recipient == operator`.

### Proof of Concept
1. Staker creates `staking_contract` with `operator1`, stake accrues rewards over an epoch.
2. `operator1` calls `set_beneficiary_for_operator(beneficiary)`.
3. Staker calls `switch_operator(staker, operator1, operator2, new_commission)` — this internally calls `request_commission_internal(operator1, ...)`, adding a distribution entry keyed to `operator1` for the commission accrued up to the switch: [6](#0-5) 
4. Lockup expires; anyone calls `distribute(staker, operator2)` (the contract is now keyed under `operator2`).
5. Inside `distribute_internal`, the check `if (recipient == operator)` compares `operator1 == operator2` → false, so the commission is deposited to `operator1` directly rather than `beneficiary`, contrary to the beneficiary design documented for the feature: [4](#0-3)

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
