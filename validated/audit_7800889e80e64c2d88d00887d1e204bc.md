Based on the code paths I traced, the claimed vulnerability does not hold. Here is the analysis:

**The equality claimed:** the tally for hash `H` in `block_pre_commits` should equal genuine, verified pre-commits for that exact block content; the audit hypothesizes this could be broken by replaying an honest signer's pre-commit under a "manipulated" `signer_signature_hash`.

**Why the guard holds:**

1. `add_block_pre_commit` writes with a composite key `(signer_signature_hash, signer_addr)` and `get_block_pre_committers` / `has_committed` always filter `WHERE signer_signature_hash = ?1`, so a pre-commit recorded for hash `H1` can never be counted toward hash `H2`'s tally. [1](#0-0) 

2. `handle_block_pre_commit`'s `stacker_address` parameter is not attacker-suppliable metadata — it is derived upstream from the StackerDB chunk that carried the `BlockPreCommit(hash)` payload. The dispatcher recovers the sender's public key via `chunk.recover_pk()`, and that recovery uses `get_slot_metadata().auth_digest()`, which is built from `data_hash = Sha512Trunc256Sum::from_data(&self.data)` — a hash over the *entire* serialized message, including the `signer_signature_hash` payload itself. [2](#0-1) [3](#0-2) 

3. Consequently, an attacker cannot take a legitimately-signed chunk from an honest signer and substitute a different `signer_signature_hash` while keeping the same signature valid: any change to the payload changes `data_hash`, which changes the digest that was signed, so `recover_pk` either fails or returns a public key that does not match any real signer's address. In `signer.rs`, addresses recovered this way are checked against `is_valid_signer`; a mismatched/garbage key is simply dropped before `handle_block_pre_commit` is ever called. [4](#0-3) 

4. The only thing an attacker can do is rebroadcast the *exact same* chunk bytes an honest signer already sent. That reproduces the identical `(hash, addr)` key, and `INSERT OR REPLACE` makes this idempotent — it does not add new weight, and the honest signer's genuine pre-commit for their own already-decided vote was going to be counted anyway.

There is no hash-collision or key-confusion path in `add_block_pre_commit`'s keying: the cryptographic binding between the recovered signer address and the exact payload bytes (including the hash) prevents attributing a pre-commit for hash H2 to an honest signer's vote that was actually cast for H1. The 70% threshold check in `handle_block_pre_commit` (`NakamotoBlockHeader::compute_voting_weight_threshold`) therefore only ever tallies weight from committers whose signature genuinely covers that specific hash. [5](#0-4)
