### Title
`getLargestAccounts` returns cached results across different commitment levels, serving stale/wrong-slot data regardless of requested freshness - (File: rpc/src/rpc.rs)

### Summary
Analogous to the DittoETH finding where `proposeRedemption` used a cached oracle price (`LibOracle.getPrice`) instead of an updated one, Agave's `getLargestAccounts` RPC method caches its results in `LargestAccountsCache` keyed only by the `RpcLargestAccountsFilter`, with no consideration of the `commitment` level requested by the caller. This can cause an RPC client requesting a fresher commitment level (e.g. `processed`) to receive a stale response computed against an older bank/slot.

### Finding Description
`get_largest_accounts` first checks a cache via `get_cached_largest_accounts`, keyed solely by `config.filter`: [1](#0-0) 

The cache lookup and cache value (`LargestAccountsCacheValue`) contain only `accounts`, `slot`, and `cached_time` — there is no `commitment` dimension in the cache key at all: [2](#0-1) 

`get_largest_accounts` calls `self.bank(config.commitment)` to resolve the bank for the requested commitment, but that resolved bank/slot is *only used if the cache misses*. If a cache hit occurs, the response uses the previously cached `slot` and `accounts`, which may have been computed for an entirely different commitment level (e.g., cached while a caller asked for `finalized`, then served again to a caller asking for `processed`): [3](#0-2) 

This mirrors the DittoETH root cause exactly: a cached value that should be time/context-sensitive is reused without validating that it still reflects the caller's requested reference point, undermining the correctness guarantee that `commitment`-scoped RPC calls are supposed to provide.

### Impact Explanation
A client that explicitly requests `processed` (or `confirmed`) commitment to get the most up-to-date view of top-balance accounts can receive data computed at an earlier, possibly much older, slot (up to `LARGEST_ACCOUNTS_CACHE_DURATION` seconds stale) while the `RpcResponseContext.slot` field misleadingly reports that older slot as if it were the correctly resolved slot for the request. This is a "wrong-slot data returned" condition from a single unprivileged RPC call — no special/validator privileges are needed, and it requires no more than one call. Because the cache key ignores commitment, mixing commitment levels amplifies the staleness window; e.g., a `finalized` query's result can be served to a `processed` query issued moments later, silently increasing effective staleness in high-throughput/volatile periods (analogous to the Ditto redemption path failing to reflect current market conditions during volatility).

### Likelihood Explanation
High likelihood of triggering: any client can call `getLargestAccounts` with different `commitment` values in quick succession using the JSON-RPC API — this is a normal, permitted usage pattern and requires no crafted input or elevated access.

### Recommendation
Include `commitment` (or the resolved bank slot's commitment class) as part of the `LargestAccountsCache` key, or invalidate/skip the cache when the resolved bank for the current request's commitment differs from the cached entry's bank/slot commitment. At minimum, only serve a cached response when the requested commitment matches what the cached entry was computed under.

### Proof of Concept
1. Call `getLargestAccounts` with `{"commitment": "finalized"}` — this populates `LargestAccountsCache` for filter `None` with `slot = S1` (an older, finalized slot).
2. Immediately (within `LARGEST_ACCOUNTS_CACHE_DURATION`) call `getLargestAccounts` with `{"commitment": "processed"}`.
3. `get_cached_largest_accounts` returns the entry cached in step 1 because the cache key does not include commitment; the response reports `context.slot = S1` and the finalized-era account balances, even though the caller asked for the most recent processed state, which may have since changed (e.g., large transfers changed the largest-account rankings).

*(Note: I was unable to directly inspect the numeric value of `LARGEST_ACCOUNTS_CACHE_DURATION` in the available index before running out of tool iterations, but its existence and usage in `rpc_service.rs` confirm the cache has a non-zero TTL during which this cross-commitment staleness window is exploitable.)*

#[derive(Debug, Clone)]
pub struct LargestAccountsCache {
    duration: u64,
    cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>,
}

#[derive(Debug, Clone)]
struct LargestAccountsCacheValue {
    accounts: Vec<RpcAccountBalance>,
    slot: u64,
    cached_time: SystemTime,
}

impl LargestAccountsCache {
    pub(crate) fn new(duration: u64) -> Self {
        Self {
            duration,
            cache: HashMap::new(),
        }
    }

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }
