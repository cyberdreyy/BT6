### Title
Cross-user response confusion via unsanitized MessageId-only key in `savedCallbacks` map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.savedCallbacks` is keyed solely by the client-supplied `msg.Body.MessageId` [1](#0-0) , with no binding to the requester's `Sender`/DON. Since two unrelated HTTP clients can pick the same `MessageId` string, one user's `HandleLegacyUserMessage` call silently overwrites another's entry in the map, and the first node response for that `MessageId` is delivered to whichever callback is currently registered—not necessarily the original submitter.

### Finding Description
In `HandleLegacyUserMessage`, the handler stores the caller's callback keyed only by `msg.Body.MessageId`: [2](#0-1) 
There is no existence check (unlike a true "insert-if-absent") — a plain map write — so if attacker sends a request with `MessageId = X` after (or racing) a victim's request also using `MessageId = X`, the attacker's `savedCallback` entry simply replaces the victim's in the map, orphaning the victim's callback.

On the node-response path, `handleWebAPITriggerMessage` looks the callback up again using only the echoed `msg.Body.MessageId` from the node's response: [3](#0-2) 
`HandleNodeMessage` only validates that the DON node's signature matches its own claimed `nodeAddr` (`msg.Body.Sender != nodeAddr`) [4](#0-3)  — it performs no check that the response corresponds to the *user* who originally registered that `MessageId`. Whichever request is currently keyed under `MessageId` receives the reply.

Crucially, `MessageId` is fully attacker-controlled: it is set from the client's signed `Message.Body.MessageId` field, an arbitrary string chosen by the caller (see the CLI tool `core/scripts/gateway/web_api_trigger/invoke_trigger.go` defaulting to `"12345"`, and tests hard-coding `"12345"`) [5](#0-4) [6](#0-5) . Validation only checks length/null-byte constraints, not uniqueness or namespacing: [7](#0-6) .

This is a real regression relative to the pattern used elsewhere in the same package tree: `common.RequestCache` (used by the `vault` and `confidentialrelay` handlers) explicitly namespaces its cache key by `{sender, id}` and rejects duplicate keys with `"request already exists"`: [8](#0-7) [9](#0-8) . The capabilities handler's hand-rolled `savedCallbacks` map does not use this safer primitive and omits the sender binding entirely.

### Impact Explanation
An unprivileged HTTP client of the gateway's user-facing endpoint can cause a legitimate victim's in-flight `web_api_trigger` request to never receive its correct response (silently dropped/orphaned callback), while the attacker's own callback instead receives the DON node's response intended to correlate with the victim's `MessageId`. This is a cross-user response confusion / broken request isolation bug: the victim's callback channel is discarded, and depending on downstream consumers of `HandleLegacyUserMessage` (e.g., HTTP handler waiting on `cb.Wait`), the victim's HTTP request may hang until timeout or receive no response, while an attacker who shares a `MessageId` can intercept the reply meant for that ID slot. This matches the "cross-user response confusion / hijacked capability result delivery" impact class in the audit scope.

### Likelihood Explanation
Feasibility is high: the only precondition is that the attacker, as an ordinary HTTP client with a valid signing key (any key works — the code does not require any special privilege, allowlist entry, or role), submits a `web_api_trigger` message with a `MessageId` value colliding with a targeted victim's message. Since `MessageId` is entirely attacker-chosen and many client tools/scripts use short, predictable, or default IDs (e.g., `"12345"`), collisions are trivially producible without needing tight timing — the attacker's request just needs to be received after the victim's registration and before the victim's node response arrives (a window on the order of the DON response latency, typically well under `defaultCallbackMaxAgeSec` = 120s). No signature forgery, DON compromise, or gateway compromise is required.

### Recommendation
Key `savedCallbacks` by a composite of the verified request `Sender` (derived from the signature, not attacker-supplied) and `MessageId`, mirroring `common.RequestCache`'s `globalId{sender, id}` pattern. Reject/dedupe on insertion if a key already exists rather than silently overwriting, and validate at lookup time in `handleWebAPITriggerMessage` that the node response's target sender matches the original requester before invoking `savedCb.SendResponse`. Consider migrating this handler to reuse `common.RequestCache` directly instead of a bespoke `map[string]*savedCallback`.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler via `setupHandler(t)`.
2. Create two distinct signed `Message`s (`victimMsg`, `attackerMsg`) using different private keys but with the **same** `MessageId = "dup-id"`, via the existing `triggerRequest` helper.
3. Register victim's callback: `cbVictim := hc.NewCallback(); handler.HandleLegacyUserMessage(ctx, victimMsg, cbVictim)`.
4. Immediately register attacker's callback with same `MessageId`: `cbAttacker := hc.NewCallback(); handler.HandleLegacyUserMessage(ctx, attackerMsg, cbAttacker)`.
5. Assert `len(handler.savedCallbacks) == 1` and that the stored entry now points to `cbAttacker` (proving overwrite occurred).
6. Simulate a node response with `MessageId = "dup-id"` via `hc.ValidatedResponseFromMessage` + `handler.HandleNodeMessage(ctx, resp, nodes[0].Address)`.
7. Assert `cbAttacker.Wait(ctx)` returns the response, and `cbVictim.Wait(ctx)` times out / never resolves — demonstrating the victim's callback was silently dropped and the response was misdirected to the attacker, in violation of per-sender isolation.

```go
func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
```
