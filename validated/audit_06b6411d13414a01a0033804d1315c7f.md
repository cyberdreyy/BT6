### Title
JWT replay-cache TOCTOU race allows concurrent replay of a single JWT to trigger duplicate workflow executions - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` checks `jwtCache.isReplay(claims.ID)` and only later calls `jwtCache.recordUsage(claims.ID)` after further processing, with no atomicity between the check and the record. Two goroutines processing the same JWT concurrently can both observe `isReplay()==false` before either calls `recordUsage()`, so both pass authorization and both trigger workflow execution from a single signed JWT.

### Finding Description
`httpTriggerHandler.HandleUserTriggerRequest` (core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go:88-140) calls `h.authorizeRequest` (line 361-369) which calls `h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)`.

In `Authorize` (core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go:80-108):
1. Line 87: `h.jwtCache.isReplay(claims.ID)` — this only takes `cache.mu.RLock()`, checks map membership, and releases the lock (lines 399-405).
2. Lines 92-104: authorized-key lookup logic (no locking related to jwtCache).
3. Line 105: `h.jwtCache.recordUsage(claims.ID)` — this is called only at the very end, after all other checks pass, taking `cache.mu.Lock()` to insert the jti (lines 407-412).

This is a classic check-then-act (TOCTOU) race: `isReplay` and `recordUsage` are two separate, non-atomic critical sections. If two goroutines call `Authorize` concurrently with the same token (same `jti`), both can execute `isReplay(claims.ID)` and get `false` before either has called `recordUsage(claims.ID)`. Both goroutines then pass the authorized-key check and both call `recordUsage`, and both return a valid `*gateway.AuthorizedKey` to their respective `authorizeRequest` callers, allowing both requests to proceed to `checkRateLimit` and `sendWithRetries`, triggering two independent workflow executions from a single signed JWT. There is no per-jti mutex, no atomic check-and-insert (e.g., a single locked operation that checks-and-inserts), and no idempotency key derived from `jti` at the `setupCallback`/request-ID level that would prevent this (the request-ID dedup in `setupCallback` at line 398-435 is keyed on the caller-supplied JSON-RPC `req.ID`, not on `jti`, so an attacker can send two requests with different `req.ID` values but the identical JWT/`jti` to bypass that unrelated dedup entirely).

### Impact Explanation
This allows an attacker holding a single legitimately signed JWT for workflow A to trigger the workflow's execution more than once concurrently, bypassing the "one signed request = one authenticated action" invariant. This maps to Chainlink's bounty class of unauthorized/duplicate job run or action trigger from a single credential — impactful for CRE workflows tied to funds movement, external side effects, or rate/quota-limited executions, since the replay window (`JWTReplayPeriodMs`) is meant to strictly bound a JWT to one use.

### Likelihood Explanation
Exploitation only requires an attacker to hold one valid, unexpired JWT for a workflow they are otherwise authorized to trigger (an unprivileged holder of one signed credential — matching the allowed unprivileged-attacker model). No admin/operator access is needed. The race window between `isReplay` and `recordUsage` is small but real network-facing services routinely receive genuinely concurrent requests (e.g., attacker deliberately fires two requests near-simultaneously), making this readily reproducible under load or with a burst of concurrent goroutines, as would be demonstrated in a concurrency unit test.

### Recommendation
Make JWT replay check-and-record atomic: hold `cache.mu.Lock()` for the full check-and-insert sequence, e.g. add a method `checkAndRecord(jti) bool` that under a single lock checks presence and inserts if absent, returning whether it was a replay. Call this once in `Authorize` immediately after JWT verification, before doing any authorized-key lookups, and remove the separate `isReplay`/`recordUsage` calls in favor of this atomic method. If authorization subsequently fails (e.g., signer not found), consider whether to leave the jti marked used (to avoid probing) or roll it back—but the check-and-insert step itself must never leave a race window.

### Proof of Concept
Go concurrency unit test in `core/services/gateway/handlers/capabilities/v2` (or a new `workflow_metadata_handler_race_test.go`):
1. Construct a `WorkflowMetadataHandler` with a valid workflow ID registered and an authorized key matching a test signer.
2. Craft one valid JWT-signed `jsonrpc.Request` (fixed `jti`) for that workflow/signer, following the pattern used in existing `Authorize`/`VerifyRequestJWT` tests.
3. Launch two goroutines that both call `h.Authorize(workflowID, token, req)` "simultaneously" (e.g., synchronized via a start `sync.WaitGroup`/channel to maximize the race window), each recording success/failure.
4. Assert that in a statistically significant number of trials (e.g., loop N=1000 times, each with a fresh handler/jti), at least one trial shows **both** goroutines returning `nil` error (i.e., both succeeded), demonstrating that the replay guard failed to serialize the two calls.
5. Optionally add a `-race` flag run to confirm the map accesses in `jwtReplayCache` don't corrupt state, and to show that without the fix, functionally duplicate authorizations occur even though the map itself is race-free (proving this is a logical TOCTOU bug, not just a data race). func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
