### Title
`purchase_with_cap()` silently transfers excess SUI payment to kiosk owner profits — (`File: crates/sui-framework/packages/sui-framework/sources/kiosk/kiosk.move`)

---

### Summary

`Kiosk::purchase_with_cap` accepts any `payment: Coin<SUI>` whose value is **≥ min_price**, then deposits the **entire coin** into `self.profits`. Any amount above `min_price` is permanently transferred to the kiosk owner with no refund to the buyer.

---

### Finding Description

`purchase_with_cap` uses a `>=` guard and then unconditionally puts the whole coin into profits:

```move
// kiosk.move line 427
assert!(paid >= min_price, EIncorrectAmount);   // >=, not ==

// kiosk.move line 432
coin::put(&mut self.profits, payment);           // entire coin consumed
``` [1](#0-0) 

The excess `paid - min_price` is never split off and returned to the caller. It silently accrues to the kiosk owner's withdrawable profits.

Contrast with the regular `purchase` path, which enforces strict equality and is not affected:

```move
// kiosk.move line 381
assert!(price == payment.value(), EIncorrectAmount);  // strict ==
``` [2](#0-1) 

The root cause is identical to the reported Solidity bug: a `>=` payment check combined with full consumption of the payment object and no change-return path.

---

### Impact Explanation

A buyer who passes a `Coin<SUI>` with value greater than `min_price` — whether by mistake, because they did not split the coin first, or because a third-party dApp constructed the PTB — permanently loses the excess to the kiosk owner. The loss is irreversible once the transaction is committed. This constitutes **harmful smart-contract behavior** (Medium impact under the allowed gate).

---

### Likelihood Explanation

`purchase_with_cap` is a public framework function callable by any SUI holder. Overpayment is realistic in several common flows:

1. A buyer holds a single large coin and passes it directly without splitting.
2. A dApp or PTB builder constructs the payment coin from a larger balance without trimming to exactly `min_price`.
3. A buyer intentionally bids above `min_price` expecting change back (consistent with the auction-style semantics the `PurchaseCap` documentation implies).

---

### Recommendation

Either enforce strict equality (matching the `purchase` path):

```move
assert!(paid == min_price, EIncorrectAmount);
```

Or split the excess and return it to the caller before depositing:

```move
let paid = payment.value();
assert!(paid >= min_price, EIncorrectAmount);
assert!(object::id(self) == kiosk_id, EWrongKiosk);

let excess = paid - min_price;
if (excess > 0) {
    let change = coin::split(&mut payment, excess, ctx);
    transfer::public_transfer(change, tx_context::sender(ctx));
};
coin::put(&mut self.profits, payment);
``` [3](#0-2) 

---

```text
public fun purchase_with_cap<T: key + store>(
    self: &mut Kiosk,
    purchase_cap: PurchaseCap<T>,
    payment: Coin<SUI>,
): (T, TransferRequest<T>) {
    let PurchaseCap { id, item_id, kiosk_id, min_price } = purchase_cap;
    id.delete();

    let id = item_id;
    let paid = payment.value();
    assert!(paid >= min_price, EIncorrectAmount);
    assert!(object::id(self) == kiosk_id, EWrongKiosk);

    df::remove<Listing, u64>(&mut self.id, Listing { id, is_exclusive: true });

    coin::put(&mut self.profits, payment);
    self.item_count = self.item_count - 1;
    df::remove_opt<Lock, bool>(&mut self.id, Lock { id });
    let item = dof::remove<Item, T>(&mut self.id, Item { id });

    (item, transfer_policy::new_request(id, paid, object::id(self)))
}
