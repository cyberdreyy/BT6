### Title
Cross-user response confusion via attacker-controlled MessageId collision in savedCallbacks map - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`MessageId` is a fully attacker-controlled field of the user-submitted `api.Message`, validated only for length/null-byte constraints in `Message.Validate` [1](#0-0) , and is used directly and exclusively as the key into `h.savedCallbacks` with no existence check or per-sender namespacing [2](#0-1) . Any unauthenticated gateway client can submit a request with a `MessageId` colliding with another in-flight user's `MessageId`, overwriting that user's saved callback before the DON node's response arrives.

### Finding Description
In `gateway.ProcessRequest`, a legacy request only has its `MessageId` validated for length and trailing-null-byte constraints via `msg.Validate()` — there is no uniqueness or ownership check, and the ID is entirely chosen by the caller [3](#0-2) . The request is then dispatched to `HandleLegacyUserMessage`, which unconditionally overwrites any existing map entry: `h.savedCallbacks[msg.Body.MessageId] = &savedCallback{...}` [4](#0-3) . The map is keyed solely by `MessageId` (a plain string), with no binding to `Sender`/requester identity anywhere in the `savedCallback` struct [5](#0-4) .

Exploit flow: victim submits a `MethodWebAPITrigger` request with `MessageId=X`, which stores victim's `Callback` in `savedCallbacks[X]` and forwards the request to all DON members [6](#0-5) . Before any node responds, the attacker submits their own `MethodWebAPITrigger` message with the same `MessageId=X`, overwriting `savedCallbacks[X]` with the attacker's own callback. When a DON node later replies with `MessageId=X` (which could be the response to either the victim's or attacker's forwarded request, since nodes echo back whatever MessageId they were given), `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks[X]` and delivers the response to whichever callback currently occupies that slot — the attacker's, if it overwrote last [7](#0-6) . This can cause the victim's HTTP request to time out and never receive a response, while the attacker's HTTP connection receives whatever response the DON node sent back (potentially containing information intended for the victim). The identical unguarded pattern exists in `handler.dummy.go`'s `savedCallbacks` map [8](#0-7) , confirming this is a structural gap rather than an isolated bug.

No authentication is required to reach this path — `HandleLegacyUserMessage` is invoked directly from the gateway's public HTTP `ProcessRequest` entry point for any client presenting a validly-signed `api.Message` with a matching `DonId`; there is no per-sender scoping of callback storage or any check that a `MessageId` is unique/not already in flight [9](#0-8) .

### Impact Explanation
This enables cross-user response confusion / request-response hijacking within a shared DON's gateway handler: an unprivileged, unauthenticated attacker able to submit signed requests to the same gateway/DON can cause another user's in-flight `web_api_trigger` response (which may include computed data, execution results, or headers/body content returned via `Response.Body`/`Headers`) to be delivered to the attacker's own HTTP connection instead of the victim's, and cause the victim to receive no response (denial of service for that request). This matches the "cross-user response confusion" / unauthorized disclosure-of-another-user's-response-data class explicitly called out as in-scope.

### Likelihood Explanation
Exploitation requires only: (1) the ability to submit signed gateway messages (any gateway client credential, not privileged), (2) knowledge or prediction of a victim's in-flight `MessageId`, and (3) submitting a colliding request before the victim's response arrives. The `MessageId` value is entirely chosen by the requester and is not required to be random/unpredictable by the protocol — if a client-side implementation uses predictable IDs (sequential counters, timestamps, or a fixed scheme), collision is trivial; even with a random 128-byte space, the underlying design flaw (no ownership/uniqueness enforcement, no scoping by sender) remains a genuine defense-in-depth gap that a co-tenant with insight into another client's ID generation scheme (which is application-specific and outside gateway's control) could exploit. The race window is small but real given asynchronous DON response delivery and concurrent client access to the same handler instance.

### Recommendation
Scope `savedCallbacks` keys by both `Sender` and `MessageId` (e.g., `sender+":"+messageId`) rather than `MessageId` alone, and/or reject `HandleLegacyUserMessage` calls when an entry for the same key already exists instead of silently overwriting it, returning an error to the second caller. Apply the same fix to `handler.dummy.go`.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, construct two `api.Message`s, `victimMsg` and `attackerMsg`, with identical `Body.MessageId` but different `Body.Sender`/payload, each signed by a different key.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCallback)` to populate `savedCallbacks[msgID]` with the victim's callback.
3. Before delivering any node response, call `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCallback)` with the same `msgID`, and assert via reflection/inspection (or exported test helper) that `savedCallbacks[msgID]` now points to the attacker's callback, not the victim's.
4. Simulate a node response for `msgID` via `handler.HandleNodeMessage`, and assert that `attackerCallback.SendResponse` is invoked (receiving the response) while `victimCallback.SendResponse` is never called — demonstrating the overwrite/hijack and confirming line `handler.go:412` performs no existence check.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
