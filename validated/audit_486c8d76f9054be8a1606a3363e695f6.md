## Title
MultisigFactory::create Has No Existence Check or Failure Callback — Colliding `name` Silently Freezes the Caller's Attached Deposit - ([File: multisig-factory/src/lib.rs])

### Summary
`MultisigFactory::create` derives the sub-account to deploy as `"{name}.{current_account_id}"` and immediately issues `create_account()` + `deploy_contract()` + `transfer()` + `function_call("new", …)` as one promise batch, with no local bookkeeping of already-used names and, critically, no callback to detect and refund a failed creation. [1](#0-0)  This mirrors the report's bug class: the contract assumes the target identifier ("account name" here, "token address" in the original report) cannot already be taken, and provides no reconciliation path when that assumption is violated by another party.

### Finding Description
`create()` builds `account_id = format!("{}.{}", name, env::current_account_id())` and fires a single promise chain without ever checking whether that account already exists, and without registering any `.then(...)` callback on itself: [1](#0-0) 

Compare this with the two sibling factories in the same repository, `StakingPoolFactory` and `LockupFactory`, both of which explicitly guard against/handle a failed `create_account()`:
- `StakingPoolFactory::create_staking_pool` inserts the target id into an `UnorderedSet` first (`assert!(self.staking_pool_account_ids.insert(&staking_pool_account_id), "The staking pool account ID already exists")`) and registers `on_staking_pool_create`, which checks `is_promise_success()` and, on failure, refunds the attached deposit back to `predecessor_account_id` via `Promise::new(predecessor_account_id).transfer(...)`. [2](#0-1) [3](#0-2) 
- `LockupFactory::create` similarly registers `on_lockup_create`, which refunds the deposit to `predecessor_account_id` if `is_promise_success()` is false. [4](#0-3) 

`MultisigFactory::create` has neither mechanism. On NEAR, sub-account creation via `CreateAccount` can only be attempted by the parent account (here, the factory itself acting as predecessor of its own promise), so an external attacker cannot pre-create the sub-account directly. However, nothing stops an attacker from calling the factory's own `create("popular-name", attacker_members, 1)` before a legitimate caller's `create("popular-name", legit_members, k)` lands. Whichever transaction executes first successfully creates `"popular-name.multisig-factory"` and becomes its owner. When the second transaction's promise batch executes, `create_account()` fails because the account already exists, which fails the entire action batch (`deploy_contract`, `transfer`, `function_call` in the same batch all fail together). Because there is no callback checking `is_promise_success()`, the attached NEAR deposit from the second (legitimate) caller is never returned to that caller — the refund of a failed receipt's transferred balance goes to the receipt's predecessor, which is the `MultisigFactory` contract account itself, not the original transaction signer. `MultisigFactory` exposes no method to withdraw or reallocate that stranded balance.

### Impact Explanation
This breaks the custody binding "attached deposit sent by the caller == value received by the caller's intended contract." A caller's NEAR is debited but never delivered to them nor returned to them; it becomes stuck in the factory account with no code path to recover it. This matches the Critical impact category: funds permanently frozen, reached purely by an unprivileged attacker without any foundation/owner/multisig-member/victim-key/redeploy/malicious-validator dependency — the attacker only needs to submit a `create` call with a `name` they anticipate (or observe) another user will also use.

### Likelihood Explanation
Likelihood is moderate to high in any environment with visible mempools/transaction ordering, and even opportunistically without front-running whenever two independent users pick the same human-meaningful `name` (e.g., a common team/project name) for their multisig. No special access or timing precision beyond ordinary transaction submission is required, and the factory itself performs no uniqueness check that would otherwise prevent the race.

### Recommendation
Mirror the pattern already used by `StakingPoolFactory` and `LockupFactory`: maintain a persisted set of already-created multisig account ids and reject `create()` calls that reuse a name still pending/created, and/or attach a `.then(...)` callback (`on_multisig_create`) that checks `is_promise_success()` and refunds `env::attached_deposit()` to `env::predecessor_account_id()` when the account creation fails.

### Proof of Concept
1. Attacker observes (or simply predicts) a pending transaction calling `MultisigFactory::create(name: "acme", members: [victim_key], num_confirmations: 2)`.
2. Attacker submits `create(name: "acme", members: [attacker_key], num_confirmations: 1)` with a smaller attached deposit, which lands first: `"acme.multisig-factory"` is created and controlled solely by the attacker.
3. The victim's original transaction executes: the `Promise::new("acme.multisig-factory").create_account()...` batch fails because the account already exists. Since `MultisigFactory::create` has no callback (unlike `on_staking_pool_create`/`on_lockup_create`), the victim's attached NEAR deposit is refunded to the receipt predecessor — the `MultisigFactory` contract account — not to the victim.
4. The victim's NEAR is now stuck in the `MultisigFactory` account balance permanently, with no exposed method to reclaim or redirect it, while the attacker holds sole control of the "acme" multisig identity the victim intended to own.

    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }

    /// Callback after a lockup was created.
    /// Returns the promise if the lockup creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
