### Title
Regular-file extraction in tar+zstd extractor writes through a pre-existing symlink instead of replacing it - ([File: commands/helpers/archive/tarzstd/tarzstd_extractor.go])

### Summary
`extractor.Extract` in `commands/helpers/archive/tarzstd/tarzstd_extractor.go` creates regular files with a plain `os.Create(path)` call (line 88) without first removing any pre-existing filesystem entry at that path. If a symlink was left at `path` by a previous extraction into the same (reused) directory, `os.Create` follows the symlink (standard POSIX/Go semantics, no `O_NOFOLLOW`) and writes the new archive's file content through it to the symlink's target, rather than replacing the symlink with a regular file.

### Finding Description
`Extract` processes tar entries in a single pass: symlink entries are deferred and only materialized on disk after the loop finishes via `os.Symlink(hdr.Linkname, path)` at lines 76 and 113-117, while regular file entries are written immediately with `os.Create(path)` at line 88. Within one archive/one `Extract` call, this ordering is safe: a symlink named `P` is never actually created on disk until the deferred loop, so a later regular-file entry for the same `P` in the *same* archive simply gets `os.Create` on a non-existent path.

The exploit path spans two extraction cycles into the *same reused directory* (e.g. the runner's cache dir passed as `wd` in `commands/helpers/cache_extractor.go` `CacheExtractorCommand.Execute`, lines 618-663, calling `archive.NewExtractor(...).Extract(...)`):
1. First extraction: archive contains only a symlink entry `P -> /some/target`. It gets deferred and, at the end of `Extract`, actually created on disk with `os.Symlink` (lines 113-116). This symlink now persists in the cache directory.
2. Second extraction (subsequent job/pipeline run reusing the same cache directory, e.g. same cache key): the archive contains a *regular file* entry named `P`. The loop hits the `fi.Mode().IsRegular()` branch (line 87) and calls `os.Create(path)` directly. Since `os.Create` is `OpenFile(name, O_RDWR|O_CREATE|O_TRUNC, 0666)` with no `O_NOFOLLOW`, and a symlink already exists at `path`, the OS resolves the symlink and opens/truncates the target file instead of replacing the symlink.

Critically, the runner's own zip extractors (`helpers/archives/zip_extract.go`, `extractZipFileEntry`, lines 41-59) explicitly call `os.Remove(file.Name)` immediately before `os.OpenFile(..., O_CREATE|O_TRUNC, ...)` — precisely to avoid this class of issue. The tar+zstd extractor has no equivalent removal/guard, so it is inconsistent with the safer pattern already present elsewhere in the codebase. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The archiver side confirms symlinks are faithfully round-tripped: `tarzstd_archiver.go` reads the symlink target via `os.Readlink` and stores it as a tar header with `Linkname` set (lines 85-96), so an attacker fully controls the planted symlink's name and target through ordinary job file operations (`ln -s`) before the cache is saved. [5](#0-4) 

As for whether cleanup prevents this: `shells/abstract.go`'s `addExtractCacheCommand` only removes cache paths after a *failed* extraction, gated by `FF_CLEAN_UP_FAILED_CACHE_EXTRACT` — there is no cleanup of the cache directory before a normal/successful extraction, since caches are intentionally incremental/persistent across runs. This means a symlink planted by one job's cache save can persist into a later job's cache restore into the same directory. [6](#0-5) 

### Impact Explanation
An attacker who controls two sequential pipeline runs sharing the same cache key/directory (a normal capability for any pipeline author, no special privileges required) can plant a symlink `P -> /some/writable/path` via a cache save in run 1, then in run 2 push a cache/archive containing a regular file named `P`. On restore, the tar+zstd extractor writes that regular file's content through the stale symlink to `/some/writable/path` instead of at the intended cache path `P`. The impact is scoped to writing attacker-controlled content to whatever path the symlink target resolves to, within the privileges of the process running cache extraction (typically the build/helper container's user) — a path-confinement violation of "file operations must stay within intended cache root," though the ultimate target is still limited to paths writable by that process (e.g. not `/etc/shadow` unless the extractor runs as root, which is not the documented/typical case for build execution).

### Likelihood Explanation
Feasible and repeatable: it only requires the attacker to control CI job scripts across two runs using the same `cache: key`, which is entirely within a normal, unprivileged pipeline author's control. No cross-tenant/cross-project access is needed since it's the attacker's own cache being poisoned and then abused within their own job — the primary risk is escaping the intended cache-root when the symlink target points outside of it (e.g. to a shared workspace path or another cache-mounted volume), which can matter in shared-runner/shared-filesystem deployments.

### Recommendation
Before creating a regular file in the `fi.Mode().IsRegular()` branch of `tarzstd_extractor.go` (around line 87-88), remove any pre-existing filesystem entry at `path` (mirroring `extractZipFileEntry`'s `os.Remove(file.Name)` pattern), or use `os.OpenFile` with `O_CREATE|O_EXCL` after an explicit `os.Remove`/`Lstat` check, ensuring symlinks are never silently dereferenced. Apply the same guard before `os.Mkdir` for directory entries and before `os.Symlink` for symlink entries, so any stale entry type from a previous extraction is unconditionally replaced rather than followed.

### Proof of Concept
Go integration test in `commands/helpers/archive/tarzstd`:
```go
func TestExtractDoesNotFollowStaleSymlinkAcrossRuns(t *testing.T) {
    dir := t.TempDir()

    // Run 1: archive containing only a symlink "victim" -> outsideTarget
    outside := filepath.Join(t.TempDir(), "outside.txt")
    require.NoError(t, os.WriteFile(outside, []byte("original"), 0644))
    buildAndExtractArchive(t, dir, []tarEntry{
        {name: "victim", linkname: outside, typeflag: tar.TypeSymlink},
    })
    fi, err := os.Lstat(filepath.Join(dir, "victim"))
    require.NoError(t, err)
    require.True(t, fi.Mode()&os.ModeSymlink != 0) // symlink persisted

    // Run 2: archive containing a regular file "victim" with attacker content
    buildAndExtractArchive(t, dir, []tarEntry{
        {name: "victim", content: []byte("attacker-controlled"), typeflag: tar.TypeReg},
    })

    // Assertion: outside.txt (the old symlink target) must NOT have been overwritten
    content, _ := os.ReadFile(outside)
    assert.Equal(t, "original", string(content), "extraction must not write through a stale symlink")

    // Assertion: "victim" in dir must now be a regular file, not still resolving through the symlink
    fi2, err := os.Lstat(filepath.Join(dir, "victim"))
    require.NoError(t, err)
    assert.False(t, fi2.Mode()&os.ModeSymlink != 0, "victim should be replaced with a regular file")
}
```
Expected current (buggy) behavior: the assertion on `outside.txt` content fails because `os.Create` followed the symlink and overwrote `outside.txt` with `"attacker-controlled"`.

func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
