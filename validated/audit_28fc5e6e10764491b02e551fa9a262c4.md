### Title
Loss-adjusted withdraw receipt escapes its haircut when a second request overwrites `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` records the epoch to haircut through a single per-user slot, `lastWithdrawRequest[_user]`. When a stop epoch realizes a loss, `collectWithdrawFunds` funds only a reduced amount and stores the haircut in `lossRecoveryPriceByEpoch[epochNumber]`. The only path that applies that haircut, `_claimLossAdjustedWithdrawRequest`, reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Because `requestWithdraw` overwrites `lastWithdrawRequest[_user]` with the new `epochNumber` on every request and never checks for an existing unclaimed receipt, a user can place a second withdraw request, move the marker to a non-loss epoch, and have the old loss-adjusted receipt paid at par through `_claimFundedWithdrawRequest`.

### Finding Description
- On `requestWithdraw`, the strategy sets `lastWithdrawRequest[_user] = currentEpoch` and accumulates `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` without checking whether the user still holds an unclaimed loss-adjusted receipt (`IdleCreditVault.sol` requestWithdraw body, `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequests[_user] += _amount`).
- On a lossy `stopEpochWithDuration`, `collectWithdrawFunds(_amount)` with `_amount < pendingBasis` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws`, so the strategy only ever pulls the post-haircut amount from the CDO.
- `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]` and returns early if `lossRecoveryPriceByEpoch[lossEpoch] == 0`.
- `_clearWithdrawClaimForEpoch` only clears the epoch passed to it; the stale `withdrawsRequestsByEpoch[_user][lossEpoch]` and its share of `withdrawsRequests[_user]` survive untouched.
- `_claimFundedWithdrawRequest` then pays `amount = withdrawsRequests[_user] + settledApr0` at par via `_transferFundedClaim`, once `epochNumber > lastWithdrawRequest[_user]` — a condition the attacker's second request trivially satisfies after the next stop.

Attack sequence (unprivileged lender):
1. Epoch N running: attacker calls `requestWithdraw(X)` via the CDO; `lastWithdrawRequest[attacker] = N`, `withdrawsRequests[attacker] += X`.
2. Honest manager calls `stopEpochWithDuration` with a loss; borrower funds only `pendingBasis * (1 - haircut)`. `lossRecoveryPriceByEpoch[N] = price < RECOVERY_FULL`.
3. Epoch N+1 running: attacker calls `requestWithdraw(dust)` (any small tranche amount, e.g. acquired by depositing 1 unit). `lastWithdrawRequest[attacker] = N+1` — the pointer to the loss epoch is destroyed.
4. Epoch N+1 stops normally and is fully funded. Attacker calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` sees `lossRecoveryPriceByEpoch[N+1] == 0` and returns 0; `_claimFundedWithdrawRequest` pays the full aggregate `X + dust` at par.

The attacker receives `X` at 100% instead of `X * lossRecoveryPrice / RECOVERY_FULL`, while the strategy was only funded `X * lossRecoveryPrice / RECOVERY_FULL` for that receipt. The difference is paid out of underlying that belongs to other funded claimants or the default-recovery reserve.

### Impact Explanation
Direct theft / insolvency equal to the escaped haircut: `X * (RECOVERY_FULL - lossRecoveryPrice) / RECOVERY_FULL`. With a 50% loss-adjusted price the attacker doubles their payout relative to entitlement. The strategy's funded reserve is drained by exactly the haircut amount, so other pending-epoch claimants (or the recovery reserve in a later default) are left short. The "one receipt one payout at its epoch price" and loss-socialization invariants are both broken — a single user unilaterally opts out of an already-realized, already-crystallized loss.

### Likelihood Explanation
Fully attacker-controlled and cheap: it requires only two `requestWithdraw` calls (the second can be dust-sized) timed around a lossy stop, plus one `claimWithdrawRequest`. No privileged role, timing race, or external dependency is needed. Any lossy `stopEpochWithDuration` creates the condition; KYC-gated tranche holders are the expected user base, so the attacker profile is explicitly in scope. The only precondition is that the vault uses per-epoch loss accounting (`defaultRecoveryInitialized`), which is the current code path.

### Recommendation
Do not allow `requestWithdraw` to overwrite `lastWithdrawRequest[_user]` while an uncleared loss-adjusted receipt exists, or make the loss claim epoch-independent. Concretely, either:
- in `requestWithdraw`, settle/apply any existing loss-adjusted receipt before recording the new request (i.e. eagerly run `_clearWithdrawClaimForEpoch(_user, lastWithdrawRequest[_user], false)` when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and convert it into a haircutted funded balance), or
- iterate `withdrawsRequestsByEpoch` entries rather than relying on the single `lastWithdrawRequest` slot when resolving the loss epoch, so every receipt is priced by the epoch that created it.

### Proof of Concept
Reproducible Foundry fork PoC (structure; reuse helpers from `test/foundry/IdleCreditVault.t.sol`/`IdleCDOEpochQueue.t.sol`):

```solidity
function testLossHaircutEscape() external {
    // Epoch N running: attacker deposits and requests withdraw of X tranches
    uint256 tranchesX = _depositWithUser(attacker, 1_000e6);
    _requestWithdrawWithUser(attacker, tranchesX);

    // Manager stops epoch N with a 50% loss (stopEpochWithDuration -> collectWithdrawFunds partial)
    _stopCurrentEpochWithLoss(50e16); // lossRecoveryPriceByEpoch[N] = 0.5e5-ish < RECOVERY_FULL

    // Epoch N+1 running: attacker requests a dust withdraw to overwrite lastWithdrawRequest
    uint256 dust = _depositWithUser(attacker, 1); // minimal tranche amount
    _requestWithdrawWithUser(attacker, dust);
    assertEq(strategy.lastWithdrawRequest(attacker), strategy.epochNumber()); // marker moved off loss epoch

    // Epoch N+1 stops cleanly and is fully funded
    _stopCurrentEpochWithApr(10e18);

    // Attacker claims: loss path skipped (lossRecoveryPriceByEpoch[N+1] == 0),
    // funded path pays aggregate at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(cdoEpoch);
    strategy.claimWithdrawRequest(attacker);

    uint256 paid = underlying.balanceOf(attacker) - balPre;
    uint256 entitled = tranchesX * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL + dust;
    assertGt(paid, entitled); // haircut escaped: paid ~= tranchesX + dust at par
}
```

Supporting code: `requestWithdraw` marker overwrite (`IdleCreditVault.sol`, `lastWithdrawRequest[_user] = currentEpoch`), single-slot loss-epoch lookup in `_claimLossAdjustedWithdrawRequest`, haircut storage in `collectWithdrawFunds`, and par payout in `_claimFundedWithdrawRequest` (`_transferFundedClaim(_user, amount)`).

Uncertainty note: I verified the claim-path and request-path logic shown above, but did not read `_transferFundedClaim`'s balance source or the exact `epochNumber` bump ordering inside `stopEpochWithDuration`; the finding assumes `lastWithdrawRequest` and `lossRecoveryPriceByEpoch` share the same epoch key (which the code comments indicate is the intended design). The PoC should confirm both on fork.
