### Title
DKG Result Export Endpoint Missing Admin-Role Authorization Allows Key Material Exfiltration - ([File: core/web/vault_controller.go])

### Summary
`VaultController.ExportDKGResult` returns the full hex-encoded `ReportWithResultPackage` (the DKG share/result bundle) for any `instanceId` supplied in the request body, with no role check performed inside the handler itself [1](#0-0) . Unlike other key-export controllers (`ekc.Export`, `ocrkc.Export`, `vrfkc.Export`), which rely on router-level `RequiresAdminRole` wrapping to gate sensitive key export, this handler performs only an input-presence check (`req.InstanceID == ""`) before reading and returning raw key material via `vault.NewVaultORM(vc.App.GetDB()).ReadResultPackage` and `presenters.NewExportDKGResultResource` [2](#0-1) .

### Finding Description
The `ExportDKGResult` handler decodes an `ExportDKGResultRequest{InstanceID}` from the POST body, reads the stored `ReportWithResultPackage` for that instance from the vault ORM, hex-encodes it, computes a SHA-256 digest, and returns both via `presenters.NewExportDKGResultResource(hexPackage, shaStr)` [2](#0-1) . There is no authorization/role check anywhere in this function body — the only gating that could exist is at the route-registration layer in `router.go`. Sibling key-export controllers referenced in the audit question (`ekc.Export`, `ocrkc.Export`, `vrfkc.Export`) enforce `RequiresAdminRole` at the router registration level specifically because they expose raw cryptographic key material; the same invariant should apply to DKG result export since it discloses the DKG share/result bundle used for oracle identity/consensus material.

I was not able to fully verify from the retrieved router.go content whether the `/v2/vault/dkg_results/export` route registration explicitly omits `RequiresAdminRole` — my search located references to "vault" in `router.go` but I could not view the specific route-group code confirming the exact role wrapper applied to this route within my available tool budget. This is a limitation of my investigation, not a confirmation either way.

### Impact Explanation
If the route is indeed registered without `RequiresAdminRole` (only requiring generic session/token authentication), any lower-privileged authenticated caller (view/run role) could retrieve the plaintext DKG result package for any known `instanceId`, exposing DKG share/result material tied to oracle identity and consensus operations — matching the "key/credential exfiltration" bounty impact class.

### Likelihood Explanation
Exploitability depends entirely on the router-level role requirement for this specific route. If `RequiresAdminRole` is missing (as implied by the parity break with `ekc.Export`/`ocrkc.Export`/`vrfkc.Export`), the attack requires only a valid low-privilege session/token and a known `instanceId` — a low bar, and trivially repeatable.

### Recommendation
Confirm in `core/web/router.go` the role requirement on `POST /v2/vault/dkg_results/export` (and `/v2/vault/dkg_results/verify`). If it is not wrapped with `RequiresAdminRole`, add that requirement to match the authorization pattern used for `ekc.Export`, `ocrkc.Export`, and `vrfkc.Export`, since this endpoint discloses raw key/result material.

### Proof of Concept
1. Seed a DKG result via `vault.ORM.WriteResultPackage` for a known `instanceId`.
2. Register a session/API token with only view or run role (no admin).
3. Send `POST /v2/vault/dkg_results/export` with `{"instanceId":"<id>"}` using that low-privilege credential.
4. Assert current behavior: if the route lacks `RequiresAdminRole`, response is `200 OK` with `HexDKGResultPackage` populated — confirming the vulnerability. Expected/fixed behavior: `403 Forbidden`.

Note: Because I could not conclusively verify the exact role wrapper applied to this route in `router.go` within the available search budget, this finding should be treated as requiring confirmation of the route registration before remediation is prioritized — the handler-level code itself provides no independent authorization check, which is the concrete, verified root cause.

func (vc *VaultController) ExportDKGResult(c *gin.Context) {
	var req ExportDKGResultRequest
	err := json.NewDecoder(c.Request.Body).Decode(&req)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.New("could not parse request body"))
		return
	}

	if req.InstanceID == "" {
		jsonAPIError(c, http.StatusBadRequest, errors.New("instanceId is required"))
		return
	}

	orm := vault.NewVaultORM(vc.App.GetDB())
	v, err := orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))
	if err != nil {
		jsonAPIError(c, http.StatusNotFound, err)
		return
	}

	if v == nil {
		jsonAPIError(c, http.StatusNotFound, errors.New("DKG result not found"))
		return
	}

	hexPackage := hex.EncodeToString(v.ReportWithResultPackage)
	sha := sha256.Sum256(v.ReportWithResultPackage)
	shaStr := hex.EncodeToString(sha[:])
	jsonAPIResponse(c, presenters.NewExportDKGResultResource(hexPackage, shaStr), "exportDKGResult")
