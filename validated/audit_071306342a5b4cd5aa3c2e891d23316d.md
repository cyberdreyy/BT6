### Title
Instant `updateMultiplier` failsafe lets an OPERATOR_ROLE holder bypass the timed corporate-action path and immediately re-scale every holder's UI balance - (File: crates/common/precompiles/src/b20_asset/logic/v2.rs)

### Summary
The B20 asset precompile exposes two multiplier setters: the scheduled `updateUIMultiplier(newMultiplier, effectiveAt)` — described as "the canonical corporate-action path (splits, reinvested dividends)" that requires a future `effectiveAt` — and an "instant failsafe" `updateMultiplier(newMultiplier)` that writes the multiplier *immediately*, with no timing restriction whatsoever, and silently cancels any live pending scheduled update. Both require only `OPERATOR_ROLE`. This mirrors the reported class of bug: a privileged, role-guarded setter that should only be adjustable through a controlled/delayed path can instead be triggered at any time by the same privileged role, stripping value/expectations from token holders who relied on the announced schedule.

### Finding Description
`AssetV2::update_multiplier` in `crates/common/precompiles/src/b20_asset/logic/v2.rs` (lines 725-768) requires only `ensure_operator_role`, performs a bounds check, and then unconditionally overwrites the live multiplier: [1](#0-0) 

Contrast this with the canonical scheduled path `update_ui_multiplier`, which enforces `effective_at > now`, rejects overlapping in-flight schedules, and is explicitly documented as the "canonical corporate-action path": [2](#0-1) 

The ABI-level doc comments make the intent explicit: `updateUIMultiplier` is "the canonical corporate-action path," while `updateMultiplier` is "Instant failsafe... Deprecated... the canonical setter is the scheduled `updateUIMultiplier`": [3](#0-2) 

Because `updateMultiplier` has no `onlyBefore*`-style timing gate (unlike the audited `SAM::setGoldenEggFee` fix which added `onlyBeforeSAMPhase`), the same `OPERATOR_ROLE` account that legitimately scheduled a future, transparent multiplier change via `updateUIMultiplier` can instead call the "failsafe" `updateMultiplier` at any moment to instantly overwrite the multiplier, silently discarding (cancelling) any pending scheduled update in the process: [4](#0-3) 

This gives the operator two paths to the same state, one gated by advance-notice/timelock semantics and one not — undermining the entire purpose of the scheduled mechanism, exactly as the original report describes an artist stripping a promised prize by using an ungated setter instead of the intended gated one.

### Impact Explanation
The multiplier directly determines every holder's UI-facing balance and total supply via `effective_multiplier`/`scaledBalanceOf`/`totalSupplyUI`. An operator can, without any notice period, instantly reduce the multiplier to the protocol minimum (any nonzero value up to `MAX_UI_MULTIPLIER`), immediately depressing every holder's displayed/scaled balance and total supply, or cancel a previously-announced favorable schedule (e.g., a dividend/split holders were expecting at a fixed future timestamp) and substitute an unfavorable value effective immediately. This is an unauthorized/unexpected value-stripping operation reachable by a single signed transaction from an already-provisioned `OPERATOR_ROLE` account — a role that, per the B20 model, is meant to only take scheduled, delayed corporate actions, not instantaneous ones. This qualifies as a concrete unauthorized operation causing loss of expected value for B20 asset-token holders.

### Likelihood Explanation
Any account holding `OPERATOR_ROLE` on a B20 asset token (a role routinely granted at token creation/administration) can call `updateMultiplier` at any time with no additional precondition beyond the role check and the multiplier bound check — no cooldown, no minimum notice, no restriction tied to a live pending schedule other than clearing it. This makes exploitation trivial and immediate for any operator-privileged account, differing from the scheduled function's built-in guardrails.

### Recommendation
Restrict `updateMultiplier`'s "instant failsafe" semantics so it cannot be used to bypass the advance-notice guarantee that `updateUIMultiplier` provides: e.g., disallow instant overwrite while a live pending schedule exists (require it to be cancelled first via a separately-gated path, or require the same minimum notice), or restrict the instant setter to a stricter role/governance path (multi-sig / timelock) distinct from the operator role that manages routine scheduled updates, so a single operator key cannot unilaterally undo/replace an announced multiplier change without notice.

### Proof of Concept
1. Operator (holding `OPERATOR_ROLE`) calls `updateUIMultiplier(newMultiplier=3×WAD, effectiveAt=T+30days)` — publicly announcing a future, favorable re-scaling (e.g., a stock split or dividend), as shown in `golden_update_ui_multiplier_schedules_pending` [5](#0-4) .
2. Holders make economic decisions expecting the scheduled multiplier to take effect at `T+30days`.
3. Before `T+30days`, the same operator calls `updateMultiplier(newMultiplier=0.5×WAD)`. This is accepted immediately (no timing check), instantly overwrites the current multiplier, and silently cancels the previously announced pending schedule, emitting `UIMultiplierUpdateCancelled` + `MultiplierUpdated`/`UIMultiplierUpdated`, as demonstrated in `update_multiplier_clears_live_pending_with_cancel_event` / `golden_update_multiplier_clears_live_pending_and_emits_cancellation` [6](#0-5) [7](#0-6) .
4. All holders' `scaledBalanceOf`/`totalSupplyUI` values instantly reflect the new, unfavorable multiplier with zero notice, stripping the value they were promised/expected from the previously scheduled corporate action.

        caller: Address,
        new_multiplier: U256,
        effective_at: U256,
        privileged: bool,

        let now = token.accounting().timestamp()?;
        self.ensure_operator_role(token, caller, privileged)?;
        if new_multiplier.is_zero() || new_multiplier > Self::MAX_UI_MULTIPLIER {
            return Err(BasePrecompileError::revert(IB20Asset::InvalidMultiplier {}));
        }
        if effective_at <= now {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtInPast {
                effectiveAt: effective_at,
            }));
        }
        if effective_at > U256::from(u64::MAX) {
            return Err(BasePrecompileError::revert(IB20Asset::EffectiveAtTooFar {
                effectiveAt: effective_at,
            }));

        // A live pending blocks a new schedule.
        if U256::from(pending_effective_at) > now {
            return Err(BasePrecompileError::revert(IB20Asset::UIMultiplierUpdateExists {
                effectiveAt: U256::from(pending_effective_at),
            }));
        }

#[test]
fn golden_update_multiplier_clears_live_pending_and_emits_cancellation() {
    let mut s = fresh();
    seed(&mut s, |t| give_role(t, operator_role(), ALICE));
    warp(&mut s, u(1));
    op(
        &mut s,
        ALICE,
        FakePolicyAccounting::new(),
        IB20Asset::updateUIMultiplierCall {
            newMultiplier: B20AssetStorage::WAD * u(3),
            effectiveAt: u(1_000),
        }
        .abi_encode(),
    )
    .unwrap();

    let out = op(
        &mut s,
        ALICE,
        FakePolicyAccounting::new(),
        IB20Asset::updateMultiplierCall { newMultiplier: B20AssetStorage::WAD * u(5) }.abi_encode(),
    )
    .unwrap();

    assert!(out.is_empty());
    read(&mut s, |t| {
        assert_eq!(t.multiplier().unwrap(), B20AssetStorage::WAD * u(5));
        assert_eq!(t.pending_multiplier().unwrap(), 0);
        assert_eq!(t.pending_effective_at().unwrap(), 0);
    });
    let events = s.get_events(TOKEN);
    assert_eq!(
        events[events.len() - 3],
        IB20Asset::UIMultiplierUpdateCancelled {
            cancelledMultiplier: B20AssetStorage::WAD * u(3),
            cancelledEffectiveAt: u(1_000),
        }
        .encode_log_data()
    );
    assert_eq!(
        events[events.len() - 2],
        IB20Asset::MultiplierUpdated { multiplier: B20AssetStorage::WAD * u(5) }.encode_log_data()
    );
    assert_eq!(
        events[events.len() - 1],
        IB20Asset::UIMultiplierUpdated {
            oldMultiplier: B20AssetStorage::WAD,
            newMultiplier: B20AssetStorage::WAD * u(5),
            effectiveAtTimestamp: u(1),
        }
        .encode_log_data()
    );
    assert_root("update_multiplier_clears_pending", s, ROOT_UPDATE_MULTIPLIER_CLEARS_PENDING);
}
