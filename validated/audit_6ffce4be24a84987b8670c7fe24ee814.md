### Title
Vote commission percentage misreported due to floor-division truncation instead of documented ceiling rounding - (File: vote/src/vote_state_view/field_frames.rs)

### Summary
The reported bug class ("lack of parameter precision" from integer percentage parameters) maps onto agave's basis-points-to-percentage conversion for vote account commission. The value returned to unprivileged RPC callers via `getVoteAccounts`/`RpcVoteAccountInfo.commission` is computed with a simple integer division that truncates fractional basis points, while the documented/expected conversion formula used elsewhere in the codebase explicitly rounds up (`div_ceil`).

### Finding Description
`CommissionView::commission_percent()` converts the raw `inflation_rewards_commission_bps` (u16, 0–10000) into the legacy `u8` percentage field by simple truncating division: [1](#0-0) 

```
pub(super) fn commission_percent(&self) -> u8 {
    if !self.frame.use_bps {
        self.buffer[0]
    } else {
        let data = unsafe { *(self.buffer.as_ptr() as *const [u8; 2]) };
        let bps = u16::from_le_bytes(data);
        let percent = (bps / 100).min(u8::MAX as u16);
        percent as u8
    }
}
```

This uses plain `bps / 100` (floor division). However, the RPC response type that surfaces this field to unprivileged JSON-RPC clients explicitly documents that the conversion should be **ceiling** division: [2](#0-1) 

```
/// An 8-bit unsigned integer used as a fraction (commission/100) for
/// rewards payout. Before SIMD-0291 activation, this is the native
/// commission value. After activation, this is derived from basis
/// points with: `bps.div_ceil(100).min(255)`.
```

Because the actual decoder implementation (`commission_percent`) truncates rather than rounds up as documented, any basis-points value that is not an exact multiple of 100 (e.g. 149 bps, which should report as 2% under `div_ceil`, or any of the huge space of non-round bps values now permitted by SIMD-0291/SIMD-0464, where `inflation_rewards_commission_bps` can be set to any `u16` via `set_inflation_rewards_commission_bps`) will be reported as a lower percentage than intended: [3](#0-2) 

This is reachable purely by reading vote account state — no privileged or validator-role action is required, since any RPC client can query vote accounts and any vote-account owner can set arbitrary basis-points commission values through the (now on-chain-supported) `VoteInitV2`/`set_inflation_rewards_commission_bps` mechanism referenced in the CLI: [4](#0-3) 

### Impact Explanation
This causes the JSON-RPC `getVoteAccounts` response (and any other consumer of `commission_percent`) to return incorrect account-derived data to callers — a "wrong data returned" condition affecting downstream systems (delegators, staking UIs, and monitoring tools) that decide where to stake based on the reported commission percentage. It does not directly compromise consensus (the underlying basis-points value used for actual reward math is unaffected), but it is a decoder misreporting bug in an unprivileged read path.

### Likelihood Explanation
Any vote account operator can set a non-round-hundred basis-points commission (e.g., via `--inflation-rewards-commission-bps` with an arbitrary value under 10000, or any value under SIMD-0291's unclamped storage), and any RPC client querying vote accounts will observe the truncated (lower) percentage instead of the documented ceiling-rounded value. This requires no special permissions and triggers on every read of the field for such an account.

### Recommendation
Change `commission_percent()` in `vote/src/vote_state_view/field_frames.rs` to use `bps.div_ceil(100).min(u8::MAX as u16)` to match the documented conversion semantics in `rpc-client-types/src/response.rs`, ensuring consistent, non-truncating percentage reporting across all consumers of vote account commission data.

### Proof of Concept
1. Set a vote account's `inflation_rewards_commission_bps` to a value like `149` (1.49%) using `set_inflation_rewards_commission_bps` (reachable via `VoteInitV2`/on-chain vote instructions per SIMD-0464/0291).
2. Query the account via `getVoteAccounts` RPC or any path that calls `CommissionView::commission_percent()`.
3. Observe the returned `commission` field is `1` (floor of 149/100) instead of `2`, the ceiling-rounded value documented in `RpcVoteAccountInfo.commission`'s doc comment, demonstrating the decoder misreports the account's actual commission rate to unprivileged callers.

**Note on completeness:** I was not able to fully trace every call site that consumes `commission_percent()` (e.g., confirming whether `rpc/src/rpc.rs` uses this exact function versus `VoteStateHandler::commission()`, whose rounding logic I could not fully verify within the available tool calls) or confirm whether `VoteStateHandler::commission()` uses `div_ceil` consistently. If a discrepancy does not in fact exist between the two implementations (i.e., if `VoteStateHandler::commission()` also floors), the severity would be reduced to "documentation vs. implementation mismatch" rather than a cross-component inconsistency; verifying this requires reading `programs/vote/src/vote_state/handler.rs`'s `commission()` implementation directly, which was not retrieved in full.
