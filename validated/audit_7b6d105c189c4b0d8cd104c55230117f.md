### Title
Unfunded pre-default instant-withdraw receipts bypass the recovery haircut and drain the default reserve at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The external bug is a validation-once-then-auto-follow flaw: the SSRF check runs on the submitted URL, then pycurl follows redirects to unvalidated destinations. The closest idle-tranches analog is in `IdleCreditVault.claimInstantWithdrawRequest`. An instant-withdraw receipt is validated and minted at request time (`requestInstantWithdraw`, lines 356-375), but after a borrower default the claim path applies the recovery haircut only to receipts recorded in `defaultRecoveryEpoch` via `_claimDefaultedInstantWithdrawRequest` (lines 842-856). Any instant receipt recorded in an *earlier* epoch that was never funded (`pendingInstantWithdraws` still covers it, `collectInstantWithdrawFunds` was never called) falls through to the blanket `_transferFundedClaim(_user, amount)` at lines 387-392 and is paid **at par** out of the same underlying reserve that backs haircutted defaulted-epoch claims — the "redirect" (the post-default claim hop) is never re-validated against funding status.

### Finding Description
- `requestInstantWithdraw` burns CDO strategy tokens and mints the user a receipt, incrementing `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `pendingInstantWithdraws` [1](#0-0) .
- Funding is a separate privileged hop: the manager calls `getInstantWithdrawFunds` after the deadline, which triggers `collectInstantWithdrawFunds`, pulling cash from the borrower and decrementing `pendingInstantWithdraws` [2](#0-1) . If the epoch defaults before this hop, the receipt stays unfunded.
- After `finalizeDefaultRecovery`, `claimInstantWithdrawRequest` first calls `_claimDefaultedInstantWithdrawRequest`, which clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and pays `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` [3](#0-2) . It then unconditionally pays the *entire remaining* `instantWithdrawsRequests[_user]` at par [4](#0-3) .
- Because an unfunded request made in epoch N-1 lives in `instantWithdrawsRequestsByEpoch[_user][N-1]`, it is never haircutted. The `pendingInstantWithdraws` bookkeeping in `_claimDefaultedInstantWithdrawRequest` (lines 850-852) even acknowledges that claims larger than the pending bucket correspond to already-funded reserve — but there is no per-user check that the older receipt was actually funded before paying it at par.

### Impact Explanation
The recovery reserve is sized during default finalization assuming all outstanding instant receipts are paid at `defaultRecoveryPrice`. An unprivileged lender holding an unfunded instant receipt from a pre-default epoch withdraws `1.0x` instead of `defaultRecoveryPrice/RECOVERY_FULL`, directly over-drawing the reserve. Every defaulted-epoch claimant (normal, APR0, instant) receives less than their pro-rata recovery, i.e. direct theft of unclaimed recovery proceeds quantified as `receiptAmount * (1 - defaultRecoveryPrice/RECOVERY_FULL)`. If the receipt is large relative to the reserve, late claimants' transfers can revert entirely — permanent freezing of their recovery.

### Likelihood Explanation
Requires only a KYC-passing tranche holder who requests an instant withdraw during a buffer period where `lastEpochApr > unscaledApr + instantWithdrawAprDelta` [5](#0-4) , and the epoch then defaults before `getInstantWithdrawFunds` runs. Borrower default is an honest, plausible event, and the attacker need only front-run the default (e.g., when the borrower visibly fails to repay). Instant withdrawals are disabled in programmable-borrower mode (`_isInstantWithdrawEnabled` gate), so this applies only to the standard fixed-APR variant. Uncertainty: if default finalization somehow swept `pendingInstantWithdraws` into the reserve funding amount before pricing, the theft reduces to a haircut-timing edge — the exact reserve accounting in `finalizeDefaultRecovery` was not fully traceable within available context and should be confirmed in the PoC.

### Recommendation
In `claimInstantWithdrawRequest`, after default finalization, do not pay the remaining `instantWithdrawsRequests[_user]` at par unless it was actually funded. Track funded instant receipts separately (e.g., a `fundedInstantWithdraws[_user]` bucket credited by `collectInstantWithdrawFunds` pro-rata, or record `pendingInstantWithdraws` per epoch at default time), and route any unfunded pre-default receipt through `defaultRecoveryPrice` exactly like defaulted-epoch receipts. Analogous to the SSRF fix: validate each redirect hop — apply the haircut check to every receipt epoch, not just `defaultRecoveryEpoch`.

### Proof of Concept
Fork test (Foundry, standard `IdleCDOEpochVariant`, non-programmable):

```solidity
// Setup: user deposits AA, epoch 0 runs, stopEpoch sets a low APR so that
// lastEpochApr > unscaledApr + instantWithdrawAprDelta in the buffer of epoch 1.
uint256 mintedAA = idleCDO.depositAA(100_000 * ONE_SCALE);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, lowApr, expectedFunds);   // APR drops -> instant enabled

// USER (unprivileged) requests instant withdraw in epoch N-1 (pre-default).
uint256 requested = cdoEpoch.requestWithdraw(mintedAA, address(AAtranche)); // instant path
assertGt(strategy.pendingInstantWithdraws(), 0);

// Manager NEVER calls getInstantWithdrawFunds -> receipt unfunded.
// Borrower defaults at next stopEpoch; recovery finalized at haircut price.
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager); cdoEpoch.stopEpoch(0, 0);          // transferFrom fails -> default
vm.prank(manager); strategy.finalizeDefaultRecovery(/* ... */);
uint256 recoveryPrice = strategy.defaultRecoveryPrice();
assertLt(recoveryPrice, RECOVERY_FULL);

// USER claims: _claimDefaultedInstantWithdrawRequest only clears
// instantWithdrawsRequestsByEpoch[user][defaultEpoch] (== 0 for this user),
// then pays full instantWithdrawsRequests at par from the recovery reserve.
uint256 balPre = underlying.balanceOf(user);
vm.prank(user); cdoEpoch.claimInstantWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;

// Invariant broken: unfunded receipt paid at 1.0x while defaulted receipts
// get recoveryPrice < 1.0x from the same reserve.
assertApproxEqAbs(paid, requested, 2);            // par payout
assertLt(paid, requested);                        // expected: requested * recoveryPrice / RECOVERY_FULL
// Follow-on: a defaulted-epoch claimant now reverts or receives less
// because the reserve was over-drawn by (1 - recoveryPrice) * requested.
```

Key lines: request `IdleCreditVault.sol:356-375`, unconditional par payout `IdleCreditVault.sol:387-392`, epoch-scoped haircut `IdleCreditVault.sol:843-855`.
