### Title
Stale rejection weight is never retracted when a signer switches its vote to Accept for the same block, breaking the miner's aggregated-weight tally — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The Venus report's bug class is a value snapshotted at decision time (`borrowBalance`) becoming stale by execution time, so a downstream equality check (`repayAmount > maxClose`) fails even though the underlying position is still valid, reverting a legitimate action. The direct analog here is the miner-side signer-response tally in `StackerDBListener::poll_events` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`): once a signer's `Rejected` message is counted into `total_weight_rejected` for a given `signer_signature_hash`, that weight is never removed if the same signer later legitimately switches to `Accepted` for the identical block. The two vote types are tracked with two independent membership sets (`gathered_signatures` for accepts, `responded_signers` for rejects) instead of one "current vote per signer" state, so a vote-switch adds weight to the new side without subtracting it from the old one.

### Finding Description
For `BlockResponse::Accepted`, the weight-add is gated only on `!block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

For `BlockResponse::Rejected`, the weight-add is gated on `block.responded_signers.insert(slot_id)`: [2](#0-1) 

Note that the `Accepted` branch unconditionally does `block.responded_signers.insert(slot_id)` at the end (so `responded_signers` and `gathered_signatures` are two different, imperfectly-synchronized notions of "has this signer already voted"): [3](#0-2) 

Sequence that triggers the divergence:
1. Signer S sends `Rejected` for block B (`signer_signature_hash = H`) with a transient/re-evaluable reason (e.g. `NoSignerConsensus`, `ConnectivityIssues`, `UnknownParent`/`NotFoundError` while waiting on the parent block). `responded_signers.insert(slot_id)` succeeds, `total_weight_rejected += S.weight`.
2. The condition resolves (e.g. the node catches up on the parent, or global signer consensus is found). The signer-side logic explicitly allows the SAME block hash to be reconsidered — this is deliberate, and the reject reasons above are exactly the ones marked reevaluable: [4](#0-3) 
3. On re-proposal of block B, signer S now validates it successfully and sends `Accepted` for the same `H`. Because `gathered_signatures` was never touched by step 1, the check `!block.gathered_signatures.contains_key(&slot_id)` is true, so `total_weight_approved += S.weight` — while `total_weight_rejected` still contains S's earlier vote with no subtraction anywhere in the codebase (no code path decrements `total_weight_rejected` on a later accept, or vice versa).

The result: `block.total_weight_approved + block.total_weight_rejected` can now exceed `self.total_weight`, and specifically `total_weight_rejected` reflects at least one *retracted* vote. This tally is consumed directly by `SignCoordinator::wait_for_signer_signatures_or_timeout` to decide whether to declare the block dead or accepted: [5](#0-4) 

This breaks the "aggregated-weight vs verified-accepts" equality: the miner's rejection tally no longer reflects each signer's *current* disposition, only the union of every disposition it has ever held for that block hash.

### Impact Explanation
This is a liveness wedge / miner-vs-signer-set divergence, not merely a logging cosmetic issue, because the miner's local tally (this file) and the signer set's own convergence mechanism are two independent bookkeeping systems. The signer-to-signer consensus in `stacks-signer/src/v0/signer.rs` (`store_and_process_block_rejection`, `store_and_process_block_signature`) tracks rejections/signatures per address via dedicated SignerDB tables that are re-queried fresh each time (`get_block_rejection_signer_addrs`, `get_block_signatures`), so it does not have this bug — a signer's later acceptance is what actually gets stored and counted there. But the miner only sees the flawed local tally in `stackerdb_listener.rs`/`signer_coordinator.rs`. Consequences:
- The miner can conclude `total_weight_rejected` crossed the >30%-blocking-minority threshold (using stale, retracted rejection weight) and abandon/re-mine a *different* block at the same height, while the true signer set — using its own correct, retraction-aware counting — may still converge on and sign the *original* block B, producing two competing blocks at the same height (a conflicting-block/equivocation-adjacent scenario), or at minimum forcing needless re-mining even though the position (signer consensus) genuinely supports B, i.e., a spurious liveness stall exactly mirroring the Venus DoS pattern (a legitimate operation reverted/abandoned because a stale intermediate snapshot was never refreshed).
- Conversely, `percent_approved`/`percent_rejected` metrics used for operator-facing decisions become >100%-inconsistent, masking the real signer state.

### Likelihood Explanation
No majority collusion or malicious key is required — the trigger is a *single* signer legitimately reconsidering a re-evaluable rejection reason (a normal, expected occurrence: transient connectivity issues, waiting on `UnknownParent`, or a global-state-consensus hiccup are exactly the class of reasons the codebase itself designates as reevaluable). This can happen purely from ordinary network/timing jitter (a one-slot miner's proposal arriving before the parent is processed by some signers, or a signer briefly losing global-state consensus), i.e., "a one-slot miner plus gossip" is sufficient, matching the scope requirement.

### Recommendation
Track a single "current vote" per `slot_id` per block (e.g., an enum `Accepted(weight)`/`Rejected(weight)` keyed by `slot_id`) instead of two independently-gated sets. When a new message for a slot supersedes a previous one, subtract the previous vote's weight from its bucket before adding the new vote's weight to the other bucket, so `total_weight_approved + total_weight_rejected` always equals the sum of weights of signers who have *currently* responded, never double-counting a retracted vote.

### Proof of Concept
1. Configure a 2+ signer set where signer `S1` has weight ≥30% (blocking-minority weight) and signer `S2` has weight ≥70% (accept-threshold weight, or split with more signers to reach exactly threshold behavior).
2. Cause `S1` to initially reject a proposed block `B` (hash `H`) with a transient, re-evaluable reason — e.g. delay `S1`'s stacks-node in processing `B`'s parent block so `S1` returns `ValidationFailed(UnknownParent)`/`NotFoundError` (both listed as reevaluable in `should_reevaluate_reject_reason`). The miner's `stackerdb_listener.rs` records `total_weight_rejected += S1.weight`.
3. Let `S1`'s node catch up; the miner re-sends/`S1` re-evaluates the same proposal `B` (same `H`) and now legitimately sends `Accepted`. `stackerdb_listener.rs`'s `Accepted` handler checks only `gathered_signatures`, which has no entry for `S1`'s slot, so it adds `total_weight_approved += S1.weight` without ever decrementing `total_weight_rejected`.
4. Observe (via the `info!` logs at lines 448-462/548-564, or by inspecting `BlockStatus`) that `block.total_weight_rejected` still includes `S1`'s weight even though `S1` has since accepted `B`, and that `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`.
5. With a second signer `S2` independently rejecting `B` for an unrelated but sufficient amount of weight, `total_weight_rejected` (inflated by `S1`'s stale vote) crosses the `>30%` blocking-minority check in `signer_coordinator.rs` (lines 509-513) and the miner treats `B` as dead/re-mines, even though the true, current signer disposition (per SignerDB, used by `stacks-signer/src/v0/signer.rs`) may not actually block `B`.

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
