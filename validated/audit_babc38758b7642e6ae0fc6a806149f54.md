### Title
Callback deserialization panic in `on_get_account_total_balance` permanently sticks `staking_information.status` at `Busy` - ([File: lockup/src/owner_callbacks.rs])

### Summary
`refresh_staking_pool_balance` sets `staking_information.status = Busy` in one receipt and relies on the follow-up callback `on_get_account_total_balance` to flip it back to `Idle`. That callback takes `#[callback] total_balance: WrappedBalance`, whose deserialization is performed by SDK-generated wrapper code that runs *before* the function body (and thus before `set_staking_pool_status(Idle)`) executes. A pool that returns a value that cannot be deserialized into `WrappedBalance` causes the callback receipt to panic entirely, so `Idle` is never written, and `status` is left at `Busy` forever.

### Finding Description
Binding claimed: `staking_information.status == TransactionStatus::Idle` once the promise chain of any owner-initiated pool operation (here `refresh_staking_pool_balance`) has fully resolved, success or failure.

Code path:
- `refresh_staking_pool_balance` (`lockup/src/owner.rs`, lines 176-209) calls `self.set_staking_pool_status(TransactionStatus::Busy)` and schedules `ext_staking_pool::get_account_total_balance(...)`, chained via `.then(ext_self_owner::on_get_account_total_balance(...))`.
- `on_get_account_total_balance` (`lockup/src/owner_callbacks.rs`, lines 281-294) is declared with `#[callback] total_balance: WrappedBalance`. Under the near-sdk version in use, the `#[callback]` parameter is deserialized (serde/Borsh, `.expect(...)`) by macro-generated code that executes *prior* to the annotated function body — i.e. before `assert_self()` and before `self.set_staking_pool_status(TransactionStatus::Idle)` at line 283 run.
- If the pool returns a payload that fails to deserialize as `WrappedBalance`, that deserialization panics, aborting the entire callback receipt. The write of `Busy` performed by the *prior* receipt (`refresh_staking_pool_balance`) has already been committed to state and is not rolled back by the failing callback receipt.
- `set_staking_pool_status(TransactionStatus::Idle)` (`lockup/src/internal.rs`, lines 16-21) is therefore never reached, and no other method in the contract can reset `staking_information.status` outside of the same broken callback chain (`unselect_staking_pool` itself requires `assert_staking_pool_is_idle()` first — `lockup/src/owner.rs` lines 49-51).
- `assert_no_staking_or_idle` (`lockup/src/internal.rs`, lines 79-88) and `assert_staking_pool_is_idle` (lines 90-101) both then permanently panic with "Contract is currently busy with another operation," blocking `transfer`, `add_full_access_key`, and every other staking-pool owner method (`deposit_to_staking_pool`, `deposit_and_stake`, `withdraw_from_staking_pool`, `withdraw_all_from_staking_pool`, `stake`, `unstake`, `unstake_all`, `unselect_staking_pool`).

Existing guards (`assert_owner`, `assert_self()`, `is_promise_success()`) do not prevent this: `assert_self()` and `is_promise_success()` only run inside the callback body, which is never reached because the panic happens in the SDK-generated deserialization step that precedes the body. Note the other callbacks that gate the same `Busy` flag (`on_staking_pool_deposit`, `_stake`, `_withdraw`, `_unstake`, `_unstake_all`) only use `is_promise_success()` and do not deserialize a typed value from the pool, so they are not affected — this specific issue is isolated to `on_get_account_total_balance`, which is the one handler that deserializes an actual pool-supplied value (`WrappedBalance`) via `#[callback]`.

### Impact Explanation
If triggered, the lockup's `staking_information.status` is permanently stuck at `Busy`. This blocks `transfer()` and `add_full_access_key()` (both gated by `assert_no_staking_or_idle`), and every other owner staking method gated by `assert_staking_pool_is_idle`, with no code path to reset the flag. This freezes the owner's liquid and locked NEAR balance in the lockup contract indefinitely — matching the Critical category "funds permanently frozen."

### Likelihood Explanation
The mechanism itself (SDK deserializing `#[callback]` args before the annotated function body runs) is real and directly exploitable by any pool contract that is the counterparty of `refresh_staking_pool_balance`. However, reaching this state requires the lockup owner to have already selected the malicious pool via `select_staking_pool`, which itself requires the pool to pass `ext_whitelist::is_whitelisted` (`lockup/src/owner_callbacks.rs` lines 7-25, `lockup/src/owner.rs` lines 12-41). I was unable to fully confirm within the available tool budget whether the whitelist contract (`whitelist/src/lib.rs`) permits open/self-registration (e.g., automatically whitelisting any pool deployed through `staking-pool-factory`) or is restricted to foundation-curated entries. If whitelisting is foundation-gated and not attacker-reachable, this reduces to a self-inflicted foot-gun by an owner who deliberately delegates to an untrusted-but-whitelisted pool, rather than a purely attacker-driven exploit. This precondition should be verified before treating the finding as fully attacker-controlled.

### Recommendation
- Avoid relying on `#[callback]`-typed deserialization for pool-controlled values where a deserialization failure can abort the callback before state can be repaired. Prefer `#[callback_result]`/`Result<..., PromiseError>` style handling (if the SDK version supports it) so the callback body always executes and can catch and handle a bad/malformed return value.
- Alternatively, wrap the state transition (`set_staking_pool_status(Idle)`) so it happens deterministically regardless of the deserialization outcome, e.g. by not typing the parameter and manually attempting/catching deserialization inside the function body instead of relying on the macro-generated pre-body deserialization.
- Add an owner/foundation "force unlock" escape hatch that can reset `staking_information.status` to `Idle` without depending on the original callback completing successfully, guarded by appropriate checks (e.g. only allowed once, or after some ping/verification with the pool).
