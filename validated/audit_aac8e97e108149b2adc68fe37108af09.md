**What the rekt.news report describes**: The Origin Protocol hack combined a flash loan with a fake/malicious ERC20 token that re-entered the protocol during a token transfer callback, exploiting the fact that the protocol trusted an attacker-controlled token's `transfer`/`transferFrom` behavior mid-flow to manipulate internal accounting before it settled.

**What I checked in this codebase** for an analogous pattern (arbitrary/fake token + reentrancy across a public entry point that mints/burns shares or moves funds):

- `ProvisionerV2.deposit`/`mint`/`refundDeposit`/`cancelRequest`/`refundRequest` all operate on a `TokenDetailsV2 storage tokenDetails = tokensDetails[token]` gate via `_requireSyncDepositsEnabled` or `tokenDetails.asyncDepositEnabled/asyncRedeemEnabled` checks, meaning only admin-registered tokens can flow through these paths — an attacker can't substitute an arbitrary malicious ERC20 as the `token` parameter and have it accepted by the accounting logic. [1](#0-0) [2](#0-1) 

- `solveRequestsDirect` and `cancelRequest`/`refundRequest` are guarded with `nonReentrant` (transient reentrancy guard), and `MultiDepositorVault.enter`/`exit` are restricted to `onlyProvisioner`, so a malicious token can't re-enter the vault's mint/burn logic through a transfer hook to double-count units. [3](#0-2) [4](#0-3) 

- Price/quote binding goes through `PriceAndFeeCalculatorV2` → `OracleRegistry.getQuoteForUser`, which resolves oracles per registered `(base, quote)` pair and per-vault overrides, not per-token contract behavior at call time — there's no path where an attacker-supplied token contract's return value or callback directly perturbs the numeraire conversion. [5](#0-4) [6](#0-5)
