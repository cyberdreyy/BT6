### Title
Epoch yield keeps accruing to burned `address(1)` tranche shares after all real depositors of a tranche class exit, permanently locking the class's yield share - ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
`IdleCDOTranche.mint` permanently mints `MIN_LIQUIDITY = 10**3` shares to `address(1)` on the first deposit of each tranche class. Those dead shares keep a non-zero `totalSupply` and a non-zero `lastNAV` forever. In `IdleCDOCreditVault._virtualPriceAux`, epoch gains are split by `trancheAPRSplitRatio` across *saved NAV classes*, not by active depositors, so a tranche class whose only remaining holder is `address(1)` still receives its full split share of every epoch's interest. That yield accrues to shares that can never be redeemed, permanently locking funds in the CDO. This is the same bug class as the WrappedVault report: rewards attributed to dead shares during a period with no active depositors are locked, and there is no `ownerClaim` escape hatch.

### Finding Description
On the first mint of each tranche, `IdleCDOTranche` mints 1000 shares to `address(1)` and subtracts them from the user's amount: [1](#0-0) 

When all real AA (or BB) holders exit via `requestWithdraw`/claim, `_withdrawOps` burns only `msg.sender`'s shares and decrements `lastNAV` by their underlyings; the dead 1000 shares and their NAV dust remain: [2](#0-1) 

On subsequent `stopEpoch` → `_updateAccounting` → `_virtualPriceAux`, the emptied class passes both guards: `trancheSupply != 0` (dead shares) and `lastNAV != 0` (dust + any leftover). Since `_lastNAV != _lastTrancheNAV` and `totalGain > 0`, the class is credited `totalGain * split / FULL_ALLOC` even though it has zero active depositors: [3](#0-2) 

Worse, with Adaptive Yield Split active, `_updateSplitRatio` enforces `minAprSplitAYS` (floor `AA_RATIO_LIM_DOWN = 50000`, set at initialize), so even an AA class with ~0 TVL is entitled to at least 50% of the yield split ratio regardless of actual TVL: [4](#0-3) [5](#0-4) 

The credited `lastNAVAA`/`lastNAVBB` grows each epoch, but `getContractValue` counts the underlying strategy tokens, so the NAV attributed to `address(1)` is backed by real funds that no key holder can ever withdraw — the tranche tokens at `address(1)` are unspendable. Unlike the report's recommendation, there is no mechanism for owner/feeReceiver to sweep yield attributed to dead shares; `_skimDonatedAssets` only removes *unsolicited* donations not tracked in NAV, so it cannot rescue this locked yield.

### Impact Explanation
Permanent freezing of yield. Every epoch that runs after one tranche class has been fully exited by real users routes that class's split share of `expectedEpochInterest` into NAV owned solely by `address(1)`. With AYS's 50% floor, an AA-empty vault loses roughly half of every epoch's interest to dead shares; over multiple epochs this compounds. The loss equals `tranche share of net epoch interest` per epoch — unbounded in aggregate and irrecoverable because no claim/sweep function exists for `address(1)`-attributed NAV.

### Likelihood Explanation
Requires all holders of one tranche class to fully exit — normal in a credit vault lifecycle (lenders redeem after epochs, or a class is deliberately left empty since `depositBB` is gated by `isBBDepositEnabled`). No attacker action is needed; an unprivileged user simply being the last to withdraw triggers it, and every subsequent `startEpoch`/`stopEpoch` cycle locks more yield. The guards that look like protections (`trancheSupply == 0` and `lastTrancheNAV == 0` early returns in `_virtualPriceAux`) are specifically defeated by the `address(1)` MIN_LIQUIDITY seed, which keeps both non-zero forever.

### Recommendation
Mirror the fix direction suggested in the report:
- Treat economically-empty classes as empty: in `_virtualPriceAux`, skip gain attribution when the class's claimable supply is only the `MIN_LIQUIDITY` dead shares (e.g., `trancheSupply <= MIN_LIQUIDITY`), routing 100% of gain to the populated class.
- Alternatively/additionally, add a privileged `ownerClaim`-style sweep that mints/withdraws the NAV attributable to `address(1)` dead shares, so yield accrued during zero-active-depositor periods can be refunded instead of locked.
- When AYS computes `tvlAARatio` for `_updateSplitRatio`, subtract dead-share NAV so an empty class does not retain the 50% floor entitlement.

### Proof of Concept
Foundry fork PoC (against `IdleCDOEpochVariant` + `IdleCreditVault` test harness in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testYieldLockedToDeadShares() external {
    // 1. Alice deposits AA only (BB never enabled/deposited is equivalent
    //    because BB dead shares also accrue if BB had history).
    uint256 amt = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amt); // mints 1000 dead shares to address(1) + shares to us

    // 2. Epoch 1 runs and stops normally (yield split fine while AA populated).
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // 3. Alice requests and claims a full AA withdraw during buffer.
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(2, initialProvidedApr, _expectedFundsEndEpoch());
    cdoEpoch.claimWithdrawRequest(address(AAtranche));
    // AA totalSupply == 1000 (all held by address(1)); lastNAVAA == dust > 0.
    assertEq(IERC20(AAtranche).totalSupply(), 10**3);
    assertGt(cdoEpoch.lastNAVAA(), 0);

    // 4. Keep a BB depositor active so epochs keep producing interest.
    //    Run another epoch; borrower repays principal + interest.
    uint256 navAA_before = cdoEpoch.lastNAVAA();
    uint256 interest = cdoEpoch.expectedEpochInterest();
    _startEpochAndCheckPrices(2);
    _stopEpochAndCheckPrices(3, initialProvidedApr, _expectedFundsEndEpoch());

    // 5. AA's split share of epoch interest accrued entirely to address(1):
    uint256 navAA_after = cdoEpoch.lastNAVAA();
    assertGt(navAA_after, navAA_before); // dead-share NAV grew
    // Those underlyings sit in the strategy/CDO backing shares no one can burn:
    // funds permanently locked ≈ AAShare * net epoch interest (>= ~50% with AYS floor).
}
```

Key assertions: after step 3 `AAtranche.totalSupply() == MIN_LIQUIDITY` yet `lastNAVAA > 0`; after step 5 `lastNAVAA` increases by approximately the AA split share of the epoch's net interest, and that value is unreachable since `address(1)` cannot call `requestWithdraw`/`burn`. The existing `_skimDonatedAssets`, `Default` revert, and `trancheSupply == 0` guards do not prevent it.
