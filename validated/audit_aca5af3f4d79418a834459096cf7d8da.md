### Title
UserController.Create omits audit.Audit(...) logging for admin user creation, hindering detection of privilege escalation - ([File: core/web/user_controller.go])

### Summary
`UserController.Create` (core/web/user_controller.go, lines 52-106) creates a new API user, including with `role=admin`, but never calls `u.App.GetAuditLogger().Audit(...)`, unlike `UpdatePassword`, `NewAPIToken`, and `DeleteAPIToken` which emit audit events on both success and failure paths. This is a logging-completeness gap: if any role-wiring defect allowed a lower-privileged actor to reach this endpoint, the resulting admin account creation would leave no audit trail.

### Finding Description
`Create` binds a `newUserRequest{Email, Password, Role}`, validates the role via `clsession.GetUserRole`, validates email/password complexity, constructs the user via `clsession.NewUser`, and persists it via `u.App.AuthenticationProvider().CreateUser(ctx, &user)` [1](#0-0) . No `audit.Audit(...)` call exists anywhere in this function, on either the success path (line 105, `jsonAPIResponse`) or the duplicate-key/error paths. By contrast, `UpdatePassword` audits both `audit.PasswordResetAttemptFailedMismatch` and `audit.PasswordResetSuccess` [2](#0-1) , `NewAPIToken` audits `audit.APITokenCreateAttemptPasswordMismatch` and `audit.APITokenCreated` [3](#0-2) , and `DeleteAPIToken` audits `audit.APITokenDeleteAttemptPasswordMismatch` and `audit.APITokenDeleted` [4](#0-3) . Notably, `UpdateRole` and `Delete` also lack audit calls in this file, but the question scopes only `Create`.

I was unable to locate and confirm the actual route wiring/role-gating for `/v2/users` POST within the indexed portion of the codebase — `UserController` is only referenced in `core/web/user_controller.go`, `core/web/user_controller_test.go`, and a single (non-conclusive) match in `core/web/router.go`, and the file registering `v2Routes`/admin-only route groups was not retrievable via the available search tools. This means **Q1 (the wiring bypass allowing a non-admin to reach `Create`)** could not be independently verified in this session — the question's premise (a hypothetical wiring defect) is explicitly a precondition, not something demonstrated here.

### Impact Explanation
Standing alone, the missing audit log is a logging-completeness defect, not itself an authorization bypass — `AUTHORIZATION_EXACTNESS` is not violated by this code path in isolation. The security-relevant chain is: (1) an authorization/wiring bypass (Q1) allows a non-admin caller to reach `Create` and successfully create a role=admin account, and (2) because `Create` performs no audit logging, that privilege-escalation event is invisible in the audit trail relied upon for detection/forensics — unlike every other sensitive mutation on `UserController` (password reset, token creation/deletion). This compounds impact only when combined with an actual authorization bypass, which is outside this function and unverified here.

### Likelihood Explanation
The audit-logging gap itself is 100% reproducible (call `Create` as a legitimate admin and observe no audit entry is emitted). However, exploitability as "undetected privilege escalation" is entirely conditional on the unverified Q1 wiring defect existing; without confirming that a lower-privileged actor can actually invoke `Create`, this is a hardening/defense-in-depth gap rather than a standalone confirmed vulnerability.

### Recommendation
Add `u.App.GetAuditLogger().Audit(...)` calls in `UserController.Create`: emit a `UserCreated`-style audit event (with fields such as target email and assigned role) on successful creation, mirroring the pattern in `UpdatePassword`/`NewAPIToken`/`DeleteAPIToken`. Also consider adding equivalent audit events to `UpdateRole` and `Delete`, which share the same gap, to ensure all user/role management operations are auditable regardless of how they are reached.

### Proof of Concept
Go unit test (handler-level, following the existing pattern in `core/web/user_controller_test.go`):
1. Set up a test app with a mock/fake `audit.AuditLogger` (as used elsewhere in the test suite for `UpdatePassword`/`NewAPIToken` tests).
2. POST `/v2/users` with `{"email":"attacker@example.com","password":"<complex>","role":"admin"}` as an authenticated admin session (baseline, since the wiring bypass is unverified).
3. Assert HTTP 200 and that the user is created via `AuthenticationProvider().CreateUser`.
4. Assert `auditLogger.Audit(...)` was called with a `UserCreated` (or equivalent) event type and metadata including the created email/role — this assertion currently **fails** because `Create` never calls `Audit`.
5. Compare against a parallel test on `UpdatePassword`/`NewAPIToken`, where the equivalent assertion **passes**, demonstrating the inconsistency.

func (u *UserController) Create(c *gin.Context) {
	ctx := c.Request.Context()
	type newUserRequest struct {
		Email    string `json:"email"`
		Password string `json:"password"`
		Role     string `json:"role"`
	}

	var request newUserRequest
	if err := c.ShouldBindJSON(&request); err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	userRole, err := clsession.GetUserRole(request.Role)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, err)
		return
	}

	if verr := clsession.ValidateEmail(request.Email); verr != nil {
		jsonAPIError(c, http.StatusBadRequest, verr)
		return
	}

	if verr := utils.VerifyPasswordComplexity(request.Password, request.Email); verr != nil {
		jsonAPIError(c, http.StatusBadRequest, verr)
		return
	}

	user, err := clsession.NewUser(request.Email, request.Password, userRole)
	if err != nil {
		jsonAPIError(c, http.StatusBadRequest, errors.Errorf("error creating API user: %s", err))
		return
	}
	if err = u.App.AuthenticationProvider().CreateUser(ctx, &user); err != nil {
		// If this is a duplicate key error (code 23505), return a nicer error message
		var pgErr *pgconn.PgError
		if ok := errors.As(err, &pgErr); ok {
			if pgErr.Code == "23505" {
				jsonAPIError(c, http.StatusBadRequest, errors.Errorf("user with email %s already exists", request.Email))
				return
			}
		}
		if errors.Is(err, clsession.ErrNotSupported) {
			jsonAPIError(c, http.StatusBadRequest, errUnsupportedForAuth)
			return
		}
		u.App.GetLogger().Errorw("Error creating new API user", "err", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("error creating API user"))
		return
	}

	jsonAPIResponse(c, presenters.NewUserResource(user), "user")
