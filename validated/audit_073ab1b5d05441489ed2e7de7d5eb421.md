### Title
Lockup Factory lets the unprivileged caller substitute an arbitrary "whitelist" contract into the deployed lockup, bypassing the staking-pool safety check - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` accepts a caller-supplied `whitelist_account_id: Option<ValidAccountId>` that, if present, is baked into the newly deployed lockup contract as `staking_pool_whitelist_account_id`, completely bypassing the factory's own trusted default (`self.whitelist_account_id`) set at `new()`. There is no validation that the supplied account is actually the official NEAR Foundation whitelist contract, nor any restriction on who may set it.

### Finding Description
`LockupFactory::new` stores one trusted `whitelist_account_id` at initialization [1](#0-0) . However, `create()` lets any caller override this trusted value per-lockup via the `whitelist_account_id` parameter:

```
let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
    account_id.into()
} else {
    self.whitelist_account_id.clone()
};
``` [2](#0-1) 

This value is passed straight into the deployed lockup contract's `new()` call as `staking_pool_whitelist_account_id`, with no equality/authorization check against the factory's own configured whitelist [3](#0-2) .

Inside the lockup contract, that stored account ID is the sole source of truth used to gate which staking pool the owner is allowed to delegate to: `select_staking_pool` calls `ext_whitelist::is_whitelisted` against `self.staking_pool_whitelist_account_id` and only accepts the pool if it returns `true` [4](#0-3) ; the callback then unconditionally trusts that result and stores the staking pool as the delegation target [5](#0-4) . From there `deposit_and_stake` will move real NEAR balance out of the lockup account to whatever pool was accepted [6](#0-5) .

The `create()` test suite even documents this as an intentional "custom whitelist" feature [7](#0-6) , but nothing in the code enforces that a custom whitelist is itself the legitimate, foundation-controlled `WhitelistContract` (`whitelist/src/lib.rs`) rather than an attacker-deployed contract whose `is_whitelisted` always returns `true`.

The binding this breaks: for every deployed lockup, `lockup.staking_pool_whitelist_account_id` should equal the single foundation-audited whitelist account that the whole system (whitelist/README.md's threat model) relies on to guarantee "delegated tokens can not be lost or locked." The factory instead lets the deploying/funding caller (an unprivileged party, since anyone can call `create` and pay the deposit) set this field to any account of their choosing.

### Impact Explanation
An attacker can call `create()` (funding the deposit themselves, or having it paid by someone else) specifying a victim as `owner_account_id` and a self-controlled contract as `whitelist_account_id` that always answers `is_whitelisted -> true`. The resulting lockup silently loses the protection the whitelist is supposed to provide: any staking pool the owner (or anyone able to trigger `select_staking_pool`, subject to `assert_owner`) selects will be accepted as "whitelisted," even a malicious pool that never returns staked NEAR. Since `deposit_and_stake`/`stake` then move the lockup's real NEAR balance to that pool [6](#0-5) , this can lead to permanent loss of the lockup's funds — the core guarantee described in `whitelist/README.md` ("the lockup contract should be able to recover delegated tokens back... In order to enforce this, only approved accounts...can receive delegated tokens") is defeated for any lockup created this way.

### Likelihood Explanation
`create()` is a permissionless, `#[payable]` method callable by anyone [8](#0-7) , and the `whitelist_account_id` override requires no special privilege or foundation approval — it is a plain optional argument. No additional trust assumption beyond "attacker can call the factory and pay the minimum deposit" is needed.

### Recommendation
Remove the caller-suppliable `whitelist_account_id` override in `create()`, or if flexibility is required, restrict it to a foundation-controlled/`assert`-checked allow-list, ensuring every deployed lockup's `staking_pool_whitelist_account_id` is always the officially configured whitelist stored in `self.whitelist_account_id`.

### Proof of Concept
1. Attacker deploys a malicious contract `fake-whitelist` implementing `is_whitelisted(...) -> true` unconditionally.
2. Attacker calls `lockup_factory.create({owner_account_id: "victim", lockup_duration, ..., whitelist_account_id: "fake-whitelist"})` with the minimum attached deposit, per [9](#0-8) .
3. The deployed lockup for `victim` now has `staking_pool_whitelist_account_id = "fake-whitelist"`.
4. When `victim` (owner) later calls `select_staking_pool("attacker-pool")`, the check against `fake-whitelist` returns `true` regardless of the pool's legitimacy [10](#0-9) , and `on_whitelist_is_whitelisted` accepts it [5](#0-4) .
5. `deposit_and_stake` moves lockup NEAR to `attacker-pool`, which never returns it — funds are lost.

    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,

        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()

    pub fn on_whitelist_is_whitelisted(
        &mut self,
        #[callback] is_whitelisted: bool,

    ) -> bool {
        assert_self();

        self.staking_information = Some(StakingInformation {

            status: TransactionStatus::Idle,
            deposit_amount: 0.into(),
