## Analysis

The Predy report describes admin-updatable interest rate parameters (`irmParams`) being written directly to storage without first "closing out" the interest accrual for the period since the last update (`applyInterestForToken`). This causes the *new* rate to be incorrectly retroactively applied to the *elapsed* time window, over/under-charging interest and mis-crediting protocol fees.

marginfi-v2 has the exact same structural pattern: `Bank::accrue_interest` computes interest owed for `time_delta = current_timestamp - self.last_update` using the *current* `bank.config.interest_rate_config`, and only some instructions call `accrue_interest` before mutating state (e.g. `lending_pool_emissions_deposit` explicitly calls `bank.accrue_interest(...)` before changing share values), but the admin instructions that mutate `interest_rate_config` itself do not.

Specifically:
- `lending_pool_configure_bank` (full config update) calls `bank.configure(&bank_config)`, which directly overwrites `self.config.interest_rate_config` via `InterestRateConfigImpl::update`, with no preceding `accrue_interest` call. [1](#0-0) [2](#0-1) 

- `lending_pool_configure_bank_interest_only` (the scoped `delegate_curve_admin` path) does the same thing even more directly — it writes `interest_rate_config` in-place with zero accrual step beforehand. [3](#0-2) 

- `Bank::accrue_interest` builds the `InterestRateCalc` from `self.config.interest_rate_config` (the *current* value at accrual time) and applies it across the entire `time_delta` since `last_update`, exactly the retroactive-application pattern the Predy report flags. [4](#0-3) 

- Contrast this with `lending_pool_emissions_deposit`, which correctly calls `bank.accrue_interest(...)` immediately before it mutates `asset_share_value`, showing the codebase's own established pattern of "settle interest before changing state that affects the calculator." [5](#0-4) 

So after any `interest_rate_config` change (curve points, `zero_util_rate`/`hundred_util_rate`, `protocol_ir_fee`, `insurance_ir_fee`, `protocol_fixed_fee_apr`, etc.), the next `accrue_interest` call (triggered permissionlessly via `lending_pool_accrue_bank_interest`, or implicitly during any deposit/withdraw/borrow/repay/liquidation) will apply the *new* curve/fee parameters to the entire time window since `last_update`, not just the time after the config change. This misstates `asset_share_value`/`liability_share_value` and the protocol/insurance fee accrual (`cache.accumulated_since_last_update`, protocol/insurance revenue fields) for that stale window, causing over- or under-accrual of interest and fees for lenders/borrowers, and misallocated protocol/insurance revenue — a genuine accounting-path/value-misvaluation defect, not merely a theoretical concern, since `lending_pool_accrue_bank_interest` is permissionlessly callable by anyone at any time (including immediately after a config change, or with a long delay to maximize the retroactive misapplication window). [6](#0-5) 

### Title
Interest rate config updates apply new curve/fee parameters retroactively to unaccrued interest, mis-stating share values and protocol/insurance fees - (File: `programs/marginfi/src/instructions/marginfi_group/configure_bank.rs`, `programs/marginfi/src/instructions/marginfi_group/configure_bank_lite.rs`)

### Summary
`lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only` update `bank.config.interest_rate_config` without first calling `Bank::accrue_interest` to settle the interest owed for the elapsed period under the *old* curve/fee parameters. The next accrual (which can be permissionlessly triggered) then applies the *new* parameters across the entire time delta since `last_update`, retroactively misstating interest and protocol/insurance fees.

### Finding Description
`Bank::accrue_interest` computes `time_delta = current_timestamp - self.last_update` and builds the `InterestRateCalc` from `self.config.interest_rate_config` at the moment accrual runs, then applies that curve/fee configuration across the whole `time_delta`. [7](#0-6) 

`lending_pool_configure_bank` (admin-only, `has_one = admin`) and `lending_pool_configure_bank_interest_only` (delegate_curve_admin-only) both mutate `interest_rate_config` directly via `bank.configure(...)` / `InterestRateConfigImpl::update(...)` without calling `bank.accrue_interest(...)` beforehand to close out interest owed under the prior configuration. [8](#0-7) [3](#0-2) 

Elsewhere in the same file, `lending_pool_emissions_deposit` demonstrates the correct pattern of calling `accrue_interest` before any state change that depends on the interest calculator, showing this omission in the config paths is inconsistent with the codebase's own accounting invariant. [5](#0-4) 

Because `last_update` is only advanced inside `accrue_interest` itself, any elapsed time between the last accrual and a config change remains "unsettled" under the old parameters; the config change silently swaps in new parameters, and the next accrual (via `lending_pool_accrue_bank_interest`, or implicitly inside deposit/withdraw/borrow/repay/liquidation flows) applies the new curve/fee schedule over that entire unsettled window. [6](#0-5) 

### Impact Explanation
This retroactively misapplies interest rate curve changes (`zero_util_rate`, `hundred_util_rate`, `points`) and fee parameters (`protocol_ir_fee`, `insurance_ir_fee`, `protocol_fixed_fee_apr`, `insurance_fee_fixed_apr`) to a time period that should have used the prior configuration. This directly corrupts `asset_share_value`/`liability_share_value` (and thus every depositor's/borrower's real balance) as well as protocol/insurance revenue accounting (`accumulated_protocol_fees_outstanding`/insurance fields derived from `InterestRateStateChanges`), producing a durable, financially-material misstatement in the bank's accounting state that benefits or harms depositors/borrowers depending on the direction of the rate change.

### Likelihood Explanation
The bug is deterministically triggered any time `interest_rate_config` is updated while `time_delta` since `last_update` is non-zero (i.e., any config update that isn't immediately preceded by an accrual in the same slot). Given `lending_pool_accrue_bank_interest` is permissionlessly callable and accrual also happens implicitly through normal user activity (deposits, withdrawals, borrows, repayments), the misapplied window will almost always be realized shortly after any interest-rate-config update, making this a high-likelihood, structurally guaranteed accounting error rather than an edge case.

### Recommendation
In `lending_pool_configure_bank` and `lending_pool_configure_bank_interest_only`, call `bank.accrue_interest(clock.unix_timestamp, &group, ...)` (settling interest/fees under the existing `interest_rate_config` and advancing `last_update`) before applying the new `InterestRateConfigOpt`/`BankConfigOpt` to `bank.config.interest_rate_config`.

### Proof of Concept
1. Bank has outstanding assets/liabilities with `last_update = T0` and interest_rate_config `C_old` (low rates).
2. No accrual occurs between `T0` and `T1` (e.g., no user activity or explicit accrual call).
3. At `T1`, admin calls `lending_pool_configure_bank_interest_only` to set `interest_rate_config = C_new` (much higher `hundred_util_rate`/`zero_util_rate`/fee rates) — this directly overwrites config with no accrual, per `configure_bank_lite.rs` lines 27-29.
4. At `T2 > T1`, any user action or a permissionless call to `lending_pool_accrue_bank_interest` triggers `Bank::accrue_interest`, which computes `time_delta = T2 - T0` (spanning both the `C_old` and `C_new` periods) and applies `C_new` across the *entire* `time_delta`, per `bank.rs` lines 520-564.
5. Result: interest/fees for the `[T0, T1]` sub-interval are computed with `C_new` instead of `C_old`, producing an incorrect `asset_share_value`/`liability_share_value` and incorrect protocol/insurance fee accrual relative to the correct two-piece calculation.

pub fn lending_pool_configure_bank(
    ctx: Context<LendingPoolConfigureBank>,
    bank_config: BankConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;

    // If settings are frozen, you can only update the deposit and borrow limits, everything else is ignored.
    if bank.get_flag(FREEZE_SETTINGS) {
        bank.configure_unfrozen_fields_only(&bank_config)?;

        msg!("WARN: Only deposit+borrow limits updated. Other settings IGNORED for frozen banks!");

        emit!(LendingPoolBankConfigureFrozenEvent {
            header: GroupEventHeader {
                marginfi_group: ctx.accounts.group.key(),
                signer: Some(*ctx.accounts.admin.key)
            },
            bank: ctx.accounts.bank.key(),
            mint: bank.mint,
            deposit_limit: bank.config.deposit_limit,
            borrow_limit: bank.config.borrow_limit,
        });
    } else {
        // Settings are not frozen, everything updates
        bank.configure(&bank_config)?;
        msg!("Bank configured!");

        let group = ctx.accounts.group.load()?;
        bank.emode.validate_entries_with_liability_weights(
            &bank.config,
            group.emode_max_init_leverage,
            group.emode_max_maint_leverage,
        )?;

        emit!(LendingPoolBankConfigureEvent {
            header: GroupEventHeader {
                marginfi_group: ctx.accounts.group.key(),
                signer: Some(*ctx.accounts.admin.key)
            },
            bank: ctx.accounts.bank.key(),
            mint: bank.mint,
            config: bank_config,
        });
    }

    Ok(())
}

    fn accrue_interest(
        &mut self,
        current_timestamp: i64,
        group: &MarginfiGroup,
        #[cfg(not(feature = "client"))] bank: Pubkey,
    ) -> MarginfiResult<()> {
        #[cfg(all(not(feature = "client"), feature = "debug"))]
        sol_log_compute_units();

        let time_delta: u64 = (current_timestamp - self.last_update).try_into().unwrap();
        if time_delta == 0 {
            return Ok(());
        }

        let total_assets = self.get_asset_amount(self.total_asset_shares.into())?;
        let total_liabilities = self.get_liability_amount(self.total_liability_shares.into())?;

        self.last_update = current_timestamp;

        if (total_assets == I80F48::ZERO) || (total_liabilities == I80F48::ZERO) {
            #[cfg(not(feature = "client"))]
            emit!(LendingPoolBankAccrueInterestEvent {
                header: GroupEventHeader {
                    marginfi_group: self.group,
                    signer: None
                },
                bank,
                mint: self.mint,
                delta: time_delta,
                fees_collected: 0.,
                insurance_collected: 0.,
            });

            return Ok(());
        }
        let ir_calc = self
            .config
            .interest_rate_config
            .create_interest_rate_calculator(group);

        let InterestRateStateChanges {
            new_asset_share_value: asset_share_value,
            new_liability_share_value: liability_share_value,
            insurance_fees_collected,
            group_fees_collected,
            protocol_fees_collected,
        } = calc_interest_rate_accrual_state_changes(
            time_delta,
            total_assets,
            total_liabilities,
            &ir_calc,
            self.asset_share_value.into(),
            self.liability_share_value.into(),
        )?;

pub fn lending_pool_configure_bank_interest_only(
    ctx: Context<LendingPoolConfigureBankInterestOnly>,
    interest_rate_config: InterestRateConfigOpt,
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    msg!(
        "Configuring bank: {:?} mint: {:?}",
        ctx.accounts.bank.key(),
        bank.mint
    );

    // If settings are frozen, interest rates can't update.
    if bank.get_flag(FREEZE_SETTINGS) {
        msg!("WARN: Bank settings frozen, did nothing.");
    } else {
        bank.config
            .interest_rate_config
            .update(&interest_rate_config);
        bank.config.interest_rate_config.validate()?;
        msg!("Bank configured!");
    }

    Ok(())
}
