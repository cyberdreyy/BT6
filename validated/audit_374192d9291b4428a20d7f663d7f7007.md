### Title
Vault shareholder can drain shared ERC4626 liquidity to block `stopEpoch` funding or force a borrower default and LP haircut - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
In `IdleCDOEpochVariant` with `isProgrammableBorrower` enabled, stopping an epoch depends on `ProgrammableBorrower.onStopEpoch` being able to pull `shortfall` liquidity out of a shared external ERC4626 `vault`. Any unprivileged holder of that vault's shares can withdraw idle liquidity immediately before the manager calls `stopEpoch`, which either (a) makes `stopEpoch` revert with `StopEpochVaultLiquidityUnavailable` (repeatable freeze of all matured withdraw claims) or (b) — when the attacker's drain leaves `_currentVaultAssets()` below the shortfall — lets `onStopEpoch` return `true` so the subsequent `getFundsFromBorrower` `transferFrom` fails and `_handleBorrowerDefault` fires, socializing a loss across LPs that the borrower never caused. This is the credit-vault analog of a privileged counterparty blocking a victim's exit to force loss.

### Finding Description
`stopEpoch`/`_stopEpoch` requires pulling `_amountToPullFromBorrower + _pendingWithdraws` from the borrower. In programmable mode it first calls `IProgrammableBorrower(_borrower()).onStopEpoch(...)`.

In `ProgrammableBorrower.onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:231-268):

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) { ... }
  catch { revert StopEpochVaultLiquidityUnavailable(); }
}
```

Two attacker-controlled outcomes, both requiring only that the attacker is a shareholder/depositor of the same ERC4626 vault:

1. **Repeatable freeze.** The attacker calls `vault.withdraw`/`redeem` to strip the vault's idle asset balance so `vault.withdraw(shortfall, ...)` reverts (ERC4626 liquidity failure). `onStopEpoch` reverts, the revert bubbles out of `stopEpoch`, the epoch stays `isEpochRunning`, `pendingWithdraws` stays unfunded, and `claimWithdrawRequest`/`claimInstantWithdrawRequest` revert for every LP (`epochNumber <= lastWithdrawRequest` guard). Each time liquidity refills, the attacker re-drains it — a cheap liveness block on the whole pool's exit, mirroring the external report's partyB refusing `fillCloseRequest`.

2. **Forced default.** If the attacker drains deeper so `shortfall > _currentVaultAssets()`, `onStopEpoch` returns `true` without reverting. `stopEpoch` then attempts `getFundsFromBorrower(_amountToPullFromBorrower + _pendingWithdraws)`, the `transferFrom` fails because the borrower contract does not hold the tokens, and the catch block calls `_handleBorrowerDefault` (contracts/IdleCDOEpochVariant.sol:501-505): `defaulted = true`, deposits paused, withdraw requests disabled, epoch stopped. LPs can then only exit through the default-recovery path (`finalizeDefault` → haircut via `_claimDefaultedWithdrawRequest` / `lossRecoveryPriceByEpoch`), taking a loss entirely manufactured by a third party. This is the direct analog of "partyB blocks exits so partyA gets liquidated": an unprivileged actor blocks the funding leg of `stopEpoch` so honest LPs eat a default haircut.

The broken invariant is solvency/fair exit: withdrawal funding must depend only on the honest borrower's repayment, not on third-party liquidity in a shared yield vault. Existing guards do not stop it — `defaulted` checks, `skipDefaultCheck`, `_onlyIdleCDO`, and reserve checks all assume vault liquidity is stable between epochs; the test `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` (test/foundry/ProgrammableBorrowerCreditVault.t.sol:372-399) confirms the revert path but does not consider an attacker deliberately inducing it.

### Impact Explanation
- Temporary or effectively permanent freezing of all matured withdraw requests and LP exits while `stopEpoch` cannot complete.
- In the deeper-drain variant, a forced borrower `defaulted` state: `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are disabled, and pending/active claims are only payable through `finalizeDefault`, which applies an aggregate recovery multiplier — direct, quantified LP loss equal to the unrecovered shortfall (up to the full pending-withdraw plus interest basis).

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault admits third-party depositors (e.g., a shared Morpho-style vault) and shared, finite idle liquidity — exactly the configuration the codebase supports (`setVault`, `_depositToVault`). The attacker only needs vault shares and a well-timed withdraw around the epoch-end `stopEpoch` call; no privilege and no capital at risk beyond vault share price exposure. Repeated griefing of the revert path costs only gas.

### Recommendation
- Do not let a single `stopEpoch` depend on instantly pulling the full shortfall from a shared vault: pre-fund reserve/liquidity buffers during the epoch (e.g., keep `epochPendingWithdraws` in `underlyingToken` on-hand instead of in the vault), or unwind vault exposure progressively rather than at stop time.
- On `shortfall > _currentVaultAssets()`, do not silently return `true` into a failing `transferFrom` that triggers `_handleBorrowerDefault`; surface a distinct "external liquidity shortfall" state that keeps the epoch running and lets the manager retry or partially settle, so third-party drains cannot manufacture a default.
- Consider permissioned/isolated vault wrappers for the programmable-borrower sleeve so external depositors cannot consume the liquidity the facility depends on.

### Proof of Concept
Foundry-style sketch (programmable-borrower setup as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testVaultDepositorForcesStopEpochDefault() external {
    // setup: programmable borrower mode, real shared ERC4626 vault, LP deposits AA,
    // LP calls cdoEpoch.requestWithdraw(...) so pendingWithdraws > 0, epoch runs.
    idleCDO.depositAA(amount);
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)), address(aaTranche));
    _startEpochAndCheckPrices(0);

    uint256 pending = strategy.pendingWithdraws();

    // attacker: unprivileged vault shareholder drains idle liquidity
    uint256 idle = USDC.balanceOf(address(vault));
    vm.prank(attacker);
    vault.withdraw(idle, attacker, attacker); // or redeem shares

    // case A: vault still "covers" on paper but withdraw fails -> retryable revert
    // case B: _currentVaultAssets() < shortfall -> onStopEpoch returns true,
    //         borrower transferFrom fails -> forced default
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // case B: succeeds but defaulted == true

    assertTrue(cdoEpoch.defaulted(), "attacker-induced default");
    // LP matured claim can no longer pay at par; only haircut via finalizeDefault
}
```

Note: the exact revert-vs-default branch depends on whether post-drain `_currentVaultAssets()` still exceeds the shortfall; both branches are attacker-reachable, and the deeper-drain branch produces the forced default and LP haircut shown above.
