### Title
Request-ID reuse after `sendResponseAndClearRequest` clears a completed request allows a stale node response to be captured by a new request with the same ID - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`newActiveRequest` and `sendResponseAndClearRequest` both key `activeRequests` purely by the caller-supplied `req.ID` with no generation/nonce binding. Once `sendResponseAndClearRequest` deletes the map entry for a completed request, any subsequent `HandleJSONRPCUserMessage` call that reuses the same ID is admitted, and a straggling `HandleNodeMessage` response still in flight for the *original* request will be matched to the *new* `activeRequest` and folded into its bundle/Callback.

### Finding Description
`newActiveRequest` (`core/services/gateway/handlers/confidentialrelay/handler.go:368-383`) only checks `h.activeRequests[req.ID] != nil` under `h.mu.Lock()` and, if absent, installs the new `activeRequest`. `sendResponseAndClearRequest` (`handler.go:659-679`) claims the request via `ar.completed.CompareAndSwap`, sends the payload, then does `delete(h.activeRequests, ar.req.ID)` under a separate `h.mu.Lock()` acquisition. Between the delete and any still-in-flight node reply for the original request, the map slot for that ID is empty.

`HandleNodeMessage` (`handler.go:391-429`) routes purely by `resp.ID`: `ar := h.getActiveRequest(resp.ID)`. Nodes are fanned out to concurrently in `fanOutToNodes`, and only 2F+1 (or on grace/timeout, F+1) signed responses are required to complete a request — the remaining, slower nodes' responses are not cancelled or discarded, they are simply looked up again later against whatever the map holds for that ID. If a new `activeRequest` for a different caller has been inserted under the same ID in the interim, the straggling response for the original request is `addResponseForNode`'d into the new request's `responses` map, `Bundle`d, and can trigger `forwardBundleOrTerminateIfReady` → `sendResponseAndClearRequest` delivering it through the *new* caller's `Callback`.

There is no per-instantiation nonce/generation counter on `activeRequest`, and confidential relay's `HandleJSONRPCUserMessage` performs no authorization/ownership binding of the ID (unlike `core/services/gateway/handlers/vault/handler.go`, which prefixes IDs with an authorized owner before using them). The only ID-related checks are non-empty and ≤200 characters (`handler.go:350-355`).

### Impact Explanation
If exploited, an attacker who both (a) can reach `HandleJSONRPCUserMessage` with a signed/authorized gateway request and (b) knows or can predict the exact `req.ID` string used by another caller's still-completing request, can receive that caller's bundled relay-node response instead of the intended recipient — a cross-user response confusion / confidentiality-adjacent bug matching Chainlink's "unauthorized disclosure of another user's request/response data" bounty class. The severity of actual data exposure is mitigated by the design comment in `bundler.go` that "the gateway is a dumb fan-in... The enclave is the sole trust anchor" — for `MethodSecretsGet` the forwarded content is opaque ciphertext/shares that require the enclave's key to decrypt, so misdelivery of that specific payload does not by itself yield plaintext secrets. For `MethodCapabilityExec`, however, `CapabilityResponseResult.Payload` can carry the base64-encoded plaintext output of a workflow's capability call, so misdelivery there is a genuine content leak to the wrong party.

### Likelihood Explanation
Exploitation requires: (1) valid credentials/auth to submit gateway JSON-RPC requests, (2) advance knowledge of another party's exact `req.ID` (an arbitrary string chosen by that party's own client — not attacker controlled and not enforced to be random/secret by this handler), and (3) winning a narrow timing race immediately after the victim's request completes and before all fanned-out node sends resolve. There is no rate limit or backoff preventing repeated attempts to win this race once the ID is known, so likelihood scales with the attacker's ability to predict/observe IDs and with request volume/latency spread across the DON, but is inherently probabilistic and requires precise timing rather than a deterministic trigger.

### Recommendation
Bind delivery to a specific `activeRequest` instantiation rather than to the mutable ID string: attach a per-instantiation nonce/generation value when creating the `activeRequest`, and either encode it into the ID sent to nodes or verify it out-of-band before applying a node response. Alternatively, keep a short-lived tombstone (e.g., valid until `nodeSendTimeout` has elapsed since completion) so `newActiveRequest` rejects ID reuse until any responses genuinely in flight for the previous instantiation can no longer arrive, and reject/drop node responses for IDs found in the tombstone set as stale rather than routing them to a newly admitted request.

### Proof of Concept
Go handler-level integration test in `core/services/gateway/handlers/confidentialrelay`:
1. Start a handler with `F=1`, `N=4` (as in existing tests), using a fake clock and mocked `don`.
2. Submit request A with `ID = "shared-id"`; deliver 2F+1 (3) signed responses via `HandleNodeMessage` so `forwardBundleOrTerminateIfReady` calls `sendResponseAndClearRequest`, completing A and deleting `activeRequests["shared-id"]` — assert `h.getActiveRequest("shared-id") == nil`.
3. Immediately (same goroutine, no further ticks) call `h.HandleJSONRPCUserMessage` again with `ID = "shared-id"` and a fresh callback `cbB` (request B), succeeding because the map slot was cleared.
4. Deliver one more `HandleNodeMessage` response tagged `ID = "shared-id"` representing node 4's straggling reply to *request A* (constructed with A's original params/result).
5. Assert this straggler response is added to B's `responses` (`ar.addResponseForNode` returns true) and, once B's own quorum is reached, that B's bundle includes A's straggler entry — demonstrating the isolation violation. Contrast with an expected fix where the straggler is dropped as unrecognized/stale rather than merged into B.
