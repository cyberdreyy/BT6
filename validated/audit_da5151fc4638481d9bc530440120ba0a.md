### Title
Client-controlled `recent_blockhash` unknown to the bank causes `.unwrap()` panic in `process_transaction_with_commitment_and_context` - ([File: banks-server/src/banks_server.rs])

### Summary
`BanksServer::process_transaction_with_commitment_and_context` calls `bank.get_blockhash_last_valid_block_height(&blockhash)` and unconditionally `.unwrap()`s the result after sanitization/signature verification succeed. Since sanitization does not validate the blockhash against the bank's blockhash queue, a client can submit a `VersionedTransaction` with a syntactically valid, correctly signed message whose `recent_blockhash` was never registered by (or has aged out of) the bank, causing the `Option::unwrap()` on `None` to panic the async task.

### Finding Description
The RPC path is: `process_transaction_with_commitment_and_context` (`banks-server/src/banks_server.rs:317-361`) takes the raw `recent_blockhash` from the client-supplied `transaction.message` at line 323, then sanitizes via `SanitizedTransaction::try_create` (lines 327-336) and verifies signatures via `sanitized_transaction.verify()` (line 338). Neither of these performs any blockhash-queue lookup — `RuntimeTransaction::try_create`/`try_from` only check instruction/account count limits and resolve static/dynamic account keys (`runtime-transaction/src/runtime_transaction/sdk_transactions.rs:78-134`), and `verify()` is purely a signature check. After both checks pass, line 343-346 calls `self.bank(commitment).get_blockhash_last_valid_block_height(&blockhash).unwrap()`. If the client supplies a `recent_blockhash` that is not currently in the bank's blockhash queue (e.g., a random `Hash`, or a legitimate but since-expired blockhash), this lookup returns `None`, and `.unwrap()` panics, unwinding on whatever thread is executing this async task (the tarpc/tokio server-handling task).

### Impact Explanation
This is a validator/RPC-process crash triggered by a single, unprivileged client request over the BanksServer RPC interface (used by `solana-banks-client`/BanksServer test/RPC harness) — it matches the "single-request process crash" bounty category since no special privileges, multiple calls, or non-standard inputs are needed beyond one malformed transaction submission.

### Likelihood Explanation
Highly likely and trivially reproducible: an attacker only needs to build a `VersionedTransaction` with a valid signer keypair (so `verify()` passes) and any `recent_blockhash` not present in the bank's active blockhash queue (default construction, `Hash::default()`, or a stale hash), and call `process_transaction_with_commitment_and_context` or `process_transaction_with_preflight_and_commitment_and_context` once. No race condition or timing dependency is required beyond the message/signature being internally consistent.

### Recommendation
Replace the `.unwrap()` at line 343-346 with proper error handling: if `get_blockhash_last_valid_block_height` returns `None`, return `Some(Err(TransactionError::BlockhashNotFound))` (or equivalent existing variant) instead of panicking, mirroring how sanitization/verify failures are already surfaced as `Some(Err(err))`.
