### Title
Confirmations from a removed multisig member remain counted toward the confirmation threshold, allowing a request to execute below the intended live-member threshold - (File: multisig2/src/lib.rs)

### Summary
### Finding Description
The external report describes a class of bug where a mutable parameter (APR) is changed without first settling/reconciling state that was accrued under the old parameter, so a later settlement uses the wrong (new) value against old-accrual data. The closest analog reachable in this repo set is in `multisig2/src/lib.rs`: the binding "confirmations counted versus live members" is broken because `delete_member` purges only the requests *created by* the removed member, but not the confirmations that member previously cast on *other* pending requests.

`delete_member` only cleans up requests where the deleted member is the creator: [1](#0-0) 

```
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    assert(
        self.members.len() - 1 >= self.num_confirmations as u64,
        "Removing given member will make total number of members below number of confirmations",
    );
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    ...
    self.members.remove(&member);
    ...
}
``` [1](#0-0) 

It filters `self.requests` by `r.member == member` — i.e., requests the deleted member *authored* — and only removes confirmations tied to those specific requests. It never scans the `confirmations: LookupMap<RequestId, HashSet<String>>` map to strip the removed member's entries from requests created by *other* members that the removed member had already confirmed.

`confirm()` later counts confirmations purely by set size, without re-validating that every entry in the set still corresponds to a current member: [2](#0-1) 

```
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let member = self.current_member().unwrap_or_else(...);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert(!confirmations.contains(&member.to_string()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(member.to_string());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
``` [2](#0-1) 

Only the caller of `confirm()` is checked to be a current member (`current_member()` must resolve and `assert_valid_request` requires `current_member().is_some()`); the pre-existing entries already stored in `confirmations` are never re-validated against the live `members` set.

### Impact Explanation
The binding that should hold is:
`len({confirmations on request R}) ∩ {live members} + 1(new confirmer) >= num_confirmations`

But the actual check performed is:
`len({confirmations on request R}) + 1(new confirmer) >= num_confirmations`

These two are not equal once a member who had confirmed request `R` (created by someone else) is later removed via a `DeleteMember` action — the stale confirmation is never purged, so it is still counted as if it came from a live member.

Concretely: with 3 members `A, B, C` and `num_confirmations = 2`:
1. `A` calls `add_request` for `R` (no confirm).
2. `B` calls `confirm(R)` → `confirmations = {B}` (1 < 2, not yet executed).
3. Members execute a separate confirmed `DeleteMember{B}` request. The assert `members.len() - 1 >= num_confirmations` (`3-1=2 >= 2`) passes, so `B` is removed. `delete_member` only removes requests *authored* by `B`; `R` (authored by `A`) is untouched, and `R`'s confirmation set still contains `B`.
4. `C` (now one of only two live members, `A` and `C`) calls `confirm(R)`: `confirmations.len() = 1` (`B` is still in the set) `+ 1 = 2 >= num_confirmations(2)` → `R` executes.

`R` executes with confirmations effectively from `B` (removed, no longer a member) and `C` — i.e., only **one** live member (`C`) actually approved it, while the contract believes the `2`-of-`N` threshold was met. This is a multisig request executed below the intended live-member threshold, which per the rules is a Critical-severity impact (funds transfer, key additions/removals, or arbitrary function calls can all be scheduled as `MultiSigRequestAction`s, so this can be used to move funds or add unauthorized keys with fewer live approvals than configured).

### Likelihood Explanation
This does not require any privileged actor beyond normal multisig operation: it only requires (a) a request pending confirmation from one member, and (b) a subsequent (legitimately-approved) `DeleteMember` request removing that confirming member, which is a routine operational action (e.g., rotating keys/removing a compromised or departing member) rather than an attack requiring social engineering or a malicious deployer. Any member colluding with, or simply outliving, another member's confirmation can exploit the residual confirmation to execute a request with fewer live approvals than `num_confirmations` requires. The bug is deterministic and always reachable whenever a confirming (non-authoring) member is removed before the request they confirmed is resolved.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests authored by the removed member) and remove the deleted member's identifier from every confirmation set, or invalidate/re-count confirmations lazily against the current `members` set inside `confirm()` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 2` and members `{A, B, C}`.
2. As `A`, call `add_request` to create request `R` (e.g., a `Transfer` action) — do not confirm.
3. As `B`, call `confirm(R)` — confirmations for `R` become `{B}` (size 1, below threshold, not executed).
4. As two members (any 2 of `A/B/C`), execute a `DeleteMember{member: B}` request (this passes the `members.len()-1 >= num_confirmations` check since `3-1=2>=2`), removing `B` from `members`. Note `R` was authored by `A`, so `delete_member`'s cleanup of "outstanding requests by public_key" does not touch `R`, and `R`'s confirmation set still contains `B`.
5. As `C` (one of the two remaining live members), call `confirm(R)`. The check `confirmations.len() (1, containing stale "B") + 1 >= 2` passes, and `R` is executed via `execute_request`, even though only `C` — a single live member — actually approved it after `B`'s removal. [1](#0-0) [2](#0-1)
