### Title
Unchecked subtraction in `L1BlockInfo::operator_fee_refund` can underflow/wrap on a crafted refund-heavy transaction - (File: `crates/common/evm/src/l1block.rs`)

### Summary
`L1BlockInfo::operator_fee_refund` computes the "effective gas used" for the Isthmus operator-fee refund with a raw, uncapped subtraction of `gas.remaining() + gas.refunded()` from `gas.limit()`. Unlike every other fee computation in the same file and in `eip8130.rs`, this expression uses plain `u64` arithmetic instead of `checked_sub`/`saturating_sub`, and it uses the **raw** gas-refund counter instead of the EIP‑3529-capped refund that `eip8130.rs`'s `capped_refund` computes for the analogous case.

### Finding Description [1](#0-0) 

```rust
pub fn operator_fee_refund(&self, gas: &Gas, spec_id: BaseSpecId) -> U256 {
    if !spec_id.is_enabled_in(BaseUpgrade::Isthmus) {
        return U256::ZERO;
    }
    let operator_cost_gas_limit =
        self.operator_fee_charge_inner(U256::from(gas.limit()), spec_id);
    let operator_cost_gas_used = self.operator_fee_charge_inner(
        U256::from(gas.limit() - (gas.remaining() + gas.refunded() as u64)),
        spec_id,
    );
    operator_cost_gas_limit.saturating_sub(operator_cost_gas_used)
}
```

`gas.limit() - (gas.remaining() + gas.refunded() as u64)` is intended to equal the net gas used after applying the SSTORE refund. It is only valid so long as `gas.remaining() + gas.refunded() <= gas.limit()`. Elsewhere in the same codebase, the corresponding EIP‑8130 gas-billing path explicitly caps the raw refund counter to the EIP‑3529 `gas_used / 5` ceiling before using it, and even documents why a naive/raw refund value cannot be trusted: [2](#0-1) 

`operator_fee_refund` skips that cap entirely and casts the framework's raw (potentially larger) refund counter directly into the subtraction. A transaction that accrues a large refund relative to its consumed gas (e.g. many storage-clearing `SSTORE`s) can make `gas.remaining() + gas.refunded()` exceed `gas.limit()`, causing this subtraction to underflow.

### Impact Explanation
The workspace does not set `overflow-checks = true` for the release profile (no matches found for `overflow-checks` anywhere in the repo), so in a standard release build this underflow wraps silently to a value near `u64::MAX` rather than panicking. That wrapped, enormous "gas used" is then fed into `operator_fee_charge_inner`, producing an `operator_cost_gas_used` that is then subtracted (via `saturating_sub`) from `operator_cost_gas_limit`, yielding an incorrect (typically zero) operator-fee refund to the payer instead of the correct amount. This corrupts fee accounting for affected transactions.

More importantly, this same crate (`base-common-evm` / `l1block.rs`) is depended on by the proof/executor and proof stack (`crates/proof/executor`, `crates/proof/proof`, `crates/proof/client`, `crates/proof/host`, zkVM programs under `crates/proof/zk`), several of which build under different compilation profiles/targets (e.g., zkVM guest programs) than the canonical sequencer/validator node. If any of these consuming programs is compiled with overflow checks enabled (common in some zkVM/no_std guest build configurations) while the mainline node build is not (or vice versa), the two would compute divergent results for the same transaction — the node silently wraps to a wrong refund while the fault-proof/zk program panics or computes a different wrapped value. That divergence can produce a different state root / operator-fee-vault balance between the canonical execution and the fault-proof program, i.e. a wrong provable output root, which is one of the accepted high-impact categories for this program.

Even absent a build-profile divergence, this is at minimum a fee-accounting correctness bug reachable by any unprivileged transaction sender post-Isthmus.

### Likelihood Explanation
Reaching the underflow requires a single, ordinary EIP‑1559/standard transaction (fully attacker-controlled, no privileged access needed) that clears enough previously-set storage slots to accumulate a refund counter comparable to or larger than its own consumed gas budget. This is achievable with a moderate number of `SSTORE` operations transitioning non-zero slots to zero within the gas limit, since `operator_fee_refund` uses the *uncapped* refund counter rather than the correctly capped one used elsewhere in the codebase (`capped_refund` in `eip8130.rs`). No special permissions, precompile access, or sequencer/validator role are required — this is directly reachable by any transaction sender post-Isthmus activation.

### Recommendation
1. Replace the raw subtraction with checked/saturating arithmetic, mirroring the discipline used throughout `eip8130.rs`:
   ```rust
   let gas_used = gas.limit().saturating_sub(gas.remaining().saturating_add(gas.refunded() as u64));
   ```
2. More fundamentally, apply the EIP-3529 refund cap (`gas_used / 5`, i.e. reuse or port `capped_refund`/`MAX_REFUND_QUOTIENT` from `eip8130.rs`) to `gas.refunded()` before using it here, so the "effective gas used" calculation matches the actual consensus-charged gas used rather than an uncapped refund counter.
3. Add a unit/property test asserting `operator_fee_refund` never underflows and matches `operator_cost_gas_limit - operator_cost_gas_used` computed against the properly capped refund, across the full range of `(limit, remaining, refunded)` combinations, including adversarial refund-heavy transactions.
4. Audit `crates/proof/executor` and the zkVM guest programs to confirm they use the identical (fixed) arithmetic and profile-level overflow-check settings as the canonical node, to rule out any output-root divergence from this code path.

### Proof of Concept
Conceptual PoC (mirrors the pattern of the original `LPDA` report, applied to this codebase's arithmetic):
```rust
use revm::interpreter::Gas;

// Construct a Gas accounting state where the raw refund counter exceeds
// gas_used, e.g. by simulating a transaction that clears many storage
// slots (each granting a refund) relative to gas actually consumed.
let mut gas = Gas::new(30_000); // gas_limit = 30_000
// ... drive execution such that gas.remaining() is small (most gas spent)
// and gas.refunded() accumulates well beyond what capped_refund would allow,
// e.g. gas.remaining() = 1_000, gas.refunded() = 29_500
// => gas.remaining() + gas.refunded() = 30_500 > gas.limit() (30_000)

let l1_block_info = L1BlockInfo { operator_fee_scalar: Some(U256::from(1_000_000)), ..Default::default() };
// operator_fee_refund computes: 30_000 - 30_500 -> underflows (wraps in release, panics in debug)
let refund = l1_block_info.operator_fee_refund(&gas, BaseSpecId::new(BaseUpgrade::Isthmus));
```
This requires wiring up the exact revm `Gas` counters (which is internal state produced by interpreter execution, not directly settable), so the concrete exploit is: craft a standard transaction whose execution trace clears a sufficient number of non-zero storage slots such that its accumulated (uncapped) SSTORE refund, when added to the interpreter's `remaining()` gas, exceeds the transaction's `gas_limit()`, triggering the subtraction underflow described above.

    /// refund: clamps a net-negative counter to zero (a net negative grants no
    /// refund, never adds to gas owed), then applies EIP-3529's `gross_used / 5`
    /// ceiling. Accounting refunds signed across the whole transaction — rather
    /// than flooring each call's refund at zero — is what makes offsetting SSTORE

    fn capped_refund(signed_refund: i64, gross_used: u64) -> u64 {
        u64::try_from(signed_refund.max(0)).unwrap_or(0).min(gross_used / MAX_REFUND_QUOTIENT)
    }
