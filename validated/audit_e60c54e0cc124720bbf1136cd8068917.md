## Title
Stale rejection weight is never reversed when a signer later accepts the same block, letting a resolved rejection permanently poison the coordinator's blocking-minority tally - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The node-side `StackerDBListener` (used by the mining coordinator, `signer_coordinator.rs`) tallies `total_weight_approved` and `total_weight_rejected` per block independently. When a signer first rejects a proposal and later legitimately reconsiders and accepts the *same* block hash (a flow the signer protocol explicitly supports for several reject reasons), the listener adds that signer's weight to `total_weight_approved` but never removes it from `total_weight_rejected`. The stale rejection weight is never reclaimed, so the coordinator's "blocking minority" check can trip on weight that no longer represents a live rejection — mirroring the reported bug class where an add/remove delta is computed against a reference point (here, the earlier rejection) that is never adjusted when the underlying position (vote) changes.

### Finding Description
In `handle_block_response` inside `stacks-node/src/nakamoto_node/stackerdb_listener.rs`:

- The `Accepted` branch only guards against double counting via `gathered_signatures`: [1](#0-0) 
It adds `signer_entry.weight` to `total_weight_approved` if the slot is not already in `gathered_signatures` — it never checks or clears any prior entry the same slot has in the rejection tally.

- The `Rejected` branch guards against double counting via `responded_signers`: [2](#0-1) 
This correctly prevents a signer from being re-counted as a rejecter if they already responded, but it means a signer that rejects **first** gets their weight permanently added to `total_weight_rejected`, with no corresponding decrement path anywhere in the file.

The `BlockStatus` struct exposes both tallies to the coordinator with no reconciliation invariant enforced between them: [3](#0-2) 

The mining coordinator in `signer_coordinator.rs::get_block_status` evaluates the rejection branch *first*, unconditionally, using this stale `total_weight_rejected`: [4](#0-3) 
If `total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight`, the coordinator gives up on the block (`NakamotoNodeError::SignersRejected`), excluding transactions and forcing a new proposal — even if every signer whose weight is baked into that number has since accepted.

Critically, a signer switching from reject to accept for the same block is not a hypothetical/malicious path. The signer protocol explicitly designs for it: `should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs` marks reasons like `ValidationFailed(NotFoundError)`, `NoSortitionView`, `ConnectivityIssues`, and `ConsensusHashMismatch` as reconsiderable: [5](#0-4) 
and this exact reject→accept transition (rejection while a race exists, then acceptance on reproposal) is validated by existing tests (`signer_reevaluates_proposal_with_missing_burn_view`, `signer_can_accept_rejected_block`): [6](#0-5) [7](#0-6) 

Notably, the *signer-side* DB (`SignerDb::add_block_signature`/`add_block_rejection_signer_addr`) already fixed this exact class of bug — a signature clears a prior rejection record, per the changelog and regression test: [8](#0-7) [9](#0-8) 
but the node-side `stackerdb_listener.rs` tally used by the mining coordinator was never given the equivalent reconciliation, leaving the coordinator's aggregate view inconsistent with the true, current set of rejecting signers.

### Impact Explanation
This breaks the equality between "aggregated rejected weight" and "currently verified rejecting signers." A block that in reality has strictly less than the 30%+ blocking-minority weight of live rejections can still be treated by the mining coordinator as globally rejected, because earlier (now-superseded) rejections are never subtracted. This causes the coordinator to abandon a signable block, exclude transactions, and force costly re-proposals — a liveness wedge on block production driven by ordinary network timing/race conditions rather than any signer majority or malicious action, matching the High-impact category of "acting on a stale ... threshold."

### Likelihood Explanation
No majority or malicious signer key is required — this can occur from a single signer whose vote flips from reject to accept due to a benign, well-documented race (e.g., burn view / parent-block visibility lag at proposal time), a scenario the codebase explicitly tests for and expects to happen in normal operation. The corresponding stale weight simply accumulates without ever being reclaimed, so it can be exercised any time a miner reproposes the same block hash after a transient, reconsiderable rejection.

### Recommendation
When processing an `Accepted` response for a slot in `handle_block_response`, check whether that slot previously contributed to `total_weight_rejected` (e.g., track per-slot vote kind, not just `gathered_signatures`/`responded_signers` presence) and subtract the signer's weight from `total_weight_rejected` before/while adding it to `total_weight_approved`, so the two tallies stay reconciled with the current, live set of votes — mirroring the fix already applied on the signer side (`SignerDb::add_block_signature` clearing prior rejection records).

### Proof of Concept
1. Miner proposes block B (sighash H) to signer set with weight_threshold T and blocking minority M = total_weight - T + 1.
2. Signer X (weight w) evaluates B, hits a transient/reconsiderable failure (e.g., burn view not yet visible on X's node) and returns `Rejected` for H with `RejectCode::ValidationFailed(NotFoundError)`. `StackerDBListener::handle_block_response` records this: `total_weight_rejected += w` (stacks-node/src/nakamoto_node/stackerdb_listener.rs:515-518).
3. Enough other signers accumulate rejection weight from similar transient races such that `total_weight_rejected` is just under M, while a majority of signers (including X, after reconsideration) actually now accept once the miner re-proposes the identical block B.
4. Miner re-proposes B; X's `should_reevaluate_reject_reason` returns true for `NotFoundError`, X re-validates and sends `Accepted` for the same H.
5. `handle_block_response`'s `Accepted` branch adds `w` to `total_weight_approved` (line 443-446) but performs no corresponding subtraction from `total_weight_rejected`.
6. If the sum of stale-but-unretracted rejection weight from X and similarly-recovered signers crosses M, `signer_coordinator.rs::get_block_status`'s rejected-branch check (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`, checked before the approved branch) fires, and the coordinator treats the block as rejected/`SignersRejected` even though live signer sentiment (recomputed from scratch) would have crossed the 70% approval threshold instead.

/// Determine if a block should be re-evaluated based on its rejection reason˝
fn should_reevaluate_reject_reason(block_info: &BlockInfo) -> bool {
    if let Some(reject_reason) = &block_info.reject_reason {
        match reject_reason {
            RejectReason::ValidationFailed(ValidateRejectCode::UnknownParent)
            | RejectReason::ValidationFailed(ValidateRejectCode::NotFoundError)
            | RejectReason::NoSortitionView
            | RejectReason::ConnectivityIssues(_)
            | RejectReason::TestingDirective
            | RejectReason::InvalidTenureExtend
            | RejectReason::ConsensusHashMismatch { .. }
            | RejectReason::NoSignerConsensus
            | RejectReason::NotRejected
            | RejectReason::Unknown(_) => true,
            RejectReason::ValidationFailed(_)
            | RejectReason::RejectedInPriorRound
            | RejectReason::SortitionViewMismatch
            | RejectReason::ReorgNotAllowed
            | RejectReason::InvalidBitvec
            | RejectReason::PubkeyHashMismatch
            | RejectReason::InvalidMiner
            | RejectReason::NotLatestSortitionWinner
            | RejectReason::InvalidParentBlock
            | RejectReason::DuplicateBlockFound
            | RejectReason::IrrecoverablePubkeyHash
            | RejectReason::ProblematicTransactions
            | RejectReason::ProposalTooOld => {
                // No need to re-validate these types of rejections.
                false
            }
        }
    } else {
        false
    }
}
