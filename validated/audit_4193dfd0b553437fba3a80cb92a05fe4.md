### Title
Multisig deployed with zero deposit leaves it unable to pay for its own storage - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` is `#[payable]` but never asserts a minimum attached deposit before creating and deploying a multisig account, unlike its sibling factories. An attacker can call `create` with `attached_deposit = 0`, producing a live multisig account (with member keys/accounts installed) that has no NEAR balance to cover its own storage staking cost, which can render the account unable to accept further state-changing calls (e.g., `add_request`), permanently freezing any funds later sent to it.

### Finding Description
The invariant being violated is: `deployed_multisig.account_balance >= storage_cost(deployed_multisig)` — i.e., every multisig created via the factory must be able to pay for its own storage. `MultisigFactory::create` builds and dispatches the promise chain unconditionally: [1](#0-0) 

Note there is no `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` anywhere in this function, and `.transfer(env::attached_deposit())` simply forwards whatever was attached — including zero — to the newly created account. Compare this to `StakingPoolFactory::create_staking_pool`, which explicitly enforces a minimum deposit before creating the account: [2](#0-1) 

`lockup-factory/src/lib.rs` follows the same pattern using its own `MIN_ATTACHED_BALANCE` check. `multisig-factory` has no equivalent constant or assertion, and also has no `.then()` callback to `assert_self()`/`is_promise_success()` that could detect creation failure and refund the caller as `on_staking_pool_create` does.

Exploit flow: an unprivileged attacker calls `create("victim", members, num_confirmations)` with `attached_deposit = 0` and sufficient prepaid gas. The factory creates `victim.<factory>`, deploys the `multisig2.wasm` code, transfers 0 yoctoNEAR, and calls `new` with the attacker-chosen `members`/`num_confirmations`. The resulting account exists on-chain, holds member keys/accounts as configured by the attacker, but has an account balance of (near) zero — insufficient to cover the storage staked by its own contract code and state. Any subsequent attempt to mutate state on that account (e.g., a legitimate `add_request` call funding it later) can fail due to insufficient balance to cover storage staking, and because the account's balance can never organically exceed the code+state storage cost without an external top-up, it is effectively bricked for its intended multisig purpose — funds sent to it for storage/gas top-up purposes or held for confirmations are frozen if the account can't process further requests.

None of the codebase's existing guards apply here: `assert_self()`, `is_promise_success()`, `assert_one_yocto()`, and the deposit checks used in `staking-pool-factory`/`lockup-factory` (`MIN_ATTACHED_BALANCE`) are simply absent from `multisig-factory::create`.

### Impact Explanation
This falls under "funds permanently frozen" (Critical) or, at minimum, "funds frozen for at least one epoch but recoverable" (High), because a multisig deployed this way cannot cover its own storage and cannot reliably process requests, freezing anything later deposited to it for confirmations. This is not merely griefing without attacker gain — while the attacker doesn't extract funds, the vulnerability breaks the stated invariant "a created multisig can pay for its storage," a core safety property, and any user who is directed to or relies on such an under-funded multisig account risks losing access to funds sent there. Each `create` call is independent and repeatable per account name chosen by the attacker.

### Likelihood Explanation
Trivial and highly likely: any account can call `create` with `attached_deposit: 0` and normal prepaid gas; no privileges, whitelisting, or special account state are required. The attacker's cost is just gas fees for the transaction itself.

### Recommendation
Add a `MIN_ATTACHED_BALANCE` constant (sized to cover the deployed `multisig2.wasm` code + initial state storage cost) and assert `env::attached_deposit() >= MIN_ATTACHED_BALANCE` at the top of `create`, mirroring the pattern already used in `staking-pool-factory::create_staking_pool` and `lockup-factory`. Additionally, consider adding a `.then()` callback with `assert_self()`/`is_promise_success()` to detect deployment failure and refund the caller, consistent with `StakingPoolFactory::on_staking_pool_create`.
