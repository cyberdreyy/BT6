### Title
Tenure-change duplicate check in `SortitionsView::validate_tenure_change_payload` (v1) still uses `get_last_globally_accepted_block` instead of `get_last_signed_block`, allowing v1 signers to accept a duplicate tenure-start block that v2 signers reject - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in v1 checks for an existing block in the tenure using `signer_db.get_last_globally_accepted_block` [1](#0-0) , while the equivalent v2 check (`GlobalStateView::validate_tenure_change_payload`) was fixed to use `signer_db.get_last_signed_block`, which also covers `LocallyAccepted` blocks [2](#0-1) . The v2 change was an explicit regression fix, documented in a test that states the old (`get_last_globally_accepted_block`) logic "would miss blocks in `LocallyAccepted` or `PreCommitted` state and incorrectly allow a duplicate tenure change" [3](#0-2) . This fix was never backported to v1, so v1 still contains the exact bug the v2 regression test was written to prevent.

### Finding Description
Equality that must hold: **UNIQUENESS** — at most one tenure-start block may ever be signed (locally or globally accepted) per tenure, and this must hold identically for every signer regardless of which chainstate module (v1 or v2) they are running.

Root cause: v1's `validate_tenure_change_payload` only looks for a *globally* accepted block in the tenure via `get_last_globally_accepted_block` [4](#0-3) . A block that a v1 signer has itself `mark_locally_accepted`'d (i.e., signed, but not yet globally accepted because the 70% threshold hasn't been reached) is invisible to this query. v2's equivalent check was rewritten to use `get_last_signed_block`, which covers both `LocallyAccepted` and `GloballyAccepted` states, explicitly to close this gap — the v2 code comment states "Only blocks we have signed (locally or globally accepted) count here" [5](#0-4) .

Exploit flow with an unprivileged single-slot miner:
1. Miner proposes tenure-start block A for consensus hash `CH`.
2. Some signer set (mixed v1/v2 due to a mid-cycle `active_signer_protocol_version` split, computed independently per signer from gossiped `StateMachineUpdate`s via `determine_latest_supported_signer_protocol_version` [6](#0-5) ) signs A. Some v2 signers reach the pre-commit/sign threshold locally and call `mark_locally_accepted`, but the aggregate signature does not yet reach the global 70% threshold (global acceptance not yet observed by anyone).
3. Miner (or an equivocating relay) proposes a second, conflicting tenure-start block B for the same `CH`.
4. v1 signers call `check_proposal` → `validate_tenure_change_payload` → `get_last_globally_accepted_block(CH)` returns `None` (A is only locally accepted) → no `DuplicateBlockFound` → v1 signers may sign B.
5. v2 signers call `check_proposal` → `validate_tenure_change_payload` → `get_last_signed_block(CH)` returns A → `DuplicateBlockFound` → v2 signers reject B.

Existing guards do not prevent this: the node-side validation and StackerDB/P2P transport are out of scope and do not perform this duplicate check; the guard lives entirely in signer-side chainstate logic, and it is inconsistent between the two chainstate implementations that can be concurrently active across the signer set during a protocol-version transition.

### Impact Explanation
This breaks block uniqueness (Critical, chain-safety category): weight ends up split across two conflicting tenure-start blocks A and B at the same height/tenure — v2 signers' signatures back A, v1 signers' signatures back B. If the v1-signing subset plus any already-signed weight for B is sufficient, B could reach global acceptance despite a competing globally-relevant A also collecting signatures, i.e. a genuine equivocation/fork at the signer level rather than merely a stalled tenure. This is a shared, node-independent vulnerability (any relayed dual proposal during the version-split window triggers it for every affected v1 signer), and it is repeatable each time the protocol-version negotiation results in a mixed v1/v2 signer set for a given tenure.

### Likelihood Explanation
Preconditions: (1) the reward-cycle/tenure boundary where `active_signer_protocol_version` computation is genuinely split across the signer set — plausible during any live upgrade rollout since the version is negotiated independently per signer from asynchronously-gossiped `StateMachineUpdate` messages (see `determine_active_signer_protocol_version` / `check_block_against_state` branching on `state_version.uses_global_state()` [7](#0-6) ); (2) a v1-tracked block A that is locally-accepted but not yet globally-accepted, a normal transient state in the block-signing protocol itself. Attacker cost is exactly one miner slot plus the ability to gossip a second proposal — no majority signer control, no compromised keys, no local host access, matching the stated unprivileged-attacker model. The bug is deterministic given these preconditions, not probabilistic, so it is fully repeatable whenever the split state and a locally-accepted-only block coincide.

### Recommendation
Backport the v2 fix to v1: change `validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` (line 505-506) to call `signer_db.get_last_signed_block(&block.header.consensus_hash)` instead of `get_last_globally_accepted_block`, mirroring the logic and comment already present in v2 (`stacks-signer/src/chainstate/v2.rs`, lines 340-348). Add a regression test analogous to `check_tenure_change_rejects_when_locally_accepted_block_exists` (currently only in `chainstate/tests/v2.rs`) to `chainstate/tests/v1.rs`.

    pub fn determine_latest_supported_signer_protocol_version(&self) -> Option<u64> {
        let mut protocol_versions = HashMap::new();
        for (address, update) in &self.address_updates {
            let Some(weight) = self.address_weights.get(address) else {
                continue;
            };
            let entry = protocol_versions
                .entry(update.local_supported_signer_protocol_version)
                .or_insert_with(|| 0);
