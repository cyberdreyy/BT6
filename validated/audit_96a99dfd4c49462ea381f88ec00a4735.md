### Title
Stale instant-withdraw receipts hidden in the global `pendingInstantWithdraws` bucket escape default-finalization accounting and are later paid at par, draining the vault - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks instant-withdraw receipts both globally (`pendingInstantWithdraws`, `instantWithdrawsRequests[user]`) and per epoch (`instantWithdrawsRequestsByEpoch`, `instantWithdrawClaimsByEpoch`). At default finalization, only the *current* epoch's instant claims are added to the recovery basis (`defaultPendingClaimBasis`) and the prefunded reserve is computed as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`. Instant receipts recorded in earlier epochs are therefore invisible to both the claim basis and the reserve computation — like an SCM fd hidden in a SOCKMAP queue that neither GC pass can inspect. After finalization, `_claimDefaultedInstantWithdrawRequest` clears only the default-epoch bucket, so the stale remainder in `instantWithdrawsRequests[_user]` is paid at par through `_transferFundedClaim`, spending underlying that belongs to current-epoch instant claimants.

### Finding Description
- `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, `pendingInstantWithdraws` and `instantWithdrawsRequests[user]` (lines 366–374).
- `collectInstantWithdrawFunds` only decrements the *global* `pendingInstantWithdraws` (line 401); per-user and per-epoch entries are never touched. So if the CDO collects instant funds covering only part of the queue (or collects for a newer epoch while an older receipt is pending), a stale per-epoch receipt persists indefinitely.
- `defaultPendingClaimBasis` adds only `instantWithdrawClaimsByEpoch[epochNumber]` (lines 644–649). A stale receipt from epoch N < defaultEpoch contributes to `pendingInstantWithdraws` but contributes zero to `basis`.
- `_defaultPrefundedInstantReserve` computes `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` (lines 716–723). If the stale amount makes `pendingInstantWithdraws` larger than the current-epoch basis, prefunded reserve is computed as 0 even though the strategy already holds collected underlying earmarked for those current-epoch claims — the collected funds are not added to `defaultRecoveryReserve`.
- After `finalizeDefaultRecovery`, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest` (clears only `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`), then unconditionally pays the leftover `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim` (lines 380–393, 842–856). The reserve guard in `_transferFundedClaim` protects only `defaultRecoveryReserve`, not the unaccounted collected funds.

Net effect: a holder of a stale (never-funded or partially funded) instant receipt escapes the recovery haircut entirely and is paid 1:1 from underlying that `finalizeDefaultRecovery` failed to reserve for the genuine current-epoch instant claimants.

### Impact Explanation
Direct theft plus insolvency of the recovery pool. The attacker (any KYC-passing lender who left an unfunded instant receipt outstanding) claims their full stale receipt at par. The underlying they receive was collected for other users' current-epoch instant claims but was excluded from `defaultRecoveryReserve` due to the `instantBasis - pendingInstant` subtraction going negative. Consequently, when legitimate claimants call `_claimDefaultedInstantWithdrawRequest`, `_transferDefaultRecovery` reverts on `defaultRecoveryReserve -= _amount` (underflow) or the vault balance is insufficient — permanent freezing of unclaimed recovery up to the size of the stale receipt.

### Likelihood Explanation
Requires an instant-withdraw receipt that remains recorded across an epoch boundary while `pendingInstantWithdraws` stays nonzero — e.g., partial collection of the instant queue at a stopEpoch, or an instant request made in an epoch whose claims were funded only partially before the next epoch. The comment at line 923 ("Pending instant withdrawals are never cleared automatically") confirms stale instant pending is an expected state. Then borrower default with `pendingInstantWithdraws != 0` triggers the mis-accounting deterministically. Attacker needs no privilege beyond holding tranche tokens during a buffer period where instant withdrawals are enabled.

### Recommendation
At `finalizeDefaultRecovery`, account for *all* outstanding instant receipts, not just the current epoch: include every epoch's unsettled instant basis in `defaultPendingClaimBasis` (or bound the global `pendingInstantWithdraws` by total unsettled claims), and compute the prefunded reserve as `min(instantClaimsTotal, collected)` rather than `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws`. In `_claimDefaultedInstantWithdrawRequest`, clear and haircut all epochs' instant receipts, not only `defaultRecoveryEpoch`, so no receipt can fall through to the at-par `_transferFundedClaim` path unfunded.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// Epoch N (instant enabled): userA requests instant withdraw of A.
// Manager stops epoch; CDO collects only part of the instant queue,
// so pendingInstantWithdraws == dustA > 0 and
// instantWithdrawsRequestsByEpoch[userA][N] stays set.

// Epoch N+1 (default epoch): userB requests instant withdraw of B.
// startEpoch moves partial cash; borrower repays nothing; stopEpoch(0,0) -> defaulted().
// Now: pendingInstantWithdraws == A_rem + B_pending,
//      instantWithdrawClaimsByEpoch[N+1] == B.

// finalizeDefaultRecovery(recovered, source):
//   basis  = pendingWithdraws + B          // A_rem missing from basis
//   prefundedReserve = B > pending ? B - pending : 0  // 0 if A_rem+B_pending >= B
// The collected instant cash already in the vault is NOT reserved.

// Post-finalization:
// userB claims default epoch -> reserve ok.
// userA calls claimInstantWithdrawRequest: _claimDefaultedInstantWithdrawRequest
// clears nothing (nothing at defaultEpoch), then instantWithdrawsRequests[userA]
// pays A at par via _transferFundedClaim -> steals B's collected cash.
// userB's remaining claim reverts / underpays => permanent freezing of unclaimed recovery.
assertEq(underlying.balanceOf(userA) - pre, A);           // paid at par, no haircut
vm.expectRevert();                                        // userB's haircutted claim now fails
cdo.claimInstantWithdrawRequest(userB);
```

Uncertainty note: I could not verify within the available iterations exactly which CDO path leaves a partially collected `pendingInstantWithdraws` across epochs (the precise `stopEpoch`/instant-trigger conditions in `IdleCDOEpochVariant.sol`), so the PoC assumes partial collection is reachable via the normal instant-withdraw flow. The accounting asymmetry itself — global pending vs per-epoch basis/reserve and the epoch-scoped clearing in `_claimDefaultedInstantWithdrawRequest` — is confirmed in `IdleCreditVault.sol` lines 366–403, 644–649, 716–723, and 842–856.
