### Title
Unauthenticated Gateway Message Flood Exhausts Global RequestCache Capacity, Denying Service to Legitimate Requesters - (File: core/services/gateway/handlers/common/requestcache.go)

### Summary
`requestCache.NewRequest` enforces a single global capacity bound (`maxCacheSize`) shared by all senders, with no per-sender quota or allowlist check performed before the entry is admitted. An attacker who can submit arbitrarily many signed gateway messages with distinct `MessageId`s can fill this shared cache to `maxCacheSize`, causing subsequent legitimate `NewRequest` calls (from any other sender) to be rejected with `"request cache is full"` until attacker entries expire via `timeout`.

### Finding Description
`requestCache[T].NewRequest` keys pending requests by `globalId{sender, messageId}` and checks a single shared counter against `maxCacheSize`: [1](#0-0) 
There is no per-sender limit, allowlist gate, or authentication requirement inside `NewRequest` itself — the only requirement to occupy a cache slot is a unique `(sender, MessageId)` pair, and `sender`/`MessageId` are attacker-supplied fields on the incoming `api.Message`. Any client capable of producing a validly-formed, self-signed gateway message (the rules explicitly treat "any address sending signed gateway requests" as an unprivileged attacker, since generating a signing key/address requires no authorization) can generate an unbounded number of distinct `(sender, MessageId)` pairs and call `NewRequest` repeatedly through the gateway ingress path until `len(c.cache) >= maxCacheSize`. Each admitted entry occupies a slot for the full `timeout` duration (via the `time.AfterFunc` timer) before being evicted, so an attacker can sustain saturation by continuously injecting new fake messages faster than the timeout clears old ones. Once full, all subsequent legitimate callers (including honest users) receive the `"request cache is full"` error and are denied service, an availability/isolation violation between unrelated senders using the same shared cache instance.

### Impact Explanation
This causes denial of service: legitimate low-privilege users' `NewRequest` calls are rejected once the shared cache reaches capacity, matching the "denial of service preventing legitimate users from getting responses" bounty impact class. The impact is bounded to disruption of gateway request/response correlation for whichever handler subsystem shares this cache instance — it does not itself lead to authentication bypass, secret disclosure, or fund movement.

### Likelihood Explanation
Feasibility depends on: (1) which handler wires `RequestCache` for externally-reachable gateway requests, and (2) whether an outer layer (allowlist, per-sender rate limiter, workflow-owner authorization) filters requests before they reach `NewRequest`. In the reviewed code, `NewRequestCache`/`RequestCache` usage in this snapshot of the repo is only exercised from unit tests [2](#0-1) ; I could not locate a production call site in this indexed codebase that wires a live `requestCache` instance to an externally reachable `HandleJSONRPCUserMessage`/`HandleLegacyUserMessage` path. Some gateway/capability handlers examined (e.g. `core/capabilities/vault/gw_handler.go`) instead implement authorization/allowlist checks (`AuthorizeRequest`) before processing, and `gateway.go`'s `ProcessRequest` performs message-ID length limits but no visible per-sender quota [3](#0-2) . Because the exact production wiring of this `RequestCache` type to a live, unauthenticated ingress endpoint could not be confirmed with the available index, this should be treated as an unconfirmed/best-effort finding pending verification of the actual call site.

### Recommendation
If `requestCache` is (or will be) used for externally reachable requests, add a per-sender quota (e.g., max in-flight entries per `sender`) in addition to the global `maxCacheSize`, and/or require sender allowlisting/authorization before `NewRequest` admits an entry, mirroring the pattern already used in `core/capabilities/vault/gw_handler.go`'s `AuthorizeRequest` flow.

### Proof of Concept
Go unit test plan (extending `requestcache_test.go`):
1. Create `cache := common.NewRequestCache[requestState](time.Hour, N)` with small `N` (e.g., 5).
2. In a loop, call `cache.NewRequest(lggr, &api.Message{Body: api.MessageBody{MessageId: fmt.Sprintf("attacker-%d", i), Sender: "0xattacker"}}, callback, state)` for `i` in `0..N-1`, asserting `require.NoError`.
3. Then attempt `cache.NewRequest(lggr, &api.Message{Body: api.MessageBody{MessageId: "victim-1", Sender: "0xvictim"}}, callback, state)` and assert it returns `errors.New("request cache is full")`, demonstrating a legitimate different-sender request is denied purely due to attacker-filled capacity.
4. (For full end-to-end confirmation) trace/instrument the actual production handler that constructs a `requestCache` instance and repeat the same flood via its externally reachable `HandleJSONRPCUserMessage`/`HandleLegacyUserMessage` entry point to confirm no allowlist/quota intercepts the attacker messages before `NewRequest`.
