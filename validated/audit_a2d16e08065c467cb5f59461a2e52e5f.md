### Title
External Initiator credential is treated as an authenticated User, bypassing the "EIs not allowed" numeric-job-ID restriction in `PipelineRunsController.Create` - ([File: core/web/pipeline_runs_controller.go])

### Summary
`auth.AuthenticateExternalInitiator` fabricates a `*clsessions.User{Role: clsessions.UserRoleRun}` and stores it under the same `SessionUserKey` used for real user sessions. This makes `auth.GetAuthenticatedUser` return `ok=true` for a pure EI-credentialed request, satisfying both `auth.RequiresRunRole` and the `isUser` check inside `PipelineRunsController.Create`, even though the code's own comment says EI credentials must not be allowed to run int-ID jobs.

### Finding Description
The route is registered in `core/web/router.go`:
```go
userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateExternalInitiator,
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
``` [1](#0-0) 

When a request carries only EI headers (`X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret`), `AuthenticateExternalInitiator` succeeds and explicitly does:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [2](#0-1) 

This is not a silent `ok=false` case as the question hypothesized — the middleware actively fabricates a `*clsessions.User` object and stores it under `SessionUserKey`, the exact key `GetAuthenticatedUser` reads:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
}
``` [3](#0-2) 

Consequently `auth.RequiresRunRole` sees `ok=true` and `user.Role == UserRoleRun` (`!= UserRoleView`), so the request passes through to the handler:
```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok { ... }
		if user.Role == clsessions.UserRoleView { ... }
		handler(c)
	}
}
``` [4](#0-3) 

Inside `PipelineRunsController.Create`, the code explicitly intends to block EIs from the numeric-ID run path, but the check it uses cannot distinguish a real user from an EI-fabricated user, since both are `*clsessions.User` under `SessionUserKey`:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
    ...
}
``` [5](#0-4) 

This confirms identity confusion: an EI credential is indistinguishable from a real user at this checkpoint, contradicting the comment's intent. The only way to tell an EI apart at this point would be to also check `auth.GetAuthenticatedExternalInitiator(c)` and reject if present, which `Create` does not do.

### Impact Explanation
An EI credential holder can trigger `prc.App.RunJobV2(ctx, jobID, nil)` for **any numeric job ID** on the node, completely bypassing the intended per-job `externalInitiators` allow-list mechanism (which is designed to scope an EI to only the specific webhook job(s) that name it, referenced by UUID). This matches the Chainlink bounty "unauthorized job run" impact class, since it lets a restricted, job-scoped credential holder run pipeline executions for jobs it was never authorized against, by numeric job ID.

However, `RunJobV2` itself is explicitly gated:
```go
// Only used for local testing, not supported by the UI.
func (app *ChainlinkApplication) RunJobV2(ctx context.Context, jobID int32, meta map[string]any) (int64, error) {
	if build.IsProd() {
		return 0, errors.New("manual job runs not supported on secure builds")
	}
	...
}
``` [6](#0-5) 
This means the concrete impact is confined to non-production (`build.IsProd() == false`) builds; on production/secure builds the handler is a dead end regardless of who reaches it. The authorization-bypass/identity-confusion bug in `auth.RequiresRunRole`/`GetAuthenticatedUser`/`PipelineRunsController.Create` is real, but its exploitable impact is limited by this separate build-mode gate.

### Likelihood Explanation
- Precondition: a valid, currently-active EI accesskey/secret for the target node (obtainable by anyone who was granted an EI credential for even one unrelated job).
- No session cookie or user API token is required.
- The request path `POST /v2/jobs/:ID/runs` with `:ID` as an integer is directly reachable and unauthenticated apart from the EI headers.
- Feasibility is high and fully repeatable, but the ultimate `RunJobV2` execution only proceeds on non-production builds; on production builds the request reaches `prc.Create`'s `isUser` branch (proving the identity-confusion bug) but `RunJobV2` immediately errors out.

### Recommendation
In `core/web/pipeline_runs_controller.go`, explicitly reject requests authenticated as an External Initiator before treating them as a "user" for the numeric-ID path, e.g.:
```go
if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI {
    jsonAPIError(c, http.StatusUnauthorized, errors.New("external initiators cannot run jobs by numeric ID"))
    return
}
```
More fundamentally, avoid overloading `SessionUserKey` with a fabricated `User` object for EI authentication in `core/web/auth/auth.go`'s `AuthenticateExternalInitiator`; instead, introduce a distinct marker/role (or rely solely on `SessionExternalInitiatorKey`) so `GetAuthenticatedUser` never returns `ok=true` for EI-only requests, preserving identity separation across authentication methods.

### Proof of Concept
Handler-level integration test (Go, using `httptest` similar to existing tests in `core/web/router_test.go` and `core/services/job/runner_integration_test.go`):
1. Start app with a non-prod build tag (as tests normally run), create a job with a numeric ID via the edit-role user flow.
2. Create an External Initiator via `cltest.CreateExternalInitiatorViaWeb`, obtaining `AccessKey`/`Secret`.
3. Send `POST /v2/jobs/<numericJobID>/runs` using only headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (no session cookie, no `X-API-KEY`).
4. Assert that the response is **not** `401 Unauthorized` and instead proceeds to attempt `RunJobV2` (e.g., returns `200`/pipeline run resource in a non-prod test build, or an internal error from `RunJobV2` rather than an auth rejection) — proving that `prc.Create`'s `isUser` branch was entered for an EI-only credential.
5. As a control, assert that a request with a job UUID (webhook-type reference) from the same EI still correctly reaches the webhook-removed rejection path (as in `TestRunner_WebhookJobRemoved`), confirming EI auth succeeded and only the numeric-ID branch is the point of identity confusion.
