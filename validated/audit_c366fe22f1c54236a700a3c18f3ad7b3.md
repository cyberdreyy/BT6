### Title
Loss-adjusted withdraw receipts escape their haircut when `lossRecoveryPriceByEpoch` is keyed on a different epoch than `lastWithdrawRequest` — (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The kernel bug is a reference released too early: once a padata lands on `queue->serial.list`, the consumer can free `pd` before the producer finished using it; the fix grabs the next item before releasing the lock. The analog in `IdleCreditVault` is the single-slot "reference" `lastWithdrawRequest[_user]` versus the per-epoch receipt ledger `withdrawsRequestsByEpoch[_user][epoch]`. Both the re-request guard in `requestWithdraw` and the haircut claim in `_claimLossAdjustedWithdrawRequest` resolve the loss epoch exclusively through `lastWithdrawRequest[_user]`, while `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` at whatever `epochNumber` is current when the CDO calls it during `stopEpoch`. If those two keys desynchronize — i.e., `epochNumber` is bumped (in `deposit()`, called from the stop flow) before `collectWithdrawFunds` writes the price — the receipt under the old epoch key is never matched to its haircut, and the aggregate `withdrawsRequests[_user]` is later paid at par through `_claimFundedWithdrawRequest`. The "reference" (the pending-loss epoch pointer) is dropped before the next pending item is secured.

### Finding Description
Three code fragments interact:

1. `collectWithdrawFunds` writes the haircut keyed by the *current* `epochNumber` at call time: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` [1](#0-0) 
2. `epochNumber` is incremented inside `deposit()` whenever the CDO deposits while `isEpochRunning()` — i.e., during the `stopEpoch` deposit [2](#0-1) 
3. Both guard sites resolve the loss epoch only via `lastWithdrawRequest[_user]`:
   - `requestWithdraw` reads `lossEpoch = lastWithdrawRequest[_user]` and only reverts when `lossRecoveryPriceByEpoch[lossEpoch] != 0` *and* the user still holds a receipt under that same key [3](#0-2) 
   - `_claimLossAdjustedWithdrawRequest` applies the haircut only to `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` [4](#0-3) 

Meanwhile the claimable amount in `_claimFundedWithdrawRequest` is the aggregate `withdrawsRequests[_user]`, which is only decremented per-epoch inside `_clearWithdrawClaimForEpoch` — a function reached only through the keyed lookup above [5](#0-4) [6](#0-5) 

If `epochNumber` is incremented before `collectWithdrawFunds` runs (order inside `stopEpoch`/`stopEpochWithDuration`), a request made in epoch N is stored as `withdrawsRequestsByEpoch[u][N]` with `lastWithdrawRequest[u] = N`, but the loss price lands under `lossRecoveryPriceByEpoch[N+1]`. The re-request guard then reads `lossRecoveryPriceByEpoch[N] == 0` and does not block a new request; the claim path reads the same zero slot, skips the haircut, and `_claimFundedWithdrawRequest` pays the full aggregate `withdrawsRequests[u]` at par once the gating epoch passes.

### Impact Explanation
A receipt that should pay `claimBasis * lossRecoveryPrice / 1e18` instead pays `claimBasis` in full. The excess is `claimBasis * (1 - lossRecoveryPrice)` of underlying pulled from the strategy's funded pool — the same pool backing all other pending/funded receipts — so the loss intended for pending withdrawers is re-socialized onto funded claimants, and the last claimants become unclaimable (insolvency of the funded bucket). This is a direct theft/loss-socialization bypass, not a temporary freeze.

### Likelihood Explanation
Exploitation requires only an unprivileged KYC'd lender calling `cdoEpoch.requestWithdraw` during the affected epoch and `claimWithdrawRequest` after the next epoch boundary — the honest owner/manager `stopEpochWithDuration` call supplies the loss. No privileged misbehavior, no oracle manipulation, no reentrancy is needed. The preconditions are: a realized loss at stopEpoch creating a non-zero `lossRecoveryPrice`, and the intra-transaction ordering where `deposit()` bumps `epochNumber` ahead of `collectWithdrawFunds` (or, equivalently, any flow where the request epoch key and the stored loss-price key diverge). Caveat: I verified the key divergence surfaces in `IdleCreditVault`, but I did not fully trace the CDO-side `stopEpoch` ordering of `deposit()` vs. `collectWithdrawFunds` within this scan; if the price write provably precedes the increment in every path, the divergence does not manifest and the guard holds.

### Recommendation
Mirror the kernel fix — secure the next reference before releasing the current one. Concretely, in `requestWithdraw` and `_claimLossAdjustedWithdrawRequest`, do not trust `lastWithdrawRequest` as the sole loss-epoch pointer; scan or track per-epoch receipts (e.g., revert in `requestWithdraw` if *any* `withdrawsRequestsByEpoch` entry with a non-zero `lossRecoveryPriceByEpoch` remains unclaimed), or key `lossRecoveryPriceByEpoch` by the request epoch captured before any `epochNumber` mutation (pass the stopped-epoch id from the CDO into `collectWithdrawFunds` rather than reading live `epochNumber`).

### Proof of Concept
Foundry fork sketch (harness patterns from `test/foundry/IdleCreditVault.t.sol`):

```solidity
// 1. User deposits into AA, epoch starts, user calls cdoEpoch.requestWithdraw(0, AA)
//    => withdrawsRequestsByEpoch[u][N] = X; lastWithdrawRequest[u] = N
// 2. Warp past epochEndDate; manager calls cdoEpoch.stopEpochWithDuration
//    with a partial loss so collectWithdrawFunds receives _amount < pendingBasis.
//    Assert key divergence:
assertEq(strategy.epochNumber(), N + 1);
assertEq(strategy.lossRecoveryPriceByEpoch(N),   0);        // guard slot: empty
assertGt(strategy.lossRecoveryPriceByEpoch(N+1), 0);        // haircut stored here
// 3. User requests a new withdraw (guard passes because slot N is empty)
// 4. After epoch N+1 ends, user calls cdoEpoch.claimWithdrawRequest()
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
// BUG: paid X at par instead of X * lossRecoveryPrice / 1e18
assertGt(underlying.balanceOf(user) - balPre, X * strategy.lossRecoveryPriceByEpoch(N+1) / 1e18);
```

The assertion that must be confirmed on the fork is step 2 (whether `lossRecoveryPriceByEpoch` is indexed by `N` or `N+1`); if it lands under `N`, the guard correctly blocks step 3 and the analog collapses to a non-issue.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
