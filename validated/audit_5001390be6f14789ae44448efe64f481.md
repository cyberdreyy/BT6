### Title
APR0 withdraw receipts in a loss epoch escape the `lossRecoveryPriceByEpoch` haircut and are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` keeps two parallel bookkeeping structures for the same pending receipt: `withdrawsRequestsByEpoch[user][epoch]` for normal requests and `apr0Users[user]` (`principal`/`principalEpoch`, later `settledPrincipal`) for APR=0 requests. The loss-epoch guard that forces a user to claim a haircutted receipt before opening a new one, and the loss-adjusted claim path, only key off the normal per-epoch structure. An APR0 receipt created in an epoch that later records a `lossRecoveryPriceByEpoch` is therefore settled and paid at par by `_claimFundedWithdrawRequest`, while the funded cash for that epoch was already reduced by the haircut in `collectWithdrawFunds`. This is the on-chain analog of unsynchronized access to shared data: two structures representing one logical receipt diverge, and the reader/writer that should see the haircut sees a stale par value instead.

### Finding Description
In `requestWithdraw` (lines 259-294), normal requests record `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, while APR0 requests go through `_requestWithdrawApr0`, which writes only `apr0Users[_user]` and `apr0TotalPrincipal`. Both kinds increment `pendingWithdraws`.

When `stopEpoch`/`stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` sets `lossRecoveryPriceByEpoch[epochNumber]` to `funded * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws`; only the reduced amount is transferred to the strategy (lines 411-429). The pre-request guard (lines 261-271) only blocks a new request while `apr0Users[user].principal != 0` and points at the loss epoch — i.e. only before settlement.

On claim (lines 301-350), `_claimLossAdjustedWithdrawRequest` resolves receipts through `lastWithdrawRequest`/`withdrawsRequestsByEpoch`, then `_claimFundedWithdrawRequest` unconditionally calls `_settleApr0`, moves `principal` to `settledPrincipal`, and pays `settledPrincipal + settledInterest` at par via `_transferFundedClaim`. Nothing in the funded path subtracts the `lossRecoveryPriceByEpoch` haircut from the APR0 bucket even though its principal was part of the `pendingBasis` that the loss was charged against.

Net effect: `pendingBasis` for the loss epoch included the APR0 principal, the funded amount was `pendingBasis - pendingLoss`, but the APR0 user can withdraw principal + interest at full value, consuming underlying that the haircut assumed would be burned.

### Impact Explanation
Direct theft / insolvency of the claim reserve. The strategy holds `pendingBasis * lossRecoveryPrice` underlying for that epoch's receipts. Each APR0 claimant of that epoch withdraws principal (plus any settled interest) at par, so the first claimer(s) drain more than their share and later loss-epoch claimants — normal receipt holders and other APR0 users — are left with claims that revert on insufficient balance, i.e. permanent freezing of unclaimed recovery funds. Loss scales with the APR0 principal share of `pendingBasis` and the haircut size (up to the full pending balance on near-total loss).

### Likelihood Explanation
Requires a vault operating with `unscaledApr == 0` (APR0 mode is an explicitly supported, tested configuration) and a `stopEpochWithDuration` loss — or borrower underfunding — in the epoch containing APR0 requests. An unprivileged KYC'd lender can create the APR0 receipt with a normal `requestWithdraw`; the loss event itself is part of the ordinary credit lifecycle and does not require attacker control of the borrower. Claiming is permissionless through `cdoEpoch.claimWithdrawRequest()`.

### Recommendation
Make the APR0 bucket loss-epoch aware: either record APR0 requests into `withdrawsRequestsByEpoch` as well (so `lossRecoveryPriceByEpoch` claims cover them), or in `_settleApr0`/`_claimFundedWithdrawRequest` apply `lossRecoveryPriceByEpoch[principalEpoch]` to `principal`/`settledPrincipal` before paying, and extend the `requestWithdraw` guard so a settled-but-unclaimed APR0 receipt from a loss epoch blocks new requests the same way an unsettled one does.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVaultApr0Loss.t.sol
// SPDX-License-Identifier: MIT
pragma solidity 0.8.10;
import "./IdleCreditVault.t.sol"; // reuse existing harness

contract Apr0LossEpochClaimPoC is IdleCreditVaultTest {
    function testApr0ReceiptEscapesLossEpochHaircut() external {
        // APR0 mode
        _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
        vm.prank(owner);
        cdoEpoch.setIsAYSActive(false);
        vm.prank(manager);
        IdleCreditVault(address(strategy)).setAprs(0, 0);

        // Victim and attacker deposit AA
        uint256 amount = 10_000 * ONE_SCALE;
        address attacker = makeAddr("apr0Attacker");
        _depositWithUser(attacker, amount, true);
        idleCDO.depositAA(amount);
        _transferBurnedTrancheTokens(attacker, true);
        _transferBurnedTrancheTokens(address(this), true);

        _startEpochAndCheckPrices(0);

        // Both request withdraw during the APR0 epoch (buffer phase)
        vm.prank(attacker);
        cdoEpoch.requestWithdraw(0, address(AAtranche));
        cdoEpoch.requestWithdraw(0, address(AAtranche));

        // Epoch stops with a realized loss: borrower returns less than pending basis
        vm.warp(cdoEpoch.epochEndDate() + 1);
        uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
        uint256 funded = pending / 2; // 50% loss
        deal(defaultUnderlying, borrower, funded);
        vm.prank(manager);
        cdoEpoch.stopEpochWithDuration(0, epochDuration, pending - funded);

        uint256 lossEpoch = IdleCreditVault(address(strategy)).epochNumber();
        assertEq(
            IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(lossEpoch),
            funded * 1e18 / pending
        );

        // Attacker claims: receipt for the loss epoch is paid at PAR
        uint256 balPre = underlying.balanceOf(attacker);
        vm.prank(attacker);
        cdoEpoch.claimWithdrawRequest();
        uint256 attackerPaid = underlying.balanceOf(attacker) - balPre;

        // Attacker's fair share is pending/2 * lossRecoveryPrice = funded/2
        // but he receives his full principal + settled interest (> funded/2),
        // leaving the strategy short for the second claimant.
        assertGt(attackerPaid, funded / 2, "apr0 receipt bypassed loss haircut");

        // Victim claim now reverts / is underpaid: strategy holds only
        // funded - attackerPaid < victim's haircutted share.
        vm.expectRevert(); // insufficient underlying in strategy
        cdoEpoch.claimWithdrawRequest();
    }
}
```

Caveat: I was not able to read `_claimLossAdjustedWithdrawRequest`/`_transferFundedClaim` in full within available iterations; the PoC assumes the loss-adjusted path resolves receipts via `withdrawsRequestsByEpoch` only (consistent with the guard comment at `IdleCreditVault.sol:268-269` and the claim ordering at lines 312-313). If that path already consumes `apr0Users` for the loss epoch, the finding collapses; the Foundry test above settles it definitively.
