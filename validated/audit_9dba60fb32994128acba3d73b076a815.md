### Title
Signer permanently drops (never accepts/rejects) a proposal on any non-2xx/non-429 `/v3/block_proposal` response, e.g. the node's independent `block_proposal_max_age_secs` staleness gate — reintroducing the fixed "replication void" livelock - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The Sherlock report's bug class is an inconsistency between two independent bounds that are supposed to represent "the same" validity window, checked in different places with different constants. In this repo, the signer's own staleness gate in `handle_block_proposal` uses the signer-local `self.block_proposal_max_age_secs`, while the stacks-node's `/v3/block_proposal` RPC endpoint enforces its own, independently-configured `block_proposal_max_age_secs` (`stackslib/src/net/api/postblock_proposal.rs:1223-1234`, `stackslib/src/net/connection.rs:44-45`, `DEFAULT_BLOCK_PROPOSAL_MAX_AGE_SECS`). These two values live in separate config files (signer config vs. node config) and are not required to match. When the node's threshold is tighter than the signer's, the node answers a proposal the signer already accepted as "not too old" with an immediate HTTP 422 rather than a `BlockValidateReject`. The client-side handling of that response, `submit_block_for_validation` in `stacks-signer/src/v0/signer.rs:2585-2645`, only special-cases HTTP 429 (queues a pending re-submission); any other failure status (422, 400, etc.) falls to the generic `Err(e)`/`else` branch which only logs a warning — it does not send any `BlockRejection`, does not requeue, and does not otherwise mark the block. This exactly reproduces the "silent drop" livelock class that `stacks-signer/changelog.d/replication-void-fix.changed` says was already fixed for the signer's own local staleness check, but the fix (`ProposalTooOld`) was not extended to cover the equivalent staleness rejection coming back from the node's mirrored, independently-tunable bound.

### Finding Description
- Signer-side staleness gate (loose bound): [1](#0-0) 
This deliberately rejects (with `ProposalTooOld`) proposals older than `self.block_proposal_max_age_secs`; anything younger passes through to `submit_block_for_validation`.

- Node-side staleness gate (independently configured bound): [2](#0-1) 
This uses `network.get_connection_opts().block_proposal_max_age_secs`, a value taken from the *node's* config (`stackslib/src/config/mod.rs:3883-3888`, default `DEFAULT_BLOCK_PROPOSAL_MAX_AGE_SECS = 600` in `stackslib/src/net/connection.rs:44-45`), and returns a bare HTTP 422 with no `BlockValidateReject` body, before any actual chainstate validation.

- Client submission path that swallows this response: [3](#0-2) 
`stacks_client.submit_block_for_validation` returns `Err(ClientError::RequestFailure(status))` for the 422. Only `status == 429` is handled (queues a pending re-submission via `insert_pending_block_validation`). Every other status, including 422, falls into `warn!("{self}: Received non-429 status from stacks node: {status}")` and returns — no `BlockRejection` is created, `submitted_block_proposal` remains unset, and the block is never requeued for (re-)validation, nor is `check_pending_block_validations` invoked for it.

Because the signer already inserted the `BlockInfo` for this proposal into `signer_db` before calling `submit_block_for_validation` (`stacks-signer/src/v0/signer.rs:1717-1719`), the signer is now permanently "stuck": it holds a `BlockInfo` in the `Unprocessed`/pending state that will never transition (no accept, no reject, no automatic retry), and it never sends a `BlockResponse` for that `signer_signature_hash` at all.

### Impact Explanation
This falls in the same class the maintainers already treated as a liveness bug worth a dedicated fix (`ProposalTooOld` / `replication-void-fix.changed`, documented in `stacks-node/src/tests/signer/v0/proposal_replication_void.rs:157-189`): a miner's `propose_block` resend loop only exits on rejection weight reaching ~30%, a burn/stacks tip change, or the block landing in the staging DB. If enough signers in the set are configured with a `block_proposal_max_age_secs` looser than the node's own threshold (a very plausible default/operator drift, since these are two entirely separate knobs on two separate binaries/config files with independent defaults), those signers will silently drop every stale-to-the-node re-proposal instead of emitting `ProposalTooOld` rejections. The 30% rejection weight needed for the miner to give up and re-mine may never accumulate, reproducing the exact tenure livelock the `ProposalTooOld` fix was meant to eliminate — this time via the RPC failure path rather than the signer's own local timestamp check. This is a liveness wedge on the affected signers (they never sign or reject the stuck proposal) and can stall block production for the tenure.

### Likelihood Explanation
No majority or malicious signer key is required — a single miner re-proposing a stale block, combined with default/typical configuration where the node-side and signer-side max-age values simply aren't kept in lockstep (they are set in different config files: `sample/conf/*.toml` for the node vs `sample/conf/signer/*.toml` for the signer), is enough to trigger the non-429 error branch. Any transient non-2xx/non-429 response from `/v3/block_proposal` (422 for staleness being the clearest, deterministic example) reaches the same silently-dropped code path.

### Recommendation
In `stacks-signer/src/v0/signer.rs::submit_block_for_validation`, treat any non-429 `RequestFailure` (and other submission errors) the same way the local staleness check is now handled: create and broadcast a `BlockRejection` (e.g. a new `RejectReason::ConnectivityIssues`/`ProposalTooOld`-style variant reflecting "node rejected without validating") instead of only logging a warning, so the miner's rejection-weight mechanism still functions. Alternatively/additionally, align the two `block_proposal_max_age_secs` bounds so the node's threshold is never tighter than any signer's, or have the signer surface the node's HTTP error body (which conveys the specific reason) and map it to an explicit rejection rather than dropping it.

### Proof of Concept
1. Configure a signer with `block_proposal_max_age_secs = 600` (or leave default) while the paired stacks-node is configured with a tighter `block_proposal_max_age_secs` (e.g. 60), which is a legal, independent configuration in both `sample/conf/signer/*.toml` and node `[connection_options]`.
2. Miner proposes block `B` with a header timestamp aged, say, 90s.
3. Signer's local check in `handle_block_proposal` (`stacks-signer/src/v0/signer.rs:1606-1628`) passes (90s < 600s), so the proposal is stored via `insert_block` and forwarded via `submit_block_for_validation`.
4. Node's RPC handler (`stackslib/src/net/api/postblock_proposal.rs:1223-1234`) computes `90s + 60s < now` → true, and returns HTTP 422 without calling `validate`.
5. `stacks_client.submit_block_for_validation` returns `Err(ClientError::RequestFailure(422))`.
6. In `stacks-signer/src/v0/signer.rs:2627-2643`, `status.as_u16() != 429`, so execution falls to `warn!("{self}: Received non-429 status from stacks node: {status}")` and returns; no rejection is ever sent for `B`'s `signer_signature_hash`, and the stored `BlockInfo` is never revisited.
7. Repeat across enough of the signer set (each independently under-configured relative to their node) and the miner's resend loop for `B` never accumulates 30% rejection weight, reproducing the tenure livelock that `ProposalTooOld`/`replication-void-fix` was introduced to prevent.
