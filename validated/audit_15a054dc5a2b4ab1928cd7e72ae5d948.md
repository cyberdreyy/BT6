### Title
Stop-epoch loss haircut is indexed by the post-increment `epochNumber`, so loss-adjusted withdraw receipts are claimed at par instead of at `lossRecoveryPriceByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is already bumped by `deposit()` earlier in the same `stopEpoch` flow, while pending receipts are keyed by the epoch in which `requestWithdraw` ran (`lastWithdrawRequest[_user]` / `withdrawsRequestsByEpoch[_user][requestEpoch]`). `_claimLossAdjustedWithdrawRequest` looks the haircut up under `lastWithdrawRequest[_user]`, finds `0`, and returns — so the request falls through to `_claimFundedWithdrawRequest`, which pays the full pre-haircut `withdrawsRequests[_user]` at par from a strategy that only received the reduced amount. This is the direct analog of CVE-2016-7502: an index one past the intended bound reads a zero/absent slot, silently skipping the loss-adjustment logic.

### Finding Description
Receipt keying:

- `requestWithdraw` records `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `lastWithdrawRequest[_user] = currentEpoch` where `currentEpoch = epochNumber` at request time (epoch N, while the epoch is running or in the buffer keyed under N) — `contracts/strategies/idle/IdleCreditVault.sol:260-293`.
- `deposit()` increments `epochNumber` when called while the epoch is still marked running, which is exactly the `stopEpoch` path per the inline comment "deposit done on stopEpoch (before setting the var to false)" — `IdleCreditVault.sol:607-610`.
- `collectWithdrawFunds(_amount)` is invoked later in the same stop flow; when `_amount < pendingWithdraws` it writes `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` — i.e. under N+1, not N — `IdleCreditVault.sol:411-421`.
- On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` = slot N, which is `0`, so it returns early — `IdleCreditVault.sol:789-795`.
- `_claimFundedWithdrawRequest` then only requires `epochNumber > lastWithdrawRequest[_user]` (N+1 > N), clears `withdrawsRequests[_user]` entirely, burns the full receipt, and pays `amount` at par via `_transferFundedClaim` — `IdleCreditVault.sol:326-349`.

The same off-by-one poisons the re-request guard at `IdleCreditVault.sol:261-271`: `lossRecoveryPriceByEpoch[lossEpoch]` is checked under the user's *request* epoch, so the stored haircut at `lossEpoch + 1` is invisible and the guard never triggers. No other guard (skim, flags, `pendingWithdraws` — already zeroed at `collectWithdrawFunds:420`) stops the par payout.

### Impact Explanation
Insolvency / direct theft of other users' funds. Suppose `pendingWithdraws = P` and the realized loss makes the borrower fund only `P * r` (`r = lossRecoveryPrice < 1`). Every pending receipt still claims `P` at par: the strategy collected only `P * r`, so the shortfall `(P - P*r)` is paid out of underlying held for active tranche holders (or `defaultRecoveryReserve`), diluting the BB-first waterfall and stealing from LPs and/or recovery claimants. The entire `lossRecoveryPriceByEpoch` mechanism becomes dead code: `stopEpochWithDuration(_lossAmount)` losses on pending receipts are silently socialized onto remaining holders instead of the requesters. Broken invariants: fair burn (receipt tokens redeemed above their funded value) and loss waterfall (pending receipt holders escape their pro-rata loss share defined by `previewLossAdjustedWithdrawFunds`, `IdleCreditVault.sol:440-460`).

### Likelihood Explanation
Triggerable by any KYC-passing lender / tranche holder: request a withdraw during an epoch (or via the standard path that lands in `pendingWithdraws`), wait for the epoch to be stopped with a loss via `stopEpochWithDuration` (owner/manager-initiated, honest role — the attacker only sequences around it), then call `claimWithdrawRequest`. The payout is at par unconditionally. The only requirement is that `deposit()` (which bumps `epochNumber`) executes before `collectWithdrawFunds` inside `stopEpoch`, matching the documented ordering in `deposit()`. Note: this conclusion rests on that call ordering inside `IdleCDOEpochVariant.stopEpoch`/`stopEpochWithDuration`; if `collectWithdrawFunds` were invoked strictly before any `deposit()` in the same transaction, the indices would coincide and the bug would not manifest — the surrounding code comments strongly indicate deposit-first ordering, but a confirming trace of `stopEpoch` in `IdleCDOEpochVariant.sol`/`IdleCDOEpochVariantPrefunded.sol` should be the first step of the PoC.

### Recommendation
Key the loss haircut by the same epoch identifier used to key the receipts. In `collectWithdrawFunds`, store under the epoch the pending receipts were requested in — e.g. `lossRecoveryPriceByEpoch[epochNumber - 1]` if `epochNumber` is intentionally bumped first, or better, snapshot the request epoch explicitly when receipts are created (store a global `currentWithdrawEpoch` set alongside `pendingWithdraws` at `requestWithdraw`) and write `lossRecoveryPriceByEpoch` under that value. Additionally, make `_claimLossAdjustedWithdrawRequest` defensive: if `withdrawsRequestsByEpoch[_user][e]` is nonzero for *any* epoch `e` with a nonzero `lossRecoveryPriceByEpoch[e]`, route through the haircut path, and consider iterating/checking the request epoch recorded at request time rather than relying solely on `lastWithdrawRequest`.

### Proof of Concept
Foundry fork test sketch (deploy `IdleCDOEpochVariant` + `IdleCreditVault` as in `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testLossEpochIndexMismatch() external {
    // KYC user deposits during buffer, epoch starts
    uint256 tranches = _depositWithUser(user, 100e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    // user requests withdraw during running epoch N (epochNumber == N)
    uint256 reqEpoch = strategy.epochNumber();
    _requestWithdrawWithUser(user, tranches);
    assertEq(strategy.withdrawsRequestsByEpoch(user, reqEpoch), expected);

    // borrower realizes a loss; owner stops epoch with _lossAmount > 0
    // inside stopEpoch: deposit() bumps epochNumber to N+1,
    // collectWithdrawFunds(funded < pending) writes lossRecoveryPriceByEpoch[N+1]
    vm.prank(cdoEpoch.owner());
    cdoEpoch.stopEpochWithDuration(lossAmount, ...);

    assertGt(strategy.lossRecoveryPriceByEpoch(reqEpoch + 1), 0); // haircut stored at N+1
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0);     // lookup slot N is empty

    // user claims: _claimLossAdjustedWithdrawRequest finds price 0 at slot N,
    // _claimFundedWithdrawRequest pays FULL basis at par despite only funded*r collected
    uint256 stratBalPre = underlying.balanceOf(address(strategy));
    vm.prank(user); // via cdo.claimWithdrawRequest
    cdoEpoch.claimWithdrawRequest(user);
    // user received full claimBasis while strategy only collected claimBasis*r
    // -> deficit == claimBasis * (1 - r) drained from strategy balance
}
```

Expected result: `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]] == 0` while `lossRecoveryPriceByEpoch[lastWithdrawRequest[user] + 1] != 0`, and the user's payout equals the un-haircut `withdrawsRequests` basis, demonstrating the broken loss-socialization invariant.
