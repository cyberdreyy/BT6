### Title
Missing `rewards_pool` Sufficiency Guard in `redeem_fungible_staked_sui` Permanently Locks `FungibleStakedSui` Principal and Rewards in Inactive Pools — (File: `crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

---

### Summary

`redeem_fungible_staked_sui` calls `pool.rewards_pool.split(rewards_amount)` without capping `rewards_amount` to the actual pool balance. The sibling function `withdraw_rewards` (used for regular `StakedSui`) explicitly guards against this with `.min(pool.rewards_pool.value())`. Because both paths draw from the same shared `rewards_pool`, regular stakers can drain it to zero via `withdraw_rewards`. When the pool is subsequently inactive (no new rewards ever deposited), any `FungibleStakedSui` holder whose computed `rewards_amount > 0` is permanently locked out of both their rewards **and** their principal, because the `split` abort rolls back the entire transaction.

---

### Finding Description

`redeem_fungible_staked_sui` computes `rewards_amount` from the exchange rate and then unconditionally calls:

```move
// staking_pool.move line 221
sui_out.join(pool.rewards_pool.split(rewards_amount));
``` [1](#0-0) 

`Balance::split` aborts if `rewards_amount > pool.rewards_pool.value()`. The developers already identified this exact failure mode for regular `StakedSui` withdrawals and added a guard:

```move
// staking_pool.move line 439
reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value());
pool.rewards_pool.split(reward_withdraw_amount)
``` [2](#0-1) 

The comment at line 437 reads: *"This may happen when we are withdrawing everything from the pool and the rewards pool balance may be less than reward_withdraw_amount. TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN."* — confirming the developers knew `rewards_pool` can be insufficient but did not apply the same guard to `redeem_fungible_staked_sui`. [3](#0-2) 

**Shared pool, asymmetric guards.** Both `withdraw_rewards` and `redeem_fungible_staked_sui` draw from the same `pool.rewards_pool` balance. Regular stakers can drain it to zero (each call is capped by `.min()`, so no individual call fails, but collectively they exhaust the pool). Once drained, any `FungibleStakedSui` redemption with `rewards_amount ≥ 1` aborts. [4](#0-3) 

**Permanent lock in inactive pools.** When a validator leaves, `deactivate_staking_pool` sets `deactivation_epoch`. After that, `deposit_rewards` is never called for this pool, so `rewards_pool` never grows again. If regular stakers drain `rewards_pool` to zero before all `FungibleStakedSui` holders redeem, those holders are permanently locked. [5](#0-4) 

**`rewards_amount` cannot be avoided by splitting.** `rewards_amount = floor(v × total_rewards / FS)`. When the pool has accumulated rewards such that `total_rewards ≥ FS` (e.g., pool value has doubled), even redeeming `v = 1` token yields `rewards_amount ≥ 1`. The user cannot split their `FungibleStakedSui` finely enough to escape the abort. [6](#0-5) 

**Public entry path.** `redeem_fungible_staked_sui` is `public(package)` and is called from `sui_system.move` and `sui_system_state_inner.move`, making it reachable by any ordinary SUI holder who owns a `FungibleStakedSui` object. [7](#0-6) 

---

### Impact Explanation

When `pool.rewards_pool.split(rewards_amount)` aborts, the entire transaction is rolled back. The `FungibleStakedSui` object is **not** consumed (Move rolls back all effects on abort), so the user retains it — but can never successfully redeem it against an inactive pool with a drained `rewards_pool`. Both the principal (safely held in `FungibleStakedSuiData.principal`) and the rewards are permanently inaccessible. This is a **permanent fund lock** matching the High/Medium bounty impact class.

---

### Likelihood Explanation

Medium. The scenario requires: (1) a user holds `FungibleStakedSui` for a validator pool; (2) the validator leaves, deactivating the pool; (3) regular `StakedSui` holders withdraw before the `FungibleStakedSui` holder, draining `rewards_pool`; (4) the pool has accumulated enough rewards that `total_rewards ≥ FS`, making `rewards_amount ≥ 1` unavoidable. Steps 2–4 are normal protocol events that occur without any coordination or malicious intent.

---

### Recommendation

Apply the same guard used in `withdraw_rewards` to `redeem_fungible_staked_sui`:

```move
// Before:
sui_out.join(pool.rewards_pool.split(rewards_amount));

// After:
let actual_rewards = rewards_amount.min(pool.rewards_pool.value());
sui_out.join(pool.rewards_pool.split(actual_rewards));
``` [1](#0-0) 

This mirrors the existing fix in `withdraw_rewards` and ensures the function never aborts due to an insufficient `rewards_pool`, regardless of how much regular stakers have withdrawn.

---

### Proof of Concept

1. Pool is active with `sui_balance = 2_000`, `rewards_pool = 1_000`, `pool_token_balance = 1_000`.
2. User A holds `FungibleStakedSui { value: 500 }` (half the pool tokens). `FungibleStakedSuiData { total_supply: 1_000, principal: 500 }`.
3. Exchange rate: `{ sui_amount: 2_000, pool_token_amount: 1_000 }` → `total_sui_amount = 1_000`, `total_rewards = 500`.
4. Validator leaves → pool deactivated. Exchange rate frozen. No new `deposit_rewards` calls.
5. Regular staker B holds `StakedSui` with `pool_token_withdraw_amount = 500`. Calls `request_withdraw_stake`. `withdraw_rewards` computes `reward_withdraw_amount = 500`, capped to `min(500, 1_000) = 500`. `rewards_pool` drained to `500`.
6. Another regular staker C withdraws similarly, draining `rewards_pool` to `0`.
7. User A calls `redeem_fungible_staked_sui` with `value = 500`.
   - `rewards_amount = floor(500 × 500 / 1_000) = 250`
   - `pool.rewards_pool.split(250)` → **abort** (`rewards_pool.value() = 0 < 250`)
8. User A retries — same abort every time. Pool is inactive; `rewards_pool` never refills. **Principal of 250 SUI and rewards of 250 SUI are permanently locked.** [4](#0-3) [8](#0-7)

public(package) fun redeem_fungible_staked_sui(
    pool: &mut StakingPool,
    fungible_staked_sui: FungibleStakedSui,
    ctx: &TxContext,
): Balance<SUI> {
    let FungibleStakedSui { id, pool_id, value } = fungible_staked_sui;
    assert!(pool_id == object::id(pool), EWrongPool);

    id.delete();

    let latest_exchange_rate = pool.pool_token_exchange_rate_at_epoch(ctx.epoch());
    let fungible_staked_sui_data: &mut FungibleStakedSuiData =
        &mut pool.extra_fields[FungibleStakedSuiDataKey {}];

    let (
        principal_amount,
        rewards_amount,
    ) = latest_exchange_rate.calculate_fungible_staked_sui_withdraw_amount(
        value,
        fungible_staked_sui_data.principal.value(),
        fungible_staked_sui_data.total_supply,
    );

    fungible_staked_sui_data.total_supply = fungible_staked_sui_data.total_supply - value;

    let mut sui_out = fungible_staked_sui_data.principal.split(principal_amount);
    sui_out.join(pool.rewards_pool.split(rewards_amount));

    pool.pending_total_sui_withdraw = pool.pending_total_sui_withdraw + sui_out.value();
    pool.pending_pool_token_withdraw = pool.pending_pool_token_withdraw + value;

    sui_out
}

fun withdraw_rewards(
    pool: &mut StakingPool,
    principal_withdraw_amount: u64,
    pool_token_withdraw_amount: u64,
    epoch: u64,
): Balance<SUI> {
    let exchange_rate = pool.pool_token_exchange_rate_at_epoch(epoch);
    let total_sui_withdraw_amount = exchange_rate.get_sui_amount(pool_token_withdraw_amount);
    let mut reward_withdraw_amount = if (total_sui_withdraw_amount >= principal_withdraw_amount) {
        total_sui_withdraw_amount - principal_withdraw_amount
    } else 0;

    // This may happen when we are withdrawing everything from the pool and
    // the rewards pool balance may be less than reward_withdraw_amount.
    // TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN.
    reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value());
    pool.rewards_pool.split(reward_withdraw_amount)
}
