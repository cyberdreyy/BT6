### Title
Stale confirmations from removed multisig members still count toward execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::confirm` counts pre-existing entries in the `confirmations` `HashSet<String>` for a request without verifying that each confirming identity is still a current member of `self.members`. `delete_member` only clears confirmations for requests that the deleted member *originated*, not confirmations they cast on requests originated by others. This lets a request execute with fewer *live* member approvals than `num_confirmations` actually requires.

### Finding Description
The custody binding that must hold is: *confirmations counted == confirmations from currently authorized members*. On `confirm`, the contract increments and checks `confirmations.len() as u32 + 1 >= self.num_confirmations` [3](#0-2) , then executes the request via `execute_request`, which can transfer funds, add/delete keys, deploy contracts, etc. [4](#0-3) .

`delete_member` is the only path that prunes stored confirmations, and it does so by filtering `self.requests` for entries whose *originating* `r.member == member`, deleting those requests/confirmations entirely [5](#0-4) . It does not iterate `self.confirmations` values to strip the removed member's identity string from confirmation sets belonging to *other* members' requests. Those stale confirmation entries remain counted by `confirm()` for as long as that other request stays open.

Concretely: member A opens request R (not deleted), member B confirms R (adds "B" to `confirmations[R]`), then B is removed from the multisig via `DeleteMember`. `confirmations[R]` still contains "B". If `num_confirmations` is, say, 3, and originally A, B, C were expected to approve, now only A and C are live members, yet R can still be executed once C confirms (A + B(stale) + C = 3 confirmations counted), even though B is no longer an authorized signer. This is exactly a "confirmations counted versus live members" divergence: the recorded claim (confirmation count) exceeds what live authorization actually supports.

The legacy `multisig/src/lib.rs` (pk-based) has the analogous gap: `DeleteKey` only purges requests signed by that key (`r.signer_pk == pk`) [6](#0-5) , not confirmations that key placed on other members' requests.

### Impact Explanation
This breaks the multisig's core authorization guarantee: a request can be executed (transfer, `AddKey`/`AddMember`, `FunctionCall`, `DeployContract`) with approval from fewer currently-authorized parties than the configured threshold — effectively a request executed below the intended live-member threshold. Because `execute_request` can move NEAR out of the account (`Transfer`) or grant new full-access keys (`AddKey`), this maps to the Critical impact category: "a multisig request executed below threshold" / funds moved by a party not entitled to it.

### Likelihood Explanation
Requires no special privilege beyond being (or having been) a legitimate multisig member at some point — a plausible scenario for organizations that rotate signers. Any time a member confirms a pending request and is later removed (e.g., employee offboarding, key rotation, compromised-key removal) while that request is still open, the stale confirmation persists and counts toward execution. The attack is passive from the removed member's perspective (no further action from them needed) — the remaining members just need to reach `num_confirmations - 1` new confirmations, one fewer than intended.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate all pending `confirmations` entries and remove the departing member's identity from every set, not just requests they originated. Alternatively, validate at `confirm()` time (and before executing) that every entry in the stored confirmation set still corresponds to a member currently in `self.members`, discarding/ignoring stale entries when computing the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 3`.
2. A calls `add_request` to create request R (transfer funds out).
3. B calls `confirm(R)` → `confirmations[R] = {A, B}` (A auto-confirmed via `add_request_and_confirm` or separately confirms).
4. Members submit and confirm a `DeleteMember { member: B }` request, which executes `delete_member`, removing B from `self.members` and its access key — but R is untouched since `r.member == A`, not B, so `confirmations[R]` still contains B.
5. C calls `confirm(R)` → `confirmations.len() + 1 == 3 >= num_confirmations`, and `execute_request` fires the transfer — approved using only 2 live members (A, C) plus a stale confirmation from removed member B, one short of the intended 3-live-member threshold.

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
