### Title
Legacy pending withdraw receipts escape the `lossRecoveryPriceByEpoch` haircut and over-claim at par, draining funded underlyings from haircutted claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` applies a haircut to the entire `pendingWithdraws` aggregate when a `stopEpochWithDuration` loss is realized, but the haircut is only enforced per-epoch through `withdrawsRequestsByEpoch`. Receipts created before the per-epoch mapping existed ("legacy" receipts, `withdrawsRequests` set, `withdrawsRequestsByEpoch` empty) are included in the loss-bearing `pendingBasis` yet are later paid at full par via `_claimFundedWithdrawRequest`. This mirrors the CVE bug class (an over-read of uninitialized/stale bounds): the vault reads a loss-epoch claim basis of `0` from a mapping that was never written for the legacy epoch, so the loss never propagates to that receipt. The result is insolvency for the funded-claim pool: haircutted users cannot be paid in full.

### Finding Description
When `stopEpochWithDuration` realizes a loss, `IdleCDOEpochVariant` calls `collectWithdrawFunds(_amount)` with `_amount < pendingBasis`. The strategy then computes a pro-rata recovery price over the whole `pendingWithdraws` bucket and stores it under `lossRecoveryPriceByEpoch[epochNumber]`: [1](#0-0) 

Every receipt inside `pendingWithdraws` — including legacy receipts — is implicitly haircutted, because only `_amount` underlyings are pulled in.

On the claim side, the loss haircut is applied only if `_withdrawClaimAmountsForEpoch` finds a non-zero `withdrawsRequestsByEpoch[_user][lossEpoch]` (or a matching `apr0Users` principal). For a legacy receipt that value is `0`, so `_claimLossAdjustedWithdrawRequest` returns `0` and execution falls into `_claimFundedWithdrawRequest`, which pays the full aggregate `withdrawsRequests[_user]` at par: [2](#0-1) [3](#0-2) 

The code acknowledges that legacy receipts cannot be haircutted and reverts the loss-stop only when `defaultRecoveryInitialized` is still false (line 416). But after any new `requestWithdraw` lazily initializes recovery accounting, a subsequent loss stop succeeds while legacy receipts remain inside `pendingWithdraws`. The epoch gate in `_claimFundedWithdrawRequest` (`epochNumber <= lastWithdrawRequest[_user]`) does not help: `epochNumber` is incremented by the loss-bearing `stopEpoch`, so the legacy holder's `lastWithdrawRequest` (set in an older epoch) passes immediately.

Broken invariant: loss waterfall / fair claim — the aggregate haircut is not binding on every receipt that was included in `pendingBasis`.

### Impact Explanation
Direct insolvency / theft with quantified loss. Example: `pendingWithdraws = 100` = 50 (legacy user L) + 50 (epoch user E). A 50% loss stop funds `50` and stores `lossRecoveryPriceByEpoch[E_epoch] = 0.5e18`. Claims owed: L gets `50 * 1.0 = 50` (par), E gets `50 * 0.5 = 25`, total owed `75` vs `50` actually held. If L claims first, E is underpaid by 25 (permanent loss of up to the entire unfunded haircut). If L claims last, L's own transfer can revert/underpay — either way the funded pool is short by exactly the legacy receipt's escaped haircut. The legacy holder, an unprivileged unclaimed-receipt holder, extracts the haircut share that was meant to be socialized.

### Likelihood Explanation
Medium-low but concrete. Pre-conditions: (1) a strategy upgraded from a pre-`withdrawsRequestsByEpoch` implementation while normal receipts were still pending (explicitly contemplated by the code comments and covered by `testUpgradeWithLegacyPendingWithdrawNeedsNoUpgradeAndCall`), (2) lazy `defaultRecoveryInitialized` flips true on the next new `requestWithdraw`, and (3) a subsequent `stopEpochWithDuration` realizes a loss while the legacy receipt is still unclaimed. No privileged user misbehavior is required; the honest owner simply calls `stopEpochWithDuration` with a loss. Attacker = any holder of a stale unclaimed receipt.

### Recommendation
Track legacy aggregate receipts explicitly. When `collectWithdrawFunds` applies a haircut and `defaultRecoveryInitialized` is true, either (a) record the pre-initialization pending portion in a dedicated `legacyPendingBasis`/`legacyRecoveryPrice` and have `_claimFundedWithdrawRequest` price the unfunded remainder through it, or (b) permanently require a migration call (`initializeDefaultRecovery`-style) that snapshots `withdrawsRequests` into per-epoch storage before any further loss stop is permitted. At minimum, revert `collectWithdrawFunds` on `_amount < pendingBasis` whenever the aggregate `withdrawsRequests` totals cannot be attributed to per-epoch receipts.

### Proof of Concept
Foundry fork test extending `test/foundry/IdleCreditVault.t.sol` (pattern from `testUpgradeWithLegacyPendingWithdrawNeedsNoUpgradeAndCall`):

```solidity
function testLegacyReceiptEscapesLossHaircut() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address legacyUser = makeAddr('legacyUser');
    address epochUser  = makeAddr('epochUser');

    // 1) Both deposit and request withdrawal in the buffer
    _depositWithUser(legacyUser, 10_000 * ONE_SCALE, true);
    _depositWithUser(epochUser,  10_000 * ONE_SCALE, true);
    vm.prank(legacyUser);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // basis 50
    vm.prank(epochUser);
    cdoEpoch.requestWithdraw(0, address(BBtranche)); // basis 50

    // 2) Simulate legacy state: erase legacyUser's per-epoch record
    stdstore.target(address(creditVault))
      .sig(creditVault.withdrawsRequestsByEpoch.selector)
      .with_key(legacyUser).with_key(creditVault.epochNumber())
      .checked_write(uint256(0));

    // 3) Epoch starts, borrower repays with a loss ->
    //    owner calls stopEpochWithDuration(_lossAmount = 50% of basis)
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() / 2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, lossAmount); // loss path

    // collectWithdrawFunds stored lossRecoveryPriceByEpoch[e] = 0.5e18,
    // vault holds only 50% of pendingBasis.

    // 4) Legacy user claims FIRST at par via _claimFundedWithdrawRequest
    vm.prank(legacyUser);
    cdoEpoch.claimWithdrawRequest(); // receives full 50, not 25

    // 5) Epoch user claims via _claimLossAdjustedWithdrawRequest -> 25 owed
    uint256 balPre = underlying.balanceOf(epochUser);
    vm.prank(epochUser);
    cdoEpoch.claimWithdrawRequest(); // vault balance insufficient -> revert/underpay
    assertLt(underlying.balanceOf(epochUser) - balPre, 25 * ONE_SCALE);
}
```

```text
  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);
```

```text
  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
```
