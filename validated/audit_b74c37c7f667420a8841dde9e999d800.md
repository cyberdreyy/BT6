### Title
Overwritten `lastWithdrawRequest` pointer lets a loss-adjusted withdraw receipt claim at full par, stealing the haircut from the pool - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug class is a stale/lost pointer: `rio_add_net()` registered the device but on failure `kfree()` released it while `mport->net` still pointed at it (use-after-free). The analog in `IdleCreditVault` is the inverse bookkeeping mistake: `requestWithdraw()` unconditionally overwrites `lastWithdrawRequest[_user]` with the newest request epoch, losing the only pointer used to find a prior epoch's loss-adjusted haircut (`lossRecoveryPriceByEpoch`). The "freed" receipt is then still reachable through the aggregate `withdrawsRequests[_user]`, which `_claimFundedWithdrawRequest()` pays out at full par. A user with a haircut receipt followed by a normal receipt gets paid the un-haircut amount, extracting the difference from funded withdrawal reserves.

### Finding Description
`requestWithdraw` mints the user a strategy-token receipt and records per-epoch and aggregate claims plus a single "latest epoch" pointer (contracts/strategies/idle/IdleCreditVault.sol:271-295):

- `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`
- `withdrawsRequests[_user] += _amount`
- `lastWithdrawRequest[_user] = currentEpoch` — overwrite, no chaining

When the manager stops an epoch with an explicit loss (`stopEpochWithDuration(..., _lossAmount)`), `previewLossAdjustedWithdrawFunds` reduces the funded `pendingWithdraws` and stores `lossRecoveryPriceByEpoch[epoch]` so pending receipts for that epoch must be claimed at a haircut.

At claim time, `claimWithdrawRequest` runs `_claimLossAdjustedWithdrawRequest` first, but it only ever inspects **one** epoch — the current value of `lastWithdrawRequest[_user]` (lines 789-800):

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

If the user made a second request in a later epoch B, `lossEpoch == B`, `lossRecoveryPriceByEpoch[B] == 0`, and the function returns 0 **without clearing epoch A's entry** in `withdrawsRequestsByEpoch` or decrementing `withdrawsRequests`. Control then falls through to `_claimFundedWithdrawRequest` (lines 319-350), which pays the entire aggregate `withdrawsRequests[_user]` — which still includes the epoch-A haircut receipt — at full par via `_transferFundedClaim`, burns all receipt tokens, and clears the mapping.

The epoch-A loss-adjusted receipt is therefore paid twice over in economic terms: it was already discounted when funding was sized (`pendingWithdraws` was reduced by the loss), yet it is redeemed as if the loss never happened. This is the exact kernel pattern: one pointer (`lastWithdrawRequest`) is overwritten while the resource it described (the discounted receipt) remains live and is consumed through a different path (`withdrawsRequests`) at the wrong value.

### Impact Explanation
Direct theft / pool insolvency. The attacker receives `claimBasis_A * (1 - lossRecoveryPriceByEpoch[A]) / RECOVERY_FULL` more underlying than entitled. Those underlyings come from the strategy's funded withdrawal reserve, so every other pending claimant or remaining LP absorbs the shortfall pro rata — the loss intended to be socialized onto the epoch-A receipts is instead pushed onto unrelated users. With a 20% haircut on a 1M receipt, the attacker nets ~200k underlyings above entitlement.

### Likelihood Explanation
Requires a `stopEpochWithDuration` with nonzero `_lossAmount` (an honest manager action, in-scope), then a second `requestWithdraw` by the same user in a later epoch before claiming. Withdrawal requests are open during buffer periods (`allowAAWithdrawRequest`/`allowBBWithdrawRequest` re-enabled after each successful stop, IdleCDOEpochVariant.sol:481-482), and the code explicitly supports multiple unclaimed requests ("if a user does not claim a withdraw request and instead requests another withdraw..."). No privileged collusion, KYC bypass, or oracle manipulation is needed — any KYC-passing lender can hold two receipts across a loss epoch and a normal epoch.

### Recommendation
In `requestWithdraw`, do not blindly overwrite `lastWithdrawRequest[_user]`: either
- store the user's request epochs in a set/linked list so `_claimLossAdjustedWithdrawRequest` can iterate all pending epochs and apply each `lossRecoveryPriceByEpoch`, or
- when a prior unclaimed receipt exists for an epoch with `lossRecoveryPriceByEpoch != 0`, force immediate settlement of that epoch's claim (or revert) before accepting the new request, mirroring `put_device()` + `mport->net = NULL` — never leave a live resource reachable after its pointer is replaced.

A minimal fix: in `requestWithdraw`, if `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0`, revert and require the user to claim first.

### Proof of Concept
Foundry fork PoC (sketch, following `test/foundry/IdleCreditVault.t.sol` conventions):

```solidity
// Setup: pool with AA + BB deposits, standard epoch variant.
_depositWithUser(attacker, 1_000_000 * ONE_SCALE, true);   // AA tranche tokens
// Epoch 0: attacker requests withdraw (buffer period)
vm.prank(attacker);
uint256 reqA = cdoEpoch.requestWithdraw(0, address(AAtranche));
uint256 epochA = strategy.epochNumber();

// Manager stops epoch 0 WITH a loss -> lossRecoveryPriceByEpoch[epochA] = p < 1e18
deal(defaultUnderlying, borrower, fundedAmount);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(newApr, 0, epochDuration, lossAmount); // loss > 0
uint256 pA = strategy.lossRecoveryPriceByEpoch(epochA);
assertLt(pA, strategy.RECOVERY_FULL());

// Epoch 1 buffer: attacker requests a second, small withdraw.
// This OVERWRITES lastWithdrawRequest[attacker] -> epochA pointer is lost.
vm.prank(attacker);
cdoEpoch.requestWithdraw(smallAmount, address(AAtranche));

// Epoch 1 ends normally; both receipts now claimable.
// ... startEpoch, warp, stopEpoch(0, interest) ...

uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(attacker) - balPre;

// BUG: epoch-A receipt paid at par instead of at pA haircut.
uint256 expected = reqA * pA / 1e18 + reqB;
assertGt(paid, expected);          // attacker overpaid by reqA * (1 - pA)/1e18
assertEq(strategy.withdrawsRequests(attacker), 0); // aggregate cleared anyway
```

Key assertions: `lossRecoveryPriceByEpoch[epochA] > 0` yet never applied; `paid` equals `reqA + reqB` (par) instead of `reqA * pA / 1e18 + reqB`. The excess is drawn from strategy underlyings reserved for other claimants.

Caveat: I was unable to fully verify `previewLossAdjustedWithdrawFunds`'s exact accounting of `pendingWithdraws` vs. per-epoch receipt pricing within the iterations available; the core claim rests on `lastWithdrawRequest` being a single-slot pointer that is unconditionally overwritten at `requestWithdraw` (IdleCreditVault.sol:282) and being the sole lookup key in `_claimLossAdjustedWithdrawRequest` (lines 790-791), which is confirmed in the code above.
