### Title
WebAPI trigger requests can be signature-replayed to repeatedly execute a workflow - (File: `core/capabilities/webapi/trigger/trigger.go`)

### Summary
The `web-api-trigger@1.0.0` capability accepts signed messages from external, unprivileged senders via the Gateway and starts a workflow execution for each one. The only check that limits repeated execution of the exact same signed message is a per-sender/global token-bucket rate limiter — there is no nonce, message-id dedup cache, or one-time-use marker tied to the ECDSA signature itself.

### Finding Description
`triggerConnectorHandler.HandleGatewayMessage` validates an incoming `api.Message` (`hc.ValidatedMessageFromReq`), recovers the sender address from the ECDSA signature over the message body via `Message.ExtractSigner`/`Message.Validate` [1](#0-0) , and then calls `processTrigger` with that sender address [2](#0-1) .

Inside `processTrigger`, authorization is limited to (a) checking the sender is in `allowedSenders` and (b) a `ratelimit.RateLimiter.Allow(body.Sender)` check — no verification is performed that this specific signed message (`body.MessageId` / `payload.TriggerEventId`) has not already been processed: [3](#0-2) 

`TriggerEventID` is derived deterministically from attacker-controlled fields (`body.Sender + payload.TriggerEventId`) and is only used to tag the emitted `capabilities.TriggerEvent`; it is never checked against a "seen" set before dispatching the event to the workflow engine [4](#0-3) .

Because the signature (over `MessageId`, `Method`, `DonId`, `Receiver`, `Payload`) contains no timestamp/nonce binding it to a single use [5](#0-4) , any party who obtains a copy of a previously-submitted, validly-signed trigger message (e.g., by observing it in transit, logs, or because it was originally sent by the legitimate but now-compromised counterparty) can resubmit that exact same message to the Gateway repeatedly. Each resubmission passes signature validation and sender allowlist checks identically, and is only throttled — not blocked — by the rate limiter, so it will re-trigger the associated workflow execution multiple times.

This mirrors the reported bug class: a signature that authorizes an action is not bound to a nonce/one-time value, so it can be replayed to repeat the action more times than the original signer intended.

### Impact Explanation
Repeated invocation of `trigger.ch <- tr` causes the target workflow to execute again for each replay, up to the sender/global rate limit [6](#0-5) . If the downstream workflow performs any stateful or fund-moving action per execution (e.g., an on-chain write, a payment, or an external side effect), this allows unauthorized duplicate job runs at a rate bounded only by the configured RPS/burst rather than by the true intent of the original signer.

### Likelihood Explanation
Exploitation requires an attacker to obtain a single previously-signed, valid trigger message (via network capture, logging, or a compromised intermediary) — no private key or credential compromise of the actual signer is needed. Because the message flows over the internet-facing Gateway HTTP/WS endpoint and rate limiting is the sole mitigating control, likelihood is moderate; the constraint is limited to configured RPS/burst rather than a hard cryptographic prevention.

### Recommendation
Bind each trigger signature to a single use: include a monotonically increasing nonce or timestamp validity window in the signed payload, and maintain a bounded "seen message-id" cache (similar to the JWT replay cache used in `core/capabilities/webapi/webapicap`-adjacent gateway v2 handlers, e.g. `jwtReplayCache` in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`) so that a given `MessageId`/`TriggerEventId` can only be accepted once, independent of the rate limiter.

### Proof of Concept
1. Legitimate allowed sender signs and submits a `web_api_trigger` message with `MessageId = "m1"`, `TriggerEventId = "e1"`.
2. Gateway/`triggerConnectorHandler.HandleGatewayMessage` validates the signature, confirms sender is allowed, and dispatches a `TriggerResponse` for workflow execution.
3. Attacker captures the exact same signed request (same signature bytes, same body) and resubmits it N times before the rate-limit window resets.
4. Each resubmission passes `Message.Validate()` (signature is still valid — nothing invalidates it after first use) and `allowedSenders`/`rateLimiter.Allow` checks in `processTrigger`, causing the workflow to be triggered N additional times with the same `TriggerEventID`.

**Confidence/uncertainty note:** I was unable to fully verify, within the available search budget, whether an additional layer in the Gateway's HTTP ingress path (`core/services/gateway/handlers/capabilities/handler.go` or `v2/http_handler.go`) performs message-id deduplication before messages reach `triggerConnectorHandler`. If such a dedup layer exists there, it would mitigate this finding; I could not confirm its presence or absence from the code I was able to inspect.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

// Message signatures are over the following data:
//  1. MessageId aligned to 128 bytes
//  2. Method aligned to 64 bytes
//  3. DonId aligned to 64 bytes
//  4. Receiver (in hex) aligned to 42 bytes
//  5. Payload (raw bytes before parsing)
func (m *Message) Sign(privateKey *ecdsa.PrivateKey) error {
	if m == nil {
		return errors.New("nil message")
	}
	rawData := GetRawMessageBody(&m.Body)
	signature, err := gw_common.SignData(privateKey, rawData...)
	if err != nil {
		return err
	}
	m.Signature = utils.StringToHex(string(signature))
	m.Body.Sender = strings.ToLower(crypto.PubkeyToAddress(privateKey.PublicKey).Hex())
	return nil
}
