### Title
Job-controlled build-image `pull_policy` is reused verbatim for the helper and init-permission containers - (File: executors/kubernetes/kubernetes.go)

### Summary
`preparePullManager` in `executors/kubernetes/kubernetes.go` builds `dockerPullPoliciesPerContainer` by assigning `s.options.Image.PullPolicies` (the job's own build-image pull policy, taken from `.gitlab-ci.yml` `image.pull_policy`) not only to `buildContainerName` but also to `helperContainerName` and `initPermissionContainerName` (and `stepsBootstrapInitContainerName` when native steps are used). There is no independent, runner-controlled pull policy for the helper/init-permission containers.

### Finding Description
In `preparePullManager` (executors/kubernetes/kubernetes.go:489-493):

```go
dockerPullPoliciesPerContainer := map[string][]common.DockerPullPolicy{
    buildContainerName:          s.options.Image.PullPolicies,
    helperContainerName:         s.options.Image.PullPolicies,
    initPermissionContainerName: s.options.Image.PullPolicies,
}
```

`s.options.Image.PullPolicies` is derived from the job payload's `image.pull_policy`, which is an attacker-controlled (job-author-controlled) CI configuration field. This same slice is fed as the "policy" argument for the helper container and the init-permission container, which run the runner's trusted helper image rather than the user's build image.

For each container, `k8sPullPoliciesPerContainer[containerName]` is computed via `pull_policies.ComputeEffectivePullPolicies(k8sPullPolicies, allowedPullPolicies, pullPolicies, s.Config.Kubernetes.PullPolicy)` (kubernetes.go:518-519). Looking at `ComputeEffectivePullPolicies` (helpers/pull_policies/pull_policies.go:12-34):
- If the admin has not set `allowed_pull_policies` (the common default), `allowedPullPolicies` is empty, and the function returns the job-supplied `pullPolicies` unmodified (line 17: `if len(allowedPullPolicies) == 0 { return pullPolicies, nil }`).
- Even when `allowed_pull_policies` is configured, it only checks that the requested policy is a member of the *allowed* set — it does not distinguish "policy intended for the build image" from "policy forced onto the trusted helper/init containers." If `Never` (or `IfNotPresent`) is an allowed policy at all (a common, legitimate admin choice for caching build images), a job can request it and it will silently also apply to the helper and init-permission containers.

The resulting per-container `api.PullPolicy` values are handed to `pull.NewPullManager(...)`, which is used to configure how those containers are pulled/scheduled on the node. This means the job author, simply by setting `image.pull_policy: [never]` for their own build image, forces the same "never pull" behavior onto the helper image and init-permission image containers, with no independent check tying helper/init-container image provenance to a runner-enforced policy.

Existing protections do not stop this:
- `allowed_pull_policies` restricts *which* policy values are permitted globally, not *which containers* a given policy value may apply to.
- There is no separate map/config entry for helper or init-permission container pull policy independent of `s.options.Image.PullPolicies`.

### Impact Explanation
On a shared Kubernetes node where a previous tenant/job has already caused a helper (or init-permission) image with the same name:tag to be cached locally (e.g., through normal pulls, or a poisoned/older cached layer), a subsequent unrelated job can set `pull_policy: [never]` on its own build image and have that same "never" policy silently propagate to the helper container and init-permission container. Kubelet will then use whatever image is already cached under that name on the node instead of pulling the runner-trusted helper image, regardless of whether the current job actually intended `never` for anything but its own build image. This breaks the invariant that helper/init container image provenance must not be gated by job-controlled input, and creates a path to cross-tenant image-cache reuse for the helper containers that execute GitLab Runner's own trusted logic.

### Likelihood Explanation
This is straightforward to trigger: the attacker only needs to set `image.pull_policy` in their `.gitlab-ci.yml`, a normal, documented, user-facing field. No additional privilege is required, and the code path is unconditionally exercised on every job (`preparePullManager` is called in `Prepare`, kubernetes.go:434). The main precondition — a stale/cached helper image already present under the expected name on the shared node — is plausible on long-lived shared runners/node pools, and does not require attacker control of any other tenant or admin compromise.

### Recommendation
Decouple the helper and init-permission container pull policies from `s.options.Image.PullPolicies`. The helper/init-permission containers should use a runner/administrator-controlled policy (e.g., `s.Config.Kubernetes.PullPolicy` or a dedicated `helper_image_pull_policy` config) that is never influenced by job-supplied `image.pull_policy`, mirroring how the helper image itself (`HelperImage`) is not user-selectable.

### Proof of Concept
Go unit test in `executors/kubernetes/kubernetes_test.go` targeting `preparePullManager`:
```go
func TestPreparePullManager_HelperContainerIgnoresJobPullPolicy(t *testing.T) {
    s := &executor{ /* ... build executor with s.options.Image.PullPolicies = []common.DockerPullPolicy{common.PullPolicyNever} */ }
    pm, err := s.preparePullManager()
    require.NoError(t, err)

    // Assert: helper/init-permission container policy must not equal "Never"
    // just because the job's build image requested it.
    assert.NotEqual(t, api.PullNever, pm.GetPullPolicy(helperContainerName))
    assert.NotEqual(t, api.PullNever, pm.GetPullPolicy(initPermissionContainerName))
}
```
Expected (current, buggy) result: both assertions fail because `helperContainerName` and `initPermissionContainerName` inherit `PullPolicyNever` from `s.options.Image.PullPolicies`, demonstrating that job-controlled input governs pull behavior of the trusted helper/init containers. func (s *executor) preparePullManager() (pull.Manager, error) {
	allowedPullPolicies, err := s.Config.Kubernetes.GetAllowedPullPolicies()
	if err != nil {
		return nil, &common.BuildError{
			Inner:         fmt.Errorf("getting allowed pull policies: %w", err),
			FailureReason: common.ConfigurationError,
		}
	}

	dockerPullPoliciesPerContainer := map[string][]common.DockerPullPolicy{
		buildContainerName:          s.options.Image.PullPolicies,
		helperContainerName:         s.options.Image.PullPolicies,
		initPermissionContainerName: s.options.Image.PullPolicies,
	}
	// Concrete's container set differs from legacy: it has an
	// init-steps-bootstrap init container (running the helper image) and no
	// helper container. The pull manager keys its retry cursor per container
	// name, so the bootstrap container must be registered here for pull-retry
	// to cover helper-image pull failures. This is neutral pull-policy
	// plumbing, not script-execution logic, so the conditional is retained
	// deliberately rather than forked into a separate builder.
	if s.Build.UseNativeSteps() {
		dockerPullPoliciesPerContainer[stepsBootstrapInitContainerName] = s.options.Image.PullPolicies
	}
	for containerName, service := range s.options.Services {
		dockerPullPoliciesPerContainer[containerName] = service.PullPolicies
	}

	k8sPullPoliciesPerContainer := map[string][]api.PullPolicy{}
	for containerName, pullPolicies := range dockerPullPoliciesPerContainer {
		k8sPullPolicies, err := s.getPullPolicies(pullPolicies)
		if err != nil {
			return nil, &common.BuildError{
				Inner:         fmt.Errorf("converting pull policy for container %q: %w", containerName, err),
				FailureReason: common.ConfigurationError,
			}
		}

		k8sPullPolicies, err = pull_policies.ComputeEffectivePullPolicies(
			k8sPullPolicies, allowedPullPolicies, pullPolicies, s.Config.Kubernetes.PullPolicy)
		if err != nil {
			return nil, &common.BuildError{
				Inner:         fmt.Errorf("invalid pull policy for container %q: %w", containerName, err),
				FailureReason: common.ConfigurationError,
			}
		}

		s.BuildLogger.Println(fmt.Sprintf("Using effective pull policy of %s for container %s", k8sPullPolicies, containerName))

		k8sPullPoliciesPerContainer[containerName] = k8sPullPolicies
	}

	return pull.NewPullManager(k8sPullPoliciesPerContainer, &s.BuildLogger), nil
}

// ComputeEffectivePullPolicies returns the intersection of the specified pullPolices and allowedPullPolicies, or
// an error if pullPolicies is not empty but the intersection IS empty. In other words, it limits pullPolicies to what
// is in allowedPullPolicies, and returns an error if none of pullPolicies was in allowedPullPolicies. All of the
// arguments are ultimately ~[]string, but defined in different ways.
func ComputeEffectivePullPolicies[A ~string, B ~string, C ~[]string](pullPolicies, allowedPullPolicies []A, ciPullPolicies []B, executorPullPoilcies C) ([]A, error) {
	if len(pullPolicies) == 0 {
		return allowedPullPolicies, nil
	}
	if len(allowedPullPolicies) == 0 {
		return pullPolicies, nil
	}
	var actuallyAllowed []A
	for _, policy := range pullPolicies {
		if slices.Contains(allowedPullPolicies, policy) {
			actuallyAllowed = append(actuallyAllowed, policy)
		}
	}

	if len(actuallyAllowed) == 0 {
		return nil, &incompatiblePullPolicyError[A]{
			pullPolicies:        pullPolicies,
			allowedPullPolicies: allowedPullPolicies,
			pullPolicySource:    getPullPolicySource(ciPullPolicies, executorPullPoilcies),
		}
	}
	return actuallyAllowed, nil
}
