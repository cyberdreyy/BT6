### Title
Cross-job pipeline run disclosure via GET /v2/jobs/:ID/runs/:runID ignoring job ownership check - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Show` reads only the `:runID` path parameter and never uses `:ID` (the job ID) to validate that the requested run actually belongs to that job. It calls `prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)`, which looks up a pipeline run purely by its numeric ID, so any authenticated user who can call this endpoint can fetch any run's full details by guessing/enumerating `runID`, regardless of which job it belongs to.

### Finding Description
In `core/web/pipeline_runs_controller.go`, `Show` is: [1](#0-0) 

Note that `c.Param("ID")` (the job ID from the route `/jobs/:ID/runs/:runID`) is never read or referenced anywhere in this function — only `c.Param("runID")` is used to build the lookup key, and `FindRun` is invoked with just that run ID. The `pipeline.ORM.FindRun` interface signature confirms it only takes an `id int64` with no job-scoping parameter: [2](#0-1) . Compare this with `Index`, which correctly scopes `PipelineRuns` calls to the parsed `jobSpec.ID` when an `:ID` is present: [3](#0-2) . `Show` has no equivalent check that the found run's `PipelineSpecID`/job matches the `:ID` route parameter, nor a comparison after fetching. As a result, a request to `/v2/jobs/<jobB-ID>/runs/<jobA-runID>` will successfully return job A's run data (task outputs, meta, inputs) rendered via `presenters.NewPipelineRunResource`, with the URL's job ID component completely ignored.

### Impact Explanation
This allows a user with any credentials sufficient to call this authenticated endpoint (e.g., a run/view-role session) to read pipeline run details for jobs they should not have access to by supplying an arbitrary or foreign `runID`, since `runID` is a simple sequential/numeric primary key and easily enumerable. Task outputs and run metadata can include sensitive values (e.g., data pulled by bridges/adapters, or secrets embedded in task configuration/outputs), so this is a cross-user/cross-job information disclosure — matching an "unauthorized data disclosure" class impact rather than a fund-movement or key-compromise class.

### Likelihood Explanation
Exploitability requires only a valid authenticated session capable of hitting job/run read endpoints (no special job ownership check exists to bypass — there simply is no such check). Since pipeline run IDs are sequential integers, an attacker can trivially enumerate `runID` values across the small ID space and pair them with any `:ID` value (or an ID they do own) to retrieve arbitrary runs. This is deterministic and repeatable, not race-dependent.

### Recommendation
In `Show`, parse and validate `c.Param("ID")` into a job ID (as `Index` does), fetch the run via `FindRun`, and then verify that the run's associated job/pipeline spec ID matches the parsed job ID before returning the presenter response — returning 404 (not 403, to avoid leaking existence) on mismatch. Alternatively, extend `pipeline.ORM.FindRun` (or add a new ORM method) that accepts both `jobID` and `runID` and filters by both in the SQL query so no application-layer post-fetch check can be skipped.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go` style:
1. Create Job A and Job B via the job ORM/fixtures, each with a completed pipeline run (`runA.ID`, `runB.ID`), where `runA` includes a distinguishing task output/meta value.
2. As an authenticated run/view-role test client, `GET /v2/jobs/<JobB.ID>/runs/<runA.ID>`.
3. Assert HTTP 200 and that the response body's `id`/attributes match `runA` (not `runB` or an error), demonstrating the `:ID` path segment had no effect on authorization or data returned.
4. As a contrasting negative-control assertion, also verify `GET /v2/jobs/<JobA.ID>/runs/<runB.ID>` similarly returns `runB`'s data — proving job/run pairing in the URL is never validated.

func (prc *PipelineRunsController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	pipelineRun := pipeline.Run{}
	err := pipelineRun.SetID(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	pipelineRun, err = prc.App.PipelineORM().FindRun(ctx, pipelineRun.ID)
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	res := presenters.NewPipelineRunResource(pipelineRun, prc.App.GetLogger())
	jsonAPIResponse(c, res, "pipelineRun")
}
