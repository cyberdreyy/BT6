### Title
Pre-default-epoch unfunded instant-withdraw receipts are excluded from the recovery haircut basis but still paid at par after `finalizeDefaultRecovery` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The c-ares bug is a stale-handle problem: a request is re-enqueued, the connection handle is closed, but `read_answers()` keeps using the freed handle. The closest analog in this codebase is `IdleCreditVault.claimInstantWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest`, where an instant-withdraw receipt created in an *earlier* epoch but left unfunded survives default finalization as a stale aggregate handle (`instantWithdrawsRequests[user]`), is never included in the recovery claim basis for `defaultRecoveryEpoch`, and is then paid out at par from the default recovery reserve.

### Finding Description
`defaultPendingClaimBasis()` only adds `instantWithdrawClaimsByEpoch[epochNumber]` — i.e., receipts recorded in the *current* (default) epoch — to the pending claim basis when `pendingInstantWithdraws != 0` (`IdleCreditVault.sol:644-649`). However, `pendingInstantWithdraws` is a *global* counter that also carries unfunded instant receipts requested in earlier epochs (`requestInstantWithdraw`, `IdleCreditVault.sol:366-375`). Those older receipts therefore:

1. Are not haircut in `totalBasis`, so `recoveryPrice` is computed without them.
2. Set `defaultInstantWithdrawsFinalized = true` (line 696), which gates the claim path.
3. Are not cleared by `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (lines 842-856).

In `claimInstantWithdrawRequest` (lines 380-393), after the no-op defaulted-epoch clear, the code pays `instantWithdrawsRequests[_user]` — the *stale* pre-default receipt — in full via `_transferFundedClaim`, at par, straight out of the recovery reserve. This is exactly the UAF shape: the epoch-scoped claim handle (`instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`) was recycled across epoch boundaries, but the aggregate handle (`instantWithdrawsRequests`, `pendingInstantWithdraws`) is still dereferenced as if it were live and funded.

Additionally, `_defaultPrefundedInstantReserve()` (lines 716-723) computes `instantBasis - pendingInstant` where `instantBasis` is only the current epoch's claims while `pendingInstant` is global — so a large stale unfunded receipt can corrupt the reserve sizing as well.

### Impact Explanation
The attacker receives 100% of their stale instant receipt while every other defaulted receipt and active LP is paid `recoveryPrice < RECOVERY_FULL`. Since the reserve was sized on `totalBasis` that excluded this claim, the payment directly dilutes/drains `defaultRecoveryReserve`, causing later legitimate claimants (post-default requests, defaulted-epoch receipts, `DefaultDistributor` claims) to receive less than the finalized recovery price or to revert on insufficient balance. Broken invariant: one receipt one payout at the finalized recovery price; solvency of the recovery reserve. Loss is bounded by the stale unfunded instant receipt amount but is direct theft from other users.

### Likelihood Explanation
Requires an instant-withdraw receipt to remain unfunded (`pendingInstantWithdraws > 0`) across an epoch boundary — i.e., the borrower/queue never funded the instant queue before `stopEpoch` rolled `epochNumber` — and then a borrower default finalized in a later epoch. The attacker only needs to have made an instant withdrawal request (any tranche-token holder can) and then call `cdoEpoch.claimInstantWithdrawRequest()` after `finalizeDefaultRecovery`. Honest actors (manager/borrower) supply the trigger via normal epoch flow and default; no privileged malicious action is needed. Likelihood is moderate: it depends on instant withdrawals being enabled and left partially unfunded at an epoch roll, which is operationally plausible but not guaranteed.

### Recommendation
In `defaultPendingClaimBasis()`, include the full stale instant exposure, not just the current epoch: e.g., `basis += instantWithdrawClaimsByEpoch[epochNumber]` should account for all unfunded instant receipts still covered by `pendingInstantWithdraws` (track instant claims per-epoch for all outstanding epochs, or include `pendingInstantWithdraws`-backed older claims in basis). Symmetrically, `_claimDefaultedInstantWithdrawRequest` should haircut *any* receipt that was unfunded at finalization, not only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` — e.g., iterate or store the set of epochs with unfunded receipts, or cap the par-funded remainder of `claimInstantWithdrawRequest` to amounts provably funded before default.

### Proof of Concept
Sketch (Foundry, fork-style consistent with `test/foundry/IdleCreditVault.t.sol`):

```solidity
// epoch E1 running, instant withdraws enabled
// user (attacker) requests instant withdraw via CDO
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(amount, tranche); // mints receipt, pendingInstantWithdraws += amount
// borrower never funds the instant queue; epoch ends, epochNumber -> E2
_stopCurrentEpochWithApr(...);
// epoch E2 runs; borrower defaults (no repayment), owner stops epoch -> defaulted
// manager calls finalizeDefaultRecovery -> recoveryPrice < RECOVERY_FULL
// attacker's E1 receipt was excluded from defaultPendingClaimBasis
// (instantWithdrawClaimsByEpoch[E2] does not include it)
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
// _claimDefaultedInstantWithdrawRequest clears byEpoch[E2]==0, then
// instantWithdrawsRequests[attacker] (the E1 amount) is paid at PAR
assertGt(underlying.balanceOf(attacker) - balPre,
         amount * strategy.defaultRecoveryPrice() / 1e18); // overpaid vs recovery price
// subsequent claims from other users revert/underpay: reserve drained
```

Note: I verified the claim/finalization logic statically; the one piece I could not fully confirm within the available searches is whether any other code path forces funding or clears `pendingInstantWithdraws` for stale instant receipts at `stopEpoch`/`startEpoch`. If the CDO always forces instant funding before an epoch rolls, this path is unreachable and the finding reduces to a defense-in-depth gap — that check should be part of PoC development.
