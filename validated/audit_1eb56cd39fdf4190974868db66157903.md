### Title
Image-by-ID short-circuit bypasses `allowed_pull_policies` / pull-policy enforcement - ([File: executors/docker/internal/pull/manager.go])

### Summary
`getImageUsingPullPolicy` returns a locally cached image without any pull or auth re-check whenever `existingImage.ID == imageName`, regardless of the effective pull policy computed from `allowed_pull_policies`. An unprivileged job that sets `image:` to the sha256 ID of an image already cached on a shared Docker host (pulled earlier by any other tenant/job) will hit this short-circuit and reuse that cached image even under an admin-enforced `always`/`if-not-present`-only policy that is meant to force a registry round trip and auth check on every job.

### Finding Description
`GetDockerImage` computes the effective pull policy via `pull_policies.ComputeEffectivePullPolicies` (`executors/docker/internal/pull/manager.go:126-133`), which enforces `allowed_pull_policies`. It then calls `getImageUsingPullPolicy` per policy. Inside that function: [1](#0-0) 

- `ImageInspectWithRaw(m.context, imageName, platform)` is called with the attacker-controlled `imageName`.
- If that lookup succeeds (`err == nil`) and `existingImage.ID == imageName` (line 257), the function returns the cached image immediately — before `resolveAuthConfigForImage` and `pullDockerImage` are ever invoked. This check happens unconditionally for any non-`Never` policy, including `always`.
- Docker's `ImageInspectWithRaw` matches by ID/digest even when only the short or full ID string is passed, so any job specifying an already-cached image's ID as `image:` satisfies this branch.
- On a shared Docker host (default for many Docker executor deployments, or any host reused across projects), an image ID cached by one tenant's earlier build remains resolvable to any other tenant's job on that host, since Docker's local image store is not project-scoped.
- The `allowed_pull_policies` mechanism only restricts which *pull policy names* a job may request; it has no visibility into, and provides no protection against, the ID short-circuit, which sidesteps the pull/auth step entirely regardless of policy.

### Impact Explanation
An unprivileged job can reuse another tenant's previously-pulled (potentially private/authenticated) image on a shared runner host by referencing its raw ID, without triggering the registry pull or auth-config resolution that `allowed_pull_policies=always` is meant to guarantee. This defeats the administrator's intent that every job re-authenticate/re-pull, and allows cross-tenant reuse of cached image content that the job author never had the credentials to pull themselves. Impact is scoped to restriction bypass / cross-tenant image reuse as described.

### Likelihood Explanation
Requires: (1) a Docker executor on a host shared across multiple tenants/projects (common default, especially with autoscaling fleets that don't wipe the image cache between jobs), and (2) knowledge of the target image's ID/digest, which can often be discovered from public build logs, `docker images` output leaked in job logs, or predictable/well-known base images. Given these, the bypass is deterministic and repeatable on every job run against that host.

### Recommendation
Only allow the by-ID short-circuit when the effective pull policy explicitly permits skipping the pull (e.g., only under `if-not-present`/`never`), or require that the by-ID lookup still passes through `resolveAuthConfigForImage`/policy enforcement for `always`. At minimum, gate the `existingImage.ID == imageName` fast path so it cannot be reached at all when the effective pull policy is `always`.

### Proof of Concept
Go unit test in `executors/docker/internal/pull/manager_test.go` style:
1. Mock `docker.Client.ImageInspectWithRaw` to return `image.InspectResponse{ID: "sha256:deadbeef..."}` and `nil` error for any `imageName`.
2. Configure `ManagerConfig.DockerConfig` with `PullPolicy = "always"` and `AllowedPullPolicies = []{"always"}`.
3. Call `manager.GetDockerImage("sha256:deadbeef...", spec.ImageDockerOptions{}, nil)`.
4. Assert that `client.ImagePullBlocking` (or `resolveAuthConfigForImage`) is **never** called, and that the returned image equals the mocked `existingImage` — demonstrating the pull/auth step was skipped despite an `always` pull policy.
