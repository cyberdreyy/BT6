### Title
Local wall-clock race in `check_parent_tenure_choice` lets a signer sign a tenure-change that reorgs an already-confirmed tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
The reported bug is a "reorg race" that lets an attacker steal a victim's deployed contract because the victim's transaction ordering, not any protocol invariant, decides who owns a deterministic address. The closest analog in this repo is `SortitionData::check_parent_tenure_choice`, which decides whether a miner is allowed to reorg a previously-built tenure based purely on **local, non-consensus timing measurements** (`sortition_state_received_time` vs. `approved_time`) recorded by each individual signer. Because this timing is derived from when *that signer* happened to receive gossip/burn-block events rather than from any canonical, agreed-upon fact, a signer can be tricked (by ordinary network jitter or by an attacker who controls delivery timing of the burn-block/tenure messages it relays) into believing a reorg attempt was "poorly timed" and therefore permissible, when in fact the reorged tenure already has one globally accepted (canonical) block.

### Finding Description
`check_parent_tenure_choice` (`stacks-signer/src/chainstate/mod.rs:170-295`) is the sole gate that decides if a miner's new tenure is allowed to replace ("reorg") a tenure the signer already treats as valid. For each tenure being reorged it:

1. Rejects immediately if more than one block was already globally accepted in that tenure (`globally_accepted_blocks > 1` at lines 210-223).
2. If the tenure produced exactly one block, it computes:
   - `sortition_state_received_time` — this signer's local receive time for the *new* tenure's burn block (`signer_db.get_burn_block_receive_time`, line 198-199).
   - `local_block_info.approved_time` — this signer's local approval timestamp for the *reorged* tenure's first block (line 251-253).
   - `proposal_to_sortition = sortition_state_received_time - approved_time` (line 254).
3. If `proposal_to_sortition < first_proposal_burn_block_timing` (a config duration, default seconds-scale, `config.rs`), the reorg is deemed to be against a "poorly timed" block and is **permitted** (lines 259-274), marking the reorged tenure as `superseded` via `record_superseded_tenure`/`mark_tenure_superseded` (lines 291-294, 303-315). Once superseded, this signer's own earlier signature on the reorged tenure's block is explicitly excluded from blocking a later conflicting signature (see `reorg_permit_stands` in the pre-commit flow, `docs/signer-flows.md:251-252`).

Both `sortition_state_received_time` and `approved_time` are **wall-clock timestamps recorded independently by each signer**, not values derived from canonical chain state or agreed upon by the signer set. They depend entirely on message-propagation latency to that specific signer. This is structurally the same class of bug as the Vault report: a security decision (who is allowed to "own"/build on a given piece of state) is made using an attacker-influenceable, non-deterministic input (arrival/ordering timing) instead of a consensus-anchored fact.

A miner/relay that can delay delivery of the earlier tenure's block-approval gossip to a specific signer, or that benefits from ordinary network jitter, can cause that signer's local `approved_time` to appear anomalously close to the new sortition's `sortition_state_received_time`. This flips `check_parent_tenure_choice` from `Ok(false)` to `Ok(true)` for that signer only, even though the reorged tenure already produced a globally accepted (canonical) block. That signer then proceeds through `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:497-504`, `v2.rs` equivalent) and signs a tenure-change block that conflicts with/reorgs an already-canonical block — a **conflicting/non-canonical signature** — while other signers, whose local timing differs, correctly refuse. This breaks the "signed vs. validated" equality this class of bug is meant to catch: the on-chain fact (one block already globally accepted) is identical for every signer, but the per-signer decision is not, because it depends on each signer's own clock/gossip timing rather than that shared fact.

### Impact Explanation
This matches the Critical impact category: a signer signing a conflicting/non-canonical block. Signing a tenure-change that reorgs an already globally-accepted block, when this should be disallowed, is exactly the kind of equivocation-guard failure the pre-commit conflict logic (`get_signed_conflicts`/`reorg_permit_stands`) is built to prevent — and once `mark_tenure_superseded` fires, that signer's earlier signature is explicitly disqualified from blocking the replacement, compounding the effect for exactly the signer(s) whose clock/gossip timing was manipulated.

### Likelihood Explanation
This does not require a majority of signers or any signer's private key — it only requires influencing the delivery timing of gossip/burn-block events to a single signer (or relying on natural network jitter around a burn-block boundary), matching the report's "reorg + frontrun/backrun timing" bug class. However, `first_proposal_burn_block_timing` is expected to be configured as a short window intended only to tolerate genuinely last-second proposals near a sortition boundary, so triggering it deliberately against a well-connected signer requires a fairly narrow timing window, keeping likelihood low-to-medium, consistent with the medium severity of the original report.

### Recommendation
Replace the locally-observed `sortition_state_received_time`/`approved_time` timing heuristic with a decision based on canonical, node-verifiable facts (e.g., comparing burn-block heights/consensus hashes rather than per-signer receipt timestamps), or require the "poorly timed" determination to be corroborated by the stacks-node's own view of block/burn-block ordering rather than each signer's independent wall clock. At minimum, widen and clock-skew-harden `first_proposal_burn_block_timing` handling so an attacker cannot cheaply move a signer across the threshold via message delay alone.

### Proof of Concept
1. Tenure T1 mines and globally accepts exactly one block B1; most signers record `approved_time` for B1 at t0.
2. The next miner starts tenure T2, deliberately or incidentally causing signer S's copy of the T1→B1 approval gossip to arrive late (near t0+Δ) while S's burn-block receive time for T2 lands at t0+Δ+ε.
3. For signer S, `proposal_to_sortition = (t0+Δ+ε) − (t0+Δ) = ε`, which is `< first_proposal_burn_block_timing`, so `check_parent_tenure_choice` returns `Ok(true)` and marks T1 as superseded for S.
4. S signs T2's tenure-change block, which reorgs away the already globally-accepted B1 — while other signers whose local timings differ correctly reject the same proposal (`Ok(false)`), producing a signer that signed a conflicting/non-canonical block based purely on its own local timing view.     pub fn check_parent_tenure_choice(
```rust
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
            }

            // disallow reorg if more than one block has already been signed
            let globally_accepted_blocks =
                signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
            if globally_accepted_blocks > 1 {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already more than one globally accepted block.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => ?tenure.first_block_mined,
                    "globally_accepted_blocks" => globally_accepted_blocks,
                );
                return Ok(false);
            }

            let Some(first_block_mined) = &tenure.first_block_mined else {
                // The node saw no blocks in this tenure, so the reorg takes nothing away from
                // the canonical chain. We may still hold a signature over a block in it that
                // the node has never seen (a block we accept locally is not handed to the node
                // until the whole signer set has signed it), so the reorg must still be
                // recorded if it is permitted.
                superseded_tenures.push(tenure);
                continue;
            };
            let Some(local_block_info) =
                signer_db.get_first_approved_block_in_tenure(&tenure.consensus_hash)?
            else {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks, and there is no local knowledge for that tenure's block timing.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => %first_block_mined,
                );
                return Ok(false);
            };

            let checked_proposal_timing = if let Some(sortition_state_received_time) =
                sortition_state_received_time
            {
                // how long was there between when the proposal was received and the next sortition started?
                let proposal_to_sortition = if let Some(approved_at) =
                    local_block_info.approved_time
                {
                    sortition_state_received_time.saturating_sub(approved_at)
                } else {
                    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
                    0
                };
                if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
                    info!(
                        "Miner is not building off of most recent tenure. A tenure they reorg has already mined blocks, but the block was poorly timed, allowing the reorg.";
                        "parent_tenure" => %self.parent_tenure_id,
                        "last_sortition" => %self.prior_sortition,
                        "violating_tenure_id" => %tenure.consensus_hash,
                        "violating_tenure_first_block_id" => %first_block_mined,
                        "violating_tenure_proposed_time" => local_block_info.proposed_time,
                        "new_tenure_received_time" => sortition_state_received_time,
                        "new_tenure_burn_timestamp" => self.burn_header_timestamp,
                        "first_proposal_burn_block_timing_secs" => first_proposal_burn_block_timing.as_secs(),
                        "proposal_to_sortition" => proposal_to_sortition,
                    );
                    superseded_tenures.push(tenure);
                    continue;
                }
                true
            } else {
                false
            };

            warn!(
                "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already mined blocks.";
                "parent_tenure" => %self.parent_tenure_id,
                "last_sortition" => %self.prior_sortition,
                "violating_tenure_id" => %tenure.consensus_hash,
                "violating_tenure_first_block_id" => %first_block_mined,
                "checked_proposal_timing" => checked_proposal_timing,
            );
            return Ok(false);
        }
        // Every reorged tenure cleared the rules, so the reorg is permitted.
        for tenure in superseded_tenures {
            self.record_superseded_tenure(signer_db, tenure);
        }
        Ok(true)
    }

    /// signature we already placed on one of its blocks must stop counting as a conflict while
    /// `self`'s sortition remains canonical.
```

```rust
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
```

```markdown
One decision does have to be recorded, because it is ours rather than the
node's. When a miner builds off something other than the prior sortition,
`check_parent_tenure_choice` decides whether the reorg is allowed: it is, if
every tenure being reorged has at most one globally accepted block and produced
its first block too close to the next sortition to count
(`first_proposal_burn_block_timing`). Having sanctioned that replacement, the
signer records those tenures as **superseded** (`mark_tenure_superseded`), so its
own signature over what they built does not then block the replacement it just
permitted — the node cannot answer this one at signing time, since it still
serves the reorged tenure as fully live until the replacement lands. What _is_
still derived from the node is the permit's own validity: the record carries the
permitting tenure's sortition, and it only excludes conflicts while that
sortition remains canonical (section 5, `reorg_permit_stands`), so a burnchain
fork that orphans the permitting tenure automatically voids the permit. A record
more than `MAX_FORK_DEPTH` (100) burn blocks below the tip is dropped; a fork
that deep would cause far bigger problems than a stale conflict.
```
