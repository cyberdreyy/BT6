### Title
Tenure-change duplicate-block guard checks only global acceptance, allowing a signer to sign two conflicting first blocks of the same tenure - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`validate_tenure_change_payload` rejects a second tenure-change proposal for the same tenure only if `SignerDb::get_last_globally_accepted_block` finds a prior block already in `GloballyAccepted` state. A block the signer has already locally/self-signed but that the miner never broadcast (or that never reached the threshold) is invisible to this check, so a malicious miner can get the same signer to sign a second, conflicting tenure-change block for the identical `consensus_hash`.

### Finding Description
In `check_proposal`, when the incoming block carries a tenure-change payload, the code calls `self.validate_tenure_change_payload(...)` [1](#0-0) . Inside `validate_tenure_change_payload`, the only check that is supposed to prevent signing two different "first blocks" of the same tenure is: [2](#0-1) 

`get_last_globally_accepted_block` keys strictly on the `GloballyAccepted` block state, so it returns `None` for any block the signer has only signed locally (`SignedSelf`/locally accepted but not yet globally accepted) — for example a first candidate the miner requested a signature for but never gathered enough signatures on, or never broadcast at all. All the other checks executed before this guard — `check_tenure_change_confirms_parent` and `check_parent_tenure_choice` — validate parent-tenure linkage and reorg legitimacy, not "have I already signed a different block for this exact tenure." Neither of them detects that a *second*, differently-constructed tenure-change block for the same `consensus_hash` is a sibling/conflicting proposal rather than the same one being re-proposed.

There is a related but distinct guard, `SortitionState::is_timed_out`, which uses `db.has_signed_block_in_tenure(sortition)` (any signed state, not just globally accepted) to prevent the *sortition's miner status* from being marked `InvalidatedBeforeFirstBlock`/timed-out once a signature has been produced [3](#0-2) . However, that function only affects whether the miner is treated as still-valid for continuing to sign; it does not block a second, conflicting proposal from the same still-valid miner from reaching `validate_tenure_change_payload`, and once there, the only anti-duplicate check is the globally-accepted-only lookup shown above.

Exploit flow: an attacker who wins a miner slot proposes tenure-change block A for consensus_hash `CH`; the targeted signer locally validates and signs it (state becomes `SignedSelf`), but the miner never gathers a quorum/broadcasts it, so it never reaches `GloballyAccepted`. The miner then proposes tenure-change block B, also for `CH`, with different transactions. `check_proposal` → `validate_tenure_change_payload` runs, `get_last_globally_accepted_block(CH)` returns `None` (only A's local record exists), so the `DuplicateBlockFound` branch is skipped and B is signed too.

### Impact Explanation
This breaks the uniqueness/equivocation-guard safety property: at most one block should ever be signed by an honest signer for a given tenure, even before global acceptance. If a single unprivileged miner-slot holder can obtain two signatures from the same signer for the same tenure, this facilitates conflicting/competing tenure-change blocks carrying the same signer's weight toward two different chain histories, which is a chain-safety (equivocation) violation — matching the "Critical: signer signing ... conflicting block" category in scope.

### Likelihood Explanation
Preconditions are attacker-controlled and cheap: win one miner slot, propose a first tenure-change block that gets signed but deliberately withhold it from ever reaching global acceptance (simply don't gossip/rebroadcast it to enough signers, or gossip it to only this target signer), then propose a second tenure-change candidate for the same `consensus_hash`. No majority-signer collusion, no compromised keys, and no local access are required — only crafting two BlockProposals and controlling gossip of the signature-collection process for the first one, which is within the stated attacker capability (single miner slot + gossip). This is repeatable each tenure.

### Recommendation
Change the duplicate-tenure-change guard in `validate_tenure_change_payload` to also consult any block the signer has already locally accepted/signed for the same `consensus_hash` (not only `GloballyAccepted`), e.g. by checking `signer_db.has_signed_block_in_tenure` or an equivalent "signed-by-me" lookup keyed by consensus hash before allowing a second, different tenure-change block to be signed, and by comparing the signer-signature-hash of any existing record against the newly proposed block to detect conflicting siblings.

### Proof of Concept
Rust test outline for `stacks-signer/src/chainstate/tests/v1.rs` (or wherever `SortitionsView` tests live):
1. Construct a `SignerDb` and insert a `BlockInfo` for tenure-change block A with `consensus_hash = CH`, state = `SignedSelf` (locally signed, not globally accepted).
2. Build a `SortitionsView` whose `cur_sortition.data.consensus_hash == CH` and `miner_status == Valid`.
3. Construct a second `NakamotoBlock` B, also carrying a tenure-change payload with `prev_tenure_consensus_hash` matching the same parent tenure, `consensus_hash = CH`, but a different body/signer-signature-hash than A.
4. Call `view.check_proposal(client, &mut signer_db, &block_b, false, ReplayTransactionSet::none())`.
5. Assert: `get_last_globally_accepted_block(&CH)` returns `None` (confirming the guard is blind to A), and that the call currently returns `Ok(())` for B (i.e., no `RejectReason::DuplicateBlockFound`) — demonstrating the signer would sign a second conflicting block for the same tenure. After the fix, assert the call returns `Err(RejectReason::DuplicateBlockFound)` instead.
