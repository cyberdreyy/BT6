## Analysis

I traced the fee-routing analog to the PANTHEON `FEE_ADDRESS` bug in this repository's escrow/factory contracts. The relevant flow is:

1. `BaseEscrowFactory._postInteraction()` parses `integratorFeeRecipient` / `protocolFeeRecipient` directly from `extraData` (attacker-controllable order extension bytes, committed only by the maker's signature — no on-chain whitelist or non-zero check) and stores them, along with the computed `protocolFeeAmount`/`integratorFeeAmount`, into `DstImmutablesComplement.parameters`. [1](#0-0) [2](#0-1) 

2. `EscrowDst._withdraw()` blindly trusts whatever recipient addresses are embedded in `immutables.parameters` and transfers the fee amounts to them without validating they are non-zero: [3](#0-2) 

There is no on-chain check anywhere in `BaseEscrowFactory.sol`, `ImmutablesLib.sol`, or `EscrowDst.sol` that `protocolFeeRecipient`/`integratorFeeRecipient` extracted from calldata is non-zero — exactly the same missing guard as the `PANTHEON.sol` `FEE_ADDRESS` bug, just moved from an owner-config variable into unchecked calldata fields.

However, tracing who controls this value: the `extraData` consumed in `_postInteraction` is part of the order's `extension`, whose hash is committed inside the order (signed by the maker) — the maker is an unprivileged, ordinary swap user who can freely choose to encode `protocolFeeRecipient = address(0)` / `integratorFeeRecipient = address(0)` while keeping a non-zero fee percentage. When a resolver fills that order (a normal, expected fill action, not a privileged/malicious-resolver action — the resolver isn't required to inspect fee-recipient correctness on-chain), the computed `protocolFeeAmount`/`integratorFeeAmount` are locked into the destination escrow's immutable `parameters` and later paid to the zero address on `withdraw()`, permanently burning value that should have gone to the protocol/integrator.

This matches the bounty's "unprivileged user" attacker model (order-fill lifecycle) and the "High: theft or permanent loss of unclaimed fee-like value" impact class, since the fee funds are actually locked into escrow (funded by the resolver as part of destination escrow creation) and then burned to `address(0)` on withdrawal — an on-chain, unrecoverable loss with no counter-check against a canonical/expected recipient address.

### Title
Zero-Address Fee Recipients in Order Extension Cause Permanent Loss of Protocol/Integrator Fees - (File: contracts/BaseEscrowFactory.sol / contracts/EscrowDst.sol)

### Summary
`BaseEscrowFactory._postInteraction()` extracts `protocolFeeRecipient` and `integratorFeeRecipient` directly from the maker-signed order `extraData` with no non-zero validation, and bakes the corresponding fee amounts into the destination escrow's immutable `parameters`. `EscrowDst._withdraw()` later transfers the fee amounts to whatever address was embedded, without any zero-address or sanity check — mirroring the PANTHEON `FEE_ADDRESS` bug where fees silently go to `address(0)`.

### Finding Description
`_postInteraction` parses the first 40 bytes of `extraData` as `integratorFeeRecipient`/`protocolFeeRecipient` and computes fee amounts via `FeeTaker._getFeeAmounts`, then packs both amounts and recipients into `DstImmutablesComplement.parameters` with no validation that the recipients are non-zero. [1](#0-0) 
`ImmutablesLib` merely decodes these values without any sanity checks. [4](#0-3) 
When the destination escrow is later withdrawn, `EscrowDst._withdraw()` unconditionally sends the fee amounts to the recipients decoded from `immutables.parameters`. [5](#0-4) 
Since the `extraData`/extension is committed by the order-creating maker (an unprivileged party) and is never checked against a canonical/expected 1inch or integrator address on-chain, a maker can encode `protocolFeeRecipient = address(0)` and/or `integratorFeeRecipient = address(0)` while leaving non-zero fee percentages. Any resolver who fills the order (an ordinary fill action, not a privileged operation) funds the destination escrow including the fee portion, and that portion is irrecoverably burned on withdrawal.

### Impact Explanation
This causes permanent, unrecoverable loss of protocol and/or integrator fee revenue that was already collected/allocated within the destination escrow — matching the bounty's High-severity class "theft or permanent loss of unclaimed fee-like value" during the live swap lifecycle, triggered purely by an unprivileged maker's order construction with no admin, resolver, or governance involvement required.

### Likelihood Explanation
Likely reachable: crafting an order extension with a zero fee-recipient field requires no special privilege — any user creating a limit order through the standard flow controls the extension bytes that are hash-committed into their own signed order. No on-chain guard in `BaseEscrowFactory.sol` or `EscrowDst.sol` prevents this, so the only barrier is whether resolvers/off-chain tooling filter such malformed orders, which is not an enforced on-chain invariant.

### Recommendation
Add explicit non-zero checks on `protocolFeeRecipient` and `integratorFeeRecipient` in `_postInteraction` (and in `createDstEscrow`'s parameters validation) before they are baked into escrow immutables, e.g., `if (protocolFeeAmount > 0 && protocolFeeRecipient == address(0)) revert InvalidFeeRecipient();` (and similarly for the integrator fee), analogous to pre-setting/validating `FEE_ADDRESS` in the PANTHEON recommendation.

### Proof of Concept
1. A maker creates and signs a cross-chain swap order whose `extension` extraData encodes a non-zero `protocolFee`/`integratorFee` percentage but sets `protocolFeeRecipient` and `integratorFeeRecipient` to `address(0)` (the 40 leading bytes consumed in `_postInteraction`).
2. A resolver fills the order via the Limit Order Protocol; `_postInteraction` computes non-zero `protocolFeeAmount`/`integratorFeeAmount` and stores `address(0)` recipients into `DstImmutablesComplement.parameters` — no revert occurs. [2](#0-1) 
3. The resolver calls `createDstEscrow`, funding the destination escrow with `amount + safetyDeposit`, implicitly including the fee portion.
4. Upon `withdraw()`, `EscrowDst._withdraw()` sends `protocolFeeAmount`/`integratorFeeAmount` to `address(0)`, permanently burning the fee value instead of routing it to 1inch/integrator. [5](#0-4)

        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
