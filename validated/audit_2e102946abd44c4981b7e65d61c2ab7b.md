### Title
Coordinator treats a stale rejection weight as authoritative over a later valid signature threshold, causing a validly-signed block to be discarded - ([File: stacks-node/src/nakamoto_node/signer_coordinator.rs])

### Summary
`SignerCoordinator::get_block_status` accumulates `total_weight_rejected` and `total_weight_approved` in the shared `BlockStatus` independently and never reconciles them when a signer changes its mind from reject to accept for the same block. Because the coordinator's decision loop checks the rejection condition before the acceptance condition, a block that has legitimately reached the 70% signature threshold can be discarded as `SignersRejected` if a blocking minority's earlier (and since-superseded) rejection weight is still on the books. This is the same class of bug as the vault report: two independently-tracked "limit" counters (reject-weight vs approve-weight) are allowed to both cross their threshold at once, and the code path that fires first wins, freezing/discarding valid progress instead of reconciling the two.

### Finding Description
Per the documented signer semantics (`docs/signer-flows.md`, section 6/`store_and_process_block_rejection`), a signer's rejection is explicitly a *revocable opinion*: `LocallyRejected --> LocallyAccepted: re-evaluated` is a valid transition, and a signer that rejected a proposal may later sign it once conditions change (e.g. `check_block_against_signer_db_state` re-evaluation, or receiving enough pre-commits). When that happens, the signer broadcasts a fresh `BlockResponse::Accepted` for the same `signer_signature_hash` it previously rejected.

On the node/coordinator side, `StackerDBListener`'s event loop tracks these independently in a single `BlockStatus`:
- On `BlockResponse::Rejected`, it does `block.responded_signers.insert(slot_id)` and, if new, adds the signer's weight to `total_weight_rejected` [1](#0-0) .
- On `BlockResponse::Accepted`, it separately checks only `!block.gathered_signatures.contains_key(&slot_id)` and adds the same signer's weight to `total_weight_approved` [2](#0-1) .

Nothing in the accept path removes that signer's weight from `total_weight_rejected`, and nothing in the reject path checks whether the signer already accepted. `total_weight_rejected` is only ever reset to 0 via `reset_rejections`, which is invoked solely on the coordinator's overall wait-loop timeout [3](#0-2) , not whenever a rejecting signer subsequently accepts.

In `SignerCoordinator::get_block_status`, the wait predicate returns control to the caller as soon as either the rejection count changes or the approval weight reaches threshold [4](#0-3) . The loop body then evaluates the reject condition strictly before the accept condition:

```
if block_status.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight {
    ... return Err(NakamotoNodeError::SignersRejected { ... });
} else if block_status.total_weight_approved >= self.weight_threshold {
    ... return Ok(...);
}
``` [5](#0-4) 

Because a stale, already-superseded rejection weight from a signer who later accepted is never cleared, `total_weight_rejected` can independently exceed the blocking-minority threshold (`total_weight - weight_threshold`) at the exact same time `total_weight_approved` legitimately reaches `weight_threshold` (70%). Since the reject branch is checked first, the coordinator declares the block dead (`SignersRejected`) even though it actually carries a valid, threshold-crossing set of signatures.

This exactly mirrors the vault report's root cause: two independently-tracked threshold conditions ("min proportionality"/reject-lock and "max proportionality"/approve-lock analogues) can be satisfied simultaneously due to stale/non-reconciled state, and the code's fixed check ordering resolves the conflict in the wrong direction instead of detecting/preventing the double-count.

### Impact Explanation
This is a liveness wedge on block production: a block that a supermajority of signers actually signed can be discarded by the miner/coordinator as rejected. Beyond wasted tenure time, the coordinator also permanently or temporarily bans any txid that the blocking-minority rejectors flagged as failed (`permanently_excluded_txids`/`temporarily_excluded_txids`, computed from the same stale `failed_txids` map) [6](#0-5) , even though those signers ultimately signed off on the block. This falls under the "signer/coordinator wedged into never making progress on valid signer output" liveness category.

### Likelihood Explanation
This requires only ordinary signer behavior already exercised by the codebase's own tests (a signer rejecting a proposal, then re-evaluating and signing it later, e.g. after a pre-commit threshold re-check or a conflict going stale) combined with timing such that the stale rejection weight from a blocking minority persists while the remaining/same signers push approval over 70%. No signer key compromise or majority collusion is required — a single miner orchestrating proposal/re-proposal timing (as already modeled in the repo's own sibling-scenario tests) combined with signers whose local state legitimately flips from reject to accept is sufficient to reach this code path.

### Recommendation
Reconcile the two counters instead of tracking them independently: when a signer's `BlockResponse::Accepted` arrives, remove their prior contribution (if any) from `total_weight_rejected` (and vice versa upon a later rejection overriding an earlier acceptance, if that is intended to be possible), so a signer's weight can only count toward one side at a time. Alternatively, compute `total_weight_rejected` from the current set of *outstanding* rejecting signers only, excluding any signer present in `gathered_signatures`.

### Proof of Concept
1. Miner proposes block `B`. Coordinator's `BlockStatus` for `B` starts empty.
2. A blocking-minority subset of signers `R` (weight > `total_weight - weight_threshold`) initially reject `B` (e.g., because their local chainstate check transiently disagrees, per `check_block_against_signer_db_state`); their weight is recorded in `total_weight_rejected` [1](#0-0) .
3. `R`'s local state re-evaluates (as covered by the "re-evaluated" transition and covered by existing repo tests like `reproposal_signs_replacement_after_conflict_times_out`), and they now sign `B`, broadcasting `BlockResponse::Accepted`.
4. The coordinator's listener adds `R`'s weight to `total_weight_approved` without touching `total_weight_rejected` [2](#0-1) . Combined with the rest of the signer set's approvals, `total_weight_approved >= weight_threshold` is now true, while `total_weight_rejected` (still holding `R`'s stale rejection) remains above the blocking-minority threshold.
5. On the next wake of `get_block_status`'s wait loop, the reject branch is checked first and the coordinator returns `Err(SignersRejected)` for `B`, discarding a block that in fact carries valid signatures over the 70% threshold [7](#0-6) .
