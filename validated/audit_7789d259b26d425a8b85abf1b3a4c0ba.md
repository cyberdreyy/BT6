### Title
Authenticated External Initiator (EI) requests satisfy the `isUser` check and can trigger `RunJobV2` for arbitrary job IDs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates manual job-run triggering on `auth.GetAuthenticatedUser`, but that helper only checks whether *any* `*clsessions.User` object was stored in the Gin context under `SessionUserKey` — it cannot distinguish a genuine session/API-token user from an External Initiator (EI) that was granted a synthetic `UserRoleRun` user object by `AuthenticateExternalInitiator`. Because of this, an EI credential holder can satisfy the `isUser` check and call `RunJobV2` for any `int32` job ID on the node, not only the job(s) actually registered to that EI in `external_initiator_webhook_specs`.

### Finding Description
In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` explicitly documents and implements EI requests as assuming the "run" role by storing a synthetic user object: [1](#0-0) 

`GetAuthenticatedUser` simply reads whatever object is stored under `SessionUserKey`: [2](#0-1) 

This means an EI-authenticated request context is indistinguishable from a genuine session/API-token user context — both produce `ok == true` from `GetAuthenticatedUser`.

In `PipelineRunsController.Create`, the code comment explicitly states the intent that EIs should not be allowed to use this int-ID path ("only users are allowed to run jobs using int IDs - EIs not allowed"), and the only guard against EI use is a UUID-parsing check (rejecting the legacy webhook-by-UUID path) combined with `isUser`: [3](#0-2) 

Because `isUser` is `true` for both real users and EI-authenticated requests (per the synthetic user set in `auth.go`), an EI credential holder who supplies an `int32` job ID (any job ID, not necessarily tied to that EI) passes the `isUser` gate and reaches `prc.App.RunJobV2(ctx, jobID, nil)`. `RunJobV2` performs no ownership or EI-to-job binding check — it simply loads the job by ID and executes its pipeline: [4](#0-3) 

There is no lookup against `external_initiator_webhook_specs` anywhere in this call path to confirm the calling EI is actually associated with the target job. The authorization check is role-based only ("is there a run-capable user in context"), not binding-based ("is this specific EI allowed to run this specific job").

### Impact Explanation
An EI credential (which is meant to be scoped to trigger only its own registered webhook job(s)) can be used to trigger pipeline execution of *any* job on the node by ID, including jobs the EI has no legitimate relationship with. This is an authorization/role-boundary bypass leading to unauthorized job execution, which can result in unintended on-chain transactions, unauthorized fund movement (for jobs that submit transactions), or unauthorized consumption of node/bridge resources — matching the "unauthorized job run" bounty impact class. Note: this vulnerability path is only reachable in non-production builds, since `RunJobV2` immediately returns an error when `build.IsProd()` is true, which materially limits real-world severity on secure/production node builds.

### Likelihood Explanation
Preconditions: attacker must possess valid EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` or equivalent headers) for some external initiator registered on the node, and the node must be running a non-production build (`build.IsProd() == false`). No other privilege (session, API token, admin) is required. Given a valid EI credential, exploitation is a single unauthenticated-role HTTP POST to `/v2/jobs/:ID/runs` with an arbitrary `int32` job ID — no additional steps needed, making it trivially repeatable.

### Recommendation
Distinguish EI-derived authentication from genuine user authentication in `PipelineRunsController.Create` (e.g., check `auth.GetAuthenticatedExternalInitiator` and reject if present, rather than relying solely on `isUser`), and/or have `RunJobV2` (or a wrapper) verify that the calling principal (when an EI) is bound to the target job via `external_initiator_webhook_specs` before executing the pipeline.

### Proof of Concept
Go handler-level integration test plan:
1. Set up a test node with two jobs, `jobA` (registered to `EI1` in `external_initiator_webhook_specs`) and `jobB` (not related to `EI1`).
2. Authenticate as `EI1` via `AuthenticateExternalInitiator` (valid access key/secret headers).
3. Issue `POST /v2/jobs/{jobB.ID}/runs` (integer ID of `jobB`, not associated with `EI1`).
4. Assert the current (buggy) behavior: `isUser` is `true` (because `AuthenticateExternalInitiator` set a synthetic `UserRoleRun` user), `RunJobV2` is invoked, and a `201`/success response with a pipeline run resource is returned for `jobB`.
5. Add a table-test asserting the expected/fixed behavior: the request should be rejected with `401`/`403` because `jobB` is not bound to `EI1` in `external_initiator_webhook_specs`, verifying that fixing the check to include EI/job binding causes rejection while a request for `jobA` (properly bound) still succeeds.

// GetAuthenticatedUser extracts the authentication user from the context.
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
