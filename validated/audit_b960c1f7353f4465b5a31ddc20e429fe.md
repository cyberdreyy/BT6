### Title
Missing sender allowlist enforcement in legacy `HandleLegacyUserMessage` allows any signed message to reach any configured DON - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
The gateway's `ProcessRequest` in `core/services/gateway/gateway.go` routes any legacy `Message` whose `Body.DonId` matches a configured handler directly to `handler.HandleLegacyUserMessage`, requiring only a syntactically valid, self-signed message. `HandleLegacyUserMessage` itself contains an explicit `// TODO: apply allowlist and rate-limiting here` and performs no check that the message's signer/sender has any legitimate relationship with the target DON before forwarding the request to every node in that DON.

### Finding Description
In `core/services/gateway/gateway.go` lines 250-262, when `msg.Body.DonId != ""` the gateway takes the legacy path: it calls `msg.Validate()` (which only checks field lengths/formats and extracts the signer address via `ExtractSigner`, see `core/services/gateway/api/message.go` lines 54-88) and looks up the handler purely by `handlerKey = msg.Body.DonId` in `g.handlers`. No check ties the extracted `msg.Body.Sender` to any permission for that specific DON.

Once routed, `handler.HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` (lines 341-421) validates only:
- payload unmarshal success,
- `payload.Timestamp` non-zero and not stale,
- `msg.Body.Method == MethodWebAPITrigger`.

Immediately following these checks is the comment `// TODO: apply allowlist and rate-limiting here` (line 384), confirming no allowlist/authorization check is implemented for who may send a trigger message for a given DON. The handler then forwards the message to **every node** in `h.donConfig.Members` via `don.SendToNode` (lines 416-419).

Because `Message.Sign`/`SignKS` (in `api/message.go`) works with any ECDSA key the attacker controls (no registration required to produce a syntactically valid signature), an attacker who knows/guesses a valid `don_id` string (these are often predictable, e.g., derived from DON name) can self-sign an arbitrary `web_api_trigger` message and have the gateway forward it to all nodes of a DON they have no registered relationship with.

### Impact Explanation
This is an allowlist/authorization bypass at the gateway layer: an unprivileged attacker can inject arbitrary attacker-controlled `web_api_trigger` payloads into a DON's node set without any registered relationship to that DON, forwarded to every member node. Depending on downstream (DON-side) trust in the gateway's forwarding, this can result in unauthorized triggering of workflow processing, resource exhaustion (spam) of DON nodes, or forged trigger data being processed by nodes as if legitimately gateway-relayed — matching the "allowlist/quota bypass" and "unauthorized job run" impact classes called out in scope.

### Likelihood Explanation
Low operational barrier: the attacker needs only (1) the network-reachable gateway user-facing HTTP endpoint, (2) a known/guessed `don_id` string, and (3) the ability to generate an ECDSA keypair and sign a message per the documented raw-body format (`GetRawMessageBody`) — no credentials, prior registration, or DON membership are required. The missing check is explicitly marked as unimplemented (`TODO`) rather than incidentally absent, making this a confirmed gap rather than a hypothetical one. It is fully repeatable per request.

### Recommendation
Implement the allowlist check referenced by the TODO before forwarding: verify `msg.Body.Sender` (or equivalent request-level identity) against a DON-specific allowlist of authorized senders/workflow owners prior to invoking `don.SendToNode`, and add per-sender/per-DON rate limiting in `HandleLegacyUserMessage`, consistent with what already exists for node-rate-limiting (`h.nodeRateLimiter`).

### Proof of Concept
Handler-level Go test plan in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` via `NewHandler` with a `donConfig` containing one or more `Members`, backed by a mock `handlers.DON`.
2. Generate an arbitrary ECDSA key not present anywhere in `donConfig` or any allowlist.
3. Build an `api.Message` with `Body.Method = MethodWebAPITrigger`, `Body.DonId` set to the handler's configured DON ID, and a valid `webapicap.TriggerRequestPayload` (with fresh `Timestamp`); sign it with the attacker key via `msg.Sign(attackerKey)`.
4. Call `h.HandleLegacyUserMessage(ctx, msg, callback)` and assert:
   - No error/rejection is returned due to sender identity,
   - The mock `don.SendToNode` is invoked once per `donConfig.Members` entry with the attacker's forwarded request,
   - Confirm no allowlist/authorization related error code (e.g., a hypothetical `Unauthorized`) is ever produced, demonstrating the absence of the check described in the TODO.
