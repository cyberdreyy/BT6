### Title
Per-workflow (not per-owner) HTTP trigger rate limit allows quota bypass via multiple workflow IDs under one owner - ([File: core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go])

### Summary
The gateway's HTTP trigger rate limiter is keyed by `settings.ScopeWorkflow` (workflow ID), not by workflow owner, despite the handler's documentation claiming "per-workflow-owner" rate limits. A single owner who registers/controls multiple workflow IDs gets an independent rate-limit bucket per workflow ID, allowing them to multiply their effective throughput against the DON by simply rotating which workflow ID they submit trigger requests under.

### Finding Description
`httpTriggerHandler.checkRateLimit` builds the rate-limit context via `contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Workflow: workflowID})` and then calls `h.userRateLimiter.AllowErr(ctx)` [1](#0-0) . The rate limiter itself is constructed from `cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit` [2](#0-1) , i.e. a setting under the `PerWorkflow` settings namespace. When the limit is exceeded, the error path explicitly branches on `settings.ScopeWorkflow` as the expected/handled scope (`case settings.ScopeWorkflow: ... "per workflow rate limit exceeded"`), confirming the limiter's bucket key resolves at workflow scope rather than owner scope [3](#0-2) .

Because the settings-resolution hierarchy in this codebase is `workflow.<id> → owner.<id> → org.<id> → global` (most-specific first, as documented for the CRE settings system) [4](#0-3) , and the `PerWorkflow.HTTPTrigger.RateLimit` setting/limiter operates at `ScopeWorkflow`, each distinct `workflowID` gets its own independent token bucket, keyed on `contexts.CRE.Workflow`. The `Owner` field is carried in the context for logging/metrics but is not what the limiter buckets on for this particular limiter (contrast with `syncerlimiter.NewWorkflowLimits`, which explicitly builds an owner-scoped limiter keyed on `contexts.CREValue(ctx).Owner` for a different purpose — workflow *count* limits, not HTTP trigger *rate* limits [5](#0-4) ).

An attacker who is a single owner but registers/selects N different workflow IDs (workflow ID creation is cheap — it only requires a valid workflow registration with a distinct name/tag under the same owner address, validated only for hex format in `validateWorkflowID`/`resolveWorkflowID`) can submit trigger requests varying only the `workflowID` (or `workflowName`/`workflowTag` combination) selector while keeping the same owner/signing key. Each workflow ID resolves to a separate `ScopeWorkflow` bucket in `h.userRateLimiter`, so the attacker's aggregate throughput scales linearly with the number of workflow IDs they control, rather than being capped by a single owner-level quota.

### Impact Explanation
This is a rate-limit/quota bypass (allowlist/quota bypass impact class): an attacker can exceed the DON operator's intended per-owner fair-share of trigger execution capacity by fragmenting requests across multiple owned workflow IDs, causing disproportionate consumption of shared DON execution capacity ("free/excess DON execution" as described in the question) at the expense of other tenants. It does not grant cross-tenant data access or credential compromise, but it does defeat the fairness/anti-abuse control the rate limiter is meant to enforce.

### Likelihood Explanation
Feasibility is high: no privileged access is required beyond being a normal workflow owner who can register additional workflow IDs (cheap, self-service action available to any owner). The attack requires only varying the `workflowID`/`workflowName`+`workflowTag` selector in the JSON-RPC `workflows.execute` params while reusing the same owner key for authorization (`authorizeRequest` validates the signing key against the workflow's owner but does not aggregate rate-limit state across workflows owned by that key) [6](#0-5) . It is fully repeatable and requires no timing races or race conditions — it is a straightforward mechanical proof by table test asserting the limiter's key/scope.

### Recommendation
Add or switch to an owner-scoped rate limiter (analogous to `PerOwner.*` settings and the pattern used in `syncerlimiter.NewWorkflowLimits`) so that `checkRateLimit` enforces a quota keyed on `workflowRef.workflowOwner` in addition to (or instead of) the per-workflow-ID bucket. Concretely: introduce a `PerOwner.HTTPTrigger.RateLimit` cresetting, construct a second `limits.RateLimiter` from it in `NewGatewayHandler`, and require both the per-workflow and per-owner limiters to `Allow` in `checkRateLimit`, so an owner cannot escape the aggregate cap merely by spreading load across multiple workflow IDs.

### Proof of Concept
Go handler-level integration test plan in `core/services/gateway/handlers/capabilities/v2`:
1. Construct a `gatewayHandler`/`httpTriggerHandler` with `cresettings.Default.PerWorkflow.HTTPTrigger.RateLimit` set to a small limit (e.g. 1 request per 5s per workflow, via `cresettings` override as shown in `cresettings_override_test.go`).
2. Register two (or more) distinct workflow IDs under the *same* `workflowOwner` in the metadata handler's workflow reference table.
3. Submit `N` trigger requests for `workflowID_1` from the same owner and assert the first is allowed and the second (within the window) is throttled (`jsonrpc.ErrLimitExceeded`, `settings.ScopeWorkflow`).
4. Submit a request for `workflowID_2` (same owner, immediately after step 3's throttle) and assert it is **allowed**, demonstrating that the owner's overall request rate is not capped in aggregate — i.e., total allowed throughput scales with number of workflow IDs owned, violating the intended "per-workflow-owner" invariant.
5. Add a table test iterating over `{1, 5, 50}` workflow IDs for one owner, asserting total successful trigger requests within the rate window equals `numWorkflowIDs × perWorkflowLimit`, not `perWorkflowLimit` alone — proving the bypass.

func (h *httpTriggerHandler) checkRateLimit(ctx context.Context, workflowID, requestID string, callback handlers.Callback) error {
	workflowRef, found := h.workflowMetadataHandler.GetWorkflowReference(workflowID)
	if !found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "workflow reference not found", callback)
		return errors.New("workflow reference not found")
	}

	// TODO orgID https://smartcontract-it.atlassian.net/browse/CRE-1707
	ctx = contexts.WithCRE(ctx, contexts.CRE{Owner: workflowRef.workflowOwner, Workflow: workflowID})
	if err := h.userRateLimiter.AllowErr(ctx); err != nil {
		lggr := logger.With(h.lggr, platform.KeyWorkflowID, workflowID, platform.KeyWorkflowOwner, workflowRef.workflowOwner, "requestID", requestID, "err", err)
		if errLimited, ok := errors.AsType[limits.ErrorRateLimited](err); ok {
			switch errLimited.Scope {
			case settings.ScopeWorkflow:
				lggr.Errorf("failed to start execution: per workflow rate limit exceeded")
				h.metrics.IncrementWorkflowThrottled(ctx, h.lggr)
			default:
				lggr.Errorf("failed to start execution: unexpected rate limit for scope %s", errLimited.Scope)
			}
			h.handleUserError(ctx, requestID, jsonrpc.ErrLimitExceeded, "rate limit exceeded", callback)
			return err
		}
		return fmt.Errorf("failed to check rate limit: %w", err)
	}
	return nil
}

type keyedOwnerSettings struct {
	getter settings.Getter
	key    string
	vals   map[string]string
}

func (k keyedOwnerSettings) GetScoped(ctx context.Context, scope settings.Scope, key string) (value string, err error) {
	if k.getter != nil {
		value, err = k.getter.GetScoped(ctx, scope, key)
	}
	if value != "" {
		return
	}
	if k.key != key || scope != settings.ScopeOwner {
		return "", nil
	}
	return k.vals[contexts.CREValue(ctx).Owner], nil
}
