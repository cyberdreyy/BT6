### Title
Cross-tenure signature-conflict guard silently disarms on a local timer, letting a signer double-sign at the same height once a fresh proposal in an unrelated tenure arrives - (File: stacks-signer/src/v0/signer.rs)

### Summary
`handle_block_pre_commit` guards a signer against endorsing two conflicting blocks at the same Stacks height by querying `SignerDb::get_signed_conflicts`, which deliberately spans **all** tenures [1](#0-0) . But that guard only blocks a conflict while it is "fresh" (`conflict.last_endorsed > freshness_cutoff`), and freshness is a **local wall-clock check**, not a node-verified death check [2](#0-1) . Once a conflict falls outside `tenure_last_block_proposal_timeout`, the only guard executed afterward re-checks conflicts in the *proposed block's own tenure only* [3](#0-2) . A stale conflict that lives in a **third tenure** (neither the proposal's own tenure nor its tenure-change parent) is never re-verified against the node at all before the signature is produced.

### Finding Description
The pre-commit signing path in `Signer::handle_block_pre_commit` runs two sequential guards before calling `mark_locally_accepted`/signing:

1. `check_block_against_signer_db_state`, which only looks at **one** tenure: the tenure-change block's parent tenure (`check_tenure_change_confirms_parent`) or, for any other block, its own tenure (`check_latest_block_in_tenure`) [4](#0-3) . This is explicitly documented as covering only that single tenure [5](#0-4) .

2. The any-tenure conflict scan from `get_signed_conflicts`, but the loop that can actually *block* a stale, cross-tenure conflict requires `conflict.last_endorsed > freshness_cutoff` as the first (short-circuiting) predicate [6](#0-5) . `freshness_cutoff` is derived purely from `get_epoch_time_secs()` minus a configured duration [7](#0-6)  — it says nothing about whether the node has actually confirmed the earlier tenure/block dead. Once a conflict ages past that timer, this predicate is false and the conflict is dropped from consideration, regardless of `conflict_still_blocks`'s answer.

3. The remaining check, at lines 1432-1457, only re-examines conflicts whose `consensus_hash` equals the **proposed block's own tenure** [8](#0-7) . A stale conflict recorded in some other (third) tenure is therefore never asked about again.

The design comment in the codebase acknowledges this gap and asserts it is safe because "whether this block may replace what another tenure built is settled by the chainstate checks above" [9](#0-8) . But "the chainstate checks above" (`check_block_against_signer_db_state`, step 1) only examine the proposal's own/parent tenure, not the third tenure where the stale conflict actually lives. So for a conflict recorded in a tenure that is neither the proposal's own tenure nor its tenure-change parent, **no code path ever re-asks the node whether that earlier, already-signed block is still live** before the second signature is produced. `get_signed_conflicts` is explicitly designed to be cross-tenure precisely because "two blocks at the same height are siblings no matter which tenure they belong to" [10](#0-9) , yet the enforcement mechanism for stale members of that set silently narrows back to same-tenure only.

### Impact Explanation
If exploited, a single signer can be induced to place its threshold signature over two blocks at the same Stacks height in different tenures — a textbook equivocation/double-sign, which is exactly the "Critical" impact class called out for this scan (a signer signing a conflicting block; a rejection/staleness mistakenly recounted as safe-to-sign). Because the guard is time-based rather than node-verified, this does not require compromising a majority of signers, the auth token, or any key material — only causing a delay (natural network latency, a stalled proposal, a temporarily unreachable node, or simply the passage of the configured timeout) between the first tenure's signature and a later, cross-tenure proposal at the same height.

### Likelihood Explanation
The precondition — a rival tenure surfacing at a height already signed in another tenure, and enough elapsed time for the first signature to go "stale" per `tenure_last_block_proposal_timeout` — is one the codebase already anticipates repeatedly elsewhere in this file (fork/reorg handling, `conflict_still_blocks`, `reorg_permit_stands`). It is realistically reachable by an adversarial miner sequence (mine tenure A, get it fully signed, let its own proposal pipeline stall/timeout past the configured window, then mine or continue a competing tenure B to the same Stacks height) without needing cooperation from other signers. I was not able to fully confirm the exact default value of `tenure_last_block_proposal_timeout` from the search results (matches were found in `stacks-signer/src/config.rs` per `grep_search`, but the specific default line wasn't retrieved before the iteration budget ran out), so I cannot state precisely how large this exploitation window is in practice — this is an acknowledged gap in my verification.

### Recommendation
Remove the freshness short-circuit for cross-tenure conflicts, or make `conflict_still_blocks` (the node-verified liveness check) authoritative regardless of local staleness for conflicts outside the proposal's own/parent tenure — i.e., only skip the node round-trip once `conflict_still_blocks` (or an equivalent node-confirmed-orphaned check) has actually returned "dead," never purely because a local timer elapsed. Alternatively, extend `check_block_against_signer_db_state` to also cover conflicts recorded in tenures other than the proposal's own/parent tenure before allowing a second signature at the same height.

### Proof of Concept
Conceptual sequence (cannot be executed here, but traceable directly in the cited code):
1. Miner A's tenure T1 proposes block N at height H; the signer set (including the victim signer) pre-commits and signs it, and the block is at least `LocallyAccepted`/`GloballyAccepted` — `signed_self`/`signed_group` is set, recorded by `get_signed_conflicts` with `last_endorsed` = that signing time.
2. No further proposal reaches the victim signer for longer than `tenure_last_block_proposal_timeout` (network delay, stalled miner, or an adversary simply waiting).
3. A different tenure T2 (already at height H-1 through its own prior blocks — e.g., surfacing from a parallel fork the signer previously tracked) proposes a block at the same height H. This proposal is neither a tenure-change block whose parent is T1, nor is it in T1's own tenure, so `check_block_against_signer_db_state` only inspects T2 (or T2's own parent), never T1.
4. In `handle_block_pre_commit`, `get_signed_conflicts(H, …)` returns the T1 block as a conflict, but `conflict.last_endorsed <= freshness_cutoff` now, so the `find()` at lines 1403-1421 skips it entirely — `conflict_still_blocks`/`reorg_permit_stands` are never even called for it.
5. The own-tenure check at lines 1432-1457 only matches conflicts whose `consensus_hash == block_info.block.header.consensus_hash` (T2), so the T1 conflict is not caught there either.
6. The signer proceeds to `mark_locally_accepted` and signs the T2 block at height H — producing a second, conflicting signature at the same height as the still-possibly-canonical T1 block, purely because of elapsed local time rather than any node-confirmed proof that T1 is dead.
