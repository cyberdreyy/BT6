### Title
Missing context/timeout propagation in `defaultAzureKeyVault.GetSecret` causes unkillable goroutine/socket leak on job cancellation - (File: helpers/azure_key_vault/service/azure_key_vault.go)

### Summary
`defaultAzureKeyVault.GetSecret` issues the Azure SDK call with `context.Background()` instead of a context derived from the job's cancellation/timeout context, and the secret-resolution call chain (`Build.resolveSecrets` → `attemptResolveSecrets` → `executeResolveSecretsStage` → resolver → `GetSecret`) never threads a `context.Context` at all. When a job references an Azure Key Vault server whose endpoint accepts a TCP connection but never responds, the call blocks forever and is immune to the job's own timeout/cancellation, leaking a goroutine and an open connection for the life of the runner process.

### Finding Description
`defaultAzureKeyVault.GetSecret` calls `v.client.GetSecret(context.Background(), name, version, nil)` with no deadline: [1](#0-0) .

Tracing the call chain upward: `azureKeyVaultResolver.Resolve` calls `s.GetSecret(name, version)` synchronously with no context parameter at all [2](#0-1) . This is invoked from `Build.executeResolveSecretsStage`, again with no context [3](#0-2) , which is wrapped by `Build.attemptResolveSecrets` using `retry.New().WithMaxTries(attempts)` — note `retry.New()` defaults to `ctx: context.Background()` and `WithContext` is never called here, so the retry loop itself also has no deadline [4](#0-3) [5](#0-4) . `resolveSecrets(trace JobTrace)` (called from the job's `Run`/`executeScript` path) has no `ctx` parameter either [6](#0-5) .

Because the entire secret-resolution stage runs synchronously inside the goroutine spawned by `Build.run` (`buildFinish <- b.executeScript(...)`), a hang in `GetSecret` means `executeScript` never returns and `buildFinish` never fires [7](#0-6) . The outer `select` does correctly react to `ctx.Done()` (job timeout/cancel) and moves on to report failure, then calls `waitForBuildFinish(buildFinish, WaitForBuildFinishTimeout)`, which gives up after a bounded timeout and simply returns, leaving the underlying goroutine running [8](#0-7) . Since `GetSecret` used `context.Background()`, the goroutine executing it is **not** killed by this cancellation — it remains blocked on the network call indefinitely, holding a goroutine and (depending on the Azure SDK transport) an open TCP connection, for the remaining lifetime of the runner process (there is no process-wide reaper for this leaked goroutine).

The `Server.URL` for an Azure Key Vault secret reference is part of job-supplied secrets configuration (`spec.AzureKeyVaultServer` populated from the job payload processed by the resolver), so a pipeline author who can configure a `secrets:` entry pointing at an attacker-controlled or non-responsive vault endpoint can trigger this hang without any special runner or admin privilege.

Existing protections do not stop this: there is no per-call HTTP/TLS client timeout configured on `azsecrets.NewClient` (`azcore.ClientOptions{}` is empty, using SDK defaults which do not include a request deadline) [9](#0-8) , no context propagation from the job's cancellation tree into `GetSecret`, and `waitForBuildFinish`'s bounded wait only stops the *runner from reporting the job as still running* — it does not, and cannot, terminate the leaked goroutine.

### Impact Explanation
Each job that references a non-responsive/malicious Azure Key Vault endpoint leaks one goroutine plus an open socket for the remainder of the runner process's life, entirely decoupled from the job's own timeout/cancellation. This is a real resource leak reachable by an unprivileged pipeline author who controls the Azure Key Vault server reference in a job's `secrets:` configuration. Repeated triggering (e.g., via a CI schedule or repeated pipeline runs) accumulates leaked goroutines/connections on the shared runner host, degrading it over time and potentially affecting other tenants' jobs on the same runner (through memory/FD/goroutine pressure), even though the individual job's own concurrency slot is freed after `WaitForBuildFinishTimeout`.

### Likelihood Explanation
Highly feasible and fully attacker-controllable: a normal pipeline author only needs to define a `secrets:` block referencing an Azure Key Vault server they control (or a firewalled/unresponsive host), reachable by the runner. No admin privilege, no leaked keys, and no cluster/GitLab-admin compromise are required. The bug is deterministic and repeatable on every such job execution.

### Recommendation
Thread a `context.Context` through the entire secret-resolution path (`resolveSecrets`, `attemptResolveSecrets`, `executeResolveSecretsStage`, `SecretResolver.Resolve`, and `AzureKeyVault.GetSecret`), derived from the job's overall cancellation/timeout context, and pass it into `v.client.GetSecret(ctx, ...)` instead of `context.Background()`. Additionally, apply a bounded per-request timeout (e.g., via `context.WithTimeout` or an `azcore.ClientOptions` retry/transport timeout) so a single hung upstream call cannot outlive the job or leak indefinitely.

### Proof of Concept
Go unit/integration test plan:
1. In `helpers/azure_key_vault/service`, construct a fake `azsecrets.Client` (or wrap `defaultAzureKeyVault` behind an interface substitution) whose `GetSecret` blocks on an unbuffered channel/`select{}` until the test explicitly releases it.
2. Call `Build.attemptResolveSecrets(trace, attempts)` with `attempts > 1` from a goroutine, and simultaneously cancel/timeout the job's `ctx` used in `Build.run`.
3. Assert that:
   - `Build.run` returns (job reported as timed out/canceled) within `WaitForBuildFinishTimeout`.
   - The mocked `GetSecret` call is still blocked/running afterward (e.g., via a "call started" channel that never receives a matching "call finished" signal), proving no context cancellation reached the underlying SDK call.
   - `runtime.NumGoroutine()` remains elevated by one persistent goroutine after the job supposedly ended, demonstrating the leak.

	b.Log().Debugln("Waiting for signals...")
	select {
	case <-ctx.Done():
		err = b.handleError(context.Cause(ctx))

	case signal := <-b.SystemInterrupt:
		err = &BuildError{
			Inner:         fmt.Errorf("aborted: %v", signal),
			FailureReason: RunnerInterrupted,
		}
		b.setCurrentState(BuildRunRuntimeTerminated)

	case err = <-buildFinish:
		// It's possible that the parent context being cancelled will
		// terminate the build early, bringing us here, and although we handle
		// `ctx.Done()` above, select statements are not ordered.
		// We handle this the same as if we received ctx.Done(), but
		// return early because we're no longer waiting for the build
		// to finish.
		if ctx.Err() != nil {
			return b.handleError(context.Cause(ctx))
		}

		if err != nil {
			b.setCurrentState(BuildRunRuntimeFailed)
		} else {
			b.setCurrentState(BuildRunRuntimeSuccess)
		}
		return err

	case err = <-buildPanic:
		b.setCurrentState(BuildRunRuntimeTerminated)
		return err
	}

	b.Log().WithError(err).Debugln("Waiting for build to finish...")

	// Wait till we receive that build did finish
	runCancel()
	b.waitForBuildFinish(buildFinish, WaitForBuildFinishTimeout)

	return err
}

// waitForBuildFinish will wait for the build to finish or timeout, whichever
// comes first. This is to prevent issues where something in the build can't be
// killed or processed and results into the Job running until the GitLab Runner
// process exists.
func (b *Build) waitForBuildFinish(buildFinish <-chan error, timeout time.Duration) {
	select {
	case <-buildFinish:
		return
	case <-time.After(timeout):
		b.logger.Warningln("Timed out waiting for the build to finish")
		return
	}
}

func (b *Build) attemptResolveSecrets(trace JobTrace, attempts int) error {
	retryRunner := retry.New().WithMaxTries(attempts)

	if b.IsFeatureFlagOn(featureflags.UseExponentialBackoffStageRetry) {
		backoffConfig := b.getStageRetryBackoffConfig()
		retryRunner = retryRunner.
			WithBackoff(backoffConfig.Min, backoffConfig.Max).
			WithBuildLog(&b.logger)
	}

	return retry.NewNoValue(retryRunner, func() error {
		return b.executeResolveSecretsStage(trace)
	}).Run()
}

func (b *Build) executeResolveSecretsStage(trace JobTrace) error {
	b.OnBuildStageStartFn.Call(BuildStageResolveSecrets)
	defer b.OnBuildStageEndFn.Call(BuildStageResolveSecrets)

	section := helpers.BuildSection{
		Name:        string(BuildStageResolveSecrets),
		SkipMetrics: !b.Job.Features.TraceSections,
		Run: func() error {
			logger := b.getNewLogger(trace, b.Log(), false)
			defer logger.Close()

			resolver, err := b.secretsResolver(&logger, GetSecretResolverRegistry(), b.IsFeatureFlagOn)
			if err != nil {
				return fmt.Errorf("creating secrets resolver: %w", err)
			}

			variables, err := resolver.Resolve(b.Secrets)
			if err != nil {
				return fmt.Errorf("resolving secrets: %w", err)
			}

			b.secretsVariables = variables
			b.RefreshAllVariables()

			return nil
		},
	}

	return section.Execute(&b.logger)
}
