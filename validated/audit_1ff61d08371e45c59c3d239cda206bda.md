### Title
Signer protocol v1's `validate_tenure_change_payload` duplicate-check omits locally-accepted (already-signed) blocks, allowing a signer to sign two conflicting tenure-start blocks — (File: `stacks-signer/src/chainstate/v1.rs`)

### Summary
This is the same coverage-gap bug class as the Bleach advisory: a security-relevant check (URI sanitization for `action`) was applied to one attribute (`action`) but not an equivalent sibling attribute (`formaction`), because the allowlist set wasn't kept consistent between similar code paths. In this codebase, the analogous check is the tenure-start "duplicate block" guard in `validate_tenure_change_payload`, which exists in two parallel, protocol-version-specific implementations (v1 and v2) that are supposed to enforce the same invariant but query different, non-equivalent state.

### Finding Description
`validate_tenure_change_payload` exists in both `stacks-signer/src/chainstate/v1.rs` and `stacks-signer/src/chainstate/v2.rs`, and both are meant to reject a tenure-start block proposal if the signer has already committed to a block in that tenure:

- v1 queries only globally-accepted blocks: [1](#0-0) 

- v2 queries `get_last_signed_block`, which covers **both** locally-accepted and globally-accepted blocks: [2](#0-1) 

The v2 test suite explicitly documents that this v1-style behavior (`get_last_globally_accepted_block`) was a bug for v2 and was fixed by switching to `get_last_signed_block`: [3](#0-2) 

`docs/signer-flows.md` confirms this divergence is intentional/known but still present for v1 as of this snapshot: [4](#0-3) 

`mark_locally_accepted` in the signing flow corresponds to the point where the signer has **already produced its signature** (`SIGN: mark_locally_accepted, handle_block_signature, broadcast acceptance`), so "locally accepted" is not a tentative state — it means the signer has committed a signature to that block, well before global consensus (70% weight) is reached: [5](#0-4) 

Because v1's duplicate check only looks at *globally* accepted blocks, a v1 signer that has already signed a locally-accepted tenure-start block A (not yet globally accepted) will not detect the conflict when a competing/replacement tenure-start block B for the same tenure is proposed. The proposal-time duplicate check is also documented as never re-run at validate-ok or at signing time, so it must catch this at proposal time; the only remaining backstop is the pre-commit "own-tenure conflict guard" (`get_signed_conflicts` reasoning, section 5), which itself defers to the node's `get_tenure_tip` and explicitly allows signing when the tenure "never confirmed" — precisely the case for a tenure whose only entry is locally accepted but not globally accepted: [6](#0-5) [7](#0-6) 

This lets a v1 signer proceed to also sign block B, producing two conflicting signatures from the same signer at the same tenure-start height — breaking the equivocation guard ("one signature per height/tenure") that the duplicate check exists to enforce.

### Impact Explanation
This maps to the Critical impact category: a signer signing a conflicting block. A single miner (one-slot) can trigger it by re-proposing a different tenure-start block for the same tenure before the first locally-accepted block reaches global acceptance; no majority collusion or other signer's key is required — only the targeted v1 signer's own local state and a second proposal from the (legitimate) miner slot.

### Likelihood Explanation
Likelihood is moderate: it requires (a) a signer running the older v1 signer-protocol path (`state_version` where `uses_global_state()` is false), and (b) a tenure-start block that a signer has locally-accepted but that stalls before reaching global acceptance — a scenario the codebase itself acknowledges happens in practice (the v2 regression test comment references "a stall seen on mainnet" for the *sibling* pre-commit case). The proposal-time race window (locally accepted but not yet globally accepted) is realistic under normal network delay/latency, and v1 remains a supported/active code path per `check_block_against_state`'s branch on `state_version.uses_global_state()`.

### Recommendation
Change `stacks-signer/src/chainstate/v1.rs`'s `validate_tenure_change_payload` to use `get_last_signed_block` (matching v2 and matching what the pre-commit signing guard already treats as "signed") instead of `get_last_globally_accepted_block`, so a locally-accepted (already-signed) block in the same tenure is always treated as a duplicate/conflict regardless of active signer protocol version.

### Proof of Concept
1. Signer S runs protocol v1 (`state_version.uses_global_state() == false`).
2. Miner proposes tenure-start block A for tenure T. S validates it, pre-commits, and — once 70% pre-commit weight is reached — signs A via `mark_locally_accepted` (S now holds a signature on A), but A has not yet reached the 70% signature threshold needed for global acceptance (e.g., other signers are slow/offline).
3. Miner (or an equivocating variant of the same slot) proposes a second, different tenure-start block B for the same tenure T (e.g., different transaction set).
4. S's v1 `check_proposal` → `validate_tenure_change_payload` calls `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)` — this returns `None` because A is only locally accepted, not globally accepted: [1](#0-0) 
5. No `DuplicateBlockFound` rejection is raised; B passes the proposal-time check and is submitted for validation and pre-commit.
6. At pre-commit/signing time, the node's `get_tenure_tip` for tenure T has not yet observed A (since A never reached global consensus), so the "own tenure confirmed at ≥ this height" check resolves to "never confirmed," permitting S to sign B as well.
7. S has now signed two conflicting tenure-start blocks (A and B) at the same tenure/height — a concrete equivocation.

- `validate_tenure_change_payload` rejects with `DuplicateBlockFound` when we
