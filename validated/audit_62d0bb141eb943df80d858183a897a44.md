### Title
Stale instant-withdraw housekeeping inflates default recovery basis and creates a phantom reserve, letting an attacker double-dip default recovery - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The Xen CVE is a race in cleanup of housekeeping structures: IDs are leaked and bypassed because the cleanup path doesn't remove all state before reuse. The direct analog is `claimInstantWithdrawRequest`: it clears only the aggregate `instantWithdrawsRequests[_user]` but never cleans up the per-epoch housekeeping entries `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If a funded instant receipt is claimed in the same epoch that later ends in borrower default, the already-paid amount is still counted in `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, corrupting `defaultRecoveryPrice` and leaving the recovery reserve under-collateralized.

### Finding Description
`requestInstantWithdraw` records three pieces of state per epoch: `instantWithdrawsRequests[_user]` (aggregate), `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` (`contracts/strategies/idle/IdleCreditVault.sol:366-374`).

When the claim is funded and paid, `claimInstantWithdrawRequest` zeroes only the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

(`IdleCreditVault.sol:387-392`) — `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are never decremented on this path; they are only cleared inside `_claimDefaultedInstantWithdrawRequest` (`IdleCreditVault.sol:842-856`).

If the borrower then defaults in that same epoch while `pendingInstantWithdraws != 0` (e.g., another request was only partially funded by the CDO via `collectInstantWithdrawFunds`, which decrements the global pending counter at `IdleCreditVault.sol:398-403`), `finalizeDefaultRecovery` computes:

- `defaultPendingClaimBasis()` → `basis += instantWithdrawClaimsByEpoch[epochNumber]` (`IdleCreditVault.sol:644-649`), which still includes the attacker's already-claimed amount `X`.
- `_defaultPrefundedInstantReserve()` → `instantBasis - pendingInstant` (`IdleCreditVault.sol:716-723`), which treats the already-paid-out `X` as underlying still held by the strategy and adds it to `reserveAmount` (`IdleCreditVault.sol:685-686`).

The stale entry therefore counts `X` twice: once as paid out to the attacker at par, once as phantom prefunded reserve and once as defaulted claim basis. `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` (`IdleCreditVault.sol:688`) is computed against a reserve that overstates real holdings by `X`. No guard catches this: `_claimDefaultedInstantWithdrawRequest` is unreachable for the attacker (their aggregate is 0, so `instantWithdrawsRequests[_user] -= claimBasis` would underflow), but every honest defaulted claimant claims against the inflated `defaultRecoveryPrice` and the phantom `defaultRecoveryReserve` (`IdleCreditVault.sol:912-917` decrements a counter whose real token backing is short by `X`).

### Impact Explanation
Direct insolvency/theft of unclaimed recovery funds. The recovery reserve is under-collateralized by the full claimed amount `X`. Early claimants (including any attacker-controlled second account holding an unfunded instant or normal defaulted receipt) withdraw `claimBasis * inflatedPrice`, and the last claimant(s) — defaulted normal withdrawers or active AA/BB holders via `DefaultDistributor` — find the reserve depleted and their claims revert or pay less than the accounted recovery price. Loss equals `X` (the attacker's instant request size), bounded only by the liquidity in the instant queue at default time. Quantified: with `X` claimed at par pre-default, the reserve is short `X`, so defaulted claimants collectively lose `min(X, totalDefaultBasis * price)` of recovery value.

### Likelihood Explanation
Requires a borrower default in the same epoch in which a funded instant withdrawal was claimed while some other instant request remains unfunded — a plausible sequence: CDO collects partial instant funds (`collectInstantWithdrawFunds` with `_amount < pendingInstantWithdraws`), the funded user claims, then `stopEpoch` fails and `finalizeDefaultRecovery` runs before the epoch rolls over. The attacker is an ordinary KYC'd lender; no privileged action needed. The inflated-price payout accrues to all claimants pro rata, so an attacker controlling multiple receipts captures a share of the phantom `X` while externalizing the rest of the loss onto honest claimants.

### Recommendation
Mirror the cleanup done in `_claimDefaultedInstantWithdrawRequest` on the funded claim path: in `claimInstantWithdrawRequest`, zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount) for receipts created in the current epoch, or track funded-vs-pending per epoch so `_defaultPrefundedInstantReserve` cannot count already-claimed receipts. At minimum, `instantWithdrawClaimsByEpoch` must reflect only still-outstanding claims when `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` read it.

```solidity
pragma solidity 0.8.x;

import "forge-std/Test.sol";

contract StaleInstantClaimPoC is Test {
    // Deploy: IdleCDOEpochVariant + IdleCreditVault strategy, AA tranche, instant withdraws enabled.

    function test_staleInstantInflatesRecovery() public {
        // --- Epoch N running ---
        // 1. KYC'd attacker deposits, requests instant withdraw of X.
        //    instantWithdrawsRequestsByEpoch[attacker][N] = X
        //    instantWithdrawClaimsByEpoch[N] = X
        //    pendingInstantWithdraws = X
        // 2. Victim (or attacker acct2) requests instant withdraw Y.
        //    instantWithdrawClaimsByEpoch[N] = X + Y, pendingInstantWithdraws = X + Y

        // 3. Borrower/CDO funds only X via collectInstantWithdrawFunds(X)
        //    => pendingInstantWithdraws = Y, strategy holds X.

        // 4. Attacker calls claimInstantWithdrawRequest -> receives X at par.
        //    instantWithdrawsRequests[attacker] = 0
        //    BUG: instantWithdrawsRequestsByEpoch[attacker][N] still = X
        //    BUG: instantWithdrawClaimsByEpoch[N] still = X + Y

        // 5. Borrower defaults in same epoch; manager calls finalizeDefault(recovered).
        //    defaultPendingClaimBasis()  = pendingWithdraws + (X + Y)   // X double-counted
        //    _defaultPrefundedInstantReserve() = (X + Y) - Y = X        // phantom X
        //    defaultRecoveryReserve = recovered + X  // but balance only grew by X already spent
        //    defaultRecoveryPrice is computed as if X of underlying were still held.

        // 6. Attacker acct2 (or early claimant) claims defaulted receipt:
        //    gets Y * recoveryPrice, where recoveryPrice was inflated by phantom X.
        //    Later claimants' _transferDefaultRecovery reverts / pays short:
        //    real reserve backing = recovered, accounted reserve = recovered + X.
        //    Insolvency = X.
    }
}
```
