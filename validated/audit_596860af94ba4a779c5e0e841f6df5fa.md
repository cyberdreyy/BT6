### Title
`RequiresEditRole`/`RequiresRunRole` use blacklist-style role checks instead of deny-by-default whitelist, allowing any unrecognized `UserRole` value to bypass restriction on `/v2/vault/dkg_results/export` - ([File: core/web/auth/auth.go])

### Summary
`auth.RequiresEditRole` and `auth.RequiresRunRole` reject access only when `user.Role` exactly equals `clsessions.UserRoleView` (and, for edit, also `UserRoleRun`), rather than checking that the role is one of the explicitly allowed values. Any `sessions.UserRole` string that is not exactly `"view"`/`"run"` — including an empty string or any other unexpected value — falls through both checks and is treated as authorized to reach `VaultController.ExportDKGResult` and `VaultController.VerifyDKGResult`.

### Finding Description
The vault routes are wired in `v2Routes` as: [1](#0-0) 

Both are guarded by `auth.RequiresEditRole`: [2](#0-1) 

Note the check is a **negative/exclusion list**: `if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun { deny }`, then falls through to `handler(c)` for everything else. Contrast this with `RequiresAdminRole`, which correctly implements an **inclusion/whitelist** check: `if user.Role != clsessions.UserRoleAdmin { deny }`. [3](#0-2) 

Because `sessions.UserRole` is a plain string type with no compile-time exhaustiveness guarantee, `RequiresEditRole`/`RequiresRunRole` will authorize *any* value that is not literally `"view"` (or additionally `"run"` for edit) — this includes an empty string `UserRole("")`, a role from a future addition, or a value corrupted/mismapped by an upstream provider bug. The GraphQL equivalent (`authenticateUserCanEdit` in `core/web/resolver/auth.go`) at least uses a `switch` with only the negative cases enumerated and a `default:` no-op, which is the same anti-pattern. [4](#0-3) 

Regarding the specific LDAP scenario cited in the question: `GroupSearchResultsToUserRole` returns `sessions.UserRoleView, ErrUserNoLDAPGroups` (not an empty string) on the no-match case, and its caller `FindUser` treats the error path by returning `sessions.User{}, err` (zero-value `Role` = `""`), which propagates as a hard error up through `CreateSession`, causing that specific login attempt to fail (or fall back to local admin login) rather than be persisted as a valid session with role `""`. [5](#0-4) [6](#0-5) [7](#0-6) 

So the exact "empty role from `ErrUserNoLDAPGroups`" login path does not directly yield an authorized session in the current code — that specific chain is not directly exploitable as described. However, `AuthorizedUserWithSession` and `FindUserByAPIToken` read `user_role` directly out of the `ldap_sessions` / `ldap_user_api_tokens` tables as a raw string with no validation against the known enum, and construct a `sessions.User{Role: foundSession.UserRole}` unconditionally: [8](#0-7) [9](#0-8) 

If any stored `user_role` value in those tables is ever anything other than exactly `"admin"`, `"edit"`, `"run"`, or `"view"` (e.g. due to a future role addition, a data migration bug, manual DB edit, or a provider integration bug elsewhere that isn't caught before persistence), `RequiresEditRole` and `RequiresRunRole` will fail open and grant access to edit/run-gated routes including the vault DKG export/verify endpoints, while `RequiresAdminRole`'s whitelist would correctly still deny access to admin-only routes for the same degenerate value.

### Impact Explanation
If a user session or API token ever carries a `UserRole` value that is not one of the four canonical constants, that user gains Edit-level privileges system-wide (not just for vault routes) purely due to `RequiresEditRole`'s exclusion-based logic, including the ability to call `VaultController.ExportDKGResult`, which returns the raw hex-encoded DKG result package (`ReportWithResultPackage`) — key material related to the Vault/DKG capability. This matches an authorization-bypass / secret-disclosure impact class. The `RequiresRunRole`-gated routes (e.g. `/v2/replay_from_block/:number`, `/v2/find_lca`, job run triggering) would be similarly affected for a degenerate role value.

### Likelihood Explanation
Exploitability is contingent on a precondition external to this code: a `UserRole` value not equal to the four known constants must actually be persisted/returned for an authenticated principal. The specific "empty role from `ErrUserNoLDAPGroups`" scenario in the question is not directly reachable in the current LDAP login flow, since that error path aborts login rather than completing session creation. The vulnerability is nonetheless real as a defense-in-depth defect: `RequiresEditRole`/`RequiresRunRole` are not deny-by-default, unlike `RequiresAdminRole`, so this class of bug becomes live the moment any other code path (new role type, integration bug, DB corruption) produces a non-canonical role. Likelihood of the exact attack chain described (unprivileged attacker forging an empty-role login) is low today given the current LDAP code aborts on that condition, but the underlying authorization-exactness defect is present and should be treated as a real weakness.

### Recommendation
Change `RequiresEditRole` and `RequiresRunRole` (and the GraphQL `authenticateUserCanEdit`/`authenticateUserCanRun` equivalents) to use inclusion/whitelist checks matching `RequiresAdminRole`'s pattern, e.g.:
```go
switch user.Role {
case clsessions.UserRoleAdmin, clsessions.UserRoleEdit:
    // allowed
default:
    deny
}
```
Additionally, validate/normalize `UserRole` values at the point of session/token persistence (LDAP sync, OIDC claims mapping, local auth) so that any unrecognized role string is rejected before being stored, rather than relying solely on downstream middleware to filter it out.

### Proof of Concept

2. Call `auth.RequiresEditRole(handlerCalled)(c)` and assert the wrapped handler is NOT invoked and the response is `401`/`403` (currently it IS invoked — test fails, demonstrating the bug).
3. Repeat for `auth.RequiresRunRole`.
4. Repeat for `auth.RequiresAdminRole` with the same degenerate role value and assert it correctly denies (control case showing whitelist works).
5. Handler-level integration test: register a fake session/token in the LDAP or local auth store with `user_role` set to a non-canonical string, authenticate as that user, `POST /v2/vault/dkg_results/export`, and assert the response is `401 Unauthorized`/`403 Forbidden` rather than `200 OK` with `ExportDKGResultResource` data.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	if !foundSession.Valid {
		// Sessions expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_sessions WHERE id = $1", sessionID); execErr != nil {
			l.lggr.Errorf("error purging stale ldap session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}
	return sessions.User{
		Email: foundSession.UserEmail,
		Role:  foundSession.UserRole,
	}, nil
}

func GroupSearchResultsToUserRole(ldapGroups []*ldap.Entry, adminCN string, editCN string, runCN string, readCN string) (sessions.UserRole, error) {
	// If defined Admin group name is present in groups search result, return UserRoleAdmin
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == adminCN {
			return sessions.UserRoleAdmin, nil
		}
	}
	// Check edit role
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == editCN {
			return sessions.UserRoleEdit, nil
		}
	}
	// Check run role
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == runCN {
			return sessions.UserRoleRun, nil
		}
	}
	// Check view role
	for _, group := range ldapGroups {
		if group.GetAttributeValue("cn") == readCN {
			return sessions.UserRoleView, nil
		}
	}
	// No role group found, error
	return sessions.UserRoleView, ErrUserNoLDAPGroups
}
