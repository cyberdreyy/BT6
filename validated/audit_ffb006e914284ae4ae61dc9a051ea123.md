### Title
Any External Initiator credential can trigger a run of any job (no per-EI job binding check) - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` decides whether to call `RunJobV2` solely by checking `auth.GetAuthenticatedUser(c)`, but `AuthenticateExternalInitiator` also populates `SessionUserKey` with a synthetic `User{Role: UserRoleRun}` [1](#0-0) . As a result, any valid EI access-key/secret satisfies both `RequiresRunRole` and the `isUser` check in `Create`, letting it call `RunJobV2` for any int32 job ID with no verification that the job is bound to that EI.

### Finding Description
The route is wired as:
```
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
```
with `userOrEI` authenticated via `AuthenticateExternalInitiator`, `AuthenticateByToken`, or `AuthenticateBySession` [2](#0-1) .

`AuthenticateExternalInitiator` sets `SessionExternalInitiatorKey` to the resolved EI, but it ALSO sets `SessionUserKey` to a synthetic user with `Role: UserRoleRun`: [1](#0-0) 

`RequiresRunRole` only checks that a `SessionUserKey` user exists and its role is not `View`, which the synthetic EI user satisfies [3](#0-2) .

Inside `PipelineRunsController.Create`, the only gate before calling `RunJobV2` for an arbitrary int32 job ID is:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    ...
    jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
``` [4](#0-3) 

The comment claims "EIs not allowed," but because `AuthenticateExternalInitiator` writes the same `SessionUserKey`, `isUser` evaluates to `true` for EI-authenticated requests exactly the same as for a real logged-in user or API-token user. `RunJobV2` is called with only the numeric job ID — there is no lookup of `auth.GetAuthenticatedExternalInitiator(c)` or any check that the target job's spec references that specific EI. Historically, only `Webhook`-type jobs carried an `externalInitiators` binding, but webhook job creation and execution have since been fully removed (`job.ErrJobTypeRemoved`, enforced in `orm.CreateJob` and `pipeline_runs_controller.go`'s explicit UUID rejection) [5](#0-4) [6](#0-5) . Non-webhook job types (OCR, VRF, Cron, etc.) never had any EI-binding concept at all, so nothing in the code path checks whether the caller (EI or user) is authorized for the specific job being triggered by int32 ID.

### Impact Explanation
Any holder of a valid EI access-key/secret pair (a low-privilege credential intended only to trigger a specific bound webhook job) can call `POST /v2/jobs/:ID/runs` for **any** job ID on the node (OCR jobs, VRF jobs, cron jobs, etc.), causing unauthorized pipeline runs. Depending on job configuration this can cause resource exhaustion (repeated forced runs), unintended bridge/API calls, or unauthorized on-chain transmissions/state changes tied to that job's pipeline. This matches "unauthorized job run" / authorization bypass under Chainlink's bounty impact classes.

### Likelihood Explanation
Requires only a valid EI credential (access key + secret) issued for any purpose — no special scope, no admin access, no knowledge of which jobs the EI was originally intended for. The attack is a single unauthenticated-relative-to-target-job HTTP POST and is fully repeatable against every int32 job ID in the node.

### Recommendation
In `PipelineRunsController.Create`, distinguish EI-authenticated requests from real user requests by checking `auth.GetAuthenticatedExternalInitiator(c)` explicitly (not just the synthetic `SessionUserKey`), and either reject EI-triggered runs outright (consistent with webhook job removal) or verify the requested job is actually associated with that specific EI before calling `RunJobV2`. Alternatively, stop `AuthenticateExternalInitiator` from writing `SessionUserKey`, and have `RequiresRunRole` accommodate EI identity separately with its own authorization check against the target job.

### Proof of Concept
1. Create two independent EIs (`EI-A`, `EI-B`) via `POST /v2/external_initiators` (as an admin/edit user) and a non-webhook job (e.g., a Cron or OCR job) `Job-X` with int32 ID unrelated to either EI.
2. Authenticate as `EI-A` using its access key/secret via `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` headers.
3. Send `POST /v2/jobs/<Job-X-ID>/runs` with the EI-A credentials.
4. Assert current (vulnerable) behavior: `http.StatusOK`/`201` with a `pipelineRun` resource returned, and a new row in `pipeline_runs` for `Job-X`.
5. Expected secure behavior: `403 Forbidden` (or `404`) since `Job-X` was never bound to `EI-A`.
6. Handler-level Go test: extend `TestPipelineRunsController_*` in `core/web/pipeline_runs_controller_test.go` to build an HTTP client using `cltest.CreateExternalInitiatorViaWeb`, obtain `AccessKey`/`Secret`, and issue the POST with those headers against a job created independently of that EI, asserting the run is rejected rather than executed.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
