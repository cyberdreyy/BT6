I found the specific gap: the `MAX_CALL_PHASES_PER_TX` / `MAX_ACCOUNT_CHANGES_PER_TX` bounds that protect the on-chain EIP-8130 transaction path (RLP decode and txpool admission) are not applied to the `eth_call`/`eth_estimateGas` JSON-RPC simulation path.

### Title
Unbounded `calls`/`account_changes` allocation in EIP-8130 `eth_call`/`eth_estimateGas` simulation requests - (File: crates/common/rpc-types/src/transaction/request.rs)

### Summary
`Eip8130RequestFields` (the AA fields layered onto `eth_call`/`eth_estimateGas` requests) deserializes `account_changes: Option<Vec<AccountChange>>` and `calls: Option<Vec<Vec<Call>>>` via plain `serde` with no length bound, unlike the consensus RLP decoder and the txpool admission path, which both explicitly cap these fields.

### Finding Description
The on-chain EIP-8130 transaction type enforces `Eip8130Constants::MAX_CALL_PHASES_PER_TX` (1,024) during RLP decode [1](#0-0)  and again during txpool structural validation [2](#0-1) , and `account_changes` is separately capped by `MAX_ACCOUNT_CHANGES_PER_TX` at admission [3](#0-2) . These are documented explicitly as anti-DoS bounds: "Bounding the count while decoding prevents a sequence of single-byte empty RLP lists from amplifying into unbounded allocations before transaction-pool admission limits run." [4](#0-3) 

However, the JSON-RPC simulation request type used by `eth_call`/`eth_estimateGas` deserializes the same fields with no such bound: `account_changes: Option<Vec<AccountChange>>` and `calls: Option<Vec<Vec<Call>>>` are plain `serde`-derived fields with only `#[serde(default)]`, no visitor cap and no post-deserialize length check. [5](#0-4)  This differs from the pattern the codebase otherwise uses for exactly this bug class: the `validity` predicate list on `base_sendRawTransactionValidity` is deserialized through a bounded visitor (`deserialize_bounded_predicates`) that aborts mid-stream once the count exceeds `DEFAULT_MAX_VALIDITY_PREDICATES`, precisely to stop an attacker from forcing allocation of "tens of thousands of predicates that are ultimately rejected." [6](#0-5) 

`to_eip8130_simulation_tx` copies the deserialized (unbounded) vectors straight into the `TxEip8130` used for simulation without re-checking phase/account-change counts: [7](#0-6)  and the resulting `simulate` entrypoint is explicitly documented as "reachable only from the read-only RPC simulation path" — i.e. `eth_call`/`eth_estimateGas`, requiring no signature verification: [8](#0-7) 

### Impact Explanation
Any anonymous RPC client can submit `eth_call`/`eth_estimateGas` with a JSON body containing a `calls` array with far more than 1,024 phases (each an empty `Vec<Call>`, cheap on the wire but each phase materializes a heap-allocated `Vec`), or an oversized `account_changes` array, bypassing both bounds that exist for the on-chain wire format. This is directly analogous to the `qs` CVE-2014-7191 pattern: a small request body deserializes into a disproportionately large in-memory structure, exhausting node memory/CPU and causing a denial of service on the public `eth_*` RPC surface. Because it requires no gas payment, no signature, and no chain state, it is cheaper to repeat than a real transaction-based attack, and the request path runs before any resource metering equivalent to txpool admission.

### Likelihood Explanation
High. The `eth_call`/`eth_estimateGas` HTTP JSON-RPC endpoints are the canonical unauthenticated public RPC surface explicitly reachable per scope ("public `eth_*`... query paths"). No special conditions are needed beyond crafting a JSON body with a large nested array — no signing, no funds, no prior state.

### Recommendation
Apply the same defense-in-depth pattern already used for `SendRawTransactionValidityOptions`/`deserialize_bounded_predicates`: deserialize `Eip8130RequestFields::calls` and `Eip8130RequestFields::account_changes` through a bounded `serde` visitor that aborts as soon as the count exceeds `Eip8130Constants::MAX_CALL_PHASES_PER_TX` / `MAX_ACCOUNT_CHANGES_PER_TX`, mirroring `deserialize_calls`/`deserialize_bounded_predicates`, rather than relying on the RLP-decode/txpool-admission bounds that this JSON path never traverses.

### Proof of Concept
```
POST /  (eth RPC)
{
  "jsonrpc":"2.0","id":1,"method":"eth_estimateGas",
  "params":[{
     "from":"0x0000000000000000000000000000000000000001",
     "calls": [ [] , [] , ... /* e.g. 5,000,000 empty phases */ ]
  }, "latest"]
}
```
Each `[]` element deserializes to a heap-allocated empty `Vec<Call>`; a request with several million such elements is small on the wire (a few bytes per `[]`) but forces the node to allocate and hold millions of `Vec` objects during deserialization of `Eip8130RequestFields::calls`, before `Eip8130GasEstimator::estimate`/`to_eip8130_simulation_tx` ever runs a bound check — unlike the RLP/txpool path, which rejects this shape at 1,025 phases.

**Caveat / uncertainty:** I was not able to fully trace whether `jsonrpsee`'s configured `max_request_body_size` (a server-level HTTP body cap) is set low enough in default node configuration to make the wire-size-vs-allocation amplification impractical in practice — that HTTP body cap is a mitigating factor that could reduce or eliminate real-world impact depending on deployment configuration, and I could not locate the default body-size limit for the main `eth_*` RPC server (only the separate prover-service CLI's `RPC_MAX_REQUEST_BODY_BYTES` was found). This should be verified before treating the finding as fully exploitable in a default deployment.

    fn decode_calls(buf: &mut &[u8]) -> alloy_rlp::Result<Vec<Vec<Call>>> {
        let header = Header::decode(buf)?;
        if !header.list {
            return Err(alloy_rlp::Error::UnexpectedString);
        }
        if buf.len() < header.payload_length {
            return Err(alloy_rlp::Error::InputTooShort);
        }

        let (mut payload, rest) = buf.split_at(header.payload_length);
        let mut phases = Vec::new();
        while !payload.is_empty() {
            if phases.len() >= Eip8130Constants::MAX_CALL_PHASES_PER_TX {
                return Err(alloy_rlp::Error::Custom("too many EIP-8130 call phases"));
            }
            phases.push(Vec::<Call>::decode(&mut payload)?);
        }
        *buf = rest;
