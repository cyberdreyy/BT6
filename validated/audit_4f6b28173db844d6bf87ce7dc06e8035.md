## Analog found

### Title
Malicious tenure-holding miner can indefinitely suppress its own inactivity timeout by spamming invalid reorg proposals, wedging signers into never failing over - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
The LayerZero bug lets any caller drain a shared, limited resource (`address(this).balance`) that legitimate cross-chain operations depend on, by triggering cheap unnecessary operations, permanently DOSing the protocol once the resource is exhausted. The Stacks-signer analog is structurally the same shape: the "shared limited resource" is the *miner-inactivity clock* (`last_activity_time`), a single, one-slot actor (the currently active tenure's miner) can "top it up" for free with cheap, always-rejected proposals, and once that clock is kept alive forever, the resource legitimate operation depends on — the signers' ability to fail over to a functioning miner — is permanently unavailable.

### Finding Description
`SortitionData::check_latest_block_in_tenure` treats *any* reorg-attempt proposal (one whose `chain_length` does not exceed the tenure's last signed/pre-committed block) as valid "miner activity" and refreshes `last_activity_time`, as long as the freshness window (`reorg_attempts_activity_timeout`) hasn't elapsed — which includes the case where there is no `signed_group` timestamp at all (`is_none_or` short-circuits true): [1](#0-0) 

This check is invoked on every ordinary (non-tenure-change) block proposal for the active miner's own tenure via `confirms_latest_block_in_same_tenure`: [2](#0-1) 

and it is reached directly from `GlobalStateView::check_proposal` (v2) before any stacks-node validation is even attempted: [3](#0-2) 

The only thing that ever demotes an unresponsive miner is `SortitionState::is_timed_out`, which compares `now - last_activity_time` (falling back to burn-block receive time) against `block_proposal_timeout`: [4](#0-3) 

and is consumed by `check_miner_inactivity`, the sole mechanism that reverts to the prior tenure's miner when the current one goes idle: [5](#0-4) 

Because the "activity" update happens on rejection, not acceptance, the miner that won the current sortition slot — a single actor, no majority or other signer's key needed — can keep broadcasting distinct, never-valid block proposals (chain_length ≤ known tip, e.g. re-proposing the same height with a different nonce/timestamp so each gets a fresh `signer_signature_hash` and bypasses `should_reevaluate_block` dedup) forever. Each one is rejected with `InvalidParentBlock`, but each one also calls `update_last_activity_time`, resetting the very clock that would otherwise let signers fail over to a working miner. The reset only stops working once `reorg_attempts_activity_timeout` (default 200s, `reorg_attempts_activity_timeout_ms`) has elapsed since the last *globally signed* block — but the miner only needs to keep proposals coming faster than that interval to keep the suppression alive indefinitely, exactly mirroring how the LayerZero attacker only needs to keep draining ETH faster than it's replenished.

### Impact Explanation
This is a High-severity liveness wedge: "a signer wedged into never signing valid blocks." As long as the malicious miner holds its sortition slot, it can prevent the entire signer set from ever timing it out and falling back to the prior miner, while itself never producing a chain-advancing block. The chain stalls for that miner's tenure duration with no recovery path available to the signers, purely from repeated cheap, locally-rejected proposals gossiped over StackerDB — the same "cheap unnecessary operation exhausts a resource all legitimate operations depend on" pattern as the LayerZero finding.

### Likelihood Explanation
Any miner that wins a sortition slot can trigger this unilaterally; it requires no cooperation from other miners or a majority of signers, and no privileged access (no `auth_token`, no signer key). It only requires being able to construct syntactically distinct invalid Nakamoto blocks at or below the known tip and broadcast them as `BlockProposal` messages faster than `reorg_attempts_activity_timeout`/`block_proposal_timeout` — trivially satisfiable by a miner that already controls block construction for its own tenure.

### Recommendation
Do not treat an invalid/non-advancing proposal as unconditional "activity" for the purposes of the inactivity clock. At minimum, cap the number of times, or the total duration, that `update_last_activity_time` can be refreshed by rejected/reorg-attempt proposals within a tenure, or require some proof of genuine progress (e.g., a strictly-improving, previously-unseen candidate, or a rate limit tied to burn-block height rather than wall-clock) before the timeout window is extended again.

### Proof of Concept
1. Miner M wins the sortition for tenure T and produces the first valid tenure-change block, which signers globally accept (this is required so `check_miner_inactivity` treats M as `ActiveMiner`).
2. M then repeatedly proposes blocks at the same (or lower) `chain_length` as the accepted tip, each with a distinct nonce/timestamp so `signer_signature_hash` differs and `should_reevaluate_block` does not short-circuit.
3. Each proposal reaches `handle_block_proposal` → `check_proposal` → `confirms_latest_block_in_same_tenure` → `check_latest_block_in_tenure`, is rejected (`InvalidParentBlock`), but calls `signer_db.update_last_activity_time(...)` on the way out because `info.signed_group` freshness holds.
4. As long as M repeats step 2 more often than `reorg_attempts_activity_timeout` (default 200s), `SortitionState::is_timed_out` in `check_miner_inactivity` never returns `true`, so signers never fail over to the prior miner, and M's tenure never produces a new valid block — the chain stalls indefinitely for as long as M chooses to keep this up.

    /// Check if the sortition identified by the ConsensusHash is timed out based on
    /// the blocks within the signer db and the block proposal timeout
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        signer_db: &SignerDb,
        eval: &GlobalStateEvaluator,
        local_address: &StacksAddress,
        timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = signer_db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) =
            signer_db.get_burn_block_received_time_from_signers(eval, sortition, local_address)?
        else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = signer_db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };
        if elapsed > timeout {
            info!("Sortition has timed out";
                "sorition" => %sortition,
                "timeout" => %timeout.as_secs(),
                "elapsed" => %elapsed.as_secs()
            )
        }
        Ok(elapsed > timeout)
    }
