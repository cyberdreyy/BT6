### Title
Confirmations from a member deleted via `DeleteMember` remain counted toward `num_confirmations` on requests created by other members - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges requests and confirmation state that the *removed* member itself originated. It does not scan the `confirmations` map for entries where the removed member had already confirmed a request created by a *different* member. Those stale confirmations remain in the `HashSet<String>` stored under `confirmations`, and `confirm()` counts confirmations purely by set length without re-validating that every entry is still a current member of `self.members`. This is the direct NEAR-analog of the Backd finding: a stale reference (there, a delisted pool still tracked by the reward handler; here, a deleted member's confirmation still tracked by an active request) keeps contributing to downstream accounting after the entity backing it was removed.

### Finding Description
`delete_member` (`multisig2/src/lib.rs:356-379`) removes the member from `self.members` and cleans up only requests it authored: [1](#0-0) 

It does not iterate `self.confirmations` to strip the deleted member's `to_string()` entry from confirmation sets belonging to requests created by *other* members. Meanwhile, `confirm()` (`multisig2/src/lib.rs:294-315`) determines whether a request executes solely from `confirmations.len() as u32 + 1 >= self.num_confirmations` — it never checks that the accounts/keys inside `confirmations` are still members: [2](#0-1) 

Binding that should hold: `confirmations_counted(request) == confirmations_by_live_members(request)`. After a `DeleteMember` execution, this equality breaks whenever the deleted member had confirmed an outstanding request authored by someone else — `confirmations_counted` still includes the ghost entry while `confirmations_by_live_members` does not.

### Impact Explanation
This lets a request execute (moving funds via `Transfer`, deploying code via `DeployContract`, adding a full-access key via `AddKey`, etc.) with fewer *live* confirmations than `num_confirmations` requires. Concretely:
1. Member A creates request R (e.g., a `Transfer`).
2. Member B confirms R (1 confirmation stored, contract requires say 2).
3. The multisig then removes member B via a separate `DeleteMember` request/execution (legitimate, e.g., because B's key was compromised or B left).
4. R's confirmation set still contains B's entry (untouched by `delete_member`, since R was authored by A, not B).
5. Member C (the only other member, or a newly added member) confirms R — `confirmations.len() + 1 == 2 >= num_confirmations`, so R executes, even though B is no longer a member and only one *currently valid* member (C) actually confirmed it alongside a ghost entry from the removed member.

This crosses the "confirmations counted versus live members" custody boundary called out in the rules and matches "a multisig request executed below threshold" in the Critical impact category — funds can move (or a key/contract can be added) with effectively K-1 live signers instead of the required K.

### Likelihood Explanation
This requires only routine multisig operation, not any privileged bypass: creating requests, confirming them, and later removing a member are all standard, documented multisig flows. The precondition (an outstanding, partially-confirmed request existing at the time a confirmer is removed) is a plausible and even common operational sequence for a live multisig (e.g., rotating out a compromised or departing signer while other requests are pending). No malicious contract deployment, foundation privilege, or social engineering is needed beyond the normal K-of-N confirmation process already exposed by the contract.

### Recommendation
When executing `DeleteMember`, iterate all entries in `self.confirmations` (not just requests authored by the removed member) and remove the deleted member's string key from every confirmation set, consistent with how `remove_request` cleans up state for requests it fully owns. Alternatively, change `confirm()` to recompute the effective confirmation count by filtering the stored confirmation set against `self.members.contains(...)` before comparing against `num_confirmations`, so removed members can never contribute to reaching the threshold.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 2`.
2. As A, call `add_request` with a `Transfer` action to some receiver (request `R`, id `0`).
3. As B, call `confirm(0)` — confirmations for `R` now contain `{B}` (1 of 2 required, request stays open per `multisig2/src/lib.rs:304-314`).
4. As A (or via a separate already-confirmed request), execute a `DeleteMember { member: B }` request — this calls `delete_member` (`multisig2/src/lib.rs:356-379`), which removes B from `self.members` and only clears requests B itself authored; `R`'s confirmations (still `{B}`) are untouched because `R.member == A`, not `B`.
5. As C, call `confirm(0)` — `confirmations.len() (=1, still containing stale "B") + 1 = 2 >= num_confirmations (2)`, so `execute_request` runs the `Transfer`, even though only one live member (C) plus the request author (A) — not two live confirming members — actually authorized it, and B, now removed, effectively still "voted."     pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
