### Title
Stale confirmations from deleted multisig members are still counted toward the confirmation threshold, allowing requests to execute below the live-member threshold - ([File: multisig2/src/lib.rs], [File: multisig/src/lib.rs])

### Summary
`delete_member` (and the analogous `DeleteKey` handling in the legacy `multisig` contract) only purges pending requests that were *created* by the removed member, but never scrubs that member's *confirmations* left on other still-pending requests. `confirm()` later counts those stale confirmations toward `num_confirmations`, so a request can execute with fewer live, authorized approvers than the configured threshold.

### Finding Description
The binding that must hold is: `confirmations recorded for a request == confirmations from currently-live members`. In `multisig2/src/lib.rs`, `delete_member` removes only requests where `r.member == member`: [1](#0-0) 

It never inspects `self.confirmations` for entries where the deleted member's identity appears inside *other* requests' confirmation sets. `confirm()` blindly trusts the stored `confirmations` set size against `self.num_confirmations`: [2](#0-1) 

`get_confirmations`/`current_member` show confirmations are tracked by member identity (account id or public key string), independent of whether that member is still in `self.members`: [3](#0-2) 

The same pattern exists in the legacy single-key `multisig` contract: `DeleteKey` only cleans requests originated by that key (`r.signer_pk == pk`) and removes `num_requests_pk`, but does not scrub that key's confirmation entries from other pending requests: [4](#0-3) [5](#0-4) 

This is structurally the same bug class as the external report: a piece of accounting state (`lastCollateralError_Offset` there, `confirmations` here) is left un-reset when the entity it was scoped to (a collateral slot there, a multisig member/key here) is removed/overwritten, causing the equality between "recorded" and "actual/live" values to diverge — here `recorded confirmations != live-member confirmations`, which is one of the explicitly in-scope bindings ("confirmations counted versus live members").

### Impact Explanation
This breaks the multisig's core authorization guarantee: a request can be executed with fewer distinct, currently-authorized approvers than `num_confirmations` requires. Since `execute_request` can perform `Transfer`, `FunctionCall`, `AddKey`, `DeployContract`, etc., a request executed below the true live threshold is a direct path to unauthorized fund movement or unauthorized privileged action — matching the "Critical: a multisig request executed below threshold" impact category.

### Likelihood Explanation
This requires no attacker privilege beyond being a legitimate, still-active multisig member who exploits ordinary member turnover (a common, expected multisig operation): confirm a pending request early, have that confirming member later removed via a normal `DeleteMember`/`DeleteKey` request, then have a remaining member supply the final confirmation. No malicious deployment, redeploy, or foundation/owner privilege is needed beyond standard multisig member actions already granted by the system.

### Recommendation
When removing a member/key (`delete_member` in `multisig2/src/lib.rs`, `DeleteKey` handling in `multisig/src/lib.rs`), iterate over all pending requests' confirmation sets and remove any confirmation entry belonging to the removed member/key, not just the requests they originated. Alternatively, re-validate at `confirm()` time (or at execution time) that every entry in the stored confirmations set still corresponds to a current member before comparing the count against `num_confirmations`.

### Proof of Concept
Using `multisig2` with 4 members `A, B, C, D` and `num_confirmations = 3`:
1. `A` calls `add_request_and_confirm(request_X)` → `confirmations[X] = {A}`.
2. `B` calls `confirm(request_X)` → since `len({A}) + 1 = 2 < 3`, `B` is added → `confirmations[X] = {A, B}`.
3. A separate multisig request to `DeleteMember{member: B}` reaches threshold and executes → `delete_member` removes `B` from `self.members` and deletes only requests `B` had created; `confirmations[X] = {A, B}` is left untouched (see `multisig2/src/lib.rs:355-374`).
4. `C` calls `confirm(request_X)` → `len({A,B}) + 1 = 3 >= num_confirmations(3)` → `execute_request` runs with only `A` and `C` being live members (2 of 4 live members, i.e., below the required 3-of-4 threshold), because `B`'s stale confirmation was still counted. [2](#0-1) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
