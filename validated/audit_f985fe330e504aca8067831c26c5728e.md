### Title
Trusted-payer PayerBook can be seeded from a stale balance snapshot for a payer's *first* admission, allowing mempool reservations to exceed the payer's real on-chain balance - ([File: crates/execution/txpool/src/validator.rs])

### Summary
`MempoolGuard`'s balance-bounded ("trusted") payer accounting is supposed to guarantee `Σ max_cost ≤ balance` at all times [1](#0-0) . This invariant is enforced by advancing a `classification_generation` counter whenever a trusted payer's balance changes, so any in-flight validation against the old balance is rejected at admission time [2](#0-1) . However, the generation is only advanced for a balance diff when the payer is *already* known-trusted in the cache (`cache.is_trusted_cached(diff.address)`) [3](#0-2) . For the very first EIP-8130 transaction(s) from a given trusted payer, the trust classification has not yet been cached at the moment a concurrent balance-decreasing diff for that payer arrives, so the diff does not bump the generation - exactly mirroring the Knox pattern where a capacity-limiting check ("has the auction started/finalize") is only triggered conditionally on a state flag that a racing actor can still be on the "not yet set" side of.

### Finding Description
`try_admit` seeds a payer's `PayerBook` only on the *first* successful admission for that payer, using the `payer_balance` captured in the transaction's `LimitClass` during validation: [4](#0-3) 

That `payer_balance` is a validation-time snapshot read alongside the fee check in `validate_eip8130_full`: [5](#0-4) 

The mempool's only defense against admitting a reservation against a stale/too-high balance is the `classification_generation` mechanism: `try_admit`/`gate_protocol_admission`/`add_validated_sidecar_transaction` reject admission if the generation captured at validation time no longer matches the current generation [6](#0-5) . `invalidate_limit_class_cache` is the only place that advances this generation on a balance change, and it explicitly restricts that advance to payers already recorded as trusted in `limit_class_cache`: [7](#0-6) 

The trust classification itself is written into the cache lazily, inside `is_high_rate_account`, only after validation determines the payer is trusted — and only if the generation hasn't already moved: [8](#0-7) 

This creates a window, analogous to the Knox `_addOrder`/`_finalizeAuction` gap (where the capacity check is only invoked conditionally on `block.timestamp >= auction.startTime`): for a payer that has never before been observed by this node's cache as trusted, a balance-decreasing state diff that lands concurrently with (or just before) that payer's first transaction(s) being validated will not advance `classification_generation`, because `cache.is_trusted_cached()` is false at that moment. Any transaction(s) validated with the old (higher) balance can then be admitted via `try_admit`, seeding (or adding to) the `PayerBook` with a balance figure that is no longer accurate, since the generation check that is supposed to catch this staleness never fired.

### Impact Explanation
If the trusted payer's balance actually dropped below what `PayerBook` believes it has, the aggregate reservation invariant `Σ max_cost ≤ balance` used throughout `PayerBook`/`MempoolGuard` to bound admission is violated for that payer's first-seen book. This can cause the pool to admit and later attempt to include sponsored transactions the payer cannot actually cover, which the block builder/executor would then need to drop or which would fail on execution — an analogous "temporarily stuck" resource-accounting failure to the Knox report's over-sold auction capacity (where a limit-enforcing check was conditionally skipped, letting commitments exceed the backing resource). It does not directly enable theft, but it breaks a documented safety invariant of the mempool's balance-bounded trusted-payer path and can allow transient over-commitment of sponsor funds in the pool, which the design explicitly claims should be impossible ("For a trusted account ETH can only leave through gas it sponsors, so `Σ max_cost ≤ balance` is a true upper bound" [1](#0-0) ).

### Likelihood Explanation
This requires a specific race: a trusted payer's on-chain balance decreasing (e.g., via a non-EIP-8130 transaction, or a separate concurrent drain) at essentially the same moment the payer's classification is first being computed/cached by validation for a new transaction, before any admission has cached it as trusted. Because trust classification is cached per-node and long-lived once set, this window realistically only exists for a payer's first transaction(s) observed by a given node (e.g., after node restart/cache-clear, or the very first time a sponsor contract is used). This narrows likelihood, but sponsor/paymaster balances draining concurrently with their first-ever pooled transaction is a plausible operational scenario, not a purely theoretical one.

### Recommendation
Do not gate the generation bump on `is_trusted_cached`; either (a) always advance the generation on any balance change for addresses that are structurally eligible to be a trusted payer (i.e., are payers of any pending EIP-8130 transaction currently in validation/admission, tracked independent of cache population), or (b) have `try_admit`/`PayerBook::new` re-validate/re-read the canonical balance at the moment the book is first created rather than trusting a validation-time snapshot, closing the gap between "not yet cached as trusted" and "already admitted with a stale balance."

### Proof of Concept
Conceptual reproduction (cannot be executed here, but follows directly from the cited code paths):
1. Deploy/observe a payer contract whose code hash is in `trusted_proxy_code_hashes` (a "high-rate" sponsor), but ensure this validator node has never cached its trust status (fresh node, or after `clear_limit_class_cache`).
2. Concurrently: (a) submit a first EIP-8130 transaction sponsored by this payer while its balance is `B`, entering `validate_eip8130_full` and capturing `payer_balance = B` in `LimitClass` [5](#0-4) , and (b) drain the payer's balance down to `B' < B` via another transaction whose resulting state diff is delivered to `invalidate_limit_class_cache` before `is_high_rate_account` has cached `trusted(payer) = true` for this payer.
3. Because `cache.is_trusted_cached(payer)` is `false` at that moment, the balance diff does not advance `classification_generation` [9](#0-8) .
4. The original transaction from step 2(a) reaches `try_admit`, which creates `PayerBook::new(B)` (the stale, higher balance) and reserves against it [4](#0-3) , even though the payer's real balance is now `B'`.
5. Further sponsored transactions from the same payer can then be admitted up to the stale `B`, exceeding the true balance `B'`, until a *subsequent* balance diff (now correctly seen as a cached-trusted payer) finally corrects the book via `on_balance_changed`.

    /// Invalidates classifications affected by canonical state changes.
    pub fn invalidate_limit_class_cache(&self, diffs: &[crate::AccountStateDiff]) {
        let mut cache = self.limit_class_cache.write();
        // Advance the generation for every classification surface change, even
        // on a cache miss: a validation may have read the old state but not yet
        // inserted it. Its guarded insertion or later pool admission must see a
        // changed generation rather than retain that stale classification.
        let mut changed = false;
        for diff in diffs {
            if diff.code_changed {
                changed = true;
                cache.invalidate_code(diff.address);
            }
            if diff.address == AccountConfigurationStorage::ADDRESS {
                for slot in &diff.changed_slots {
                    changed = true;
                    cache.invalidate_slot(slot);
                }
            }
            // A balance change is not part of the cached classification, but it
            // seeds a trusted payer's `PayerBook` on first admission.
            // `on_balance_changed` only corrects payers that already have a book;
            // a trusted payer with no book yet would otherwise seed it from the
            // (now stale) validation snapshot. Advance the generation so an
            // admission whose validation predates this diff re-validates against
            // the fresh balance.
            //
            // Restricted to *known-trusted* payers: only they use the balance
            // book, and a trusted payer with a pending transaction was just
            // classified into the cache during that validation. Ordinary balance
            // churn — the vast majority, and unrelated to any book — must not
            // advance the generation and bounce unrelated admissions.
            if diff.balance.is_some() && cache.is_trusted_cached(diff.address) {
                changed = true;
            }
        }
        if changed {
            self.limit_class_cache_generation.fetch_add(1, Ordering::Release);
        }
    }
