### Title
Rejection votes silently dropped due to single-column `PRIMARY KEY(signer_addr)` in `block_rejection_signer_addrs`, undercounting the rejection quorum - (File: `stacks-signer/src/signerdb.rs`)

### Summary
The `block_rejection_signer_addrs` table's primary key is `signer_addr` alone, not `(signer_signature_hash, signer_addr)`. Once any signer has recorded a rejection for one block, its `add_block_rejection_signer_addr` call for a *different* block hash silently fails with a constraint violation, and the caller (`store_and_process_block_rejection`) swallows that error instead of returning early — continuing to compute rejection-consensus using an incomplete rejection set. This is directly analogous to the Holograph finding: a data structure/event lacking the distinguishing parameter (there, "owner"; here, "signer_signature_hash" in the key) causes downstream aggregation to be systematically wrong.

### Finding Description
The table is declared with only `signer_addr` as the primary key: [1](#0-0) 

`add_block_rejection_signer_addr` looks up an existing row scoped by *both* `signer_signature_hash` and `signer_addr` to decide whether to update or insert: [2](#0-1) 

Because the actual `PRIMARY KEY` is only `signer_addr`, once a signer address has a row for block hash A, an attempt to `INSERT` a row for the same `signer_addr` with a *different* hash B (the `None => insert` branch, since the lookup filtered on hash B finds nothing) collides with the existing primary-key value and the insert fails with a `rusqlite` constraint-violation error.

The caller does not treat that error as fatal or retry — it just logs and falls through to compute consensus from whatever rejections are already persisted: [3](#0-2) 

So from the *second* distinct block a given signer ever rejects onward, that signer's rejection weight is permanently excluded from `get_block_rejection_signer_addrs` / `total_reject_weight` for every subsequent block, even though the signer did broadcast (and thus other signers may have received) a genuine rejection.

### Impact Explanation
`total_reject_weight` drives the "does a blocking minority (>30%) exist" check that marks a block `GloballyRejected`: [4](#0-3) 

If enough individual signers' rejections are dropped this way (which happens deterministically for every signer after their first ever rejection, requiring no majority and no key compromise — just normal chain operation across multiple tenures/forks), the locally-computed rejection weight for an invalid/non-canonical/conflicting block can understate the true blocking minority. This breaks the aggregated-weight vs. verified-rejects equality that liveness/safety guarantees for block finalization rely on: a block that should be recognized as globally rejected by the local signer's bookkeeping may never cross that threshold, and conversely the signer keeps re-evaluating/holding state based on stale, incomplete rejection data. This matches the required impact class ("a rejection recounted [i.e. miscounted] as an accept" / broken aggregated-weight-vs-verified-accepts equality).

### Likelihood Explanation
This requires no majority, no other signer's key, and no auth token — it is triggered purely by normal signer operation: any single signer that rejects more than one distinct block over its lifetime (a routine occurrence — competing miner proposals, reorgs, retries) hits the primary-key collision. A one-slot miner or gossip peer proposing a second conflicting/invalid block at any point after a signer has ever rejected anything is sufficient to trigger silent vote-dropping for that signer going forward.

### Recommendation
Change the table definition to `PRIMARY KEY (signer_signature_hash, signer_addr)` (matching how `signer_signature_hash` is treated in the analogous `block_signatures`/lookup logic), and add a schema migration to correct any already-deployed databases. Additionally, `store_and_process_block_rejection` should treat an `Err` from `add_block_rejection_signer_addr` as fatal to this rejection's processing (return, do not fall through to consensus computation) rather than silently continuing.

### Proof of Concept
1. Signer S receives Block A (hash `h1`) and rejects it → `add_block_rejection_signer_addr(h1, S, reason)` inserts `(h1, S)`, primary key `S` now occupied.
2. Later (any subsequent tenure/fork/retry — no majority needed), signer S receives a different Block B (hash `h2`) and rejects it → lookup for `(h2, S)` finds nothing, falls to `None => insert` branch, attempts `INSERT (h2, S)`.
3. This insert violates the `PRIMARY KEY(signer_addr)` constraint since `S` already has a row for `h1`; `rusqlite` returns an error.
4. `store_and_process_block_rejection` logs the error but does not return; `get_block_rejection_signer_addrs(h2)` is subsequently queried and does not include S's vote.
5. S's rejection weight for block B (and every block after `h1`) is never counted toward `total_reject_weight`, permanently understating the true rejecting weight for this signer. [1](#0-0) [2](#0-1) [3](#0-2)
