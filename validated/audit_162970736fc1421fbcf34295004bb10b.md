### Title
`InitializeBuffer` in `bpf_loader_upgradeable` sets buffer authority without requiring any signature, allowing hijacking of a not-yet-initialized buffer account - (File: programs/bpf_loader/src/lib.rs)

### Summary
The `UpgradeableLoaderInstruction::InitializeBuffer` handler sets the buffer's `authority_address` from whatever pubkey is supplied as instruction account #1, with no signer check on that account and no signer/owner check on the buffer account itself beyond it being `Uninitialized`. [1](#0-0)  This mirrors the `DODOApproveProxy.init` pattern: an "initializer" function that establishes ownership/authority state is reachable by anyone as long as the target account is still uninitialized, with no proof that the caller controls it.

### Finding Description
A buffer account is typically created in a separate `system_instruction::create_account` (or `create_account_with_seed`) call that assigns ownership to `bpf_loader_upgradeable::id()`, after which a follow-up `InitializeBuffer` instruction is expected to be sent by the same party to set the buffer's authority. However, `InitializeBuffer` performs no signature check at all: [1](#0-0) 

Any transaction sender can construct an `InitializeBuffer` instruction referencing:
- account #0 = the victim's buffer pubkey (public, writable, owned by `bpf_loader_upgradeable`, still `Uninitialized`)
- account #1 = an attacker-controlled pubkey (not required to be a signer)

If this transaction lands before the legitimate owner's own `InitializeBuffer` call (e.g., the account creation and initialization are sent as two separate transactions, or the attacker races/front-runs the initialization in the same slot), the buffer's `authority_address` becomes the attacker's key. Because subsequent operations (`Write`, `SetAuthority`, `SetAuthorityChecked`, and `Close`) all gate on matching `authority_address` plus that authority's signature, [2](#0-1)  the legitimate creator is permanently locked out and the attacker gains exclusive control.

The attacker can then call `Close` on the hijacked buffer, which requires only the (attacker's own) authority signature via `common_close_account`, and transfers all lamports held by the buffer account to a recipient of the attacker's choosing: [3](#0-2) 

### Impact Explanation
This allows an unprivileged transaction sender to seize control of another party's buffer account and subsequently drain its lamports (which can be non-trivial: buffers for large programs must be funded to rent-exempt minimum, which scales with program size, sometimes multiple SOL). This is a concrete unsigned/unauthorized fund movement, analogous to `DODOApproveProxy.init` letting anyone take ownership and later abuse owner-only functions.

### Likelihood Explanation
Exploitability depends on a timing window between account creation (`CreateAccount` assigning the buffer to `bpf_loader_upgradeable`) and the follow-up `InitializeBuffer` call landing as separate transactions/instructions rather than atomically in the same transaction as creation. Many CLI/tooling flows (e.g., `solana program deploy`) bundle creation and initialization together in one transaction, which would not be exploitable this way; but any workflow, custom tooling, or manual instruction construction that separates these two steps (or any race within the same slot when instructions are unconfirmed/pending) creates the window. I was not able to confirm from the indexed code whether every call path in this repo always sends `CreateAccount` and `InitializeBuffer` atomically in one transaction (e.g., in `cli/src/program.rs`) — this would need to be verified in a full checkout to determine real-world reachability precisely.

### Recommendation
Require the buffer account (account #0) to be a signer in `InitializeBuffer`, so only the party that also authorizes/created the account can set its authority — analogous to the `DODOApproveProxy` fix of requiring the initializer to be permissioned/signed rather than callable by anyone. Alternatively, mandate that `InitializeBuffer` and the preceding `CreateAccount` be enforced as part of the same atomic transaction/instruction sequence at the SDK/CLI level, and reject `InitializeBuffer` if the buffer account was not created within the same transaction.

### Proof of Concept
1. Victim submits `create_account(payer, buffer_pubkey, ..., owner=bpf_loader_upgradeable::id())` in transaction T1, intending to submit `InitializeBuffer` in a follow-up transaction T2.
2. After T1 lands (buffer account exists, `Uninitialized` state, owned by `bpf_loader_upgradeable`), an attacker observes this on-chain and submits their own transaction containing `UpgradeableLoaderInstruction::InitializeBuffer` with account #0 = `buffer_pubkey`, account #1 = `attacker_pubkey` (not signer), before the victim's T2 lands.
3. `buffer.get_state()` is still `Uninitialized`, so the check at [4](#0-3)  passes, and `authority_address` is set to `attacker_pubkey`.
4. Victim's own `InitializeBuffer` (T2) now fails with `AccountAlreadyInitialized`.
5. Attacker submits `UpgradeableLoaderInstruction::Close` with themselves as authority (self-signed), reaching `common_close_account`, transferring all lamports from the buffer account to an attacker-controlled recipient account: [3](#0-2)
