### Title
Cache key can inject arbitrary PowerShell via smart-quote breakout of `psSingleQuote`-quoted `--header` argument - ([File: shells/abstract.go, shells/powershell.go])

### Summary
An attacker-controlled cache `key:` value, after `ExpandValue` expansion in `newCacheConfig`, becomes the `HumanKey`/`cachekey` metadata value that is embedded verbatim into an S3 `x-amz-meta-*` upload header via `getCacheUploadURLAndEnv`. That header string is later placed unescaped into a `--header` CLI argument and quoted with `psSingleQuote` in `PsWriter.buildCommand`, which only doubles ASCII `'` characters and does not account for PowerShell's documented Unicode "smart quote" equivalence classes, allowing early termination of the single-quoted token and injection of attacker-controlled PowerShell.

### Finding Description
- `newCacheConfig` (`shells/abstract.go:133-208`) expands the job-supplied cache key with `build.GetAllVariables().ExpandValue(userKey)` to produce `rawKey`, then computes `HumanKey`. When `featureflags.HashCacheKeys` is enabled, the `sanitizer` is set to the identity function (`shells/abstract.go:146-149`), so `HumanKey` is **not** filesystem/shell-sanitized and can contain arbitrary Unicode, including PowerShell "smart quote" characters (U+2018/2019/201A/201B, U+201C/201D/201E/201F), which PowerShell's tokenizer documents as equivalent to ASCII `'`/`"` for opening/closing quoted string literals.
- `addCacheUploadCommand` (`shells/abstract.go:1539-1601`) builds `metadata := map[string]string{"cachekey": cacheConfig.HumanKey}` and passes it to `getCacheUploadURLAndEnv` (`shells/abstract.go:1603-1633`), which calls `adapter.WithMetadata(metadata)` before `adapter.GetUploadURL(ctx)`. The S3 adapter turns this metadata into `x-amz-meta-cachekey`-style presign headers, which are returned in `uploadURL.Headers` and appended as literal, unescaped `--header` CLI arguments: `fmt.Sprintf("%s: %s", key, value)` (`shells/abstract.go:1621-1626`).
- These `args` (including the `--header "...: <HumanKey>"` string) are passed to `w.IfCmdWithOutput(info.RunnerCommand, args...)` (`shells/abstract.go:1595`), which on PowerShell calls `PsWriter.IfCmdWithOutput` → `buildCommand(psSingleQuote, cmd, arguments...)` (`shells/powershell.go:499-500`, `384-394`). Each argument is quoted with `psSingleQuote`, which (as used throughout `powershell.go`, e.g. `SetupGitCredHelper` at line 291) escapes only the ASCII apostrophe by doubling it.
- Because PowerShell treats the Unicode smart-quote family as members of the same "single quote" token class as ASCII `'`, embedding one of these code points inside a `psSingleQuote`-wrapped string can close the string early even though no ASCII `'` was doubled/escaped, letting the remainder of the cache-key-derived text be parsed as new PowerShell tokens/statements in the generated cache-archiver invocation script.
- No other check (allowed-image, path validation, masking) applies to cache key content used as S3 metadata; the only mitigating control is `cachekey.Sanitize`, which is bypassed entirely when `FF_HASH_CACHE_KEYS` is on.

### Impact Explanation
If exploitable, this allows a normal pipeline author to have arbitrary PowerShell statements executed by the runner's helper/job shell process during the cache-upload stage, breaking the sandbox boundary of the job's own script execution and gaining code execution in the job's PowerShell shell context (same trust level as the job itself, but via an unintended injection path rather than the job's own script step) — a genuine "unsafe parsing" / injection bug in shell command construction.

### Likelihood Explanation
Preconditions: PowerShell/pwsh shell executor, `FF_HASH_CACHE_KEYS` enabled (removes cache-key sanitization), a `cache:key` field or `CACHE_FALLBACK_KEY`/CI variable value containing a PowerShell smart-quote character, and the runner's S3 cache backend reflecting the `cachekey` metadata into presign headers. These are all attacker-controllable via ordinary `.gitlab-ci.yml`/variable configuration, making the trigger straightforward to reach; the main uncertainty is whether the concrete S3 SDK path used by `GetUploadURL` actually surfaces `WithMetadata` values as request headers (this could not be independently confirmed from the retrieved code) and whether `psSingleQuote`'s exact implementation contains any additional filtering beyond ASCII-quote doubling.

### Recommendation
- Reject or strip PowerShell "smart quote" code points (U+2018, U+2019, U+201A, U+201B, U+201C, U+201D, U+201E, U+201F) and other non-ASCII quote-equivalent characters in `psSingleQuote`/`psDoubleQuote`, or use `-EncodedCommand`/argument arrays instead of string concatenation for building PowerShell invocations.
- Always sanitize `HumanKey` (cache key metadata) regardless of `FF_HASH_CACHE_KEYS` state before it is used in any header/metadata value that flows into a generated shell command.
- Avoid embedding raw cache-key-derived text into HTTP headers passed as CLI arguments; pass such values via the existing `--env-file`/environment mechanism instead, consistent with how other metadata is already handled (`CACHE_METADATA` env var).

### Proof of Concept
Go fuzz test outline:
```go
func FuzzCacheKeyPsInjection(f *testing.F) {
    f.Add("\u2019; calc")
    f.Fuzz(func(t *testing.T, key string) {
        build := newTestBuild(t) // helper constructing common.Build with FF_HASH_CACHE_KEYS=true
        build.Variables = spec.Variables{{Key: "CI_CACHE_KEY", Value: key}}
        cfg, _, err := newCacheConfig(build, "$CI_CACHE_KEY")
        if err != nil { return }

        w := NewPsWriter(&PowerShell{}, common.ShellScriptInfo{Build: build})
        // simulate metadata->header->args flow
        args, env, _ := getCacheUploadURLAndEnv(context.Background(), build, cfg.HashedKey,
            map[string]string{"cachekey": cfg.HumanKey})
        w.IfCmdWithOutput("gitlab-runner", append([]string{"cache-archiver"}, args...)...)
        script := w.String()

        // Parse with a PowerShell AST parser (via pwsh -NoProfile -Command
        // "[System.Management.Automation.Language.Parser]::ParseInput(...)")
        // and assert:
        // 1. no ParseError is produced that differs from expected argument-count errors, and
        // 2. the parsed command's argument list length equals len(args)+1 (no extra injected commands/tokens).
        assertSingleCommandInvocation(t, script, len(args)+1)
    })
}
```
Expected result if vulnerable: for keys containing U+2019/U+201C etc., the parsed AST shows more than one command/statement (i.e., extra injected commands), demonstrating breakout from the intended `--header` argument.
