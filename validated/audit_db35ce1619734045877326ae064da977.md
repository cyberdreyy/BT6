### Title
Instant-withdraw request bricks `startEpoch` in programmable-borrower mode, freezing the pool - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
The external report describes pools silently becoming unavailable so no new positions can be opened. The analog in `IdleCDOEpochVariant` is a mode conflict between the instant-withdraw path and the programmable-borrower invariant: `requestWithdraw` can still create an instant-withdraw receipt while `isProgrammableBorrower` is true, but `startEpoch` hard-reverts via `_checkProgrammableBorrowerMode()` whenever `_pendingInstant() != 0`. A single unprivileged tranche-token holder can therefore make the epoch state machine unable to transition from buffer to running, leaving the pool "unavailable" — deposits idle, queued withdraw requests unprocessable — until an admin intervenes.

### Finding Description
`requestWithdraw` gates the instant path only on `_isInstantWithdrawEnabled()` and the APR delta condition; it never checks `isProgrammableBorrower` [1](#0-0) . The comment on line 758 acknowledges "Programmable borrower deployments do not support instant withdrawals," but nothing enforces it at request time.

Meanwhile, `startEpoch` calls `_checkProgrammableBorrowerMode()`, which reverts when `isProgrammableBorrower && _pendingInstant() != 0` [2](#0-1) , and the only code paths that decrease `pendingInstantWithdraws` are `collectInstantWithdrawFunds` (called inside `startEpoch` itself [3](#0-2) ) and `getInstantWithdrawFunds`, which explicitly reverts when `isProgrammableBorrower` is set [4](#0-3) .

Attack sequence (buffer phase, programmable + minted-interest mode, instant withdrawals enabled by the honest manager):
1. Manager stops an epoch with a lower `_newApr`, so `lastEpochApr > unscaledApr + instantWithdrawAprDelta`.
2. Attacker (a KYC-passed tranche holder) calls `requestWithdraw(dust, AATranche)` — the instant branch burns CDO strategy tokens and increments `pendingInstantWithdraws` [5](#0-4) .
3. Every subsequent `startEpoch` call reverts with `NotAllowed` at `_checkProgrammableBorrowerMode`.

Because `setIsProgrammableBorrower` only blocks changes while `isEpochRunning` [6](#0-5) , the poisoned state persists across the buffer for any amount of time.

### Impact Explanation
Temporary freezing of all pool funds. While `startEpoch` is bricked, the epoch can never begin: `requestWithdraw` receipts (normal and the attacker's instant one) cannot be funded or claimed because claims settle only through epoch transitions in `IdleCreditVault`, and deposits accepted during the buffer remain idle. There is no user-side escape — tranche tokens were already burned in `requestInstantWithdraw`/`_withdrawOps`. Recovery requires the honest owner to call `setIsProgrammableBorrower(false)` and then restart the epoch, meaning fund availability is entirely admin-dependent. Loss = opportunity cost plus locked principal for the duration of the freeze, proportional to total pool NAV; even a 1-wei request triggers it.

### Likelihood Explanation
Requires three conditions: instant withdrawals enabled (`disableInstantWithdraw == false` via `setInstantWithdrawParams`), an APR decrease between epochs so the instant branch is reachable, and `isProgrammableBorrower == true` — either configured before the request or enabled by the owner during the buffer while a pending instant receipt exists (the setter does not check `_pendingInstant()`). All are plausible operational configurations; the attacker action itself is a single unprivileged dust request, so likelihood of exploitation conditional on configuration is high. Overall likelihood is moderate due to the configuration preconditions.

### Recommendation
Block instant-withdraw requests at request time in programmable mode, e.g. add `isProgrammableBorrower` to the `requestWithdraw` instant branch check (route the request to the normal withdraw path instead), or enforce `disableInstantWithdraw`/`_isInstantWithdrawEnabled() == false` inside `setIsProgrammableBorrower` and `startEpoch`. Additionally, provide a recovery path that clears stranded `pendingInstantWithdraws` (e.g., allow `getInstantWithdrawFunds` in programmable mode after `instantWithdrawDeadline`) so a single receipt cannot wedge the state machine.

### Proof of Concept
Foundry fork PoC (schematic, using the repo's test harness conventions):

```solidity
function testInstantRequestBricksProgrammableStartEpoch() external {
  // setup: programmable borrower + minted interest configured by owner
  vm.prank(owner);
  cdoEpoch.setIsInterestMinted(true);
  vm.prank(owner);
  cdoEpoch.setIsProgrammableBorrower(true);
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(3 days, 1000, false); // enable instant path

  idleCDO.depositAA(10_000 * ONE_SCALE);

  // epoch 0 runs and stops with a lower APR so instant requests unlock
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

  // attacker (KYC'd holder) files a dust instant withdraw request
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(1, address(AAtranche));
  assertGt(IdleCreditVault(address(strategy)).pendingInstantWithdraws(), 0);

  // buffer elapses; manager tries to start the next epoch -> always reverts
  vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod() + 1);
  vm.expectRevert(NotAllowed.selector);
  vm.prank(manager);
  cdoEpoch.startEpoch(); // _checkProgrammableBorrowerMode: _pendingInstant() != 0

  // getInstantWithdrawFunds is also unusable in programmable mode
  vm.expectRevert(NotAllowed.selector);
  vm.prank(manager);
  cdoEpoch.getInstantWithdrawFunds();

  // pool is frozen until owner disables the programmable flag
}
```

Note: I could not fully verify the exact `_pendingInstant()`/`_isInstantWithdrawEnabled()` bodies (index excerpts truncated their definitions), but their semantics are confirmed by the revert conditions in `startEpoch`/`getInstantWithdrawFunds` and the `requestInstantWithdraw` ledger updates cited above.
