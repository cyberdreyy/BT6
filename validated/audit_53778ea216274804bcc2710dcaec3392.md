### Title
Multisig confirm() counts confirmations from members already removed via DeleteMember, allowing execution below live-member threshold - (File: multisig2/src/lib.rs / multisig/src/lib.rs)

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` implement a K-of-N confirmation scheme where a `confirm()` call executes the pending request as soon as `confirmations.len() + 1 >= num_confirmations`. When a member is removed via `DeleteMember`/`DeleteKey`, the cleanup logic in `delete_member`/the `DeleteKey` action only purges confirmations for requests that the removed member itself **originated** (`r.member == member` / `r.signer_pk == pk`). It does not remove that member's stale confirmations from **other** pending requests they had merely confirmed. This is the same class of bug as the reported Yearn V3 issue: a piece of state tied to a participant (`current_debt` for a drained lender / a confirmation for a removed signer) becomes stale/invalid, but a downstream equality/threshold check (`new_debt == current_debt` / `confirmations.len()+1 >= num_confirmations`) does not account for this staleness, producing incorrect behavior.

### Finding Description
In `multisig2/src/lib.rs`:
- `confirm()` (lines 292-315) computes whether to execute a request purely by counting entries in the `confirmations: LookupMap<RequestId, HashSet<String>>` set for that `request_id`: `if confirmations.len() as u32 + 1 >= self.num_confirmations { ... execute_request ... }`.
- `delete_member()` (lines 356-379) only removes confirmations for requests where `r.member == member` (i.e., requests the removed member itself created): 
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
```
It never scans other pending requests' `confirmations` sets to strip out entries belonging to the removed member.

The identical pattern exists in `multisig/src/lib.rs`'s `DeleteKey` action handler (lines 198-216), which filters `r.signer_pk == pk` (requests originated by that key) before clearing confirmations, again leaving the deleted key's confirmations on requests it didn't originate untouched.

**Binding broken:** `confirmations recorded for request R` should equal `confirmations from currently live members for request R`. After a member/key deletion, this equality is violated — a removed member's vote remains in the `HashSet<String>` for any request they confirmed but did not create, and it is still counted by `confirm()`'s threshold check.

### Impact Explanation
This allows a multisig request (e.g., a `Transfer` draining funds, or an `AddKey`/`AddMember` granting new control) to be executed with fewer than `num_confirmations` *live* members' consent — i.e., a multisig request executed below threshold. This directly matches the Critical impact category "a multisig request executed below threshold." Example: with `num_confirmations = 3` and members A, B, C, D:
1. A creates request R1 (e.g., `Transfer` to an attacker-controlled account) and confirms (1/3).
2. B confirms R1 (2/3, one more needed).
3. Separately, member B is removed via a legitimate `DeleteMember{member: B}` request (a distinct, unrelated cleanup, e.g. B's key was compromised or B left the org). `delete_member` only inspects requests where `r.member == B` (i.e., requests B *originated*), so R1 (originated by A) is untouched — B's confirmation on R1 remains in `confirmations`.
4. C confirms R1. `confirmations.len() + 1 = 3 >= 3` → request executes, even though the currently live members are only A, C, D and only two of them (A, C) ever approved R1 while B — no longer a member — is the third counted vote.

### Likelihood Explanation
This requires no attacker to compromise the multisig itself — it can occur through routine operational usage: a member is removed for benign reasons (rotation, incident response, key compromise) while other requests are mid-confirmation, which is a plausible and unprivileged-from-the-attacker's-perspective sequence of legitimate multisig actions. No malicious member collusion is even strictly required if the deleted member's key was compromised or a request was left pending during a member's departure; an attacker who compromises one already-confirmed member's key (before removal) benefits directly since their stale confirmation persists and still counts after removal.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over **all** pending requests' `confirmations` sets and remove the entry corresponding to the deleted member/key, not only the requests that member originated:
```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    for (request_id, _) in self.requests.iter() {
        if let Some(mut confirmations) = self.confirmations.get(&request_id) {
            if confirmations.remove(&member.to_string()) {
                self.confirmations.insert(&request_id, &confirmations);
            }
        }
    }
    ...
}
```
Alternatively, validate at `confirm()` time that every entry in `confirmations` still corresponds to a current member (filter live members before comparing count to `num_confirmations`), rather than trusting the raw stored count.

### Proof of Concept
Using `multisig2/src/lib.rs` test harness style (based on `test_multi_3_of_n` at lines 573-612):
```rust
// members: A, B, C, D ; num_confirmations = 3
let mut c = MultiSigContract::new(members(), 3); // A,B,C,D

// A creates and confirms R1 (attacker transfer)
testing_env!(context_as(A));
let r1 = c.add_request(MultiSigRequest {
    receiver_id: attacker(),
    actions: vec![MultiSigRequestAction::Transfer { amount: BIG_AMOUNT.into() }],
});
c.confirm(r1); // 1/3

// B confirms R1
testing_env!(context_as(B));
c.confirm(r1); // 2/3, confirmations = {A, B}

// Separately: C and D (and A) remove B via DeleteMember request (3-of-4 confirm)
testing_env!(context_as(C));
let r_del = c.add_request(MultiSigRequest {
    receiver_id: env::current_account_id(),
    actions: vec![MultiSigRequestAction::DeleteMember { member: member_b() }],
});
c.confirm(r_del);
testing_env!(context_as(D));
c.confirm(r_del);
testing_env!(context_as(A));
c.confirm(r_del); // executes DeleteMember(B); members now {A, C, D}

// R1's confirmations still contain B's stale entry (delete_member only cleared
// requests where r.member == B, but r1.member == A)
assert_eq!(c.get_confirmations(r1).len(), 2); // {A, B} — B no longer a member!

// C confirms R1: count becomes 3 (A, B[stale], C) >= num_confirmations(3) → executes
testing_env!(context_as(C));
c.confirm(r1); // Transfer executes with only A and C being live approvers
```

```rust
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
```

```rust
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);

        self.num_requests_pk.remove(&member.to_string());

            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
```
