### Title
`outgoingToken` field on GraphQL `Bridge` type is readable by any authenticated user regardless of role, including minimal view-role sessions - ([File: core/web/resolver/bridge.go])

### Summary
The `Bridge` GraphQL type's `outgoingToken` field is resolved unconditionally by `BridgeResolver.OutgoingToken`, and the parent `Query.Bridge`/`Query.Bridges` resolvers only enforce `authenticateUser`, which accepts any authenticated session including `UserRoleView`. This lets the lowest-privileged authenticated GraphQL caller enumerate and harvest every configured bridge's `outgoingToken` via the paginated `bridges` query.

### Finding Description
`BridgeResolver.OutgoingToken` simply returns the stored secret with no role gating: [1](#0-0) 

The `Query.Bridge` and `Query.Bridges` resolvers, which are the only entry points that populate `BridgeResolver`, call `authenticateUser(ctx)` — not `authenticateUserCanRun`, `authenticateUserCanEdit`, or `authenticateUserIsAdmin`: [2](#0-1) 

`authenticateUser` only checks that a valid GQL session exists in context; it performs no role comparison at all, unlike its sibling helpers that explicitly reject `UserRoleView`/`UserRoleRun`: [3](#0-2) 

The GraphQL schema itself declares `outgoingToken: String!` as a plain non-nullable field on `Bridge` with no separate authorization annotation, and it is returned in both the `bridge(id)` single lookup and the paginated `bridges` list query, which supports `offset`/`limit` for full enumeration: [4](#0-3) 

The session itself is established via cookie-based `AuthenticateGQL` middleware attached to `POST /query`, and it accepts any valid, non-expired session regardless of role — the role check is left entirely to individual resolvers: [5](#0-4) [6](#0-5) 

Existing tests confirm the field is returned to any `authenticated: true` test case with no role differentiation asserted (only `unauthorizedTestCase` for the fully unauthenticated case is checked), meaning there's no test verifying role-based redaction of `outgoingToken`: [7](#0-6) 

Root cause: unlike write/mutation resolvers throughout `core/web/resolver/mutation.go` which consistently use `authenticateUserCanEdit`/`authenticateUserIsAdmin` for sensitive operations (e.g. `DeleteBridge`, `CreateP2PKey`, `SetGlobalLogLevel`), the bridge *read* path uses the weakest check (`authenticateUser`), and the sensitive `outgoingToken` field is not separately gated or redacted based on role at the resolver level.

### Impact Explanation
`OutgoingToken` is the bearer credential the node injects when forwarding job-run data to an external adapter (bridge). Disclosure of this token to a low-privileged (`view`-role) session lets that caller impersonate the node when calling the external adapter directly, i.e., request impersonation / credential exposure toward the external adapter — a legitimate Chainlink bounty "credential/secret disclosure" impact. Because `bridges` is a paginated list query, an attacker with only a `view` role can enumerate and exfiltrate every configured bridge's outgoing token in one or a few requests, not just one.

### Likelihood Explanation
Minimal precondition: any authenticated session, including the lowest role (`UserRoleView`) created via a normal API login. No admin, edit, or run privileges are required. The attack is a single GraphQL query (`query{ bridges{ results{ name outgoingToken } } }`), fully repeatable, and requires no timing or race conditions — this makes exploitation straightforward for any user who legitimately has a "view-only" account (e.g., an auditor or read-only dashboard user).

### Recommendation
Require at least `edit` (or `admin`) role to read `outgoingToken`, either by:
1. Changing `Query.Bridge`/`Query.Bridges` to call `authenticateUserCanEdit`/`authenticateUserIsAdmin` instead of `authenticateUser`, or
2. Redacting `BridgeResolver.OutgoingToken()` (returning an empty string or an error) unless the caller's session role (obtained via `auth.GetGQLAuthenticatedSession(ctx)`) is `edit` or `admin`, mirroring the REST bridge presenter's behavior if it already restricts this field.

### Proof of Concept
Go handler-level integration test plan (extending `core/web/resolver/bridge_test.go` style `GQLTestCase`):
1. Build a `gqlTestFramework` session authenticated with `sessions.UserRoleView` (or `UserRoleRun`) instead of the default admin fixture used in `unauthorizedTestCase`.
2. Mock `f.Mocks.bridgeORM.On("FindBridges", ...)` to return a `bridges.BridgeType` with `OutgoingToken: "secret-token"`.
3. Execute query: `query{ bridges(offset:0, limit:10){ results{ name outgoingToken } metadata{ total } } }`.
4. Assert current (vulnerable) behavior: response contains `"outgoingToken":"secret-token"` with HTTP 200, no error — proving the bug.
5. After remediation, re-run and assert either a `Forbidden`/`RoleNotPermittedError` GraphQL error, or `outgoingToken` returned as `null`/empty for `view`/`run` roles, while `edit`/`admin` roles still receive the real token.

// Authenticates the user from the session cookie, presence of user inherently provides 'view' access.
func authenticateUser(ctx context.Context) error {
	if _, ok := auth.GetGQLAuthenticatedSession(ctx); !ok {
		return unauthorizedError{}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'run' role.
func authenticateUserCanRun(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role == sessions.UserRoleView {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}

// AuthenticateGQL middleware checks the session cookie for a user and sets it
// on the request context if it exists. It is the responsibility of each resolver
// to validate whether it requires an authenticated user.
//
// We currently only support GQL authentication by session cookie.
func AuthenticateGQL(authenticator Authenticator, lggr logger.Logger) gin.HandlerFunc {
	return func(c *gin.Context) {
		ctx := c.Request.Context()
		session := sessions.Default(c)
		sessionID, ok := session.Get(SessionIDKey).(string)
		if !ok {
			return
		}

		user, err := authenticator.AuthorizedUserWithSession(ctx, sessionID)
		if err != nil {
			if errors.Is(err, clsessions.ErrUserSessionExpired) {
				lggr.Warnw("Failed to authenticate session", "err", err)
			} else {
				lggr.Errorw("Failed call to AuthorizedUserWithSession, unable to get user", "err", err)
			}
			return
		}

		ctx = WithGQLAuthenticatedSession(c.Request.Context(), user, sessionID)

		c.Request = c.Request.WithContext(ctx)
	}
}
