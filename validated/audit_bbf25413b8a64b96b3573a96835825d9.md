### Title
Loss-adjusted withdraw receipt is paid at par after a subsequent withdraw request — (`File: contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
The kernel bug pattern is "teardown/decrement executed on a shared counter even though the per-entry lookup failed." The vault analog lives in the claim path: `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. it only ever checks the *latest* request epoch. If a user's earlier receipt belongs to a loss-adjusted epoch but their `lastWithdrawRequest` has since moved to a later epoch, the lookup misses and the claim falls through to `_claimFundedWithdrawRequest`, which pays the **entire aggregate** `withdrawsRequests[_user]` at par — including the receipt that was only partially funded by the borrower.

### Finding Description
- `requestWithdraw` stores only a single marker: `lastWithdrawRequest[_user] = currentEpoch` (line 282), while the owed amount accumulates in the aggregate `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch`.
- When a stop ends with a realized loss, `collectWithdrawFunds` records `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` and zeroes `pendingWithdraws`, but leaves each user's `withdrawsRequests`/`withdrawsRequestsByEpoch` basis at full value (lines 411-430). Only `pendingBasis * price` underlying is actually collected.
- On claim, `_claimLossAdjustedWithdrawRequest` derives the epoch solely from `lastWithdrawRequest[_user]` (line 790). If the user made any later `requestWithdraw` (which is explicitly allowed — the code comments note unclaimed requests just wait longer), `lastWithdrawRequest` now points to a later epoch whose `lossRecoveryPriceByEpoch` is 0, so the function returns 0.
- `_claimFundedWithdrawRequest` then burns and pays `withdrawsRequests[_user]` in full (lines 338-349), even though the epoch-N portion was funded only at `lossRecoveryPrice`.

### Impact Explanation
The user receives `amount_N` at par instead of `amount_N * lossRecoveryPrice / RECOVERY_FULL`. The shortfall `(1 - price) * amount_N` is paid out of underlyings held for other receipts or active LPs, since `pendingWithdraws` was already zeroed and only the haircutted amount was ever collected. This is direct theft / insolvency: either later claimants' funded claims revert on insufficient balance (permanent freezing of their withdrawals) or the strategy's solvency is eroded by the unfunded payout.

### Likelihood Explanation
Requires only ordinary user actions: request a withdraw, let the epoch end in a `stopEpochWithDuration` loss (a designed, honest-manager flow), request another withdraw in a later epoch, wait one epoch, then claim. No privileged misbehavior is needed; the attacker is a normal KYC'd tranche holder. The guard `_clearWithdrawClaimForEpoch` would correctly clear per-epoch state — but it is never reached because the loss-epoch lookup is keyed only to `lastWithdrawRequest`.

### Recommendation
Track the loss-epoch per user (e.g. iterate `withdrawsRequestsByEpoch` epochs with a nonzero `lossRecoveryPriceByEpoch`, or store a per-user loss epoch pointer separate from `lastWithdrawRequest`), so a loss-adjusted receipt is always claimed through `_claimLossAdjustedWithdrawRequest` regardless of later requests. Alternatively, when a user has an unclaimed loss-adjusted receipt, revert new `requestWithdraw` calls until it is claimed.

### Proof of Concept
Foundry fork sketch (mainnet fork, epoch variant + IdleCreditVault):
1. `depositAA(user, X)`; `startEpoch`.
2. `requestWithdraw(user, xTranche)` → `lastWithdrawRequest[user]=N`, `withdrawsRequests[N]+=x`.
3. `stopEpochWithDuration(loss)` so `collectWithdrawFunds(p*x)` runs → `lossRecoveryPriceByEpoch[N]=p<1`, `pendingWithdraws=0`.
4. `startEpoch`; `requestWithdraw(user, yTranche)` → `lastWithdrawRequest[user]=N+1`.
5. `stopEpoch` fully funds epoch N+1 receipts (`collectWithdrawFunds(y)`).
6. `claimWithdrawRequest(user)`: loss lookup on epoch N+1 returns 0; funded path burns and transfers `x + y` at par.
7. Assert `underlying.balanceOf(user) == x + y` while the strategy only ever received `p*x + y` — a `(1-p)*x` deficit borne by other claimants.
