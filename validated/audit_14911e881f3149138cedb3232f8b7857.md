### Title
Yield-split and fee parameters updated without processing accrued interest apply retroactively - ([File: contracts/IdleCDOCreditVault.sol])

### Summary

`setIsAYSActive`, `setMinAprSplitAYS`, the inherited `setTrancheAPRSplitRatio`, and `setFeeParams` update the parameters that govern how accrued-but-unsplit interest is divided between AA and BB tranches (and how much performance fee is taken), but none of them first call `_updateAccounting()`. Interest accrued since the last deposit/withdraw is therefore split under the *new* parameters instead of the parameters in force while it accrued — the same bug class as missing `processInterests` on `setTreasuryWeights`.

### Finding Description

`_updateAccounting` splits all NAV gain accrued since the last accounting checkpoint (`lastNAVAA + lastNAVBB`) using the *current* values of `trancheAPRSplitRatio` and `fee`:

- `contracts/IdleCDOCreditVault.sol:228-234` reads `trancheAPRSplitRatio` and `fee` and calls `_virtualPriceAux` for both tranches.
- `contracts/IdleCDOCreditVault.sol:306-313` computes `totalGain = nav - _lastNAV` and applies `fee` to the whole gain.
- `contracts/IdleCDOCreditVault.sol:324-328` splits the entire pending gain between AA and BB via `trancheAPRSplitRatio`.

Because deposits/withdrawals are the only routine triggers of `_updateAccounting` (line 200), a potentially large amount of interest can sit accrued-but-unsplit for a long time in a credit vault where interest only materializes at `stopEpoch` or on strategy-token price updates.

The parameter setters do not checkpoint first:

```solidity
// contracts/IdleCDOCreditVault.sol:450-453
function setIsAYSActive(bool _active) external virtual {
    _checkOnlyOwner();
    isAYSActive = _active;
}
```

```solidity
// contracts/IdleCDOCreditVault.sol:479-482
function setMinAprSplitAYS(uint256 _aprSplit) external virtual {
    _checkOnlyOwner();
    _checkAmountTooHigh((minAprSplitAYS = _aprSplit) > FULL_ALLOC);
}
```

and the inherited `setTrancheAPRSplitRatio` (`contracts/IdleCDO.sol:900-903`) also just writes the variable. In `setFeeParams` (`contracts/IdleCDOCreditVault.sol:461-470`), `_accrueManagementFee()` checkpoints only the *management* fee; the *performance* `fee` is applied at line 313 to the whole `nav - lastNAV` delta, so changing `fee` retroactively re-prices fees on already-accrued gains.

An honest owner/manager call therefore shifts yield between tranche classes (or between LPs and the fee receiver) for interest earned entirely under the previous parameters — a loss of yield for one side of the pool proportional to `accruedGain * |newSplit - oldSplit|`.

### Impact Explanation

Medium. Any pending accrued gain is split at the wrong ratio. With `splitRatio` moved by Δ and pending gain G, one tranche class permanently loses up to `G * Δ / FULL_ALLOC` to the other; raising `fee` retroactively skims `(newFee - oldFee) * G / FULL_ALLOC` from all LPs. The yield is redistributed to the counterparty tranche/fee receiver — a direct transfer of unclaimed yield, not just a price blip.

### Likelihood Explanation

Medium. Requires a legitimate owner call (split-ratio tuning, AYS toggle, fee change) while meaningful interest is accrued-but-unsplit — exactly the window between accounting checkpoints, which in this credit vault can span an entire epoch. No attacker action is required; the loss window exists until the next deposit/withdraw/harvest.

### Recommendation

Call `_updateAccounting()` (or `_forceUpdateAccounting()`) inside `setTrancheAPRSplitRatio`, `setMinAprSplitAYS`, `setIsAYSActive`, and `setFeeParams` before writing the new values, mirroring how `setFee` in `IdleTokenFungible.sol` calls `_updateFeeInfo()` before changing the fee. Note the accrued-gain checkpoint also fixes the `minAprSplitAYS` → `_updateSplitRatio` path.

### Proof of Concept

Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testRetroactiveSplitRatio() external {
    // AA and BB both funded; epoch running with fixed APR
    idleCDO.depositAA(10_000 * ONE_SCALE);
    idleCDO.depositBB(10_000 * ONE_SCALE);

    // accrue interest: warp into a running epoch / bump strategy value so
    // getContractValue() > lastNAVAA + lastNAVBB (pending gain G)
    vm.warp(cdoEpoch.epochEndDate());
    // simulate borrower repayment into the vault so nav grows by G

    uint256 oldSplit = cdoEpoch.trancheAPRSplitRatio();

    // owner raises AA split (or toggles AYS / changes minAprSplitAYS)
    vm.prank(owner);
    cdoEpoch.setTrancheAPRSplitRatio(oldSplit + 20_000); // +20%

    // next interaction crystallizes pending G under the NEW ratio
    vm.prank(owner);
    cdoEpoch.updateAccounting();

    // BB NAV increased by G * (1 - (oldSplit+20%)) instead of G * (1 - oldSplit):
    // BB holders lost G * 20% of accrued yield to AA holders.
}
```

Same shape for `setFeeParams`: deposit, let `nav - lastNAV` grow, then `setFeeParams` raising `fee`; the subsequent `updateAccounting` charges the new fee on the whole accrued gain, not just post-change gains.
