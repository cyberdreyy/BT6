### Title
Dust APR0 withdraw request permanently gates `stopEpoch` behind `prepareStopEpochWithApr0` revert after any APR change - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
An unprivileged lender can freeze the epoch state machine by opening a dust `requestWithdraw` while `unscaledApr == 0`. Once `apr0TotalPrincipal > 0`, `prepareStopEpochWithApr0` hard-reverts if the honest manager/borrower ever sets a non-zero APR, so every subsequent `stopEpoch` reverts until APR is restored to 0 — a hang of the vault's core settlement function matching the CVE-2020-14769 "easily exploitable → hang/crash (DoS)" bug class.

### Finding Description
- `requestWithdraw` mints an APR0 receipt whenever `unscaledApr == 0`, with no minimum amount, and routes into `_requestWithdrawApr0`, which increments the global `apr0TotalPrincipal` bucket.
- At `stopEpoch`, `IdleCDOEpochVariant` calls `prepareStopEpochWithApr0`, which reverts whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` (`IdleCreditVault.sol:502-508`).
- Attack sequence (running APR0 epoch): attacker deposits dust via `depositAA`, calls `requestWithdraw` for 1 wei → `apr0TotalPrincipal = 1`. Later, the honest borrower/manager sets a positive APR for the next epoch (a normal business operation via `setAprsWithBuffer`). From that point every `stopEpoch` call reverts with `NotAllowed`, so the current epoch can never be stopped, `epochNumber` never advances, and all pending withdraw claims (gated on `epochNumber > lastWithdrawRequest` at `IdleCreditVault.sol:326`) are frozen.

### Impact Explanation
Temporary freezing of all vault funds: no lender can claim withdraws, no new epoch can start, and borrower repayment via `stopEpoch` is blocked. Impact scales with full pool TVL for the duration of the freeze. Unwinding requires the manager to diagnose the grief and set APR back to 0, which may not be economically possible mid-epoch if a new rate was already committed to the borrower.

### Likelihood Explanation
Cost to the attacker is 1 wei plus gas; trigger condition is a routine APR change by honest privileged roles — exactly the allowed "sequence around their calls" model. The guard is intentional (APR0 principal must settle under the rate it was booked), but it converts a dust receipt into a veto over the state machine, which is the DoS analog.

### Recommendation
In `prepareStopEpochWithApr0`, settle the APR0 bucket using the stored `apr0RateByEpoch` rate for the request epoch instead of reverting when `unscaledApr` changed, or gate `_requestWithdrawApr0` on the epoch's booked rate rather than the mutable `unscaledApr`, so a post-request APR change cannot brick `stopEpoch`.

### Proof of Concept
Foundry fork PoC (against `IdleCreditVault.t.sol` harness):
```solidity
// APR0 epoch running
address attacker = makeAddr('attacker');
_depositWithUser(attacker, 1); // dust deposit
vm.prank(attacker);
cdoEpoch.requestWithdraw(0, address(AAtranche)); // apr0TotalPrincipal = 1 wei

// honest manager sets APR for next epoch
vm.prank(manager);
strategy.setAprsWithBuffer(5e18, epochDuration, buffer);

// borrower funded, epoch end reached
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpoch(0, 0); // permanently reverts while apr0TotalPrincipal != 0
```
