### Title
`storeOnFetch` decided per-`singleflight`-flight rather than per-caller allows a `Store=false` requester's response to be cached and served to other callers - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
`(rc *responseCache) Fetch` uses `singleflight.Group.Do` keyed only by `req.Hash()` and decides whether to persist the fetched response using the `storeOnFetch` boolean captured from whichever goroutine's closure happens to execute the shared `fetchFn`, not from each individual caller's own `CacheSettings.Store`. When two concurrent `OutboundHTTPRequest`s hash to the same key but disagree on `CacheSettings.Store`, only one caller's `storeOnFetch` value is honored for both, so a request that opted out of caching can still get cached (or vice versa) depending purely on scheduling order.

### Finding Description
`Fetch` is called from `makeOutgoingRequest` in `core/services/gateway/handlers/capabilities/v2/http_handler.go` at line 435: `h.responseCache.Fetch(httpCtx, req, callback, req.CacheSettings.Store)`, whenever `req.CacheSettings.MaxAgeMs > 0`. `req` is fully attacker/node-controlled JSON-RPC parameters coming from a workflow node's `OutboundHTTPRequest` (`core/services/gateway/handlers/capabilities/v2/http_handler.go` lines 403-441).

Inside `Fetch` (`core/services/gateway/handlers/capabilities/v2/response_cache.go` lines 66-108), the cache key is `req.Hash()` (line 67) and the call goes through `rc.flight.Do(cacheKey, func() (any, error) {...})` (line 83). `singleflight.Group.Do` guarantees only **one** of the concurrently-arriving closures actually executes for a given key; all other concurrent callers with the same key block and receive the same result from that single execution. However, `storeOnFetch` (line 95: `if storeOnFetch && isCacheableStatusCode(response.StatusCode)`) is a closure variable bound to whichever caller's goroutine happened to be the one selected by singleflight to run the callback — it is not the logical union/intersection of all concurrent callers' intents. Because `storeOnFetch` is captured per-goroutine but only one goroutine's callback body actually executes, the *other* concurrent caller's `storeOnFetch` preference is silently discarded regardless of what it was.

Concretely: caller A issues a request with `CacheSettings.Store=false` (meaning "do not persist this response") and caller B concurrently issues a request that hashes to the identical `req.Hash()` (same method/URL/headers/body/workflowOwner) with `CacheSettings.Store=true`. If singleflight happens to select **A's** goroutine to actually run `flight.Do`'s function body, then `storeOnFetch=false` is used, and B's request result is silently not cached even though B asked for it. Conversely, if singleflight selects **B's** goroutine to run the shared closure, then `storeOnFetch=true` is used, and the shared response is persisted — but this response is stored and returned as A's result too (since singleflight returns the same result to every waiter), and it becomes available in the cache for any *third*, unrelated caller with `MaxAgeMs>0` and the same hash, which will get a cache hit at the fast path (lines 71-77) and receive a response that was tied to a request that explicitly declared `Store=false`.

No component validates or reconciles `Store` flags across concurrent same-key requests; `req.Hash()` does not need to (and apparently does not) factor in `CacheSettings.Store`, so requests differing only by that flag collide into the same singleflight/cache entry. The comment in the code itself acknowledges the callback runs "only one fetchFn... per key" but does not address that `storeOnFetch` is caller-specific state being applied globally to all colliding callers.

### Impact Explanation
This is a cross-request/cross-user response confusion and unintended persistence issue: a response explicitly marked non-cacheable (`Store=false`, e.g., because it may contain per-caller sensitive data returned from an external endpoint, or was intended to be short-lived/private) can end up stored in the shared `responseCache` and later served via the fast-path cache hit (lines 74-77) to any other node/workflow request that shares the same `Hash()` and sets `MaxAgeMs>0`. This matches the "cross-user response confusion" bounty impact class — unintended disclosure of response data across workflow/caller boundaries within the gateway's HTTP action capability. Because `Hash()` is based on request fields (method/URL/headers/body/workflowOwner per the doc comment on `responseCache`), practical exploitation requires the colliding requests to share the same `workflowOwner`-scoped hash, which somewhat limits blast radius to callers under the same owner, but it still breaks the intended "the caller controls whether *this* response gets persisted" invariant.

### Likelihood Explanation
Preconditions: an attacker (or race condition between the attacker's own workflow's concurrent action steps, or via the gateway between concurrently retried workflow executions) needs to trigger two `OutboundHTTPRequest`s that hash identically (`req.Hash()` — same method/URL/headers/body/workflowOwner) but set different `CacheSettings.Store` values, arriving close enough in time to race inside `singleflight.Group.Do`. This requires only the privileges already available to a workflow node/DON member issuing `HTTPAction` outbound requests through the gateway (no operator/admin access needed) — an unprivileged attacker who can cause two concurrent identical outbound HTTP actions with differing `Store` settings (e.g., by running a workflow twice concurrently, or if two different workflow steps share owner and hash inputs) can trigger this. The race window is narrow (only affects requests that collide within the same in-flight window) but is fully reproducible under a race-detector test with controlled goroutine scheduling, and does not depend on network timing outside the gateway process.

### Recommendation
Do not treat `storeOnFetch` as a value derived from whichever goroutine wins the singleflight race. Instead:
- Track `storeOnFetch` intent per-request outside the shared closure, e.g. by having each caller register its own `Store` flag before/after `flight.Do` returns, and independently call `rc.Set(req, response)` for its own value of `CacheSettings.Store` after obtaining `response` from `Do`, mirroring the non-cache-lookup branch in `makeOutgoingRequest` (lines 436-440) that already calls `h.responseCache.Set` directly.
- Alternatively, only cache automatically inside `Fetch` when *all* concurrently-waiting callers for that key set `Store=true`, e.g., by aggregating callers' `storeOnFetch` values that arrived for the in-flight key (requires additional per-key state, e.g., a `sync.Map` of pending store flags) and requiring unanimity, or simpler: never store inside the singleflight closure, and instead let each caller unconditionally decide storage after `Do` returns based on its own `storeOnFetch`, using `isExpiredOrNotCached`/`Set` guarded by `cacheMu` (same as the `Set` method already does), so a `Store=false` caller can never contribute to writing the cache even if it happens to be the "winning" closure.

### Proof of Concept
Go test in `core/services/gateway/handlers/capabilities/v2/response_cache_test.go` (new test, run with `-race`):
1. Construct a `responseCache` via `newResponseCache` with a metrics stub and TTL long enough to observe.
2. Build two `gateway.OutboundHTTPRequest` values, `reqA` and `reqB`, that produce the identical `Hash()` (same method/URL/headers/body/workflowOwner) but `reqA.CacheSettings.Store = false` and `reqB.CacheSettings.Store = true`, both with `MaxAgeMs` set (or test independent of MaxAgeMs since `Fetch` is invoked directly).
3. Use a synchronization gate (e.g., a channel or `sync.WaitGroup` plus a short `time.Sleep`/`runtime.Gosched()`) inside a shared `fetchFn` to force both `Fetch(ctx, reqA, fetchFn, false)` and `Fetch(ctx, reqB, fetchFn, true)` to be launched concurrently in separate goroutines so they race into `rc.flight.Do(cacheKey, ...)`.
4. Repeat the race many iterations (e.g., 100+) under `go test -race`, and after each pair completes, assert: cache is populated (`rc.cache[cacheKey]` non-nil) **only if** the actual winning goroutine's `storeOnFetch` argument was `true`; specifically assert failure cases where the goroutine invoked with `storeOnFetch=false` (reqA) is the one selected to run the closure yet the cache still becomes populated because `reqB` (Store=true) was blocked on the same flight and its intended persistence overrides/ignores A's opt-out and vice versa.
5. Add a third, independent `Fetch` call (`reqC`, unrelated caller, `MaxAgeMs>0`, `Store=false`, same hash) shortly after and assert whether it receives a cache hit populated by the response tied to `reqA` (`Store=false`) — demonstrating that an opted-out response became retrievable by an unrelated caller.
6. Expected (failing) assertion demonstrating the bug: there exists a race outcome where `reqA` (`Store=false`) is the closure that executes and `storeOnFetch=false` was passed only for that goroutine, yet since singleflight only runs one function body per key, the concurrently-blocked `reqB`'s intended `Store=true` is discarded/ignored — proving `storeOnFetch` decisions are singleflight-execution-order dependent rather than per-caller-honored, and that whichever value happens to win can end up persisted and served to `reqC`.
