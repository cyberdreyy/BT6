### Title
User enumeration via distinguishable content and timing in `CreateSession`/`BeginWebAuthnLogin` login flow - (File: core/sessions/localauth/orm.go)

### Summary
The login flow in `(*orm).CreateSession` performs an early-return `FindUser` lookup before any constant-time or password-hash comparison, and propagates the raw SQL "no rows" error directly to the HTTP client, while a known email with a wrong password instead reaches the `bcrypt`-based `utils.CheckPasswordHash` path and returns a different literal error string ("Invalid password"). This lets an unauthenticated client distinguish unknown from known accounts by response content and by timing (bcrypt verification is expensive, the early DB-miss path is not), before any WebAuthn/MFA challenge is even generated.

### Finding Description
`SessionsController.Create` (`core/web/sessions_controller.go:29-68`) binds the JSON request and calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`, forwarding any resulting error verbatim as the HTTP 401 body: [1](#0-0) .

Inside `(*orm).CreateSession` (`core/sessions/localauth/orm.go`):
1. `user, err := o.FindUser(ctx, sr.Email)` is called first; if the email does not exist in the `users` table, this returns immediately with the raw SQL error (`sql.ErrNoRows`/pgx "no rows in result set") before any password check, MFA lookup, or constant-time comparison occurs: [2](#0-1) .
2. Only for a *found* user does the code proceed to `constantTimeEmailCompare` and then `utils.CheckPasswordHash(sr.Password, ...)`, returning the distinct string "Invalid password" on mismatch: [3](#0-2) .
3. WebAuthn/MFA challenge generation via `sessions.BeginWebAuthnLogin` (`core/sessions/webauthn.go:103-131`) is only reached for known accounts that passed the password check and have registered WebAuthn credentials, further downstream of the FindUser branch: [4](#0-3) .

Because the unknown-account path short-circuits before the (comparatively slow) `bcrypt.CompareHashAndPassword` call performed inside `utils.CheckPasswordHash`, and because the error text differs ("no rows..." vs "Invalid password" vs "MFA Error"), an unauthenticated attacker sending POST /sessions requests can:
- Distinguish unknown accounts (fast response, distinctive DB error text) from existing accounts (slower response due to bcrypt, "Invalid password"/"MFA Error" text).
- Use this oracle to enumerate valid operator emails, which is a prerequisite for credential-stuffing/targeted-password/targeted-WebAuthn attacks against real accounts.

Note that `constantTimeEmailCompare` in `core/sessions/localauth/orm.go:234-241` mitigates timing differences *within* the "user found" branch (comparing `sr.Email` vs `user.Email`), but does nothing for the FindUser-not-found branch, which is the actual enumeration oracle.

### Impact Explanation
This does not by itself grant admin control of the node; it is a reconnaissance/enumeration primitive that narrows the attack surface for downstream credential or WebAuthn-registration-forgery attacks. Per the question framing (Immunefi bounty class: "Critical - node takeover"), this specific finding only supports the *first stage* of such an attack (account discovery), not privilege escalation itself. The response/timing oracle is real and exploitable to build a list of valid operator emails, which increases attacker efficiency in credential attacks and phishing but does not directly bypass authentication or authorization on its own.

### Likelihood Explanation
Trivial precondition: any unauthenticated HTTP client that can reach POST /sessions. No credentials, roles, or prior access required. The oracle is deterministic and repeatable: the error text differs unconditionally between missing-email and wrong-password cases, and there is a measurable timing gap due to the absent bcrypt computation for missing users. This is straightforward to script and requires no race conditions or timing sophistication beyond simple statistical averaging.

### Recommendation
- In `(*orm).CreateSession`, when `FindUser` returns not-found, do not return early. Instead run a dummy/constant-cost `bcrypt` comparison against a fixed dummy hash (to normalize timing) and return the exact same generic error message/format used for a real "wrong password" case (e.g., always "invalid credentials"), regardless of whether the email exists.
- Ensure `sessions_controller.go`'s `Create` handler surfaces a single generic message and HTTP status (401) for all authentication failures (unknown email, wrong password, failed MFA), never propagating the underlying error string from the ORM layer.
- Apply the same normalization to any WebAuthn registration/BeginWebAuthnLogin failure paths so that they don't leak whether a given email has 2FA enabled versus not existing at all.

### Proof of Concept
Table-driven handler test in `core/web/sessions_controller_test.go` style:
1. Seed one known user with a password and one without WebAuthn.
2. Send POST /sessions with:
   - Case A: unknown email + arbitrary password.
   - Case B: known email + wrong password.
3. Assert:
   - Response bodies differ (`"no rows in result set"`-derived vs `"Invalid password"`) — demonstrates content-based enumeration.
   - Measure wall-clock time for many repeated requests to Case A vs Case B; assert Case B's mean latency (bcrypt cost) is statistically distinguishable (e.g., >5x) from Case A's mean latency — demonstrates timing-based enumeration.
4. Expected (vulnerable) result: both content and timing differ, confirming the finding. After the fix, both content and timing should converge to identical generic failure responses.
