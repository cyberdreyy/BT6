### Title
Confirmations from removed multisig members remain counted toward the K-of-N execution threshold - (File: `multisig2/src/lib.rs`)

### Summary
`DeleteMember` (multisig2) and `DeleteKey` (multisig) only purge confirmations/requests that a removed member *originated*, not confirmations that removed member cast on other members' still-pending requests. A revoked member's stale confirmation therefore continues to count toward `num_confirmations` when the request is later executed, letting a request execute with fewer live/authorized confirmers than the configured threshold.

### Finding Description
The multisig's core guarantee is: a request executes only once `K` (i.e. `num_confirmations`) of the *currently authorized* `N` members have confirmed it — an equality of "confirmations counted == live-member confirmations." `confirm()` in `multisig2/src/lib.rs` simply grows a `HashSet<String>` of member identifiers for a request and executes once `confirmations.len() + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member()`, which is what actually removes a member from `self.members` (and, if key-based, deletes their access key), only scrubs requests/confirmations for requests that member *originated* (`r.member == member`, i.e., the request creator field, not confirmer): [2](#0-1) 

It never iterates `self.confirmations` to strip the departing member's entries from *other* members' pending requests that they had merely confirmed. The equivalent logic exists in the legacy `multisig/src/lib.rs`, where `DeleteKey` purges only requests whose `signer_pk == pk` (the request's own creator key), leaving stale confirmations by that key on other requests intact: [3](#0-2) 

There is also no live-membership check inside `confirm()`/`execute_request()` at execution time — the code trusts the raw count of strings/keys in the `confirmations` set, without verifying each entry still belongs to `self.members`.

### Impact Explanation
This breaks the multisig's fundamental authorization guarantee: `num_confirmations` is meant to represent K distinct, currently-trusted signers, but a stale confirmation from an already-removed member is indistinguishable from a live one and is counted toward reaching the threshold. This can let a request (e.g., `Transfer`, `AddKey`/`AddFullAccessKey`, `FunctionCall`, `DeployContract`) execute with effectively fewer authorized confirmations than K, i.e. "a multisig request executed below threshold" — a Critical-severity impact per the given classification. Since the multisig commonly custodies NEAR balances and controls contract upgrade/access-key rights, this is an authorization boundary crossed by an already-revoked party's leftover vote, not merely a griefing or DoS issue.

### Likelihood Explanation
Reachability is straightforward and requires no privileged deployment deviation: any legitimate operational sequence where (1) member A confirms a pending request R created by member B, (2) the group later executes a separate `DeleteMember`/`DeleteKey` request removing A (for routine key-rotation, compromise response, etc.), and (3) a live member later confirms R, triggers the bug — the stale confirmation from A is still counted, and R can execute even though only one *currently authorized* member (the last confirmer) actually approved it at that point along with a revoked one. No malicious deployment or foundation/owner deviation is needed; it's a straightforward operational gotcha reachable by any set of members through the contract's own confirm/delete flow.

### Recommendation
When removing a member (`delete_member` in multisig2, or processing `DeleteKey` in multisig), iterate all pending requests' confirmation sets and remove the departing member's/key's entry wherever present (not just requests they originated). Alternatively, validate at `confirm()`/execution time that every entry in the stored `confirmations` set still corresponds to a member present in `self.members`, discarding stale entries before comparing the count against `num_confirmations`.

### Proof of Concept
1. Deploy multisig2 with `num_confirmations = 2`, `members = [A, B, C]`.
2. Member B calls `add_request_and_confirm(R)` — `R`'s confirmations = `{B}` (1/2).
3. Members create and confirm a separate request `D` = `DeleteMember { member: A }` with 2 confirmations (e.g. B and C), which executes `delete_member(A)`. Because `D.member == A` matches only requests *created* by A (none here), and `R` was created by B, `R`'s confirmation set is untouched; A's key/entry is removed from `self.members` and its access key deleted, but A never confirmed `R` in this scenario — the point is that if instead A had confirmed `R` first (step 2 replaced by A calling `confirm(R)`), A's confirmation entry `{A}` on `R` would survive the deletion of A as a member.
4. Now with corrected order: A confirms `R` first (`confirmations = {A}`), then `D = DeleteMember{A}` executes (removing A from `members`, but not touching `R`'s confirmations because `R.member == B ≠ A`).
5. Member B (or C) now calls `confirm(R)`. `confirmations.len() + 1 = 2 >= num_confirmations (2)` → `execute_request(R)` runs, even though A is no longer a member — R executed with only 1 currently-authorized confirmation (B) plus one stale, revoked confirmation (A), violating the 2-of-N live-member guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
