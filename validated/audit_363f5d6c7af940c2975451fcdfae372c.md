### Title
Already-funded instant-withdraw receipts are swept into `defaultRecoveryReserve` but can never be claimed, permanently freezing claimants' funds while inflating the recovery price for others — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external report's bug class is a claim state-machine that fails to record "funds already moved" before reverting a request to a claimable/payable state, enabling double-spend or loss of record. The closest credit-vault analog is in `IdleCreditVault.finalizeDefaultRecovery` / `claimInstantWithdrawRequest`: when a default is finalized while current-epoch instant-withdraw receipts are fully prefunded (`pendingInstantWithdraws == 0` but `instantWithdrawClaimsByEpoch[epochNumber] != 0`), the strategy sweeps the prefunded backing into `defaultRecoveryReserve` via `_defaultPrefundedInstantReserve`, yet sets `defaultInstantWithdrawsFinalized = false`. That flag makes `claimInstantWithdrawRequest` route those receipts through `_transferFundedClaim`, which is explicitly forbidden from spending the reserve — so the claim reverts forever, while the swept funds inflate `defaultRecoveryPrice` and are paid out to other claimants.

### Finding Description

At finalization, `finalizeDefaultRecovery` computes `prefundedReserve = _defaultPrefundedInstantReserve()` and adds it to `reserveAmount`, which becomes `defaultRecoveryReserve` and the numerator of `defaultRecoveryPrice` (`reserveAmount * RECOVERY_FULL / totalBasis`). `defaultPendingClaimBasis()` only includes the instant claim basis when `pendingInstantWithdraws != 0`, so when the instant queue was already fully funded by `collectInstantWithdrawFunds` (pending drained to zero, underlyings sitting in the strategy, users not yet claimed), the instant claimants' backing is counted in the reserve but their claim basis is excluded from `totalBasis` — the reserve is double-counted: it simultaneously backs (a) the instant receipts and (b) the inflated `defaultRecoveryPrice` paid to everyone else. [1](#0-0) [2](#0-1) [3](#0-2) 

The claim path then strands those receipts. With `defaultInstantWithdrawsFinalized == false`, `claimInstantWithdrawRequest` skips `_claimDefaultedInstantWithdrawRequest` and calls `_transferFundedClaim`, which reverts whenever `balance - defaultRecoveryReserve < amount`. Since the prefunded instant backing was folded into `defaultRecoveryReserve` and the recovered amount was also added to the same reserve, `balance` equals `reserve` (plus at most dust), so the funded-claim guard reverts on every call. There is no other path that pays these receipts: `_transferDefaultRecovery` is only reached via the skipped defaulted-instant branch. [4](#0-3) [5](#0-4) 

This is exactly the "claim_tx_hash written but row reverted to pending" shape: the strategy records "the transfer already happened" only as an untouchable reserve credit (`prefundedReserve`) rather than as a claimable credit, so the money is spent twice in accounting — once to other recovery claimants through the inflated `defaultRecoveryPrice`, and once notionally to the instant claimants who can never withdraw it.

### Impact Explanation

Two harms, both requiring only honest privileged sequencing plus one unlucky unprivileged claimant:

1. **Permanent freeze of unclaimed instant receipts.** Any user whose instant-withdraw request was funded via `collectInstantWithdrawFunds` but not yet claimed when the borrower defaults has their full claim permanently bricked — `_transferFundedClaim` always reverts, and no recovery-ratio path is available because `defaultInstantWithdrawsFinalized` is false. Loss = the user's full prefunded instant claim amount.
2. **Theft-by-misallocation.** The frozen backing is not idle — it was folded into `reserveAmount`, raising `defaultRecoveryPrice` for all defaulted normal/APR0 claimants and active tranche holders. Other unprivileged claimants (an attacker who also holds a defaulted withdraw receipt) are paid above their fair pro-rata share out of the instant claimants' funds. The invariant "one receipt, one payout; reserve is isolated per claimant class" is broken.

### Likelihood Explanation

The trigger requires a specific but unremarkable sequence in a single epoch: instant withdrawals enabled → user requests instant withdraw → CDO calls `collectInstantWithdrawFunds` (funding it, draining `pendingInstantWithdraws` to 0) → user does not claim before the borrower defaults and `finalizeDefaultRecovery` runs. Claim-before-finalization is exactly what a normal user does *not* rush to do; the window is the entire period between funding and default finalization, which includes the honest-manager-driven `finalizeDefault`/`finalizeDefaultRecovery` governance process. No attacker timing, reentrancy, or privileged misbehavior is needed — any unprivileged instant-withdrawer in that window is frozen, and any unprivileged defaulted claimant benefits from the overpayment. The partially-prefunded variant (0 < `pendingInstantWithdraws` < `instantBasis`) is handled correctly because `defaultInstantWithdrawsFinalized` becomes true and `_claimDefaultedInstantWithdrawRequest` pays the claimBasis at the recovery ratio; only the fully-prefunded edge case is broken, which caps likelihood below High.

### Recommendation

Track prefunded instant claims as their own claimable bucket instead of folding them into the shared reserve:

1. In `finalizeDefaultRecovery`, when `pendingInstantWithdraws == 0` and `instantWithdrawClaimsByEpoch[epochNumber] != 0`, record a separate `prefundedInstantReserve` (or set `defaultInstantWithdrawsFinalized` semantics so these receipts claim at `RECOVERY_FULL`, i.e., 1:1, via `_transferDefaultRecovery`), and exclude that amount from `reserveAmount` used for `defaultRecoveryPrice`. These claimants were already fully funded — they should be paid at par, not contribute their backing to the recovery pool.
2. Alternatively, keep them in `totalBasis` and treat their recovery ratio as 1:1: add `instantBasis` to `pendingBasis` in `defaultPendingClaimBasis` when prefunded, and let `claimInstantWithdrawRequest` route them through `_claimDefaultedInstantWithdrawRequest` with a per-epoch stored price. This mirrors the report's recommended `claimed_unconfirmed` intermediate state: "funded but unclaimed" must be a distinct, payable state — never collapsible into the general reserve and never routed through the funded-claim path that refuses to touch the reserve.
3. Add a post-finalization invariant check or test: `underlyingToken.balanceOf(this) - defaultRecoveryReserve` must cover all claims routed through `_transferFundedClaim` (old funded receipts), and every unit counted in `defaultRecoveryReserve` must have a payable claimant.

### Proof of Concept

```solidity
// 1. Deposit AA, run epoch 0 normally.
uint256 mintedAA = idleCDO.depositAA(amountWei);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, apr, expectedFunds);

// 2. Epoch 1 running, instant withdraws enabled: user requests instant withdraw.
cdoEpoch.setInstantWithdrawParams(delay, 1e18, false); // manager
uint256 req = cdoEpoch.requestInstantWithdraw(mintedAA / 2, user);

// 3. CDO funds the instant request: collectInstantWithdrawFunds pulls underlying
//    to the strategy; pendingInstantWithdraws -> 0, instantWithdrawClaimsByEpoch[epoch] = req.
_getInstantFunds(); // warps past delay, calls getInstantWithdrawFunds -> collectInstantWithdrawFunds
assertEq(strategy.pendingInstantWithdraws(), 0);
assertGt(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), 0);
// user does NOT claim yet.

// 4. Borrower defaults; manager finalizes:
cdoEpoch._handleBorrowerDefault(...);              // honest manager path
strategy.finalizeDefaultRecovery(recovered, source); // via CDO
// _defaultPrefundedInstantReserve() = instantBasis - 0 = req
// defaultRecoveryReserve includes req; defaultInstantWithdrawsFinalized = false.

// 5a. User claim permanently reverts:
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimInstantWithdrawRequest(); // _transferFundedClaim: balance - reserve < req

// 5b. Inflation check: recoveryPrice > fair share because req was in reserveAmount
//     but instant basis was excluded from totalBasis:
assertGt(strategy.defaultRecoveryPrice(), reserveWithoutInstant * RECOVERY_FULL / totalBasis);
// A defaulted-receipt claimant (attacker) claims and receives more than pro-rata.
```

  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
    if (pendingInstant == 0) return prefundedReserve;
    uint256 instantBasis = instantWithdrawClaimsByEpoch[epochNumber];
    if (instantBasis > pendingInstant) {
      prefundedReserve = instantBasis - pendingInstant;
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
