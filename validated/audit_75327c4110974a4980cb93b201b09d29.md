### Title
`get_globally_accepted_block_count_in_tenure` miscounts globally-accepted blocks via `MAX-MIN+1` instead of `COUNT(*)`, corrupting `check_parent_tenure_choice`'s reorg-permission gate - ([File: stacks-signer/src/signerdb.rs])

### Summary
`SignerDb::get_globally_accepted_block_count_in_tenure` computes the number of globally-accepted blocks in a tenure with `MAX(stacks_height) - MIN(stacks_height) + 1` rather than `COUNT(*)`. This formula silently assumes every stacks height between the tenure's lowest and highest tracked `GloballyAccepted` block is present in the local signer DB. When the local record set for that tenure is non-contiguous (a routine occurrence — see below), the formula overstates the true number of known globally-accepted blocks. This value directly feeds the reorg-admission check `check_parent_tenure_choice`, which refuses a reorg outright whenever it computes more than one globally-accepted block in a reorged tenure. An inflated count can therefore cause a signer to refuse a legitimate/valid reorg it should have permitted.

`MAX-MIN+1` equals the *count* of distinct heights present only if the set of recorded `GloballyAccepted` heights for that tenure is contiguous. It is not required to be contiguous:
- A signer that starts tracking a tenure mid-stream (joined late, restarted, or was down) will only have DB rows for the blocks it actually processed in that tenure. `check_latest_block_in_tenure` will opportunistically mark the node's *current tip* block as `GloballyAccepted` even if the signer never saw/processed the tenure's earlier blocks: [3](#0-2) 
- Once a block reaches `BlockState::GloballyAccepted` the state machine documents this state as terminal (`GloballyAccepted --> [*]`), so gaps caused by never having a local record for intermediate heights are never “backfilled”.
- `get_globally_accepted_block_count_in_tenure`'s own unit test only exercises the *contiguous* case (heights 2 and 3), so the discontiguous case is untested: [4](#0-3) 

Because `MAX-MIN+1` is always ≥ the true number of tracked rows (never less), the bug is one-directional: it can only **inflate** the reorg-refusing verdict, never mask a real multi-block tenure.

### Impact Explanation
`check_parent_tenure_choice` is the sole authority (per-signer) for deciding whether a miner's chosen parent tenure represents a permitted reorg: [5](#0-4) 

If the count is over-reported for a tenure that legitimately has ≤1 globally-accepted block (e.g. a signer only has one stale DB record from a tip check plus a later opportunistic tip-mark at a much higher height, or simply gapped records from downtime), `check_parent_tenure_choice` will return `Ok(false)` and the tenure-change block will be rejected with `RejectReason::ReorgNotAllowed`: [6](#0-5) 

If enough signers (or all of them) have inconsistent/gapped local block histories for the reorged tenure — plausible after any restart, resync, or period offline — they can each independently and legitimately refuse a valid tenure-change proposal that the protocol would otherwise permit, stalling block production on that fork until the operators intervene or the affected tenure ages out of `MAX_FORK_DEPTH`. This matches the "signer wedged into never signing valid blocks" / liveness-wedge class from the rules, though the wedge is scoped to the specific tenure-reorg decision rather than the whole signer, and is self-correcting once the offending tenure record ages past `MAX_FORK_DEPTH` (pruned by `prune_superseded_tenures`).

Note: I could not find any code path where this bug directly causes a signer to sign an invalid/non-canonical block (i.e., no "critical" over-count-to-under-count reversal), because the formula only ever over-counts, which is conservative. The concrete guaranteed effect is spurious rejection of otherwise-valid reorgs (liveness), not signing something unsafe (safety).

### Likelihood Explanation
Reaching a gapped record set requires no majority collusion and no privileged access — an ordinary node restart, resync, late-join, or brief signer downtime mid-tenure is sufficient to leave the local `blocks` table with non-contiguous `GloballyAccepted` heights for a tenure. Any subsequent proposal that reorgs off of/away-from such a tenure will trip this miscount deterministically once triggered (it is a pure SQL aggregate over already-owned data, no attacker input needed).

### Recommendation
Change the query to use `COUNT(*)` (or `COUNT(DISTINCT stacks_height)`) instead of `MAX(stacks_height) - MIN(stacks_height) + 1`:

```sql
SELECT COUNT(*) FROM blocks WHERE consensus_hash = ?1 AND state = ?2
```

Add a regression test that inserts non-contiguous `GloballyAccepted` heights for a tenure (e.g. heights 2 and 10 only) and asserts the returned count is `2`, not `9`.

### Proof of Concept
1. In a `SignerDb`, insert a block at `stacks_height = 2` for `consensus_hash = tenure_x` with `state = GloballyAccepted` (representing the one block this signer happened to process/observe for the tenure).
2. Simulate `check_latest_block_in_tenure` later opportunistically marking the node's current tip for that same tenure — e.g. `stacks_height = 20` — as `GloballyAccepted` as well (per [3](#0-2) ), without any intermediate heights ever being locally recorded.
3. Call `get_globally_accepted_block_count_in_tenure(&tenure_x)`. It returns `20 - 2 + 1 = 19`, though only 2 rows actually exist.
4. Call `check_parent_tenure_choice` for a miner proposing to reorg away from `tenure_x` under conditions that should otherwise be permitted (e.g. `tenure_x`'s only real block was poorly timed near the sortition boundary). Because `globally_accepted_blocks (19) > 1`, the function returns `Ok(false)` and the reorg is refused via `RejectReason::ReorgNotAllowed`, even though the tenure genuinely had at most one (or even zero, depending on record provenance) accepted block that should count against the rule.

I was unable to fully trace every real-world path that produces non-contiguous local records (this requires deeper knowledge of exact insertion timing across the `stacks_client` tip-mark code and restart bootstrapping, which the index does not fully expose); the analysis above is based on the documented terminal-state guarantee and the tip-marking code shown, both directly cited.

    pub fn check_parent_tenure_choice(
        &self,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        first_proposal_burn_block_timing: &Duration,
    ) -> Result<bool, SignerChainstateError> {
        // if the parent tenure is the last sortition, it is a valid choice.
        // if the parent tenure is a reorg, then all of the reorged sortitions
        //  must either have produced zero blocks _or_ produced their first (and only) block
        //  very close to the burn block transition.
        if self.prior_sortition == self.parent_tenure_id {
            return Ok(true);
        }
        info!(
            "Most recent miner's tenure does not build off the prior sortition, checking if this is valid behavior";
            "sortition_state.consensus_hash" => %self.consensus_hash,
            "sortition_state.prior_sortition" => %self.prior_sortition,
            "sortition_state.parent_tenure_id" => %self.parent_tenure_id,
        );

        let tenures_reorged =
            client.get_tenure_forking_info(&self.parent_tenure_id, &self.prior_sortition)?;
        if tenures_reorged.is_empty() {
            warn!("Miner is not building off of most recent tenure, but stacks node was unable to return information about the relevant sortitions. Marking miner invalid.");
            return Ok(false);
        }

        // this value *should* always be some, but try to do the best we can if it isn't
        let sortition_state_received_time =
            signer_db.get_burn_block_receive_time(&self.burn_block_hash)?;

        // Track which tenures are superseded by the reorg, then mark them in
        // the DB after the reorg is permitted.
        let mut superseded_tenures = Vec::new();
        for tenure in tenures_reorged.iter() {
            if tenure.consensus_hash == self.parent_tenure_id {
                // this was a built-upon tenure, no need to check this tenure as part of the reorg.
                continue;
            }

            // disallow reorg if more than one block has already been signed
            let globally_accepted_blocks =
                signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash)?;
            if globally_accepted_blocks > 1 {
                warn!(
                    "Miner is not building off of most recent tenure, but a tenure they attempted to reorg has already more than one globally accepted block.";
                    "parent_tenure" => %self.parent_tenure_id,
                    "last_sortition" => %self.prior_sortition,
                    "violating_tenure_id" => %tenure.consensus_hash,
                    "violating_tenure_first_block_id" => ?tenure.first_block_mined,
                    "globally_accepted_blocks" => globally_accepted_blocks,
                );
                return Ok(false);
            }
