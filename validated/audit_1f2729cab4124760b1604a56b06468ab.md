## Title
`createDstEscrow` accepts caller-supplied `Timelocks` with no minimum/ordering validation, letting the funding party (taker) collapse the destination withdrawal window and grief the maker's already-locked source funds - ([File: contracts/BaseEscrowFactory.sol])

## Summary
The GoGoPool finding shows that when a duration-like parameter used to gate a later time-based state transition is accepted from an unprivileged caller without bounds/consistency checks, that caller can pick a degenerate value that defeats the parameter's purpose (there: minimizing a slashing window; here: minimizing a withdrawal window). The same root cause exists in `BaseEscrowFactory.createDstEscrow`, which accepts a fully caller-controlled `Timelocks` value with only a single, partial check.

## Finding Description
`createDstEscrow` takes `dstImmutables` entirely from `msg.sender` (the taker funding the destination leg) and only validates one relationship: [1](#0-0) 

```solidity
function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
    ...
    immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
    // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
    if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();
    ...
}
```

Only `Stage.DstCancellation` is bounded against `srcCancellationTimestamp` (itself also a caller-supplied argument). There is **no check** that:
- `Stage.DstWithdrawal < Stage.DstPublicWithdrawal < Stage.DstCancellation` (correct ordering), or
- `Stage.DstWithdrawal` has any minimum duration from `deployedAt`.

`Timelocks` is a single packed `uint256` with per-stage `uint32` offsets from `deployedAt`, entirely defined by the caller of `createDstEscrow`: [2](#0-1) 

`EscrowDst.withdraw`/`publicWithdraw` gate the maker's ability to reveal the secret and claim funds strictly by these attacker-chosen offsets: [3](#0-2) 

and `EscrowDst.cancel` lets the taker reclaim the funds they funded as soon as `DstCancellation` elapses: [4](#0-3) 

Because the taker (an unprivileged, ordinary protocol participant who is simply the party calling `createDstEscrow`) fully controls `DstWithdrawal`/`DstPublicWithdrawal`/`DstCancellation` independently of anything the maker signed, they can set `DstWithdrawal`/`DstCancellation` to a minimal duration (e.g. 1–2 seconds), collapsing the window in which the maker can realistically observe the deployed escrow, obtain the secret path, and submit `withdraw` before the taker calls `cancel()` and reclaims their own deposited funds. Meanwhile the maker's original assets are already locked on the source chain in `EscrowSrc`, whose `SrcCancellation` bound comes from the maker-signed order data set during `_postInteraction` and is unaffected by this manipulation: [5](#0-4) [6](#0-5) 

So the maker cannot recover their source-chain funds until `SrcCancellation` elapses (a duration the maker agreed to as part of a full, honest swap), even though the destination leg was sabotaged within seconds of `createDstEscrow`.

## Impact Explanation
This matches the Medium/High bounty bucket "temporary freezing of funds during the live swap lifecycle": the maker's already-committed source-chain tokens become stuck for the full `SrcCancellation` duration because the taker, an unprivileged actor entering exclusively through the public `createDstEscrow` function, can unilaterally choose a degenerate `Timelocks` value for the destination leg that makes real withdrawal by the maker practically impossible, without any on-chain requirement that these values be consistent with the order the maker actually signed.

## Likelihood Explanation
`createDstEscrow` has no access control and no cross-check binding `dstImmutables.timelocks` (aside from the `DstCancellation` upper bound) to the order data that was hashed/signed on the source chain. Any address that observes a `SrcEscrowCreated` event (public) can call `createDstEscrow` and supply an arbitrarily small `DstWithdrawal`/`DstCancellation` window; this requires no privileged role, no governance, and no compromised infrastructure - it is directly reachable by the ordinary unprivileged taker flow.

## Recommendation
In `createDstEscrow`, validate the internal ordering and minimum spacing of the destination timelock stages relative to each other and to a protocol-defined minimum window, e.g.:
```solidity
if (
    immutables.timelocks.get(TimelocksLib.Stage.DstWithdrawal) < block.timestamp + MIN_WITHDRAWAL_DELAY ||
    immutables.timelocks.get(TimelocksLib.Stage.DstPublicWithdrawal) < immutables.timelocks.get(TimelocksLib.Stage.DstWithdrawal) ||
    immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) < immutables.timelocks.get(TimelocksLib.Stage.DstPublicWithdrawal)
) revert InvalidCreationTime();
```
Additionally, consider binding the accepted `dstImmutables.timelocks` (or at least the relative-offset portion) to the same timelocks value that was emitted/signed on the source side, so a taker cannot substitute an arbitrary, unrelated `Timelocks` for the destination leg.

## Proof of Concept
1. Maker signs and the resolver fills an order via `_postInteraction`, producing a real `EscrowSrc` with `SrcCancellation` set to, e.g., `now + 2 days` (per the maker-approved order data).
2. The taker calls `createDstEscrow` with `dstImmutables.timelocks` crafted so that `DstWithdrawal = deployedAt + 1`, `DstPublicWithdrawal = deployedAt + 1`, `DstCancellation = deployedAt + 2` (passes the only check since `2 <= srcCancellationTimestamp`).
3. Two seconds after deployment the taker calls `EscrowDst.cancel(immutables)`, reclaiming the safety deposit and the funded destination amount before the maker had any real chance to submit `withdraw(secret, immutables)`.
4. The maker never receives the destination asset, and their original tokens stay locked in `EscrowSrc` until `SrcCancellation` (up to the full `2 days`), at which point they must call `cancel` themselves to recover their own funds — a multi-day temporary freeze caused entirely by an unvalidated, unprivileged input to `createDstEscrow`.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

```text
library TimelocksLib {
    enum Stage {
        SrcWithdrawal,
        SrcPublicWithdrawal,
        SrcCancellation,
        SrcPublicCancellation,
        DstWithdrawal,
        DstPublicWithdrawal,
        DstCancellation
    }

    uint256 private constant _DEPLOYED_AT_MASK = 0xffffffff00000000000000000000000000000000000000000000000000000000;
    uint256 private constant _DEPLOYED_AT_OFFSET = 224;

    /**
     * @notice Sets the Escrow deployment timestamp.
     * @param timelocks The timelocks to set the deployment timestamp to.
     * @param value The new Escrow deployment timestamp.
     * @return The timelocks with the deployment timestamp set.
     */
    function setDeployedAt(Timelocks timelocks, uint256 value) internal pure returns (Timelocks) {
        return Timelocks.wrap((Timelocks.unwrap(timelocks) & ~uint256(_DEPLOYED_AT_MASK)) | value << _DEPLOYED_AT_OFFSET);
    }

    /**
     * @notice Returns the start of the rescue period.
     * @param timelocks The timelocks to get the rescue delay from.
     * @return The start of the rescue period.
     */
    function rescueStart(Timelocks timelocks, uint256 rescueDelay) internal pure returns (uint256) {
        unchecked {
            return rescueDelay + (Timelocks.unwrap(timelocks) >> _DEPLOYED_AT_OFFSET);
        }
    }

    /**
     * @notice Returns the timelock value for the given stage.
     * @param timelocks The timelocks to get the value from.
     * @param stage The stage to get the value for.
     * @return The timelock value for the given stage.
     */
    function get(Timelocks timelocks, Stage stage) internal pure returns (uint256) {
        uint256 data = Timelocks.unwrap(timelocks);
        uint256 bitShift = uint256(stage) * 32;
        // The maximum uint32 value will be reached in 2106.
        return (data >> _DEPLOYED_AT_OFFSET) + uint32(data >> bitShift);
    }
```
