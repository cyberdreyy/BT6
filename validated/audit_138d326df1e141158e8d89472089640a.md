### Title
Unrestricted access to `/debug/vars` (expvar) for any authenticated session user regardless of role - ([File: core/web/router.go])

### Summary
The `debugRoutes` function registers `GET /debug/vars` behind `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` only, with no role check (`auth.RequiresAdminRole`, `RequiresEditRole`, or `RequiresRunRole`). Any user with a valid session cookie, including one with the lowest privilege `view` role, can hit this endpoint and receive Go's default `expvar` output.

### Finding Description
`debugRoutes` in [1](#0-0)  mounts `expvar.Handler()` under `/debug`, protected only by `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)`. Compare this to nearly every other sensitive route in `v2Routes`, which is additionally wrapped with a role-check helper (`auth.RequiresAdminRole`, `auth.RequiresEditRole`, `auth.RequiresRunRole`) as seen throughout [2](#0-1) .

The `auth.Authenticate` middleware itself only establishes *who* the caller is (it sets `SessionUserKey` in the gin context) — it performs no role gating on its own, as shown in [3](#0-2) . Role enforcement is an opt-in wrapper applied per-route (`RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` in [4](#0-3) ), and `debugRoutes` does not apply any of them.

Consequently, any authenticated session — including the lowest `clsessions.UserRoleView` role — reaches Go's built-in `expvar` handler, which by default publishes `cmdline` (the process's `os.Args`) and `memstats` (`runtime.MemStats`) variables, plus any other package-registered `expvar.Publish` variables in the binary.

Note: The same router file also mounts `pprof`-based debug endpoints (`metricRoutes`) under the `authv2` group without any role wrapper either [5](#0-4) , indicating this is a systemic pattern rather than an isolated typo — but it still represents a real authorization-exactness gap for the `/debug/vars` route specifically named in the question.

### Impact Explanation
This is an internal runtime state disclosure vulnerability: a low-privilege `view`-role session user (who is meant to only have read access to job/pipeline data) can retrieve process command-line arguments and Go runtime memory/GC statistics. If the node was launched with any secret passed as a CLI flag (rather than via file/env var), it would be disclosed via `cmdline`. Even absent literal secrets in argv, this leaks internal operational details (binary paths, flags, heap/GC sizing) useful for further reconnaissance/fingerprinting by any authenticated low-privilege user, violating the principle that debug/introspection endpoints should require an elevated (admin) role.

### Likelihood Explanation
Minimal precondition: an attacker only needs valid credentials for the lowest-privilege `view` role (obtainable by design if any view-only user exists), then issue `GET /debug/vars` with that session cookie. No token, no elevated role, no special network position needed — fully repeatable and deterministic given `auth.AuthenticateBySession` succeeds.

### Recommendation
Wrap the `/debug` group (and the `pprof` `metricRoutes`) with `auth.RequiresAdminRole` (or at minimum `auth.RequiresEditRole`) so that only privileged operators can access `expvar`/`pprof` debug output, e.g.:
```go
func debugRoutes(app chainlink.Application, r *gin.RouterGroup) {
    group := r.Group("/debug", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
    group.GET("/vars", auth.RequiresAdminRole(func(c *gin.Context) { expvar.Handler().ServeHTTP(c.Writer, c.Request) }))
}
```
Also ensure no secrets are ever passed via CLI flags/argv, defense-in-depth against `cmdline` disclosure.

### Proof of Concept
Go handler-level integration test plan (in `core/web/router_test.go` style):
1. Set up a test app with `NewRouter`, seed a user with `clsessions.UserRoleView`.
2. Log in via `POST /sessions` to obtain a valid session cookie for the view-role user (using `SessionsController`).
3. Issue `GET /debug/vars` with that session cookie attached.
4. Assert: HTTP status `200 OK`.
5. Parse response body as JSON and assert presence of `"cmdline"` and `"memstats"` top-level keys.
6. Contrast with a route wrapped by `auth.RequiresAdminRole` (e.g. `GET /v2/users`) using the same view-role session, asserting `403 Forbidden`, to demonstrate the inconsistency: `/debug/vars` lacks the role gate applied elsewhere.

// Authenticate is middleware which authenticates the request by attempting to
// authenticate using all the provided methods.
func Authenticate(store Authenticator, methods ...authMethod) gin.HandlerFunc {
	return func(c *gin.Context) {
		var err error
		for _, method := range methods {
			err = method(c, store)
			if !errors.Is(err, auth.ErrorAuthFailed) {
				break
			}
		}
		if err != nil {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, err)

			return
		}

		c.Next()
	}
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
