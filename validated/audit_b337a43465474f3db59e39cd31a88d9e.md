### Title
Malicious lender can permanently DoS write-off fulfillment via equality check on mutable `userRequests.tranches` - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`fullfillWriteOffRequest` requires the fulfiller-supplied `_tranches` to exactly equal the current stored `userRequests[_user].tranches`. Because `createWriteOffRequest` lets the same lender top up their request at any time while the epoch is running, an attacker (any unprivileged tranche-token holder posing as a lender, or anyone able to grief a known lender's request by... ) can front-run a fulfiller's transaction, add a dust amount of tranche tokens, and make the fulfiller's tx revert with `WrongRequest`. This is repeatable for the entire running epoch, freezing escrowed tranche tokens and blocking the borrower's debt write-off path (`writeOffDeposit`), exactly mirroring the `num_positions != id` front-run DoS in the Lockbox report.

### Finding Description
In `contracts/IdleCreditVaultWriteOffEscrow.sol`, `createWriteOffRequest` accumulates into per-user storage without any uniqueness:

```solidity
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
```

`fullfillWriteOffRequest` then enforces an exact equality on that mutable value:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

Since a fulfiller must hardcode `_tranches` at tx submission, any mutation of `userRequests[_user].tranches` between submission and execution invalidates the tx. The mutation path is permissionless: the lender (the attacker) calls `createWriteOffRequest(1 wei, 0)` — `underlyingsRequested` has no lower bound, only `amount == 0` is rejected.

Sequence:
1. Attacker (KYC'd lender, holds AA/BB tranche tokens) calls `createWriteOffRequest(1000e18, 500e18)` during a running epoch. Their tranche tokens are escrowed.
2. Borrower/fulfiller observes the request and submits `fullfillWriteOffRequest(attacker, 1000e18, 500e18)` with the underlying approved.
3. Attacker front-runs with `createWriteOffRequest(1, 0)` → stored `tranches` becomes `1000e18 + 1` → fulfiller's tx reverts `WrongRequest`.
4. Repeat indefinitely while `isEpochRunning()` is true. Each repeat costs the attacker only gas and 1 wei of tranche tokens.

Unlike the deleted-request path (attacker could also `deleteWriteOffRequest` to grief, but that would pull their tokens back), topping up keeps the escrow open, so the fulfiller can never settle the trade, and the borrower's intended `writeOffDeposit` of those tranches to reduce debt is blocked.

### Impact Explanation
- The fulfiller's transaction deterministically reverts; no write-off exchange can ever be completed against a request the attacker controls, for as long as the epoch runs (epochs can be months long).
- Legitimate lenders' escrowed tranche tokens remain locked — a fulfillment they agreed to cannot execute; this is a temporary freezing of user funds with economic harm: the lender misses the exit, and the borrower cannot use `writeOffDeposit` to burn tranches against the escrowed debt, preserving borrower liabilities into `stopEpoch` and worsening the loss/NAV split for all tranche holders.
- No privileged guard stops this: `fullfillWriteOffRequest` is callable by any wallet and `createWriteOffRequest` only requires a nonzero amount and a running epoch.

### Likelihood Explanation
High — the attack requires only holding the tranche token and submitting an ordinary `createWriteOffRequest` with dust, cheap on any mempool with front-running capability. It works in every fixed-APR/AYS/prefunded mode that uses the escrow, during every running epoch. The attacker has a direct incentive mirroring the report: the fulfiller is typically the borrower buying back debt at a discount, and a competing claimant or a griefer benefiting from higher borrower debt (or simply a competitor wanting the write-off themselves at a later price) can block all fulfillments.

### Recommendation
Do not require exact equality on mutable request state. Either:
- Snapshot the terms: pass the request parameters (`tranches`, `underlyings`) and only require `currentRequest.underlyings <= _underlyings` and `currentRequest.tranches >= _tranches`, then decrement `userRequests[_user]` and `pendingUnderlyings` by the fulfilled amounts, or
- Key requests by an immutable ID (e.g., a per-user nonce or `keccak256` of terms) so top-ups create a new request rather than mutating the one being fulfilled.

### Proof of Concept
Foundry fork-style test against `IdleCreditVaultWriteOffEscrow` (pool in running epoch, `isEpochRunning() == true`):

```solidity
// attacker is a KYC'd lender holding tranche tokens
vm.startPrank(attacker);
tranche.approve(address(escrow), type(uint256).max);
escrow.createWriteOffRequest(1000e18, 500e18);
vm.stopPrank();

// fulfiller tries to fulfill observed terms
underlying.approve(address(escrow), 500e18);
vm.expectRevert(); // WrongRequest — but first, attacker front-runs:
vm.startPrank(attacker);
escrow.createWriteOffRequest(1, 0); // dust top-up
vm.stopPrank();

escrow.fullfillWriteOffRequest(attacker, 1000e18, 500e18); // reverts WrongRequest
```

Caveat I could not fully verify within the analysis: whether `createWriteOffRequest`'s top-up while a fulfiller tx is pending is the intended design surface for griefing in this variant, and whether the borrower's `writeOffDeposit` flow is considered an in-scope loss path rather than "previously acknowledged." The core mechanic (user-supplied equality against an attacker-mutable counter) is confirmed in `IdleCreditVaultWriteOffEscrow.sol:123-131` and `:86-101`.
