### Title
Own-tenure conflict guard fails open on node RPC error, allowing a signer to sign two conflicting blocks in the same tenure at the same height - (File: stacks-signer/src/v0/signer.rs)

### Summary
In the pre-commit-to-signature path (`store_and_process_block_signature`'s sibling, the final own-tenure conflict re-check that runs immediately before `handle_block_pre_commit` marks a block `locally_accepted`), a stale-but-still-relevant same-tenure conflict is only vetoed if `stacks_client.get_tenure_tip(...)` succeeds and reports the tenure already at or above the proposed height. If the RPC call errors for any reason, the code logs a warning and **falls through to sign**, rather than refusing.

### Finding Description
`handle_block_pre_commit` re-derives whether a stale conflict in the block's *own* tenure still blocks signing: [1](#0-0) 

When a stale same-tenure conflict exists and the reorg permit does not cover it, the code asks the node `get_tenure_tip(consensus_hash)`. Only an `Ok` response with `tip_height >= chain_length` vetoes signing. Any `Err(e)` (RPC failure, connection reset, node overload, timeout, or a malformed/unexpected response) is treated as "tenure as unconfirmed" — i.e., the conflict is dropped and the code proceeds to `mark_locally_accepted` + `handle_block_signature`, producing a signature.

This mirrors the general "assume-higher-on-node-unreachable" fail-open pattern the codebase relies on elsewhere (`check_latest_block_in_tenure`, `stacks-signer/src/chainstate/mod.rs:450-460`), but there the fallback is safe because the *stacks-node's own* `/v3/block_proposal` validation is the real backstop for that specific check. Here, at the pre-commit → signature boundary, this `get_tenure_tip` call is itself the last safety re-check before the signer's one irreversible act (placing a signature). There is no subsequent node-side re-validation of "did I already sign a conflicting sibling in this tenure" — that guarantee lives entirely in the signer's own logic.

A one-slot miner can trivially induce this condition: by re-proposing a second, conflicting block at the same height in the same tenure after the first block's signature has gone stale (a scenario the code explicitly anticipates and normally handles safely via the `Ok` branch — see `reproposal_signs_replacement_after_conflict_times_out`), while the signer's own `get_tenure_tip` RPC to its paired stacks-node happens to fail (a transient node hiccup, restart, or load spike — none of which require majority collusion or another signer's key). The signer will then sign the second, conflicting sibling even though the first one's signature might still be valid/live, breaking the "we do not sign two blocks that could both end up in the chain" guarantee described directly above this code: [2](#0-1) 

### Impact Explanation
This breaks the equality the guard exists to enforce: "a fresh/stale-but-live conflict must veto a second signature over a sibling block." A local RPC failure — not attacker-controlled cryptography, not a majority of signers — causes the signer to place a second signature over a block that conflicts with one it may have already (or will) sign elsewhere. Per the scan rules, this falls under "a signer signing an invalid/non-canonical/conflicting block," a Critical-class safety break, since it can contribute a valid signature toward a sibling/conflicting block that should have been refused.

### Likelihood Explanation
This requires only:
1. A miner re-proposing a conflicting block at the same height in the same tenure after the original signature has gone stale (miner-controlled, single slot, well within the "one-slot miner + gossip" threat model).
2. A transient failure of the signer's own `get_tenure_tip` RPC call at the moment of re-evaluation — a condition that is not adversary-controlled but is realistic (node restart, timeout, degraded I/O), and the code path treats it identically to "the tenure was never confirmed," which is the more benign case the fallback was designed for.

No majority, no other signer's key, and no auth token access is required. The likelihood is moderate rather than high because it depends on a coincidental RPC failure rather than a fully attacker-controlled trigger.

### Recommendation
Change the `Err(e)` branch at `stacks-signer/src/v0/signer.rs:1449-1455` to refuse to sign (treat as "conflict still blocks," matching the conservative default used everywhere else conflict liveness cannot be determined, e.g. `conflict_still_blocks`'s `Err` branches which explicitly `return true` to keep the conflict blocking) rather than falling through to `mark_locally_accepted`. This preserves the fail-safe posture: an inability to confirm the tenure's canonical tip should never be silently converted into permission to sign.

### Proof of Concept
1. Signer S pre-commits to and signs block A (tenure T, height h). `A`'s signature becomes stale per `tenure_last_block_proposal_timeout`.
2. Miner re-proposes block B, also in tenure T at height h (a legitimate re-proposal scenario, as covered by `reproposal_signs_replacement_after_conflict_times_out`, [3](#0-2) ).
3. B reaches the pre-commit threshold; `handle_block_pre_commit` finds A as a stale same-tenure conflict and calls `stacks_client.get_tenure_tip(&T)` to determine whether A is already confirmed by the node (code at lines 1432-1457 above).
4. If this RPC call errors (node timeout/restart/etc.) instead of returning `Ok`, the `Err(e)` branch is taken, no veto occurs, and S proceeds to `mark_locally_accepted` and signs B — even though the node may still consider A's tenure state live, i.e., without the intended confirmation that A is not "already built on."

Note: I could not execute this against a live signer/node pair to observe the concrete downstream chain-level consequence (whether the node's own append-time checks in `validate_nakamoto_tenure_snapshot`/duplicate-block logic would still catch the second signature before it becomes consensus-breaking); this is a signer-side logic gap, and its full blast radius depends on interaction with node-side idempotency checks not covered in this pass.
