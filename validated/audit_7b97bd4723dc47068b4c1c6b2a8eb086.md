### Title
Stale-epoch instant-withdraw receipts are excluded from `defaultPendingClaimBasis`, inflating the recovery price and draining the default reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external report (`H5O_msg_flush` heap overflow) is a stale-state-during-flush bug: pending messages that were not accounted in the flush corrupt memory. The analog is `IdleCreditVault`'s default-recovery "flush" of pending receipts: `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` only count `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch — while instant receipts are tracked per request epoch and can survive unfunded across an epoch boundary. An attacker holding an unfunded instant receipt from an earlier epoch is invisible to recovery accounting, so `defaultRecoveryPrice` is computed against too small a basis (too high), early claimants are overpaid, and the reserve is exhausted before late claimants are paid.

### Finding Description
- Instant withdraw requests are recorded per request epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` (IdleCreditVault.sol:367-374).
- `collectInstantWithdrawFunds` only decrements `pendingInstantWithdraws`; it does not clear per-epoch claim basis (lines 398-403). At `startEpoch`, if `pendingInstant > totUnderlyings`, only partial funding is sent and the unfunded remainder — including requests made in the *previous* epoch — carries forward (IdleCDOEpochVariant.sol:279-290).
- On default, `finalizeDefaultRecovery` computes `pendingBasis = defaultPendingClaimBasis()`, which adds only `instantWithdrawClaimsByEpoch[epochNumber]` — i.e. receipts whose `requestEpoch == epochNumber` at finalization (lines 644-649). Receipts requested in earlier epochs and still unfunded are omitted from `totalBasis`, so `recoveryPrice = reserveAmount * 1e18 / totalBasis` is overstated (lines 679-692).
- Symmetrically, `_defaultPrefundedInstantReserve` derives the already-funded portion as `instantWithdrawClaimsByEpoch[epochNumber] - pendingInstantWithdraws` using only the current-epoch claim map (lines 716-723), miscounting the reserve split when earlier-epoch claims exist.
- After finalization, `_claimDefaultedInstantWithdrawRequest` clears only `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` (lines 842-856); the remainder of `instantWithdrawsRequests[_user]` is then paid **at par** through `_transferFundedClaim` in `claimInstantWithdrawRequest` (lines 380-393). The attacker therefore redeems an unfunded stale receipt without any haircut, while the same receipts were never included in the basis that sized the reserve.

### Impact Explanation
Direct theft / insolvency. Because the excluded basis makes `defaultRecoveryPrice` larger than the true pro-rata ratio, every defaulted-epoch claimant is overpaid from `defaultRecoveryReserve`; once the reserve drains, later claimants (including honest KYC'd lenders and tranche holders) receive nothing. The attacker additionally claims their stale-epoch instant receipt at par via `_transferFundedClaim`, further draining funded strategy balance. The loss is bounded by the attacker's stale instant basis plus the aggregate overpayment factor `trueBasis/computedBasis - 1` applied to all defaulted claims — easily quantified in a fork PoC by comparing reserve before/after claims.

### Likelihood Explanation
Reachable by an unprivileged lender: request an instant withdraw late in epoch N-1, let it remain (partially) unfunded through `startEpoch` N (manager honestly calls `getInstantWithdrawFunds`/`startEpoch` with insufficient CDO cash, which the honest-sequence rules allow), then wait for a borrower default and `finalizeDefault` in epoch N. All attacker steps are ordinary user calls (`requestInstantWithdraw`, `claimInstantWithdrawRequest`); no privileged misbehavior is required. Guard review: `defaulted`/finalization flags gate the path but do not check for stale-epoch instant claims; `requestInstantWithdraw` has no guard against carrying old receipts.

### Recommendation
In `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, account for the *entire* outstanding instant claim set, not just `instantWithdrawClaimsByEpoch[epochNumber]` (e.g. track a global `totalInstantClaims` counter incremented at request and decremented at claim/collect). Alternatively, in `_claimDefaultedInstantWithdrawRequest`, iterate/clear all epochs with nonzero `instantWithdrawsRequestsByEpoch` and route unfunded stale receipts through `defaultRecoveryPrice` instead of paying them at par via `_transferFundedClaim`.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// 1. Deposit AA/BB, startEpoch(0). Attacker requests instant withdraw near
//    the instantWithdrawDeadline of epoch N-1:
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(ATTACK_AMOUNT, address(AAtranche));

// 2. Manager (honest) calls getInstantWithdrawFunds with borrower cash that
//    covers only part of pendingInstantWithdraws, or startEpoch partial-funds it.
//    pendingInstantWithdraws > 0 persists; attacker's basis sits in
//    instantWithdrawsRequestsByEpoch[attacker][N-1].

// 3. Epoch N runs; borrower defaults (stopEpoch catch -> _handleBorrowerDefault).
// 4. Manager calls finalizeDefault(recovered, manager).
//    Observe: strategy.defaultPendingClaimBasis() excludes attacker's N-1 basis
//    (only instantWithdrawClaimsByEpoch[N] counted) ->
//    defaultRecoveryPrice is overstated.

// 5. Attacker calls cdoEpoch.claimInstantWithdrawRequest():
//    - _claimDefaultedInstantWithdrawRequest clears only epoch-N entries (0 for attacker)
//    - _transferFundedClaim pays attacker full instantWithdrawsRequests at par.
assertEq(underlying.balanceOf(attacker) - balPre, ATTACK_AMOUNT); // unhaircut payout

// 6. Honest defaulted-epoch claimants then claim:
//    reserve insufficient -> last claimant receives < basis * trueRecoveryPrice
//    or reverts; quantify shortfall = reserveBefore - sum(payouts).
```

Caveat: the exact post-claim funding source depends on the reserve-guard logic in the tail of `_transferFundedClaim` (IdleCreditVault.sol:897+, partially beyond indexed context); if it hard-blocks spending `defaultRecoveryReserve`, the impact is permanent freezing of the stale receipt plus the still-valid overstated-`defaultRecoveryPrice` insolvency. Either outcome satisfies the acceptance criteria (theft or insolvency).
