## Finding

### Title
Staked-collateral (SVSP) LST price can be inflated by anyone via a direct lamport transfer to the pool's stake/on-ramp accounts - ([File: programs/marginfi/src/state/price.rs])

### Summary
The `StakedWithPythPush` oracle path prices an LST by dividing a "net asset value" (raw lamport balance of the pool's stake/on-ramp accounts) by the LST mint supply, then uses this as a multiplier on the underlying Pyth SOL price. Because the NAV is computed from a raw account `lamports()` read rather than from state that is only mutated through gated stake-pool operations, anyone can inflate it with a plain System Program transfer to the (publicly derivable) stake or on-ramp account, instantly and permanently raising the multiplier used to value every position collateralized by that bank — mirroring the reported class of "oracle value derived from a balance that can be pushed via a raw transfer, bypassing any lock/CPI-gated path."

### Finding Description
For `OracleSetup::StakedWithPythPush`, the exchange-rate/multiplier is computed as: [1](#0-0) 

`staked_pool_net_asset_value` simply reads `pool_stake_info.lamports()` and `pool_onramp_info.lamports()` (minus rent-exempt reserves) — it does not verify that the balance change came from a legitimate stake/delegate/rewards-accrual operation.

This NAV feeds directly into the price multiplier applied to the Pyth SOL price for the whole bank: [2](#0-1) 

Both accounts are deterministically derivable from public data stored on the `Bank` itself: the validator vote account is `bank.integration_acc_1`, and the on-ramp PDA is `derive_staked_onramp_from_vote(bank.integration_acc_1)`: [3](#0-2) 

Since Solana allows crediting lamports to any account via a simple System Program transfer regardless of that account's owner, any unprivileged actor can send SOL directly to `pool_stake_info` or `pool_onramp_info` to raise `sol_pool_adjusted_balance` without minting any corresponding LST supply — inflating `multiplier = sol_pool_adjusted_balance / lst_supply` for every holder of that LST bank in a single, irreversible step, with no lock/TWAP/CPI-gate analogous to Curve's `check_lock` protecting it.

### Impact Explanation
The multiplier directly scales the USD value assigned to every deposit/collateral position denominated in that staked-collateral bank (`price_feed.price.price` and `ema_price.price` are both multiplied by it before being fed into health checks). An inflated multiplier increases the apparent collateral value of all LST holders in that bank simultaneously, which can:
- Push an otherwise-liquidatable/underwater position back above the liquidation threshold (griefing a liquidator / delaying liquidation), and
- Let a large holder of the affected LST borrow more than their real collateral backs.

The magnitude of usable impact is inversely proportional to total pool size — a newly created or low-TVL single-validator staked-collateral bank ("few funds in the pool," directly echoing the original report's caveat) can be meaningfully skewed cheaply, whereas a large/mature pool requires proportionally more capital to move.

### Likelihood Explanation
No privileged role, oracle-account key match, or special CPI access is required — only a plain SOL transfer to a publicly-derivable PDA. `check_primary_oracle_key` only validates `oracle_keys[0]` (the Pyth feed), not the stake/on-ramp accounts' balances, so this path is unauthenticated by design. Exploitability is bounded by pool economics (donations are a sunk cost, and the attacker only recaptures value proportional to their own share of the LST supply times LTV), which limits this mainly to griefing/threshold-nudging on small pools rather than a directly self-enriching attack on large ones — but it remains a concrete, reachable, unauthenticated price-manipulation primitive with no code-level mitigation (e.g., TWAP, deposit-only accounting, or reconciliation against expected stake) in the codebase.

### Recommendation
Do not derive NAV from a raw `lamports()` read of accounts that can receive arbitrary unauthenticated transfers. Either:
- Track NAV via state that is only mutated through the SVSP program's own gated stake/deposit/withdraw instructions (e.g., reconcile against the stake account's `Delegation.stake` field plus a bounded, rate-limited accrual window), or
- Cap the per-block/per-slot delta the oracle will accept for the multiplier, and/or require that `total_asset_value_init_limit` always be set (non-zero) for staked-collateral banks so a single-transfer NAV spike cannot translate into materially more borrowing power.

### Proof of Concept
1. Identify a `StakedWithPythPush` bank with a small underlying single-validator pool (`bank.integration_acc_1` = validator vote account is public on the `Bank` account).
2. Derive `pool_onramp_info = derive_staked_onramp_from_vote(vote)` (or use the pool's main stake account, whichever holds a small rent-exempt-adjusted balance).
3. Send a plain SOL transfer from any unprivileged wallet to that account.
4. Call any instruction that re-prices the bank (e.g., `pulse_health`, `deposit`, `borrow`) and observe that `staked_pool_net_asset_value` — and therefore `price_multiplier` / `oracle_price` for that bank — increased by exactly the transferred lamports, with no corresponding change in LST supply, per `staked_pool_net_asset_value` at [1](#0-0) .

```rust
fn staked_pool_net_asset_value(
    pool_stake_info: &AccountInfo,
    pool_onramp_info: &AccountInfo,
    rent: &Rent,
) -> MarginfiResult<u64> {
    let pool_rent_exempt_reserve = rent.minimum_balance(pool_stake_info.data_len());
    let onramp_rent_exempt_reserve = rent.minimum_balance(pool_onramp_info.data_len());

    let main_stake_value = pool_stake_info
        .lamports()
        .saturating_sub(pool_rent_exempt_reserve);
    let onramp_value = pool_onramp_info
        .lamports()
        .saturating_sub(onramp_rent_exempt_reserve);

    Ok(main_stake_value.saturating_add(onramp_value))
}
```
