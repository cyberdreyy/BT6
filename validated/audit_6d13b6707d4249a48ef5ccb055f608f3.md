Confirmed: `multisig-factory/src/lib.rs` is the entire contract (single file, 50 lines), with only a `create` function and no callback or refund mechanism.

### Title
Front-running the `create` account name in `multisig-factory` permanently freezes the victim's deposit - (File: multisig-factory/src/lib.rs)

### Summary
`MultisigFactory::create` derives the new sub-account's name directly from the attacker-observable, user-supplied `name` parameter, deploys a promise that creates the account, deploys the multisig contract, and transfers the attached deposit, but never checks whether the target account already exists before submitting the promise and never registers a `.then()` callback to detect promise failure and refund the caller. Any unprivileged attacker who observes a pending `create` transaction in the mempool can front-run it by calling `create` first with the same `name`, claiming the account. When the victim's original transaction executes afterward, `create_account` fails because the account already exists, so the whole batched promise (deploy + transfer + `new` call) never executes — but the victim's attached deposit was already credited to the factory contract's balance in the original (successful) function-call receipt. Because there is no refund path, that NEAR is permanently stuck in the factory contract.

### Finding Description
`create` computes the target account deterministically and cheaply from attacker-visible input: [1](#0-0) 

Unlike its sibling factories, this contract performs no existence check on `account_id` before issuing the promise, and unlike `lockup-factory`'s `create`/`on_lockup_create` and `staking-pool-factory`'s `create_staking_pool`/`on_staking_pool_create`, `MultisigFactory` registers no `.then()` callback: [2](#0-1) [3](#0-2) 

Those two other factories explicitly refund the caller's `attached_deposit` when the create-account promise fails: [4](#0-3) 

`multisig-factory` has no such logic anywhere in its (single-file) source, and `MultisigFactory` itself stores no owner or state that would allow later recovery of stranded funds: [5](#0-4) 

**Custody binding broken:** value debited from the caller (attached deposit consumed by the factory's successful `create` receipt) must equal value delivered (funds forwarded into a live multisig account controlled per the caller's intended `members`/`num_confirmations`). When the target account is squatted first, delivered value is `0`, yet debited value remains the full attached deposit, and it is retained by the factory contract with no method to move or reclaim it.

### Impact Explanation
Because the attached deposit is credited to the factory's own balance as part of the *original* (predecessor) receipt — a receipt that succeeds regardless of what happens to the promise it returns — a failure in the downstream `create_account`/`deploy_contract`/`transfer`/`function_call` batch does not roll back that credit. With no `.then()` callback and no admin/owner/withdraw function in `MultisigFactory`, the deposited NEAR (up to the full amount attached, e.g. 50 NEAR per the README example) is permanently frozen inside the factory contract. This matches the Critical impact category "funds permanently frozen."

### Likelihood Explanation
Any unprivileged actor watching the mempool can trivially front-run any `create` call by copying the visible `name` argument and submitting their own `create` transaction with higher gas price/priority (no whitelisting, no permissions, no special knowledge required — `create` is a fully public, un-gated entrypoint). Because sub-account names chosen by users are often predictable/desirable (team or product names, as shown in the README example `"test"`), motivated griefers or extortionists have an incentive to squat likely names and cause deposit loss for legitimate users, mirroring the exact bug class described in the external report (front-running a name-claiming creation call).

### Recommendation
- Check `env::is_valid_account_id` and account non-existence is not enough (NEAR runtime already enforces name collisions at `create_account`), so instead add a `.then()` callback (`on_create`) mirroring `lockup-factory`/`staking-pool-factory`, that checks `is_promise_success()` and refunds `env::attached_deposit()` to `env::predecessor_account_id()` on failure.
- Alternatively/additionally, mitigate the front-running vector itself by requiring a commit-reveal scheme, or by using a random/attacker-unpredictable suffix for the account name and returning the resulting account id to the caller off-chain.

### Proof of Concept
1. Victim submits `create({"name": "acme", "members": [...], "num_confirmations": 2})` with 50 NEAR attached, targeting `acme.multisig-factory.near`.
2. Attacker observes the pending transaction, and submits their own `create({"name": "acme", "members": [{"account_id": "attacker"}], "num_confirmations": 1})` with minimal deposit, with higher gas price so it lands first.
3. Attacker's transaction succeeds: `acme.multisig-factory.near` is created and controlled solely by `attacker`.
4. Victim's transaction executes: `create` succeeds as a top-level call (attached 50 NEAR is credited to the factory contract's balance), but the returned promise's `create_account` action fails since `acme.multisig-factory.near` already exists; the chained `deploy_contract`, `transfer`, and `function_call` actions in that same batch never execute.
5. No callback exists to detect the failure, so the victim's 50 NEAR is never returned; it is now stuck in the `multisig-factory` contract's balance permanently, with no method in `MultisigFactory` (which has zero stored fields) able to move it out.

    #[payable]
    pub fn create(
        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }
