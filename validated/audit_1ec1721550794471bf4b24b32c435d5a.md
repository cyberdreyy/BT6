### Title
Miner-Controlled `last_activity_time` Refresh Lets a Malicious Miner Indefinitely Suppress the Inactivity Timeout - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` treats certain invalid/stale/reorg-style block proposals from the *current tenure's own miner* as valid "activity" and refreshes `last_activity_time`, which is the sole input that `SortitionState::is_timed_out` (v1 and v2) uses to decide whether the miner has gone inactive and the signer set should fall back to the prior miner. Because the refresh condition is satisfied by cheap, repeatable, invalid proposals, a single one-slot miner can keep resetting this clock forever, exactly as SapienVault's weighted-average lockup could be pushed back down by staking again — here the "clock" (`last_activity_time`) is recomputed on every crafted, low-cost input from the same actor who benefits from resetting it, defeating the intended monotonic timeout that should let the group move on.

### Finding Description
`get_tenure_last_block_info`/`check_latest_block_in_tenure` compares an incoming block proposal against the tenure's last known signed/pre-committed block. When the incoming proposal does not advance the chain (`chain_length <= info.block.header.chain_length` or a fresh pre-commit blocks it), the code deliberately still calls `signer_db.update_last_activity_time(...)`: [1](#0-0) [2](#0-1) 

The gate for the first refresh path is:
```
info.signed_group.is_none_or(|signed_time| signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs())
```
i.e. it is satisfied whenever the last known block in the tenure is *not yet globally accepted* (`signed_group == None`) or was globally accepted recently. In practice, while a tenure is actively being mined this condition is almost always true, so nearly any lower/duplicate/reorg-shaped proposal from the tenure's miner counts as "activity" and updates the clock — even though the proposal itself is being rejected as non-canonical.

This clock is the *only* signal `is_timed_out` uses to decide inactivity: [3](#0-2) [4](#0-3) 

Both v1's and v2's `is_timed_out` compute `elapsed = now - last_activity_time` and compare it to `block_proposal_timeout`; `last_activity_time` defaults to the burn-block-received time only if never set, but once `update_last_activity_time` is called, it is pushed forward to `get_epoch_time_secs()` at call time — with no cap, no decay, and no accounting of the *quality* of the activity that produced it. The miner that produced the low/invalid proposal is the same party whose inactivity is being measured, so this is analogous to SapienVault's staker being able to reset the very lockup counter that is supposed to constrain them: the party with an incentive to move the guard is the one whose repeated cheap action moves it.

The impact is the mirror of the lockup case: instead of *shortening* a lockup, the miner *lengthens/refreshes* the inactivity window indefinitely, preventing `check_proposal` from ever marking `cur_sortition.miner_status = InvalidatedBeforeFirstBlock`: [5](#0-4) 

As long as the miner is never marked invalid, signers keep waiting on it rather than falling back to the prior sortition's miner, and — per `docs/signer-flows.md` — the whole tenure-timeout/fallback design depends on this timer eventually firing: [6](#0-5) 

### Impact Explanation
This is a liveness wedge fitting "a signer wedged into never signing valid blocks... or losing the equivocation guard on restart" — more precisely, the whole signer set can be wedged into never falling back from a stalled/malicious current-tenure miner, because the fallback path (`is_timed_out` → mark invalid → consider `last_sortition`) never fires while the miner keeps refreshing `last_activity_time` with cheap invalid/reorg proposals. This can stall block production for the tenure without requiring any signer collusion, a majority of signers, or another signer's key — only the one-slot miner's own proposal stream, which every signer receives directly.

### Likelihood Explanation
The refresh condition (`info.signed_group.is_none_or(...)`) is satisfied under normal, expected conditions for a tenure that has not yet reached global acceptance for a while — i.e., exactly the window during which the timeout matters most. A miner simply needs to keep sending a proposal (any proposal that is judged non-advancing or conflicting with a fresh pre-commit) more often than `block_proposal_timeout`/`reorg_attempts_activity_timeout`, which is cheap (no signatures from other parties required, no fee cost beyond proposing) and fully within a single miner's control, making exploitation highly likely once the miner's slot has been won.

### Recommendation
Do not let a proposal from the tenure's *own miner* that fails the "does it advance the tenure" check extend `last_activity_time` when that same miner has not produced a genuinely new, higher, or differently-constructed block since the last refresh. Concretely:
- Track the last chain_length/proposal fingerprint that triggered a refresh, and only update `last_activity_time` if the new proposal is materially different from (and not merely a resend of) prior ones — analogous to disallowing a "shorter lockup" from overriding a longer one.
- Consider bounding the number of activity-refreshes an unadvancing miner can generate within one `block_proposal_timeout` window, so repeated invalid resubmission cannot indefinitely defer the fallback to the prior sortition winner.
- Alternatively, decouple "counts as miner activity" from "prevents timeout by resetting the same value used for is_timed_out" so a determined party cannot use one mechanism (activity crediting for now-slow miners) to defeat the other (timeout-driven failover).

### Proof of Concept
1. Miner M wins the current sortition/tenure and proposes an initial block B0; some signers pre-commit/locally-accept it (`signed_group` remains `None` until 70%+ globally accept).
2. M never lets the tenure reach global acceptance (e.g., withholds broadcasting, or the network is slow) and, just before `block_proposal_timeout` would elapse, resends a proposal B1 with `chain_length <= B0.chain_length` (a "reorg attempt" or duplicate low proposal).
3. In `check_latest_block_in_tenure`, since `info.signed_group.is_none()` (or is within `reorg_attempts_activity_timeout`), the code calls `signer_db.update_last_activity_time(tenure_id, now)` and returns `Ok(false)` (the proposal is rejected) — see [1](#0-0) .
4. `SortitionState::is_timed_out` recomputes `elapsed` from the just-refreshed `last_activity_time`, so `elapsed <= block_proposal_timeout` remains true indefinitely — see [7](#0-6) .
5. M repeats step 2 every cycle shorter than `block_proposal_timeout`. `cur_sortition.miner_status` in `check_proposal` never transitions to `InvalidatedBeforeFirstBlock` (see [5](#0-4) ), so signers never fall back to `last_sortition`'s miner, wedging the tenure.

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
