### Title
Missing predecessor/owner check in `replace()` allows any caller to overwrite raw contract storage - (File: state-manipulation/src/lib.rs)

### Summary
The `replace` function exported by the `state-manipulation` tool writes arbitrary attacker-supplied base64 key/value pairs directly into the calling account's storage via `storage_write`, with no check that the caller is the account itself or its owner. While this wasm is deployed on any account (e.g. a lockup, pool, or multisig temporarily running it for a migration), any unprivileged NEAR account can call `replace` and rewrite that account's persistent state, including `StakingContract` fields like `total_staked_balance`, `last_total_balance`, or per-delegator `unstaked` amounts.

### Finding Description
The claimed binding is: `predecessor_account_id_that_can_mutate_state == account_owner_or_self` (i.e., only the account's rightful owner/contract logic may write to its storage). In `replace()` this binding is violated — no such check exists anywhere in the function.

```rust
#[cfg(feature = "replace")]
#[no_mangle]
pub fn replace() {
    ...
    let input = input().unwrap();
    let args: ReplaceInput = serde_json::from_slice(&input).unwrap();
    for (key, value) in args.entries {
        storage_write(
            &base64::decode(key).unwrap(),
            &base64::decode(value).unwrap(),
        );
    }
}
``` [1](#0-0) 

The function is a bare `#[no_mangle]` export, not wrapped in `near_bindgen`, and contains no call to `env::predecessor_account_id()`, no `assert_eq!` against `env::current_account_id()`, and no owner assertion of any kind. `storage_write` itself performs no authorization either. [2](#0-1)  Consequently, once this wasm is deployed on an account (the premise given — a temporary migration tool), any account that can send a NEAR transaction can call `replace` on it and pass any base64-encoded Borsh storage key/value pair, including keys that collide with `StakingContract`'s `last_total_balance`, `total_staked_balance`, or a delegator's `unstaked` field, directly overwriting that raw storage slot.

The accompanying test (`workspaces_test`) demonstrates exactly this call pattern — deploying the wasm and calling `replace` with arbitrary base64 key/value entries and no owner/predecessor setup — confirming there is no authorization gate to bypass. [3](#0-2) 

### Impact Explanation
Any attacker able to send a transaction to the affected account while `state-manipulation` (`replace` feature) is deployed can rewrite arbitrary storage slots, including `StakingContract.total_staked_balance`/`last_total_balance` or delegator `unstaked` balances. This can be used to inflate an attacker-controlled account's staked/unstaked balance or corrupt total-balance accounting that governs subsequent withdrawals, directly enabling NEAR to be withdrawn from the pool/lockup/multisig account by a party never entitled to it — matching the Critical impact category. The attack is repeatable against every account running this tool and against every targeted storage key.

### Likelihood Explanation
The only precondition is that the vulnerable wasm (`replace` feature) is currently deployed on the target account, which the question states as the scenario (temporary migration tool on a testnet lockup/pool/multisig). Given that precondition, exploitation requires nothing more than knowing the target's Borsh storage key layout and sending one transaction with `entries` — no deposit, no special role, no key compromise. This is trivially repeatable and low-cost for the attacker.

### Recommendation
Add an explicit authorization check at the top of `replace()` (and `clean()`) — e.g. assert `env::predecessor_account_id() == env::current_account_id()` so the account can only call this on itself, or otherwise assert against a hardcoded/whitelisted owner — before performing any `storage_write`/`storage_remove`.

### Proof of Concept
```rust
#[tokio::test]
async fn unauthorized_replace_overwrites_state() -> anyhow::Result<()> {
    let wasm = fs::read("res/state_manipulation.wasm").await?;
    let worker = workspaces::sandbox().await?;
    let contract = worker.dev_deploy(&wasm).await?; // simulates victim account running the tool

    // Attacker account, unrelated to contract owner
    let attacker = worker.dev_create_account().await?;

    let key = base64::encode(b"STATE"); // stand-in for StakingContract's total_staked_balance key
    let malicious_value = base64::encode(&999_999_999_999u128.to_le_bytes());

    // Attacker calls replace directly, no owner/predecessor check exists
    attacker
        .call(&worker, contract.id(), "replace")
        .args_json(&serde_json::json!({ "entries": [(key.clone(), malicious_value.clone())] }))?
        .max_gas()
        .transact()
        .await?;

    let state_items = contract.view_state(&worker, None).await?;
    // Left side: value the rightful owner/contract logic never set
    // Right side: value now present in raw storage, written by attacker
    assert_eq!(
        state_items.get(b"STATE".as_ref()).unwrap(),
        &base64::decode(malicious_value).unwrap()
    );
    Ok(())
}
```
This demonstrates the binding `state_mutation_authorized_by == account_owner` is false: the mutation was authorized only by an unprivileged attacker account, yet the storage value changed exactly as requested.
