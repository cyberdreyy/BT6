### Title
Precompile instruction signature-count byte is trusted for fee/compute-cost accounting without validating it against the instruction's actual data size - (File: `runtime-transaction/src/signature_details.rs`)

### Summary
The Liferay advisory (CVE-2025-43793) is a case of CWE-1284 "Improper Validation of Specified Quantity in Input": a declared value (the effective TLD boundary) is trusted for a security-relevant decision without validating it against the actual structure it describes. The analogous pattern in Agave is `get_num_signatures_in_instruction`, which reads the first byte of a secp256k1/ed25519/secp256r1 precompile instruction as the "declared" signature count and uses it directly for fee and compute-unit accounting, without checking that the instruction's actual data length is large enough to contain that many signature-offset records.

### Finding Description
`get_num_signatures_in_instruction` simply reads `instruction.data[0]` as a `u64` count with no bound or size cross-check: [1](#0-0) 

This value is accumulated per program (`Secp256k1`/`Ed25519`/`Secp256r1`) into `PrecompileSignatureDetails` by `PrecompileSignatureDetailsBuilder::process_instruction`: [2](#0-1) 

This declared count feeds directly into both the compute-cost model (`CostModel::get_signature_cost`, using `SECP256K1_VERIFY_COST`/`ED25519_VERIFY_STRICT_COST`/`SECP256R1_VERIFY_COST`) and the fee calculation (`calculate_signature_fee`), both of which are computed *before* the precompile's own `verify()` routine ever runs and validates the data: [3](#0-2) [4](#0-3) 

By contrast, the actual precompile verification logic (`ed25519.rs`, `secp256k1.rs`, `secp256r1.rs`) does cross-validate the declared count against the real instruction size before trusting it, e.g.: [5](#0-4) [6](#0-5) 

The accounting path in `signature_details.rs`, which is used for both leader-side cost estimation (`CostModel::estimate_cost`) and post-hoc fee/cost calculation, has no equivalent check — it accepts `data[0]` as truth regardless of whether `instruction.data` actually contains enough bytes to back that many signature-offset structures.

### Impact Explanation
Because a single unprivileged transaction sender fully controls the precompile instruction's data bytes, they can set `data[0]` to an inflated value (up to 255) while supplying only minimal instruction data (e.g., 1–2 bytes) — a value that will be rejected by the real `verify()` function (`InvalidInstructionDataSize`) as soon as actual execution occurs. However, the inflated count is already baked into:
- the transaction's *estimated* compute-unit cost used by leader-side block-cost tracking/packing (`cost-model/src/cost_tracker.rs`, `cost_model.rs`) before execution ever runs, and
- the fee charged to the sender via `calculate_signature_fee`.

This creates a disconnect between the quantity used for cost/fee accounting and the quantity actually structurally present/verifiable in the instruction, which is precisely the CWE-1284 bug class cited in the report. This falls into the "leader-side cost limits" and "fee and compute-budget accounting" in-scope categories, since the mismatched accounting occurs purely from data supplied in a single submitted transaction and is exercised before any privileged or leader-only code path is involved.

### Likelihood Explanation
High reachability: any transaction containing a secp256k1/ed25519/secp256r1 program instruction reaches this code path during normal sanitization/cost-estimation, with no special privilege required. Crafting the mismatched `data[0]` vs. `data.len()` is trivial and entirely at the sender's discretion.

### Recommendation
Make `get_num_signatures_in_instruction` (or its caller) validate that `instruction.data.len()` is consistent with the declared count using the same `SIGNATURE_OFFSETS_START` / `SIGNATURE_OFFSETS_SERIALIZED_SIZE` arithmetic already used in the corresponding `verify()` functions, clamping the count to zero (or otherwise not counting it toward cost/fee) when the data is too short to back it. This aligns the accounting path with the verification path so a declared quantity can never diverge from the actually-present structure size.

### Proof of Concept
1. Construct a transaction containing an instruction whose `program_id` is `secp256r1_program::ID` with `data = [255]` (i.e., `num_signatures = 255`, but no signature-offset records actually present).
2. During transaction ingestion, `PrecompileSignatureDetailsBuilder::process_instruction` reads `data[0] = 255` and adds `255` to `num_secp256r1_instruction_signatures`, independent of the fact that `data.len() == 1` is far too small to contain any `Secp256r1SignatureOffsets`. [7](#0-6) 
3. `CostModel::get_signature_cost` and `calculate_signature_fee` both compute cost/fee as if 255 real secp256r1 verifications will occur (`255 * SECP256R1_VERIFY_COST` CU and `255 * lamports_per_signature` fee), before the transaction is ever executed. [8](#0-7) 
4. Only later, during actual instruction processing, does `precompiles/src/secp256r1.rs::verify` reject the instruction (`data.len() < expected_data_size` → `InvalidInstructionDataSize`), meaning no real cryptographic verification work is ever performed despite the inflated cost/fee already having been assessed based on the unvalidated declared count. [9](#0-8)

/// Calculate fees from signatures.
pub fn calculate_signature_fee(
    SignatureCounts {
        num_transaction_signatures,
        num_ed25519_signatures,
        num_secp256k1_signatures,
        num_secp256r1_signatures,
    }: SignatureCounts,
    lamports_per_signature: u64,
) -> u64 {
    let signature_count = num_transaction_signatures
        .saturating_add(num_ed25519_signatures)
        .saturating_add(num_secp256k1_signatures)
        .saturating_add(num_secp256r1_signatures);
    signature_count.saturating_mul(lamports_per_signature)
}
