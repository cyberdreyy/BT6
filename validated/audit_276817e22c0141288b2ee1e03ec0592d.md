### Title
Confirmations retained after a signer key is deleted allow request execution below the effective live-member threshold - (File: multisig/src/lib.rs)

### Summary
In the `multisig` contract, confirmations are recorded per `PublicKey` in the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map [1](#0-0) . When a key is revoked via the `DeleteKey` multisig action, the contract only purges requests that were *authored* by that key and its `num_requests_pk` entry — it never scans other requests' `confirmations` sets to strip the deleted key's prior confirmation [2](#0-1) . As a result, a confirmation cast by a key while it was a valid signer remains counted toward `num_confirmations` even after that key is deleted, so a request can be executed once the confirmation count reaches the threshold with fewer than `num_confirmations` still-authorized keys actually agreeing.

### Finding Description
`confirm()` checks only that the signer's key hasn't already confirmed and that the running count reaches `num_confirmations`; it never re-validates that the previously stored public keys in the confirmations set are still active multisig keys: [3](#0-2) 

The `DeleteKey` action's cleanup logic is: [2](#0-1) 

It removes only `self.requests`/`self.confirmations` entries for requests whose `signer_pk == pk` (i.e., requests *added* by the deleted key), and removes `num_requests_pk` for that key. It does **not** iterate over `self.confirmations` to remove `pk` from confirmation sets of other pending requests that this key previously *confirmed* (but did not author).

This breaks the intended binding: "confirmations counted == confirmations from currently-live members." After a key is deleted, its stale confirmation on any request it participated in (but did not create) continues to count toward the `num_confirmations` threshold in `confirm()`'s `confirmations.len() as u32 + 1 >= self.num_confirmations` check.

### Impact Explanation
This is a Critical-class issue per the accepted impact categories: "a multisig request executed below threshold." An action (e.g. `Transfer`, `AddKey`/full-access-key grant, `FunctionCall`) can be executed with fewer genuinely live/authorized confirmations than `num_confirmations` requires, because a revoked key's stale confirmation is silently retained and counted. This can lead to unauthorized fund transfers or privilege escalation (e.g., adding a full-access key) approved by a quorum that no longer holds the required number of active keys.

### Likelihood Explanation
Likelihood is Medium: it requires (a) a request pending confirmation, (b) that request already confirmed by one or more keys, and (c) one of those confirming keys subsequently removed via a `DeleteKey` action (a legitimate, expected multisig operation — e.g., during routine key rotation or after a suspected key compromise). This is a normal operational sequence for any multisig that rotates keys, not a contrived edge case, and does not require compromising any key beyond the ones the multisig already trusts.

### Recommendation
When executing `MultiSigRequestAction::DeleteKey`, also iterate all entries of `self.confirmations` and remove the deleted `pk` from every confirmation `HashSet`, not just from requests it authored. Alternatively, re-validate at confirmation-count time (in `confirm()`) that every public key in the stored confirmation set is still a valid/registered multisig key, discarding stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Multisig contract initialized with `num_confirmations = 3` and keys `K1, K2, K3, K4` all having full access to the contract account (predecessor == current account).
2. `K1` calls `add_request` to create a `Transfer` request `R` (receiver: attacker-controlled or colluding account).
3. `K2` calls `confirm(R)` → confirmations = {K2}. `K3` calls `confirm(R)` → confirmations = {K2, K3} (2 of 3, not yet executed since `2+1 >= 3` only holds once a 3rd confirm is submitted).
4. Separately, the group legitimately revokes `K3` (suspected compromise) via a new request+confirmations that executes `MultiSigRequestAction::DeleteKey { public_key: K3 }`. Per `execute_request`, this only removes requests where `signer_pk == K3` (i.e., requests K3 authored) and clears `num_requests_pk` for K3 [2](#0-1) . Request `R`'s confirmation set still contains K3, since K3 did not author R.
5. `K4` (or even a re-confirming `K1`) calls `confirm(R)` → confirmations.len() == 2 (K2, K3) + 1 == 3 == `num_confirmations`, so `execute_request` fires the `Transfer`, even though `K3` is no longer an authorized key. Only two currently-live keys (K2 and K4/K1) actually approved, one fewer than the configured threshold of 3.

Note: I could not execute this against a live/deployed instance (no runtime access in this environment); the sequence above is derived directly from the code paths in `confirm()` and `execute_request()`/`DeleteKey` cleanup shown above.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
