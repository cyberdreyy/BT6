### Title
Instant-withdraw receipts leave stale per-epoch claim basis after funding, enabling a double payout from the default-recovery reserve - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a missing cleanup on an exit path: `nvmet_alloc_ctrl()` took an error branch that skipped freeing an already-allocated resource. The analog in `IdleCreditVault` is the symmetric flaw: `claimInstantWithdrawRequest` pays out a funded instant receipt but only clears the aggregate `instantWithdrawsRequests[_user]` — it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`. If that same epoch later defaults and recovery is finalized with `defaultRecoveryEpoch == epochNumber`, `_claimDefaultedInstantWithdrawRequest` reads the stale per-epoch basis and pays the user a second time out of `defaultRecoveryReserve`, diluting or draining honest defaulted-epoch claimants.

### Finding Description
`requestInstantWithdraw` records basis in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` (IdleCreditVault.sol:366-374). The funded-claim path clears only the first:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` are left populated. By contrast, the normal withdraw path clears per-epoch entries via `_clearWithdrawClaimForEpoch` (IdleCreditVault.sol:815-836), and the defaulted instant path clears its own basis (IdleCreditVault.sol:847-853). The funded instant path is the only one that leaks the per-epoch record.

Later, `_claimDefaultedInstantWithdrawRequest` (IdleCreditVault.sol:842-856) computes `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` — non-zero for our attacker — burns the receipt tokens (which still exist conceptually? No: the receipt tokens were already burned at the funded claim). The burn `_burn(_user, claimBasis)` at line 854 would revert on insufficient balance... unless the attacker holds enough newly minted receipt tokens. The attacker can satisfy this by opening a *new* request in the same epoch after claiming the first (instant requests are allowed repeatedly during the epoch), so they hold fresh receipt tokens ≥ the stale basis. The claim then pays `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL` from the recovery reserve for basis that was already paid at par.

### Impact Explanation
Direct theft of recovery funds. The attacker receives a second payout on already-settled basis, funded by `defaultRecoveryReserve`, which is sized to satisfy genuine defaulted-epoch claimants. Every wei the attacker extracts beyond the real unfunded remainder is taken from honest users' recovery proceeds (or the reserve is inflated by the stale `instantWithdrawClaimsByEpoch` entry, in which case the haircut ratio `defaultRecoveryPrice` is computed against phantom claims and other claimants are underpaid). Broken invariant: one receipt, one payout.

### Likelihood Explanation
Requires: instant-withdraw mode enabled (non-programmable pools), the attacker claiming a funded instant receipt, re-requesting so they hold receipt tokens, and the borrower defaulting in the same epoch with recovery finalized. The attacker cannot cause the default (borrower is honest), so this is opportunistic: an attacker keeps a stale-claim position ready and only exercises it when a default occurs. Medium likelihood, medium-high impact when it lands.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch bookkeeping alongside the aggregate: locate the epoch(s) backing `instantWithdrawsRequests[_user]` (or track the request epoch like `lastWithdrawRequest`), zero `instantWithdrawsRequestsByEpoch[_user][epoch]` and decrement `instantWithdrawClaimsByEpoch[epoch]`, mirroring `_clearWithdrawClaimForEpoch`.

### Proof of Concept
Foundry fork sketch (contracts/strategies/idle/IdleCreditVault.sol):
1. Deploy `IdleCDOEpochVariant` + `IdleCreditVault` with instant withdraws enabled; user `A` deposits AA, `startEpoch`.
2. `A` calls `cdo.requestInstantWithdraw` (or the CDO instant path) → `requestInstantWithdraw` records `instantWithdrawsRequestsByEpoch[A][N]` and mints receipt tokens.
3. Borrower/CDO funds instant claims (`collectInstantWithdrawFunds`); `A` calls `claimInstantWithdrawRequest` — paid at par, aggregate zeroed, per-epoch basis still N → stale.
4. `A` requests instant withdraw again in epoch N (fresh receipt tokens ≥ stale basis).
5. Borrower defaults; manager calls `stopEpochWithDuration`/`finalizeDefault` + `finalizeDefaultRecovery` → `defaultRecoveryEpoch = N`, `defaultInstantWithdrawsFinalized = true`.
6. `A` calls `claimInstantWithdrawRequest` → `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[A][N]` and pays recovery on already-settled basis.

Caveat I could not fully verify within available iterations: the exact sizing of `defaultRecoveryReserve` relative to `instantWithdrawClaimsByEpoch` in `finalizeDefaultRecovery` (in `IdleCDOEpochVariant.sol`), which determines whether the theft drains the reserve directly or dilutes the recovery price — either way it is theft of unclaimed yield from other claimants.
