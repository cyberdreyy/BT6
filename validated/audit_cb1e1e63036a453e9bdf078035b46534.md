### Title
Programmable-borrower ERC4626 vault losses are floored at zero in `totalInterestDueNow`, so withdrawals are paid at pre-loss NAV and early claimants drain the pool - (contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
When `IdleCDOEpochVariant` runs in programmable-borrower mode, the realized epoch interest is read from `ProgrammableBorrower.totalInterestDueNow()`. That function nets the external ERC4626 vault sleeve's PnL against borrower/buffer gains but floors the result at zero. A loss in the external vault that exceeds epoch gains is never reported to the CDO, never haircuts pending withdraw receipts (`_lossAmount` is always 0 on the `stopEpoch` path), and never reduces tranche NAV — NAV is counted purely in CDO-held strategy tokens. Withdrawals continue to be priced and funded at pre-loss par value until the borrower simply cannot fund a pull, at which point the pool defaults. First-come withdrawers are paid in full out of remaining vault liquidity; later holders inherit the entire shortfall.

### Finding Description
In `IdleCDOEpochVariant._stopEpoch`, the pool-facing interest is resolved via `_resolveStopEpochInterest` → `IProgrammableBorrower(_borrower()).totalInterestDueNow()`. In `ProgrammableBorrower`:

```solidity
uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
return totalGain > loss ? totalGain - loss : 0;
```
`contracts/strategies/idle/ProgrammableBorrower.sol` (`totalInterestDueNow` / `_vaultNetInterest`). If the external vault position is impaired (e.g., bad debt/liquidation inside the MetaMorpho-style vault) so that `earnedAssets + epochWithdrawnFromVault < epochStartVaultAssets + epochDepositedToVault`, the shortfall is only netted against *gains*. Once `loss > totalGain`, the function returns 0: the loss beyond gains never surfaces to the CDO.

The CDO's NAV is unaffected because `IdleCDOCreditVault.getContractValue()` counts `strategyToken` balance (minted 1:1 at deposit), not the borrower's real collateral:

```solidity
return _contractTokenBalance(strategyToken) + _contractTokenBalance(token) - unclaimedFees;
```
`contracts/IdleCDOCreditVault.sol`. There is no burn or reprice of strategy tokens when the vault sleeve loses principal.

Pending withdraw receipts are also not haircut: in `_stopEpoch`, `previewLossAdjustedWithdrawFunds(_lossAmount)` is called with `_lossAmount = 0` (only `stopEpochWithDuration` accepts a non-zero loss, and that is not the programmable flow), so `collectWithdrawFunds` funds `pendingWithdraws` at full basis. Meanwhile `ProgrammableBorrower.onStopEpoch` happily withdraws `shortfall` from the impaired vault as long as `shortfall <= _currentVaultAssets()` — i.e., it pays pending receipts out of already-damaged collateral, leaving the residual LP claims less backed than NAV claims.

Net effect, mirroring the Blueberry SoftVault report: pool "balances" (tranche NAV and pending receipts) are tracked at par while the real underlying position has shrunk, so redemptions are effectively first-come-first-served over a deficit pool. Early withdrawers receive full underlying value; once the remaining sleeve cannot cover a later `_amountToPullFromBorrower + _pendingWithdraws`, `getFundsFromBorrower` reverts and `_handleBorrowerDefault` triggers — the loss is dumped entirely on whoever did not exit first.

### Impact Explanation
- Any tranche holder (KYC-passing lender) who requests withdrawal after an external vault impairment but before the deficit is realized exits at pre-loss `virtualPrice`, receiving more than their fair share.
- Remaining LP claims become undercollateralized with no accounting signal (`virtualPrice`/`lastNAV` stay inflated); the loss is eventually crystallized as a borrower default borne entirely by those who didn't exit — direct loss of fair share of funds, up to the full vault impairment beyond accrued gains.
- The same applies to instant withdrawals: `requestInstantWithdraw` receipts are funded from `totUnderlyings` at `startEpoch` at par value even though the sleeve backing them is impaired.

### Likelihood Explanation
- Requires a programmable-borrower deployment with an external ERC4626 vault sleeve and an impairment event in that vault (e.g., bad debt from a borrower liquidation in the underlying Morpho markets). Such events are normal tail risk for credit vaults; no privileged or malicious action is needed to create the condition.
- Exploitation only needs the unprivileged action of calling `requestWithdraw`/`claim*` earlier than other LPs — pure ordering advantage, exactly the "earlier withdrawers steal deposits of late withdrawers" pattern from the reference report.
- Existing guards do not stop it: `_skimDonatedAssets` is irrelevant, `Default` revert only fires on NAV-visible losses (none here), `onStopEpoch` deliberately returns success when vault shares *can* still cover the immediate pull, and `previewLossAdjustedWithdrawFunds` receives `_lossAmount = 0` so receipts are never haircut on the normal stop path.

### Recommendation
Do not floor vault losses at zero for pool accounting. Options:
- In `ProgrammableBorrower`, report the full signed vault delta (allow `totalInterestDueNow` semantics to convey principal impairment, or expose `vaultLoss()` and have `IdleCDOEpochVariant._stopEpoch` pass it as `_lossAmount` to `previewLossAdjustedWithdrawFunds`/`collectWithdrawFunds`) so pending receipts are haircut pro rata and the active-side loss is applied BB-first via `_updateAccounting`.
- Alternatively, burn a proportional amount of CDO-held strategy tokens at `stopEpoch` to reflect vault principal losses in `getContractValue`, so `virtualPrice` drops for all tranche holders before further withdrawals can be priced at par.

### Proof of Concept
Foundry fork sketch against the programmable-borrower credit vault (pattern follows `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// Setup: programmable borrower vault, isInterestMinted = true
vm.prank(owner);
cdoEpoch.setIsInterestMinted(true);

// User A (attacker) and User B each deposit equal AA
uint256 amount = 10_000 * oneScale;
idleCDO.depositAA(amount);           // attacker
_depositWithUser(userB, amount, true);

_startEpochAndCheckPrices(0);        // idle cash parked into ERC4626 vault

// --- Impair the external vault sleeve beyond epoch gains ---
// Simulate a loss > totalInterestDueNow by removing vault shares
// (analogous to bad debt in the underlying lending market)
uint256 shares = morphoVault.balanceOf(address(programmableBorrower));
programmableBorrower.rescueTokens(address(morphoVault), sink, shares * 3 / 4);

// Precondition: vault loss exceeds gains so totalInterestDueNow() == 0,
// yet cdoEpoch.virtualPrice(aaTranche) still reports ~par NAV.
assertEq(programmableBorrower.totalInterestDueNow(), 0);
assertGt(programmableBorrower.vaultLoss(), 0);

// Attacker requests withdrawal at pre-loss price
uint256 reqA = cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)), address(aaTranche));

// Attacker front-runs startEpoch processing via instant withdrawal;
// onStopEpoch funds pending receipts from the damaged sleeve because
// shortfall <= _currentVaultAssets() — receipt paid at full basis.
// ...warp epochEndDate, manager calls stopEpoch(0,0) which succeeds...
// attacker claims `reqA` underlyings in full.

// Later, userB's claim is unbacked: NAV still shows par, but the sleeve is
// short; the next large pull fails -> getFundsFromBorrower reverts ->
// _handleBorrowerDefault, and userB absorbs the entire vault loss.
```
