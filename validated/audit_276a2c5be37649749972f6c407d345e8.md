### Title
Fail-open "assume higher" fallback in `check_latest_block_in_tenure` is reused in a signing-time recheck that must fail closed - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_latest_block_in_tenure` deliberately treats a failed `get_tenure_tip` RPC call as if the check had passed ("assume higher"), on the documented rationale that the proposal will still be independently validated by the node's `/v3/block_proposal` endpoint. That rationale is only true the *first* time the function runs (at proposal arrival). The same function is reused, via `check_block_against_signer_db_state`, as the *signing-time* recheck that runs after node validation has already happened, whose entire purpose is to catch state changes that occurred while validation was in flight. At that later call site the original safety net no longer exists, so a transient node-connectivity failure at exactly this recheck silently converts "we could not verify" into "verified OK," letting the signer proceed to sign a block it never actually re-confirmed.

### Finding Description
`check_latest_block_in_tenure` documents and implements a fail-open default:

<cite repo="ThankGod76/stacks-core--008" path="stacks-signer/src/chainstate/mod.rs" start="366="374 /> [1](#0-0) 

If the signer's own `signer_db` lookups (`get_tenure_last_block_info`, `get_last_accepted_block`) don't find a conflicting block — for example because gossip of a competing signer's pre-commit/signature was dropped or delayed — the function falls through to asking the node for the tenure tip. When that RPC fails for any reason, the code returns `Ok(true)`, i.e. "the check passes," instead of failing closed.

This function is exposed through `check_tenure_change_confirms_parent` and `confirms_latest_block_in_same_tenure`, both wired into `check_block_against_signer_db_state`: [2](#0-1) 

The docstring itself flags the danger: this check is explicitly meant to be run *after* the node has already validated the block, to catch drift. It is invoked from `handle_block_validate_ok` right before the block is marked pre-committed and pre-commits are broadcast: [3](#0-2) 

and, per the documented flow, again at the pre-commit-threshold "RECHECK" step immediately before a signature is produced (section 5 of `docs/signer-flows.md`): [4](#0-3) 

At this second, signing-time use, the "the node's proposal endpoint is the backstop" justification from the original docstring no longer applies — the node already validated the block once; this recheck exists specifically because circumstances can change between validation and signing (e.g. a sibling block winning the race). Contrast this with the deliberately fail-closed treatment of the same class of failure elsewhere in the signer, e.g. `conflict_still_blocks`, which explicitly keeps a conflict blocking whenever the node is unreachable, precisely because "wrongly signing cannot be taken back": [5](#0-4) [6](#0-5) 

This is the direct analog to the reported bug class: a check whose non-answer ("could not verify") is silently treated as "success," misleading the caller (here, the signer) about whether an actual verification occurred, in a context where the fallback's original safety justification does not hold.

### Impact Explanation
If the fallback fires during the signing-time recheck (validate-ok path or pre-commit-threshold RECHECK), the signer treats an unverifiable state as "still consistent" and proceeds to `mark_pre_committed`/eventually sign, without having actually confirmed the block still confirms the tenure's true latest tip. In a sibling-block race — two conflicting tenure-start (or same-height) blocks proposed by one miner, each pre-committed/signed by different subsets of signers because of normal gossip propagation delay — this can let a signer sign a block that conflicts with one already globally accepted elsewhere, i.e. a signer signing a non-canonical/conflicting block. That is a Critical-class outcome per the stated impact criteria.

### Likelihood Explanation
This requires two coincident but individually ordinary conditions: (1) a genuine sibling/competing-block race, which a single miner can create unilaterally by proposing two conflicting blocks at the same height/tenure (the codebase's own test suite explicitly exercises `run_sibling_scenario`), combined with a signer's local DB not yet reflecting the other block's acceptance (delayed/lossy gossip, which the code elsewhere treats as a normal, expected occurrence — see the "outdated peer" handling in `handle_block_response`); and (2) a transient failure of the `get_tenure_tip` RPC to the signer's own node occurring at exactly the recheck moment. Condition (2) is not directly attacker-controlled and depends on node/network reliability, so this is a real but timing-dependent race rather than a deterministically triggerable exploit.

### Recommendation
Make the signing-time reuse of `check_latest_block_in_tenure` fail closed when the node is unreachable, matching the pattern used in `conflict_still_blocks`. Concretely, either: (a) split the function so the proposal-arrival call site keeps the "assume higher" fallback (justified by the downstream node validation) while the post-validation recheck call sites (`check_block_against_signer_db_state`) return "check failed / do not sign" (or "wait/retry") on RPC failure; or (b) thread a flag distinguishing "pre-validation" vs "post-validation/signing" contexts into `check_latest_block_in_tenure` and choose the safe default accordingly.

### Proof of Concept
1. Miner proposes two conflicting blocks, A and B, at the same height in the same tenure.
2. Signer S receives A, validates it via the node, marks it pre-committed, broadcasts its pre-commit for A.
3. Other signers converge on B and sign it; B becomes globally accepted. The gossip carrying that information to S is dropped/delayed, so `get_last_signed_block`/`get_last_accepted_block` in S's local `signer_db` still show no conflict for A.
4. More delayed pre-commits for A (from signers who also missed B's outcome) arrive at S and push A's pre-commit weight over the 70% threshold, triggering the `RECHECK` step (`check_block_against_signer_db_state` → `check_latest_block_in_tenure`).
5. At that exact moment, S's call to `client.get_tenure_tip` fails (transient RPC error/timeout). Per `stacks-signer/src/chainstate/mod.rs:450-461`, the function returns `Ok(true)` ("assume higher") instead of failing the check.
6. S proceeds to sign A, producing a valid signature on a block that conflicts with the already globally accepted B — the exact safety violation the RECHECK step exists to prevent.
