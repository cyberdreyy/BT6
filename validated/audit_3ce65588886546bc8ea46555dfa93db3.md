### Title
Stale confirmations from a removed multisig member allow request execution below `num_confirmations` live members - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` only purges confirmations for requests that the removed member *originally created* (`r.member == member`), not for other pending requests that the removed member had merely *confirmed*. As a result, a member's confirmation string can remain in another request's `confirmations: HashSet<String>` after that member is deleted, letting `confirm` count a non-member's stale confirmation toward `num_confirmations` and execute a `Transfer` (or any other action) with fewer genuinely live confirmations than required.

### Finding Description
The binding the contract is supposed to enforce is:

`count(m in self.confirmations[R] such that m ∈ self.members) == self.num_confirmations` before `execute_request(R)` fires.

In practice, `confirm` only checks the raw set size: [1](#0-0) 
`confirmations.len() as u32 + 1 >= self.num_confirmations` is evaluated against the stored `HashSet<String>` without re-validating that every entry in it is still `self.members.contains(...)`.

`delete_member` removes stale state only for requests *created by* the removed member, not requests they merely *confirmed*: [2](#0-1) 
The `request_ids` filter matches on `r.member == member` (the request's originating signer), so a request `R` created by `alice` and confirmed by `bob` is untouched when `bob` is deleted — `bob`'s entry in `self.confirmations[R]` (added at line 311 during `bob`'s earlier `confirm` call) is never removed.

Exploit flow:
1. Deploy a multisig via `MultisigFactory::create` (or `MultiSigContract::new`) with members `[Account{alice}, Account{bob}, Account{carol}]`, `num_confirmations = 2`.
2. `alice` calls `add_request` with a `Transfer{amount}` action targeting some receiver → request `R` (`R.member == alice`).
3. `bob` calls `confirm(R)` → `confirmations[R] = {bob}` (1 < 2, not yet executed).
4. Members confirm and execute a `DeleteMember{member: Account{bob}}` request (via `alice` + `carol`, i.e. without `bob`). `delete_member` runs and, because `R.member == alice != bob`, `R`'s `confirmations` entry is left untouched (still contains `"bob"`), while `self.members` no longer contains `bob`.
5. `carol` calls `confirm(R)`. `assert_valid_request` and the "already confirmed" check both pass (they check `carol`, not `bob`). `confirmations.len() as u32 + 1 == 2 >= num_confirmations`, so `execute_request(R)` fires the `Transfer`, even though only `carol` is a currently-live confirming member; `bob`'s stale entry supplied the second "confirmation."

None of the existing guards (`assert_valid_request`, `assert_self_request`, the "already confirmed" check) validate that entries already stored in `confirmations` still belong to `self.members`, so the divergence goes undetected.

### Impact Explanation
NEAR is moved out of the multisig contract account via a `Transfer` (or any other request action, including `AddKey`/`FunctionCall`) that is executed with fewer than `num_confirmations` currently-live members having actually approved it. This directly matches the Critical category "a multisig request executed below `num_confirmations` live members." It is repeatable for any multisig instance (created by any user via the factory) whenever a member who previously confirmed a still-pending request is later removed via `DeleteMember` — a normal, expected admin operation (e.g., revoking a departing or compromised signer) — without the deployer realizing the pending request's approval count is now inflated by a phantom signer.

### Likelihood Explanation
This requires no special privilege beyond what any deployer/user of a multisig already has: create a multisig with ≥3 members via the public factory, have one member confirm a pending request, then remove that member through the standard `DeleteMember` flow before the request is otherwise resolved. This is a plausible and low-cost sequence (e.g., revoking access after suspected compromise, or an insider deliberately arranging the ordering to under-collect real approvals). It is deterministic and reproducible in a unit test with `testing_env!`.

### Recommendation
When executing `DeleteMember`, scan all pending requests' `confirmations` sets (not just those authored by the removed member) and remove the deleted member's identifier from every one of them; alternatively, when tallying confirmations in `confirm`, filter `confirmations.get(&request_id)` against `self.members` before counting/comparing to `num_confirmations`.

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_after_delete_member() {
    // 1. Setup multisig with alice, bob, carol; num_confirmations = 2
    testing_env!(context_with_account(alice(), amount));
    let mut c = MultiSigContract::new(
        vec![
            MultisigMember::Account { account_id: alice() },
            MultisigMember::Account { account_id: bob() },
            MultisigMember::Account { account_id: carol() },
        ],
        2,
    );

    // 2. alice creates Transfer request R (R.member == alice)
    let r_id = c.add_request(MultiSigRequest {
        receiver_id: some_receiver(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    });

    // 3. bob confirms R -> confirmations[R] = {bob}, not yet executed
    testing_env!(context_with_account(bob(), amount));
    c.confirm(r_id);
    assert_eq!(c.confirmations.get(&r_id).unwrap().len(), 1);

    // 4. alice + carol create & confirm DeleteMember{bob}
    testing_env!(context_with_account(alice(), amount));
    let del_id = c.add_request(MultiSigRequest {
        receiver_id: alice(), // current_account_id in this context setup
        actions: vec![MultiSigRequestAction::DeleteMember {
            member: MultisigMember::Account { account_id: bob() },
        }],
    });
    testing_env!(context_with_account(carol(), amount));
    c.confirm(del_id); // executes delete_member, removes bob from self.members

    // Binding check (LHS): live confirmers for R should now be 0, not 1
    let stale_confirmations = c.confirmations.get(&r_id).unwrap();
    assert!(stale_confirmations.contains(&MultisigMember::Account{account_id: bob()}.to_string()));
    assert!(!c.get_members().contains(&MultisigMember::Account { account_id: bob() }));

    // 5. carol confirms R -> should NOT execute (only carol is live-confirmed == 1 < 2)
    //    but current code executes because stale bob entry inflates the count.
    let result_before = c.requests.get(&r_id).is_some();
    c.confirm(r_id);
    let result_after = c.requests.get(&r_id).is_some();

    assert!(result_before, "request should still be pending before carol confirms");
    assert!(!result_after, "BUG: request executed with only 1 live confirmation (carol) against num_confirmations=2, using bob's stale entry");
}
```
This demonstrates `execute_request` firing (request removed from `self.requests`, `Promise::transfer` scheduled) while only one currently-live member (`carol`) actually approved `R`, violating the intended `num_confirmations` guarantee.

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
