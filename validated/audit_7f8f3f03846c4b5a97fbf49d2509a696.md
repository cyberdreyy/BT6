Stale confirmations from removed multisig members are not purged from requests they did not create, letting `confirm` execute below the true live-member threshold - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::delete_member` only deletes requests (and their confirmation sets) whose *original creator* (`r.member`) equals the member being removed; it never scans `self.confirmations` to strip the removed member's confirmation entry from requests **created by other members**. Because `confirm` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` with no re-validation that every entry in the confirmations set still belongs to `self.members`, a stale confirmation cast by a now-removed (and possibly later re-added) member is silently counted toward execution, allowing `execute_request` (including `Transfer`) to fire with fewer than `num_confirmations` distinct confirmations from members who were continuously members through execution.

### Finding Description
Binding that should hold: `confirmers_counted_at_execution == |{ m in self.members : m confirmed request_id while continuously a member up to execution }|`.

Code path:
- `add_request` creates `MultiSigRequestWithSigner { member: current_member, .. }` and an empty confirmation `HashSet`: [1](#0-0) 
- `confirm` inserts the caller's member string into the request's confirmation `HashSet` and, once the set size hits `num_confirmations`, calls `execute_request` with no check that existing entries in the set are still current members: [2](#0-1) 
- `delete_member` only removes requests/confirmations for requests where `r.member == member` (i.e. requests the removed member *created*); it does not scan other requests' confirmation sets to remove the departing member's confirmation entries there: [3](#0-2) 

Exploit flow (attacker is not required to be privileged beyond being a legitimate multisig member at the time they confirm, which is within the described scope since the finding concerns the accounting binding, not privilege escalation by an outsider):
1. Multisig with members `A, B, C, D`, `num_confirmations = 3`.
2. `A` creates a `Transfer` request (`request_id`) and self-confirms → confirmations = `{A}`.
3. `B` confirms → confirmations = `{A, B}` (len 2, `<3`, not yet executed).
4. Members `A, C, D` (3 confirmations, satisfying `num_confirmations`) approve a `DeleteMember { member: B }` request. `delete_member` runs its filter over `self.requests` looking for requests where `r.member == B`; since `request_id`'s creator is `A`, it is skipped — `self.confirmations.get(&request_id)` still equals `{A, B}` even though `B` is no longer in `self.members`.
5. `C` now calls `confirm(request_id)`. `confirmations.len() + 1 = 3 >= num_confirmations`, so `execute_request` fires the `Transfer` even though only `A` and `C` were continuously members through confirmation and execution — `B`'s confirmation, cast while a member but never invalidated after removal, is silently reused.
6. Optionally, re-adding `B` afterward via a fresh `AddMember` makes `B` a "current" member again at the moment of execution, but this doesn't change the root cause: the stale HashSet entry was never re-validated, it is the same code path with or without re-addition.

Existing guards do not catch this: `assert_valid_request` only checks the caller is currently a member and that the request/confirmation maps exist; it does not audit every entry inside the confirmation `HashSet` against `self.members`. [4](#0-3) 

### Impact Explanation
This allows a `Transfer` (or any other `MultiSigRequestAction`, including `AddKey`/`DeleteMember`/`FunctionCall`) to execute with fewer than `num_confirmations` confirmations from members who were continuously part of `self.members`, moving NEAR out of the multisig account without the required live-member consensus. This matches the Critical category "a multisig request executed below `num_confirmations` live members." The blast radius is any multisig deployed via this contract with membership churn (any `DeleteMember` action on a member who has outstanding confirmations on requests they didn't create).

### Likelihood Explanation
Preconditions are simple and achievable by legitimate members without any external attacker privilege: an outstanding request confirmed by fewer than `num_confirmations` members, followed by a `DeleteMember` action against one of the confirmers (not the request's creator), followed by one more confirmation from a still-current member. No unusual balances, no timing dependency beyond normal request cooldown for deletion, and it is fully repeatable across requests/members.

### Recommendation
In `delete_member`, iterate all entries of `self.confirmations` (not just requests created by the removed member) and remove the departing member's string from every confirmation `HashSet`; alternatively, in `confirm`, before counting/executing, filter the confirmation set down to entries that are still contained in `self.members` and only count/execute based on that filtered, live set.

    // yet execute_request fired using {alice, bob(stale), key_C} == 3.

        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key

            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
