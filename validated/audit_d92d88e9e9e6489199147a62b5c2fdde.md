### Title
Attacker can use a reorg to hijack a factory-deployed credit vault address and steal depositor funds - ([File: contracts/IdleCreditVaultFactory.sol](contracts/IdleCreditVaultFactory.sol))

### Summary
`IdleCreditVaultFactory.deployCreditVault` and `deployRevolvingCreditVault` are permissionless and deploy all vault components with `CREATE` (`_deployProxy` → `new TransparentUpgradeableProxy`), so each deployed `IdleCDOEpochVariant` / `IdleCreditVault` address depends only on the factory's nonce. On reorg-prone chains the factory targets (Polygon, Optimism, Arbitrum, Base, etc.), an attacker can observe a deployment tx in a reorged block, replay `deployCreditVault` first to consume the same nonce, and land a proxy at the exact same address — but bound to attacker-chosen, potentially malicious `implementation` / `underlying` / `manager` params. The honest depositor's subsequent `depositAA`/`depositBB` then funds the attacker's vault.

### Finding Description
In the external report, `Factory.deploySurgePool` uses `CREATE`, making pool addresses nonce-predictable and hijackable under a reorg. `IdleCreditVaultFactory` has the same shape, worse:

- `deployCreditVault` (line 92) and `deployRevolvingCreditVault` (line 126) are `external` with no access control — anyone can call them and consume factory nonces.
- `_deployProxy` (line 280) uses `new TransparentUpgradeableProxy(implementation, proxyAdmin, data)` — `CREATE`, so `vaultAddress = keccak(rlp(factory, nonce))`. The CDO proxy is the second `CREATE` inside the call, so its address is `keccak(rlp(factory, nonce+1))`, fully predictable.
- Critical security params are caller-supplied: `cvParams.implementation` (the CDO implementation the proxy delegates to), `strategyData.implementation`, `cvParams.underlying`, `cvParams.apr`, `strategyData.manager`, `ancillaryParams.keyring` (setting `keyring == address(0)` disables whitelist checks entirely, line 169). An attacker can pass a malicious implementation contract exposing `IdleCDOCreditVault.initialize` that simply skims any deposited underlying, while keeping `underlying` identical so deposit txs execute unchanged.

Attack sequence:
1. Honest deployer calls `deployCreditVault(...)`; a KYC'd depositor then calls `depositAA`/`depositBB` on the emitted/predicted CDO address.
2. A reorg drops both txs. Attacker calls `deployCreditVault` with the same `underlying` but malicious `implementation` (and `keyring = address(0)`), consuming the same nonce so the CDO proxy lands at the identical address.
3. The depositor's tx replays against the attacker's proxy at that address; the malicious implementation pulls/holds the underlying instead of deploying real vault logic.
4. Attacker drains the deposited tokens.

### Impact Explanation
Direct theft of depositor funds: every deposit routed to the hijacked address in the post-reorg window is lost. Unlike the Surge case (fixed pool logic, malicious collateral), here the attacker controls the implementation code itself, so the entire deposit is capturable. The fair-mint/solvency invariants never get a chance to apply because the deposit never reaches real vault code.

### Likelihood Explanation
Requires (a) a reorg deep enough to reorder a deployment and deposits, and (b) a depositor submitting a deposit to an address learned from the pre-reorg state. Both are the same assumptions accepted as Medium in the original report; idle-tranches deploys on the same reorg-prone L2s. The attack is cheap (one `deployCreditVault` call) and fully deterministic since only the nonce matters.

### Recommendation
Deploy the CDO/strategy proxies with `CREATE2` using a salt that commits to the deployment parameters and the deployer, e.g. `salt = keccak256(abi.encode(msg.sender, cvParams.implementation, underlying, apr, manager))`, so an attacker cannot land a differently-configured proxy at the same address. Alternatively restrict `deployCreditVault`/`deployRevolvingCreditVault` to the treasury/owner.

### Proof of Concept
Foundry test (no fork needed — the bug is in nonce-based addressing; a fork variant would replay on a Polygon/Arbitrum fork with `vm.rollFork`):

```solidity
// test/foundry/IdleCreditVaultFactoryReorg.t.sol
function test_ReorgHijackVaultAddress() public {
    // factory, underlying, creator, depositor as in IdleCreditVaultFactory.t.sol
    IdleCreditVaultFactory.CreditVaultParams memory honest = _makeCreditVaultParams(feeReceiver);
    honest.underlying = address(underlying);
    honest.implementation = address(new IdleCDOEpochVariant());

    // Depositor precomputes the CDO address the honest deploy will produce:
    // strategy proxy = nonce N, cv proxy = nonce N+1
    uint256 n = vm.getNonce(address(factory));
    address predictedCv = vm.computeCreateAddress(address(factory), n + 1);

    // --- simulated reorg: attacker deploys first with same params but
    // malicious implementation (a contract exposing initialize() that skims) ---
    MaliciousCDO evil = new MaliciousCDO();
    IdleCreditVaultFactory.CreditVaultParams memory evilParams = honest;
    evilParams.implementation = address(evil); // attacker-chosen code
    vm.prank(attacker);
    factory.deployCreditVault(evilParams, strategyData, ancillary);
    address hijackedCv = vm.computeCreateAddress(address(factory), n + 1); // same formula
    // hijackedCv == predictedCv for the honest user's deposit

    // Depositor's pre-signed/replayed deposit lands on the malicious proxy
    vm.startPrank(depositor);
    underlying.approve(hijackedCv, 1e18);
    MaliciousCDO(hijackedCv).depositAA(1e18); // skimmed by attacker's impl
    vm.stopPrank();
    assertEq(underlying.balanceOf(attacker), 1e18);
}
```

The malicious implementation only needs to mimic `initialize` + `depositAA` (pull `underlying` via `transferFrom` and forward to the attacker), which is unconstrained since `cvParams.implementation` is arbitrary caller input.
