### Title
Instant-withdraw receipt paid at par during the default-finalization gap, bypassing the recovery haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` only routes a defaulted-epoch instant receipt through the haircut path when *both* `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are set. During the window where default recovery is finalized but instant-withdraw finalization has not yet run, the function still pays the full aggregate `instantWithdrawsRequests[_user]` at par via `_transferFundedClaim`, smuggling a defaulted (haircut) receipt through the funded-claim path.

### Finding Description
The bug class of ALPINE-CVE-2022-32215 is ambiguous interpretation of a single request by two parsers (request smuggling). The analog here is the vault's dual receipt accounting: the aggregate counter `instantWithdrawsRequests[_user]` versus the per-epoch record `instantWithdrawsRequestsByEpoch[_user][epoch]` written in `requestInstantWithdraw` [1](#0-0) .

On claim, the code decides which "parser" interprets the receipt: [2](#0-1) 

```solidity
if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
  _claimDefaultedInstantWithdrawRequest(_user);
}
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_claimDefaultedInstantWithdrawRequest` is what applies `defaultRecoveryPrice` and spends the isolated `defaultRecoveryReserve` [3](#0-2) . It is skipped whenever `defaultInstantWithdrawsFinalized` is false, but `instantWithdrawsRequests[_user]` still contains the defaulted-epoch receipt, so it is paid at full value from the vault's non-reserve underlyings. The guard in `_transferFundedClaim` only requires `balance - reserve >= amount` [4](#0-3) , which does not distinguish a defaulted receipt from an honestly funded one — the same receipt is therefore settled twice-inconsistent: counted into the recovery pool at `defaultRecoveryEpoch` by finalization accounting, then paid again at par by the funded path.

The normal-withdraw path does not share this flaw: `claimWithdrawRequest` keys haircut claims off `defaultRecoveryFinalized` alone [5](#0-4) .

### Impact Explanation
An attacker holding an instant-withdraw receipt created in `defaultRecoveryEpoch` calls the CDO's instant-claim path after `finalizeDefault` but before instant-withdraw finalization is marked complete. They receive `claimBasis` at par instead of `claimBasis * defaultRecoveryPrice / RECOVERY_FULL`, over-withdrawing by the haircut amount. The payout comes from underlyings not inside `defaultRecoveryReserve`, i.e. funds earmarked for other pending withdrawers or the CDO — a direct, quantified theft of `claimBasis * (RECOVERY_FULL - defaultRecoveryPrice) / RECOVERY_FULL`. Additionally, the reserve share earmarked for that claim is never consumed by `_transferDefaultRecovery`, leaving `defaultRecoveryReserve` permanently overstated and stranding recovery assets.

### Likelihood Explanation
Exploitability hinges on a realizable ordering gap between `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized`. The existence of two separate flags, plus the code comment describing "older instant receipt already funded before default finalization," indicates they are set in distinct operations, so the window exists at minimum between the two admin calls (the caller roles are honest, but the sequencing gap is protocol state, not an admin mistake). The attacker only needs an instant receipt in the default epoch — obtainable by any KYC'd tranche holder via the instant-withdraw APR-drop path — and to sequence a claim inside the gap. If `defaultInstantWithdrawsFinalized` is set atomically inside the same transaction as `defaultRecoveryFinalized` (this could not be fully verified in the CDO-side `finalizeDefault`/`finalizeDefaultRecovery` flow within the search budget), the window collapses and the finding reduces to a defense-in-depth gap.

### Recommendation
Split the conditions: clear defaulted-epoch instant receipts whenever `defaultRecoveryFinalized` is true (or when `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch] != 0`), not only when `defaultInstantWithdrawsFinalized` is also set. Alternatively, revert instant claims while `defaultRecoveryFinalized && !defaultInstantWithdrawsFinalized` so no receipt can be interpreted by the funded parser until the default parser has run. Ensure the CDO's claim entrypoint cannot reach the vault between the two finalization flags.

### Proof of Concept
Foundry fork PoC sketch (mirroring `testClaimWithdrawRequestWithInstantDefault` in `test/foundry/IdleCreditVault.t.sol`):

```solidity
// setup: deposit AA, trigger APR drop, requestInstantWithdraw in epoch N
idleCDO.depositAA(amount);
cdoEpoch.requestWithdraw(trancheAmount, address(AAtranche)); // instant path
// borrower defaults -> manager calls _handleBorrowerDefault / finalizeDefault
// which sets defaultRecoveryFinalized = true and defaultRecoveryEpoch = N,
// but defaultInstantWithdrawsFinalized is still false.

// ATTACK: claim instant withdraw in the gap
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimInstantWithdrawRequest(); // routes through claimInstantWithdrawRequest
uint256 paidPar = underlying.balanceOf(attacker) - balPre;

uint256 expectedHaircut =
  claimBasis * strategy.defaultRecoveryPrice() / RECOVERY_FULL;
assertGt(paidPar, expectedHaircut); // haircut bypassed; funds stolen at par
```

The assertion that `paidPar > expectedHaircut` demonstrates the smuggled receipt; the delta is the loss borne by other claimants/LPs.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
```
