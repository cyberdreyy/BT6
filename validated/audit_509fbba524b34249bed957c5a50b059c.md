### Title
Loss-adjusted withdraw receipt escapes its haircut when the user files a later request — paid at par via `_claimFundedWithdrawRequest` (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
An invalid-free bug releases a resource that was already logically freed. The analog in `IdleCreditVault` is a stale per-epoch withdraw receipt: when `stopEpochWithDuration` realizes a loss, `collectWithdrawFunds` records a `lossRecoveryPriceByEpoch[epoch]` haircut, but the per-user receipt is only cleared through `_claimLossAdjustedWithdrawRequest`, which looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. Since `requestWithdraw` unconditionally overwrites `lastWithdrawRequest[_user]`, a second request in a later epoch permanently orphans the earlier loss-adjusted receipt, which is then paid at 100% par through `_claimFundedWithdrawRequest`. [1](#0-0) [2](#0-1) 

### Finding Description
- `requestWithdraw` adds to `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` and sets `lastWithdrawRequest[_user] = currentEpoch`. [3](#0-2) 
- On a partial-loss stop, `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber]` and pulls only the haircut-funded `_amount` into the strategy. [4](#0-3) 
- The only path applying that haircut is `_claimLossAdjustedWithdrawRequest`, keyed on `lastWithdrawRequest[_user]` — a single slot tracking only the *most recent* request epoch. If the user requested again in epoch N+1, `lossEpoch` resolves to N+1, `lossRecoveryPriceByEpoch[N+1] == 0`, and the loss path returns 0 without ever touching `withdrawsRequestsByEpoch[_user][N]`. [5](#0-4) 
- `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` (which still aggregates the epoch-N receipt) at par and burns it, because the epoch gate `epochNumber <= lastWithdrawRequest` is satisfied once epoch N+2 begins. [6](#0-5) 
- `_clearWithdrawClaimForEpoch` can only clear an epoch via the loss/default path, and it is never invoked for the orphaned epoch. [7](#0-6) 

Broken invariant: loss waterfall / one-receipt-one-payout. The epoch-N receipt was funded only `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, yet it is redeemed for `claimBasis`. The shortfall is paid out of the strategy's underlying balance that backs other users' funded claims; `_transferFundedClaim`'s reserve check protects only `defaultRecoveryReserve`, not other claimants' funded underlyings. [8](#0-7) 

### Impact Explanation
An unprivileged lender converts a haircut receipt into a par receipt, stealing `basis * (1 - lossRecoveryPrice)` of underlyings. Because the strategy only received the post-haircut amount for that epoch, the excess is drawn from funds earmarked for other pending/funded claimants — direct theft plus insolvency for last claimants. With a 50% `lossRecoveryPrice`, a 100k-underlying receipt yields a ~50k overpayment in a single claim.

### Likelihood Explanation
Requires a `stopEpochWithDuration` partial-loss epoch (honest manager action, an existing feature with explicit loss pricing), and the attacker merely calls `requestWithdraw` twice across epochs — a permitted, documented flow ("requests another withdraw... wait another epoch"). No privileged misbehavior, no oracle manipulation. The orphaned-receipt gap is deterministic once both conditions hold.

### Recommendation
Track loss-adjusted claims per epoch rather than via `lastWithdrawRequest`. In `_claimLossAdjustedWithdrawRequest`, iterate or check `lossRecoveryPriceByEpoch` for every epoch present in `withdrawsRequestsByEpoch[_user]` (or store a per-user set of loss epochs), and ensure `_claimFundedWithdrawRequest` excludes any epoch with a nonzero `lossRecoveryPriceByEpoch`. Alternatively, settle/clear prior loss-epoch receipts inside `requestWithdraw` before overwriting `lastWithdrawRequest`.

### Proof of Concept
Foundry fork PoC sketch (based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testLossReceiptEscapesHaircut() external {
    uint256 amount = 100_000 * ONE_SCALE;
    address attacker = makeAddr("attacker");

    _depositWithUser(attacker, amount, true);
    uint256 trancheBal = IERC20(AAtranche).balanceOf(attacker);

    // Epoch N: request withdraw, then manager stops with a realized loss
    vm.prank(attacker);
    uint256 receiptN = cdoEpoch.requestWithdraw(trancheBal / 2, address(AAtranche));
    _startEpochAndCheckPrices(0);
    // stopEpochWithDuration(_lossAmount) -> collectWithdrawFunds(partial)
    // => lossRecoveryPriceByEpoch[N] = e.g. 50%
    _stopEpochWithLoss(receiptN / 2); // helper: borrower funds only half

    // Epoch N+1: attacker files a second request -> lastWithdrawRequest overwritten
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBal / 4, address(AAtranche));
    _startEpochAndCheckPrices(1);
    _stopEpochAndCheckPrices(1, initialProvidedApr, _expectedFundsEndEpoch());

    // Epoch N+2 started; attacker claims
    _startEpochAndCheckPrices(2);
    uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();

    // BUG: epoch-N receipt paid at par instead of 50% haircut
    uint256 paid = IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre;
    assertGt(paid, receiptN / 2, "loss-adjusted receipt paid above haircut price");
}
```

Expected result: `claimWithdrawRequest` pays the epoch-N receipt at 100% because `lastWithdrawRequest` points at epoch N+1 and `lossRecoveryPriceByEpoch[N+1] == 0`, while `withdrawsRequestsByEpoch[attacker][N]` remains in the aggregate `withdrawsRequests` paid by `_claimFundedWithdrawRequest`.

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
