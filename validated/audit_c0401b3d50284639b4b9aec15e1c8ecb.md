### Title
`get_locked_amount` rounds the release schedule down, allowing locked/unvested tokens to become transferable before they are actually released - (File: lockup/src/getters.rs)

### Summary
`get_locked_amount` computes the still-locked portion of the linear release schedule using floor (truncating) integer division, so it can under-report the locked amount by up to a fraction of a yoctoNEAR at any given `block_timestamp`. This under-reported "locked" value is subtracted (via `get_liquid_owners_balance`) from the account's balance to determine how much the owner can `transfer` out, so the rounding direction is backwards relative to what the safety/custody guarantee requires.

### Finding Description
The lockup contract's release schedule is intended to guarantee that `locked_amount(t)` is always at least as large as the schedule dictates, so that `liquid_balance = balance - locked_amount` never exceeds what has genuinely vested/unlocked. In `get_locked_amount`: [1](#0-0) 

```
let time_left = U256::from(end_timestamp - block_timestamp);
let unreleased_amount = U256::from(lockup_amount) * time_left
    / U256::from(release_duration);
unreleased_amount.as_u128()
```

`U256` division truncates toward zero, i.e. it rounds **down**. Because `unreleased_amount` represents the amount still locked (not yet released), rounding it down means the reported locked amount is an under-estimate of the true locked amount for that timestamp — the opposite of what a safety-critical schedule check should do. This mirrors the reported `_maxDeposit`/`expectedSupplyAssets` bug class exactly: a value that gates a withdrawal/claim ceiling is rounded in the direction that favors the claimant instead of the ledger.

The value is used directly to gate the owner's ability to move funds out of the escrow account: [2](#0-1) 

`transfer` asserts `get_liquid_owners_balance().0 >= amount.0` before sending NEAR to an arbitrary `receiver_id`. `get_liquid_owners_balance` is derived from `get_balance() - get_locked_amount()` (per `getters.rs`), so an under-estimated `get_locked_amount()` directly inflates the amount the owner is permitted to transfer at a given timestamp, permitting a fraction of the still-locked/unvested balance to be released and moved out earlier than the schedule intends.

`get_locked_amount` is also used as the completion gate for adding a full access key to the account: [3](#0-2) 

so the same rounding-down bias could in principle let `get_locked_amount()` read `0` one integer-division step earlier than the schedule truly reaches full release.

### Impact Explanation
This breaks the core custody binding for the lockup contract: "releasable amount must equal (or be no greater than) what the release schedule allows, at every point in time." Because `unreleased_amount` truncates instead of rounding up, the owner (an account that is only entitled to what has genuinely unlocked) can transfer out slightly more than the schedule allows — i.e. locked/unvested tokens released early. Per the stated impact categories this falls under Critical ("locked or unvested tokens released early"). The maximum discrepancy per call is bounded by strict integer-division truncation error (`< 1` unit of `release_duration`'s fractional remainder, i.e. at most a handful of yoctoNEAR per query, since `lockup_amount * time_left / release_duration` truncates a fraction strictly less than 1), so the absolute magnitude of any single early release is negligible in economic terms, but it is a real, deterministic bias in the intended direction of safety.

### Likelihood Explanation
This is triggered automatically on every call to `get_locked_amount` while `release_duration` is configured and the release is in progress (`lockup_timestamp <= block_timestamp < end_timestamp`) — no special privileges are required beyond being the lockup owner calling the already-permitted `transfer` method. It requires no redeploy, no foundation action, and no defect in `near-sdk`; it is a straightforward off-by-rounding-direction bug reachable through the contract's normal, documented flow.

### Recommendation
Round `unreleased_amount` up instead of down, e.g. using ceiling division `(lockup_amount * time_left + release_duration - 1) / release_duration`, consistent with the ceiling-division helpers already used elsewhere in the repo for share/amount conversions (see `staking-pool/src/internal.rs` `num_shares_from_staked_amount_rounded_up` / `staked_amount_from_num_shares_rounded_up`, which correctly bias rounding in the safe direction). This guarantees `get_locked_amount()` never under-reports the truly locked balance, closing the early-release gap.

### Proof of Concept
Conceptual trace (deterministic, no attacker action needed beyond calling documented methods):
1. Lockup contract configured with `lockup_amount = L`, `release_duration = R`, `lockup_timestamp = T0`, no vesting (`VestingInformation::None`).
2. At `block_timestamp = T0 + t` where `0 < t < R`, the true remaining-locked fraction is `L * (R - t) / R` (exact rational value). The contract computes `unreleased_amount = floor(L * (R - t) / R)`, which for a specific `t` (e.g. `L=1000, R=3, t=1` → true value `≈333.33` truncated to `333`) is strictly less than the exact schedule value.
3. `get_locked_amount()` returns this truncated `unreleased_amount` (since `termination_withdrawn_tokens = 0` and no vesting).
4. Owner calls `transfer(amount, receiver_id)` where `amount` is chosen equal to `get_liquid_owners_balance()`, which is now `balance - truncated_locked_amount`, i.e. strictly larger than the balance minus the true schedule-required locked amount.
5. The `assert!` in `transfer` (`lockup/src/owner.rs:477-482`) passes and the extra (still-technically-locked) fractional amount is transferred to `receiver_id`, one call earlier than the exact schedule would allow.

Note: I was unable to fully trace the exact body of `get_liquid_owners_balance`/`get_balance` (only `get_locked_amount` and `get_unvested_amount` bodies were retrieved), so the precise arithmetic combining `get_locked_amount` with `MIN_BALANCE_FOR_STORAGE` and staking balances could not be independently confirmed from source in this pass; if a Devin session with full repo access can inspect `lockup/src/getters.rs` in its entirety (including `get_balance`, `get_liquid_owners_balance`, `get_owners_balance`), that would firm up the exact per-call bound on the early-release amount.
