### Title
Integer underflow / out-of-bounds panic when decoding attacker-supplied MPT node RLP list in `rlp_list_element_length` - (File: crates/proof/mpt/src/util.rs)

### Summary
`TrieNode::decode` (used by every `TrieProvider` implementation in the fault-proof program and derivation pipeline) calls `rlp_list_element_length` to count the top-level elements of an RLP list before deciding whether the node is a branch (17 elements) or leaf/extension (2 elements). This helper subtracts an attacker-controlled `payload_length` from `buf.len()` without first checking that `payload_length <= buf.len()`, mirroring the class of out-of-bounds/underflow bug described in CVE-2017-13755 (unchecked length field taken from crafted, untrusted structured input leading to reads past the intended bounds).

### Finding Description
`rlp_list_element_length` decodes an RLP header and then computes: [1](#0-0) 

`header.payload_length` originates purely from the RLP header bytes decoded by `alloy_rlp::Header::decode`, which does not verify that the declared payload length actually fits within the remaining slice — that check is deferred to the caller. Here, `buf.len() - header.payload_length` is computed unconditionally: if a malicious/crafted node preimage declares a `payload_length` larger than the actual remaining buffer, this subtraction underflows (`usize` panic in debug builds; wraps to a near-`usize::MAX` value in release builds). The subsequent `while buf.len() > len_after_consume` loop then keeps decoding headers and calling `buf.advance(header.payload_length)`, which will attempt to advance past the end of the slice and panic once a `payload_length` exceeds what remains.

This function is only ever reached from `TrieNode::decode`: [2](#0-1) 

which is the single decode path used by every `TrieProvider` in the fault-proof program (`OracleL1ChainProvider::trie_node_by_hash`, `DiskTrieNodeProvider::trie_node_by_hash`, the executor test fixture provider, and generally the code path that resolves state/storage/receipt trie nodes fetched from the preimage oracle during dispute-game execution): [3](#0-2) [4](#0-3) 

The preimage bytes fed into `TrieNode::decode` are supplied through the preimage oracle by a potentially adversarial dispute-game participant (challenger/defender can serve any bytes for a claimed hash prior to it being checked against the hash commitment, or more relevant, the fault-proof program must be robust to *any* byte sequence claimed to correspond to a trie node during untrusted derivation of L1 deposit/system-config data and state proofs). A crafted node payload with a length field larger than the actual buffer size will crash the process instead of returning a decode error.

### Impact Explanation
The fault-proof program is required to always terminate deterministically and either produce a correct output root or a well-defined error — a panic/crash during trie traversal is a denial-of-service against the dispute-game execution: the honest party's program halts instead of computing the correct output, which can prevent submission of the correct claim within the dispute-game clock and lead to loss of the dispute or an incorrect adjudicated output root. This falls squarely into the allowed "node halt" / "wrong provable output root" impact categories.

### Likelihood Explanation
Reaching this code only requires supplying a crafted RLP-encoded value (with a bogus length prefix) as the preimage for a hash that the fault-proof program is instructed to fetch via `trie_node_by_hash`/`bytecode_by_hash`/`header_by_hash`. Any actor able to influence which bytes are served as an MPT node preimage during proof generation (e.g., during dispute-game preimage serving) can trigger it with a single malformed node — no privileged access is required, and the check that is missing (`payload_length <= remaining buffer length`) is a basic bounds validation absent from an otherwise input-facing parsing routine.

### Recommendation
In `rlp_list_element_length`, validate `header.payload_length <= buf.len()` (returning `alloy_rlp::Error::InputTooShort` otherwise) before performing the subtraction, mirroring the explicit bounds check already done for the same purpose in `TxDeposit::rlp_decode`: [5](#0-4) 

### Proof of Concept
1. Construct a byte buffer beginning with an RLP list header claiming a `payload_length` larger than the number of bytes that actually follow it (e.g., header byte `0xf8` + length byte declaring 200, followed by only 10 bytes of payload).
2. Feed this buffer as the return value of a `TrieProvider::trie_node_by_hash` call, e.g., by making the preimage oracle return it for a requested hash in `OracleL1ChainProvider::trie_node_by_hash` or the disk-backed `DiskTrieNodeProvider::trie_node_by_hash`.
3. Calling `TrieNode::decode(&mut buf)` invokes `rlp_list_element_length`, computing `buf.len() (10) - header.payload_length (200)`, which underflows and subsequently causes `buf.advance(...)` to be called with a length exceeding the remaining bytes, panicking the process instead of returning a `alloy_rlp::Error`.

I was unable to directly inspect the `alloy_rlp`/`bytes` crate's `Buf::advance` implementation in this index (external dependency) to confirm the exact panic message, but the standard `bytes::Buf` contract for slice-backed buffers asserts `cnt <= self.remaining()` and panics otherwise, which is consistent with this analysis.

pub(crate) fn rlp_list_element_length(buf: &mut &[u8]) -> alloy_rlp::Result<usize> {
    let header = Header::decode(buf)?;
    if !header.list {
        return Err(alloy_rlp::Error::UnexpectedString);
    }
    let len_after_consume = buf.len() - header.payload_length;

    let mut list_element_length = 0;
    while buf.len() > len_after_consume {
        let header = Header::decode(buf)?;
        buf.advance(header.payload_length);
        list_element_length += 1;
    }
    Ok(list_element_length)
}

impl Decodable for TrieNode {
    /// Attempts to decode the [`TrieNode`].
    fn decode(buf: &mut &[u8]) -> alloy_rlp::Result<Self> {
        // Peek at the header to determine the type of Trie node we're currently decoding.
        let header = Header::decode(&mut (**buf).as_ref())?;

        if header.list {
            // Peek at the RLP stream to determine the number of elements in the list.
            let list_length = rlp_list_element_length(&mut (**buf).as_ref())?;

            match list_length {
                BRANCH_LIST_LENGTH => {
                    let list = Vec::<Self>::decode(buf)?;
                    Ok(Self::Branch { stack: list })
                }
                LEAF_OR_EXTENSION_LIST_LENGTH => {
                    // Advance the buffer to the start of the list payload.
                    buf.advance(header.length());
                    // Decode the leaf or extension node's raw payload.
                    Self::try_decode_leaf_or_extension_payload(buf)
                        .map_err(|_| alloy_rlp::Error::UnexpectedList)
                }
                _ => Err(alloy_rlp::Error::UnexpectedLength),
            }
