### Title
Multisig `DeleteKey` action fails to purge stale confirmations left by the removed key on other pending requests, allowing a request to execute below the intended live-member threshold - ([File: multisig/src/lib.rs])

### Summary
When a multisig key is removed via `MultiSigRequestAction::DeleteKey`, the contract only clears requests that were *created* by that key. It does not remove confirmations that key had already cast on *other* still-pending requests. Those stale confirmations continue to count toward `num_confirmations` in `confirm()`, so a request can later execute with fewer currently-live keys than the configured threshold requires.

### Finding Description
`confirm()` counts confirmations purely from the persisted `HashSet<PublicKey>` for the request, with no re-validation that each key in the set is still an active multisig key at execution time: [1](#0-0) 

When a `DeleteKey` action is executed, the cleanup logic only removes requests where `r.signer_pk == pk` (i.e., requests *authored* by the deleted key) and clears that key's `num_requests_pk` entry. It never scans `self.confirmations` to strip the deleted key's public key from confirmation sets of requests authored by *other* signers: [2](#0-1) 

Concretely:
1. Key `C` creates request `R` (e.g., a `Transfer`). `num_confirmations = 3`.
2. Key `A` (a legitimate but soon-to-be-revoked member, e.g. suspected compromised) calls `confirm(R)`. `confirmations[R] = {A}`.
3. The group executes a separate, properly-authorized request to `DeleteKey { public_key: A }` to revoke `A`. This only removes requests where `signer_pk == A`; `R` (authored by `C`) is untouched, and `confirmations[R]` still contains `A`.
4. Only one more live key, `B`, needs to confirm `R`: `confirmations.len() (1, from stale A) + 1 (B) = 2 >= num_confirmations` may now be reached with only 2 *actually live* keys (`B` confirming, plus stale `A`) instead of 3, or in a 2-of-N config, `B` alone would suffice where before `A` had to be one of the live 2.

The equality broken is: `confirmations counted` should equal `confirmations from currently-authorized keys`, but instead `confirmations counted` includes confirmations from keys that have since been revoked.

### Impact Explanation
This directly matches the Critical impact category "a multisig request executed below threshold." An attacker (or a compromised/former key holder whose key was supposed to be neutralized) can have their earlier confirmation continue to count toward execution of arbitrary pending actions — including `Transfer`, `AddKey`, `FunctionCall`, or further `DeleteKey`/`SetNumConfirmations` requests — effectively lowering the live quorum needed by the remaining signers, undermining the entire security guarantee of the k-of-n multisig.

### Likelihood Explanation
This requires no privileged action by the attacker beyond having been a legitimate multisig key holder at some point who confirmed a request before being removed; the vulnerability is triggered automatically as a side effect of the normal, well-intentioned `DeleteKey` workflow (e.g., rotating out a departing member or revoking a suspected-compromised key) combined with any pre-existing pending request that the removed key had confirmed. No special conditions beyond ordinary contract usage are needed, making this readily reachable in practice whenever key rotation happens while requests are outstanding.

### Recommendation
In the `DeleteKey` branch of `execute_request`, in addition to removing requests authored by the deleted key, iterate over all entries in `self.confirmations` and remove the deleted public key from every confirmation set (persisting the updated sets, and re-checking whether removal would have already caused stale over-counting for any request whose count was based on it).

### Proof of Concept
Given `multisig/src/lib.rs`:
1. `new(3)` — 3 confirmations required, keys `A`, `B`, `C` are valid access keys.
2. `C` calls `add_request(Transfer{...})` → `request_id = R`.
3. `A` calls `confirm(R)` → `confirmations[R] = {A}` (not yet executed, since `1 < 3`).
4. Group runs and confirms a separate request `DeleteKey{public_key: A}` to revoke `A`'s access key (e.g., because `A` is compromised).
   - Execution path: [2](#0-1)  — only requests with `signer_pk == A` are purged; `R` (authored by `C`) is unaffected, so `confirmations[R]` still equals `{A}`.
5. `B` calls `confirm(R)` → `confirmations.len() (1) + 1 = 2`. If `num_confirmations` had meanwhile been lowered to 2 via a legitimate `SetNumConfirmations` request (a normal governance action), `R` executes the `Transfer` with only `B` as a currently-live confirming key, plus the stale confirmation from the already-revoked `A`.

This demonstrates the executed request relying on a confirmation from a key no longer authorized on the account, breaking the threshold guarantee.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
