## Analog Found: Cross-Client Request-ID Collision DoS in the Gateway Confidential-Relay Handler

### Title
Unprivileged clients can DoS each other's confidential-relay gateway requests via request-ID collision (missing sender-binding on request ID) - (File: `core/services/gateway/handlers/confidentialrelay/handler.go`)

### Summary
The `LeapFactory` bug pattern is: a user-supplied identifier (`deploymentSalt`) is used directly as the sole key for a global, deduplicated resource, without binding it to the caller's identity, so any unprivileged actor can pre-empt/collide with another user's identifier and cause their legitimate call to revert. The `confidentialrelay` gateway handler in chainlink exhibits the identical pattern: the JSON-RPC `req.ID` supplied by an unauthenticated/unprivileged gateway client is used as the sole key into a shared, global `activeRequests` map, with no binding to the sender's identity.

### Finding Description
`handler.HandleJSONRPCUserMessage` accepts any client's JSON-RPC request and only validates that `req.ID` is non-empty and not too long, then calls `h.newActiveRequest(req, callback)`: [1](#0-0) 

The handler stores in-flight requests in a single shared map keyed purely by the raw request ID: [2](#0-1) 

The confirmed behavior — verified in the handler's own test suite — is that submitting a request with an ID that already exists in `activeRequests` causes the call to fail with `"request ID already exists"`, regardless of who owns the pre-existing entry: [3](#0-2) 

Crucially, unlike the sibling `vault` gateway handler — which explicitly namespaces the request ID by the *authorized* caller (`authorizedOwner + separator + originalRequestID`) before using it as a lookup/dedup key, precisely to prevent this class of collision: [4](#0-3) 

the `confidentialrelay` handler performs no such namespacing. It uses the caller-chosen `req.ID` verbatim as the global map key, so nothing prevents two different, unrelated, unprivileged clients from choosing the same ID — accidentally or maliciously.

This is the direct analog of the `LeapFactory.createDrop()` issue: there, `deploymentSalt` (fully attacker/user-controlled) is used as the sole key for `Clones.predictDeterministicAddress`/`cloneDeterministic` without incorporating `msg.sender`, so an attacker can observe a pending transaction and front-run with the same salt, causing the victim's `predictedAddress.code.length > 0` check to revert. Here, `req.ID` (fully client-controlled) is used as the sole key for the `activeRequests` map without incorporating any authenticated caller identity, so an attacker who can predict or brute-force a victim's chosen `req.ID` (e.g., if the calling application uses low-entropy or predictable IDs, or the attacker races immediately after observing an ID used by the same integration) can register that ID first and cause the victim's legitimate request to be rejected as a duplicate.

### Impact Explanation
Any unprivileged gateway client can deny service to another client's confidential-relay request simply by submitting a request with the same `id` value first. Because the map is global and not scoped per authenticated sender, this is a direct cross-user DoS: the legitimate caller's `HandleJSONRPCUserMessage` invocation errors out and the associated capability/secrets-get workflow execution fails, without the attacker needing any special privilege — only network access to the gateway's public HTTP/JSON-RPC endpoint.

### Likelihood Explanation
Likelihood depends on how request IDs are generated by legitimate callers of this method (`MethodSecretsGet`/`MethodCapabilityExec`). If callers use sufficiently random/high-entropy IDs, the attack requires guessing; but the mechanism itself provides zero protection — there is no per-sender scoping at all, in contrast to the vault handler which was hardened this exact way. Any caller using deterministic, sequential, or otherwise low-entropy IDs (or simply an attacker who can observe/replay an ID pattern used by a target integration) can exploit this immediately.

### Recommendation
Namespace `activeRequests` keys by an identifier tied to the requester (e.g., authenticated sender/connection identity, gateway-assigned session ID, or an owner-prefixed ID similar to the pattern already used in `GatewayVaultRequestProcessor.authorizeAndStamp`), rather than trusting the raw, unauthenticated client-supplied `req.ID` as a globally unique key. At minimum, apply the same owner/sender-prefixing pattern used by the vault gateway handler to the confidential-relay handler's request-ID handling.

### Proof of Concept
1. Attacker sends a JSON-RPC request to the gateway's confidential-relay endpoint with `id = "X"` and a low-cost/no-op valid method/params, which gets registered in `activeRequests["X"]`.
2. Before the attacker's request completes/times out, the victim (an unrelated legitimate client) sends its own genuine `MethodCapabilityExec`/`MethodSecretsGet` request also using `id = "X"` (e.g., because the victim's client-side ID generation is predictable, sequential, or was observed by the attacker).
3. The victim's call to `h.newActiveRequest` finds `"X"` already present in the shared map and fails immediately with `"request ID already exists"`, as reproduced by `TestConfidentialRelayHandler_DuplicateRequestID`, denying the victim's request without exploiting the actual capability logic. func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
```go
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	l := logger.With(h.lggr, "method", req.Method, "requestID", req.ID)
	l.Debugw("handling confidential relay request")

	ar, err := h.newActiveRequest(req, callback)
	if err != nil {
		return err
	}

	return h.fanOutToNodes(ctx, l, ar)
}
```

```go
func TestConfidentialRelayHandler_DuplicateRequestID(t *testing.T) {
	t.Parallel()
	h, cb, don, _ := setupHandler(t, 4)
	don.On("SendToNode", mock.Anything, mock.Anything, mock.Anything).Return(nil)

	params := json.RawMessage(`{"workflow_id":"wf1"}`)
	req := jsonrpc.Request[json.RawMessage]{
		ID:     "req-dup",
		Method: MethodCapabilityExec,
		Params: &params,
	}

	err := h.HandleJSONRPCUserMessage(t.Context(), req, cb)
	require.NoError(t, err)

	cb2 := common.NewCallback()
	err = h.HandleJSONRPCUserMessage(t.Context(), req, cb2)
	require.ErrorContains(t, err, "request ID already exists")
}
```
