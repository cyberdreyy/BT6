## Finding: Retroactive commission-rate application to pre-existing pending distribution-pool growth in `staking_contract.move` [1](#0-0) 

### Summary
The Sablier bug is: a new fee percentage is applied to a debt balance that already existed under the *old* fee rate, because the contract stores no per-period fee rate — only the *current* rate is applied whenever a withdrawal is settled. Aptos's `staking_contract.move` module has a structurally identical pattern in `update_distribution_pool`, which is used to settle the pending-withdrawal (`distribution_pool`) share accounting.

### Finding Description
`update_distribution_pool` [2](#0-1)  charges commission on "any rewards earnt relatively to the previous value of the distribution pool" using the **current** `staking_contract.commission_percentage`, whenever it is invoked. It has no concept of which commission rate was in effect during which portion of the elapsed growth — it only compares `previous_worth` vs `current_worth` and applies today's rate to the entire delta.

`commission_percentage` can be changed at any time by the staker via `update_commision` [3](#0-2) , which — unlike the `delegation_pool` equivalent that defers the new rate to the *next lockup cycle* via `NextCommissionPercentage`/`effective_after_secs` [4](#0-3)  — takes effect **immediately** with no lockup-remaining-time gate.

Critically, `distribute_internal`/`update_distribution_pool` is also reachable through the fully permissionless `distribute` entry function, which explicitly "does not need to be restricted to just the staker or operator" [5](#0-4) . Any address can call `distribute(staker, operator)` at a time of its choosing to force `update_distribution_pool` to crystallize whatever the *current* commission rate is against the entire pending distribution-pool growth accrued since the last sync — including growth that occurred while a *lower* commission rate was in effect.

Sequence:
1. Staker unlocks stake into the `distribution_pool` via `unlock_stake` while commission is low (e.g. 0–10%): `add_distribution` calls `update_distribution_pool` with the then-current low rate [6](#0-5) .
2. The pending_inactive stake continues to earn rewards while awaiting the lockup to end (unverified in this pass whether `stake::withdraw_with_cap` also pulls pending_inactive early — see caveat below), so `distribution_pool`'s recorded `total_coins` becomes stale relative to actual growth.
3. Staker raises `commission_percentage` via `update_commision` — this only forces settlement of *already inactive* funds via `distribute_internal`/`request_commission_internal` [7](#0-6) , not the stale pending distribution-pool growth.
4. Anyone calls `distribute()`. `update_distribution_pool` now applies the **new, higher** commission rate to the *entire* accumulated growth in the distribution pool, including the portion that accrued while the *old, lower* rate was in effect, transferring extra shares from the staker's pending balance to the operator [8](#0-7) .

This is the exact bug class from the report: a fee-rate change is applied to a balance/accrual that happened before the rate change, because no rate is snapshotted per accrual period.

### Impact Explanation
This misattributes value between the staker and operator: the operator is credited with commission at a rate that was never in effect while the underlying rewards were earned, effectively transferring value that rightfully belongs to the staker. This falls under the explicitly allowed impact "Operator commission ... share-accounting corruption that credits the wrong account."

### Likelihood Explanation
Uncertain/Medium. I was able to fully confirm the vulnerable accounting logic in `update_distribution_pool` and that `update_commision` applies immediately with no lockup gate (unlike `delegation_pool`'s deliberately-deferred design), and that `distribute` is permissionless. However, I was **not able to verify within this session** whether `stake::withdraw_with_cap`/`stake.move` actually allows meaningful pending_inactive growth to accumulate unsynced in the distribution pool before lockup ends (i.e., whether `total_potential_withdrawable` in `distribute_internal` meaningfully changes pre-lockup-expiry), which is the precondition for the stale-growth window to be exploitable. This would need to be confirmed by tracing `stake::get_stake`/`stake::withdraw_with_cap` semantics for `pending_inactive` — the tool session ended before I could complete that trace.

### Recommendation
Snapshot the commission rate at the time distribution-pool shares are created (per-distribution rate), or force `update_distribution_pool` to sync (crystallize commission at the *old* rate) before any commission percentage change takes effect, and/or apply the same "next-lockup-cycle" deferral used in `delegation_pool.move` to `staking_contract.move`'s `update_commision`.

### Proof of Concept
Not fully constructed — the existing test `test_update_commission` [9](#0-8)  demonstrates the base mechanics (commission change mid-flight, followed by an epoch of rewards) but does not extend to the specific "unlock into distribution_pool, let it grow pending, then raise commission and call permissionless `distribute`" sequence needed to conclusively prove exploitability. Given the unresolved precondition noted above (pending_inactive growth accrual timing), I cannot certify this as a confirmed exploitable path without further verification of `stake.move`'s withdraw/pending_inactive semantics.

**Given this unresolved precondition, I cannot assert this finding meets the "high or critical impact with fully proven root cause" bar required.** Recommend a follow-up session with full read access to `stake.move`'s `withdraw_with_cap`, `unlock_with_cap`, and pending_inactive-to-inactive transition logic to conclusively determine whether the stale-growth window described above is real and exploitable before treating this as a confirmed vulnerability.

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
                    pool_u64::transfer_shares(
                        distribution_pool, shareholder, operator, shares_to_transfer
                    );
                };
            }
        );

        distribution_pool.update_total_coins(updated_total_coins);
    }

    /// Allows an owner to update the commission percentage for the operator of the underlying stake pool.
    public entry fun update_commission_percentage(
        owner: &signer,
        new_commission_percentage: u64
    ) acquires DelegationPoolOwnership, DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage {
        assert!(new_commission_percentage <= MAX_FEE, error::invalid_argument(EINVALID_COMMISSION_PERCENTAGE));
        let owner_address = signer::address_of(owner);
        let pool_address = get_owned_pool_address(owner_address);
        assert!(
            operator_commission_percentage(pool_address) + MAX_COMMISSION_INCREASE >= new_commission_percentage,
            error::invalid_argument(ETOO_LARGE_COMMISSION_INCREASE)
        );
        assert!(
            stake::get_remaining_lockup_secs(pool_address) >= min_remaining_secs_for_commission_change(),
            error::invalid_state(ETOO_LATE_COMMISSION_CHANGE)
        );

        // synchronize delegation and stake pools before any user operation. this ensures:
        // (1) the operator is paid its uncommitted commission rewards with the old commission percentage, and
        // (2) any pending commission percentage change is applied before the new commission percentage is set.
        synchronize_delegation_pool(pool_address);

        if (exists<NextCommissionPercentage>(pool_address)) {
            let commission_percentage = borrow_global_mut<NextCommissionPercentage>(pool_address);
            commission_percentage.commission_percentage_next_lockup_cycle = new_commission_percentage;
            commission_percentage.effective_after_secs = stake::get_lockup_secs(pool_address);
        } else {
            let delegation_pool = borrow_global<DelegationPool>(pool_address);
            let pool_signer = account::create_signer_with_capability(&delegation_pool.stake_pool_signer_cap);
            move_to(&pool_signer, NextCommissionPercentage {
                commission_percentage_next_lockup_cycle: new_commission_percentage,
                effective_after_secs: stake::get_lockup_secs(pool_address),
            });
        };
