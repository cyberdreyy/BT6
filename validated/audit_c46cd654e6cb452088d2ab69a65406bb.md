## Analog Confirmed

### Title
Lack of slippage control for `kamino_withdraw` collateral-to-liquidity conversion - ([File: programs/marginfi/src/instructions/kamino/withdraw.rs])

### Summary
`kamino_withdraw` accepts a Kamino **collateral token** amount as input and converts it to underlying **liquidity tokens** at execution time via `integration_acc_1.load()?.collateral_to_liquidity(collateral_amount)`, then transfers whatever liquidity amount results. There is no user-supplied minimum-liquidity-out parameter, so the actual underlying amount received can differ from what the user calculated off-chain when signing the transaction, exactly mirroring the Napier `issue()` slippage report (fixed input converted through a time-varying exchange rate, no bound on the output).

### Finding Description
The instruction's own doc comment acknowledges the design gap: [1](#0-0) . The withdrawal flow burns marginfi bank shares 1:1 against the user-specified `amount` of Kamino collateral tokens [2](#0-1) , then computes the expected liquidity payout from the *current* reserve exchange rate immediately before the CPI [3](#0-2) , and transfers whatever amount is actually received, only sanity-checked against its own just-computed expectation with `assert_within_one_token` [4](#0-3) .

This "expected" value is derived from state read at execution time — not from any value the user committed to when constructing/signing the transaction. Because Kamino's collateral↔liquidity exchange rate changes with interest accrual and reserve activity between the moment a user (or their client) estimates `amount` off-chain and the moment the transaction actually lands on-chain (a later slot, possibly after other deposits/withdrawals/interest accruals against the same reserve), the liquidity tokens ultimately delivered to the user can be materially different from what they intended, with no instruction-level bound to prevent an unfavorable outcome. Unlike the JupLend integration in this codebase, which recomputes an exact expected-shares value from rates refreshed inside the *same* instruction and enforces `require_eq!` [5](#0-4) , `kamino_withdraw` provides no analogous guarantee tied to what the user actually asked for in liquidity terms — the caller has to reverse-engineer the exchange rate themselves and hope it hasn't moved by execution time.

### Impact Explanation
A user who withdraws a Kamino-backed position by specifying a collateral-token `amount` (as the API requires) has no way to guarantee a minimum liquidity-token payout. If the reserve's exchange rate shifts unfavorably between signing and landing (e.g., due to intervening deposits/withdrawals by other parties, interest-rate changes, or a `refresh_reserve` update reflecting newly accrued interest/utilization), the user receives less underlying liquidity than they calculated off-chain for the same collateral burned — a direct, silent loss of value with no revert path, matching the "loss of assets for the affected users" impact in the source report.

### Likelihood Explanation
Any user (unprivileged) calling `kamino_withdraw` is exposed; no special privileges are required to trigger the unfavorable rate movement, since the Kamino reserve's exchange rate updates through ordinary interest accrual and other users' deposit/withdraw/borrow activity happening between transaction construction and execution. This is a permissionless, integration/CPI accounting path directly reachable by ordinary account holders.

### Recommendation
Add an optional `min_liquidity_out` (or `max_collateral_in` for the inverse direction) parameter to `kamino_withdraw`, and `require!()` that the actual liquidity received (`received` at line 211) meets or exceeds the user-specified minimum before completing the transfer, reverting the instruction otherwise.

### Proof of Concept
1. User Alice holds Kamino collateral shares in a marginfi Kamino bank and wants to withdraw ~100 USDC worth of liquidity.
2. She reads the current reserve exchange rate off-chain and computes `amount` (collateral tokens) needed to redeem ~100 USDC, then signs a `kamino_withdraw(amount)` transaction.
3. Before her transaction lands, other activity on the same Kamino reserve accrues interest / shifts utilization, changing the collateral→liquidity exchange rate.
4. Alice's transaction executes: `bank_account.withdraw(amount)` burns her shares [2](#0-1) , and `collateral_to_liquidity(collateral_amount)` now yields less than 100 USDC [6](#0-5) .
5. The instruction has no mechanism to reject this outcome — `assert_within_one_token` only checks internal consistency between the CPI result and the just-computed expectation, not against Alice's original intent — so she receives less than expected with no recourse.
