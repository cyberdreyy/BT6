### Title
`setApr`/`setAprs` treat `idleCDO == address(0)` as "unset" and skip all access control, letting any EOA poison `lastApr`/`unscaledApr` before the CDO is linked - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` uses the zero address as the "CDO not yet configured" sentinel. In `setApr`, when `idleCDO == address(0)` the caller check (`msg.sender != _cdo && msg.sender != manager`) is skipped entirely, so during the window between `initialize` and `setWhitelistedCDO` any unprivileged address can write `lastApr` and, critically, `unscaledApr`, which is stored with no cap at all. Poisoning `unscaledApr` desynchronizes the APR0 accounting invariant and can permanently brick `stopEpoch` (via `prepareStopEpochWithApr0`'s `revert NotAllowed()`), freezing all vault funds.

### Finding Description
The external report's bug class — `address(0)` overloaded to mean "no address set / None" rather than a real account — appears verbatim here:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:225-235
function setApr(uint256 _apr) public {
    address _cdo = idleCDO;
    // if cdo is not yet set we skip the check (this can happen only during the setup)
    if (_cdo != address(0)) {
      if (msg.sender != _cdo && msg.sender != manager) revert NotAllowed();
    }
    uint256 _maxApr = maxApr;
    if (_maxApr != 0 && _apr > _maxApr) revert NotAllowed();
    lastApr = _apr;
}
```

`setApr` is `public`, and both `setAprs` and `setAprsWithBuffer` funnel into it. Two separate problems:

1. **`unscaledApr` is unbounded and unauthenticated in the window.** `setAprs(uint256 _unscaledApr, uint256 _apr)` writes `unscaledApr = _unscaledApr` unconditionally before calling `setApr`. While `idleCDO == address(0)`, anyone can set it to any value.

2. **`unscaledApr` controls the APR0 state machine.** `requestWithdraw` routes requests into the APR0 bucket iff `unscaledApr == 0` (line 285). `prepareStopEpochWithApr0` reverts `NotAllowed` whenever `apr0TotalPrincipal != 0 && unscaledApr != 0` (lines 506–508). So an attacker who flips `unscaledApr` 0 → nonzero (or nonzero → 0) in the setup window makes the normal epoch flow inconsistent with the stored APR0 bucket:

   - Vault deployed as fixed-APR (`unscaledApr != 0` at init): attacker sets `unscaledApr = 0`. Lenders' `requestWithdraw` calls now populate `apr0Users`/`apr0TotalPrincipal` instead of `withdrawsRequests`, minting the same receipt tokens but diverting principal into a bucket whose interest/settlement semantics the honest operator never configured.
   - Vault deployed as APR0 (`unscaledApr = 0`): attacker sets `unscaledApr = 1`. Once any user has an APR0 request outstanding (`apr0TotalPrincipal != 0`), every subsequent `stopEpoch` that reaches `prepareStopEpochWithApr0` reverts → epoch can never close → all deposits and pending withdrawals are frozen permanently (no unpause path exists because `unscaledApr` can then only be changed by CDO/manager, and fixing it requires a manager tx that itself cannot unbrick an already-reverting accounting state without an upgrade).

Additionally `lastApr` can be driven to `maxApr` (default 20e18 = 2000% scaled) before the CDO is linked, inflating `expectedEpochInterest` at the first `stopEpoch` and forcing borrower-facing obligations the honest deployer never intended.

The factory (`IdleCreditVaultFactory._configureCreditVault`, lines 304–306) calls `setAprs` then `setWhitelistedCDO` inside one transaction, so factory-deployed vaults are safe. But `initialize` itself does not bind the CDO, `setWhitelistedCDO` is a separate `onlyOwner` call, and nothing prevents a non-atomic deployment (manual proxy deployment, multisig-batched ops, or any deployment script that doesn't use the factory) from leaving a mempool-visible gap in which the sentinel grants universal write access. This is exactly the "zero address used as Option::None" hazard the source report describes: the sentinel silently converts an authorization check into no check.

### Impact Explanation
Permanent freezing of the entire vault TVL (all lender deposits and funded withdraw receipts) for the APR0-desync case, or mispricing of epoch interest up to the `maxApr` bound. Loss is bounded only by `getContractValue()`. No privileged attacker is required — only an unprivileged EOA transacting in the configuration gap.

### Likelihood Explanation
Requires a deployment where `initialize` and `setWhitelistedCDO` are not executed atomically. The in-repo factory is atomic, so likelihood is low for factory-deployed vaults but nonzero for any manual/upgraded deployment path; the vulnerable code path itself unconditionally bypasses auth whenever `idleCDO == 0`.

### Recommendation
Do not use `address(0)` as an "unset ⇒ authorized" sentinel. Options:
- Move the "not yet linked" authorization into `initialize` (e.g., set `idleCDO` directly at init, or accept a one-time `setupDone` flag that `setWhitelistedCDO` flips), and revert in `setApr`/`setAprs`/`setAprsWithBuffer` whenever the CDO link is absent.
- At minimum, gate the `idleCDO == 0` branch with `msg.sender == owner()` so the setup window is owner-only.
- Bound `unscaledApr` with the same `maxApr` check applied to `lastApr`.

### Proof of Concept
Foundry fork-style PoC (attacker is a random EOA, owner honest but deploys non-atomically):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVault} from "../contracts/strategies/idle/IdleCreditVault.sol";
import {ERC1967Proxy} from "@openzeppelin/contracts/proxy/ERC1967/ERC1967Proxy.sol";

contract ZeroAddressAprPoisoningTest is Test {
    IdleCreditVault strat;
    address owner = address(0x0A);
    address manager = address(0x0B);
    address attacker = address(0xBAD);
    address cdo = address(0xCD0); // stand-in; attack needs only a placeholder
    IERC20 underlying = IERC20(address(new MockERC20()));

    function setUp() public {
        IdleCreditVault impl = new IdleCreditVault();
        bytes memory init = abi.encodeWithSelector(
            IdleCreditVault.initialize.selector,
            address(underlying), owner, manager, address(0xB0),
            "Borrower", uint256(0) // APR0-mode vault
        );
        strat = IdleCreditVault(address(new ERC1967Proxy(address(impl), init)));
    }

    function test_attackerPoisonsUnscaledAprBeforeCdoLink() public {
        // idleCDO == address(0): access check skipped entirely
        vm.prank(attacker);
        strat.setAprs(1, 0);           // unscaledApr = 1, breaks APR0 invariant
        assertEq(strat.unscaledApr(), 1);

        // owner finishes setup honestly
        vm.prank(owner);
        strat.setWhitelistedCDO(cdo);

        // Any user with an APR0 request (apr0TotalPrincipal != 0) now makes
        // prepareStopEpochWithApr0 revert NotAllowed() on every stopEpoch.
        // => epoch can never close, all deposits permanently frozen.
    }

    function test_attackerMaxesApr() public {
        vm.prank(attacker);
        strat.setAprs(type(uint256).max, 20e18); // lastApr hits maxApr cap
        assertEq(strat.lastApr(), 20e18);
        assertEq(strat.unscaledApr(), type(uint256).max); // unbounded
    }
}
```

Caveat: the PoC demonstrates the auth bypass directly on the strategy; a full end-to-end freeze PoC additionally drives a deposit/`requestWithdraw` through a real `IdleCDOEpochVariant` so `apr0TotalPrincipal != 0` when `stopEpoch` is attempted — reverting in `prepareStopEpochWithApr0` at `contracts/strategies/idle/IdleCreditVault.sol:506-508`.
