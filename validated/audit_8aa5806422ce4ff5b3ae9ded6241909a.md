### Title
Signer weight double-counted across accept/reject tallies via reject-then-accept equivocation - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` accumulates two independent weight tallies per block — `total_weight_approved` and `total_weight_rejected` — that the mining coordinator (`SignCoordinator`) treats as mutually exclusive, disjoint contributions from the signer set. A single signer can send a `Rejected` response for a block and later send an `Accepted` response for the same block. Because the two response handlers use different "already counted" guards (`responded_signers` for rejections vs. `gathered_signatures` for acceptances), the signer's weight is added to *both* tallies, breaking the invariant that `total_weight_approved + total_weight_rejected <= total_weight` per signer contribution.

### Finding Description
In `handle_signer_messages` (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`), the `BlockResponse::Accepted` branch guards weight addition with: [1](#0-0) 

which only checks `block.gathered_signatures.contains_key(&slot_id)`. The `BlockResponse::Rejected` branch guards with a different set: [2](#0-1) 

which checks/inserts into `block.responded_signers`. The Accepted branch never checks `responded_signers`, and the Rejected branch never checks `gathered_signatures`. If a signer's slot first delivers a `Rejected` message (weight added to `total_weight_rejected`, and `responded_signers` gets the slot id), and the *same* slot later delivers an `Accepted` message for the *same* block hash, the Accepted branch sees `gathered_signatures` still empty for that slot and adds the signer's weight to `total_weight_approved` as well — with no subtraction from `total_weight_rejected`. The reverse order (accept-then-reject) is correctly guarded because `responded_signers.insert` returns `false` the second time, but reject-then-accept is not.

This is analogous to the ZeroLend `PoolVoter`/`OmnichainStaking` issue: there, a live-read balance with no lock let a single actor's stake be recounted across repeated stake/unstake actions to inflate a vote tally; here, a live per-message weight-add with an inconsistent "already responded" check lets a single signer's weight be recounted across two supposedly disjoint tallies by flipping their vote once.

### Impact Explanation
`SignCoordinator::begin_sign` uses these two tallies to decide the outcome of a block round: [3](#0-2) 

Because a single equivocating signer's weight can land in both `total_weight_rejected` and `total_weight_approved`, the aggregated weight no longer reflects the true, distinct verified support/opposition of the signer set. This can inflate `total_weight_rejected` toward the `blocking_minority` needed to trigger `NakamotoNodeError::SignersRejected` (which drives permanent/temporary txid exclusion) using a weight that is simultaneously (and separately) contributing to `total_weight_approved`, or it can let `total_weight_approved` reach the acceptance threshold with a "double-spent" fraction of true weight that also fed the reject side. This breaks the aggregated-weight vs. verified-accepts equality the coordinator relies on to decide accept/reject, which the rules classify as a Critical-class analog.

### Likelihood Explanation
Any single signer with its own key can independently emit two StackerDB chunks (Rejected then Accepted) for the same block hash without needing any other signer's cooperation, majority, or elevated access — only gossip/StackerDB write access to its own slot, which every signer has by design. No secp256k1/serde defect or node-consensus-acceptance assumption is required; the flaw is purely in the listener's tally bookkeeping.

### Recommendation
Use a single unified "already responded" guard (e.g., `responded_signers`) for both `Accepted` and `Rejected` branches so a slot's weight is counted at most once total, or explicitly move/void the earlier tally entry when a signer's vote for a block hash flips (i.e., subtract from `total_weight_rejected` before adding to `total_weight_approved`, or reject late flip-flops outright).

### Proof of Concept
1. Node's `StackerDBListener` is running and tracking `BlockStatus` for a proposed block with hash `H` for signer slot `S` (weight `w`).
2. Signer at slot `S` publishes `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`. `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`. [2](#0-1) 
3. The same signer at slot `S` then publishes `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `H`. Since `gathered_signatures` does not yet contain `S`, the guard passes → `total_weight_approved += w`. [4](#0-3) 
4. Now `total_weight_approved` and `total_weight_rejected` both include weight `w` from the same signer, even though only one true vote exists — inflating both sides of the threshold checks in `SignCoordinator::begin_sign`.
