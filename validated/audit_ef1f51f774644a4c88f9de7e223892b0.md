### Title
Unbounded per-notification decode cost for `jsonParsed` `accountSubscribe` on Config/validator-info accounts - ([File: account-decoder/src/parse_config.rs], [File: account-decoder/src/lib.rs], [File: rpc/src/rpc_subscriptions.rs])

### Summary
An `accountSubscribe` with `encoding: jsonParsed` on a Config-program account owned by an attacker-controlled writer re-runs `bincode::deserialize` + `serde_json::from_str` on the full `config_data` payload on every notification, and this decoding path has no size cap, unlike the Base58 path which enforces `MAX_BASE58_BYTES`. Because the attacker fully controls the content of the account they write to, and the notification fires automatically whenever the account changes, the per-notification CPU/memory cost scales with whatever size payload the attacker last wrote, bounded only by the protocol's global 10 MiB account-data ceiling rather than any subscription-specific or `MAX_VALIDATOR_INFO` limit.

### Finding Description
`RpcSolPubSubInternal::account_subscribe` accepts an `encoding` field (defaulting to Binary, but attacker-selectable as `JsonParsed`) with no data-size restriction [1](#0-0) . Each time the subscribed account changes, `filter_account_result` re-encodes the full account via `encode_ui_account` [2](#0-1) .

Inside `encode_ui_account`, the `Base58`/`Binary` path caps cost by refusing to encode data larger than `MAX_BASE58_BYTES` (128 bytes) [3](#0-2) , but the `JsonParsed` branch has no equivalent check — it unconditionally calls `parse_account_data_v3(pubkey, account.owner(), account.data(), additional_data)` on the entire account buffer [4](#0-3) .

For an account owned by the Config program, `parse_account_data_v3` dispatches to `parse_config(data, pubkey)` [5](#0-4) . `parse_config` first `bincode::deserialize`s a `ConfigKeys` header, and if `keys[0].0 == validator_info::id()`, calls `parse_config_data::<String>`, which `bincode::deserialize`s the remaining bytes into a `String`, and then `serde_json::from_str` parses that string as arbitrary JSON [6](#0-5) . Both the bincode and serde_json parsing cost scale linearly (or worse, for deeply-nested JSON) with the size of the string the attacker wrote.

The `MAX_VALIDATOR_INFO = 576` constant is only enforced client-side in the CLI's `validator-info publish` command [7](#0-6)  and is not visible anywhere in the RPC/pubsub decode path, meaning nothing in `parse_config`, `encode_ui_account`, or `filter_account_result` limits the size of `config_data` before parsing it. The only real ceiling is the global account-size cap `MAX_PERMITTED_DATA_LENGTH` (10 MiB) enforced by the System program's `CreateAccount` instruction [8](#0-7) , which is orders of magnitude larger than the intended validator-info payload size, and this repo does not show the Config program's own `store` instruction enforcing any smaller bound (the Config-program processor source was not found in this index, so it cannot be confirmed here whether it independently caps write size below the account's allocated length — but even the CLI-imposed 576-byte convention is not an on-chain invariant reachable from this code path).

An attacker who: (1) creates/owns a Config account whose first key is `validator_info::id()`, (2) allocates it up to the system-wide max size, and (3) is a signer on later `store` transactions, can repeatedly resize/rewrite `config_data` to near-maximal size. A single `accountSubscribe(pubkey, {encoding: "jsonParsed"})` from the attacker (or a victim who happens to subscribe to that pubkey) will then trigger full re-parsing of that large payload on every subsequent write, at attacker-chosen rate (one write per slot, satisfying the "no more than one call per CLUSTER_SLOT_TIME_TARGET/2" precondition since account writes are on-chain transactions, and the subscription itself is a single persistent call).

### Impact Explanation
This falls into "unbounded cost for a single low-rate call": the RPC/pubsub node performs CPU/memory work proportional to attacker-supplied on-chain data size (up to the ~10 MiB account cap) for every notification of a single subscription, with no decoder-side or subscription-side size guard analogous to `MAX_BASE58_BYTES`. Repeated notifications at slot cadence turn this into a sustained, attacker-tunable CPU/memory drain on any RPC node servicing pubsub subscriptions with `jsonParsed` encoding for Config accounts.

### Likelihood Explanation
Feasible with a single unprivileged client: no special program authority, no elevated node access, and no more than one websocket subscription plus periodic legal `store` transactions on an account the attacker controls, at ordinary transaction cadence. This is fully within the "unprivileged attacker, ≤1 call per `CLUSTER_SLOT_TIME_TARGET`/2" threat model since notifications are naturally rate-limited to at most one per slot.

### Recommendation
Add an explicit size guard in the `JsonParsed` branch of `encode_ui_account` (or in `parse_account_data_v3`/`parse_config`) analogous to `MAX_BASE58_BYTES`, rejecting or falling back to raw binary encoding when `account.data().len()` exceeds a small bound (e.g., `MAX_VALIDATOR_INFO` for Config/validator-info accounts, or a generic cap for jsonParsed parsing generally). Enforce this bound consistently on the decode path rather than relying solely on client-side CLI conventions.

fn test_parse_config_cost_scales_with_attacker_payload() {

        let result = parse_config(account.data(), &info_pubkey);

        assert!(result.is_ok());
        // Demonstrates: elapsed time grows with `size`, with no cap enforced

        }
    });

pub fn parse_config(data: &[u8], _pubkey: &Pubkey) -> Result<ConfigAccountType, ParseAccountError> {
    let parsed_account = deserialize::<ConfigKeys>(data).ok().and_then(|key_list| {
        if !key_list.keys.is_empty() && key_list.keys[0].0 == validator_info::id() {
            parse_config_data::<String>(data, key_list.keys).and_then(|validator_info| {
                Some(ConfigAccountType::ValidatorInfo(UiConfig {
                    keys: validator_info.keys,
                    config_data: serde_json::from_str(&validator_info.config_data).ok()?,
                }))
            })
        } else {
            None
        }
    });
    parsed_account.ok_or(ParseAccountError::AccountNotParsable(
        ParsableAccount::Config,
    ))
}

fn parse_config_data<T>(data: &[u8], keys: Vec<(Pubkey, bool)>) -> Option<UiConfig<T>>
where
    T: serde::de::DeserializeOwned,
{
    let config_data: T = deserialize(get_config_data(data).ok()?).ok()?;
    let keys = keys
        .iter()
        .map(|key| UiConfigKey {
            pubkey: key.0.to_string(),
            signer: key.1,
        })
        .collect();
    Some(UiConfig { keys, config_data })
}
