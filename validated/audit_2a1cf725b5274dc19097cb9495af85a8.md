## Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing execution of a request below the live-member quorum — ([File: multisig2/src/lib.rs])

## Summary
`MultiSigContract::confirm` decides whether a request has reached quorum by counting entries in the `confirmations: HashSet<String>` associated with that `request_id`. When a member is deleted via `DeleteMember`, `delete_member` only purges requests that were *created* by the removed member; it does not scrub that member's confirmations from *other* still-pending requests. A confirmation recorded by a member who has since been removed therefore continues to count toward `num_confirmations` forever, letting a request execute (moving NEAR, deploying code, adding/removing keys, etc.) with fewer live, currently-authorized confirmations than the configured threshold.

## Finding Description
`confirm()` only validates that the *new* confirming caller is a current member via `current_member()`: [1](#0-0) 

It never re-validates the *existing* entries already stored in `confirmations` for that request. Membership removal is implemented in `delete_member`: [2](#0-1) 

This only clears confirmations for requests where `r.member == member` (i.e. requests the removed member *authored*). It does nothing to the confirmation sets of other pending requests that the removed member merely *confirmed*. Since `confirmations` is a `HashSet<String>` keyed by the member's serialized identity, and `MultiSigRequestWithSigner`/`get_confirmations` never cross-check membership at read time either: [3](#0-2) 

a confirmation from a member that is no longer in `self.members` still satisfies `confirmations.len() as u32 + 1 >= self.num_confirmations` in `confirm()`.

The equality that should hold before executing any `MultiSigRequestAction` (Transfer, FunctionCall, AddKey, DeployContract, etc.) is:
```
count(confirmations ∩ live_members) >= num_confirmations
```
But the contract actually checks:
```
count(confirmations) >= num_confirmations   (regardless of current liveness)
```
These diverge as soon as any confirming member is removed after confirming but before the request reaches quorum.

The same pattern exists in the older `multisig` contract, where `DeleteKey` similarly only removes requests signed (created) by the deleted key, not that key's confirmations on other pending requests: [4](#0-3) [5](#0-4) 

## Impact Explanation
This breaks the multisig's core custody guarantee that any state-changing/fund-moving action requires `num_confirmations` *currently authorized* signers. A `Transfer` request can be executed via `Promise::new(receiver_id).transfer(amount)` once the (stale-inclusive) confirmation count reaches the threshold, even though one or more of the counted approvals came from a member who was later removed and is no longer trusted. This directly matches the Critical category "a multisig request executed below threshold," resulting in NEAR being moved, keys added/deleted, or contract code deployed, by a set of parties that does not actually meet the account's own quorum policy at execution time.

## Likelihood Explanation
No special privilege beyond being (or having been) one of the multisig's own members is required, and the sequence is a normal part of multisig lifecycle management: members are added and removed over time (e.g., an employee leaving, key rotation, or a compromised key being revoked) while other requests are in flight. Any pending request that a subsequently-removed member had confirmed retains that confirmation indefinitely; the remaining members do not need to do anything special to trigger the flaw — a normal `confirm()` call by another legitimate member completes execution while unknowingly relying on a since-revoked approval. This is straightforward to hit in practice whenever `DeleteMember`/`DeleteKey` execute while any other request is outstanding.

## Recommendation
In `confirm()` (and any place that computes quorum, e.g. `get_confirmations`/`get_num_confirmations` usage), filter `confirmations` to only those entries that are still present in `self.members` before comparing against `num_confirmations`. Additionally, when a member is deleted in `delete_member`/`DeleteKey`, actively remove that member's identity string from the confirmation sets of *all* pending requests (not just requests they authored), or lazily filter at `confirm()` time:
```rust
let live_confirmations: u32 = confirmations
    .iter()
    .filter(|c| self.members.contains_str(c)) // membership check
    .count() as u32;
if live_confirmations + 1 >= self.num_confirmations { ... }
```

## Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]` and `num_confirmations = 3`.
2. `A` calls `add_request_and_confirm(Transfer{ receiver_id: attacker, amount })` → confirmations = `{A}`.
3. `B` calls `confirm(request_id)` → confirmations = `{A, B}` (2/3, not yet executed).
4. Members legitimately reach quorum on a separate request to `DeleteMember{ member: B }` (e.g. B key compromised) and it executes — `self.members` is now `{A, C}`, but the Transfer request's `confirmations` set still contains `{A, B}` untouched, since `delete_member` only purges requests *created by* B, not B's confirmation on the Transfer request created by A.
5. `C` calls `confirm(transfer_request_id)`. `confirmations.len() (2) + 1 == 3 >= num_confirmations (3)` → the Transfer executes, funded by a stale confirmation from the removed member `B`, even though only `A` and `C` are currently live, authorized members (2 of 2 live members, not the required 3).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
