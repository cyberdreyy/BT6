### Title
Signer defaults to "safe to sign" instead of "refuse" when its own node is unreachable while re-checking a same-tenure signed conflict — ([File: stacks-signer/src/v0/signer.rs])

### Summary
When the pre-commit threshold is reached, `handle_block_pre_commit` re-checks whether the proposal conflicts with a block this signer already signed in the *same tenure* (`get_signed_conflicts` + the "stale, same-tenure" branch). If that conflict is stale, the code asks the node for the tenure's canonical tip to decide whether the conflicting/older block is already the network's confirmed state. If the node call errors, the code does **not** refuse to sign — it logs "treating the tenure as unconfirmed" and falls through to producing a signature. The identical “ask the node, and if unreachable assume the safe answer” pattern in `check_latest_block_in_tenure` (used earlier in the very same evaluation path) also fails open (`Ok(true)` ⇒ "assume higher"). Both failures happen on the same signer/node pair, so a single connectivity hiccup to the signer's own stacks-node removes every remaining guard against signing a block that duplicates chain state the network has already finalized.

### Finding Description
The relevant control flow, in order, for a proposal that crosses the pre-commit threshold in its own tenure:

1. `check_block_against_signer_db_state` → `confirms_latest_block_in_same_tenure` → `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:376-478`). If the previously signed tip in this tenure has gone stale (older than `tenure_last_block_proposal_timeout`), the function stops trusting its own local record and asks the node via `client.get_tenure_tip(tenure_id)`. If that call errors: [1](#0-0) 

the function returns `Ok(true)` — i.e. "the proposal is higher than the tenure tip", which lets the block pass this check.

2. Assuming that first check passed (or the block is not a tenure-change block routed through it), `handle_block_pre_commit` runs its own stale-conflict guard directly against `get_signed_conflicts`: [2](#0-1) 

Here, if a stale, same-tenure conflict exists (a block this signer already signed at ≤ the proposed height) and the node's `get_tenure_tip` call errors, the code again does not refuse — it warns "Treating the tenure as unconfirmed" and falls through to the signing logic a few lines below (`mark_locally_accepted` / `handle_block_signature`, `stacks-signer/src/v0/signer.rs:1458` onward).

Both guards are meant to catch the same scenario from different code paths: "did the network already finalize a block at/above this height in this tenure, making the current proposal a duplicate/conflicting re-proposal?" Both guards answer that question by calling the *same* node the signer is attached to. If that node is transiently unreachable (restart, overload, brief network partition — an ordinary operational event, not something requiring a majority of signers or another signer's key), **both** checks fail open in the same direction: "assume it's fine, sign it." This breaks the "signed vs. validated" equality the rest of the state machine works hard to preserve — everywhere else in this exact file (`conflict_still_blocks`, `reorg_permit_stands`, the fresh-conflict path) an unreachable node causes the code to *keep blocking* on the theory that "wrongly signing cannot be taken back." This one path inverts that principle.

This is the direct analog of the FUXA report's bug class: a missing/unavailable input (no token → auto-issue a guest token that still passes verification; here, no node answer → assume the answer that unlocks the sensitive operation) silently converts an "I can't tell" state into "proceed as if authorized/verified," bypassing the check's intended purpose.

### Impact Explanation
If the signer signs a proposal that in fact duplicates or conflicts with chain state the network has already progressed past (because the connectivity failure masked that fact), it produces a valid signature over a block that should have been rejected as non-canonical/conflicting. That signature is a durable, aggregatable artifact ("a bearer instrument," per the same file's own documentation) that can combine with other signers' votes toward the 70% signing threshold for a chain state the node has already superseded — i.e., exactly the "signer signing … a conflicting block" impact class.

### Likelihood Explanation
Reaching this path needs: (a) a proposal (which a single miner, or gossiped stale traffic, can trigger) that conflicts with something this signer already signed at the same/lower height in the same tenure, and (b) the signer's own node RPC being briefly unreachable at the moment `get_tenure_tip` is called. (b) is an ordinary transient condition (node restart/backpressure/network blip), not something an attacker needs a majority or special access to arrange, and the miner/gossip side of (a) is explicitly within the stated threat model. No secondary signer key or majority collusion is required.

### Recommendation
Make the two "node unreachable" branches fail closed instead of fail open:
- In `check_latest_block_in_tenure` (`stacks-signer/src/chainstate/mod.rs:450-460`), an RPC error should not automatically resolve to "proposal is higher"; it should propagate a `ConnectivityIssues`/hold response so the caller can keep the pre-commit/signature withheld rather than assume success.
- In `handle_block_pre_commit`'s same-tenure stale-conflict branch (`stacks-signer/src/v0/signer.rs:1436-1456`), on `Err(e)` from `get_tenure_tip`, refuse to sign for now (return without producing a signature) instead of treating the tenure as unconfirmed, consistent with the fresh-conflict path and with `conflict_still_blocks`'s stated design principle that inability to confirm should delay signing rather than risk an unrecoverable signature.

### Proof of Concept
1. Signer S signs block B1 at height H in tenure T (stored as `LocallyAccepted`/`GloballyAccepted`); time passes beyond `tenure_last_block_proposal_timeout` so the conflict record for B1 becomes "stale" per `get_signed_conflicts`/`get_tenure_last_block_info`.
2. The network has actually finalized B1 (or something ≥ height H in T) as canonical.
3. The miner (or stale gossip) re-proposes/resends a competing block B2 at height ≤ H in the same tenure T. B2 gathers enough pre-commits to cross the 70% pre-commit threshold on signer S.
4. At the exact moment S's `handle_block_pre_commit` re-checks chainstate (`check_latest_block_in_tenure`) and the stale same-tenure conflict guard (`get_signed_conflicts` branch), S's connection to its own stacks-node is transiently down (`get_tenure_tip` returns `Err`).
5. Both guards fail open ("assume higher" / "treat as unconfirmed"), and S signs B2 (`mark_locally_accepted` → `handle_block_signature` → broadcasts acceptance), producing a valid signature over a block that duplicates/conflicts with already-finalized chain state — the exact case the two checks exist to prevent.
