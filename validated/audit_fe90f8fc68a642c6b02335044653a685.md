### Title
Node-side reject/accept weight double-counting on signer vote-flip inflates `total_weight_rejected` without offset - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
### Finding Description
`StackerDBListener::run` maintains, per proposed block, two independent weight accumulators, `total_weight_approved` and `total_weight_rejected`, gated by two different, asymmetric guards.

- On `BlockResponse::Accepted`, the code only guards against double counting the *same* branch: `if !block.gathered_signatures.contains_key(&slot_id) { total_weight_approved += weight }`, then unconditionally does `block.responded_signers.insert(slot_id)`. [1](#0-0) 

- On `BlockResponse::Rejected`, the code guards on the *shared* `responded_signers` set: `if block.responded_signers.insert(slot_id) { total_weight_rejected += weight }`. [2](#0-1) 

Because `responded_signers` is shared between both branches but the *accept* branch does not check it before adding weight (it checks `gathered_signatures` instead), a signer that first rejects a block (adding weight to `total_weight_rejected`, and marking `responded_signers`) and later flips to accept the same block still gets its weight added to `total_weight_approved` (since `gathered_signatures` was empty for it). Its weight is never subtracted from `total_weight_rejected` — there is no code path that decrements or resets that value on a vote change. The reverse flip (accept → reject) is correctly blocked, since the reject branch's guard (`responded_signers.insert`) will return `false` for a signer that already responded. This produces a permanent, one-directional accumulation bug: `total_weight_rejected` becomes a monotonically-growing value that reflects a signer's *historical* opinion, not its current one, while `total_weight_approved` reflects its current opinion. The two totals are supposed to be complementary views of the same signer set but are computed and applied under a broken shared/unshared guard, i.e., an equality the coordinator relies on ("each signer counts once, in exactly the tally matching their latest vote") is broken.

### Impact Explanation
This is a coordinator-side (node) bookkeeping value used to decide, alongside `weight_threshold`, whether a block should be treated as globally rejected (dead) via the check `block.total_weight_rejected.saturating_add(self.weight_threshold) > self.total_weight` (line 567-574). A single miner/signer combination that first sends a rejection and later revises to acceptance (both are messages a single signer, plus its own gossip, can trigger without needing a majority) causes its weight to be double-booked: once permanently in the stale-reject pool and once in the live-accept pool. This can cause the node to prematurely declare a block dead (miss-count a rejection that has since been retracted) even though the actual live signature set could still reach the 70% acceptance threshold, causing the miner to give up on a block that is still signable — a liveness degradation of the block-production path. It does not, however, break signature validity or let an invalid/non-canonical block get signed, and no equality guarded by consensus rules (i.e., `verify_signer_signatures` in `stackslib/src/chainstate/nakamoto/mod.rs`) is affected, since that check independently re-derives weight strictly from the actual signatures in the block. So the blast radius is confined to the miner-side StackerDB listener's internal bookkeeping/telemetry and its decision of when to give up retrying a block, not to a signature that gets accepted into the chain.

### Likelihood Explanation
Triggerable by a single signer (which the report frames analogously to "a one-slot miner") legitimately changing its vote once — a normal occurrence given `should_reevaluate_block`/`should_reevaluate_reject_reason` logic in the signer client explicitly supports re-evaluating and re-sending a different `BlockResponse` for a previously-seen proposal. No majority or privileged access is required; this is reachable through the signer's own re-evaluation logic and gossip.

### Recommendation
Track a single "latest response" state per slot instead of two independent, asymmetrically-guarded weight accumulators, e.g. store an `Option<Vote>` per slot (`Accepted`/`Rejected`) and recompute `total_weight_approved`/`total_weight_rejected` from that map on each update, or explicitly subtract the previous vote's weight from its corresponding tally before adding the new vote's weight to the other. This restores the invariant that a signer's weight can appear in at most one tally at a time and that it reflects only the signer's current vote.

### Proof of Concept
1. Node proposes block B to the signer set; `weight_threshold` requires 70% weight to approve, and the "dead" check trips when `total_weight_rejected + weight_threshold > total_weight` (i.e., roughly >30% reject).
2. Signer S (weight w) evaluates B and sends `BlockResponse::Rejected` (e.g., due to a transient/racy condition). The listener executes the `Rejected` branch: `responded_signers.insert(S)` succeeds, `total_weight_rejected += w`.
3. B is re-proposed or S's local view changes (`should_reevaluate_block`/`should_reevaluate_reject_reason` allow re-evaluation), and S now sends `BlockResponse::Accepted` for the same `signer_signature_hash`. The listener executes the `Accepted` branch: `gathered_signatures.contains_key(S)` is `false` (first acceptance) so `total_weight_approved += w` is added and `responded_signers.insert(S)` is a no-op (already present).
4. Now both `total_weight_approved` includes `w` (correctly, reflecting S's current vote) and `total_weight_rejected` still includes `w` (incorrectly, reflecting S's stale vote) — `total_weight_approved + total_weight_rejected` can exceed `total_weight` by `w`, and the "globally rejected" check can fire using inflated `total_weight_rejected` even while enough live signatures accumulate toward `weight_threshold`, causing the miner to prematurely treat the block as dead.
