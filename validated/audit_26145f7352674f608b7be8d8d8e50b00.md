### Title
Front-runnable `setTrancheAPRSplitRatio` lets a tranche holder force yield settlement at the stale ratio — (File: contracts/IdleCDO.sol)

### Summary
`IdleCDO.setTrancheAPRSplitRatio` (and the AYS-related setters) overwrite `trancheAPRSplitRatio` without first settling accrued-but-unsplit yield via `_updateAccounting`. Because any user can trigger `_updateAccounting` through `depositAA/depositBB/withdrawAA/withdrawBB`, an unprivileged tranche holder can front-run the owner transaction and crystallize all pending yield at the *old* ratio, capturing a share the owner intended to redirect — the exact analog of front-running `updateBorrowCap` to borrow more than intended.

### Finding Description
- `_updateAccounting` splits the gain accrued since the last deposit/withdraw/harvest using the *current* value of `trancheAPRSplitRatio` read at call time: `totalBBGain = totalGain * (FULL_ALLOC - _trancheAPRSplitRatio) / FULL_ALLOC`. The split is therefore retroactive over the whole unaccounted period, not prospective. [1](#0-0) 
- `_deposit` and the withdraw path both call `_updateAccounting()` before minting/burning, and are permissionless (`whenNotPaused` only). Any EOA or tranche holder can force settlement at will. [2](#0-1) 
- `setTrancheAPRSplitRatio` writes the new ratio directly with no `_updateAccounting()` call beforehand: [3](#0-2) 
- The same pattern exists in `IdleCDOCreditVault` for `setMinAprSplitAYS`/`setIsAYSActive`, which also change the effective split applied to pending yield without settling it. Note the codebase already recognizes this hazard class for fees: `setFeeParams` in `IdleCDOCreditVault` calls `_accrueManagementFee()` *before* overwriting `fee`/`managementFee`, while the yield-split setters have no equivalent settlement. [4](#0-3) 
- `_updateSplitRatio` recomputes `trancheAPRSplitRatio` after every deposit/withdraw only when `isAYSActive`; with AYS off the owner-set value is used verbatim, so the front-run ordering fully determines which ratio prices the accrued gain. [5](#0-4) 

Concrete scenario (epoch-agnostic, any market with pending yield):
1. Owner broadcasts `setTrancheAPRSplitRatio` lowering the AA share from 50% → 20% (e.g., rebalancing incentives after NAV drift).
2. Pending accrued gain `G` exists since the last accounting (strategy price appreciated / interest accrued).
3. An AA holder (any unprivileged KYC'd lender) front-runs with a 1-wei `depositAA` (or a withdraw). `_updateAccounting` splits `G` at 50% to AA; the owner tx then lands.
4. Without the front-run, the owner's tx itself triggers no settlement, so the *next* deposit/withdraw by anyone would split all of `G` at 20% — the attacker's ordering choice decides the outcome, and they pick whichever ratio favors their tranche.

### Impact Explanation
Direct, quantified wealth transfer between tranche holders: the favored tranche receives `G * |oldRatio - newRatio| / FULL_ALLOC` more than the owner intended. Since `G` covers the entire period since the last accounting (potentially the full epoch duration between user interactions), the misallocated amount scales with TVL and time, not with the attacker's gas-cost dust deposit. The broken invariant is the fairness of the AA/BB interest waterfall — parameter changes are applied retroactively to accrued yield and the transaction ordering that determines the applied ratio is attacker-controllable.

### Likelihood Explanation
Requires (a) unsplit accrued gain at the moment of the setter tx and (b) a mempool-observable owner/manager transaction. Both are common: accounting only settles on user interactions, and on public mempools (Ethereum mainnet deployments) owner txs are trivially sandwichable. The attack costs one dust deposit and is repeatable for `setMinAprSplitAYS`/`setIsAYSActive` toggles. Likelihood is moderate — bounded by how often governance changes the split while yield is pending.

### Recommendation
Settle accounting inside the setter before overwriting the parameter, mirroring `setFeeParams`' `_accrueManagementFee()` pattern:

```solidity
function setTrancheAPRSplitRatio(uint256 _trancheAPRSplitRatio) external virtual {
    _checkOnlyOwner();
    _updateAccounting(); // settle pending yield at the old ratio first
    _checkAmountTooHigh((trancheAPRSplitRatio = _trancheAPRSplitRatio) > FULL_ALLOC);
}
```

Apply the same to `setMinAprSplitAYS` and `setIsAYSActive` in `IdleCDO`/`IdleCDOCreditVault` (and any setter that changes `fee`, `lossToleranceBps`, or other parameters consumed by `_updateAccounting`/`_virtualPriceAux` for already-accrued amounts). Alternatively document that ratio changes are intentionally retroactive and always bundle them with a preceding `harvest`/accounting call via the timelock — but settling in the setter is safer.

### Proof of Concept
Foundry fork test sketch (mainnet fork of a live IdleCDO with AYS disabled):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";
import "../contracts/IdleCDO.sol";

contract FrontRunSplitRatioPoC is Test {
    IdleCDO cdo = IdleCDO(0x_CDO_ADDRESS); // forked instance, isAYSActive == false
    address owner = cdo.owner();
    address aaHolder = 0x_AA_HOLDER;
    IERC20Detailed token = IERC20Detailed(cdo.token());

    function testFrontRunRatioChange() public {
        uint256 oldRatio = cdo.trancheAPRSplitRatio(); // e.g. 50_000
        uint256 priceAA_before = cdo.virtualPrice(cdo.AATranche());

        // --- time passes: strategy accrues yield, no one calls deposit/withdraw ---
        vm.roll(block.number + 100_000);
        // simulate pending gain G by warping time / mocking strategy price increase
        // (getContractValue() > lastNAVAA + lastNAVBB)

        uint256 pendingGain = cdo.getContractValue() -
            (cdo.lastNAVAA() + cdo.lastNAVBB());
        assertGt(pendingGain, 0);

        // === attacker (AA holder) front-runs owner's setTrancheAPRSplitRatio ===
        vm.prank(aaHolder);
        cdo.depositAA(1); // dust deposit forces _updateAccounting at oldRatio

        uint256 navAA_afterFrontRun = cdo.lastNAVAA();

        // === owner tx lands ===
        vm.prank(owner);
        cdo.setTrancheAPRSplitRatio(20_000);

        // Baseline without front-run: the pending gain would have been split at 20%.
        // Attacker's AA NAV captured gain at 50% instead.
        uint256 attackerExtra =
            pendingGain * (50_000 - 20_000) / cdo.FULL_ALLOC(); // * (1 - fee)
        assertGt(navAA_afterFrontRun, 0);
        // The extra AA NAV is exactly the redirected share:
        // navAA_afterFrontRun - (lastNAVAA_old + AA share at 20%) == attackerExtra
    }
}
```

The test asserts that the AA NAV crystallized by the dust `depositAA` reflects `oldRatio`, and that identical pending gain would have been split at `newRatio` had the owner tx executed first — i.e., the ordering, controlled by the attacker, decides who receives `G * Δratio / FULL_ALLOC`.

```text
  function _updateSplitRatio(uint256 tvlAARatio) internal virtual {
    uint256 _minSplit = minAprSplitAYS;
    _minSplit = _minSplit == 0 ? AA_RATIO_LIM_DOWN : _minSplit;

    if (isAYSActive) {
      uint256 aux;
      if (tvlAARatio >= AA_RATIO_LIM_UP) {
        aux = tvlAARatio == FULL_ALLOC ? FULL_ALLOC : AA_RATIO_LIM_UP;
      } else if (tvlAARatio > _minSplit) {
        aux = tvlAARatio;
      } else {
        aux = _minSplit;
      }
      trancheAPRSplitRatio = aux * tvlAARatio / FULL_ALLOC;
    }
  }
```
