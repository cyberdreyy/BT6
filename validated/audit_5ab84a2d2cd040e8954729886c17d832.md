### Title
FREEZE_SETTINGS does not protect a bank's e-mode risk parameters, letting `emode_admin` (or `admin`) silently override the "frozen risk profile" guarantee - ([File: programs/marginfi/src/instructions/marginfi_group/config_bank_emode.rs])

### Summary
`FREEZE_SETTINGS` is documented and implemented as a credible, irreversible commitment that a bank's risk parameters (weights, oracle setup, interest curves, init limits) cannot change once frozen. Every direct bank-configuration instruction correctly enforces this: `lending_pool_configure_bank`, `lending_pool_configure_bank_oracle`, `lending_pool_set_fixed_oracle_price`, and `lending_pool_configure_bank_interest_only`/`_limits_only` all check `bank.get_flag(FREEZE_SETTINGS)` and block or silently ignore risk-affecting changes. However, `lending_pool_configure_bank_emode` (callable by `emode_admin`) and `lending_pool_clone_emode` (callable by `emode_admin` or `admin`) never check `FREEZE_SETTINGS` at all, so they can freely overwrite `bank.emode.emode_config.entries` — which directly set `asset_weight_init`/`asset_weight_maint` used for collateral valuation in e-mode pairs — on a bank that is supposed to have its risk profile permanently locked.

### Finding Description
The freeze mechanism is documented explicitly: [1](#0-0) 

It is enforced consistently in every other bank-config code path, e.g. the primary configure instruction: [2](#0-1) 

...the oracle instruction: [3](#0-2) 

...the fixed-price instruction: [4](#0-3) 

...and the lite curve/limit instructions: [5](#0-4) 

But `lending_pool_configure_bank_emode`, gated only by `has_one = emode_admin`, writes directly to `bank.emode.emode_tag` and `bank.emode.emode_config.entries` (including the collateral asset weights) with no `FREEZE_SETTINGS` check whatsoever: [6](#0-5) 

Likewise `lending_pool_clone_emode`, callable by `admin` or `emode_admin`, overwrites the entire `emode` struct on a target bank without any freeze check: [7](#0-6) 

This is functionally the same bug class as the referenced report: a documented, security-relevant "lock" (there: role freezing via `AccessControlUpgradable`/`GranularRoles.hasRole`; here: `FREEZE_SETTINGS` on `Bank`) is bypassed because a specific privileged code path was not wired into the enforcement logic, even though every sibling code path enforces it correctly. In the referenced bug, `ADMIN_ROLE` bypassed the intended freeze via `hasRole`'s override; here, `emode_admin` (and even `admin` via clone) bypasses the intended freeze via a code path that omits the `FREEZE_SETTINGS` guard that its sibling instructions all implement.

### Impact Explanation
E-mode `asset_weight_init`/`asset_weight_maint` entries directly control how much borrowing power/collateral value a position receives for correlated-asset pairs — this is a risk parameter of the same class as the collateral/liability weights that `FREEZE_SETTINGS` is explicitly meant to lock (per `guides/ADMIN/BANK_STATE.md`: "cannot change anything that affects the risk profile of the bank (such as weights ... )"). Once a bank is frozen (e.g., to give depositors/integrators a credible commitment that terms won't change), the `emode_admin` role can still silently raise or lower effective collateral weights for e-mode pairs, undermining the guarantee users and integrators rely on. This can be used to increase leverage/borrowing power on a "frozen" bank (increasing protocol risk of bad debt) or to reduce it after users have taken positions relying on the frozen commitment (unexpectedly reducing borrowing power / triggering liquidations), i.e. a durable inconsistency with direct financial effect on borrowers' health and protocol solvency.

### Likelihood Explanation
This requires the `emode_admin` (a real, ordinarily-trusted but scoped delegate key, separate from full `admin`) key, or the group `admin` via `lending_pool_clone_emode`. It does not require an admin key compromise beyond what is already trusted for e-mode management — that key is intentionally scoped to a narrower, lower-trust purpose than full admin per the permissions guide, so use of it to bypass a documented freeze guarantee is a genuine violation of the intended guardrails (analogous to the referenced finding, which was rated High specifically because it broke an explicit, documented safety boundary rather than merely because "admin has power").

### Recommendation
Add the same `FREEZE_SETTINGS` guard used elsewhere to `lending_pool_configure_bank_emode` and `lending_pool_clone_emode` (as the destination bank check), e.g.:
```rust
check!(!bank.get_flag(FREEZE_SETTINGS), MarginfiError::Unauthorized /* or dedicated error */);
```
before mutating `bank.emode`. This makes the e-mode configuration path consistent with `lending_pool_configure_bank`, `lending_pool_configure_bank_oracle`, `lending_pool_set_fixed_oracle_price`, and `lending_pool_configure_bank_interest_only`/`_limits_only`, restoring the documented "frozen risk profile" guarantee.

### Proof of Concept
1. Group admin freezes a bank via `lending_pool_configure_bank` with `freeze_settings = true`, setting `FREEZE_SETTINGS` on `bank.flags` (confirmed test: `tests/specs/basic/04_configureBank.spec.ts` "(admin) Freeze USDC settings so they cannot be changed again").
2. Confirm oracle/config changes on this bank now fail/are ignored per `config_bank_oracle.rs`/`configure_bank.rs` checks.
3. As `emode_admin`, call `lending_pool_configure_bank_emode` on the same frozen bank with new `EmodeEntry` values (e.g., raising `asset_weight_init`/`asset_weight_maint` for a paired collateral tag) — this succeeds because `config_bank_emode.rs` performs no `FREEZE_SETTINGS` check (test infrastructure exists at `programs/marginfi/tests/admin_actions/setup_bank.rs` `configure_bank_emode_success` and `test-utils/src/marginfi_group.rs::try_lending_pool_configure_bank_emode`, none of which set/check `FREEZE_SETTINGS`).
4. Alternatively, `admin` or `emode_admin` calls `lending_pool_clone_emode` to overwrite the frozen bank's `emode` field wholesale from another bank, again with no freeze check.
5. Result: the bank's effective collateral risk parameters for e-mode pairs change even though `FREEZE_SETTINGS` is set, contradicting the documented guarantee that frozen banks cannot have risk-profile-affecting settings changed.

```rust
pub fn lending_pool_configure_bank_emode(
    ctx: Context<LendingPoolConfigureBankEmode>,
    emode_tag: u16,
    entries: [EmodeEntry; MAX_EMODE_ENTRIES],
) -> MarginfiResult {
    let mut bank = ctx.accounts.bank.load_mut()?;
    let group = ctx.accounts.group.load()?;

    let mut sorted_entries = entries;
    sorted_entries.sort_by_key(|e| e.collateral_bank_emode_tag);

    // Prevent footguns from passing data in padding, which could interfere with future values in
    // that assumed-empty space. Yes, we could simply take a struct without padding as input, but
    // having a separate config type has proved to be more of a pain than dealing with padding.
    for entry in sorted_entries.iter_mut() {
        entry.pad0 = [0; 5];
    }

    bank.emode.emode_tag = emode_tag;
    bank.emode.emode_config.entries = sorted_entries;
    bank.emode.timestamp = Clock::get()?.unix_timestamp;

    bank.emode.validate_entries_with_liability_weights(
        &bank.config,
        group.emode_max_init_leverage,
        group.emode_max_maint_leverage,
    )?;

    if bank.emode.emode_config.has_entries() {
        msg!("emode entries detected and activated");
        bank.emode.update_emode_enabled();
    } else {
        msg!("no emode entries detected");
        bank.emode.update_emode_enabled();
    }

    msg!(
        "emode tag set to {:?} entries set to: {:?}",
        emode_tag,
        sorted_entries
    );

    Ok(())
}
```

```rust
pub fn lending_pool_clone_emode(ctx: Context<LendingPoolCloneEmode>) -> MarginfiResult {
    let group = ctx.accounts.group.load()?;

    check!(
        ctx.accounts.signer.key() == group.admin || ctx.accounts.signer.key() == group.emode_admin,
        MarginfiError::Unauthorized
    );

    let source_bank = ctx.accounts.copy_from_bank.load()?;
    let mut destination_bank = ctx.accounts.copy_to_bank.load_mut()?;

    destination_bank.emode = source_bank.emode;

    msg!(
        "emode settings copied from {:?} to {:?}",
        ctx.accounts.copy_from_bank.key(),
        ctx.accounts.copy_to_bank.key()
    );

    Ok(())
}
```
