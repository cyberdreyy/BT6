### Title
Blacklisted async-deposit/redeem requester permanently freezes escrowed funds in `ProvisionerV2` refund/cancel/solve paths - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2` escrows a user's tokens (or vault units) when they call `requestDeposit`/`requestRedeem`, and later releases them via `refundRequest`, `cancelRequest`, or the solver-facing `_solveDepositVaultFixedPrice`/`_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice`/`_solveRequestDirect` refund branches, all of which funnel through `_transferWithFallback` [1](#0-0) . If the fallback recipient (`requester`) is blacklisted by the underlying ERC20 (e.g. USDC), or if `receiver == requester` for a self-refund, the final transfer leg is an un-guarded `safeTransfer` that reverts, causing the whole transaction — and the state-clearing of the request hash — to revert as well, since the hash is cleared before the transfer inside the same call and Solidity reverts roll back all effects together [2](#0-1) . This permanently locks the escrowed funds in the contract with no code path able to release them.

### Finding Description
The relevant flow:
1. An ordinary user calls `requestDeposit(token, tokensIn, minUnitsOut, ..., receiver)` (public, `anyoneButVault`), pulling `tokensIn` into `ProvisionerV2` and recording `asyncRequestHashes[depositHash] = true` [3](#0-2) . The same pattern applies to `requestRedeem`, which escrows vault units instead [4](#0-3) .
2. Before the request is solved, the requester's address becomes blacklisted on the debt/deposit token (USDC-style token, in-scope per Aera's asset list).
3. After the deadline passes, anyone can call `refundRequest(token, request)` (`request.deadline < block.timestamp` OR authorized) [5](#0-4) . This calls `_clearHashAndTransferRefund`, which unsets the hash **then** calls `_transferWithFallback(transferToken, requester, request.receiver, amount)` [2](#0-1) .
4. `_transferWithFallback` only wraps the transfer to `receiver` in a try (`trySafeTransfer`); the fallback transfer to `requester` uses a plain `safeTransfer` that reverts on failure:
```solidity
function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
    if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
        token.safeTransfer(requester, amount);
    }
}
``` [1](#0-0) 
If `requester` (i.e., `request.user`, the original depositor/redeemer) is blacklisted — which is the common case since users typically set `receiver == msg.sender` — the `receiver == requester` branch skips the try path entirely and goes straight to the reverting `safeTransfer`. Because the hash-clearing effect (`asyncRequestHashes[requestHash] = false`) happens in the same transaction before the revert, the entire transaction (including the hash-clear) rolls back, leaving `asyncRequestHashes[requestHash] = true` forever. The identical unguarded-fallback pattern also exists in `_solveDepositVaultFixedPrice`, `_solveRedeemVaultAutoPrice`, `_solveRedeemVaultFixedPrice`, and `_solveRequestDirect`'s refund branches, all of which call `_transferWithFallback` with `request.user` as the fallback address [6](#0-5) [7](#0-6) [8](#0-7) . No path in `ProvisionerV2` allows an admin or the user to recover tokens once the hash is permanently stuck with no working refund path (no rescue/sweep function is present in this contract).

This directly mirrors the report's root cause: an outbound transfer to a specific address that becomes blacklisted is not wrapped in a try/catch (or is wrapped incompletely, only for the primary recipient but not the fallback), causing the refund transaction — and thus the whole recovery mechanism — to permanently revert, freezing escrowed user funds.

### Impact Explanation
Escrowed deposit tokens (or vault units, for redeem requests) become permanently locked in `ProvisionerV2` with no way to retrieve them once the requester is blacklisted by the token issuer, since every code path that could release the escrow (`refundRequest`, `cancelRequest`'s underlying `_clearHashAndTransferRefund`, and the async-solve refund branches) reverts unconditionally when the fallback destination address is blacklisted. This is a permanent freezing of user funds, not merely temporary, since `asyncRequestHashes[requestHash]` can never be successfully cleared through any exposed function.

### Likelihood Explanation
Requires: (1) the deposit/redeem token supports blacklisting (e.g., USDC, in scope per Aera's supported asset list), and (2) the requester's address gets blacklisted after submitting an async request but before/instead of it being solved (a realistic real-world event for any USDC holder subject to compliance action, sanctions, or accidental blacklisting). No privileged role, collusion, or third-party fault is needed — the DOS is triggerable by ordinary token-issuer action against an ordinary user's own address, and the resulting freeze is then permanent regardless of who calls `refundRequest` afterward (even a helpful third party cannot rescue the funds).

### Recommendation
Wrap the fallback transfer in `_transferWithFallback` with a try/catch (or `trySafeTransfer`) as well, and if both the primary and fallback transfers fail, retain the escrowed funds under a separate, explicitly claimable/admin-recoverable accounting entry (e.g., a per-user "stuck funds" ledger) instead of reverting the hash-clearing effects. Ensure the hash is cleared regardless of transfer outcome so the request lifecycle can complete, and expose a rescue mechanism for such stuck balances.

### Proof of Concept
1. Deploy `ProvisionerV2` with a mock blacklistable ERC20 (`MockBlacklistToken`) as the deposit token, mimicking USDC's `isBlacklisted`/transfer-revert behavior.
2. As `alice`, call `requestDeposit(token, 100e6, minUnitsOut, 0, deadline, maxPriceAge, true, alice)` — tokens move from `alice` to `ProvisionerV2`; `asyncRequestHashes[depositHash] = true`.
3. Warp past `deadline` without any solver acting on the request.
4. Call `token.setBlacklisted(alice, true)`.
5. Call `provisioner.refundRequest(token, request)` from any address.
   - Assert: the call reverts (bubbling up the token's blacklist revert) because `_transferWithFallback` hits `receiver == requester` and calls the unguarded `safeTransfer(alice, amount)`.
6. Assert: `asyncRequestHashes[depositHash]` is still `true` (unchanged from step 2), and repeated calls to `refundRequest`/`cancelRequest` always revert the same way — confirming `100e6` tokens are permanently stuck in `ProvisionerV2` with no recoverable path.

    /// @inheritdoc IProvisionerV2
    function refundRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: deadline is in the past or authorized
        require(
            request.deadline < block.timestamp || isAuthorized(msg.sender, msg.sig),
            Aera__DeadlineInFutureAndUnauthorized()
        );

        if (_isRequestTypeDeposit(request.requestType)) {
            // Effects + interactions: clear hash, emit refund event, and transfer full token amount with fallback
            _clearHashAndTransferRefund(token, request, request.user, request.tokens, token);
        } else {
            // Effects + interactions: clear hash, emit refund event, and transfer full unit amount with fallback
            _clearHashAndTransferRefund(token, request, request.user, request.units, IERC20(MULTI_DEPOSITOR_VAULT));
        }
    }

    function requestDeposit(
        IERC20 token,
        uint256 tokensIn,
        uint256 minUnitsOut,
        uint256 solverTip,
        uint256 deadline,
        uint256 maxPriceAge,
        bool isFixedPrice,
        address receiver
    ) public anyoneButVault returns (bytes32 depositHash) {
        // Requirements: token amount and min units out are positive, async deposits are enabled
        _validateNonZeroAmounts(minUnitsOut, tokensIn);
        require(tokensDetails[token].asyncDepositEnabled, Aera__AsyncDepositDisabled());

        // Requirements: common request validation
        _validateRequest(receiver, solverTip, deadline, isFixedPrice);

        RequestType requestType = _getRequestType(isFixedPrice, true);

        // Interactions: transfer tokens from sender to provisioner
        token.safeTransferFrom(msg.sender, address(this), tokensIn);

        depositHash = _getRequestHashParams(
            token, msg.sender, receiver, requestType, tokensIn, minUnitsOut, solverTip, deadline, maxPriceAge
        );

        // Requirements: hash has not been used
        require(!asyncRequestHashes[depositHash], Aera__HashCollision());

        // Effects: set hash as used
        asyncRequestHashes[depositHash] = true;
