### Title
`store.List()` checks base64-encoded line length instead of decoded message length, allowing a crafted masking.db entry to trigger an out-of-range slice panic - ([File: commands/helpers/internal/store/store.go])

### Summary
`Store.List()` at [1](#0-0)  decodes each line to `msg` via base64, then validates length using `len(line)` (the *encoded* string) instead of `len(msg)` (the *decoded* bytes) against `s.c.NonceSize()`. Because base64 expands 3 decoded bytes into 4 encoded characters, a line can be long enough in encoded form to pass the check while decoding to fewer bytes than `NonceSize()` (24, since `chacha20poly1305.NewX` uses a 24-byte nonce), causing `msg[:s.c.NonceSize()]` to panic with an out-of-range slice.

### Finding Description
`List()` reads each newline-delimited entry from `masking.db`, base64-decodes it into `msg`, then does:
```go
if len(line) < s.c.NonceSize() {
    return results, fmt.Errorf("encrypted message length too small")
}
nonce, ciphertext := msg[:s.c.NonceSize()], msg[s.c.NonceSize():]
``` [1](#0-0) 

`line` is the base64-encoded text (plus trailing `\n`); `msg` is the decoded byte slice, which is roughly `3/4` the length of `line`. A crafted 24-character base64 line (no padding, e.g. 6 groups of 4 chars) plus its newline gives `len(line) == 25 >= 24`, satisfying the check, but decodes to only 18 bytes (`len(msg) == 18 < 24`). The subsequent `msg[:s.c.NonceSize()]` (`msg[:24]`) then panics with "slice bounds out of range" since `msg` only has 18 elements.

Legitimate entries are only ever produced by `Store.Add()`, which base64-encodes `nonce + ciphertext (with Seal overhead)`, always producing a decoded length `>= NonceSize()+Overhead()` — so this bug is unreachable through normal `Add()`/`List()` usage. It is only reachable if something else appends malformed content directly to `masking.db`.

`masking.db` lives in the job's `RUNNER_TEMP_PROJECT_DIR` / `TmpProjectDir()`, as seen in `commands/helpers/proxy_exec.go`'s `NewProxy` (`store.Open(dir)` → `addmask.New(db, ...)` → `db.List()`) [2](#0-1) , and in `shells/proxy_exec.go`, which wires `info.Build.TmpProjectDir()` as the directory passed to `proxy-exec --temp-dir` for every shell step when `IsProxyExec()` is enabled [3](#0-2) . Since `TmpProjectDir` is the job's own working directory tree, a job's own script (running as the same OS user as the runner helper on shell/non-isolated executors, or with filesystem access to that path in general) can write an arbitrary file to it, including appending a crafted line to `masking.db` before a later step invokes `proxy-exec` again.

No existing check in `List()` prevents this: the length check is checking the wrong value entirely, and there is no `recover()` around the decode/slice logic in `List()`, `NewProxy`, or the `proxy-exec` command entrypoint.

### Impact Explanation
A job that can write into its own `TmpProjectDir` can cause the `gitlab-runner-helper proxy-exec` process (invoked for every subsequent shell step of that job, when proxy-exec/masking is enabled) to panic when it calls `store.Open` → `addmask.New` → `List()` to preload prior masked secrets. This crashes the helper process handling that job step, breaking that step's execution (and any later steps in the same job that also go through `proxy-exec`), until the malformed `masking.db` is removed. This matches the scoped impact: crash of `proxy-exec` for jobs sharing that directory.

### Likelihood Explanation
This requires a build using `ProxyExec`/masking (`config.ProxyExec` / `IsProxyExec()`) with at least one job step where the job script has write access to `TmpProjectDir` before a subsequent `proxy-exec` invocation reads `masking.db`, which is the normal case for shell-executor jobs where the job process and the runner helper share the filesystem and often the same OS user. Constructing the crafted base64 line is deterministic and requires no cryptographic secrets — any base64 string whose encoded length (plus `\n`) is `>= NonceSize()` but whose decoded length is `< NonceSize()` triggers it (e.g., 24 base64 chars decoding to 18 bytes). This is fully attacker/job-controlled and repeatable.

### Recommendation
Fix the length check in `List()` to validate the decoded message length, not the encoded line length:
```go
msg, err := base64.StdEncoding.DecodeString(strings.TrimSuffix(line, "\n"))
if err != nil {
    return results, fmt.Errorf("decoding msg: %w", err)
}
if len(msg) < s.c.NonceSize() {
    return results, fmt.Errorf("encrypted message length too small")
}
```
Additionally, consider wrapping the per-line parsing in `List()` so a single malformed line only skips that entry (with a logged warning) rather than aborting/panicking the whole read, to make the helper more resilient to a corrupted or tampered `masking.db`.

### Proof of Concept
```go
// store_malformed_test.go (package store)
func TestList_MalformedShortLine_DoesNotPanic(t *testing.T) {
    dir := t.TempDir()

    db, err := Open(dir)
    require.NoError(t, err)
    require.NoError(t, db.Add("legit-secret")) // ensures key material exists
    db.Close()

    // Craft a base64 line whose encoded length >= NonceSize() (24)
    // but whose decoded length < NonceSize(): 24 base64 chars -> 18 bytes.
    crafted := strings.Repeat("A", 24) + "\n"

    pathname := filepath.Join(dir, "masking.db")
    f, err := os.OpenFile(pathname, os.O_APPEND|os.O_WRONLY, 0o644)
    require.NoError(t, err)
    _, err = f.WriteString(crafted)
    require.NoError(t, err)
    f.Close()

    db2, err := Open(dir)
    require.NoError(t, err)
    defer db2.Close()

    require.NotPanics(t, func() {
        _, _ = db2.List()
    })
    _, err = db2.List()
    require.Error(t, err) // should return an error, not panic
}
```
Expected current behavior: the test panics inside `List()` at `msg[:s.c.NonceSize()]` with "slice bounds out of range"; after the fix, `List()` returns an error (`"encrypted message length too small"`) instead.
