## Title
Stale confirmations from removed multisig members still count toward quorum, allowing requests to execute below the live-member threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
When a multisig member is removed via `DeleteMember` (in `multisig2`) or `DeleteKey` (in `multisig`), the contract only purges *requests that member originally created*, but never scrubs that member's existing *confirmations* on requests created by other members. A confirmation cast by a member while they were still valid continues to count toward `num_confirmations` even after that member has been deleted, letting a request execute with fewer live-member approvals than the configured threshold.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides whether to execute a request purely by comparing the size of the stored `confirmations: HashSet<String>` for that `request_id` against `num_confirmations`: [1](#0-0) 

`delete_member()` removes the member from `self.members` and deletes access keys, but only cleans up `requests`/`confirmations` for requests where `r.member == member` — i.e. requests that member *authored*, not requests they merely confirmed: [2](#0-1) 

If member `B` confirms a request `R` authored by member `A`, and `B` is subsequently removed from the multisig (via a separate, properly-quorate `DeleteMember` request), `B`'s entry remains inside `self.confirmations[R]`. That stale confirmation is never invalidated, so it still counts when a later, live member confirms `R` — the sum can reach `num_confirmations` even though only one *currently valid* member (plus one *former* member) actually approved it.

The equivalent bug exists in the legacy `multisig/src/lib.rs` contract via the `DeleteKey` action, which only purges requests where `r.signer_pk == pk` (the deleted key's own authored requests): [3](#0-2) 

This is the direct NEAR analog of the Sherlock M-8 bug class: an authorization artifact (partyB's `singleUpnlSig` / here, a member's `confirm`) that was valid under one state of the world (partyA not yet liquidated / member still active) is consumed later under a materially different state (partyA already partially liquidated / member already removed), letting the custody-affecting action (fund deallocation / multisig fund transfer) execute on stale authorization instead of being revalidated against current state. The binding broken is: `confirmations counted for request R == confirmations by currently-live members for R`. This invariant is violated once membership changes after a confirmation was cast but before the request finished collecting quorum.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding explicitly called out as Critical: a `Transfer`, `AddKey`/`AddMember`, `FunctionCall`, or `DeployContract` multisig request can be executed with effectively fewer independent, currently-authorized approvals than `num_confirmations` requires. Since multisig requests include `Transfer` (moving NEAR) and `AddKey`/`AddMember` (granting new signing authority over the account), this can lead to unauthorized movement of funds or unauthorized privilege escalation on the multisig account — i.e., a multisig request executed below its intended threshold.

### Likelihood Explanation
No victim keys, redeploys, or foundation/owner privileges are required beyond the normal, intended operation of the multisig: any legitimate member can confirm a request, and any legitimate quorum can later vote to remove another member (e.g., due to a compromised or departing member) — this is exactly the scenario the removal feature exists for. The flaw is triggered purely by the ordinary sequence "member confirms a still-pending request" → "that member is later removed" → "the pending request is later completed by other members," which is a realistic operational pattern (pending requests can persist, and `REQUEST_COOLDOWN` even actively encourages requests staying open for at least 15 minutes).

### Recommendation
When removing a member (`delete_member` in `multisig2`, `DeleteKey` handling in `multisig`), iterate all `confirmations` entries (not only `requests` authored by that member) and remove the departing member's/key's confirmation from every pending request's confirmation set. Alternatively, when checking quorum in `confirm()`, re-validate that every entry in the stored confirmation set still corresponds to a current member (filter `confirmations` against `self.members`/live keys before comparing against `num_confirmations`), rather than trusting the raw stored `HashSet` length.

### Proof of Concept
Using `multisig2` semantics (3 members A, B, C; `num_confirmations = 2`):
1. `A.add_request(R)` — creates request `R` (author = `A`), 0 confirmations.
2. `B.confirm(R)` — `confirmations[R] = {B}` (len 1 < 2, not yet executed).
3. Separately, quorum (`A` + `C`) approves and executes a `DeleteMember { member: B }` request. `delete_member` removes `B` from `self.members`, but since `B` did not author `R`, `confirmations[R]` is left untouched, still containing `B`.
4. `C.confirm(R)` — `current_member()` returns `C` (valid). `confirmations[R].len() + 1 = 2 >= num_confirmations (2)` → `R` executes.
5. Result: `R` (e.g. a `Transfer` of funds) executed with confirmations from only one currently-valid member (`C`) plus one confirmation from an already-removed member (`B`), instead of two confirmations from currently-live members as the `num_confirmations = 2` policy requires.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
