## Title
Builder pending‑withdrawal amount is not capped to builder balance before being committed to the execution payload, causing Gwei creation — (`specs/gloas/beacon-chain.md`, `get_builder_withdrawals`)

### Summary
`get_builder_withdrawals` builds the `Withdrawal` objects for `state.builder_pending_withdrawals` using the raw, requester-supplied `withdrawal.amount` with no check against the builder's actual balance. This value is what ends up in `state.payload_expected_withdrawals`, i.e. the amount the execution layer will actually pay out. The only place that clamps to the builder's real balance is `apply_withdrawals`, which uses `min(withdrawal.amount, builder_balance)` purely to update the *consensus-layer* bookkeeping (`state.builders[...].balance`). The clamped value never propagates back into the committed `Withdrawal.amount`. Since the spec's own commentary states that "the execution layer mints the full committed amount regardless" of any consensus-layer capping, an under-collateralized builder pending withdrawal causes the EL to mint Gwei that has no consensus-layer balance behind it — the exact "discount factor bypass" pattern from the external report (a paid-out amount silently exceeding what the ledger actually reserved).

### Finding Description
In `get_builder_withdrawals`: [1](#0-0) 

the withdrawal is built directly from the queued `withdrawal.amount` with **no comparison to `state.builders[builder_index].balance`**:
```python
builder_index = withdrawal.builder_index
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal.amount,
    )
)
```

Contrast this with the sibling function for validator pending partial withdrawals, which explicitly caps the amount to the available balance *before* constructing the `Withdrawal`: [2](#0-1) 
```python
balance = get_balance_after_withdrawals(state, validator_index, all_withdrawals)
if is_eligible_for_partial_withdrawals(validator, balance):
    withdrawal_amount = min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)
    withdrawals.append(Withdrawal(..., amount=withdrawal_amount))
```

For builders, the analogous clamp is applied only later, in `apply_withdrawals`, and only to the internal balance ledger, not to the `Withdrawal.amount` already placed in `state.payload_expected_withdrawals`: [3](#0-2) 
```python
def apply_withdrawals(state: BeaconState, withdrawals: Sequence[Withdrawal]) -> None:
    for withdrawal in withdrawals:
        if is_builder_index(withdrawal.validator_index):
            builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
            builder_balance = state.builders[builder_index].balance
            state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
        else:
            decrease_balance(state, withdrawal.validator_index, withdrawal.amount)
```

The spec text itself confirms the payout semantics: whatever amount is committed in `payload_expected_withdrawals` is what the EL mints, independent of any CL-side saturation: [4](#0-3) 

Concrete before/after on a specific state (mirrors the repo's own test):
- Pre-state: `state.builders[0].balance = 1_000_000_000` (1 ETH). `state.builder_pending_withdrawals = [BuilderPendingWithdrawal(builder_index=0, amount=5_000_000_000, fee_recipient=addr)]`.
- `get_builder_withdrawals` emits `Withdrawal(validator_index=builder_flag(0), address=addr, amount=5_000_000_000)` — the full 5 ETH, unclamped.
- `apply_withdrawals` sets `state.builders[0].balance = 1_000_000_000 - min(5_000_000_000, 1_000_000_000) = 0`.
- `state.payload_expected_withdrawals` still records `amount = 5_000_000_000`, which the EL will pay to `addr` in full.
- Result: 4 ETH is paid to `addr` with no corresponding balance ever having existed for it on the consensus layer — a straightforward Gwei-creation event. This exact behavior is asserted as expected in the repository's own test: [5](#0-4) 

### Impact Explanation
This breaks the "Gwei created ... or paid to a non-owner" equality: the amount the execution layer mints/pays out (`Withdrawal.amount` in the committed payload) can exceed the amount the consensus layer actually held and removed from the builder's balance. Any builder whose pending withdrawal request amount is not fully covered by its current balance (e.g., due to slashing, prior payments, or simply requesting more than is deposited) causes the block to commit an execution payload withdrawal larger than what CL state can back, inflating total supply — a Critical-class issue per the task's rubric ("Gwei created, destroyed, or paid to a non-owner").

### Likelihood Explanation
The `builder_pending_withdrawals` queue is populated from data outside strict cross-validation with the builder's live balance (e.g., via `settle_builder_payment` appending withdrawals for payments, or from prior epochs where the builder's balance may have since decreased due to other pending withdrawals or slash31); nothing in `process_execution_payload_bid`/pending payment settlement guarantees the queued amount can never exceed the current balance at the time `get_builder_withdrawals` runs. No malicious peer, coalition, or client bug is required — any block proposer that processes an ordinary block once a builder's balance has dropped below a previously queued withdrawal amount will trigger this discrepancy as ordinary state transition.

### Recommendation
Cap the amount placed in the `Withdrawal` object to the builder's current balance at construction time, matching the pattern already used for validator partial withdrawals:
```python
builder_index = withdrawal.builder_index
builder_balance = state.builders[builder_index].balance
withdrawal_amount = min(withdrawal.amount, builder_balance)
withdrawals.append(
    Withdrawal(
        index=withdrawal_index,
        validator_index=convert_builder_index_to_validator_index(builder_index),
        address=withdrawal.fee_recipient,
        amount=withdrawal_amount,
    )
)
```
This keeps `apply_withdrawals`'s bookkeeping and the actually-committed/minted `Withdrawal.amount` consistent, eliminating the supply-inflation path.

### Proof of Concept
1. Register builder `B` with `balance = 1 ETH`.
2. Queue `BuilderPendingWithdrawal(builder_index=B, amount=5 ETH, fee_recipient=A)` in `state.builder_pending_withdrawals`.
3. Call `get_expected_withdrawals(state)` → `payload_expected_withdrawals` contains `Withdrawal(validator_index=builder_flag(B), address=A, amount=5 ETH)`.
4. Call `process_withdrawals(state)` → `apply_withdrawals` sets `state.builders[B].balance = 0`; the committed withdrawal amount remains 5 ETH.
5. Per spec, the execution layer mints/pays 5 ETH to `A` although the consensus layer only ever tracked/removed 1 ETH for `B` — 4 ETH created with no backing, matching the existing test's expected values. [5](#0-4)

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],

    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(

                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

*Note*: Unlike deposits (which are applied at the child's slot via
`apply_parent_execution_payload`), withdrawal balance deductions are applied
immediately via `apply_withdrawals`. Deferring the deduction to the child's slot
would break the total supply invariant: state transitions between the commitment
slot and the deduction slot (e.g., `process_pending_consolidations` at an epoch
boundary) can reduce a validator's balance below the committed withdrawal
amount, causing `decrease_balance` to saturate at zero. Since the execution
layer mints the full committed amount regardless, any CL-side saturation creates
a net supply inflation. As a consequence, `state.balances` reflects the
withdrawal deduction before the corresponding execution payload is confirmed,
creating a transient asymmetry with the EL state at `state.latest_block_hash`.
Off-chain consumers that require CL/EL balance consistency can reconstruct
pre-deduction balances by adding back `state.payload_expected_withdrawals`.
