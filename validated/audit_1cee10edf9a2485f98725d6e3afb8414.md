### Title
Unbounded Connection Acceptance in RPC PubSub WebSocket Listener Enables Resource-Exhaustion DoS - (File: rpc/src/rpc_pubsub_service.rs)

### Summary
The RPC PubSub WebSocket server's `listen` loop accepts every incoming TCP connection unconditionally and spawns an unbounded tokio task per connection, with no per-IP or global connection cap analogous to the ones enforced on the TPU QUIC ingest path. An unauthenticated remote client can open large numbers of parallel WebSocket connections to exhaust validator memory/file-descriptor/thread resources, mirroring the "many parallel unauthenticated read connections" DoS class described in the referenced indy-node report (CVE-2022-31006).

### Finding Description
`PubSubService::listen` binds a `TcpListener` and, in its accept loop, unconditionally accepts every connection and spawns a new task to handle it, only wrapping it with a metrics `TokenCounter` (which records but does not limit): [1](#0-0) 

This contrasts sharply with the TPU QUIC ingest path in `streamer/src/nonblocking/quic.rs` and `streamer/src/nonblocking/swqos.rs`, where every incoming connection is subject to: an overall connection-rate limiter, a per-IP `ConnectionRateLimiter`, and per-peer/staked/unstaked connection caps enforced via `SwQos::try_add_connection` and `ClientConnectionTracker::new(..., qos.max_concurrent_connections())`: [2](#0-1) [3](#0-2) 

The `rpc_pubsub` config (`PubSubConfig`) only exposes `max_active_subscriptions` (default 1,000,000) and queue-capacity limits that bound subscriptions/notifications per already-established connection, but there is no configuration or code path limiting the number of concurrent TCP/WebSocket connections that can be opened in the first place: [4](#0-3) 

Each accepted connection performs a WebSocket handshake and then loops on `receiver.receive_data` and `IoHandler::handle_request`, holding a socket, buffers, an `IoHandler`, and a broadcast receiver subscription for its lifetime: [5](#0-4) 

Since `--rpc-pubsub-*` flags govern only application-level subscription/queue quotas and not raw connection admission, a public, unauthenticated attacker can open an effectively unbounded number of raw TCP connections (with or without ever completing the WebSocket handshake) to consume validator sockets, memory, and tokio task/thread resources — directly analogous to the "500 parallel read requests per node" attack pattern in the report, but here compounded by lack of any per-IP admission control (the QUIC/TPU path's `ConnectionRateLimiter` has no counterpart here).

### Impact Explanation
A successful attack can starve the validator's RPC PubSub service of file descriptors, memory, and tokio scheduler capacity, denying legitimate RPC/PubSub clients (including downstream services relying on account/slot/signature subscriptions) — an availability impact against the JSON RPC surface without requiring any stake, funds, or privileged access. This does not affect consensus but degrades a public-facing validator service in the same manner the report describes for indy-node's public read-request endpoint.

### Likelihood Explanation
The RPC PubSub port is by design exposed to any client and requires no authentication to open a TCP/WebSocket connection; opening thousands of parallel sockets from one or more hosts is straightforward and matches exactly the attacker model used in the referenced report (unprivileged remote client, no allowlist possible for read-only public endpoints). Likelihood is high wherever operators expose `--rpc-pubsub-address`/full RPC to the public internet, which is common practice.

### Recommendation
Add connection-level admission control to `PubSubService::listen` mirroring the TPU QUIC protections: a global concurrent-connection cap, a per-IP concurrent-connection cap and/or per-IP new-connection rate limiter (reusing `streamer::nonblocking::connection_rate_limiter::ConnectionRateLimiter` or an equivalent), and a handshake timeout so that half-open/idle sockets are reclaimed quickly. Expose these as configurable `--rpc-pubsub-*` CLI options with sane defaults, and reject/close connections that exceed limits before allocating per-connection buffers.

### Proof of Concept
1. Start a validator with default full RPC / RPC PubSub enabled (`--rpc-pubsub-address` reachable).
2. From an attacker host (or several), open N (e.g., tens of thousands) raw TCP connections to the PubSub port, either completing minimal WebSocket handshakes or leaving them pending, without ever closing them (analogous to the report's 500-parallel-connections-per-VM, scaled).
3. Observe in `rpc_pubsub_service.rs::listen` that every connection is accepted and a task is spawned regardless of source IP or total count, since only a metrics counter (`TokenCounter`) tracks them: [6](#0-5) .
4. Legitimate PubSub/RPC clients experience connection refusals, severe latency, or the RPC PubSub thread becoming unresponsive as descriptors/memory are exhausted, reproducing the "unreachable network" denial-of-service outcome described in the referenced report.
