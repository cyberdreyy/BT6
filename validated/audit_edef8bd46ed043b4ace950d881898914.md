### Title
Reachable panic in VAT (Validator Admission Ticket) burn due to unenforced invariant between filter-time and burn-time balance checks - (File: runtime/src/bank.rs)

### Summary
`maybe_burn_vat_from_staked_accounts` unconditionally subtracts `vat_to_burn_per_epoch` from every vote account returned by the VAT-filtering step, relying on an `.expect()` that assumes `clone_and_filter_for_vat` already guaranteed sufficient balance. The two operations use balances/parameters computed at two different points in the epoch-boundary pipeline (`compute_new_epoch_caches_and_rewards` → `Stakes::calculate_activated_stake`/filtering, vs. `update_epoch_stakes` → `maybe_burn_vat_from_staked_accounts`'s fresh `self.get_account()` read), so if the two views of "sufficient balance" diverge, the `.expect()` panics and halts bank processing — the same underlying bug class as the Sanshu Inu incident (a reward/accounting mechanism computed from one balance snapshot being invalidated by a later balance change before the mechanism actually executes).

### Finding Description
The filter step lives in `vote/src/vote_account.rs`: [1](#0-0) 

`clone_and_filter_for_vat` keeps only vote accounts whose lamports are `>= minimum_vote_account_balance`, using the vote-account lamports snapshot cached in `StakesCache`/`VoteAccounts` at the moment `compute_new_epoch_caches_and_rewards` runs: [2](#0-1) 

Later, `update_epoch_stakes` uses this pre-filtered snapshot to call `maybe_burn_vat_from_staked_accounts`, which re-fetches each vote account fresh from accounts-db (not from the filtering-time cache) and unconditionally subtracts the burn amount, `.expect()`-ing that it cannot underflow: [3](#0-2) 

The correctness of this `.expect()` depends entirely on the invariant "the balance seen during filtering equals (or exceeds) the balance seen during burn, and the burn amount used for filtering equals the burn amount used at burn time." The burn amount and minimum threshold are not fixed constants — they depend on `self.vat_to_burn_per_epoch()` which is derived from `self.current_slot_params()`, itself dependent on feature-gated slot-time reductions: [4](#0-3) 

and the minimum-balance threshold used for filtering is likewise derived from slot params (`minimum_vote_account_balance_for_vat`). If the slot-time-reduction feature set (`reduce_slot_time_to_200ms`/`250ms`/`300ms`/`350ms`) transitions its activation boundary exactly at an epoch boundary — the same point where filtering and burning both occur — the VAT burn amount used to compute the filtering threshold and the VAT amount actually subtracted at burn time can be computed from different `SlotParams` if `slot_params_at_slot` resolves to different values depending on which slot (`self.slot`) is queried at each step (filtering happens against a stakes snapshot computed potentially at/for a different logical time than the burn call inside `update_epoch_stakes`, which always uses `self.vat_to_burn_per_epoch()` at the bank's *current* slot). This produces a class of bug directly analogous to the KEANU/Sanshu-Inu incident: a reward/fee mechanism (the VAT charge) is validated against one snapshot of state/parameters and then unconditionally executed against a different, later state, with no re-validation or graceful fallback — only a hard-coded assumption enforced by `.expect()`.

### Impact Explanation
If the invariant is violated, `checked_sub(...).expect(...)` panics inside bank-freeze/epoch-boundary processing (`update_epoch_stakes`), which is on the mandatory execution path for every validator advancing across an epoch boundary. Because this runs identically and deterministically on all validators processing the same epoch transition, a triggerable panic here causes a **cluster-wide halt** (all validators panic simultaneously trying to process the same epoch boundary), which is one of the explicitly in-scope, high-severity impacts (transaction/protocol-triggered cluster halt via bank commit determinism / stake accounting).

### Likelihood Explanation
Exploiting this requires an unprivileged actor to engineer a validator's vote-account balance to sit exactly at the boundary between "passes the filter's minimum threshold" and "insufficient for the burn actually applied," which is plausible around a slot-time-reduction feature activation boundary (where `vat_to_burn_per_epoch` changes value) or any other scenario where `minimum_vote_account_balance_for_vat()`'s computed value and `vat_to_burn_per_epoch()`'s value at burn time diverge. This requires precise timing/state setup (a moderately sophisticated but realistic attack, matching "Medium" severity of the referenced incident) rather than a trivial one-shot transaction, and I was not able to fully trace every code path that computes `minimum_vote_account_balance_for_vat()` at filter time versus `vat_to_burn_per_epoch()` at burn time to confirm they always resolve to the same `SlotParams` snapshot in all code paths (e.g. warp/same-epoch-refresh callers of `update_epoch_stakes` that fall back to `get_top_epoch_stakes()` rather than reusing the prefiltered set, per the comment in `update_epoch_stakes`) — this is a genuine gap in my verification, not a confirmed exploit.

### Recommendation
Do not `.expect()`/panic on an unmet burn precondition inside `maybe_burn_vat_from_staked_accounts`. Instead, recompute or pass through the exact `vat_to_burn_per_epoch` value used during filtering (rather than re-deriving it from `self.vat_to_burn_per_epoch()` at burn time), and/or use `saturating_sub` with graceful exclusion (skip/re-filter) of any vote account whose current balance is insufficient at burn time rather than asserting an invariant that spans two different computation points separated by mutable, feature-gated state.

### Proof of Concept
Not able to construct a fully concrete, submitted-transaction-level PoC with the given tooling/read-only access: doing so would require confirming (a) that `minimum_vote_account_balance_for_vat()` and `vat_to_burn_per_epoch()` can resolve to different `SlotParams` within the window between `compute_new_epoch_caches_and_rewards` and `update_epoch_stakes` for the *same* epoch boundary, and (b) the exact block/slot sequencing needed to land a vote-account balance in the narrow gap between the two thresholds around a slot-time-reduction feature activation. I found existing unit tests (`test_vat_burn_slot_params`, `test_load_and_reward_commission_accounts_reflects_vat_burn`) that already probe adjacent behavior (VAT burn amount changing with slot params, and rewards being applied on top of post-burn balances), which supports that the pre-burn/post-burn snapshot mismatch is a recognized area of fragility in this subsystem, but none of them test the specific filter-vs-burn threshold mismatch described above.

    pub fn clone_and_filter_for_vat(
        &self,
        max_vote_accounts: usize,
        minimum_vote_account_balance: u64,
    ) -> VoteAccounts {
        assert!(max_vote_accounts > 0, "max_vote_accounts must be > 0");
        let capacity = max_vote_accounts.min(self.vote_accounts.len());
        let mut entries_to_sort: Vec<(&Pubkey, &VoteAccount, u64)> = Vec::with_capacity(capacity);
        for (pubkey, (stake, vote_account)) in self.vote_accounts.iter() {
            let has_bls = vote_account
                .vote_state_view()
                .bls_pubkey_compressed()
                .is_some();
            let has_stake = *stake != 0u64;
            let has_balance = vote_account.lamports() >= minimum_vote_account_balance;

            if !has_bls || !has_stake || !has_balance {
                continue;
            }
            entries_to_sort.push((pubkey, vote_account, *stake));

    ///
    /// Note: This must ONLY be called after the vote accounts have been filtered (`clone_and_filter_for_vat`)
    /// to the top `MAX_ALPENGLOW_VOTE_ACCOUNTS` that contain enough balance for admission.
    fn maybe_burn_vat_from_staked_accounts(&mut self, epoch_stakes: &VersionedEpochStakes) {
        let feature_snapshot = self.feature_set.snapshot();
        if !feature_snapshot.alpenglow {
            return;
        }

        let vat_to_burn_per_epoch = self.vat_to_burn_per_epoch();
        let vote_accounts = epoch_stakes.stakes().vote_accounts();
        debug_assert!(vote_accounts.len() <= 2000);
        // +1 for the incinerator account
        let mut accounts_to_store: Vec<(Pubkey, AccountSharedData)> =
            Vec::with_capacity(vote_accounts.len() + 1);
        let mut total_vat = 0u64;

        // Vote accounts have already been filtered by clone_and_filter_for_vat to only include
        // accounts with non-zero stake and sufficient balance.
        for (vote_pubkey, _stake) in vote_accounts.delegated_stakes() {
            let mut account = self.get_account(vote_pubkey).unwrap();
            total_vat += vat_to_burn_per_epoch;
            account.set_lamports(
                account
                    .lamports()
                    .checked_sub(vat_to_burn_per_epoch)
                    .expect(
                        "Vote accounts should have already been filtered to contain enough \
                         balance for the VAT",
                    ),
            );
            accounts_to_store.push((*vote_pubkey, account));
        }
