### Title
Stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` entries survive `claimInstantWithdrawRequest` and become phantom claim basis at default finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The CVE-2017-17848 bug class is "a part is referenced (and counted for the signature) but never displayed": accounting that is included in a global check while its substance is absent. The analog lives in `IdleCreditVault`: when a user claims an instant withdrawal through the normal (non-default) path, `claimInstantWithdrawRequest` clears `instantWithdrawsRequests[_user]` but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. A later borrower default in the same epoch then treats that already-paid amount as an outstanding instant claim: `defaultPendingClaimBasis()` adds it to the recovery basis and `_defaultPrefundedInstantReserve()` counts it as already-held recovery collateral, inflating `recoveryPrice` without backing.

### Finding Description
In `claimInstantWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:380-393) the non-default path only does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]`, which were incremented in `requestInstantWithdraw` (lines 366-374). Those per-epoch mappings are only cleared inside `_claimDefaultedInstantWithdrawRequest` (lines 842-856).

Consequences at `finalizeDefaultRecovery` (lines 661-710):

1. `defaultPendingClaimBasis()` (lines 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever `pendingInstantWithdraws != 0`. The stale, already-claimed amount X is included, so `totalBasis` is inflated by X. This dilutes `recoveryPrice` for all default claimants.
2. Worse, `_defaultPrefundedInstantReserve()` (lines 716-723) computes `instantBasis - pendingInstant`. With stale X, `instantBasis = X + Y` (Y = genuinely unfunded claims), so `prefundedReserve` is inflated by X even though no X of underlying is held. `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` (line 686) is therefore overstated, and `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed on phantom collateral that was already paid out at par.
3. Additionally, `_claimDefaultedInstantWithdrawRequest` pays the stale basis to the attacker again: `claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` returns the already-claimed X, which is transferred at `defaultRecoveryPrice` provided `instantWithdrawsRequests[_user] >= claimBasis` (satisfied if the attacker re-requested in the same epoch, whose receipt tokens are burned to cover the burn).

### Impact Explanation
Direct theft plus insolvency of the recovery reserve. Two effects compound:

- The attacker who already received X at par is paid X * recoveryPrice again from `defaultRecoveryReserve` via the stale per-epoch entry (double-claim against the reserve, burned against a second legitimate receipt so no underflow occurs).
- Simultaneously `prefundedReserve` is overstated by X, so `recoveryPrice` is higher than real backing supports. Early claimants (the attacker first) drain the reserve; later default claimants find `defaultRecoveryReserve` underflowing in `_transferDefaultRecovery` (line 915) or receive less than entitled. The "one receipt, one payout" and solvency invariants are both broken; honest users bear the shortfall.

Quantified: for a stale claimed amount X and genuine pending basis P, the attacker extracts roughly `X * recoveryPrice` extra tokens, and the recorded reserve exceeds real underlying by X, so the aggregate haircut shortfall equals X of underlying.

### Likelihood Explanation
Requires: (a) a funded instant withdrawal claimed in epoch E via `claimInstantWithdrawRequest`, (b) at least one unfunded instant request in the same epoch E (`pendingInstantWithdraws != 0`), (c) the borrower defaulting and `finalizeDefault` being called while epochNumber == E. The attacker controls (a) fully and can create (b) with a second request of their own (so no dependence on other users' timing). Only (c) — a real borrower default — is outside attacker control, and rules disallow making the borrower malicious, so likelihood is moderate: it is a conditional accounting bug that triggers on an organic default, not an attacker-forced one. No existing guard prevents it: `_transferFundedClaim`'s reserve check only protects the reserve on funded claims, and `_ensureDefaultRecoveryInitialized` does not normalize instant buckets.

### Recommendation
In `claimInstantWithdrawRequest`, clear per-epoch accounting on the normal claim path:

```solidity
uint256 currentEpoch = epochNumber;
uint256 epochBasis = instantWithdrawsRequestsByEpoch[_user][currentEpoch];
instantWithdrawsRequestsByEpoch[_user][currentEpoch] = 0;
instantWithdrawClaimsByEpoch[currentEpoch] -= epochBasis;
instantWithdrawsRequests[_user] = 0;
```

(Take care for funded receipts spanning older epochs — the safe fix is to clear the entry corresponding to the request's own epoch, or track claim epoch per request like `lastWithdrawRequest`.) Also consider asserting in `finalizeDefaultRecovery` that `instantWithdrawClaimsByEpoch[epochNumber]` matches the sum of live `instantWithdrawsRequestsByEpoch` entries, or that claimed-at-par receipts can never re-enter default basis.

### Proof of Concept
Foundry fork PoC (sketch against the existing harness in `test/foundry/IdleCreditVault.t.sol`, which provides `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, `_checkDefault`, `_getInstantFunds`):

```solidity
function testStaleInstantClaimBasisInflatesDefault() external {
  uint256 instantDelay = cdoEpoch.instantWithdrawDelay();
  vm.prank(manager);
  cdoEpoch.setInstantWithdrawParams(instantDelay, 1000, false);

  address attacker = makeAddr('stale-instant-attacker');
  uint256 X = 10_000 * ONE_SCALE;
  uint256 Y = 10_000 * ONE_SCALE;
  _depositWithUser(attacker, X + Y, true);
  idleCDO.depositAA(X + Y); // deepen CDO cash so first instant request is fundable

  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

  // Request #1 in epoch 1, get it funded, claim at par
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(X + Y, address(AAtranche)); // instant request = full balance
  _startEpochAndCheckPrices(1);
  vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
  _getInstantFunds(); // collectInstantWithdrawFunds reduces pendingInstantWithdraws
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest(); // pays at par; leaves byEpoch entries stale

  IdleCreditVault cv = IdleCreditVault(address(strategy));
  // stale phantom basis still recorded for epoch 1
  assertGt(cv.instantWithdrawsRequestsByEpoch(attacker, 1), 0);

  // Request #2 same epoch, left unfunded -> pendingInstantWithdraws != 0
  // (re-deposit a small amount first so a second receipt exists to be burned)
  _depositWithUser(attacker, Y, true);
  vm.prank(attacker);
  cdoEpoch.requestWithdraw(Y, address(AAtranche));

  // borrower defaults in epoch 1
  _checkDefault();

  // basis is inflated by stale X; prefunded reserve also inflated by X
  uint256 basis = cv.defaultPendingClaimBasis();
  assertGt(basis, Y); // includes phantom X

  // finalize with an honest recovery computed on the true basis
  uint256 activeBasis = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
  uint256 recovered = (activeBasis + Y) * 7e17 / ONE_TRANCHE;
  deal(defaultUnderlying, manager, recovered);
  vm.startPrank(manager);
  IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
  cdoEpoch.finalizeDefault(recovered, manager);
  vm.stopPrank();

  // attacker claims: stale epoch-1 entry pays again out of recovery reserve
  vm.prank(attacker);
  cdoEpoch.claimInstantWithdrawRequest();
  // assert attacker received > Y * recoveryPrice (double payout on X)
}
```

Expected result pre-fix: `instantWithdrawsRequestsByEpoch[attacker][1]` remains nonzero after the par claim, `defaultPendingClaimBasis` includes X, `_defaultPrefundedInstantReserve` adds phantom X, and the attacker's final claim exceeds the haircutted Y basis — demonstrating double payout and reserve insolvency. Exact epoch sequencing should be verified against `requestWithdraw` routing in `IdleCDOEpochVariant` (instant vs normal path selection was not fully traced within this pass).
