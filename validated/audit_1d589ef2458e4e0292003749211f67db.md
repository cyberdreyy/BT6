### Title
User enumeration via distinguishable login error messages in CreateSession - ([File: core/sessions/localauth/orm.go])

### Summary
The `POST /sessions` endpoint returns different, attacker-visible error strings depending on whether the submitted email exists in the `users` table or exists but the password is wrong, allowing an unauthenticated attacker to enumerate registered admin/API-user emails. The endpoint is explicitly unauthenticated and only rate-limited, not blocked, for anonymous callers.

### Finding Description
`SessionsController.Create` calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)` and on any returned error simply forwards it verbatim as the HTTP body via `jsonAPIError(c, http.StatusUnauthorized, err)` [1](#0-0) , and `jsonAPIError` serializes `err.Error()` directly into the JSON response when the error is not a `*models.JSONAPIErrors` [2](#0-1) .

Inside `CreateSession`, the first step is `o.FindUser(ctx, sr.Email)` [3](#0-2) , which executes `SELECT * FROM users WHERE lower(email) = lower($1)` via `findUser` [4](#0-3) . For a nonexistent email this returns the raw `sql.ErrNoRows` (or driver-specific "no rows" error) which is propagated unmodified back through `CreateSession` at line 147 and ultimately serialized as the JSON error body (e.g. `"sql: no rows in result set"`).

If the email does exist but the password is wrong, execution proceeds past `FindUser` and fails at `utils.CheckPasswordHash`, returning the distinct string `pkgerrors.New("Invalid password")` [5](#0-4) .

Both cases return the same HTTP status code (401) but with clearly distinguishable JSON bodies. Comparing the two responses directly reveals whether an email is registered, without any authentication, rate-limit bypass, or timing analysis required. The `constantTimeEmailCompare` / "Invalid email" branch [6](#0-5)  is effectively unreachable in normal flow since `findUser` already matches case-insensitively, so the real oracle is the "not-found" DB error vs. "Invalid password" distinction, not the "Invalid email" string mentioned in the question — but the underlying enumeration vulnerability the question describes is confirmed.

The route is registered unauthenticated: `unauth.POST("/sessions", sc.Create)` under only a rate limiter, with no additional access control [7](#0-6) .

### Impact Explanation
This allows anonymous account/user enumeration against the Chainlink node's local operator UI/API authentication, disclosing which email addresses are provisioned as node operator accounts. This maps to Chainlink's "account enumeration" / authentication information disclosure impact class — it does not by itself grant login, but it materially aids credential-stuffing and targeted phishing/brute-force campaigns against confirmed operator accounts.

### Likelihood Explanation
No preconditions or credentials are required; the attacker just needs network access to the node's HTTP API and sends two POST requests to `/sessions`, one with a known/guessed email and one with a definitely-nonexistent email, and diffs the JSON bodies. It is fully repeatable and deterministic (not merely a timing side-channel), limited only by the unauthenticated rate limiter (`rl.UnauthenticatedPeriod()`).

### Recommendation
Normalize all `CreateSession` login-failure paths (email-not-found, wrong-password, invalid-email-case) to return one generic, identical error (e.g., `"Invalid email or password"`), with the same HTTP status and same JSON structure, and ensure `sql.ErrNoRows` from `FindUser` in `CreateSession` is caught and remapped rather than passed through raw. Consider adding a constant-time delay/dummy password hash comparison for the not-found branch to mitigate timing-based enumeration.

### Proof of Concept
Go handler-level integration test plan (extending `TestSessionsController_Create` in `core/web/sessions_controller_test.go`):
1. Create one valid user via `app.AuthenticationProvider().CreateUser`.
2. POST `/sessions` with `{"email":"nonexistent@test.net","password":"whatever"}` and capture response body/status.
3. POST `/sessions` with `{"email":"<valid user email>","password":"wrongpassword"}` and capture response body/status.
4. Assert both return `401`, but `assert.NotEqual(t, body1, body2)` — demonstrating the bodies differ (`"sql: no rows in result set"` vs `"Invalid password"`), proving the enumeration oracle.
5. As a fix verification, patch `CreateSession`/`Create` to return an identical generic message for both cases and re-run the test asserting `assert.Equal(t, body1, body2)`.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()

		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),

	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
