### Title
`getSupply` RPC handler computes `circulating` via unchecked subtraction of independently-sampled values, allowing wrong data (or panic) from a single unprivileged call - (File: `rpc/src/rpc.rs`)

### Summary
`JsonRpcRequestProcessor::get_supply` computes `circulating = total_supply - non_circulating_supply.lamports` using a plain (non-saturating) `u64` subtraction, where the two operands are captured at different points in time / via different mechanisms rather than atomically from a single consistent snapshot. [1](#0-0)  This mirrors the root cause of the external report: an "amount" is derived from the difference of two values that are not guaranteed to be consistent with each other (one derived from a live/mutating balance, the other computed independently), producing a wrong result instead of the intended delta.

### Finding Description
`get_supply` first computes `non_circulating_supply` by scanning stake-program accounts and summing each account's *current* balance one at a time via `bank.get_balance(pubkey)` inside `calculate_non_circulating_supply`. [2](#0-1)  Only *after* this scan completes does the handler read `total_supply = bank.capitalization()`. [3](#0-2)  It then performs `total_supply - non_circulating_supply.lamports` with a raw `-` operator: [4](#0-3) 

Notably, the sibling REST endpoint that performs the equivalent computation explicitly guards against this with `saturating_sub`: [5](#0-4)  The JSON-RPC `getSupply` path lacks this protection, despite computing the same kind of difference from the same two logically-independent values (`bank.capitalization()` and a summed set of individually re-read account balances).

If `bank.get_balance()` calls performed during the non-circulating scan observe balances that, summed together, exceed the separately-sampled `bank.capitalization()` (e.g., due to the scan iterating over accounts as they are concurrently being read/updated for a non-finalized/"processed" commitment bank, or due to any accounting inconsistency between the incrementally-scanned per-account lamports and the single atomic capitalization counter), the subtraction underflows. Since the codebase does not set `overflow-checks = true` for release builds, [6](#0-5)  the subtraction silently wraps to a huge, incorrect `u64` value in release builds, or panics the RPC-serving thread if debug/overflow-checked builds are used.

### Impact Explanation
This directly matches the "wrong-slot/fork/account data returned" and "decoder/consensus misreporting" acceptable-impact categories: an unprivileged JSON-RPC caller invoking `getSupply` can receive a bogus `circulating` field (e.g., an astronomically large `u64` from underflow wraparound) instead of an error or a sane value, corrupting supply reporting consumed by wallets, explorers, and monitoring tooling. In an overflow-checked build (some validator operators may build with debug assertions for testing or safety tooling), the same call would panic the request-handling thread instead. The bug is reachable with a single `getSupply` JSON-RPC call and requires no special privileges.

### Likelihood Explanation
`getSupply` is a standard, publicly exposed JSON-RPC method callable by any client with access to a validator's RPC endpoint. The unguarded subtraction executes on every invocation; the only requirement for observable wrong output is any transient inconsistency between the sum of non-circulating account balances (read account-by-account during a scan) and the bank's independently-tracked capitalization counter, which is plausible whenever the resolved bank is not a fully-frozen/finalized snapshot (e.g., `processed` commitment) or when non-circulating account balances are updated between the start of the scan and completion.

### Recommendation
Change the computation in `get_supply` to use `total_supply.saturating_sub(non_circulating_supply.lamports)`, mirroring the existing `calculate_circulating_supply_async` helper used by the `/v0/circulating-supply` REST path, and consider deriving both `total_supply` and `non_circulating_supply` from a single, internally consistent read of the bank state to avoid any residual inconsistency being masked rather than fixed.

### Proof of Concept
Not independently reproduced against a live cluster; the analysis is based on static code review comparing `get_supply` in `rpc/src/rpc.rs` (unguarded subtraction) against the equivalent, already-hardened logic in `calculate_circulating_supply_async` in `rpc/src/rpc_service.rs` (uses `saturating_sub`), which confirms this exact underflow scenario was anticipated and fixed in one code path but not the other.

async fn calculate_circulating_supply_async(bank: &Arc<Bank>) -> Result<u64, SupplyCalcError> {
    let total_supply = bank.capitalization();
    let bank = Arc::clone(bank);
    let non_circulating_supply =
        tokio::task::spawn_blocking(move || calculate_non_circulating_supply(&bank))
            .await
            .expect("Failed to spawn blocking task")
            .map_err(|e| SupplyCalcError::Scan(e.to_string()))?;

    Ok(total_supply.saturating_sub(non_circulating_supply.lamports))
}
