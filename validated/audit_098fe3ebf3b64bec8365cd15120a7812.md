### Title
`process_dump` panics on truncated/attacker-crafted `ProgramData` account due to unconditional offset assumption - ([File: cli/src/program.rs])

### Summary
`process_dump` in `cli/src/program.rs` computes the ELF offset for an upgradeable-loader `ProgramData` account using the fixed `size_of_programdata_metadata()` (the size assuming `upgrade_authority_address: Some(..)`), then indexes `&programdata_account.data[offset..]` without a bounds check. An attacker who controls the target account's on-chain bytes (e.g., a `ProgramData`-tagged account with `upgrade_authority_address: None` and a short data buffer) can make `bincode::deserialize` succeed while `data.len() < offset`, causing an out-of-bounds slice panic in the CLI process that queries it via a single `getAccountInfo` RPC call.

### Finding Description
`process_dump` deserializes the account bytes returned by `rpc_client.get_account_with_commitment` and, upon matching `UpgradeableLoaderState::ProgramData { .. }`, unconditionally computes:
```rust
let offset = UpgradeableLoaderState::size_of_programdata_metadata();
let program_data = &programdata_account.data[offset..];
``` [1](#0-0) 

`size_of_programdata_metadata()` is the *serialized size assuming `Some(Pubkey)`* for the authority field. If the attacker-controlled account instead encodes `upgrade_authority_address: None`, `bincode::deserialize` needs far fewer bytes to succeed (no embedded 32-byte pubkey), so an attacker can craft an account with `data.len()` smaller than `size_of_programdata_metadata()` that still deserializes successfully as `UpgradeableLoaderState::ProgramData`. `account-decoder`'s own equivalent code, `parse_bpf_upgradeable_loader`, correctly branches on `upgrade_authority_address.is_some()` to compute a reduced offset for the `None` case: [2](#0-1) 

`process_dump` reuses the exact same account-decoding pattern but omits this branch, so `&programdata_account.data[offset..]` will panic with an out-of-bounds slice index when `data.len() < offset`. The same unconditional-offset pattern (without checking `authority_address.is_some()`) also appears for the `Buffer` case at: [3](#0-2) 

The attacker only needs to (1) create/own an account owned by `bpf_loader_upgradeable::id()` containing a serialized `UpgradeableLoaderState::Program { programdata_address }` pointing at a second attacker-controlled account, and (2) set that second account's data to a minimal `UpgradeableLoaderState::ProgramData { slot, upgrade_authority_address: None }` encoding with total length less than `size_of_programdata_metadata()`. When a victim runs `solana program dump <program_pubkey>` against the attacker's accounts, the CLI issues two `getAccountInfo` RPC calls and panics on the second.

### Impact Explanation
This matches the "decoder panic and misreporting" scoped-impact category: a single, attacker-authored account served by `getAccountInfo` causes a panic in code that decodes RPC-returned account bytes. It confirms the panic is not unique to `account-decoder` but is a repeatable pattern anywhere the same offset-without-bounds-check logic is reused against untrusted RPC data (here, `cli::program::process_dump`).

### Likelihood Explanation
Fully attacker-controlled and requires no special privileges: the attacker only needs to deploy/own two ordinary accounts (a `Program` pointer account and an undersized `ProgramData` account with `upgrade_authority_address: None`), then have any client (victim) query them once via `solana program dump`. The bug is deterministic and 100% reproducible on the crafted input.

### Recommendation
Mirror the safe pattern already used in `account-decoder/src/parse_bpf_loader.rs`: branch on whether `upgrade_authority_address` (or `authority_address` for `Buffer`) is `Some`/`None` before computing the offset, and use `data.get(offset..)` instead of `data[offset..]`, returning a descriptive `Err` instead of panicking when the account is malformed/too short. Apply the same fix to both the `ProgramData` and `Buffer` branches in `process_dump`.

### Proof of Concept
```rust
// cli/src/program.rs (unit-test style PoC)
#[test]
fn test_process_dump_panics_on_truncated_programdata_account_with_no_authority() {
    use solana_loader_v3_interface::state::UpgradeableLoaderState;

    // Craft a ProgramData account with upgrade_authority_address: None,
    // whose serialized size is smaller than size_of_programdata_metadata()
    // (which assumes Some(Pubkey)).
    let state = UpgradeableLoaderState::ProgramData {
        slot: 0,
        upgrade_authority_address: None,
    };
    let data = bincode::serialize(&state).unwrap();
    assert!(data.len() < UpgradeableLoaderState::size_of_programdata_metadata());

    // Simulate what process_dump does:
    assert!(matches!(
        bincode::deserialize::<UpgradeableLoaderState>(&data),
        Ok(UpgradeableLoaderState::ProgramData { .. })
    ));

    let offset = UpgradeableLoaderState::size_of_programdata_metadata();
    // This indexing operation panics: "range start index N out of range
    // for slice of length M" because offset > data.len().
    let _program_data = &data[offset..];
}
```
Expected result: the test panics with an out-of-bounds slice index, demonstrating that a single attacker-crafted account (reachable via one `getAccountInfo` call in `process_dump`) crashes the consuming client process without any bounds check, confirming the pattern-level vulnerability outside `account-decoder`.
