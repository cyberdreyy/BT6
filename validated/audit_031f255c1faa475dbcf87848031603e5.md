### Title
Stale confirmations from a deleted (and possibly re-added) member are still counted toward `num_confirmations`, allowing a request to execute with fewer live-member approvals - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` only purges `confirmations` entries for requests the removed member *authored* (`r.member == member`), never for requests the member merely *confirmed*. Because `confirm()` only checks the raw size of the `confirmations` HashSet and never re-validates that each entry corresponds to an account still in `self.members`, a stale confirmation string survives member removal (and even survives removal-then-re-addition), letting it be counted toward the `num_confirmations` threshold for a request whose approval chain should only include confirmations cast by continuously-live members.

### Finding Description
The intended binding is:

`|{s ∈ confirmations[request_id] : s corresponds to a member in self.members continuously from cast time through execution time}| == num_confirmations`

The actual code only checks `confirmations.get(&request_id).len()`, with no cross-check against current membership: [1](#0-0) 

`delete_member` removes confirmations only for requests the removed member authored: [2](#0-1) 

The `request_ids` filter (`r.member == member`) matches requests added via `add_request` by that member, not requests where the member merely called `confirm()` on someone else's request. Since `confirm()` stores the confirming member's `to_string()` directly into the shared `confirmations` HashSet keyed by `request_id`, and `delete_member` never scans `confirmations` values (only `requests` values) for the removed member's string, that entry is never purged if the member didn't author the request.

Exploit flow with 4 members (M plus 3 others) and `num_confirmations = 3`:
1. Some other member authors request A (`add_request`). `confirmations[A] = {}`.
2. M calls `confirm(A)` → `confirmations[A] = {M}`, size 1 < 3, so no execution yet.
3. A separate `DeleteMember{M}` request reaches 3 confirmations and executes: `delete_member` removes M from `self.members` and drops M's `num_requests_pk` entry, but since M did not author request A, `confirmations[A]` is left untouched — `{M}` remains.
4. Optionally, `AddMember{M}` later re-admits M — irrelevant to the bug since the stale entry was never removed regardless.
5. Two other current members call `confirm(A)`. On the second of these, `confirmations.len() as u32 + 1 >= num_confirmations` → `2 + 1 >= 3` is true, and `remove_request` + `execute_request` run, executing A's actions (e.g. `Transfer`) even though only 2 currently-live members plus one stale/former member's vote back it.

None of the existing guards catch this: `assert_valid_request` only checks that the *caller* is currently a member and that the request/confirmations exist; it does not re-validate the *previously stored* confirmation entries. `confirm()` has no membership re-check on the entries inside the `HashSet`.

### Impact Explanation
This lets a multisig request (including a `Transfer` of NEAR out of the multisig account) execute with fewer than `num_confirmations` *live* members' approval, since one "confirmation" belongs to an account that was not a member at execution time (or for part of the interval). This directly matches the Critical category "a multisig request executed below `num_confirmations` live members," moving NEAR funds out of the multisig based on an approval chain that does not actually reflect current, continuous membership. It is repeatable for every pending request that a to-be-removed member confirmed without authoring, and for every multisig contract instance, since the flaw is structural in `delete_member`.

### Likelihood Explanation
Preconditions require only actions that legitimate multisig members would take in the ordinary course of managing membership (a member confirms a request they didn't author, then that member is later removed via a normal `DeleteMember` request while the earlier request stays pending, then confirmed to completion by remaining members). No attacker-controlled unprivileged actor is strictly needed to trigger the accounting mismatch — it is a member/governance bookkeeping flaw reachable purely through routine multisig operations (add/confirm/delete-member sequencing), making it highly feasible to reach unintentionally, and it requires no special privilege beyond being a multisig member performing normal actions.

### Recommendation
In `delete_member`, before removing the member from `self.members`, iterate over all entries in `self.confirmations` (not just `self.requests` filtered by authorship) and remove the deleted member's `to_string()` key from every request's confirmation set, decrementing effectively pending confirmations. Alternatively, when checking `confirmations.len() as u32 + 1 >= self.num_confirmations` in `confirm()`, filter/recount only those confirmation strings that currently correspond to `self.members` members before comparing against the threshold.

### Proof of Concept
```rust
#[test]
fn stale_confirmation_survives_member_deletion() {
    // members: alice, bob, keyA, keyB ; num_confirmations = 3
    testing_env!(context_with_key(test_key_a(), 1_000));
    let mut c = MultiSigContract::new(members(), 3);

    // Step 1: alice authors request A (Transfer)
    testing_env!(context_with_account(alice(), 1_000));
    let request_id = c.add_request(MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: 500.into() }],
    });

    // Step 2: bob confirms A (bob did NOT author it)
    testing_env!(context_with_account(bob(), 1_000));
    c.confirm(request_id);
    assert!(c.confirmations.get(&request_id).unwrap().contains(&bob().to_string()));

    // Step 3: DeleteMember{bob} authored+confirmed to threshold by alice, keyA, keyB
    // (separate request, reaches 3 confirmations, executes delete_member)
    // ... add_request + confirm x3 for DeleteMember{ member: Account{bob} } ...

    // ASSERT the broken binding: bob's stale entry is still present in confirmations[A]
    // even though bob is no longer in c.members
    assert!(!c.get_members().contains(&MultisigMember::Account { account_id: bob() }));
    assert!(c.confirmations.get(&request_id).unwrap().contains(&bob().to_string()));

    // Step 4: two more *current* members confirm A; bob's stale vote is counted
    testing_env!(context_with_key(test_key_a(), 1_000));
    c.confirm(request_id); // len 2
    testing_env!(context_with_key(test_key_b(), 1_000));
    c.confirm(request_id); // len 2 + 1 >= 3 -> executes with only 2 live confirmers + 1 stale
    assert_eq!(c.requests.len(), 0); // request A executed
    // Binding violated: only 2 live members + bob's pre-removal vote reached threshold 3
}
```

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
