## Analog Identified: Stale Confirmations From Removed Multisig Members Are Still Counted Toward the Confirmation Threshold

### Title
Multisig executes requests using confirmations from members already deleted from the multisig, allowing a request to execute below the real live-member threshold - (File: `multisig2/src/lib.rs`)

### Summary
The bug-class in the external report is: a limit/guard (`term.maxDebt`) is checked against stale accumulated state instead of being enforced strictly before/at the moment of the action, letting an actor exploit the gap between "recorded state" and "real state" to extract value they should not be entitled to. The equivalent binding in this NEAR multisig contract is: **confirmations counted toward `num_confirmations` == confirmations from accounts that are still live members**. This binding is broken because `delete_member` purges only the *requests originated by* the removed member, not the *confirmations that member previously cast on other members' pending requests* [1](#0-0) .

### Finding Description
`delete_member` is the only cleanup path invoked when a member is removed. It filters `self.requests` for entries whose `r.member == member` (i.e., requests the removed member authored) and deletes those requests plus their confirmation sets, and also removes `num_requests_pk` for that member [2](#0-1) . It never scans `self.confirmations` for entries where the removed member's identity appears as a *confirmer* of a request authored by someone else. Those stale confirmations remain in the `HashSet<String>` stored in `self.confirmations`.

`confirm()` determines whether to execute a request purely by counting entries in that stored set:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [3](#0-2) 

There is no re-validation that every entry in `confirmations` still corresponds to a member present in `self.members` — `assert_valid_request` only checks that the *current caller* is a member, not that all *prior* confirmers still are [4](#0-3) . `current_member()` similarly only validates the calling account against the live `self.members` set at call time, giving no signal about other confirmers' current standing [5](#0-4) .

The equality that should hold is:
`confirmations.len() (counted toward threshold)` == `count of confirmers who are still in self.members`

After a `DeleteMember` action removes a member who had already confirmed some other pending request, the left side stays unchanged while the right side drops by one, breaking the equality.

### Impact Explanation
This falls under the Critical impact category "a multisig request executed below threshold." Concretely: with `num_confirmations = K` and `N` current members, a request can execute with as few as `K-1` (or fewer, if multiple confirmers are later removed) *actually live* members having approved it, because one or more confirmations came from accounts/keys that were subsequently deleted via a legitimate `DeleteMember`/`DeleteKey` action processed on a different, unrelated request. Any of the sensitive `MultiSigRequestAction` types — `Transfer`, `AddMember`, `DeleteMember`, `AddKey`, `FunctionCall`, `DeployContract` — can be pushed through this weakened threshold, so NEAR (or any assets the multisig custodies) can be moved, or governance/membership can be altered, without the intended K-of-N live-member authorization.

### Likelihood Explanation
This requires only ordinary permitted multisig usage, no attacker key compromise, no owner error, and no redeploy:
1. A request R1 (e.g., a large `Transfer`) is created and gets confirmed by member B (1 of K confirmations, sitting below threshold).
2. Separately, and entirely through normal governance, the multisig confirms a `DeleteMember` request removing member B (e.g., because B's key was rotated/offboarded) — this is a routine, expected operation, not an attack on its own.
3. B's stale confirmation on R1 is never purged.
4. The remaining members confirm R1 up to `K-1` fresh confirmations; on the last confirm, `confirmations.len() + 1 >= num_confirmations` is satisfied by combining live confirmations with B's stale one, and R1 executes despite B no longer being a member.

The precondition (a pending request confirmed by a member who is later removed before threshold is otherwise reached) is a plausible sequence in any multisig with member turnover, making this reasonably likely to occur in practice rather than a purely theoretical edge case.

### Recommendation
When executing `delete_member`, iterate `self.confirmations` (not just `self.requests` authored by the removed member) and strip the removed member's entry from every pending request's confirmation set. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmer set against current `self.members` before comparing against `num_confirmations`, so only live members' confirmations count toward the threshold.

### Proof of Concept
1. Deploy `MultiSigContract` with members `[A, B, C]` and `num_confirmations = 3`.
2. A creates request R1: `Transfer { amount: X }` (via `add_request_and_confirm`), giving `confirmations(R1) = {A}` [6](#0-5) .
3. B confirms R1 → `confirmations(R1) = {A, B}` (2 of 3; not yet executed) [7](#0-6) .
4. Separately, C creates and the group fully confirms a `DeleteMember { member: B }` request (using 3 valid confirmations from A, B, C on that distinct request) which executes `delete_member`, removing B from `self.members` — but R1's `confirmations` set (`{A, B}`) is untouched because R1 was authored by A, not B [1](#0-0) .
5. C confirms R1: `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → R1 executes and the `Transfer` is sent, even though B is no longer a member and only A and C are truly live approvers [8](#0-7) .

Result: a transfer request executed with only 2 live-member confirmations against a nominal 3-of-N threshold.

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
