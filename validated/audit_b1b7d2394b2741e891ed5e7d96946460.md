### Title
Donation-inflated ERC4626 `convertToAssets` poisons `totalInterestDueNow`, minting unbacked epoch interest to tranche holders - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
Analogous to Black trusting an unvalidated `pyproject.toml` `version` field to select code to execute, `ProgrammableBorrower` trusts the external ERC4626 vault's live `convertToAssets` price to select how much epoch interest the IdleCDO books. `_vaultNetInterest()` treats `vault.convertToAssets(shares)` as realized PnL without validation. A tranche holder who is also a "direct token sender" into the underlying vault can inflate the share price right before `stopEpoch`, cause `mintStrategyTokens(_grossInterest)` to mint unbacked interest into pool NAV, then withdraw/redeem at the inflated tranche price and unwind the donation by redeeming their own vault shares.

### Finding Description
- `_currentVaultAssets()` prices the entire position via `vault.convertToAssets(vault.balanceOf(this))` (`ProgrammableBorrower.sol:546-549`).
- `_vaultNetInterest()` converts that valuation into `interest` when `earnedAssets > principalAssets` (`ProgrammableBorrower.sol:337-347`), and `totalInterestDueNow()` returns it to the CDO (`ProgrammableBorrower.sol:330-334`).
- In `IdleCDOEpochVariant._stopEpoch`, the resolved interest becomes `_grossInterest`; in minted-interest mode the CDO pulls only `pendingWithdraws` cash (`_amountToPullFromBorrower = 0`, line 376) and calls `_strategy.mintStrategyTokens(_grossInterest)` (line 430) before `_updateAccounting()` raises tranche prices (line 436). No solvency check verifies the vault actually gained assets vs. a transient price spike — the only cap is `maxApr` on the *override* path (line 379), which does not apply to the programmable `totalInterestDueNow()` path.

Attack sequence (running epoch, minted-interest, programmable mode):
1. Attacker (KYC'd lender) deposits into AA tranche during the epoch via `depositDuringEpoch`, and holds a small vault share position.
2. Attacker directly transfers `D` underlying into the ERC4626 vault (donation). Every vault share, including `ProgrammableBorrower`'s, is now worth more; `_vaultNetInterest()` reports ~`D * pbShares/totalShares` as fake `vaultInterest`.
3. Honest manager calls `stopEpoch`. `totalInterestDueNow()` returns the inflated amount; `mintStrategyTokens(_grossInterest)` mints unbacked strategy tokens and `_updateAccounting()` lifts AA tranche price by ~the fake interest.
4. Attacker instantly withdraws/redeems tranche at the inflated NAV. Because interest was *minted*, not pulled as cash, the excess NAV is paid from real pool liquidity (pending-withdraw buffer / other LPs' principal).
5. Attacker redeems their vault shares; donation is partially recoverable only if the vault's `totalAssets` can later be pulled back — for a standard balance-based ERC4626 the donation is a cost, so the attack is profitable only when `share of minted interest captured > D donated`. This holds when the attacker controls a large fraction of the vault's share supply *outside* the ProgrammableBorrower position... Actually the constraint is reversed: the fake interest credited to the pool equals `D * pbShares / totalShares`, which is maximized when the ProgrammableBorrower dominates the vault — the normal case for a dedicated facility vault. The attacker captures that minted interest pro-rata through their tranche position, so profitability requires tranche share × `D` > `D`... This is only net-positive if the attacker also recovers the donation, which requires either (a) a vault whose `convertToAssets` can be inflated transiently via flash-borrowed liquidity or manipulable `totalAssets`, or (b) the attacker holding both most vault shares and most tranche shares, in which case gains and costs mostly net out.

I could not fully verify a strictly profitable parametrization without knowing the concrete vault's `totalAssets` implementation and the attacker's feasible tranche share; if `convertToAssets` is only donation-inflatable, the attack transfers the attacker's own money to LPs (self-harm). A transient inflation vector (e.g., a vault that counts flash-loanable or attacker-reclaimable balances in `totalAssets`) makes it a clean theft; the code has no guard (no min-liquidity, no TWAP, no deviation check on `totalInterestDueNow` vs. contractual `borrowerInterestAccruedNow`).

### Impact Explanation
Broken invariant: fair mint/burn — `_grossInterest` minted into NAV is backed by a spoofed valuation, so withdrawals immediately after `stopEpoch` pay real cash against phantom yield, diluting/draining remaining LPs and pending withdraw requests.

### Likelihood Explanation
Requires a programmable-borrower deployment whose ERC4626 vault allows balance donation or transient `convertToAssets` manipulation, plus a KYC'd tranche holder timing a deposit before the honest `stopEpoch` call. Guard check: `_skimDonatedAssets` only skims tokens sent to the *CDO itself*, not the external vault; `onStopEpoch` liquidity check (`shortfall > _currentVaultAssets`) uses the same inflated price, so it does not catch the spoof.

### Recommendation
Bound `totalInterestDueNow()` to contractual sources: cap vault PnL credit at `min(vaultInterest, borrowerInterestAccruedNow() + bufferInterest + realizedYield)` or require `stopEpoch` to first redeem vault shares to cash and price interest off received assets, not `convertToAssets`. Alternatively sanity-check `_grossInterest` against `maxApr`-derived bounds on the programmable path as is done for the `_interest > 1` override.

### Proof of Concept
Foundry fork PoC sketch: deploy `IdleCDOEpochVariant` + `ProgrammableBorrower` against a mainnet ERC4626 vault; attacker deposits AA via `depositDuringEpoch`, `vm.prank` direct-transfers underlying into the vault, warps past `epochEndDate`, calls `stopEpoch(0,0)` as manager, then `claimInstantWithdrawRequest`/redeem — assert tranche price jumped and attacker redeemed more underlying than deposited minus donation cost only if vault allows reclaim.   function totalInterestDueNow() external view returns (uint256) {
    (uint256 vaultInterest, uint256 loss) = _vaultNetInterest();
    uint256 totalGain = vaultInterest + borrowerInterestAccruedNow() + bufferInterest;
    return totalGain > loss ? totalGain - loss : 0;
  }

  /// @notice Compute the net vault delta split into interest and loss (mutually exclusive).
  function _vaultNetInterest() internal view returns (uint256 interest, uint256 loss) {
    if (!epochAccountingActive) return (0, 0);
    uint256 earnedAssets = _currentVaultAssets() + epochWithdrawnFromVault;
    uint256 principalAssets = epochStartVaultAssets + epochDepositedToVault;
    int256 netDelta = bufferedVaultDelta + int256(earnedAssets) - int256(principalAssets);
    if (netDelta > 0) {
      interest = uint256(netDelta);
    } else {
      loss = uint256(-netDelta);
    }
  }
