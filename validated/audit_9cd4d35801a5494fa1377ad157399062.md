### Title
Pausing MultiDepositorVault does not block ERC20 `transfer`/`transferFrom` of vault units - ([File: v3/src/core/MultiDepositorVault.sol])

### Summary
`MultiDepositorVault` inherits `BaseVault`'s `Pausable` and applies `whenNotPaused` only to the explicit `enter`/`exit` functions and to `BaseVault.submit`. The ERC20 `_update` override used by the vault's own unit token does not check `paused()`, so standard OpenZeppelin `transfer`/`transferFrom` calls on the vault-unit ERC20 remain fully functional while the vault is paused.

### Finding Description
`MultiDepositorVault` is `ERC20, FeeVault` where `FeeVault` extends `BaseVault` (which is `Pausable`). `BaseVault.pause()` calls `_pause()` and is callable by any auth/guardian (`onlyAuthOrGuardian`). This pause is checked in `submit()` [1](#0-0)  and in the vault's own `enter`/`exit` functions [2](#0-1) .

However, the only override of the ERC20 transfer path is `_update`, which checks a `beforeTransferHook` and a units-locked flag from the provisioner, but never checks `paused()`: [3](#0-2) 

Because standard OZ `ERC20.transfer`/`transferFrom` (inherited unmodified) internally call `_update`, and `_update` has no pause check, any holder can freely transfer/receive vault units via ordinary ERC20 calls while the vault is paused. This mirrors the FootiumClub root cause exactly: the pause guard was attached to specific "action" functions (`safeMint` in FootiumClub; `enter`/`exit`/`submit` here) instead of the token's core transfer hook (`_beforeTokenTransfer` in FootiumClub; `_update` here), leaving the generic transfer path unprotected.

### Impact Explanation
An emergency `pause()` on `MultiDepositorVault` (e.g., triggered by a guardian/owner in response to a bad price, an oracle issue, or a detected exploit) is expected to freeze all vault activity. In reality, holders of vault units can continue to freely transfer/trade their units peer-to-peer (or to other contracts) during the pause window, undermining the emergency response — e.g., an attacker who obtained units through a bug can move them to a fresh address before the response team can act, or units subject to scrutiny can be shuffled to evade any address-specific remediation, all while deposits/withdrawals via the provisioner are frozen.

### Likelihood Explanation
No privileged or malicious actor collusion is required beyond ordinary use of the standard, unmodified `transfer`/`transferFrom` functions that any ERC20 holder can call at any time; the only precondition is that the vault has been paused by its owner/guardian, at which point every unit holder retains full transfer capability.

### Recommendation
Add a `paused()`/`whenNotPaused` check inside `MultiDepositorVault._update` (or override `_beforeTokenTransfer`-equivalent logic) so that all unit transfers — including plain `transfer`/`transferFrom`, not just `enter`/`exit` — are blocked while the vault is paused, mirroring OpenZeppelin's `ERC20Pausable` pattern.

### Proof of Concept
1. Deploy `MultiDepositorVault` via its factory with a valid `Provisioner`/`FeeVault` configuration; mint units to `alice` via a normal `enter()` call (unpaused).
2. Have an auth/guardian address call `pause()` on the vault (`BaseVault.pause()`), setting `Pausable._paused = true`.
3. Assert: `alice` calling `provisioner`-mediated `enter`/`exit` reverts (or `submit()` reverts) as expected due to `whenNotPaused`.
4. Assert: `alice` calling `vault.transfer(bob, amount)` directly on the vault's ERC20 interface succeeds and updates balances, even though `vault.paused() == true` — demonstrating that ordinary secondary transfers of vault units are not frozen during an emergency pause.

    function enter(address sender, IERC20 token, uint256 tokenAmount, uint256 unitsAmount, address recipient)
        external
        whenNotPaused
        onlyProvisioner
    {
        // Interactions: pull tokens from the sender
        if (tokenAmount > 0) token.safeTransferFrom(sender, address(this), tokenAmount);

        // Effects: mint units to the recipient
        _mint(recipient, unitsAmount);

        // Log the enter event
        emit Enter(sender, recipient, token, tokenAmount, unitsAmount);
    }

    /// @inheritdoc IMultiDepositorVault
    function exit(address sender, IERC20 token, uint256 tokenAmount, uint256 unitsAmount, address recipient)
        external
        whenNotPaused
        onlyProvisioner
    {
        // Effects: burn units from the sender
        _burn(sender, unitsAmount);

        // Interactions: transfer tokens to the recipient
        if (tokenAmount > 0) token.safeTransfer(recipient, tokenAmount);

        // Log the exit event
        emit Exit(sender, recipient, token, tokenAmount, unitsAmount);
    }

    /// @notice Internal function to update token balances with transfer hook checks
    /// @param from The address tokens are transferred from
    /// @param to The address tokens are transferred to
    /// @param amount The amount of tokens to transfer
    /// @inheritdoc ERC20
    function _update(address from, address to, uint256 amount) internal override {
        IBeforeTransferHook hook = beforeTransferHook;
        if (address(hook) != address(0)) {
            // Requirements: perform before transfer checks
            hook.beforeTransfer(from, to, provisioner);
        }

        // Requirements: check that the from address does not have its units locked
        // from == address(0) is to allow minting further units for user with locked units
        // to == address(0) is to allow burning units in refundDeposit
        require(
            from == address(0) || to == address(0) || !IProvisionerV2(provisioner).areUserUnitsLocked(from),
            Aera__UnitsLocked()
        );

        // Effects: transfer the tokens
        return super._update(from, to, amount);
    }
