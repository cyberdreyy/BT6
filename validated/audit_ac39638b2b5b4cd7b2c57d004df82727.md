### Title
Orphaned loss-adjusted withdraw receipt settles at par after `lastWithdrawRequest` is overwritten - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks a user's pending withdraw epoch through a single-slot pointer `lastWithdrawRequest[_user]`. When `stopEpochWithDuration` realizes a loss, the haircut for pending receipts is stored in `lossRecoveryPriceByEpoch[epochNumber]` and `_claimLossAdjustedWithdrawRequest` only looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`. If a user makes a second withdraw request before claiming, `lastWithdrawRequest` is overwritten with the new epoch, so the loss-epoch lookup returns 0 and is skipped. The orphaned receipt basis stays inside `withdrawsRequests[_user]` and is later paid **at par** by `_claimFundedWithdrawRequest`, letting the user sidestep the realized loss entirely.

This mirrors the reference bug class: a pending-operation reference (the current-file pointer in `@fastify/multipart`; the `lastWithdrawRequest` pointer here) is cleared/replaced while the underlying obligation is still open, so the cleanup path (`_claimLossAdjustedWithdrawRequest` / abort handling) finds nothing and the obligation settles through the wrong path (hanging request / full-price payout).

### Finding Description
Relevant code:

- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` and adds to `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) 
- `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` and zeroes `pendingWithdraws` when the borrower under-funds receipts after `stopEpochWithDuration` [2](#0-1) 
- `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[_user]` and returns early if `lossRecoveryPriceByEpoch[lossEpoch] == 0` [3](#0-2) 
- `_claimFundedWithdrawRequest` then pays the entire `withdrawsRequests[_user]` aggregate (which still contains the loss-epoch basis, since `_clearWithdrawClaimForEpoch` was never invoked for it) at par via `_transferFundedClaim` [4](#0-3) 

The haircutfunding was already collected into the vault at `_amount < pendingBasis`. Paying the orphaned receipt at 100% spends more underlyings than were funded for it; the difference is drained from the vault's funded-claim balance backing other claimants and receipts.

### Impact Explanation
Direct insolvency / theft scaled by the realized loss. With pending receipt basis `X` and recovery price `p < 1`, the attacker claims `X` instead of `X*p/RECOVERY_FULL`, extracting `X*(1-p)` extra underlyings per claim from funds reserved for other users' funded claims. Every wei overpaid is a wei missing for later claimants; on a 50% haircut the attacker effectively doubles their recovery at the expense of the remaining receipt holders.

### Likelihood Explanation
Requires a partial-loss `stopEpochWithDuration` (borrower under-funds pending receipts but the epoch is not fully defaulted), plus the attacker holding additional tranche tokens to place a second `requestWithdraw` in the next epoch before claiming. Both steps are unprivileged user actions available to any KYC-passing lender/tranche holder. No privileged cooperation is needed — the honest manager/owner sequence of `stopEpochWithDuration` → `collectWithdrawFunds` → later epochs is exactly what creates the condition. The guard `epochNumber <= lastWithdrawRequest[_user]` only forces the attacker to wait one more epoch, which elapses naturally.

### Recommendation
Track loss-adjusted claims per epoch rather than via the single `lastWithdrawRequest` pointer — e.g. iterate `withdrawsRequestsByEpoch` epochs, or store a separate mapping `lossAdjustedClaims[user][epoch]` populated at `collectWithdrawFunds` time, and always subtract the loss-epoch basis from the par-payable aggregate in `_claimFundedWithdrawRequest`. At minimum, apply the haircut to any `withdrawsRequestsByEpoch[user][e]` where `lossRecoveryPriceByEpoch[e] != 0`, independent of which epoch `lastWithdrawRequest` points to.

### Proof of Concept
Foundry fork steps (against `test/foundry/IdleCreditVault.t.sol` harness):

1. Deposit `D` underlying via `cdoEpoch.depositAA` as attacker; `startEpoch()`.
2. `requestWithdraw(X tranche)` → `lastWithdrawRequest[attacker] = N`, `withdrawsRequests = X`.
3. Warp past `epochEndDate`; honest owner calls `stopEpochWithDuration` with `_lossAmount` such that `previewLossAdjustedWithdrawFunds` returns `pendingToFund < pendingBasis`; borrower funds `pendingToFund` → `lossRecoveryPriceByEpoch[N] = p < RECOVERY_FULL`, `pendingWithdraws = 0`.
4. New epoch `N+1` starts; attacker calls `requestWithdraw(Y)` with remaining tranche → `lastWithdrawRequest[attacker] = N+1`.
5. Epoch `N+1` stops normally, fully funded. Attacker calls `cdoEpoch.claimWithdrawRequest()`.
6. Observe: `_claimLossAdjustedWithdrawRequest` checks epoch `N+1` (price 0, skips); `_claimFundedWithdrawRequest` pays `X + Y` at par. Assert `received == X + Y` where correct payout is `X*p/RECOVERY_FULL + Y`. Assert vault underlying balance is short `X*(1-p)/RECOVERY_FULL` versus other claimants' entitlements.

Caveat I could not fully verify within the exploration budget: whether the epoch flow in this deployment permits a fresh `requestWithdraw` in epoch `N+1` immediately after a `stopEpochWithDuration` (i.e., that the pool resumes rather than entering emergency shutdown), and whether `apr0` flows change the accounting. If `stopEpochWithDuration` permanently prevents further epochs, the attack surface narrows to the instant-withdraw path (`claimInstantWithdrawRequest` similarly skips `_claimDefaultedInstantWithdrawRequest` when `defaultInstantWithdrawsFinalized` is false while paying the aggregate at par).

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;
