### Title
Repeated APR0 `requestWithdraw` overwrites `apr0Users.principalEpoch`, losing the per-epoch rate reference and letting the merged claim drain funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Intel microcode advisory describes a "missing reference to an active allocated resource" letting a local authenticated actor cause denial of service. The analog in `IdleCreditVault` is the `Apr0UserData` struct: it stores a single `principal`/`principalEpoch` pair per user (`IdleCreditVault.sol:78-85`), so a second APR0 `requestWithdraw` in a later epoch overwrites the epoch reference that ties the earlier principal to its funded `apr0RateByEpoch` entry. The merged principal is then settled at the new epoch's rate even though `prepareStopEpochWithApr0` only reserved interest on the *new* principal amount.

### Finding Description
In `requestWithdraw` (lines 285-294), when `unscaledApr == 0`, the request is routed to `_requestWithdrawApr0` and `lastWithdrawRequest[_user]` is overwritten with `currentEpoch`. There is no guard preventing a user who already has an open APR0 principal from a previous epoch (`apr0Users[_user].principal != 0`, `principalEpoch == N`) from requesting again in epoch `N+1` — the only preemptive check (lines 263-271) applies solely when `lossRecoveryPriceByEpoch` is set for a loss-adjusted epoch.

`_settleApr0` (lines 545-560) resolves interest as `principal * apr0RateByEpoch[principalEpoch]`. Because `principalEpoch` now points at `N+1`, the *entire* accumulated `principal` (old + new) accrues the epoch `N+1` rate. However, `prepareStopEpochWithApr0` (lines 513-538) computed and reserved `_apr0NetInterest` — via `pendingWithdraws += _apr0NetInterest` — pro-rata on `apr0TotalPrincipal`, which only ever received the *new* request amount for epoch `N+1`. The interest reserved in epoch `N` for the original principal (`apr0RateByEpoch[N]`) becomes unreachable: it is never claimed under its own rate, while epoch `N+1`'s reserve is over-claimed by `oldPrincipal * apr0RateByEpoch[N+1]` (less fees).

The broken invariant is "one receipt one payout / funded-claim solvency": `withdrawsRequests`/APR0 claims are paid from the strategy's funded underlying balance via `_transferFundedClaim`, but the claimed basis no longer matches the amount the borrower was asked to fund.

### Impact Explanation
An unprivileged KYC-passing lender holding AA tranche tokens in an APR0-configured vault can extract interest that was never reserved. The over-claim is paid out of the strategy's pooled underlying, which also backs other users' funded withdraw receipts and instant-withdraw claims. Direct consequence: the last funded claimant's `claimWithdrawRequest`/`claimInstantWithdrawRequest` reverts on transfer — temporary freezing of funds proportional to `oldPrincipal * apr0RateByEpoch[N+1]`. If instead `apr0RateByEpoch[N+1] < apr0RateByEpoch[N]`, the epoch-`N` interest reserved into `pendingWithdraws` is permanently stranded in the strategy as orphaned yield.

Quantified theft example: attacker requests principal `P` in epoch `N`, lets it stop, requests a dust amount in epoch `N+1` which stops with `apr0RateByEpoch[N+1] = r`. Claim pays `P * r` of interest that was only ever funded as `dust * r` — attacker profit ≈ `(P - dust) * r` taken from other claimants.

### Likelihood Explanation
Requires a vault running in APR0 mode (`unscaledApr == 0`), a subsequent epoch with a positive override interest in `stopEpoch` (which the honest manager/borrower flow produces whenever the borrower repays real interest), and a user willing to defer their claim by one extra epoch — all achievable by an ordinary lender with no privileged role and no default event. The sequencing cost is just an additional epoch of waiting, so the attack is repeatable each epoch pair. Likelihood is limited mainly by APR0 pools being a specific configuration and by the need for positive realized interest in the second epoch.

### Recommendation
In `_requestWithdrawApr0` (and the APR0 branch of `requestWithdraw`), revert with `NotAllowed` when `apr0Users[_user].principal != 0` belongs to an earlier unsettled epoch — i.e. require the user to claim (which calls `_settleApr0` and deletes `apr0Users[_user]`) before opening a new APR0 request. Alternatively, settle the existing `principal` into `settledPrincipal`/`settledInterest` at its own `apr0RateByEpoch[principalEpoch]` inside `_requestWithdrawApr0` before accumulating the new principal, so each principal tranche keeps the epoch reference under which its interest was reserved.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (test/foundry/IdleCreditVault.t.sol harness)
// Setup: APR0 vault (setAprs(0,0)), isAYSActive off, attacker is KYC'd AA holder.

uint256 P = 100_000 * ONE_SCALE;
idleCDO.depositAA(P);                       // attacker deposit
_transferBurnedTrancheTokens(attacker, true);

// Epoch N: attacker makes APR0 withdraw request of P
cdoEpoch.requestWithdraw(P / 2, AAtranche); // principal P0
_startEpochAndCheckPrices(N);
// honest borrower/manager stop epoch N -> apr0RateByEpoch[N] = rN, funded for P0
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpoch(0, poolInterestN);

// Attacker does NOT claim. Epoch N+1: request a dust amount.
cdoEpoch.requestWithdraw(1, AAtranche);     // overwrites apr0Users.principalEpoch -> N+1
_startEpochAndCheckPrices(N + 1);
// stop epoch N+1 with positive override interest -> apr0RateByEpoch[N+1] = rN1
// apr0TotalPrincipal only contained the dust amount, so reserve ~= dust * rN1
vm.warp(cdoEpoch.epochEndDate() + 1);
cdoEpoch.stopEpoch(0, poolInterestN1);

// Claim: settledInterest = (P0 + dust) * rN1, but only dust * rN1 was reserved.
uint256 balPre = underlying.balanceOf(attacker);
cdoEpoch.claimWithdrawRequest();
uint256 stolen = underlying.balanceOf(attacker) - balPre - (P0 + 1);
assertGt(stolen, 0);                        // > reserve; drained from funded pool

// A second honest user's funded claim now underflows/reverts:
vm.prank(victim);
vm.expectRevert();                          // strategy balance shortfall
cdoEpoch.claimWithdrawRequest();
```

Uncertainty note: I could not re-read the `_requestWithdrawApr0` body in this pass; the finding assumes it accumulates `principal` and rewrites `principalEpoch` to the current epoch without settling the prior tranche. The struct shape (`Apr0UserData` at `IdleCreditVault.sol:78-83`, single `principalEpoch`), the settle logic at lines 545-560, and the claim-clearing logic at lines 821-831 (`apr0User.principalEpoch == _claimEpoch` compared against the single stored epoch) all confirm there is only one epoch reference per user, which is the "missing reference to the active allocated resource" the advisory describes.
