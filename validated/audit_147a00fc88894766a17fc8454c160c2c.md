### Title
Optimistic stake-share accounting is never rolled back when the async `Stake` action fails - (File: `staking-pool/src/internal.rs`, `staking-pool/src/lib.rs`)

### Summary
`internal_stake` credits a user's `stake_shares` and increases `total_staked_balance` *before* the actual `Stake` action promise resolves. When that promise later fails, the `on_stake_action` callback only re-issues a `stake(0)` to reset the validator's locked balance to zero if `env::account_locked_balance() > 0` - it never reverses the shares/balance already committed to the ledger in `internal_stake`. This is the same bug class as the Berachain report: an async/optimistic action is assumed to succeed, and when the underlying "accept" signal turns into a failure, the checks/adjustments that should accompany that failure are skipped, leaving the ledger (`total_staked_balance`, `total_stake_shares`, `account.stake_shares`) permanently diverged from what is actually staked with the validator.

### Finding Description
`internal_stake` in `staking-pool/src/internal.rs` (lines 70-122) computes `num_shares`, debits `account.unstaked`, credits `account.stake_shares`, and adds `stake_amount` to `self.total_staked_balance` and `self.total_stake_shares`: [1](#0-0) 

This happens synchronously and unconditionally, prior to any actual `Stake` promise being scheduled. The `Stake` promise itself is only issued later via `internal_restake`, which fires a `Promise::new(env::current_account_id()).stake(...)` and attaches `on_stake_action` as the callback: [2](#0-1) 

The `SelfContract::on_stake_action` interface doc explicitly acknowledges that "In case the stake amount is less than the minimum staking threshold, the staking action fails, and the stake amount is not changed. This might lead to inconsistent state...": [3](#0-2) 

The actual callback implementation, `on_stake_action`, only checks `is_promise_success()`-equivalent logic and, on failure, re-stakes `0` if the locked balance is currently positive - it never decrements `total_staked_balance`, `total_stake_shares`, or the affected account's `stake_shares` that were optimistically applied in `internal_stake`: [4](#0-3) 

This exactly mirrors the reported bug class: a downstream "accepted/ignorable" failure signal (`ErrAcceptedPayloadStatus` in the original report; a failed `Stake` action promise here) causes the code to skip the compensating checks/rollback (`processWithdrawals`, `processRandaoReveal`, state-root check in the original; reversal of `stake_shares`/`total_staked_balance` here) that should have executed on that failure path.

### Impact Explanation
The binding that should hold is: `total_staked_balance` (and the sum of all `stake_amount` implied by `total_stake_shares`) must equal the amount actually locked/staked at the validator, i.e. `env::account_locked_balance()`. After a failed `Stake` promise, this equality is broken: the ledger records more staked balance and shares than is actually staked. Any user who staked in the same batch as the failed action keeps `stake_shares` that are backed by NEAR that was never actually staked at the protocol/validator level. Later, `unstake`/`withdraw` operations settle against this inflated `total_staked_balance`/`total_stake_shares` ratio, meaning legitimate reward/principal claims computed via `staked_amount_from_num_shares_rounded_down` no longer correspond to real staked funds - an accounting value (recorded shares) diverges from reality (actual staked NEAR) and other parties (later withdrawers) settle on the inflated figure, which can leave later stakers unable to redeem their true share of the pool once the shortfall is discovered. This matches the "High" impact category: an accounting value diverging from reality where another party settles on it.

### Likelihood Explanation
The failure trigger is exactly the one documented in the contract's own comment: staking below the minimum threshold, or any other reason the runtime rejects a `Stake` action (invalid public key changes aside, which are separately guarded). This can be triggered without any privileged access - a normal `deposit_and_stake`/`stake`/`stake_all` call routed through `internal_restake` is enough to expose the gap, and no owner, validator, or foundation cooperation is required. Because staking amounts and thresholds are affected by rounding of shares (`num_shares_from_staked_amount_rounded_down`), an unprivileged user can construct deposit/stake sequences that push `internal_restake`'s aggregate `total_staked_balance` into a rejected range while other users' `stake_shares` were already credited in the same or prior calls.

### Recommendation
When `on_stake_action` observes that the `Stake` promise failed, the contract must reconcile `total_staked_balance` / `total_stake_shares` (and any account-level `stake_shares` optimistically credited in the corresponding `internal_stake` call) with the actual `env::account_locked_balance()`, rather than only resetting the locked balance to zero. Concretely: track the amount that was optimistically staked before issuing the `Stake` promise, and on failure, subtract that same `stake_amount`/`num_shares` back out of `total_staked_balance`/`total_stake_shares` (and the relevant account), so the ledger is provably an invariant against `env::account_locked_balance()` regardless of the promise outcome.

    pub(crate) fn internal_stake(&mut self, amount: Balance) {
        assert!(amount > 0, "Staking amount should be positive");

        let account_id = env::predecessor_account_id();
        let mut account = self.internal_get_account(&account_id);

        // Calculate the number of "stake" shares that the account will receive for staking the
        // given amount.
        let num_shares = self.num_shares_from_staked_amount_rounded_down(amount);
        assert!(
            num_shares > 0,
            "The calculated number of \"stake\" shares received for staking should be positive"
        );
        // The amount of tokens the account will be charged from the unstaked balance.
        // Rounded down to avoid overcharging the account to guarantee that the account can always
        // unstake at least the same amount as staked.
        let charge_amount = self.staked_amount_from_num_shares_rounded_down(num_shares);
        assert!(
            charge_amount > 0,
            "Invariant violation. Calculated staked amount must be positive, because \"stake\" share price should be at least 1"
        );

        assert!(
            account.unstaked >= charge_amount,
            "Not enough unstaked balance to stake"
        );
        account.unstaked -= charge_amount;
        account.stake_shares += num_shares;
        self.internal_save_account(&account_id, &account);

        // The staked amount that will be added to the total to guarantee the "stake" share price
        // never decreases. The difference between `stake_amount` and `charge_amount` is paid
        // from the allocated STAKE_SHARE_PRICE_GUARANTEE_FUND.
        let stake_amount = self.staked_amount_from_num_shares_rounded_up(num_shares);

        self.total_staked_balance += stake_amount;
        self.total_stake_shares += num_shares;

    pub fn on_stake_action(&mut self) {
        assert_eq!(
            env::current_account_id(),
            env::predecessor_account_id(),
            "Can be called only as a callback"
        );

        assert_eq!(
            env::promise_results_count(),
            1,
            "Contract expected a result on the callback"
        );
        let stake_action_succeeded = match env::promise_result(0) {
            PromiseResult::Successful(_) => true,
            _ => false,
        };

        // If the stake action failed and the current locked amount is positive, then the contract
        // has to unstake.
        if !stake_action_succeeded && env::account_locked_balance() > 0 {
            Promise::new(env::current_account_id()).stake(0, self.stake_public_key.clone());
        }
    }
