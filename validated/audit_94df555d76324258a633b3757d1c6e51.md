### Title
Signer defaults to signing a conflicting block when its own-tenure-tip RPC check fails, breaking the equivocation guard - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
When the pre-commit threshold is reached for a block that conflicts with a *stale* (timed-out) signature the signer already placed in the **same tenure**, the signer is supposed to ask the node whether that tenure's canonical tip already reflects the other conflicting block before signing the replacement. If that RPC call errors (timeout, transient failure, node busy validating another sibling proposal, etc.), the code logs a warning and falls through to sign anyway, instead of refusing to sign as every other "can't confirm" branch in this same function does.

### Finding Description
In `Signer::handle_block_pre_commit` (`stacks-signer/src/v0/signer.rs`), once a *fresh* conflicting signature has already been ruled out (lines 1403-1421 return early if a fresh, still-live conflict exists), the code separately handles **stale** conflicts that are in the block's *own tenure*: [1](#0-0) 

- Lines 1432-1435 select same-tenure conflicts that are not covered by a reorg permit.
- Line 1436 asks the node for the tenure's canonical tip via `stacks_client.get_tenure_tip(...)`.
- If the RPC succeeds and the tip is `>=` the proposed height, the signer correctly refuses to sign (lines 1437-1447), because signing would duplicate state the node already built (i.e., the earlier conflicting sibling is canonical).
- **If the RPC call itself errors** (line 1449, `Err(e)`), the code only logs `"Treating the tenure as unconfirmed"` and does **not** return — it falls through past this whole block, eventually reaching `mark_locally_accepted` at line 1467 and signs the block.

This is the opposite default used by every other doubt-handling branch in this exact code path:
- `conflict_still_blocks` (lines 1137-1206) explicitly documents: *"If we have no saved burn block, or the node is unreachable, the conflict keeps blocking. That only delays the replacement until our signature goes stale, whereas wrongly signing cannot be taken back."* [2](#0-1) 
- Inside `conflict_still_blocks`, every `Err` branch on RPC failure returns `true` (conflict still blocks) — see lines 1176-1189, 1196-1202.

The section-5 flow documented in `docs/signer-flows.md` also states this is the intended contract: on `"node unreachable"` for the *cross-tenure* conflict path the answer is `HOLD1` (refuse), while only the *own-tenure* path is documented to fall through to `SIGN` on `"node unreachable"`: [3](#0-2) 

So the code deliberately treats "node unreachable while checking a stale same-tenure conflict" as equivalent to "confirmed tenure tip is below the proposal," even though the two are not equivalent — this mirrors the Pendle report's root cause: an unverified assumption (in Pendle's case, guaranteed 1:1 redemption; here, "no answer means safe to sign") substituted for an actual on-chain/verified check.

### Impact Explanation
This breaks the one-per-height/no-double-signature safety invariant that this exact function otherwise enforces (see `stale_sibling_still_refused_when_canonical_tip_at_height` test at `stacks-signer/src/v0/tests.rs:791-807`, which asserts the signer must refuse in the "tip at height" case). If the equivalent RPC call instead errors transiently at the wrong moment, the signer will sign a stale-superseded sibling block even though the node's canonical tenure tip is already at/above that height — i.e., the signer produces a valid signature over a block that is provably not canonical for its own tenure. Accumulated across a subset of signers hitting this same race, this contributes toward two mutually conflicting blocks at the same height both crossing the signature threshold, i.e. a signer signing a non-canonical/conflicting block — the Critical impact category (a signer signing an invalid/non-canonical/conflicting block).

### Likelihood Explanation
The conflicting-sibling scenario itself is fully within a single winning miner's control (propose two tenure-start blocks with different timestamps at the same tenure/height, as exercised by the existing `async_sibling_validation` test harness in `stacks-signer/src/v0/tests.rs`). The remaining trigger — the signer's own-node RPC (`get_tenure_tip`) erroring at the moment the pre-commit threshold is reached for the stale sibling — is a timing/environmental condition (timeout, node under load from validating the flurry of sibling proposals, 429, etc.) rather than a purely deterministic single-actor action, so likelihood is lower than a fully deterministic bug, but the miner can increase the odds by keeping the node busy with proposal validation traffic exactly when the second sibling reaches threshold.

### Recommendation
Make the own-tenure stale-conflict check fail closed like `conflict_still_blocks` and the cross-tenure branch: on `Err` from `stacks_client.get_tenure_tip(...)` at line 1449, `return` (refuse to sign for now) instead of falling through, consistent with the documented principle that an unconfirmed answer must not be treated as "safe to sign."

### Proof of Concept
1. Miner proposes tenure-start block `A` for tenure `T` at height `h`; enough signers pre-commit and sign it locally (`mark_locally_accepted`).
2. Before `A`'s signature freshness window (`tenure_last_block_proposal_timeout`) expires... wait for it to expire (or set it low), so the earlier signature becomes "stale" per `get_signed_conflicts`/`freshness_cutoff`.
3. Miner re-proposes a conflicting sibling block `B` for the same tenure `T` and height `h` (different timestamp). Enough signers pre-commit `B`, crossing the 70% pre-commit threshold on a signer that had earlier signed `A`.
4. On that signer, execution reaches `stacks-signer/src/v0/signer.rs:1432` — the conflict with `A` is in `B`'s own tenure and not reorg-permitted, so it calls `stacks_client.get_tenure_tip(&T)` at line 1436.
5. If that specific RPC call errors (e.g., the local node is still busy validating another in-flight proposal, or a transient timeout), the `Err(e)` branch at line 1449 only logs and does not return.
6. Execution falls through to line 1467 and the signer signs `B`, even though, had the RPC succeeded, the node's canonical tip for tenure `T` might already be at/above height `h` (i.e., `A` is canonical) — the exact case the `stale_sibling_still_refused_when_canonical_tip_at_height` test (`stacks-signer/src/v0/tests.rs:791-807`) asserts must be refused.
