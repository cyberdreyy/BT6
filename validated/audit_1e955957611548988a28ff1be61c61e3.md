### Title
Uncapped Builder Withdrawal Amount Committed to Execution Payload While Beacon-State Balance Deduction Is Capped — Gwei Created / Overpayment - ([File: specs/gloas/beacon-chain.md])

### Summary
In the Gloas fork, `get_builder_withdrawals` constructs `Withdrawal` objects for the execution payload using the *uncapped, committed* `amount` field of `state.builder_pending_withdrawals`, while `apply_withdrawals` deducts only `min(withdrawal.amount, builder_balance)` from the corresponding builder's consensus-layer balance. If a builder's balance is insufficient to cover a queued pending withdrawal at settlement time, the `Withdrawal` object broadcast in the execution payload still commits to the full, uncapped amount — the exact same "unchecked/optimistic transfer" bug class as the reported ERC20 issue, where a value transfer is assumed to succeed for the full amount without verifying (or properly capping) what is actually available. [1](#0-0) [2](#0-1) 

### Finding Description
`get_builder_withdrawals` iterates `state.builder_pending_withdrawals` and appends a `Withdrawal(... amount=withdrawal.amount)` verbatim, with no check against the builder's actual current balance: [3](#0-2) 

This `Withdrawal` list becomes part of `payload_expected_withdrawals`, which is committed to and enforced by the execution layer as real ETH transfers to `withdrawal.address` (here, `withdrawal.fee_recipient`).

Meanwhile, `apply_withdrawals` — which mutates the *beacon-state* accounting — deliberately caps the deduction to the available balance to avoid underflow: [4](#0-3) 

```python
builder_balance = state.builders[builder_index].balance
state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
```

The two operations use different, disconnected quantities: the payload embeds the *full requested* `withdrawal.amount`, while the state deduction is the *capped* `min(withdrawal.amount, builder_balance)`. This is confirmed directly by the repository's own test, which is explicit that this is intentional/known current behavior rather than a hypothetical: [5](#0-4) 

The test shows: builder balance = 1 ETH, pending withdrawal = 5 ETH. Post-state: `builders[0].balance == 0` (capped), but `payload_expected_withdrawals` still contains a withdrawal with `amount == 5 ETH` (uncapped). Since the execution layer credits `fee_recipient` with exactly the amount specified in the committed `Withdrawal`, this means 4 ETH would be created out of nothing on the execution layer without any corresponding decrease anywhere in the consensus-layer balance ledger — breaking the "Gwei created" invariant that the total ETH supply is conserved across the consensus/execution boundary.

This is structurally identical to the reported ERC20 bug: a payment operation ("transfer") is emitted/committed as if it succeeded in full, while the underlying balance bookkeeping silently caps/truncates the actual movement, with no reconciliation between the two, no assertion that `builder_balance >= withdrawal.amount`, and no revert if it does not hold.

### Impact Explanation
This falls under Critical impact per the rules: "Gwei created, destroyed, or paid to a non-owner," and "a payload...that the block did not commit to" in spirit (the payload's withdrawal instruction is inconsistent with what the state actually backs). Whenever a builder's balance is insufficient to cover the full committed pending withdrawal amount at sweep/settlement time, the fee_recipient is paid the full uncommitted-but-uncovered amount on the execution layer while the consensus layer only reduces the builder's balance by the smaller, capped amount — inflating total ETH supply beyond what beacon-state accounting reflects.

### Likelihood Explanation
The invariant that `can_builder_cover_bid` maintains at bid-acceptance time (balance ≥ MIN_DEPOSIT_AMOUNT + all pending withdrawals/payments for that builder) is supposed to prevent this scenario during normal, single-bid processing. However, the repository's own test (`test_builder_withdrawal_insufficient_balance`) demonstrates the shortfall condition is reachable and is handled by capping rather than by an assertion/error — meaning the spec authors anticipated (or at least tolerate) a state where `builder_balance < withdrawal.amount` at settlement time, but chose to silently cap the internal ledger instead of also correcting/capping the payload's committed `Withdrawal.amount` to match. I was not able to fully trace every code path across epochs/forks (e.g., interactions between builder sweep withdrawals fully draining balance and queued pending withdrawals for the same builder that haven't yet been processed due to per-slot processing caps) that would organically produce this shortfall without any external/malicious actor, so I cannot state with full certainty how often, under honest multi-validator operation, this deficit condition is triggered — this needs further confirmation from a background engineering session with fuller state-machine tracing.

### Recommendation
Ensure that the amount embedded in the `Withdrawal` object sent to the execution layer is always capped to the same value actually deducted from the consensus-layer balance (i.e., compute `amount = min(withdrawal.amount, builder.balance)` in `get_builder_withdrawals`/`get_builders_sweep_withdrawals` before constructing the `Withdrawal`, matching exactly what `apply_withdrawals` subtracts), or alternatively assert/guarantee (via invariant maintained throughout bid acceptance, settlement, and sweep withdrawal) that `builder_balance >= sum(pending withdrawal amounts)` always holds so the cap in `apply_withdrawals` is unreachable/dead code. The current mismatch between the payload commitment and the state mutation must be eliminated so that no execution-layer payment can exceed what was actually deducted from consensus-layer balances.

### Proof of Concept
Using the repository's own test scaffold as a concrete demonstration (already present in the codebase, not hypothetical):
1. Register builder 0 with balance = 1 ETH (`spec.Gwei(1_000_000_000)`).
2. Queue a `BuilderPendingWithdrawal` for builder 0 with `amount = 5 ETH` (`spec.Gwei(5_000_000_000)`), via `prepare_process_withdrawals(... builder_withdrawal_amounts={0: 5_000_000_000}, builder_balances={0: 1_000_000_000})`. [6](#0-5) 
3. Call `spec.process_withdrawals(state)`.
4. Observe post-state: `state.builders[0].balance == 0` (capped deduction), while `state.payload_expected_withdrawals` contains a `Withdrawal` with `amount == 5_000_000_000` (uncapped) destined for `fee_recipient`. [7](#0-6) 

This is exactly the "committed withdrawal amount ≠ actual balance movement" discrepancy: were this `Withdrawal` honored by the execution layer (as it is designed to be, per EIP-7732 semantics), 4 ETH would be paid to `fee_recipient` without any corresponding balance decrease anywhere in the beacon state — Gwei created from nothing, analogous to the reported "bidder gets NFT without payment" bug where an operation was treated as successful/complete for the full committed amount despite the underlying balance being insufficient.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count
