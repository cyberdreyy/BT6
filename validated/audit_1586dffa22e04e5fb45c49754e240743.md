## Title
Unbounded destination-side fee amounts in `createDstEscrow` cause permanent withdrawal DoS and secret leakage, enabling theft of source-chain funds - (File: contracts/BaseEscrowFactory.sol, contracts/EscrowDst.sol)

### Summary
The reported SKALE bug is a missing sanity check allowing a fee value that exceeds 100% of the base amount, which combined with unchecked arithmetic breaks accounting invariants. This repository contains the same root cause on the destination-escrow path: the fee-sanity check that exists for the source path is never enforced on the destination path.

### Finding Description
On the source path, `BaseEscrowFactory._postInteraction` explicitly guards against oversized fees before creating the src escrow: [1](#0-0) 

This check ensures `integratorFeeAmount + protocolFeeAmount < takingAmount` for the source-side `Immutables`. However, `createDstEscrow` takes an entirely separate, caller-supplied `Immutables` struct and performs no equivalent validation of the `parameters` field (which encodes `protocolFeeAmount`, `integratorFeeAmount`, and the fee recipients): [2](#0-1) 

The only checks performed are on `msg.value` and the relative cancellation timing — there is no on-chain requirement that the destination `Immutables.parameters` match (or even be consistent with) the fee amounts validated during the corresponding source `postInteraction` call. The caller of `createDstEscrow` (the taker) fully controls the fee values baked into the deployed `EscrowDst` clone.

`EscrowDst._withdraw` then subtracts the unvalidated fee amounts directly from `immutables.amount`: [3](#0-2) 

Because the contract is compiled with Solidity 0.8.23 (built-in checked arithmetic), if `integratorFeeAmount + protocolFeeAmount > immutables.amount`, line 92 (`immutables.amount - integratorFeeAmount - protocolFeeAmount`) reverts unconditionally, and thus `withdraw`/`publicWithdraw` for that escrow can never succeed.

### Impact Explanation
A taker who calls `createDstEscrow` (a permissionless, external, payable function reachable by any unprivileged caller) can set fee amounts in `dstImmutables.parameters` that sum to more than `dstImmutables.amount`. Consequences:
- The maker's withdrawal on the destination chain will always revert (permanent freezing of the maker's destination funds until the cancellation timelock, at which point only the taker — not the maker — can reclaim the deposited destination tokens via `cancel`).
- Since the maker's `withdraw(secret, immutables)` call is broadcast (and reverted transactions still expose calldata), the secret is leaked publicly. The taker (or anyone) can then use the leaked secret to withdraw the maker's original tokens from the source-chain escrow, while the destination-chain deposit is eventually returned to the taker via `cancel`.
- Net effect: the maker loses their source-chain funds while never receiving destination-chain funds — a direct theft of user funds enabled by an unbounded/unvalidated fee value, matching the Critical impact category (direct theft of user funds) and also independently matching High/Medium (permanent/temporary freezing of funds) under the bounty scope.

### Likelihood Explanation
`createDstEscrow` is a normal, unprivileged part of the live swap lifecycle explicitly called out as an allowed attacker entry point. No whitelist or fee-consistency check restricts the caller from supplying arbitrary `parameters`, so exploitation only requires the caller to construct valid `Immutables` (which they already must do to compute the deterministic CREATE2 address and fund it) with fee values that sum above the deposited amount.

### Recommendation
Add an explicit fee-sanity check in `createDstEscrow` (or in `EscrowDst._withdraw`) mirroring the existing guard in `_postInteraction`:
```solidity
if (dstImmutables.protocolFeeAmount() + dstImmutables.integratorFeeAmount() >= dstImmutables.amount) revert InvalidFeeAmounts();
```
Additionally, consider requiring that destination fee parameters be provably derived from (or cross-checked against) the `DstImmutablesComplement` emitted during the corresponding source-chain `SrcEscrowCreated` event, rather than trusting arbitrary caller-supplied values.

### Proof of Concept
1. Maker/taker perform a normal src fill; `SrcEscrowCreated` is emitted with correct, validated `protocolFeeAmount`/`integratorFeeAmount` in `DstImmutablesComplement.parameters`.
2. The taker calls `createDstEscrow` directly with a *different* `Immutables.parameters` value where `protocolFeeAmount + integratorFeeAmount > amount` (still satisfying `msg.value == safetyDeposit + amount` and the timelock check).
3. The destination `EscrowDst` clone deploys successfully (no fee validation performed).
4. When the maker calls `withdraw(secret, immutables)` using these immutables, `contracts/EscrowDst.sol` line 92 underflows and reverts every time — withdrawal is permanently impossible.
5. The secret from the maker's (reverted) transaction is now public; it can be used to withdraw the source-side escrow funds, while the taker later calls `cancel` on the destination escrow to recover their own deposited tokens.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
