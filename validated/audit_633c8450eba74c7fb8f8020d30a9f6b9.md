### Title
Epoch-key mismatch between `collectWithdrawFunds` and `_claimLossAdjustedWithdrawRequest` pays haircutted receipts at par - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestWithdraw` tags each receipt with the pre-increment request epoch in `lastWithdrawRequest[_user]` (`IdleCreditVault.sol:282`). `collectWithdrawFunds`, invoked by the CDO during `stopEpoch`, stores the loss haircut under `lossRecoveryPriceByEpoch[epochNumber]`, but `epochNumber` is already incremented when the epoch stops (tests observe `strategy.epochNumber()` advancing at stop, e.g. `IdleCDOEpochQueue.t.sol:1208`). `_claimLossAdjustedWithdrawRequest` looks the price up via `lastWithdrawRequest[_user]` — the request epoch — so it reads key `N` while the haircut was stored under key `N+1`, finds `0`, and returns early. The claim then falls through to `_claimFundedWithdrawRequest`, which pays `withdrawsRequests[_user]` at full par even though the borrower only funded the haircutted amount.

### Finding Description
The goliath smuggling bug is a request-framing ambiguity: two parsers interpret the same message under different lengths. The analog here is two components interpreting the same withdraw receipt under different epoch indices:

- `requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount` (`IdleCreditVault.sol:282-293`).
- `stopEpochWithDuration(_lossAmount)` underfunds `pendingWithdraws`; `collectWithdrawFunds` then stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis` (`IdleCreditVault.sol:411-421`). Since the epoch has already stopped/advanced, `epochNumber` is the epoch *after* the request epoch.
- `_claimLossAdjustedWithdrawRequest` uses `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (`IdleCreditVault.sol:790-791`) — the stale request-epoch key — so the lookup misses, returns 0, and `_claimFundedWithdrawRequest` (`IdleCreditVault.sol:319-349`) pays the full `withdrawsRequests[_user]` because its only gate is `epochNumber > lastWithdrawRequest[_user]`, which trivially holds.

Note: if `collectWithdrawFunds` is invoked strictly before `epochNumber` increments inside `stopEpoch`, the keys align and the bug collapses — this was not fully verifiable from the indexed CDO stop-flow; the claim ordering in `claimWithdrawRequest` (lines 301-314) is consistent with the loss path being intended to consume the receipt first.

### Impact Explanation
Direct theft/insolvency: every loss-adjusted receipt is paid at par while the strategy only received `pendingBasis - pendingLoss` underlyings. Early claimers drain the funded reserve; later claimers' transfers revert, permanently freezing their withdrawals. Broken invariant: one receipt, one haircutted payout — loss waterfall is bypassed.

### Likelihood Explanation
Triggers on any `stopEpochWithDuration` with `_lossAmount > 0` while `pendingWithdraws > 0`, reachable by an unprivileged tranche holder calling `requestWithdraw` before a lossy epoch end. No privileged collusion needed; manager `stopEpoch` calls are honest inputs.

### Recommendation
Store `lossRecoveryPriceByEpoch` under the same epoch key recorded in `lastWithdrawRequest`/`withdrawsRequestsByEpoch` (the request epoch, i.e. `epochNumber - 1` post-increment, or capture the epoch before increment), or have `_claimLossAdjustedWithdrawRequest` iterate `withdrawsRequestsByEpoch` keys rather than trusting `lastWithdrawRequest`.

### Proof of Concept
```solidity
// fork mainnet; standard epoch variant
_depositWithUser(user1, 100e6);          // USDC
cdoEpoch.startEpoch();                    // epoch N running
_requestWithdrawWithUser(user1, bal);    // lastWithdrawRequest[user1] = N

// stop epoch N with a loss: borrower funds only part of pendingWithdraws
uint256 pending = strategy.pendingWithdraws();
deal(underlying, borrower, interest + pending / 2);  // 50% funded
cdoEpoch.stopEpochWithDuration(lossAmount, duration); // epochNumber -> N+1
// lossRecoveryPriceByEpoch[N+1] = ~0.5e18; pendingWithdraws = 0
// lastWithdrawRequest[user1] = N  => lookup hits key N (empty) => par claim

cdoEpoch.claimWithdrawRequest();          // pays user1 FULL amount
// strategy balance was only pending/2 => transfer pulls from reserve
// or reverts for subsequent claimers => frozen withdrawals
assert(strategy.lossRecoveryPriceByEpoch(N) == 0);
assert(strategy.lossRecoveryPriceByEpoch(N + 1) != 0);
```
