## Title
Stale confirmations from removed multisig members allow request execution below the configured confirmation threshold - (File: `multisig2/src/lib.rs`)

### Summary
When a multisig member is removed via `DeleteMember`, the contract only purges pending *requests created by* that member; it never removes that member's already-recorded *confirmations on requests created by other members*. Those stale confirmations continue to count toward the `num_confirmations` threshold check in `confirm()`, letting a request execute with fewer live-member approvals than the contract's configured threshold requires.

### Finding Description
`delete_member` in `multisig2/src/lib.rs` cleans up state as follows: [1](#0-0) 

It removes the member from `self.members`, deletes any requests whose *creator* (`r.member`) equals the removed member, and clears `num_requests_pk` for that member. It never scans `self.confirmations` to strip entries that reference the removed member on requests created by *other* members.

`confirm()` counts entries purely from the stored `HashSet<String>` without checking whether each entry still corresponds to a current member: [2](#0-1) 

So if member `B` confirms request `R` (created by `A`), and `B` is later removed via `DeleteMember`, `R`'s confirmation set still contains `B`. Any remaining member confirming `R` afterward causes `confirmations.len() + 1 >= num_confirmations` to be satisfied using `B`'s now-invalid vote, even though `B` is no longer part of the multisig and did not (and cannot) re-affirm the request.

This is the same class of bug as the referenced report: a piece of derived/bookkeeping state (`unit` in the curve case; here, the confirmation set) is not recomputed/invalidated when the underlying set (`curve`/`members`) shrinks, so a bound check (`maxLockDuration / unit` vs. `curve.length`; here, `confirmations.len() >= num_confirmations` vs. live member count) is evaluated against stale data. The identical pattern also exists in the legacy `multisig/src/lib.rs` `DeleteKey` handler, which likewise only removes requests created by the deleted key without stripping its confirmations from requests created by others.

### Impact Explanation
This breaks the core custody/authorization binding of a multisig: *confirmations counted versus live members*. A `Transfer`, `AddKey`, `FunctionCall`, or any other privileged `MultiSigRequestAction` can be executed with strictly fewer than `num_confirmations` *current* members having approved it, because a removed member's vote is silently retained and reused. Per the stated impact taxonomy this is Critical: "a multisig request executed below threshold" — e.g., funds can be transferred out of the multisig account, or a full-access/rogue key can be added to the account, with insufficient live authorization.

### Likelihood Explanation
No special privilege beyond being one of the multisig's own members is required to trigger this — it is a natural consequence of the ordinary member-removal workflow (removing a departing/compromised member) combined with any request that member had previously confirmed but was not yet executed or explicitly deleted. Since `delete_request` also requires waiting `REQUEST_COOLDOWN` (15 minutes) before manual deletion, there's a realistic window where a stale request with the removed member's confirmation persists and can be exploited by the remaining members (or reused if the removed member colluded before departure).

### Recommendation
When executing `DeleteMember` (and the analogous `DeleteKey` path in `multisig/src/lib.rs`), iterate over all `confirmations` entries and remove the deleted member's identifier from every confirmation set, not just from requests the member itself created. Alternatively, validate at `confirm()` time that every entry in the confirmation set still belongs to `self.members` before counting it toward the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C], num_confirmations = 2)`.
2. `A` calls `add_request` creating `R1 = Transfer { amount, receiver_id: attacker }`.
3. `B` calls `confirm(R1)` → `confirmations[R1] = {B}` (len 1, below threshold, not yet executed).
4. `A` and `C` create and confirm a `DeleteMember { member: B }` request, reaching threshold 2 and executing it: `B` is removed from `self.members`; only requests created by `B` are purged; `confirmations[R1]` is untouched and still contains `B`.
5. Now only `A` and `C` are members. `C` calls `confirm(R1)`: `confirmations[R1].len() (1) + 1 = 2 >= num_confirmations (2)` → `R1` executes, transferring funds to `attacker`, even though only `C` (a single current member) actually approved `R1` — `A` never confirmed it, and `B`'s stale vote was reused after `B` was removed.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
