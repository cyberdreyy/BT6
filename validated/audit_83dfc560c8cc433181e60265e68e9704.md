### Title
Dust APR0 withdraw request permanently trips `stopEpoch` via hard revert in `prepareStopEpochWithApr0` once APR becomes non-zero — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external bug is a `WARN_ON` (a hard assertion meant only for kernel bugs) placed on a condition that can legitimately change between queueing and processing — the OGM's interface could be reassigned while the packet sat in the queue, so the assertion fires spuriously and the fix is to degrade gracefully (`pr_warn`) instead of asserting.

The direct analog lives in `IdleCreditVault.prepareStopEpochWithApr0`. When `unscaledApr == 0`, `requestWithdraw` routes the request into a separate APR0 bucket (`_requestWithdrawApr0`, `apr0TotalPrincipal`). The bucket's validity is a *request-time* condition. Yet at settlement time — inside `stopEpoch` — the code re-checks a mutable condition with a hard revert: `if (unscaledApr != 0) revert NotAllowed();` [1](#0-0) . `unscaledApr` legitimately changes between request and settlement (`setAprs`/`setAprsWithBuffer` have no `apr0TotalPrincipal` guard, lines 206–220). Like the kernel WARN, an assertion meant to protect an invariant instead fires on a normal timing interleaving — but here a revert in `stopEpoch` freezes the whole pool, not just logs a warning.

### Finding Description

- `requestWithdraw` snapshots APR-zoneness at request time: `if (unscaledApr == 0 && !isClosed) _requestWithdrawApr0(_amount, _user);` [2](#0-1) . This bumps `apr0TotalPrincipal` (line 576).
- `prepareStopEpochWithApr0` is called by the CDO inside `stopEpoch`. If `apr0TotalPrincipal != 0` and `unscaledApr != 0` at that instant, it reverts `NotAllowed` (lines 502–508), reverting the entire `stopEpoch`.
- `setApr`/`setAprs` are callable by manager or the CDO and never check `apr0TotalPrincipal` (lines 206–235). Setting APR for a new epoch mid-lifecycle is a normal operation — the test `testApr0InvariantRevertsIfAprChangesAfterApr0Request` proves this exact sequence reverts (test/foundry/IdleCreditVault.t.sol:3306–3338).
- Sequence for an unprivileged tranche-token holder:
  1. During a buffer/epoch where `unscaledApr == 0` (a supported "APR0" mode), the attacker calls `cdoEpoch.requestWithdraw(dustAmount, tranche)` — e.g., 1 wei. `apr0TotalPrincipal` becomes 1.
  2. Honest manager/queue configures a non-zero APR for a subsequent epoch via `setAprsWithBuffer` (normal operation).
  3. Every `stopEpoch` call now reverts in `prepareStopEpochWithApr0`. The epoch cannot close, `epochNumber` cannot advance, pending withdrawals cannot settle — all lender funds and borrower-held principal are frozen in the strategy.
- The only recovery is for the manager to call `setAprs(0, 0)` before stopping. That zeroes `lastApr`, which collapses `expectedEpochInterest` for the entire running epoch to zero — meaning all honest lenders forfeit a full epoch of yield (a quantified loss equal to the epoch's expected interest), or the pool stays frozen. Either way, a dust request converts into pool-wide damage.
- No existing guard stops it: `_checkAllowed`/KYC only gates entry, `_onlyIdleCDO` is satisfied, and the revert is reachable precisely through honest-privileged sequencing. The revert was added as an "APR0 lifecycle invariant" (per the test comment) — exactly the misuse-of-assertion pattern of the CVE: an assertion guarding against a state that is not a bug, just a legitimate race.

### Impact Explanation

Temporary freezing of all pool funds (deposits, pending withdraws, borrower recall) for the duration of the frozen epoch, or — if unfrozen via `setAprs(0,0)` — permanent loss of an entire epoch of yield for all active LPs, quantified as `expectedEpochInterest` on the full pool NAV. Attacker cost is a dust tranche amount and a single `requestWithdraw` call. Repeated whenever APR returns to zero, the attacker can grief every APR0 transition.

### Likelihood Explanation

Trigger requires a zero-APR epoch window plus a subsequent APR change before `stopEpoch` — a normal operational sequence for a credit vault that repriced its borrower. Any KYC'd lender or tranche holder can execute step 1; no privileged cooperation needed. It is mitigated only by the manager noticing and deliberately burning the epoch's yield to unblock, so the finding is a realistic griefing/freeze vector rather than theoretical.

### Recommendation

Do not hard-revert `stopEpoch` on a request-time snapshot (mirror the fix: `pr_warn`, not `WARN_ON`). Options:

- In `prepareStopEpochWithApr0`, when `unscaledApr != 0` and `apr0TotalPrincipal != 0`, settle the bucket at zero rate (`apr0RateByEpoch[epochNumber] = 0` / skip accrual) and clear `apr0TotalPrincipal` instead of reverting — APR0 requesters simply earn nothing, matching their economic expectation at request time.
- Alternatively, make `setApr`/`setAprs` revert when `apr0TotalPrincipal != 0`, shifting the guard to the state-transition point (request-time invariant becomes a set-time precondition), so `stopEpoch` can never inherit the bad combination.

### Proof of Concept

Foundry fork PoC (mainnet Clearpool USDC vault, mirroring `IdleCreditVault.t.sol` harness):

```solidity
function testDustApr0RequestFreezesStopEpoch() external {
    // Setup: pool in APR0 mode (unscaledApr == 0), attacker holds tranche tokens
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);

    idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(underlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);
    _forceLastEpochAprToZero(); // unscaledApr == 0 window

    // Attacker files a dust APR0 request (1 wei of tranche)
    address attacker = makeAddr('attacker');
    dealTranche(attacker, 1); // give attacker 1 wei AA tranche
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(1, address(AAtranche));
    assertEq(IdleCreditVault(address(strategy)).apr0TotalPrincipal(), 1);

    _startEpochAndCheckPrices(1);
    // Honest manager reprices APR for a later epoch — normal operation
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(1e18, 1e18);

    // stopEpoch now always reverts -> epoch frozen
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.stopEpoch(0, 0);

    // Only recovery path: manager zeroes APR, destroying the whole epoch's yield
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    uint256 lostInterest = <expected epoch interest>; // > 0 previously, now 0
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // succeeds but epoch accrued 0 interest
}
```
