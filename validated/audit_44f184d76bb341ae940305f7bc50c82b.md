This is a real, verifiable gap between the CostTracker's `allocated_accounts_data_size` accounting and actual account-data growth tracked via `resize_delta`/`accounts_resize_delta`.

### Title
`CostTracker::would_fit`'s per-block accounts-data-growth gate (`MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`) is not enforced against CPI-driven `AccountInfo::resize`/realloc growth - ([File: cost-model/src/cost_model.rs])

### Summary
`CostModel::calculate_allocated_accounts_data_size` only inspects top-level System Program instructions (`CreateAccount`, `CreateAccountWithSeed`, `Allocate`, `AllocateWithSeed`, `CreateAccountAllowPrefund`) to estimate account-data growth for a transaction, both for the pre-execution estimate and the post-execution "actual" recompute used by `check_block_cost_limits`/`CostTracker::would_fit`. Any account-data growth performed via a program's own `AccountInfo::resize()` (the realloc path, enforced instead by `transaction_accounts.rs`'s `resize_delta`/`can_data_be_resized` and `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`) is never counted toward `allocated_accounts_data_size`, so it never contributes to `CostTracker`'s `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` gate.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` iterates only the transaction's top-level instructions and matches on `program_id == system_program::id()`, deserializing System Program instructions to extract the declared `space` field [1](#0-0) . Any other instruction (including a call into an attacker-deployed program that internally calls `AccountInfo::resize`/realloc, whether directly or via CPI) returns `SystemProgramAccountAllocation::None` and contributes zero to `tx_attempted_allocation_size` [2](#0-1) .

This same function is used both for the pre-execution estimate (`CostModel::calculate_cost`) and for the "actual" post-execution cost used by `check_block_cost_limits` (`CostModel::calculate_cost_for_executed_transaction` → `calculate_transaction_cost`, which unconditionally recomputes `allocated_accounts_data_size` via the same static instruction-based function regardless of what was passed as "actual" data) [3](#0-2) [4](#0-3) . The "actual" recompute only replaces `programs_execution_cost` and `loaded_accounts_data_size_cost` (a CU/compute-budget cost based on bytes *loaded*, not bytes *grown*) — `allocated_accounts_data_size` is never derived from the real resize activity that occurred during execution [5](#0-4) .

`CostTracker::would_fit` gates purely on this `allocated_accounts_data_size` field against `limits.allocated_data_size` (default `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA = 100_000_000`) [6](#0-5) [7](#0-6) . Meanwhile, the actual, runtime-enforced measure of account growth from CPI realloc is tracked completely separately, per-account, via `TransactionAccounts::resize_delta`/`update_accounts_resize_delta`, bounded per-transaction by `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (20MB) [8](#0-7) , and aggregated into `Bank::accounts_data_size_delta_on_chain` via `commit_transactions`'s `accounts_resize_delta` sum [9](#0-8) . Nothing wires this per-transaction `resize_delta` back into `CostTracker`'s `allocated_accounts_data_size`, so a transaction that grows account data purely via `AccountInfo::resize`/CPI-realloc (not via a top-level System Program `CreateAccount`/`Allocate`/`CreateAccountWithSeed` instruction) is counted as `allocated_accounts_data_size = 0` in both the pre- and post-execution cost, and never contributes to the block's `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` budget — even though it is a legitimate, bounded (up to 20MB per transaction) accounts-db growth event.

Note: the `calculate_allocated_accounts_data_size` function's own doc comment acknowledges this is incomplete: "eventually, potentially determine account data size of all writable accounts / at the moment, calculate account data size of account creation" [10](#0-9) , indicating this is a known, intentional simplification rather than a hidden logic bug, though its security consequence (an unbounded/uncapped avenue for per-block accounts-db growth via realloc-based programs) does not appear to be otherwise mitigated.

### Impact Explanation
An attacker can pack a block (or many sequential leader-slot transactions within a bank) with transactions that each CPI into their own deployed program, which each call `AccountInfo::resize()`/realloc to grow account data by up to `MAX_PERMITTED_DATA_INCREASE` (10KB) per instruction or up to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION` (20MB) per transaction, without any top-level System Program `CreateAccount`/`Allocate`/`CreateAccountWithSeed`/`AllocateWithSeed` instruction. `CostTracker::would_fit` will never report `CostTrackerError::WouldExceedAccountDataBlockLimit` for these transactions since `allocated_accounts_data_size` stays at 0, even as real accounts-db growth (tracked separately via `resize_delta`/`accounts_data_size_delta_on_chain`) accumulates well past `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` (100MB) in a single block. This is a compute/cost-metering-bypass class issue: the per-block cap intended to bound the rate of accounts-db growth (and thus snapshot/replay/storage growth) can be exceeded without ever tripping the intended cost-tracker gate.

### Likelihood Explanation
Fully achievable by an unprivileged attacker: deploy an SBPF program that calls `account.resize(...)` (directly or via CPI, e.g. the existing `programs/sbf/rust/realloc`/`realloc_invoke` test programs demonstrate the exact mechanics) [11](#0-10) , fund a keypair, and submit many such transactions to fill a block. No special configuration, keys, or privileged capability is required beyond normal program deployment and transaction submission.

### Recommendation
Extend `CostModel::calculate_allocated_accounts_data_size` (or the post-execution recompute path in `calculate_cost_for_executed_transaction`) to also account for the actual account-data growth measured at execution time (e.g., `AccountsDeltas::accounts_resize_delta`/`TransactionExecutionDetails::accounts_deltas`, which is already computed per transaction) [12](#0-11) , and feed that "actual" allocated-data-size value into `CostTracker::try_add`/`would_fit` post-execution so that CPI-driven realloc growth is charged against `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA` regardless of whether it originated from a System Program instruction.

### Proof of Concept
A concrete PoC would deploy a Rust SBF program exercising `AccountInfo::resize` similarly to the existing `programs/sbf/rust/realloc_invoke` test program, submit repeated transactions (each growing a distinct account by close to `MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION`) into the same bank via `bank.load_execute_and_commit_transactions`/`execute_batch`, and assert that `bank.write_cost_tracker().unwrap().allocated_accounts_data_size` stays at (or near) 0 (and `try_add`/`would_fit` never returns `CostTrackerError::WouldExceedAccountDataBlockLimit`) while `bank.load_accounts_data_size_delta_on_chain()` grows well past `MAX_BLOCK_ACCOUNTS_DATA_SIZE_DELTA`. I was unable to fully verify within this investigation whether any other layer (e.g., accounts-db snapshotting or a separate resource-exhaustion guard) independently caps total per-block growth from this path; based on the code reviewed, `CostTracker` is the only mechanism explicitly designed for this purpose and it does not observe CPI-realloc-driven growth.

    /// eventually, potentially determine account data size of all writable accounts
    /// at the moment, calculate account data size of account creation
    fn calculate_allocated_accounts_data_size<'a>(
        instructions: impl Iterator<Item = (&'a Pubkey, SVMInstruction<'a>)>,
        feature_set: &FeatureSet,
    ) -> u64 {
        let mut tx_attempted_allocation_size = Saturating(0u64);
        for (program_id, instruction) in instructions {
            match Self::calculate_account_data_size_on_instruction(
                program_id,
                instruction,
                feature_set,
            ) {
                SystemProgramAccountAllocation::Failed => {
                    // If any system program instructions can be statically
                    // determined to fail, no allocations will actually be
                    // persisted by the transaction. So return 0 here so that no
                    // account allocation budget is used for this failed
                    // transaction.
                    return 0;
                }
                SystemProgramAccountAllocation::None => continue,
                SystemProgramAccountAllocation::Some(ix_attempted_allocation_size) => {
                    tx_attempted_allocation_size += ix_attempted_allocation_size;
                }
            }
        }

        // The runtime prevents transactions from allocating too much account
        // data so clamp the attempted allocation size to the max amount.
        //
        // Note that if there are any custom bpf instructions in the transaction
        // it's tricky to know whether a newly allocated account will be freed
        // or not during an intermediate instruction in the transaction so we
        // shouldn't assume that a large sum of allocations will necessarily
        // lead to transaction failure.
        (MAX_PERMITTED_ACCOUNTS_DATA_ALLOCATIONS_PER_TRANSACTION as u64)
            .min(tx_attempted_allocation_size.0)
    }

    pub(crate) fn update_accounts_resize_delta(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        let accounts_resize_delta = self.resize_delta.get();
        self.resize_delta.set(
            accounts_resize_delta.saturating_add((new_len as i64).saturating_sub(old_len as i64)),
        );
        Ok(())
    }

    pub(crate) fn can_data_be_resized(
        &self,
        old_len: usize,
        new_len: usize,
    ) -> Result<(), InstructionError> {
        // The new length can not exceed the maximum permitted length
        if new_len > MAX_ACCOUNT_DATA_LEN as usize {
            return Err(InstructionError::InvalidRealloc);
        }
        // The resize can not exceed the per-transaction maximum
        let length_delta = (new_len as i64).saturating_sub(old_len as i64);
        if self.resize_delta.get().saturating_add(length_delta)
            > MAX_ACCOUNT_DATA_GROWTH_PER_TRANSACTION
        {
            return Err(InstructionError::MaxAccountsDataAllocationsExceeded);
        }
        Ok(())
    }
