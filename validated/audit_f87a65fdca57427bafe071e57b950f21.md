## Title
Stale confirmations from removed multisig keys/members count toward the approval threshold, allowing request execution below the configured `num_confirmations` - (File: multisig/src/lib.rs, multisig2/src/lib.rs)

### Summary
The external report describes an unvalidated field (`ip_address`) being trusted to enforce a security boundary (host restriction on Redpanda ACLs), letting an attacker widen the boundary to `*`. The structural analog in this repository is in the `multisig` and `multisig2` contracts: the `confirm` function only counts the *size* of the stored confirmation set against `num_confirmations`, without re-validating that every entry in that set still corresponds to a live multisig member/key. When a key/member is removed, only confirmations on requests *originally submitted* by that key are cleaned up — confirmations that key contributed to *other* pending requests are never purged. Those stale confirmations continue to count toward the M-of-N threshold, breaking the binding `confirmations counted == live members who approved`.

### Finding Description
`confirm()` in both contracts computes approval purely from the size of the `HashSet` of confirmers: [1](#0-0) 

The corresponding cleanup logic in the `DeleteKey` action only removes confirmations for requests where the request's *original signer* (`r.signer_pk`) equals the key being deleted — it does not scan the `confirmations` sets of other active requests for stale entries from that key: [2](#0-1) 

The same pattern exists in `multisig2`'s `DeleteMember`/`confirm`, keyed on `r.member` (the original request adder) rather than on who confirmed: [3](#0-2) [4](#0-3) 

Because a removed key's/member's prior confirmation on a *different* request (one they didn't originally add) is never invalidated, that confirmation remains valid data that gets summed into the threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations`. This breaks the intended equality: `confirmations recorded == confirmations from currently authorized members`.

### Impact Explanation
This allows a `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or `DeployContract` request to execute with fewer *live* member approvals than `num_confirmations` requires — i.e., "a multisig request executed below threshold," which is explicitly listed as Critical impact. Funds controlled by the multisig account can be moved (or a full-access key added) by a coalition smaller than the configured threshold, undermining the entire M-of-N custody guarantee of the contract.

### Likelihood Explanation
This requires no privileged access beyond being (or having been) a legitimate multisig member/key holder at some point — a realistic operational scenario (key rotation, offboarding a team member, revoking a compromised key). Any time a member is removed after having confirmed, but not created, a still-pending request, the stale confirmation persists silently and will be counted on the next confirmation, with no error or warning surfaced to the remaining members.

### Recommendation
When deleting a key/member (`DeleteKey`/`DeleteMember`), iterate over **all** active requests' confirmation sets (not just requests originally added by that key/member) and remove any confirmation entries belonging to the removed key/member. Alternatively, validate membership of every entry in the confirmation set at the time `confirm()` computes the threshold, discarding/ignoring confirmations from accounts/keys no longer present in `self.members` (multisig2) or no longer holding an access key (multisig).

### Proof of Concept
1. Deploy `multisig` with keys `A, B, C, D` and `num_confirmations = 3`.
2. `A` calls `add_request` for `Transfer { amount }` to an external account → request `X`, confirmations `{}`.
3. `D` (later to be revoked, e.g. suspected compromised) calls `confirm(X)` → confirmations `{D}` (1/3).
4. `A` calls `confirm(X)` → confirmations `{D, A}` (2/3), not yet executed.
5. Members `A, B, C` submit and confirm a separate request `Y` = `DeleteKey { public_key: D }` to revoke `D`'s key (e.g. because `D` is suspected malicious). `Y` executes via `execute_request`, which only cleans confirmations for requests where `signer_pk == D` — request `X` was signed/added by `A`, so its confirmation set `{D, A}` is left untouched. `D`'s key is now deleted from the account.
6. `B` calls `confirm(X)` → `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → request `X` executes the `Transfer`, even though only `A` and `B` are currently authorized signers (2 live approvals), with `D`'s stale, already-revoked confirmation making up the third. [1](#0-0) [2](#0-1)

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
