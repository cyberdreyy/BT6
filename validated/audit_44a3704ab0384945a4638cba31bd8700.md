### Title
Stale `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` entries are never removed on claim, inflating default-recovery basis and permanently trapping recovered funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is a use-after-free: an error path frees an `opp_table` but fails to unlink it from the global `lazy_opp_tables` list, so a later iteration dereferences freed entries. The direct analog in `IdleCreditVault` is an entry that is logically "freed" (an instant-withdraw receipt that was fully funded and claimed at par) but is never unlinked from the per-epoch accounting maps `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch`. When the borrower later defaults in the same epoch, `defaultPendingClaimBasis` iterates that stale epoch bucket and counts already-paid receipts as outstanding claims, diluting `defaultRecoveryPrice` and leaving the excess recovery permanently stranded in the contract.

### Finding Description
`requestInstantWithdraw` records each receipt in three places: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the aggregate `instantWithdrawClaimsByEpoch[currentEpoch]`, plus `pendingInstantWithdraws` [1](#0-0) .

On a successful claim, `claimInstantWithdrawRequest` clears only the aggregate per-user counter and burns the receipt; it never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]` [2](#0-1) .

If the borrower defaults while `pendingInstantWithdraws != 0` (i.e., only part of the epoch's instant queue was funded), `finalizeDefaultRecovery` sets `defaultInstantWithdrawsFinalized = true` and `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — which still contains the already-claimed, already-paid receipts [3](#0-2) . The stale entries inflate `totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed against phantom claims [4](#0-3) . The unpaid user then claims via `_claimDefaultedInstantWithdrawRequest` at the diluted price, while the share of the reserve reserved for the stale entry can never be paid: re-claiming underflows `instantWithdrawsRequests[_user] -= claimBasis` [5](#0-4) .

### Impact Explanation
Every underlying token recovered for instant-withdraw claimants is split over a basis that includes receipts already paid at par. If attacker A requests and claims an instant withdraw of amount `X` in epoch N, and victim B's instant request of amount `Y` remains unfunded when the borrower defaults, the finalized basis is `X + Y` (+ normal pending) instead of `Y`. B receives only `Y/(X+Y)` of their fair recovery share; the proportional remainder of `defaultRecoveryReserve` has no valid claimant (A's double-claim reverts on underflow) and is permanently locked in the strategy — direct loss to B equal to `recovered * X/(X+Y)` and permanent freezing of recovery funds. A needs only a normal KYC-allowed deposit and an instant-withdraw request; sequencing is ordinary user behavior, not privileged.

### Likelihood Explanation
The attacker's transactions are minimal and unprivileged: deposit, request instant withdraw, get funded by the honest CDO via `collectInstantWithdrawFunds`, claim, then let a borrower default occur in the same epoch while some other instant receipt stays unfunded — a routine partial-liquidity condition. No guard exists: `claimInstantWithdrawRequest` deliberately ignores the per-epoch maps, and nothing else clears them. The conditions (partial instant funding followed by same-epoch default) are plausible whenever instant liquidity is thinner than the queue.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and `instantWithdrawClaimsByEpoch[epochNumber]` alongside `instantWithdrawsRequests[_user]` (mirroring how `_claimDefaultedInstantWithdrawRequest` already decrements both maps), so paid receipts are unlinked from the epoch claim list before default finalization can read them.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol style, instant-withdraw enabled variant
function testStaleInstantEpochEntryDilutesRecovery() external {
    // epoch N running, APR normal, instant mode
    address userA = makeAddr("attacker");
    address userB = makeAddr("victim");
    uint256 amtA = 100_000 * ONE_SCALE;
    uint256 amtB = 100_000 * ONE_SCALE;

    _depositWithUser(userA, amtA, true);
    _depositWithUser(userB, amtB, true);
    _startEpochAndCheckPrices(0);

    // both request instant withdraw in epoch N
    vm.prank(userA); cdoEpoch.requestInstantWithdraw(amtA, address(AAtranche));
    vm.prank(userB); cdoEpoch.requestInstantWithdraw(amtB, address(AAtranche));

    // CDO has cash for only A's request; fund and let A claim at par
    deal(defaultUnderlying, address(cdoEpoch), amtA);
    vm.prank(manager); cdoEpoch.collectInstantWithdrawFunds(amtA); // pendingInstantWithdraws = amtB
    vm.prank(userA); cdoEpoch.claimInstantWithdrawRequest();       // A paid 1:1
    // BUG: instantWithdrawsRequestsByEpoch[A][N] and
    //      instantWithdrawClaimsByEpoch[N] still contain amtA

    // borrower defaults in the same epoch; recovery sized to amtB + active basis
    _handleBorrowerDefault(); // honest manager path
    uint256 recovery = /* recovered funds for pending instant claims */;
    deal(defaultUnderlying, recoverySource, recovery);
    cdoEpoch.finalizeDefaultRecovery(recovery, recoverySource);

    // basis counted amtA + amtB -> defaultRecoveryPrice ~ recovery/(amtA+amtB)
    // B claims only ~half of what the reserve holds for instant receipts
    uint256 balPre = underlying.balanceOf(userB);
    vm.prank(userB); cdoEpoch.claimInstantWithdrawRequest();
    uint256 paid = underlying.balanceOf(userB) - balPre;
    assertLt(paid, recovery, "victim diluted by stale claimed entry");

    // the remainder of defaultRecoveryReserve is permanently stranded:
    // A cannot claim it again (instantWithdrawsRequests[A] underflows),
    // and no other claimant exists for the phantom basis.
}
```

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }

    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }
