### Title
Signer weight double-counted across accepted/rejected tallies when a signer flips its vote (`Reject` → `Accept`) — `StackerDBListener` weight bookkeeping (`stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::run` maintains, per proposed block, two independent weight counters — `total_weight_approved` and `total_weight_rejected` — guarded by two *different* dedup sets: `gathered_signatures` for acceptances and `responded_signers` for rejections. Because `Accepted` handling both writes to `responded_signers` *and* dedups against `gathered_signatures`, while `Rejected` handling dedups against `responded_signers` only, a single signer that legitimately flips its verdict from `Reject` to `Accept` for the same block causes its weight to be added to both `total_weight_rejected` and `total_weight_approved`, violating the invariant that a signer's weight belongs to at most one side of the tally.

### Finding Description
In the `Accepted` branch: [1](#0-0) 
the dedup check is `!block.gathered_signatures.contains_key(&slot_id)`, and after adding weight it inserts into **both** `gathered_signatures` and `responded_signers`.

In the `Rejected` branch: [2](#0-1) 
the dedup check is `block.responded_signers.insert(slot_id)` — it only consults/updates `responded_signers`, never touches `gathered_signatures`.

Sequence that breaks the equality:
1. Signer `S` (weight `w`) evaluates a proposal and rejects it (e.g. transient `check_block_against_signer_db_state` failure, or a conflict that is later resolved — the signer-side design explicitly allows `LocallyRejected → LocallyAccepted : re-evaluated`, documented in `docs/signer-flows.md` §2 and implemented via `should_reevaluate_block`/`should_reevaluate_reject_reason` in `stacks-signer/src/v0/signer.rs`). The node receives the `Rejected` message: `responded_signers.insert(slot_id)` succeeds (first time) → `total_weight_rejected += w`.
2. The same block proposal is re-evaluated by `S` (re-proposal, or a later pre-commit re-check that now sees the block as valid) and `S` sends `Accepted`. On the node side, the `Accepted` handler checks `gathered_signatures.contains_key(&slot_id)`, which is still empty for `S` (it was never populated by the earlier `Rejected` path) → the guard passes → `total_weight_approved += w` a **second time** for the same underlying signer weight.
3. Now `total_weight_rejected` and `total_weight_approved` both contain `w` for signer `S` simultaneously. The sum `total_weight_approved + total_weight_rejected` can exceed `total_weight`, and the threshold check: [3](#0-2) 
can fire based on weight that includes a signer whose vote is not cleanly "currently approving" relative to the rejected tally — the two counters are no longer disjoint subsets of the same weighted signer set, breaking the aggregated-weight vs. verified-accepts equality that `SignerCoordinator`/the miner rely on to decide the block has reached the 70% threshold.

### Impact Explanation
This falls under the "aggregated-weight vs verified-accepts" equality-break category (Critical per the rules): the miner/`SignerCoordinator` trusts `total_weight_approved >= weight_threshold` (computed via `NakamotoBlockHeader::compute_voting_weight_threshold`, wired in `SignerCoordinator`/`StackerDBListener::new`) as proof that a genuine 70%-by-weight, mutually-exclusive-vote quorum approved the block. With the double-count, the threshold can be reached using weight from a signer whose vote history is inconsistent (also present in `total_weight_rejected`), understating the true diversity/exclusivity of the approving set. This is triggerable by a single signer flipping its vote — no majority collusion needed — and requires only the signer's own key (the signer's normal re-evaluation logic legitimately produces a Reject-then-Accept sequence for the same block hash).

### Likelihood Explanation
Reject→Accept transitions for the same `signer_signature_hash` are an intended, first-class part of the v0 signer's state machine (`BlockState::LocallyRejected → LocallyAccepted : re-evaluated`, and the async-sibling-validation re-proposal path exercised by `stacks-signer/src/v0/tests.rs` `async_sibling_validation` tests), so this sequence is not a contrived edge case — any signer whose transient rejection reason clears (e.g. `ConnectivityIssues`, a stale conflict going stale, `check_block_against_signer_db_state` recovering) will naturally produce this exact node-side sequence.

### Recommendation
Use a single, unified per-block "last known vote" map (slot_id → vote kind + weight) instead of two independently-dedup'd sets (`gathered_signatures` for accept, `responded_signers` for reject). On any new vote from a slot, first check the signer's previous recorded vote in that unified map; if it differs from the incoming vote, subtract the previously-counted weight from the old bucket before adding it to the new bucket (or simply recompute both totals from the unified map on every update rather than incrementally patching two counters guarded by different keys).

### Proof of Concept
Conceptual repro (network-observable):
1. Node proposes block `B`; signer `S` (weight `w`) submits `BlockResponse::Rejected` for `B` → node: `responded_signers={S}`, `total_weight_rejected += w`.
2. `S`'s local re-evaluation (per `should_reevaluate_reject_reason`/timeout path) later flips to `BlockResponse::Accepted` for the same `signer_signature_hash` → node's `Accepted` handler checks `gathered_signatures` (empty for `S`) → adds `w` to `total_weight_approved`.
3. Inspect `StackerDBListener`'s `blocks` map for `B`: `total_weight_rejected >= w` and `total_weight_approved >= w` hold simultaneously, i.e., `S`'s weight is counted on both sides — confirmable by unit-testing `StackerDBListener::run`'s message-handling loop directly with a synthetic `Rejected` then `Accepted` message pair from the same `slot_id`, and observing both counters increment for that slot without either being decremented.
