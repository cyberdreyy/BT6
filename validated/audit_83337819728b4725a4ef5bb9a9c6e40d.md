### Title
Signer weight double-counted across accept/reject tallies on message flip lets a single signer's stale rejection permanently poison a block's status - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener` maintains two independent, monotonically-incrementing weight counters per block — `total_weight_approved` and `total_weight_rejected` — inside `BlockStatus` [1](#0-0) . Unlike the DB-backed signer-side tallies (`store_and_process_block_signature` / `store_and_process_block_rejection` in `stacks-signer/src/v0/signer.rs`), which recompute weight from the source-of-truth table on every call [2](#0-1) , this node-side listener never recomputes from a canonical set; it only increments. The guard against double-counting a single message kind (`gathered_signatures.contains_key(&slot_id)` for accepts, `responded_signers.insert(slot_id)` for rejects) does not prevent the *same signer's* weight from being added to both counters when that signer's decision changes for the same block.

### Finding Description
On an accepted `BlockResponse`, weight is added to `total_weight_approved` guarded only by `!block.gathered_signatures.contains_key(&slot_id)`, and `slot_id` is then also inserted into the shared `responded_signers` set [3](#0-2) . On a rejected `BlockResponse`, weight is added to `total_weight_rejected` guarded by `block.responded_signers.insert(slot_id)` [4](#0-3) .

If a signer first sends a **Reject** for a block (weight added to `total_weight_rejected`, `slot_id` inserted into `responded_signers`) and later sends an **Accept** for the same block (a legitimate, protocol-supported transition — the signer state machine explicitly supports re-evaluating and reversing a rejection, see `should_reevaluate_reject_reason`/`should_reevaluate_block` [5](#0-4) ), the Accept branch checks `gathered_signatures`, not `responded_signers`. Since `gathered_signatures` does not yet contain this `slot_id`, the Accept weight is added to `total_weight_approved` as well. Nothing ever subtracts the earlier weight from `total_weight_rejected`. The signer's weight is now permanently double-booked: once as rejected, once as approved, for the lifetime of that `BlockStatus` entry.

### Impact Explanation
`SignerCoordinator::get_block_status` derives the miner's decision purely from these two counters: it checks `total_weight_rejected + weight_threshold > total_weight` first (global-reject path, returning `SignersRejected`), and only afterward checks `total_weight_approved >= weight_threshold` [6](#0-5) . Because a stale rejection weight is never cleared even after the same signer switches to accept, `total_weight_rejected` can be inflated with weight that no longer reflects any signer's current opinion. In a set where the rejecting/blocking minority is close to the >30% threshold, one or more signers legitimately reversing an earlier rejection (a normal, protocol-endorsed flow) can push `total_weight_rejected` over the blocking threshold even though a genuine super-majority currently approves the block — permanently wedging that specific block proposal into the `SignersRejected` branch and forcing the miner to abandon a block that in fact has enough live approvals. This is a liveness wedge: the signer set can never sign this particular proposal even though a valid quorum currently supports it, satisfying the "signer wedged into never signing valid blocks" impact category.

### Likelihood Explanation
This does not require a majority of colluding signers or key compromise — a single signer naturally flip-flopping (reject then accept) due to normal re-evaluation logic, or a delayed/reordered gossip delivery of an earlier reject arriving after a later accept, is enough to poison the counters for that one block hash. Because `BlockStatus` is scoped per `block_signer_sighash` and persists for the life of that specific proposal's wait loop, the effect is a targeted DoS against one proposal rather than a fleet-wide fault, keeping likelihood moderate-to-high in networks with any latency/reordering or signers that reconsider rejections.

### Recommendation
Use a single `HashMap<slot_id, Decision>` (Accept/Reject) per block instead of two independently-incremented counters plus a separate `responded_signers` set, and recompute `total_weight_approved`/`total_weight_rejected` from that map on each update (mirroring the DB-driven recomputation already used in `stacks-signer/src/v0/signer.rs`), so a signer's most recent decision is the only one counted, and switching decisions properly moves weight from one bucket to the other instead of accumulating in both.

### Proof of Concept
I could not fully verify the block-status lifecycle helpers (`reset_rejections`, and how/when a fresh `BlockStatus` is inserted into the shared `blocks` map for a given `block_signer_sighash`) because my last tool call to trace those definitions failed to execute before the iteration budget ended. This should be confirmed against `stacks-node/src/nakamoto_node/stackerdb_listener.rs` (the `blocks: Arc<Mutex<HashMap<Sha512Trunc256Sum, BlockStatus>>>` initialization and any code path that clears/replaces an entry) and `stacks-node/src/nakamoto_node/signer_coordinator.rs::reset_rejections` before treating this as fully proven; the reasoning above is based on the accept/reject handler code shown in the citations, which does show the double-count guard asymmetry described.
