### Title
Mid-epoch deposit priced against a stale `trancheAPRSplitRatio` lets a depositor mint discounted tranche shares that capture interest they never paid for - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`depositDuringEpoch` mints tranche shares at a discounted price that bakes in the *expected* epoch interest for that tranche, computed with the **current** `trancheAPRSplitRatio`. The actual interest is distributed later, at `stopEpoch`/`_updateAccounting`, using whatever `trancheAPRSplitRatio` is in force **at that moment**. Since `setTrancheAPRSplitRatio` can be called by the (honest) owner at any time, a KYC'd lender can front-run a ratio increase: deposit mid-epoch while their tranche's expected interest share is low (cheap shares), then let the owner's routine ratio change credit them a full share of the real interest. This is the same bug class as `AdvancedDistributor`: the factor used at mint time differs from the factor used at settlement/burn time.

### Finding Description
In `depositDuringEpoch` the mint amount is:

```solidity
uint256 trancheExpected = _calcTrancheInterestShare(
    _netGainAfterFees(expectedInt - pendingFees, ...), _tranche);   // uses trancheAPRSplitRatio NOW
uint256 trancheInterest = _calcTrancheInterestShare(
    _netGainAfterFees(interest, ...), _tranche);                    // uses trancheAPRSplitRatio NOW
uint256 expectedFinal = _lastSavedNAV(_tranche) + trancheExpected;
_minted = (_amount + trancheInterest) * _trancheTotSupply / expectedFinal;
```
`contracts/IdleCDOEpochVariant.sol:699-725`

`_calcTrancheInterestShare` multiplies by `trancheAPRSplitRatio` (per the test mirror at `test/foundry/IdleCreditVault.t.sol:1928-1931`), i.e. the mint price commits to a split ratio sampled at deposit time. But when the epoch is stopped, `_updateAccounting` re-splits the realized gain between AA and BB using `trancheAPRSplitRatio` read fresh (`contracts/IdleCDOCreditVault.sol:228-236`), and `trancheAPRSplitRatio` is mutable by the owner via `setTrancheAPRSplitRatio` (`contracts/IdleCDO.sol:899-903`) — with AYS disabled it stays at whatever the owner last set.

Scenario (mirroring the report):
1. Owner sets `trancheAPRSplitRatio` low (AA share of yield ≈ 0), e.g. to favor BB during a junior-heavy period.
2. Epoch starts. Attacker (KYC-passed lender) calls `depositDuringEpoch(AA)`. `trancheExpected` and `trancheInterest` for AA are ≈ 0, so `expectedFinal` is small and the attacker receives *more* AA shares per underlying — the mint price implicitly assumes AA earns almost nothing this epoch.
3. Owner later raises `trancheAPRSplitRatio` (a routine, honest operation; the attacker just front-runs/positions around it).
4. At `stopEpoch`, `_updateAccounting` credits AA with the new, larger share of the epoch interest, distributed pro-rata over the inflated AA supply — including the attacker's cheap shares.

The reverse also holds: if the ratio drops after a BB-priced deposit, the depositor's shares are burned/redeemed at a price reflecting less interest than priced in — griefing/underpayment path analogous to "burn more than minted → revert" in the report.

### Impact Explanation
Fair-mint invariant broken: shares minted under interest assumption A are settled under assumption B. The attacker captures a slice of tranche interest that was never priced into their shares, diluting existing AA holders' epoch yield. Quantifiable as roughly `attackerShares/AATotalSupply × (AA interest share delta)` — e.g. with 10% APR on 1000 USDC and a 0%→50% AA ratio flip, the attacker mints ~5% more shares than warranted and extracts ~half of the pool's epoch AA yield spread across the extra supply.

### Likelihood Explanation
- Requires only an unprivileged KYC-passed lender; no privileged collusion.
- Requires an owner `setTrancheAPRSplitRatio` change mid-epoch while `isDepositDuringEpochDisabled == false` and `isAYSActive == false` (AYS auto-updates the ratio, so the window exists only in fixed-ratio mode — which is precisely the mode where deposits during epoch are allowed).
- The attacker can watch the mempool and front-run the ratio transaction, exactly like front-running `setVoteFactor` in the original report.

Uncertainty: if `trancheAPRSplitRatio` is intended to be immutable post-deployment in these vaults, the practical window narrows; the code nonetheless exposes the setter unconditionally.

### Recommendation
Snapshot the split ratio used for mid-epoch pricing (e.g. store `trancheAPRSplitRatio` at `startEpoch` into an `epochSplitRatio` variable) and use that snapshot both in `depositDuringEpoch`'s `_calcTrancheInterestShare` calls and in the epoch-end gain distribution — or forbid `setTrancheAPRSplitRatio` while `isEpochRunning`, mirroring the report's fix of making the factor deployment-time constant.

### Proof of Concept
Foundry sketch (extend `test/foundry/IdleCreditVault.t.sol`, reusing `_startEpochAndCheckPrices`/`_toggleEpoch` helpers):

```solidity
function testMidEpochDepositStaleSplitRatio() external {
    // 10% apr, 365-day epoch, AYS off; AA ratio set to 0 (BB gets all yield)
    vm.startPrank(manager);
    cdoEpoch.setEpochParams(365 days, 0);
    IdleCreditVault(address(strategy)).setAprs(10e18, 10e18);
    vm.stopPrank();
    vm.prank(owner);
    cdoEpoch.setTrancheAPRSplitRatio(0);

    idleCDO.depositAA(1000 * ONE_SCALE);
    vm.prank(owner);
    cdoEpoch.setIsAYSActive(false);
    _startEpochAndCheckPrices(0);

    vm.warp(cdoEpoch.epochEndDate() - cdoEpoch.epochDuration() / 2);
    vm.prank(owner);
    cdoEpoch.setIsDepositDuringEpochDisabled(false);

    // Attacker deposits AA mid-epoch; trancheInterest for AA = 0, minted shares
    // priced as if AA earns nothing this epoch
    address attacker = makeAddr('attacker');
    deal(defaultUnderlying, attacker, 1000 * ONE_SCALE);
    vm.startPrank(attacker);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), 1000 * ONE_SCALE);
    uint256 minted = cdoEpoch.depositDuringEpoch(1000 * ONE_SCALE, address(AAtranche));
    vm.stopPrank();
    // minted ≈ (1000 + 0) * supply / (lastNAVAA + 0) -> no interest discount

    // Owner legitimately restores the AA split before epoch end
    vm.prank(owner);
    cdoEpoch.setTrancheAPRSplitRatio(50_000); // 50% to AA

    _toggleEpoch(false, 10e18, _expectedFundsEndEpoch());

    // Attacker's shares now earn the full AA interest share they were never
    // priced for: attackerValue > deposit + correctly-prorated interest
    uint256 attackerValue = minted * cdoEpoch.virtualPrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
    // Under a correct snapshot, attacker should get ~1000 * (1 + 10%/2 * 0.5) = 1025;
    // they instead receive ~1050 -> ~25 USDC siphoned from existing AA holders
    assertGt(attackerValue, 1025 * ONE_SCALE);
}
```
