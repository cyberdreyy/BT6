### Title
Service containers can overwrite the shared `stepsRunnerBinaryPath()` helper binary before the build container's `execStepsProxy` exec runs it - (File: `executors/kubernetes/steps_pod.go`, `executors/kubernetes/steps.go`)

### Summary
In Concrete mode, `stepsVolumeMounts()` mounts the same `scripts` emptyDir at `s.scriptsDir()` in the bootstrap init container, the build container (`stepsBuildContainer`), and every job-declared service container (`stepsServiceContainer`), with no `ReadOnly: true` set on any of these mounts. Because emptyDir volumes are pod-level shared storage, any service container process (fully controlled by the job author via `.gitlab-ci.yml` `services:` entrypoint/command) can write to `s.scriptsDir()` and overwrite the file at `s.stepsRunnerBinaryPath()` before `execStepsProxy` (`executors/kubernetes/steps.go`) later execs that exact path inside the build container.

### Finding Description
`stepsVolumeMounts()` (`executors/kubernetes/steps_pod.go:532-557`) returns a mount of the `scripts` volume at `s.scriptsDir()` with no `ReadOnly` flag, and this same mount list is used by:
- the bootstrap init container (`buildStepsBootstrapInitContainer`, line 139),
- the build container (`stepsBuildContainer`, line 350),
- every service container (`stepsServiceContainer`, line 438).

`stepsRunnerBinaryPath()` (`executors/kubernetes/steps_pod.go:42-44`) resolves to `path.Join(s.scriptsDir(), helperBinaryName)`. The build container's `Command` is set to `[stepsRunnerBinaryPath(), "steps", "serve", ...]` (`steps_pod.go:314`). Separately, `execStepsProxy` (`executors/kubernetes/steps.go:239-259`) issues a fresh `pods/exec` request against `Container: buildContainerName` with `Command: []string{s.stepsRunnerBinaryPath(), "steps", "proxy", "--socket", socketPath}` — this is a brand-new process launch resolved at exec time, reading whatever bytes currently exist at that path on the shared emptyDir.

Service container image/command/entrypoint are attacker-controlled CI config (`services:` `name`/`entrypoint`/`command` in `.gitlab-ci.yml`), consumed via `s.options.Services` and `getCommandAndArgs` (`executors/kubernetes/kubernetes.go:1653-1668`). `verifyAllowedImages` only restricts which *image* may run as a service via `AllowedServices` (`kubernetes.go:1611-1638`); it does not restrict what that service process can write to a volume it has been mounted into. Since the service container mounts the same `scripts` emptyDir at the same path as the build container, and the mount is writable, an unprivileged job author can configure a service whose command overwrites `s.stepsRunnerBinaryPath()` (e.g. with an arbitrary payload) any time before or during the job's step-runner exec session against the build container.

Existing checks (`verifyAllowedImages`) only gate image identity, not filesystem writes into a shared volume; there is no checksum/integrity verification of the binary at exec time, and no `ReadOnly: true` on the service (or build) container's scripts mount.

### Impact Explanation
If a service container overwrites the binary before `execStepsProxy`'s exec fires (or before the build container's initial `steps serve` command is (re)invoked, e.g., after a container restart/exec retry), the `pods/exec` call executes attacker-supplied code under the identity/namespace of the build container in the job's pod. This escalates a job-controlled service process into arbitrary code execution in the build container's context — i.e., the job author gains control over what `execStepsProxy`/`Command` actually runs, beyond the sandbox boundary intended by the pull-policy/allowed-images checks. This directly violates the stated invariant that helper/runner binaries must not be overwritable via job/service-controlled shared volume mounts.

### Likelihood Explanation
Preconditions: FF_CONCRETE (native steps) enabled and the job declares at least one service. The service's `entrypoint`/`command` are fully job-author-controlled CI config, no special runner configuration or privileged access is required beyond normal permission to define services (which is standard, unprivileged CI author capability). The race is feasible: the service container starts concurrently with the build container and can begin writing to the shared path essentially at pod start, well before the job's step-runner "ready" signal triggers `execStepsProxy`. This is repeatable per-job.

### Recommendation
Mount the `scripts` emptyDir read-only (`ReadOnly: true`) in all service containers (and ideally in the build container after bootstrap completes, if feasible), so only the init container can write the binary. Alternatively, verify a checksum/signature of the file at `stepsRunnerBinaryPath()` immediately before each `execStepsProxy` invocation and before the build container's `steps serve` starts, failing closed on mismatch. Consider isolating the helper binary onto a separate volume that is never mounted into service containers at all, since services have no legitimate need to access `scriptsDir()`.

### Proof of Concept
Go integration test in `executors/kubernetes/steps_pod_test.go`:
1. Build a Concrete pod spec via `stepsBuildContainer()` and `stepsServiceContainer()` for a job with one service.
2. Assert both containers' `VolumeMounts` contain a `scripts` mount at `ex.scriptsDir()` with `ReadOnly` unset/false (`assert.False(t, mount.ReadOnly)`), proving the shared writable mount.
3. In a fake/kind cluster (or with a fake `remotecommand` exec harness), start the service container with a command that overwrites `s.stepsRunnerBinaryPath()` with a marker script, then trigger `execStepsProxy` against the build container and assert the executed process content/output matches the attacker's marker rather than the original helper binary, demonstrating that no checksum/read-only guard exists to reject the tampered binary. // stepsServiceContainer builds a single Concrete service container. It
// mirrors buildContainer(isServiceContainer: true) except that it mounts
// stepsVolumeMounts (no logs emptyDir) instead of getVolumeMounts.
func (s *executor) stepsServiceContainer(
	name string,
	service spec.Image,
	securityContext *api.SecurityContext,
) (api.Container, error) {
	if err := s.verifyAllowedImages(containerBuildOpts{
		name:               name,
		image:              service.Name,
		imageDefinition:    service,
		isServiceContainer: true,
	}); err != nil {
		return api.Container{}, err
	}

	containerPorts := make([]api.ContainerPort, len(service.Ports))
	proxyPorts := make([]proxy.Port, len(service.Ports))
	for i, port := range service.Ports {
		proxyPorts[i] = proxy.Port{Name: port.Name, Number: port.Number, Protocol: port.Protocol}
		containerPorts[i] = api.ContainerPort{ContainerPort: int32(port.Number)}
	}

	if len(proxyPorts) > 0 {
		aliases := service.Aliases()
		if len(aliases) == 0 {
			aliases = []string{fmt.Sprintf("proxy-%s", name)}
		}
		for _, alias := range aliases {
			s.ProxyPool[alias] = s.newProxy(alias, proxyPorts)
		}
	}

	pullPolicy, err := s.pullManager.GetPullPolicyFor(name)
	if err != nil {
		return api.Container{}, err
	}

	command, args := s.getCommandAndArgs(service)

	return api.Container{
		Name:            name,
		Image:           service.Name,
		ImagePullPolicy: pullPolicy,
		Command:         command,
		Args:            args,
		Env:             buildVariables(s.getServiceVariables(service)),
		Resources: api.ResourceRequirements{
			Limits:   s.configurationOverwrites.getServiceResourceLimits(name),
			Requests: s.configurationOverwrites.getServiceResourceRequests(name),
		},
		Ports:           containerPorts,
		VolumeMounts:    s.stepsVolumeMounts(),
		SecurityContext: securityContext,
		Lifecycle:       s.prepareLifecycleHooks(),
		Stdin:           true,
	}, nil
}

// stepsVolumeMounts returns the volume mounts shared by the bootstrap
// init container and the build container in Concrete mode.
func (s *executor) stepsVolumeMounts() []api.VolumeMount {
	mounts := []api.VolumeMount{
		{
			Name:      "scripts",
			MountPath: s.scriptsDir(),
		},
	}

	mounts = append(mounts, s.getVolumeMountsForConfig()...)

	if s.isDefaultBuildsDirVolumeRequired() {
		mounts = append(mounts, api.VolumeMount{
			Name:      "repo",
			MountPath: s.AbstractExecutor.RootDir(),
		})
	}

	if s.isDefaultCacheDirVolumeRequired() {
		mounts = append(mounts, api.VolumeMount{
			Name:      "cache",
			MountPath: s.AbstractExecutor.CacheDir(),
		})
	}

	return mounts
}

func (s *executor) verifyAllowedImages(opts containerBuildOpts) error {
	// check if the image/service is allowed
	internalImages := []string{
		s.ExpandValue(s.Config.Kubernetes.Image),
		s.ExpandValue(s.helperImageInfo.Name),
	}

	var (
		optionName    string
		allowedImages []string
	)
	if opts.isServiceContainer {
		optionName = "services"
		allowedImages = s.Config.Kubernetes.AllowedServices
	} else if opts.name == buildContainerName {
		optionName = "images"
		allowedImages = s.Config.Kubernetes.AllowedImages
	}

	verifyAllowedImageOptions := common.VerifyAllowedImageOptions{
		Image:          opts.image,
		OptionName:     optionName,
		AllowedImages:  allowedImages,
		InternalImages: internalImages,
	}

	return common.VerifyAllowedImage(verifyAllowedImageOptions, s.BuildLogger)
}

func (s *executor) shouldUseStartupProbe() bool {
	honorEntrypoint := s.Build.IsFeatureFlagOn(featureflags.KubernetesHonorEntrypoint)
	legacyExecMode := s.Build.IsFeatureFlagOn(featureflags.UseLegacyKubernetesExecutionStrategy)

	// For attach mode, the system waits until the entrypoint ran and the shell is spawned anyway, regardless if there is
	// something running as part of the entrypoint or not. For legacy exec mode, we don't wait for the entrypoint (we run
	// a separate process as opposed to attaching to the "main" process), thus we need a signal when the entrypoint is
	// done and the shell is spawned. However, when in exec mode and ignoring the image's entrypoint (thus only starting
	// the shell), we don't really have to wait, either.
	// Thus, in summary: We only need a startupProbe if we run in exec mode *and* honor the image's entrypoint.
	return honorEntrypoint && legacyExecMode
}

func (s *executor) getCommandAndArgs(imageDefinition spec.Image, command ...string) (retCommand []string, retArgs []string) {
	if s.Build.IsFeatureFlagOn(featureflags.KubernetesHonorEntrypoint) {
		return []string{}, command
	}

	if len(command) == 0 && len(imageDefinition.Entrypoint) > 0 {
		command = imageDefinition.Entrypoint
	}

	var args []string
	if len(imageDefinition.Command) > 0 {
		args = imageDefinition.Command
	}

	return command, args
}
