### Title
Stale Confirmations From Removed Multisig Members Allow Request Execution Below the Configured Threshold - (File: `multisig2/src/lib.rs`)

### Summary
`MultiSigContract::delete_member` in `multisig2/src/lib.rs` only clears confirmations for requests that were *created* by the removed member. It never scans the `confirmations` map to strip confirmation entries that the removed member previously cast on requests created by *other* members. Those stale confirmations continue to count toward `num_confirmations` in `confirm()`, so a request can later execute with fewer live-member confirmations than the configured threshold — breaking the equality `confirmations counted == confirmations from current live members`.

### Finding Description
`confirm()` checks the threshold purely by set size: [1](#0-0) 

`delete_member()` only removes requests/confirmations where the removed member was the *creator* (`r.member == member`); it does not touch the `confirmations` `LookupMap` entries of other requests where that member had merely confirmed: [2](#0-1) 

Because `confirmations` is a `HashSet<String>` keyed by `member.to_string()` and is never re-validated against the current `self.members` set at confirm-time, a confirmation string from an account/key that has since been removed from `members` remains in the set and is still counted by `confirmations.len() as u32 + 1 >= self.num_confirmations` in `confirm()`.

This breaks the custody/authorization binding the contract is supposed to guarantee: "number of confirmations required to authorize a request" is documented and enforced as confirmations from *current* members, but the code enforces it against *ever-recorded* confirmation strings, including ones belonging to accounts/keys no longer part of the multisig.

### Impact Explanation
This falls under the "Critical" impact category explicitly listed as in-scope: *a multisig request executed below threshold*. Any pending `MultiSigRequest` (e.g. `Transfer` of NEAR, `AddKey` granting a full-access key, `DeployContract`, `AddMember`/`DeleteMember`) can be executed with fewer live-member confirmations than `num_confirmations`, because a stale confirmation from a since-removed member is silently counted. This can lead to unauthorized movement of NEAR held by the multisig account or unauthorized privilege escalation (adding a full access key) with insufficient live authorization.

### Likelihood Explanation
The bug is triggered purely through the contract's own documented API (`add_request`, `confirm`, and the `DeleteMember` action executed via the normal multisig flow) — no foundation privilege, redeploy, or malicious validator is required. Any normal churn in multisig membership (a routine, expected operation) combined with a request that received a confirmation from the departing member before removal is sufficient to leave a stale, still-counted confirmation behind. Membership changes are a standard and expected lifecycle event for this contract, making the precondition easy to hit in practice.

### Recommendation
When removing a member in `delete_member`, iterate over all entries in `self.confirmations` (not just requests created by that member) and remove the departing member's `to_string()` entry from each confirmation set. Alternatively, validate at `confirm()`/threshold-check time that every string in the confirmations set still corresponds to a member currently present in `self.members`, filtering out stale entries before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. Member `A` calls `add_request` to create request `R` (e.g. `Transfer { amount }` to an attacker-controlled account). Confirmations for `R` = `{}`.
3. Member `B` calls `confirm(R)`. Confirmations for `R` = `{B}` (1 < 3, not yet executed).
4. Through a separate, properly-confirmed multisig request, `B` is removed via `MultiSigRequestAction::DeleteMember { member: B }` (executed via `delete_member`, `multisig2/src/lib.rs:356-379`). Because `R` was created by `A`, not `B`, the filter `r.member == member` does not match `R`, so `B`'s stale confirmation entry on `R` is never removed. Live members are now `{A, C, D}`.
5. Member `C` calls `confirm(R)`. Confirmations for `R` = `{B(stale), C}`, size 2, `2 + 1 >= 3` → threshold check passes and `execute_request(R)` runs — even though only `C` (and originally `A`, if counted as an implicit initiator, but per code only explicit `confirm` calls count) is a current, live confirming member besides the stale `B` entry.

Result: `R` (e.g., a NEAR transfer) executes with confirmations effectively backed by only 1 current live member's explicit confirmation (`C`) plus a stale, no-longer-valid confirmation from removed member `B`, instead of the required 3 live confirmations — demonstrating the threshold-bypass.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
