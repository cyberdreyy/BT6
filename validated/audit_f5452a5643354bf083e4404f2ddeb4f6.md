### Title
Loss-adjusted withdraw receipts evade their haircut when a user has pending requests in more than one epoch — `lastWithdrawRequest` only tracks the latest request epoch (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` records only the user's *last* request epoch in `lastWithdrawRequest[_user]`. When a stop-epoch loss is applied to the aggregate `pendingWithdraws` bucket via `collectWithdrawFunds`, the haircut is stored under the *current* `epochNumber` in `lossRecoveryPriceByEpoch`. `_claimLossAdjustedWithdrawRequest` then clears only the entries matching that one epoch (`_clearWithdrawClaimForEpoch`), resets the pointer to 0, and lets `_claimFundedWithdrawRequest` pay every remaining per-epoch receipt at par — even though the borrower only funded `pendingBasis * lossRecoveryPrice`. The result is identical in spirit to the Linux bug: a pointer into per-epoch state is left "reset" to a value that makes older sibling structures reachable again at full value.

### Finding Description
Relevant code:

- `requestWithdraw` overwrites the pointer without aggregating older pending epochs: `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) 
- The guard that forces claiming a loss-adjusted receipt only inspects `lastWithdrawRequest`, so receipts in earlier epochs are invisible to it [2](#0-1) 
- `collectWithdrawFunds` funds `pendingBasis * lossRecoveryPrice` for the *whole* aggregate pending bucket, but records the haircut under a single epoch key [3](#0-2) 
- `claimWithdrawRequest` pays the loss-adjusted slice for `lastWithdrawRequest` only, then falls through to `_claimFundedWithdrawRequest`, which pays the rest of `withdrawsRequests[_user]` at par [4](#0-3) 
- `_clearWithdrawClaimForEpoch` zeroes only `withdrawsRequestsByEpoch[_user][_claimEpoch]` and then clears `lastWithdrawRequest` to 0, so the earlier-epoch remainder is treated as an already-funded receipt [5](#0-4) 
- `_claimFundedWithdrawRequest` gate `epochNumber <= lastWithdrawRequest[_user]` passes trivially once the pointer is reset to 0 [6](#0-5) 

Concrete sequence (normal fixed-APR mode, unprivileged lender):

1. Epoch N buffer: attacker calls `requestWithdraw` for amount A. `withdrawsRequestsByEpoch[attacker][N] = A`, `lastWithdrawRequest = N`, `pendingWithdraws += A`.
2. Epoch N+1 running, then stop — attacker intentionally does not claim. Epoch N+1 buffer: attacker calls `requestWithdraw` again for amount B (allowed because `lossRecoveryPriceByEpoch[N] == 0`). Now `withdrawsRequestsByEpoch` has entries in N and N+1, `lastWithdrawRequest = N+1`, `pendingWithdraws = A + B`.
3. Epoch N+2 runs; borrower repays short and manager calls `stopEpochWithDuration`/`stopEpoch` with `_lossAmount` such that `pendingToFund < A + B`. `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[N+2]` — wait, keyed by `epochNumber` at collection time, which is the epoch that just ended (N+2), while `lastWithdrawRequest` is N+1. The haircut price is looked up via `lossRecoveryPriceByEpoch[lastWithdrawRequest]` = `lossRecoveryPriceByEpoch[N+1]` = 0... unless the loss epoch key equals the request epoch.

Re-checking the keying: `collectWithdrawFunds` writes `lossRecoveryPriceByEpoch[epochNumber]`, and `epochNumber` is only incremented inside `deposit()` during the same stop. `requestWithdraw` stores `currentEpoch = epochNumber` *before* increment, so a request made in the buffer before stop of epoch E is recorded with `epochNumber == E`, and the loss write at that stop is also keyed `E`. So the haircut lookup correctly matches the *latest* request — but any earlier pending epochs (step 2's epoch-N receipt, still unclaimed because it was stacked) share the same aggregate `pendingWithdraws` haircut yet are keyed under epoch E only through the single pointer.

Revised sequence: attacker stacks requests at epochNumbers E and E (same epoch via two `requestWithdraw` calls is fine — same key) — that doesn't create the bug. The divergence needs two different request epochs: request at E−1 (claimable after stop E−1), skip claiming, request again at E. At stop of E with a loss, `lossRecoveryPriceByEpoch[E]` is set and applied to `pendingWithdraws = A + B`. On claim: `_clearWithdrawClaimForEpoch(user, E)` clears only `withdrawsRequestsByEpoch[user][E] = B`, pays `B * lossRecoveryPrice`; `lastWithdrawRequest` resets to 0; `_claimFundedWithdrawRequest` then pays the remaining `withdrawsRequests[user] = A` at **par**. The borrower funded only `(A+B) * price`, so A's haircut portion is stolen from the funded pool.

### Impact Explanation
The attacker recovers `A + B*price` instead of `(A+B)*price` — stealing `A * (1 - price)` of underlying that was reserved for other pending-receipt holders (or, after default finalization, from the isolated `defaultRecoveryReserve`, since `_transferFundedClaim` only guards `balance - reserve >= amount` and the reserve itself was sized assuming the aggregate haircut). With a 50% loss and A = 1,000,000 units, the attacker over-claims 500,000 units, leaving later claimants with an insolvent pool — direct theft plus permanent loss for honest withdrawers.

### Likelihood Explanation
- Requires only an unprivileged tranche holder making ordinary `requestWithdraw` calls across two buffer periods and waiting for a partial-loss stopEpoch (`stopEpochWithDuration(_lossAmount)` is an expected protocol operation for realized losses).
- Nothing blocks stacking requests across epochs; the comments in `_claimFundedWithdrawRequest` explicitly document that requesting again merges both requests into one claim.
- The only mitigating guard (`requestWithdraw` lines 263–271) inspects `lastWithdrawRequest` alone, so it cannot see the epoch-E−1 receipt once a second request overwrites the pointer.

### Recommendation
Track per-epoch pending receipts rather than a single pointer: either (a) iterate/zero all `withdrawsRequestsByEpoch` entries contributing to `withdrawsRequests` when applying a loss-adjusted claim, or (b) refuse new `requestWithdraw`s while `withdrawsRequests[_user] != 0` (not only when a loss price exists for `lastWithdrawRequest`), or (c) store an explicit per-epoch claim basis so `_claimLossAdjustedWithdrawRequest` sums every epoch whose receipts were pending at the haircut. At minimum, keep a `firstUnclaimedRequestEpoch` or bitmap so resetting `lastWithdrawRequest` to 0 cannot orphan earlier receipts into the funded-claim path.

### Proof of Concept
Foundry fork PoC sketch against `IdleCDOEpochVariant` + `IdleCreditVault`:

```solidity
// setup: attacker deposits AA, epoch machinery running with manager/borrower honest

// 1) epoch K buffer
cdoEpoch.requestWithdraw(0, address(AAtranche));        // receipt A at epochNumber K
startEpoch(); warp(end); stopEpoch(apr, 0);             // epoch K ends, receipt A claimable

// 2) epoch K+1 buffer — attacker does NOT claim, stacks a second request
cdoEpoch.requestWithdraw(0, address(AAtranche));        // receipt B at epochNumber K+1
startEpoch();

// 3) borrower repays short → manager stops with loss covering pendingWithdraws
uint256 pending = creditVault.pendingWithdraws();       // == A + B
uint256 loss = pending / 2;                              // 50% haircut on pending bucket
deal(underlying, borrower, owed - loss);
stopEpochWithDuration(newApr, loss);                     // sets lossRecoveryPriceByEpoch[K+1] ≈ 0.5e18

// 4) attacker claims once
cdoEpoch.claimWithdrawRequest();
// _claimLossAdjustedWithdrawRequest pays B * 0.5
// _claimFundedWithdrawRequest then pays A * 1.0
// assert received == A + B/2  >  (A + B) / 2  → over-claim of A/2
```

Assert `underlying.balanceOf(attacker) == A + B/2` while the vault only received `(A+B)/2` for the whole pending bucket; subsequent honest claimants' `_transferFundedClaim` calls revert on insufficient balance or drain the default recovery reserve.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;
    }
    if (_amount != 0) {
      underlyingToken.safeTransferFrom(idleCDO, address(this), _amount);
    }
  }

  function _clearWithdrawClaimForEpoch(address _user, uint256 _claimEpoch, bool _isClearingApr0) internal returns (uint256 claimBasis, uint256 burnAmount) {
    (claimBasis, burnAmount) = _withdrawClaimAmountsForEpoch(_user, _claimEpoch);
    if (claimBasis == 0) return (claimBasis, burnAmount);

    uint256 normalAmount = withdrawsRequestsByEpoch[_user][_claimEpoch];
    if (normalAmount != 0) {
      withdrawsRequestsByEpoch[_user][_claimEpoch] = 0;
      // The aggregate may also include older funded receipts; clear only this epoch's piece.
      withdrawsRequests[_user] -= normalAmount;
    }
    Apr0UserData storage apr0User = apr0Users[_user];
    if (apr0User.principal != 0 && apr0User.principalEpoch == _claimEpoch) {
      if (_isClearingApr0) {
        uint256 apr0Principal = apr0User.principal;
        uint256 totalApr0Principal = apr0TotalPrincipal;
        // prepareStopEpochWithApr0 may already close the global APR0 bucket before default finalization.
        apr0TotalPrincipal = apr0Principal >= totalApr0Principal ? 0 : totalApr0Principal - apr0Principal;
      }
      apr0User.principal = 0;
      apr0User.principalEpoch = 0;
    }
    if (lastWithdrawRequest[_user] == _claimEpoch) {
      // The cleared epoch was the latest request marker. Any remaining normal/APR0 receipt
      // is older and already funded, so it can continue to the funded-claim path.
      lastWithdrawRequest[_user] = 0;
    }
  }
