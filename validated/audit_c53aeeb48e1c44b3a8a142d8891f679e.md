Based on my analysis of the report's root-cause pattern — a per-message-hash reentrancy lock (keyed on parameters like nonce/value/minGasLimit that can be varied while `target`/`message` stay constant) combined with post-external-call effects updates, allowing the same effective action to be replayed by crafting two different hashes — I checked for an analog in `ProvisionerV2`'s async request-hash system, which is the closest conceptual match (hash-keyed replay protection for deposit/redeem/solve flows).

Findings:
- All solve/refund/cancel functions that perform external interactions (`_solveDepositVaultFixedPrice`, `_solveRedeemVaultFixedPrice`, `_solveRequestDirect`, `refundDeposit`, `refundRequest`, `cancelRequest`) unset the `asyncRequestHashes`/`syncDepositHashes` entry (the Effect) **before** the external interaction (vault `enter`/`exit`, token transfers), correctly following checks-effects-interactions, unlike the CrossDomainMessenger's success/failure state which is set only after the external call. [1](#0-0) [2](#0-1) [3](#0-2) 
- The externally reachable functions that perform interactions (`deposit`, `mint`, `solveRequestsVault`, `solveRequestsDirect`, `refundRequest`, `cancelRequest`) all carry the transient `nonReentrant` modifier, which is a **global** reentrancy lock rather than a per-hash lock like CrossDomainMessenger's `reentrancyLocks[versionedHash]`. A global lock cannot be bypassed by varying a non-critical parameter to produce a different hash, which is exactly the bypass technique described in the report. [4](#0-3)
