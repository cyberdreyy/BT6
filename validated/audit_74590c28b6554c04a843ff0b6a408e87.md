### Title
Builder pending withdrawals commit an execution-layer payment larger than the CL balance actually debited - ([File: specs/gloas/beacon-chain.md])

### Summary
`get_builder_withdrawals` in the Gloas fork builds a `Withdrawal` entry using the raw, requested `withdrawal.amount` from `state.builder_pending_withdrawals`, without capping it to the builder's actual balance. That `Withdrawal` is placed into `state.payload_expected_withdrawals`, which the execution layer is required to honor as an actual payment. Meanwhile `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from the builder's CL-side balance. When a requested amount exceeds the builder's balance, the block commits to a payout larger than what is actually removed from the builder's stake — Gwei is created and paid to the `fee_recipient` without backing.

### Finding Description
`get_builder_withdrawals` iterates `state.builder_pending_withdrawals` and appends:
```python
Withdrawal(
    index=withdrawal_index,
    validator_index=convert_builder_index_to_validator_index(builder_index),
    address=withdrawal.fee_recipient,
    amount=withdrawal.amount,
)
``` [1](#0-0) 

There is no check against `state.builders[builder_index].balance` here — unlike the sibling function for partial validator withdrawals, which explicitly caps the amount at creation time: `withdrawal_amount = min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)` [2](#0-1) , and unlike the builder-sweep function, which withdraws exactly `builder.balance` (so no mismatch is possible) [3](#0-2) .

The mismatch only shows up later, in `apply_withdrawals`, which caps the *balance decrease* but not the *committed amount*:
```python
if is_builder_index(withdrawal.validator_index):
    builder_index = convert_validator_index_to_builder_index(withdrawal.validator_index)
    builder_balance = state.builders[builder_index].balance
    state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [4](#0-3) 

The `Withdrawal` object (with the uncapped `amount`) is what ends up in `state.payload_expected_withdrawals`, and per the spec's own note, "any execution payload that has the corresponding block as parent beacon block is required to honor these withdrawals in the execution layer" [5](#0-4) . So the execution layer is committed to crediting `fee_recipient` the full requested amount, while the consensus layer only ever debited `min(requested, balance)` from the builder. If `requested > balance`, the difference is Gwei that is paid out on the EL side but never removed from any CL account — created from nothing.

This is confirmed by the repo's own test, which documents the exact behavior:
```
Output State Verified:
    - withdrawal.amount: 5 ETH (requested amount)
    - builders[0].balance: 0 (deduction capped to available balance)
```
with `withdrawal_amount = 5 ETH` and `available_balance = 1 ETH` [6](#0-5) . The assertion helper explicitly checks that only the capped amount is removed from `builder.balance`, while `withdrawal_amounts_builders` records the full, uncapped requested amount as the committed withdrawal [7](#0-6) .

This is directly analogous to the reported Solidity bug class ("emits wrong data" — the recorded amount doesn't match what was actually deducted) but with a materially worse consequence here: the mismatched value is not just a log/event, it is the actual field the execution layer uses to mint/transfer ETH.

### Impact Explanation
This breaks the core equality that any Gwei paid out to an external address must be backed by an equal Gwei decrease somewhere in the beacon state. A builder (or anyone able to get an oversized entry into `state.builder_pending_withdrawals`, e.g. by requesting more than their current balance, or by balance being depleted by prior withdrawals/other mechanisms between request and processing) can cause the execution layer to mint/pay out more Gwei to `fee_recipient` than was ever debited from the builder's CL balance. This is Critical-severity under the stated impact criteria: "Gwei created ... paid to a non-owner" / "a payload executed or paid that the block did not commit to [correctly]," since the CL/EL supply invariant is violated.

### Likelihood Explanation
The path is reachable purely through the spec's own defined transition functions (`get_builder_withdrawals` → `get_expected_withdrawals` → `process_withdrawals` → `apply_withdrawals`), requiring no client bug, malicious peer, or coalition — only a builder pending-withdrawal entry whose requested `amount` exceeds the builder's balance at processing time. The test suite itself demonstrates this exact scenario, confirming it is a reachable, spec-following state transition rather than a theoretical edge case.

### Recommendation
Cap the amount placed into the `Withdrawal` object in `get_builder_withdrawals` to the builder's actual (available) balance, consistent with how `get_pending_partial_withdrawals` and `get_builders_sweep_withdrawals` already do it, e.g.:
```python
amount=min(withdrawal.amount, builder.balance)
```
and remove or align the redundant `min()` clamp in `apply_withdrawals` so the committed `Withdrawal.amount` and the CL balance deduction always agree.

### Proof of Concept
Using the repo's existing test as the concrete scenario:
1. Set `state.builders[0].balance = 1 ETH`.
2. Enqueue `BuilderPendingWithdrawal(builder_index=0, amount=5 ETH, fee_recipient=addr)` into `state.builder_pending_withdrawals`.
3. Run `process_withdrawals(state)`.
4. Result: `state.payload_expected_withdrawals` contains a `Withdrawal` with `amount = 5 ETH` to `addr` (the amount the execution layer is bound to honor), while `state.builders[0].balance` is only decreased to `0` (i.e., only 1 ETH was actually removed). The 4 ETH difference is paid out with no backing balance decrease anywhere in state. [8](#0-7)
