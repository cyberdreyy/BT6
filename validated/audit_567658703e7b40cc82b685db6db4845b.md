### Title
Missing tenant/ownership authorization on DKG result export allows cross-workflow secret disclosure - ([File: core/web/vault_controller.go])

### Finding Description
`VaultController.ExportDKGResult` accepts an arbitrary, caller-supplied `instanceId` string and uses it directly to look up and return the raw DKG result package: `orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))` [1](#0-0) . If found, it hex-encodes the full `ReportWithResultPackage` and returns it verbatim to the caller, along with its SHA-256 digest [2](#0-1) .

Nowhere in this handler (or in `VerifyDKGResult`, which shares the same lookup pattern) is there any check binding the requesting caller/session to the subscriber, workflow, or DON that owns the given `instanceId`. The only gate on `instanceId` is a non-empty string check [3](#0-2) . Any caller who can reach this route with a valid instance ID — including one belonging to a different tenant/workflow — receives the complete raw result package (which is meant to hold decryptable DKG-derived key-share material, per its use in `VerifyDKGResult`/`vaultcap.VerifyDKGResult`). This is a classic missing object-level authorization (IDOR-style) flaw: authentication may be enforced by the router group, but per-resource authorization is entirely absent at the handler level, so the sensitivity of the endpoint is reduced to "does the attacker know or can guess/enumerate the instanceId string."

I was unable to confirm from the router registration in this session exactly which role tier (admin-only vs. any-authenticated/run-role) gates `/v2/vault/dkg_results/export` — that portion of `core/web/router.go` was not fully retrieved before the session ended, so the exact minimum privilege required to reach the handler is unverified. Regardless of what session/token role is required to reach the endpoint, once reached, the handler itself performs no ownership check for the `instanceId`, so any caller (across tenants) with API access to this route can pull another subscriber's DKG result package.

### Impact Explanation
This corresponds to a credential/key-material exposure impact: the DKG `ReportWithResultPackage` contains cryptographic material tied to a DKG instance's participants and, per the sibling `VerifyDKGResult` flow, is used together with a node's DKG recipient key to derive decryptable shares. Leaking it to an unauthorized caller who owns a different workflow/subscriber breaks the confidentiality guarantee of the Vault DKG result store and could aid decryption/verification attacks against other tenants' DKG outputs, constituting cross-user secret disclosure.

### Likelihood Explanation
Exploitability requires only knowledge (or successful guessing/enumeration) of a valid `instanceId` string belonging to another tenant, plus whatever minimal API access is needed to reach `/v2/vault/dkg_results/export`. There is no cryptographic barrier or ownership check in the handler; the request is a single trivial POST with a JSON body. If the route is reachable by any authenticated/run-role token (not restricted to admin), the likelihood is high and fully repeatable, since the same instanceId can be exported repeatedly by any tenant.

### Recommendation
Add an ownership/authorization check in `ExportDKGResult` (and `VerifyDKGResult`) that verifies the requesting caller/session is authorized for the specific `instanceId`'s owning subscriber/workflow before returning the result package — e.g., look up the DKG instance's owning entity and compare against the authenticated principal, or restrict the endpoint to an admin-only role if cross-tenant export is never intended for regular API tokens. Additionally, confirm via `core/web/router.go` that this route is not exposed to run/view-role tokens if such lower-privilege exposure is unintended.

### Proof of Concept
1. In `core/web/vault_controller_test.go`, extend `setupVaultControllerTests` to create two simulated tenants/instance IDs (e.g., `"tenant-a-instance"` and `"tenant-b-instance"`), each written via `orm.WriteResultPackage` with distinct `ReportWithResultPackage` bytes.
2. Build an HTTP client using `cltest.HTTPClientCleaner` configured with a run-role (non-admin) session/API token instead of the default admin session used in existing tests (mirror how other tests in the package construct restricted-role clients, if such a helper exists, e.g., via `app.NewHTTPClient` with a non-admin user role).
3. POST to `/v2/vault/dkg_results/export` with `{"instanceId": "tenant-b-instance"}` using the run-role client that is only supposed to be associated with tenant A.
4. Assert: currently the response returns `http.StatusOK` with the hex-encoded `ReportWithResultPackage` for `tenant-b-instance` — this should instead return `http.StatusForbidden`/`http.StatusNotFound` because the caller has no association with that instance.
5. Expected fix outcome: the handler should reject or scope the lookup so only the owning tenant's client can retrieve a given `instanceId`'s result package.
