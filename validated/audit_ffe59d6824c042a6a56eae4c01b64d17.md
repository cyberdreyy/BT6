### Title
Instant-withdraw claims are paid from the shared strategy balance without checking that the borrower actually funded the instant bucket, letting an instant receipt drain underlyings collected for matured normal withdraw receipts - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2017-8061 is a boundary bug: a DMA scatterlist was assumed to live inside one virtual page, but the buffer straddled a page boundary and the DMA engine wrote into memory owned by a different domain. The credit-vault analog is an *accounting-boundary* violation in `IdleCreditVault`: instant-withdraw receipts and normal (epoch-matured) withdraw receipts are two logically isolated buckets, but `claimInstantWithdrawRequest` pays the receipt straight out of the contract's raw underlying balance via `_transferFundedClaim`, without verifying that the instant bucket was ever funded (`pendingInstantWithdraws` is only decremented in `collectInstantWithdrawFunds`, never consulted or decremented on the claim path). The only isolation guard protects `defaultRecoveryReserve`, not the funded normal-receipt pool. An unprivileged KYC'd lender can therefore cross the bucket boundary and spend underlyings that were collected at `stopEpoch` to back other users' matured normal withdraw receipts.

### Finding Description
In `requestWithdraw` on the CDO side (`IdleCDOEpochVariant.sol:761-768`), when `lastEpochApr > unscaledApr + instantWithdrawAprDelta`, the tranche burn happens immediately and `IdleCreditVault.requestInstantWithdraw` mints the user a strategy-token receipt and increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). The backing underlyings for that receipt only arrive later, when the borrower sends liquidity at the next `startEpoch` and the CDO calls `collectInstantWithdrawFunds`, which does `pendingInstantWithdraws -= _amount` and pulls tokens in (`IdleCreditVault.sol:398-403`).

The claim path, however, enforces no such funding boundary:

```
function claimInstantWithdrawRequest(address _user) external {
  _onlyIdleCDO();
  ...
  uint256 amount = instantWithdrawsRequests[_user];
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;
  _transferFundedClaim(_user, amount);   // pays from raw balance
}
```

`_transferFundedClaim` (`IdleCreditVault.sol:897-907`) only reverts if the transfer would dip into `defaultRecoveryReserve`; funds held for matured `withdrawsRequests`/`withdrawsRequestsByEpoch` receipts collected through `collectWithdrawFunds` are not ring-fenced. So between `stopEpoch` N (which funds normal receipts into the strategy) and `startEpoch` N+1 (which funds instant receipts), an attacker who requested an instant withdraw in the buffer can claim against a strategy balance that consists entirely of other users' funded normal receipts — exactly the "scatterlist spanning more than one page" pattern: one logical transfer consuming memory (here, underlying) belonging to a different accounting domain.

No guard stops this: `claimInstantWithdrawRequest` in the CDO (`IdleCDOEpochVariant.sol:975-979`) only checks `allowInstantWithdraw`; there is no `epochNumber`/epoch-wait gate like `_claimFundedWithdrawRequest` has, and no per-bucket balance check.

### Impact Explanation
Direct theft / permanent freezing: the instant claimer receives underlyings earmarked for matured normal withdraw receipts. When the honest receipt holders later call `claimWithdrawRequest`, `_transferFundedClaim` reverts on insufficient balance (or pays them from subsequently collected instant funds only if the borrower keeps over-funding). If the borrower funded exactly `pendingWithdraws` at `stopEpoch` — the honest assumption — the stolen amount equals the attacker's instant receipt, and honest claimants are left permanently under-funded unless governance rescues them. Loss is bounded by the attacker's deposit size but requires no privileged action.

### Likelihood Explanation
Requirements: (a) instant withdrawals enabled (`allowInstantWithdraw`, `!disableInstantWithdraw`, non-programmable borrower), (b) an APR decrease exceeding `instantWithdrawAprDelta` so the instant path triggers inside `requestWithdraw`, (c) existing matured normal receipts already funded in the strategy, and (d) the attacker claims before `collectInstantWithdrawFunds` runs at the next `startEpoch` (or whenever the strategy holds other-bucket funds while `pendingInstantWithdraws` is nonzero). All attacker steps are ordinary user calls available to any `isWalletAllowed` lender; sequencing only relies on honest manager/borrower timing.

### Recommendation
Enforce the bucket boundary on the claim path: track funded instant liquidity separately (e.g., a `fundedInstantWithdraws` counter incremented in `collectInstantWithdrawFunds`), and cap the payable amount in `claimInstantWithdrawRequest` at that counter, decrementing it on claim — mirroring how `collectWithdrawFunds`/`lossRecoveryPriceByEpoch` fence normal receipts and how `_transferFundedClaim` fences `defaultRecoveryReserve`. Equivalently, in `IdleCDOEpochVariant.claimInstantWithdrawRequest`, gate claims until after the epoch-start funding call for the request's epoch.
