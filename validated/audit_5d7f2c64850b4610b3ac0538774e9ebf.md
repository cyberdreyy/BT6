### Title
Miner's per-block signer weight tally double-counts a signer that rejects then accepts, letting a stale rejection persist in `total_weight_rejected` after the signer's real vote flips to acceptance - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener` tallies signer weight for a proposed block into two mutually-exclusive counters, `total_weight_approved` and `total_weight_rejected`, which `SigningCoordinator` (`signer_coordinator.rs`) treats as an equality: reaching 70% of one implies the other cannot also be true. The `Rejected` handler gates its weight increment on `responded_signers.insert(slot_id)` [1](#0-0) , but the `Accepted` handler gates its own increment only on `!gathered_signatures.contains_key(&slot_id)`, never checking whether that signer already contributed to `total_weight_rejected` [2](#0-1) . A signer that first broadcasts a `Rejected` response and later broadcasts an `Accepted` response for the same block (overwriting their own StackerDB slot) has its weight counted in *both* tallies, because nothing ever removes or corrects the stale rejection weight once the signer's real vote flips.

### Finding Description
`BlockStatus` (`stackerdb_listener.rs`) holds `responded_signers`, `gathered_signatures`, `total_weight_approved`, and `total_weight_rejected` [3](#0-2) .

- On `BlockResponse::Accepted`: weight is added to `total_weight_approved` if the slot isn't already in `gathered_signatures`; `responded_signers` is inserted unconditionally afterward [2](#0-1) .
- On `BlockResponse::Rejected`: weight is added to `total_weight_rejected` *only if* `responded_signers.insert(slot_id)` returns `true` (i.e., this is the first response ever recorded for that slot) [1](#0-0) .

This asymmetry means:
- Accept → Reject: blocked correctly, because `responded_signers` already contains the slot from the Accept branch, so the Reject branch's `insert` returns `false` and no reject weight is added.
- Reject → Accept: **not** blocked. The Reject branch already inserted the slot into `responded_signers` and added the signer's weight to `total_weight_rejected`. When the same signer later sends `Accepted`, the Accept branch only checks `gathered_signatures` (still empty for that slot), so it adds the same signer's weight to `total_weight_approved` as well — the weight now lives in both tallies simultaneously, with no mechanism to retract the earlier `total_weight_rejected` contribution.

`SigningCoordinator::run` in `signer_coordinator.rs` consumes these two counters as if they were mutually exclusive views of the same fixed pool of signer weight: it checks the reject condition first (`total_weight_rejected + weight_threshold > total_weight`) and, if not true, checks the accept condition (`total_weight_approved >= weight_threshold`) [4](#0-3) . Because a flipped signer's weight is never subtracted from `total_weight_rejected`, that counter can hold weight belonging to a signer whose *current* vote is actually acceptance, inflating the apparent rejecting weight beyond what any signer currently intends. The same stale-weight problem also affects the per-txid `failed_txids` weight tracking, which is only ever incremented in the `Rejected` branch and is never corrected when the reporting signer later accepts [5](#0-4) .

### Impact Explanation
This is a direct analog of the reported bug class: a value ("this signer's current weight/vote") is excluded from a correction it should undergo (removing/retracting the stale rejection) when a superseding message (the acceptance) arrives, so a downstream equality check (`rejected weight vs. blocking-minority threshold`) is evaluated against a stale, uncorrected figure. The practical consequence is a liveness wedge: a block that a real supermajority currently wants to sign can be driven into the `SignersRejected` branch using weight from a signer that has already switched to acceptance, and/or transactions can be excluded via `failed_txids` on the strength of a rejection the reporting signer no longer holds. This matches the "wedge the state machine"/liveness category in scope, since it can prevent the miner-side coordinator from ever accepting a legitimately-supported block or transaction set.

### Likelihood Explanation
Triggering it only requires one signer (or a small colluding set near the blocking-minority weight) to publish a `Rejected` response for a block and then overwrite their own StackerDB slot with an `Accepted` response for the same block — an operation any single signer's own client can perform unilaterally, with no majority or other signer's key required. This is well within a "one-slot" actor's capability, matching the scope constraint that the analog must be triggerable by a single miner/signer plus normal gossip.

### Recommendation
Make the two tallies mutually exclusive based on the signer's *latest* response rather than accumulating independently:
- Before adding weight in the `Accepted` branch, check if the slot is already present in a rejection-tracking set (or `responded_signers` combined with a "last response kind" map) and, if so, subtract the previously-added weight from `total_weight_rejected` (and from any `failed_txids` entries the signer had reported) before adding it to `total_weight_approved`.
- Symmetrically, do this for the already-guarded `Accepted → Rejected` case so any future refactor doesn't reintroduce the same asymmetry.
- Alternatively, track a single `HashMap<slot_id, ResponseKind>` per block and recompute `total_weight_approved`/`total_weight_rejected` from that map on each update, eliminating the possibility of a slot's weight existing in both tallies at once.

### Proof of Concept
1. Miner proposes block `B`; `StackerDBListener` creates a fresh `BlockStatus` for `B`.
2. Signer `S` (weight `w`) sends `BlockResponse::Rejected` for `B`. The listener records `responded_signers.insert(S.slot) == true`, so `total_weight_rejected += w` (`stackerdb_listener.rs` lines 515-518).
3. Signer `S` changes its vote and sends `BlockResponse::Accepted` for the same `B` (overwriting its own slot in StackerDB with a higher version). The listener checks only `!gathered_signatures.contains_key(S.slot)` (true), so `total_weight_approved += w` (`stackerdb_listener.rs` lines 443-465). `S`'s weight `w` is now present in both `total_weight_approved` and `total_weight_rejected`.
4. If enough such flips occur so that `total_weight_rejected + weight_threshold > total_weight` in `SigningCoordinator::run` (`signer_coordinator.rs` lines 509-522), the coordinator treats the block as `SignersRejected` and starts excluding transactions via `failed_txids`, even though the actual, current votes of the flipped signers were acceptances.
