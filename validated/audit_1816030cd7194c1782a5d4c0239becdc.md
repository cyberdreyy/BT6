### Title
Performance fee and APR-split changes are applied retroactively to unaccrued yield — `setFeeParams` checkpoints only the management fee, not the pending gain — ([File: contracts/IdleCDOCreditVault.sol](contracts/IdleCDOCreditVault.sol))

### Summary
The external issue (Angle `SavingsVest`) is a parameter-change-without-accrual bug: yield-state variables are not checkpointed when fee/vesting parameters change, so already-accrued yield is recomputed under the new parameters. The closest analog exists in `IdleCDOCreditVault.setFeeParams` (and `IdleCDO.setFeeParams` / `setTrancheAPRSplitRatio`): the performance `fee` and `trancheAPRSplitRatio` are applied inside `_updateAccounting` to the *entire* NAV gain accrued since the last accounting call, but the setters do not force an accounting checkpoint first. `setFeeParams` calls `_accrueManagementFee()` — a partial mitigation for the management fee only, mirroring the "incomplete fix" pattern of the original report — while leaving the performance fee and split ratio applied retroactively.

### Finding Description
In `IdleCDOCreditVault._updateAccounting`, pending gain is taxed and split using the *current* storage values:

```solidity
if (nav > _lastNAV) {
  unclaimedFees += (nav - _lastNAV) * fee / FULL_ALLOC;   // L230-231
}
... _virtualPriceAux(..., _aprSplitRatio);                // L233-234, uses current trancheAPRSplitRatio
```

`_virtualPriceAux` likewise applies the current `fee` to the whole `totalGain` since the last update (`totalGain -= totalGain * fee / FULL_ALLOC`, L312-313) and splits the remainder with the current `trancheAPRSplitRatio` (L326).

`setFeeParams` (L461-470) checkpoints only the management-fee accrual via `_accrueManagementFee()` and then overwrites `fee`, `feeSplit`, and `managementFee`. It does **not** call `_updateAccounting()`/`_forceUpdateAccounting()` first, so:

- `fee` (performance fee): on the next deposit/withdraw/`stopEpoch`, all gain accrued since the last accounting — potentially an entire epoch of interest — is charged at the **new** fee rate, not the rate in force while it accrued. In `IdleCDO.sol` the same problem exists with no mitigation at all: `setFeeParams` (L860-864) and `setTrancheAPRSplitRatio` (L900-903) do not even accrue the management fee.
- `trancheAPRSplitRatio`: all accrued-but-unsplit gain is divided between AA and BB at the **new** ratio, transferring yield already earned by one tranche class to the other. `setMinAprSplitAYS` and AYS-driven `_updateSplitRatio` changes inside `_withdrawOps` (L381, L386-400) have the same retroactive effect on pending gain, since `_updateAccounting` is invoked *after* the burn/`_updateSplitRatio` ordering only on deposits (on withdraws the new ratio is set before the next accounting touches the gain).

No guard prevents this: `skipDefaultCheck`, `Default` revert, pause flags, and the skim/`_skimDonatedAssets` logic are all orthogonal; there is no checkpoint of `lastNAVAA`/`lastNAVBB`/`unclaimedFees` in any of these setters.

### Impact Explanation
Direct transfer of unclaimed yield between users and `feeReceiver`, or between AA and BB tranche holders:

- **Fee increase:** with e.g. 1 epoch of accrued interest `G` pending, raising `fee` from `f0` to `f1` causes `unclaimedFees += G * f1 / FULL_ALLOC` instead of `G * f0 / FULL_ALLOC`, so tranche holders lose `G * (f1 - f0) / FULL_ALLOC` of yield they accrued under the old rate. With `MAX_FEE` up to 20% (`_fee > MAX_FEE` check) and a full-epoch `G`, the loss is material.
- **Split-ratio change:** raising `trancheAPRSplitRatio` retroactively gives AA holders a larger share of `G` that was accrued under the old ratio; BB holders lose `G * (1 - fee) * (r1 - r0) / FULL_ALLOC` (symmetric for the opposite direction). A BB holder depositing just before an honest ratio change loses yield with no recourse.

### Likelihood Explanation
Requires only an honest owner calling `setFeeParams` / `setTrancheAPRSplitRatio` — a routine governance action explicitly provided for. The trigger is not exotic: any parameter change made while `nav > lastNAVAA + lastNAVBB` (i.e., essentially always mid-epoch in fixed-APR mode, since accounting only runs on user interactions or `stopEpoch`) produces the misallocation. The bug is deterministic once triggered; likelihood is moderate (admin action needed) with quantifiable, non-speculative loss — consistent with the Medium severity of the source finding.

### Recommendation
Force a full accounting checkpoint before overwriting yield-affecting parameters:

- In `IdleCDOCreditVault.setFeeParams` and `IdleCDO.setFeeParams`, call `_forceUpdateAccounting()` (which internally runs `_accrueManagementFee` plus the NAV/fee split) before assigning `fee`, `feeSplit`, and `managementFee`. Currently only the management-fee leg is checkpointed, so the performance fee on pending gain is still misapplied — the same "incomplete mitigation" shape as the Angle fix.
- In `setTrancheAPRSplitRatio` (and `setMinAprSplitAYS` when AYS is active), call `_forceUpdateAccounting()` before writing the new ratio so pending gain is split at the old ratio.
- Alternatively document and enforce via `minAprSplitAYS` bounds that ratio changes only occur when `getContractValue() == lastNAVAA + lastNAVBB`.

### Proof of Concept
Foundry fork sketch (credit-vault variant):

```solidity
// setup: depositAA(100_000e6), depositBB(20_000e6), startEpoch with fixed APR,
// fee = 0, trancheAPRSplitRatio = r0
vm.warp(epochEnd);
deal(underlying, borrower, expectedInterest); // borrower repays principal+interest

uint256 navPre = cdo.getContractValue();
uint256 lastNAV = cdo.lastNAVAA() + cdo.lastNAVBB();
uint256 pendingGain = navPre - lastNAV;
assertGt(pendingGain, 0);

// honest owner raises fee from 0 to MAX_FEE before stopEpoch/accounting
vm.prank(owner);
cdo.setFeeParams(feeReceiver, MAX_FEE, feeSplit, mgmtFee);

// next interaction applies MAX_FEE to the WHOLE pendingGain
vm.prank(manager);
cdo.stopEpoch(newApr, 0);

assertEq(cdo.unclaimedFees(), pendingGain * MAX_FEE / FULL_ALLOC);
// holders lose pendingGain * MAX_FEE / FULL_ALLOC vs the 0-fee terms they accrued under
```

Same pattern for `setTrancheAPRSplitRatio`: warp mid-epoch, call `cdo.setTrancheAPRSplitRatio(r1)`, then any `depositAA` triggers `_updateAccounting`, splitting the entire pre-change gain at `r1`; assert `virtualPrice(BB)` drops relative to the same gain split at `r0`.

**Caveat:** I could not fully verify the `deposit`/`withdraw` ordering for `_updateSplitRatio` in AYS mode (whether accounting precedes the ratio write on every path) within the available iterations; the `setFeeParams`/`setTrancheAPRSplitRatio` retroactivity itself is confirmed by the code shown.
