### Title
Loss-adjusted withdraw receipt is re-released at par when the user queues a second withdrawal - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The kernel bug releases the same node twice because a `continue` path drops the reference and the normal exit path drops it again. The vault analog is `claimWithdrawRequest`: a pending receipt that was already haircut by `collectWithdrawFunds` (loss release #1) can be released a second time at full par through `_claimFundedWithdrawRequest`, because `_claimLossAdjustedWithdrawRequest` only looks at `lastWithdrawRequest[_user]` — a single-slot marker that a later `requestWithdraw` overwrites.

### Finding Description
`requestWithdraw` records `lastWithdrawRequest[_user] = currentEpoch` and adds `_amount` to both `withdrawsRequests[_user]` and `withdrawsRequestsByEpoch[_user][currentEpoch]` [1](#0-0) . When a `stopEpochWithDuration` loss is applied, `collectWithdrawFunds` sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber]`, i.e. the strategy receives only the reduced amount [2](#0-1) . The user's `withdrawsRequests` and per-epoch basis, however, remain at the unhaircutted value.

On claim, `_claimLossAdjustedWithdrawRequest` derives the loss epoch solely from `lastWithdrawRequest[_user]` [3](#0-2) . If the user makes a second `requestWithdraw` in a later epoch (explicitly supported — the code comment says unclaimed requests can stack), `lastWithdrawRequest` is overwritten, `lossRecoveryPriceByEpoch[newEpoch] == 0`, and the loss path returns 0. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — the aggregate including the E1 haircutted basis — at par, guarded only by `epochNumber > lastWithdrawRequest` [4](#0-3) . The per-epoch haircut in `withdrawsRequestsByEpoch[_user][E1]` is never enforced.

### Impact Explanation
The attacker recovers the `pendingLoss` portion of their E1 receipt that was never funded by the borrower. Each unit stolen is backed by underlying reserved for other users' funded receipts or active-LP NAV, so the theft is a direct insolvency transfer: later claimants' `transferFundedClaim`/recovery payouts revert or are shortchanged. Loss ≈ `e1Basis * (1 - lossRecoveryPriceByEpoch[E1] / RECOVERY_FULL)`, up to nearly the full E1 receipt for severe losses.

### Likelihood Explanation
Requires an unprivileged tranche holder, an epoch stopped with `stopEpochWithDuration(_lossAmount > 0)` (honest manager call), and a second honest withdrawal request before claiming. No privileged misbehavior needed; the only precondition is the user not claiming between the two epochs, which the design explicitly allows.

### Recommendation
Track all unclaimed loss epochs per user (or iterate `withdrawsRequestsByEpoch` epochs) rather than relying on the single `lastWithdrawRequest` slot. Alternatively, in `_claimFundedWithdrawRequest`, subtract any basis in epochs that have a nonzero `lossRecoveryPriceByEpoch`, or block new `requestWithdraw` while the user holds an uncleared loss-adjusted receipt.

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
