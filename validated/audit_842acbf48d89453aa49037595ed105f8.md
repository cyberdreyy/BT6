### Title
External-Initiator credentials bypass the "EIs not allowed" restriction on int-ID job runs - ([File: core/web/pipeline_runs_controller.go])

### Summary
`PipelineRunsController.Create` gates int-ID job runs on `auth.GetAuthenticatedUser(c)` returning `isUser == true`, intending (per the inline comment) to restrict this path to genuine dashboard/API users. However, `auth.AuthenticateExternalInitiator` also sets `SessionUserKey` to a synthetic `User{Role: UserRoleRun}`, so `GetAuthenticatedUser` returns `ok == true` for EI-authenticated callers as well, defeating the intended restriction.

### Finding Description
The route `POST /v2/jobs/:ID/runs` is registered with `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateExternalInitiator, auth.AuthenticateByToken, auth.AuthenticateBySession)` wrapped in `auth.RequiresRunRole(prc.Create)` [1](#0-0) . `AuthenticateExternalInitiator` authenticates the caller against External Initiator (EI) credentials and then sets both `SessionExternalInitiatorKey` and `SessionUserKey` to a synthetic `User{Role: UserRoleRun}` [2](#0-1) . `RequiresRunRole` only checks that the role is not `UserRoleView`, so this synthetic run-role user passes [3](#0-2) .

Inside `PipelineRunsController.Create`, the code explicitly comments that int-based job IDs should only be usable by users, not EIs, and gates that logic on `_, isUser := auth.GetAuthenticatedUser(c); if isUser {...}` [4](#0-3) . But `GetAuthenticatedUser` simply checks for the presence of a `*clsessions.User` in `SessionUserKey` [5](#0-4)  — it cannot distinguish a genuine session/token-authenticated user from the synthetic user object that `AuthenticateExternalInitiator` injects. As a result, a caller authenticated purely via EI credentials (`X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers) satisfies `isUser == true` and can trigger `prc.App.RunJobV2(ctx, jobID, nil)` for any int job ID, directly contradicting the stated invariant.

### Impact Explanation
An attacker holding only External-Initiator credentials (not a genuine dashboard user/API token) can trigger pipeline runs of arbitrary jobs by integer ID via `RunJobV2`, bypassing the intended restriction that reserves int-ID job triggering for authenticated users only. This is an authorization-bypass / unauthorized-job-run issue: EI credentials, which are meant to be scoped to specific webhook/EI-triggered job flows, can be used to invoke runs on any job in the node (subject only to `RunJobV2`'s own internal checks, if any), which can result in unintended fund-moving or state-changing job executions (e.g., OCR, keeper, VRF, or other job types) outside of their intended trigger path.

### Likelihood Explanation
This requires only valid External-Initiator credentials — a lower-privileged credential class than a full dashboard user session or API token. Any node operator that has created an EI (a common integration pattern) has effectively handed out credentials capable of running arbitrary int-ID jobs, which is inconsistent with the documented least-privilege intent. The exploit is deterministic and repeatable: any request with valid EI headers to `POST /v2/jobs/:intID/runs` will succeed.

### Recommendation
Distinguish genuine authenticated users from EI-derived synthetic users, e.g., by checking `auth.GetAuthenticatedExternalInitiator(c)` first and rejecting int-ID runs when an EI is present, or by introducing a separate context key/type for EI-synthesized users so `GetAuthenticatedUser` (or a new function) can differentiate them from real users. The check in `PipelineRunsController.Create` should reject the request when `SessionExternalInitiatorKey` is set, regardless of `SessionUserKey`.

### Proof of Concept
Handler-level Go test plan:
1. Set up a test app with `NewRouter`, create an `ExternalInitiator` record with known access key/secret via the app's ORM (as done in `core/bridges/external_initiator_test.go`), and create a job with a known int ID.
2. Send `POST /v2/jobs/<intID>/runs` with headers `X-Chainlink-EA-AccessKey` and `X-Chainlink-EA-Secret` set to the EI's credentials (do not set a session cookie or API token headers).
3. Assert the response is `200 OK` and contains a `pipelineRun` resource (i.e., `prc.App.RunJobV2` was invoked and a run was created) — confirming `isUser` evaluated `true` for the EI-authenticated request.
4. Contrast with expected behavior: assert instead that the response should be `401`/`422` ("bad job ID" / forbidden) for EI-only credentials, per the code comment's stated invariant, and show the current code fails this assertion.

```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	if !ok {
		return nil, false
	}

	user, ok := obj.(*clsessions.User)

	return user, ok
}
```

```go
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
```
