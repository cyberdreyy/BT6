### Title
Multisig executes requests below the live confirmation threshold via stale confirmations from removed members - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm` decides whether a request is authorized purely by comparing the size of a `confirmations` set to `num_confirmations`, without verifying that every entry in that set still corresponds to a current member. When a member/key is removed via `DeleteMember`/`DeleteKey`, the code only purges requests *authored* by that member and its `num_requests_pk` entry — it never scrubs that member's confirmation from other, still-pending requests. This lets a request execute with a confirmation count that no longer reflects the number of live signers actually approving it, breaking the "confirmations counted versus live members" binding.

### Finding Description
In `multisig2/src/lib.rs`, `confirm()` only checks the raw length of the confirmations set: [1](#0-0) 

`delete_member()` removes outstanding requests **created by** the removed member and clears its `num_requests_pk` entry, but does not touch `self.confirmations` entries for other requests that member had already confirmed: [2](#0-1) 

The same pattern exists in the v1 contract: `DeleteKey` only removes requests where `r.signer_pk == pk`, leaving that key's confirmations on other requests intact, while `confirm()` again just measures `confirmations.len()`: [3](#0-2) [4](#0-3) 

Concretely: with members A, B, C, D and `num_confirmations = 4`, request X (e.g. `Transfer` to an attacker-controlled account) is created by A (auto-confirmed), then confirmed by B and D — 3 confirmations, one short of threshold. A separate request removing D as a member is then confirmed and executed (`delete_member`). D's confirmation on X is never scrubbed. C then confirms X: `confirmations.len() as u32 + 1 >= 4` becomes true and `execute_request` runs the transfer, even though only 3 currently-live members (A, B, C) ever approved it — D's approval came from an account that is no longer a member at execution time.

### Impact Explanation
This is a direct instance of the impact category "a multisig request executed below threshold": funds can be transferred, keys added/removed, or contract code deployed by the multisig account with fewer live-member approvals than `num_confirmations` nominally requires, because a stale confirmation from a since-removed member is still counted. Since `Transfer` and `FunctionCall` actions can move NEAR directly, this is a Critical-impact custody-binding break (recorded/counted approvals vs. actual live approving members).

### Likelihood Explanation
No external/unprivileged attacker capability is needed beyond ordinary participation as one of the existing members going through the normal `add_request`/`confirm` flow; the flaw is in the protocol's own confirmation-tracking logic, not in trusting an already-privileged owner to misbehave arbitrarily. Any multisig that removes or rotates a member while that member has outstanding confirmations on other pending requests is exposed, which is a realistic operational scenario (key rotation, member offboarding) rather than a contrived edge case.

### Recommendation
When removing a member/key in `delete_member` (`multisig2/src/lib.rs`) and the `DeleteKey` action (`multisig/src/lib.rs`), iterate over `self.requests`/`self.confirmations` and remove the departing member's entry from every confirmation set it appears in (not just requests it authored). Alternatively, have `confirm()` recompute the effective confirmation count by filtering the stored confirmation set against current membership before comparing to `num_confirmations`, so stale entries never count toward the threshold.

### Proof of Concept
1. Deploy multisig with members `[A, B, C, D]` and `num_confirmations = 4`.
2. `A.add_request_and_confirm({ receiver_id: multisig, actions: [Transfer{amount}] })` → request X gets 1 confirmation (A).
3. `B.confirm(X)` → 2 confirmations.
4. `D.confirm(X)` → 3 confirmations (below threshold, request not yet executable).
5. Separately, members reach threshold on a `DeleteMember{member: D}` request and it executes — D is removed from `self.members`; D's confirmation on X remains in `self.confirmations[X]` because `delete_member` only clears requests where `r.member == D`.
6. `C.confirm(X)` → `confirmations.len() as u32 + 1 == 4 >= self.num_confirmations` → `execute_request` runs the `Transfer`, even though D is no longer a member and only 3 live members (A, B, C) ever actually approved X. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
