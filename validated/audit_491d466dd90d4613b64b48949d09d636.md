### Title
APR0 per-epoch interest rate flooring leaves borrower-funded interest permanently stranded in `IdleCreditVault` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`prepareStopEpochWithApr0` credits the full aggregate APR0 net interest (`_apr0NetInterest`) into `pendingWithdraws`, and the CDO pulls exactly that amount from the borrower at `stopEpoch`. However, each APR0 user's claim is recomputed as `principal * apr0RateByEpoch[epoch] / 1e18`, where `apr0RateByEpoch` itself is `(_apr0NetInterest * 1e18) / _principal` — floored twice. The sum of all user claims is therefore strictly less than the aggregate funded amount whenever division does not produce integers, leaving excess underlyings stranded in the strategy contract. This is the same bug class as the referenced `_computeTotalRewards` issue: a separately computed aggregate exceeds the sum of individually rounded payouts.

### Finding Description
In `prepareStopEpochWithApr0`, the vault computes a pro-rata APR0 interest share over aggregate principal, then books it wholesale: [1](#0-0) 

- `pendingWithdraws += _apr0NetInterest` (line 535) — the borrower-facing aggregate.
- `apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal` (line 537) — integer division rounds the per-unit rate **down**.

`stopEpoch` then pulls `_amountToPullFromBorrower + _pendingWithdraws` from the borrower and pushes `_pendingWithdraws` to the strategy via `collectWithdrawFunds`, so the strategy receives the un-floored `_apr0NetInterest` on top of principal. [2](#0-1) 

But each user settles via `_settleApr0`, which applies the floored rate with another floor: [3](#0-2) 

`settledInterest += principal * rate / 1e18` — summed over users, `Σ floor(p_i * floor(N*1e18/P) / 1e18) ≤ N`, and is strictly less than `N` whenever `N * 1e18` is not divisible by total principal or per-user products don't divide evenly. The payout in `_claimFundedWithdrawRequest` uses only this per-user rounded amount. [4](#0-3) 

There is no mechanism to reconcile the difference: the strategy has no skim/sweep of claim dust (`transferToken` is an owner rescue for arbitrary tokens, not accounted dust), and `apr0RateByEpoch`/claims do not route the remainder anywhere. The same two-step floor pattern repeats in default recovery (`defaultRecoveryPrice = reserve * 1e18 / totalBasis`, then each claim pays `claimBasis * price / 1e18`), so finalized recovery also permanently leaves a residual in `defaultRecoveryReserve`. [5](#0-4) [6](#0-5) 

### Impact Explanation
Every epoch in which APR0 withdraw requests exist and the division is inexact strands a small amount of borrower-funded underlying inside `IdleCreditVault`. The loss per epoch is bounded by roughly `(number of distinct APR0 claimants) + 1` units of the underlying's smallest denomination, but it is cumulative and never reclaimable by users, since each user's claim basis is fully consumed while their floored share is paid. Analogously, each `finalizeDefaultRecovery` strands up to ~`RECOVERY_FULL`-precision dust per claimant inside `defaultRecoveryReserve`. This matches the reported issue's impact: funds are sent/held in excess of the sum of payable claims and cannot be utilized by the intended recipients.

### Likelihood Explanation
The excess materializes whenever `_apr0NetInterest * 1e18 % apr0TotalPrincipal != 0` or any `principal_i * rate % 1e18 != 0` — i.e., in the common case of non-round principals and interest. It requires no attacker action beyond ordinary APR0 `requestWithdraw` usage during the buffer phase; any KYC-passed lender triggers it. No existing guard stops it: the strategy never reconciles the funded aggregate against claimed amounts. Impact is bounded to dust per operation, which is why this mirrors the original Medium's "small excess quantity … accumulate funds that cannot be utilized" rather than a theft.

### Recommendation
Mirror the recommended fix from the report — derive the aggregate from the sum of parts instead of an independent rounded computation:

```solidity
// prepareStopEpochWithApr0: don't book the gross _apr0NetInterest blindly;
// store the rate first, then sum floored per-principal claims, or carry the remainder.
apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;
uint256 _remainder = _apr0NetInterest - _sumFlooredClaims; // or
// simplest: keep the funding at _apr0NetInterest but explicitly credit the remainder
// to pendingWithdrawFees / feeReceiver so it is not untracked dust:
_adjPendingWithdrawFees += _apr0NetInterest - _claimableTotal;
pendingWithdraws += _claimableTotal;
```

Equivalently, add a `sweepDust()` path that sends `balance - (pendingWithdraws outstanding funded amount) - defaultRecoveryReserve` to `feeReceiver`, and in `finalizeDefaultRecovery` attribute the final rounding remainder of `defaultRecoveryReserve` to `feeReceiver` once all claims for `defaultRecoveryEpoch` are exhausted.

### Proof of Concept
Foundry fork sketch (pattern follows `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testApr0RateDustStrandsFundedInterest() external {
    // Setup: APR0 mode, three KYC'd lenders deposit in buffer phase.
    _setFeeParams(TL_MULTISIG, feeBps, FULL_ALLOC, 0); // fee > 0 for realism
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setApr(0); // unscaledApr == 0 -> APR0 path

    uint256 p1 = 1_000 * ONE_SCALE + 1;
    uint256 p2 = 2_000 * ONE_SCALE + 3;
    uint256 p3 = 3_000 * ONE_SCALE + 7;
    uint256 r1 = idleCDO.depositAA(p1); // user1
    // ... requestWithdraw for each user with distinct principal remainders ...

    // Epoch runs, borrower funds a non-round interest amount.
    deal(defaultUnderlying, borrower, expectedEpochInterest);
    vm.warp(cdoEpoch.epochEndDate());
    vm.prank(manager);
    cdoEpoch.stopEpoch(newApr, /* _interest */ overrideInterest);

    // All users claim.
    uint256 balBefore = IERC20Detailed(defaultUnderlying).balanceOf(address(strategy));
    cdoEpoch.claimWithdrawRequest(); // per user
    // ...
    uint256 dust = IERC20Detailed(defaultUnderlying).balanceOf(address(strategy));
    // Invariant: strategy should hold no untracked underlying after all claims.
    // Actual: dust > 0 equals _apr0NetInterest - sum(floor(principal_i * rate / 1e18)),
    // permanently stranded because apr0Users were deleted and no accounting references it.
    assertGt(dust, 0);
}
```

The same structure applies to `finalizeDefaultRecovery`: fund a recovery amount such that `reserve * 1e18 % totalBasis != 0`, have all defaulted claimants claim, and observe `defaultRecoveryReserve` retains a positive remainder no one can claim.
