### Title
Instant-withdraw receipts escape the default-recovery haircut and are paid at par before instant claims are finalized — ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
In the Linux `p9_fd_cancelled` bug, a request was removed twice because the guard only skipped the `REQ_STATUS_RCVD`/`REQ_STATUS_ERROR` states instead of skipping anything `!= SENT`. The structural analog in `IdleCreditVault.claimInstantWithdrawRequest` is a guard that only diverts receipts to the haircut path when *both* `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are set, while the "pay at par" funded path below it runs unconditionally. A defaulted-epoch instant receipt that has not yet been transitioned to the finalized instant-claims state is therefore paid 1:1 instead of at `defaultRecoveryPrice`, letting a holder drain the default-recovery reserve ahead of haircut-bearing claimants.

### Finding Description
`claimInstantWithdrawRequest` is called by the CDO on behalf of users:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:380-393
function claimInstantWithdrawRequest(address _user) external {
  _onlyIdleCDO();
  if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
  }
  uint256 amount = instantWithdrawsRequests[_user];
  _burn(_user, amount);
  instantWithdrawsRequests[_user] = 0;
  _transferFundedClaim(_user, amount);
}
```

The kernel bug's shape is identical: the guard enumerates a specific state pair (`defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`) instead of "anything that is not fully settled". When `defaultRecoveryFinalized == true` but `defaultInstantWithdrawsFinalized == false`, a receipt recorded in `instantWithdrawsRequests[_user]` / `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` falls straight through to `_transferFundedClaim` and is paid **at par**.

`_claimDefaultedInstantWithdrawRequest` (lines 842-856) shows what these receipts are *supposed* to get: `(claimBasis * defaultRecoveryPrice) / RECOVERY_FULL`, paid from the default recovery reserve via `_transferDefaultRecovery`. The comment at lines 850-851 confirms that unfunded instant receipts are counted as prefunded reserve during default finalization — i.e. the reserve is sized to cover them only at the haircut price. Paying them at par via `_transferFundedClaim` over-consumes the pooled recovery/funded balance, directly reducing what later defaulted-epoch claimants (both instant and normal) can recover.

This mirrors the kernel trace exactly: two removal paths (`_claimDefaultedInstantWithdrawRequest` vs. the funded path) both capable of consuming the same receipt, with the discriminator checking an enumerated state rather than "is this receipt still in a state that hasn't been resolved".

### Impact Explanation
An unprivileged tranche-token holder who requested an instant withdraw during the defaulted epoch and never collected it (a normal occurrence — `pendingInstantWithdraws` exists precisely for unfunded instant receipts) calls `claimInstantWithdrawRequest` after `finalizeDefaultRecovery` but before instant claims are finalized. They receive `instantWithdrawsRequests[user]` in underlying at 1:1 while the reserve was provisioned at `defaultRecoveryPrice < RECOVERY_FULL`. The excess is stolen from the recovery pool: every other defaulted-epoch claimant's effective recovery ratio is diluted, and in the worst case the last claimants' `_transferDefaultRecovery` reverts on insufficient balance — permanent freezing of unclaimed yield for honest users plus direct theft by the early claimer. Loss magnitude: `instantBasis * (1 - defaultRecoveryPrice/RECOVERY_FULL)` per receipt, i.e. up to the full haircut on all pending instant receipts.

### Likelihood Explanation
- Requirements: instant withdrawals enabled (`setInstantWithdrawParams`), ≥1 unfunded instant receipt outstanding in the defaulted epoch, and borrower default with `defaultRecoveryPrice < RECOVERY_FULL` — all unprivileged-market conditions.
- The existence of `defaultInstantWithdrawsFinalized` as a *separate* flag from `defaultRecoveryFinalized` implies the two are set by separate steps; if they were always set atomically the second flag would be redundant. Any ordering gap (or a finalization path that sets one without the other) opens the window. The normal-withdraw path does not share this defect because `claimWithdrawRequest` (lines 301-314) routes through `_claimDefaultedWithdrawRequest` on `defaultRecoveryFinalized` alone.
- Even if finalization is atomic today, the guard is fragile in exactly the way the kernel fix addressed; but as written, if a gap exists the exploit is a single claim transaction costing only gas.

### Recommendation
Mirror the kernel fix: treat "not fully settled" as the skip condition rather than enumerating settled states. Gate the funded-path payout on the receipt not belonging to a defaulted, not-yet-finalized epoch, e.g.:

```solidity
if (defaultRecoveryFinalized) {
  if (defaultInstantWithdrawsFinalized) {
    _claimDefaultedInstantWithdrawRequest(_user);
  } else {
    // receipts tagged to defaultRecoveryEpoch must wait for instant finalization
    uint256 pendingDefaulted = instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch];
    uint256 amount = instantWithdrawsRequests[_user] - pendingDefaulted;
    ... // pay only the non-defaulted remainder
  }
}
```

Alternatively, revert claims entirely while `defaultRecoveryFinalized && !defaultInstantWithdrawsFinalized`, ensuring no receipt can be paid at par during the transition window.

### Proof of Concept
Foundry fork PoC sketch (build on `test/foundry/IdleCreditVault.t.sol` helpers `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testInstantClaimEscapesDefaultHaircut() external {
  _useInstantWithdrawVariant();               // enable instant withdraws, set instantDelay
  uint256 amountWei = 10000 * ONE_SCALE;
  idleCDO.depositAA(amountWei);
  idleCDO.depositBB(amountWei);
  _startEpochAndCheckPrices(0);

  // attacker requests instant withdraw mid-epoch; it is recorded but stays unfunded
  uint256 req = cdoEpoch.requestInstantWithdraw(attackerAmount, address(AAtranche));
  assertGt(strategy.instantWithdrawsRequests(attacker), 0);

  // borrower defaults; owner/manager finalizes default recovery at haircut price
  _handleBorrowerDefaultViaManager();          // sets defaultRecoveryFinalized, defaultRecoveryPrice < RECOVERY_FULL
  // do NOT call the instant-claims finalization step, so defaultInstantWithdrawsFinalized == false

  uint256 balPre = underlying.balanceOf(attacker);
  cdoEpoch.claimInstantWithdrawRequest();      // falls through to _transferFundedClaim
  uint256 got = underlying.balanceOf(attacker) - balPre;

  uint256 haircut = req * strategy.defaultRecoveryPrice() / RECOVERY_FULL;
  assertGt(got, haircut);                      // paid at par, haircut escaped
  // recovery reserve / funded balance is now short by got - haircut for other claimants
}
```

Caveat: the PoC assumes `defaultRecoveryFinalized` and `defaultInstantWithdrawsFinalized` are set by separate calls/transactions in `finalizeDefaultRecovery` / the instant-claims finalization path; if the manager call sets both atomically, the window collapses and this degrades to a fragile-guard hardening issue rather than an exploitable bug. I was unable to read the body of `finalizeDefaultRecovery`/`_handleBorrowerDefault` to confirm the flag-setting order before the iteration limit.
