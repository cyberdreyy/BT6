### Title
Missing upper-bound check on `payload.Timestamp` allows perpetually-fresh replay of captured trigger requests - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` validates message freshness only by checking that the timestamp is not too old (`now - MaxAllowedMessageAgeSec > payload.Timestamp`), but never validates an upper bound (i.e., that `payload.Timestamp <= now`). A message signed with a Timestamp set far in the future will pass the "stale message" check indefinitely, regardless of how long after issuance it is replayed.

### Finding Description
In `core/services/gateway/handlers/capabilities/handler.go`, `HandleLegacyUserMessage` decodes `webapicap.TriggerRequestPayload` and enforces freshness with: [1](#0-0) 

The check `uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp)` only rejects messages that are *too old*; it never rejects messages whose `Timestamp` is set arbitrarily in the future. Since `payload.Timestamp` is inside `webapicap.TriggerRequestPayload`, which is part of `msg.Body.Payload`, and the whole payload is covered by the message signature (`Message.Sign` signs `MessageId | Method | DonId | Receiver | Payload`, see [2](#0-1)  and [3](#0-2) ), the value is set once at signing time and cannot be altered afterward without invalidating the signature. However, the original signer (or anyone who legitimately captures the fully signed message in transit, from logs, from a proxy, etc.) can present the exact same signed message again at any later point in time, and the staleness check will never reject it if the embedded `Timestamp` was inflated beyond `now + MaxAllowedMessageAgeSec` at signing time.

This defeats the intended purpose of the freshness/anti-replay check: it is supposed to bound how long a captured/leaked signed request remains usable. With an inflated future `Timestamp`, that bound becomes effectively unlimited (until real time catches up to the forged value), so the check no longer provides any anti-replay protection for that message.

### Impact Explanation
This matches Chainlink's "unauthorized job run" bounty impact class in a limited/scoped way: a legitimately-signed `web_api_trigger` request, once captured (e.g., via a compromised or observing intermediary, request logging, or accidental exposure) can be replayed indefinitely to re-trigger the same workflow/job execution, bypassing the intended staleness/anti-replay guarantee. It does not grant cross-user privilege escalation or credential disclosure (the attacker must already possess or capture a validly-signed message), and it does not defeat the message signature itself.

### Likelihood Explanation
Exploitability requires only that the attacker (or a party in a position to capture a signed message, such as a network observer, logging pipeline, or the sender itself) obtains one signed `web_api_trigger` message containing an inflated future `Timestamp`. No special privilege beyond being able to submit or capture a signed gateway message is needed; the flaw is deterministic and 100% repeatable since it is a pure logic gap (no time window, no race condition).

### Recommendation
Add an explicit upper-bound check rejecting timestamps set too far in the future, e.g.:
```go
now := uint(time.Now().Unix())
if now-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) || uint(payload.Timestamp) > now+h.config.MaxAllowedMessageAgeSec {
    // reject as stale/invalid
}
```
This bounds the valid timestamp window symmetrically around `now`, closing the "forever fresh" gap.

### Proof of Concept
1. In `core/services/gateway/handlers/capabilities/handler_test.go`, construct a `handler` with `MaxAllowedMessageAgeSec` set small (e.g., 5).
2. Build a `webapicap.TriggerRequestPayload` with `Timestamp = time.Now().Unix() + 1e9` (or `+10000`), marshal it into a signed `api.Message` with method `MethodWebAPITrigger`.
3. Call `HandleLegacyUserMessage` immediately — assert no "stale message" error is returned (expected, current behavior).
4. `time.Sleep` past the configured `MaxAllowedMessageAgeSec` window (or mock `time.Now` to advance past it), then replay the identical signed message via `HandleLegacyUserMessage` again.
5. Assert the "stale message" error path in [1](#0-0)  is still NOT triggered — demonstrating the check never rejects the replayed message despite the elapsed time exceeding `MaxAllowedMessageAgeSec`.

func GetRawMessageBody(msgBody *MessageBody) [][]byte {
	alignedMessageId := make([]byte, MessageIdMaxLen)
	copy(alignedMessageId, msgBody.MessageId)
	alignedMethod := make([]byte, MessageMethodMaxLen)
	copy(alignedMethod, msgBody.Method)
	alignedDonId := make([]byte, MessageDonIdMaxLen)
	copy(alignedDonId, msgBody.DonId)
	alignedReceiver := make([]byte, MessageReceiverLen)
	copy(alignedReceiver, msgBody.Receiver)
	return [][]byte{alignedMessageId, alignedMethod, alignedDonId, alignedReceiver, msgBody.Payload}
}
