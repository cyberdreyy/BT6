### Title
Closed-pool (`epochEndDate == 0`) withdraw requests mint interest-inflated receipts and drain the claim reserve ahead of legitimate claimants - (File: contracts/IdleCreditVault.sol)

### Summary
Like the Rails bug where a `nil`/empty parameter caused the intended `WHERE` restriction to disappear, `IdleCreditVault.requestWithdraw` treats `epochEndDate() == 0` as a "closed pool" sentinel that silently disables the normal receipt restrictions: `pendingWithdraws` is never incremented, the APR0 path is skipped, and `_claimFundedWithdrawRequest`'s epoch-wait guard (`epochNumber <= lastWithdrawRequest`) is bypassed entirely. Meanwhile the CDO-side receipt amount is still priced as principal **plus a full epoch of interest** via `_calcInterestWithdrawRequest`. The attacker gets an instantly-claimable, overvalued receipt paid out of the vault's recalled-funds reserve, at the expense of earlier receipt holders who find the reserve short.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `IIdleCDOEpochVariant(idleCDO).epochEndDate() == 0` the code sets `isClosed = true` and then (a) skips `pendingWithdraws += _amount` and (b) falls into the normal `withdrawsRequests` bookkeeping. A closed pool has already recalled all borrower funds into the CDO/strategy, so pending receipts are meant to be paid from that reserve at once — but nothing prevents a holder from opening a **new** request after close.

The receipt amount comes from `IdleCDOEpochVariant.requestWithdraw`, which computes `_underlyings = principal + interest - totalFees` where `interest` comes from `_calcInterestWithdrawRequest`. That function only early-returns when `epochDuration == 0`; `epochDuration` stays nonzero after a pool is closed, and `lastApr` is unchanged, so a post-close request still mints a receipt including interest for an epoch that will never run — the vault will never accrue that yield.

Because `epochEndDate == 0` also disables the claim-side guard in `_claimFundedWithdrawRequest` (`if (epochEndDate() != 0 && epochNumber <= lastWithdrawRequest[_user]) revert`), the attacker's inflated receipt is claimable in the same transaction. `_transferFundedClaim` pays from underlying already sitting in the strategy (the recalled pool funds reserved for pre-close receipts). The extra "interest" portion is taken directly from that reserve, so earlier legitimate receipt holders (or other tranche holders in the closed pool) end up under-funded — a NULL-check-style bypass: the `0` sentinel removes every restriction while leaving the accounting path active.

This is analogous to CVE-2013-6417: a special parameter value (`0` here, `nil`/`NULL` there) is interpreted differently by two cooperating components — the CDO still prices interest while the vault reads `epochEndDate == 0` as "no epoch bookkeeping needed" — producing missing restrictions.

### Impact Explanation
- Direct theft of reserve funds: each post-close `requestWithdraw` mints a receipt for `principal + interest - fees` while only `principal` was ever funded. The interest component is paid out of underlying reserved for other users' claims, so the last claimants cannot be made whole (insolvency for remaining receipts).
- Also affects a pool before its first epoch (`epochEndDate == 0` initially): a request made then gets `isClosed = true` treatment — `pendingWithdraws` not incremented, no epoch-wait before claim — the same missing-restriction class.
- Loss magnitude: up to one full epoch of interest per request (`amount * apr * epochDuration / year`), repeatable per account since each request overwrites `lastWithdrawRequest`.

### Likelihood Explanation
- Requirements: pool in closed state (`epochEndDate == 0` after full recall / pool close) or pre-first-epoch, and `allowAAWithdrawRequest`/`allowBBWithdrawRequest` still enabled — nothing in `requestWithdraw` blocks the closed state, and the manager does not need to be malicious, merely not to have flipped the allow flags.
- Attacker is an ordinary KYC'd tranche holder; no privileged role needed. The interest inflation scales with position size and APR, so this is most profitable on large AA/BB positions.
- Uncertainty: I could not fully verify within tool limits whether `stopEpoch`-with-close (`_interest == 1` sentinel path) leaves underlying idle in the vault versus the CDO; the exploit requires claimable underlying present in the strategy, which holds when close funds are collected via `collectWithdrawFunds`/`collectInstantWithdrawFunds`. If reserves sit only in the CDO, impact reduces to reserve-accounting corruption rather than immediate theft.

### Recommendation
- In `IdleCreditVault.requestWithdraw` and `IdleCDOEpochVariant.requestWithdraw`, revert (or force a pure principal-only path) when the pool is closed (`epochEndDate() == 0` after at least one epoch) rather than silently skipping `pendingWithdraws` bookkeeping.
- In `_calcInterestWithdrawRequest`, also return zero interest when the pool is closed so post-close receipts cannot include unaccrued yield.
- Make the claim-side gate consistent: the epoch-wait check should not be fully disabled by the same sentinel that skips funding accounting; use an explicit `poolClosed` flag instead of overloading `epochEndDate == 0`.

### Proof of Concept
A Foundry PoC (sketch, on the existing `IdleCreditVault.t.sol` harness):

```solidity
// 1. Setup: user1 deposits AA, epochs run, borrower recalls all -> pool closed.
//    (drive stopEpoch with the "repay all" sentinel so epochEndDate becomes 0,
//     and collectWithdrawFunds pulls recalled underlying into the strategy.)
// 2. Attacker (KYC'd AA holder) calls:
cdoEpoch.requestWithdraw(attackerShares, address(AAtranche));
//    - IdleCDOEpochVariant._calcInterestWithdrawRequest returns interest > 0
//      because epochDuration != 0, so receipt = principal + interest - fees.
//    - IdleCreditVault.requestWithdraw sees epochEndDate()==0 -> isClosed ->
//      pendingWithdraws NOT increased; withdrawsRequests[user] += inflated amount.
// 3. Attacker claims immediately (same tx):
cdoEpoch.claimWithdrawRequest();
//    - _claimFundedWithdrawRequest skips `epochNumber <= lastWithdrawRequest`
//      because epochEndDate()==0, pays principal+interest from the reserve.
// 4. Assert: attacker received more underlyings than their tranche value;
//    remaining reserve < sum of outstanding pre-close receipts -> last
//    claimant's claimWithdrawRequest() reverts on insufficient balance.
```

Key assertions: `requested > principal` (receipt includes phantom epoch interest), attacker claim succeeds in the same block as the request, and a prior receipt holder's claim fails or pays out less than `withdrawsRequests[user]`.
