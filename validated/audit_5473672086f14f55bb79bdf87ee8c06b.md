### Title
Permissionless staked bank creation succeeds against a zero-supply LST mint, permanently unpriceable and wasting group bank-slot capacity - ([File: programs/marginfi/src/instructions/marginfi_group/add_pool_permissionless.rs])

### Finding Description
`lending_pool_add_bank_permissionless` calls `group.add_bank()` (consuming a bank slot) at [2](#0-1)  before calling `bank.config.validate_oracle_setup(ctx.remaining_accounts, ...)` at [3](#0-2) , which delegates to `OraclePriceFeedAdapter::validate_bank_config` at [4](#0-3) . The `lst_supply > 0` guard (`ZeroSupplyInStakePool`) only exists in `load_oracle_context_with_max_age`, the pricing path used by `pulse_health`/price-load calls, at [1](#0-0) . I was unable to fully confirm the body of `validate_bank_config`'s `StakedWithPythPush` arm (truncated past line 1000 in the tool output) to verify whether it independently re-checks `lst_supply`, so I cannot conclusively state whether creation-time validation duplicates or omits this check.

### Impact Explanation
If confirmed that `validate_bank_config`'s creation-time path does not check `lst_supply > 0`, an attacker could create an SPL single-pool mint before any stake delegation (supply zero) and call `lending_pool_add_bank_permissionless`, consuming a `group.add_bank()` slot for a bank that will always revert with `ZeroSupplyInStakePool` during any subsequent `pulse_bank_price`/health-pulse call (division by `lst_supply` at [5](#0-4)  and [6](#0-5)  would divide by zero if not guarded, or fail the explicit check). This would create a permanently broken/unusable bank entry without allowing fund loss, matching a bank-slot exhaustion scoped impact rather than a fund-loss vulnerability.

### Likelihood Explanation
This requires an unprivileged attacker to control the exact timing between SPL single-pool creation and stake delegation, since a legitimate validator would typically delegate stake immediately, making a persistent zero-supply window a self-inflicted or attacker-orchestrated edge case with narrow economic incentive (the attacker pays creation costs, e.g. vault rent, to grief one bank slot). I could not verify from the available code whether `validate_bank_config`'s creation-time branch already independently guards against zero supply, which is necessary to determine if this is exploitable at all.
