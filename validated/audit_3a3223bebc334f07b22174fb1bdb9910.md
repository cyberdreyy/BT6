### Title
Instant-withdraw receipts from prior epochs are excluded from default recovery accounting and become permanently unclaimable — ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault` tracks instant-withdraw receipt basis per epoch (`instantWithdrawClaimsByEpoch`), but the default-recovery path only ever reads the **current** epoch bucket (`instantWithdrawClaimsByEpoch[epochNumber]`). If an instant withdraw request stays partially unfunded across an epoch boundary (i.e., `pendingInstantWithdraws > 0` while the receipt was recorded in an earlier epoch), its basis is silently dropped from both the recovery claim basis and the prefunded reserve. After `finalizeDefaultRecovery`, the holder's claim always reverts, permanently freezing their funds — a stale/out-of-range epoch-index read analogous to the CVE's out-of-bounds read in `SDL_InvalidateMap`.

### Finding Description
Analogous to an out-of-bounds/stale-index read, the vault reads receipt data through a single epoch index that does not match where the data was actually written:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` only when `pendingInstantWithdraws != 0` [1](#0-0) .
- `_defaultPrefundedInstantReserve()` similarly only inspects `instantWithdrawClaimsByEpoch[epochNumber]` [2](#0-1) .
- `requestInstantWithdraw` records basis under the epoch active at request time (`instantWithdrawClaimsByEpoch[currentEpoch] += _amount`), while `pendingInstantWithdraws` is a global aggregate with no epoch dimension [3](#0-2) .
- `pendingInstantWithdraws` is decremented only when the CDO calls `collectInstantWithdrawFunds`, so a partially collected instant queue survives into later epochs [4](#0-3) .

Broken sequence:

1. Epoch N buffer: victim calls `requestInstantWithdraw(1000e6)`. `instantWithdrawClaimsByEpoch[N] = 1000e6`, `pendingInstantWithdraws = 1000e6`.
2. Epoch N+1 runs; borrower only repays part, CDO collects e.g. 400e6 via `collectInstantWithdrawFunds`. `pendingInstantWithdraws = 600e6` remains.
3. Epoch N+1 ends, epoch N+2 starts (`epochNumber` now N+2). Borrower defaults.
4. Manager calls `finalizeDefault`. `defaultPendingClaimBasis()` reads `instantWithdrawClaimsByEpoch[N+2] == 0` → the victim's 600e6 (and the 400e6 already-collected portion of their receipt) contributes zero basis and zero prefunded reserve.
5. `defaultRecoveryFinalized = true`, `defaultInstantWithdrawsFinalized = true` (since `pendingInstantWithdraws != 0`), reserve sized only for active basis + normal pendingWithdraws.
6. Victim calls `claimInstantWithdrawRequest` via the CDO: `_claimDefaultedInstantWithdrawRequest` finds `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch=N+2] == 0`, then falls through to the funded path: `amount = instantWithdrawsRequests[user] = 1000e6`, `_burn`, `_transferFundedClaim` — which reverts because `balance - reserve < amount` (all strategy balance is the recovery reserve, and the victim was never included in it) [5](#0-4) [6](#0-5) .

The user's receipt tokens are burned-or-reverted either way: they cannot claim at par (reserve guard), and they cannot claim through recovery (zero basis for their epoch). The same stale-index pattern exists in `_claimDefaultedInstantWithdrawRequest`, which only clears `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` [7](#0-6) .

### Impact Explanation
Permanent freezing of user funds. Any instant-withdraw requester whose receipt was recorded in an epoch earlier than `defaultRecoveryEpoch` while `pendingInstantWithdraws > 0` loses their entire claim basis: it is excluded from `totalBasis` in `finalizeDefaultRecovery`, so no recovery reserve is allocated to them, and the `_transferFundedClaim` reserve guard permanently reverts their post-default claim. Loss equals the full unfunded instant receipt amount of such users; additionally the "prefunded" portion of their receipt (already collected underlying) is absorbed into the general recovery reserve for other claimants.

### Likelihood Explanation
Requires a specific but honest-actor sequence: an instant withdraw that is only partially collected before an epoch rolls, followed by a borrower default in a later epoch. Partial collection is a normal operating mode (`collectInstantWithdrawFunds` accepts partial `_amount`), and instant receipts carrying across epochs is permitted by design (receipts are claimable "at any time"). No privileged misbehavior is needed; the manager/borrower act normally.

### Recommendation
Track instant-withdraw claim basis globally (not only per current epoch) for default accounting: either maintain an aggregate `instantWithdrawClaimsTotal` used by `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`, or iterate/accumulate all epochs with outstanding instant basis. Alternatively, make `_claimDefaultedInstantWithdrawRequest` clear `instantWithdrawsRequests[_user]` at `defaultRecoveryPrice` regardless of which epoch recorded the receipt, and include that full amount in the finalized basis.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` setup):

```solidity
// setup: depositAA, startEpoch(0), borrower borrows, stopEpoch(0)
// 1) buffer of epoch 1: victim requestInstantWithdraw(1000e6)
cdoEpoch.requestInstantWithdraw(victimShares, address(AAtranche)); // via victim prank
// 2) startEpoch(1); borrower repays only partial instant amount
//    CDO calls collectInstantWithdrawFunds(400e6) -> pendingInstantWithdraws = 600e6
// 3) warp, stopEpoch(1), startEpoch(2) -> epochNumber advanced
// 4) borrower defaults: cdoEpoch._handleBorrowerDefault / finalizeDefault(...)
//    finalizeDefaultRecovery pulls recovery; victim basis = instantWithdrawClaimsByEpoch[epochNumber] == 0
// 5) victim claim:
vm.prank(victim);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.claimInstantWithdrawRequest();
// assert victim underlying balance unchanged and instantWithdrawsRequests[victim] still > 0
// assert defaultRecoveryReserve == strategy balance (no headroom for victim)
```

Key assertion: after finalization, `strategy.instantWithdrawsRequests(victim) > 0` while `underlyingToken.balanceOf(strategy) == strategy.defaultRecoveryReserve()`, so both the funded path and the recovery path are unreachable for the victim.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
