### Finding: Asymmetric dedup keys let a signer's weight be counted in both `total_weight_approved` and `total_weight_rejected`

In `stackerdb_listener.rs`, `BlockStatus` tracks two separate weight accumulators plus a `responded_signers` set meant to ensure each signer's vote counts once: [1](#0-0) 

When an `Accepted` message arrives, the dedup check is against `gathered_signatures` (not `responded_signers`), and afterward it unconditionally inserts into both maps: [2](#0-1) 

When a `Rejected` message arrives, the dedup check is against `responded_signers` only: [3](#0-2) 

Because the accept path never consults `responded_signers`, a signer who first sends `Rejected` (weight credited to `total_weight_rejected`, `responded_signers` now contains their slot) can subsequently send `Accepted` for the *same* `signer_signature_hash`, and since `gathered_signatures` was never populated by the earlier rejection, the accept branch treats it as a fresh vote and adds the same signer's weight to `total_weight_approved` as well. The reverse order (accept-then-reject) is correctly guarded, because the accept path always inserts into `responded_signers` too — but the reject path's own dedup key is not consulted by the accept path, so the guard is one-directional.

The miner's coordinator loop then evaluates both totals independently: [4](#0-3) 

This breaks the invariant that a responding signer's weight should be attributed to exactly one side of the accept/reject tally. A single signer (no majority required — they only need control of their own key) can inflate `total_weight_approved` by their own weight while their earlier rejection remains permanently recorded in `total_weight_rejected`. This is precisely the "rejection recounted as acceptance" pattern called out in the analog rules: the signer's authentic rejection response is silently re-attributed as an acceptance once they later emit any accept message for the same block hash, regardless of their true final position, and the two ledgers (`approved`/`rejected`) can now double-book the same responder instead of being mutually exclusive partitions of `total_weight`.

Whether this is exploitable to actually flip an outcome depends on borderline weight distributions (e.g. right at the 70%/30% boundary), since the inflation is bounded to the flipping signer's own weight; but it is a genuine break of the "aggregated-weight vs verified-accepts" equality the rules ask about, reachable by a single signer without needing a majority, node access, or another party's key.
