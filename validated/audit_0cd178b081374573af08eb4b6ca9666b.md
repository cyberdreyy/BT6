### Title
Reorg-timing check in `check_parent_tenure_choice` treats an already group-signed tenure as "unsigned/late-arriving," permitting an unconditional reorg of a canonical tenure - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_parent_tenure_choice` decides whether a miner may build off something other than the prior sortition (a reorg) by measuring how close the reorged tenure's first block was to the next sortition. When the locally-stored record of that first block has no `approved_time`, the code assumes "we did not sign over the reorged tenure's first block" and hard-codes the elapsed time to `0`, which is always `< first_proposal_burn_block_timing`. This is the same bug class as the reported curve-pool issue: a boundary/derived value that is supposed to gate a decision degenerates to a constant that always satisfies the check, silently disabling the intended protection. Here, `approved_time` being `None` does **not** imply "unsigned" — a signer can hold a block whose `signed_group` field is set (i.e., it already knows the block was globally/group-accepted) while `approved_time` is `None`, because these fields are set independently and `get_first_approved_block_in_tenure`'s own query treats `signed_self`, `signed_group`, and `approved_time` as three independent "approved" indicators.

### Finding Description
`check_parent_tenure_choice` in [1](#0-0)  permits a reorg of a tenure that already mined a block only if that block was "poorly timed" relative to the next sortition: [2](#0-1) 

The timing gap is computed as:
```
proposal_to_sortition = sortition_state_received_time - approved_at   // if approved_time is Some
proposal_to_sortition = 0                                             // if approved_time is None
```
and the reorg is allowed whenever `proposal_to_sortition < first_proposal_burn_block_timing`. When `approved_time` is `None`, `proposal_to_sortition` is forced to `0`, which is always less than any positive `first_proposal_burn_block_timing` (default 60s, see the sample config comment at [3](#0-2) ). The reorg is therefore unconditionally permitted, regardless of how long the tenure has actually existed.

The premise "`approved_time` is None ⟹ we did not sign this block" is false. The record used here comes from `SignerDb::get_first_approved_block_in_tenure`, whose SQL treats three independent columns as equally valid evidence of "approved": [4](#0-3) 

`signed_self`, `signed_group`, and `approved_time` are set by different code paths and are not coupled. `approved_time` is only stamped by `mark_pre_committed` (this signer's own validate→pre-commit path); `signed_group` is stamped by `mark_locally_accepted(true)` when a signer observes the *rest of the signer set* reach the 70% signature threshold on a block, per the flow documented in [5](#0-4)  — including explicitly the "outdated peer" fallback where a signer receives a peer's acceptance without ever having seen (or issued) a pre-commit for that block: [6](#0-5) 

That a `signed_self`/`signed_group` timestamp can exist while `approved_time` is `None` is directly demonstrated by the signerdb regression test which sets these fields independently and asserts the `approved`/`signed` predicates still hold: [7](#0-6) [8](#0-7) 

So a signer that never personally pre-committed a tenure's first block — because it joined late, restarted, or simply received other signers' acceptances before its own pre-commit (the documented "outdated peer" path) — but that *does* know the block reached global/group signature threshold (`signed_group` set, `approved_time` unset), will have `check_parent_tenure_choice` treat that already-canonical tenure as a "late-arriving proposal" and grant an unconditional reorg permit. The tenure is then recorded as superseded via `record_superseded_tenure` → `SignerDb::mark_tenure_superseded` [9](#0-8) , which causes `reorg_permit_stands` to exclude that tenure's blocks from the conflict guard at signing time [10](#0-9) , letting this signer place its signature on a block that conflicts with (reorgs) a tenure it already knows to be globally accepted/canonical.

### Impact Explanation
This breaks the "approved-parent vs canonical" equality that `check_parent_tenure_choice` exists to enforce: a signer ends up signing a conflicting/non-canonical replacement block for a tenure that was already established (globally accepted) — a Critical-class outcome ("a signer signing an invalid, non-canonical, or conflicting block"). Because the trigger condition (`approved_time == None` while the block is nonetheless known to be signed/group-accepted) can occur independently on multiple signers under ordinary network conditions (restarts, message ordering, the documented outdated-peer path), a single malicious miner can time a competing tenure proposal to exploit it on enough signers to fracture consensus around an already-canonical tenure.

### Likelihood Explanation
No majority of signers or key compromise is required — the condition is a per-signer local-state quirk reachable through ordinary gossip/timing races that the codebase already documents as expected ("outdated peer" fallback, restarts before validating a tenure's first block). A single miner only needs to propose a competing tenure at the right moment while some signers have this record shape; the bug then unconditionally grants that miner a reorg permit at those signers regardless of the tenure's actual age or legitimacy.

### Recommendation
In `check_parent_tenure_choice`, do not default `proposal_to_sortition` to `0` when `approved_time` is `None`. Instead, distinguish "we have no committed timing record" from "we know the block was signed": if `signed_self` or `signed_group` is set (i.e., `has_signed_block_in_tenure`/`get_first_approved_block_in_tenure` matched via those fields rather than `approved_time`), treat the tenure as *not* poorly timed (deny the reorg, or fall back to the group's own approved/signed timestamp if available) rather than assuming the earliest possible timing that trivially satisfies the threshold.

### Proof of Concept
1. Signer S restarts (or is otherwise behind) right as tenure A's first block is being decided; S never calls `mark_pre_committed` for that block (so `approved_time` stays `None`), but shortly after receives peer `Accepted` responses that push the group signature past the 70% threshold, causing S to call `mark_locally_accepted(true)` and set `signed_group` (per the "outdated peer" fallback in `store_and_process_block_signature`/`handle_block_pre_commit`). Tenure A is now globally accepted from the network's perspective, and S's local record for A's first block has `signed_group = Some(t)`, `approved_time = None`.
2. A miner proposes a new tenure C whose block commit builds off the sortition *prior* to tenure A (a reorg of A, and possibly B if B built on A).
3. S's `check_parent_tenure_choice` runs for tenure C: `tenures_reorged` includes A; `globally_accepted_blocks` for A is `1` (passes the `>1` guard); `get_first_approved_block_in_tenure(A)` returns S's stored block info with `approved_time == None`.
4. The code sets `proposal_to_sortition = 0`, which is `< first_proposal_burn_block_timing` (e.g. the default 60s), so S treats A as "poorly timed" and marks A as superseded by C via `record_superseded_tenure`.
5. S subsequently signs a block in tenure C at the pre-commit threshold: at signing time, `reorg_permit_stands` finds A's conflict record superseded by C's (still-canonical) sortition and excludes it from the conflict guard [11](#0-10) , so S signs the conflicting tenure-C block even though A was already globally accepted/canonical — despite S never having independently verified that A's block was actually "late" relative to the sortition.

    /// Whether a reorg permit recorded for this conflict's tenure still stands.
    ///
    /// `check_parent_tenure_choice` records a permit when the reorg-timing rules sanction a
    /// later tenure replacing what the conflict's tenure built (see
    /// [`SignerDb::mark_tenure_superseded`]). A standing permit excludes the conflict entirely:
    /// our signature must not stand in the way of a replacement we sanctioned. But the permit
    /// is only as alive as the sortition it was granted to: if a burnchain fork orphaned the
    /// permitting sortition, the reorg we sanctioned can no longer happen, and the record must
    /// not keep suppressing the conflict.
    ///
    /// A false 404 here (e.g. from a node still catching up) only restores a conflict the
    /// permit could have excluded, which at worst delays the replacement, so unlike
    /// `conflict_still_blocks` no tip-height guard is needed. A node error voids the permit for
    /// the same reason: blocking is the direction that can be taken back.
    fn reorg_permit_stands(
        &self,
        stacks_client: &StacksClient,
        conflict: &SignedConflictInfo,
    ) -> bool {
        let Some(superseded_by) = &conflict.superseded_by else {
            return false;
        };
        match stacks_client.get_sortition_by_burn_hash(&superseded_by.burn_block_hash) {
            Ok(_) => true,
            Err(ClientError::RequestFailure(reqwest::StatusCode::NOT_FOUND)) => {
                info!("{self}: The tenure we permitted to reorg a conflicting block's tenure was itself orphaned by a burnchain fork. The permit no longer excludes the conflict.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                    "superseded_by_burn_block_hash" => %superseded_by.burn_block_hash,
                );
                false
            }
            Err(e) => {
                warn!("{self}: Failed to check whether the sortition that permitted a reorg is still canonical: {e:?}. Treating the permit as void.";
                    "conflicting_consensus_hash" => %conflict.consensus_hash,
                    "superseded_by_consensus_hash" => %superseded_by.consensus_hash,
                );
                false
            }
        }
    }
