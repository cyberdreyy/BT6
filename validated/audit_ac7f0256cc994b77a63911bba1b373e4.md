Let me check the stopEpoch ordering in the CDO variant to confirm whether `epochNumber` is incremented before `collectWithdrawFunds`.### Title
Loss-adjusted withdraw receipts escape their haircut because `lossRecoveryPriceByEpoch` is keyed by the post-`deposit` `epochNumber` while receipts are marked with the pre-stop request epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analog of CVE-2020-3864 ("a context may not have had a unique security origin"): in `IdleCreditVault`, a stop-epoch loss context (`lossRecoveryPriceByEpoch`) is keyed by an epoch counter that is incremented inside the same `stopEpoch` processing that applies the loss, so it does not uniquely match the epoch identifier stamped on the pending withdraw receipts (`lastWithdrawRequest` / `withdrawsRequestsByEpoch`). As a result, pending receipts recorded under request-epoch `E` look up `lossRecoveryPriceByEpoch[E]` (zero) instead of the haircut stored under `E+1`, skip `_claimLossAdjustedWithdrawRequest`, and are paid at par through `_claimFundedWithdrawRequest` even though `collectWithdrawFunds` zeroed `pendingWithdraws` and only pulled the haircut amount. Paying receipts at par from under-funded reserves makes the vault insolvent for later claimants.

### Finding Description
`IdleCreditVault.requestWithdraw` stamps each receipt with the *current* `epochNumber` at request time (`lastWithdrawRequest[_user] = currentEpoch`, `withdrawsRequestsByEpoch[_user][currentEpoch] += _amount`) [1](#0-0) .

When a stop-epoch loss occurs, `IdleCDOEpochVariant.stopEpoch` calls into the strategy. During that processing, `deposit()` is invoked while `isEpochRunning()` is still true, which executes `epochNumber += 1` (the comment at line 607-610 explicitly documents "deposit done on stopEpoch ... so we reset the counter; epochNumber += 1") [2](#0-1) . Subsequently `collectWithdrawFunds` stores the haircut under the *already-incremented* counter: `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` [3](#0-2) .

At claim time, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` — i.e., the request-epoch key `E`, not the storage key `E+1` — finds `0`, and returns nothing [4](#0-3) . Control falls to `_claimFundedWithdrawRequest`, whose gate `epochNumber <= lastWithdrawRequest[_user]` passes because `epochNumber` is now `E+1 > E`, and it pays `withdrawsRequests[_user]` in full via `_transferFundedClaim` [5](#0-4) . The receipt tokens are burned and the full, un-haircut amount is transferred, while `pendingWithdraws` was zeroed and only `pendingToFund` (the haircut amount) was ever collected into the strategy.

The invariant broken is the loss waterfall / "one receipt one haircut-adjusted payout": receipts escape the loss socialization entirely. No guard stops this — the `requestWithdraw` re-request check (lines 263-271) only triggers when `lossRecoveryPriceByEpoch` is nonzero *at the user's own epoch key*, which is precisely the key that was never written.

### Impact Explanation
Direct theft / insolvency. First claimants with pending receipts in a loss epoch withdraw 100% of their basis instead of `lossRecoveryPrice` (e.g., a 50% loss haircut means they extract 2x what was funded for them). Since only the haircut total was transferred into the strategy, each par payout drains funds reserved for other receipt holders; subsequent claimants — including users whose new requests coincidentally match the stored key, and holders of funded receipts behind them — find the strategy under-collateralized and their claims revert or are permanently impaired. Loss is quantified as `Σ(claimBasis_i * (1 - lossRecoveryPrice))` extracted at par until the funded balance is exhausted.

### Likelihood Explanation
Requires only (a) pending withdraw receipts at a `stopEpoch`/`stopEpochWithDuration` where the borrower funds less than `pendingWithdraws` (partial repayment / realized loss — a normal, expected flow per `previewLossAdjustedWithdrawFunds`), and (b) the ordering assumption that the epoch-bumping `deposit()` executes before `collectWithdrawFunds` within `stopEpoch`, which the code comments imply ("deposit done on stopEpoch"). The attacker needs no privilege — any tranche holder with a pending request benefits automatically, no timing manipulation needed; the mis-keying is systematic for every receipt in that epoch.

**Uncertainty:** I was unable to read `IdleCDOEpochVariant.stopEpoch` (and `IdleCDOEpochVariantPrefunded.stopEpoch`) to confirm that the `deposit()` call that increments `epochNumber` strictly precedes `collectWithdrawFunds` inside the same `stopEpoch`. If `collectWithdrawFunds` runs before the incrementing deposit, the key matches and the bug does not trigger via this path — though a secondary mismatch remains possible for receipts requested in the *buffer of the new epoch* sharing the aggregate `pendingWithdraws` with a prior-epoch loss.

### Recommendation
Key the loss-adjusted haircut by the epoch in which the receipts were requested, not by the mutated counter: capture `pendingEpoch` (e.g., persist the epoch of the pending bucket when the first request of a cycle is recorded, or snapshot `epochNumber` at `prepareStopEpoch`/before the deposit increment) and write `lossRecoveryPriceByEpoch[requestEpoch]`. Alternatively, store the haircut under every pending receipt's epoch or change `_claimLossAdjustedWithdrawRequest` to look up the haircut by the epoch the loss was applied. Add a regression test that requests a withdraw, stops the epoch with a partial funding loss, and asserts the claim pays `claimBasis * lossRecoveryPrice`, not `claimBasis`.

```solidity
// SPDX-License-Identifier: MIT
// Foundry fork test against the deployed IdleCDOEpochVariant + IdleCreditVault.
// Assumes stopEpoch order: deposit() (bumps epochNumber) -> collectWithdrawFunds().

function test_LossEpochKeyMismatch_PaysReceiptsAtPar() public {
    // --- Setup: epoch E running, LP has deposited and holds tranche tokens ---
    uint256 depositAmt = 100_000e6;
    deal(underlying, lp, depositAmt);
    vm.prank(lp);
    cdoEpoch.depositAA(depositAmt);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // --- LP requests withdraw during buffer of epoch E+1 ---
    // (allowAAWithdrawRequest gate satisfied; epoch not running)
    // After prior stopEpoch, epochNumber == E+1, so:
    //   lastWithdrawRequest[lp] = E+1
    //   withdrawsRequestsByEpoch[lp][E+1] = X
    vm.prank(lp);
    cdoEpoch.requestWithdraw(tranche.balanceOf(lp), address(tranche));
    uint256 reqEpoch = strategy.epochNumber(); // == E+1
    uint256 pending = strategy.pendingWithdraws();
    assertEq(strategy.lastWithdrawRequest(lp), reqEpoch);

    vm.prank(manager);
    cdoEpoch.startEpoch(); // epoch E+1 running

    // --- Borrower repays only half: realized loss, stopEpochWithDuration path ---
    // Inside stopEpoch: deposit() executes while isEpochRunning() =>
    //   epochNumber becomes E+2 BEFORE collectWithdrawFunds stores
    //   lossRecoveryPriceByEpoch[E+2] = ~0.5e18.
    uint256 funded = pending / 2; // 50% haircut
    deal(underlying, borrower, funded);
    vm.prank(borrower);
    IERC20(underlying).approve(address(cdoEpoch), funded);
    // stopEpochWithDuration(lossAmount) -> previewLossAdjustedWithdrawFunds ->
    //   collectWithdrawFunds(funded) with _amount < pendingBasis
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(lossAmount, duration);

    // Stored key is E+2; user's marker is E+1 -> lookup misses the haircut.
    assertEq(strategy.lossRecoveryPriceByEpoch(reqEpoch), 0, "user epoch key never written");
    assertGt(strategy.lossRecoveryPriceByEpoch(strategy.epochNumber()), 0);
    assertEq(strategy.pendingWithdraws(), 0, "pending zeroed though underfunded");

    // --- lp claims: skips loss path, gate epochNumber(E+2) > lastWithdrawRequest(E+1) passes ---
    uint256 balPre = underlying.balanceOf(lp);
    vm.prank(lp);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(lp) - balPre;

    // BUG: paid at par instead of ~funded share; drains the half-funded reserve.
    assertEq(got, pending, "receipt escaped haircut and claimed at par");
}
```

```text
  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
```
