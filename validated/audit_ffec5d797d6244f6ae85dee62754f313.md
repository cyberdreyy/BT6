### Title
Positional `minAmount` arrays in reward harvesting can be misbound to a mutated reward-token list, losing slippage protection - ([File: contracts/strategies/convex/ConvexBaseStrategy.sol])

### Summary
The Angle finding shows that slippage-protection arrays bound only by index position (not by token address) silently apply to the wrong tokens when the underlying list changes between parameter computation and execution. The same pattern exists in the IdleCDO reward-harvesting path: `IdleCDO._sellAllRewards` and `ConvexBaseStrategy.redeemRewards` match caller-supplied `_minAmount` / `_minAmountsWETH` values to the on-chain reward-token list purely by array index, with no address binding. A change to the reward list (removal, addition, or reordering performed by the honest owner) between the off-chain computation of `extraData` and the harvest execution misaligns every min-amount, leaving rewards sold at near-zero floors and sandwichable.

### Finding Description
In `ConvexBaseStrategy.redeemRewards`, the extra reward data is decoded and applied positionally:

```solidity
// contracts/strategies/convex/ConvexBaseStrategy.sol:286-298
(_minAmountsWETH, _skipSell, _minDepositToken, _minLpToken) = abi.decode(_extraData, (uint256[], bool[], uint256, uint256));
IBaseRewardPool(rewardPool).getReward();
...
for (uint256 i = 0; i < _convexRewards.length; i++) {
    if (_skipSell[i]) continue;
    _reward = _convexRewards[i];          // fetched fresh from storage
    ...
    _router.swapExactTokensForTokens(
        _rewardBalance,
        _minAmountsWETH[i],                // bound by index, not by address
        _reward2WethPath,
        ...
    );
```

The token actually swapped is read from the mutable `convexRewards` storage array at execution time (line 298), while the slippage floor was computed off-chain against the list as it existed when the caller built `_extraData`. There is no check that `_minAmountsWETH[i]` corresponds to `_convexRewards[i]` — no token addresses are passed alongside the amounts, and no length check beyond Solidity's implicit bounds check.

The identical pattern exists in `IdleCDO._sellAllRewards` (`contracts/IdleCDO.sol:641-668`), where `_rewards = _strategy.getRewardTokens()` is read fresh and `_minAmount[i]` / `_skipReward[i]` are applied by index to whatever `_rewards[i]` is at that moment:

```solidity
// contracts/IdleCDO.sol:657-666
for (uint256 i; i < rewardsLen; ++i) {
    _rewardToken = _rewards[i];
    if (_skipReward[i]) { continue; }
    ...
    (_soldAmounts[i], _swappedAmounts[i]) = _sellReward(_rewardToken, _paths[i], _sellAmounts[i], _minAmount[i]);
}
```

The reward lists are owner-mutable in the strategies that expose reward-list setters (e.g., `setRewardTokens`-style functions across the strategy family, and the `Reward[]` initializer in `ConvexBaseStrategy` for Convex deployments where extra reward gauges get added or rotated over the pool's lifetime — exactly the "collateral revoked and a new one added" scenario in the original issue). The owner is honest, but a list mutation executed between the keeper's `extraData` computation and the harvest transaction landing on-chain produces the misbinding.

### Impact Explanation
When the list order shifts, a min-amount computed for reward token X (a high-value reward) is applied to the swap of reward token Y (or vice versa). If a valuable reward ends up bound to a near-zero floor, its `swapExactTokensForTokens` executes unprotected; an MEV attacker sandwiches it and extracts essentially the full value of that reward up to its intended minimum. The loss is borne by the vault's NAV and therefore by all tranche holders — direct theft of yield, matching the accepted "theft of unclaimed yield" impact class. Additionally, a length mismatch makes harvest revert (temporary freezing of accounting updates), and a `_paths[i]` misbinding can make a swap revert permanently until a new consistent state is reached.

### Likelihood Explanation
The trigger requires only the honest owner to modify the reward list (adding a new extra-reward gauge, removing a dead one, or reordering entries — routine maintenance on Convex/Curve strategies) while a harvest is being prepared or in-flight. Off-chain keepers necessarily compute `extraData` against the then-current list, so the race window exists whenever governance/ops touches the reward configuration. It is not exploitable on demand by the attacker — the attacker only captures the mispriced swap once the misbinding occurs — which caps likelihood, consistent with a Medium.

### Recommendation
Mirror the recommended mitigation from the original report: bind slippage parameters to token addresses, not positions. Accept `extraData` as an array of `(address rewardToken, uint256 minAmount, bool skipSell, bytes path)` tuples and look up the index (or skip unknown tokens), or at minimum pass the expected `address[]` reward list and `require` it equals the on-chain list before applying indexed amounts:

```solidity
address[] memory _expectedRewards = abi.decode(_extraData, (address[]));
require(keccak256(abi.encode(_expectedRewards)) == keccak256(abi.encode(convexRewards)), "rewards changed");
```

### Proof of Concept
Reproducible on a Foundry mainnet fork against a Convex strategy deployment (e.g., a ConvexBaseStrategy-backed CDO):

```solidity
// 1. Fork mainnet at a block where the strategy holds pending Convex rewards.
// 2. Keeper computes extraData off-chain:
//    _minAmountsWETH = [minCRV, minCVX, minExtra] against convexRewards = [CRV, CVX, EXTRA]
// 3. Owner (honest) adds a new reward token / rotates the list:
vm.prank(owner);
strategy.addExtraReward(NEW_REWARD); // shifts indices, e.g. inserts at a front position
// 4. Keeper's harvest lands:
vm.prank(keeper);
cdo.harvest(false, 0, true, encodedExtraData, new bytes[](0));
// 5. Inside redeemRewards, _minAmountsWETH[0] (minCRV, ~0 for cheap reward) is now
//    applied to the swap of NEW_REWARD or CRV is protected by minCVX, etc.
//    The valuable reward sells with a near-zero floor.
// 6. Attacker sandwich:
vm.prank(attacker);
// buy dipped pair before swap, sell after -> captures reward value up to intended min
// assert: WETH received by strategy < intended minAmount for the sold reward
```

Key assertions: (a) harvest succeeds despite misbound arrays (no address check reverts); (b) `balanceOf(WETH)` gained for the misprotected reward is below its computed `minAmount` floor; (c) the delta is capturable by a sandwiching EOA.

Caveat: the exact owner-facing setter name and ordering semantics differ per strategy (`convexRewards` is set via the `Reward[]` initializer and maintained by Convex gauges upstream in `ConvexBaseStrategy`, while `setRewardTokens`-style setters exist in the euler/harvest strategy family where `getRewardTokens()` feeds `_sellAllRewards`). The misbinding primitive itself is identical in both `ConvexBaseStrategy.sol:286-298` and `IdleCDO.sol:657-666` regardless of which concrete setter mutates the list.
