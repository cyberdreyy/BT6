### Title
`check_parent_tenure_choice` skips the local-signer-knowledge check when the node reports `first_block_mined = None`, permitting a reorg of a tenure with an already-approved block - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` only consults `signer_db.get_first_approved_block_in_tenure` when the node's `TenureForkingInfo::first_block_mined` is `Some(..)`. When the node returns `None` for a reorged tenure - which happens whenever `network.stacks_tip.block_id()` used by `TenureForkingInfo::from_snapshot` has not yet advanced to include a just-globally-accepted block of that tenure - the function unconditionally pushes the tenure to `superseded_tenures` and eventually returns `Ok(true)`, never checking whether the local signer already holds an approved/signed block for that tenure. This lets a competing miner's reorg be approved even though the signer's own DB proves a block was actually signed in the tenure being reorged.

### Finding Description
The property that must hold is: *the parent/tenure a signer approves for a new proposal must equal the canonical chain's actual parent, and any reorg of a tenure that already produced a locally-approved/signed block must be rejected unless timing rules explicitly excuse it.* The code enforces this correctly in the `Some(first_block_mined)` branch (`stacks-signer/src/chainstate/mod.rs:225-245`), which calls `signer_db.get_first_approved_block_in_tenure` and rejects (`Ok(false)`) if local knowledge conflicts and can't be reconciled by timing.

But the `None` branch (`stacks-signer/src/chainstate/mod.rs:225-233`) does **not** perform this check: [1](#0-0) 

It only relies on `signer_db.get_globally_accepted_block_count_in_tenure(&tenure.consensus_hash) > 1` (lines 210-223) to short-circuit to `Ok(false)`; a tenure with exactly one locally-approved (but not yet marked globally-accepted in this signer's own DB) block passes that gate, falls into the `None` branch, is pushed to `superseded_tenures`, and the loop continues to `Ok(true)` at line 294 - permitting the reorg.

`first_block_mined` is computed server-side in `TenureForkingInfo::from_snapshot` (`stackslib/src/net/api/get_tenures_fork_info.rs:139-194`) via `NakamotoChainState::get_nakamoto_tenure_start_block_header(&mut chainstate.index_conn(), tip_block_id, &sn.consensus_hash)`, where `tip_block_id` is `network.stacks_tip.block_id()` captured at request time (`get_tenures_fork_info.rs:232,251`). If the queried node's own idea of the canonical Stacks tip has not yet caught up to a block that was just globally accepted in that tenure (a normal propagation/processing race, not requiring any privileged access), this lookup returns `None` even though the block genuinely exists and was signed.

Attack flow: an unprivileged attacker wins a single BTC sortition slot, and immediately crafts a `BlockProposal` whose `TenureChangePayload.prev_tenure_consensus_hash`/`parent_tenure_id` points at an older sortition than `prior_sortition`, i.e., a reorg of the most recently active tenure. If the attacker manages to get this proposal to a victim signer at a moment when that signer's connected stacks-node's `network.stacks_tip` has not yet advanced to reflect the just-accepted block of the tenure being reorged, `get_tenure_forking_info` returns `first_block_mined = None` for that tenure even though `signer_db.get_first_approved_block_in_tenure` on the signer side has a real entry for it. `check_parent_tenure_choice` then supersedes that tenure and returns `Ok(true)`, and the signer proceeds to sign the attacker's competing/reorging block.

### Impact Explanation
This breaks canonicity (Critical): a signer signs a block for a tenure that reorgs another tenure which the signer itself already knows produced a signed/approved block, purely because a transient, race-prone RPC field said otherwise. If enough signers hit this same race independently (each connected to their own node, which can each independently lag), the network could finalize a reorg that discards an already-signed block, i.e., a chain-safety violation matching the "signer signing an invalid/non-canonical/conflicting block" category.

### Likelihood Explanation
No majority of signers, no compromised keys, and no local host access are required - only a single winning BTC slot and the ability to gossip a `BlockProposal`/`TenureChange` claiming an older parent tenure, timed to arrive while the target's connected node's tip has not caught up. This is a timing-dependent race (bounded by however long it takes the target node to advance `network.stacks_tip` after globally accepting a block), so it is not always exploitable, but it is repeatable across sortitions and does not require coordination with other signers or privileged access.

### Recommendation
In the `None` branch of `check_parent_tenure_choice`, before unconditionally superseding the tenure, consult `signer_db.get_first_approved_block_in_tenure` (and/or the globally-accepted record) the same way the `Some` branch does, and apply the same timing check (`first_proposal_burn_block_timing`) rather than assuming "node returned None" implies "nothing to lose." Only supersede unconditionally when the local signer DB also has no record of an approved/signed block for that tenure.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v2.rs` (or `mod.rs` tests):
1. Populate `signer_db` with a `BlockInfo` for tenure `T_old` via `insert_block`, then mark it approved so `signer_db.get_first_approved_block_in_tenure(&T_old)` returns `Some(local_block_info)`.
2. Construct a mocked `StacksClient`/`get_tenure_forking_info` response containing a `TenureForkingInfo` for `T_old` with `first_block_mined: None`, `nakamoto_blocks: None`, and `globally_accepted_blocks` count in `signer_db` staying `<= 1`.
3. Build a `SortitionData` whose `parent_tenure_id` differs from `prior_sortition` (forcing the reorg path), with `prior_sortition`/`consensus_hash` set to represent the new sortition superseding `T_old`.
4. Call `check_parent_tenure_choice(&mut signer_db, &client, &first_proposal_burn_block_timing)`.
5. Assert `Ok(false)` is expected (i.e., the signer should refuse to endorse a reorg of a tenure it locally knows had an approved block) - and show the current code instead returns `Ok(true)`, demonstrating the gap.
