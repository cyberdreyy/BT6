### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
The reported ParaSpace bug is a TOCTOU issue where a point-in-time health check ("has the account really recovered") can be satisfied with a stale/transient state rather than the actual current trust state. The `multisig2` contract has an analogous binding-violation: the number of *confirmations counted* for a pending request is meant to represent the number of *currently live, authorized members* who approved it, but `delete_member` never purges a removed member's confirmations from requests created by *other* members. This lets a request execute using a confirmation from an account that is no longer a member at execution time, i.e. `confirmations.len() >= num_confirmations` becomes true without `num_confirmations` live members actually having approved.

### Finding Description
`confirm()` executes a request once `confirmations.len() as u32 + 1 >= self.num_confirmations`: [1](#0-0) 

`delete_member()` is the only place that cleans up member-related state when a member is removed. It removes the member from `self.members`, deletes the member's own `num_requests_pk` entry, and deletes any *requests that member itself created* (along with those requests' confirmation sets): [2](#0-1) 

Critically, it does **not** scan `self.confirmations` for entries where the removed member appears as a *confirmer* on requests created by other members. Those stale confirmations remain in the `HashSet<String>` stored under `self.confirmations`, keyed by `member.to_string()`.

The invariant that should hold is:
```
confirmations_counted(request) == |{live members who confirmed request}|
```
After a member is deleted, this equality is broken for any request they confirmed but did not create: `confirmations_counted(request)` still includes the departed member, while the true set of live confirmers is smaller by one.

### Impact Explanation
This falls under the explicitly listed Critical impact: "a multisig request executed below threshold." A request can be executed with fewer genuinely live/authorized confirmations than `num_confirmations` requires, because a stale confirmation from a deleted member is still counted. Since multisig requests include `Transfer`, `FunctionCall`, `AddKey`/`AddMember` (full account takeover), and `DeployContract`, this can lead to unauthorized movement of NEAR held by the multisig account, or unauthorized code/key changes — a violation of the core multisig custody guarantee.

### Likelihood Explanation
Reaching this requires ordinary, unprivileged multisig operations (no owner/foundation/redeploy required): any member can create and confirm requests, and any coalition reaching `num_confirmations` can execute a `DeleteMember` request through the completely standard flow. The specific sequence — member confirms a request, is later removed via a separate `DeleteMember` request, and the first request is subsequently pushed over threshold by a new confirmer — is a natural operational sequence (e.g., during routine membership rotation), not a contrived edge case, so likelihood is reasonably high in any multisig with active membership churn and outstanding requests.

### Recommendation
In `delete_member`, iterate over all outstanding `requests`/`confirmations` and remove the deleted member's public key/account string from every confirmation set (not just requests they created), re-checking (and possibly re-triggering) threshold logic afterward. Alternatively, when validating in `confirm`, filter `confirmations` against the currently live `self.members` set before comparing against `num_confirmations`, so removed members' stale approvals never count.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 2`.
2. `B` calls `add_request(X)` for `Transfer{amount}` — a legitimate, unrelated request. `confirmations[X] = {}`.
3. `A` calls `confirm(X)` — since `0 + 1 < 2`, this only records `confirmations[X] = {A}` (per `confirm` logic at [1](#0-0) ).
4. Separately, `B` and `C` create and confirm a `DeleteMember{A}` request, reaching 2 confirmations and executing `delete_member(A)` ( [2](#0-1) ). This removes `A` from `self.members`, but request `X`'s confirmation set (created by `B`, not `A`) is untouched — `confirmations[X]` still equals `{A}`.
5. Members are now `{B, C}`; `num_confirmations` remains `2`.
6. `C` calls `confirm(X)`. `confirmations[X].len() (1) + 1 = 2 >= num_confirmations (2)` → request `X` executes, transferring funds, even though the only currently-live confirmer is `C` (plus the stale, no-longer-valid confirmation from removed member `A`).

This demonstrates a multisig request executing with a confirmation count that does not correspond to the number of live, authorized members — violating the intended `K`-of-`N` custody guarantee.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
