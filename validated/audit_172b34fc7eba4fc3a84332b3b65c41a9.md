### Title

Unvalidated credit-vault underlying token can freeze all pooled assets - ([File: contracts/IdleCreditVaultFactory.sol](contracts/IdleCreditVaultFactory.sol))

### Summary

`IdleCreditVaultFactory.deployCreditVault` is permissionless and accepts `cvParams.underlying` without checking whether the ERC20 can pause, blacklist, freeze, or otherwise block transfers involving the deployed strategy. [1](#0-0)  That arbitrary token is passed to both `IdleCreditVault.initialize` and `IdleCDOCreditVault.initialize`. [2](#0-1)  The strategy stores it permanently and only validates that `decimals()` succeeds. [3](#0-2)  An unprivileged attacker can therefore deploy a pool whose underlying is an attacker-controlled freezable ERC20, induce users to deposit, and then freeze the strategy’s token account, permanently preventing recovery of pooled funds.

### Finding Description

Deposits first move the underlying from the depositor to the credit-vault contract. [4](#0-3)  The same deposit flow then calls `IdleCreditVault.deposit`, which pulls those tokens into the strategy and mints strategy receipts. [5](#0-4) 

Normal repayment and withdrawal paths depend on that strategy continuing to transfer the same token: `sendInterestAndDeposits` transfers underlying back to the CDO. [6](#0-5)  Funded withdrawal claims ultimately call `_transferFundedClaim`, while epoch settlement pulls funded withdrawal amounts from the CDO into the strategy. [7](#0-6) [8](#0-7) 

Because the underlying address is immutable after initialization, an attacker can deploy the pool with an ERC20 that initially behaves normally, allow victims to deposit, then activate a freeze or blacklist covering the strategy address. The attacker need not hold the owner, manager, guardian, borrower, Keyring-admin, feeReceiver, or queue roles; they only call the permissionless factory and control the token contract they selected as `underlying`.

The broken invariant is withdrawal solvency: tranche balances and strategy-token receipts remain internally accounted for, but the ERC20 backing them can no longer leave the strategy.

### Impact Explanation

All deposits held by the malicious underlying can be permanently frozen. Deposits already forwarded to `IdleCreditVault` cannot be returned because outbound transfers revert. A freeze covering the CDO as well also blocks funded claim payouts and repayment custody. The loss equals the vault’s full underlying balance, less only funds already withdrawn before the freeze.

### Likelihood Explanation

The exploit requires users to deposit into a malicious pool. Deployment itself is permissionless, the malicious token only needs ERC20 metadata and ordinary transfer behavior before activation, and the attacker can preserve appearances by assigning honest addresses to the protocol roles. This is plausible for unofficial or phishing pools, but requires attracting victim liquidity, so it is less certain than a flaw in an already trusted vault.

### Recommendation

Do not allow arbitrary `cvParams.underlying` values in `IdleCreditVaultFactory`. Maintain a treasury-controlled allowlist of approved underlying tokens and reject every other address in `_deployBaseCreditVault`. Since ERC20 freezing or blacklisting capability has no universal interface, absence of such controls cannot be reliably proven through a single `freeze_authority`-style query. For approved tokens, deployment checks should also verify expected metadata and probe deposits/transfers only as a secondary sanity check, not as a replacement for review.

                borrowerName: "VictimPool"

        vm.prank(cv);
        IdleCreditVault(strategy).sendInterestAndDeposits(1e6);
    }

    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;

      pendingWithdraws = pendingBasis - _amount;
    }
