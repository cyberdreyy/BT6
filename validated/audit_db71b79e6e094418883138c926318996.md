### Title
EI-authenticated requests are made indistinguishable from real UserRoleRun users via synthetic `SessionUserKey`, defeating downstream role/EI-specific checks - ([File: core/web/auth/auth.go])

### Summary
`AuthenticateExternalInitiator` synthesizes a `*clsessions.User{Role: clsessions.UserRoleRun}` and stores it under the same `SessionUserKey` used by real authenticated users (`AuthenticateByToken`/`AuthenticateBySession`). Any downstream handler that calls `auth.GetAuthenticatedUser(c)` (including `auth.RequiresRunRole`) cannot tell whether the request came from a genuine run-role user or from an external initiator credential.

### Finding Description
In the `userOrEI` route group in `core/web/router.go`, requests to `POST /v2/jobs/:ID/runs` are authenticated by trying, in order, `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, `auth.AuthenticateBySession` [1](#0-0) .

`AuthenticateExternalInitiator` verifies the EI's access-key/secret against the DB, then sets both `SessionExternalInitiatorKey` and `SessionUserKey` — the latter populated with a freshly constructed `&clsessions.User{Role: clsessions.UserRoleRun}` that has no identity fields (no email, no ID) tying it back to the EI record [2](#0-1) . `AuthenticateByToken`/`AuthenticateBySession` set `SessionUserKey` to the real `*clsessions.User` loaded from the DB in exactly the same way [3](#0-2) [4](#0-3) .

`GetAuthenticatedUser` simply reads `SessionUserKey` and type-asserts to `*clsessions.User`, with no way to distinguish the synthetic EI user from a real one [5](#0-4) . Consequently `auth.RequiresRunRole`, which only checks `user.Role != UserRoleView`, treats both identically [6](#0-5) .

This is concretely exploited (not merely theoretical) in `PipelineRunsController.Create`, the handler wired to this exact route: the code comment states "only users are allowed to run jobs using int IDs - EIs not allowed," and the code implements that intent via `_, isUser := auth.GetAuthenticatedUser(c); if isUser { ... }` [7](#0-6) . Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `isUser` evaluates to `true` for a valid EI credential just as it does for a real run-role user — the intended EI restriction ("EIs not allowed" to trigger runs by int job ID) does not actually hold. An attacker holding only EI credentials (access key/secret, obtainable e.g. from a compromised/leaked external-initiator integration, which is a lower-privilege credential than a full user account) can call `POST /v2/jobs/:ID/runs` with an arbitrary integer job ID and trigger `prc.App.RunJobV2(ctx, jobID, nil)` for any job on the node, not just the job the EI is nominally bound to.

### Impact Explanation
This is an authorization/role-scoping bypass: a credential intended to be scoped to a single job (external initiator) can trigger runs of any job by numeric ID, because the code's own EI-exclusion check (`isUser`) is rendered meaningless by the shared `SessionUserKey` mechanism. This maps to Chainlink's "unauthorized job run" bounty impact class — an attacker with only EI credentials can force execution of pipelines/jobs they should not control, potentially causing unwanted on-chain transactions, fund movement (for jobs with transmitters), or resource exhaustion.

### Likelihood Explanation
Precondition is possession of valid EI access-key/secret (a lower-privileged credential than a full user account, often distributed to external systems and thus at higher risk of leakage). No admin or user-session access needed. The bypass is deterministic and repeatable: every request through `AuthenticateExternalInitiator` sets the same synthetic `UserRoleRun` object, so the `isUser` check in `PipelineRunsController.Create` will always pass for any valid EI credential.

### Recommendation
Do not overload `SessionUserKey` for external initiators. Either:
1. Have `AuthenticateExternalInitiator` avoid setting `SessionUserKey` entirely, and update `auth.RequiresRunRole` / any handler needing "run-or-EI" semantics to explicitly check `GetAuthenticatedExternalInitiator` OR `GetAuthenticatedUser`, never conflating the two.
2. Introduce a distinct marker (e.g., a `Source`/`AuthMethod` field on the session object, or a separate context key such as `SessionAuthMethodKey`) so downstream handlers such as `PipelineRunsController.Create` can reliably exclude EI-originated requests as the code comment already intends.
3. Fix `PipelineRunsController.Create` to check `_, isEI := auth.GetAuthenticatedExternalInitiator(c); if isEI { reject }` in addition to/instead of relying on `isUser`.

### Proof of Concept
Go handler-level integration test plan (in `core/web` test package, using `cltest` harness already used by `pipeline_runs_controller_test.go`):
1. Create a job with an integer ID via the test harness.
2. Create a valid `bridges.ExternalInitiator` (via `bridges.NewExternalInitiator`) and persist it so `FindExternalInitiator` succeeds.
3. Send `POST /v2/jobs/:ID/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` (per `static.ExternalInitiatorAccessKeyHeader`/`SecretHeader`) matching the EI, and the job's integer ID as `:ID`.
4. Assert the response is `200 OK` and a pipeline run is created (i.e., `prc.App.RunJobV2` was invoked) — proving `isUser` was true and the "EIs not allowed" comment/intent in `core/web/pipeline_runs_controller.go` line 110 does not hold.
5. As a contrast/root-cause test, directly call `auth.AuthenticateByToken` for a real `UserRoleRun` user and `auth.AuthenticateExternalInitiator` for the EI in two separate `gin.Context`s, then assert `auth.GetAuthenticatedUser(c)` returns structurally equivalent `*clsessions.User{Role: UserRoleRun}` values (differing only by pointer identity/absence of Email/ID) for both, documenting that downstream code cannot tell them apart.

	obj, ok := c.Get(SessionUserKey)

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
