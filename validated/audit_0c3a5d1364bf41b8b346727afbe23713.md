### Title
Unauthenticated MFA challenge oracle leaks raw WebAuthn CredentialAssertion JSON via 401 error body - ([File: core/web/sessions_controller.go])

### Summary
When a caller supplies valid `sr.Email`/`sr.Password` for a WebAuthn-enabled account but omits `sr.WebAuthnData`, `orm.CreateSession` intentionally serializes the full `protocol.CredentialAssertion` challenge object into the returned `error`. `SessionsController.Create` passes that error unmodified to `jsonAPIError`, which places `err.Error()` directly into the JSON HTTP 401 response body, exposing the raw internal WebAuthn challenge state to the caller.

### Finding Description
`SessionsController.Create` binds the request, fetches the user's registered WebAuthn tokens, and calls `sc.App.AuthenticationProvider().CreateSession(ctx, sr)`. On error it does: `jsonAPIError(c, http.StatusUnauthorized, err)` [1](#0-0)  — the error is forwarded verbatim as the API error payload.

In `orm.CreateSession`, once email/password have been validated and the user is found to have `uwas` (WebAuthn credentials) but `sr.WebAuthnData == ""`, the code calls `sessions.BeginWebAuthnLogin`, JSON-marshals the resulting `protocol.CredentialAssertion` `options`, and returns it as the error string: `return "", pkgerrors.New(string(j))` [2](#0-1) .

`jsonAPIError` does not sanitize or generalize the error — it calls `models.NewJSONAPIErrorsWith(err.Error())` and writes it directly into the JSON response [3](#0-2) . This means the full serialized `protocol.CredentialAssertion` (RPID, allowed credential IDs, challenge nonce, user verification requirements, etc.) is returned as the literal text of the 401 error body to any client who already knows/guesses valid email+password.

This is confirmed by the existing unit test `TestORM_WebAuthn`, which unmarshals `err.Error()` directly into a `protocol.CredentialAssertion` struct and checks fields like `ca.Response.RelyingPartyID` [4](#0-3) .

Because password validation happens strictly before the MFA branch (`constantTimeEmailCompare` and `utils.CheckPasswordHash` are checked first) [5](#0-4) , this exact response (full challenge JSON vs. a generic "Invalid email"/"Invalid password" error) becomes a binary oracle confirming valid credentials AND additionally discloses internal WebAuthn session/challenge details (including the enumerated credential IDs registered to the account) to an unauthenticated caller.

### Impact Explanation
This is an information-disclosure / authentication-oracle issue reachable pre-auth by anyone who can guess/know valid credentials. It leaks:
- Confirmation that a given email/password pair is valid (credential-guessing oracle), distinct from generic "invalid credentials" responses for non-MFA or wrong-credential cases.
- Internal WebAuthn state: RPID, registered credential ID(s) associated with the account, and challenge nonce — information intended only for the legitimate browser session that requested it, not for arbitrary HTTP callers.

This does not by itself allow forging a WebAuthn assertion (the credential's private key material stays on the authenticator), so it does not directly enable full session takeover. The impact is scoped to credential validity oracle + internal state/credential-ID disclosure, matching a low/informational bounty class rather than critical key/secret disclosure — but it is a real violation of the defensive design already partially present in the code (the code comments even show explicit intent to avoid leaking "if an account has MFA tokens or not" prior to password check, which this branch undermines after password check).

### Likelihood Explanation
- Precondition: attacker must already possess (or successfully guess) valid email+password for an MFA-enabled account.
- No authentication, session, or role is required to reach `POST /sessions` (`SessionsController.Create`).
- Fully repeatable: each request with correct creds and empty `WebAuthnData` returns a fresh serialized challenge in the 401 body.

### Recommendation
In `orm.CreateSession` (core/sessions/localauth/orm.go), do not return the raw serialized `CredentialAssertion` as the `error` message consumed by `jsonAPIError`. Instead:
1. Return a distinct, structured sentinel (e.g., a typed error or a dedicated result value) indicating "MFA challenge required," and have `SessionsController.Create` handle that case explicitly, returning the challenge JSON only within a proper structured response body (not the generic error path) — or continue returning it but ensure the HTTP semantics/documentation reflect that this is a legitimate step-up-auth flow, and audit whether credential IDs need to be included in the pre-auth challenge (WebAuthn spec allows omitting `allowCredentials` for privacy-preserving discoverable credentials).
2. More importantly, ensure the response for this branch is not gated only on the two-factor requirement: consider issuing the same generic response structure whether or not MFA is required, or rate-limit/lock down this endpoint to reduce credential-guessing oracle value regardless of the WebAuthn leakage.

### Proof of Concept
Handler-level Go test plan (using `httptest` + gin router with `SessionsController`):
1. Seed a user via `orm.CreateUser` with known email/password, then register a WebAuthn credential via `sessions.AddCredentialToUser` (mirroring `TestORM_WebAuthn` setup) [6](#0-5) .
2. Configure the app's WebAuthn config (`RPID`, `RPOrigin`) so `sc.App.GetWebAuthnConfiguration()` returns non-empty values, as used in `SessionsController.Create` [7](#0-6) .
3. POST `{"email": "<user>", "password": "<validPassword>"}` (no `webAuthnData`) to `/sessions`.
4. Assert the HTTP status is `401`.
5. Assert-and-fail: attempt `json.Unmarshal` of the response body's `errors[0].detail` (or equivalent JSONAPI error field) into `protocol.CredentialAssertion`; if unmarshal succeeds and `ca.Response.RelyingPartyID` / `ca.Response.AllowedCredentials` are populated, this proves the raw challenge is leaked (test should currently FAIL demonstrating the bug, i.e., the assertion "response contains only a generic MFA-required message" does not hold).
6. Compare against a wrong-password request to same account — the body differs qualitatively (generic "Invalid password" string vs. full JSON structure), proving the oracle.

func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
