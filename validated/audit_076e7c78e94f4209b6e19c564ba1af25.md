### Title
Signer can sign two conflicting tenure-start blocks for the same tenure when the duplicate has a higher chain length - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
The one-time `DuplicateBlockFound` check (which prevents accepting a second `BlockFound` tenure-change block for a tenure the signer has already signed) only runs at proposal time in `validate_tenure_change_payload`. The docs explicitly acknowledge this and rely on the own-tenure conflict guard inside `handle_block_pre_commit` (via `SignerDb::get_signed_conflicts`) as the substitute defense once a block crosses the pre-commit threshold minutes later. That substitute guard, however, filters conflicts by `stacks_height >= <candidate block's chain_length>`. A second (duplicate) tenure-start proposal for the same tenure that confirms more of the parent tenure (and therefore has a **higher** `chain_length` than the already-signed first block) falls below that floor and is never returned as a conflict, so the signer signs it — producing two signed, conflicting first blocks for the same tenure.

### Finding Description
Two independent mechanisms are supposed to jointly enforce "at most one signed tenure-start block per tenure":

1. **Proposal-time check** — `validate_tenure_change_payload` (v1: `stacks-signer/src/chainstate/v1.rs:461-520`, v2: `stacks-signer/src/chainstate/v2.rs:306-359`) rejects a `BlockFound` tenure-change with `RejectReason::DuplicateBlockFound` if `get_last_signed_block`/`get_last_globally_accepted_block` already returns a signed block for that tenure's `consensus_hash`. This check is height-agnostic — any signed block in the tenure trips it.

2. **Pre-commit-time re-check** — `check_block_against_signer_db_state` (`stacks-signer/src/v0/signer.rs:1803-1880`) is re-run once the pre-commit threshold is reached. For a tenure-change block it only calls `check_tenure_change_confirms_parent`, which checks the **parent** tenure's tip — it never checks whether the signer has already signed a block in the tenure the proposal itself belongs to:

`height` here is set to the **candidate (new) block's** `chain_length`, and only signed blocks at or above that height are returned. This design is correct for the *sibling-at-same-height* case the tests exercise (`stacks-signer/src/v0/tests.rs:603-827`, all constructing A and B with identical `chain_length`), but it silently assumes two tenure-start blocks for the same tenure always share the same height.

That assumption is false: a `BlockFound` tenure-change's `chain_length` is `parent.chain_length + 1`, and `previous_tenure_end` (the chosen parent within the parent tenure) is miner-controlled. If the parent tenure produces additional blocks between the first tenure-start proposal (A, confirming an earlier parent block) and a second tenure-start proposal for the *same* tenure (B, confirming a later parent block), B's `chain_length` is strictly **greater** than A's. Once this signer has already signed A (`signed_self` set, tracked in `signerdb.rs` `blocks` table with A's lower `stacks_height`), and B later reaches the pre-commit threshold, `get_signed_conflicts(B.chain_length, B_hash)` excludes A because `A.stacks_height < B.chain_length`. The subsequent conflict-blocking logic (`stacks-signer/src/v0/signer.rs:1403-1465`) operates only on the (now empty) `conflicts` list, so it signs B unconditionally:

The result: this signer now holds two of its own signatures over two different, mutually exclusive "first blocks" of the same tenure (A and B), breaking the invariant `DuplicateBlockFound` exists to enforce — one canonical tenure-start block per tenure.

### Impact Explanation
This is a signer signing a conflicting/non-canonical block: two signed candidates for the "first block of tenure X" can coexist in this signer's ledger of signatures, each eligible to be aggregated toward the network-wide 70% threshold. If the rest of the signer set (or a mix of stale/late pre-commits) also lands on B after having endorsed A, or if different subsets of signers converge on A vs B, the network can end up with irreconcilable signature sets for the same tenure — exactly the "signed vs validated"/"one-per-tenure canonical" equality the `DuplicateBlockFound` check is meant to protect. This matches the required Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
A single miner fully controls the ordering and content of tenure-start proposals it broadcasts, including the choice of `previous_tenure_end` (which parent-tenure block to confirm) and the timing of a re-proposal after the parent tenure has advanced. No cooperation from a majority of signers or any other signer's key is required to trigger the flawed local decision inside a single signer's `handle_block_pre_commit`; the only external dependency is the ordinary pre-commit weight from honest peers who have no visibility into this signer's own prior signature. The scenario (parent tenure advancing between two same-tenure proposals) is a normal occurrence during tenure boundaries/reorgs, and the code path is explicitly documented as depending on this height-based conflict query to substitute for a check that intentionally does not re-run.

### Recommendation
In `handle_block_pre_commit`, the own-tenure duplicate check must not be height-bounded by the candidate block's own `chain_length`. Add an explicit re-check equivalent to `DuplicateBlockFound` — i.e., re-run (or directly query) whether this signer has already signed *any* block in the same tenure (`get_last_signed_block(&block.header.consensus_hash)`/`get_last_globally_accepted_block`) independent of height, for tenure-change (`BlockFound`) proposals, before signing. Alternatively, extend `get_signed_conflicts` (or add a dedicated query) to also return same-`consensus_hash` signed blocks regardless of height so the freshness/conflict-resolution logic in `handle_block_pre_commit` can correctly refuse or resolve the duplicate.

### Proof of Concept
1. Miner produces tenure T with parent tenure P currently at height 9. It proposes tenure-start block A for T, confirming P at height 9 (A.chain_length = 10). Signer validates A, pre-commits, crosses threshold, and signs A (`signed_self` set, stored in `signerdb` at `stacks_height = 10`).
2. Before A is finalized/globally accepted, the miner mines an additional block in parent tenure P (P now at height 10), then proposes a second tenure-start block B for the **same tenure T** (same `consensus_hash`), this time with `previous_tenure_end` pointing to P's new height-10 block (B.chain_length = 11).
3. At proposal time, `validate_tenure_change_payload` would reject B with `DuplicateBlockFound` — but suppose B's proposal validation happens to race the point where A is signed (B is validated/pre-committed before A's `signed_self` timestamp is recorded), matching the same race pattern the existing sibling tests already exercise (`stacks-signer/src/v0/tests.rs::run_sibling_scenario`).
4. Once B crosses the pre-commit threshold, `handle_block_pre_commit` calls `check_block_against_signer_db_state` (passes — it only checks confirms-parent against P, which is satisfied) and then `get_signed_conflicts(11, B_hash)`. Because A's `stacks_height` is 10 (< 11), the query returns no conflicts.
5. The signer proceeds to `mark_locally_accepted` and signs B, even though it already signed A — a different, conflicting first block for tenure T. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

    fn validate_tenure_change_payload(
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        parent_tenure_id: &ConsensusHash,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        config: &ProposalEvalConfig,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the signer's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            config.tenure_last_block_proposal_timeout,
            config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }

        // reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count

            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";

                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }

Order matters here: the chainstate re-check runs first and produces an explicit
(sticky) rejection when the block now conflicts with a signed one. The conflict
guard behind it is the silent backstop for what that re-check cannot see, and
silence keeps the door open to sign later once the conflict goes stale. Two
blind spots make the guard necessary:

- the re-check only ever looks at _one_ tenure (a tenure-change block's parent,
  or any other block's own), so a signed sibling at the same height in a third
  tenure is invisible to it;
- the `DuplicateBlockFound` check that would catch a second block in the same
  tenure lives in `check_proposal` and runs only at proposal arrival, never
  again. A block that crosses the pre-commit threshold minutes later has no
  other guard, which is what the own-tenure branch above covers.
