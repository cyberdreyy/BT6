### Title
`B20Variant::compute_address_from_hash` truncates keccak256 to a 72-bit tail, making B-20 token address collisions orders of magnitude more feasible than a standard 160-bit birthday attack - (File: crates/common/precompiles/src/b20_factory/variant.rs)

### Summary
The `B20Factory` precompile derives every B-20 token's contract address deterministically from `keccak256(creator, salt)`, but instead of using the standard 160-bit address space it truncates the hash to only a **9-byte (72-bit) tail**, with the remaining 11 bytes fixed to a constant prefix/discriminant. This collapses the collision-resistance of the address space from the already-marginal `2^80` birthday bound discussed in the referenced report down to roughly `2^36`, a workload trivially achievable on commodity hardware rather than requiring a multi-million-dollar ASIC farm.

### Finding Description
`B20Variant::compute_address_from_hash` builds the 20-byte token address as `PREFIX_BYTE(1) || zeros(9) || discriminant(1) || tail(9)`, where `tail` is just the first 9 bytes of `keccak256(creator, salt)`: [1](#0-0) 

Compare this to a normal CREATE2/CREATE address, which embeds a full 160-bit hash output. Here only 72 bits of entropy determine the address, so by the birthday bound an attacker needs only about `sqrt(2^72) ≈ 2^36` (~6.9×10^10) `keccak256` evaluations — computable by an attacker-controlled `caller` grinding over `salt` values, since `createB20` uses `ctx.caller()` and an attacker-supplied `salt` as the hash preimage — to find two `(creator, salt)` pairs whose derived token addresses collide: [2](#0-1) 

The factory's only defense against a collision is an "already deployed" check keyed on the account's code hash: [3](#0-2) 

This makes `createB20` a reachable, unprivileged precompile entrypoint (any transaction sender or contract can call it) whose deterministic-address derivation has far weaker collision resistance than the 160-bit scheme the original report already flagged as a Medium-severity, multi-year, multi-million-dollar risk.

### Impact Explanation
Because `getB20Address` lets any caller pre-compute a future token's address off-chain before `createB20` is called: [4](#0-3) 

an attacker can grind `salt` values (keeping `creator = attacker`) to find a colliding `(creator, salt)` pair that lands on the same 72-bit tail as a legitimate, not-yet-created token address a victim contract/user has already computed and is relying on (e.g. for pre-funding, approvals, or off-chain bookkeeping). The attacker can then front-run the legitimate `createB20` call, deploying their own attacker-controlled B-20 token (with attacker-chosen `initialAdmin`, roles, and `initCalls`) at that exact address. The legitimate creator's later `createB20` call reverts with `TokenAlreadyExists`, permanently denying them that address and potentially misdirecting any value or trust a victim placed in the precomputed address to an attacker-controlled contract instead.

### Likelihood Explanation
Unlike the ~`2^80` birthday attack in the referenced report — estimated to cost ~$4.6M in specialized ASIC hardware and energy over two years — a `2^36`-class collision search is achievable with ordinary GPUs in a short, inexpensive computation, since only 9 bytes of hash output need to match. This makes the attack practical today for any unprivileged caller of the `B20Factory` precompile, not merely a theoretical future risk.

### Recommendation
Do not truncate the address-derivation hash to 9 bytes. Either embed the full 160-bit `keccak256(creator, salt)` output (matching standard CREATE2-style derivation) as the token address, or, if a fixed structural prefix identifying B-20 tokens is required, retain at least the full remaining ~152 bits of hash entropy rather than reducing to 72 bits, so the birthday/preimage bound stays consistent with the security margin expected of other address-derivation schemes in the codebase (e.g. the 256→160-bit CREATE2 derivation used elsewhere in `crates/execution/eip8130/src/apply.rs`).

### Proof of Concept
1. `B20Variant::compute_address_from_hash` is called from `create_b20`'s `route` handler with `hash = keccak256((caller, salt).abi_encode())`, and only `hash[..9]` (72 bits) determines the resulting token address's non-fixed bytes: [5](#0-4) .
2. An attacker (as `caller`) enumerates ~`2^36` `salt` values off-chain, computing `compute_address` for each, and checks for a match against any target address of interest (e.g. one returned by a victim's earlier `getB20Address` call, or against each other for a birthday-style self-collision) — a workload feasible on a single modern GPU.
3. Upon finding a colliding `salt`, the attacker calls `createB20` first with their own malicious `params`/`initCalls`, causing `set_code` to install attacker-controlled bytecode at the shared address: [6](#0-5) .
4. The legitimate party's subsequent `createB20` call for the same intended address now reverts with `TokenAlreadyExists`, confirming the address was captured by the attacker instead.

    /// Computes this variant's deterministic token address for `creator` and `salt`.
    ///
    /// Returns the address and the 9-byte hash tail embedded in the address.
    pub fn compute_address(self, creator: Address, salt: B256) -> (Address, [u8; 9]) {
        let hash = keccak256((creator, salt).abi_encode());
        self.compute_address_from_hash(hash)
    }

    /// Computes the deterministic token address from a pre-computed `keccak256(creator, salt)` hash.
    ///
    /// Use when the hash is already available (e.g. after charging keccak gas via `ctx.metered_keccak256`)
    /// to avoid re-encoding and re-hashing.
    pub fn compute_address_from_hash(self, hash: B256) -> (Address, [u8; 9]) {
        let mut tail = [0u8; 9];
        tail.copy_from_slice(&hash[..9]);

        let mut addr_bytes = [0u8; 20];
        addr_bytes[..11].copy_from_slice(&self.address_prefix());
        addr_bytes[11..].copy_from_slice(&tail);

        (Address::from(addr_bytes), tail)
    }
