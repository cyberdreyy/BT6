### Title
Instant-withdraw claims ignore the funded/pending split and can drain cash earmarked for other claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays the user's *aggregate* `instantWithdrawsRequests[_user]` balance at par from the strategy's underlying balance, without checking how much of the instant queue has actually been funded via `collectInstantWithdrawFunds` (`pendingInstantWithdraws`). When the CDO's available cash at `startEpoch` covers only part of the instant queue — a state the code explicitly acknowledges ("cash covered only part of the instant queue") — claims are effectively first-come-first-served against a shared, under-funded pot. An attacker can front-run honest claimants and withdraw receipts whose funding was never collected, leaving later claimants' funded shares permanently short. This is the same bug class as the consensus.State race: a claim path consumes shared state without observing the funded-vs-unfunded transition state.

### Finding Description
In `IdleCreditVault.claimInstantWithdrawRequest`, the claim logic is:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [1](#0-0) 

`_transferFundedClaim` only guards the `defaultRecoveryReserve` isolation invariant; it does not check `pendingInstantWithdraws` or compare the strategy's cash balance against the still-unfunded remainder of the queue. [2](#0-1) 

Funding is tracked separately: `requestInstantWithdraw` increases `pendingInstantWithdraws`, and `collectInstantWithdrawFunds` is the only function that decreases it, pulling cash from the CDO. [3](#0-2) [4](#0-3) 

The code itself documents that the instant queue can be only partially funded — `_defaultPrefundedInstantReserve` exists precisely because `instantWithdrawClaimsByEpoch[epochNumber]` can exceed `pendingInstantWithdraws`'s complement, i.e. collected cash covers only part of the queue. [5](#0-4) 

A user can also hold receipts across multiple epochs: `instantWithdrawsRequestsByEpoch` accumulates per epoch while `instantWithdrawsRequests[_user]` aggregates them, and the normal claim path never decrements `instantWithdrawClaimsByEpoch` or `pendingInstantWithdraws` (unlike `_claimDefaultedInstantWithdrawRequest`, which does). [6](#0-5) 

So when `pendingInstantWithdraws > 0` (queue underfunded), the first user to call `claimInstantWithdrawRequest` through the CDO is paid their full aggregate — including the unfunded current-epoch portion — out of cash collected for the whole queue. Honest users' receipts then revert on insufficient balance until more funding arrives, and if the epoch sequence moves on without topping up, the shortfall is permanent.

### Impact Explanation
Direct theft / freezing of other users' withdrawal proceeds. The attacker needs only to be a KYC'd tranche holder: request an instant withdrawal in epoch N (possibly combined with an older already-funded receipt to enlarge the aggregate), then claim immediately when epoch N+1 starts and only partial instant liquidity was moved. The attacker receives underlyings pro-rata belonging to other instant claimants; victims' `claimInstantWithdrawRequest` calls revert on `safeTransfer` underflow and their receipts can remain frozen if no further funding materializes. Loss equals the underfunded instant balance drained ahead of honest claimants (bounded by the attacker's deposit, but the attacker only risks their own principal which is returned anyway).

### Likelihood Explanation
Moderate. It requires a partially funded instant queue, which the code acknowledges occurs when CDO cash at `startEpoch` covers only part of `pendingInstantWithdraws`. No privileged misbehavior is needed — honest `startEpoch`/`collectInstantWithdrawFunds` sequencing suffices. The attacker must be able to request instant withdrawals (instant mode enabled, KYC'd) and win the claim ordering, which is trivially achievable via gas priority in the same block the delay elapses. Uncertainty: whether the CDO-side `claimInstantWithdrawRequest` wrapper adds additional gating beyond the delay flag was not fully verified; if it also blocks claims while `pendingInstantWithdraws` exceeds collected funds, the window narrows but does not disappear for multi-epoch aggregate receipts, since the per-epoch ledgers are never decremented on the normal claim path.

### Recommendation
In `claimInstantWithdrawRequest`, cap the payable amount at the funded portion: track a funded-balance counter (or reuse `pendingInstantWithdraws` / per-epoch funded shares) and pay each user at most `min(theirReceipt, fundedShare)`, mirroring how `_claimDefaultedInstantWithdrawRequest` decrements `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch`. Also decrement `instantWithdrawClaimsByEpoch` and the pending bucket on the normal claim path for consistency, and revert (or pay pro-rata) when the strategy's claimable cash is below the requested amount rather than draining the shared pot FIFO.

### Proof of Concept
Foundry fork sketch (mainnet fork per `foundry.toml`, using the existing test scaffolding in `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testInstantClaimDrainsUnfundedShare() external {
    // Setup: standard epoch variant, instant withdrawals enabled
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18); // epoch 0 -> epoch 1
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    uint256 amount = 100e6;
    address attacker = makeAddr('attacker');
    address victim = makeAddr('victim');

    uint256 tA = _depositWithUser(attacker, amount);
    uint256 tV = _depositWithUser(victim, amount);

    vm.prank(manager);
    cdoEpoch.startEpoch();

    // Both request instant withdrawals in epoch 1
    _requestInstantWithdraw(attacker, tA); // cdoEpoch.requestInstantWithdraw path
    _requestInstantWithdraw(victim, tV);

    // stopEpoch triggers instant mode; startEpoch moves only PARTIAL cash
    // (simulate liquidity constraint: borrower returns less than pendingInstantWithdraws)
    _stopCurrentEpochWithApr(1e18);
    uint256 pending = strategy.pendingInstantWithdraws();
    // fund only half
    deal(underlying, address(cdoEpoch), pending / 2, true);
    vm.prank(manager);
    cdoEpoch.startEpoch(); // collects only pending/2 into strategy

    skip(101); // instant delay passes

    // Attacker claims first: receives FULL aggregate even though queue is underfunded
    uint256 pre = IERC20Detailed(underlying).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(IERC20Detailed(underlying).balanceOf(attacker) - pre, tA,
        'attacker paid at par from shared underfunded pot');

    // Victim's identical funded claim now reverts on underflow / shortfall
    vm.expectRevert();
    vm.prank(victim);
    cdoEpoch.claimInstantWithdrawRequest();
}
```

Key assertion: `strategy.pendingInstantWithdraws()` remains non-zero after the attacker's claim (the normal path never decrements it), proving the attacker consumed funding earmarked for the victim's receipt rather than their own collected share.

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
