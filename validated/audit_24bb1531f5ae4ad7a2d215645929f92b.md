## Finding: Stale rejection weight is never retracted when a signer flips to acceptance, letting `total_weight_rejected` and `total_weight_approved` double-count the same signer

### Title
Miner-side signer response tally double-counts a signer's weight across reject→accept transitions, letting stale rejection weight falsely trigger `SignersRejected` on an otherwise-approved block - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The external report's bug class is: a critical threshold check depends on an accumulator that outside activity can push into a permanently-wrong state, defeating the intended guard. The direct analog here is in the node-side `StackerDBListener`'s `BlockStatus` tally: `total_weight_approved` and `total_weight_rejected` are two independently-incremented, monotonically-growing counters that are never reconciled against each other when a signer changes its vote.

### Finding Description
`BlockStatus` tracks per-block tallies via two collections: `gathered_signatures` (accept) and `responded_signers` (shared "has responded" set used by both accept and reject paths), defined at [1](#0-0) .

On `BlockResponse::Accepted`, weight is added to `total_weight_approved` only if the slot is not already in `gathered_signatures`, and the slot is then inserted into both `gathered_signatures` and `responded_signers`: [2](#0-1) .

On `BlockResponse::Rejected`, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (first response ever), and it is **never removed** afterward: [3](#0-2) .

Consider the order reject → accept for the same signer/slot on the same block:
1. Reject arrives first: `responded_signers.insert(slot_id)` → `true`, so `total_weight_rejected` gains that signer's weight.
2. The signer later reconsiders (a legitimate, documented flow — "repeat my earlier answer unless the reason I rejected has since gone away") and sends `Accepted` for the same block.
3. On accept: `gathered_signatures.contains_key(&slot_id)` is `false` (it was never populated by the reject path), so `total_weight_approved` gains that signer's weight too. `responded_signers.insert(slot_id)` now returns `false` (no-op), so nothing in the reject path is retracted.

The result: the same signer's weight is now counted in *both* `total_weight_rejected` and `total_weight_approved` simultaneously, and `total_weight_rejected` for that block can never be reduced. The signer-side code demonstrates that this reconciliation is understood to be necessary elsewhere: `SignerDb::add_block_signature` explicitly deletes any prior rejection record for that signer/block before recording the new signature, precisely to prevent an accept and a stale reject from coexisting: [4](#0-3) . The node-side `StackerDBListener` tally has no equivalent cleanup.

### Impact Explanation
This breaks the "aggregated-weight vs verified-accepts" equality: `total_weight_rejected` no longer reflects the *current* set of signers refusing the block, only the historical union of everyone who ever rejected it, even after they flipped to accept. `SignerCoordinator::get_block_status` checks the rejection threshold before the acceptance threshold in its polling loop: [5](#0-4) . If enough weight (>30%, the "blocking minority") transiently rejects a block (e.g. due to a stale-conflict window described in the signer flow docs) and then reconsiders to accept once the transient condition clears, the miner can still see `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and return `SignersRejected`, discarding a block that in reality has legitimate ≥70% acceptance weight. This is a liveness wedge on block production/consensus tallying at the node/coordinator layer explicitly in scope (`signer_coordinator.rs`, `stackerdb_listener.rs`), not merely a cosmetic log discrepancy, since it directly gates the `Ok`/`Err` outcome the miner acts on.

### Likelihood Explanation
No majority of signers, no signer private key, and no auth token are needed by the triggering party — this is purely a property of the miner-side tally logic and is exercisable by the normal reconsideration behavior already documented for the signer (`should_reevaluate_reject_reason`), which a miner can deliberately provoke by choosing proposal/re-proposal timing (e.g. around burn-chain forks or conflict staleness windows) to make ≥30% weight of signers reject-then-accept the same block hash.

### Recommendation
When processing `BlockResponse::Accepted` for a signer slot, remove that slot's prior contribution from `total_weight_rejected` (and vice versa for `Rejected` arriving after `Accepted`, if that transition is ever considered valid), mirroring the reconciliation `SignerDb::add_block_signature` already performs on the signer side. Alternatively, track the tally by iterating a single `HashMap<slot_id, Vote>` and recomputing `total_weight_approved`/`total_weight_rejected` from the current per-signer vote map rather than maintaining two independently-incrementing counters.

### Proof of Concept
1. Node proposes block `B`; signer `S` (weight `w`, where `w` alone or combined with other rejecters exceeds 30% of total weight) sends `BlockResponse::Rejected` for `B` (e.g., due to a transient chainstate conflict). `total_weight_rejected += w`.
2. The conflict condition becomes stale/resolved (per the signer's own reconsideration logic); `S` now sends `BlockResponse::Accepted` for the same `B`. `total_weight_approved += w` (since `gathered_signatures` never had `S`'s slot).
3. `total_weight_rejected` still includes `w` from step 1 — it was never decremented.
4. If the cumulative stale-rejected weight from step 1 (across `S` and any other signers who behaved the same way) exceeds the blocking-minority threshold, `SignerCoordinator::get_block_status` returns `Err(SignersRejected { .. })` even though the current, live vote count would satisfy `total_weight_approved >= weight_threshold`.
