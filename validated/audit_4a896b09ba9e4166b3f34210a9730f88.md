### Title
Multisig requests can execute below the required confirmation threshold because stale confirmations from deleted members are never purged - ([File: multisig2/src/lib.rs])

### Summary
`MultiSigContract::confirm` counts the size of the `confirmations` `HashSet<String>` for a request to decide whether `num_confirmations` has been reached, but `delete_member` only purges requests that were *originated* by the removed member - it never scans other pending requests to strip out confirmations that the removed member previously cast as a *confirmer*. A request can therefore be executed once its confirmation set reaches `num_confirmations` in size even though one (or more) of those confirmations belongs to an account/key that is no longer a member, i.e. it executes with fewer *live* confirmers than the configured threshold.

### Finding Description
`confirm()` only checks that the *current* signer hasn't already confirmed, then compares the confirmation-set length to the threshold: [1](#0-0) 

It never re-validates that every entry already stored in `confirmations` still corresponds to a member in `self.members`.

`delete_member` is the only place that scrubs stale state, but it filters requests by `r.member == member`, which is the field recording who *created* the request, not who has *confirmed* it: [2](#0-1) 

Because of this, if member `B` confirms request `R` (created by `A`), and `B` is later deleted from the multisig via a separate `DeleteMember` request, `R`'s confirmation set still contains `B`'s identity string. `R` was not touched by `delete_member` because `R.member == A`, not `B`. The invariant that should hold is:

```
counted_confirmations(request) == |{ m ∈ confirmations(request) : m ∈ current_members }|
```

but after a member deletion this can become false: `counted_confirmations(request) > |live confirmers|`. A subsequent legitimate confirmation from any remaining live member can push `confirmations.len() + 1 >= num_confirmations` and trigger `execute_request`, even though the number of *currently valid* members who approved is strictly less than `num_confirmations`.

### Impact Explanation
This breaks the "multisig request executed below threshold" custody binding explicitly called out as Critical impact: a `Transfer`, `AddKey`, `FunctionCall`, or any other privileged action can be executed by the multisig account with fewer live approvals than the configured `k`-of-`n` threshold, effectively lowering the security threshold of the account without anyone noticing, and can be used to move funds (`MultiSigRequestAction::Transfer`) out of the multisig-controlled account with insufficient live authorization.

### Likelihood Explanation
This requires no attacker privilege beyond ordinary multisig operation: it can occur any time a request is partially confirmed, and later one of its confirmers is removed via a normal `DeleteMember` action (a routine key-rotation/off-boarding event), followed by one more live member confirming the original pending request. No malicious member collusion, redeploy, or external access is needed - it is a latent bug in bookkeeping that will surface during normal member turnover.

### Recommendation
When deleting a member, iterate over **all** pending requests' confirmation sets (not just requests they created) and remove the deleted member's identity from each. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set to only those entries still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. `A` calls `add_request_and_confirm(R)` where `R` is `Transfer { amount, receiver_id: attacker }` → `confirmations(R) = {A}`.
3. `B` calls `confirm(R)` → `len == 2 < 3` → `confirmations(R) = {A, B}`.
4. Separately, `A`, `C`, `D` confirm and execute a `DeleteMember { member: B }` request (3 confirmations, satisfying the threshold) — this removes `B` from `self.members`, but `R` is untouched since `R`'s creator field is `A`, not `B`; see `delete_member` filter at [3](#0-2) .
5. `C` calls `confirm(R)` → `confirmations(R).len() (2) + 1 >= 3` → `execute_request(R)` runs the `Transfer` to the attacker, even though the live confirmers on `R` are only `A` and `C` (2 < 3).

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
