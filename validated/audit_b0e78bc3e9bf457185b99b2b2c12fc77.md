### Title
Node-side StackerDB vote tally never retracts a stale rejection when a signer later accepts, letting stale reject-weight wedge a legitimately-supported block — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The PrestaShop advisory is about state being mutated via a replayed/out-of-order request without re-validating context (path traversal via a stale/crafted delete path). The structural analog here is a **replayed vote from the same signer being applied to the wrong bucket without invalidating the earlier one** — the miner-side StackerDB listener's live vote tally treats `Accepted` and `Rejected` `BlockResponse`s from the same signer as independent, additive events instead of mutually-exclusive, latest-wins votes, unlike the equivalent logic that already exists (and is tested) in `SignerDb`.

### Finding Description
`stacks-signer/src/signerdb.rs` enforces a clean invariant for the same signer flipping their vote on the same block: `add_block_signature` clears out any prior rejection for that signer once they sign, and vice versa. This is explicitly tested: [1](#0-0) 

The node-side tally used by the mining coordinator to decide whether a proposed block was accepted or blocked, in `StackerDBListener`, does **not** replicate this invariant. `BlockStatus` tracks `total_weight_approved`, `total_weight_rejected`, `gathered_signatures` and `responded_signers` as independent counters: [2](#0-1) 

When a `Rejected` response arrives first, the signer's weight is added to `total_weight_rejected` and their slot is recorded in `responded_signers`: [3](#0-2) 

If the *same* signer later re-evaluates the identical block (same `signer_signature_hash`) and sends `Accepted` — a fully legitimate, single-signer, non-adversarial event documented in the signer's own re-evaluation flow (`should_reevaluate_reject_reason`, section 3 of `docs/signer-flows.md`) — the accept path checks only `gathered_signatures`, not `responded_signers`, before crediting weight: [4](#0-3) 

Since `gathered_signatures` does not yet contain this slot, the full weight is added to `total_weight_approved` **on top of** the weight already sitting in `total_weight_rejected` from the earlier rejection — the earlier rejection is never subtracted or cleared. The same signer's weight is now double-counted across both opposing totals, and `total_weight_approved + total_weight_rejected` can exceed `total_weight`.

The consuming loop in the coordinator checks the rejection condition before the acceptance condition: [5](#0-4) 

Because the stale rejection weight is never retracted, `total_weight_rejected` can remain permanently inflated by weight belonging to a signer who has since switched to acceptance, so the coordinator can conclude `NakamotoNodeError::SignersRejected` (block blocked) for a proposal that in fact has (or would reach) sufficient live acceptance weight.

### Impact Explanation
This breaks the aggregated-weight vs. verified-accepts equality explicitly called out as in-scope: the coordinator's rejection/acceptance decision is driven by weight sums that no longer reflect each signer's current, single vote. Because the reject-branch check runs first in `wait_for_block_acceptance` (`signer_coordinator.rs`), a stale/retracted rejection can cause the coordinator to treat an actually-supported block as globally rejected, wedging that tenure's block production and forcing the miner to abandon and re-mine — a liveness impact reachable by ordinary vote-flip traffic from a single signer, requiring no majority collusion, no key compromise, and no auth token.

### Likelihood Explanation
The trigger condition — a signer initially rejecting a proposal (e.g. `SortitionViewMismatch`, `ConnectivityIssues`, or any reevaluable reject reason) and then later reconsidering and accepting the *same* block bytes on a re-proposal — is a documented, intended part of the signer's own state machine (`should_reevaluate_reject_reason`, `docs/signer-flows.md` section 3). It requires only one signer's ordinary behavior plus the miner re-broadcasting the identical proposal, both of which are normal operational conditions, not an attack requiring majority control.

### Recommendation
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, make the `Accepted`/`Rejected` handling mutually exclusive per signer slot, mirroring `SignerDb::add_block_signature`/`add_block_rejection_signer_addr`: before crediting an acceptance, check whether the slot is already present in the rejection-contributing set and subtract its weight from `total_weight_rejected` (and symmetrically guard/clear on the reject path if a signature already exists, consistent with the "signatures are irrevocable" design documented in `signerdb.rs`). Track rejecting slots (not just an aggregate counter) so weight can be correctly retracted when a signer's final vote changes.

### Proof of Concept
1. Miner proposes block B; signer S initially rejects it (e.g. transient `ConnectivityIssues` or `SortitionViewMismatch`), and its `BlockResponse::Rejected` reaches the node — `total_weight_rejected += weight(S)`, `responded_signers.insert(S)`.
2. The condition causing S's rejection resolves (per `should_reevaluate_reject_reason`), and S re-evaluates and re-sends `BlockResponse::Accepted` for the identical `signer_signature_hash` of B.
3. In `stackerdb_listener.rs`, `gathered_signatures` does not yet contain S's slot, so `total_weight_approved += weight(S)` is applied — S's weight now counts in both `total_weight_rejected` and `total_weight_approved` simultaneously, and `total_weight_rejected` is never decremented.
4. If other signers' rejection weight, combined with S's stale rejection weight, crosses the blocking-minority threshold in `signer_coordinator.rs` (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`), the coordinator returns `NakamotoNodeError::SignersRejected` even though S's current, live vote is acceptance — wedging a block that in reality may have (or be close to) sufficient live support.
