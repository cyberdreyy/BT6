### Title
Masker chain built in caller-supplied order instead of phrase length, allowing shorter masked value to fragment and partially expose a longer masked value that contains it as a substring - (File: common/buildlogger/internal/masker/masker.go)

### Summary
`masker.New` documents that per-phrase writers "are stacked ... in length order, starting with the longest," but the implementation simply iterates `phrases` in the order given and stacks them without any length-based sort. If the caller-provided `MaskPhrases` slice happens to place a shorter phrase (e.g. `secret`) after a longer phrase containing it as a prefix (e.g. `secret_suffix`), the shorter phrase's masker layer becomes the outermost layer in the write chain and consumes/replaces the substring before the longer phrase's masker ever sees the full byte sequence, causing the longer secret to be split into `[MASKED]` + the unmasked remainder.

### Finding Description
`masker.New` (common/buildlogger/internal/masker/masker.go:27-37) builds the writer chain as:
```go
m.next = w
for i := 0; i < len(phrases); i++ {
    m.next = &masker{next: m.next, phrase: phrases[i]}
}
``` [1](#0-0) 

Because each new masker wraps the previous `m.next`, the *last* element of `phrases` ends up as the outermost writer (the first to see incoming bytes via `Masker.Write` → `m.next.Write`), and the *first* element ends up closest to the underlying writer `w` (processed last). This is the opposite of, and unrelated to, the "longest first" ordering promised in the package doc comment at the top of the file: [2](#0-1) 

There is no sort by `len(phrase)` anywhere in `New`, and `internal.Unique` (called from `Logger.New` in common/buildlogger/build_logger.go) only deduplicates entries, preserving whatever order the CI variable resolution produced.

When the outer (shorter) phrase masker matches a substring inside the longer phrase's text, its per-write state machine completes the match, calls `m.Write(mask)` to emit `[MASKED]` immediately to the next writer, and then continues scanning the remainder of the buffer as ordinary bytes (masker.go:96-111). The `[MASKED]` token and the leftover bytes (e.g. `_suffix`) are sent to the inner (longer-phrase) masker as two separate `Write` calls; the inner masker's fast path forwards `[MASKED]` untouched (masker.go:62-64) and treats `_suffix` as unrelated data, so it can never reconstruct or mask the original full phrase. The final logger output contains `[MASKED]_suffix` instead of a single `[MASKED]` covering the whole secret value, leaking the suffix portion of the longer secret in plaintext.

This is directly reachable: `Logger.wrap` builds the mask chain via `masker.New(w, l.maskPhrases)` for every build log stream (common/buildlogger/build_logger.go:220), and `l.maskPhrases` is derived from job variables marked as masked. A pipeline author who defines two masked CI/CD variables where one value is a substring/prefix of the other (e.g., a masked `secret_suffix` value and a masked `secret` value) controls both the phrase content and, indirectly through variable definition/resolution order, the order they are appended into the `MaskPhrases` slice passed to `masker.New`.

Existing protections do not stop this: there's no ordering/sorting safeguard in `New`, no length-based prioritization, and no post-write verification that all masked phrases are absent from output (that check exists only in the fuzz test file, not at runtime).

### Impact Explanation
When two masked values share a prefix/substring relationship and the shorter one is ordered after the longer one in the slice passed to `masker.New`, the longer secret's suffix (or any part following the shared prefix) is emitted in cleartext into the job trace/log, which is visible to anyone who can view that build log. This is a genuine, scoped exposure of protected (masked) values, matching the "Secret masking ... exposes protected values" impact category.

### Likelihood Explanation
Preconditions are fully attacker-controllable within normal CI authoring: any project maintainer or pipeline author can define two masked variables such that one value is a prefix of the other (e.g., `SECRET=foo` and `SECRET_TOKEN=foosuffix`, both marked "Masked" in CI/CD variable settings, or simply reused/derived values). The exploit does not require any privileged action beyond normal masked-variable configuration, and the resulting log fragment will reliably occur whenever such a slice ordering places the shorter phrase later than the longer, overlapping phrase - this is not a rare race but a deterministic function of the order variables are gathered/passed to `l.maskPhrases`, over which the implementation provides no correctness guarantee.

### Recommendation
Sort `phrases` by descending byte length (and, for equal lengths, deterministically, e.g. lexicographically) inside `masker.New` before constructing the writer chain, so that longer phrases are always checked before any shorter phrase that could be a prefix/substring of them, restoring the invariant documented in the package comment. Add a regression test in `masker_test.go` mirroring the fuzz test's post-write assertion (`bytes.Contains(contents, mask)` for every configured phrase) specifically for overlapping-phrase inputs regardless of input slice order.

### Proof of Concept
```go
func TestMasking_OverlappingPhrases_ShortAfterLong(t *testing.T) {
    buf := new(bytes.Buffer)
    w := masker.New(internal.NewNopCloser(nopWriteCloser{buf}), [][]byte{
        []byte("secret_suffix"), // longer phrase first in slice
        []byte("secret"),        // shorter phrase, substring of the above, added second
    })

    _, err := w.Write([]byte("value: secret_suffix end"))
    require.NoError(t, err)
    require.NoError(t, w.Close())

    got := buf.String()
    // Assert the full longer secret never leaks in fragments.
    require.NotContains(t, got, "_suffix", "longer masked phrase's suffix leaked due to masker stacking order")
    require.Equal(t, "value: [MASKED] end", got)
}
```
Expected current (buggy) result: output is `value: [MASKED]_suffix end`, failing the `NotContains` assertion and demonstrating partial secret disclosure caused by phrase-stacking order.

func New(w io.WriteCloser, phrases [][]byte) *Masker {
	m := &Masker{}
	m.next = w

	// Create a masker for each unique phrase
	for i := 0; i < len(phrases); i++ {
		m.next = &masker{next: m.next, phrase: phrases[i]}
	}

	return m
}
