## Finding

### Title
Legacy WebAPI capabilities handler allows callback hijacking via attacker-chosen, non-unique `message_id` - (File: core/services/gateway/handlers/capabilities/handler.go)

### Summary
`handler.HandleLegacyUserMessage` in the gateway's WebAPI capabilities handler stores each user's response callback in a shared map keyed solely by the client-supplied `message_id`, with no check that the ID is unique and no binding to the requesting sender. Any unprivileged client can choose an arbitrary `message_id` (bounded only by a length check), so a second request using the same ID silently overwrites the first request's callback entry, similar in nature to how the referenced Balancer bug used unchecked/malformed identifying data (`userData`) that broke the intended request/response linkage and left the original actor stuck.

### Finding Description
`Message.Validate()` only checks length/format of `Body.MessageId` — it never verifies uniqueness: [1](#0-0) 

In `HandleLegacyUserMessage`, the callback is inserted into `h.savedCallbacks` keyed purely by the attacker-controlled `msg.Body.MessageId`, with no existence check before the write: [2](#0-1) 

Contrast this with sibling handlers in the same codebase that explicitly guard against duplicate/attacker-chosen IDs, e.g. the vault handler: [3](#0-2) 
and the confidential-relay handler test asserting `"request ID already exists"` is rejected: [4](#0-3) 

The legacy capabilities `handler.go` has no such guard. When a node later responds, matching is done purely by `MessageId` via `handleWebAPITriggerMessage`: [5](#0-4) 

If two different unprivileged clients (or a malicious client racing a victim) submit legacy `web_api_trigger` requests with the same `message_id`, the second `HandleLegacyUserMessage` call silently replaces the first entry in `savedCallbacks`. Whichever callback occupies the slot when the DON node's response arrives receives that response — this can result in:
- The original client's request never receiving a response (their callback reference is lost, they hang until the connection/HTTP timeout), i.e., permanently "stuck" analogous to the cited report's trapped user.
- Or the attacker's callback erroneously receiving the response intended for another client (cross-user response confusion), if the attacker submits a colliding ID and the victim's node reply arrives while the attacker's entry is in place.

### Impact Explanation
This breaks the request/response integrity guarantee of the gateway callback path for an unprivileged (any authenticated DON-facing HTTP client) actor. It can cause silent request loss (client requests are simply dropped without an error response) and, more seriously, response payloads being delivered to the wrong caller because the map does not scope entries by sender/receiver.

### Likelihood Explanation
`message_id` is fully client controlled (subject only to a max length and no-trailing-null check) and there is no server-side uniqueness enforcement or sender binding on this legacy code path, so exploitation only requires an attacker to guess or predict an in-flight `message_id` (or race a known value) — no privileged access or protocol violation required.

### Recommendation
Scope `savedCallbacks` (and lookups in `handleWebAPITriggerMessage`) by `(sender, message_id)` similar to `core/services/gateway/handlers/common/requestcache.go`'s `globalId{sender, id}` pattern, and reject `HandleLegacyUserMessage` calls that reuse an in-flight ID for the same key, as is already done in the vault and confidentialrelay handlers.

### Proof of Concept
1. Client A sends a legacy `web_api_trigger` message with `message_id = "X"`; `HandleLegacyUserMessage` stores `savedCallbacks["X"] = callbackA` and forwards the request to DON nodes.
2. Before a node responds, Client B sends its own legacy message reusing `message_id = "X"`; this overwrites `savedCallbacks["X"] = callbackB` with no error.
3. When a DON node responds to Client A's original request with `MessageId = "X"`, `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers Client A's response to Client B.
4. Client A's callback is never invoked and hangs until its own timeout; Client B receives a response for a request it never made.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
