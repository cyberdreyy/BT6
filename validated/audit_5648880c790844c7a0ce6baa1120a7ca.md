### Title
Rejection weight double-counted as approval weight in miner-side block status tracking - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The Yield `Cauldron.stir` bug duplicated balances because a value was cached and then written back using a stale/incorrect guard when `from == to`. The analogous flaw here is a mismatched guard variable: the node's per-block signer-response tally uses two different tracking sets (`gathered_signatures` for acceptances and `responded_signers` shared across both branches) to decide whether a signer's weight has "already been counted," and the two branches don't consult each other consistently — allowing the same signer's weight to be added to both `total_weight_rejected` and `total_weight_approved` for the same block.

### Finding Description
In the `BlockResponse::Accepted` branch, the guard that prevents double counting is: [1](#0-0) 
This checks only `block.gathered_signatures.contains_key(&slot_id)` — i.e., whether *this* signer has previously *accepted*. It never checks `block.responded_signers`, even though `responded_signers` is the set that the rejection branch uses as its own de-duplication mechanism: [2](#0-1) 

Consequence: if a signer first sends a `Rejected` response for a block (inserted into `responded_signers`, and `signer_entry.weight` added to `total_weight_rejected`), and later sends an `Accepted` response for the *same* `block_sighash` with a valid signature, the accept branch sees `gathered_signatures` does **not** yet contain this `slot_id` (since it was never populated on the reject path), so it unconditionally adds `signer_entry.weight` to `total_weight_approved` as well. The signer's weight is now counted in both tallies simultaneously — the same "balance" (weight) has been duplicated across two accounting buckets instead of being moved from one to the other.

The reverse ordering (accept-then-reject) is correctly guarded, because the reject branch's `responded_signers.insert(slot_id)` returns `false` once the slot has already responded via the accept path — but the asymmetry means only one direction of the flip is protected.

This directly matches the report's `stir`-style duplication pattern: a value is conceptually "moved" from one bucket (rejected) to another (approved) upon a signer changing its vote, but because the two branches use non-overlapping state to detect "already counted," the old value is never subtracted, and the new value is added on top — duplicating the signer's weight.

### Impact Explanation
`total_weight_approved` and `total_weight_rejected` are consulted to decide whether the node has gathered enough distinct signer weight to broadcast a block or to abandon it: [3](#0-2) 
A single Byzantine signer (no majority required) can inflate `total_weight_approved` past the acceptance threshold using weight that legitimately belongs to a rejection, by simply sending a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash`. This can cause the miner/coordinator to believe the approval threshold has been reached with fewer genuinely-approving distinct signers than required, i.e., a rejection is effectively recounted as an acceptance contributing toward the broadcast decision — matching the "Critical: a rejection recounted as an accept" impact category.

### Likelihood Explanation
Triggering this requires only one malicious/misbehaving signer (not a majority) sending two ordinary, validly-signed `BlockResponse` messages (`Rejected` then `Accepted`) for the same block hash over StackerDB — well within a single signer's own key and message-signing capability, with no dependence on transport/StackerDB sync bugs, no need for another signer's key, and no auth-token or local access requirement.

### Recommendation
Use a single, unified "has this signer already responded to this block" set (e.g., `responded_signers`) as the sole gate for weight accounting in *both* branches, and make the accept/reject transition explicit: if a signer's response changes, subtract the previously-counted weight from the old bucket before adding it to the new bucket (or simply refuse to let a signer's vote flip after the first response is recorded, consistent with the existing changelog fix "Do not count both a block acceptance and a block rejection for the same signer/block" that was applied elsewhere but is missing here).

### Proof of Concept
1. Signer S (weight `w`) sends `BlockResponse::Rejected` for block hash `H`. `responded_signers` now contains S's slot; `total_weight_rejected += w`.
2. Signer S then sends `BlockResponse::Accepted` for the same hash `H`, signed validly.
3. In the accept branch, `block.gathered_signatures.contains_key(&slot_id)` is `false` (S never appeared in `gathered_signatures`), so the guard at lines 443-446 executes and `total_weight_approved += w`.
4. Now `w` has been added to both `total_weight_rejected` and `total_weight_approved` for the same block, from a single signer's two responses — the accounting invariant "each signer's weight counted at most once toward the final decision" is broken.
