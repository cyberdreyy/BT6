### Title
Write-off fulfiller can overpay underlying tokens above the requested amount and the excess is not refunded — (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`fullfillWriteOffRequest` accepts an arbitrary `_underlyings` amount and only checks that it is *not lower* than the lender's request. Any amount sent above `currentRequest.underlyings` is pulled from the fulfiller and split between the lender and the feeReceiver with no cap and no refund, so an unprivileged fulfiller who accidentally passes (or approves and transfers) more than intended permanently loses the excess.

### Finding Description
In `contracts/IdleCreditVaultWriteOffEscrow.sol:123-155`, the fulfilment check is a one-sided bound:

```solidity
// check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}
```

Then the full `_underlyings` is pulled from the caller and redistributed:

```solidity
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
uint256 _totFee = (_underlyings * _exitFee) / FULL_VALUE;
underlyingToken.safeTransfer(feeReceiver, _totFee);
underlyingToken.safeTransfer(_user, _underlyings - _totFee);
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

The fulfiller receives exactly `_tranches` tranche tokens regardless of how large `_underlyings` is — identical to the BVB `buyPosition` pattern where a caller sends more value than required, gets the same output as a caller paying the minimum, and has no way to recover the difference. The function "can be called by any wallet" (line 122), so the exposed party is an unprivileged actor, not the borrower. The comment's "borrower can choose to overpay if needed" is the only rationale for the open upper bound, but the check enforces overpayment capability on *every* fulfiller, including arbitrary third parties and fat-fingered EOA/multisig calls. There is no `==` equality option, no `maxUnderlyings` parameter, and no mechanism to return the excess. Epoch gating (`createWriteOffRequest` requires `isEpochRunning()`) does not mitigate this; fulfilment is allowed whenever a request exists.

### Impact Explanation
Direct, permanent loss of funds for the fulfiller. The excess `_underlyings - currentRequest.underlyings` is irrevocably transferred: ~`(excess * exitFee)/100_000` to `feeReceiver` and the rest to the lender `_user`, who receives a windfall beyond what they asked for. Loss is bounded only by the fulfiller's approved/balance amount and equals the full excess — e.g., a fulfiller intending to fill a 90,000 USDC request who passes 900,000 USDC loses ~809,100 USDC (after the 0.1% fee) while receiving the same tranche tokens.

### Likelihood Explanation
Likelihood is moderate: it requires a fulfiller (any wallet — keeper bots, liquidation desks, or the borrower acting through an unprivileged helper) to pass a larger `_underlyings` than the request, e.g., due to decimal confusion, copying a wallet balance instead of the request amount, or a frontend bug. The protocol deliberately exposes the unsafe bound rather than reverting on `!=`, which removes the natural guardrail present in exact-match fulfilment designs. No privileged actor needs to be involved or malicious.

### Recommendation
Change the check to exact equality, or add an explicit optional overpayment path:

```solidity
if (currentRequest.tranches != _tranches || _underlyings != currentRequest.underlyings) {
  revert WrongRequest();
}
```

If borrower overpayment is genuinely needed, gate it: `if (_underlyings != currentRequest.underlyings && msg.sender != borrower) revert WrongRequest();`, and/or cap the payout to the lender at `currentRequest.underlyings` and refund `safeTransfer(msg.sender, _underlyings - currentRequest.underlyings)` for the excess.

### Proof of Concept
Foundry PoC sketch (against an existing vault/epoch deployment or the repo's fork-test setup for `IdleCDOEpochVariant` + `IdleCreditVaultWriteOffEscrow`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {IdleCreditVaultWriteOffEscrow} from "../contracts/IdleCreditVaultWriteOffEscrow.sol";
import {IERC20Detailed} from "../contracts/interfaces/IERC20Detailed.sol";

contract WriteOffOverpayTest is Test {
    IdleCreditVaultWriteOffEscrow escrow; // deployed escrow for a running epoch
    IERC20Detailed underlying;
    IERC20Detailed tranche;
    address lender = address(0xA11CE);
    address fulfiller = address(0xF1FF);

    function testFulfillerOverpayNoRefund() public {
        // setup: epoch running, lender created request for 100 tranches -> 90_000e6 underlyings
        uint256 requested = 90_000e6;
        uint256 overpaid  = 900_000e6;

        deal(address(underlying), fulfiller, overpaid);
        vm.startPrank(fulfiller);
        underlying.approve(address(escrow), overpaid);
        uint256 tranchesReq = escrow.userRequests(lender) /* .tranches = 100e18 */;
        escrow.fullfillWriteOffRequest(lender, tranchesReq, overpaid); // typo: 900k instead of 90k
        vm.stopPrank();

        // fulfiller got the same 100e18 tranches they would have received paying 90k
        assertEq(tranche.balanceOf(fulfiller), tranchesReq);
        // lender received ~overpaid * (1 - exitFee) — a windfall ~10x their request
        assertGt(underlying.balanceOf(lender), requested);
        // fulfiller has 0 underlying left; excess is unrecoverable (no refund fn, owner-only emergencyWithdraw)
        assertEq(underlying.balanceOf(fulfiller), 0);
    }
}
```

The PoC shows the broken fair-exchange invariant: one receipt (the escrowed tranches) should map to the requested payout (`currentRequest.underlyings`), but the fulfiller's output is invariant to `_underlyings` while their cost is not, and the surplus is absorbed by the lender and `feeReceiver` with no recovery path.
