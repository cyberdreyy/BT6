### Title
Cancel/refund of an async deposit request permanently reverts (and locks user's escrowed principal) if the deposit token is paused - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2.cancelRequest` and `refundRequest` both unconditionally attempt to transfer the user's escrowed deposit token back out of the contract as part of clearing the request hash. If that token is a pausable/blacklistable asset and is paused at the moment the user tries to cancel or refund, the transfer reverts and — because the effects (unsetting the hash) happen before the transfer and there is no separate claim path — the whole transaction reverts, permanently freezing the user's escrowed tokens until the token is unpaused. This mirrors the root cause of M-12 (GMX): the cancel/refund path couples fund state cleanup with an unconditional token transfer, so a paused/blacklisted token blocks cancellation entirely.

### Finding Description
`requestDeposit` escrows the user's `tokensIn` in the Provisioner via `token.safeTransferFrom` [1](#0-0) . The user can later self-cancel via `cancelRequest`, or anyone with a legitimate deadline (or an authorized caller) can call `refundRequest`. Both paths ultimately call `_clearHashAndTransferRefund`, which unsets the async hash and then calls `_transferWithFallback` to send the escrowed token back: [2](#0-1) 

`_transferWithFallback` tries `token.trySafeTransfer` to the `receiver`, and if that fails (or `receiver == requester`) falls back to a plain `token.safeTransfer` to the `requester`. When the deposit token is *fully paused* (not merely blacklisting one address), both the try-transfer and the fallback `safeTransfer` revert, because the pause makes every transfer call fail regardless of destination. Since `safeTransfer` (unlike `trySafeTransfer`) does not swallow the revert, the entire `cancelRequest`/`refundRequest` transaction reverts.

The same pattern exists in the deposit-cancellation fee path of `cancelRequest`, which also does a direct `token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee)` before reaching the refund transfer [3](#0-2) , and in `_solveDepositVaultFixedPrice`/`_solveDepositVault` refund branches used when a deposit request's deadline has passed, which also call `_transferWithFallback` on the paused token [4](#0-3) .

There is no separate "claim" mechanism decoupled from the transfer (as recommended in M-12's fix suggestion); the hash is only unset atomically with the (reverting) transfer, so on revert the state simply never advances and the user cannot free their escrowed tokens by any code path while the token remains paused.

### Impact Explanation
User principal (the escrowed deposit token, e.g., a centrally pausable/blacklistable stablecoin) becomes temporarily but completely frozen in `ProvisionerV2` for the entire duration the token is paused: `cancelRequest`, `refundRequest`, and even solver-driven expiry-refund branches all revert, and there is no alternate withdrawal path for the escrowed tokens. This matches a live bounty "temporary freezing of user funds" (Medium) impact, since funds are recoverable only once the third-party token unpauses, but until then are fully inaccessible to the depositor.

### Likelihood Explanation
This requires only that (a) the vault's Provisioner accepts a token capable of a hard, non-address-specific pause (common stablecoin/asset patterns), and (b) the token happens to be paused while a user's async deposit request exists (before or after the request's deadline). No privileged role, oracle manipulation, or MEV is needed — an ordinary user (or the token issuer's routine compliance/pause action, entirely outside the protocol's control) triggers this. Given that async deposit flows are meant to sit in escrow for potentially long periods (until solved or the deadline passes), the window of exposure to any pause event by the token issuer is realistic.

### Recommendation
Decouple state clearing from the token transfer for the deposit refund/cancel path: mark the request as refundable/canceled (clearing the hash) independent of the transfer outcome, and let the user retry a dedicated "claim" call later, or use only `trySafeTransfer` with a stored pending-balance credit if both transfer attempts fail, instead of letting the failed `safeTransfer` in `_transferWithFallback` propagate and revert the whole cancel/refund.

### Proof of Concept
1. Deploy `ProvisionerV2` wired to a `MultiDepositorVault` and a mock ERC20 that supports `pause()`/`unpause()` and reverts all `transfer`/`transferFrom` calls while paused (mimic USDC-style pause).
2. Enable async deposits for the token via `setTokenDetails`, and enable `_depositCancellationsEnabled` via `setCancellationDetails`.
3. As user Alice, call `requestDeposit(token, tokensIn, minUnitsOut, 0, deadline, maxPriceAge, true)`, escrowing `tokensIn` into the Provisioner.
4. As the token admin, call `token.pause()`.
5. As Alice, call `cancelRequest(token, request)` — assert it reverts (bubbling the paused-token revert reason), even though `_depositCancellationsEnabled` is `true` and Alice is the legitimate request owner.
6. Assert `asyncRequestHashes[requestHash]` is still `true` and Alice's `tokensIn` remain stuck in the Provisioner with no way to retrieve them (also assert `refundRequest` reverts identically after `deadline` passes).
7. Call `token.unpause()` and show `cancelRequest` now succeeds, confirming funds were frozen strictly for the pause duration.

    function cancelRequest(IERC20 token, RequestV2 calldata request) external nonReentrant {
        // Requirements: self-cancel caller must be request user
        require(msg.sender == request.user, Aera__CallerIsNotRequestUser());

        if (_isRequestTypeDeposit(request.requestType)) {
            // Requirements: deposit cancellation toggle must be enabled
            require(_depositCancellationsEnabled, Aera__DepositRequestCancellationDisabled());

            uint256 refundAmount = request.tokens;
            // Requirements: pre-deadline self-cancel applies cancellation fee
            if (block.timestamp < request.deadline) {
                uint256 cancellationFee = _computeDepositCancellationFeeTokens(token);
                // Requirements: cancellation fee cannot exceed escrowed amount
                require(cancellationFee <= refundAmount, Aera__CancellationFeeExceedsRequestAmount());
                if (cancellationFee != 0) {
                    unchecked {
                        // unchecked: safe because cancellationFee <= refundAmount is enforced above
                        refundAmount -= cancellationFee;
                    }
                    // Interactions: transfer cancellation fee to vault
                    token.safeTransfer(MULTI_DEPOSITOR_VAULT, cancellationFee);
                }
            }

            // Effects + interactions: clear hash, emit refund event, and transfer net token amount with fallback
            _clearHashAndTransferRefund(token, request, msg.sender, refundAmount, token);

    function _clearHashAndTransferRefund(
        IERC20 token,
        RequestV2 calldata request,
        address requester,
        uint256 amount,
        IERC20 transferToken
    ) internal {
        bytes32 requestHash = _getRequestHash(token, request);
        // Requirements: hash has been set
        require(asyncRequestHashes[requestHash], Aera__HashNotFound());
        // Effects: unset hash as used
        asyncRequestHashes[requestHash] = false;
        // Interactions: transfer amount to receiver, fallback to requester on transfer failure
        _transferWithFallback(transferToken, requester, request.receiver, amount);

        // Log refund event
        if (_isRequestTypeDeposit(request.requestType)) {
            emit DepositRefunded(requestHash);
        } else {
            emit RedeemRefunded(requestHash);
        }
    }

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
