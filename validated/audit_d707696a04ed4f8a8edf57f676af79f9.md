### Title
Missing validation of `underlyingsRequested` lets a fulfiller seize escrowed tranche tokens for free - ([File: contracts/IdleCreditVaultWriteOffEscrow.sol](contracts/IdleCreditVaultWriteOffEscrow.sol))

### Summary
`createWriteOffRequest` validates that the deposited tranche amount is non-zero but never validates `underlyingsRequested`. Any request stored with `underlyings == 0` satisfies the fulfilment check `_underlyings < currentRequest.underlyings` with `_underlyings = 0`, so a permissionless fulfiller can call `fullfillWriteOffRequest`, transfer zero underlying, and receive all of the victim's escrowed tranche tokens. This is the same bug class as the referenced advisory: attacker-reachable input is accepted without validation into a security-critical comparison.

### Finding Description
In `createWriteOffRequest` the escrow only rejects `amount == 0`:

- `IdleCreditVaultWriteOffEscrow.sol:89-90` — `if (amount == 0) revert NotAllowed();`
- `IdleCreditVaultWriteOffEscrow.sol:97-101` — stores `WriteOffRequest{tranches: ..., underlyings: currentRequest.underlyings + underlyingsRequested}` with no check that `underlyingsRequested != 0` and no sanity bound.

In `fullfillWriteOffRequest` the only economic guard is:

- `IdleCreditVaultWriteOffEscrow.sol:129-131` — `if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) revert WrongRequest();`

When `currentRequest.underlyings == 0`, a fulfiller passes `_underlyings = 0`, `safeTransferFrom` pulls nothing, the fee math `(_underlyings * _exitFee) / FULL_VALUE` yields 0, the user receives `0 - 0`, and line 151 transfers `currentRequest.tranches` to the fulfiller.

The escrow is also cumulative: `userRequests[msg.sender]` adds to `tranches` and `underlyings` independently across calls (lines 97-100). A lender who tops up tranche collateral in a second `createWriteOffRequest(amount2, 0)` — a natural usage of the additive API — silently widens a zero-underlying request, or one whose `underlyings` was already partially "paid down" is not even required; the aggregate just needs `underlyings == 0`. There is no way for the victim to prevent fulfilment once the request exists: `deleteWriteOffRequest` exists but can be front-run by the fulfiller in the same block the request is created, and the mempool-visible `createWriteOffRequest(..., underlyingsRequested = 0)` is directly exploitable by any EOA.

Note the preconditions are weak rather than impossible: `createWriteOffRequest` requires the epoch to be running (`isEpochRunning()`), which is the normal operating state of the vault, and the lender only needs to hold tranche tokens — exactly the contract's intended users.

### Impact Explanation
Direct theft. The fulfiller pays 0 underlying (and 0 exit fee) and receives `currentRequest.tranches`, i.e. AA/BB tranche tokens backed by vault funds redeemable through `requestWithdraw`/`claimWithdrawRequest` or `writeOffDeposit`. Loss equals the full underlying value of the escrowed tranche tokens; the fulfiller's cost is only gas. "One receipt one payout" and fair-exchange invariants are broken: tranches leave escrow with zero consideration.

### Likelihood Explanation
- The vulnerable parameter is fully attacker-relevant and user-controlled at creation; the escrow API explicitly supports multi-call accumulation where passing `0` for `underlyingsRequested` on a top-up is a plausible input.
- Fulfilment is permissionless ("this function can be called by any wallet", line 122), so a generic mempool bot or any unprivileged EOA qualifies as the attacker under the threat model.
- The only honest-actor dependency is that a lender submits a request with `underlyingsRequested == 0` (or tops up collateral with 0), which the contract neither prevents nor warns about — a classic missing-validation trigger, not a malicious-privileged-role assumption.

### Recommendation
- Revert in `createWriteOffRequest` when `underlyingsRequested == 0` (and optionally when the aggregate `currentRequest.underlyings + underlyingsRequested` is 0 for a request holding non-zero tranches).
- Strengthen `fullfillWriteOffRequest` with `_underlyings == currentRequest.underlyings` (exact match) or a minimum-price invariant so "overpay allowed" cannot collapse to "pay nothing".
- Optionally enforce a per-tranche floor price at fulfilment (`_underlyings >= _tranches * minPrice / ONE_TRANCHE`).

### Proof of Concept
Foundry fork PoC sketch against a live `IdleCreditVaultWriteOffEscrow` (epoch running):

```solidity
// test/foundry/WriteOffEscrowZeroUnderlying.t.sol
function testFulfillZeroUnderlyingStealsTranches() external {
    // epoch is running
    assertTrue(cdoEpoch.isEpochRunning());

    address lender = makeAddr("lender");
    address attacker = makeAddr("attacker");

    // lender holds AA tranche tokens
    uint256 tranches = 100e18;
    deal(address(AAtranche), lender, tranches);

    // lender creates a write-off request but forgets/mis-sets the ask
    vm.startPrank(lender);
    AAtranche.approve(address(escrow), tranches);
    escrow.createWriteOffRequest(tranches, 0); // underlyingsRequested == 0, accepted
    vm.stopPrank();

    // attacker (any EOA) fulfils with 0 underlying and receives the tranches
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(lender, tranches, 0);

    assertEq(AAtranche.balanceOf(attacker), tranches);       // stolen
    assertEq(AAtranche.balanceOf(address(escrow)), 0);
    assertEq(underlying.balanceOf(attacker), 0);             // paid nothing
    assertEq(underlying.balanceOf(lender), 0);               // lender got nothing
}
```

The PoC only uses `createWriteOffRequest` (running epoch, any tranche holder) and the permissionless `fullfillWriteOffRequest`, both in-scope production paths in `contracts/IdleCreditVaultWriteOffEscrow.sol`.
