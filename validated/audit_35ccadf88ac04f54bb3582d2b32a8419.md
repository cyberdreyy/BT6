### Title
Attacker-controlled `underlyingsRequested` inflates shared `pendingUnderlyings`, letting the borrower write off debt against escrowed tranches that were never paid for - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
The write-off escrow stores per-user requests whose `underlyings` field is a purely attacker-supplied number, and aggregates them into the global `pendingUnderlyings` counter. This counter is the shared "temporary" state consumed by `IdleCDOEpochVariant.writeOffDeposit` to bound how much borrower debt can be written off against escrowed tranche tokens — analogous to CVE-2023-49347, where intermediate data passed between components sits in a location any user can read and manipulate.

### Finding Description
`createWriteOffRequest` escrows `amount` tranche tokens but accepts `underlyingsRequested` with no bound relative to the tranche value or vault price, and adds it verbatim to `pendingUnderlyings`: [1](#0-0) 

An unprivileged lender (any KYC-passing tranche holder) can therefore set `pendingUnderlyings` to an arbitrary value for the cost of temporarily escrowing tranche tokens, which are refundable via `deleteWriteOffRequest` at any time while an epoch is running.

### Impact Explanation
`pendingUnderlyings` is the contract-level record of how much underlying value is collectively claimed by escrowed tranches; the CDO's `writeOffDeposit` path uses the escrowed position to let the borrower burn tranche tokens and cancel debt. By inflating `underlyingsRequested` far beyond the real value of the escrowed tranches, an attacker makes the recorded claim basis diverge from the actual escrowed value, breaking the "one escrowed tranche position ⇔ paid underlyings" invariant. Depending on how `writeOffDeposit` consumes `pendingUnderlyings`, this either lets a fulfiller/borrower write off more debt than underlyings actually delivered (direct loss socialized to all lenders via the tranche waterfall in `_updateAccounting`), or permanently desynchronizes the counter since `deleteWriteOffRequest` only subtracts the stored per-user amount while legacy-upgrade requests can underflow it via the clamped subtraction at line 112. Note: the exact `writeOffDeposit` consumption of `pendingUnderlyings` lives in `IdleCDOEpochVariant.sol` and could not be fully verified in this pass — the exploitation magnitude depends on whether it caps the burn at `pendingUnderlyings` or at per-request data.

### Likelihood Explanation
Requires only a tranche-token holder (unprivileged, no privileged role). Cost is gas plus temporarily escrowed tranches, refundable on demand. The gate `isEpochRunning()` in `createWriteOffRequest` just requires the epoch to be in the running phase, the normal state.

### Recommendation
Validate `underlyingsRequested` against the current tranche `virtualPrice` (e.g., cap it at a multiple of the escrowed tranches' redemption value), or derive the claim basis solely from escrowed tranche amounts priced at request time instead of trusting user input. In `writeOffDeposit`, bound the debt burn by underlyings actually transferred in `fullfillWriteOffRequest`, not by the self-declared requested amount.

### Proof of Concept
```solidity
// Foundry fork PoC sketch (running epoch, attacker = KYC'd AA holder)
uint256 tranches = 100e18;               // small real escrow
uint256 fakeAsk  = 100_000_000e6;        // arbitrary, unbounded input

vm.startPrank(attacker);
IERC20(AAtranche).approve(address(escrow), tranches);
escrow.createWriteOffRequest(tranches, fakeAsk);
assertEq(escrow.pendingUnderlyings(), fakeAsk); // global counter now attacker-controlled

// borrower path: writeOffDeposit consumes escrowed tranches; if gated by
// pendingUnderlyings, debt burn exceeds underlyings ever paid in.
// cleanup is free: attacker can refund tranches anytime
escrow.deleteWriteOffRequest();
vm.stopPrank();
```

Residual uncertainty: the precise invariant break depends on `IdleCDOEpochVariant.writeOffDeposit`'s use of escrow state, which I could not fully inspect; if it only burns against per-request fulfilled data, the impact reduces to counter desynchronization rather than direct theft, in which case this should be downgraded or rejected.

```text
  function createWriteOffRequest(uint256 amount, uint256 underlyingsRequested) external nonReentrant {
    // can request write off only when epoch is running
    if (!IdleCDOEpochVariant(idleCDOEpoch).isEpochRunning()) revert EpochNotRunning();
    // cannot request write off with 0 tranche tokens
    if (amount == 0) revert NotAllowed();

    // get tranche tokens from user
    IERC20Detailed(tranche).safeTransferFrom(msg.sender, address(this), amount);
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[msg.sender];
    // update user requests
    userRequests[msg.sender] = WriteOffRequest({
      tranches: currentRequest.tranches + amount,
      underlyings: currentRequest.underlyings + underlyingsRequested
    });
    pendingUnderlyings += underlyingsRequested;
  }
```
