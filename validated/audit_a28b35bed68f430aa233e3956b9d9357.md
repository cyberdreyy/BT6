### Title
Unvalidated `setRoleAdmin` on B‑20 tokens can permanently brick the `UNPAUSE_ROLE`, freezing all transfers while a token is paused - (File: `crates/common/precompiles/src/b20_asset/logic/v2.rs`)

### Summary
The reported Chromia bug is a class of vulnerability where a privileged "update the most-privileged authority" function (`update_main_auth_descriptor()`) fails to validate that the *new* authority actually retains the capability flags needed to keep the account operable, risking a state where no party can perform critical operations and funds become permanently stuck. The same bug class is reachable in Base's native B‑20 precompile role system: `set_role_admin()` lets a `DefaultAdmin`-privileged caller repoint a role's admin (e.g. `UNPAUSE_ROLE`) to an arbitrary role identifier without checking that the new admin role has any members or is otherwise reachable, which can permanently remove the ability to grant/revoke that role — including the role required to lift a pause and unfreeze transfers.

### Finding Description
`set_role_admin` in the B‑20 asset/stablecoin logic (present in both V1 and V2, e.g. `crates/common/precompiles/src/b20_asset/logic/v2.rs:645-667`) only checks that the *caller* currently holds the *previous* admin role for `role`; it performs no validation whatsoever on `new_admin_role`: [1](#0-0) 

```
let previous_admin_role = token.accounting().role_admin(role)?;
if !privileged {
    self.ensure_role_admin_mutations_available(token, caller)?;
    B20Guards::ensure_role(token, caller, previous_admin_role)?;
}
token.accounting_mut().set_role_admin(role, new_admin_role)?;
```

There is no check that any account currently holds `new_admin_role`, nor any restriction on which role identifiers are acceptable. This mirrors the exact root cause in the external report: a function that transfers the "most privileged" relationship for an operation without validating that the resulting privilege holder can actually exercise the needed capability.

The impact is concrete because `grant_role`/`revoke_role` gate all future role mutations strictly on `role_admin(role)` membership (not on `DEFAULT_ADMIN_ROLE` membership, unless `role_admin(role)` happens to still be `DefaultAdmin`): [2](#0-1) 

The gate is used for every built-in operational role, including `PAUSE_ROLE`/`UNPAUSE_ROLE`: [3](#0-2) 

`pause`/`unpause` themselves are role-gated with no privileged/factory bypass reachable from a normal transaction, and `unpause` is the only way to clear a paused `TRANSFER` (or `MINT`/`BURN`/`SEIZE`) feature bit once set: [4](#0-3) 

The existing golden test even demonstrates the reachable, unguarded state transition — `setRoleAdmin` moving a role's admin to another role (`Metadata`) that currently has zero members, with no revert: [5](#0-4) 

### Impact Explanation
If a token's `DefaultAdmin` (or any account holding the current `role_admin(UNPAUSE_ROLE)`) calls `setRoleAdmin(UNPAUSE_ROLE, R)` where `R` is a role with no current members (accidentally or via a compromised/malicious admin key), the ability to grant `UNPAUSE_ROLE` to anyone is permanently severed — no account can gain the role required to unpause, since granting requires holding `R`, which nothing can ever grant either (its own admin chain is equally unreachable). If the `TRANSFER` pausable feature is (or later becomes) paused, every holder's tokens become permanently frozen with no recovery path, matching the "permanent freezing of funds" impact bar from the report. The same logic applies to `PAUSE_ROLE`'s admin or any other operational role's admin (e.g., `MINT`, `BURN`, `SEIZE`), each capable of bricking a distinct privileged capability, and to `DefaultAdmin` itself if its own admin chain is redirected, which can eventually strand the whole role hierarchy once the last holder of the affected role renounces or is revoked.

### Likelihood Explanation
`setRoleAdmin` is a normal, unprivileged (from the perspective of chain consensus) B‑20 selector reachable by any account holding the relevant role-admin role on a live B‑20 token, dispatched directly from `crates/common/precompiles/src/b20_asset/dispatch.rs:323-326`. No special preconditions beyond normal admin-key operation are required, and the harmful state is a single transaction away (`setRoleAdmin` to an empty role) combined with either an existing pause or a subsequent pause before the mistake/malice is noticed. Because this requires an admin-privileged token deployer/operator (not an arbitrary anonymous attacker), likelihood is bounded by that trust assumption, but the missing validation converts an ordinary operational/config error into an irreversible, protocol-level fund freeze rather than a recoverable mistake — precisely the situation the referenced report flags as requiring an explicit validation fix.

### Recommendation
Update `set_role_admin` (and any equivalent path) to validate that `new_admin_role` is safe to adopt before committing the change — e.g., require that `new_admin_role` currently has at least one member (mirroring the existing `ensure_role_admin_mutations_available` check already used for `DefaultAdmin`), or restrict `new_admin_role` to a set of roles known to always have a manageable membership path back to `DefaultAdmin`. This closes the gap the same way the upstream Chromia fix closed it for `update_main_auth_descriptor()`: validate the resulting privileged relationship retains the required capability before allowing the mutation.

### Proof of Concept
1. Deploy a B‑20 asset/stablecoin token; `ADMIN` holds `DEFAULT_ADMIN_ROLE` and is granted `UNPAUSE_ROLE`/`PAUSE_ROLE` as in `etc/systems/tests/b20_precompile.rs:605-617`.
2. `ADMIN` calls `pause([TRANSFER])` — transfers now revert (`b20_precompile.rs:618-631` shows the pause/unpause pattern).
3. `ADMIN` (who is `role_admin(UNPAUSE_ROLE)` by default) calls `setRoleAdmin(UNPAUSE_ROLE, METADATA_ROLE)` — succeeds unconditionally per `set_role_admin` (`b20_asset/logic/v2.rs:645-667`), exactly as validated by `golden_set_role_admin` (`b20_asset_v2_golden.rs:1744-1765`), since nothing checks whether `METADATA_ROLE` has any holders.
4. `ADMIN` calls `renounceRole(UNPAUSE_ROLE, ADMIN)` (unconditionally allowed; only `DefaultAdmin`'s last-holder is special-cased in `renounce_role`, `b20_asset/logic/v2.rs:614-631`).
5. No account can now call `grantRole(UNPAUSE_ROLE, x)`, because `grant_role` requires the caller to hold `role_admin(UNPAUSE_ROLE) == METADATA_ROLE`, and `METADATA_ROLE` has zero holders and cannot itself be granted by anyone reachable.
6. `TRANSFER` remains permanently paused; all balances on the token are frozen with no on-chain recovery path.

    Seize,
