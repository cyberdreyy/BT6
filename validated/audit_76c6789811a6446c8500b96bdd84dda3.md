### Title
Stale instant-withdraw per-epoch receipts survive funded claims, inflating default-recovery basis and permanently freezing same-epoch claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` clears the aggregate `instantWithdrawsRequests[user]` but never clears `instantWithdrawsRequestsByEpoch[user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` (`IdleCreditVault.sol:387-392`). This is the direct analog of the Mosquitto bug: a request/claim cycle (CONNECT/DISCONNECT) leaves stale subscription state that is later re-processed. If the borrower defaults in the same epoch, the stale basis is counted again in `defaultPendingClaimBasis`, diluting `defaultRecoveryPrice` for all claimants, and `_claimDefaultedInstantWithdrawRequest` underflows on `instantWithdrawsRequests[user] -= claimBasis`, permanently freezing the user's legitimate post-default claim.

### Finding Description
In `IdleCreditVault.requestInstantWithdraw` (line 356-375) both the aggregate and the per-epoch counters are incremented:

```
instantWithdrawsRequests[_user] += _amount;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
```

The funded-claim path (lines 387-392) only clears the aggregate:

```
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][currentEpoch]` and `instantWithdrawClaimsByEpoch[currentEpoch]` retain the already-paid basis — exactly the "stale entry after disconnect" defect.

Consequences when a default is finalized in that epoch:

1. `defaultPendingClaimBasis` (line 644-649) adds `instantWithdrawClaimsByEpoch[epochNumber]`, which still includes basis already paid out and burned. `finalizeDefaultRecovery` divides the reserve by this inflated `totalBasis` (line 688), so `defaultRecoveryPrice` is lower than warranted — every defaulted-epoch and active claimant is diluted, and the corresponding reserve portion is stranded in the contract.
2. `_claimDefaultedInstantWithdrawRequest` (line 842-856) reads the stale `instantWithdrawsRequestsByEpoch[user][defaultEpoch]` and executes `instantWithdrawsRequests[_user] -= claimBasis`. Since a user who claimed once and re-requested has `instantWithdrawsRequests < claimBasis`, this subtraction reverts (Solidity 0.8 panic), so `claimInstantWithdrawRequest` permanently reverts for that user — their genuinely unfunded receipt can never be recovered.

Broken invariant: one receipt, one payout; isolated recovery reserve sized exactly to outstanding claims.

### Impact Explanation
- Permanent freezing of unclaimed yield: any user who claimed a funded instant withdrawal and re-requested in the same epoch loses the ability to claim the new receipt after default finalization; the receipt tokens are burned-equivalent but unclaimable.
- Reserve dilution/stranding: every stale instant claim lowers `defaultRecoveryPrice`, so honest default claimants (AA/BB holders and pending withdrawers) recover less; the excess reserve is locked forever.
- The existing guards do not stop it: `pendingInstantWithdraws != 0` gating only checks the unfunded remainder, not the stale per-epoch totals; `_ensureDefaultRecoveryInitialized` reverts on pending instant withdrawals but does not clean historical `instantWithdrawClaimsByEpoch`.

### Likelihood Explanation
Requires instant withdrawals enabled (`allowInstantWithdraw`), a user who claims an instant withdrawal and re-requests within the same epoch, and a borrower default before the new request is funded — plausible in an epoch of meaningful duration. The attacker is an ordinary KYC'd lender (unprivileged). The grief is self-inflicted for the freeze, but the reserve dilution harms all claimants, and the frozen-claim DoS applies to any honest user matching the pattern.

### Recommendation
In `claimInstantWithdrawRequest`, clear the per-epoch entries alongside the aggregate: zero `instantWithdrawsRequestsByEpoch[_user][epochNumber]` and decrement `instantWithdrawClaimsByEpoch[epochNumber]` by the claimed amount. Alternatively, make `defaultPendingClaimBasis` and `_claimDefaultedInstantWithdrawRequest` compute basis from the still-unfunded remainder rather than cumulative per-epoch records.

### Proof of Concept
```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.x;
import "forge-std/Test.sol";

contract StaleInstantReceiptPoC is Test {
    // Setup: standard IdleCDOEpochVariant + IdleCreditVault, allowInstantWithdraw = true,
    // attacker is a KYC'd AA holder. Epoch E is running.

    function testStaleInstantReceiptInflatesDefaultBasis() external {
        // 1. Attacker requests instant withdraw of amount A in epoch E.
        cdoEpoch.requestInstantWithdraw(A);              // receipt minted
        // 2. Epoch start funds the request; collectInstantWithdrawFunds reduces
        //    pendingInstantWithdraws; attacker claims at par.
        cdoEpoch.claimInstantWithdrawRequest();
        //    instantWithdrawsRequests[attacker] == 0, BUT
        //    instantWithdrawsRequestsByEpoch[attacker][E] == A   (stale)
        //    instantWithdrawClaimsByEpoch[E]          == A   (stale)

        // 3. Attacker requests instant withdraw again, amount B (unfunded).
        cdoEpoch.requestInstantWithdraw(B);
        //    instantWithdrawsRequestsByEpoch[attacker][E] == A + B
        //    instantWithdrawClaimsByEpoch[E]          == A + B (A was already paid)

        // 4. Borrower defaults mid-epoch; manager/owner calls default handling and
        //    finalizeDefaultRecovery(recovered, source).
        //    defaultPendingClaimBasis() counts A + B though only B is outstanding.
        //    => defaultRecoveryPrice is depressed for ALL claimants.

        // 5. Attacker's own claim now reverts:
        //    _claimDefaultedInstantWithdrawRequest does
        //    instantWithdrawsRequests[attacker] (== B) -= claimBasis (== A + B) -> panic.
        vm.expectRevert();
        cdoEpoch.claimInstantWithdrawRequest();          // B permanently frozen

        // 6. Other claimants also recover less; the diluted share of
        //    defaultRecoveryReserve is stranded in the strategy forever.
    }
}
```
