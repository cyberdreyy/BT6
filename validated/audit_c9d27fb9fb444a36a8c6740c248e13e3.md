### Title
Timing side-channel in `localLoginFallback` allows local-admin email enumeration under OIDC fallback path - ([File: core/sessions/oidcauth/oidc.go])

### Summary
`localLoginFallback` performs a DB lookup keyed by email, then a `constantTimeEmailCompare`, and finally `utils.CheckPasswordHash` (bcrypt). Because the expensive bcrypt comparison is only reached when a matching user row is found, the overall response time for an unknown email (fast SQL miss / no-row return) is measurably different from a known email with a wrong password (bcrypt computation cost), independent of whether `constantTimeEmailCompare` itself is constant-time.

### Finding Description
`CreateSession` is invoked from `SessionsController.Create` (`core/web/sessions_controller.go:56`), which is reachable by any unauthenticated client hitting the login endpoint — no prior credentials are required, matching the stated precondition.

Inside `localLoginFallback` (`core/sessions/oidcauth/oidc.go:580-597`):
1. `oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)` queries `SELECT * FROM users WHERE lower(email) = lower($1)`. If the email doesn't exist, this returns `sql.ErrNoRows` almost immediately and the function returns early (line 583-585) — no `constantTimeEmailCompare` and no `CheckPasswordHash` are executed.
2. If the email exists, `constantTimeEmailCompare` (lines 586-589) runs (this branch is effectively unreachable as a mismatch, since the SQL already filtered by `lower(email)`), and then `utils.CheckPasswordHash(sr.Password, string(user.HashedPassword))` is called (line 591), which performs a bcrypt hash comparison — an operation deliberately expensive (tens to hundreds of milliseconds) to resist brute forcing.

The `subtle.ConstantTimeCompare`-based email check is largely cosmetic here because the actual email disambiguation already happened at the SQL layer via `WHERE lower(email) = lower($1)` (a query that returns `sql.ErrNoRows` fast for non-existent users). The real, dominant timing signal is not the string-compare step at all, but the presence/absence of the expensive bcrypt call gated behind "was a user row found." An attacker submitting a fixed wrong password against many candidate emails can distinguish "user not found" (fast SQL-miss path) from "user found, wrong password" (slow bcrypt path) via wall-clock timing, without needing valid credentials.

### Impact Explanation
This allows enumeration of which email addresses correspond to valid local-admin accounts under OIDC auth mode, matching the scoped impact described (account/email enumeration). This does not by itself grant authentication bypass, session creation, or credential disclosure — it only leaks whether an email is a registered local admin. This maps to a low-severity information-disclosure class in the Chainlink bounty taxonomy (user/account enumeration), not authentication bypass or privilege escalation, since password guessing is still required and presumably bcrypt-protected against brute force.

### Likelihood Explanation
Feasible and repeatable: no credentials or special network position are needed beyond ability to send repeated POST requests to the session-creation endpoint (`/sessions`) and measure response latency. Real-world noise (network jitter, DB query variance, GC pauses) would require statistical averaging over many requests per candidate email, but the timing gap introduced by bcrypt (typically tens of ms at default cost factors) vs. a fast SQL no-row lookup is large enough to be distinguishable with a modest number of samples, making this a practical enumeration primitive rather than a purely theoretical one.

### Recommendation
Perform a bcrypt-equivalent-cost operation (e.g., compare against a precomputed dummy hash) on the "user not found" path so that both branches take comparable time, or restructure `localLoginFallback` to always call `utils.CheckPasswordHash` against either the real hash or a fixed dummy hash regardless of whether the email was found, deferring the "invalid email" vs. "invalid password" distinction only in the returned error (not in code timing). Additionally, since the SQL query already filters by lowercased email, the `constantTimeEmailCompare` step provides no real security value and should not be relied upon as the timing-safety measure; the DB-miss vs. bcrypt-hit asymmetry is the actual channel to close.

### Proof of Concept
Go benchmark/table test plan (to be run against `oidcAuthenticator.CreateSession`/`localLoginFallback` with a test DB):
1. Seed one known user (`known@example.com`) with a bcrypt-hashed password.
2. For N iterations, call `CreateSession` with `sr.Email = "known@example.com"` and a fixed wrong password; record latency.
3. For N iterations, call `CreateSession` with `sr.Email = "unknown-<i>@example.com"` (nonexistent) and the same fixed wrong password; record latency.
4. Compute mean/median latency for both groups and assert (to demonstrate the vulnerability) that the "known email" group is statistically significantly slower than the "unknown email" group (e.g., via a t-test or simple threshold comparison), showing the timing distributions are distinguishable — falsifying the invariant that "authentication soundness" (no identity leak without valid credentials) holds.

func (oi *oidcAuthenticator) localLoginFallback(ctx context.Context, sr clsessions.SessionRequest) (clsessions.User, error) {
	var user clsessions.User
	err := oi.ds.GetContext(ctx, &user, SQLSelectUserbyEmail, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return user, errors.New("invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		oi.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil
}

func constantTimeEmailCompare(left, right string) bool {
	const constantTimeEmailLength = 256
	length := mathutil.Max(constantTimeEmailLength, len(left), len(right))
	leftBytes := make([]byte, length)
	rightBytes := make([]byte, length)
	copy(leftBytes, left)
	copy(rightBytes, right)
	return subtle.ConstantTimeCompare(leftBytes, rightBytes) == 1
}
