### Title
Post-default withdraw requests pay out 1:1 from the fixed default-recovery reserve, draining funds reserved for defaulted-epoch claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.finalizeDefaultRecovery()` sizes `defaultRecoveryReserve` exactly to cover the defaulted-epoch claim basis (`activeBasis + pendingBasis`) at `defaultRecoveryPrice`. Afterwards, `requestWithdraw()` enters a post-default branch that mints a fresh receipt (`postDefaultRequests[_user]`) which is later paid **1:1 out of that same reserve** via `_claimPostDefaultWithdrawRequest` → `_transferDefaultRecovery`. No new underlying is ever added to the reserve for these post-default claims: the branch deliberately avoids increasing `pendingWithdraws` ("Preserve request/claim UX after default without increasing borrower-facing pendingWithdraws"), and only burns/mints strategy tokens. The result is an over-allocated reserve: post-default requesters steal recovery funds, and the last defaulted-epoch claimants' claims revert permanently.

### Finding Description
The external bug class is a mishandled edge path introduced by an incomplete fix. The analog here is the post-default request flow grafted onto recovery accounting:

1. `finalizeDefaultRecovery` computes `reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve` and `recoveryPrice = reserveAmount * 1e18 / totalBasis` (`IdleCreditVault.sol:686-692`). The reserve is therefore fully allocated to `totalBasis` claimants.
2. Post-finalization, `requestWithdraw` (`:247-257`) skips `pendingWithdraws` accounting entirely, burns `_amount` of CDO strategy tokens, mints `_amount` receipt tokens to the user, and sets `postDefaultRequests[_user] = _amount`. No underlying is pulled into the reserve.
3. `claimWithdrawRequest` → `_claimPostDefaultWithdrawRequest` (`:760-767`) pays `postDefaultRequests` at par via `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` (`:912-917`).

Because the reserve was sized only for the defaulted basis, every post-default claim consumes recovery belonging to other claimants. Once the reserve is depleted below an outstanding defaulted claim, `_transferDefaultRecovery` underflows on `defaultRecoveryReserve -= _amount` (or the ERC20 transfer fails) and reverts `NotAllowed`-style — permanently freezing that claimant's recovery. The `_transferFundedClaim` reserve guard (`:897-907`) does not apply since this path uses `_transferDefaultRecovery`. The "user should first claim old already-funded withdraw requests" guard at `:248-251` only serializes a user's own requests; it does not cap or fund post-default claims.

The attacker is an ordinary tranche-token holder (KYC-passed lender) — permitted by the threat model. Sequence: borrower defaults → CDO calls `finalizeDefaultRecovery` → attacker requests withdraw post-default (CDO applies the virtualPrice haircut, so the request is cheap in underlying terms but still mints a 1:1 receipt) → attacker claims 1:1 from the reserve before/alongside legitimate defaulted claimants → the tail claimants' recovery reverts forever.

### Impact Explanation
Direct theft plus permanent freezing. The attacker extracts `postDefaultRequests` amounts up to the full remaining `defaultRecoveryReserve`; equivalently, that amount of recovery owed to defaulted-epoch receipt holders and (indirectly) active tranche holders becomes unclaimable and their `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls permanently revert.

### Likelihood Explanation
Requires a borrower default followed by recovery finalization — a rare but designed-for state. After that, any single tranche holder can trigger the drain with ordinary, unprivileged `requestWithdraw`/`claimWithdrawRequest` calls through the CDO. No privileged role, timing race, or external oracle manipulation is needed.

### Recommendation
Either fund post-default claims from a separate source, or reserve for them: e.g., require the CDO to deposit underlying (`collectWithdrawFunds`-style) before honoring post-default requests, or pay post-default claims at `defaultRecoveryPrice` (not 1:1) while proportionally increasing `totalBasis`/reserve accounting at finalization. Alternatively, revert post-default `requestWithdraw` until all defaulted claims are settled.

### Proof of Concept
A Foundry fork PoC would: (1) deploy `IdleCreditVault` + epoch CDO, lender deposits, `startEpoch`, borrower draws funds; (2) lender A requests withdraw (receipt minted in epoch N); (3) borrower defaults, CDO calls `finalizeDefaultRecovery(recovered < basis)` → `defaultRecoveryPrice` < 1e18, `defaultRecoveryReserve = recovered`; (4) attacker B (tranche holder) calls CDO `requestWithdraw` post-default → `postDefaultRequests[B] = amount` with no funding; (5) B calls `claimWithdrawRequest` → receives `amount` 1:1 from the reserve; (6) lender A calls `claimWithdrawRequest` → `_transferDefaultRecovery` underflows/reverts, A's recovery is permanently frozen.

**Uncertainty note:** I could not fully verify `IdleCDOEpochVariant.sol`'s post-default funding path within the available iterations (grep confirmed `postDefaultRequests`-related handling exists only in the strategy). If the CDO pulls underlying into the strategy reserve for post-default requests elsewhere, the drain would be partially offset — but nothing in `IdleCreditVault` adds to `defaultRecoveryReserve` after finalization, and the code comments state post-default requests are "already backed by the default recovery reserve," confirming they consume the fixed reserve.
