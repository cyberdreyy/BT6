Looking at the `confirm` function in `multisig/src/lib.rs`, I can identify a genuine analog of the reported bug class ("confirmations counted versus live members" binding break).

### Title
`confirm` counts confirmations against a stale `num_confirmations` threshold and stale key set, allowing a request executed with fewer live signer confirmations than currently required - (File: `multisig/src/lib.rs`)

### Summary
The multisig contract's threshold-check binding — "number of distinct confirming keys ≥ `num_confirmations` required by the current contract state" — can be broken because `confirm()` reads `self.num_confirmations` and executes as soon as the *current* threshold is met, but keys can be added/deleted, and `num_confirmations` itself can be changed as a bundled single-action request, mid-flight relative to already-outstanding requests and their already-collected confirmations.

### Finding Description
`add_request` records a `MultiSigRequestWithSigner` and an empty confirmation set at request creation time, independent of the number of keys or the confirmation threshold at that moment [1](#0-0) . Confirmations accumulate in `self.confirmations` per `request_id` [2](#0-1) , and execution triggers once `confirmations.len() + 1 >= self.num_confirmations` — using the **live, current** `self.num_confirmations` value, not any value bound to the request at creation time [3](#0-2) .

Because `SetNumConfirmations` is itself just another request that can be added and confirmed like any other [4](#0-3) , and `AddKey`/`DeleteKey` requests independently mutate the effective signer set [5](#0-4) , there is a window where an old, already-partially-confirmed request (e.g. a `Transfer`) can accumulate just enough confirmations to cross a threshold that was lowered *after* the request was created, or cross a threshold using confirmations from keys that have since been deleted (the confirming `PublicKey` set is never revalidated against currently active keys before `execute_request` runs — `confirm()` only checks that the *caller's* key hasn't already confirmed [6](#0-5) , it does not re-validate that all previously stored confirming public keys in the `HashSet<PublicKey>` are still valid access keys on the account).

This is directly analogous to the reported bug's root cause pattern: a recorded/claimed state (`confirmations` accumulated under one threshold/key-set assumption) is used to authorize an action under a different, currently-live state (the live `num_confirmations` or live key set), without re-validating the binding equality "confirmations recorded == confirmations that are still valid under current authorization state" at execution time.

### Impact Explanation
If exploited, a request (e.g., a `Transfer` of NEAR funds, or an `AddKey`/`DeleteKey` action) could be executed with a lower effective confirmation count than the threshold that governs the account at execution time, or with confirmations from keys removed from the multisig in the interim — i.e., "a multisig request executed below threshold," which falls squarely in the Critical impact category defined by the rules.

### Likelihood Explanation
This requires no foundation, no owner, no redeploy — only a sequence of ordinary calls available to existing key holders of the multisig (`add_request`, `confirm`, `add_request_and_confirm`, and a `SetNumConfirmations`/`AddKey`/`DeleteKey` request) issued in a particular order. Any keyholder able to add and confirm requests can attempt this ordering; whether it is trivially exploitable by a single unprivileged party depends on the number of colluding/compromised keys required, which is a limitation of what could be confirmed from static code reading alone — dynamic/interleaved-call testing would be needed to fully confirm the exploit window, which I was not able to execute in this environment.

### Recommendation
Bind the `num_confirmations` value (and/or a snapshot of currently valid signer keys) to the request at the time it is created, and validate it does not shrink below what was in effect when earlier confirmations were collected; alternatively, invalidate/require re-confirmation of outstanding requests whenever `num_confirmations` changes or a confirming key is deleted, and validate at `execute_request` time that all currently stored confirming public keys are still active access keys on the account.

### Proof of Concept
Conceptual sequence (not executed/verified end-to-end in this session):
1. Multisig deployed with `num_confirmations = 3` and keys `K1, K2, K3, K4`.
2. `K1` calls `add_request_and_confirm` with a `Transfer` action → request has 1 confirmation.
3. `K2` calls `confirm` on the same request → 2 confirmations, still below 3, not executed.
4. Separately, `K3` and `K4` create and confirm a `SetNumConfirmations { num_confirmations: 2 }` request, which executes immediately (single-action) and lowers `self.num_confirmations` to 2 [4](#0-3) .
5. The `Transfer` request from step 2/3 — with only 2 confirmations gathered under the old threshold of 3 — is now eligible: any third holder confirming, or even re-checking, sees `confirmations.len() + 1 >= self.num_confirmations` (2+1 ≥ 2) trivially true, executing a transfer that was never actually confirmed under the intended 3-of-n policy in effect when it was created.     pub fn add_request(&mut self, request: MultiSigRequest) -> RequestId {
        assert_eq!(
            env::current_account_id(),
            env::predecessor_account_id(),
            "Predecessor account must much current account"
        );
        // track how many requests this key has made
        let num_requests = self
            .num_requests_pk
            .get(&env::signer_account_pk())
            .unwrap_or(0)
            + 1;
        assert!(
            num_requests <= self.active_requests_limit,
            "Account has too many active requests. Confirm or delete some."
        );
        self.num_requests_pk
            .insert(&env::signer_account_pk(), &num_requests);
        // add the request
        let request_added = MultiSigRequestWithSigner {
            signer_pk: env::signer_account_pk(),
            added_timestamp: env::block_timestamp(),
            request: request,
        };
        self.requests.insert(&self.request_nonce, &request_added);
        let confirmations = HashSet::new();
        self.confirmations
            .insert(&self.request_nonce, &confirmations);
        self.request_nonce += 1;
        self.request_nonce - 1
    }

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
