### Title
EI-credential holders can trigger arbitrary integer-ID job runs via POST /v2/jobs/:ID/runs due to `AuthenticateExternalInitiator` forging a User identity - ([File: core/web/pipeline_runs_controller.go])

### Summary
The `PipelineRunsController.Create` handler gates integer-ID job runs on `auth.GetAuthenticatedUser(c)` returning `isUser == true`, with an explicit comment that "only users are allowed to run jobs using int IDs - EIs not allowed." However, the `AuthenticateExternalInitiator` middleware itself sets a synthetic `*clsessions.User{Role: clsessions.UserRoleRun}` into the same context key (`SessionUserKey`) that `GetAuthenticatedUser` reads from, causing `isUser` to evaluate `true` for EI callers too, defeating the intended restriction.

### Finding Description
The route is registered in `core/web/router.go` as:
```go
userOrEI := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateExternalInitiator,
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
...
userOrEI.POST("/jobs/:ID/runs", auth.RequiresRunRole(prc.Create))
``` [1](#0-0) 

In `core/web/auth/auth.go`, `AuthenticateExternalInitiator` successfully authenticates an EI credential and then writes a fabricated user object into the session context under the exact key used for real authenticated users:
```go
c.Set(SessionExternalInitiatorKey, ei)
c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})
``` [2](#0-1) 

`GetAuthenticatedUser` simply reads that same key without distinguishing whether it was set by a real user session/token or by the EI middleware:
```go
func GetAuthenticatedUser(c *gin.Context) (*clsessions.User, bool) {
	obj, ok := c.Get(SessionUserKey)
	...
}
``` [3](#0-2) 

In `PipelineRunsController.Create`, the intended check is:
```go
_, isUser := auth.GetAuthenticatedUser(c)
// only users are allowed to run jobs using int IDs - EIs not allowed
if isUser {
    var jobID int32
    jobID64, err := strconv.ParseInt(idStr, 10, 32)
    if err == nil {
        jobID = int32(jobID64)
        jobRunID, err := prc.App.RunJobV2(ctx, jobID, nil)
        ...
    }
}
``` [4](#0-3) 

Because `isUser` is derived from the presence of a `SessionUserKey` entry — which `AuthenticateExternalInitiator` unconditionally populates for any successfully authenticated EI — the comment's intended distinction ("EIs not allowed" for int IDs) is never actually enforced by this code. An attacker holding only an EI access key/secret (no user session, no user API token) can authenticate via `AuthenticateExternalInitiator`, `RequiresRunRole` passes (the synthetic user has `UserRoleRun`), and then `Create` treats them as `isUser == true`, allowing them to run any job by its integer ID — not just webhook jobs identified by UUID as originally intended.

### Impact Explanation
This is an authorization bypass allowing an EI-credential holder (a narrow-scope integration credential normally meant only to trigger webhook-type job runs) to trigger arbitrary job runs by integer ID, matching Chainlink's "unauthorized job run" bounty impact class. Depending on what jobs exist on the node (e.g., jobs writing on-chain transactions, VRF fulfillment, keeper/automation jobs), this could cause unintended fund-moving transactions or unauthorized reruns of sensitive jobs the EI holder should have no access to trigger.

### Likelihood Explanation
Precondition is minimal: possession of any valid external-initiator access key/secret pair registered on the node (no user session or user API token required). The exploit is a single unauthenticated-as-user HTTP POST with EI headers to `/v2/jobs/:ID/runs` using an integer job ID, and is fully repeatable since the design flaw is structural (shared context key), not a race condition or timing issue.

### Recommendation
Use a distinct context key/type for EI-derived pseudo-users versus real authenticated users (e.g., a separate `SessionAuthMethodKey` or a boolean flag `isExternalInitiator`), and have `PipelineRunsController.Create` check `auth.GetAuthenticatedExternalInitiator(c)` explicitly to reject int-ID runs when the caller authenticated via the EI method, regardless of the synthetic user role set for `RequiresRunRole` compatibility.

### Proof of Concept
Go handler-level integration test plan in `core/web/pipeline_runs_controller_test.go`:
1. Set up a test app with an `ExternalInitiator` created and stored (as done via `cltest.MustInsertExternalInitiator` or similar helper used elsewhere in EI tests) and a job with a valid integer ID.
2. Send `POST /v2/jobs/:jobID/runs` (integer job ID) with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to the EI's credentials, and no session cookie or `X-API-KEY`/`X-API-SECRET`.
3. Assert that the response status is `401` or `422` and that `prc.App.RunJobV2` was never invoked (e.g., via a mock/spy on `JobORM`/`RunJobV2`).
4. Currently, given the code above, the expected/actual result is that the request succeeds (200 with a `pipelineRun` resource), proving that `isUser` incorrectly evaluates `true` for EI-only credentials and the int-ID run is executed — confirming the bypass.
