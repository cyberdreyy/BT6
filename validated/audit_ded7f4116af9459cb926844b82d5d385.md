### Title
Missing destination-root confinement in `ExtractZipArchive` allows zip-slip path escape — ([File: helpers/archives/zip_extract.go])

### Summary
`ExtractZipArchive` writes every zip entry directly using the archive-supplied `file.Name` with no path-containment check against a restore root, unlike the sibling tar+zstd extractor which explicitly joins entries to a root directory and rejects any resolved path that escapes it. This is not the TOCTOU-style "validate-then-retarget" race the question describes — there is no validation step at all to race against — but it is a related and more fundamental defect: an unprivileged job can supply cache/artifact zip content with `../` sequences, absolute paths, or symlink entries that `os.Mkdir`, `os.OpenFile`, or `os.Symlink` will honor outside the intended extraction directory.

### Finding Description
`extractZipFile` (helpers/archives/zip_extract.go:61-83) calls `os.MkdirAll(filepath.Dir(file.Name), 0o777)` and then, depending on entry type, `os.Mkdir(file.Name, ...)`, `os.Symlink(string(data), file.Name)`, or `os.OpenFile(file.Name, ...)` — all using `file.Name` verbatim, taken from the attacker-controlled `zip.File.FileHeader.Name` field [1](#0-0) . `ExtractZipArchive` only runs `errorIfGitDirectory`, which merely warns/skips `.git`-path entries, and performs no `filepath.Clean`/`filepath.Abs`/prefix check against a destination root before extracting [2](#0-1) . `extractZipSymlinkEntry` also lets an attacker create arbitrary symlinks pointing anywhere on disk via `os.Symlink(string(data), file.Name)`, using attacker-controlled link target data read straight from the zip entry [3](#0-2) .

By contrast, the tar+zstd extractor used elsewhere in the same codebase explicitly joins each entry to a fixed root and rejects any path that doesn't have that root as prefix: `path, err = filepath.Abs(filepath.Join(e.dir, hdr.Name)); if !strings.HasPrefix(path, e.dir+string(filepath.Separator)) && path != e.dir { return fmt.Errorf(...) }` [4](#0-3) . `ExtractZipArchive` has no equivalent containment logic, so `helpers/archives/path_check_helper.go`'s only check is a `.git` name check, not a root-confinement check [5](#0-4) . The legacy zip extractor path (`commands/helpers/archive/ziplegacy/zip_legacy_extractor.go`) passes a `dir` parameter into `NewExtractor` but never uses it — `Extract` ignores `e.dir` entirely and calls `archives.ExtractZipArchive(zr)` directly, so entries are written relative to the process's current working directory with no join to, or validation against, that directory [6](#0-5) .

Regarding the specific premise of the question (validate one path, then race a swap before the final write lands on a different real path): this precondition does not exist in the code, because there is no validation call whose result is later used for a separate write operation. The `os.Remove` + `os.OpenFile`/`os.Symlink` pattern in `extractZipFileEntry`/`extractZipSymlinkEntry` does have an unlink-then-recreate TOCTOU window on the *same* `file.Name`, but since `file.Name` is never checked against a root in the first place, there is no "validated path" being retargeted — the path was never validated to begin with.

### Impact Explanation
If a destination root is ever assumed (e.g., cache/artifact restore into a job's working directory), an attacker-controlled zip (cache/artifact content built during a job, or a maliciously crafted artifact consumed by a downstream job) can supply entry names with `..` segments or absolute paths, or symlink entries pointing outside the intended directory. Combined with the ziplegacy extractor's outright disregard of the `dir` parameter, this could permit writing/overwriting files outside the intended cache/artifact working directory. Concrete impact would be file-write path-root escape within the executor's writable filesystem (job/build root escape), scoped to whatever filesystem access the job process already has — not a container/sandbox escape by itself.

### Likelihood Explanation
Feasibility depends entirely on how/where zip extraction is invoked in the runner's cache/artifact download flow, which was not fully traced here (grep found no other call site of `ExtractZipFile`/`ExtractZipArchive` besides `zip_extract.go`, its tests, and the unused-`dir` legacy wrapper). It is certain that the archive-level function itself performs zero path-containment validation for zip entries, unlike the parallel tar+zstd extractor, so if any caller relies on `ExtractZipArchive`/`ExtractZipFile` to safely restore into a specific directory without doing its own containment check first, that caller is exposed to zip-slip. Whether a caller currently does its own external containment check (e.g. chdir into the target dir before calling) could not be confirmed from the available index and would need direct inspection of the cache/artifact extraction command wiring in a full checkout.

### Recommendation
Add root-confinement validation in `ExtractZipArchive`/`extractZipFile` mirroring the tar+zstd extractor: resolve each entry against an explicit destination root with `filepath.Join`+`filepath.Abs`, reject entries whose resolved path does not have the root as a prefix, and reject symlink targets that resolve outside the root. Make `ExtractZipArchive` and `ExtractZipFile` accept a destination directory argument rather than relying on process CWD, and fix the legacy zip extractor to actually use its `dir` parameter instead of ignoring it.

### Proof of Concept
Go unit test extending `helpers/archives/zip_extract_test.go`:
1. Build a `zip.Writer` with an entry named `../../evil.txt` (and separately one named `/tmp/evil2.txt` or with `filepath.Separator` leading slash where applicable).
2. Call `ExtractZipArchive` on the resulting `*zip.Reader` from within a temp working directory.
3. Assert that `../../evil.txt` (relative to the temp dir, i.e., outside it) does NOT exist after extraction — currently it will exist, proving the escape.
4. Add a second entry that is `os.ModeSymlink` with link target `/etc/passwd`-style absolute path outside the working dir, then confirm a subsequent "file" entry with a name matching that symlink's location does not overwrite content outside the working directory.

Because the actual call sites that pass an explicit destination directory could not be fully enumerated from the indexed code, a background engineer should also grep the full checkout for callers of `ExtractZipFile`/`ExtractZipArchive`/`ziplegacy.NewExtractor` to confirm whether any currently-shipping cache/artifact restore path is exposed, and extend the PoC into an integration test against that call site.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()

	err = os.Symlink(string(data), file.Name)
	return
}

func extractZipFile(file *zip.File) (err error) {
	// Create all parents to extract the file
	err = os.MkdirAll(filepath.Dir(file.Name), 0o777)
	if err != nil {
		return err
	}

	switch file.Mode() & os.ModeType {
	case os.ModeDir:
		err = extractZipDirectoryEntry(file)

	case os.ModeSymlink:
		err = extractZipSymlinkEntry(file)

	case os.ModeNamedPipe, os.ModeSocket, os.ModeDevice:
		// Ignore files of these types
		logrus.Warningf("File ignored: %q", file.Name)

	default:
		err = extractZipFileEntry(file)
	}
	return
}

func isPathAGitDirectory(path string) bool {
	parts := strings.Split(filepath.Clean(path), string(filepath.Separator))
	if len(parts) > 0 && parts[0] == ".git" {
		return true
	}
	return false
}

func errorIfGitDirectory(path string) *os.PathError {
	if !isPathAGitDirectory(path) {
		return nil
	}

	return &os.PathError{
		Op:   ".git inside of archive",
		Path: path,
		Err:  errors.New("trying to archive or extract .git path"),
	}
}
