### Title
Missing-timestamp fallback in `check_parent_tenure_choice` always treats a reorged tenure's block as "poorly timed", improperly sanctioning reorgs it should refuse — (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`SortitionData::check_parent_tenure_choice` decides whether a miner is allowed to reorg a prior tenure that already produced a block. The permitted case (`Ok(true)`) is supposed to require that the reorged tenure's first block was "poorly timed" — i.e. produced too close to the next sortition to give competing miners a chance to RBF (`first_proposal_burn_block_timing`). When the local signer has no `approved_time` on record for that block, the code substitutes `0` as the elapsed time, which always satisfies `< first_proposal_burn_block_timing`, unconditionally treating the block as poorly timed and permitting the reorg — regardless of how much time actually elapsed.

### Finding Description [1](#0-0) 

The relevant branch:
```
let proposal_to_sortition = if let Some(approved_at) = local_block_info.approved_time {
    sortition_state_received_time.saturating_sub(approved_at)
} else {
    info!("We did not sign over the reorged tenure's first block, considering it as a late-arriving proposal");
    0
};
if Duration::from_secs(proposal_to_sortition) < *first_proposal_burn_block_timing {
    ... // reorg permitted, tenure marked superseded
}
```
`local_block_info` is fetched via `get_first_approved_block_in_tenure`, which returns any block with `signed_self`, `signed_group`, OR `approved_time` set ( [2](#0-1) ). A block can be returned by this query while `approved_time` itself is `None` on that particular row if `signed_self`/`signed_group` was set without `approved_time` (e.g. group-signed while `mark_locally_accepted(group_signed=true)` only sets `signed_group`, never touching `approved_time` — see `mark_locally_accepted` in [3](#0-2) ). In that situation `local_block_info.approved_time` is `None`, forcing `proposal_to_sortition = 0`, which is always less than any positive `first_proposal_burn_block_timing`. This turns the timing check into a tautology: any tenure whose first block reached this signer only via group-signature observation (not local pre-commit/local acceptance) is *always* judged "poorly timed," no matter how long it was actually live, and the reorg is unconditionally sanctioned (`superseded_tenures.push(tenure)` → `record_superseded_tenure`/`mark_tenure_superseded`).

The comment describes the intended semantics as "late-arriving proposal," implying this path is meant for blocks this signer never locally validated at all — but the DB predicate for `get_first_approved_block_in_tenure` also matches blocks this signer *did* observe as signed by the group, just without a local `approved_time` timestamp, silently pulling those into the same permissive branch.

Once the reorg is sanctioned, `check_parent_tenure_choice` returns `true` from `check_proposal` (v1, [4](#0-3) ) or `validate_tenure_change_payload` ( [5](#0-4) ), permitting the signer to proceed to sign the new tenure-change block that reorgs the prior tenure's canonical, already-signed block — a path this rule exists specifically to gate.

### Impact Explanation
This degrades the "poorly-timed tenure" safety gate from a genuine elapsed-time check into a no-op whenever this particular code path is hit, causing this signer to sign a tenure-change block that reorgs an established, previously-signed tenure it should have refused. This falls under the "signer signing a … conflicting block" category, since it authorizes signing over a block that displaces a tenure the rule was designed to protect. Because each signer runs this logic independently on their own local `SignerDb` state, this is triggered per-signer without needing a majority — an individual signer's local knowledge gaps (e.g., how it received/recorded the prior block) are what flip the outcome, and a miner does not need any other signer's cooperation to have this specific signer approve/sign a reorg that timing rules should forbid.

### Likelihood Explanation
The trigger condition — a block being returned by `get_first_approved_block_in_tenure` with `approved_time == None` — requires a specific local-DB state (a block that reached "signed" status without a recorded pre-commit/local-acceptance `approved_time`, e.g., via `signed_group` alone). This is a plausible but not universally common path (occurs for group-observed signatures without local approval flow, or DB migrations that only backfilled `approved_time` from `signed_self`, per the schema note at [6](#0-5) ). It does not require a majority of signers or any privileged access — only a scenario where the local signer's stored `BlockInfo` for the reorged tenure's first block lacks `approved_time`.

### Recommendation
Do not default `proposal_to_sortition` to `0` (i.e., "definitely poorly timed") when `approved_time` is missing. Instead:
- Fall back to `proposed_time` (which is always populated, per `BlockInfo::from(BlockProposal)` at [7](#0-6) ) to compute a genuine elapsed duration, or
- Treat "no approved_time known" as insufficient local knowledge and default to refusing the reorg (`Ok(false)`), consistent with the sibling case a few lines above where "no local knowledge for that tenure's block timing" already returns `Ok(false)` ( [8](#0-7) ), rather than silently assuming the most permissive value.

### Proof of Concept
1. Signer S receives and processes a tenure-change block group-signature acceptance for tenure T's first block such that `signed_group` gets set via `mark_locally_accepted(true)` (see [9](#0-8) ) without ever going through `mark_pre_committed`/`mark_locally_accepted(false)`, leaving `approved_time = None` on that stored `BlockInfo`.
2. A new sortition occurs long after tenure T's first block was actually produced/accepted network-wide (well past `first_proposal_burn_block_timing`), and a miner proposes a tenure-change block building on an earlier ancestor, reorging tenure T.
3. Signer S calls `check_parent_tenure_choice` → `get_first_approved_block_in_tenure(T)` returns the block with `approved_time = None` → `proposal_to_sortition` is forced to `0` → `Duration::from_secs(0) < first_proposal_burn_block_timing` is always true → the reorg is sanctioned and tenure T is marked superseded, even though the real elapsed time from tenure T's first block to the new sortition was far greater than the configured `first_proposal_burn_block_timing`.
4. Signer S then signs the new tenure's tenure-change block, participating in a reorg the timing rule was meant to block.

    /// in tenure changes, we need to check:
    /// (1) if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    /// (2) if the parent tenure was a valid choice
    fn validate_tenure_change_payload(
        &self,
        proposed_by: &ProposedBy,
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the sortition's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        let parent_tenure_id = &proposed_by.state().data.parent_tenure_id;
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            self.config.tenure_last_block_proposal_timeout,
            self.config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // now, we have to check if the parent tenure was a valid choice.
        let is_valid_parent_tenure = proposed_by.state().data.check_parent_tenure_choice(
            signer_db,
            client,
            &self.config.first_proposal_burn_block_timing,
        )?;
        if !is_valid_parent_tenure {
            return Err(RejectReason::ReorgNotAllowed);
        }
        let last_in_current_tenure = signer_db
            .get_last_globally_accepted_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
