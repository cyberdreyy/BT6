### Title
Unprivileged taker can self-declare arbitrary fee amounts/recipients in `createDstEscrow`, diverting the maker's destination funds - (File: `contracts/BaseEscrowFactory.sol`, `contracts/EscrowDst.sol`)

### Summary
`createDstEscrow` accepts the entire `IBaseEscrow.Immutables` struct — including the `parameters` field that encodes `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient` — directly from the calling taker, with no on-chain check against the fee terms that were actually agreed to and emitted on the source chain during `_postInteraction`. Because `EscrowDst._withdraw` blindly trusts these self-supplied fee fields when splitting funds between the maker and the "fee recipients," a malicious taker can inflate the fee amounts and point the recipients at addresses they control, diverting part of the maker's expected destination-chain payout to themselves. This is a direct analog of the reported `ERC721SeaDrop` issue — instead of an owner/admin picking their own fee recipient/fee amount to bypass the intended fee, here it is the unprivileged taker who calls the public `createDstEscrow` entry point to bake self-serving fee parameters into the escrow, with the swap's own `withdraw` logic later honoring them.

### Finding Description
On the source chain, `BaseEscrowFactory._postInteraction` computes `integratorFeeAmount`/`protocolFeeAmount` from the maker-signed order/extension via `FeeTaker._getFeeAmounts`, and packages the agreed fee terms into `DstImmutablesComplement.parameters`, which is only *emitted* in the `SrcEscrowCreated` event: [1](#0-0) 

That emitted `parameters` blob is never enforced on the destination chain. `createDstEscrow` is a standalone, publicly callable function that takes `dstImmutables` (including its own independent `parameters` field) directly from `msg.sender` with no cross-check against what was computed/emitted on the source chain: [2](#0-1) 

The only invariants enforced at deployment are the funded native/token balances and the `srcCancellationTimestamp` ordering — nothing validates `dstImmutables.parameters`, `dstImmutables.amount`, or the fee recipients against the maker-agreed values from `_postInteraction`.

When the taker (the only party allowed to call the private `withdraw`, per `onlyCaller(immutables.taker.get())`) later withdraws, `EscrowDst._withdraw` decodes the fee amount/recipient fields straight out of the attacker-supplied `parameters` calldata and uses them to split the escrowed `amount`: [3](#0-2) 

These decoders (`integratorFeeAmountCd`, `protocolFeeAmountCd`, `protocolFeeRecipientCd`, `integratorFeeRecipientCd`) simply read raw offsets from the calldata `parameters` bytes with no correctness check other than a length bound: [4](#0-3) 

Since `parameters` is included in the `Immutables` hash used by `onlyValidImmutables`, the taker's fabricated fee data is "valid" as long as it matches what the taker deployed the escrow with — it is entirely self-consistent and passes every check in the contract. The maker never signs or otherwise commits any destination-chain fee terms on-chain; the source-chain order signature only binds the source-chain fee computation, not the fields consumed by `EscrowDst.withdraw`.

### Impact Explanation
A malicious/unprivileged taker can call `createDstEscrow` with `dstImmutables.parameters` encoding an inflated `protocolFeeAmount`/`integratorFeeAmount` and set the corresponding recipients to an address they control. When they subsequently call `EscrowDst.withdraw`, the diverted amount is paid to themselves instead of the maker, while the maker still only receives `immutables.amount - integratorFeeAmount - protocolFeeAmount`. This is a direct diversion of value that was contractually owed to the maker on the destination chain, fitting the bounty's "theft of coins/tokens meant for transaction fees" / theft of the maker's swap proceeds, reachable purely through the public, unprivileged `createDstEscrow` → `withdraw` flow described in the audit pivots (destination path / accounting path).

### Likelihood Explanation
High. No privileged role, signature, or off-chain relayer cooperation is required — any address holding the destination token/native funds can call `createDstEscrow` themselves and then call `withdraw` (they must be the `taker` field they set, which they control since it is self-declared calldata) once the withdrawal window opens. Off-chain infrastructure (relayer/resolver UI, `SrcEscrowCreated` event comparison) is the only mitigating factor, matching the "decision-making happens off-chain" caveat noted in the analogous SeaDrop report, but nothing on-chain prevents or reverts the manipulation.

### Recommendation
Bind `createDstEscrow`'s accepted `parameters` (and ideally `amount`, `token`, `maker`) to the fee terms and amounts that were actually computed and emitted during the corresponding `_postInteraction` call, e.g. by having the factory store/commit a hash of the `DstImmutablesComplement` (including `parameters`) at src-escrow-creation time and requiring `createDstEscrow` to supply immutables whose corresponding fields match that commitment (e.g., via `orderHash` lookup), rather than trusting caller-supplied fee data outright.

### Proof of Concept
1. Maker signs an order via the Limit Order Protocol; taker fills it, `_postInteraction` runs, computing legitimate `protocolFeeAmount`/`integratorFeeAmount` and emitting `SrcEscrowCreated` with the correct `DstImmutablesComplement.parameters`.
2. Instead of using that data, the taker calls `createDstEscrow` directly with a custom `dstImmutables.parameters` blob: `abi.encode(largeProtocolFeeAmount, largeIntegratorFeeAmount, attackerAddr, attackerAddr)`, funding the escrow with `dstImmutables.amount` and the safety deposit as required.
3. Once the `DstWithdrawal` timelock stage begins, the taker (who is `immutables.taker`) calls `withdraw(secret, immutables)` with those same immutables.
4. `EscrowDst._withdraw` transfers `largeProtocolFeeAmount` and `largeIntegratorFeeAmount` to `attackerAddr` (the taker themselves), and only `amount - largeProtocolFeeAmount - largeIntegratorFeeAmount` to the maker — less than the maker was contractually owed, with the difference retained by the taker.     function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
