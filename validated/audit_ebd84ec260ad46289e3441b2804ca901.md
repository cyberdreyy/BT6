### Title
Fee-on-transfer underlyings let a fulfiller settle a write-off while paying the lender less than requested - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`fullfillWriteOffRequest` validates the fulfiller’s gross transfer amount before the token transfer, then pays the lender based on that nominal amount rather than the amount actually received. With a fee-on-transfer underlying, both the fulfiller-to-escrow transfer and the escrow-to-lender transfer can reduce delivered value. If the escrow holds enough residual underlying to cover the inbound fee, fulfillment succeeds, the request is deleted, the fulfiller receives the escrowed tranche tokens, and the lender receives less than the requested amount.

### Finding Description
A lender creates a write-off request by depositing tranche tokens and recording the exact amount of underlying requested. The request stores the gross `underlyingsRequested` without measuring whether the escrow received the full tranche amount, although tranche tokens are protocol-controlled and normally do not charge transfer fees [1](#0-0) .

During fulfillment, the contract accepts any `_underlyings` greater than or equal to the request, deletes the request, and pulls the nominal amount from the fulfiller [2](#0-1) . It then transfers the protocol fee and sends `_underlyings - _totFee` to the lender using nominal amounts, not balance deltas [3](#0-2) .

For a token charging fee \(f\), a gross fulfillment of \(U\) credits the escrow with only \(U(1-f)\). The subsequent lender transfer of \(U\), or \(U-\text{exitFee}\), is itself reduced to approximately \(U(1-f)\). Thus, even if the transaction succeeds, the lender’s realized balance increase is below the request.

The vault factory and strategy accept an arbitrary underlying token address and do not reject fee-on-transfer tokens [4](#0-3) . The strategy likewise initializes `underlyingToken` directly from the supplied address [5](#0-4) .

### Impact Explanation
A lender can permanently lose the difference between the requested underlying amount and the actual amount received while still surrendering the escrowed tranche tokens. For a 1% fee-on-transfer token and zero escrow exit fee, a request for 1,000,000 units can be fulfilled while the lender receives only 990,000 units. The request is removed atomically, so the lender cannot cancel and recover the tranche tokens afterward.

This violates the escrow’s one-receipt-one-payout invariant: the protocol treats the fulfiller’s nominal `_underlyings` as satisfying `currentRequest.underlyings`, but the lender’s actual balance delta is lower. The impact is bounded by the token’s transfer fee and any additional escrow exit fee, but applies to the entire write-off payment.

### Likelihood Explanation
Likelihood depends on deploying a credit vault with a fee-on-transfer underlying and on the escrow containing enough residual underlying to cover the inbound transfer deficit. Residual underlying can come from prior fees, rounding dust, or an unsolicited direct transfer; direct token senders are in scope. Any unprivileged fulfiller can then call `fullfillWriteOffRequest`.

Without residual escrow funds, the same transaction generally reverts when outbound transfers exceed the amount actually received, causing a temporary fulfillment failure rather than loss. When residual funds are present, the flawed accounting converts them into the missing transfer-fee budget and allows the underpaid fulfillment to succeed.

### Recommendation
Measure actual underlying received and delivered:

1. Record `underlying.balanceOf(address(this))` immediately before `safeTransferFrom`.
2. Pull the fulfiller’s payment and compute `received = balanceAfter - balanceBefore`.
3. Require `received >= currentRequest.underlyings`, or explicitly define whether the request denotes gross or net proceeds.
4. Calculate the escrow exit fee from `received`.
5. Record the lender’s balance before the payout and require `lenderAfter - lenderBefore >= expectedNetAmount`.
6. Alternatively, document and enforce that fee-on-transfer underlyings are unsupported during vault initialization.

### Proof of Concept
A Foundry fork test can reproduce the issue with a test ERC20 that applies a 1% fee to both `transfer` and `transferFrom`:

```solidity
function testFulfillFeeOnTransferPaysLenderLessThanRequested() public {
    uint256 requested = 1_000_000e6;
    uint256 trancheAmount = 100e18;

    // Configure a 1% fee-on-transfer underlying and deploy the vault/escrow
    // through the normal factory path.
    FeeOnTransferToken underlying = new FeeOnTransferToken(100); // 1%
    (vault, strategy, escrow) = deployVaultWithUnderlying(address(underlying));

    // Honest setup: give the KYC-passing lender tranche tokens and disable
    // the escrow exit fee to isolate the token-transfer fee.
    dealTranche(lender, trancheAmount);
    vm.prank(owner);
    escrow.setExitFee(0);

    // Running epoch: lender escrows tranches and requests `requested`.
    vm.prank(lender);
    tranche.approve(address(escrow), trancheAmount);
    vm.prank(lender);
    escrow.createWriteOffRequest(trancheAmount, requested);

    // Seed the escrow with enough residual underlying to cover the inbound
    // token fee. This can be an unsolicited transfer by an unprivileged sender.
    uint256 inboundFee = requested * 100 / 10_000;
    underlying.mint(attacker, requested + inboundFee);
    vm.prank(attacker);
    underlying.transfer(address(escrow), inboundFee);

    // Fulfill using the exact nominal requested amount.
    vm.prank(attacker);
    underlying.approve(address(escrow), requested);

    uint256 lenderBefore = underlying.balanceOf(lender);
    vm.prank(attacker);
    escrow.fullfillWriteOffRequest(lender, trancheAmount, requested);
    uint256 lenderReceived = underlying.balanceOf(lender) - lenderBefore;

    // The contract accepted `requested`, deleted the request and transferred
    // the tranche tokens, but the lender only received the post-fee amount.
    assertEq(tranche.balanceOf(attacker), trancheAmount);
    assertEq(escrow.userRequests(lender).tranches, 0);
    assertEq(lenderReceived, requested * 99 / 100);
    assertLt(lenderReceived, requested);
}
```

The important assertions are that the stored request is cleared, the fulfiller receives the tranche tokens, and `lenderReceived` is below the exact `underlyings` amount that satisfied the pre-transfer check.

  function fullfillWriteOffRequest(address _user, uint256 _tranches, uint256 _underlyings) external nonReentrant {
    // get current write-off request
    WriteOffRequest memory currentRequest = userRequests[_user];
    // check if the user has a write-off request
    if (currentRequest.tranches == 0) revert Is0();
    // check if the request matches at least the expected values (borrower can choose to overpay if needed, but not underpay)
    if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
      revert WrongRequest();
