### Title
Programmable-borrower mode can coexist with enabled instant withdrawals, letting any user permanently freeze epoch settlement - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`IdleCDOEpochVariant` supports two mutually exclusive operational modes: programmable-borrower accounting (`isProgrammableBorrower`, which requires minted interest and forbids instant funding) and instant withdrawals (`disableInstantWithdraw == false` with `pendingInstantWithdraws` settled through `getInstantWithdrawFunds`). The setters do not enforce exclusivity: `setIsProgrammableBorrower` only blocks changes while an epoch is running, and `setInstantWithdrawParams` never checks `isProgrammableBorrower`. Once both are active, an unprivileged lender can create a `pendingInstantWithdraws` balance that can never be cleared, permanently bricking `stopEpoch`.

### Finding Description
The conflict is between three guards that were each added separately:

- `getInstantWithdrawFunds` reverts when `isProgrammableBorrower` is true (`_checkNotAllowed(isProgrammableBorrower || ...)`) [1](#0-0) , so pending instant requests cannot be funded in programmable mode.
- `_stopEpoch` reverts while `_pendingInstant() != 0` [2](#0-1) , so the epoch can never close while instant requests are outstanding.
- `setIsProgrammableBorrower` cannot be called while `isEpochRunning` [3](#0-2) , so the misconfiguration cannot be undone mid-epoch.

`setInstantWithdrawParams` only checks owner/manager and `paused()` — it does not require `_disable == true` when `isProgrammableBorrower` is set [4](#0-3) . `_checkProgrammableBorrowerMode` (called in `startEpoch` and `_stopEpoch`) validates `isInterestMinted` and `_pendingInstant() == 0` [5](#0-4) , but it runs only at epoch boundaries — it does not prevent instant requests *during* a running epoch, and it does not prevent enabling programmable mode while `disableInstantWithdraw == false`.

Attack sequence:

1. Owner enables `isProgrammableBorrower` while `disableInstantWithdraw == false` (no check prevents this combination).
2. `startEpoch` succeeds because `isInterestMinted == true` and `pendingInstantWithdraws == 0`.
3. During the running epoch, any tranche holder whose withdraw triggers the instant path (APR moved more than `instantWithdrawAprDelta` vs `lastEpochApr`) calls `requestWithdraw`, which routes to `requestInstantWithdraw` in `IdleCreditVault` and increases `pendingInstantWithdraws` [6](#0-5) .
4. `getInstantWithdrawFunds` reverts (`isProgrammableBorrower`), `stopEpoch` reverts (`_pendingInstant() != 0`), and `setIsProgrammableBorrower(false)` reverts (`isEpochRunning`). No exit path exists.

### Impact Explanation
Permanent freezing of all pool funds. Every LP's tranche tokens, all pending withdraw receipts, and the user's own instant receipt become unclaimable: the epoch cannot stop, the borrower is never asked to repay, and `startEpoch`/`stopEpoch`/`getInstantWithdrawFunds`/`setIsProgrammableBorrower` all revert. Total loss equals the full pool NAV plus accrued receipts — effectively insolvency-by-deadlock. The deployment task itself shows the intended invariant (programmable mode requires `disableInstantWithdraw = true`) [7](#0-6) , but nothing on-chain enforces it.

### Likelihood Explanation
Triggering requires only an ordinary instant withdraw request during a running epoch after a sufficient APR change — an action any KYC'd lender can take in normal usage. The precondition is a single privileged misconfiguration (enabling programmable mode, or re-enabling instant withdrawals via `setInstantWithdrawParams(_delay, _aprDelta, false)` after the fact), which the code neither prevents at set time nor allows to be corrected once an epoch is live. The pattern is identical to the external report: two modes with incompatible reset/settlement logic are settable simultaneously.

### Recommendation
Enforce mode exclusivity in the setters:

- In `setInstantWithdrawParams`, revert when `_disable == false && isProgrammableBorrower` (mirroring the prefunded variant, which already forces `_disable` [4](#0-3) , and `IdleCDOEpochVariantPrefunded.sol` line 31-32).
- In `setIsProgrammableBorrower(true)`, revert unless `disableInstantWithdraw` is already true.
- Alternatively model the configuration as a single enum (`Normal | Programmable | Prefunded`) so incompatible flag combinations are unrepresentable.

### Proof of Concept
Foundry fork PoC sketch (anvil mainnet fork against an existing `IdleCDOEpochVariant` credit vault with instant withdrawals configured):

```solidity
function testProgrammableInstantDeadlock() external {
    // precondition: disableInstantWithdraw == false, owner enables programmable mode
    vm.prank(owner);
    cdoEpoch.setIsProgrammableBorrower(true);
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    // start an epoch (passes: minted on, no pending instant)
    vm.warp(cdoEpoch.epochEndDate() + cdoEpoch.bufferPeriod());
    vm.prank(manager);
    cdoEpoch.startEpoch();

    // warp lastEpochApr down so an instant request is triggered, then lender requests
    uint256 amt = 1_000e6;
    _depositAA(lender, amt); // before start in practice; shown for brevity
    vm.prank(lender);
    cdoEpoch.requestWithdraw(amt, address(trancheAA)); // routes to requestInstantWithdraw
    assertGt(strategy.pendingInstantWithdraws(), 0);

    // funding path bricked
    vm.expectRevert();
    vm.prank(manager);
    cdoEpoch.getInstantWithdrawFunds(); // reverts: isProgrammableBorrower

    // epoch can never stop
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.expectRevert();
    vm.prank(manager);
    cdoEpoch.stopEpoch(newApr, 0); // reverts: _pendingInstant() != 0

    // and the flag cannot be flipped back mid-epoch
    vm.expectRevert();
    vm.prank(owner);
    cdoEpoch.setIsProgrammableBorrower(false); // reverts: isEpochRunning
}
```

Uncertainty note: the exact `requestWithdraw` → instant-branch gating in `IdleCDOEpochVariant` (whether it checks `disableInstantWithdraw` per-request rather than only via `instantWithdrawAprDelta`/`lastEpochApr`) was not fully read; if instant requests are also blocked by an additional flag while programmable, the deadlock precondition additionally requires that flag's state, but the setter-level exclusivity gap described above stands regardless.

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;
  }
