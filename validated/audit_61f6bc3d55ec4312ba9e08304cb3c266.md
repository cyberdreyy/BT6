### Title
Front-runnable deterministic lockup address lets an attacker squat any owner's lockup with attacker-chosen terms - (`lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create` derives the new lockup's account ID purely from `owner_account_id` (`hex::encode(&env::sha256(owner_account_id)[..20])`) and lets *any* caller trigger creation for *any* `owner_account_id`, with no check that the caller is the owner or the foundation. Since NEAR account IDs are globally unique and can never be recreated once taken, whoever calls `create()` first for a given owner permanently owns that owner's canonical lockup address and its parameters.

### Finding Description
The invariant the protocol relies on is: `lockup_account_for(owner) == terms chosen by owner's real grantor`. This is broken because: [1](#0-0) [2](#0-1) 

`create` only asserts `env::attached_deposit() >= MIN_ATTACHED_BALANCE` — no `assert_eq!(env::predecessor_account_id(), owner_account_id)` and no foundation-only gate. `owner_account_id`, `lockup_duration`, `lockup_timestamp`, `vesting_schedule`, `release_duration`, and `whitelist_account_id` are all fully attacker-controlled parameters passed straight into `LockupArgs` and forwarded to the deployed lockup's `new` call: [3](#0-2) 

The target account (`lockup_account_id`) is a deterministic function of `owner_account_id` alone, so any unprivileged attacker can call `create(victim_owner, attacker_duration, ..., attacker_vesting_schedule, ..., attacker_whitelist)` with just `MIN_ATTACHED_BALANCE` attached (3.5 NEAR) before the victim's real grantor does. Because NEAR account IDs can never be reused once an account has existed there, the legitimate grantor's later `create()` call for the same owner fails at `create_account()` (account already exists), and the whole batch fails, refunded via `on_lockup_create`: [4](#0-3) 

The described edge case — "account created but `new` call fails" — makes this even worse: the multi-action receipt (`create_account`, `deploy_contract`, `transfer`, `function_call("new", ...)`) is not atomic in NEAR; if `create_account`/`deploy_contract`/`transfer` succeed but the final `function_call` to `new` panics (e.g. invalid vesting hash, malformed args, or any assertion inside the lockup's `new`), the account still exists with the lockup wasm deployed and NEAR balance transferred, but its state was never initialized. `on_lockup_create`'s `is_promise_success()` check treats the whole receipt as failed and only refunds the predecessor from the factory's own balance — it never attempts to delete or reclaim the now-permanently-squatted, uninitialized account: [5](#0-4) 

Either way (successful attacker-parameterized creation, or squatted/uninitialized account), the canonical address `hex(sha256(owner))+"."+factory` is permanently unusable for the real owner with legitimate, foundation-chosen terms. No existing guard (`assert_self`, `is_promise_success`, `MIN_ATTACHED_BALANCE` check) prevents an arbitrary caller from choosing `owner_account_id` and racing the real grant.

### Impact Explanation
This matches the Critical category "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." An attacker permanently claims a victim's canonical lockup address before the NEAR Foundation/grantor issues the real grant, either (a) deploying a fully-initialized lockup contract with attacker-chosen `vesting_schedule`, `lockup_duration`, `release_duration`, and `whitelist_account_id`, which any tooling/UI resolving "the lockup for account X" would treat as trusted, or (b) permanently squatting the address with an uninitialized, unusable contract, blocking the legitimate lockup from ever being created there. This is repeatable against any owner account whose grant hasn't been created yet, for the cost of `MIN_ATTACHED_BALANCE` (3.5 NEAR) per victim, so the blast radius spans every future NEAR Foundation grant recipient.

### Likelihood Explanation
Preconditions are minimal: the attacker needs to know or predict a future grant recipient's `owner_account_id` (e.g., publicly announced team members, well-known usernames) and hold `MIN_ATTACHED_BALANCE` (3.5 NEAR). No privileged role, key, or foundation status is required — `create` is a fully public, unauthenticated, payable method. The attack is trivially repeatable across any number of target owners.

### Recommendation
Restrict `create` so that only the `foundation_account_id` (or an authorized caller specified by the owner via signature/whitelist) may create a lockup for a given `owner_account_id`, e.g. `assert_eq!(env::predecessor_account_id(), self.foundation_account_id)`. Additionally, make the multi-action creation atomic from the caller's perspective by having `on_lockup_create` detect the "created-but-uninitialized" state (e.g. via a followup view call) — though the primary fix is authorization, since address squatting is possible even when `new` fully succeeds.

### Proof of Concept
`cargo test` in `lockup-factory` (extending existing `tests` module):
1. Initialize `LockupFactory` as in `test_create_lockup_success`.
2. As `attacker_account` (not `victim_owner`), call `contract.create(victim_owner, attacker_chosen_duration, None, attacker_vesting_schedule, None, Some(attacker_whitelist))` with `MIN_ATTACHED_BALANCE` attached; assert the call succeeds and derives `lockup_account_id = hex::encode(&sha256(victim_owner)[..20]) + "." + factory`.
3. Complete the promise chain (`testing_env_with_promise_results(..., PromiseResult::Successful(vec![]))`, then `contract.on_lockup_create(...)`); assert it returns `true` (lockup created with attacker's terms).
4. Simulate the real grantor (`foundation_account` acting on behalf of `victim_owner`) subsequently calling `contract.create(victim_owner, legit_duration, ..., legit_vesting_schedule, ...)`; in a real `near-workspaces`/`near-sdk-sim` integration test (not unit test, since account-existence collisions aren't modeled by `testing_env!`), assert `create_account` for the same `lockup_account_id` fails, the whole receipt fails, and `on_lockup_create` returns `false` with the deposit refunded — proving the legitimate lockup terms were never applied while the attacker's terms remain live at the canonical address, i.e. `lockup_account.vesting_schedule == attacker_vesting_schedule != legit_vesting_schedule`.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
