## Analog Found: Unvalidated fee amounts in `createDstEscrow` cause `EscrowDst._withdraw` to underflow-revert, letting funds redirect to the taker on cancellation

### Root-cause classification
The 1inch report's root cause is: a downstream function performs unguarded arithmetic (`sharesToTokens(...) - s.staked`) whose inputs can be set (via `commisionRate`) such that the subtraction produces a value that trips a `require`/underflow check, permanently blocking a legitimate claim (`redeemAllRewards`) even though value is actually owed. The analogous invariant in this repo is: **"funds owed to a party (fee recipients + maker) must never exceed the escrowed amount, so a subtraction of fees from `amount` never underflows."**

### Finding Description
`EscrowDst._withdraw` computes the maker's payout by subtracting fee amounts from the escrowed `amount`: [1](#0-0) 

```solidity
uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
...
uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
```

These fee values come straight from `immutables.parameters`, which for the destination escrow is populated when `createDstEscrow` is called: [2](#0-1) 

```solidity
function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
    ...
    IBaseEscrow.Immutables memory immutables = dstImmutables;
    immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
    if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

    bytes32 salt = immutables.hashMem();
    address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
    if (token != address(0)) {
        IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
    }
    ...
}
```

`createDstEscrow` never validates that `protocolFeeAmount + integratorFeeAmount < immutables.amount`. This is in sharp contrast to the source-side path (`_postInteraction`), which explicitly guards this exact invariant: [3](#0-2) 

```solidity
(uint256 integratorFeeAmount, uint256 protocolFeeAmount, bytes calldata tail) = FeeTaker._getFeeAmounts(...);
if (integratorFeeAmount + protocolFeeAmount >= takingAmount) revert InvalidFeeAmounts();
```

Because `dstImmutables` (including the fee sub-fields encoded in `parameters`) is fully caller-controlled calldata, the caller of `createDstEscrow` can freely encode `protocolFeeAmount + integratorFeeAmount >= amount`. `onlyValidImmutables` only checks that the supplied immutables hash matches the deployed clone's address/salt — it performs no semantic validation of the fee fields: [4](#0-3) 

When the maker later calls `withdraw`/`publicWithdraw` with the correct secret, `_withdraw`'s `immutables.amount - integratorFeeAmount - protocolFeeAmount` underflows under Solidity 0.8's checked arithmetic and reverts every single time, regardless of the secret being correct — exactly mirroring the external report's pattern of a legitimate claim reverting due to a bad but caller-influenced arithmetic input.

Critically, `cancel()` on the destination escrow does **not** subtract fees and returns the **full** `immutables.amount` to the taker: [5](#0-4) 

```solidity
function cancel(Immutables calldata immutables) ... {
    _uniTransfer(immutables.token.get(), immutables.taker.get(), immutables.amount);
    _ethTransfer(msg.sender, immutables.safetyDeposit);
    emit EscrowCancelled();
}
```

So once withdrawal is permanently bricked by an unvalidated fee configuration, the swap flow is forced into cancellation, and the entire deposited amount (including what should have gone to the protocol/integrator fee recipients and the maker) is returned to the taker who created the escrow, not the maker who was owed the funds.

### Impact Explanation
This is a business-logic failure reachable by an unprivileged caller of `createDstEscrow` (this is one of the explicitly allowed unprivileged entry points per the audit scope — "destination path: `createDstEscrow`"). The unprivileged caller supplies calldata fee values that violate the `fees < amount` invariant, causing:
- Permanent denial of the maker's withdrawal path for the entire lifetime of the escrow (temporary/permanent freezing of funds during the live swap lifecycle).
- Redirection of the full destination-side deposit back to the taker via `cancel()`, effectively letting the escrow creator recapture 100% of the funds while the maker (who already fulfilled their side on the source chain) receives nothing on the destination chain.

This matches the bounty's High-severity category ("temporary freezing of funds during the live swap lifecycle") and could also be framed as Medium ("smart contract unable to operate because required token/native balances can be broken by an unprivileged actor").

### Likelihood Explanation
High — no privileged role or validator/oracle collusion is required. Any address calling `createDstEscrow` directly controls the entire `dstImmutables.parameters` payload, including fee amounts, since there is no cross-check against a corresponding on-chain commitment from the source-chain `SrcEscrowCreated` event/order data.

### Recommendation
Add the same guard used on the source side to `createDstEscrow`:
```solidity
if (dstImmutables.integratorFeeAmount() + dstImmutables.protocolFeeAmount() >= dstImmutables.amount) revert InvalidFeeAmounts();
```
Alternatively, derive/validate the destination fee parameters against the `DstImmutablesComplement` emitted during `_postInteraction` rather than trusting arbitrary caller-supplied `parameters`.

### Proof of Concept
1. Attacker (any address, acting as `taker`) calls `createDstEscrow` with `dstImmutables.amount = 100`, `parameters` encoding `protocolFeeAmount = 60`, `integratorFeeAmount = 60` (sum = 120 > 100), and deposits the required 100 tokens + safety deposit.
2. Escrow deploys successfully — no validation rejects the malformed fee split.
3. After the withdrawal window opens, the maker calls `withdraw(secret, immutables)` with the correct secret; `_withdraw` computes `100 - 60 - 60` which underflows and reverts (Panic 0x11), for every subsequent attempt, including `publicWithdraw`.
4. After the cancellation timelock elapses, the attacker (as `taker`) calls `cancel(immutables)`, which transfers the full `100` tokens back to themselves plus the safety deposit — the maker receives nothing despite having fulfilled the source-chain leg of the swap.

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }

    function protocolFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {

        }

    /**
     * @notice Returns the integrator fee amount from the immutables (calldata version).

    function integratorFeeAmountCd(IBaseEscrow.Immutables calldata immutables) external pure returns (uint256 ret) {
        bytes calldata parameters = immutables.parameters;

        assembly ("memory-safe") {
