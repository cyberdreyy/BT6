I found `add_block_signature` in `stacks-signer/src/signerdb.rs` correctly deletes the corresponding rejection entry when a signature arrives (symmetric cleanup), but the reverse direction has no such symmetry guarantee: `add_block_rejection_signer_addr` needs to be checked for whether it deletes a prior signature entry.## Title
Stale accepted-signature weight is not cleared on a later rejection, letting one signer's weight double-count toward both the 70% accept and 30%+ reject tallies - ([File: stacks-signer/src/signerdb.rs])

### Summary
`SignerDb::add_block_signature` cleans up any prior rejection recorded for the same `(block_sighash, signer_addr)` before inserting a signature, guaranteeing that an "accept" overwrites an earlier "reject" for weight-tallying purposes. `SignerDb::add_block_rejection_signer_addr` has no matching cleanup: it never removes a prior row from `block_signatures` when a signer later sends a rejection for a block it had already signed. This breaks the invariant that a single signer's weight should count toward at most one side of the 70%/30% threshold split, exactly mirroring the reported bug class (a balance/credit is increased on one path but the corresponding decrease on the reciprocal path is missing).

### Finding Description
`add_block_signature` explicitly deletes the corresponding `block_rejection_signer_addrs` row before inserting the signature: [1](#0-0) 

This design intentionally makes "accept" the authoritative, later-wins state relative to "reject" for a given signer/block pair.

`add_block_rejection_signer_addr`, however, only touches the `block_rejection_signer_addrs` table (checking/inserting/updating `reject_code`) — it performs no corresponding `DELETE FROM block_signatures`: [2](#0-1) 

Consequently, if a signer address `S` first has its acceptance signature stored (`add_block_signature`) and later sends a `Rejected` response for the same block (a state transition explicitly documented as valid: `LocallyAccepted --> LocallyRejected : re-evaluated`), both:
- `get_block_signatures(block_hash)` (used by `compute_signature_signing_weight` in `store_and_process_block_signature`)
- `get_block_rejection_signer_addrs(block_hash)` (used by `compute_signature_signing_weight`/`compute_reject_code_signing_weight` in `store_and_process_block_rejection`)

will simultaneously include `S`'s weight: [3](#0-2) [4](#0-3) 

This means `total_signature_weight` (accept tally) and `total_reject_weight` (reject tally), computed independently from these two tables via `compute_signature_signing_weight`/`compute_reject_code_signing_weight`, can share overlapping weight for `S`, so `total_signature_weight + total_reject_weight` can exceed `total_weight`. That breaks the equality the state machine relies on: that the accept-weight and reject-weight partitions are disjoint subsets of the total signer weight.

### Impact Explanation
Because `store_and_process_block_signature` can already have driven the block to `LocallyAccepted`/broadcast (`mark_locally_accepted(true)`, `broadcast_signed_block`) using `S`'s counted weight, and `BlockInfo::check_state` permits `LocallyAccepted --> GloballyRejected` as long as the block was never `GloballyAccepted`: [5](#0-4) 

a subsequent rejection tally that double-counts `S`'s weight (previously already spent toward the accept threshold) can push the block to `mark_globally_rejected()`: [6](#0-5) 

This produces a signer-local state that contradicts an action it already took (having signed and broadcast the block), i.e., a rejection is "recounted" using weight that logically already belongs to the accept side. This is exactly the impact category "a rejection recounted as an accept" (here, the reverse — accept weight silently retained under a reject tally), and can wedge the signer's view of consensus into disagreement with what it already published to the node, or contribute to reaching the 30% blocking-minority threshold with weight that should have already been retired.

### Likelihood Explanation
No majority of signers or key compromise is required. The trigger is a single signer address flipping its vote from accept to reject for the same block hash — a transition the code explicitly documents and supports (`LocallyAccepted --> LocallyRejected: re-evaluated`) and that ordinary gossip/re-evaluation logic can produce (e.g., a signer that accepted a block, then later re-evaluates and rejects it after a conflicting proposal or chainstate recheck). The bug is purely a bookkeeping asymmetry between two DB write paths, so it is reached anytime this normal flip occurs, which is a realistic operational scenario, not an attacker-controlled edge case requiring privileged access.

### Recommendation
In `SignerDb::add_block_rejection_signer_addr` (`stacks-signer/src/signerdb.rs`), mirror the cleanup done in `add_block_signature`: before inserting/updating the rejection row, execute `DELETE FROM block_signatures WHERE signer_signature_hash = ?1 AND signer_addr = ?2` so a later rejection retires any previously counted acceptance weight for that signer, keeping the accept/reject weight partitions disjoint.

### Proof of Concept
1. Signer `S` sends a valid `Accepted` response for block `B`. The receiving signer calls `store_and_process_block_signature`, which calls `add_block_signature(B, S, sig)`, inserting into `block_signatures`. `total_signature_weight` in `compute_signature_signing_weight` now includes `S`.
2. Due to a later re-proposal/re-evaluation (or simple out-of-order/duplicate gossip), `S` sends `Rejected` for `B`. `store_and_process_block_rejection` calls `add_block_rejection_signer_addr(B, S, reason)`, inserting into `block_rejection_signer_addrs` — the `block_signatures` row for `S` is left untouched.
3. `get_block_signatures(B)` still returns `S`'s signature, so `total_signature_weight` still includes `S`'s weight; `get_block_rejection_signer_addrs(B)` also now includes `S`. Both `compute_signature_signing_weight` (accept path) and `compute_reject_code_signing_weight`/rejection-weight computation (reject path) count `S`'s weight simultaneously, allowing `total_signature_weight + total_reject_weight > total_weight` and potentially the reject tally reaching consensus on a block this local signer already marked/broadcast as accepted.

Note: I was unable to view the full body of `add_block_rejection_signer_addr` above line 1950 (only the tail matching arms were retrieved), so I cannot rule out that an early, unseen part of the function performs the missing deletion — but nothing in the observed code, tests (`reject_then_accept` only tests the accept-after-reject direction), or documentation (`docs/signer-flows.md` section 6, which only describes accept overwriting reject implicitly) suggests the reverse cleanup exists.

        &self,
        block_sighash: &Sha512Trunc256Sum,
        signer_addr: &StacksAddress,
        signature: &MessageSignature,
    ) -> Result<bool, DBError> {
