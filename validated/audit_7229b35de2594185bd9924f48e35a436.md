### Title
Unauthenticated `MethodPublicKeyGet` can squat an owner-prefixed `activeRequests` key and block a legitimate authorized secrets request - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
`h.activeRequests` in `handler.go` is a single shared map keyed by `req.ID` used by both the unauthenticated `MethodPublicKeyGet` path and the authorized secrets methods. Because `MethodPublicKeyGet` skips `h.requestProcessor.ProcessRequest` (and therefore the owner-prefixing performed in `GatewayVaultRequestProcessor.authorizeAndStamp`), an unauthenticated caller fully controls the raw key inserted into `h.activeRequests`, including keys of the form `"<owner>:<originalRequestID>"` that a legitimate authorized request would later compute and try to register.

### Finding Description
In `HandleJSONRPCUserMessage` [1](#0-0) , when `req.Method == vaulttypes.MethodPublicKeyGet`, the code calls `h.newActiveRequest(req, callback)` directly with the client-supplied, unmodified `req.ID` (subject only to the empty/200-char checks at lines 404-410), bypassing `h.requestProcessor.ProcessRequest` entirely.

For authorized secrets methods (`MethodSecretsCreate/Update/Delete/List`), `ProcessRequest` is called first [2](#0-1) , which internally calls `authorizeAndStamp`. That function rewrites `req.ID` to `authorizedOwner + vaulttypes.RequestIDSeparator + originalRequestID` **before** `newActiveRequest` is invoked [3](#0-2) . Because `req` is passed by pointer into `ProcessRequest`, this mutation persists back into the caller's `req` used at line 447.

`newActiveRequest` itself is method-agnostic and simply keys on whatever `req.ID` it is given [4](#0-3) :
```go
if h.activeRequests[req.ID] != nil {
    return nil, errors.New("request ID already exists: " + req.ID)
}
```

Because the unauthenticated `MethodPublicKeyGet` path never strips/adds a prefix and there is no charset restriction on `req.ID` (only a length cap of 200), an unauthenticated attacker can craft a `PublicKeyGet` request whose `req.ID` is literally `"<victim-owner-address><RequestIDSeparator><guessed-original-request-id>"`. If the attacker registers that entry first (only possible while the public key is not yet cached, i.e. `h.getCachedPublicKey()` returns nil — line 417), the entry occupies `h.activeRequests[key]`. When the victim's legitimate, fully authorized secrets request later computes the same prefixed ID via `authorizeAndStamp` and calls `newActiveRequest`, it will be rejected with `"request ID already exists"`, even though the victim never collided with anything themselves — the collision was manufactured by an unauthenticated actor from a different, unauthenticated code path.

This directly violates the stated isolation invariant: an unauthenticated method (`MethodPublicKeyGet`) is able to interact with and interfere with authorized users' request state.

### Impact Explanation
This is a cross-privilege-boundary interference / denial-of-service on a specific victim's secrets operation: an unauthenticated caller can cause a legitimate, fully-authorized `SecretsCreate/Update/Delete/List` request to fail with an internal-looking "request ID already exists" error, without ever passing authorization. It also creates an oracle: if the attacker's guess-and-squat attempt itself fails with "request ID already exists" (because the victim registered first), that confirms a request with that owner/ID pair is currently in flight — a minor existence-leak. The impact is scoped to availability/interference of a single guessed request rather than key or secret disclosure or fund movement, but it does breach the intended isolation between the unauthenticated public-key path and the authenticated request namespace.

### Likelihood Explanation
Exploitability hinges entirely on the attacker's ability to guess two values ahead of time: (1) the victim's `authorizedOwner` (a workflow/DON owner address, which in the CRE/vault model is often a known, non-secret identifier rather than a per-request secret), and (2) the exact `originalRequestID` the victim's client will submit for a not-yet-cached-public-key window. This second value is normally caller-chosen (e.g., a UUID), which is not realistically guessable unless a deployment generates predictable/sequential/deterministic request IDs (e.g., derived from a public workflow execution ID). Additionally, the race is only viable while `h.getCachedPublicKey()` returns nil, i.e., before the public key has been cached (the code notes it is "cache[d] quite aggressively," narrowing the exploit window mostly to node startup or cache-eviction periods). Given these two independent guessing/timing requirements, likelihood is low in typical deployments but the underlying isolation gap in the code is real and not mitigated by any explicit check.

### Recommendation
Give the unauthenticated `MethodPublicKeyGet` path its own request-ID namespace, separate from the authorized-request namespace, e.g., by prefixing all `PublicKeyGet` request IDs with a fixed, reserved sentinel (distinct from `vaulttypes.RequestIDSeparator`-based owner prefixes) before calling `newActiveRequest`, or by maintaining a separate map for unauthenticated public-key requests. Additionally, reject/strip any client-supplied `req.ID` containing `vaulttypes.RequestIDSeparator` on the unauthenticated path so it can never collide with an owner-prefixed key.

### Proof of Concept
Go unit test plan in `core/services/gateway/handlers/vault/handler_test.go`:
1. Construct a `handler` with `h.cachedPublicKeyObject == nil` (no cached key) so the `PublicKeyGet` path reaches `newActiveRequest`.
2. Determine (or mock the authorizer to return) a known `authorizedOwner` value, e.g. `"0xOwner"`, and pick `originalRequestID = "abc"`. Compute `victimKey = "0xOwner" + vaulttypes.RequestIDSeparator + "abc"`.
3. As the unauthenticated attacker, call `h.HandleJSONRPCUserMessage(ctx, jsonrpc.Request{ID: victimKey, Method: vaulttypes.MethodPublicKeyGet}, callback)` and assert it succeeds, registering `h.activeRequests[victimKey]`.
4. As the victim, call `h.HandleJSONRPCUserMessage(ctx, jsonrpc.Request{ID: "abc", Method: vaulttypes.MethodSecretsCreate, Auth: validAuthForOwner0xOwner, Params: validCreateSecretsParams}, callback)` with a mock `requestProcessor` that authorizes the request and stamps `req.ID = victimKey` per `authorizeAndStamp` logic.
5. Assert the victim's call returns the error `"request ID already exists: " + victimKey"` even though the victim never previously submitted a conflicting request — demonstrating that an unauthenticated `PublicKeyGet` request blocked an authorized secrets request.
6. (Optional oracle test) Reverse the order — victim registers first — then attacker submits the colliding `PublicKeyGet` and observe the attacker receives an error confirming the ID/owner pair is active, demonstrating the information-leak variant.

```go
func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
```
