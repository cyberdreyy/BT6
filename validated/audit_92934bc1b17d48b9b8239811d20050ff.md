### Title
Loss-adjusted withdrawals only haircut the latest epoch's receipt — earlier-epoch pending requests in the same unfunded `pendingWithdraws` bucket are paid at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` can underfund `pendingWithdraws` and records a single `lossRecoveryPriceByEpoch[epochNumber]` (IdleCreditVault.sol:411-421). But claim-side loss accounting is keyed to a single pointer, `lastWithdrawRequest[_user]`, while the funded-claim path pays the *aggregate* `withdrawsRequests[_user]` at par. A user with receipts spanning the loss epoch and an earlier epoch has only the latest-epoch slice haircut; the earlier slice — which was equally part of the underfunded `pendingWithdraws` — is paid 1:1 via `_claimFundedWithdrawRequest`, draining underlyings that were only partially funded and leaving other claimants short. This mirrors the CVE bug class: a shared container (the aggregate receipt) is treated as fully owned/funded while part of it belongs to a haircut bucket, so one "append" (the par payout) consumes value accounted elsewhere.

### Finding Description
At `requestWithdraw`, receipts for every epoch are summed into `withdrawsRequests[_user]` and per-epoch `withdrawsRequestsByEpoch[_user][epoch]`, and the single `lastWithdrawRequest[_user]` is overwritten with the newest epoch (IdleCreditVault.sol:282-293). The only guard against mixing a loss-adjusted epoch with new requests checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (lines 261-271) — i.e., it only inspects the *latest* epoch.

Claim flow (lines 301-350):
1. `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, clears **only that epoch's** bucket via `_clearWithdrawClaimForEpoch`, and pays `claimBasis * lossRecoveryPrice / RECOVERY_FULL` (lines 789-800, 811-837). It also zeroes `lastWithdrawRequest` (line 835).
2. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[_user]` — which still contains the earlier-epoch request — at par, with the guard `epochNumber <= lastWithdrawRequest` now bypassed because `lastWithdrawRequest` was reset to 0 (lines 326-349).

`pendingWithdraws` at the loss epoch included **both** the earlier-epoch and loss-epoch receipts, yet only `amount < pendingBasis` was funded (line 414). The earlier-epoch portion was never separately funded at par — it shared the same underfunded pot. Paying it at par breaks the loss-socialization invariant: the first user to claim extracts more than their pro-rata share of the funded amount, and the shortfall is borne by later claimants whose payouts revert on insufficient balance or are implicitly reduced.

Attack sequence (unprivileged KYC'd lender):
1. Buffer of epoch N: `requestWithdraw` amount X. Epoch N runs and ends fully funded... actually simpler: request X in epoch N, then *before claiming* request Y in epoch N+1 (permitted — `lastWithdrawRequest` is just updated to N+1; note at lines 323-324 documents this delay-both-requests behavior). `pendingWithdraws` = X + Y.
2. Epoch N+1 ends underfunded: `collectWithdrawFunds(amount < X + Y)` sets `lossRecoveryPriceByEpoch[N+1] = p < RECOVERY_FULL`.
3. `claimWithdrawRequest`: receives `Y * p` (loss-adjusted) **plus** `X` at par — total `X + Y·p`, while only `(X + Y)·p` was ever funded for this user.
4. Other users' loss-adjusted claims (`claimBasis · p`) now exceed the remaining balance → last claimants are underpaid or permanently unable to claim the funded remainder.

### Impact Explanation
Direct theft / insolvency with quantified loss: the attacker extracts `X·(1 − p)` more underlyings than funded for their position. With a 50% recovery price and equal earlier/latest requests, they recover ~75% of total basis while the vault funded only 50% — the excess is taken from underlyings reserved for other loss-adjusted claimants, who then cannot be made whole.

### Likelihood Explanation
Requires an epoch that stops underfunded (`stopEpochWithDuration`/`collectWithdrawFunds` partial funding), which is a designed recovery mode, plus a user holding unclaimed receipts across two consecutive epochs — a normal usage pattern explicitly contemplated by the code comments. The attacker must be a whitelisted lender; no privileged collusion is needed since loss epochs are initiated by honest manager calls. Impact is bounded to the haircut shortfall (medium), matching the source CVE's medium severity.

### Recommendation
In `_claimLossAdjustedWithdrawRequest` (or `collectWithdrawFunds`), apply the epoch's `lossRecoveryPrice` to the **entire** `withdrawsRequests[_user]`/`apr0` basis that was outstanding when the loss epoch closed, not only the `lastWithdrawRequest` epoch slice — e.g., clear and haircut all epochs ≤ loss epoch, or track per-epoch funding ratios so each bucket is paid exactly its funded share. Alternatively, make `requestWithdraw` revert whenever *any* unclaimed earlier-epoch receipt exists once a loss price is recorded for a prior epoch, and iterate all epochs with `lossRecoveryPriceByEpoch` set during claims rather than relying on the single `lastWithdrawRequest` pointer.

### Proof of Concept
```solidity
// Foundry fork test sketch (harness mirrors test/foundry/IdleCreditVault.t.sol)
function testLossEpochOnlyHaircutsLatestRequest() external {
    _useStandardEpochVariant();
    uint256 amount = 10_000 * ONE_SCALE;
    _depositWithUser(attacker, amount); // KYC'd lender

    // Epoch N: request X
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(xTranches, address(AAtranche));
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, apr, expectedFunds); // epoch N+1 begins

    // Epoch N+1: request Y (lastWithdrawRequest -> N+1, withdrawsRequests = X+Y)
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(yTranches, address(AAtranche));
    _startEpochAndCheckPrices(1);

    // Epoch N+1 ends underfunded: fund only 50% of pendingWithdraws (X+Y)
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    _stopEpochWithPartialFunding(pending / 2); // lossRecoveryPriceByEpoch[N+1] = 0.5e18

    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // Funded for this user was (X+Y)*0.5, but they receive X + Y*0.5
    assertEq(got, xClaim + yClaim / 2);          // overpayment = xClaim/2
    assertGt(got, (xClaim + yClaim) / 2);        // exceeds funded share
    // Subsequent victims' loss-adjusted claims now lack underlying balance.
}
```

Caveat: the exact epoch index used as the key in `lossRecoveryPriceByEpoch` depends on whether `epochNumber` is incremented before or after `collectWithdrawFunds` inside `stopEpoch` in `IdleCDOEpochVariant.sol` (I was unable to verify that ordering within the iteration budget). If the price is keyed to the *following* epoch rather than the request epoch, the same flaw manifests even more severely: `lossRecoveryPriceByEpoch[lastWithdrawRequest]` would never be found and the entire underfunded receipt would pay at par. Either ordering leaves a live vulnerability; the PoC should assert the actual keying once confirmed.
