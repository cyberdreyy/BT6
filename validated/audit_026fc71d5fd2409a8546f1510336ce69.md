### Title
`getLargestAccounts` commitment bypass via unkeyed cache returns unrooted/processed data as finalized - ([File: rpc/src/rpc_cache.rs])

### Summary
`LargestAccountsCache` stores cached largest-accounts results keyed **only** by `Option<RpcLargestAccountsFilter>`, with no `CommitmentConfig`/bank identity in the key. A single unprivileged client that calls `getLargestAccounts` once with a low commitment (`processed`/default) and then again with `finalized` within the cache TTL (`self.duration` seconds) will receive the cached `slot`/`accounts` pair that was actually computed from the earlier, less-committed bank, mislabeled as a `finalized` response.

### Finding Description
`LargestAccountsCache::get_largest_accounts` and `set_largest_accounts` in `rpc/src/rpc_cache.rs` operate on `cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>` [1](#0-0) . The lookup and insertion logic only consult/store by `filter`, checking solely elapsed time against `self.duration` for freshness [2](#0-1) . There is no field in `LargestAccountsCacheValue` recording which bank, slot-commitment level, or bank hash produced the cached `slot`/`accounts`, and no commitment parameter is threaded through `get_largest_accounts`/`set_largest_accounts`.

In `JsonRpcRequestProcessor::get_largest_accounts` (`rpc/src/rpc.rs`), the handler resolves a bank according to the requested `commitment` (e.g., `processed` picks the most recent, possibly unrooted bank; `finalized` should pick a rooted bank), then consults the shared `largest_accounts_cache` before doing the (expensive) computation. Because the cache entry keyed by `filter` alone is reused across calls regardless of the commitment used to populate it, a `finalized`-commitment request that hits a still-fresh cache entry populated by an earlier `processed`-commitment call will return the processed bank's `slot` and `accounts` verbatim, without ever consulting a rooted bank.

This breaks the RPC invariant that `finalized` responses must derive from rooted state: the attacker only needs to issue two ordinary JSON-RPC calls (`processed` then `finalized`) from a single unprivileged client within the TTL window, well under the one-call-per-`CLUSTER_SLOT_TIME_TARGET/2` threshold.

### Impact Explanation
This is a commitment/fork-correctness violation: a client explicitly requesting `finalized` largest-account data can be served slot/account data computed from an unrooted, potentially-reverted bank. Downstream consumers (e.g., wallets, exchanges, monitoring tooling) that rely on `finalized` meaning "safe/rooted" may act on data that can later be invalidated by a fork choice change, i.e., wrong-slot/fork data returned to a caller under a security-relevant commitment guarantee.

### Likelihood Explanation
Fully reachable with default configuration: the cache is constructed with `duration` > 0 (non-zero cache TTL is the default), requires no special privileges, no interleaving from other clients, and no more than two ordinary calls from one client within the cache window. The exploit is deterministic given a slot change/fork-reordering event between the two calls, and trivially repeatable each time the largest-accounts ordering shifts between an unrooted bank and its eventual rooted successor.

### Recommendation
Include the resolved commitment level (or, more robustly, the bank's slot and hash/rooted status) in the `LargestAccountsCache` key, or simply skip/refresh the cache whenever the requested commitment differs from the commitment level used to populate the cached entry. At minimum, do not serve a cached entry produced under a lower commitment level to a request specifying a stricter (`confirmed`/`finalized`) commitment.

### Proof of Concept
Integration test outline against `JsonRpcRequestProcessor`:
1. Create a test bank at slot `N`, advance/mutate accounts so that `get_largest_accounts` ordering differs from what it will be after rooting.
2. Call the RPC handler for `getLargestAccounts` with `filter=Circulating`, `commitment=processed` while bank `N` is unrooted; assert this populates `LargestAccountsCache` via `set_largest_accounts(&filter, N, accounts_processed)`.
3. Immediately (within `duration` seconds) advance the bank to slot `N+k`, root it, and change account balances so `get_largest_accounts` on the rooted bank would return different `accounts`/`slot`.
4. Call the RPC handler again with the same `filter`, `commitment=finalized`.
5. Assert (bug reproduction) that the returned `slot`/`accounts` equal the stale `(N, accounts_processed)` cached value from step 2, instead of the rooted `(N+k, accounts_rooted)` — demonstrating the finalized response derives from unrooted state.

Unit-level companion test in `rpc/src/rpc_cache.rs` can directly show the key collision: call `set_largest_accounts(&Some(Circulating), N, accounts_a)` then `get_largest_accounts(&Some(Circulating))` and observe it returns `(N, accounts_a)` with no way to distinguish or invalidate based on commitment, confirming the missing key dimension.

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }

    pub(crate) fn set_largest_accounts(
        &mut self,
        filter: &Option<RpcLargestAccountsFilter>,
        slot: u64,
        accounts: &[RpcAccountBalance],
    ) {
        self.cache.insert(
            filter.clone(),
            LargestAccountsCacheValue {
                accounts: accounts.to_owned(),
                slot,
                cached_time: SystemTime::now(),
            },
        );
    }
