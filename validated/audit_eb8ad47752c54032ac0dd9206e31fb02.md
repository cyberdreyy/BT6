### Title
Stale-epoch instant-withdraw receipts bypass the default recovery haircut and are paid at par from the recovery reserve - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to CVE-2024-33600 (a "not-found" lookup result being consumed as if it were a hit), `IdleCreditVault._claimDefaultedInstantWithdrawRequest` looks up a defaulted instant receipt only under `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]`. A receipt created in an earlier epoch is a "not-found" hit for that key, so the code falls through to the funded-claim path and pays `instantWithdrawsRequests[user]` in full from underlying held by the strategy — which after `finalizeDefaultRecovery` is the haircutted `defaultRecoveryReserve`. The stale receipt's basis was also never included in `defaultPendingClaimBasis`, which only adds `instantWithdrawClaimsByEpoch[epochNumber]` (the current/default epoch), so the recovery price was computed without it.

### Finding Description
- `requestInstantWithdraw` records receipts per request epoch: `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount` and `instantWithdrawClaimsByEpoch[currentEpoch] += _amount`, and bumps the aggregate `pendingInstantWithdraws` (IdleCreditVault.sol:367-374). Nothing forces the receipt to be claimed or funded before the epoch rolls.
- At default finalization, `defaultPendingClaimBasis()` adds only `instantWithdrawClaimsByEpoch[epochNumber]` — the current epoch — to the recovery basis (IdleCreditVault.sol:644-649). `_defaultPrefundedInstantReserve` uses the same current-epoch key (lines 716-723). An unfunded instant receipt from an older epoch contributes to `pendingInstantWithdraws` but its claim basis is excluded from `totalBasis`, so `defaultRecoveryPrice` is set without it.
- Because `pendingInstantWithdraws != 0`, `defaultInstantWithdrawsFinalized` is set true (line 696). When the stale-epoch user claims, `_claimDefaultedInstantWithdrawRequest` reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — zero for the old-epoch receipt — and returns early without clearing anything (lines 842-845).
- `claimInstantWithdrawRequest` then proceeds: `amount = instantWithdrawsRequests[_user]` (still nonzero), burns the receipt, and calls `_transferFundedClaim(_user, amount)` (lines 387-392), paying the full unhaircutted amount out of the strategy's underlying balance — the recovery reserve meant to be shared pro rata at `defaultRecoveryPrice`.

No guard stops this: `requestInstantWithdraw` has no staleness check on prior epoch receipts, and the claim path treats "not found at defaultEpoch" as "nothing to haircut" rather than reverting.

### Impact Explanation
Direct theft of recovery funds. The stale-epoch instant receipt holder receives 100% of their claim while every other claimant (active LPs via the repriced NAV, defaulted normal receipts, same-epoch instant receipts) is paid `basis * defaultRecoveryPrice / 1e18`. Since the stale basis was excluded from `totalBasis`, the reserve is underprovisioned by exactly the stale claim amount; the last claimants to withdraw (or `_claimPostDefaultWithdrawRequest`/`_claimDefaultedWithdrawRequest` callers drawing on `defaultRecoveryReserve`) are left unpaid — a broken "one receipt, haircutted payout" invariant and effective insolvency of the recovery reserve up to the size of cross-epoch instant receipts.

### Likelihood Explanation
Requires an instant withdraw request to remain unclaimed across at least one `stopEpoch`/`startEpoch` boundary and a subsequent borrower default before it is claimed. Instant receipts are normally funded quickly via `collectInstantWithdrawFunds`, but the code explicitly permits unfunded instant requests to persist (`pendingInstantWithdraws` is a standalone counter and `claimInstantWithdrawRequest` has no epoch gate). An unprivileged user can open an instant request during a buffer period; if the borrower fails to fund it before epoch rollover and later defaults, the payout-at-par path is reached through a single `claimInstantWithdrawRequest` call by that user via the CDO. Conditions are uncommon but fully attacker-influenced on the request side.

### Recommendation
- In `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve`, account for all outstanding instant claim basis, not only `instantWithdrawClaimsByEpoch[epochNumber]` (e.g., track a global `instantWithdrawClaimsTotal`, or settle/sweep stale-epoch receipts into the current epoch key at `stopEpoch`).
- In `_claimDefaultedInstantWithdrawRequest`, treat a nonzero `instantWithdrawsRequests[_user]` with zero `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` as an unfunded defaulted receipt: haircut it by `defaultRecoveryPrice` and pay via `_transferDefaultRecovery` instead of falling through to the par `_transferFundedClaim` path.
- Alternatively, revert in `claimInstantWithdrawRequest` when `defaultRecoveryFinalized` and the user's receipt epoch is not `defaultRecoveryEpoch`, forcing claims through an explicit epoch-aware path.

### Proof of Concept
Foundry fork sketch (mirroring `test/foundry/IdleCreditVault.t.sol` helpers such as `_depositWithUser`, `_startEpochAndCheckPrices`, `_checkDefault`):

```solidity
// Setup: users STALE (instant receipt in epoch N) and NORMAL (active LP).
_depositWithUser(STALE, 10_000 * ONE_SCALE, true);
_depositWithUser(NORMAL, 10_000 * ONE_SCALE, true);

// Epoch N buffer: STALE requests an instant withdraw via the CDO.
vm.prank(STALE);
cdoEpoch.requestInstantWithdraw(STALEshares, address(AAtranche));
uint256 staleAmount = IdleCreditVault(address(strategy)).instantWithdrawsRequests(STALE);
// Borrower never funds it: pendingInstantWithdraws stays nonzero.

// Roll the epoch so epochNumber advances past STALE's request epoch.
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, 0); // epochNumber = N+1

// Run a new epoch and force borrower default in epoch M > N.
vm.prank(manager); cdoEpoch.startEpoch();
deal(defaultUnderlying, strategy.borrower(), 0, true);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(cdoEpoch.owner()); cdoEpoch.stopEpoch(0, 0);
assertTrue(cdoEpoch.defaulted());

// Finalize with partial recovery, e.g. 50%.
uint256 recovered = partial;
deal(defaultUnderlying, manager, recovered);
vm.startPrank(manager);
underlying.approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
uint256 price = IdleCreditVault(address(strategy)).defaultRecoveryPrice();
assertLt(price, 1e18);

// Exploit: STALE's receipt is keyed at epoch N, but defaultRecoveryEpoch = M.
// _claimDefaultedInstantWithdrawRequest finds 0 at [STALE][M] and returns early;
// claimInstantWithdrawRequest then pays the FULL receipt from the reserve.
uint256 balPre = underlying.balanceOf(STALE);
vm.prank(STALE);
cdoEpoch.claimInstantWithdrawRequest();
assertEq(underlying.balanceOf(STALE) - balPre, staleAmount); // paid at par, not * price / 1e18

// Consequence: reserve drained — another claimant's haircutted payout now underflows/fails.
vm.prank(NORMAL);
cdoEpoch.claimWithdrawRequest(); // receives less than basis * price, or reverts on insufficient reserve
```
