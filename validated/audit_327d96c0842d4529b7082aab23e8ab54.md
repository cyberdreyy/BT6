## Finding

The core-contracts--012 repo contains a NEAR-specific analog of the Blueberry bug (a value used to gate an authorization decision that is not kept in sync with the actual, current state). Here the equivalent binding is **confirmations counted toward the `num_confirmations` threshold must correspond to currently-live multisig members/keys** — but `delete_member`/`DeleteKey` only purges *requests originated by* the removed member, not *confirmations already cast by* that member on other still-pending requests. ### Title
Stale confirmations from removed multisig members/keys are still counted toward the execution threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` executes a request once `confirmations.len() + 1 >= self.num_confirmations` [4](#0-3) . `delete_member` (in `multisig2`) and the `DeleteKey` action (in `multisig`) only clean up **requests that the removed member/key itself created**, filtering on `r.member == member` / `r.signer_pk == pk` [5](#0-4) [6](#0-5) . Neither routine scans the `confirmations` map for entries where the removed member/key had merely *confirmed* someone else's still-pending request. As a result, a confirmation cast by a member who is later removed remains permanently counted against `num_confirmations` for that unrelated request.

### Finding Description
The invariant that should hold is: `confirmations counted for request R == confirmations from accounts that are members at the time R is executed`. This is violated because:
1. Member/Key `A` confirms pending request `R` (not yet enough confirmations to execute).
2. The multisig later executes `DeleteMember { member: A }` (or `DeleteKey`) via a separate, properly-confirmed request. `delete_member`/`DeleteKey` removes `A` from `self.members` (or revokes the on-chain access key) and clears only requests `A` itself had submitted — `R` is untouched because `R.member != A` [7](#0-6) [8](#0-7) .
3. `R`'s confirmation set still contains `A`'s (now-invalid) confirmation.
4. A remaining member confirms `R`. `confirm()` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` — it never re-validates that every entry in `confirmations` still belongs to `self.members` [9](#0-8) .
5. `R` executes with fewer *currently authorized* signers than `num_confirmations` actually requires, because one "vote" belongs to an entity that is no longer part of the trust set.

The same pattern exists in the original `multisig` contract: `DeleteKey` purges requests keyed by `signer_pk == pk` but leaves that key's confirmations on other pending requests intact [2](#0-1) .

### Impact Explanation
This directly breaks the authorization/threshold binding the multisig is meant to enforce: "a request is executed only if `num_confirmations` *currently authorized* signers approved it." A malicious or compromised member (e.g., one whose key is being revoked precisely because it's compromised) can pre-seed a confirmation on an arbitrary request (e.g., a `Transfer` or `AddKey`/`FunctionCall`), get removed, and that ghost confirmation still lets the remaining members execute the request with one fewer *live* approver than intended — effectively executing a request below the true, current threshold (Critical class: "a multisig request executed below threshold").

### Likelihood Explanation
This requires a normal, expected operational sequence — confirm a request, then remove a member/key (a routine security operation, e.g. revoking a lost or compromised key) — with no attacker needing any special privilege beyond having been a legitimate member at some point. This is a realistic and even common operational scenario for any long-lived multisig wallet that rotates its signers.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, also scan all pending requests' `confirmations` sets and remove the entry for the deleted member/key (not just requests it authored). Alternatively, when checking `confirm()`'s threshold, re-validate that every stored confirming identity is still present in `self.members` (or a live access key on-chain) before counting it toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `[A, B, C]`, `num_confirmations = 2`.
2. `A` calls `add_request_and_confirm(R)` where `R = Transfer{...}` to some receiver — `R` now has 1 confirmation (`A`), short of the threshold of 2.
3. Separately, `B` and `C` submit and confirm `DeleteMember{member: A}` (reaching threshold 2), executing it. `A` is removed from `self.members`; only requests where `A` was the request's `member` are purged — `R` is untouched because `R.member == A`'s own add-request confirm, but here consider `R` was instead created and confirmed initially by `A` then also confirmed by `B` before deletion, so `R.member == A`. To keep `R` alive, have `B` create `R` and `A` confirm it (`R.member == B`, confirmations = {A}); now `DeleteMember{A}`'s cleanup filters on `r.member == A`, so `R` (owned by `B`) is unaffected. `R.confirmations` still contains `A`.
4. `C` calls `confirm(R)`. `confirmations.len() (1, from A) + 1 >= num_confirmations (2)` is true, so `R` executes — funded/authorized by only one currently-live member (`C`) plus a stale confirmation from removed member `A`, i.e. below the intended live-member threshold of 2.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
