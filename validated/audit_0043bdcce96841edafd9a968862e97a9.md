### Title
A withdrawing user can cancel a queued withdrawal after a loss epoch to escape their pro-rata share of the pending-receipt haircut - (File: contracts/IdleCDOEpochQueue.sol)

### Summary
The external bug class is a permissionless cancel path that remains open in the same window where the outcome of a commitment becomes observable, letting a user opt out of an unfavorable result. The analog exists in `IdleCDOEpochQueue.deleteWithdrawRequest`: a queued withdrawal can be deleted until `epochWithdrawPrice[_requestEpoch]` is set, but the loss applied to pending receipts is already crystallized earlier, at `stopEpochWithDuration`/`stopEpoch` time. Between `_stopEpoch` (which reduces `pendingWithdraws` pro rata via `previewLossAdjustedWithdrawFunds`) and the privileged `processWithdrawRequests`, a user can delete their request, receive tranche tokens back at par, and leave the already-reduced `pendingWithdraws` pool to the remaining receipt holders.

### Finding Description
When the manager stops an epoch with a loss (`stopEpochWithDuration(_newApr, _interest, _duration, _lossAmount)`), `_stopEpoch` calls `IdleCreditVault.previewLossAdjustedWithdrawFunds(_lossAmount)`, which assigns a pro-rata share of the loss to the aggregate `pendingWithdraws` pool — pending receipts have no tranche identity, so they are haircut uniformly regardless of whether they originated from AA or BB tranches (`contracts/IdleCDOEpochVariant.sol:391-393`). The remaining loss is applied BB-first to active positions.

The loss is therefore already reflected in strategy state (`pendingWithdraws` reduced, `burnStrategyTokens` executed) before the epoch queue processes the requests. `epochWithdrawPrice[_requestEpoch]` is only set when the manager/owner later calls `processWithdrawRequests` on `IdleCDOEpochQueue`. During the gap, `deleteWithdrawRequest` still succeeds because its only guard is `epochWithdrawPrice[_requestEpoch] != 0 || isEpochWithdrawZero[_requestEpoch]` (`contracts/IdleCDOEpochQueue.sol:203-218`).

An attacker holding a queued withdrawal derived from AA tranches can observe the realized loss transaction (`stopEpochWithDuration` with `_lossAmount > 0`), see that pending receipts were haircut while AA tranche value was untouched (BB-first waterfall), and call `deleteWithdrawRequest` before `processWithdrawRequests` executes. They receive full tranche tokens back, while `epochPendingWithdrawals` decreases but the already-fixed, reduced strategy-level claimable pool is divided among the remaining withdrawers — concentrating the deleted user's loss share onto them. This mirrors the YOLO report: the attacker waits until the outcome (the loss allocation) is knowable, then exercises a still-open cancel path to opt out.

### Impact Explanation
Loss meant to be shared pro rata across all pending receipts is shifted entirely onto the users who do not front-run the processing transaction. The escaping user holds AA tranches at full value while other pending withdrawers absorb a larger haircut than intended — a direct redistribution of loss / effective theft of the difference between the pro-rata share and zero. The broken invariant is fair loss allocation (one receipt, proportional payout), and the amount is bounded by the pending-receipt portion of `_lossAmount` but can be arbitrarily concentrated if the attacker dominates the pending pool.

### Likelihood Explanation
Requires an epoch stopped with `_lossAmount > 0` (borrower underperformance or credit loss event — an accepted scenario for this vault type) and a nonzero window between `stopEpochWithDuration` and `queue.processWithdrawRequests`. Both are privileged calls, but the attacker only needs to be a KYC'd lender with a queued withdrawal, and the mempool-visible manager transaction gives them the same "observe then cancel" opportunity as the VRF-fulfillment front-run in the source report. No privileged collusion needed; the attacker merely reacts to honest manager transactions.

### Recommendation
Block deletion of withdrawal requests once the corresponding epoch has been stopped with a pending-receipt loss — e.g., record a flag/price basis in the queue at stop time (or have `processWithdrawRequests` be invoked atomically within `stopEpoch`), or apply the already-computed loss to tranche tokens returned by `deleteWithdrawRequest` rather than returning them at par.

### Proof of Concept
Foundry fork test sketch (pattern follows `test/foundry/IdleCDOEpochQueue.t.sol`):

```solidity
function testDeleteWithdrawRequestEscapesPendingLoss() external {
    // attacker (KYC'd AA holder) and victim both queue withdrawals in the buffer period
    uint256 trancheAttacker = 100 * ONE_TRANCHE;
    uint256 trancheVictim   = 100 * ONE_TRANCHE;
    _requestWithdrawWithUser(attacker, trancheAttacker);
    _requestWithdrawWithUser(victim,   trancheVictim);
    uint256 requestEpoch = strategy.epochNumber() + 1;

    // manager stops epoch with a loss hitting pending receipts pro rata,
    // small enough that the BB-first active waterfall leaves AA tranches whole
    uint256 loss = 10 * ONE_TRANCHE; // sized so previewLossAdjustedWithdrawFunds haircut < loss fully covered for AA holders
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(0, interest, duration, loss);

    // attacker sees the loss tx and deletes BEFORE processWithdrawRequests sets epochWithdrawPrice
    vm.prank(attacker);
    queue.deleteWithdrawRequest(requestEpoch);
    assertEq(tranche.balanceOf(attacker), trancheAttacker); // full tranches back, no haircut

    // victim's request is processed and pays out at a worse effective price
    vm.prank(manager);
    queue.processWithdrawRequests();
    // victim bears the attacker's escaped loss share on top of their own pro-rata part
}
```

Note: the exact sizing of `_lossAmount` and whether AA-valued pending receipts are haircut while AA tranches stay whole depends on `previewLossAdjustedWithdrawFunds`'s split between the pending pool and active positions; I confirmed the pro-rata pending share and BB-first active waterfall from `IdleCDOEpochVariant.sol:391-393` and the timing gap from `IdleCDOEpochQueue.sol:203-218`, but did not fully trace `previewLossAdjustedWithdrawFunds` internals, so the PoC parameters need tuning against a live fork.
