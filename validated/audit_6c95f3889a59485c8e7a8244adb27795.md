### Title
Stale confirmations from removed multisig members are not purged from other pending requests, allowing execution below the live K-of-N threshold - (File: `multisig2/src/lib.rs`)

### Summary
The Boros report describes a check (`_isEnoughIMStrict`) that is supposed to guarantee an invariant (health ratio ≥ Hf) but fails to account for the invariant's dependency changing over time (risk parameters drifting). The same failure pattern exists in the NEAR `multisig2` contract: the `confirm` function treats the count of stored confirmation entries on a request as proof that `num_confirmations` *live* members approved it, but `delete_member` never purges a departing member's confirmation entries from requests they confirmed but did not create. This breaks the binding "confirmations counted == live members who approved," letting a request execute with fewer than `num_confirmations` currently-authorized approvers.

### Finding Description
`confirm()` decides whether to execute a request purely by comparing the size of the `confirmations` set (plus the current caller) to `self.num_confirmations`: [1](#0-0) 

`delete_member()` is the only place that cleans up state when a member leaves. It removes **requests created by** the departing member and their `num_requests_pk` entry, but it only scrubs `self.confirmations` for requests where `r.member == member` (i.e., requests the departing member *authored*): [2](#0-1) 

It does **not** scan `self.confirmations` for entries where the departing member's account/key string appears as a *confirmer* on requests authored by someone else. Those stale confirmation strings remain in the `HashSet<String>` for those other pending requests.

Because `confirm()` never re-validates that every string in the stored `confirmations` set still corresponds to `self.current_member()`-eligible membership, a confirmation cast by a member before their removal continues to count toward `num_confirmations` indefinitely.

### Impact Explanation
This breaks the multisig's core custody guarantee: "a request requires `K` out of the *current* `N` members to approve before any transfer/key-change/contract-call executes." An attacker (or even members acting in good faith, unaware of the state) can get a `Transfer`, `AddKey`, `FunctionCall`, or `DeployContract` request executed with only `K-1` (or fewer) *live* member approvals, by exploiting a confirmation left behind by a member who has since been removed. This is a multisig request executed below threshold — moving NEAR (or granting access) that a properly-enforced K-of-N policy would have blocked. This maps to the report's Critical impact category ("a multisig request executed below threshold").

### Likelihood Explanation
No special privilege is required beyond being (or having been) an ordinary multisig member — a normal, expected occurrence in the "K out of N" governance model, since membership rotation (removing a departed/compromised key) is a documented supported operation via `AddMember`/`DeleteMember`. Any workflow where: (1) a request is confirmed by member B but not yet fully confirmed, (2) B is later removed for any reason, and (3) the request is confirmed by another member, triggers the bug — this requires no attacker collusion with removed members, only ordinary sequencing of legitimate operations.

### Recommendation
When executing `DeleteMember`, iterate `self.confirmations` for **all** pending requests (not just ones the departing member authored) and remove the departing member's entry from each confirmation set. Alternatively, change `confirm()` to filter/re-validate the stored confirmation set against `self.members` before counting (`confirmations.iter().filter(|m| self.members.contains(m)).count()`), so that only confirmations from currently-live members are counted toward `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C}` and `num_confirmations = 2`.
2. `A` calls `add_request` for a `Transfer` request `R` (receiver attacker-controlled or arbitrary), 0 confirmations.
3. `B` calls `confirm(R)` — `confirmations = {B}`, `1 < 2`, request stays pending.
4. Members execute a separate, legitimately-approved request (2-of-3, e.g. A+C) with action `DeleteMember { member: B }`. Per `delete_member`, only requests *authored* by `B` are cleaned up; `R` (authored by `A`) is untouched, so `confirmations` for `R` still contains `B`. [3](#0-2) 
5. `C` (now one of only two remaining live members, along with `A`) calls `confirm(R)`. Inside `confirm()`: `confirmations.len() as u32 + 1 = 1 (stale B) + 1 (C) = 2 >= num_confirmations (2)` → `execute_request(R)` runs. [4](#0-3) 
6. The transfer executes with only `C`'s live approval plus a stale, no-longer-valid approval from removed member `B` — one live approval short of the intended 2-of-2 (post-removal, 2-of-2) live threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
