## Analysis Result

### Title
Unbounded full-ledger account scan in unindexed `getProgramAccounts` RPC path allows resource-exhaustion DoS - (File: `accounts-db/src/accounts.rs`, `accounts-db/src/accounts_db.rs`, `rpc/src/rpc.rs`)

### Summary
The reported SKALE bug is a class of vulnerability where a single operation iterates over an entire global entity set (all nodes) whose size is attacker/user-uncontrolled and grows over time, causing the operation's cost to scale with total system size rather than with the request itself. Agave's `getProgramAccounts` RPC method exhibits the same bug class: when a program's accounts are not covered by an optional secondary index (the default configuration), the call scans **every account stored in the entire accounts-db**, and unlike the indexed code path, this particular path enforces **no byte/size limit**.

### Finding Description
`getProgramAccounts` is exposed unauthenticated to any RPC client [1](#0-0) . It is routed to `JsonRpcRequestProcessor::get_filtered_program_accounts`, which only uses the secondary `ProgramId` index if one has been explicitly enabled by the operator; otherwise it falls through to `bank.get_filtered_program_accounts` [2](#0-1) , with an explicit comment that no byte-limit is applied on this branch ("this path does not need to provide a mb limit because we only want to support secondary indexes").

`Bank::get_filtered_program_accounts` forwards to `Accounts::load_by_program_with_filter` [3](#0-2) , which calls `AccountsDb::scan_accounts` and applies the program-owner filter only *after* each account is loaded from storage [4](#0-3) . `AccountsDb::scan_accounts` iterates the **entire accounts index** — every pubkey visible from the ancestors, for the whole ledger — invoking `scan_func` (and thus loading each account from the cache or storage) for every single one [5](#0-4) .

This is functionally identical to `_generateGroup` in the SKALE report: a single externally-triggerable call whose cost scales linearly with the size of a growing global data structure (all schain nodes vs. all accounts in the ledger), performed without any owner-based pre-filtering or hard cap. In contrast, the indexed scan path (`get_filtered_indexed_accounts` / `load_by_index_key_with_filter`) does track accumulated result bytes and aborts the scan via `ScanConfig::abort()` once `scan_results_limit_bytes` is exceeded [6](#0-5)  — that mitigation is conspicuously absent from the unindexed path.

### Impact Explanation
Since secondary indexes (`--account-index program-id`) are opt-in and off by default, most RPC nodes serving `getProgramAccounts` for arbitrary/uncommon program IDs will execute a full-ledger scan on every such call, loading (and cloning) every account in accounts-db to test the owner filter. On mainnet-scale ledgers this is extremely CPU/IO/memory intensive per request and unbounded in size. A remote, unprivileged client can issue such requests (optionally querying rarely-used or invalid program IDs to guarantee the "no accounts return early" worst case) repeatedly/concurrently to exhaust an RPC node's CPU, memory, and disk I/O, causing degraded service or crash (OOM) of the RPC node — matching the "ingest starvation / RPC crash" impact category.

### Likelihood Explanation
High for any RPC node that has not enabled the `program-id` secondary index (the default). No special privileges, program deployment, or account state pre-conditions are required — any client with network access to a public RPC endpoint can trigger this by calling `getProgramAccounts` with any `program_id` (including one with few or zero matching accounts, e.g. a freshly generated pubkey, to maximize wasted per-account scan work relative to returned data).

### Recommendation
Apply a `byte_limit_for_scan`/result-size abort mechanism (equivalent to the one already used in `load_by_index_key_with_filter`) to the unindexed `load_by_program_with_filter`/`scan_accounts` path as well, or require/auto-enable per-program filtering via the accounts index (or a bounded default) before allowing `getProgramAccounts` calls that would otherwise force a full ledger scan. At minimum, document and rate-limit this RPC method more aggressively when secondary indexes are disabled, and consider erroring out (as `getLargestAccounts`/`getSupply` do for other expensive scans) rather than silently performing an unbounded scan.

### Proof of Concept
1. Start a validator/RPC node **without** `--account-index program-id`.
2. Populate accounts-db with a large number of accounts (as occurs naturally on mainnet-beta).
3. From any unauthenticated RPC client, repeatedly call:
   ```json
   {"jsonrpc":"2.0","id":1,"method":"getProgramAccounts","params":["<arbitrary/rarely-used-program-id>"]}
   ```
4. Each call triggers `AccountsDb::scan_accounts` to iterate and load every account in the ledger via the code path `rpc.rs::get_filtered_program_accounts` → `bank.rs::get_filtered_program_accounts` → `accounts.rs::load_by_program_with_filter` → `accounts_db.rs::scan_accounts`, with no byte-limit guard, consuming CPU/memory/I/O proportional to total ledger size regardless of how many (if any) accounts match.
5. Concurrent/repeated invocation from multiple clients exhausts node resources, degrading or crashing the RPC service for legitimate users.

        ancestors: &Ancestors,
