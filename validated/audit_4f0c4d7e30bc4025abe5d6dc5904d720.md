### Title
Loss-adjusted claim clears `lastWithdrawRequest` before the funded-claim epoch gate runs, letting older haircut receipts pay out at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
CVE-2024-4629 is a check-before-effect flaw: the brute-force check runs before the protector locks the account, so parallel attempts exceed the allowed quota. The same class exists in `IdleCreditVault.claimWithdrawRequest`: the "wait one epoch" guard lives in `_claimFundedWithdrawRequest`, but it executes *after* `_claimLossAdjustedWithdrawRequest`/`_clearWithdrawClaimForEpoch` have already mutated `lastWithdrawRequest[_user]` to `0`. The gate therefore evaluates post-clearing state, and an older loss-adjusted (haircut) receipt is paid at par through the funded path.

### Finding Description
`claimWithdrawRequest` chains the claim paths in order: `_claimPostDefaultWithdrawRequest`/`_claimDefaultedWithdrawRequest`, then `_claimLossAdjustedWithdrawRequest`, then `_claimFundedWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:301-313).

`_claimLossAdjustedWithdrawRequest` keys off `lastWithdrawRequest[_user]` (the *latest* request epoch) and calls `_clearWithdrawClaimForEpoch`, which clears that epoch's basis and, when the cleared epoch is the latest marker, resets `lastWithdrawRequest[_user] = 0` (lines 789-800, 832-836). Only afterward does `_claimFundedWithdrawRequest` enforce `epochNumber <= lastWithdrawRequest[_user]` → now `0`, so the check passes unconditionally (line 326), and it pays the entire remaining `withdrawsRequests[_user]` aggregate at par (lines 338-349).

Attack sequence (unprivileged lender only):
1. Epoch A: user requests withdraw (buffer). `stopEpochWithDuration` applies a loss → `lossRecoveryPriceByEpoch[A]` set; borrower funds only `pendingToFund`.
2. User does not claim; epoch B buffer: user requests withdraw again → `lastWithdrawRequest = B`, `withdrawsRequests` aggregates A+B.
3. Epoch B also stops with a loss → `lossRecoveryPriceByEpoch[B]` set.
4. User calls `claimWithdrawRequest` once: loss path clears only epoch B (pays `B * price`), resets `lastWithdrawRequest = 0`; funded path then pays epoch A's full basis at par instead of `A * lossRecoveryPriceByEpoch[A]`.

Broken invariant: loss waterfall / one-receipt-one-payout. Excess paid = `A * (RECOVERY_FULL - lossRecoveryPriceByEpoch[A]) / RECOVERY_FULL`, drained from the vault's funded-claim reserve at the expense of other pending claimants. Existing guards (`NotAllowed` epoch gate, `lossRecoveryPrice == 0` skip, `_onlyIdleCDO`) do not stop it — the gate is bypassed precisely because state was mutated earlier in the same call.

### Impact Explanation
Direct theft / insolvency: the attacker converts a haircutted receipt into a full-par payout, extracting underlyings that belong to other funded withdraw/instant-withdraw claimants. Loss scales with the older receipt size and the haircut depth; repeatable whenever two consecutive stop epochs carry losses (e.g., repeated partial borrower shortfalls, which require no malicious privileged role — `stopEpochWithDuration(_lossAmount)` is a normal manager flow).

### Likelihood Explanation
Requires a user holding receipts across two loss-adjusted epochs. Loss stops are an expected mechanism in this codebase (`previewLossAdjustedWithdrawFunds`, `lossRecoveryPriceByEpoch` are core features, not edge cases), so co-occurrence is realistic in any stressed credit pool. No privileged collusion, no oracle manipulation, no timing race needed — single transaction, deterministic.

### Recommendation
Do not let partial-epoch clearing silently downgrade the epoch gate. Options: (a) snapshot `lastWithdrawRequest`/`epochNumber` at the top of `claimWithdrawRequest` and pass the pre-mutation values into `_claimFundedWithdrawRequest`'s gate; (b) in `_clearWithdrawClaimForEpoch`, when clearing the latest epoch but residual basis remains in earlier epochs, set `lastWithdrawRequest` to the oldest remaining pending epoch instead of `0`; (c) iterate all epochs with nonzero `lossRecoveryPriceByEpoch` for the user inside the loss path before falling through to par claims.

### Proof of Concept
Foundry fork (modeled on `test/foundry/IdleCDOEpochQueue.t.sol` loss-adjusted flows such as `testProcessWithdrawalClaimsZeroPayout`):

```solidity
// Setup: standard epoch variant, user deposits, epoch 0 runs.
// Epoch A (buffer): user requests withdraw of tranchesA via cdoEpoch.requestWithdraw.
// stopEpochWithDuration(apr, 0, duration, lossA) -> lossRecoveryPriceByEpoch[A] < RECOVERY_FULL.
// user does NOT claim.
// Epoch B (buffer): user requests withdraw of tranchesB -> lastWithdrawRequest = B.
// stopEpochWithDuration(apr, 0, duration, lossB) -> lossRecoveryPriceByEpoch[B] < RECOVERY_FULL.
uint256 balPre = underlying.balanceOf(user);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user) - balPre;
uint256 entitled =
    basisA * strategy.lossRecoveryPriceByEpoch(A) / RECOVERY_FULL +
    basisB * strategy.lossRecoveryPriceByEpoch(B) / RECOVERY_FULL;
assertGt(paid, entitled); // excess = basisA * (1 - priceA), stolen from funded reserve
```

Uncertain details I could not fully verify within the iteration budget: the exact epoch index under which `collectWithdrawFunds` records `lossRecoveryPriceByEpoch` relative to `lastWithdrawRequest` numbering (the `_claimLossAdjustedWithdrawRequest` design implies they coincide), and whether `_requestWithdrawApr0` interacts with the residual basis in APR0 mode — but neither affects the core ordering bug in fixed-APR mode.
