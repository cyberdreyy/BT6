## Finding

### Title
Permissionless SPL-single-pool staked-collateral banks price LST via raw account lamports, enabling donation-based valuation inflation - (File: `programs/marginfi/src/state/price.rs`)

### Summary
Staked-collateral banks (`ASSET_TAG_STAKED`) price their LST using `staked_pool_net_asset_value`, which sums the **raw lamport balance** of the validator's stake account and its "on-ramp" account, minus rent-exempt reserves [1](#0-0) . Because both accounts can receive lamports from an ordinary `SystemProgram::transfer` (no special authority needed, as demonstrated in the test suite itself) [2](#0-1) , and because both the SPL single-pool (validator stake pool) and the corresponding marginfi bank can be created **permissionlessly by any signer** for any validator via `lending_pool_add_bank_permissionless` [3](#0-2) , an attacker can stand up a low-TVL pool they nearly wholly own, donate SOL into it to spike its NAV/price, and borrow against the inflated collateral in the same transaction — directly analogous to the ParaSpace low-TVL Uniswap V3 pool manipulation.

### Finding Description
`lending_pool_add_bank_permissionless` requires only a `fee_payer: Signer` and derives/validates the stake-pool PDA chain from an attacker-supplied `validator_vote_account`; no admin, validator, or pool-owner signature is required [4](#0-3) . SPL single-pools themselves are also permissionlessly initializable by anyone (`SinglePoolProgram.initialize`) [5](#0-4) , so an attacker fully controls both the validator target and the initial LST supply distribution of a brand-new pool, becoming the de-facto sole holder of that LST.

The canonical (post-SVSP) NAV formula used for pricing is:
```rust
fn staked_pool_net_asset_value(
    pool_stake_info: &AccountInfo,
    pool_onramp_info: &AccountInfo,
    rent: &Rent,
) -> MarginfiResult<u64> {
    let pool_rent_exempt_reserve = rent.minimum_balance(pool_stake_info.data_len());
    let onramp_rent_exempt_reserve = rent.minimum_balance(pool_onramp_info.data_len());

    let main_stake_value = pool_stake_info.lamports().saturating_sub(pool_rent_exempt_reserve);
    let onramp_value = pool_onramp_info.lamports().saturating_sub(onramp_rent_exempt_reserve);

    Ok(main_stake_value.saturating_add(onramp_value))
}
``` [1](#0-0) 

This NAV is then divided by `lst_supply` to compute the price multiplier applied to the SOL oracle price for that bank [6](#0-5) . Unlike the legacy formula, which read the stake account's parsed `delegation.stake` field (an amount only changed by explicit stake-program instructions), this canonical formula reads raw `.lamports()` on both the stake account and the on-ramp account. Any unprivileged actor can inflate these balances via a plain SOL transfer — the test suite explicitly demonstrates this by using `SystemProgram.transfer` directly to `splSolPool` to simulate "appreciation" and shows this immediately raises `priceMultiplier` [7](#0-6) . The on-ramp account in particular is meant to hold *unswept, not-yet-deposited* SOL pending a legitimate deposit-and-mint step, yet its balance is already counted as backing NAV for existing LST holders before any shares are minted for it [1](#0-0) .

### Impact Explanation
Because the attacker can arrange to own virtually all of a chosen (possibly freshly-minted) pool's LST supply, a donation to the stake/on-ramp account increases the marked price of the attacker's own collateral almost 1:1, while genuinely legitimate LST holders elsewhere are unaffected (isolated per-validator pools). Within a single transaction the attacker can: (1) transfer SOL into the target validator's stake/on-ramp account, (2) trigger a price refresh (`pulse_bank_price`/health pulse) that reads the now-inflated NAV, and (3) borrow against the inflated collateral value — all before any external correction can occur, since there is no AMM-style arbitrage mechanism for a native stake account's NAV. This allows unauthorized extraction of borrowed liquidity backed by artificially inflated collateral, a direct value-redirection/misvaluation with financial effect on the lending pool, mirroring the mechanics judged High severity in the referenced ParaSpace report.

### Likelihood Explanation
The attack requires no privileged keys: pool creation, bank creation, and lamport donation are all permissionless operations reachable by any funded account, and the exact "donate lamports to inflate NAV" mechanic is already validated by the project's own test (`s05_solAppreciates.spec.ts`) as functionally increasing price. The only capital requirement is the size of the donation relative to the amount the attacker wants to borrow, which can be obtained via flash-borrowing SOL elsewhere in the same transaction (Solana supports atomic multi-instruction transactions), making this a self-contained, single-transaction exploit rather than a multi-block/arbitrage-exposed one.

### Recommendation
- Do not count unswept `pool_onramp` lamports toward NAV until they have actually been converted into pool shares via the legitimate SPL single-pool deposit path; only count balances that correspond to minted LST supply.
- Where raw lamport balances must be used, require a bank to have a minimum bootstrapped/verified TVL (or a minimum number of independent depositors) before permissionless creation is allowed, and/or apply a deposit/withdrawal-limit and time-delay/TWAP-style dampening on the price multiplier so instantaneous donations cannot be used within a single transaction to spike collateral value before a borrow.
- Consider gating `lending_pool_add_bank_permissionless` (or at least enabling it for use as collateral with non-negligible weight) behind a minimum pre-existing NAV/LST-supply threshold, analogous to the recommended Uniswap V3 pool TVL whitelist in the referenced report.

### Proof of Concept
1. Attacker calls `SinglePoolProgram.initialize` for an arbitrary/low-stake validator vote account, becoming (with a small deposit) the owner of nearly all outstanding LST for that pool.
2. Attacker calls `lending_pool_add_bank_permissionless` with `fee_payer` = attacker, `validator_vote_account` = the chosen validator; no privileged signer is required [4](#0-3) .
3. Attacker deposits their small amount of LST as collateral into a marginfi account.
4. In one transaction, attacker: (a) `SystemProgram.transfer`s a large amount of SOL (optionally flash-borrowed) directly to the pool's `sol_pool`/`pool_onramp` account, (b) triggers a price/health pulse so `staked_pool_net_asset_value` re-reads the inflated lamport balance [1](#0-0) , and (c) borrows against the now-inflated collateral valuation of their LST position.
5. The borrowed funds are extracted; the donated SOL remains stuck in the stake/on-ramp account (or can be partially reclaimed by the attacker calling the legitimate SPL single-pool deposit instruction to mint shares for themselves), while the lending pool is left under-collateralized relative to the honest valuation of the attacker's original stake.
