### Title
Flip-flopped signer response inflates both `total_weight_approved` and `total_weight_rejected` for the same block, breaking weight conservation and enabling a false global rejection despite real consensus - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
`StackerDBListener::run` tracks per-block weight bookkeeping (`total_weight_approved`, `total_weight_rejected`, `gathered_signatures`, `responded_signers`) used by the mining coordinator to decide whether a proposed block has reached the 70% signing threshold or should be abandoned as rejected. The `Accepted` branch gates the `total_weight_approved` increment only on membership in `gathered_signatures`, never on whether the same slot already contributed to `total_weight_rejected` via `responded_signers`. A signer that first rejects and later legitimately accepts the same block (its own key only — no majority or other signer's key required) therefore has its weight counted in *both* buckets simultaneously, breaking the implicit weight-conservation invariant the coordinator relies on to decide the block's fate. This is the same bug class as the Axelar report: a value (weight) computed/consumed under one accounting "denomination" (rejected) is reused unadjusted under a second, different denomination (approved) without reconciling the two, producing an accounting mismatch that misleads the consumer of the aggregate.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the `Accepted` handling path is: [1](#0-0) 

```
if !block.gathered_signatures.contains_key(&slot_id) {
    block.total_weight_approved = block.total_weight_approved.saturating_add(signer_entry.weight);
    ...
}
block.gathered_signatures.insert(slot_id, signature);
block.responded_signers.insert(slot_id);
```

and the `Rejected` handling path is: [2](#0-1) 

```
if block.responded_signers.insert(slot_id) {
    block.total_weight_rejected = block.total_weight_rejected.saturating_add(signer_entry.weight);
    ...
}
```

`responded_signers` is a single set shared between the two branches, and it is meant to make each slot's *first* response idempotent. But the `Accepted` branch does **not** consult `responded_signers` before crediting `total_weight_approved` — it only checks `gathered_signatures`. Consequently:

1. Signer S (slot `k`, weight `w`) sends a `Rejected` message for block `B`. `responded_signers.insert(k)` succeeds ⇒ `total_weight_rejected += w`.
2. S later sends a valid `Accepted` message for the *same* `B` (e.g., it revalidated and changed its mind, or a malicious/one-slot signer intentionally does this to manipulate the coordinator's bookkeeping). `gathered_signatures` does not yet contain `k` ⇒ `total_weight_approved += w` as well. `responded_signers.insert(k)` is called again but its return value is not checked at this point, so nothing undoes the earlier `total_weight_rejected` credit.

The result: for this one block, `w` is now counted in *both* `total_weight_approved` and `total_weight_rejected`. This breaks the equality the coordinator implicitly assumes — that the weight in the rejected bucket and the weight in the approved bucket are disjoint subsets of `total_weight` — analogous to the Axelar bug where a single token amount was carried across two different unit contexts (source decimals vs. destination decimals) without reconciliation, corrupting the receiving side's accounting.

This corrupted state is then consumed by the mining coordinator's polling loop: [3](#0-2) 

The rejection-threshold check (`total_weight_rejected.saturating_add(weight_threshold) > total_weight`) is evaluated *before* the acceptance-threshold check (`total_weight_approved >= weight_threshold`). Because a flip-flopping signer's weight persists forever in `total_weight_rejected` (it is never removed when the signer later accepts), it is possible for the rejection-threshold branch to fire even though the same signer's current, valid signature is already present in `gathered_signatures` and would otherwise have let the block reach real 70% approval. In that case the coordinator returns `Err(NakamotoNodeError::SignersRejected { .. })` and abandons block `B`, even though a genuine supermajority of live signatures for `B` already exist in `gathered_signatures`.

### Impact Explanation
Abandoning `B` despite it having reached genuine 70% approval forces the miner to build a different, competing block at the same chain height/tenure slot. Signers who already broadcast (and stored, via `signer_db.add_block_signature`) their acceptance of `B` can subsequently be asked to sign the *new* competing block; nothing in this path prevents them from doing so once the coordinator itself treats `B` as dead. This is the un-mitigated path toward a signer signing a conflicting block at the same height — a Critical-class outcome per the stated impact taxonomy ("a signer signing an invalid, non-canonical, or conflicting block"). At minimum, independent of the conflicting-block escalation, this is a concrete liveness wedge: a validly-approved block can be discarded by the local node/coordinator bookkeeping due to stale, double-counted rejection weight from a signer who has since accepted.

### Likelihood Explanation
The trigger requires only a single signer (one stackerdb slot) sending a `Rejected` message for a block followed later by a valid `Accepted` message for the *same* `signer_signature_hash` — entirely within that signer's own key material and normal StackerDB gossip, no majority collusion, no other signer's key, and no auth_token access needed. Transient rejects followed by acceptance are a realistic occurrence (e.g., a signer initially rejects due to a stale sortition/chainstate view, then re-evaluates after its view catches up and accepts) — exactly the kind of re-evaluation flow the codebase's own `should_reevaluate_block`/pre-commit re-check logic is built to allow. The bookkeeping flaw is therefore reachable under ordinary operation, not just adversarial action, which increases likelihood further.

### Recommendation
Make the two buckets mutually exclusive per slot for a given block, mirroring how a cross-chain bridge must reconcile (not just carry over) an amount when moving between two different accounting contexts:
- Before crediting `total_weight_approved`, check whether `slot_id` is already present in `responded_signers`/counted in `total_weight_rejected`; if so, subtract its weight from `total_weight_rejected` (and remove any per-txid problematic/failed weight it contributed) before adding it to `total_weight_approved`, and vice versa for the reject path.
- Alternatively, track a single `HashMap<SlotId, Verdict>` (Accepted/Rejected) per block and always recompute `total_weight_approved`/`total_weight_rejected` from that authoritative map rather than incrementally mutating two independent running counters that can drift.
- Add an invariant assertion/test that `total_weight_approved + total_weight_rejected` (summed over each slot's *current* verdict only) never exceeds `total_weight`.

### Proof of Concept
1. Configure a reward set with signers of known weights (as in the existing `nakamoto_block_signatures` tests) and instantiate a `StackerDbListener`/coordinator flow (or a focused unit test against the `blocks` map directly).
2. For a proposed block `B`, have signer S (weight `w`) emit `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `B`. Assert `total_weight_rejected == w`.
3. Then have S emit a valid `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `B` (a legitimately signed acceptance over `B`'s `signer_signature_hash`). Assert:
   - `total_weight_approved == w` (S's weight now also present here), and
   - `total_weight_rejected` is still `w` (never decremented) — i.e. `total_weight_approved + total_weight_rejected == 2w`, violating the expectation that each slot's weight is counted in exactly one bucket.
4. With additional signers arranged so that the *stale* `total_weight_rejected` alone (composed of one or more such flip-flopped, already-reversed rejections) crosses `total_weight.saturating_sub(weight_threshold)`, show that `poll_for_signer_signatures` in `signer_coordinator.rs` returns `Err(SignersRejected)` even though `gathered_signatures`' real, current weight already meets `weight_threshold`.
