### Title
Unsound `pop_last` + visited-pruning optimization in `verify_package_no_cyclic_relationships` allows intra-package module cycles to escape detection, enabling publication of a package with cyclic dependencies — (`external-crates/move/crates/move-vm-runtime/src/validation/verification/linkage.rs`)

---

### Summary

`verify_package_no_cyclic_relationships` in the production `latest` runtime uses a `pop_last()` iteration with a "remove visited" pruning step that is logically unsound. When the alphabetically-last module in a package depends on (but is not itself part of) a cycle among other modules in the same package, the cycle escapes detection entirely. The same bug re-fires when `verify_linkage_and_cyclic_checks_for_publication` re-verifies cached dependencies during a second package's publication, so a dependent package P_user also passes publication checks.

---

### Finding Description

**The optimization and why it is wrong**

`verify_package_no_cyclic_relationships` builds a `BTreeMap` of all modules in the package, then iterates with `pop_last()`:

```rust
while let Some((_, module)) = to_visit_modules.pop_last() {
    let visited = cyclic_dependencies::verify_module(&module.value, |id| { ... })?;
    for k in visited.iter() {
        to_visit_modules.remove(k);   // ← prunes B and C from future checks
    }
}
``` [1](#0-0) 

`cyclic_dependencies::verify_module` runs a DFS with `target = self_id` and returns the set of all nodes traversed. It only detects a cycle if a path leads back to `target`:

```rust
if cursor == target { return Ok(true); }
let is_new = visited.insert(cursor.clone());
if is_new { for dep in deps(cursor)? { ... } }
Ok(false)
``` [2](#0-1) 

The `visited` set returned contains every node traversed, but those nodes were only checked for paths back to the current `target`. They were **not** checked for cycles among themselves.

**Concrete exploit structure**

Craft a package with three modules:
- `Z` (alphabetically last): depends on `B`
- `B`: depends on `C`
- `C`: depends on `B` (cycle: B → C → B)

Execution of `verify_package_no_cyclic_relationships`:

1. `to_visit_modules = {B, C, Z}` (BTreeMap, sorted)
2. `pop_last()` → Z; `verify_module(Z)`, target = Z
   - DFS: Z→B (B≠Z, insert B) → C (C≠Z, insert C) → B (already in `visited`, `is_new=false`, skip) → returns `false`
   - No cycle back to Z found; `visited = {B, C}`
3. Remove B and C from `to_visit_modules` → `to_visit_modules = {}`
4. Loop ends. **Cycle B↔C never detected.**

The existing test `publish_cyclic_modules_partial_package_cycle` (A has *no* dependencies + B↔C) passes only because A's `visited` set is empty, so B and C are not pruned and C is subsequently popped and checked. The test does not cover the case where the non-cyclic module **depends on** a cyclic module. [3](#0-2) 

**P_user publication also bypasses the check**

`verify_linkage_and_cyclic_checks_for_publication` re-runs `verify_package_no_cyclic_relationships` on every entry in `cached_packages` (which includes P_cyclic):

```rust
for package in cached_packages.values() {
    let package_modules = package.as_modules().into_iter().collect::<Vec<_>>();
    verify_package_valid_linkage(&package_modules, cached_packages, &relocation_map)?;
    verify_package_no_cyclic_relationships(&package_modules, cached_packages, &relocation_map)?;
}
``` [4](#0-3) 

Because P_cyclic's module set still has the same Z→B↔C structure, the same `pop_last` pruning fires again and the cycle escapes detection a second time. P_user is published with a transitive cyclic dependency.

**This runtime is production**

`sui-execution/latest/sui-adapter` (the current production adapter) directly depends on `external-crates/move/crates/move-vm-runtime` and calls `validate_for_publish` → `verify_linkage_and_cyclic_checks_for_publication`: [5](#0-4) [6](#0-5)

### Impact Explanation

A malicious package publisher (ordinary SUI holder, no special privilege) can publish a package containing a hidden intra-package module cycle. The on-chain state then contains a package that violates the fundamental invariant that all published packages are acyclic. Any subsequent call into that package causes the VM to attempt to load a cyclic module graph, which can produce infinite recursion or a stack overflow in the loader, crashing the validator process. A dependent package P_user can also be published, widening the attack surface to any caller of P_user.

This satisfies: **state corruption from package publish** (Critical gate) and **validator crash reachable from public input** (High/Medium gate).

---

### Likelihood Explanation

The exploit requires only a crafted package publish transaction — the lowest-privilege public entry point. The attacker needs to name one module with a lexicographically greater identifier than the cyclic pair (e.g., `z_entry` depending on `alpha` and `beta` where `alpha↔beta`). No leaked keys, no malicious validators, no governance quorum.

---

### Recommendation

Replace the unsound pruning optimization. The correct fix is to check every module in the package as a cycle target independently, without removing modules from the to-visit set based on another module's DFS traversal. A correct implementation either:

1. Removes the `for k in visited.iter() { to_visit_modules.remove(k); }` pruning entirely (safe but slower), or
2. Only prunes a module M from `to_visit_modules` after M itself has been used as the `target` in `verify_module(M, ...)`.

Add a regression test: package with modules `{Z (depends on B), B (depends on C), C (depends on B)}` must return `CYCLIC_MODULE_DEPENDENCY`.

```

  module 0xADDR::alpha    { use 0xADDR::beta;  }
  module 0xADDR::beta     { use 0xADDR::alpha; }   // cycle: alpha ↔ beta

Step 1: publish P_cyclic via MoveVM::publish_package.
  verify_package_no_cyclic_relationships:
    pop_last → z_entry; DFS(target=z_entry): visits alpha, beta; no path back to z_entry.
    visited = {alpha, beta}; both removed from to_visit.
    to_visit empty → returns Ok(()).
  P_cyclic published successfully with alpha↔beta cycle on-chain.

Step 2: publish P_user { use P_cyclic::z_entry; }
  verify_linkage_and_cyclic_checks_for_publication:
    cached_packages contains P_cyclic.
    verify_package_no_cyclic_relationships(P_cyclic modules):
      Same pop_last → z_entry path; same pruning; cycle missed again.
    verify_package_no_cyclic_relationships(P_user modules): no intra-package cycle.
  P_user published successfully.

Step 3: call P_user::some_fn → loads z_entry → loads alpha → loads beta → loads alpha → ...
  Infinite recursion / stack overflow in module loader → validator crash.
