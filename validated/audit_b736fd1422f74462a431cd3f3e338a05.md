### Title
Permissionless `deposit`/`mint` on `ProvisionerV2` lets anyone extend a victim's `userUnitsRefundableUntil` lock, freezing the victim's entire pre-existing vault-unit balance from transfer - (File: v3/src/core/ProvisionerV2.sol)

### Summary
`ProvisionerV2.deposit`/`mint` are permissionless functions that let any caller mint vault units to an arbitrary `receiver` address, and as a side effect set `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout` for the *entire* receiver address [1](#0-0) . `MultiDepositorVault._update` blocks any ERC20 transfer where `areUserUnitsLocked(from)` is true, and this check applies to the sender's whole unit balance, not just the newly-received dust amount [2](#0-1) . This mirrors the ThorWallet `isBridgedTokenHolder` root cause: a per-address global flag/timestamp is set by receiving a trivial, attacker-initiated inflow, and it is then used to gate transfers of the victim's entire balance rather than just the newly received portion.

### Finding Description
`deposit()`/`mint()` are guarded only by `anyoneButVault` and `_requireValidReceiver(receiver)` - there is no requirement that `msg.sender == receiver` or that `receiver` approved the depositor [3](#0-2) . Both functions call `_syncDeposit(token, tokensIn, unitsOut, receiver)`, which unconditionally sets `userUnitsRefundableUntil[receiver] = block.timestamp + depositRefundTimeout` [4](#0-3) . `areUserUnitsLocked(user)` simply returns `userUnitsRefundableUntil[user] >= block.timestamp` [5](#0-4) . `MultiDepositorVault._update` reverts any transfer (`transfer`/`transferFrom`) where `from` is locked, except when `from == address(0)` (mint) or `to == address(0)` (burn/redeem) [6](#0-5) .

Root-cause parity with the ThorWallet finding:
- A single per-address state variable (boolean `isBridgedTokenHolder` vs. timestamp `userUnitsRefundableUntil`) is set by an inbound transfer/mint that the victim did not request.
- The resulting restriction is applied to the victim's **entire** balance, not scoped to the specific tokens/units that triggered the state change.
- A malicious actor can trigger the state change with a trivial/dust amount at negligible cost, repeatedly, to keep the victim locked.

An ordinary attacker can call `deposit(token, dustTokensIn, 1, victim)` for any amount of `tokensIn` that rounds to at least 1 unit under `_tokensToUnitsFloorIfActive`, repeatedly, to continuously push `userUnitsRefundableUntil[victim]` forward (capped by `MAX_DEPOSIT_REFUND_TIMEOUT` = 30 days per repeat) [7](#0-6) . Note that redemption (`exit`, called with `to == address(0)` via `_burn`) is not blocked, so this is a transfer-only restriction, not a full fund freeze — it prevents the victim from moving/using vault units peer-to-peer (e.g., as DeFi collateral) for the duration of the lock, which can be perpetually re-extended by the attacker at near-zero cost.

### Impact Explanation
Funds are not stolen, but the victim's vault-unit ERC20 transferability is frozen for `depositRefundTimeout` (up to 30 days) and can be indefinitely re-triggered by an attacker sending trivial deposits on the victim's behalf. This matches an Immunefi Medium-severity "temporary freezing of user funds/transferability" class: the victim cannot transfer, sell, or use their vault units in any external protocol while locked, even though they retain the ability to redeem through the provisioner itself.

### Likelihood Explanation
High feasibility: `deposit`/`mint` are fully permissionless (`anyoneButVault`, no receiver consent/approval check for these entry points), require only a minimal token amount that produces `unitsOut >= 1`, and can be repeated indefinitely by the attacker to keep re-arming the lock on any address holding, or about to hold, vault units.

### Recommendation
Do not let a deposit performed by a third party extend an unrelated receiver's refund lock unconditionally. Options: (1) require `msg.sender == receiver` or an explicit opt-in/approval from `receiver` before `userUnitsRefundableUntil[receiver]` is updated by someone else's deposit; (2) track refund-lock state per deposit hash/amount rather than a single global per-user timestamp, so unrelated pre-existing balances are never subject to another user's newly triggered refund window; (3) scope the `_update` lock check to only the specific units still within their refund window rather than the account's full balance.

### Proof of Concept
Local Foundry fork steps:
1. Deploy/fork `ProvisionerV2` + `MultiDepositorVault` with a whitelisted token and `depositRefundTimeout` set to a nonzero value.
2. As `victim`, call `deposit()` normally (or otherwise acquire units) so `victim` holds a meaningful unit balance and is currently unlocked (`areUserUnitsLocked(victim) == false`).
3. As `attacker` (unrelated EOA), call `provisioner.deposit(token, dustAmount, 1, victim)` where `dustAmount` is the minimum that yields `unitsOut >= 1`.
4. Assert `provisioner.areUserUnitsLocked(victim) == true` and `provisioner.userUnitsRefundableUntil(victim) == block.timestamp + depositRefundTimeout`.
5. As `victim`, call `vault.transfer(otherAddress, victimUnitBalance)` and assert it reverts with `Aera__UnitsLocked()`, despite `victim` never having interacted with `attacker` or consented to the lock.
6. Repeat step 3 just before expiry to show the attacker can perpetually re-lock `victim` at minimal cost.

    function deposit(IERC20 token, uint256 tokensIn, uint256 minUnitsOut, address receiver)

    function _syncDeposit(IERC20 token, uint256 tokenAmount, uint256 unitAmount, address receiver) internal {
        uint256 refundableUntil = block.timestamp + depositRefundTimeout;
        bytes32 depositHash = _getDepositHash(msg.sender, receiver, token, tokenAmount, unitAmount, refundableUntil);

        // Requirements: deposit hash is not set
        require(!syncDepositHashes[depositHash], Aera__HashCollision());
        // Effects: set hash as used
        syncDepositHashes[depositHash] = true;

        // Effects: set receiver's refundable until timestamp
        userUnitsRefundableUntil[receiver] = refundableUntil;

        // Interactions: enter vault
        IMultiDepositorVault(MULTI_DEPOSITOR_VAULT).enter(msg.sender, token, tokenAmount, unitAmount, receiver);

        // Log deposit event
        emit Deposited(msg.sender, receiver, token, tokenAmount, unitAmount, depositHash);
    }

    function _update(address from, address to, uint256 amount) internal override {
        IBeforeTransferHook hook = beforeTransferHook;
        if (address(hook) != address(0)) {
            // Requirements: perform before transfer checks
            hook.beforeTransfer(from, to, provisioner);
        }

        // Requirements: check that the from address does not have its units locked
        // from == address(0) is to allow minting further units for user with locked units
        // to == address(0) is to allow burning units in refundDeposit
        require(
            from == address(0) || to == address(0) || !IProvisionerV2(provisioner).areUserUnitsLocked(from),
            Aera__UnitsLocked()
        );

        // Effects: transfer the tokens
        return super._update(from, to, amount);
