### Title
Deleted multisig members' stale confirmations remain counted toward quorum, allowing a request to execute below the required confirmation threshold - ([File: multisig2/src/lib.rs])

### Summary
`delete_member` in `multisig2/src/lib.rs` only purges the confirmations of requests that were *created by* the member being removed. It does not purge confirmations that the removed member previously cast on *other* pending requests created by someone else. Those stale confirmations remain in the `confirmations` map and continue to be counted by `confirm()` toward `num_confirmations`, even though the confirming member no longer belongs to `self.members` and has had their access key deleted. This lets a request be executed with fewer live/authorized confirmations than `num_confirmations`, mirroring the reported bug class of state that is removed from one structure (the trove/sorted list, here `self.members`) while stale references to it remain trusted elsewhere (the trove manager / here `self.confirmations`), leading to an authorization/threshold check that no longer reflects reality.

### Finding Description
The multisig contract enforces a K-of-N confirmation scheme: `confirm()` checks `confirmations.len() as u32 + 1 >= self.num_confirmations` before executing a request [1](#0-0) . `confirmations` is a `HashSet<String>` keyed by `request_id`, storing the string identity of each member who confirmed [2](#0-1) .

When a member is removed via `DeleteMember`, `delete_member` is invoked:
```rust
fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
    ...
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&member.to_string());
    self.members.remove(&member);
    ...
}
``` [3](#0-2) 

The filter `r.member == member` only matches requests whose **creator** (`MultiSigRequestWithSigner.member`) is the member being deleted [4](#0-3) . It does not scan `self.confirmations` for entries where the removed member's identity string appears as a *confirmer* of requests created by other members. Those confirmation entries are left intact.

`current_member()` (used by `confirm()`) validates that the *caller* is currently in `self.members` before adding a new confirmation [5](#0-4) , but this check is only applied at the moment a new confirmation is added — it is never re-applied retroactively to confirmations that already exist in the set when tallying `confirmations.len()` in `confirm()`. So a stale confirmation string from a now-deleted member is indistinguishable from a live member's confirmation and is counted equally.

**Binding broken:** `confirmations counted == live members who confirmed`. After a member is deleted, this becomes `confirmations counted > live members who confirmed`, because a removed member's confirmation persists in the count.

### Impact Explanation
This falls under the "Critical" impact category explicitly listed in scope: "a multisig request executed below threshold." A request intended to require `num_confirmations` live, currently-authorized members can execute with only `num_confirmations - 1` (or fewer, if multiple members who confirmed are later removed) actual live confirmations, because a removed member's stale confirmation is still tallied. This breaks the fundamental custody/authorization guarantee of the multisig (funds transfers, key additions, contract deployments, etc., are all executed through this same `confirm()`/`execute_request()` path), enabling an under-authorized execution of privileged actions such as `Transfer`, `AddKey`, `FunctionCall`, etc.

### Likelihood Explanation
This requires no privileged access beyond being (or having been) a legitimate multisig member at some point — precisely an "unprivileged former member" scenario, not requiring collusion with the foundation, an owner, or any redeploy. The sequence is a normal part of multisig operation: a member confirms a pending request created by someone else, and is later removed from the multisig (a routine `DeleteMember` action, e.g., due to key rotation, employee offboarding, or compromise response). No unusual timing or race condition is required — the stale confirmation persists indefinitely until the request is separately deleted, confirmed to execution, or the confirmations map entry is otherwise cleared.

### Recommendation
In `delete_member`, before removing the member from `self.members`, iterate over `self.requests`/`self.confirmations` and remove the deleted member's identity string from every confirmation set (not just requests they created), e.g.:
```rust
for (request_id, _) in self.requests.iter() {
    if let Some(mut confirmations) = self.confirmations.get(&request_id) {
        if confirmations.remove(&member.to_string()) {
            self.confirmations.insert(&request_id, &confirmations);
        }
    }
}
```
Alternatively, when tallying confirmations in `confirm()`, recompute the count by filtering `confirmations` against `self.members.contains(...)` for each entry rather than trusting the raw set length, so removed members' stale confirmations are never counted toward quorum.

### Proof of Concept
1. Multisig initialized with members `{A, B, C}` and `num_confirmations = 2`.
2. Member `B` calls `add_request(R)` where `R` transfers funds to an attacker-controlled account (`r.member = B`).
3. Member `A` calls `confirm(R)` — `confirmations[R] = {A}` (1 confirmation, below threshold of 2), so it just stores the confirmation [6](#0-5) .
4. Separately, the remaining members execute a `DeleteMember{A}` request (via normal 2-of-3 confirmation) to remove `A` for unrelated reasons (e.g., offboarding). `delete_member` removes `A` from `self.members` and only clears requests where `r.member == A` — since `R` was created by `B`, `R` and its confirmation set `{A}` are untouched [7](#0-6) .
5. Member `C` (the only other live member) calls `confirm(R)`. `confirmations.len()` is `1` (stale `A`) `+ 1 = 2 >= num_confirmations (2)` → `R` executes [8](#0-7) , even though only one currently-live member (`C`) actually authorized it. The transfer in `R` is executed below the 2-of-3 threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
