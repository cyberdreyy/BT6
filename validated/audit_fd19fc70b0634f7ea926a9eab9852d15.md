### Title
Copyable RANDAO hash-chain commitments allow replay of already-public reveals, letting a validator grind/steer future duty selection - (File: `specs/_features/eip8321/beacon-chain.md`)

### Summary
In the EIP-8321 hash-chain RANDAO feature, `process_randao_commitment_registration` accepts any 32-byte `commitment` value as long as the *registering validator's own* BLS signature covers the registration message; it never verifies that the registrant actually knows a preimage of that commitment. [1](#0-0) 
This lets a validator copy another validator's still-unrevealed commitment as its own. Once the victim later reveals the matching preimage in a block (making it public), the copier can submit that same, already-public value as its own `hash_chain_reveal` in a subsequent slot, because `verify_hash_chain_reveal` only checks `blake3(HASH_CHAIN_RANDAO_DST + reveal) == commitment`, with no binding to who generated the reveal or when it was first used. [2](#0-1) 

### Finding Description
`process_randao` mixes the raw reveal directly into the RANDAO accumulator via a hash chain path: [3](#0-2) 

The security property RANDAO depends on is that every proposer's contribution to `randao_mixes` is *unpredictable to everyone, including the contributor,* until the moment it is revealed on-chain. In the legacy BLS scheme this holds because the reveal is a deterministic-but-unforgeable signature that only the proposer's private key can produce for that epoch.

The hash-chain scheme breaks this property for copied commitments: the copier's `randao_commitments[copier]` entry is set, at registration time, to the same hash as some other validator's chain link, chosen and observed on-chain by the copier ahead of time. The copier does not need to prove knowledge of the preimage — `process_randao_commitment_registration` only checks the copier's own signature over the registration message, not a chain-link proof: [1](#0-0) 

Once the *victim* proposes and reveals the true preimage (which is required to unlock its own next commitment), that preimage becomes public calldata in a finalized block, and the state overwrites `randao_commitments[victim]` with it. But the copier's own slot still holds the *original* (still-unconsumed) commitment hash, which is identical to what the victim just revealed. The copier can therefore later present that now-public value as `body.hash_chain_reveal` and pass `verify_hash_chain_reveal` for its own proposal, mixing an already-known value into `randao_mixes` rather than fresh unpredictable data.

The spec's own note treats this only as "self-defeating" for the copier (it forfeits slots until the victim reveals), but it does not account for what happens *after* the victim reveals: the copier does not merely recover parity — it gains a **known, precomputable** RANDAO contribution instead of a fresh one, which it can time strategically. A staking operator running several validator indices could register copies of several different honest validators' commitments. As each victim reveals over time, the operator accumulates a menu of already-known candidate reveal values. At any of its own proposal opportunities, it can choose whichever available copied-and-now-revealed value produces the most favorable resulting seed for future proposer/committee assignment (via `get_seed`/`get_randao_mix`, looked up `MIN_SEED_LOOKAHEAD` epochs later), or simply skip the slot if none are favorable — a materially stronger grinding capability than the single skip/propose bit available under the legacy scheme. [4](#0-3) 

### Impact Explanation
This is a duty-selection steering issue: RANDAO mixes feed `get_seed`, which determines committee assignment and `get_beacon_proposer_index` for future epochs. A validator that can select, from several already-known candidate contributions, which one to inject (or whether to skip) effectively steers who is chosen for future proposer/attester duties — the class of impact explicitly called out as High ("a duty selection one participant can steer"). It does not directly move Gwei or cause an invalid state transition (each individual copied reveal still passes the stated verification rule), but it undermines the entropy/unpredictability guarantee that RANDAO is meant to provide, which is the exact "constant/predictable difficulty-source" bug class referenced in the external report, mapped onto the beacon chain's randomness primitive.

### Likelihood Explanation
Exploitability requires only a single malicious validator (no coalition, no peer compromise, no foreign key): register a commitment copied from a public, currently-pending registration or a mid-chain commitment belonging to any other validator, and wait for that validator to reveal. This is fully within a single validator's own authority using its own key, satisfying the "unprivileged" requirement. It requires the attacker to run multiple validators to accumulate several usable copied values to meaningfully "choose" among, but a single copy already breaks the unpredictability invariant.

### Recommendation
Bind the commitment to proof of preimage knowledge at registration time (e.g., require a signature or hash-chain proof that is bound to the registering validator's identity, such as hashing in the validator index/pubkey at each link, `blake3(HASH_CHAIN_RANDAO_DST + validator_index + link)`), so a commitment copied from another validator can never produce a matching reveal for the copier. Alternatively, reject registrations whose `commitment` value collides with any other validator's currently pending or active commitment.

### Proof of Concept
1. Validator V registers commitment `C = blake3(DST + seed_V)` via `process_randao_commitment_registration`.
2. Validator A (attacker) observes `C` on-chain and, before `C` activates, registers the identical `commitment=C` for its own index using its own signature — this passes all checks in `process_randao_commitment_registration` since there is no preimage proof.
3. Both `pending_randao_commitments` entries activate; `randao_commitments[V] == randao_commitments[A] == C`.
4. V is selected to propose, and reveals `seed_V` via `process_randao`, which passes `verify_hash_chain_reveal` (`blake3(DST+seed_V)==C`) and publicly stores `seed_V` in `state.randao_commitments[V]`, while `state.randao_commitments[A]` is untouched and still equals `C`.
5. Later, A is selected to propose. A submits `body.hash_chain_reveal = seed_V` (publicly known from step 4). `verify_hash_chain_reveal` succeeds because `blake3(DST+seed_V) == C == randao_commitments[A]`, letting A mix a value into `randao_mixes` that was already public before A's slot began, instead of fresh unpredictable randomness. ```python
def verify_hash_chain_reveal(
    state: BeaconState, body: BeaconBlockBody, proposer_index: ValidatorIndex
) -> None:
    """
    Verify that ``body`` reveals the preimage of the proposer's stored commitment.
    """
    assert body.hash_chain_reveal != Bytes32()
    assert body.randao_reveal == G2_POINT_AT_INFINITY
    commitment = state.randao_commitments[proposer_index]
    assert blake3(HASH_CHAIN_RANDAO_DST + body.hash_chain_reveal) == commitment

def process_randao(state: BeaconState, body: BeaconBlockBody) -> None:
    epoch = get_current_epoch(state)
    proposer_index = get_beacon_proposer_index(state)

    # [New in EIP8321]
    if state.randao_commitments[proposer_index] != UNSET_RANDAO_COMMITMENT:
        verify_hash_chain_reveal(state, body, proposer_index)
        mix = blake3(get_randao_mix(state, epoch) + body.hash_chain_reveal)
        state.randao_mixes[epoch % EPOCHS_PER_HISTORICAL_VECTOR] = mix
        state.randao_commitments[proposer_index] = body.hash_chain_reveal
    else:
        verify_bls_randao_reveal(state, body, proposer_index)
        mix = xor(get_randao_mix(state, epoch), sha256(body.randao_reveal))
        state.randao_mixes[epoch % EPOCHS_PER_HISTORICAL_VECTOR] = mix

def process_randao_commitment_registration(
    state: BeaconState, signed_registration: SignedRandaoCommitmentRegistration
) -> None:
    registration = signed_registration.message
    index = registration.validator_index

    assert index < len(state.validators)
    assert registration.commitment != UNSET_RANDAO_COMMITMENT
    assert state.randao_commitments[index] == UNSET_RANDAO_COMMITMENT
    assert all(pending.validator_index != index for pending in state.pending_randao_commitments)

    # Fork-agnostic domain since registrations are valid across forks
    domain = compute_domain(
        DOMAIN_RANDAO_COMMITMENT_REGISTRATION,
        genesis_validators_root=state.genesis_validators_root,
    )
    signing_root = compute_signing_root(registration, domain)
    validator = state.validators[index]
    assert bls.Verify(validator.pubkey, signing_root, signed_registration.signature)

def get_seed(state: BeaconState, epoch: Epoch, domain_type: DomainType) -> Bytes32:
    """
    Return the seed at ``epoch``.
    """
    mix = get_randao_mix(
        state, epoch + EPOCHS_PER_HISTORICAL_VECTOR - MIN_SEED_LOOKAHEAD - 1
    )  # Avoid underflow
    return sha256(domain_type + uint_to_bytes(epoch) + mix)
