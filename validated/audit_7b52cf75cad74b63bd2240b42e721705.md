### Title
Re-requesting a withdrawal in a later epoch lets a loss-adjusted receipt escape its haircut and be paid at par — (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`requestWithdraw` overwrites `lastWithdrawRequest[_user]` with the current epoch while accumulating the old receipt into the aggregate `withdrawsRequests[_user]`. The claim path only checks `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` (the *latest* epoch) for a loss haircut, then pays the whole aggregate at par in `_claimFundedWithdrawRequest`. This is the analog of CVE-2020-0431's missing bounds check: the epoch index used to look up the haircut is not bounded to the epochs that actually carry receipts, so a receipt from a loss epoch is read as a "fully funded" receipt of a later clean epoch.

### Finding Description
- `requestWithdraw` sets `lastWithdrawRequest[_user] = currentEpoch` and adds to `withdrawsRequests[_user]` / `withdrawsRequestsByEpoch[_user][currentEpoch]` without checking whether the user holds an unclaimed receipt from an earlier epoch that suffered a `stopEpochWithDuration` loss [1](#0-0) .
- On a lossy stop, `collectWithdrawFunds` funds only `_amount < pendingBasis`, sets `pendingWithdraws = 0` and stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis`. All pending receipts of that epoch are thereafter entitled to only `claimBasis * lossRecoveryPrice / RECOVERY_FULL` [2](#0-1) .
- The claim router first tries `_claimLossAdjustedWithdrawRequest`, which uses only `lossEpoch = lastWithdrawRequest[_user]` and returns 0 if that latest epoch has no recorded loss [3](#0-2) .
- `_claimFundedWithdrawRequest` then pays the entire `withdrawsRequests[_user]` (old loss-epoch receipt + new receipt) at par once `epochNumber > lastWithdrawRequest[_user]` [4](#0-3) .
- The code explicitly permits stacking requests ("if a user does not claim a withdraw request and instead requests another withdraw, he will have to wait for another epoch to claim both requests"), so no guard stops the sequence; `deleteWithdrawRequest` only exists on the queue, not on this path.

### Impact Explanation
The strategy receives only `pendingBasis * lossRecoveryPrice / RECOVERY_FULL` for the loss-epoch receipts. An attacker who re-requests in a clean later epoch claims `receipt * 1.0` instead of `receipt * lossRecoveryPrice / RECOVERY_FULL`, withdrawing `(1 - lossRecoveryPrice)` more than entitled from the pool that funds all haircutted claimants. Honest users claiming the same loss epoch afterwards find the strategy under-reserved — direct theft / insolvency for the last claimers, proportional to the attacker's share of the loss-epoch pending bucket and the haircut size.

### Likelihood Explanation
Requires an unprivileged lender (KYC'd) with a pending receipt in an epoch that ends via `stopEpochWithDuration(_lossAmount)`, plus one extra `requestWithdraw` in the following epoch and two epochs of waiting. All roles involved stay honest; the lossy stop is a normal, supported operation (tested in `test/foundry/IdleCDOEpochQueue.t.sol` around line 830). No privileged misbehavior needed.

### Recommendation
Track per-epoch loss exposure rather than only the latest epoch: either iterate `withdrawsRequestsByEpoch` over all epochs with `lossRecoveryPriceByEpoch != 0` for the user, or block `requestWithdraw` while `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0` and the old receipt is uncleared. Alternatively, settle the loss-adjusted portion into a separate haircutted balance at request time.

### Proof of Concept
Foundry fork PoC (sketch, extending `test/foundry/IdleCDOEpochQueue.t.sol` patterns):

```solidity
// epoch N running: attacker + victim request withdrawals
_requestWithdrawWithUser(attacker, 100e18);
_requestWithdrawWithUser(victim,   100e18);

// manager stops epoch N with a 50% loss; borrower funds only pendingToFund
uint256 pendingBasis = strategy.pendingWithdraws();          // 200e18 + interest
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
// borrower repays fundsToRepay incl. pendingToFund (~= pendingBasis/2)
cdoEpoch.stopEpochWithDuration(apr, 0, duration, lossAmount);
// => lossRecoveryPriceByEpoch[N] ~= 0.5e18; strategy holds only ~pendingBasis/2 for these receipts

// buffer of epoch N+1: attacker re-requests instead of claiming
cdoEpoch.startEpoch();
_requestWithdrawWithUser(attacker, 1e18);                    // lastWithdrawRequest -> N+1

// epoch N+1 ends cleanly, fully funded
cdoEpoch.stopEpoch(...);

// attacker claims: _claimLossAdjustedWithdrawRequest looks up epoch N+1 (no loss) -> 0
// _claimFundedWithdrawRequest pays withdrawsRequests[attacker] (101e18) at PAR
strategy.claimWithdrawRequest(attacker);  // receives ~101e18, not ~51e18

// victim claims correct haircutted amount, but pool is drained:
strategy.claimWithdrawRequest(victim);    // expects ~50e18; strategy is short by ~50e18
```

The broken invariant is one-receipt-one-priced-payout / loss waterfall: a receipt minted in a loss epoch is paid at a later epoch's un-impaired price because only `lastWithdrawRequest` is consulted for the loss lookup.

Note: I verified the claim routing and funding logic in `IdleCreditVault.sol` (lines 271–460, 560–800) but could not fully confirm within this session that no other path (e.g., CDO-side gating on repeat `requestWithdraw` after a loss epoch) blocks step 3; the vault itself imposes no such check.

  function collectWithdrawFunds(uint256 _amount) external {
    _onlyIdleCDO();
    uint256 pendingBasis = pendingWithdraws;
    if (_amount < pendingBasis) {
      // Legacy receipts do not have per-epoch ownership data, so they can only be fully funded.
      if (!defaultRecoveryInitialized) revert NotAllowed();
      uint256 lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis;
      // Avoid storing a zero price, which is indistinguishable from "no loss-adjusted epoch".
      if (lossRecoveryPrice == 0) revert NotAllowed();
      pendingWithdraws = 0;
      lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice;
    } else {
      // A plain implementation upgrade may leave legacy normal receipts pending. Their next
      // successful stop can fully fund the aggregate before lazy initialization occurs.
      pendingWithdraws = pendingBasis - _amount;

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
