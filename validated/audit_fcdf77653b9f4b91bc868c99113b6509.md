### Title
Fail-open handling of a failed `get_tenure_tip` RPC lets a signer sign a conflicting block in the same tenure - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
In `handle_block_pre_commit`, once the pre-commit threshold is reached, the signer must decide whether a stale-but-same-tenure conflicting signature still blocks the new block. To answer that, it queries the node for the tenure's canonical tip via `stacks_client.get_tenure_tip(...)`. If that RPC call fails, the code does **not** refuse to sign (the safe default used elsewhere in the very same function); instead it logs a warning and falls through, ultimately signing the "replacement" block anyway.

### Finding Description
The decision path is: [1](#0-0) 

- Conflicts in the **same tenure** (`conflict.consensus_hash == block_info.block.header.consensus_hash`) that are not covered by a valid reorg permit require checking whether the node's tenure tip is already at or above the proposed block's height; if it is, the existing conflicting signature already represents chain state that the new block would duplicate, so the signer must refuse to sign.
- This check depends entirely on a successful `get_tenure_tip` RPC call to the local stacks-node.
- On `Err(e)` (RPC/connectivity failure, node restart, timeout, node paused/overloaded, etc.) the code logs `"Treating the tenure as unconfirmed"` and does not return - it simply falls out of the `match` with no refusal: [2](#0-1) 
- Immediately after, because `conflicts` is non-empty, the code logs `"Signing the replacement"` and proceeds to `mark_locally_accepted`/sign: [3](#0-2) 

This is the direct analog of the reported `StakedEXA::harvest()` bug class: a decision that depends on an external subsystem's state (there, the `Market`'s paused/frozen flag reachable via a revert; here, the node's RPC availability/tenure tip) is not treated as "unknown, therefore refuse," but is instead assumed to resolve favorably for the caller, causing an unsafe action to proceed. Contrast this with the *other* error-handling branch just a few lines earlier in the same function, which does fail closed: a `signer_db` query error causes an explicit `return` ("Refusing to sign"): [4](#0-3) 

So within one function, an error on the local DB query is treated as "refuse", while an error on the node RPC for the exact same conflict-resolution question is treated as "proceed and sign." This asymmetry is also reflected (and appears intentional) in the flow documentation: [5](#0-4) 

### Impact Explanation
If the local stacks-node briefly fails to answer `get_tenure_tip` (restart, load, RPC timeout, temporary disconnect - none of which require compromising a majority of signers, another signer's key, or the auth token), a signer that has already signed one block in a tenure can end up also signing a second, conflicting block at the same/higher height in that tenure once the pre-commit threshold for the second block is reached. This breaks the "one signed block per height per tenure" equivocation guard that the rest of `handle_block_pre_commit` is explicitly designed to enforce, matching the in-scope Critical impact category: "a signer signing an invalid, non-canonical, or conflicting block."

### Likelihood Explanation
Triggering requires only a transient RPC/connectivity failure between the signer and its own node at the moment the pre-commit threshold is reached for a block that conflicts with an already-signed sibling in the same tenure - a condition a single node/signer operator (or ordinary network flakiness) can hit without needing majority signer collusion, another signer's key, or local file access. This matches the "market frozen/paused" precondition class in the source report: an external dependency being transiently unavailable during a security-relevant check.

### Recommendation
Treat an error from `get_tenure_tip` the same way the earlier `get_signed_conflicts` DB error is treated: refuse to sign (return without marking `locally_accepted`) rather than falling through to "treating the tenure as unconfirmed." At minimum, retry or re-queue the pre-commit evaluation instead of defaulting to sign-on-uncertainty for a check whose entire purpose is preventing conflicting signatures.

### Proof of Concept
1. Signer S has already signed block A in tenure T (`get_signed_conflicts` will later return A as a same-tenure conflict for any block at height ≥ A's height).
2. A competing/re-proposed block B at the same height in tenure T is proposed and validated; pre-commits accumulate and cross the 70% threshold, invoking `handle_block_pre_commit` for B on signer S.
3. `conflicts` (from `get_signed_conflicts`) includes A; A is same-tenure and (assume) not covered by a reorg permit, so the code reaches the `stacks_client.get_tenure_tip(...)` call at line 1436.
4. Simulate/introduce a transient RPC failure from S's node at that exact moment (network partition/restart/timeout to the local node's RPC endpoint).
5. Execution hits the `Err(e)` branch at lines 1449-1455, logs "Treating the tenure as unconfirmed," and does not return.
6. Because `conflicts` is non-empty, code proceeds to log "Signing the replacement" and calls `mark_locally_accepted`, producing a second signature over B despite A already being signed in the same tenure - violating the intended one-signature-per-height-per-tenure guarantee.
