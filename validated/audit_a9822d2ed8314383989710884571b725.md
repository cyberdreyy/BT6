### Title
Bridge OutgoingToken secret disclosed via GET /v2/bridge_types/:BridgeName to any authenticated (including view-role) user - (File: core/web/presenters/bridges.go)

### Finding Description
`presenters.NewBridgeResource` unconditionally copies `b.OutgoingToken` into the JSON-serialized `BridgeResource.OutgoingToken` field, which has no `omitempty` and no caller-privilege gating: [1](#0-0) 

By contrast, `IncomingToken` is tagged `omitempty` and is only ever populated explicitly in `BridgeTypesController.Create` right after generation (`resource.IncomingToken = bta.IncomingToken`), and is never re-derivable afterward because the stored `BridgeType.IncomingTokenHash` is a salted hash, not plaintext: [2](#0-1) [3](#0-2) 

However, `BridgeType.OutgoingToken` is stored and retained in plaintext in the DB, and `FindBridge` returns it as-is. `BridgeTypesController.Show` calls `btc.App.BridgeORM().FindBridge` and directly feeds the result to `presenters.NewBridgeResource` with no role check beyond whatever authentication middleware sits in front of the route: [4](#0-3) 

This same unconditional inclusion of `OutgoingToken` also occurs in `Index`, `Update`, and `Destroy` responses, meaning any authenticated caller permitted to invoke these read/list endpoints receives the outgoing secret in plaintext: [5](#0-4) 

I was unable to fully confirm within this session the exact role-requirement middleware attached to the `/v2/bridge_types/:BridgeName` GET route (the `v2Routes` registration in `core/web/router.go` was not retrieved before the tool budget was exhausted), so I cannot state with certainty whether `Show`/`Index` are gated by `RequiresEditRole` or a lower `RequiresViewRole`/authenticated-only check. If the route only requires authentication (any role, including view), the presenter code confirmed above unconditionally leaks `OutgoingToken` to that caller.

### Impact Explanation
If `Show`/`Index` are reachable by view-role (or lower-privileged) authenticated sessions, this discloses the bridge's `OutgoingToken`, the shared secret the node uses to authenticate itself to the external adapter/bridge endpoint. An attacker in possession of it could forge requests directly to the bridge's consumer service impersonating the Chainlink node, matching the "secret/credential disclosure" bounty impact class scoped to the bridge integration boundary — it does not, by itself, grant control over the node's own accounts, keys, or job execution.

### Likelihood Explanation
Requires only an existing authenticated session/API token for the node (any role capable of invoking bridge read endpoints) and knowledge/guess of a configured bridge name; no additional privilege escalation step beyond obtaining a low-privilege session is needed if the route's role check permits it. Feasibility hinges on the unconfirmed role gate on the route, which is the key uncertainty in this analysis.

### Recommendation
- Redact `OutgoingToken` from `BridgeResource` for GET/Index responses (make it `omitempty` and only populate it, like `IncomingToken`, at creation time, or restrict its output to `RequiresEditRole`/`RequiresAdminRole` callers).
- Verify and, if needed, tighten the role middleware on the bridge_types read routes in `core/web/router.go` so `Show`/`Index` require edit/admin role, not just authentication/view role.

### Proof of Concept
Go handler-integration test plan (using `core/web/bridge_types_controller_test.go` patterns):
1. Create a bridge via admin/edit session (`POST /v2/bridge_types`), capture the `OutgoingToken` value stored in DB.
2. Authenticate a second session/token scoped to view-role (per the app's RBAC test helpers used elsewhere in `core/web/*_controller_test.go`).
3. Issue `GET /v2/bridge_types/<name>` with the view-role session.
4. Assert:
   - If route enforces edit/admin role: response is `401/403` before reaching `presenters.NewBridgeResource` (no vulnerability).
   - If route only requires authentication: response body JSON contains `attributes.outgoingToken` equal to the stored plaintext token, confirming disclosure to a view-role caller — this is the vulnerable case, and the fix is to gate/redact the field as above.

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
