### Title
Signer accepts a block for a tenure whose `last_sortition.miner_status` is `InvalidatedBeforeFirstBlock` because `check_proposal`'s `ProposedBy::LastSortition` branch never re-checks `last_sortition.miner_status` - (File: stacks-signer/src/chainstate/v1.rs)

### Summary
`SortitionsView::check_proposal` computes and can flip `last_sortition.miner_status` to `SortitionMinerStatus::InvalidatedBeforeFirstBlock` in the very same call (via the `is_timed_out` check at lines 205-219), but the acceptance gate for `ProposedBy::LastSortition` proposals only inspects `self.cur_sortition.miner_status`, never `last_sortition.miner_status`. A miner who has already been ruled invalid for their own (now "last") tenure can therefore still get a block for that tenure accepted, as long as the newer (`cur_sortition`) tenure has also independently timed out before its first block.

### Finding Description
The claimed identity check is: "the `SortitionMinerStatus` consulted == the status object of the sortition the block's `consensus_hash` actually names." This identity is broken for the `LastSortition` branch.

- At lines 205-219, `check_proposal` independently evaluates `last_sortition`'s timeout status and, if timed out with no signed block, sets `last_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock`: [1](#0-0) 

- Later, when the proposed block's `consensus_hash` matches `last_sortition.data.consensus_hash`, the code resolves `ProposedBy::LastSortition(last_sortition)` (lines 245-253), and the acceptance gate for that branch checks only `self.cur_sortition.miner_status`: [2](#0-1) 

The `last_sortition.miner_status` value that was just computed a few lines earlier (and could be `InvalidatedBeforeFirstBlock`) is never read in this branch. Compare with the `CurrentSortition` branch, which correctly consults `sortition.miner_status` (the status object matching the sortition the block actually names): [3](#0-2) 

Root cause: the `LastSortition` gate was written to answer "has the newer miner been excused yet?" but omits the complementary check "is the older miner (the one this block actually names) still considered valid?" The `SortitionMinerStatus` object bound to `last_sortition` is mutated but structurally disconnected from the decision that dispatches on it.

Attacker's exact proposal/message: a `NakamotoBlock` (wrapped in a `BlockProposal`) whose `header.consensus_hash` equals the already-invalidated `last_sortition`'s consensus hash, signed by that sortition's winning miner key (which the attacker controls, since they won that slot), and pushed again (or simply not-yet-processed) after the newer tenure (`cur_sortition`) itself times out.

Exploit flow:
1. Attacker wins sortition N (this becomes `last_sortition` after the next sortition N+1 occurs). Attacker withholds/never gets a block signed for N within `block_proposal_timeout`.
2. The next sortition N+1 occurs; `SortitionsView::fetch_view`/`reset_view` builds a fresh view with `cur_sortition = N+1` (status reset to `Valid` per `TryFrom<SortitionInfo>`) and `last_sortition = N`.
3. Signer calls `check_proposal` for some proposal. At lines 144-163, if `cur_sortition` (N+1) has also timed out with no block, it is marked `InvalidatedBeforeFirstBlock`.
4. In the very same call, lines 205-219 independently evaluate `last_sortition` (N)'s timeout and, since N never had a signed block either, mark it `InvalidatedBeforeFirstBlock` too.
5. Attacker (re)gossips their block proposal for tenure N. `consensus_hash` matches `last_sortition`, so `ProposedBy::LastSortition` is selected.
6. The gate at lines 304-306 only checks `self.cur_sortition.miner_status != InvalidatedBeforeFirstBlock` — which is now true (since step 3) — so the branch is entered and the proposal proceeds to pubkey/tenure-change checks, never rejecting on the fact that `last_sortition.miner_status` is itself `InvalidatedBeforeFirstBlock`.
7. The proposal can pass and be signed, even though the signer's own state machine has already ruled this exact tenure's miner invalid.

Existing guards don't catch this: the pubkey-hash check (line 276) only verifies the block was signed by the correct sortition winner, not that the winner is still "valid"; the tenure-change/parent-block checks address a different property (parent linkage), not miner validity. The one guard that exists (`InvalidatedBeforeFirstBlock`) is computed but not read for this exact code path.

### Impact Explanation
This breaks the canonicity/validity safety property: the signer can sign a block for a tenure it has already determined is invalid (`InvalidatedBeforeFirstBlock`), i.e., a rejection outcome is effectively bypassed for the `LastSortition` path. Per the severity rubric this is Critical: "a signer signing an invalid, non-canonical, or conflicting block." The bug is deterministic and repeatable any time two consecutive tenures both go empty (a realistic and not-uncommon condition, e.g., during rapid successive burn blocks or slow/absent miners), not merely a one-off race.

### Likelihood Explanation
Preconditions are attacker-cheap and match the question's setup exactly: the attacker needs to win one sortition (their own miner slot, consistent with the unprivileged attacker model), withhold a block long enough to trip `block_proposal_timeout` for their own tenure, and then rely on (or wait for) the following tenure to also go empty/time out — a natural, frequently-occurring network condition, not something requiring majority-signer collusion or privileged access. No auth token, no other signer's key, and no local host access are needed; only a single BlockProposal gossip message is required. This is repeatable across reward cycles/tenures whenever two consecutive sortitions are both empty.

### Recommendation
In the `ProposedBy::LastSortition` branch of `check_proposal` (stacks-signer/src/chainstate/v1.rs, lines 301-316), also require that `last_sortition.miner_status` is not `InvalidatedBeforeFirstBlock` (i.e., check both `last_sortition.miner_status == SortitionMinerStatus::Valid` or `InvalidatedAfterFirstBlock`, in addition to the existing `cur_sortition.miner_status == InvalidatedBeforeFirstBlock` requirement) before accepting the proposal, mirroring the identity check already performed correctly in the `CurrentSortition` branch.

### Proof of Concept
Add a test in `stacks-signer/src/chainstate/tests/v1.rs` modeled on `check_proposal_invalid_status`, but targeting `last_sortition`'s own status instead of only `cur_sortition`'s:

```rust
#[test]
fn check_proposal_last_sortition_invalid_status_bypass() {
    let (stacks_client, mut signer_db, block_sk, mut view, mut block) =
        setup_test_environment(function_name!());

    // Simulate that BOTH the current tenure and the last tenure have
    // been independently ruled invalid before their first block
    // (as would happen via the is_timed_out logic at lines 205-219
    // and 144-163 in the same check_proposal call).
    view.cur_sortition.miner_status = SortitionMinerStatus::InvalidatedBeforeFirstBlock;
    view.last_sortition.as_mut().unwrap().miner_status =
        SortitionMinerStatus::InvalidatedBeforeFirstBlock;

    // Craft a block proposal naming the already-invalidated last_sortition's tenure.
    block.header.consensus_hash = view
        .last_sortition
        .as_ref()
        .unwrap()
        .data
        .consensus_hash
        .clone();
    block.header.sign_miner(&block_sk).unwrap();

    let result = view.check_proposal(
        &stacks_client,
        &mut signer_db,
        &block,
        false,
        ReplayTransactionSet::none(),
    );

    // Correct behavior: MUST be rejected because last_sortition.miner_status
    // is InvalidatedBeforeFirstBlock (the sortition the block's consensus_hash
    // actually names is already invalid).
    result.expect_err(
        "Proposal for a last_sortition tenure that is itself InvalidatedBeforeFirstBlock \
         must be rejected, but current code only checks cur_sortition.miner_status",
    );
}
```

Before the fix, `check_proposal` returns `Ok(())` (bug: identity violated — the status consulted is `cur_sortition.miner_status`, not `last_sortition.miner_status`, the one that actually names the proposal's tenure). After adding the recommended check, the test should assert `RejectReason::InvalidMiner` (or a new dedicated reason) and pass.
