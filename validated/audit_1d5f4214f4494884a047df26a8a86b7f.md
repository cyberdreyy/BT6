### Title
Front-runnable, unauthenticated `LockupFactory::create()` allows deployment of a maliciously-configured lockup at the address a funder will predict, releasing tokens without vesting/forfeiture - (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` derives the lockup contract's account ID **only** from `sha256(owner_account_id)`, and is callable by *anyone* who attaches the small `MIN_ATTACHED_BALANCE` (3.5 NEAR). Because the resulting address depends solely on a value (`owner_account_id`) that is public and chosen by the caller, an attacker can pre-compute the exact address a legitimate funder (e.g. an employer or the NEAR Foundation) intends to use for a given employee/owner, and race to deploy the lockup first with attacker-favorable parameters (no vesting schedule, no `foundation_account_id`, minimal `lockup_duration`, no `release_duration`). This is the NEAR analog of the reported CREATE2-salt-hijack: the predicted address does not bind the deployed contract's *state*, only its owner field, so a party trusting the address gets a contract in an unexpected configuration.

### Finding Description
`create()` computes the deterministic account id purely from the attacker-suppliable `owner_account_id` and the immutable factory account id: [1](#0-0) 

There is no access control on who may call `create()`, no registry preventing re-use of a given `owner_account_id`, and no verification that the `predecessor_account_id` matches or is authorized by the `owner_account_id`. Any account can call `create()` for any `owner_account_id`, choosing:
- `vesting_schedule = None` → `foundation_account_id` is set to `None`, i.e. no forfeiture/termination authority at all: [2](#0-1) 
- an arbitrarily small `lockup_duration` and `release_duration = None`, so once the fixed `TransfersInformation::TransfersEnabled` timestamp (already in the past, `TRANSFERS_STARTED`) plus the tiny duration elapses, the entire balance unlocks in one shot: [3](#0-2) 

The lockup contract's own unlock logic confirms this: with `release_duration = None`, `unreleased_amount` is `0` as soon as `lockup_timestamp <= block_timestamp`, and with `vesting_information = VestingInformation::None`, `get_unvested_amount` also returns `0`, so `get_locked_amount()` becomes `0` immediately — full balance liquid: [4](#0-3) [5](#0-4) 

Because `create_account()` fails on-chain if the target account already exists, whichever `create()` call lands first on the deterministic address "wins" it; the loser's promise chain fails and its deposit is refunded via `on_lockup_create`: [6](#0-5) 

The `assert_called_by_foundation` check that guards clawback of unvested tokens only fires `if let Some(foundation_account_id)` — with `foundation_account_id = None` (attacker's deployment), the clawback path is permanently unavailable, i.e. the intended forfeiture/termination protection can never be enforced for that lockup: [7](#0-6) 

### Impact Explanation
A funder (employer/foundation) that computes the predicted lockup address off-chain from `owner_account_id` and later sends NEAR to that address as a "top-up" (a plain transfer to an already-existing account, bypassing `create()`), or that relies on `owner_account_id` matching as sufficient verification, will unknowingly fund a lockup contract with:
- no vesting schedule and no `foundation_account_id` (no clawback/forfeiture ever possible), and
- an attacker-chosen short `lockup_duration` with no `release_duration` (immediate full release once the fixed transfers-enabled timestamp plus duration elapses — which, given `TRANSFERS_STARTED` is already a past timestamp, can be near-instant).

This is a case of "locked or unvested tokens released early" and permanent loss of the intended forfeiture mechanism — a Critical impact per the stated criteria, because the deployed contract's *state* (the actual custody schedule) diverges from what the funder/verifier assumed the address represented.

### Likelihood Explanation
Likelihood is high for any unprivileged attacker who can observe/guess a target `owner_account_id` before the legitimate `create()` transaction is included: the attack only requires calling the public `create()` method with the victim's `owner_account_id` and 3.5 NEAR, no special permissions, no owner keys, and no cooperation from any privileged party. The address is fully and cheaply predictable off-chain by anyone (same `sha256` formula the legitimate funder uses), enabling a pure front-run.

### Recommendation
Bind the deployed lockup's address (or its accepted initialization) to more than `owner_account_id`: e.g. require the funder to be the same as `owner_account_id` or a designated authorized creator, include the full set of critical parameters (`vesting_schedule`/`foundation_account_id` presence, `lockup_duration`, `release_duration`) in the derived salt/address, or provide a way for the funder to verify—atomically, on-chain, in the same transaction—that the account did not already exist with unexpected parameters before transferring additional funds to it (e.g. only fund via the factory's `create()` call itself, never via a bare transfer to a precomputed address).

### Proof of Concept
1. Foundation/employer decides to grant `alice.near` a lockup with a vesting schedule and intends to later top up `alice.near`'s lockup address (`sha256("alice.near")[:20].lockup-master`) directly.
2. Before the Foundation's `create()` transaction lands, an attacker submits `create(owner_account_id="alice.near", lockup_duration=1, lockup_timestamp=None, vesting_schedule=None, release_duration=None, whitelist_account_id=None)` with `MIN_ATTACHED_BALANCE` attached (`lockup-factory/src/lib.rs:107-166`).
3. The attacker's transaction executes first, deploying the lockup contract at the exact predicted address with `owner_account_id = "alice.near"`, `foundation_account_id = None`, no vesting schedule, and a 1-nanosecond `lockup_duration`.
4. The Foundation's later `create()` call for the same `owner_account_id` fails (`create_account` on an existing account fails), and its deposit is refunded via `on_lockup_create` (`lockup-factory/src/lib.rs:171-198`) — but if the Foundation instead performs a raw `transfer` to the already-known address (a common "top-up" pattern) rather than re-issuing `create()`, those funds land in the attacker-configured contract.
5. Because `TRANSFERS_STARTED` is already in the past and `lockup_duration=1` and `release_duration=None`, `get_locked_amount()` returns `0` essentially immediately (`lockup/src/getters.rs:65-113`), and since `vesting_information = VestingInformation::None`, no foundation clawback is ever possible (`lockup/src/internal.rs:110-120`). Alice (owner) can withdraw the entire balance immediately, defeating the intended lockup/vesting/forfeiture guarantee.

                    .as_bytes(),

            false
        }
    }

    pub fn get_locked_amount(&self) -> WrappedBalance {
        let lockup_amount = self.lockup_information.lockup_amount;
        if let TransfersInformation::TransfersEnabled {
            transfers_timestamp,
        } = &self.lockup_information.transfers_information
        {
            let lockup_timestamp = std::cmp::max(
                transfers_timestamp
                    .0
                    .saturating_add(self.lockup_information.lockup_duration),
                self.lockup_information.lockup_timestamp.unwrap_or(0),
            );
            let block_timestamp = env::block_timestamp();
            if lockup_timestamp <= block_timestamp {
                let unreleased_amount =
                    if let &Some(release_duration) = &self.lockup_information.release_duration {
                        let end_timestamp = lockup_timestamp.saturating_add(release_duration);
                        if block_timestamp >= end_timestamp {
                            // Everything is released
                            0
                        } else {
                            let time_left = U256::from(end_timestamp - block_timestamp);
                            let unreleased_amount = U256::from(lockup_amount) * time_left
                                / U256::from(release_duration);
                            // The unreleased amount can't be larger than lockup_amount because the
                            // time_left is smaller than total_time.
                            unreleased_amount.as_u128()
                        }
                    } else {
                        0
                    };

                let unvested_amount = match &self.vesting_information {
                    VestingInformation::VestingSchedule(vs) => self.get_unvested_amount(vs.clone()),
                    VestingInformation::Terminating(terminating) => terminating.unvested_amount,
                    // Vesting is private, so we can assume the vesting started before lockup date.
                    _ => U128(0),
                };
                return std::cmp::max(
                    unreleased_amount
                        .saturating_sub(self.lockup_information.termination_withdrawn_tokens),
                    unvested_amount.0,
                )
                .into();
            }
        }
        // The entire balance is still locked before the lockup timestamp.
        (lockup_amount - self.lockup_information.termination_withdrawn_tokens).into()
    }

    pub fn get_unvested_amount(&self, vesting_schedule: VestingSchedule) -> WrappedBalance {
        let block_timestamp = env::block_timestamp();
        let lockup_amount = self.lockup_information.lockup_amount;
        match &self.vesting_information {
            VestingInformation::Terminating(termination_information) => {
                termination_information.unvested_amount
            }
            VestingInformation::None => U128::from(0),
            _ => {
                if block_timestamp < vesting_schedule.cliff_timestamp.0 {
                    // Before the cliff, nothing is vested
                    lockup_amount.into()
                } else if block_timestamp >= vesting_schedule.end_timestamp.0 {
                    // After the end, everything is vested
                    0.into()
                } else {
                    // cannot overflow since block_timestamp < vesting_schedule.end_timestamp
                    let time_left = U256::from(vesting_schedule.end_timestamp.0 - block_timestamp);
                    // The total time is positive. Checked at the contract initialization.
                    let total_time = U256::from(
                        vesting_schedule.end_timestamp.0 - vesting_schedule.start_timestamp.0,
                    );
                    let unvested_amount = U256::from(lockup_amount) * time_left / total_time;
                    // The unvested amount can't be larger than lockup_amount because the
                    // time_left is smaller than total_time.
                    unvested_amount.as_u128().into()
                }
            }
        }
    }
