### Title
Stale confirmations from a removed multisig key are still counted toward quorum, letting a request execute below the real live-member threshold - (File: `multisig/src/lib.rs`)

### Summary
The external report's root cause is that a "top voted" custody decision (`dropTopVotedPiece`) can be based on a metric (`quorumVotes`, cached from `totalSupply()` at piece-creation time) that no longer reflects the live/authoritative state. The direct NEAR analog is in the Basic Multisig contract: the quorum check in `confirm()` counts entries in the `confirmations: HashSet<PublicKey>` set for a request, but `DeleteKey` (the action that revokes a key's membership) only purges confirmations for requests *authored by* the removed key, not confirmations that key had already *cast* on other pending requests. The binding `confirmations_counted == confirmations_from_currently_live_members` is broken.

### Finding Description
`confirm()` executes a request once the number of entries in the request's confirmation set reaches `num_confirmations`: [1](#0-0) 

The set is simply a `HashSet<PublicKey>` of keys that have confirmed; it is never validated against the current set of live access keys on the account, because as the contract's own README acknowledges, NEAR has no way to query the current access-key set on-chain: [2](#0-1) 

`DeleteKey` is the action that revokes a member's authority (it issues `promise.delete_key(pk)`), but its cleanup logic only removes requests and confirmation sets for requests whose `signer_pk` (i.e., the request's *author*) equals the deleted key. It never scans other pending requests to strip confirmations that the deleted key had already cast on them: [3](#0-2) 

Concretely: key `B` confirms pending request `R1` (created by key `A`), leaving `R1` at 1/`num_confirmations` confirmations. The multisig later executes a separate `DeleteKey{public_key: B}` request (approved by the required threshold), revoking `B`. `R1`'s confirmation set still contains `B`'s public key, because the `DeleteKey` handler only filtered on `r.signer_pk == pk` (author), not on entries inside `confirmations` maps of *other* requests. Key `A` can then call `confirm(R1)`; the count `confirmations.len() + 1 = 2` satisfies `num_confirmations` and `R1` (e.g. a `Transfer` or `AddKey`) executes — even though only one currently-live, authorized key (`A`) actually approved it.

### Impact Explanation
This breaks the multisig's core custody guarantee: a request (transfer of funds, adding a new full-access key, deploying new contract code, etc.) can be executed with confirmations that include a key that is no longer a trusted member of the multisig. This matches the Critical impact bucket "a multisig request executed below threshold" — the *effective* threshold of currently-authorized signers is lower than `num_confirmations` states, enabling unauthorized fund movement or privilege escalation (e.g., an attacker who once held a now-revoked key, or a compromised key that was deliberately removed after being used to pre-confirm a malicious pending request, can still push that request through).

### Likelihood Explanation
This requires no attacker privilege beyond normal multisig membership: any key that confirms a request and is later removed retains a "ghost vote" on all *other* pending requests it confirmed. In active multisigs that rotate keys (a normal, expected operational event — replacing a compromised or departing member), this can occur naturally, and can also be deliberately engineered (confirm several innocuous-looking pending requests broadly, then get removed, with those confirmations still able to be leveraged by a colluding remaining member to push execution below the intended live threshold).

### Recommendation
When executing `DeleteKey` (or `DeleteMember` in `multisig2`), scan all pending requests' `confirmations` sets (not just requests authored by the removed key) and strip the removed key/member from every confirmation set, re-evaluating request state accordingly. Alternatively, validate at `confirm()`/execution time that all counted confirmers are still current members before allowing execution.

### Proof of Concept
1. Deploy `MultiSigContract::new(2)` with 3 access keys `A`, `B`, `C`.
2. Key `A` calls `add_request` with `MultiSigRequest{ receiver_id: <self>, actions: [Transfer{amount}] }` → `R1` (0 confirmations).
3. Key `B` calls `confirm(R1)` → `R1` now has 1 confirmation (`{B}`), below threshold of 2.
4. Separately, `A` and `C` create and confirm a `DeleteKey{public_key: B}` request against the multisig account, executing it (2/2 confirmations) — `B` is now revoked as an access key.
5. Key `A` calls `confirm(R1)`. `confirmations.len() + 1 == 2 >= num_confirmations`, so `execute_request` fires the `Transfer`, even though `B` is no longer a valid multisig member — the transfer executed with only one currently-live confirming key. [4](#0-3) [3](#0-2)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
