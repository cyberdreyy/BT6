### Title
Unconstrained `protocolFeeAmount`/`integratorFeeAmount` in caller-supplied `createDstEscrow` immutables enables theft of maker funds or DoS on destination withdrawal - ([File: contracts/BaseEscrowFactory.sol])

### Summary
`createDstEscrow` accepts an arbitrary `Immutables` struct from `msg.sender`, including the `parameters` field that encodes `protocolFeeAmount`, `integratorFeeAmount`, `protocolFeeRecipient`, and `integratorFeeRecipient`. Unlike the source-side path (`_postInteraction`), there is no check that `integratorFeeAmount + protocolFeeAmount` stays below `immutables.amount`, and no check that the fee recipients/amounts match any legitimately agreed values.

### Finding Description
On the source chain, `BaseEscrowFactory._postInteraction` computes `integratorFeeAmount`/`protocolFeeAmount` via `FeeTaker._getFeeAmounts` and explicitly guards them: [1](#0-0) 

This guarded value pair is only emitted (in `SrcEscrowCreated`) as an off-chain hint for the destination escrow's `parameters`; it is not itself enforced on-chain for the destination side.

On the destination chain, `createDstEscrow` builds the `Immutables` directly from caller-supplied calldata (`dstImmutables`), with no validation of the `parameters` bytes field (which holds the fee amounts/recipients) at all: [2](#0-1) 

`EscrowDst._withdraw` then blindly trusts these caller-supplied values, transferring `integratorFeeAmount` and `protocolFeeAmount` to attacker-controllable recipients before computing the maker's remainder: [3](#0-2) 

Since anyone can call `createDstEscrow` (no whitelist/access-control modifier on this function) and freely choose `parameters`, `protocolFeeRecipient`, and `integratorFeeRecipient` — with `protocolFeeAmount + integratorFeeAmount` unconstrained relative to `immutables.amount` — this is the same unbounded "fee percentage/amount" bug class as the external `LoanVault.setApr/setFundingFee` report, but reachable by an unprivileged caller rather than an owner:
- Setting `integratorFeeAmount` (or `protocolFeeAmount`) close to or equal to `immutables.amount`, with the corresponding fee recipient set to an attacker address, diverts most/all of the maker's destination funds to the attacker as a "fee" instead of the maker.
- Setting `integratorFeeAmount + protocolFeeAmount > immutables.amount` causes `immutables.amount - integratorFeeAmount - protocolFeeAmount` in `_withdraw` (contracts/EscrowDst.sol:92) to underflow and revert under Solidity 0.8 checked arithmetic, permanently DoS-ing `withdraw`/`publicWithdraw` for that escrow until the cancellation timelock, freezing the deposited destination funds during the live swap lifecycle.

### Impact Explanation
This maps to two allowed bounty impacts:
- Theft of unclaimed fee-like value / maker funds: an attacker-chosen fee recipient captures value that should have gone to the maker (High, potentially Critical if it results in permanent loss of the maker's destination-side proceeds).
- Temporary freezing of funds during the live swap lifecycle: an underflow-induced revert blocks `withdraw`/`publicWithdraw` on the destination escrow until cancellation (Medium/High).

### Likelihood Explanation
Any unprivileged address can call `createDstEscrow` directly and fully control the `Immutables.parameters` field; there is no on-chain cross-check against the source-side committed fee percentages/amounts (the only such check, `InvalidFeeAmounts`, exists solely in `_postInteraction` for the source path). The likelihood of triggering the state depends on whether downstream off-chain relayers/makers validate the destination escrow's parameters before revealing the secret; the on-chain contract itself provides no such guarantee, which is the root cause matching the report's "no min/max validation on a percentage/amount input" class.

### Recommendation
Add validation in `createDstEscrow` (or in `EscrowDst._withdraw`) mirroring the source-side guard: require `integratorFeeAmount + protocolFeeAmount < immutables.amount`, and ideally bind the destination `parameters` (fee amounts and recipients) to the values already committed on the source side (e.g., via a hash check against `DstImmutablesComplement.parameters` emitted in `SrcEscrowCreated`), rather than trusting arbitrary caller-supplied fee data.

### Proof of Concept
1. Attacker (any unprivileged address) observes/derives a plausible `hashlock`, `maker`, `token`, `amount`, `taker`, and `timelocks` for a target swap (or crafts their own).
2. Attacker calls `createDstEscrow(dstImmutables, srcCancellationTimestamp)` with `dstImmutables.parameters = abi.encode(protocolFeeAmount = immutables.amount, integratorFeeAmount = 0, protocolFeeRecipient = attacker, integratorFeeRecipient = attacker)`, funding it with the required `amount + safetyDeposit`.
3. On `withdraw`, `EscrowDst._withdraw` (contracts/EscrowDst.sol:84-93) sends `protocolFeeAmount` (= full `amount`) to the attacker-controlled `protocolFeeRecipient`, leaving `amount - protocolFeeAmount = 0` for the maker.
4. Alternatively, setting `protocolFeeAmount + integratorFeeAmount > immutables.amount` makes line 92's subtraction underflow and revert, permanently blocking withdrawal until cancellation. [2](#0-1) [3](#0-2)

```text
    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
```

```text
    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }
```
