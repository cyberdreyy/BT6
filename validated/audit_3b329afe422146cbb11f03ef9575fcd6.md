### Title
Late block-validation OK response overrides an already GloballyRejected block's `valid` flag and re-triggers pre-commit broadcast - (File: stacks-signer/src/v0/signer.rs, `handle_block_validate_ok`)

### Summary
`handle_block_validate_ok()` fails to distinguish "reached consensus by acceptance/being locally accepted" from "reached consensus by global rejection" when a `mark_pre_committed()` call fails. Because `has_reached_consensus()` is true for *both* `GloballyAccepted` and `GloballyRejected`, a late/stale `Ok` validation response for a block that this signer has already recorded as `GloballyRejected` will still flip `valid = Some(true)` on the in-memory `BlockInfo`, persist it to `signerdb`, broadcast a `BlockPreCommit` for it, and feed it back into `handle_block_pre_commit` — all despite the block being terminally rejected.

### Finding Description
In `handle_block_validate_ok` [1](#0-0) :

```rust
if let Err(e) = block_info.mark_pre_committed() {
    if !block_info.has_reached_consensus()
        && block_info.state != BlockState::LocallyAccepted
    {
        warn!("{self}: Failed to mark block as approved: {e:?}",);
        return;
    }
}
self.signer_db.insert_block(&block_info)...;
self.send_block_pre_commit(signer_signature_hash.clone());
let address = self.stacks_address.clone();
self.handle_block_pre_commit(stacks_client, sortition_state, &address, signer_signature_hash);
```

`BlockInfo::mark_pre_committed()` [2](#0-1)  unconditionally mutates `self.valid = Some(true)` and stamps `approved_time` **before** attempting the state transition `move_to(PreCommitted)`. If the transition fails (e.g. because the block's state is already terminal), the function returns `Err`, but the `valid`/`approved_time` mutations on the struct are not rolled back — Rust has no such rollback semantics here.

The guard around this failure only re-returns (aborts) when `!has_reached_consensus() && state != LocallyAccepted`. `has_reached_consensus()` [3](#0-2)  is `true` for **both** `GloballyAccepted` and `GloballyRejected`. The inline comment only anticipates the accepted case ("The block may have reached enough signatures before we validated the block"), but the boolean condition also silently lets the `GloballyRejected` case fall through to the same "continue anyway" path used for `GloballyAccepted`/`LocallyAccepted`.

As a result, when a stale/delayed `BlockValidateOk` for a block arrives *after* this signer already processed enough peer rejections to call `mark_globally_rejected()` (via `store_and_process_block_rejection` [4](#0-3) ), the code:
1. sets `valid = Some(true)` on the `BlockInfo` whose `state` is still `GloballyRejected`,
2. persists this inconsistent record (`state = GloballyRejected`, `valid = true`) to signerdb,
3. calls `send_block_pre_commit(...)`, broadcasting a `BlockPreCommit` StackerDB message for a block this signer's own state machine has terminally rejected,
4. immediately re-processes that pre-commit locally via `handle_block_pre_commit`, whose gating check `if !block_info.valid.unwrap_or(false)` [5](#0-4)  now passes because `valid` was just forced to `true`, letting this now-"valid" globally-rejected block continue toward the pre-commit-weight tally and (if the pre-commit/reorg/conflict checks downstream pass) the signature path.

This mirrors the report's bug class exactly: an aggregate/derived field (`valid`) is updated as a side effect of a call whose "real" state transition (`move_to`) is not completed/rolled back atomically, and the resulting inconsistent intermediate state (rejected block marked `valid=true`) is then acted upon — here, broadcast to peers — rather than discarded.

### Impact Explanation
This is reachable by a single miner (via delaying/racing block proposals) plus normal signer gossip, and requires no majority of signers or key compromise — only ordinary asynchronous timing between the stacks-node's `/v3/block_proposal` validation response and the rest of the signer set's rejection gossip, both of which a miner can influence by proposing conflicting/competing blocks or by causing validation latency. The consequence is a signer emitting a `BlockPreCommit` for a block it has already recorded, in its own signerdb, as `GloballyRejected`. This is exactly the class of equality break called out in scope: a signer signing/pre-committing to an invalid or non-canonical/conflicting block. In the worst case, propagated across several signers experiencing similar validation-latency races, this could contaminate the pre-commit weight tally for a block the network has already terminally rejected, undermining the guarantee that `GloballyRejected` is truly terminal against being re-signed.

### Likelihood Explanation
Requires only ordinary timing: a `BlockValidateOk` response returning to a signer after that signer (or the network) has already reached `GloballyRejected` for the same block. Given that validation is asynchronous (submitted to the node and awaited), and block rejection can complete quickly across a strong majority of signers while one signer's own validation is still pending or delayed (network jitter, node load, or a miner intentionally proposing many competing blocks to induce validation queuing), this is a plausible, non-majority-controlled race. Likelihood is Medium: no adversarial signer collusion is required, but it does need a validation response ordered oddly relative to consensus-reaching gossip, which is intermittent by nature rather than always reproducible on demand.

### Recommendation
In `handle_block_validate_ok`, split the fallback condition so that a `GloballyRejected` state is never treated as "safe to continue": only continue past the `mark_pre_committed()` failure when the state is `GloballyAccepted` or `LocallyAccepted` (i.e., explicitly exclude `GloballyRejected`), and unconditionally `return` (without persisting the mutated `valid`/`approved_time` fields, or after reloading a fresh, unmutated copy of the terminal state) when `state == BlockState::GloballyRejected`. Additionally, make `BlockInfo::mark_pre_committed()` (and similarly `mark_locally_accepted`) not mutate `valid`/timestamps before `move_to` succeeds, so a failed transition leaves the struct byte-for-byte unchanged (validate-then-mutate rather than mutate-then-validate), removing the root cause of the observable inconsistent intermediate state.

### Proof of Concept
Conceptual sequence (matches existing test harness patterns such as those in `stacks-signer/src/v0/tests.rs`, e.g. `re_propose_b_after` scenarios that already exercise "validation returns after another decision was made" races [6](#0-5) ):

1. Miner proposes block `B`. Signer `S` submits it for node validation (`submit_block_for_validation`), and validation is slow/delayed for `S`.
2. Other signers in the set reject `B` (invalid transaction, stale conflict, etc.) fast enough that `S` receives their `BlockResponse::Rejected` messages and, via `handle_block_rejection` → `store_and_process_block_rejection`, crosses the rejection weight threshold and calls `block_info.mark_globally_rejected()`, persisting `state = GloballyRejected` for `B` in `S`'s signerdb [4](#0-3) .
3. `S`'s delayed `BlockValidateOk` for `B` finally arrives. `handle_block_validate_ok` loads `block_info` for `B` (state `GloballyRejected`), calls `block_info.mark_pre_committed()`, which sets `valid = Some(true)` then fails `move_to(PreCommitted)` because `GloballyRejected → PreCommitted` is not an allowed transition per `check_state` [7](#0-6) .
4. The guard `!block_info.has_reached_consensus() && state != LocallyAccepted` evaluates to `false` (since `has_reached_consensus()` is `true` for `GloballyRejected`), so execution does **not** return early.
5. `S` calls `insert_block` (persisting `valid = true` alongside `state = GloballyRejected`), then `send_block_pre_commit(B)` — broadcasting a `BlockPreCommit` for `B` over StackerDB — and finally `handle_block_pre_commit` locally, which now passes its `valid` gate check because `valid` was force-set to `true` in step 3.

I was not able to fully trace whether `block_lookup_by_reward_cycle` (used inside `handle_block_pre_commit`) applies any additional filtering that would suppress processing of blocks already in a terminal state before this pre-commit is acted upon further — I did not locate and read that function's implementation before the iteration budget was exhausted, so downstream mitigation (if any) inside `handle_block_pre_commit`/`block_lookup_by_reward_cycle` remains unverified. The inconsistency itself (persisting `valid=true` on a `GloballyRejected` `BlockInfo`, and unconditionally broadcasting a `BlockPreCommit` for it) is confirmed directly from the cited code.

    fn check_state(&self, state: BlockState) -> bool {
        let prev_state = &self.state;
        if *prev_state == state {
            return true;
        }
        match state {
            BlockState::Unprocessed => false,
            BlockState::LocallyAccepted | BlockState::LocallyRejected => !matches!(
                prev_state,
                BlockState::GloballyRejected | BlockState::GloballyAccepted

            BlockState::GloballyAccepted => !matches!(prev_state, BlockState::GloballyRejected),
            BlockState::GloballyRejected => !matches!(prev_state, BlockState::GloballyAccepted),
            BlockState::PreCommitted => matches!(prev_state, BlockState::Unprocessed),
        }
    }
