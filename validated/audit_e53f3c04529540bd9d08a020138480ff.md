### Title
`getLargestAccounts` cache keyed only by filter, not commitment — returns stale/wrong-slot balances across commitment levels - ([File: rpc/src/rpc.rs])

### Summary
`JsonRpcRequestProcessor::get_largest_accounts` caches its result in `LargestAccountsCache` keyed solely on `RpcLargestAccountsFilter` (`Circulating`/`NonCirculating`/`None`), while completely ignoring the `commitment` the caller requested. A subsequent unprivileged `getLargestAccounts` call using a different (stricter or looser) commitment level than the one that populated the cache will receive the previous commitment's stale slot/balances instead of data computed against the bank matching the requested commitment.

### Finding Description
`get_largest_accounts` in [1](#0-0)  first resolves `bank = self.bank(config.commitment)` for the requested commitment, but then checks `self.get_cached_largest_accounts(&config.filter)` — a lookup that only depends on `filter`, not on `commitment`. If a cache hit occurs, the response is returned with `RpcResponseContext::new(slot)` using the **cached** slot/accounts, discarding the just-resolved `bank` entirely.

The cache itself, `LargestAccountsCache`/`get_largest_accounts`/`set_largest_accounts` in [2](#0-1) , stores/retrieves entries by `filter` only and validates freshness purely by wall-clock `duration`, with no consideration of which commitment level (processed/confirmed/finalized) produced the cached snapshot: [3](#0-2) .

`set_cached_largest_accounts` is called with `bank.slot()` after computing the result for whichever commitment happened to be first requested: [4](#0-3) .

Sequence:
1. Client A calls `getLargestAccounts` with `commitment: "processed"`. Cache miss; result computed from the processed bank and cached under `filter` key with the processed bank's slot.
2. Within the cache TTL window, Client B calls `getLargestAccounts` with the same `filter` but `commitment: "finalized"`. `self.bank(config.commitment)` resolves the finalized bank correctly, but `get_cached_largest_accounts` returns the stale processed-commitment entry, and that stale `(slot, accounts)` is returned as if it reflected the finalized bank.

This is a genuine cross-commitment cache-key collision bug: an unprivileged RPC caller receives wrong-slot/wrong-fork account balance data that does not correspond to the commitment level they explicitly requested, directly analogous to the external report's root cause — a balance/state value not being kept in sync with the operation/context that should have invalidated or scoped it (vault balance not updated after `withdrawReserves()`, leading to stale value used in subsequent exchange-rate calculations).

### Impact Explanation
This meets the "wrong-slot/fork/account data returned" acceptance criterion for a single unprivileged RPC call (`getLargestAccounts`), reachable by any RPC client with no special privileges. It can mislead consumers (block explorers, monitoring, wallets) computing supply/whale-balance information into believing finalized-commitment data is being served when it is actually a lower/higher commitment snapshot (or vice versa), or serving data from a slot inconsistent with the `context.slot` semantics callers rely on for consistency checks.

### Likelihood Explanation
High likelihood of triggering under normal usage: `getLargestAccounts` is a public, unauthenticated JSON-RPC method; any two callers (or the same caller varying commitment, e.g. UI polling with `processed` then reconciling with `finalized`) hitting the endpoint within the cache TTL for the same/no filter will observe this cross-contamination. No special timing beyond issuing two calls with different commitments inside the cache window is needed.

### Recommendation
Include `commitment` (or the resolved bank's commitment/slot) as part of the cache key in `LargestAccountsCache`, e.g. key on `(filter, commitment)` instead of `filter` alone, so that `get_cached_largest_accounts`/`set_cached_largest_accounts` never returns a cached entry computed for a different commitment level than the one requested.

### Proof of Concept
1. Configure a validator RPC node with an active `LargestAccountsCache` TTL window (`duration` > 0).
2. Send `getLargestAccounts` with `{"commitment":"processed"}` — observe cache populated with the processed bank's slot/accounts.
3. Immediately (within TTL) send `getLargestAccounts` with `{"commitment":"finalized"}` and the same/absent `filter`.
4. Observe the response's `context.slot` and account balances match step 2's processed-commitment snapshot rather than reflecting the finalized bank resolved in `get_largest_accounts` at [5](#0-4) , confirming stale/incorrect-commitment data is returned.

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }

    pub(crate) fn set_largest_accounts(
        &mut self,
        filter: &Option<RpcLargestAccountsFilter>,
        slot: u64,
        accounts: &[RpcAccountBalance],
    ) {
        self.cache.insert(
            filter.clone(),
            LargestAccountsCacheValue {
                accounts: accounts.to_owned(),
                slot,
                cached_time: SystemTime::now(),
            },
        );
    }
