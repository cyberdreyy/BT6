### Title
`ComputeBudgetInstructionDetails::try_from` truncates instruction index via `i as u8`, causing `DuplicateInstruction` errors to reference an aliased index rather than the true offending instruction - ([File: compute-budget-instruction/src/compute_budget_instruction_details.rs])

### Summary
`ComputeBudgetInstructionDetails::try_from` enumerates a transaction's instructions with a `usize` counter and truncates it to `u8` before calling `process_instruction`, so an instruction at position 256 (or any position ≡ 0 mod 256) is reported as index 0. If a `SetComputeUnitLimit` (or any other compute-budget instruction) is duplicated between index 0 and index 256, the returned `TransactionError::DuplicateInstruction` cites the wrong, aliased index.

### Finding Description
`try_from` iterates instructions with `.enumerate()` (yielding a `usize` index `i`) and calls `compute_budget_instruction_details.process_instruction(i as u8, &instruction)` [1](#0-0) . `process_instruction` stores/consults `requested_compute_unit_limit: Option<(u8, u32)>` and, on a second `SetComputeUnitLimit`, returns `TransactionError::DuplicateInstruction(index)` using the truncated `index` argument [2](#0-1) .

Because `i as u8` wraps modulo 256, an attacker who crafts a message with a `ComputeBudgetInstruction::SetComputeUnitLimit` at instruction index 0 and a second one at instruction index 256 (with 255 filler/no-op instructions in between, e.g. instructions targeting an arbitrary non-compute-budget program id) causes:
- Instruction 0: `requested_compute_unit_limit` set to `Some((0, value))`.
- Instructions 1–255: classified as `num_non_compute_budget_instructions` (no validation of program existence occurs at this stage) [3](#0-2) .
- Instruction 256: `i as u8` truncates to 0, so `process_instruction(0, ...)` is called; since `requested_compute_unit_limit.is_some()` is true, it returns `TransactionError::DuplicateInstruction(0)` — not `DuplicateInstruction(256)`.

This is reachable purely through message construction: `try_from` is invoked from `process_compute_budget_instructions` [4](#0-3)  and from `VersionedTransactionConfiguration::try_from_legacy_and_v0_instructions` [5](#0-4) , both of which are part of transaction sanitization performed on client-submitted transactions (e.g. via `sendTransaction`/`simulateTransaction`), before any execution. No existing guard limits the number of instructions to ≤256 in this code path, and no code corrects for the truncation; the wraparound is a genuine correctness defect, not just a cosmetic display quirk, because the returned `TransactionError` is part of the RPC response consumed by clients/wallets for diagnostics and retry logic.

Feasibility of fitting 257+ instructions within the ~1232-byte packet size limit: a legacy/v0 message can reuse a single dummy program id and zero-account, zero-data instructions to keep each filler instruction to ~3 bytes (1-byte program-id index + compact-u16 0 accounts + compact-u16 0 data length), while the two real `SetComputeUnitLimit` instructions require a handful of extra bytes each. This keeps the whole 257+-instruction message comfortably under the packet limit alongside compact account-key table, header, blockhash, and one signature — so this is achievable by a single unprivileged client crafting one transaction, satisfying the "single call" constraint.

### Impact Explanation
This is a correctness/error-attribution bug: an unprivileged client's single `sendTransaction`/`simulateTransaction` call can receive a `TransactionError::DuplicateInstruction` citing an incorrect instruction index (0 instead of 256), violating the invariant that returned error data faithfully represents the actual offending instruction. It does not crash the validator or corrupt consensus state; it is scoped to misleading/incorrect error reporting to the client for a single benign, non-malicious-looking transaction shape, matching a "decoder/reporting misattribution" class of bug rather than a DoS or consensus issue.

### Likelihood Explanation
The bug triggers deterministically whenever a legacy/v0 message contains ≥257 instructions with a compute-budget duplicate exactly 256 apart (or any multiple-of-256 apart) in position. Building such a transaction requires only client-side message construction — no special privileges, no validator/leader control, and only one JSON-RPC call. The main constraint is fitting within the packet size limit, which appears achievable using minimal filler instructions as outlined above.

### Recommendation
Change `try_from`'s instruction index bookkeeping to avoid lossy truncation: either bound-check the total instruction count against `u8::MAX` before truncating (returning a sanitize failure for messages with too many instructions, if such a limit is intended elsewhere), or change `requested_compute_unit_limit`/`requested_compute_unit_price`/`requested_heap_size`/`requested_loaded_accounts_data_size_limit` and `process_instruction`'s index parameter to use a wider integer type (e.g., `u16` or `usize`) consistently with how `TransactionError::DuplicateInstruction`/`InstructionError` indices are represented downstream, ensuring the reported index always matches the true instruction position.

### Proof of Concept
Integration test sketch (extends the existing test module in `compute-budget-instruction/src/compute_budget_instruction_details.rs`):
```rust
#[test]
fn test_try_from_duplicate_index_truncation() {
    let dummy_program = Pubkey::new_unique();
    let mut instructions = vec![ComputeBudgetInstruction::set_compute_unit_limit(1_000)];
    // 255 filler instructions to push the next compute-budget ix to index 256
    for _ in 0..255 {
        instructions.push(Instruction::new_with_bincode(dummy_program, &(), vec![]));
    }
    instructions.push(ComputeBudgetInstruction::set_compute_unit_limit(2_000));

    let tx = build_sanitized_transaction(&instructions);
    let result = ComputeBudgetInstructionDetails::try_from(
        SVMStaticMessage::program_instructions_iter(&tx),
    );

    // Expected (correct) behavior: error should reference the true duplicate at index 256.
    // Actual (buggy) behavior observed: TransactionError::DuplicateInstruction(0)
    // because `256 as u8 == 0`.
    assert_eq!(result, Err(TransactionError::DuplicateInstruction(256_u8 /* fails to compile / truncates */)));
}
```
Note: since `TransactionError::DuplicateInstruction` takes a `u8`, expressing the "correct" index 256 requires widening the type per the recommendation above; the PoC's practical assertion today is `assert_eq!(result, Err(TransactionError::DuplicateInstruction(0)))`, demonstrating the misattributed index instead of the true index 256, which is precisely the bug being proven.

    fn process_instruction(&mut self, index: u8, instruction: &SVMInstruction) -> Result<()> {
        let invalid_instruction_data_error =
            TransactionError::InstructionError(index, InstructionError::InvalidInstructionData);
        let duplicate_instruction_error = TransactionError::DuplicateInstruction(index);

        match try_from_slice_unchecked(instruction.data) {
            Ok(ComputeBudgetInstruction::RequestHeapFrame(bytes)) => {
                if self.requested_heap_size.is_some() {
                    return Err(duplicate_instruction_error);
                }
                self.requested_heap_size = Some((index, bytes));
