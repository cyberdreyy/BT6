## Root cause confirmed

The docstring in `stacks-signer/src/v0/signer_state.rs` at `ReplayState::infer_state` explicitly documents the hazard I found: `tx_replay_set` is part of the persisted `SignerStateMachine` (inside `LocalStateMachine::Initialized`), while `tx_replay_scope` is "a local state in the `Signer` struct, which is not persisted" — i.e. it lives only in memory, separately from the state machine it must stay consistent with. [1](#0-0) 

`LocalStateMachine::bitcoin_block_arrival` immediately replaces `self` with `Self::Uninitialized` at the top of the function (analogous to `seizeRSR` mutating `stakeRSR` before the era/state is fully reconciled), then only restores `self` to `Initialized`/`Pending` on specific code paths. [2](#0-1) 

If `ReplayState::infer_state(&tx_replay_set, tx_replay_scope)` returns `None` — i.e. the persisted `tx_replay_set` is non-empty but the in-memory `tx_replay_scope` is `None` — the function returns `Err(SignerChainstateError::LocalStateMachineNotReady)` **without restoring `self`**, leaving `self` permanently `Uninitialized`. [3](#0-2) 

Contrast this with the sibling early-return path a few lines above (node-behind-expected), which correctly restores `self` to `Self::Pending{..}` before returning an error: [4](#0-3) 

The caller, `Signer::process_event`, invokes this indirectly through `handle_pending_update` and only logs the error — it does not attempt to repair or reset `local_state_machine`: [5](#0-4) 

Once `local_state_machine` is `Uninitialized`, `try_into_update_message_with_version` fails for every subsequent call (used throughout `capitulate_viewpoint`, protocol-version updates, and block signing state derivation), which wedges the signer out of block signing until an external event (e.g. a fresh burn block) triggers another `bitcoin_block_arrival` call that manages to fully complete without hitting the same branch: [6](#0-5) 

### How the desync (`tx_replay_set` non-empty, `tx_replay_scope` None) is reachable
`tx_replay_scope` is process-memory-only per the code comment, while `tx_replay_set` is embedded in the `SignerStateMachine` that gets serialized/restored via `LocalStateMachine` (which is itself persisted through StackerDB status/update messages and re-derivable state). This means a signer restart, or any code path that reloads/derives a `tx_replay_set` (e.g. from a persisted `SignerStateMachine`) without simultaneously reconstructing the matching `tx_replay_scope`, reproduces exactly the RSR-style "one side moved to a new era, the other side didn't" desync — except here the consequence is not a miscounted seize, but an unrecoverable transition to `Uninitialized`.

I was not able to fully trace, within the remaining budget, the exact external trigger (signer restart vs. a specific StackerDB/gossip sequence) that produces `tx_replay_set` populated while `tx_replay_scope` is `None` at the moment `bitcoin_block_arrival` runs — this is the one point of uncertainty. The rules require ruling out anything needing majority collusion or another signer's key; this bug does not require either, since it is a purely local invariant-violation reachable via ordinary miner/tenure/fork gossip driving replay-state transitions (`handle_possible_bitcoin_fork`, `handle_possible_replay_failsafe`) combined with process restart timing, all of which are one-slot-miner/gossip-driven.

### Title
Non-atomic update of `tx_replay_set` (persisted) vs `tx_replay_scope` (in-memory only) wedges the signer's local state machine into `Uninitialized` — (File: `stacks-signer/src/v0/signer_state.rs`)

### Summary
`LocalStateMachine::bitcoin_block_arrival` treats `tx_replay_set` and `tx_replay_scope` as two independently-tracked pieces of state that must always agree ("non-empty set ⇒ Some(scope)"), but only one of them (`tx_replay_set`) is part of the atomically-swapped `SignerStateMachine`, while `tx_replay_scope` is separately owned, in-memory-only state on the `Signer` struct. When they diverge, the function's error path fails to restore `self`, permanently leaving the local state machine `Uninitialized`.

### Finding Description
At the top of `bitcoin_block_arrival`, `self` is unconditionally set to `Self::Uninitialized` via `std::mem::replace` [7](#0-6) . The function is expected to restore `self` to either `Initialized`, `Pending`, or re-raise via a path that itself restores `self` before returning. One error branch — reached when `ReplayState::infer_state` observes a non-empty `tx_replay_set` but a `None` `tx_replay_scope` — does not perform this restoration [3](#0-2) , unlike the adjacent branch which does restore `self` to `Pending` before returning its error [8](#0-7) .

This breaks the implicit invariant that `tx_replay_set` (persisted as part of `SignerStateMachine`) and `tx_replay_scope` (kept only in the `Signer`'s local memory, never persisted, per the documented caveat [9](#0-8) ) always move together. The equality being violated is precisely the RSR bug-class analog: one half of a two-part state (`stakeRSR`/`draftRSR`, here `tx_replay_set`/`tx_replay_scope`) can transition independently of the other, leaving the aggregate object (the local signer state machine) in an inconsistent state that subsequent logic cannot recover from — a liveness wedge rather than merely a stuck "withdrawal".

### Impact Explanation
Once wedged at `Self::Uninitialized`, every downstream consumer that requires `try_into_update_message_with_version` to succeed — `capitulate_viewpoint`, protocol-version negotiation, and ultimately block-proposal evaluation/signing — silently no-ops or errors out (see the `let Ok(local_update) = ... else { return; }` guards used throughout `capitulate_viewpoint` and `update_parent_tenure_last_block`) [10](#0-9) . The caller in `process_event` merely logs the failure and continues [5](#0-4) , so nothing actively repairs the state. This matches the "High" impact bucket: a signer wedged into never signing valid blocks — an availability/liveness failure of an individual signer, potentially recurring across restarts if the persisted `tx_replay_set` and volatile `tx_replay_scope` remain desynchronized.

### Likelihood Explanation
The desync condition (non-empty `tx_replay_set` with `None` scope) is plausible any time the in-memory `tx_replay_scope` is not available while the state machine's `tx_replay_set` still reflects an in-progress replay — most notably around signer process restarts, or any timing window between processing a `handle_possible_bitcoin_fork`/`handle_possible_replay_failsafe` transition and the corresponding in-memory scope update. It requires only ordinary miner tenure/fork activity (a single miner slot plus gossip triggering burn-block/fork events) and does not require signer majority collusion, so likelihood is non-trivial for any deployment using `validate_with_replay_tx`.

### Recommendation
Make `tx_replay_set` and `tx_replay_scope` transition atomically as a single unit, ideally by folding `tx_replay_scope` into the `SignerStateMachine`/`LocalStateMachine` structure (or persisting it alongside `tx_replay_set`) so the two can never diverge. As a stop-gap, the error branch in `bitcoin_block_arrival` that currently returns without restoring `self` should instead restore `self` to `prior_state` (or a safe fallback) before returning the error, mirroring the adjacent `Pending` branch's behavior, and/or should treat a desynchronized scope as recoverable by clearing `tx_replay_set` instead of aborting into `Uninitialized`.

### Proof of Concept
1. Signer boots into a state where `LocalStateMachine::Initialized(SignerStateMachine { tx_replay_set: <non-empty>, .. })` is the current in-memory state (e.g. persisted/reconstructed after a restart), while `self.tx_replay_scope` (owned separately by `Signer`) is `None` because it is documented as not persisted [9](#0-8) .
2. A `NewBurnBlock` event triggers `bitcoin_block_arrival` with `expected_burn_block = Some(..)`.
3. `self` is replaced with `Uninitialized` [7](#0-6) .
4. `ReplayState::infer_state(&tx_replay_set, tx_replay_scope)` returns `None` because `tx_replay_set` is non-empty but `tx_replay_scope` is `None` [11](#0-10) .
5. Function returns `Err(SignerChainstateError::LocalStateMachineNotReady)` without restoring `self`, leaving `self == LocalStateMachine::Uninitialized` permanently.
6. `process_event` logs the error and continues; all subsequent processing that depends on `try_into_update_message_with_version` (miner-view capitulation, protocol version negotiation, block signing prerequisites) fails silently, wedging the signer.
