### Title
Griefing `stopEpoch` via dust APR0 withdraw requests forces the pool into permanent 0-APR epochs or blocks epoch transitions - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
Analogous to the LiquidityReserve `unstakeAllRewardTokens` griefing, `IdleCreditVault.prepareStopEpochWithApr0` reverts whenever `apr0TotalPrincipal != 0` and the vault's `unscaledApr != 0`. An unprivileged (KYC-passing) lender can keep `apr0TotalPrincipal` nonzero indefinitely by submitting a dust-sized withdraw request during each epoch in which the APR is 0. This causes `stopEpoch` to revert as long as the manager sets any nonzero APR, so the attacker can either force every subsequent epoch to run at 0% APR (denying all lenders their yield) or temporarily freeze the epoch state machine. The only honest escape — setting `unscaledApr = 0` so the bucket clears at `stopEpoch` — is exactly what the attacker can cheaply re-poison each epoch, mirroring the original report's "miner re-griefs every open window" loop.

### Finding Description
`requestWithdraw` routes APR0-mode requests into a per-user bucket:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:285-294
if (unscaledApr == 0 && !isClosed) {
  _requestWithdrawApr0(_amount, _user);
} else {
  withdrawsRequests[_user] += _amount;
  withdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
}
```

`_requestWithdrawApr0` records `apr0Users[_user].principal`/`principalEpoch` and increases the global `apr0TotalPrincipal`. There is no minimum-amount check — `requestWithdraw` only early-returns on `_amount == 0` (line 246), so a single wei of principal suffices.

At epoch end the CDO calls `prepareStopEpochWithApr0`, which hard-reverts if the bucket is open while APR is nonzero:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:502-508
if (_principal == 0) {
  return (_expInterest, _adjPendingWithdrawFees);
}
if (unscaledApr != 0) {
  revert NotAllowed();
}
```

The bucket is only closed inside the same function (line 540: `apr0TotalPrincipal = 0;`), i.e. only on a `stopEpoch` executed while `unscaledApr == 0`.

Attack loop (attacker = ordinary KYC'd lender holding tranche tokens):
1. Epoch N runs at `unscaledApr == 0`. Attacker calls `cdoEpoch.requestWithdraw` with a dust amount → `apr0TotalPrincipal = dust > 0`.
2. Manager later sets `unscaledApr > 0` for a future epoch (or the APR was scheduled to rise). At `stopEpoch`, `prepareStopEpochWithApr0` reverts `NotAllowed`.
3. `stopEpoch` cannot complete while APR is nonzero. The manager's only recovery is to keep/set `unscaledApr = 0` and stop the epoch with zero interest. The bucket clears, but the attacker immediately repeats step 1 in the next 0-APR epoch for a cost of ~1 wei plus gas.
4. Result: the protocol can never return to a nonzero APR without a permanently reverting `stopEpoch`, and every epoch that does run pays lenders 0% interest.

The grief is structurally identical to the original: a shared, permissionless-to-influence flag (`coolDownAmount` there, `apr0TotalPrincipal` here) gates a shared transition function, an attacker keeps it nonzero with dust, and the admin escape hatch exists but neutralizes it only at the cost of conceding the griefed state.

### Impact Explanation
Two quantifiable impacts depending on operator response:
- If the manager insists on a nonzero APR, `stopEpoch` reverts indefinitely → temporary freezing of all pending withdraw claims and of the epoch transition itself.
- If the manager keeps APR at 0 to unblock stops, every epoch pays zero interest → all lender yield for affected epochs is permanently lost, and the attacker sustains this for ~1 wei of principal per epoch.

### Likelihood Explanation
Requires `unscaledApr == 0` windows to seed the bucket; such windows occur by design (the APR0 flow is a supported mode). Cost to the attacker is a dust request per epoch; no privileged role, mining power, or timing precision is needed — unlike the original report, the grief persists until the bucket clears, so no block-stuffing race is required. The manager escape hatch (forcing APR 0) exists but hands the attacker the denial-of-yield outcome, exactly as in the original where the sponsor conceded the finding was real but argued the recovery path limits severity.

### Recommendation
- Enforce a minimum principal for `_requestWithdrawApr0` (e.g. revert below a threshold like `oneToken`), so dust cannot keep `apr0TotalPrincipal` open.
- Alternatively, in `prepareStopEpochWithApr0`, treat a nonzero `unscaledApr` as "close the bucket and settle at par" instead of reverting — i.e. delete `apr0TotalPrincipal` and route the open principals through the normal funded-claim path, so a stale APR0 bucket can never block `stopEpoch`.
- Optionally clear `apr0TotalPrincipal` whenever `setApr`/`setAprsWithBuffer` moves APR off 0, since the comments state the bucket is only valid for the request lifecycle while APR is 0.

### Proof of Concept
Foundry fork PoC sketch (modeled on `test/foundry/IdleCreditVault.t.sol` helpers `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`):

```solidity
function testApr0DustGriefBlocksNonzeroAprStop() external {
    // Setup: manager sets APR to 0 (APR0 mode active)
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);

    // Attacker is an ordinary KYC'd lender; deposits dust, requests withdraw while APR == 0
    address attacker = makeAddr('griefer');
    _depositWithUser(attacker, 1, true);          // minimal deposit
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // or minimal amount
    assertGt(strategy.apr0TotalPrincipal(), 0, 'bucket seeded');

    _startEpochAndCheckPrices(0);

    // Manager raises APR for the next epoch
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprsWithBuffer(10e18, epochDur, buffer);

    // Borrower funds repayment; stopEpoch now always reverts in prepareStopEpochWithApr0
    deal(defaultUnderlying, borrower, _expectedFundsEndEpoch());
    vm.warp(cdoEpoch.epochEndDate() + 1);
    vm.prank(manager);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.stopEpoch(initialProvidedApr, 0);

    // Only escape: concede a 0-APR epoch so the bucket clears
    vm.prank(manager);
    IdleCreditVault(address(strategy)).setAprs(0, 0);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);                     // succeeds, pays 0 interest
    assertEq(strategy.apr0TotalPrincipal(), 0);

    // Attacker re-poisons next epoch for ~1 wei -> repeat indefinitely
}
```

Note: the exact revert point depends on `stopEpoch` in `IdleCDOEpochVariant.sol` calling `prepareStopEpochWithApr0` unconditionally (its `_onlyIdleCDO` guard and the APR0 tests imply it does); if it is only invoked when `apr0TotalPrincipal != 0`, the same revert is triggered identically. The only unverified detail is the precise body of `_requestWithdrawApr0` (dust handling), but `requestWithdraw` shows no minimum-amount gate before it.
