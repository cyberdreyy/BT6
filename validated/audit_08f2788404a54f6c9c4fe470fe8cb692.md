### Title
Async redeem solve transfers to blacklisted receiver revert without fallback, freezing user funds until deadline - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`ProvisionerV2` protects refund paths from blacklist-related token transfer failures via `_transferWithFallback`, which retries a transfer to the original requester if the receiver-transfer fails [1](#0-0) . However, the successful "solve" paths for async redeems (`_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice`) transfer the redeemed token directly to `request.receiver` via a bare `token.safeTransfer`, with no fallback protection [2](#0-1) [3](#0-2) . If the redeem token is USDC and `request.receiver` becomes blacklisted, the solve reverts, mirroring the root cause of the referenced report (direct push-transfer to a potentially-blacklisted recipient with no pull-based fallback).

### Finding Description
When a solver calls `solveRequestsVault`, each queued redeem request is processed by `_solveRequestDirect`/`_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice`. For requests whose `deadline` has not yet passed, both functions burn the user's vault units via `IMultiDepositorVault.exit` and then push the underlying token straight to `request.receiver`: [2](#0-1) [3](#0-2) 

Compare this to the deadline-passed refund branch in the very same functions, which explicitly uses `_transferWithFallback` to fall back to the original requester if the receiver-transfer reverts: [4](#0-3) 

The pattern is identical to the report's root cause: an ordinary, permissionless transfer to a third party (here `request.receiver`, which can be set arbitrarily by the requester at request-creation time) that reverts if that address is blacklisted by the token (e.g., USDC), with no protocol-side pull/claim mechanism for the successful-solve branch.

### Impact Explanation
If `request.receiver` is blacklisted by the redeem token before the solver processes the request, the pre-deadline solve call reverts. The user's vault units remain locked in escrow (already transferred to the provisioner at request-creation time) and cannot be redeemed for tokens through this path. The freeze is temporary: once the request's `deadline` elapses, `refundRequest`/`cancelRequest` become available and return the *vault units* (not the underlying token) via the fallback-protected `_clearHashAndTransferRefund`, so principal is eventually recoverable in unit form once blacklist status changes or the receiver is corrected. This matches the "temporary freezing of user funds" Medium-severity impact category referenced in the prompt.

### Likelihood Explanation
Requires: (1) the vault's underlying redeem token supports blacklisting (e.g., USDC), and (2) `request.receiver` is or becomes blacklisted between request creation and solving. Both preconditions mirror the original report exactly and are realistic for USDC-denominated vaults, which is the deployed asset class ProvisionerV2 is designed to support.

### Recommendation
Route the pre-deadline "solved" token payout in `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` through the same `_transferWithFallback` helper already used by the refund branches, so a blacklisted receiver cannot block redemption; alternatively, credit the amount to an internal claimable balance for the receiver to pull later.

### Proof of Concept
On a local fork with a mainnet-fork-deployed vault using USDC as the redeem token:
1. Deploy `ProvisionerV2`/`MultiDepositorVault` per existing test harness, enable async redeem for USDC.
2. User A calls `requestRedeem` with `receiver = userB`, escrowing vault units.
3. Have USDC's blacklister blacklist `userB` (fork USDC has a real blacklist; use `cheats` to call the blacklister role, or fork state where `userB` is already blacklisted).
4. Call `solveRequestsVault` (or `solveRequestsDirect`) for that request before `deadline`.
5. Assert the transaction reverts (the `token.safeTransfer(request.receiver, ...)` call reverts due to USDC blacklist), leaving the request's units still escrowed and `asyncRequestHashes[redeemHash]` still `true`, i.e. the redeem cannot be solved until deadline/refund path is used.

    /// @notice Transfers amount to receiver and falls back to requester if receiver transfer fails
    /// @param token The ERC20 token being transferred
    /// @param requester The original requester address used as fallback receiver
    /// @param receiver The intended receiver from the request
    /// @param amount The amount of tokens to transfer
    function _transferWithFallback(IERC20 token, address requester, address receiver, uint256 amount) internal {
        // Interactions: transfer to receiver, fallback to requester on transfer failure
        if (receiver == requester || !token.trySafeTransfer(receiver, amount)) {
            token.safeTransfer(requester, amount);
        }
    }
