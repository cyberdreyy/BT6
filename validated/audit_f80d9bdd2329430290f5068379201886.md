### Title
Signer broadcasts a `BlockRejection` even when the local state transition to "locally rejected" fails - (File: `stacks-signer/src/v0/signer.rs`)

### Summary
In `stacks-signer/src/v0/signer.rs`, three response-handling paths (`handle_block_pre_commit`, `handle_block_validate_ok`, `handle_block_validate_reject`) call `block_info.mark_locally_rejected()` and, on `Err`, only *log* a warning conditionally (`if !block_info.has_reached_consensus()`) - the error is never used to prevent or alter the subsequent behavior. In every case, whether `mark_locally_rejected()` succeeds or fails, the code unconditionally proceeds to `self.signer_db.insert_block(&block_info)`, `self.handle_block_rejection(...)`, and `self.send_block_response(&block_info.block, block_rejection.into())`, broadcasting a signed `BlockRejection` message.

### Finding Description
This mirrors the audit's core bug class: a state-mutating call whose failure is not checked/`require`d, so the caller proceeds as if it had succeeded, producing an externally observable effect (in Maple's case an unrecoverable token transfer; here a signed, broadcast protocol message) that no longer matches the underlying state.

Concretely, at [1](#0-0)  (pre-commit re-check path):
```
if let Err(e) = block_info.mark_locally_rejected() {
    if !block_info.has_reached_consensus() {
        warn!("{self}: Failed to mark block as locally rejected: {e:?}");
    }
};
self.signer_db.insert_block(&block_info).unwrap_or_else(...);
self.handle_block_rejection(&block_rejection, sortition_state);
self.send_block_response(&block_info.block, block_rejection.into());
```
The same pattern recurs in `handle_block_validate_ok` ( [2](#0-1) ) and `handle_block_validate_reject` ( [3](#0-2) ).

Per `docs/signer-flows.md`, `BlockInfo::check_state` is a state machine where "each global state is unreachable from the other" and local states are only reachable "from anything not yet global" ( [4](#0-3) ). This means `mark_locally_rejected()` is *expected* to fail specifically when `block_info` has already reached a terminal global state (`GloballyAccepted`/`GloballyRejected`) — i.e., precisely the case gated by `has_reached_consensus()`. In that branch the code deliberately suppresses the warning (treating the failure as "expected/benign"), yet it still executes `send_block_response(...)`, broadcasting a freshly-signed `BlockRejection` for a block whose `block_info.state`/`valid` fields were *not* actually mutated to rejected (the mutation was rejected by the internal invariant check). The signed message and the signer's own recorded DB state diverge: the DB still reflects an already-globally-accepted (canonical) block, while the network sees this signer emit a signed rejection for that same block hash.

This breaks the "signed vs validated" equality the whole flow doc's design goals are built around ("A signature is never given away cheaply... every red path is a broadcast verdict others can count" — docs/signer-flows.md lines 54-56): here a broadcast rejection verdict is emitted precisely in the one case where the local record was *not* actually changed to reflect it, because the attempted state mutation silently failed and was never checked.

### Impact Explanation
A signer emitting a validly signed `BlockRejection` for a block it has already (or will have) recorded as globally accepted creates a durable, verifiable, cryptographically signed artifact that contradicts the signer's own recorded state. This is exactly the class of bug the rules flag as Critical-adjacent ("a rejection recounted as an accept" / conflicting signed responses about the same block) because:
- Rejection weight tallies performed by other signers and by the node's `stackerdb_listener.rs` (`total_weight_rejected`, see [5](#0-4) ) treat every signed rejection as authoritative evidence from that signer, without cross-checking it against the signer's actual recorded terminal state.
- If this fires before the block is fully broadcast/observed as canonical elsewhere (e.g., other signers still forming their local view), the spurious rejection could contribute to driving the 30%-rejection livelock/global-rejection threshold (`docs/signer-flows.md` line 44) for a block that this very signer's own database considers already accepted — a direct conflicting-response condition.

### Likelihood Explanation
This requires only a single miner (crafting or re-broadcasting a proposal) plus ordinary StackerDB gossip timing (a validation response or pre-commit tally arriving after the signer's own consensus state for that block hash has already advanced) — well within a one-slot-miner-plus-gossip threat model, and does not require a majority of signers or another signer's key.

### Recommendation
Treat `mark_locally_rejected()` (and its sibling `mark_*` calls guarded the same way) as authoritative: if the state transition fails because the block has already reached a terminal/global state, do not broadcast a new `BlockRejection` — the response must be derived from and consistent with the actually-persisted `block_info.state`, not fabricated independently of it. At minimum, gate `send_block_response` on the success of the corresponding `mark_*` call, mirroring the "always `require`" fix recommended for `ERC20Helper.transfer`.

### Proof of Concept
Conceptual trigger (exact reproduction would require a Devin session with test harness access, which is outside this analysis's scope):
1. Miner proposes block `B`; signer processes it and independently records `B` as `GloballyAccepted` via an early flood of `BlockResponse::Accepted` gossip messages reaching threshold before this signer's own validation round-trips complete.
2. A delayed `BlockPreCommit` or `BlockValidateOk`/`BlockValidateReject` for `B` then arrives and is processed by `handle_block_pre_commit` / `handle_block_validate_ok` / `handle_block_validate_reject`.
3. `check_block_against_signer_db_state` (or the reject-response path) determines `B` "no longer passes checks," and `block_info.mark_locally_rejected()` is called — which fails because `B.state == GloballyAccepted` (terminal state, per `BlockInfo::check_state`'s invariant that global states are unreachable from each other/local).
4. Because `has_reached_consensus()` is true, the `Err` is silently swallowed (no warning, no abort), and the code unconditionally calls `send_block_response(&block_info.block, block_rejection.into())`, broadcasting a signed `BlockRejection` for `B` even though the signer's own `signer_db` still (correctly) records `B` as `GloballyAccepted`.

I was not able to fully inspect the exact internals of `mark_locally_rejected`/`check_state`/`has_reached_consensus` (the tool budget was exhausted before retrieving `signerdb.rs`'s function bodies directly), so the precise state-machine transition table is inferred from `docs/signer-flows.md`'s description rather than confirmed line-by-line in `signerdb.rs`. A Devin session with full repo access should verify `BlockInfo::check_state`'s transition table directly against `signerdb.rs` to confirm which prior states cause `mark_locally_rejected()` to return `Err`.
