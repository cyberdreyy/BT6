### Title
Post-default instant-withdraw receipts are indexed under `defaultRecoveryEpoch` and paid from `defaultRecoveryReserve` without ever joining the recovery claim basis - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The kernel bug is a lifecycle/use-after-free flaw: after an object is torn down, a stale path still dereferences it. The direct analog in `IdleCreditVault` is that after `finalizeDefaultRecovery` crystallizes the recovery accounting (`defaultRecoveryEpoch`, `defaultRecoveryPrice`, `defaultRecoveryReserve`), `requestInstantWithdraw` still appends new receipts under the *unchanged* `epochNumber` — which equals `defaultRecoveryEpoch`. `claimInstantWithdrawRequest` then treats those brand-new receipts as defaulted-epoch claims and pays them from `defaultRecoveryReserve`, even though `defaultPendingClaimBasis` never counted them. Recovery funds earmarked for pre-default claimants are drained by receipts created after finalization.

### Finding Description
`finalizeDefaultRecovery` computes `totalBasis = activeBasis + defaultPendingClaimBasis()` and sets `defaultRecoveryReserve`, `defaultRecoveryPrice`, `defaultRecoveryEpoch = epochNumber`, and `defaultInstantWithdrawsFinalized` [1](#0-0) . After default, `epochNumber` never advances (the pool is dead), so `epochNumber == defaultRecoveryEpoch` permanently.

`requestInstantWithdraw` has no `defaultRecoveryFinalized` branch (unlike `requestWithdraw`, which routes post-default requests into `postDefaultRequests` at lines 247–258). It unconditionally records the new receipt at `instantWithdrawsRequestsByEpoch[_user][epochNumber]` — i.e., under `defaultRecoveryEpoch` [2](#0-1) .

`claimInstantWithdrawRequest` then calls `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — now nonzero because of the *new* request — burns it, decrements `instantWithdrawClaimsByEpoch[defaultEpoch]` and `pendingInstantWithdraws` (saturating), and pays `claimBasis * defaultRecoveryPrice / 1e18` via `_transferDefaultRecovery` [3](#0-2) [4](#0-3) .

The reserve was sized as `reserveAmount` against `totalBasis` at finalization; post-default instant receipts inflate claims against that fixed reserve without adding to the basis — exactly the "access freed state after teardown" shape of the mlx5e bug.

### Impact Explanation
Any tranche-token holder can, after default finalization, request an instant withdraw and immediately claim up to `amount * defaultRecoveryPrice` from `defaultRecoveryReserve`. Repeating (or sandwiching) drains the reserve, so legitimate defaulted-epoch withdraw and instant claimants find the reserve depleted — direct theft/insolvency of recovery funds, quantified as `min(attacker request, reserve) * defaultRecoveryPrice / 1e18` per call. If `defaultInstantWithdrawsFinalized` was false (instant bucket fully funded pre-default), the request instead falls through to `_transferFundedClaim`, which post-default can only be backed by the same reserve-held underlying — same drain through the par path.

### Likelihood Explanation
Reachability requires the CDO to still route `requestInstantWithdraw`/`claimInstantWithdrawRequest` post-default. `IdleCreditVault.requestInstantWithdraw` itself has no default gate and `_onlyIdleCDO` is the only check [5](#0-4) , while `requestWithdraw` was explicitly given a post-default path — indicating the authors expected withdraw flows to remain callable after default, but only patched the normal path. Uncertainty: whether `IdleCDOEpochVariant.getInstantWithdrawFunds`/instant-withdraw timing gating (which I could not fully verify within the available iterations) blocks instant requests once `defaulted()` is set; if the instant window is closed post-default, the attack is unreachable. A Foundry PoC must confirm that call path.

### Recommendation
Mirror the `requestWithdraw` fix: in `requestInstantWithdraw`, either revert when `defaultRecoveryFinalized` is set, or route the receipt into `postDefaultRequests`-style accounting (priced by `defaultRecoveryPrice`, funded separately, never recorded under `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`). Additionally, guard `claimInstantWithdrawRequest`/`_claimDefaultedInstantWithdrawRequest` so only receipts created *before* finalization are paid from `defaultRecoveryReserve` (e.g., snapshot the eligible per-user basis at finalization, or require `instantWithdrawsRequestsByEpoch` writes to use an epoch strictly greater than `defaultRecoveryEpoch`).

### Proof of Concept
```solidity
// Foundry fork test, post-default phase (fixed-APR, instant enabled)
// Pre: borrower defaulted; finalizeDefaultRecovery(recovered, src) done.
// defaultRecoveryEpoch == strategy.epochNumber(); reserve = R, price = P<1e18.

uint256 amountWei = 1_000e6;
// attacker is a normal AA/BB tranche holder (unprivileged)
uint256 mintedAA = idleCDO.depositAA(amountWei); // or held before default

// 1) Post-default instant withdraw request (no default branch in strategy)
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(mintedAA, attacker); // IdleCDO -> strategy.requestInstantWithdraw

// instantWithdrawsRequestsByEpoch[attacker][defaultRecoveryEpoch] == mintedAA
// but this basis was never counted in defaultPendingClaimBasis()

// 2) Claim: _claimDefaultedInstantWithdrawRequest pays from recovery reserve
uint256 reservePre = strategy.defaultRecoveryReserve();
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();

uint256 paid = underlying.balanceOf(attacker) - balPre;
assertEq(paid, mintedAA * strategy.defaultRecoveryPrice() / 1e18);
assertLt(strategy.defaultRecoveryReserve(), reservePre); // reserve drained by unaccounted claim

// 3) Legit defaulted-epoch claimant now underpaid/reverts on exhausted reserve
```

If the CDO's instant-withdraw gating rejects requests after `defaulted()`, the finding degrades to unreachable and should be downgraded; confirm step 1 on fork before final reporting.

    _onlyIdleCDO();

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();
    if (defaultRecoveryFinalized && defaultInstantWithdrawsFinalized) {
      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
