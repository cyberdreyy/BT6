### Title
Instant-withdraw receipts requested in a prior epoch escape default haircut clearing and are permanently frozen - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`requestInstantWithdraw` records receipt basis under `instantWithdrawsRequestsByEpoch[user][epochNumber]`, but `_claimDefaultedInstantWithdrawRequest` only clears basis stored under `defaultRecoveryEpoch`. When a default is finalized in an epoch later than the one in which an unfunded instant-withdraw request was recorded, the claim path skips the haircut clearing and falls through to `_transferFundedClaim`, which reverts against the isolated `defaultRecoveryReserve`. The user's recovery claim is permanently frozen.

### Finding Description
The Linux bug is an uninitialized `spi_transfer` struct — a structure used while one field was never written. The analog here is a *stale epoch tag* on the instant-receipt struct: the receipt is written under the epoch number at request time, but the default-claim path reads it only under the epoch number at finalization time.

In `requestInstantWithdraw`, basis is keyed by `epochNumber` at request time (IdleCreditVault.sol:367-372):

```solidity
uint256 currentEpoch = epochNumber;
instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
pendingInstantWithdraws += _amount;
```

`epochNumber` only increments inside `stopEpoch`, so an instant request recorded during epoch N stays keyed to N even if the borrower underfunds it (`collectInstantWithdrawFunds` at IdleCDOEpochVariant.sol:282 only pulls what the CDO holds; the remainder stays in `pendingInstantWithdraws`).

If the borrower subsequently defaults and `finalizeDefault`/`finalizeDefaultRecovery` runs with `defaultRecoveryEpoch = epochNumber = N+1` (or any later epoch), then in `claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) the call to `_claimDefaultedInstantWithdrawRequest` reads only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` (line 844), which is 0 for this user. Execution falls through to:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`_transferFundedClaim` (lines 897-907) reverts whenever `balance - defaultRecoveryReserve < amount`. After default finalization, essentially the entire strategy balance *is* the recovery reserve, so the call reverts — and the receipt basis is already burned/cleared unreachable-state aside, the revert means the user can never claim. Their per-epoch basis in epoch N is never cleared, `instantWithdrawClaimsByEpoch[N]` remains permanently nonzero, and the portion of the reserve implicitly allocated to that receipt is locked forever.

### Impact Explanation
Permanent freezing of unclaimed yield / recovery funds. Any user whose instant-withdraw request was left underfunded across an epoch boundary before default finalization loses the ability to claim their recovery share, and the corresponding reserve slice is stranded in the strategy contract. Loss equals the full (haircut-adjusted) recovery entitlement of affected instant receipts — quantitatively `instantWithdrawsRequestsByEpoch[user][staleEpoch] * defaultRecoveryPrice / 1e18` per user.

### Likelihood Explanation
Requires a sequence: instant withdrawals enabled, a pending instant request that is not fully funded at `startEpoch` (borrower underfunding — the code explicitly handles this case at IdleCDOEpochVariant.sol:286-289), then at least one `stopEpoch` bumping `epochNumber`, then borrower default and `finalizeDefault`. This is exactly the "unfunded remainder" scenario the accounting at lines 849-853 contemplates, so the precondition is a supported protocol state, not an edge case.

### Recommendation
In `_claimDefaultedInstantWithdrawRequest`, clear the user's instant basis across epochs rather than only `defaultRecoveryEpoch` — e.g., iterate/aggregate `instantWithdrawsRequests[_user]` as the claim basis (as the pre-migration aggregate did) or store a per-user last-instant-request epoch marker analogous to `lastWithdrawRequest` so the correct epoch key is used. Ensure the funded-reserve path can never be reached with uncleared defaulted instant basis.

### Proof of Concept
A Foundry fork PoC would: (1) deploy/proxy `IdleCreditVault` + `IdleCDOEpochVariant` with instant withdrawals enabled (`setInstantWithdrawParams`); (2) user deposits AA, requests instant withdraw during buffer of epoch N via `requestInstantWithdraw`; (3) `startEpoch` with insufficient underlying so `collectInstantWithdrawFunds` leaves `pendingInstantWithdraws > 0`; (4) run `stopEpoch`/`startEpoch` to bump `epochNumber`; (5) borrower fails to repay, `finalizeDefault` with partial recovery; (6) `claimInstantWithdrawRequest` reverts in `_transferFundedClaim` because the basis keyed at epoch N was never cleared at `defaultRecoveryEpoch` — the user's recovery is permanently unclaimable.

Caveat: I could not fully read `finalizeDefaultRecovery`/`_handleBorrowerDefault` to confirm `defaultRecoveryEpoch` is set to the post-increment `epochNumber` rather than the request epoch; if it instead snapshots the epoch in which pending instant basis was recorded, the mismatch narrows. Verification of that assignment is needed to confirm exploitability.
