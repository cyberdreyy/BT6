### Title
Vote program's unchecked `Authorize`/`AuthorizeWithSeed` instruction permits setting `authorized_withdrawer` to `Pubkey::default()` with no new-authority co-signature, permanently bricking the vote account - (File: programs/vote/src/vote_state/mod.rs)

### Summary
The Vote program's `authorize()` function, invoked via the `VoteInstruction::Authorize` (and `AuthorizeWithSeed`) instruction path, lets the current `authorized_withdrawer` reassign the withdrawer authority to any arbitrary `Pubkey` — including `Pubkey::default()` (the all-zero pubkey with no known private key) — with no validation that the new authority is non-default and without requiring the new authority to co-sign.

### Finding Description
In `vote_state::authorize`, the `VoteAuthorize::Withdrawer` branch only verifies the *current* withdrawer signed, then unconditionally writes the caller-supplied `authorized` pubkey into state: [1](#0-0) 

There is no check anywhere in this path rejecting `authorized == Pubkey::default()`, unlike the external report's OTLM contract which is missing exactly this check on its `receiver_` setter. The unchecked `Authorize` instruction (as opposed to `AuthorizeChecked`) does not require the new authority to sign, so a single transaction signed only by the current withdraw authority can set `authorized_withdrawer` to the zero pubkey, which is an address with no corresponding private key. This is analogous to the report's `setOptionReceiver` being callable with `address(0)` despite `initialize` validating against it. The corresponding processor entry point that dispatches to this function is `process_authorize_with_seed_instruction` / the main `Authorize` handling in `programs/vote/src/vote_processor.rs`, and tests confirm the unchecked variant reaches production logic (e.g. `test_authorize_withdrawer`): [2](#0-1) 

For comparison, the checked variant naturally prevents this because it requires the new authority to sign the transaction (impossible for the default pubkey, which has no private key), but the unchecked `Authorize` instruction has no equivalent protection.

### Impact Explanation
Setting `authorized_withdrawer` to `Pubkey::default()` permanently and irrecoverably locks the vote account: no party can ever authorize a new withdrawer (`VoteAuthorize::Withdrawer` requires the current withdrawer to sign, and nobody holds the private key for the zero pubkey), and no party can ever withdraw the account's lamports (vote account balance, including rewards) via the `Withdraw` instruction, since that also requires the `authorized_withdrawer` signature. This permanently locks funds in the account, matching the "concrete unsigned fund movement... or stake/reward corruption" bar, since staked rewards routed to the vote account become permanently unwithdrawable.

### Likelihood Explanation
This can be triggered by any transaction signed solely by the current authorized withdrawer (a normal, legitimately-reachable path, no special privilege required beyond controlling the current withdraw key) — it requires only a mistaken or malicious call with `new_authorized_pubkey = Pubkey::default()`, exactly mirroring the report's "owner mistakenly calls setter with zero address" scenario. It is a self-inflicted/operator-mistake bug class rather than an externally-forced exploit, which somewhat limits severity compared to a bug that lets an unrelated attacker steal funds, but it is fully reachable by a single validly-signed transaction from the withdraw authority.

### Recommendation
Add an explicit check in `vote_state::authorize` (and the analogous stake program authorize path, if it has the same gap) rejecting `authorized == Pubkey::default()` for `VoteAuthorize::Withdrawer` (and ideally `VoteAuthorize::Voter`), returning `InstructionError::InvalidInstructionData` or similar, mirroring the recommended `if receiver_ == address(0) revert ...` pattern from the source report.

### Proof of Concept
1. Vote account `V` has `authorized_withdrawer = W`.
2. `W` submits a transaction with `VoteInstruction::Authorize(Pubkey::default(), VoteAuthorize::Withdrawer)`, signing only as the current authority (satisfies `verify_authorized_signer(vote_state.authorized_withdrawer(), signers)` at [1](#0-0) ).
3. The instruction succeeds; `authorized_withdrawer` is now `Pubkey::default()`.
4. No subsequent `Withdraw` or `Authorize(Withdrawer)` instruction can ever succeed, since both require a signature from `authorized_withdrawer`, and no private key exists for `Pubkey::default()`.
5. All lamports held in the vote account beyond rent-exempt minimum become permanently unwithdrawable.

**Note:** I could not locate the stake program's analogous `authorize` implementation (files under `programs/stake*/src/`) in the index within available search iterations, so I cannot confirm whether the identical gap exists there. If it does, it would represent a parallel instance of the same bug class with similar (or more severe, given stake accounts hold larger balances) impact.
