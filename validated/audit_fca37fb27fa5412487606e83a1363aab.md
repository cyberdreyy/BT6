### Title
Unbounded growth of the EIP-8130 2D-nonce txpool sidecar's `lanes` map degrades block building and txpool RPC service over time - (File: crates/execution/txpool/src/two_d_nonce_pool.rs)

### Summary
`TwoDNoncePool` keeps a `lanes: HashMap<LaneId, NonceLane<T>>` keyed by `(sender, nonce_key)` [1](#0-0) . `nonce_key` is an attacker-chosen `U256` field of an EIP-8130 transaction's 2D nonce channel [2](#0-1) , so any unprivileged sender can create an unbounded number of distinct lanes at negligible cost — one new `(sender, nonce_key)` lane per submitted transaction with a fresh `nonce_key`.

Every core txpool read — `pending_transactions`, `queued_transactions`, `all_transactions`, `pending_and_queued_txn_count`, `transactions_by_sender` — walks `self.lanes.values()` in full, i.e. its cost scales with the *total number of lanes ever created*, not with the number of currently pending/queued transactions [3](#0-2) . I could not find any pruning/eviction path (`lanes.remove`, `lanes.retain`) for empty or fully-mined lanes in this file, suggesting stale lanes persist indefinitely once created.

This is structurally identical to `BondAggregator.liveMarketsBy`: an ever-growing, attacker-influenced collection is fully iterated on every call from hot/critical paths, so per-call cost grows without bound over the life of the chain.

### Finding Description
`TransactionPool` methods on the sidecar are called from:
- Block building: `pending_transactions()`/`best_transactions_with_attributes` combine `protocol_pool` output with `nonce_pool.read().pending_transactions()` [4](#0-3) , which is exercised by the flashblocks payload builder's best-transactions iteration [5](#0-4) .
- Public RPC: `txpool_content` / `txpool_contentFrom`, exposed via `basectl txpool` and any RPC client, funnels into the same full-pool enumeration [6](#0-5) .

Because `nonce_key` is not scoped, capped, or reclaimed, an attacker can cheaply mint a very large number of distinct `(sender, nonce_key)` lanes (e.g. using many nonce_key values from a small number of funded accounts, each just needing to pay for one valid or even a single pending transaction per lane) and never advance/complete them. Each of the read paths above then walks every lane on every call, so per-block and per-RPC-request work grows linearly (or worse, given HashMap iteration and per-lane BTreeMap scans) with the total number of distinct lanes ever observed by the node, mirroring the described "at least/at most N external calls per market" pattern in the original finding.

### Impact Explanation
If lanes are never pruned, the cost of `pending_transactions()`, `all_transactions()`, and related calls increases monotonically as the chain progresses. Since these are invoked on every flashblock/payload-building cycle and on every `txpool_content`/`txpool_contentFrom` RPC call, sustained growth can push per-block or per-RPC-call latency past the block/flashblock time budget, causing block building to stall (an operational "node halt" for block production) and making the txpool RPC path unable to respond within acceptable time ("an RPC the node can no longer serve"), both of which are explicitly in-scope impact categories.

### Likelihood Explanation
Any unprivileged transaction sender that can submit EIP-8130 transactions controls the `nonce_key` field and can generate new lanes cheaply and repeatedly; no special privilege, keys, or node cooperation is required, only sustained low-cost transaction submission over time.

### Recommendation
Bound and reclaim the `lanes` map: cap the number of live `(sender, nonce_key)` lanes per sender (mirroring `Eip8130Constants::MAX_*` caps already used elsewhere for actor/config-change counts, e.g. [7](#0-6) ), evict/garbage-collect lanes once they become empty (fully mined/removed) rather than leaving them resident forever, and/or paginate the full-pool enumeration paths so a single call's cost does not scale with the all-time lane count.

### Proof of Concept
1. From N distinct funded accounts (or one account across nonce_key namespace, since `nonce_key` is per-account-and-channel), submit EIP-8130 transactions each specifying a unique, never-reused `nonce_key` (each maps to a new `LaneId` in `two_d_nonce_pool.rs`).
2. After each submission, `TwoDNoncePool::pending_transactions`/`all_transactions` is invoked by block building (`best_transactions_with_attributes`) and by `txpool_content` RPC calls, each time iterating `self.lanes.values()` in full [8](#0-7) .
3. Repeat over time without ever completing/mining these lanes (or after mining, since no eviction was found for the map itself); observe that the per-call/per-block cost of these iterations grows proportionally to the cumulative number of lanes created, independent of currently pending/queued transaction count, degrading block-building and RPC-serving latency.

**Uncertainty**: I could not view the entire `two_d_nonce_pool.rs` file (pruning logic may exist elsewhere, e.g. in a `prune_mined_transactions` implementation not captured by my grep) within the available iterations, so it's possible lanes with fully-mined/removed transactions are cleaned up on some other path I did not locate; if such pruning exists and reliably empties/removes exhausted lanes, the severity of this analog would be reduced to a bounded-growth concern rather than a strictly unbounded one. This should be verified directly in the repository (search for all call sites removing entries from `lanes`, and for any garbage-collection call scheduled alongside block finalization) before treating this as fully confirmed.

    /// Returns the number of pending and queued transactions.
    pub(crate) fn pending_and_queued_txn_count(&self) -> (usize, usize) {
        let mut pending = 0;
        let mut queued = 0;
        for lane in self.lanes.values() {
            let pending_in_lane = lane.consecutive_pending_len();
            let live_in_lane = lane.live_transactions().count();
            pending += pending_in_lane;
            queued += live_in_lane.saturating_sub(pending_in_lane);
        }
        pending += self.nonce_free.len();
        (pending, queued)
    }

    /// Returns all pending transactions.
    pub(crate) fn pending_transactions(&self) -> Vec<Arc<ValidPoolTransaction<T>>> {
        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            for transaction in lane.consecutive_pending_transactions() {
                transactions.push(Arc::clone(transaction));
            }
        }
        transactions.extend(self.nonce_free.values().cloned());
        transactions
    }

    /// Returns all queued transactions.
    pub(crate) fn queued_transactions(&self) -> Vec<Arc<ValidPoolTransaction<T>>> {
        let mut transactions = Vec::new();
        for lane in self.lanes.values() {
            for transaction in lane.queued_transactions() {
                transactions.push(Arc::clone(transaction));
            }
        }
        transactions
    }
