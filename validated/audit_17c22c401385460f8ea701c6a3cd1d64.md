### Title
Miner-controlled activity-refresh in `check_latest_block_in_tenure` wedges the inactivity fallback, stalling the tenure indefinitely - (File: `stacks-signer/src/chainstate/mod.rs`)

### Summary
`check_latest_block_in_tenure` treats *any* block proposal that conflicts with a merely pre-committed (unsigned) block in the current tenure as "miner activity" and refreshes `last_activity_time`, even though the proposal itself is rejected. Because `SortitionState::is_timed_out` derives inactivity purely from `last_activity_time`, a single non-cooperative winning miner can keep resubmitting conflicting/never-thresholded block proposals for its own tenure to perpetually refresh this timestamp, which prevents `check_miner_inactivity` from ever falling back to a valid prior miner — a liveness wedge triggerable by one miner with no signer collusion.

### Finding Description
The Grav CVE's root cause is a protective check (`isDangerousFunction`) that can be silently bypassed by mutating a piece of trusted state (`safe_functions`) through a path the check does not itself defend. The same "protected control path has an unprotected side-channel that feeds it" pattern exists here.

The safety mechanism in question is the signer's miner-inactivity fallback: if the active miner for a tenure stops proposing, signers must eventually time it out and revert to a valid prior miner so the chain does not stall (`check_miner_inactivity`, `stacks-signer/src/v0/signer_state.rs:284-374`). This decision is driven entirely by `SortitionState::is_timed_out`: [1](#0-0) 

`is_timed_out` computes `elapsed` as `now - last_activity` (falling back to the burn-block receive time if no activity was ever recorded), and only reports timeout once `elapsed > block_proposal_timeout`. It explicitly does *not* count a merely pre-committed block as "signed" (that was previously a bug, fixed per the changelog note below), but it still trusts `last_activity_time` unconditionally.

`last_activity_time` is refreshed by `check_latest_block_in_tenure`, which runs on every incoming block proposal for the *proposal's own tenure* (`confirms_latest_block_in_same_tenure`). Two branches update it even when the proposal is ultimately rejected: [2](#0-1) [3](#0-2) 

The second branch is the exploitable one: as soon as a signer has a fresh, merely `PreCommitted` block for the tenure (validated by the node, but never having reached the 70% pre-commit threshold), *any subsequent proposal at the same or lower height* from that miner is treated as "miner activity" and calls `signer_db.update_last_activity_time(...)`, then the proposal is rejected. There is no rate limit, no bound on how many times this can happen, and no requirement that the competing proposals be materially different — the miner can keep generating validatable-but-conflicting tenure-start proposals (e.g. varying the transaction set) at will.

This breaks the liveness guarantee the timeout mechanism exists to provide: as long as the miner resubmits more often than `block_proposal_timeout`, `elapsed` never exceeds the threshold, so `is_timed_out` never returns true, and `check_miner_inactivity` never reverts to the prior (valid) miner: [4](#0-3) 

The changelog confirms the designers previously fixed the closely related "signed" side of this exact hazard but did not close the `last_activity_time` refresh side-channel: [5](#0-4) 

### Impact Explanation
This is a **liveness wedge**: a single sortition-winning miner (an in-scope, one-slot attacker, no gossip beyond normal block-proposal broadcast) can prevent signers from ever timing out its tenure and falling back to a valid prior miner. If the miner's own competing proposals also never reach the 70% pre-commit/signature threshold (e.g. because the miner deliberately splits votes by varying content, or because of ordinary gossip-timing variance it can amplify), signers are stuck waiting on that tenure indefinitely — block production stalls until the next burn block, matching the "High - a signer wedged into never signing valid blocks" impact category.

### Likelihood Explanation
The attacker needs only to control the winning miner for one tenure — no majority of signers, no other signer's key, and no local/auth-token access. The mechanic (get a block pre-committed, then repeatedly submit conflicting proposals to refresh activity) is a straightforward extension of already-documented conflict-handling logic (the log message "Counting it as miner activity, but not rejecting the proposal" explicitly acknowledges the side-effect), making this readily discoverable and repeatable by any miner operator who wants to stall the network.

### Recommendation
Bound the "count as activity" side effect: only accept a limited number of activity refreshes from a competing proposal, cap the total extension time from this branch independently of the base `block_proposal_timeout`, or require distinct/novel proposals (rather than a mere resubmission at the same height) to qualify as "activity." Alternatively, base inactivity purely on time since the *pre-commit* was first observed for that tenure, rather than allowing later conflicting proposals to reset the clock indefinitely.

### Proof of Concept
1. Miner M wins the sortition for tenure T and proposes tenure-start block A at height H; signers validate A and mark it `PreCommitted` (validated but under the 70% threshold), setting `approved_time`.
2. Before `tenure_last_block_proposal_timeout` expires, M proposes a second, differently-constructed block B at the same height H (a "conflict" with the pre-committed A).
3. Each signer's `check_latest_block_in_tenure` sees `is_fresh_pre_commit == true` and `block.header.chain_length <= info.block.header.chain_length`, rejects B, but calls `update_last_activity_time` (`stacks-signer/src/chainstate/mod.rs:427-447`).
4. M repeats step 2 with blocks C, D, E, … at an interval shorter than `block_proposal_timeout`, none of which reach the pre-commit/signature threshold.
5. `SortitionState::is_timed_out` (`stacks-signer/src/chainstate/v1.rs:55-94`) never observes `elapsed > block_proposal_timeout`, so `check_miner_inactivity` never reverts to the prior sortition's miner; the tenure never advances and the chain stalls until the next Bitcoin block forces a new sortition.

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
