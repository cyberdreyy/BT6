### Title
Fee-on-transfer underlying breaks `IdleCreditVault` funding accounting: strategy tokens and claim reserves are credited for the nominal amount while fewer underlyings are received - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The Kairos bug class — recording the nominal transfer amount instead of the actual received balance — has a direct analog in `IdleCreditVault`. Several functions pull underlying via `safeTransferFrom` and then credit the **requested** `_amount` to internal accounting (strategy-token supply, funded withdraw reserves, default recovery reserve). With a fee-on-transfer pool currency (e.g. USDT with its fee enabled, which is a supported pool currency on Clearpool-style vaults), the vault receives `_amount - fee` but accounts `_amount`, creating an unbacked liability that is ultimately borne by the last claimers.

### Finding Description
Three pull paths record the nominal amount rather than the balance delta:

1. `deposit()` pulls `_amount` from the IdleCDO and mints `_amount` strategy tokens 1:1 to the CDO (`IdleCreditVault.sol:596-617`). With a fee `f`, the vault receives `_amount - f` underlying but the CDO holds `_amount` strategy tokens that price at `oneToken` (`price()` returns `oneToken` unconditionally, `IdleCreditVault.sol:174-176`). The CDO's `getContractValue()` therefore counts `_amount` while only `_amount - f` exists. Compare with `IdleCDO._deposit`, which correctly mints tranche shares by balance delta (`IdleCDO.sol:250-253`).

2. `collectWithdrawFunds(_amount)` and `collectInstantWithdrawFunds(_amount)` clear `pendingWithdraws`/`pendingInstantWithdraws` by the nominal amount and pull `_amount` from the CDO (`IdleCreditVault.sol:398-430`). The vault receives `_amount - f`, so aggregate funded claims exceed actual holdings; the last `claimWithdrawRequest`/`claimInstantWithdrawRequest` calls revert on insufficient balance (or drain the `defaultRecoveryReserve` guard margin).

3. `finalizeDefaultRecovery(_recoveredAmount, _recoverySource)` adds the nominal `_recoveredAmount` into `defaultRecoveryReserve` and computes `defaultRecoveryPrice` on it (`IdleCreditVault.sol:686-708`). Actual reserve is lower by the fee, so defaulted-epoch and post-default claims (`_claimDefaultedWithdrawRequest`, `_claimPostDefaultWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`) are priced on phantom funds and the final claimants' transfers fail permanently.

Note the CDO-side deposit also misbehaves upstream: `IdleCDOCreditVault._deposit` mints shares on the received delta but then calls `IIdleCDOStrategy(strategy).deposit(_amount)` with the pre-fee amount (`IdleCDOCreditVault.sol:202-211`), compounding the mismatch.

### Impact Explanation
Insolvency / permanent freezing of user funds. Each deposit, withdraw-funding, and default-recovery pull silently books `f` more liability than assets. Funded withdraw claimants and default-recovery claimants hold address-bound receipts (`_transfer` reverts unless called by the CDO, `IdleCreditVault.sol:939-942`), so losses cannot be exited early; the deficit concentrates on whoever claims last, whose `safeTransfer` reverts forever since the vault is undercollateralized with no mechanism to replenish. Loss per occurrence equals the token's transfer fee times the amount moved (e.g. ~1% of every deposit and every funded claim batch).

### Likelihood Explanation
Requires the pool currency to charge transfer fees. USDT — a standard pool currency for these credit vaults — has a built-in, owner-toggleable fee mechanism, so no exotic token is needed. No privileged misbehavior is required: the gap is created by honest deposits, borrower funding, and recovery funding flowing through the accounting paths. The `_skim`/donation guards do not help because the shortfall is under-receipt, not an over-balance.

### Recommendation
Measure actual received amounts everywhere underlying is pulled:

```solidity
// deposit
uint256 balBefore = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - balBefore;
_mint(msg.sender, received);
totEpochDeposits += received;
return received;
```

Apply the same before/after pattern in `collectWithdrawFunds`, `collectInstantWithdrawFunds` and `finalizeDefaultRecovery` (using the received value for `reserveAmount` and the `lossRecoveryPrice`/`defaultRecoveryPrice` computation), and pass the measured received amount — not `_amount` — to `IIdleCDOStrategy.deposit` from `IdleCDOCreditVault._deposit`/`IdleCDO._deposit`. Alternatively, explicitly document and enforce that only non-fee-on-transfer tokens may be used as `token`.

### Proof of Concept
Reproducible on a Foundry fork:

1. Deploy `IdleCDOCreditVault` + `IdleCreditVault` with a mock fee-on-transfer ERC20 (1% fee on `transferFrom`) as `token`.
2. KYC'd lender calls `depositAA(100e6)`: CDO receives `99e6`, mints shares for 99, then `strategy.deposit(100e6)` pulls 100, vault receives 99, mints **100** strategy tokens to the CDO. `getContractValue()` reports 100 while total real underlying is 99.
3. User calls `requestWithdraw`; manager stops epoch; borrower/queue funds via `collectWithdrawFunds(100e6)`: vault receives 99 but `pendingWithdraws` cleared by 100. First claimer for 60 succeeds; second claimer for 40 reverts on `safeTransfer` despite holding a valid funded receipt.
4. For the default path, call `finalizeDefaultRecovery(recovered, source)` with a fee-charging pull: `defaultRecoveryReserve` is set to `recovered` while only `recovered·99/100` was received; the last defaulted claim permanently reverts in `_transferDefaultRecovery`.

Assert `vault.balanceOf(cdo)` + pending claims > `underlying.balanceOf(vault)` after step 2, and that the final claim reverts.
