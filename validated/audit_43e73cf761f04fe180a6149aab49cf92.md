### Title
Stale confirmations from removed multisig members remain counted toward the confirmation threshold, allowing requests to execute below the configured `K`-of-`N` threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`DeleteMember` (in `multisig2`) and `DeleteKey` (in `multisig`) only purge outstanding *requests* that were created by the removed member/key, and clear that member's `num_requests_pk` counter. Neither path scrubs the removed member's *confirmation* entries that were already cast on other, still-pending requests created by other members. Because `confirm()` counts entries in the `confirmations` set purely by length, a confirmation cast by a member who has since been removed still counts toward `num_confirmations`, letting a request execute with fewer live/authorized approvals than the contract's configured threshold.

### Finding Description
The confirmation-counting invariant the contract is supposed to guarantee is:
`confirmations.len() (at execution time) == number of confirmations from currently valid members >= num_confirmations`

`confirm()` only checks the raw set size against `num_confirmations`, with no re-validation that every entry in the set still corresponds to a live member: [1](#0-0) 

When a member is deleted via `DeleteMember`, the contract removes only the requests *created by* that member and the member's own request-count bookkeeping — it does not iterate `confirmations` to strip that member's votes from requests created by other members: [2](#0-1) 

The same pattern exists in the legacy `multisig` contract's `DeleteKey` action, which filters `self.requests` by `r.signer_pk == pk` (creator only) before clearing confirmations, again leaving that key's confirmations on other members' pending requests untouched: [3](#0-2) [4](#0-3) 

Storage layout confirms confirmations are keyed only by `RequestId` and store `String` identities of members, with no reference to the live `members` set at read time: [5](#0-4) 

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding directly called out in scope: a multisig `Transfer`/`FunctionCall`/`AddKey` request can be executed with fewer than `num_confirmations` *currently authorized* approvals, because one or more counted confirmations belong to an account/key that has already been removed from `members`. This is a "multisig request executed below threshold" — Critical impact per the given classification, since it can move NEAR (or trigger `AddKey`/`FunctionCall` actions) with insufficient live authorization.

### Likelihood Explanation
The trigger requires ordinary multisig operation, not any privileged bypass: a legitimate member confirms a request (partial confirmation, below threshold) and later the multisig — by ordinary, correct governance action — removes that same member (e.g., because their key was compromised, they left the organization, or the group is rotating signers). This is a normal, expected lifecycle event, not owner/foundation misuse, so the "stale request left half-confirmed" scenario combined with a subsequent member-removal is realistic. An attacker who anticipates their own removal (or a still-pending stale request from a soon-to-be-removed member) can pre-position confirmations to be exploited afterward with only one honest confirmation.

### Recommendation
When removing a member/key (`delete_member` / `DeleteKey`), iterate over all pending requests' `confirmations` sets and strip any entry belonging to the removed member, in addition to purging requests created by that member. Alternatively, when counting confirmations in `confirm()`, filter the set to only entries still present in `self.members` before comparing to `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C]`, `num_confirmations = 2`.
2. `B` calls `add_request` with a `Transfer` action to attacker-controlled `receiver_id`. Request `R` is created with 0 confirmations.
3. `A` calls `confirm(R)`. `confirmations[R] = {A}` (1/2, not yet executed) — see the `else` branch in `confirm`: [6](#0-5) 
4. Separately, the group legitimately removes `A` via a `DeleteMember{member: A}` request confirmed by `B` and `C` (2/2 confirmations, executes normally). `delete_member` removes `A` from `members`, deletes `A`'s own outstanding requests, but does **not** touch `confirmations[R] = {A}` since `R` was created by `B`, not `A`: [7](#0-6) 
5. `C` (a live member) calls `confirm(R)`. `confirmations[R].len() == 1` (stale `A`) `+ 1 == 2 >= num_confirmations(2)` → request executes, transferring funds, despite only one currently-valid member (`C`) having actually approved it post-removal.

This demonstrates a request executing below the intended live-member threshold, satisfying the Critical "multisig request executed below threshold" impact criterion.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
