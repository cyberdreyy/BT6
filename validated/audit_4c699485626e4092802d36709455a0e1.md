### Title
Missing MessageId uniqueness check in `HandleLegacyUserMessage` allows callback hijacking / cross-user response delivery in `handleWebAPITriggerMessage` - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`handler.savedCallbacks` is keyed only by the client-supplied `msg.Body.MessageId`, and `HandleLegacyUserMessage` unconditionally overwrites any existing entry for that ID with no existence/ownership check. `handleWebAPITriggerMessage` later resolves a DON node's response purely by that same ID and delivers it to "whatever callback is currently registered," with no binding to the sender/session that originally issued the request.

### Finding Description
`HandleLegacyUserMessage` registers a callback for a user request: [1](#0-0) 
This assignment is a plain map write with no check for whether `msg.Body.MessageId` is already in use by another (still in-flight) request. `MessageId` is a plain, client/user-supplied string (per the module docs, "User Requests: Plain string identifiers"), not a gateway-generated, collision-resistant value.

`handleWebAPITriggerMessage` resolves node responses purely by this same ID: [2](#0-1) 
It looks up, deletes, and forwards `savedCb.SendResponse` to whatever callback is registered under that ID at the moment the node response arrives — there is no verification that the callback still corresponds to the original requester/session that generated the outbound request the node is replying to.

`HandleNodeMessage` only checks that `msg.Body.Sender == nodeAddr` (i.e., that the DON connection presenting the message is the node it claims to be): [3](#0-2) 
This authenticates the *node*, but does nothing to bind the response back to the specific request/session/user that triggered it beyond the shared `MessageId` string.

Exploit flow (no malicious/compromised node required): an attacker who can guess or race a victim's chosen `MessageId` (e.g., short-lived, predictable, or externally observable IDs) submits their own legacy user message with the same `MessageId` *after* the victim's request has been dispatched to the DON but *before* the DON's response returns. Because `HandleLegacyUserMessage` overwrites `h.savedCallbacks[id]` unconditionally, the victim's registered `savedCallback` is silently replaced with the attacker's own callback. When the legitimate DON node response for the victim's original request subsequently arrives with the same `MessageId`, `handleWebAPITriggerMessage` delivers it to the attacker's callback instead of the victim's — a genuine cross-session response misdelivery caused purely by application-layer logic, not by a compromised node.

### Impact Explanation
This is cross-user response confusion: an attacker can receive a response payload (which may contain another user's HTTP trigger response body/headers) that was intended for a different session, matching the "unauthorized action on / disclosure of another user's data" bounty impact class. The severity depends on how predictable/observable `MessageId` values are in real deployments; the code itself provides no defense-in-depth against collision (no ownership/version check, no per-caller salting).

### Likelihood Explanation
Requires no privileged role — an unprivileged caller of the legacy webapi-trigger user message path just needs to (a) learn or predict another in-flight request's `MessageId`, and (b) submit their own request with that same ID before the real response returns. Feasibility depends entirely on `MessageId` entropy/predictability at the call site, which this handler code does not enforce or validate at all. The race window is bounded by `CallbackMaxAgeSec` (default 120s), which is a comparatively generous window for the race.

### Recommendation
In `HandleLegacyUserMessage`, reject (or fail loudly) if `h.savedCallbacks[msg.Body.MessageId]` already exists rather than silently overwriting it. Additionally, bind the response to the original request more strongly than a bare string ID — e.g., include and verify the original requester/session identity or a per-request nonce/HMAC in the round-trip, so `handleWebAPITriggerMessage` can validate that the responding node's message actually corresponds to the request it dispatched, not merely that some entry exists under a matching ID.

### Proof of Concept
Go handler-level test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with a mock `handlers.DON`.
2. Call `HandleLegacyUserMessage` with `MessageId = "X"` and callback `callbackVictim` (a mock capturing `SendResponse` calls); assert `h.savedCallbacks["X"].Callback == callbackVictim`.
3. Before any node response arrives, call `HandleLegacyUserMessage` again with the same `MessageId = "X"` and a different callback `callbackAttacker`; assert `h.savedCallbacks["X"].Callback` is now `callbackAttacker` (demonstrating silent overwrite, no collision check).
4. Simulate the DON node delivering the legitimate response for the victim's original request via `HandleNodeMessage`/`handleWebAPITriggerMessage` with `resp.ID = "X"`.
5. Assert `callbackAttacker.SendResponse` was invoked with the victim's response payload, and `callbackVictim.SendResponse` was never called — proving cross-user response delivery purely from ID collision, independent of any node compromise.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
