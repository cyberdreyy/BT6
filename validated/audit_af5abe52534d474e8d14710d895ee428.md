### Title
Stale confirmations from deleted multisig keys are still counted toward the confirmation threshold, allowing a request to execute below the effective live-member threshold - (File: multisig/src/lib.rs)

### Summary
The external report describes a class of bug where a piece of "trusted" derived state (a rendered dialog) is computed from stale/unvalidated data rather than being re-verified at the point of use, letting an attacker manipulate the outcome. The equivalent binding in this repo's `multisig` contract is: `confirmations.len()` (recorded confirmations for a request) must equal the number of *currently live* multisig members who actually endorsed the request. `MultiSigContract::confirm` [1](#0-0)  never re-validates that the public keys already present in a request's confirmation set are still members of the multisig at the moment the threshold check `confirmations.len() as u32 + 1 >= self.num_confirmations` is evaluated.

### Finding Description
When a key is removed via `MultiSigRequestAction::DeleteKey`, the contract only purges requests **originated by** that key and their confirmation sets; it does not scan other pending requests to strip that key's confirmation from their `confirmations` sets: [2](#0-1) 

Consequently, a public key that confirmed request `R1` and was later removed from the multisig (via a separate, properly-threshold-approved `DeleteKey` request `R2`) still counts as a valid confirmation on `R1`. The `confirm` threshold check treats `self.confirmations.get(&request_id)` as a proxy for "currently live members who endorsed this request", but that set is never revalidated against the set of keys still attached to the account: [3](#0-2) 

`assert_valid_request`, which gates both `confirm` and `delete_request`, also performs no such liveness check — it only asserts predecessor==current account and that the request/confirmations entries exist: [4](#0-3) 

### Impact Explanation
This breaks the equality "confirmations counted == live members who endorsed the request." With `num_confirmations = N` and members A, B, C, D:
- A and B confirm `R1` (a `Transfer`), reaching 2/N confirmations.
- A separate request `R2` (`DeleteKey { public_key: B }`) is properly confirmed by A, C, D and executes, removing B as an access key.
- `R1`'s confirmation set still contains B's stale confirmation (count = 2).
- C confirms `R1`; count becomes 3, satisfying `>= N` even though B is no longer a valid signer on the account — only A and C are truly live confirmers.
- `R1` executes (e.g. `Transfer`, `AddKey`, `DeployContract`, `FunctionCall`) with fewer live-key confirmations than the configured threshold implies.

This directly matches the specified Critical impact bucket: "a multisig request executed below threshold."

### Likelihood Explanation
No privileged role is required beyond normal multisig key holders acting within their granted `add_request`/`confirm` permissions — this is reachable by any subset of legitimate key holders following ordinary operational flows (one member being rotated out while other requests are in flight is a realistic, even expected, operational sequence). No foundation, redeploy, or external actor is needed, and it does not rely on ignoring documented initialization.

### Recommendation
When executing `DeleteKey` (or the analogous `DeleteMember` in `multisig2`), iterate over all pending requests' confirmation sets and remove the deleted key/member from each, or alternatively re-validate (at `confirm`-time and at execution-time) that every public key present in a request's `confirmations` set is still an active access key/member before counting it toward the threshold.

### Proof of Concept
1. Deploy `multisig` with `num_confirmations = 3` and keys A, B, C, D added as full-access function-call keys.
2. A calls `add_request_and_confirm` with `MultiSigRequest { receiver_id: <self>, actions: [Transfer{ amount }] }` → request `R1`, confirmations = {A}.
3. B calls `confirm(R1)` → confirmations = {A, B} (2/3).
4. Separately, A creates and (with C, D) confirms `MultiSigRequestAction::DeleteKey{ public_key: B }` as request `R2`, reaching 3/3 and executing — B's access key is removed from the account per `execute_request`'s `DeleteKey` branch [2](#0-1) . Note that `R1`'s confirmation set is untouched because `DeleteKey`'s cleanup only targets requests where `r.signer_pk == pk` (i.e., requests *originated* by B, not requests B merely confirmed).
5. C calls `confirm(R1)` → `confirmations.len() = 2` (A, B) `+ 1 = 3 >= num_confirmations(3)` → `R1` executes the `Transfer`, even though B (one of the two "confirming" keys) no longer exists as a member of the multisig — only A and C are live confirmers, i.e., an effective 2-of-4 execution against a nominal 3-of-4 policy.

Note: `multisig2/src/lib.rs` uses an analogous `confirmations: LookupMap<RequestId, HashSet<String>>` pattern gated by `confirm`/`assert_valid_request` [5](#0-4) ; I located `DeleteMember` in the action dispatch [6](#0-5)  but was unable to inspect the body of `fn delete_member` before running out of tool iterations, so I cannot confirm with certainty whether it purges stale confirmations from unrelated pending requests. This should be verified separately.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
