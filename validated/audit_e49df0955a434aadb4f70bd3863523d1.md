### Title
Any contract can force an arbitrary victim account to burn NEAR tokens via a permission-less `DeployGlobalContract` action - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_deploy_global_contract` deducts `storage_cost = global_contract_storage_amount_per_byte * code.len()` from `account.amount()` where `account` is always the account that is currently executing the receipt (i.e. the receipt's `receiver_id`), not the receipt's `predecessor_id`. Unlike other "administrative" actions (`DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`) which the protocol restricts to only run when `predecessor_id == receiver_id` (the "actor permission"/`sir` check), `DeployGlobalContract` carries no such restriction, so an attacker contract can dispatch a promise batch targeting an unrelated victim account and force that victim to burn its own balance for a deploy it never requested.

### Finding Description
`action_deploy_global_contract` (runtime/runtime/src/global_contracts.rs:24-62) computes the storage cost and subtracts it directly from `account.amount()`, burning the tokens (`result.tokens_burnt`) regardless of who initiated the receipt: [1](#0-0) 

The `account` parameter passed into this function is always the `Account` corresponding to the receipt's `receiver_id`, since every action in a receipt's action list is applied to the account owning the receipt — this is standard NEAR receipt-processing semantics, but for administrative/self-only actions this is protected by an explicit `predecessor_id == receiver_id` ("actor permission") requirement, as documented: [2](#0-1) 

That documented list — `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount` — explicitly does **not** include `DeployGlobalContract`. Correspondingly, `validate_action_with_mode` in `action_validation.rs` performs only structural/size validation for `Action::DeployGlobalContract` (via `validate_deploy_global_contract_action`), with no receiver/predecessor identity check: [3](#0-2) 

Because `promise_batch_action_deploy_global_contract`/`_by_account_id` (near-vm-runner `logic.rs`) let any contract A append a `DeployGlobalContract` action to a promise batch whose `receiver_id` is any account V that A names (there is no requirement that V == A, and no opt-in mechanism from V), the receipt executes at V with V's own `Account` struct, and `action_deploy_global_contract` burns `storage_cost` from V's balance: [4](#0-3) 

This differs from the `DeployContract` action, which the runtime restricts to `sir` (signer-is-receiver / actor-permission) semantics specifically to prevent exactly this kind of third-party account modification. Since `DeployGlobalContract` was not added to that restricted set, any account with existing NEAR balance is a valid, un-opted-in target: attacker contract A only needs to know V's `account_id` (public information) to create a promise batch (`promise_batch_create(V)` → `promise_batch_action_deploy_global_contract(...)`) and dispatch it. When the resulting receipt executes on shard hosting V, `action_deploy_global_contract` unconditionally deducts the storage cost from V, with no signature, access key, or deposit from V involved anywhere in the flow.

### Impact Explanation
This allows an unprivileged attacker to burn tokens out of any account's balance without that account's authorization, repeatedly and up to `max_contract_size` per call, at negligible cost to the attacker (only the attacker's own gas/attached-deposit for the outgoing `FunctionCall` + dispatched action fees). This is a loss-of-funds / griefing vector against arbitrary victim accounts, matching the "Stealing or loss of funds" bounty category, since the victim's NEAR balance is reduced (`tokens_burnt`) as a direct consequence of an action the victim never signed, requested, or had any access-key permission check for.

### Likelihood Explanation
Preconditions are minimal and fully within an ordinary unprivileged attacker's capability: deploy any wasm contract that calls `promise_batch_create` targeting the victim account and appends `promise_batch_action_deploy_global_contract`/`_by_account_id`. No special key, no validator/node access, and no cooperation from the victim contract is required — the deploy mode has no deposit field to opt the victim out, and the storage-staking-style balance check (`LackBalanceForState`) merely fails the action gracefully if the victim's balance is insufficient, but otherwise proceeds to burn funds if the victim can afford it. This is fully repeatable per block/per receipt for any target account with a non-zero balance.

### Recommendation
Add `DeployGlobalContract` (and `DeployGlobalContractByAccountId`, if that's a separate action variant) to the actor-permission ("sir") check enforced for `DeployContract`/`Stake`/`AddKey`/`DeleteKey`/`DeleteAccount`, i.e. require `predecessor_id == receiver_id` (or that the action list begins with `CreateAccount`) before allowing `action_deploy_global_contract` to execute and burn the account's balance. Alternatively, require an explicit deposit from the predecessor that covers the storage cost rather than debiting the executing account's own balance when predecessor != receiver.

### Proof of Concept
Runtime-level integration test (analogous to `check_meta_tx_no_fn_call`/`meta_tx_deploy` pattern in `integration-tests/src/tests/features/delegate_action.rs`):
1. Create two accounts, `attacker` (deploys a wasm contract with a method that does `promise_batch_create(victim)` then `promise_batch_action_deploy_global_contract(code)`) and `victim` (funded plain account, no special contract, never signs/authorizes anything related to this deploy).
2. Submit a `FunctionCall` transaction from `attacker` invoking that method.
3. Apply the resulting receipts through the runtime test harness.
4. Assert: `victim`'s balance decreases by `global_contract_storage_amount_per_byte * code.len()` and `ActionResult.tokens_burnt` reflects that burn, even though `victim` never submitted, signed, or authorized a `DeployGlobalContract` action, and `attacker`'s own balance is unaffected by the storage cost.

    fn promise_batch_action_deploy_global_contract_impl(
        &mut self,
        promise_idx: u64,
        code_len: u64,
        code_ptr: u64,
        mode: GlobalContractDeployMode,
        method_name: &str,
    ) -> Result<()> {
        self.result_state.gas_counter.pay_base(base)?;
        if self.context.is_view() {
            return Err(HostError::ProhibitedInView { method_name: method_name.to_owned() }.into());
        }
        let code = get_memory_or_register!(self, code_ptr, code_len)?;
        let code_len = code.len() as u64;
        let limit = self.config.limit_config.max_contract_size;
        if code_len > limit {
            return Err(HostError::ContractSizeExceeded { size: code_len, limit }.into());
        }
        let code = code.into_owned();

        let (receipt_idx, sir) = self.promise_idx_to_receipt_idx_with_sir(promise_idx)?;

        self.pay_action_base(ActionCosts::deploy_global_contract_base, sir)?;
        self.pay_action_per_byte(ActionCosts::deploy_global_contract_byte, code_len, sir)?;

        self.ext.append_action_deploy_global_contract(receipt_idx, code, mode);
        Ok(())
    }
