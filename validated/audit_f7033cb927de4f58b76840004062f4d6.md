### Title
`StackerDBListener` double-counts a signer's weight in both `total_weight_rejected` and `total_weight_approved` when a signer legitimately flips its vote from Reject to Accept - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` tallies each signer's `BlockResponse` for a proposed block into two independent counters, `total_weight_approved` and `total_weight_rejected`, guarding each counter with a *different* de-duplication set. The reject path guards on `block.responded_signers.insert(slot_id)`, while the accept path guards on `block.gathered_signatures.contains_key(&slot_id)`. Because these are two different tracking structures, a signer who first rejects and later re-evaluates and accepts the same block (a state transition explicitly allowed by the signer-side state machine, `LocallyRejected -> LocallyAccepted`) has its weight added to `total_weight_rejected` once and then *also* added to `total_weight_approved` later, without the stale rejection weight ever being removed.

### Finding Description
In `stacks-node/src/nakamoto_node/stackerdb_listener.rs`, the reject branch increments `total_weight_rejected` guarded by: [1](#0-0) 

and the accept branch increments `total_weight_approved` guarded by a different check: [2](#0-1) 

`responded_signers` is unconditionally inserted into on *both* the accept path (`block.responded_signers.insert(slot_id)` at line 465) and the reject path, but the accept-side weight addition is gated on `gathered_signatures.contains_key(&slot_id)`, not on `responded_signers`. So:

1. Signer S sends `Rejected` for block B. `responded_signers.insert(slot_id)` succeeds (first time) → `total_weight_rejected += weight(S)`.
2. Signer S later re-evaluates (per `docs/signer-flows.md`'s documented `LocallyRejected --> LocallyAccepted : re-evaluated` transition, backed by `BlockInfo::check_state` in `stacks-signer/src/signerdb.rs`) and sends `Accepted` for the same block B.
3. In the accept branch, `gathered_signatures` does **not** yet contain `slot_id` (only the reject path touched `responded_signers`, not `gathered_signatures`), so the code executes `total_weight_approved += weight(S)`.
4. `weight(S)` is now counted in both `total_weight_rejected` and `total_weight_approved` simultaneously, and `total_weight_rejected` is never decremented when the vote flips.

This breaks the invariant that a given signer's weight can only ever be attributed to one side of the tally at a time, i.e. it breaks the "aggregated-weight vs verified-accepts" equality this coordinator is supposed to maintain (`total_weight_approved + total_weight_rejected <= total_weight` per signer contribution).

### Impact Explanation
`signer_coordinator.rs::get_block_status` uses these two counters directly to decide the fate of a block proposal: [3](#0-2) 

Because the reject-check (`total_weight_rejected.saturating_add(weight_threshold) > total_weight` → `SignersRejected`) is evaluated ahead of the accept-check, a stale rejection weight that lingers after the signer has actually accepted can combine with a minority of other genuine rejecters to falsely cross the "blocking minority" line and cause the miner to abandon/rebuild a block that in reality already has (or would have) enough real accept weight. This is a liveness wedge on block production reachable purely by ordinary signer re-evaluation and StackerDB gossip (no majority collusion, no auth token, no other signer's key needed) — a single signer's natural reject→accept transition is sufficient to corrupt the miner's weight tally for that block. This matches the "aggregated-weight vs verified-accepts" equality break called out in scope, with a High-severity liveness consequence (miner wedged away from accepting an actually-signable block).

### Likelihood Explanation
The reject→accept transition is an explicitly documented, expected code path (`docs/signer-flows.md` section 2/3, `BlockInfo::check_state` in `signerdb.rs`, and exercised in `stacks-signer/src/v0/tests.rs`), not an edge case requiring malicious behavior — it happens whenever a signer initially rejects (e.g., because of a stale chain view, connectivity issue, or timeout) and then re-proposal/re-evaluation causes it to accept. Any single signer, even a well-behaved one, can trigger the double count during normal operation; no special privileges or majority control are required, only ordinary message flow through StackerDB.

### Recommendation
Use a single, consistent per-slot "final vote" bookkeeping structure that reflects only the signer's most recent decision, and adjust both counters symmetrically:
- Track each signer's latest response (accept/reject) in one map (e.g. keyed by `slot_id`), and when a new response supersedes a previous opposite response, decrement the old bucket's weight before/while incrementing the new bucket's weight.
- Alternatively, gate the accept-branch's weight addition on `!block.responded_signers.contains(&slot_id) || <was previously rejected>` and explicitly subtract from `total_weight_rejected` (and vice versa for a later reject after accept, if that transition is also possible) so a signer's weight is only ever attributed to its current vote.

### Proof of Concept
1. Node proposes block B to signer set with signer S having weight W.
2. S evaluates B and, due to a transient condition (e.g. `ConnectivityIssues`, stale chain view, or `RejectReason` that is re-evaluable), sends `BlockResponse::Rejected` for B → node's `StackerDBListener` records `total_weight_rejected += W` via `responded_signers.insert(slot_id)`.
3. The miner re-proposes/re-broadcasts B (or S re-evaluates on its own per `should_reevaluate_block`/`should_reevaluate_reject_reason`), and this time S signs and sends `BlockResponse::Accepted` for the same `signer_signature_hash`.
4. Node's `StackerDBListener` accept branch checks only `gathered_signatures.contains_key(&slot_id)` (false, since S never accepted before) and adds `total_weight_approved += W`, while `total_weight_rejected` still contains W from step 2 for the same signer S.
5. Now `total_weight_approved + total_weight_rejected` exceeds the true weight consented by the signer set, and depending on other signers' independent responses, `get_block_status` in `signer_coordinator.rs` can hit `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and reject block B (`NakamotoNodeError::SignersRejected`) even though the real, current tally of signer intents supports acceptance.
