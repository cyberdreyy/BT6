### Title
Gateway response correlation trusts only `MessageId` without validating `DonId`/`Sender`/`Receiver`, enabling response spoofing across the OutgoingConnectorHandler request/response boundary - (File: `core/capabilities/webapi/outgoing_connector_handler.go`)

### Summary
`OutgoingConnectorHandler.HandleSingleNodeRequest`/`HandleGatewayMessage` correlate an outbound gateway request with its response purely by `MessageId`. Neither the handler nor its caller (`FetcherService.Fetch`) verifies that the responding message's `DonId`, `Sender`, or `Receiver` actually correspond to the DON/gateway the original request was sent to. This mirrors the reported `fchain-contracts` bug class: an externally supplied message is accepted and used to drive privileged application logic based on a single loosely-verified correlation value (there, `validationID`/nonce; here, `MessageId`), without cross-checking it against the state of the original request.

### Finding Description
`handleSingleNodeRequest` registers a response channel keyed only by the caller-supplied `messageID` [1](#0-0) , then sends the signed request to a selected gateway.

When a message with matching method arrives back via `HandleGatewayMessage`, the code:
1. Cryptographically validates the message's own internal consistency (`ValidatedMessageFromReq` → `Message.Validate()`), which only checks field lengths/format and derives `Sender` from whichever key produced the signature — it does not check the signer against any allow-list or expected identity [2](#0-1) .
2. Looks up the response channel purely by `body.MessageId` [3](#0-2) .
3. Applies only a per-sender/global rate limit, not an identity check, before delivering the message onto the channel [4](#0-3) .

The consumer, `FetcherService.Fetch`, only calls `resp.Validate()` (the same generic format check) and logs — but never asserts — that `resp.Body.DonId` matches the DON the request targeted or that `resp.Body.Sender`/`resp.Body.Receiver` correspond to the expected gateway/node [5](#0-4) .

By contrast, the sibling node-side handler `capabilities.handler.HandleNodeMessage` explicitly enforces `msg.Body.Sender != nodeAddr` before processing [6](#0-5) , and the dummy handler does the same [7](#0-6) , showing that this class of identity check is an established pattern elsewhere in the codebase but is missing from `OutgoingConnectorHandler.HandleGatewayMessage`.

### Impact Explanation
Because correlation relies solely on `MessageId` (a value chosen/derivable by the calling workflow, e.g., a deterministic hash of URL/workflow parts as seen in test helpers), any actor able to get a well-formed, self-signed message with a colliding `MessageId` and an allowed method (`MethodWebAPITarget`, `MethodComputeAction`, `MethodWorkflowSyncer`) delivered through the same connector instance can have its payload accepted as the legitimate response for a pending outbound fetch/compute/sync request — without the recipient DON/gateway/receiver identity ever being checked. This can result in cross-request/cross-workflow response confusion: a workflow's `Fetch()` call could receive attacker-influenced payload data (e.g., spoofed HTTP fetch results or compute action results) that downstream logic in the workflow will treat as authentic, potentially affecting execution or externally-visible results derived from that data.

### Likelihood Explanation
Exploitability depends on whether an unprivileged party can produce a message with a colliding `MessageId` and a valid signature (any keypair — the signature format check does not pin the signer) that reaches this connector instance via the gateway's routing. Given `MessageId`s are workflow/caller supplied and, in some code paths, are deterministic (hash of URL + parts), collisions are plausible in normal multi-tenant DON operation, especially given no `DonId`/`Sender`/`Receiver` cross-check is enforced as a second line of defense. This raises likelihood above merely theoretical, though full exploitation requires being able to inject a message through the gateway relay path for that method.

### Recommendation
In `OutgoingConnectorHandler.HandleGatewayMessage` and `FetcherService.Fetch`, in addition to the existing `MessageId` lookup, verify that the incoming message's `DonId` matches the DON ID used for the original request, that `Receiver` (if set) matches this node's own address, and that `Sender` corresponds to an expected/authorized gateway identity for that DON — analogous to the `Sender != nodeAddr` check already used in `capabilities.handler.HandleNodeMessage`. Consider also recording the originating request's `DonId`/gateway alongside the response channel so responses can be validated against the specific request context rather than `MessageId` alone.

### Proof of Concept
1. A workflow calls `FetcherService.Fetch(ctx, messageID, req)`, which calls `HandleSingleNodeRequest` and registers a channel keyed by `messageID` [1](#0-0) .
2. Before (or instead of) the legitimate gateway response arriving, a message is delivered to `HandleGatewayMessage` with: the same `MessageId`, an allowed `Method`, a self-generated valid signature (any keypair), and arbitrary `Payload`/`DonId`/`Sender`/`Receiver` values.
3. `ValidatedMessageFromReq`/`Message.Validate()` accept it since they only check format and self-consistency of the signature, not signer identity [2](#0-1) .
4. `HandleGatewayMessage` finds the channel by `MessageId`, passes the per-sender rate limit (attacker controls the sender key so this is easy to satisfy), and delivers the attacker payload onto the channel [8](#0-7) .
5. `Fetch()` receives this message, performs only the generic `resp.Validate()` format check, and returns the attacker-controlled payload as the legitimate fetch result [9](#0-8) .

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageId, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonId) == 0 || len(m.Body.DonId) > MessageDonIdMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonId, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (d *dummyHandler) HandleNodeMessage(ctx context.Context, resp *jsonrpc.Response[json.RawMessage], nodeAddr string) error {
	var msg api.Message
	err := json.Unmarshal(*resp.Result, &msg)
	if err != nil {
		return err
	}
	msg.Body.MessageId = resp.ID
	err = msg.Validate()
	if err != nil {
		return err
	}
	if nodeAddr != msg.Body.Sender {
		return fmt.Errorf("node address %s does not match message sender %s", nodeAddr, msg.Body.Sender)
