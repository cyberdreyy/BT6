### Title
`IdleCreditVault.claimInstantWithdrawRequest` pays out receipts before the borrower funds them, letting an attacker drain buffer-period deposits - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
Analogous to the CaSS bug (a missing securing step leaves assets exposed to an actor who should not have access), `claimInstantWithdrawRequest` omits the "funding" step: it burns the user's instant-withdraw receipt and immediately transfers underlying, without verifying that the corresponding funds were actually collected via `collectInstantWithdrawFunds` (the only place `pendingInstantWithdraws` is decremented). Between `stopEpoch` and the next `startEpoch`, the strategy can hold underlying from buffer-period `deposit()` calls, and an attacker can claim their instant receipt against those funds before the borrower ever sends repayment.

### Finding Description
In `requestInstantWithdraw`, the CDO burns strategy tokens, mints an equal receipt to the user, increments `instantWithdrawsRequests[_user]` and `pendingInstantWithdraws` (`IdleCreditVault.sol:356-375`). The funds backing those receipts only arrive later: at `startEpoch`, borrower funds flow through the CDO and `collectInstantWithdrawFunds` pulls `pendingInstantWithdraws` worth of underlying into the strategy (`IdleCreditVault.sol:398-403`).

`claimInstantWithdrawRequest` contains no check that funding occurred:

```
// contracts/strategies/idle/IdleCreditVault.sol:380-393
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

It never reads or decrements `pendingInstantWithdraws`, never checks `epochNumber`/`instantWithdrawsRequestsByEpoch`, and `_transferFundedClaim` only guards `defaultRecoveryReserve` (`IdleCreditVault.sol:897-907`) — which is zero outside default. So any underlying sitting in the strategy (e.g., buffer-period deposits held by `deposit()` at `IdleCreditVault.sol:596-617` before being forwarded to the borrower) is freely spendable by a receipt holder.

The CDO wrapper `IdleCDOEpochVariant.claimInstantWithdrawRequest` adds only an `allowInstantWithdraw` flag check (`IdleCDOEpochVariant.sol:975-979`), no funding or phase check.

### Impact Explanation
Broken invariant: one receipt one payout / solvency. An attacker who is a KYC'd tranche holder:

1. During the running epoch, calls `requestInstantWithdraw` for `X` underlying (receipt minted, `pendingInstantWithdraws += X`).
2. In the buffer window after `stopEpoch` (before `startEpoch` calls `collectInstantWithdrawFunds`), other users' deposits land in the strategy via `deposit()`.
3. Attacker calls `claimInstantWithdrawRequest`; `_transferFundedClaim` transfers `X` of the depositors' underlying — up to the full strategy balance.

The stolen underlying still backs newly minted strategy tokens for the buffer depositors, so the CDO's NAV claims exceed actual assets: direct theft of up to `min(X, strategy balance)`, producing unbacked strategy tokens / insolvency of equal size.

### Likelihood Explanation
Requirements: `allowInstantWithdraw` enabled, an epoch transition with a non-empty instant queue, and at least `X` underlying deposited during the buffer window before `startEpoch`. All actors in the sequence are unprivileged; the attacker only needs to pass KYC and hold tranche tokens. No privileged misbehavior is required — the missing funded-check is entirely in the claim path.

### Recommendation
Gate `claimInstantWithdrawRequest` on funding: track funded vs. unfunded instant receipts (e.g., require `pendingInstantWithdraws` coverage via a `fundedInstantWithdraws` counter incremented only in `collectInstantWithdrawFunds`), or record per-epoch funding and only allow claims for epochs whose receipts were fully collected. Alternatively, pull the underlying atomically at request time.

### Proof of Concept
```solidity
// Foundry fork test (mainnet fork of an epoch-enabled IdleCDOEpochVariant + IdleCreditVault)
function testInstantClaimBeforeFunding() public {
    // --- running epoch ---
    // attacker (KYC'd LP) requests instant withdraw of X underlying
    vm.startPrank(attacker);
    tranche.approve(address(cdo), type(uint256).max);
    cdo.requestInstantWithdraw(X, address(tranche)); // receipt minted, pendingInstantWithdraws += X
    vm.stopPrank();

    // --- borrower/manager call stopEpoch; epoch ends, funds NOT yet sent for instant queue ---
    vm.prank(manager);
    cdo.stopEpoch();

    // --- buffer period: a new depositor deposits; underlying sits in the strategy ---
    vm.startPrank(victimLp);
    underlying.approve(address(cdo), X);
    cdo.depositAA(X); // underlying now held by IdleCreditVault awaiting startEpoch
    vm.stopPrank();

    // --- attacker claims before startEpoch / collectInstantWithdrawFunds ---
    uint256 balPre = underlying.balanceOf(attacker);
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest();
    assertEq(underlying.balanceOf(attacker) - balPre, X); // stole victim's buffer deposit
}
```

Uncertainty note: the exact ordering of `collectInstantWithdrawFunds` relative to `startEpoch` (IdleCDOEpochVariant grep results were content-truncated) should be confirmed; the vulnerability holds as long as any window exists where receipts are claimable while the strategy holds unrelated underlying, which the code structure (funding decoupled from claiming, no per-epoch funding flag) implies.
