### Title
APR0 withdraw receipt bricks `stopEpoch` when the manager sets any nonzero APR — all vault funds frozen - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
CVE-2018-2640 is an availability bug: a low-privilege input leaves the system in a state where a critical operation (query execution) hangs/crashes. The analog in idle-tranches is `prepareStopEpochWithApr0`, which hard-reverts whenever `apr0TotalPrincipal != 0` while `unscaledApr != 0`. An unprivileged KYC-passed lender can open an APR0 withdraw receipt while `unscaledApr == 0`; any subsequent legitimate APR change by the manager makes every `stopEpoch` / `stopEpochWithDuration` call revert, freezing the epoch state machine and all borrower-held and vault-held funds.

### Finding Description
In `IdleCreditVault.requestWithdraw`, when `unscaledApr == 0` and the pool is not closed, the request is routed to `_requestWithdrawApr0`, which sets `apr0Users[user].principal` and increases `apr0TotalPrincipal` [1](#0-0) [2](#0-1) .

At epoch stop, `IdleCDOEpochVariant._stopEpoch` unconditionally calls `IdleCreditVault.prepareStopEpochWithApr0` [3](#0-2) . That function reverts with `NotAllowed` if the open APR0 bucket is non-empty and `unscaledApr != 0` [4](#0-3) .

The deadlock:

1. In an APR0 vault (e.g., programmable-borrower deployments, which the docs note use APR=0, or any fixed-APR vault temporarily at 0), during the buffer phase the attacker deposits into AA/BB (passes `isWalletAllowed`) and calls `requestWithdraw`. Their receipt lands in the APR0 bucket: `apr0TotalPrincipal > 0`.
2. `startEpoch` proceeds normally; it never touches the APR0 bucket. During or before the epoch, the honest manager calls `setAprs`/`setAprsWithBuffer` with a nonzero APR (a routine operation; `setApr` only gates on `msg.sender == cdo || manager` and `maxApr`) [5](#0-4) .
3. After `epochEndDate`, `stopEpoch` reverts inside `prepareStopEpochWithApr0` — every time, since `apr0TotalPrincipal` cannot be cleared.

There is no cancellation path: the attacker cannot withdraw the receipt (claim requires `epochNumber > lastWithdrawRequest`, which only `stopEpoch` increments) [6](#0-5) , and `_clearWithdrawClaimForEpoch` only runs in default/loss-claim paths that require borrower default or a loss-adjusted stop — both unreachable because `stopEpoch` itself reverts. `restoreOperations`/`finalizeDefault` do not clear `apr0TotalPrincipal` either.

The broken invariant is liveness/solvency: a single unprivileged receipt converts the epoch state machine into a permanently un-stoppable state pending privileged intervention.

### Impact Explanation
While `stopEpoch` reverts, `isEpochRunning` stays true, deposits remain paused (`_pause()` at `startEpoch`), withdraw requests are disabled, the borrower is never asked to repay, and no lender can claim anything. Quantified impact: the entire vault TVL (all tranche NAV plus pending receipts) is frozen. Recovery requires the manager to discover the workaround — resetting `unscaledApr` to 0 via `setAprs(0, 0)` before retrying `stopEpoch` — and even then any intended APR transition for the next epoch must be deferred one full epoch. Until that governance action, freezing is indefinite; for a vault whose manager is a multisig with latency, this is a prolonged DoS of all funds, matching the CVE's availability-only impact class.

### Likelihood Explanation
Medium. It requires an APR0-configured vault (the documented programmable-borrower mode uses APR=0), a KYC-passed attacker performing a normal `requestWithdraw` during a buffer phase, and one routine honest manager APR change. No malicious privileged role, oracle manipulation, or timing precision is needed — the guard itself is the trap. The rescue path (set APR back to 0, stop, settle, then raise APR) exists, so the freeze is technically recoverable, which keeps this at the CVE's Medium severity rather than Critical.

### Recommendation
In `prepareStopEpochWithApr0`, do not revert on `unscaledApr != 0`. Settle the stale APR0 bucket instead: treat it like `_settleApr0` with zero rate — move `apr0TotalPrincipal` into claimable principal (or fold it into `withdrawsRequests`/pending basis at par) and zero `apr0TotalPrincipal` before applying the new-APR interest math. Alternatively, gate `requestWithdraw`/`_requestWithdrawApr0` so APR0 receipts can only be opened when the next epoch's APR is also committed to 0, or add a CDO-only escape to forcibly settle the bucket. Add a regression test: APR0 request → `setAprs(nonzero)` → `stopEpoch` must succeed and the receipt must remain claimable at principal.

### Proof of Concept
Foundry test sketch (fork/mainnet harness style of `test/foundry/IdleCreditVault.t.sol`):

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "../TestIdleCDOBase.sol";

contract Apr0StopEpochDoS is TestIdleCDOBase {
  // Uses an IdleCDOEpochVariant + IdleCreditVault deployed with apr = 0
  // (programmable-borrower style vault).

  function test_Apr0ReceiptBricksStopEpoch() public {
    // ---- buffer phase, unscaledApr == 0 ----
    address attacker = makeAddr("attacker");
    _kycAllow(attacker);                    // Keyring credential or keyring unset
    uint256 amount = 1e6;                   // dust-sized deposit suffices
    deal(address(underlying), attacker, amount);

    vm.startPrank(attacker);
    underlying.approve(address(cdo), amount);
    cdo.depositAA(amount);                  // or depositBB
    cdo.requestWithdraw(0, cdo.AATranche()); // full-balance request
    vm.stopPrank();

    IdleCreditVault vault = IdleCreditVault(cdo.strategy());
    assertGt(vault.apr0TotalPrincipal(), 0); // attacker's receipt parked in APR0 bucket

    // ---- honest manager sets a nonzero APR for the next epoch ----
    vm.prank(vault.manager());
    vault.setAprs(5e18, 5e18);              // routine APR update; allowed any time

    // ---- epoch runs, then end date passes ----
    _startEpochAndSkip();                   // startEpoch succeeds; warp past epochEndDate

    // ---- every stopEpoch attempt reverts: epoch can never stop ----
    vm.prank(vault.manager());
    vm.expectRevert(NotAllowed.selector);
    cdo.stopEpoch(0, 0);

    // attacker cannot unbrick it themselves: claim requires epochNumber bump
    vm.prank(attacker);
    vm.expectRevert(NotAllowed.selector);
    cdo.claimWithdrawRequest();

    // vault remains paused / epoch-running: all TVL frozen pending manager
    // discovering the setAprs(0,0) workaround
    assertTrue(cdo.isEpochRunning());
    assertTrue(cdo.paused());
  }
}
```
