### Title
Sliced `requestWithdraw` calls inflate withdraw interest against shrinking tranche NAV - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`requestWithdraw` lets any KYC'd tranche holder choose how many underlying to lock into a withdrawal receipt, and `_calcInterestWithdrawRequest` prices the projected epoch interest for that slice against the *current* saved tranche NAV (`_lastSavedNAV`). Because each accepted request immediately removes the requested principal from live NAV via `_withdrawOps`, splitting one withdrawal into many small calls makes each subsequent slice divide by a smaller `_trancheBal`, so the same requester accumulates strictly more `interest` than a single equivalent request. This is the direct analog of the UMA `updateTrackersRange` flaw: the intended behavior is one roundwise-linear accumulation against a fixed epoch NAV, but the attacker can force the accounting to be applied incrementally with an updating base, turning linear rewards into super-linear payout and making `pendingWithdraws`/`pendingWithdrawFees` exceed what the epoch's interest actually funds.

### Finding Description
In `IdleCDOEpochVariant.requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791) the projected interest for a request is computed as:

- `interest = _amount * totTrancheInterest / _trancheBal` where `_trancheBal = _lastSavedNAV(_tranche)` (contracts/IdleCDOEpochVariant.sol:856-878).
- The request then calls `creditVault.requestWithdraw(_underlyings, msg.sender, principal)` and `_withdrawOps(_amount, principal, _tranche)`, burning tranche tokens and reducing saved NAV by `principal` before any subsequent request.

If a holder owning fraction `f` of the tranche NAV submits the withdrawal in `N` slices instead of once, the per-slice denominator `B - i*x` shrinks each time while the numerator rate `totTrancheInterest` stays fixed for the epoch. The summed payout is `totTrancheInterest * x * Σ 1/(B - i*x)`, which telescopes above the fair `totTrancheInterest * f`. For example, a holder owning `B/2` split across many slices approaches `ln(2) * totTrancheInterest ≈ 0.69 * T` instead of the intended `0.5 * T` — roughly +39% over the pro-rata share — and the surplus is taken from the other tranche class via the `interestForOverUnderPerformance`/`pendingWithdrawFees` bookkeeping, not from new borrower funds.

Additionally, nothing forces the slices to belong to distinct epochs: `IdleCreditVault.requestWithdraw` (contracts/strategies/idle/IdleCreditVault.sol:243-295) happily accumulates `withdrawsRequests[user]` and `withdrawsRequestsByEpoch[user][currentEpoch]` for repeated calls, so the entire amplification can be executed in a single buffer phase. The extra `interest` inflates `_underlyings`, which inflates `pendingWithdraws` in the strategy, so at `stopEpoch` the borrower must fund receipts that exceed the interest the epoch actually generated — the same solvency invariant broken in the UMA report (payouts exceeding captured yield).

### Impact Explanation
The broken invariant is fair per-epoch interest distribution and solvency of pending withdrawals. Each excess wei of computed `interest` becomes part of the user's minted receipt (`_mint(_user, _amount)` in `IdleCreditVault.requestWithdraw`) and of `pendingWithdraws`, which `stopEpoch` sources from the borrower/strategy. The excess is drawn from the tranche-wide interest pool, i.e., stolen from other tranche holders' yield; in thin-liquidity configurations it can push `pendingWithdraws` above realizable interest plus principal, causing underfunded claims or forced borrower funding of phantom yield. The amplification factor is bounded (≈ `ln(1/f)` per epoch, so realistic gains are tens of percent of the epoch interest share, repeatable every epoch), making this a medium-severity theft of unclaimed yield rather than unbounded inflation — unlike the original exponential UMA case, Idle Tranches' NAV-based denominator keeps the bound logarithmic.

### Likelihood Explanation
Requirements: a whitelisted (`isWalletAllowed`/Keyring) tranche holder, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` open (buffer phase between epochs), and `epochDuration > 0` with a nonzero APR so `totTrancheInterest > 0`. Splitting a large request into many slices is unprivileged and cheap; the only cost is gas per call. No privileged action, default, or oracle manipulation is needed, and none of the existing guards (`_skimDonatedAssets`, `_guarded`, KYC, `_onlyIdleCDO`, loss-recovery checks) restrict the number or granularity of requests. The main limitations are that gains are bounded per epoch and fees (`_totalWithdrawFees`) shave each slice's interest.

### Recommendation
Apply epoch interest to withdraw requests round-wise, mirroring the UMA fix: snapshot `_trancheBal` (or the effective NAV) once per epoch — e.g., cache the NAV used for `_calcInterestWithdrawRequest` at the first request after `_updateAccounting` for a given epoch — and compute all subsequent slices' interest against that frozen base. Alternatively, accumulate a per-epoch requested amount per user and settle the interest once per epoch rather than per call. Add a monitoring invariant comparing `pendingWithdraws` + live NAV against `getContractValue()`/token backing after each `requestWithdraw` and `stopEpoch`.

### Proof of Concept
Fork test outline (Foundry, mainnet fork, based on `test/foundry/IdleCreditVault.t.sol` helpers):

```solidity
function testSlicedRequestWithdrawInflatesInterest() external {
    // Setup: deposit AA for attacker + other LPs so attacker owns fraction f of AA NAV.
    // Epoch 0 runs and stops normally so lastEpochApr is set and requests are allowed.
    _startEpochAndCheckPrices(0);
    vm.warp(cdoEpoch.epochEndDate() + 1);
    deal(defaultUnderlying, borrower, cdoEpoch.expectedEpochInterest());
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0); // buffer phase opens, allowAAWithdrawRequest = true

    uint256 attackerBal = IERC20(AAtranche).balanceOf(attacker);

    // Path A (control): fresh snapshot — single request of full balance
    uint256 snap = vm.snapshot();
    vm.prank(attacker);
    uint256 oneShot = cdoEpoch.requestWithdraw(attackerBal, address(AAtranche));

    vm.revertTo(snap);

    // Path B: same total requested in N small slices
    uint256 N = 64;
    uint256 slice = attackerBal / N;
    uint256 slicedTotal;
    for (uint256 i; i < N; ++i) {
        vm.prank(attacker);
        slicedTotal += cdoEpoch.requestWithdraw(slice, address(AAtranche));
    }
    vm.prank(attacker);
    slicedTotal += cdoEpoch.requestWithdraw(attackerBal - slice * N, address(AAtranche));

    // Sliced payout strictly exceeds one-shot payout for the same principal
    assertGt(slicedTotal, oneShot, "sliced withdraw requests over-accrue epoch interest");
    // And pendingWithdraws is inflated by the same surplus the borrower must fund
    assertGt(
        IdleCreditVault(address(strategy)).pendingWithdraws(),
        oneShot,
        "pendingWithdraws exceed single-request baseline"
    );
}
```

Note: verification was limited by iteration budget — the exact extra payout depends on `_withdrawOps` reducing `_lastSavedNAV(_tranche)` synchronously (consistent with `_calcInterestWithdrawRequest` reading the saved NAV each call) and on `_totalWithdrawFees` still leaving net amplification. If `_lastSavedNAV` is only updated in `_updateAccounting`/`stopEpoch` and not decremented by `_withdrawOps`, the slicing vector disappears and the closest remaining analog would be the APR0 `apr0RateByEpoch` accrual, which already accrues exactly once per epoch and is guarded by `testApr0WithdrawRollsAcrossEpochsNoDoubleAccrual`.
