### Title
Malicious ERC4626 vault liquidity drain forces retryable `stopEpoch` reverts, freezing all LP funds — (`contracts/strategies/idle/ProgrammableBorrower.sol`)

### Summary
The Hermes bug is "attacker-controlled configuration injected into a trusted execution path causes unintended behavior." The credit-vault analog is `ProgrammableBorrower.onStopEpoch`: an unprivileged user of the programmable borrower's ERC4626 vault (an allowed attacker class) can drain the vault's idle liquidity so that `vault.withdraw` reverts inside the privileged `stopEpoch` flow, making epoch settlement permanently retryable-but-always-failing and freezing every LP's funds.

### Finding Description
During `IdleCDOEpochVariant._stopEpoch`, a programmable-borrower deployment calls `IProgrammableBorrower(_borrower()).onStopEpoch(_amountToPullFromBorrower + _pendingWithdraws, ...)`. [1](#0-0) 

Inside `onStopEpoch`, when the borrower contract's on-hand underlyings do not cover `_amountRequired`, it computes `shortfall` and:

- returns `true` when `shortfall > _currentVaultAssets()` (insolvency → later `transferFrom` fails → real default path), but
- otherwise calls `vault.withdraw(shortfall, ...)` and **reverts with `StopEpochVaultLiquidityUnavailable`** if the ERC4626 withdrawal fails. [2](#0-1) 

The comment in `IdleCDOEpochVariant` explicitly says "Hook reverts bubble so transient ERC4626 liquidity failures can be retried" [3](#0-2) . This means vault `maxWithdraw`/`withdraw` reverting — an external condition fully controllable by a third-party vault depositor — hard-blocks `stopEpoch`. While `isEpochRunning` is still true, `allowAAWithdrawRequest`/`allowBBWithdrawRequest` were set `false` at `startEpoch` [4](#0-3) , deposits are paused, and `unpause` is blocked by `_beforeUnpause` [5](#0-4) . No LP can exit until the epoch stops.

An attacker who is a large depositor in the shared MetaMorpho/ERC4626 vault can redeem (or keep redeemed) the vault's idle liquid assets right before the manager's `stopEpoch` call and keep them out, at essentially zero cost (the funds remain theirs; they only forgo vault yield). Every subsequent `stopEpoch` reverts in `onStopEpoch` because `vault.withdraw(shortfall)` exceeds `maxWithdraw`. The epoch cannot stop, so:

- pending withdraw receipts are never funded (funds can only be pulled at stop),
- tranche holders cannot exit (requests disabled during a running epoch, no stop → no buffer → no claims),
- the pool sits in limbo indefinitely rather than defaulting, because `shortfall <= _currentVaultAssets()` keeps taking the revert branch instead of the `return true` (default) branch — shares still economically cover the shortfall, so the honest borrower is neither allowed to settle nor defaulted.

This is the "injected config poisons a trusted subprocess" pattern: external, attacker-influenced state (vault idle liquidity — the analog of `.git/config`) hijacks the privileged `stopEpoch` routine into a failure mode that honest privileged roles (manager/owner calling `stopEpoch`, honest borrower repaying) cannot work around. `_skimDonatedAssets`, the `shortfall > _currentVaultAssets()` coverage check, and the honest borrower repaying do not help — the revert happens before `transferFrom` is even attempted.

### Impact Explanation
Temporary freezing of the entire pool's funds: all AA/BB tranche holders' principal plus accrued interest (the full `getContractValue()`, e.g. all deposited USDC) is locked for as long as the attacker keeps vault liquidity below the required `shortfall`. The attacker can repeat the drain each time liquidity returns (vault borrowers repay, new depositors enter), extending the freeze indefinitely for the cost of gas and foregone yield on the drained amount. Funds are not stolen, but the freeze can persist far beyond `epochEndDate`, and LP exit rights are entirely suspended.

### Likelihood Explanation
Requires only a programmable-borrower deployment (`isProgrammableBorrower == true`, which forces minted-interest mode where `_amountToPullFromBorrower` includes pending withdraws) and a shared ERC4626 vault whose idle liquidity a whale/depositor can withdraw — a normal property of MetaMorpho-style vaults where idle liquidity fluctuates. The attacker needs no privileged role, no KYC, and no capital lockup; on a popular shared vault they may not even need to act — organic liquidity squeezes trigger the same freeze. The only mitigation is hoping liquidity returns before LPs suffer, and `setVault` cannot rescue the situation since it reverts while shares remain in the old vault (`vault.balanceOf != 0`) and epoch accounting cannot be cleared without stopping. [6](#0-5) 

### Recommendation
Decouple epoch settlement from vault liquidity timing:

- On `vault.withdraw` failure inside `onStopEpoch`, do not revert. Instead return a status (or withdraw `vault.maxWithdraw(...)` partially) and let `IdleCDO` attempt `transferFrom` for whatever is on hand; shortfall can be retried or handled through the existing default path rather than hard-blocking the state machine.
- Alternatively, add a permissioned/manager fallback in `IdleCDOEpochVariant` that can complete `stopEpoch` with reduced recovered cash (treating the unrecovered portion via `previewLossAdjustedWithdrawFunds`/`_lossAmount`) after a grace period, so external vault liquidity cannot hold the epoch state machine hostage.
- If retryable failure is intentional, bound it: track consecutive failures or a deadline past which the pool routes into `_handleBorrowerDefault` so LP exit is guaranteed.

### Proof of Concept
```solidity
// test/foundry/ProgrammableBorrowerVaultLiquidityGrief.t.sol
// Fork test against the live MetaMorpho vault used by ProgrammableBorrowerCreditVault.t.sol
function testVaultLiquidityDrainFreezesStopEpoch() external {
    uint256 amount = 10_000 * oneScale; // USDC scale
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true); // required for programmable mode

    idleCDO.depositAA(amount);
    _startEpochAndCheckPrices(0); // PB deposits all on-hand assets into the ERC4626 vault

    // LP requests a normal withdraw during buffer next epoch; or pendingWithdraws > 0
    // so onStopEpoch must pull cash: _amountToPullFromBorrower + _pendingWithdraws > onHand.

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // ATTACKER: large depositor in the shared ERC4626 vault redeems all idle liquidity.
    address vaultUser = makeAddr("vaultWhale");
    uint256 idle = underlying.balanceOf(vaultAddress); // or vault.maxWithdraw per share
    deal(vaultAddress, vaultUser, morphoVault.convertToShares(idle)); // give attacker shares
    vm.prank(vaultUser);
    morphoVault.redeem(morphoVault.balanceOf(vaultUser), vaultUser, vaultUser);
    // Now vault.maxWithdraw(programmableBorrower) < shortfall even though
    // convertToAssets(shares) >= shortfall economically.

    // Honest manager tries to stop the epoch; every attempt reverts inside the hook.
    vm.prank(manager);
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    cdoEpoch.stopEpoch(0, 0);

    // Epoch is stuck: still running, no default, LP exits remain disabled.
    assertTrue(cdoEpoch.isEpochRunning());
    assertFalse(cdoEpoch.defaulted());
    assertFalse(cdoEpoch.allowAAWithdrawRequest());
    // LPs cannot withdraw, unpause reverts, setVault/setBorrower revert (epoch active / shares > 0).
    // As long as the attacker keeps vault liquidity drained (or it stays thin organically),
    // all pool funds remain frozen past epochEndDate.
}
```

The revert originates at `ProgrammableBorrower.sol:246-252` (`try vault.withdraw ... catch { revert StopEpochVaultLiquidityUnavailable(); }`), propagates through `onStopEpoch` into `IdleCDOEpochVariant._stopEpoch`, and leaves the epoch in a permanently running, non-defaulted, non-exitable state.
