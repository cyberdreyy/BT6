### Title
Commitment-agnostic cache key allows monotonic slot regression in `LargestAccountsCache` - ([File: rpc/src/rpc_cache.rs])

### Summary
`LargestAccountsCache::set_largest_accounts` unconditionally overwrites the cached entry for a given filter with the newly supplied slot, with no check that the new slot is greater than or equal to the previously cached slot. Because the cache is keyed only by `Option<RpcLargestAccountsFilter>` and not by commitment level, a client can cache a high slot under one commitment level and then overwrite it with a lower slot obtained under a different (lower) commitment level, causing subsequent reads within the TTL window to return the stale, regressed slot regardless of which commitment was requested.

### Finding Description
The cache struct stores entries in `cache: HashMap<Option<RpcLargestAccountsFilter>, LargestAccountsCacheValue>` [1](#0-0) . The key type is only the `RpcLargestAccountsFilter` (`Circulating`/`NonCirculating`/`None`); nothing about the commitment level used to select the bank for that particular `getLargestAccounts` call is part of the key.

`set_largest_accounts` performs a last-write-wins `HashMap::insert` with no ordering/monotonicity check against the existing entry's `slot` field: [2](#0-1) 

`get_largest_accounts` only checks TTL expiry (`elapsed < Duration::from_secs(self.duration)`) before returning `(value.slot, value.accounts.clone())`; it performs no validation that the returned slot is consistent with, or at least not older than, what was previously served for the same filter key: [3](#0-2) 

Given the call sequence in the question:
1. `set_largest_accounts(filter, slot=100, ...)` — e.g., populated by a `getLargestAccounts` call at `finalized` commitment, caching slot 100.
2. `set_largest_accounts(filter, slot=40, ...)` — the same client issues a second `getLargestAccounts` call with the same filter but `processed` commitment (or any commitment resolving to an earlier/rolled-back bank), before the TTL expires. Since the cache key does not encode commitment, this overwrites the same `HashMap` entry, replacing slot 100 with slot 40.
3. `get_largest_accounts(filter)` — a third call (potentially even requesting `finalized` again) within the TTL window returns `(40, accounts)`, i.e., a stale/regressed slot value that no longer reflects the highest/most recent finalized state that had already been cached and could legitimately be expected to still be valid.

No component of the code path re-validates monotonicity or ties the cached slot to the commitment level that produced it, so the invariant "returned data belongs to the requested commitment level and is never derived from unrooted/superseded slots" is not enforced by this cache.

### Impact Explanation
This causes the RPC endpoint to return `getLargestAccounts` responses with an incorrect/regressed `slot` field (and potentially stale balances) to any client that hits the cache within the TTL, independent of the commitment level requested by that later caller. This falls under "wrong-slot/fork/account data returned" from a single, unprivileged client using only ordinary sequential JSON-RPC calls — no concurrency, elevated privileges, or off-limits techniques are required.

### Likelihood Explanation
The attack requires only two sequential `getLargestAccounts` calls with the same `filter` parameter but different commitment levels, issued by a single unprivileged client within the cache TTL (`duration`), followed by a third read. This is trivially reproducible and needs no special preconditions beyond normal RPC availability.

### Recommendation
Include the commitment level in the cache key (e.g., `(Option<RpcLargestAccountsFilter>, CommitmentLevel)`), or alternatively enforce monotonicity in `set_largest_accounts` by only overwriting the entry when `slot >= existing.slot` for the same key (and never allowing entries from a lower commitment level to overwrite ones from a higher commitment level).

### Proof of Concept
```rust
#[test]
fn test_lower_slot_overwrites_higher_slot_within_ttl() {
    let mut cache = LargestAccountsCache::new(30); // 30s TTL, plenty of time for two calls
    let filter = Some(RpcLargestAccountsFilter::Circulating);
    let accounts: Vec<RpcAccountBalance> = Vec::new();

    // Simulates a getLargestAccounts(finalized) response caching slot 100.
    cache.set_largest_accounts(&filter, 100, &accounts);
    assert_eq!(cache.get_largest_accounts(&filter).unwrap().0, 100);

    // Simulates a subsequent getLargestAccounts(processed) response with a lower slot,
    // overwriting the same cache entry because the key does not include commitment.
    cache.set_largest_accounts(&filter, 40, &accounts);

    // A third read within the TTL window returns the regressed slot instead of
    // preserving/erroring on the monotonicity violation.
    let (slot, _) = cache.get_largest_accounts(&filter).unwrap();
    assert_eq!(slot, 40, "cache slot regressed from 100 to 40 within the same TTL window");
}
```
Expected assertion failure under a fixed invariant: the second `set_largest_accounts` call should either be rejected (slot < cached slot) or keyed separately by commitment, so the final read never returns a slot lower than one already cached and unexpired for the same filter.

    pub(crate) fn get_largest_accounts(
        &self,
        filter: &Option<RpcLargestAccountsFilter>,
    ) -> Option<(u64, Vec<RpcAccountBalance>)> {
        self.cache.get(filter).and_then(|value| {
            if let Ok(elapsed) = value.cached_time.elapsed()
                && elapsed < Duration::from_secs(self.duration)
            {
                return Some((value.slot, value.accounts.clone()));
            }
            None
        })
    }
