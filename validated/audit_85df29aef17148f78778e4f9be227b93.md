### Title
Stale write-off requests can be force-filled after tranche value changes without lender confirmation - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow` lets any account permanently execute a lender’s previously created write-off request at its fixed nominal underlying amount. A request remains executable after the epoch ends and after tranche NAV has changed, even though creation is only permitted while an epoch is running. There is no expiry, epoch binding, borrower restriction, or final lender confirmation before the escrow transfers the escrowed tranche tokens.

### Finding Description
`createWriteOffRequest` escrows the caller’s tranche tokens and stores a fixed `underlyingsRequested` amount while the epoch is running.

`fullfillWriteOffRequest` can later be called by any wallet. It only checks that:

- the request exists;
- `_tranches == currentRequest.tranches`;
- `_underlyings >= currentRequest.underlyings`.

It does not verify that the request was created in the current epoch, that the tranche’s current value remains below the requested payout, or that the lender still accepts the original terms. Once a request remains pending through an epoch transition and accrued interest raises the tranche’s redemption value, an unprivileged buyer can pay the stale request amount, receive the appreciated tranche tokens, and capture the difference. The lender cannot prevent this except by winning a cancellation race before the buyer’s transaction.

The relevant flow is:

```solidity
userRequests[msg.sender] = WriteOffRequest({
  tranches: currentRequest.tranches + amount,
  underlyings: currentRequest.underlyings + underlyingsRequested
});
```

followed by unrestricted execution:

```solidity
if (currentRequest.tranches != _tranches || _underlyings < currentRequest.underlyings) {
  revert WrongRequest();
}

delete userRequests[_user];
underlyingToken.safeTransferFrom(msg.sender, address(this), _underlyings);
underlyingToken.safeTransfer(_user, _underlyings - _totFee);
IERC20Detailed(tranche).safeTransfer(msg.sender, _tranches);
```

The stored request therefore functions as an indefinite, stale-priced sell order even though the protocol treats write-off requests as epoch-specific actions.

### Impact Explanation
An attacker can force a lender to sell appreciated tranche tokens at an outdated fixed price.

For example:

1. A lender escrows `10,000` AA tranche tokens and requests `10,000` underlying.
2. The epoch completes and interest raises the tranche value to `1.10` underlying per tranche token.
3. The attacker pays only `10,000` underlying.
4. The attacker receives tranche tokens with a current claim value of `11,000` underlying.
5. The lender loses approximately `1,000` underlying in current claim value, less any applicable fees or withdrawal haircut.

This is a direct forced asset sale at stale terms. The attacker does not need a privileged role, Keyring approval, borrower status, or lender approval at fulfillment time.

### Likelihood Explanation
Likelihood is moderate.

The attack requires a lender to leave a write-off request pending while tranche value appreciates. This can naturally happen when a lender expects the intended borrower to negotiate fulfillment but the request remains unfilled through `stopEpoch`. At that point any EOA can monitor `userRequests`, compare each fixed request amount with current tranche value, and atomically fulfill profitable requests.

The existing controls do not prevent it:

- `nonReentrant` only prevents reentrancy;
- `WrongRequest` prevents underpayment or changing the tranche amount;
- `deleteWriteOffRequest` gives the lender a cancellation path but does not prevent a front-run or stale fill;
- restricting creation to `isEpochRunning` does not restrict fulfillment to the same epoch;
- the borrower check is absent by design, so any buyer can execute the request.

### Recommendation
Bind each request to an explicit validity scope and require fresh lender consent if epoch state or tranche value changes.

At minimum:

- store the creation epoch or `epochNumber`;
- allow fulfillment only while `isEpochRunning` and only during the same epoch in which the request was created; or
- add a request expiry timestamp; or
- require the fulfiller to submit a lender-signed quote containing the tranche amount, underlying amount, deadline, nonce, and chain/contract identifiers.

A two-step fulfillment is also possible: the buyer commits funds, then the lender calls `confirmWriteOffRequest` to release tranche tokens, with an automatic refund if confirmation does not occur before expiry.

### Proof of Concept
The following Foundry test can be added to `test/foundry/IdleCreditVaultWriteOffEscrow.t.sol`, which already deploys `escrow`, `cdoEpoch`, `tranche`, `underlying`, `borrower`, and `LP`:

```solidity
function testStaleWriteOffRequestCanBeFilledAfterEpochWithoutFreshConsent() external {
    uint256 requestedTranches = 10_000e18;
    uint256 requestedUnderlyings = 10_000e6;
    address attacker = makeAddr("attacker");

    // LP creates the request during the running epoch.
    vm.prank(LP);
    escrow.createWriteOffRequest(requestedTranches, requestedUnderlyings);

    // Honest protocol actors complete the epoch and fund normal obligations.
    _stopCurrentEpoch();

    // The request remains executable even though creation is no longer possible
    // and the tranche value has changed with post-epoch accounting.
    vm.expectRevert(abi.encodeWithSelector(EpochNotRunning.selector));
    vm.prank(LP);
    escrow.createWriteOffRequest(1e18, 1e6);

    deal(address(underlying), attacker, requestedUnderlyings);

    uint256 lpUnderlyingBefore = underlying.balanceOf(LP);
    uint256 attackerTranchesBefore = tranche.balanceOf(attacker);

    vm.startPrank(attacker);
    underlying.approve(address(escrow), requestedUnderlyings);
    escrow.fullfillWriteOffRequest(
        LP,
        requestedTranches,
        requestedUnderlyings
    );
    vm.stopPrank();

    uint256 fee =
        requestedUnderlyings * escrow.exitFee() / escrow.FULL_VALUE();

    assertEq(
        underlying.balanceOf(LP) - lpUnderlyingBefore,
        requestedUnderlyings - fee
    );
    assertEq(
        tranche.balanceOf(attacker) - attackerTranchesBefore,
        requestedTranches
    );

    (uint256 remainingTranches, uint256 remainingUnderlyings) =
        escrow.userRequests(LP);
    assertEq(remainingTranches, 0);
    assertEq(remainingUnderlyings, 0);
}
```

The exploit is the state transition itself: the attacker obtains all escrowed tranche tokens for the stale request amount after the epoch boundary, without any post-epoch confirmation from `LP`.
