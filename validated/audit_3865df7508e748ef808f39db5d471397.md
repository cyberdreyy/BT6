### Title
Zip cache extraction lacks path-traversal/chroot check present in tarzstd extractor - ([File: helpers/archives/zip_extract.go])

### Summary
`CacheExtractorCommand.Execute` (`commands/helpers/cache_extractor.go`) resolves the extraction directory via `os.Getwd()` and passes it to `archive.NewExtractor(format, f, size, wd)`, but for the `zip`/`zipzstd` formats (`ziplegacy.NewExtractor` and `fastzip.NewExtractor`) the `dir`/`wd` parameter is effectively unused for path confinement. The underlying `archives.ExtractZipArchive` → `extractZipFile`/`extractZipFileEntry`/`extractZipSymlinkEntry` write directly to `file.Name` with no `filepath.Join(dir, ...)` + chroot validation, unlike `tarzstd.extractor.Extract`, which explicitly rejects any resolved path outside `e.dir` [1](#0-0) .

### Finding Description
The reachable call path is: `RunSingleCommand.processBuild` → `Build.Run` → shell-generated script invokes `gitlab-runner cache-extractor --file <cache.zip>` → `CacheExtractorCommand.Execute` [2](#0-1)  → `archive.NewExtractor(format, f, size, wd)` → for zip formats, `ziplegacy.extractor.Extract` [3](#0-2)  or `fastzip.extractor.Extract` [4](#0-3) .

Critically, `ziplegacy.extractor.Extract` calls `archives.ExtractZipArchive(zr)` and **never passes `e.dir` into the extraction logic at all** [3](#0-2) . Inside, `extractZipFile` writes using the raw `file.Name` from the zip header with no path validation: [5](#0-4) 
There is no `filepath.Join(dir, ...)`, no `filepath.Abs`, and no prefix check comparable to the tarzstd extractor's chroot check [6](#0-5) . A `file.Name` of `../../etc/cron.d/x` or an absolute path would be passed straight to `os.MkdirAll(filepath.Dir(file.Name), ...)` and `os.OpenFile(file.Name, ...)`, writing outside the intended cache/build root. `extractZipSymlinkEntry` similarly calls `os.Symlink(string(data), file.Name)` with no target validation, permitting a symlink at an attacker-controlled path pointing anywhere on the filesystem.

The `fastzip` extractor delegates directly to the third-party `saracen/fastzip` library `fastzip.NewExtractorFromReader(...).Extract(ctx)` [7](#0-6) ; that library's own internal path handling was not verifiable in this repository's index, so whether it applies its own confinement could not be confirmed here — this is a genuine gap in verification, not a claim of safety or unsafety for that path.

Because cache extraction runs unprivileged in the job's own shell/executor context (not as root, and confined by whatever filesystem permissions the job process already has), the write succeeds only insofar as the job's own process has write permission to the target path. This limits the practical impact to paths writable by the job user/container — but within that constraint, it still breaks the invariant that "extracted cache entries must remain confined to `wd`" for a shared/poisoned cache object.

### Impact Explanation
A cache object retrieved under an attacker-influenced or colliding `CI_CACHE_KEY` and extracted via the legacy `zip` (and potentially `zipzstd`) format can write files or symlinks outside the job's `CacheDir`/`BuildDir`, anywhere the job process has filesystem write permission (e.g., other paths inside the same shared runner host/container, other project checkouts under the same runner user in `shell`/`custom` executors, or shared volumes in some executor configurations). This is a cross-cache/cross-project file-write escape confined to the extraction step, matching the "file write outside build root" scoped impact.

### Likelihood Explanation
Requires: (1) a shared/distributed cache backend where cache keys can collide or be predicted across projects/pipelines, and (2) the ability to place a crafted `.zip` object under that key (e.g., by running a job in a project that shares the cache key/prefix and uploading a malicious cache archive). Both preconditions are describable as attacker-controlled inputs (job-controlled `cacheOptions.Key`/`CI_CACHE_KEY`) rather than admin/leaked-credential compromise, matching the question's threat model. Given those preconditions, exploitation is deterministic and repeatable — no timing races or privilege escalation beyond what the job process already has.

### Recommendation
Add the same chroot/path-confinement check used in `tarzstd.extractor.Extract` to the zip extraction path: resolve each `file.Name` against the target `dir` (e.g., `filepath.Abs(filepath.Join(dir, file.Name))`) and reject entries whose resolved path does not have `dir` as a prefix, for both regular/directory entries and symlink targets, before performing any `os.Mkdir`/`os.OpenFile`/`os.Symlink`/`os.Remove` operations. This requires threading the `dir` parameter through `ExtractZipArchive`/`extractZipFile`/`extractZipSymlinkEntry`/`extractZipFileEntry` in `helpers/archives/zip_extract.go`, and auditing whether `saracen/fastzip` already performs equivalent validation (if not, apply the same fix or switch fastzip usage to write into a validated subdirectory).

### Proof of Concept
Go unit test in `helpers/archives` (mirroring existing zip test structure):
1. Build an in-memory `*zip.Reader` containing a single entry with `Name = "../../../tmp/pwned"` (and a second variant with an absolute path `/tmp/pwned2`).
2. Run in a temp working directory `wd` (e.g., `t.TempDir()`), `chdir` into a subdirectory of `wd` to simulate the cache root, then call `archives.ExtractZipArchive(zr)`.
3. Assert that no file exists at `/tmp/pwned` / `/tmp/pwned2` outside `wd`, and/or assert that `ExtractZipArchive` returns/logs an error rejecting the entry (currently it does not — the test should fail against current code, demonstrating the bug).
4. As a companion, add a fuzz test `FuzzExtractZipFile` feeding random `file.Name` seeds including `../`, absolute paths, and symlink entries, asserting all resulting file operations remain rooted under the extraction directory — analogous to the existing prefix check in `tarzstd_extractor.go` lines 62-63.

```go
func (c *CacheExtractorCommand) Execute(cliContext *cli.Context) {
	log.SetRunnerFormatter()

	c.normalizeExtractorArgs()
	if err := validateCacheTransferTuning(c.TransferBufferSize, c.ChunkSize, c.Concurrency); err != nil {
		logrus.Fatalln(err)
	}

	wd, err := os.Getwd()
	if err != nil {
		logrus.Fatalln("Unable to get working directory")
	}

	if c.File == "" {
		warningln("Missing cache file")
	}

	if c.URL != "" || c.GoCloudURL != "" {
		err := c.doRetry(c.download)
		if err != nil {
			warningln(err)
		}
	} else {
		logrus.Infoln(
			"No URL provided, cache will not be downloaded from shared cache server. " +
				"Instead a local version of cache will be extracted.")
	}

	f, size, format, err := openArchive(c.File)
	if os.IsNotExist(err) {
		warningln("Cache file does not exist")
	}
	if err != nil {
		logrus.Fatalln(err)
	}
	defer f.Close()

	extractor, err := archive.NewExtractor(format, f, size, wd)
	if err != nil {
		logrus.Fatalln(err)
	}

	err = extractor.Extract(context.Background())
	if err != nil {
		logrus.Fatalln(err)
	}
```

```go
func extractZipFileEntry(file *zip.File) (err error) {
	var out *os.File
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	// Remove file before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	out, err = os.OpenFile(file.Name, os.O_WRONLY|os.O_CREATE|os.O_TRUNC, file.Mode().Perm())
	if err != nil {
		return err
	}
	defer func() { _ = out.Close() }()
	_, err = io.Copy(out, in)

	return
}
```
