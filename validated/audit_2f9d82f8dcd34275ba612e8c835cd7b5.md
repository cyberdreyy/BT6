### Title
Stale confirmations from removed multisig members still count toward `num_confirmations` threshold - ([File: multisig/src/lib.rs])

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` implement a k-of-n confirmation scheme where a `MultiSigRequest` executes once `confirmations.len() + 1 >= num_confirmations`. When a member/key is removed via `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), the contract only purges *requests that were created by* that key/member; it never scans the `confirmations` map to strip that key's/member's prior confirmations from *other* pending requests that they merely confirmed. This breaks the binding "confirmations counted == live members," letting a request execute using a confirmation from a party who is no longer a member of the multisig, effectively executing below the intended live threshold.

### Finding Description
In `execute_request`, the `DeleteKey` branch removes only the requests whose `signer_pk` equals the deleted key, and clears `num_requests_pk` for that key: [1](#0-0) 

It never iterates over the `confirmations: UnorderedMap<RequestId, HashSet<PublicKey>>` map to remove the deleted key from confirmation sets of requests that were *created by other keys* but *confirmed* by the key being removed.

`confirm()` counts confirmations purely from this map, without re-validating that every entry in the set still corresponds to a currently-valid access key/member: [2](#0-1) 

Consider `num_confirmations = 2` with keys `A`, `B`, `C`:
1. `B` creates request `R` (e.g., a `Transfer`). `A` calls `confirm(R)` → `confirmations = {A}` (1 of 2).
2. The group later decides to remove `A` (e.g., compromised or departing signer) via a separate, properly-confirmed `DeleteKey{public_key: A}` request. `execute_request` runs the `DeleteKey` branch: it removes any *requests* created by `A`, but request `R` was created by `B`, so it is untouched — `A`'s confirmation entry in `confirmations[R]` survives, and `promise.delete_key(A)` only removes `A`'s on-chain access key.
3. After `A`'s key is deleted, `C` calls `confirm(R)`. `confirmations.len()` is still `1` (containing stale `A`), so `1 + 1 >= 2` is satisfied and `R` executes — funded and authorized by only one currently-live signer (`C`), plus a defunct confirmation from `A`.

The same pattern exists in `multisig2/src/lib.rs`: `DeleteMember`/`delete_member` removes the member from the `members` set and any requests they authored, but does not scrub `confirmations` entries they left on requests created by other members: [3](#0-2) [4](#0-3) 

This is the precise "confirmations counted versus live members" custody binding called out in the rules: the equality `len(confirmations[R]) == |{live members who confirmed R}|` is violated once any confirming member/key is removed after confirming but before the request reaches threshold.

### Impact Explanation
A `MultiSigRequest` (e.g., a `Transfer` of the multisig's NEAR, an `AddKey`/`AddFullAccessKey`, or a `DeployContract`) can be executed with fewer *live* confirmations than the configured `num_confirmations`, because a stale confirmation from a removed signer continues to count. This directly matches the Critical impact category "a multisig request executed below threshold" — funds can be moved, or the account's authority structure (keys/members) modified, without the intended number of currently-authorized parties agreeing.

### Likelihood Explanation
This requires no external attacker key compromise or foundation privilege — it is a natural consequence of ordinary multisig operations: (a) a request is created and partially confirmed, (b) a signer is later removed for entirely legitimate reasons (key rotation, offboarding), and (c) the stale, pending request is confirmed afterward. Any remaining signer (malicious or not fully aware of the stale confirmation) can complete the confirmation and trigger execution below the intended threshold. Given that key rotation/removal is an expected multisig operation and pending requests can persist (no forced expiry beyond the 15-minute delete cooldown), this is readily reachable in normal operation.

### Recommendation
When executing `DeleteKey` (`multisig`) or `DeleteMember` (`multisig2`), iterate over all entries in `confirmations` and remove the deleted key/member from every confirmation set, not just requests they authored. Alternatively, when counting confirmations in `confirm()`, filter the stored confirmation set against the currently valid set of members/keys before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig` contract with `num_confirmations = 2` and access keys `A`, `B`, `C`.
2. As `B`, call `add_request({receiver_id: <victim/self>, actions: [Transfer{amount}]})` → `request_id = R` (unconfirmed).
3. As `A`, call `confirm(R)` → `confirmations[R] = {A}` (1/2, not yet executed).
4. Separately, create and fully confirm a `DeleteKey{public_key: A}` request (executes via `execute_request`), removing `A`'s on-chain access key. Note `R` is untouched because `r.signer_pk == B != A` in the `DeleteKey` filter (`multisig/src/lib.rs:202-207`).
5. As `C`, call `confirm(R)`. `confirmations[R].len() == 1` (stale `A`) `+ 1 (C) == 2 >= num_confirmations`, so `execute_request` runs the `Transfer`, moving funds authorized effectively by only one live signer (`C`) instead of two.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
