### Title
Metering `Deduct` earmarks a full credit balance slice for a capability call but never restores it when the call fails, causing unfair, permanent balance loss - ([File: core/services/workflows/v2/capability_executor.go])

### Summary
In `ExecutionHelper.callCapability`, the metering system deducts (earmarks) a chunk of the workflow's local credit balance *before* the capability actually executes, based only on a derived maximum spend (available balance divided by open concurrent call slots), not the real cost of the call. If the capability execution subsequently fails, `Settle` — the only code path that reconciles the earmark against real usage — is never invoked, so the earmarked credits are never returned to the balance.

### Finding Description
`meterReport.Deduct` is called with `metering.ByDerivedAvailability(...)`, which computes a spend limit from `getMaxSpendForInvocation` (available local balance divided by concurrent call slots, capped by any user limit) and immediately subtracts that amount from the report's local balance via `r.balance.Minus(limit.Decimal)`. [1](#0-0) [2](#0-1) 

The capability is then executed: [3](#0-2) 

Only in the success path (`err == nil`) is `meterReport.Settle(meteringRef, capResp.Metadata)` called, which reconciles the actual reported spend against the earmark and returns any unused credits to `r.balance`: [4](#0-3) 

On any error path — capability-not-found, user error, or system error — the function returns early without ever calling `Settle`: [5](#0-4) 

`Report.Deduct`/`ByDerivedAvailability` unconditionally debit `r.balance` at call time, and `Report.Settle` is the sole mechanism that gives back unspent earmarked credits: [6](#0-5) [7](#0-6) 

This mirrors the Kakarot `handle_l1_message` bug class: a coarse, upfront "max fee" charge is deducted from the payer's balance before the actual operation completes, and that debit is not corrected/refunded when the operation does not go through to a successful, chargeable conclusion — unfairly depleting the payer's balance for work that was never actually billed.

### Impact Explanation
Every failed capability call (e.g. a transient system error, a capability returning a user error due to bad input, a timeout via `CapabilityCallTime`, or any non-nil error from `capability.Execute`) permanently consumes a slice of the workflow's local credit balance equal to `availableBalance / openConcurrentCallSlots` (or the user-supplied spend limit, if lower), with no correction. Because `getMaxSpendForInvocation` derives its limit from a live division of remaining balance, repeated failures (which an unprivileged workflow owner can trigger merely by invoking a capability with parameters that cause user errors, or by capabilities that are flaky/rate-limited) will progressively and unfairly drain the local balance, causing legitimate subsequent capability calls in the same execution to be denied for "insufficient funding" even though no real spend was ever billed by the capability DON. This is a fund-accounting integrity bug reachable by a normal (non-privileged) workflow author submitting workflow executions, and it results in unwarranted denial of otherwise well-funded operations.

### Likelihood Explanation
Any capability invocation that errors before returning a metering-bearing response will trigger this: user errors are a normal, frequent occurrence (bad payload, permission errors, target-service errors, etc.) and require no special access — a standard workflow author can reliably invoke this path with everyday malformed or edge-case requests. The concurrent-call-slot-based earmark division also means the amount at risk per failure can be a meaningful fraction of the total remaining execution budget, especially late in an execution when few concurrent slots remain open.

### Recommendation
Ensure the earmarked amount from `Deduct` is always reconciled back to the balance regardless of the capability execution outcome — e.g., wrap the `Deduct`/`Execute` sequence with a `defer`/`finally` that calls `Settle` (with zero/failure metering data) on any early return, or add an explicit `Release`/`Refund` method on `Report` that restores the un-settled `step.Deduction` amount to `r.balance` on error before returning from `callCapability`. Any capability failure that doesn't produce billable `ResponseMetadata.Metering` should refund the full earmarked amount rather than leaving it permanently subtracted.

### Proof of Concept
1. Workflow with `openConcurrentCallSlots = 1` and no explicit user spend limit calls a capability via `CallCapability`.
2. `ByDerivedAvailability` computes `spendLimit = r.balance / 1` (essentially the entire remaining balance) and immediately does `r.balance.Minus(spendLimit)`, per `metering.go` lines 360-377.
3. The capability's `Execute` call returns a user error (e.g., invalid payload) — a condition fully controllable by the unprivileged workflow author.
4. `callCapability` hits the `err != nil` branch (lines 263-284 in `capability_executor.go`) and returns without calling `meterReport.Settle`.
5. `r.balance` remains debited by the full earmarked amount even though nothing was billed/consumed by the capability, and the next legitimate capability call in the same execution can now fail with `ErrInsufficientFunding`/be forced into metering mode despite the workflow's real credit balance being sufficient.

func (r *Report) Deduct(ref string, opt DeductOpt) ([]capabilities.SpendLimit, error) {
	r.mu.Lock()
	defer r.mu.Unlock()

	if !r.reserved {
		return nil, ErrNoReserve
	}

	if opt == nil {
		return nil, ErrDeductOptionRequired
	}

	if _, ok := r.steps[ref]; ok {
		return nil, ErrStepDeductExists
	}

	return opt(ref, r)
}

// Settle handles the actual spends that each node used for a given capability invocation in the engine,
// by returning earmarked local balance to the available to use pool and adding the spend to the metering report.
// The Deduct method must be called before Settle.
// We expect to only set this value once - an error is returned if a step would be overwritten.
func (r *Report) Settle(ref string, metadata capabilities.ResponseMetadata) error {
	r.mu.Lock()
	defer r.mu.Unlock()

	if !r.reserved {
		return ErrNoReserve
	}

	step, ok := r.steps[ref]
	if !ok {
		return ErrNoDeduct
	}

	if step.Spends != nil {
		return ErrStepSpendExists
	}
