### Title
Dust queued deposit permanently bricks `stopEpoch` on the prefunded variant, freezing all epoch funds - ([File: contracts/IdleCDOEpochQueue.sol])

### Summary
The prefunded epoch queue requires that, at `stopEpoch`/`stopEpochWithDuration` time, `epochPendingDeposits[epoch] == 0` — i.e., every queued deposit must have been forwarded to the borrower via `processDepositsToBorrower()`. But `processDepositsToBorrower()` reverts once the subscription cutoff (`prefundedDepositWindow`) is reached, and `deleteRequest()` can only be called by the depositor themselves. A KYC-passing lender can therefore deposit a 1-wei queued deposit late in the epoch; if the manager has not already prefunded (which would close the epoch to new deposits), that dust sits in `epochPendingDeposits` forever, `prefundedDepositsToProcess()` reverts, and `stopEpochWithDuration` can never complete — freezing the entire pool's funds until owner intervention.

### Finding Description
`requestDeposit()` has no minimum amount and adds to `epochPendingDeposits[nextEpoch]` for any `amount`, gated only by `isWalletAllowed` (KYC) and the deposit cutoff:

- `IdleCDOEpochQueue.sol:121-126` — `safeTransferFrom` then `epochPendingDeposits[nextEpoch] += amount`.
- `IdleCDOEpochQueue.sol:114-117` — deposits are blocked only once `epochPrefundedDeposits != 0` **or** `block.timestamp + prefundedDepositWindow >= epochEndDate`.

The only path that clears `epochPendingDeposits` into `epochPrefundedDeposits` is `processDepositsToBorrower()`, which reverts under the *same* cutoff:

- `IdleCDOEpochQueue.sol:164` — `_checkNotAllowed(_prefundedWindow == 0 || block.timestamp + _prefundedWindow < _cdo.epochEndDate())`.

Meanwhile the prefunded stop flow hard-requires zero raw pending deposits:

- `IdleCDOEpochQueue.sol:277-282` — `prefundedDepositsToProcess()` reverts via `_checkNotAllowed(epochPendingDeposits[_epoch] != 0)`, with the comment "Prefunded queues must not reach stopEpochWithDuration with raw underlyings still sitting in the queue."
- `IdleCDOEpochQueue.sol:265` — `processPrefundedDeposits()` likewise reverts if `epochPendingDeposits[_epoch] != 0`.

There is no admin sweep or force-clear: `deleteRequest()` (line 184) only zeroes `userDepositsEpochs[msg.sender]`, so the manager cannot remove the attacker's dust.

Attack sequence (prefunded AA queue, epoch running, attacker is a KYC-passed wallet):
1. Attacker calls `queue.requestDeposit(1)` while `block.timestamp + window < epochEndDate` and the epoch has not yet been prefunded.
2. Time passes past `epochEndDate - prefundedDepositWindow`. From this point `processDepositsToBorrower()` always reverts (line 164), so `epochPendingDeposits[nextEpoch] == 1` can never be cleared by anyone except the attacker.
3. Manager calls `stopEpochWithDuration(...)`; the prefunded variant calls `prefundedDepositsToProcess()` / `processPrefundedDeposits()`, which revert on `epochPendingDeposits != 0`. Every subsequent `stopEpoch` attempt reverts.

Caveat: I was unable to read `IdleCDOEpochVariantPrefunded.stopEpochWithDuration` internals in the available iterations to confirm the exact call ordering, but the in-code comments at lines 263-265 and 280-281 state the invariant is enforced inside the prefunded stop flow, and `processPrefundedDeposits` is invoked "atomically from stopEpoch on the prefunded variant" (line 249).

### Impact Explanation
A single wei of underlying permanently blocks epoch finalization. Since `stopEpoch` can never succeed, the epoch state machine is stuck in "running" forever: no `startEpoch`, no withdraw processing, no settlement of `pendingWithdraws`, and all lender principal/interest in the vault plus borrower-held funds remain locked. The only recourse is privileged intervention (e.g., owner repointing `epochQueue` to a different contract via the factory/orchestrator), which also strands the honestly queued deposits. This maps the external bug class (low-privilege input → deterministic crash/hang of the service) to a low-cost, unprivileged permanent freeze of all pool funds — direct fund impact, not mere gas/DoS.

### Likelihood Explanation
Requirements are minimal: the attacker needs only Keyring KYC (same bar as any lender) and 1 wei of underlying. The condition is that the epoch was not prefunded before the cutoff — this is the normal state whenever the manager prefunds late or demand is low, and the attacker can time the dust deposit to just before the cutoff to minimize the manager's reaction window. Because `deleteRequest` is self-service only, the attack cannot be undone by the honest manager or owner through the queue. Likelihood is gated mainly by the prefunded variant being in use and the manager not having prefunded; severity is high (full TVL freeze) but owner rescue exists, consistent with a Medium analog of a 6.5-CVSS DoS.

### Recommendation
- In `processDepositsToBorrower()`, allow sweeping leftover `epochPendingDeposits` after the cutoff, or add an owner/manager `sweepPendingDeposits(epoch)` that refunds `userDepositsEpochs` balances to depositors so `stopEpoch` is never hostage to a single non-cooperative depositor.
- Alternatively, enforce a minimum `requestDeposit` amount and/or auto-refund (rather than revert on) residual pending deposits inside `prefundedDepositsToProcess`/`processPrefundedDeposits`, e.g., treat unprefunded dust as `epochPrice` = current `virtualPrice` or mark it withdrawable.

### Proof of Concept
Foundry fork PoC outline (against `test/foundry` harness using the prefunded variant, e.g. `IdleCDOEpochVariantPrefunded` + AA `IdleCDOEpochQueue`):

```solidity
// setup: prefunded CDO + AA queue, manager, KYC'd attacker
uint256 window = queue.prefundedDepositWindow(); // nonzero, e.g. 5 days

// 1) normal lenders deposit into CDO; epoch is running; manager has NOT prefunded yet
vm.prank(attacker);
underlying.approve(address(queue), 1);
vm.prank(attacker);
queue.requestDeposit(1);                       // epochPendingDeposits[nextEpoch] == 1

// 2) warp past the deposit cutoff
vm.warp(cdoEpoch.epochEndDate() - window + 1);

// 3) manager can no longer clear pending deposits
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
queue.processDepositsToBorrower();             // line 164 cutoff check

// 4) epoch end: stopEpoch reverts forever via prefundedDepositsToProcess()
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);
cdoEpoch.stopEpochWithDuration(0, 0, duration, 0); // reverts: epochPendingDeposits != 0

// 5) grief is permanent absent owner queue-swap; attacker never calls deleteRequest(1)
```

If the prefunded queue path is out of scope for the deployment under review, then no equivalent analog was confirmed — note that the non-prefunded `processDeposits` path does not share this freeze, since users can always self-serve `deleteRequest` before `epochPrice` is set.
