### Title
Check-then-act race between `isReplay` and `recordUsage` allows JWT replay / duplicate execution - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` calls `jwtCache.isReplay(claims.ID)` and, only after several unrelated checks, calls `jwtCache.recordUsage(claims.ID)`. These are two separate lock acquisitions (`RLock`/`RUnlock` then `Lock`/`Unlock`) with no atomicity between the read and the write, so two concurrent `Authorize()` calls carrying the identical `jti` can both pass the `isReplay` check before either records usage, defeating the single-use ("consume-once") guarantee.

### Finding Description
`Authorize` at [1](#0-0)  performs: verify JWT → `isReplay(claims.ID)` → look up authorized keys → `recordUsage(claims.ID)`. `isReplay` and `recordUsage` are implemented as independent critical sections: [2](#0-1) . There is no compare-and-swap or single lock spanning "check jti absent" + "insert jti", so this is a classic TOCTOU race: if two requests carrying the same `jti` arrive concurrently, both can observe `isReplay == false` before either calls `recordUsage`, and both proceed to execute successfully. This breaks the intended one-signed-authorization-to-one-execution invariant for high-value single-use authorizations.

The other half of the question — long-lived replay across the full 24h `cleanupPeriod` window because `cleanupOldEntries` only runs on a ticker — is not exploitable as described, because `VerifyRequestJWT` independently enforces a hard cap on token lifetime (`maxJWTExpiryDuration = 5 * time.Minute`, and `duration > maxExpiryDuration` is rejected) at [3](#0-2) , and the underlying `jwt.ParseWithClaims` call also enforces `exp` validation as part of `verifiedToken.Valid`. So even though a `jti` may sit in `jwtCache.cache` for up to ~2×`cleanupPeriod` before eviction, an attacker cannot replay the same JWT after its 5-minute expiry — the JWT itself will fail signature/claims validation in `VerifyRequestJWT` long before the replay-cache entry is evicted. Thus the "indefinite replay within 24h" scenario is mitigated by JWT expiry, but the concurrent-race scenario is not mitigated at all.

### Impact Explanation
An attacker who is a legitimate authorized signer for a workflow (or who has intercepted another authorized signer's still-valid, unexpired JWT) can fire two (or more) concurrent requests bearing the identical `jti` within the JWT's 5-minute validity window. Both requests can pass the `isReplay` check and both get authorized, resulting in duplicate/unauthorized workflow executions charged against the signer's (or victim's) workflow — violating the "one signed authorization = one execution" invariant. This matches Chainlink's "unauthorized job run" / duplicate-execution impact class.

### Likelihood Explanation
Exploitability requires only: (1) a validly signed, unexpired JWT (an authorized signer can trivially generate two authorization requests with the same `jti` for the same digest, or an eavesdropper can capture one in transit), and (2) submitting it via two near-simultaneous requests to `Authorize`. No elevated privileges beyond "authorized signer for the workflow" (or JWT interception) are needed, and the race window, while narrow, is deterministically triggerable by firing goroutines/requests concurrently — this is fully reproducible in a unit test.

### Recommendation
Make the check-and-record atomic: hold `cache.mu.Lock()` across a single "check-and-insert" operation (e.g., `if _, exists := cache.cache[jti]; exists { return true }; cache.cache[jti] = time.Now(); return false`), and have `Authorize` call this single atomic method instead of separate `isReplay` + `recordUsage` calls.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`:
1. Build a `WorkflowMetadataHandler` with an authorized key/workflowID and a valid signed JWT (same `jti`, same digest) for a single `jsonrpc.Request`.
2. Launch two goroutines simultaneously calling `h.Authorize(workflowID, token, req)` with the identical token, synchronized via a `sync.WaitGroup`/barrier channel to maximize the race window.
3. Assert that exactly one of the two calls returns success (`*gateway.AuthorizedKey`, nil error) and the other returns the "JWT token has already been used" error.
4. Run with `go test -race -count=100` — expect intermittent failures showing both calls succeeding, proving `isReplay`+`recordUsage` is not atomic and violates the single-use invariant.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
