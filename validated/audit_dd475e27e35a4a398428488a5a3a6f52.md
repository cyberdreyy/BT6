### Title
Stale instant-withdraw receipts from a pre-default epoch escape the recovery haircut and are paid at par (or permanently freeze) - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` pays the aggregate `instantWithdrawsRequests[_user]` balance at par through `_transferFundedClaim`, after clearing only the *default-epoch* slice via `_claimDefaultedInstantWithdrawRequest`. But `finalizeDefaultRecovery` computes the recovery basis using only `instantWithdrawClaimsByEpoch[epochNumber]` — the *current* epoch. An instant receipt created in an earlier epoch that was only partially funded at `startEpoch` remains in `pendingInstantWithdraws` and `instantWithdrawsRequests` yet is excluded from `defaultPendingClaimBasis`. This is a receipt-type confusion: an unfunded pre-default receipt is treated as a fully funded one, letting it claim 100% while every defaulted-epoch claimant is haircut to `defaultRecoveryPrice`.

### Finding Description
The CDO calls `IdleCreditVault.requestInstantWithdraw`, which records both a per-user aggregate (`instantWithdrawsRequests[_user]`) and a per-epoch basis (`instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`).

At `finalizeDefaultRecovery` (`IdleCreditVault.sol:644-710`):
- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the basis **only for the current epoch** (line 647).
- `_defaultPrefundedInstantReserve()` computes `instantBasis(epochNumber) - pendingInstantWithdraws`, also keyed to the current epoch (lines 716-723).

If `pendingInstantWithdraws` contains basis recorded under an *earlier* epoch (a partially funded instant request from epoch N-1), it is:
1. Not in `totalBasis`, so `recoveryPrice` is unaffected — it contributes nothing to the haircut denominator.
2. Not in `prefundedReserve`, so its already-collected funds are not isolated.

Later, `claimInstantWithdrawRequest` (lines 380-393) clears only `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and then pays the *entire remaining* `instantWithdrawsRequests[_user]` via `_transferFundedClaim`. The stale-epoch component is therefore paid at full face value out of non-reserve vault balance. Symmetrically, the guard in `requestWithdraw` (lines 261-271) never inspects `instantWithdrawsRequestsByEpoch` for non-last epochs, so nothing prevents this state from being reached.

### Impact Explanation
Broken invariant: "one receipt, one haircut" — all unfunded claims at default must share the same `defaultRecoveryPrice`. The stale instant receipt either:

- **Steals from other claimants**: if the vault holds non-reserve underlyings (borrower-send remnants, later funded claims), the user withdraws the full stale amount `S` instead of `S * recoveryPrice`, directly reducing funds available for funded claimants — an unbounded-by-principal gain of `S * (1 - recoveryPrice)` for the attacker.
- **Permanently freezes claims**: if only `defaultRecoveryReserve` plus the partially prefunded `C < S` remains, `_transferFundedClaim`'s `balance - reserve < _amount` check reverts forever, freezing the user's legitimate `C` and blocking `claimInstantWithdrawRequest` for that user (the whole call reverts, including their funded portion).

Impact is quantified: loss = `S * (1 - recoveryPrice)` stolen from the recovery pool, or permanent freezing of `S`.

### Likelihood Explanation
Requires: instant withdrawals enabled, a partial instant funding at `startEpoch` (honest borrower cash shortfall — the code explicitly supports partial funding since `collectInstantWithdrawFunds` decrements `pendingInstantWithdraws` by whatever was collected), a subsequent epoch, and a borrower default finalized via `finalizeDefaultRecovery`. All privileged roles (manager stopping/starting epochs, borrower funding, owner finalizing) act honestly; the attacker is an ordinary KYC'd tranche holder who simply made an instant-withdraw request in epoch N-1 and claims after finalization. Partial instant funding is a normal operating condition, making this reachable without exotic timing.

### Recommendation
- In `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()`, aggregate `instantWithdrawClaimsByEpoch` over all epochs contributing to `pendingInstantWithdraws`, not just `epochNumber` (e.g., track a global `instantClaimsBasis` counter incremented in `requestInstantWithdraw` and decremented on claim).
- In `_claimDefaultedInstantWithdrawRequest`, clear and haircut every epoch slice with a nonzero basis, not only `defaultRecoveryEpoch`; or iterate the user's per-epoch instant receipts.
- Add a regression test: partially fund an instant request in epoch N-1, run epoch N, default, finalize, and assert the stale receipt claims at `defaultRecoveryPrice`.

### Proof of Concept
Foundry fork PoC sketch (pattern follows `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testStaleInstantReceiptEscapesDefaultHaircut() external {
  // setup: instant withdraws enabled, lender deposits AA in epoch 0
  uint256 amount = 10_000 * ONE_SCALE;
  idleCDO.depositAA(amount);
  _transferBurnedTrancheTokens(address(this), true);
  _startEpochAndCheckPrices(0);
  _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

  // epoch 1: force APR drop so requestWithdraw routes to instant path
  _forceInstantWithdrawConditions(); // lastEpochApr > unscaledApr + instantWithdrawAprDelta
  uint256 S = cdoEpoch.requestWithdraw(instantAmount, address(AAtranche));
  // instantWithdrawsRequests[cdo]=S, instantWithdrawClaimsByEpoch[1]=S,
  // pendingInstantWithdraws=S

  // startEpoch with only partial cash C < S available for instant queue
  deal(defaultUnderlying, address(cdoEpoch), C);
  vm.prank(manager);
  cdoEpoch.startEpoch(); // collectInstantWithdrawFunds(C): pendingInstantWithdraws = S-C

  // user does not claim; epoch 1 runs; borrower defaults
  vm.warp(cdoEpoch.epochEndDate() + 1);
  vm.prank(manager);
  cdoEpoch.stopEpochWithDuration(0, _loss); // or _handleBorrowerDefault path
  // finalize recovery with recoveredAmount R
  cdoEpoch.finalizeDefaultRecovery(R, recoverySource);
  // basis included instantWithdrawClaimsByEpoch[epochNumber] only;
  // stale epoch-0/1 slice (S unfunded) was excluded -> recoveryPrice ignores it

  // attacker claims at par
  uint256 balPre = underlying.balanceOf(address(this));
  cdoEpoch.claimInstantWithdrawRequest();
  uint256 got = underlying.balanceOf(address(this)) - balPre;
  // BUG: got == S (par) instead of funded part + S_unfunded * defaultRecoveryPrice
  assertEq(got, S); // haircut escaped; reserve/other claimants bear the loss
}
```
