### Title
Unprivileged ERC4626 depositor can poison `totalInterestDueNow()` via share-price donation, forcing `stopEpoch` to revert or triggering a spurious borrower default - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
The Jenkins bug is a trust-boundary failure: a trusted pipeline retrieves a library from the *same untrusted revision* an attacker can modify. The analog in idle-tranches is `ProgrammableBorrower`: the epoch settlement pipeline (`stopEpoch`) prices the entire epoch from `totalInterestDueNow()`, which reads `convertToAssets()` of an external ERC4626 vault — a value any unprivileged depositor of that vault can modify by donating underlying. The system trusts a "library" (vault share price) that untrusted users can rewrite, and there is no guard analogous to the upstream fix ("abort retrieval if the library comes from an untrusted revision").

### Finding Description
`ProgrammableBorrower._vaultNetInterest()` computes epoch yield as `convertToAssets(shares) + epochWithdrawnFromVault - epochStartVaultAssets - epochDepositedToVault` (`contracts/strategies/idle/ProgrammableBorrower.sol:337-347`). `convertToAssets` reflects the vault's live `totalAssets/totalSupply`, which any ERC4626 depositor can inflate by transferring underlying directly to the vault (a donation). The inflated value flows into `totalInterestDueNow()` (`ProgrammableBorrower.sol:330-334`), which `IdleCDOEpochVariant._resolveStopEpochInterest`/`stopEpoch` uses as the single pool-facing interest figure.

Two failure modes, both gated only by data the attacker controls:

1. **Minted-interest mode** (`isInterestMinted = true`, the tested programmable configuration): `stopEpoch` enforces `_checkNotAllowed(_maxApr != 0 && _grossInterest > _calcInterestWithApr(getContractValue(), _maxApr) + _pendingWithdrawFees)` (`contracts/IdleCDOEpochVariant.sol:377-380`). A donation larger than `TVL * maxApr * epochPeriod` makes every `stopEpoch` call revert. Since an ERC4626 donation cannot be withdrawn by the borrower adapter's `vault.withdraw` into a lower price (the price stays elevated permanently), the epoch can never be stopped under the configured cap. The pool is stuck in `isEpochRunning`, blocking all `requestWithdraw` fulfillment and LP exits until the owner manually raises `maxApr` — a temporary freezing of the entire pool NAV at an attack cost of one donation.

2. **Cash mode** (`isInterestMinted = false`): `_amountToPullFromBorrower = _expectedInterest + _pendingWithdraws` now includes phantom donated "interest". `onStopEpoch` will attempt `vault.withdraw(shortfall)`; on vaults where idle liquidity is lendable (e.g., Morpho-style), the withdraw can fail or leave the borrower's `transferFrom` short, so `getFundsFromBorrower` throws and `_handleBorrowerDefault` runs (`IdleCDOEpochVariant.sol:395-404,408`) — a spurious default that crystallizes a loss waterfall onto BB/AA holders even though the borrower is solvent and the donated assets still sit in the vault.

The broken invariant is the same as CVE-2022-29047: the settlement path assumes its externally retrieved value (Pipeline library / `convertToAssets`) is not attacker-modifiable, and no sanity bound ties `totalInterestDueNow` to assets the borrower actually controls (it exceeds `borrowerPrincipal + contractual interest + on-hand balance`).

### Impact Explanation
- Temporary freezing of the full pool NAV (all pending and active withdrawals) until privileged intervention, costing the attacker only an irreversible donation of `~maxApr`-scaled size.
- In cash mode, forced default: `defaulted = true`, recovery accounting engages, tranche prices are haircut, and LPs suffer the default-claim flow despite zero real credit loss. Funds are recoverable only through the slow recovery path, and reputation/sequencing damage is permanent.

### Likelihood Explanation
Attacker needs only to be a depositor of the configured ERC4626 vault (explicitly in scope: "a user of the programmable borrower's ERC4626 vault"). No KYC or tranche position required. Donation attacks on ERC4626 `convertToAssets` are standard and cheap (the donation is the cost, and for mode 1 only needs to exceed the `maxApr` bound, not the pool TVL). The existing guards do not stop it: `_skimDonatedAssets` only protects the CDO's own underlying balance, not the vault's share price; `setVault`/`setBorrower` gates are owner-only but don't bound mid-epoch `convertToAssets` drift; `shortfall > _currentVaultAssets → return true` in `onStopEpoch` actually *uses* the poisoned valuation rather than rejecting it.

### Recommendation
Bound the vault-yield leg independently of spot `convertToAssets`: cap `vaultInterest` at `shares * (epochStartPrice + maxGrowthRate)` using a share-price snapshot taken at `onStartEpoch`, or track vault contributions/withdrawals against a deposited-assets baseline with a configurable max slippage. At minimum, on the minted path treat `_grossInterest` above the cap as clampable rather than reverting, so a poisoned price cannot freeze the epoch.

### Proof of Concept
Foundry fork sketch (mode 1, minted-interest programmable vault, e.g., MetaMorpho as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
// Setup mirrors testProgrammableBorrowerStopEpochAutoRealizesInterestWithRealVault
vm.prank(owner); cdoEpoch.setIsInterestMinted(true);
idleCDO.depositAA(10_000 * oneScale);
_startEpochAndCheckPrices(0);               // onStartEpoch snapshots epochStartVaultAssets

// Attacker (any EOA holding USDC) donates to the ERC4626 vault to pump convertToAssets
uint256 cap = strategy.maxApr();            // e.g. 20e18
uint256 donation = (cdoEpoch.getContractValue() * (cap/100) * epochLen / 365 days / 1e18) + pendingFees + 1;
deal(USDC, attacker, donation);
vm.prank(attacker);
IERC20(USDC).transfer(address(morphoVault), donation);  // donation, not deposit

assertGt(programmableBorrower.totalInterestDueNow(), expectedLegitInterest);

vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
vm.expectRevert(NotAllowed.selector);        // _grossInterest exceeds maxApr-derived cap
cdoEpoch.stopEpoch(0, 0);
// Every subsequent stopEpoch reverts while the donated price persists =>
// requestWithdraw claimants cannot be funded; pool frozen until owner calls strategy.setMaxApr(0).
```

Uncertainty note: I did not read `_resolveStopEpochInterest`/`getFundsFromBorrower` bodies; the PoC assumes `_interest = 0` resolves to `totalInterestDueNow()` (making it `> 1`, enabling the cap check) as the interface docs and tests imply. If the resolved value stays `0` in minted mode, mode 1 instead mints inflated-but-backed interest and the exploitable path is mode 2's spurious default, which requires the borrower's vault liquidity to be insufficient — still reachable on lendable ERC4626 vaults after the attacker first drains available liquidity as a borrower/depositor.
