### Title
Unauthenticated cross-user callback overwrite via attacker-chosen MessageId collision - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`Message.Validate` in `core/services/gateway/api/message.go` only checks length/format of `MessageId`, never uniqueness, and it is fully attacker-chosen and signed by the attacker's own key. `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` writes to `h.savedCallbacks[msg.Body.MessageId]` unconditionally with no existence check, so a second request using the same `MessageId` as a still in-flight victim request silently overwrites the victim's callback pointer, causing the eventual DON response to be delivered to the attacker instead of the victim.

### Finding Description
`Message.Validate` (`core/services/gateway/api/message.go:54-88`) validates only that `MessageId` is non-empty, ≤128 bytes, and doesn't end in a null byte; it places no constraint tying `MessageId` uniqueness to sender identity. [1](#0-0) 

Requests reach the gateway via `gateway.ProcessRequest` (`core/services/gateway/gateway.go:218-292`), which decodes the JSON-RPC body, calls `msg.Validate()` for legacy requests, and dispatches to `h.HandleLegacyUserMessage(ctx, msg, callback)` with a fresh per-request `callback`. [2](#0-1) 

In `handler.go`, `HandleLegacyUserMessage` stores the callback keyed purely by the attacker-controlled `MessageId` string with no check for a pre-existing entry: [3](#0-2) . If two concurrent requests (victim, then attacker) present the identical `MessageId`, the second `h.mu.Lock()`/write silently replaces the map entry — there is no `if _, exists := h.savedCallbacks[id]; exists { reject }` guard, unlike the equivalent code path in `core/services/gateway/handlers/confidentialrelay/handler.go:368-383` (`newActiveRequest`), which explicitly rejects duplicate `req.ID` with `"request ID already exists"`. The same unguarded pattern also exists in `handler.dummy.go:62-66`. [4](#0-3) 

When the DON eventually responds with that `MessageId`, `handleWebAPITriggerMessage` looks up and deletes the single map entry and delivers the payload to whichever callback is currently stored — the attacker's, if it overwrote the victim's — via `savedCb.SendResponse(...)`. [5](#0-4) 

No authentication/signature check ties `MessageId` to the caller across the whole flow: the signature only proves the *current* message's authenticity, not that the `MessageId` hasn't been claimed by another sender, so this is not stopped by existing signature verification in `ExtractSigner`.

### Impact Explanation
Cross-user response confusion: a victim's DON response payload (which may contain sensitive trigger/workflow output data) can be diverted to an attacker-controlled callback and returned in the attacker's HTTP response instead of the victim's, and the victim's own request will simply receive no response (silent DoS/timeout). This matches the "cross-user response confusion" impact class called out in the audit rules.

### Likelihood Explanation
The attack requires: (1) no privileges beyond being any gateway client able to sign and submit a `MethodWebAPITrigger` message (attacker generates their own valid signature over an arbitrary chosen `MessageId`), and (2) knowledge of a specific victim's in-flight `MessageId` value, timed to arrive before the victim's DON response completes. The server-side flaw (missing uniqueness check) is unconditionally present and 100% reproducible once the ID is known/guessed; however, actual exploitability hinges on how predictable/guessable the victim's client-chosen `MessageId` is in practice, which is not enforced or generated by this codebase and is therefore uncertain/out of scope for this repo. Confirmed only by comparison to `confidentialrelay/handler.go`, which reflects the safer intended pattern.

### Recommendation
In `core/services/gateway/handlers/capabilities/handler.go:HandleLegacyUserMessage` (and `handler.dummy.go:HandleLegacyUserMessage`), before writing to `savedCallbacks`, check for an existing entry under the lock and reject the request (mirroring `confidentialrelay/handler.go`'s `newActiveRequest` duplicate check). Additionally, consider scoping the callback map key by `(sender, MessageId)` tuple instead of `MessageId` alone, since `Sender` is cryptographically verified via `ExtractSigner` in `Message.Validate`, preventing any two distinct senders from ever colliding on the same key regardless of ID predictability.

### Proof of Concept
Add to `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build two `api.Message` values (`victimMsg`, `attackerMsg`) with identical `MessageId` (e.g., `"shared-id"`) but signed by two different keys (`nodes[0].PrivateKey` vs a second unrelated key), each with valid, distinct payloads.
2. Call `handler.HandleLegacyUserMessage(ctx, victimMsg, victimCb)`, then immediately `handler.HandleLegacyUserMessage(ctx, attackerMsg, attackerCb)`.
3. Assert `len(handler.savedCallbacks) == 1` and that `handler.savedCallbacks["shared-id"].Callback == attackerCb` (overwritten), not `victimCb`.
4. Simulate the DON response via `handler.HandleNodeMessage(...)` with `MessageId = "shared-id"` and assert that `attackerCb.Wait(ctx)` receives the response while `victimCb.Wait(ctx)` times out — demonstrating the victim's response is misdelivered to the attacker.
