### Title
Wrapper's fixed 10s `terminateWrapper` timeout has no SIGKILL escalation and abandons the wrapped `gitlab-runner run` process group on shutdown - (File: helpers/runner_wrapper/wrapper.go)

### Summary
`Wrapper.terminateWrapper` sends a single `SIGTERM` to the wrapped `gitlab-runner run` process and waits only `w.terminationTimeout` (default `DefaultTerminationTimeout` = 10s) before giving up with `errProcessExitTimeout`. The caller (`commands/wrapper.go`) treats that error as fatal and calls `log.Fatal`, which exits the wrapper process via `os.Exit` without ever forcing the child (or its process-group siblings created via `setProcessGroup`) to die, so a slow-to-abort job can outlive the operator-visible "shutdown."

### Finding Description
`Wrapper.terminateWrapper` ( [1](#0-0) ) signals `SIGTERM` once via `terminateWrappedProcess` and then races `w.errCh` against `time.After(w.terminationTimeout)`. If the wrapped process hasn't exited in `terminationTimeout` (10s by default, see `DefaultTerminationTimeout` at [2](#0-1) ), it returns `errProcessExitTimeout` and takes no further action — there is no SIGKILL escalation anywhere in this path, and `forcefulShutdown` on Unix ( [3](#0-2) ) is unused by `terminateWrapper` and, even if it were, only re-sends `SIGTERM`.

The wrapped child is started with its own process group (`setProcessGroup` sets `Setpgid: true`, [4](#0-3) ), so on Linux it is not tied to the wrapper's session and is not killed automatically when the wrapper process exits.

The caller `RunnerWrapperCommand.Execute` treats any error from `w.Run(ctx)` (including `errProcessExitTimeout`) as fatal and calls `log.WithError(err).Fatal(...)` ( [5](#0-4) ), which via logrus performs `os.Exit`, terminating only the wrapper itself. The wrapped `gitlab-runner run` process — along with any job/build processes it spawned and manages, and the credentials/tokens it holds for polling multiple projects — is left running, orphaned, with no further termination attempt.

Meanwhile, the wrapped `run` process's own shutdown path (`RunCommand.Stop` → `handleForcefulShutdown`, [6](#0-5) ) waits up to `config.GetShutdownTimeout()` for `mr.runFinished`, and individual job kill escalation in shell/custom executors uses `graceful_kill_timeout`/`force_kill_timeout` (`osKillWait.KillAndWait`, [7](#0-6) ) which default to values far larger than the wrapper's 10s (`GracefulTimeout` is 10 minutes, [8](#0-7) ). A pipeline author who writes a job script that ignores/ traps `SIGTERM` (e.g., `trap '' TERM; sleep 600`) or that is simply mid-way through legitimate teardown work when a shutdown is requested will routinely exceed the wrapper's fixed 10-second budget even though the inner `run` process is behaving exactly as documented and will eventually finish cleanup on its own. The wrapper layer's short, non-escalating timeout is strictly tighter than the invariants the inner process already relies on, so it is essentially guaranteed to fire under attacker/job-controlled delay, and when it does, the operator/orchestrator driving the wrapper (e.g., via its gRPC status/shutdown API in `commands/wrapper.go`) is told (via the fatal error / process exit) that shutdown happened, while jobs for other tenants continue executing and polling with valid auth tokens.

### Impact Explanation
Once `errProcessExitTimeout` propagates and the wrapper process exits via `log.Fatal`, the underlying `gitlab-runner run` process and any of its child job processes (still in their own process group) keep running and holding GitLab runner auth tokens, continuing to poll/execute jobs belonging to other, unrelated projects/tenants — even though the party managing the wrapper (autoscaler/orchestrator) believes shutdown completed because the wrapper process is gone and/or reported an error. This directly violates the invariant that runner shutdown must reliably free resources shared across tenants, since resource reclamation (e.g., terminating the VM/host that was scheduled for teardown) may proceed based on the false assumption that the runner and its jobs are stopped.

### Likelihood Explanation
This is highly reachable: any job whose graceful abort takes longer than the wrapper's `terminationTimeout` (default 10s, configurable via `--process-termination-timeout` but still a fixed independent budget) will trigger it. A pipeline author fully controls how quickly their job script responds to `SIGTERM` (trapping/ignoring it, or simply doing slow cleanup/network I/O), making the timing deterministic and trivially reproducible without any privileged access — it only requires the operator to be using the `wrapper` command mode (used for orchestrated/autoscaled deployments) and to trigger a shutdown while such a job is running.

### Recommendation
- Escalate to `SIGKILL` of the wrapped process's entire process group (`syscall.Kill(-pgid, SIGKILL)`) when `terminationTimeout` elapses, instead of just returning `errProcessExitTimeout`.
- Align the wrapper's timeout semantics with the inner `run` process's own shutdown timeout (`GetShutdownTimeout`/`GracefulTimeout`) so it doesn't race an artificially shorter deadline, or make `commands/wrapper.go` attempt a forced kill of the child process group before calling `log.Fatal`.
- Ensure `commands/wrapper.go`'s fatal-error path performs cleanup (force-kill child group) prior to exiting, so the orchestrator's view of "runner stopped" always matches reality.

### Proof of Concept
Extend `wrapper_test.go` "timeout when waiting for wrapped process termination" case: mock `commander.Wait` to block far longer than `terminationTimeout` (as already done at [9](#0-8) ), then add an assertion that after `terminateWrapper()` returns `errProcessExitTimeout`, the mock process is never asked to receive `SIGKILL` (only `SIGTERM` was ever called), proving no escalation occurs. A follow-up integration test can start a real subprocess that traps `SIGTERM` and sleeps, run `Wrapper.Run` with `ctx` cancellation, and assert that after `terminateWrapper` returns the error, the subprocess PID is still alive (`syscall.Kill(pid, 0)` returns nil) — demonstrating the orphaned, still-running process.

func (w *Wrapper) terminateWrapper() error {
	w.log.Info("Shutting down wrapper process...")

	err := w.terminateWrappedProcess()
	if err != nil {
		if errors.Is(err, api.ErrProcessNotInitialized) {
			return nil
		}
		return err
	}

	select {
	case err := <-w.errCh:
		w.log.WithError(err).Info("Wrapped application exited")

		return nil

	case <-time.After(w.terminationTimeout):
		return errProcessExitTimeout
	}
}
```

func (mr *RunCommand) handleForcefulShutdown() error {
	mr.processStateTracker.SetForcefulShutdown()

	mr.log().
		WithField("shutdown-timeout", mr.configfile.Config().GetShutdownTimeout()).
		WithField("StopSignal", mr.stopSignal).
		Warning("Starting forceful shutdown")

	go mr.abortAllBuilds()

	// Wait for graceful shutdown or abort after timeout
	for {
		select {
		case mr.stopSignal = <-mr.stopSignals:
			mr.log().WithField("stop-signal", mr.stopSignal).Warning("[handleForcefulShutdown] received stop signal")
			return fmt.Errorf("forced exit with stop signal: %v", mr.stopSignal)

		case <-time.After(mr.configfile.Config().GetShutdownTimeout()):
			return errors.New("shutdown timed out")

		case <-mr.runFinished:
			// Everything finished we can exit now
			return nil
		}
	}
}

// KillAndWait will take the specified process and terminate the process and
// wait util the waitCh returns or the graceful kill timer runs out after which
// a force kill on the process would be triggered.
func (kw *osKillWait) KillAndWait(command Commander, waitCh chan error) error {
	process := command.Process()
	if process == nil {
		return ErrProcessNotStarted
	}

	log := kw.logger.WithFields(logrus.Fields{
		"PID": process.Pid,
	})

	processKiller := newProcessKiller(log, command)
	processKiller.Terminate()

	select {
	case err := <-waitCh:
		return err
	case <-time.After(kw.gracefulKillTimeout):
		processKiller.ForceKill()

		select {
		case err := <-waitCh:
			return err
		case <-time.After(kw.forceKillTimeout):
			return &KillProcessError{pid: process.Pid}
		}
	}
```
