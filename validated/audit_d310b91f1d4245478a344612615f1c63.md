### Title
View-role users can retrieve a bridge's confidential `outgoingToken` via GET /v2/bridge_types/:BridgeName - ([File: core/web/bridge_types_controller.go])

### Summary
The route `authv2.GET("/bridge_types/:BridgeName", bt.Show)` is registered without any role wrapper (`RequiresEditRole`/`RequiresAdminRole`), only requiring authentication. `BridgeTypesController.Show` builds its response via `presenters.NewBridgeResource(bt)`, which unconditionally copies `bt.OutgoingToken` into the JSON response with no redaction, so any authenticated user — including view/run role — receives the bridge's outgoing token in plaintext.

### Finding Description
`core/web/router.go` registers the route as: `authv2.GET("/bridge_types/:BridgeName", bt.Show)` [1](#0-0) , with `authv2` requiring only `auth.Authenticate(...)` (token or session), and no `RequiresEditRole`/`RequiresAdminRole` wrapper applied — unlike the sibling `PATCH`/`DELETE`/`POST` routes on the same resource which are wrapped with `auth.RequiresEditRole` [2](#0-1) .

`BridgeTypesController.Show` fetches the `bridges.BridgeType` from the ORM and serializes it directly: `jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")` [3](#0-2) .

`presenters.NewBridgeResource` copies `OutgoingToken: b.OutgoingToken` into `BridgeResource`, whose `OutgoingToken` field is tagged `json:"outgoingToken"` (no `omitempty`, no redaction logic, unlike `IncomingToken` which is commented as "only provided when creating a Bridge"): [4](#0-3) .

The existing RBAC test table explicitly documents that `GET /v2/bridge_types/MOCK` is `viewOnlyAllowed: true` [5](#0-4) , confirming this is the intended access level for the route — i.e., view-role users are meant to be able to call `Show`. However, `TestBridgeController_Show` only asserts `Name`, `URL`, and `Confirmations` match, and never checks that `OutgoingToken` is redacted or empty [6](#0-5) . Meanwhile `TestBridgeTypesController_Create_Success` confirms `outgoingToken` is a real, non-empty secret value populated at creation time and persisted on the `bridges.BridgeType` row [7](#0-6) . The `OutgoingToken` field on `bridges.BridgeType` is the credential used to authenticate outgoing calls from the node to the external adapter [8](#0-7) .

No middleware, presenter redaction, or role check intercepts this: authentication is verified, but authorization role is not checked at all for `Show`, and the presenter performs no field-level masking.

### Impact Explanation
A user with only `view` (or `run`) role — the lowest privileged authenticated roles in the node's session RBAC — can retrieve any bridge's `outgoingToken` by simply calling `GET /v2/bridge_types/:BridgeName`. This token is a secret credential used by the node to authenticate itself to external adapters; its disclosure lets a low-privileged/read-only session holder impersonate the node to the external adapter or reuse the credential outside the node, violating the "secrets never leave" invariant. This matches the Chainlink bounty impact class of "sensitive secret/credential disclosure via broken access control," scoped to leakage of a single external-adapter integration secret (not a private key controlling on-chain funds).

### Likelihood Explanation
Precondition is minimal: any valid authenticated session or API token with `view` role (the lowest tier) suffices — no edit/admin privileges are needed. The exploit is a single GET request with no special crafting, fully deterministic and repeatable for every bridge on the node. This is a design/authorization gap (missing role wrapper + missing presenter redaction) rather than a misconfiguration, and is directly reachable from the documented, tested API surface (the RBAC test table already codifies `viewOnlyAllowed: true` for this route without codifying token redaction).

### Recommendation
Add redaction of `OutgoingToken` in `presenters.NewBridgeResource`/`BridgeResource` for read paths (`Index`/`Show`), or add a role check to `BridgeTypesController.Show` (or a separate presenter for view/run vs edit/admin) so that only edit/admin-role callers, or none via API, receive `outgoingToken`. Since `POST` (`Create`) intentionally returns `outgoingToken` once, but `Show` should not repeat it — track this similarly to `IncomingToken`'s "only provided on creation" convention.

### Proof of Concept
1. Add a Go handler-level test in `core/web/bridge_types_controller_test.go`:
   - Create a bridge via `app.BridgeORM().CreateBridgeType` with a known `OutgoingToken`.
   - Create an HTTP client authenticated with a `view`-role session/user (see helpers used elsewhere for role-restricted clients, e.g. `cltest.NewApplication` + a view-role session, or reuse pattern from `auth_test.go` `routesRolesMap`).
   - Call `GET /v2/bridge_types/<name>` as the view-role user.
   - Assert `resp.StatusCode == 200` (confirms route is reachable without edit/admin role).
   - Parse the JSON:API response into `presenters.BridgeResource` and assert `resource.OutgoingToken == ""` (expected/fixed behavior) — currently this assertion will fail because `resource.OutgoingToken` equals the real secret, proving the leak.

func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

func TestBridgeTypesController_Create_Success(t *testing.T) {
	t.Parallel()

	app := cltest.NewApplication(t)
	require.NoError(t, app.Start(t.Context()))
	client := app.NewHTTPClient(nil)

	resp, cleanup := client.Post(
		"/v2/bridge_types",
		bytes.NewBuffer(cltest.MustReadFile(t, "../testdata/apiresponses/create_random_number_bridge_type.json")),
	)
	t.Cleanup(cleanup)
	cltest.AssertServerResponse(t, resp, http.StatusOK)
	respJSON := cltest.ParseJSON(t, resp.Body)
	btName := respJSON.Get("data.attributes.name").String()

	assert.NotEmpty(t, respJSON.Get("data.attributes.incomingToken").String())
	assert.NotEmpty(t, respJSON.Get("data.attributes.outgoingToken").String())

	ctx := t.Context()
	bt, err := app.BridgeORM().FindBridge(ctx, bridges.MustParseBridgeName(btName))
	require.NoError(t, err)
	assert.Equal(t, "randomnumber", bt.Name.String())
	assert.Equal(t, uint32(10), bt.Confirmations)
	assert.Equal(t, "https://example.com/randomNumber", bt.URL.String())
	assert.Equal(t, assets.NewLinkFromJuels(100), bt.MinimumContractPayment)
	assert.NotEmpty(t, bt.OutgoingToken)
}

func TestBridgeController_Show(t *testing.T) {
	t.Parallel()

	app := cltest.NewApplication(t)
	require.NoError(t, app.Start(t.Context()))

	client := app.NewHTTPClient(nil)

	bt := &bridges.BridgeType{
		Name:          bridges.MustParseBridgeName(testutils.RandomizeName("showbridge")),
		URL:           cltest.WebURL(t, "https://testing.com/bridges"),
		Confirmations: 0,
	}
	ctx := t.Context()
	require.NoError(t, app.BridgeORM().CreateBridgeType(ctx, bt))

	resp, cleanup := client.Get("/v2/bridge_types/" + bt.Name.String())
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusOK, resp.StatusCode, "Response should be successful")

	var resource presenters.BridgeResource
	cltest.ParseJSONAPIResponse(t, resp, &resource)
	assert.Equal(t, bt.Name.String(), resource.Name, "should have the same name")
	assert.Equal(t, bt.URL.String(), resource.URL, "should have the same URL")
	assert.Equal(t, bt.Confirmations, resource.Confirmations, "should have the same Confirmations")

	resp, cleanup = client.Get("/v2/bridge_types/nosuchbridge")
	t.Cleanup(cleanup)
	assert.Equal(t, http.StatusNotFound, resp.StatusCode, "Response should be 404")
}
