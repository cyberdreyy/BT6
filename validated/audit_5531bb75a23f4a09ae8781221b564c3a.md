### Title
Builder pending withdrawal commits the full requested amount to the execution payload even when the builder's balance can only cover part of it, minting Gwei that was never backed by a deducted balance - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` places the *full, uncapped* `withdrawal.amount` from `state.builder_pending_withdrawals` into the `Withdrawal` object that becomes part of `state.payload_expected_withdrawals` (the CL's commitment to the EL), while `apply_withdrawals` only deducts `min(withdrawal.amount, builder_balance)` from the builder's actual balance. This is the exact bug-class from the report: a debt/obligation that is only *partially* covered by the paying account's funds, but instead of being scaled down (or left as pending remainder), the accounting operations on the two sides of the same amount diverge.

### Finding Description
`get_builder_withdrawals` builds the commitment withdrawal record using the *requested* amount unconditionally: [1](#0-0) 

`apply_withdrawals`, however, caps the actual balance deduction to what the builder has: [2](#0-1) 

The withdrawal object that is committed into `state.payload_expected_withdrawals` (and thus into the execution payload that the EL is required to honor) carries `amount = withdrawal.amount` (the full requested amount), not the capped amount. This is confirmed by the spec's own test suite: [3](#0-2) 

In this test, a builder with only 1 ETH balance has a pending withdrawal requesting 5 ETH. The output withdrawal committed to the EL still has `amount = 5 ETH` (`withdrawal_amounts_builders={builder_index: withdrawal_amount}`), while the builder's CL-side balance is only reduced by 1 ETH (`builder_balances={builder_index: 0}`). The `payload_expected_withdrawals` entry is exactly what the execution layer is contractually bound to credit to `fee_recipient` — i.e., the EL will mint the full 4 ETH difference to an address with no corresponding balance ever having existed on the CL side.

This directly parallels the Sherlock finding: instead of scaling the committed obligation down to what can actually be funded (as `decrease_balance`'s own underflow protection correctly does for validator balances), the builder-withdrawal path lets the *commitment* (analogous to "debt cleared") diverge from the *actual funds removed* (analogous to `earningsAccumulator`), breaking the create/destroy-Gwei equality instead of merely leaving debt uncleared.

### Impact Explanation
This breaks the "Gwei created ... paid to a non-owner" invariant at Critical severity: the execution layer will mint ETH to `fee_recipient` for an amount that was never actually held/deducted from the builder's `state.builders[*].balance`. Unlike the original DeFi report (where under-clearing merely leaves bad debt on the books), here the CL *commits* to paying out more than it deducts, meaning new, unbacked ETH is minted on the execution layer for every builder withdrawal request that exceeds the builder's remaining balance. Every such shortfall inflates total ETH supply by the difference, and it is fully deterministic/spec-following — no malicious peer, coalition, or client bug is required, only that `withdrawal.amount > builder.balance` at the time the builder's withdrawal is scheduled.

### Likelihood Explanation
`can_builder_cover_bid` is meant to keep `builder.balance` sufficient to cover all pending withdrawals plus `MIN_DEPOSIT_AMOUNT`, but it only gates new bids/deposits at the time they are made: [4](#0-3) 

If anything reduces `builder.balance` after a `BuilderPendingWithdrawal` is queued and before it is processed (e.g., a later builder-pending-withdrawal or sweep entry draining the balance first within the same processing loop, given entries are processed in queue order and each entry's cap is evaluated against the balance *as of that iteration*, not reserved up front), a subsequent queued withdrawal for the same builder can exceed the remaining balance, triggering the mismatch. The spec's own test explicitly exercises and asserts this exact scenario as expected behavior, indicating it is a designed code path, not a rare edge case, and is reachable purely through legitimate protocol state transitions.

### Recommendation
Make the committed `Withdrawal.amount` in `get_builder_withdrawals` equal to `min(withdrawal.amount, state.builders[builder_index].balance)` at the time the withdrawal is scheduled (mirroring what `apply_withdrawals` actually deducts), and carry the un-covered remainder over as a new/partial `BuilderPendingWithdrawal` rather than dropping it, so the amount that the execution layer is committed to pay always equals the amount actually removed from the builder's balance.

### Proof of Concept
1. Builder `B` has `balance = 1 ETH`.
2. A `BuilderPendingWithdrawal{builder_index=B, amount=5 ETH, fee_recipient=X}` is enqueued in `state.builder_pending_withdrawals` (reachable via normal builder-payment/withdrawal-request processing once `B`'s balance has been reduced below the queued amount by intervening operations).
3. On the next processed slot, `get_builder_withdrawals` produces `Withdrawal(validator_index=convert(B), address=X, amount=5 ETH)` unconditionally (per [5](#0-4) ), which is placed into `state.payload_expected_withdrawals`.
4. `apply_withdrawals` executes `state.builders[B].balance -= min(5 ETH, 1 ETH)`, leaving `balance = 0` (per [6](#0-5) ).
5. The execution layer, following the committed payload withdrawal list, credits address `X` with the full `5 ETH` from `payload_expected_withdrawals`, while only `1 ETH` was ever removed from any CL-tracked balance — net `4 ETH` created out of nothing. This exact behavior (committed amount = requested amount, deducted amount = capped amount) is verified as the expected/asserted outcome in `test_builder_withdrawal_insufficient_balance` [3](#0-2) .

def can_builder_cover_bid(
    state: BeaconState, builder_index: BuilderIndex, bid_amount: Gwei
) -> bool:
    builder_balance = state.builders[builder_index].balance
    pending_withdrawals_amount = get_pending_balance_to_withdraw_for_builder(state, builder_index)
    min_balance = MIN_DEPOSIT_AMOUNT + pending_withdrawals_amount
    if builder_balance < min_balance:
        return False
    return builder_balance - min_balance >= bid_amount
