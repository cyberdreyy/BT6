### Title
Fee-on-transfer underlying overmints credit-vault strategy tokens and creates bad debt - (`contracts/strategies/idle/IdleCreditVault.sol`)

### Summary

`IdleCDOCreditVault._deposit` correctly mints tranche shares using the underlying balance delta, but then forwards the caller-supplied nominal `_amount` to `IdleCreditVault.deposit`. `IdleCreditVault.deposit` pulls `_amount` from the CDO and mints `_amount` strategy tokens without measuring the amount actually received. With a fee-on-transfer underlying, the strategy receives less than `_amount` while the CDO receives a nominal 1:1 strategy-token claim, breaking strategy-token backing and potentially consuming raw CDO reserves to satisfy the second transfer. [1](#0-0) [2](#0-1) 

The same nominal-amount assumption exists when borrower funds are pulled and later forwarded to withdrawal reserves. A fee-on-transfer repayment delivers less than the requested amount, but downstream logic proceeds as if the nominal amount arrived; insufficient follow-on liquidity is treated as borrower failure/default, while any reserve consumed to make the transfer succeed creates bad debt. [3](#0-2) [4](#0-3) 

### Finding Description

The credit-vault factory accepts `cvParams.underlying` and initializes both the CDO and `IdleCreditVault` with that arbitrary ERC20 address; no code rejects fee-on-transfer tokens. [5](#0-4) [6](#0-5) 

During deposit, the CDO first records `_preBal`, transfers `_amount` from the lender, and mints only `balanceAfter - _preBal` worth of tranche shares. That first leg is fee-aware. [7](#0-6) 

The accounting then regresses: `_deposit` invokes `IIdleCDOStrategy(strategy).deposit(_amount)` with the original nominal amount rather than the measured amount received. `IdleCreditVault.deposit` performs `underlyingToken.safeTransferFrom(idleCDO, strategy, _amount)` and unconditionally `_mint(idleCDO, _amount)`. A second transfer fee therefore leaves the strategy holding `_amount - fee`, while the CDO owns `_amount` strategy tokens whose `price()` is always one underlying unit. [8](#0-7) [9](#0-8) [10](#0-9) 

For example, with a 5% transfer fee:

1. The CDO already holds 50 raw underlying.
2. A lender deposits 1,000.
3. The lender-to-CDO transfer delivers 950, so the lender receives only 950 units of tranche exposure.
4. The CDO asks the strategy to pull 1,000. The strategy receives 950 after the second fee and mints 1,000 strategy tokens to the CDO.
5. The CDO's 50-unit raw reserve is consumed, while the strategy-token balance overstates actual strategy-held underlying by 50.

The CDO's `getContractValue` counts strategy tokens at face value plus raw underlying, so the resulting missing assets remain embedded in NAV and tranche pricing. [11](#0-10) 

A related mismatch exists in `finalizeDefaultRecovery`: the strategy adds nominal `_recoveredAmount` to `defaultRecoveryReserve` before pulling that amount, but does not reduce the reserve by any transfer fee. The recorded claim reserve can therefore exceed the tokens actually held, leaving later recovery claims underfunded or reverted. [12](#0-11) 

### Impact Explanation

Each successful CDO deposit with a fee-on-transfer underlying overmints strategy tokens by the fee charged on the CDO-to-strategy transfer. The deficit is equal to that second transfer fee and is borne by the vault rather than the depositor, whose tranche mint was already reduced by the first fee. [1](#0-0) [13](#0-12) 

This creates strategy-token insolvency and can transfer value from existing raw reserves or later users to earlier claims. Where the nominal pull exceeds available CDO balance, the deposit instead reverts, temporarily blocking deposits; where borrower or recovery transfers are involved, the shortfall can strand withdrawal or default-recovery claims and produce bad debt despite an honest payer approving the requested amount. [3](#0-2) [14](#0-13) 

### Likelihood Explanation

The bug requires the vault's configured `token` to charge a transfer fee. Deployment does not enforce otherwise because the underlying is supplied as a parameter to the external factory deployment path. [15](#0-14) [16](#0-15) 

The deposit exploit succeeds only while the CDO holds enough raw underlying to cover the first transfer fee; otherwise `strategy.deposit(_amount)` reverts after requesting more than the CDO received. Raw balances can exist as direct transfers or funds returned to the CDO before being forwarded, and the balance-aware minting path explicitly anticipates measuring incoming deltas rather than trusting `_amount`. Borrower-repayment and recovery paths do not require attacker-controlled reserve seeding because the protocol itself requests nominal sums. [11](#0-10) [1](#0-0) [4](#0-3) 

### Recommendation

Use balance deltas for every underlying movement that mints shares, reserves recovery funds, or funds withdrawal claims.

At minimum:

```solidity
uint256 before = underlyingToken.balanceOf(address(this));
underlyingToken.safeTransferFrom(msg.sender, address(this), _amount);
uint256 received = underlyingToken.balanceOf(address(this)) - before;
_mint(msg.sender, received);
totEpochDeposits += received;
return received;
```

That change belongs in `contracts/strategies/idle/IdleCreditVault.sol` `deposit`, and the CDO should pass the measured amount it received rather than the original `_amount`. [1](#0-0) [17](#0-16) 

Apply the same before/after pattern to `getFundsFromBorrower`, `collectWithdrawFunds`, `collectInstantWithdrawFunds`, `finalizeDefaultRecovery`, borrower funding, and any WriteOffEscrow fulfillment path. Revert or explicitly reconcile the shortfall rather than treating nominal approval as receipt. [3](#0-2) [14](#0-13) 

If fee-on-transfer assets are not intended to be supported, restrict deployment to an allowlist of known non-fee tokens or explicitly validate token behavior during deployment. [5](#0-4) 

### Proof of Concept

A focused Foundry test can reproduce the overmint without relying on the external report:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import "@openzeppelin/contracts/token/ERC20/ERC20.sol";
import "../contracts/strategies/idle/IdleCreditVault.sol";
import "../contracts/IdleCDOEpochVariant.sol";

contract FeeToken is ERC20 {
    uint256 public constant FEE_BPS = 500; // 5%

    constructor() ERC20("Fee Token", "FEE") {
        _mint(msg.sender, 1_000_000 ether);
    }

    function mint(address to, uint256 amount) external {
        _mint(to, amount);
    }

    function _update(address from, address to, uint256 amount) internal override {
        if (from == address(0) || to == address(0)) {
            super._update(from, to, amount);
            return;
        }

        uint256 fee = amount * FEE_BPS / 10_000;
        super._update(from, to, amount - fee);
        super._update(from, address(0xdead), fee);
    }
}

contract FeeOnTransferCreditVaultTest is Test {
    FeeToken token;
    IdleCreditVault strategy;
    IdleCDOEpochVariant cdo;
    address attacker = address(0xA11CE);

    function testDepositOvermintsStrategyTokens() public {
        token = new FeeToken();

        // Deploy and initialize through the normal proxy/factory fixture used by
        // test/foundry/IdleCreditVault.t.sol. The important parameters are:
        // token == address(token)
        // strategy == IdleCreditVault
        // cdo.strategy == address(strategy)
        // cdo.token == address(token)

        // Seed raw CDO reserve so the nominal CDO-to-strategy pull succeeds.
        token.transfer(address(cdo), 50 ether);

        token.mint(attacker, 1_000 ether);
        vm.prank(attacker);
        token.approve(address(cdo), 1_000 ether);

        uint256 strategyTokenBefore = token.balanceOf(address(strategy));

        vm.prank(attacker);
        uint256 mintedTranches = cdo.depositAA(1_000 ether);

        // First transfer fee: attacker receives only 950 backing.
        assertEq(mintedTranches, 950 ether);

        // Second transfer fee: strategy receives 950, not 1,000.
        uint256 strategyReceived =
            token.balanceOf(address(strategy)) - strategyTokenBefore;
        assertEq(strategyReceived, 950 ether);

        // IdleCreditVault nevertheless minted the nominal amount.
        assertEq(strategy.balanceOf(address(cdo)), 1_000 ether);

        // The CDO recognizes 1,000 strategy-token units while the strategy holds
        // only 950 underlying units. The 50-unit raw reserve was consumed to make
        // the nominal transfer succeed.
        assertEq(token.balanceOf(address(cdo)), 0);
        assertEq(cdo.getContractValue(), 1_000 ether);
        assertEq(
            token.balanceOf(address(strategy)) + token.balanceOf(address(cdo)),
            950 ether
        );
    }
}
```

The asserted invariant is that `strategy.balanceOf(cdo)` must not exceed the strategy's actual underlying balance plus any explicitly recorded non-underlying backing. Here it exceeds actual strategy-held underlying by the 5% second-transfer fee, while the pre-existing 50-unit CDO reserve disappears. [18](#0-17) [11](#0-10)
