### Title
Attacker-controlled ERC4626 liquidity drain makes `stopEpoch` uncallable, freezing all tranche withdrawals - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`IdleCDOEpochVariant._stopEpoch` delegates liquidity recall to `ProgrammableBorrower.onStopEpoch`, which calls `vault.withdraw(shortfall, ...)` on an external ERC4626 vault (e.g., a MetaMorpho vault). When the withdrawal reverts, the hook reverts with `StopEpochVaultLiquidityUnavailable`, bubbling up and reverting the whole `stopEpoch` transaction. Because ERC4626 `withdraw` only succeeds when the vault has sufficient *idle* (unallocated) liquidity, any unprivileged holder of the vault's shares (or a borrower in the vault's underlying markets) can keep idle liquidity below `shortfall`, causing every `stopEpoch` call to revert. The epoch can never be stopped, so no withdraw requests are ever fulfilled and no new epoch can start — a spurious, repeated "crash" of the epoch state machine analogous to `fuse_do_getattr()` marking a healthy inode bad and crashing. ### Finding Description
The bug class in CVE-2020-36322 is "inappropriate state marking/failure in a situation the code should have tolerated, producing a denial of service." In idle-tranches, the matching surface is the programmable-borrower stop-epoch path:

1. During a running epoch, the facility's idle cash is parked in an external ERC4626 `vault` via `_depositToVault` (`ProgrammableBorrower.sol:216`).
2. When the manager calls `stopEpoch`, `_stopEpoch` computes `_amountToPullFromBorrower + _pendingWithdraws` and calls `onStopEpoch` (`IdleCDOEpochVariant.sol:398`).
3. `onStopEpoch` computes `shortfall = _amountRequired - onHand` and, provided `shortfall <= _currentVaultAssets()` (the *accounting* value of shares), calls `vault.withdraw(shortfall, address(this), address(this))` (`ProgrammableBorrower.sol:240-246`).
4. If `vault.withdraw` reverts — which happens whenever the vault's idle liquidity is below `shortfall`, even though the borrower's shares are fully backed — the catch reverts with `StopEpochVaultLiquidityUnavailable` (`ProgrammableBorrower.sol:251-252`).
5. This revert propagates out of `onStopEpoch`, out of `_stopEpoch`, and reverts the entire manager `stopEpoch` transaction. Unlike the `getFundsFromBorrower` transfer (which is wrapped in try/catch and falls back to `_handleBorrowerDefault`), this failure path is unrecoverable within the call and repeatable indefinitely.

An unprivileged attacker who is a user of the ERC4626 vault can, in the same block as (or before) each `stopEpoch` call, remove the vault's idle liquidity below `shortfall` — e.g., by redeeming their own vault shares, or by borrowing/withdrawing liquidity in the vault's underlying markets (for MetaMorpho, borrowing against Morpho markets drains the market liquidity that backs `maxWithdraw`). The accounting value `_currentVaultAssets()` is unchanged by liquidity moves (share price is unaffected), so the guard at line 245 still passes and the doomed `vault.withdraw` is attempted and reverts every time.

While `stopEpoch` is bricked:
- `isEpochRunning` stays true, so `requestWithdraw` / `depositDuringEpoch` remain gated, and all `pendingWithdraws` already queued stay unfunded forever (funds were pulled into the borrower at `startEpoch`).
- `claimWithdrawRequest`/`claimInstantWithdrawRequest` have nothing to pay because `collectWithdrawFunds` is only reached after the successful pull (`IdleCDOEpochVariant.sol:408-410`).
- The pool cannot be closed, defaulted (the honest `transferFrom` failure path is never reached because the revert happens earlier), or restarted.

This is distinct from the legitimate `shortfall > _currentVaultAssets()` real-default path (`ProgrammableBorrower.sol:245`), where the hook correctly returns `true` so the outer `try/catch` triggers `_handleBorrowerDefault`. The flaw is that a *transient, attacker-manufacturable* liquidity condition is treated the same as an unrecoverable accounting failure — the withdraw is attempted inline instead of being bounded by `vault.maxWithdraw(address(this))`, and the revert is allowed to kill the whole state transition rather than degrading to default or a partial pull.

### Impact Explanation
Temporary freezing of all user funds in the pool. For as long as the attacker keeps vault idle liquidity below `shortfall` (cheap to sustain — the attacker only needs to front a redeem/borrow in the same block as each `stopEpoch` attempt, and can recycle capital), every LP's principal and every pending withdraw receipt is frozen inside a running epoch that cannot end. Quantified: 100% of `pendingWithdraws` plus all active tranche NAV (`lastNAVAA + lastNAVBB`) are unclaimable for the duration of the grief; unlike a genuine default, no `finalizeDefault` recovery path is even reachable, so there is no terminal state users can exit through. Existing guards do not help: the `shortfall > _currentVaultAssets()` check tests accounting value, not withdrawable liquidity, and the try/catch in `IdleCDOEpochVariant.sol:501-505` never runs because the hook reverts before `getFundsFromBorrower` is attempted.

### Likelihood Explanation
Requires only an unprivileged account able to transact with the configured ERC4626 vault — an explicitly in-scope attacker ("a user of the programmable borrower's ERC4626 vault"). MetaMorpho-style vaults routinely run with most assets allocated and little idle liquidity, so `shortfall` exceeding idle cash is a normal condition, not an edge case. The attacker needs no privileged role and no cooperation from borrower/manager; the window is every `stopEpoch` call after `epochEndDate`. Cost is limited to transaction fees plus temporarily locking capital in the vault/markets.

### Recommendation
In `ProgrammableBorrower.onStopEpoch`, bound the recall by actual withdrawable liquidity instead of accounting value: compute `maxW = vault.maxWithdraw(address(this))`, attempt `vault.withdraw(min(shortfall, maxW), ...)`, and treat the residual shortfall as either (a) a partial pull followed by a second `transferFrom` attempt inside the CDO's existing try/catch so the pool degrades to `_handleBorrowerDefault` cleanly, or (b) an explicit, documented default condition. At minimum, never let a third-party liquidity revert propagate unclassified out of the state-transition function — either convert it into the default path (so users get `finalizeDefault` recovery) or withdraw what is available and let the CDO's `transferFrom` catch block decide.

### Proof of Concept
Reproducible Foundry fork PoC (against a live MetaMorpho USDC vault, as in `test/foundry/ProgrammableBorrowerCreditVault.t.sol`):

```solidity
function testStopEpochBrickedByVaultLiquidityDrain() external {
    uint256 amount = 10_000 * oneScale;
    vm.prank(owner);
    cdoEpoch.setIsInterestMinted(true);

    idleCDO.depositAA(amount);
    // Queue a normal withdraw so stopEpoch needs to pull cash
    cdoEpoch.requestWithdraw(aaTranche.balanceOf(address(this)) / 2, address(aaTranche));
    _startEpochAndCheckPrices(0); // idle cash parked into MetaMorpho vault

    uint256 pendingWithdraws = strategy.pendingWithdraws();
    assertGt(pendingWithdraws, 0);

    // Attacker: unprivileged user of the same ERC4626 vault drains idle liquidity
    // below `shortfall`, e.g. redeeming a large share position or borrowing in the
    // vault's underlying Morpho markets, so that vault.withdraw(shortfall) reverts
    // even though convertToAssets(borrowerShares) >= shortfall.
    address attacker = makeAddr('attacker');
    _drainVaultIdleLiquidity(attacker, pendingWithdraws - 1); // helper: deposit+redeem/borrow
    assertLt(availableIdleLiquidity(vault), pendingWithdraws);
    assertGe(vault.convertToAssets(vault.balanceOf(address(programmableBorrower))), pendingWithdraws);

    vm.warp(cdoEpoch.epochEndDate() + 1);

    // Every stopEpoch attempt reverts; epoch can never close.
    vm.expectRevert(StopEpochVaultLiquidityUnavailable.selector);
    vm.prank(manager);
    cdoEpoch.stopEpoch(0, 0);

    assertFalse(cdoEpoch.defaulted());        // no default path reached
    assertTrue(cdoEpoch.isEpochRunning());    // epoch stuck running
    assertEq(strategy.pendingWithdraws(), pendingWithdraws); // receipts unfunded

    // Repeatable: attacker re-drains liquidity on each retry; withdraw receipts
    // and all active tranche NAV stay frozen with no finalizeDefault escape.
}
```

The same pattern already exists in the codebase's own regression test `testProgrammableBorrowerStopEpochRevertsWhenVaultLiquidityUnavailable` (`test/foundry/ProgrammableBorrowerCreditVault.t.sol:372-399`), which confirms the revert path; the finding is that this revert is attacker-manufacturable on real vaults and leaves no terminal exit for LPs.
