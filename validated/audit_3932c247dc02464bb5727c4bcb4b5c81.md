### Title
Post-default instant-withdraw requests write into the finalized default-epoch bucket and drain `defaultRecoveryReserve` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw` has an explicit `defaultRecoveryFinalized` branch that routes new requests into `postDefaultRequests` and rejects users with pending claims (`IdleCreditVault.sol:247-257`). `requestInstantWithdraw` has no equivalent branch (`IdleCreditVault.sol:356-375`). After default finalization it still mints a receipt and records it under `instantWithdrawsRequestsByEpoch[user][epochNumber]`. Because `epochNumber` no longer advances after default, `epochNumber == defaultRecoveryEpoch`, so a brand-new, fully-backed post-default receipt is aliased onto the finalized default-epoch bucket. `claimInstantWithdrawRequest` then clears it through `_claimDefaultedInstantWithdrawRequest`, which pays `claimBasis * defaultRecoveryPrice` out of `defaultRecoveryReserve` (`IdleCreditVault.sol:380-393`, `842-856`) — reserve that was sized at finalization to cover only default-epoch claimants.

### Finding Description
The UAF analog is reuse of finalized (logically freed) epoch state: `epochNumber` is frozen at `defaultRecoveryEpoch` once the pool is defaulted, so every post-default `requestInstantWithdraw` re-enters the already-settled epoch bucket instead of a fresh one.

Concretely:

- `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) has no `defaultRecoveryFinalized` check, unlike `requestWithdraw` (`:247`). It executes `instantWithdrawsRequestsByEpoch[_user][epochNumber] += _amount` and `instantWithdrawClaimsByEpoch[epochNumber] += _amount`, where `epochNumber == defaultRecoveryEpoch`.
- On claim, `claimInstantWithdrawRequest` sees `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized` and invokes `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` — now containing the attacker's new receipt — burns it, and calls `_transferDefaultRecovery`, which does `defaultRecoveryReserve -= amount` and transfers underlying (`:912-917`).
- The reserve accounting set in `finalizeDefaultRecovery` (`:685-709`) assumed `instantWithdrawClaimsByEpoch[defaultRecoveryEpoch]` was the complete instant basis. Post-default deposits inflate both the per-user epoch slot and `instantWithdrawClaimsByEpoch`, so each post-default claim consumes reserve allocated to honest default-epoch claimants. Since the attacker deposits post-default and immediately withdraws at `defaultRecoveryPrice`, they recycle the reserve; honest claimants' later `_transferDefaultRecovery` calls underflow (`defaultRecoveryReserve -= _amount` reverts) once it is depleted, permanently freezing their claims.
- Additionally, if `reserveAmount > totalBasis` at finalization (`defaultRecoveryPrice > RECOVERY_FULL`, explicitly allowed per `:687`), each post-default instant claim pays out *more* than the basis minted — a direct profit loop until the reserve is empty.
- Related corruption: `_claimDefaultedInstantWithdrawRequest` clamps `pendingInstantWithdraws` to 0 when `claimBasis >= pending` (`:849-852`), so a large post-default receipt also zeroes the unfunded counter that other accounting (e.g., `defaultPendingClaimBasis`) relies on.

No guard stops this: `_onlyIdleCDO` is satisfied through the normal CDO `requestInstantWithdraw` entry point, `_ensureDefaultRecoveryInitialized` is a no-op post-init, and there is no post-default reject path on the instant flow.

### Impact Explanation
Direct theft of `defaultRecoveryReserve` and permanent freezing of honest default-epoch claimants' recovery. The attacker deposits `X` underlying post-default (funds go to the defaulted borrower / strategy), receives an `X`-sized receipt aliased to `defaultRecoveryEpoch`, and claims `X * defaultRecoveryPrice / 1e18` from the reserve. This is repeatable until the reserve is exhausted; if `defaultRecoveryPrice > 1e18` each iteration is net-profitable. Loss is bounded by `defaultRecoveryReserve`, i.e., up to the entire recovered amount earmarked for all default-epoch receipt holders.

### Likelihood Explanation
Requires the vault to be in the defaulted-and-finalized state with a non-zero `defaultRecoveryReserve`, and instant withdrawals to remain callable on the CDO post-default (the instant path is gated on the CDO side by the instant-withdraw enable/delay flags and epoch phase — I could not fully confirm within the available context that `IdleCDOEpochVariant.requestInstantWithdraw` is ungated after `defaulted()`, so reachability should be verified; the strategy-side missing guard is unconditional regardless). Preconditions are plausible: default finalization is a normal mode the code explicitly supports, and the asymmetry with `requestWithdraw`'s explicit post-default branch indicates the instant path was overlooked.

### Recommendation
Mirror the `requestWithdraw` treatment in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is true, either revert (`NotAllowed`) or route the request into `postDefaultRequests` so it is paid 1:1 from prefunded post-default backing, never from `defaultRecoveryReserve`. Also consider keying post-default receipts to a distinct epoch bucket (e.g., `epochNumber + 1`) so they cannot alias `defaultRecoveryEpoch` while `epochNumber` is frozen.
