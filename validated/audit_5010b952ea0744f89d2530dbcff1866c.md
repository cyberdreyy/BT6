### Title
Unbounded per-request CPU cost via zstd compression of maximum-sized account data in `Base64Zstd` encoding - (File: `account-decoder/src/lib.rs`)

### Summary
`encode_ui_account` performs synchronous zstd compression of the entire (post-slice) account data whenever `UiAccountEncoding::Base64Zstd` is requested, with no cap on input size independent of `account.data().len()`. An attacker can grow an owned account to the maximum permitted size via `Allocate`/realloc and repeatedly request it through `getAccountInfo`/`getProgramAccounts` with `encoding: base64+zstd`, forcing the validator's RPC thread pool to run a full compression pass over attacker-chosen (e.g., incompressible) data on every single call.

### Finding Description
`encode_ui_account` in [1](#0-0)  handles `UiAccountEncoding::Base64Zstd` by constructing a `zstd::stream::write::Encoder` and calling `write_all` on `slice_data(account.data(), data_slice_config)` — i.e., the full account data by default (no `data_slice` supplied) — with no length check comparable to the `MAX_BASE58_BYTES` guard used for `Base58`/`Binary` encodings in `encode_bs58` ( [2](#0-1) ).

This function is reached directly from `getAccountInfo` via `RpcClient::get_account_info` → `JsonRpcRequestProcessor::get_account_info` → `get_encoded_account` → `encode_account` → `encode_ui_account`, and from `getProgramAccounts` via `get_program_accounts` → `encode_account` ( [3](#0-2)  and [4](#0-3) ). Unlike Base58, `encode_account` performs its size-limiting check only `if (encoding == UiAccountEncoding::Binary || encoding == UiAccountEncoding::Base58)` ( [5](#0-4) ); `Base64Zstd` falls through to the `else` branch with no size restriction at all.

An unprivileged attacker can grow an account they own up to `MAX_PERMITTED_DATA_LENGTH` bytes (~10 MiB) using the System Program's `Allocate` instruction, which is bounded only by that constant, not by any smaller practical cap ( [6](#0-5) ). They then fill it with high-entropy (incompressible) data via their own program logic (out of scope to detail further, but reachable since the attacker fully controls their own account's contents through normal transactions). Once the account exists on-chain, a single `getAccountInfo` (or `getProgramAccounts`) call specifying `encoding: "base64+zstd"` causes `encode_ui_account` to run zstd compression over the entire ~10 MB of attacker-chosen bytes synchronously in the RPC handler's blocking task (`spawn_blocking` in `get_account_info`, [7](#0-6) ). Compression of incompressible/random data is markedly slower than for all-zero data because it can't find repeated matches, so CPU/latency scales with attacker-authored account size and entropy, not with any fixed request-level cost cap.

### Impact Explanation
This falls under the "RPC DoS from a single low-rate call" bounty category: a single unprivileged JSON-RPC request (within the `CLUSTER_SLOT_TIME_TARGET / 2` cadence limit) triggers unbounded, attacker-scalable CPU work on the validator's RPC processing path, with no explicit cost cap tied to the encoding choice. Repeated, allowed-rate calls against a maximally-sized attacker-controlled account can degrade RPC responsiveness or consume RPC thread-pool capacity disproportionately to normal usage, without requiring multiple clients, unfiltered `getProgramAccounts` scans, or secondary-index abuse.

### Likelihood Explanation
Feasibility is high and fully within an unprivileged attacker's control: growing an owned account to near-maximum size via `Allocate`/realloc is a normal, permitted operation, and choosing `encoding=base64+zstd` is a standard, publicly documented RPC parameter. No special privileges, validator control, or multiple concurrent clients are needed — a single client issuing one call per allowed interval is sufficient to repeatedly trigger the expensive compression path indefinitely.

### Recommendation
Apply an explicit size cap for `Base64Zstd` encoding in `encode_account`/`encode_ui_account` analogous to the `MAX_BASE58_BYTES` check for `Base58`/`Binary` — e.g., reject (or fall back to plain `Base64`) if the sliced data exceeds a fixed threshold, or cap the number of bytes fed to `zstd::stream::write::Encoder` regardless of `account.data().len()`, decoupling worst-case per-request compression cost from attacker-controlled account size.

```rust
use std::time::Instant;

#[test]
fn bench_base64zstd_cost_scales_with_account_size() {
    let max_size = 10 * 1024 * 1024; // MAX_PERMITTED_DATA_LENGTH
    let zero_account = AccountSharedData::from(Account {
        data: vec![0u8; max_size],
        ..Account::default()
    });
    let mut rng_data = vec![0u8; max_size];
    // fill with pseudo-random incompressible bytes
    for (i, b) in rng_data.iter_mut().enumerate() {
        *b = (i as u64).wrapping_mul(2654435761).to_le_bytes()[0];
    }
    let random_account = AccountSharedData::from(Account {
        data: rng_data,
        ..Account::default()
    });

    let t0 = Instant::now();
    let _ = encode_ui_account(&Pubkey::default(), &zero_account, UiAccountEncoding::Base64Zstd, None, None);
    let zero_time = t0.elapsed();

    let t1 = Instant::now();
    let _ = encode_ui_account(&Pubkey::default(), &random_account, UiAccountEncoding::Base64Zstd, None, None);
    let random_time = t1.elapsed();

    // EXPECTED (currently failing): there should be a per-request cost cap
    // independent of account.data().len(), so times should be bounded and
    // comparable regardless of content/size. Today, random_time will be
    // substantially larger due to compression working harder on incompressible
    // data, with no code path enforcing an upper bound before compressing.
    assert!(
        random_time.as_millis() < 5, // placeholder for "cheap regardless of size/content"
        "Base64Zstd encoding cost is unbounded and scales with attacker-controlled \
         account size/entropy: zero={:?} random={:?}",
        zero_time,
        random_time
    );
}
```
Expected result on current code: the assertion fails, demonstrating that `encode_ui_account`'s `Base64Zstd` branch has no fixed per-request cost cap and its runtime is driven by attacker-controlled account size/content, unlike the `Base58` path which is bounded by `MAX_BASE58_BYTES`.
