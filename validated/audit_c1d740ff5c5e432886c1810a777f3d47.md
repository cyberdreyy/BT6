### Title
Missing Merkle-proof length/depth validation in `BlockIdRepairType::FecSetRoot` verification allows forged intermediate-node roots to pass proof checks - (File: `core/src/repair/serve_repair.rs`)

### Summary
`BlockIdRepairType::verify_response` for the `FecSetRoot` variant only checks that the returned Merkle proof is non-empty before calling `merkle_tree::verify_merkle_proof`, unlike the sibling `ParentAndFecSetCount` branch which explicitly computes and enforces the exact expected proof length. `merkle_tree::verify_merkle_proof`/`get_merkle_root` (in `ledger/src/shred/merkle_tree.rs`) never validates that the number of supplied proof entries matches the real depth of the double-Merkle tree for the requested leaf position — this is the same root cause as the reported `WithdrawTrieVerifier` bug: a shortened proof can be used to “prove” an intermediate tree node as if it were the target leaf, because the fold only checks that the running index reaches `0`, not that the path length is correct.

### Finding Description
The double-Merkle tree verification helpers live in `ledger/src/shred/merkle_tree.rs`: [1](#0-0) 

`get_merkle_root` folds over whatever proof entries are supplied, shifting `index` right each iteration, and only rejects the result if the final `index != 0`. It performs no check that the number of folded entries corresponds to the actual depth from the claimed leaf to the root. `verify_merkle_proof` inherits this weakness and additionally does not check `proof.len()` against any expected value before calling `get_merkle_root`.

This function is used by `BlockIdRepairType::verify_response` in `core/src/repair/serve_repair.rs` to authenticate metadata returned by an arbitrary (untrusted) cluster peer answering a block-id repair request: [2](#0-1) 

For `ParentAndFecSetCount`, the code explicitly derives the correct `proof_size` from `fec_set_count` and rejects any proof whose length does not match exactly (lines 306-311). For `FecSetRoot`, however, the only length-related guard is `fec_set_proof.is_empty()` (line 340) — there is no check that `fec_set_proof.len()` corresponds to the real depth for `fec_set_index`.

Because a malicious repair responder can observe the entire real double-Merkle tree for a slot (it is public data broadcast via Turbine), it can pick any genuine intermediate node `X` at some level `m` on the true ancestor path of the requested `fec_set_index`, and present `X` as the “`fec_set_root`” together with the genuine suffix of the real proof (levels `m..depth`). Since `X` and the suffix are authentic values from the real tree, the fold in `get_merkle_root` reproduces the true `block_id` exactly, and `verify_merkle_proof` succeeds — even though `X` is not the true FEC-set root leaf, just an internal node reinterpreted as a leaf via a shortened proof. This is a direct structural analog of the `WithdrawTrieVerifier` issue: proof-length is never validated, so an intermediate node can be substituted for the intended leaf.

### Impact Explanation
The client (`BlockIdRepairService`) treats the (forged) `fec_set_root` as trustworthy once `verify_response` returns `true`: [3](#0-2) 

It then issues `ShredForBlockId` repair requests keyed on this bogus root. Since no genuine, leader-signed shred will ever carry that root (real shreds embed and are signed over the true FEC-set root, not an unrelated internal tree node), these follow-up requests can never be satisfied. This lets any single malicious peer that is selected to answer a `BlockIdRepairType::FecSetRoot` request permanently poison the client’s repair state for that FEC set with an unresolvable root, wasting repair bandwidth/retries and stalling the node’s ability to reconstruct the alternate block (a resource-exhaustion / repair-starvation condition on the node’s block-sync path), without requiring any privileged access, leaked keys, or MITM — just being a normal peer that responds to a routed repair request.

### Likelihood Explanation
Any node participating as a peer can be selected to answer `BlockIdRepairType` requests via the standard repair peer-selection mechanism (`ServeRepair`), and crafting the forged response requires no cryptographic break — only replaying real, already-public intermediate hashes and proof suffixes the attacker legitimately observed from Turbine. This makes the attack straightforward to mount by any adversarial cluster participant that is a repair peer, without needing to be a stake-weighted leader or otherwise privileged.

### Recommendation
Add an explicit proof-length/depth check in the `FecSetRoot` branch of `BlockIdRepairType::verify_response`, analogous to the one already present for `ParentAndFecSetCount`: compute the expected proof length for `fec_set_index` from the known/expected tree size (e.g., total number of leaves = `fec_set_count + 1`, tracked once known, or otherwise bound proof length to `get_proof_size`) and reject any `fec_set_proof` whose length does not exactly match. More generally, harden `merkle_tree::verify_merkle_proof`/`get_merkle_root` to take an expected proof length (tree depth) parameter and fail if the supplied proof does not have exactly that many entries, rather than relying solely on the terminal `index == 0` check.

### Proof of Concept
1. Attacker observes the real double-Merkle tree for slot `S` (public via Turbine) with true root `block_id` and true FEC-set leaves at various depths.
2. Victim sends `BlockIdRepairType::FecSetRoot { slot: S, block_id, fec_set_index }` to the attacker (selected as a repair peer).
3. Attacker picks any genuine intermediate node `X` at depth `m` on the ancestor path implied by `fec_set_index`, and responds with `BlockIdRepairResponse::FecSetRoot { fec_set_root: X, fec_set_proof: <real suffix proof from depth m to root> }`.
4. `BlockIdRepairType::verify_response` (`core/src/repair/serve_repair.rs:333-353`) calls `merkle_tree::verify_merkle_proof(X, leaf_index, suffix_proof, block_id)`, which succeeds since the math correctly reconstructs `block_id`.
5. `process_block_id_repair_response` in `block_id_repair_service.rs` accepts `X` as `fec_set_merkle_root` and queues `ShredForBlockId` requests keyed on `X`, which no genuine signed shred can ever satisfy, stalling repair for that FEC set.

// Recovers root of the merkle tree from a leaf node
// at the given index and the respective proof.
pub fn get_merkle_root<'a, I>(index: usize, node: Hash, proof: I) -> Result<Hash, Error>
where
    I: IntoIterator<Item = &'a MerkleProofEntry>,
{
    let (index, root) = proof
        .into_iter()
        .fold((index, node), |(index, node), other| {
            let parent = if index % 2 == 0 {
                join_nodes(node, other)
            } else {
                join_nodes(other, node)
            };
            (index >> 1, parent)
        });
    (index == 0)
        .then_some(root)
        .ok_or(Error::InvalidMerkleProof)
}

/// Given a flattened merkle `proof` for `node` at `index`,
/// verify the proof against merkle root `root`
pub fn verify_merkle_proof(
    node: Hash,
    index: usize,
    proof: &[u8],
    expected_root: Hash,
) -> Result<(), Error> {
    let proof = proof
        .chunks(SIZE_OF_MERKLE_PROOF_ENTRY)
        .map(<&MerkleProofEntry>::try_from)
        .map(|entry| entry.map_err(|_| Error::InvalidMerkleProof))
        .collect::<Result<Vec<_>, Error>>()?;
    let merkle_root = get_merkle_root(index, node, proof)?;

    (merkle_root == expected_root)
        .then_some(())
        .ok_or(Error::InvalidMerkleProof)
}

    fn verify_response(&self, response: &Self::Response) -> bool {
        match (self, response) {
            (_, Self::Response::Ping { ping }) => ping.verify(),
            (
                Self::ParentAndFecSetCount {
                    slot: _slot,
                    block_id,
                },
                Self::Response::ParentFecSetCount {
                    fec_set_count,
                    parent_info: (parent_slot, parent_block_id),
                    parent_proof,
                },
            ) => {
                if *fec_set_count > MAX_FEC_SETS_PER_SLOT {
                    return false;
                }

                // + 1 here to account for the parent info which is the final leaf of the tree
                let proof_size = merkle_tree::get_proof_size(*fec_set_count as usize + 1);
                if parent_proof.len()
                    != proof_size as usize * merkle_tree::SIZE_OF_MERKLE_PROOF_ENTRY
                {
                    return false;
                }

                let parent_info_leaf = hashv(&[
                    &parent_slot.to_le_bytes(),
                    parent_block_id.as_ref(),
                    &fec_set_count.to_le_bytes(),
                ]);
                merkle_tree::verify_merkle_proof(
                    parent_info_leaf,
                    *fec_set_count as usize,
                    parent_proof,
                    *block_id,
                )
                .is_ok()
            }

            (
                Self::FecSetRoot {
                    slot: _slot,
                    block_id,
                    fec_set_index,
                },
                Self::Response::FecSetRoot {
                    fec_set_root,
                    fec_set_proof,
                },
            ) => {
                // The double-Merkle tree contains at least one FEC-set root and
                // the parent-info leaf, so a valid proof cannot be empty.
                if fec_set_proof.is_empty() {
                    return false;

                debug_assert_eq!(*fec_set_index as usize % DATA_SHREDS_PER_FEC_BLOCK, 0);

                    leaf_index,
                    fec_set_proof,
                    *block_id,
                )
                .is_ok()
            }

            (Self::ParentAndFecSetCount { .. }, _) | (Self::FecSetRoot { .. }, _) => false,
        }
