### Title
`rewardPerTokenStored` can be permanently pinned while `lastUpdateTime` advances, starving all reward distribution - ([File: contracts/StakingRewards.sol](contracts/StakingRewards.sol))

### Summary
`StakingRewards` (used by `IdleCDO` via `stakeFor`/`depositReward` to stream rewards to AA/BB tranche stakers, controlled by `AAStaking`/`BBStaking` deploy flags) uses the Synthetix `updateReward` modifier which unconditionally writes `lastUpdateTime = lastTimeRewardApplicable()` even when the `rewardPerToken()` increment rounds down to zero. An unprivileged staker can keep the elapsed-time delta small by calling `getReward()`/`stake()`/`withdraw()` every block, so the per-token accumulator never ticks while reward time is consumed. The same pattern exists in `contracts/DelegateStakingRewardsIDLE.sol`. [1](#0-0) [2](#0-1) 

### Finding Description
In `contracts/StakingRewards.sol`:

```solidity
// line 70
return rewardPerTokenStored + ((lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 / _totalSupply);
```

```solidity
// updateReward modifier
rewardPerTokenStored = rewardPerToken();
lastUpdateTime = lastTimeRewardApplicable();
```

The increment `(elapsed * rewardRate * 1e18) / _totalSupply` is integer-division truncated. When `_totalSupply > elapsed * rewardRate * 1e18` the increment is `0`, yet `lastUpdateTime` is still advanced, so that elapsed time is permanently discarded from the emission schedule. There is no checkpoint of un-accrued time and no mechanism to recover it before `periodFinish`.

`stake(uint256)`, `withdraw(uint256)` and `getReward()` are all public and unpermissioned (no whitelist, unlike `DelegateStakingRewardsIDLE`). A tranche-token holder stakes a small amount once, then calls `getReward()` on every block for the whole `rewardsDuration`. Each call rewrites `lastUpdateTime` to the current timestamp while adding `0` to `rewardPerTokenStored`, provided the staked supply and `rewardRate` satisfy `_totalSupply > Δt · rewardRate · 1e18` for a one-block `Δt` (~12 s on mainnet, ~2 s on L2s where the codebase also deploys — see `.openzeppelin/polygon.json` and `POLYGON_ZK_RPC_URL` in the README).

Rewards emitted during the griefed period are never credited to `rewards[account]` and remain in the contract balance.

### Impact Explanation
Direct suppression — and effective temporary freezing — of the entire reward budget for an epoch. All legitimate stakers (including the protocol's own `feeReceiver` position staked via `stakeFor` from `IdleCDO`) receive `0` rewards for the duration; the undistributed reward tokens sit in the contract until the owner calls `recoverERC20` (which only blocks `stakingToken`, not `rewardsToken`). The broken invariant is the emission-schedule conservation invariant: `elapsed time × rewardRate` must equal cumulative distributed rewards, and it does not.

Concrete quantification: with `rewardRate = 1e14` wei/s (~8.64 reward tokens/day) and `_totalSupply = 1e30` (e.g. 1e12 units of an 18-decimal tranche token, achievable since tranche supply scales with CDO deposits), a 12-second delta gives `12·1e14·1e18/1e30 < 1`, so every update accrues exactly zero while consuming 12 seconds. Sustained over `rewardsDuration = 1 day`, ~8.64 reward tokens (the full period budget) are withheld from all stakers.

### Likelihood Explanation
- Requirements: (a) `rewardRate` low relative to staked supply — true when `IdleCDO` streams small fee amounts or a low-value reward token over `rewardsDuration`; (b) an attacker willing to send one cheap `getReward()` transaction per block — cheap on Polygon/L2 deployments, which this codebase supports.
- The attack needs no privileged role: `stake`, `withdraw`, `getReward` are open to any tranche-token holder. Only 1 wei of staking token is needed to have a valid `account` for `getReward`.
- Even without an attacker, frequent `depositReward`/`stakeFor` calls triggered by `IdleCDO.harvest` flows produce the same truncation ("rounding eats into rewards"), systematically under-distributing relative to the configured `rewardRate`.
- Cost to attacker is gas only; griefed rewards are not stolen but frozen until owner recovery, matching the "temporary freezing of unclaimed yield" severity class.

### Recommendation
Only advance `lastUpdateTime` when the accumulator actually changes, preserving un-accrued time:

```solidity
modifier updateReward(address account) {
    uint256 newRewardPerToken = rewardPerToken();
    if (newRewardPerToken != rewardPerTokenStored) {
        rewardPerTokenStored = newRewardPerToken;
        lastUpdateTime = lastTimeRewardApplicable();
    }
    if (account != address(0)) {
        rewards[account] = earned(account);
        userRewardPerTokenPaid[account] = rewardPerTokenStored;
    }
    _;
}
```

(Scrutinize interplay with `depositReward`, which also sets `lastUpdateTime = block.timestamp` — the leftover calculation already accounts for un-accrued time via `remaining * rewardRate`.) Alternatively, track accrued reward time as a separate "reward debt" so fractional units are not discarded. Apply the same fix to `contracts/DelegateStakingRewardsIDLE.sol` (`updateReward` at line 206–214).

### Proof of Concept
Foundry fork/local test against `contracts/StakingRewards.sol`:

```solidity
function test_RewardAccumulationPinned() public {
    // Setup: stakingToken & rewardsToken are 18-dec mocks already deployed
    // stakingRewards.initialize(deployer, rewardToken, stakingToken, owner, true)

    // 1. Seed a large total supply (whale stakers)
    stakingToken.mint(whale, 1e30);
    vm.prank(whale);
    stakingToken.approve(address(sr), type(uint256).max);
    vm.prank(whale);
    sr.stake(1e30);                       // _totalSupply = 1e30

    // 2. Owner/distribution deposits rewards -> rate low vs supply
    rewardToken.mint(distribution, 8.64e18);
    vm.prank(distribution);
    rewardToken.approve(address(sr), 8.64e18);
    vm.prank(distribution);
    sr.depositReward(address(0), 8.64e18); // rewardRate = 1e14 wei/s

    // 3. Attacker stakes 1 wei, then calls getReward() every block
    stakingToken.mint(attacker, 1);
    vm.startPrank(attacker);
    stakingToken.approve(address(sr), 1);
    sr.stake(1);

    uint256 blocksInDay = 1 days / 12;     // ~7200 blocks at 12 s
    for (uint256 i; i < blocksInDay; ++i) {
        vm.warp(block.timestamp + 12);
        vm.roll(block.number + 1);
        sr.getReward();                    // advances lastUpdateTime, adds 0
    }
    vm.stopPrank();

    // 4. Assertions
    assertEq(sr.rewardPerTokenStored(), 0);        // accumulator never moved
    assertEq(sr.earned(whale), 0);                 // whale earned nothing
    assertEq(sr.earned(attacker), 0);
    assertEq(sr.lastUpdateTime(), block.timestamp);// time fully consumed
    // 8.64e18 rewardToken remains in the contract, undistributed
    assertEq(rewardToken.balanceOf(address(sr)), 8.64e18);
}
```

Key trace: each iteration computes `(12 * 1e14 * 1e18) / 1e30 = 0`, so `rewardPerTokenStored` stays `0` while `lastUpdateTime` walks forward to `periodFinish`. After the loop `block.timestamp >= periodFinish`, so even `rewardPerToken()` view returns `0` and no one can ever claim the period's rewards without an owner `recoverERC20` intervention.
