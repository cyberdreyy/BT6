## Title
Operator's pending commission bypasses configured beneficiary after `switch_operator` in `staking_contract` - (File: `aptos-move/framework/aptos-framework/sources/staking_contract.move`)

## Summary
`staking_contract::switch_operator` moves a `StakingContract` (including its `distribution_pool`) from the `old_operator` key to the `new_operator` key in the staker's `Store`, after first calling `request_commission_internal` for the old operator. That call books the old operator's unpaid commission as a distribution-pool share keyed under the raw `old_operator` address. Once the underlying stake becomes withdrawable and someone later calls `distribute()`, the payout is only redirected to `beneficiary_for_operator(operator)` when `recipient == operator` — but by then `operator` refers to `new_operator`, not `old_operator`. As a result, the old operator's already-accrued commission silently bypasses their configured `BeneficiaryForOperator` and is paid to the raw `old_operator` account address instead.

## Finding Description
`switch_operator` forces payout accounting before moving the staking contract to a new key: [1](#0-0) 

`request_commission_internal` records the commission as a distribution-pool share for `recipient = operator` (the old operator) via `add_distribution`: [2](#0-1) 

This share is not necessarily payable immediately — `stake::unlock_with_cap` only moves it to `pending_inactive`; it becomes withdrawable only once the stake pool's lockup expires. Meanwhile, the `StakingContract` struct (carrying its `distribution_pool` with the old operator's still-unpaid share) is removed from the `old_operator` key and re-inserted under `new_operator`: [3](#0-2) 

When `distribute()`/`distribute_internal` is later invoked (necessarily with `operator = new_operator`, since `old_operator` no longer exists as a key in `Store.staking_contracts`), the code only redirects a share's payout to the operator's beneficiary if the shareholder equals the *current* `operator` parameter: [4](#0-3) 

Since the leftover share's `recipient` is `old_operator` while `operator` is now `new_operator`, the `if (recipient == operator)` check is `false`, so `beneficiary_for_operator(old_operator)` is never consulted. The old operator's commission is deposited straight to the raw `old_operator` address rather than to their configured `BeneficiaryForOperator` address.

## Impact Explanation
Operators set a beneficiary via `set_beneficiary_for_operator` specifically so that commission payouts land on a chosen (e.g., cold-storage/custodial) address rather than the hot operator account: [5](#0-4) 

After a `switch_operator` call by the staker, any commission that was already accrued (and recorded via `request_commission_internal` during the switch) permanently loses this redirection: it is credited to the wrong account (the operator's own address) instead of the beneficiary the operator explicitly configured. This is an operator commission/beneficiary "credits the wrong account" corruption as covered by the required impact list, and can represent a meaningful, non-trivial amount of value routed away from the intended custody address without recourse for the operator once distributed.

## Likelihood Explanation
`switch_operator` and `switch_operator_with_same_commission` are unprivileged, ordinary staker-initiated entry functions with no special preconditions: [6](#0-5) 

Any staker who switches operators while the old operator has unpaid/unlocked-but-not-yet-withdrawable commission (a common, ordinary state given staking lockup periods) will trigger this misrouting for that operator once `distribute()` is eventually called. No attacker privilege is needed; the break arises purely from routine operator-switch/distribution sequencing.

## Recommendation
Track the beneficiary redirection per-recipient at the time the distribution share is recorded (e.g., store the resolved beneficiary alongside the share, or key on the `operator` value captured in `add_distribution` rather than the outer `distribute_internal`'s live `operator` argument), so that a share created for `old_operator` is always paid to `beneficiary_for_operator(old_operator)` regardless of subsequent operator switches.

## Proof of Concept
1. Staker creates a staking contract with `old_operator`, `commission_percentage > 0`.
2. `old_operator` calls `set_beneficiary_for_operator(operator, beneficiary_address)`.
3. Stake pool earns rewards; staker calls `switch_operator(staker, old_operator, new_operator, new_commission_percentage)`. Internally `request_commission_internal` books unpaid commission as a `distribution_pool` share under `old_operator`, then the `StakingContract` (with that pool) is re-keyed to `new_operator`.
4. After the lockup period elapses, anyone calls `distribute(staker_address, new_operator)`.
5. `distribute_internal` iterates shareholders; for the share with `recipient == old_operator`, the check `recipient == operator` (`operator == new_operator`) is false, so funds are sent directly to `old_operator`'s address instead of `beneficiary_address`, contradicting the beneficiary configuration set in step 2.

    fun request_commission_internal(
        operator: address,
        staking_contract: &mut StakingContract,
    ): u64 {
        // Unlock just the commission portion from the stake pool.
        let (total_active_stake, accumulated_rewards, commission_amount) =
            get_staking_contract_amounts_internal(staking_contract);
        staking_contract.principal = total_active_stake - commission_amount;

        // Short-circuit if there's no commission to pay.
        if (commission_amount == 0) {
            return 0
        };

        // Add a distribution for the operator.
        add_distribution(
            operator,
            staking_contract,
            operator,
            commission_amount
        );

        // Request to unlock the commission from the stake pool.
        // This won't become fully unlocked until the stake pool's lockup expires.
        stake::unlock_with_cap(commission_amount, &staking_contract.owner_cap);

    /// Allows an operator to change its beneficiary. Any existing unpaid commission rewards will be paid to the new
    /// beneficiary. To ensures payment to the current beneficiary, one should first call `distribute` before switching
    /// the beneficiary. An operator can set one beneficiary for staking contract pools, not a separate one for each pool.
    public entry fun set_beneficiary_for_operator(
        operator: &signer, new_beneficiary: address
    ) acquires BeneficiaryForOperator {
        assert!(
            features::operator_beneficiary_change_enabled(),
            std::error::invalid_state(EOPERATOR_BENEFICIARY_CHANGE_NOT_SUPPORTED)
        );
        // The beneficiay address of an operator is stored under the operator's address.
        // So, the operator does not need to be validated with respect to a staking pool.
        let operator_addr = signer::address_of(operator);
        let old_beneficiary = beneficiary_for_operator(operator_addr);
        if (exists<BeneficiaryForOperator>(operator_addr)) {
            borrow_global_mut<BeneficiaryForOperator>(operator_addr).beneficiary_for_operator =
                new_beneficiary;
        } else {
            move_to(
                operator,
                BeneficiaryForOperator { beneficiary_for_operator: new_beneficiary }
            );
        };

        emit(
            SetBeneficiaryForOperator {
                operator: operator_addr,
                old_beneficiary,
                new_beneficiary
            }
        );
    }
