## Analysis Result [1](#0-0) 

### Title
Stale confirmations from a removed multisig member remain counted toward quorum, allowing a request to execute below the declared `num_confirmations` threshold - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
`delete_member` (and `DeleteKey` in the legacy `multisig` contract) purges only the *requests created by* the removed member, but never scans and strips that member's *confirmations recorded on requests created by other members*. Because `confirm()` counts every entry in the `confirmations` set — including ones belonging to a member who is no longer part of `members` — a request can reach `num_confirmations` using votes from fewer *live* signers than the declared threshold, breaking the equality `confirmations.len() == live_signers_who_approved`.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` decides execution purely from set size:
```
if confirmations.len() as u32 + 1 >= self.num_confirmations {
    let request = self.remove_request(request_id);
    self.execute_request(request)
}
``` [2](#0-1) 

`delete_member` is the only place that removes stored state tied to a departing member, and it filters exclusively on `r.member == member` (i.e., who *authored* the request), then wipes only those authored requests' confirmations:
```
let request_ids: Vec<u32> = self.requests.iter()
    .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
    .collect();
for request_id in request_ids {
    self.confirmations.remove(&request_id);
    self.requests.remove(&request_id);
}
``` [3](#0-2) 

It never inspects `self.confirmations` entries for *other* requests (authored by different members) that the departing member may have already confirmed. Those stale entries stay in the `HashSet<String>` for that `request_id` forever.

`delete_member`'s only safety check is on member-count vs. threshold:
```
assert(
    self.members.len() - 1 >= self.num_confirmations as u64,
    "Removing given member will make total number of members below number of confirmations",
);
``` [4](#0-3) 
This guarantees enough *members exist*, but does nothing to guarantee that a pending request's confirmation count still reflects *live* member approval. The identical gap exists in the legacy `multisig` contract's `DeleteKey` handler, which filters on `r.signer_pk == pk` before clearing confirmations, leaving the deleted key's votes intact on requests it did not author. [5](#0-4) 

**Concrete violated equality:** the contract's implicit invariant is `num_confirmations` live-member approvals are required to execute a request. After a member removal, the real invariant becomes `confirmations ⊆ members`, but the code allows `confirmations ⊄ members` to persist and still be counted, so `live_approvals_needed(N) < num_confirmations` in practice.

### Impact Explanation
This is exactly the Critical impact category "a multisig request executed below threshold." With members `{A, B, C, D}` and `num_confirmations = 3`:
1. `A` creates and confirms a `Transfer` request `R` to an attacker-controlled account (`add_request_and_confirm`), leaving `confirmations(R) = {A}`.
2. Members separately confirm and execute a `DeleteMember{A}` request; `A` is removed. `R` is untouched because it was authored by `A`... wait, actually `R` was authored by `A`, so it *would* be purged. The stronger variant: `B` authors `R` (so `r.member == B`), and `A` merely *confirms* it. Now `confirmations(R) = {A, B}`. Removing `A` still only purges requests where `r.member == A`; `R` (authored by `B`) is untouched and keeps `A` in its confirmation set.
3. Members now number `{B, C, D}` = 3, satisfying `delete_member`'s assert (`3 >= 3`), so removal succeeds.
4. `C` confirms `R`: `confirmations(R).len() == 2` (`A`,`B`) before insert, `+1 == 3 >= num_confirmations(3)` → `R` executes.
5. `R` (e.g., a `Transfer` of NEAR out of the multisig account) executes with approvals from only two *live* members (`B`,`C`) plus one stale ghost vote from removed member `A`, instead of the required three live approvals from `{B,C,D}`.

Funds move (or an `AddKey`/`FunctionCall` action executes) without `D`'s consent, even though the contract's threshold was specifically set to require it. This directly matches "a multisig request executed below threshold" under Critical impact.

### Likelihood Explanation
This requires no external privilege beyond being (or having been) a normal multisig member — the exact actors the multisig is designed to coordinate among. Any two colluding remaining members can exploit a stale confirmation from a member removed after voting on a request they didn't author. This is a realistic operational sequence (member rotation is a normal multisig lifecycle event), not a theoretical edge case, and requires no cryptographic break, redeploy, or foundation/owner privilege.

### Recommendation
In `delete_member` (and `DeleteKey` in the legacy contract), iterate over **all** pending requests' confirmation sets — not just requests authored by the removed member — and remove the departing member's identity string from each. Alternatively, when counting confirmations in `confirm()`, filter the confirmation set against current `self.members` before comparing to `num_confirmations`, so any stale/removed identities are excluded at count time regardless of when cleanup happened.

### Proof of Concept
1. Deploy `multisig2` with `members = [A, B, C, D]`, `num_confirmations = 3`.
2. `B` calls `add_request` with `MultiSigRequestAction::Transfer{ amount }` targeting an attacker account → `request_id = R`.
3. `A` calls `confirm(R)` → `confirmations(R) = {A}`.
4. Members separately create/confirm a `DeleteMember{A}` request (using `B`, `C`, `D`'s 3 legitimate confirmations) → executes, `members = {B, C, D}`. `R` is untouched since `r.member == B`, not `A`, per the filter in `delete_member`.
5. `C` calls `confirm(R)` → `confirmations(R).len()==1 (A)`, `+1 = 2 < 3` → not yet executed, inserted, now `{A, C}`... 

   (Correcting to match code: after step 3, `confirmations(R) = {A}`, size 1. `C` confirms: `1 + 1 = 2 < 3`, adds `C` → `{A, C}`, size 2. `D` confirms: `2 + 1 = 3 >= 3` → executes.)
6. `R` executes using confirmations `{A (removed), C, D}` — i.e., a 2-of-3-live-member approval (`C`,`D`) is sufficient to move funds even though the contract enforces `num_confirmations = 3` and member `B`, the actual author, never had to re-approve, and `A`'s vote should have been invalidated on removal.     /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
