### Title
Stale confirmations from removed multisig members still count toward `num_confirmations`, allowing execution below threshold - (File: multisig2/src/lib.rs)

### Summary
`delete_member` in the `multisig2` contract removes a member from `self.members` and purges only the requests *that member authored*, but it never removes that member's confirmation entries recorded on requests authored by other members. `confirm()` counts confirmations purely by set size, without re-validating that each recorded confirmer is still a current member. This lets a stale confirmation from a deleted member continue to count toward the K-of-N threshold, so a request can be executed with fewer than `num_confirmations` live-member approvals.

### Finding Description
The multisig's core security invariant is: a request executes only once at least `num_confirmations` **current** members have confirmed it — i.e. `confirmations recorded == confirmations from live members`.

`confirm()` enforces the threshold purely numerically: [1](#0-0) 

`delete_member()` only cleans up requests *added by* the removed member, and their confirmations; it does not touch confirmations the removed member cast on requests added by other members: [2](#0-1) 

Sequence breaking the binding:
1. Multisig is `K`-of-`N` (e.g. 3-of-4): members `A, B, C, D`.
2. `A` creates request `R` (e.g. `Transfer` funds to attacker-controlled account, or `AddKey`). `B` confirms `R` — `confirmations(R) = {A, B}` (2 of 3 needed).
3. Before `C`/`D` confirm `R`, a separate governance action removes `B` from the multisig via `DeleteMember{member: B}` (perhaps legitimately, e.g. `B`'s key was compromised or `B` left the org). `delete_member` only looks at requests where `r.member == B` (i.e., requests *authored* by `B`); `R` was authored by `A`, so `R`'s confirmations set is untouched and still contains `B`.
4. Now only `C` (a genuinely still-current member) needs to call `confirm(R)`. `confirmations.len() = 2` (`A`, `B` — with `B` no longer a member) `+ 1 = 3 >= num_confirmations(3)`, so `execute_request` fires.
5. `R` executes having received real approval from only `A` and `C` — two currently live members — while the threshold nominally requiring 3 live approvals is bypassed because a removed member's stale approval is still counted.

This directly breaks the equality `confirmations counted == confirmations from live members`: the left side includes a member no longer in `self.members`, while the right side (actual live approvers) is one short of `num_confirmations`.

### Impact Explanation
This is Critical: a multisig `MultiSigRequest` (fund `Transfer`, `FunctionCall`, `AddKey`, `AddMember`, `DeleteMember`, `DeployContract`) can be executed with fewer than the configured `num_confirmations` live-member approvals. Since this contract is intended to gate movement of NEAR funds and control over the account (adding access keys, deploying new code), an attacker or colluding minority of members can leverage previously-cast confirmations from members who have since been removed to push through a transfer or account-takeover action that should have required more live approvals — i.e., "a multisig request executed below threshold" as defined in the impact criteria.

### Likelihood Explanation
This does not require any unauthorized access or compromised keys — it only requires the normal, expected operational sequence of "member confirms a request, then later that member is removed for any legitimate reason (turnover, compromised key rotation) before the request is executed," which is a realistic operational pattern for any multisig with member churn. No special privileges beyond being an ordinary current member are needed to trigger the outcome once the stale confirmation exists.

### Recommendation
When removing a member in `delete_member`, iterate over *all* active requests' confirmation sets (not just those authored by the removed member) and strip the removed member's identifier from each `confirmations` entry. Alternatively, when counting confirmations in `confirm()` (and before executing), filter the confirmation set to only those confirmer identifiers still present in `self.members` before comparing against `num_confirmations`, so stale/removed-member confirmations can never count toward the execution threshold.

### Proof of Concept
Using the contract's own test harness style (`multisig2/src/lib.rs` tests):
1. `MultiSigContract::new(members(), 3)` with members `{alice, bob, key_E, key_F}`.
2. As `alice`, `add_request` a `Transfer` request `R` to `bob`.
3. As `key_E`, `confirm(R)` — now `confirmations(R) = {alice, key_E}` (2/3).
4. As a current member, `add_request_and_confirm` a `DeleteMember{member: key_E}` request and get it confirmed by 3 members to execute — this removes `key_E` from `self.members`, but per `delete_member`'s logic (`multisig2/src/lib.rs:362-371`) it only scans/removes requests where `r.member == key_E` (i.e. requests key_E authored) — `R` was authored by `alice`, so `R`'s confirmations entry (still containing `key_E`) is untouched.
5. As `key_F` (the last live member besides alice), call `confirm(R)`. `confirmations.len() == 2` (`alice`,`key_E`) `+ 1 == 3 >= num_confirmations(3)` → `execute_request` fires, transferring funds — even though only `alice` and `key_F` are actually still members of the multisig (2 live confirmations, not 3).     fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }

        self.num_requests_pk.remove(&member.to_string());

        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
