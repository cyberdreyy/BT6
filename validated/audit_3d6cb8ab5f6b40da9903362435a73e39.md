**Reasoning:** `AccountId` in this codebase (re-exported from the `near-account-id` crate via `core/primitives-core/src/types.rs`) is a simple newtype wrapping a validated `String`; it is constructed once through `FromStr`/parsing and stored as that exact string, with no secondary "normalized" or alternate structural representation that could diverge from `as_str()`. [1](#0-0)  Because both `sender_id` (the outer receipt's receiver_id, already parsed to `AccountId` before reaching `apply_delegate_action`) and `delegate_action.sender_id()` are the same `AccountId` type with a single canonical byte representation, the check at `delegate_action.sender_id().as_str() != sender_id.as_str()` in `runtime/runtime/src/actions.rs` is equivalent to full structural/byte equality of the two `AccountId` values. [2](#0-1)  Consequently, when the check passes, `sender_id.clone()` passed into `set_access_key` at the `DelegateNonceUpdate::AccessKey` branch is guaranteed to be identical (not just string-equal) to the value that was validated, so the `TrieKey::access_key` constructed in `set_access_key_by_handle` in `core/store/src/utils/mod.rs` is keyed on the exact same identity that was checked. [3](#0-2)  There is no evidence in the repo of any alternate `AccountId` construction path that could produce two instances with equal `as_str()` but different trie-key bytes, so the premised "writer vs checker key off different normalized forms" scenario is not reachable.

/// Variant of [`set_access_key`] used by genesis state application and
/// iteration paths that already hold a `PublicKeyHandle` (e.g. when reading
/// from a `StateRecord` or replaying state changes).
pub fn set_access_key_by_handle(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    key_handle: PublicKeyHandle,
    access_key: &AccessKey,
) {
    debug_assert!(
        access_key.gas_key_info().is_none() || access_key.nonce == 0,
        "gas key access key must have nonce 0, got {}",
        access_key.nonce
    );
    set(state_update, TrieKey::access_key(account_id, key_handle), access_key);
}
