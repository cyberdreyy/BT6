### Title
Loss-adjusted withdrawal receipts bypass haircut due to epoch index mismatch in `lossRecoveryPriceByEpoch` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
When `stopEpochWithDuration`/`stopEpoch` funds pending withdrawals for less than `pendingWithdraws`, `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` — but `epochNumber` has already been incremented by the stop-epoch `deposit()` call, while user receipts were recorded under the previous epoch via `lastWithdrawRequest`. The loss-adjusted claim path therefore never fires and receipts are paid at par from an under-funded reserve.

### Finding Description
The bug class is a missing consistency check between two state slots that are supposed to reference the same epoch:

- `requestWithdraw` records receipts under `currentEpoch = epochNumber` at request time and sets `lastWithdrawRequest[_user] = currentEpoch` [1](#0-0) 
- `deposit()` increments `epochNumber` while `isEpochRunning` is still true — i.e. during `stopEpoch` funding, *before* the epoch flag is cleared [2](#0-1) 
- `collectWithdrawFunds` then writes `lossRecoveryPriceByEpoch[epochNumber]` using the already-incremented value [3](#0-2) 

The claim path keys off the stale epoch:

- `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, which is the pre-increment epoch and returns 0, so it returns early without clearing the receipt [4](#0-3) 
- `_claimFundedWithdrawRequest` then only requires `epochNumber > lastWithdrawRequest[_user]`, which holds, and pays `withdrawsRequests[_user]` at full par [5](#0-4) 

The strategy only received `_amount < pendingBasis` from the CDO, so paying receipts at par drains the funded reserve.

### Impact Explanation
Every loss-adjusted epoch pays receipts unhaircutted. The first claimers withdraw `claimBasis` at 1:1 instead of `claimBasis * lossRecoveryPrice / RECOVERY_FULL`, extracting the difference from the under-funded reserve; later claimers (or other pending receipts) are left with unbacked receipts — direct theft plus partial insolvency of the vault. Loss scales with `pendingBasis - _amount`, i.e. up to the full realized loss being socialized onto non-claiming users instead of the pending redeemers it was assigned to.

### Likelihood Explanation
Triggering requires only an honest `stopEpoch`/`stopEpochWithDuration` sequence where the borrower funds less than `pendingWithdraws` (partial-loss epoch) while at least two withdraw requests are pending — no privileged misbehavior needed. The first user to call `claimWithdrawRequest` after funding takes the unhaircutted share.

Caveat: I was unable to read the exact ordering of `deposit()` vs `collectWithdrawFunds` inside `IdleCDOEpochVariant.stopEpoch`/`_afterStopEpochWithDuration` within the available iterations. The finding holds if `epochNumber` is incremented (via the strategy `deposit()` call that pulls borrower funds) before `collectWithdrawFunds` runs, which matches the code comment at line 608 ("deposit done on stopEpoch (before setting the var to false)"). If the CDO collects withdraw funds before the incrementing deposit, the key matches and no bug exists — this ordering should be verified first.

### Recommendation
Store the loss recovery price under the epoch the receipts belong to: either use `epochNumber - 1` (the epoch whose requests are being funded), or pass the claim epoch explicitly from the CDO, or record `lossRecoveryPriceByEpoch[lastWithdrawRequest]`-equivalent per-request data. Add an invariant test that requests withdrawals in epoch N, stops epoch N+1 with partial funding, and asserts claims pay `basis * lossRecoveryPrice / RECOVERY_FULL`.

### Proof of Concept
Foundry fork outline (requires confirming the stopEpoch ordering):

```solidity
// 1. Users A and B deposit into AA tranche during buffer.
// 2. startEpoch(); warp past epochEndDate.
// 3. stopEpoch(apr, interest) succeeds; epochNumber becomes N+1, buffer opens.
// 4. A and B call cdoEpoch.requestWithdraw(fullBalance, AAtranche)
//    -> lastWithdrawRequest[A] = lastWithdrawRequest[B] = N+1
// 5. startEpoch(); warp past epochEndDate.
// 6. stopEpochWithDuration / stopEpoch where borrower funds < pendingWithdraws
//    -> deposit() bumps epochNumber to N+2
//    -> collectWithdrawFunds sets lossRecoveryPriceByEpoch[N+2] = price < RECOVERY_FULL
// 7. A calls claimWithdrawRequest():
//    - _claimLossAdjustedWithdrawRequest reads lossRecoveryPriceByEpoch[N+1] == 0, skips
//    - _claimFundedWithdrawRequest: epochNumber (N+2) > N+1 -> pays withdrawsRequests[A] at par
// assertEq(payout, A_basis) instead of A_basis * price / RECOVERY_FULL
// 8. B's claim then underflows/reverts or leaves the reserve drained.
```

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
