### Title
Missing Access Control on Pipeline Run Resume Endpoint - (File: `core/web/router.go`, `core/web/pipeline_runs_controller.go`)

### Summary
The `PATCH /v2/resume/:runID` route is mounted on the unauthenticated route group and is guarded solely by knowledge of an opaque `runID`, with no session, API-token, or RBAC role check comparable to every other job-pipeline-affecting endpoint in the router.

### Finding Description
`v2Routes` explicitly registers the resume endpoint on the unauthenticated router group, before the `authv2` group that wraps every other mutating route with `auth.Authenticate` + `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`: [1](#0-0) 

```go
unauthedv2 := r.Group("/v2")
...
unauthedv2.PATCH("/resume/:runID", prc.Resume)
authv2 := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(),
    auth.AuthenticateByToken,
    auth.AuthenticateBySession,
))
```

`Resume` itself performs zero authentication or authorization checks — it parses the `runID` as a UUID, decodes an arbitrary JSON body into a `pipeline.ResumeRequest`, and directly calls `App.ResumeJobV2` to inject the caller-supplied result into the paused pipeline task: [2](#0-1) 

This is architecturally identical to the reported bug class: a state-mutating function (`proposeMint`/`proposeBurn` in the external report, `ResumeJobV2` here) that is reachable by any unprivileged caller without any role/ownership check — contrasted with every sibling endpoint in this codebase (`RunJob`, `Create` job, `Create` pipeline run, etc.) which are wrapped in `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole`: [3](#0-2) [4](#0-3) 

The only protection is that `runID` is a UUID (122 bits of entropy), which functions as a bearer-token-like secret instead of a proper authorization check. The endpoint is explicitly acknowledged as unauthenticated in the audit event name `audit.UnauthedRunResumed` used when logging the action: [5](#0-4) 

### Impact Explanation
If a pending task's `runID` is disclosed (e.g., leaked via logs, error messages, external adapter callbacks, monitoring/observability tooling, or a misconfigured bridge integration echoing the ID), any unprivileged network client can supply an arbitrary `ResumeRequest` result for that specific paused pipeline task. Since pipeline tasks commonly feed into downstream ETH transmission tasks (e.g., committing off-chain-computed values on-chain), attacker-controlled resume data can inject falsified data into a job run without any authentication, potentially resulting in incorrect on-chain transmissions/fund movement driven by node-controlled keys. This matches the "unauthorized job run or fund movement" acceptance criterion.

### Likelihood Explanation
Exploitation requires the attacker to learn or guess a valid, currently-pending `runID` (UUID). Brute-forcing a 122-bit UUID is impractical, so the realistic likelihood depends on incidental disclosure of the ID (logs, external adapter responses, monitoring dashboards, or node operators exposing this internal API endpoint on the public internet without additional network-level protections). Given the endpoint is intentionally exposed as unauthenticated by design (to support asynchronous bridge/external-adapter callbacks resuming `bridge` tasks), the practical likelihood is lower than a fully open unauthenticated mint/burn function, but the underlying access-control gap is identical in kind: no RBAC/session/API-key enforcement whatsoever on a state-mutating endpoint.

### Recommendation
Introduce an additional layer of authorization beyond UUID secrecy: e.g., require the resume request to be authenticated with a per-task HMAC-signed callback token bound to the originating bridge/external-adapter, restrict the endpoint to allow-listed source IPs/bridge URLs, or bind the `runID` to a short validity window and single-use semantics enforced server-side, in addition to auditing/rate-limiting the endpoint.

### Proof of Concept
Given a leaked/observed pending task `runID` (UUID), an unauthenticated client can call:
```
PATCH /v2/resume/<runID>
Content-Type: application/json

{"value": "<attacker-controlled-result>"}
```
This reaches `PipelineRunsController.Resume` → `App.ResumeJobV2` with no session cookie, API token, or role check required, as confirmed by its registration under `unauthedv2` in `core/web/router.go` line 243.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
