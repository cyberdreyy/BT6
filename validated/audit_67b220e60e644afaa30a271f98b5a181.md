### Title
Exit fee is read at fulfillment time instead of being cached at request creation, so write-off requesters can be charged a fee they never agreed to - (File: contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.fullfillWriteOffRequest` prices the exit fee from the live `exitFee`/`feeReceiver` storage values, while `createWriteOffRequest` only caches `tranches` and `underlyings` in the `WriteOffRequest` struct. If the owner changes `exitFee` between request creation and fulfillment, the lender is charged a different (up to 10x higher) fee than the one in effect when they escrowed their tranche tokens, and any third-party fulfiller can force that settlement atomically.

### Finding Description
The escrow stores only two fields per request: [1](#0-0) 

At fulfillment, the fee is computed from the *current* global `exitFee` and paid to the *current* `feeReceiver`: [2](#0-1) 

`exitFee` is initialized to 100 (0.1%) and can be raised by the honest owner at any time up to `MAX_EXIT_FEE = 1_000` (1%): [3](#0-2) [4](#0-3) 

This is the same bug class as the SecondSwap report: a user commits to an action (escrowing tranche tokens for a fixed ask) under one fee schedule, and a later administrative fee change is applied retroactively to their pending request. The lender's "quoted" fee exists only implicitly — nothing in `WriteOffRequest` records the fee terms at request time.

### Impact Explanation
A lender who created a request when `exitFee = 100` expecting to receive `underlyings * 0.999` can instead receive only `underlyings * 0.99` after a `setExitFee(1_000)` — a direct loss of up to 0.9% of the requested underlyings, taken as fee and sent to `feeReceiver`. Because `fullfillWriteOffRequest` is permissionless (`_dev this function can be called by any wallet`), any unprivileged fulfiller can settle the request in the same transaction window after the fee change, giving the lender no opportunity to react between `setExitFee` and fulfillment. The lender's only recourse is `deleteWriteOffRequest`, which requires them to monitor the fee parameter and front-run a fulfillment — protection that should not be their responsibility. Broken invariant: a committed trade is settled under changed terms.

### Likelihood Explanation
Requires only a legitimate, honest owner fee update (`setExitFee` / `setFeeReceiver`) to occur while a write-off request is open, plus any fulfiller (borrower or third party) completing the request. Write-off requests can sit open for an entire running epoch (`createWriteOffRequest` requires `isEpochRunning`), so the exposure window is large. No attacker privilege, no default, no oracle manipulation needed. Impact is bounded by `MAX_EXIT_FEE` (1%), consistent with a medium-severity fee-integrity issue.

### Recommendation
Cache the fee terms in the `WriteOffRequest` struct at creation time (e.g., `uint256 exitFee; address feeReceiver;` or store the already-computed `feeAmount`), and use the cached values in `fullfillWriteOffRequest`. Alternatively, let the requester specify a `maxExitFee` / `minReceived` parameter that fulfillment must satisfy, so settlement reverts if the current fee exceeds what the lender agreed to.

### Proof of Concept
Foundry fork test outline (same style as `test/foundry/IdleCreditVault.t.sol`):

```solidity
// Assume: escrow deployed for AA tranche, owner honest, epoch running.
address lender = makeAddr("lender");
address fulfiller = makeAddr("fulfiller");

// 1. Lender deposits AA and creates a write-off request while exitFee = 100 (0.1%)
deal(address(AAtranche), lender, 1000e18);
deal(defaultUnderlying, fulfiller, 500e6);

vm.startPrank(lender);
IERC20(address(AAtranche)).approve(address(escrow), 1000e18);
escrow.createWriteOffRequest(1000e18, 500e6); // expects 500e6 * 0.999 = 499.5e6
vm.stopPrank();

// 2. Honest owner raises the exit fee to the max before fulfillment
vm.prank(owner);
escrow.setExitFee(1_000); // 1%

// 3. Any wallet fulfills; lender is charged the NEW fee, not the fee at request time
vm.startPrank(fulfiller);
IERC20(defaultUnderlying).approve(address(escrow), 500e6);
escrow.fullfillWriteOffRequest(lender, 1000e18, 500e6);
vm.stopPrank();

// Lender receives 495e6 instead of the 499.5e6 expected at request time:
assertEq(IERC20(defaultUnderlying).balanceOf(lender), 500e6 - (500e6 * 1_000 / 100_000)); // 495e6
// Fee receiver pockets the 4.5e6 difference the lender never agreed to:
assertEq(IERC20(defaultUnderlying).balanceOf(feeReceiver), 5e6);
```
