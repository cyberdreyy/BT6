### Title
Unsanitized secret/variable key used as file name allows path traversal outside the temp variables directory - (File: shells/bash.go, shells/powershell.go, common/secrets.go)

### Summary
`spec.Variable.Key` — which for secrets is populated directly from the `secrets:` map key (`variableKey`) with no validation — is passed unmodified into `ShellWriter.TmpFile()`/`Variable()`, which builds the on-disk file path with `path.Join(TemporaryPath, key)`. Because `path.Join`/`path.Clean` resolve `..` lexically without confining the result to `TemporaryPath`, a key containing enough `../` segments causes the generated variable file to be written outside the intended temp/variables directory.

### Finding Description
`defaultSecretsResolver.Resolve` iterates `spec.Secrets` and for each `variableKey` calls `handleSecret`, which builds: [1](#0-0) 
with `Key: variableKey` copied verbatim from the job's `secrets:` map key and `File: secret.IsFile()`. No format/character validation is performed on `variableKey` anywhere in `defaultSecretsResolver.Resolve`/`handleSecret`: [2](#0-1) 

These resolved variables are merged into the build's variable set via `b.secretsVariables = variables; b.RefreshAllVariables()` in `executeResolveSecretsStage`: [3](#0-2) 

When the shell scripts are generated, `AbstractShell.writeExports` calls `w.Variable(variable)` for every build variable, including secret-derived ones: [4](#0-3) 

For `BashWriter`, `Variable()` treats `File: true` variables by computing the file path from the raw `Key`: [5](#0-4) [6](#0-5) 

`TmpFile` builds `path.Join(b.TemporaryPath, name)`. Go's `path.Join`/`path.Clean` process `..` purely lexically — they do not clamp the result to stay under `TemporaryPath` — so a `Key` such as `"../../malicious"` (or a Unicode/crafted variant) resolves to a path *above* `TemporaryPath`, not inside it. The generated bash script does `mkdir -p <TemporaryPath>` (the original, un-escaped directory) then `printf ... > <resolved-variable-file>`, so if the resolved (escaped) path's parent directory already exists in the job's filesystem, the file gets written there directly, without ever going through `TemporaryPath`. `PsWriter.Variable` on Windows/PowerShell exhibits the identical pattern: [7](#0-6) 

The cleanup path (`writeCleanupScript`) reconstructs the same unsanitized path with `w.TmpFile(variable.Key)` for removal, confirming there is no key sanitization anywhere on this path: [8](#0-7) 

Notably, the codebase *does* have a key-sanitization helper, `isValidDotEnvKey`, but it is only applied to the unrelated `DotEnvVariables`/cache-export path, not to `Variable()`/`TmpFile()`: [9](#0-8) 
This shows the project is aware such input needs validation in some code paths but has not applied an equivalent check to file-backed variable name construction.

### Impact Explanation
An unprivileged pipeline author who can define a `secrets:` block (Azure Key Vault or any other backend, since the vulnerable code is resolver-agnostic in `common/secrets.go`) with a crafted key such as `"../../malicious"` and `file: true`, can, once the secret resolves successfully, cause the runner-generated build script to write the (masked) secret value to an attacker-chosen filename outside the job's dedicated `.tmp`/variables directory — anywhere writable within the job's build/container filesystem that the path traversal reaches (e.g., overwriting/creating files in the build root, HOME, or other pre-existing directories the job process can write to). This is a concrete file-write-outside-intended-root primitive, matching the scoped impact ("arbitrary file creation outside variables root").

### Likelihood Explanation
The attack is trivial to trigger: any job author who can add a `secrets:` entry (a normal, non-admin CI feature) controls the map key directly, and the vulnerable code path is exercised on every `File: true` secret resolution regardless of backend (Azure Key Vault, Vault, GCP). The only precondition is that the crafted key still resolves to a real secret. This repository shows no server-side (Runner) validation of the key; whether GitLab Rails performs environment-variable-name validation on `secrets:` keys before dispatching the job is outside this repo's code and unverifiable here, but Runner itself does not defend against a malformed key, which is a missing defense-in-depth check independent of any upstream validation.

### Recommendation
Sanitize/validate `variableKey` before it becomes a file-backed variable `Key`:
- In `common/secrets.go` `handleSecret`, reject or normalize keys that are not valid identifiers (reuse/extend `isValidDotEnvKey`-style validation, or explicitly disallow `/`, `\`, and `..`).
- Defense-in-depth: in `shells/bash.go` `TmpFile`/`BashWriter.Variable` and `shells/powershell.go` `PsWriter.Variable`, verify (e.g., via `filepath.Rel`/prefix check after `filepath.Clean`) that the resolved variable file path stays within `TemporaryPath` before emitting `mkdir`/`printf`/`WriteAllText` commands, and fail the job otherwise.

### Proof of Concept
Go unit test (add to `shells/bash_test.go` alongside `Test_BashWriter_Variable`):
```go
func Test_BashWriter_Variable_PathTraversal(t *testing.T) {
    w := BashWriter{TemporaryPath: "/builds/project/.tmp"}
    w.Variable(spec.Variable{Key: "../../../../tmp/pwned", Value: "secret", File: true})
    out := w.String()
    // Assert the resolved file path stays within TemporaryPath.
    assert.NotContains(t, out, "> \"/tmp/pwned\"")
    assert.Contains(t, out, "/builds/project/.tmp/")
}
```
This currently fails (the generated script writes to `/tmp/pwned`), demonstrating the escape. A fuzz test (`FuzzBashWriter_Variable(f *testing.F)`) seeding Unicode and `../` sequences as `Key`, asserting `strings.HasPrefix(resolvedPath, TemporaryPath)` for every generated `printf ... > path` line, would generalize the proof across the input space described in the question.

func isValidDotEnvKey(key string) bool {
	validKeyPattern := `^[A-Za-z_][A-Za-z0-9_]*$`
	matched, _ := regexp.MatchString(validKeyPattern, key)
	return matched
}
