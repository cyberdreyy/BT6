### Title
Premature clearing of the tx-replay guard on unrelated Stacks-block arrival — (File: `stacks-signer/src/v0/signer_state.rs`)

### Summary
`LocalStateMachine::stacks_block_arrival` clears the signer's `tx_replay_set` whenever a new Stacks block arrives that has no matching row in `block_validated_by_replay_txs` for the *current* replay-set hash, even though that absence does not prove the replay obligation was satisfied — it can simply mean this signer never validated that particular block against its current replay set. This mirrors the Notional bug class: a security-relevant field (there, `maturity`; here, `tx_replay_set`) is zeroed based on an incomplete/incorrect inference from a helper lookup that assumes a condition ("not found ⇒ safe to clear") which the surrounding code does not actually guarantee.

### Finding Description
`LocalStateMachine::stacks_block_arrival` is the handler invoked when a `NewBlock` event arrives (any Stacks block the node has now processed) [1](#0-0) . Its replay-guard logic is:

```
if let Some(replay_set_hash) = NakamotoBlockProposal::tx_replay_hash(&prior_state_machine.tx_replay_set...) {
    match db.get_was_block_validated_by_replay_tx(signer_signature_hash, replay_set_hash) {
        Ok(Some(BlockValidatedByReplaySet { replay_tx_exhausted, .. })) => {
            if replay_tx_exhausted { tx_replay_set = ReplayTransactionSet::none(); }
        }
        Ok(None) => {
            // "got a new block during replay that wasn't validated by our replay set"
            tx_replay_set = ReplayTransactionSet::none();
        }
        ...
    }
}
``` [2](#0-1) 

`get_was_block_validated_by_replay_tx` only returns `Some` if *this* signer previously validated *that exact* `signer_signature_hash` against its currently-held `tx_replay_set` hash, and recorded it via `insert_block_validated_by_replay_tx` when a `BlockValidateOk` for that proposal came back [3](#0-2) , [4](#0-3) .

The `Ok(None)` branch is reached whenever this signer never independently validated the block that just landed on-chain against its current replay set. This can legitimately happen with a one-slot miner plus normal gossip:
- The block that was globally accepted was validated primarily by *other* signers' pre-commits/signatures (the local signer may have been slow, restarted, or never received the proposal), so no local row exists in `block_validated_by_replay_txs` for that hash.
- A single miner (a "one-slot" actor for that sortition window) simply proposes and gets the block accepted before this signer's own validation round-trip records anything against the current replay hash.

In both cases the function unconditionally interprets `Ok(None)` as proof the incoming block "wasn't validated by our replay set," and clears `tx_replay_set` to `none()`, exactly as the Notional code unconditionally treated `pr[1]` being unset as proof `accountDebtTwo` was zero. The underlying assumption — that a `None` lookup result means the replay obligation was resolved (or moot) — does not hold; it only means *this signer's local record-keeping* has no matching entry, which is a much weaker condition than "the chain now reflects a fully replayed transaction set."

This clears the equality that the replay-protection mechanism depends on: all signers must converge on the same `tx_replay_set` (enforced globally via `GlobalStateEvaluator::determine_global_state` majority/longest-common-prefix logic) [5](#0-4) . If one signer's local view of `tx_replay_set` snaps to `none()` prematurely because of this false-negative lookup, that signer will thereafter validate/sign blocks as if no replay set constraint is in force, i.e., it can approve a block containing transactions that duplicate/replay pre-fork nonces that the rest of the honest set is still supposed to block via `validate_replay` (`stackslib/src/net/api/postblock_proposal.rs`) [6](#0-5) .

### Impact Explanation
This falls into "a signer wedged into never signing valid blocks, [or] acting on a stale reward set/threshold" / signing invalid-by-protocol-rule blocks (loss of the tx-replay-set enforcement invariant). Concretely: a signer whose local `tx_replay_set` gets zeroed early will stop rejecting proposals that skip the required replay transactions (`validate_replay`'s `InvalidTransactionReplay` rejection is bypassed locally because the signer no longer supplies/enforces a replay set at proposal time), diverging from peers still enforcing it. Depending on aggregate weight this can contribute a non-canonical/incorrect acceptance vote into the tally, or — more reliably observable — cause the signer's local state to permanently diverge from the correctly-converged global state, since `stacks_block_arrival` is not gated on whether the arriving block belongs to the replay scope/tenure at all.

### Likelihood Explanation
This requires no majority collusion and no key compromise: it is triggered purely by ordinary asynchronous timing — a signer that hasn't (yet, or ever) locally validated the specific globally-accepted block against its own `tx_replay_set` hash, which is routine whenever a signer is not the one who validated/proposed that block, restarts, or lags. Given `NewBlock` events fire for every processed Stacks block, and the replay set is expected to persist across multiple blocks during an active replay episode, the false-negative window is frequently reachable in real operation.

### Recommendation
Do not treat `Ok(None)` from `get_was_block_validated_by_replay_tx` as proof the replay set is exhausted/no-longer-needed. Only clear `tx_replay_set` when there is positive evidence the replay obligation was resolved: either (a) this signer's own `Ok(Some(replay_tx_exhausted = true))` record, or (b) an independent, node-verifiable check that the newly-arrived block's on-chain contents actually consumed the entirety of the current replay set (e.g., by replaying/diffing the block's tx list against `tx_replay_set` directly, similar to `validate_replay` in `postblock_proposal.rs`), instead of relying on the absence of a local bookkeeping row.

### Proof of Concept
1. Signer S is in an active tx-replay episode with `tx_replay_set = [tx1, tx2]` (set via a prior Bitcoin fork, per `handle_fork_for_new_replay`) [7](#0-6) .
2. A single miner proposes a valid replay block `B` (containing `tx1`); it is validated and pre-committed/signed primarily by other signers before S's own `handle_block_validate_response` records a row in `block_validated_by_replay_txs` for `(B, hash([tx1,tx2]))` — e.g., S was momentarily behind, restarted, or received the `NewBlock` event before finishing its own validate round-trip.
3. S's `stacks_block_arrival` runs for block `B`: `get_was_block_validated_by_replay_tx(B, hash([tx1,tx2]))` returns `Ok(None)` because S has no local record.
4. S clears `tx_replay_set` to `none()`, even though only `tx1` (not `tx2`) has actually been replayed on-chain.
5. S subsequently validates/signs the *next* proposal without requiring `tx2` to be replayed, diverging from the rest of the signer set (which still enforces `[tx2]`), breaking the intended equality between signers' `tx_replay_set` views and undermining the replay-protection guarantee.
