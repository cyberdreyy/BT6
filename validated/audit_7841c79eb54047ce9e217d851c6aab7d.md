### Title
Claimed instant-withdraw receipts stay in `instantWithdrawClaimsByEpoch` and dilute default recovery for remaining claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The OpenSIPS bug is a parser accepting input that leaves fields "initialized" by assumption while downstream code (`calc_tag_suffix` / `MD5StringArray`) consumes a null/uninitialized value, producing a crash. The closest analog in idle-tranches is a bookkeeping field that is assumed to be cleared but is not: `claimInstantWithdrawRequest` clears the per-user aggregate `instantWithdrawsRequests[_user]` and burns the receipt tokens, but never clears the per-epoch index `instantWithdrawsRequestsByEpoch[_user][epoch]` nor the epoch total `instantWithdrawClaimsByEpoch[epoch]`. `finalizeDefaultRecovery` then consumes that stale epoch total via `defaultPendingClaimBasis` as if it were still an unpaid claim basis — the equivalent of passing an uninitialized/stale value into a sensitive computation.

### Finding Description
Instant withdraw flow (`contracts/strategies/idle/IdleCreditVault.sol`):

- `requestInstantWithdraw` records both the aggregate and the per-epoch basis:
  `instantWithdrawsRequests[_user] += _amount`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount`, `instantWithdrawClaimsByEpoch[currentEpoch] += _amount` (lines 366–374).
- `claimInstantWithdrawRequest` (lines 380–393) burns the full `instantWithdrawsRequests[_user]` and zeroes the aggregate, but leaves `instantWithdrawsRequestsByEpoch` and `instantWithdrawClaimsByEpoch` untouched.
- At default, `defaultPendingClaimBasis` (lines 644–649) adds `instantWithdrawClaimsByEpoch[epochNumber]` to `pendingWithdraws` whenever `pendingInstantWithdraws != 0`, and `finalizeDefaultRecovery` (lines 679–692) computes `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` over that inflated basis.
- The stale per-epoch entry also makes `_claimDefaultedInstantWithdrawRequest` (lines 842–856) revert for the already-claimed user via underflow on `instantWithdrawsRequests[_user] -= claimBasis` (aggregate already 0), permanently reverting their `claimInstantWithdrawRequest` path once `defaultInstantWithdrawsFinalized` is set.

Scenario (instant mode, running epoch): users A and B request instant withdrawals in the same epoch. The CDO funds only part of the queue (so `pendingInstantWithdraws > 0` remains for B). A claims and is paid in full — his epoch entries are never decremented. The borrower then defaults and `finalizeDefaultRecovery` runs: `totalBasis` still counts A's already-paid claim, so `recoveryPrice` is set lower than fair. B (and every defaulted normal/APR0 receipt holder) is paid less than the correct pro-rata share, and the unclaimed remainder of `defaultRecoveryReserve` is stranded forever (claims only pay out `claimBasis * defaultRecoveryPrice`, and the inflated basis means the reserve can never be fully consumed).

### Impact Explanation
Direct, quantified loss and permanent freezing: if A's already-paid claim was fraction `f` of the true pending basis, every remaining claimant's recovery is scaled down by roughly `1/(1+f)`, and `defaultRecoveryReserve` retains ~`f * reserve` as dust that no claim path can withdraw (owner can only rescue it via `transferToken`, i.e., it is frozen from the protocol's own accounting). Additionally, the already-claimed user hits a permanent revert in the default-claim path. This breaks the "one receipt, one payout" and fair-recovery invariants, and is reachable in a normal running→defaulted sequence by an unprivileged instant-withdraw requester who simply claims before default.

### Likelihood Explanation
Requires an epoch with instant withdrawals enabled where the queue is only partially funded (one user claims while `pendingInstantWithdraws` stays nonzero) followed by a borrower default and `finalizeDefaultRecovery`. Partial instant funding is an explicit, supported state (`_defaultPrefundedInstantReserve` exists precisely because `pendingInstantWithdraws` can be lower than the epoch claim basis), and defaults are a first-class flow, so the precondition is realistic rather than contrived. No privileged misbehavior is needed — the manager sequence (partial funding → default → finalize) is honest.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][...]` and `instantWithdrawClaimsByEpoch[...]` for the epochs being claimed (or, simplest, for `epochNumber`/the epochs recorded for that user) in the same transaction that zeroes `instantWithdrawsRequests[_user]`. Additionally, in `_claimDefaultedInstantWithdrawRequest`, cap `claimBasis` at `instantWithdrawsRequests[_user]` before the subtraction so a stale entry cannot underflow and permanently revert.

### Proof of Concept
Foundry fork PoC (in the style of `test/foundry/IdleCDOEpochQueue.t.sol` / `IdleCreditVault.t.sol`):

```solidity
function testStaleInstantClaimDilutesDefaultRecovery() external {
    _useStandardEpochVariant();
    _stopCurrentEpochWithApr(10e18);          // epoch 1
    vm.prank(manager);
    cdoEpoch.setInstantWithdrawParams(100, 1e18, false);

    address A = makeAddr('A'); address B = makeAddr('B');
    uint256 ta = _depositWithUser(A, 50e6);
    uint256 tb = _depositWithUser(B, 50e6);
    vm.prank(manager); cdoEpoch.startEpoch();

    strategy.requestInstantWithdraw(ta, A);   // via CDO context
    strategy.requestInstantWithdraw(tb, B);

    // Fund only A: CDO transfers underlyings to strategy for A's claim,
    // pendingInstantWithdraws stays > 0 for B.
    // (mirror how tests collect instant funds, then)
    strategy.claimInstantWithdrawRequest(A);  // A paid in full
    assertEq(strategy.instantWithdrawsRequests(A), 0);
    // BUG: epoch index still contains A's paid claim
    assertEq(strategy.instantWithdrawClaimsByEpoch(strategy.epochNumber()), ta + tb);

    // borrower default in same epoch, then manager calls finalizeDefaultRecovery
    // with recovered amount R.
    // recoveryPrice = R*1e18 / (pendingWithdraws + (ta+tb))  // includes paid A
    // expected fair:  R*1e18 / (pendingWithdraws + tb)
    // B claims -> receives less; ~ta worth of reserve is stranded in
    // defaultRecoveryReserve forever.
}
```

Key assertions: `instantWithdrawClaimsByEpoch[epoch]` is unchanged after A's claim; `defaultPendingClaimBasis()` post-default equals `pendingWithdraws + (ta + tb)` instead of `pendingWithdraws + tb`; B's payout is below the fair pro-rata share and `defaultRecoveryReserve` retains unclaimable dust equal to A's share of the recovery price computation.
