### Title
Signer weight double-counted in both approve and reject tallies when a signer switches its vote - (File: stacks-node/src/nakamoto_node/stackerdb_listener.rs)

### Summary
The node-side `StackerDBListener` message loop tallies `BlockResponse::Accepted` and `BlockResponse::Rejected` messages from signers into `BlockStatus.total_weight_approved` / `total_weight_rejected`, which the `SignerCoordinator::get_block_status` loop then compares against `weight_threshold` to decide whether a block is approved or blocking-rejected. The two branches use inconsistent de-duplication keys, so a single signer that first rejects and later accepts the same block has its weight added to *both* tallies instead of being moved from one to the other.

### Finding Description
In the message-processing loop, the `Accepted` branch gates whether to add weight on `block.gathered_signatures.contains_key(&slot_id)`: [1](#0-0) 

while the `Rejected` branch gates on a completely different set, `block.responded_signers.insert(&slot_id)`: [2](#0-1) 

Crucially, the `Accepted` branch unconditionally inserts the slot into `responded_signers` regardless of whether it was already present: [1](#0-0) 

Sequence that breaks the invariant `total_weight_approved` and `total_weight_rejected` should each reflect disjoint, currently-held signer opinions:
1. Signer `S` (weight `w`) sends `Rejected` for block `B`. `responded_signers.insert(S)` succeeds → `total_weight_rejected += w`.
2. Signer `S` later sends `Accepted` for the same `B` (e.g., reconsiders, or a node restart/resend). The `Accepted` branch only checks `gathered_signatures.contains_key(S)`, which is still false, so it adds `total_weight_approved += w` as well. `S`'s weight is now counted in **both** tallies simultaneously; `S`'s rejection weight is never subtracted.
3. In `get_block_status`, the rejection-threshold check runs before the approval check: [3](#0-2) 
So a stale rejection weight that should have been superseded by the signer's later acceptance can still push `total_weight_rejected` past the blocking-minority threshold (`total_weight - weight_threshold`), even though that same signer's current, valid vote is "accept." This can cause `get_block_status` to return `NakamotoNodeError::SignersRejected` for a block that in fact has enough current approving weight to clear the 70% threshold — an aggregated-weight tally that no longer matches the set of currently-valid accept/reject opinions.

The reverse direction (Accepted → later Rejected) is correctly guarded, since the `Rejected` branch's `responded_signers.insert` returns `false` once the slot was already recorded by the `Accepted` branch, so no double count occurs in that order. The bug is specific to the Reject→Accept ordering, which is only reachable because the two branches key their "already counted" check off two different tracking sets (`gathered_signatures` vs `responded_signers`) instead of a single shared one.

### Impact Explanation
This directly breaks the "aggregated-weight vs verified-accepts" equality the scan targets: the node's weight tally for rejections can retain stale weight from a signer that has since switched to accepting, allowing a block that currently has sufficient approving weight to be miscounted as blocked/rejected by the miner-side coordinator. This is a liveness issue reachable by a single signer switching its own vote — no majority or other signer's key is required — and it corrupts the coordinator's view of consensus on a per-block basis.

### Likelihood Explanation
Triggering requires only one signer (which could be a single miner-connected signer, or a signer that legitimately changes its mind, or resends a stale cached response after a restart) to emit a `Rejected` message and later an `Accepted` message for the same `signer_signature_hash`. Both message kinds are ordinary, protocol-legal signer outputs; no majority collusion, no other signer's key, and no auth token are needed — it is entirely within a single signer's own control to produce this sequence.

### Recommendation
Use a single, shared per-signer "current vote" tracking structure (or explicitly remove the signer's prior contribution) instead of two independently-gated sets. Concretely, before adding weight in the `Accepted` branch, check (and clear) any prior entry for that slot in the rejection tally (and vice versa in the `Rejected` branch), so a signer's weight is only ever counted toward its most recent vote.

### Proof of Concept
Not executed (index-only analysis, no runtime/test harness access). The trace above (`stackerdb_listener.rs:386-465` for `Accepted`, `stackerdb_listener.rs:486-519` for `Rejected`, combined with the threshold checks in `signer_coordinator.rs:509-519`) demonstrates the double-count is reachable purely by message ordering from a single signer; a concrete regression test would send `Rejected(slot, B)` then `Accepted(slot, B)` from the same signer through `StackerDBListener` and assert `total_weight_approved + total_weight_rejected` includes that signer's weight only once.
