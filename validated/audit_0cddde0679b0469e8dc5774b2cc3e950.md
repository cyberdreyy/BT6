### Title
First-depositor share inflation via direct token donation lets an attacker steal subsequent depositors' funds - (File: contracts/IdleCDOCreditVault.sol)

### Summary
`IdleCDOCreditVault` mints tranche shares at `priceAA`/`priceBB`, which are derived from `getContractValue()` — a value that includes the raw unlent `token` balance of the vault. An attacker can be the first depositor with 1 wei of underlying, then donate a large amount of underlying directly to the vault (not through `depositAA`/`depositBB`). The next depositor's `_updateAccounting()` call prices the attacker's single share at the donated NAV, so the victim's `_mintSharesAtCurrPrice` mints ~0 shares while the vault still records the victim's underlying in `lastNAVAA`/`lastNAVBB`. The attacker then redeems their 1 share at the inflated price and drains both the donation and the victim's principal.

### Finding Description
In `_deposit` (`contracts/IdleCDOCreditVault.sol:191-212`), the flow is:

1. `_updateAccounting()` recomputes `priceAA`/`priceBB` from `nav = getContractValue()`.
2. The victim's underlying is pulled in via `_transferUnderlyingsFrom`.
3. `_mintSharesAtCurrPrice` mints `_amount * ONE_TRANCHE_TOKEN / _tranchePrice(_tranche)` shares (line 346).

`getContractValue()` counts `strategyTokens * price + _contractTokenBalance(token) - unclaimedFees`, so a plain `ERC20.transfer` of underlying to the vault inflates `nav`. In `_virtualPriceAux` (lines 287-337), when `trancheSupply != 0` and `_lastNAV != 0`, the donated amount is treated as `totalGain` and folded into the tranche price: `_virtualPrice = (_lastTrancheNAV + _totalTrancheGain) * ONE_TRANCHE_TOKEN / trancheSupply`.

Attack sequence (buffer phase, before any real TVL):

1. Attacker calls `depositAA(1)` → receives `1 * ONE / oneToken` shares; `lastNAVAA = 1`.
2. Attacker calls `token.transfer(vault, D)` directly with `D` large (e.g. 501 USDC).
3. Victim calls `depositAA(V)` where `V < D`. `_updateAccounting` sets `priceAA ≈ (1 + D) * ONE / supply`. `_minted = V * ONE / priceAA` rounds down to 0 — and there is no `minShares`/`minted > 0` check, so the deposit succeeds and `lastNAVAA += V`.
4. Attacker calls `withdrawAA(0)` in a later block (`_checkSameBlock` only blocks same-block deposit→withdraw, not cross-block). Their shares redeem at the inflated price, returning `D + V` (up to available liquidity) — victim's funds included.

The victim's only defense would be to notice they received 0 shares, but the underlying is already captured in NAV and split between tranches by `_updateSplitRatio`. Unlike the zero-supply case (which safely returns `oneToken` at line 297), the attacker's dust deposit creates nonzero supply and NAV, which is exactly the precondition the guard doesn't cover.

### Impact Explanation
Direct theft of depositor funds: any first depositor of a freshly deployed or fully-redeemed credit vault can steal the entire next deposit. Loss equals the victim's deposit amount (bounded only by the attacker's donation size). Same severity class as the ERC4626 inflation attack in the external report.

### Likelihood Explanation
- Requires the vault to have near-zero tranche supply (fresh deployment or after full redemption), which occurs at every vault launch and after defaults/write-offs that wipe a class.
- Attacker needs capital equal to roughly the victim's deposit size for the donation, but recovers the donation plus the victim's funds, so the attack is profitable for any victim deposit.
- On chains with public mempools this is a standard frontrun; the attacker can also simply monitor and repeat every block since failed attempts cost only gas.
- No existing guard blocks it: `_checkSameBlock` is per-user and per-block, `skipDefaultCheck`/`Default` revert only applies to losses, and `_guarded`/`limit` only caps size. The `_skimDonatedAssets` helper exists for manually sweeping stray tokens but is not invoked inside `_deposit`, so it does not prevent the donation from entering NAV before minting.

### Recommendation
Apply standard ERC4626 inflation mitigations at the vault level:

- Enforce a minimum initial deposit / mint a dead-share amount to `address(0)` or the vault itself on first deposit (e.g. require `_minted >= MIN_SHARES` and lock part of the first mint).
- Add a `minShares` slippage parameter to `depositAA`/`depositBB` and revert if `_minted < minShares` (also protects the 0-share case directly).
- Exclude unaccounted unlent balance from `getContractValue()` during share pricing, or automatically route donations through `_skimDonatedAssets` so they cannot inflate `priceAA`/`priceBB` mid-deposit.

### Proof of Concept
```solidity
// Foundry fork test against a live IdleCDOCreditVault instance
function test_FirstDepositorInflation() public {
    // vault: deployed IdleCDOCreditVault, AA tranche supply == 0
    deal(address(token), attacker, 601e6);
    deal(address(token), victim,   500e6);

    // 1) attacker dust deposit -> 1 wei NAV, ~1e12 shares
    vm.startPrank(attacker);
    token.approve(address(cdo), type(uint256).max);
    cdo.depositAA(1);

    // 2) donation inflates getContractValue()
    token.transfer(address(cdo), 501e6);
    vm.stopPrank();

    // 3) victim deposit mints 0 shares, lastNAVAA += 500e6
    vm.startPrank(victim);
    token.approve(address(cdo), type(uint256).max);
    uint256 minted = cdo.depositAA(500e6);
    vm.stopPrank();
    assertEq(minted, 0); // rounded to zero by inflated priceAA

    // 4) attacker redeems all shares, drains donation + victim principal
    vm.prank(attacker);
    uint256 redeemed = cdo.withdrawAA(0);
    assertGt(redeemed, 1000e6); // > donation + victim deposit
}
```

Note: if `AATranche` already has live supply, the equivalent attack applies to whichever tranche class has zero supply (e.g. a wiped BB class after `lastNAVBB == 0` is excluded by the `_lastTrancheNAV == 0` guard, so the dust-deposit setup must be replayed on that class before its NAV is revived). The PoC assumes a pre-launch/fully-redeemed AA tranche, which is the realistic launch-window scenario.
