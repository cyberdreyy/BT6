### Title
Signer chainstate validation silently switches between two unequal authority models (v1 local-only vs v2 global-state) per call, letting a version-boundary miner get a conflicting tenure-start block signed under the weaker check - ([File: stacks-signer/src/v0/signer.rs])

### Summary
The signer validates every block proposal through one of two mutually exclusive "governance" paths for chainstate correctness: the legacy `SortitionsView` (v1, local-state-only) or the newer `GlobalStateView` (v2, global-signer-state). Which path runs is *not* fixed per block; it is re-derived from `determine_active_signer_protocol_version()` at every checkpoint (proposal, validate-ok, pre-commit). The two paths are not equivalent: v1's tenure-change duplicate check only looks at `get_last_globally_accepted_block`, while v2's uses the strictly stronger `get_last_signed_block` (which also catches locally-accepted-but-not-yet-globally-accepted blocks). During a live protocol-version transition, a signer can evaluate a competing tenure-start proposal under v1 even after it has already locally accepted a conflicting tenure-start block, sign it, and end up having signed two conflicting blocks in the same tenure — exactly the class of hidden dual-authority bug described in the Hubble report, where two coexisting governance mechanisms of unequal strength let an attacker exploit the weaker one.

### Finding Description
`check_block_against_state` in `stacks-signer/src/v0/signer.rs` chooses the validation authority for a given call based on `state_version.uses_global_state()`: [1](#0-0) 

`state_version` comes from `self.determine_active_signer_protocol_version()`, which is computed fresh at each call from the signer's `GlobalStateEvaluator` — i.e. it depends on the *current* distribution of peers' broadcast protocol versions, not on anything pinned to the specific block being evaluated: [2](#0-1) 

`SortitionStateVersion::from_protocol_version` draws the v1/v2 line at `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`: [3](#0-2) 

The two paths are not equally strict. v1's `validate_tenure_change_payload` rejects a duplicate tenure-start block only when a **globally accepted** block already exists in the tenure: [4](#0-3) 

v2's equivalent check instead uses `get_last_signed_block`, which also covers **locally accepted (signed but not yet globally accepted)** blocks: [5](#0-4) 

The project's own regression test documents that the v1-style check ("`get_last_globally_accepted_block`... would miss blocks in `LocallyAccepted` or `PreCommitted` state") is a known-fixed bug for v2, but the fix was made version-specific rather than universal, leaving v1 exactly as weak as before: [6](#0-5) 

Because the active version is re-evaluated at every checkpoint from the live `GlobalStateEvaluator` state rather than fixed per proposal, a signer straddling the v1/v2 activation boundary (i.e. during the network's live protocol-version rollout, when `determine_active_signer_protocol_version()` can legitimately resolve to v1 for one call and v2 for another as peer broadcasts arrive) can:
1. Locally accept and sign a tenure-start block A for tenure T while `check_block_against_state` still resolves to v1 (block A only reaches `LocallyAccepted`, not yet `GloballyAccepted`).
2. Receive a competing tenure-start proposal B for the same tenure T from the same or another miner while the signer's evaluator still (or again) resolves the active version to v1.
3. `check_block_against_local_state` → v1 `SortitionsView::check_proposal` → `validate_tenure_change_payload` checks only `get_last_globally_accepted_block`, which is `None` (A is only `LocallyAccepted`), so the duplicate is **not detected**, and block B passes proposal-time validation.
4. The signer proceeds to validate/pre-commit/sign B, ending up having placed its signature on two conflicting tenure-start blocks (A and B) for the same tenure.

This is the "hidden governance" analog: two coexisting validation authorities (v1 local-only, v2 global-state) of unequal strength, where the choice of which one governs a given check is re-derived silently and independently at each call site rather than pinned once, and the weaker one is exploitable exactly at the moment the report describes — a rogue/weaker path hiding under a supposedly-unified check.

### Impact Explanation
This breaks the "one signed block per tenure-start" equality that both `validate_tenure_change_payload` implementations exist to enforce. A signer ends up signing a conflicting/duplicate tenure-start block it should have rejected, which is exactly the Critical-severity impact category defined by the rules ("a signer signing an invalid, non-canonical, or conflicting block"). If enough signers straddle the version boundary at the same moment (a normal condition during a live rollout, not requiring signer collusion), two conflicting tenure-start blocks could each independently accumulate signature weight.

### Likelihood Explanation
The trigger only requires: (a) the network to be in the middle of a live signer-protocol-version transition (a supported, expected operational state, not an edge case requiring a majority of malicious signers), and (b) a miner (or gossiping party) to (re-)propose a competing tenure-start block for a tenure the signer has already locally accepted a block in. No majority of signers, no signer key compromise, and no auth-token/local access is required — only the natural asynchrony of `determine_active_signer_protocol_version()` being re-evaluated per call from peer-broadcast state that can itself fluctuate near the activation threshold.

### Recommendation
Pin the active protocol/authority version once per block (e.g. at the time `BlockInfo` is first created for a proposal) and reuse that pinned version for every subsequent checkpoint (validate-ok recheck, pre-commit recheck) instead of re-deriving it from the live `GlobalStateEvaluator` at each call. Additionally, close the v1 duplicate-detection gap directly: have v1's `validate_tenure_change_payload` also consult `get_last_signed_block` (or an equivalent local-plus-global check), matching v2's stronger semantics, so the "hidden" weaker governance path cannot be relied upon even transiently during a version rollout.

### Proof of Concept
1. Signer S runs in a network transitioning through `GLOBAL_SIGNER_STATE_ACTIVATION_VERSION`.
2. Miner proposes tenure-start block A for tenure T; S's `determine_active_signer_protocol_version()` resolves to V1 at this moment (`check_block_against_state` → `check_block_against_local_state`). A passes v1's checks, S validates and signs A; A reaches `LocallyAccepted` in `signerdb` (not yet `GloballyAccepted`) — see `stacks-signer/src/chainstate/tests/v2.rs:756-850` for the exact scenario reproduced as a v2 regression test, which demonstrates the state (`LocallyAccepted`, not `GloballyAccepted`) that v1's check misses.
3. Miner (or the same miner replacing its own proposal) proposes a second tenure-start block B for the same tenure T. S's evaluator still/again resolves to V1 for this call.
4. `SortitionsView::check_proposal` → `validate_tenure_change_payload` (`stacks-signer/src/chainstate/v1.rs:505-518`) calls `get_last_globally_accepted_block`, which returns `None` because A is only `LocallyAccepted`. No `DuplicateBlockFound` is raised.
5. S proceeds to submit B for node validation, pre-commits, and ultimately signs B — now holding signatures over two conflicting tenure-start blocks (A and B) in tenure T.
