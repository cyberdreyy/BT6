### Title
Stale rejection weight never cleared when a signer reconsiders and accepts a block — miner-side `SignersRejected` can fire despite real 70% approval - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
The miner-side `StackerDBListener` tallies `total_weight_approved` and `total_weight_rejected` per block using two different, inconsistent de-duplication guards. A signer's weight can be added to `total_weight_rejected` from an initial `Rejected` message, and later — when the same signer legitimately reconsiders and sends `Accepted` for the same block — that signer's weight is *also* added to `total_weight_approved`, without ever removing/decrementing the earlier rejection weight. The two counters are meant to summarize disjoint, current signer intent, but they are additive-only and keyed by non-equivalent sets (`gathered_signatures` vs `responded_signers`), so a signer's final "accept" does not retract its earlier "reject" from the tally used to gate the miner's `SignersRejected` decision.

### Finding Description
In `handle_new_stackerdb_chunks` (stackerdb_listener.rs), the `Accepted` branch guards weight accumulation on `gathered_signatures`: [1](#0-0) 
while the `Rejected` branch guards weight accumulation on `responded_signers`: [2](#0-1) 

The `Accepted` branch inserts into *both* `gathered_signatures` and `responded_signers` at the end, but the `Rejected` branch inserts only into `responded_signers`: [3](#0-2) 

Trace the two possible message orders for one signer/slot on one `block_sighash`:

1. **Accept then Reject:** `gathered_signatures` and `responded_signers` both get the slot on Accept. A later Reject checks `responded_signers.insert(slot_id)` → already present → returns `false` → correctly suppressed. No double count.
2. **Reject then Accept (the reconsideration path signers are explicitly designed to support — see the comment "we do not change our votes on rejected blocks unless we receive a new block proposal for it and the reject reason allows us to reconsider" in `handle_block_pre_commit`, `stacks-signer/src/v0/signer.rs`):** Reject first sets `responded_signers` (not `gathered_signatures`) and adds weight to `total_weight_rejected`. A later legitimate Accept for the *same* `signer_signature_hash` checks `!gathered_signatures.contains_key(&slot_id)` → true (that map was never touched by the Reject) → weight is added a second time, now to `total_weight_approved`.

The result: the same signer's weight ends up counted in **both** `total_weight_rejected` and `total_weight_approved` simultaneously, and the stale rejection weight is never retracted. Nothing in this file, nor in `signer_coordinator.rs`, decrements `total_weight_rejected` when a later Accept supersedes an earlier Reject from the same signer.

### Impact Explanation
`SignCoordinator::get_block_status` in `stacks-node/src/nakamoto_node/signer_coordinator.rs` checks rejection weight *before* checking approval weight: [4](#0-3) 

Because the rejection branch is evaluated first (`if ... rejected ... > total_weight { return Err(SignersRejected) } else if approved >= threshold { Ok(...) }`), an inflated/stale `total_weight_rejected` — kept alive by a signer who has since flipped to Accept — can push the miner into concluding the block was rejected by a blocking minority even though real, current signer intent (post-reconsideration) has crossed the 70% acceptance threshold. This is a liveness wedge on the miner's block-production path: a valid, actually-approved block can be discarded/retried (`SignersRejected`), and the miner may also mis-attribute per-tx blame via `failed_txids` weight tracking that was computed off this same stale rejection.

This does not itself cause an invalid/non-canonical block to be signed (bounded to Medium-adjacent territory per the report's own downgrade rationale — the flaw is in bookkeeping, not in producing an unsafe signature), but it does break the intended equality "current tally of `total_weight_rejected`/`total_weight_approved` reflects each signer's *latest* recorded position" and can wedge block production even when a real quorum exists.

### Likelihood Explanation
This requires only a single signer (no majority, no other signer's key, no auth token) to send a `Rejected` message followed later by an `Accepted` message for the same `signer_signature_hash` — a sequence the signer state machine itself is documented to perform under normal "reconsideration" conditions, and which any single misbehaving or even honestly-reconsidering signer can trigger over gossip/StackerDB. No majority collusion is needed; the flaw is purely in the miner's bookkeeping of two disjoint sets.

### Recommendation
Use a single, consistent per-slot state tracker (e.g., store the signer's *current* vote — Accept or Reject — per `slot_id`, and when a new message supersedes a previous one, subtract the old contribution from the corresponding total before adding the new one). Concretely: gate the `Rejected` branch's weight increment on the same key used by the `Accepted` branch (`gathered_signatures`/`responded_signers` unified), and when a slot's vote flips from Reject→Accept (or vice versa), decrement the stale bucket's weight (`saturating_sub`) before incrementing the new bucket's weight, so that `total_weight_approved` and `total_weight_rejected` never simultaneously include the same signer's weight.

### Proof of Concept
1. Miner proposes block `B` with `signer_signature_hash = H`. Signer `S` (weight `w`) initially rejects: sends `BlockResponse::Rejected` for `H`. `stackerdb_listener.rs` records `responded_signers.insert(slot_S)` → true → `total_weight_rejected += w`.
2. Per the signer's own reconsideration logic (`handle_block_pre_commit`/related reconsideration path in `stacks-signer/src/v0/signer.rs`), `S` later determines `B` is acceptable and sends `BlockResponse::Accepted` for the same `H`.
3. In `stackerdb_listener.rs`, the Accepted branch checks `!gathered_signatures.contains_key(&slot_S)` → true (unset) → `total_weight_approved += w`, and only now inserts `slot_S` into both `gathered_signatures` and `responded_signers`.
4. `total_weight_rejected` still includes `w` from step 1; it is never decremented. If other signers push `total_weight_rejected` (including this stale `w`) past the blocking-minority threshold in `SignCoordinator::get_block_status`, the miner returns `NakamotoNodeError::SignersRejected` even though `S`'s current, latest vote (and possibly enough other signers') is Accept and the true approved weight already meets or exceeds the 70% threshold.
