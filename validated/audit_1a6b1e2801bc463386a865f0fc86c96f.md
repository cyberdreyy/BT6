### Title
`DeployGlobalContract`/`GlobalContractDeployMode::AccountId` is not restricted to self-calls, letting an unprivileged attacker force a victim account to burn balance and register malicious code under the victim's identity - ([File: runtime/runtime/src/global_contracts.rs])

### Summary
`action_deploy_global_contract` (and the `initiate_distribution` helper it calls) binds the `GlobalContractIdentifier::AccountId` to the `account_id` argument, which is the *receiver* of the action receipt being applied, not the original transaction `signer_id`. Unlike `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`, the `DeployGlobalContract` action is not restricted to receipts where `predecessor_id == receiver_id`, so any unprivileged account `A` can send (directly, or via a `FunctionCall`-created promise) an action receipt with `DeployGlobalContractAction{deploy_mode: AccountId, code: <malicious>}` targeting an arbitrary victim account `B` as receiver.

### Finding Description
`action_deploy_global_contract` receives `account_id` as the account currently being acted upon (the receiver of the enclosing action receipt), and uses it both to debit storage cost and to build the `GlobalContractIdentifier`: [1](#0-0) 
`initiate_distribution` then sets `GlobalContractIdentifier::AccountId(account_id.clone())` directly, with no comparison to the receipt's `predecessor_id` (the actual sender/attacker): [2](#0-1) 

The runtime's action-validation layer enumerates which actions require `predecessor_id == receiver_id` ("administrative", self-only actions): `DeployContract`, `Stake`, `AddKey`, `DeleteKey`, `DeleteAccount`. `DeployGlobalContract` and `UseGlobalContract` are conspicuously absent from that restricted set, both in the docs and in `validate_action_with_mode`, which dispatches `Action::DeployGlobalContract` to `validate_deploy_global_contract_action` with no receiver/predecessor check: [3](#0-2) [4](#0-3) 

Because of this gap, an attacker `A` can:
1. Sign a transaction (or have contract `A` create a cross-contract promise via `promise_batch_create`) with `receiver_id = B` (any victim account) and action `DeployGlobalContract{deploy_mode: AccountId, code: <attacker-chosen wasm>}`.
2. This produces an action receipt with `predecessor_id = A`, `receiver_id = B`.
3. When applied, `apply_action_receipt` invokes `action_deploy_global_contract` with `account_id = B` (the receiver), which: (a) debits/burns `B`'s balance for `storage_cost = per_byte_fee * code.len()`; (b) builds `GlobalContractIdentifier::AccountId(B)`; (c) emits a `GlobalContractDistributionReceipt` that stores the attacker's code under the trie key keyed by `B`'s account id.

The resulting global contract, permanently addressable and later updatable-looking as "owned by B" (per the documented semantics of `AccountId` mode: "Contract is deployed under the owner account id... This allows the owner to update the contract for all its users"), was in fact authored and funded from `A`'s malicious input while `B` never consented, and `B`'s NEAR balance was burned to pay for it.

### Impact Explanation
Two combined violations of the intended invariant ("a promise must not carry privileges its creator lacked"):
- **Loss of funds**: an unprivileged attacker can force any victim account to burn NEAR balance (`LackBalanceForState`/`tokens_burnt` path) for storage it never asked to pay for, purely by directing a receipt at it, with no receiver-side consent check.
- **Identity/authorization escalation**: under `AccountId` mode, the global contract identifier — intended to represent ownership/control by the named account — is populated using the receiver's id even though the code and the deploy decision came from the unrelated attacker account, letting the attacker impersonate `B` as the "owner" of arbitrary wasm code in the global contract registry.

This maps to the NEAR bounty categories of theft/loss of funds and authorization escalation across accounts/promises.

### Likelihood Explanation
Low cost, fully reachable by an ordinary unprivileged client: it only requires funding an account, signing a transaction (or a simple wasm contract that issues a cross-contract promise) targeting any receiver with a `DeployGlobalContractAction`. No special access key permission beyond a normal `FullAccess` key on the attacker's own account is required, and it is trivially repeatable against any account with a non-zero balance.

### Recommendation
Add `DeployGlobalContract` (and `UseGlobalContract`, which has the analogous issue of rewriting an arbitrary receiver's `AccountContract` pointer) to the set of actions requiring `predecessor_id == receiver_id` (self-only, unless preceded by `CreateAccount` in the same receipt), consistent with `DeployContract`/`Stake`/`AddKey`/`DeleteKey`/`DeleteAccount`. Enforce this check in the actor-permission validation path (`runtime/runtime/src/actions.rs::check_actor_permissions` or equivalent) rather than relying only on `validate_action_with_mode`.

### Proof of Concept
Unit/integration test plan:
1. Build a `Receipt`/action receipt with `predecessor_id = "attacker.near"`, `receiver_id = "victim.near"`, actions `[DeployGlobalContractAction{code: <arbitrary wasm>, deploy_mode: AccountId}]`.
2. Apply it through the runtime (`Runtime::apply` or `apply_action_receipt`) against a state where `victim.near` exists with sufficient balance and never signed/authorized this action.
3. Assert:
   - `victim.near`'s balance decreases by `storage_cost` (loss of funds despite no consent).
   - The resulting `GlobalContractDistributionReceipt`/stored `GlobalContractIdentifier::AccountId` equals `"victim.near"` (not `"attacker.near"`), i.e. `account_id` passed into `initiate_distribution` differs from `receipt.predecessor_id()`.
   - `UseGlobalContract{AccountId("victim.near")}` from any third account resolves to the attacker-supplied malicious code.

pub(crate) fn action_deploy_global_contract(
    state_update: &mut TrieUpdate,
    account: &mut Account,
    account_id: &AccountId,
    apply_state: &ApplyState,
    deploy_contract: &DeployGlobalContractAction,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let _span = tracing::debug_span!(target: "runtime", "action_deploy_global_contract").entered();

    let storage_cost = apply_state
        .config
        .fees
        .storage_usage_config
        .global_contract_storage_amount_per_byte
        .saturating_mul(deploy_contract.code.len() as u128);
    let Some(updated_balance) = account.amount().checked_sub(storage_cost) else {
        result.result = Err(ActionErrorKind::LackBalanceForState {
            account_id: account_id.clone(),
            amount: storage_cost,
        }
        .into());
        return Ok(());
    };
    result.tokens_burnt =
        result.tokens_burnt.checked_add(storage_cost).ok_or(IntegerOverflowError)?;
    account.set_amount(updated_balance);

    initiate_distribution(
        state_update,
        account_id.clone(),
        deploy_contract.code.clone(),
        &deploy_contract.deploy_mode,
        apply_state.shard_id,
        result,
    )?;

fn initiate_distribution(
    state_update: &mut TrieUpdate,
    account_id: AccountId,
    contract_code: Arc<[u8]>,
    deploy_mode: &GlobalContractDeployMode,
    current_shard_id: ShardId,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    let id = match deploy_mode {
        GlobalContractDeployMode::CodeHash => {
            GlobalContractIdentifier::CodeHash(hash(&contract_code))
        }
        GlobalContractDeployMode::AccountId => {
            GlobalContractIdentifier::AccountId(account_id.clone())
        }
    };
    // Increment the nonce and write it to state immediately to prevent multiple
    // distributions with the same nonce from being initiated. This requires
    // allowing the same nonce in the freshness check when applying the
    // distribution receipt.
    let nonce = increment_nonce(state_update, &id)?;
    let distribution_receipt =
        GlobalContractDistributionReceipt::new(id, current_shard_id, vec![], contract_code, nonce);
    let distribution_receipts =
        Receipt::new_global_contract_distribution(account_id, distribution_receipt);
    // No need to set receipt_id here, it will be generated as part of apply_action_receipt
    result.new_receipts.push(distribution_receipts);
    Ok(())
