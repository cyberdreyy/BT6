### Title
Builder pending withdrawal pays the EL fee_recipient more Gwei than is deducted from the builder's balance - (File: specs/gloas/beacon-chain.md)

### Summary
`get_builder_withdrawals` constructs a `Withdrawal` whose `amount` equals the raw, unclamped `builder_pending_withdrawals[i].amount`, while `apply_withdrawals` only decreases `state.builders[builder_index].balance` by `min(withdrawal.amount, builder_balance)`. When a builder's balance is less than the requested withdrawal amount, the execution-layer withdrawal that the block commits to (and that the EL actually credits to `fee_recipient`) is larger than the amount subtracted from the builder's on-chain balance, creating Gwei that is not backed by any deduction.

### Finding Description
In `get_builder_withdrawals` (specs/gloas/beacon-chain.md), each entry of `state.builder_pending_withdrawals` is converted into a `Withdrawal` object directly:
```
amount=withdrawal.amount
```
with no `min()` against the builder's current balance [4](#0-3) .

This `Withdrawal` list becomes `state.payload_expected_withdrawals`, which the execution payload must match exactly (this is the field the EL commits to and pays out). Meanwhile, `apply_withdrawals` reduces the *builder's* stored balance using a `min()` cap:
```
builder_balance = state.builders[builder_index].balance
state.builders[builder_index].balance -= min(withdrawal.amount, builder_balance)
``` [5](#0-4) 

So if `builder.balance < withdrawal.amount`, the beacon state only deducts `builder.balance` (driving it to zero), but the `Withdrawal` object — and therefore the amount the execution layer pays to `fee_recipient` — still carries the full, uncapped `withdrawal.amount`. The difference (`withdrawal.amount - builder.balance`) is Gwei paid to the recipient with no corresponding decrease anywhere in consensus-layer state: it is created from nothing.

This is explicitly exercised and treated as expected behavior by the test suite, e.g. `test_builder_withdrawal_insufficient_balance`, which sets `builder.balance = 1 ETH` but requests a `5 ETH` withdrawal, and asserts the resulting withdrawal still carries `amount = 5 ETH` while `builders[0].balance` merely goes to `0` [3](#0-2) . The same pattern recurs in `test_builder_withdrawal_insufficient_balance_realistic_bounds` and `test_all_builder_withdrawals_zero_balance` [6](#0-5) .

Note the contrast with validator partial/full withdrawals, where the amount placed in the `Withdrawal` itself is already clamped to available balance (`min(balance - MIN_ACTIVATION_BALANCE, withdrawal.amount)` for partials, `balance` itself for full withdrawals) [7](#0-6) ; only the builder path lacks this clamp at the point where the committed `Withdrawal.amount` is produced.

### Impact Explanation
This breaks the Gwei-conservation equality between what is deducted from consensus-layer balances and what the execution layer is instructed to pay out. A builder (or an operator who set up the `BuilderPendingWithdrawal` entry, e.g., via a prior `process_execution_payload_bid` that queued more withdrawal than the builder retains) can cause the protocol to commit to paying a `fee_recipient` more Gwei than exists in the builder's balance, with the excess materializing with no debit anywhere in `state`. This is a case of "Gwei paid to a non-owner" beyond what was actually available — a Critical-class equality break per the given impact definitions (Gwei created and paid out that the state's own balances do not support).

### Likelihood Explanation
The condition is reachable purely through normal, honest-looking sequences: `builder_pending_withdrawals` entries are created independently of the builder's current balance (e.g., by builder payment/withdrawal logic elsewhere in Gloas), and a builder's balance can decrease between the time a pending withdrawal is queued and the time it's swept for processing (via other withdrawals, slashable-like builder balance changes, or additional pending withdrawals draining the same builder first). No malicious peer or coalition is required — a single builder whose balance simply becomes insufficient by the time its queued withdrawal is processed triggers this every time, as demonstrated directly by the spec's own test vectors.

### Recommendation
Clamp the `amount` field written into the `Withdrawal` in `get_builder_withdrawals` to `min(withdrawal.amount, state.builders[builder_index].balance)` (accounting for any withdrawals already committed earlier in the same payload against the same builder, similar to how `get_balance_after_withdrawals` is used for validators), so the amount promised to the execution layer never exceeds what `apply_withdrawals` actually removes from `state.builders[...].balance`.

### Proof of Concept
1. Builder `B` has `state.builders[B].balance = 1_000_000_000` (1 ETH).
2. `state.builder_pending_withdrawals` contains an entry `{builder_index: B, fee_recipient: R, amount: 5_000_000_000}` (5 ETH) — as constructed in `test_builder_withdrawal_insufficient_balance`.
3. `process_withdrawals` runs: `get_builder_withdrawals` emits `Withdrawal(validator_index=convert(B), address=R, amount=5_000_000_000)` unclamped.
4. `apply_withdrawals` sets `state.builders[B].balance = max(0, 1_000_000_000 - min(5_000_000_000, 1_000_000_000)) = 0`.
5. The execution payload commits to (and the EL pays) `R` the full `5_000_000_000` Gwei per `state.payload_expected_withdrawals`, while only `1_000_000_000` Gwei was ever deducted anywhere in the beacon state — `4_000_000_000` Gwei is paid with no source, violating Gwei conservation.

def get_builder_withdrawals(
    state: BeaconState,
    withdrawal_index: WithdrawalIndex,
    prior_withdrawals: Sequence[Withdrawal],
) -> Tuple[Sequence[Withdrawal], WithdrawalIndex, Uint64]:
    withdrawals_limit = MAX_WITHDRAWALS_PER_PAYLOAD - 1
    assert len(prior_withdrawals) <= withdrawals_limit

    processed_count = Uint64(0)
    withdrawals: list[Withdrawal] = []
    for withdrawal in state.builder_pending_withdrawals:
        all_withdrawals = list(prior_withdrawals) + withdrawals
        has_reached_limit = len(all_withdrawals) >= withdrawals_limit
        if has_reached_limit:
            break

        builder_index = withdrawal.builder_index
        withdrawals.append(
            Withdrawal(
                index=withdrawal_index,
                validator_index=convert_builder_index_to_validator_index(builder_index),
                address=withdrawal.fee_recipient,
                amount=withdrawal.amount,
            )
        )
        withdrawal_index += 1
        processed_count += 1

    return withdrawals, withdrawal_index, processed_count

def test_builder_withdrawal_insufficient_balance(spec, state):
    """
    Test builder withdrawal with insufficient balance.

    Input State Configured:
        - state.builders[0]: Builder exists with only 1 ETH balance
        - builder_pending_withdrawals: Contains 1 entry requesting 5 ETH
        - builders[0].balance: 1 ETH (insufficient for requested 5 ETH)

    Output State Verified:
        - payload_expected_withdrawals: Contains 1 withdrawal
        - withdrawal.amount: 5 ETH (requested amount)
        - builders[0].balance: 0 (deduction capped to available balance)
        - builder_pending_withdrawals: Reduced by 1 (processed even if capped)
        - next_withdrawal_index: Incremented by 1
    """
    builder_index = 0
    withdrawal_amount = spec.Gwei(5_000_000_000)
    available_balance = spec.Gwei(1_000_000_000)

    prepare_process_withdrawals(
        spec,
        state,
        builder_indices=[builder_index],
        builder_withdrawal_amounts={builder_index: withdrawal_amount},
        builder_balances={builder_index: available_balance},
    )

    pre_state = state.copy()
    yield from run_gloas_withdrawals_processing(spec, state)

    assert_process_withdrawals(
        spec,
        state,
        pre_state,
        withdrawal_count=1,
        builder_balances={builder_index: 0},
        builder_pending_delta=-1,
        withdrawal_index_delta=1,
        withdrawal_amounts_builders={builder_index: withdrawal_amount},
    )
