### Title
Post-default instant withdraw requests mint unfundable receipts that are permanently frozen - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.requestWithdraw()` has an explicit post-default path: after `defaultRecoveryFinalized`, new requests are routed to `postDefaultRequests` and paid 1:1 from the isolated `defaultRecoveryReserve`. `requestInstantWithdraw()` has no equivalent branch. An attacker (or any user) can call the instant-withdraw request path after default finalization; the strategy burns their tranche tokens, mints a receipt, and records it under `instantWithdrawsRequestsByEpoch[user][epochNumber]` — an epoch that is never the `defaultRecoveryEpoch`, never funded by anyone, and never claimable. Like the kernel bug (a page allocated for a frame that is silently dropped on the error path), the receipt is allocated on a path the protocol can never settle: the reserved resource (burned principal) is leaked into an unreachable claim bucket.

### Finding Description
In `requestWithdraw`, the `defaultRecoveryFinalized` branch burns/mints and stores `postDefaultRequests[_user]`, which `_claimPostDefaultWithdrawRequest` pays from `defaultRecoveryReserve`. [1](#0-0)  `requestInstantWithdraw` instead unconditionally executes the pre-default flow: it burns the CDO's strategy tokens, mints the user a receipt, and increments `instantWithdrawsRequests`, `instantWithdrawsRequestsByEpoch[user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`, and `pendingInstantWithdraws`. [2](#0-1) 

On the claim side, `claimInstantWithdrawRequest` only clears the *defaulted-epoch* basis via `_claimDefaultedInstantWithdrawRequest`, which looks up `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]`. [3](#0-2) [4](#0-3)  A post-default instant receipt lives under a later epoch index, so it survives that clearing. It is then paid via `_transferFundedClaim`, which reverts whenever the payout would consume `defaultRecoveryReserve`. [5](#0-4)  Since no borrower repayment or `collectInstantWithdrawFunds` funding exists post-default (the epoch machine is terminal), the only balance the strategy holds post-finalization is the recovery reserve itself, so the claim reverts forever. Worse, `pendingInstantWithdraws` is permanently inflated, and `_ensureDefaultRecoveryInitialized` / finalization accounting treat it as an unfunded remainder that nothing resolves. [6](#0-5) 

### Impact Explanation
Any unprivileged user holding tranche tokens (or strategy-token receipts via the CDO) after `finalizeDefaultRecovery` can request an instant withdraw. Their tranche tokens are burned immediately, but the minted receipt maps to an epoch bucket that `_claimDefaultedInstantWithdrawRequest` will never touch and that `_transferFundedClaim` will never pay (reserve guard reverts). Result: permanent loss of the user's remaining post-haircut principal — the protocol destroys the backing while leaving an unclaimable receipt. This is permanent freezing/destruction of user funds, not a gas or DoS-only issue: the user's tranche tokens are gone with zero payout. It also permanently pollutes `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`, which can block or skew any subsequent recovery accounting that reads the unfunded remainder.

### Likelihood Explanation
The trigger requires only that the CDO still exposes `requestInstantWithdraw` after default finalization — the strategy itself does not gate it, and honest privileged roles (borrower, manager) are not involved. Any tranche holder who misses finalization or arrives afterward can hit it accidentally; an attacker can also grief the reserve accounting deliberately. The only mitigating uncertainty is whether `IdleCDOEpochVariant` independently blocks instant-withdraw requests once `defaulted()` is set; I was unable to confirm the CDO-side gating within the search budget, so likelihood is rated medium.

### Recommendation
Mirror `requestWithdraw`'s post-default handling in `requestInstantWithdraw`: either `revert NotAllowed()` when `defaultRecoveryFinalized` (instant liquidity cannot exist in a terminated vault), or route the request through `postDefaultRequests`-style accounting payable from `defaultRecoveryReserve`. Symmetrically, `claimInstantWithdrawRequest` should reject or reserve-fund any receipt whose epoch is not `defaultRecoveryEpoch` once recovery is finalized.

// Foundry fork test against an IdleCreditVault after finalizeDefaultRecovery
// Precondition: pool defaulted, manager called finalizeDefault/finalizeDefaultRecovery,
// defaultRecoveryFinalized == true, defaultInstantWithdrawsFinalized == true.

function testPostDefaultInstantWithdrawFrozen() external {
    // attacker is an unprivileged tranche holder; assume 'attacker' holds
    // AA tranche tokens post-default and idleCDO.requestInstantWithdraw path is open.
    uint256 amount = 100e18;

    // 1. Request instant withdraw post-default via the CDO (strategy sees msg.sender == idleCDO)
    vm.prank(attacker);
    cdoEpoch.requestInstantWithdraw(amount, address(AAtranche)); // burns tranches, mints receipt

    uint256 epochNow = strategy.epochNumber();
    assertEq(strategy.instantWithdrawsRequestsByEpoch(attacker, epochNow), amount);
    assertGt(strategy.pendingInstantWithdraws(), 0); // never funded by anyone

    // 2. Claim: defaulted-epoch clearing skips this receipt (different epoch index),
    //    then _transferFundedClaim reverts because payout would eat defaultRecoveryReserve.
    vm.prank(attacker);
    vm.expectRevert(NotAllowed.selector);
    cdoEpoch.claimInstantWithdrawRequest();

    // 3. Invariant broken: user's tranche tokens burned, receipt unclaimable forever.
    assertEq(strategy.instantWithdrawsRequests(attacker), amount);
}

  function requestInstantWithdraw(uint256 _amount, address _user) external {
    _onlyIdleCDO();
    _ensureDefaultRecoveryInitialized();
    // burn strategy tokens from cdo
    _burn(msg.sender, _amount);
  
    // mint equal amount of strategy tokens to the user as receipt, useful in case of default
    _mint(_user, _amount);

    // increase the instant withdraw requests for the user
    instantWithdrawsRequests[_user] += _amount;
    uint256 currentEpoch = epochNumber;
    // we record both per-user (old, kept for compatibility) and per-epoch so on
    // finalization we can distinguish "default-epoch pending instant receipts"
    // from old funded instant receipts.
    instantWithdrawsRequestsByEpoch[_user][currentEpoch] += _amount;
    instantWithdrawClaimsByEpoch[currentEpoch] += _amount;
    // increase the total instant withdraw requests
    pendingInstantWithdraws += _amount;

  function claimInstantWithdrawRequest(address _user) external {
    _onlyIdleCDO();

      // Clear the defaulted-epoch instant receipt first, then continue so the same call can
      // also pay any older instant receipt that was already funded before default finalization.
      _claimDefaultedInstantWithdrawRequest(_user);
    }
    uint256 amount = instantWithdrawsRequests[_user];
    // burn strategy tokens from user
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
    _transferFundedClaim(_user, amount);
  }

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
