### Title
View-role authenticated user can retrieve bridge `OutgoingToken` via unrestricted `GET /v2/bridge_types/:BridgeName` - ([File: core/web/router.go])

### Summary
`GET /v2/bridge_types/:BridgeName` is registered only under the generic `authv2` group (session or API token authentication), without any `auth.RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper, unlike sibling mutating routes (`Create`, `Update`, `Destroy`). `BridgeTypesController.Show` serializes the bridge into `presenters.BridgeResource`, which includes the raw `OutgoingToken` field, so any authenticated user regardless of role (including `UserRoleView`) can read it.

### Finding Description
In `core/web/router.go:268-273`, the bridge type routes are defined as:
- `POST /bridge_types` → wrapped with `auth.RequiresEditRole`
- `GET /bridge_types/:BridgeName` (`bt.Show`) → **no role wrapper**, only the outer `authv2` group's `auth.Authenticate(... AuthenticateByToken, AuthenticateBySession)`
- `PATCH`/`DELETE /bridge_types/:BridgeName` → wrapped with `auth.RequiresEditRole`

`auth.Authenticate` (`core/web/auth/auth.go:157-175`) only verifies identity (valid session or API token), it performs no role check. Role enforcement is exclusively done by explicit wrapper functions `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` (`core/web/auth/auth.go:200-255`), none of which is applied to `Show`.

`BridgeTypesController.Show` (`core/web/bridge_types_controller.go:125-146`) looks up the bridge and calls `presenters.NewBridgeResource(bt)`, which populates `OutgoingToken: b.OutgoingToken` (`core/web/presenters/bridges.go:18,37`) unconditionally — there's no redaction based on caller role, unlike `IncomingToken` which is only ever set explicitly in `Create` (never in `Show`). The `OutgoingToken` is the bridge's authentication secret sent to external adapters/EIs; leaking it lets an attacker impersonate the bridge/EI toward the node when it makes outbound bridge calls.

A user with `UserRoleView` (the lowest role, which per `RequiresRunRole`/`RequiresEditRole` is explicitly excluded from run/edit actions) can still successfully authenticate via session or API token and hit this endpoint, since `Show` has no role gate at all.

### Impact Explanation
This is a secret/credential disclosure vulnerability: a low-privilege view-only authenticated user can extract the `OutgoingToken` of any bridge configured on the node. This token is normally sent by the node to authenticate itself when calling the external bridge, and could be misused for impersonation/replay against the bridge's endpoint if that endpoint checks the token, or simply constitutes secret leakage beyond the caller's authorized privilege tier. This corresponds to the "unauthorized secret/credential disclosure" bounty impact class.

### Likelihood Explanation
Preconditions are minimal: only a valid view-role session or view-role API token is needed (the lowest privilege tier the node issues). The request is a single unauthenticated-role GET request (`GET /v2/bridge_types/<BridgeName>`) with no additional obstacles — fully repeatable and deterministic.

### Recommendation
Wrap the `Show` route with a role check consistent with the sensitivity of `OutgoingToken`, e.g. `authv2.GET("/bridge_types/:BridgeName", auth.RequiresEditRole(bt.Show))`, matching `Create`/`Update`/`Destroy`. Alternatively, redact `OutgoingToken` from the `BridgeResource` returned by `Show`/`Index` unless the caller has edit/admin role (similar to how `IncomingToken` is only populated for `Create`).

### Proof of Concept
Add a handler-level test in `core/web/bridge_types_controller_test.go`:
1. Seed a bridge with a known `OutgoingToken` via `BridgeORM().CreateBridgeType`.
2. Create a test client authenticated as a `UserRoleView` user (session or API token), similar to existing patterns using `cltest.CreateJobRunViaExternalInitiator`/`cltest.CreateUserWithSession` helpers in the test file.
3. Issue `GET /v2/bridge_types/<BridgeName>` with that view-role client.
4. Assert the response is `200 OK` (proving no role gate) and decode `presenters.BridgeResource`, asserting `resource.OutgoingToken == seededOutgoingToken` — confirming the secret is exposed.
5. As a comparison, add a companion test asserting `POST/PATCH/DELETE /v2/bridge_types/...` correctly returns `401 Unauthorized` for the same view-role user (via `RequiresEditRole`), highlighting the inconsistency that only `Show` is unguarded. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
