### Title
Write-off requests let any tranche holder reserve arbitrarily large lender liquidity with refundable collateral - (contracts/IdleCreditVaultWriteOffEscrow.sol)

### Summary
`IdleCreditVaultWriteOffEscrow.createWriteOffRequest` accepts a tranche-token deposit `amount` and an independent, unbounded `underlyingsRequested` value, and accumulates the latter into the global `pendingUnderlyings` counter. Because the tranche deposit is fully refundable via `deleteWriteOffRequest` and `underlyingsRequested` is not bounded by the value of the deposited tranches, an attacker can make the pool treat a very large amount of underlying as reserved for write-off fulfillment while posting little or effectively free collateral — the same asymmetric "lock LP funds cheaply" griefing class as the Hyperdrive short report.

### Finding Description
- `createWriteOffRequest` only requires `isEpochRunning()` and `amount != 0`; there is no check that `underlyingsRequested` is consistent with the value of `tranches` deposited. The full `underlyingsRequested` is added to `pendingUnderlyings` (contracts/IdleCreditVaultWriteOffEscrow.sol:86-102).
- `pendingUnderlyings` is the pool-facing signal that lender capital must remain reserved/available so that a fulfiller (typically the borrower, via `fullfillWriteOffRequest` → `writeOffDeposit`) can settle the requests. It is only released when requests are fulfilled or deleted (lines 112, 134).
- The attacker can call `deleteWriteOffRequest` at any time to recover the deposited tranche tokens, so the griefing position costs nothing beyond gas and transient tranche-token acquisition. There is no expiry, no bond/cost proportional to `underlyingsRequested`, and no requirement that the requester be KYC'd — `createWriteOffRequest` does not call `isWalletAllowed`, unlike `requestDeposit`/`requestWithdraw` in `IdleCDOEpochQueue` (contracts/IdleCDOEpochQueue.sol:103-143).
- Analogous to the Hyperdrive report: the trader paid only the small implied interest while forcing LPs to fund the full bond notional; here the attacker posts a small (and refundable) tranche amount while forcing the pool to keep a large `underlyingsRequested` amount of lender liquidity reserved for the escrow.

### Impact Explanation
Temporary freezing of lender funds. While `pendingUnderlyings` is elevated, the reserved underlying cannot be treated as free liquidity for the epoch (drawdowns by the borrower, instant withdrawals, and stop-epoch settlement all have to respect the outstanding write-off demand). An attacker holding tranche tokens worth, e.g., 1% of TVL can register `underlyingsRequested` orders of magnitude larger, forcing the pool/borrower to keep capital idle for the duration of the epoch with no recourse — the requests are only cleared by the attacker's own `deleteWriteOffRequest` or by a fulfiller paying the requested underlyings. Quantification: funds frozen ≈ `pendingUnderlyings` at attacker's choice; attacker cost ≈ refundable tranche deposit + gas.

### Likelihood Explanation
- Attacker requirements are minimal: acquire tranche tokens (any KYC'd lender can also do this directly) and call one function during a running epoch.
- No privileged role is needed; the honest owner/manager cannot clear `pendingUnderlyings` on the attacker's behalf (only `emergencyWithdraw` of token balances exists, not request deletion).
- The attack is repeatable every epoch and can also occur "naturally" if lenders set stale inflated `underlyingsRequested` values, mirroring the report's "can also happen naturally" note.
- Caveat: the exact magnitude of frozen liquidity depends on how `pendingUnderlyings` is consumed downstream (reservation vs. informational); I could not fully trace its use in `IdleCreditVault`/`IdleCDOEpochVariant` accounting within the available passes, so the worst case assumes it gates borrower drawdown/liquidity as designed.

### Recommendation
- Bound `underlyingsRequested` to the value of the deposited tranches at the current `virtualPrice` (e.g., `underlyingsRequested <= amount * virtualPrice(tranche) / ONE_TRANCHE`), updated when the request is topped up.
- Apply the same `isWalletAllowed` check used by `IdleCDOEpochQueue` so only KYC'd lenders can create requests.
- Optionally add a request expiry or allow owner/manager to cancel stale requests and decrement `pendingUnderlyings`.

### Proof of Concept
```solidity
// Foundry fork test sketch (running epoch, AA escrow)
function testCheapLiquidityLockup() public {
    // attacker holds a small amount of tranche tokens
    uint256 smallTranches = 1e18;               // ~1 unit of tranche token
    uint256 hugeAsk       = 50_000_000e6;       // e.g. 50M USDC requested

    vm.startPrank(attacker);
    IERC20(tranche).approve(address(escrow), smallTranches);
    escrow.createWriteOffRequest(smallTranches, hugeAsk);
    vm.stopPrank();

    // pool now carries hugeAsk in pendingUnderlyings while attacker posted ~nothing
    assertEq(escrow.pendingUnderlyings(), hugeAsk);

    // reserved liquidity cannot be drawn/spent elsewhere for the rest of the epoch;
    // attacker exits the position for free at any time:
    vm.prank(attacker);
    escrow.deleteWriteOffRequest();
    assertEq(escrow.pendingUnderlyings(), 0);
    assertEq(IERC20(tranche).balanceOf(attacker), smallTranches); // fully refunded
}
```
