### Title
Confirmations from Deleted Multisig Members Are Not Purged, Allowing Requests to Execute Below the Confirmed Threshold - (multisig2/src/lib.rs)

### Summary
`delete_member()` in the `multisig2` contract only removes the pending *requests* that were originally created by the member being removed. It does not scan and strip that member's stale `confirmation` entry from other pending requests that member had merely *confirmed* (but not created). Because `confirm()` counts confirmations purely by set size (`confirmations.len() + 1 >= self.num_confirmations`) without checking that every entry in the set still corresponds to a current member, a stale confirmation from a removed member remains permanently counted toward the K-of-N threshold for any request it was previously added to.

### Finding Description
The binding the multisig is supposed to guarantee is:
```
count(confirmations for request R that belong to CURRENT members) == count required to execute R (num_confirmations)
```

`confirm()` blindly trusts the stored confirmation set size: [1](#0-0) 

`delete_member()` only cleans up requests where the removed member was the *creator* (`r.member == member`), and separately clears `num_requests_pk`. It never inspects the `confirmations` map of other, still-pending requests to remove the entry belonging to the member being deleted: [2](#0-1) 

Sequence:
1. Member A creates request R (a `Transfer`).
2. Member B (a distinct, currently valid member) calls `confirm(R)` — `confirmations = {A, B}`. `num_confirmations = 3`, so R stays pending (not yet enough confirmations).
3. Through a separate, legitimate `DeleteMember { member: B }` request, the multisig removes B (e.g., because B's key was compromised or B left the organization). `delete_member` only removes requests whose `r.member == B` (i.e., requests B created), so R (created by A) is untouched, and B's entry stays inside `confirmations` for R.
4. Member C (a currently valid member, distinct from A and B) calls `confirm(R)`. The check becomes `confirmations.len() (2, i.e. {A,B}) + 1 = 3 >= num_confirmations (3)` → true, and R executes.

R is executed with confirmations from only 2 live members (A and C) even though `num_confirmations = 3` — the stale confirmation attributed to the removed member B is silently counted as if it were still authoritative.

### Impact Explanation
This breaks the fundamental K-of-N authorization guarantee of the multisig contract, which the README documents as the core security property (any transfer, key addition, function call, or membership change requires `K` valid confirmations). A request — including a `Transfer` of funds, `AddKey` (granting full access), or `DeleteMember`/`AddMember` — can be executed with fewer than the configured number of *currently valid* confirmations, directly matching the "Critical: a multisig request executed below threshold" impact category.

### Likelihood Explanation
This requires no privileged attacker and no compromise: it occurs from entirely ordinary, expected multisig operation — creating a request, confirming it, and later removing a member who had confirmed an as-yet-unexecuted request (a routine key-rotation or offboarding event). Any minority coalition (K-1 of the remaining live members) can subsequently push execution of the older pending request through using the leftover phantom confirmation.

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' `confirmations` sets (not only those the member created) and remove the deleted member's entry. Alternatively, validate at `confirm()`-time (and at execution time) that every account/key present in a request's confirmation set is still a current member before counting it toward `num_confirmations`.

### Proof of Concept
```
// num_confirmations = 3, members = {A, B, C, D}
A: add_request(Transfer{...})                 // request R created
B: confirm(R)                                 // confirmations(R) = {A, B}; len+1=2 < 3, pending

// Separate legitimate governance action to rotate out B
A: add_request_and_confirm(DeleteMember{B})
C: confirm(...)                               // reaches 3 confirmations, executes delete_member(B)
                                               // delete_member only purges requests created BY B; R is untouched,
                                               // confirmations(R) still contains "B"

C: confirm(R)                                 // confirmations(R).len() (2: {A,B}) + 1 = 3 >= 3 -> executes
// R (the Transfer) executes with live confirmations only from A and C (2 members),
// even though num_confirmations == 3 and B is no longer a member.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
