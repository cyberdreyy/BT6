### Title
Unauthenticated-role bridge secret disclosure via `GET /v2/bridge_types` leaks `OutgoingToken` for every bridge - ([File: core/web/bridge_types_controller.go])

### Summary
The `GET /v2/bridge_types` route is registered with only `paginatedRequest(bt.Index)` and no role gate, while write endpoints on the same resource require `auth.RequiresEditRole`. Since `presenters.NewBridgeResource` unconditionally includes the bridge's `OutgoingToken` in the JSON response, any authenticated user/token with the lowest role (`run`, or even `view`, since no role check exists at all on this route) can enumerate and exfiltrate every bridge's `OutgoingToken` secret.

### Finding Description
The route table shows the asymmetry directly: [1](#0-0) 

`GET /bridge_types` and `GET /bridge_types/:BridgeName` are wrapped only in the base `Authenticate` middleware group (session or token, any role), whereas `Create`, `Update`, and `Destroy` require `auth.RequiresEditRole`. `RequiresRunRole` only excludes `UserRoleView`; `RequiresEditRole` additionally excludes `UserRoleRun`: [2](#0-1) 

But `Index` isn't even wrapped in `RequiresRunRole` — it has no role check at all, so even a `view`-role token/session can call it.

`BridgeTypesController.Index` fetches all bridge rows for the page and serializes each with `presenters.NewBridgeResource`: [3](#0-2) 

`NewBridgeResource` copies `b.OutgoingToken` into the response struct unconditionally (not `omitempty`, no redaction), unlike `IncomingToken` which is deliberately empty here (only set explicitly on `Create`): [4](#0-3) 

The `Show` handler (`GET /bridge_types/:BridgeName`, also unguarded by any role check) exhibits the identical leak for a single bridge: [5](#0-4) 

So a low-privileged token holder authenticates, then calls `GET /v2/bridge_types?size=1000`, and the response body contains every bridge's `outgoingToken` field in plaintext — a secret meant to authenticate inbound callbacks from external adapters to the node (i.e., the node trusts requests bearing this token as legitimate bridge responses).

### Impact Explanation
This matches Chainlink's "sensitive data/secret disclosure leading to request forgery" impact class. Possessing `OutgoingToken` values allows the attacker to forge legitimate-looking outgoing bridge callback requests to the node for bridges they don't own/administer, potentially manipulating job run results/pipeline data across the whole node — a mass secret exfiltration limited only by the number of configured bridges.

### Likelihood Explanation
Trivial and fully repeatable: requires only a valid `run`-role (or even `view`-role, since no role gate exists) API token or session — no edit/admin privilege needed. A single paginated GET request (`size=1000`) exfiltrates all bridges in one call; repeating with pagination covers the rest. No timing, race, or environment-specific conditions are needed.

### Recommendation
- Add a role gate on `GET /v2/bridge_types` and `GET /bridge_types/:BridgeName` (at minimum `auth.RequiresEditRole`, consistent with the write endpoints), or
- Strip/redact `OutgoingToken` from `presenters.NewBridgeResource` for list/show responses and only reveal it (like `IncomingToken`) at creation time or via an explicit admin-only reveal endpoint, mirroring the pattern already used for `IncomingToken`.

### Proof of Concept
Handler-level integration test (extends existing `core/web/bridge_types_controller_test.go` patterns):
1. Start `cltest.NewApplication`, create a run-role (or view-role) API token/session distinct from the default admin session used in `TestBridgeTypesController_Index`.
2. Create a bridge via an admin/edit session (`POST /v2/bridge_types`) and capture the returned `outgoingToken` from the DB (`orm.FindBridge`).
3. Using the run-role client, call `GET /v2/bridge_types?size=1000`.
4. Assert response status is `200 OK` (not `401`/`403`) and that `resources[i].OutgoingToken` equals the bridge's actual `OutgoingToken` from the DB — proving the secret is returned to a role that has no edit/admin privilege.
5. Additionally assert that the same run-role client can call `GET /v2/bridge_types/:BridgeName` (`Show`) and get the same leaked `OutgoingToken`.
6. Expected fix assertion: after remediation, either the run-role request returns `401/403`, or `resources[i].OutgoingToken` is empty/redacted.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// 'edit'

	return func(c *gin.Context) {

			c.Abort()

func (btc *BridgeTypesController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	bridges, count, err := btc.App.BridgeORM().BridgeTypes(ctx, offset, size)

	resources := make([]presenters.BridgeResource, 0, len(bridges))
	for _, bridge := range bridges {
		resources = append(resources, *presenters.NewBridgeResource(bridge))
	}

	paginatedResponse(c, "Bridges", size, page, resources, count, err)
}

// Show returns the details of a specific Bridge.
func (btc *BridgeTypesController) Show(c *gin.Context) {
	ctx := c.Request.Context()
	name := c.Param("BridgeName")

	taskType, err := bridges.ParseBridgeName(name)
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	bt, err := btc.App.BridgeORM().FindBridge(ctx, taskType)
	if errors.Is(err, sql.ErrNoRows) {
		jsonAPIError(c, http.StatusNotFound, errors.New("bridge not found"))
		return
	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	jsonAPIResponse(c, presenters.NewBridgeResource(bt), "bridge")
}
