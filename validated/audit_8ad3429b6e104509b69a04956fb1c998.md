### Title
Drained ERC4626 vault liquidity permanently reverts `stopEpoch` and freezes the credit pool - (File: contracts/strategies/idle/ProgrammableBorrower.sol)

### Summary
`ProgrammableBorrower.onStopEpoch` treats a "covered but illiquid" ERC4626 withdrawal as a hard revert (`StopEpochVaultLiquidityUnavailable`) rather than letting `IdleCDOEpochVariant.stopEpoch` proceed to the default path. An unprivileged LP of the configured ERC4626 vault can keep its cash drained, so every `stopEpoch` call reverts, the epoch can never close, and all tranche funds stay locked.

### Finding Description
`IdleCDOEpochVariant.stopEpoch` calls `ProgrammableBorrower.onStopEpoch` before pulling funds. In `onStopEpoch` (contracts/strategies/idle/ProgrammableBorrower.sol:240-253) the logic is:

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  // Only an otherwise-covered ERC4626 withdrawal failure should make stopEpoch retryable.
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The coverage check uses `convertToAssets(shares)`, which only measures the claim size — not the vault's available liquidity. If the vault's idle liquidity is below `shortfall` (e.g. an attacker LP withdraws all lendable assets), `vault.withdraw` reverts and `onStopEpoch` reverts. `stopEpoch` therefore reverts before the `transferFrom` failure that would trigger `_handleBorrowerDefault`, and `onDefault` is also unreachable because it is only invoked after a failed settlement. `borrow()` and `repay()` are epoch-gated, `emergencyExitVault`/`rescueTokens` are owner-only and equally liquidity-dependent, so no honest or unprivileged path unwinds the position while the vault stays drained.

### Impact Explanation
Broken invariant: epoch state machine liveness. Direct consequence: temporary (attacker-sustained, potentially indefinite) freezing of all pool funds — pending withdraw receipts, tranche redemptions, and principal recall are all blocked while the epoch is wedged between `isEpochRunning = true` and an unstoppable `stopEpoch`. An LP attacker only needs to hold the vault's liquidity out; the attack is repeatable each time liquidity returns, and `depositDuringEpoch`/claims are gated by the epoch flags. Quantified loss: 100% of vault-backed tranche value unavailable for the duration of the grief.

### Likelihood Explanation
Requires the deployment to use a vault whose liquidity can be drained by third parties (standard for lending/ERC4626 vaults) and an attacker willing to hold that liquidity out. The attacker pays no direct cost beyond opportunity cost of the withdrawn liquidity, and can front-run each `stopEpoch`. Medium likelihood, conditional on vault choice.

### Recommendation
In `onStopEpoch`, distinguish "shares don't cover" from "withdraw reverted": pre-check `vault.maxWithdraw(address(this))` (or convert the revert into `return true`) so that an illiquid-but-covered position falls through to IdleCDO's `transferFrom` failure and the existing default/finalizeDefault recovery path, instead of reverting the whole stop flow. Alternatively, let the failed-withdraw path still snapshot `bufferStartVaultAssets` and clear `epochAccountingActive` so a later `onDefault`/recovery can proceed.
