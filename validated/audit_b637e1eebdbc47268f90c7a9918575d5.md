### Title
ETH attached to a withdrawal is permanently locked in the ephemeral `EthenaCooldownRequest` clone — (`contracts/IdleCDOEthenaVariant.sol`)

### Summary
`IdleCDOEthenaVariant._withdraw` forwards `msg.value` into the freshly deployed `EthenaCooldownRequest` clone via `ClonesWithImmutableArgs.clone(target, data, value)`. The clone has no ETH-recovery path: its `rescue` only sweeps ERC20 tokens, and it has no payable/ETH-transfer function. Any native token attached to a withdraw call is therefore irrecoverably stuck in a single-use clone.

### Finding Description
In `contracts/IdleCDOEthenaVariant.sol` (lines 82-85), the cooldown clone is created with:

```solidity
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender),
  msg.value
));
```

`ClonesWithImmutableArgs.clone(address, bytes, uint256)` sends the given ETH value to the new clone at deployment. Reading `msg.value` here does not itself require the calling function to be `payable`, but the explicit forwarding shows the design tolerates value being attached (the chain/L2 IdleCDO variants use `payable` entrypoints).

The clone contract (`contracts/strategies/ethena/EthenaCooldownRequest.sol`) exposes only:
- `startCooldown()` — calls `cooldownShares` on sUSDe
- `unstake()` — sends sUSDe proceeds to the user
- `rescue(address _token)` — transfers only the ERC20 `IERC20Detailed(_token).balanceOf(address(this))` to the multisig

There is no `receive`/ETH sweep and no way to move native balance out of the clone (calling `rescue` with `address(0)`/WETH cannot retrieve ETH). The clone's only legitimate inflows should be sUSDe; ETH is never needed for `cooldownShares` or `unstake`. So any `msg.value` forwarded serves no purpose and becomes permanently locked.

This is the direct analog of the reported bug: a code path that accepts (and here actively forwards) native value while performing an ERC20-denominated operation, with no check that `msg.value == 0` and no recovery mechanism.

Caveat I could not fully resolve within the index: whether the concrete `withdrawAA`/`withdrawBB` entrypoints for this deployment are `payable`. If they are non-payable, `msg.value` is always 0 and the loss path is unreachable — the verification hinges on the deployed variant's entrypoint modifier. If payable, the loss is unconditional.

### Impact Explanation
A withdrawer (or an integrator contract/relayer acting on behalf of a withdrawer) that attaches any ETH to a withdraw call loses the entire amount. It is forwarded to a deterministic-but-ephemeral clone address whose bytecode contains no ETH withdrawal logic; even the trusted `TL_MULTISIG` `rescue` cannot recover it (ERC20-only transfer). Loss equals `msg.value` sent — permanent freezing of user funds with zero benefit, identical in effect to the OpenQ `receiveFunds` lost-`msg.value` issue.

### Likelihood Explanation
Low-to-medium: it requires a user to attach ETH to a withdraw transaction (e.g., via a multicall/batching front-end, an L2 retryable-ticket flow where ETH is commonly attached, or wallet error). It requires no attacker and no privileged misbehavior. The fix cost is trivial, and the precedent report classifies this as Medium.

### Recommendation
In `IdleCDOEthenaVariant._withdraw`, deploy the clone without forwarding value and reject attached ETH:

```solidity
require(msg.value == 0, "no-eth");
EthenaCooldownRequest clone = EthenaCooldownRequest(cooldownImpl.clone(
  abi.encodePacked(address(this), msg.sender)
));
```

Alternatively add a `sweepETH()` function to `EthenaCooldownRequest` restricted to `TL_MULTISIG`, but reverting on `msg.value != 0` is the simpler invariant.

### Proof of Concept
Foundry fork (mainnet), assuming a payable withdraw entrypoint:

```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;
import "forge-std/Test.sol";

contract EthenaMsgValueTest is Test {
    IdleCDOEthenaVariant cdo = IdleCDOEthenaVariant(payable(ETHEENA_CDO));
    address user = makeAddr("user");

    function testEthLockedInClone() public {
        // user holds AA tranche tokens; sUSDe cooldown active
        deal(USDE, address(cdo-strategy-liquidity...)); // fund CDO liquidity
        deal(address(AATranche), user, 1000e18);

        vm.recordLogs();
        vm.prank(user);
        cdo.withdrawAA{value: 1 ether}(1000e18); // attaches ETH

        // recover clone address from NewCooldownRequestContract event
        address clone = _extractCloneFromLogs();
        assertEq(clone.balance, 1 ether);      // ETH forwarded to clone
        // no function on EthenaCooldownRequest can move ETH:
        // rescue() only does IERC20Detailed(_token).transfer -> cannot send ETH
        vm.expectRevert();
        EthenaCooldownRequest(clone).rescue(address(0)); // not ETH-capable
        assertEq(clone.balance, 1 ether);      // permanently locked
    }
}
```

If the deployed `withdrawAA` is non-payable, the call reverts and the finding reduces to dead/misleading code that should still be cleaned up by removing the `msg.value` forward.
