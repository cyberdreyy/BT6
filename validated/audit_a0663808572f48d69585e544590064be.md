## Finding: Valid

### Title
Public, permissionless `create()` lets an attacker pre-deploy the deterministic lockup address for a victim owner with an attacker-chosen whitelist - ([File: lockup-factory/src/lib.rs])

### Summary
`LockupFactory::create` computes the lockup's account id deterministically from only `owner_account_id` (`sha256(owner_account_id)[..20] + "." + factory`), and lets the caller supply an arbitrary `whitelist_account_id` that is passed straight through as `staking_pool_whitelist_account_id` with no check that it matches the canonical `self.whitelist_account_id`, and no check that the caller is the owner or the foundation. Any unprivileged account can front-run the intended lockup creation for a known/predictable `owner_account_id` (e.g. an employee about to receive a vesting lockup) by calling `create()` first with a hostile whitelist contract, permanently occupying that deterministic address with attacker-chosen parameters.

### Finding Description
The broken binding: `staking_pool_whitelist_account_id(lockup_at(owner)) == factory.whitelist_account_id` is expected to hold for every lockup created by the canonical factory flow, but the code allows `staking_pool_whitelist_account_id(lockup_at(owner)) == whitelist_account_id_chosen_by_predecessor`.

In `create`, the lockup account id is derived purely from `owner_account_id`: [1](#0-0) 
and the whitelist is taken from the caller-supplied optional parameter, defaulting to the canonical one only when omitted: [2](#0-1) 
There is no assertion that `env::predecessor_account_id() == owner_account_id` (or that predecessor is the foundation), and no assertion that the supplied `whitelist_account_id` equals `self.whitelist_account_id`. `create()` is `#[payable]` and callable by any account for `MIN_ATTACHED_BALANCE` (3.5 NEAR): [3](#0-2) 

Because the account id is a pure function of `owner_account_id`, anyone can compute in advance the exact account address that the foundation would use for a given employee/owner, and race to call `create()` first with:
- `owner_account_id` = the victim's known/intended owner id,
- `whitelist_account_id` = a contract the attacker deploys and controls (which can answer `is_whitelisted` with `true` for any pool),
- minimal `vesting_schedule`/`lockup_duration` and the minimum attached deposit.

`Promise::new(lockup_account_id).create_account()...` will succeed for the attacker (first mover), deploying the lockup with the hostile whitelist baked into its `staking_pool_whitelist_account_id` field, consumed later by the victim's lockup via `select_staking_pool` -> `ext_whitelist::is_whitelisted(..., &self.staking_pool_whitelist_account_id, ...)`: [4](#0-3) 
When the legitimate creator (foundation) subsequently attempts to create the real lockup for that same `owner_account_id`, the account-creation sub-action fails (`AccountAlreadyExists`), `on_lockup_create` detects `is_promise_success() == false` and simply refunds the foundation's deposit: [5](#0-4) 
leaving the attacker's hostile lockup permanently squatting the canonical address for that owner, with a whitelist the protocol/owner believe is the canonical staking-pool whitelist but is actually attacker-controlled.

None of the existing guards prevent this: `assert_self()`/`is_promise_success()` only gate the callback's own logic, and there is no `assert_called_by_foundation` or ownership check anywhere in `create`. The existing test `test_create_lockup_with_custom_whitelist_success` even demonstrates that supplying a custom whitelist is accepted with no restriction: [6](#0-5) 

### Impact Explanation
Once the owner (the real victim employee) is later granted use of / funded on this squatted lockup, or independently starts using it as their canonical lockup, `select_staking_pool` will trust the attacker-controlled whitelist instead of the canonical `whitelist_account_id`, letting the owner "successfully" select an attacker-deployed fake staking pool that the real whitelist would have rejected. Subsequent `deposit_and_stake` calls send the owner's NEAR to that attacker contract, which can simply keep it - NEAR leaving the lockup to a party never entitled to it. This matches the Critical category "a lockup deployed with parameters its rightful creator never chose" (the whitelist parameter was chosen by the attacker, not the foundation/rightful creator), and can also lead to funds being irrecoverably routed to the attacker's pool. The attack is repeatable against any predictable/known future owner account id, at a cost of only `MIN_ATTACHED_BALANCE` (3.5 NEAR) per squatted address.

### Likelihood Explanation
No privileged role is required: the attacker only needs to know or guess a target `owner_account_id` before the real lockup is created, deploy a malicious "whitelist" contract, and call the public, unauthenticated `create()` with `MIN_ATTACHED_BALANCE`. This is entirely within the unprivileged attacker capability set (send a transaction, attach a deposit, deploy and name a contract). The only timing constraint is winning the race against the legitimate creator, which is plausible since employee/owner account ids are often known or predictable ahead of the actual on-chain creation transaction.

### Recommendation
In `LockupFactory::create`, restrict `whitelist_account_id` override to the foundation account (`assert_called_by_foundation`) or remove the override entirely and always use `self.whitelist_account_id`. Additionally, require `env::predecessor_account_id() == foundation_account_id` (or otherwise gate `create()`) so arbitrary accounts cannot deploy lockups for owner ids they don't control, closing the address-squatting race.

### Proof of Concept
`cargo test` plan (extending `lockup-factory/src/lib.rs` test module):
1. Initialize `LockupFactory::new(whitelist_account_id(), foundation_account_id())`.
2. As `attacker`, call `contract.create(victim_owner_account_id(), lockup_duration, None, None, None, Some(attacker_whitelist_account_id()))` with `MIN_ATTACHED_BALANCE`, then simulate `on_lockup_create` with `PromiseResult::Successful` to confirm the lockup at `lockup_account_for(victim_owner_account_id())` now exists with `staking_pool_whitelist_account_id == attacker_whitelist_account_id()` (assert via constructed `LockupArgs`/derived account id, matching the existing `hex::encode(sha256(owner))` derivation at lines 119-121).
3. As `foundation`, call `contract.create(victim_owner_account_id(), ..., None)` (default/canonical whitelist) targeting the same `owner_account_id`; simulate the account-creation promise as `PromiseResult::Failed` and assert `on_lockup_create` returns `false` and refunds `attached_deposit` to `foundation` - proving the legitimate creation is blocked and the squatted address with `attacker_whitelist_account_id()` remains in place, i.e. `staking_pool_whitelist_account_id(lockup_at(victim_owner)) != self.whitelist_account_id`.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
