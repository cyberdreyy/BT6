### Title
Stale `instantWithdrawsRequestsByEpoch` receipt lets an instant-withdraw claim be paid twice, including once from the default recovery reserve - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
The ArtGobblers bug is a "stale field revives a consumed asset" bug: `mintLegendaryGobbler` burned tokens but never cleared `getApproved`, so approvals let users `transferFrom(address(0), …)` and resurrect the sacrificed tokens, minting legendaries for free. The idle-tranches analog lives in `IdleCreditVault`: a successfully claimed instant-withdraw receipt is never cleared from the per-epoch ledger `instantWithdrawsRequestsByEpoch[_user][epoch]`, so if that same epoch later ends in a borrower default, `_claimDefaultedInstantWithdrawRequest` re-reads the stale entry and pays the same receipt a second time — this time out of the isolated `defaultRecoveryReserve` meant for genuinely defaulted claimants.

### Finding Description
Instant withdraw requests record two pieces of state in `requestInstantWithdraw`: the aggregate `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (plus `instantWithdrawClaimsByEpoch`). The per-epoch map exists specifically so that, after `finalizeDefault`, `_claimDefaultedInstantWithdrawRequest` can distinguish receipts of the defaulted epoch from older funded ones [1](#0-0) .

The funded claim path `claimInstantWithdrawRequest` only clears the aggregate: it burns the receipt tokens, sets `instantWithdrawsRequests[_user] = 0`, and pays underlying — but never touches `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` [2](#0-1) . Instant claims are allowed during the epoch (the queue contract documents "Claims can be done during the epoch for instant withdrawals"), so a receipt can be fully consumed in epoch N while its per-epoch ledger entry still says the user is owed N-epoch recovery.

If epoch N subsequently ends in a borrower default and `finalizeDefault` sets `defaultRecoveryEpoch = N` with `defaultInstantWithdrawsFinalized`, the next call to `claimInstantWithdrawRequest` first runs `_claimDefaultedInstantWithdrawRequest`, which reads `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]`, finds the stale nonzero `claimBasis`, and executes `instantWithdrawsRequests[_user] -= claimBasis; instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis; _burn(_user, claimBasis); _transferDefaultRecovery(_user, claimBasis * defaultRecoveryPrice / RECOVERY_FULL)` [3](#0-2) . The consumed receipt has effectively been "revived" — exactly like the resurrected Gobbler.

Two reverts could mask the bug for a passive victim, but a deliberate attacker controls both:

1. `instantWithdrawsRequests[_user] -= claimBasis` underflows if the aggregate is 0. The attacker fixes this by calling `requestInstantWithdraw` again after default finalization (that function has no `defaultRecoveryFinalized` gate — unlike `requestWithdraw`, which does [4](#0-3) ), topping the aggregate up to ≥ `claimBasis`.
2. `_burn(_user, claimBasis)` needs receipt-token balance. The attacker already holds freshly minted receipt tokens from that same post-default `requestInstantWithdraw` (it mints `_amount` to `_user` [5](#0-4) ).

After the defaulted claim pays out, the function continues to `amount = instantWithdrawsRequests[_user]` and pays the legitimately funded remainder too [6](#0-5) . The required underlying comes from `defaultRecoveryReserve`, which `_transferDefaultRecovery` decrements without any check that the claimant's per-epoch receipt was still outstanding [7](#0-6) . No existing guard stops this: the reserve isolation in `_transferFundedClaim` protects the reserve from funded claims, not from defaulted-claim bookkeeping [8](#0-7) .

### Impact Explanation
Broken invariant: one receipt, one payout. An unprivileged tranche holder who claimed an instant withdrawal in the epoch that later defaults can drain `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` from `defaultRecoveryReserve` — up to 100% of their already-paid claim. This directly steals recovery funds earmarked for honest defaulted-epoch claimants; the last claimants' `_transferDefaultRecovery` calls then underflow/revert, permanently freezing the residual reserve. Loss is quantified: `amount_already_claimed × recoveryPrice`, bounded only by the attacker's instant-withdraw size, which is limited by their tranche holdings, not by any protocol cap.

### Likelihood Explanation
Requires: (a) instant withdrawals enabled and a claim executed in epoch N; (b) epoch N ends in borrower default with a nonzero `defaultRecoveryPrice` (i.e., some recovery exists to steal); (c) `defaultInstantWithdrawsFinalized` set. All are normal protocol states reachable by an unprivileged user sequencing around honest manager/owner calls. The post-default top-up step is available because `requestInstantWithdraw` omits the `defaultRecoveryFinalized`/`postDefaultRequests` handling that `requestWithdraw` has — the same asymmetry that makes the exploit chain work also suggests this edge was not fully considered.

### Recommendation
In `claimInstantWithdrawRequest`, when paying the funded aggregate, also clear the per-epoch entries: for each epoch the user's aggregate covers — or at minimum the epoch stored alongside the request — set `instantWithdrawsRequestsByEpoch[_user][epoch] = 0` and decrease `instantWithdrawClaimsByEpoch[epoch]`. Simplest robust fix mirroring the report's first mitigation ("reset ownership in the loop"): track `lastInstantRequestEpoch[_user]` and clear that per-epoch slot in the funded claim path, so a consumed receipt can never be reinterpreted as a defaulted-epoch claim basis. Also consider gating `requestInstantWithdraw` after `defaultRecoveryFinalized` the same way `requestWithdraw` is.

### Proof of Concept
Foundry fork test skeleton (adapted to the existing `test/foundry/IdleCreditVault.t.sol` harness, which already has `_depositWithUser`, `_startEpochAndCheckPrices`, `_stopEpochAndCheckPrices`, and defaulted-pool helpers):

```solidity
function testStaleInstantEpochEntryPaidTwiceFromRecovery() external {
    _useInstantWithdrawVariant(); // enable instant withdraws, delay, minAprDiff
    address user = makeAddr('user');
    uint256 amountWei = 100e6;
    uint256 tranches = _depositWithUser(user, amountWei, true); // AA tranche

    // Epoch N starts; user requests and claims an instant withdraw DURING epoch N
    vm.prank(manager); cdoEpoch.startEpoch();
    vm.prank(user);    cdoEpoch.requestInstantWithdraw(tranches, address(AAtranche));
    // borrower/CDO funds instant liquidity, user claims successfully
    vm.prank(user);    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(strategy.instantWithdrawsRequests(user), 0);
    // BUG: instantWithdrawsRequestsByEpoch[user][N] still holds the basis
    assertGt(strategy.instantWithdrawsRequestsByEpoch(user, N), 0);

    // Epoch N defaults; manager finalizes with partial recovery
    _stopEpochDefaulted();            // defaulted() == true, defaultRecoveryEpoch = N
    _finalizeDefault(recovered);      // sets defaultRecoveryPrice, defaultInstantWithdrawsFinalized

    // Top up aggregate + receipt balance post-default (requestInstantWithdraw has no default gate)
    vm.prank(user); cdoEpoch.requestInstantWithdraw(dust, address(AAtranche)); // dust >= 0, but minted receipt < claimBasis
    // if needed, combine with a postDefault request to hold >= claimBasis receipt tokens

    uint256 balPre = underlying.balanceOf(user);
    vm.prank(user); cdoEpoch.claimInstantWithdrawRequest();
    uint256 stolen = underlying.balanceOf(user) - balPre;

    // stale defaulted-epoch basis paid again out of the recovery reserve
    assertEq(stolen, claimBasis * strategy.defaultRecoveryPrice() / RECOVERY_FULL + dustPayout);
}
```

Caveats I could not fully verify within the available context: the exact IdleCDO-side gating for instant claims mid-epoch in `IdleCDOEpochVariant` (the queue contract documents it is permitted), the precise semantics of `defaultInstantWithdrawsFinalized`, and whether `instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis` can underflow before payout in every ordering (the `pending` clamp at line 849-852 suggests it was anticipated partially). Even if a specific ordering reverts, the uncleared per-epoch ledger means legitimately-claimed receipts pollute default-epoch accounting, which is the defect to fix regardless.

```text
    _burn(_user, amount);

    instantWithdrawsRequests[_user] = 0;
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
