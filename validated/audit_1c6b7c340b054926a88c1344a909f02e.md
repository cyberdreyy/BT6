### Title
Stale confirmations from removed multisig members are still counted toward the confirmation threshold, allowing execution below the effective live-member quorum - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
Both the `multisig` and `multisig2` contracts implement K-of-N confirmation logic where a pending `MultiSigRequest` accumulates `confirmations: HashSet<PublicKey/String>` from signers, and executes once `confirmations.len() + 1 >= num_confirmations`. When a key/member is revoked (`DeleteKey` in `multisig`, `DeleteMember` in `multisig2`), the contract only cleans up requests whose *creator* (`signer_pk`/`member`) matches the removed key/member. It does **not** scrub that removed key's confirmations from *other* pending requests that it merely confirmed (but did not create). Those stale confirmations remain in the `confirmations` set and continue to count toward `num_confirmations` at execution time.

### Finding Description
In `multisig/src/lib.rs`, `execute_request`'s `DeleteKey` branch only removes requests created by the deleted key: [1](#0-0) 
It does not iterate over `self.confirmations` to strip the deleted `pk` from confirmation sets of requests created by *other* signers. The same pattern exists in `multisig2/src/lib.rs`'s `delete_member`: [2](#0-1) 

The `confirm` method simply checks length of the confirmation set against `num_confirmations`, without validating that every entry in the set still corresponds to a **current** member: [3](#0-2) [4](#0-3) 

The binding that should hold is:
`num_confirmations == count of confirmations from currently-live members`

But the actual invariant enforced is:
`num_confirmations == count of confirmations ever recorded, regardless of whether the confirming key/member is still a member`

Because `DeleteKey`/`DeleteMember` only purges requests *authored* by the removed key, a confirmation made by that key on someone else's still-pending request survives the removal. If that pending request later collects enough *additional* live confirmations to reach `num_confirmations` (counting the stale one), it executes — even though fewer live members than the configured threshold ever approved it in its final, current-membership state.

### Impact Explanation
This crosses the "confirmations counted versus live members" custody boundary explicitly named as a critical category: a multisig request can be executed with fewer truly live/authorized approvals than `num_confirmations` requires. Given that `MultiSigRequestAction::Transfer`, `FunctionCall`, `DeployContract`, and `AddKey` actions can move funds or fully compromise the account, this allows a transaction to execute "below threshold" — matching the report's core theme (a party whose authorization should have been revoked can still effectively spend/approve funds) even though the mechanism differs from the external report's centralized-signer scenario. This is analogous because: just as the report's compromised central signer can create/approve orders without the maker's real consent, here a revoked signer's stale approval persists and can be silently combined with a smaller-than-intended set of live signers to authorize fund movement, defeating the K-of-N custody guarantee the contract advertises.

### Likelihood Explanation
Exploitation requires: (1) a signer becomes compromised or is later revoked for cause, (2) that signer had confirmed — but not authored — at least one pending request before revocation, and (3) the remaining live members (or the same compromised member acting through a colluding second key before revocation completes) later push that pending request over threshold. This is a realistic organizational sequence: an org detects a compromised key, revokes it via `DeleteMember`/`DeleteKey`, but the revocation cleanup logic silently leaves a "vote" from the compromised key attached to any request it had confirmed for a different purpose. Any attacker who anticipates being revoked can pre-position confirmations on multiple pending/pre-created requests to retain effective voting power after removal.

### Recommendation
When executing `DeleteKey`/`DeleteMember`, iterate over all entries of `self.confirmations` (not just `self.requests` filtered by author) and remove the deleted key/member's public key or member string from every confirmation set, not only from requests it authored. Additionally, `confirm`/execution threshold checks should validate that every public key/member counted in a confirmation set is still present in the current member set before comparing against `num_confirmations`.

### Proof of Concept
1. Initialize `multisig2` with 3 members `A, B, C` and `num_confirmations = 2`.
2. Legitimate member `B` creates a benign `MultiSigRequest` (request `X`) for some future action.
3. Compromised member `A` calls `confirm(X)` — `confirmations[X] = {A}` (1/2).
4. Organization detects `A` is compromised and submits/executes a `DeleteMember { member: A }` request (via `B`+`C` confirming it, e.g., a separate request `Y`). `delete_member` removes `A` from `self.members` and deletes `A`'s access key, but only purges requests where `r.member == A` — request `X` was authored by `B`, so it is untouched; `confirmations[X]` still contains `A`.
5. Later, member `C` calls `confirm(X)`, unaware `A` was revoked. `confirmations[X].len() + 1 = 2 >= num_confirmations (2)` → request `X` executes, effectively approved by only one currently-live member (`C`) plus a ghost vote from a revoked key `A`, instead of the required 2 live-member confirmations.         assert!(

            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {

        } else {

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
