### Title
Loss-adjusted withdraw receipts claimable at par due to epoch-keying mismatch between `collectWithdrawFunds` and `lastWithdrawRequest` - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks pending withdraw receipts by the epoch in which `requestWithdraw` ran (`lastWithdrawRequest[_user]`, `withdrawsRequestsByEpoch[_user][epoch]`). When `stopEpochWithDuration` realizes a loss and the borrower under-funds pending receipts, `collectWithdrawFunds` stores the haircut under `lossRecoveryPriceByEpoch[epochNumber]` — but `epochNumber` is incremented inside `deposit()` while the epoch is still running, so the haircut is keyed to `N+1` while every receipt taken during the epoch points at `N`. `_claimLossAdjustedWithdrawRequest` therefore never finds the recovery price, and `_claimFundedWithdrawRequest` pays the full un-haircutted basis from an under-funded strategy.

### Finding Description
The external bug (CVE-2015-8812) is a failure to identify an error condition on a packet path, leaving a stale resource reference that is later dereferenced (UAF). The analog here is the partial-funding error path in `collectWithdrawFunds`:

- `requestWithdraw` records receipts under the *current* `epochNumber` (line 282, 293) — the value before the epoch ends.
- In `deposit()` (lines 607-610), when `isEpochRunning()` is true, `epochNumber += 1` executes — this is the deposit performed during `stopEpoch`.
- `collectWithdrawFunds` (lines 411-430) stores `lossRecoveryPriceByEpoch[epochNumber] = lossRecoveryPrice` when `_amount < pendingBasis`. If this call happens after the epoch increment (the normal stopEpoch ordering: repay/deposit first, then collect pending-withdraw funding), the haircut lands under `N+1`.
- `_claimLossAdjustedWithdrawRequest` (lines 789-801) looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e. under `N`, finds `0`, and returns early.
- Control then falls into `_claimFundedWithdrawRequest` (lines 319-350). Its gate `epochNumber <= lastWithdrawRequest[_user]` is `N+1 <= N` → false, so it burns the receipt and calls `_transferFundedClaim(_user, withdrawsRequests[_user])` at par.

The strategy only pulled `_amount < pendingBasis` underlying from the CDO, yet each receipt is paid in full. First claimants drain the funded amount; the strategy is left insolvent for the remainder (`_transferFundedClaim` reverts on insufficient balance), so either early claimants over-receive at the expense of later ones (theft of the shared funded pool) or, symmetrically, the haircut is applied but double-deducted.

### Impact Explanation
Broken invariant: loss waterfall / "one receipt one (haircutted) payout". A realized stop-epoch loss intended to socialize pro rata across pending receipts is instead paid at par until the funded reserve is exhausted. Quantified loss: `pendingBasis - _amount` distributed to early claimers, with equal freezing losses for late claimers whose receipts revert permanently (funds are gone; no top-up path exists for funded claims).

### Likelihood Explanation
Requires an epoch stopped with a loss (`stopEpochWithDuration(_lossAmount)` / under-funded `collectWithdrawFunds`) while pending withdraw receipts exist — a borrower stress event, but attainable by an unprivileged lender purely through timing of `requestWithdraw`/`claimWithdrawRequest` ordering; no privileged misbehavior needed. The only assumption is that `collectWithdrawFunds` is invoked after the epoch increment inside `stopEpoch`, which matches the stated flow ("stopEpoch must source from borrower/strategy for all pending receipts"); I was unable to fully trace `IdleCDOEpochVariant.stopEpoch` ordering within this session, so that call order should be confirmed.

### Recommendation
Key the loss-recovery price by the epoch in which the receipts were created, not the post-increment counter: store `lossRecoveryPriceByEpoch[epochNumber - 1]` (or capture the pre-increment epoch) in `collectWithdrawFunds`, or have the CDO pass the claim epoch explicitly. Alternatively, tag each receipt epoch with its funding status so `_claimFundedWithdrawRequest` cannot pay an epoch that was only partially funded.
