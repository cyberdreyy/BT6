### Title
Flashblocks WebSocket publisher accepts oversized frames with no size limit, enabling per-connection memory-exhaustion DoS - (File: crates/builder/publish/src/listener.rs)

### Summary
The `Listener::run` loop in the flashblocks WebSocket publisher accepts every incoming TCP connection and upgrades it via `accept_hdr_async(connection, ...)` without ever constructing or passing a `WebSocketConfig` that bounds `max_message_size`/`max_frame_size`.

### Finding Description
`Listener::run` accepts connections and performs the WebSocket handshake with the bare `accept_hdr_async` call, only supplying a header callback to parse resume-position query params — no `WebSocketConfig` is built or passed. [1](#0-0) 

Once the handshake completes, the resulting stream is handed to `BroadcastLoop::run`, whose per-connection select loop reads inbound client frames via `self.stream.next()`. It only special-cases `Message::Close` and error variants; any `Message::Text`/`Message::Binary` payload is fully buffered by the underlying `tokio-tungstenite`/`tungstenite` decoder before being silently discarded (`_ => ()`). [2](#0-1) 

This is the same bug class as the OpenClaw advisory: a realtime WebSocket endpoint that upgrades connections and reads client-sent frames without capping frame/message size before allocating a buffer for them. Because no `WebSocketConfig` is supplied here, the library falls back to its built-in defaults (tens of megabytes per message/frame) — there is no explicit, intentional limit on this endpoint at all, unlike the sibling `websocket-proxy` crate in the same repo, which explicitly documents and enforces a 4 KiB cap for exactly this reason: [3](#0-2) 

The publisher's own doc/README frames this exact endpoint as a broadcast path for flashblocks pending-state data consumed by downstream RPC/flashblocks clients, i.e., a live, reachable, unauthenticated query path, and the accept loop spawns one task and one broadcast receiver/ring-buffer clone per accepted TCP connection with no per-connection accounting of inbound buffer size. [4](#0-3) 

### Impact Explanation
Any anonymous client that can reach the flashblocks WebSocket publisher port can open a connection and send large text/binary frames repeatedly. Each frame is fully buffered in memory by the WebSocket decoder before being dropped by `BroadcastLoop`, and nothing in `Listener`/`BroadcastLoop` limits frame size, message size, or the number of concurrent connections. Multiple connections sending large frames concurrently can drive unbounded memory growth in the builder/flashblocks process, leading to OOM and process termination — a denial of service of the flashblocks pending-state distribution path, matching the "node halt" / "RPC the node can no longer serve" impact bar.

### Likelihood Explanation
The endpoint is a raw TCP listener with no authentication gate shown in `Listener`/`BroadcastLoop` (unlike `websocket-proxy`, which requires an API key before upgrade). Any network client that can reach the configured bind address can trigger this with a trivial WebSocket client sending large frames — no special privileges, keys, or preconditions are needed beyond network reachability.

### Recommendation
Construct an explicit `WebSocketConfig` (bounded `max_message_size`/`max_frame_size`, e.g. a few KiB, mirroring the rationale already used in `crates/infra/websocket-proxy/src/server.rs`) and pass it into `accept_hdr_async` in `Listener::run`, since legitimate clients of this endpoint only send small control/resume-query data and never need large inbound payloads.

### Proof of Concept
1. Start the `WebSocketPublisher`/`Listener` (as constructed in `crates/builder/publish/src/publisher.rs::with_capacity`) bound to a reachable address.
2. From an external client, complete the WebSocket handshake (optionally with `?block_number=0&flashblock_index=0`) and send a large `Message::Binary`/`Message::Text` frame close to the library's default max (tens of MB) repeatedly, and/or open many concurrent connections each sending such frames.
3. Observe unbounded memory growth in the builder process as each frame is buffered before being discarded in `BroadcastLoop::run`, eventually leading to OOM/process crash and loss of the flashblocks broadcast service for all legitimate subscribers.
