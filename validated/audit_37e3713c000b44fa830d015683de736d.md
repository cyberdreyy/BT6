### Title
Unauthenticated request-ID squatting in confidential relay handler causes denial-of-service/slot hijack for another user's request - ([File: core/services/gateway/handlers/confidentialrelay/handler.go])

### Summary
`(h *handler).newActiveRequest` registers an `activeRequest` in a single global map keyed only by the raw, caller-supplied `req.ID`, with no per-caller/authorization namespace and no proof that the caller is entitled to that ID. Any unauthenticated client of the gateway's JSON-RPC endpoint can pre-register a victim's predictable/observed `req.ID` before the victim's real request arrives, causing the legitimate call to fail with "request ID already exists".

### Finding Description
`HandleJSONRPCUserMessage` validates only that `req.ID` is non-empty and ≤200 chars, then immediately calls `h.newActiveRequest(req, callback)`: [1](#0-0) 

`newActiveRequest` takes the global handler lock and checks whether `h.activeRequests[req.ID]` already exists; if so it returns an error, otherwise it inserts the new request keyed purely by `req.ID`: [2](#0-1) 

No authentication, ownership check, or per-caller namespacing occurs before this registration. Tracing the call path from the gateway entrypoint `gateway.ProcessRequest`, the raw `jsonRequest.ID` decoded from the HTTP body is passed straight through to `h.HandleJSONRPCUserMessage` with only a length check (≤200 chars) — no verification that the ID belongs to, or was issued for, the calling principal: [3](#0-2) 

This is unlike the sibling `vault` handler, which mitigates exactly this class of collision by scoping the activeRequest key to the authorized owner (`authorizedOwner + vaulttypes.RequestIDSeparator + req.ID`) derived from signature/authorization verification (`h.requestProcessor.ProcessRequest`) *before* calling `newActiveRequest`: [4](#0-3) 

The confidential relay handler has no equivalent authorization-derived namespacing or signature check gating `newActiveRequest`, so `req.ID` is attacker-controlled and globally unique across all callers. An attacker who can predict or observe a victim's upcoming `req.ID` (e.g., a workflow/execution ID reused as the JSON-RPC request ID) can submit a `HandleJSONRPCUserMessage` call with that ID first. This wins the race in `newActiveRequest`, occupying the slot. When the legitimate request with the same ID subsequently arrives, `newActiveRequest` returns `"request ID already exists: <id>"`, and `HandleJSONRPCUserMessage` propagates that error back through `gateway.ProcessRequest` as an `api.HandlerError` response — denying the victim's request. The attacker's fraudulent request is fanned out to DON nodes and its callback awaits (until timeout/cleanup), so no response is misrouted to the attacker (the isolation ensured by `getActiveRequest`/`addResponseForNode` keeps responses tied to the map entry, which belongs to the attacker's own callback), but the victim's own capability execution is effectively blocked/denied for the duration of that request ID's lifetime (up to `requestTimeout`, default 30s, or until the attacker's request completes and is removed via `sendResponseAndClearRequest`).

### Impact Explanation
This is a denial-of-service / request-slot hijack: an unauthenticated attacker can block a specific, targeted capability execution request from succeeding by pre-claiming its ID, without needing any credential, signature, or knowledge beyond the ID value. It matches the "denial of unauthorized job run" / "request impersonation of request handling" class in the scoped impact — the attacker does not read the victim's response contents (isolation for response data is preserved via per-ID `activeRequest.responses`), but they can deny the victim's execution slot deterministically for as long as the ID is predictable/reproducible.

### Likelihood Explanation
Feasibility depends entirely on the attacker's ability to predict or observe the victim's `req.ID` before it is submitted (e.g., if IDs are derived deterministically from workflow ID + execution ID, or are observable via logs/telemetry/network timing). No authentication or role is required to reach `HandleJSONRPCUserMessage` on the gateway's public JSON-RPC endpoint. The race is trivially repeatable (attacker can retry-race whenever they suspect a victim ID is about to be used), and the outcome (collision error) is deterministic given the attacker wins the map-insert race, since `newActiveRequest` holds `h.mu` for its whole check-then-insert.

### Recommendation
Scope `activeRequests` keys by a value derived from verified caller identity (e.g., signature-verified owner/executor address) combined with the caller-supplied `req.ID`, analogous to the vault handler's `owner + Separator + req.ID` pattern, rather than trusting the raw client-supplied ID as a global namespace. Alternatively/additionally, require and verify a signed binding (e.g., signed workflow/execution identity) before `newActiveRequest` is called, so an unauthenticated caller cannot claim an ID they are not authorized to use.

### Proof of Concept
Add a handler-level test in `core/services/gateway/handlers/confidentialrelay/handler_test.go`:
1. Build a `handler` via the existing `setupHandler(t, n)` helper used elsewhere in the file, with a DON mock (`don.On("SendToNode", ...).Return(nil)`).
2. Construct two distinct `jsonrpc.Request[json.RawMessage]` values — an "attacker" request and a "victim" request — both using the identical `req.ID` (e.g., `"victim-exec-id"`), each with its own `Callback` (e.g., two `common.NewCallback()` instances).
3. Launch two goroutines: goroutine A calls `h.HandleJSONRPCUserMessage(ctx, attackerReq, attackerCallback)` first (or use a short sleep/barrier to guarantee ordering representing the attacker "winning the race"); goroutine B calls `h.HandleJSONRPCUserMessage(ctx, victimReq, victimCallback)` slightly after.
4. Assert: `err` from goroutine A's call is `nil` (attacker request accepted), and `err` from goroutine B's call is non-nil and contains `"request ID already exists"`.
5. Assert isolation: `victimCallback.Wait(ctx)` with a short timeout never resolves with a routed node response (it should time out, since the victim's request was never registered) — confirming the victim never receives a response and none of the attacker's callback traffic is misrouted to the victim's callback (i.e., check `attackerCallback` is the only one that eventually receives a `SendResponse` call once DON responses/expiry are processed).
6. This demonstrates the collision-based denial: the victim's legitimate call is rejected outright due to the attacker's earlier registration under the same `req.ID`, without any authentication distinguishing the two callers.

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}

func (h *handler) HandleJSONRPCUserMessage(ctx context.Context, req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) error {
	if req.ID == "" {
		return errors.New("request ID cannot be empty")
	}
	if len(req.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return errors.New("request ID is too long: " + strconv.Itoa(len(req.ID)) + ". max is 200 characters")
	}

	h.lggr.Debugw("handling vault request", "method", req.Method, "requestID", req.ID, "request", req)
	if req.Method == vaulttypes.MethodPublicKeyGet {
		// Public key requests don't require authorization,
		// Let's process this request right away.
		// Note we cache this value quite aggressively so don't need to worry about DoS.
		publicKeyResponseBytes, cachedPublicKey := h.getCachedPublicKey()
		if cachedPublicKey == nil {
			// Not found in cache. Fetch from nodes.
			ar, err := h.newActiveRequest(req, callback)
			if err != nil {
				h.lggr.Errorw("failed to create new activeRequest", "error", err)
				return err
			}
			return h.handlePublicKeyGet(ctx, ar)
		}
		h.lggr.Debugw("returning cached public key response")
		return h.handlePublicKeyGetSynchronously(ctx, req, publicKeyResponseBytes, callback)
	}

	if !vaulttypes.IsGatewaySecretsMethod(req.Method) {
		return h.sendImmediateUserResponse(ctx, req, callback, api.UnsupportedMethodError, errors.New("this method is unsupported: "+req.Method))
	}

	_, cachedPublicKey := h.getCachedPublicKey()
	authorized, err := h.requestProcessor.ProcessRequest(ctx, &req, cachedPublicKey)
	if err != nil {
		if vaultcap.IsInvalidVaultParamsError(err) {
			return h.sendImmediateUserResponse(ctx, req, callback, api.InvalidParamsError, err)
		}
		h.lggr.Errorw("request not authorized", "method", req.Method, "requestID", req.ID, "hasAuth", req.Auth != "", "error", err)
		return errors.New("request not authorized: " + err.Error())
	}
	authorizedOwner := authorized.AuthResult.AuthorizedOwner()

	h.lggr.Debugw("handling authorized vault request", "method", req.Method, "requestID", req.ID, "authorizedOwner", authorizedOwner)
	ar, activeRequestErr := h.newActiveRequest(req, callback)
	if activeRequestErr != nil {
		return activeRequestErr
	}
