## Title
WebAuthn MFA key enrollment is not confirmed by password re-authentication - (File: `core/web/webauthn_controller.go`)

### Summary
The external report flags that `LongShort.sol` lets an unconfirmed address take over the `admin`/`treasury` role with a single unilateral call — there is no two-step "propose then confirm" pattern, so a stolen or mistaken address can permanently seize a security-critical role. The closest reachable analog in this Chainlink node is the WebAuthn (MFA) key enrollment flow: an authenticated session can permanently register a brand-new hardware/security key as a valid second factor for the account **without re-confirming the user's current password**, unlike every other sensitive credential-changing endpoint in the same package.

### Finding Description
`WebAuthnController.BeginRegistration` and `FinishRegistration` only require that the request pass through the general `authv2` authentication middleware (session cookie or API token), then immediately persist the new credential: [1](#0-0) [2](#0-1) 

Both endpoints are wired up under the standard authenticated group with no additional re-authentication step: [3](#0-2) 

Contrast this with every other credential-mutating endpoint in `UserController`, which all require the caller to re-prove possession of the current password (`TestPassword`/`CheckPasswordHash`) before making the change:
- `UpdatePassword` checks `request.OldPassword` against the stored hash before rotating the password: [4](#0-3) 
- `NewAPIToken` requires `TestPassword` before minting a new API token: [5](#0-4) 
- `DeleteAPIToken` requires `TestPassword` before revoking the token: [6](#0-5) 

The WebAuthn enrollment path breaks this consistent pattern: `FinishRegistration` calls `sessions.AddCredentialToUser`, which does a bare `INSERT` with no password confirmation and no revocation of prior state: [7](#0-6) [8](#0-7) 

Just like the `admin`/`treasury` setters in the referenced report take effect with a single call and no confirmation step from a second, independent factor, enrolling a new MFA credential here takes effect immediately from a single authenticated request, with no "confirm with current password" gate that every other identity-mutating action in the same controller enforces.

### Impact Explanation
Enrolling a WebAuthn credential is a security role change: once registered, that hardware key becomes a permanently trusted second factor for that user's account. If a session cookie or API token is transiently compromised (e.g. XSS in the Operator UI, a leaked/replayed token, or an insufficiently scoped CSRF-vulnerable browser session), an attacker can silently add their own persistent authentication key. This grants the attacker durable access to the account that survives password rotation, mirroring the impact described in the report where "inputting the wrong address...could lock out a lot of the funds and smart contract methods" — here, the equivalent is durable unauthorized account control being granted without any confirmation of the legitimate holder's current secret.

### Likelihood Explanation
Exploitation requires the attacker to already have an authenticated session or token (e.g., through XSS, session fixation, or a leaked token) — it is not exploitable from a fully unauthenticated request. However, given that the sibling endpoints (`/user/password`, `/user/token`, `/user/token/delete`) all defensively require password re-entry specifically to defend against this scenario (a hijacked but not-fully-compromised session), the omission on `/enroll_webauthn` and `/enroll_webauthn` (POST) represents an inconsistent, weaker security posture for a comparably sensitive action.

### Recommendation
Require re-authentication (e.g., current password, or `TestPassword`) as part of `BeginRegistration`/`FinishRegistration`, consistent with `NewAPIToken` and `DeleteAPIToken`. Additionally, consider notifying the account owner (e.g., via audit log alert or email) whenever a new MFA credential is enrolled, and support a "pending confirmation" step (e.g., confirm via an existing already-enrolled second factor or a time-delayed activation) before the new credential becomes active for login, analogous to the `pendingAdmin`/`pendingTreasury` two-step pattern recommended in the report.

### Proof of Concept
1. Attacker obtains a valid session cookie or API token for a victim account (e.g., via XSS, session leakage, or SSRF/log exposure of tokens).
2. Attacker calls `GET /v2/enroll_webauthn` using the hijacked credentials to receive registration challenge options (`WebAuthnController.BeginRegistration`).
3. Attacker completes the WebAuthn ceremony with their own hardware key and calls `POST /v2/enroll_webauthn` (`WebAuthnController.FinishRegistration`), which persists the credential via `sessions.AddCredentialToUser` with no password confirmation.
4. The attacker's key is now a permanently trusted MFA factor on the victim's account, and the flow does not surface any re-confirmation step to the legitimate account holder before taking effect — attacker now holds persistent second-factor access even if the original session/token is later revoked.

func (w *WebAuthnController) BeginRegistration(c *gin.Context) {
	ctx := c.Request.Context()
	user, ok := auth.GetAuthenticatedUser(c)
	if !ok {
		jsonAPIError(c, http.StatusInternalServerError, errors.New("failed to obtain current user from context"))
		return
	}

	orm := w.App.AuthenticationProvider()
	uwas, err := orm.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		w.App.GetLogger().Errorf("failed to obtain current user MFA tokens: error in GetUserWebAuthn: %+v", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	webAuthnConfig := w.App.GetWebAuthnConfiguration()

	options, err := w.inProgressRegistrationsStore.BeginWebAuthnRegistration(*user, uwas, webAuthnConfig)
	if err != nil {
		w.App.GetLogger().Errorf("error in BeginWebAuthnRegistration: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	optionsp := presenters.NewRegistrationSettings(*options)

	jsonAPIResponse(c, optionsp, "settings")
}

func (w *WebAuthnController) FinishRegistration(c *gin.Context) {
	ctx := c.Request.Context()
	user, ok := auth.GetAuthenticatedUser(c)
	if !ok {
		logger.Sugared(w.App.GetLogger()).AssumptionViolationf("failed to obtain current user from context")
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	orm := w.App.AuthenticationProvider()
	uwas, err := orm.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		w.App.GetLogger().Errorf("failed to obtain current user MFA tokens: error in GetUserWebAuthn: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	webAuthnConfig := w.App.GetWebAuthnConfiguration()

	credential, err := w.inProgressRegistrationsStore.FinishWebAuthnRegistration(*user, uwas, c.Request, webAuthnConfig)
	if err != nil {
		w.App.GetLogger().Errorf("error in FinishWebAuthnRegistration: %s", err)
		jsonAPIError(c, http.StatusBadRequest, errors.New("registration was unsuccessful"))
		return
	}

	if sessions.AddCredentialToUser(ctx, w.App.AuthenticationProvider(), user.Email, credential) != nil {
		w.App.GetLogger().Errorf("Could not save WebAuthn credential to DB for user: %s", user.Email)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

func AddCredentialToUser(ctx context.Context, ap AuthenticationProvider, email string, credential *webauthn.Credential) error {
	credj, err := json.Marshal(credential)
	if err != nil {
		return err
	}

	token := WebAuthn{
		Email:         email,
		PublicKeyData: sqlxTypes.JSONText(credj),
	}
	return ap.SaveWebAuthn(ctx, &token)
}

func (o *orm) SaveWebAuthn(ctx context.Context, token *sessions.WebAuthn) error {
	sql := "INSERT INTO web_authns (email, public_key_data) VALUES ($1, $2)"
	_, err := o.ds.ExecContext(ctx, sql, token.Email, token.PublicKeyData)
	return err
}
