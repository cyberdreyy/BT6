### Title
LPs can dodge `stopEpochWithDuration` pro-rata loss by front-running the stop with funded instant withdrawals - ([File: contracts/IdleCDOEpochVariant.sol](contracts/IdleCDOEpochVariant.sol))

### Summary
`stopEpochWithDuration(_lossAmount)` realizes a loss that is split pro rata between pending withdraw receipts (`lossRecoveryPriceByEpoch`) and the active basis (BB-first waterfall via `burnStrategyTokens`). Instant-withdraw liquidity that was already funded into `IdleCreditVault` is excluded from both bases, so a tranche holder can observe the loss-bearing `stopEpochWithDuration` transaction in the mempool, instantly exit at par through `requestInstantWithdraw` + `claimInstantWithdrawRequest`, and let the remaining holders absorb the escaped share of the loss. This is the same bug class as the external report: escaping a pro-rated loss by exiting around a known loss event.

### Finding Description
When `IdleCDOEpochVariant._stopEpoch` runs with `_lossAmount > 0`, it calls `IdleCreditVault.previewLossAdjustedWithdrawFunds`, which computes `totalBasis = activeBasis + pendingBasis` — where `pendingBasis` is `pendingWithdraws` (normal receipts) and `activeBasis` derives from `getContractValue()` / `balanceOf(idleCDO) + expectedEpochInterest` (`IdleCreditVault.sol:440-484`). `pendingInstantWithdraws` and the underlyings already parked in the vault via `collectInstantWithdrawFunds` (`IdleCreditVault.sol:398-403`) participate in neither side.

The only gate on stopping is `_pendingInstant() != 0` reverting the stop (`IdleCDOEpochVariant.sol:345`), which forces the manager to call `getInstantWithdrawFunds()` first — i.e., fund instant requests at par from the borrower before the loss is applied (`IdleCDOEpochVariant.sol:558-574`). Once `allowInstantWithdraw` is true (set at `startEpoch` when surplus exists, or after `getInstantWithdrawFunds`), a holder can:

1. See the manager's `getInstantWithdrawFunds`/`stopEpochWithDuration(_, _, _, loss)` transactions in the mempool (or simply observe `block.timestamp > epochEndDate` and pending instant liquidity in the vault).
2. Front-run with `requestInstantWithdraw` and `claimInstantWithdrawRequest`, burning their strategy tokens and pulling funded underlyings at 1:1 (`IdleCreditVault.sol:356-392`).
3. When `stopEpochWithDuration` executes, `_lossAmount` is burned against a smaller active basis plus normal receipts — the attacker's escaped share is redistributed onto remaining AA/BB holders and pending receipts.

The analogous `requestWithdraw` path is already mitigated: pending receipts share the loss pro rata (`lossRecoveryPriceByEpoch`, `IdleCreditVault.sol:417-421`, `457-459`). The instant path has no equivalent haircut — claims are paid at par from the funded reserve (`IdleCreditVault.sol:387-392`).

### Impact Explanation
Remaining tranche holders and pending receipt holders absorb a larger effective loss than the intended pro-rata split. Quantified: if funded instant liquidity `I` exits at par before a loss `L` is applied to `active + pending` basis, each remaining unit takes `L/(active+pending)` instead of `L/(active+pending+I)`. For a pool with meaningful instant liquidity this can move the realized loss per unit by double-digit percent, a direct redistribution of loss from the exiting user to honest LPs.

### Likelihood Explanation
Requires (a) instant withdrawals enabled and funded (a normal supported mode, gated by `instantWithdrawDeadline` and `allowInstantWithdraw`), and (b) a mempool-visible or predictable loss-bearing `stopEpochWithDuration`/`getInstantWithdrawFunds` call — both manager-called and therefore public-mempool transactions. Cost to the attacker is gas plus the instant-withdraw APR delta, below the avoided loss share. An unprivileged tranche holder suffices; no privileged role needed.

### Recommendation
Include funded but unclaimed instant receipts in the loss basis (extend `previewLossAdjustedWithdrawFunds` / `_lossActiveBasis` to cover `pendingInstantWithdraws` and store a per-epoch instant recovery price), or block instant claims between `epochEndDate` and the next `startEpoch` so loss realization cannot be front-run. Alternatively apply the same `lossRecoveryPriceByEpoch` haircut to instant receipts funded in the loss epoch.

### Proof of Concept
Reproducible as a Foundry fork test (structure; exact helper names per `test/foundry/IdleCDOEpochVariant*.t.sol`):

```solidity
// Setup: pool with borrower funded, AA + BB deposits, epoch started with
// surplus underlyings so allowInstantWithdraw == true and instant liquidity
// is already in IdleCreditVault (collectInstantWithdrawFunds at startEpoch).

// 1. Attacker (unprivileged AA holder) sees manager's
//    stopEpochWithDuration(newApr, interest, duration, lossAmount) pending
//    (or epochEndDate passed) and front-runs:
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackerStrategyTokens); // burns, mints receipt
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest(attacker);          // paid 1:1 from vault

// 2. Manager executes the loss-bearing stop:
deal(address(underlying), borrower, interest + pendingToFund);
vm.prank(borrower); underlying.approve(address(cdoEpoch), type(uint256).max);
vm.prank(manager);
cdoEpoch.stopEpochWithDuration(newApr, interest, duration, lossAmount);

// 3. Assert: attacker received full par value; remaining AA/BB virtualPrice
//    dropped by more than lossAmount/(totalBasis) — i.e., they absorbed the
//    attacker's escaped share:
assertGt(priceDropPerUnit, expectedProRataDrop);
```

Note: I verified the loss-splitting math (`previewLossAdjustedWithdrawFunds`, `_lossActiveBasis`, `collectWithdrawFunds`, `burnStrategyTokens`) and the instant-funding/claim flow, but the index did not expose the CDO-side `requestInstantWithdraw`/`claimInstantWithdrawRequest` guard bodies, so the PoC assumes instant claims are permissionless once `allowInstantWithdraw` is set — consistent with `disableInstantWithdraw`/`allowInstantWithdraw` flag usage throughout. If a hidden guard blocks user-initiated instant claims in this state, the finding should be downgraded.
