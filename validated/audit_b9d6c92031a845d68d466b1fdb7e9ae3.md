### Title
Front-runnable multisig name squatting with no deposit floor lets an attacker deploy attacker-controlled members at a trusted sub-account name - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds the sub-account id purely from the caller-supplied `name` and deploys `multisig2.wasm` with a fully caller-supplied `members` / `num_confirmations` payload, with no ownership check, no name reservation, and no minimum-deposit assertion (unlike `staking-pool-factory::create_staking_pool`, which enforces `MIN_ATTACHED_BALANCE`). Anyone who calls `create("myDAO", [attacker_key], 1)` before the intended team does will permanently own `myDAO.<factory>`, since NEAR account names are unique and first-come-first-served.

### Finding Description
The invariant the protocol relies on is: `members(<name>.<factory>) == members_chosen_by_the_intended_owner_of("<name>")`. `MultisigFactory::create` breaks this binding because the sub-account address is derived only from `name` (attacker supplied) and the contract never checks who is entitled to that name: [1](#0-0) 

There is no `assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, ...)` guard as exists in the sibling factory: [2](#0-1) 

and no registry/uniqueness bookkeeping (`staking_pool_account_ids.insert(...)`) or rollback callback either — `MultisigFactory` has no persisted state at all: [3](#0-2) 

Exploit flow: an attacker who learns (or guesses) that a team plans to deploy a multisig at `myDAO.multisig-factory.near` calls `create(name="myDAO", members=[AccessKey{attacker_pubkey}], num_confirmations=1)` with 0 (or minimal) attached deposit before the real team's transaction lands. Because NEAR sub-account creation is atomic and first-come-first-served, the attacker's transaction, once included, permanently owns `myDAO.multisig-factory.near` with themselves as the sole confirming member. Any later legitimate `create` call for the same `name` fails at the protocol level (`CreateAccount` action fails because the account already exists), so the real owners cannot ever get that name back. Users/integrations that trust "the multisig at `myDAO.<factory>`" based on the human-readable name will now be interacting with an attacker-controlled multisig and can be induced to route deposits/approvals into it.

No existing guard prevents this: there is no `assert_owner`, no allowlist of `name -> intended member set`, no `assert_one_yocto`, and no minimum deposit check on this path.

### Impact Explanation
This matches the "an account whitelisted or a lockup deployed with parameters its rightful creator never chose" Critical category, generalized to multisigs: funds/approvals a protocol or set of users route to `myDAO.<factory>` in the belief that it is controlled by the intended team are instead controlled by the attacker's chosen key(s), with `num_confirmations` the attacker also controls (e.g., `1`, allowing unilateral withdrawal of anything sent there). The blast radius is any name that hasn't yet been claimed and that an attacker can predict or front-run; it is repeatable across every unclaimed name and requires no privileged role.

### Likelihood Explanation
The attack requires only an unprivileged NEAR account, a small amount of gas, and (practically, due to storage staking requirements for deploying `multisig2.wasm`) enough NEAR to cover the contract's storage cost — this is a much lower bar than any deposit the legitimate team might have intended to fund the multisig with, and the code itself enforces no floor. The main precondition is that the attacker learn/predict the intended `name` before the legitimate creation transaction is processed, which is a standard front-running/name-squatting scenario on a public, permissionless account-creation entrypoint.

### Recommendation
Do not rely on the human-chosen `name` as an authorization mechanism. At minimum: (1) add a `MIN_ATTACHED_BALANCE` assertion mirroring `staking-pool-factory`/`lockup-factory` so squatting an unfunded multisig is not free; (2) require the caller to be one of the `members` being registered (or otherwise prove ownership/intent) before allowing sub-account creation; (3) consider deriving the sub-account name deterministically from a canonical identifier of the intended owner (as `lockup-factory` does) rather than an arbitrary attacker-chosen string, so squatting an arbitrary name provides the attacker no leverage over a specific victim's expected address.

use near_sdk::{testing_env, MockedBlockchain, VMContext};
use near_sdk::json_types::Base58PublicKey;

fn ctx(predecessor: &str, deposit: u128) -> VMContext {
    VMContextBuilder::new()
        .current_account_id("multisig-factory".to_string())
        .predecessor_account_id(predecessor.to_string())
        .attached_deposit(deposit)
        .prepaid_gas(10u64.pow(15))
        .finish()

#[test]
fn test_name_squatting_no_deposit_required() {
    // Binding under test: members(myDAO.multisig-factory) == members chosen by the
    // intended owner ("legit-team"), for ANY name not yet created.

    // Attacker calls create() first, with 0 attached deposit and attacker's own key,
    // for a name the real team intends to use.
    testing_env!(ctx("attacker.near", 0));
    let mut factory = MultisigFactory::default();
    let attacker_key = Base58PublicKey::try_from("ed25519:8h1...attacker".to_string()).unwrap();
    let promise = factory.create(
        "myDAO".to_string(),
        vec![MultisigMember::AccessKey { public_key: attacker_key.clone() }],
        1, // num_confirmations attacker controls
    );
    // Assert: no panic occurs despite attached_deposit == 0 -> no MIN_ATTACHED_BALANCE guard exists.
    // (Compare to staking_pool_factory::create_staking_pool which panics with
    // "Not enough attached deposit to complete staking pool creation" under the same conditions.)

    // The legit team's later attempt to create the SAME name will fail at the NEAR
    // runtime level (CreateAccount action fails, account already exists) - this cannot
    // be exercised in a pure unit test (requires near-workspaces / RuntimeStandalone to
    // observe cross-account effects), but the unit test above already demonstrates the
    // missing binding: the contract itself places no restriction correlating `name` with
    // any legitimate owner or minimum funding, in contrast to the sibling factory.
}
