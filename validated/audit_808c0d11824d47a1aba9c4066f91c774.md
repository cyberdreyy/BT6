### Title
`StakingRewards.updateReward` advances `lastUpdateTime` even when `rewardPerToken` delta rounds to zero, permanently burning accrued rewards — ([File: contracts/StakingRewards.sol](contracts/StakingRewards.sol))

### Summary
`StakingRewards` uses the classic Synthetix `rewardPerTokenStored` / `lastUpdateTime` accumulator. The `updateReward` modifier unconditionally stores `lastUpdateTime = lastTimeRewardApplicable()` on every call, even when the integer division `(elapsed * rewardRate * 1e18) / _totalSupply` truncates to zero. An unprivileged attacker can grief `getReward()` (or dust `stake`/`withdraw`) every block so that each call consumes the elapsed time without increasing `rewardPerTokenStored`, permanently destroying the rewards accrued in each interval — the exact analog of the LoopFi `lastBalance`-advances-without-index bug.

### Finding Description
`rewardPerToken()` computes the delta as a floor division:

```solidity
return rewardPerTokenStored + ((lastTimeRewardApplicable() - lastUpdateTime) * rewardRate * 1e18 / _totalSupply);
``` [1](#0-0) 

The modifier then commits both values:

```solidity
rewardPerTokenStored = rewardPerToken();
lastUpdateTime = lastTimeRewardApplicable();
``` [2](#0-1) 

When `elapsed * rewardRate * 1e18 < _totalSupply`, the added term is 0, yet `lastUpdateTime` still jumps forward — the reward for that window is erased from history and can never be distributed (contrast with the LoopFi fix: advance the "lastBalance" analogue only by `delta * totalSupply`, i.e. only consume time proportional to the index actually advanced). `getReward()` is permissionless and carries no whitelist check (unlike `DelegateStakingRewardsIDLE`, which gates it via `_checkWhiteList`): [3](#0-2) [4](#0-3) 

Truncation also shaves up to `_totalSupply / 1e18` wei of reward per update even when the delta is nonzero, an accumulating loss matching the report's secondary point.

### Impact Explanation
Theft / permanent freezing of unclaimed yield: reward tokens streamed to tranche-token stakers (this contract is what `IdleCDO` calls via `depositReward`/`stakeFor` to distribute incentives to tranche holders) are silently burned from the accounting — they sit in the contract unclaimable by any staker and are only recoverable by the honest owner through `recoverERC20`, meaning users permanently lose that yield. With a large `_totalSupply` (e.g. a tranche with ~10^24+ supply) and a modest `rewardRate`, each poked call can destroy up to just under `_totalSupply / 1e18` tokens of accrued reward, repeatable every block. [5](#0-4) [6](#0-5) 

### Likelihood Explanation
`getReward()`, `stake()` and `withdraw()` are all callable by any EOA with zero cost beyond gas (cheap on L2 deployments). The condition `elapsed * rewardRate * 1e18 < _totalSupply` is satisfied whenever total staked tranche tokens are large relative to the per-second reward rate — precisely the normal operating regime once a rewards program is funded via `depositReward` and many users are staked. Even without an attacker, ordinary user activity produces the same cumulative truncation loss.

### Recommendation
Advance `lastUpdateTime` only by the amount of time actually "paid for": compute `delta = rewardPerToken() - rewardPerTokenStored`; if `delta == 0`, do not update `lastUpdateTime`. More precisely, set `lastUpdateTime += delta * _totalSupply / (rewardRate * 1e18)` (or store the un-consumed remainder) so that stored index and consumed time advance at the same pace, eliminating both the griefing vector and the systematic rounding loss.

### Proof of Concept
Foundry fork scenario (against a deployed `StakingRewards` instance or a local deployment with `shouldTransfer = false`):

```solidity
// contracts/StakingRewards.sol
function test_rewardBurnedByRounding() public {
    // setup: honest staker deposits large stake
    deal(address(stakingToken), alice, 1_000_000e18);
    vm.prank(alice);
    stakingRewards.stake(1_000_000e18);          // _totalSupply large

    // owner/rewardsDistribution funds a modest reward rate
    uint256 reward = 100e18;
    deal(address(rewardsToken), distributor, reward);
    vm.prank(distributor);
    stakingRewards.depositReward(address(0), reward); // rewardRate = reward / 1 days

    // attacker pokes getReward() every second so that
    // elapsed * rewardRate * 1e18 / _totalSupply == 0 each call
    for (uint256 i; i < 86_400; ++i) {
        vm.warp(block.timestamp + 1);
        vm.prank(attacker);                      // any EOA
        stakingRewards.getReward();
    }

    // the whole period elapsed, lastUpdateTime == periodFinish,
    // but rewardPerTokenStored never moved -> alice earned 0
    assertEq(stakingRewards.earned(alice), 0);
    assertEq(rewardsToken.balanceOf(address(stakingRewards)), reward); // stuck
}
```

Each iteration: `lastTimeRewardApplicable() - lastUpdateTime = 1`, `1 * rewardRate * 1e18 / _totalSupply` truncates to 0 while `lastUpdateTime` advances — by `periodFinish`, the entire `reward` is unaccounted and unclaimable, demonstrating permanent loss of stakers' yield.
