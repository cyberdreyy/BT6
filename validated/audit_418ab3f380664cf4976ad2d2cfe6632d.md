### Title
Non-atomic check-then-act in `jwtReplayCache` allows JWT replay under concurrent requests, enabling double authorization/execution of a single signed request - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` calls `jwtCache.isReplay(claims.ID)` and `jwtCache.recordUsage(claims.ID)` as two separate, independently-locked operations with unrelated authorized-key lookup logic in between, rather than performing an atomic check-and-set. Two concurrent `Authorize` calls carrying the identical signed JWT (same `jti`/digest) can both observe `isReplay == false` before either calls `recordUsage`, so both are authorized even though the JWT and its bound request digest are meant to be single-use.

### Finding Description
`Authorize` in [1](#0-0)  performs, in order: JWT signature/digest verification, `h.jwtCache.isReplay(claims.ID)`, an authorized-keys map lookup, and finally `h.jwtCache.recordUsage(claims.ID)`.

The cache implementation itself, `jwtReplayCache`, uses separate lock acquisitions for the read (`isReplay`, `RLock`) and write (`recordUsage`, `Lock`) paths: [2](#0-1) . There is no single critical section that both checks and records usage atomically (unlike, e.g., `RequestReplayGuard.CheckAndRecord` used elsewhere in the vault package, which correctly checks-and-inserts under one lock: [3](#0-2) ).

Because `isReplay` and `recordUsage` are decoupled by intervening logic (map lookups, no lock held across the gap), two goroutines that call `Authorize` concurrently with the exact same previously-observed signed JWT will both pass `isReplay` (both see "not yet used"), both pass the authorized-key check, and both then call `recordUsage`, redundantly writing the same `jti`. Both calls return a valid `*gateway.AuthorizedKey`, and the caller (`httpTriggerHandler.authorizeRequest`, [4](#0-3) ) proceeds to trigger workflow execution for both. The per-request digest binding enforced by `VerifyRequestJWT` ( [5](#0-4) ) does not help here because both concurrent requests carry the identical, unmodified digest/token — the race is purely in the cache's check-then-act sequence, not in digest validation.

### Impact Explanation
An attacker who can send two copies of the same valid signed gateway request concurrently (e.g., a workflow-side actor or anyone capable of resending previously observed gateway traffic bearing a valid signature) can cause a single signed authorization to be accepted twice, resulting in the DON executing the same workflow trigger request twice. This maps to unintended duplicate job/workflow execution — DON compute resources are consumed twice for a single authorized/billed action, and depending on the workflow logic, one signed intent could trigger duplicate on-chain or off-chain side effects.

### Likelihood Explanation
Exploitation requires only possession of one valid signed JWT for a workflow-execute request (no special privilege beyond the ability to send gateway requests, matching the specified unprivileged threat model) and firing it via two near-simultaneous requests. The race window is small but real and deterministically reproducible in a unit test that issues both `Authorize` calls from separate goroutines without synchronization; in a live gateway serving concurrent HTTP requests, achieving temporal overlap between the `isReplay` read and the pending `recordUsage` write is feasible.

### Recommendation
Make the JWT replay check-and-record atomic: add a single method (e.g., `checkAndRecord(jti string) bool`) on `jwtReplayCache` that holds one exclusive lock for the entire check-then-insert sequence and returns whether the `jti` was newly recorded, then have `Authorize` reject the request if that method reports the `jti` was already present — mirroring the pattern already used correctly in `vault.RequestReplayGuard.CheckAndRecord`.

### Proof of Concept
Go concurrency test in `core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler_test.go`:
1. Build a `WorkflowMetadataHandler` with one authorized signer (as in `TestWorkflowMetadataHandler_Authorize`).
2. Create a single signed JWT/`jsonrpc.Request` pair via `utils.CreateRequestJWT` + `SignedString`.
3. Launch two goroutines that both call `handler.Authorize(workflowID, tokenString, req)` simultaneously (e.g., synchronized with a `sync.WaitGroup` and a start barrier/channel to maximize overlap).
4. Collect both `(key, err)` results.
5. Assert that exactly one call succeeds (`err == nil`, non-nil key) and the other fails with "JWT token has already been used" — running the test with `-race` and repeating in a loop (or increasing goroutine count as in `TestRequestReplayGuard_ConcurrentAccess`) to demonstrate that, as currently implemented, both calls can succeed, violating the expected one-time-use invariant.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}
```

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```

func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}

func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)
	key, err := h.workflowMetadataHandler.Authorize(workflowID, req.Auth, req)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInvalidRequest, "Auth failure: "+err.Error(), callback)
		return nil, errors.Join(errors.New("auth failure"), err)
	}
	return key, nil
}
