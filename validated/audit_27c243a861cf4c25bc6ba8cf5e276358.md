### Title
Group-level withdrawal/borrow rate limits can be bypassed via repeated withdrawals during the off-chain settlement lag — ([File: programs/marginfi/src/utils/general.rs])

### Summary
The group-level USD rate limiter in marginfi is checked **read-only** during `lending_account_withdraw`/`lending_account_borrow` (and the Kamino/Drift/Solend/JupLend withdraw analogs), and is only actually decremented later by a trusted `delegate_flow_admin` off-chain worker via `update_group_rate_limiter`, batched at up to ~1,500-slot (~10 minute) intervals. Because the on-chain instruction never mutates `group.rate_limiter` for outflows, this mirrors the M-6 pattern: an accounting system (CircuitBreaker high-water-mark / marginfi group rate limiter) that only updates on a lagging/aggregated schedule, letting a user extract far more value in the interim than the configured cap allows, because the cap check has no memory of outflows that already happened in the same window.

### Finding Description
For a withdraw/borrow, `record_withdrawal_outflow` in [1](#0-0)  immediately mutates the **bank-level** rate limiter (`bank.rate_limiter.try_record_outflow`), but for the **group-level** limiter it only performs a read-only check against `group.rate_limiter.hourly/daily.effective_remaining_capacity(...)` and emits a `RateLimitFlowEvent` — it never calls `try_record_outflow` on `group.rate_limiter`: [2](#0-1) 

The actual decrement of `group.rate_limiter` only happens later, when `delegate_flow_admin` submits an aggregated batch through `update_group_rate_limiter`: [3](#0-2) 

This is explicitly documented as intentional design ("Group-level rate limiting is checked read-only during user actions, then settled later from aggregated events") to avoid making the group account `mut` on every user transaction: [4](#0-3) , with settlement batches allowed to lag up to `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` (1,500 slots, ~10 min): [5](#0-4) .

This is the same root-cause shape as the M-6 report: a "capacity" limiter is only checked against a **stale/cached** total that isn't updated atomically with the flow that consumes it, so concurrent/rapid consumption within the settlement window is invisible to the check. In M-6 the staleness came from base-token deposits not counted until swapped/deposited to the vault at hedge time; here the staleness comes from the deliberate deferral of the group rate-limiter mutation to an off-chain aggregator. In both cases, "as long as the observed outflow between sync intervals doesn't (individually) exceed the threshold, withdrawals are allowed" even though the cumulative effect across many transactions within that window can massively exceed the configured cap.

Any account holder (no privilege required) who can issue multiple withdraw/borrow instructions across one or many banks before the flow admin catches up can each pass the `effective_remaining_capacity` check independently, since none of them decrement that shared state. The `RateLimitFlowEvent` log is explicitly non-authoritative ("an indexing aid, not a source of truth... Solana log truncation can drop events" per the guide), so there is no guarantee the aggregator can even fully reconstruct what actually happened, and no way to retroactively block already-executed withdrawals.

### Impact Explanation
The group hourly/daily USD rate limit is a protocol-level defense meant to cap total drainable value from a group during a time window (analogous to the withdrawal-cap/circuit-breaker purpose in the source report). Because the check never decrements the shared counter it reads, an attacker (or a set of colluding accounts) can withdraw/borrow an amount far in excess of the configured cap — bounded only by their actual collateral and per-bank rate limits — by issuing multiple transactions inside a single settlement window. In the worst case (multiple banks, admin briefly delayed or unresponsive), this fully defeats the stated purpose of the group rate limiter, the same "TVL bypass" impact class described in M-6, though bounded by real collateral (unlike M-6's unbacked-inflation angle) rather than by unlimited artificial value creation.

### Likelihood Explanation
Medium-to-High. No special privilege, oracle manipulation, or exotic setup is required — only ordinary permissionless withdraw/borrow instructions repeated within the ~10-minute (or longer, if the off-chain worker lags/is unavailable) settlement window. The bank-level limiter provides only a per-bank ceiling, not a cross-bank/group ceiling, so an attacker spreading withdrawals across multiple banks (or waiting for bank-level windows to roll over) can multiply the effective bypass.

### Recommendation
Either (a) make the group rate-limiter check itself atomic/pessimistic by reserving/decrementing an in-memory or on-chain "committed" counter synchronously with each withdraw/borrow (accepting the account-mut serialization cost, at least for group-limited banks), or (b) bound worst-case exposure during the settlement lag by capping per-transaction/per-window outflow more conservatively (e.g., track a short, tightly-bounded on-chain "pending outflow since last settlement" counter that is checked and incremented in the same instruction, separate from the slower USD-precise off-chain reconciliation), or (c) drastically shrink `MAX_RATE_LIMIT_UPDATE_LAG_SLOTS` and add a hard per-transaction/per-account cap so no single window can be exploited to withdraw a multiple of the configured limit.

### Proof of Concept
1. Admin configures `configure_group_rate_limits` with a daily cap of, say, $1,000,000 for the group.
2. Attacker (or several colluding users) with sufficient real collateral distributed across N different banks in the group each withdraw/borrow $900,000 worth of assets (within each bank's own limiter and within the group's `effective_remaining_capacity`, since that check is stateless read-only per call — see `record_withdrawal_outflow`, [6](#0-5) ).
3. Because `group.rate_limiter` is never mutated inside `record_withdrawal_outflow`, each of the N withdrawals independently observes the same (undiminished) `effective_remaining_capacity` and passes.
4. Before `delegate_flow_admin` calls `update_group_rate_limiter` (which can lag up to 1,500 slots, and depends on off-chain event aggregation that can also miss truncated logs), the group has already had N × $900,000 withdrawn — far exceeding the configured $1,000,000 daily cap.
5. When the admin's aggregated update finally lands, it can only record what already happened; it cannot claw back withdrawals or prevent the already-completed bypass.

pub fn record_withdrawal_outflow(
    group_rate_limit_enabled: bool,
    native_amount: u64,
    balance_amount: u64,
    price: I80F48,
    bank: &mut Bank,
    group: &MarginfiGroup,
    group_key: Pubkey,
    bank_key: Pubkey,
    marginfi_account: &MarginfiAccount,
    clock: &Clock,
) -> MarginfiResult<()> {
    // Rate limiting tracks net outflow; skip for flashloan/liquidation/deleverage flows.
    if !should_skip_rate_limit(marginfi_account.account_flags) {
        if bank.rate_limiter.is_enabled() {
            bank.rate_limiter
                .try_record_outflow(native_amount, clock.unix_timestamp)?;
        }

        // Group-level rate limiting: read-only validation + event emission.
        // The admin aggregates events off-chain and calls update_group_rate_limiter.
        if group_rate_limit_enabled {
            check!(price > I80F48::ZERO, MarginfiError::InvalidRateLimitPrice);

            let value = calc_value(
                I80F48::from_num(balance_amount),
                price,
                bank.get_balance_decimals(),
                None,
            )?;
            if group.rate_limiter.hourly.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .hourly
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupHourlyRateLimitExceeded.into());
                }
            }
            if group.rate_limiter.daily.is_enabled() {
                let remaining = group
                    .rate_limiter
                    .daily
                    .effective_remaining_capacity(clock.unix_timestamp);
                if value.to_num::<i64>() > remaining {
                    return Err(MarginfiError::GroupDailyRateLimitExceeded.into());
                }
            }

            emit!(RateLimitFlowEvent {
                group: group_key,
                bank: bank_key,
                mint: bank.mint,
                flow_direction: 0, // outflow
                native_amount,
                mint_decimals: bank.mint_decimals,
                current_timestamp: clock.unix_timestamp,
            });
        }

pub fn update_group_rate_limiter(
    ctx: Context<UpdateGroupRateLimiter>,
    outflow_usd: Option<u64>,
    inflow_usd: Option<u64>,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,
) -> MarginfiResult {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let clock = Clock::get()?;

    check!(
        outflow_usd.is_some() || inflow_usd.is_some(),
        MarginfiError::GroupRateLimiterUpdateEmpty
    );
    validate_event_slots(
        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::GroupRateLimiterUpdateFutureSlot
    );
    check!(
        clock.slot.saturating_sub(event_end_slot) <= MAX_RATE_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::GroupRateLimiterUpdateStale
    );
    check!(
        update_seq == group.rate_limiter_last_admin_update_seq.saturating_add(1),
        MarginfiError::GroupRateLimiterUpdateOutOfOrderSeq
    );

    if let Some(inflow) = inflow_usd {
        check!(
            is_valid_rate_limit_amount(inflow),
            MarginfiError::InvalidConfig
        );
        group
            .rate_limiter
            .record_inflow(inflow, clock.unix_timestamp);
        msg!("Group rate limiter inflow recorded: {} USD", inflow);
    }

    if let Some(outflow) = outflow_usd {
        group
            .rate_limiter
            .try_record_outflow(outflow, clock.unix_timestamp)?;
        msg!("Group rate limiter outflow recorded: {} USD", outflow);
    }

    group.rate_limiter_last_admin_update_slot = event_end_slot;
    group.rate_limiter_last_admin_update_seq = update_seq;

    Ok(())
}
