### Title
Over-decrement of shared `pendingInstantWithdraws` counter when a prefunded defaulted instant receipt is claimed strands other claimants' unfunded basis - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug is an iteration-stride mismatch that drives a shared refcount below its true value (over-decrement of a counter that must equal the sum of per-entry contributions). The closest analog in the credit vault is `_claimDefaultedInstantWithdrawRequest`, which decrements the global `pendingInstantWithdraws` aggregate by the user's *entire* `claimBasis` even though part of that basis was already funded out of the prefunded recovery reserve. When `claimBasis` exceeds the remaining `pendingInstantWithdraws`, the code saturates the global counter to 0 instead of decrementing only the user's unfunded share, erasing unfunded basis that still belongs to other defaulted-epoch instant claimants.

### Finding Description
In `IdleCreditVault._claimDefaultedInstantWithdrawRequest` (contracts/strategies/idle/IdleCreditVault.sol:842-856):

```solidity
claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
...
uint256 pending = pendingInstantWithdraws;
pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
```

The comment itself acknowledges the mismatch: "`pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger, the extra amount was already counted as prefunded reserve during default finalization." So a single user's `claimBasis` can legitimately exceed the whole remaining `pendingInstantWithdraws` even though other users in the same `defaultEpoch` still hold unfunded instant receipts (`instantWithdrawsRequestsByEpoch[other][defaultEpoch] > 0` contributing to that counter). The saturating write collapses the aggregate to 0 while `instantWithdrawClaimsByEpoch[defaultEpoch]` still holds those other users' basis — the per-entry ledger and the global counter are now inconsistent, exactly like the refcount being decremented N extra times while the entries remain.

The same pattern is a classic "stride mismatch": the decrement applied per entry uses the entry's full size (claim basis = unfunded + prefunded share) against a counter that only tracks the unfunded stride.

### Impact Explanation
`pendingInstantWithdraws` is the vault's record of unfunded instant-withdraw liability owed by the borrower/strategy. If it is driven to 0 early, the remaining claimants' unfunded share is no longer tracked as a liability: any subsequent accounting path that relies on `pendingInstantWithdraws` to size borrower funding, gate new instant requests (`requestInstantWithdraw` increments it; `collectInstantWithdrawFunds`/stopEpoch funding decrements it), or to validate `_ensureDefaultRecoveryInitialized` (which reverts if `pendingInstantWithdraws != 0`) treats the vault as fully funded while `defaultRecoveryReserve` only covers the haircut-adjusted reserve. The result is understated liabilities and potential insolvency for late claimants — their receipt basis was counted, but the funding obligation that backs it has been erased. Depending on the surrounding flows, impact is either permanent freezing/theft of unclaimed instant withdrawals for remaining defaulted-epoch claimants or reserve over-drain to earlier claimants.

### Likelihood Explanation
Requires: instant withdrawals enabled, at least one instant receipt in the default epoch partially covered by prefunded liquidity at default finalization (so `claimBasis > pendingInstantWithdraws`), and at least one other claimant whose basis is unfunded. The first claimant to call `claimInstantWithdrawRequest` (via `claimWithdrawRequest`'s default path / the instant claim path) triggers the saturated zeroing. Attacker is just a tranche/token holder making a normal claim — no privileged action needed, but the scenario depends on the honest manager/borrower sequencing (default finalization with a prefunded portion), which lowers likelihood.

### Recommendation
Track the per-user unfunded share separately, or decrement `pendingInstantWithdraws` only by `min(claimBasis, pending)` while keeping `instantWithdrawsRequestsByEpoch`/`instantWithdrawClaimsByEpoch` as the source of truth for what remains claimable. Alternatively, split instant claim basis at finalization into `funded` and `unfunded` components per epoch so per-entry decrements always match the stride of the counter being decremented. Add an invariant check: `sum(instantWithdrawsRequestsByEpoch[·][e]) - fundedShare[e] == pendingInstantWithdraws` for the default epoch.
