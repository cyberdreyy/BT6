### Title
Unmapped stackerdb slot_id crashes the node-side signer coordination loop, wedging block-signature collection - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run()` builds a fixed `slot_id -> signer_entry` map once at construction time and then processes every incoming signer message keyed by `chunk.slot_id`. If a message arrives for a `slot_id` absent from that map, the handler does not skip or log-and-continue — it returns `Err(...)` from `run()` itself, terminating the entire listener loop that the mining/coordinator path depends on to collect pre-commits and block-response signatures.

### Finding Description
`StackerDBListener::new` builds `signer_entries` once from the reward set at the time the listener is constructed [1](#0-0) . In the main loop, each accepted `SignerMessages` event is matched against this static map:
```
for (slot_id, _pk, message) in messages.into_iter() {
    let Some(signer_entry) = &self.signer_entries.get(&slot_id) else {
        return Err(NakamotoNodeError::SignerSignatureError(
            "Signer entry not found".into(),
        ));
    };
``` [2](#0-1) 

Note that the `signer_set != self.signer_set` guard only filters out messages tagged for a *different reward cycle* [3](#0-2) ; it does not protect against a chunk whose `slot_id` simply isn't present in the `signer_entries` map that was snapshotted at listener-construction time, e.g. any drift between the contract's writer-slot layout at chunk-acceptance time and the reward-set snapshot captured in `StackerDBListener::new`. Unlike other error paths in this same function (which `warn!`/`debug!` and `continue`, e.g. the deserialization-failure and pubkey-recovery-failure paths at lines 342–346 and 596–611 shown in `libsigner/src/events.rs`), this one uses `return Err(...)`, which unwinds out of the `for` loop and out of the enclosing `loop { ... }` in `run()`, ending the whole listener thread rather than skipping the one bad message.

This is analogous to the libxmljs bug class: an untrusted, attacker/gossip-influenced input value (here, a `slot_id` on an accepted StackerDB chunk) is used to index into a data structure without a graceful "not found" fallback, and the resulting failure mode is not a rejection of the one bad item but a crash/termination of the entire message-processing component that the rest of the system depends on for liveness.

### Impact Explanation
If triggered, this breaks the state machine's liveness guarantee: the `StackerDBListener` thread is the mechanism by which the miner/coordinator learns about signer pre-commits and accept/reject signatures (`propose_block` / `get_block_status` in `signer_coordinator.rs`) [4](#0-3) . Killing this loop means the coordinator stops receiving signer votes for any in-flight or subsequent block proposal, matching the "High" impact category of a signer/coordinator wedged into never processing valid signatures. This would manifest as a stalled tenure until (if ever) something notices and restarts the listener — I could not confirm from the available code whether such a restart path exists, since I ran out of budget before locating and reading the exact call site in `signer_coordinator.rs` that spawns/monitors `StackerDBListener::run()`.

### Likelihood Explanation
The precise conditions that cause a chunk's `slot_id` to fall outside the `signer_entries` snapshot (e.g., timing around a reward-cycle boundary, or discrepancies between the `.signers-X-Y` contract's configured slot count and the parsed `reward_set_signers` enumeration) were not fully verified in this pass — I could not confirm whether this is reachable by a single miner/gossip actor under normal protocol operation or requires an unusual/edge-case sequence of events. This is a gap in my analysis that would need direct code tracing of the StackerDB slot-authorization logic (`stackerdb/mod.rs`) against the `signer_entries` construction to determine exact triggerability by a single non-majority actor.

### Recommendation
Change the "signer entry not found for slot_id" branch in `stacks-node/src/nakamoto_node/stackerdb_listener.rs` (lines 373–377) to `warn!`-and-`continue` (as is already done for deserialization and pubkey-recovery failures a few lines earlier), rather than `return Err(...)`, so a single unexpected/unmapped chunk cannot terminate the entire listener loop. Additionally, verify whether `signer_entries` needs to be refreshed rather than fixed at construction time to avoid boundary-condition mismatches.
