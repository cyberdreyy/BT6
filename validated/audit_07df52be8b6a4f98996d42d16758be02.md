### Title
Invalid reorg-attempt proposals reset the miner-inactivity timer, indefinitely suppressing fallback to a valid tenure - (File: `stacks-signer/src/chainstate/mod.rs`, `stacks-signer/src/chainstate/v1.rs`)

### Summary
`check_latest_block_in_tenure` treats a rejected, non-canonical reorg-attempt proposal as valid "miner activity" and calls `update_last_activity_time`, which unconditionally overwrites the tenure's `last_activity_time` with the current time regardless of what the previous value was. [1](#0-0) [2](#0-1) 

### Finding Description
The ETWAP bug class is an asymmetric state update: one direction of an update happens gradually/conditionally, while the other happens immediately and unconditionally, letting an attacker who controls the "immediate" side game the tracked value. The stacks-signer inactivity timer has the same asymmetric shape.

`SortitionState::is_timed_out` (v1) computes elapsed inactivity as `now - last_activity_time` and only falls back to the prior tenure once `elapsed > block_proposal_timeout`. [3](#0-2) 

`last_activity_time` is meant to reflect genuine miner progress, but `check_latest_block_in_tenure` also bumps it to `get_epoch_time_secs()` whenever the current miner proposes a block that *fails* the "does this confirm the tip we expect" check (an invalid/non-canonical reorg attempt against an already-signed or pre-committed block), as long as the reorg-attempt is within `reorg_attempts_activity_timeout`: [4](#0-3) 

This "update on any signal, immediately, unconditionally" is exactly the ETWAP flaw's asymmetric-direction problem: an actor who fully controls one side of the equality (here, the single elected miner for the tenure — no majority of signers needed) can keep resetting `last_activity_time` to "now" by repeatedly proposing (or gossiping) rejected/invalid reorg proposals, each one individually rejected but each one still counted as activity. Because `is_timed_out` only measures elapsed time since the last reset, an attacker-miner can indefinitely prevent `elapsed > block_proposal_timeout` from ever becoming true, even though it has produced zero valid/canonical blocks in the tenure. This wedges the fallback-to-prior-tenure liveness mechanism (`SortitionMinerStatus::InvalidatedBeforeFirstBlock` transition in `check_proposal`) from ever triggering, since that transition is gated by `is_timed_out`: [5](#0-4) 

The comment in the flow docs corroborates that this is treated as intentional "miner activity," but does not account for the case where the reorg attempts are repeated indefinitely purely to keep resetting the clock rather than making progress: [6](#0-5) 

### Impact Explanation
This is a liveness wedge triggerable by a single actor (the current tenure's elected miner, a one-slot actor), matching the in-scope "High" impact class: a signer can be wedged into never falling back to a valid/prior miner, since the inactivity timeout that gates that fallback can be perpetually reset by proposals that are rejected on every other check. While signers still reject each individual bad proposal (no invalid block is signed), the tenure can be starved indefinitely from ever recognizing the current miner as inactive, blocking recovery to the last valid tenure and stalling block production for that duration.

### Likelihood Explanation
Medium-High: it requires only the currently-elected miner (or anyone able to relay proposals under that miner's tenure, since checks run at proposal arrival before signature verification of block content) to periodically submit reorg-attempt proposals against an already-signed or pre-committed tip, spaced within `reorg_attempts_activity_timeout` of each other. No majority of signers or additional keys are needed; this is purely local per-signer bookkeeping abused by network-visible messages.

### Recommendation
Do not let a *rejected* proposal unconditionally overwrite `last_activity_time` to `now`. Distinguish "the miner is alive and building" (advancing chain length canonically) from "the miner sent a proposal" — e.g., only refresh the timer the first time a given rejected attempt is seen, rate-limit/cap how many resets a series of failed reorg attempts can grant, or make the update monotonic/decayed similarly to genuine forward progress instead of an unconditional overwrite of the timestamp, mirroring the ETWAP fix of applying symmetric logic in both directions.

### Proof of Concept
1. Sortition `T` elects miner `M`. Signers have a `BlockInfo` `B` that is signed/pre-committed in tenure `T` (`get_tenure_last_block_info` / `get_last_accepted_block` returns `Some`). [7](#0-6) 
2. `M` (or any relayer of `M`'s tenure) repeatedly proposes blocks with `chain_length <= B.header.chain_length` (an invalid reorg attempt against the already-signed/pre-committed tip), spaced less than `reorg_attempts_activity_timeout` apart.
3. Each such proposal enters `check_latest_block_in_tenure`, fails the primary check (`block.header.chain_length <= info.block.header.chain_length`), but because `signed_group` is fresh (or absent for a locally-accepted block) it calls `signer_db.update_last_activity_time(tenure, now)` before returning `Ok(false)`. [8](#0-7) 
4. `SortitionState::is_timed_out` for tenure `T` computes `elapsed = now - last_activity_time`, which never exceeds `block_proposal_timeout` because it keeps being reset in step 3. [9](#0-8) 
5. `check_proposal`'s timeout branch (`SortitionMinerStatus::InvalidatedBeforeFirstBlock`) never fires for `M`'s sortition, so signers never fall back to the prior valid tenure, wedging tenure progress as long as the attacker keeps sending rejected reorg attempts within the window. [5](#0-4)

        consensus_hash: &ConsensusHash,
        signer_db: &SignerDb,
        tenure_last_block_proposal_timeout: Duration,
    ) -> Result<Option<BlockInfo>, ClientError> {
        // Get the last signed block in the tenure
        let last_signed_block = signer_db
            .get_last_signed_block(consensus_hash)
            .map_err(|e| ClientError::InvalidResponse(e.to_string()))?;

        let Some(block_info) = last_signed_block else {
            return Ok(None);
        };

        // `approved_time` may hold the pre-commit time; use the actual signature time.
        let Some(signed_over_time) = block_info.signed_self.max(block_info.signed_group) else {
            return Ok(None);
        };

        if signed_over_time.saturating_add(tenure_last_block_proposal_timeout.as_secs())
            > get_epoch_time_secs()
        {
            // The last accepted block is not timed out, return it
            Ok(Some(block_info))
        } else {
            // The last accepted block is timed out
            info!(
                "Last accepted block has timed out";
                "signer_signature_hash" => %block_info.block.header.signer_signature_hash(),
                "signed_over_time" => signed_over_time,
                "state" => %block_info.state,
            );
            Ok(None)
        }
    }

    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
