### Title
Account email enumeration via distinguishable error responses in `CreateSession` - ([File: core/sessions/localauth/orm.go])

### Summary
`CreateSession` returns the raw, unwrapped database error when `FindUser` fails to find a matching email, while returning the fixed strings `"Invalid email"`/`"Invalid password"` for existing accounts. These distinct error contents are propagated verbatim to the HTTP client via `sessions_controller.go`, allowing an unauthenticated attacker to distinguish whether an email exists in the `users` table, which is exactly the anti-enumeration property `constantTimeEmailCompare` is meant to protect.

### Finding Description
In `core/sessions/localauth/orm.go`, `CreateSession` first calls `o.FindUser(ctx, sr.Email)`: [1](#0-0) 
`findUser` performs `SELECT * FROM users WHERE lower(email) = lower($1)` and returns whatever error `sqlx` produces (e.g. `sql.ErrNoRows`) unmodified: [2](#0-1) 
If the email does not exist, this raw DB error is returned immediately from `CreateSession` at line 147, **before** `constantTimeEmailCompare` or the password check are ever reached. Only when a user row is found does execution proceed to the "constant-time" checks that yield the generic `"Invalid email"` (line 156) or `"Invalid password"` (line 161) messages: [3](#0-2) 

Because `findUser`'s SQL query already does the case-insensitive email match, `constantTimeEmailCompare(sr.Email, user.Email)` at line 154 is essentially always true whenever `FindUser` succeeds — it can never actually observe a mismatch under normal operation, so it does not provide the anti-enumeration property implied by its name/comment. The real branch point that leaks account existence is the early `FindUser` failure path, which returns a *different error type and message* than the "wrong password" case.

This error is not sanitized before being sent to the client: `SessionsController.Create` forwards `err` from `CreateSession` directly into the HTTP response body: [4](#0-3) 

So an attacker POSTing to `/sessions` with a fixed wrong password and varying `email` values will receive:
- A raw SQL/driver error (e.g. `"sql: no rows in result set"` or similar) when the email does not exist.
- `"Invalid password"` when the email exists but the password is wrong.

These are trivially distinguishable by response content (no timing analysis needed), confirming the account-enumeration concern raised in the question, though the root cause is the unguarded `FindUser` error path rather than the ordering of `constantTimeEmailCompare` vs. the password check.

### Impact Explanation
An unauthenticated attacker can enumerate valid admin/operator emails on a Chainlink node's `/sessions` login endpoint by observing distinct error bodies. This is a precursor to targeted credential-stuffing or brute-force attacks against known admin accounts — consistent with an "information disclosure enabling further attack" bounty class rather than direct authentication bypass. It does not by itself grant access to the account/session.

### Likelihood Explanation
- Preconditions: none beyond network access to the node's `/sessions` HTTP endpoint; fully unauthenticated.
- No special credential or role is needed.
- The behavior is deterministic and trivially repeatable (a simple two-request comparison: existing vs. non-existing email, same wrong password).

### Recommendation
Normalize the error returned from `FindUser`/`findUser` failures in `CreateSession` (and in `TestPassword`) so that "email not found" and "email found, wrong password" produce an identical, generic error message/type (e.g. always return `"Invalid email or password"` regardless of which check failed), and ensure the code path timing is not observably different (e.g. always perform a dummy password hash comparison even when no user is found). Also avoid leaking the underlying DB error object (`sql.ErrNoRows`) to the HTTP layer.

### Proof of Concept
Go unit test in `core/sessions/localauth/orm_test.go`:
```go
func TestORM_CreateSession_NoEmailEnumeration(t *testing.T) {
    ctx := t.Context()
    _, orm := setupORM(t)

    existing := cltest.MustRandomUser(t)
    require.NoError(t, orm.CreateUser(ctx, &existing))

    _, errExistingWrongPwd := orm.CreateSession(ctx, sessions.SessionRequest{
        Email:    existing.Email,
        Password: "wrong-password",
    })

    _, errNonExistentEmail := orm.CreateSession(ctx, sessions.SessionRequest{
        Email:    "doesnotexist@example.com",
        Password: "wrong-password",
    })

    require.Error(t, errExistingWrongPwd)
    require.Error(t, errNonExistentEmail)
    // Assert both error responses are identical/generic to prevent enumeration.
    assert.Equal(t, errExistingWrongPwd.Error(), errNonExistentEmail.Error())
}
```
Expected current (vulnerable) behavior: assertion fails because `errNonExistentEmail.Error()` is a raw DB error (e.g. contains `"sql: no rows"`) while `errExistingWrongPwd.Error()` is `"Invalid password"`. A handler-level integration test against `SessionsController.Create` should additionally assert the raw JSON response bodies for both cases are byte-identical.
