### Title
Multisig `DeleteKey`/`DeleteMember` only purges requests where the removed key is the *original signer*, leaving stale confirmations from that key on other requests — allowing execution below `num_confirmations` threshold - ([File: multisig/src/lib.rs])

### Summary
When a multisig key/member is removed via `MultiSigRequestAction::DeleteKey` (`multisig/src/lib.rs`) or `MultiSigRequestAction::DeleteMember` (`multisig2/src/lib.rs`), the cleanup logic only removes/prunes requests whose `signer_pk`/`member` (the original *creator* of the request) equals the key being deleted. It does **not** scan and strip that key's *confirmations* contributed to other, still-pending requests it did not create. Those stale confirmations remain counted toward `num_confirmations` when a later `confirm()` call tallies the set, letting a request execute with fewer live, authorized signers than the configured threshold.

### Finding Description
`execute_request`'s `DeleteKey` branch in `multisig/src/lib.rs` does: [1](#0-0) 
It filters `self.requests` by `r.signer_pk == pk` — i.e. only requests *originated* by the deleted key — and clears their confirmations/requests. Confirmations that the deleted key added to *other* requests (created by different signers) are left untouched inside `self.confirmations`, which is a raw `HashSet<PublicKey>` per request: [2](#0-1) 

`confirm()` counts membership purely by set size, with no re-validation that each entry in the confirmation set is still a live access key on the account: [3](#0-2) 

The identical pattern exists in `multisig2/src/lib.rs`'s `delete_member`, which filters `requests` by `r.member == member` only, and never scans `self.confirmations` for stale entries belonging to the removed member: [4](#0-3) 

The binding that should hold is: `count(confirmations for request R) >= num_confirmations` should imply `count(live members among those confirmations) >= num_confirmations`. Because a removed key's confirmation on a request it did not create is never purged, that equality/implication is broken — the recorded confirmation count diverges from the count of currently-authorized signers.

### Impact Explanation
This breaks the "confirmations counted versus live members" custody binding explicitly called out as in-scope. A multisig request (e.g. a `Transfer` draining NEAR from the multisig account, or a `DeployContract`/`AddKey` privilege escalation) can be executed once `confirmations.len() + 1 >= num_confirmations` is satisfied, even though one of the counted confirmations belongs to a key that has since been deleted from the account. This is functionally a multisig request executed below the true threshold of live authorized signers — matching the Critical impact category "a multisig request executed below threshold."

### Likelihood Explanation
No privileged actor, redeploy, or malicious validator is required. The scenario only needs: (1) `num_confirmations >= 3` (or more generally more than 2, so a request isn't auto-executed on its 2nd confirmation), (2) a request pending with fewer than threshold confirmations, one of which is later removed via a legitimate `DeleteKey`/`DeleteMember` request, and (3) a subsequent confirmation from a still-valid key that pushes the stale count over threshold. This is an ordinary sequence of otherwise-legitimate multisig operations (add request, partially confirm, remove an unrelated key/member, confirm again) rather than any edge-case or misconfiguration, making it readily reachable in normal contract operation.

### Recommendation
When removing a key/member (`DeleteKey` / `DeleteMember`), iterate over **all** pending requests' confirmation sets (not just requests where the removed key is the original `signer_pk`/`member`) and strip the removed key/member's entry from each. Alternatively, validate at `confirm()`/execution time that every public key/member in a request's confirmation set is still an active key/member before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize multisig with `num_confirmations = 3` and keys `A, B, C, D`.
2. `A` calls `add_request_and_confirm(request1)` (a `Transfer` to attacker-controlled account) → `confirmations = {A}`.
3. `B` calls `confirm(request1)` → `confirmations = {A, B}` (2 < 3, not executed).
4. Separately, `A, C, D` confirm a `DeleteKey { public_key: B }` request (own 3-of-4 threshold) to legitimately remove `B` from the multisig, e.g. because `B`'s device was compromised. This executes `execute_request`'s `DeleteKey` branch: it filters requests where `signer_pk == B`; `request1` was created by `A`, so it is skipped — `confirmations[request1]` still contains `B`.
5. `C` now calls `confirm(request1)` → `confirmations = {A, B, C}`, size 3 `>= num_confirmations`, so `remove_request` + `execute_request` run and the `Transfer` executes.
6. Result: the transfer executed with confirmations from `A`, `B` (deleted key), `C` — only 2 live authorized signers approved it, one fewer than the configured `num_confirmations = 3`. [1](#0-0) [3](#0-2) [4](#0-3)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
