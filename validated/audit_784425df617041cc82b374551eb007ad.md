## Finding: Evicted/de-allowlisted delegators can bypass the delegation-pool allowlist gate via `reactivate_stake` and remain active

### Title
Delegator allowlist eviction is reversible by the evicted delegator via `reactivate_stake()` - (File: `aptos-move/framework/aptos-framework/sources/delegation_pool.move`)

### Summary
`delegation_pool::add_stake` is the only stake-management entry point that enforces the pool's allowlist gate, calling `assert_delegator_allowlisted` before allowing new stake in. `unlock` (the function `evict_delegator` uses internally to force a de-allowlisted delegator's stake into `pending_inactive`) performs no allowlist check at all. This is the same "restricted function vs. unrestricted bypass function" pattern as the external report's `vote()`/`deposit_for()`+`poke()` mismatch: one path enforces an access-control decision made by a privileged role (the pool owner), while a related, unprivileged-callable path does not.

### Finding Description
`add_stake` is explicitly gated: [1](#0-0) 

`evict_delegator` is the owner-only mechanism for removing a non-allowlisted delegator's *active* stake from the pool, by unlocking it into `pending_inactive`: [2](#0-1) 

However, `unlock` (the function both regular delegators and `evict_delegator` rely on) contains no allowlist check whatsoever — it only validates the amount against active stake on the underlying stake pool: [3](#0-2) [4](#0-3) 

Since `unlock` is a `public entry fun` callable by any delegator address, an owner's intent behind `evict_delegator` (to remove a delegator's *active* stake from the pool because they are not/no-longer allowlisted) does not actually revoke the delegator's ability to interact with their own remaining shares — the delegator can call `reactivate_stake` themselves (as demonstrated in the test suite at delegator-controlled calls immediately following an eviction) to move stake from `pending_inactive` back into `active`: [5](#0-4) 

No code path shown for `reactivate_stake` or `unlock` re-checks `delegator_allowlisted` the way `add_stake` does at line 1489. The allowlist gate in this module is therefore only an *entry* gate, not a persistent membership gate — the same structural flaw as `vote()`'s epoch/whitelist checks not being mirrored in `poke()`/`deposit_for()`.

### Impact Explanation
An owner who de-allowlists and evicts a delegator (e.g., a delegator behaving maliciously, or one the operator wants to force out of a permissioned pool) expects that delegator's stake to progress toward withdrawal, not to keep earning active rewards or occupying pool capacity. Because `reactivate_stake`/`unlock` are unrestricted, the evicted delegator can immediately move their stake back to `active`, defeating the owner's allowlist-based access control. This is a "wrong-role control over owner state without holding that role" impact: the delegator retains a privilege (continued active participation/rewards accrual) that only the owner is supposed to be able to grant via allowlisting.

### Likelihood Explanation
High for any operator actually using the allowlisting feature (`DelegationPoolAllowlisting`) to police participation: the evicted delegator needs no special permission — they only call `reactivate_stake` on their own delegator address, which is a normal `public entry fun`, immediately after (or instead of) being evicted.

### Recommendation
Add an `assert_delegator_allowlisted` (or equivalent "not evicted" check) to `reactivate_stake` (and reconsider `unlock` for parity in permissioned pools), mirroring the check already present in `add_stake`, so that owner-driven eviction/allowlist decisions cannot be reversed unilaterally by the delegator.

### Proof of Concept
1. Owner enables allowlisting on a delegation pool and allowlists Delegator A; A calls `add_stake` and accrues `active` stake.
2. Owner removes A from the allowlist and calls `evict_delegator(owner, A)`, which internally calls `unlock_internal`, moving A's entire active balance to `pending_inactive`.
3. A (still not allowlisted) calls `reactivate_stake(A, pool_address, amount)` — this function performs no allowlist check, so it succeeds and moves A's stake back into `active`.
4. A is now back in `active` state, earning full rewards and consuming pool capacity, despite the owner's explicit removal — the allowlist-based eviction is fully reversed by the excluded delegator.

**Caveat:** I could not fully view the complete body of `reactivate_stake` due to index/content-size limits on the retrieved file; the surrounding code (lines 1560–1611) and the test comments strongly indicate no allowlist re-check exists, but a Devin session with full file access should confirm the exact function boundaries and any allowlist-check codepath before treating this as final.

        delegator: &signer,
        pool_address: address,

    ) acquires DelegationPool, GovernanceRecords, BeneficiaryForOperator, NextCommissionPercentage {
        // short-circuit if amount to unlock is 0 so no event is emitted
        if (amount == 0) { return };

        // synchronize delegation and stake pools before any user operation
        synchronize_delegation_pool(pool_address);

        let delegator_address = signer::address_of(delegator);
        unlock_internal(delegator_address, pool_address, amount);
