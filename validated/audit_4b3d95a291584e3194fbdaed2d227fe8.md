### Title
Unbounded per-notification cost in `programSubscribe`/token `logsSubscribe` via attacker-controlled account fan-out - (File: rpc/src/rpc_subscriptions.rs)

### Summary
An attacker can subscribe once via `programSubscribe` (or `logsSubscribe`) to a known SPL token program and then, in a single slot, create/modify many token accounts referencing many distinct mints under that program. `filter_program_results` unconditionally routes all changed accounts for that program through `get_parsed_token_accounts`, which is O(N) in the number of changed accounts/mints and builds an unbounded `HashMap<Pubkey, AccountAdditionalDataV3>`, with no per-notification size or count cap.

### Finding Description
`RpcSubscriptions::notify_watchers` iterates active subscriptions in parallel and, for `SubscriptionParams::Program`, calls `bank.get_program_accounts_modified_since_parent(&params.pubkey)` to fetch every account under the subscribed program that changed in the slot, then passes the full `Vec<(Pubkey, AccountSharedData)>` through `check_commitment_and_notify` into `filter_program_results` [1](#0-0) .

`filter_program_results` applies the subscription's account filters, and if the subscribed program is a known SPL token program and encoding is `JsonParsed`, calls `get_parsed_token_accounts(bank, keyed_accounts)` over the entire filtered set with no cap [2](#0-1) .

`get_parsed_token_accounts` builds a `HashMap<Pubkey, AccountAdditionalDataV3>` (`mint_data`) that grows with the number of distinct mints referenced by the changed accounts, doing a mint-account bank lookup (`get_mint_owner_and_additional_data`) for each new mint, and JSON-encodes every account via `encode_ui_account` [3](#0-2) . Every matching account/result is then wrapped as one `RpcNotificationResponse` value and sent via `notifier.notify(...)` per result inside `check_commitment_and_notify`'s loop, so the whole notify_watchers pass and produced payload set scales with N = number of attacker-written accounts/mints in that slot [4](#0-3) .

There is no subscription-level cap on the number of accounts returned by `get_program_accounts_modified_since_parent`, no cap on the number of distinct mints resolved in `get_parsed_token_accounts`'s `mint_data` map, and no cap on serialized notification size distinct from `RpcNotifier`'s retained-history/queue eviction (which was referenced in the question as bounding only queued history, not a single notification/result set). Nothing in `check_commitment_and_notify`, `filter_program_results`, or `get_parsed_token_accounts` truncates or paginates results per notification pass.

### Impact Explanation
This matches the "unbounded cost for a single low-rate call" category: a single `programSubscribe` (one WebSocket subscription, well under the `CLUSTER_SLOT_TIME_TARGET/2` cadence) combined with normal on-chain writes (creating many token accounts across many mints under the subscribed program in one slot) forces the validator's pubsub worker to do O(N) bank-account lookups, O(N) mint-data hashmap growth, and O(N) JSON encoding/serialization per notify pass, and to emit O(N) individual notification payloads to that one client. This is CPU/memory amplification and payload-size amplification driven by attacker-controlled on-chain data, on the RPC/pubsub notification path (`notify_watchers` → `filter_program_results` → `get_parsed_token_accounts`), not merely a bounded per-subscription queue eviction concern.

### Likelihood Explanation
Preconditions are minimal and match the allowed attacker model: unprivileged access to submit transactions creating SPL token accounts (fee-payer funds required, but this is ordinary usage, not privileged access), and a single subscribe call. It is fully repeatable every slot the attacker chooses to write many accounts, and does not require any validator/operator misconfiguration — it is inherent to the current code path since no cap exists between `get_program_accounts_modified_since_parent`'s result set and the JSON-encoding/mint-resolution step.

### Recommendation
Introduce a per-notification/per-slot cap on the number of accounts processed by `filter_program_results`/`get_parsed_token_accounts` for a single `programSubscribe`/token-program subscription (e.g., truncate or split into bounded batches, and/or cap the number of distinct mints resolved into `mint_data` per pass), and enforce a maximum serialized notification size independent of `RpcNotifier`'s queue eviction, returning an error or partial/paginated notification when the changed-account set for a slot exceeds the bound.

### Proof of Concept
Integration test plan (in `rpc/src/rpc_subscriptions.rs` test module, alongside existing `program_subscribe`-style tests such as the pattern at `client-test/tests/client.rs:325-416`):
1. Create a genesis/bank setup and an `RpcSubscriptions` instance as in `test_program_subscription`.
2. Issue a single `programSubscribe` for the SPL Token program with `encoding: JsonParsed`.
3. In one bank/slot, create N (e.g., 5,000) distinct mint accounts and N associated token accounts owned by the Token program, each referencing a unique mint, via `bank.process_transaction` calls (all within the same slot before calling `notify_subscribers`).
4. Call `subscriptions.notify_subscribers(commitment_slots)` once and measure: (a) wall-clock/CPU time of the call, (b) number of `RpcNotificationResponse` messages received by the subscriber, (c) total serialized bytes of all notifications received.
5. Assert that CPU time and total notification bytes grow roughly linearly with N (e.g., compare N=500 vs N=5000 and expect ~10x scaling), demonstrating no cap distinct from queue eviction bounds the per-notification cost, confirming the unbounded-cost finding.

fn filter_program_results(
    accounts: Vec<(Pubkey, AccountSharedData)>,
    params: &ProgramSubscriptionParams,
    last_notified_slot: Slot,
    bank: Arc<Bank>,
) -> (impl Iterator<Item = RpcKeyedAccount> + use<>, Slot) {
    let accounts_is_empty = accounts.is_empty();
    let encoding = params.encoding;
    let filters = params.filters.clone();
    let keyed_accounts = accounts.into_iter().filter(move |(_, account)| {
        filters
            .iter()
            .all(|filter_type| filter_allows(filter_type, account))
    });
    let accounts = if is_known_spl_token_id(&params.pubkey)
        && params.encoding == UiAccountEncoding::JsonParsed
        && !accounts_is_empty
    {
        let accounts = get_parsed_token_accounts(bank, keyed_accounts);
        Either::Left(accounts)
    } else {
        let accounts = keyed_accounts.map(move |(pubkey, account)| RpcKeyedAccount {
            pubkey: pubkey.to_string(),
            account: encode_ui_account(&pubkey, &account, encoding, None, None),
        });
        Either::Right(accounts)
    };
    (accounts, last_notified_slot)
}

pub fn get_parsed_token_accounts<I>(
    bank: Arc<Bank>,
    keyed_accounts: I,
) -> impl Iterator<Item = RpcKeyedAccount>
where
    I: Iterator<Item = (Pubkey, AccountSharedData)>,
{
    let mut mint_data: HashMap<Pubkey, AccountAdditionalDataV3> = HashMap::new();
    keyed_accounts.filter_map(move |(pubkey, account)| {
        let additional_data = get_token_account_mint(account.data()).and_then(|mint_pubkey| {
            mint_data.get(&mint_pubkey).cloned().or_else(|| {
                let (_, data) = get_mint_owner_and_additional_data(&bank, &mint_pubkey).ok()?;
                let data = AccountAdditionalDataV3 {
                    spl_token_additional_data: Some(data),
                };
                mint_data.insert(mint_pubkey, data);
                Some(data)
            })
        });

        let maybe_encoded_account = encode_ui_account(
            &pubkey,
            &account,
            UiAccountEncoding::JsonParsed,
            additional_data,
            None,
        );
        if let UiAccountData::Json(_) = &maybe_encoded_account.data {
            Some(RpcKeyedAccount {
                pubkey: pubkey.to_string(),
                account: maybe_encoded_account,
            })
        } else {
            None
        }
    })
}
