### Title
Signer's reorg-timing permission check depends on each signer's local wall-clock receipt time, letting a miner split the signer set into conflicting-block signers - ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`SortitionData::check_parent_tenure_choice` decides whether an incoming miner may reorg an already-mined tenure by comparing a duration computed from two **locally observed, per-signer wall-clock timestamps**: the time this signer's node received the new burn block (`sortition_state_received_time`) and the time this signer itself pre-committed/approved the earlier tenure's first block (`local_block_info.approved_time`). Because neither of these is a value all signers agree on (they are local receipt times, subject to normal network propagation jitter), a miner who proposes the reorging tenure-change block near the `first_proposal_burn_block_timing` boundary can cause the signer set to split: some signers compute `proposal_to_sortition < first_proposal_burn_block_timing` and treat the reorg as *permitted* (marking the prior tenure superseded and signing the new, competing tenure-change block), while other honest signers compute the opposite and reject the same block with `RejectReason::ReorgNotAllowed`. This is the direct analog of the reported "last-minute timing manipulation" bug class: an outcome-deciding boundary is evaluated against a value an adversary can position near the edge, and because the value is not a canonical, network-agreed quantity, honest participants disagree.

### Finding Description
In `check_parent_tenure_choice` [1](#0-0) , the signer fetches its own locally-recorded burn-block receive time via `signer_db.get_burn_block_receive_time(&self.burn_block_hash)`, and then for each reorged tenure computes `proposal_to_sortition = sortition_state_received_time.saturating_sub(approved_at)` where `approved_at` comes from `local_block_info.approved_time` [2](#0-1) . The reorg is permitted only if `Duration::from_secs(proposal_to_sortition) < first_proposal_burn_block_timing` [3](#0-2) ; otherwise it's refused and the whole tenure-change proposal is rejected with `ReorgNotAllowed` from `validate_tenure_change_payload` [4](#0-3)  (and analogously in v2 via `check_parent_tenure_choice`/`validate_tenure_change_payload` at [5](#0-4) ).

Both `sortition_state_received_time` and `approved_time` are timestamps stamped independently by each signer process when it locally received/processed an event — they are never exchanged, hashed into the block, or otherwise made canonical across the signer set. The sample config's own documentation confirms this design intent and its fragility: the reorg window is measured as `(burn_block_received - first_block_signed)` on a per-signer basis, and is explicitly noted to be sensitive to being set "too low"/"too high" [6](#0-5) .

Because ordinary network propagation delay causes different signers to record different receive times for the same burn block, and different approve times for the same earlier block, any reorg attempt whose true elapsed time is close to `first_proposal_burn_block_timing` (default 60s) will be evaluated inconsistently across the honest signer population. A miner that wants to force this split simply needs to broadcast its reorging tenure-change proposal at a moment calculated (via observing gossip/StackerDB traffic, which is public, exactly as in the Hermez report where bids are public) to sit at that boundary — no signer collusion or majority key is required, this is a natural consequence of the check's reliance on non-synchronized local clocks.

The unit tests `check_proposal_reorg_timing_bad`/`check_proposal_reorg_timing_ok` and `check_parent_tenure_choice_reorg_timing_bad`/`_ok` [7](#0-6) [8](#0-7)  confirm the pass/fail boundary is a hard threshold (30 vs 29/31 seconds), demonstrating how tightly the outcome depends on the exact timing value fed in — exactly the kind of razor-edge decision the Hermez report warns is manipulable.

### Impact Explanation
When the reorg is deemed "permitted" by a subset of signers, `record_superseded_tenure` is called, which calls `signer_db.mark_tenure_superseded` [9](#0-8)  so that signer's own earlier signature over the original tenure's block "does not later block the replacement" — i.e., that signer will go on to sign the new, reorging tenure-change block. Signers on the other side of the timing boundary reject that same block. This produces two disjoint groups of signers each willing to sign a different, mutually conflicting chain tip at the same tenure position — a direct break of the "approved-parent vs canonical" equality the signer protocol relies on to guarantee a single canonical chain, and a path to a signer set that is split between a valid tenure and a conflicting, superseding one. This matches the Critical impact category: a signer set signing a conflicting/non-canonical block due to a manipulable, per-node-local decision boundary.

### Likelihood Explanation
Likelihood is High-to-Medium: it requires no majority of signers, no key compromise, and no protocol-level access beyond what any sortition-winning miner already has (broadcasting a tenure-change block proposal at a chosen time relative to the public burn block/gossip it can observe). It does require some skill in timing the proposal relative to typical network propagation jitter across the signer set, but the underlying values (`first_proposal_burn_block_timing` defaults, StackerDB latencies) are visible/estimable, similar to how Hermez bidders can observe the public vote state to time their last-minute bid.

### Recommendation
**Short term:** Replace or supplement the locally-observed wall-clock inputs (`sortition_state_received_time`, `approved_time`) with a canonical, network-agreed timestamp where possible (e.g., derive the "proposal-to-sortition" gap primarily from data embedded in the block header / burn block timestamp rather than each signer's own receipt time), and/or widen the timing check with a shared tolerance/buffer so that normal propagation jitter cannot flip signers across the accept/reject boundary independently.

**Long term:** Revisit the reorg-permission logic so that the "was this tenure poorly timed" determination is made from data that is provably identical across all honest signers (i.e., not a function of when each individual signer process happened to observe an event), removing the timing-based manipulation surface entirely.

### Proof of Concept
1. Two honest signers, S1 and S2, each hold a valid signature over tenure T's first block, with `approved_time` recorded a few seconds apart due to normal StackerDB propagation (`local_block_info.approved_time`, set at pre-commit).
2. A new miner wins the next sortition and crafts a tenure-change block that reorgs tenure T. The miner picks the broadcast time so that `(now - T's approved_time)` is roughly `first_proposal_burn_block_timing` (default 60s) for the population of signers.
3. S1 receives the new burn block slightly earlier (`sortition_state_received_time` smaller) → computes `proposal_to_sortition < first_proposal_burn_block_timing` → `check_parent_tenure_choice` returns `Ok(true)` → S1 marks T superseded and signs the new reorging tenure-change block [10](#0-9) .
4. S2 receives the new burn block slightly later (`sortition_state_received_time` larger) → computes `proposal_to_sortition >= first_proposal_burn_block_timing` → returns `Ok(false)` → `validate_tenure_change_payload` rejects the block with `RejectReason::ReorgNotAllowed` [11](#0-10) .
5. S1 and S2 now hold signatures over two conflicting blocks (T's original block vs. the reorging tenure-change block) at effectively the same tenure position, with the split driven entirely by the miner's choice of broadcast timing relative to each signer's local clock — no majority or key compromise involved.

    /// in tenure changes, we need to check:
    /// if the tenure change confirms the expected parent block (i.e.,
    /// the last globally accepted block in the parent tenure)
    fn validate_tenure_change_payload(
        tenure_change: &TenureChangePayload,
        block: &NakamotoBlock,
        parent_tenure_id: &ConsensusHash,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        config: &ProposalEvalConfig,
    ) -> Result<(), RejectReason> {
        // Check that the tenure change's prev_tenure matches the signer's known parent tenure.
        // This catches block commits with bad parent_block_ptr (e.g., vtxindex=0 exploit).
        if &tenure_change.prev_tenure_consensus_hash != parent_tenure_id {
            warn!(
                "Block commit parent tenure mismatch: the block commit's parent_block_ptr does not correspond to the actual parent tenure";
                "committed_parent_tenure" => %parent_tenure_id,
                "actual_parent_tenure" => %tenure_change.prev_tenure_consensus_hash,
                "consensus_hash" => %block.header.consensus_hash,
                "signer_signature_hash" => %block.header.signer_signature_hash(),
            );
            return Err(RejectReason::InvalidParentBlock);
        }

        // Ensure that the tenure change block confirms the expected parent block
        let confirms_expected_parent = SortitionData::check_tenure_change_confirms_parent(
            tenure_change,
            block,
            signer_db,
            client,
            config.tenure_last_block_proposal_timeout,
            config.reorg_attempts_activity_timeout,
        )
        .map_err(SignerChainstateError::from)?;
        if !confirms_expected_parent {
            return Err(RejectReason::InvalidParentBlock);
        }
        // We already confirmed in check miner activity that the current tenure is valid. So check we are not
        // reorging the tenure blocks. Only blocks we have signed (locally or globally accepted) count
        // here: a block we have merely pre-committed to carries no signature from us, so it is safe to
        // accept a competing tenure-start block in its place if it failed to reach consensus.
        let last_in_current_tenure = signer_db
            .get_last_signed_block(&block.header.consensus_hash)
            .map_err(|e| {
                SignerChainstateError::from(ClientError::InvalidResponse(e.to_string()))
            })?;
        if let Some(last_in_current_tenure) = last_in_current_tenure {
            warn!(
                "Miner block proposal contains a tenure change, but we've already signed a block in this tenure. Considering proposal invalid.";
                "proposed_block_consensus_hash" => %block.header.consensus_hash,
                "proposed_block_signer_signature_hash" => %block.header.signer_signature_hash(),
                "last_in_tenure_signer_signature_hash" => %last_in_current_tenure.block.header.signer_signature_hash(),
            );
            return Err(RejectReason::DuplicateBlockFound);
        }
        Ok(())
    }

# Reorg protection window. Measures the time between when the first block
# of a tenure was signed and when the next burn block (sortition) arrived.
#
# If a new miner tries to reorg a tenure that already produced blocks:
#   - If (burn_block_received - first_block_signed) < this value:
#     Reorg is ALLOWED (the tenure was "poorly timed" and the incoming
#     miner did not have sufficient time to RBF an outdated commit)
#   - If (burn_block_received - first_block_signed) >= this value:
#     Reorg is DENIED (the tenure was established long enough for the
#     incoming miner to RBF any outdated commit)
#
# WARNING: Setting this too LOW allows dangerous reorgs of established
# tenures. Setting it too HIGH blocks legitimate miner handoffs when
# the previous tenure's first block arrived shortly before the sortition.
#
# Default: 60
# Units: seconds
# first_proposal_burn_block_timing_secs = 60
