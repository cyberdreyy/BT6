### Title
External Initiator can trigger job runs for arbitrary jobs, bypassing WebhookSpec.ExternalInitiatorID binding - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`AuthenticateExternalInitiator` in `core/web/auth/auth.go` authenticates an EI credential and then sets **both** `SessionExternalInitiatorKey` and a synthetic `SessionUserKey` (`&clsessions.User{Role: clsessions.UserRoleRun}`) on the gin context: [1](#0-0) 

The job-run creation handler, `PipelineRunsController.Create`, is intended to restrict integer-ID job runs to real users only ("only users are allowed to run jobs using int IDs - EIs not allowed"), but it implements this check via `auth.GetAuthenticatedUser(c)`: [2](#0-1) 

Because `AuthenticateExternalInitiator` also populates `SessionUserKey`, `GetAuthenticatedUser(c)` returns `ok=true` for EI-authenticated requests exactly the same way it does for real user sessions/tokens. The handler never calls `GetAuthenticatedExternalInitiator(c)` to check which EI authenticated the request, nor does it look up the target job's `WebhookSpec.ExternalInitiatorID` to confirm the authenticated EI is the one bound to that specific job. As a result, `isUser` is true for both real users and EI holders, and the code proceeds to call `prc.App.RunJobV2(ctx, jobID, nil)` for **any** integer job ID supplied in the URL — including DirectRequest, Cron, or any other job type/ID unrelated to the caller's EI credentials.

### Impact Explanation
An attacker holding valid credentials for one External Initiator (job-specific, low-privilege webhook trigger credentials) can invoke `POST /v2/jobs/{ID}/runs` for any job in the node by integer ID, triggering pipeline runs that were never intended to be reachable by that EI. This is an authorization/request-binding bypass allowing unauthorized triggering of job runs (e.g., DirectRequest/Cron pipelines), potentially causing unwanted on-chain transactions, fund movement, oracle responses, or resource exhaustion — matching the "unauthorized job run" bounty impact class.

### Likelihood Explanation
Exploitation requires only a legitimate EI access-key/secret pair for one webhook-bound job (a low-privilege credential type explicitly in scope as an "unprivileged" attacker per the audit rules) and knowledge/guessing of another job's integer ID (job IDs are sequential integers, easily enumerable). No additional privileges, admin access, or misconfiguration are needed — this is directly exploitable via a single crafted HTTP request and is fully repeatable.

### Recommendation
In `PipelineRunsController.Create`, when the request was authenticated via `AuthenticateExternalInitiator`, explicitly call `auth.GetAuthenticatedExternalInitiator(c)` and require that the target job (fetched by ID) is of type `job.Webhook` and that its `WebhookSpec.ExternalInitiatorID` matches the authenticated EI's ID before invoking `RunJobV2`. Do not rely solely on `GetAuthenticatedUser` to distinguish EI-authenticated requests from real user sessions, since `AuthenticateExternalInitiator` also populates `SessionUserKey`.

### Proof of Concept
1. Create two jobs: Job A = Webhook job bound to External Initiator `EI-1`; Job B = DirectRequest or Cron job with integer ID, unrelated to any EI.
2. Obtain valid `EI-1` access key/secret (as would be provisioned to an external initiator client).
3. Send `POST /v2/jobs/{JobB.ID}/runs` with headers `X-Chainlink-EA-AccessKey` / `X-Chainlink-EA-Secret` set to `EI-1`'s credentials.
4. Expected (secure) behavior: `403 Forbidden` or `404 Not Found`, since `EI-1` is not authorized for Job B.
5. Actual behavior per code inspection: request passes `AuthenticateExternalInitiator` middleware, `GetAuthenticatedUser(c)` returns the synthetic run-role user, `isUser` is `true`, and `RunJobV2(ctx, JobB.ID, nil)` is invoked, creating an unauthorized pipeline run for Job B — confirmable via a Go handler-level integration test asserting `resp.StatusCode == http.StatusCreated` (bug) instead of `403`/`404` (expected fix).
