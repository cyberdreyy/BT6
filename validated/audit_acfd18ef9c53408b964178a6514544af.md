### Title
APR=0 epoch yield-factor truncation permanently strands withdraw-requester interest — larger pooled principal reduces per-user payout vs. the true pro-rata share - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug class — a yield/accrual factor computed as `interest / totalDeposits` and then multiplied back per position, so truncation in the division is amplified by the multiplier and loses more the larger the denominator — exists verbatim in the APR0 withdrawal flow of `IdleCreditVault`. At `stopEpoch`, the vault computes a single per-epoch exchange rate `apr0RateByEpoch[epoch] = netInterest * 1e18 / apr0TotalPrincipal` (line 537), then settles each requester with `principal * rate / 1e18` (line 561). The rate is floored before being multiplied back, so the aggregate of all settled interest is strictly less than `_apr0NetInterest` that was added to `pendingWithdraws` (line 535). The residual is permanently trapped inside `pendingWithdraws` — it is counted in the borrower-owed claim basis (`defaultPendingClaimBasis`, line 645) and in default haircuts, but no code path ever pays it out.

### Finding Description
In `prepareStopEpochWithApr0` (lines 490–541):

```solidity
pendingWithdraws += _apr0NetInterest;                        // line 535
apr0RateByEpoch[epochNumber] = (_apr0NetInterest * 1e18) / _principal;  // line 537
apr0TotalPrincipal = 0;                                      // line 540
```

and in `_settleApr0` (lines 545–565):

```solidity
uint256 _rate = apr0RateByEpoch[_reqEpoch];
if (_rate != 0) {
    _apr0User.settledInterest += (_principal * _rate) / 1e18;   // line 561
}
```

Two stacked truncations mirror the TickLogic `yieldFactor` bug:

1. `_apr0InterestGross = _interestNetOfFees * _principal / _totalPrincipalForSplit` (line 521) rounds the APR0 bucket's share down against active tranche holders.
2. `rate = net * 1e18 / principal` is floored, then each of the N requesters applies `p_i * rate / 1e18`, flooring again per user. Total distributed `<` `_apr0NetInterest`; the deficit stays in `pendingWithdraws` forever because `apr0TotalPrincipal` is zeroed and the rate snapshot is immutable once `epochNumber` advances past `_reqEpoch`.

The key size-dependent property of the external report is preserved: the lost amount is `Σ p_i * frac(rate)/1e18`-shaped — a per-epoch, per-user haircut whose relative magnitude depends on the ratio of `_apr0NetInterest` to `_principal`, i.e., how much of the epoch interest is squeezed through the division. A requester whose principal is a large share of a small-interest epoch loses proportionally the same way Bob did in the report; the mechanism is identical (single rate divided by aggregate deposits, multiplied back per position), only the variable names differ.

`pendingWithdraws` is decreased only by `claimBasis` in `_claimDefaultedWithdrawRequest` (line 778) and by actual claims, so the stranded residual also inflates `defaultPendingClaimBasis` (line 645), marginally diluting every other claim's recovery haircut — the dust is double-counted as both an obligation and unpayable.

### Impact Explanation
Permanent freezing of unclaimed yield, plus a small interest transfer from APR0 withdraw requesters to active tranche holders (step 1 truncation) and to no one (step 2 residual). Per-operation magnitude is bounded by `N * principal / 1e18`-scale dust for the rate leg and < 1 wei for the gross split leg, but it accrues every epoch, is unrecoverable by design, and — as in the external report — grows with low-decimal tokens, short epochs, and large principal-to-interest ratios where the same `interest/deposits` division is replayed. The invariant "the sum of per-user settled interest equals the interest reserved for the bucket" is broken.

### Likelihood Explanation
Requires no attacker action beyond being a normal KYC'd withdraw requester during an APR0 epoch (`unscaledApr == 0`, enforced at line 506). It triggers automatically on every `stopEpoch` where `_apr0NetInterest % apr0TotalPrincipal != 0`, i.e., essentially always with real-world amounts. It cannot be exploited adversarially for profit (the loss falls on the requesters themselves), which is why it is a correctness/accounting defect rather than a theft vector — matching the external report, which was a rounding bug, not an exploit.

### Recommendation
Compute and store per-user interest directly at stopEpoch when the bucket is small enough to iterate, or keep the aggregate `_apr0NetInterest` per epoch and pay each user `p_i * _apr0NetInterest / apr0TotalPrincipal` lazily against a stored `apr0TotalPrincipalByEpoch[epoch]` instead of a pre-division rate — this confines truncation to a single division per claim. If the rate must stay, round `apr0RateByEpoch` up (or compute `settledInterest` for the last/most-recent user as the residual `bucketNet - alreadySettled`) so the bucket fully distributes. Add a property test: after settlement of all requesters, `Σ settledInterest == _apr0NetInterest` regardless of how `apr0TotalPrincipal` is split among users, with 6- and 18-decimal tokens.

### Proof of Concept
Foundry fork-style sketch (against `test/foundry/IdleCreditVault.t.sol` harness, e.g. `testDepositDuringEpochNumericalAA` setup):

```solidity
// APR0 epoch: manager sets unscaledApr = 0 via setAprs(0, 0)
// User A requests withdraw of principal pA, user B of pB in epoch E
// stopEpoch with real interest override I such that I % (pA + pB) != 0

uint256 principal = pA + pB;                        // apr0TotalPrincipal
uint256 net = (I - pendingFees) * principal / (tvl + principal);
net -= net * fee / FULL_ALLOC;                      // _apr0NetInterest
// stored rate truncates
uint256 rate = net * 1e18 / principal;

// after epochNumber advances, settle both users
uint256 settledA = pA * rate / 1e18;
uint256 settledB = pB * rate / 1e18;

uint256 pendingBefore = vault.pendingWithdraws();   // includes net
// claim both receipts...
uint256 residual = net - (settledA + settledB);
assertGt(residual, 0);                              // stranded in pendingWithdraws
// residual is never claimable: apr0TotalPrincipal == 0 and rate is frozen
```

A second assertion demonstrates the size dependence: rerun with `pA' = pA` but the epoch interest `I'` chosen so `I' % principal` is a large fraction of `principal` (e.g., `I' = principal - 1` units of remainder); the per-user loss grows while the deposited principal is unchanged — the same "larger denominator → larger absolute rounding loss" behavior reported for `TickLogic.yieldFactor`.
