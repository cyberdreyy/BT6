### Title
External-Initiator credentials satisfy the `isUser`/`RequiresRunRole` checks and can trigger arbitrary job runs via `POST /v2/jobs/:ID/runs` - ([File: core/web/pipeline_runs_controller.go], [File: core/web/auth/auth.go], [File: core/web/router.go])

### Summary
The `userOrEI` route group authenticates requests with `auth.AuthenticateExternalInitiator`, `auth.AuthenticateByToken`, or `auth.AuthenticateBySession`, and the EI method injects a synthetic `&clsessions.User{Role: UserRoleRun}` into the same `SessionUserKey` context slot used by real users. Because `PipelineRunsController.Create` and `auth.RequiresRunRole` only check `GetAuthenticatedUser(c)`/`user.Role`, an EI credential is functionally indistinguishable from a genuine run-role human/API user, allowing it to trigger a run for any numeric job ID even though the code comment explicitly states "EIs not allowed" for that path.

### Finding Description
The route is registered as: [1](#0-0) 

`auth.AuthenticateExternalInitiator` sets the same context key used for real users, with a synthetic run-role user: [2](#0-1) 

`RequiresRunRole` only inspects `user.Role`, and rejects only `UserRoleView`; both the synthetic EI user and a real run-role/edit/admin user pass: [3](#0-2) 

Inside `PipelineRunsController.Create`, the code explicitly intends to block EIs from using the integer-ID path ("only users are allowed to run jobs using int IDs - EIs not allowed"), but the actual check only verifies that `GetAuthenticatedUser` returned `ok == true`, not that the caller is a *user* as opposed to an EI: [4](#0-3) 

Because `AuthenticateExternalInitiator` always populates `SessionUserKey`, `isUser` is `true` for EI callers too, so the comment's intended restriction is not enforced by the code. Historically, legacy webhook jobs (referenced by UUID) were the only jobs an EI could trigger, and that path was scoped to the specific EI(s) listed in the job's `externalInitiators` TOML block (see `external_initiator_webhook_specs` join table and `TestRunner_WebhookJobRemoved`), but the webhook job type has since been fully removed (`job.ErrJobTypeRemoved`), permanently disabling that per-job authorization scoping check while leaving the integer-ID path — with no EI/job binding at all — open to any authenticated identity that satisfies `GetAuthenticatedUser`. [5](#0-4) 

The `GetAuthenticatedExternalInitiator(c)` accessor exists precisely to distinguish EI-origin requests from real users, but it is never consulted in `PipelineRunsController.Create`: [6](#0-5) 

### Impact Explanation
An attacker holding only a valid External Initiator access key/secret (a low-trust credential meant to be scoped to a specific webhook job) can call `POST /v2/jobs/:ID/runs` with the numeric ID of any job on the node — not just jobs it was registered for — and cause `prc.App.RunJobV2(ctx, jobID, nil)` to execute that job's pipeline. This is an authorization bypass / unauthorized job run: the EI credential is silently granted the privileges of a genuine "run" role user for every route in the `userOrEI` group gated by `RequiresRunRole` or by the `isUser` check, contradicting the code's own stated invariant that EIs are not allowed to run jobs by integer ID.

### Likelihood Explanation
Precondition is minimal: a valid, low-privilege EI access key/secret (created via `POST /external_initiators`, itself only requiring edit role once — but per the threat model the EI credential holder itself is the unprivileged attacker). Job IDs are small sequential integers and are also exposed via `GET /jobs` (reachable in the `authv2` group for any authenticated identity, though not EI) or can be brute-forced; no per-EI-to-job binding exists to prevent triggering unrelated jobs. The exploit is fully repeatable and requires no timing or race conditions.

### Recommendation
In `PipelineRunsController.Create`, explicitly reject requests originating from an External Initiator before allowing the integer-ID job-run path, e.g. check `if _, isEI := auth.GetAuthenticatedExternalInitiator(c); isEI { return 401/403 }`, rather than relying on the overloaded `GetAuthenticatedUser` boolean which EI authentication also satisfies. More broadly, avoid overloading `SessionUserKey` for EI identities; use a distinct signal (or a dedicated `Source`/`AuthMethod` field on the context) so downstream handlers can always differentiate EI-origin requests from genuine user sessions/tokens.

### Proof of Concept
Handler-level integration test in `core/web/pipeline_runs_controller_test.go`:
1. Start an app with an `ExternalInitiator` `eiA` registered, and a separate job `jobB` (non-webhook, e.g. cron or OCR type) with a valid numeric ID that has no relation to `eiA`.
2. Send `GET /v2/ping` with `eiA`'s `X-EI-ACCESS-KEY`/`X-EI-SECRET` headers via `cltest.UnauthenticatedGet`; assert `200 OK` with `{"message":"pong"}`.
3. Send `POST /v2/jobs/<jobB.ID>/runs` (numeric ID) with the same EI headers.
4. Assert the response is `200 OK` (or triggers `RunJobV2`) rather than `401 Unauthorized`, demonstrating the EI credential bypassed the intended "EIs not allowed" restriction and triggered a run for a job with no relationship to that EI.
5. Unit-test companion: call `auth.AuthenticateExternalInitiator(c, store)` directly, then `auth.GetAuthenticatedUser(c)`, and assert the returned `*clsessions.User{Role: UserRoleRun}` is structurally identical to a database-backed run-role `clsessions.User`, then assert `auth.RequiresRunRole` and the `isUser` check in `PipelineRunsController.Create` cannot distinguish the two, while `auth.GetAuthenticatedExternalInitiator(c)` returns `ok == true`, proving detection is possible but not used.

func AuthenticateExternalInitiator(c *gin.Context, store Authenticator) error {
	ctx := c.Request.Context()
	eia := &auth.Token{
		AccessKey: c.GetHeader(static.ExternalInitiatorAccessKeyHeader),
		Secret:    c.GetHeader(static.ExternalInitiatorSecretHeader),
	}

	ei, err := store.FindExternalInitiator(ctx, eia)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return auth.ErrorAuthFailed
		}

		return errors.Wrap(err, "finding external initiator")
	}

	ok, err := bridges.AuthenticateExternalInitiator(eia, ei)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionExternalInitiatorKey, ei)

	// External initiator endpoints (wrapped with AuthenticateExternalInitiator) inherently assume the role
	// of 'run' (required to trigger job runs)
	c.Set(SessionExternalInitiatorKey, ei)
	c.Set(SessionUserKey, &clsessions.User{Role: clsessions.UserRoleRun})

	return nil
}

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
