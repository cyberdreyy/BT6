### Title
Job script can spawn a detached descendant that inherits the trace-stream pipe FDs, hanging `Commander.Wait()`/`Run()` and preventing stream release until job timeout - ([File: helpers/process/commander.go], [File: executors/custom/command/command.go])

### Summary
`NewOSCmd` assigns the job's trace writer directly to `exec.Cmd.Stdout`/`Stderr` [1](#0-0) . Because that writer is not an `*os.File`, Go's `os/exec` internally creates a pipe and a background copy goroutine, and `Cmd.Wait()` will not return until that goroutine observes EOF - which only happens once **every** process holding the write end of the pipe (including any inherited-FD descendant spawned by the job) has closed it.

### Finding Description
`command.Run()` starts the driver/job process and waits on `c.cmd.Wait()` inside `waitForCommand()`, blocking on `c.waitCh` until `Wait()` returns [2](#0-1) ; `waitForCommand()` itself does nothing but call `c.cmd.Wait()` and push the result to `c.waitCh` [3](#0-2) . `osCmd.Wait()` on unix is a thin wrapper around `exec.Cmd.Wait()` [4](#0-3) .

Because `CommandOptions.Stdout`/`Stderr` are set as generic `io.Writer` (the job trace writer) rather than `*os.File`, `exec.Cmd` allocates an OS pipe and a copier goroutine per stream; `Wait()`'s documented contract is that it "will not return until stdin/stdout/stderr [copy goroutines] complete," which in turn only completes once all writers of the pipe's write end - including any process that inherited the FD before `exec` - have exited/closed it. A job's own script (executed as the custom-executor driver's child, fully attacker-controlled content) can trivially daemonize/double-fork a background process (`setsid ... &`, `nohup ... &`, or an explicit fork+exec that doesn't set `close-on-exec`) before the main script exits. That detached process inherits the trace-stream FD and keeps it open indefinitely.

`setProcessGroup` puts the started process into its own process group via `Setpgid` [5](#0-4) , but that mechanism is only exercised by the killer path triggered from `c.context.Done()` in `Run()`'s `select` [6](#0-5)  - i.e., only on job cancellation/timeout. On the normal-completion path there is no equivalent step that force-kills leftover group members after the main process exits; the code relies solely on `c.cmd.Wait()` returning, which is exactly what a lingering FD-holding descendant prevents. So the invariant "a job's I/O streams must be fully released once its Commander completes" is violated: the Commander does not complete (`Wait()` hangs) as long as the descendant is alive, and only the job's own configured timeout (which can be very large or unset in some flows) will eventually trigger the group kill and free the pipe.

### Impact Explanation
While `Wait()` is blocked, the goroutine, the trace-stream writer, and any underlying resources associated with that job's log delivery remain held by the runner process for as long as the descendant lives - up to the job's timeout, which is attacker/administrator configurable and can be large. Since this consumes a runner "slot"/goroutine and keeps that job's trace stream unclosed, concurrently running jobs on the same runner host can be starved of concurrency slots or, if trace writers share buffering/streaming resources, experience delayed log delivery. This is a resource-exhaustion issue reachable purely from job-controlled script content, not an admin misconfiguration.

### Likelihood Explanation
The precondition is simply that the custom-executor driver executes attacker-supplied script content (true for the `run` stage of any custom executor, which by design runs the CI job's script) and that the OS permits FD inheritance across `fork()`/detachment without `O_CLOEXEC` (default on Linux/unix unless explicitly set, and Go's `os.Pipe`/`exec` FDs passed to a child are inheritable by that child's own children unless the child itself sets close-on-exec). Producing a detached grandchild that outlives the parent (`setsid cmd & disown`, or double-fork) is a one-line technique, fully within reach of an unprivileged pipeline author. This is highly repeatable and does not depend on any race condition.

### Recommendation
- Ensure descendant processes cannot retain inherited stdout/stderr pipe FDs past the main process's lifetime: on Linux, mark the pipe FDs `O_CLOEXEC`, or run the child in its own PID namespace/process group and unconditionally kill the whole group after `Wait()` on the main process handle is not achievable (chicken-and-egg since `Wait()` itself hangs) - so:
- Prefer waiting on the process exit status independently of I/O completion: use `Cmd.Process.Wait()` semantics or read `Process.Wait()`-based exit detection (e.g., via `syscall.Wait4`) rather than `exec.Cmd.Wait()`, and only afterwards drain/close the trace pipe with a bounded timeout, force-closing the write end (killing the whole process group by negative PID) if draining does not complete promptly.
- Alternatively, always kill the process group (`syscall.Kill(-pgid, ...)`) immediately after the direct child's exit status is detected, regardless of whether `context.Done()` fired, so orphaned descendants are reaped before relying on `Wait()`'s I/O-completion semantics.

### Proof of Concept
Go integration test (unix):
```go
func TestCommanderWaitHangsOnDetachedGrandchild(t *testing.T) {
    var stdout, stderr bytes.Buffer
    opts := process.CommandOptions{Stdout: &stdout, Stderr: &stderr}
    // script spawns a detached grandchild that duplicates stdout/stderr and sleeps
    cmd := process.NewOSCmd("/bin/sh", []string{"-c",
        `setsid sh -c 'exec >&1 2>&2; sleep 30' </dev/null & exit 0`}, opts)

    require.NoError(t, cmd.Start())

    done := make(chan error, 1)
    go func() { done <- cmd.Wait() }()

    select {
    case <-done:
        // Wait() must return promptly once the direct child exits
    case <-time.After(3 * time.Second):
        t.Fatal("Wait() blocked on detached grandchild holding trace-stream FDs open")
    }
}
```
Expected (current) result: the test fails/times out, demonstrating `Wait()` blocks for the sleep duration of the detached grandchild rather than returning when the direct child exits, confirming the FD-retention hang.

```go
func (c *command) waitForCommand() {
	err := c.cmd.Wait()

	eerr, ok := err.(*exec.ExitError)
	if ok {
		exitCode := getExitCode(eerr)
		switch {
		case exitCode == BuildFailureExitCode:
			err = c.parseBuildFailure(eerr)
		case exitCode != SystemFailureExitCode:
			err = &ErrUnknownFailure{Inner: eerr, ExitCode: exitCode}
		}
	}

	c.waitCh <- err
}
```
