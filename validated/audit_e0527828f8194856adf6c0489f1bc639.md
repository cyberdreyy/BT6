## Analysis Result: Valid Finding

I traced the full `switch_operator` → `distribute` flow in `staking_contract.move` and confirmed the mechanism described in the question is real.

### Key trace

`switch_operator` is a staker-only privileged call, but the *consequence* it creates is later triggered by anyone through the permissionless `distribute` entry function [1](#0-0) .

Inside `switch_operator`, the sequence is:
1. `distribute_internal(staker_address, old_operator, &mut staking_contract)` flushes only the *already inactive* funds and pays out any existing `old_operator` shares correctly through `beneficiary_for_operator(old_operator)` [2](#0-1) .
2. `request_commission_internal(old_operator, &mut staking_contract)` is called **after** that flush, and computes/records *new* commission shares keyed to `old_operator` inside the same `distribution_pool` — but this commission has not yet unlocked from the stake pool, so it is not redeemed at this point [3](#0-2) .
3. The operator on the stake pool is switched, and the *same* `StakingContract` object — including its `distribution_pool`, which still holds unredeemed shares keyed to `old_operator` — is re-inserted into the map under the `new_operator` key [4](#0-3) .

Later, once that commission becomes inactive/withdrawable, any unprivileged account can call `distribute(staker, new_operator)` [5](#0-4) . Inside `distribute_internal`, the beneficiary resolution is gated by a single equality check against the *current* `operator` parameter (`new_operator`):

```
if (recipient == operator) {
    recipient = beneficiary_for_operator(operator);
};
``` [6](#0-5) 

Since the pool's remaining shareholder is `old_operator`, not `new_operator`, this check fails, and `old_operator`'s commission is deposited straight to `old_operator`'s raw address via `aptos_account::deposit_coins`, completely bypassing `beneficiary_for_operator(old_operator)`.

### Title
Unprivileged `distribute` call misroutes old operator's pending commission to raw address instead of registered beneficiary after `switch_operator` - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Summary
`distribute_internal` resolves the beneficiary redirection using an equality check against the function's `operator` parameter, not against the actual address of each shareholder in `distribution_pool`. When `switch_operator` re-keys a `StakingContract` (and its `distribution_pool`) from `old_operator` to `new_operator` while unredeemed commission shares for `old_operator` remain in the pool, any later call to `distribute` (which is explicitly documented and implemented as permissionless — "Allow anyone to distribute already unlocked funds") pays that commission to `old_operator`'s raw account address instead of `old_operator`'s registered `beneficiary_for_operator`.

### Finding Description
`distribution_pool` is a shares ledger shared across operator switches — it is not reset or re-keyed when `switch_operator` changes the map key from `old_operator` to `new_operator`. Commission requested via `request_commission_internal(old_operator, ...)` inside `switch_operator` adds shares keyed to `old_operator`'s address into this pool, but since the associated stake hasn't unlocked yet, it isn't paid out at that time. The pool object then gets carried over under the `new_operator` key [7](#0-6) . When `distribute` eventually redeems all shares, `distribute_internal`'s beneficiary check `recipient == operator` only matches the operator passed into the current call (`new_operator`), so `old_operator`'s leftover shares are redeemed straight to `old_operator`'s address rather than through `beneficiary_for_operator(old_operator)` [6](#0-5) .

### Impact Explanation
This breaks the beneficiary abstraction that operators rely on for commission custody (e.g., routing to a cold wallet/multisig distinct from the operator's hot signing key used for validator duties). An unprivileged party merely calling the public `distribute` entry function can trigger this misrouting; no privileged role is required to invoke the entrypoint that manifests the bug (only the earlier, legitimate `switch_operator` action by the staker is required to set up the scenario). Funds are not stolen by the attacker, but they are redirected away from the intended beneficiary custody, which the review's decision standard treats as impactful for role/beneficiary boundary violations.

### Likelihood Explanation
Requires: (1) staker calls `switch_operator` while the old operator has pending, not-yet-unlocked commission and has a `BeneficiaryForOperator` set, and (2) anyone subsequently calls permissionless `distribute(staker, new_operator)` once that commission becomes withdrawable. Both are ordinary, expected operational sequences (operator rotation is a documented supported flow via `switch_operator`), so this is readily triggerable without any special privilege for the second step.

### Recommendation
In `distribute_internal`, resolve the beneficiary per-shareholder rather than by comparing against the function's `operator` parameter — e.g., check if `recipient` has a registered `BeneficiaryForOperator` (or track the historical operator identity in the distribution pool) rather than relying on `recipient == operator`.

### Proof of Concept
1. Set up a staking contract for `staker`/`operator1`, call `set_beneficiary_for_operator(operator1, beneficiary1)`.
2. Advance epochs to accrue rewards, call `request_commission` to add unredeemed commission shares for `operator1` in `distribution_pool`, but do **not** call `distribute` yet (so the shares remain unredeemed/un-unlocked).
3. Call `switch_operator(staker, operator1, operator2, ...)` — this internally calls `distribute_internal` (flushing only already-inactive funds) then `request_commission_internal(operator1, ...)`, adding fresh, still-locked commission shares keyed to `operator1` into the pool that gets moved under the `operator2` key.
4. Advance epochs/lockup so that commission becomes inactive.
5. From an arbitrary unprivileged account, call `distribute(staker, operator2)`.
6. Assert: `coin::balance<AptosCoin>(operator1)` increased by the commission amount, while `coin::balance<AptosCoin>(beneficiary1)` did **not** — confirming payout bypassed `beneficiary_for_operator(operator1)`.
