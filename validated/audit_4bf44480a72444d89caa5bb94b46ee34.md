### Title
Stale per-epoch instant-withdraw records inflate default recovery and overpay early claimants - ([File: contracts/strategies/idle/IdleCreditVault.sol])

### Summary
`claimInstantWithdrawRequest` pays out a funded instant-withdraw receipt but only clears the aggregate `instantWithdrawsRequests[_user]`; it never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or decrements `instantWithdrawClaimsByEpoch[epoch]`. Like the advisory's leaked `oldObject` annotation, a copy of a supposedly-consumed value survives in a parallel record. If the epoch later ends in a borrower default, `finalizeDefaultRecovery` reads these stale entries via `defaultPendingClaimBasis` and `_defaultPrefundedInstantReserve`, inflating both the claim basis and the assumed prefunded reserve, which produces an overstated `defaultRecoveryPrice` and overpays claimants who already withdrew, draining the isolated reserve.

### Finding Description
In `requestInstantWithdraw`, three records are written: `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and `instantWithdrawClaimsByEpoch[currentEpoch]` [1](#0-0) . On the normal funded path, `claimInstantWithdrawRequest` burns the receipt and zeroes only the aggregate [2](#0-1) . The per-epoch entries are only cleared in `_claimDefaultedInstantWithdrawRequest`, which runs exclusively after default finalization [3](#0-2) .

At default finalization, `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` to the basis whenever `pendingInstantWithdraws != 0` [4](#0-3) , and `_defaultPrefundedInstantReserve` computes `instantBasis - pendingInstant`, treating the stale (already-claimed-and-spent) amounts as underlying still held by the strategy [5](#0-4) . Both feed `reserveAmount` and `totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is computed against phantom funds [6](#0-5) . Since the claimed underlying already left the contract, `defaultRecoveryReserve` exceeds the actual balance, and `_transferDefaultRecovery` will pay early claimants an inflated share until the reserve/balance is exhausted [7](#0-6) .

Additionally, a user who claimed their instant request pre-default retains `instantWithdrawsRequestsByEpoch[_user][defaultEpoch] != 0`, so `_claimDefaultedInstantWithdrawRequest` executes `instantWithdrawsRequests[_user] -= claimBasis` on a zeroed aggregate — an underflow revert that permanently blocks `claimInstantWithdrawRequest` for that user, freezing any other funded receipts they hold [8](#0-7) .

### Impact Explanation
Direct theft plus permanent freezing. The stale `instantWithdrawClaimsByEpoch` inflates `defaultRecoveryPrice` above what the real reserve supports, so users whose defaulted instant receipts are processed first receive more underlying than their pro-rata share, and the reserve is depleted before legitimate later claimants (including normal withdraw receipt holders claiming through `_transferDefaultRecovery`) are paid — unclaimed yield/recovery is stolen, not just delayed. Separately, any user who claimed a funded instant withdrawal in the defaulted epoch can never call `claimInstantWithdrawRequest` again, permanently freezing any other receipt balances routed through that function.

### Likelihood Explanation
Only unprivileged actors are needed for setup: any tranche-token holder can call `requestInstantWithdraw` and later claim through the honest CDO path — this is normal usage, not adversarial privilege. The trigger is a borrower default in the same epoch where at least one instant withdrawal was partially funded/claimed, which is an ordinary protocol event the code explicitly supports (`defaultInstantWithdrawsFinalized` exists precisely for the partial-funding case). No guard prevents it: `_ensureDefaultRecoveryInitialized` only checks `pendingInstantWithdraws`/aggregate counters, not the stale per-epoch records [9](#0-8) .

### Recommendation
On the funded claim path in `claimInstantWithdrawRequest`, also clear `instantWithdrawsRequestsByEpoch[_user][epochNumber]` (or track the claim's request epoch) and decrement `instantWithdrawClaimsByEpoch` by the claimed amount, mirroring what `_claimDefaultedInstantWithdrawRequest` already does. Alternatively, store the request epoch alongside instant receipts so the correct per-epoch bucket can be decremented at claim time.

### Proof of Concept
Foundry fork PoC (against the existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
function testStaleInstantClaimInflatesDefaultRecovery() external {
    // running epoch, unprivileged user
    address user1 = makeAddr('instantUser');
    _depositWithUser(user1, 10_000 * ONE_SCALE, true);

    // buffer/stop so epoch is running, then request instant withdraw
    // (funded via collectInstantWithdrawFunds by the honest CDO)
    cdoEpoch.requestInstantWithdraw(5_000 * ONE_SCALE, address(AAtranche));
    uint256 reqEpoch = creditVault.epochNumber();

    // honest manager/borrower partially or fully funds and user claims normally
    vm.prank(user1);
    cdoEpoch.claimInstantWithdrawRequest();
    assertEq(creditVault.instantWithdrawsRequests(user1), 0);
    // BUG: per-epoch copies survive
    assertGt(creditVault.instantWithdrawsRequestsByEpoch(user1, reqEpoch), 0);
    assertGt(creditVault.instantWithdrawClaimsByEpoch(reqEpoch), 0);

    // another unclaimed instant request keeps pendingInstantWithdraws != 0,
    // then borrower repays less than owed -> honest manager triggers default
    // and finalizeDefaultRecovery runs with reqEpoch == epochNumber:
    // - defaultPendingClaimBasis includes the stale 5_000e18 basis
    // - _defaultPrefundedInstantReserve counts the already-paid 5_000e18
    //   as strategy-held underlying
    // - defaultRecoveryPrice is inflated; first defaulted claimants are
    //   overpaid until the real balance is exhausted -> later claimants get 0
    // - a second claimInstantWithdrawRequest by user1 reverts on underflow
}
```

Quantified loss: every already-claimed instant amount in the defaulted epoch is double-counted in `reserveAmount`/`totalBasis`, so up to `instantWithdrawClaimsByEpoch[epoch] - pendingInstantWithdraws` of phantom underlying distorts the recovery price; claimants processed early receive roughly `(realReserve + phantom) / (realBasis + phantomBasis)` per unit of basis, directly transferring the shortfall to later claimants whose `_transferDefaultRecovery` then reverts or underpays to zero.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
```
