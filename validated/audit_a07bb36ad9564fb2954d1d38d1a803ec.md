Based on my review of the multisig2 contract, there is a plausible analog to the reported bug class: a custody/authorization binding that can silently drift from what the "confirmations vs. live members" invariant is supposed to enforce, because a delete operation does not retroactively invalidate confirmations already recorded by removed members on *other* pending requests.

### Title
Stale confirmations from removed members can count toward execution threshold in `MultiSigContract::confirm` - (File: `multisig2/src/lib.rs`)

### Summary
`delete_member` (invoked via `MultiSigRequestAction::DeleteMember`) only purges outstanding requests and confirmation sets for the request(s) *created by* the removed member, but leaves that member's confirmation string present in the `confirmations` sets of any *other* still-pending requests they had previously confirmed. `confirm` later counts these confirmation sets by raw length against `num_confirmations` without re-validating that each recorded confirmer is still a current member.

### Finding Description
`delete_member` deletes only requests where `r.member == member` (i.e., requests the removed member authored), and calls `self.confirmations.remove(&request_id)` solely for those authored requests: [1](#0-0) 

It never scans other members' pending requests to strip the removed member's entry out of their `confirmations` HashSet<String>. Meanwhile, `confirm` treats the confirmation-set length as a proxy for "distinct live members who approved": [2](#0-1) 

The set is keyed by `member.to_string()` (an arbitrary serialized string, not validated against current membership at read time), so a confirmation recorded while the member was still valid remains in the count forever, even after that member is removed via `DeleteMember`.

The binding that should hold is:
```
confirmations.len() (for a pending request) == number of *currently authorized* members who approved it
```
But after a `DeleteMember` action executes, this becomes:
```
confirmations.len() >= number of currently authorized members who approved it
```
i.e. recorded approvals can exceed the count of members who are still entitled to grant them — mirroring the audit's core pattern of "trust granted to an entity being evaluated against stale/incorrect binding data" (there, `RESERVE_TYPE`/`params` bound to the wrong reserve; here, a confirmation count bound to a member who no longer exists in the `members` set).

### Impact Explanation
If a K-of-N multisig has an in-flight request R (not yet confirmed) that already has confirmations from members A and B, and subsequently a `DeleteMember` request removes member A (a separate, already-confirmed action), request R's confirmation set still contains A's entry. When the remaining count of *legitimate* confirmers needed is recalculated, only B (and any further members) needs to add confirmations to reach `num_confirmations`, effectively executing R with fewer *live* confirmers than the configured threshold — a multisig request executed below threshold. This falls under the Critical impact category defined by the rules ("a multisig request executed below threshold"), since NEAR (or contract calls, key additions, etc.) can be moved/authorized with fewer than `num_confirmations` currently-authorized signers.

### Likelihood Explanation
This requires a specific but realistic sequencing: an existing pending request must have partial confirmations, and a `DeleteMember` request affecting one of those confirmers must be separately confirmed and executed before the original request reaches its confirmation threshold. This is plausible in normal multisig operational flow (e.g., offboarding a compromised or departing member) and does not require any privileged or out-of-scope action beyond what a normal multisig member/owner already can do — it is a data-consistency gap in the contract's own bookkeeping, not a deployment misconfiguration.

### Recommendation
When executing `DeleteMember`, iterate over all pending requests' confirmation sets and remove the string representation of the deleted member from each, or alternatively have `confirm`/`execute_request` re-validate that every entry in a request's confirmation set still corresponds to a member present in `self.members` before counting it toward the threshold.

### Proof of Concept
1. Deploy `MultiSigContract::new(members = [A, B, C, D], num_confirmations = 3)`.
2. A calls `add_request` for `Transfer { amount }` to some receiver → `request_id = 0`.
3. A calls `confirm(0)` → confirmations = {A}.
4. B calls `confirm(0)` → confirmations = {A, B} (still below threshold of 3, request stays pending).
5. Separately, C and D (and one more) submit and confirm a `DeleteMember { member: A }` request against `receiver_id = current_account_id()`, which executes `delete_member`, removing A from `self.members` — but request 0's `confirmations` set still contains A's string entry (untouched, since request 0 was authored/owned by A but not itself deleted since it's still pending and not authored by A being scanned — note: request 0 *was* authored by A, so it actually *would* be deleted by the `filter_map` on `r.member == member`). 

   To bypass that specific cleanup path, use a request authored by a *different, still-live* member (e.g., B authors request 0, A and B confirm it) so `delete_member(A)` does not match `r.member == member` for request 0 and leaves A's confirmation in place.
6. Now only C confirms request 0: confirmations = {A, B, C}, length 3 ≥ `num_confirmations` (3) → `execute_request` runs the transfer, even though A is no longer a valid member and only B and C are truly current, live confirmers. [3](#0-2) [1](#0-0)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
