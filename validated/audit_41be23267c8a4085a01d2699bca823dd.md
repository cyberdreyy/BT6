### Title
Stale `lastWithdrawRequest` lets legacy/aggregate withdraw receipts skip the loss haircut and over-claim funded reserves - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` records an epoch-level haircut in `lossRecoveryPriceByEpoch[epochNumber]` when the borrower underfunds `pendingWithdraws`. Loss-adjusted claims are keyed off the single-slot pointer `lastWithdrawRequest[_user]`. `requestWithdraw` tries to prevent that pointer from moving past an unclaimed loss epoch, but its guard only checks `withdrawsRequestsByEpoch[_user][lossEpoch]` and open `apr0Users` principal. A user whose receipt exists only in the aggregate `withdrawsRequests[_user]` bucket (a legacy/pre-upgrade receipt — a state this codebase explicitly supports via lazy `defaultRecoveryInitialized`) has zero per-epoch basis, so the guard passes. Their new request overwrites `lastWithdrawRequest` with a fresh epoch carrying no loss price, the loss-adjusted claim path silently returns 0, and `_claimFundedWithdrawRequest` pays the full aggregate — including the haircutted amount — at par.

### Finding Description
The bug mirrors the fscache race: a "discard" flag (`lossRecoveryPriceByEpoch[lossEpoch]`) is set while a receipt is pending, but before the claim "worker" runs, a second `requestWithdraw` mutates the pointer (`lastWithdrawRequest`) the claim uses to find the flag — so the haircut state is never applied.

Sequence:

1. User U holds a legacy pending receipt: `withdrawsRequests[U] = X`, `withdrawsRequestsByEpoch[U][*] = 0` (pre-upgrade state; see `testUpgradeWithLegacyPendingWithdrawNeedsNoUpgradeAndCall`).
2. Another user makes any `requestWithdraw`/`requestInstantWithdraw`, which calls `_ensureDefaultRecoveryInitialized` and sets `defaultRecoveryInitialized = true`, unblocking partial funding.
3. `stopEpoch` underfunds `pendingWithdraws` (realized loss, e.g. `stopEpochWithDuration(_lossAmount)`); `collectWithdrawFunds` stores `lossRecoveryPriceByEpoch[epochNumber] = _amount * 1e18 / pendingBasis < 1e18` and zeroes `pendingWithdraws`. Only `_amount` underlyings were transferred to the vault.
4. U calls `requestWithdraw` again. The guard at `IdleCreditVault.sol:263-271` evaluates `withdrawsRequestsByEpoch[U][lossEpoch] != 0` → false (per-epoch basis is zero), so it does not revert. `lastWithdrawRequest[U]` is overwritten to `currentEpoch`.
5. U calls `claimWithdrawRequest`. `_claimLossAdjustedWithdrawRequest` reads `lossEpoch = lastWithdrawRequest[U] = currentEpoch`, finds `lossRecoveryPriceByEpoch[currentEpoch] == 0`, returns 0. `_claimFundedWithdrawRequest` then pays `withdrawsRequests[U]` — which still contains the entire haircutted legacy basis `X` — plus the new receipt, at par, via `_transferFundedClaim`.

The vault transferred out `X` while only `X * recoveryPrice` of that basis was funded, so U's payout is inflated by `X * (1 - recoveryPrice)` taken from the funded reserve backing other users' loss-adjusted claims.

### Impact Explanation
Direct theft / insolvency: the last loss-adjusted claimants of the loss epoch find the reserve short by `X * (1 - lossRecoveryPrice)` and their `_transferFundedClaim` reverts or underpays. With a 50% haircut and a 100k-underlying legacy receipt, U extracts ~50k underlyings belonging to other receipt holders, in a single permissionless sequence across two epochs (any unprivileged receipt holder qualifies; no privileged attacker needed).

### Likelihood Explanation
Requires (a) an aggregate-only pending receipt — possible for any receipt that was pending across the implementation upgrade (explicitly supported state), and (b) a subsequent underfunded stop (`collectWithdrawFunds` with `_amount < pendingBasis`, i.e. `stopEpochWithDuration` loss or underfunded close). Condition (b) is a normal, designed-for protocol path — realized borrower losses are part of the credit-vault model — so the trigger does not depend on attacker control of privileged roles.

### Recommendation
In `requestWithdraw`, extend the guard so the aggregate bucket is also checked: revert when `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]] != 0 && withdrawsRequests[_user] != 0` (not just the per-epoch entry), or backfill `withdrawsRequestsByEpoch[_user][lastWithdrawRequest[_user]]` from `withdrawsRequests[_user]` during `_ensureDefaultRecoveryInitialized`/first post-upgrade request so every funded-or-haircut receipt is attributable to an epoch. Alternatively, make `_claimLossAdjustedWithdrawRequest` consult the epoch(s) that actually hold `lossRecoveryPriceByEpoch` rather than trusting `lastWithdrawRequest` as the sole pointer.
