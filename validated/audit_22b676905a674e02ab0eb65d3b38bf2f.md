### Title
Front-runnable `InitializeBuffer` instruction lets an attacker hijack buffer authority and steal rent lamports before the legitimate deployer's initialization lands - (File: `programs/bpf_loader/src/lib.rs`)

### Summary
The BPF Upgradeable Loader's program-buffer creation flow is split across two separate transactions: (1) `system_instruction::create_account` to allocate and assign the buffer account to `bpf_loader_upgradeable`, and (2) `UpgradeableLoaderInstruction::InitializeBuffer` to bind an authority to that account. The `InitializeBuffer` handler sets the buffer's `authority_address` from whatever pubkey is passed as instruction account #1, without requiring that account to sign. Any unprivileged transaction sender who observes the pending/confirmed `create_account` transaction can race the legitimate deployer's `InitializeBuffer` transaction, submitting their own `InitializeBuffer` naming themselves as authority first. This mirrors the reported bug class: a multi-step, non-atomic "deploy + initialize" pattern that a third party can intervene in to seize control before the legitimate owner initializes it.

### Finding Description
In `process_loader_upgradeable_instruction`, the `InitializeBuffer` arm only checks that the account state is `Uninitialized`, then unconditionally records whatever key is supplied as account #1 as the authority, with no signer requirement on that account: [1](#0-0) 

Because the buffer account was already created (owner = `bpf_loader_upgradeable`, state = `Uninitialized`) by a prior `system_instruction::create_account` transaction from the legitimate deployer, its address and existence are publicly visible on-chain/in the mempool before the deployer's own `InitializeBuffer` transaction lands. An attacker can submit a higher-priority `InitializeBuffer` transaction for that exact buffer pubkey, naming an address they control as the authority — no signature from that authority address is required by this instruction.

Once the attacker's transaction lands first, the account becomes `UpgradeableLoaderState::Buffer { authority_address: Some(attacker_key) }`. The deployer's legitimate `InitializeBuffer` transaction then fails with `AccountAlreadyInitialized`: [2](#0-1) 

The attacker, now holding the authority, can immediately issue `Close` on the buffer account. The `Close` handler for the `Buffer` state calls `common_close_account`, gated only on the stored `authority_address` matching and signing — which the attacker now satisfies — and transfers all lamports (the rent-exemption funds the legitimate deployer paid via `create_account`) to a recipient account the attacker controls: [3](#0-2) 

This results in concrete, unsigned fund movement: the deployer's lamports deposited into the buffer account for rent-exemption are stolen by a party who never signed the original `create_account` transaction and was never authorized by the deployer.

### Impact Explanation
Any account created and assigned to `bpf_loader_upgradeable` (buffer accounts used for program deploys and upgrades) is momentarily in an `Uninitialized` state after `create_account` and before `InitializeBuffer` executes. During that window, an unprivileged attacker who front-runs the `InitializeBuffer` call can seize authority over the account and drain its lamports via `Close`, without needing any signature from the deployer. This is a direct, unauthorized fund-theft vector reachable by any transaction sender monitoring the network for buffer-creation transactions (a routine step of every program deploy/upgrade via `solana program deploy`), since account pubkeys and owners are visible before the `InitializeBuffer` transaction confirms.

### Likelihood Explanation
Every program deployment and every upgrade using the standard `solana program deploy`/CLI flow performs `create_account` followed by a distinct `InitializeBuffer` transaction (confirmed by the CLI's `do_process_program_deploy`/`do_process_program_upgrade` flow, which separately provisions and initializes the buffer). This two-step, non-atomic pattern is used for essentially all program deployments on the network, making the race window a standard, frequently-recurring opportunity rather than a rare edge case. Exploitation only requires observing a `create_account` transaction targeting `bpf_loader_upgradeable::id()` and quickly submitting a competing `InitializeBuffer` with higher priority fee.

### Recommendation
Require the new authority account (#1) to be a signer in `InitializeBuffer`, closing the gap that currently allows anyone to claim authority over an uninitialized buffer account without proving control of the claimed authority key. Additionally/alternatively, encourage and support a single-instruction "create + initialize" buffer creation path (mirroring the `upgradeAndCall` recommendation from the original report) so buffer provisioning and authority binding happen atomically within one transaction, eliminating the race window entirely.

### Proof of Concept
1. Victim sends Tx A: `system_instruction::create_account(payer, buffer_pubkey, lamports, size, owner=bpf_loader_upgradeable::id())`, creating an `Uninitialized` buffer account.
2. Attacker observes Tx A (pending or just-confirmed) and immediately submits Tx B: `UpgradeableLoaderInstruction::InitializeBuffer` on `buffer_pubkey` with account #1 = `attacker_key` (no signature needed for `attacker_key`), using a higher priority fee to land before the victim's own `InitializeBuffer` transaction.
3. Tx B succeeds; buffer state becomes `Buffer { authority_address: Some(attacker_key) }`.
4. Victim's legitimate Tx C (`InitializeBuffer` naming their own authority) fails with `AccountAlreadyInitialized` (`programs/bpf_loader/src/lib.rs:162-165`).
5. Attacker submits Tx D: `UpgradeableLoaderInstruction::Close` on `buffer_pubkey`, signed by `attacker_key`, with a recipient account the attacker controls. `common_close_account` validates `attacker_key` as the stored authority and signer, then transfers all lamports (the rent-exemption funds paid by the victim in Tx A) to the attacker's recipient account (`programs/bpf_loader/src/lib.rs:710-716`).
6. Result: victim loses the lamports funded in Tx A with no recourse, and the attacker has stolen funds without ever signing the original account-creation transaction.
