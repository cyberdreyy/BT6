### Title
Stale-epoch instant-withdraw receipts pollute default accounting and claim at par after finalization - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks instant-withdraw receipts with two inconsistent keys: a global aggregate (`pendingInstantWithdraws`, `instantWithdrawsRequests[user]`) and a per-epoch map (`instantWithdrawClaimsByEpoch[epoch]`). The global bucket acts like a polluted prototype — leftover receipts from an older epoch flip the `pendingInstantWithdraws != 0` flag and contaminate default-recovery accounting for the current epoch, while `_claimDefaultedInstantWithdrawRequest` only clears the *default epoch's* per-user slice. A stale receipt therefore (a) dilutes the recovery price of every claimant and (b) is still paid out at par from funded-claim assets after finalization.

### Finding Description
In `requestInstantWithdraw` the strategy increments both the global `pendingInstantWithdraws` and `instantWithdrawClaimsByEpoch[epochNumber]` (lines 371-374). Funding arrives via `collectInstantWithdrawFunds`, which only decrements the global counter (lines 398-403); if the borrower under-funds or skips the instant queue, the receipt and the global counter survive indefinitely across epoch transitions, since nothing migrates `instantWithdrawClaimsByEpoch[N]` when `epochNumber` rolls to `N+1` in `deposit` (lines 607-610).

At default finalization three mismatches appear:

1. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` whenever the *global* `pendingInstantWithdraws != 0` (lines 644-648). A stale receipt from epoch N leaves the flag set, so the current epoch M's instant claims — which may already be fully funded — are wrongly added to the haircut basis, lowering `defaultRecoveryPrice` for all defaulted receipts and active LPs (lines 679-688).
2. `_defaultPrefundedInstantReserve` compares the stale global `pendingInstantWithdraws` against `instantWithdrawClaimsByEpoch[epochNumber]` (lines 716-723), miscomputing the prefunded reserve when the unfunded remainder belongs to a different epoch than the claim basis.
3. After finalization, `claimInstantWithdrawRequest` calls `_claimDefaultedInstantWithdrawRequest`, which clears only `instantWithdrawsRequestsByEpoch[user][defaultRecoveryEpoch]` (lines 843-847). The attacker's stale epoch-N slice remains in `instantWithdrawsRequests[user]` and is paid out 1:1 through `_transferFundedClaim` (lines 387-392, 897+), which deliberately bypasses `defaultRecoveryReserve` — so the stale receipt is redeemed at par from funded-claim assets that belong to other users.

No guard prevents this: `_ensureDefaultRecoveryInitialized` only sets a flag, `requestInstantWithdraw` has no stale-epoch check, and the honest manager/borrower sequence (partial instant funding, epoch roll, later default) is entirely routine.

### Impact Explanation
Direct theft plus recovery dilution. The attacker (any KYC-passing lender who requested an instant withdraw that was left unfunded) recovers their stale receipt at 100% instead of the recovery haircut, paid from funded-claim assets reserved for honest withdraw/instant claimants — insolvency of the funded-claim pool by up to the stale receipt amount. Simultaneously, the wrongly-included current-epoch instant basis lowers `defaultRecoveryPrice`, so every defaulted receipt holder and active LP claims less than entitled; the difference is socialized. Quantified loss ≈ stale receipt amount × (1 − recoveryPrice) stolen at par, plus basis-dilution loss proportional to the wrongly added `instantWithdrawClaimsByEpoch`.

### Likelihood Explanation
Requires: (1) an instant withdraw request left partially unfunded — possible whenever borrower cash returned at `startEpoch` covers only part of the queue, a scenario the code explicitly contemplates in the `defaultPendingClaimBasis` comment (lines 636-640); (2) the pool surviving to a later default — routine credit-vault operation. The attacker only needs to hold a pending instant receipt across an epoch boundary and wait, or can deliberately keep a small stale receipt alive knowing defaults eventually occur. No privileged cooperation needed.

### Recommendation
Key `pendingInstantWithdraws` per epoch or reconcile it at epoch rollover: when `epochNumber` increments, fold any still-unfunded instant basis into the new epoch's `instantWithdrawClaimsByEpoch` (or refund/expire it). Make `defaultPendingClaimBasis` include *all* outstanding instant basis, not just the current epoch's, and make `_claimDefaultedInstantWithdrawRequest` clear the user's full outstanding instant basis across epochs so stale receipts are haircut, not paid at par.

### Proof of Concept
Foundry fork PoC sketch (mirroring `test/foundry/IdleCreditVault.t.sol` default tests):

```solidity
// 1. Attacker deposits AA, calls cdoEpoch.requestInstantWithdraw(attackerAmount)
//    during the buffer of epoch N.
// 2. Borrower funds only part of the instant queue at startEpoch ->
//    pendingInstantWithdraws = attackerAmount (stale), epoch N completes normally.
// 3. Epoch N+1: honest user opens instant withdraw X; it is fully funded
//    via collectInstantWithdrawFunds -> pendingInstantWithdraws still = attackerAmount.
// 4. Borrower defaults; owner calls cdoEpoch.finalizeDefault(recovered, source).
//    defaultPendingClaimBasis() = pendingWithdraws
//      + instantWithdrawClaimsByEpoch[N+1]   // X wrongly added, triggered by stale flag
//    -> recoveryPrice lower than honest value.
// 5. Attacker calls cdoEpoch.claimInstantWithdrawRequest():
//    _claimDefaultedInstantWithdrawRequest clears only epoch N+1 slice (0 for attacker);
//    attacker then receives attackerAmount at par via _transferFundedClaim,
//    draining funded-claim underlying owed to honest users.
assertEq(strategy.defaultRecoveryPrice() < honestRecoveryPrice, true);
assertGt(underlying.balanceOf(attacker) - balPre, attackerAmount * recoveryPrice / 1e18);
```

Uncertainty note: I could not fully verify in the remaining iterations whether unfunded instant receipts can always survive an epoch transition (the CDO may force-fund them at `startEpoch` via `getInstantWithdrawFunds`); the PoC should confirm that `pendingInstantWithdraws` can remain non-zero across a `stopEpoch`/`deposit` rollover. If instant queues are always fully drained each epoch, the stale-flag precondition may not be reachable and the finding reduces to recovery-dilution only.
