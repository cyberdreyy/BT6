### Title
Claimed instant-withdraw receipts are never cleared from `instantWithdrawsRequestsByEpoch`, corrupting default-recovery accounting and permanently freezing recovery funds - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
The external bug class (heap buffer overflow in `BerEncoder_encodeOctetString`: writes past the intended buffer corrupt adjacent state) maps to an accounting-bounds violation in the queued/delayed withdrawal surface: `claimInstantWithdrawRequest` clears the aggregate receipt `instantWithdrawsRequests[_user]` but never clears the per-epoch records `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. That stale per-epoch "leftover" is later read by `defaultPendingClaimBasis` during `finalizeDefaultRecovery`, where it is counted a second time as defaulted claim basis. The consequences are a depressed `defaultRecoveryPrice` (all default claimants receive less), permanent locking of the excess reserve, and an arithmetic-underflow revert that permanently freezes the affected user's remaining instant receipts. [1](#0-0) 

### Finding Description
`requestInstantWithdraw` records both `instantWithdrawsRequests[_user]` and the per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` / `instantWithdrawClaimsByEpoch[currentEpoch]`. [2](#0-1)  The normal claim path burns the aggregate and zeroes it, but leaves the per-epoch entries untouched:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [3](#0-2) 

Attack sequence (attacker is a KYC-passing lender / tranche holder; borrower default is a normal protocol event, not attacker-caused):

1. Epoch N running, APR dropped below `lastEpochApr - instantWithdrawAprDelta` → attacker calls `requestWithdraw`, which routes to `creditVault.requestInstantWithdraw`. [4](#0-3) 
2. Borrower partially prefunds the instant queue via the honest `startEpoch`/`collectInstantWithdrawFunds` flow, so `instantBasis = instantWithdrawClaimsByEpoch[N] > pendingInstantWithdraws` — exactly the prefunded-reserve case `_defaultPrefundedInstantReserve` was built for. [5](#0-4) 
3. `allowInstantWithdraw` is true (pool requesting all funds / repaying), so the attacker calls `claimInstantWithdrawRequest` and is paid from the funded part. His `instantWithdrawsRequests` goes to 0, but `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` still hold the full amount.
4. The borrower then defaults on repayment; the honest manager calls `stopEpoch` → `_handleBorrowerDefault` and later `finalizeDefaultRecovery`. `defaultPendingClaimBasis` adds `instantWithdrawClaimsByEpoch[epochNumber]` (still containing the already-claimed amount) to `basis`. [6](#0-5) 
5. `recoveryPrice = reserveAmount * 1e18 / totalBasis` is computed over an inflated `totalBasis`, so every claimant's haircut is larger than warranted. [7](#0-6) 
6. When the attacker (who made any further same-epoch instant request, or whose leftover basis is now double-counted) tries `_claimDefaultedInstantWithdrawRequest`, `instantWithdrawsRequests[_user] -= claimBasis` underflows because `claimBasis` includes the already-claimed amount — the call permanently reverts. [8](#0-7) 

No existing guard stops this: `_transferFundedClaim` only protects `defaultRecoveryReserve`, `_ensureDefaultRecoveryInitialized` explicitly does not clear pending instant withdrawals, and nothing validates that per-epoch basis equals the live aggregate.

### Impact Explanation
Two direct, quantifiable harms:

- **Dilution / permanent locking of recovery funds**: `defaultRecoveryPrice` is divided by an inflated basis. The difference between the real recovery entitlement and paid claims remains in `defaultRecoveryReserve` forever — it can only be consumed by `_transferDefaultRecovery`, which is only reachable through claims priced at the depressed ratio. Locked amount ≈ the total prefunded-then-claimed instant receipts (potentially the full instant queue for that epoch).
- **Permanent freezing of user claims**: any user whose `instantWithdrawsRequestsByEpoch` exceeds their current `instantWithdrawsRequests` balance (because part was already claimed) hits a Solidity arithmetic underflow in `_claimDefaultedInstantWithdrawRequest` and can never claim the remainder — a permanent freeze of unclaimed yield/receipts.

This violates the "one receipt one payout" and solvency-conservation invariants of the withdrawal receipt system.

### Likelihood Explanation
Requires a specific but realistic sequence: instant withdrawals enabled (APR decrease), partial prefunding of the instant queue so some claims settle early, then a borrower default in the same epoch with `pendingInstantWithdraws != 0` at finalization so `defaultInstantWithdrawsFinalized` is set. Prefunded-instant accounting (`_defaultPrefundedInstantReserve`, `instantWithdrawClaimsByEpoch`) exists precisely because partial prefunding is an expected state, so the trigger conditions are within normal protocol operation. Likelihood is moderate; impact on recovery fairness and locked funds is high.

### Recommendation
In `claimInstantWithdrawRequest`, decrement `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount (tracking the request epoch, e.g. via a `lastInstantRequest` marker analogous to `lastWithdrawRequest`), so already-paid receipts cannot re-enter `defaultPendingClaimBasis`. Alternatively, make `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` derive the instant basis from the live aggregate rather than the uncleaned per-epoch total, and cap `_claimDefaultedInstantWithdrawRequest`'s `claimBasis` at `instantWithdrawsRequests[_user]` instead of reverting.

### Proof of Concept
Foundry fork PoC sketch (against `IdleCreditVault` + `IdleCDOEpochVariant` deployment on mainnet fork, per `foundry.toml`):

```solidity
function test_staleInstantBasisCorruptsRecovery() public {
    // 1. KYC'd attacker deposits AA, epoch starts with borrower draw.
    // 2. Manager lowers APR so requestWithdraw routes to requestInstantWithdraw.
    vm.prank(attacker);
    cdo.requestWithdraw(0, AA); // mints instant receipt, sets instantWithdrawClaimsByEpoch[N]

    // 3. Borrower prefunds instant queue via startEpoch transfer; attacker claims.
    vm.prank(attacker);
    cdo.claimInstantWithdrawRequest(); // paid; per-epoch entries NOT cleared

    uint256 staleBasis = vault.instantWithdrawClaimsByEpoch(epochN);
    assertGt(staleBasis, 0); // BUG: should be 0 after full claim

    // 4. Borrower defaults; manager finalizes recovery.
    vm.prank(manager); cdo.stopEpoch(...);        // _handleBorrowerDefault path
    vault.finalizeDefaultRecovery(recovered, source);

    // totalBasis includes staleBasis -> defaultRecoveryPrice depressed.
    // 5. Attacker's remaining same-epoch instant receipt reverts on claim
    //    (instantWithdrawsRequests[_user] -= claimBasis underflows),
    //    and the reserve surplus is permanently locked.
}
