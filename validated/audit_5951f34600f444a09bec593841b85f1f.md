### Title
Group-level rate limiter can be bypassed by issuing multiple borrow/withdraw actions before the off-chain settlement updates the counter - (File: `programs/marginfi/src/utils/general.rs`)

### Summary
The group-level USD rate limiter follows the same flawed pattern as the reported `QuestSystem.MaxCompletions` bug: an action's eligibility is checked against a limit-tracking counter that is only mutated later (at "settlement"/"completion" time), not at the moment the limited action is performed. This lets an unprivileged user perform the limited action repeatedly — bypassing the intended cap — before the counter catches up.

### Finding Description
`record_withdrawal_outflow` enforces the group-level rate limit purely as a **read-only** check against `group.rate_limiter`, and explicitly does **not** mutate the group account during user instructions: [1](#0-0) 

The group counter (`group.rate_limiter.hourly/daily.cur_window_outflow`) is only advanced later, out-of-band, when an admin/`delegate_flow_admin` calls `update_group_rate_limiter` with aggregated `outflow_usd`/`inflow_usd` from off-chain-collected `RateLimitFlowEvent`s: [2](#0-1) 

This is by design, and is documented as intentional to avoid making the group account `mut` (and thus serializing) on every user instruction: [3](#0-2) 

The test suite itself confirms and names this behavior "read-only during user instructions": multiple borrows/repays in sequence do not change the group's `cur_window_outflow` at all until an explicit admin update lands: [4](#0-3) 

This is structurally identical to the `QuestSystem._isQuestAvailable()` bug: the check (`accountData.completions[questId] >= questDef.maxCompletions` / `value.to_num::<i64>() > remaining`) is evaluated against a counter that is only incremented on "completion" (quest completion / admin settlement), not on "start" (quest start / user borrow-withdraw). Any number of qualifying actions performed before the counter is updated will each independently pass the same stale check.

### Impact Explanation
A user (or set of colluding users) can withdraw/borrow USD value from the group far in excess of the configured `groupHourly`/`groupDaily` rate limit by issuing many borrow/withdraw instructions (across many banks and/or many separate transactions) within the window before the off-chain worker calls `update_group_rate_limiter`. Per the guide, admin settlement happens only "at intervals" and the on-chain staleness bound is as high as 1500 slots (~10 minutes): [5](#0-4) 

During that entire window, every single borrow/withdraw is checked against the same unmutated `remaining` capacity, so the group-wide protection (whose stated purpose is to be "a defense if the risk workflow is abused or compromised") provides effectively no real-time bound on aggregate outflow — it only produces an after-the-fact accounting discrepancy once the admin update is applied and (retroactively) fails future actions. This defeats the core purpose of the group rate limiter as a circuit-breaker.

### Likelihood Explanation
Likelihood is high: this requires no privileged access, no oracle manipulation, and no unusual conditions — it is simply exploiting the intentional "read-only, settle-later" design by issuing more actions than intended within the settlement lag window, exactly as described in the analogous report ("starting the same quest multiple times before completing them").

### Recommendation
If the group-level rate limiter is meant to serve as a real-time circuit breaker (not just an accounting/alerting mechanism), either bound the maximum single-window exposure more tightly (e.g., require the group account to be touched/mutated per outflow instruction, accepting the serialization cost), or explicitly document/accept — as the `Proof of Play` team did for the analogous quest issue — that the group limiter is a delayed, eventual-consistency safeguard rather than a hard per-action cap, and size the bank-level (immediately-mutated) limits so that worst-case exposure during the admin-settlement lag is acceptable.

### Proof of Concept
1. Admin configures `groupHourly = 10` (USD) via `configure_group_rate_limits`, while leaving bank-level limits high/disabled, as in the existing test setup.
2. A user (or several colluding accounts) issues N separate `lending_account_borrow`/withdraw transactions (or a single transaction spanning multiple banks), each below the bank-level limit and each checked via `record_withdrawal_outflow` against the same, unmutated `group.rate_limiter.hourly.effective_remaining_capacity` (see `tests/specs/basic/17_rateLimiter.spec.ts:748-785`, which explicitly demonstrates the group counter stays at 0 across multiple borrows/repays).
3. Each of the N actions independently passes the `remaining` check and succeeds, so aggregate outflow = N × (limit), even though `groupHourly = 10`.
4. Only when the off-chain worker eventually calls `update_group_rate_limiter` does the counter reflect the true aggregate outflow — by which time the funds have already moved.

```rust
pub fn update_group_rate_limiter(
    ctx: Context<UpdateGroupRateLimiter>,
    outflow_usd: Option<u64>,
    inflow_usd: Option<u64>,
    update_seq: u64,
    event_start_slot: u64,
    event_end_slot: u64,
) -> MarginfiResult {
    let mut group = ctx.accounts.marginfi_group.load_mut()?;
    let clock = Clock::get()?;

    check!(
        outflow_usd.is_some() || inflow_usd.is_some(),
        MarginfiError::GroupRateLimiterUpdateEmpty
    );
    validate_event_slots(
        event_start_slot,
        event_end_slot,
        group.rate_limiter_last_admin_update_slot,
    )?;
    check!(
        event_end_slot <= clock.slot,
        MarginfiError::GroupRateLimiterUpdateFutureSlot
    );
    check!(
        clock.slot.saturating_sub(event_end_slot) <= MAX_RATE_LIMIT_UPDATE_LAG_SLOTS,
        MarginfiError::GroupRateLimiterUpdateStale
    );
    check!(
        update_seq == group.rate_limiter_last_admin_update_seq.saturating_add(1),
        MarginfiError::GroupRateLimiterUpdateOutOfOrderSeq
    );

    if let Some(inflow) = inflow_usd {
        check!(
            is_valid_rate_limit_amount(inflow),
            MarginfiError::InvalidConfig
        );
        group
            .rate_limiter
            .record_inflow(inflow, clock.unix_timestamp);
        msg!("Group rate limiter inflow recorded: {} USD", inflow);
    }

    if let Some(outflow) = outflow_usd {
        group
            .rate_limiter
            .try_record_outflow(outflow, clock.unix_timestamp)?;
        msg!("Group rate limiter outflow recorded: {} USD", outflow);
    }
```

```markdown
## Why These Flows Exist

Both systems avoid making the group account writable in every user transaction.

- Bank-level rate limiting is updated inline because the bank account is already writable.
- Group-level rate limiting is checked read-only during user actions, then settled later from
  aggregated events.
- Deleverage withdraw limits are also checked read-only during the withdraw, then settled later from
  aggregated events.

This avoids serializing all activity in a group through one writable group account.
```
