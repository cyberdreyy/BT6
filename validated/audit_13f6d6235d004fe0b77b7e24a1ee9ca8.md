### Title
Loss of the equivocation guard on signer restart due to un-reconciled local SignerDb state - (File: `stacks-signer/src/signerdb.rs`, `stacks-signer/src/v0/signer.rs`)

### Summary
The double-signing ("equivocation") guard that stops a signer from placing a signature on two conflicting sibling blocks at the same Stacks height is derived *exclusively* from the local SignerDb sqlite `blocks` table via `SignerDb::get_signed_conflicts`. Unlike the miner-view/state-machine (`StateMachineUpdate`), which is replicated over StackerDB and can be reloaded on startup even after the local DB is wiped, the record of "I previously signed block X at height H" has no external source of truth. If a signer's local database is lost or reset independently of the rest of the network (disk failure, backup restore, migration reset, or an operator resetting the working directory), the signer resumes with a fully empty conflict set and can re-sign a genuinely conflicting sibling block, breaking the "signer never signs two blocks at the same height" invariant the guard exists to enforce.

### Finding Description
`SignerDb::get_signed_conflicts` is the sole mechanism used to detect "a block I (or the observed group) already signed exists at or above this height, in any tenure": [1](#0-0) 

The design explicitly states this fact is *never* independently reconstructed — it is derived once from local storage and only cleared by staleness or node-derived death, not restored from any other party: [2](#0-1) 

This query result directly gates whether the signer proceeds to sign at the pre-commit threshold, in `handle_block_pre_commit`: [3](#0-2) 

Compare this to the separate miner-viewpoint state machine, which *is* durable across a lost local database: it can be reconstructed from `StateMachineUpdate` messages that peers gossip over StackerDB, as demonstrated by the `signer_loads_stackerdb_updates_on_startup` test, whose second phase explicitly clears the local DB/state-machine records and then verifies the signer recovers its miner-viewpoint from other signers' StackerDB slots before signing again: [4](#0-3) 

No equivalent recovery path exists for the `blocks` table (and hence `get_signed_conflicts`): a signature a signer previously placed over a block is not gossip-replicated back into the local `blocks` table on start-up; it is only known to have been broadcast as a `BlockResponse` at the time, and other signers' copies of that acceptance are not consulted to reconstruct *this* signer's own conflict history. If the local database that backs `get_signed_conflicts` is lost, the guard silently starts from an empty set: any future sibling proposal at a height this signer already endorsed will pass `handle_block_pre_commit`'s conflict check with an empty conflicts vector and be signed, exactly the double-sign scenario the guard exists to prevent (see the `own-tenure`/`fresh conflict` tests that this guard is meant to satisfy): [5](#0-4) 

### Impact Explanation
This is the "High - a signer ... losing the equivocation guard on restart" category. A one-slot miner (plus normal gossip) does not even need to actively exploit anything beyond timing: it only needs to propose a genuinely conflicting sibling block after the signer's local conflict history has been reset. The signer would then sign a second, conflicting block at a height it already signed, which is precisely the double-sign the pre-commit conflict guard (section 5 of `docs/signer-flows.md`) is designed to make impossible.

### Likelihood Explanation
The likelihood requires the signer operator's local storage to be reset/lost independently of the network state (e.g., crash before fsync, restoring an out-of-date backup, redeploying with a fresh data directory, or a botched migration) while its previously-signed block height is still live/contestable on the network. This is an operational hazard rather than something a remote attacker can trigger directly, so likelihood is low, but the consequence — an unreconciled equivocation guard — is a genuine gap between the design intent ("a signature is a bearer instrument ... only staleness or node-derived death ... clears a conflict") and what is actually recoverable after local storage loss.

### Recommendation
Treat the signed-block/conflict history the same way the miner-view state machine is treated: reconcile it against externally observable facts on startup (e.g., derive "I signed at height H in tenure T" from the node's canonical chain state / already-broadcast `BlockResponse` gossip still present in StackerDB, or refuse to resume signing until such reconciliation succeeds) instead of trusting the local `blocks` table as the sole and unverified source of truth for `get_signed_conflicts`.

### Proof of Concept
1. Signer S signs block A at height H in tenure T1 (`mark_locally_accepted`, recorded only in S's local `blocks` table via `SignerDb::insert_block`).
2. S's local SignerDB is lost/reset (disk issue, backup restore, redeploy) while block A/T1 is still contestable (not yet stale, not yet globally accepted+reorged away per `conflict_still_blocks`).
3. S restarts. `get_signed_conflicts` at height H now returns an empty vector because the `blocks` table has no record of block A.
4. A miner proposes conflicting sibling block B at height H in tenure T2; it passes normal proposal validation (`check_proposal`), reaches the 70% pre-commit threshold, and `handle_block_pre_commit` finds `conflicts.is_empty()`, so S signs B — even though block A at the same height was previously signed by S and may still be live on the network.

    pub fn get_signed_conflicts(
        &self,
        height: u64,
        excluded_signer_signature_hash: &Sha512Trunc256Sum,
    ) -> Result<Vec<SignedConflictInfo>, DBError> {
        let query = "SELECT b.consensus_hash, b.signer_signature_hash, b.stacks_height, b.state,
                MAX(COALESCE(b.signed_self, 0), COALESCE(b.signed_group, 0)) AS last_endorsed,
                st.superseded_by_consensus_hash, st.superseded_by_burn_block_hash
            FROM blocks b
            LEFT JOIN superseded_tenures st ON st.consensus_hash = b.consensus_hash
            WHERE (b.signed_self IS NOT NULL OR b.signed_group IS NOT NULL)
                AND b.stacks_height >= ?1
                AND b.signer_signature_hash != ?2
            ORDER BY b.stacks_height DESC";
        let args = params![
            u64_to_sql(height)?,
            excluded_signer_signature_hash.to_string(),
        ];
        query_rows(&self.db, query, args)
    }
