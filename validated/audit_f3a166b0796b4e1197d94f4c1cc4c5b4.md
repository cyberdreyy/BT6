### Title
Builder payment quorum bypass on payment eviction — funds settle without attester quorum - ([File: specs/gloas/beacon-chain.md])

### Summary
In `apply_parent_execution_payload`, when a parent block's builder payment entry has aged out of the `builder_pending_payments` window (more than one epoch old), the fallback path unconditionally appends a `BuilderPendingWithdrawal` for the builder's bid value — bypassing the attester-quorum check (`weight >= quorum`) that normally gates whether a builder payment is settled.

### Finding Description
Builder payments are normally only realized (moved to `builder_pending_withdrawals`, i.e. money actually leaving the builder's balance) if a quorum of PTC/attester weight confirms payload availability. This is enforced in `process_builder_pending_payments`: [1](#0-0) 
```python
def process_builder_pending_payments(state: BeaconState) -> None:
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)
    ...
```
i.e., a payment must accumulate `weight >= quorum` (from `process_attestation`) before the withdrawal is created; otherwise it is silently dropped with no withdrawal (the fee is *not* charged to the builder).

However, `apply_parent_execution_payload` — invoked when a later block's `process_parent_execution_payload` finally applies a FULL parent payload whose commitment slot is now more than one epoch old — takes a different path: [2](#0-1) 
```python
    # Settle the builder payment
    if parent_epoch == get_current_epoch(state):
        payment_index = SLOTS_PER_EPOCH + parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_epoch == get_previous_epoch(state):
        payment_index = parent_slot % SLOTS_PER_EPOCH
        settle_builder_payment(state, payment_index)
    elif parent_bid.value > 0:
        # Parent is older than the previous epoch, its payment entry has been
        # evicted from builder_pending_payments. Append the withdrawal directly.
        state.builder_pending_withdrawals.append(
            BuilderPendingWithdrawal(
                fee_recipient=parent_bid.fee_recipient,
                amount=parent_bid.value,
                builder_index=parent_bid.builder_index,
            )
        )
```
The third branch (`elif parent_bid.value > 0`) is only reached because the pending-payment slot storing `weight` has already been overwritten/rotated by two epoch boundaries of `process_builder_pending_payments` (as documented in the code comment "its payment entry has been evicted"). At that point the original `weight` information (whether attesters ever reached quorum for that payload) is gone, and the code substitutes an unconditional charge based solely on `parent_bid.value`, i.e. it pays the builder's committed bid regardless of whether quorum was ever reached.

This is confirmed by the accompanying test, whose comment explicitly documents the divergence in behavior: [3](#0-2) 
```python
    # Build Block 2 with 2+ epochs of missed slots. During the slot advancement,
    # process_builder_pending_payments runs at each epoch boundary:
    #   1st boundary: shifts payment from second half to first half
    #   2nd boundary: checks quorum on first half — weight 0 < quorum → evicted
    # When Block 2 is processed, parent is FULL so apply_parent_execution_payload
    # runs. Since parent_epoch is older than previous_epoch, payment_index is None.
    # The fix creates the withdrawal directly from the bid in this case.
```
The test itself sets weight to `0` (no attestation participation) for the payment, and asserts that the builder is nonetheless charged the full bid `value`: [4](#0-3) 
```python
    # Verify apply_parent_execution_payload actually ran (parent was FULL)
    parent_slot_index = bid.slot % spec.SLOTS_PER_HISTORICAL_ROOT
    assert state.execution_payload_availability[parent_slot_index]

    # Verify the builder was charged — balance decreased by the bid value
    assert state.builders[builder_index].balance == pre_builder_balance - value
```
This is the exact equality break requested by the scan rules: "a builder payment ... doubled" / "a payment applied that the block did not commit to" — here a payment is applied (Gwei moved from builder to `fee_recipient`) that the attesting committee explicitly did *not* commit to via quorum (`weight == 0 < quorum`), simply because the payment record aged past the 2-epoch tracking window before the parent payload was actually included/applied.

### Impact Explanation
This breaks the invariant that builder payments require quorum-confirmed payload delivery before Gwei moves. A validator/proposer chain that misses 2+ epochs of slots before finally including a previously-bid-but-unattested parent payload will cause the builder to be charged their full bid value unconditionally — even though no committee ever attested that the payload was actually available/delivered. Conversely, for the fee_recipient (proposer or configured recipient) this results in a payment being credited that the network's attestation-based consensus never approved. This is a Gwei-movement rule (payment application) diverging from the quorum-gated rule enforced everywhere else in the spec, i.e., "a payment applied that the block did not commit to" via quorum consensus. It can be triggered purely by chain conditions (a run of missed/empty slots) rather than by direct attacker action, so it is a protocol-level consensus inconsistency rather than an economic attack requiring stake.

### Likelihood Explanation
Requires two consecutive epoch boundaries of the parent payload's payment record aging out of the tracking window (`builder_pending_payments`, sized `2 * SLOTS_PER_EPOCH`) before the corresponding FULL parent is finally applied — i.e., a run of 2+ epochs of missed/skipped slots following a builder-bid block, followed by that block's payload finally being surfaced as the "parent" of a later block. Long sequences of missed slots are a realistic (if not everyday) liveness condition on Ethereum, making this reachable without any malicious coalition, purely through timing/network conditions already covered by the spec's own regression test.

### Recommendation
Preserve the accumulated `weight` for a payment even after it rotates out of the live `builder_pending_payments` window (e.g., retain the last known weight value in `state.latest_execution_payload_bid`/a small side record, or extend the window), and gate the eviction fallback in `apply_parent_execution_payload` on `weight >= quorum` rather than unconditionally appending a withdrawal whenever `parent_bid.value > 0`. If quorum was never reached, the fallback should discard the payment (consistent with `process_builder_pending_payments`) rather than force-settling it.

### Proof of Concept
1. Builder submits a bid with `value > 0` for block `N`; block `N` is included, creating a `BuilderPendingPayment` with `weight = 0`.
2. No PTC/attester participation ever reaches quorum for the slot of block `N` (or attesters simply never vote high enough weight).
3. Chain proceeds through 2 full epoch boundaries without processing the parent of block `N` (e.g., due to missed slots after `N`), causing `process_builder_pending_payments` to rotate the entry out with `weight (0) < quorum`, discarding it (as demonstrated in `test_process_builder_pending_payments_below_quorum`).
4. A later block finally includes block `N`'s payload as its "parent" (`process_parent_execution_payload` → `apply_parent_execution_payload`), with `parent_epoch` now older than `get_previous_epoch(state)`.
5. The `elif parent_bid.value > 0` branch unconditionally appends a `BuilderPendingWithdrawal` for the builder's original bid `value`, and this withdrawal is later executed in `apply_withdrawals`, deducting `value` from the builder's balance and paying `fee_recipient` — despite step 3 already having determined (via quorum) that this payment should not be settled.
This exact flow is reproduced by `test_builder_payment_after_missed_epochs` in `tests/core/pyspec/eth_consensus_specs/test/gloas/sanity/test_blocks.py`, which explicitly asserts the builder is charged even with `weight = 0`.

def process_builder_pending_payments(state: BeaconState) -> None:
    """
    Processes the builder pending payments from the previous epoch.
    """
    quorum = get_builder_payment_quorum_threshold(state)
    for payment in state.builder_pending_payments[:SLOTS_PER_EPOCH]:
        if payment.weight >= quorum:
            state.builder_pending_withdrawals.append(payment.withdrawal)

    old_payments = state.builder_pending_payments[SLOTS_PER_EPOCH:]
    state.builder_pending_payments[:SLOTS_PER_EPOCH] = old_payments
    new_payments = [BuilderPendingPayment.empty() for _ in range(SLOTS_PER_EPOCH)]
    state.builder_pending_payments[SLOTS_PER_EPOCH:] = new_payments
