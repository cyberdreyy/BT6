### Title
JWT jti replay check and recordUsage are non-atomic, allowing a single JWT to authorize two concurrent trigger executions - ([File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go])

### Summary
`WorkflowMetadataHandler.Authorize` calls `jwtCache.isReplay(claims.ID)` and, after signer/authorization checks, calls `jwtCache.recordUsage(claims.ID)` as two separate, independently-locked operations rather than a single atomic check-and-set. Two concurrent `Authorize` calls using the same valid JWT can both pass `isReplay` before either has executed `recordUsage`, letting a single-use JWT authorize two distinct executions.

### Finding Description
`Authorize` verifies the JWT, then checks replay status and finally records usage as three separate steps: [1](#0-0) 

`isReplay` takes an `RLock`, checks map membership, and releases the lock; `recordUsage` takes a separate `Lock` later to insert the jti: [2](#0-1) 

Because these are two distinct critical sections with unrelated work (map lookups on `h.authorizedKeys`, signer comparison) happening in between, there is a TOCTOU (time-of-check-to-time-of-use) window. If two goroutines call `Authorize(workflowID, sameToken, req)` concurrently:
1. Goroutine A calls `isReplay(jti)` → false (not yet recorded).
2. Goroutine B calls `isReplay(jti)` → false (A hasn't called `recordUsage` yet).
3. Both proceed through the authorized-keys/signer check (both succeed, since it's the same valid signer).
4. Both call `recordUsage(jti)` — this is idempotent (just overwrites the map entry) and returns no error, so it does not retroactively reject either call.
5. Both `Authorize` calls return success with `&key, nil`.

No middleware, mutex, or per-jti serialization exists elsewhere in the file to prevent this; `h.mu` guards only `authorizedKeys`/`workflowIDToRef`/`workflowShards` state, not the `jwtCache`. The call site in `http_trigger_handler.go` invokes `Authorize` per incoming gateway request without any additional single-flight/dedup mechanism visible in this file.

### Impact Explanation
This breaks authentication soundness for the gateway's JWT-based external-caller authorization used to trigger workflow executions. A holder of one valid signed JWT (a run-role external caller, not an operator) can double-spend it to trigger two workflow executions concurrently instead of one, bypassing the single-use invariant the replay cache is meant to enforce. This maps to Chainlink's "unauthorized job run" / authentication bypass impact class — an attacker gets extra unauthorized executions from a credential meant to be single-use.

### Likelihood Explanation
Preconditions are minimal: attacker only needs one valid signed JWT for a workflow (something an authorized run-role caller normally possesses to trigger the workflow once). The race window is realistic in a network-facing gateway handling concurrent HTTP requests — firing two nearly-simultaneous requests with the same token is trivial for any external caller and requires no special timing precision beyond ordinary network jitter. It's fully repeatable and doesn't depend on gateway internals beyond normal concurrent request handling.

### Recommendation
Make the replay check-and-record atomic under a single lock, e.g. add a `checkAndRecord(jti) (alreadyUsed bool)` method on `jwtReplayCache` that holds `cache.mu.Lock()` for the entire duration: check for existence, and if absent, insert immediately, returning whether it was already present. Call this single atomic method in place of `isReplay` + `recordUsage`, ideally as the very first step of `Authorize` (before the signer/authorized-keys checks) so an attacker can't extend the race window by causing extra work between the check and the record.

### Proof of Concept
```go
func TestAuthorize_ConcurrentReplaySameJTI(t *testing.T) {
    h := newTestWorkflowMetadataHandler(t) // helper constructing handler w/ jwtCache + authorizedKeys populated
    workflowID := "workflow-1"
    token, req := buildValidSignedJWT(t, workflowID) // same jti in both goroutines

    var wg sync.WaitGroup
    results := make([]error, 2)
    wg.Add(2)
    for i := 0; i < 2; i++ {
        i := i
        go func() {
            defer wg.Done()
            _, err := h.Authorize(workflowID, token, req)
            results[i] = err
        }()
    }
    wg.Wait()

    successCount := 0
    for _, err := range results {
        if err == nil {
            successCount++
        }
    }
    // Expect exactly one success; test fails today because both can succeed.
    assert.Equal(t, 1, successCount, "JWT with identical jti was accepted more than once")
}
```
Run with `-race` and repeated iterations (e.g., wrap in a loop) to reliably surface the TOCTOU window given `isReplay`/`recordUsage` are independently locked.

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
