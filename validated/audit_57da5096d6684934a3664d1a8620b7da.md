### Title
Race condition in WebAuthn registration challenge store allows attacker to substitute their own security key for the victim's during MFA enrollment - ([File: core/sessions/webauthn.go])

### Summary
`WebAuthnSessionStore.take()` deletes the in-progress registration challenge on first read and is called exactly once via `GetWebauthnSession` inside `FinishWebAuthnRegistration`. Because the challenge is keyed only by `user.Email + "-registration"` and consumed on a first-read basis with no binding to the specific HTTP request/response pair that will finish it, an attacker holding (or racing against) the victim's authenticated session can send a competing `POST /webauthn/register/finish` request with their own attestation response and "win" the race, causing their own device to be enrolled as a valid MFA credential on the victim's account.

### Finding Description
`BeginWebAuthnRegistration` stores the challenge under a deterministic key (`user.Email + "-registration"`) via `store.SaveWebauthnSession` [1](#0-0) . `FinishWebAuthnRegistration` retrieves and deletes that same key via `store.GetWebauthnSession(userRegistrationIndexKey)` [2](#0-1) , which internally calls `take()`, a single-consumer, delete-on-read primitive with no correlation to which specific HTTP request is entitled to consume it [3](#0-2) [4](#0-3) .

The `WebAuthnController.FinishRegistration` handler only requires the requester to be authenticated as `user` (via `auth.GetAuthenticatedUser(c)`) — it does not verify that the specific attestation response corresponds to the browser/device that received the specific `CredentialCreation` options from `BeginRegistration` [5](#0-4) . Because the challenge/session data is looked up purely by email and consumed by whichever request calls `take()` first, if two requests carrying valid attestation responses for the same session race to `POST /webauthn/register/finish`, only the first is validated against the stored `sessionData`; the second gets `"assertion not in challenge store"` and fails.

If an attacker has obtained the victim's session cookie (e.g. via XSS, malware, or a shared/stolen cookie) and the victim is in the process of registering a new WebAuthn key, the attacker can pre-generate their own attestation response (registering their own physical key against the RP as an unauthenticated ceremony is possible because the WebAuthn challenge itself, once leaked from the DOM/JS response of `BeginRegistration`, could be reused) and race the finish call. If the attacker's forged response validates first, `AddCredentialToUser` persists the attacker's public key credential as a legitimate 2FA credential tied to the victim's account, while the victim's own `FinishRegistration` request fails with the store-consumed error [6](#0-5) .

### Impact Explanation
This allows an attacker who already possesses a stolen/shared session cookie to silently plant a persistent, attacker-controlled MFA credential (WebAuthn key) on the victim's account. This is a credential-persistence/backdoor: even if the victim later rotates their password or the leaked session expires, the attacker's registered security key remains valid for subsequent logins (`FinishWebAuthnLogin`/`ValidateLogin`), giving the attacker durable authenticated access to the account. This matches the "unauthorized action on another user's job/subscription/secret" / credential-persistence impact class.

### Likelihood Explanation
Exploitation requires the attacker to already have obtained the victim's session cookie (via session theft, XSS, or a shared session) and requires winning a race against the legitimate `FinishRegistration` call while the victim is actively enrolling a new key — a narrow timing window. Because the precondition (stolen/shared session) already grants the attacker broad account access, the marginal value of this bug is establishing durable, MFA-bypassing persistence rather than initial compromise. Likelihood is low-to-moderate given the race-window constraint but is deterministic once the precondition and timing are met, since `take()` provides no per-request binding beyond "first reader wins."

### Recommendation
Bind the stored challenge to more than the user's email — e.g., include a per-ceremony random nonce issued to the specific `BeginRegistration` response and required to be echoed back to `FinishRegistration` (or scoped to the specific session/cookie ID) so `take()`'s single-consumer semantics also verify requester identity for that specific ceremony instance, not just "first successful attestation wins." Additionally, invalidate/rotate in-progress registration challenges when a new `BeginWebAuthnRegistration` is issued for the same user, and consider requiring re-authentication (password/step-up) immediately before `FinishRegistration` to reduce the value of a stolen session cookie for this flow.

### Proof of Concept
Go unit test plan in `core/sessions/webauthn_test.go`:
1. Call `BeginWebAuthnRegistration` for user "victim@example.com", capturing `options` and confirming the session is stored under `victim@example.com-registration`.
2. Construct two `*http.Request` values: one with the victim's genuine `CredentialCreationResponse` body, one with an attacker-controlled forged `CredentialCreationResponse` body (using a different WebAuthn keypair), both targeting the same session store instance.
3. Fire both into `FinishWebAuthnRegistration` concurrently (e.g., via goroutines with a `sync.WaitGroup` and a barrier channel to maximize race probability), and assert:
   - Only one call succeeds (returns non-nil `*webauthn.Credential`, nil error).
   - The other call fails with `"assertion not in challenge store"`.
   - Additionally assert that the store's internal map no longer contains the key after both calls (single-consumer semantics of `take()`).
4. Extend the test to show that when the attacker's forged response wins the race, `AddCredentialToUser` would persist the attacker's `PublicKeyData` under the victim's email — demonstrating cross-user credential substitution.

// take returns the val for key, as well as removing it.
func (store *WebAuthnSessionStore) take(key string) (val string, ok bool) {
	store.mu.Lock()
	defer store.mu.Unlock()
	val, ok = store.inProgressRegistrations[key]
	if ok {
		delete(store.inProgressRegistrations, key)
	}
	return
}
```

// GetWebauthnSession unmarshals and returns the webauthn session information
// from the session cookie, which is removed.
func (store *WebAuthnSessionStore) GetWebauthnSession(key string) (data webauthn.SessionData, err error) {
	assertion, ok := store.take(key)
	if !ok {
		err = pkgerrors.New("assertion not in challenge store")
		return
	}
	err = json.Unmarshal([]byte(assertion), &data)
	return
}

func (w *WebAuthnController) FinishRegistration(c *gin.Context) {
	ctx := c.Request.Context()
	user, ok := auth.GetAuthenticatedUser(c)
	if !ok {
		logger.Sugared(w.App.GetLogger()).AssumptionViolationf("failed to obtain current user from context")
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	orm := w.App.AuthenticationProvider()
	uwas, err := orm.GetUserWebAuthn(ctx, user.Email)
	if err != nil {
		w.App.GetLogger().Errorf("failed to obtain current user MFA tokens: error in GetUserWebAuthn: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("unable to register key"))
		return
	}

	webAuthnConfig := w.App.GetWebAuthnConfiguration()

	credential, err := w.inProgressRegistrationsStore.FinishWebAuthnRegistration(*user, uwas, c.Request, webAuthnConfig)
	if err != nil {
		w.App.GetLogger().Errorf("error in FinishWebAuthnRegistration: %s", err)
		jsonAPIError(c, http.StatusBadRequest, errors.New("registration was unsuccessful"))
		return
	}

	if sessions.AddCredentialToUser(ctx, w.App.AuthenticationProvider(), user.Email, credential) != nil {
		w.App.GetLogger().Errorf("Could not save WebAuthn credential to DB for user: %s", user.Email)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}
```
