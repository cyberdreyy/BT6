### Title
Internal `writeMethodsEnabled.AllowErr` errors are echoed verbatim to the vault write-method caller - ([File: core/services/gateway/handlers/vault/handler.go])

### Summary
In `handleSecretsCreate`, `handleSecretsUpdate`, and `handleSecretsDelete`, when `h.writeMethodsEnabled.AllowErr(ctx)` returns a non-`ErrorNotAllowed` error (the "fatal"/unexpected branch), the handler wraps the raw error with `"error checking if write methods are enabled: "+err.Error()` and sends it straight to the requester as the JSON-RPC error message via `h.errorResponse(..., api.FatalError, ...)`. Because the `api.FatalError` case in `errorResponse` performs no redaction (unlike `api.NodeReponseEncodingError`, which explicitly replaces the message), whatever internal error text the `limits.GateLimiter` backend (settings/feature-flag service, DB, etc.) produces is returned unmodified to the caller.

### Finding Description
The reachable path is: an authorized vault caller (any workflow owner/API-token holder whose request passes `h.requestProcessor.ProcessRequest`) sends a `secrets.create`/`secrets.update`/`secrets.delete` JSON-RPC request through the gateway. `HandleJSONRPCUserMessage` dispatches to `handleSecretsCreate` [1](#0-0) , which calls the gate limiter: [2](#0-1) 

If `AllowErr` returns an error that is not `limits.ErrorNotAllowed{}` (e.g., a settings-service/DB lookup failure inside the `limits.GateLimiter` implementation), the code takes the `else if err != nil` branch and constructs a new error whose text is `"error checking if write methods are enabled: " + err.Error()`, then routes it through `h.errorResponse(..., api.FatalError, ...)`. In `errorResponse`, the `api.FatalError` case is an empty `case` with no sanitization [3](#0-2) , so the error string (including the wrapped internal error) is placed directly into the JSON-RPC response body via `h.codec.EncodeNewErrorResponse(...)` [4](#0-3)  and returned to the caller as `RawResponse`.

This is inconsistent with the codebase's own established pattern for handling unexpected gate errors: elsewhere (`gateAllows` in `core/services/ocr2/plugins/vault/plugin_utils.go`) unexpected gate errors are logged internally and never surfaced to the caller [5](#0-4) , and the `NodeReponseEncodingError` branch in the same `errorResponse` function intentionally strips the underlying error text before returning it to the user [6](#0-5) . The `handleSecretsCreate`/`Update`/`Delete` fatal-error branches lack this same redaction.

### Impact Explanation
An authorized-but-unprivileged vault write caller can trigger disclosure of internal error text originating from the settings/feature-flag backend that backs `limits.GateLimiter` (e.g. connectivity errors, backend-specific messages) whenever that backend misbehaves. This matches a low-severity "information disclosure aiding further attacks" class: it does not by itself grant privilege escalation or secret disclosure, but it can leak internal architecture/implementation detail to a requester who should only ever see generic, sanitized error responses (as intended for `FatalError`).

### Likelihood Explanation
Exploitability depends entirely on the `limits.GateLimiter` backend for `GatewayVaultManagementEnabled` returning an error other than `ErrorNotAllowed` — this normally requires an internal fault (e.g., settings-service outage or misbehavior), which is not attacker-controlled. The caller only needs to be an already-authorized vault requester (a normal workflow owner/API-token holder) sending a standard `secrets.create`/`update`/`delete` request during such a backend fault; no additional privilege is required beyond ordinary vault write authorization.

### Recommendation
In the fatal-error branches of `handleSecretsCreate`, `handleSecretsUpdate`, and `handleSecretsDelete`, log the underlying error via `l.Errorw(...)` (as already done) but return a generic, sanitized message to the caller instead of embedding `err.Error()`, e.g. `errors.New("internal error checking write method availability")`, consistent with the `api.NodeReponseEncodingError` redaction pattern in `errorResponse`.

### Proof of Concept
1. Construct a `handler` via `newHandlerWithAuthorizer` (or equivalent test constructor) with a mocked `limits.GateLimiter` for `writeMethodsEnabled` whose `AllowErr(ctx)` returns a custom internal error, e.g. `errors.New("settings backend: connection refused to internal-db-host:5432")` (not wrapping `limits.ErrorNotAllowed{}`).
2. Call `handler.HandleJSONRPCUserMessage` (or directly `handleSecretsCreate`) with a valid authorized `secrets.create` request and a fake `Callback`/`activeRequest`.
3. Capture the `gwhandlers.UserCallbackPayload.RawResponse` returned via the callback.
4. Assert that `RawResponse`'s error message contains the literal mock string `"connection refused to internal-db-host:5432"` — demonstrating the internal error text leaks to the caller instead of a generic `FatalError`-style message.
5. Assert `ErrorCode == api.FatalError` to confirm this is the intended "sanitized" branch that should not contain raw backend detail.

// gateAllows reports whether the given CRE gate allows the gated behavior.
// When evaluation errors for reasons other than ErrorNotAllowed, it logs an error and returns false.
func gateAllows(ctx context.Context, lggr logger.Logger, gate limits.GateLimiter, gateName string) bool {
	err := gate.AllowErr(ctx)
	if err == nil {
		return true
	}
	if errors.Is(err, limits.ErrorNotAllowed{}) {
		return false
	}
	lggr.Errorw("unexpected error evaluating CRE gate", "gate", gateName, "error", err)
	return false
}
