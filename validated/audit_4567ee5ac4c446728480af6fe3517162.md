### Title
Illiquid-vault revert inside `onStopEpoch` permanently blocks `stopEpoch` and freezes LP funds - ([File: contracts/strategies/idle/ProgrammableBorrower.sol](contracts/strategies/idle/ProgrammableBorrower.sol))

### Summary
The f2fs bug is a blocking/sleepable operation invoked from a context that cannot tolerate blocking (softirq → `schedule()`). The closest credit-vault analog is `ProgrammableBorrower.onStopEpoch`, which executes a failable, liquidity-dependent external `vault.withdraw()` inside the single atomic `stopEpoch` transition of `IdleCDOEpochVariant`. When the ERC4626 sleeve is *nominally* solvent (`convertToAssets` covers the shortfall) but *cash-illiquid*, the withdrawal reverts and the hook reverts with `StopEpochVaultLiquidityUnavailable`, aborting the whole `stopEpoch`. The epoch cannot transition to "stopped", so no withdraw request can be funded or claimed, until the external vault regains liquidity — a condition an unprivileged vault user can force.

### Finding Description
`onStopEpoch` is called synchronously by `IdleCDOEpochVariant.stopEpoch` before the CDO pulls funds via `transferFrom`. Inside it, at lines 240-254:

```solidity
uint256 onHand = underlyingToken.balanceOf(address(this));
if (_amountRequired > onHand) {
  uint256 shortfall = _amountRequired - onHand;
  if (shortfall > _currentVaultAssets()) return true;
  try vault.withdraw(shortfall, address(this), address(this)) returns (uint256 shares) {
    ...
  } catch {
    revert StopEpochVaultLiquidityUnavailable();
  }
}
```

The intent (per the comment) is that only an "otherwise-covered" withdrawal failure should make `stopEpoch` retryable, while an uncovered position falls through to the CDO's `transferFrom` failure → default path. The flaw: `_currentVaultAssets()` uses `vault.convertToAssets(shares)`, which values shares at the vault's *accounting* price, not its *redeemable cash*. For ERC4626 lending-style vaults (Morpho/Idle-style, Euler, etc.), `totalAssets` includes lent-out or locked funds, so `convertToAssets` can report full coverage while `maxWithdraw`/`withdraw` reverts due to zero idle liquidity. In that state:

- `shortfall > _currentVaultAssets()` is false → the hook attempts `vault.withdraw` → it reverts → `StopEpochVaultLiquidityUnavailable` propagates → `stopEpoch` reverts.
- Epoch stays `isEpochRunning == true`. `epochNumber` is never bumped, `collectWithdrawFunds`/`collectInstantWithdrawFunds` are never invoked, and `_claimFundedWithdrawRequest` keeps reverting on `epochNumber <= lastWithdrawRequest[_user]` (`IdleCreditVault.sol:326-328`), so every pending withdrawer is frozen.
- The escape hatch `emergencyExitVault` also calls `vault.redeem`, which fails for the same liquidity reason, and `setVault` is gated on `vault.balanceOf(address(this)) == 0`, so there is no way to route around the illiquid sleeve while accounting is active.

This mirrors the f2fs bug class exactly: a recoverable asynchronous failure (vault illiquidity) is raised inside a non-deferrable critical section (the epoch state transition) instead of being deferred to the already-existing failure path (CDO `transferFrom` failure → `_handleBorrowerDefault`/default accounting), turning a liquidity timing condition into a protocol-level freeze.

### Impact Explanation
All LP funds in the credit vault are temporarily frozen for the entire duration of the external vault's illiquidity: pending withdraw requests cannot be funded (stopEpoch reverts) and cannot be claimed (`epochNumber` never advances), deposits during the buffer are usable but exit is impossible, and tranche holders cannot redeem. If the vault illiquidity is long-lived or adversarially maintained (borrower draws in the underlying vault, utilization pinning), the freeze approaches permanence for practical purposes. The quantified loss equals the full `pendingWithdraws` plus all active tranche NAV (`lastNAVAA + lastNAVBB`) for the freeze duration — LP capital and yield are locked with no recourse, and the orderly default path that would at least crystallize the loss and start recovery accounting (`defaultRecoveryReserve`, `finalizeDefaultRecovery`) is unreachable because the CDO never sees a failed `transferFrom`.

### Likelihood Explanation
The trigger is reachable by the explicitly in-scope attacker "a user of the programmable borrower's ERC4626 vault": such a user withdraws (or causes to be drawn) the vault's idle liquidity so that `convertToAssets` still values the ProgrammableBorrower's shares above `shortfall` while `withdraw` reverts. No privileged role is required — honest borrower/manager `stopEpoch` timing is public, and the attacker only needs to hold vault shares or influence vault utilization, both standard for any ERC4626 integration. The existing guards do not stop it: `onStopEpoch`'s `nonReentrant` is irrelevant, the `try/catch` deliberately reverts rather than degrading to the default path, and `onDefault` (which avoids `convertToAssets` for this exact reason, per its comment) is unreachable because defaulting requires the CDO's pull to fail first — which never happens because the hook reverts earlier.

### Recommendation
Do not let a covered-but-illiquid vault revert abort `stopEpoch`. Instead, mirror the "insufficient coverage" branch: on `vault.withdraw` failure, return `success = true` and skip clearing `epochPendingWithdraws`/`epochAccountingActive` (or return a distinct status), so the subsequent CDO `transferFrom` fails naturally and the flow proceeds through the existing default/`stopEpochWithDuration` loss path — the same deferral the f2fs fix applies by moving the blocking work out of the atomic context. Alternatively, cap `shortfall` at `vault.maxWithdraw(address(this))` before deciding coverage, and treat `maxWithdraw == 0` with `shortfall > 0` as under-covered rather than as a hard revert.

### Proof of Concept
```solidity
// SPDX-License-Identifier: UNLICENSED
pragma solidity 0.8.10;

import "forge-std/Test.sol";
import {ProgrammableBorrower} from "../contracts/strategies/idle/ProgrammableBorrower.sol";

// Minimal illiquid-but-solvent ERC4626 stub: convertToAssets reports full
// coverage, withdraw() reverts because there is no idle cash.
contract IlliquidVault {
    address public asset;
    mapping(address => uint256) public balanceOf_;
    uint256 public price = 1e18; // shares still worth full value on paper
    bool public liquid;

    constructor(address _asset) { asset = _asset; }

    function balanceOf(address a) external view returns (uint256) { return balanceOf_[a]; }
    function convertToAssets(uint256 shares) external view returns (uint256) {
        return shares * price / 1e18; // nominal solvency
    }
    function deposit(uint256 a, address r) external returns (uint256 s) {
        s = a * 1e18 / price; balanceOf_[r] += s;
    }
    function withdraw(uint256, address, address) external view returns (uint256) {
        require(liquid, "no idle liquidity"); // lent out / locked
        return 0;
    }
    function redeem(uint256, address, address) external view returns (uint256) {
        require(liquid, "no idle liquidity");
        return 0;
    }
    function setShares(address a, uint256 s) external { balanceOf_[a] = s; }
    function setLiquid(bool l) external { liquid = l; }
}

contract StopEpochAtomicityTest is Test {
    // Arrange: idleCDO (this test), ProgrammableBorrower holding vault shares whose
    // convertToAssets value >= shortfall, vault cash-illiquid (attacker drained idle cash).
    // Act: call onStopEpoch exactly as IdleCDOEpochVariant.stopEpoch does.
    // Assert: reverts StopEpochVaultLiquidityUnavailable => stopEpoch cannot complete
    // while vault is illiquid => pending withdraws/LP NAV frozen; default path unreachable
    // because the CDO's transferFrom is never reached.
}
```

Concretely, on a mainnet fork: deploy a vault where `convertToAssets` over-reports redeemable liquidity (or use an existing utilized lending ERC4626), seed `ProgrammableBorrower` with shares, let an external vault user remove idle liquidity so `withdraw` reverts, then have the honest manager call `stopEpoch` on `IdleCDOEpochVariant`. The call reverts with `StopEpochVaultLiquidityUnavailable` every time until the vault re-liquefies, while `emergencyExitVault` and `setVault` are also blocked — demonstrating freeze of `pendingWithdraws` + active NAV with no attacker privilege beyond being a vault user.
