### Title
Post-default withdraw requests drain the fixed `defaultRecoveryReserve`, freezing/stealing pre-default recovery claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The use-after-free analog is a stale-resource-reference bug: `finalizeDefaultRecovery` crystallizes a fixed `defaultRecoveryReserve` sized only for `totalBasis` (active basis + pending receipts) at finalization time, but `requestWithdraw` keeps minting new `postDefaultRequests` receipts afterwards whose claims are paid out of that same already-"freed"/closed reserve via `_transferDefaultRecovery`. New receipts consume recovery assets they were never accounted for, so earlier defaulted claimants can no longer be paid.

### Finding Description
In `IdleCreditVault.finalizeDefaultRecovery` the reserve is computed exactly once:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:686-692
uint256 reserveAmount = _recoveredAmount + prefundedReserve + defaultRecoveryReserve;
uint256 recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis;
defaultRecoveryReserve = reserveAmount;
```

`totalBasis = activeBasis + pendingBasis` where `pendingBasis = defaultPendingClaimBasis()` — only pre-default `pendingWithdraws` and current-epoch instant claims. `postDefaultRequests` are excluded because they cannot exist yet.

After finalization, `requestWithdraw` still accepts new requests (lines 247-257): it burns CDO strategy tokens, mints a receipt to the user, and records `postDefaultRequests[_user] = _amount` — **without transferring any new underlying into the vault and without growing the reserve**. `claimWithdrawRequest` then routes to `_claimPostDefaultWithdrawRequest` (lines 760-767), which calls `_transferDefaultRecovery`:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:912-917
defaultRecoveryReserve -= _amount;
underlyingToken.safeTransfer(_user, _amount);
```

So a post-default claimant is paid 1:1 from a reserve that was only funded for `recoveryPrice * totalBasis`. Each post-default claim directly shrinks the reserve available to defaulted-epoch claimants (`_claimDefaultedWithdrawRequest`, `_claimDefaultedInstantWithdrawRequest`). When the reserve is exhausted, `defaultRecoveryReserve -= _amount` underflows (Solidity 0.8 panic) and all remaining legitimate default claims revert permanently.

Broken invariant: reserve conservation — the reserve should exactly cover `totalBasis` claims at `recoveryPrice`; post-default receipts are an unaccounted extra claim class on the same finite pool.

### Impact Explanation
An unprivileged tranche holder (or any user able to obtain tranche tokens after a default) can withdraw underlying belonging to defaulted-epoch receipt holders and active-LP recovery claimants. Loss = the post-default claim amount (up to the reserve balance); victims suffer theft plus permanent freezing, since their claims revert once the reserve is depleted. No privileged role is required: `requestWithdraw`/`claimWithdrawRequest` are permissionless user flows via the CDO.

### Likelihood Explanation
Requires a borrower default that reaches `finalizeDefaultRecovery` (rare but a designed-for state), and that post-finalization withdraw requests are enabled — which the code explicitly supports rather than reverting. The attack is then a single `requestWithdraw` + `claimWithdrawRequest` sequence with no timing constraints. Severity is bounded by reserve size, but the claim pays 1:1 while pre-default claims pay at a haircut, so the attacker is strictly advantaged.

### Recommendation
Track a separate accounting bucket for post-default claims, or fund them explicitly: e.g., in `requestWithdraw`'s post-default branch, require the CDO to `safeTransferFrom` the underlying backing the burned tokens into the strategy and add it to a `postDefaultReserve` (not `defaultRecoveryReserve`), and make `_claimPostDefaultWithdrawRequest` spend from that bucket. Alternatively, proportionally enlarge `totalBasis`/reserve when post-default receipts are created, so the fixed reserve is never silently oversubscribed.

### Proof of Concept
Foundry fork sketch (same pattern as `test/foundry/IdleCreditVault.t.sol`, mainnet fork block ~23032567):

```solidity
function testPostDefaultClaimDrainsRecoveryReserve() external {
    // 1. Deposit AA/BB, start epoch, request withdraws so pendingWithdraws > 0.
    idleCDO.depositAA(10_000 * ONE_SCALE);
    _startEpochAndCheckPrices(0);
    cdoEpoch.requestWithdraw(0, address(AAtranche)); // victim pending receipt

    // 2. Warp past epoch end; borrower defaults with partial recovery.
    vm.warp(cdoEpoch.epochEndDate() + 1);
    // ... drive cdoEpoch default path -> finalizeDefaultRecovery(partialRecovery, source)
    // assert strategy.defaultRecoveryFinalized() && reserve == recoveryPrice * totalBasis / RECOVERY_FULL

    // 3. Attacker (fresh tranche holder) opens a post-default request and claims.
    deal(address(AAtranche), attacker, attackerTranches);
    vm.startPrank(attacker);
    cdoEpoch.requestWithdraw(attackerTranches, address(AAtranche));
    uint256 reservePre = strategy.defaultRecoveryReserve();
    cdoEpoch.claimWithdrawRequest();
    vm.stopPrank();

    // 4. Reserve shrank by an amount that was never in totalBasis.
    assertLt(strategy.defaultRecoveryReserve(), reservePre);

    // 5. Victim's defaulted claim now reverts / is underpaid when reserve is exhausted.
    vm.prank(victim);
    vm.expectRevert(); // underflow in _transferDefaultRecovery once drained
    cdoEpoch.claimWithdrawRequest();
}
```

Uncertainty note: whether the burned CDO strategy tokens in the post-default branch are intended to implicitly back the claim with "freed" vault underlying could not be fully confirmed within the available exploration budget — however, since the payout path decrements `defaultRecoveryReserve` rather than drawing on unreserved balance (`_transferFundedClaim`'s `balance - reserve` guard exists precisely to prevent this), the reserve-conservation break stands on the code as written.
