This qualifies as a genuine analog. The redeem-solving success path in `ProvisionerV2` transfers payout tokens directly with unprotected `safeTransfer`, unlike every other transfer path in the same contract (refunds, cancellations) which use the guarded `_transferWithFallback`/`trySafeTransfer` pattern specifically to avoid blacklist-induced reverts.

### Title
Unprotected `safeTransfer` to `request.receiver` in redeem-vault solving lets a blacklisted receiver DoS batch settlement - ([File: v3/src/core/ProvisionerV2.sol])

### Summary
`_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice`, invoked from `_solveRequestsVault`/`solveRequestsVault`, pay out the redeemed underlying token to `request.receiver` via a bare `token.safeTransfer(request.receiver, tokenOutAfterTip)` [1](#0-0)  and `token.safeTransfer(request.receiver, request.tokens)` [2](#0-1) . Unlike the refund/cancel paths, which deliberately use `_transferWithFallback` (a try/fallback wrapper) to tolerate a blacklisted or reverting recipient [3](#0-2) , the success-path payout has no such protection. Any ordinary user who submits `requestRedeem` and is later blacklisted by the underlying token issuer (e.g. a USDC-like token) will cause `token.safeTransfer` to that receiver to revert, unwinding the entire `_solveRequestsVault` call and thus every other request batched in the same `solveRequestsVault` transaction.

### Finding Description
An ordinary user calls `requestRedeem(token, unitsIn, minTokensOut, ...)` [4](#0-3) , escrowing vault units in the Provisioner and setting an async request hash with a future `deadline`. If that user (or the `receiver` they designated) is later added to the underlying token's blacklist (a normal, permissionless real-world event for regulated stablecoins), any subsequent `solveRequestsVault` call that includes their request in its `requests` array will process the exit against the `MultiDepositorVault` (burning units, pulling underlying tokens into the Provisioner) and then attempt `token.safeTransfer(request.receiver, ...)`, which reverts [5](#0-4) . Because `_solveRequestsVault` iterates all requests inline with no try/catch around this transfer (unlike the deliberate emit-and-`continue` guard pattern used elsewhere in the same loop for price/amount/cap checks) [6](#0-5) , the revert propagates and reverts the whole batch, including the exits and payouts intended for every other, unrelated user bundled in that transaction. The only unaffected path is `refundRequest` after `deadline` expiry, which correctly uses `_transferWithFallback` to return vault units (not the blacklist-restricted underlying token) to the user [7](#0-6) .

### Impact Explanation
While the blacklisted requester's own funds are not stolen (their escrowed units are recoverable via `refundRequest` post-deadline), every other user whose redeem request is bundled with the blacklisted one in a `solveRequestsVault` call is denied service for that transaction, and the guardian/solver must proactively detect and exclude the poisoned request to keep processing the batch. This matches a temporary freeze of legitimate users' withdrawal processing, consistent with a live Medium-severity "temporary freeze of funds" impact.

### Likelihood Explanation
The only prerequisite is that some request's designated `receiver` becomes blacklisted by the underlying token issuer after `requestRedeem` is submitted but before `solveRequestsVault` processes it — a routine, externally-triggered event for centralized stablecoins, requiring no protocol privilege or collusion. The vulnerable code path (`_solveRedeemVaultAutoPrice`/`_solveRedeemVaultFixedPrice`) is reached whenever the guardian/solver batches that pending request, which is the normal operational flow.

### Recommendation
Wrap the payout transfers in `_solveRedeemVaultAutoPrice` and `_solveRedeemVaultFixedPrice` with the same `_transferWithFallback`/`trySafeTransfer` protection already used in refund and cancellation code paths, so a single unpayable receiver degrades to a fallback transfer (or is skipped/refunded) instead of reverting the entire batch.

### Proof of Concept
1. Deploy `ProvisionerV2` + `MultiDepositorVault` on a fork with a mock ERC20 that supports a `blacklist(address)` function mimicking USDC's `isBlacklisted` check in `transfer`.
2. User `A` calls `requestRedeem(token, unitsIn, minTokensOut, 0, futureDeadline, maxPriceAge, true)` with `receiver = A`.
3. User `B` calls `requestRedeem(...)` similarly with `receiver = B`.
4. Blacklist `A` on the mock token.
5. Guardian calls `solveRequestsVault(token, [requestA, requestB], "", "")`.
6. Assert the whole transaction reverts (due to `token.safeTransfer` to blacklisted `A` failing), and confirm `requestB`'s units are never exited/transferred — demonstrating that `B`'s legitimate redemption is blocked purely by `A`'s blacklist status.
