### Title
Division-before-multiplication in `jovian_da_footprint` truncates the Jovian DA-footprint gas estimate, allowing block DA-footprint limits to be underenforced - (File: `crates/common/l1-fees/src/params.rs`)

### Summary
`L1FeeParams::jovian_da_footprint` divides the FastLZ-estimated compressed size by `1_000_000` *before* multiplying by the DA-footprint gas scalar, instead of multiplying first and dividing last. This mirrors the exact division-before-multiplication precision-loss bug class from the referenced Sherlock report (`_totalVestedAt` dividing before multiplying), and causes the DA-footprint gas charged per transaction to be under-counted whenever the sub-1e6 remainder times the scalar would otherwise round the result up.

### Finding Description
`tx_estimated_size_fjord` returns the FastLZ compressed-size estimate scaled by `1e6` [1](#0-0) . The correct/consistent pattern used everywhere else in this same file multiplies first and divides last, e.g. in `data_gas` (Fjord branch), `calculate_tx_l1_cost_bedrock`, `calculate_tx_l1_cost_ecotone`, and `calculate_tx_l1_cost_fjord`: [2](#0-1) [3](#0-2) 

However, `jovian_da_footprint` reverses this order — it divides the scaled estimate by `1_000_000` first, then multiplies by `scalar`: [4](#0-3) 

Because `tx_estimated_size_fjord` is an integer scaled by `1e6` (e.g. `126_387_400` for a real transaction, per the existing test vector) [5](#0-4) , dividing by `1_000_000` first (`wrapping_div`) truncates any sub-1e6 remainder before it ever gets a chance to be scaled up by `scalar`. For example, `126_387_400 / 1_000_000 = 126` (truncating `0.3874` bytes), then `126 * scalar`. If instead the multiplication happened first (`126_387_400 * scalar / 1_000_000`), the fractional remainder could carry through and round the final gas value up by a full unit for many `scalar` values — the two orders diverge whenever `(estimated_size mod 1_000_000) * scalar >= 1_000_000`.

This function computes the per-transaction contribution to `da_footprint_used`, which is the value tracked against the Jovian DA-footprint block limit [6](#0-5) , a resource-metering limit introduced specifically to bound how much data-availability load a block can impose. Every transaction sender contributes to this accounting, making the bug reachable by any ordinary transaction sender post-Jovian activation.

### Impact Explanation
The truncation systematically undercounts each transaction's DA-footprint gas contribution. Since this quantity is summed into `da_footprint_used` and checked against a fixed per-block DA-footprint gas limit, a block builder/executor that includes many transactions each slightly under-charged can pack a larger amount of real DA data into a block than the protocol's DA-footprint limit intends to allow. This is a resource-metering/block-building correctness issue: the enforced limit silently drifts from the specified limit, degrading the guarantee the Jovian DA-footprint mechanism is meant to provide (bounding L1 data-availability load per block). Because block validity and re-execution (via `common/evm2/src/executor.rs`, `builder/core/src/execution.rs`, and consensus/protocol code) all rely on the same computation, a persistent underestimate could also produce systematic disagreement with any external/reference implementation that performs multiply-then-divide, which is a correctness/consensus-relevant risk for a resource-accounting invariant.

### Likelihood Explanation
This code path executes on every single transaction once Jovian is active and `da_footprint_gas_scalar` is configured (not `None`) — it is not conditional on attacker behavior; any normal transaction triggers it. The precision loss occurs deterministically whenever the FastLZ-estimated size has a non-zero remainder mod `1_000_000`, which is the common case for real transaction payloads (as shown by the existing Fjord test vectors with non-round sizes) [5](#0-4) . Likelihood of the rounding divergence occurring is high; the practical per-transaction magnitude is small, but it is systematic and cumulative across a full block's transactions.

### Recommendation
Reorder the arithmetic in `jovian_da_footprint` to multiply before dividing, consistent with the rest of `params.rs`:

```rust
pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
    let Some(scalar) = self.da_footprint_gas_scalar else {
        return 0;
    };
    U256::from(tx_estimated_size_fjord(input))
        .saturating_mul(scalar)
        .wrapping_div(U256::from(1_000_000u64))
        .saturating_to::<u64>()
}
```
Verify against the upstream OP-stack reference `jovian_da_footprint_estimation` formula and add a test case with a non-round `tx_estimated_size_fjord` value and non-trivial `scalar` to confirm the multiply-first order matches the specification exactly.

### Proof of Concept
Using the existing Fjord test vector's estimated size of `126_387_400` (scaled by `1e6`) [5](#0-4)  and an example `scalar = 3`:

- Current (divide-then-multiply): `126_387_400 / 1_000_000 = 126` (truncated), `126 * 3 = 378`.
- Correct (multiply-then-divide): `126_387_400 * 3 = 379_162_200`, `379_162_200 / 1_000_000 = 379`.

The current implementation undercounts by `1` gas unit for this input/scalar combination; larger `scalar` values or different remainders produce proportionally larger discrepancies, and this happens for every transaction whose compressed-size estimate is not an exact multiple of `1_000_000`, which is the typical case.

```rust
/// Calculate the estimated compressed transaction size in bytes, scaled by 1e6.
/// This value is computed based on the following formula:
/// max(minTransactionSize, intercept + fastlzCoef*fastlzSize)
pub fn tx_estimated_size_fjord(input: &[u8]) -> u64 {
    let fastlz_size = flz_compress_len(input) as u64;

    fastlz_size
        .saturating_mul(L1_COST_FASTLZ_COEF)
        .saturating_sub(L1_COST_INTERCEPT)
        .max(MIN_TX_SIZE_SCALED)
}
```
