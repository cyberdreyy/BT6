### Title
Post-default instant withdrawals bypass the finalized recovery haircut and drain non-reserve repayments at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The vim bug is a use-after-free: `qf_update_buffer` keeps operating on a quickfix buffer after it has been freed, i.e., state is mutated/used after its lifecycle was supposed to be closed. The closest analog in this codebase is the instant-withdraw receipt bucket of `IdleCreditVault`: `finalizeDefaultRecovery` "frees" (crystallizes) the defaulted epoch's claim accounting into `defaultRecoveryReserve`/`defaultRecoveryPrice`, but `requestInstantWithdraw` — unlike `requestWithdraw` — has no `defaultRecoveryFinalized` branch and keeps writing new receipts into `instantWithdrawsRequestsByEpoch[user][epochNumber]`, `instantWithdrawsRequests`, `instantWithdrawClaimsByEpoch`, and `pendingInstantWithdraws` while `epochNumber` still equals `defaultRecoveryEpoch`. These post-finalization claims are then paid **at par** through `claimInstantWithdrawRequest` → `_transferFundedClaim` from any non-reserve balance, while every claimant whose receipt existed at finalization is capped at `defaultRecoveryPrice`.

### Finding Description
`requestWithdraw` explicitly handles the finalized-default state: it reverts if the user still has stale receipts and routes the new request through `postDefaultRequests`, paying from `defaultRecoveryReserve` at the post-haircut price (`IdleCreditVault.sol:247-258`). `requestInstantWithdraw` (`IdleCreditVault.sol:356-375`) has no such branch — it simply burns CDO strategy tokens, mints a receipt to the user, and adds the amount to `instantWithdrawsRequestsByEpoch[user][epochNumber]` and `pendingInstantWithdraws`, even though `epochNumber == defaultRecoveryEpoch` and that epoch's accounting was already finalized.

On the claim side, `claimInstantWithdrawRequest` (`IdleCreditVault.sol:380-393`) only applies the recovery haircut via `_claimDefaultedInstantWithdrawRequest` when `defaultInstantWithdrawsFinalized` is true (which requires `pendingInstantWithdraws != 0` *at finalization time*, line 696). Any receipt recorded after finalization — or any receipt in a vault finalized with `pendingInstantWithdraws == 0` — falls through to `_burn(_user, amount)` + `_transferFundedClaim(_user, amount)`, i.e., a **1:1 par payout**.

`_transferFundedClaim` (`IdleCreditVault.sol:897-907`) protects `defaultRecoveryReserve` but pays freely from any balance above it. Two consequences:

1. **Recovery bypass**: underlying arriving after finalization (borrower partial repayments routed through `sendInterestAndDeposits`/`deposit`, or funds returned by the programmable borrower vault) sits as non-reserve balance. It was never folded into `defaultRecoveryPrice`, so it does not accrue to defaulted claimants or to tranche virtualPrice. A post-default instant withdrawer — any KYC-passed lender holding tranche tokens — can claim it at par, first-come-first-served, while pre-default receipt holders remain locked at `recoveryPrice`. This is theft/misallocation of post-default recovery value: economically those repaid funds belong to the defaulted-epoch creditor set, not to whoever files a fresh instant receipt first.
2. **Receipt double-basis when `defaultInstantWithdrawsFinalized` is true**: a user with an unclaimed defaulted-epoch instant receipt who files a new post-default instant request has both amounts merged into `instantWithdrawsRequestsByEpoch[user][defaultEpoch]`; the next claim clears the *combined* basis against `instantWithdrawsRequests`/`pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch`, mutating per-epoch accounting that finalization was supposed to have closed (the literal use-after-free shape: writes into a "freed" epoch bucket).

### Impact Explanation
Permanent misallocation/theft of post-default recovery funds, quantified as `min(freeBalance, instantReceiptAmount)` paid at par instead of being distributed at `defaultRecoveryPrice` to the finalized creditor set. In a realistic default (recovery price < 1, borrower later partially repays), each repaid unit can be extracted at 100% by the first instant-withdraw claimant while rightful claimants hold receipts worth only `recoveryPrice`. The loss equals the entire non-reserve post-finalization balance the attacker can cover with instant receipts.

### Likelihood Explanation
Requires a defaulted and finalized vault (`finalizeDefaultRecovery` executed), the CDO still routing `requestInstantWithdraw`/`claimInstantWithdrawRequest` post-default (the sibling `requestWithdraw` path is explicitly supported post-default, per the `postDefaultRequests` flow and tests at `test/foundry/IdleCreditVault.t.sol:4644-4653`), and non-reserve underlying reaching the strategy — a partial borrower repayment post-finalization suffices, and direct token transfers to the strategy are an in-scope adversary capability. All attacker steps are unprivileged (tranche-token holder actions). If the CDO layer reverts instant-withdraw requests whenever `defaulted()` is true, the vector collapses — that gating is the main uncertainty I could not fully confirm in `IdleCDOEpochVariant.sol`.

### Recommendation
Mirror the `requestWithdraw` handling in `requestInstantWithdraw`: when `defaultRecoveryFinalized` is set, either revert or route the receipt through `postDefaultRequests`/reserve-backed accounting instead of the live instant buckets. Additionally, any post-finalization inflow (repayments, direct transfers) should be swept into `defaultRecoveryReserve` (or re-price via a new finalization step) so it cannot be claimed at par outside the recovery waterfall, and `_claimDefaultedInstantWithdrawRequest` should refuse to clear a per-epoch basis that was mutated after `defaultRecoveryEpoch` was sealed.

### Proof of Concept
Foundry fork sketch against `test/foundry/IdleCreditVault.t.sol` harness:

```solidity
// 1. Deposit as attacker + victim, run epoch, borrower defaults (stopEpoch with 0 funds).
_depositWithUser(attacker, 10_000 * ONE_SCALE, true);
_depositWithUser(victim,   10_000 * ONE_SCALE, true);
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr, 0);          // borrower returns nothing
// ensure pendingInstantWithdraws == 0 at finalization so defaultInstantWithdrawsFinalized == false
cdoEpoch.finalizeDefault(recovered, manager);                // recoveryPrice < 1e18

// 2. Borrower partially repays post-finalization (or anyone sends underlying to the vault).
//    These funds land as free balance, NOT in defaultRecoveryReserve.
uint256 repay = 5_000 * ONE_SCALE;
deal(defaultUnderlying, borrower, repay);
vm.prank(borrower);
underlying.transfer(address(strategy), repay);               // or via CDO deposit path

// 3. Attacker files a NEW instant withdraw request post-default.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackerTrancheBalance, address(AAtranche));

// 4. Claim pays at PAR from the repaid (non-reserve) funds.
uint256 balPre = underlying.balanceOf(attacker);
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
assertGt(underlying.balanceOf(attacker) - balPre, 0);        // paid 1:1

// 5. Meanwhile victim's defaulted-epoch receipt is still capped at defaultRecoveryPrice:
//    _claimDefaultedWithdrawRequest pays claimBasis * recoveryPrice / 1e18.
// The repaid `repay` never reached defaultRecoveryReserve, so it was stolen at par
// instead of being shared across the finalized creditor set.
```

Note: step 3 assumes `IdleCDOEpochVariant` still routes `requestInstantWithdraw` when defaulted; if it hard-reverts on `defaulted()`, the finding reduces to the accounting-corruption variant (2) only, which alone is medium/low. The par-drain of post-finalization inflows via pre-existing or newly-funded instant receipts remains valid even under a partial block, since `claimInstantWithdrawRequest` itself has no default-state gating on the funded path.
