### Title
Current-tenure miner can indefinitely suppress the inactivity fallback with cheap junk re-proposals — ([File: stacks-signer/src/chainstate/mod.rs])

### Summary
`check_latest_block_in_tenure` treats *any* block proposal that fails its height/parent check as valid "miner activity" and refreshes `last_activity_time` for the tenure, even though the proposal itself is worthless (a stale height, or one conflicting with an already signed/pre-committed block). Because `SortitionState::is_timed_out` (the only trigger for falling back to a prior, valid miner) measures elapsed time strictly against this same `last_activity_time`, a malicious or stalling current-tenure miner can keep resetting its own inactivity clock forever by sending cheap, invalid re-proposals, without ever producing a valid extending block. This is the same bug class as the "dust execution" report: a cheap, attacker-controlled write to shared state (`last_activity_time`) perpetually defeats the equality/timeout check (`elapsed > block_proposal_timeout`) that other, legitimate participants rely on to make progress.

### Finding Description
`SortitionData::check_latest_block_in_tenure` is called at proposal arrival for every incoming `BlockProposal` (via `check_proposal` in v1/v2), before the block is ever submitted to the node for real validation: [1](#0-0) 

When the proposed block does not confirm more blocks than what the signer already signed/observed (`chain_length <= info.block.header.chain_length`), the function does not merely reject the proposal — if the currently signed/accepted block is still "fresh" (`signed_group` recent, or absent), it explicitly calls `signer_db.update_last_activity_time(...)` before returning `Ok(false)`: [2](#0-1) 

A second branch does the same for a proposal that merely conflicts with a fresh pre-commit at or below the pre-committed height: [3](#0-2) 

This `last_activity_time` is exactly the value `SortitionState::is_timed_out` (v1) uses to decide whether the miner has gone inactive and the signer set should fall back to the prior tenure's miner: [4](#0-3) 

`check_miner_inactivity` is the only path that lets a signer abandon a stalled current miner in favor of a valid prior one, and it only fires once `is_timed_out` returns true: [5](#0-4) 

Because the "activity" check at proposal arrival runs on static header fields (chain length vs. the locally-known tip) and completes before any expensive node validation, a miner can produce many such junk proposals (e.g. reusing/incrementing timestamps to change the `signer_signature_hash` while keeping `chain_length` unchanged or below the known tip) far more cheaply than mining a real extending block. Each one refreshes `last_activity_time` to "now," so `elapsed > block_proposal_timeout` in `is_timed_out` never becomes true, and `check_miner_inactivity` never triggers the fallback to the prior, valid miner. This wedges the state machine's failover mechanism: the chain cannot progress and the signer set has no other liveness path back to a good miner, purely due to a stream of cheap, invalid proposals from the single current-tenure miner — the direct analog of the dust-order griefer keeping `nonceBalance` perpetually unsatisfiable for other participants at negligible cost.

### Impact Explanation
This is a liveness wedge produced by a single, one-slot actor (the current tenure's miner) using only gossiped `BlockProposal` messages — no majority of signers, no other signer's key, and no node access is required. It matches the allowed "High" impact category: a signer (here, the whole signer set's fallback mechanism) is wedged into never being able to act on a stale/stuck miner situation, stalling the chain until the next burn block regardless of how long the current miner refuses to produce a valid block.

### Likelihood Explanation
The comment in the code even acknowledges the tradeoff explicitly ("The miner may just be slow, so count this invalid block proposal towards valid miner activity") but places no bound on how often or how cheaply this credit can be claimed. Since the check happens before real block validation and only inspects the header's `chain_length`/consensus hash against locally cached state, generating a stream of qualifying junk proposals is inexpensive for the tenure's own miner, making exploitation straightforward for anyone who already won the sortition and wants to stall rather than mine honestly.

### Recommendation
Bound how much credit repeated invalid/duplicate proposals can give the miner's activity timer — e.g., only refresh `last_activity_time` a limited number of times per tenure for this kind of failed check, or require the proposal to at least differ meaningfully (not just in timestamp) from previously-seen junk before it counts as activity, so a miner cannot indefinitely defer the inactivity-based fallback with negligible-cost resubmissions.

### Proof of Concept
1. Attacker wins a sortition and becomes the active tenure miner.
2. Instead of mining a valid extending block, attacker repeatedly broadcasts `BlockProposal` messages whose `chain_length` is at or below the tenure's already-signed/pre-committed height (varying only the timestamp so each has a distinct `signer_signature_hash`), at an interval shorter than `block_proposal_timeout`.
3. Each such proposal is checked by `check_latest_block_in_tenure`, fails the height check, but hits the `update_last_activity_time` branch (either the signed-block path at [6](#0-5)  or the pre-commit path at [7](#0-6) ), refreshing `last_activity_time`.
4. `SortitionState::is_timed_out` never observes `elapsed > block_proposal_timeout` because `last_activity_time` is continually reset.
5. `check_miner_inactivity` never reverts to the prior valid miner, and the chain stalls in this tenure indefinitely, purely as a result of the current miner's cheap junk re-proposals.

    pub fn check_latest_block_in_tenure(
        tenure_id: &ConsensusHash,
        block: &NakamotoBlock,
        signer_db: &mut SignerDb,
        client: &StacksClient,
        tenure_last_block_proposal_timeout: Duration,
        reorg_attempts_activity_timeout: Duration,
    ) -> Result<bool, ClientError> {
        let last_block_info = SortitionData::get_tenure_last_block_info(
            tenure_id,
            signer_db,
            tenure_last_block_proposal_timeout,
        )?;

        if let Some(info) = last_block_info {
            // N.B. this block might not be the last globally accepted block across the network;
            // it's just the highest one in this tenure that we know about.  If this given block is
            // no higher than it, then it's definitely no higher than the last globally accepted
            // block across the network, so we can do an early rejection here.
            if block.header.chain_length <= info.block.header.chain_length {
                warn!(
                    "Miner's block proposal does not confirm as many blocks as we expect";
                    "proposed_block_consensus_hash" => %block.header.consensus_hash,
                    "signer_signature_hash" => %block.header.signer_signature_hash(),
                    "proposed_chain_length" => block.header.chain_length,
                    "expected_at_least" => info.block.header.chain_length + 1,
                );
                if info.signed_group.is_none_or(|signed_time| {
                    signed_time + reorg_attempts_activity_timeout.as_secs() > get_epoch_time_secs()
                }) {
                    // Note if there is no signed_group time, this is a locally accepted block (i.e. tenure_last_block_proposal_timeout has not been exceeded).
                    // Treat any attempt to reorg a locally accepted block as valid miner activity.
                    // If the call returns a globally accepted block, check its globally accepted time against a quarter of the block_proposal_timeout
                    // to give the miner some extra buffer time to wait for its chain tip to advance
                    // The miner may just be slow, so count this invalid block proposal towards valid miner activity.
                    if let Err(e) = signer_db.update_last_activity_time(
                        &block.header.consensus_hash,
                        get_epoch_time_secs(),
                    ) {
                        warn!("Failed to update last activity time: {e}");
                    }
                }
                return Ok(false);
            }
        }

impl SortitionState {
    /// Check if the given sortition identified by its ConsensusHash has timed out based on current signed blocks
    /// and the time at which the burn block for it was first recorded in the provided signerdb
    pub fn is_timed_out(
        sortition: &ConsensusHash,
        db: &SignerDb,
        block_proposal_timeout: Duration,
    ) -> Result<bool, SignerChainstateError> {
        // If we've already signed a block in this tenure, the miner can't have timed out: we have
        // committed a signature to this tenure and must not help abandon it.
        //
        // Importantly, a block we have only pre-committed to does not count! A pre-commit carries
        // no signature, and if it never reaches the pre-commit threshold the tenure can stall
        // indefinitely. Treating it as signed here would suppress the inactivity timeout for
        // exactly the signers that pre-committed, so they could never fall back to the prior
        // miner and the tenure could never recover.
        let has_block = db.has_signed_block_in_tenure(sortition)?;
        if has_block {
            return Ok(false);
        }
        let Some(received_ts) = db.get_burn_block_receive_time_ch(sortition)? else {
            return Ok(false);
        };
        let received_time = UNIX_EPOCH + Duration::from_secs(received_ts);
        let last_activity = db
            .get_last_activity_time(sortition)?
            .map(|time| UNIX_EPOCH + Duration::from_secs(time))
            .unwrap_or(received_time);

        let Ok(elapsed) = std::time::SystemTime::now().duration_since(last_activity) else {
            return Ok(false);
        };

        if elapsed > block_proposal_timeout {
            info!(
                "Tenure miner was inactive too long and timed out";
                "tenure_ch" => %sortition,
                "elapsed_inactive" => elapsed.as_secs(),
                "config_block_proposal_timeout" => block_proposal_timeout.as_secs()
            );
        }
        Ok(elapsed > block_proposal_timeout)
    }
