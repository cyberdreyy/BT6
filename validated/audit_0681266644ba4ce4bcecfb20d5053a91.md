### Title
Confirmations from deleted multisig members remain counted toward execution threshold, allowing requests to execute below the live-member quorum - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
The multisig contracts (`multisig` and `multisig2`) execute a pending request once `confirmations.len() + 1 >= num_confirmations`, but the confirmation set for a request is never re-validated against the current set of live members. When a member who already confirmed a *different, still-pending* request is later removed via `DeleteMember`/`DeleteKey`, their stale confirmation continues to count toward that pending request's threshold, letting it execute with fewer live-member approvals than `num_confirmations` requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` (and the equivalent in `multisig/src/lib.rs`) decides execution purely by counting entries in the `confirmations` `HashSet<String>` for the request: [1](#0-0) 

The threshold check does not verify that each recorded confirmer is still present in `self.members`.

The only place that cleans up stale request state on member removal is `delete_member`, which purges requests *authored* by the removed member (`r.member == member`), but it never scans other requests' `confirmations` sets to strip out the removed member's stale approval: [2](#0-1) 

The same pattern exists in the legacy `multisig` contract's `DeleteKey` handling inside `execute_request`, which filters requests by `r.signer_pk == pk` (the request's original signer) and likewise never touches `confirmations` entries made by that key on other requests: [3](#0-2) 

As a result, the binding the contract is supposed to maintain — `count(confirmations that belong to a currently-live member) >= num_confirmations` before executing a request — silently degrades to `count(all historically recorded confirmations, live or not) >= num_confirmations`. This is the same class of bug as the referenced report: a recorded/committed state (a confirmation, analogous to the L1-recorded protocol version) is treated as permanently valid and is never reconciled against the real, current state of the system (the live member set, analogous to the real L2 execution outcome) that it is supposed to reflect.

### Impact Explanation
This crosses the multisig's core authorization boundary: "a request needs `num_confirmations` confirmations from members currently entitled to sign." Once a member is removed, any request they previously confirmed can still be pushed to execution by fewer *live* members than the configured threshold — including `Transfer` actions that move NEAR out of the multisig account, or further membership/key changes. This falls squarely into "a multisig request executed below threshold," listed as a Critical impact.

### Likelihood Explanation
This does not require a malicious insider or key compromise — it can happen through completely ordinary multisig operation: legitimate turnover of a signer (e.g., removing a departing member) combined with one pre-existing pending request that member had confirmed. No special privilege beyond the normal member/confirm flow that the contract already exposes is needed to trigger execution below quorum; the remaining live members are simply unaware that a stale confirmation is still silently counted.

### Recommendation
When executing `DeleteMember`/`DeleteKey`, iterate over `self.confirmations` (not just `self.requests` filtered by original author) and remove the deleted member's public key/identifier from every request's confirmation set, decrementing effective counts accordingly. Alternatively, when checking the threshold in `confirm()`, filter the confirmations set to only those entries whose member is still present in `self.members` before comparing against `num_confirmations`.

### Proof of Concept
1. Deploy `multisig2` with members `{A, B, C, D}` and `num_confirmations = 3`.
2. `A` calls `add_request` to create request `R1` (e.g., `Transfer` to some account), then `A` calls `confirm(R1)` → confirmations = `{A}`.
3. `B` calls `confirm(R1)` → confirmations = `{A, B}` (2 of 3 — not yet executed).
4. Separately, `A`, `C`, `D` legitimately create and confirm a `DeleteMember { member: B }` request (a normal 3-of-4 operation, e.g. because B lost access). This executes `delete_member`, which removes `B` from `self.members` and only deletes requests where `r.member == B` (requests B authored) — `R1`'s confirmations set `{A, B}` is untouched.
5. `C` now calls `confirm(R1)`: `confirmations.len() + 1 = 3 >= num_confirmations (3)` evaluates true, and `R1` (the `Transfer`) executes — even though only `A` and `C` are still live members who approved it (2 live approvals, not the required 3). [4](#0-3) [5](#0-4)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
