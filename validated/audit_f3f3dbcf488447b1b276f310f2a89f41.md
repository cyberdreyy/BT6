### Title
Cache extractors create symlinks without validating `Linkname` target, allowing cache-planted symlinks (e.g. `node_modules -> /etc`) to redirect later job I/O outside the build root - (File: `commands/helpers/archive/tarzstd/tarzstd_extractor.go`, `helpers/archives/zip_extract.go`)

### Summary
`CacheExtractorCommand.Execute` calls `extractor.Extract`, which for the `tarzstd` and legacy `zip` formats creates filesystem symlinks directly from the archive's `Linkname` (tar) or decoded link-target bytes (zip) with no check that the target stays inside the extraction root (`e.dir`). A pipeline author who controls what gets cached (e.g. by creating a symlinked directory named `node_modules` pointing to `/etc` and letting `CacheArchiverCommand` snapshot it) can seed the shared project cache with that symlink; when a later job restores the same cache key and subsequently treats `node_modules` as an ordinary directory (via its own build steps or a later cache re-extraction that writes files under that path), file operations transparently follow the symlink and touch `/etc` instead of the intended cache/build subtree.

### Finding Description
`CacheExtractorCommand.Execute` (`commands/helpers/cache_extractor.go:618-664`) opens the downloaded/local cache archive and calls `archive.NewExtractor(format, f, size, wd).Extract(ctx)` [1](#0-0) .

For `tarzstd`, `Extract` only validates the *path* derived from `hdr.Name` against directory traversal (`filepath.Abs`/`strings.HasPrefix` check), but the symlink target itself is never checked: [2](#0-1) 
and later: [3](#0-2) 
`os.Symlink(hdr.Linkname, path)` is invoked with `hdr.Linkname` taken verbatim from the archive - an attacker-controlled tar header field. It can be an absolute path like `/etc`, so the created filesystem object at `path` (e.g. `<wd>/node_modules`) becomes a symlink pointing anywhere on the host filesystem that the job process has permission to create/traverse.

The legacy zip extractor has the identical gap: [4](#0-3) 
`extractZipSymlinkEntry` reads the symlink target from the zip entry's file content (`data`) and calls `os.Symlink(string(data), file.Name)` without validating that the target stays under the extraction root.

Neither extractor de-references or refuses pre-existing symlink components either - the traversal check in `tarzstd_extractor.go` (`strings.HasPrefix(path, e.dir+...)`) is a purely lexical/string check on the computed path; it does not call `filepath.EvalSymlinks` or otherwise detect that an intermediate path component (e.g. `node_modules`) is already a symlink pointing outside `e.dir`. Consequently:
1. Job A (attacker-controlled) creates a directory entry named `node_modules` as a symlink to `/etc`, lets `CacheArchiverCommand` (out of scope, but confirmed to Lstat and preserve symlinks as-is per `helpers/archives/zip_create.go:17-30`) snapshot it into the shared cache blob under a cache key reused by later pipelines of the same project.
2. Job B, in a later pipeline run using the same cache key, runs `CacheExtractorCommand.Execute`, which recreates `wd/node_modules` as a symlink to `/etc` via the vulnerable `os.Symlink` calls shown above - no check rejects an absolute, out-of-root `Linkname`.
3. Any subsequent operation in Job B - either the job's own script writing into `node_modules` (e.g. `npm install`) or a second extraction phase within the same archive/another cache archive that writes entries under `node_modules/...` - resolves that path through the symlink at the OS level (`os.Create`, `os.OpenFile`, etc. always follow symlinks for intermediate path components), landing writes/reads on `/etc` instead of the intended cache subtree.

No existing "allowed images", overwrite-guard, or path-validation logic in these two extractors stops this, because the only check present (`archive/tarzstd/tarzstd_extractor.go:62-64`) only guards against `../`-style escapes in the *name*, not against the *symlink target itself* or pre-existing symlinked path components inherited from a prior extraction.

### Impact Explanation
A shared/reused cache lets an unprivileged pipeline author (in control of job scripts/cache contents) plant a symlink that redirects subsequent read/write operations for a well-known directory name (`node_modules`, `vendor`, `.cache`, etc.) to an arbitrary host path such as `/etc`, persisting across pipeline runs that share the same cache key. This is a concrete file-operation escape outside the intended cache/build root, matching the scoped impact: persistent multi-run file access outside the cache root that survives job cancellation (the symlink remains on disk / in the cache archive independent of any single job's lifetime).

### Likelihood Explanation
Preconditions are realistic and attacker-controlled: any pipeline author who can define a job that creates a symlinked directory and has that cache path uploaded via `CacheArchiverCommand` (standard `cache:` config feature) can trigger this without special privileges. The `tarzstd` and legacy `zip` cache formats are both officially supported extraction paths (`archive.Register` for `TarZstd`/`Zip`), reachable simply by selecting those cache/archive formats. Because caches are frequently shared across branches/MRs of the same project (documented GitLab behavior), a single poisoning run followed by any later run reusing the key reproduces the issue deterministically.

### Recommendation
- In `tarzstd_extractor.go`, before calling `os.Symlink(hdr.Linkname, path)`, resolve/validate that the symlink target, when joined against the containing directory, would resolve inside `e.dir` (or simply reject absolute `Linkname` values and any relative one that escapes `e.dir` via `..`).
- In `helpers/archives/zip_extract.go`'s `extractZipSymlinkEntry`, apply the equivalent validation to the decoded `data` before calling `os.Symlink`.
- Additionally, when constructing `path` for each entry, verify that no existing path component up to `filepath.Dir(path)` is itself a symlink outside `e.dir` (e.g., using `filepath.EvalSymlinks` on the parent and re-checking the prefix), to prevent a symlink planted by one archive entry (or a prior extraction) from redirecting subsequent entries.

### Proof of Concept
Go test outline (two-phase, mirroring `helpers/archives/zip_extract_test.go` conventions):
```go
func TestTarZstdExtractSymlinkEscape(t *testing.T) {
    dir := t.TempDir()

    // Phase 1: build a malicious tarzstd cache archive containing a single
    // symlink entry "node_modules" -> "/etc".
    archiveData := buildTarZstdArchive(t, []tarEntry{
        {name: "node_modules", typeflag: tar.TypeSymlink, linkname: "/etc"},
    })

    e, err := tarzstd.NewExtractor(bytes.NewReader(archiveData), int64(len(archiveData)), dir)
    require.NoError(t, err)
    require.NoError(t, e.Extract(context.Background()))

    target, err := os.Readlink(filepath.Join(dir, "node_modules"))
    require.NoError(t, err)
    // BUG: assertion fails today because target == "/etc"
    assert.NotEqual(t, "/etc", target, "extractor must not create symlinks pointing outside the cache root")

    // Phase 2: simulate a later job/extraction writing through the planted symlink.
    f, err := os.Create(filepath.Join(dir, "node_modules", "poc-should-not-exist"))
    if err == nil {
        f.Close()
        _, statErr := os.Stat("/etc/poc-should-not-exist")
        assert.Error(t, statErr, "/etc must not have been written to via the cache symlink")
        _ = os.Remove("/etc/poc-should-not-exist")
    }
}
```
Expected (fixed) behavior: `Extract` rejects or rewrites the out-of-root `Linkname`, so `node_modules` is never a symlink to `/etc`, and no file operation under it can touch `/etc`.

func extractZipSymlinkEntry(file *zip.File) (err error) {
	var data []byte
	in, err := file.Open()
	if err != nil {
		return err
	}
	defer func() { _ = in.Close() }()

	data, err = io.ReadAll(in)
	if err != nil {
		return err
	}

	// Remove symlink before creating a new one, otherwise we can error that file does exist
	_ = os.Remove(file.Name)
	err = os.Symlink(string(data), file.Name)
	return
}
