## Title
Stale confirmations from removed multisig members still count toward the confirmation threshold, allowing execution below the live-member quorum - (`multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
Both `multisig` and `multisig2` contracts remove a member/key's *own created requests* when that member is deleted, but they never scrub that member's *confirmations on requests created by other members*. A stale confirmation from an already-removed member therefore still counts toward `num_confirmations`, letting a request execute with fewer genuinely-live approvals than the configured threshold `K`.

### Finding Description
The binding the multisig is supposed to enforce is:
`confirmations counted at execution time == confirmations from currently-live members`.

In `confirm`, the contract simply compares the size of the stored `confirmations` set (plus the caller) against `num_confirmations`, with no check that every entry in that set still corresponds to a current member: [1](#0-0) 

When a member/key is removed via `DeleteKey` (v1) or `DeleteMember` (v2), the contract only purges requests that member *originated*; confirmations that member placed on requests created by *other* members are left untouched: [2](#0-1) [3](#0-2) 

Concretely: member `C` confirms request `R` (created by member `A`). Later the multisig legitimately removes `C` (e.g. `DeleteMember`/`DeleteKey` executed by the required K signers, for key rotation, compromise response, etc.). `R`'s `confirmations` entry still contains `C`'s vote. If any remaining member later confirms `R`, the count `confirmations.len() + 1` can reach `num_confirmations` while it actually includes a vote from someone who is no longer a member at all, i.e. the request executes with fewer than `K` *live* approvals.

### Impact Explanation
This breaks the core custody/authorization guarantee of the multisig: "a request requires K-of-N *current* members to approve" becomes "a request requires K confirmations ever recorded, some of which may belong to accounts/keys that have since been stripped of authority." An attacker who controls (or previously controlled, before removal) a stale confirmation, combined with fewer than `K` currently valid confirmations, can push a `Transfer`, `FunctionCall`, `AddKey`/`AddMember`, or other privileged action to execution — i.e. a multisig request executed below the live-member threshold, matching the Critical impact category (funds moved / privileged action authorized without the intended quorum).

### Likelihood Explanation
Member/key removal is a normal, expected multisig lifecycle operation (rotating compromised keys, removing departing signers). Any request that is pending confirmation at the time a confirming member is removed is silently left in this inconsistent state — no special attacker capability beyond being (or having been) a legitimate multisig participant is required, and no code path currently prevents or cleans this up.

### Recommendation
When removing a key/member (`DeleteKey` in `multisig/src/lib.rs`, `DeleteMember` in `multisig2/src/lib.rs`), iterate over *all* pending requests' `confirmations` sets (not just requests the member created) and strip any confirmation belonging to the removed member/key, or re-validate at `confirm`/execution time that every recorded confirmation still corresponds to a current member before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize multisig2 with members `[A, B, C, D, E]` and `num_confirmations = 3`.
2. `A` calls `add_request` for a `Transfer` to attacker-controlled account → `request_id = R`.
3. `A` and `C` call `confirm(R)` → `confirmations = {A, C}` (2 of 3).
4. Separately, `A, B, D` (3 members) execute a `DeleteMember { member: C }` request, which succeeds via `delete_member` — this only removes requests *created* by `C`, not `C`'s confirmation entry on `R`.
5. `B` calls `confirm(R)`. Code path: `confirmations.len() as u32 + 1 >= self.num_confirmations` → `2 + 1 >= 3` → true, `R` executes.
6. `R` was approved by `A`, `B`, and a stale vote from `C`, who was no longer a member at execution time — only 2 of the 4 remaining live members actually approved, below the intended 3-of-N quorum. [4](#0-3)

        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
