### Title
Lockup account ID is deterministically derived from `owner_account_id` alone, letting an attacker front-run and permanently squat the victim's lockup address with attacker-chosen terms and attacker as owner - (File: lockup-factory/src/lib.rs)

### Summary
`LockupFactory::create` derives the to-be-created lockup's `AccountId` purely from `sha256(owner_account_id)` with no uniqueness guard tied to the caller, deposit terms, or a pending-grant registry. Any unprivileged account can call `create` first, naming a real victim as `owner_account_id` but supplying attacker-chosen `vesting_schedule`, `lockup_duration`, `release_duration`, and `whitelist_account_id`, permanently occupying the deterministic address before the legitimate grantor's transaction lands.

### Finding Description
The broken binding: `lockup_account_id_for(owner) == the lockup deployed by owner's rightful grantor with the grantor's chosen terms`. The code computes the address with no dependency on caller identity or terms: [1](#0-0) 

`create` is `#[payable]` and callable by any account holding `MIN_ATTACHED_BALANCE`; the only guard is the deposit floor: [2](#0-1) 

There is no check that `predecessor_account_id` is the foundation, no check that `owner_account_id` consented, and no reservation/registry preventing a second, different `create` call for the same `owner_account_id` from being submitted first. `Promise::new(lockup_account_id).create_account()...` is fired unconditionally with attacker-controlled `LockupArgs` (including `owner_account_id` field of `LockupArgs`, which the attacker also fully controls and can set to the victim's ID or to themselves) and deployed with `CODE` immediately: [3](#0-2) 

Because NEAR account creation is a one-time, address-exclusive operation, whichever `create` call's `create_account()` action executes first on-chain wins that account id permanently; any subsequent `create` call targeting the same derived address fails at the runtime level (`AccountAlreadyExists`), and the callback simply refunds the *later* caller's deposit: [4](#0-3) 

So the attacker's exploit is: observe (or predict) that a grant for `victim.near` is imminent, call `create(owner_account_id = victim.near, ..., attacker's own vesting_schedule/whitelist/lockup_duration)` with `owner_account_id` set to the attacker's own account or to `victim.near` combined with attacker-favorable terms, and attach `MIN_ATTACHED_BALANCE`. If the attacker's transaction lands first, the address `hex::encode(sha256(owner_account_id))[..20].<factory>` is permanently deployed under attacker's chosen `LockupArgs`. The legitimate grantor's later `create` call for the same `owner_account_id` reverts on `create_account()` and only refunds the deposit back to that grantor via `on_lockup_create` - the intended owner never gets a correctly-parameterized lockup at the canonical, protocol-trusted address, and any downstream system (exchange, foundation tooling, user) that treats "the lockup at `hex(sha256(owner))...`" as authoritative for that owner now interacts with an attacker-controlled contract instance.

None of the existing guards catch this: there is no `assert_owner`/`assert_called_by_foundation` on `create` (it's intentionally open to any payer), `assert_self()` only protects the callback from being called by non-self, and `is_promise_success()` in `on_lockup_create` only distinguishes success/failure after the race is already decided - it does nothing to prevent the race itself.

### Impact Explanation
This is a Critical-class finding per the rules: "an account whitelisted or a lockup deployed with parameters its rightful creator never chose." The attacker gains permanent control (as `owner_account_id` in `LockupArgs`, or by naming the real owner but fixing all other terms - `vesting_schedule`, `release_duration`, `whitelist_account_id`) of the canonical lockup contract address for a target owner. Because the protocol/tooling and users identify "the lockup for account X" by this exact deterministic address, any NEAR sent to that address by the foundation, an employer, or automated tooling that assumes the address is trustworthy is deposited into a contract the attacker parameterized (e.g., pointing `staking_pool_whitelist_account_id` at an attacker-controlled pool, or setting `vesting_schedule`/`release_duration` to release attacker-favorable terms). This is a one-shot-per-victim-address race (repeatable across every distinct `owner_account_id` the attacker wants to target), and the blast radius is every future grant for any account whose address has not yet been claimed.

### Likelihood Explanation
The attack requires only `MIN_ATTACHED_BALANCE` (3.5 NEAR) and knowledge/prediction of an `owner_account_id` for whom a grant is expected (e.g., publicly known team/investor accounts, or new employees whose account names are guessable/announced in advance). No special privilege, key, or foundation role is needed - `create` is open to any account. The attacker can attempt this cheaply and repeatedly against many target owner accounts in parallel, and only needs their transaction to land before the legitimate grantor's transaction for the same owner.

### Recommendation
Restrict `create` to only be callable by `foundation_account_id` (or another trusted, gated role) as is already the model for other privileged actions in this codebase, and/or incorporate a nonce/registry approach so that lockup account IDs cannot be squatted by arbitrary unprivileged callers before the legitimate grant is issued.

### Proof of Concept
```rust
// lockup-factory/src/lib.rs tests module
#[test]
fn test_attacker_front_runs_victim_lockup_address() {
    let mut context = VMContextBuilder::new()
        .current_account_id(account_factory())
        .predecessor_account_id(account_near())
        .finish();
    testing_env!(context.clone());

    let mut contract = LockupFactory::new(whitelist_account_id(), foundation_account_id());

    const LOCKUP_DURATION: u64 = 63036000000000000;
    let lockup_duration: WrappedTimestamp = LOCKUP_DURATION.into();

    // Attacker (unprivileged) front-runs the address derived from the victim's account id,
    // but supplies their own custom whitelist / no vesting terms.
    context.is_view = false;
    context.predecessor_account_id = String::from(attacker_account_id());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(
        account_tokens_owner(), // victim's owner_account_id -> deterministic address
        lockup_duration,
        None,
        None,
        None,
        Some(attacker_whitelist_account_id()), // attacker-chosen pool whitelist
    );

    // Simulate successful account creation for attacker's call (wins the race).
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Successful(vec![]));
    assert!(contract.on_lockup_create(
        lockup_account(), // hex(sha256(owner_account_id)).factory - SAME address victim's grantor targets
        ntoy(35).into(),
        String::from(attacker_account_id()),
    ));

    // Legitimate grantor now tries to create the *real* lockup for the same owner_account_id.
    context.predecessor_account_id = String::from(account_tokens_owner_grantor());
    context.attached_deposit = ntoy(35);
    testing_env!(context.clone());
    contract.create(account_tokens_owner(), lockup_duration, None, None, None, None);

    // create_account() for the same address fails at runtime (AccountAlreadyExists) ->
    // on_lockup_create sees is_promise_success() == false and only refunds the grantor's deposit.
    context.predecessor_account_id = account_factory();
    context.attached_deposit = ntoy(0);
    testing_env_with_promise_results(context.clone(), PromiseResult::Failed);
    let res = contract.on_lockup_create(
        lockup_account(),
        ntoy(35).into(),
        String::from(account_tokens_owner_grantor()),
    );
    assert_eq!(res, false);
    // Binding broken: lockup_account() now permanently runs with attacker's LockupArgs,
    // not the grantor's, for owner_account_id == account_tokens_owner().
}
```
This demonstrates: `address_for(owner) -> contract_state` is claimed by whichever `create` call's `create_account()` lands first, independent of caller identity, breaking the invariant that the lockup at an owner's derived address carries only the terms that owner's rightful grantor chose.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
