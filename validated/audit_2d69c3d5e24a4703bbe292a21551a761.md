### Title
Permissionless `StartExecuteOrder` allows unprivileged front-running/griefing of a user's limit order execution slot - (File: `programs/marginfi/src/instructions/marginfi_account/order.rs`)

### Summary
The Meson `MesonSwap.postSwap` bug is a case where a primary identifier for a user action (`encodedSwap`) does not incorporate the initiator's identity, and the underlying instruction can be invoked by *any* unprivileged party, so an attacker can front-run and consume that identifier before the legitimate initiator, causing a durable denial of service against a specific user. The closest reachable analog in marginfi-v2 is `StartExecuteOrder`, the entry point for keeper-driven limit-order execution, whose `executor` account is explicitly unchecked/unprivileged and which `init`s a unique per-order PDA (`execute_record`) keyed only by the `order` pubkey.

### Finding Description
`StartExecuteOrder` is designed to be permissionlessly callable by "keepers" to begin executing a user's stop-loss/take-profit order: [1](#0-0) 

The `executor` field is an `UncheckedAccount` with no signer requirement in `StartExecuteOrder` ("no checks whatsoever, executor decides this without restriction"), and the `execute_record` PDA is derived solely from the `order` account's key: [2](#0-1) 

Because `execute_record` is a unique, `init`-only PDA per `order` (i.e. per user's placed order, since `order` itself is a PDA of `[ORDER_SEED, marginfi_account, bank_keys_hash]`), and any address can be passed as `executor` without proving control of it, any actor observing a pending/triggerable order in the mempool can call `start_execute_order` first, consuming the unique `execute_record` slot for that order before the legitimate keeper/executor's transaction lands - directly mirroring the Meson pattern where `encodedSwap` (lacking the initiator address) could be front-run by any unprivileged caller to occupy the swap's identifier slot.

The instruction does attempt to bound this: `start_execute_order` calls `validate_instructions` requiring the transaction to also contain a matching `END_EXECUTE_ORDER` instruction: [3](#0-2) 

and `end_execute_order` requires `has_one = executor` as a `Signer`: [4](#0-3) 

This means a bare front-run of `start_execute_order` alone (without a paired, correctly signed `end_execute_order` in the same atomic transaction) should cause the whole transaction to fail via `validate_instructions`, preventing the `execute_record` PDA from persisting in a "poisoned" state from a single-instruction griefing attack. I was not able to fully verify the exact semantics of `validate_instructions` (defined in `programs/marginfi/src/instructions/marginfi_account/liquidate_start.rs`) within the available context/tool budget - specifically whether it strictly enforces adjacency/ordering of `start`/`end` within the same transaction for *this* order/account pair, or merely checks that instructions with those discriminators exist anywhere in the transaction. If the latter, a malicious actor could potentially pair their own `start_execute_order` with a self-controlled, intentionally-failing-but-still-parseable `end_execute_order` targeting a *different* execute_record, or otherwise construct a transaction that satisfies the discriminator check while genuinely completing (as `executor`, using their own signature) a no-op-like execution — in which case the "poisoning" outcome would require the attacker to also satisfy `end_execute_order`'s health/slippage/tag constraints, which is nontrivial and generally would not block the account from any legitimate financial action other than that specific order.

### Impact Explanation
If exploitable, this would let a griefer occupy or interfere with a specific user's order-execution flow at the moment the order becomes triggerable, potentially delaying stop-loss/take-profit execution during adverse price movement (a availability/DoS impact with financial consequences for that user, similar in class to the Meson case). However, unlike the Meson bug — where `postSwap` succeeds and fully consumes the identifier for any caller providing a valid signature, permanently blocking the real initiator — here, completing a state change that blocks the *legitimate* actor also requires satisfying `has_one = executor` (a signer check) and the full health/trigger/slippage constraints of `end_execute_order`, or otherwise causing atomic transaction failure only for a single attempted execution window (which the legitimate keeper can simply retry in a subsequent slot, since `order` itself is not consumed by a failed/pre-empted `StartExecuteOrder`+`EndExecuteOrder` attempt).

### Likelihood Explanation
Low-to-Medium. Exploiting this requires unverified confirmation that `validate_instructions` does not adequately bind the `start`/`end` pair to the same execution flow/executor for the specific order, which I could not confirm within the available tool budget. Absent that confirmation, this is a plausible but not proven DoS vector, and the underlying design (permissionless keeper execution) is likely intentional, with the atomic same-transaction pairing being the intended safeguard against exactly the class of griefing described in the Meson report.

### Recommendation
- Short term: Audit `validate_instructions` (in `liquidate_start.rs`) to confirm it strictly enforces that a matching, correctly-executor-signed `end_execute_order` for the *same* `order`/`execute_record` pair is present in the same transaction as `start_execute_order`, preventing any dangling/poisoned `execute_record` state from a single unpaired call.
- Long term: Consider requiring `executor` to be a `Signer` already at `StartExecuteOrder` time (rather than only at `EndExecuteOrder`), so that occupying a user's `execute_record` slot always requires a real, attributable signature up front, reducing the surface for mempool front-running/griefing of pending orders — directly analogous to Meson's long-term recommendation to bind postings to a verified initiator/executor identity rather than relying solely on an identifier lacking that binding.

### Proof of Concept
Not constructed — full exploitation requires resolving the open question above (exact enforcement semantics of `validate_instructions`) plus a live/bankrun test harness which I did not have execution access to in ask-only mode. pub struct EndExecuteOrder<'info> {
    #[account(
        constraint = (!group.load()?.is_protocol_paused()) @ MarginfiError::ProtocolPaused
    )]
    pub group: AccountLoader<'info, MarginfiGroup>,

    /// The account owning the order
    #[account(
        mut,
        has_one = group @ MarginfiError::InvalidGroup,
        constraint = {
            let acc = marginfi_account.load()?;
            acc.get_flag(ACCOUNT_IN_ORDER_EXECUTION)
                && !acc.get_flag(ACCOUNT_IN_FLASHLOAN)
                && !acc.get_flag(ACCOUNT_FROZEN)
                && !acc.get_flag(ACCOUNT_DISABLED)
                && !acc.get_flag(ACCOUNT_IN_RECEIVERSHIP)
                && !acc.get_flag(ACCOUNT_IN_DELEVERAGE)
        } @MarginfiError::UnexpectedOrderExecutionState
    )]
    pub marginfi_account: AccountLoader<'info, MarginfiAccount>,

    /// The executioner ☠️
    pub executor: Signer<'info>,

    /// CHECK: no checks whatsoever, executor decides this without restriction
    #[account(mut)]
    pub fee_recipient: UncheckedAccount<'info>,

    #[account(
        mut,
        has_one = marginfi_account,
        close = fee_recipient
    )]
    pub order: AccountLoader<'info, Order>,

    /// This keeps track of the relevant state to be checked at the end of execution.
    #[account(
        mut,
        has_one = order,
        has_one = executor,
        close = fee_recipient
    )]
    pub execute_record: AccountLoader<'info, ExecuteOrderRecord>,

    // Note: there is just one FeeState per program, so no further check is required.
    #[account(
        seeds = [FEE_STATE_SEED.as_bytes()],
        bump,
    )]
    pub fee_state: AccountLoader<'info, FeeState>,
}
