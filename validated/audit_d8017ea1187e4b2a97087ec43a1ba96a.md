### Title
Malicious integrator/protocol fee recipient can block legitimate `EscrowDst.withdraw` when destination asset is native ETH - (File: contracts/EscrowDst.sol)

### Summary
`EscrowDst._withdraw` performs up to three sequential, unconditional token/native transfers (integrator fee, protocol fee, and the maker's net amount) plus a safety-deposit transfer to the caller in a single atomic call. When the destination asset is native ETH, the fee transfers use `_ethTransfer`, a low-level `call` to the fee recipient that reverts the whole transaction if the recipient rejects the payment. The integrator/protocol fee recipient addresses are attacker-influenced data that travels from the maker's order fill on the source chain (`_postInteraction` extraData) into the destination escrow's immutables `parameters`, so a malicious order creator can poison this field and deterministically block `withdraw`/`publicWithdraw` on the destination escrow. [1](#0-0) [2](#0-1) 

### Finding Description
`_withdraw` in `EscrowDst.sol` transfers the integrator fee, then the protocol fee, then the remaining amount to the maker, and finally the safety deposit to the caller — all in one transaction: [3](#0-2) 

`_uniTransfer`/`_ethTransfer` in `BaseEscrow.sol` revert the entire call if a native-token `call` to the recipient fails: [4](#0-3) 

The `integratorFeeRecipient` and `protocolFeeRecipient` addresses are decoded from `extraData` supplied at order fill time (`_postInteraction`), then packed into the destination escrow's `parameters` and read back via `ImmutablesLib.integratorFeeRecipientCd`/`protocolFeeRecipientCd` during `_withdraw`: [5](#0-4) [6](#0-5) 

If the destination token is native ETH (`dstToken == address(0)`), a maker who controls (or colludes to set) the fee-recipient fields can point one of them at a contract with a reverting/absent `receive()`/`fallback()`. Once the resolver deploys the `EscrowDst` clone with the poisoned immutables and later calls `withdraw`/`publicWithdraw` with the valid secret, the `_ethTransfer` to the poisoned fee recipient reverts, which reverts the entire `_withdraw` — including the safety-deposit payout to the caller and the maker's own principal transfer — for as long as the withdrawal window is open. This mirrors the root cause in the external report: an atomic multi-recipient payout where one poisoned recipient blocks all legitimate transfers in the same call.

Note: this only applies when the destination asset is native ETH; for ERC20 destination tokens, `safeTransfer` does not invoke the recipient's code, so a recipient address alone cannot force a revert (this differs from the external report's malicious-*token* scenario, since the ERC20 here is not attacker-controlled).

### Impact Explanation
Unlike the original IntentVault bug, `EscrowDst.cancel` does not perform any fee-split transfers — it sends the full `immutables.amount` straight to the taker (resolver) and the safety deposit to the caller: [7](#0-6) 

So a resolver is not permanently robbed; they can eventually reclaim their deposited ETH via `cancel` once the cancellation timelock elapses. The concrete impact is: (1) the maker never receives the destination payout via the intended `withdraw` path within the withdrawal window (the swap effectively always fails), and (2) the resolver's deposited native ETH and safety deposit are frozen in the escrow for the full withdrawal window until the cancellation timelock opens, i.e., temporary freezing of funds during the live swap lifecycle, and the destination escrow is rendered unable to complete its core operation (`withdraw`) due to a balance/recipient condition set by an unprivileged actor (the maker).

### Likelihood Explanation
Requires (a) the destination asset for a given swap to be native ETH, and (b) the attacker to control or influence the `integratorFeeRecipient`/`protocolFeeRecipient` fields encoded in the fill's `extraData`, which are ultimately derived from order/extension data associated with the maker's order. I was not able to fully confirm from the indexed code/tests whether these fee-recipient fields are always fixed by the resolver/integrator infrastructure (in which case a maker cannot influence them) or can be freely chosen by whoever constructs the fill call/extension for a given order. This is a material open question that determines whether the "unprivileged actor" attacker model is actually satisfiable in production, and could not be resolved with the available index (the wiring between the signed order's `extension` and `_postInteraction`'s `extraData` argument is defined in the imported `limit-order-protocol`/`limit-order-settlement` packages, whose full source was not available in this index).

### Recommendation
Perform fee and principal transfers independently using low-level calls that do not propagate failure (matching the fix pattern used in the cited external report), e.g. wrap each `_uniTransfer` fee payout in a try/catch or record failed fee transfers for later rescue, so a poisoned fee recipient cannot block the maker's principal payout or the caller's safety-deposit payout in the same transaction.

### Proof of Concept
1. Attacker (maker) creates a Fusion order whose destination token is native ETH (`dstToken = address(0)`), and crafts/collaborates on the fill `extraData` such that `integratorFeeRecipient` (or `protocolFeeRecipient`) is set to `EvilReceiver`, a contract with no payable `receive()`/`fallback()` (or one that unconditionally reverts).
2. Resolver fills the order; `_postInteraction` encodes `integratorFeeRecipient`/`protocolFeeRecipient` into `DstImmutablesComplement.parameters` [8](#0-7) .
3. Resolver calls `createDstEscrow{value: ...}` funding the `EscrowDst` clone with the destination ETH and safety deposit [9](#0-8) .
4. Once the withdrawal window opens and the secret is revealed, resolver calls `EscrowDst.withdraw(secret, immutables)`. Execution reaches `_ethTransfer(EvilReceiver, integratorFeeAmount)` inside `_withdraw`, which reverts with `NativeTokenSendingFailure`, reverting the whole transaction [3](#0-2) [10](#0-9) .
5. Every subsequent `withdraw`/`publicWithdraw` attempt within the withdrawal/public-withdrawal windows fails identically, forcing the swap to fall through to `cancel` after the `DstCancellation` timelock, where funds return to the resolver without any fee-split logic [11](#0-10) .

    function _withdraw(bytes32 secret, Immutables calldata immutables)
        internal
        onlyValidImmutables(immutables.hash())
        onlyValidSecret(secret, immutables.hashlock)
    {
        uint256 integratorFeeAmount = immutables.integratorFeeAmountCd();
        uint256 protocolFeeAmount = immutables.protocolFeeAmountCd();
        if (integratorFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.integratorFeeRecipientCd().get(), integratorFeeAmount);
        }
        if (protocolFeeAmount > 0) {
            _uniTransfer(immutables.token.get(), immutables.protocolFeeRecipientCd().get(), protocolFeeAmount);
        }
        uint256 amount = immutables.amount - integratorFeeAmount - protocolFeeAmount;
        _uniTransfer(immutables.token.get(), immutables.maker.get(), amount);
        _ethTransfer(msg.sender, immutables.safetyDeposit);
        emit EscrowWithdrawal(secret);
    }

    function createDstEscrow(IBaseEscrow.Immutables calldata dstImmutables, uint256 srcCancellationTimestamp) external payable {
        address token = dstImmutables.token.get();
        uint256 nativeAmount = dstImmutables.safetyDeposit;
        if (token == address(0)) {
            nativeAmount += dstImmutables.amount;
        }
        if (msg.value != nativeAmount) revert InsufficientEscrowBalance();

        IBaseEscrow.Immutables memory immutables = dstImmutables;
        immutables.timelocks = immutables.timelocks.setDeployedAt(block.timestamp);
        // Check that the escrow cancellation will start not later than the cancellation time on the source chain.
        if (immutables.timelocks.get(TimelocksLib.Stage.DstCancellation) > srcCancellationTimestamp) revert InvalidCreationTime();

        bytes32 salt = immutables.hashMem();
        address escrow = _deployEscrow(salt, msg.value, ESCROW_DST_IMPLEMENTATION);
        if (token != address(0)) {
            IERC20(token).safeTransferFrom(msg.sender, escrow, immutables.amount);
        }

        emit DstEscrowCreated(escrow, immutables.hashlock, immutables.taker);
    }
