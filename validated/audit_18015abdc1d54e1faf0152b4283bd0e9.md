### Title
Staker Receives Fewer Rewards Than Entitled When `rewards_pool` Balance Is Insufficient — (`File: crates/sui-framework/packages/sui-system/sources/staking_pool.move`)

---

### Summary

`withdraw_rewards` in `staking_pool.move` silently caps the actual reward payout to the current `rewards_pool` balance when that balance is less than the exchange-rate-calculated entitlement. The caller (`request_withdraw_stake`) then records the **full** pool-token amount as withdrawn and destroys the staker's `StakedSui` object. The staker permanently loses the difference between their entitled rewards and what was actually paid, with no way to reclaim it.

---

### Finding Description

In `withdraw_rewards`:

```move
fun withdraw_rewards(
    pool: &mut StakingPool,
    principal_withdraw_amount: u64,
    pool_token_withdraw_amount: u64,
    epoch: u64,
): Balance<SUI> {
    let exchange_rate = pool.pool_token_exchange_rate_at_epoch(epoch);
    let total_sui_withdraw_amount = exchange_rate.get_sui_amount(pool_token_withdraw_amount);
    let mut reward_withdraw_amount = if (total_sui_withdraw_amount >= principal_withdraw_amount) {
        total_sui_withdraw_amount - principal_withdraw_amount
    } else 0;

    // This may happen when we are withdrawing everything from the pool and
    // the rewards pool balance may be less than reward_withdraw_amount.
    // TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN.
    reward_withdraw_amount = reward_withdraw_amount.min(pool.rewards_pool.value());
    pool.rewards_pool.split(reward_withdraw_amount)
}
``` [1](#0-0) 

The function computes `reward_withdraw_amount` from the stored exchange rate, then **silently clamps** it to `pool.rewards_pool.value()`. The clamped (lesser) balance is returned.

The caller `request_withdraw_stake` then does:

```move
let rewards_withdraw = pool.withdraw_rewards(...);
let total_sui_withdraw_amount = principal_withdraw_amount + rewards_withdraw.value();

pool.pending_total_sui_withdraw = pool.pending_total_sui_withdraw + total_sui_withdraw_amount;
pool.pending_pool_token_withdraw =
    pool.pending_pool_token_withdraw + pool_token_withdraw_amount;
``` [2](#0-1) 

`pending_pool_token_withdraw` is incremented by the **full** `pool_token_withdraw_amount` (the staker's entire entitlement), while `pending_total_sui_withdraw` only reflects the capped, lesser amount actually paid. The `StakedSui` object is then destroyed:

```move
principal_withdraw.join(rewards_withdraw);
principal_withdraw
``` [3](#0-2) 

The staker's receipt is gone. The shortfall stays in `rewards_pool` and is silently redistributed to remaining stakers.

**When does `rewards_pool.value() < reward_withdraw_amount`?**

This occurs when the exchange rate used to compute the entitlement is stale — specifically when epochs are missing from the `exchange_rates` table (e.g., after safe-mode epochs). `pool_token_exchange_rate_at_epoch` falls back to the most recent available rate:

```move
while (epoch >= activation_epoch) {
    if (pool.exchange_rates.contains(epoch)) {
        return pool.exchange_rates[epoch]
    };
    epoch = epoch - 1;
};
``` [4](#0-3) 

A stale (earlier) rate can imply a higher SUI entitlement than the `rewards_pool` actually holds, triggering the cap. The existing test suite confirms this scenario is reachable and produces the discrepancy:

```
// total withdraw: min(100 * 155000000000 / 86666666666, pool.sui_balance()) = 155000000000
assert!(pool.pool_token_balance() < pool.pending_pool_token_withdraw_amount());
``` [5](#0-4) 

The same silent cap is also present in `calculate_rewards`, meaning the displayed reward estimate already hides the shortfall from the user: [6](#0-5) 

---

### Impact Explanation

Any ordinary SUI holder who staked before a safe-mode period and withdraws afterward will receive fewer SUI rewards than the exchange rate entitles them to. Their `StakedSui` object is consumed in the same transaction, making the loss **permanent and irreversible**. The shortfall is not burned — it remains in `rewards_pool` and accrues to other stakers, constituting an involuntary transfer of value away from the withdrawing staker.

This matches the allowed impact gate: **harmful smart-contract behavior / permanent fund loss** reachable from public input (the public entry `sui_system::request_withdraw_stake`).

---

### Likelihood Explanation

Safe mode has been activated on Sui mainnet. Any staker who withdraws after a safe-mode period where one or more epoch exchange rates were not recorded is exposed. The condition is not rare or adversarially constructed — it is a normal consequence of the network's safe-mode recovery path. The developers themselves flag the condition with `// TODO: FIGURE OUT EXACTLY WHY THIS CAN HAPPEN.` [7](#0-6) 

---

### Recommendation

`withdraw_rewards` must not silently cap the payout. Two options:

1. **Assert sufficiency**: `assert!(pool.rewards_pool.value() >= reward_withdraw_amount, EInsufficientRewardsPoolBalance)` — abort the transaction so the staker's `StakedSui` is not consumed.
2. **Track the shortfall**: Record the unpaid reward amount in a per-staker or pool-level field so the staker can claim it once the pool is replenished, rather than silently forfeiting it.

The root cause (stale exchange rates after safe mode) should also be addressed so that the `rewards_pool` balance is always consistent with the exchange rates stored in the table.

---

### Proof of Concept

1. Validator pool is active. Epoch 1 runs normally; exchange rate is recorded.
2. Epochs 2–4 are safe-mode epochs; no exchange rates are recorded for those epochs.
3. Epoch 5 runs normally; new exchange rate is recorded with a higher SUI/token ratio.
4. Staker who staked in epoch 1 calls `sui_system::request_withdraw_stake` in epoch 5.
5. `pool_token_exchange_rate_at_epoch(stake_activation_epoch=1)` returns the epoch-1 rate.
6. `pool_token_exchange_rate_at_epoch(current_epoch=5)` returns the epoch-5 rate.
7. The computed `reward_withdraw_amount` exceeds `pool.rewards_pool.value()` because the epoch-5 rate implies more accumulated rewards than were actually deposited into `rewards_pool` (safe-mode epochs contributed no rewards but the rate jumped).
8. `reward_withdraw_amount` is silently clamped; the staker receives less SUI than owed.
9. The staker's `StakedSui` is destroyed; the shortfall is unrecoverable.

This exact scenario is exercised by the existing test at `crates/sui-framework/packages/sui-system/tests/rewards_distribution_tests.move` lines 901–1018. [8](#0-7)
