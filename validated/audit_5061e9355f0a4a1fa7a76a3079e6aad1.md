### Title
Attacker-forgeable `StageCommandStatus` JSON in job stdout causes stale/false `IsExited()==true`, letting `runWithAttach`'s cancellation branch skip `stageCancellationScript` while a real process is still alive - (File: executors/kubernetes/kubernetes.go)

### Summary
`forwardLogLine` sets the executor-wide `s.remoteStageStatus` field whenever a stdout log line successfully unmarshals into `shells.StageCommandStatus`, with no authentication that the line actually originated from the runner's own trap script rather than the job's own script output. Because this status is shared across the whole build (never reset per-stage) and the cancellation check in `runWithAttach` only inspects `IsExited()` without correlating to the current stage or actual process liveness, a job script can leave the executor believing a process has exited when it (or a later stage's real process) is still running, causing the cancellation script to be skipped.

### Finding Description
The stage script's stdout/stderr is redirected into the same log file the runner's exit-status trap writes its JSON marker to: `s.buildRedirectionCmd` pipes everything through `2>&1 | tee -a %s` [1](#0-0) . This file is tailed by the log processor, and every line is passed to `forwardLogLine`, which tries to parse it as `shells.StageCommandStatus` via `TryUnmarshal` [2](#0-1) . `TryUnmarshal` only requires the JSON object to contain `command_exit_code` and/or `script`; it has no signature, nonce, or other binding to the actual trap invocation [3](#0-2) . Consequently a job script that echoes `{"command_exit_code":0,"script":"<stage>"}` to stdout is indistinguishable from the legitimate trap marker.

When such a line is parsed, `forwardLogLine` unconditionally overwrites `s.remoteStageStatus` (guarded only by `remoteStageStatusMutex`, not scoped per stage or per invocation) and, if `IsExited()`, pushes to `s.remoteProcessTerminated` [4](#0-3) . `s.remoteStageStatus` is never reset when a new stage begins in `runWithAttach` or `ensurePodsConfigured`; it persists across stages of the same build because `processLogs`/log tailing is started once per pod, not once per stage [5](#0-4) .

The cancellation branch in `runWithAttach` only checks the stale/global flag, not the stage or actual liveness of the exec'd process:
```
case <-ctx.Done():
    ...
    script := s.stageCancellationScript(string(cmd.Stage))
    if !s.remoteStageStatus.IsExited() {
        err := <-s.runInContainerWithExec(...) // runs stageCancellationScript
    }
    return fmt.Errorf("build aborted")
``` [6](#0-5) 

Note that `StageCommandStatus.BuildStage()` exists specifically to disambiguate which stage a status line refers to (and is used for that purpose in `checkScriptExecution`'s retry logic) [7](#0-6) [8](#0-7) , but the cancellation check in `runWithAttach` does not use it — it blindly trusts the last-seen global `IsExited()` value.

Exploit flow:
1. A job stage's script prints a forged exit-status JSON line to its own stdout (which is teed into the shared log file consumed by the log processor), then continues running (or forks/execs a detached background child) without truly terminating.
2. `forwardLogLine` marks `s.remoteStageStatus.IsExited() == true` and/or the completion is consumed prematurely by `runInContainer`'s goroutine, letting `runWithAttach` return early while the underlying process is still alive in the container.
3. Because `s.remoteStageStatus` is not reset, this stale `IsExited()==true` value persists into subsequent stage executions (e.g. `after_script`, cleanup).
4. If the job is cancelled while a later stage's genuinely-running process has not yet emitted any status line, `ctx.Done()` in `runWithAttach` sees the stale `IsExited()==true` and skips `s.runInContainerWithExec(... stageCancellationScript ...)`, leaving the real process running inside the pod unterminated.

Existing checks are insufficient: there is no cross-check against `BuildStage()`, no per-invocation nonce/token binding the exit marker to a specific `ExecOptions`/`executeRequest` call, and no verification against actual pod/container process state (e.g. via `/proc` liveness) before skipping cancellation.

### Impact Explanation
A job's script (fully attacker-controlled) can suppress the runner's own process-cleanup logic on cancellation, leaving processes running inside the build pod after the job is supposedly aborted. This delays pod/namespace teardown and can leave resources consumed/occupied longer than intended in namespaces that may be shared across jobs (depending on runner namespace-per-job configuration), matching the scoped "persistent process leakage... surviving job cancellation" impact.

### Likelihood Explanation
This is fully reachable by an unprivileged pipeline author: it only requires writing arbitrary text to stdout in a job script, which is the most basic capability of any CI job, combined with backgrounding a process so the script's controlling process appears to exit early or the log stream includes a forged completion line before the real work finishes. No cluster-admin, docker.sock, or privileged-container assumptions are needed — the bug lives purely in the trust the log-processing/exit-marker protocol places in the shared stdout stream. It is deterministically reproducible.

### Recommendation
- Bind the trap-generated exit marker to something the job's own script output cannot forge (e.g. a random per-invocation token embedded by the runner and required in the JSON, or write the exit marker to a distinct fd/side-channel not reachable by the tee'd stdout stream).
- Scope `s.remoteStageStatus`/`remoteProcessTerminated` per invocation/stage (reset at the start of each `runWithAttach`/`runInContainer` call) instead of using a single persistent executor field.
- In `runWithAttach`'s cancellation branch, verify `s.remoteStageStatus.BuildStage() == cmd.Stage` (as already done in `checkScriptExecution`) in addition to `IsExited()`, and/or independently probe process liveness (e.g. via the same `/proc` scan used in `stageCancellationScript`) rather than trusting only the log-derived flag.

### Proof of Concept
Go unit test sketch (executors/kubernetes/kubernetes_test.go style):
1. Construct an `executor` with a fake `kubeClient`/`ExecOptions.Executor` stub recording invocations of `runInContainerWithExec`.
2. Start stage A's `runWithAttach` with a script that writes a spoofed `{"command_exit_code":0,"script":"stepA"}` line via a fake log source feeding `forwardLogLine` directly, while a real backgrounded goroutine simulating the exec'd process remains "alive" (e.g. a channel not yet closed).
3. Assert `s.remoteStageStatus.IsExited() == true` after the spoof, without the real process channel having closed.
4. Begin stage B's `runWithAttach` (different `cmd.Stage`), cancel its context (`cancel()`), and assert that `runInContainerWithExec` IS invoked with `stageCancellationScript(stage B)` (currently it would be skipped because of the stale flag) — expected assertion: `mockExec.CalledWith(stageCancellationScript)` is true, and fails on current code because `!s.remoteStageStatus.IsExited()` evaluates false due to the stale/forged status from stage A.

		// powershell outputs utf16, so we re-encode the output to utf8
		// this is important because our json decoder that detects the exit status

func (s *executor) forwardLogLine(w io.Writer, line string) {
	var status shells.StageCommandStatus
	if !status.TryUnmarshal(line) {
		if _, err := w.Write([]byte(line)); err != nil {
			s.BuildLogger.Warningln(fmt.Sprintf("Error writing log line to trace: %v", err))
		}

		return
	}

	s.BuildLogger.Debugln(fmt.Sprintf("Setting remote stage status: %s", status))
	s.remoteStageStatusMutex.Lock()
	s.remoteStageStatus = status
	s.remoteStageStatusMutex.Unlock()

	if status.IsExited() {
		s.remoteProcessTerminated <- status
	}
}

// TryUnmarshal tries to unmarshal a json string into its pointer receiver.
// It wil return true only if the unmarshalled struct has all of its required fields be non-nil.
// It's safe to use the struct only if this method returns true.
func (c *StageCommandStatus) TryUnmarshal(line string) bool {
	var status stageCommandExitStatusImpl
	err := status.tryUnmarshal(line)
	if err != nil {
		return false
	}

	if status.isEmpty() {
		return false
	}

	status.applyTo(c)

	return true
}

func (c StageCommandStatus) IsExited() bool {
	return c.CommandExitCode != nil
}

func (c StageCommandStatus) BuildStage() common.BuildStage {
	if c.Script == nil {
		return ""
	}

	// When using `powershell/pwsh`, script contains only the script name without its extension being executed.
	// When using `bash` shell, script contains the script absolute path. We therefore need to extract the script name.
	split := strings.Split(*c.Script, "/")
	stage := split[len(split)-1]

	return common.BuildStage(stage)
}
