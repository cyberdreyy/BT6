### Title
Loss-adjusted withdraw receipts keyed to the wrong epoch are paid at par, breaking the stopEpochWithDuration haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`collectWithdrawFunds` stores the partial-funding haircut under the *post-increment* `epochNumber`, while pending receipts and `lastWithdrawRequest` are recorded under the *request-time* epoch. Because `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` and treats `0` as "no loss-adjusted epoch", every pending receipt falls through to `_claimFundedWithdrawRequest` and is paid 1:1 even though the strategy only collected the haircutted amount. This is the same bug class as the referenced advisory: a required per-record field (the recovery price keyed by the correct epoch) is missing/NULL at lookup time and the code does not verify the record it actually dereferences.

### Finding Description
The normal lifecycle is:

1. During buffer/epoch N a user calls `requestWithdraw`, which records `withdrawsRequestsByEpoch[user][epochNumber = N]` and `lastWithdrawRequest[user] = N`, and adds `_amount` to `pendingWithdraws` [1](#0-0) .
2. At `stopEpoch`/`stopEpochWithDuration` the CDO repays funds through `deposit()`, which increments `epochNumber` to N+1 while `isEpochRunning()` is still true [2](#0-1) .
3. When the borrower underfunds (`_amount < pendingBasis`), `collectWithdrawFunds` writes the haircut to `lossRecoveryPriceByEpoch[epochNumber]` — i.e. key **N+1**, not key **N** where the receipts live [3](#0-2) .
4. On claim, `_claimLossAdjustedWithdrawRequest` reads `lossRecoveryPriceByEpoch[lastWithdrawRequest[user]]` = `lossRecoveryPriceByEpoch[N]` = `0` and returns 0 [4](#0-3) .
5. Execution continues into `_claimFundedWithdrawRequest`, which pays the full `withdrawsRequests[user]` at par once `epochNumber > lastWithdrawRequest[user]` (now N+1 > N) [5](#0-4) .

The same mismatch defeats the guard in `requestWithdraw` (lines 261-271): `lossRecoveryPriceByEpoch[lastWithdrawRequest]` reads key N, so an unclaimed haircutted receipt is invisible and the user can even stack new requests. The invariant broken is "one receipt, one loss-adjusted payout": the pending-loss portion computed by `previewLossAdjustedWithdrawFunds` is never actually applied to any receipt.

Caveat I could not fully verify within search limits: this depends on `epochNumber` having been incremented before `collectWithdrawFunds` is invoked inside `stopEpoch`/`stopEpochWithDuration` in `IdleCDOEpochVariant.sol`/`IdleCDOEpochVariantPrefunded.sol`. Given `epochNumber` only ever increments inside `deposit()` when `isEpochRunning()` [2](#0-1)  and the funding flow necessarily routes through `deposit`/`collectWithdrawFunds` during stopEpoch, the mismatch holds unless `collectWithdrawFunds` is deliberately invoked before the deposit — in which case keys align and the bug disappears. The surrounding tests only exercise the full-funding branch, so the loss path is uncovered either way.

### Impact Explanation
Direct insolvency: the strategy collects `pendingBasis - pendingLoss` from the borrower but pays out `pendingBasis`. Every pending withdrawer of the loss epoch can claim un-haircutted funds; the deficit is socialized to whoever claims last or to remaining active holders whose NAV was already reduced by `activeLoss`. The loss is effectively applied twice to the pool (once to active NAV, zero times to receipts) instead of once.

### Likelihood Explanation
Requires only an honest `stopEpochWithDuration(_lossAmount)` (borrower repays less than owed — a normal credit event, not a malicious privileged action). Any unprivileged lender with a pending withdraw receipt in that epoch triggers the overpayment by simply calling `claimWithdrawRequest`.

### Recommendation
Store the haircut under the epoch in which the pending receipts were recorded (e.g. `epochNumber - 1` after the deposit increment, or the epoch captured at `startEpoch`), or better: make `collectWithdrawFunds` derive the loss epoch from the receipt bookkeeping (`lastWithdrawRequest`/a dedicated `pendingWithdrawEpoch`) rather than the mutable global counter, and add a `NotAllowed` revert if a pending-receipt claim finds no recovery price for a partially funded epoch.

### Proof of Concept
Foundry sketch (fork of existing `test/foundry/IdleCreditVault.t.sol` harness):

```solidity
// setup: depositAA, user1 deposit, user1 requestWithdraw during epoch 0
// startEpoch(0); warp past epochEndDate
// borrower repays less than owed: stopEpochWithDuration(loss)
uint256 pending = creditVault.pendingWithdraws();          // > 0
uint256 funded = pending - loss_share;                     // partial funding
// inside stopEpochWithDuration: deposit() bumps epochNumber 0 -> 1,
// collectWithdrawFunds(funded) sets lossRecoveryPriceByEpoch[1] = funded*1e18/pending
assertEq(creditVault.lossRecoveryPriceByEpoch(1), expectedPrice);
assertEq(creditVault.lossRecoveryPriceByEpoch(0), 0);      // user's request epoch

// user claims: _claimLossAdjustedWithdrawRequest sees price[0]==0, returns 0
// _claimFundedWithdrawRequest pays withdrawsRequests[user] in full
uint256 balPre = underlying.balanceOf(user1);
vm.prank(user1);
cdoEpoch.claimWithdrawRequest();
uint256 paid = underlying.balanceOf(user1) - balPre;
assertEq(paid, pending);            // expected: pending * recoveryPrice / 1e18
// strategy underlying balance is now insolvent by pending - funded
```

Expected assertion: `paid` equals the full `pending` basis instead of `pending * lossRecoveryPrice / 1e18`, leaving `underlying.balanceOf(strategy)` short by the unapplied `pendingLoss`.
