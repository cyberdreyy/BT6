### Title
`claimInstantWithdrawRequest` pays the full aggregate instant-withdraw receipt at par without validating that the corresponding funds were actually collected — unfunded receipts drain the strategy's underlying balance (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.claimInstantWithdrawRequest` assembles the payout as a single aggregate — `instantWithdrawsRequests[_user]` spanning every request epoch — and transfers it via `_transferFundedClaim` without verifying that `collectInstantWithdrawFunds` actually pulled enough underlying from the CDO to cover that aggregate. This mirrors the hashcat `outfile_write()` overflow: the function "appends" receipt amounts into one output buffer (the user's claim) and pays it out without checking the accumulated total against funded capacity.

### Finding Description
`requestInstantWithdraw` increments three counters: per-user `instantWithdrawsRequests[_user]`, per-user-per-epoch `instantWithdrawsRequestsByEpoch[_user][epoch]`, and the global unfunded remainder `pendingInstantWithdraws` [1](#0-0) . Funding arrives separately through `collectInstantWithdrawFunds`, which decrements `pendingInstantWithdraws` and pulls underlying from the CDO [2](#0-1) .

The claim path then does:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
``` [3](#0-2) 

There is no check that the aggregate receipt was funded — `pendingInstantWithdraws`, `instantWithdrawClaimsByEpoch`, and the per-epoch basis are ignored except in the post-default path, which only clears `instantWithdrawsRequestsByEpoch[_user][defaultEpoch]` for the single default epoch [4](#0-3) . Two consequences:

1. **Partial funding overpays.** If the CDO collects only part of a pending instant queue (partial `collectInstantWithdrawFunds`, which is explicitly contemplated — the code comments note "that cash covered only part of the instant queue" [5](#0-4) ), a claimant still receives 100% of `instantWithdrawsRequests[_user]` at par.

2. **Stale cross-epoch receipts escape the haircut.** A receipt requested in epoch `e < defaultRecoveryEpoch` that was never funded is not included in `defaultPendingClaimBasis` — only `instantWithdrawClaimsByEpoch[epochNumber]` (current epoch) is added [6](#0-5)  — and `_claimDefaultedInstantWithdrawRequest` only clears the default epoch's basis. The stale receipt remains in `instantWithdrawsRequests[_user]` and is paid at par through `_transferFundedClaim`, whose only guard is `balance - defaultRecoveryReserve >= amount` [7](#0-6) . That guard protects the reserve, not other claimants' funded balances.

### Impact Explanation
An unprivileged lender (tranche-token holder) who requested an instant withdraw that was only partially funded — or left an unfunded instant receipt from an epoch before a borrower default — claims the full aggregate amount at par. The payout consumes underlying held by the strategy for legitimately funded loss-adjusted withdraw claims and other funded instant receipts, i.e., theft of unclaimed withdrawals / insolvency for later claimants, quantified as the unfunded remainder of the attacker's aggregate receipt. In the worst case, if the non-reserve balance is insufficient, the transaction reverts and genuinely funded claimants are temporarily frozen behind the inflated claimant ordering.

### Likelihood Explanation
Requires the CDO to call `claimInstantWithdrawRequest` on the user's behalf while the instant queue is only partially funded, or a default finalization while a stale cross-epoch instant receipt exists. `defaultInstantWithdrawsFinalized` is set whenever `pendingInstantWithdraws != 0` at finalization [8](#0-7) , and `defaultPendingClaimBasis` only counts current-epoch instant basis — so any earlier-epoch unfunded remainder structurally escapes recovery accounting. Note a caveat: `claimInstantWithdrawRequest` is `_onlyIdleCDO`-gated, so the practical exploitability depends on when `IdleCDOEpochVariant` exposes this claim to users; I could not confirm the exact CDO-side gating within the search budget, but no strategy-side funded check exists.

### Recommendation
Track funded vs. unfunded instant receipts per epoch and pay only the funded portion, or store a per-epoch funded price (like `lossRecoveryPriceByEpoch`) for instant claims. Include all non-zero `instantWithdrawClaimsByEpoch` entries — not just the current epoch — in `defaultPendingClaimBasis`, and clear stale `instantWithdrawsRequestsByEpoch[user][e]` entries during default claims so old unfunded receipts receive the recovery haircut instead of par payment.

### Proof of Concept
Foundry fork PoC sketch (fixed-APR, non-closed vault):

1. Lender deposits into AA tranche during buffer phase; `startEpoch` runs.
2. Attacker (KYC'd lender) calls CDO `requestInstantWithdraw` for amount `X`; strategy mints `X` receipt tokens and sets `pendingInstantWithdraws += X`.
3. At next `startEpoch`, the CDO only has cash to partially fund the instant queue: `collectInstantWithdrawFunds(X/2)` executes — `pendingInstantWithdraws = X/2`, strategy holds only `X/2` underlying for instant claims.
4. CDO calls `claimInstantWithdrawRequest(attacker)`: strategy burns the full `X` receipt and transfers `X` underlying via `_transferFundedClaim` — the guard passes because `defaultRecoveryReserve == 0` — overpaying `X/2` taken from funds earmarked for other funded withdraw claimants.
5. Variant B: leave the `X/2` unfunded receipt across `stopEpoch`; borrower defaults; `finalizeDefaultRecovery` computes reserve basis excluding the stale epoch; attacker claims the stale receipt at par post-finalization while current-epoch claimants take the haircut.

Assert: attacker receives `X` while only `X/2` was collected; sum of payouts exceeds funded balance (the analog of writes exceeding `HCBUFSIZ_LARGE`).

  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
