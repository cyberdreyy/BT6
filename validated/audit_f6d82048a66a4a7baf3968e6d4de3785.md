### Title
`MultisigFactory::create` has no failure callback, so attached NEAR is not returned to the caller if account creation fails (e.g. via account-name front-running) - (File: `multisig-factory/src/lib.rs`)

### Summary
`MultisigFactory::create` builds the target account deterministically from user-supplied input (`name.<factory_account_id>`) and issues a single promise batch — `create_account()` → `deploy_contract()` → `transfer(attached_deposit)` → `function_call("new", ...)` — with no `.then()` callback to detect failure and refund the caller.

### Finding Description
`create` computes the sub-account id purely from `name` and `env::current_account_id()`: [1](#0-0) . This is the same deterministic-target pattern flagged in the external report: any party can pre-create the account NEAR-side (an account name cannot be created twice), so the legitimate deployer's `create_account()` action inside the batch will fail. Unlike `lockup-factory` and `staking-pool-factory`, which both attach a `.then(ext_self::on_..._create(...))` callback that checks `is_promise_success()` and explicitly `Promise::new(predecessor_account_id).transfer(attached_deposit.0)` on failure ( [2](#0-1)  and [3](#0-2) ), `MultisigFactory::create` returns the raw promise with no failure handling at all: [4](#0-3) .

When the batched receipt (`create_account`+`deploy_contract`+`transfer`+`function_call`) fails because the target account already exists, the attached deposit that was queued for `.transfer()` never reaches the intended sub-account, and — because there is no callback — it is never returned to the original caller (`env::predecessor_account_id()`). The binding that should hold is: `deposit attached by caller == NEAR ultimately controlled by that caller`. Here that equality breaks: the caller's NEAR is consumed by the factory's outgoing (failed) receipt while no compensating transfer credits it back to them, unlike its sibling factories which explicitly restore this invariant.

### Impact Explanation
An unprivileged attacker who knows or predicts a target `name` (e.g., watching mempool/observing an expected vanity name, or racing a commonly-used name) can front-run by creating `name.<factory>` themselves before the legitimate caller's `create` transaction lands. The victim's `create` call then fails inside the promise batch, and — absent any refund callback — the attached NEAR deposit is not returned to the victim, resulting in funds effectively lost from the caller's perspective (frozen/misdirected rather than returned), matching the High-impact category "funds frozen ... or an accounting value diverging from reality where another party settles on it."

### Likelihood Explanation
Any user can call `MultisigFactory::create` with any `name`; account names are public/observable before finality, so front-running the sub-account creation requires no special privileges, matching the report's own "DoS as a result of front-running" scenario adapted to a fund-loss context here, since — unlike the Sequence `Factory.deploy` revert (which only reverts, refunding gas/deposit to the caller because the failing call itself reverts the whole transaction) — this NEAR promise-batch pattern separates the deposit-bearing promise from the calling transaction, so a batch failure does not automatically return funds without an explicit refund callback.

### Recommendation
Add a `.then()` callback to `MultisigFactory::create` (mirroring `on_lockup_create` / `on_staking_pool_create`) that checks `is_promise_success()` and explicitly transfers the attached deposit back to `env::predecessor_account_id()` if the account/deploy/init sequence failed.

### Proof of Concept
1. Attacker observes an in-flight `MultisigFactory::create(name="alice", ...)` transaction with attached deposit `D`.
2. Attacker submits `create_account` for `alice.<factory>` (or any transaction that results in that account existing) before the victim's transaction is included.
3. Victim's `create` call executes: the promise batch's `create_account()` action fails (account already exists), causing `deploy_contract`, `transfer(D)`, and `function_call("new", ...)` to also fail as part of the same receipt.
4. Because `create` has no `.then()` callback, no code path returns `D` to the victim's account; the deposit is not restored to the caller, unlike the equivalent failure path in `lockup-factory`/`staking-pool-factory`.

        &mut self,
        name: AccountId,
        members: Vec<MultisigMember>,
        num_confirmations: u64,
    ) -> Promise {
        let account_id = format!("{}.{}", name, env::current_account_id());
        Promise::new(account_id)
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                json!({ "members": members, "num_confirmations": num_confirmations })
                    .to_string()
                    .as_bytes()
                    .to_vec(),
                0,
                env::prepaid_gas() - CREATE_CALL_GAS,
            )
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
