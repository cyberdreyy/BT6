### Title
Users can split `requestWithdraw` into dust-sized requests to pay zero upfront management and performance fees - (File: contracts/IdleCDOEpochVariant.sol)

### Summary
`IdleCDOEpochVariant.requestWithdraw` computes the withdrawal fee per request via `_totalWithdrawFees`, which relies on two floor-division products: `_calculateManagementFee` (`nav * managementFee * duration / 3153600000000`) and the performance fee inside `_netGainAfterFees` (`gain * fee / FULL_ALLOC`). Both round down to 0 for small enough inputs, and there is no minimum request amount, so a KYC'd lender can fragment one withdrawal into many calls and pay no fees while still receiving principal plus per-request interest.

### Finding Description
In `requestWithdraw` (contracts/IdleCDOEpochVariant.sol:739-791), after `_trancheToUnderlyings`, the receipt amount is computed as:

```solidity
(uint256 interest, int256 diff) = _calcInterestWithdrawRequest(_underlyings, _tranche);
uint256 totalFees = _totalWithdrawFees(principal, interest);
_underlyings = principal + interest - totalFees;
pendingWithdrawFees += totalFees;
```

`_totalWithdrawFees` (IdleCDOEpochVariant.sol:900-906) returns `_mgmtFee` when `_mgmtFee >= _interest`, else `interest - _netGainAfterFees(interest, _mgmtFee)`. Two rounding-to-zero paths exist:

- `_calculateManagementFee` (IdleCDOCreditVault.sol:558-561) = `principal * managementFee * duration / 3153600000000`. With `managementFee = 1000` (1%) and `duration ≈ 35 days ≈ 3.0e6 s`, the fee floors to 0 whenever `principal < ~1043` wei of underlying.
- When interest is positive but `< FULL_ALLOC / fee` (e.g. interest < 10 wei at a 10% performance fee), `_netGainAfterFees` (IdleCDOEpochVariant.sol:889-894) returns the gain unchanged, so `totalFees = interest - interest = 0`.

Per-request interest itself is prorated linearly (`_interest = _amount * totTrancheInterest / _trancheBal`, line 870), so a request sized just above the "interest ≥ 1 wei" threshold but below the "management fee ≥ 1 wei" threshold yields `principal + interest` with `totalFees == 0`. `requestWithdraw` performs no minimum-amount check — only `_checkTranche`, the allow-withdraw flags, and `isWalletAllowed` (lines 740-744) — and each request creates a normal claimable receipt via `creditVault.requestWithdraw` while `pendingWithdrawFees` accrues 0.

### Impact Explanation
The fee receivers (split between `feeReceiver` and owner per `_transferFeeUnderlyings` / `feeSplit`) lose the entire upfront management fee and net performance fee on withdrawals executed this way, up to `managementFee`-rate × principal plus `fee`-rate × interest for the requesting position. `pendingWithdrawFees` under-accruing also means `startEpoch`/`stopEpoch` accounting that treats those fees as reserved for fee receivers is off by the evaded amount. The loss is bounded by the total fee that would have been charged, matching the external report's medium-severity fee-loss class.

### Likelihood Explanation
An unprivileged KYC-passing lender can execute this during the buffer/stopped phase whenever `allowAAWithdrawRequest`/`allowBBWithdrawRequest` are set. The constraint is granularity: the dodged fee per request is at most ~1 wei of management fee plus a few wei of performance fee, so extracting a meaningful fraction of a large position requires many calls (roughly `principal / ~1000` requests at the parameters above). On low-gas networks this is economically viable; on mainnet the gas floor substantially shrinks the practical exploitability, which is why the realistic severity is medium/low rather than high. Uncertainty: I did not fully verify whether `IdleCreditVault.requestWithdraw` aggregates per-epoch receipts or enforces its own minimum; aggregation would not change the fee outcome since fees are computed in the CDO before the vault call, but a vault-side minimum would.

### Recommendation
Enforce a minimum `requestWithdraw` size (in underlying terms) such that `principal * managementFee * duration >= 3153600000000`, or round fees up (`ceil` division) so a nonzero fee is always charged, or accumulate a single per-user receipt per epoch and compute fees once on the aggregate.

### Proof of Concept
Foundry fork test sketch (extend `test/foundry/IdleCreditVault.t.sol`):

```solidity
function testRequestWithdrawFeeDodgedBySplitting() external {
    uint256 amount = 10_000 * ONE_SCALE;
    uint256 mgmtFeeRate = 1_000; // 1%
    _setFeeParams(TL_MULTISIG, 0, FULL_ALLOC, cdoEpoch.managementFee());
    _setManagementFee(mgmtFeeRate);

    uint256 trancheAmount = idleCDO.depositAA(amount);
    _transferBurnedTrancheTokens(address(this), true);

    // Baseline: one big request pays expectedMgmtFee > 0
    uint256 principal = trancheAmount * cdoEpoch.tranchePrice(address(AAtranche)) / ONE_TRANCHE_TOKEN;
    uint256 expectedMgmtFee = _calcManagementFee(principal, mgmtFeeRate, _withdrawRequestManagementFeeDuration());
    assertGt(expectedMgmtFee, 0);

    // Attacker: many requests each with principal < fee-rounding threshold
    uint256 feesBefore = cdoEpoch.pendingWithdrawFees();
    uint256 chunkTranche = 1e15; // tranche tokens worth < ~1043 wei underlying
    uint256 n = IERC20(AAtranche).balanceOf(address(this)) / chunkTranche;
    for (uint256 i; i < n; ++i) {
        cdoEpoch.requestWithdraw(chunkTranche, address(AAtranche));
    }
    // Invariant: no fees were accrued despite interest-bearing receipts
    assertEq(cdoEpoch.pendingWithdrawFees() - feesBefore, 0, "split requests dodge all fees");
}
```

Each chunk yields `_mgmtFee == 0` (principal below threshold) and performance fee `== 0` (interest below `FULL_ALLOC / fee`), so `pendingWithdrawFees` stays flat while the attacker later claims `principal + interest` per receipt via `claimWithdrawRequest`, versus paying `expectedMgmtFee` on the equivalent single request.
