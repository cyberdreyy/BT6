### Title
Stale confirmations from a removed member are still counted toward the confirmation threshold, allowing a request to execute with fewer than `num_confirmations` live members - (File: multisig2/src/lib.rs)

### Summary
`delete_member` only purges pending `requests`/`confirmations` for the *requests originally submitted by* the removed member, but it never scrubs that member's identity string out of the `confirmations` set of *other* still-pending requests that the member had merely confirmed. Any request that already sits at `num_confirmations - 1` before the member is removed can later be pushed to execution by one more live member, even though the actually-live confirming members are one short of `num_confirmations`.

### Finding Description
The invariant that should hold is: at the moment a request executes, `confirmations.len() == num_confirmations` and every entry in `confirmations` corresponds to an account/key that is still in `self.members`. `confirm()` only checks the *count* of `confirmations`, never re-validates that every stored identity is still a current member: [1](#0-0) 

`delete_member` removes pending requests/confirmations only for requests whose *original submitter* (`r.member`) is the member being deleted — it does not touch the `confirmations` set of other requests where the deleted member had simply added a confirmation: [2](#0-1) 

`assert_valid_request` also does nothing to revalidate stored confirmations against the current member set, it only checks the caller and that the request/confirmations entries exist: [3](#0-2) 

Exploit flow (fully reproducible with ordinary multisig usage, e.g. a multisig the "attacker" deploys and controls via the public factory, satisfying the rule that they may "create their own ... multisig through the public factories with chosen arguments"):
1. Member `A` submits request `R` (e.g. `Transfer`), and members `B` and `C` confirm it, leaving `confirmations(R) = {B, C}` with `num_confirmations = 3` (one short of execution).
2. Members submit and pass a separate `DeleteMember { member: C }` request. `delete_member` removes `C` from `self.members`, deletes any requests *created by* `C`, but leaves `confirmations(R) = {B, C}` untouched because `R` was created by `A`, not `C`.
3. Any remaining member `D` calls `confirm(R)`. `confirmations.len() as u32 + 1 == 3 >= num_confirmations`, so `R` executes — even though the only truly live confirming members are `B` and `D` (2), one short of the required 3.

Because `execute_request` can carry `Transfer`, `AddKey`, `FunctionCall`, or `DeployContract` actions, this lets a request that never had genuine `num_confirmations` support from *currently live* members move funds, add a new full-access key, or run an arbitrary function call — all guarded only by a confirmation count that includes a phantom, no-longer-a-member identity.

### Impact Explanation
This breaks the Critical-severity invariant explicitly listed in scope: "a multisig request executed below `num_confirmations` live members." The concrete consequence is that NEAR (or a granted key/deploy) leaves/affects the multisig account with one fewer genuine confirming member than the contract's configured threshold demands. This is repeatable on any multisig instance and against any pending request whenever a confirming member is later removed while a stale confirmation lingers — a normal, foreseeable membership-rotation scenario, not a contrived edge case.

### Likelihood Explanation
No special privilege beyond ordinary multisig membership/rotation is needed to trigger it — it only requires (a) a request sitting at `num_confirmations - 1` confirmations, and (b) any one of the confirming members being removed afterward via a routine `DeleteMember` action (a normal maintenance operation, e.g. rotating out a lost/compromised key). Both are common, expected multisig lifecycle events, making this highly likely to occur in production usage without any attacker needing special access — the "attacker" role here is satisfied by anyone able to deploy/operate their own multisig via the public factory to demonstrate the flaw.

### Recommendation
In `delete_member`, iterate over **all** entries in `confirmations` (not just requests where `r.member == member`) and remove the deleted member's identity string from every confirmation set; alternatively, revalidate in `confirm()`/`execute_request` that every string in `confirmations.get(&request_id)` still corresponds to a current member of `self.members` before counting it toward the threshold, discarding stale entries.

### Proof of Concept
```rust
#[test]
fn test_stale_confirmation_after_member_removal_still_counts() {
    let amount = 1_000;
    // members(): alice (Account), bob (Account), key1 (AccessKey "Eg2jts..."), key2 (AccessKey TEST_KEY)
    testing_env!(context_with_key(
        PublicKey::try_from(TEST_KEY.to_vec()).unwrap(),
        amount
    ));
    let mut c = MultiSigContract::new(members(), 3);

    // 1. alice submits transfer request R
    testing_env!(context_with_account(alice(), amount));
    let request_id = c.add_request(MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    });

    // 2. bob confirms -> confirmations = {bob}
    testing_env!(context_with_account(bob(), amount));
    c.confirm(request_id);

    // 3. key1 confirms -> confirmations = {bob, key1}, one short of 3
    let key1 = PublicKey::from(
        "Eg2jtsiMrprn7zgKKUk79qM1hWhANsFyE6JSX4txLEuy".parse().unwrap(),
    );
    testing_env!(context_with_key(key1.clone(), amount));
    c.confirm(request_id);
    assert_eq!(c.get_confirmations(request_id).len(), 2);

    // 4. Remove key1 via a separate DeleteMember request confirmed by alice, bob, key2
    let key1_member = MultisigMember::AccessKey { public_key: key1.clone() };
    testing_env!(context_with_account(alice(), amount));
    let del_id = c.add_request(MultiSigRequest {
        receiver_id: alice(),
        actions: vec![MultiSigRequestAction::DeleteMember { member: key1_member.clone() }],
    });
    c.confirm(del_id); // alice confirms (1)
    testing_env!(context_with_account(bob(), amount));
    c.confirm(del_id); // bob confirms (2)
    testing_env!(context_with_key(
        PublicKey::try_from(TEST_KEY.to_vec()).unwrap(),
        amount
    ));
    c.confirm(del_id); // key2 confirms (3) -> executes delete_member(key1)

    // key1 is no longer a member
    assert!(!c.get_members().contains(&key1_member));

    // BUT R's confirmations still contain key1's stale entry
    assert_eq!(c.get_confirmations(request_id).len(), 2); // still {bob, key1}

    // 5. key2 confirms R -> only bob and key2 are truly live members that confirmed,
    //    yet execution proceeds because stale key1 confirmation is still counted.
    testing_env!(context_with_key(
        PublicKey::try_from(TEST_KEY.to_vec()).unwrap(),
        amount
    ));
    c.confirm(request_id);

    // R executed (removed from requests) with only 2 live-member confirmations,
    // violating the num_confirmations(3) invariant.
    assert_eq!(c.requests.len(), 0);
}
```
This test demonstrates that `R` executes after only `bob` and `key2` (2 live members) genuinely confirmed it, with `key1`'s stale, post-removal confirmation making up the required third, directly violating the stated invariant.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
