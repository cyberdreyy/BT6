### Title
Numeric job-ID path in PipelineRunsController.Create bypasses the webhook ErrJobTypeRemoved guard - ([File: core/web/pipeline_runs_controller.go])

### Finding Description
`PipelineRunsController.Create` only enforces the "webhook job type has been removed" guard when the path parameter `idStr` parses as a UUID: [1](#0-0) . If `idStr` instead parses as an `int32` (e.g., a numeric job ID), execution falls into a completely separate branch that calls `prc.App.RunJobV2(ctx, jobID, nil)` directly, with no job-type check at all: [2](#0-1) . The `ErrJobTypeRemoved` sentinel in this codebase is only referenced at job-creation time (`core/services/job/orm.go`) and in the GraphQL resolver mutation path (`core/web/resolver/mutation.go`); it is not shown to be enforced inside the `RunJobV2` execution path itself. Thus if a webhook-type job exists in the database with a numeric external/primary ID that is also int32-parseable (e.g., a job created/migrated before the webhook-type-removed validation was added to `CreateJob`), a request to `POST /jobs/<int-id>/runs` skips the UUID-only guard entirely and proceeds to attempt execution via `RunJobV2`.

### Impact Explanation
If confirmed that `RunJobV2` performs no independent job-type gating, this allows execution of a job type ("webhook") that the application intends to be permanently blocked from being run via this endpoint, i.e., authorization/gating bypass for a "removed" job type by an authenticated user (any user with run permission), rather than a full privilege escalation to admin. This matches a moderate-severity "improper access control / unauthorized job run" class rather than fund movement or credential disclosure.

### Likelihood Explanation
Exploitability strictly requires the precondition described in the prompt: an existing webhook-type job record whose ID is int32-parseable, which in the current codebase can only originate from data created before this specific type-removal validation existed (I could not confirm from available files whether such legacy records are producible in-flow today, since `CreateJob` in `core/services/job/orm.go` appears to reject `Webhook` type at insertion — this was only partially verified due to file size/truncation). Without confirming that `RunJobV2` (in `core/services/chainlink/application.go`) lacks its own type check, and without confirming that a webhook job with a plain int32 ID can exist under current validation, this remains speculative rather than a demonstrated, reproducible bypass.

### Recommendation
Move the webhook/removed-type check inside `RunJobV2` (or the job ORM's job-fetch-and-run path) so it is enforced for both UUID and int32 lookup paths, rather than duplicating an incomplete guard only in the HTTP controller for the UUID branch.

### Proof of Concept
Integration test plan: (1) directly insert a `Job` row with `Type: job.Webhook` and a small int32 `ID` via test DB fixtures (bypassing normal `CreateJob` validation, to simulate a legacy/migrated record); (2) issue `POST /v2/jobs/<id>/runs` as an authenticated user; (3) assert whether the response is `422` with `ErrJobTypeRemoved` (safe) or `500`/success indicating the job actually executed (vulnerable) — the actual assertion result depends on `RunJobV2`'s internal implementation, which was not fully inspected in this review.

**Caveat: I was unable to fully load and verify the body of `RunJobV2` in `core/services/chainlink/application.go` or confirm whether `CreateJob`/other insertion paths in `core/services/job/orm.go` can still produce a webhook job with an int32-friendly ID under current validation. This finding is reported with that explicit uncertainty rather than as a fully confirmed, reproducible vulnerability.**
