### Title
Unconditional `savedCallbacks` map overwrite by attacker-controlled MessageId causes cross-user response misdelivery - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` stores each incoming trigger callback in `h.savedCallbacks` keyed solely by the client-supplied `msg.Body.MessageId`, with no check for whether an entry already exists for that key. Because `MessageId` is fully attacker-controlled (client-chosen, only length/format validated), any sender who submits a request using the same `MessageId` as another in-flight, legitimate request silently overwrites the victim's `savedCallback`, so the DON's eventual response is delivered to the attacker's callback instead of the victim's.

### Finding Description
`gateway.ProcessRequest` decodes the JSON-RPC request and, for legacy requests, only validates the message via `msg.Validate()` [1](#0-0) . `Message.Validate()` only checks length/format of `MessageId` (1–128 bytes, no trailing null) — it does not enforce uniqueness or attribute the ID to a specific sender [2](#0-1) .

In `handler.HandleLegacyUserMessage`, after validating the payload, the handler unconditionally writes into the shared map without checking for a pre-existing entry:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageId] = &savedCallback{id: msg.Body.MessageId, createdAt: time.Now(), Callback: callback}
don := h.don
h.mu.Unlock()
``` [3](#0-2) 

When any node eventually responds with that same `MessageId`, `handleWebAPITriggerMessage` looks up and deletes by `MessageId` and delivers the response to whichever `savedCallback` occupies that key at that moment:
```go
h.mu.Lock()
savedCb, found := h.savedCallbacks[msg.Body.MessageId]
delete(h.savedCallbacks, msg.Body.MessageId)
h.mu.Unlock()
if found {
    return savedCb.SendResponse(...)
}
``` [4](#0-3) 

Because insertion is a bare map write (no `ok`-check, no per-sender namespacing of the key, no rejection of duplicate IDs), any attacker who submits a `MethodWebAPITrigger` request using a `MessageId` that collides with a victim's still-pending request overwrites the victim's callback entry. This does not require exhausting `MaxSavedCallbacks` or racing `pruneCallbacks`; a simple, deterministic overwrite happens the instant the attacker's request is processed with the colliding ID — `pruneCallbacks`/eviction pressure is not a necessary precondition, it's just one path (attacker also floods to consume capacity) but the direct overwrite path is unconditional and always available regardless of map size. The `h.mu.Lock()` in both `HandleLegacyUserMessage` and `handleWebAPITriggerMessage`/`pruneCallbacks` protects the map's internal consistency (no corruption), but it does **not** prevent one sender's entry from silently replacing another's under the same key — there is no "reject if key already exists" check anywhere in the code.

### Impact Explanation
This results in cross-user response confusion: a legitimate caller's trigger response (which may include the DON's HTTP-fetched/aggregated data) can be delivered to an unrelated attacker instead of the intended requester, and the legitimate requester instead receives no response (silent failure/timeout). This matches the "attacker-controlled data returned to another user" / "cross-user response confusion" impact class called out in the audit rules.

### Likelihood Explanation
The precondition is minimal: an attacker only needs the ability to send a validly signed `MethodWebAPITrigger` legacy message (which any unauthenticated gateway client can do, since `HandleLegacyUserMessage` performs no allowlist check at this stage — noted directly in the code as `// TODO: apply allowlist and rate-limiting here`) [5](#0-4) . Exploitability then hinges on the attacker knowing or guessing the victim's chosen `MessageId` string (max 128 bytes, arbitrary format, chosen entirely client-side); if the calling application uses low-entropy or predictable/sequential IDs, this is trivially exploitable and fully repeatable. If IDs are high-entropy random UUIDs, the attacker would need to already know the specific victim ID, lowering but not eliminating real-world risk (e.g., IDs leaked via logs, shared systems, or predictable per-integration schemes).

### Recommendation
In `HandleLegacyUserMessage`, check for an existing entry under `msg.Body.MessageId` before inserting, and reject (or return an error response) instead of silently overwriting if a live (non-expired) callback already occupies that key. Consider deriving the internal callback key from a combination of `MessageId` and the verified `Sender` address (`msg.Body.Sender`) rather than `MessageId` alone, so that no two distinct senders can ever collide on the same key.

### Proof of Concept
Go unit test in `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Build handler via `setupHandler(t)`.
2. Create "victim" signed trigger message `msgVictim` with `MessageId = "shared-id"`, call `handler.HandleLegacyUserMessage(ctx, msgVictim, cbVictim)`.
3. Assert `handler.savedCallbacks["shared-id"]` is `cbVictim`'s wrapper.
4. Create "attacker" signed trigger message `msgAttacker` (different signer key) with the same `MessageId = "shared-id"`, call `handler.HandleLegacyUserMessage(ctx, msgAttacker, cbAttacker)`.
5. Assert `handler.savedCallbacks["shared-id"]` now points to `cbAttacker` (overwritten) — demonstrating the missing existence check.
6. Simulate the DON node response for the victim's original request (`hc.ValidatedResponseFromMessage(msgVictim)`), call `handler.HandleNodeMessage`, then assert that `cbAttacker.Wait()` receives the response (cross-user leak) while `cbVictim.Wait()` times out/never resolves — proving response misdelivery.

func (m *Message) Validate() error {

		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageId) == 0 || len(m.Body.MessageId) > MessageIdMaxLen {
		return errors.New("invalid message ID length")
	}

	}

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageId]
	delete(h.savedCallbacks, msg.Body.MessageId)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JsonRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
