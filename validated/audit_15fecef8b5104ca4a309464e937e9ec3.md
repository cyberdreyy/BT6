### Title
Unauthenticated access to LOOP plugin discovery, metrics, and pprof proxy endpoints - ([File: core/web/router.go])

### Summary
`loopRoutes` registers `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*`, and `/plugins/:name/debug/pprof/symbol` directly on the `api` group without any `auth.Authenticate(...)` wrapper, unlike `debugRoutes` which explicitly requires session authentication for `/debug/vars`. Since `sessions.Sessions` only attaches a cookie-store to the gin context and `rateLimiter` only throttles requests, neither of the group-level middlewares actually authenticates the caller, so any unauthenticated client can reach these handlers.

### Finding Description
In `NewRouter` (`core/web/router.go:78-91`), the `api` group is created with only `rateLimiter(...)` and `sessions.Sessions(...)` as middleware: [1](#0-0) 

`debugRoutes` deliberately re-wraps its sub-group with an authentication requirement: [2](#0-1) 

But `loopRoutes` registers its endpoints directly on `r` (the `api` group) with no additional `auth.Authenticate` middleware at all: [3](#0-2) 

`sessions.Sessions` (gin-contrib/sessions) merely injects a session store accessor into the gin context for downstream handlers to use — it performs no cookie validation or session-existence check by itself. `rateLimiter` only enforces request-count limits. Neither middleware calls `c.Abort()` for missing/invalid credentials. As a result, a request to `GET /discovery` (or `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*`) with zero cookies and no token reaches `LoopRegistryServer.discoveryHandler` / `pluginMetricHandler` / `pluginPPROFHandler` in `core/web/loop_registry.go` unauthenticated, in contrast with `/debug/vars`, which is blocked by `auth.Authenticate(..., auth.AuthenticateBySession)` and returns 401.

`discoveryHandler` (`core/web/loop_registry.go:53-81`) discloses the node's internal discovery hostname, exposed Prometheus port, and the names of all registered LOOP plugins — internal topology information not meant for public exposure. `pluginMetricHandler` and `pluginPPROFHandler`/`pluginPPROFPOSTSymbolHandler` proxy arbitrary requests to internal plugin Prometheus/pprof endpoints (`core/web/loop_registry.go:96-215`), including CPU/heap profiling and trace collection, which can leak internal plugin operational data and be abused for resource-consumption (e.g., `seconds` param controlling profiling duration) without any credential.

### Impact Explanation
This is an authentication-bypass on internal diagnostic route families: an unauthenticated attacker can enumerate registered LOOP plugins and their metrics endpoints, retrieve internal Prometheus metrics and CPU/heap/goroutine pprof dumps from plugin processes, and trigger long-running profile/trace requests against internal plugin services — information disclosure and a resource-exhaustion vector, matching Chainlink's "unauthorized information disclosure / denial of service via internal diagnostics" bounty impact class. It does not grant fund movement or job execution, so impact is scoped to internal-diagnostics disclosure/DoS.

### Likelihood Explanation
No preconditions are required — the attacker only needs network access to the node's API port and to issue a plain `GET` request with no cookie or token. This is trivially repeatable and requires no privileges, unlike the properly-protected `/debug/vars` sibling route.

### Recommendation
Wrap `loopRoutes` registrations with the same `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` (or an equivalent admin/edit-role-gated middleware) used for `debugRoutes`, e.g. create the group via `r.Group("/", auth.Authenticate(...))` before registering `/discovery`, `/plugins/:name/metrics`, and the pprof proxy routes in `core/web/router.go`.

### Proof of Concept
Go handler-level integration test (in `core/web` test package, using `NewRouter`/`httptest.NewServer` similar to existing router tests):
1. Build an `httptest.Server` from `NewRouter(app, nil)` with a test `chainlink.Application` that has at least one registered LOOP plugin in `app.GetLoopRegistry()`.
2. Use `http.Client{}` with no cookie jar (or an explicit empty `http.Client{}`), i.e., send zero cookies.
3. `GET {server.URL}/discovery` — assert `resp.StatusCode == 200` and body is valid JSON containing `targetgroup.Group` entries with the plugin name label `__meta_plugin_name`.
4. `GET {server.URL}/debug/vars` with the same no-cookie client — assert `resp.StatusCode == 401`.
5. Document the asymmetry: identical (lack of) credentials yields 200 for `/discovery` vs 401 for `/debug/vars`, confirming `loopRoutes` bypasses authentication while `debugRoutes` correctly enforces it.
