### Title
Loss-adjusted withdraw haircut is keyed only to `lastWithdrawRequest`, so multi-epoch receipts are paid at par and drain funded underlyings - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault.collectWithdrawFunds` applies a `stopEpochWithDuration` loss to the *aggregate* `pendingWithdraws` basis and records a single `lossRecoveryPriceByEpoch[epochNumber]`. But `_claimLossAdjustedWithdrawRequest` only looks up `lastWithdrawRequest[_user]` — a single epoch per user. A user holding receipts from an earlier epoch (which are still inside `pendingWithdraws` and therefore already haircut in the funded amount) never has that earlier-epoch basis cleared by `_clearWithdrawClaimForEpoch`, so it falls through to `_claimFundedWithdrawRequest` and is paid **at par**. Total payouts then exceed the amount actually collected, so the last claimants' transfers revert — a permanent freeze/theft of funded withdraw proceeds.

### Finding Description
- `requestWithdraw` accumulates every request into the global `pendingWithdraws` (`pendingWithdraws += _amount`, line 279) and into per-epoch `withdrawsRequestsByEpoch[_user][currentEpoch]`, while `lastWithdrawRequest[_user]` is overwritten each time (line 282). The in-code comment at lines 323-324 explicitly allows a user to hold two unclaimed receipts across epochs.
- On a lossy stop, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * RECOVERY_FULL / pendingBasis` over the **whole** `pendingWithdraws` (which includes older-epoch receipts) and zeroes the bucket (lines 413-421).
- `_claimLossAdjustedWithdrawRequest` (lines 789-801) derives the claim epoch solely from `lastWithdrawRequest[_user]` and clears only `withdrawsRequestsByEpoch[_user][lossEpoch]` via `_clearWithdrawClaimForEpoch` (lines 811-820). Any receipt basis in earlier epochs stays in `withdrawsRequests[_user]`.
- The remaining basis is then paid 1:1 by `_claimFundedWithdrawRequest` → `_transferFundedClaim` (lines 338-349, 897-906), even though the borrower only funded `pendingToFund < pendingBasis`.

The invariant "one haircutted aggregate basis ⇒ haircutted payouts" is broken: each user can only map one epoch to the recovery price, so any basis parked in earlier epochs escapes the haircut entirely.

### Impact Explanation
Direct theft plus permanent freezing. An attacker (any KYC'd lender) requests a withdraw in epoch N, does not claim, and requests again in epoch N+1. When epoch N+1 ends with a partial loss, the attacker claims: the epoch-N+1 portion is haircut, but the epoch-N portion pays out at full par from the underfunded strategy balance. Honest users whose entire receipt is in the loss epoch are correctly haircut and/or find the strategy balance exhausted — `underlyingToken.safeTransfer` (or the `defaultRecoveryReserve` guard in `_transferFundedClaim`, line 904) reverts for them permanently, since `pendingWithdraws` was already zeroed and there is no reflow mechanism. The attacker's excess gain equals `olderReceipt * (1 - lossRecoveryPrice/RECOVERY_FULL)` stolen from other claimants.

### Likelihood Explanation
Requires: a user stacking unclaimed receipts across two epochs (explicitly supported UX per the code comments, and incentivized since claiming early resets the wait), and a `stopEpochWithDuration` with `_lossAmount > 0` — a normal protocol path for partial borrower repayment executed by the honest manager. No privileged misbehavior needed; the attacker only chooses claim ordering (first-come drains the shortfall). The `lossRecoveryPrice != 0` gating in `requestWithdraw` (lines 263-270) only forces claiming of *loss-epoch* receipts before new requests; it does nothing for pre-loss older receipts.

### Recommendation
- Iterate/clear all of a user's `withdrawsRequestsByEpoch` entries (or store per-epoch recovery prices applied per entry) instead of relying on a single `lastWithdrawRequest` key.
- Alternatively, block new `requestWithdraw` while the user holds *any* unclaimed `withdrawsRequests`/`apr0Users` basis that is still inside `pendingWithdraws`, so the aggregate basis and the per-user haircut always span the same epochs.
- Add an invariant check in `collectWithdrawFunds`/claims: cumulative paid amount must never exceed cumulative collected amount for a loss epoch.

### Proof of Concept
```solidity
// Foundry fork-style sketch against IdleCDOEpochVariant + IdleCreditVault
function testLossHaircutSkippedForOldEpochReceipt() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address attacker = makeAddr("attacker");
    address victim   = makeAddr("victim");
    _depositWithUser(attacker, amount, true);
    _depositWithUser(victim,   amount, true);

    // Epoch 0: attacker requests half, never claims.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(trancheBalOf(attacker) / 2, address(AAtranche));
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch()); // fully funded

    // Epoch 1: attacker requests rest; victim requests fully. Both in pendingWithdraws.
    vm.prank(attacker);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    vm.prank(victim);
    cdoEpoch.requestWithdraw(0, address(AAtranche));
    _startEpochAndCheckPrices(1);

    // Borrower repays only part -> manager stops with loss via stopEpochWithDuration.
    uint256 pendingBasis = strategy.pendingWithdraws();
    uint256 activeBasis  = cdoEpoch.getContractValue() + cdoEpoch.expectedEpochInterest();
    uint256 lossAmount   = (activeBasis + pendingBasis) * 9e17 / 1e18; // keep 10% recovery
    (uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmount);
    uint256 repay = cdoEpoch.expectedEpochInterest() + pendingToFund;
    deal(defaultUnderlying, borrower, repay);
    vm.prank(borrower);
    IERC20Detailed(defaultUnderlying).approve(address(cdoEpoch), repay);
    vm.prank(manager);
    cdoEpoch.stopEpochWithDuration(initialProvidedApr, 0, cdoEpoch.epochDuration(), lossAmount);

    // Attacker claims: epoch-1 part haircut, epoch-0 part paid AT PAR (bug).
    vm.prank(attacker);
    cdoEpoch.claimWithdrawRequest();
    uint256 attackerGot = underlying.balanceOf(attacker);
    // attackerGot > pendingToFund * attackerBasis / pendingBasis  -> overpaid

    // Victim (or later claimants) now reverts: strategy balance exhausted.
    vm.prank(victim);
    vm.expectRevert(); // SafeERC20 transfer fails / NotAllowed reserve guard
    cdoEpoch.claimWithdrawRequest();
}
```

Note: the exact revert surface depends on whether `defaultRecoveryReserve` is set (guard at `_transferFundedClaim` reverts `NotAllowed`) or not (ERC20 transfer fails); either way later claimants are permanently frozen because `pendingWithdraws` was zeroed and no re-funding path exists. One ordering detail could not be fully verified within the search budget — whether `epochNumber` is incremented before `collectWithdrawFunds` runs during `stopEpoch` (in `deposit()` at lines 607-611). If it is, `lossRecoveryPriceByEpoch` is stored under `epochNumber+1` while all receipts are keyed to the request epoch, which makes the mismatch unconditional (every loss-epoch receipt claims at par), worsening the bug rather than invalidating it.
