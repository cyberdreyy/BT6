### Title
Case-mismatched owner-address normalization causes valid vault secret requests to be rejected - (File: core/services/workflows/v2/secrets.go)

### Summary
The `RemoteAddressValidator` bug class — inconsistent case-normalization of addresses across comparison sites, leading to false negatives on otherwise-valid requests — has a direct analog in the workflow engine's Vault secrets path. `secretsFetcher` normalizes the workflow owner address to an EIP-55 **checksummed (mixed-case)** string in one place, while other owner-normalization helpers used across the same Vault/CRE surface lowercase the address instead. Because a map lookup key built from these differently-cased values is used to match a request to its response, the mismatch causes valid, correctly-signed secret requests from an authorized workflow owner to fail with "could not find response for the request."

### Finding Description
`normalizeOwner` in `core/services/workflows/v2/secrets.go` returns a checksummed, mixed-case hex address: [1](#0-0) 

This is used both to build the outgoing Vault request (`vault.SecretIdentifier{Owner: owner, ...}`) via `GetRawSecrets`, and again as `responseOwner` to build the lookup key against the Vault batch response: [2](#0-1) [3](#0-2) 

The response-side map key (`keyFor(secretResponse.Id.Owner, ...)`) is built from `secretResponse.Id.Owner`, i.e., whatever case the Vault DON's response actually returns for `Owner`. Elsewhere in the same codebase, the canonical convention for comparing/normalizing owner addresses in the Vault/CRE stack is to **lowercase** (strip `0x`, `strings.ToLower`), not checksum-case: [4](#0-3) [5](#0-4) 

If the Vault DON echoes back the owner in its own normalized (lowercased) form, but `secretsFetcher.getVaultSecretsForBatch` builds the local `responseOwner`/lookup key using the *checksummed* form from `normalizeOwner`, the two strings will differ only in letter case (e.g. `0xAb...` vs `0xab...`), exactly mirroring the `_lowerCase` bug in `RemoteAddressValidator`: comparison of the "same" address fails purely due to case handling, because normalization is inconsistent between the request-building path and the map-key path used for the response.

### Impact Explanation
This is reachable from an unprivileged-but-legitimate workflow caller: any workflow owner requesting `GetSecrets` for its own secrets can be denied service. The resulting failure mode is a false negative — the request is treated as if "no response was found for the request" — which for a security control (secret retrieval bound to the authenticated owner) causes availability failure and forces callers into local-override fallback paths (`overrideFetcher`) or outright secret-fetch failure, mirroring "valid sender address being invalidated" in the original finding. It does not by itself allow retrieving another owner's secrets, so the risk is availability/false-rejection rather than direct disclosure, matching the reasoning that led judges to grade the original finding Medium/QA depending on whether non-canonical address casing is actually reachable.

### Likelihood Explanation
Likelihood depends on whether the Vault DON's response encoding of `Owner` diverges from `normalizeOwner`'s checksummed form — this could not be fully confirmed from static inspection alone within the available tool budget; the vault-side code path that populates `SecretResponse.Id.Owner` was not located/verified in this pass. Given that the wider codebase's convention (`vaultutils.NormalizeOwner`, `LocalSecretOverrideOwnerKey`) is lowercase-based normalization while `secretsFetcher.normalizeOwner` uniquely uses checksummed `common.HexToAddress(...).Hex()`, the inconsistency is real and present in the code, but I could not verify with full certainty (within this session) that it is actually triggered end-to-end in production traffic versus being masked by some other normalization step on the Vault DON side.

### Recommendation
Standardize on a single canonical owner-address representation across the entire Vault/secrets request-response path (recommend lowercase, hex, no `0x` prefix, consistent with `vaultutils.NormalizeOwner` and `LocalSecretOverrideOwnerKey`). Update `normalizeOwner` in `core/services/workflows/v2/secrets.go` to lowercase instead of returning `common.HexToAddress(owner).Hex()`, or alternatively perform a case-insensitive comparison (normalize both sides immediately before building/using the `keyFor` lookup key) so any case mismatch between the outgoing request's `Owner` and the Vault DON response's `Owner` cannot cause response/request correlation failures.

### Proof of Concept
1. A workflow with owner address `0xAbCdEf...` (mixed case as commonly supplied) calls `secretsFetcher.GetSecrets`.
2. `GetRawSecrets` normalizes the owner via `normalizeOwner`, which returns the **checksummed** form, e.g. `0xAbCdEf0000000000000000000000000000000001`, and sends this as `SecretIdentifier.Owner` to the Vault capability (`core/services/workflows/v2/secrets.go:313-333`).
3. Suppose the Vault DON's response instead echoes the owner using a lowercase convention (consistent with `vaultutils.NormalizeOwner`, `core/capabilities/vault/vaultutils/owner.go:5-9`), e.g. `abcdef0000000000000000000000000000000001`.
4. In `getVaultSecretsForBatch`, `responseOwner` is again computed via the checksummed `normalizeOwner` (`core/services/workflows/v2/secrets.go:415-419`), while the response map is keyed by `secretResponse.Id.Owner` from the Vault reply (`core/services/workflows/v2/secrets.go:422-425`).
5. Because `keyFor(responseOwner, namespace, r.Id)` (checksummed) does not equal the map key built from the lowercase `secretResponse.Id.Owner`, the lookup at `core/services/workflows/v2/secrets.go:433-440` fails with `"could not find response for the request"`, even though the Vault DON did in fact return a valid, correctly-authorized response for that owner.

func normalizeOwner(owner string) (string, error) {
	if len(owner) < 40 {
		return "", errors.New("invalid owner address: too short")
	}

	if owner[:2] != "0x" {
		owner = "0x" + owner
	}

	return common.HexToAddress(owner).Hex(), nil
}
