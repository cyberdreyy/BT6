## Title
`getTokenAccountsByOwner`/`getProgramAccounts` (jsonParsed) misreport SPL token balances because the mint account's owning program is never verified before its decoded decimals/extension config are trusted - (File: `rpc/src/parsed_token_accounts.rs`)

### Summary
This is the same root-cause pattern as the Spartan report: a "cheap"/attacker-controlled input (there, a `Synth`'s underlying token; here, the `mint` pubkey embedded in a token account's raw data) is used to price/scale a result without validating that it actually belongs to the expected authority (there, the pool's `TOKEN`; here, an actual SPL Token/Token-2022 program). Agave's JSON-RPC token-account pretty-printing path trusts whatever pubkey sits in bytes `0..32` of a token account and reads "additional data" (decimals, `InterestBearingConfig`, `ScaledUiAmountConfig`) from whatever account lives at that address, without checking that account is owned by a genuine token program.

### Finding Description
`get_token_account_mint` simply reads the first 32 bytes of a (structurally valid) token-account blob as a `Pubkey` with no ownership check: [1](#0-0) 

That value is then used in `get_parsed_token_accounts` (used to render `getTokenAccountsByOwner` / `getTokenAccountsByDelegate` / `getProgramAccounts` results with `jsonParsed` encoding) to look up the "mint" and compute display data: [2](#0-1) 

The lookup helper `get_mint_owner_and_additional_data` does return the mint's actual owning program id, but the caller in `get_parsed_token_accounts` immediately discards it (`let (_, data) = ...`), so the "is this really a Token/Token-2022 mint" check is never performed on this path: [3](#0-2) 

Contrast this with sibling RPC methods that do perform the equivalent of the report's recommended fix ("check the provided synth's underlying token") by explicitly requiring `is_known_spl_token_id(&mint_owner)`: [4](#0-3) [5](#0-4) 

and with the SVM's own pre/post balance collector, which explicitly checks `*mint_account.owner() != program_id` before trusting the mint's decimals: [6](#0-5) 

`get_parsed_token_accounts` is missing that same ownership check. As long as the outer account is genuinely owned by `spl_token`/`spl_token_2022` (a precondition enforced by `PARSABLE_PROGRAM_IDS` dispatch in `parse_account_data_v3`, which selects the parser purely by the account's *owner* program id), the token program itself does not require that the `mint` field it was initialized with point at an account actually owned by a token program - it only requires the bytes to unpack as a `Mint`. An attacker can therefore create their own account (owned by their own on-chain program) whose data is crafted to unpack as a `Mint` with an attacker-chosen `decimals` value and/or an `InterestBearingConfig`/`ScaledUiAmountConfig` extension, and point a legitimately-owned SPL token account's `mint` field at it. [7](#0-6) 

### Impact Explanation
When any unprivileged client calls `getTokenAccountsByOwner`, `getTokenAccountsByDelegate`, or `getProgramAccounts` with `encoding: "jsonParsed"` against such a crafted account, Agave's validator RPC will compute and return an incorrect `uiAmount`/`uiAmountString`/`decimals` (potentially wildly wrong, e.g. off by orders of magnitude via a bogus `ScaledUiAmountConfig` multiplier or `decimals`) for that token account. This is a wrong-data-returned / decoder-misreporting bug served by the validator to any RPC caller from a single, cheap read-only call - matching the "decoder panic and misreporting" impact bucket. It does not affect consensus state, but it does cause the validator to serve incorrect account data to API consumers who trust `jsonParsed` output.

### Likelihood Explanation
Reachable by any unprivileged user with one JSON-RPC call (`getTokenAccountsByOwner`/`getProgramAccounts`) against an account they fully control the setup of (their own program owning the "fake mint" account, and a normal token account whose `mint` field they choose at `InitializeAccount` time). No validator/operator privileges, no multiple calls, and no secondary index required.

### Recommendation
In `get_parsed_token_accounts` (and anywhere else that derives `SplTokenAdditionalData(V2/V3)` from a token account's embedded `mint` field), verify the resolved mint account is actually owned by a known SPL token program (`is_known_spl_token_id`) before trusting its decoded decimals/extension configuration, mirroring the check already performed in `get_token_program_id_and_mint`, `get_token_account_balance`, and `svm/src/transaction_balances.rs::unpack_token_account`.

### Proof of Concept
1. Deploy a minimal on-chain program `P` that can write arbitrary bytes into an account it owns.
2. Use `P` to create account `M` with data crafted to `unpack` as a `spl_token_2022_interface::state::Mint` (or with a `ScaledUiAmountConfig`/`InterestBearingConfig` extension) with an attacker-chosen `decimals`/multiplier.
3. Create a normal SPL Token (or Token-2022) token account `T`, owned by the real token program, via `InitializeAccount`, passing `M` as the `mint` argument (the token program only unpacks `M`'s data as `Mint`; it does not require `M.owner == token_program_id`).
4. Call `getTokenAccountsByOwner`/`getProgramAccounts` with `{"encoding":"jsonParsed"}` for the owner of `T`.
5. Observe the RPC response's `uiAmount`/`decimals` for `T` reflect `M`'s attacker-chosen values instead of a legitimate mint's values, as computed by `get_parsed_token_accounts`: [8](#0-7)

pub(crate) fn get_mint_owner_and_additional_data(
    bank: &Bank,
    mint: &Pubkey,
) -> Result<(Pubkey, SplTokenAdditionalDataV2)> {
    if mint == &spl_token_interface::native_mint::id() {
        Ok((
            spl_token_interface::id(),
            SplTokenAdditionalDataV2::with_decimals(spl_token_interface::native_mint::DECIMALS),
        ))
    } else {
        let mint_account = bank.get_account(mint).ok_or_else(|| {
            Error::invalid_params("Invalid param: could not find mint".to_string())
        })?;
        let mint_data = get_additional_mint_data(bank, mint_account.data())?;
        Ok((*mint_account.owner(), mint_data))
    }
}

/// Analyze a passed Pubkey that may be a Token program id or Mint address to determine the program
/// id and optional Mint
fn get_token_program_id_and_mint(
    bank: &Bank,
    token_account_filter: TokenAccountsFilter,
) -> Result<(Pubkey, Option<Pubkey>)> {
    match token_account_filter {
        TokenAccountsFilter::Mint(mint) => {
            let (mint_owner, _) = get_mint_owner_and_additional_data(bank, &mint)?;
            if !is_known_spl_token_id(&mint_owner) {
                return Err(Error::invalid_params(
                    "Invalid param: not a Token mint".to_string(),
                ));
            }
            Ok((mint_owner, Some(mint)))
        }
        TokenAccountsFilter::ProgramId(program_id) => {
            if is_known_spl_token_id(&program_id) {
                Ok((program_id, None))
            } else {
                Err(Error::invalid_params(
                    "Invalid param: unrecognized Token program id".to_string(),
                ))
            }
        }
    }
}

impl SvmTokenInfo {
    fn unpack_token_account<CB: TransactionProcessingCallback>(
        account_loader: &mut AccountLoader<CB>,
        account: &AccountSharedData,
        index: usize,
    ) -> Option<Self> {
        let program_id = *account.owner();
        let generic_token::Account {
            mint,
            owner,
            amount,
        } = generic_token::Account::unpack(account.data(), &program_id)?;

        let mint_account = account_loader.load_account(&mint)?;
        if *mint_account.owner() != program_id {
            return None;
        }

        let generic_token::Mint { decimals, .. } =
            generic_token::Mint::unpack(mint_account.data(), &program_id)?;

        Some(Self {
            account_index: index.try_into().ok()?,
            mint,
            amount,
            owner,
            program_id,
            decimals,
        })
    }

pub fn parse_account_data_v3(
    pubkey: &Pubkey,
    program_id: &Pubkey,
    data: &[u8],
    additional_data: Option<AccountAdditionalDataV3>,
) -> Result<ParsedAccount, ParseAccountError> {
    let program_name = PARSABLE_PROGRAM_IDS
        .get(program_id)
        .ok_or(ParseAccountError::ProgramNotParsable)?;
    let additional_data = additional_data.unwrap_or_default();
    let parsed_json = match program_name {
        ParsableAccount::AddressLookupTable => {
            serde_json::to_value(parse_address_lookup_table(data)?)?
        }

            serde_json::to_value(parse_bpf_upgradeable_loader(data)?)?

        ParsableAccount::Sysvar => serde_json::to_value(parse_sysvar(data, pubkey)?)?,
        ParsableAccount::Vote => serde_json::to_value(parse_vote(data, pubkey)?)?,
    };
