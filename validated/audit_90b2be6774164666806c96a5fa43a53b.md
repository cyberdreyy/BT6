### Title
Confirmations from a revoked/deleted key remain counted toward the confirmation threshold, allowing request execution with fewer than `num_confirmations` *live* signers - (File: `multisig/src/lib.rs`)

### Summary
`confirm()` executes a request purely by comparing the *size* of the `confirmations` `HashSet<PublicKey>` against `self.num_confirmations`, without checking that each recorded confirming key is still a currently valid multisig key. When a key is removed via a `DeleteKey` action, only requests whose *original signer* (`signer_pk`) equals the deleted key are purged; confirmations that the deleted key contributed to *other* requests (added by a different signer) are never removed. This is the same bug class as the Sherlock M-4 finding: a total (`get_tax_amount`) is computed by summing/counting only a subset of the actual objects that matter, so the recorded count diverges from the true value it is supposed to represent. Here the "true value" is the number of currently authorized signers who approved a request, and the "recorded count" is a stale confirmation set that can include keys no longer part of the multisig.

### Finding Description
- `confirm()` in `multisig/src/lib.rs` (lines 246-266) checks:
  `if confirmations.len() as u32 + 1 >= self.num_confirmations { ... execute_request(...) }` [1](#0-0) 
  This treats every `PublicKey` ever stored in `confirmations` as a valid, live approval.
- Key removal is handled inside `execute_request()`'s `DeleteKey` arm (lines 198-216):
  ```rust
  MultiSigRequestAction::DeleteKey { public_key } => {
      ...
      let request_ids: Vec<u32> = self.requests.iter()
          .filter(|(_k, r)| r.signer_pk == pk)   // only requests ORIGINATED by pk
          .map(|(k, _r)| k).collect();
      for request_id in request_ids {
          self.confirmations.remove(&request_id);
          self.requests.remove(&request_id);
      }
      self.num_requests_pk.remove(&pk);
      promise.delete_key(pk)
  }
  ``` [2](#0-1) 
  The filter only matches requests whose `signer_pk` (the key that *created* the request) equals the deleted key. It does **not** scan the `confirmations` map for entries where the deleted key appears as a *confirmer* of a request created by someone else. Those confirmations survive untouched.
- Binding broken: the multisig's core security guarantee is `live confirming keys ≥ num_confirmations` before any `Transfer`/`FunctionCall`/`AddKey` action executes. After a `DeleteKey`, the actual set of "still-valid" confirmations for outstanding requests can be smaller than `confirmations.len()`, because a removed key's earlier confirmation is still counted. A new, otherwise legitimate confirmation from a live key can then push `confirmations.len()+1 >= num_confirmations`, executing the request even though the number of *currently authorized* approvers is below threshold.

### Impact Explanation
This breaks the K-of-N custody guarantee that the multisig contract exists to enforce: a `Transfer` (or `AddKey`/`FunctionCall`) request can be executed by `execute_request()` — moving NEAR out of the account or granting a new full-access key — with fewer than `num_confirmations` currently-live keys having approved it. This is a Critical-class issue per the given impact taxonomy ("a multisig request executed below threshold"): funds can be moved, or access keys added/removed, by a coalition smaller than the account owners intended, because one of the counted "confirmations" belongs to a key that has since been revoked and is no longer trusted.

### Likelihood Explanation
Requires only ordinary, in-scope multisig operations: (1) request R1 created by key A, (2) confirmed by key B (adds B to `confirmations[R1]`, not yet reaching threshold), (3) a separate request executes `DeleteKey { public_key: B }` (a normal key-rotation action any member can help authorize), (4) confirmation of R1 continues later by keys C/D. No foundation, redeploy, victim key theft, or social engineering is needed — it is a direct consequence of normal request/confirm/key-rotation flows interacting with the `DeleteKey` cleanup logic in `execute_request()`. This matches the escalation criteria: an unprivileged path exists purely from documented, intended contract usage.

### Recommendation
When executing `DeleteKey`, iterate over **all** entries in `self.confirmations` (not just `self.requests` filtered by `signer_pk`) and remove the deleted public key from every confirmation set, re-checking (or simply leaving unexecuted) any request whose confirmation count would no longer meet `num_confirmations`. Alternatively, validate at `confirm()`/execution time that every key in a request's confirmation set is still present among currently valid access keys (e.g., via `promise_batch_action_*` introspection or by maintaining an explicit "current keys" set the contract updates on every `AddKey`/`DeleteKey`), rejecting stale confirmations before comparing against the threshold.

### Proof of Concept
1. Initialize `MultiSigContract::new(3)` with keys `A, B, C, D` (N=4, K=3).
2. `A` calls `add_request_and_confirm(request = Transfer{...})` → `request_id = R1`, `confirmations[R1] = {A}`.
3. `B` calls `confirm(R1)` → `confirmations[R1] = {A, B}` (2 < 3, not yet executed). [3](#0-2) 
4. Separately, a request `R2 = { actions: [DeleteKey{public_key: B}] }` is created and confirmed by 3 different keys (e.g. `A, C, D`) and executes, revoking `B`'s access key on-chain.
5. Because `R2`'s `signer_pk` (whoever created R2) is not `B`, the `DeleteKey` cleanup filter `r.signer_pk == pk` does not match `R1` (which was created/signed by `A`), so `confirmations[R1]` still equals `{A, B}` even though `B`'s key no longer exists on the account. [4](#0-3) 
6. `C` (a live key) calls `confirm(R1)`. `confirmations.len() (2) + 1 = 3 >= num_confirmations (3)` → `execute_request` runs the `Transfer`. [5](#0-4) 
7. Result: the transfer executed with approvals from `{A, B(revoked), C}` — only 2 currently-live keys actually authorized it, one short of the intended 3-of-4 threshold, yet the contract treated it as fully authorized.

Note: I could not execute this scenario against the actual test harness (no code execution available in this environment); the trace above is derived directly from reading `multisig/src/lib.rs`'s `confirm()`, `execute_request()`, and the `DeleteKey` arm, and should be validated with a unit/integration test (e.g., extending `multisig/src/lib.rs`'s existing `test_multi_3_of_n`-style tests) before treating it as fully confirmed.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }
