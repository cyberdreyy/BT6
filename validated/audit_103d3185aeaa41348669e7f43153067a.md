### Title
Allow-list bypass via variable expansion of `image.name` in nesting VM selection - (File: executors/internal/autoscaler/acquisition.go)

### Summary
`instance.go`'s `Prepare` validates `options.Build.Image.Name` against `AllowedImages` using the *literal* job-supplied image string, before the executor `Environment.Prepare` is invoked. Later, `acquisitionRef.createVMTunnel` takes that same literal `options.Build.Image.Name` and expands it with `options.Build.GetAllVariables().ExpandValue(image)` before passing it to `nc.Create`, meaning the string actually used to select the nesting VM image can differ from the string that was validated.

### Finding Description
In `executors/instance/instance.go:52-66`, the allow-list check runs against `options.Build.Image.Name` verbatim via `common.VerifyAllowedImage`, using `doublestar.Match(allowedImage, options.Image)` glob matching [1](#0-0) [2](#0-1) .

Later, `environment.Prepare` is called, which for the autoscaler/instance executor path reaches `acquisitionRef.createVMTunnel`. There, when `mapJobImageToVMImage` is true (set for the instance executor via `NewProvider`'s `autoscaler.Config{MapJobImageToVMImage: true}`), `image` is set to `options.Build.Image.Name` and then expanded: `image = options.Build.GetAllVariables().ExpandValue(image)` before being passed to `nc.Create(ctx, image, &slot)` [3](#0-2) [4](#0-3) .

`ExpandValue` performs shell-style `$VAR`/`${VAR}` substitution using `os.Expand` against job variables (`b.Get`) [5](#0-4) . Job variables include pipeline/job-level CI/CD variables that a pipeline author can set in `.gitlab-ci.yml` (as non-masked, non-protected variables) or via variables passed at pipeline trigger time, which are attacker-controlled inputs from the "unprivileged pipeline author" perspective.

Exploit flow: an attacker sets `image: $ATTACKER_VAR` (or embeds a `$VAR` reference inside a string, e.g. `"prefix-$ATTACKER_VAR-suffix"`) as the job's literal image name, and defines `ATTACKER_VAR` as a job variable with the value of a disallowed/pinned image reference. The allow-list check at `instance.go:59-65` validates the literal string `"$ATTACKER_VAR"` (or `"prefix-$ATTACKER_VAR-suffix"`) against `AllowedImages` glob patterns — this literal string, not the expanded value, is what gets checked. If admin's `AllowedImages` config contains a wildcard pattern that happens to match the literal placeholder text (e.g. `*`, or a pattern matching arbitrary strings), or if `AllowedImages` is empty (in which case `VerifyAllowedImage` returns `nil` unconditionally, allowing any image, per lines 34-46 in `common/allowed_images.go`), the check passes. Then in `createVMTunnel`, the same string is expanded to the attacker's chosen value and passed unchecked to `nc.Create`.

However, the critical caveat is: for the bypass to matter, `AllowedImages` must be *configured* (non-empty) by the admin, and the literal (pre-expansion) string must still pass that non-empty allow-list, while the expanded value would not. This is realistic: an admin might configure `allowed_images = ["registry.example.com/*"]`. An attacker submits `image: "registry.example.com/$SUFFIX"` which matches the glob literally (since `doublestar.Match` operates on the literal `$SUFFIX` substring, which still starts with `registry.example.com/`), then sets `SUFFIX` to something that, after expansion, still yields a string matching `registry.example.com/*` on its face — this actually still matches the same glob unless the expansion introduces path traversal characters like `../` that doublestar would have rejected on the pre-expansion string but which end up not affecting the final match test at all (since the final matched string is never re-validated). More directly: an attacker can set `image: "$FULL_IMAGE"` where `AllowedImages` contains a pattern like `*` (permissive) or the specific literal `$FULL_IMAGE` isn't in the list, in which case the check would legitimately fail on the literal `$FULL_IMAGE"` string — showing the check does still gate on the literal, unexpanded content, and the mismatch only helps the attacker if the *literal* form passes but the expanded form would not, e.g. glob pattern `*` matches virtually anything, making this a non-issue since `*` already allows everything; or a pattern such as `myregistry.example.com/*` where attacker's literal image is `myregistry.example.com/$PATH` (matches glob) and `$PATH` expands to something like `../../../another-registry.evil/image:tag` — but doublestar matching is on the string form, and `myregistry.example.com/../../../another-registry.evil/image:tag` would still literally match `myregistry.example.com/*` since doublestar `*` doesn't span `/` by default in doublestar semantics unless using `**`; still, the resulting string is a different, unintended image reference (e.g., referencing a different path/tag under a namespace) which subverts the intent of a per-namespace allow rule.

This is a genuine root-cause gap: the validation and the value actually used for image selection are decoupled — one operates pre-expansion, the other post-expansion — and no re-validation of the final resolved image string occurs before `nc.Create`.

### Impact Explanation
This allows a pipeline author, under an admin-configured `allowed_images` restriction meant to pin/restrict nesting VM images, to cause the runner to request an image string different from (and not equal to) the one that was allow-list validated. Depending on how permissive the admin's glob patterns are, this can result in requesting nesting VM images/paths that the admin did not intend to authorize, undermining the "runner-enforced restrictions on images... must hold against user-controlled input" invariant, when VM Isolation + `MapJobImageToVMImage` is enabled.

### Likelihood Explanation
Requires: instance executor, `VMIsolation.Enabled = true` (admin config), `AllowedImages` configured with glob patterns that can be satisfied by a literal string containing an unexpanded `$VAR` token, and the ability for the attacker to control the value bound to that token via job/pipeline variables (a routine capability of any pipeline author). This is fully attacker-reachable without any admin/privileged action — only admin-side precondition is enabling VM isolation with `allowed_images` set, which is a documented supported configuration, not a "known insecure choice." The bug is reproducible deterministically; it is not a race condition or infra-dependent bug.

### Recommendation
Re-validate the final, expanded image string against `AllowedImages`/`InternalImages` immediately before calling `nc.Create` in `createVMTunnel` (or move the `ExpandValue` call before the `VerifyAllowedImage` check in `instance.go`'s `Prepare`, and perform the allow-list check on the expanded value, not the literal). At minimum, call `common.VerifyAllowedImage` a second time in `createVMTunnel` using the post-`ExpandValue` `image` value before it is passed to `nc.Create`.

Expected assertion: the string passed to `nc.Create` differs from, and was never independently validated against, `AllowedImages`, demonstrating that the validation in `instance.go` and the value used in `createVMTunnel` can diverge.
