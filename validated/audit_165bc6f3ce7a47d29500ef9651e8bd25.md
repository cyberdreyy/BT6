### Title
Stale per-epoch instant-withdraw aggregate inflates default recovery basis and locks recovery funds - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`claimInstantWithdrawRequest` pays out a funded instant-withdraw receipt but never decrements the epoch-level aggregates `instantWithdrawsRequestsByEpoch[_user][epoch]` and `instantWithdrawClaimsByEpoch[epoch]`. If the borrower defaults later in the same epoch while other instant receipts remain unfunded (`pendingInstantWithdraws != 0`), `defaultPendingClaimBasis()` and `_defaultPrefundedInstantReserve()` reuse the stale aggregate, counting already-paid underlying as still-held reserve. `finalizeDefaultRecovery` then computes an inflated `recoveryPrice`, so later defaulted-epoch claims revert on insufficient actual balance — permanently locking recovery funds for the last claimants, the same "shared bucket drained but not reset" class as the Spigot `removeSpigot()` bug.

### Finding Description
The analog of `escrowed[token]` (one bucket shared by many `revenueContract`s, emptied by the first call without reset) is `instantWithdrawClaimsByEpoch[epoch]` (one bucket shared by all instant receipts of an epoch, consumed by a claim without decrement).

`requestInstantWithdraw` increases both per-user and per-epoch basis (IdleCreditVault.sol:366-374). On a normal funded claim, only the per-user aggregate is cleared:

```solidity
// contracts/strategies/idle/IdleCreditVault.sol:387-392
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

Neither `instantWithdrawsRequestsByEpoch[_user][epoch]` nor `instantWithdrawClaimsByEpoch[epoch]` is decremented, and `pendingInstantWithdraws` was already reduced at funding time by `collectInstantWithdrawFunds` (IdleCreditVault.sol:398-403), so the strategy no longer holds the paid tokens.

If the borrower then defaults in that epoch while `pendingInstantWithdraws != 0` (partial funding of the instant queue), default finalization uses the stale aggregates:

- `defaultPendingClaimBasis()` adds `instantWithdrawClaimsByEpoch[epochNumber]` — including the already-claimed amount — to the haircut basis (IdleCreditVault.sol:644-649).
- `_defaultPrefundedInstantReserve()` counts `instantBasis - pendingInstant` as underlying already held by the strategy, i.e. it assumes the claimed user's payout is still in the contract (IdleCreditVault.sol:716-723).

`finalizeDefaultRecovery` folds that phantom prefunded amount into `reserveAmount` and divides by the inflated `totalBasis` (IdleCreditVault.sol:685-700). The resulting `defaultRecoveryPrice` is backed by fewer real tokens than the accounting claims. Subsequent claims via `_claimDefaultedInstantWithdrawRequest` / `_claimDefaultedWithdrawRequest` call `_transferDefaultRecovery`, which decrements `defaultRecoveryReserve` and transfers real tokens (IdleCreditVault.sol:912-917); once the phantom share is reached, the ERC20 transfer reverts and remaining claimants can never recover — identical mechanics to the second `removeSpigot()` reverting on `ERC20: transfer amount exceeds balance`, except here there is no owner "send tokens back" escape that restores the haircut ratio for users.

### Impact Explanation
Permanent freezing of defaulted-recovery funds for the last claimants of the defaulted epoch, and/or dilution of all recovery claimants (the phantom basis lowers everyone's payout share while the dust remains locked in the vault). The lost/locked amount equals the claimed instant receipt volume in the default epoch — up to the full instant queue size. Broken invariant: one receipt one payout / donation isolation of the recovery reserve.

### Likelihood Explanation
Requires a partially funded instant-withdraw queue in the epoch in which the borrower defaults and at least one user claims an instant receipt before finalization — an ordinary, unprivileged user action, not privileged collusion. Instant withdraws and partial funding at `startEpoch` are first-class features (`defaultPendingClaimBasis` explicitly handles "startEpoch moved cash that covered only part of the instant queue"), and borrower default is a supported flow, so the scenario is plausible but not attacker-forceable on demand; the attacker must time their own instant claim into the epoch that later defaults.

### Recommendation
Mirror the fix applied upstream in the Spigot (no longer transfer from a shared unstated bucket): clear the per-epoch aggregates when a funded instant receipt is consumed. In `claimInstantWithdrawRequest`, after computing `amount`, decrement `instantWithdrawsRequestsByEpoch[_user][currentEpoch]` (clamped) and `instantWithdrawClaimsByEpoch[currentEpoch]` by the claimed amount, so `defaultPendingClaimBasis`/`_defaultPrefundedInstantReserve` only ever reflect outstanding receipts. Add a regression test: two instant requests in epoch N, partial funding, one user claims, then `finalizeDefaultRecovery` — assert recovery price and that all remaining claimants can be paid.
