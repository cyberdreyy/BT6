### Title
Post-default instant withdrawals bypass recovery accounting and drain `defaultRecoveryReserve` at par - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The kernel bug treats a single marker (`PACKET_OUTGOING`) as sufficient proof that an skb's control buffer is a `sock_exterr_skb`, while another subsystem uses the same marker with different buffer ownership. The analog in `IdleCreditVault` is `claimInstantWithdrawRequest`: it uses `defaultInstantWithdrawsFinalized` (snapshot of `pendingInstantWithdraws != 0` at finalization time) as the sole discriminator between "unfunded defaulted-epoch instant receipt, pay at `defaultRecoveryPrice`" and "funded instant receipt, pay at par". `requestInstantWithdraw` has no post-default routing at all (unlike `requestWithdraw`, which is explicitly redirected to `postDefaultRequests`), so a receipt created after `finalizeDefaultRecovery` collides with the same epoch key and, in the `pendingInstantWithdraws == 0` finalization case, is paid 1:1 from the commingled strategy balance that holds `defaultRecoveryReserve`.

### Finding Description
Two asymmetric paths exist for post-default receipts:

- `requestWithdraw` checks `defaultRecoveryFinalized` and parks new requests in `postDefaultRequests`, paying them via `_transferDefaultRecovery` which accounts against `defaultRecoveryReserve` (IdleCreditVault.sol:247-258, 760-767).
- `requestInstantWithdraw` (IdleCreditVault.sol:356-375) has no `defaultRecoveryFinalized` branch. It mints a receipt, increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch[_user][epochNumber]`, `instantWithdrawClaimsByEpoch[epochNumber]`, and `pendingInstantWithdraws`.

`claimInstantWithdrawRequest` (IdleCreditVault.sol:380-393) then decides claim type purely on `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`:

- **Case A — `pendingInstantWithdraws == 0` at finalization** (`defaultInstantWithdrawsFinalized == false`, IdleCreditVault.sol:696): a post-default instant request is never routed through `_claimDefaultedInstantWithdrawRequest`. The full `instantWithdrawsRequests[_user]` — including the brand-new, never-funded request — is paid at par via `_transferFundedClaim`. The strategy's underlying balance at that point consists of `defaultRecoveryReserve` tokens reserved for defaulted-epoch claimants and active-LP recovery; nothing decrements `defaultRecoveryReserve`, so the attacker extracts haircut-priced recovery funds at 100 cents on the dollar.
- **Case B — `defaultInstantWithdrawsFinalized == true`**: since `epochNumber` never advances after default, the new receipt lands in `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` and is indistinguishable from a defaulted-epoch receipt; `_claimDefaultedInstantWithdrawRequest` clears it at `defaultRecoveryPrice`. The user still receives only the haircut while their principal was burned, and `pendingInstantWithdraws`/`instantWithdrawClaimsByEpoch` bookkeeping is decremented as if an old claim settled.

The marker (`defaultInstantWithdrawsFinalized`, frozen at finalization) plays the role of `PACKET_OUTGOING`: it is treated as proof of which claim class a receipt belongs to, but post-default receipts share the same epoch key under different ownership semantics.

### Impact Explanation
In Case A, an unprivileged tranche holder who still holds receipt-bearing tranche tokens can, after a finalized default, call the CDO's instant-withdraw entry point and recover 100% of nominal value while every other defaulted claimant is entitled only to `defaultRecoveryPrice`. The payout is drawn from the same strategy token balance backing `defaultRecoveryReserve` without decrementing it, so either later legitimate recovery claims over-draw (insolvency of the reserve) or revert on insufficient balance (permanent freezing of other users' recovery). Loss magnitude is bounded by the reserve size but is direct theft of funds earmarked for other claimants.

### Likelihood Explanation
Requires a finalized default with `pendingInstantWithdraws == 0` at finalization (all instant receipts funded at that moment) plus residual tranche tokens to request against — an ordinary state, since instant funding commonly completes via `collectInstantWithdrawFunds` during a normal epoch. The uncertainty is whether `IdleCDOEpochVariant.requestInstantWithdraw`/`claimInstantWithdrawRequest` reverts when `defaulted()` is true; I was unable to verify the CDO-side guard in the available iterations. If the CDO gates instant flows on `!defaulted`, the attack is not reachable and this reduces to an accounting inconsistency only (Case B still causes the post-default requester to be silently haircut and `instantWithdrawClaimsByEpoch`/`pendingInstantWithdraws` to be debited against the wrong bucket). Also unverified: whether `_transferFundedClaim` enforces a funded-balance check that would exclude `defaultRecoveryReserve` tokens.

### Recommendation
Mirror the normal-withdraw path: in `requestInstantWithdraw`, when `defaultRecoveryFinalized`, either revert or route the request into `postDefaultRequests`-equivalent accounting paid via `_transferDefaultRecovery`. Additionally, key post-default receipts to a distinct epoch slot (e.g., bump `epochNumber` at finalization or store a `postDefault` flag) so a new request can never alias `instantWithdrawsRequestsByEpoch[*][defaultRecoveryEpoch]`, and make `_transferFundedClaim` respect `defaultRecoveryReserve` once `defaultRecoveryFinalized` is set.

### Proof of Concept
```solidity
// test/foundry/IdleCreditVault.t.sol context
// Precondition: epoch running, all instant claims already funded
// (collectInstantWithdrawFunds pulled pendingInstantWithdraws to 0).

// 1. Default the pool: borrower repays 0.
deal(defaultUnderlying, borrower, 0);
vm.warp(cdoEpoch.epochEndDate() + 1);
vm.prank(manager);
cdoEpoch.stopEpoch(0, 0);
assertTrue(cdoEpoch.defaulted());

// 2. Finalize recovery at e.g. 70% price.
uint256 activeBasis = cdoEpoch.getContractValue()
    + cdoEpoch.expectedEpochInterest() - cdoEpoch.pendingWithdrawFees();
uint256 recovered = activeBasis * 7e17 / 1e18;
deal(defaultUnderlying, manager, recovered);
vm.startPrank(manager);
IERC20Detailed(defaultUnderlying).approve(address(strategy), recovered);
cdoEpoch.finalizeDefault(recovered, manager);
vm.stopPrank();
assertFalse(IdleCreditVault(address(strategy)).defaultInstantWithdrawsFinalized());

// 3. Attacker (tranche holder) requests an instant withdraw post-default.
vm.prank(attacker);
cdoEpoch.requestInstantWithdraw(attackerTrancheBal, address(AAtranche)); // if not gated by defaulted()

// 4. Attacker claims: full receipt paid at par from strategy balance
//    that backs defaultRecoveryReserve; reserve accounting unchanged.
uint256 balPre = IERC20Detailed(defaultUnderlying).balanceOf(attacker);
uint256 resPre = IdleCreditVault(address(strategy)).defaultRecoveryReserve();
vm.prank(attacker);
cdoEpoch.claimInstantWithdrawRequest();
assertGt(IERC20Detailed(defaultUnderlying).balanceOf(attacker) - balPre, 0);
assertEq(IdleCreditVault(address(strategy)).defaultRecoveryReserve(), resPre);
// reserve now under-collateralized: other claimants' recovery claims
// either over-draw or revert.
```

The decisive dependency (CDO-side gating of instant flows while `defaulted`) could not be confirmed within the search budget; if `requestInstantWithdraw`/`claimInstantWithdrawRequest` revert on `defaulted()`, this finding is not exploitable and should be downgraded to a hardening note on the flag-vs-epoch-key ambiguity.
