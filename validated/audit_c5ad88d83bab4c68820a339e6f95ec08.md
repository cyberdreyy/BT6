### Title
Pre-fix fallthrough in `validate_delegate_action_key` advances access-key/gas-key nonce despite `DepositWithFunctionCall` validation failure - ([File: runtime/runtime/src/actions.rs])

### Summary
In `validate_delegate_action_key`, when a FunctionCall-permission key is used with a `FunctionCall` action carrying `deposit > 0`, the code sets `result.result` to `DepositWithFunctionCall` error. Before `ProtocolFeature::FixDelegateActionDepositWithFunctionCallError` is enabled, there is no unconditional early `return`, so execution can continue past the receiver/method checks and reach the final `match nonce_update` block, which mutates the access key's (or gas key's) nonce in `state_update` even though the action is going to fail. [1](#0-0) [2](#0-1) 

### Finding Description
The flow is: deposit>0 sets `result.result = DepositWithFunctionCall` error at line 665-669. Under the pre-fix behavior (protocol feature disabled), no `return` occurs here, so execution falls to the `receiver_id` check (line 679) and then the `method_names` check (line 689). [3](#0-2) 

- If `receiver_id` mismatches or `method_name` mismatches, those branches themselves call `return Ok(())` after overwriting `result.result`, so the function exits before the nonce_update block — no state mutation occurs, matching the question's concern about error-kind swapping without state mutation.
- However, if `receiver_id` *matches* and `method_name` *matches* (i.e., the delegate action is otherwise perfectly valid except for the illegal deposit), neither the receiver nor method-name branch fires, and execution falls out of the `if let` block entirely to line 713's `match nonce_update`, which **does** execute — persisting `access_key.nonce = delegate_nonce.nonce()` (or the gas key nonce) via `set_access_key`/`set_gas_key_nonce` — despite `result.result` already holding a fatal error. [2](#0-1) 

Post-fix, `FixDelegateActionDepositWithFunctionCallError` gates this: `return Ok(())` executes unconditionally right after the deposit check, so the nonce_update block is unreachable and no state mutation occurs. [4](#0-3) 

This confirms the specific mechanism the question asks about: the *choice* of error kind (DepositWithFunctionCall vs ReceiverMismatch/MethodNameMismatch) does correlate with whether nonce mutation happens in the pre-fix code — but only in the sub-case where receiver_id and method_name both happen to be valid. In that sub-case the pre-fix code silently advances the nonce for an action it is simultaneously failing.

### Impact Explanation
This does not grant authorization escalation or fund theft: the delegate action still fails (`result.result` carries the error and the outer caller propagates the failure), so the attached `FunctionCall` never executes and no value transfer/contract call succeeds. The only consequence is nonce consumption on a rejected action. NEAR's transaction/nonce model already treats nonce consumption as normal for failed actions in many paths (nonce advancement is intentionally decoupled from action success, as an anti-replay measure), so this by itself is not a "state divergence" or "double-spend" bug — it is a bounded self-inconsistency (a failing DelegateAction still burns a nonce) that existed only pre-fix and is exactly what the fix (`FixDelegateActionDepositWithFunctionCallError`) was introduced to make consistent/eliminate. It does not enable an attacker to gain unauthorized execution, mint value, or affect other accounts' funds — the sender/relayer of the delegate action only affects their own key's nonce state. No cross-account authorization escalation, no consensus divergence, no shard halt.

### Likelihood Explanation
Reaching the fallthrough sub-case pre-fix requires only crafting a `SignedDelegateAction` with a FunctionCall action whose `receiver_id`/`method_name` both satisfy the permission's restrictions but `deposit > 0` — trivially constructible by any key holder/relayer. However, this is gated entirely by protocol version: whether the vulnerable pre-fix code path is reachable on current mainnet depends on `FixDelegateActionDepositWithFunctionCallError` already being stabilized past the current protocol version, which could not be conclusively confirmed from the available index (the `ProtocolFeature` enum listing and its stabilization version were not fully retrieable within tool limits). If the feature is already stabilized on mainnet, this pre-fix path is dead code and not exploitable.

### Recommendation
No additional recommendation is needed beyond the already-present fix: keeping the unconditional `return Ok(())` after setting `DepositWithFunctionCall` (as currently implemented under the protocol-feature gate) ensures the nonce_update block is never reached when the deposit validation fails, for both the plain-nonce and gas-key-nonce cases.

### Proof of Concept
Unit test plan (in `runtime/runtime/src/actions.rs` or an integration test):
1. Create a FunctionCall-permission access key for `sender_id` with `receiver_id = "receiver"` and empty `method_names`, with known `access_key.nonce = N`.
2. Build a `DelegateAction` with `receiver_id = "receiver"`, a single `Action::FunctionCall` with `method_name` unrestricted and `deposit = 1` (>0), and `nonce = N + 1`.
3. Call `validate_delegate_action_key` twice:
   - With `apply_state.current_protocol_version` set below `FixDelegateActionDepositWithFunctionCallError`'s stabilization version — assert `result.result` is `Err(DepositWithFunctionCall)` and then assert (using `get_access_key`) whether `access_key.nonce` was advanced to `N+1` in `state_update` (this reproduces the fallthrough nonce mutation when receiver/method match).
   - With the protocol version at/above stabilization — assert `result.result` is `Err(DepositWithFunctionCall)` and assert `access_key.nonce` remains `N` (untouched), confirming the fix prevents the mutation.
4. Additionally test the sub-case where `receiver_id` in the DelegateAction does NOT match the permission's `receiver_id` (deposit>0 AND receiver mismatch): assert that pre-fix, `result.result` becomes `ReceiverMismatch` (overwriting `DepositWithFunctionCall`) and nonce is untouched (since the receiver-mismatch branch itself returns early) — matching the question's premise that error-kind swapping in that sub-case does not, by itself, cause state mutation.
