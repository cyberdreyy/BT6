### Title
Division-before-multiplication precision loss in Jovian DA-footprint gas accounting causes systematic under-metering of block DA-footprint usage - ([File: crates/common/l1-fees/src/params.rs], [File: crates/common/evm/src/executor/block_executor.rs])

### Summary
Both the engine-neutral `L1FeeParams::jovian_da_footprint` helper and the `BaseBlockExecutor::jovian_da_footprint_estimation` routine compute the post-Jovian DA-footprint gas by dividing the FastLZ-estimated compressed size by `1_000_000` *before* multiplying by the DA-footprint gas scalar, instead of multiplying first and dividing last. This is the exact division-before-multiplication precision-loss pattern flagged in the external DODO `_SolveQuadraticFunctionForTrade` report, applied here to a consensus-relevant gas-metering computation reachable by any unprivileged transaction sender.

### Finding Description
`tx_estimated_size_fjord` returns the FastLZ-estimated compressed transaction size **scaled by 1e6** (i.e. `real_size_bytes * 1_000_000`), per: [1](#0-0) 

The correct way to convert this back to a real byte count and multiply by a per-byte scalar is `estimated_size * scalar / 1_000_000` (multiply first, divide last), which is exactly what the sibling function `data_gas_fjord` does: [2](#0-1) 

However, `L1FeeParams::jovian_da_footprint` instead divides first and multiplies second: [3](#0-2) 

The comment on this function even documents the (incorrect) order explicitly: "divided back down by `1e6`... and multiplied by the DA-footprint gas scalar."

The same bug is duplicated in the block executor's own DA-footprint estimation, which independently divides then multiplies: [4](#0-3) 

Because `wrapping_div`/`saturating_div` truncates (floors) the compressed-size-in-bytes value *before* the scalar multiplication is applied, any fractional byte-count information above the truncation point is discarded before the scalar can amplify it. For any transaction whose estimated compressed size is not an exact multiple of `1_000_000`, the DA-footprint gas value computed by this order is `floor(size/1e6) * scalar`, which is `<= floor(size * scalar / 1e6)` — i.e. it can only ever under-report (never over-report) versus the mathematically correct multiply-then-divide order, and the discrepancy scales with `scalar`.

### Impact Explanation
The DA-footprint value feeds:
- The block-level DA-footprint resource limit (`da_footprint_used` in `BaseBlockExecutor`, referenced by the Jovian DA-footprint block limit spec) used during block building/validation to bound how much compressed data a block may include — under-metering permits more compressed transaction data into a block than the protocol intends, i.e. a resource-metering/block-building bypass reachable by simply submitting transactions with sizes that don't divide evenly by 1e6 (virtually all real transactions).
- The `blob_gas_used` receipt field surfaced via `crates/execution/rpc/src/eth/receipt.rs`, which is consensus/derivation-relevant metadata reported to clients and consumers of receipts.

Because this is consensus-path code shared between the block executor and (per the module) EVM2/flashblocks state builder, a systematic under-count changes what data-footprint a given block is charged, which can diverge block-building behavior/limits from what the correct formula would produce, and any node computing the "correct" value differently (e.g. multiply-then-divide) would diverge from nodes using this truncated order — a potential state/consensus divergence source across implementations, not merely a display bug.

### Likelihood Explanation
Any unprivileged sender's transaction is estimated via `tx_estimated_size_fjord`, and this function runs unconditionally for every transaction post-Jovian activation on the execution/derivation and RPC receipt paths. The truncation happens on essentially every transaction whose FastLZ-estimated size isn't an exact multiple of `1_000_000`, which is the common case, making the precision loss reachable with a single ordinary transaction and always present, not an edge case.

### Recommendation
Change both `L1FeeParams::jovian_da_footprint` and `BaseBlockExecutor::jovian_da_footprint_estimation` to multiply by the scalar before dividing by `1_000_000`, matching the pattern already used correctly in `data_gas_fjord`:
```rust
U256::from(tx_estimated_size_fjord(input))
    .saturating_mul(scalar)
    .wrapping_div(U256::from(1_000_000u64))
    .saturating_to::<u64>()
```
and equivalently reorder the `saturating_div(1_000_000).saturating_mul(scalar)` chain in `block_executor.rs` to `saturating_mul(scalar).saturating_div(1_000_000)`. Any other engine (e.g. `crates/common/evm2/src/executor.rs`, `crates/execution/flashblocks/src/state_builder.rs`) that reimplements this arithmetic independently should be audited and aligned to the same corrected order to avoid a client/consensus divergence.

### Proof of Concept
Given `tx_estimated_size_fjord(input) = 1_999_999` (i.e. ~1.999999 compressed bytes after the 1e6 scaling) and `da_footprint_gas_scalar = 3`:
- Current (buggy) order: `1_999_999 / 1_000_000 = 1` (floored) `* 3 = 3`.
- Correct order: `1_999_999 * 3 = 5_999_997`, `/ 1_000_000 = 5` (floored).

The buggy path reports a DA-footprint gas of `3` where the mathematically correct value is `5` — a ~40% under-count for this input, reproducible deterministically for any attacker-chosen transaction payload whose estimated size is not an exact multiple of `1_000_000`, with no special privileges required to submit such a transaction. /// Calculate the estimated compressed transaction size in bytes, scaled by 1e6.
```rust
/// This value is computed based on the following formula:
/// max(minTransactionSize, intercept + fastlzCoef*fastlzSize)
pub fn tx_estimated_size_fjord(input: &[u8]) -> u64 {
    let fastlz_size = flz_compress_len(input) as u64;

    fastlz_size
        .saturating_mul(L1_COST_FASTLZ_COEF)
        .saturating_sub(L1_COST_INTERCEPT)
        .max(MIN_TX_SIZE_SCALED)
}
```

```rust
    /// Calculates the Jovian DA-footprint gas for posting the enveloped transaction bytes `input`.
    ///
    /// The footprint is the FastLZ-estimated compressed size (scaled by `1e6`, as
    /// [`tx_estimated_size_fjord`] returns) divided back down by `1e6` and multiplied by the
    /// DA-footprint gas scalar. Returns zero when no scalar is set (pre-Jovian or unconfigured).
    /// Mirrors the reference `jovian_da_footprint_estimation`.
    pub fn jovian_da_footprint(&self, input: &[u8]) -> u64 {
        let Some(scalar) = self.da_footprint_gas_scalar else {
            return 0;
        };
        U256::from(tx_estimated_size_fjord(input))
            .wrapping_div(U256::from(1_000_000u64))
            .saturating_mul(scalar)
            .saturating_to::<u64>()
    }
```

```rust
    fn jovian_da_footprint_estimation(
        &mut self,
        tx_env: &E::Tx,
        tx: impl RecoveredTx<R::Transaction>,
    ) -> Result<u64, BlockExecutionError> {
        // Try to use the enveloped tx if it exists, otherwise use the encoded 2718 bytes
        let encoded = tx_env
            .encoded_bytes()
            .map_or_else(
                || estimate_tx_compressed_size(tx.tx().encoded_2718().as_ref()),
                |encoded| estimate_tx_compressed_size(encoded),
            )
            .saturating_div(1_000_000);

        // Load the L1 block contract into the cache. If the L1 block contract is not pre-loaded the
        // database will panic when trying to fetch the DA footprint gas scalar.
        self.evm.db_mut().basic(Predeploys::L1_BLOCK_INFO).map_err(BlockExecutionError::other)?;

        let da_footprint_gas_scalar = L1BlockInfo::fetch_da_footprint_gas_scalar(self.evm.db_mut())
            .map_err(BlockExecutionError::other)?
            .into();

        Ok(encoded.saturating_mul(da_footprint_gas_scalar))
    }
```
