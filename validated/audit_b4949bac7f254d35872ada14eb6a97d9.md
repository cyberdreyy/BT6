### Title
Stale confirmations from deleted keys count toward the multisig execution threshold - (File: `multisig/src/lib.rs`)

### Summary
`MultiSigContract::confirm()` in `multisig/src/lib.rs` counts entries in the per-request `confirmations` `HashSet<PublicKey>` to decide whether a request has reached `num_confirmations` and should execute. When a key is removed from the multisig via `MultiSigRequestAction::DeleteKey`, the cleanup logic only removes **requests that were added by** that key (`r.signer_pk == pk`) — it does not scan and strip that key's `PublicKey` out of the `confirmations` sets of other, still-pending requests that it may have confirmed. This breaks the binding "confirmations counted == live members who confirmed": a stale confirmation from a now-deleted key remains in the set and is later summed together with confirmations from still-valid keys to reach the threshold, letting a request execute with fewer live signers than `num_confirmations` requires.

### Finding Description
`execute_request`'s `DeleteKey` branch:
```rust
MultiSigRequestAction::DeleteKey { public_key } => {
    self.assert_self_request(receiver_id.clone());
    let pk: PublicKey = public_key.into();
    // delete outstanding requests by public_key
    let request_ids: Vec<u32> = self
        .requests
        .iter()
        .filter(|(_k, r)| r.signer_pk == pk)
        .map(|(k, _r)| k)
        .collect();
    for request_id in request_ids {
        self.confirmations.remove(&request_id);
        self.requests.remove(&request_id);
    }
    self.num_requests_pk.remove(&pk);
    promise.delete_key(pk)
}
``` [1](#0-0) 

This only purges requests whose `signer_pk` (the pk that *added* the request) equals the deleted key. It does not touch `confirmations` entries where the deleted key appears as a *confirmer* of a request added by someone else.

`confirm()` then trusts the raw count of the `confirmations` set:
```rust
pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
    self.assert_valid_request(request_id);
    let mut confirmations = self.confirmations.get(&request_id).unwrap();
    assert!(!confirmations.contains(&env::signer_account_pk()), ...);
    if confirmations.len() as u32 + 1 >= self.num_confirmations {
        let request = self.remove_request(request_id);
        self.execute_request(request)
    } else {
        confirmations.insert(env::signer_account_pk());
        self.confirmations.insert(&request_id, &confirmations);
        PromiseOrValue::Value(true)
    }
}
``` [2](#0-1) 

There is no re-validation that every public key inside `confirmations` still belongs to a currently-live multisig key at the time the threshold check is performed. The binding that should hold is:

`confirmations.len()` (used for threshold) == number of *currently authorized* keys that confirmed

Sequence that breaks it (for `num_confirmations = 3`, keys A, B, C, D all valid initially):
1. Key A adds Request X (`add_request`), not yet confirmed by anyone else.
2. Key B calls `confirm(X)` → `confirmations = {B}`.
3. Separately, A/B/C confirm and execute a `DeleteKey { public_key: B }` request (a distinct, already-executed request). Because Request X was added by A, not B, it is not in the `r.signer_pk == pk` filter, so it survives untouched and `confirmations = {B}` remains, even though B's key no longer exists on-chain.
4. Key C now calls `confirm(X)`. Count becomes `{B, C}` = 2, still below 3, so it's stored.
5. Key D calls `confirm(X)`. Count becomes `{B, C, D} = 3 >= num_confirmations(3)` → `execute_request` fires.

Only C and D are actually live signers who approved X at execution time (B's authorization was revoked before X was decided), yet the contract executed a 3-of-4 multisig action with effectively 2 live confirmations. This directly weakens the `K` in the `K`-of-`N` custody guarantee that this account (which may hold NEAR/tokens/access keys) is supposed to enforce.

### Impact Explanation
This is a Critical-class issue per the scan's impact categories: "a multisig request executed below threshold." Any `MultiSigRequestAction` — including `Transfer` of NEAR held by the account, `AddKey`/`DeleteKey`, or `FunctionCall` to another contract — can be pushed through with fewer live confirmations than the configured `num_confirmations`, letting a party (or colluding subset of parties) execute actions like moving funds or granting itself additional keys without the intended quorum of currently-authorized signers.

### Likelihood Explanation
Requires: (a) a request pending confirmation by an existing key, (b) that confirming key subsequently being deleted through the ordinary `DeleteKey` flow (a routine, expected multisig operation, e.g. offboarding a departing signer), and (c) the pending request later being confirmed by other keys to reach the (unchanged) threshold. No special privileges beyond normal multisig key rotation are needed, and key rotation/offboarding is a foreseeable, common operational event, making this a realistically medium-likelihood, high-impact defect in an in-scope contract (`multisig/src/lib.rs`).

### Recommendation
When executing `DeleteKey` (and similarly in `multisig2`'s `DeleteMember`), iterate over **all** pending `confirmations` sets (not just requests added by that key) and remove the deleted public key from every set, re-checking whether any request now needs its confirmation state updated. Alternatively, validate at `confirm()`/execution time that every public key in a request's `confirmations` set still corresponds to a currently valid access key on the account before counting it toward the threshold.

### Proof of Concept
Using the existing test harness in `multisig/src/lib.rs`:
```rust
#[test]
fn test_stale_confirmation_counts_after_delete_key() {
    let amount = 1_000;
    // Key A adds request X but does not confirm
    testing_env!(context_with_key(pk_a(), amount));
    let mut c = MultiSigContract::new(3);
    let request_x = MultiSigRequest {
        receiver_id: bob(),
        actions: vec![MultiSigRequestAction::Transfer { amount: amount.into() }],
    };
    let request_id = c.add_request(request_x);

    // Key B confirms X
    testing_env!(context_with_key(pk_b(), amount));
    c.confirm(request_id);
    assert_eq!(c.get_confirmations(request_id).len(), 1); // {B}

    // A separate request deletes key B, confirmed/executed by A/C/D
    // ... add_request_and_confirm + confirm x2 for DeleteKey{public_key: B} ...
    // executes successfully, key B removed from access keys

    // Request X's confirmations still contain B (not cleaned up)
    assert_eq!(c.get_confirmations(request_id).len(), 1); // still {B}, stale

    // Key C confirms X -> count = {B, C} = 2 (< 3, stored)
    testing_env!(context_with_key(pk_c(), amount));
    c.confirm(request_id);

    // Key D confirms X -> count = {B, C, D} = 3 >= num_confirmations(3) -> EXECUTES
    // even though B is no longer an authorized key: only C and D are live confirmers.
    testing_env!(context_with_key(pk_d(), amount));
    c.confirm(request_id);
    assert_eq!(c.requests.get(&request_id), None); // executed with only 2 live signers
}
```
This demonstrates the request executes with the count reaching `num_confirmations` while one of the counted "confirmations" belongs to a key that was already deleted, i.e., fewer live members actually approved than the threshold requires. [3](#0-2)
