### Title
Epoch-keyed instant-withdraw claim basis fragments unfunded receipts across epochs, inflating `defaultRecoveryPrice` and permanently freezing older instant claimants - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` tracks instant-withdraw claims in two different keys: a global unfunded counter `pendingInstantWithdraws` and a per-epoch bucket `instantWithdrawClaimsByEpoch[epochNumber]`. When `startEpoch` only partially funds the instant queue and the pool later defaults in a subsequent epoch, `defaultPendingClaimBasis()` adds only the *current* epoch's instant claims to the recovery basis even though `pendingInstantWithdraws` still reflects the older epoch's unfunded receipts. This is the same bug class as the Fuel fix: identical claims fragmented by an epoch key so that the aggregate (the "vote group"/claim basis) is undercounted.

### Finding Description
In `requestInstantWithdraw` each receipt is recorded both globally and per-epoch (`instantWithdrawsRequestsByEpoch[user][currentEpoch]`, `instantWithdrawClaimsByEpoch[currentEpoch]`) and `pendingInstantWithdraws` is increased [1](#0-0) . `collectInstantWithdrawFunds` decrements only the global counter, so a partially funded instant queue leaves `pendingInstantWithdraws > 0` while `epochNumber` advances at the next `stopEpoch` [2](#0-1) [3](#0-2) .

At default finalization, `defaultPendingClaimBasis` computes `basis = pendingWithdraws + instantWithdrawClaimsByEpoch[epochNumber]` — i.e., only the *current* epoch's instant claims [4](#0-3) . Old-epoch unfunded instant receipts (still inside `pendingInstantWithdraws`/`instantWithdrawsRequests`) are excluded from `totalBasis`, so `recoveryPrice = reserveAmount * RECOVERY_FULL / totalBasis` is inflated [5](#0-4) . Worse, `_defaultPrefundedInstantReserve` uses the same current-epoch-only basis, so already-held funds backing old instant claims are not reserved [6](#0-5) . On the claim side, `_claimDefaultedInstantWithdrawRequest` only clears `instantWithdrawsRequestsByEpoch[defaultRecoveryEpoch]`, leaving old-epoch instant receipts to fall through to the par-funded path, where `_transferFundedClaim` reverts because the balance is consumed by the reserve [7](#0-6) [8](#0-7) .

### Impact Explanation
Two symmetric harms from one undercounted basis:
- **Theft of unclaimed yield:** normal defaulted-epoch claimants and current-epoch instant claimants each receive `claimBasis * defaultRecoveryPrice / RECOVERY_FULL` at an inflated price, draining `defaultRecoveryReserve` beyond their fair share [9](#0-8) .
- **Permanent freeze:** holders of the old-epoch unfunded instant receipts can never claim — the defaulted path ignores their epoch key and the funded path reverts on the reserve guard [10](#0-9) . Loss equals `old-epoch instant basis × intended recovery price`.

### Likelihood Explanation
Requires: (a) an instant-withdraw queue only partially funded at `startEpoch` (explicitly contemplated by the code comments for `_defaultPrefundedInstantReserve`), (b) the pool surviving into a later epoch and then defaulting. All calls in the sequence (`startEpoch`, `stopEpoch`, `finalizeDefault`) are honest manager/owner actions; the attacker is merely a defaulted-epoch withdraw requester claiming first. This is an edge case requiring a specific multi-epoch sequence plus a default, hence moderate-low likelihood but a deterministic accounting break once reached.

### Recommendation
Make the default basis epoch-agnostic, like the Fuel fix grouping by `block_id`: either sum `instantWithdrawClaimsByEpoch` over all epochs with unfunded claims, or track a global `instantWithdrawClaims` aggregate alongside `pendingInstantWithdraws` so `defaultPendingClaimBasis()` includes every unfunded instant receipt regardless of request epoch. Symmetrically, `_claimDefaultedInstantWithdrawRequest` and `_defaultPrefundedInstantReserve` should clear/count per-user instant receipts across all epochs, not only `defaultRecoveryEpoch`/`epochNumber`.

### Proof of Concept
Foundry fork PoC sketch (against `test/foundry` harness, e.g. `IdleCreditVault`-based vault):

```solidity
// 1. Running epoch, APR decreased -> user A requestWithdraw triggers
//    requestInstantWithdraw(X). pendingInstantWithdraws = X,
//    instantWithdrawClaimsByEpoch[E] = X.
// 2. Manager startEpoch with only partial cash: collectInstantWithdrawFunds(X/2)
//    -> pendingInstantWithdraws = X/2, epoch still unfunded.
// 3. stopEpoch -> epochNumber = E+1. No new instant requests in E+1.
// 4. Attacker B (KYC'd lender) requestWithdraw in epoch E+1
//    -> pendingWithdraws = B_amount, withdrawsRequestsByEpoch[B][E+1].
// 5. Borrower fails repayment; manager stopEpoch -> defaulted.
// 6. finalizeDefault(recovered, source):
//    totalBasis = activeBasis + pendingWithdraws + instantWithdrawClaimsByEpoch[E+1](=0)
//    -> old instant basis X/2 excluded -> defaultRecoveryPrice inflated.
// 7. B calls claimWithdrawRequest -> receives claimBasis * inflatedPrice,
//    draining reserve beyond fair share.
// 8. A calls claimInstantWithdrawRequest -> _claimDefaultedInstantWithdrawRequest
//    clears epoch E+1 (zero for A); instantWithdrawsRequests[A] falls to
//    _transferFundedClaim -> reverts NotAllowed (balance == reserve).
// Assert: A's claim permanently reverts; B received > B_basis * fairPrice.
```

Caveat: step 2 requires `startEpoch` to succeed with only partial instant-queue funding; the in-code comments confirm partial coverage is an accepted state (`pendingInstantWithdraws` remaining non-zero after `startEpoch`), but the PoC should verify the exact CDO funding path allows it on the target deployment.

```text
  function _defaultPrefundedInstantReserve() internal view returns (uint256 prefundedReserve) {
    uint256 pendingInstant = pendingInstantWithdraws;
```

```text
  function _claimDefaultedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, defaultEpoch, true);
    if (claimBasis == 0) return amount;

    // pendingWithdraws stores the claim basis owed by the borrower, including APR0 interest.
    pendingWithdraws -= claimBasis;
    // Only receipt principal exists as strategy tokens. APR0 interest is included in claimBasis
    // but was never minted as a user strategy-token receipt.
    _burn(_user, burnAmount);
    amount = (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL;
    _transferDefaultRecovery(_user, amount);
  }
```

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```

```text
  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
    }
    underlyingToken.safeTransfer(_user, _amount);
  }
```
