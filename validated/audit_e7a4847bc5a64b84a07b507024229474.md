### Title
LDAP-backed users deactivated upstream (e.g., banned/disabled) can still authenticate and act via a previously-issued API key - ([File: core/sessions/ldapauth/ldap.go])

### Summary
The HackerOne report describes a HackerOne platform bug where a banned user, blocked from submitting reports through normal session-based flows, could bypass the ban by authenticating with a previously-issued API key, since the API-key code path did not re-check the account's restricted/banned status. The Chainlink node's LDAP authentication provider (`core/sessions/ldapauth`) has an analogous gap: interactive session login (`FindUser`) revalidates the upstream "active" status of a user on every request, but the API-token authentication path (`FindUserByAPIToken`) trusts a locally cached role/email and never re-checks whether the user has since been deactivated upstream.

### Finding Description
When an LDAP user logs in interactively, `ldapAuthenticator.FindUser` queries the upstream LDAP server for the account's active status via `validateUsersActive` and rejects it with `"user not active"` if the account has been disabled/deactivated in the identity provider: [1](#0-0) 

However, `FindUserByAPIToken`, which is invoked by `web/auth.AuthenticateByToken` for every API-key-authenticated request, only queries the local `ldap_user_api_tokens` cache table for the email, role, and token expiry — there is no call to `validateUsersActive` or any upstream re-check: [2](#0-1) 

This cached token data is only reconciled with the upstream LDAP directory's active-status state by a periodic background job (`LDAPServerStateSyncer.Work`/`run`), gated by the `UpstreamSyncInterval` config, which purges tokens belonging to users no longer marked active upstream: [3](#0-2) [4](#0-3) 

Because this sync is asynchronous/interval-based rather than checked per-request, a user whose account is disabled/deactivated upstream (the operational equivalent of a "ban") continues to be treated as authenticated and retains their cached role for every API-token request until the next sync cycle removes the token. The generic `web/auth.AuthenticateByToken` middleware, shared across all authentication providers, simply trusts whatever `FindUserByAPIToken` returns and grants the corresponding role in the request context: [5](#0-4) 

### Impact Explanation
An operator using LDAP authentication (`WebServer.AuthenticationMethod = 'ldap'`) who disables/deactivates a user account in the upstream directory — e.g., because that user is compromised, offboarded, or otherwise restricted — cannot immediately revoke that user's node access if the user holds a previously issued API token. The user's API-key-authenticated requests continue to succeed with their last-known role (potentially Admin/Edit/Run), allowing continued job management, key operations, or fund-moving actions, until the background sync interval elapses and purges the stale token. This is a privilege/authorization bypass analogous to the reported bug class: restriction imposed on the primary (session) channel is not enforced on the secondary (API key) channel.

### Likelihood Explanation
This requires the node to be configured with LDAP authentication and `UserAPITokenEnabled = true` — a non-default but supported and documented configuration. The window of exposure is directly proportional to the configured `UpstreamSyncInterval`; operators with long intervals (or misconfigured/omitted intervals) face a larger exposure window. No attacker action beyond already holding a previously legitimate API token is required — this is purely a server-side revalidation gap, not something exploitable by an unrelated third party, but it directly undermines administrator expectations that deactivating a user cuts off all access.

### Recommendation
Have `FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` perform (or trigger) the same `validateUsersActive` check against the upstream LDAP server that `FindUser` performs, rejecting the token if the account is no longer active, rather than relying solely on the periodic sync job to purge revoked users' tokens.

### Proof of Concept
1. Configure a Chainlink node with `WebServer.AuthenticationMethod = 'ldap'` and `WebServer.LDAP.UserAPITokenEnabled = true`, with a reasonably long `UpstreamSyncInterval`.
2. As an active LDAP user, log in and call `POST /v2/user/token` to obtain an API key/secret (persisted via `SetAuthToken`, see [6](#0-5) ).
3. Have the LDAP administrator deactivate/disable this user's account in the upstream directory (setting the configured `ActiveAttribute` to a non-allowed value).
4. Attempt to log in interactively via `/sessions` — this fails with `"user not active"` because `FindUser` calls `validateUsersActive`.
5. Instead, issue an authenticated API request using the previously obtained API key/secret headers (`X-Chainlink-APIKey` / `X-Chainlink-APISecret`) before the next `UpstreamSyncInterval` tick — the request succeeds with the user's cached role, since `FindUserByAPIToken` never checks upstream active status.

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}
	if !foundUserToken.Valid { // API Token expired, purge
		if _, execErr := l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE token_key = $1", apiToken); execErr != nil {
			l.lggr.Errorf("error purging stale ldap API token session: %v", execErr)
		}
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	return sessions.User{
		Email: foundUserToken.UserEmail,
		Role:  foundUserToken.UserRole,
	}, nil
}

// SetAuthToken updates the user to use the given Authentication Token.
func (l *ldapAuthenticator) SetAuthToken(ctx context.Context, user *sessions.User, token *auth.Token) error {
	if !l.config.UserApiTokenEnabled() {
		return errors.New("API token is not enabled ")
	}

	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(token, salt)
	if err != nil {
		return fmt.Errorf("LDAPAuth SetAuthToken hashed secret error: %w", err)
	}

	err = sqlutil.TransactDataSource(ctx, l.ds, nil, func(tx sqlutil.DataSource) error {
		// Is this user a local CLI Admin or upstream LDAP user?
		// Check presence in local users table. Set localauth_user column true if present.
		// This flag omits the session/token from being purged by the sync daemon/reaper.go
		isLocalCLIAdmin := false
		err = l.ds.QueryRowxContext(ctx, "SELECT EXISTS (SELECT 1 FROM users WHERE email = $1)", user.Email).Scan(&isLocalCLIAdmin)
		if err != nil {
			return fmt.Errorf("error checking user presence in users table: %w", err)
		}

		// Remove any existing API tokens
		if _, err = l.ds.ExecContext(ctx, "DELETE FROM ldap_user_api_tokens WHERE user_email = $1", user.Email); err != nil {
			return fmt.Errorf("error executing DELETE FROM ldap_user_api_tokens: %w", err)
		}
		// Create new API token for user
		_, err = l.ds.ExecContext(
			ctx,
			"INSERT INTO ldap_user_api_tokens (user_email, user_role, localauth_user, token_key, token_salt, token_hashed_secret, created_at) VALUES ($1, $2, $3, $4, $5, $6, now())",
			user.Email,
			user.Role,
			isLocalCLIAdmin,
			token.AccessKey,
			salt,
			hashedSecret,
		)
		if err != nil {
			return fmt.Errorf("failed insert into ldap_user_api_tokens: %w", err)
		}
		return nil
	})
	if err != nil {
		return errors.New("error creating API token")
	}

	l.auditLogger.Audit(audit.APITokenCreated, map[string]any{"user": user.Email})
	return nil
}

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

func (l *LDAPServerStateSyncer) Close() error {
	close(l.stopCh)
	<-l.done
	return nil
}

func (l *LDAPServerStateSyncer) run() {
	defer close(l.done)
	ctx, cancel := l.stopCh.NewCtx()
	defer cancel()
	ticker := time.NewTicker(l.config.UpstreamSyncInterval().Duration())
	defer ticker.Stop()

	for {
		select {
		case <-ctx.Done():
			return
		case <-ticker.C:
			l.Work(ctx)
		}
	}
}

func AuthenticateByToken(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	token := &auth.Token{
		AccessKey: c.GetHeader(APIKey),
		Secret:    c.GetHeader(APISecret),
	}
	if token.AccessKey == "" {
		return auth.ErrorAuthFailed
	}

	if token.Secret == "" {
		return auth.ErrorAuthFailed
	}

	// We need to first load the user row so we can compare tokens using the stored salt
	user, err := authr.FindUserByAPIToken(ctx, token.AccessKey)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) || errors.Is(err, clsessions.ErrUserSessionExpired) {
			return auth.ErrorAuthFailed
		}
		return err
	}

	ok, err := clsessions.AuthenticateUserByToken(token, &user)
	if err != nil {
		return err
	}
	if !ok {
		return auth.ErrorAuthFailed
	}

	c.Set(SessionUserKey, &user)

	return nil
}
