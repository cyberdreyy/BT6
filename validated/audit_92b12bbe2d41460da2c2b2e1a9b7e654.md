### Title
Loss haircut keys the whole `pendingWithdraws` aggregate to a single epoch, so earlier-epoch receipts escape the haircut and over-claim - ([File: contracts/strategies/idle/IdleCreditVault.sol](contracts/strategies/idle/IdleCreditVault.sol))

### Summary
`collectWithdrawFunds` prices a realized stop-epoch loss against the entire `pendingWithdraws` aggregate, but stores the haircut under a single epoch key (`lossRecoveryPriceByEpoch[epochNumber]`). Claimants only apply that haircut to receipts recorded under `lastWithdrawRequest[_user]`; receipts from earlier epochs that are still inside `pendingWithdraws` are paid out at par by `_claimFundedWithdrawRequest`. This is the same class as the libevent bug: the funded amount ("pullup window") covers only a fraction of the logical claim set, yet the claim path iterates the full aggregate and pays the unfunded remainder as if it were funded.

### Finding Description
`requestWithdraw` records each receipt under the current `epochNumber` and adds `_amount` to both `withdrawsRequestsByEpoch[_user][currentEpoch]` and the aggregate `withdrawsRequests[_user]` / `pendingWithdraws`, updating `lastWithdrawRequest[_user]` each time. A second request in a later epoch is allowed: the only guard rejects a new request when `lossRecoveryPriceByEpoch[lastWithdrawRequest]` is non-zero, and it is non-zero only *after* a loss has already been collected. [1](#0-0) 

On a loss, `collectWithdrawFunds` computes `lossRecoveryPrice = _amount * 1e18 / pendingBasis` over the *whole* aggregate and zeroes `pendingWithdraws`, i.e. the strategy receives `pendingBasis * price` — enough to pay every receipt at `price`, not at par. [2](#0-1) 

But the claim path splits payment by epoch window:
- `_claimLossAdjustedWithdrawRequest` looks up `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]` and pays `claimBasis * price` only for receipts in that one epoch. [3](#0-2) 
- `_claimFundedWithdrawRequest` then pays the *entire remaining* `withdrawsRequests[_user]` aggregate at par via `_transferFundedClaim`. [4](#0-3) 

`previewLossAdjustedWithdrawFunds` itself states the intended invariant: "all pending receipts share their aggregate portion of the loss pro rata." [5](#0-4) 

### Impact Explanation
A user with receipts in two pending epochs gets the earlier-epoch portion paid at 100% even though the borrower only funded `pendingBasis * price`. If the attacker claims before other users, they withdraw more than their pro-rata funded share — direct theft of other claimants' funded underlying; if they claim last, the transfer reverts, permanently freezing the remaining claimants' funds. Quantification: if receipts are split `A` (epoch N−1) and `B` (epoch N) with recovery price `p < 1`, the attacker extracts `A + B·p` while only `(A+B)·p` was funded — an over-payment of `A·(1−p)`, which for a 50% loss and equal receipts is ~25% of the funded pool.

### Likelihood Explanation
Any unprivileged user (KYC-passing lender / tranche holder) can create the precondition: call `requestWithdraw` in epoch N−1, deliberately skip `claimWithdrawRequest`, then `requestWithdraw` again in epoch N (allowed, since no loss price exists yet). The trigger is `stopEpochWithDuration(_lossAmount)` — a normal, honest-manager path whenever the borrower underpays. Note a second-order mismatch: `epochNumber` is bumped inside `deposit()` during the stop flow (`deposit` increments `epochNumber` while `isEpochRunning` is still true). [6](#0-5)  If `collectWithdrawFunds` runs after that bump, the price is stored under `requestEpoch+1` and never matches any `lastWithdrawRequest`, so *all* loss-adjusted receipts are paid at par — same invariant break, larger magnitude. Exact ordering was not fully verified against `IdleCDOEpochVariant.stopEpoch`, but either ordering is exploitable whenever `pendingWithdraws` spans more than one request epoch.

### Recommendation
Track the haircut per receipt, not per lookup key. Either (a) apply the loss pro rata at claim time to the user's full pending basis (iterate all epochs or store the user's aggregate basis at the loss epoch), or (b) revert `requestWithdraw` when the user has any unfunded pending receipts, enforcing one pending epoch per user — mirroring the already-enforced rule for post-default requests. Also make `collectWithdrawFunds` record the price under an epoch key guaranteed to equal the receipts' `lastWithdrawRequest` (e.g., `epochNumber` before the stop-time bump), or store a global `pendingLossPrice` consumed on claim.

### Proof of Concept
Foundry fork sketch (single user demonstrates the over-claim; adding a second claimant shows insolvency):

```solidity
// Setup: AYS vault, fees 0 for clarity, epoch running normally.
uint256 amt = 10_000 * ONE_SCALE;
idleCDO.depositAA(amt);

// Epoch N-1: request half, do NOT claim.
uint256 reqA = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)) / 2, address(AAtranche));
_startEpochAndCheckPrices(1);
// stop epoch N-1 fully funded (no loss) so reqA is claimable but left unclaimed.
vm.warp(cdoEpoch.epochEndDate() + 1);
deal(underlying, borrower, strategy.pendingWithdraws() + cdoEpoch.expectedEpochInterest());
cdoEpoch.stopEpoch(0, 0);

// Epoch N: request the rest. Guard passes because no loss price exists yet.
uint256 reqB = cdoEpoch.requestWithdraw(IERC20(AAtranche).balanceOf(address(this)), address(AAtranche));
_startEpochAndCheckPrices(2);
vm.warp(cdoEpoch.epochEndDate() + 1);

// Borrower underpays: fund only 50% of aggregate pendingWithdraws via stopEpochWithDuration.
(uint256 pendingToFund,) = strategy.previewLossAdjustedWithdrawFunds(lossAmt);
deal(underlying, borrower, pendingToFund + cdoEpoch.expectedEpochInterest());
cdoEpoch.stopEpochWithDuration(lossAmt, 0, 0); // sets lossRecoveryPriceByEpoch[epochN] = 0.5e18

// Claim: reqB paid at 0.5, reqA paid at par -> user receives reqA + reqB/2
// while strategy only holds (reqA + reqB)/2 -> drains funds owed to other claimants
// (or reverts for the last claimant -> permanent freeze).
cdoEpoch.claimWithdrawRequest();
```

Uncertainty: whether `lossRecoveryPriceByEpoch` is keyed pre- or post-bump of `epochNumber` during `stopEpochWithDuration` was not fully verified in `IdleCDOEpochVariant`; the multi-epoch-aggregate exploit holds under the pre-bump ordering, and the post-bump ordering makes even single-epoch loss receipts claimable at par.

    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  /// @notice Preview how a realized stop-epoch loss is split between active LPs and pending receipts.
  /// @dev Without pending receipts, a loss cannot exceed its active basis. When pending receipts
  /// exist, all pending receipts share their aggregate portion of the loss pro rata because the
  /// pending bucket does not retain tranche identity. The remaining active loss is later applied
  /// by the CDO through its ordinary BB-first waterfall.
  /// @param _lossAmount realized loss amount
  /// @return pendingToFund amount of pending withdrawals that should be funded by the borrower
  /// @return activeLoss amount of loss that remains assigned to active LPs
  function previewLossAdjustedWithdrawFunds(uint256 _lossAmount) external view returns (uint256 pendingToFund, uint256 activeLoss) {
    uint256 pendingBasis = pendingWithdraws;
    // Full zero-loss funding is safe for legacy aggregate receipts and needs no migration call.
    if (_lossAmount == 0) return (pendingBasis, _lossAmount);

    IIdleCDOEpochVariant cdo = IIdleCDOEpochVariant(idleCDO);
    uint256 activeBasis = _lossActiveBasis(cdo);
    if (pendingBasis == 0) {
      if (_lossAmount > activeBasis) revert NotAllowed();
      return (0, _lossAmount);
    }

    // Legacy pending receipts do not have the per-epoch ownership data needed to store a haircut.
    if (!defaultRecoveryInitialized) revert NotAllowed();
    uint256 totalBasis = activeBasis + pendingBasis;
    if (_lossAmount >= totalBasis) revert NotAllowed();

    uint256 pendingLoss = _lossAmount * pendingBasis / totalBasis;
    pendingToFund = pendingBasis - pendingLoss;
    activeLoss = _lossAmount - pendingLoss;
  }

  function _claimLossAdjustedWithdrawRequest(address _user) internal returns (uint256 amount) {
    uint256 lossEpoch = lastWithdrawRequest[_user];
    uint256 lossRecoveryPrice = lossRecoveryPriceByEpoch[lossEpoch];
    if (lossRecoveryPrice == 0) return amount;

    (uint256 claimBasis, uint256 burnAmount) = _clearWithdrawClaimForEpoch(_user, lossEpoch, false);
    if (claimBasis == 0) return amount;

    // pendingWithdraws was already cleared when the borrower funded the loss-adjusted amount.
    _burn(_user, burnAmount);
    amount = (claimBasis * lossRecoveryPrice) / RECOVERY_FULL;
    _transferFundedClaim(_user, amount);
  }
