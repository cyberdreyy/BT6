### Title
Deleting a multisig key does not purge its prior confirmations on other pending requests, allowing a request to execute with fewer live-member approvals than `num_confirmations` - (File: `multisig/src/lib.rs`, `multisig2/src/lib.rs`)

### Summary
The multisig contracts count confirmations toward the `num_confirmations` threshold from a `HashSet<PublicKey>` (or member set in `multisig2`) that is never cleaned up when the confirming key/member is removed from the multisig, unless that removed key happened to be the *original creator* of the request. A revoked key's stale confirmation on any request it previously confirmed (but did not create) remains counted forever, so a request can later be executed with a smaller number of truly-live approvals than the configured threshold requires.

### Finding Description
In `multisig/src/lib.rs`, `confirm()` decides whether to execute a request purely by counting entries already stored in `self.confirmations.get(&request_id)`: [1](#0-0) 

When a `DeleteKey` action executes, the cleanup logic only removes pending *requests whose original signer* (`r.signer_pk`) equals the deleted key; it does not touch that key's entries inside `self.confirmations` for other pending requests it had merely confirmed: [2](#0-1) 

The intended custody binding is:
```
confirmations counted toward num_confirmations  ==  approvals from currently-live members
```
Because a removed key's prior confirmation is never purged from `self.confirmations` for requests it didn't originate, this equality breaks: `confirmations counted > approvals from currently-live members`.

The same flaw is present in the newer `multisig2` contract. `delete_member()` only deletes requests originated by the removed member, not that member's confirmations recorded on other pending requests, and `confirm()` counts confirmations the same way: [3](#0-2) [4](#0-3) 

### Impact Explanation
This breaks the core custody guarantee of the multisig: a request (e.g. `Transfer`, `AddKey`, `FunctionCall`) can be executed while having strictly fewer approvals from currently valid/live members than `num_confirmations` requires. This is exactly the "multisig request executed below threshold" Critical scenario: funds can be moved, or a new access key can be added to the account, with an insufficient number of live authorizers, because one of the counted approvals came from a key/member that has since been revoked (e.g. because it was known to be compromised, or the employee/party holding it left the organization).

### Likelihood Explanation
No privileged or out-of-scope actor is required. Any legitimate use of the `DeleteKey`/`DeleteMember` action to rotate out a member (a normal, expected operational action, not requiring foundation/owner/redeploy) leaves behind stale confirmation entries. Any pending request that the removed member had confirmed prior to removal retains that confirmation indefinitely. A single additional, otherwise-legitimate confirmation from a currently live member is then enough to push the count over threshold and trigger execution, even though the effective number of live approvers is one less than required. This is easily triggered in normal contract usage (member rotation is a documented, expected multisig operation) and does not require simultaneous compromise of multiple current members.

### Recommendation
When removing a key/member (`DeleteKey` in `multisig`, `DeleteMember` in `multisig2`), iterate over all pending requests' confirmation sets and remove the deleted key/member from every one of them, not just from requests it originated. Alternatively, revalidate at `confirm()`-time (or at execution time) that every public key/member present in the stored confirmations set is still a live key/member of the contract before counting it toward `num_confirmations`.

### Proof of Concept
1. Initialize multisig with `num_confirmations = 3` and access keys `A, B, C, D`.
2. `A` calls `add_request(R)` where `R` is e.g. `Transfer { amount: <all funds> }` to an attacker-controlled `receiver_id`, without confirming.
3. `B` calls `confirm(R)` → `confirmations(R) = {B}` (< 3, stored, not executed) — see `confirm()` at [1](#0-0) .
4. `C` calls `confirm(R)` → `confirmations(R) = {B, C}` (< 3, stored, not executed).
5. Some time later, the organization legitimately revokes `B` (e.g. `B` is compromised or offboarded) via a separate, properly-confirmed `DeleteKey { public_key: B }` request. This executes `MultiSigRequestAction::DeleteKey`, which only purges requests *originated* by `B`; since `B` did not originate `R`, `R`'s `confirmations` set is left untouched, still containing `B` — see [2](#0-1) .
6. `D` (or `A`) now calls `confirm(R)`. The check `confirmations.len() + 1 >= num_confirmations` evaluates `2 + 1 >= 3` → true, and `R` (the `Transfer` to the attacker) is executed, even though `B`'s public key is no longer a valid access key on the account. Only two truly live keys (`C` and `D`) actually authorized the transfer at execution time, one fewer than the configured 3-of-N threshold.

    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert!(
            !confirmations.contains(&env::signer_account_pk()),
            "Already confirmed this request with this key"
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(env::signer_account_pk());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
