### Title
Tenure-extend idle-timeout gate can be bypassed by reusing any differing canonical `burn_view_consensus_hash`, letting a single miner extend its tenure indefinitely - ([File: stacks-signer/src/chainstate/v1.rs], [File: stacks-signer/src/chainstate/v2.rs])

### Summary
The signer's full-tenure-extend validation is supposed to gate a `TenureChangeCause::Extended` transaction behind either (a) the burnchain view having genuinely changed, or (b) a configured idle timeout (`tenure_idle_timeout_secs` + buffer) having elapsed since the tenure's last block. In practice, condition (a) is checked only as a "not-equal" comparison against the tenure's *current* known burn view, with no requirement that the supplied `burn_view_consensus_hash` represent a *later*/new sortition. A single active miner can therefore satisfy `changed_burn_view = true` by supplying any other canonical, height-eligible consensus hash and repeatedly bypass the idle-timeout throttle, extending its own tenure indefinitely without ever waiting out `tenure_idle_timeout_secs`.

### Finding Description
In `check_proposal`, the full tenure-extend gate is: [1](#0-0) 

`current_burn_view` is fetched from `client.get_tenure_tip(tenure_id).burn_view` — the tenure's *currently known* burn view — and `changed_burn_view` is simply `tenure_extend.burn_view_consensus_hash != current_burn_view`. If `changed_burn_view` is true, the idle-timeout check (`enough_time_passed`) is skipped entirely (`if !changed_burn_view && !enough_time_passed && !is_in_replay`).

Node-side validation of the tenure-change payload (`check_nakamoto_tenure`) only requires that `burn_view_consensus_hash` refer to a canonical sortition whose height is `>=` the tenure's own sortition height, and — for `Extended` causes — that `prev_tenure_consensus_hash == tenure_consensus_hash`: [2](#0-1) 

Nothing in this check forces `burn_view_consensus_hash` to be the *latest* canonical burn view; any canonical sortition consensus hash at or after the tenure's own sortition height is accepted. Combined with the signer-side check, a miner can supply any such hash that merely differs from the signer's currently cached `current_burn_view`, satisfy `changed_burn_view`, and skip the idle-timeout wait — over and over, by alternating among a small set of valid canonical hashes.

This is confirmed by the existing unit tests, which show that supplying an arbitrary/unrelated consensus hash (`ConsensusHash([64;20])`) as `burn_view_consensus_hash` causes the extend proposal to *validate* even with none of the real idle-timeout conditions satisfied: [3](#0-2) [4](#0-3) 

This is the direct structural analog of the reported `setEndTimestamp` issue: a privileged single actor (the current miner) can trivially reset/bypass a deadline-based gate (`tenure_idle_timeout_secs`) that was specifically designed to force a timely handoff, defeating the purpose of the throttle and letting the actor "extend" state indefinitely.

### Impact Explanation
The `tenure_idle_timeout_secs`/`tenure_extend_wait_timeout_ms` mechanism exists precisely to bound how long one miner can hold the tenure before yielding to the next sortition winner or before the block-limit/read-count budget is legitimately refreshed (see the miner/signer coordination doc): [5](#0-4) 

If the "changed burn view" escape hatch can be satisfied by any differing-but-canonical hash rather than a genuinely new/latest burn view, a malicious or buggy miner can repeatedly re-trigger `Extended` tenure changes and keep the signer approving them without ever honoring the idle timeout. This is a liveness/fairness break: it can starve other winning miners of their turn and lets one miner indefinitely retain tenure and its associated cost/read budgets, which is exactly the "no timely handoff / never lets the intended condition become false" failure class described in the source report, mapped onto the signer's block-proposal-approval logic (a signer approving/signing a proposal whose stated justification for bypassing a safety gate is not actually true).

### Likelihood Explanation
This requires no majority collusion and no signer key compromise — only the currently active, one-slot miner crafting a `TenureChangePayload` with a `burn_view_consensus_hash` equal to some other canonical, height-eligible consensus hash (e.g., an earlier sortition within the same tenure window) instead of the true current tip. This is well within a single miner's normal capability to construct, and the existing test suite already demonstrates the signer accepts it (`check_tenure_extend_burn_view_change` expects the proposal to validate).

### Recommendation
Tighten the "changed burn view" condition so it cannot be satisfied by an arbitrary, stale, or unrelated canonical hash:
- Require that `tenure_extend.burn_view_consensus_hash` corresponds to a sortition height strictly greater than (not merely different from) the current known `current_burn_view`'s height, i.e., it must represent forward progress on the canonical burnchain.
- Alternatively/additionally, independently re-derive "did the burn view actually advance" from the signer's own most-recently-observed canonical burn tip rather than trusting a simple inequality against a single cached `tenure_tip.burn_view` value, and reject extends whose burn view does not match the signer's currently observed canonical tip.
- Apply the equivalent fix to both `stacks-signer/src/chainstate/v1.rs` and `v2.rs`, since both contain the identical bypassable logic.

### Proof of Concept
1. Current miner wins tenure at sortition `T` and mines a block; the signer's `get_tenure_tip` reports `current_burn_view = C0`.
2. Before `tenure_idle_timeout_secs` elapses, the miner proposes a block containing a `TenureChangePayload{ cause: Extended, burn_view_consensus_hash: C_old, tenure_consensus_hash: T, prev_tenure_consensus_hash: T, ... }` where `C_old` is any other canonical consensus hash whose sortition height is `>= T`'s height (e.g., a hash from earlier in the same tenure window) and `C_old != C0`.
3. Node-side `check_nakamoto_tenure` accepts this payload because all its height/ancestor constraints are satisfied (see cited checks) — it does not require `C_old` to be the true latest tip.
4. Signer-side `check_proposal` computes `changed_burn_view = (C_old != C0) = true`, and since the first branch of the `if !changed_burn_view && !enough_time_passed && !is_in_replay` is false, the idle-timeout requirement is skipped and the extend is approved — matching the behavior explicitly exercised by `check_tenure_extend_burn_view_change` in the existing test suite.
5. The miner repeats this with a different eligible `C_old` value each round, perpetually satisfying `changed_burn_view` and never actually waiting out `tenure_idle_timeout_secs`, extending its tenure indefinitely.
