### Title
Bridge/Bridges GraphQL queries expose `outgoingToken` bridge credentials to view-role users - ([File: core/web/resolver/query.go])

### Summary
The `Bridge` and `Bridges` resolvers only call `authenticateUser`, which merely checks for a valid session and grants access to any role including `UserRoleView`. Because `BridgeResolver.OutgoingToken()` unconditionally returns `bridge.OutgoingToken`, a session with the lowest privilege role can retrieve the bridge's outgoing authentication token via GraphQL, even though this token is a secret used by the node to authenticate to the external adapter/bridge.

### Finding Description
`(r *Resolver) Bridge` and `(r *Resolver) Bridges` gate access with `authenticateUser(ctx)` only: [1](#0-0) [2](#0-1) 

`authenticateUser` simply checks a valid authenticated session exists and does not restrict by role, unlike `authenticateUserCanRun`, `authenticateUserCanEdit`, and `authenticateUserIsAdmin`, which explicitly exclude `UserRoleView`: [3](#0-2) 

The `BridgeResolver.OutgoingToken()` field resolver returns the raw stored secret with no redaction: [4](#0-3) 

The GraphQL schema exposes `outgoingToken` as a plain non-nullable string field on `Bridge`: [5](#0-4) 

`OutgoingToken` is generated as a genuine secret (`utils.NewSecret(24)`) at bridge creation time and is stored/used to authenticate the node's outbound requests to the external adapter, as opposed to `IncomingTokenHash`, which is only ever hashed and never exposed after creation: [6](#0-5) 

A view-role session can therefore issue `{bridges{results{name url outgoingToken}}}` or `{bridge(id:"x"){... on Bridge {url outgoingToken}}}` and receive the adapter URL plus the outgoing secret token in the response, as confirmed by the existing table test which asserts the exact plaintext token is returned in a successful authenticated response (test does not distinguish role, since `authenticateUser` accepts any role): [7](#0-6) [8](#0-7) 

Note: the equivalent REST `BridgeResource` presenter also unconditionally serializes `OutgoingToken` for any authenticated caller with read access to `/v2/bridge_types`: [9](#0-8) 
This shows the exposure is a pre-existing, consistent design decision spanning both REST and GraphQL — the app treats `OutgoingToken` as data visible to any authenticated user, unlike `IncomingToken`, which is only returned once at creation via `CreateBridgeSuccessResolver.IncomingToken()` (gated separately by `authenticateUserCanEdit` in the mutation resolver, not examined here for `Create`/`Update`). Because the same secret-exposure behavior already exists identically in the long-standing REST API, this is best characterized as an established (if debatable) authorization-model choice for `view` role rather than a GraphQL-specific regression, but it remains a genuine credential-disclosure path reachable by the lowest-privileged authenticated role.

### Impact Explanation
A `UserRoleView` session — the lowest privilege authenticated role in the node — can read the `outgoingToken` and `url` for every configured bridge. This is Chainlink's node-to-external-adapter shared secret; possessing it (together with the bridge URL, also disclosed) lets an attacker directly query the external adapter/bridge endpoint outside of the node, potentially triggering paid computations, hitting rate-limited quotas, or pivoting into internal-only bridge infrastructure if the URL is not internet-reachable but is reachable from the attacker's vantage point. This matches a credential/secret disclosure impact class, scoped to bridge/EI adapter credentials rather than node keys or funds.

### Likelihood Explanation
Trivial and fully repeatable: any user provisioned with `view` role (the minimum role a node operator can grant) can immediately query `bridges{results{outgoingToken url}}` over the standard `/query` GraphQL endpoint with no additional preconditions, and existing unit tests confirm the plaintext token is returned in the response payload.

### Recommendation
Restrict `Bridge`/`Bridges` resolvers (or at minimum the `outgoingToken` field) to `authenticateUserCanEdit` (or a dedicated bridge-secret permission), or redact `outgoingToken` from the resolver output for `view`/`run` roles and only reveal it to `edit`/`admin` roles, mirroring how `IncomingToken` is already treated as create-time-only sensitive data. Apply the equivalent fix to the REST `BridgeResource` presenter/`BridgeTypesController` if the intended fix is to restrict this data node-wide rather than only in GraphQL.

### Proof of Concept
Go table test plan (extending `core/web/resolver/bridge_test.go`):
1. Build a GQL test session authenticated with `sessions.UserRoleView` (via the `gqlTestFramework`/`authenticated` mechanism used in `Test_Bridges`/`Test_Bridge`).
2. Mock `App.BridgeORM().BridgeTypes` / `FindBridge` to return a `bridges.BridgeType` with `OutgoingToken: "secret-outgoing-token"`.
3. Execute the query `{bridges{results{name url outgoingToken}}}` (or `bridge(id:"bridge1"){...outgoingToken}`) as the view-role session.
4. Assert the response is NOT an authorization error and that `outgoingToken` equals `"secret-outgoing-token"` — demonstrating the current behavior returns the secret to a view-role user.
5. After applying the fix (switching to `authenticateUserCanEdit` or field-level redaction), re-run and assert either a `RoleNotPermittedError`/`Unauthorized` response for view role, or that `outgoingToken` is omitted/redacted for view role while still returned for edit/admin roles.

// Bridge retrieves a bridges by name.
func (r *Resolver) Bridge(ctx context.Context, args struct{ ID graphql.ID }) (*BridgePayloadResolver, error) {
	if err := authenticateUser(ctx); err != nil {
		return nil, err
	}

	name, err := bridges.ParseBridgeName(string(args.ID))
	if err != nil {
		return nil, err
	}

	bridge, err := r.App.BridgeORM().FindBridge(ctx, name)
	if err != nil {
		if errors.Is(err, sql.ErrNoRows) {
			return NewBridgePayload(bridge, err), nil
		}

		return nil, err
	}

	return NewBridgePayload(bridge, nil), nil
}

// Authenticates the user from the session cookie, presence of user inherently provides 'view' access.
func authenticateUser(ctx context.Context) error {
	if _, ok := auth.GetGQLAuthenticatedSession(ctx); !ok {
		return unauthorizedError{}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'run' role.
func authenticateUserCanRun(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	if session.User.Role == sessions.UserRoleView {
		return RoleNotPermittedError{session.User.Role}
	}
	return nil
}

// Authenticates the user from the session cookie and asserts at least 'edit' role.
func authenticateUserCanEdit(ctx context.Context) error {
	session, ok := auth.GetGQLAuthenticatedSession(ctx)
	if !ok {
		return unauthorizedError{}
	}
	switch session.User.Role {
	case sessions.UserRoleView, sessions.UserRoleRun:
		return RoleNotPermittedError{session.User.Role}
	default:
	}
	return nil
}

// NewBridgeType returns a bridge type authentication (with plaintext
// password) and a bridge type (with hashed password, for persisting)
func NewBridgeType(btr *BridgeTypeRequest) (*BridgeTypeAuthentication,
	*BridgeType, error,
) {
	incomingToken := utils.NewSecret(24)
	outgoingToken := utils.NewSecret(24)
	salt := utils.NewSecret(24)

	hash, err := incomingTokenHash(incomingToken, salt)
	if err != nil {
		return nil, nil, err
	}

	return &BridgeTypeAuthentication{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingToken:          incomingToken,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, &BridgeType{
		Name:                   btr.Name,
		URL:                    btr.URL,
		Confirmations:          btr.Confirmations,
		IncomingTokenHash:      hash,
		Salt:                   salt,
		OutgoingToken:          outgoingToken,
		MinimumContractPayment: btr.MinimumContractPayment,
		UseConnectionManager:   btr.UseConnectionManager,
	}, nil
}
