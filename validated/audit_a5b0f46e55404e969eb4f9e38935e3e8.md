### Title
Unauthenticated cross-subscriber DKG result confirmation via missing ownership check - (core/web/vault_controller.go)

### Summary
`VaultController.VerifyDKGResult` looks up a `ResultPackage` solely by the caller-supplied `instanceId`, with no check that the caller is entitled to that DKG ceremony/subscription. Any authenticated API caller who knows or guesses another subscriber's `instanceId` can retrieve that subscriber's `ReportWithResultPackage` and get the node to verify it against an attacker-supplied `masterPublicKey`.

### Finding Description
The handler decodes the request body into `VerifyDKGResultRequest{InstanceID, MasterPublicKey}` and immediately calls `orm.ReadResultPackage(c.Request.Context(), dkgocrtypes.InstanceID(req.InstanceID))` with no association to the requester's identity, role, or subscription ownership [1](#0-0) . It then verifies the retrieved `ReportWithResultPackage` against the attacker-supplied `masterPublicKey` using the node's local DKG recipient key and returns a 200 with a SHA-256 digest resource on success, or a 400 on verification failure, or 404 if not found [2](#0-1) . There is no authorization check comparing the instance's owning subscriber to the caller's token/identity anywhere in this function — the only gating is the presence of a valid DKG recipient key on the node itself (`vc.App.GetKeyStore().DKGRecipient()`), which is a node-level artifact, not a per-caller credential. Because HTTP-level authentication in this router only gates access by role (e.g., view/run/admin) and not by subscription/tenant ownership, any caller whose token clears the route's role check can submit an arbitrary `instanceId` belonging to a different subscriber's ceremony and receive a definitive 200-vs-400 signal about whether the supplied `masterPublicKey` matches that other subscriber's stored DKG result — an oracle for another party's protected state. The same missing-ownership pattern exists in the sibling `ExportDKGResult` handler, which returns the full hex-encoded `ReportWithResultPackage` for any `instanceId` with no ownership check at all [3](#0-2) .

I was unable to confirm from the indexed router.go content what specific role (`ViewRole`, `RunRole`, `AdminRole`) is required to reach `/v2/vault/dkg_results/verify` — router.go route registration for the vault group did not fully resolve in the search results. This is a limitation of what I could confirm; however, regardless of the exact role tier required, the vulnerability is that the handler performs no per-caller ownership/subscription check whatsoever, so any caller meeting only the route's role bar (which in Chainlink's API is not tied to subscription identity) can query any other subscriber's ceremony.

### Impact Explanation
This breaks per-subscriber isolation for DKG ceremony state: an unprivileged caller can (a) exfiltrate another subscriber's full serialized `ReportWithResultPackage` via `ExportDKGResult`, or (b) use `VerifyDKGResult` as a cryptographic oracle to confirm whether a guessed/derived `masterPublicKey` matches another subscriber's DKG result. This corresponds to a cross-user information disclosure / authorization-bypass class finding — confirmation and leakage of another party's confidential ceremony data, which could aid further compromise of that subscriber's vault secrets.

### Likelihood Explanation
Exploitability requires only knowledge of a valid `instanceId` string and a token that satisfies whatever role gate is applied to the `/v2/vault/dkg_results/*` routes; no ownership token or subscription-specific credential is checked in the handler itself. If the route is reachable at any authenticated role weaker than an ownership-scoped check (which the code shows does not exist), the exploit is trivially repeatable — one HTTP POST per guess.

### Recommendation
Add a per-request ownership/authorization check in `VaultController.VerifyDKGResult` and `ExportDKGResult` that validates the requester is entitled to the given `instanceId` (e.g., look up the owning subscription/DON identity associated with the instance and compare it against the caller's authenticated identity or an explicit ACL) before calling `orm.ReadResultPackage`. Reject with 403/404 (prefer 404 to avoid existence leakage) when the caller has no association with the instance.

### Proof of Concept
1. In `core/web/vault_controller_test.go`, use `vault.NewVaultORM(db).WriteResultPackage` to write a `ResultPackage` for instance `"owner-A-instance"` tied to a fictitious subscriber A.
2. Configure the test app with a DKG recipient key and set up an HTTP client authenticated with only view-role (or minimal role) credentials unrelated to subscriber A.
3. POST to `/v2/vault/dkg_results/verify` with `{"instanceId": "owner-A-instance", "masterPublicKey": "<attacker-supplied-or-guessed-key>"}`.
4. Assert that the handler proceeds past the ORM read (i.e., does not return 403/404 for lack of ownership) and instead returns either 200 (verification succeeded) or 400 (verification failed) — both of which prove the read succeeded without any ownership check, contrary to expected per-subscriber isolation.
5. Repeat with `ExportDKGResult` to confirm the raw `ReportWithResultPackage` hex is returned to the unrelated caller.
