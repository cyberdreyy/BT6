### Title
Signer weight double-counted across both accept and reject tallies in `StackerDBListener` — a rejection is never excluded from the acceptance weight - (File: `stacks-node/src/nakamoto_node/stackerdb_listener.rs`)

### Summary
`StackerDBListener::handle_stackerdb_event` (the node/coordinator-side StackerDB message loop) maintains two independent weight counters per block, `total_weight_approved` and `total_weight_rejected`, inside a shared `BlockStatus`. Each counter is individually deduplicated against replays of the *same* message type from a signer, but nothing prevents a single signer slot from contributing its weight to *both* counters for the same block by sending one `BlockResponse::Accepted` and one `BlockResponse::Rejected` message.

### Finding Description
`BlockStatus` tracks, per block hash: [1](#0-0) 

For `BlockResponse::Accepted`, weight is added to `total_weight_approved` gated only on `!block.gathered_signatures.contains_key(&slot_id)`, then the slot is also inserted into `responded_signers`: [2](#0-1) 

For `BlockResponse::Rejected`, weight is added to `total_weight_rejected` gated on `block.responded_signers.insert(slot_id)` returning `true` (first time this slot_id is seen at all): [3](#0-2) 

The two gates are on disjoint data structures for the purpose of preventing *repeat* messages of the same type, but there is no check in the `Accepted` branch for whether `slot_id` is already present in `responded_signers` (i.e., already rejected), nor a check in the `Rejected` branch for whether the slot already appears in `gathered_signatures` (i.e., already accepted). Consequently a single signer can send `Rejected` first (added to `total_weight_rejected`, and to `responded_signers`), then send `Accepted` for the very same `signer_signature_hash` — the accept branch only checks `gathered_signatures`, which is still empty for that slot, so it proceeds to add the same signer's weight to `total_weight_approved` as well.

The coordinator (`stacks-node/src/nakamoto_node/signer_coordinator.rs`) then evaluates both tallies against thresholds independently: [4](#0-3) 

This is structurally the same class of defect as the reported TOKE-11 bug: two running counters (`assetsPulled`/`debtMinDecrease` there, `total_weight_approved`/`total_weight_rejected` here) are updated per "round" (per incoming message) without accounting for how the two interact, so the termination/threshold conditions can be satisfied using overlapping weight instead of strictly partitioned weight. Here, the one signer's weight is not "spent once" across the vote — it can be recounted into the acceptance tally after already being counted in the rejection tally.

### Impact Explanation
This falls under the explicitly listed impact category "a rejection recounted as an accept." An equivocating (or simply buggy/faulty) signer that emits both an `Accepted` and a `Rejected` response for the same `signer_signature_hash` has its weight applied to both `total_weight_approved` and `total_weight_rejected`. Because `total_weight_approved + total_weight_rejected` is no longer bounded by `self.total_weight`, the two threshold checks in `signer_coordinator.rs` (70% approve / >30% blocking-minority reject) are no longer mutually exclusive over the true reward-set weight. This weakens the safety guarantee that the coordinator's accept/reject decision reflects a strictly-partitioned tally of distinct, non-overlapping signer weight, and it does so silently (there is no log or rejection of the conflicting second message; both are recorded as if independent, legitimate votes).

### Likelihood Explanation
Triggering the double count requires only a single signer (one StackerDB slot) sending two ordinary, individually-valid protocol messages for the same block over the existing StackerDB channel — no majority, no key compromise, and no invalid signature is needed. This satisfies the "single slot plus gossip" trigger bar. Reaching the point where this materially flips the coordinator's overall accept/reject decision does require the pre-existing honest-signer split to be close to the threshold boundary, but the underlying accounting defect itself is unconditionally triggerable by one signer.

### Recommendation
Make the two tallies mutually exclusive per slot: before crediting `total_weight_approved`, check that `slot_id` is not already present in `responded_signers` as a rejecter (and vice versa for the reject path), or better, track a single `HashMap<slot_id, Vote>` and refuse to overwrite/re-tally a slot that has already voted the opposite way for the same block, logging/ignoring the conflicting second message.

### Proof of Concept
1. Node is coordinating signatures for block `B` with `signer_signature_hash = H`, `weight_threshold` set to 70% of `total_weight`.
2. Signer at `slot_id = 5` (weight `w`) sends `SignerMessageV0::BlockResponse(BlockResponse::Rejected(...))` for `H`. `stackerdb_listener.rs` line 515-518 adds `w` to `total_weight_rejected` and inserts `5` into `responded_signers`.
3. The same signer at `slot_id = 5` then sends `SignerMessageV0::BlockResponse(BlockResponse::Accepted(...))` for the same `H` with a validly-recoverable signature. Lines 443-465: `gathered_signatures.contains_key(&5)` is `false`, so `total_weight_approved` is incremented by `w` again, and `5` is inserted into `gathered_signatures`.
4. `total_weight_approved` and `total_weight_rejected` now both include weight `w` from the same signer, so `total_weight_approved + total_weight_rejected` can exceed `self.total_weight`, letting both threshold branches in `signer_coordinator.rs` (lines 509-545) be reachable using overlapping rather than disjoint signer weight.
