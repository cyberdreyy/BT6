### Title
Duplicate tenure-change block dedup check uses global-acceptance state instead of local-signing state, allowing a signer to sign two conflicting tenure-start blocks - ([File: stacks-signer/src/chainstate/v1.rs])

### Summary
`SortitionsView::validate_tenure_change_payload` in `stacks-signer/src/chainstate/v1.rs` guards against re-signing a second tenure-change block for the same tenure by checking `signer_db.get_last_globally_accepted_block(&block.header.consensus_hash)`. Because this lookup only returns a block once it has reached global acceptance, a block the signer has already locally signed (state `Accepted`, not yet `GloballyAccepted`) is invisible to this check, leaving a window in which a second, conflicting tenure-change block for the same `consensus_hash` passes the dedup check and can be validated/signed.

### Finding Description
The uniqueness property the dedup check is supposed to enforce is: *a signer must sign at most one block per (tenure, height)*. In `validate_tenure_change_payload`: [1](#0-0) 

the duplicate check queries `get_last_globally_accepted_block(&block.header.consensus_hash)`. This function only returns a record once the block has crossed the global-acceptance threshold recorded in `signerdb.rs`; a block this same signer already locally signed and persisted with state `Accepted` (not yet `GloballyAccepted`) does not satisfy that predicate and is not returned. Consequently, `last_in_current_tenure` is `None`, no `RejectReason::DuplicateBlockFound` is raised, and the function proceeds to the remaining checks (parent tenure match, parent-tenure-choice validity) and returns `Ok(())`, permitting the signer's caller to sign a second, distinct tenure-change block for the exact same `consensus_hash`.

An attacker who wins a single miner slot can trigger this by gossiping two distinct `BlockProposal`s for the same tenure-start consensus hash in quick succession (e.g., two forked tenure-change payloads, or a proposal and a rebroadcast with a different tie-breaking transaction), before the first one accumulates enough signer weight to reach `GloballyAccepted`. Any individual signer that has locally accepted proposal A but has not yet observed global acceptance of A will not block proposal B from passing `validate_tenure_change_payload`, and can sign B as well.

Root cause: the check consults a *global* state predicate to guard against a purely *local* signing action (this signer's own commitment), rather than checking whatever function reflects the signer's own last signed block for that tenure (i.e., the equivalent of `get_last_signed_block` used by v2's parallel logic).

### Impact Explanation
This breaks the uniqueness/chain-safety guarantee that a signer never signs two conflicting blocks at the same tenure-start height. If enough signers hit this same race independently (each locally signing block A, then also signing conflicting block B before global acceptance propagates), the aggregated signatures could support two conflicting tenure-change blocks, a direct chain-safety violation. This matches the "Critical" category: signer signing a conflicting block.

### Likelihood Explanation
Preconditions are narrow but attacker-achievable with only one miner slot: the attacker must get two distinct tenure-change block proposals for the same tenure into gossip/StackerDB before the first is globally accepted by the signer set. Because global acceptance requires network propagation and aggregation across signers, there is a natural window (network latency, threshold aggregation time) during which a single signer's local acceptance of block A is not yet globally reflected. The attack needs only crafting BlockProposals and gossiping them — within the stated unprivileged threat model (one miner slot + gossip) — and is repeatable every tenure-change opportunity the attacker wins.

### Recommendation
Change the dedup check in `validate_tenure_change_payload` (v1.rs) to use the signer's own last-signed-block record for the consensus hash (an equivalent of v2's `get_last_signed_block`) instead of `get_last_globally_accepted_block`, so that any block this signer has already locally signed (regardless of global-acceptance status) blocks a second conflicting proposal for the same tenure.

### Proof of Concept
Rust test in `stacks-signer/src/chainstate/tests/v1.rs` (parallel to existing v2 tests):
1. Build a `SignerDb` and insert a `BlockInfo` for consensus_hash `CH` with `state = BlockState::Accepted` (locally signed only, not globally accepted) via `signer_db.insert_block`.
2. Construct a second, distinct `NakamotoBlock` with the same `consensus_hash = CH` and a valid `TenureChangePayload` referencing the same parent tenure.
3. Call `SortitionsView::validate_tenure_change_payload` (or `check_proposal`) with this second block.
4. Assert the call returns `Ok(())` (bug) instead of `Err(RejectReason::DuplicateBlockFound)` (expected safe behavior), demonstrating that a locally-Accepted-but-not-globally-accepted first block fails to block a conflicting second block from passing validation.
