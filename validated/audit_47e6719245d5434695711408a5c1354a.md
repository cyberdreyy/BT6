### Title
`isTransferProcessed` Nonce Key Missing Source-Chain Domain Separation Enables Permanent Fund Lock — (File: `bridge/evm/contracts/SuiBridge.sol`)

### Summary
The `isTransferProcessed` replay-guard in `SuiBridge.sol` is keyed only by `message.nonce` (`uint64`), not by `(message.chainID, message.nonce)`. Simultaneously, `MessageVerifier.verifyMessageAndSignatures` explicitly skips the chain-ID domain check for `TOKEN_TRANSFER` messages. When the bridge is configured with more than one source chain — which `BridgeConfig` permits — nonces from different source chains collide in the single-dimensional map, permanently locking the funds of any user whose transfer nonce was already consumed by a transfer from a different source chain.

### Finding Description

**Root cause 1 — chain-ID check skipped for TOKEN_TRANSFER in `MessageVerifier`**

`MessageVerifier.verifyMessageAndSignatures` enforces `message.chainID == committee.config().chainID()` only for governance message types. For `TOKEN_TRANSFER` the entire block is bypassed:

```solidity
if (messageType != BridgeUtils.TOKEN_TRANSFER) {
    // verify chain ID
    require(
        message.chainID == committee.config().chainID(), "MessageVerifier: Invalid chain ID"
    );
    require(message.nonce == nonces[message.messageType], "MessageVerifier: Invalid nonce");
    nonces[message.messageType]++;
}
``` [1](#0-0) 

For `TOKEN_TRANSFER`, `message.chainID` carries the **source** chain identifier. The modifier intentionally skips the chain-ID equality check because the target-chain check is deferred to the function body. However, this means no per-source-chain domain separation is enforced at the modifier level.

**Root cause 2 — `isTransferProcessed` keyed by nonce alone**

The replay guard in `SuiBridge` is a flat mapping over `uint64`:

```solidity
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;
``` [2](#0-1) 

Both `transferBridgedTokensWithSignatures` (V1) and `transferBridgedTokensWithSignaturesV2` (V2) read and write this same map using only `message.nonce` as the key:

```solidity
require(!isTransferProcessed[message.nonce], "SuiBridge: Message already processed");
...
isTransferProcessed[message.nonce] = true;
``` [3](#0-2) 

The nonce is a per-source-chain sequence number. Two independent source chains each maintain their own counter starting at 0. When both are supported by the same bridge deployment, their nonces are numerically identical at every step.

**Root cause 3 — `BridgeConfig` supports multiple source chains**

`BridgeConfig.initialize` accepts an array of supported chain IDs and marks each one as valid:

```solidity
for (uint8 i; i < _supportedChains.length; i++) {
    require(_supportedChains[i] != _chainID, "BridgeConfig: Cannot support self");
    supportedChains[_supportedChains[i]] = true;
}
``` [4](#0-3) 

The `onlySupportedChain` modifier only checks membership in this set — it does not restrict the bridge to a single source chain:

```solidity
modifier onlySupportedChain(uint8 targetChainID) {
    require(
        committee.config().isChainSupported(targetChainID),
        "SuiBridge: Target chain not supported"
    );
    _;
}
``` [5](#0-4) 

### Impact Explanation

When two source chains (e.g., Sui Mainnet `chainID=0` and Sui Testnet `chainID=1`) are both listed as supported, their per-chain nonce counters are independent but share the same `isTransferProcessed` key space. The first transfer from either chain at nonce `N` sets `isTransferProcessed[N] = true`. Any subsequent transfer from the **other** source chain at nonce `N` — carrying a valid committee quorum signature and a correct target-chain payload — is permanently rejected with `"SuiBridge: Message already processed"`. The user's tokens are burned or locked on the source chain with no recourse: the bridge record is consumed, the nonce can never be reused, and the target-chain claim is permanently blocked. This constitutes **permanent fund lock**, a High-impact class under the bounty criteria.

### Likelihood Explanation

The vulnerability is latent in the production code. It activates the moment governance adds a second source chain to an existing bridge deployment — a legitimate operational action (e.g., adding Sui Testnet support to a shared committee bridge, or onboarding a new Sui-compatible network). Once that configuration is live, the collision occurs naturally and deterministically as both chains process transfers: nonce 0 from chain A collides with nonce 0 from chain B, nonce 1 with nonce 1, and so on. No adversarial input is required beyond the governance configuration step; ordinary users trigger the lock simply by bridging.

### Recommendation

Key `isTransferProcessed` by `(sourceChainID, nonce)` instead of `nonce` alone:

```solidity
// Before
mapping(uint64 nonce => bool isProcessed) public isTransferProcessed;

// After
mapping(uint8 sourceChainID => mapping(uint64 nonce => bool isProcessed))
    public isTransferProcessed;
```

Update every read and write site in `SuiBridge.sol` and `SuiBridgeV2.sol`:

```solidity
require(!isTransferProcessed[message.chainID][message.nonce], "SuiBridge: Message already processed");
...
isTransferProcessed[message.chainID][message.nonce] = true;
```

Additionally, restore the explicit source-chain domain check inside `verifyMessageAndSignatures` for `TOKEN_TRANSFER` (verifying `message.chainID` is in the expected source-chain set, not just any supported chain), mirroring the chain-ID guard already present for governance messages. [1](#0-0) 

### Proof of Concept

1. Deploy `BridgeConfig` with `_supportedChains = [0, 1]` (Sui Mainnet and Sui Testnet both supported as source chains for the same Ethereum bridge).
2. User A deposits tokens on Sui Mainnet; the bridge node collects quorum signatures and calls `transferBridgedTokensWithSignatures` with `message.chainID = 0`, `message.nonce = 5`. The call succeeds; `isTransferProcessed[5] = true`.
3. User B deposits tokens on Sui Testnet; the bridge node collects quorum signatures and calls `transferBridgedTokensWithSignatures` with `message.chainID = 1`, `message.nonce = 5` (Sui Testnet has also processed 5 prior transfers). The call reverts: `"SuiBridge: Message already processed"`.
4. User B's tokens are permanently locked: burned on Sui Testnet, unclaimable on Ethereum. The nonce `5` on Sui Testnet can never be reused, and `isTransferProcessed[5]` is already consumed by chain 0's transfer.
