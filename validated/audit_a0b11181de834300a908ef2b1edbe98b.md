### Title
Stale per-epoch instant-withdraw entries enable a post-default double claim - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary

The external bug is an invalidation routine (`flush_tlb_range`) that clears leaf-level entries but skips intermediate-level entries, leaving stale state that later paths still honor. The direct analog lives in `IdleCreditVault.claimInstantWithdrawRequest`: a successful claim clears only the aggregate `instantWithdrawsRequests[_user]` (the "leaf" receipt), but never clears `instantWithdrawsRequestsByEpoch[_user][epoch]` or `instantWithdrawClaimsByEpoch[epoch]` (the "mid-level" per-epoch bookkeeping). When the same epoch later defaults and `defaultRecoveryFinalized` is set, `_claimDefaultedInstantWithdrawRequest` reads those stale per-epoch entries and pays the user a second time out of the isolated `defaultRecoveryReserve`, stealing recovery funds owed to genuinely defaulted claimants. [1](#0-0) [2](#0-1) 

### Finding Description

`requestInstantWithdraw` records three pieces of state for each request: the aggregate `instantWithdrawsRequests[_user]`, the per-user per-epoch `instantWithdrawsRequestsByEpoch[_user][currentEpoch]`, and the per-epoch total `instantWithdrawClaimsByEpoch[currentEpoch]`. [3](#0-2) 

In `claimInstantWithdrawRequest`, the normal funded path burns and zeroes only the aggregate:

```solidity
uint256 amount = instantWithdrawsRequests[_user];
_burn(_user, amount);
instantWithdrawsRequests[_user] = 0;
_transferFundedClaim(_user, amount);
```

`instantWithdrawsRequestsByEpoch[_user][*]` and `instantWithdrawClaimsByEpoch[*]` are left untouched — exactly like the x86 `flush_tlb_range` skipping non-leaf invalidations. The only place the per-epoch entries are cleared is `_claimDefaultedInstantWithdrawRequest`, which runs at the top of `claimInstantWithdrawRequest` when `defaultRecoveryFinalized && defaultInstantWithdrawsFinalized`. It uses `instantWithdrawsRequestsByEpoch[_user][defaultRecoveryEpoch]` as the claim basis and pays `(claimBasis * defaultRecoveryPrice) / 1e18` from `defaultRecoveryReserve` via `_transferDefaultRecovery`, which decrements the shared reserve. [2](#0-1) [4](#0-3) 

Sequence (all attacker steps are unprivileged; manager/owner calls are honest sequencing):

1. Epoch N running. Attacker calls `requestWithdraw` on `IdleCDOEpochVariant` while APR dropped, triggering `requestInstantWithdraw` — receipt of amount A minted, `instantWithdrawsRequestsByEpoch[attacker][N] += A`, `instantWithdrawClaimsByEpoch[N] += A`. [5](#0-4) 
2. Manager calls `getInstantWithdrawFunds`; `collectInstantWithdrawFunds` funds the receipts and `allowInstantWithdraw` is enabled. [6](#0-5) 
3. Attacker calls `claimInstantWithdrawRequest`, receives A at par. Aggregate zeroed; `instantWithdrawsRequestsByEpoch[attacker][N]` and `instantWithdrawClaimsByEpoch[N]` remain = A (stale entries survive the "flush"). [1](#0-0) 
4. Epoch N's `stopEpoch` fails to pull funds → `_handleBorrowerDefault`; default recovery is finalized for epoch N (`defaultRecoveryEpoch == N`). The stale `instantWithdrawClaimsByEpoch[N]` is included in the unfunded/prefunded instant-receipt accounting (the code explicitly tolerates prefunded remainder via `pendingInstantWithdraws` clamping). [7](#0-6) 
5. Attacker calls `claimInstantWithdrawRequest` again. `_claimDefaultedInstantWithdrawRequest` reads the stale `instantWithdrawsRequestsByEpoch[attacker][N] = A`, pays `A * defaultRecoveryPrice` out of `defaultRecoveryReserve` — a second payout for a receipt already settled at par. [8](#0-7) 

Note `_burn(_user, claimBasis)` inside the defaulted path would normally catch a double claim because the receipt tokens were already burned — but `_burn` of a zero balance reverts in standard ERC20... unless the attacker splits the position: request instant withdraws from two addresses, or re-request after claiming. Critically, `requestWithdraw` post-default is blocked while `instantWithdrawsRequests[_user] != 0`, but nothing blocks simply holding new minted receipts: the attacker can make a *second* instant request (amount B) before claiming the first — wait, cleaner variant: attacker makes request A, lets it be funded, claims it (aggregate → 0, per-epoch stale A). Before default finalization the attacker makes a new request B in the same epoch, receiving receipt tokens B. After default, `_claimDefaultedInstantWithdrawRequest` computes `claimBasis = A + B` (per-epoch map accumulated both), burns only B, and pays out `(A+B) * recoveryPrice` — claimBasis exceeds burnAmount, so the burn succeeds and the payout includes A again. [9](#0-8) 

### Impact Explanation

Direct theft of the isolated default-recovery reserve: every wei of the stale basis `A` is paid a second time at `defaultRecoveryPrice`, shrinking `defaultRecoveryReserve` available to honest defaulted-epoch claimants (`_transferDefaultRecovery` decrements the shared reserve and reverts for later claimants once drained). Broken invariant: one receipt, one payout. Loss is quantified as `staleBasis * defaultRecoveryPrice`, bounded by the attacker's instant-withdraw size, which is unbounded by capital cost beyond KYC and deposit. [4](#0-3) 

### Likelihood Explanation

Requires a borrower default in the same epoch where the attacker held a funded-then-claimed instant receipt, plus recovery finalization (`defaultInstantWithdrawsFinalized`). Defaults are an explicitly modeled flow (`_handleBorrowerDefault`, `finalizeDefaultRecovery`), and instant withdraws are a designed, manager-funded feature. The attacker controls request timing and size; no privileged misbehavior is needed. The missing cleanup is unconditional — every successful instant claim leaves the stale per-epoch entries. One residual uncertainty: whether `defaultRecoveryEpoch` equals the request-epoch key used in `instantWithdrawsRequestsByEpoch` (i.e., whether `epochNumber` increments before or after the default is recorded). If recovery epochs are keyed post-increment, the stale-entry window narrows to receipts requested in the post-increment epoch, but the missing-clear defect itself is confirmed in the code.

### Recommendation

In `claimInstantWithdrawRequest`, clear the per-epoch structures alongside the aggregate: delete `instantWithdrawsRequestsByEpoch[_user][epoch]` for each epoch contributing to the claim (or track the open request epoch like `lastWithdrawRequest` for normal requests) and decrement `instantWithdrawClaimsByEpoch[epoch]` by the claimed amount. Alternatively, compute the default claim basis as `min(perEpochEntry, instantWithdrawsRequests[_user])` so already-claimed receipts cannot re-enter recovery accounting.

```text
  function _claimDefaultedInstantWithdrawRequest(address _user) internal returns (uint256 claimBasis) {
    uint256 defaultEpoch = defaultRecoveryEpoch;
    claimBasis = instantWithdrawsRequestsByEpoch[_user][defaultEpoch];
    if (claimBasis == 0) return claimBasis;

    instantWithdrawsRequestsByEpoch[_user][defaultEpoch] = 0;
    instantWithdrawsRequests[_user] -= claimBasis;
    uint256 pending = pendingInstantWithdraws;
    // `pendingInstantWithdraws` is only the unfunded remainder. If this user's claim is larger,
    // the extra amount was already counted as prefunded reserve during default finalization.
    pendingInstantWithdraws = claimBasis >= pending ? 0 : pending - claimBasis;
    instantWithdrawClaimsByEpoch[defaultEpoch] -= claimBasis;
    _burn(_user, claimBasis);
    _transferDefaultRecovery(_user, (claimBasis * defaultRecoveryPrice) / RECOVERY_FULL);
  }
```
