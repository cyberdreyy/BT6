### Title
Unauthenticated MessageId flooding can evict legitimate users' pending callbacks before DON response arrives - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` inserts a `savedCallback` into the shared `savedCallbacks` map keyed by attacker-controlled `msg.Body.MessageId` for every incoming gateway HTTP request, with no authentication, allowlist, or per-user rate limiting applied before insertion (the `TODO: apply allowlist and rate-limiting here` comment confirms this is unimplemented). Since `ProcessRequest` in `gateway.go` reaches `HandleLegacyUserMessage` for any request that decodes/validates as a legacy message with a valid DON ID, an unauthenticated attacker can submit many distinct-`MessageId` requests to inflate `savedCallbacks` past `MaxSavedCallbacks`, causing `pruneCallbacks` to evict the oldest half of entries by `createdAt` regardless of which requester/user they belong to.

### Finding Description
- `HandleLegacyUserMessage` (core/services/gateway/handlers/capabilities/handler.go:341-421) validates payload structure/timestamp/method but performs no per-caller authentication, allowlisting, or rate limiting (explicit TODO at line 384) before storing the callback: [1](#0-0) , [2](#0-1) .
- The only checks are message parseability, non-zero timestamp, staleness window (`MaxAllowedMessageAgeSec`), method matching `MethodWebAPITrigger`, and message-level signature/HMAC validation performed generically in `common.ValidatedRequestFromMessage`. None of these limit the *number* of distinct MessageIds a single caller (or many callers/IPs) can submit within the prune interval.
- `gateway.ProcessRequest` (core/services/gateway/gateway.go:218-292) reaches this handler for any externally submitted legacy request that decodes and passes `msg.Validate()`, requiring only a syntactically valid signed/authenticated JSON-RPC envelope for a known DON ID — this is the standard "unauthenticated client of the gateway" path described in the threat model (no operator/admin privilege required), matching the "restricted API token / signed gateway requests" attacker class.
- `pruneCallbacks` (core/services/gateway/handlers/capabilities/handler.go:299-339) runs only every `CallbackPruneIntervalSec` (default 30s) and, when `len(savedCallbacks) > MaxSavedCallbacks` (default 20000), sorts all entries by `createdAt` and deletes the older half (`entries[:len(entries)-maxSize/2]`) with **no consideration of which requester owns the entry** — eviction is purely time-order-based: [3](#0-2) .
- If an attacker submits >`MaxSavedCallbacks` distinct-`MessageId` legacy trigger requests within one prune interval (or repeatedly across intervals to keep pushing legitimate older entries out), a legitimate user's callback registered earlier will be deleted from `savedCallbacks` before the DON's `handleWebAPITriggerMessage` response arrives and looks it up by `MessageId` (handler.go:148-162). Once evicted, the legitimate response lookup at line 150 (`found=false`) silently drops the DON's response, and the legitimate user's original `callback.Wait(ctx)` in `gateway.go:278` times out (`api.RequestTimeoutError`) — a denial of service against that specific in-flight request.
- This is a "no reachable, unmitigated path" checks failure: rate limiting only exists as a node-side `nodeRateLimiter` applied in `handleWebAPIOutgoingMessage` (line 166) for DON→gateway outgoing messages, not for the user-facing `HandleLegacyUserMessage` ingress path.

### Impact Explanation
This is a resource-exhaustion/availability issue at the individual-request level (isolation/availability violation for a legitimate run/edit-role user's in-flight web API trigger callback), not a fund-movement or credential-disclosure bug. Impact is bounded to denial of callback delivery/timeout for legitimate concurrent requests during an attack window; it does not grant privilege escalation, secret exposure, or cross-user data leakage — the attacker cannot read or redirect another user's response, only cause it to be dropped/time out. This aligns with a low/medium "Denial of Service" bounty class rather than a critical impact class.

### Likelihood Explanation
Feasibility requires only the ability to send well-formed (validly signed/HMAC'd per whatever the DON's gateway auth scheme requires) legacy JSON-RPC requests with `web_api_trigger` method and unique `MessageId`s to a known DON ID — the same capability any legitimate node/user client already has to invoke `HandleLegacyUserMessage` legitimately, since `msg.Validate()`/signature checks in `common.ValidatedRequestFromMessage` do not prevent an attacker from using their own valid credentials with many distinct MessageIds. Reaching `MaxSavedCallbacks` (default 20000) within a 30s prune interval requires substantial request throughput but is not otherwise access-controlled or rate-limited per-caller at this ingress point, making it feasible for a moderately resourced attacker and fully repeatable.

### Recommendation
Implement the still-outstanding TODO at handler.go:384: apply per-caller allowlisting and rate limiting (e.g., extend `nodeRateLimiter`-style limiting keyed by sender/API token/IP) before inserting into `savedCallbacks`. Additionally, consider bounding `savedCallbacks` growth per-sender (quota) rather than relying purely on global `MaxSavedCallbacks`/age-based eviction, so a single attacker cannot starve capacity intended for other legitimate senders.

### Proof of Concept
Go handler-level test plan for `core/services/gateway/handlers/capabilities/handler_test.go`:
1. Construct a `handler` with small `MaxSavedCallbacks` (e.g., 10) and `CallbackPruneIntervalSec` large enough to not fire automatically; call `pruneCallbacks()` manually.
2. Register N/2 "legitimate" callbacks by calling `HandleLegacyUserMessage` (or directly populating `savedCallbacks`) with `createdAt` timestamps earlier in time, using distinct valid `MessageId`s, and attach mock `handlers.Callback` implementations that assert `SendResponse` is eventually called.
3. Simulate attacker flood: insert N (attacker-crafted) entries with distinct `MessageId`s and later `createdAt` timestamps, exceeding `MaxSavedCallbacks`.
4. Call `h.pruneCallbacks()` directly.
5. Assert: the legitimate (earlier `createdAt`) entries are deleted from `h.savedCallbacks` (i.e., `evicted` count includes them), regardless of requester identity.
6. Follow-up: for one evicted legitimate `MessageId`, simulate the DON's delayed response via `handleWebAPITriggerMessage` and assert `found == false` (savedCb absent), i.e., the legitimate user's response is silently dropped/never delivered — reproducing the availability violation end-to-end.

	// If there are still too many callbacks, sort them by creation time and remove the oldest ones.
	maxSize := h.config.MaxSavedCallbacks
	var evicted int
	if len(h.savedCallbacks) > maxSize {
		type entry struct {
			id        string
			createdAt time.Time
		}
		entries := make([]entry, 0, len(h.savedCallbacks))
		for id, cb := range h.savedCallbacks {
			entries = append(entries, entry{id, cb.createdAt})
		}
		sort.Slice(entries, func(i, j int) bool {
			return entries[i].createdAt.Before(entries[j].createdAt)
		})
		// Trim to maxSize/2 to avoid sorting the list too frequently.
		for _, e := range entries[:len(entries)-maxSize/2] {
			delete(h.savedCallbacks, e.id)
			evicted++
		}
	}
