## Analog Found

### Title
Permissionless, unbatched `KeeperCloseOrder` claims can be front-run, causing a keeper bot's batched cleanup transaction to fail entirely while the attacker steals the rent — (`File: programs/marginfi/src/instructions/marginfi_account/order.rs`)

### Summary
`marginfi_account_keeper_close_order` is a fully permissionless instruction that lets *any* signer close a stale `Order` account and self-assign the returned rent to an arbitrary `fee_recipient` of their choosing. [1](#0-0)  Because Solana transactions are atomic (unlike the PoolTogether/EVM case where a failed sub-call in a loop can be swallowed), a keeper bot that bundles several `KeeperCloseOrder` instructions into one transaction to amortize fees across many small rent claims is exposed to the exact PoolTogether `claimPrizes` front-run pattern: an attacker who observes the pending batch can race to close just one of the target `Order` accounts first (paying themselves the rent), which makes that specific `Order` account already-closed/reinitialized by the time the honest bot's transaction lands — causing account deserialization on that instruction to fail and the *entire* atomic transaction (and every other legitimate close bundled with it) to revert.

### Finding Description
`KeeperCloseOrder` accepts an `UncheckedAccount` for `fee_recipient` with the explicit comment "no checks whatsoever, keeper decides this without restriction," and closes the `order` account (`close = fee_recipient`) after verifying only that the order's tagged balances are no longer active or that the user cleared keeper-close flags. [1](#0-0)  The handler logic performs `has_one = marginfi_account` and eligibility checks (`can_close`) before closing and paying out rent. [2](#0-1) 

The documentation confirms bots ("Keepers") are expected to run this permissionlessly and are economically incentivized by "whatever is leftover... as profit" plus "the rent from the Order (currently worth about $0.25)" — i.e., a small per-item incentive that only becomes worth the fixed Solana transaction-fee overhead when many stale orders are closed together in a single batched transaction. [3](#0-2)  The p0-cli tooling explicitly supports keeper batch operations of this kind (`keeper-close-order`, `execute-order-keeper`). [4](#0-3) 

Because `Order` accounts are cheap, permissionlessly derivable PDAs and `fee_recipient` is unchecked, any third party can call `keeper_close_order` on the exact same `order` PDA the bot intends to close, closing it first and keeping the rent for themselves. When this happens against one instruction inside a bot's multi-order batched transaction, Solana's all-or-nothing transaction semantics mean the *whole* transaction fails — not just the front-run leg — because Anchor's account deserialization for the now-closed/re-owned `Order` account will error out before the handler even executes. This directly mirrors the referenced PoolTogether root cause: a malicious actor front-runs one item of a batch a bot economically depends on batching, causing the bot's transaction to fail and its gas/fees to be wasted, while the attacker walks away with the value (rent) that would have gone to the batch.

### Impact Explanation
- The keeper bot loses the Solana transaction fee (and any priority fee) for the entire batched transaction, not just the contested order — a direct, repeatable financial loss to unprivileged actors running this permissionless maintenance operation.
- The attacker captures the ~$0.25 rent value for the front-run order, redirecting value away from the legitimate keeper.
- At scale, an attacker (or a keeper competing for the same cleanup fees) can systematically front-run every batch a rival bot submits, since `Order` PDAs and their close-eligibility are all publicly observable on-chain, degrading the reliability of the permissionless keeper ecosystem the protocol relies on for order housekeeping (similar to how PoolTogether's bot-incentive design was undermined). This is bounded in magnitude (rent-sized, no protocol insolvency), consistent with the "Low/Medium" severity ultimately assigned to the original finding.

### Likelihood Explanation
Any signer can call `keeper_close_order` with zero authorization checks on `fee_recipient`, and eligible `Order` accounts (and their derivable PDAs) are fully observable on-chain/in the mempool. [2](#0-1)  Given the documented economic incentive to batch several closes per transaction to make the ~$0.25 rent worthwhile relative to fees, and given Solana's atomic transaction execution, this is straightforward and low-cost to execute for any party monitoring pending keeper transactions or independently scanning for closeable orders.

### Recommendation
- Make each `KeeperCloseOrder` instruction fault-tolerant to already-closed/ineligible order accounts (e.g., accept the order account as `UncheckedAccount` and manually check discriminator/ownership before attempting the close, returning `Ok(())` early with an event if the order is already closed) instead of relying on Anchor's `AccountLoader`/`has_one` constraints to hard-fail the whole instruction.
- Consider a batched/atomic-per-item variant (loop over `remaining_accounts` in a single instruction, à la `sync_indexer_flags`) so that one stale/contested order does not abort unrelated closes bundled in the same transaction.
- Optionally allow the bot to specify an expected `fee_recipient`/order state and simply no-op (rather than error) if state has changed since simulation.

### Proof of Concept
1. Keeper bot simulates and finds N stale `Order` accounts eligible for `keeper_close_order`, and submits a single transaction with N `KeeperCloseOrder` instructions (one per order), self-assigning `fee_recipient` to collect all N rents in one shot to offset the transaction fee.
2. An attacker observing the pending transaction (via RPC polling, Jito bundle simulation, or independent scanning of eligible orders) submits their own `KeeperCloseOrder` for just one of the N target orders, naming themselves as `fee_recipient`, and lands it first.
3. The bot's original transaction now references an `order` account that is closed / no longer owned by the program for that one instruction; Anchor's account validation for that leg fails.
4. Because Solana transactions execute atomically, the bot's entire N-order transaction reverts — the bot pays the transaction fee for nothing and collects zero rent, while the attacker collects the rent for the one order they front-ran. [1](#0-0)

pub fn keeper_close_order(ctx: Context<KeeperCloseOrder>) -> MarginfiResult {
    let KeeperCloseOrder {
        order: order_loader,
        marginfi_account,
        ..
    } = &ctx.accounts;

    let order = order_loader.load()?;
    let marginfi_account_info = marginfi_account.to_account_info();

    // Manual owner check: Only attempt to deserialize when the account is not closed
    let (authority_pk, group_pk, can_close) = if marginfi_account_info.owner.eq(&system_program::ID)
        && marginfi_account_info.data_is_empty()
    {
        (Pubkey::default(), Pubkey::default(), true)
    } else {
        // Deserialize manually using bytemuck to avoid lifetime issues
        let mut data = marginfi_account_info.try_borrow_mut_data()?;

        // Check discriminator
        require!(
            data.len() >= 8 + std::mem::size_of::<MarginfiAccount>(),
            MarginfiError::InternalLogicError
        );

        let disc = &data[..8];
        check_eq!(
            disc,
            MarginfiAccount::DISCRIMINATOR,
            MarginfiError::InternalLogicError
        );

        let marginfi_account: &mut MarginfiAccount =
            bytemuck::from_bytes_mut(&mut data[8..8 + std::mem::size_of::<MarginfiAccount>()]);

        let balances = &marginfi_account.lending_account.balances;
        // Can close if any of the balances used in the order no longer exists (or if its tag was cleared)
        let can_close = order.tags.iter().any(|tag| {
            !balances
                .iter()
                .any(|balance| balance.is_active() && balance.tag == *tag)
        });
        if can_close {
            marginfi_account.decrement_active_orders()?;
        }
        (
            marginfi_account.authority,
            marginfi_account.group,
            can_close,
        )
    };

    check!(can_close, MarginfiError::LiquidatorOrderCloseNotAllowed);

    emit!(KeeperCloseOrderEvent {
        header: AccountEventHeader {
            signer: None,
            marginfi_account: marginfi_account_info.key(),
            marginfi_account_authority: authority_pk,
            marginfi_group: group_pk,
        },
        order: order_loader.key(),
    });

    Ok(())
}

#[derive(Accounts)]
pub struct KeeperCloseOrder<'info> {
    /// CHECK: This uses an unchecked account here so the instruction can be called even when the
    /// marginfi account was closed.
    /// The ownership check is checked in the handler or/and type checks are made in the handler.
    #[account(mut)]
    pub marginfi_account: UncheckedAccount<'info>,

    /// CHECK: no checks whatsoever, keeper decides this without restriction
    #[account(mut)]
    pub fee_recipient: UncheckedAccount<'info>,

    #[account(
        mut,
        has_one = marginfi_account,
        close = fee_recipient
    )]
    pub order: AccountLoader<'info, Order>,
}
