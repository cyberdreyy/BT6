### Title
`path.Join` in `kv_v2.engine.dataPath`/`metadataPath` does not prevent `secret.Path` from traversing outside the configured engine mount - ([File: helpers/vault/secret_engines/kv_v2/engine.go])

### Summary
`engine.dataPath` and `engine.metadataPath` build the Vault request path with `path.Join(e.path, "data"/"metadata", p)`, and `path.Join` internally calls `path.Clean`, which lexically resolves `..` segments rather than rejecting them. A `p` (i.e. `secret.Path`) containing enough `../` segments collapses the configured mount prefix (`e.path`) entirely, producing a path rooted at a sibling Vault mount.

### Finding Description
`engine.dataPath` and `engine.metadataPath` are defined as: [1](#0-0) [2](#0-1) 

`path.Join` performs a purely lexical `Clean`, with no filesystem/mount awareness and no check that the result remains a descendant of `e.path`. For example, with `e.path = "secret"` and `p = "../../other-mount/data/secretname"`, `path.Join("secret", "data", p)` cleans to `"other-mount/data/secretname"` - the `secret` mount prefix is fully consumed by the two leading `..` segments, and the crafted suffix reproduces the exact KV-v2 data-read path shape (`<mount>/data/<path>`) for an entirely different mount. The same applies to `metadataPath` for `Delete`.

This value flows unmodified from job configuration through `engine.Get`/`Delete` → `client.Read`/`client.Delete` (`helpers/vault/client.go`, `Read`/`Delete` just forward the path string to the OpenBao SDK's `Logical().Read/Delete`): [3](#0-2) 

The call chain is `resolver.Resolve` (`helpers/secrets/resolvers/vault/resolver.go`) → `service.GetField` (`helpers/vault/service/vault.go:97-106`, which calls `engine.Get(secretDetails.SecretPath())`) → `kv_v2.engine.Get`/`Delete`. No component in this chain canonicalizes or allow-lists `secret.Path`/`secret.Field`, and `VaultSecret.Path` is subject to CI variable expansion before being used: [4](#0-3) 

Because `s.Path = vars.ExpandValue(s.Path)` interpolates job/pipeline variables into the templated Vault path, any `.gitlab-ci.yml` pattern that builds the Vault secret path from a user-influenced CI/CD variable (e.g. a pipeline-trigger variable, merge-request variable, or other job input not restricted to a safe charset) allows an attacker to inject `../` sequences that are only resolved at `dataPath`/`metadataPath` construction time - after any config-time validation has already passed.

### Impact Explanation
If a `.gitlab-ci.yml` secrets definition builds its Vault path using an attacker-influenced variable, this allows unauthorized cross-mount secret reads via `Get`/`dataPath`, or deletion of another project's KV-v2 metadata (effectively deleting/destroying that secret's versions) via `Delete`/`metadataPath`, scoped exactly to the impact stated in the question.

### Likelihood Explanation
Exploitability strictly depends on the precondition (already assumed true for this question) that `secret.Path` is attacker-influenced without server-side canonicalization or allow-listing - e.g. via a Vault secrets path template that interpolates a pipeline-trigger/API-supplied CI variable that isn't restricted to a safe charset. Given that precondition, the traversal itself is deterministic and repeatable: `path.Join`/`path.Clean` will always collapse `../` segments the same way, so any crafted path with enough leading `..` reliably lands outside `e.path`.

### Recommendation
After computing `dataPath`/`metadataPath`, verify the cleaned result remains a strict descendant of `e.path` (e.g. `strings.HasPrefix(result, e.path+"/")` or compare path segments) and reject/error out otherwise, rather than trusting `path.Join`'s lexical cleaning alone. Additionally, reject `secret.Path`/`secret.Field` values containing `..` segments or leading `/` before they reach the engine.

### Proof of Concept
```go
func TestKvV2Engine_DataPath_DoesNotEscapeMount(t *testing.T) {
    e := &engine{path: "secret"}
    tests := []string{
        "../../other-mount/data/secretname",
        "..%2f..%2fother-mount/data/secretname", // if URL-decoded upstream
        "/../../other-mount/data/secretname",
    }
    for _, p := range tests {
        got := e.dataPath(p)
        assert.True(t, strings.HasPrefix(got, "secret/"),
            "dataPath(%q) = %q escaped mount prefix", p, got)
    }
}
```
Expected current behavior: the assertion fails for `"../../other-mount/data/secretname"`, since `dataPath` returns `"other-mount/data/secretname"`, proving the escape. A fuzz test (`func FuzzDataPath(f *testing.F)`) seeded with traversal payloads can be used to confirm the invariant never holds without the fix.
