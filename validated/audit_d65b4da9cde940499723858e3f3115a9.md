### Title
Miner-side `StackerDBListener` liveness wedge on unexpected slot_id in signer message chunk - ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
`StackerDBListener::run` returns a hard `Err(NakamotoNodeError::SignerSignatureError(...))` from its main event loop whenever it receives a signer message whose `slot_id` is not present in `self.signer_entries`. Because `self.signer_entries` is built once at listener construction from the reward-set signer list [1](#0-0) , any gossiped chunk on the `.signers-X-Y` StackerDB whose `slot_id` falls outside that map causes the entire listener loop to abort instead of just skipping the message.

### Finding Description
`try_from` on `StackerDBChunksEvent` accepts any chunk whose first byte parses to a valid `SignerMessageTypePrefix` for the given message lane and whose signature recovers to *some* public key — it does not check that the recovered public key/slot_id corresponds to a signer actually in the current reward set [2](#0-1) . The `slot_id` returned is simply `chunk.slot_id` from the StackerDB chunk metadata, which is determined by which physical slot in the `.signers-X-Y` replica the chunk was written to.

In `StackerDBListener::run`, once a `SignerEvent::SignerMessages` batch is obtained, each message is looked up by `slot_id` in `self.signer_entries`:

```
for (slot_id, _pk, message) in messages.into_iter() {
    let Some(signer_entry) = &self.signer_entries.get(&slot_id) else {
        return Err(NakamotoNodeError::SignerSignatureError(
            "Signer entry not found".into(),
        ));
    };
``` [3](#0-2) 

Unlike every other malformed/mismatched input path in this loop — deserialization failure, wrong contract, wrong signer_set, unknown pubkey — which are handled with `continue`/`debug!`/`warn!` (e.g. lines 335-361 and the `_pk` lookup done separately in `SignerCoordinator`), this one specific failure mode (`slot_id` present in the chunk set but absent from `signer_entries`) propagates as a hard `Err` out of the `run()` loop. That terminates the entire `StackerDBListener` thread for the remainder of the tenure.

Whether a slot_id outside the currently-tracked reward-set range can be populated depends on the StackerDB's slot layout for `.signers-X-Y`, which is derived from `stackerdb-get-signer-slots` in the boot contract and can, in principle, diverge from the miner's locally cached `signer_entries` (e.g., during a reward-cycle boundary, if the listener's snapshot of the reward set is stale relative to the live StackerDB replica config, or via replica misconfiguration/stale sync). Any slot present in the replica's chunk set but not represented in the miner's `signer_entries` map — reachable purely by writing (or having previously written) a valid-looking chunk to that slot — triggers the abort.

### Impact Explanation
This breaks the liveness guarantee of the mining-side signer aggregation: once `StackerDBListener::run()` returns `Err`, the loop that turns signer `BlockResponse`/`BlockPreCommit`/`StateMachineUpdate` gossip into approved-weight tracking (`self.blocks`, `total_weight_approved`, etc.) stops entirely. The miner then can never again learn about new signer acceptances/rejections for the rest of that listener's lifetime, effectively wedging the node into never being able to observe enough signer weight to approve/push a block — a High-severity liveness wedge per the stated impact categories ("a signer [node] wedged into never signing valid blocks ... or acting on stale ... state"). This is a direct structural analog of the mercurius bug class: an uncaught/unhandled error path on attacker-influenced/malformed input causing the service (here, the block-approval listener) to stop functioning, rather than gracefully rejecting the bad input.

### Likelihood Explanation
Reachable by a single StackerDB writer (a one-slot signer/gossip participant, consistent with in-scope threat model) writing a validly-signed, validly-typed chunk into a slot id that is not (or no longer) reflected in the miner's in-memory `signer_entries` snapshot — e.g., around a stale reward-set view, a slot reallocation, or a lingering stale slot from the outgoing signer set. No majority collusion or other signer's key is required; the only requirement is a validly-signed chunk from *some* known slot writer landing on a `slot_id` the miner's cached `signer_entries` doesn't recognize at that instant. All other analogous mismatch conditions in the exact same loop (unknown contract, wrong signer set, deserialization failure, pubkey parse failure a few lines below) are handled defensively with `continue`; only this one aborts the whole loop, which strongly suggests it is an oversight rather than an intentional fail-fast design, increasing confidence this is a real bug rather than benign behavior.

### Recommendation
Change the `Signer entry not found` branch in `StackerDBListener::run` (and the analogous "Failed to parse signer public key" branch just below it) from `return Err(...)` to `continue` (with a `warn!`/`debug!` log), matching the defensive handling used for every other malformed/unrecognized-signer condition in the same loop. This ensures a single unexpected or stale slot_id cannot take down the entire listener thread and its block-approval bookkeeping.

### Proof of Concept
1. A StackerDB writer with a valid slot on the `.signers-X-Y` contract (or a stale/reallocated slot no longer tracked in the miner's `signer_entries`) writes a well-formed `SignerMessage` (e.g. `BlockPreCommit`) to a `slot_id` value not present in `StackerDBListener::signer_entries`.
2. The chunk passes `SignerMessageTypePrefix` validation and signature recovery in `TryFrom<StackerDBChunksEvent>` [4](#0-3)  and is returned as part of `SignerEvent::SignerMessages`.
3. `StackerDBListener::run` iterates the message, fails the `signer_entries.get(&slot_id)` lookup, and returns `Err(NakamotoNodeError::SignerSignatureError(...))` [3](#0-2) , terminating the listener's event loop for the remainder of the tenure and preventing any further signer weight aggregation.
