## Summary

The Bold report's root cause is **floor-division truncation in a `pool_u64`-style share pool that resets to zero on each call**, letting an unprivileged actor split operations into many small increments to make the "commission owed" side of the math truncate to zero every time. The Aptos-native analog exists in `staking_contract::update_distribution_pool`, which recomputes operator commission from the *delta* of an unscaled `pool_u64::Pool` (scaling factor = 1) on every `add_distribution` call, with no minimum-operation-size guard. [1](#0-0) 

### Title
Staker can salami-slice `unlock_stake` calls to bypass operator commission via truncation in `update_distribution_pool` - (File: aptos-move/framework/aptos-framework/sources/staking_contract.move)

### Finding Description
`staking_contract`'s `distribution_pool` is created with `pool_u64::create` (deprecated alias of `new`), which defaults to `scaling_factor = 1` — i.e. no scaling to reduce rounding error, unlike `delegation_pool`'s active/inactive share pools which use `SHARES_SCALING_FACTOR`. [2](#0-1) [1](#0-0) 

Every time stake is unlocked or commission requested, `add_distribution` is invoked, which calls `update_distribution_pool` with the *current* total pending/inactive amount: [3](#0-2) 

`update_distribution_pool` computes, for every non-operator shareholder, the delta in their share's worth since the pool's last recorded total, and charges commission on that delta via floor division, then converts the resulting `unpaid_commission` back into shares (also floor division) to transfer from the shareholder to the operator: [4](#0-3) 

Because this computation is re-run from scratch on every call, and both divisions floor independently with **no minimum-size enforcement** on `unlock_stake`, a staker can trigger many separate small increments of `total_distribution_amount` (e.g. by repeatedly calling `unlock_stake` with `amount = 1` unit whenever fresh rewards have accrued): [5](#0-4) 

For each such tiny increment, `(current_worth - previous_worth) * commission_percentage / 100` rounds down to `0`, so `shares_to_transfer` is `0` and no commission shares are ever moved to the operator for that increment — even though the operator is entitled to `commission_percentage`% of every reward dollar under the contract. Unlike the Bold Trove batch, there is no accumulating "remainder" carried to the next call: each truncation is an independent loss to the operator, repeatable indefinitely at the cost of one transaction per increment.

This mirrors the Bold bug class exactly: (1) truncation-based share math re-derived from a live delta on each call, and (2) a cheap, permissionless, arbitrarily-repeatable action (`unlock_stake`) that an unprivileged party (the staker, who does not hold the operator/beneficiary role) can spam to bias the rounding permanently in their own favor, corrupting the commission share accounting that should credit the operator/beneficiary.

### Impact Explanation
This lets the staker withdraw stake and its rewards while systematically underpaying (approaching zero) the commission owed to the operator/beneficiary, i.e. **operator commission share-accounting corruption that traps value away from the rightful beneficiary**, which is explicitly in scope under "Operator commission, beneficiary payout, or share-accounting corruption that credits the wrong account or traps value." The magnitude of value at risk scales with total commission owed over the life of the contract and is bounded only by the number of transactions the staker is willing to pay for.

### Likelihood Explanation
The precondition (staker controls timing/size of their own `unlock_stake` calls, no minimum unlock amount enforced) is trivially met by any staker in a `staking_contract` with a nonzero `commission_percentage`. The only cost is gas for many small transactions; no special privilege or race condition is required. This is a moderate-likelihood, self-serve griefing/theft vector against operators of `staking_contract` pools — I was not able to fully quantify the practical extractable value (it depends on `AptosCoin` decimals, reward rate, and how many transactions the staker is willing to submit), which I flag as unresolved given the remaining tool budget.

### Recommendation
Follow the same mitigations proposed for Bold's Batch Shares: (1) use a nontrivial `scaling_factor` for `distribution_pool` (matching the pattern already used in `delegation_pool`'s share pools) to shrink truncation magnitude; (2) round commission calculations in the operator's favor (round up commission owed, round down staker's take) rather than always flooring both; (3) enforce a minimum unlock/distribution size in `unlock_stake`/`add_distribution`, analogous to `delegation_pool`'s `MIN_COINS_ON_SHARES_POOL`/`assert_min_active_balance` checks, to make salami-slicing economically impractical.

### Proof of Concept
Conceptual reproduction (not run against the framework's Move test harness due to no remaining tool calls):
1. Staker creates a `staking_contract` with `commission_percentage = 10` and some `principal`.
2. Let rewards accrue for one epoch so the underlying stake pool's active balance grows by `R` octas.
3. Instead of calling `unlock_stake(staker, operator, R)` once (which would floor `R/10` commission to the operator, an acceptable ~1-octa rounding loss), the staker calls `unlock_stake(staker, operator, 1)` repeatedly, `R` times, once per octa of accrued reward becoming visible in `stake::get_stake`.
4. On each call, `update_distribution_pool`'s `unpaid_commission = (current_worth - previous_worth) * 10 / 100` evaluates to `0` for a 1-octa delta, so `shares_to_transfer = 0` and the operator receives no commission share for that increment.
5. After `R` such calls, the staker has withdrawn the full `R` octas of rewards while the operator's commission distribution remains effectively at `0`, versus the `R/10` octas it would have received from a single bulk `unlock_stake(R)` call.

Because I could not execute this against the repo's Move test suite in this session, I could not empirically confirm the exact truncation bound across multiple epochs (e.g., whether `distribute_internal`'s periodic dust sweep to the staker at line 913-919 of `staking_contract.move` mitigates or exacerbates the loss). This should be validated with a Move unit test before treating the numeric impact as final. [6](#0-5)

    fun update_distribution_pool(
        distribution_pool: &mut Pool,
        updated_total_coins: u64,
        operator: address,
        commission_percentage: u64
    ) {
        // Short-circuit and do nothing if the pool's total value has not changed.
        if (distribution_pool.total_coins() == updated_total_coins) { return };

        // Charge all stakeholders (except for the operator themselves) commission on any rewards earnt relatively to the
        // previous value of the distribution pool.
        let shareholders = &distribution_pool.shareholders();
        shareholders.for_each_ref(
            |shareholder| {
                let shareholder: address = *shareholder;
                if (shareholder != operator) {
                    let shares = pool_u64::shares(distribution_pool, shareholder);
                    let previous_worth = pool_u64::balance(distribution_pool, shareholder);
                    let current_worth =
                        pool_u64::shares_to_amount_with_total_coins(
                            distribution_pool, shares, updated_total_coins
                        );
                    let unpaid_commission =
                        (current_worth - previous_worth) * commission_percentage / 100;
                    // Transfer shares from current shareholder to the operator as payment.
                    // The value of the shares should use the updated pool's total value.
                    let shares_to_transfer =
                        pool_u64::amount_to_shares_with_total_coins(
                            distribution_pool, unpaid_commission, updated_total_coins
                        );
