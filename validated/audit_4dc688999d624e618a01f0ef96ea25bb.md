## Finding

### Title
Instant, un-ramped fixed oracle price updates allow value extraction via sandwich around `lending_pool_set_fixed_oracle_price` - ([File: programs/marginfi/src/instructions/marginfi_group/set_fixed_oracle_price.rs])

### Summary
The referenced DODO/`MagicLP` finding (M-09) shows that instantaneously updating a price-determining parameter (`I`) via `setParameters()`, with no ramping, creates a profitable sandwich window for unprivileged bots at the expense of liquidity providers. marginfi has a directly analogous mechanism: `lending_pool_set_fixed_oracle_price` lets the group admin instantaneously overwrite `bank.config.fixed_price` for any bank using the `Fixed`/`FixedKamino`/`FixedDrift`/`FixedJuplend` oracle setup, in a single atomic instruction with no delay, ramp, or pause requirement.

### Finding Description
`lending_pool_set_fixed_oracle_price` directly sets `bank.config.fixed_price` to an arbitrary admin-supplied value in one instruction [1](#0-0) . This price is the sole valuation source used for every health/borrow-power/liquidation calculation on that bank once `OracleSetup::Fixed*` is active — there is no confidence interval, no staleness check, and, critically, no ramp/lerp mechanism analogous to the recommended mitigation in the referenced report (private RPC or slow ramping of a price-determining parameter).

Because the update is a normal, non-privileged-attack, single-slot state transition, any unprivileged party observing the pending transaction (or the transaction itself, since Solana leaders can reorder/insert transactions within a slot, and since this is a public, non-secret admin action many bots watch for) can position transactions immediately before and after the price jump: 
- Before a price increase: deposit the asset (or borrow against a correlated bank) while price is still low, then immediately after the bump, borrow/withdraw against the now-inflated collateral value.
- Before a price decrease: borrow the soon-to-be-cheapened asset at the old (high) valuation, then repay/close cheaply after the drop, or trigger favorable liquidations against other users whose health flips based on the sudden repricing.

The codebase's own test suite demonstrates the exact mechanic of an instant fixed-price jump being used to flip account health and trigger downstream actions (`limit_order_start_succeeds_after_fixed_price_shift`), confirming the state transition is a single atomic jump with immediate effect on liquidation/health outcomes [2](#0-1) . Likewise `update_fixed_bank_price` in the admin test suite confirms this is a straightforward, unguarded instant overwrite [3](#0-2) .

There is no cooldown, ramp, or pre-pause requirement enforced by the instruction itself — only `FREEZE_SETTINGS` (which if set, blocks the update entirely rather than ramping it) and a staked-asset restriction are checked [4](#0-3) . This mirrors the DODO `_I_` parameter update pattern precisely: a single-step, admin-triggered price parameter change with global, instantaneous effect on all dependent valuations.

### Impact Explanation
Since `fixed_price` feeds directly into collateral/liability valuation for health checks, borrow limits, and liquidation eligibility, an instant jump can be sandwiched by unprivileged bots to extract value that would otherwise accrue to liquidity providers/the protocol — e.g., extracting excess borrowing power right after a price increase, or realizing risk-free arbitrage/liquidation profit right after a price decrease. This directly parallels the accepted C4 finding's impact: LP losses funding MEV-bot profit due to unramped price parameter changes.

### Likelihood Explanation
Likelihood is moderate: this requires the fixed-price mechanism to be in active use for a bank (an admin operational choice, e.g. LSTs/vault wrappers without a live oracle) and requires bots monitoring for these transactions. It does not require any bug in oracle correctness or third-party price feeds (which are excluded per `SECURITY.md`), since `Fixed*` oracle types have no external oracle at all — the "price" is purely protocol-internal state, so this is not "incorrect data supplied by third-party oracles" and not excluded by the standard oracle-manipulation carve-out. The action is a normal, intended admin operation (not privileged-address abuse), and the actual attacker/beneficiary of the sandwich is an unprivileged third party, so this is not excluded by the "attacks requiring access to privileged addresses" clause either.

### Recommendation
Add a time-delay/ramp mechanism for `fixed_price` updates (e.g., linear interpolation over N slots/seconds similar to TWAP-style ramps), or require the bank to be paused (`operational_state = Paused`) while the price is updated and only re-enabled after the update settles, preventing same-slot/adjacent-slot sandwiching around the price jump.

### Proof of Concept
1. Admin calls `lending_pool_set_fixed_oracle_price` to raise `fixed_price` for `BankMint::X` from `P0` to `P1` (as in `update_fixed_bank_price` test) [5](#0-4) .
2. A bot deposits collateral into bank `X` in the same/adjacent slot, valued at `P0`.
3. Immediately after the price update lands, the bot borrows against the same collateral now valued at `P1`, extracting the price-delta as free borrowing power, then withdraws.
4. As shown in `limit_order_start_succeeds_after_fixed_price_shift`, a single `set_fixed_oracle_price` call is sufficient to instantly flip account health/trigger conditions with no intervening delay [2](#0-1) , confirming the exploitable atomic-jump behavior.

```rust
#[tokio::test]
async fn update_fixed_bank_price() -> anyhow::Result<()> {
    let test_settings = TestSettings {
        banks: vec![TestBankSetting {
            mint: BankMint::Fixed,
            ..Default::default()
        }],
        ..Default::default()
    };
    let test_f = TestFixture::new(Some(test_settings)).await;

    let bank_f = test_f.get_bank(&BankMint::Fixed);
    let bank_before = bank_f.load().await;
    assert_eq!(bank_before.config.oracle_setup, OracleSetup::Fixed);
    assert_eq!(I80F48::from(bank_before.config.fixed_price), I80F48!(2.0));

    let new_price_value = I80F48!(4.2);
    let new_price_wrapped = new_price_value.into();

    {
        let ctx = test_f.context.borrow();
        let ix = Instruction {
            program_id: marginfi::ID,
            accounts: marginfi::accounts::LendingPoolSetFixedOraclePrice {
                group: test_f.marginfi_group.key,
                admin: ctx.payer.pubkey(),
                bank: bank_f.key,
            }
            .to_account_metas(Some(true)),
            data: marginfi::instruction::LendingPoolSetFixedOraclePrice {
                price: new_price_wrapped,
            }
            .data(),
        };

        let tx = Transaction::new_signed_with_payer(
            &[ix],
            Some(&ctx.payer.pubkey()),
            &[&ctx.payer],
            ctx.banks_client.get_latest_blockhash().await.unwrap(),
        );

        ctx.banks_client.process_transaction(tx).await?;
    }

    let bank_after = bank_f.load().await;
    assert_eq!(bank_after.config.oracle_setup, OracleSetup::Fixed);
    assert_eq!(I80F48::from(bank_after.config.fixed_price), new_price_value);
```
