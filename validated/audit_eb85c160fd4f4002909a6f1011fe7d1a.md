### Title
Multisig executes requests below the configured signature threshold because confirmations from removed members/keys are never invalidated - (File: `multisig2/src/lib.rs`, `multisig/src/lib.rs`)

### Summary
Both `multisig/src/lib.rs` and `multisig2/src/lib.rs` remove a departing signer's own *submitted* requests when that signer/key is deleted, but they never scrub that signer's *confirmations* on requests submitted by other members. As a result, a stale confirmation from a member who has since been removed still counts toward `num_confirmations`, letting a request execute with fewer currently-live signers than the configured K-of-N threshold.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` only compares the confirmation count to `self.num_confirmations`; it never checks whether the accounts/keys in the `confirmations` set are still members: [1](#0-0) 

When a member is removed via `DeleteMember`, `delete_member()` only clears requests *created* by that member (`r.member == member`) and their `num_requests_pk` entry — it does not touch `self.confirmations` entries where that member is merely one of the confirming signers on requests created by someone else: [2](#0-1) 

The legacy `multisig/src/lib.rs` contract has the identical gap: `DeleteKey` purges requests signed by the deleted key but leaves that key's confirmations on other outstanding requests intact: [3](#0-2) 

The custody binding that should hold is: `confirmations counted toward execution == confirmations from currently live members`. Because stale confirmations are never purged, this equality breaks — the contract can execute a `MultiSigRequestAction` (including `Transfer`, `AddKey`, `FunctionCall`, `DeployContract`, etc.) using a mix of confirmations from live and already-removed signers.

### Impact Explanation
This directly maps to the explicitly listed Critical impact: "a multisig request executed below threshold." Consider a 3-of-4 multisig. Member A confirms request X (created by member B), leaving 1 confirmation recorded. A is later removed via a normal `DeleteMember` action (e.g., team member departs) — a routine, non-malicious operation. Request X still shows 1 confirmation belonging to the now-removed A. Only two more genuinely live members (C and D) need to confirm to reach `confirmations.len()+1 >= num_confirmations` (3), so the request — which could be a `Transfer` of the multisig's NEAR balance, an `AddKey` granting full access, or a `DeployContract` upgrade — executes with only 2 of 4 currently-live members actually agreeing, instead of the required 3. This is an authorization-threshold bypass with direct custody impact (funds transferred, or contract control ceded) and does not require any single member to act maliciously — it can occur purely from ordinary member churn.

### Likelihood Explanation
This requires no exploit sophistication or privileged/insider intent beyond the routine, expected operational flow of any multisig that occasionally rotates members: some member confirms a pending request, then is later removed (for entirely legitimate reasons) before that request finishes collecting confirmations. Multisig membership changes are a normal, expected lifecycle event, making this readily triggerable in production without any attacker needing to intentionally engineer the scenario.

### Recommendation
When removing a member/key (`delete_member` in `multisig2`, the `DeleteKey` branch in `multisig`), iterate all outstanding requests and strip the removed member's/key's confirmation from every `confirmations` entry, not just requests they authored. Alternatively, when counting confirmations in `confirm()`, filter the confirmation set to only identities still present in `self.members` (or the legacy key/account-key set) before comparing against `num_confirmations`, ensuring the K-of-N guarantee is always evaluated against currently live signers.

### Proof of Concept
1. Deploy `multisig2` with `num_confirmations = 3` and 4 members: A, B, C, D.
2. B calls `add_request` creating request X (e.g., `Transfer { amount }` to an attacker-controlled or arbitrary receiver).
3. A calls `confirm(X)` → `confirmations[X] = {A}` (1 confirmation recorded). [1](#0-0) 
4. The members submit and confirm a separate request `DeleteMember { member: A }` (reaching 3 confirmations from B, C, D on that separate request) — this executes `delete_member`, which removes A from `self.members` but does **not** touch `confirmations[X]`: [2](#0-1) 
5. C calls `confirm(X)` → `confirmations[X] = {A, C}` (2 confirmations, still under 3).
6. D calls `confirm(X)` → `confirmations.len() + 1 = 3 >= num_confirmations (3)` → request X executes via `execute_request`, transferring funds even though only C and D (2 of the 3 currently-live members) actually authorized it. [4](#0-3)

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }
