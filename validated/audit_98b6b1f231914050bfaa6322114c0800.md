### Title
Confirmations from a deleted multisig member remain counted toward the execution threshold, allowing a request to execute below the live-member confirmation threshold - (File: multisig2/src/lib.rs)

### Summary
`confirm()` counts entries in the `confirmations` set for a request without verifying that every recorded confirmer is still a current member. `delete_member()` removes a departing member's own outstanding *requests*, but never scrubs that member's *confirmations* on other members' still-pending requests. As a result, a confirmation cast by a member who is later removed continues to count toward `num_confirmations`, letting a request execute with fewer live-member approvals than the configured threshold requires.

### Finding Description
`confirm()` in `multisig2/src/lib.rs` only checks `confirmations.len() as u32 + 1 >= self.num_confirmations` to decide whether to execute a request: [1](#0-0) 

`delete_member()`, invoked through the `DeleteMember` request action, removes the departing member from `self.members`, deletes any *requests they authored*, and clears their `num_requests_pk` entry — but it never iterates `self.confirmations` to strip that member's confirmation from *other* pending requests they had previously confirmed: [2](#0-1) 

Compare this to `remove_request()`, which only clears confirmations for the specific request being removed/executed, not confirmations belonging to a removed member across all requests: [3](#0-2) 

The binding that should hold is:
`num_confirmations required == confirmations from members who are members at time of execution`

Because stale confirmations aren't purged, this becomes:
`confirmations.len() (including confirmations from now-deleted members) >= num_confirmations`, which can be true even when the count of *live* member confirmations is strictly less than `num_confirmations`.

### Impact Explanation
This breaks the authorization threshold guarantee central to a K-of-N multisig: a `Transfer`, `AddKey`, `FunctionCall`, or other privileged action encoded in a `MultiSigRequest` can be executed with fewer than `K` currently-authorized approvals. Since `Transfer` and `AddKey` actions can move NEAR or grant full access keys out of the multisig account, this is a critical impact per the rubric: "a multisig request executed below threshold" leading to potential unauthorized movement of funds held by the multisig account. This matches the pattern explicitly called out in scope ("confirmations counted versus live members").

### Likelihood Explanation
The scenario requires: (1) a pending request that has been partially confirmed by member A, (2) member A subsequently being removed via a separate `DeleteMember` request (a routine, expected multisig operation, e.g. offboarding a departing signer), and (3) the remaining request later collecting confirmations from other live members up to `num_confirmations` — at which point A's stale confirmation is silently counted. This does not require any attacker privilege escalation beyond what a normal multisig operational workflow already produces (member removal is a standard, expected action, not a hypothetical edge case), making the likelihood non-trivial in any multisig that rotates membership while requests are outstanding.

### Recommendation
When deleting a member in `delete_member()`, iterate all entries in `self.confirmations` (or maintain a reverse index from member → confirmed request IDs) and remove the deleted member's entry from every request's confirmation set, in addition to removing requests they authored. Alternatively, validate at `confirm()`/execution time that every principal in the `confirmations` set is still a current member before counting it toward the threshold.

### Proof of Concept
1. Multisig configured with `num_confirmations = 3` and members `{A, B, C, D}`.
2. Member A creates request R1 (`add_request_and_confirm`), producing `confirmations[R1] = {A}`.
3. Member B confirms R1: `confirmations[R1] = {A, B}` (2 < 3, not yet executed).
4. Separately, members confirm and execute a `DeleteMember { member: A }` request, removing A from `self.members`. `delete_member()` removes A's own authored requests and its `num_requests_pk` entry, but `confirmations[R1]` still contains `A`.
5. Member C confirms R1: `confirmations.len() + 1 == 3 >= num_confirmations`, so `execute_request(R1)` runs — even though only B and C are still live members (2 live confirmations), below the intended 3-of-N threshold.

    /// Confirm given request with given signing key.
    /// If with this, there has been enough confirmation, a promise with request will be scheduled.
    pub fn confirm(&mut self, request_id: RequestId) -> PromiseOrValue<bool> {
        self.assert_valid_request(request_id);
        let member = self
            .current_member()
            .unwrap_or_else(|| env::panic_str("Must be validated above"));
        let mut confirmations = self.confirmations.get(&request_id).unwrap();
        assert(
            !confirmations.contains(&member.to_string()),
            "Already confirmed this request with this key",
        );
        if confirmations.len() as u32 + 1 >= self.num_confirmations {
            let request = self.remove_request(request_id);
            /********************************
            NOTE: If the tx execution fails for any reason, the request and confirmations are removed already, so the client has to start all over
            ********************************/
            self.execute_request(request)
        } else {
            confirmations.insert(member.to_string());
            self.confirmations.insert(&request_id, &confirmations);
            PromiseOrValue::Value(true)
        }
    }

    /// Delete member from the list. Removes access key if the member is key based.
    fn delete_member(&mut self, promise: Promise, member: MultisigMember) -> Promise {
        assert(
            self.members.len() - 1 >= self.num_confirmations as u64,
            "Removing given member will make total number of members below number of confirmations",
        );
        // delete outstanding requests by public_key
        let request_ids: Vec<u32> = self
            .requests
            .iter()
            .filter_map(|(k, r)| if r.member == member { Some(k) } else { None })
            .collect();
        for request_id in request_ids {
            // remove confirmations for this request
            self.confirmations.remove(&request_id);
            self.requests.remove(&request_id);
        }
        // remove num_requests_pk entry for member
        self.num_requests_pk.remove(&member.to_string());
        self.members.remove(&member);
        match member {
            MultisigMember::AccessKey { public_key } => promise.delete_key(public_key.into()),
            MultisigMember::Account { account_id: _ } => promise,
        }
    }

    /// Removes request, removes confirmations and reduces num_requests_pk - used in delete, delete_key, and confirm
    fn remove_request(&mut self, request_id: RequestId) -> MultiSigRequest {
        // remove confirmations for this request
        self.confirmations.remove(&request_id);
        // remove the original request
        let request_with_signer = self
            .requests
            .remove(&request_id)
            .unwrap_or_else(|| env::panic_str("Failed to remove existing element"));
        // decrement num_requests for original request signer
        let original_member = request_with_signer.member;
        let mut num_requests = self
            .num_requests_pk
            .get(&original_member.to_string())
            .unwrap_or(0);
        // safety check for underrun (unlikely since original_signer_pk must have num_requests_pk > 0)
        if num_requests > 0 {
            num_requests = num_requests - 1;
        }
        self.num_requests_pk
            .insert(&original_member.to_string(), &num_requests);
        // return request
        request_with_signer.request
    }
