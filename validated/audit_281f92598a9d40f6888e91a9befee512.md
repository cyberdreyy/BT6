Confirmed: `drift/withdraw.rs`, `kamino` withdraw path (via `asset_tag` checks), `juplend/withdraw.rs`, and `solend/withdraw.rs` all gate execution on the bank's `config.asset_tag` matching the expected integration type. This validates the finding below.

### Title
`lending_pool_configure_bank`'s asset_tag change permits freezing funds in an integration bank without checking outstanding integration positions - (File: `programs/marginfi/src/state/bank.rs`)

### Summary
`Bank::configure`, invoked by the admin-only `lending_pool_configure_bank` instruction, lets the group `admin` change a bank's `asset_tag` (e.g. from `ASSET_TAG_DRIFT`/`ASSET_TAG_KAMINO`/`ASSET_TAG_JUPLEND`/`ASSET_TAG_SOLEND` to any other tag) with no check for whether the bank still has an open integration position (Drift user, Kamino obligation, JupLend position, Solend obligation) or outstanding user balances tied to that integration. This mirrors the TransmuterBuffer `setAlchemist` bug class: an admin-controlled "which external implementation backs this bank" pointer is switched while exposure to the old implementation is still open, and there is no on-chain guard preventing it.

### Finding Description
`Bank::configure` unconditionally applies `set_if_some!(self.config.asset_tag, config.asset_tag)`: [1](#0-0) 

All the integration-specific deposit/withdraw/claim instructions (Drift, Kamino, JupLend, Solend) validate that `bank.config.asset_tag` matches the expected tag before allowing any operation, e.g. `drift/withdraw.rs`, `juplend/withdraw.rs`, `solend/withdraw.rs`: [2](#0-1) [3](#0-2) 

The regular (non-integration) `lending_account_withdraw`/`lending_account_deposit` instructions only accept `ASSET_TAG_DEFAULT`/`ASSET_TAG_SOL`/`ASSET_TAG_STAKED` banks, per the integrator guide: [4](#0-3) [5](#0-4) 

Because `configure()` performs no check that `getTotalCredit`/`getAvailableFlow`-equivalent state (outstanding obligation balance, active integration balances on user accounts) is zero before flipping `asset_tag`, an admin who mis-sets or maliciously sets the tag while the bank still has funds in the old integration (e.g. an active Kamino/Drift/JupLend obligation with non-zero deposits) makes both the old integration's withdraw path (which requires the *old* tag, now gone) and the generic withdraw path (which rejects integration tags entirely) unusable for that bank. This is functionally identical to `setAlchemist` switching `sources[alchemist]` without verifying `getTotalCredit()`/`getAvailableFlow()` are zero — the pointer that determines "which code path is authoritative for this bank's funds" is swapped with no closure check on the old path's exposure.

This exact scenario is exercised (though framed as an intentional admin-config demo, not flagged as unsafe) in the Drift bank test suite, where the admin sets `assetTag = ASSET_TAG_KAMINO` on a Drift bank and the test comment states "but all Drift operations will now fail on it": [6](#0-5) 
followed by a user attempt to interact with the bank failing with `WrongBankAssetTagForDriftOperation`: [7](#0-6) 

If the admin does not immediately restore the correct tag (as the test conveniently does next), any user funds already deposited into that bank's underlying Drift/Kamino/JupLend/Solend integration position remain deposited there, but become **unreachable through any marginfi instruction**: the integration-specific withdraw requires the old tag, and the generic withdraw instruction explicitly rejects integration asset tags.

### Impact Explanation
If the admin's `asset_tag` change is applied to a bank that still holds live deposits/borrows in its underlying integration (Kamino obligation, Drift user account, JupLend position, Solend obligation), every user holding a balance in that bank loses the ability to withdraw or repay through any marginfi instruction path — a durable, financial-impact fund freeze, matching the severity class of the original `setAlchemist` report (admin-only trigger, but systemic user-fund-freeze impact "system breaking with external assumptions").

### Likelihood Explanation
Triggering this requires an admin action (`lending_pool_configure_bank` with a new `asset_tag`), so it is not exploitable by an unprivileged attacker directly. However, likelihood of *operational* occurrence is non-trivial: `BankConfigOpt.asset_tag` is a routinely-used field (also exercised for legitimate migrations/corrections), there is no on-chain safeguard against applying it to a bank with an open integration position, and the codebase's own test suite demonstrates the exact hazardous pattern (change tag → operations fail → admin must remember to revert) without any protocol-enforced guard rail, exactly the kind of "operational mistake" the original C4 report was concerned about.

### Recommendation
Before allowing `asset_tag` to change on a bank whose current tag is an integration tag (`ASSET_TAG_KAMINO`, `ASSET_TAG_DRIFT`, `ASSET_TAG_JUPLEND`, `ASSET_TAG_SOLEND`), require that the bank's underlying integration exposure is fully closed — e.g., check that `total_asset_shares`/`total_liability_shares` are zero (or equivalently that the linked obligation/spot balance is empty) — analogous to requiring `getAvailableFlow()`/`getTotalCredit()` be zero before `setAlchemist` switches. Reject the `asset_tag` change with an explicit error (e.g., `IntegrationExposureNotClosed`) otherwise, forcing depositors to be fully withdrawn from the old integration before the tag can be repointed.

### Proof of Concept
1. Admin creates a Kamino- or Drift-wrapped bank (`ASSET_TAG_KAMINO`/`ASSET_TAG_DRIFT`) and users deposit funds, opening a live Kamino obligation / Drift user position.
2. Admin (accidentally or via a compromised/malicious admin key) calls `lending_pool_configure_bank` with `bank_config_opt.asset_tag` set to a different tag (e.g. `ASSET_TAG_DEFAULT` or another integration tag), as shown in [6](#0-5) . `Bank::configure` applies this with no exposure check [8](#0-7) .
3. Any user attempting to withdraw via the original integration-specific instruction now fails asset-tag validation (`WrongBankAssetTagForDriftOperation`), as demonstrated in [7](#0-6) .
4. The generic `lending_account_withdraw` instruction also rejects the bank because integration asset tags are excluded from that path [5](#0-4) .
5. If the admin does not restore the correct tag (unlike the test, which immediately does so at line 290-309), user funds remain locked in the underlying integration position indefinitely, with no instruction path able to reach them.

    fn configure(&mut self, config: &BankConfigOpt) -> MarginfiResult {
        set_if_some!(self.config.asset_weight_init, config.asset_weight_init);
        set_if_some!(self.config.asset_weight_maint, config.asset_weight_maint);
        set_if_some!(
            self.config.liability_weight_init,
            config.liability_weight_init
        );
        set_if_some!(
            self.config.liability_weight_maint,
            config.liability_weight_maint
        );
        set_if_some!(self.config.deposit_limit, config.deposit_limit);

        set_if_some!(self.config.borrow_limit, config.borrow_limit);

        if let Some(new_state) = config.operational_state {
            // JupLend banks must be activated exactly once through `juplend_init_position`.
            check!(
                !(self.config.asset_tag == ASSET_TAG_JUPLEND
                    && self.config.operational_state == BankOperationalState::Uninitialized),
                MarginfiError::Unauthorized
            );
            // These states are unreachable by configuration
            check!(
                new_state != BankOperationalState::KilledByBankruptcy
                    && new_state != BankOperationalState::Uninitialized,
                MarginfiError::Unauthorized
            );
            // Log operational state change
            let old_state = self.config.operational_state;
            self.config.operational_state = new_state;
            msg!(
                "Operational state changed from {:?} to {:?}",
                old_state,
                new_state
            );
        }

        if let Some(ir_config) = &config.interest_rate_config {
            self.config.interest_rate_config.update(ir_config);
        }

        // Log risk tier change
        if let Some(new_risk_tier) = config.risk_tier {
            let old_risk_tier = self.config.risk_tier;
            self.config.risk_tier = new_risk_tier;
            msg!(
                "Risk tier changed from {:?} to {:?}",
                old_risk_tier,
                new_risk_tier
            );
        }

        set_if_some!(self.config.asset_tag, config.asset_tag);
