## Analog Found

### Title
Cross-tenant request-ID squatting causes denial-of-service in HTTP Trigger Gateway handler - (File: `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`)

### Summary
The FIVA report's root cause is that a shared, deterministic state object (`RedeemDeposit`'s address) is keyed only by `(YTMinter, recipient)` and omits the transfer initiator, so any unprivileged actor can address and mutate another user's in-flight state by supplying the victim's identifier. The Chainlink Gateway's `httpTriggerHandler` has the same class of defect: pending trigger callbacks are stored in a single global map keyed only by the caller-supplied `req.ID` string, with no binding to the authenticated/authorized caller, workflow, or owner. Any unprivileged client hitting the gateway's public HTTP-trigger endpoint can pre-occupy another user's request ID, blocking that user's legitimate request.

### Finding Description
`httpTriggerHandler.callbacks` is declared as `map[string]savedCallback // requestID -> savedCallback` and is written to and read from purely by the raw client-supplied `req.ID`: [1](#0-0) 

`setupCallback` rejects a new request outright if any *other* caller has already registered the same `req.ID`, and this check happens under a single mutex protecting the process-wide map — there is no per-owner, per-workflow, or per-authorized-key namespacing of the key space: [2](#0-1) 

Authorization (`h.authorizeRequest` / `h.workflowMetadataHandler.Authorize`) happens earlier and validates the caller against the *target workflow*, but it never rewrites or scopes `req.ID` before it is used as the map key, unlike the Vault gateway handler, which explicitly stamps the request ID with the authorized owner (`authorizedOwner + Separator + originalRequestID`) precisely to prevent ID collisions across different callers before storing it in its own `activeRequests` map: [3](#0-2) 

Because the HTTP trigger path lacks this owner-scoping step, `req.ID` is a raw, attacker-influenceable string shared across every tenant/workflow calling this DON's HTTP trigger endpoint. `validateRequestID` only checks for emptiness and disallows `/`, it does not bind the ID to the caller: [4](#0-3) 

An attacker who can predict or observe a victim's chosen request ID (e.g., because it is sequential, a well-known constant used by an integration, or leaked via logs/telemetry/network observation) can send their own HTTP trigger request using that exact `id` value ahead of the victim. Because the check-then-set happens under `callbacksMu` with no ownership check on the ID itself, the victim's subsequent legitimate request will be rejected with `jsonrpc.ErrConflict` ("requestID ... has already been used"), exactly analogous to the FIVA bug where an attacker's message to a shared, under-scoped state object interferes with a legitimate user's operation.

### Impact Explanation
This allows an unprivileged, unauthenticated-relative-to-victim actor to deny/disrupt another tenant's workflow execution requests on a shared Gateway DON simply by racing a request with the same `id`. It does not require any node/peer compromise, operator privilege, or mocked-only path — it is reachable purely from the public gateway ingress used by ordinary API clients. Depending on how integrators choose/generate request IDs (client-controlled, and the code explicitly documents it as a *user*-facing field), this can be a practical vector to block time-sensitive workflow triggers or cause silent execution failures for a targeted workflow owner.

### Likelihood Explanation
Likelihood depends on the ID being guessable/observable and on request timing (attacker must submit first). Many integrations use predictable IDs (timestamps, incrementing counters, or fixed identifiers reused across retries), and the ID is not secret — it is user-supplied and appears in JSON-RPC envelopes potentially visible via shared infra/logs. No cryptographic secret or session token is required to exploit it; only knowledge of the target `id` string and the ability to call the gateway endpoint (unauthenticated for structural purposes, since authorization is workflow-scoped, not ID-scoped).

### Recommendation
Scope the `callbacks` map key by `(authorizedOwner/workflowID, req.ID)` instead of by raw `req.ID` alone — mirroring the pattern already used in `gateway_vault_request_processor.go`'s `authorizeAndStamp`, which prefixes the request ID with the authorized owner before using it as a lookup key. This ensures that request-ID collisions can only occur within a single authorized caller's own namespace, not across tenants.

### Proof of Concept
1. Victim submits a legitimate HTTP trigger request to the Gateway with `id = "order-42"` for `workflowID = W_victim`.
2. Before the victim's request completes, an attacker (with access to any authorized workflow, or even the same public endpoint) submits their own trigger request also using `id = "order-42"` (for any workflow they're authorized to call), racing to call `setupCallback` first.
3. Whichever request registers first into `h.callbacks["order-42"]` wins; the other party's `setupCallback` call finds `h.callbacks["order-42"]` already present at line 402 and returns `jsonrpc.ErrConflict`, terminating that request with "requestID: order-42 has already been used."
4. If the attacker wins the race, the victim's legitimate trigger is denied, without the attacker needing any information about or access to the victim's workflow itself. [2](#0-1)

func (h *httpTriggerHandler) validateRequestID(ctx context.Context, requestID string, callback handlers.Callback) error {
	if requestID == "" {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "'id' field is required and cannot be empty. Use a new unique request 'id' for each request", callback)
		return errors.New("empty request ID")
	}
	// Request IDs from users must not contain "/", since this character is reserved
	// for internal node-to-node message routing (e.g., "http_action/{workflowID}/{uuid}").
	if strings.Contains(requestID, "/") {
		h.handleUserError(ctx, requestID, jsonrpc.ErrInvalidRequest, "request ID must not contain '/'", callback)
		return errors.New("request ID must not contain '/'")
	}
	return nil
}

func (h *httpTriggerHandler) setupCallback(ctx context.Context, requestID string, callback handlers.Callback, requestStartTime time.Time, workflowID string) (<-chan struct{}, error) {
	h.callbacksMu.Lock()
	defer h.callbacksMu.Unlock()

	if _, found := h.callbacks[requestID]; found {
		h.handleUserError(ctx, requestID, jsonrpc.ErrConflict, fmt.Sprintf("requestID: %s has already been used. Ensure the requestID is unique for each request.", requestID), callback)
		return nil, fmt.Errorf("in-flight request ID: %s", requestID)
	}
