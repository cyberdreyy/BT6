### Title
Double-counted signer weight across `total_weight_approved` / `total_weight_rejected` lets the miner treat an already-quorum-signed block as rejected — ([File: stacks-node/src/nakamoto_node/stackerdb_listener.rs])

### Summary
The node-side `StackerDBListener` tallies signer weight for a block into two independent buckets, `total_weight_approved` and `total_weight_rejected`, using two independent de-duplication guards keyed on different maps/sets. If a single signer first rejects a block proposal and later, on a legitimate re-proposal of the *same* block (same `signer_signature_hash`), sends an `Accepted` response, that signer's weight is added to *both* buckets. The `SignerCoordinator` then evaluates `total_weight_rejected` before `total_weight_approved`, so the inflated rejection tally can make it wrongly conclude the block was rejected by the signer set even though it actually gathered a genuine ≥70% signature quorum.

### Finding Description
`BlockStatus` in [1](#0-0)  tracks `responded_signers` (a `HashSet<u32>` of slot ids that have responded at all), `gathered_signatures` (a `BTreeMap<u32, MessageSignature>` of slots that accepted), `total_weight_approved`, and `total_weight_rejected`.

In the `Accepted` message handler, weight is added to `total_weight_approved` only if the slot is not already present in `gathered_signatures`, and then the slot is unconditionally inserted into both `gathered_signatures` and `responded_signers`: [2](#0-1) 

In the `Rejected` message handler, weight is added to `total_weight_rejected` only if `responded_signers.insert(slot_id)` returns `true` (i.e., the slot has never responded before, in either direction): [3](#0-2) 

This correctly prevents double counting in the "accept-then-reject" order (a slot already in `responded_signers` via `Accepted` will not add reject weight). But it does **not** protect the opposite order: "reject-then-accept" for the same block. If a slot rejects first, `responded_signers` gains that slot id and `total_weight_rejected` is incremented. If that same slot later sends `Accepted` for the *same block hash* (same `signer_signature_hash`/`BlockStatus` entry), the guard checked is only `!gathered_signatures.contains_key(&slot_id)` — which is still `false` (not present), so `total_weight_approved` is also incremented for that same signer's weight.

This reject-then-accept transition is not a majority-controlled or exotic path — it is an explicitly supported part of the signer state machine: `LocallyRejected --> LocallyAccepted : re-evaluated`, and a defined set of rejection reasons are treated as re-evaluable on re-proposal of the same block: [4](#0-3) 

Reasons such as `ConnectivityIssues`, `NotFoundError`, `NoSortitionView`, and `NoSignerConsensus` are all re-evaluable, and a documented test (`signer_reevaluates_proposal_with_missing_burn_view`) exercises exactly this re-proposal/re-evaluation flow for the same `signer_signature_hash`: [5](#0-4) 

A single miner (which controls proposal timing/broadcast order) can trigger a subset of signers into a transient rejection (e.g. a burn-view/connectivity race) and then, on re-proposal after the transient condition clears, those signers validate and sign, sending `Accepted` for the identical block hash. Each such signer's weight then lands in both `total_weight_rejected` and `total_weight_approved` for that block's `BlockStatus`.

On the consuming side, `SignerCoordinator::wait_for_signatures` (or its caller) checks the rejection condition before the acceptance condition: [6](#0-5) 

Because `total_weight_rejected` can be inflated with weight that legitimately also appears in `total_weight_approved`, it is possible for both `total_weight_rejected.saturating_add(weight_threshold) > total_weight` and `total_weight_approved >= weight_threshold` to hold simultaneously for the same block. Since the reject branch is evaluated first, the coordinator returns `Err(NakamotoNodeError::SignersRejected{..})` and discards the block, even though it actually carries a valid, gathered quorum of signatures (`gathered_signatures`) that should have produced `Ok(...)`.

### Impact Explanation
This breaks the intended equality between "aggregated weight" and "verified accepts": the coordinator's rejection/acceptance tallies are supposed to be built from disjoint per-signer contributions, but the accept-path's de-duplication check does not account for a prior rejection recorded via the reject-path's separate guard set. The result is a liveness wedge on the miner/coordinator: a block that genuinely reached the required signature threshold from real signer signatures can be discarded as "rejected" by the node, wasting the tenure's mining opportunity and the already-collected valid signatures — achievable by ordinary proposal-timing behavior of a single miner, no majority of signers or key compromise required.

### Likelihood Explanation
The reject-then-accept transition for the same block hash is a first-class, documented, and tested path in the signer software (`should_reevaluate_reject_reason`, the `LocallyRejected --> LocallyAccepted` state transition, and the existing `signer_reevaluates_proposal_with_missing_burn_view` test). A miner naturally re-proposing the same block after a transient validation failure (a normal occurrence, e.g., due to burn-view timing/connectivity blips) is enough to trigger the double count for any signer(s) who experienced the transient rejection reason before later accepting.

### Recommendation
Use a single, unified per-slot state (or a single map from slot id to "final vote": Accept/Reject) to decide which weight bucket a signer's weight belongs to, and make the two handlers share that same guard so a slot can only ever contribute weight to one of `total_weight_approved` / `total_weight_rejected` for a given block, regardless of the arrival order of `Rejected` and `Accepted` messages. Concretely, before adding weight in the `Accepted` arm, also check (and clear, moving the weight) if the slot is present in `responded_signers` due to a prior rejection, or restructure `BlockStatus` so `responded_signers` records the signer's *current* vote rather than merely "has responded".
