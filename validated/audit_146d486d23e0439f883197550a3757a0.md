### Title
Changing the whitelisted CDO freezes funded withdrawal claims - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault` authorizes withdrawal processing through the mutable `idleCDO` address, while the deployed `IdleCDOEpochVariant` continues forwarding user claims to that strategy. Calling `setWhitelistedCDO()` with a replacement address therefore makes every existing funded, instant, loss-adjusted, or recovery claim revert until the original CDO is restored.

### Finding Description
`IdleCreditVault.requestWithdraw()` burns the CDO’s strategy-token principal, mints an address-bound receipt to the user, and records the claim in `withdrawsRequests`, `withdrawsRequestsByEpoch`, or the APR0 accounting structures. [1](#0-0) 

The CDO’s public `claimWithdrawRequest()` forwards the user’s address to `IdleCreditVault.claimWithdrawRequest()`. [2](#0-1)  The strategy immediately requires `msg.sender == idleCDO`, so authorization depends on the strategy’s current configured CDO rather than the CDO that created and funded the receipt. [3](#0-2) [4](#0-3) 

`setWhitelistedCDO()` can replace that pointer at any time and only rejects the zero address. [5](#0-4)  It does not check whether receipts are pending, whether an epoch is active, or whether the configured CDO still references this strategy. After replacement, calls originating from the original CDO revert in `_onlyIdleCDO()`, even though `_transferFundedClaim()` still holds and would otherwise pay the matured underlying balance to the receipt owner. [6](#0-5) 

The same failure blocks queued withdrawals because `IdleCDOEpochQueue.processWithdrawalClaims()` must call the original CDO’s `claimWithdrawRequest()` or `claimInstantWithdrawRequest()` before releasing epoch payouts to queue users. [7](#0-6) 

### Impact Explanation
An unprivileged tranche holder can create a withdrawal receipt and have the claim funded during a normal epoch stop, but a subsequent routine CDO replacement makes the claim path revert with `NotAllowed()`. [8](#0-7) 

The affected user loses access to the entire matured claim rather than only epoch interest; for example, a funded 10,000-underlying receipt leaves all 10,000 underlying unavailable while the strategy points to a different CDO. [9](#0-8)  All users of the affected CDO are affected, including queue participants whose aggregate claim processing is routed through the same stale CDO. [10](#0-9) 

The owner can restore the previous address or rescue assets with `transferToken()`, so the impact is ordinarily temporary freezing rather than a cryptographically permanent loss. [11](#0-10)  If a migration abandons the original CDO without first settling receipts, the freeze is indefinite for every outstanding claim.

### Likelihood Explanation
The flaw requires an honest owner to execute a plausible operational migration or configuration change; users cannot invoke `setWhitelistedCDO()` themselves. [5](#0-4)  The exploit sequence is nevertheless simple because an attacker only needs an ordinary pending or matured withdrawal when the replacement occurs, and no epoch-state or outstanding-claim guard prevents the update. [12](#0-11) 

### Recommendation
Do not allow `setWhitelistedCDO()` to replace an already-configured CDO while the strategy has active obligations. Prefer a one-time setter, or require an explicit migration state in which `pendingWithdraws`, `pendingInstantWithdraws`, defaulted recovery claims, and all other claim liabilities are proven settled before updating `idleCDO`.

If replacement must remain supported, retain the old CDO as an authorized settlement-only caller until all receipts created under it are claimed, or atomically migrate receipt ownership and authorization to the replacement CDO. Direct owner rescue should not be the compatibility mechanism for ordinary claims.

### Proof of Concept
The following drop-in test uses the existing `IdleCreditVault.t.sol` Foundry fixture and demonstrates a funded 10,000-underlying claim becoming inaccessible after the owner changes the whitelisted CDO:

```solidity
function testChangeWhitelistedCDOFreezesMaturedClaim() external {
    uint256 amount = 10_000 * ONE_SCALE;
    address user = makeAddr("user");
    address replacementCdo = makeAddr("replacement-cdo");

    // User deposits and creates a normal withdrawal receipt.
    _depositWithUser(user, amount, true);
    vm.prank(user);
    uint256 claimAmount = cdoEpoch.requestWithdraw(0, address(AAtranche));
    assertGt(claimAmount, 0, "receipt was not created");

    // The next successful stop funds the pending receipt in IdleCreditVault.
    _startEpochAndCheckPrices(0);
    _stopEpochAndCheckPrices(0, initialProvidedApr, _expectedFundsEndEpoch());

    IdleCreditVault creditVault = IdleCreditVault(address(strategy));
    assertEq(
        creditVault.withdrawsRequests(user),
        claimAmount,
        "funded claim is not recorded"
    );

    // Routine CDO replacement is unrestricted.
    vm.prank(owner);
    creditVault.setWhitelistedCDO(replacementCdo);

    // The original CDO still routes the user's claim, but is no longer authorized.
    uint256 userBalanceBefore = underlying.balanceOf(user);
    vm.prank(user);
    vm.expectRevert(abi.encodeWithSelector(NotAllowed.selector));
    cdoEpoch.claimWithdrawRequest();

    assertEq(
        underlying.balanceOf(user),
        userBalanceBefore,
        "frozen claim paid underlying"
    );
    assertGe(
        underlying.balanceOf(address(creditVault)),
        claimAmount,
        "funded claim is missing from strategy"
    );

    // Restoring the original CDO proves the failure is pointer staleness.
    vm.prank(owner);
    creditVault.setWhitelistedCDO(address(cdoEpoch));

    vm.prank(user);
    cdoEpoch.claimWithdrawRequest();
    assertEq(
        underlying.balanceOf(user) - userBalanceBefore,
        claimAmount,
        "user did not receive matured claim"
    );
}
```

  function _claimFundedWithdrawRequest(address _user) internal returns (uint256 amount) {
    // User should wait at least an epoch before claiming the withdraw. Once the epoch is over user can withdraw 
    // at any time even if a new epoch started. 
    // So if epochNumber is the same as the last withdraw request then we revert. Epoch number is increased at stopEpoch
    // NOTE: If a user does not claim a withdraw request and instead requests another withdraw, he will have to wait
    // for another epoch to claim both requests.
    // NOTE 2: if borrower defaults, old withdraw requests can still be claimed
    if (IIdleCDOEpochVariant(idleCDO).epochEndDate() != 0 && (epochNumber <= lastWithdrawRequest[_user])) {
      revert NotAllowed();
    }
    // settle APR=0 requests once the related epoch has ended
    _settleApr0(_user);
    Apr0UserData storage _apr0User = apr0Users[_user];
    // Claim includes:
    // - settled APR0 principal from finalized epochs
    // - still-open APR0 principal: if pool-close mode was used (_interest == 1), IdleCDO sets
    //   epochEndDate = 0 and claims can be immediate, while _settleApr0 can still skip settlement
    //   for the current request epoch (reqEpoch >= epochNumber).
    // - settled APR0 interest
    uint256 normalAmount = withdrawsRequests[_user];
    uint256 apr0PrincipalAmount = _apr0User.settledPrincipal + _apr0User.principal;
    uint256 apr0InterestAmount = _apr0User.settledInterest;
    amount = normalAmount + apr0PrincipalAmount + apr0InterestAmount;
    // burn strategy tokens 1:1 with the principal only (normal amount already includes interest)
    _burn(_user, normalAmount + apr0PrincipalAmount);
    withdrawsRequests[_user] = 0;
    lastWithdrawRequest[_user] = 0;
    if (apr0PrincipalAmount != 0 || apr0InterestAmount != 0) {
      delete apr0Users[_user];
    }
    _transferFundedClaim(_user, amount);

  function _transferFundedClaim(address _user, uint256 _amount) internal {
    if (_amount == 0) return;
    uint256 reserve = defaultRecoveryReserve;
    if (reserve != 0) {
      uint256 balance = underlyingToken.balanceOf(address(this));
      // This should be unreachable when accounting is consistent. Keep the guard so old funded
      // receipts can never spend underlyings reserved for default recovery claimants.
      if (balance < reserve || balance - reserve < _amount) revert NotAllowed();
