### Title
Stale `lossRecoveryPriceByEpoch` lookup binds new withdraw receipts to a prior loss epoch's haircut - (File: contracts/strategies/idle/IdleCreditVault.sol)

### Summary
`IdleCreditVault._claimLossAdjustedWithdrawRequest` resolves a user's loss-adjusted claim via `lossRecoveryPriceByEpoch[lastWithdrawRequest[_user]]`, i.e., it assumes `lastWithdrawRequest` always points at the *epoch that stored the haircut* — a strictly-ordered binding. New withdraw requests overwrite `lastWithdrawRequest` with the *current* `epochNumber`, and `epochNumber` is only bumped inside `deposit()` when the epoch is running. There is no validation that the request epoch is strictly greater than the epoch that owns the stored recovery price, so a request recorded under the same `epochNumber` key as a `stopEpochWithDuration` loss epoch gets bound to that epoch's `lossRecoveryPrice` — the same class of defect as the TensorFlow advisory (missing increasing-order check causing a binding to an invalid/stale element).

### Finding Description
In `requestWithdraw`, per-epoch receipt accounting is keyed by `epochNumber` (`withdrawsRequestsByEpoch[_user][currentEpoch]`, `lastWithdrawRequest[_user] = currentEpoch`) at `contracts/strategies/idle/IdleCreditVault.sol:260-293`. In `collectWithdrawFunds`, a partial funding writes `lossRecoveryPriceByEpoch[epochNumber]` at `contracts/strategies/idle/IdleCreditVault.sol:411-430`. Both sides index by the same monotonically-ish-increasing counter, but `epochNumber` is only incremented inside `deposit()` when `isEpochRunning()` is true (`IdleCreditVault.sol:607-614`). Requests made during the buffer phase (or during a stop in which the deposit-bump has not yet run relative to `collectWithdrawFunds`) can therefore be recorded under the same `epochNumber` that already stores a nonzero `lossRecoveryPriceByEpoch`.

The guard at `IdleCreditVault.sol:263-271` only reverts when *the same user* already holds a receipt in that loss epoch. A different user (attacker) opening a fresh request under the colliding epoch number passes the guard, then `_claimLossAdjustedWithdrawRequest` (`IdleCreditVault.sol:789-800`) computes `claimBasis * lossRecoveryPrice / RECOVERY_FULL` and pays from `_transferFundedClaim` — the strategy's funded underlying pool that was sourced only for the original loss-epoch basis. If the attacker's `claimBasis` exceeds the originally funded basis, the payout drains underlying earmarked for honest loss-epoch claimants (or, if the balance is insufficient, reverts and blocks their claims).

Caveat I could not fully resolve: whether `collectWithdrawFunds` executes before or after the `deposit()`-driven `epochNumber += 1` inside the same `stopEpoch`/`stopEpochWithDuration` call chain in `IdleCDOEpochVariant`. If the bump strictly precedes `collectWithdrawFunds`, the collision requires a same-`epochNumber` request, which the buffer-phase flow provides; if the bump strictly precedes the price write *and* requests can only land in the bumped value, the collision window narrows to requests made between the write and the next bump. A Foundry PoC is required to pin down the exact intra-transaction ordering.

### Impact Explanation
If the epoch collision is reachable, a KYC-passing tranche holder can bind a freshly created, fully-backed withdraw receipt to an old haircut price and claim `claimBasis * p_loss` from the funded claim pool. When `claimBasis` is larger than the originally funded basis, the payout exceeds the funded reserve for that epoch and either steals other users' funded withdrawal proceeds or renders their claims unexecutable (permanent freezing of funded claims). Loss is bounded by the funded claim pool balance.

### Likelihood Explanation
Requires a realized `stopEpochWithDuration` loss (`lossRecoveryPriceByEpoch[e] != 0`) followed by a new `requestWithdraw` recorded under the same `epochNumber`. Loss-adjusted stops are exceptional but supported production behavior; requesting a withdraw in the buffer phase is a normal unprivileged action. The determining factor is the `epochNumber` bump ordering relative to `collectWithdrawFunds`, which needs fork PoC confirmation.

### Recommendation
In `IdleCreditVault.requestWithdraw`, revert when `lossRecoveryPriceByEpoch[currentEpoch] != 0` for *any* new request (not only when the same user holds a receipt in that epoch), or key loss-adjusted claims off an immutable per-receipt epoch that cannot collide — e.g., store the request epoch in a per-user struct and require `requestEpoch > lastLossEpoch`. Alternatively, bump `epochNumber` atomically at the top of the stop path so no request can ever be recorded under a loss-priced epoch key.

### Proof of Concept
Sketch (requires Foundry fork of an in-scope credit vault; ordering of `epochNumber` bump vs `collectWithdrawFunds` must be confirmed):

```solidity
// 1. LP_A deposits AA, epoch runs, LP_A requests withdraw -> pendingWithdraws = X
// 2. stopEpochWithDuration with _lossAmount > 0 -> collectWithdrawFunds(X - loss)
//    stores lossRecoveryPriceByEpoch[E] = p < 1e18, pendingWithdraws = 0
// 3. Attacker (KYC'd AA holder) calls cdoEpoch.requestWithdraw(amount, AA)
//    while strategy.epochNumber() still == E (buffer phase).
//    -> lastWithdrawRequest[attacker] = E, withdrawsRequestsByEpoch[attacker][E] = Y
// 4. Next stopEpoch funds receipts; attacker calls claimWithdrawRequest()
//    -> _claimLossAdjustedWithdrawRequest reads price p for epoch E,
//       pays Y * p from funded pool reserved for LP_A's X * p
// 5. If Y * p > funded amount, transfer pulls other claimants' funds
//    (theft) or reverts, blocking LP_A's legitimate loss-adjusted claim.
```

Note: this finding is conditional on the `epochNumber` increment timing; if `collectWithdrawFunds` always runs strictly before the `deposit()`-triggered `epochNumber += 1` within `stopEpoch` and no request can be recorded under the pre-bump value afterwards, the collision is unreachable and this reduces to a non-issue.
