### Title
Instant-withdraw receipts requested after `getInstantWithdrawFunds()` drain already-funded claims of earlier requesters - (contracts/strategies/idle/IdleCreditVault.sol)

### Summary
The external bug is a publish-then-flag ordering: a socket is inserted into the lookup hash table before `SOCK_RCU_FREE` is set, so a concurrent reader can observe and use an object whose protection flag is not yet set. The closest credit-vault analog is the instant-withdraw path: `requestInstantWithdraw` records a receipt in the same aggregate claim bucket (`instantWithdrawsRequests[_user]`) that `claimInstantWithdrawRequest` pays out in full, while the funding guard is a single epoch-level flag (`allowInstantWithdraw`) set once by `getInstantWithdrawFunds()`. A receipt created *after* that flag is set is "visible" to the claim path with no per-request funding marker — it rides on a funding round that was collected for earlier requesters.

### Finding Description
In `IdleCreditVault.sol`, `requestInstantWithdraw` mints receipt strategy tokens and increments `instantWithdrawsRequests[_user]`, `instantWithdrawsRequestsByEpoch`, and `pendingInstantWithdraws` (lines 356-375). `claimInstantWithdrawRequest` burns the entire `instantWithdrawsRequests[_user]` balance and calls `_transferFundedClaim` (lines 380-393) — it does not check that the specific receipt was part of a completed funding round; the only gate is `allowInstantWithdraw` in `IdleCDOEpochVariant.claimInstantWithdrawRequest` (lines 975-979), which `getInstantWithdrawFunds` sets after pulling `pendingInstantWithdraws` from the borrower.

Sequence in a running epoch with instant withdrawals enabled:

1. User A requests an instant withdraw in the buffer; `pendingInstantWithdraws = A`.
2. Epoch starts; after `instantWithdrawDelay`, the manager calls `getInstantWithdrawFunds()` → `collectInstantWithdrawFunds` moves `pendingInstantWithdraws` to 0 and transfers A underlyings into the vault; `allowInstantWithdraw = true`.
3. Attacker B (any tranche holder / KYC-passing lender) calls `requestWithdraw` on the CDO while the epoch is running; if the instant path is taken, `requestInstantWithdraw` mints B a receipt and sets `instantWithdrawsRequests[B] = B`.
4. B calls `claimInstantWithdrawRequest()` in the same transaction or immediately after. `allowInstantWithdraw` is already true, so the claim burns B's fresh receipt and transfers B underlyings out of the vault balance that was collected for A.
5. A's subsequent claim reverts (insufficient vault balance) or is paid only if the borrower funds B's request in a second `getInstantWithdrawFunds` round — which the flag/guard structure does not guarantee, since `pendingInstantWithdraws` was already drained once and `allowInstantWithdraw` is already set.

The broken invariant is "one receipt, one funded payout": the funding reservation (`collectInstantWithdrawFunds` decrementing `pendingInstantWithdraws`) is matched to receipts by aggregate balance rather than by the epoch/request that was actually funded, so a late receipt is claimable before its own funding flag round exists — the same "object reachable before its guard is set" pattern as the UDP bug.

### Impact Explanation
Direct theft of funded withdrawal proceeds: B receives underlyings that were collected specifically to satisfy A's matured instant request. A's receipt remains burned-or-frozen: `claimInstantWithdrawRequest` will revert on insufficient vault balance once B has drained it, so A suffers permanent freezing of their claim unless the honest borrower happens to over-fund later. Loss is bounded by the funded `pendingInstantWithdraws` balance at the time of the attack.

### Likelihood Explanation
Requires an epoch where instant withdrawals trigger (`lastEpochApr` condition met), a completed `getInstantWithdrawFunds` round, and the CDO's `requestWithdraw` still routing new requests through `requestInstantWithdraw` while `allowInstantWithdraw` is true — i.e., `disableInstantWithdraw` must not already block new instant requests mid-epoch. I was not able to fully verify in the indexed code whether `requestWithdraw` permits the instant path after `allowInstantWithdraw` is set; if the CDO forces post-funding requests into the normal `pendingWithdraws` bucket, this vector is closed and the finding should be downgraded. Under the assumption instant requests remain routable, the attack is a two-transaction sequence by any unprivileged tranche holder.

### Recommendation
Track funding per request epoch for instant withdrawals, mirroring the normal-path `withdrawsRequestsByEpoch`/`lossRecoveryPriceByEpoch` accounting: record `instantFundedEpoch` when `collectInstantWithdrawFunds` runs and have `claimInstantWithdrawRequest` only pay receipts whose `instantWithdrawsRequestsByEpoch[_user][e]` belong to a funded epoch `e`, or revert when `pendingInstantWithdraws != 0` covers the claimed amount. Alternatively, disallow the instant path in `requestWithdraw` once `allowInstantWithdraw` is set for the running epoch so new receipts cannot join an already-funded bucket.

### Proof of Concept
Foundry fork PoC outline (mirroring `testClaimInstantWithdrawRequest` in `test/foundry/IdleCreditVault.t.sol:4742`):

```solidity
// setup: deposits, epoch0 run, epoch0 stop with lower APR so instant path triggers
idleCDO.depositAA(amountWei);            // victim A + attacker B hold AA tranches
_startEpochAndCheckPrices(0);
_stopEpochAndCheckPrices(0, initialProvidedApr / 2, _expectedFundsEndEpoch());

// A requests instant withdraw
vm.prank(A);
uint256 reqA = cdoEpoch.requestWithdraw(aTrancheBal, address(AAtranche));

// epoch 1 starts; manager collects instant funds for A
_startEpochAndCheckPrices(1);
vm.warp(block.timestamp + cdoEpoch.instantWithdrawDelay() + 1);
_getInstantFunds();                       // allowInstantWithdraw = true, vault holds reqA

// B requests instant withdraw AFTER funding round completed
vm.startPrank(B);
uint256 reqB = cdoEpoch.requestWithdraw(bTrancheBal, address(AAtranche));
// B claims immediately — funded reserve collected for A is drained to B
cdoEpoch.claimInstantWithdrawRequest();
vm.stopPrank();
assertEq(underlying.balanceOf(B) - balBPre, reqB);

// A's claim now reverts / underpays
vm.prank(A);
vm.expectRevert();                        // or assertLt payout < reqA
cdoEpoch.claimInstantWithdrawRequest();
```

Note: step "B requests instant after funding" must be validated against `IdleCDOEpochVariant.requestWithdraw`'s instant-path gating (`disableInstantWithdraw`/`allowInstantWithdraw`), which I could not fully confirm from the indexed excerpts; if that path is blocked post-funding, the exploit window closes.
